## 回答

# 基于「Harness Engineering + 细分领域知识」的一个具体实例与最佳实践

## 先说结论

基于你提供的内容，一个非常现实的判断是：

- 今年被大幅 “通关” 的，不一定是所有软件工程能力，而是大量 “有明确输入、明确流程、明确验收标准” 的应用开发工作。
- 真正拉开差距的，不只是会用 Coding Agent，而是能不能把 Agent 装进一套稳定的`Harness`里。
- 短期最有价值的组合，确实是：`Harness Engineering 能力 + 行业 / 场景知识 + 可验证交付流程`。
- 单靠 “让 Agent 自由发挥” 很难形成稳定生产力，最后往往会像评论里说的那样：因为不稳定，只能 “固化成 Python 流程”。

---

## 一个具体实例

### 场景：做一个 “电商客服质检与知识库助手”

假设你在一个中型电商团队，目标是开发一个内部应用，解决两个问题：

1. 自动抽检客服聊天记录，识别高风险对话  
2. 基于公司知识库，辅助生成标准化回复建议

这是一个非常适合 Harness Engineering 的场景，因为它有：

- 明确输入：聊天记录、订单信息、售后规则、FAQ
- 明确输出：风险标签、问题分类、回复建议、人工复核结果
- 明确验收：准确率、误报率、平均处理时长、人工采纳率

---

## 为什么这个例子适合用 Harness Engineering

因为它不是 “让模型写点代码” 这么简单，而是一个典型的 “Agent 能做很多，但必须被流程约束” 的问题。

如果直接把需求扔给 Agent，常见问题会是：

- 分类口径不一致
- 回复建议风格漂移
- 同样案例多次执行结果不同
- 规则更新后，旧流程失效
- 出错时难以定位是 Prompt、工具、模型还是数据问题

所以真正高价值的，不是 “AI 会不会”，而是你能不能把它变成：

- 可重复执行
- 可观测
- 可评估
- 可回滚
- 可持续优化

这就是 Harness Engineering 的核心。

---

## 这个实例的一套推荐架构

```text
数据输入层
  -> 聊天记录 / 订单信息 / 商品信息 / 售后规则 / FAQ

预处理层
  -> 数据脱敏
  -> 对话切分
  -> 关键字段提取
  -> 案例标准化

任务编排层（Harness）
  -> Step 1: 问题识别
  -> Step 2: 风险分类
  -> Step 3: 检索知识库
  -> Step 4: 生成回复建议
  -> Step 5: 规则校验
  -> Step 6: 输出结构化结果

验证层
  -> 自动评分
  -> 规则校验
  -> 人工抽检
  -> 历史基准集对比

交付层
  -> 客服工作台展示
  -> 质检后台报表
  -> 反馈数据回流
```

这里的关键是：`模型只是其中一个组件，Harness 才是生产系统本体。`

---

## 具体到这个实例的最佳实践

## 1. 先拆 “任务流”，不要先堆模型能力

很多团队一上来会问：

- 用哪个模型？
- 要不要多 Agent？
- 要不要 computer use？

但在这个例子里，更重要的是先把任务拆成稳定步骤，而不是让一个大 Agent 一把梭。

### 推荐拆法

- `识别用户诉求`
- `判断是否涉及退款 / 投诉 / 违规承诺`
- `从知识库检索相关规则`
- `生成候选回复`
- `用规则引擎做二次校验`
- `输出 “建议回复 + 依据 + 风险标签”`

### 最佳实践

- 每一步只解决一个明确问题
- 步骤之间传递结构化字段，而不是长文本自由发挥
- 把 “判断” 和 “生成” 分开，降低误差叠加
- 能用规则解决的，不交给模型

一句话：`先做可控的流水线，再考虑智能性。`

---

## 2. 输出必须结构化，禁止 “只看自然语言答案”

比如不要让模型直接输出：

> 这段对话可能有售后风险，建议客服安抚用户并说明规则。

而要输出成：

```json
{
  "intent": "退款咨询",
  "risk_level": "high",
  "risk_types": ["超范围承诺", "情绪升级"],
  "policy_refs": ["refund_rule_3.2", "service_tone_1.4"],
  "suggested_reply": "非常抱歉给您带来不便，根据当前订单状态……",
  "need_human_review": true
}
```

### 最佳实践

- 强制 JSON 或 schema 输出
- 每个字段都有枚举值或格式约束
- 把 “结论” 和 “依据” 一起输出
- 给前端、日志、评测系统统一消费格式

这样做的好处是：

- 易评测
- 易追踪
- 易统计
- 易接入业务系统

---

## 3. 不要把 “知识” 只写在 Prompt 里

你提供的评论里提到一个很关键的问题：Skill 不稳定，所以很多人最后改成 Python 流固定下来。  
这件事本质上说明：`隐式能力不如显式流程稳定。`

在这个客服质检例子里，不要把售后规则全塞进 Prompt，而应该分层：

### 正确做法

- 稳定规则：写成代码或规则配置
- 常变知识：放到可更新知识库
- 模型职责：做理解、归纳、生成，不做最终制度解释

### 举例

- “7 天无理由” 适用条件：规则引擎判断
- “用户当前情绪是否升级”：模型判断
- “该给出怎样的礼貌回复”：模型生成
- “回复是否违反公司承诺边界”：规则校验

### 最佳实践

- `规则`与`生成`解耦
- 高频变化内容做成知识源，不要硬编码在 Prompt
- Prompt 只定义任务、风格、边界，不承担全部业务逻辑

---

## 4. 设计 “可回放” 的 Harness

真正能形成壁垒的，不是某次跑通，而是每次都能复现。

所以这个系统必须支持：

- 输入样本回放
- 中间步骤日志
- 模型版本记录
- Prompt 版本记录
- 工具调用记录
- 最终结果比对

### 一个理想的记录单元

```json
{
  "case_id": "cs_2025_0812_001",
  "model_version": "gpt-x-yyy",
  "prompt_version": "risk_v12",
  "kb_version": "faq_2025_08_10",
  "workflow_version": "review_flow_v7",
  "inputs": {},
  "intermediate_outputs": {},
  "final_output": {},
  "human_label": {},
  "metrics": {}
}
```

### 最佳实践

- 每个线上结果都能被完整回放
- 每次改 Prompt、规则、模型，都能跑回归集
- 线上问题先定位是哪一层坏了，再修

没有可回放能力，就没有真正的工程化优化。

---

## 5. 先做 “小闭环高价值”，不要追求 “大而全多 Agent”

你给的内容里提到了：

- Skills 管理
- 多 Agent 管理
- 手机控制
- computer use

这些都很前沿，但在业务落地时，最容易踩的坑就是：  
`为复杂而复杂。`

对于这个客服助手，第一阶段最值得做的，不是多 Agent 协作，而是一个小闭环：

### 第一阶段目标

- 只覆盖 “退款 / 投诉” 两类高频场景
- 只做 “风险识别 + 建议回复”
- 只接一个客服后台页面
- 先让人工点击 “采纳 / 修改 / 驳回”

### 最佳实践

- 从高频、高损失、高标准化场景切入
- 优先解决 20% 场景里最贵的问题
- 人在环（Human-in-the-loop）作为默认机制
- 不追求自动化率，先追求有效率和可接受率

这类项目，`先把一个垂直切口做到 10x`，远比 “做一个看起来无所不能的平台” 更重要。

---

## 6. 用评测集驱动优化，而不是凭感觉调 Prompt

这是最关键的一条。

如果没有评测集，所谓优化通常只是：

- 今天看起来不错
- 明天换个案例又不行
- 团队里每个人都靠主观印象判断

### 在这个实例里，评测集应该怎么建

至少准备 3 类数据：

- `黄金集`：人工标注、用于核心回归
- `真实线上集`：每天抽样回流
- `对抗集`：故意放边界模糊、话术复杂、规则冲突案例

### 核心指标

- 风险识别准确率
- 高风险漏报率
- 建议回复采纳率
- 平均处理时长下降比例
- 人工二次修改率
- 用户投诉率变化

### 最佳实践

- 每次改动都必须过回归评测
- 不只看总分，要看细分场景分布
- 对高风险类别设置单独门槛
- 线上指标和离线指标要打通

工程上最危险的事，就是 “模型好像变聪明了”，但没人知道它是不是在关键场景退化了。

---

## 7. 为 “不稳定” 预留兜底机制

评论里有人说 Skill 不稳定，这几乎是所有 Agent 系统都会遇到的现实。

所以你在这个例子里必须假设：

- 模型偶尔答非所问
- 检索偶尔召回错误
- 结构化输出偶尔失败
- 工具调用偶尔超时
- 某些边界案例判断飘忽

### 兜底设计

- JSON 解析失败就重试一次
- 关键字段缺失则降级到人工处理
- 高风险场景默认人工复核
- 检索不到依据时禁止生成确定性结论
- 超时后返回 “辅助摘要” 而不是空白结果

### 最佳实践

- 把失败视为常态，而不是异常
- 所有关键节点都有降级路径
- 先保证系统 “不会乱来”，再追求 “更聪明”

一个能稳定给出 80 分结果的系统，通常比偶尔 95 分、偶尔翻车的系统更有商业价值。

---

## 8. 把人工反馈直接设计成训练资产

这个例子里，客服主管和质检员的反馈极其宝贵，不应只是 “看过了”，而应变成系统资产。

### 可采集的反馈

- 是否采纳建议回复
- 修改了哪些句子
- 风险标签是否正确
- 是否缺少关键政策依据
- 哪类案例最容易错

### 最佳实践

- 每次人工修改都结构化记录
- 把 “驳回原因” 做成标准标签
- 用反馈反推 Prompt、规则和知识库缺陷
- 建立 “错误案例池”，反复回归

长期看，最有价值的不是模型本身，而是你积累的：

- 真实业务数据
- 错误分布认知
- 调优方法论
- 评测体系
- 工作流资产

这就是细分领域壁垒。

---

## 9. computer use 要谨慎用在 “验收”，不要滥用在 “主流程”

你提供的内容里提到 computer use，这很有潜力，但最佳实践不是把它塞到每个流程里。

在这个客服系统里，它更适合做：

- 自动打开测试环境
- 模拟客服点选工单
- 验证回复是否正常展示
- 检查表单联动和按钮流程
- 截图留档做回归对比

而不是让它成为主业务逻辑的一部分。

### 最佳实践

- `computer use`用于 UI 验收和端到端验证
- 核心业务判断仍放在可控 API / 规则链路里
- GUI 自动化只做 “最后一公里确认”，不做事实来源

这样能兼顾自动化能力和系统稳定性。

---

## 10. 团队分工要从 “写功能” 转向 “设计系统约束”

在这种趋势下，团队里最值钱的人，未必是最会手写每一行业务代码的人，而是最会定义下面这些东西的人：

- 任务拆分方式
- Agent 边界
- 工具协议
- 评测标准
- 数据回流机制
- 风险兜底策略

### 在这个例子里的关键角色

- `业务专家`：定义客服规则、场景优先级
- `Harness 工程师`：设计工作流、状态流转、回放能力
- `应用工程师`：接前后端、权限、日志、集成
- `评测负责人`：建设基准集和指标系统

### 最佳实践

- 不要把 Agent 项目当成 “Prompt 外包”
- 核心竞争力在流程设计和验收体系
- 让业务专家深度参与标注与验收，而不只是提需求

---

## 一套可落地的方法论

如果把这个实例总结成一个最实用的方法论，可以是：

### 第一步：选场景

选同时满足这 4 条的场景：

- 高重复
- 高成本
- 有规则
- 可评估

### 第二步：先搭 Harness，不先赌模型

优先做：

- 输入标准化
- 步骤拆分
- 结构化输出
- 日志与回放
- 回归评测

### 第三步：让人参与最后决策

先默认：

- AI 提建议
- 人工做确认
- 反馈自动回流

### 第四步：用数据迭代，不靠体感

持续跟踪：

- 哪些案例错得最多
- 哪些规则最常冲突
- 哪些输出最常被改写
- 哪些步骤最不稳定

---

## 最后的判断

基于你给的这段内容，我会把 “最佳实践” 浓缩成一句话：

> 不要把 AI 应用开发理解成 “让 Agent 替你写软件”，而要理解成 “把模型能力装配进一套可验证、可回放、可迭代的 Harness 系统里”。

在这个意义上，真正先吃到红利的人，通常不是 “最先用上 Agent 的人”，而是最先把`Agent -> Workflow -> Evaluation -> Feedback`这条链路打通的人。

## 可直接复用的实践清单

```markdown
- 从高频、规则清晰、可评估的垂直场景切入

- 所有关键输出结构化，禁止只返回自然语言
- 把业务规则写进代码 / 配置，不要全塞进 Prompt

- 默认设计失败兜底和人工接管机制
- 把人工修改与驳回原因沉淀为训练资产
- computer use 用于验收，不滥用在核心业务判断
- 团队核心能力从 “写功能” 升级为 “设计 Harness 与评测系统”
```
