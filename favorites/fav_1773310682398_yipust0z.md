下面给你一个**具体实例**，并基于该实例提炼出**最佳实践**。

## 实例：产品团队要回答  
**“当前 roadmap 上有哪些功能，可能与既有决策冲突？”**

### 错误做法：全放 Markdown / 文件夹
例如：

```txt
company/
  strategy/
  decisions/
  projects/product-alpha/features/
  meetings/
  research/
```

表面上看很清晰，但一旦要回答：

- 哪个功能关联了哪些决策？
- 哪些决策已经被后续决策覆盖？
- 哪些结论只是会议纪要里的猜测，不是正式决定？
- Google Doc 更新后，哪些摘要、哪些结论需要重算？

就会变成：

- 到处 grep / 全文搜索
- 靠 wikilink 猜关系
- 靠标签区分 “正式 / 非正式”
- 靠人工或 agent 反复维护副本

结果是：**能读，不能治理；能遍历，不能校验；能链接，不能持续保持真相一致。**

## 最佳实践：三层架构

### 1）源系统层：只认原始事实
来源包括：

- Google Docs：策略文档
- Slack：讨论与决策上下文
- Jira / Linear：roadmap、feature、issue
- CRM：客户反馈
- Notion：会议纪要

**原则**：  
不要把这些原文 “复制” 成另一个 markdown 事实库，而是保存**源链接 / 源 ID**。

---

### 2）数据库层：存 “结构化上下文图”
把真正需要推理、查询、依赖追踪的内容抽出来，存成结构化记录。

比如核心表：

- `sources`
  - source_id
  - source_type（gdoc/slack/jira/notion）
  - external_id
  - updated_at

- `decisions`
  - decision_id
  - title
  - status（proposed/active/superseded）
  - owner
  - effective_date
  - supersedes_decision_id
  - source_id

- `features`
  - feature_id
  - name
  - roadmap_status
  - owner
  - source_id

- `decision_feature_links`
  - decision_id
  - feature_id
  - relation_type（supports/conflicts_with/constraints）

- `claims`
  - claim_id
  - subject
  - predicate
  - object
  - confidence
  - claim_type（fact/inference/speculation）
  - source_id

- `derivations`
  - derived_entity_id
  - derived_from_source_id
  - extraction_method
  - last_verified_at

这样一来，系统能明确知道：

- 什么是**正式决策**
- 什么只是**会议里的观点**
- 什么已经**失效**
- 某条知识是从哪里抽取出来的
- 上游变化后，哪些下游需要重新评估

---

### 3）文件层：只放 “给 agent 的工作说明”
文件依然有价值，但用途要变：

适合放：

- SOP
- 提示词模板
- 分析框架
- agent scratchpad
- 团队约定的操作手册

不适合放：

- 作为唯一事实源的结构化业务知识
- 大量需要跨实体查询和更新传播的关系数据

**一句话**：  
**文件用于引导，数据库用于记忆，业务系统用于存真相。**

## 这个实例下的最佳实践（精炼）

### 1. 不复制真相，只保存指针
把 Google Doc、Slack、Jira 的**URL/ID**存进数据库，而不是复制出一份 markdown 摘要当主记录。  
**好处**：避免双份内容漂移。

### 2. 先建 “类型”，再建 “链接”
至少区分：

- decision
- feature
- source
- claim
- owner
- dependency

再定义关系：

- supports
- conflicts_with
- derived_from
- supersedes
- owned_by

**好处**：agent 看到的不只是文本，而是 “这是什么、和谁什么关系”。

### 3. 区分 “权威性” 和 “时效性”
每条记录必须有：

- status（active /superseded/draft）
- owner
- source
- updated_at
- confidence /authority_level

**好处**：避免把猜测、纪要、正式决策混成一类。

### 4. 所有派生知识都要记录 provenance
任何摘要、结论、标签、冲突判断，都记录：

- derived_from 哪个 source
- 何时生成
- 用什么规则 /agent 生成
- 上游变更后是否需要重算

**好处**：实现 “更新可追踪、错误可回滚”。

### 5. 用数据库回答问题，不用全文搜索硬猜
像 “哪些功能与当前决策冲突” 这种问题，本质是结构化查询，不应依赖 markdown 遍历。  
**好处**：查询稳定、可重复、可自动化。

### 6. 文件系统只做入口，不做知识图本体
保留少量高价值文件：

- onboarding.md
- where-to-look.md
- agent-playbook.md

但不要让目录树承担数据库职责。  
**好处**：避免 “表面简单，实际偷偷重建数据库”。

### 7. 让 agent 维护 ETL，而不是维护副本
agent 的职责应是：

- 从源系统 API 拉取更新
- 抽取结构化实体和关系
- 更新数据库
- 标记受影响的派生结论待重算

而不是：
- 到处改 markdown 副本
- 靠文本同步事实

**好处**：把维护变成 “依赖传播”，不是 “内容搬运”。

---

## 最后总结成一句话
在这个实例里，**最佳实践不是 “把知识整理成更好的文件夹”**，而是：

> **用源系统保存事实，用数据库保存结构、关系和 provenance，用文件给 agent 提供操作入口。**
