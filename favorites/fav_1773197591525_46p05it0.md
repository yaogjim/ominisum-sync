# 智能体软件工程 \#4 ｜ 当 Agent 写完代码，谁来说「可以合并」？

[← 返回总览](../README.md)

## 回答

**主旨概括：**  
这篇文章讨论的是：当 Agent 能自动写大量代码后，传统靠人读 diff 来决定 “能不能合并” 的方式已经不够用了。作者提出用**agent-spec**把 “审查代码” 改成 “先写合约、再让机器验证是否符合合约”，从而建立一个可执行、可追溯的质量门禁。

---

## 一、为什么传统 Code Review 不够用了

- 前两篇文章已指出两个问题：
  - Agent 一天能产出几十个 PR，**人工 Code Review 会崩溃**
  - 多个 Agent 并发工作时，**Git 的心智模型会变成瓶颈**
- 更根本的问题是：
  - **代码写完后、合并前，缺少一个确定性的机器质量门禁**
- 传统流程的问题：
  - 人类 reviewer 要读几百行 diff，靠经验判断 “写得对不对”
  - 这个过程依赖**经验、注意力、时间**，而这些在 Agent 时代都不可扩展
- 单靠 CI 也不够：
  - CI 只能检查 “现有测试是否通过”
  - 但**不能判断 Agent 是否真正实现了任务意图**
- 所以作者提出：
  - **agent-spec 不是更好的 Code Review 工具**
  - 而是换了范式：**从审代码变成审合约，从事后审变成事前定义**

---

## 二、核心思想：把审查点从 “写完后” 前移到 “写之前”

- 传统的人类注意力分配：
  - 写 Issue（10%）→ Agent 编码（0%）→ 读 diff（80%）→ Approve（10%）
- agent-spec 的新分配：
  - 写 Contract（60%）→ Agent 编码（0%）→ 看 explain 摘要（30%）→ Approve（10%）
- 关键变化：
  - 人不再把大量时间花在 “读代码”
  - 而是把时间花在**定义什么叫做正确**
- 好处：
  - 人类工作从低效的 “猜 Agent 写得对不对”
  - 变成高价值的 “提前定义任务意图、技术决策、边界和验收标准”
- 代码完成后，人类看到的不是大段 diff，而是摘要：
  - 原意图是什么
  - 改了哪些文件
  - 是否超出允许范围
  - 测试是否都通过
- 如果这些都满足，Approve 可能只要**5 秒**

## 三、Task Contract 的四个核心要素

### 1）Intent：任务意图
- 说明 “要做什么、为什么做、在什么上下文做”
- 例子：
  - 在现有认证模块中新增用户注册接口
  - 用户用邮箱 + 密码注册
  - 成功后发送验证邮件
  - 这是用户系统的第一步

### 2）Decisions：已定技术决策
- 不是建议，而是**必须执行的决定**
- 例子：
  - 路由：`POST /api/v1/auth/register`
  - 密码哈希：`bcrypt`，cost factor = **12**
  - 验证 token：`crypto.randomUUID ()`，存数据库，**24 小时**过期
  - 邮件发送：使用现有`EmailService`，**不要新建一个**

### 3）Boundaries：修改边界
- 明确 Agent **能改什么、不能改什么**
- 例子：
  - Allowed Changes：
    - `crates/api/src/auth/**`
    - `crates/api/tests/auth/**`
    - `migrations/`
  - Forbidden：
    - **不要新增依赖**
    - **不要修改现有 login 接口**
- 重点：
  - 不是靠 prompt 里一句 “请不要改别的文件”
  - 而是靠工具**确定性检查**
  - 改了不该改的文件，直接**fail**

### 4）Completion Criteria：完成条件
- 用 BDD 风格写验收场景，并且**直接绑定测试函数**
- 例子：
  - 场景 1：新用户注册成功  
    - 测试：`test_register_returns_201_for_new_user`
    - 结果：返回**201**
  - 场景 2：重复邮箱注册被拒绝  
    - 测试：`test_register_rejects_duplicate_email`
    - 结果：返回**409**
- 作者特别强调：
  - **异常路径场景数量要 ≥ 正常路径**
- 原因：
  - 如果只写 “注册成功返回 201”
  - Agent 可能忽略重复邮箱、密码强度、输入校验等问题
- 额外特点：
  - DSL 同时支持**中文和英文**
  - 方便中文团队直接用母语写规范

## 四、七步工作流：从写 Contract 到最终归档

### 第 1 步：人类写 Contract
- 命令：`agent-spec init ...`
- 人类填写四要素
- 这是最需要专注的阶段，大约占**60%**的人类时间

### 第 2 步：先检查 Contract 质量
- 命令：`agent-spec lint ... --min-score 0.7`
- 内置**8 个 linter**
- 会检查：
  - 模糊动词（如 “处理”“manage”）
  - 没有量化的约束（如 “应该快” 但没写`<200ms`）
  - 不可机械验证的说法（如 “界面要美观”）
  - 非确定性措辞（如 “大约”）
  - 缺少测试绑定
  - 会诱发 Agent 讨好式输出的表达（如 “find all bugs”）
- 若分数低于**0.7**，先改 Contract

### 第 3 步：Agent 读取 Contract 并编码
- Contract 会转成结构化 prompt
- Agent 受到三类约束：
  - Decisions：怎么做
  - Boundaries：能改哪里
  - Completion Criteria：做到什么算完成

### 第 4 步：lifecycle 自动验证 + 自动重试
- 核心命令：`agent-spec lifecycle ...`
- 包含四层验证：
  1. **L1 Structural Verifier**  
     - 检查代码模式  
     - 比如规定禁止`.unwrap ()`，就扫描源码  
     - **零 token 成本，确定性**
  2. **L2 Boundaries Verifier**  
     - 检查改动文件是否超边界  
     - **零 token 成本，确定性**
  3. **L3 Test Verifier**  
     - 运行 Contract 中绑定的测试  
     - 直接验证验收标准是否满足  
     - 这是**最关键的一层**
  4. **L4 AI Verifier**  
     - 处理前三层覆盖不到的问题  
     - 比如竞态、资源泄漏、安全隐患  
     - 只给出**uncertain**，不做确定性裁决
- 如果失败，会生成`failure_summary`
- Agent 据此自动修复并重跑：
  - `Code → lifecycle → FAIL (2/5) → fix → lifecycle → PASS (5/5)`
- 系统还会记录运行日志，比如：
  - “这个 Contract 跑了**3 次**才通过”

### 第 5 步：guard 门禁
- 用于 pre-commit 或 CI
- 对所有 spec 统一跑 lint + verify
- 有任何一个 spec 不通过：
  - commit 被拦截
  - 或 PR 失败

### 第 6 步：人类做最终 Contract Acceptance
- 命令：`agent-spec explain ...`
- Reviewer 不看 diff，而看执行摘要：
  - 任务意图
  - 技术决策
  - 修改范围
  - 验收结果
- 最后只要回答两个问题：
  1. Contract 定义得对吗？
  2. 验证都通过了吗？
- 两个都 “是”，就可以 Approve

### 第 7 步：stamp 归档
- 把 Contract 和 commit 建立追溯关系
- 以后别人问：
  - “为什么这段代码这么写？”
- 可以直接追溯到当时的 Contract，看见完整意图和决策

## 五、验证结果只有四种，避免 “假通过”

- agent-spec 只允许四种结果：
  - **pass**：确定通过
  - **fail**：确定失败，并附证据
  - **skip**：根本没被验证到
  - **uncertain**：AI 分析了，但无法确定
- 最重要的一条：
  - **skip ≠ pass**
- 只有满足：
  - failed == 0
  - skipped == 0
  - uncertain == 0
- 才算真正通过
- 这比普通工具只给 pass/fail 更诚实：
  - 它明确区分了
    - 已验证通过
    - 明确失败
    - 根本没覆盖
    - 只能概率判断

---

## 六、AI Verifier 的定位：补充，不是假装权威

- AI Verifier 用来补足机械验证无法覆盖的问题：
  - 竞态条件
  - 资源泄漏
  - 隐含安全漏洞
  - 设计合理性
- 但它不会说 “确定通过 / 失败”
- 它永远只输出：
  - **uncertain**
  - 附带结构化分析和置信度
- 两种模式：
  1. **Caller 模式**
     - 外部 Agent（如 Claude Code、Codex）自己读取请求并分析
     - 结果再合并回报告
  2. **Backend 模式**
     - 系统接入独立 AI 后端做分析
- 共同点：
  - AI 的结论是给人类参考的，不直接进入自动判决链

## 七、和 jj 的结合：更顺手，但不是必须

- 作者之前介绍过 jj（Jujutsu）对 Agent 更友好：
  - 一切皆 commit
  - 稳定 change ID
  - 冲突是数据，不阻塞 rebase
  - 有 operation log，便于回退
- agent-spec 可与 jj 自然结合，但**不是强依赖**
- 在 Git 和 jj 中都能工作
- 结合点主要有三个：

### 1）Change Scope：统一发现改动
- Git 下要分别看 staged /unstaged/untracked
- jj 下只需一个`jj diff --name-only`
- 对 BoundariesVerifier 来说，来源不重要，只要能检查 “是否改了不该改的文件” 即可

### 2）Stamp：用 stable change ID 做追踪
- jj 下额外记录：
  - `Spec-Name`
  - `Spec-Passing: true`
  - `Spec-Summary: 4/4 passed`
  - `Spec-Change: kkmpptqz`
- 这里的`kkmpptqz`是 jj 的**stable change ID**
- 优势：
  - 即使 amend 后 commit 内容变了，change ID 仍不变
  - 追溯链不会断

### 3）Run History：比较两次运行间改了什么
- 如果日志里有 jj operation ID
- 可以展示：
  - “上次 fail，这次 pass，中间 Agent 到底改了哪些文件”
- 对排查问题很有用

## 八、agent-spec 不包打天下，而是做 “组合框架”

- 它能保证的是：
  - **代码符合 Contract**
- 但不能单独解决所有代码质量问题，比如：
  - 竞态条件
  - 资源泄漏
  - 抽象设计差
  - 代码风格不统一
- 作者认为这不是缺陷，而是有意为之：
  - 它不想变成一个 “大而全但每样都不够深” 的工具
- 它更像一个编排框架：
  - 把各种工具的输出统一纳入 Contract 验收标准

### 两种组合方式

#### 1）把质量规则写进 Spec
- 例如项目级规则：
  - 禁止`.unwrap ()`、`.expect ()`
  - 禁止`panic!`、`todo!`
  - 金额处理禁止用`f32/f64`
- 这些可由 StructuralVerifier 机械检测

#### 2）把外部工具接入 Completion Criteria
- 例子：
  - `cargo clippy -- -D warnings`必须通过
  - 覆盖率必须**>= 80%**
- 这样 Agent 不只是 “功能对了”
- 还要同时满足静态检查和测试覆盖率要求

## 九、三层 Spec 继承：组织、项目、任务分层管理

- agent-spec 支持三层继承：
  - `org.spec → project.spec → task.spec`
- 各层职责：
  - **org.spec（组织级）**
    - 通用安全和编码规则
    - 例如：禁止硬编码凭证、所有用户输入必须校验
  - **project.spec（项目级）**
    - 项目技术栈和约定
    - 例如：使用 PostgreSQL、统一结构化错误、用`thiserror`
  - **task.spec（任务级）**
    - 单个任务的意图、边界、验收标准
- 优点：
  - 安全团队管组织规范
  - 项目负责人管项目规范
  - 开发者只关注具体任务
- 系统负责自动合并约束和决策

## 十、Skills：不仅给工具，也要教 Agent 怎么用工具

- agent-spec 不只是 CLI，还提供给 Agent 的工作流指南（Skills）
- 安装方式：
  - `npx skills add ZhangHanDong/agent-spec`

### 两类 Skill
1. **agent-spec-tool-first**
   - 教 Agent 按七步流程工作
   - 包括一个重要约束：
     - lifecycle 失败后，应该改代码
     - **不要偷偷改 spec 来让自己通过**
2. **agent-spec-authoring**
   - 教 Agent 怎么写高质量 Contract
   - 包括：
     - 四要素结构
     - 测试绑定格式
     - 双语关键词
     - “异常路径 ≥ 正常路径” 原则

### 多 Agent 适配
- 不只支持 Claude Code
- 也提供：
  - Codex 的`AGENTS.md`
  - Cursor 的`.cursorrules`
  - Aider 的`.aider.conf.yml`
- 核心理念：
  - **CLI-first、Agent-agnostic**
  - 只要能调 shell 命令的 Agent，都能接入

## 十一、真实案例：agent-spec 用自己管理自己

- 作者强调这是一个**self-hosting**的真实循环
- agent-spec 项目自己就有`project.spec`
- 里面规定了自己的开发规则，例如：
  - 公开 CLI 与 gateway 行为必须有回归测试
  - DSL 语法变更必须同步更新 AST、解析输出和回归测试
  - 验证结果必须区分`pass /fail/skip /uncertain`
- 每次提交都经过`agent-spec guard`
- 新功能开发也都有对应的`task spec`
- 甚至`specs/roadmap/`下的 Phase 0 ~ Phase 6 路线图，都是按 agent-spec 的 Contract 格式写的
- 作者观点很明确：
  - **如果 agent-spec 不能用来管理自己，就没资格管理别的项目**

## 十二、当前能力与已知限制

### 目前最强的适用场景
- Contract 能通过以下方式验证：
  - 显式测试
  - 代码模式匹配
  - 边界路径检查
  - staged 或显式变更集上的验证

### 目前限制
- **TestVerifier 目前偏 Rust/Cargo**
  - 通过`cargo test`执行
  - 非 Rust 项目可用 Contract 和 Boundaries，但测试执行要自行扩展
- **AI Verifier 真实后端还没完全接入**
  - 当前可用 stub 和 caller 模式
- **对抗式多 Agent 验证**（如 Bug Finder / Skeptic / Referee）
  - 目前只是预留能力
- **继承机制暂不完整**
  - 目前 Resolver 只继承`Constraints`和`Decisions`
  - **不继承 Boundaries**
  - 例如 project.spec 中定义的禁止目录，task.spec 不会自动继承

## 一句话总结

**作者的核心观点是：在 Agent 时代，真正可扩展的 “可合并判断” 不应该靠人读代码，而应该靠人先写清楚任务合约，再由机器分层验证；人类最终只审 “合约是否合理、验证是否通过”。**
