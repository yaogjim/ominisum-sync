- 避免从零自研通用 Agent Harness，优先基于成熟平台构建垂直场景解决方案。

## 解读（1）

### 2026-06-02 07:43:49

##### 1. 总结

宝玉的核心观点：

> **不要再卷 Agent Harness（智能体底层框架）了，价值不大。**  
> 因为这类基础设施模型公司更强、迭代更快，小团队很难赢。

但机会仍然很大：

> **基于成熟 Agent Harness，去做垂直行业解决方案，才有价值。**

原因是：

- **MCP** 主要解决“连接工具/系统”的问题
- **Skills** 主要解决“领域知识”的问题
- 但真实业务里还需要：
  - 重新设计 AI 原生工作流
  - 设计人机协作界面
  - 整理高质量行业数据
  - 适配具体业务场景

结论：

> **模型公司做底座，创业者/团队做应用。**  
> Agent 可能成为未来的“操作系统”。

---

##### 2. 解读

简单说：

###### 不要造“发动机”，要造“车”

Agent Harness 就像发动机、底盘。

这些东西：

- 技术门槛高
- 更新太快
- 巨头资源更多
- 模型一升级，很多自研工作可能失效

所以小团队硬做底层，很容易白忙。

---

###### 真正的机会在“行业落地”

比如：

- 医疗里的初步分诊
- 法律里的合同初审
- 电商里的客服处理
- 教育里的作业批改
- 金融里的材料审核
- 企业里的报销、审批、招聘筛选

这些地方不是简单接个大模型就行。

难点在于：

> 怎么让 AI 真正嵌进业务流程，并且让人愿意用、用得顺。

这需要懂行业、懂流程、懂产品。

---

###### 不能把旧流程直接套给 Agent

一个重要提醒是：

> 不要把原来的表单、审批、系统字段，原封不动接给 Agent。

这样只是多了一个“聊天壳”，没有真正提升效率。

更好的切入点是：

- 人需要反复判断的环节
- 规则不完全固定的环节
- 需要生成初稿的环节
- 需要匹配、分类、审核的环节

这些地方，Agent 更容易产生价值。

---

##### 3. 我的意见

我认同这个判断。

未来 AI 创业的重点，不是“我也做一个 Agent 框架”，而是：

> **我能不能用现成 AI 能力，解决一个真实、具体、愿意付费的问题。**

更值得做的是：

- 找一个细分场景
- 深入理解业务流程
- 改造人机协作方式
- 积累行业数据
- 做出用户真的离不开的产品

一句话：

> **底层拼不过巨头，应用才是机会。**  
> **谁更懂场景，谁更有价值。**

## 结构化（1）

### 2026-06-02 07:55:03

##### 主旨概括

宝玉认为，**再去做通用的 Agent Harness（智能体运行框架）价值已经不大**，因为很难竞争过模型公司，而且模型一升级，很多自研工作可能就失效。真正有机会的是：**基于成熟的 Agent Harness，面向具体行业和业务场景做 AI 原生方案和应用落地**。

---

##### 1. 通用 Agent Harness 不适合小团队继续投入

原文核心观点是：  
做 Agent Harness 这种底层框架，已经越来越像模型公司的事情。

关键原因包括：

- **模型公司更有资源和能力**：模型、工具链、算力、Token 资源都更充足。
- **迭代速度太快**：小团队很难跟上 Harness 的更新节奏。
- **模型升级会让很多工作白做**：底层能力一变，原来围绕旧模型做的优化可能失效。

热门回复中也有人补充：  
> Harness 迭代速度太快，小 team 根本跟不上。  
宝玉也回应：  
> 是的，完全跟不上，顶级团队还有无限量 token。

---

##### 2. 更有价值的是基于成熟 Harness 做具体方案

宝玉认为，虽然通用 Agent Harness 价值下降，但**在成熟 Harness 之上做垂直领域解决方案，仍然大有可为**。

可以理解为：

- 模型公司负责提供“地基”：模型、Agent Harness、基础能力。
- 其他团队负责在上面“盖房子”：做具体行业应用、工作流改造、用户体验和业务落地。

Ray 的回复总结得很直接：  
> 基础设施别跟巨头抢，在巨头搭好的地基上盖房子才是正经事。

---

##### 3. MCP 和 Skills 只解决了部分问题

宝玉提到：

- **MCP 只是解决连接问题**  
  也就是让 Agent 能接入各种工具、系统、数据源。

- **Skills 只是解决领域知识问题**  
  也就是让 Agent 掌握某些专业能力或知识。

但真实业务落地远不止这些。  
一个 Agent 能“连接工具”、懂一些“专业知识”，并不代表它就能顺畅进入企业流程、被真实用户高效使用。

---

##### 4. 垂直领域仍有大量工作要做

宝玉指出，垂直领域还有很多模型公司做不到、也不适合做的事情。

主要包括：

###### 4.1 重构旧工作流，设计 AI Native 的 Agent 工作流

不是把原来的流程原封不动搬给 Agent，而是要重新思考：

- 哪些步骤适合 Agent 参与？
- 哪些节点应该由 AI 先处理？
- 哪些地方仍需要人来判断？
- 原有审批流、表单流、系统字段是否需要重新设计？

热门回复中提到一个关键落地思路：  
不要先把旧流程完整搬进 Agent，而是先找那些“人需要反复判断，但规则又不完全固定”的节点。

例如：

- 审核
- 分诊
- 匹配
- 生成初稿

这些位置更适合 Agent 发挥作用。

很多失败案例并不是 Harness 不行，而是企业只是把原来的表单流、审批流套了一层聊天界面，结果并没有真正提升效率。

---

###### 4.2 重新设计 Human-in-the-Loop 的 UI 和 UX

Agent 并不意味着完全无人参与。  
很多业务场景中，人仍然需要在关键节点介入，比如确认、修正、审批、判断风险。

因此需要重新设计：

- 人什么时候介入？
- 人如何看到 Agent 的判断依据？
- 人如何快速修改 Agent 的输出？
- Agent 如何把复杂信息变成人容易决策的界面？

这部分不是简单做一个聊天框就能解决，而是需要深度结合具体业务。

---

###### 4.3 整理垂直领域的高质量数据

垂直领域的数据往往分散、杂乱、格式不统一。  
要让 Agent 真正好用，需要有人做数据整理和知识沉淀。

包括：

- 行业知识整理
- 历史案例沉淀
- 标准流程归纳
- 高质量标注数据建设
- 企业内部文档结构化

这些“脏活累活”很难标准化，但恰恰是应用能否落地的关键。

---

##### 5. 应用层才是更大的机会

热门回复中有人认为：  
> 做应用才是搞 AI 的终局，降低使用门槛就是未来唯一的大机会。

其中举了一个商业案例：

- 有人做了一个“生成一秒视频”的小程序；
- 每秒视频收费 **0.6 元**；
- 成本约 **0.1 元**；
- 上线第 **5 天赚了 127 万元**。

这个例子说明：  
即使底层技术不是最先进，只要能降低用户使用门槛、满足具体需求，也可能产生很强的商业价值。

---

##### 6. 最终判断：Agent 会成为未来的操作系统

宝玉最后的判断是：

> Agent 是未来的操作系统。

他的意思是：

- 少数模型公司会提供模型和 Agent Harness；
- 这些基础设施会像操作系统一样，成为上层应用的底座；
- 更多团队和创业者应该基于这些底座，构建行业应用和具体解决方案。

换句话说，未来机会不在“重复造操作系统”，而在“基于操作系统做应用生态”。

---

##### 总结

这篇内容的核心判断是：**通用 Agent Harness 已经不适合大多数团队继续投入，底层框架会越来越集中到模型公司手里；真正的机会在垂直领域应用落地。**

具体来说，值得做的是：

- 重构 AI Native 工作流；
- 设计人机协作的 UI/UX；
- 整理行业高质量数据；
- 找到真实业务中适合 Agent 的判断、分诊、匹配、生成等节点；
- 基于模型公司提供的模型和 Harness，做用户真正愿意付费的应用。

#### 核心判断

> **不要再重复造 Agent Harness（智能体底层编排/框架）了，价值会被模型公司快速吞掉；更大的机会在于：基于成熟 Harness，重构具体行业的 AI Native 工作流。**

模型公司会提供模型、工具调用、Agent Harness、长上下文、记忆、多模态、代码执行等底层能力。创业者/产品团队真正值得做的，是把这些能力嵌进真实业务，让它变成用户愿意持续付费的产品、流程和系统。

---

#### 一、启发

##### 1. Agent 的机会不在「再造底座」，而在「业务重构」

过去很多团队会做：

- Agent 框架
- Workflow 编排
- 多 Agent 协作
- 工具调用层
- Memory 系统
- Prompt 管理平台

但这些能力正在快速被模型公司、云厂商、开源框架吸收。你今天做出来的复杂 Harness，可能下个月模型升级后就被原生能力替代。

更值得关注的是：

> **一个行业原来的流程，如何被 Agent 重新设计一遍。**

不是把旧系统接上 AI，而是问：

- 哪些人工判断可以交给 AI？
- 哪些环节需要人机协同？
- 哪些界面不该再是表单，而应该是任务流？
- 哪些数据需要重新整理，才能让 Agent 真正可靠？

---

##### 2. MCP 和 Skills 只是基础，不是终局

文中提到：

- **MCP 解决连接问题**
- **Skills 解决领域知识问题**

但真实业务还缺很多层：

| 层级 | 解决什么问题 |
|---|---|
| MCP | 连接工具、系统、数据库 |
| Skills | 让 Agent 具备领域知识和操作能力 |
| Workflow | 决定 Agent 在业务中怎么流转 |
| Human-in-the-loop | 决定人什么时候介入、怎么介入 |
| UI/UX | 决定用户是否真的愿意使用 |
| Data | 决定结果是否稳定、可控、可复用 |
| Governance | 决定风险、权限、审计、合规 |

真正的商业价值，更多出现在后五层。

---

##### 3. 垂直领域不是没机会，而是不能只做「聊天壳」

很多失败的垂直 Agent，本质上只是：

> 旧流程 + ChatGPT 界面 + 一些工具调用

这并没有改变业务效率。

真正有价值的 Agent 产品，不是「让用户和系统聊天」，而是：

- 帮用户完成任务
- 帮用户减少判断
- 帮用户生成可交付物
- 帮组织沉淀数据
- 帮团队重构协作方式

---

#### 二、高价值信息深挖

##### 1. 为什么 Agent Harness 价值变低？

原因有四个：

###### ① 模型公司天然有优势

模型公司拥有：

- 最新模型能力
- 无限 Token 资源
- 一手推理优化能力
- 原生工具调用能力
- 更强的上下文、记忆、多模态能力
- 大量开发者反馈

小团队做 Harness，很难跟上节奏。

---

###### ② 模型升级会直接抹平中间层价值

很多 Agent 框架曾经解决的问题，例如：

- 复杂 Prompt 分解
- 多步推理
- 工具选择
- 错误恢复
- 任务规划
- 代码执行
- 文件解析

未来会越来越多被模型原生能力吸收。

所以风险是：

> 你辛苦做的工程优化，可能只是模型暂时不够强时的补丁。

---

###### ③ Harness 很难形成持久差异化

如果你的产品卖点是：

- 我能调多个工具
- 我能编排多个 Agent
- 我有记忆
- 我有任务规划
- 我有插件系统

这些都很容易被复制，且用户未必关心。

用户真正关心的是：

- 我的合同能不能更快审完？
- 我的客服能不能少招人？
- 我的销售线索能不能更准？
- 我的财务报表能不能自动生成？
- 我的审核准确率能不能提高？
- 我的员工培训成本能不能下降？

---

##### 2. 真正的大机会：Agent Native Workflow

文章里最重要的观点是：

> **不是把旧工作流搬进 Agent，而是重新设计适合 Agent 的工作流。**

这点非常关键。

很多公司做 AI 改造，会犯一个错误：

- 原来是表单流
- 原来是审批流
- 原来是字段录入
- 原来是人工复制粘贴
- 原来是层层转交

然后他们只是把这些流程接给 Agent。

结果只是：

> 多了一个聊天入口，但流程本身没有变。

真正的 AI Native 工作流应该从任务本身重构。

例如：

###### 传统流程

用户填写表单 → 系统校验 → 人工审核 → 主管复核 → 输出结果

###### AI Native 流程

Agent 读取上下文 → 自动补全信息 → 识别风险点 → 生成判断建议 → 人只处理高风险/不确定部分 → 系统自动沉淀案例

这不是「加 AI」，而是「重写流程」。

---

##### 3. 适合 Agent 切入的节点

引用回复里有一个高价值判断：

> 不要先完整搬旧流程，而是先找「人反复判断但规则不完全固定」的节点。

这类节点最适合 Agent：

- 审核
- 分诊
- 匹配
- 初稿生成
- 信息归类
- 风险识别
- 异常检测
- 客诉处理
- 销售线索评分
- 合同条款初审
- 需求理解与拆解
- 报告生成
- 内容质检

这些任务的共同特点是：

| 特征 | 说明 |
|---|---|
| 高频 | 每天大量重复发生 |
| 半结构化 | 有规则，但不能完全写死 |
| 依赖上下文 | 需要理解文本、历史、语境 |
| 人工成本高 | 需要熟练员工判断 |
| 可人机协同 | AI 先处理，人做确认 |
| 结果可反馈 | 可以持续积累数据 |

---

#### 三、可迁移清单

##### 1. 判断一个 Agent 机会是否值得做

可以用这份清单筛选：

###### 任务层面

- [ ] 是否是高频任务？
- [ ] 是否存在大量重复判断？
- [ ] 是否规则不完全固定？
- [ ] 是否需要理解文本、图片、语音、表格等上下文？
- [ ] 是否现在由人通过经验完成？
- [ ] 是否可以先让 AI 做初稿/初判？
- [ ] 是否可以通过人类反馈持续改进？

###### 商业层面

- [ ] 是否能直接节省人力成本？
- [ ] 是否能提升收入转化？
- [ ] 是否能缩短交付周期？
- [ ] 是否能降低错误率？
- [ ] 是否有清晰付费方？
- [ ] 是否结果可以被量化？
- [ ] 是否客户有强烈痛点，而不是尝鲜需求？

###### 数据层面

- [ ] 是否有历史数据？
- [ ] 是否有标准样例？
- [ ] 是否有专家判断记录？
- [ ] 是否能收集用户反馈？
- [ ] 是否能形成行业数据壁垒？
- [ ] 是否能把隐性知识显性化？

###### 产品层面

- [ ] 是否不只是聊天界面？
- [ ] 是否嵌入现有工作流？
- [ ] 是否能让用户少操作，而不是多操作？
- [ ] 是否设计了人类确认环节？
- [ ] 是否有权限、审计、追溯机制？
- [ ] 是否能处理异常情况？

---

##### 2. Agent 产品设计清单

###### Step 1：找节点，不找完整流程

不要一开始就说：

> 我要做一个完整的 XX 行业 Agent。

而是先找一个具体节点：

- 客服质检
- 合同初审
- 简历筛选
- 病历摘要
- 销售跟进建议
- 采购报价比对
- 财务凭证核对
- 内容审核分诊

---

###### Step 2：判断 AI 的角色

Agent 不一定要完全自动化，可以是：

| 角色 | 适用场景 |
|---|---|
| Copilot | 辅助人完成任务 |
| Reviewer | 检查错误和风险 |
| Generator | 生成初稿、报告、方案 |
| Router | 分诊、分类、派单 |
| Analyst | 汇总、分析、提炼 |
| Operator | 执行工具操作 |
| Monitor | 监控异常并提醒 |

多数场景下，先从 **Copilot / Reviewer / Router / Generator** 做起，比直接做全自动 Agent 更现实。

---

###### Step 3：设计 Human-in-the-loop

要明确：

- 人什么时候介入？
- 人是确认、修改还是驳回？
- AI 的置信度如何展示？
- 哪些情况必须升级给人？
- 人的反馈如何进入系统？
- 错误结果如何追溯？

一个好 Agent 产品，不是消灭人，而是让人只处理高价值判断。

---

###### Step 4：构建数据闭环

高价值垂直 Agent 的护城河往往不是模型，而是数据。

需要沉淀：

- 标准案例
- 专家决策
- 用户修改记录
- 错误原因
- 高风险样本
- 行业术语
- 流程规则
- 交付模板

长期看，这些会变成行业知识资产。

---

#### 四、反方与张力

##### 1. 反方：Agent Harness 真的完全没价值了吗？

不一定。

在以下场景，做 Harness 仍然可能有价值：

- 企业内部需要私有化部署
- 对合规、审计、安全要求极高
- 行业工具链非常复杂
- 多模型调度成本很高
- 需要跨系统稳定编排
- 对延迟、成本、可靠性有强约束
- 大企业需要统一 Agent 管理平台

但这类机会更像是：

> 企业级中间件 / AI 基础设施，而不是普通创业团队最优切入口。

如果没有极强工程能力、客户资源和资金，不建议把 Harness 当主战场。

---

##### 2. 张力：做应用容易被模型公司吞掉吗？

也有风险。

如果你的应用只是：

- 套壳聊天
- 简单 Prompt
- 简单生成内容
- 没有业务系统集成
- 没有数据壁垒
- 没有工作流重构
- 没有用户粘性

那同样会被模型公司或大平台吞掉。

所以应用层也必须向下扎：

> **从功能应用，变成业务系统。**

真正不容易被吞掉的是：

- 深入行业流程
- 掌握客户数据
- 绑定组织协作
- 承担业务结果
- 有交付和运营能力
- 嵌入企业权限、审计、合规体系
- 能持续沉淀行业专有知识

---

##### 3. 张力：降低门槛 vs 构建壁垒

热门回复里提到一个小程序「生成一秒视频收费 0.6 元，成本 0.1 元，上线第五天赚 127 万」。

这说明：

> 低门槛消费级 AI 应用仍然可能爆发。

但它和垂直 Agent 是两类机会：

| 类型 | 优势 | 风险 |
|---|---|---|
| 低门槛 AI 应用 | 起量快、验证快、现金流快 | 容易被复制，生命周期短 |
| 垂直 Agent 系统 | 壁垒更高、客户价值深 | 销售慢、交付重、周期长 |

两者都能做，但打法不同：

- 想快速赚钱：做轻应用、流量、体验、分发
- 想长期壁垒：做垂直流程、数据、系统、客户成功

---

#### 五、情境化落地

##### 1. 如果你是 AI 创业者

建议不要问：

> 我能做一个什么 Agent？

而要问：

> 哪个行业里，有一批人每天在做大量重复判断，而且结果可以被 AI 先处理？

可优先寻找这些场景：

- 法务：合同审查、条款风险识别
- 医疗：病历摘要、问诊分诊、报告解读
- 教育：作业批改、学习诊断、教案生成
- 招聘：简历筛选、面试纪要、候选人匹配
- 销售：线索评分、客户跟进、话术生成
- 财务：凭证核对、报销审核、异常检测
- 保险：理赔初审、材料核验、风险评估
- 电商：客服分诊、评价分析、商品文案生成
- 内容：审核分流、选题策划、爆款分析
- 制造：故障诊断、工单分派、质检报告

切入点要小，价值要硬。

---

##### 2. 如果你是企业产品负责人

不要一上来做「企业级 AI Agent 平台」。

更好的路径是：

###### 第一阶段：找一个高频痛点

例如：

- 客服每天要处理 5000 条咨询
- 法务每周要审 200 份合同
- 销售每天要写大量跟进记录
- HR 每月要筛几千份简历
- 财务每周要核对大量单据

---

###### 第二阶段：让 AI 做初稿/初判

不要追求 100% 自动化。

先让 AI 做：

- 摘要
- 分类
- 初审
- 推荐
- 风险提示
- 下一步建议

人负责最终判断。

---

###### 第三阶段：设计反馈闭环

每次人工修改都要记录：

- AI 哪里错了？
- 人为什么改？
- 哪类样本容易出错？
- 哪些规则需要补充？
- 哪些案例可以沉淀为模板？

这一步决定系统能否越用越好。

---

##### 3. 如果你是独立开发者/小团队

不建议投入大量时间做通用 Agent 框架。

更适合的方向：

- 找一个窄场景
- 用成熟模型和现成 Harness
- 快速做出可用产品
- 用 UI/UX 降低使用门槛
- 通过分发和定价快速验证
- 再逐步沉淀数据和流程

你的优势不是和 OpenAI、Anthropic、Google 拼底层，而是：

> 更快理解一个具体人群的真实需求，并把 AI 包装成他们愿意付费的体验。

---

#### 六、最终提炼

##### 一句话总结

> **Agent 底座会被模型公司平台化，真正的机会在于基于底座重构垂直行业的工作流、交互和数据闭环。**

##### 最值得记住的 5 点

1. **不要和模型公司抢 Harness，去做基于 Harness 的业务系统。**
2. **MCP 解决连接，Skills 解决知识，但真正难的是工作流、交互、数据和人机协同。**
3. **不要把旧流程套上聊天壳，要重构 AI Native 工作流。**
4. **优先寻找「人反复判断但规则不完全固定」的业务节点。**
5. **长期壁垒来自行业数据、流程嵌入、客户协作和结果交付，而不是 Prompt 或框架。**
