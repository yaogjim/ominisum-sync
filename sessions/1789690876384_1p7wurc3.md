## 分析要点

- **核心高价值点**：定位出预构建协调器失败源于AOT导出时固化的SM数量，并指出不能简单移除检查，而应在RTX 5090上重新构建以同步生成启动网格和集群限制。
- **留存建议**：建议精读并存档，作为异构GPU推理部署、硬件适配和上线前检查的专项参考（包含完整的构建、探测、预检、启动和回滚路径，并记录了AOT硬件适配门槛、资源约束及实测运行点。）

**知识要点**

- AOT生成的GPU内核可能固化SM数量；硬件更换后，设备校验、启动网格和集群限制必须一起重新生成。
- 同一部署可通过容量参数在预填充吞吐与KV池规模之间取舍，而文中两个运行点的解码速度基本相近。
- 分布式推理上线可按构建、离线就绪探测、跨节点只读预检、工作节点优先启动、协调器启动和验证回滚的顺序执行。

**行动项**

- 先核对GPU、主机内存、模型分片、镜像版本、RDMA设备和各节点可用内存是否满足前置条件。
- 在实际启动前依次运行本机构建、就绪探测和带JSON输出的只读预检，并先使用默认干运行检查Docker命令。
- 根据预填充吞吐或KV容量目标选择运行点，并补跑同提示、同基准的TP4 vLLM对照测试。

This is a **source-and-configuration research release** for running [tpurtell/ds41rt](https://github.com/tpurtell/ds41rt) — the attention-FFN-disaggregated (AFD) DeepSeek-V4.1-Flash engine — with the **coordinator on a 32 GB RTX 5090** instead of the 96 GB RTX PRO 6000 the upstream release targets. The four DGX Sparks run the unmodified published expert image. It is not a prebuilt image and not a one-command installer; it is what we ran, with our addresses and paths taken out, so you can run it on your own machines.

Measured results (prefill, decode, 1M context, concurrency) are in the public report:**[https://services.turquoisebay.ai/share/dsv41-afd-hybrid/](https://services.turquoisebay.ai/share/dsv41-afd-hybrid/)**

`bench/hostcache/` holds the load generators, reducers, mock server, test suite and bench plan behind the second report in this series, **"Same hardware, double the work: a write-back KV snapshot cache for DS41RT"** ([https://services.turquoisebay.ai/share/ds41rt-hostcache/](https://services.turquoisebay.ai/share/ds41rt-hostcache/)). The cache code is on the engine fork ([https://github.com/hughmadden/ds41rt](https://github.com/hughmadden/ds41rt), branch `hostcache/rc4`). See `bench/hostcache/README.md`.

Path What it is

`scripts/afd-build-coordinator.sh` Rebuilds the coordinator image at the published v1 revision **on the 5090**, so the AOT kernel export reads that GPU's SM count. No source patch.

`scripts/afd-plan-probe.sh` Boots the coordinator with loopback peers (no Sparks) far enough to read the memory planner's line. How the memory matrix in `docs/GATES.md` was measured.

`scripts/afd-ready-probe.sh` Boots to readiness with loopback peers and serves `/health` and `/v1/models`. The last offline gate.

`scripts/afd-preflight.sh` Read-only GO/NO-GO across the coordinator host and all four Sparks (image revisions, AOT SM count, model shards, ports, memory headroom). `--json` available.

`scripts/afd-launch-experts.sh` Starts one expert rank on a Spark. Dry-run by default. Refuses to start without the fabric address and RDMA device.

`scripts/afd-launch-coordinator.sh` Starts the coordinator at the measured operating point. Dry-run by default.

`scripts/afd-launch-fleet.sh` Worker-first bring-up of all four ranks then the coordinator. Dry-run by default.

`scripts/afd-stage-engram-tier.sh` Optional: stage the two Engram shards on a dedicated local device. Formats a device when applied; refuses on partitions or mounts.

`scripts/coordinator-footprint.py` Computes the coordinator-resident weight footprint from the checkpoint's safetensors headers.

`docs/GATES.md` The two findings that decide whether this works: the AOT SM-count gate, and the memory plan on 32 GB. Plus the multi-port RDMA fix.

`docs/SETTINGS.md` The operating point, the pool arithmetic, and the hard constraints.

`docs/RUNBOOK.md` The ordered sequence: build, stage, preflight, launch, verify, roll back.

#### Prerequisites

- **Coordinator host:** x86\_64 Linux, an RTX 5090 (32 GB, compute capability 12.0, 170 SMs), at least 128 GB of host RAM, a local NVMe holding the full DeepSeek-V4.1-Flash checkpoint (48 shards, about 510 GB), Docker with the NVIDIA runtime, and an RDMA-capable NIC on the same RoCE fabric as the Sparks with `/dev/infiniband` exposed.
- **Four DGX Sparks** (GB10, 128 GB unified memory each) on that fabric, each with Docker, the published `ghcr.io/tpurtell/ds41rt-spark-expert:v1` image, and the full checkpoint reachable at a local path (every rank reads its slices out of all 48 shards). About 100 GiB of free unified memory per Spark at launch.
- A checkout of `tpurtell/ds41rt` **with submodules** at the v1 revision `9ea5c96468da690fe7dd01471d4fa2fb8555a606`. Upstream has since published v2; it has not been built or tested on a 5090 by this recipe.

```
# 1. build the coordinator on the 5090 host (the AOT export reads this GPU's SM count)
REPO=/path/to/ds41rt scripts/afd-build-coordinator.sh          # -> ds41rt-coordinator-rtx5090:v1

# 2. prove it fits and boots, with no Sparks involved
MODEL_DIR=/path/to/DeepSeek-V4.1-Flash scripts/afd-ready-probe.sh   # READY in ~4 s

# 3. on each Spark, the expert rank (dry-run first, then --apply), worker-first 3,2,1,0
FABRIC_IP=<spark fabric ip> RDMA_DEVICE=<e.g. rocep1s0f1> scripts/afd-launch-experts.sh <rank> --apply

# 4. the coordinator (capacity 1024 default; BATCH=80 + CAPACITY=256 on the ranks = pool-first point)
PEERS=<ip0>:19441,<ip1>:19441,<ip2>:19441,<ip3>:19441 \
DEVICE_MAP=<coordinator fabric ip>=<coordinator rdma device> \
MODEL_DIR=/path/to/DeepSeek-V4.1-Flash scripts/afd-launch-coordinator.sh --apply
```

Or run `scripts/afd-preflight.sh` first and `scripts/afd-launch-fleet.sh --apply` for all of step 3 and 4. Every launcher prints the exact `docker run` it would execute before it does.

The published coordinator image fails on a 5090 before loading any weights, with CUDA status 101 (`cudaErrorInvalidDevice`). Its native library hard-checks the device's SM count against a constant generated at AOT export time from whichever GPU ran the export: 188 on the RTX PRO 6000, 170 on the 5090. Patching the check out would be unsound, because the same constant sizes the launch grids and cluster limits. Running the vendor's own build on the 5090 regenerates everything for 170 SMs and is the only delta from the published image (`docs/GATES.md`).

A small pull request to upstream that names the expected and observed SM counts in that error is at [hughmadden/ds41rt, branch `sm-count-diagnostic`](https://github.com/hughmadden/ds41rt/tree/sm-count-diagnostic).

- Measured on one fleet, on 2026-09-14 (Sydney), single runs per cell. See the report for the numbers and their caveats.
- Two operating points, one flag pair: prefill capacity 1024 (default; prefill 5,377 tok/s at 170k prompt tokens, 2.5M-token KV pool) or capacity 256 (`BATCH=80` and `CAPACITY=256`; prefill 2,000 tok/s, 7.79M-token pool). Decode is the same at both (74 vs 73.5 tok/s). The widening was suggested by DS41RT's author and measured the same day.
- The like-for-like baseline (the same four Sparks running the reference TP4 vLLM deployment, same prompts, same bench) has not been run yet. The report says so where it matters.
- The Engram dedicated-tier script is optional and was **not** needed for the measured results: the tables were served from ordinary NVMe with host RAM as page cache and no read bottleneck.

## 深度解读（1）

### 2026-09-18 10:17:06

#### 这不是一次“5090 跑大模型”的炫技，而是异构推理系统的可移植性样本

这个项目最有价值的地方，并非宣称 RTX 5090 能运行 DeepSeek-V4.1-Flash，而是具体展示了：**当模型服务被拆成协调器与专家节点后，更换一块 GPU 会在哪些环节失效，又该如何把“能启动”变成可验证、可复现的部署。**

##### 容器并不等于硬件可移植

上游协调器镜像是在 188 个 SM 的 RTX PRO 6000 上生成的，放到只有 170 个 SM 的 5090 上，会在加载权重前直接报 `cudaErrorInvalidDevice`。原因不是普通的兼容性检查，而是 AOT 编译时固化的 SM 数量同时参与了启动网格与集群限制计算。因此，简单删除检查虽然可能绕过报错，却可能让执行配置失真。

作者采取的办法是：不改源码，在 5090 上重新执行上游构建，让相关内核按 170 个 SM 重新导出。这揭示了一个容易被容器化掩盖的问题：**AI 推理制品不仅依赖 CUDA 版本，还可能依赖具体 GPU 拓扑。** 对推理平台而言，镜像版本之外还需要记录编译目标、设备能力和模型分片，并在启动前验证。仓库中的 probe、preflight、dry-run 和 worker-first 启动顺序，实际是在补齐这套“硬件感知的发布协议”。

##### 同一套硬件，“性能”取决于把显存留给什么

项目测得两个明显不同的运行点：prefill capacity 为 1024 时，17 万 token 提示词的预填充达到 5,377 tok/s，但 KV 池只有 250 万 token；把 capacity 降至 256，并调整 batch 后，预填充降到 2,000 tok/s，KV 池却扩大到 779 万 token，而解码速度几乎不变，约为 74 tok/s。

这说明服务能力不能只用一个吞吐数字概括。面向短请求、强调首轮处理速度的场景，前者更合适；长上下文或高并发会话更需要后者。**配置本质上是在预填充并行度与可容纳的上下文之间分配显存，而不是寻找唯一的“最佳参数”。** 产品侧真正需要定义的是工作负载分布和服务目标，再由系统选择运行点。

##### 它证明了可行性，还没有证明经济性

这套方案仍要求四台 DGX Spark、RDMA/RoCE 网络、约 510GB 模型存储，协调器需要至少 128GB 主存，每台 Spark 启动时约有 100GiB 可用统一内存。它不是低成本消费级部署，更不是一键安装包。

同时，数据来自单个集群、每个测试单元仅运行一次，同硬件 TP4 vLLM 基线尚未实测，v2 版本也未验证。因此合理结论是：**5090 可以替代更昂贵的专业卡承担协调器角色，且部署边界已被工程化描述；但尚不能据此断言整套 AFD 架构更快或更划算。**

更值得关注的机会，是为异构推理集群建立自动化的“编译目标识别—内存规划—网络检查—运行点选择”控制层。这个仓库用脚本证明了问题确实存在；下一步要验证的是，这类兼容与调参工作在更多模型和硬件组合中是否足够重复，值得从一次性运维知识变成平台能力。

## 口播总结（1）

### 2026-09-20 00:22:37

这份项目解决的是一个很具体的问题：怎样用一张三十二 GB 显存的 RTX 5090，替代原方案中的九十六 GB RTX PRO 6000，充当 DeepSeek V4.1 Flash 推理系统的协调器，同时让四台 DGX Spark 负责专家计算。

它不是预制镜像，也不是一键安装工具，而是一套经过实际运行的源码、配置、检查脚本和操作流程。最关键的价值，是说明了这套组合为什么默认无法启动，以及怎样在不修改核心逻辑的前提下，让它安全地跑起来。

先理解系统结构。DS41RT 使用一种注意力与前馈网络分离的架构，简称 AFD。协调器主要处理注意力计算和任务调度。四台 DGX Spark 则分别运行专家计算进程。项目没有修改 Spark 上官方发布的专家镜像，真正需要重新构建的，只有 RTX 5090 上的协调器。

这里遇到的第一个障碍，不是显存，而是 GPU 的计算单元数量。

官方协调器镜像是在 RTX PRO 6000 上构建的。构建过程中，系统会进行提前编译，也就是 AOT 编译，并把那张显卡的流式多处理器数量写进本地库。RTX PRO 6000 有一百八十八个这类单元，通常简称为 S M。RTX 5090 只有一百七十个。

因此，官方镜像放到 5090 上以后，会在加载任何模型权重之前直接失败，返回 CUDA 错误一百零一，也就是设备无效。原因是程序发现，实际的一百七十个 S M，与编译时记录的一百八十八个不一致。

一种看似简单的办法，是删除这项检查。但项目作者明确认为，这样做并不可靠。因为一百八十八这个数字不只是用于检查，还参与决定 GPU 内核的启动网格和集群限制。强行绕过检查，可能让后续计算使用错误的参数。

正确做法，是在 RTX 5090 本机上，使用上游项目自己的构建流程重新生成协调器镜像。这样，提前编译阶段会自动读取一百七十个 S M，并据此重新生成相关内核。整个移植过程中，不需要给引擎源码打补丁。与官方镜像相比，核心差异只是构建所依据的 GPU 不同。

第二个关键问题，是三十二 GB 显存到底够不够，以及怎样在吞吐量和缓存容量之间取舍。

项目给出了两个实测运行点。默认方案把预填充容量设为一千零二十四。在十七万提示词元的测试中，预填充速度约为每秒五千三百七十七个词元，可使用的键值缓存池约为二百五十万个词元。

这里的键值缓存，也叫 K V 缓存，是大模型保存历史上下文计算结果的内存区域。缓存池越大，系统能够同时保留的上下文通常就越多。

另一个方案把容量降到二百五十六，并把批量参数设为八十。这样做会明显降低预填充速度，每秒大约处理两千个词元，但 K V 缓存池可以扩大到七百七十九万个词元。换句话说，默认方案更重视快速读入提示内容；第二种方案牺牲预填充吞吐量，换取大约三倍的上下文缓存空间。

有意思的是，这两种设置对逐词生成速度影响很小。实测解码速度分别约为每秒七十四个和七十三点五个词元。因此，主要取舍发生在预填充速度和缓存容量之间，而不是最终的逐词生成速度。

不过，这些数字需要谨慎看待。测试来自同一套设备，记录日期是二零二六年九月十四日，地点在悉尼，而且每个测试单元只运行了一次。更重要的是，项目还没有完成严格的同条件基线测试。也就是说，同样四台 DGX Spark、同样提示内容和同样测试方法下，参考的四路张量并行 vLLM 部署还没有实际跑过。因此，这些结果能证明该配置可以运行，也能展示两个运行点之间的差异，但还不能据此得出它一定比参考方案更快的结论。

硬件门槛也不低。协调器主机需要六十四位 Linux 系统、一张三十二 GB 的 RTX 5090，以及至少一百二十八 GB 主机内存。本地固态硬盘要保存完整的 DeepSeek V4.1 Flash 检查点。模型共有四十八个分片，总大小约五百一十 GB。

协调器和四台 DGX Spark 还必须位于同一个支持 RoCE 的高速网络中。RoCE 可以简单理解为在以太网上承载远程直接内存访问，也就是 R D M A。每台 Spark 配备一百二十八 GB 统一内存，启动时大约需要留出一百 GiB 可用空间。虽然每个专家进程只使用其中一部分权重，但启动时，每个进程都需要能够访问全部四十八个模型分片。

实际部署强调先验证，再启动。先在 5090 主机上重新构建协调器镜像。然后不连接任何 Spark，只使用本机回环连接启动协调器，检查内存规划并验证服务是否能进入就绪状态。实测中，就绪探测大约四秒完成。

接下来运行预检。预检不会修改系统，而是检查协调器和四台 Spark 的镜像版本、提前编译时记录的 S M 数量、模型分片、网络端口、R D M A 设备以及内存余量，并给出可以启动或不可启动的判断。

正式启动时，要先启动四个专家进程，再启动协调器。推荐顺序是专家编号三、二、一、零，最后才是协调器。启动脚本默认只进行演练，不会立刻执行。每个脚本都会先打印完整的 Docker 命令，只有明确加入执行参数后才真正启动。专家启动脚本如果没有获得高速网络地址和 R D M A 设备名称，也会拒绝运行。这些设计主要是为了避免把配置错误带进多机环境。

项目还提供一个可选的 Engram 专用存储层脚本，用于把两个相关分片放到独立本地设备上。不过，公开测试并没有使用这个方案。测试中的数据直接放在普通 NVMe 固态硬盘上，并利用主机内存作为页面缓存，没有观察到读取瓶颈。这个脚本还可能格式化整块设备，因此会拒绝对已经分区或挂载的设备操作。

仓库中另外包含一套主机内存 K V 快照缓存的基准测试工具，用来研究写回式缓存能否让相同硬件承担更多工作。不过，这部分缓存代码位于单独的引擎分支，不属于基础部署的必要条件。

最后要注意版本范围。这套流程针对上游第一版的指定代码修订进行构建和验证。上游后来已经发布第二版，但这份方案没有在 RTX 5090 上构建或测试第二版，不能假定它可以直接复用。

最值得记住的有三点。第一，官方协调器不能直接运行在 RTX 5090 上，根因是提前编译时固化了错误的 S M 数量；正确方案是在 5090 上重新构建，而不是绕过安全检查。第二，三十二 GB 显存确实可以承载协调器，但必须在预填充速度和 K V 缓存容量之间明确取舍。第三，这是一套有实测依据的研究配置，不是一键式产品；它证明了可行性，但尚未完成与参考部署的严格同条件性能对比。

## 深度解读-口播（1）

### 2026-09-30 12:05:39

这份项目材料最值得关注的，是一个有条件的判断：配合四台 DGX Spark，三十二 GB 显存的 RTX 五零九零，也能承担 DeepSeek 四点一 Flash 推理系统的协调工作。但这不等于把整个模型装进一张消费级显卡，更不等于已经证明，这套方案比其他部署方式更快。

理解这个项目，先要看清计算任务是怎么分配的。

项目使用的是名为 DS41RT 的推理引擎。它把注意力计算和前馈网络计算拆到不同设备上。简单说，不是让每台机器都承担相同的工作，而是让协调端和专家端分工合作。

这里，RTX 五零九零承担协调端的工作，四台 DGX Spark 运行专家端。上游原本面向的协调端显卡，是九十六 GB 显存的 RTX PRO 六千。这个项目要解决的核心问题，就是把协调端迁移到只有三十二 GB 显存的五零九零上。

所以，显存门槛降低了，但整套系统的硬件要求并不低。协调端仍然需要至少一百二十八 GB 主机内存，以及能够存放完整模型的本地高速固态硬盘。模型检查点有四十八个分片，总体积约五百一十 GB。四台 Spark 也都要能访问完整的模型文件，并通过支持远程直接内存访问的高速网络，与协调端连接。

要记住的第一点是：这是分工架构下的协调端迁移，不是单卡容纳整个大模型。

迁移的第一个障碍，也不是显存不够，而是预编译程序与硬件不匹配。

材料说，上游发布的协调端镜像，在五零九零上还没加载模型权重，就会报错。原因藏在提前编译的原生库里：编译时，程序会读取当时显卡的流式多处理器数量。流式多处理器，可以粗略理解为显卡内部的一类计算单元。

原来的 RTX PRO 六千有一百八十八个，五零九零有一百七十个。启动时，程序会核对实际数量和编译时记录的数量。两者不一致，就拒绝继续运行。

看起来，把检查删掉就能绕过去。但作者明确指出，这样做并不可靠。因为同一个数量，还参与决定计算任务的启动规模和其他运行限制。删掉检查，只是消除了报警，并没有消除底层的不匹配。

项目采用的办法，是直接在五零九零上，使用上游自己的构建流程重新编译。这样，相关参数会按照一百七十个计算单元重新生成，而不需要修改引擎源代码。

这里的关键认识是：遇到硬件适配错误，不能只让程序“不报错”，还要确认程序内部的执行配置，确实适合这块硬件。

解决编译问题之后，才轮到三十二 GB 显存够不够用。材料给出了两种实测运行配置，体现出一个很清楚的取舍：输入处理速度，与后续可保留的上下文缓存容量，并不总能同时最大化。

先解释两个词。预填充，是模型先处理用户输入的整段提示。解码，是模型随后逐个生成输出词元。词元是模型处理文本的基本单位，不能直接等同于一个汉字。

默认配置把预填充容量参数设为一千零二十四。在十七万词元的提示输入测试中，预填充速度约为每秒五千三百七十七个词元。但用于保存历史计算结果的键值缓存池，容量约为二百五十万词元。

另一种配置，把预填充容量参数降到二百五十六，并配合调整批处理参数。材料给出的预填充速度约为每秒两千个词元，缓存池却扩大到约七百七十九万词元。

换句话说，默认配置处理输入更快；另一种配置牺牲了一部分输入处理速度，换来大约三倍的缓存空间。这里的“一千零二十四”和“二百五十六”是运行参数，不是同时服务的用户数量，也不是模型的上下文长度。

有意思的是，两种配置的解码速度几乎一样，分别约为每秒七十四个和七十三点五个词元。也就是说，这次调整主要改变了输入处理速度和缓存容量，对后续逐词生成的速度影响很小。

因此，不能只看一个“每秒生成多少词元”的数字，就判断整套系统的表现。输入有多长、需要保留多少上下文，同样会影响配置选择。

不过，这些结果有明确边界。

材料中的测量来自一套机器，每个测试条件只运行了一次。项目还没有完成真正同条件的基准对比：让同样的四台 Spark，使用参考方案中的另一套推理引擎，处理同样的提示，并运行同样的测试。

所以，目前可以说，这套五零九零协调端方案已经给出了可运行的配置和实测范围；但不能据此断言，它优于参考部署。能运行、测得了性能，以及证明更优，是三件不同的事。

最后，这个仓库提供的是源码、配置和研究性部署流程，不是开箱即用的镜像，也不是一键安装器。

它的工具安排体现了比较谨慎的工程思路：先在五零九零上构建，再用不依赖真实 Spark 的探测方式，检查内存规划和启动就绪状态。之后检查四台专家端的镜像、模型文件、网络端口和内存余量，确认通过，再启动专家端，最后启动协调端。启动脚本默认只展示将要执行的命令，不直接运行。

版本也有边界：这套流程针对上游第一版。上游虽然已经发布第二版，但材料明确说明，第二版尚未按这套方案在五零九零上构建和测试。

最值得记住的，是这三层区别：三十二 GB 显卡能承担协调工作，不代表它独自承载了整个模型；预填充更快，不代表缓存容量也更大；有实测结果，也不代表已经完成公平的性能比较。这个项目的价值，正是把硬件适配、资源取舍和验证边界，交代得比较具体。
