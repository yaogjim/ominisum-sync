docs: reposition Chorus as an Agent Harness

88d3647 ·

Chorus

**面向 AI 与人类协作的 Agent Harness**

English

Chorus 是一个 Agent Harness —— 包裹在 LLM 外面的基础设施层，负责管理会话生命周期、任务状态、子 Agent 编排、可观测性和故障恢复。它让多个 AI Agent（PM、Developer、Admin）和人类在同一平台上协作，完成从需求到交付的全流程。

受 **[AI-DLC（AI-Driven Development Lifecycle）](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/)** 方法论启发。核心理念： **Reversed Conversation** — AI 提议，人类验证。

---

AI Agent 的可靠性取决于模型之外的系统。模型负责推理，但会话边界、任务状态、上下文交接、子 Agent 协调和故障恢复——这些都发生在模型之外。这套外围系统就是 **Agent Harness** 。

没有 harness，Agent 在长任务中会漂移、跨会话丢失上下文、重复工作、静默失败。一个好的 harness 解决这些问题：

Harness 能力 它解决什么问题 Chorus 的解决方式

**会话生命周期** Agent 重启后丢失工作进度 每个 Agent 拥有持久化 Session，Plugin 在启动/退出时自动创建和关闭

**任务状态机** 没有统一的进度真相源 任务按严格的生命周期流转——认领、进行中、提交验证、已验证——所有人实时可见

**上下文连续性** 新的上下文窗口从零开始 每次 check-in 恢复 Agent 的角色设定、当前分配和项目状态，无需重新探索

**子 Agent 编排** 多 Agent 协作缺乏协调就会混乱 生命周期钩子自动接管——Session、上下文注入、解锁任务发现，无需手写编排逻辑

**可观测性** 看不到的东西没法调试 每个操作都带 Session 归因记录；Kanban 和 Worker 徽标实时展示谁在做什么

**故障恢复** 卡住的任务阻塞整条流水线 空闲 Session 自动过期，孤儿任务释放回任务池，任何 Agent 可重新接手

**规划与分解** Agent 不经规划就开始编码 PM Agent 在执行前构建任务依赖图——没有经过审批的计划，不开始任何工作

Chorus 不是一个 framework——它不提供需要你自己组装的构建积木。它是一个 **完整的 harness** ，带有开箱即用的默认配置：生命周期钩子、50+ MCP 工具、基于角色的权限、以及内建的人类审核环节。

#### AI-DLC 工作流

```
Idea ──> Proposal ──> [Document + Task DAG] ──> Execute ──> Verify ──> Done
  ^          ^               ^                     ^          ^         ^
Human     PM Agent       PM Agent              Dev Agent    Admin     Admin
creates   analyzes       drafts PRD            codes &      reviews   closes
          & plans        & tasks               reports      & verifies
```

三个 Agent 角色：

角色 职责 MCP 工具前缀

**PM Agent** 分析 Idea、创建 Proposal（PRD + 任务拆解）、管理文档 `chorus_pm_*`

**Developer Agent** 认领任务、编写代码、报告工作、提交验证 `chorus_*_task`, `chorus_report_work`

**Admin Agent** 创建项目/Idea、审批 Proposal、验证任务、管理生命周期 `chorus_admin_*`

所有角色共享只读和协作工具（ `chorus_get_*` 、 `chorus_checkin` 、 `chorus_add_comment` 等）。

#### 功能特性

任务支持依赖关系（DAG），Kanban 看板实时展示任务状态和活跃 Worker 徽标。PM 创建 Proposal 时通过 `dependsOnDraftUuids` 设定任务执行顺序。

##### Session 可观测性

每个 Developer Agent 创建 Session 并 checkin 到任务，UI 上实时显示哪个 Agent 正在处理哪个任务：

- Kanban 卡片显示 Worker 徽标
- 任务详情面板显示活跃 Worker
- Settings 页面管理 Agent 和 Session

支持 Claude Code Agent Teams 多 Agent 并行工作，Team Lead 分配 Chorus 任务给多个 Sub-Agent，每个 Sub-Agent 独立管理自己的任务生命周期。

Claude Code 插件自动化 Session 生命周期管理：

- **SubagentStart** — 自动创建 Chorus Session
- **TeammateIdle** — 自动发送心跳
- **SubagentStop** — 自动 checkout 任务 + 关闭 Session + 发现新解锁任务

##### 需求澄清

PM Agent 在创建 Proposal 前通过结构化问答轮次澄清需求。问题按类别分类（功能性、范围、技术等），支持在 CC 终端或 Web UI 上回答。Proposal 提交前必须完成澄清或显式跳过。

##### Proposal 审批流

PM Agent 创建 Proposal（包含文档草稿和任务草稿），Admin 审批后草稿物化为正式 Document 和 Task 实体。

##### 通知系统

应用内通知 + SSE 实时推送 + Redis Pub/Sub 跨实例传播：

- **10 种通知类型** — 任务分配/验证/重开、提案批准/驳回、评论新增等
- **个人偏好设置** — 每种通知类型可独立开关
- **MCP 工具** — `chorus_get_notifications` 、 `chorus_mark_notification_read` 供 Agent 使用
- **Redis Pub/Sub** — 可选，支持多 ECS 实例间 SSE 事件同步（ElastiCache Serverless）

> **通知系统设计文档 →**

##### @Mention

评论和实体描述中支持 @mention — 用户和 AI Agent 可以互相 @，触发定向通知：

- **Tiptap 编辑器** — 输入 `@` 弹出自动补全下拉框，搜索用户/Agent
- **权限隔离** — 用户可 @ 同公司所有用户 + 自己名下的 Agent；Agent 遵循同 owner 规则
- **Mention 通知** — `action="mentioned"` 带上下文片段，点击直达源实体
- **MCP 工具** — `chorus_search_mentionables` 供 Agent 查询 UUID 后精确写入 mention

> **@Mention 系统设计文档 →**

##### 活动流

全量记录所有参与者的操作，支持 Session 归因（AgentName / SessionName 格式），实现完整的工作审计追踪。

## 结构化（1）

### 2026-03-17 09:49:19

这篇文章主要介绍了 Chorus：它不是单纯调用 LLM 的工具，而是一层专门管理 AI Agent 协作的 “Agent Harness”。核心目标是让多个 AI Agent 与人类在同一平台上，稳定地完成从需求分析到交付验证的完整流程。

- **1. Chorus 的定位与核心理念**
  - Chorus 被定义为一个 “Agent Harness”，即包裹在大模型外部的基础设施层。
  - 它重点解决的不是 “模型会不会推理”，而是 “长流程任务怎么持续、可控、可恢复地推进”。
  - 核心理念是：`Reversed Conversation`，也就是 “AI 先提出方案，人类再审核确认”。
  - 文章强调：Agent 的可靠性主要取决于模型之外的系统，而不是模型本身。

- **2. 为什么需要 Harness**
  - 如果没有 harness，Agent 在长任务中容易出现 4 类问题：漂移、跨会话丢上下文、重复劳动、静默失败。
  - Chorus 对应提供了完整机制：
    - **会话生命周期管理**：Agent 重启后不丢进度，Session 持久化保存。
    - **任务状态机**：任务按 “认领 → 进行中 → 提交验证 → 已验证” 流转，所有人都能看到统一进度。
    - **上下文连续性**：每次 check-in 自动恢复角色设定、任务分配和项目状态，不必重新摸索。
    - **子 Agent 编排**：通过生命周期钩子自动管理 Session、上下文注入和任务发现。
    - **可观测性**：每个操作都能追溯到具体 Session，Kanban 和 Worker 徽标实时展示谁在做什么。
    - **故障恢复**：空闲 Session 自动过期，孤儿任务回到任务池，其他 Agent 可继续接手。
    - **规划与分解**：PM Agent 必须先建立任务依赖图，未经审批不能直接开工。
  - 文章明确说：Chorus 不是一个需要自己拼装的 framework，而是 “开箱即用” 的完整 harness。

- **3. AI-DLC 工作流与角色分工**
  - Chorus 采用 AI-DLC（AI-Driven Development Lifecycle）方法，把流程拆成：
    - `Idea → Proposal → Document + Task DAG → Execute → Verify → Done`
  - 三类 Agent 分工明确：
    - **PM Agent**：分析需求、创建 Proposal、拆解任务、管理文档。
    - **Developer Agent**：认领任务、写代码、汇报进展、提交验证。
    - **Admin**：创建项目和 Idea、审批 Proposal、验证任务、管理生命周期。

## 产品-技术开发（1）

### 2026-03-17 10:01:54

这是一个很典型、也很有前瞻性的方向：它不是再做一个 “会调用 LLM 的应用”，而是在做 “AI 协作操作系统” 的基础设施层。核心价值不在模型能力，而在把 Agent 从 “单轮聪明” 变成 “多轮可控、可审计、可恢复的生产力单元”。

**产品解读**
- `Chorus`的产品定位非常清晰：不是 AI IDE、不是 workflow builder、也不是单一 Agent，而是`Agent Harness`。这一定义是对的，因为企业真正缺的不是 “再多一个 Agent”，而是 “让多个 Agent 和人稳定协作的控制层”。
- 它抓住了 AI 落地的真实痛点：长任务漂移、上下文丢失、多 Agent 互相踩踏、失败无法恢复、过程不可审计。这个切口比 “提升模型 prompt” 更接近企业刚需。
- `Reversed Conversation`很关键：AI 提议，人类验证。这个机制天然适合需求、方案、执行、验收这类高风险场景，比 “AI 直接做决定” 更适合企业治理。
- 三角色设计`PM / Developer / Admin`是合理的最小闭环：PM 负责结构化规划，Dev 负责执行，Admin 负责审批与验收。产品边界清楚，便于权限隔离和责任归因。
- 真正的护城河不是 50+ MCP tools，而是`任务状态机 + Session 生命周期 + Proposal 审批 + Activity 审计 + DAG 执行模型`组合起来后的流程确定性。

**产品上最值得肯定的设计**
- `Proposal -> Approve -> Materialize`：先草稿、后审批、再实体化，这是 AI 系统里很成熟的 “沙箱到生产” 模式。
- `Task DAG`：比普通待办列表更适合多 Agent 协作，避免 “大家都挑最顺手的做，最后主链路没人做”。
- `Session 可观测性`：谁在做、做到哪一步、是否空闲，这类信息是 Agent 系统可运维的前提。
- `故障恢复`：孤儿任务回收、Session 过期，这决定系统是否能长期运行，而不是 demo 级运行。
- `需求澄清门控`：很多 AI 系统失败不是因为不会执行，而是开始执行时需求就没被澄清。

**技术解读**
- 架构分层是对的：`Plugin/Hook -> API -> Service -> UI -> Data`，说明它在把 “Agent 行为” 与 “业务状态” 解耦。
- 把 Session 生命周期放在插件 Hook 自动管理，是非常重要的实现策略。因为如果靠 Agent 自己记得调用 “创建 Session / 心跳 /checkout”，稳定性会很差。
- `UUID-first`是好选择。多 Agent、多草稿、多实体的系统里，名称会变，UUID 才适合追踪和引用。
- `SSE + Redis Pub/Sub`也合理：SSE 适合轻量实时推送，Redis 负责跨实例广播，足够支撑中等规模协作场景。
- `角色前缀工具域`设计很好，MCP 工具天然按角色隔离，降低误调用风险，也让 Skill 文档更容易教模型使用。

**关键技术最佳实践**
- **状态机先于 Prompt**
  - 不要让 Agent “理解自己现在该做什么”，而要让系统用显式状态约束它。
  - 最佳实践：任务状态至少定义`todo -> in_progress -> to_verify -> done/reopened`，并在服务端校验非法跳转。
  - 例子：Developer 不能直接把`todo`改成`done`；必须先`checkin`后才能`report_work`；Admin 才能`verify_task`。

- **Session 作为一等公民**
  - 每个 Agent 执行任务必须绑定 Session，而不是把 Agent 当无状态调用器。
  - 最佳实践：Session 存`agent_id /task_id/started_at /heartbeat_at/checkout_reason /context_snapshot_version`。
  - 例子：Claude 子 Agent 启动时自动创建 Session；10 分钟无心跳标记`inactive`；30 分钟自动 checkout 并释放任务。

- **上下文恢复要结构化，不要靠拼接长 prompt**
  - 恢复上下文时返回结构化对象，而不是超长自然语言。
  - 最佳实践返回：
    - `role/persona`
    - `current_task`
    - `acceptance_criteria`
    - `dependencies`
    - `recent_activity`
    - `blocked_reasons`
    - `suggested_next_actions`
  - 例子：`chorus_checkin`返回 JSON，让模型直接消费，而不是再读一堆文档。

- **Proposal 审批必须 “冻结输入”**
  - 一旦进入审批，Proposal 草稿应版本冻结，避免 “审批时内容又变了”。
  - 最佳实践：`proposal_version` + `approved_version`，审批记录绑定具体版本。
  - 例子：Admin 审的是`proposal v7`，通过后才 materialize 成正式 PRD 和 Task；PM 继续修改则产生`v8`，需重新审批。

- **DAG 不只是展示层，要参与调度**
  - 很多系统把 DAG 只做成图谱 UI，这是不够的。
  - 最佳实践：服务端提供`get_unblocked_tasks ()`，只返回依赖已完成且未被占用的任务。
  - 例子：Task C 依赖 A/B；A 完成、B 未完成时，任何 Agent 都不能 checkin C。

- **审计日志必须可机器归因**
  - Activity 不能只是 “有人做了某事”，必须能明确到`agent/session/tool/action/entity`。
  - 最佳实践字段：`actor_type`、`actor_id`、`session_id`、`tool_name`、`entity_type`、`entity_id`、`before`、`after`、`trace_id`。
  - 例子：后续排查 “任务为何误关闭”，可以直接查到是哪个 Session 调了哪个 MCP 工具。

**一个可直接借鉴的实现范式**
```ts
type TaskState =
  | "todo"
  | "in_progress"
  | "to_verify"
  | "done"
  | "reopened";

function transitionTask (task: Task, action: Action, actor: Actor) {
  assertPermission (actor, action, task);

  const next = stateMachine (task.state, action);

  if (!next) throw new Error ("Invalid state transition");

  persistAuditLog ({
    actorId: actor.id,
    actorType: actor.type,
    sessionId: actor.sessionId,
    entityType: "task",
    entityId: task.id,
    before: task.state,
    after: next,
    action,
  });

  return updateTask (task.id, { state: next });
}
```
这个模式的价值在于：状态转移、权限、审计三件事在服务端统一收口，Agent 只能 “申请动作”，不能 “直接改结果”。

**从产品到工程，最强的一条最佳实践链路**
- `Idea`进入后，先走结构化澄清，而不是直接生成 PRD。
- PM 输出`Proposal`时，同时产出`Document Draft + Task DAG Draft`。
- Admin 审批通过后，草稿实体化。
- Developer 只能领取`unblocked`任务。
- 开发中所有行为都必须绑定 Session。
- 提交后进入`to_verify`，由 Admin 或指定 Reviewer 验证。
- 超时 Session 自动回收，任务回流任务池。
- 全链路事件进入 Activity + Notification。

这条链路的优点是：每一步都可控、可解释、可追责，也适合后续接入更多模型或 Agent Runtime。

**我认为当前最该补强的地方**
- `Execution Metrics`应尽快做，这是从 “能跑” 到 “能管理” 的分水岭。至少要有：
  - 任务周期时长
  - Agent 活跃时长
  - 重开率
  - Proposal 驳回率
  - DAG 关键路径耗时
- `Proposal Granular Review`很重要。企业不会只接受 “整单通过 / 整单拒绝”，更需要 “第 3 个任务拆得不对，请局部重提”。
- `Checkin Context Density`应谨慎，不能一味加信息。最佳实践是 “高相关摘要 + 原文链接”，避免上下文再次膨胀。
- `Auto-Scheduling`不要过早做成 “系统自动派单”，先做 “推荐领取” 更稳。因为自动派单会把调度错误放大。

**如果把它作为企业级产品继续演进，建议这样做**
- 增加`policy engine`：例如 “高风险操作必须人审”“生产环境变更必须双确认”。
- 增加`memory tiers`：短期 Session memory、中期项目 memory、长期组织 knowledge 分层管理。
- 增加`evaluation harness`：不是只看任务完成，而要看提案质量、返工率、验收通过率。
- 增加`tool sandbox`：不同角色、不同项目、不同环境的工具能力隔离。
- 增加`human workload view`：不仅看 Agent 在做什么，也看人类审批瓶颈在哪里。

**一句话判断**
- 这不是 “又一个 AI 协作面板”，而是在构建`AI 团队的运行时系统`。
- 产品方向是对的，技术架构也成立；真正的胜负手不在模型，而在`状态、治理、恢复、审计、调度`这五件事能否做深。

**先给结论**
在 Chorus 这种 Agent Harness 里，最佳实践不是 “让 Agent 更聪明”，而是：

- 先把任务生命周期设计清楚，再让 Agent 参与
- 先定义系统外部状态真相源，再谈上下文注入
- 先保证可恢复、可审计，再追求自动化程度
- 让 PM / Developer / Admin 各自只做自己职责内的动作
- 所有自动化行为都要可见、可追踪、可人工接管

下面我用这个具体功能把最佳实践展开。

**具体实例设计**

假设你要做的功能叫：`Task SLA Escalation`

规则如下：
- 任务进入`In Progress`后，24 小时内没有新的`checkin`、`report_work`或状态变化；
- 系统判定该任务 “可能阻塞”；
- 自动创建通知：
  - Developer Agent：提醒更新进展
  - PM Agent：提醒评估是否阻塞
  - Admin：提醒是否需要人工介入
- 如果对应 Session 已 inactive，则：
  - 自动关闭 Session
  - 自动 checkout 任务
  - 将任务重新暴露到`unblocked task pool`

这就是一个非常典型的 Chorus 场景。

**在这个实例上的最佳实践**

- **1. 把 “超时” 建模为 Harness 规则，不要塞给 Agent 自己记**
  - 不要让 Developer Agent 靠 prompt 记住 “24 小时没更新就要提醒”。
  - 正确做法是把它实现成平台规则：定时扫描`task + session + last activity`。
  - 原因很简单：Agent 的上下文窗口会变，prompt 会漂移，只有 Harness 层的规则才稳定。

- **2. 以任务状态机为主线，不要直接围绕消息流写逻辑**
  - 最容易犯的错是：“检测到超时 -> 发一条通知”。
  - 更好的做法是定义明确状态，例如：
    - `in_progress`
    - `stale_warning_sent`
    - `reassign_pending`
    - `to_verify` / `reopened`
  - 即使 UI 最后只展示通知，底层也应该有状态依据。
  - 这样可以避免重复提醒、通知风暴、以及多个实例并发下的状态不一致。

- **3. Session 与 Task 要分开建模，但通过事件关联**
  - 最佳实践不是把 “任务卡住” 直接等同于 “Agent 不工作了”。
  - 因为可能出现：
    - Session 活着，但任务确实复杂，需要长时间处理；
    - Session 死了，但任务还没有被系统回收；
    - Agent 已经提交工作，但没正确 checkout。
  - 所以要分别看：
    - `Task.lastProgressAt`
    - `Session.lastHeartbeatAt`
    - `Task.assigneeSessionId`
  - 然后通过事件归因连接起来，而不是混成一个字段。

- **4. 所有自动动作必须写入 Activity Stream**
  - 这是 Chorus 里非常关键的最佳实践。
  - 比如系统自动触发：
    - `stale_warning_sent`
    - `session_auto_expired`
    - `task_auto_checkout`
    - `task_reopened_to_pool`
  - 都必须进入活动流，并带上归因，例如：
    - `system/sla-monitor`
    - 或`SessionName` / `AgentName`
  - 否则后面你根本分不清：
    - 是 Agent 没做事；
    - 还是系统误判；
    - 还是 Admin 手工干预过。

- **5. 自动化只负责 “建议和保护”，最终决策保留给人类或 Admin**
  - 这是最符合 README 中`Reversed Conversation — AI 提议，人类验证`的做法。
  - 例如：
    - 系统可以自动提醒 “建议回收任务”
    - 但不要第一版就直接强制改派所有任务
  - 更稳妥的流程是：
    - 第一次超时：通知
    - 第二次超时：建议回收
    - Session inactive + 任务无更新：自动 checkout，但保留 Admin 审计入口
  - 这体现的是 “渐进自动化”，不是 “一步到位全自动”。

- **6. 定时任务逻辑必须幂等**
  - 这是实现层面最重要的一条。
  - 因为 Chorus 明确支持 SSE、Redis Pub/Sub、可能多实例部署。
  - 在这种环境里，超时扫描器可能重复执行。
  - 所以必须保证：
    - 同一个任务同一轮超时只发一次通知
    - 同一个 inactive Session 只关闭一次
    - 同一个任务不会被重复 checkout
  - 最常见做法是：
    - 用数据库事务 + 唯一约束
    - 或给 “升级动作” 加去重键，比如`taskId + escalationLevel + dateWindow`

**推荐的实现方式**

如果把这个功能放到 Chorus 的现有架构里，我会建议这样落位：

- **API/Service 层**
  - 新增一个`sla-monitor`服务，不直接放进某个 Agent 工具里
  - 它负责：
    - 扫描超时任务
    - 判断 Session 存活
    - 触发通知与活动流记录
    - 视情况执行任务回收

- **数据层**
  - 为任务增加类似字段：
    - `lastProgressAt`
    - `staleWarningSentAt`
    - `escalationLevel`
  - 为 Session 确保已有或补充：
    - `lastHeartbeatAt`
    - `closedAt`
    - `closeReason`

- **通知层**
  - 复用现有通知系统，不单独造一套提醒机制
  - 新增通知类型，例如：
    - `task_stale_warning`
    - `task_escalated`
    - `task_reassignment_suggested`

- **活动流**
  - 每次自动动作都记录事件
  - 事件描述要能让人一眼看懂，比如：
    - “Task exceeded SLA after 24h without progress”
    - “Session auto-expired due to heartbeat timeout”
    - “Task returned to unblocked pool”

- **Web UI**
  - 不只是弹通知
  - 最佳实践是把 “超时风险” 直接显示到：
    - Kanban 卡片徽标
    - Task Detail 面板
    - Sessions 页面
  - 因为 Chorus 的核心优势就是可观测性，不能把关键风险藏在消息中心里。

**一个符合 Chorus 理念的流程示例**

下面是这个实例的推荐流程：

```text
1. Developer Agent 认领任务，创建 Session，并 checkin
2. 任务进入 In Progress
3. 24 小时内无 heartbeat / 无 report_work / 无状态更新
4. SLA Monitor 扫描发现异常
5. 系统写入 Activity Stream：task stale detected
6. 系统发送通知给 Developer / PM / Admin
7. 如果 Session 已 inactive：
   - 自动关闭 Session
   - 自动 checkout 任务
   - 写入 Activity Stream
   - 将任务重新释放到可领取池
8. PM 或 Admin 决定：
   - 重新分配
   - 拆分任务
   - 或标记为真实阻塞
```

这个流程的关键不是 “自动提醒” 本身，而是：
- 每一步都有状态依据
- 每一步都有归因记录
- 每一步都能人工接管
- 即使 Agent 掉线，系统仍能恢复

这就是 Harness 思维。

**在这个实例中，最容易踩的坑**

- **把超时逻辑写成 prompt 约束**
  - 这样最脆弱，也最难测试。

- **只有通知，没有状态落库**
  - 会导致系统不知道 “这条通知处理过没有”。

- **直接依据 Session 超时就关闭任务**
  - 任务和 Session 不是一回事，必须分别判断。

- **自动回收后不保留审计记录**
  - 会破坏 Chorus 的可观测性优势。

- **只在 UI 展示风险，不进入 MCP / Activity / Notification**
  - 这样 Agent、Web UI、Admin 三端会看到不同真相源。

- **没有幂等设计**
  - 多实例部署下非常容易重复发通知和重复回收任务。

**如果要把它提升成 “最佳实践模板”，我建议遵循这 6 条**

- **状态先行**
  - 任何自动化动作先定义状态流转，再定义通知文案。

- **事件完整**
  - 每个自动动作必须可审计、可追溯。

- **职责分离**
  - PM 负责判断计划与阻塞，Developer 负责执行与汇报，Admin 负责最终治理。

- **自动化渐进**
  - 先提醒，再建议，再回收，不要一上来就全自动改派。

- **上下文恢复可重复**
  - checkin 返回中应包含：
    - 当前任务状态
    - 是否已触发超时提醒
    - 最近活动摘要
    - 下一步推荐动作

- **恢复优于聪明**
  - 设计目标不是 “尽量不出错”，而是 “出错后快速恢复”。

**一句话概括这个实例上的最佳实践**

对于 Chorus 这样的 Agent Harness，最佳实践是：
**把 “任务超时升级” 设计成可审计、可恢复、幂等的系统级工作流，而不是依赖 Agent 记忆和 prompt 自觉的行为约束。**
