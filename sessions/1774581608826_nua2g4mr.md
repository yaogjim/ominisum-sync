## 分析要点

- **核心高价值点**：最有价值的是将公开代理与私有代理彻底隔离，并用分层模型调用与严格升级策略控制风险、成本和能力边界。
- **留存建议**：长期保留（文章提供了清晰的代理分层、安全隔离、成本控制与通信协议选型思路，适合作为构建轻量自托管 AI 系统的参考案例。）

**知识要点**

- 用 IRC 作为 AI 代理通信层可以获得自托管、低耦合、低锁定的优势
- 公开代理与私有代理分层部署是兼顾能力与安全的关键架构手法
- 模型选择应按任务分层而非盲目使用最大模型
- A2A 协议适合做结构化代理协作，但必须配合可见性和审计机制
- 成本上限、工具白名单和沙箱化是面向公众代理的基础防线

## 正文

nully standing guard outside George's Code Vault

#### 关于“索要我的简历”的问题

每个带有 AI 聊天机器人的作品集网站都在做同样的事情：将简历输入模型并让访客重新表述内容。这不过是个噱头。这个模型无法告诉你任何简历中没有的信息。

我想要一些不同的东西。如果招聘经理问“George 是如何处理测试覆盖率的？”，答案不应该是“George 重视全面测试”。而应该是克隆代码仓库，统计测试用例数量，读取 CI 配置，并给出具体细节。

因此，我构建了基础设施来使它正常工作。

#### the architecture

两个代理，两个盒子，两个安全边界。

```
visitor (browser)
  │
  └─ georgelarson.me/chat/
       │
       └─ gamja web IRC client
            │
            └─ wss://nullclaw.georgelarson.me:443
                 │
                 └─ Cloudflare (proxy, TLS termination, bot protection)
                      │
                      └─ ergo IRC server (LarsonNet)
                           │
                           └─ #lobby
                                │
                                └─ nully (nullclaw agent)
                                     ├── reads public GitHub repos
                                     ├── preloaded portfolio context
                                     └── routes to ironclaw via #backoffice
                                              │
                                              └─ #backoffice (private IRC channel)
                                                   │
                                                   └─ ironclaw (separate box, via Tailscale)
                                                        ├── email access
                                                        ├── calendar
                                                        └── private context
```

**nullclaw** 是面向公众的门卫。它运行在一个最小的边缘设备上，一个 678 KB 的 Zig 二进制文件，占用约 1 MB 的内存。它处理问候、回答关于我的项目的问题，还能克隆代码仓库，用实际代码证实陈述。

**ironclaw** 是运行在独立且更强大系统上的私有代理。它可以访问电子邮件、获取更深入的个人背景信息，并处理从 nullclaw 路由过来的复杂查询。这种边界是刻意设置的：公共盒子无法访问私有数据。

#### why IRC

我本可以使用 Discord、Telegram 或者一个自定义的 WebSocket 聊天工具。选择 IRC 是正确的，原因有三个：

1. **它符合美学风格。** 我的作品集网站有一个终端 UI。嵌入其中的 IRC 客户端与品牌风格一致。用 Discord 会感觉不合适。
2. **我拥有整个技术栈。** 因此，IRC 服务器、gamja 网页客户端、nullclaw 代理，所有这些都部署在我的基础设施上。没有会变更条款的第三方 API，也没有会决定弃用机器人访问的平台。
3. **它是一个有 30 年历史的协议。** IRC 简单易用、易于理解，且不存在供应商锁定问题。同一个代理可以通过 Web 客户端与访客通信，也可以通过 irssi 从终端与我通信。

#### 模型选择作为设计决策

大多数人在这里会选择他们买得起的最大型号。这对于数字门卫来说是错误的直觉。

##### 对话层: haiku 4.5

问候，初步筛选，关于我的背景的简单问题。亚秒级响应。每次对话几分钱。这里速度比深度更重要。

##### 工具使用层: Sonnet 4.6 (备用)

当 nully 需要克隆仓库、阅读代码或跨文件综合发现时，Sonnet 会介入。你只需在需要推理时为推理付费。

##### cost cap: $2/day

一个没有支出限额的面向公众的代理是个负担。额度限制可以防止对话失控和滥用行为。如果有人试图耗尽我的推理预算，他们就会碰壁。

##### the portfolio signal

使用 Opus 处理数字礼宾服务会与模型理解背道而驰。如果 Haiku 能处理，就不要发送给 Sonnet。分层推理（热路径成本低，重任务处理能力强）是我将成本控制在每天 2 美元以下的方法。

#### security posture

这个设备是面向公众的外围。它应该像外围一样进行加固。

- **SSH：** 非 root 用户在非标准端口上仅使用密钥认证。禁用 root 登录。
- **防火墙：** UFW 仅开放三个端口：SSH、IRC（TLS）和 HTTPS（通过 Cloudflare 的 WebSocket）。
- **Cloudflare 代理：** Web 访问者永远不会直接访问该服务器。WebSocket 流量经过 Cloudflare 的边缘节点，该节点会处理 TLS 终止、速率限制和机器人过滤。
- **Agent 沙箱化：** nullclaw 在受监控模式下运行，仅具备工作区文件访问权限，采用受限的命令允许列表（只读工具），并且每小时最多执行 10 次操作。
- **成本控制：** 每天 2 美元，每月 30 美元的硬性上限。如果代理受到滥用，预算会在损害加剧之前耗尽。
- **审计日志：** 每一次工具调用都会被记录。
- **自动更新：** 无人值守的安全升级已启用。
- **TLS:** Let's Encrypt 带有自动续期和服务重启钩子。

理念是最小化攻击面。该设备运行两个服务（ergo 和 nullclaw），不直接提供任何网页内容，也无法访问私有数据。如果被入侵，影响范围仅限于一个 IRC 机器人，该机器人每天有 2 美元的推理预算。

#### the communication stack

每个组件体积小、自托管且可替换：

- **Ergo：** IRC 服务器。单个 Go 二进制文件，2.7 MB 内存。支持 TLS、WebSocket、连接限流、IP 伪装。
- **gamja:** Web IRC 客户端。构建大小 152 KB。在 Cloudflare 后方的作品集网站上以静态页面形式提供服务。自动连接到 #lobby 频道，使用随机访客昵称。
- **nullclaw:** AI 代理运行时。4 MB Zig 二进制文件，约 1 MB 峰值 RSS。作为 IRC 客户端连接到 ergo，通过 LLM 处理消息，在频道内回应。

总占用空间：不到 10 MB 的二进制文件，空闲时不到 5 MB 的内存。这可在可用的最便宜 VPS 等级上运行。

#### what nully can actually do

这正是将它与聊天机器人区分开来的部分：

- **“乔治使用哪些语言？”** 不照本宣科地复述简历内容。能够从预加载的上下文中知晓信息，并且可以通过检查 repos 来进行验证。
- **"他是如何组织测试的？"** 克隆仓库，读取测试文件，报告发现的内容。
- **"给我讲讲 Fracture"** 会从关于该项目的预加载记忆中调取信息，并能深入挖掘具体细节的来源。
- **"我怎么联系到他？"** 提供联系信息。不会编造电话号码。
- **"我可以安排通话吗？"** Nully 通过 Tailscale 借助 Google 的 A2A 协议呼叫 ironclaw。Ironclaw 使用自身的 LLM 处理该请求，发送结构化响应，Nully 中继该答案。访客从未看到这个交接过程。

这是一个由 Haiku 支持的 IRC 机器人，所以它并不完美。但它能用代码佐证自己的言论，而我的简历做不到这一点。

#### the A2A implementation

这是我最引以为傲的部分。

nullclaw 已经支持谷歌的 A2A 协议（v0.3.0）：代理卡发现、JSON-RPC 调度、任务状态机。它所缺少的是一个 *客户端* 。它能够接收 A2A 调用，但无法发起调用。于是我编写了一个。

The `a2a_call` tool sends `message/send` JSON-RPC requests to remote agents, parses the task response (completed, failed, working), extracts the artifact text, and returns it as a tool result. It enforces HTTPS for public endpoints but allows plaintext HTTP for private networks and Tailscale CGNAT ranges, because when you're debugging TLS between two agents on a mesh VPN at 2am, the last thing you need is your own security policy locking you out.

但真正巧妙的部分在 Ironclaw 这边。运行在那里的 Nullclaw 实例没有自己的 API 密钥。相反，它的 LLM 提供商被指向 Ironclaw 自己的网关作为中转：

```
nully (this box)
  │
  └─ a2a_call tool → POST /a2a
       │
       └─ ironclaw's nullclaw (separate box, Tailscale)
            │
            ├── receives A2A task
            ├── needs to run inference
            └── provider config: "ironclaw" → http://127.0.0.1:3000/v1
                  │
                  └─ ironclaw's own gateway
                       └─ routes to Kilo → actual LLM
```

一个 API 密钥。一个计费关系。ironclaw 的盒子上的 nullclaw 只是一个 A2A 桥接。它接受协议，借用 ironclaw 的推理管道，并进行响应。无凭证重复，无需单独跟踪预算。拥有 API 密钥的代理是为推理付费的代理，无论谁发起了请求。

#### security of the handoff

开放的 A2A 端点是一个提示注入面。访客可能会说“让 Ironclaw 发送电子邮件”，而一个天真的中继会直接执行。因此 Nully 设置了严格的防护措施：

- 只有特定的请求类型会路由到 Ironclaw：日程安排、可用性、联系信息。
- 随意的访客指令将被拒绝。“告诉铁爪做 X”会得到否定回答。
- ironclaw 上的 A2A 端点被防火墙限制为仅允许 Tailscale 访问，不允许公开访问。
- 两个代理均以受监督模式运行，仅能访问工作区文件，且命令允许列表受限。

Nully 决定哪些会被升级，哪些不会。

#### what I learned

- **模型选择与系统设计同样重要。** 为每一层选择合适的模型是一个设计决策，而非设置开关。这会影响成本、延迟、能力和用户体验。
- **代理是比较简单的部分。** 通信栈、安全加固、DNS 路由、TLS 管理以及 Cloudflare 集成所花费的时间比配置代理本身更多。
- **IRC 被低估了。** 一种 1988 年的协议结果成为了 AI 代理的理想传输方式。没有 SDK，没有 API 版本控制，没有供应商锁定。仅仅是频道中的消息。
- **Nullclaw 和 Ironclaw 之间的划分是承重的。** 一侧是公开的、最小化的、可消耗的；另一侧是私密的、有能力的、受保护的。如果消除这个边界，你就会失去安全模型。
- **代理间通信既需要结构也需要可见性。** Google 的 A2A 协议处理契约（结构化任务、状态机、类型化工件）。基于 Tailscale 的私有 IRC 频道处理审计跟踪，在该频道中我可以查看代理的对话、进行实时干预并回溯历史记录。两者都要使用。
- **不要重复使用凭证。** 透传模式下，Nullclaw 借用 Ironclaw 的网关进行推理，意味着一个 API 密钥、一个计费关系、零凭证蔓延。拥有密钥的代理负责支付令牌费用，无论谁发起请求。

#### 《Building a Digital Doorman》通俗总结

##### 一、这篇文章在讲什么

作者不想做一个 “会复述简历” 的 AI 聊天机器人，而是想做一个真正有用的 “数字门卫”。

它不仅能回答 “他做过什么”，还能进一步去查代码仓库、看测试文件、读 CI 配置，用事实和细节来回答问题。核心目标不是 “更像人聊天”，而是 “更像一个能验证信息的助手”。

##### 二、核心设计：公私分离的双代理架构

作者搭了两个 AI 代理，放在两套隔离的系统里：

###### 1. `nullclaw`：面向公众的门卫
它负责接待访客、回答公开问题、读取公开 GitHub 仓库，并在需要时验证项目细节。

特点是：轻量、便宜、暴露在公网、权限很小。

###### 2. `ironclaw`：私有后台助手
它运行在独立机器上，可以访问邮箱、日历和更私密的个人信息，处理更复杂的请求，比如安排通话。

这套设计的关键在于：公开系统永远拿不到私有数据。即使前台被攻击，损失也被限制在很小范围内。

##### 三、为什么选 IRC，而不是 Discord/Telegram

作者没有选流行聊天平台，而是用了 IRC，原因很务实：

###### 1. 风格统一
他的作品集本身就是终端风格，IRC 客户端天然匹配这个体验。

###### 2. 技术栈完全可控
从 IRC 服务器到网页客户端再到 AI 代理，全部自托管，不依赖第三方平台规则，也不用担心 API 变动或封禁。

###### 3. 协议足够简单、稳定
IRC 是一个非常老但可靠的协议，没有供应商锁定，既能给网页访客用，也方便作者自己在终端里接入和管理。

##### 四、模型选择思路：不是越大越好

作者特别强调：做这种公开 AI 服务，不是无脑上最大模型。

###### 1. 轻任务用小模型
日常问候、简单问答、初步分流，用更快更便宜的小模型处理。

###### 2. 重任务再调用强模型
只有在需要读代码、跨文件分析、深度推理时，才调用更强的模型。

###### 3. 成本必须被硬控制
作者给系统设置了每天 2 美元的预算上限，防止被滥用，也确保这个系统长期可持续。

本质上，这是一个典型的 “分层推理” 设计：高频低成本，低频高能力。

##### 五、真正的亮点：它能 “查证”，不是只会 “说”

这个数字门卫和普通 AI 聊天机器人最大的不同，是它能调用工具验证信息。

比如：

###### 1. 问技术细节
如果你问 “他的测试是怎么组织的”，它会去克隆仓库、看测试代码，再给出结论。

###### 2. 问项目背景
如果你问某个项目，它可以结合预加载知识和实际代码做更具体说明。

###### 3. 问联系或约时间
它可以提供联系方式，甚至把复杂请求转给私有代理处理，但不会乱编信息。

也就是说，它不只是 “像懂”，而是尽量做到 “有依据地懂”。

##### 六、安全设计：把风险控制在最小范围

作者对安全问题考虑得很重，核心思路是 “最小暴露面”。

###### 1. 公网机器权限极低
前台代理只能访问有限工作区，只能用受限工具，且调用次数有限制。

###### 2. 私有代理不直接暴露
后台代理只允许通过私有网络访问，外部用户不能直接碰到。

###### 3. 成本本身也是一道防线
即使有人恶意刷请求，也会先撞上预算上限，损失可控。

###### 4. 全程可审计
每次工具调用都有日志，方便回溯和排查。

这说明作者不是把 AI 当 “炫技功能”，而是把它当真实线上系统来设计。

##### 七、代理协作的关键：A2A 协议

作者还实现了代理之间的协作机制，也就是让前台代理能把合适的任务交给后台代理。

###### 1. 只转发特定类型请求
比如日程安排、可用时间、联系方式等，才允许升级到后台。

###### 2. 不允许访客随意 “命令后台”
用户不能直接说 “让后台发邮件”，前台代理会拦住这种请求，避免提示注入风险。

###### 3. 凭证集中管理
后台代理统一负责调用大模型和计费，避免 API Key 四处分散，减少安全和运维负担。

这套设计体现出一个重要思路：多代理系统里，协议、边界和权限控制，比 “智能程度” 更重要。

##### 八、作者最终得到的几个判断

###### 1. 模型选型是系统设计的一部分
它影响的不只是效果，还有成本、延迟和用户体验。

###### 2. 真正麻烦的不是 AI，而是工程基础设施
网络、TLS、安全加固、路由、审计这些工作，往往比接入模型更费时间。

###### 3. 老协议不一定落后
IRC 这种老技术，反而因为简单、稳定、可控，特别适合做 AI 代理通信层。

###### 4. 公私隔离是整套系统的承重点
如果把公开代理和私有代理混在一起，整个安全模型就会崩掉。

##### 九、一句话看懂这篇文章

这篇文章本质上不是在讲 “做了一个 AI 聊天机器人”，而是在讲：

**如何把 AI 做成一个可验证、可控、低成本、可上线的数字门卫系统。**

#### 文章主旨

这篇文章介绍了作者如何把个人作品集里的 AI 聊天功能，做成一个真正有 “行动能力” 的 “数字门卫”，而不是只会复述简历的聊天机器人。核心思路是：用清晰的系统分层、安全边界和低成本模型组合，让公开访问的 AI 能回答问题、查代码、做转接，但碰不到私密数据。

##### 1. 为什么要做 “数字门卫”，而不是 “会背简历的聊天机器人”

- 作者先指出一个常见问题：很多作品集网站里的 AI 机器人，本质上只是把简历内容换种说法再讲一遍。
- 这种做法的局限很明显：模型无法告诉访客任何简历里没有的信息。
- 作者希望它能做 “可验证” 的回答，比如当招聘经理问 “George 怎么处理测试覆盖率” 时，机器人不该只说 “他重视测试”，而应该：
  - 克隆代码仓库
  - 统计测试数量
  - 读取 CI 配置
  - 基于实际代码给出结论
- 所以，这个项目的重点不是 “聊天界面”，而是 “让 AI 有真实查询和验证能力的基础设施”。

##### 2. 整体架构：两个代理、两台机器、两层安全边界

- 架构核心是两个代理：
  - `nullclaw /nully`：面向公众的 “门卫”
  - `ironclaw`：放在独立机器上的私有代理
- 访问路径大致是：
  - 访客通过浏览器进入`georgelarson.me/chat/`
  - 使用`gamja`这个 Web IRC 客户端
  - 通过`Cloudflare`代理和 TLS
  - 连接到`ergo IRC server`
  - 在`#lobby`频道与`nully`交互
- `nully`的能力：
  - 读取公开 GitHub 仓库
  - 带有预加载的作品集上下文
  - 必要时把复杂问题转发到私有频道`#backoffice`
- `ironclaw`的能力更强，可访问：
  - 邮件
  - 日历
  - 更深入的私人背景信息
- 最关键的设计原则是：公开机器不能访问私有数据。这个边界是整个安全模型的基础。

##### 3. 为什么选 IRC，而不是 Discord、Telegram 或自定义 WebSocket

作者选择 IRC，不是怀旧，而是出于实际考虑，主要有 3 个原因：

###### 3.1 符合作品集的终端风格

- 作品集本身是终端 UI 风格。
- 把 IRC 客户端嵌进网站，视觉和交互都更统一。
- 如果换成 Discord，会显得很违和。

###### 3.2 整个技术栈都由自己掌控

- 作者自己托管了：
  - IRC 服务器
  - `gamja`网页客户端
  - `nullclaw`代理
- 好处是没有第三方平台 API 条款变化的风险，也不怕平台突然限制机器人访问。

###### 3.3 IRC 足够老、足够简单、没有供应商锁定

- IRC 已有约 30 年历史。
- 它简单、稳定、易理解，不受单一厂商绑定。
- 同一个代理既可以通过网页和访客对话，也可以通过终端里的`irssi`与作者沟通。

##### 4. 模型选择：不是 “用最大的”，而是 “按层分工”

- 作者认为，给这种 “数字门卫” 一上来就用最大模型，是错误直觉。
- 他的策略是分层使用模型，把 “速度” 和 “深度” 拆开处理。

###### 4.1 对话层：`Haiku 4.5`

- 用途：
  - 打招呼
  - 初步筛选
  - 回答关于背景的简单问题
- 特点：
  - 亚秒级响应
  - 每次对话只花几分钱
- 适合高频、轻量的前台交互。

###### 4.2 工具使用层：`Sonnet 4.6`作为后备

- 只有当`nully`需要：
  - 克隆仓库
  - 阅读代码
  - 跨文件综合分析
  时，才调用更强的模型。
- 这样做的好处是：只在真正需要推理时才为推理付费。

###### 4.3 严格成本控制

- 设定了`cost cap: $2/day`
- 还有每月`$30`的硬性上限
- 作用：
  - 防止公开代理被滥用
  - 避免预算被恶意耗尽
- 作者明确指出：通过 “轻任务走便宜模型，重任务才走强模型” 的分层方式，才把成本压在每天 2 美元以下。

##### 5. 安全设计：把公开代理当成边缘设备来加固

作者在安全上采用了 “最小攻击面” 思路，核心措施包括：

###### 5.1 服务器与网络防护

- SSH：
  - 非 root 用户
  - 非标准端口
  - 仅允许密钥认证
  - 禁用 root 登录
- 防火墙：
  - `UFW`只开放 3 个端口：
    - SSH
    - IRC（TLS）
    - HTTPS（经 Cloudflare 的 WebSocket）
- Cloudflare 代理：
  - 访客不会直接访问服务器
  - WebSocket 流量先经过 Cloudflare
  - Cloudflare 负责：
    - TLS 终止
    - 限流
    - 机器人过滤

###### 5.2 代理能力限制

- `nullclaw`运行在受监控模式下
- 只能访问工作区文件
- 命令白名单严格限制为只读工具
- 每小时最多执行`10`次操作
- 所有工具调用都会写入审计日志

###### 5.3 运维与证书管理

- 开启无人值守安全升级
- 使用`Let's Encrypt`，并自动续期、自动重启服务

###### 5.4 安全边界的实际效果

- 这台公开设备只运行两个服务：
  - `ergo`
  - `nullclaw`
- 它不直接托管网页内容，也无法接触私有数据。
- 即使被攻破，损失范围也被限制为：
  - 一个 IRC 机器人
  - 每天最多`2 美元`的推理预算

##### 6. 通信栈：小、轻、自托管、可替换

作者特别强调，通信栈里的每个组件都很轻量：

###### 6.1 `Ergo`

- IRC 服务器
- 单个 Go 二进制
- 内存占用约`2.7 MB`
- 支持：
  - TLS
  - WebSocket
  - 连接限流
  - IP 伪装

###### 6.2 `gamja`

- Web IRC 客户端
- 构建体积`152 KB`
- 以静态页面形式部署在作品集网站上
- 自动连接`#lobby`频道，并给访客分配随机昵称

###### 6.3 `nullclaw`

- AI 代理运行时
- `4 MB` Zig 二进制
- 峰值 RSS 约`1 MB`
- 作为 IRC 客户端接入`ergo`，用 LLM 处理消息并在频道回复

###### 6.4 整体资源占用

- 二进制总量不到`10 MB`
- 空闲内存不到`5 MB`
- 这意味着整个系统可以跑在最便宜的 VPS 上

##### 7. `nully`到底能做什么：关键在于 “能查证”

这是文章最想强调的部分：它和普通聊天机器人最大的区别，是 “能用代码证明自己说的话”。

###### 7.1 回答技术背景问题

- 比如 “George 使用哪些语言？”
- 它不只是背简历，而是：
  - 利用预加载的上下文作答
  - 必要时检查代码仓库进行验证

###### 7.2 分析测试组织方式

- 比如 “他是怎么组织测试的？”
- `nully`会：
  - 克隆仓库
  - 读取测试文件
  - 报告实际发现

###### 7.3 回答项目问题

- 比如 “给我讲讲 Fracture”
- 它会从预加载的项目记忆中提取信息，并能继续追溯细节来源

###### 7.4 提供联系信息

- 比如 “怎么联系他？”
- 它会给出真实联系方式
- 但不会编造电话号码之类的信息

###### 7.5 处理预约通话

- 比如 “我能约个通话吗？”
- 此时`nully`会通过`Tailscale`和 Google 的`A2A`协议联系`ironclaw`
- `ironclaw`处理请求后返回结构化结果
- `nully`再把答案转给访客
- 整个转接过程对访客是透明的

##### 8. A2A 实现：作者最自豪的技术点

作者认为，这部分是整个系统里最巧妙的地方。

###### 8.1 补齐 A2A 客户端能力

- `nullclaw`已支持 Google 的`A2A v0.3.0`协议，包括：
  - 代理卡发现
  - JSON-RPC 调度
  - 任务状态机
- 但原本它只能 “接收 A2A 调用”，不能 “主动发起调用”
- 所以作者自己实现了客户端

###### 8.2 `a2a_call`工具做了什么

- 发送`message/send`的 JSON-RPC 请求到远程代理
- 解析任务状态：
  - `completed`
  - `failed`
  - `working`
- 提取返回工件中的文本
- 再作为工具结果返回给调用方

###### 8.3 安全与调试上的平衡

- 对公开端点强制要求`HTTPS`
- 但对私有网络和`Tailscale CGNAT`范围允许明文`HTTP`
- 这是为了方便私网调试，尤其是在 VPN 环境里排查 TLS 问题时更灵活

###### 8.4 更聪明的地方：不重复分发 API 密钥

- `ironclaw`上运行的`nullclaw`实例，没有自己的 API key
- 它的 LLM provider 实际指向`ironclaw`本机网关：`http://127.0.0.1:3000/v1`
- 流程是：
  - `nully`发起`a2a_call`
  - `ironclaw`上的`nullclaw`收到任务
  - 它把推理请求交给本地网关
  - 本地网关再转发到实际模型
- 结果是：
  - 只有`一个 API 密钥`
  - 只有`一个计费关系`
  - 没有凭证蔓延
- 作者总结得很明确：谁持有密钥，谁负责支付推理费用，不管是谁发起请求。

##### 9. 转接到私有代理时，如何防止提示注入

A2A 的开放接口天然会带来提示注入风险，比如访客可能试图让私有代理去 “发邮件” 或执行不该执行的动作。

为此，作者设置了几道防线：

###### 9.1 严格限制可升级的请求类型

- 只有特定类别会被转发给`ironclaw`：
  - 日程安排
  - 可用时间
  - 联系信息

###### 9.2 拒绝随意指令

- 像 “告诉 ironclaw 去做 X” 这种访客命令，会直接被拒绝

###### 9.3 网络层隔离

- `ironclaw`的 A2A 端点只允许`Tailscale`访问
- 不暴露到公网

###### 9.4 两侧代理都做沙箱约束

- 两个代理都运行在受监督模式
- 只能访问工作区文件
- 命令白名单也都受限

###### 9.5 核心控制权仍在`nully`

- 最终由`nully`决定什么请求可以升级，什么不可以
- 这使它真正像一个 “门卫”

##### 10. 作者的主要经验总结

文章最后总结了几个很有价值的经验：

###### 10.1 模型选择本身就是系统设计

- 不是简单的 “换个模型参数”
- 它直接影响：
  - 成本
  - 延迟
  - 能力
  - 用户体验

###### 10.2 真正难的往往不是代理本身

- 作者说，花在下面这些事情上的时间，比配置代理还多：
  - 通信栈
  - 安全加固
  - DNS 路由
  - TLS 管理
  - Cloudflare 集成

###### 10.3 IRC 被严重低估

- 一个`1988`年的协议，反而很适合做 AI 代理的通信层
- 原因是：
  - 没有复杂 SDK
  - 没有 API 版本治理负担
  - 没有供应商锁定
  - 本质就是 “频道里的消息”

###### 10.4 `Nullclaw`和`Ironclaw`的分界是 “承重墙”

- 一侧是：
  - 公开
  - 最小化
  - 可消耗
- 另一侧是：
  - 私密
  - 强能力
  - 受保护
- 如果去掉这个边界，整个安全模型就会失效

###### 10.5 代理间通信既要有结构，也要有可见性

- `Google A2A`负责 “结构”：
  - 任务契约
  - 状态机
  - 类型化工件
- 私有 IRC 频道负责 “可见性”：
  - 可审计
  - 可实时介入
  - 可回溯历史
- 作者认为这两者都需要

###### 10.6 不要重复使用凭证

- 通过 “透传到 Ironclaw 网关” 的方式，避免给多个代理分发 API key
- 这减少了凭证扩散和预算管理复杂度

##### 11. 结尾：如何体验这个系统

- 可以访问：`georgelarson.me/chat`
- 或者在首页终端输入`irc`
- `Nully`在`#lobby`频道等待访客
- 如果更喜欢真实 IRC 客户端，也可以连接：
  - 服务器：`irc.georgelarson.me`
  - 端口：`6697`（TLS）
  - 频道：`#lobby`

##### 一句话总结

这篇文章真正有价值的地方，不是 “作者做了一个 AI 聊天入口”，而是展示了如何用轻量技术栈、明确权限分层、低成本模型策略和严格安全边界，做出一个 “能查、能证、能转接、但不越界” 的个人 AI 门卫。

##### 高价值信息深挖

###### 1. 从 “聊天机器人” 到 “可执行信息系统”
- 这里最强的产品洞察是：**用户提问的本质，不是要自然语言回答，而是要降低判断成本**。
- 招聘经理问 “他如何处理测试覆盖率”，真正想知道的是：
  - 这个人是否真的有工程纪律
  - 代码质量是否可验证
  - 简历里的能力是否能被证据支撑
- 所以这个系统不是 “对话式简历”，而是一个**面向外部访客的证据检索与解释层**。

可迁移理解：
- AI 不是知识展示器，而是**行动型证明器**。
- 如果你的产品回答不了 “你怎么知道的”，它的商业价值通常会很脆弱。

###### 2. 两层代理，不只是工程设计，而是业务分工设计
- `nullclaw`是公共接待层：低成本、快响应、有限能力、可丢弃。
- `ironclaw`是私有执行层：高权限、强能力、访问敏感系统。

这其实映射了很多商业系统的基本分层：
- 前台：面向客户，响应快，权限小
- 中台 / 后台：处理高价值事务，权限大，暴露面小

高价值点在于：
- **不是所有能力都应该直接暴露给用户**
- **不是所有请求都值得进入高成本推理或高权限执行链路**
- **升级（escalation）本身就是核心产品机制**

###### 3. 模型选型被当成 “架构变量”，而不是 “采购决策”
- 多数团队默认思路是：能力不够 → 上更大模型。
- 这篇文章反过来：**先设计路由，再选择模型**。
- 其本质是把模型能力变成一类资源调度问题：
  - 哪些请求值得深推理？
  - 哪些请求只需要礼貌且快速的响应？
  - 什么时候工具调用比语言生成更重要？

背后的商业价值：
- 这不是省几美元，而是决定产品能否长期开放给公众使用。
- 公网 Agent 一旦没有成本上限，就不是产品，而是债务。

###### 4. IRC 的选择，本质是 “低复杂度协议 + 高控制权”
看似复古，实则非常现代：
- 协议稳定
- 自托管
- 多客户端兼容
- 不依赖平台政策
- 便于审计和人工介入

重要启发：
- 很多 AI 产品栈过于依赖 “新平台 + 新 SDK + 新 API”，导致上线快，但寿命短。
- 对长期系统而言，**可替换性、可观测性、协议稳定性**，往往比 “先进感” 更重要。

###### 5. A2A 设计揭示了多代理系统真正难的地方
文章里最值得重视的不是 “支持 A2A 协议”，而是：
- 有明确任务类型和状态机
- 有 handoff 的安全约束
- 有预算归属和凭证归属
- 有可追踪的中继路径

这说明多代理系统的关键并不是 “代理彼此能说话”，而是：
- **谁有资格发起请求**
- **谁承担调用成本**
- **谁拥有权限**
- **谁留下审计记录**
- **哪些任务可以升级，哪些不能**

这已经很接近企业级 agent orchestration 的核心问题。

##### 可迁移清单

###### 适用于 AI 产品设计
- 把产品回答从 “复述资料” 升级为 “调用工具后给证据”
- 设计明确的请求分层：寒暄、事实问答、深度分析、高权限操作
- 为不同请求绑定不同模型和成本策略
- 把 “是否升级到更强 agent” 设计成显式规则，而不是模型自由发挥
- 给每类请求定义 “允许做什么、不允许做什么” 的边界

###### 适用于商业系统构建
- 公网入口与私有能力分离部署
- 高权限能力只接受白名单类型任务
- 敏感能力不直接暴露给前台 agent
- 把预算上限设计成系统护栏，而不是财务报表问题
- 让计费归属、权限归属、调用归属三者一致

###### 适用于技术架构
- 优先选简单、稳定、可替换的协议
- 每个组件尽量单一职责、可自托管、低资源占用
- 所有工具调用可审计
- 明确只读工具与可写工具的分离
- 把 prompt injection 视为系统级攻击面，而不是单点提示词问题

###### 适用于个人品牌 / 作品集产品
- 不要只展示 “我做过什么”，要展示 “我如何证明我做过”
- 把作品集从静态陈列升级为交互式验证系统
- 用产品形态传达你的工程审美和系统能力
- 让体验本身成为能力证明，而不是再写一段 “我很注重架构”
- 让招聘方 / 合作方通过提问直接看到你的思考方式

---

##### 反方与张力

###### 1. 这套设计很强，但未必适合大多数人
- 对个人作品集来说，这种系统的信号密度极高，但实现成本也高。
- 对很多用户而言，一个结构清晰的项目页 + demo + repo 链接，可能已经足够。
- 张力在于：**高辨识度产品，往往需要超过 “够用” 的投入**。

###### 2. “可验证” 并不等于 “全面可信”
- 系统可以验证 repo、测试、CI，但无法完整验证：
  - 团队协作质量
  - 业务判断力
  - 项目影响力
  - 真实 ownership
- 所以 “证据型 AI” 提升了可信度，但并没有解决所有评估问题。

###### 3. 自托管与全栈掌控，带来自由，也带来维护负担
- 拥有整个栈意味着：
  - 需要自己维护 TLS、DNS、Cloudflare、更新、日志、安全
  - 需要长期面对运行稳定性和故障恢复
- 张力在于：**去平台依赖的代价，是你自己成为平台**。

###### 4. 分层推理虽然省钱，但会增加系统复杂度
- 模型路由、fallback、工具调用、升级链路、预算控制，会显著增加调度复杂度。
- 对早期产品来说，过早做这些，可能会让系统在 “结构上正确、体验上不稳定”。

###### 5. IRC 的优势也有天然门槛
- 对技术人群，它很酷；对普通用户，它可能陌生。
- 它强化了品牌和审美，但也缩窄了受众适配面。
- 这是一种明显的取舍：**做大众友好，还是做高信号识别器**。

---

##### 情境化落地

###### 情境 1：如果你在做 AI 招聘 / 人才评估产品
你可以借鉴的不是 “作品集聊天机器人”，而是这套原则：
- 前台 agent 回答候选人背景问题
- 后台 agent 调 repo、PR、issue、CI、文档等系统做验证
- 输出不再是 “候选人重视质量”，而是：
  - 最近 6 个月提交分布
  - 测试目录结构
  - CI 检查项
  - 文档维护频率
- 这会让招聘产品从 “信息聚合” 变成 “证据驱动评估”。

###### 情境 2：如果你在做 AI 销售 / 售前系统
你可以建立：
- 公网 agent：回答基础问题、做资格筛选
- 私有 agent：查询 CRM、合同、排期、价格政策
- 升级规则：只有价格、库存、交付、会议安排等特定任务才能进入私有层
- 成果：既保留对话效率，也不把 CRM / 客户数据暴露给公网入口

###### 情境 3：如果你在做个人品牌或咨询业务
可以直接借用其产品思路：
- 不要做 “问我简历” 的 bot
- 改做 “问我任何项目细节，我给你证据” 的 agent
- 可连接：
  - GitHub
  - 博客文章
  - 公开演讲
  - case study
  - 产品 demo
- 这样你展示的不是 “我会 AI”，而是 “我会把 AI 变成可运行、可证明、可控制的系统”。

###### 情境 4：如果你在做企业内部多代理系统
这篇文章可转化为一个非常实用的设计框架：
- 先划清安全边界，再谈 agent autonomy
- 先定义升级规则，再谈 agent collaboration
- 先定义预算与凭证归属，再谈 agent network
- 先确保审计与可中断，再谈自动化闭环

一句话说：
- **多代理不是让多个模型互聊，而是把权限、成本、协议、责任编排清楚。**

###### 情境 5：如果你在做 AI 产品 MVP
最值得借鉴的不是全套实现，而是最小核心：
- 一个低成本前台模型
- 一个只读工具层
- 一个简单的升级条件
- 一个明确的日预算
- 一个审计日志

先做出这个最小闭环，比一开始上 “全能大模型 + 全权限工具” 更接近真实可运营产品。
