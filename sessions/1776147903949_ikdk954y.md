## 正文

**Barret李靖**

Spec-driven development (SDD) 的通用实现基本会参照 openspec，实践下来，效果还是一般，大模型会偷懒，任务拆解不充分，也缺少 review 过程。

想让 Agent 持续跑长程任务，同时确保交付质量，需要让它明确项目目标，并将任务拆解到最小颗粒度，再让每个小任务在干净的环境下执行，执行之后，用子 Agent 对当前提交的代码进行 review，进入到 review → feedback → modify → review 的循环。

每个环节都需要精心构造最有效的 context，例如 review 过程，需要给定代码上下文、修改记录、验证手段、脚本工具库等等。

真实项目的执行过程，会包含立项、拆迭代、拆任务等过程，将这套流程复刻到 coding agent 的 plan 过程，依然奏效。如图一，它是一个跑了大概半天任务，而对于更复杂的任务，可以跑一两天不停歇。

每个 sprints 和 tasks 的执行过程，以及 review 的规范，尽量严苛，可以考虑编写脚本的方式来保障质量，例如架构必须分层，L2 可以调用 L1 和 L0，倘若 L0 调用了 L2 就是反模式，需要报错阻断，这种规则问题就可以交给 eslint + governance scripts 来保障的。code review 过程中，也可以要求 AI 根据需要，自主编写文档/程序来确保项目规则/脚本持续沉淀。

## 通俗精炼（1）

### 2026-04-14 06:24:38

#### 用更严格流程，提升 Coding Agent 的交付质量

##### 核心观点

作者认为，常见的 Spec-driven development（SDD）做法虽然参考了 openspec，但实际效果一般。主要问题是：**大模型会偷懒、任务拆解不够细、缺少系统化 review**，所以长程任务容易跑偏，质量也不稳定。

##### 关键方法

要让 Agent 持续执行复杂任务、同时保证结果可用，关键是把人类真实项目流程“搬”给 AI：

- **先明确项目目标**
- **再把任务拆到最小颗粒度**
- **每个小任务在干净环境中独立执行**
- **完成后交给子 Agent 做 code review**
- **进入 review → feedback → modify → review 的闭环**

本质上，就是把 AI 开发从“直接写代码”，升级为“按工程流程协作交付”。

##### 重点不在写代码，在构造上下文

作者强调，每个环节都需要精心准备最有效的 context。比如在 review 阶段，不能只给代码，还要补充：

- 代码上下文
- 修改记录
- 验证方法
- 可用脚本和工具库

也就是说，**AI 能否做好，不只取决于模型能力，更取决于你是否把任务环境搭完整**。

##### 为什么这套方法有效

真实项目本来就不是“一次性写完”，而是要经过：

- 立项
- 拆迭代
- 拆任务
- 执行
- review
- 修正

作者发现，把这套流程复刻到 coding agent 的 plan 过程里，依然有效。简单任务可以持续跑半天，更复杂的任务甚至能连续跑一两天。

##### 如何保障质量

作者建议把规范尽量做严，并通过脚本自动化约束质量。例如：

- 架构必须分层
- 高层可以调用低层，低层不能反向调用高层
- 一旦出现违规调用，直接报错阻断

这类规则可以交给 `eslint` 和治理脚本处理。甚至在 code review 中，还可以要求 AI **主动补充文档、脚本和规则**，把项目规范持续沉淀下来。

##### 一句话总结

这条内容的核心不是“AI 会不会写代码”，而是：**要把 AI 当成工程团队来管理，而不是当成一个一次性代码生成器来使用。** 只有通过细任务拆解、独立执行、严格 review 和规则化治理，Agent 才更可能稳定完成长程复杂任务。

## 结构化（1）

### 2026-04-14 06:27:11

#### 主旨概括

这篇内容的核心观点是：**想让 Coding Agent 稳定完成长周期、高质量的开发任务，不能只靠通用的 SDD（Spec-driven development）框架，而是要把真实软件项目里的“立项—拆解—执行—评审—迭代”流程完整复刻出来**。  
作者认为，关键不在于让 Agent 一次性做大任务，而在于**把目标讲清楚、把任务拆细、让执行和 review 严格闭环，并用脚本把规范固化下来**。

##### 1. 现有通用 SDD 的问题

- 目前很多 SDD 的通用实现，基本会参考 `openspec`。
- 但作者实践后觉得，**整体效果一般**。
- 主要问题有三个：
  - **大模型会“偷懒”**，不会主动做到足够细致；
  - **任务拆解不充分**，导致执行时容易糊成一团；
  - **缺少 review 过程**，产出质量难以持续保障。

**通俗理解**：  
如果只给 AI 一个大目标，比如“帮我做一个后台系统”，它往往会直接开干，但中间少了很多人类团队本来会做的步骤，比如拆里程碑、拆子任务、做代码审查，所以结果容易“看起来做了很多，实际不够稳”。

##### 2. 作者给出的核心解决思路

- 要让 Agent 持续跑**长程任务**，同时又保证交付质量，需要做到三件事：
  - **明确项目目标**；
  - **把任务拆到最小颗粒度**；
  - **每个小任务都在干净环境中执行**。
- 小任务执行完之后，还要让**子 Agent 专门对当前代码提交做 review**。
- 整个过程不是一次 review 就结束，而是进入循环：
  - `review → feedback → modify → review`

**举个例子**：  
如果目标是“新增用户登录模块”，不要直接让 Agent 一次做完。更好的方式是拆成：
1. 定义接口和数据结构；
2. 实现登录逻辑；
3. 补测试；
4. 跑验证；
5. 再让子 Agent review 当前提交；
6. 根据反馈修改，再 review 一轮。  

这样比“一次性生成整套代码”更稳定。

##### 3. 为什么上下文设计很关键

- 作者强调：**每个环节都要精心构造最有效的 context（上下文）**。
- 以 review 为例，不能只丢一段代码给 AI，而要同时提供：
  - **代码上下文**；
  - **修改记录**；
  - **验证手段**；
  - **脚本工具库** 等信息。

**关键点**：  
AI 能不能 review 到位，很多时候不是能力不够，而是**给它的信息不完整**。  
比如只看 diff，它可能不知道这段代码在整个项目中的位置；如果再补上相关模块、提交意图、测试方式，它的 review 质量会明显更高。

##### 4. 把真实项目流程搬进 Agent 的 plan 中

- 真实项目通常会经历这些过程：
  - **立项**
  - **拆迭代**
  - **拆任务**
- 作者认为，把这套流程**原样复刻到 coding agent 的 plan 过程里，依然有效**。
- 文中提到：
  - 图一展示的是一个**大概跑了半天**的任务；
  - 对于更复杂的任务，Agent 可以**连续跑一两天不停歇**。

**这说明什么？**  
作者不是在强调“AI 一次写完代码”，而是在强调：  
**只要流程设计对，Agent 可以像一个持续运转的执行系统，长时间推进复杂工作。**

##### 5. 质量保障要靠“严苛规范 + 自动化脚本”

- 作者建议对每个 `sprint`、`task` 的执行过程，以及 review 规范，尽量设置得**更严苛**。
- 这些质量要求可以通过**脚本**来保障，而不是只靠口头要求。
- 文中给了一个很具体的案例：
  - 架构必须**分层**；
  - `L2` 可以调用 `L1` 和 `L0`；
  - 如果 `L0` 反过来调用 `L2`，就属于**反模式**；
  - 这种情况应该**直接报错并阻断**。
- 这类规则可以交给：
  - `eslint`
  - `governance scripts`
  来自动检查和执行。

**通俗理解**：  
不要指望 AI 永远自觉遵守架构规则。  
更靠谱的方法是：**把规则写成程序**，谁违反就自动报错。  
比如“底层模块不能依赖高层模块”，这类原则非常适合脚本化。

##### 6. Code Review 不只是挑错，还要沉淀规则

- 作者进一步提出，在 code review 过程中，也可以要求 AI：
  - **根据需要自主编写文档**；
  - **根据需要自主编写程序/脚本**；
- 目的不是只解决当前问题，而是把项目中的规范、检查脚本、工具链**持续沉淀下来**。

**意思是**：  
一次 review 发现一个问题，不应只改这一次代码；  
更好的做法是顺手补一个规范或脚本，让同类问题以后自动被拦住。  
这样项目会越来越“自带治理能力”。

##### 总结

- 作者的核心经验是：**Agent 做长程开发任务，重点不在“让它更聪明”，而在“把工程流程设计得更完整、更严格”**。
- 关键方法包括：
  - 明确目标；
  - 把任务拆到最小颗粒度；
  - 在干净环境中逐个执行；
  - 引入子 Agent review；
  - 形成 `review → feedback → modify → review` 闭环；
  - 用 `eslint` 和治理脚本固化架构与规范。
- 文中的重要实践数据是：
  - 一个任务可持续运行**约半天**；
  - 更复杂的任务可以连续运行**一两天**。
- 最终目标是让 Agent 不只是“会写代码”，而是像一个有流程、有约束、有质量保障的开发系统。

#### 总结

这段内容的核心意思是：

- 只靠传统的 **Spec-driven development（按规格驱动开发）** 去让 Agent 做开发，效果不够好。

- 每完成一个小任务，就进入一套闭环：**review → feedback → modify → review**。
- 为了让 Agent 跑长任务还能保证质量，需要把真实项目中的流程（立项、迭代拆分、任务拆解、规范约束、质量检查）完整搬到 Agent 的工作流里。
- 一些明确的工程规则，不要只靠 AI 自觉，最好通过 **eslint、governance scripts、自动化检查** 强制执行。

#### 解读

##### 1. 作者想表达的重点是什么？

作者其实是在说一句很现实的话：

> **AI 能写代码，但如果没有流程约束，它很难稳定地产出高质量结果。**

很多人以为，只要把需求写清楚，Agent 就会自动完成复杂开发。  
但真实情况是：

- 它会省步骤；
- 会跳过一些边角问题；
- 会在“看起来差不多”时提前收工；
- 出现问题时，也不一定会主动做严格自查。

所以，问题不只是“模型聪不聪明”，而是**有没有一套能约束它、纠正它、持续推进它的机制**。

---

##### 2. 为什么“拆小任务”这么重要？

因为大模型处理复杂任务时，最容易出问题的地方就是：

- 一次想做太多；
- 中间推理链断掉；
- 忽略依赖关系；
- 最后产出“整体看着对，细节其实有坑”。

把任务拆到最小颗粒度，本质上是在降低每一步的复杂度。  
这样做有几个好处：

- 更容易执行；
- 更容易验证；
- 更容易 review；
- 出错时更容易定位和修复。

可以理解为：  
**不要让 AI 一口气盖整栋楼，而是让它一次只砌一块砖，并且每砌完一层都检查。**

---

##### 3. 为什么要“干净环境”执行？

作者提到“小任务在干净环境下执行”，这很关键。

因为 Agent 在长时间任务里，很容易受到历史上下文污染：

- 前面做过的错误假设会延续；
- 临时补丁会越来越多；
- 旧上下文会干扰当前判断。

干净环境的意义是：

- 每个任务尽量基于清晰目标开始；
- 减少“越改越乱”；
- 让每一步结果更可复现。

这有点像软件工程里的“隔离”和“可回放”思想。

---

##### 4. 为什么 review 比生成代码更重要？

这段话特别强调 review，不只是让 AI 写，还要让另一个子 Agent 去审。

这是因为：

- **生成代码** 解决的是“做出来”；
- **review 代码** 解决的是“做得对不对、稳不稳、后续能不能维护”。

AI 最大的问题往往不是不会写，而是：

- 没发现自己写得不规范；
- 没意识到架构已经偏了；
- 没有主动补验证；
- 没有沉淀规则和文档。

所以 review 闭环的价值在于：  
它让 Agent 不只是“输出答案”，而是开始具备一点“工程治理能力”。

---

##### 5. 为什么要把真实研发流程搬给 Agent？

作者提到：真实项目有立项、拆迭代、拆任务，这一套流程给 Agent 也有效。

这说明一个很重要的判断：

> **Agent 开发不是单次问答，而更像“管理一个初级但高产的工程团队”。**

如果把 Agent 当成“万能程序员”，容易失望；  
但如果把它当成“执行力很强、但需要强管理的工程成员”，就更符合现实。

所以真正有效的，不是一个神奇 Prompt，  
而是：

- 明确目标；
- 精细拆解；
- 强约束执行；
- 严格 review；
- 自动化验收；
- 规则持续沉淀。

---

##### 6. 作者其实在反对什么？

作者并不是反对 SDD，而是在提醒：

- **只有 spec，不够；**
- **只有任务计划，不够；**
- **只有 Agent 自动跑，不够。**

缺的是真正的“过程控制”和“质量保障”。

换句话说，作者反对的是一种过于理想化的想法：

> “把需求丢给 AI，它会自己优雅地完成复杂工程。”

现实是，越复杂的任务，越要靠工程机制兜底。
