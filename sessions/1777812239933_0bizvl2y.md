## 通俗精炼（1）

### 2026-05-03 12:43:34

#### AI 编程流水线的瓶颈：从“工具跟不上模型”到“模型跟不上工具”

##### 核心内容

作者提到，之前用 **Claude Code + Codex** 做了一个自动化开发系统（harness）：  
只要提交 issue，就会有 AI Agent 自动完成：

- 需求规划（plan）
- 代码实现（impl）
- 交叉评审（cross-review）
- 返工修改（rework）
- 提交 PR

这个系统效率很高，一天能提交 100 多个 PR。

##### 当前问题

最近 Claude Opus 能力下降后，整条自动化链路的成功率跌到 **不到 50%**。

过去大家常说：  
> harness 跟不上模型能力。

但这次情况反过来了：  
> 模型能力跟不上 harness 了。

也就是说，自动化工程流水线已经搭好了，但底层模型不稳定或能力退化，会直接导致整个 Agent 工作流失效。

##### 评论区观点

###### 1. Harness 是模型能力不足时的补丁

有人认为，harness 本质上是因为模型还不够强，所以需要流程、约束和工具来辅助。  
如果模型真的达到 AGI，可能就不需要复杂流程了。

###### 2. Harness 可能才是未来

也有人认为，未来的 AGI 不是单纯神经网络，而是“神经网络 + 程序系统”的结合。  
因此 harness 这类工程化框架反而非常关键。

###### 3. 企业真实痛点

有评论提到，他们公司也做了类似系统，但 Opus 能力下降后，团队同样受到明显影响。

##### 总结判断

这条内容反映了一个重要趋势：

> AI Agent 的生产力，不只取决于模型本身，也取决于模型与工程化流程的匹配度。

当模型足够强时，harness 可以放大效率；  
但当模型波动或退化时，复杂 Agent 流水线会被迅速拖垮。

这说明当前 AI 编程自动化还没有完全稳定，真正可规模化落地，需要同时解决：

- 模型能力稳定性
- Agent 流程设计
- 自动评审与纠错机制
- 人机协同边界
- 工程系统容错能力

## 解读（1）

### 2026-05-03 13:02:15

#### 一、内容总结

这条推文讲的是：

作者之前用 **Claude Code + Codex** 做了一个自动化开发系统，也就是所谓的 **harness / agent 工作流**。

流程大概是：

> 提交 issue → AI agent 自动做计划 → 编码实现 → 交叉 review → 修改返工 → 提交 PR

效果曾经很好，**一天能自动提交 100 多个 PR**。

但现在作者认为 **Claude Opus 能力下降了**，导致整条自动化链路成功率不到 50%。  
以前大家常说：

> harness 跟不上模型能力。

但现在反过来了：

> 模型能力跟不上 harness 了。

评论区也有人表示类似情况：公司内部的 agent 系统也因为 Opus 表现变差而受到影响。

---

#### 二、深入浅出解读

##### 1. 什么是 harness？

可以把 **harness** 理解成一套“AI 自动干活的流水线”。

单个模型只是一个“大脑”，但 harness 会给它安排：

- 什么时候读需求
- 什么时候写计划
- 什么时候写代码
- 什么时候测试
- 什么时候 review
- 出错后怎么返工
- 多个 agent 如何协作

简单说：

> 模型负责“思考和生成”，harness 负责“组织流程和管控执行”。

---

##### 2. 为什么以前效果好？

因为当模型能力足够强时，它可以在这个流程里稳定完成任务。

比如：

- 需求理解准确
- 计划拆解合理
- 代码质量能过关
- review 能发现问题
- 返工能真的修好 bug

这时 harness 就像一个自动化工厂，模型就是里面的工人。  
工人能力强，流水线自然产出高。

---

##### 3. 为什么现在失败率变高？

作者说的“Opus 降智”，本质上是在说：

> 模型的稳定性、推理能力、代码能力或指令遵循能力下降了。

一旦模型质量下降，整个链路会被放大影响。

例如：

- plan 阶段理解错需求
- impl 阶段写出有问题的代码
- review 阶段看不出问题
- rework 阶段越修越乱

单步失败可能还好，但多步 agent 链路里，每一步都依赖前一步。  
如果每一步成功率都下降，最终整体成功率会迅速崩掉。

---

##### 4. “模型能力跟不上 harness”是什么意思？

过去大家认为：

> 模型越来越强，但工程系统、工具链、harness 还不够成熟。

也就是说，瓶颈在工程系统。

但作者现在的意思是：

> 他的 harness 已经能组织复杂开发流程了，可模型本身变弱了，反而成了短板。

这说明一个问题：

**Agent 系统不是只看设计得多复杂，最终还是高度依赖底层模型质量。**

---

#### 三、我的意见

我认为这件事反映了一个很现实的问题：

##### 1. Agent 系统不能过度依赖单一模型

如果整条链路都押注在某一个模型上，一旦模型更新、降级、风格变化，系统就会大面积失效。

更稳妥的做法是：

- 多模型备选
- 不同任务用不同模型
- 关键步骤加入人工审核
- 对模型输出做自动化测试和验证

---

##### 2. harness 仍然是未来，但需要更强的容错设计

我同意评论里“harness 才是未来”的观点。

因为真正可用的 AI 工程系统，不可能只是“问答式聊天”，而应该是：

- 有流程
- 有记忆
- 有工具
- 有测试
- 有回滚
- 有监督
- 有错误恢复能力

但 harness 不能假设模型永远聪明。  
它必须默认模型会犯错，并设计好兜底机制。

---

##### 3. 当前阶段，AI agent 更适合“半自动化”

完全自动一天提交 100 多个 PR 听起来很酷，但风险也很高。

目前更靠谱的模式可能是：

> AI 做 70%～90% 的重复工作，人类负责关键判断和最终把关。

特别是在代码、生产系统、业务逻辑这类场景中，完全无人值守仍然不稳。

---

#### 四、简短结论

这条推文的核心观点是：

> 好的 agent 流水线已经能大幅提升开发效率，但它的上限和稳定性仍然受制于底层模型能力。

我的看法是：

> harness 很重要，模型也很重要。未来真正强大的 AI 开发系统，一定是“强模型 + 强流程 + 强验证 + 人类兜底”的组合，而不是单靠某一个大模型自动完成一切。
