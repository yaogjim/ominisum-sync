从非结构化文档中提取文本对开发者来说是一个经典难题。几十年来，传统的光学字符识别（OCR）系统一直难以处理复杂的版式，常常将多列 PDF、嵌入式图片和嵌套表格转换为无法阅读的纯文本乱码。

今天，大型语言模型（LLMs）的多模态能力终于使可靠的文档理解成为可能。

LlamaParse 弥合了传统 OCR 与视觉语言基于代理的解析之间的差距。它在 PDF、演示文稿和图像中提供最先进的文本提取能力。

在这篇文章中，你将学习如何使用 Gemini 为 LlamaParse 提供支持，从非结构化文档中提取高质量文本和表格，并构建一个智能个人财务助手。提醒一下，Gemini 模型可能会出错，不应被依赖来提供专业建议。

##### Why LlamaParse?

在很多情况下，LLMs 已经能够有效地执行此任务，但是，当处理大型文档集合或高度可变的格式时，一致性和可靠性会变得更具挑战性。

像 LlamaParse 这样的专用工具通过引入预处理步骤和可自定义的解析指令来补充 LLM 的能力，这些预处理步骤和解析指令有助于对大型表格或密集文本等复杂元素进行结构化处理。在一般的解析基准测试中，这种方法相比直接处理原始文档显示出约 13–15% 的改进。

##### 用例：解析券商报表

券商报表是文档解析的终极挑战。它们包含密集的金融术语、复杂的嵌套表格和动态布局。

为了帮助用户了解自己的财务状况，你需要一个工作流，不仅能够解析文件，而且还能明确地提取表格，并通过 LLM 解释数据。

由于这些高级推理和多模态需求，Gemini 3.1 Pro 是作为底层模型的完美适配。它在巨大的上下文窗口与原生空间布局理解能力之间取得了平衡。

该工作流程分为四个阶段：

1. **导入：** 你将一个 PDF 提交到 LlamaParse 引擎。
2. **Route:** 引擎解析文档并发出一个 `ParsingDoneEvent` 。
3. **Extract:** 此事件触发两个并行任务——文本提取和表格提取——它们并发运行以减少延迟。
4. **综合：** 一旦两个提取过程完成，Gemini 生成一份人类可读的摘要。

这种双模型架构是经过深思熟虑的设计选择： **Gemini 3.1 Pro** 负责解析过程中复杂的布局理解，而 **Gemini 3 Flash** 负责最终的总结——同时兼顾准确性和成本优化。

你可以在 [LlamaParse x Gemini 演示 GitHub 代码仓库](https://github.com/run-llama/llamaparse-gemini-demo) 中找到本教程的完整代码。

##### 步骤 1: 创建和使用解析器

你工作流程中的第一步是解析。你创建一个由 Gemini 3.1 Pro 支持的 LlamaParse 客户端，并在 [resources.py](https://github.com/run-llama/llamaparse-gemini-demo/blob/main/src/llamaparse_gemini/resources.py) 中定义它，以便你可以将其作为资源注入到你的工作流程中。

```python
def get_llama_parse() -> LlamaParse:
    return LlamaParse(
        api_key=os.getenv("LLAMA_CLOUD_API_KEY"),
        parse_mode="parse_page_with_agent",
        model="gemini-3.1-pro",
        result_type=ResultType.MD,
    )
```


`parse_page_with_agent` 模式应用了一层由 Gemini 指导的代理式迭代，以根据视觉上下文修正并格式化 OCR 结果。

在 [workflow.py](https://github.com/run-llama/llamaparse-gemini-demo/blob/main/src/llamaparse_gemini/workflow.py) 中，定义事件、状态和解析步骤：

```python
class BrokerageStatementWorkflow(Workflow):
    @step
    async def parse_file(
        self,
        ev: FileEvent,
        ctx: Context[WorkflowState],
        parser: Annotated[LlamaParse, Resource(get_llama_parse)]
    ) -> ParsingDoneEvent | OutputEvent:
        result = cast(ParsingJobResult, (await parser.aparse(file_path=ev.input_file)))
        async with ctx.store.edit_state() as state:
            state.parsing_job_result = result
        return ParsingDoneEvent()
```


请注意，您不会立即处理解析结果。相反，而是将它们存储在全局的 `WorkflowState` 中，以便后续的提取步骤可以使用它们。

##### Step 3: Generate the summary

提取数据后，你可以提示 Gemini 3.1 Pro 用通俗易懂的语言生成摘要。

## 结构化（1）

#### 文章主旨

这篇文章主要讲的是：如何结合`LlamaParse`和`Gemini`，把复杂的非结构化金融文档（尤其是券商报表）解析成高质量文本和表格，再进一步生成通俗易懂的财务摘要。  
核心价值在于：相比直接把原始 PDF 扔给大模型，这种 “专用解析工具 + 多模态模型” 的组合，在复杂文档场景下更稳定、更准确，也更适合工程化落地。

#### 1. 背景：为什么文档解析一直很难

- 传统 OCR 多年来都很难处理复杂版式文档。
- 对于多列 PDF、嵌入图片、嵌套表格这类内容，传统方法常常只能输出 “不可读的纯文本乱码”。
- 现在，多模态大语言模型的出现，让 “真正理解文档内容和布局” 成为可能。
- 文章指出，`LlamaParse`的作用，就是连接传统 OCR 和基于视觉语言模型的代理式解析，让 PDF、演示文稿、图片中的文本提取更可靠。

**通俗理解：**  
以前像是在 “照着图片抄字”，现在则更像是 “先看懂页面结构，再整理内容”。

#### 2. 为什么选择 LlamaParse

- 虽然 LLM 在很多文档提取任务里已经能工作，但面对**大批量文档**或**格式变化很大的文件**时，一致性和可靠性仍然是难点。
- `LlamaParse`通过两类能力增强了解析效果：
  - 预处理步骤
  - 可自定义的解析指令
- 这些能力特别适合处理：
  - 大型表格
  - 高密度文本
  - 结构复杂的页面元素
- 文章给出的关键数据是：在通用解析基准测试中，这种方法相比 “直接处理原始文档”，**提升约 13%–15%**。

**例子：**  
如果直接让模型读取一份复杂报表，它可能漏掉表格结构；而 LlamaParse 会先把页面拆解和整理，再交给模型理解，结果更稳定。

#### 3. 用例：为什么券商报表是典型难题

- 券商报表被称为 “文档解析的终极挑战”。
- 原因在于它通常同时具备：
  - 密集的金融术语
  - 复杂的嵌套表格
  - 动态变化的页面布局
- 如果目标是帮助用户理解自身财务状况，系统不能只 “读出文字”，还必须：
  - 明确提取表格
  - 再由 LLM 对数据进行解释
- 基于这个需求，文章选择`Gemini 3.1 Pro`作为底层解析模型，因为它兼顾：
  - 超大上下文窗口
  - 原生空间布局理解能力

**通俗理解：**  
一份券商报表不只是 “字多”，而是 “结构非常乱又信息非常密”，所以需要既能看懂版面、又能理解内容的模型。

#### 4. 整体工作流：四阶段完成金融文档理解

文章把整个流程拆成四个阶段：

##### 4.1 导入（Import）

- 用户先把一个 PDF 提交给`LlamaParse`引擎。

##### 4.2 路由（Route）

- 引擎完成解析后，发出一个`ParsingDoneEvent`事件。

##### 4.3 提取（Extract）

- 这个事件会同时触发两个并行任务：
  - 文本提取
  - 表格提取
- 两个任务并发执行，用来降低整体延迟。

##### 4.4 综合（Synthesize）

- 等文本和表格都提取完成后，再由 Gemini 生成一份适合人类阅读的摘要。

**关键设计：双模型架构**

- `Gemini 3.1 Pro`：负责解析阶段的复杂布局理解
- `Gemini 3 Flash`：负责最终总结，兼顾低延迟和成本优化

**这意味着：**
- 难的部分用更强的模型做
- 汇总的部分用更快、更省钱的模型做

#### 6. 第一步：创建解析器并执行解析

##### 6.1 解析器配置

- 在`resources.py`中创建`LlamaParse`客户端。
- 核心配置包括：
  - `parse_mode="parse_page_with_agent"`
  - `model="gemini-3.1-pro"`
  - `result_type=ResultType.MD`

##### 6.2 `parse_page_with_agent`的作用

- 这个模式会在 OCR 基础上增加一层 “由 Gemini 引导的代理式迭代”。
- 它会根据页面的视觉上下文，对 OCR 结果进行修正和格式化。

**简单说：**
不是机械识别文字，而是 “看着页面布局，反复校正提取结果”。

##### 6.3 工作流中的解析步骤

- 在`workflow.py`中，解析后的结果不会立刻处理。
- 它会先被保存到全局的`WorkflowState`中。
- 这样后续的提取步骤就都可以复用这份解析结果。

**这样设计的好处：**
- 状态清晰
- 各步骤解耦
- 方便扩展后续流程

#### 7. 第二步：并行提取文本和表格

- 在解析完成后，需要同时提取：
  - 完整 markdown 文本
  - 表格数据
- 这样做是为了给后续 LLM 足够上下文，帮助它更准确地解释财务报表。

##### 7.1 为什么要分成两个提取任务

- 文本适合提供整体语义和上下文
- 表格则承载了金融报表中最关键的结构化数据

##### 7.2 并行执行带来的好处

- `extract_text`和`extract_tables`都监听同一个`ParsingDoneEvent`
- 因此`LlamaIndex Workflows`会自动让它们**并行执行**
- 好处包括：
  - 降低整体流水线延迟
  - 让架构天然更可扩展
  - 后续如果新增更多提取任务，也容易接入

**例子：**  
如果串行执行，必须先抽完文字再抽表格；并行执行则两项同时进行，整体更快。

#### 8. 第三步：生成最终摘要

- 文本和表格都提取后，系统会提示 Gemini 生成一个 “通俗易懂” 的结果摘要。
- 这里文章改用`Gemini 3 Flash`做总结，原因是：
  - 延迟更低
  - 成本更低
  - 适合文本聚合类任务

##### 8.1 如何确保两类数据都准备好了

- 系统通过`ctx.collect_events`等待两个事件都完成：
  - `TablesExtractionDoneEvent`
  - `TextExtractionDoneEvent`
- 只有两者都返回后，才真正调用 Gemini API 做总结。

**这一步的关键点：**
- 不让模型只看 “半成品”
- 必须等文本和表格都齐全，摘要才更完整
