#### Sandbank

> AI Agent 统一沙箱 SDK — 一次编写，多云运行。

Sandbank 提供统一的 TypeScript 接口来创建、管理和编排云端沙箱。切换 Provider 无需修改业务代码。

**[官网](https://sandbank.dev)** \| **English** \| **日本語**

#### 为什么选择 Sandbank?

AI Agent 需要隔离的执行环境，但每家云厂商的 API 都不一样 — Daytona、Fly.io、Cloudflare Workers 各有一套。Sandbank 将它们统一到一个接口后面：

```
import { createProvider } from '@sandbank.dev/core'
import { DaytonaAdapter } from '@sandbank.dev/daytona'

const provider = createProvider(new DaytonaAdapter({ apiKey: '...' }))
const sandbox = await provider.create({ image: 'node:22' })

const result = await sandbox.exec('echo "Hello from the sandbox"')
console.log(result.stdout) // Hello from the sandbox

await provider.destroy(sandbox.id)
```

把 `DaytonaAdapter` 换成 `FlyioAdapter` 或 `CloudflareAdapter` — 代码零改动。

Sandbank 内置编排层，支持多 Agent 实时协作。 **Relay** 负责沙箱间的消息传递和共享上下文。

```
import { createSession } from '@sandbank.dev/core'

const session = await createSession({
  provider,
  relay: { type: 'memory' },
})

// 在隔离沙箱中启动 Agent
const architect = await session.spawn('architect', {
  image: 'node:22',
  env: { ROLE: 'architect' },
})

const developer = await session.spawn('developer', {
  image: 'node:22',
  env: { ROLE: 'developer' },
})

// 共享上下文 — 所有 Agent 均可读写
await session.context.set('spec', { endpoints: ['/users', '/posts'] })

// 等待所有 Agent 完成
await session.waitForAll()
await session.close()
```

在沙箱内部，Agent 使用 `@sandbank.dev/agent` ：

```
import { connect } from '@sandbank.dev/agent'

const session = await connect() // 自动读取 SANDBANK_* 环境变量

session.on('message', async (msg) => {
  if (msg.type === 'task') {
    // 执行任务...
    await session.send(msg.from, 'done', result)
  }
})

await session.complete({ status: 'success', summary: '完成了 5 个 API 端点' })
```

#### 设计原则

1. **最小接口，最大互操作** — 只做真正的最大公约数 (exec + files + lifecycle)
2. **显式优于隐式** — 不自动 fallback、不缓存、不隐式重试
3. **能力检测，而非假实现** — 不支持就报错，不返回假数据
4. **幂等操作** — 销毁已销毁的沙箱不报错
5. **完全解耦** — Provider 层和 Session 层独立，自由组合

#### 一、先说结论：Sandbank Cloud 是什么？

**一句话总结：**

> Sandbank Cloud 是一个面向 AI Agent / vibe coder / 浏览器自动化场景的“云端沙箱基础设施服务”，它把**隔离计算环境 + 浏览器自动化 + 临时开发环境 + 按次支付**整合成一个极简产品。

它不是传统意义上的云主机，也不是单纯的 browser automation 平台，更不是普通的在线 IDE。  
它更像是：

- **给 AI Agent 用的可编程临时工作空间**
- **给开发者/自动化场景用的“即开即用 codebox”**
- **给浏览器任务提供真实/轻量浏览器执行环境**
- **用 x402 + USDC 做 machine-to-machine payment 的 API 服务**

##### 4）浏览器自动化技术栈：双轨方案

这是这次上线最值得关注的部分。

文档提到每个沙箱都内置浏览器自动化，有两种模式：

###### A. Lightpanda（默认）
特点：

- 轻量级无头浏览器
- 瞬间启动
- 零额外开销
- 适合：
  - 读取页面
  - 数据抓取
  - 简单表单

缺点：

- JS 引擎有限

###### B. Browserbox `--chrome`
特点：

- 在**独立 KVM 微型虚拟机**中运行真实 Chrome
- 支持：
  - 完整渲染
  - 登录流程
  - 复杂 SPA
  - OAuth
  - 验证码
- 支持：
  - VM 快照
  - PNG 截图通过 relay 传输

###### 技术判断

这个设计非常实用，也很“产品化”。

因为浏览器自动化世界有个经典矛盾：

- 轻量 browser 成本低、快，但不兼容复杂页面
- 真 Chrome 兼容性强，但更贵、更重、启动慢

Sandbank 没有只押注一种，而是做了 **分层浏览器策略**：

- 默认走轻模式，提高效率和成本控制
- 复杂场景再切到真 Chrome VM

这背后是很成熟的 infra 产品思路：  
**不是追求技术纯粹，而是做 workload-aware 的分级执行。**

这也很适合 AI Agent，因为 Agent 往往不知道目标站点复杂度，系统可以引导它：

- 先尝试轻浏览器
- 不行再用 `--chrome`

这就是典型的 agent-native 设计。

#### 三、产品理念分析

从官网、README、X 内容看，Sandbank 的产品理念非常鲜明，我总结为 6 个关键词：

---

##### 1）Agent-first，而不是 human-first

这是它和传统云开发环境产品最大的差别。

不是“让人先去控制台点点点”，而是：

- Agent 自主读取 skill 文档
- Agent 自主创建沙箱
- Agent 自主管理支付
- Agent 自主执行命令、文件、浏览器操作

文档甚至直接写：

> 在 Agent 系统提示词中加入这一行，它就能自主学会创建、执行和管理沙箱。

这很不一样。  
大多数 SaaS 仍然是“人注册、拿 API key、集成 SDK”。

Sandbank 的思路是：

> **产品的第一用户不是人，而是 AI Agent。**

这是非常超前也非常一致的设计。

---

##### 2）极简接口，尽量不搞抽象幻觉

README 中设计原则很硬核：

- 最小接口，最大互操作
- 显式优于隐式
- 不自动 fallback、不缓存、不隐式重试
- 能力检测，而非假实现
- 不支持就报错，不返回假数据

这说明团队非常重视“基础设施的可预测性”。

###### 这是一种 infra 工程师审美

很多 AI 产品喜欢“帮你聪明地处理”。  
但在沙箱/执行环境里，过度智能往往意味着：

- 不可调试
- 行为不稳定
- 跨 provider 结果不一致
- Agent 很难建立可靠策略

Sandbank 选择的是更底层、更克制的路线：

> **让系统简单、显式、可组合。**

这也意味着它更容易获得技术开发者信任。

---

##### 3）无需注册、无需 API key、按次付费

官网最亮眼的一句是：

- 无需注册
- 无需 API Key
- 无需订阅
- 通过 x402 + USDC 按次付费
- Agent 自动处理支付

这不仅是支付方案，更是产品哲学：

> **把基础设施消费从“账号体系”改造成“协议调用”。**

传统 API 服务是：

- 注册
- 创建团队
- 绑定信用卡
- 申请 key
- 设置限额
- 月结

Sandbank 想做的是：

- 有钱包即可
- API 402 要求付款
- 客户端支付后自动重试
- 完成调用

这是非常典型的 **machine-native commerce** 方向。

它不是把支付嵌在 UI 里，而是嵌在协议里。

---

##### 4）一次写代码，多云运行；但商业上提供最好用的默认云

开源 SDK 很明显在强调：

- 不绑定 provider
- Daytona / Fly / Cloudflare / BoxLite 都支持
- 换 provider 业务代码零改动

- warm pool

- x402
- db9
- 更完整的体验

这反映出一种成熟策略：

> 开源层解决“可迁移性”，商业层解决“最佳默认体验”。

这样用户更容易接受，因为不会担心被锁死。

##### 5）vibe coding / 云端协作 / 可分享执行现场

这说明 Sandbank 的理念不仅是“跑代码”，还是：

> **把“工作现场”云化、状态化、共享化。**

## 追问（1）

### 回答 · 2026-03-16 08:44:07

可以用一个很具体的场景来讲：

**实例：做一个“自动登录 + 回归测试 + 登录态快照复用”的电商后台沙箱**

假设你有一个电商商家后台，团队每天都要验证这 3 件事：
- 能否正常登录
- 商品发布流程是否可用
- 订单页筛选是否正常

你希望把这件事放到 `Sandbank cloud` 里的云端沙箱中完成，并利用它提到的：
- 浏览器自动化能力
- 内置 browser cli / skill
- snapshot 快照保存登录态和临时文件

这样每次就不用重复人工登录，也不用在本地配置一堆浏览器环境。

**推荐做法**

- 第一步，不要一开始就把“全量 e2e”搬上去，先只做一个高频、最稳定、最值钱的流程，比如“登录 -> 进入商品页 -> 新建商品 -> 校验成功提示”。
- 第二步，把“首次人工登录”与“后续自动化复用”分开。第一次在沙箱里手动完成带验证码、2FA 或企业微信扫码的登录，然后立刻创建一个 snapshot，后续测试都基于这个快照启动。
- 第三步，把自动化拆成两层：
  - `登录态基础沙箱`：只负责保存已登录状态
  - `业务测试脚本`：每次从该 snapshot 拉起新沙箱，执行商品创建、订单筛选等脚本  
  这样登录出问题时，只需要更新基础快照，不影响测试逻辑。
- 第四步，所有测试数据都用“可识别前缀”，比如商品名统一用 `e2e-sandbank-时间戳`，这样方便清理，也避免误伤真实数据。
- 第五步，失败时一定要保留现场：截图、控制台日志、网络错误、当前 URL、关键页面 HTML。沙箱的价值不只是“跑通”，更是“失败后可复盘”。

**这个实例里的最佳实践**

- **登录态管理**
  - 用 snapshot 保存 cookie、本地存储、临时文件，但不要把账号密码硬编码进脚本。
  - 对高风险账号使用测试专用子账号，权限最小化，只开放商品和订单的必要权限。
  - 给 snapshot 设置更新机制，比如 7 天轮换一次，或登录失败后触发人工重建。

- **自动化脚本设计**
  - 不要依赖脆弱选择器，优先用稳定标识，比如 `data-testid`、语义化按钮文本、固定路由。
  - 每个脚本只验证一个业务目标，例如“商品发布成功”，不要把十几个断言塞进一个超长流程里。
  - 加入显式等待条件，比如“等待商品列表出现新商品名”，不要只靠固定 `sleep`。

- **环境隔离**
  - 每次测试从 snapshot 派生新的临时沙箱，不要长期复用同一个运行中的环境。
  - 把“测试环境”和“生产环境”完全分开；如果必须上生产，只允许只读巡检，不允许写操作。
  - 使用独立的测试数据空间，比如测试店铺、测试分类、测试订单标签。

- **可观测性**
  - 每次运行生成统一报告：开始时间、沙箱 ID、脚本版本、是否命中 snapshot、失败步骤。
  - 对关键步骤自动截图：登录后首页、商品提交前、提交成功后、订单筛选结果页。
  - 如果页面涉及异步请求，记录失败请求的接口名和状态码，比只看“页面没出来”更有用。

- **团队协作**
  - 把“创建 snapshot 的方法”和“何时重建 snapshot”写成标准操作文档。
  - 如果多人共用沙箱体系，给不同业务线拆分独立快照，不要所有人共用一个登录态。
  - 在 CI 中只跑核心冒烟用例，完整回归放到定时任务，避免每次提交都跑得过重。

**一个理想工作流**

1. 在 Sandbank cloud 创建商家后台沙箱  
2. 人工完成一次登录  
3. 保存为 `merchant-login-base` snapshot  
4. 编写浏览器自动化脚本：  
   - 打开商品页  
   - 创建测试商品  
   - 校验成功 toast  
   - 截图保存  
5. 每次执行时，从 `merchant-login-base` 启动新沙箱  
6. 脚本跑完后销毁沙箱，只保留日志、截图和报告  
7. 如果登录失效，再人工更新一次 snapshot

**为什么这是最佳实践**
- 省掉重复登录，特别适合有验证码、扫码、2FA 的场景
- 把“登录问题”和“业务流程问题”解耦，排障更快
- 云端沙箱环境一致，比每个人本地浏览器环境更稳定
- 快照 + 临时沙箱模式，兼顾效率和隔离性
- 很适合文章里提到的 e2e 测试、模拟用户登录、凭证和用户态备份

**一句话建议**
最优策略不是“把所有操作都自动化”，而是先把“最贵的人工步骤”——登录和环境准备——沉淀成 snapshot，再把最关键的业务路径做成可重复执行的自动化流程。
