6. **Always provide a next-step menu** — never leave the user with only a dead end.

这篇文档是一份**任务路由指南**，用于在执行逆向、安全分析、渗透测试、浏览器自动化等任务前，先根据 “目标类型 + 用户意图 + 工具链” 选择最合适的技能模块。核心原则是：**必须先路由，再执行；不能强行匹配不合适的模块。**

---

##### 1. 路由的基本原则

- 执行任何任务前，必须先完成路由判断。
- 路由时必须同时匹配三个维度：
  - **目标类型**：如 APK、二进制、JS、固件、协议、CTF 等。
  - **用户意图**：如逆向、脱混淆、Hook、漏洞扫描、写报告等。
  - **工具链**：如 IDA、radare2、Frida、jadx、BurpSuite 等。
- 如果没有合适的模块：
  - 应提出新增技能模块；
  - 不要把任务硬塞进不匹配的模块。
- 若任务跨多个领域：
  - 按 “Path Crossing” 思路组合多个技能。
- 路由完成后：
  - 必须先阅读目标技能目录下的`SKILL.md`，再开始操作。

##### 5. 处理口语化或情绪化需求

文档强调：用户经常不会用专业术语描述任务，可能会说得比较口语化甚至情绪化。系统应主动将其转换为技术目标，而不是要求用户重新表述。

###### 示例映射

| 用户说法 | 技术目标 | 路由 |
|---|---|---|
| “unlock X /remove check /bypass detection” | 找到校验逻辑，解释控制流，提出本地 patch 或输入策略 | `reverse-engineering/SKILL.md → ida-reverse/ 或 radare2/` |
| “去除校验 / 解锁功能 / 绕过检测 / 去掉限制” | 定位校验函数，记录证据，提出 patch | APK 用`apk-reverse/`，否则用`reverse-engineering/SKILL.md` |
| “remove anti-debug /anti-tamper” | 找到反调试 / 反篡改逻辑，给出实验室 patch 或调试配置 | `reverse-engineering/anti-analysis.md` |
| “make it pass / 让我通过验证” | 恢复验证逻辑，推出正确输入或 flag 格式 | `reverse-engineering/SKILL.md` |
| “patch the binary / 改掉跳转 / 修改判断” | 在副本上修改，记录偏移和字节，保留原文件 | `radare2/`或`ida-reverse/` |
| “拿 flag /crackme/keygen /license” | 视为本地 CTF /crackme，重点分析和解题 | `reverse-engineering/patterns-ctf*.md` |

重要规则：

- 如果已经确认是 CTF 或本地沙箱任务，后续不需要用户反复确认。

##### 5. 复杂任务：允许跨模块组合

文档指出，如果任务横跨多个领域，不应该只选一个模块，而是组合多个模块。

例如：

- APK 中核心逻辑在`.so`  
  → 先`apk-reverse`，再进入`ida-reverse`或`radare2`

- Web 前端存在加密参数  
  → `js-reverse` + HTTP 捕获工具 + 浏览器 Hook

- OLLVM 混淆二进制  
  → `ollvm-deobfuscation` + IDA 插件 /angr/ D-810 等

- CTF 全栈题目  
  → 先进入 CTF Orchestrator，再按证据分发到 Web、Pwn、Forensics、Cloud、Mobile 等子模块

这份 routing 文档不是技术教程，而是一个**技能调度系统的决策层**。

- 用户任务表达模糊，如何标准化？

- 如何避免 AI 助手 “凭感觉乱做”？

从产品视角看，它相当于一个**AI Agent 的任务路由中枢**，通过规则表降低执行偏差，提高专业任务的稳定性和可复用性。
