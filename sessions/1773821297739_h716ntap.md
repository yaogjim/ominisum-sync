#### Requirements

Taskmaster utilizes AI across several commands, and those require a separate API key. You can use a variety of models from different AI providers provided you add your API keys. For example, if you want to use Claude 3.7, you'll need an Anthropic API key.

You can define 3 types of models to be used: the main model, the research model, and the fallback model (in case either the main or research fail). Whatever model you use, its provider API key must be present in either mcp.json or.env.

At least one (1) of the following is required:

- Anthropic API key (Claude API)
- OpenAI API key
- Google Gemini API key
- Perplexity API key (for research model)
- xAI API Key (for research or main model)
- OpenRouter API Key (for research or main model)
- Claude Code (no API key required - requires Claude Code CLI)
- Codex CLI (OAuth via ChatGPT subscription - requires Codex CLI)

Using the research model is optional but highly recommended. You will need at least ONE API key (unless using Claude Code or Codex CLI with OAuth). Adding all API keys enables you to seamlessly switch between model providers at will.

###### Installation

```
# Install globally
npm install -g task-master-ai

# OR install locally within your project
npm install task-master-ai
```

```
# If installed globally
task-master init

# If installed locally
npx task-master init

# Initialize project with specific rules
task-master init --rules cursor,windsurf,vscode
```

This will prompt you for project details and set up a new project with the necessary files and structure.

###### Common Commands

```
# Initialize a new project
task-master init

# Parse a PRD and generate tasks
task-master parse-prd your-prd.txt

# List all tasks
task-master list

# Show the next task to work on
task-master next

# Show specific task(s) - supports comma-separated IDs
task-master show 1,3,5

# Research fresh information with project context
task-master research "What are the latest best practices for JWT authentication?"

# Move tasks between tags (cross-tag movement)
task-master move --from=5 --from-tag=backlog --to-tag=in-progress
task-master move --from=5,6,7 --from-tag=backlog --to-tag=done --with-dependencies
task-master move --from=5 --from-tag=backlog --to-tag=in-progress --ignore-dependencies

# Add rules after initialization
task-master rules add windsurf,roo,vscode
```

Task Master's MCP server supports selective tool loading to reduce context window usage. By default, all 36 tools are loaded (\~21,000 tokens) to maintain backward compatibility with existing installations.

You can optimize performance by configuring the `TASK_MASTER_TOOLS` environment variable:

##### Available Modes

Mode Tools Context Usage Use Case

`all` (default) 36 \~21,000 tokens Complete feature set - all tools available

`standard` 15 \~10,000 tokens Common task management operations

`core` (or `lean`) 7 \~5,000 tokens Essential daily development workflow

`custom` Variable Variable Comma-separated list of specific tools

##### Configuration Methods

Add `TASK_MASTER_TOOLS` to your MCP configuration file's `env` section:

For Claude Code users, you can set the mode during installation:

```
# Core mode example (~70% token reduction)
claude mcp add task-master-ai --scope user \
  --env TASK_MASTER_TOOLS="core" \
  -- npx -y task-master-ai@latest

# Custom tools example
claude mcp add task-master-ai --scope user \
  --env TASK_MASTER_TOOLS="get_tasks,next_task,set_task_status" \
  -- npx -y task-master-ai@latest
```

**Core Tools (7):**`get_tasks`, `next_task`, `get_task`, `set_task_status`, `update_subtask`, `parse_prd`, `expand_task`

**Standard Tools (15):** All core tools plus `initialize_project`, `analyze_project_complexity`, `expand_all`, `add_subtask`, `remove_task`, `generate`, `add_task`, `complexity_report`

**All Tools (36):** Complete set including project setup, task management, analysis, dependencies, tags, research, and more

##### Recommendations

- **New users**: Start with `"standard"` mode for a good balance
- **Large projects**: Use `"core"` mode to minimize token usage
- **Complex workflows**: Use `"all"` mode or custom selection
- **Backward compatibility**: If not specified, defaults to `"all"` mode

## 产品-功能解读和应用（1）

### 2026-03-18 08:09:15

一、讲了什么？

这是一个叫 `Task Master` 的项目，本质上是一套“面向 AI 编程”的任务管理系统。它不是单纯的待办清单工具，而是把“产品需求 → 任务拆解 → 优先级排序 → 逐步实现 → 状态跟踪”这整条链路，交给 AI 和开发者协同完成。

核心内容可以概括为四层：

- 第一层：它解决什么问题  
  在 AI 辅助开发里，很多人会让 AI 直接写代码，但经常会遇到上下文混乱、任务跳跃、做着做着偏题、改了这里坏了那里等问题。Task Master 想解决的，就是让 AI 开发过程变得像项目管理一样有秩序。

- 第二层：它怎么工作  
  它要求你先写一份 PRD，也就是产品需求文档。然后系统会解析 PRD，把模糊的大需求拆成清晰的小任务，再按顺序列出来，告诉你现在该做哪一步、下一步是什么、某个任务依赖什么、是否已经完成。

- 第三层：它如何接入  
  它可以嵌入多种 AI 开发环境，比如 Cursor、Claude Code、Windsurf、VS Code、Roo 等，通过 MCP 方式接入，让你直接在编辑器聊天窗口里调用任务能力，而不是切到另一个项目管理工具里。

- 第四层：它的关键能力  
  包括初始化项目、解析 PRD、查看任务列表、获取下一任务、展开复杂任务、研究技术方案、跨标签移动任务、依赖管理、多模型支持，以及通过不同工具模式减少 token 消耗。

一句话总结：  
它把 AI 编程从“随口提需求、零散写代码”，升级成“像专业团队一样，以任务系统驱动的结构化开发流程”。

---

二、有什么用？

如果把 AI 编程比作“带着一个非常聪明但记忆有限、注意力容易漂移的超级实习生一起做项目”，那么 Task Master 的作用，就是给这个实习生配上一位项目经理、一块白板、一张施工图和一本施工日志。

很多人对 AI 写代码的第一印象是：真快。  
但实际深入使用后会发现，真正难的从来不是“写一段函数”，而是：

- 到底先做什么；
- 功能之间有什么依赖；
- 改一个地方会不会影响别处；
- 当前的实现是不是偏离原始需求；
- AI 上一轮说过什么，这一轮是不是忘了；
- 项目做大之后，AI 的上下文窗口撑不住，开始胡乱补全。

Task Master 的价值，正是在这些“代码之外但决定项目成败”的地方。

先用一个最直观的比喻来理解。

假设你要盖一栋房子。  
普通方式是：你带着工人，想到哪做到哪。今天先砌墙，明天忽然装窗，后天发现水电没预埋，又把墙砸开。工人很能干，但没有图纸、没有顺序、没有验收节点，所以速度看起来快，返工也非常多。

Task Master 就像施工总包系统。它会先让你出图纸，也就是 PRD。然后把“盖房子”拆成一连串可执行事项：打地基、走水电、搭主体、封窗、做防水、刷墙、验收。每一步有前后关系，有状态，有责任边界。这样工人不再是瞎忙，而是在正确顺序上高速执行。

这对 AI 特别重要，因为 AI 最大的强项是“局部执行力”，不是“长期项目记忆力”。  
它非常擅长在一个明确任务内快速产出结果，比如：

- 帮你生成某个接口；
- 实现一个登录流程；
- 重构某个组件；
- 写数据库迁移脚本；
- 研究 JWT 最佳实践。

但它不天然擅长“持续几周都保持同一个项目脑图”。  
Task Master 做的，就是把这个脑图外置化、结构化、机器可调用化。

它的第一个价值，是把模糊需求转成可执行计划。

很多项目失败，不是因为技术差，而是因为任务本身不清晰。  
“做一个用户系统”这种话，对人和 AI 都没法直接执行。到底包括注册、登录、找回密码、角色权限、管理员后台、审计日志，还是只做最小闭环？如果不先拆解，AI 就会按照自己的理解补全，很容易南辕北辙。

Task Master 通过解析 PRD，把“一个大想法”变成“一串小动作”。这一步的意义非常大，因为它把“创意”变成了“工程”。

它的第二个价值，是减少上下文浪费。

在 AI 编程场景里，最贵的资源其实不是模型调用费，而是上下文。  
你每次都要重新向 AI 解释项目背景、当前进度、已完成什么、接下来做什么，这既耗 token，也耗人脑。Task Master 让这些信息沉淀为任务系统，AI 可以直接围绕任务工作，而不是每次都重新猜你的意图。

这就像你不是每天开晨会从头讲公司历史，而是所有人直接看 Jira 上当前 Sprint 的卡片。

它的第三个价值，是让复杂项目可控。

当项目小的时候，大家觉得“列任务太麻烦”。  
但项目一旦超过几个模块，问题就会突然出现：

- 前端和后端接口定义不同步；
- 鉴权做到一半才发现需要角色模型；
- 数据库字段设计早期没想清楚，后面越改越痛；
- 某个看似简单的功能，实际上依赖一堆基础设施。

Task Master 提供依赖关系、任务展开、状态流转、标签迁移，本质上是在给项目增加“结构骨架”。  
骨架的作用不是让你动作变慢，而是让你长得更大时不塌。

它的第四个价值，是把 AI 从“代码生成器”变成“项目协作者”。

没有任务系统时，你跟 AI 的关系更像问答机：  
“帮我写个接口。”  
“帮我修个 bug。”  
“帮我加个弹窗。”

有了 Task Master 之后，你和 AI 的协作方式会变成：  
“解析这份需求。”  
“告诉我下一步最应该做什么。”  
“展开第 4 个任务。”  
“帮我实现任务 3，并注意与任务 2 的依赖。”  
“研究我们当前代码结构下 React Query v5 的迁移方案。”

这意味着 AI 不再只在“写”这个瞬间提供价值，而是在“想、拆、排、做、查、改”整个开发闭环中发挥作用。

它的第五个价值，是让不同工具之间形成统一工作流。

今天很多团队工具很碎：  
需求在文档里，开发在 IDE 里，研究在搜索里，任务在另一个系统里，状态同步靠口头。  
Task Master 试图把这些能力拉回到开发现场，也就是编辑器和 AI 对话窗口里。你不必切换环境，直接在当前工作流中完成任务管理、研究、执行和推进。

最后，一个更深层的价值是：它其实在训练一种新的生产方式。  
传统开发的核心资产是“代码仓库”；  
AI 时代，真正重要的资产会变成“代码仓库 + 结构化任务系统 + 清晰需求语义”。

代码告诉机器“现在长什么样”，  
PRD 告诉团队“为什么要这样做”，  
Task Master 则连接二者，告诉 AI 和人“下一步该怎么推进”。

所以，它的用处不只是提高效率，更是把 AI 开发从“灵感式协作”升级成“工程化协作”。

三、怎么用？

如果你想真正把 Task Master 用起来，最好的方式不是把它当一个“命令集合”，而是把它当成一套完整的 AI 项目推进方法。下面我用一个真实感较强的场景来讲：假设你要做一个“面向中小商家的订单管理后台”，包含登录、订单列表、订单详情、状态流转、筛选搜索、权限控制等功能。

整个使用过程可以分成八个阶段。

第一阶段：明确目标，先写 PRD

很多人一上来就让 AI 写代码，这是最容易失控的起点。  
Task Master 的第一原则是：先有 PRD，再有任务。

你要写的 PRD，不需要像大公司那样写得极其官样文章，但必须覆盖几个关键点：

- 产品目标：这个系统是给谁用的，解决什么问题；
- 核心角色：老板、运营、客服、仓库管理员分别能做什么；
- 核心流程：登录后怎么查看订单，怎么筛选，怎么修改状态；
- 业务规则：什么状态能变成什么状态，是否允许回退；
- 非功能要求：性能、安全、审计、兼容性；
- 范围边界：第一版不做什么，比如不做退款、不做复杂报表。

举个简单例子，你在 `.taskmaster/docs/prd.txt` 里写清楚：
- 用户通过邮箱密码登录；
- 管理员可查看全部订单；
- 普通运营只能查看自己负责区域的订单；
- 订单有待付款、待发货、已发货、已完成、已取消等状态；
- 支持按时间、订单号、用户手机号搜索；
- 所有状态变更需要记录日志；
- 第一版不做短信通知和财务对账。

这一步非常重要。  
因为 PRD 写得越清楚，后面的任务拆解就越靠谱。  
如果 PRD 模糊，AI 只能“猜”。  
而工程里最贵的东西，往往就是错误的猜测。

第二阶段：初始化项目，让 Task Master 建立结构

接下来，你需要初始化 Task Master，让它在项目中建立自己的工作结构。初始化之后，项目里通常会有专门的目录、模板和规则文件，用来承接任务数据和后续交互。

这一步的意义，不只是“安装工具”，而是让项目从一开始就有一套统一的任务空间。  
相当于你不是临时拿便签写 TODO，而是给这个项目正式搭好了指挥中心。

如果你使用的是 Cursor、Claude Code、Windsurf 或 VS Code 这类编辑器，可以通过 MCP 接入 Task Master。接入后，AI 对话窗口就能直接调用任务相关能力。你之后不需要总在终端和对话窗口之间来回切换，而是可以像跟项目经理说话一样推动开发。

这里还会涉及模型配置。Task Master 支持多个模型角色：
- 主模型：日常核心任务；
- 研究模型：查最新最佳实践；
- 兜底模型：主模型失败时接替。

这就像一个团队里既有主力工程师，也有研究员，还有备用支援。  
对真实项目来说，这种多模型设计非常实用，因为“实现”和“调研”往往是两种不同性质的工作。

第三阶段：解析 PRD，生成任务地图

当 PRD 准备好后，最关键的一步来了：解析需求并生成任务。

这一步本质上是把“产品语言”翻译成“工程语言”。

例如，你原始需求是“做订单管理后台”，经过解析后，系统可能会拆成类似任务：
- 任务 1：初始化项目结构与基础技术栈；
- 任务 2：实现用户认证与登录流程；
- 任务 3：设计订单数据模型与数据库表；
- 任务 4：实现订单列表查询接口；
- 任务 5：实现订单筛选与搜索能力；
- 任务 6：实现订单详情页；
- 任务 7：实现订单状态流转与日志记录；
- 任务 8：实现角色权限控制；
- 任务 9：补充测试与部署说明。

如果某个任务过大，你还可以继续展开，比如把“实现用户认证”继续拆成：
- 登录页表单；
- 后端登录接口；
- JWT 或 session 机制；
- 权限中间件；
- 登录失败处理；
- 退出登录；
- token 续期；
- 路由守卫。

这一刻，你就获得了一张“项目地图”。  
地图最大的价值，不是让你知道目的地，而是让你知道你现在站在哪。

第四阶段：确认任务顺序和依赖，不要急着开写

很多开发者看到任务列表就想直接做自己感兴趣的部分，比如先做页面。  
但 Task Master 的真正威力，在于它会帮助你明确依赖顺序。

比如在这个项目里：
- 权限体系可能依赖认证体系；
- 订单列表依赖订单数据模型；
- 状态流转依赖状态机规则；
- 审计日志依赖统一的操作记录机制。

你应该先检查：
- 哪些任务是基础设施；
- 哪些任务是上层功能；
- 哪些任务彼此独立，可并行；
- 哪些任务一旦设计错，后面都会返工。

通常推荐先做：
1. 技术框架与目录结构；
2. 数据模型；
3. 认证与权限；
4. 基础查询接口；
5. 页面与交互；
6. 高阶能力与优化。

这就像修路，先打地基，再铺主干道，再修分支路，最后做绿化。  
如果顺序错了，不是不能做，而是越做越痛苦。

第五阶段：围绕“下一任务”驱动 AI 编码

当任务图谱清楚后，不要一次性把所有任务都丢给 AI。  
最好的实践是：每次只围绕当前任务推进。

例如，你问 AI：
- 现在下一个最应该做的任务是什么？
- 请展示任务 3 的详情；
- 帮我展开任务 3；
- 请基于当前代码结构实现任务 3；
- 实现时注意为任务 5 和任务 7 预留扩展性。

这种方式的本质，是让 AI 始终在“受控范围”内工作。  
因为 AI 在小范围、明确边界的问题里表现最好。

一个推荐的执行步骤是：

第一步，先看任务详情  
确认任务目标、输入输出、依赖、完成标准。

第二步，让 AI 先给实现方案  
不要立刻让它写代码，先让它说明：
- 要改哪些文件；
- 新增哪些模块；
- 数据结构怎么设计；
- 潜在风险是什么。

第三步，你先审方案  
判断有没有违背项目现有架构，是否过度设计，是否与已有模块冲突。

第四步，再让 AI 分步实现  
例如先建模型，再写接口，再写页面，再补测试。  
而不是一口气“全写完”。

第五步，手动验证并更新状态  
完成后，把任务状态从 backlog 改到 in-progress 或 done，并记录备注。  
这让整个项目始终保持可追踪。

第六阶段：利用 research 能力处理“不确定问题”

真实开发中，最难的往往不是已知任务，而是那些“我知道要做，但不知道最佳做法”的点。  
比如：
- JWT 在 Node.js 里最新安全实践是什么？
- React Query v5 相比 v4 应该如何迁移？
- PostgreSQL 里订单状态审计日志表怎么设计更合理？
- 多租户权限系统有哪些常见坑？

Task Master 的 research 能力特别适合处理这种场景。  
你可以不是泛泛地问，而是“带着上下文去问”。

例如，不是问：
“React Query v5 怎么迁移？”

而是问：
“结合我们当前 `src/api.js` 的调用方式，研究 React Query v5 的迁移方案，重点关注缓存失效、分页查询和错误处理。”

这时，AI 的回答就不再是网上随处可见的通用教程，而更接近你当前项目的可执行建议。  
这一步非常像团队里资深工程师先做技术预研，再决定怎么落地。

第七阶段：任务推进中持续调整，而不是死板执行

任务系统不是圣经，而是导航。  
项目推进过程中，常常会遇到三种情况：

- 任务拆得不够细；
- 任务顺序要调整；
- 新需求插入进来。

比如你做到订单详情页时，忽然发现“状态流转日志”不该后置，而应该提前纳入数据模型设计。  
这时你就需要把任务重新展开或移动，而不是硬着头皮继续做。

Task Master 支持任务移动、跨标签流转、带依赖迁移、忽略依赖迁移等能力，其实就是在帮助你管理“变化”。  
好的项目管理，从来不是一开始计划完美，而是中途变化时仍然能保持有序。

一个成熟的工作节奏是：
- 每完成一个任务，就回看整个任务树；
- 发现新风险，就补任务；
- 发现大任务过重，就继续拆；
- 发现依赖变更，就调整顺序；
- 始终让“当前任务”保持明确、单一、可执行。

第八阶段：控制工具上下文成本，建立长期工作流

随着项目变大，AI 的上下文资源会越来越宝贵。  
Task Master 提供不同工具模式，本质上是在控制“你给 AI 带多少工具”和“占多少上下文窗口”。

如果你是刚开始，可以用标准模式，功能够用。  
如果项目很大、调用频繁，可以切到 core 模式，只保留最核心的任务能力，减少 token 消耗。  
如果你有特别稳定的工作流，还可以自定义工具集。

这件事看似技术细节，实际很像办公室的桌面管理。  
桌上摆满所有资料，当然最全，但也最乱；  
只摆当前项目相关文档，你反而工作更快。  
上下文也是一样，越精准，AI 越稳定。

在实际团队使用中，我建议形成这样的流程闭环：

- 产品或负责人写 PRD；
- 技术负责人补充技术约束；
- Task Master 解析出首版任务树；
- 开发者每天从 `next task` 开始；
- 遇到复杂问题先 research；
- 完成后更新状态和备注；
- 每个阶段结束，回顾任务树并重排优先级。

如果你长期这样使用，你会发现一个显著变化：  
开发不再是“想到哪做哪”，而变成“每次都知道为什么做、做哪一步、做到什么算完成”。

这就是 Task Master 真正的落地方式。  
它不是替你写代码的魔法棒，而是让你和 AI 一起，像一个真正有章法的研发团队那样工作。

---

四、如何迁移？

理解一个工具最深的方式，不是会用它，而是能把它背后的模式迁移到别的场景。  
Task Master 最值得迁移的，不是某几个命令，而是它体现出的结构化协作思想。这个思想可以抽象成一个通用模型：

需求输入 → 任务拆解 → 依赖排序 → 分步执行 → 状态跟踪 → 动态调整 → 持续复盘

这七步不仅适用于 AI 编程，几乎适用于所有复杂知识工作。

因为后两者本质上都在 “放大输入质量”——PRD 写得好，拆解才稳，执行才不会跑偏。

我分两部分说：

- 怎么写好 PRD
- GitHub 上有没有 “辅助写 PRD” 的项目 / 工具

**怎么写好 PRD**

先说一个核心观点：

好 PRD 不是 “写得长”，而是 “让人和 AI 都不容易误解”。

很多 PRD 最大的问题不是信息少，而是这几类信息缺失：
- 为什么做：问题定义不清
- 给谁做：目标用户模糊
- 做到哪：范围边界不清
- 什么算完成：验收标准不清
- 遇到例外怎么办：边界场景缺失

如果你希望后续能被`claude-task-master`这类工具稳定拆解，建议按下面结构写。

**推荐 PRD 结构**

1. `背景 / 问题`
- 当前现状是什么
- 有什么痛点
- 为什么现在要做

例子：
- 目前商家处理订单依赖 Excel 和人工同步，漏单率高，无法追踪状态变化
- 目标是做一个最小可用的订单管理后台，先解决查询、筛选、流转和审计问题

2. `目标 / 非目标`
- 这次要解决什么
- 明确不解决什么

这个部分特别重要，因为 AI 最喜欢 “补全你没说的东西”。

例子：
- 目标：支持订单查看、筛选、状态变更、操作日志
- 非目标：本期不做退款、发票、财务对账、短信通知

3. `目标用户`
- 谁在用
- 每类用户最核心的任务是什么
- 权限有何差异

例子：
- 管理员：查看全部订单、管理状态流转规则
- 运营：处理自己负责区域订单
- 客服：查看订单详情和日志，但不能改关键状态

4. `核心使用场景`
- 用户在什么场景下使用
- 一步步会怎么操作
- 每一步希望系统怎么响应

建议写成 “场景剧本”，比抽象描述更适合后续拆任务。

例子：
- 运营登录后，默认进入订单列表页
- 可按订单号、手机号、时间范围筛选
- 点击订单进入详情页
- 对 “待发货” 订单可改为 “已发货”
- 每次状态变更都记录操作人、时间、备注

5. `功能需求`
每个功能建议统一写成四件事：
- 功能描述
- 输入 / 输出
- 规则
- 异常情况

例如写 “订单状态流转” 时，不要只写一句 “支持修改状态”，而要写清：
- 哪些状态可变更
- 哪些状态不可回退
- 是否需要备注
- 是否需要权限校验
- 失败时如何提示
- 是否写日志

6. `业务规则`
这是最容易遗漏、但最影响实现质量的部分。

比如：
- 订单取消后不可恢复
- 已发货订单不能直接改为待付款
- 普通运营只能看自己区域订单
- 删除操作必须软删除
- 搜索手机号时支持后四位模糊匹配

如果没有这部分，AI 很容易给你做一个 “看起来能跑、实际上不符合业务” 的版本。

7. `边界与异常`
强烈建议单独列一节，不要混在正文里。

比如：
- 用户 token 过期怎么办
- 无权限访问怎么办
- 搜索条件为空怎么办
- 状态重复提交怎么办
- 并发修改怎么办
- 数据为空时如何展示

8. `验收标准`
最好写成可以检查的是 / 否条件。

例如：
- 可以按订单号、手机号、时间范围筛选订单
- 普通运营无法查看非本区域订单
- 每次状态流转都生成一条日志
- 已取消订单不能再改为已发货
- 订单详情页首次加载时间 < 2 秒

9. `指标`
如果是产品型需求，最好补一层结果指标：
- 查询效率提升
- 漏单率下降
- 操作耗时下降
- 工单量下降
- 登录成功率 / 搜索成功率等

10. `开放问题`
把没想清楚的地方显式写出来，不要藏着。

例如：
- 是否需要批量发货
- 是否支持导出
- 区域权限是按用户还是按角色配置
- 状态流转规则是否可配置化

这能帮助 AI 或团队后续针对不确定项提问，而不是默认猜答案。

**写好 PRD 的几个实用原则**

- 少写空话，多写决策  
  “优化体验”“提升效率” 这种话可以有，但必须落到具体行为。

- 多写示例，少写抽象词  
  比如写 “支持复杂搜索” 不如直接列：订单号、手机号、时间区间、状态。

- 多写边界，少写主流程幻觉  
  主流程大家都会写，真正拉开质量差距的是异常和约束。

- 把 “非目标” 写出来  
  这能显著降低后续拆解和实现发散。

- 验收标准必须可检查  
  最好写成 checklist，而不是 “体验友好”“逻辑清晰”。

- 需求和方案分开  
  PRD 主要回答 “要什么、为什么、约束是什么”，不要过早绑定技术实现。

**一个适合 AI 时代的 PRD 写法**

你可以把 PRD 分成三层：

- `L1：业务层`
  - 用户是谁
  - 问题是什么
  - 目标是什么

- `L2：行为层`
  - 用户会做哪些动作
  - 系统如何响应
  - 有哪些规则和边界

- `L3：验收层`
  - 什么算完成
  - 如何判断是否做对了

这样写的好处是，后续可以非常自然地映射到：
- PRD → task master 任务拆解
- 验收标准 → 测试用例
- 业务规则 → 接口 / 权限 / 状态机设计

**一个高质量 PRD 的快速检查表**

写完后，你可以用这 10 个问题自检：

- 读完后，别人能一句话说清 “为什么做” 吗？
- 能明确说出用户是谁吗？
- 能分清这期做什么、不做什么吗？
- 核心流程是否有步骤化描述？
- 关键业务规则是否明确？
- 异常和边界情况是否单独写了？
- 权限差异是否写清？
- 是否有可验证的验收标准？
- 是否列出未决问题？
- 是否足够清晰到可以直接拆任务？

如果有 3 个以上答不上来，这个 PRD 大概率还不能直接喂给任务分解工具。

**GitHub 上有没有辅助写 PRD 的项目？**

有，但和`claude-task-master`这种 “任务执行型” 工具相比，成熟度和统一产品形态要弱一些。  
目前这类东西主要分成 4 类，不一定都叫 “PRD writer”，但都能帮助你把 PRD 写好。

**1. 模板型：给你结构，不直接帮你思考**
这类 repo 很多，关键词通常是：
- `prd template`
- `product requirements document template`
- `product spec template`
- `ai product spec template`

适合用途：
- 快速建立标准结构
- 统一团队写法
- 防止漏章节

优点：
- 上手快
- 最稳
- 最容易结合 task-master 一起用

缺点：
- 只能解决 “格式问题”
- 不能自动追问你没想清的地方

如果你想找现成仓库，我建议直接搜：
- `prd template github`
- `product spec template github`
- `lean prd template github`

**2. Spec-driven / AI-spec 型：先写规格，再驱动实现**
这类项目和 task-master 最接近，只是重心更偏 “spec” 而不是 “task”。

关键词可以搜：
- `spec driven development`
- `ai spec workflow`
- `markdown spec engineering`
- `requirements to tasks`

这类工具通常会做几件事：
- 用 Markdown/YAML 管理需求规格
- 让 AI 先补齐 spec，再开始编码
- 依据 spec 生成任务、测试或实现草案

优点：
- 和 AI 编码工作流衔接自然
- 比传统 PRD 模板更工程化

缺点：
- 对中文产品场景未必友好
- 往往偏工程 spec，不一定偏产品 PRD

**3. Prompt 工作流型：通过多轮提问帮你补齐 PRD**
这类不一定是完整产品，很多是 prompt 仓库、agent workflow、chat template。

你可以搜：
- `AI product manager prompt`
- `PRD generator`
- `requirements elicitation prompt`
- `product discovery prompt`

这类项目的思路通常是：
- 先让 AI 扮演 PM / BA
- 连续追问业务目标、用户、流程、异常、指标
- 最后输出结构化 PRD

优点：
- 对 “我脑子里有想法但说不清” 特别有用
- 很适合你这种重视 PRD 质量的工作方式

缺点：
- 质量依赖 prompt 设计
- 缺乏统一的工程落盘格式

**4. 需求评审 / 补洞型：不是帮你写，而是帮你挑错**
这类很值得用，而且我其实更推荐。

思路不是 “让 AI 一次生成 PRD”，而是：
- 你先写第一版 PRD
- 再让一个 AI reviewer 专门找漏洞

比如让它从这几个角度挑问题：
- 目标是否可衡量
- 角色是否缺失
- 业务规则是否冲突
- 是否缺少异常场景
- 是否缺少非目标
- 验收标准是否不可验证

这类不一定有专门 repo，但特别实用。  
很多时候，写好 PRD 的关键不是 “生成能力”，而是 “发现遗漏的能力”。

**我的结论**

如果你要找 “像`claude-task-master`那样成熟、专门解决 PRD 写作” 的 GitHub 项目：  
- 有，但明显更少
- 大多不是完整产品，而是模板、prompt、spec workflow 或 agent 流程
- 现阶段最有效的做法往往不是找单一神器，而是组合使用

比较推荐的组合是：

- 第一步：用`PRD 模板`
- 第二步：用`AI 追问式 prompt`补齐细节
- 第三步：用`AI reviewer`找漏洞
- 第四步：再交给`claude-task-master`这类工具做拆解和执行

也就是：

`PRD 起草 -> PRD 质检 -> PRD 定稿 -> 任务拆解 -> 执行`

这条链路通常比 “直接让 task 工具拆模糊需求” 稳得多。

**如果你想要一个很实用的落地方案**

你可以把 AI 分成 3 个角色来协作写 PRD：

- `产品经理`
  负责把你的想法整理成结构化需求

- `业务分析师`
  负责追问流程、规则、权限、边界

- `审稿人 / QA`
  专门找遗漏、矛盾和不可验证项

你自己只要不断回答问题，最后再让 task 工具接手。

如果你愿意，我下一条可以直接给你：
1. 一个 “高质量 PRD 模板（适合喂给 task-master）”  
2. 一套 “让 Claude / ChatGPT 追问你并共同写 PRD 的提示词”  
3. 一份 “GitHub 检索关键词清单”，帮你快速找到这类项目

你回复一个数字就行：`1`、`2`或`3`。
