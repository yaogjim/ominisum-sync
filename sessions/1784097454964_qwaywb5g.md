#### Herdr + Pi + Claude Code 最佳实践：以 “订单接口幂等性改造” 为例

下面用一个完整实例说明如何组合：

- **Herdr**：管理多个持久化 Agent 终端、观察状态。
- **Pi**：负责代码库探索、制定计划、测试设计。
- **Claude Code**：负责复杂实现和独立代码审查。
- **Git Worktree**：隔离不同 Agent 的修改。
- **CI**：作为最终质量门禁，而不是相信 Agent 的口头结论。

> 核心原则：**先定义契约，再并行执行；每个 Agent 独占分支和文件；最后由独立 Reviewer 和 CI 验证。**

---

##### 一、具体需求

假设现有项目是一个 TypeScript + Express + Redis 的订单服务：

```text
acme-order-service/
├── src/
│   ├── http/routes/orders.ts
│   ├── services/order-service.ts
│   └── infra/redis.ts
├── test/
├── package.json
└── tsconfig.json
```

现在要完成 Issue `#142`：

> 为`POST /v1/orders`增加幂等请求支持，避免客户端重试时重复创建订单。

###### 验收标准

1. 请求必须携带`Idempotency-Key`。
2. 首次请求正常创建订单。
3. 相同用户使用相同 Key 和相同请求体重试时：
   - 不重复创建订单；
   - 返回第一次请求的状态码和响应体；
   - 增加响应头`Idempotent-Replayed: true`。
4. 相同 Key 携带不同请求体时返回`409`。
5. 两个并发请求使用同一个 Key 时，最多只创建一个订单。
6. 幂等记录保存 24 小时。
7. 不缓存`5xx`响应。
8. Key 必须按用户或租户隔离，防止跨用户读取响应。
9. 通过 lint、类型检查、单元测试和集成测试。

###### 2. 建立统一的`AGENTS.md`

在项目根目录创建：

```md
# AGENTS.md

## 项目环境

- Node.js 20
- TypeScript strict mode
- pnpm
- Express
- Redis 仅用于缓存和分布式协调

## 必须执行的验证命令

- `pnpm lint`
- `pnpm typecheck`
- `pnpm test`
- `pnpm test:integration`

## 修改规则

1. 修改代码前必须阅读批准后的计划文档。
2. 不得直接修改 main 分支。
3. 不得添加生产依赖，除非计划中明确批准。
4. 不得修改数据库 Schema。
5. 不得关闭或跳过现有测试。
6. 不得使用`any`绕过类型错误。
7. 不得在日志、测试快照或提交中写入密钥、Token 和用户隐私数据。
8. 不得执行 force push。
9. 每个 Agent 只能修改分配给自己的文件。
10. 如果实际代码与计划冲突，停止工作并报告，不得自行扩大需求。

## 幂等性功能约束

- 幂等 Key 必须按 tenantId/userId 隔离。
- 请求体需要生成稳定摘要。
- 不得将 Authorization、Cookie 等敏感 Header 写入 Redis。
- 相同 Key、不同请求摘要返回 HTTP 409。
- 并发请求最多创建一个订单。
- 不缓存 5xx 响应。
- 幂等记录 TTL 为 24 小时。

## 提交要求

提交前必须报告：

- 修改文件
- 执行过的测试
- 测试结果
- 未解决风险
- Git commit SHA
```

###### 计划文件应该类似

```md
# Issue 142：订单创建接口幂等性

## 目标

为`POST /v1/orders`增加基于 Redis 的用户级幂等控制。

## 非目标

- 不修改数据库 Schema
- 不为其他接口增加幂等性
- 不替换现有 Redis 客户端
- 不引入新的生产依赖

## API 契约

| 场景 | 结果 |
|---|---|
| 缺少 Idempotency-Key | 400 |
| 首次请求 | 正常创建订单 |
| 相同 Key、相同请求体 | 返回第一次响应 |
| 相同 Key、不同请求体 | 409 |
| 相同 Key 正在处理中 | 409 + IDEMPOTENCY_IN_PROGRESS |
| 业务 4xx | 按现有错误契约处理 |
| 服务 5xx | 不缓存结果，释放处理状态 |

## Redis Key

`idempotency:orders:{tenantId}:{userId}:{sha256 (idempotencyKey)}`

不得直接把原始 Key、Authorization 或 Cookie 写入 Redis。

## 文件所有权

### Implementer

- `src/http/middleware/idempotency.ts`
- `src/http/routes/orders.ts`
- `src/infra/idempotency-store.ts`

### Test Engineer

- `test/integration/orders.idempotency.test.ts`
- `test/helpers/idempotency.ts`

### Reviewer

- 只读，不修改任何文件
```

##### 十、问题修复流程

如果 Reviewer 发现问题，不要让 Reviewer 直接修改。

正确流程是：

1. Reviewer 输出问题。
2. 人类判断问题是否成立。
3. 将确认的问题发送给原 Implementer。
4. Implementer 在自己的 worktree 修复并提交。
5. 将修复提交 cherry-pick 到 integration 分支。
6. 重新执行全部测试。
7. 使用新的 Reviewer 会话复查高风险问题。

例如：

```bash
cd ../acme-142-integration
git cherry-pick <fix-commit-sha>

pnpm lint
pnpm typecheck
pnpm test
pnpm test:integration
```

这能保持角色边界清晰：

- Reviewer 负责发现问题；
- Implementer 负责修改；
- CI 负责验证；
- 人类负责接受风险和合并。

##### 十一、该实例中的关键测试矩阵

| 场景 | 请求 A | 请求 B | 预期结果 |
|---|---|---|---|
| 首次创建 | Key=`k1`，Body=`A` | 无 | 创建一次 |
| 正常重放 | Key=`k1`，Body=`A` | Key=`k1`，Body=`A` | 返回同一订单 |
| 请求冲突 | Key=`k1`，Body=`A` | Key=`k1`，Body=`B` | 第二次返回 409 |
| 用户隔离 | User A，Key=`k1` | User B，Key=`k1` | 各自创建 |
| 并发请求 | 同一用户、Key、Body | 同时发送 | 最多创建一次 |
| 首次 5xx | Key=`k2`，服务失败 | 修复后重试 | 允许再次执行 |
| 重放标识 | 首次请求 | 再次请求 | 第二次包含 replay Header |
| TTL | 首次请求 | 检查 Redis | TTL 约为 24 小时 |

并发测试不能只检查两个响应，还必须检查数据库中的订单数量：

```ts
expect (await countOrdersForUser (user.id)).toBe (1);
```

否则两个请求都返回同一个响应，并不代表底层没有创建两次。

##### 十二、Herdr 在该流程中的正确使用方式

###### 1. Herdr 状态用于观察，不作为完成证据

Herdr 的`working`、`blocked`、`done`很适合快速观察多个 Agent，但真正的交付证据应该是：

- 具体 commit SHA；
- 干净的`git status`；
- 修改文件列表；
- 本地测试结果；
- CI 结果；
- Reviewer 结论。

Agent 显示`done`，不等于功能已经正确完成。

---

###### 2. `blocked`时及时介入

出现以下情况时，Agent 应进入 blocked，而不是自行猜测：

- 计划引用的函数不存在；
- 需要新增依赖；
- Redis 不支持计划要求的原子操作；
- 需求没有定义 Redis 故障时的行为；
- 现有 API 契约与计划冲突；
- 必须修改未授权文件。

人类处理 blocked 的方式应该是：

1. 补充决策；
2. 必要时更新计划；
3. 重新批准计划；
4. 再让 Agent 继续。

不要只回复 “你自己决定”。

---

###### 3. 不让多个 Agent 修改同一 worktree

多个 Agent 共享同一工作目录可能导致：

- Agent A 覆盖 Agent B 的文件；
- 测试结果受到未提交修改影响；
- 一个 Agent 将另一个 Agent 的改动一起提交；
- 无法判断某段代码由谁产生。

最佳实践是：

```text
一个可写 Agent
=
一个 worktree
=
一个分支
=
一组明确文件
```

只读 Reviewer 可以使用 integration worktree，但必须确保它不修改文件。

---

###### 4. 不要盲目追求并行数量

这个实例只需要两个并行执行 Agent：

- 一个实现；
- 一个测试。

不建议再拆成五六个 Agent 同时修改：

- Redis Store；
- Middleware；
- Route；
- Error Handler；
- 测试；
- 文档。

任务过度切分会增加接口协调、冲突和集成成本。只有当模块边界和文件所有权非常清晰时，增加 Agent 数量才有收益。

##### 十四、最值得复用的最佳实践

1. **先计划，后编码**：Agent 不应在需求模糊时直接修改代码。
2. **计划必须引用代码证据**：禁止根据目录名和经验猜测实现。
3. **每个 Agent 使用独立 worktree**：从文件系统层面隔离修改。
4. **按角色而不是按模型分工**：Planner、Implementer、Tester、Reviewer 的职责必须明确。
5. **测试与实现并行，但以同一契约为准**：测试 Agent 不查看实现分支。
6. **Reviewer 使用新会话并保持只读**：减少自我审查偏差。
7. **Herdr 状态不是质量门禁**：commit、测试、CI 和审查才是证据。
8. **规定 Agent 可以修改什么，也要规定不能修改什么**。
9. **遇到计划外问题必须 blocked**：不得自行扩大范围。
10. **Agent 不持有生产密钥，不直接 push/merge，不绕过 CI**。
11. **高风险逻辑必须验证故障和并发场景**：不能只测试正常路径。
12. **由人类承担最终决策责任**：尤其是安全语义、依赖变更和发布风险。

通过这一流程，Herdr 负责让多 Agent 工作**可观察**，Pi 负责让任务和测试**结构化**，Claude Code 负责复杂实现与独立审查，而 Git Worktree、CI 和人工门禁共同保证整个过程**可追踪、可验证、可回滚**。

##### 4. 高质量工作流的核心实践

###### 4.1 建立结构化技能体系

建议为 Pi 创建自定义 Skills 或提示模板，把开发过程拆成标准步骤。核心技能可包括：

- `create-plan`：分析需求并生成详细实施计划
- `implement-plan`：按照计划完成代码实现
- `implementation-review`：检查实现是否符合计划
- `code-review`：以独立审查者身份检查代码
- `use-subagents`：编排多个子 Agent

统一规则写入 `AGENTS.md`，可让不同 Agent 持续遵守同一套标准。文章认为，这是保证多 Agent 工作质量的关键。

###### 4.2 使用 Herdr 进行并行编排

主 Agent 可通过 Herdr CLI 或 Socket API：

- 创建新窗格或标签页
- 启动子 Agent
- 向不同 Agent 发送任务
- 使用 `herdr wait` 等待任务完成
- 汇总并审查各 Agent 的输出

一个典型的四窗格分工案例是：

1. **窗格 1：主 Pi**  
   负责需求规划和核心功能实现。
2. **窗格 2：Claude Code**  
   并行实现另一模块或处理复杂代码。
3. **窗格 3：Pi 审查者**  
   负责代码审查和测试。
4. **窗格 4：辅助 Agent**  
   负责文档、重构或其他支持任务。

Agent 还可以把 Herdr 本身当作工具，自主创建和控制其他 Agent，从而形成接近“AI 开发团队”的协作模式。

###### 4.3 隔离项目、分支和上下文

推荐每个功能或 Issue 使用：

- 独立的 Git 分支
- 独立的 `git worktree`
- 独立的 Agent 会话

这样可以避免多个 Agent 同时修改同一工作目录，降低代码冲突和污染主分支的风险。

Pi 可通过 `/tree` 查看和切换会话树，在不同思路之间进行分支探索，而不会干扰主上下文。

Herdr 工作区可按用途划分，例如：

- `main`：核心开发
- `review`：代码审查
- `experiment`：实验性修改

因此可以把 Herdr 部署在服务器上，让 Agent 持续运行，开发者再通过手机或笔记本远程查看和接管任务。

建议采用以下机制：

- 实时观察 Agent 状态，发现 `blocked` 时及时介入。


##### 三个工具各自解决不同问题

- **Herdr**：类似专为 AI Agent 设计的 tmux，可在持久窗格中运行多个代理，显示 idle、working、blocked、done 等状态，并通过 CLI 或 Socket API 调度任务。

其中 Pi 可通过生命周期钩子向 Herdr 精确上报状态；Claude Code 主要依赖界面检测和会话恢复，集成方式相对间接。

##### 高质量的关键是流程结构化

文章建议把开发拆成明确技能，例如 `create-plan`、`implement-plan`、代码审查和子代理编排，并在项目根目录用 `AGENTS.md` 或 `CLAUDE.md` 统一记录编码规范与禁止事项。

典型分工是：主 Agent 负责规划和核心实现，其他窗格并行开发模块、运行测试、审查代码或补充文档。主 Agent还能通过 Herdr 创建窗格、发送任务并等待结果，形成接近“AI 小团队”的协作模式。

##### 隔离、审查与上下文管理决定可靠性

每个功能或 Issue 应使用独立 Git worktree 和分支，避免 Agent 污染主代码；再结合交叉审查、Git hooks 或 CI 设置质量关卡。Pi 的会话树和上下文压缩可降低上下文膨胀，Herdr 的持久会话则便于远程开发和中断后恢复。
