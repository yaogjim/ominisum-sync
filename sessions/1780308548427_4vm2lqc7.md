## 解读（2）

### 2026-06-01 10:08:00

##### 一、总结

kAI 认为：

- 国内厂商没必要重复造 Coding Agent 的“外壳/框架”。
- 可以直接基于 **pi-coding-agent** 做自家 Agent，包括 DeepSeek、Kimi 等。
- Agent 的 **Harness / Runtime 框架** 已逐渐稳定，类似 Transformer 架构一样，没必要各做一套。
- 更重要的是：用统一框架作为基准，观察和改进自家模型的 **Agentic 行为**。
- Kimi 已从 Python 版 `kimi-cli` 转向基于 TypeScript 和 `pi-tui` 的新 `kimi-code`。

---

##### 二、解读

简单说：

> 不要把精力浪费在“写一个 Claude Code 外壳”上，而应该把精力放在“模型本身怎么更会干活”上。

Coding Agent 大致分两层：

1. **模型能力**  
   会不会理解需求、拆任务、写代码、修 bug、调用工具。

2. **Agent 框架**  
   提供终端交互、文件读写、工具调用、上下文管理、执行命令等能力。

kAI 的意思是：

- 第二层已经有比较成熟的开源方案，比如 `pi-coding-agent`。
- 各家可以复用它，快速搭建自己的 Agent。
- 然后重点优化第一层：让自家模型在这个环境里表现更好。

这就像：

> 大家不需要重新发明“键盘和显示器”，而是应该提升“打字的人”的能力。

热门回复里有人提到 Cursor 的优势，认为 Cursor 因为有自己的 IDE 和大量数据，所以能训练出更好用的 Composer。

kAI 回应的核心是：

- 正因为如此，更应该用 pi 这类可定制框架。
- 它可以模拟 Claude Code、Codex 等环境。
- 想要什么 Agent 行为，可以在框架层定制。

---

##### 三、我的意见

我基本同意。

###### 1. 复用框架是好事

国内厂商如果都各自重写一个 Claude Code 类产品，容易陷入重复建设。

更合理的路线是：

> 统一 Agent 框架 + 各自优化模型能力。

这样能更快迭代，也方便横向比较模型表现。

###### 2. 但框架不是完全不重要

Agent 体验不只靠模型，也靠：

- 工具调用设计
- 上下文管理
- 任务规划机制
- 错误恢复能力
- IDE / CLI 交互体验
- 数据闭环

Cursor 强的地方，不只是模型，也包括产品、数据和工程闭环。

###### 3. 最关键还是数据闭环

谁能收集真实开发场景中的高质量反馈，谁就更容易做出好用的 Coding Agent。

所以结论是：

> 可以基于 pi-coding-agent 起步，但真正的竞争力在于模型、数据、产品体验和持续训练闭环。

##### 1. 总结

作者认为：

- 国内 AI 公司没必要重复造 Coding Agent 框架。
- 可以直接基于 **pi-coding-agent** 做自己的 Agent，包括 DeepSeek、Kimi 等。
- 现在 Agent 的“大框架”已经逐渐稳定，类似 Transformer 架构一样。
- 更重要的是：用统一框架作为 **Harness / 测试基准**，观察和改进自家模型的 Agent 能力。

评论区的核心分歧：

- 有人认为真正强的是 **Cursor 这类产品 + 数据 + 后训练**，不是单纯框架。
- 作者回应：正因为如此，pi 这类框架可定制，能模拟 Claude Code、Codex 等环境，方便调模型行为。

---

##### 2. 解读

简单说，这条推文在讲：

> Coding Agent 的底层框架可能已经没那么神秘了，大家没必要各写一套，重点应该转向模型能力和产品体验。

###### 什么是 Harness？

可以理解为：

> 给模型跑任务、调用工具、执行代码、观察结果的一套“测试和运行环境”。

比如一个 Coding Agent 需要：

- 读文件
- 改代码
- 跑测试
- 看报错
- 再修改
- 最后提交结果

这些流程就需要一个稳定的框架来承载。

###### 作者的观点

作者觉得：

- Agent 框架本身已经逐渐标准化；
- 重复开发意义不大；
- 统一框架反而方便比较不同模型；
- 真正该卷的是：
  - 模型会不会规划；
  - 会不会调试；
  - 会不会长期执行任务；
  - 会不会像 Claude Code / Cursor 一样好用。

---

##### 3. 我的意见

我基本认同。

###### 框架不是核心壁垒

Agent 框架很重要，但它更像“生产线”。

真正决定产品水平的是：

- 模型能力；
- 训练数据；
- 后训练方法；
- 工具调用质量；
- IDE / CLI 产品体验；
- 用户数据反馈闭环。

###### 统一框架有好处

国内厂商如果都基于成熟框架改造，可以：

- 少走弯路；
- 更快验证模型；
- 更容易对比效果；
- 把资源投入到模型和体验上。

###### 但不能只靠框架

仅仅套一个 pi-coding-agent，不会自动变成 Claude Code 或 Cursor。

最终差距还是在：

> 数据、后训练、产品打磨、真实用户反馈。

---

##### 结论

**Agent 框架可以复用，Agent 能力不能照搬。**

国内厂商用统一框架做底座是好事，但真正的竞争力，还是来自模型训练、产品体验和数据闭环。
