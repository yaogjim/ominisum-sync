> **一句话点评**：观点鲜明、架构感强，但证据主要靠类比与主张，缺少实证支撑。
>
> **摘要**：文章批评把组织知识全部放进 Markdown/文件系统的做法，认为这只是用更差的介质重造数据库。作者主张用数据库承载结构化关系、来源追踪和依赖更新，文件层只保留指令、摘要和代理工作区。

## 分析要点

- **核心高价值点**：最有价值的点是把“schema 本身也是上下文”讲清楚：类型、依赖、来源和权威性信息应成为 agent 可查询的一等结构，而不是埋在文本里。
- **留存建议**：中期保留，适合作为知识管理架构讨论的观点参考（提出了文件系统与数据库在组织上下文管理中的结构性差异，对设计 AI 工作流有启发）

**知识要点**

- 文件树中的目录、链接和模板本质上很快会演化成隐式数据库 schema
- 组织知识管理的核心难点不是可遍历性，而是真实性维护、来源追踪和派生更新
- 更合理的分层是：业务系统作事实源，文件层承载指令与摘要，数据库层保存结构化关系与 provenance

**行动项**

- 审视现有知识库中哪些关系、状态和来源信息其实已经在用隐式文件约定表达
- 为关键决策、文档和任务建立结构化元数据表，而不是仅靠 Markdown 链接维护
- 设计从 Drive、Slack、Notion、CRM 等源系统抽取指针和依赖关系的最小数据模型

### a file system is not all you need

there's a couple of articles going around on structured context graphs for knowledge work and argue that files are the best primitive

heres one:

> Company Graphs = Context Repositoryeverything is a context problem when people say AI cant do real work, what theyre actually saying is they gave it bad context @alexalbert\_\_ said 2026 will transform knowledge work (read this after you...
>
> — Heinrich

and the diagnosis is true: context is the bottleneck. companies are sitting on scattered knowledge: decisions, rationale, meeting outputs, changing priorities. agents need a structure to traverse it without starting from zero every time

but this ongoing romanticization of putting everything in markdown files is reinventing the database in the worst possible substrate. heres why

#### the data modeling problem

the article talks about wikilinks as "semantic connections" and maps of content for navigation

but the moment you need to query across your graph, like find all decisions that contradict the current roadmap, you're doing a full text scan across thousands of files. a real database gives you joins, indexes, constraints. markdown files just give you grep

that company directory tree?

```markdown
company/
├── org/
│   ├── decisions/
│   ├── strategy/
│   ├── competitors/
├── projects/
│   ├── product-alpha/
│   │   ├── features/
│   │   ├── decisions/
```

that's a schema. decisions have a many-to-many with features. competitors link to research

congratulations, you've built a database

of course it works at a small scale. lots of things do

#### maintenance is the real killer

the article names the right failure mode. every wiki and knowledge base dies because maintenance is expensive. then it handwaves the solution with "agents don't get bored of maintenance"

the problem is structural

if your source of truth is a google doc and you've extracted claims into a markdown note, you now have two copies. two copies drift. no matter how diligent your agent is, the moment the original doc gets edited by a human, the note becomes stale

a database with a reference to the original source doesn't have this problem. you store a drive file id, a slack message url, a notion block id. information dependencies should be encoded in the database

and when that google doc updates, you trace everything derived from it and cascade the update. dependency tracked, provenance preserved. zero drift by design, not by maintenance discipline

#### the code analogy breaks here

people extend the code analogy to justify cramming everything into files: agents already live in filesystems, so give company context the same shape

but code was easier for models because code has more than textual structure. it’s executable. unit tests run every update to catch errors

company context is nothing like that

a meeting note linking to a strategy doc is not the same relation as a file importing a module. a summarized decision is not self-verifying. a product plan doesn't throw an exception because the sales team is operating on a different assumption. that contradiction can sit there for months, sounding perfectly coherent in prose

so "the agent can traverse the graph" is a much weaker claim than it sounds. traversal is not truth maintenance. a model can move beautifully through a network of notes and still fail to determine which parts are live, which parts are stale, which parts are binding, and which parts were always just one person's interpretation

#### the flattening problem

a note might contain a decision. or a guess. or a meeting summary. or a stale belief that was true three months ago. or someone's personal framing of an issue another team would strongly disagree with

all of it becomes text. all of it becomes traversable. all of it looks more structurally similar than it really is

what is authoritative? what is speculative? what is current? what has been superseded? who owns this piece of knowledge?

a markdown graph makes many things readable. it does not make them governable

and here's the irony: the filesystem is presented as minimalist, but in practice you start adding metadata. status tags. typed links. templates. special notes for decisions. rules for what agents can rewrite and how provenance gets preserved

at some point you're not escaping the need for a richer system. you're rebuilding one inside a folder tree because the folder tree feels philosophically cleaner. the complexity doesn't disappear. it just gets hidden away

#### schema is context too

here's something the file advocates miss entirely: structure is itself information for the agent

when data lives in a typed schema, the agent knows how it was generated. it knows what kind of thing it's reading. it knows what other records depend on it and what it depends on. it can reason about provenance, not just content

a markdown file can tell an agent what a decision says. a schema can tell it whether that decision is still active, who made it, what it superseded, what was derived from it, and what needs to be re-evaluated if it changes

#### better architecture

```text
work apps → drive, slack, CRM, linear, code repos
file layer → instructions, synthesis, agent scratchpad, SOPs for where things live
database layer → extracted info, relationships, pointers to sources, metadata, provenance
```

the work apps are where the source of truth comes from

the file layer is the hot access metadata. where you kickstart the agent with base instructions and teach it basic procedures to form a prior of how/where to look

the database is the graph. it stores derived information, structure, relationships, dependency chains. it points to where things actually live and tracks what was derived from what

#### give your agents a database

>
> — dax
>
> [https://x.com/thdxr/status/2011638639831499041](https://x.com/thdxr/status/2011638639831499041)
>
> ![图片](https://pbs.twimg.com/profile_images/1602333093485891584/mmVqjFNI_x96.jpg)![图片](https://pbs.twimg.com/profile_images/784085800191393793/jnrx5fjL_bigger.jpg)![Image](https://pbs.twimg.com/media/G-rGlJ7XgAA4HaC?format=jpg&name=large)

the end state is an agent that can write its own ETL

it ingests from your existing sources through their APIs. it maintains a structured index with typed relationships and dependency tracking. when a source updates, it knows exactly what to re-evaluate. when you reject its suggestion and do something differently, that goes in a table as a local system of record the agent can reference and learn from over time

when it spawns, the agent can lean on this structure by querying a live graph of your organization's context, tracing claims back to their origin, updating derived beliefs when the ground truth changes

#### the future belongs to organizations that accumulate context

not organizations that write better notes or wikis. organizations that build a structured, pointer-based, provenance-aware layer that gets smarter as they operate

decisions don't evaporate into slack. research doesn't die in someone's head. when a source updates, everything derived from it updates too. when an agent makes a suggestion you reject, that goes in a table. the organization learns from its own record

that's what compounding context actually looks like. a live graph that traces claims to their origin, preserves the distinctions that matter, and makes the whole organization legible to the agents working inside it

and this is whats needed for agents to go from copilots to coworkers

## 结构化（1）

### 2026-03-12 10:13:17

**主旨概括：**  
这篇文章的核心观点是：**“上下文” 确实是 AI 和知识工作的瓶颈，但 “把一切都放进 Markdown 文件和文件夹” 并不是最佳方案。**  
作者认为，**文件系统适合做说明和入口层，但真正的知识图谱、关系、依赖、溯源，应该交给数据库来管理。**

---

##### 1. 背景：作者认同 “上下文很重要”，但反对 “文件万能”
- 文章先引用了一种流行观点：公司知识分散在决策、会议纪要、优先级变化等各处，AI 之所以做不好工作，往往是因为**拿到的上下文太差**。
- 作者认同这个诊断：**context is the bottleneck（上下文是瓶颈）**。
- 但作者反对进一步得出的结论 ——**“文件 / Markdown 是最好的基础结构”**。
- 他认为，这种做法本质上是在**用最不适合的载体重造数据库**。

**例子：**  
原文引用了一条推文，提到**2026 年将改变知识工作**，并拿 “公司图谱 = 上下文仓库” 作为论点；相关贴文显示有**54 条回复、153 次转发、1.3K 点赞、797K 浏览**，说明这种观点传播很广。

---

##### 2. 数据建模问题：文件夹看似简单，实际上已经在 “偷偷建数据库”
- 作者指出，很多人把 wiki link、内容地图、文件目录当成 “语义连接”。
- 但一旦要做复杂查询，比如：
  - **找出所有与当前路线图冲突的决策**
- 你就会发现，Markdown 文件只能靠：
  - 全文扫描
  - grep 搜索
- 而数据库则天然支持：
  - 查询
  - 索引
  - 约束
  - 多表关系（join）

**原文案例：**
```markdown
company/
├── org/
│ ├── decisions/
│ ├── strategy/
│ ├── competitors/
├── projects/
│ ├── product-alpha/
│ │ ├── features/
│ │ ├── decisions/
```

- 作者说，这种目录结构看起来像文件管理，实际上已经隐含了 “schema（模式）”：
  - decision 和 feature 是多对多关系
  - competitor 会连接 research
- 结论：**你其实已经在设计数据库，只是放在文件夹里实现而已。**

**对应引用：**  
作者还引用了文章《**Oops, You Wrote a Database!**》，意思是：  
**不学习数据库的人，最后往往会自己写出一个低配数据库。**

---

##### 3. 维护问题：知识库真正死掉，不是因为没人写，而是因为会 “漂移”
- 文章认为，所有 wiki 和知识库最大的死因不是创建难，而是**维护成本太高**。
- 有人说 “AI agent 不会厌烦维护”，但作者认为这只是回避问题。
- 根本问题是：**如果源信息在 Google Doc，而你又把结论提炼成 Markdown 笔记，就产生了两份副本。**
- 两份副本迟早会：
  - 不一致
  - 过时
  - 漂移（drift）

**例子：**
- 原始信息在 Google Doc
- AI / 人又提取了一份 “结论笔记”
- 如果之后 Google Doc 被人改了，而笔记没同步，AI 读到的就是旧信息

- 作者认为，更合理的方法是：
  - 在数据库里存**源对象引用**
  - 比如：
    - Google Drive 文件 ID
    - Slack 消息 URL
    - Notion block ID
- 然后把 “哪些信息是从哪个来源推导出来的” 记录下来

这样一来：
- 源文档一更新
- 系统就能追踪所有派生信息
- 自动触发重算或更新

**结论：**  
好的系统应该做到：  
**依赖可追踪、来源可追溯、信息不靠人肉维护来避免漂移。**

---

##### 4. “代码类比” 并不成立：知识文本不像代码那样能自我校验
- 有人主张：AI 之所以擅长代码，是因为代码都放在文件里，所以公司知识也应该放在文件里。
- 作者认为这个类比有问题。
- 因为代码不只是 “文本有结构”，它还具有：
  - 可执行性
  - 可测试性

**关键区别：**
- 代码改了，可以跑单元测试发现错误
- 但公司知识不会自动报错

**例子：**
- 一个会议纪要链接到战略文档，不等于代码里的 import 关系
- 一份产品计划和销售团队的理解不一致时，也不会像程序一样抛异常
- 这种矛盾可能会**在系统里静静存在几个月，看起来还都很合理**

**结论：**  
AI 能在知识图谱里 “遍历”，不等于它能判断：
- 哪些内容仍然有效
- 哪些已经过时
- 哪些是正式决策
- 哪些只是某个人的理解

---

##### 5. “文本扁平化” 问题：所有内容都长得像文本，但地位完全不同
- 作者强调，现实里的知识并不都是一种类型：
  - 有的是正式决策
  - 有的是猜测
  - 有的是会议总结
  - 有的是三个月前还成立、现在已失效的旧认知
  - 有的是某个人的主观看法
- 一旦都放进 Markdown，它们都会被 “扁平化” 为普通文本。
- 对 AI 来说，它们都变得 “可读、可遍历”，但**不代表它们同样权威、同样可靠、同样当前有效**。

作者提出几个关键问题：
- 什么是权威信息？
- 什么只是推测？
- 什么仍然有效？
- 什么已经被取代？
- 谁对这条知识负责？

**结论：**  
Markdown 图谱提高了 “可阅读性”，但没有自动带来**可治理性**。

---

##### 6. 文件系统并不真的 “简单”，最后还是会补出一套隐藏结构
- 作者指出，文件系统常被包装成 “极简方案”。
- 但在实际使用中，团队很快就会不断往里补规则，比如：
  - 状态标签
  - 类型化链接
  - 模板
  - 专门的决策笔记格式
  - agent 可以改什么、不能改什么
  - 如何保留来源信息

- 也就是说，复杂性并没有消失，只是**藏进文件夹和命名规范里**了。

**结论：**  
当你不断给文件系统加元数据和规则时，本质上已经说明：  
**你需要的是更丰富的系统，而不是单纯的文件夹。**

---

##### 7. 作者的核心观点：Schema（结构）本身就是上下文
- 作者认为，很多 “文件派” 忽略了一点：  
  **结构化模式（schema）本身就是给 AI 的重要上下文。**
- 如果数据放在有类型的 schema 里，AI 不只知道 “内容写了什么”，还知道：
  - 这是什么类型的信息
  - 它是怎么产生的
  - 它依赖什么
  - 哪些记录依赖它
  - 来源是否可靠
  - 更新后会影响哪些下游内容

**对比：**
- Markdown 文件只能告诉 AI：  
  “这个决策写了什么”
- Schema 还能告诉 AI：  
  - 这个决策是否仍然有效  
  - 谁做的  
  - 它取代了哪个旧决策  
  - 哪些内容是从它推导出来的  
  - 如果它变了，哪些信息要重新评估

---

##### 8. 作者给出的更好架构：文件层 + 数据库层 + 工作应用层
作者最后提出一个三层架构：

###### （1）工作应用层
来源系统包括：
- Drive
- Slack
- CRM
- Linear
- 代码仓库

**作用：**  
这些地方才是真正的**源事实（source of truth）**所在。

###### （2）文件层
包括：
- 指令
- 摘要 / 综合文档
- agent scratchpad（临时工作区）
- SOP（标准操作说明）

**作用：**  
给 AI 提供快速入口、工作说明和查找路径。  
文件层适合做 “热启动” 和 “导航”。

###### （3）数据库层
包括：
- 提取后的结构化信息
- 实体关系
- 指向原始来源的指针
- 元数据
- provenance（溯源）
- dependency chain（依赖链）

**作用：**  
数据库才是真正的 “图谱层”，负责管理：
- 关系
- 派生信息
- 依赖更新
- 来源跟踪

---

##### 9. 一句话结论
**文件不是没用，但它不该承担数据库的工作。**  
更合理的做法是：**用文件做入口和说明，用数据库做知识图谱、依赖管理和溯源，原始事实仍保留在业务系统里。**

## 产品-技术开发（1）

### 2026-03-12 10:14:17

下面我用**产品视角 + 技术架构视角 + 可落地最佳实践**来解读这篇《**a file system is not all you need**》。

---

#### 一、核心观点：它反对的不是文件，而是 “拿文件冒充知识系统”

##### 产品层解读
文章的核心不是 “Markdown 没用”，而是：

> **文件适合承载内容，不适合承载事实、关系、状态、依赖和可追溯性。**

对 AI 产品尤其如此。  
因为 AI 要做的不只是 “读到内容”，而是要回答：

- 哪条信息是**当前有效**的？
- 哪条是**推测 / 草稿 / 会议讨论**？
- 哪条信息**覆盖 / 废弃**了旧结论？
- 结论来自哪里？是否能**追溯到原始证据**？
- 如果源文档变了，哪些下游结论要**重算**？

这些问题，本质上不是 “文本检索问题”，而是**数据建模 + 依赖管理 + 事实治理问题**。

---

#### 二、为什么 “全放文件里” 会在产品上失控

##### 1）查询能力弱：能读，不代表能算
文件系统天然擅长：

- 浏览
- 阅读
- 模糊搜索
- 人工编辑

但 AI 产品需要的是：

- 条件过滤
- 关联查询
- 版本比较
- 状态约束
- 依赖追踪

###### 例子
用户问：

> 找出 “所有与当前 roadmap 冲突的决策”

如果全是 markdown：
- 先全文检索 “roadmap /decision/deprecated /priority”
- 再靠 LLM 理解
- 成本高、速度慢、准确率不稳定

如果是数据库：
- `Decision.status = active`
- `Decision.related_product = roadmap.product_id`
- `Decision.priority != current_priority`
- `Decision.superseded_by is null`

这是结构化查询，不该交给全文扫描硬做。

---

##### 2）会出现 “双份真相”，然后持续漂移
这是文章最重要的一点。

###### 错误做法
- Google Doc 是原文
- Agent 抽取一份 markdown 总结
- Notion 再有一份专题页
- Slack 里还有一次讨论结论

最后你得到的是：
- 多份 “看起来都对” 的副本
- 但没有一个系统知道**谁才是源头**

###### 正确思路
不要复制知识本体，要保存：

- **source pointer**：原始来源引用
  - `drive_file_id`
  - `slack_message_url`
  - `notion_block_id`
  - `linear_issue_id`
- **derived artifact**：从来源抽出的结论
- **provenance**：由谁、何时、依据什么抽取
- **dependency**：哪些结论依赖哪些来源

这样源更新时，系统知道要重算哪些结论，而不是全库重刷。

---

##### 3）文本把不同性质的信息 “压平” 了
这是很多 AI 知识库产品的隐藏灾难。

在一篇笔记里可能混着：

- 已批准决策
- 个人猜测
- 会议纪要
- 历史背景
- 过期结论
- 争议观点

对人来说，靠上下文还能分辨。  
对 agent 来说，如果没有显式 schema，它们都只是 “句子”。

###### 产品后果
Agent 很容易把：
- “讨论过”
误当成
- “已决定”

把：
- “上季度成立”
误当成
- “当前仍然成立”

这会直接导致业务事故。

---

#### 三、对 AI 产品设计的真正启示：要做 “Context OS”，不是 “更聪明的 Wiki”

##### 最合理的三层架构

文章给的方向非常对，可以进一步产品化成：

###### 1. Source Layer：事实来源层
系统只接入，不篡改原始系统：

- Google Drive / Docs
- Slack
- Notion
- Linear / Jira
- GitHub
- CRM
- 数据仓库

职责：
- 作为原始事实来源
- 保存更新时间、作者、权限、链接

---

###### 2. Knowledge Graph / DB Layer：结构化上下文层
这是 AI 真正工作的底座。

存什么：
- 实体：Decision、Project、Feature、Risk、Customer、Competitor、Meeting、Owner
- 关系：supports /contradicts/derived_from /supersedes/blocks /belongs_to
- 状态：draft /active/deprecated /speculative/approved
- 时效：valid_from /valid_to/last_verified_at
- 归属：owner /approver/team
- 溯源：source_id /extraction_run_id/confidence

这是 “可计算上下文”。

---

###### 3. File / Prompt Layer：给 Agent 的工作台
文件仍然重要，但角色要变：

适合放：
- SOP
- 系统指令
- prompt templates
- agent scratchpad
- 临时 synthesis
- playbook

不适合放：
- 真正的事实主记录
- 关键状态机
- 复杂依赖关系

###### 一句话
**文件是工作界面，数据库才是记忆底座。**

---

#### 四、技术设计上，最佳实践应该怎么做

---

##### 实践 1：定义 typed entity，而不是只做 chunk + embedding

###### 错误范式
很多 RAG 系统只做：
- 文档切 chunk
- 向量化
- 检索 top-k
- 丢给 LLM

这只适合 “回答文档里写了什么”，不适合 “组织级协作推理”。

###### 正确范式
至少定义一套基础实体：

```text
Decision
- id
- title
- status
- made_by
- made_at
- scope
- supersedes_decision_id
- source_ref
- confidence

Project
Feature
Owner
Meeting
ResearchFinding
Risk
CustomerFeedback
Policy
Assumption
```

关系表示：

```text
Decision --affects--> Feature
Decision --derived_from--> Meeting
ResearchFinding --supports--> Decision
Assumption --contradicts--> Policy
Project --owned_by--> Team
```

###### 好处
Agent 在推理时不再只看文本，而是能利用 “对象类型 + 关系语义”。

---

##### 实践 2：所有抽取结果必须带 provenance
任何 agent 抽出来的结构化信息，都必须记录：

- 来源系统
- 来源对象 ID
- 来源版本 / 时间戳
- 抽取模型版本
- 抽取时间
- 抽取置信度
- 是否经人工确认

###### 示例表结构

```sql
extractions (
  id,
  source_type,          -- gdoc /slack/notion
  source_object_id,
  source_version,
  extracted_entity_type,
  extracted_entity_id,
  model_version,
  confidence,
  extracted_at,
  reviewed_by_human
)
```

###### 产品价值
当用户问：
> 这个结论从哪来的？

系统不是给一句 “根据资料推断”，而是能返回：
- 来自哪篇文档
- 哪次会议
- 哪段消息
- 是否被后续信息覆盖

这是企业级可信 AI 的关键。

---

##### 实践 3：做增量更新，不做全量重建
当源文档变化时，不要每次重建全知识库。

###### 推荐机制
- 对 source 做变更监听
  - Google Drive webhook
  - Slack event
  - Notion webhook
  - GitHub webhook
- 标记受影响节点
- 基于 dependency graph 做局部重算

###### 例子
Google Doc 更新了 PRD：

1. doc version changed
2. 找到所有`derived_from (doc_id)`的实体
3. 只重算：
   - Feature summary
   - Open risks
   - Impacted decisions
4. 标记旧结论为`stale`
5. 新结论通过审核后替换为`active`

###### 好处
- 成本低
- 时效高
- 避免整库抖动
- 更适合 agent 持续工作

---

##### 实践 4：把 “状态机” 做清楚，别让所有内容平权
不同知识对象必须有生命周期。

###### 例如 Decision 状态机
```text
proposed -> reviewed -> approved -> active -> superseded /deprecated
```

###### 例如 Assumption 状态机
```text
hypothesis -> under_validation -> validated /rejected
```

###### 为什么重要
没有状态机，Agent 会把：
- proposal 当 active
- rejected assumption 当事实
- 历史决策当现行规则

这不是模型能力问题，是产品建模缺失。

---

##### 实践 5：检索分两段，不要只用向量召回
企业知识问答建议用**Hybrid Retrieval**：

###### 第一段：结构化过滤
先按 schema 筛：
- team = product
- status = active
- updated_at > 90 days
- entity_type in (decision, roadmap_item)

###### 第二段：语义检索 / 重排
在候选集上做：
- embedding search
- BM25
- reranker
- LLM reasoning

###### 好处
- 召回更准
- 幻觉更少
- token 成本更低
- 对 “当前有效内容” 更敏感

---

#### 五、一个可落地的产品方案示例

##### 场景：做一个 “AI 产品决策助手”

###### 用户需求
PM 问：
- 当前 roadmap 受哪些历史决策约束？
- 哪些决策已经过时？
- 某个客户反馈是否影响优先级？
- 为什么这个功能没做？

---

##### 推荐系统设计

###### 数据源接入
- Linear：项目、issue、roadmap
- Google Docs：PRD、会议记录
- Slack：讨论记录
- CRM：客户反馈
- GitHub：实现状态

###### 数据库 schema
核心表：

```text
sources
entities
relationships
claims
decisions
roadmap_items
feedback
meetings
dependencies
evaluation_logs
```

###### 示例
`decisions`表：

```sql
id
title
status
owner
made_at
supersedes_id
source_ref
last_verified_at
```

`relationships`表：

```sql
from_entity_id
relation_type   -- supports /contradicts/affects /derived_from
to_entity_id
confidence
source_ref
```

`dependencies`表：

```sql
upstream_source_id
downstream_entity_id
dependency_type
```

---

##### Agent 工作流
###### 问题：
> 为什么 Alpha 功能在 roadmap 里被降级？

###### Agent 执行
1. 查`roadmap_items`找 Alpha 当前状态
2. 查关联`decisions`
3. 查支持 / 反对该决策的`feedback`、`research finding`
4. 查最近 30 天是否有新的 source 更新
5. 输出答案时附上：
   - 当前有效决策
   - 决策 owner
   - 原始会议 / 文档链接
   - 是否存在冲突证据

###### 输出效果
不是 “我从文档中推测可能因为资源不足”，而是：

- 2025-02-03 决策 D-193 将 Alpha 从 P1 降为 P2
- owner: VP Product
- 原因：2 个 enterprise 客户需求转向 Beta；平台团队容量不足
- 证据来源：
  - Slack thread xxx
  - Strategy doc yyy
  - Linear planning cycle zzz
- 注意：2025-02-28 有新客户反馈可能影响该判断，尚未评审

这就是企业级 agent。

#### 六、这篇文章对技术团队最有价值的提醒

##### 1）RAG 不是知识系统
RAG 解决的是 “找相关文本”，  
不是 “维护可治理的组织记忆”。

---

##### 2）Schema 本身就是上下文
很多团队只关注 prompt/context window，忽略了：

> **结构化 schema 对 agent 来说也是强上下文。**

类型、状态、依赖、时间、来源、owner，这些比多塞 20 页 markdown 更有价值。

---

##### 3）Agent 需要的是可执行的数据层，不是更大的笔记堆
真正让 agent 从 copilot 变 coworker 的不是：
- 更多文档
- 更长上下文
- 更复杂 prompt

而是：
- 可查询
- 可验证
- 可追溯
- 可更新
- 可治理

---

#### 七、最佳实践清单

##### 产品侧
- 用文件承载说明、流程、草稿；不用它承载核心事实
- 所有知识对象显式区分：事实 / 决策 / 假设 / 讨论 / 历史
- 每条关键知识必须有 owner、状态、时效、来源
- 回答必须可追溯到原始证据
- 给用户展示 “当前有效” 和 “已过期 / 待确认” 的区别

##### 技术侧
- 建 typed schema，不只做向量库
- 所有抽取结果保留 provenance
- 用 webhook + 增量 ETL 做更新
- 做 dependency graph，支持局部重算
- 检索采用 “结构化过滤 + 语义检索” 混合模式
- 为关键实体建立状态机和约束
- 对 agent 输出加 evidence bundle，而不是只给自然语言答案

---

#### 八、一个很实用的结论

##### 什么时候文件优先？
- prompt
- SOP
- 人类写作
- 草稿
- agent scratchpad
- 轻量知识沉淀

##### 什么时候数据库优先？
- 决策追踪
- 关系网络
- 状态管理
- 权威性判断
- 依赖更新
- provenance
- 组织级长期记忆

---

#### 最后一句总结

这篇文章本质上是在说：

> **AI 时代的知识系统，不该是 “文档仓库 + 检索”，而应该是 “来源系统 + 结构化上下文图谱 + 可追溯推理层”。**

## 产品-最佳实践（1）

### 2026-03-12 10:16:44

下面给你一个**具体实例**，并基于该实例提炼出**最佳实践**。

---

##### 实例：产品团队要回答  
**“当前 roadmap 上有哪些功能，可能与既有决策冲突？”**

###### 错误做法：全放 Markdown / 文件夹
例如：

```txt
company/
  strategy/
  decisions/
  projects/product-alpha/features/
  meetings/
  research/
```

表面上看很清晰，但一旦要回答：

- 哪个功能关联了哪些决策？
- 哪些决策已经被后续决策覆盖？
- 哪些结论只是会议纪要里的猜测，不是正式决定？
- Google Doc 更新后，哪些摘要、哪些结论需要重算？

就会变成：

- 到处 grep / 全文搜索
- 靠 wikilink 猜关系
- 靠标签区分 “正式 / 非正式”
- 靠人工或 agent 反复维护副本

结果是：**能读，不能治理；能遍历，不能校验；能链接，不能持续保持真相一致。**

---

##### 最佳实践：三层架构

###### 1）源系统层：只认原始事实
来源包括：

- Google Docs：策略文档
- Slack：讨论与决策上下文
- Jira / Linear：roadmap、feature、issue
- CRM：客户反馈
- Notion：会议纪要

**原则**：  
不要把这些原文 “复制” 成另一个 markdown 事实库，而是保存**源链接 / 源 ID**。

---

###### 2）数据库层：存 “结构化上下文图”
把真正需要推理、查询、依赖追踪的内容抽出来，存成结构化记录。

比如核心表：

- `sources`
  - source_id
  - source_type（gdoc/slack/jira/notion）
  - external_id
  - updated_at

- `decisions`
  - decision_id
  - title
  - status（proposed/active/superseded）
  - owner
  - effective_date
  - supersedes_decision_id
  - source_id

- `features`
  - feature_id
  - name
  - roadmap_status
  - owner
  - source_id

- `decision_feature_links`
  - decision_id
  - feature_id
  - relation_type（supports/conflicts_with/constraints）

- `claims`
  - claim_id
  - subject
  - predicate
  - object
  - confidence
  - claim_type（fact/inference/speculation）
  - source_id

- `derivations`
  - derived_entity_id
  - derived_from_source_id
  - extraction_method
  - last_verified_at

这样一来，系统能明确知道：

- 什么是**正式决策**
- 什么只是**会议里的观点**
- 什么已经**失效**
- 某条知识是从哪里抽取出来的
- 上游变化后，哪些下游需要重新评估

---

###### 3）文件层：只放 “给 agent 的工作说明”
文件依然有价值，但用途要变：

适合放：

- SOP
- 提示词模板
- 分析框架
- agent scratchpad
- 团队约定的操作手册

不适合放：

- 作为唯一事实源的结构化业务知识
- 大量需要跨实体查询和更新传播的关系数据

**一句话**：  
**文件用于引导，数据库用于记忆，业务系统用于存真相。**

---

##### 这个实例下的最佳实践（精炼）

###### 1. 不复制真相，只保存指针
把 Google Doc、Slack、Jira 的**URL/ID**存进数据库，而不是复制出一份 markdown 摘要当主记录。  
**好处**：避免双份内容漂移。

###### 2. 先建 “类型”，再建 “链接”
至少区分：

- decision
- feature
- source
- claim
- owner
- dependency

再定义关系：

- supports
- conflicts_with
- derived_from
- supersedes
- owned_by

**好处**：agent 看到的不只是文本，而是 “这是什么、和谁什么关系”。

###### 3. 区分 “权威性” 和 “时效性”
每条记录必须有：

- status（active /superseded/draft）
- owner
- source
- updated_at
- confidence /authority_level

**好处**：避免把猜测、纪要、正式决策混成一类。

###### 4. 所有派生知识都要记录 provenance
任何摘要、结论、标签、冲突判断，都记录：

- derived_from 哪个 source
- 何时生成
- 用什么规则 /agent 生成
- 上游变更后是否需要重算

**好处**：实现 “更新可追踪、错误可回滚”。

###### 5. 用数据库回答问题，不用全文搜索硬猜
像 “哪些功能与当前决策冲突” 这种问题，本质是结构化查询，不应依赖 markdown 遍历。  
**好处**：查询稳定、可重复、可自动化。

###### 6. 文件系统只做入口，不做知识图本体
保留少量高价值文件：

- onboarding.md
- where-to-look.md
- agent-playbook.md

但不要让目录树承担数据库职责。  
**好处**：避免 “表面简单，实际偷偷重建数据库”。

###### 7. 让 agent 维护 ETL，而不是维护副本
agent 的职责应是：

- 从源系统 API 拉取更新
- 抽取结构化实体和关系
- 更新数据库
- 标记受影响的派生结论待重算

而不是：
- 到处改 markdown 副本
- 靠文本同步事实

**好处**：把维护变成 “依赖传播”，不是 “内容搬运”。

---

##### 最后总结成一句话
在这个实例里，**最佳实践不是 “把知识整理成更好的文件夹”**，而是：

> **用源系统保存事实，用数据库保存结构、关系和 provenance，用文件给 agent 提供操作入口。**
