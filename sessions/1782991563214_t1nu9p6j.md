- **核心高价值点**：将子代理调用从逐次工具调用转为由模型生成代码进行确定性调度，可显著提升大规模覆盖和复杂工作流可靠性。
- **留存建议**：长期保留，适合作为多代理系统设计和任务编排模式参考（提供了动态子代理的核心思想、快速上手方式和六类可复用编排模式，对AI Agent系统设计有方法论价值）

**知识要点**

- 动态子代理通过代码解释器暴露task\(\)函数，让模型使用循环、分支、Promise.all等代码结构调度子代理
- 程序化调度能避免模型在大规模任务中遗漏范围，例如对数百页文档或大量文件进行确定性覆盖
- 常见编排模式包括分类并行动、扇出与合成、对抗性验证、生成和筛选、锦标赛、循环直到完成
- responseSchema可让子代理结果结构化，便于后续过滤、评分和管道化处理
- 动态子代理体现递归语言模型思想：模型写代码，代码再调度更多模型完成任务

### 在深度代理中介绍动态子代理

随着代理承担更具挑战性的任务，它们会遇到困难：

1. 可靠地大规模完成工作
2. 管理他们自己的上下文

我们一直在尝试以我们称之为

[动态子代理](https://docs.langchain.com/oss/python/deepagents/dynamic-subagents): 即不通过通用工具调用的方式来下达子代理任务，而是由代理编写一个简短的脚本来驱动子代理执行。这意味着模型可以依靠它擅长编写的代码模式（如循环、分支或并发）来编写适合该任务的编排逻辑。

### 为什么需要动态子代理？

Deep Agents 已经支持

[子代理](https://docs.langchain.com/oss/python/deepagents/subagents)。它们隔离上下文，让主代理委派离散的工作单元，并将中间结果排除在主上下文窗口之外。那么我们为什么需要动态子代理？

对于普通子代理，主模型会逐个直接调用它们。这在小规模时是可行的。当需要生成数百个子代理，或者编排逻辑是条件性或多阶段的时候，这种方式就会失效。

动态子代理通过程序化编排解决这一问题。不再逐个进行工具调用，代理会编写一个简短的脚本，该脚本编排并调用子代理，并在轻量级解释器中运行。

典型示例：一个300页的文档中每页一个子代理。与其调用子代理工具300次，代理编写一个循环：

```javascript
const results = await Promise.all(pages.map(page =>
  task({ description: `Summarize page ${page.number}`, subagentType: "summarizer" })
));
```

这开启了两项工具调用型编排无法可靠提供的内容：

大规模的确定性覆盖。 没有结构时，代理会对范围做出判断，筛选 500 个项目中的 75 个并宣称完成。调度循环不会如此。覆盖成为结构性保障，而非提示工程问题。

可靠的复杂编排。 将编排写为代码比让模型将其重现为一系列工具调用更可靠，尤其是对于扇出+合成、多阶段管道或条件分支。

这背后的理念与

[Claude 代码中的工作流](https://code.claude.com/docs/en/workflows)和

[递归语言模型 (RLMs)](https://arxiv.org/abs/2512.24601)

：一个模型编写代码，而该代码会调度更多的代理。

### 它是如何工作的

代理被赋予一个

[eval 工具](https://docs.langchain.com/oss/python/deepagents/interpreters)。它会编写在解释器内安全执行的 JavaScript 代码。当

[子代理](https://docs.langchain.com/oss/python/deepagents/subagents)

被配置时，解释器会暴露一个内置的全局 task()函数，从代码中调度它们。根据手头的任务，模型会编写不同的代码——循环、分支、Promise.all——并且解释器会确定性地执行这些代码。

![Image](https://pbs.twimg.com/media/HL_mrZJXQAANIoZ?format=jpg&name=large)

task() 接受一个描述、一个子代理类型和一个可选的响应模式——当提供该参数时，结果已经是一个类型化的对象，准备好进行过滤或传递到下一步。

```javascript
const result = await task({
  description: "Review src/auth/login.ts for security issues.",
  subagentType: "reviewer",
  responseSchema: {
    type: "object",
    properties: {
      severity: { type: "string", enum: ["high", "medium", "low"] },
      issues: { type: "array", items: { type: "string" } },
    },
  },
});

const critical = result.severity === "high" ? result.issues : [];
critical; // model sees the last line
```

更多信息请参见

[程序化子代理](https://docs.langchain.com/oss/python/deepagents/programmatic-subagents)和

[口译员](https://docs.langchain.com/oss/python/deepagents/interpreters)

文档里有。

#### 分类并行动

首先对项目进行分类，然后每个项目由专业子代理根据其分类进行处理。这使您能够处理不同项目需要不同专业知识的混合输入。

![Image](https://pbs.twimg.com/media/HL_nTO2W4AAf0Bf?format=jpg&name=large)

使用场景： 分类处理支持工单、错误日志、用户反馈，或任何需要根据类型进行不同处理的项目。

示例 : 对支持工单积压进行分类处理。坐席阅读工单并将每个工单分类为缺陷、功能请求或问题。缺陷分配给缺陷调查员，功能请求分配给功能分析师，问题分配给支持响应者。结果是按类别分组的汇总。

查看跟踪

[这里](https://smith.langchain.com/public/20b1da82-de4a-4de4-ae20-6097c059cd94/r)。

#### 扇出与合成

代理在多个项目中并行分发同类型的工作，然后合并结果。

![Image](https://pbs.twimg.com/media/HL_nY3xWAAAyDK4?format=jpg&name=large)

用例： 代码审查跨目录，分析一批文档，处理日志文件，在多个服务中运行相同的检查。

按文件的安全审查覆盖整个源代码树。代理发现 src/目录下的所有 TypeScript 文件，并为每个文件并行分配一名安全审查员。然后将结果合并成一份优先级排序的报告，其中包含严重程度评级以及需要修改的代码行。

查看跟踪

[这里](https://smith.langchain.com/public/d80cdf1a-37fc-4823-8500-417fe624fe3e/r)。

#### 对抗性验证

两阶段模式。第一阶段生成发现结果，第二阶段将每个发现结果发送给独立验证者，只有通过共识验证的发现结果才会被保留。当置信度比速度更重要时，这种模式可减少假阳性。

![Image](https://pbs.twimg.com/media/HL_nhh-XYAAUKig?format=png&name=large)

用例：安全审计中误报代价高昂、合规检查、任何需要对发现结果有高置信度的审查。

在误报不可接受的安全审计中，审计员会广泛排查潜在漏洞，然后每个发现都会提交给独立的验证者，验证者会重新阅读代码并返回确认（CONFIRMED）或否定（REFUTED）的判定结果。只有确认的发现会被写入最终报告。

查看跟踪

[这里](https://smith.langchain.com/public/6f47c6c5-34ee-454e-9ffe-bf23e4a619e6/r)。

#### 生成和筛选

多个子代理针对同一问题生成独立的解决方案。该代理通过代码比较、评分并筛选结果，仅保留最优解。

![Image](https://pbs.twimg.com/media/HL_nr7uWMAAwPb7?format=jpg&name=large)

用例： 架构提案、重构策略、内容变体，任何在正式决策前探索多种选项能产生更佳结果的任务。

竞争中的限流组件重新设计方案，已排序。代理程序通过架构器生成多个独立的 rate-limiter.ts 重新设计方案，每个方案写入独立文件以避免相互覆盖。随后，它根据突发流量下的正确性、多实例支持能力和复杂度对这些方案进行评分。最强的方案胜出，并附带胜出理由。

[这里](https://smith.langchain.com/public/fbecf524-e8c5-4db4-930f-4a82b22d5d59/r)。

#### 锦标赛

变体由裁判助理进行面对面比较，获胜者晋级淘汰赛。

![Image](https://pbs.twimg.com/media/HL_nwwpXYAAmNhZ?format=png&name=large)

用例： 基于主观标准的优化、风格选择、在相互竞争的实现方案之间进行选择。

针对混乱的 createOrder 处理程序的改写的两两对决淘汰制。几位编写者各自生成带有不同优先级的候选改写版本，然后由评审者进行两两对比，逐轮晋级获胜者，直到决出最终优胜者。并附上评审者的推理过程。

查看跟踪

[这里](https://smith.langchain.com/public/f89bcdb7-57be-4a3e-a290-36dbdaaa4294/r)。

#### 循环直到完成

代理运行一个发现循环，与它已发现的内容进行去重，直到不再出现新结果。当工作范围事先未知时很有用。

![Image](https://pbs.twimg.com/media/HL_n1q7XIAAW9l4?format=jpg&name=large)

使用场景： 全面搜索、无效代码检测、依赖审计，任何你想要全面性而非固定数量结果的扫描。

基于轮次的安全扫描。代理程序执行一次扫描轮次，检查在代码中发现的内容，只有当之前的扫描轮次发现了新问题时，才会开始下一轮扫描。当某一轮扫描没有发现新内容时停止，然后报告汇总结果以及总共执行的扫描轮次数量。

#### 结论

动态子代理是赋予代理更多自主性和更高可靠性的方式。代码处理覆盖范围和中间上下文，而模型仍负责处理需要大量判断的工作。上述模式是一个起点。在实际应用中，代理会根据任务需求组合和混合这些模式。

这是递归语言模型思想的最简形式。一个编写代码的代理，而该代码会调度更多代理。这是一个递归调用自身的代理，不受上下文窗口限制，也不被固定在某个工作流程中。代理可以尽可能深入地分解问题，并以任何合适的形式重组这些片段。上述的编排模式是可能实现的早期雏形，但随着模型编写代码的能力不断提升，其上限只会持续提高。

[动态子代理](https://docs.langchain.com/oss/python/deepagents/dynamic-subagents) 这就是 Deep Agents 让你如今能够掌控的方式。开始使用时，请在你的代理中添加一个代码解释器，或者使用

[dcode](https://docs.langchain.com/oss/python/deepagents/code/overview)

，在那里动态子代理可以开箱即用。

#### 动态子代理：深度总结、通俗解读与辩证思考

##### 一句话总结

**动态子代理 = 让主代理写一段代码，用代码批量、并行、条件化地调度子代理，从而更可靠地完成大规模复杂任务。**

---

##### 1. 深度总结

传统代理在处理复杂任务时有两个瓶颈：

1. **规模不可靠**  
   例如要检查 500 个文件，模型可能只挑一部分做，然后误以为完成了。

2. **上下文难管理**  
   大量中间结果塞进主代理上下文，会导致混乱、遗漏、成本上升。

Deep Agents 原本已有「子代理」机制：  
主代理可以把任务交给子代理，子代理独立处理，避免污染主上下文。

但问题是：  
**普通子代理需要主代理一个个调用。**

当任务变成：

- 300 页文档逐页总结；
- 1000 个文件逐个审查；
- 多阶段筛选、验证、合成；
- 根据不同类型分派不同专家；

这种逐个调用方式就不稳定、不高效。

于是提出了 **动态子代理**。

它的核心变化是：

> 主代理不再逐次手动调用子代理，而是写一段脚本，由脚本来调度子代理。

例如：

```js
const results = await Promise.all(
  pages.map(page =>
    task({
      description: `Summarize page ${page.number}`,
      subagentType: "summarizer"
    })
  )
);
```

这意味着：

- 循环保证覆盖所有页面；
- `Promise.all` 保证并行处理；
- 条件分支可以决定不同任务交给不同子代理；
- 多阶段流程可以用代码稳定表达。

本质上，这是：

> **模型负责判断，代码负责调度。**

---

##### 2. 通俗解读

可以把主代理想象成一个项目经理。

###### 普通子代理模式

项目经理亲自一个个发任务：

> “你去看第 1 页。”  
> “你去看第 2 页。”  
> “你去看第 3 页。”  
> ……

如果只有 5 页，没问题。  
如果有 300 页，就容易漏、慢、乱。

---

###### 动态子代理模式

项目经理写一张任务分发表：

> “所有页面，每页派一个总结员，并行处理，最后汇总。”

然后系统按表执行。

这就像从：

> 人工派活

升级为：

> 写程序自动派活

所以动态子代理的优势不是“更聪明”，而是：

> **更有组织、更可控、更不容易漏。**

---

##### 3. 它解决了什么关键问题？

###### 1. 大规模覆盖

以前模型可能会“凭感觉”处理一部分。  
现在用代码循环：

```js
files.map(file => task(...))
```

只要文件列表完整，就能保证每个文件都被处理。

**覆盖变成代码结构问题，而不是提示词问题。**

---

###### 2. 复杂流程更可靠

很多任务不是一步完成的，而是：

1. 先扫描；
2. 再分类；
3. 再交给不同专家；
4. 再验证；
5. 最后合成报告。

让模型靠自然语言一步步记住流程，很容易乱。

但写成代码后：

```js
if (type === "bug") {
  task({ subagentType: "bug-investigator" })
} else if (type === "feature") {
  task({ subagentType: "feature-analyst" })
}
```

流程更稳定。

---

###### 3. 上下文更清爽

子代理处理中间细节，主代理只拿最终结果。  
这避免主代理被大量过程信息淹没。

---

##### 4. 六种典型编排模式

###### 1. 分类并行动

先分类，再分派给不同专家。

适合：

- 工单处理；
- 用户反馈分析；
- 错误日志归类。

例子：

> 缺陷交给缺陷调查员，功能请求交给产品分析师，普通问题交给客服代理。

---

###### 2. 扇出与合成

同一种任务，分发给多个对象并行处理，最后汇总。

适合：

- 多文件代码审查；
- 多文档总结；
- 多服务日志分析。

例子：

> 每个 TypeScript 文件派一个安全审查员，最后合成风险报告。

---

###### 3. 对抗性验证

先发现问题，再让独立验证者确认。

适合：

- 安全审计；
- 法律审查；
- 高风险决策。

价值：

> 降低误报，提高可信度。

---

###### 4. 生成和筛选

多个子代理分别提出方案，再评分筛选。

适合：

- 架构设计；
- 重构方案；
- 文案变体；
- 产品策略。

价值：

> 先发散，再收敛。

---

###### 5. 锦标赛

多个方案两两 PK，胜者晋级。

适合：

- 主观质量比较；
- 风格选择；
- 多实现方案优选。

价值：

> 用比较代替绝对打分，更接近人类评审。

---

###### 6. 循环直到完成

不断扫描、去重，直到没有新发现。

适合：

- 安全扫描；
- 死代码检测；
- 依赖风险审计；
- 开放式搜索。

价值：

> 不预设固定轮数，而是根据结果动态停止。

##### 5. 本质洞察

动态子代理的关键不只是“多开几个代理”。

它真正重要的是：

> **把大模型不擅长的流程控制，交给代码；把代码不擅长的判断、理解、生成，交给模型。**

模型擅长：

- 理解任务；
- 判断优先级；
- 总结信息；
- 生成方案；

- 分支；
- 并发；
- 去重；
- 排序；
- 结构化数据流转。

动态子代理把两者结合起来。

## 结构化（1）

### 2026-07-22 09:40:26

#### 在深度代理中引入动态子代理

动态子代理让主代理不再逐个调用子代理，而是编写一段包含循环、分支和并发逻辑的脚本，批量调度子代理。它主要解决复杂任务中的**大规模可靠执行、上下文隔离和多阶段编排**问题。

##### 1. 为什么需要动态子代理

Deep Agents 原本已支持普通子代理，可将独立任务委派出去，并把中间结果隔离在主代理的上下文之外。

但普通子代理需要主模型逐次发起工具调用，在以下场景中容易失效：

- 需要同时生成数百个子代理；
- 任务包含条件判断或多个处理阶段；
- 必须确保所有项目都被处理，不能遗漏；
- 需要扇出、汇总、验证等复杂流程。

动态子代理的做法是：让代理编写简短脚本，由轻量级解释器确定性执行，并在脚本中调度其他子代理。

例如，处理一份 **300 页文档**时，不必调用子代理工具 300 次，而是编写并发循环：

```javascript
const results = await Promise.all(
  pages.map(page =>
    task({
      description: `Summarize page ${page.number}`,
      subagentType: "summarizer"
    })
  )
);
```

##### 2. 动态子代理的两项核心优势

###### 大规模、确定性的任务覆盖

如果只靠自然语言提示，代理可能从 **500 个项目中挑选 75 个**处理，然后声称任务已完成。程序化循环则能从结构上保证每个项目都被调度，覆盖率不再依赖模型的临场判断。

###### 更可靠的复杂编排

把流程写成代码，通常比让模型连续发起大量工具调用更稳定，尤其适用于：

- 扇出并汇总；
- 多阶段处理管道；
- 条件分支；
- 并行执行；
- 循环直到满足停止条件。

这一理念与 Claude Code 工作流及**递归语言模型（RLM）**相似：模型负责写代码，代码再调度更多代理。

##### 3. 快速开始

安装带 QuickJS 解释器的 Deep Agents：

```bash
pip install -U "deepagents[quickjs]"
```

创建代理并加入代码解释器中间件：

```python
from deepagents import create_deep_agent
from langchain_quickjs import CodeInterpreterMiddleware

agent = create_deep_agent(
    model="openai:gpt-5.5",
    middleware=[CodeInterpreterMiddleware()],
)
```

Deep Agents 自带通用子代理；针对具体业务，也可以配置带有独立名称、描述和系统提示的自定义子代理。代理主要依据子代理的**名称和描述**来选择适合的角色。

提示词中加入 `"workflow"` 即可触发动态子代理，例如：

```python
result = await agent.ainvoke({
    "messages": [{
        "role": "user",
        "content": "Run a workflow that reviews every file in src/routes/ and summarizes the top risks."
    }]
})
```

该任务会审查 `src/routes/` 中的每个文件，并汇总最重要的风险。

##### 4. 通过 dcode 直接体验

最快的体验方式是使用基于 Deep Agents 构建的终端编码代理 **dcode**。它默认启用代码解释器，无需额外配置。

安装并运行：

```bash
curl -LsSf https://langch.in/dcode | bash
dcode
```

当子代理被创建时，dcode 会在动态子代理面板中实时展示，并按照执行阶段分组。除终端外，也可通过 ACP 在 Zed 等工具中使用。

##### 5. 工作原理

主代理会获得一个 `eval` 工具，并编写可在安全解释器中运行的 JavaScript。配置子代理后，解释器会提供全局 `task()` 函数，供代码调度子代理。

模型可以根据任务自动生成：

- `for` 或 `map` 循环；
- `if/else` 条件分支；
- `Promise.all` 并发执行；
- 多阶段数据处理流程。

`task()` 可接收三个主要参数：

- `description`：具体任务；
- `subagentType`：子代理类型；
- `responseSchema`：可选的结构化响应格式。

例如，让审查员检查登录代码，并仅保留高危问题：

```javascript
const result = await task({
  description: "Review src/auth/login.ts for security issues.",
  subagentType: "reviewer",
  responseSchema: {
    type: "object",
    properties: {
      severity: {
        type: "string",
        enum: ["high", "medium", "low"]
      },
      issues: {
        type: "array",
        items: { type: "string" }
      }
    }
  }
});

const critical =
  result.severity === "high" ? result.issues : [];

critical;
```

由于返回结果已经是类型化对象，脚本可以直接进行过滤、比较，或传入下一阶段。

##### 6. 六种常见编排模式

这些模式不是固定功能开关，而是代理根据任务自然形成、组合和调整的工作流。

###### 6.1 分类并行动

先对输入分类，再交由不同专业子代理处理。

**适用场景：**

- 支持工单；
- 错误日志；
- 用户反馈；
- 不同类型需要不同专业能力的混合输入。

**案例：**先将支持工单分成缺陷、功能请求和普通问题，再分别交给缺陷调查员、功能分析师和支持响应者，最后按类别汇总。

---

###### 6.2 扇出与合成

将同一种任务并行分发到多个项目，最后统一汇总结果。

**适用场景：**

- 跨目录代码审查；
- 批量文档分析；
- 日志处理；
- 对多个服务执行同一检查。

**案例：**找出 `src/` 下所有 TypeScript 文件，为每个文件分配安全审查员并行检查，最终生成按严重程度排序的报告，并标明需要修改的代码行。

---

###### 6.3 对抗性验证

采用两阶段流程：

1. 第一批子代理广泛寻找潜在问题；
2. 第二批独立验证者逐条复核。

只有获得共识确认的结果才进入最终报告，可降低误报。

**适用场景：**置信度比速度更重要、无法接受误报的安全审计。

**案例：**审计员发现潜在漏洞后，验证者重新阅读相关代码，并返回 `CONFIRMED` 或 `REFUTED`；最终只保留被确认的问题。

---

###### 6.4 生成和筛选

多个子代理针对同一问题独立提出方案，再由程序比较、评分并选出最优结果。

**适用场景：**

- 架构提案；
- 重构策略；
- 内容变体；
- 需要先探索多个选项再决策的任务。

**案例：**多个架构子代理分别重新设计 `rate-limiter.ts`，并写入不同文件，避免互相覆盖；之后按突发流量下的正确性、多实例支持和复杂度进行评分，选出最佳方案并说明理由。

---

###### 6.5 锦标赛

多个候选方案进行两两对比，由评审子代理选择胜者，胜者逐轮晋级，直到产生最终结果。

**适用场景：**

- 主观标准优化；
- 风格选择；
- 多个实现方案之间的比较。

**案例：**多名编写者分别改写混乱的 `createOrder` 处理程序，再由评审者进行淘汰赛式两两比较，最终选出优胜版本，并保留评审理由。

---

###### 6.6 循环直到完成

代理反复执行发现任务，并对结果去重；只要新一轮仍发现新内容，就继续扫描，直到没有新增结果。

**适用场景：**

- 全面搜索；
- 无效代码检测；
- 依赖审计；
- 任务范围事先未知、强调完整性的扫描。

**案例：**代码安全扫描按轮次执行。若当前轮发现新问题，则进入下一轮；某轮没有新发现时停止，并报告汇总结果及总扫描轮数。

##### 7. 总结

动态子代理把职责进行了清晰拆分：

- **代码**负责覆盖范围、并发调度、流程控制和中间上下文；
- **模型**负责分析、判断和生成等高认知任务。

其本质是递归语言模型思想的简化实现：一个代理编写代码，代码再调用更多代理。这样既不受固定工作流约束，也能通过不断分解和重组任务，缓解单一上下文窗口的限制。

上述六种编排模式只是起点；实际使用中，代理可以根据任务混合多种模式。要开始使用，可为 Deep Agents 添加代码解释器，或直接使用默认支持动态子代理的 dcode。

## 口播总结（1）

### 2026-08-03 01:18:37

#### 动态子代理：让代理用代码调度更多代理

这篇材料介绍了一种叫“动态子代理”的方法。你可以把它理解为：主代理不再一个接一个地手动调用子代理，而是先写一段小程序，让程序自动安排、并行运行和整理大量子代理任务。听完你会了解，它为什么能提升代理处理大规模、复杂任务时的覆盖率和可靠性，以及它常见的六种工作模式。

##### 一、为什么需要动态子代理

首先，核心结论是：当任务规模变大，或者流程开始出现并行、分支和多阶段处理时，普通的子代理调用方式就不够可靠了。

这里的“子代理”，指的是被主代理临时派出去完成某个独立任务的小代理。它们通常拥有相互隔离的上下文，也就是不会把所有中间过程都塞回主代理的上下文窗口。这样，主代理可以把任务拆开，再把结果收回来。

问题在于，普通方式通常是主代理逐个调用子代理。任务少的时候，这种办法还能工作。但如果要处理数百个对象，或者流程需要根据中间结果做判断，单纯依靠一连串工具调用就容易出错。

举个典型例子。假设有一份三百页的文档，每一页都要交给一个子代理总结。普通方式需要调用子代理工具三百次。动态子代理则可以让主代理写一个循环，把三百页自动分发出去，还可以同时运行多个任务。

这带来两个重要变化。

第一，是大规模、确定性的覆盖。没有明确程序结构时，代理可能只挑选五百个项目中的七十五个，然后误以为自己已经完成了全部工作。可是，一个明确的调度循环会逐项处理。覆盖范围不再依赖一句提示词，而是由程序结构来保证。

第二，是更可靠的复杂编排。所谓“编排”，就是安排任务的执行顺序和协作方式。把这种安排写成代码，通常比让模型自己连续重复很多次工具调用更稳定。尤其是在“先大量并行处理，再统一汇总”、多阶段流水线，以及条件分支这些场景中，程序更容易准确执行。

这种思路和 Claude Code 中的工作流，以及“递归语言模型”相近。递归语言模型可以简单理解为：一个模型先写代码，而这段代码再去调度更多模型或代理。

##### 二、动态子代理到底是怎么工作的

接下来，核心结论是：动态子代理把“如何调用子代理”这件事交给代码，而不是完全交给模型临场安排。

具体来说，主代理会获得一个叫 `eval` 的工具。它可以写一段 JavaScript，然后让这段代码在一个安全的轻量级解释器中运行。

当系统配置好子代理之后，解释器里会提供一个内置的 `task()` 函数。主代理可以通过这个函数调度子代理，并指定三项内容：任务描述、子代理类型，以及可选的响应格式。

比如，主代理可以让一个名为“审查员”的子代理检查登录代码是否存在安全问题。它还可以要求子代理返回结构化结果，包括风险等级和问题列表。这样，主代理就能直接根据结果判断：如果风险等级是高，就把问题留下；如果不是，就进行过滤。

这意味着，模型可以根据任务需要写出不同的程序结构。简单任务可以使用循环；需要条件判断时可以使用分支；需要同时处理许多对象时，可以使用 `Promise.all` 这样的并发机制。之后，解释器会按照代码确定性地执行。

换句话说，模型负责判断“应该怎么安排任务”，代码负责稳定地执行“到底安排了哪些任务、执行了多少次，以及结果怎样流转”。

##### 三、如何开始使用

更具体地说，核心结论是：要使用动态子代理，需要给代理接入代码解释器；而 Deep Agents 已经提供了相应的快速使用方式。

Deep Agents 是这套代理系统。快速入门时，可以安装带有 QuickJS 支持的版本，也就是为 JavaScript 代码提供解释执行能力的组件。然后创建一个深度代理，并加入代码解释器中间件。

Deep Agents 自带一个通用子代理配置，可以直接用于工作流。如果某种任务需要特定角色，也可以配置自定义子代理。自定义时，需要给它设置名称、描述和系统提示。名称和描述很重要，因为主代理会根据这些信息判断应该调用哪个角色。

触发动态子代理的方式也比较直接。可以在用户请求中加入“workflow”，也就是“工作流”这个词。例如，让代理运行一个工作流，检查 `src/routes` 目录中的每一个文件，并总结最重要的风险。

如果想更快体验，也可以使用基于 Deep Agents 构建的终端编码代理 dcode。它已经内置并启用了代码解释器，所以动态子代理可以直接使用，不需要额外配置。dcode 还会在动态子代理面板中实时显示子代理的调度情况，并按照不同阶段进行分组。

当然，也可以通过 ACP，也就是一种代理通信协议，在自己选择的工具中使用它，例如 Zed。

##### 四、六种常见的动态编排模式

接下来，材料介绍了六种常见模式。它们不是必须手动打开的独立功能，而是代理面对不同任务时，自然会采用的不同组织方式。

###### 1. 分类并行处理

第一种模式是“分类并行处理”。

核心结论是：先判断每个项目属于哪一类，再把不同类别交给不同的专业子代理处理。

通俗地说，这适合混合输入。因为一批任务里，可能同时存在缺陷、功能请求和普通咨询。如果所有任务都交给同一种代理，处理效果可能不够好。分类之后，就能让每个子代理发挥自己的专长，而且不同类别可以并行处理。

典型案例是处理支持工单积压。一个代理先阅读工单，把它们分成缺陷、功能请求和问题三类。接着，缺陷交给缺陷调查员，功能请求交给功能分析师，普通问题交给支持响应者。最后，再把不同类别的结果汇总起来。

###### 2. 扇出与合成

第二种模式是“扇出与合成”。

核心结论是：把同一种工作同时分发给许多子代理，最后再把结果合并成一个整体报告。

“扇出”可以理解为从一个任务分出很多条并行路径；“合成”则是把这些路径的结果重新汇总。它适合代码审查、文档分析、日志处理，以及在多个服务中执行同一种检查。

例如，要对整个源代码目录进行安全审查。主代理先找出 `src` 目录下所有 TypeScript 文件，再为每个文件并行安排一个安全审查员。最后，把所有发现合并成一份按优先级排序的报告，报告中还包括严重程度和需要修改的代码行。

这种模式正是动态子代理最典型的应用之一。它能把大范围任务拆成许多彼此独立的小任务，同时避免让主代理一次性承受所有中间内容。

###### 3. 对抗性验证

第三种模式是“对抗性验证”。

核心结论是：先让一批代理尽可能多地发现问题，再让独立的验证者逐条复核，只有得到确认的问题才进入最终结果。

这种模式的重点不是最快，而是减少误报。它适合安全审计等对准确率要求很高的任务。

例如，在安全审计中，第一批审计员会广泛寻找潜在漏洞。每发现一个问题，就交给独立验证者重新阅读相关代码。验证者需要判断这个问题是“确认”，还是“驳回”。只有被确认的漏洞，才会写入最终报告。

因此，这个流程相当于给重要发现增加了一道独立检查。尤其在误报成本很高的场景里，它比单个代理直接下结论更稳妥。

###### 4. 生成与筛选

第四种模式是“生成与筛选”。

核心结论是：让多个子代理针对同一个问题分别提出方案，再通过程序比较、评分和筛选，保留最好的结果。

这种方法适合架构设计、重构策略、内容变体等任务。只要在正式决策之前，多探索几种方案，就可能得到更好的结果。

材料中的例子是重新设计一个限流组件。多个架构代理分别生成不同的 `rate-limiter.ts` 重构方案，每个方案写入独立文件，避免彼此覆盖。随后，主代理根据几个标准进行评分，包括突发流量下是否正确、是否支持多实例，以及整体复杂度。最后选出最强方案，并说明它胜出的理由。

这里的关键是，代码不仅负责生成多个候选方案，还负责统一比较这些方案，让筛选过程更加明确。

###### 5. 锦标赛

第五种模式是“锦标赛”。

核心结论是：让多个候选方案进行两两比较，胜者继续晋级，直到决出最终方案。

它和“生成与筛选”有些相似，但更强调面对面的淘汰过程，适合主观标准较强的选择任务，比如风格判断、实现方案比较，或者多个质量都不错的版本之间的竞争。

举个例子，可以针对一个混乱的 `createOrder` 处理程序，先生成多个不同的改写版本。然后让评审代理两两比较这些版本，胜者进入下一轮。经过多轮对决后，最终留下一个优胜版本，同时给出评审理由。

如果任务很难用单一分数衡量，而是更适合让评审者直接比较“哪个更好”，锦标赛模式就比较合适。

###### 6. 循环直到完成

第六种模式是“循环直到完成”。

核心结论是：代理不断进行扫描和发现，只有在新一轮不再发现新内容时才停止。

这种模式适合事先不知道工作范围的任务。比如全面搜索、无效代码检测和依赖审计。它的目标不是固定处理多少个项目，而是尽量做到全面。

材料中的例子是分轮次进行安全扫描。代理先完成一轮扫描，记录发现的问题。只有当上一轮确实发现了新问题，才会继续下一轮。如果某一轮没有新的发现，流程就停止。最终报告不仅汇总问题，还会说明总共执行了多少轮扫描。

这类模式把“什么时候算完成”交给了结果本身，而不是预先规定一个固定数量。

##### 五、动态子代理带来的更大变化

更重要的是，动态子代理不只是让调用次数变少，而是改变了代理处理复杂问题的方式。

核心结论是：代码负责覆盖范围、任务调度和中间结果管理；模型则集中处理真正需要判断和推理的部分。

如果所有中间内容都留在主代理的上下文里，任务越大，越容易超出上下文窗口，或者让主代理被大量细节干扰。动态子代理则可以把工作拆散，让程序管理这些中间过程，只把必要结果传到下一步。

这也让代理能够自由组合前面提到的模式。比如，先分类，再并行处理；然后对高风险结果进行对抗性验证；最后从多个解决方案中进行筛选。实际任务不一定只使用一种模式，而是会根据需要混合使用。

从更长远的角度看，这可以被视为递归语言模型思想的一种简单形式：一个代理编写代码，而这段代码继续调度更多代理。这样，代理可以把问题分得更细，再用适合任务的方式重新组合这些部分。

材料认为，这些模式只是早期形态。随着模型编写和执行代码的能力提高，动态子代理能够处理的任务复杂度也可能继续提升。

##### 六、最后回顾：最值得记住的几点

最后，可以记住五个结论。

第一，动态子代理的核心，不是逐个调用子代理，而是让主代理先写程序，再由程序统一调度子代理。

第二，它特别适合大规模任务。比如三百页文档可以通过循环自动覆盖，而不是手动调用三百次。

第三，代码能够提供确定性的覆盖范围和更可靠的复杂流程，减少代理漏项、错序或中途失控的情况。

第四，常见的六种模式包括：分类并行处理、扇出与合成、对抗性验证、生成与筛选、锦标赛，以及循环直到完成。

第五，使用动态子代理，需要接入代码解释器；在 dcode 中，它已经可以开箱即用。它的长远意义，是让代理不仅能够调用工具，还能够编写调度更多代理的程序，从而处理更大、更复杂、也更灵活的任务。

## 深度解读（1）

### 2026-09-18 00:41:26

#### 动态子代理的关键，不是“更多 Agent”，而是把编排变成可执行程序

这篇文章真正有价值的地方，并非提出了多智能体协作，而是明确了一种职责分工：**让模型负责判断与分解，让代码负责覆盖、调度和控制。**

普通子代理仍由主模型逐次调用。当任务只有几项时问题不大；面对数百个文件、页面或工单，模型却可能漏项、提前停止，或把大量中间结果塞回上下文。动态子代理让模型先生成循环、分支、并发和多阶段管道，再由解释器执行。于是，“处理全部 500 个对象”不再是一句容易被模型软化的自然语言要求，而成为一个可以检查的遍历过程。

##### 它解决的是执行可靠性，而非推理可靠性

这里需要区分两种“可靠”。程序化调度可以保证每个文件都被调用一次、失败后重试、满足条件才进入下一阶段；但它不能保证每个子代理都读懂了文件，也不能保证最终综合正确。**确定性覆盖只保证工作被派发，不保证工作被做好。**

文章列出的分类分流、扇出合成、生成筛选、对抗验证和循环搜索，本质上分别对应传统计算中的路由、MapReduce、候选搜索、交叉验证和迭代收敛。新意不在这些模式本身，而在于模型可以根据任务临时编写编排，而不必让开发者预先固化所有工作流。固定流程适合已知业务；动态编排更适合范围和路径需要先阅读材料才能确定的任务，例如跨代码库安全审查、未知依赖排查或长文档证据搜索。

其中，结构化返回尤其重要。子代理如果只交回自然语言，主代理仍要重新阅读和解释全部结果；若返回严重程度、证据位置、置信度等类型化字段，后续筛选、去重和路由就可以交给代码。**这实际上把模型输出从“聊天内容”转成了可计算的数据。**

##### 上下文瓶颈没有消失，只是被重新布置

文章声称这种递归代理“不受上下文窗口限制”，表述偏乐观。上下文隔离确实避免主代理看到所有过程，但最终合成仍可能成为瓶颈：300 个摘要即使各自很短，汇总时仍可能超长；分层压缩又会丢失细节。可行方案不是假设上下文无限，而是建立分层聚合、可检索证据和来源引用，让最终代理只读取候选结论，并能按需回查原文。

系统复杂度也会从提示词转移到分布式执行：并发上限、成本预算、超时重试、重复执行、任务依赖、共享状态和故障恢复都会成为真实问题。对抗验证也不天然可靠；如果生成者与验证者使用相同模型、提示和信息，它们可能产生高度相关的错误，而非真正独立的复核。

##### 更值得关注的是 Agent 的“控制平面”

从产品角度看，机会未必是再做一个多 Agent 界面，而是提供可靠的控制平面：任务图、预算与并发管理、结构化输出、证据溯源、失败重试、实时追踪和质量评测。目标用户是需要处理大批异构材料、又不能接受抽样遗漏的研发、安全、法务和运营团队；现有替代方案则是人工抽样、固定工作流和批处理脚本。

最应验证的不是“用户是否喜欢多个代理”，而是三个条件：任务能否拆成相对独立的单元，全面覆盖是否真的有业务价值，以及质量提升能否抵消调用成本与新增故障面。动态子代理最重要的启示是：**Agent 能力的下一步，不只是模型更聪明，而是把概率性的智能嵌入可观测、可约束、可验证的执行系统。**
