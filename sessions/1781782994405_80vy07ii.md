Ponytail, the lazy senior dev

#### Ponytail

*He says nothing. He writes one line. It works.*

**80-94% less code · 3-6× faster · 42-75% cheaper**  
Per-task code, latency, and cost on the Claude API, not your plan's quota. Median across Haiku, Sonnet, and Opus (10 runs for code and latency, 30 for the re-verified cost). Results vary by model and prompt: the ruleset re-injects each turn, so on a short prompt or a terse reasoning model that overhead can outweigh the savings. Reproduce it yourself.

---

You know him. Long ponytail. Oval glasses. Has been at the company longer than the version control. You show him fifty lines; he looks at them, says nothing, and replaces them with one.

Ponytail puts him inside your AI agent.

You ask for a date picker. Your agent installs flatpickr, writes a wrapper component, adds a stylesheet, and starts a discussion about timezones.

With ponytail:

```
<!-- ponytail: browser has one -->
<input type="date">
```

More survivors in examples/.

#### Numbers

Five everyday tasks (email validator, debounce, CSV sum, countdown timer, rate limiter), three models, three arms: no skill, the [caveman](https://github.com/JuliusBrussee/caveman) skill, and ponytail. Ten runs per cell, median reported.

Median lines of code per arm across Haiku, Sonnet and Opus; ponytail writes 80-94% less code than the no-skill baseline

**80-94% less code, 42-75% less cost, and 3-6× faster than a no-skill agent, on every Claude model.** Every shortcut ponytail takes is marked in the code with a `ponytail:` comment naming its upgrade path. Reproduce it yourself: `npx promptfoo eval -c benchmarks/promptfooconfig.yaml`. Method and raw numbers: benchmarks/. Production-grade tasks, where an unconstrained agent bloats far more, are written up in benchmarks/results/.

**That is the byproduct, not the pitch.** These are Claude numbers, and they vary by model. Capable instruction-following models follow the ladder and write far less, cheaper and faster. Terse reasoning models can go the other way: the ladder is a deliberation step, so the model spends thinking tokens working through the rungs before it saves any output, and together with the always-on ruleset that can cost more than the shorter code saves. On GPT-5.5 it does. And all of this is single-shot, one prompt in and one answer out: a real agent session re-injects the ruleset and runs the ladder every turn, which this benchmark does not measure, so per-session cost can land either way. The rule was never "fewest tokens." It is: write only what the task needs, and never cut validation, error handling, security, or accessibility. The code ends up small because it is necessary, not golfed, and that is the part that stays maintainable. Lower cost and latency are a side effect on the models that follow it.

Before writing code, the agent stops at the first rung that holds:

```
1. Does this need to exist?   → no: skip it (YAGNI)
2. Stdlib does it?            → use it
3. Native platform feature?   → use it
4. Installed dependency?      → use it
5. One line?                  → one line
6. Only then: the minimum that works
```

Lazy, not negligent: trust-boundary validation, data-loss handling, security, and accessibility are never on the chopping block.

#### Commands

Command What it does

`/ponytail [lite | full | ultra | off]` Set the intensity, or turn it off. No argument reports the current level.

`/ponytail-review` Review the current diff for over-engineering, hands back a delete-list.

`/ponytail-audit` Audit the whole repo for over-engineering, not just the diff.

`/ponytail-debt` Harvest the `ponytail:` shortcuts you've deferred into a ledger, so "later" doesn't become "never".

`/ponytail-help` Quick reference for the commands above.

Commands need a skill-capable host (Claude Code, Codex, OpenCode, Gemini, pi). In Codex they're skills, invoke with `@` (`@ponytail-review`). The instruction-only adapters (Cursor, Windsurf, Cline, Copilot, Kiro, Antigravity) load the always-on ruleset without the commands.

#### Ponytail 项目深度总结与解读

##### 一句话总结

**Ponytail 是一套给 AI 编程助手用的“少写代码规则集”：让 AI 在写代码前先想想——能不写就不写，能用现成的就别造轮子。**

---

##### 核心内容总结

###### 1. 它解决什么问题？

很多 AI Agent 写代码时容易：

- 过度设计
- 引入不必要依赖
- 写复杂封装
- 把简单问题工程化
- 产出大量“看起来专业但没必要”的代码

Ponytail 的目标是反过来：

> **只写任务真正需要的代码。**

---

###### 2. 它的核心原则

Ponytail 给 AI 一个写代码前的判断阶梯：

1. **这东西真的需要存在吗？**  
   不需要就不写。

2. **标准库能解决吗？**  
   能用标准库就用标准库。

3. **平台原生能力能解决吗？**  
   比如浏览器已有 `&lt;input type="date">`，就别装日期选择器库。

4. **项目已有依赖能解决吗？**  
   已经装了就复用。

5. **一行代码能解决吗？**  
   一行就别写十行。

6. **最后才写最小可行实现。**

这不是代码高尔夫，而是：

> **懒，但不草率。**

---

###### 3. 它强调什么不能省？

Ponytail 明确说，以下内容不能为了少写代码而砍掉：

- 输入校验
- 安全边界
- 错误处理
- 数据丢失保护
- 可访问性
- 必要的业务逻辑

也就是说，它反对的是“虚胖代码”，不是“必要工程质量”。

---

###### 4. 宣称的效果

项目 README 中给出的 Claude API 测试结果显示：

- 代码量减少 **80–94%**
- 速度提升 **3–6 倍**
- 成本降低 **42–75%**

但作者也承认：

- 结果依赖模型和提示词
- 规则集每轮都会注入，可能增加 token 成本
- 对某些推理模型，反而可能更贵
- 单轮 benchmark 不等于真实长期 Agent 会话

所以它的真正卖点不是“省 token”，而是：

> **让 AI 写更少、更必要、更容易维护的代码。**

---

##### 深入浅出解读

###### Ponytail 像什么？

它像团队里那个很资深、很懒、但很靠谱的老程序员。

你说：

> “我要一个日期选择器。”

普通 AI 可能会：

- 安装 flatpickr
- 写 React wrapper
- 加 CSS
- 处理时区
- 写一堆配置

Ponytail 会说：

```html
<input type="date">
```

然后结束。

---

##### 它真正反对的是什么？

不是反对复杂代码。

而是反对：

- 为了“显得专业”而复杂
- 为了“可扩展”提前抽象
- 为了“架构感”制造层级
- 为了“完整性”引入无用依赖
- 为了“未来可能用到”写现在不需要的东西

换句话说：

> **别把一个螺丝刀问题，做成一套机械臂系统。**

---

##### 它的设计哲学

###### 1. YAGNI

> You Aren’t Gonna Need It  
> 你现在不需要它。

很多代码不是因为需求存在，而是因为开发者幻想未来会需要。

Ponytail 强制 AI 先问：

> 这个东西真的该写吗？

---

###### 2. 复用优先

优先级大致是：

```text
不写 > 标准库 > 原生平台 > 已有依赖 > 一行代码 > 自己实现
```

这对 AI 很重要，因为 AI 很擅长“生成”，但不擅长“克制”。

---

###### 3. 最小但正确

Ponytail 不是让 AI 写“短代码”，而是写“必要代码”。

短代码可能危险；  
必要代码才可靠。

---

- 小功能实现
- 工具函数
- 前端常见组件
- 脚本任务

##### 我的辩证思考

###### Ponytail 的价值

它抓住了 AI 编程的一个核心问题：

> **AI 太容易“多做”。**

人类高级工程师的能力，不只是会写代码，而是知道：

- 哪些不用写
- 哪些不用抽象
- 哪些不用引入依赖
- 哪些现在不用考虑
- 哪些复杂性是假复杂性

Ponytail 把这种经验固化成规则，对 AI Agent 很有价值。

---

###### 但它也有边界

“少写代码”不是银弹。

如果过度追求极简，可能导致：

- 缺少扩展点
- 隐藏复杂性
- 忽略长期演进
- 低估业务边界
- 把必要设计误判为过度设计

所以真正重要的不是“越少越好”，而是：

> **复杂度要与问题匹配。**

---

##### 最重要的判断标准

可以用一句话概括：

> **不是能不能写得更少，而是能不能在不牺牲正确性的前提下，少写。**

好的 Ponytail 风格代码应该是：

- 少
- 清楚
- 安全
- 可维护
- 够用
- 不炫技

而不是：

- 短
- 隐晦
- 偷懒
- 缺校验
- 难扩展

---

##### 最终评价

Ponytail 本质上不是一个普通插件，而是一种 AI 编程价值观：

> **让 AI 从“代码生成器”变成“克制的工程师”。**

它最有意义的地方，不是节省了多少 token，而是提醒我们：

> **最好的代码，往往是你没有写的那部分。**

## 结构化（1）

### 2026-06-18 11:50:26

##### 主旨概括

**Ponytail 是一个给 AI 编程代理使用的“少写代码”规则集/插件**，目标是让 AI 像经验丰富但很“懒”的资深工程师一样：优先不用写代码、用标准库、用平台能力，只有必要时才写最少可维护代码。  
它强调：**不是代码高尔夫，也不是偷懒省掉质量，而是在不牺牲安全、验证、可访问性等前提下避免过度工程。**

---

##### 1. Ponytail 的核心理念：最好的代码是没写的代码

文章用一个“长马尾、戴眼镜的老员工”做比喻：别人写了 50 行代码，他看一眼，沉默，然后用 1 行替代并且能运行。

Ponytail 就是把这种思维放进 AI agent 里：

- 不急着新建组件、装依赖、写复杂封装；
- 先判断任务是否真的需要代码；
- 能用浏览器原生能力就不用库；
- 能一行解决就不写几十行。

**例子：**

用户要一个日期选择器，普通 AI 可能会：

- 安装 `flatpickr`
- 写包装组件
- 加样式文件
- 讨论时区问题

而 Ponytail 可能直接写：

```html
<!-- ponytail: browser has one -->
<input type="date">
```

意思是：浏览器已经内置日期选择器，不必造轮子。

---

##### 2. 实测效果：代码更少、速度更快、成本更低

作者在 Claude API 上做了基准测试，覆盖：

- 5 个日常任务：
  - 邮箱验证器
  - debounce
  - CSV 求和
  - 倒计时器
  - 限流器
- 3 个模型
- 3 种模式：
  - 无 skill
  - caveman skill
  - ponytail
- 每组 10 次运行，取中位数

结果显示，相比没有 skill 的 agent：

- **代码量减少 80%–94%**
- **成本降低 42%–75%**
- **速度提升 3–6 倍**

这些结果来自 Claude API，不是用户订阅套餐额度。

作者也提醒：结果会因模型和提示词而变化。  
对于某些“简短推理模型”，Ponytail 的规则注入和思考步骤可能反而增加 token 成本。

---

##### 3. Ponytail 的判断阶梯：写代码前先问 6 个问题

Ponytail 要求 AI 在写代码前按顺序判断：

1. **这个东西真的需要存在吗？**  
   不需要就跳过，符合 YAGNI 原则。

2. **标准库能做吗？**

5. **一行代码能解决吗？**

6. **只有前面都不行时，才写最小可用实现。**

但作者强调：这是“懒”，不是“不负责任”。以下内容不能被省掉：

- 信任边界校验
- 数据丢失处理
- 安全性

##### 1. 一句话判断

> 最值得保留的是：**把“资深工程师的懒”编码成 AI Agent 的前置决策梯：先判断是否不做，再判断能否复用，最后才写代码。**

它不是一个“少写代码”的工具，而是一套可迁移的工程判断框架：**减少产出不是目标，减少不必要的存在才是目标。**

---

##### 2. 最重要的洞见

###### 洞见 1：真正高级的工程能力，是“先证明不该写”

###### **核心观点：**  
> 写代码前的第一问不是“怎么实现”，而是“这东西需要存在吗？”

**为什么重要：**  
多数 AI Agent 默认把需求理解为“生成代码任务”，于是会自动扩展：装库、封装组件、加配置、写抽象。  
Ponytail 反过来要求 Agent 先过一条决策梯：

1. 不需要存在 → 不写  
2. 标准库能做 → 用标准库  
3. 平台原生能做 → 用原生能力  
4. 已有依赖能做 → 复用  
5. 一行能做 → 一行  
6. 最后才写最小实现  

**反常识之处：**  
我们常把“能力强”理解为“能写复杂系统”；但资深工程师的能力往往体现为：**让复杂系统不出现。**

**可迁移价值：**  
适用于产品、组织、流程、战略决策：  
> 先问“能不能不做”，再问“能不能复用”，最后才问“怎么做”。

**我应该记住什么：**  
> 最优解经常不是更好的实现，而是取消实现。

---

###### 洞见 2：“少”不是偷懒，前提是不能削掉边界条件

###### **核心观点：**  
> Lazy, not negligent：懒惰可以砍掉样板、抽象和过度设计，但不能砍掉验证、安全、数据保护和可访问性。

**为什么重要：**  
“极简主义”最容易被误用成代码高尔夫：短，但脆弱。  
Ponytail 的关键边界是：  
- 信任边界验证不能省  
- 数据丢失处理不能省  
- 安全不能省  
- 可访问性不能省  

**反常识之处：**  
真正的“少写代码”不是追求最短，而是追求**只保留必要复杂度**。

**可迁移价值：**  
任何降本增效都应区分两类成本：  
- 可砍成本：仪式、重复、炫技、过度抽象  
- 不可砍成本：安全、质量、信任、合规、关键体验  

**我应该记住什么：**  
> 极简不是少做事，而是不做错事、不做多余事。

---

###### 洞见 3：成本降低只是副产品，不是优化目标

###### **核心观点：**  
> Ponytail 的目标不是“最少 token”，而是“只写任务真正需要的代码”。

**为什么重要：**  
文章特别强调：在某些模型上，规则注入和推理步骤本身会增加成本。  
尤其在真实 Agent 会话里，规则每轮都会重新注入，成本未必总是下降。

**反常识之处：**  
很多 AI 工具宣传“更便宜、更快”，但这里承认：  
> 如果模型执行规则的思考成本超过代码节省，它可能更贵。

这反而更可信。

**可迁移价值：**  
不要把副指标当目标。  
- 少代码是结果，不是目标  
- 低成本是结果，不是目标  
- 快交付是结果，不是目标  
真正目标是：**减少不必要复杂度，同时保留关键质量。**

**我应该记住什么：**  
> 好系统不是永远更省，而是在正确的地方不浪费。

###### 洞见 4：每个“偷懒决策”都要留下升级路径

###### **核心观点：**  
> Ponytail 会用 `ponytail:` 注释标记每个捷径，并说明未来升级路径。

**为什么重要：**  
这是轻描淡写但很关键的设计。  
极简方案最大风险是：今天省掉的东西，明天没人知道为什么省、何时该补。

它用注释和债务命令把“暂时不做”变成可追踪资产，而不是遗忘的技术债。

**可迁移价值：**  
在产品、技术、组织中，所有“先不做”的决定都应留下三件事：

- 为什么现在不做  
- 什么条件下需要做  
- 将来如何补上  

**我应该记住什么：**  
> 好的懒惰不是逃避未来，而是给未来留清楚入口。

##### 3. 底层逻辑

###### **逻辑一：复杂度不是写出来的，是默认生成出来的**

- 表层现象：AI Agent 容易为简单需求生成大量代码。
- 深层原因：Agent 默认把任务理解为“实现更多”，而不是“判断是否必要”。
- 推导结论：要控制复杂度，必须在生成前加入决策约束，而不是生成后再重构。

---

###### **逻辑二：复用顺序决定系统复杂度**

- 表层现象：一个日期选择器可以是库、组件、样式、时区讨论，也可以只是 `&lt;input type="date">`。
- 深层原因：不同实现路径的维护成本完全不同；原生能力和标准库通常拥有最低长期成本。
- 推导结论：工程决策应优先选择“已有且足够好”的能力，而不是立即构造新层。

---

###### **逻辑三：真正的降本来自减少存在物，而不是压缩存在物**

- 表层现象：代码量、延迟、成本下降。
- 深层原因：不是代码被写得更短，而是不必要的代码根本没有出现。
- 推导结论：最高级的优化不是优化执行效率，而是消除无需执行的东西。

## 深度解读（1）

### 2026-09-18 00:46:15

#### AI 编程真正缺的，可能不是能力，而是“停止继续写”的判断

Ponytail 最值得注意的，不是它宣称能减少 80%—94% 的代码，而是它给 AI 编程代理增加了一套明确的**停止规则**：先判断功能是否需要存在，再依次检查标准库、平台原生能力、已有依赖和一行代码能否解决；只有这些都不成立，才开始写最小实现。

这看似只是 YAGNI 和“少造轮子”的重述，实际针对了 AI 代理的一个具体偏差：**模型更擅长证明自己做了很多事，而不擅长判断什么不该做。**用户要日期选择器，安装第三方库、包装组件、添加样式，显得完整且专业；直接使用 `&lt;input type="date">`，反而像没有充分工作。只要评价标准偏向“交付了多少可见产物”，代理就会自然过度实现。

##### 它提供的不是编码技巧，而是一种决策顺序

Ponytail 的关键设计是让代理“停在第一个足够成立的台阶”，而不是先生成复杂方案，再要求它事后精简。两者差异很大：后者已经让模型投入了设计、依赖选择和代码组织，沉没成本会促使它保留方案；前者则把“是否需要新增代码”变成首要问题。

这可以迁移到更广泛的产品工作中。AI 很容易把模糊需求展开成更多页面、流程、配置和文档，因为生成的边际成本极低；但**生成成本下降，不等于系统复杂度的持有成本下降**。每个新增组件仍然带来测试、升级、安全、兼容和认知负担。未来 AI 产品开发的重要能力，可能不是把需求展开得更快，而是建立一套可靠的“最小变更决策”：优先复用现有能力，限制变更面，并为暂缓实现的部分保留升级路径。

Ponytail 要求给每个捷径添加注释，说明以后如何升级，并提供债务清单，这一点尤其重要。它避免了把“简单”误解成草率：当前只做最低成本方案，但明确触发升级的条件。**可逆的简化比一次性追求完备更有价值。**

##### 漂亮数字证明力有限，真正该测的是维护负担

项目在五个日常小任务、三个 Claude 模型上报告了更少代码、更低成本和更短延迟，但这些任务本身很适合用标准能力解决，而且测试是单轮生成。真实代理会在多轮会话中反复注入规则，推理开销可能抵消输出节省；作者也承认在 GPT-5.5 上成本反而更高。因此，这些数字只能说明“约束能显著改变模型行为”，不能证明它已在复杂工程中带来同等收益。

更有意义的验证指标应当是：完成相同验收条件时，变更文件数、引入依赖数、缺陷率、回滚难度以及数周后的维护成本，而不是单纯统计代码行数。少写代码也可能漏掉边界条件，所以项目明确把信任边界验证、数据丢失、安全和无障碍排除在删减范围之外。

对 AI 开发工具而言，这提示了一个真实机会：在模型之上构建跨工具的**复杂度治理层**，持续审查新增依赖、重复能力和不必要抽象。它的价值不在于让 AI “更懒”，而在于纠正代理的行动偏好——把“完成任务”从产出最多，改成以最小、可验证、可升级的变更解决问题。
