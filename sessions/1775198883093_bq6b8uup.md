## 通俗精炼（1）

### 2026-04-03 06:48:03

#### AI 编程工作流正在成型，但 “全自动” 还不现实

##### 核心观点

作者分享了一套当前较实用的 AI 开发流程：  
先用`Claude + Gemini`生成前端和 mock 数据，再交给`Codex`写服务端代码，之后让`Claude`做 review，最后由`Codex`跑`Playwright`做端到端测试，自己再做最终验收和关闭 issue。

这套方法的本质不是 “一把梭自动开发”，而是把不同模型放在各自更擅长的环节里协作。

##### 为什么要这样分工

问题很直接：  
`Codex`在前端表现不够稳定，而 “全程交给 AI” 又容易失控，产出偏离预期。

所以更现实的做法是：
- 用更擅长生成界面和交互的模型先把前端雏形搭起来
- 再让更适合工程落地的工具补服务端代码
- 用额外模型做 review 和测试，降低翻车概率

本质上，这是一种 “多模型接力” 的工程化思路，而不是迷信单一模型。

##### 当前痛点

这套流程能跑起来，但成本和效率问题也很明显：

- `Claude`用量少但单价高，整体成本偏贵
- `Gemini CLI`速度慢，影响开发流畅度
- 前端仍然需要人反复沟通和校正，离完全自动化还有距离

也就是说，AI 已经能显著提效，但还没到 “省心到不用盯” 的阶段。

##### 评论区透露的更大趋势

讨论里有一个更值得关注的判断：  
过去很多公司死在 “从网页到移动端转型太慢”，未来也可能有公司死在 “Agent 化太慢”。

这背后的意思是：
- AI 不只是提效工具，可能会重塑产品形态
- 企业未来的竞争点，不只是有没有模型，而是能不能把产品和工作流真正 Agent 化
- 谁更早完成组织、产品、工具链的重构，谁就更可能占先机

##### 可落地的启发

对产品和技术团队来说，这段讨论释放了几个信号：

- 不要追求单模型包打天下，要按能力拆环节
- 前端、服务端、review、测试可以由不同 AI 分工完成
- 人的角色没有消失，重点转向 “编排、校准、验收”
- 真正的门槛，正在从 “会不会写代码” 转向 “会不会设计 AI 协作流程”

##### 一句话总结

这篇内容最有价值的地方在于：  
它展示了 AI 编程的现实状态 —— 已经能形成可用工作流，但核心竞争力不在模型本身，而在你如何把多个 AI 工具组织成一条高效、可控的生产链。

## 产品-最佳实践（1）

### 2026-04-03 06:48:32

#### 基于这个 AI 开发 Flow 的一个具体实例与最佳实践

你给出的内容，本质上是在讨论一个很典型的**多模型协作开发流**：

1. 先做前端原型 + mock 数据  
2. 再让 Codex 写正式代码  
3. 用 Claude 做 review  
4. 让 Codex 跑 Playwright 做 E2E  
5. 自己验收并关 issue  

这个 flow 已经很接近当前个人开发者 / 小团队的高效做法了。问题主要集中在两点：

- **前端生成质量不稳定**，容易 “AI 放飞”
- **模型组合成本高**，Claude 贵、Gemini CLI 慢

下面我用一个具体项目来说明，怎样把这个 flow 优化成更稳、更省、更适合长期复用的最佳实践。

---

##### 具体实例：做一个「订阅聚合管理面板」

假设你要做一个 Web 应用：`SubHub`

目标功能：

- 展示多个订阅源状态
- 查看今日请求量、成功率、延迟
- 支持新增 / 编辑订阅源
- 有一个简单的异常告警面板

---

##### 推荐的最佳实践 Flow

###### 1. 用擅长前端的模型先产出 “可验收原型”，但不要直接进入正式开发

###### 目标
不是 “一次生成完整前端”，而是先拿到一个**可讨论、可修改、可验收的静态界面**。

###### 做法
让前端模型只负责这几件事：

- 页面信息架构
- 布局与交互草图
- 假数据展示
- 组件拆分建议

###### 示例 Prompt
```markdown
请为一个 “订阅聚合管理面板” 生成前端原型，要求：

- 技术栈：React + Tailwind
- 页面包括：
  - 仪表盘概览
  - 订阅源列表
  - 新增 / 编辑订阅源弹窗
  - 异常告警区块
- 使用 mock 数据
- 不要接真实 API
- 不要写复杂状态管理
- 优先关注：信息层级、可读性、操作路径
- 输出：
  1. 页面结构说明
  2. 组件树
  3. 可运行的静态前端代码
```

###### 最佳实践
- **先锁页面结构，再锁视觉细节**，不要一开始就让模型 “做漂亮 UI”
- **mock 数据结构要尽量贴近未来真实接口**
- **先验收静态页面，再进入后端联调**
- 前端阶段只追求两个词：`可看`、`可改`

###### 为什么这样做
因为 AI 在前端最容易出问题的地方，不是 “写不出页面”，而是：

- 组件边界混乱
- 状态流设计混乱
- 视觉花哨但不实用
- 和后端数据结构脱节

所以前端模型的职责应该是：**快速生成交互草图，而不是决定整个工程结构**。

---

###### 2. mock 数据不是临时凑数，而是后续接口契约的基础

很多人会把 mock 数据当成演示用假数据，但最佳实践是：**把 mock 直接升格为接口契约草案**。

###### 示例 mock 数据
```json
{
  "summary": {
    "totalSources": 12,
    "healthySources": 10,
    "failedSources": 2,
    "avgLatencyMs": 182
  },
  "sources": [
    {
      "id": "src_001",
      "name": "OpenAI Relay",
      "status": "healthy",
      "todayRequests": 12430,
      "successRate": 0.982,
      "latencyMs": 156,
      "updatedAt": "2025-02-01T10:20:00Z"
    }
  ],
  "alerts": [
    {
      "id": "alert_001",
      "level": "warning",
      "message": "Gemini proxy latency is above threshold",
      "createdAt": "2025-02-01T09:12:00Z"
    }
  ]
}
```

###### 最佳实践
- 每个字段都要有明确语义，不要出现`data`, `info`, `extra`这种空泛命名
- 提前统一：
  - 时间格式
  - 状态枚举值
  - 分页结构
  - 错误返回结构
- mock 数据尽量覆盖：
  - 正常情况
  - 空状态
  - 错误状态
  - 极端值

###### 为什么这样做
这样做之后，Codex 写服务端时就不需要 “猜前端要什么”，而是直接按契约实现。

---

###### 3. 让 Codex 接手时，不是 “写代码”，而是 “按契约落地工程”

这是整个 flow 里最关键的一步。

###### 错误方式
```markdown
根据这个页面把后端写出来
```

这种指令太模糊，Codex 很容易：
- 自己发明数据结构
- 自己补业务逻辑
- 自己做过度封装
- 最后和前端原型脱节

###### 正确方式
给 Codex 的输入应当包括：

- 页面原型
- mock 数据
- 接口契约
- 技术栈约束
- 非功能要求

###### 示例任务拆法
```markdown
请基于以下约束实现服务端：

- 技术栈：Node.js + Fastify + PostgreSQL + Prisma
- 只实现以下接口：
  - GET /api/summary
  - GET /api/sources
  - POST /api/sources
  - PATCH /api/sources/:id
  - GET /api/alerts
- 返回结构必须与 mock 数据一致
- 先不做认证
- 需要可运行的 Prisma schema、seed、基本校验
- 不要过度抽象
- 每完成一步，说明目录结构和设计理由
```

###### 最佳实践
- **限制范围**：一次只让 Codex 做一个子系统
- **先 CRUD，后优化**
- **明确禁止过度抽象**
- **让它解释目录结构和设计取舍**
- **要求和 mock 完全对齐**

###### 为什么这样做
Codex 更适合把明确约束落成工程代码，而不是替你做产品决策或 UI 审美判断。

---

###### 4. 把 Claude Review 从 “代码审美检查” 升级为 “风险审查”

你提到会用 Claude review，这一步非常对，但最好把 review 标准化。

###### 不要只问
```markdown
帮我 review 一下这段代码
```

###### 应该问
```markdown
请从以下角度 review 这次提交：

1. 是否存在接口契约与前端 mock 不一致的问题
2. 是否有状态枚举、错误处理、时间格式不统一的问题
3. 是否有明显的边界条件遗漏
4. 是否有不必要的抽象或后续维护成本高的问题
5. 是否缺少关键测试场景
```

###### 最佳实践
让 Claude 优先查这几类问题：

- 契约不一致
- 命名不一致
- 错误处理缺失
- 测试遗漏
- 潜在回归风险
- 维护成本高的抽象

###### 为什么这样做
Review 阶段最有价值的不是 “这段代码优不优雅”，而是：

- 会不会线上翻车
- 会不会后面难改
- 会不会和前端对不上

---

###### 5. Playwright 不只是 “最后跑一下”，而应该绑定验收路径

你提到让 Codex 跑 Playwright 做 E2E，这已经很好了，但最佳实践是：**让 E2E 直接映射验收清单**。

###### 示例验收用例
```markdown
验收场景：

1. 打开仪表盘，能看到 summary 卡片
2. 进入订阅源列表，能展示 mock / 真实数据
3. 新增订阅源后，列表立即可见
4. 编辑订阅源后，状态正确刷新
5. 当接口返回空数据时，页面显示空状态
6. 当接口报错时，页面显示错误提示
```

###### 最佳实践
- 每个核心业务动作至少一个 E2E
- 空状态、错误状态一定要测
- 不要让 Playwright 只测 “能打开页面”
- 测试标题写成人能看懂的话
- 验收标准先写，再让 Codex 生成测试

###### 为什么这样做
很多 AI 生成的 E2E 最大问题是：
- 用例很多，但没覆盖真实业务风险
- 只验证页面元素存在，不验证业务结果

---

##### 这个实例上的 “更优模型分工”

结合你原文提到的问题，我建议把模型职责拆得更清楚：

| 阶段 | 更适合的模型角色 | 目标 |
|---|---|---|
| 前端原型 | 前端表达能力强的模型 | 出静态页面、组件结构、mock |
| 工程实现 | Codex | 落地后端、重构、补测试、跑命令 |
| 风险审查 | Claude | 查契约问题、回归风险、测试缺口 |
| 验收补漏 | 你自己 | 判断是否真符合产品预期 |

---

##### 一套更稳、更省成本的实战策略

###### A. 把 Claude 用在 “高价值节点”，不要用在铺量阶段
Claude 最贵，但也最适合做：

- 架构方案评估
- PR review
- 风险检查
- Prompt 重写
- 难点边界分析

不要拿它做：

- 大段样板代码生成
- 反复改 UI 文案
- 普通 CRUD 起手

###### 原则
> Claude 用在 “避免返工” 的节点，而不是 “加速堆代码” 的节点。

---

###### B. 把前端模型限制在 “原型层”，不要让它接管工程层
因为你已经观察到：**Codex 前端容易放飞，纯 AI 一把梭前端也容易失控**。

###### 所以推荐策略是
- 前端模型：只出原型、组件树、假数据
- Codex：负责工程化接入和代码整理
- 你：决定最终视觉和交互取舍

这会比 “让一个模型从设计到上线全包” 稳定得多。

---

###### C. 所有模型共享一份 “项目约束文档”
这是降低漂移的最有效方法之一。

###### 示例内容
```markdown
项目约束：

- 前端技术栈：React + Tailwind
- 后端技术栈：Fastify + Prisma + PostgreSQL
- 时间统一 ISO 8601
- 状态枚举：
  - healthy
  - warning
  - failed
- API 错误格式：
  - code
  - message
  - details
- 禁止：
  - 过度抽象
  - 未经说明新增依赖
  - 自创数据结构
```

###### 最佳实践
每次换模型、换阶段时，都把这份约束文档带上。

---

##### 最推荐的最终工作流

```markdown
1. 用前端强模型生成静态原型 + mock 数据
2. 你先验收页面结构，不满意就只改原型，不动正式工程
3. 把 mock 数据整理成 API 契约
4. 让 Codex 按契约写服务端和联调代码
5. 让 Claude 做风险导向 review
6. 让 Codex 基于验收清单生成 Playwright E2E
7. 你做最终验收，只关注产品是否可用
```

---

##### 一句话结论

你的 flow 方向是对的，真正的最佳实践不是 “找到最强单模型”，而是：

> **让不同模型只做自己最擅长的那一层，并且用 mock + 契约 + 验收清单把它们串起来。**

这样做的收益是：

- 前端不容易失控
- 后端实现更稳
- Claude 用量更省
- E2E 更贴近真实验收
- 整体返工率更低

- 不建议多个 agent 同时改同一批核心文件
- 最稳的串法是：前端原型产物冻结 -> Codex 实现 -> Claude review -> Codex 跑 E2E
- 真正把流程串起来的，不是 prompt 本身，而是中间那几份 “标准交付物”

下面我按你前面的例子，用`SubHub`这个 “订阅聚合管理面板” 项目，给你一套能落地的实践。

---

**整体设计**

先把`cmux`里的角色定下来。

建议一个 session 里至少有 5 个 pane /window：

- `orchestrator`：你自己，负责发任务、看产物、做 gate
- `frontend`：前端原型 agent，负责页面原型、组件树、mock 数据
- `backend`：Codex，负责服务端和联调实现
- `review`：Claude，负责风险导向 review
- `qa`：Codex 或另一个 agent，负责 Playwright E2E 和回归验证

这 5 个角色不要混。谁负责什么，一开始就定死。

---

**第一步：先定义 “阶段产物”，不要先定义 prompt**

如果没有统一产物，`cmux`只会变成 “同时开 4 个聊天窗”。

我建议你在项目里先放一套固定目录：

```text
docs/
  00-prd.md
  01-ui-spec.md
  02-api-contract.md
  03-acceptance.md

mock/
  dashboard.json
  sources.json
  alerts.json

reviews/
  latest-review.md

handoff/
  frontend-to-backend.md
  backend-to-review.md
  review-to-qa.md

tests/e2e/
```

每一阶段只认这些文件，不认口头描述。

推荐每个阶段的交付物：

- 前端阶段交付：`docs/01-ui-spec.md` + `mock/*.json`
- 后端阶段交付：`docs/02-api-contract.md` + 代码实现
- review 阶段交付：`reviews/latest-review.md`
- QA 阶段交付：`tests/e2e/*` + 验证结果
- 最终验收交付：`docs/03-acceptance.md`打勾

这样`cmux`里的每个 pane 都知道：自己不是 “接着聊”，而是 “基于文件继续生产”。

---

**第二步：把`cmux` session 设计成 “串行写入 + 并行检查”**

这是最关键的实践原则。

不要让多个 agent 同时改主分支同一片代码。最稳的方式是：

- 写代码阶段串行
- review 和测试可以并行
- 人工只在关键节点做 gate

建议流程是：

1. `frontend`产出原型和 mock
2. 你确认 UI 结构和 mock 没问题
3. `backend`才开始写正式代码
4. `review`在`backend`接近完成时介入
5. `qa`在接口稳定后写 E2E 并执行
6. 你看最终效果并验收

也就是说，`cmux`是并排开着，但流程不是全并发乱跑，而是**阶段式推进**。

---

**第三步：在`cmux`里给每个 pane 固定职责**

如果`cmux`支持类似 session/pane 命名和发送命令，建议你按这个逻辑组织。

一个典型 session：

- `pane 1: orchestrator`
  - 你本人
  - 看 git 状态、看产物、决定下一步
- `pane 2: frontend`
  - 只允许改`docs/01-ui-spec.md`、`mock/`、前端原型代码
- `pane 3: backend`
  - 只允许改后端实现、接口定义、数据库 schema
- `pane 4: review`
  - 只读，输出 review 文件，不直接改业务代码
- `pane 5: qa`
  - 只写`tests/e2e/`，运行 Playwright，记录失败截图 / 日志

最重要的不是 pane 数量，而是这个规则：

- `frontend`不碰后端
- `backend`不重做 UI 设计
- `review`不直接接管实现
- `qa`不顺手改业务逻辑

这样 agent 不会相互污染。

---

**第四步：给每个阶段写 “固定 handoff 模板”**

这一步是把流程真正串起来的关键。

###### A. 前端 -> 后端 handoff

在`handoff/frontend-to-backend.md`放固定结构：

```md
目标页面：
- 仪表盘
- 订阅源列表
- 新增 / 编辑弹窗
- 告警区块

已确认内容：
- 页面信息结构已冻结
- mock 数据字段已冻结
- 状态枚举：healthy /warning/failed
- 时间格式：ISO 8601

需要后端实现：
- GET /api/summary
- GET /api/sources
- POST /api/sources
- PATCH /api/sources/:id
- GET /api/alerts

要求：
- 返回字段必须与 mock 一致
- 不得自行发明新字段
- 不做认证
- 先做最小可运行版本
```

这个 handoff 一旦确认，`backend` pane 的 Codex 就只按这份文件工作。

###### B. 后端 -> Review handoff

`handoff/backend-to-review.md`：

```md
本次变更：
- 已实现 summary /sources/alerts 接口
- 已接入 Prisma schema 和 seed
- 已完成前后端联调

请重点 review：
1. 契约是否与 mock 一致
2. 错误处理是否完整
3. 状态枚举是否统一
4. 是否有过度抽象
5. 是否缺少关键测试
```

###### C. Review -> QA handoff

`handoff/review-to-qa.md`：

```md
请优先覆盖以下风险：
- 新增订阅源后列表未刷新
- 编辑状态后 summary 未同步
- 空数据状态未处理
- 接口报错时页面提示缺失
```

这样每一步都是带上下文切换，不是重新解释一遍项目。

---

**第五步：让`cmux`只做编排，不做 “智能决策”**

你用`cmux`时，最好的姿势不是让它替你决定流程，而是：

- 帮你维持多个 agent 常驻
- 快速切 pane
- 把 prompt 和产物扔到对应 pane
- 收集输出
- 在阶段节点执行下一步

换句话说，`cmux`做的是 “工作台”，不是 “总设计师”。

一个典型操作节奏会像这样：

###### 阶段 1：前端原型
在`frontend` pane 发任务：

```text
基于 docs/00-prd.md 生成：
1. docs/01-ui-spec.md
2. mock/dashboard.json
3. mock/sources.json
4. mock/alerts.json

要求：
- 只做静态原型
- 不接真实 API
- mock 字段可直接作为未来接口契约
- 不要设计复杂状态管理
```

然后你在`orchestrator` pane 检查这几样：

- 页面结构对不对
- mock 字段够不够
- 是否覆盖空状态 / 错误状态
- 状态命名是否统一

确认后，进入下一阶段。

###### 阶段 2：Codex 正式实现
在`backend` pane 发任务：

```text
请基于：
- docs/01-ui-spec.md
- mock/*.json
- handoff/frontend-to-backend.md

实现后端最小可运行版本。

要求：
- 返回结构必须与 mock 一致
- 先实现 CRUD 和列表查询
- 不要过度抽象
- 每完成一个接口，更新 docs/02-api-contract.md
```

这里最好要求它 “边做边更新契约文档”，避免后面 review 时口径不一致。

###### 阶段 3：Claude review
在`review` pane 发任务：

```text
请 review 当前变更，重点检查：
- API 与 mock 是否一致
- 字段命名是否漂移
- 状态流是否存在边界遗漏
- 是否缺失必要测试
- 是否有未来维护成本高的抽象

输出到 reviews/latest-review.md
```

你看 review 结论后，再决定要不要回到`backend` pane 修。

###### 阶段 4：Playwright E2E
在`qa` pane 发任务：

```text
请基于 docs/03-acceptance.md 和 handoff/review-to-qa.md：
1. 编写 Playwright 用例
2. 跑测试
3. 输出失败点和修复建议
```

**第六步：把 “阶段切换条件” 写死，不要靠感觉**

这是很多 AI flow 最容易崩的地方。

你要明确规定：上一阶段没过，不准进入下一阶段。

推荐 gate 规则：

###### Gate 1：前端阶段完成，才能进后端
满足以下条件才允许切换：
- `docs/01-ui-spec.md`已确认
- `mock/*.json`字段冻结
- 空状态 / 错误状态有 mock 示例
- 组件边界没有明显歧义

###### Gate 2：后端阶段完成，才能进 review
满足以下条件：
- 主要接口已跑通
- 返回结构与 mock 一致
- 基础 seed 数据可用
- 前端可联调

###### Gate 3：review 完成，才能进 QA
满足以下条件：
- 高优先级问题已处理
- review 文档已落盘
- 不再改接口契约

###### Gate 4：QA 通过，才能最终验收
满足以下条件：
- 核心 E2E 全通过
- 空状态 / 错误状态有覆盖
- 关键页面手验通过

这样流程才叫 “串起来”，否则只是 “轮流问模型”。

**第七步：推荐把`cmux`和 Git 分支 /worktree 配合使用**

如果多个 pane 都会写代码，最好不要直接都指向同一个工作区。

更稳的方式：

- 主工作区：你自己看和合并
- `frontend`：`feat/ui-prototype`
- `backend`：`feat/backend`
- `qa`：`feat/e2e`
- `review`：只读当前 diff

这样有几个好处：

- agent 互不覆盖
- 你能清楚看到每一阶段改了什么
- review 可以基于明确 diff 进行
- 最后可以按阶段 merge，而不是一次性大乱炖

如果你不想搞多个 worktree，至少也要做到：
- 同一时刻只允许一个写代码 agent 改主工作区
- 其他 pane 只读或只写自己的目录

**第八步：Claude 成本高的问题，正适合用`cmux`来压缩**

结合你原文里的痛点，我建议这样用：

- `frontend`用前端强、便宜一点的模型做原型
- `backend`用 Codex 做重活
- `review`才开 Claude，而且只在 gate 节点调用
- `qa`继续交给 Codex 跑 Playwright

- Claude 只做 “高杠杆检查”

这会比 “Claude 一直在线帮你想所有事” 省很多。

```md
- 页面包含：
  - 仪表盘
  - 订阅源列表
  - 新增 / 编辑订阅源弹窗
  - 告警区
- 明确列出空状态、错误状态
- 不做复杂状态管理
```

`docs/01-ui-spec.md`里最好有：

- 页面列表
- 每个页面的组件树
- 用户操作路径
- 各页面依赖的数据字段
- 空状态 / 错误状态

这一步的产出就是后续工程的 “视觉和数据契约草案”。

**第 3 步：在`orchestrator` pane 做第一次 gate**

这一步别省。

你检查这几件事：

- 页面结构是不是你要的
- mock 字段是否明确，不要有`data`, `extra`这种泛字段
- 是否覆盖空状态和错误状态
- 状态枚举是否统一
- 页面操作路径是否清楚

只有这一步通过，才进入后端实现。

建议你把 gate 条件写进`.ai/gates/gate-frontend.md`：

```md
前端阶段通过条件：
- `docs/01-ui-spec.md`已确认
- `mock/*.json`已确认
- 所有核心页面都有明确字段来源
- 空状态和错误状态已定义
- 状态枚举和值已冻结
```

这能防止 “感觉差不多就往下走”。

**第 4 步：生成 handoff 文件`handoff/frontend-to-backend.md`**

这是最核心的一步之一。

你可以让 agent 生成，也可以自己整理，但最终要有一份稳定的 handoff：

```md
本阶段已确认：

页面：
- 仪表盘
- 订阅源列表
- 新增 / 编辑弹窗
- 告警区块

字段约束：
- 状态枚举：healthy /warning/failed
- 时间格式：ISO 8601
- 所有响应字段以 mock 为准

需要后端实现：
- GET /api/summary
- GET /api/sources
- POST /api/sources
- PATCH /api/sources/:id
- GET /api/alerts

要求：
- 返回结构必须与`mock/*.json`保持一致
- 禁止新增未说明字段
- 先实现最小可运行版本
- 不做认证
- 不做过度抽象
```

这份文件的作用是：把 “原型阶段” 正式冻结成 “实现阶段的输入”。

**第 5 步：在`backend` pane 用 Codex 落地**

这时候再让 Codex 开始写正式代码。

在`backend` pane 的任务应该非常具体：

```md
请基于以下输入实现服务端：

输入文件：
- `docs/00-prd.md`
- `docs/01-ui-spec.md`
- `mock/dashboard.json`
- `mock/sources.json`
- `mock/alerts.json`
- `handoff/frontend-to-backend.md`

实现要求：
- 技术栈：Fastify + Prisma + PostgreSQL
- 实现接口：
  - GET /api/summary
  - GET /api/sources
  - POST /api/sources
  - PATCH /api/sources/:id
  - GET /api/alerts
- 返回结构必须与 mock 一致
- 每完成一个接口，更新`docs/02-api-contract.md`
- 先做最小可运行版本
- 不要过度抽象
- 如果需要补充字段或约束，必须写入`docs/02-api-contract.md`
```

这里有两个非常重要的实践：

- 让它 “边实现边维护接口契约文档”
- 明确禁止它自己发明新结构

这样后面的 Claude review 就有统一参照物。

**第 6 步：在`orchestrator` pane 做第二次 gate**

检查后端阶段是否进入 review：

建议检查：

- 接口是否已跑通
- 返回结构是否和 mock 对齐
- 数据库 schema 是否明确
- 基础 seed 是否可跑
- 前后端是否能联调

写进`.ai/gates/gate-backend.md`：

```md
后端阶段通过条件：
- 所有核心接口可运行
- 返回结构与 mock 一致
- `docs/02-api-contract.md`已更新
- 基础 seed 数据可用
- 前端至少可联调展示主流程
```

**第 7 步：在`review` pane 用 Claude 做 “风险审查”**

这里不要让 Claude 做泛 review，而是做 “有清单的审查”。

在`review` pane 给它任务：

```md
请基于当前代码和以下文件进行 review：

输入：
- `docs/01-ui-spec.md`
- `docs/02-api-contract.md`
- `mock/*.json`
- 当前 git diff
- `handoff/backend-to-review.md`

重点审查：
1. API 是否与 mock / 契约一致
2. 字段命名是否漂移
3. 状态枚举和时间格式是否统一
4. 错误处理是否完整
5. 是否有边界条件遗漏
6. 是否有未来维护成本高的抽象
7. 是否缺少关键测试

输出到：
- `reviews/latest-review.md`
```

你最好先准备一份`handoff/backend-to-review.md`：

```md
本次实现内容：
- summary /sources/alerts 接口已实现
- Prisma schema 已建立
- seed 已添加
- 前端已可联调

请重点关注：
- 契约一致性
- 边界条件
- 错误处理
- 测试缺口
```

这样 review 的质量会明显高很多。

**第 8 步：回到`backend` pane 修 review 问题**

这一步不要让 Claude 直接改代码，还是让 Codex 执行修复。

你把`reviews/latest-review.md`作为输入喂给`backend` pane：

```md
请根据`reviews/latest-review.md`修复高优先级问题。

要求：
- 先修契约不一致
- 再修错误处理和边界问题
- 不要引入额外大改
- 如有接口变化，更新`docs/02-api-contract.md`
```

为什么这样串：

- Claude 擅长发现问题
- Codex 更适合工程化执行修复

这就是你前面那套分工思路的自然延伸。

**第 9 步：生成 QA handoff `handoff/review-to-qa.md`**

review 修完后，准备交给 QA。

示例：

```md
当前阶段状态：
- 核心接口已实现
- 高优先级 review 问题已修复
- 契约已冻结

请优先测试：
- 打开仪表盘可见 summary 卡片
- 订阅源列表正常显示
- 新增订阅源后列表刷新
- 编辑订阅源后状态同步
- 空数据时空状态正常
- 接口错误时错误提示正常
```

这份 handoff 非常适合直接作为 Playwright 任务说明。

**第 10 步：在`qa` pane 用 Codex 写并跑 Playwright**

这一步建议把验收标准写成`docs/03-acceptance.md`。

例如：

```md
验收标准：
- 打开仪表盘，看到概览卡片
- 打开订阅源列表，显示已有来源
- 新增来源后列表立即出现
- 编辑来源状态后概览同步更新
- 空数据时显示空状态
- 接口异常时显示错误提示
```

然后在`qa` pane 给任务：

```md
请基于以下文件完成 E2E：

输入：
- `docs/03-acceptance.md`
- `handoff/review-to-qa.md`
- 当前前后端实现

要求：
- 编写 Playwright 用例到`tests/e2e/`
- 核心业务路径至少一条用例一个
- 必须覆盖空状态和错误状态
- 先运行测试，再输出失败点和建议
```

这一步最重要的实践是：

不要只测 “页面打开了”，要测 “用户动作和业务结果”。

**第 11 步：你在`orchestrator` pane 做最终验收**

这时候你关注的就不是 “代码优雅不优雅”，而是：

- 产品是否符合预期
- 流程是否能跑通
- 交互是否顺
- 错误提示是否合理

也就是回到 “产品 owner” 的视角。

**如果用`cmux`，推荐这样组织每日工作流**

每天 / 每次迭代你都可以重复这个模式：

1. 在`orchestrator` pane 写今日目标
2. `frontend` pane 负责新页面 / 变更原型
3. `backend` pane 负责实现
4. `review` pane 只在关键节点触发
5. `qa` pane 在功能稳定后补测试
6. 每完成一个阶段，就更新 handoff 和 gate 文件

这样你会得到一个很清晰的流水线感，而不是混乱地在模型之间切来切去。

**最关键的 5 条实践纪律**

如果你真要用`cmux`落地，我最建议你坚持这 5 条：

- 以文件交接，不靠聊天上下文交接
- 写代码阶段尽量串行，不让多个 agent 同时改同一区域
- review 只查风险，不负责写实现
- QA 只写测试，不顺手改业务代码
- 每个阶段必须有 gate 条件，没过就不切下一阶段

这 5 条会直接决定这套东西是 “稳定提效” 还是 “加倍混乱”。

**一个更实用的串联方式：用 git worktree 配合`cmux`**

如果你想再稳一点，可以把不同 pane 绑定到不同 worktree：

- `frontend` → `feat/ui-prototype`
- `backend` → `feat/backend`
- `qa` → `feat/e2e`
- `review` → 只读当前 diff
- `orchestrator` → 主工作区

好处：

- 不会互相覆盖
- 更容易回看每阶段改了什么
- review 更容易聚焦
- 合并节奏更清楚

如果你不想搞 worktree，至少要做到：

- 同一时刻只有一个写代码 pane 有权改核心目录

**你这套 flow 用`cmux`后，最大的收益是什么**

不是 “自动化更强”，而是这几个点：

- 阶段边界更清楚
- 模型职责更清楚
- handoff 更清楚
- Claude 只在高价值节点介入，成本更低
- 返工率更低
- 你更容易从 “盯着 AI 生成代码” 切换成 “编排生产流程”

这也是你原帖里那种思路的进一步工程化版本。

**一句话落地方案**

用`cmux`串你这套流程，最推荐的方式是：

- 一个 session 固定 5 个 pane：`orchestrator` / `frontend` / `backend` / `review` / `qa`
- 用`docs/`、`mock/`、`handoff/`、`reviews/`、`tests/e2e/`作为阶段产物
- 用 gate 文件控制阶段切换
- 前端原型 → 契约冻结 → Codex 实现 → Claude review → Codex E2E → 人工验收
