**WhileTrue**

### 我阅读了 Claude Code 的源代码，以找出它为何大量消耗 token。以下是所有内容。

如果你最近浏览过 r/ClaudeCode 或 r/ClaudeAI，你会看到那些抱怨。最多 5 倍的用户在 90 分钟内消耗完 5 小时的使用时长。人们降级到 v2.1.68 版本。多个 GitHub 问题获得了 90 多个点赞，但没有官方响应。

我花了一天时间阅读打包的 \`cli.js\`，进行了对照实验，并发现了问题所在。实际上存在三个独立的问题，社区一直将它们混为一谈。

#### 三个问题

问题1: --恢复缓存未命中 (#34629)

当你使用 \`claude --resume\` 恢复会话时，消息结构与新会话不同。在版本 2.1.69 中引入的 \`deferred\_tools\_delta\` 导致第一个消息块完全不同（13.4KB vs 352B）。首次请求时缓存未命中。

这是每次恢复会话时的一次性影响。烦人，但无法解释持续消耗。

问题 2: 会话中缓存失效 (#40524)

一些用户报告，在会话中途，缓存读取量从 300K+降至 11K。缓存写入成功，但读取失败。这是一个独立的缺陷，有独立的根本原因。下面的环境变量修复方法对这个问题没有帮助。

问题3：跨会话且跨子代理缓存未命中（我发现的）

这才是大问题。而且这不是一个 bug——而是一个带有毁灭性副作用的特性。

#### 我在源代码中发现的

自 v2.1.69 版本起，Claude Code 会将这个注入到系统提示中：

```plaintext
x-anthropic-billing-header: cc_version=2.1.88.a3f; cc_entrypoint=cli; cch=00000;
```

那个 \`.a3f\` 是你第一条消息的一个 3 字符哈希值：

```javascript
const chars = [4, 7, 20].map(i => firstUserMessage[i] || "0").join("");
return sha256("59cf53e54c78" + chars + version).slice(0, 3);
```

不同的对话，不同的第一条消息，不同的哈希值。而这里有个没人注意到的点：\*\*子代理也会得到不同的哈希值。\*\*每个代理的工具调用都有其独立的消息上下文，因此其哈希值与主对话不同。

我在自己的会话中验证了这一点——一次对话中有3个不同的哈希值

```text
Main conversation:  cc_version=2.1.88.a3f  (34 API calls)
Subagent 1:         cc_version=2.1.88.e91  (3 calls)
Subagent 2:         cc_version=2.1.88.7c2  (3 calls)
```

#### 为什么这会破坏缓存

Anthropic 的提示缓存使用前缀匹配。不进行按会话隔离——缓存在组织/工作区级别共享（根据其文档）。系统提示（约 12K token）应该只缓存一次，并在所有会话和子代理中重复使用。

但账单头部位于前端，每次都会变化。前缀从不匹配。缓存未命中。每次新对话以及每次子代理调用时，都会产生 12K 令牌的缓存创建。

在一次对话中使用 5 次 Agent 工具调用？这相当于 5 × 12K = 60K 个 token 的不必要缓存重建。

#### A/B 测试

我编写了一个测试脚本。4个会话，不同的提示，8秒的间隔。

页眉开启（默认）：

cache\_read: \~11K (仅工具块)

缓存创建: \~12K (系统提示重建)

命中率: 48%

页眉关闭：

缓存读取: \~23K (工具 + 系统提示)

cache\_creation: 0

命中率：99.98%

每会话节省：系统提示成本约节省85%。约便宜7倍。

#### 修复

```bash
export CLAUDE_CODE_ATTRIBUTION_HEADER=false
```

将其添加到您的 .zshrc 或 .bashrc。仅影响新会话。

#### 让我烦恼的部分

三个事实：

悄无声息地添加了破坏缓存的账单头部，没有添加变更日志条目。

2\. 用于禁用它的环境变量在源代码中作为一个正式的功能开关存在。

3\. 这个环境变量在任何官方文档中都不存在。你必须反混淆打包的 cli.js 才能知道它的存在。

所有人都收到了头部文件。关闭开关未被文档化。

该 API 有一个\`metadata\`字段，正是为此类账单归属而设计的。将跟踪数据放入系统提示中——这会破坏基于前缀的缓存——是一个选择。

我不会告诉你该从这件事得出什么结论。事实本身就说明了一切。

#### 这无法解决的问题

需要明确的是：这个环境变量仅解决问题3。它无法解决：

会话中缓存失效 (#40524)

恢复缓存不匹配 (#34629)

长时间对话中的整体语境增长

如果您看到 cache\_read 下降到接近零（不仅仅是在第一轮），那就是问题 2——一个不同的问题。

#### 复制它

测试脚本和原始数据：

github.com/motiful/cc-cache-audit

或者快速检查一下——查看你的会话 JSONL：

```bash
grep -o '"cache_creation_input_tokens":[0-9]*' \
~/.claude/projects/*/<session-id>.jsonl \
| head -10
```

如果您看到重复的 12K+ 值，说明您正在为系统提示的重建付费。

## 通俗精炼（1）

### 2026-04-01 02:24:21

#### Claude Code 为什么会 “异常吃 Token”？

##### 核心结论

作者阅读了 Claude Code 的打包源码并做了实验后发现：**大家抱怨的高 token 消耗，其实是 3 个不同问题混在了一起**。其中，真正影响最大的，是一个并非传统意义上的 bug，而是一个**会破坏缓存命中率的设计选择**。

##### 三个问题，别混为一谈

###### 1. `--resume`恢复会话时的缓存未命中
使用`claude --resume`恢复旧会话时，请求结构和新会话不同，导致首轮请求缓存无法命中。  
**影响**：只在恢复时发生一次，虽然烦人，但不足以解释持续高消耗。

###### 2. 会话进行中缓存突然失效
有用户发现，对话过程中缓存读取量会从几十万 token 突然掉到很低。  
**影响**：这是一个独立缺陷，和下面提到的修复方法无关。

###### 3. 跨会话、跨子代理的缓存失效
这是作者认为**最关键的问题**。Claude Code 会在系统提示词里插入一个带哈希值的 billing header，这个哈希会随着**首条用户消息**变化，连**子代理**也会生成不同值。  
**结果**：原本应被复用的系统提示前缀不再一致，缓存无法复用，每次新会话、每次子代理调用都要重新创建一遍高成本缓存。

##### 为什么这会大幅增加 Token 消耗？

Anthropic 的提示缓存依赖 “前缀匹配”。正常情况下，系统提示这类固定内容应该一次缓存、多次复用。  
但现在由于前面多了一个每次变化的 header，**前缀不一致，缓存命中失败**。

通俗说：  
本来是 “同一段说明书反复复用”，现在变成 “每次都要重新抄一遍说明书”。

如果一次对话用了多次 Agent / 子代理调用，就会反复支付这部分系统提示的 token 成本。

##### 实验结果说明了什么？

作者做了 A/B 测试，结论很直接：

###### 默认开启 header
- 系统提示反复重建
- 缓存命中率只有约 48%

###### 关闭 header
- 系统提示可被复用
- 缓存命中率接近 99.98%
- 每个会话系统提示成本可节省约 85%
- 整体大约可便宜 7 倍

##### 临时解决办法

可以通过环境变量关闭这个 attribution header：

```bash
export CLAUDE_CODE_ATTRIBUTION_HEADER=false
```

把它加入`.zshrc`或`.bashrc`，**只对新会话生效**。

##### 这件事真正让人不舒服的点

###### 1. 影响缓存的改动没有明确公开说明
作者认为，这个会破坏缓存的 header 是 “悄悄加入” 的，变更日志里没有清晰提示。

###### 2. 关闭开关其实早就存在
源码里已经有正式功能开关，但没有公开文档。

###### 3. 本可以用更合理的实现方式
API 本身有`metadata`字段，理论上可以承载这类归因信息，而不是塞进系统提示词里破坏缓存。

作者的潜台词很明显：**这不是技术上做不到，而是实现方式选择得不理想。**

##### 需要注意：这个办法并不能解决所有问题

关闭环境变量只能解决第 3 个问题，**不能解决**：

- `--resume`的缓存不匹配
- 会话中途缓存突然失效
- 长对话本身带来的上下文膨胀

也就是说，如果你看到缓存读取在会话过程中持续掉到接近 0，那大概率是第 2 个问题，不是这个开关能修好的。

##### 一句话总结

这篇文章的核心观点是：**Claude Code token 消耗异常，并不只是 “模型变贵” 或 “缓存失灵” 这么简单，而是多个问题叠加，其中最致命的是一个会持续破坏缓存复用的 header 设计。**  
对重度用户来说，这意味着：**很多 token 不是花在 “思考” 上，而是花在 “重复构建本该复用的系统提示” 上。**
