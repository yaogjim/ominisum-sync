##### 开源框架，用于构建您的组织内部的编码代理。

像 Stripe、Ramp 和 Coinbase 这样的精英工程组织正在构建自己的内部编码代理——Slack 机器人、命令行界面（CLI）和 Web 应用，这些代理部署在工程师日常工作的环境中。这些代理与内部系统相连，具备适当的上下文、权限控制和安全边界，能够以最小的人工监督进行操作。

Open SWE 是该模式的开源版本。基于 [LangGraph](https://langchain-ai.github.io/langgraph/) 和 [Deep Agents](https://github.com/langchain-ai/deepagents) 构建，它为你提供了这些公司内部构建的相同架构：云沙箱、Slack 和 Linear 调用、子代理编排以及自动 PR 创建——可根据你自己的代码库和工作流进行自定义。

---

#### Architecture

Open SWE 做出与最佳内部编码代理相同的核心架构决策。以下是它如何映射到 Stripe 的 Minions、Ramp 的 Inspect 以及 Coinbase 的 Cloudbot 的概述中描述的模式的说明：

与其分叉现有代理或从零开始构建，Open SWE **组合构建于** [Deep Agents](https://github.com/langchain-ai/deepagents) 框架之上 — 类似 Ramp 基于 OpenCode 构建的方式。这为您提供了升级路径（引入上游改进），同时允许您为组织自定义编排、工具和中间件。

```
create_deep_agent(
    model="anthropic:claude-opus-4-6",
    system_prompt=construct_system_prompt(repo_dir, ...),
    tools=[http_request, fetch_url, commit_and_open_pr, linear_comment, slack_thread_reply],
    backend=sandbox_backend,
    middleware=[ToolErrorMiddleware(), check_message_queue_before_model, ...],
)
```

每个任务都在其独立的云沙箱（ **isolated cloud sandbox** ）中运行——这是一个具备完全 Shell 访问权限的远程 Linux 环境。代码仓库被克隆到其中，代理获得完全权限，任何错误的影响范围都被完全控制。不具备生产环境访问权限，也不会有确认提示。

Open SWE 开箱即用支持多种沙箱提供商 — [Modal](https://modal.com/) 、 [Daytona](https://www.daytona.io/) 、 [Runloop](https://www.runloop.ai/) 和 [LangSmith](https://smith.langchain.com/) — 你也可以接入自己的沙箱提供商。详见 自定义指南 了解详情。

这遵循了三家公司共同秉持的原则： **先隔离，然后在边界内授予完全权限。**

- 每个线程都会获得一个持久的沙箱（在后续消息中复用）
- 沙箱在变得不可访问时会自动重新创建
- 多个任务并行运行——每个都在自己的沙箱中，无需排队

##### 3\. 工具——精心挑选，而非积累

Stripe 的核心见解： *工具精选比工具数量更重要。* Open SWE 遵循这一原则，采用了一个规模小但重点突出的工具集：

Tool Purpose

`execute` Shell commands in the sandbox

`fetch_url` Fetch web pages as markdown

`http_request` API calls (GET, POST, etc.)

`commit_and_open_pr` Git 提交 + 打开 GitHub 草稿 PR

`linear_comment` 发布更新到 Linear 工单

`slack_thread_reply` Reply in Slack threads

此外还有内置的 Deep Agents 工具： `read_file` 、 `write_file` 、 `edit_file` 、 `ls` 、 `glob` 、 `grep` 、 `write_todos` 和 `task` （子代理生成）。

Open SWE 从两个来源收集上下文：

- **`AGENTS.md`** — 如果仓库在根目录下包含一个 `AGENTS.md` 文件，则会从沙箱中读取并注入到系统提示中。这相当于你仓库级别的 Stripe 规则文件：每个代理运行都应遵循的编码规范、测试要求和架构决策。
- **Source context** — The full Linear issue (title, description, comments) or Slack thread history is assembled and passed to the agent, so it starts with rich context rather than discovering everything through tool calls.

Open SWE 的编排有两个层次：

**子代理：** Deep Agents 框架原生支持通过 `task` 工具生成子代理。主代理可以将独立的子任务分发到隔离的子代理——每个子代理都有自己的中间件栈、待办事项列表和文件操作。

**中间件：** 确定性的中间件钩子围绕代理循环运行：

- **`check_message_queue_before_model`** — 注入后续消息（在执行过程中到达的 Linear 评论或 Slack 消息），这些消息会在下次模型调用前被处理。你可以在代理工作时向其发送消息，它会在下一步操作中获取你的输入。
- **`open_pr_if_needed`** — 代理后安全网，若代理未自行执行，则提交并打开 PR。这是 Stripe 确定性节点的轻量级版本——确保关键步骤无论 LLM 行为如何都能执行。
- **`工具错误中间件`** — 捕获并优雅地处理工具错误。

文章中的三家公司都汇聚于 **Slack 作为主要调用界面** 。Open SWE 也同样如此：

- **Slack** — 在任何线程中提及该机器人。支持 `repo:owner/name` 语法来指定要操作的仓库。该代理在线程中回复状态更新和 PR 链接。
- **Linear** — 在任何问题中添加评论 `@openswe` 。该代理会读取完整的问题上下文，用👀表情回应以确认，并将结果作为评论发布。
- **GitHub** — 在代理创建的拉取请求的评论中标记 `@openswe` ，以使其处理审查反馈并将修复推送到同一分支。

每次调用都会创建一个确定性的线程 ID，因此针对同一问题或线程的后续消息会路由到同一个正在运行的代理。

该代理被指示在提交前运行代码检查工具、代码格式化工具和测试。 `open_pr_if_needed` 中间件作为后盾——如果代理完成任务却未打开 PR，中间件将自动处理这种情况。

这是一个您可以为组织扩展 Open SWE 的领域：添加确定性的 CI 检查、可视化验证或审查关卡作为额外的中间件。有关具体操作，请参阅 自定义指南 。

#### Customization Guide

Open SWE 设计为可分叉并为您的组织定制。核心智能体由一个函数组装而成—— `get_agent()` （位于 `agent/server.py` 中）——您可以在该函数中替换沙箱、模型、工具和触发器。

```
# agent/server.py — the key lines
return create_deep_agent(
    model=make_model(os.environ.get("LLM_MODEL_ID", DEFAULT_LLM_MODEL_ID), temperature=0, max_tokens=20_000),
    system_prompt=construct_system_prompt(repo_dir, ...),
    tools=[http_request, fetch_url, commit_and_open_pr, linear_comment, slack_thread_reply],
    backend=sandbox_backend,
    middleware=[
        ToolErrorMiddleware(),
        check_message_queue_before_model,
        ensure_no_empty_msg,
        open_pr_if_needed,
    ],
)
```

#### 1\. Sandbox

默认情况下，Open SWE 在 [LangSmith 云沙箱](https://docs.smith.langchain.com/) 中运行每个任务 — 一个隔离的 Linux 环境，在该环境中代理会克隆仓库并执行命令。沙箱的创建和连接由 `agent/integrations/langsmith.py` 处理。

##### 使用一个自定义的沙箱模板

设置环境变量以使用自定义 Docker 镜像：

这对于预先安装您的存储库所依赖的语言、框架或内部工具非常有用——减少每次代理运行的设置时间。

##### 使用不同的沙箱提供商

设置 `SANDBOX_TYPE` 环境变量以切换提供方。每个提供方在 `agent/integrations/` 目录下有一个对应的集成文件，并且在 `agent/utils/sandbox.py` 文件中注册了一个工厂函数：

`SANDBOX_TYPE` Integration file Required env vars

`langsmith` (default) `agent/integrations/langsmith.py` `LANGSMITH_API_KEY_PROD`, `SANDBOX_TYPE="langsmith"`

`daytona` `agent/integrations/daytona.py` `DAYTONA_API_KEY`, `SANDBOX_TYPE="daytona"`

`runloop` `agent/integrations/runloop.py` `RUNLOOP_API_KEY`, `SANDBOX_TYPE="runloop"`

`modal` `agent/integrations/modal.py` Modal credentials, `SANDBOX_TYPE="modal"`

`local` `agent/integrations/local.py` 无（无隔离 — 仅用于开发）， `SANDBOX_TYPE="local"`

> **警告** : `local` 直接在你的主机上运行命令，且没有沙箱保护。仅用于启用了人在回路的本地开发。

1. **创建一个集成文件** 在 `agent/integrations/my_provider.py` 处，使用一个与该签名匹配的工厂函数：

```
def create_my_provider_sandbox(sandbox_id: str | None = None):
    """Create or reconnect to a sandbox.

    Args:
        sandbox_id: Optional existing sandbox ID to reconnect to.
            If None, creates a new sandbox.

    Returns:
        An object implementing SandboxBackendProtocol.
    """
    ...
```

1. **将其注册** in `agent/utils/sandbox.py` by importing your factory and adding it to `SANDBOX_FACTORIES`:

```
from agent.integrations.my_provider import create_my_provider_sandbox

SANDBOX_FACTORIES = {
    ...
    "my_provider": create_my_provider_sandbox,
}
```

工厂必须从 `deepagents` 返回一个实现 `SandboxBackendProtocol` 的对象。请参考现有的集成文件。

##### 构建自定义沙箱提供商

如果没有内置的提供程序适配，你可以自行构建。该代理接受任何实现了来自 deepagents 的 `SandboxBackendProtocol` 的后端。该协议要求：

- **文件操作** ： `ls_info()` 、 `read()` 、 `write()` 、 `edit()` 、 `glob_info()` 、 `grep_raw()`
- **Shell execution**: `execute(command, timeout=None) -> ExecuteResponse`
- **标识** : `id` 属性返回一个唯一的沙箱标识符

最简便的方法是扩展 `BaseSandbox` （来自 `deepagents.backends.sandbox` ）—— 它通过委托给 `execute()` 来实现所有文件操作，因此您只需要实现 shell 执行层：

```
from deepagents.backends.sandbox import BaseSandbox
from deepagents.backends.protocol import ExecuteResponse

class MySandbox(BaseSandbox):
    def __init__(self, connection):
        self._conn = connection

    @property
    def id(self) -> str:
        return self._conn.id

    def execute(self, command: str, *, timeout: int | None = None) -> ExecuteResponse:
        result = self._conn.run(command, timeout=timeout or 300)
        return ExecuteResponse(
            output=result.stdout + result.stderr,
            exit_code=result.exit_code,
            truncated=False,
        )
```

See `agent/integrations/langsmith.py` (`LangSmithBackend` 类) for a full reference implementation.

#### 2\. Model

该模型在 `agent/server.py` 文件中的 `get_agent()` 函数中进行配置。默认情况下，它使用 `anthropic:claude-opus-4-6` ，但你可以通过 `LLM_MODEL_ID` 环境变量覆盖它：

```
# Set the model via environment variable (uses provider:model format)
LLM_MODEL_ID="anthropic:claude-sonnet-4-6"
```

如果 `LLM_MODEL_ID` 未设置，将使用默认模型 (`anthropic:claude-opus-4-6`)。

##### Switching models

Use the `provider:model` format:

The `make_model()` helper in `agent/utils/model.py` wraps `langchain.chat_models.init_chat_model`. For OpenAI models, it automatically enables the Responses API. For full control, pass a pre-configured model instance directly:

```
from langchain_anthropic import ChatAnthropic

model = ChatAnthropic(model_name="claude-sonnet-4-6", temperature=0, max_tokens=16_000)

return create_deep_agent(
    model=model,
    ...
)
```

##### 根据不同上下文使用不同模型

您可以根据任务复杂度、仓库或触发源路由到不同的模型：

```
async def get_agent(config: RunnableConfig) -> Pregel:
    source = config["configurable"].get("source")
    
    if source == "slack":
        # Faster model for Slack Q&A
        model = make_model("anthropic:claude-sonnet-4-6", temperature=0, max_tokens=16_000)
    else:
        # Full model for code changes from Linear
        model = make_model("anthropic:claude-opus-4-6", temperature=0, max_tokens=20_000)
    
    return create_deep_agent(model=model, ...)
```

#### 3\. Tools

Open SWE 在内置的 Deep Agents 工具（文件操作、Shell 执行、子代理、待办事项）基础上，提供了五个自定义工具：

Tool File Purpose

`commit_and_open_pr` `agent/tools/commit_and_open_pr.py` Git commit + GitHub draft PR

`fetch_url` `agent/tools/fetch_url.py` Fetch web pages as markdown

`http_request` `agent/tools/http_request.py` HTTP API calls

`linear_comment` `agent/tools/linear_comment.py` 在 Linear 工单上发表评论

`slack_thread_reply` `agent/tools/slack_thread_reply.py` Reply in Slack threads

在 `agent/tools/` 中创建一个新文件，定义一个函数，并将其添加到工具列表中。

**示例——添加一个 Datadog 搜索工具：**

```
# agent/tools/datadog_search.py
import requests
from typing import Any

def datadog_search(query: str, time_range: str = "1h") -> dict[str, Any]:
    """Search Datadog logs for debugging context.

    Args:
        query: Datadog log query string
        time_range: Time range to search (e.g. "1h", "24h", "7d")

    Returns:
        Dictionary with matching log entries
    """
    # Your Datadog API integration here
    ...
```

Then register it in `agent/server.py`:

```
from .tools import commit_and_open_pr, fetch_url, http_request, linear_comment, slack_thread_reply
from .tools.datadog_search import datadog_search

return create_deep_agent(
    ...
    tools=[
        http_request, fetch_url, commit_and_open_pr,
        linear_comment, slack_thread_reply,
        datadog_search,  # new tool
    ],
    ...
)
```

代理将自动查看工具名称、文档字符串和参数类型 — 文档字符串用作工具描述，因此请清晰地编写它。

##### Removing tools

如果您只使用 Linear（而非 Slack），请从工具列表中移除 `slack_thread_reply` ，反之亦然。如果您不需要网页抓取，请移除 `fetch_url` 。核心工作流中唯一必不可少的工具是 `commit_and_open_pr` 。

##### Conditional tools

你可以根据触发源调整工具集：

```
base_tools = [http_request, fetch_url, commit_and_open_pr]
source = config["configurable"].get("source")

if source == "linear":
    tools = [*base_tools, linear_comment]
elif source == "slack":
    tools = [*base_tools, slack_thread_reply]
else:
    tools = [*base_tools, linear_comment, slack_thread_reply]

return create_deep_agent(tools=tools, ...)
```

#### 4\. Triggers

Open SWE 支持三种调用入口：Linear、Slack 和 GitHub。每种调用入口都作为 webhook 端点在 `agent/webapp.py` 中实现。您可以独立地添加、删除或修改触发器。

如果您不使用 Linear，只需不配置 Linear 的 webhook 并移除环境变量即可。Slack 也是如此。webhook 端点仍然存在，但不会接收事件。

要完全移除触发器的代码，请从 `agent/webapp.py` 中删除相应的端点：

- **Linear**: `linear_webhook()` and `process_linear_issue()`
- **Slack**: `slack_webhook()` and `process_slack_mention()`

##### Default repository

当未指定仓库时，设置所有触发器（Slack、Linear、GitHub）中使用的默认 GitHub 组织和仓库：

```
DEFAULT_REPO_OWNER="my-org"      # Default GitHub org (used everywhere)
DEFAULT_REPO_NAME="my-repo"      # Default GitHub repo (used everywhere)
```

这些在以下情况中用作备用方案：

- 一条 Slack 消息未指定仓库（且不存在线程元数据）
- 一个 Linear 问题的团队/项目不在 `LINEAR_TEAM_TO_REPO` 映射中
- 用户编写 `repo:name` 时没有组织前缀——该组织默认为 `DEFAULT_REPO_OWNER`

##### 从消息中提取代码仓库

Slack 和 Linear 都支持在消息或评论文本中直接指定目标仓库。agent/utils/repo.py 文件中的共享工具函数 `extract_repo_from_text()` 负责解析这些格式：

- `repo:owner/name` — 明确的组织和仓库
- `仓库所有者/名称` — 空间语法（相同结果）
- `repo:name` — repo name only; the org defaults to `DEFAULT_REPO_OWNER`  
  `repo:名称` — 仅 repo 名称；组织默认使用 `DEFAULT_REPO_OWNER`
- `https://github.com/owner/name` — GitHub 网址

The `LINEAR_TEAM_TO_REPO` 字典 in `agent/utils/linear_team_repo_map.py` maps Linear teams and projects to GitHub repos:

```

    "Engineering": {
        "projects": {
            "backend": {"owner": "my-org", "name": "backend"},
            "frontend": {"owner": "my-org", "name": "frontend"},
        },
        "default": {"owner": "my-org", "name": "monorepo"},
    },
}
```

Users can also override the team/project mapping on a per-comment basis by including `repo:owner/name` in their `@openswe` comment. This takes priority over the mapping — the mapping is used as a fallback when no repo is specified in the comment. If the team/project isn't found in the mapping either, `DEFAULT_REPO_OWNER` / `DEFAULT_REPO_NAME` is used.  
用户还可以按每条评论覆盖团队/项目映射，方法是在其@openswe 评论中包含 `仓库:所有者/名称` 。这优先于映射——当评论中未指定仓库时，该映射用作后备。如果团队/项目也未在映射中找到，则使用 `DEFAULT_REPO_OWNER` / `DEFAULT_REPO_NAME` 。

Slack 使用 `DEFAULT_REPO_OWNER` 和 `DEFAULT_REPO_NAME` 作为回退选项，当消息中未指定仓库时。

#### Prerequisites

- **Python 3.11 – 3.13** (3.14 由于依赖约束尚未支持)
- [uv](https://docs.astral.sh/uv/) package manager
- [LangGraph CLI](https://langchain-ai.github.io/langgraph/cloud/reference/cli/)
- [ngrok](https://ngrok.com/) （用于本地开发 — 将 webhook 端点暴露到互联网）

uv sync --all-extras

在后续配置 webhook 时您需要用到 ngrok URL，因此请先启动它。

```
ngrok http 2024 --url https://some-url-you-configure.ngrok.dev
```

你不需要传递 `--url` 标志，不过这样做每次启动服务器都会使用相同的子域名。如果不这样做，在本地开发时每次重启服务器，你都需要更新 GitHub、Slack 和 Linear 中的 webhook URL。

复制你设置的 HTTPS URL，或者如果你没有传递 `--url` 参数，那么就使用 ngrok 提供的那个 URL。你需要在步骤 3 和步骤 5 中将其粘贴到 webhook 设置中。

Open SWE uses [LangSmith](https://smith.langchain.com/) for:

- **追踪** ：所有代理运行都被记录，用于调试和可观测性
- **沙箱** ：每个任务在一个隔离的 LangSmith 云沙箱中运行

1. 创建一个 [LangSmith 账户](https://smith.langchain.com/) 如果您还没有的话
2. 前往 **设置 → API 密钥 → 创建 API 密钥**
3. Save it as `LANGSMITH_API_KEY_PROD`
4. 获取你的 **租户 ID** ：访问 LangSmith，登录，然后复制 URL 中的 UUID。示例：如果你的 URL 是 `https://smith.langchain.com/o/72184268-01ea-4d29-98cc-6cfcf0f2abb0/agents/chat` -&gt;，那么租户 ID 将是 `72184268-01ea-4d29-98cc-6cfcf0f2abb0` 。将其保存为 `LANGSMITH_TENANT_ID_PROD` 。
5. 获取你的 **项目 ID** ：在 LangSmith 中打开你的追踪项目，然后点击左上角紧邻项目名称的 **ID** 按钮。将其保存为 `LANGSMITH_TRACING_PROJECT_ID_PROD`

这允许每个用户使用自己的 GitHub 账户进行身份验证。没有它，所有操作将使用 GitHub App 的安装令牌（一个共享的机器人身份）。

**What this affects:**

- **按用户的 OAuth** ：PR 和提交显示触发用户的身份；每个用户的 GitHub 权限都被尊重
- **Without it (bot-token-only mode)**: all PRs and commits appear as the GitHub App bot; the app's installation-level permissions are used for everything 没有它（仅机器人令牌模式）：所有拉取请求和提交都以 GitHub App 机器人的身份出现；该应用的安装级权限被用于所有操作

To set up per-user OAuth:

1. 在 LangSmith 中，进入 **设置 → OAuth 提供商 → 添加提供商**
2. 设置 **Provider ID** 为与步骤 3a 中选择的相同字符串（例如 `github-oauth-provider` ）
3. 输入来自你的 GitHub 应用的 **客户端 ID** 和 **客户端密钥** （可在 GitHub 应用设置页面的 **OAuth 凭证** 下找到）
4. 保存。您将在环境变量中引用此提供程序 ID 作为 `GITHUB_OAUTH_PROVIDER_ID` 。

#### Open SWE 综合总结与解读

##### 一句话概括

**Open SWE 是一个面向企业内部研发场景的开源“编码代理框架”**：它把大模型、远程沙箱、Slack/Linear/GitHub 触发、工具调用、子代理协作和自动 PR 流程组合起来，让组织可以搭建一个真正能“接活、改代码、提 PR、持续收消息”的内部软件工程代理。

---

##### 综合总结

##### 1. 它是什么

Open SWE 是 `langchain-ai/open-swe` 提供的一个开源异步编码代理框架，核心目标不是做一个“聊天机器人”，而是做一个能嵌入团队真实研发流程的**工程执行代理**。

它借鉴了 Stripe、Ramp、Coinbase 等公司内部编码代理的共同设计思路，并以开源方式复现这种架构。它建立在 **LangGraph + Deep Agents** 之上，支持：

- 在**隔离的云沙箱**中执行每个任务
- 从 **Slack、Linear、GitHub** 发起任务
- 使用精简但高价值的工具集完成代码修改、网页/API 获取、评论回复、提交与开 PR
- 通过 **子代理** 并行拆解任务
- 通过 **中间件** 为代理加入确定性的控制逻辑
- 根据组织需求定制模型、沙箱、工具、触发器和提示词

换句话说，它不是一个单一产品，而更像一套“**企业编码代理的参考实现和底座**”。

---

##### 2. 它的核心架构

从三个内容综合来看，Open SWE 的设计可以概括为 6 个核心层：

###### 2.1 代理内核：Deep Agents + LangGraph

Open SWE 并没有从零手写整个代理系统，而是以 `create_deep_agent(...)` 为装配核心，把以下组件组合起来：

- 模型
- 系统提示词
- 工具集
- 沙箱后端
- 中间件链路

这意味着它的重点不是“重新发明代理框架”，而是**在成熟代理框架之上做组织级工程化封装**。

###### 2.2 执行环境：隔离沙箱

每个任务运行在独立 Linux 云沙箱中，具备完整 Shell 权限，但影响范围被隔离控制住。特点包括：

- 每个任务一个独立沙箱
- 同一线程后续消息可复用持久沙箱
- 沙箱断开可自动重建
- 多个任务可并行运行，互不阻塞
- 可切换多种沙箱提供商：`langsmith`、`daytona`、`runloop`、`modal`，也可自定义
- 支持 `local` 本地模式，但官方明确警告：**无隔离，仅适合开发测试**

这一层是 Open SWE 和“普通 AI 编程助手”差异最大的地方之一。

###### 2.3 工具层：少而精

Open SWE 强调“**工具精选比工具堆积更重要**”。默认自定义工具大致是五类：

- `commit_and_open_pr`：提交代码并创建 GitHub Draft PR
- `fetch_url`：抓取网页并转为 markdown
- `http_request`：发起 API 请求
- `linear_comment`：回写 Linear 评论
- `slack_thread_reply`：回复 Slack 线程

同时还继承 Deep Agents 的基础工具：

- 文件读写编辑
- Shell 执行
- `ls/glob/grep`
- todo 管理
- `task` 子代理生成

核心思想不是“什么都给它”，而是给**最能形成闭环**的那组能力。

###### 2.4 上下文层：仓库规则 + 工单/消息上下文

Open SWE 默认会从两个地方获取关键上下文：

- `AGENTS.md`：仓库根目录的规范文件，用于注入编码规范、架构约束、测试要求
- 触发源上下文：完整的 Linear issue、Slack thread、GitHub 评论上下文

这使代理在开始工作前就能拿到“任务背景 + 仓库规则”，而不是全靠实时搜索。

###### 2.5 编排层：子代理 + 中间件

Open SWE 的编排机制有两套：

**子代理**
- 主代理可以把独立子任务拆给多个子代理
- 每个子代理有自己的待办事项和执行上下文
- 适合并行处理多个子问题

**中间件**
- 在代理循环前后插入确定性逻辑
- 内置中间件包括：
  - `ToolErrorMiddleware`：处理工具错误
  - `check_message_queue_before_model`：在模型调用前注入新到达的后续消息
  - `ensure_no_empty_msg`：防止空消息进入模型
  - `open_pr_if_needed`：如果代理没开 PR，则补开 PR

这说明 Open SWE 不是完全放任 LLM 自由发挥，而是让**智能体能力 + 工程控制**结合。

###### 2.6 调用入口：Slack / Linear / GitHub

Open SWE 支持三类生产级入口：

- **Slack**：在线程里 `@openswe`
- **Linear**：在 issue 评论里 `@openswe`
- **GitHub**：在 issue/PR 评论中 `@openswe`

特点包括：

- 每次触发生成确定性 thread ID
- 同一任务的后续消息会回到同一个代理上下文
- 任务执行中途还可以继续给代理发消息
- 代理可以回写评论、回复线程、继续修改同一分支并推送修复

这使它不是“一次性问答”，而是更接近**持续对话式任务执行**。

##### 3. 它最强的地方：可定制

`CUSTOMIZATION.md` 表明 Open SWE 的重要设计目标是：**默认能用，但更重要的是易于按组织需求改造。**

可定制范围主要包括：

###### 3.1 沙箱可替换
你可以：
- 切换内置沙箱提供商
- 自定义 Docker 镜像
- 自己实现 `SandboxBackendProtocol`

###### 3.3 工具可增删

###### 3.4 触发器可扩展

- 定义新 webhook + 新 process 函数 + 可选回写工具

###### 3.5 提示词可模块化修改
系统提示由多个 section 组成，可分别调整：
- 工作环境约束
- 执行流程
- 编码规范
- commit/PR 规范
- code review 指南
- 沟通风格

###### 3.6 中间件可扩展
你可以在代理完成后插入：
- CI 检查
- 安全扫描
- 可视化验证
- 审核门禁
- 自动通知

这让 Open SWE 适合作为“**组织内部编码代理平台**”的起点，而不是只能照搬官方 demo。

##### 深入浅出解读

##### 1. Open SWE 本质上不是“聊天 AI”，而是“研发流程机器人”

很多 AI 工具停留在：
- 你提问
- 它回答
- 最多给你一段代码

而 Open SWE 想解决的是更完整的工程动作链：

1. 接收任务
2. 拿到上下文
3. 在隔离环境里改代码
4. 自己运行命令、检查、测试
5. 提交变更
6. 开 PR
7. 在 Slack/Linear/GitHub 回报进度
8. 收到追问后继续在同一上下文里工作

这意味着它对标的是“**能真正接软件开发任务的执行代理**”，不是“代码补全器”。

---

##### 2. 为什么它特别强调“沙箱”？

因为编码代理一旦真的能执行 Shell、写文件、提 PR，就已经不是“建议工具”了，而是“行动工具”。

这时最核心的问题就不是“它会不会写代码”，而是：

- 出错会不会污染你的机器？
- 会不会误删文件？
- 会不会拿到过多权限？
- 多个任务会不会互相干扰？

Open SWE 的回答是：**先隔离，再放权。**

也就是说：
- 在沙箱里给它较大的操作权限
- 但把风险锁在沙箱边界内
- 不直接碰生产环境
- 不默认在你本机胡乱执行

这非常符合企业工程实践。相比“在开发者本地直接让 AI 随便跑命令”，这种模式更接近可控的自动化执行。

---

##### 3. 为什么说它借鉴了大厂内部代理的共识？

从内容 1 的对比表能看出，虽然 Stripe、Ramp、Coinbase 具体实现不同，但他们的共识很一致：

- 有隔离执行环境
- 有企业上下文接入
- 有明确工具集
- 有多入口触发
- 有一定确定性控制
- 有自动产出 PR 或类似结果

Open SWE 的价值在于：**把这些共识抽象成一套开源骨架**。

所以它不是一个“天才新发明”，而是把大厂内部成熟模式“产品化、开源化、可复用化”。

---

##### 4. 它为什么要把“工具数量少”当成优点？

很多人会直觉觉得：工具越多越强。

但 Open SWE 反过来强调：
> 不是工具越多越好，而是工具要足够关键、足够稳定、足够闭环。

例如默认工具虽然不多，但已经覆盖了最关键的工作流：

- 找资料：`fetch_url` / `http_request`
- 改代码：文件工具 + Shell
- 沟通回写：Slack / Linear comment
- 交付结果：`commit_and_open_pr`

这是一种很工程化的思路：**少即是稳，少即是可控**。  
尤其在企业内部，如果代理接入几十上百个系统，复杂度、权限面和失败面都会迅速上升。

---

##### 5. 它最“像企业系统”的地方，其实是中间件

很多 AI 项目把一切都交给模型决定，但 Open SWE 里有明显的“确定性补位”设计。

例如：
- 新消息到了，不依赖模型自己想起来检查，`check_message_queue_before_model` 负责注入
- 代理忘了开 PR，不寄希望于提示词，`open_pr_if_needed` 负责兜底
- 工具报错，不是让模型自由崩溃，`ToolErrorMiddleware` 负责处理

这说明它不是“纯 LLM 驱动”，而是：
**模型负责智能决策，系统负责流程护栏。**

这是代理系统真正走向可靠性的关键一步。

---

##### 6. `AGENTS.md` 的意义非常大

看起来只是一个文件，但其实这代表一种很重要的方法：

- 不把所有规则硬编码到平台里
- 让每个仓库自己声明“这个项目的开发规矩”

这样一来，不同仓库可以自己告诉代理：
- 测试要怎么跑
- 提交规范是什么
- 哪些目录不能动
- 哪些架构约束必须遵守
- 哪些代码风格必须保持一致

这让 Open SWE 从“通用代理”变成“**知道本仓库规矩的代理**”。

对于组织来说，这比单纯换模型更重要，因为很多工程错误并不是“不会写代码”，而是“不懂项目规范”。

---

##### 7. 它为什么适合组织内部，而不只是个人玩具？

因为它解决的不是“个人效率点工具”，而是团队协作中的三个核心问题：

###### 7.1 统一入口
大家都在 Slack、Linear、GitHub 中触发，不需要每个人都学一套新工具。

###### 7.2 权限与身份
通过 GitHub App 和可选 OAuth，可以决定：
- 是用机器人身份执行
- 还是按触发用户自己的 GitHub 权限执行

这符合组织里的审计、权限继承和责任归属要求。

###### 7.3 结果回到现有流程
代理最后不是“在某个聊天窗口说改好了”，而是：
- 直接开 PR
- 把结果贴回线程/工单
- 在原工作流里继续互动

这意味着团队不用为了 AI 改造整个协作方式。

---

##### 8. 这套系统最适合哪些场景？

从内容综合判断，Open SWE 特别适合以下场景：

- 内部研发团队想搭建自己的编码代理
- 希望代理能在工单系统和沟通平台里直接接任务
- 希望代码修改发生在隔离环境，而不是开发者本机
- 希望代理自动提交、开 PR、回写状态
- 希望为不同仓库、不同团队定制规则和流程
- 希望逐步扩展内部工具，如日志、监控、CI、代码扫描

它尤其适合“**工程化要求高、流程明确、系统较多的团队**”。

---

##### 9. 它的门槛和现实挑战也很明显

虽然很强，但它不是“零成本即用”。

主要门槛包括：

###### 9.1 配置复杂
需要打通：
- GitHub App
- LangSmith
- webhook
- Slack / Linear
- 环境变量
- 默认仓库和团队映射

这比单机 AI 工具复杂得多。

###### 9.2 运维成本
需要考虑：
- 沙箱额度
- webhook 稳定性
- OAuth 配置
- 权限边界
- 失败重试
- 模型成本

###### 9.3 企业适配工作量
真正落地时，通常还要做：
- 自定义工具
- 自定义提示词
- 自定义中间件
- CI/安全/审核接入
- 仓库规范文件建设

因此，Open SWE 更像一个“**强底座**”，而不是“开箱即适配所有组织”的终极产品。

---

##### 10. 可以怎样理解它的定位？

如果用一句更直白的话说：

**Open SWE 不是替你写几段代码的 AI，而是帮你搭建“企业版 Devin / 内部工程代理系统”的开源骨架。**

它最值得关注的地方不是某个单点功能，而是把以下几件事整合到了一起：

- 代理智能
- 工程执行
- 安全隔离
- 协作平台接入
- 组织级定制能力
- PR 交付闭环

这也是它相较于普通代码助手最有价值的地方。

---

##### 结构化提炼

##### 核心价值
- 用开源方式复现企业内部编码代理架构
- 让代理真正进入 Slack / Linear / GitHub 工作流
- 用隔离沙箱承接真实代码执行任务
- 通过工具、子代理、中间件形成可控闭环
- 可深度定制，适合作为组织内部平台底座

##### 核心能力
- 云沙箱执行
- 多入口触发
- 自动提交与 PR
- 子代理并行拆分
- 仓库规范注入
- 中间件护栏
- 可插拔模型与沙箱

##### 核心优势
- 架构成熟，参考大厂内部模式
- 工程闭环完整，不止于回答
- 定制度高，适配组织流程
- 风险控制思路清晰，强调隔离与权限边界

##### 核心限制
- 部署和配置门槛较高
- 需要较强的平台工程能力
- 企业落地仍需大量定制
- 真正可用程度依赖权限、工具和规范建设

---

##### 结论

Open SWE 最值得用一句话评价的是：

**它把“AI 会写代码”升级成了“AI 能在企业研发流程里安全、持续、可定制地完成编码任务”。**

如果你只是想要一个个人代码助手，它可能显得偏重。  
但如果你的目标是为团队或组织搭建一个真正接入工单、沟通、仓库和 PR 流程的内部编码代理，Open SWE 提供的是一套非常有代表性的开源实现路径。
