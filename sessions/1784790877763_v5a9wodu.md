How teams build, test, deploy, and improve production agents  
Everyone wants to ship agents, but the best teams are no longer treating agents as one-off demos or isolated projects. They are building a repeatable Agent Development Lifecycle: a system for building, testing, deploying, monitoring, and continuously improving agents over time.

Join Harrison Chase, CEO and co-founder for LangChain for a walkthrough of the Agent Development Lifecycle and why it matters for teams moving agents into production. We’ll cover how leading teams are shifting from “build an agent” to an ongoing improvement loop powered by traces, evals, experiments, feedback, and production monitoring. You’ll learn how teams can catch failures earlier, turn production behavior into stronger evals, and improve agents without relying on guesswork.

We’ll also show how teams identify recurring failure patterns from production traces, diagnose root causes, prioritize fixes, and strengthen eval coverage over time. Finally, we’ll touch on what it takes to run long-horizon agents with durable execution, context, tools, sandboxes, and human-in-the-loop workflows.

## 结构化（1）

### 2026-07-23 07:13:20

这场分享的核心观点是：**生产级智能体（Agent）不是一次性 Demo，而是需要“构建—测试—部署—监控—改进”的持续循环，并由治理体系贯穿始终。**真正的难点不是让 Agent 偶尔完成任务，而是让它在大规模真实使用中保持可靠，并通过轨迹、评估和反馈不断进化。

##### 一、为什么需要 Agent 开发生命周期

- 过去一年，越来越多团队已经能发布 Agent；领先团队的共同点是：**尽早上线、快速迭代，并以系统化方式改进。**
- 本地演示或一次性成功并不难，难的是让 Agent 面向约 **100 名乃至更多用户**时仍能稳定运行。
- Agent 开发生命周期包含四个主要阶段：
  1. **Build：构建**
  2. **Test：测试**
  3. **Deploy：部署**
  4. **Monitor：监控**
- **Govern：治理**不是独立的一步，而是贯穿整个生命周期。
- 核心闭环是：  
  **观察行为 → 找到失败 → 分析原因 → 修改 Agent → 用评估验证 → 重新部署 → 继续监控。**

---

##### 二、构建：选择合适的抽象层级

###### 1. Framework：开发框架

框架主要提供模型输入输出、工具、提示词、检索等标准化抽象，例如：

- LangChain
- LlamaIndex
- CrewAI
- Google ADK
- OpenAI Agents SDK
- AWS Swarm

**优点：**

- 降低开发门槛；
- 统一团队技术结构；
- 方便开发者跨项目协作和快速上手。

**缺点：**

- 可能隐藏底层行为，导致性能和成本问题不透明。
- 例如，早期 LangChain 的某个 Chain 会在底层调用 LLM **5 次**，用户因此发现它比直接调用 OpenAI 慢约 **5 倍**，但框架没有清晰暴露原因。

因此，框架应尽量轻量，让开发者清楚知道底层发生了什么。

###### 2. Runtime：运行时

运行时关注 Agent 执行过程中的通用能力，例如：

- 状态管理；
- 持久化执行；
- 失败后续跑；
- 人工介入；
- 长短期记忆。

代表工具包括 LangGraph、Temporal 等。

###### 3. Harness：Agent 执行套件

Harness 比一般框架更高层，许多编程 Agent 本质上就是 Harness。其常见能力包括：

- 文件系统访问；
- 上下文管理；
- 摘要与压缩；
- 人机协作界面；
- 子 Agent；
- Skills 技能体系。

代表包括 Deep Agents、Claude Agents SDK，以及 CodeX、OpenCode、Pi 等偏编程场景的套件。

###### 4. 无代码构建正在成为可能

Agent 的定义越来越不像传统代码：

- 提示词可以保存在 `agents.md` 等 Markdown 文件中；
- 工具可通过 `mcp.json` 连接 MCP Server；
- Skills 也常由 Markdown 和少量脚本组成。

因此，未来可能只通过文件、配置和自然语言就能构建 Agent。Vercel 的 Eve、LangSmith Fleet 等都体现了这一方向。

---

##### 三、测试：用数据和指标衡量 Agent

测试的本质是：**让 Agent 运行一组输入任务，对结果评分，并根据分数判断其质量和是否可以上线。**

###### 1. 两类主要测试目标

- **回归测试**：确保原来正确的功能没有变坏，通常希望接近 **100% 通过率**。
- **基准爬坡**：例如当前通过率为 **40%**，通过持续优化提升到 **90%**。

不存在统一的“行业标准通过率”，合理目标取决于具体应用和风险要求。

###### 2. 构建测试数据集

测试输入可以来自：

- 预期的用户任务；
- 已知边界情况；
- 生产环境真实轨迹；
- 团队内部试用；
- 合成数据。

一个数据集可能包含 **50 个不同输入**。除了输入，还需要定义：

- 标准答案；
- 或用于判断质量的评价标准。

###### 3. 根据任务类型选择评分方法

**答案明确的任务：**

- 例如分类任务，可以直接判断结果应为 `true` 还是 `false`，并与标准答案比较。

**开放式任务：**

- 通常没有唯一标准答案，需要按照规则或测试程序判断。
- 例如编程 Agent 基准 **Terminal Bench 2** 不直接比较修改了哪些文件，而是运行单元测试，判断最终代码是否真正可用。

常见指标包括：

- 正确性；
- 是否满足指定标准；
- 是否符合政策与合规要求；
- 任务是否成功完成。

###### 4. Agent 测试比普通 LLM 测试更复杂

普通 LLM 测试通常只需循环调用模型；Agent 则可能：

- 单次运行 **15～30 分钟**；
- 操作外部环境；
- 修改状态；
- 生成文件等产物。

因此，每个测试任务最好运行在独立沙箱中。Terminal Bench 2 使用开源框架 **Harbor**，为每个任务建立独立环境，适合测试长时间、带状态的 Agent。

###### 5. 测试必须贴合具体应用

数据集、指标和成功标准往往是具体业务的产品问题，不能完全依赖通用工具。平台可以提供起点，但团队仍需根据业务自行定义“什么叫表现好”。

---

##### 四、部署：让长时间运行的 Agent 稳定、安全

Agent 部署与普通软件部署类似，但更强调以下能力。

###### 1. 持久化与可恢复执行

如果 Agent 执行到一半失败，理想状态是：

- 从失败步骤继续；
- 而不是重新运行整个任务。

同时需要管理：

- 当前会话内的短期记忆；
- 跨会话保存的长期记忆；
- 状态持久化。

###### 2. 流式输出

除了逐 Token 输出，还可能需要展示：

- 工具调用过程；
- 中间状态；
- 推理或执行进度。

这能改善长任务中的用户体验，让用户知道 Agent 正在做什么。

###### 3. Human-in-the-loop

本地暂停 Agent 很容易，但生产环境中需要支持：

- 暂停执行；
- 等待人工审批；
- 收到反馈后继续运行。

特别是高风险工具调用，例如发邮件、修改数据库或执行交易，应先由人批准。

###### 4. 沙箱

如果 Agent 只执行预先编写的代码，可以将其视为普通工具调用；如果 Agent 会自己编写并执行代码，这些代码属于**不可信代码**，必须放在隔离沙箱中运行。

###### 5. 虚拟文件系统

Agent 很擅长使用文件系统，因为模型已经熟悉：

- `read`、`write`；
- `edit`；
- `glob`、`grep`；
- `ls`。

但为每个 Agent 启动完整文件系统成本较高。更可扩展的做法是：

- 将数据实际保存在数据库、S3、Box、Notion 等位置；
- 对 Agent 暴露成文件系统接口。

这样既保留 Agent 熟悉的交互方式，又方便集中存储和管理上下文、提示词、Skills 与指令。

---

##### 五、监控：通过轨迹看清 Agent 做了什么

###### 1. Tracing 是最基本能力

追踪最好在正式上线前就配置好，需要记录：

- Agent 执行了哪些步骤；
- 每一步的输入与输出；
- 调用了哪些工具和子 Agent；
- LLM 实际接收了什么上下文；
- LLM 返回了什么结果。

Agent 出错往往不是模型“无缘无故犯错”，而是因为缺少或拿错了上下文。因此，查看模型实际得到的上下文是调试的关键。

###### 2. 从海量轨迹中找到值得关注的问题

生产环境可能产生数千、数百万甚至更多轨迹，团队不可能逐条查看，需要结合：

- 用户点赞或点踩；
- 用户文字反馈；
- 在线评估；
- 延迟、首 Token 时间等运行指标。

###### 3. 在线评估

在线评估是在任务完成后，对真实生产轨迹自动评分，因此：

- **不会拖慢当前 Agent 的执行；**
- 但如果对所有轨迹调用大模型，可能带来较高成本。

一种重要指标是“**感知错误**”：从对话中识别用户是否认为 Agent 出错。例如：

- “你做错了”；
- “你做了 X，但应该做 Y”；
- 用户把带报错信息的代码重新粘贴回来。

LangChain 为此训练了一个小型语言模型，以较低成本检测此类信号。

###### 4. 仪表盘与趋势分析

仪表盘可以汇总展示：

- 延迟；
- 首 Token 时间；
- 成本；
- 用户反馈；
- 在线评估结果；
- 错误率和问题趋势。

还可通过聚类分析用户使用方式，观察主题或需求是否随时间发生漂移。

---

##### 六、治理：贯穿整个生命周期

Agent 越多，治理越重要，主要包括：

###### 1. 成本控制

团队不仅要管理自己构建的 Agent，也要管理内部使用的编程 Agent等工具。随着使用规模扩大，成本可能迅速失控，因此需要：

- 成本可见性；
- 用户或团队级预算；
- 模型和 Token 使用限制。

###### 2. 工具权限

需要明确：

- Agent 能使用哪些工具；
- 以谁的身份操作；
- 使用个人账号、同事账号还是服务账号；
- 哪些工具调用必须人工批准。

例如 Agent 操作 Notion 时，必须清楚它代表哪个用户，以及可以读取或修改哪些内容。

###### 3. 审计追踪

系统应记录：

- Agent 调用了什么工具；
- 何时调用；
- 代表谁执行；
- 修改了什么内容。

Tracing 与评估结果也会成为治理和合规证据。

###### 4. 共享与可发现性

治理还包括：

- Agent 和工具的统一发现；
- 上下文、提示词、Skills 的共享；
- 组织级规范和评估标准；
- 人工审批流程。

---

##### 七、如何在大型组织中规模化

构建单个 Agent 时可以边做边摸索，但多个团队同时开发时，需要中央平台或核心 AI 团队提供统一能力：

- 用共享框架统一开发方式，促进复用并降低上手成本；
- 建立共享评估框架，避免每个团队重复开发测试系统；
- 在保留业务专属数据集的同时，设置所有 Agent 必须通过的组织级指标；
- 统一提供部署、追踪、反馈和仪表盘；
- 集中管理权限、成本和审计。

演讲者强调：**构建 Agent 往往是最有趣、也最快的环节；真正困难且耗时的是长期运营、监控和改进。**

##### 九、从监控走向自动改进：LangSmith Engine

LangSmith Engine 尝试将人工优化 Agent 的流程自动化。它会：

1. 在后台分析生产轨迹；
2. 每 **6 小时**运行一次；
3. 将重复失败聚类成不同问题；
4. 为每个问题生成名称、说明及相关轨迹；
5. 建议修改代码或提示词；
6. 将失败案例加入测试数据集；
7. 创建在线评估，以持续监控同类问题。

但系统不会完全自动应用高风险修改。代码变更仍需要人点击接受，体现了“**Agent 先完成大部分工作，人类负责审核和批准**”的模式。

##### 十、问答中的重要实践建议

###### 1. 如何控制上下文和 Token 成本

Deep Agents 采用了多种策略：

- 如果工具返回 **60,000 Token**，不全部放进上下文，而是保存到文件；
- 只向 Agent 展示最后约 **1,000 Token**，需要更多内容时再读文件；
- 上下文达到阈值后自动摘要；
- 对已经写入文件的大段内容，从历史上下文中删除，必要时再读取。

同时要避免破坏提示词缓存：相同提示词前缀可命中缓存，从而降低成本并提高速度。

###### 2. 如何测试未知场景

可以让另一个 Agent 或 LLM 自动生成新测试任务。一个方法是：

- 生成两个语义相同、表达不同的问题；
- 让 Agent 分别回答；
- 如果结果差异很大，说明至少有一个答案存在问题。

LangChain 早期的 **LangFuzz** 就采用了类似思路。

###### 3. 如何测试有状态系统

如果 Agent 会修改 Jira、Linear 等外部系统，测试环境必须：

- 模拟真实状态；
- 隔离每次测试；
- 测试结束后恢复到干净初始状态。

否则前一次测试创建或修改的数据会污染后续结果。

###### 4. Agent 不应只是“带 RAG 的聊天机器人”

未来 Agent 的价值在于真正执行工作，但完全自主执行的可靠性门槛很高。更现实的路径是：

- Agent 先生成初稿或执行方案；
- 人类审核并批准；
- 对高风险动作保留人工控制。

此外，“环境式 Agent”值得关注：它们可以在后台持续运行，由事件自动触发，而不是等待用户进入聊天窗口提问。

###### 5. 自我改进 Agent 的一种组合

演讲者提出的实现方式是：

- **Deep Agents** 负责执行；
- **Context Hub** 保存记忆、上下文和文件；
- **LangSmith** 记录轨迹；
- **LangSmith Engine** 分析轨迹并更新记忆或建议修改。

这形成了一个初步闭环：

> 执行任务 → 记录行为 → 识别问题和应记住的信息 → 更新上下文与评估 → 下一次执行时使用新经验。

---

##### 总结

生产级 Agent 的关键不在于选择某个模型或快速做出原型，而在于建立一套可重复的工程体系。**轨迹是整个体系的中心，评估负责量化效果，生产反馈推动持续改进，治理和人工审批则确保 Agent 在规模化运行时安全、可控且成本合理。**

## 口播总结（1）

### 2026-08-03 01:16:57

#### Agent 开发生命周期：从做出一个演示，到稳定服务真实用户

这场分享的核心，是介绍一套适合生产环境的“智能体开发生命周期”。听完后，你可以了解：团队怎样构建、测试、部署、监控和治理智能体，以及怎样利用真实运行数据，让智能体持续变得更可靠。

这里说的“智能体”，不是只会聊天的机器人，而是能够理解任务、调用工具、读写文件、执行操作，并在必要时与人协作的人工智能系统。真正困难的地方，不是让它偶尔完成一次任务，而是让它在大规模使用时，持续表现稳定。

##### 一、先接受一个事实：智能体不是一次性项目

最重要的结论是，优秀团队不会把智能体当成做完就结束的演示项目，而是把它当成一个持续改进的系统。

通俗地说，智能体最难解决的问题，是“行为是否可靠”。在本地运行一次，或者做出一个在社交媒体上展示的演示，通常并不难。难的是把它交给大量真实用户之后，它仍然能正确理解上下文、合理调用工具，并且在出错时能够被发现和修复。

分享中提到，领先团队通常会尽早发布一个初始版本，然后快速迭代。但这种迭代不是凭感觉修改提示词，而是依靠运行记录、评测、实验、用户反馈和生产环境监控，形成一个持续循环。

这套生命周期主要包括五个环节：构建、测试、部署、监控，以及覆盖全部环节的治理。

接下来，先从构建开始。

##### 二、构建：先选择合适的开发层级

核心结论是，构建智能体时，团队首先要决定：需要多高层的工具，以及希望掌控多少底层细节。

最常见的是使用智能体框架。框架会把模型输入、模型输出、工具、提示词和检索等能力包装成统一接口。这样做的好处是容易上手，也便于不同项目之间复用经验。新成员从一个项目切换到另一个项目时，如果使用相似的抽象方式，也会更容易理解代码。

但框架也有代价。它可能把底层发生的事情隐藏起来，导致开发者不知道系统实际上做了什么。

分享中举了一个例子：有一条看起来很简单的调用链，实际上在后台调用了五次大语言模型。结果，用户发现它为什么比直接调用模型慢五倍，却一时找不到原因。这个例子说明，框架必须尽量轻量、透明，并且清楚说明每一步的行为。

除了框架，还有“运行时”。运行时更关注智能体怎样运行，比如状态管理、持久化执行，以及如何暂停后继续执行。所谓持久化执行，就是智能体运行到一半失败时，可以从失败的步骤继续，而不必从头再来。

再往上，是“智能体工作台”，也可以理解成更高层的运行和管理方案。它通常会提供上下文管理、摘要和压缩、子智能体、技能系统，以及人类介入等能力。很多编程智能体使用的就是这种较高层的工作台。

还有一种趋势，是尽量减少代码。智能体的核心组成，往往并不一定要全部写成程序。提示词可以写在普通文本或 Markdown 文件里；工具可以通过配置文件连接；技能也可以用 Markdown 文件描述，必要时再配合脚本执行。

因此，构建智能体有时更像是在组织一组文件、指令和工具，而不只是编写大量代码。

这一部分可以这样理解：框架适合快速搭建，运行时负责可靠执行，工作台提供更完整的智能体能力，而文件化和无代码方式，则让更多非开发人员也有机会参与构建。

##### 三、测试：不要只看“能不能回答”，还要定义“怎样才算做好”

接下来的核心结论是，智能体测试的本质，是把它放在一组真实或模拟任务中运行，再根据明确标准评分。

测试通常有两种用途。第一种是回归测试，也就是确保原来能做好的事情没有被新改动破坏。第二种是基准提升，也就是不断比较不同版本，看看性能能否持续提高。

测试首先需要输入。输入可以是预期任务，也可以是已知的边界情况。它们的来源包括真实运行记录、团队自己试用智能体时留下的记录，或者由模型自动生成的测试场景。

这些输入会组成数据集。比如，一个数据集可以包含五十个不同任务。然后，团队还需要规定输出应该是什么，或者至少规定应该满足哪些标准。

对于分类任务，标准往往很清楚。例如，结果应该是真还是假，直接和正确答案比较就可以。对于开放式任务，则不一定存在唯一答案，这时就要检查一组条件。

以编程智能体为例，Terminal Bench 2 是一个常用的编程智能体基准。它不是简单检查智能体改了哪些文件，而是让智能体完成任务之后，运行单元测试。单元测试通过，才说明结果大致正确。这就是“按标准判断”，而不只是比对一段固定答案。

测试结果可以包含正确性、是否满足特定条件、是否符合某些政策等指标。把输入、评分标准和运行结果组合起来，就形成一次实验。通过比较多次实验，团队可以发现性能倒退，也可以判断一个新版本是否准备上线。

不过，测试并没有统一答案。每个应用都需要自己思考：哪些任务最重要，什么结果算正确，哪些错误绝对不能接受。这些其实已经不只是技术问题，也是产品设计问题。

更复杂的智能体测试，还需要模拟真实环境。普通的大语言模型应用，可能只是循环调用模型，很快就能完成测试。但一个真正的智能体，可能连续运行十五分钟甚至三十分钟，还会读写文件、操作工具，并产生各种外部结果。

因此，测试这类智能体时，需要把每个任务放进独立的沙箱。沙箱就是一个隔离的运行环境，可以防止不同测试相互影响，也能避免智能体执行代码时影响真实系统。Harbor 就是一个用于运行这类长期、有状态评测的开源框架。

##### 四、部署：生产环境关注的，不只是把服务启动起来

部署智能体和部署普通软件有相似之处，但更需要关注运行过程中的状态和中断。

第一个关键点，是持久化执行。智能体可能已经完成了一半任务，却因为网络、工具或模型问题失败。好的运行时应该能记录进度，并支持从中断位置恢复。

第二个关键点，是记忆。智能体既需要保存当前对话或当前任务中的短期记忆，也可能需要保存跨任务、跨会话的长期记忆。系统必须明确这些信息放在哪里，以及什么时候读取和更新。

第三个关键点，是流式输出。用户可能希望实时看到模型生成的文字，但智能体返回的内容不只有文字，还可能包括思考过程、工具调用和中间状态。产品需要决定哪些内容展示给用户，以及怎样把它们呈现得清楚。

第四个关键点，是“人在回路中”。它的意思是，在关键操作前暂停智能体，等待人类批准。这个功能在本地演示时很容易实现，但在生产环境中，要考虑任务怎样暂停、怎样记录、怎样在几小时或几天后继续。

安全执行也是部署时的重点。很多智能体需要写代码、运行代码，尤其是编程智能体。如果运行的是预先定义好的工具，风险相对容易控制。但如果代码是智能体临时生成的，就属于不可信代码，必须在安全的沙箱中执行。

另外，文件系统对智能体非常重要。大语言模型通常很擅长使用文件系统，因为它们经过大量相关训练，知道怎样读、写、搜索和整理文件。但给每个智能体都创建一套完整文件系统，可能成本较高。

因此，可以使用“虚拟文件系统”。它的意思是，底层数据实际存放在数据库、对象存储，或者其他地方，但对智能体来说，看起来仍然像一个普通文件夹。智能体可以使用读取、写入、搜索、列出文件等操作，而不必知道数据真实存在哪里。

分享中提到，Box、Notion，甚至专门的上下文存储服务，都可以被包装成这种虚拟文件系统，用来保存提示词、技能和智能体指令。

##### 五、监控：先看清智能体做了什么，再谈如何改进

监控的核心结论是，生产环境中最基础、也最必须具备的能力，是完整记录智能体的运行轨迹。

这里的“轨迹”，就是一次运行中发生的全过程。它包括每一步的输入和输出、调用了哪些工具、是否调用了子智能体，以及模型最终看到了什么上下文、返回了什么结果。

为什么上下文特别重要？因为很多智能体出错，并不是模型本身完全不会做，而是它没有拿到正确的信息，或者拿到的信息组织得不好。只有看到模型实际接收的上下文，开发者才有机会判断问题究竟出在提示词、工具、记忆，还是信息检索上。

监控不能只停留在记录。生产环境可能每天产生数千，甚至数百万条轨迹。团队不可能逐条人工查看，所以还需要收集反馈和自动评分。

最直接的信号，是用户的点赞、点踩和文字反馈。如果用户说“你做错了”，或者明确指出“你做了 X，应该做 Y”，这都说明智能体可能出现了问题。编程场景中，如果用户把一段带错误的代码贴回来，也可能意味着他实际运行后发现了错误。

这类从对话中推断出来的错误，被称为“感知错误”。它不一定有标准答案，但可以通过用户话语中的线索来判断。分享中提到，团队还训练了一个小型语言模型，用来自动识别这类信号。

此外，还可以做“在线评测”。在线评测不是上线前准备一批固定题目，而是在智能体已经运行后，自动检查真实轨迹，并给它打分。因为真实场景通常没有标准答案，所以在线评测需要依靠一些判断标准，而不是简单比对正确答案。

最后，仪表盘会把延迟、首个 token，也就是模型开始输出第一个文字所需的时间，以及用户反馈和在线评测结果集中展示出来。这样，团队不仅知道智能体是否出错，还能看到错误是否变多、速度是否变慢，以及问题主要出现在哪些场景。

##### 六、治理：让智能体在可控的边界内行动

治理不是生命周期中的最后一步，而是包围整个生命周期的一层控制机制。

首先是成本控制。智能体会频繁调用模型和工具，尤其是编程智能体，成本可能快速上升。团队需要知道每个智能体、每个团队，甚至每次任务花了多少钱，并设置相应的限制。

其次是工具权限。智能体到底能调用哪些工具？它代表谁调用工具？比如，智能体访问 Notion 时，是代表当前用户，代表另一位同事，还是代表一个服务账号？这些身份和权限必须清楚，否则智能体可能在不该操作的范围内执行任务。

还需要保留审计记录。审计记录要能回答：智能体调用了什么工具，什么时候调用的，以及它代表谁发起了这次调用。

人类审批也属于治理的一部分。某些工具在执行前必须获得人类确认；工具和智能体还应该能够被发现、管理和共享。相关的上下文、技能和指令，也需要有统一的管理方式。

所以，治理会和追踪、评测、人类审批、权限控制等能力交织在一起，而不是单独存在。

##### 七、规模化：把个人经验变成组织能力

当团队只维护一个智能体时，很多问题可以边做边解决。但当一个大型组织里有许多团队、许多智能体时，就需要把这些做法标准化。

第一，统一的构建框架可以帮助不同团队采用相似方式开发，也方便人员在项目之间切换。

第二，共享的评测框架可以避免每个团队重复编写相同的基础测试。不同应用当然仍然需要自己的数据集和部分专属指标，但安全、质量和基础行为等方面，往往可以共享组织级标准。

第三，部署基础设施最好由中央平台团队或核心人工智能团队统一提供。因为部署、状态管理、安全和权限控制都很复杂，让每个业务团队从零开始，既浪费时间，也容易产生不一致的风险。

第四，追踪、反馈和仪表盘必须足够容易使用。构建智能体通常是最有趣、也相对最快的一部分。真正耗时的，是上线后长期运行、发现问题并持续维护。因此，组织要让每个团队都能方便地观察自己的智能体。

##### 八、真正的中心：用轨迹驱动持续改进

分享最后反复强调，运行轨迹是整个生命周期的中心。

构建之后，需要通过轨迹了解智能体实际做了什么；测试时，可以从轨迹中提取真实案例；监控时，需要依靠轨迹发现错误；治理时，也可以从轨迹确认工具调用和权限使用情况。

持续改进的过程，可以概括为四步：先运行智能体，再观察轨迹；发现问题后，分析根本原因；修改提示词、工具或代码；然后重新测试、上线，并继续观察。

为了解决人工分析大量轨迹的问题，分享中还介绍了一种自动改进机制。它会在后台定期分析轨迹，把相似的失败聚类成问题。这里的“聚类”，就是把表现相近的错误归到同一类。

这个系统每六小时运行一次。它会为每类问题创建一个条目，写出问题名称和描述，并附上所有受影响的运行记录。随后，它还可能提出代码修改、提示词修改，或者把新的案例加入评测数据集，并创建在线评测来持续监控。

不过，自动化并不意味着完全不需要人。系统可以自动提出修改，但最终仍然由人审核和批准。分享者认为，比较现实的方式是让智能体完成大量分析和准备工作，再把结果作为一份草稿交给人确认。

##### 九、一个自我改进智能体可能怎样工作

最后，可以把前面的内容组合起来，形成一个自我改进的闭环。

智能体先运行，并把所有过程记录成轨迹。之后，后台系统分析这些轨迹，判断哪些内容值得记住，哪些地方反复出错。它再把新的经验写入上下文存储。下一次运行时，智能体通过虚拟文件系统读取这些经验，从而减少重复犯错。

分享中给出的组合是：一个较高层的智能体工作台，用来运行智能体；一个上下文中心，用来保存记忆、技能和指令；再加上一个能够分析轨迹、发现问题并提出修改的后台引擎。

这并不意味着智能体已经可以完全自动进化。它仍然需要评测标准、权限边界和人类审批。但这种设计可以大幅降低人工逐条查看日志、反复修改和重新部署的负担。

##### 结尾：五个最值得记住的结论

最后，用五句话回顾整场分享。

第一，智能体开发不是一次性项目，而是构建、测试、部署、监控和治理组成的持续生命周期。

第二，真正的难点不是让智能体偶尔完成任务，而是让它在真实用户和复杂环境中稳定、可靠地工作。

第三，测试不能只看模型回答得像不像，还要根据具体任务定义输入、标准、数据集和评测环境。

第四，生产监控的基础是完整轨迹。只有知道智能体看到了什么、做了什么，团队才有可能定位错误并改进它。

第五，未来会有更多智能体参与测试、监控和优化，但最可靠的方式仍然是“智能体负责分析和提出建议，人类负责审核和批准”。

## 深度解读（1）

### 2026-09-18 00:21:54

#### 生产级 Agent 的分水岭：不是“能做事”，而是“能被持续纠正”

Harrison Chase 给出的“构建—测试—部署—监控—治理”生命周期并不新鲜，几乎是把 DevOps 搬到了 Agent 领域。真正值得保留的判断是：**Agent 的核心工程问题已经从调用模型，转向管理一种会在环境中行动、结果不完全确定的行为系统。**

这解释了为什么演示容易、规模化困难。一个 Agent 在本地成功一次，只说明模型在当时的上下文里走通了一条路径；上线后，它面对的是不同表达、不断变化的数据、外部工具权限、长时间任务和中途故障。错误也不再只是“答案不对”，还可能是拿错上下文、调用错工具、修改了不该修改的状态，或执行到一半无法恢复。

##### Trace 不是日志，而是改进系统的原料

文章最有解释力的主线，是把执行轨迹放在整个生命周期中心。Trace 记录每一步输入、模型输出、工具调用和上下文，使团队不再只看到最终失败，而能判断失败究竟来自提示词、信息缺失、工具设计，还是运行环境。

更重要的是，生产轨迹可以反过来生成测试集：从用户纠正、“你做错了”等对话信号中发现重复问题，把典型失败加入回归测试，再验证修复是否有效。这样形成的不是一次性调参，而是一个闭环：

**生产行为 → 发现失败模式 → 补充评测 → 修改系统 → 重新部署。**

LangChain 提出的自动聚类问题、建议代码或提示词修改，甚至自动补充评测案例，是这一闭环的自然延伸。不过“自我改进”仍不应理解为 Agent 自主进化：它能否改对，取决于评价标准是否可靠。文中保留人工确认再应用修改，恰好说明高风险场景里，人仍是最终的目标函数提供者。

##### 评测设计，本质上是产品定义

开放任务通常没有唯一正确答案。代码 Agent 可以运行单元测试，但研究、运营或客户服务 Agent 的成功标准往往涉及完整性、合规性、成本和用户信任，需要业务专家先把“做得好”变成可执行标准。因此，评测集和指标并非纯工程资产，而是在回答一个产品问题：**我们究竟允许 Agent 在什么边界内，以怎样的代价完成什么任务？**

Agent 还会改变环境，使测试更复杂。若它能更新 Jira、修改文件或执行代码，每轮评测都需要隔离沙箱、固定初始状态并在结束后重置；一次运行可能持续数十分钟并产出文件，而非返回一段文本。传统的问答基准无法覆盖这些风险，真正有价值的评测对象应是“任务＋环境＋结果状态”。

##### 治理必须进入产品架构，而不是上线后的补丁

当 Agent 开始“做事”，权限主体就成为关键：它是在代表用户、同事还是服务账号操作？哪些动作必须审批？成本上限是多少？失败后能否恢复和审计？这些不是后台合规细节，而会直接决定交互设计。让 Agent 先产出草稿、在高风险工具调用前暂停、允许人工恢复任务，往往比追求完全自治更快创造价值。

需要注意，演讲带有明确的平台厂商视角，Trace、评测和部署能力最终都映射到 LangSmith 产品。但它揭示的机会仍然成立：**Agent 的长期壁垒未必是更复杂的提示词，而是组织能否建立一套把真实失败稳定转化为评测、修复与治理规则的学习系统。**

## 默认总结（1）

### 2026-09-18 01:51:11

##### 一句话看懂

生产级 AI Agent 不是做完即可上线的一次性项目，而要通过“构建—测试—部署—监控—治理”的持续循环，依据真实运行记录不断发现并修正问题。

##### 关键内容

- **构建与测试**：框架能降低开发门槛，但也可能隐藏实际调用和成本；测试应基于真实任务、边界案例及应用专属指标，开放式任务可用规则、单元测试或人工标准判断，不能套用统一及格线。
- **部署更重运行保障**：长时间运行的 Agent 需要断点续跑、记忆、流式输出、人工审批和安全沙箱；若会自行编写并执行代码，必须隔离不可信代码。
- **监控是改进核心**：通过 trace（完整运行轨迹）查看每一步输入、输出、工具调用与上下文，再结合用户反馈和自动评估，找出反复出现的失败，并补充测试用例。
- **治理贯穿全程**：规模化使用时还要控制成本、工具权限、身份授权和审计记录。后半段主要介绍 LangSmith 等自家产品，相关效果属于厂商主张。

##### 通俗解读

重点不是让 Agent “偶尔答对”，而是让团队知道它**何时出错、为何出错、修改后是否真的更好**。就像客服培训：先看真实对话找共性问题，再更新话术并复测，而不是凭感觉改提示词。对准备上线 Agent 的开发或平台团队值得细读；只想了解概念，可重点看生命周期、测试和监控部分，产品介绍可略读。
