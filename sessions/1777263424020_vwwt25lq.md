## 分析要点

- **核心高价值点**：监控对象包含自身输出时，事后 grep 混合日志很容易产生循环污染，应该在真实触发点写结构化审计日志。
- **留存建议**：短期参考后可删除（提供了一个关于监控工具自我污染日志的典型反例，可作为可观测性和埋点设计的提醒案例。）

**知识要点**

- 从全量日志中用关键词 grep 统计事件，容易把输出回显、复述内容和任务描述误算为真实触发。
- 工具触发时应主动写入结构化 audit log，例如包含时间、hook、pattern、target 等字段。
- 埋点、agent 监控、dashboard 等系统都可能出现自我回音导致的数据污染。

**行动项**

- 检查现有监控或埋点统计是否依赖混合日志 grep，排查是否存在自我回声污染。
- 为关键 hook 或工具触发点增加结构化 JSONL 审计日志，而不是仅依赖终端输出或自然语言日志。
- 在复盘监控数据时区分真实事件、工具输出、工具结果复述和任务描述文本。

## 正文

**Leo**

5 天监控自己的工具，306 次触发，100% 误报。原来我一直在吸它自己的尾气🤦

给 Claude Code 加了个 hook，ssh 跨机器或写关键文件前弹横幅提醒一下，怕自己手快违反 SSOT 铁律。

配套 stats 脚本统计触发次数，今天打开样本一看，全是误报。

bug 不在 hook，在 stats 脚本：它 grep 的是日志里 "⚠️ 跨机器" 这串字符。

但日志里至少有三种回声：hook 自己输出的横幅、工具结果把横幅复述了一遍、连任务描述里写 "hook 这周触发 N 次" 都被算进去。

我数的不是触发次数，是工具自己说话的回音。

修法：让工具自己写 audit log。  
log\_trigger() { echo "{ts,hook,pattern,target}" &gt;&gt; \~/.claude/logs/hook-trigger.jsonl }

工具触发自己记一行，下周用真数据复盘。

监控自己的工具，最容易骗你的就是它自己。

Claude Code 的 hook 也好，埋点 SDK、agent 监控也好，只要监控对象包括"自己"，事后 grep 就是循环陷阱。

它的输出会塞回日志、复述、甚至混进任务描述里，分不清哪条是真触发哪条是它自己讲过的话。

想知道工具被用了多少次，得让它自己说，别让日志替它说。

## 解读（1）

### 2026-04-27 04:17:04

##### 一、内容总结

Leo 给 Claude Code 加了一个**hook 提醒工具**：  
当它准备**SSH 跨机器操作**或**修改关键文件**时，弹出横幅提醒，避免误操作。

他又写了一个`stats`脚本统计 hook 触发次数。  
结果 5 天统计出：

> 触发 306 次，后来发现 100% 都是误报。

问题不在 hook 本身，而在统计脚本。

脚本用`grep" 跨机器 "`去日志里搜索关键词，但日志里出现这个词的地方不止真正触发记录，还包括：

1. hook 自己输出的提醒横幅；
2. 工具执行结果里复述了这个横幅；
3. 任务描述里提到 “hook 本周触发 N 次” 也被算进去了。

也就是说，他统计到的不是 “真实触发次数”，而是：

> 工具自己说过的话，被日志反复回声后又被统计了一遍。

最后的解决方案是：  
让 hook 在真正触发时，主动写一条结构化审计日志，例如：

```bash
log_trigger () {
  echo "{ts,hook,pattern,target}" >> ~/.claude/logs/hook-trigger.jsonl
}
```

以后统计这个专门的 audit log，而不是从杂乱日志里`grep`关键词。

---

##### 二、深入浅出解读

这件事的核心问题是：

> **你以为你在统计事件，其实你在统计事件的 “回声”。**

举个简单例子：

你想统计一个门铃响了几次。  
正确做法是：每次门铃真的响，就在本子上记一笔。

错误做法是：事后去房间录音里搜索 “门铃响了” 这句话。

问题是，录音里可能有：

- 门铃真的响；
- 有人说：“刚才门铃响了”；
- 有人复述：“他说门铃响了”；
- 有人在总结：“今天门铃响了 3 次”。

如果你只搜 “门铃响了”，这些都会被算进去。

Leo 的问题也是这样：

| 他想统计 | 实际统计到 |
|---|---|
| hook 真正触发了几次 | 日志里出现 “跨机器” 这几个字几次 |

这两者不是一回事。

---

##### 三、这件事反映的问题

###### 1. `grep 日志`很方便，但不可靠

用关键词从日志里搜数据，适合临时排查，不适合做严肃统计。

因为日志里可能混有：

- 原始事件；
- 工具输出；
- AI 复述；
- 用户描述；
- 报错信息；
- 历史总结。

这些内容会互相污染。

---

###### 2. 监控系统最怕 “监控到自己”

一旦监控对象包括自己的输出，就容易出现循环污染。

比如：

- 埋点统计把测试流量也算进去了；
- dashboard 把自己的刷新请求也算进去了；
- agent 监控把 agent 的总结内容当成真实行为；
- 日志分析把报警文本当成报警事件。

这就像站在山谷里喊话，再把回声也当成别人回应。

---

###### 3. AI 工具时代，这类问题会更常见

Claude Code、Codex、各种 agent 会不断：

- 读日志；
- 总结日志；
- 输出日志；
- 再被其他工具读取。

如果没有清晰的数据边界，AI 很容易把 “描述” 当成 “事实”。

例如：

> “我执行了 SSH 操作”  
> 和  
> “用户要求我不要执行 SSH 操作”  

如果都只靠关键词`SSH`判断，就很容易误判。

---

##### 四、我的意见

这篇内容的价值不在于一个小 bug，而在于提醒我们：

> **统计数据必须来自明确的事件源，而不是来自事后文本搜索。**

我的建议是：

###### 1. 关键事件必须单独打点

真正触发时，就写一条结构化日志：

```json
{"ts":"2025-01-01T10:00:00Z","hook":"ssh_guard","target":"prod-server","action":"blocked"}
```

不要依赖自然语言日志。

---

###### 2. 日志要区分 “事实” 和 “描述”

建议分开：

- `audit log`：记录真实事件；
- `debug log`：记录调试信息；
- `chat log`：记录 AI 和人的对话；
- `summary log`：记录总结内容。

统计时只用`audit log`。

---

###### 3. 对 AI agent 尤其要防 “回音壁”

AI 工具很擅长复述、总结、解释。  
但这些内容不能直接当成事实来源。

一句话：

> AI 说 “发生过”，不等于真的发生过。  
> 只有系统在事件发生时记录下来，才算数。

---

##### 五、结论

Leo 这次踩坑，本质是：

> 用文本回声统计真实事件，结果被自己的工具骗了。

正确做法是：

> 真事件发生时，让工具主动写结构化审计日志；  
> 统计时只读这个可信数据源。

这不仅适用于 Claude Code hook，也适用于：

- 埋点系统；
- 监控告警；
- agent 行为统计；
- 自动化运维；
- AI 编程工具。

最终原则很简单：

> **想知道工具做了什么，要记录它真正做的事，不要统计它后来怎么说。**
