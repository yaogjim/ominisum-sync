## 分析要点

- **核心高价值点**：将检测与人体回归分别计时，并通过降低检测频率、固定 ONNX 批处理形状来针对实际瓶颈优化端到端延迟。
- **留存建议**：存档；有三维人体姿态估计或实时推理需求时精读（提供模型输入输出、安装与训练流程、数据校验方式，以及可复现的推理性能调优方案。）

**知识要点**

- 单独测量检测器、人体回归器和总延迟，避免只用模型推理速度代表端到端速度。
- 固定并预热 ONNX 输入批处理形状，可减少人数变化引发的首次运行停顿。
- 训练数据转换后可用三维关节重投影误差校验图像、相机参数与二维标注是否一致。

**行动项**

- 有相关应用需求时，先按文档运行图像或视频演示，分别记录检测与回归延迟。
- 在目标硬件上运行仓库基准测试，比较不同检测间隔的速度与结果质量。
- 使用其训练数据流程时，执行转换器的校验选项并核查数据及模型许可证。

#### InstantHMR

![InstantHMR demo](https://github.com/mohamdev/InstantHMR/raw/main/models/instanthmr.gif)

InstantHMR demo

一个轻量级、可导出为 ONNX 的 MHR 人体回归器，用于 3D 人体姿态估计和网格恢复：RepViT-M1.5 主干网络 + 9-token 交叉注意力解码器 + CLIFF 相机条件化。

它基于 `facebook/sam-3d-body-dataset` 发布的真值标注进行训练——即用于构建 SAM 3D Body 的人体 MHR 拟合数据——从单个 224×224 裁剪图像预测每个人的 MHR 参数和 70 个关键点。支持通过在你自己的图像上运行模型来从 `facebook/sam-3d-body-dinov3` 蒸馏，作为一个可选项（参见训练部分），但这不是已发布模型的训练方式。

InstantHMR 以单个 `.onnx` 文件形式发布。演示流程将其与 RF-DETR 配对用于人体检测——两个阶段独立计时，因此你始终能知道延迟发生在哪里。可选地，演示会通过 Meta 的 MHR 人体模型解码原始 `mhr_params` / `shape_params` 输出，以在 Rerun 查看器中渲染完整密集的人体网格。

- **Inputs:**`image (N, 3, 224, 224)`, `cliff_cond (N, 3)`.
- **输出：** `shape_params (45)` mhr\_params (204) `cam_trans (3)` 、 `joints_2d (70, 2)` 、 `joints_3d (70, 3)` 、 `（归一化裁剪坐标）、` （以人体为中心的米制坐标，Y 轴向下）。
- 速度（仅 InstantHMR ONNX）：在单块 RTX 4070 上使用 fp16 ONNX（CUDA EP）时，\~5 毫秒/帧（约 200 FPS）；CPU 也可以运行（约 25 FPS，取决于硬件）。在 Apple Silicon 上，传入 `--device coreml` 以使用 `CoreMLExecutionProvider` 。
- 速度（完整演示，端到端）：该演示还会每帧运行 RF-DETR，在大多数硬件上，瓶颈是检测器——而不是 InstantHMR。使用 `--detector-stride N` 每第 N 帧仅运行一次 RF-DETR，并在其间复用之前的 bbox（见下文性能调优）。
- RTX 50 系列（Blackwell，sm\_120）注意事项：搭载 CUDA 12.4 wheels 的 stock Torch 不包含 sm\_120 内核，会回退到慢速路径。请使用 `python install.py` ，它会在 Blackwell GPU 上自动拉取 Torch cu128（&gt;=2.7）。

204 维的 `mhr_params` 是 MHR 模型参数，不是 6 维旋转编码。读取 `character_torch.parameter_transform.parameter_names` ，布局如下：

slice contents

`0:3` `root_tx/ty/tz` — 在语料库中始终为 0；1 单位 = 10 厘米，应用于关节 1

`3:6` `root_rx/ry/rz` — 外旋 XYZ 欧拉角，仅驱动关节参数槽位 10/11/12，不驱动其他任何内容

`6:136` 130 个局部关节角度（ `spine0_rx_flexible`, `l_knee_ry`, …）

`136:204` 68 bone-scale parameters

由于根旋转是槽位 10/11/12 独有的， `6:136` 对相机横滚完全不变——这正是训练器中 `pose_split` 所依赖的。 `shape_params (45,)` 编码身份混合形状（20 个身体 + 20 个头部 + 5 个手部组件），并且仅驱动网格：±2σ 的探测会使 127 关节骨架移动 `0.00e+00 cm` 。面部表情被设为中性（零值），因为 InstantHMR 不对其进行回归。

#### Performance tuning

在我们测量过的每台机器上，RF-DETR（检测器）每帧的开销比 InstantHMR 高 \~5–10 倍。下面两个标志针对的就是这个瓶颈。

Flag Effect

`--detector-stride N` 每隔 N 帧运行一次 RF-DETR；在中间帧上复用之前的 bbox（略微扩大）。步长 2–3 是最大的调节旋钮——对于缓慢运动，通常可将端到端 FPS 提高 2–3 倍，而质量损失可忽略不计。

`--detector-variant nano` 使用最小的 RF-DETR；在 CPU / Apple Silicon 上收益最大，因为检测器承担了所有工作。

`--device coreml` 在 macOS 上，将 InstantHMR ONNX 通过 `CoreMLExecutionProvider` 路由。

`--max-persons N` 每帧处理的最大人数（默认值：2）。见下文。

`--no-batch-persons` 禁用批量多人 HMR（每人一次 ONNX 调用）。默认值为批量处理。

`--focal PX` 当你知道相机焦距时，以像素为单位的焦距。从 `--cliff-focal` 检查点导出的模型以角度为条件，因此它们需要焦距；如果没有焦距，演示会回退到 `1.05 x` 图像对角线，这对于手机/网络摄像头来说是一个合理的替代方案，但在任何真实焦距不同的相机上都会导致人物在深度上定位错误。较旧的像素条件图会忽略它，因此不受影响。

`--max-persons` does two things at once:

1. 上限检测 — RF-DETR 可能会找到比你所需更多的人。设置 `N` 每帧仅保留 `N` 个置信度最高的检测结果。
2. 修复 ONNX 批处理大小 — CUDA / ONNX Runtime 在模型首次以新的输入形状运行时编译 GPU 内核。由于批处理维度算作形状的一部分，在演示过程中从 1 人切换到 2 人通常会导致数秒的停顿。该流水线通过始终将输入填充到恰好 `N` 个裁剪（对未使用的槽位进行零填充）来避免此问题，因此无论画面中实际有多少人，会话始终看到 `batch = N` 。

启动：在 `PosePipeline.__init__` 期间，流水线运行两次预热 — `batch = N` 和 `batch = 1` （单人路径）— 因此在第一个真实帧之前所有 CUDA 内核都已编译完成。启动成本大约为 `2 ×` 一次推理时间，并且不会随 `N` 扩展。

**Choosing `N`:**

Scene Recommended `--max-persons`

Single person / portrait 1

Two people, couples, sparring **2 (default)**

Small group, team sport 4–6

Crowd / many people visible raise `N`; also consider `--detector-stride`

提高 `N` 不会在推理时减慢单人帧的速度（填充的槽位在 GPU 上并行运行），但它会按比例增加批处理缓冲区的内存占用，并且当 `N` 较大且 GPU 无法再完全并行处理额外的裁剪时，可能会略微增加延迟。

#### Training

InstantHMR 可以从两种不同的标签来源进行训练。两者都会生成 `notebooks/distill_transformer_decoder.ipynb` 所消费的完全相同的 `images/*.png` + `annotations/*.npz` 布局，因此无论采用哪种方式，训练 notebook 都是相同的：

1. 已发布的真实标注——这是所有已发布模型所使用的数据。直接在 `facebook/sam-3d-body-dataset` 上训练——即用于构建 SAM 3D Body 的人体 MHR 拟合数据——由 `tools/parquet_to_npz.py` 转换为 `.npz` 模式，并由 `datasets_pipeline/build_split.py` 布局为 `data/sam3d_gt_<dataset>/` 。聚类语料库完全属于此类（sa1b / aic / harmony4d / coco / mpii）。
2. 教师蒸馏——一个可选项，而非默认选项。使用 `tools/annotate_dataset.py` 在你自己的图像上运行 `facebook/sam-3d-body-dinov3` 以生成逐人伪标签——参见 `docs/annotation.md` 。这是唯一会写入 `data/sam3d_distill_mix/` 的操作。用它来标注已发布数据集未覆盖的图像；请注意，这会将学生模型的上限限制在教师模型自身的准确率上，而在真实标注上训练则不会。

训练器入口点和 `data/sam3d_distill_mix` 目录出于历史原因保留了“distill”这一名称。该名称并不意味着标签来自教师推理——只有 `tools/annotate_dataset.py` 才会生成这些标签。

##### 在原始标注上训练（COCO 示例）

该数据集是受限访问的：首先在数据集页面上请求访问权限，然后 `huggingface-cli login` 。标注 parquet 文件不包含图像，因此你需要为每个子数据集下载一次源图像（COCO 和 MPII 最简单——只需一个 `wget` ；其他数据集可能需要额外的访问权限/去畸变处理，参见数据集设置指南）。

```
# 1. Annotations — download the coco_train split (uses Meta's sam-3d-body repo)
git clone https://github.com/facebookresearch/sam-3d-body
python sam-3d-body/data/scripts/download.py \
    --save_dir $ANN_DIR --splits coco_train

# 2. Images — COCO 2014 train (the split the parquet filenames reference)
mkdir -p $COCO_IMG_DIR && cd $COCO_IMG_DIR
wget http://images.cocodataset.org/zips/train2014.zip && unzip -q train2014.zip
cd -

# 3. Convert parquet -> per-crop images/ + annotations/ (.npz)
python tools/parquet_to_npz.py \
    --annotation_dir $ANN_DIR/coco_train \
    --image_dir      $COCO_IMG_DIR \
    --output_dir     data/sam3d_gt_coco \
    --validate

# 4. Point the notebook's config at the output and train:
#    cfg.images_dir      = "data/sam3d_gt_coco/images"
#    cfg.annotations_dir = "data/sam3d_gt_coco/annotations"
```

转换器从 MHR 参数中恢复 `cam_trans` ，推导出 1.2× 方形裁剪，跳过低质量拟合（ `mhr_valid` ），并写入与 `tools/annotate_dataset.py` 相同的键。 `--validate` 断言每个人的 `joints_3d + cam_trans` 重投影到存储的 `joints_2d` 上误差小于 1 px。

##### 其他划分（MPII、AI Challenger、Harmony4D、EgoHumans）

每个划分都使用相同的转换器——标注模式和 MHR 数学与数据集无关（已验证：在所有数据集上均为 0 px 重投影且主点位于图像中心）。只有图像准备方式不同。以相同方式下载标注（ `download.py --splits <split>` ），按下述方法准备图像，然后将转换器运行到其各自的 `data/sam3d_gt_<name>/` 文件夹中。

Split Image source Prep `--image_dir`

#### InstantHMR：用轻量模型从单张图像恢复人体 3D 姿态

InstantHMR 是一个开源人体姿态估计项目：它从图像中找出人物，再用轻量模型预测每个人的 3D 关节位置和人体形状参数；需要时，还能生成完整的人体网格。**最值得区分的是：人体回归模型本身约需 5 毫秒，但完整演示通常受 “先找出人在哪” 的检测器限制，不能把 200 FPS 当作端到端速度。**

##### 它如何从照片得到 3D 人体

完整演示分两步。RF-DETR 先在原图中检测人物、给出人物框；InstantHMR 再处理每个人的**224×224 裁剪图像**，预测人体姿态。两步独立计时，便于判断延迟来自哪里。

InstantHMR 使用 RepViT-M1.5 作为轻量视觉主干，以 9-token 交叉注意力解码器生成预测，并加入 CLIFF 相机条件信息，帮助模型结合人物裁剪与拍摄尺度作判断。模型发布为单个**ONNX 文件**，便于在不同推理环境运行。

对每个人，模型输出包括：

- **70 个 2D 关键点和 70 个 3D 关键点**：分别描述图像中的关节位置和立体人体姿态。文档所述原始坐标中，2D 位置相对于裁剪图像归一化；3D 位置以人体为中心、单位为米，Y 轴向下。
- **204 维`mhr_params`和 45 维`shape_params`**：前者主要描述姿态及骨骼尺度，后者描述人体形状；另有 3 维`cam_trans`用于将人体放到相机坐标中。仅看骨架不需要生成网格；若要渲染完整人体表面，则需额外使用 Meta 的 MHR 模型和资源文件解码这些参数。

##### 速度瓶颈在人体检测，不在姿态回归

项目称，在 RTX 4070 上，InstantHMR 的 FP16 ONNX 推理约**5 毫秒 / 帧，约合 200 FPS**；CPU 也可运行，速度随硬件变化，文档给出的量级约为 25 FPS。但视频演示每帧还要运行 RF-DETR。

在作者给出的**1080p、单人视频、RTX 4070、预热后 150 帧**测试中，每帧检测约需**27.1 毫秒**，InstantHMR 约需**5.3 毫秒**，合计**32.4 毫秒、30.9 FPS**。因此，200 FPS 只代表回归模型的速度，**不代表从原始视频到结果的完整流程速度**。

主要优化办法是`--detector-stride N`：每隔 N 帧才重新检测人物，中间帧沿用略微扩大的上一次人物框。同一测试里，设为 2 时端到端约**53.8 FPS**，设为 3 时约**70.4 FPS**。人物移动缓慢时，这通常划算；若人物快速移动或进出画面，旧框可能跟不上，速度收益就需要与结果质量权衡。还可以改用更小的 RF-DETR `nano`检测器，尤其适合检测开销突出的 CPU 或 Apple Silicon 环境。

##### 网格渲染是可选的另一层工作

演示默认可以在 Rerun 查看器中展示原图上的 2D 骨架、3D 场景，以及检测、回归和总延迟。若安装 MHR 相关依赖并下载人体模型资源，还能把参数解码成密集的人体网格。

**网格精细度可以换取速度**：最高质量的 LOD 0 约有 7.36 万个顶点，适合离线图片；实时摄像头默认使用 LOD 3，约 4900 个顶点。只需要关节和骨架时，不必安装这部分额外依赖。基础姿态功能支持 Python 3.11 或 3.12；网格渲染因依赖包限制，需要 Python 3.12。

##### 已发布模型用什么训练，如何复现

**已发布的 InstantHMR 模型使用 Meta 公开的`sam-3d-body-dataset`标注训练，并非在用户自己的图片上运行`sam-3d-body-dinov3`蒸馏得到。**后者只是项目另行支持的一种可选训练路径。这一区别有助于准确理解模型权重的来源；文档所称的 “真值标注”，具体是用于构建 SAM 3D Body 的人体 MHR 拟合数据。

项目提供了从原始标注重建训练样本的流程：下载相应数据集的标注与图像，转换成逐人的裁剪图和参数文件，过滤无效拟合，并检查 3D 关节经相机变换后投影回 2D 图像的误差是否小于**1 像素**。文档以 COCO 为例，也列出 MPII、AI Challenger、Harmony4D、EgoHumans；其中部分数据集还需处理图像畸变。模型 ONNX 权重则托管在 Hugging Face。

总体来看，InstantHMR 提供的是一条**“检测人物 → 轻量预测姿态与人体参数 → 按需渲染网格”**的可运行流程。评估它是否适合实际场景时，应分别看姿态模型的速度、检测器的端到端开销，以及是否真的需要较重的网格渲染。

#### InstantHMR：用轻量模型从图像恢复人体姿态和网格

InstantHMR 是一个从单人图像裁剪预测 **3D 人体姿态和 MHR 人体模型参数**的项目。它的模型可打包为单个 ONNX 文件，单独运行很快；但在完整演示中，**先找出画面里的人，通常比姿态预测更耗时**。另一个需要分清的事实是：已发布模型使用的是 SAM 3D Body 数据集提供的 MHR 拟合标注，而不是由 SAM 3D Body 教师模型临时生成的预测标签。

##### 它如何从画面中得到人体姿态

演示流程分为两步：先由 RF-DETR 检测图像中的人，取得每个人的边界框；再将每个人裁剪为 224×224 图像，交给 InstantHMR。模型以 RepViT-M1.5 为图像特征提取网络，配合一个使用 9 个查询 token 的解码器，并利用 CLIFF 相机条件信息辅助预测。

对每个人，模型主要输出：

- **70 个 2D 关键点**：位置使用裁剪图像的归一化坐标。
- **70 个 3D 关键点**：使用以人体为中心、单位为米的坐标，Y 轴向下。
- **204 维 MHR 姿态参数、45 维体型参数，以及相机平移量**。

这些参数不等于已经生成的密集人体网格。如果需要完整身体表面，还要下载 Meta 的 MHR 模型资源，让 MHR 解码器根据姿态和体型参数生成网格顶点，再结合相机平移量放入相机空间。演示可在 Rerun 中查看原图上的 2D 骨架、3D 场景、网格和各阶段耗时。网格提供多个细节等级：高精度适合离线图片，较低精度更适合实时视频。

对接 MHR 时不能把 204 维参数当作普通的旋转编码：其中包含根部位姿、130 个局部关节角和 68 个骨骼缩放参数。**45 维体型参数只改变网格，不改变输出的关节骨架**；项目也没有预测面部表情，解码时将其设为中性。

##### 单模型很快，但完整流程主要受检测器限制

项目报告：在 RTX 4070 上，InstantHMR 的 fp16 ONNX 推理约 **5 毫秒/帧**，约合 200 FPS；CPU 速度则取决于硬件，文档给出的量级约为 25 FPS。**这不是“检测＋姿态估计”的端到端帧率。**

在一组 RTX 4070、1080p 单人视频测试中，每帧都检测时，RF-DETR 平均耗时 27.1 毫秒，InstantHMR 耗时 5.3 毫秒，端到端约 **30.9 FPS**。因此，调快检测器比继续压缩姿态模型更能改善这套演示：

- `--detector-stride N`：每 N 帧检测一次，其余帧沿用并略微放大上次的人体框。上述测试中，设为 3 后端到端达到 **70.4 FPS**；代价是人物快速移动时，旧框可能不再准确。
- `--detector-variant nano`：改用更小的检测器，尤其适合检测开销突出的 CPU 或 Apple Silicon 设备。
- `--max-persons N`：限制每帧处理人数，同时将 ONNX 输入固定填充到 N 人，避免人数从 1 变 2 时因输入形状变化而出现运行时停顿。N 过大则会增加内存占用，也可能增加延迟。

如果使用以相机角度为条件的模型，最好提供真实焦距。演示虽有默认估计值，但**相机实际焦距不同时，人物的深度位置可能算错**。

##### 怎样使用，以及有哪些环境限制

下载 Hugging Face 上的 `instanthmr.onnx` 权重后，可以通过演示脚本处理单张图片、视频或摄像头，也可以在 Python 中调用 `PosePipeline` 获取各人的关键点和参数。只做姿态估计支持 Python 3.11 起；若要用 MHR 渲染网格，则需要 **Python 3.12**、额外依赖和单独下载的 MHR 资源。苹果设备可为 ONNX 指定 CoreML 执行后端。

安装上的主要提醒是：网格渲染依赖应与基础依赖在**同一次 `pip install`** 中安装，以免 PyTorch 与 torchvision 的 CUDA 版本不匹配；PyPI 上直接安装名为 `pymomentum` 的包，也可能拿到与 Meta 几何库无关的旧包。RTX 50 系列则需要支持其架构的较新 CUDA/PyTorch 包，项目建议使用 `install.py` 自动选择。

##### 已发布模型的训练数据，不要与“教师蒸馏”混淆

项目支持两种标签来源，最终都整理成相同的“裁剪图像＋标注文件”格式，再交给同一个训练 notebook：

1. **已发布模型采用的数据集标注**：来自受限访问的 `facebook/sam-3d-body-dataset`，是用于构建 SAM 3D Body 的人体 MHR 拟合数据。使用者需另外取得原始图像，因为下载的标注文件不包含图像。
2. **可选的教师蒸馏**：在自己的图像上运行 `facebook/sam-3d-body-dinov3`，用它的预测生成伪标签，以覆盖已发布数据集没有的图像。项目明确说，这**不是已发布模型的训练方式**；伪标签还会受到教师模型自身准确率的限制。

项目提供转换脚本，将 COCO、MPII 等数据集的标注与图像整理为训练格式，并可验证 3D 关节经相机投影后是否对得上存储的 2D 关键点。Harmony4D、EgoHumans 等数据集必须先按对应脚本对图像**去畸变**，否则图像与标注不匹配。仓库里部分路径和文件仍沿用 `distill` 这一历史名称，**不能据此推断标签一定来自教师模型**。

最后，仓库**代码采用 Apache 2.0**，但发布的**模型权重遵循 SAM 许可证**；若在下游使用，还需分别核查 SAM、RF-DETR 的许可条件。

## 深度解读-口播（1）

### 2026-09-30 12:23:17

从一张普通照片里，估计一个人的三维姿态，甚至恢复完整的人体表面，能不能做到足够轻、足够快？InstantHMR 给出的方案是，把人体恢复模型做成一个便于部署的小模型。不过，理解这个项目，最重要的是分清两件事：模型本身有多快，和完整应用到底有多快。

先看它做什么。演示程序会先找到画面里的人，再把每个人的图像裁成二百二十四乘二百二十四像素，交给 InstantHMR。模型随后预测七十个人体关键点，包括二维位置和三维位置，同时输出姿态、体型和相机平移参数。

这些参数不是完整的人体表面。要显示密集的三维人体网格，还需要把参数交给 Meta 的 MHR 人体模型，由这个模型生成表面的顶点。因此，检测人物、估计姿态、生成网格，是三个可以分别计时的环节。只想看骨架，就不必承担网格生成的额外开销。

InstantHMR 的网络采用轻量级视觉主干，再结合交叉注意力解码器和相机条件信息。它以一个 ONNX 文件发布。ONNX 可以理解成一种方便模型跨推理环境部署的格式。项目支持英伟达显卡、普通处理器，也支持通过苹果的 CoreML 推理后端运行。

但“支持运行”，不等于不同硬件上有相同速度。

项目报告，在一块 RTX 四零七零显卡上，用半精度模式运行 InstantHMR，单次推理约五毫秒，相当于每秒二百帧。这个数字只属于人体恢复模型，不包含前面的人体检测，也不包含后面的网格生成。普通处理器也能运行，项目给出的参考速度约为每秒二十五帧，但具体取决于硬件。

问题出在完整流水线上。演示使用的检测器叫 RF-DETR，它负责找到人的位置。作者表示，在他们测量过的机器上，检测器每帧的耗时，通常是 InstantHMR 的五到十倍。也就是说，人体姿态已经算得很快，应用却可能仍然被“找人”这一步拖慢。

一个具体测试很能说明差别。在 RTX 四零七零上，处理一千零八十像素高的视频，画面里只有一个人。每帧都运行检测器时，检测约需二十七毫秒，人体恢复约需五毫秒，整体速度约为每秒三十一帧。

如果改成每三帧检测一次，中间两帧复用上一次的人物框，整体速度就提高到约每秒七十帧。人体恢复的耗时几乎没变，省下来的主要是检测时间。

这里有个重要前提：作者说，对于缓慢运动，这种做法通常能把端到端帧率提高到原来的两到三倍，而质量损失可以忽略。不能把这个条件省掉，再把它理解成任何视频都能无代价提速。

所以，调优的关键未必是继续压缩人体恢复模型，而是先看清瓶颈。减少检测频率，或者换用更小的检测器，可能更有效。

多人场景还有另一种卡顿来源。模型第一次遇到新的输入批次大小时，推理环境可能需要编译新的显卡内核。画面从一个人变成两个人，就可能触发数秒停顿。

这个项目的处理办法，是预先设定最大人数，把输入固定填充到相同数量，并在启动时预热。这样做的目的，是避免运行过程中反复改变输入形状。代价则是更高的内存占用；人数较多时，延迟也可能增加。最大人数不是越大越好，而应当匹配实际场景。

再看另一个容易误解的地方：这个模型究竟是怎么训练出来的？

仓库中有些训练文件和目录保留了“蒸馏”这个名称，但作者特别澄清，已发布模型并不是通过运行教师模型、生成伪标签来训练的。

已发布模型使用的是 SAM 三维人体数据集公开的真值标注。具体来说，是用于构建 SAM 三维人体模型的人体 MHR 拟合数据。这里要记住，材料所说的真值标注，具体指这批已发布的人体拟合标注，不应因为“真值”二字，就把它想象成另一种未经说明的测量方式。

教师蒸馏是可选路径。用户可以在自己的图片上运行更大的 SAM 三维人体模型，让它生成逐人的伪标签，再用这些标签训练 InstantHMR。这个办法可以补充已发布数据集没有覆盖的图像。不过，按照作者的说明，学生模型也会受到教师自身准确率的限制。

这两条训练路径使用相同的数据布局，因此能进入同一个训练流程。但数据格式相同，不代表标签来源相同。判断模型能力时，应当看标签实际从哪里来，而不是只看目录名称。

最后，真正部署时，还有两个边界值得留意。

一个是相机焦距。对于以角度为条件的模型，焦距会影响人物在深度方向上的定位。如果没有提供真实焦距，演示会使用图像对角线一点零五倍的估计值。作者认为，这对手机和网络摄像头是合理的替代，但如果实际相机的焦距明显不同，人物的深度位置就可能出错。能画出三维人体，并不代表人物在相机空间里的位置一定准确。

另一个是许可证。仓库代码采用 Apache 二点零许可证，但已发布模型权重采用 SAM 许可证，下游使用还需要查看 RF-DETR 的许可证。代码、模型权重和检测器，不能当成同一套授权条件。

这个项目最值得记住的，是它把轻量人体恢复做成了一个便于部署的独立模块。每秒二百帧是模型本身的参考速度，完整应用仍要看检测和网格生成的开销。至于结果能否满足实际用途，还要一起检查训练标签的来源、相机参数，以及各组件的使用许可。
