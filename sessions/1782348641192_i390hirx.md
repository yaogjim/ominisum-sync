## 正文

**宝玉**

Google Workspace CLI 这项目当时我还转发过，没想到几个月过去，作者 Justin Poehnelt 因为这个项目被开除了。

Justin 在 Google 干了将近七年，岗位是 Workspace 开发者关系工程师。今年 3 月初，他用 Rust 写了一个 Google Workspace CLI，放在了 Google 官方 GitHub 组织下（[http://github.com/googleworkspace/cli…](http://github.com/googleworkspace/cli)），可以用命令行操作 Gmail、Drive、Calendar 等所有 Workspace 服务，还内置了 MCP 服务器，AI agent 可以直接调用。

Addy Osmani 3 月 5 日发推介绍了这个项目。然后就爆了，Hacker News 第一名，GitHub star 数冲到两万多，几天之内就有了几千个实际用户。

Google 内部的反应是两极的：有总监和高管主动来问这个工具能教他们什么；同时法务开始盘问他，为什么项目上有 Google 的 logo 和品牌色。

4 月 22 日到 24 日的 Google Cloud Next 大会上，Google Workspace 官方博客宣布官方 Workspace CLI 即将推出。两天后，Justin 被开除了。

他怀疑是 Workspace 的某些管理层和项目害怕被 AI agent 颠覆，而这种恐惧不只是针对他的 CLI，是针对整个 agent 对 Workspace 意味着什么。

Hacker News 上对这件事的观点两极分化。一派认为这是 Google 官僚主义碾压创新的典型案例，七年老员工做了个用户真正想要的东西，然后被自己公司干掉了。另一派指出，Google 有一套非常明确的开源发布审批流程，用公司品牌发布未经批准的项目，在任何大公司都可能被开除。

Justin 本人在 Hacker News 回复里的说法是：作为 DevRel 工程师，开源发布审批本来就是他日常工作的一部分，而且这个流程文档不清楚，还一直在变。

这个项目本身还活着。最新一次更新是 6 月，GitHub 上 26000 多颗星，InfoQ 和 BetterStack 都有详细的教程。Justin 被开除后还在继续写技术博客，最近一篇是用 Claude Code 的 subagent 做 Gmail 分类。

对于正在用这个 Workspace CLI 的开发者来说，眼下倒不用太担心，项目还在 Google 的 GitHub 组织下正常维护。

## 解读（1）

### 2026-06-25 00:48:40

#### Google Workspace CLI 作者被开除事件：精炼解读

##### 一、深度总结

Justin Poehnelt 是 Google Workspace 的开发者关系工程师，任职近 7 年。

他用 Rust 开发了一个 **Google Workspace CLI**，可通过命令行操作 Gmail、Drive、Calendar 等服务，并内置 MCP Server，方便 AI Agent 调用 Workspace 能力。

项目发布在 Google 官方 GitHub 组织下后迅速走红：

- Hacker News 排名第一
- GitHub Star 超过 2.6 万
- 几天内获得大量真实用户
- 被 Addy Osmani 等技术影响力人物转发

但随后 Google 内部反应分裂：

- 一些高管认为项目有启发价值
- 法务和管理流程开始关注品牌、Logo、审批合规问题
- Workspace 官方随后宣布将推出官方 CLI
- 两天后，Justin 被解雇

外界对此有两种主要看法：

1. **创新被官僚主义扼杀**  
   一个真正解决用户需求的工具，被公司内部流程和利益结构压制。

2. **大公司合规不可绕过**  
   使用 Google 官方品牌、仓库发布工具，如果未经完整审批，被处理并不意外。

Justin 本人认为，作为 DevRel 工程师，开源发布本是其工作内容之一，但 Google 的审批流程并不清晰，且不断变化。

目前项目仍在 Google GitHub 组织下维护，开发者暂时不必过度担心。

---

##### 二、深入浅出解读

这件事本质上不是“一个 CLI 工具”的问题，而是三个矛盾撞到了一起。

###### 1. 创新速度 vs 大公司流程

Justin 做出了用户真正想要的东西，而且速度很快。

但大公司更在意：

- 品牌能不能用
- 法务有没有审核
- 这个项目算个人行为还是官方产品
- 会不会影响已有路线图
- 会不会造成对外承诺风险

所以问题不是“工具好不好”，而是“它是不是按公司允许的方式出现”。

###### 2. AI Agent 正在改变 Workspace 的入口

这个 CLI 不只是命令行工具。

它内置 MCP Server，意味着 AI Agent 可以直接操作 Gmail、Drive、Calendar。

这会改变 Workspace 的使用方式：

> 用户不再点网页按钮，而是让 AI 直接替自己完成工作。

这可能威胁到原有产品设计、团队边界和商业控制权。

因此 Justin 怀疑，真正让某些人紧张的不是 CLI，而是它背后的趋势：  
**AI Agent 可能重写 Workspace 的交互入口。**

###### 3. “官方身份”既是流量，也是风险

项目放在 Google 官方 GitHub 下，天然获得信任和传播。

但这也意味着：

- 外界会认为它代表 Google 官方立场
- 出问题会牵涉公司责任
- 与官方产品规划冲突时更敏感

所以同一个动作，站在开发者视角是“推动创新”，站在法务视角可能是“未经授权发布官方产品”。

---

##### 三、辩证思考

###### 不能简单说 Google 一定错

大公司有合规流程是必要的。

如果员工都能随意用公司 Logo、官方仓库发布项目，确实会带来风险：

- 品牌滥用
- 安全责任
- 用户误导
- 产品路线混乱
- 法律和隐私问题

尤其 Workspace 涉及邮件、日历、文件等敏感数据，审批必须谨慎。

---

###### 但 Google 也暴露了严重问题

真正值得警惕的是：

> 一个被用户强烈验证的创新，没有被快速吸收，反而以开除创作者收场。

这说明组织可能存在几类病：

- 流程比用户反馈更重要
- 合规机制缺少弹性
- 内部创新缺少安全通道
- 管理层害怕被边缘项目打乱既有计划
- “拥抱 AI”停留在口号，实际仍按旧秩序运转

如果一个公司既要求员工创新，又不给清晰边界和保护机制，最后员工只能选择不做事。

---

###### 对个人开发者的启示

在大公司内部做创新，尤其使用公司品牌时，要特别注意：

- 不要默认“对公司有利”就安全
- 官方仓库、Logo、名称都很敏感
- 爆红反而会放大风险
- 技术成功不等于组织成功
- 最好提前留下审批记录和授权证据

一句话：

> 在大公司里，成果重要，流程同样重要；有时流程甚至更重要。

---

##### 四、最终判断

这件事最可能不是单一原因造成的。

它既有 **合规问题**，也有 **组织政治**，还有 **AI Agent 冲击既有产品入口** 的深层焦虑。

Justin 做出了用户需要的东西，但可能没有完全踩稳大公司的品牌与发布边界。  
Google 维护流程有其合理性，但用解雇回应成功创新，也显得僵硬和短视。

最讽刺的是：

> 项目证明了 Google Workspace 需要这样的工具；  
> 但创造这个工具的人，却被组织排除在外。
