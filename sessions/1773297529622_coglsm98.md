## 分析要点

- **核心高价值点**：最有价值的是用“控制权换速度”的视角解释框架与工具包选择，本质是在灵活性与预设能力之间做权衡。
- **留存建议**：短期参考后可保留，适合作为概念辨析材料（对理解智能体框架、运行时与开箱即用工具的分层有帮助，可作为选型时的快速参考）

**知识要点**

- 智能体开发可放在从原始代码到框架再到开箱即用工具包的连续光谱上理解
- 框架强调模块化和可替换组件，工具包强调内置决策与快速可用
- LangChain 生态可区分为框架、运行时和更高层封装工具三层

**行动项**

- 在自己的智能体项目中明确当前目标是实验构建还是快速交付，再决定选框架还是工具包
- 用一张表对比候选方案的可替换性、默认能力、状态管理和错误恢复能力

## 正文

**Tony Kipkemboi**

### 智能体测试套件与智能体框架的区别

如果你一直听到 “代理框架” 和 “代理工具” 被频繁提及却分不清两者区别，这篇文章就是为你准备的。这些术语听起来可以互换，但实际上并非如此。我曾在

[@crewAIInc](https://x.com/@crewAIInc)，这是一个代理框架，所以我清楚它们之间的界限在哪里。

代理框架和代理工具包在有主见程度的光谱上处于不同位置。如果你正在构建代理，了解它们的位置很重要，因为这会改变你需要负责的内容以及工具为你处理的内容。

如果将代理开发放在一条线上，最左侧是没有任何抽象的原始代码。你需要直接调用 API，自行管理状态，从零开始构建每一个部分。完全灵活，完全负责。

智能体框架位于中间。它们为你提供结构和抽象，但你仍然需要做出很多决策。你选择内存系统，配置工具，定义编排逻辑。框架对事物的连接方式有自己的看法，但它是模块化的。你可以交换组件。

代理框架位于最右侧。它们有着极强的预设观点，所有功能都已内置。你只需添加 API 密钥，可能指向几个工具，然后它就能运行。记忆、上下文管理、代理循环、安全检查——所有这些都由系统为你决定。

框架为你提供构建智能体的抽象概念。你定义角色、任务、工具。你指定智能体如何协作，是按顺序还是按层级工作。框架处理底层实现细节，如调用 LLM、路由工具输出、管理执行循环。但你仍然需要做出架构决策。

该框架对构建块的外观有明确的要求。它包含内存抽象、工具接口和任务结构。但这些组件是可替换的。如果你不喜欢默认的内存实现，可以插入自己的实现。如果你想使用不同的 LLM 提供商，你可以对其进行配置。该框架为你提供了一个标准接口，但你仍然可以构建这个系统。

模块化正是关键所在。框架是为那些想要构建代理（而非仅仅使用代理）的人设计的。你需要理解各个组件如何协同工作，因为由你决定使用哪些组件。

一个框架不会给你积木。它给你一个完整系统。

最近最好的例子是

[@openclaw](https://x.com/@openclaw) 几周前在网上走红。这是一个框架。你下载它，添加你的 API 密钥，然后突然你就有了一个可以在 WhatsApp、Telegram 和其他平台上聊天的代理。内存管理已处理。上下文管理已处理。代理循环已处理。工具调用、权限、状态持久化。所有这些都内置其中。

你不是在配置内存系统。你不需要决定工具如何注册，也不需要决定代理如何从错误中恢复。这些决定由构建该框架的人做出。你的工作是将其指向一个任务并让其运行。

这就是权衡之处。你能立即获得可用的东西，但你无法修改它底层的实现方式。这个框架对所有事情都有自己的设计思路，而当你使用它时，你就是在接受这种设计思路。

频谱很重要，因为它对应于不同的问题。

如果你正在进行原型设计、实验或开发自定义内容，你会需要一个框架。你需要能够灵活地替换组件、测试不同方法并控制细节。框架为你提供结构，同时不会将你锁定。

如果你需要现在就能使用、可靠且适用于特定场景的工具，你会想要一个 harness。你正在用控制权换取速度。这个 harness 已经解决了那些难题：上下文管理、持久化执行、错误恢复。你只需要使用这个解决方案即可。

框架是给构建者用的。工具是给用户用的。

这并不意味着某一个更好。这意味着它们在解决不同的问题。你要解决的问题决定了你需要哪一个。界限并不总是清晰的，我不确定它是否应该是清晰的。

一些框架正在添加类似工具的功能。

[@LangChain](https://x.com/@LangChain) 这是一个很好的例子。他们发布了 Deep Agents，他们明确称之为“代理工具”，该工具位于其框架之上。它内置了规划工具、用于上下文管理的文件系统访问、子代理生成以及内存持久化功能。你仍然在底层使用 LangChain，但 Deep Agents 提供了开箱即用的默认设置，因此你无需自己将所有东西连接起来。

LangChain 实际上区分了

[三层](https://blog.langchain.com/agent-frameworks-runtimes-and-harnesses-oh-my/)在他们自己的技术栈中 。LangChain （最初的库）是框架 。LangGraph 是他们所谓的 “代理运行时”， 它负责处理执行、状态管理和持久性 。Deep Agents 是…… 位于两者上方的安全带。 这是一家业务涵盖所有领域的公司：用于构建代理的框架、用于可靠执行代理的运行时环境，以及用于开箱即用部署代理的框架。

这是一家在该领域方向上持续推进的框架公司。Deep Agents 仍然是模块化的。你可以更换后端、配置工具、调整提示词。但它为你提供一个可用的系统，无需你自行组装每一个组件。

另一方面，这些框架并不像听起来那么封闭。以 OpenClaw 为例，它开箱即用时就极具预设性，但如果你下载源代码，你可以更换实现方式。你可以修改内存的工作方式，调整代理循环，修改工具处理方式。只是大多数人不会这么做，因为默认设置已经能正常工作了。

这种区别在于开始时已经确定的内容是什么。工具包随产品附带的是已经嵌入的决策，而框架随产品附带的是公开的选项。如果你使用的是工具包，你接受其中大部分决策并在边缘进行配置；如果你使用的是框架，你需要自己做那些决策并组装系统。

你要解决的问题决定了你需要哪一个。有时候（实际上大部分时候）你需要完全绕过代理框架，构建一个简单的

[ReAct](https://arxiv.org/pdf/2210.03629) 代理，直接使用模型端点。

你想要的已建成的东西的多少决定了你选哪一个。

## 结构化（1）

### 2026-03-12 06:38:49

**主旨概括：**  
这篇文章主要解释了**智能体框架（framework）**和**智能体测试套件 / 工具包（harness）**的区别：两者不是谁更高级，而是**面向不同需求**。  
核心差别在于：**框架给你结构和模块，适合自己搭系统；工具包给你现成可运行的系统，适合直接用。**

---

##### 1. 先看它们在 “控制权” 光谱中的位置
文章把智能体开发放在一条线里：

- **最左侧：原始代码**
  - 直接调用 API
  - 自己管理状态、上下文、执行流程
  - **灵活性最高，但也最费心**

- **中间：智能体框架**
  - 提供结构和抽象
  - 你仍需决定很多关键问题，比如：
    - 用什么记忆系统
    - 工具怎么接入
    - 多智能体如何协作
  - **适合想自己搭建的人**

- **最右侧：智能体工具包 /harness**
  - 强预设、开箱即用
  - 通常只要加上**API Key**、连几个工具就能运行
  - 系统已内置：
    - 记忆管理
    - 上下文管理
    - 智能体循环
    - 安全检查
  - **适合想快速用起来的人**

**一句话理解：**  
框架更像 “搭积木的平台”，工具包更像 “已经组装好的成品”。

---

##### 2. 智能体框架到底提供什么
框架会帮你处理底层复杂性，但**不会替你做所有决策**。

###### 关键点
- 你可以定义：
  - 智能体角色
  - 任务
  - 工具
  - 协作方式（顺序、层级等）
- 框架负责：
  - 调用 LLM
  - 路由工具输出
  - 管理执行循环
- 但你仍要决定整体架构

###### 模块化是核心
框架通常有标准接口，但组件可替换，例如：
- 不喜欢默认内存实现，可以换自己的
- 想换 LLM 提供商，也可以配置

**作者强调：**  
框架是给 “想构建智能体的人” 用的，不是给 “只想直接使用智能体的人” 用的。

---

##### 3. 工具包 /harness 的特点：现成、快，但限制更多
工具包的思路是：**很多难题已经替你决定好了**。

###### 它通常内置的能力
- 内存管理
- 上下文管理
- 智能体循环
- 工具调用
- 权限控制
- 状态持久化
- 错误恢复

###### 你不需要再决定的事
- 内存系统怎么设计
- 工具如何注册
- 出错后如何恢复

###### 代价
- 上手快，能立即产出
- 但底层实现方式通常不容易改

**通俗例子：**
- 框架像 “厨房 + 食材 + 炊具”，你自己决定怎么做菜
- harness 像 “预制套餐”，热一热就能吃，但改法不多

---

##### 4. 文章给出的典型案例
###### 案例 1：OpenClaw
作者把**@openclaw**作为工具包 /harness 的代表。

###### 它的特点
- 下载后加上**API Key**
- 很快就能得到一个可在**WhatsApp、Telegram**等平台聊天的代理
- 已处理好：
  - 内存管理
  - 上下文管理
  - 智能体循环
  - 工具调用
  - 权限
  - 状态持久化

###### 说明了什么
- 你几乎不需要自己搭系统
- 适合 “我现在就要一个能跑的代理”

但作者也补充：
- 它并不是完全不可改
- 如果你下载源代码，仍然可以修改：
  - 内存实现
  - 智能体循环
  - 工具处理方式
- 只是**大多数人不会改**，因为默认设置已经够用了

---

##### 5. 什么时候选框架，什么时候选 harness
###### 适合选框架的情况
如果你在做：
- 原型设计
- 实验
- 自定义开发
- 测试不同方案

那你更需要框架，因为你需要：
- 替换组件
- 控制细节
- 保持灵活性

###### 适合选 harness 的情况
如果你需要的是：
- 现在就能用
- 更可靠
- 面向某个具体场景的现成方案

那就更适合 harness。因为你是在：
- **用控制权换速度**
- 直接复用别人已经解决好的复杂问题

**作者总结得很直接：**
- **框架是给构建者的**
- **工具包是给使用者的**

---

##### 6. 两者的边界正在变模糊
文章指出，这个界限不是绝对的，很多产品开始 “中间化”。

###### 案例 2：LangChain / LangGraph / Deep Agents
作者用**LangChain**举了一个很有代表性的例子：

###### LangChain 技术栈的三层
- **LangChain**：框架
- **LangGraph**：代理运行时  
  - 负责执行、状态管理、持久化
- **Deep Agents**：更接近 harness 的上层方案  
  - 提供开箱即用的默认设置

###### Deep Agents 内置了什么
- 规划工具
- 文件系统访问（用于上下文管理）
- 子代理生成
- 内存持久化

###### 它的特点
- 仍然基于 LangChain
- 你还是可以：
  - 更换后端
  - 配置工具
  - 调整提示词
- 但它已经给你一个 “能直接工作的系统”

**说明：**  
现在很多框架公司不只提供框架，还提供运行时和开箱即用层，覆盖从 “自己搭” 到 “直接用” 的不同需求。

---

##### 7. 最终结论
文章最后的核心判断是：

- **工具包附带的是 “已替你做好的决策”**
- **框架附带的是 “可供你自己选择的选项”**

所以选择标准不是 “哪个更好”，而是：

- 想要**更多现成能力** → 选 harness  
- 想要**更多可控性和可替换性** → 选 framework  
- 有时甚至**两者都不用**，直接做一个简单的**ReAct 代理**，直接调用模型接口就够了

**一句话收尾：**  
你需要多少 “已经帮你建好的东西”，决定了你该选框架还是工具包。

## 产品-最佳实践（1）

### 2026-03-12 06:55:55

下面用一个具体场景说明，并给出精炼的最佳实践。

##### 具体实例：做一个 “企业客服智能体”

###### 场景
你要为一家电商公司做一个客服智能体，目标是处理：
- 订单查询
- 退款政策问答
- 转人工
- 多渠道接入（网页、WhatsApp、Telegram）

---

##### 两种选择的区别

###### 1）如果用 “智能体框架”
比如你选择一个可编排、可替换组件的框架。

你通常要自己决定：
- 用什么记忆机制
- 工具怎么注册（查订单、查物流、发工单）
- 智能体如何规划与调用工具
- 出错怎么恢复
- 多轮对话状态怎么持久化

**适合这个实例中的情况：**
- 你们客服流程复杂，未来会频繁变化
- 你需要接公司内部多个系统
- 你想精细控制成本、延迟、安全策略
- 你要做 A/B 测试，比如比较不同提示词、不同记忆策略

**本质：你是在 “造系统”。**

---

###### 2）如果用 “智能体测试套件 /harness”
这里更像 “开箱即用的代理运行方案”。

你通常只需要：
- 配置模型和 API Key
- 接上订单查询等少量工具
- 配置渠道接入
- 直接运行

系统已经替你决定了很多事：
- 对话循环
- 上下文管理
- 状态持久化
- 错误恢复
- 基础安全检查

**适合这个实例中的情况：**
- 你需要两周内先上线一个可用客服助手
- 流程相对标准化
- 团队缺少专门做智能体基础设施的人
- 你更关心 “尽快可用”，而不是 “完全可控”

**本质：你是在 “用系统”。**

---

##### 这个实例上的最佳实践

###### 如果你是大多数团队，最佳实践是：
**先用 harness 快速上线 MVP，再在关键环节逐步框架化。**

###### 为什么
因为客服场景通常有两个阶段：
1. **先验证有没有价值**
   - 用户会不会用
   - 哪些问题最常见
   - 工具调用是否稳定
2. **再优化可控性**
   - 降低误答率
   - 优化转人工逻辑
   - 做权限隔离、审计、成本治理

如果一开始就用框架全自建，容易：
- 周期长
- 决策过多
- 还没验证价值就陷入工程细节

如果一直只用 harness，也会遇到：
- 复杂流程难改
- 深度定制困难
- 被默认机制限制

---

##### 一句话决策法

- **要快速交付可用结果：选 harness**
- **要深度定制与长期演进：选框架**
- **不确定时：先 harness，后框架化**

---

##### 最终建议
在 “企业客服智能体” 这个实例里，**最佳实践不是二选一，而是分阶段选型**：

> **用 harness 验证业务，用框架承接复杂化。**

这是速度、风险和可维护性之间最稳妥的做法。

## 产品-技术开发（1）

### 2026-03-12 06:56:52

下面我用**产品视角 + 技术实现视角**，把这篇文章里的核心概念拆开。先说结论：

##### 一句话结论
**智能体框架（Framework）**是 “搭建智能体系统的积木和标准件”；  
**智能体测试套件 / 工具包（Harness）**是 “已经组装好的可运行系统，你主要做配置和接入”。

> 更准确地说，文中这个 harness 更接近：**Agent runtime /agent kit /opinionated scaffold /out-of-box agent system**，不只是 “测试” 工具。  
> 如果翻译成 “测试套件” 会有歧义，容易让人以为它只做 eval 或 QA。  
> **更好的中文：智能体工具包 / 智能体运行套件 / 开箱即用智能体系统。**

---

#### 1. 产品层面的本质区别

##### 1) 框架：卖的是 “构建能力”
适合对象：
- 平台团队
- AI 产品研发团队
- 需要自定义工作流的企业

产品特征：
- 提供抽象：Agent、Tool、Memory、Task、State、Workflow
- 允许替换组件
- 默认能力有限，但扩展性强
- 上手门槛更高

产品价值：
- 灵活性
- 可控性
- 可组合性
- 长期演进能力

典型场景：
- 企业知识库问答 + 工单流转 + CRM 联动
- 多智能体协同流程
- 高合规、高可观测、可插拔模型架构

---

##### 2) Harness：卖的是 “即刻可用”
适合对象：
- 创业团队
- 业务团队
- 需要快速上线 demo / MVP 的团队
- 不想投入大量 Agent infra 开发的人

产品特征：
- 内置：记忆、上下文窗口管理、工具注册、任务循环、错误恢复、权限控制
- 只需填 API Key、配置工具、写提示词
- 可快速交付
- 可改空间小，底层决策已被封装

产品价值：
- 上线速度
- 默认最佳实践
- 降低实现复杂度
- 降低工程门槛

典型场景：
- Telegram / WhatsApp 客服机器人
- 内部效率助手
- 标准化的信息收集、自动回复、日程处理

---

#### 2. 技术架构上的关键区别

可以把 Agent 系统拆成 6 层：

1. **模型层**：LLM/Embedding/Reranker  
2. **工具层**：搜索、数据库、API、文件、浏览器  
3. **记忆层**：短期上下文、长期记忆、用户画像  
4. **执行层**：Planner、ReAct loop、子任务拆解、重试恢复  
5. **状态层**：任务状态、会话状态、持久化、checkpoint  
6. **安全治理层**：权限、审计、限流、敏感词、人工接管

---

##### 框架的职责
框架一般只提供：
- 统一接口
- 抽象类 / 协议
- 编排机制
- 部分默认实现

你仍要自己决定：
- 用哪家模型
- 记忆如何存
- 工具如何鉴权
- 多 Agent 如何协作
- 状态如何持久化
- 失败如何恢复
- 线上如何监控

###### 技术上像这样
```python
agent = Agent (
    llm=openai_model,
    tools=[search_tool, crm_tool],
    memory=RedisMemory (),
    planner=ReactPlanner (),
    checkpoint=PostgresCheckpoint (),
)
```

你拥有系统设计权，但也承担复杂度。

---

##### Harness 的职责
Harness 一般直接把这些都包好了：
- 预置 Agent loop
- 工具调用协议
- 状态持久化
- 对话记忆
- 失败重试
- 简单安全边界
- 部署入口

###### 技术上像这样
```python
app = AgentKit (
    api_key=os.getenv ("API_KEY"),
    channels=["telegram"],
    tools=["web_search", "calendar", "gmail"],
)
app.run ()
```

你主要做：
- 填配置
- 绑定渠道
- 选择工具
- 写少量业务规则

---

#### 3. 核心判断标准：你是在 “造系统” 还是 “用系统”？

这是最实用的判断法。

##### 选框架，如果你要：
- 自定义 Agent 行为
- 控制 prompt /planner/memory
- 管理复杂工作流
- 接企业内部系统
- 做可观测、审计、权限治理
- 需要长期维护和演进

##### 选 Harness，如果你要：
- 两周内上线
- 目标场景明确
- 接入标准工具即可
- 团队缺少 AI infra 工程能力
- 优先验证业务价值而不是技术最优

---

#### 4. 最佳实践：3 个典型落地例子

---

##### 例子 A：企业客服助手
###### 目标
在 WhatsApp/Telegram 上做一个客服 Agent，回答 FAQ、查订单、升级人工。

###### 最佳选择
**优先 Harness**

###### 原因
这个场景的核心不是 “智能体架构创新”，而是：
- 快速接渠道
- 稳定运行
- 有基本记忆
- 能调工具
- 能做人工兜底

###### 推荐设计
- LLM：GPT-4.1 / Claude Sonnet
- 工具：FAQ 检索、订单查询、工单创建
- Memory：仅会话级短期记忆
- 安全：订单 / 退款类操作需二次确认
- 兜底：低置信度转人工

###### 最佳实践
1. **不要一开始做长期记忆**
   - 客服类高频问题以即时上下文 + FAQ 检索为主
2. **工具权限最小化**
   - 查订单可开放，退款操作必须人工审批
3. **输出结构化**
   - `intent`, `confidence`, `action`, `response`
4. **失败有降级路径**
   - 检索失败 → 通用答复 → 转人工
5. **记录完整轨迹**
   - 用户问题、检索命中、工具调用、最终回复

###### 一个很实用的返回协议
```json
{
  "intent": "check_order_status",
  "confidence": 0.93,
  "tool_call": {
    "name": "get_order_status",
    "args": {"order_id": "12345"}
  },
  "final_response": "您的订单已发货，预计明天送达。"
}
```

这类系统用 Harness 很合适，能快速稳定上线。

---

##### 例子 B：企业内部研究助理
###### 目标
自动读取文档、检索知识库、做总结、生成分析报告、调用多个内部 API。

###### 最佳选择
**优先框架**

###### 原因
这个场景通常要处理：
- 多阶段任务拆解
- 多数据源接入
- 自定义 memory
- 高质量可追溯输出
- 复杂权限和审计

Harness 往往不够灵活。

###### 推荐架构
- Agent 1：需求理解与任务拆解
- Agent 2：知识检索与证据收集
- Agent 3：报告生成
- Agent 4：质量校验 / 事实核查

###### 技术实现建议
- 编排：LangGraph / 自定义状态机
- 知识检索：向量检索 + keyword search hybrid
- 持久化：Postgres + Redis
- 观测：trace + token + latency + tool success rate
- 输出：引用证据链

###### 最佳实践
1. **把 “规划” 和 “执行” 拆开**
   - Planner 不直接执行危险工具
2. **每个阶段产出结构化状态**
```json
{
  "query": "...",
  "subtasks": ["查财报", "查新闻", "分析竞争对手"],
  "evidence": [],
  "draft": "",
  "quality_score": 0.0
}
```
3. **RAG 必须做引用**
   - 否则报告不可审计
4. **工具调用必须幂等**
   - 失败重试不能产生副作用
5. **加入 verifier**
   - 对关键结论进行二次校验

这个场景本质上是在 “构建生产级智能体系统”，框架更适合。

---

##### 例子 C：自动化销售外呼 / 线索培育 Agent
###### 目标
自动触达潜在客户，收集需求，安排会议，同步 CRM。

###### 最佳选择
**Hybrid：Harness 起步，框架演进**

###### 原因
前期重点是验证转化率，不是做最强架构。  
但一旦开始要求：
- 多轮个性化跟进
- 用户画像记忆
- 渠道协同（邮件 + IM + CRM）
- A/B 测试不同策略

就需要逐步转向框架。

###### 演进路径
**Phase 1：Harness**
- 快速上线消息触达
- 标准工具：邮件、日历、CRM
- 模板化脚本 + 简单记忆

**Phase 2：框架化**
- 把 lead scoring、follow-up policy、memory policy 独立出来
- 增加策略实验能力
- 做多 Agent 分工：触达、分析、预约

###### 最佳实践
1. **先做 “规则优先”，再做 “自主优先”**
   - 触达频率、话术边界先写死
2. **长期记忆只存高价值字段**
   - 行业、角色、需求、异议点、联系偏好
3. **将 CRM 同步做成事件驱动**
```python
on_message_replied -> update_lead_status -> trigger_next_action
```
4. **对业务指标做闭环**
   - 回复率
   - 预约率
   - 工具调用成功率
   - 幻觉率
   - 人工接管率

---

#### 5. 产品经理最容易踩的坑

##### 坑 1：把 Harness 当框架用
表现：
- 想深改 memory、planner、执行策略
- 结果发现系统改不动

建议：
- 一开始就明确：这是用来 “快速上线” 还是 “长期平台化”

---

##### 坑 2：把框架当产品用
表现：
- 以为用了 LangChain/LangGraph 就等于有完整 Agent 产品
- 结果发现缺少监控、权限、部署、重试、审计

建议：
- 框架只解决 “开发抽象”，不自动解决 “生产可用性”

---

##### 坑 3：过度设计 Agent
很多场景根本不需要复杂 Agent。
例如：
- FAQ 问答
- 表单填写
- 单步骤 API 调用

###### 更优解
- Prompt + Tool calling + 状态机
- 或简单 ReAct agent

> 原则：**能不用多智能体，就不要用多智能体。  
> 能不用长期记忆，就不要用长期记忆。  
> 能不用自治规划，就不要让模型自由规划。**

---

#### 6. 一个实用的决策表

| 问题 | 选 Harness | 选框架 |
|---|---|---|
| 是否要快速上线 MVP | 是 | 否 |
| 是否需要深度自定义 memory /workflow | 否 | 是 |
| 团队是否有 AI infra 能力 | 弱 | 强 |
| 是否需要高可控、强审计 | 一般 | 更适合 |
| 是否是标准化场景 | 是 | 不一定 |
| 是否要长期做平台化沉淀 | 不适合 | 适合 |

---

#### 7. 推荐的技术选型思路

##### 如果你要快
- 选 Harness / 开箱即用 Agent Kit
- 限定工具数量
- 只做会话记忆
- 加人工兜底
- 先验证业务价值

##### 如果你要稳
- 选框架 + runtime
- 明确状态机
- 做 checkpoint
- 做 observability
- 所有工具调用结构化、可回放

##### 如果你要长期可演进
- 底层用框架
- 上层封装你自己的 Harness
- 对业务团队暴露配置，不暴露复杂技术细节

这其实是最优组织形态：
**平台团队用框架造底座，业务团队用内部 Harness 快速交付。**

---

#### 8. 最后给一个最精炼的判断公式

##### 选择标准
- **想控制 “怎么做” → 框架**
- **想尽快得到 “能用的东西” → Harness**
- **场景简单 → 甚至直接 API + Tool calling**
- **场景复杂且长期运营 → 框架 + runtime + 业务层封装**
