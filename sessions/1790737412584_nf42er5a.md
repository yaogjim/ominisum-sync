## 分析要点

- **核心高价值点**：将运行时视为可替换计算单元：在派发外部操作前，先持久化具有稳定身份的状态转换及执行义务，使故障恢复依赖已提交事实而非进程内存。
- **留存建议**：精读并保留架构原则与关键协议，具体实现需结合实际负载和故障测试验证（提供运行时边界划分、持久化交付、工具授权及多线程协作的具体设计，可反复用于 Agent 平台架构评审。）

**知识要点**

- 按所有者、生命周期和扩展模式划分系统边界：运行时负责线程计算，状态、交付、凭证及沙箱生命周期由外部服务负责。
- 持久化交付应以数据库中的 Queue 与 Inbox 状态为依据；通知仅用于唤醒，线程内保持有序，并通过绑定代际与实例身份约束故障后的重新投递。
- 凭证隔离不等于动作授权；工具提议应先经过独立策略与审查，决策持久化后再次校验，才能进入可执行边界。

**行动项**

- 梳理现有 Agent 进程中的状态、凭证、消息交付和沙箱管理职责，按生命周期与扩展模式确定需要外置的边界。
- 为关键状态转换和工具结果建立稳定标识、事务提交及幂等回执，明确提交确认丢失、运行时退出和消息重投时的恢复路径。
- 在工具执行前设置独立授权关口，将决策绑定到具体动作与策略；审查失败或决策未成功提交时，不允许推进执行。

通过将运行时从沙箱中拉出，并围绕持久化的智能体工作重建系统，来扩展云智能体。

#### Scaling the wrong thing

去年年底，我开始构建云智能体，目标只有一个：扩展它们。那时我已经花了几个月时间沉浸在本地编码智能体中，尤其是从早期研究预览阶段开始的 Claude Code，以及后来的 Codex CLI。一个智能体看起来就像安装在计算机上的程序，被那台计算机的文件、Shell 和工具所包围。

Manus 关于上下文工程的文章让云版本变得具体：操作在虚拟机沙箱内运行，其文件系统作为可恢复的上下文。对于我的第一个产品 Anoma，我采取了最直接的路径，将本地智能体循环移入 E2B。沙箱成了智能体容量的单位，因此扩展智能体就意味着扩展沙箱。

使用 E2B 并没有消除管理沙箱集群的需要；更多用户仍然意味着需要配置、复用和回收更多沙箱，并且要受制于提供商的生命周期约束。 [会话](https://www.anthropic.com/engineering/managed-agents) 历史和追踪数据会一直留在这些沙箱中，直到清理为止，这使得调试依赖于对存有私有用户数据的环境的访问权限。要将 API 密钥保留在外部，就需要一个单独的网关来代理模型请求。我们不断把职责移出沙箱，以便让沙箱内的 agent 能够正常工作。

03 / 03

第一个应用分三层成长：E2B 内部的完整 agent、用于沙箱容量和模型流量的控制平面，最后是产品界面。控制平面扩展了沙箱，但每个沙箱仍然承载着一个完整的 agent。

到二月，这些限制让我确信架构需要改变。对于我的第二个产品 Tetral，我想要一个通用 agent 包 ，而不是另一个带有固定 UI 的应用。这意味着一个 SDK，开发者可以用它把云端 agent 引入自己的产品，而无需编写循环或运维其背后的基础设施。交付这个产品意味着要拥有托管层，但它仍然把沙箱作为容量单位。我考虑了两条路线。

Kubernetes 可以运行这个服务，但它的 pod 对于高频创建和销毁的沙箱来说是一个糟糕的单位。Modal 后来在大规模场景下记录了同样的不匹配：在极端的沙箱频繁创建销毁下，串行化的调度器和协调的 pod 生命周期会成为瓶颈。

另一条路线是 EC2、Firecracker，以及一个用于 microVM 创建、冷启动和回收的控制平面。这条路线可行，但会导致需要构建一个沙箱提供程序。Agent 容量仍然受限于集群所能提供的计算机数量。无论哪条路线，都会把沙箱供应留作一个独立且可替换的基础设施问题，而不是 Agent 服务的一部分。

Agent 和沙箱集群遵循不同的扩展曲线。Agent 是一个稳定的共享服务，其容量可以在许多工作之间复用。沙箱集群则是隔离的、突发性的且一次性的。保持这种波动性相互独立，就要求将两者分离。Agent 成为一个稳定的服务，而沙箱则保持为一次性的执行资源。这种设计旨在让 Kubernetes 运行一组 Agent 运行时，并在副本之间分配并发会话，而无需同时管理沙箱的频繁变动。

#### 构建系统，寻找运行时

##### The runtime boundary

将智能体与其沙箱分离留下了一个更精确的问题：如何将智能体抽象为一个能够跨并发会话扩展的服务？

技术上的赌注是将智能体视为一个运行时：一个持续运行的程序，它解释模型输出，并让智能体以受控方式访问模型、网络、文件、工具、子智能体和外部世界。Claude Code 和 Codex 已经表现得像本地运行时。在云端，只有当其身份、状态和资源都存在于进程之外时，同一个循环才能成为一个可替换的计算单元。这一标准定义了运行时的边界：每一项拥有不同所有者、生命周期或扩展模式的职责，都必须移到它之外。

01 / 06 · 捆绑式

**一个进程承担所有职责** Provider 集成、状态、交付、计算机生命周期和产品界面全部位于 agent 进程内部。

通过将 Provider 集成、状态、交付、计算机生命周期和产品界面移出可替换的计算边界，来寻找运行时。

仅有状态并不能交付工作。因此，生产者将每个输入、agent 消息或资源操作与一个 Queue 作业一起提交。这样，交付就可以比生产者存活得更久，并可由任何兼容的消费者尝试执行。Queue 负责排序、租约、重试、取消和死信处理。

计算机生命周期是另一项需要剥离的职责。Sandbox Service 拥有由提供商支持的计算机，并执行为其调度的工作。运行时只声明某个线程需要一次计算机操作。

Public API 和 Event Stream 也仍然位于执行路径之外：一个接受 SDK 请求，另一个暴露 PostgreSQL 的有序记录。两者都不执行 agent。

剩下的就是对会话和线程的计算。

运行时通过 Bridge 加载线程，应用 reducer，并声明下一个操作。运行时 pod 只是一个可替换的计算宿主。它可以保持多个会话和线程处于热状态，但不拥有其中任何一个，并且在其声明被接受之前，无法派发外部操作。

##### Write ahead of execution

可替换运行时会带来一个棘手问题。当一个 pod 消失后，其替代者必须知道某个操作是尚未开始、仍在进行中，还是已经完成。进程内存无法回答这个问题。猜测可能会导致跳过工作，或重复执行同一外部效果。

该 [协议](https://www.postgresql.org/docs/current/wal-intro.html) 借鉴了 WAL 的顺序规则：在执行其授权的操作之前，先记录一次转换。因此，任何可能推进线程或产生外部义务的转换，都必须在派发之前提交。发生故障后，运行时会从这些已提交的事实中重建该轮次，而不是恢复丢失的进程。

在派发之前，运行时向 Bridge 提交一份具有稳定标识的不可变声明。Bridge 验证所有权和顺序，然后在一个事务中提交转换及其回执。只有在收到该确认之后，运行时才可以派发操作。稳定标识是一个幂等键：重试同一份声明会返回其现有回执，而不是创建第二个转换。

Bridge 在一个事务中记录沙箱执行及其 Queue 作业。沙箱工作进程运行命令，并将原始结果存储为已完成但尚未消费。Bridge 将该结果返回给等待中的运行时，后者为原始工具使用声明 `agent.tool_result` 。

在一个事务中，Bridge 追加 `agent.tool_result` ，更新 `session_messages` 中对应的条目，将存储的沙箱结果标记为已消费，并记录一个幂等回执。只有在确认之后，reducer 才可以依赖该结果并计算下一步。

如果提交确认丢失，运行时会重新提交相同的身份标识，Bridge 则返回已存储的回执。将同一身份标识复用于不同内容会被拒绝。

##### Durable delivery

桥接提交让活动线程得以推进。队列承载了可以等待消费者并比其生产者存活更久的工作。

Queue job 告知 Bridge 的 Job Runner 投递仍需尝试。Inbox 是接收侧的记录：它指定目标 thread，并记录输入是处于排队、投递中，还是已被 runtime 接受。

每个注册事务都会创建一个 Queue job 及其 Inbox 记录。Job Runner 取走该 job，投递所引用的输入，将 Inbox 推进到 accepted，并确认该 job。

事务提交后，PostgreSQL 发出 `pg_notify` 来唤醒 Bridge 的 Job Runner。该通知不包含任何消息内容，也不拥有任何投递状态。如果它丢失了，runner 的轮询循环稍后会发现同一个 Queue 作业；消息仍然保留在 PostgreSQL 中。

在 Job Runner 租约该消息之前，Queue 会检查其目标线程。推进一个上下文的输入保持有序，因此后续的普通消息无法越过正在投递或重试的消息。其他线程则并发进行。

到达运行时即通过两步完成投递义务。Bridge 首先将 Inbox 条目标记为已接受，然后 Job Runner 确认 Queue 作业。此时 Job Runner 已完成。运行时是否以及何时将已接受的输入提交到其线程中，属于运行时自身的循环，而非投递。

仅凭超时并不能证明旧运行时已停止处理该消息。绑定代际和 pod UID 充当隔离令牌：只有在 Kubernetes 确认绑定的 pod 身份已消失后，Bridge 才会将已接受的投递返回给 Queue。随后，替换运行时可以加载线程最后提交的状态，并从同一 Inbox 义务继续。

##### Calling the model

运行时为该轮次累积了文本和工具调用。输出在进入存储上下文之前经过了 Bridge；工具调用等待 `agent.tool_use` ；而 `span.model_request_end` 关闭了提供商流。

在两条路径中，运行时都声明了它需要什么能力以及哪个资源应该处理它。Gateway 和 MCP 连接器拥有外部连接、提供商格式和凭证。Agent 可以使用这些能力，而无需任何运行时 Pod 或沙箱接收底层密钥。

##### Computers as resources

大多数能力不需要计算机。模型和 Web 请求属于 Gateway，MCP 调用属于 MCP 连接器，内存操作则通过 Bridge 进行。Shell 和文件系统工具则不同，因为它们需要执行环境。

计算机是暴露给 Agent 的资源。沙箱是当前由提供商支持的隔离实例，Sandbox Service 拥有其生命周期和执行。

队列同时推进了两个依赖项。第一个执行作业在将 Bash 执行附加到其激活后结束，而声明在 PostgreSQL 中仍为 `waiting_activation` 。并发调用可以共享该激活，而不是启动相互竞争的计算机。在激活和物化之后，每个逻辑执行都作为新作业返回到队列。

01 / 10

Bash 执行 #42 到达一台冷计算机。Sandbox Service 将该逻辑执行暂存在激活 A7 上，然后在计算机就绪后将其作为新一代返回队列。

在提交命令之前，Sandbox Service 已将该执行绑定到当时确切的那台计算机。如果在此期间另一个 worker 替换或释放了该计算机，过期的 worker 就无法将已接受的命令发送到新计算机。

随后，Sandbox Service 存储输出，供等待中的运行时通过 Bridge 完成结算。运行时故障不会取消计算机操作，也不要求重新发出 Bash 命令。

##### Scaling in two dimensions

让计算机可以独立调度，并不能让一个有序上下文朝两个方向推进。并发的模型请求会读取同一个边界，并产生相互竞争的下一个状态，因此并行工作需要独立的执行路径。

Agent 工作在两个维度上扩展：线程在一个任务内创建独立的执行路径，而会话则在从同一工作区中选择的资源上创建独立的任务。

If the main agent wanted an implementation inspected while it continued the design, it created a child thread running the same reducer and tool loop over a separate context. An independent review might need no parent history, a continuation might need all retained context, and a focused investigation only the most recent turns.

`fork_turns` made that choice explicit: `none` for no parent history, `all` for all retained parent context, or a positive number of recent turns. The runtime resolved it into an exact, immutable starting context for the child.

An in-memory child could disappear before receiving its instruction, or be created twice after a lost response. The runtime therefore committed the `spawn_agent` tool call first. In one transaction, Bridge created the child and parent relationship, saved its context and instruction, placed the instruction in its Inbox, and created the delivery job.

Only after Bridge acknowledged that transaction did the tool call return the child thread ID. Retrying the same committed call returned the same child instead of creating another.

After the fork, parent and child still had separate contexts. New parent messages did not automatically appear in the child, and neither thread could directly write into the other’s context. Further communication had to be delivered as another ordered input.

Messages and child completions returned as ordered inputs. Bridge recorded the message, destination, Inbox entry, and Queue job in one transaction. If the receiving thread was busy, the input waited behind its current turn.

`send_message`, child completion, and `wait_agent` used this path. A child’s final answer was committed before reaching the parent’s Inbox. Waiting added no second durable content channel and did not repeat the child’s work.

Child threads were appropriate when several execution paths still belonged to one task. They were not the right boundary for every responsibility around a workspace. Code implementation, documentation, auditing, and knowledge maintenance could each require an independent root agent, context, agent version, credential set, and lifecycle. Those belonged in separate sessions.

Separate sessions could still select files, memory stores, repositories, credentials, and an agent version from the same workspace. Tools and skills came from that resolved version. Execution and history stayed independent; a product could later decide which reviewed results became shared resources.

##### A separate decision

Scaling agent work also scales its external effects. Keeping credentials behind Gateway prevents the runtime and its computers from possessing a provider key or OAuth token, but it does not decide whether one proposed action should use that credential.

Credential isolation controls access to a capability. Authorization decides whether one proposed action may exercise it.

That decision belongs before execution and outside the agent proposing it. A cloud boundary can apply the same deterministic policy, content inspection, classifiers, and server-side enforcement across clients and execution environments, as [Claude Code auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode) demonstrates.

OpenAI’s [Hugging Face incident](https://openai.com/index/hugging-face-incident-and-the-road-ahead/) shows why recognizing risk inside the acting agent is not the same as enforcing a boundary around it. This does not imply that an LLM reviewer would have prevented that incident. It means a tool call must cross an authorization boundary before it can affect the outside world.

`approve_for_me` is the first mode implemented at this boundary. Its review model was inspired by Codex’s [automatic approval reviewer](https://developers.openai.com/codex/sandboxing/auto-review), then adapted to the write-ahead execution protocol.

Consider a model that proposes a Bash command whose policy is `always_ask`. The runtime first passes the proposal through a deterministic tool gate. The gate combines the session approval mode, the tool catalog, and the policy attached to that tool. Under `approve_for_me`, the first evaluation says that an independent review is required.

Nothing has been accepted for execution yet. There is no public `agent.tool_use`, no sandbox job, and no external effect. The Bash command is still a proposal produced by the open model request.

Schematically, the proposal receives a stable review identity derived from its workspace, session, thread, model request, model tool call, tool name, canonical action, and policy:

```text
review_id = H(workspace, session, thread, request, tool_call, tool, action, policy)
```

The hash binds the decision to one exact proposal. Retrying the review uses the existing identity, while changing the command or its policy creates a different review.

The reviewer runs as an internal thread using the same runtime machinery as other agent work. It receives the proposed action, the relevant parent context, the current assistant output, sibling tool calls from the same model turn, and the effective policy. These inputs are evidence, not instructions. Files, websites, tool results, and even the acting model may contain prompt injection, so platform-owned reviewer policy remains separate from the material being reviewed.

The reviewer returns only a risk level, the user authorization visible in context, an `allow` or `deny` outcome, and a rationale. Malformed output is a review failure, not permission.

在一个热父运行时生命周期内，后续的审查可以复用一个审查器线程，该线程一次处理一个审查。重叠的审查使用从其最新已提交状态复制的临时线程，从而允许并行决策而不会交错上下文历史。

Each completed tool call first reaches the Tool Gate. One review continues on the main reviewer thread while overlapping reviews use temporary copies of its latest committed state. Every decision is committed before the Tool Gate evaluates the exact proposal again.

The reviewer’s output is not yet authorization. Bridge first records the decision in PostgreSQL under the proposal’s stable identity. Only after that commit may the result return to the parent thread.

The runtime then runs the tool gate a second time, now with the committed review outcome. An allowed decision produces an executable tool use. A denial records a rejected tool result without running the command. A reviewer failure falls back to user approval only after Bridge acknowledges the failure record. If that commit fails or the runtime loses authority, the tool call does not advance.

只有在完成这第二次评估之后，运行时才会提交公开的 `agent.tool_use` 。该事件是接受边界，在此之后，执行才可能被放入 Queue 并路由到拥有所请求能力的服务。

取消遵循相同的顺序。如果父轮次在审查决定被确认之前被取消，迟到的结果可能仍可供审计，但不能推进已取消的工具调用。

Making identity and resources independent requires a public contract that names them. [The Managed Agents API](https://platform.claude.com/docs/en/managed-agents/agent-setup) provided versioned agents, sessions pinned to a resolved version, per-session overrides, and first-class files, memory stores, vaults, skills, and environments. Tetral forked that SDK and remains compatible with the Managed Agents surface it has implemented, with registered deviations, while building the runtime and cloud system beneath it. By naming the agent, its version, sessions, and resources independently, that contract makes the agent addressable beyond any one client.

##### A durable participant

An addressable agent can continue across a terminal, browser, phone, GitHub, or team product because those surfaces share one ordered session history. Closing a client does not end the session or transfer the agent between computers.

Identity makes that continuity accountable. An external action can be traced to an agent version, session, thread, policy, and review. Its deployer remains responsible, but the agent becomes a distinct actor in that chain.

[RoboBun](https://github.com/robobun) makes work on GitHub attributable to a public agent identity. [Raft](https://raft.build/resources/blog/introducing-raft-where-humans-and-agents-build-together/) places named, stateful agents together in a multi-agent workspace. [Claude Tag](https://www.anthropic.com/news/introducing-claude-tag) gives a Slack channel an asynchronous Claude and lets a team delegate to several Claudes in parallel. The interfaces differ, but each treats the agent as an addressable participant rather than an invisible completion behind a user’s account.

Identity becomes operational when it carries delegated authority. An agent can [provision an account, obtain an API token, purchase a domain, and deploy](https://blog.cloudflare.com/agents-stripe-projects/), or request a [merchant- and amount-bound payment credential without receiving card details](https://stripe.com/blog/giving-agents-the-ability-to-pay). The user or organization remains the principal; the identified agent receives limited, traceable authority.

Tetral keeps identity with the agent while the system controls credentials, policy, approval, and execution. A CLI fits work bound to an operating system, repository, compiler, or debugger. Reading an issue or posting a message should not require a computer: MCP exposes the capability, its connector supplies the session credential, and the runtime’s Tool Gate applies policy and approval.

A planned Code Mode, inspired by [OpenCode](https://github.com/anomalyco/opencode/blob/dev/packages/codemode/README.md), would let a confined JavaScript program discover and compose permitted MCP tools, transform their results, and run independent calls in parallel. CLI remains the interface for computer-native work; MCP becomes the preferred interface for capabilities native to the cloud agent.

##### Work that compounds

Adding communication or participants does not automatically improve collaboration; [coordinated swarms and independent parallel agents can spend similar tokens per result, and larger shared coding swarms can merge a smaller share of their work](https://www.anthropic.com/research/multiagent-systems).

Tetral’s bet is adversarial review before synthesis. Before work enters the shared workspace, other agents must actively challenge its conclusions and evidence, not merely agree with them. A human then decides what is accepted. This scrutiny matters because accepted work becomes the basis for subsequent exploration: an unchecked mistake can propagate into everything built upon it. The workspace holds the work itself, together with the reasoning and evidence needed to review it. Agents explore many paths, but progress accumulates by [building on validated results](https://www.anthropic.com/research/formalizing-fermats-last-theorem), not by inheriting one another’s unexamined conclusions.

两种协作结构：共享对话，以及被纳入共享工作区的独立工作。

因此，长周期产品可以为未来的评估和训练提供证据，前提是来源信息得以保留、私有数据被移除，并且由人工判断来识别成功或失败。训练应当减少有害提议，但外部影响仍然需要确定性策略、验证、内容检查、分类器、独立评审、组织规则以及人工升级。

##### 围绕智能扩展系统

More capable models create more work for every system around them. Longer horizons and more parallel paths mean more runtime transitions, tests, computers, files, network requests, stored trajectories, and external effects. The shortest of those capacities becomes the next scaling problem.

Programming languages and toolchains are part of that surface. Runtime pods have finite CPU and memory for active threads, while every generated change may start another edit, build, and test cycle. [Bun’s move from Zig to Rust](https://bun.com/blog/bun-in-rust) reduced memory use and improved throughput while addressing stability and memory-safety failures.[TypeScript’s native Go port](https://devblogs.microsoft.com/typescript/typescript-native-port/) began because the existing implementation could not scale to the largest codebases; early builds ran roughly ten times faster with substantially less memory. On my development server, one Tetral integration path can take seven or eight minutes and a full validation pass roughly half an hour. Compilation and verification can become the limit before inference does.

Execution environments have a different load from stable services. Short-lived environments must be scheduled, created, supplied with resources, paused, resumed, released, and reclaimed. Burst creation, attachment and resume latency, and high-churn scheduling matter as much as boot time. At sufficient scale they encounter [coordination and control-plane limits that ordinary service orchestration was not designed around](https://modal.com/blog/scaling-to-1-million-concurrent-sandboxes-in-seconds).

A sandbox is too heavy for every operation. File access may require only a virtual filesystem; untrusted code needs stronger isolation; platform-specific work needs the corresponding machine. The question is not only how many sandboxes can run, but how much work must pass through a full computer and how quickly each required boundary can be supplied.

[Actor systems](https://rivet.dev/actors/) suggest another point in this design space: lightweight, addressable compute that can sleep and wake without provisioning a full computer. How such a primitive should map to Tetral’s sessions, threads, or resource workers remains open. The immediate conclusion is only that a full sandbox should not be the default boundary for every operation.

A disposable execution environment is useful only if its output can outlive it. This exposes another resource boundary: storage. Session events, tool results, and logs must enter an ordered session history, while code, documents, and build outputs must return to repositories, object stores, or workspace files that another environment can load later.

More parallel agents produce more transitions, files, commits, pull requests, and test runs, pushing the systems behind those interfaces toward new limits. Session logs may scale through [PostgreSQL replicas, pooling, caching, workload isolation, and separation of write-heavy data](https://openai.com/index/scaling-postgresql/). Code storage may need a new implementation when agent-generated Git operations outgrow a traditional host, as shown by [a Git-compatible host rebuilt around an object-storage write-ahead log and replaceable local repositories](https://cursor.com/blog/git-at-any-scale).

The agent still asks for session history, files, or a repository. What changes under growing demand is the infrastructure that implements those storage interfaces.

##### 从 alpha 到 agent 原生云

The implementation will diverge as those workloads become real. Services may merge, the runtime may move beyond Bun, storage may split, and the queue, Bridge, or Kubernetes topology may be replaced. Three bets remain: the agent is cloud native; the agent system, not only the model, must scale; and the runtime keeps the agent as the computational center while the system around it preserves continuity and control.

Those bets are now concrete enough to test with other people. Tetral is open under the MIT license so product builders, infrastructure engineers, security researchers, and model providers can challenge its boundaries, implement new runtimes, connect new resources, and build products the current system did not anticipate. The thesis is now concrete enough to test in public. This alpha is the starting point for exploring the much larger space of an agent-native cloud.

### 2026-09-30 03:03:32

#### 云智能体的下一个扩展难题：让工作持续，而不是让沙箱常驻

文章从作者构建云智能体的经历出发，讨论如何让智能体同时承担更多任务、长时间运行，并安全地影响外部世界。**核心判断是：扩展云智能体，不应只是增加运行智能体的沙箱，而应把智能体运行时、持久化状态、任务投递、执行环境和授权机制分开。**模型越强，产生的并行任务、工具调用、编译测试和外部操作就越多；这些配套系统中最先达到上限的一环，会成为下一个瓶颈。

##### 1. 最初扩展错了对象：沙箱不应该等于一个智能体

本地编码智能体通常是安装在电脑上的程序，直接使用那台电脑的文件、Shell 和工具。作者最初构建产品 Anoma 时，把同样的智能体循环搬进 E2B 云沙箱：每个沙箱里运行一个完整智能体，更多用户意味着更多沙箱。

这条路径容易起步，却把两类生命周期不同的东西绑在了一起：

- **智能体服务需要稳定运行、复用计算容量**，同时处理许多会话。
- **沙箱需要隔离、按需创建和销毁**，其需求往往突发且短暂。

实际问题随之出现：团队仍要管理沙箱的配置、复用和回收；会话历史与追踪数据留在沙箱中，调试需要进入保存用户私有数据的环境；为了不把模型 API 密钥放进去，又要增加一个外部网关。

于是，团队不断把职责搬出沙箱，却仍然保留 “一个沙箱承载一个完整智能体” 的基本结构。改用 EC2、Firecracker 自建虚拟机体系，也只是把问题变成 “自己建设沙箱供应平台”，并没有改变这个绑定关系。

作者提出的转向是：**把智能体变成共享服务，把沙箱变成它按需使用的一种执行资源。** Kubernetes 可以扩展智能体运行时副本，沙箱服务则独立处理计算机的创建和回收，两者不必同步扩容。

##### 2. 运行时只负责 “计算下一步”，不拥有会话和资源

这里的 “运行时”，是持续解释模型输出、推进智能体工作、协调工具调用的程序。要让它像普通云服务一样可替换，就必须把身份、状态和资源放到进程之外。

否则，一个运行时进程退出，不仅丢失计算能力，还会把会话进度、待执行工作或资源控制权一起带走。

文章把系统拆成几类职责：

| 组件 | 负责什么 |
|---|---|
| **运行时** | 加载线程状态，处理模型输出和工具结果，计算并声明下一步操作 |
| **Bridge** | 校验运行时是否有权推进工作，把状态变化、结果和回执可靠地写入 PostgreSQL |
| **Queue、Inbox 与 Job Runner** | 保存待投递工作，处理顺序、租约、重试、取消和失败任务 |
| **Gateway 与 MCP 连接器** | 管理外部连接、服务格式和凭证；MCP 是让智能体调用外部工具的一种标准接口 |
| **Sandbox Service** | 创建和回收计算机，执行 Shell、文件系统等需要计算环境的操作 |
| **Public API 与 Event Stream** | 接收客户端请求、向外提供有序事件记录，不负责运行智能体 |

运行时内部通过**reducer**推进状态：可以把它理解为一个状态更新函数，根据已有状态和新事件，算出新的状态及下一步动作。

**运行时可以把多个会话留在内存里以提高效率，但内存不是最终依据。**任意运行时副本退出后，另一个副本都应该能够根据已提交的记录继续工作。

##### 3. 可靠恢复的关键：先记录决定，再执行操作

进程可替换后，最棘手的问题不是 “怎么重启”，而是 “重启后怎么知道之前做到了哪一步”。

例如，智能体准备执行一条 Bash 命令，运行时却突然退出。替代者必须分辨：命令尚未开始、正在执行，还是已经完成。只靠丢失的进程内存无法判断，盲目重试可能重复产生外部影响，不重试又可能漏掉工作。

作者借鉴了**WAL（预写日志）**的顺序规则：**凡是会推进线程或产生外部执行义务的变化，都要先持久化，再允许执行。**

具体流程是：

1. 运行时向 Bridge 提交一份不可变声明，附带稳定标识。
2. Bridge 校验所有权和顺序，在一个数据库事务中保存状态变化与回执。
3. 运行时收到确认后，才可以派发操作。

稳定标识充当 “幂等键”：同一声明重试时返回已有回执，而不是重复创建状态变化；如果用同一标识提交不同内容，则会被拒绝。

工具结果也遵循同样的原则。以沙箱命令为例：

- Bridge 同时记录执行任务和队列作业。
- 沙箱工作进程执行命令，把原始输出保存为 “已完成、尚未消费”。
- 运行时取得结果后，提交`agent.tool_result`。
- Bridge 在一个事务中追加结果事件、更新消息、标记结果已消费，并保存回执。
- 确认完成后，运行时才把该结果作为下一步计算的依据。

这意味着，**恢复的是已经提交的工作事实，而不是原来的进程。**即使确认消息丢失，运行时也能用原标识查询或重试，而不必重新创造那次状态变化。

##### 4. 可靠投递不只是重试，还要区分 “收到” 和 “处理完成”

Bridge 保存状态，但待处理输入仍需要可靠地送到运行时。文章为此区分了两个记录：

- **Queue job**：这份工作仍需要投递，谁可以领取、何时重试。
- **Inbox**：输入要送到哪个线程，目前是排队、投递中，还是已经被运行时接受。

注册输入时，队列作业和 Inbox 记录在同一个事务中创建。数据库提交后通过`pg_notify`唤醒投递进程，但通知只是 “提醒有活”，不承载消息内容或投递状态。即使通知丢失，轮询仍能找到数据库中的任务。

这里有两个重要边界。

**第一，同一个线程的普通输入必须保持顺序，不同线程可以并发。**前一条消息正在投递或重试时，后一条不能越过去，否则上下文会按错误顺序发展。

**第二，运行时接受输入，不等于它已经把输入提交进线程状态。** Inbox 被标记为 accepted、队列作业被确认后，投递方的责任结束；后续处理属于运行时自己的循环。

如果运行时接受输入后失联，不能仅凭超时就让另一个运行时重复处理，因为旧进程可能还在运行。系统用绑定代际和 Pod UID 区分新旧执行者，只有 Kubernetes 确认旧 Pod 身份已经消失，才重新投递已接受的输入。替代者随后从线程最后提交的状态继续。

##### 5. 计算机只是资源，不能成为所有能力的默认入口

文章强调，很多智能体能力根本不需要电脑：

- 模型和 Web 请求走 Gateway。
- MCP 工具调用走连接器。
- 记忆操作通过 Bridge。
- Shell 和文件系统工具才需要沙箱。

运行时声明需要哪种能力、由哪个资源处理；外部连接与密钥由相应服务管理。模型输出也先经过 Bridge 再进入保存的上下文，工具调用需要形成正式的`agent.tool_use`记录。

当任务需要一台尚未启动的计算机时，Sandbox Service 会先把逻辑执行挂到一次 “激活” 上。并发调用可以共享这次启动过程，而不是各自创建一台竞争中的计算机。计算机准备好后，每项逻辑执行再重新进入队列。

执行命令前，任务还必须绑定到**当时那台确切的计算机实例**。如果计算机已被替换或释放，过期工作进程不能把原命令误发到新实例上。

因此，运行时退出不必取消已经开始的计算机操作，也不要求重新发送 Bash 命令；执行结果可以先保存，等待新的运行时接续处理。

##### 6. 并行有两个维度：一个任务拆线程，多个任务建会话

**独立调度计算机，不等于同一份上下文可以并行推进。**如果两个模型请求同时读取同一状态，它们会各自产生 “下一步”，形成相互竞争的结果。真正的并行需要独立执行路径。

文章区分了三个层次：

- **线程（thread）**：一条有序上下文和执行路径。
- **会话（session）**：一个独立任务，可包含主线程和子线程。
- **工作区（workspace）**：多个任务可以从中选择文件、仓库、记忆、凭证等资源。

###### 同一任务内，用子线程分工

例如，主智能体继续设计方案，子智能体同时审查实现。创建子线程时，可以通过`fork_turns`明确选择：不继承父线程历史、继承全部保留上下文，或只继承最近若干轮。

系统把选定上下文固定成不可变的起点，并在一个事务中保存子线程、父子关系、指令、Inbox 和投递作业。只有确认后才返回子线程 ID；重试同一次创建会返回同一个子线程。

分叉以后，父子上下文相互独立。新父消息不会自动出现在子线程中，双方也不能直接修改对方历史；通信和完成通知都必须作为有序输入投递。等待子线程不会重新执行它的工作，也不会另建一套内容存储渠道。

###### 独立责任，用不同会话

代码实现、文档维护、审计和知识整理，可能需要不同的根智能体、上下文、版本、凭证和生命周期。这些更适合独立会话，而不是全部作为某个主智能体的子线程。

它们可以使用同一工作区的资源，但执行与历史保持独立。哪些成果最终成为共享资源，再由产品流程决定。

##### 7. 密钥隔离解决不了授权：工具执行前需要独立判断

**“智能体拿不到密钥” 与 “智能体被允许做这件事” 是两回事。**

Gateway 隐藏 API 密钥或 OAuth token，可以防止运行时和沙箱直接持有凭证，但无法判断某次发消息、执行命令或付款是否得到用户授权。

作者主张：授权判断必须发生在执行之前，并位于提出行动的智能体之外。文章引用 Claude Code auto mode 和 OpenAI 的 Hugging Face 事件来说明这一边界的重要性，同时明确指出：这不意味着一个 LLM 审查器就一定能够避免事故。

Tetral 已实现的`approve_for_me`模式，把独立审查接入了预写执行协议。以一条按策略必须审批的 Bash 命令为例：

1. **先过确定性的 Tool Gate。**  
   根据会话审批模式、工具目录和工具策略，判断是否需要独立审查。此时命令仍只是提议，没有公开的工具使用事件、沙箱任务或外部影响。

2. **给精确提议绑定稳定审查身份。**  
   身份包含工作区、会话、线程、模型请求、工具调用、具体动作和策略等信息。相同提议重试复用身份；命令或策略变了，就必须重新审查。

3. **独立审查器评估证据。**  
   它接收相关上下文、当前模型输出、同轮其他工具调用和有效策略，返回风险等级、上下文中可见的用户授权、允许或拒绝，以及理由。格式错误属于审查失败，不代表许可。

4. **先保存审查结果，再重新过 Tool Gate。**  
   审查器说 “允许” 本身还不是执行授权。Bridge 必须先提交决定，工具门再根据已提交结果重新评估，才能形成可执行的工具调用。

拒绝会记录失败结果而不执行命令；审查失败则在失败记录确认后转向人工审批。如果提交失败或运行时已失去权限，调用不能继续。父轮次在审查确认前取消，迟到结果也不能让命令重新推进。

审查器收到的文件、网页、工具结果乃至行动模型输出，都只是证据，不是可以覆盖平台规则的指令，因为它们可能含有提示注入。并行审查也使用独立上下文，避免多个决定交错污染同一历史。

##### 8. 持久身份让智能体成为可委派、可追责的参与者

运行时、状态和资源分离后，还需要一个公开接口把它们独立命名：智能体、版本、会话、文件、记忆、凭证库、技能和环境。

文章借鉴了 Managed Agents API。Tetral 分叉了其 SDK，并声称对**已经实现的接口范围**保持兼容、记录差异，而不是宣称完整兼容全部能力。

这样，同一个智能体可以跨终端、浏览器、手机、GitHub 或团队产品继续工作，因为这些入口访问的是同一份有序会话历史。关闭客户端既不结束会话，也不是把智能体从一台电脑 “搬到” 另一台电脑。

持久身份还有两个意义：

- **可追责**：外部操作能够追溯到智能体版本、会话、线程、策略和审查记录。部署者仍承担责任，智能体则成为责任链中可识别的一环。
- **可有限授权**：用户或组织仍是授权主体，但可以委派智能体开账户、申请 token、购买域名或部署；支付权限也可以限制到特定商户和金额，而不暴露卡号。

文章引用 RoboBun、Raft 和 Claude Tag，说明不同界面都在把智能体变成 “可直接找到并委派工作的参与者”，而不只是用户账号背后的一次模型响应。

在工具选择上，作者也主张分工：操作系统、编译器、调试器相关工作继续用 CLI；读议题、发消息等云端能力优先通过 MCP。计划中的**Code Mode**则会让受限制的 JavaScript 程序组合获准的 MCP 工具、转换结果并并行调用；这仍是规划功能。

##### 9. 多智能体协作的价值，在于积累经过检验的成果

增加参与者和通信，并不自动提高效率。文章指出，协调式群体和独立并行智能体，可能消耗相近的 token 才得到一个结果；更大的共享编码群体也可能只有较小比例的工作最终被合并。

Tetral 的押注是：**成果进入共享工作区之前，先由其他智能体主动质疑，再由人决定是否接受。**

审查不应只是表示赞同，而要挑战结论、检查证据。原因是：一旦某项成果被接受，它就会成为后续工作的基础；未经检查的错误可能扩散到所有依赖它的工作中。

因此，工作区不仅要保存产出，还要保存足以审查的理由和证据。智能体可以探索许多路径，但累积进展应依赖已验证结果，而不是互相继承未经检验的结论。

长期产品由此也可能产生有价值的评估和训练材料，但前提是保留来源信息、移除私有数据，并由人工识别成功与失败。训练可以减少危险提议，却不能替代执行时的策略、验证、内容检查、独立审查、组织规则和人工升级。

##### 10. 模型越强，瓶颈越可能出现在模型之外

更强的模型能处理更长任务、展开更多并行路径，但每条路径都要消耗现实资源：运行时 CPU 和内存、计算机、文件与网络操作、轨迹存储，以及编辑、构建和测试时间。

作者用工具链说明这一点：文中称，Bun 从 Zig 转向 Rust 改善了内存占用、吞吐和稳定性；TypeScript 的原生 Go 移植是为应对大型代码库的扩展问题，早期构建约快十倍，并显著减少内存使用。

作者自己的开发环境中，一条 Tetral 集成路径需要**7—8 分钟**，完整验证约需**半小时**。即使模型更快地产生代码，编译和验证也不会自动同步提速。

文章最终强调的不是 “推理不重要”，而是：**云智能体的能力上限取决于整条工作链，而不只取决于模型。**要让智能真正扩展，必须同时让工作能恢复、任务能可靠投递、资源能独立调度、外部行动受控，以及成果能够经过验证后持续积累。

## 深度解读-口播（1）

### 2026-09-30 11:37:21

云端智能体的下一个扩展瓶颈，可能不是模型不够聪明，而是模型周围的系统跟不上。Tetral 这篇文章提出的核心判断是：不要把一个智能体等同于一台沙箱计算机。智能体应该是持续存在的服务，沙箱只是它按需使用、用完可以释放的执行资源。

作者最初并不是这样设计的。他把本地编码智能体搬进云端沙箱。每个沙箱里，都运行着一个完整的智能体。用户增加，就增加沙箱。看起来很直接，但问题很快出现。

沙箱需要不断创建、复用和回收。会话历史和调试记录留在沙箱里，排查问题就可能需要进入存有用户私有数据的环境。为了不把模型接口的密钥交给沙箱，还得另建一个网关。

作者发现，团队一直在把职责从沙箱里搬出来，却仍然把沙箱当作智能体容量的基本单位。

问题出在这里：智能体服务和沙箱，遵循不同的扩展规律。智能体服务可以长期运行，在许多会话之间复用计算能力。沙箱则需要隔离，需求可能突然增加，而且经常用完就销毁。把两者绑在一起，就得让一个系统同时应付两种完全不同的负载。

因此，Tetral 的设计是把智能体运行时抽出来。这里的“运行时”，就是负责解释模型输出、推进任务、决定下一步操作的程序。它可以同时处理多个会话，但不拥有会话的身份和持久状态。某个运行时进程消失后，另一个进程应该能够接手。

模型连接和凭证由网关管理。沙箱的创建与命令执行由专门的服务管理。历史和任务状态放在外部存储中。这样，扩展智能体服务，不再意味着必须同步增加同样数量的完整计算机。

不过，拆开系统只是第一步。更难的问题是：进程崩溃之后，接替者怎么知道工作做到哪里了？

假设智能体准备执行一条命令。命令可能还没开始，也可能已经完成，只是确认消息没有回来。如果接替者靠猜，就可能漏掉工作，或者重复产生外部影响。

Tetral 借用了数据库“预写日志”的顺序：先记录，再执行。

运行时提出操作时，先把带有稳定标识的声明交给一个桥接服务。桥接服务检查归属和顺序，把状态变化与回执写入数据库。只有收到确认，运行时才可以继续派发操作。

稳定标识的作用，是让重复提交能够被识别。比如数据库已经保存了声明，但确认消息丢失了。运行时再次提交同一份声明，得到的是原来的回执，而不是新增一份操作记录。同一个标识如果被用于不同内容，则会被拒绝。

执行结果也遵循这个原则。沙箱服务先保存命令输出，运行时再通过桥接服务，把结果正式纳入会话状态。运行时故障，不会自动取消已经开始的命令，也不要求它重新发送那条命令。

这套设计的重点不是保存一个进程，而是保存已经确认的事实，让替代进程可以据此继续工作。

任务投递也要持久化。数据库里既保存输入，也保存对应的队列任务。唤醒工作进程的通知即使丢失，后续轮询仍然能找到任务。同一个线程里的普通输入保持顺序，其他线程则可以并发推进。

这里还有一个重要限制：超时不等于旧进程已经停止。系统必须确认旧运行时的身份已经失效，才能把相应工作交给替代者，避免两个运行时同时推进同一段上下文。

理解了“可恢复”，再看“可并行”。

同一段有序上下文，不能简单地让两个模型请求同时向前推进。因为它们读到相同的起点，却可能产生互相冲突的下一步。因此，并行需要独立的执行路径。

Tetral 区分线程和会话。线程用于同一个任务内部的分工。比如主智能体继续设计，同时创建一个子线程检查实现。子线程可以不继承父线程历史，也可以继承全部保留的历史，或者只继承最近几轮。起始上下文会被明确保存下来。

分出去之后，父子线程各自推进。父线程的新消息不会自动进入子线程。后续沟通必须作为新的有序输入投递。

会话则用于更独立的任务。例如代码实现、文档维护和审计，可能需要不同的上下文、权限和生命周期。它们可以使用同一个工作区的资源，但不应该因此混成一段共同历史。

不过，并行智能体更多，不代表协作一定更好。作者押注的是：成果进入共享工作区之前，先让其他智能体主动挑战结论和证据，再由人决定是否接受。否则，一个未经检查的错误，可能成为后续工作的共同前提。

所以，真正值得积累的，不只是智能体生成的结果，而是经过验证的结果，以及支持结果的理由和证据。

并行扩大了工作量，也扩大了外部风险。这就引出另一条必须独立的边界：授权。

把密钥藏在网关后面，只能防止运行时和沙箱直接持有密钥。它并不能回答：眼前这一次操作，到底该不该使用这项权限？

Tetral 把这个决定放在执行之前，而且放在提出操作的智能体之外。

例如，模型提出一条需要审批的命令。工具门禁先判断适用的策略。如果需要独立审查，此时命令仍然只是提案，还没有进入沙箱执行队列。

审查者会收到操作内容、相关上下文和有效策略。但文件、网页、工具结果，甚至执行模型自己的输出，都只能作为证据，不能变成审查者必须服从的指令。因为这些材料可能包含提示注入，也就是试图诱导模型偏离原定规则的内容。

审查结论也不能直接触发执行。系统先把决定持久保存，再由工具门禁对同一个具体提案重新检查。通过了，才接受为可执行操作；拒绝了，就记录拒绝结果。审查输出不合格，也不能被当成许可。

这里最值得记住的区别是：智能体觉得安全，不等于系统已经授权。

文章最后把视野拉得更远。模型越强，往往意味着更多并行任务、更多文件、更多网络请求，也意味着更多构建和测试。瓶颈可能从推理转移到编译、调度或者存储。

作者举了自己的开发环境：一条集成验证路径可能需要七八分钟，完整验证大约半小时。模型生成代码再快，验证跟不上，整体速度仍然会被限制。

同样，不是每个操作都需要完整沙箱。读文件可能只需要虚拟文件系统。调用云端服务可能只需要受控连接。只有需要执行环境的工作，才值得启动相应的计算机。临时环境可以销毁，但产出的代码、文档和结果必须留在后续环境能够访问的存储里。

Tetral 目前还是一个开放验证中的早期系统，不是已经证明的最终答案。它最有价值的判断是：让运行时可以替换，让工作状态能够延续，让权限和执行受到独立控制。

智能体的扩展，不只是增加模型调用或增加沙箱。真正要扩展的，是一整套能让工作持续、可追踪、可验证，并且安全产生外部影响的系统。
