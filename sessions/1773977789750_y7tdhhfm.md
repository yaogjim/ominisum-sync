**宝玉**

低代码是给人用的机器执行的，Skills 是给 Agent 用的，Agent 和机器执行的；Skills 是一套通用规范，低代码是一个个不同的平台。

这带来两个核心差异：

1\. 进化能力  
低代码只能由人去驱动改进，只要人不主动改进就会越来越难用，使用者和开发者是不同的主体，不具备自我进化能力

Skills 是可以 Agent 自己去使用自己去完善的，相当于程序员不断改进自己的脚本，关键这过程中人只要稍微引导和验证下

2\. 生态  
低代码几乎没有生态，真正的开发者不愿意去用，普通用户用不好，没有统一标准导致编排好的工作流也无法流通。

Skills 的生态正在蓬勃发展，[http://skills.sh](http://skills.sh) 上的已经差不多 9 万了，ClawHub 上的 Skills 前几天才1万多，现在已经快3万了。我分享的 skills 2个月多点已经快 1 万 stars了。

这篇内容的核心观点是：**“Skills 不是低代码的翻版，而是更适合 Agent 时代的一种通用能力封装与调用规范。”**

作者认为，Skills 与低代码的差异主要体现在两点：

1. **进化能力不同**  
   低代码主要是 “人设计、人维护、机器执行”，改进依赖人工推动；  
   Skills 则是 “给 Agent 用、也可由 Agent 参与改进”，因此理论上具备更强的自我迭代能力。

2. **生态基础不同**  
   低代码往往平台割裂、标准不统一，工作流难流通；  
   Skills 若形成通用规范，则有机会像操作系统上的 App 一样，成为 Agent 能力扩展的基础生态。

作者进一步用 “汽车刚出现时不如马车” 来类比当前 Skills 的不成熟，强调应从长期视角看待其潜力，而不是只盯着当下稳定性、收费模式、知识产权保护等现实问题。

#### 辩证分析

##### 观点成立的部分

###### 1. 对 “Agent 可自我增强” 的判断有前瞻性
这是全文最有价值的判断。  
低代码的典型范式是：人先把流程抽象出来，再交给系统执行；而 Skills 面向的是 Agent 的调用、组合、试错与重写。只要 Agent 的规划、反思、测试、验证能力持续提升，Skills 的确可能成为一种**可被机器持续消费和改写的能力单元**。

这意味着它和传统低代码最大的差别，不只是 “用户不同”，而是**反馈闭环不同**：
- 低代码的闭环是 “人发现问题 - 人修改流程 - 机器执行”
- Skills 的闭环可能变成 “Agent 发现问题 - Agent 重组 / 补全 Skill - 人做监督与验收”

如果这个闭环成立，Skills 的迭代速度会明显快于低代码。

###### 2. 对 “通用规范优于平台孤岛” 的判断是合理的
作者强调低代码是一个个平台，而 Skills 更像一套通用规范，这一点抓住了关键。  
历史上，平台型生态容易形成局部繁荣，但可移植性差；规范型生态一旦建立，外部开发者、工具链、市场与分发体系才更容易形成网络效应。

换句话说，**低代码更像封闭园区，Skills 更像可组合协议**。  
如果未来不同 Agent 框架、模型平台、开发环境都能读取和执行同一类 Skill 描述，那么它的生态上限确实可能高于今天常见的低代码产品。

###### 3. “先弱后强” 的技术演化判断并不荒谬
作者用 “汽车初期不如马车” 来回应质疑，这种类比虽然有煽动性，但并非没有道理。  
很多基础技术在早期都表现出：
- 不稳定
- 成本高
- 场景窄
- 体验差

但只要它满足一个更根本的趋势，例如更强扩展性、更低边际复制成本、更高自动化潜力，就可能在中长期反超。  
从这个角度看，Skills 的确符合 “早期粗糙、长期可能爆发” 的技术扩散特征。

---

##### 观点不足或值得质疑的部分

###### 1. “低代码几乎没有生态” 这个表述过于绝对
这是原文中最明显的薄弱点。  
评论区也指出，Power Platform、Salesforce 周边已经形成了大量 ISV、实施商、咨询服务和模板市场。严格说，低代码不是 “没有生态”，而是它的生态更偏向：
- 企业销售驱动
- 项目交付驱动
- 平台绑定驱动
- 非开发者友好但开发者不一定热爱

所以更准确的说法应是：  
**低代码存在生态，但不是开放型、开发者主导型、跨平台流通型生态。**

如果把 “没有生态” 改成 “生态类型受限”，论证会更严谨，也更有说服力。

###### 2. “Skills 可自我进化” 仍高度依赖底层模型可靠性
反对者引用 “每个环节稳定性 90%，十个环节整体稳定性只有 34.9%”，这个质疑很关键。  
因为 Skill 的可组合性越强，链路就越长；链路越长，误差传播越严重。  
所以 Skills 虽然在理念上适合 Agent 自我迭代，但在工程现实里，会受制于：
- 模型调用的不稳定性
- 工具接口的语义歧义
- 环境状态不可控
- 任务验证成本高

也就是说，**“能自我改进” 不等于 “能稳定自我改进”**。  
如果没有强验证、回滚、沙箱、版本管理和测试机制，所谓自我进化很可能演变为自我污染。

###### 3. “生态繁荣” 目前更多是数量信号，不等于质量信号
文中提到多个平台上 Skill 数量快速增长、GitHub stars 很高，这说明关注度在上升，但不能直接证明生态已经成熟。  
数量增长只能说明：
- 参与门槛低
- 传播热度高
- 创作者兴趣强

却不能说明：
- Skill 质量是否稳定
- 是否存在复用率高的 “头部标准件”
- 是否有成熟的调用规范和兼容性
- 是否形成付费模式与持续维护机制

换句话说，**“很多 Skill” 不等于 “有可持续生态”**。  
生态是否成立，最终还得看复用深度、商业闭环、标准统一程度，以及真实生产场景中的留存。

###### 4. 商业化与知识产权问题是关键短板，不是边角问题
评论里关于收费、授权、配置位置、知识产权保护的追问，非常切中要害。  
因为 Skill 一旦可复制、可分发、可调用，就会立刻面临几个现实问题：
- 如何收费：按下载、按调用次数、订阅制、托管服务？
- 如何防盗用：本地分发几乎天然难保护
- 如何交付：配置写死在本地还是运行在远程？
- 如何归属：谁拥有 Skill 的逻辑与数据资产？

这意味着未来真正能跑通的，很可能不是 “纯 Skill 文件市场”，而是：
- `Skill as a Service`
- 托管执行
- 云端鉴权
- API + Skill 描述混合模式

也就是说，**商业模式可能最终会把 “开放规范” 重新拉回 “平台化托管”**。  
这是 Skills 长期发展中必须面对的张力。

#### 我的评价与判断

##### 总体评价
我认为这篇内容的**方向判断是有洞见的，但论证方式带有明显的立场先行色彩**。

它最有价值的地方，不是 “低代码不行”，而是指出了一个更本质的范式变化：

> 未来的软件能力单元，不再只是给人配置、给机器执行，而是越来越多地变成给 Agent 调用、组合、重写、验证。

这是一个非常重要的判断。它抓住了 Agent 时代和传统自动化时代的分水岭。

##### 我对其核心命题的判断

###### 1. “Skills 会成为 Agent 时代的重要基础设施”—— 大概率成立
因为 Agent 如果没有外部能力封装，就只能停留在对话层；  
而一旦有规范化的 Skill、工具、接口、权限、状态管理，它才能真正进入工作流执行层。  
所以 Skills 或类似 Skills 的东西，几乎是 Agent 落地的必需品。

###### 2. “Skills 会替代低代码”—— 未必成立
更可能的结果不是替代，而是分层共存：
- **低代码**继续服务企业内部流程编排、审批、报表、集成等场景
- **Skills**成为 Agent 执行复杂任务时的能力插件层
- 二者未来甚至可能融合：低代码负责可视化流程，Skills 负责能力调用和智能补全

所以更准确的判断不是 “谁淘汰谁”，而是**谁掌握更高频、更开放、更可复用的任务入口**。

###### 3. “当前对 Skills 的批评只是短期问题”—— 这点不能过度乐观
稳定性、验证、付费、标准化、知识产权，这些不是简单的 “成长烦恼”，而是决定它能否从玩具走向基础设施的核心门槛。  
如果这些问题解决不好，Skills 很可能停留在 “开发者展示作品” 和 “实验性自动化” 的阶段，而无法成为真正可靠的生产力系统。

#### 高价值信息提取

##### 1. 最值得记住的核心概念
- **低代码**：给人配置、机器执行
- **Skills**：给 Agent 调用，且可能被 Agent 改写和增强
- 真正的差异不在 “界面形式”，而在**谁是主要使用者、谁构成迭代闭环**

##### 2. Skills 相比低代码的潜在优势
- 可被 Agent 自动调用与组合
- 有机会形成跨平台、跨框架的通用规范
- 更适合作为 Agent 的能力插件层
- 在理想条件下具备 “半自动自我进化” 潜力

##### 3. Skills 能否成立的四个关键条件
- **标准化**：统一描述、输入输出、权限和依赖规范
- **可靠性**：要能测试、回滚、验证、监控
- **商业化**：要解决收费、授权、托管和分发
- **生态质量**：要从 “数量多” 走向 “复用高、兼容好、维护稳”

##### 4. 对行业观察最有启发的一点
未来竞争的核心，可能不是 “谁的模型更强”，而是：
- 谁拥有更丰富的 Skill 生态
- 谁能让 Agent 更稳定地调用这些 Skill
- 谁能建立面向 Agent 的标准能力市场

##### 5. 一句话判断
**这不是 “低代码 vs Skills” 的简单替代关系，而是 “人驱动自动化” 向 “Agent 驱动能力编排” 迁移的信号。**
