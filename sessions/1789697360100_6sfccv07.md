## 正文

#### 查询优化器到底有多好？

Leis 等人在 2015 年提出了这个确切的问题。然后，他们在 10 年后再次提出了这个问题。

尽管自他们最初的探索以来，十年间涌现了大量研究，他们发现查询优化器仍然有很多不足之处。

当我第一次了解到这一点时，我感到很惊讶。一个 Postgres 数据库应该对其表中的内容了如指掌，不是吗？这能有多难呢？

事实证明：极其困难。事实上，查询优化器需要执行的一项特定任务——连接顺序优化——已知是 NP-hard 问题。

所以查询优化器很难。不那么难的是验证优化器选择的查询计划是好是坏。简而言之，好的查询优化器产生运行快速的计划，差的则产生缓慢的计划。语言模型特别擅长学习如何完成输出易于验证的任务。因为只有一个优化轴——查询的执行时间——这个问题完美地简化为强化那些引导模型产生更快查询计划的行为。

以下是我进行的一项实验的详细分析，该实验旨在探索一个问题：一个小型开放权重模型能否通过监督微调（SFT）和智能体强化学习（RL）进行后训练，从而产生优于 Postgres 默认计划的查询计划？

对我们问题的回答是响亮的“是”。亮点包括：

- 在 113 个连接密集型查询上实现了 44.7%的延迟降低，而一个 4B 模型最初甚至无法为其中 99 个查询生成查询计划
- 构建了一个 Postgres 测量装置，以最小化并发容器间 Linux 页面缓存争用噪声
- 设计了一种自定义 GRPO 变体，用于在本质嘈杂的环境中为 RL rollout 评分
- 将 RL 拆分到两台机器上：vLLM 和训练器运行在租用的 2x H100 节点上，四个 Postgres 容器则运行在我的桌面上
- 在五百条 GPT-6 Astra 代理轨迹上运行离策略蒸馏

让我们从头开始。

考虑以下 IMDb 数据集的片段：

假设我试图回答这个问题：“哪些日本公司在 2000 年代发行的作品最多？”我们可能会编写以下查询：

```sql
SELECT cn.name,

       COUNT(*) AS titles

FROM   title AS t,

       movie_companies AS mc,

       company_name AS cn

WHERE  t.id = mc.movie_id

  AND  mc.company_id = cn.id

  AND  cn.country_code = '[jp]'

  AND  t.production_year BETWEEN 2000 AND 2009

GROUP  BY cn.name

ORDER  BY titles DESC

LIMIT  10;
```

运行此查询会输出 10 家日本公司及其在 2000 年至 2009 年间关联的标题数量，按从高到低排序。

但 Postgres 是如何得到这些结果的？

Postgres 为我们获取这些数据所采取的路径并非必然，它与我们所说的选择性谓词（即 `WHERE` 子句中的过滤条件）密切相关。

为了说明这一点，让我们想象一下去掉日本公司筛选和日期范围筛选后的同一查询：

```sql
SELECT cn.name,

       COUNT(*) AS titles

FROM   title AS t,

       movie_companies AS mc,

       company_name AS cn

WHERE  t.id = mc.movie_id

  AND  mc.company_id = cn.id

GROUP  BY cn.name

ORDER  BY titles DESC

LIMIT  10;
```

`mc` 只能通过 `mc.company_id = cn.id` 与 `cn` 连接，而 `t` 只能通过 `t.id = mc.movie_id` 与 `mc` 连接。

##### Estimating, not counting

Postgres 在这里处境艰难。人们可能会合理地认为，它只需统计基数，然后选择能够最小化传递到后续连接的行的数量的计划即可。

但这意味着 Postgres 可以在查询规划期间计算基数。它做不到。为了知道这一点，它需要实际运行每个连接并计算结果行数。这违背了快速查询优化器的初衷。查询优化器的目标并不是在成本最小化上做到精确……它的目标是在多种类型的查询中做到足够好。

相反，Postgres 使用统计信息来估算基数。规划器查询 `pg_statistic` 表，获取每列的常见值及其频率，以及其余值的直方图。当你加上连接时，事情会变得稍微复杂一些。Postgres 不知道一个表中的行在另一个表中是如何分布的。为了解决这个问题，它假设第一个表中某个给定值的频率可以直接应用到第二个表上。这就是我之前提到的均匀分布假设。

拖动滑块以提高日本公司的产出。注意 Postgres 的估计值是静态的，而实际行数会受到影响。

早期连接中的一个错误估计可能会在剩余的连接树中级联，从而破坏所有其他估计。

#### How to steer an elephant

Postgres 总是选择成本最低的计划，而我们无法在不修改其源代码的情况下更改其成本模型，那么我们究竟如何才能引导它选择成本更高但不同的计划呢？

Enter [pg\_hint\_plan](https://github.com/ossc-db/pg_hint_plan).

`pg_hint_plan` 是一个极其简洁的第三方扩展：只需在 SQL 语句上方以注释形式添加结构化的“提示”，你就可以引导 Postgres 采用提示中提供的指令所对应的计划。例如：

```sql
/*+
  HashJoin(a b)
  SeqScan(a)
*/
EXPLAIN SELECT *
  FROM pgbench_branches b
  JOIN pgbench_accounts a ON b.bid = a.bid
  ORDER BY a.aid;
```

```sql
QUERY PLAN
---------------------------------------------------------------------------------
 Sort  (cost=31465.84..31715.84 rows=100000 width=197)
   Sort Key: a.aid
   ->  Hash Join  (cost=1.02..4016.02 rows=100000 width=197)
         Hash Cond: (a.bid = b.bid)
         ->  Seq Scan on pgbench_accounts a  (cost=0.00..2640.00 rows=100000 width=97)
         ->  Hash  (cost=1.01..1.01 rows=1 width=100)
               ->  Seq Scan on pgbench_branches b  (cost=0.00..1.01 rows=1 width=100)
(7 rows)
```

该提示要求使用 `HashJoin` 来连接 `pgbench_accounts` 和 `pgbench_branches` ，并对 `pgbench_accounts` 表执行顺序扫描；实际的查询计划完全遵循了这一要求。

#### Formulating our problem

> 语言模型能否学会生成能够产生更优查询计划的提示？

##### Useful research

为什么这可能是一个值得解决的问题？

我最初的想法是向模型提供查询语句以及 Postgres 规划器所拥有的完全相同的信息集。这相当于看看我们能否构建一个更好的基数估计器。我得出结论，这不是一条值得探索的路径；我们将要对抗的是数十年的基数估计研究。此外，仅推理延迟本身就远远超过与 Postgres 超快查询优化器相比所能学到的任何有用性。

第二个想法——也是我认为正确的表述——在于一种特定的数据库使用模式：重分析型工作负载。如果查询使用次优的默认 Postgres 计划运行数千次，那么效率收益就被白白浪费了。相反，可以训练一个模型来找到运行特定查询的更好方式。训练过程可能需要预先执行该查询数十到数百次，但在该查询的所有运行中分摊的成本将大幅降低。

目标不是试图在一次性查询的时间/效率帕累托前沿上击败 Postgres，但我们或许能够在反复运行的查询上击败它。

#### A model and its harness

我决定从一个小型 4B 模型开始，因为这样在我家里的 2 块 RTX 3090 设备（我亲切地称之为 FLOPper）上训练和推理最为容易。

模型确定后，我构建了一个轻量级 agent 框架 `qo-agent` ，用于编排提示生成。它被赋予了以下六种工具：

1. `inspect_relation` — 列出表的列及其类型和可空性、索引定义以及估算的行数和字节数
2. `get_column_stats` — 获取关系的 1-8 列的 Postgres 规划器统计信息
3. `get_plan` — 获取默认计划的估算值或提交候选者的存储计划
4. `evaluate_candidate` — 验证提议的计划操作，然后执行它以进行计时/计划诊断
5. `keep_default` — 将 Postgres 的默认计划本身作为候选返回，并结束搜索
6. `finish` — 接收提交的候选 ID 或默认计划作为输入，并结束搜索

为了利用结构化输出，代理被指示生成 [`PlanAction`](https://github.com/polyphilz/qorl/blob/main/src/qorl/plans/schemas.py#L553) JSON 对象。随后对 `evaluate_candidate` 的调用将 `PlanAction` 对象编译为提示，并将其前置到原始查询中。

A sample agent trajectory:

```sql
Agent → get_plan("default")
Tool  ← Default plan: (t ⋈ mc) ⋈ cn, hash joins, estimated rows per node
 
Agent → evaluate_candidate({
          "leading": { "left": { "left": "cn", "right": "mc" }, "right": "t" },
          "joins": [{ "relations": ["cn", "mc"], "force": "hash" }]
        })
Tool  ← c1 · valid · novel plan · 118 ms · 0.91× default · 2 attempts left
 
Agent → evaluate_candidate({
          "leading": { "left": { "left": "t", "right": "mc" }, "right": "cn" },
          "joins": [{ "relations": ["t", "mc"], "force": "nestloop" }],
          "scans": [{ "relation": "mc", "force": "index" }]
        })
Tool  ← c2 · valid · novel plan · 87 ms · 1.24× default · 1 attempt left
 
Agent → evaluate_candidate({
          "leading": { "left": { "left": "t", "right": "mc" }, "right": "cn" },
          "joins": [{ "relations": ["t", "mc"], "force": "hash" }]
        })
Tool  ← c3 · valid · novel plan · 100 ms · 1.08× default · 0 attempts left
 
Agent → finish({ "selected_candidate_id": "c2" })
Tool  ← Finished · selected c2
```

一个示例轨迹，其中代理最多可以提交三个候选方案。

##### Train time, test time

由于其规模，CEB 非常适合用于训练模型。JOB 则用于验证模型的性能。

你可能会想，在 IMDb 上同时进行训练和测试是否合理。如果效果很好，模型岂不是只是很好地学习了这个特定的数据库？

我认为这正是关键所在。我们希望模型能够很好地学习 IMDb。根据我们的问题表述，如果这个智能体持续被用于某家公司在其特定数据库上的分析工作负载，我们就不需要泛化到所有数据库。

真正的问题在于确保我们在基于 CEB 训练时不会过度拟合 JOB 查询模板。模型应该以一种方式学习 IMDb，即对于任何查询，即使是它以前未见过的结构化查询族，它仍然能够生成良好的计划。在实践中，这意味着我们需要修剪与任何 JOB 查询具有相同形状的 CEB 查询。

#### How to muffle an elephant

First, some facts:

- FLOPper 配备 16 个物理核心的 CPU、64 GB 内存和 2 TB NVMe SSD
- 我们使用的 IMDb 数据切片在磁盘上占用 8.5 GB
- Postgres 会将查询执行期间检索到的数据页缓存到缓冲区中
- 操作系统有自己的文件系统缓存，在下一层级执行相同的操作

如果我们在 Postgres 上连续运行完全相同的查询 20 次，每次运行所需的时间并不会相同。在日常工作中，这没什么大不了的。但整个论文以及训练过程本身，都依赖于衡量某种查询执行方式是否比 Postgres 默认方式更快。这意味着我们需要尽一切可能消除 Postgres 中的噪声。

首先，我需要了解 Postgres 查询执行到底有多嘈杂。

我从在实验工作流中构建“校准”功能开始。校准过程很简单：运行 个基于 Postgres 镜像构建的 Docker 容器，每个容器分配固定的 CPU 核心和 RAM 配额。我将 设置为起始值；更低的值可能会使后续训练过于缓慢，而更高的值可能导致更多的 CPU 争用，这意味着更多的噪声。每个容器分配 4 个核心，内存上限为 8 GB。

启动时，每个容器使用相同的设置初始化 Postgres，并加载 IMDb 数据。然后校准打开一个大小为四的线程池，并将全部 113 个查询推送到一个共享队列中。每当一个容器完成对一个查询的测量，它就从队列中取出下一个查询。

实际的测量过程分为两个阶段：

1. 多次运行查询以“预热”它
2. 然后再运行查询 20 次，并记录每次的执行时间

那么，预热查询意味着什么？我们需要回顾一些操作系统基础知识来理解。

每当 Postgres 执行查询时，它会向操作系统（在我们的场景中是 Linux）请求数据页。Linux 首先检查自己的文件系统缓存，即页缓存。如果这些页存在，Linux 就将它们发送过来；否则，它会从磁盘读取这些页，将其存储在自己的缓存中，然后再发送过来。Postgres 则会将接收到的页保存在自己的 `shared_buffers` 缓存中，以便于重复使用。当 `shared_buffers` 开始溢出时，Postgres 会驱逐页面。如果它再次需要这些页，就必须再次向 Linux 请求。

每当 `shared_buffers` 中发生一次针对某页的缓存命中时，Postgres 就会递增一个名为“共享命中块”（SHBs）的计数器。如果它不得不向 Linux 请求，则会递增“共享读取块”（SRBs）。

```json
{

  "Plan": {

    "Node Type": "Aggregate",

    "Shared Hit Blocks": 1800786,

    "Shared Read Blocks": 52990,

    ...

  },

  "Execution Time": 189.2,

  ...,

}
```

这些计数器让我们对查询的“预热程度”有了一定概念。每次预热运行后，我们会将其命中次数和读取次数与上一次运行进行比较。如果两者相差在 2%以内（且执行计划没有变化），我们就认为该查询已预热，并开始测量。一个查询至少需要两次预热才能有可比较的数据，并且无论怎样最多只进行五次预热。其思路是，如果计数器不再变化，就可以认为数据已经稳定，在 20 次测量期间缓存抖动也会降到最低。

查询 A 通过 Linux 调用填充 `shared_buffers` 。查询 B 需要不同的页面，在此过程中会将查询 A 的页面从 `shared_buffers` 中逐出。当 A 再次运行时，被逐出的页面会被计为读取。

##### To fool an agent

请耐心听我稍微跳过一些内容，以便更详细地说明我们究竟需要测量什么。

为了在实际代理运行过程中去噪，我不能只运行一次代理提出的计划。相反，我按顺序运行了三组交错的 `(candidate, default)` 对。选择三组在某种程度上是随意的，既能提供一定的变异性，又足够小，以免代理评估运行大部分时间都花在 Postgres 上。一旦获得了三个候选/默认执行时间元组，就分别取三个候选和三个默认值的中位数，并以它们的比值来表示，以确定最终的加速或减速。如果两个中位数相差小于任意设定的 5%，则视为持平。在该持平区间之外，候选方案可以被判定为加速或减速。

现在让我们回到之前的 `job-13b` 示例。我们在一个簇中有 14 次执行，在另一个较慢的簇中有 6 次。取三次测量的中位数这种策略听起来不错，但直到你意识到，理论上如果三次测量中至少有两次落在那个“较慢”的簇中，中位数就会偏向于出现频率较低的较慢簇。

想象一个候选计划，其执行情况与默认计划完全相同。两者之间不存在真正的差异，因此正确的奖励应为零。从我们观察到的 20 次测量中，为“候选”计划抽取三次计时，为“默认”计划抽取三次计时。从 20 次中抽取三次有 种方式；对于 `job-13b` ，其中有 230 种方式包含至少两次慢速运行，因此一侧的中位数有 \~20% 的概率落在慢速簇中。

这就是一个完全虚幻的 14-26% 加速或减速，而我们会在 \~20% 的情况下将其作为信号展示给模型。危险！

##### Tuning Postgres

我重点关注了 Postgres 暴露的两个与内存相关的设置：

1. `shared_buffers` 决定了 Postgres 可以在自己的缓存中保留多少数据库内容
2. `work_mem` 决定了单个排序/哈希操作在溢出到磁盘之前可以获取多少内存

令人惊讶的是， `work_mem` 对噪声完全没有影响，而 `shared_buffers` 承担了全部作用！

在 2 GB 的 `shared_buffers` 下，中位数查询在预热结束时其 SRB 计数器恰好为零：其工作集完全驻留在 Postgres 自身的缓存中。无操作错误率大约下降了 4 倍，第 90 百分位查询从 13%–20% 的时间被误导变为几乎从不被误导。我们的双簇查询 `job-13b` 的 CV 从 10.3% 降至 0.9%，所有 20 次运行彼此之间的差距都在 7 毫秒以内。

我在项目的剩余部分锁定了 2 GB 的 `shared_buffers` 和 4 MB 的 `work_mem` 。

#### 通过监督微调进行离策略蒸馏

我首先需要让这个 4B 模型学会 `qo-agent` 测试框架的“语言”。之后我才会让它擅长查询优化。

离策略蒸馏非常巧妙的一点是，它不需要大量数据就能很好地工作。因为每个示范都提供了数千到数万个 token 预测，我们学生模型的权重能够快速适应。

但这些都忽略了一个事实：我们已经拥有了最好的老师——更聪明、更大的模型。

策略很简单：通过让一个聪明的模型运行 `qo-agent` 框架来生成大量轨迹，然后将这些轨迹蒸馏到我们的学生 4B 模型中。

我们的 4B 模型有 46.6 亿个可调参数。如果我们想在 SFT 期间一次性更新所有这些参数，就需要一块至少有 64 GB 显存的 GPU。我想先在自己的消费级 RTX 3090 上验证我的假设，每块显卡只有 24 GB 显存，所以我在这里需要一种更参数高效的方法。

##### 设计每次 rollout 的奖励和相对优势

最初的奖励算法很简单：

加速比的计算方式为：三次默认计划测量值的中位数除以三次候选计划测量值的中位数。

对于每一个被评估为无效的候选计划，我们从加速比的自然对数中减去 0.1。如果该次 rollout 产生的计划与默认 Postgres 计划具有相同的指纹，则再减去 0.05。最后，如果轨迹最终完全没有产生任何有效候选计划，则从奖励中直接减去 3，以替代上述 0.1 或 0.05 的扣减。

## 结构化（1）

### 2026-09-18 02:25:59

#### 用 4B 模型为 PostgreSQL 寻找更快的查询计划

作者通过监督微调（SFT）和强化学习（RL），训练一个 40 亿参数的开放模型为 PostgreSQL 生成查询计划提示。在 113 条复杂连接查询上，最终计划平均降低**44.7% 延迟**，相当于约**1.81 倍速度、快 81%**；但这一方案主要适用于会被反复执行的分析型查询，而非取代 PostgreSQL 对一次性查询的快速规划。

##### 查询优化难在搜索空间巨大

SQL 只描述 “要什么结果”，数据库还要决定 “怎样执行”，包括：

- 表按什么顺序连接；
- 每次使用哈希连接、合并连接还是嵌套循环；
- 每张表使用顺序扫描、索引扫描、仅索引扫描还是位图扫描。

即使只有 3 张表，综合连接顺序、连接方向、连接算法和扫描方式，也可能产生**4,608 种执行方案**；表越多，候选数量越呈组合式增长。尤其是 “连接顺序优化” 本身属于**NP-hard 问题**，无法简单穷举。

连接顺序又会直接影响中间结果大小。例如，对 200 万行电影公司关系表，先按 “日本公司” 过滤，第一次连接约产生 10 万行；先按 “2000 年代作品” 过滤，则约产生 40 万行，后者需要向下一步传递约**4 倍数据**。

##### PostgreSQL 只能估算，误差还会逐层放大

优化器无法先执行所有候选计划再比较，因为这会让规划成本高得不可接受。PostgreSQL 因此依据`pg_statistic`中的常见值、频率和直方图来估算行数，也就是 “基数”。

难点在于，它通常不知道不同表、不同列之间的真实关联，只能采用近似的均匀分布等假设。早期连接一旦估错，中间结果的估算误差就会沿连接树不断传递，最终可能选中成本估算较低、实际却很慢的计划。

作者据此认为，这类任务适合强化学习：计划好坏虽然难以提前推导，却很容易通过实际执行时间来验证。

##### 不修改 PostgreSQL，也能控制执行计划

PostgreSQL 默认总会选择自身成本模型认为最便宜的计划。作者使用第三方扩展**`pg_hint_plan`**，通过 SQL 注释形式的提示指定：

- 表的连接顺序；
- 使用哪种连接算法；
- 使用哪种扫描方式。

例如，可以强制两张表采用哈希连接，并要求其中一张表顺序扫描。这样，语言模型不必生成完整的底层执行器，只需生成结构化提示，引导 PostgreSQL 采用不同计划。

##### 正确目标是优化 “反复运行的查询”

作者没有尝试让模型像 PostgreSQL 一样，在极短时间内为任意一次性查询制定计划。模型推理和候选测试本身较慢，很难在这类场景中胜出。

实验针对的是**重分析型工作负载**：同一条或同类查询可能执行数千次。即使前期需要运行几十到几百次来寻找好计划，只要后续反复复用，训练和搜索成本仍可被长期收益摊薄。

因此，模型也不必泛化到所有数据库；它可以专门学习某家公司某个固定数据库的数据特征。

##### 4B 模型通过工具反复提出并测试计划

作者选择小型 4B 模型，以便在两张 RTX 3090 上进行训练和推理，并构建了名为`qo-agent`的轻量级智能体框架。模型可以调用六类工具：

- 查看表结构、索引和估算行数；
- 获取列统计信息；
- 查看默认计划或候选计划；
- 执行并计时候选计划；
- 保留 PostgreSQL 默认计划；
- 从候选中选择最终方案。

模型以 JSON 形式输出计划动作，再被转换成`pg_hint_plan`提示。一次典型搜索中，模型会先查看默认计划，然后尝试有限数量的候选方案，根据实测速度继续调整，最后选择最佳候选；如果都不好，也可以直接保留默认计划。

##### 训练集和测试集按 “查询结构” 隔离

测试采用**Join Order Benchmark（JOB）**，包含**113 条查询、33 种模板**，重点考察多表连接。训练则使用规模更大的**Cardinality Estimation Benchmark（CEB）**。

两者都基于 IMDb 数据库，这在作者看来不是缺陷，因为目标本来就是让模型熟悉某个具体数据库。真正需要防止的是：模型见过测试查询的同类连接结构，只是在记忆答案。

为此，作者把查询表示为 “连接拓扑”—— 以去除别名后的表为节点、连接关系为边，并忽略过滤条件。然后检查 CEB 与 JOB 是否存在相同拓扑；结果没有重叠，因此无需额外删除训练样本。这用于检验模型能否处理从未见过的连接结构，而不仅是记忆模板。

##### 最大工程难点之一是执行时间的噪声

强化学习依赖 “候选计划到底快不快” 的奖励，但数据库计时会受两层缓存影响：

- PostgreSQL 自己的`shared_buffers`；
- Linux 文件系统的页面缓存。

同一个查询连续执行 20 次，时间也可能明显不同。实验中的`job-13b`在较小缓存下出现两个速度簇：

- 14 次耗时 186～204 毫秒；
- 6 次耗时 227～253 毫秒，慢约 14%～26%。

如果候选计划和默认计划其实完全相同，随机抽样仍可能让其中一方更多落入慢速簇，从而制造虚假的加速或减速信号。作者估算，在该查询上，奖励被误导的概率约为**40%**，足以严重干扰强化学习。

##### 通过预热、交错测量和扩大缓存降低误判

作者建立了 4 个 PostgreSQL 容器，每个分配 4 个 CPU 核和 8 GB 内存，并采用以下测量流程：

1. 反复执行查询进行预热；
2. 比较相邻执行的缓存命中块和读取块；
3. 两者变化小于 2% 且计划不变时，认为预热完成；
4. 再执行 20 次用于校准。

智能体实际评估候选时，则交错运行三组 “候选计划 — 默认计划”，分别取三次执行时间的中位数，再计算比值；差异小于 5% 时判定为持平。

进一步调参发现：

- 将`shared_buffers`从**128 MB 提高到 2 GB**，效果最明显；
- 将`work_mem`从 4 MB 提高到 32 MB，对噪声几乎没有影响。

使用 2 GB `shared_buffers`后：

- 平均 “空操作误判率” 由约**5%～5.4%**降至**1.2%～1.8%**；
- 第 90 百分位查询的误判率从**13%～20%**降至接近 0；
- `job-13b`的波动系数从**10.3%**降至**0.9%**；
- 全部查询的校准时间也从约 95 秒降至 60 秒。

这说明扩大 PostgreSQL 自身缓存、减少页面在 PostgreSQL 与 Linux 之间反复读取，是获得可靠训练奖励的关键。

##### 训练与最终结果

作者还采用了以下训练和部署设计：

- 用约**500 条 GPT-6 Astra 智能体轨迹**进行离策略蒸馏，即让小模型学习另一个模型生成的历史轨迹；
- 设计自定义**GRPO**强化学习变体，以适应带噪声的数据库计时；
- 将强化学习拆到两台机器：租用的**2×H100**节点运行 vLLM 和训练器，作者本地机器运行 4 个 PostgreSQL 容器负责实测。

最终，这个起初在 113 条 JOB 查询中有**99 条甚至无法生成查询计划**的 4B 模型，经后训练后使整体延迟降低**44.7%**。实验的核心结论不是 “小模型全面替代 PostgreSQL 优化器”，而是：对于固定数据库中大量重复执行的复杂分析查询，小模型可以通过实际执行反馈，找到比默认优化器更好的计划，并把前期搜索成本分摊到后续运行中。

## 深度解读（1）

### 2026-09-18 02:45:42

#### 这不是让 4B 模型取代 Postgres，而是把查询优化变成可摊销的实验搜索

文章最重要的贡献，并非“小模型战胜了成熟数据库优化器”，而是**重新划定了问题边界**：不要求模型在每条临时查询上即时给出最优计划，而是针对会反复执行的分析型查询，允许它预先试跑多个方案，再把搜索成本摊薄到未来数千次执行中。

Postgres 必须在毫秒级完成规划，只能依靠列统计、分布独立等近似来估算中间结果规模；一旦早期基数估错，后续连接顺序和算法选择都会被带偏。模型则通过 `pg_hint_plan` 提出连接顺序、扫描方式和并行策略，直接执行并测量。这其实不是用 AI 替代传统优化器，而是在它外面增加一个**面向固定工作负载的经验型元优化器**：Postgres 提供可靠默认方案，模型负责寻找少数值得固化的例外。

##### 真正困难的不是生成计划，而是建立可信的反馈

查询执行时间看似是天然、可验证的奖励，实验却说明：**可测量不等于可可靠优化**。

缓存抖动曾让完全相同的计划出现两簇延迟，导致“候选方案和默认方案其实相同”时，奖励仍可能被误判。作者最终把 `shared_buffers` 从 128MB 提高到 2GB，配合预热、候选与默认计划交错执行、取中位数和 5% 平局区间，才显著降低噪声。

强化学习的相对评分也有类似陷阱：普通 GRPO 会在一组全部差于 Postgres 的方案中，奖励“相对没那么差”的方案。作者因此把优势锚定到默认计划，只有真正超过基线的 rollout 才获得正向强化。这个经验可以迁移到更广泛的智能体系统：**有客观结果还不够，评估器必须抗噪，并且奖励要锚定真实业务基线，而不是同批候选的平均水平。**否则模型很可能学会利用测量误差，或稳定地产生“局部较优、绝对无用”的行为。

##### “快 81%”成立，但需要准确理解

最终的 1.81 倍加速，来自每个查询运行三条轨迹、最多评估 15 个候选，再根据反馈选择最佳方案；它对应约 **44.7% 的延迟下降**。模型自己在单条轨迹中的最终选择只有 1.40 倍几何平均加速，工作负载总体加速为 1.24 倍。因此，最强结果更接近“模型引导的多候选搜索系统”，而不是 4B 模型一次推理就能稳定给出快 81% 的计划。

适用边界也很清楚：训练和测试都基于 IMDb 数据库，虽然查询连接拓扑没有重叠，却尚未证明能跨数据库、数据分布或持续变化的业务环境泛化。模型学到的主要收益模式也相当集中——调整连接顺序、修复单个扫描方式、启用并行——这意味着还需要与更简单的启发式搜索、贝叶斯优化或 bandit 方法比较，才能确认语言模型贡献了多少不可替代的能力。

更现实的产品机会，是面向**稳定、重复、执行昂贵的 BI 和报表工作负载**：后台持续试验候选计划，只在超过安全阈值后固化提示，数据分布变化时自动重新验证，并始终保留默认计划作为回退。其价值不在于宣称通用优化器被替代，而在于证明了一类可行架构：**小模型负责缩小搜索空间，真实系统负责裁决，默认方案负责兜底。**这可能比追求一个无所不知的通用智能体更早产生可靠收益。

## 口播总结（1）

### 2026-09-18 10:04:17

一个只有四十亿参数的小型开放权重模型，能不能为数据库找到比 Postgres 更快的查询计划？这项实验给出的答案是肯定的。在一百一十三条复杂查询上，经过多次搜索并按实测结果挑选候选计划，最终执行速度达到 Postgres 默认方案的一点八一倍，相当于延迟下降百分之四十四点七。

不过，这不是要全面替代 Postgres 的优化器。它针对的是会被反复执行的分析型查询。模型可以事先花时间尝试不同方案，再把优化成本分摊到未来成千上万次运行中。

查询优化为什么这么难？可以看一个简单例子。假设数据库要找出，二零零零年代发行作品最多的日本公司。查询涉及作品、公司，以及作品和公司之间的关联表。

如果十万家公司中，只有百分之五来自日本，而一百万部作品中，有百分之二十来自二零零零年代，那么先按日本公司过滤，再连接关联表，中间结果大约是十万行。反过来，先按年代连接作品，中间结果大约是四十万行。两种写法最终答案相同，但后一种连接顺序要处理四倍的数据。

而连接顺序只是开始。每次连接还可以选择哈希连接、合并连接或嵌套循环。每张表又可以使用顺序扫描、索引扫描、仅索引扫描或位图扫描。即使只有三张表，也可能出现四千六百零八种执行方式。表一多，搜索空间就会组合爆炸。连接顺序优化本身还是一个已知的 NP 难问题。

Postgres 无法在规划阶段把所有方案都真正运行一遍。它只能根据统计信息估算每一步会产生多少行。问题是，Postgres 通常不知道不同表之间的数据分布关系，只能作出近似假设。早期的一次估算错误，会沿着整棵连接树不断放大，最终让优化器选中一个明显较慢的计划。

这项实验没有试图重建一套通用的基数估计器，而是让模型直接提出计划，再用真实执行时间验证。研究者使用名为 pg_hint_plan 的 Postgres 扩展，把连接顺序、连接算法和扫描方式写成提示，强制数据库尝试不同方案。

模型被放进一个智能体框架。它可以查看表结构、索引和列统计信息，也可以读取默认计划、提交候选计划并测量运行时间。每条轨迹最多尝试五个候选方案，最后选择一个，或者保留 Postgres 默认方案。

真正棘手的地方，是执行时间本身有噪声。Postgres 有自己的缓存，Linux 还有一层页面缓存。同一个计划连续运行，耗时也可能忽快忽慢。某条查询在二十次测试中，十四次耗时约一百九十毫秒，另外六次却慢到二百三十毫秒以上。如果直接拿这种结果训练，模型可能因为虚假的加速而获得奖励。

研究者因此交错运行候选计划和默认计划，各测三次，再比较双方的中位数。他还把 Postgres 的共享缓存从一百二十八兆字节提高到两吉字节。结果，无变化计划被错误判为有差异的概率大约下降了四倍。那条波动明显的查询，耗时变异系数也从百分之十点三降到百分之零点九。这个步骤很关键，因为强化学习只会忠实地优化奖励。如果测量是错的，模型就会学会利用噪声，而不是真正加速查询。

未经训练的四十亿参数模型几乎无法完成任务。在一百一十三条查询中，它只能为十四条生成有效候选。常见错误包括遗漏表、重复表、构造不存在的连接，以及调用错误的工具。

训练分成两个阶段。第一阶段是监督微调。研究者让更强的模型生成数百条完整操作轨迹，再把这些示范蒸馏给小模型。这里使用了低秩适配，也就是只训练一小部分附加参数。真正可训练的参数约两千一百万个，适配器只有四十二点五兆字节。这个阶段主要教会小模型如何使用工具、构造合法的连接树，并理解整个测试框架。

第二阶段是智能体强化学习。传统的组内相对奖励有一个危险：即使一组候选全都比 Postgres 慢，其中“没那么差”的候选仍可能得到正向强化。研究者因此设计了锚定版本，把 Postgres 默认计划设为零基准。真正更快的方案才获得正优势；更慢的方案得到负优势；主动保留默认计划则记为零。这样，模型不会因为在一群失败方案中排名第一，就学到错误行为。

经过一千二百次强化学习更新后，模型生成有效候选的能力明显提高。按模型自己在每条轨迹中的最终选择计算，几何平均速度约为默认计划的一点四倍，总工作负载速度约为一点二四倍，但仍有少量查询退步。

标题中的一点八一倍，是更充分搜索后的结果。每条查询运行三条轨迹，每条轨迹最多尝试五个候选，然后根据初步实测反馈，从最多十五个候选中选择最佳方案。此时，几何平均和总工作负载都达到一点八一倍，而且在这次评估中没有查询明显退步。

模型学到的也不只是盲目试错。绝大多数搜索在提交候选前，会先检查表、统计信息或默认计划。带来主要收益的策略有三类：重写连接顺序，只修正某一张表的扫描方式，以及启用并行执行。某条查询中，模型识别出低效过滤，并强制改用位图扫描，最终获得约九十倍加速。

整个实验花费约一千二百美元，其中包括租用两块 H100 GPU，以及调用教师模型生成示范。它证明的并不是“小模型已经取代数据库专家”，而是一个更具体的判断：当任务范围明确、结果容易验证，而且查询会反复运行时，小型模型可以通过少量示范和强化学习，掌握非常专业的优化能力。

最值得记住的是三点。查询优化的困难，来自巨大的组合搜索空间和不可靠的基数估计。强化学习能否成功，首先取决于测量环境和奖励是否可信。最后，小模型不必无所不知；只要拥有合适的工具、真实反馈和足够聚焦的任务，它也可能在一个高价值领域超过成熟系统的默认选择。

### 2026-09-30 11:50:37

一个四十多亿参数的小模型，能不能帮数据库找到比默认方案更快的查询路径？这项实验给出的答案是：可以。但关键不是让模型一次猜对，而是让它反复试验，用真实执行时间学习，并把试验成本分摊到长期重复运行的查询中。

先看结果。在一百一十三条连接密集型查询上，作者让训练后的模型对每条查询搜索三轮，再根据执行反馈挑选方案。最终，整批查询的总耗时比 Postgres 默认方案减少了约百分之四十五。

这里要分清两个数字：一点八一倍，是加速比；百分之四十五左右，才是耗时下降的比例。这个成绩也不是模型一次输出就能达到的，而是每条查询最多尝试十五个候选方案后，筛选出来的结果。

为什么数据库自己的优化器，还会留下这么大的改进空间？

因为数据库查询只规定要什么结果，通常不规定怎样拿到结果。同样的数据，可以先连接不同的表，也可以选择不同的连接算法和扫描方式。答案一样，工作量却可能差很多。

文章用电影数据库举了一个例子。假设要统计日本公司在二〇〇〇年到二〇〇九年间关联的作品。查询需要连接公司表、作品表，以及记录公司和作品关系的关联表。

在作者设定的例子里，日本公司占全部公司的百分之五，那个年代的作品占全部作品的百分之二十。如果先用日本公司筛选关联表，第一次连接大约留下十万行。如果先按年代筛选，第一次连接大约留下四十万行。

最终结果可以相同，但第二步需要处理的中间数据，差了四倍。这些估算有一个前提：数据分布大致均匀。

现实中，数据未必均匀。少数日本公司可能关联了大量作品，某些年代也可能特别集中。Postgres 会利用统计信息估算结果行数，但很难掌握不同表之间的全部关联。早期连接一旦估错，后续估算就可能跟着偏。

再加上连接顺序、连接算法和扫描方式的组合，搜索空间会迅速膨胀。连接顺序优化本身，就是一类已知很难求解的问题。数据库优化器追求的，是迅速找到一个足够好的计划，而不是把所有可能性都跑一遍。

作者没有试图全面替换优化器，而是换了一个应用场景：反复运行的分析查询。

如果一条查询只执行一次，调用模型、尝试多个方案，可能比省下的时间还贵。但如果同一条查询要运行几千次，提前花几十次甚至几百次执行成本，找到更快的方案，就可能值得。

模型通过一个第三方扩展，向 Postgres 提交结构化提示，影响连接顺序、连接算法和扫描方式。数据库仍然负责执行，模型负责提出候选方案、查看反馈，再决定下一步。找不到更好的方案，也可以保留默认计划。

训练分成两步。

第一步，是监督微调。简单说，就是让小模型学习更强模型的示范：怎样查看表结构和统计信息，怎样构造有效方案，怎样调用工具，以及怎样结束搜索。

这一步很必要。未经训练的小模型，在一百一十三条查询中，有九十九条连有效候选计划都生成不了。它不仅不擅长优化，还经常写错连接树，或者在错误的时机调用工具。

经过数百条示范轨迹的训练，小模型基本学会了这套工具的用法。接着，作者才用强化学习，让模型根据真实速度反馈，学习哪些选择更有价值。

不过，真正棘手的问题，不只是模型，而是怎样可靠地判断一个方案更快。

数据库执行时间会波动。数据有没有进入缓存、并发任务是否争抢资源，都会影响测量。如果奖励直接来自耗时，模型就可能把系统噪声当成优化效果。

文章里有条查询，在相同计划下反复执行，耗时竟然分成了两簇：一簇较快，一簇较慢。这意味着两个完全相同的计划，仅仅因为抽到了不同的运行时刻，也可能看起来差了百分之十几，甚至更多。

作者采用了多种办法降噪。测量前先预热查询；比较候选方案和默认方案时，交错运行三组，再分别取中位数。差异不足百分之五，就视为持平。

更关键的调整，是把 Postgres 自身的数据缓存，从一百二十八兆字节提高到两吉字节。更多数据能够留在数据库自己的缓存里，测量明显稳定。把相同计划误判成不同速度的平均概率，从大约百分之五，降到了百分之一到二左右。

要让模型学会真正的优化，先得让测量能分清进步和运气。

奖励规则本身，也需要避免误导。

作者最初重罚无效方案。结果，模型为了避免犯错，变得过于保守，反复返回数据库默认计划。

同时，常规的组内相对评分，还有另一个问题：假设几个候选方案都比默认计划慢，只要其中一个没那么差，它仍可能因为超过组内平均水平而被强化。

这相当于奖励“坏方案里比较好的那个”，而不是奖励真正的改进。

作者因此重新设计评分，把默认计划作为比较锚点。保留默认计划计为零；生成无效方案仍有惩罚，但不再重罚到让模型不敢探索；速度变化很小时，也不把它当成可靠收益。

经过后续强化学习，模型提出有效方案的比例明显上升，查询性能也逐步改善。

不过，最终成绩要连同评估条件一起理解。训练和测试都使用同一个电影数据库，只是两组查询的连接结构没有重叠。这支持了模型在同一数据库内，处理未见查询结构的能力，却不能证明模型已经适用于任意数据库。

另外，模型自己的最终选择，整批加速比约为一点二四倍。把三轮搜索中的候选方案汇总，再依据执行反馈筛选，才达到一点八一倍。可见，搜索预算和选优规则，也是系统效果的重要组成部分。

最值得记住的，不是小模型全面击败了数据库优化器，而是一个更具体的机会：面对长期重复的分析任务，小模型可以通过试验，学会利用默认计划留下的优化空间。

而这项实验最重要的两项基础，是可信的测量，以及以真实基线为标准的奖励。没有它们，模型可能学到的不是怎样更快，而是怎样碰巧得到一个好分数。
