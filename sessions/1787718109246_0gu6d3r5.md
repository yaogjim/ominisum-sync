## 摘要（1）

### 2026-08-26 04:21:49

#### 两个帖子的资源整理，以及如何真正用它们提升 Agent 的 UI 设计质量

##### 一、核心结论

这两个帖子的核心思路是正确的：**让 Agent 使用成熟组件、设计模式和设计规范，比让它凭空“设计一个好看的页面”更可靠。**

但“把十几个网站首页链接一次性丢给 Agent”通常不会明显提升质量，原因是：

1. Agent 未必能访问或完整抓取这些网站。
2. 首页链接范围太大，没有指出具体要参考哪个组件。
3. 不同资源的设计语言、依赖和技术栈可能互相冲突。
4. 组件库能改善局部精致度，但不能自动解决信息架构、视觉层级和业务流程。
5. 没有设计方向、选择标准和验收机制，Agent 很容易继续生成“紫色渐变 + 大圆角 + 玻璃效果”的通用 AI 风格。
6. 一次混用多个视觉型组件库，很容易形成“弗兰肯斯坦式 UI”。

更有效的方法是：

> 把这些资源分别用作**设计参考、基础组件、页面模块、动效规范和验收标准**，先让 Agent 做资源审计和设计决策，再让它写代码，最后通过页面截图进行视觉审查。

建议采用：

> **1 个基础组件系统 + 最多 2 个补充资源 + 1 个动效来源 + 1 套质量检查规则。**

#### 二、资源列表整理

以下共整理出 **15 个链接资源 + 1 个 MCP 资源**。  
其中 Starlink 广告及纯调侃回复不属于 UI 资源，已排除。

> 说明：以下定位根据帖子语境和这些站点通常的用途整理。实际使用前，应让 Agent 检查具体文档、技术栈、依赖和授权许可。

##### 1. 基础组件与可复用 UI

| 资源 | 来源 | 主要用途 | 推荐用法 |
|---|---|---|---|
| [shadcn/ui](https://ui.shadcn.com) | 内容 1 正文 | 基础组件系统、可编辑源码 | 作为项目的主组件基础，统一按钮、表单、弹窗、菜单等基础交互 |
| [Beautiful UI](https://beautifului.dev) | 内容 1 正文 | 视觉化组件和页面模块参考 | 挑选少量具体组件作为视觉参考或功能模块，不要整站照搬 |
| [BeUI](https://beui.dev) | 内容 1 正文 | UI 组件和模块参考 | 让 Agent 提取可用于当前页面的具体候选组件 |
| [Rare UI](https://rareui.com) | 内容 1 正文 | 更具视觉表现力的 UI 组件 | 适合作为强调模块，不适合替代全部基础组件 |
| [Easy UI](https://easyui.site) | 内容 1 回复 | 补充 UI 组件来源 | 先检查技术栈和依赖，再选择具体组件 |
| [ReUI Components](https://reui.io/components) | 内容 2 正文 | 可复用组件和页面构件 | 用于补充主组件系统中缺失的复杂模块 |
| [Shadcn Blocks](https://shadcnblocks.com) | 内容 1 回复 | 基于 shadcn 风格的页面区块 | 适合导航、Hero、定价、FAQ、后台布局等较完整区块 |

###### 这一组资源最适合解决

- 基础组件质量不稳定
- 表单、卡片、弹窗等细节粗糙
- Agent 每次重新造轮子
- 同一个项目中按钮、圆角、间距不一致

###### 需要注意

这些资源不能全部同时作为“主组件库”。最好确定：

- 一个主基础系统，例如 shadcn/ui
- 一到两个补充来源
- 所有补充组件最终都要适配项目自己的设计令牌

##### 2. 高视觉表现和动效资源

| 资源 | 来源 | 主要用途 | 推荐用法 |
|---|---|---|---|
| [Transitions](https://transitions.dev) | 内容 1 正文 | 转场和微交互动效 | 用于菜单、弹窗、列表变化、状态反馈，不要给所有元素加动画 |
| [Magic UI](https://magicui.design) | 内容 1 回复 | 动画化、视觉表现型组件 | 适合营销页重点区域或品牌展示，谨慎用于后台和生产工具 |
| [Aceternity UI](https://ui.aceternity.com) | 内容 1 回复 | 高视觉冲击组件、背景和交互效果 | 适合作为 Hero 或展示区的视觉亮点，不宜大面积混用 |
| [You Don’t Need Animations](https://emilkowal.ski/ui/you-dont-need-animations) | 内容 2 正文 | 动效使用原则与克制 | 用作动效审查规则，避免 Agent 为“高级感”而滥用动画 |

###### 这一组资源最适合解决

- 页面缺乏反馈和状态变化
- 交互显得生硬
- 营销页面缺少记忆点
- Agent 动效过多或没有目的

###### 正确原则

动效应该解释以下问题之一：

- 什么发生了变化？
- 变化从哪里来、到哪里去？
- 用户操作是否成功？
- 当前焦点和层级在哪里？

如果一个动画只是为了“看起来更高级”，通常应该删除。

##### 4. 设计规范、方法和检查清单

| 资源 | 来源 | 主要用途 | 推荐用法 |
|---|---|---|---|
| [UI Skills](https://ui-skills.com) | 内容 2 正文 | UI 设计规则或 Agent 可用的技能型资源 | 将其中适合项目的规则整理成项目长期使用的设计约束 |
| [COSS UI](https://coss.com/ui) | 内容 2 正文 | UI 方法、规范或参考资源 | 让 Agent 先提取规则，再判断哪些适合当前产品 |

这一类资源不是用来“抄组件”的，而是用来约束 Agent：

- 什么叫一致？
- 哪些状态必须设计？
- 哪些设计决策不能随意改变？
- 什么时候组件算完成？
- 怎样避免页面只在一张桌面截图中好看？

这是两个帖子中最容易被忽略、但长期价值最高的一组资源。

##### 5. 产品 UI 灵感和真实应用参考

| 资源 | 来源 | 主要用途 | 推荐用法 |
|---|---|---|---|
| Mobbin MCP，帖子未提供 URL | 内容 1 回复 | 搜索真实应用页面、流程和成熟交互模式 | 用于研究产品结构、流程、页面密度和信息层级，而不仅是视觉效果 |

Mobbin 一类资源与组件库的价值不同。

组件库主要回答：

> 这个按钮、卡片或模块怎么做？

产品参考库主要回答：

> 一个成熟产品如何组织整个任务流程和页面结构？

例如在设计支付、登录、订阅、搜索、设置等页面时，应该先参考成熟产品的完整流程，再选择具体组件实现。

#### 三、这些资源应该在设计流程中扮演什么角色

可以将全部资源划分为五层：

| 层级 | 作用 | 对应资源 |
|---|---|---|
| 产品参考层 | 决定页面结构、用户流程、内容密度 | Mobbin MCP |
| 设计规则层 | 约束层级、间距、状态、可访问性 | UI Skills、COSS UI、Design System Checklist |
| 基础组件层 | 保证按钮、表单、弹窗等一致 | shadcn/ui、ReUI |
| 页面模块层 | 加快复杂区块和页面搭建 | Shadcn Blocks、Beautiful UI、BeUI、Rare UI、Easy UI |
| 表现与动效层 | 增加适量的视觉表现和反馈 | Transitions、Magic UI、Aceternity UI、动效原则文章 |

正确顺序应该是：

> 产品任务与信息架构 → 设计规则 → 基础组件 → 页面模块 → 视觉装饰和动效

常见错误则是反过来：

> 先找一个炫酷动画 → 拼几个组件 → 最后才考虑页面要完成什么任务

这会让页面“看起来做了很多”，但实际不好用。

#### 四、为什么单纯发送链接没有效果

##### 1. Agent 可能根本没有读取资源

一些编码 Agent 没有浏览器能力，或者只能读取静态 HTML。很多组件网站又依赖客户端渲染，因此它可能只看到：

- 页面标题
- 少量说明文字
- 空的组件容器
- 无法访问的代码预览

因此必须要求 Agent 明确报告：

- 是否成功访问
- 读取了哪些具体页面
- 是否看到了代码
- 是否看到了截图或交互
- 哪些内容无法访问

不要允许它在没有读取资源的情况下，凭站点名称猜测。

---

##### 2. 首页链接没有给出选择目标

例如把 `magicui.design` 发给 Agent，没有说明：

- 要设计的是后台、官网还是移动端
- 需要 Hero、表格还是聊天组件
- 当前页面的主要用户任务是什么
- 哪种视觉风格适合品牌
- 哪些效果明确禁止

Agent 只能随机选择最显眼的组件，最终通常会产生过度设计。

更有效的是提供具体任务：

> 从该网站寻找最多 3 个适合 B2B 数据分析后台空状态的组件。不要使用渐变文字和持续循环动画。输出准确页面地址、适用理由、依赖和改造方案，先不要写代码。

---

##### 3. 组件不等于设计系统

复制来的组件可能分别拥有：

- 不同的圆角
- 不同阴影
- 不同动画速度
- 不同字体比例
- 不同按钮高度
- 不同的 Tailwind 配置
- 不同的图标库
- 不同的交互行为

如果不统一，单个组件虽然精致，组合起来却会更差。

所以 Agent 不能只做“复制粘贴”，还要做一层适配：

> 外部组件 → 项目设计令牌 → 项目基础组件 → 页面实例

---

##### 4. 缺少视觉反馈闭环

Agent 只看代码，很难判断：

- 页面是否过于拥挤
- 标题是否太大
- CTA 是否不突出
- 卡片是否太多
- 留白是否失衡
- 移动端是否断裂
- 动画是否令人烦躁

必须让 Agent 查看运行后的页面截图，而不是只审查 JSX 和 CSS。

#### 五、推荐的 Agent 协作流程

##### 阶段 0：先写设计任务书，不要先发资源

给 Agent 的项目背景至少应该包含：

```markdown
产品类型：
目标用户：
当前页面：
用户在这个页面最重要的任务：
主要 CTA：
次要任务：
品牌关键词：
明确不想要的风格：
技术栈：
现有组件库：
必须支持的设备：
可访问性要求：
性能要求：
```

例如：

```markdown
产品类型：B2B AI 客服管理后台
目标用户：客服主管和运营人员
页面：会话详情页
主要任务：快速理解用户问题并检查 AI 回复质量
主要 CTA：接管会话
品牌关键词：可靠、克制、专业、清晰
不要：紫色渐变、玻璃拟态、大面积动画、夸张圆角
技术栈：Next.js、React、Tailwind、shadcn/ui
设备：桌面优先，但必须支持 390px 手机
```

没有这些信息，再好的组件资源也不能自动产生合适的设计。

---

##### 阶段 1：让 Agent 先做资源审计，不要立即写代码

不要让 Agent 同时“浏览 15 个网站并实现页面”。先让它输出资源清单：

| 字段 | 内容 |
|---|---|
| 资源名称 | 站点或组件名称 |
| 准确地址 | 不只是首页，尽量是具体组件页面 |
| 候选组件 | 适合当前任务的具体组件 |
| 使用位置 | Hero、导航、表单、表格、空状态等 |
| 选择理由 | 为什么适合目标用户和任务 |
| 视觉特征 | 字体、密度、边框、圆角、动效 |
| 技术依赖 | React、Tailwind、Radix、Motion 等 |
| 可访问性 | 键盘、焦点、ARIA、减少动效支持 |
| 授权情况 | 是否允许商业使用和修改 |
| 改造成本 | 低、中、高 |
| 风险 | 风格冲突、性能、依赖过重等 |

要求 Agent 只推荐少量候选，而不是列出整个网站。

###### 推荐提示词

```text
你是 UI 资源研究员。先不要写代码。

项目背景：
[粘贴项目任务书]

可参考资源：
[粘贴资源列表]

请完成以下工作：

1. 检查哪些资源可以实际访问，不得假装读取了无法访问的页面。
2. 只寻找与当前页面任务直接相关的组件或设计模式。
3. 输出最多 8 个候选，并提供准确的组件页面地址。
4. 对每个候选说明：
   - 适用位置
   - 选择理由
   - 视觉特征
   - 技术依赖
   - 可访问性情况
   - 授权风险
   - 需要怎样适配我们的设计系统
5. 最终只推荐：
   - 1 个基础组件来源
   - 最多 2 个补充来源
   - 1 个动效来源
   - 1 套检查规范
6. 如果不能读取某个资源，请明确写“无法验证”，不要根据名称猜测。
```

---

##### 阶段 2：先确定设计方向，再选组件

让 Agent 根据产品目标提出两到三个设计方向，而不是直接拼装组件。

每个方向应包括：

- 3～5 个风格关键词
- 参考页面或组件
- 页面密度
- 字体层级
- 色彩策略
- 圆角和边框策略
- 是否使用阴影
- 动效原则
- 适合的业务场景
- 潜在风险

例如：

###### 方向 A：克制型企业工具

- 中高信息密度
- 中性色为主
- 1 个品牌强调色
- 细边框代替重阴影
- 小圆角
- 动画只用于状态反馈

###### 方向 B：现代 AI 工作台

- 更大的内容区
- 更柔和的背景层级
- AI 状态使用轻微动态反馈
- 对话和工具调用有明确分层
- 禁止大面积渐变和发光边框

然后由人选择一个方向。  
**不要让 Agent 把多个方向混在同一个页面里。**

---

##### 阶段 3：把外部资源转化为项目自己的小型设计系统

这是提升 UI 一致性的关键步骤。

建议先让 Agent 创建以下内容：

```text
docs/
├── design-brief.md
├── ui-principles.md
├── component-registry.md
├── resource-manifest.md
└── page-specs/
```

以及设计令牌：

```text
颜色：
- background
- foreground
- muted
- border
- primary
- destructive
- success
- warning

字体：
- display
- heading
- body
- label
- caption

空间：
- 页面边距
- 区块间距
- 卡片内边距
- 表单间距

形状：
- 按钮圆角
- 输入框圆角
- 卡片圆角

动效：
- fast
- normal
- slow
- easing
```

###### `resource-manifest.md` 示例

```yaml
- source: https://ui.shadcn.com
  exact_component: dialog
  intended_use: 创建规则弹窗
  status: approved
  dependencies:
    - radix-dialog
  adaptation:
    - 使用项目现有颜色令牌
    - 保持统一圆角
    - 增加移动端全屏模式
  license_checked: true

- source: https://transitions.dev
  exact_component: 当前选择的具体页面
  intended_use: 弹窗进入和退出
  status: approved
  constraints:
    - 时长不超过 220ms
    - 支持 prefers-reduced-motion
```

以后 Agent 不需要重新浏览所有网站，而是优先从这个内部组件目录中选择。

---

##### 阶段 4：先做页面规格，再写组件

Agent 应先输出页面结构：

```markdown
1. 顶部导航
2. 页面标题和主要操作
3. 筛选与搜索
4. 主内容区域
5. 空状态 / 加载状态 / 错误状态
6. 详情面板
7. 移动端变化
```

然后对每一部分进行组件映射：

| 页面部分 | 组件来源 | 使用方式 | 是否需要改造 |
|---|---|---|---|
| 顶部导航 | shadcn/ui + 自定义 | 作为基础框架 | 是 |
| 数据表格 | 项目现有组件 | 保持高信息密度 | 少量 |
| 空状态 | ReUI 候选组件 | 仅借用构图 | 是 |
| 详情面板 | shadcn Sheet | 移动端改为全屏 | 是 |
| 状态变化 | Transitions | 只用于面板切换 | 是 |

这样可以避免 Agent 看到哪个组件炫酷就使用哪个。

---

##### 阶段 5：按“骨架 → 状态 → 装饰”的顺序实现

推荐实现顺序：

1. 信息架构和页面骨架
2. 真实内容和真实数据长度
3. 基础组件
4. 响应式布局
5. 加载、空、错误、禁用等状态
6. 键盘和焦点行为
7. 最后才是动画、阴影、渐变和特殊效果

不要一开始就在 Hero、背景和卡片上增加大量效果，因为这些效果会掩盖布局和层级问题。

###### 实现阶段提示词

```text
你是前端设计系统工程师。

以下设计方向已经确定，不要重新发明另一套风格：
[粘贴设计方向]

以下资源已经通过审计：
[粘贴经过筛选的资源清单]

以下是设计令牌和组件规范：
[粘贴 tokens 和规范]

请实现当前页面，并遵守：

1. 外部组件必须适配项目令牌，不得保留来源站点自己的随机颜色、
   圆角、阴影和字体。
2. 不得同时引入多个功能重复的组件库。
3. 不得使用未经验证的组件或依赖。
4. 除非品牌要求，否则不要使用紫色渐变、玻璃拟态和发光边框。
5. 动画必须服务于状态变化，并支持 prefers-reduced-motion。
6. 所有交互组件必须包含：
   - hover
   - focus-visible
   - active
   - disabled
   - loading
   - error（如适用）
7. 检查 390px、768px、1440px 三个宽度。
8. 在代码中记录外部组件来源和适配说明。
9. 先实现结构和状态，再添加视觉增强。
```

#### 六、必须加入“截图审查”循环

UI 质量不能只靠代码审查。最佳方式是：

1. Agent 运行项目。
2. 使用浏览器或 Playwright 截图。
3. 截取桌面、平板、手机三个宽度。
4. 将实际截图重新交给视觉 Agent。
5. 只找出影响最大的 5 个问题。
6. 修复后重新截图比较。

如果 Agent 无法控制浏览器，可以由人手动截图，再发给 Agent。

##### 推荐的 UI 评分标准

| 维度 | 分值 | 检查内容 |
|---|---:|---|
| 用户任务和信息层级 | 20 | 主要任务是否突出，内容顺序是否合理 |
| 视觉一致性 | 20 | 颜色、字体、间距、圆角、阴影是否统一 |
| 排版和空间节奏 | 15 | 文本是否易读，页面是否拥挤或松散 |
| 响应式与状态完整性 | 15 | 手机、平板、加载、错误、空状态 |
| 可访问性 | 15 | 对比度、键盘、焦点、ARIA、减少动效 |
| 动效和视觉克制 | 10 | 动画是否必要，视觉效果是否过量 |
| 代码与性能 | 5 | 依赖、复用、SSR、包体和渲染问题 |

##### 视觉审查提示词

```text
你现在是严格的 UI 设计评审，不是实现工程师。

项目目标：
[粘贴任务书]

选定设计方向：
[粘贴设计方向]

参考资源：
[粘贴具体参考页面]

这是当前运行截图：
[提供桌面、平板、手机截图]

请不要先改代码。先完成：

1. 按以下维度打分：
   - 用户任务和信息层级：20
   - 视觉一致性：20
   - 排版和空间节奏：15
   - 响应式与状态完整性：15
   - 可访问性：15
   - 动效和视觉克制：10
   - 代码与性能：5
2. 找出影响最大的 5 个问题，按严重程度排序。
3. 每个问题说明：
   - 截图中的具体位置
   - 为什么有问题
   - 它违反了哪条设计规则
   - 应怎样修复
4. 不要提出“整体更现代”“增加高级感”这类模糊建议。
5. 修复建议必须可以转化为明确的代码改动。
```

#### 七、不同项目的资源组合建议

##### 1. 普通 SaaS 或后台系统

推荐组合：

- 基础：shadcn/ui
- 补充：ReUI 或 Shadcn Blocks，二选一或少量组合
- 产品参考：Mobbin MCP
- 规范：Design System Checklist
- 动效：Transitions + “You Don’t Need Animations”原则

重点是：

- 信息密度
- 表单和表格
- 错误与空状态
- 键盘操作
- 一致性

不建议将 Magic UI 和 Aceternity UI 作为主要设计来源。

---

##### 2. 营销官网或产品发布页

推荐组合：

- 基础：shadcn/ui
- 页面模块：Beautiful UI、BeUI、Shadcn Blocks 中选择一个
- 视觉亮点：Magic UI 或 Aceternity UI，二选一
- 动效：Transitions
- 审查：UI Skills 或 Design System Checklist

建议只在以下位置使用强视觉效果：

- Hero
- 核心功能演示
- 品牌故事
- 关键转化区

不要让每一个卡片都发光、悬浮或自动移动。

---

##### 3. AI 对话或 Agent 产品

推荐组合：

- 基础：shadcn/ui
- AI 交互：AI SDK Elements
- 复杂模块：ReUI
- 产品参考：Mobbin MCP
- 动效：Transitions
- 规范：Design System Checklist

重点检查：

- 流式输出
- 停止生成
- 失败重试
- 引用与来源
- 工具调用状态
- 长内容折叠
- 手机端输入区域
- 会话历史
- 对话空状态
- 网络中断和恢复

#### 八、推荐的“1 + 2 + 1 + 1”规则

为了避免资源过多，可以固定使用以下选择方式：

##### 1 个基础系统

例如：

- shadcn/ui

负责：

- Button
- Input
- Dialog
- Dropdown
- Tabs
- Tooltip
- Form
- 基础可访问性

##### 最多 2 个补充来源

例如：

- ReUI：补充复杂功能组件
- Shadcn Blocks：补充完整页面区块

##### 1 个动效来源

例如：

- Transitions

必要时再少量参考 Magic UI 或 Aceternity UI，但不要同时大规模使用。

##### 1 套检查规范

例如：

- Design System Checklist
- UI Skills
- “You Don’t Need Animations”原则

这个组合比一次发送十几个链接更加稳定。

---

#### 九、建立长期可复用的内部组件库

帖子中最有价值的观点不是“让 Agent 每次访问这些网站”，而是：

> 从外部资源中筛选适合自己的组件，建立一套内部可复用的组件积木。

建议每次使用外部组件后，都沉淀以下信息：

- 来源地址
- 组件截图
- 原始用途
- 当前项目用途
- 技术依赖
- 授权情况
- 已做的视觉适配
- 支持的交互状态
- 响应式行为
- 可访问性说明
- 适用和不适用的场景

内部组件目录可以分为：

```text
components/
├── primitives/     # 按钮、输入框、弹窗
├── patterns/       # 搜索、筛选、空状态、分页
├── blocks/         # 导航、Hero、定价、设置页
├── ai/             # 消息、引用、工具调用、生成状态
└── motion/         # 统一的动效封装
```

长期来看，Agent 应优先使用这个内部组件目录，而不是每次去外部网站随机寻找新组件。

---

#### 十、最重要的实践原则

##### 应该做

- 先定义用户任务和页面目标。
- 让 Agent 报告资源是否真实可访问。
- 使用具体组件页面，而不是只发首页。
- 先做资源审计，再做设计方向。
- 确定一个基础组件系统。
- 将外部组件适配到自己的设计令牌。
- 使用真实内容验证排版。
- 检查加载、空、错误、禁用等状态。
- 用实际运行截图做视觉评审。
- 将优秀组件沉淀为内部资产。
- 检查依赖、授权、可访问性和性能。

##### 不应该做

- 一次让 Agent 混用十几个组件库。
- 用炫酷组件代替信息架构设计。
- 没有读取资源却让 Agent假装参考。
- 只检查桌面端的一张静态页面。
- 只审查代码，不审查运行截图。
- 每个区域都加渐变、发光和动画。
- 直接复制外部组件而不统一字体、圆角和颜色。
- 忽略组件的加载、错误、键盘和移动端状态。

---

#### 最终总结

这些资源真正有效的用法，不是：

> “这里有 15 个 UI 网站，你参考一下，帮我做得更好看。”

而是：

1. 用 **Mobbin** 一类资源研究成熟产品的页面结构和任务流程。
2. 用 **UI Skills、COSS UI、Design System Checklist** 建立设计规则。
3. 用 **shadcn/ui** 作为稳定的基础组件系统。
4. 从 **ReUI、Shadcn Blocks、Beautiful UI 等**挑选少量具体模块。
5. 用 **Transitions、Magic UI、Aceternity UI** 做有限的视觉增强。
6. 用动效原则限制不必要的动画。
7. 将外部组件统一适配到项目自己的设计令牌。
8. 最后通过桌面、平板、手机截图反复审查和修正。

本质上，要把 Agent 从“随机生成页面的程序员”转变为一个按流程工作的团队：

> **资源研究员 → 产品设计师 → 设计系统工程师 → 前端实现者 → UI 评审员**

可以是同一个 Agent，但必须分阶段完成，不能把浏览资源、做设计决策、写代码和视觉验收混在一次指令里。

### 回答 · 2026-08-26 09:51:49

可以。关键不是把一堆 UI 网站链接直接扔给 Agent，然后说“帮我美化”，而是建立一套**基于现有代码、带约束、可验证、分阶段执行的 UI 改造流程**。

最有效的模式是：

> 先让 Agent 理解现有系统 → 审计问题 → 建立项目级设计规范 → 选取少量参考组件 → 小范围实施 → 浏览器验证 → 再逐页推广。

#### 一、先明确：Agent 改 UI 时需要哪些上下文

对于已经有功能的系统，至少要向 Agent 提供以下 5 类信息。

##### 1. 产品与用户上下文

例如：

```md
这是一个面向企业内部运营人员的管理后台。

主要用户：
- 客服
- 运营
- 财务人员

核心任务：
- 快速查询订单
- 查看异常状态
- 批量处理数据
- 尽量减少误操作

UI 优先级：
1. 信息清晰
2. 操作效率
3. 状态反馈
4. 响应式
5. 视觉表现

不是营销网站，不需要大量动画。
```

这会防止 Agent 把管理后台改成充满渐变、玻璃拟态和滚动动画的展示网站。

##### 2. 技术上下文

需要告诉 Agent：

- 使用 React、Vue、Next.js 还是其他框架
- 使用 Tailwind、CSS Modules、Styled Components 还是现有组件库
- 是否已经有 shadcn/ui、Ant Design、MUI 等
- 图标库是什么
- 表单、表格、图表分别使用什么库
- 如何启动、测试、构建项目

例如：

```md
技术栈：
- Next.js 15
- React
- TypeScript
- Tailwind CSS
- shadcn/ui
- Lucide Icons
- React Hook Form
- Zod

验证命令：
- pnpm lint
- pnpm typecheck
- pnpm test
- pnpm build

开发命令：
- pnpm dev
```

##### 3. 不允许破坏的内容

这是现有项目 UI 改造中最重要的部分：

```md
UI 改造不得：
- 修改后端接口结构
- 修改业务流程
- 删除已有功能
- 修改权限判断
- 修改表单字段语义
- 修改路由地址
- 删除 data-testid
- 用静态假数据替换真实数据
- 为了视觉效果降低可访问性
```

否则 Agent 很容易“为了设计更干净”而删除真实业务能力。

##### 4. 当前页面和组件范围

不要只说“优化整个系统”，要给出明确入口：

```md
本轮只优化：
- /orders
- /orders/[id]
- components/orders/*
- components/layout/*

暂不修改：
- 登录页
- 权限模块
- 财务结算页
```

##### 5. 参考资源的用途

不要让 Agent“综合所有网站的风格”，而要明确每类资源用来解决什么问题：

| 资源 | 主要用途 |
|---|---|
| shadcn/ui | 基础组件结构和可访问性 |
| Beautiful UI、Rare UI、ReUI | 组件布局与视觉参考 |
| Magic UI、Aceternity | 少量强调性视觉效果 |
| transitions.dev | 交互过渡 |
| UI Skills | UI 设计原则与检查 |
| Design System Checklist | 设计系统完整性检查 |
| “You Don’t Need Animations” | 防止过度动画 |
| Mobbin | 页面信息架构和产品模式参考 |

核心原则是：

> 选择一个主组件体系，其他资源只作为参考，不要同时引入五六套组件库。

如果当前项目已经使用 shadcn/ui，通常应继续以它为基础，而不是为了几个卡片效果再引入多个完整 UI 库。

#### 三、建立一个 Agent 能执行的设计 Brief

例如创建：

```md
# docs/ui/design-brief.md

## 产品类型

企业级订单管理后台。

## 设计目标

- 提升信息层级和扫描效率
- 减少页面中的视觉噪音
- 统一间距、圆角、边框和状态颜色
- 改善表格、筛选器、空状态和错误状态
- 支持桌面端和 768px 以上平板端
- 保持现有功能和业务行为不变

## 视觉方向

- 简洁、克制、专业
- 中性灰作为基础色
- 品牌蓝作为主要强调色
- 少量阴影，以边框分区为主
- 避免大面积渐变
- 避免玻璃拟态
- 避免无意义动画
- 数据密集页面优先保证可读性

## 组件策略

- 优先复用现有组件
- 基础交互组件使用 shadcn/ui
- 图标统一使用 Lucide
- 不重复创建 Button、Input、Dialog 等基础组件
- 不引入新的 UI 依赖，除非先说明原因并获得批准

## 必须保持

- API 调用方式
- 路由结构
- 权限判断
- 表单校验
- data-testid
- 埋点事件
- 键盘操作能力

## 验收标准

- TypeScript 无错误
- lint、test、build 通过
- 无明显横向溢出
- 所有表单控件有 label
- 焦点状态清晰
- 支持键盘操作
- loading、empty、error、disabled 状态完整
- 移动端或窄屏下主要任务仍可完成
```

#### 四、不要只保存资源首页，要保存“具体参考”

只给 Agent 这类信息：

```md
- https://rareui.com
- https://magicui.design
- https://beautifului.dev
```

效果往往不稳定。因为 Agent 不知道应该看哪个组件，也不一定能直接访问、抓取或正确理解网站内容。

更好的 `references.md` 是：

```md
# UI References

## 基础体系

- shadcn/ui
  - 用途：Button、Input、Dialog、Dropdown、Tabs、Table
  - 原则：以现有主题变量为基础，不复制整套示例页面
  - URL: https://ui.shadcn.com

## 订单筛选区

参考：
- URL: ...
- 参考部分：紧凑筛选器布局
- 借鉴原因：减少首屏占用
- 不要复制：品牌色、营销文案、装饰背景

## 统计卡片

参考：
- URL: ...
- 参考部分：标题、数值、变化趋势的层级
- 借鉴原因：比当前页面更易扫描
- 不要使用：动态渐变边框、持续动画

## 过渡动画

- URL: https://transitions.dev
- 仅用于：
  - Dialog 打开/关闭
  - Dropdown 出现/消失
  - 状态切换
- 时长控制在 120–220ms
- 必须支持 prefers-reduced-motion

## 禁止事项

- 不直接复制第三方品牌设计
- 不复制有版权限制的完整产品页面
- 不引入来源不明的代码
- 不为了一个视觉组件安装大型依赖
```

如果有特别喜欢的效果，最好同时提供：

- 截图
- 组件源代码
- 具体 URL
- 你喜欢的部分
- 不希望复制的部分

Agent 对“我喜欢这个页面”理解可能不准，而对“参考这个卡片的信息层级，但不要渐变和动画”理解会好得多。

#### 五、在 AGENTS.md 中写入长期约束

Cursor、Codex 等工具都适合通过仓库级规则来保持一致性。可以在根目录建立：

```md
# AGENTS.md

## UI Modernization Rules

This repository contains an existing production application.
UI work must preserve current business behavior.

### Before editing

1. Read:
   - docs/ui/design-brief.md
   - docs/ui/references.md
   - relevant route files
   - existing shared components
2. Identify the current UI framework and design tokens.
3. Reuse existing components before creating new ones.
4. Trace event handlers, permissions, API calls and loading states.
5. Do not edit code until the requested scope and plan are clear.

### Implementation rules

- Preserve API contracts, routes and business logic.
- Preserve test IDs, analytics and accessibility semantics.
- Do not replace real data with mock data.
- Do not remove features for visual simplicity.
- Do not introduce a new UI library without approval.
- Prefer design tokens over hard-coded colors and spacing.
- Prefer shared components over page-local duplication.
- Use Lucide for icons if an icon is needed.
- Do not use emoji as interface icons.
- Animations must be subtle and respect prefers-reduced-motion.
- Include loading, empty, error, disabled and success states.
- Maintain keyboard accessibility and visible focus states.

### Workflow

For any substantial UI task:

1. Audit the current implementation.
2. Propose a plan.
3. List files that will change.
4. Identify risks.
5. Implement in small batches.
6. Run lint, typecheck, tests and build.
7. Validate the result in a browser.
8. Summarize behavior preserved and visual changes made.

### Validation commands

- pnpm lint
- pnpm typecheck
- pnpm test
- pnpm build
```

Codex 一般会读取仓库中的 `AGENTS.md`。如果不同目录有不同要求，还可以在子目录建立更具体的 `AGENTS.md`。

#### 九、让 Agent 先建立 Design Tokens，而不是逐页“调 CSS”

很多项目变难看，不是某一个组件的问题，而是缺少统一标准：

- 有 8 种灰色
- 5 种圆角
- 页面间距随机
- 卡片阴影不一致
- 标题字号随意
- 状态颜色不统一

因此第一批改动通常应该包括设计 token。

例如：

```css
:root {
  --background: ...;
  --foreground: ...;

  --surface: ...;
  --surface-muted: ...;

  --border: ...;
  --border-strong: ...;

  --primary: ...;
  --primary-foreground: ...;

  --success: ...;
  --warning: ...;
  --destructive: ...;

  --radius-sm: 0.375rem;
  --radius-md: 0.5rem;
  --radius-lg: 0.75rem;
}
```

还应统一：

- 页面最大宽度
- 页面横向留白
- 标题层级
- 卡片容器
- 表单控件高度
- 表格行高
- Focus Ring
- Z-index
- 动画时长
- 状态色语义

应要求 Agent：

> 除非设计 token 无法表达，否则不要在页面中直接使用任意颜色值、任意阴影和任意圆角。

#### 十、先改“系统骨架”，再改局部页面

比较合理的顺序是：

##### 第一阶段：全局基础

- 字体与标题层级
- 背景与 Surface
- 页面宽度和留白
- 颜色 token
- 边框和圆角
- Button、Input、Select、Dialog
- Focus 状态

##### 第二阶段：应用骨架

- Header
- Sidebar
- Breadcrumb
- Page Header
- 页面内容容器
- 移动端导航

##### 第三阶段：高频业务模式

- 数据表格
- 筛选器
- 搜索
- 分页
- 表单
- Drawer/Dialog
- 详情面板
- 状态标签

##### 第四阶段：完整状态

- Loading
- Skeleton
- Empty
- Error
- No Permission
- Offline/Retry
- Success Feedback

##### 第五阶段：适度动效与视觉精修

- Dropdown/Dialog 过渡
- Hover/Pressed 状态
- 数据更新反馈
- 布局细节
- 响应式细节

不要先从动态背景、发光卡片和复杂动效开始。对已有业务系统来说，信息架构、间距和状态设计的收益通常更大。

#### 十四、给 Agent 明确的视觉验收标准

“更好看”不可验证，应转换成具体标准。

例如：

```md
## 页面验收标准

- 页面主标题在首屏清晰可见
- 主操作在视觉层级上明显，但页面最多一个主要按钮
- 筛选器在桌面端不超过两行
- 表格标题、主体和分页边界清晰
- 状态颜色具有一致语义
- 空状态提供下一步操作
- 错误状态提供重试
- 所有图标按钮有可访问名称
- 键盘焦点清晰
- 768px 下无页面级横向滚动
- 表格内容无法压缩时，滚动只发生在表格容器内
```

- 最小点击区域
- 文本行长
- 标题层级
- 表单错误位置
- 保存反馈方式

#### 十五、如何使用文章中的这些资源

推荐把资源分层使用，而不是全部安装。

##### 1. 基础组件层

优先选一个：

- shadcn/ui
- 当前项目已有的 Ant Design、MUI、Chakra 等

用途：

- Button
- Input
- Select
- Dialog
- Dropdown
- Tabs
- Tooltip
- Toast

如果项目已经有基础库，不建议仅仅为了视觉效果切换整套组件体系。

##### 2. 视觉模式参考层

可以参考：

- Beautiful UI
- Rare UI
- ReUI
- Shadcn Blocks
- Easy UI

用途：

- 卡片布局
- 页面标题
- 设置页
- 筛选区
- 详情面板
- Empty State

通常只借鉴结构、比例和层级，不一定安装代码。

##### 3. 强调型组件层

可以谨慎参考：

- Magic UI
- Aceternity UI

更适合：

- 官网
- Landing Page
- Onboarding
- 关键成功状态
- 少量品牌展示区域

不适合大量用于：

- 数据表格
- 表单
- 财务页面
- 高频后台操作

##### 4. 动效层

参考：

- transitions.dev
- Emil Kowalski 的 UI 文章

使用原则：

- 动画说明状态变化
- 不使用动画掩盖响应慢
- 不让布局持续移动
- 不让用户等待动画结束才能操作
- 支持 `prefers-reduced-motion`

##### 5. 方法论和检查层

使用：

- UI Skills
- Design System Checklist

让 Agent 在完成后做一次“设计审查”，而不是直接复制其风格。

#### 十六、避免这些常见失败方式

##### 1. 一次要求重做整个系统

容易造成：

- 改动范围失控
- 业务逻辑被误伤
- 组件风格前后不一致
- Review 困难
- 无法准确回滚

应按页面或业务流分批提交。

##### 2. 同时引入多个 UI 库

容易造成：

- Bundle 增大
- 主题不一致
- CSS 冲突
- 交互行为不统一
- 维护成本增加

应要求 Agent 在添加依赖前说明：

- 为什么现有组件无法完成
- 新依赖体积
- License
- 是否支持 SSR
- 是否支持无障碍
- 是否可只复制少量源码
- 是否会与现有样式冲突

##### 3. 只追求截图漂亮

静态截图好看，不代表真实系统好用。必须检查：

- 长文本
- 空数据
- 错误
- 权限不足
- 加载
- 分页
- 键盘
- 小屏
- 大量数据
- 表单校验

##### 4. 让 Agent 自由修改业务代码

UI 改造中应明确：

> 如果发现业务逻辑需要调整，请记录为建议，不要在当前 UI 任务中顺手修改。

##### 5. 只给资源网址，不给具体选择

Agent 可能会混合多个资源，最后变成“AI 风格拼盘”。应明确：

- 参考哪个组件
- 为什么参考
- 借鉴什么
- 不借鉴什么

#### 十七、一个适合直接复制的完整任务 Prompt

```text
你是一名资深前端工程师、产品设计师和可访问性审查者。

目标：
在不改变现有业务功能的前提下，改进当前项目的 UI、交互一致性和可用性。

开始前请阅读：
- AGENTS.md
- docs/ui/product-context.md
- docs/ui/design-brief.md
- docs/ui/references.md
- 目标路由
- 目标路由使用的组件
- components/ui
- 全局样式和主题配置
- 相关类型、测试和 API 调用

本次范围：
[填写页面、路由、组件目录]

本次不包含：
[填写明确排除的页面和模块]

必须保持：
- API 协议和请求行为
- 路由
- 权限判断
- 表单字段及校验语义
- data-testid
- 埋点事件
- 当前核心业务流程

设计方向：
- 简洁、克制、专业
- 优先改善信息层级、间距和状态反馈
- 复用现有组件
- 以现有设计系统为基础
- 外部资源只作为模式参考
- 不混合引入多个 UI 库
- 不使用无意义的渐变、发光和持续动画

工作流程：

第一步，只读审计，不修改文件：
1. 分析页面结构和组件依赖
2. 识别必须保留的业务行为
3. 识别视觉、UX、响应式和可访问性问题
4. 识别可复用组件和重复实现
5. 对照 docs/ui/references.md，指出适用和不适用的参考
6. 输出 P0/P1/P2 问题清单
7. 输出分阶段方案、修改文件和风险

等我确认计划后，再开始实施。

实施时：
- 每次只完成一个阶段
- 不引入新依赖，除非先获得批准
- 使用设计 token，避免散布硬编码样式
- 包含 loading、empty、error、disabled 和 success 状态
```

##### 真正的机会是为智能体建立“设计上下文层”

对工程师主导的小团队、独立开发者和高频原型场景，这种方法已经很实用。更值得关注的产品机会，则不是再做一个更大的组件目录，而是把组件按用途、风格、依赖、无障碍水平和适用边界结构化，并让智能体知道当前产品应该选什么、为什么选、如何保持全局一致。

现有替代方案包括 Storybook、Figma 组件库和传统设计系统；待验证的需求是：团队是否愿意维护一份同时面向人和智能体的组件注册表，以及它能否稳定减少返工，而不只是更快生成一个“第一眼好看”的页面。

**AI 前端设计的关键进步，不是模型开始拥有品味，而是品味可以被整理成代码、规则和案例，成为它能够调用的外部能力。**
