## 分析要点

- **核心高价值点**：把研发流程拆成可自动执行的/one-shot任务，并结合issue系统和多个loop，实现AI Agent并发推进项目迭代。
- **留存建议**：长期保留（提供了较完整的AI辅助编程高并发工作流，包括one-shot研发、issue自动化、loop机制和验收方法，具备复用价值。）

**知识要点**

- AI编程效率的关键不只是提示词，而是构建能持续消耗token并稳定产出的自动化流程。
- one-shot流程应将需求分析、design、edge case推演、实现和PR提交尽量自动化。
- 通过多目录或worktree实现多任务并发，可以同时运行多个AI开发会话。
- issue系统可作为AI任务调度层，todo状态触发自动开发并提交PR。
- 日志分析、竞品分析、夜间bug扫描等loop可以持续发现问题并自动创建任务。
- 提高Agent产出可靠性需要把更多时间放在架构设计、edge case和验收日志上。

**行动项**

- 为自己的项目设计一个/one-shot研发流程，覆盖需求分析、设计、实现、测试和PR提交。
- 建立AI可读取和创建的issue模板，让任务描述更结构化、细粒度。
- 尝试搭建至少一个自动loop，例如错误日志分析后自动生成修复issue。
- 在AI编码任务中要求先输出详细design和edge case清单，再进入实现阶段。
- 为AI生成代码增加验收机制，包括用例、人工检查和详细运行日志。

### 我怎么用 AI 编程 2026.06

我理解 ai 时代一个很重要的能力是有效消耗 token 的能力。之前看到 token king 都是各种羡慕，到处问别人是怎么消耗 Token 的。我也和很多同学一样，从 claude 的 $20 买起，然后 $100 5x，然后 $200 20x，截止 2026.5.29，日消耗 20x 的 30%+，一周得差不多 1.5 个 20x 才能满足需求了，日产出有效代码也到了 1w \~ 3w+ 。

![Image](https://pbs.twimg.com/media/HJqLnGtaAAER_zN?format=png&name=large)

所以怎么用到这个量？说下我的方法论，欢迎探讨。

1、用 /one-shot 研发需求。/one-shot 是个概念，可以是 skill 或 plugin。ta 是你研发一个需求的全自动化流程。你日常怎么开发需求的，比如我是用 brainstorm 产出 design，然后迭代 deisng，然后 impl，然后就想办法把这个过程给全自动化，重点是把不重要的决策点全交给 AI。减少人在这中间的决策过程，让一个 task 跑 20m+、30m+ 甚至 1h 完全不需要管，当你知道一个 /one-shot 出去后这个任务可以被高质量完成，就能并行执行 n 个任务了。

2、并发和 issue 管理。boris 日处理峰值 200+，我目前 70+，如果不限 token 的话，努努力能上 100+。1）并发不少同学用的是 worktree，我没用，我用的古法多目录法，所以会有 -2、-3、-4、-5，通常 5 个并发量，够用了，相比 worktree 的好处是省去了环境 setup 消耗，同时出问题时也可以方便地进入到对应的环境对应的 session 进行调试。2）我有个 issue 管理系统，当 issue 被标记为 todo 时，就会自动用前面的 /one-shot 去执行然后提 PR，所以我的工作就变成了 create n 个 todo status 的 issue，然后等验收。3）create issue 也可以是 ai 做的，因为 ai 可以基于你的分析，产出更事无巨细的 issue 描述，我的每个项目下都有个 /create-issue 的 skill 来干这件事，一通分析后调 /create-issue 来让 ai 干活。

![Image](https://pbs.twimg.com/media/HJqLsrbacAAZJAX?format=png&name=large)

![Image](https://pbs.twimg.com/media/HJqLyhWagAAsElR?format=jpg&name=large)

3、loop。你的 loop 越多，效率就越高。loop 可以和 /create-issue 结合。比如，1）你有完善的日志系统，会收集错误日志，有个错误日志分析的 loop，找到问题后，/create-issue，2）你有个竞品分析系统，每天早上 7:10 运行，找到重要的资讯，然后逐条分析，和当前项目做匹配，把重要的筛出来，然后 /create-issue，3）每天晚上用

[/clawpatch-bugs](https://github.com/sorrycc/skills/blob/master/clawpatch-bugs/SKILL.md) skill 找 bug，然后建 issue。loop 越多，issue create 的就越多，项目迭代速度就越快。

4、然后是怎么做验收。这是个难题，感觉没有很好的通用解。我目前是通过用例 + 人工验收 + 提升每个 issue 的代码质量 + 详细日志来做的。1）提升代码质量相关性的东西太多了，比如已有代码、架构、代码实施阶段 design 的完整性等，我的 /one-shot 会在 design 阶段消耗 80% 的时间，尽可能多的考虑 edge case，然后 20% 的时间用来写代码，所以产出代码质量会更高一些 ， 2）架构也很重要，同时要管理好项目的复杂度，当一个任务需要来回改来改去要改 n 次都改不好的时候，就要考虑架构问题了，3）日志得多花点心思，我是每次验收时遇到问题时，把错误描述给他，让 ai 直接分析相关的日志，然后给方案。

最后说下我的 setup 。

1）原则是用最好的模型和工具，2）Claude Code Max 两个账号，一个 20x 一个 5x，日常用 Opus 4.8 1M，3）Backup zenmux + 一个朋友的中转站，因为 Claude Code 经常挂了，挂了的时候随时切，4）还没开始用 codex，总感觉交任务给他没那么放心，但身边越来越多人开始用他，也准备试试。

##### 一、总结

作者认为：**AI 编程的核心能力，不是省 token，而是高效消耗 token，把 AI 变成并发研发团队。**

主要方法：

1. **/one-shot 自动开发**
   - 把需求分析、设计、实现、提 PR 自动化。
   - 人只做关键决策，普通决策交给 AI。
   - 一个任务可运行 20 分钟到 1 小时，人不用盯着。

2. **并发处理任务**
   - 同时跑多个项目目录或任务。
   - 用 issue 系统管理需求。
   - 标记为 todo 后，AI 自动开发并提交 PR。

3. **建立自动循环 loop**
   - 错误日志自动分析 → 创建 issue。
   - 竞品信息自动分析 → 创建 issue。
   - 定期找 bug → 创建 issue。
   - loop 越多，项目迭代越快。

4. **验收仍是难点**
   - 目前靠测试用例、人工验收、代码质量、日志分析。
   - 作者认为设计阶段最重要：  
     **80% 时间做设计和考虑边界情况，20% 时间写代码。**

5. **工具配置**
   - 使用 Claude Code Max 多账号。
   - 主力用 Opus 4.8 1M。
   - 准备尝试 Codex。
   - 原则：用最好的模型和工具。

##### 二、深入浅出解读

这篇文章本质上讲的是：

> 未来程序员不是“亲手写代码的人”，而是“管理 AI 编程流水线的人”。

以前开发流程是：

```text
人想需求 → 人写设计 → 人写代码 → 人调 bug
```

现在作者的流程是：

```text
人提出方向 → AI 拆需求 → AI 写设计 → AI 写代码 → AI 提 PR → 人验收
```

关键变化有三个。

###### 1. 从“写代码”变成“发任务”

作者不再把 AI 当聊天工具，而是当执行员工。

一个需求丢给 AI 后，让它自己完成：

- 分析需求
- 设计方案
- 考虑边界情况
- 写代码
- 提交 PR

人不需要每一步都插手。

---

###### 2. 从“单线程开发”变成“多线程管理”

传统程序员一次通常只做一个任务。

作者同时开多个任务，让多个 AI 并行工作。

这类似：

```text
你不是一个程序员
你是一个小型 AI 研发团队的负责人
```

所以 token 消耗非常大，但产出也变大。

---

###### 3. 从“被动修 bug”变成“自动发现问题”

作者通过 loop 自动发现任务：

- 日志里有错误 → 自动分析
- 竞品有新功能 → 自动分析
- 项目里可能有 bug → 自动扫描

然后自动生成 issue，再让 AI 去开发。

这意味着项目不是靠人想起来才改，而是靠系统持续推动迭代。

---

##### 三、我的意见

我认同核心观点：**AI 编程的上限，不在于会不会提问，而在于能不能搭建流程。**

但也要注意三点：

###### 1. 设计能力会更重要

AI 可以写代码，但需求拆解、架构设计、边界判断，仍然需要人把关。

不会设计的人，用 AI 只会更快地产生烂代码。

---

###### 2. 验收能力是瓶颈

AI 并发越多，产生的代码越多。

如果没有测试、日志、review 机制，很容易变成：

```text
代码产出很多，但质量不可控
```

所以自动化测试和日志系统非常关键。

---

###### 3. 不适合所有人一上来就这么做

作者的方法适合高频开发者、独立开发者、工程能力强的人。

普通人可以先学三个动作：

```text
1. 让 AI 先写设计，再写代码
2. 用 issue 管理任务
3. 每次改动都要求 AI 补充测试和日志
```

---

##### 四、一句话结论

**AI 编程真正的进阶，不是让 AI 帮你写几行代码，而是让 AI 持续、并发、自动化地推进整个项目。**

## 结构化（1）

##### 主旨概括

作者认为，在 AI 编程时代，关键能力之一是“高效消耗 token”：通过自动化流程、并发任务、持续循环发现问题和完善验收机制，把 AI 从辅助工具变成可并行工作的研发执行系统。作者目前日消耗已达到 Claude 20x 套餐的 30%+，每周约需 1.5 个 20x，日产出有效代码约 **1 万～3 万行以上**。

---

##### 1. 用 `/one-shot` 自动化研发需求

作者提出 `/one-shot` 是 AI 编程中的核心方法，可以理解为一个自动完成研发需求的流程、skill 或 plugin。

关键点：

- `/one-shot` 的目标是把一个需求从设计到实现尽量全自动化。
- 作者的常规流程是：
  - brainstorm 产出 design；
  - 迭代 design；
  - implementation；
  - 尽量把整个过程自动化。
- 核心思想是：  
  **把不重要的决策交给 AI，减少人的参与。**
- 理想状态是：
  - 一个任务可以跑 **20 分钟、30 分钟甚至 1 小时**；
  - 中途人不用干预；
  - 如果能保证质量，就可以同时并行多个任务。

简单来说，作者不是让 AI 只写几段代码，而是让 AI 完整承接一个研发任务。

---

##### 2. 并发执行与 issue 管理

作者认为，要真正消耗大量 token、提升产出，就必须让多个 AI 任务并行运行，并用 issue 系统管理任务流。

###### 2.1 并发方式

作者提到：

- Boris 日处理 issue 峰值可达 **200+**；
- 作者目前约 **70+**；
- 如果不限制 token，努力可以做到 **100+**。

并发方式上：

- 很多人使用 `worktree`；
- 作者没有用，而是采用“多目录法”：
  - 例如目录后缀为 `-2`、`-3`、`-4`、`-5`；
  - 通常保持 **5 个并发任务**。

作者认为多目录法的好处是：

- 省去环境 setup 的消耗；
- 出问题时可以直接进入对应目录和 session 调试；
- 对实际工作来说并发量已经足够。

###### 2.2 issue 自动执行

作者有一个 issue 管理系统：

- 当 issue 被标记为 `todo` 时；
- 系统会自动调用前面的 `/one-shot`；
- AI 自动执行任务并提交 PR。

因此，作者的工作变成了：

> 创建多个 `todo` 状态的 issue，然后等待验收。

###### 2.3 issue 也可以由 AI 创建

作者进一步把“创建 issue”也交给 AI：

- AI 可以基于分析，生成更详细、更具体的 issue 描述；
- 每个项目下都有一个 `/create-issue` skill；
- AI 分析完后，调用 `/create-issue` 生成任务。

也就是说，作者不仅让 AI 写代码，还让 AI 帮忙拆任务、建任务、执行任务。

---

##### 3. 通过 loop 持续产生任务

作者认为，系统里的 loop 越多，效率越高；loop 可以持续发现问题、分析机会，并自动生成 issue。

典型 loop 包括：

###### 3.1 错误日志分析 loop

如果项目有完善的日志系统：

- 系统会持续收集错误日志；
- AI 定期分析错误；
- 找到问题后调用 `/create-issue`；
- 再交给 `/one-shot` 执行。

###### 3.2 竞品分析 loop

作者举例说，可以建立一个竞品分析系统：

- 每天早上 **7:10** 运行；
- 自动抓取重要资讯；
- 逐条分析；
- 和当前项目进行匹配；
- 筛出有价值的信息；
- 再调用 `/create-issue` 生成任务。

###### 3.3 晚间 bug 扫描 loop

作者每天晚上会使用 `/clawpatch-bugs` skill：

- 自动找 bug；
- 自动创建 issue；
- 后续再由 AI 执行。

作者的结论是：

> loop 越多，issue 创建得越多，项目迭代速度就越快。

---

##### 4. 验收仍然是难点

作者认为，AI 自动开发中最难的是“验收”，目前没有特别通用的解决方案。

他的当前做法包括：

- 用例验证；
- 人工验收；
- 提升每个 issue 的代码质量；
- 依赖详细日志排查问题。

###### 4.1 通过设计阶段提升代码质量

作者的 `/one-shot` 流程中：

- **80% 时间用于 design 阶段**；
- 尽可能考虑 edge case；
- **20% 时间用于写代码**。

作者认为，这样能显著提高 AI 产出代码的质量。

热门回复中也有人认同这一点：

> 80% 的人类时间应该花在架构设计和 edge case 上，这是让 agent 长时间可靠产出的关键。

###### 4.2 架构很重要

作者强调，架构会直接影响 AI 编程效果。

如果一个任务：

- 来回改很多次；
- 改了很多轮仍然改不好；

那就不能只怪 AI，应该考虑是不是项目架构存在问题。

###### 4.3 日志要足够详细

作者在验收时，如果遇到问题，会：

- 把错误描述给 AI；
- 让 AI 分析相关日志；
- 再给出解决方案。

因此，详细日志是 AI 自动开发闭环里的重要基础设施。

##### 总结

作者的方法论可以概括为一套 AI 编程流水线：

1. 用 `/one-shot` 自动完成单个研发任务；
2. 用多目录方式并发跑多个任务；
3. 用 issue 系统承接任务流；
4. 用各种 loop 持续发现问题和机会；
5. 用设计、架构、日志和人工验收保证质量；
6. 用高性能模型和备用工具保障稳定产出。

核心思想不是“让 AI 帮我写代码”，而是：

> 搭建一套能持续发现任务、创建任务、执行任务、提交 PR、辅助验收的 AI 研发系统。

> 把不重要的决策点全交给 AI。

**为什么重要：**  
人如果卡在每个小决策上，就无法并发；  
只有放弃微管理，AI 才能变成“执行单元”。

**可迁移价值：**  
适用于所有知识工作：

| 领域 | `/one-shot` 思路 |
|---|---|
| 产品 | 从用户反馈到需求文档 |
| 运营 | 从数据异常到活动方案 |
| 投研 | 从新闻监控到投资备忘录 |
| 内容 | 从选题到初稿到发布清单 |
| 管理 | 从问题发现到任务拆解到责任人分配 |

**我应该记住什么：**  
> AI 工作流的单位不是 prompt，而是“完整任务闭环”。

---

###### 洞见 3：并发的前提不是更强模型，而是任务管理系统

###### **核心观点：**  
> 高产出的关键是把工作变成 issue 队列：人负责创建/筛选 todo，AI 自动执行、提 PR，人再验收。

作者的实际工作流变成：

```text
创建 issue → 标记 todo → AI /one-shot 执行 → 提 PR → 人验收
```

**为什么重要：**  
这把个人编程变成了类似小型工程组织：

- issue 是需求池  
- AI agent 是工程师  
- PR 是交付物  
- 人是产品经理 + 架构师 + QA  

**反常识之处：**  
很多人以为 AI 编程效率来自“单任务更快”；  
实际更大的效率来自“多任务并发”。

**我应该记住什么：**  
> AI 编程不是把一个人变快，而是让一个人拥有一个小团队的并发能力。

---

###### 洞见 4：loop 比 prompt 更重要

###### **核心观点：**  
> 真正可持续的 AI 产出，来自自动发现问题、自动生成 issue、自动进入执行流的循环系统。

文章中的 loop 包括：

- 错误日志分析 → 创建 bug issue  
- 竞品资讯分析 → 匹配当前项目 → 创建需求 issue  
- 每晚自动查 bug → 创建 issue  

**为什么重要：**  
单次使用 AI 是“工具”；  
loop 化以后，AI 变成“系统”。

**可迁移价值：**  
任何业务都可以问：

```text
我能不能自动发现问题？
我能不能自动生成任务？
我能不能自动派发执行？
我能不能自动验收一部分结果？
```

**我应该记住什么：**  
> 高级 AI 使用者不是更会提问，而是拥有更多自动循环。

###### 洞见 5：AI 写代码的质量，主要取决于前置设计，而不是编码阶段

###### **核心观点：**  
> `/one-shot` 中 80% 时间用于 design 和 edge case，20% 时间写代码，反而更可靠。

**反常识之处：**  
很多人以为 AI 写代码快，所以应该直接让它写；  
作者的经验是：越想让 agent 长时间可靠工作，越要把时间花在设计阶段。

**底层逻辑：**  
AI 最容易失控的地方不是语法，而是：

- 需求理解偏差  
- 架构边界不清  
- edge case 遗漏  
- 修改范围扩散  

所以设计越完整，后面的自动执行越稳定。

**我应该记住什么：**  
> AI 编程不是“少设计、多生成”，而是“重设计、快生成”。

## 深度解读（1）

### 2026-09-18 01:05:34

#### AI 编程进入“任务工厂”阶段，瓶颈已从写代码转向定义与验收

这篇经验最值得保留的，并不是“每天消耗多少 token”或“生成一万到三万行代码”，而是它展示了一种新的研发组织方式：**人不再持续陪伴 AI 写代码，而是把需求加工成可独立执行、可并发调度、最终可验收的任务。**

作者的 `/one-shot` 本质上是一条自动化研发流水线：先分析与设计，再实现和提交 PR。关键不是完全取消人的判断，而是把不重要、可逆的决策交给 AI，让单个任务能够脱离人工照看运行二十分钟甚至一小时。随后，Issue 系统成为任务队列，多个独立目录成为执行环境，日志、竞品分析和夜间扫描则不断发现问题、自动创建新任务。人的工作因此从“实现需求”转向“定义任务、配置流程、验收结果”。

##### 高并发成立的前提，是任务足够可委托

作者提到 `/one-shot` 有约 80% 的时间用于设计和边界情况，只有 20% 用于编码。这个比例比代码产量更有信息量：**Agent 能否长时间可靠工作，主要取决于任务描述是否包含目标、约束、上下文和验收条件。**

这也解释了为什么 Issue 是整个系统的关键接口。好的 Issue 不只是待办事项，而是一份小型执行协议：AI 可以据此行动，人也可以据此判断结果。任务边界模糊、架构依赖复杂时，增加模型能力或 token 往往只会让 AI 更快地产出更多需要返工的代码。

因此，“有效消耗 token”更准确的含义不是多调用模型，而是拥有足够多的**高质量、可并发、可验证任务**。没有这层准备，token 消耗量和代码行数都可能只是活动指标，而非生产率。

##### 自动发现任务既是飞轮，也是风险放大器

错误日志、竞品资讯和自动找 Bug 的 loop，可以把“发现信号—分析—创建 Issue—提交 PR”连成闭环。这使软件从等待人规划，转向持续自我暴露改进机会。

但作者也无意中指出了它的上限：Issue 生成速度可以快速扩张，验收能力却没有同步自动化。日志中的异常不一定值得修，竞品变化不一定适合跟进，静态扫描发现的问题也可能优先级很低。**如果缺少价值排序和风险分级，闭环优化的可能只是任务吞吐量，而不是产品效果。**更危险的是，架构不佳时，每个自动任务都会继续增加复杂度，使后续 Agent 更难理解和修改系统。

##### 下一层工具机会是“控制面”，不是更多代码生成

真正缺失的通用能力，可能是 AI 研发的控制面：把需求拆分、执行隔离、上下文供给、测试验收、风险分级和失败追踪连接起来。现有替代方案是 Issue Tracker、脚本、worktree、多目录和人工 Review 的拼装；机会不在于再造一个会写代码的 Agent，而在于回答三个问题：

- 哪些任务可以放心自动执行？
- 哪些变更必须由人验收？
- 系统是否真的减少了返工、缺陷和复杂度？

这篇文章仍是个人实践，缺少对缺陷率、返工时间和实际交付价值的比较数据，因此不能仅凭日处理 70 个 Issue 判断效率提升。但它准确暴露了一个变化：**当代码生成趋近廉价，稀缺资源将变成高质量任务、可观测系统，以及对结果负责的验收能力。**
