建议置顶该任务，每周末让 Codex 三省吾身一次😂

提示词如下：  
请查看我最近的 Codex 使用记录，找出重复出现的工作流程或重复提出的请求。

重点关注真实维护任务：  
持续集成失败、Pull Request 审核、测试失败定位、测试用例筛选、变更记录管理、文档更新、发布准备、部署验证、本地启动、故障排除、环境问题排查。

处理规则：  
1\. 先盘点已有能力，包括本地技能、插件技能、agents 配置、references、scripts 和 openai.yaml。  
2\. 对每个重复工作流，先判断已有能力是否已经覆盖：  
\- 触发条件是否准确  
\- 工作流是否贴合我的真实使用记录  
\- 是否缺少验证步骤  
\- 是否容易误判环境、依赖、源码、CI 或外部服务问题  
\- 是否需要补充 references、scripts、默认提示词或 agents/openai.yaml  
3\. 优先复用或优化已有技能。创建新技能前，必须说明为什么现有技能或插件技能不够用。  
4\. 只有当任务确实是可重复使用的工作流程，且现有能力无法覆盖时，才创建新技能。  
5\. 如果任务只是有限范围的调查职责，可以建议自定义子代理模板，例如：  
\- 只读分析 CI 日志  
\- 整理未解决 PR review thread  
\- 筛选最小失败测试集  
\- 检查 docs/changelog/release readiness  
\- 做部署前验证清单  
6\. 不要创建重复技能。只创建或修改真正有用的东西，保持最小改动。  
7\. 如果实际创建或修改技能，必须运行校验，并说明改了哪些文件。

输出保持简洁，按这个结构：  
1\. 重复工作流清单  
2\. 已有能力匹配情况  
3\. 建议动作：复用 / 优化已有技能 / 新建技能 / 子代理模板 / 不处理  
4\. 每个动作的原因和证据  
5\. 如有实际创建或修改，列出文件和校验结果  
6\. 后续最值得补的一个点

判断标准：  
\- 高频出现  
\- 仍然需要我手动判断  
\- 有明确验证步骤  
\- 能减少下次排障、PR、CI、测试、文档或发布准备的摩擦  
\- 不增加无意义维护负担

## 解读（1）

### 2026-06-02 06:09:23

##### 1. 内容总结

这篇内容分享了一个 **让 Codex 定期复盘自己使用记录** 的提示词。

核心目的：

> 找出你反复让 Codex 做的事，把它们沉淀成可复用的技能、脚本、配置或子代理，减少重复劳动。

重点场景包括：

- CI 失败排查
- PR Review
- 测试失败定位
- 文档 / Changelog 更新
- 发布准备
- 部署验证
- 环境问题排查

作者强调：

- **先检查已有能力**
- **优先优化已有技能**
- **不要重复造 Skill**
- **只有高频、可复用、有验证步骤的任务才值得沉淀**
- **每周让 Codex 复盘一次**

---

##### 2. 深入浅出解读

这套方法本质上是：

> 让 AI 从“临时帮你干活”，进化成“越来越懂你工作流的助手”。

可以理解成三步：

###### 第一步：回看历史

让 Codex 看看你最近经常让它做什么。

比如你总是问：

- “帮我看 CI 为什么失败”
- “帮我整理 PR review 意见”
- “帮我找最小失败测试集”

这些就是重复工作流。

---

###### 第二步：判断是否值得固化

不是所有事情都要做成 Skill。

值得沉淀的任务通常有几个特点：

- 经常出现
- 每次都要你手动判断
- 有固定流程
- 有验证方法
- 能明显省时间

不值得沉淀的任务：

- 偶发问题
- 一次性调查
- 没有稳定流程
- 做成 Skill 反而增加维护成本

---

###### 第三步：选择合适形式

不同任务用不同方式处理：

| 类型 | 适合方式 |
|---|---|
| 高频固定流程 | Skill |
| 局部调查任务 | 子代理 |
| 已有能力不完善 | 优化旧 Skill |
| 只是缺资料 | 补 references |
| 重复命令 | 写 scripts |
| 不常用任务 | 不处理 |

重点不是“多造技能”，而是：

> 少而准，可验证，能复用。

---

##### 3. 我的意见

这个方法很有价值，尤其适合长期用 Codex / Claude Code / Cursor 的开发者。

它真正解决的是一个常见问题：

> AI 用久了，但没有变得更懂你，每次还是从零开始。

我建议这样用：

###### 每周固定复盘一次

比如周五下班前运行：

> 请复盘我本周的 Codex 使用记录，找出高频重复工作流，并判断是否需要优化技能、脚本、配置或子代理。

---

###### 不要急着创建 Skill

创建 Skill 前先问三件事：

1. 这个任务出现过 3 次以上吗？
2. 下次还会再遇到吗？
3. 有没有明确的执行和验证步骤？

如果答案不是“是”，就先别做。

---

###### 最值得优先沉淀的任务

我认为优先级最高的是：

1. **CI 失败排查**
2. **测试失败定位**
3. **PR Review 整理**
4. **发布前检查**
5. **部署验证清单**

这些任务重复率高，且很容易形成标准流程。

---

##### 4. 一句话结论

这不是简单的提示词技巧，而是让 Codex 形成“工作记忆”和“自我进化流程”：

> 定期复盘、高频沉淀、避免冗余，让 AI 越用越像你的专属开发助手。

## 结构化（1）

### 2026-06-02 07:07:19

##### 主旨概括

这篇内容分享了一套提升 OpenAI Codex 工作效率的提示词方法：让 Codex 定期复盘自己的使用记录，找出重复工作流，并判断是否需要复用、优化或新建技能。作者认为这类似 Hermes 的“自进化 skill”流程，并在原提示词基础上做了优化，重点是避免重复创建冗余技能。

##### 1. 背景：用复盘提升 Codex 效率

作者看到一位开发者分享的 Codex 使用技巧后，认为其核心思路是：

- 让 Codex 回顾近期使用记录；
- 识别反复出现的工作流或请求；
- 将高频、可复用的流程沉淀为技能；
- 对有限范围的调查任务，则可以设计成自定义子代理。

作者进一步优化了这套提示词，使其更适合长期使用，并建议将该任务置顶，每周末让 Codex 做一次“自我复盘”。

##### 2. 关注重点：真实开发维护任务

提示词要求 Codex 不要泛泛总结，而是重点关注真实的软件维护场景，例如：

- 持续集成失败；
- Pull Request 审核；
- 测试失败定位；
- 测试用例筛选；
- 变更记录管理；
- 文档更新；
- 发布准备；
- 部署验证；
- 本地启动；
- 故障排除；
- 环境问题排查。

这些任务通常反复出现、容易耗费开发者时间，因此适合被系统化、流程化。

##### 3. 核心规则：先盘点已有能力，再决定是否新增

作者强调，不能一发现重复任务就创建新技能，而是要先检查现有能力是否已经覆盖。

需要盘点的内容包括：

- 本地技能；
- 插件技能；
- agents 配置；
- references；
- scripts；
- `openai.yaml`。

对每个重复工作流，需要判断：

- 触发条件是否准确；
- 是否贴合真实使用记录；
- 是否缺少验证步骤；
- 是否容易误判环境、依赖、源码、CI 或外部服务问题；
- 是否需要补充 references、scripts、默认提示词或 agents/openai.yaml。

这一部分的核心思想是：优先复用和优化已有能力，避免重复造轮子。

##### 4. 新建技能的条件：必须真正可复用

作者提出，只有满足两个条件时，才应该创建新技能：

1. 任务确实是可重复使用的工作流程；
2. 现有技能或插件技能无法覆盖。

如果要创建新技能，必须先说明为什么现有能力不够用。

例如，如果经常遇到 CI 失败，并且每次都需要手动分析日志、定位失败原因、筛选相关测试，那么它可能适合沉淀成技能。

但如果只是一次性的调查或临时分析，就不应该创建技能。

##### 5. 子代理适用场景：有限范围的调查任务

对于一些边界明确、职责较窄的任务，作者建议不要做成完整技能，而是设计成自定义子代理模板。

文中给出的例子包括：

- 只读分析 CI 日志；
- 整理未解决的 PR review thread；
- 筛选最小失败测试集；
- 检查文档、变更记录、发布准备状态；
- 制作部署前验证清单。

通俗来说，技能更像“可复用流程”，子代理更像“专门干某类小任务的助手”。

##### 6. 输出要求：让 Codex 给出可执行结论

作者设计的提示词要求 Codex 输出保持简洁，并按以下结构组织：

1. 重复工作流清单；
2. 已有能力匹配情况；
3. 建议动作：复用、优化已有技能、新建技能、子代理模板或不处理；
4. 每个动作的原因和证据；
5. 如果实际创建或修改了内容，列出文件和校验结果；
6. 后续最值得补充的一个点。

这样做的好处是，Codex 不只是“总结问题”，还要给出明确的处理建议和依据。

##### 7. 判断标准：是否值得自动化

作者给出了判断某个流程是否值得沉淀的标准：

- 高频出现；
- 仍然需要用户手动判断；
- 有明确验证步骤；
- 能减少下次排障、PR、CI、测试、文档或发布准备的摩擦；
- 不增加无意义的维护负担。

也就是说，一个流程是否应该变成技能，关键不是“能不能做”，而是“是否真的能减少未来重复劳动”。

##### 8. 引用原思路与作者优化点

引用推文中的原始建议是：

> 将一段提示词复制到 Codex 中，让它查看最近的会话，识别重复工作流或重复请求。  
> 对持续手动处理的事情，建议创建：
> 1. 技能：适用于可复用工作流；
> 2. 自定义子代理：适用于有边界的角色或调查任务。

岚叔在此基础上做了更细化的约束：

- 增加“先盘点已有能力”；
- 强调不要创建重复技能；
- 要求创建或修改后必须运行校验；
- 要求说明改动文件和验证结果；
- 将任务范围聚焦到真实开发维护场景。

##### 9. 热门回复反馈

评论区有人提到 Claude Code 的 `/insights` 功能可以用于复盘，并询问 Codex 是否有类似功能。

- 可以减少重复造轮子的情况；
- 对提升日常开发效率有帮助。

##### 总结

这篇内容的核心价值在于：把 Codex 从“被动执行工具”变成“能定期复盘和优化工作流的开发助手”。通过每周检查重复任务、复用已有能力、谨慎创建新技能或子代理，可以持续降低 CI、PR、测试、文档和发布等开发维护工作的重复成本。
