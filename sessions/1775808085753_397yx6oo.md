## 正文

今天，我们正式发布 [Deep Agents 部署的](https://docs.langchain.com/oss/python/deepagents/deploy?ref=blog.langchain.com) Beta 版本。Deep Agents 部署是目前最快捷的方式，能够以生产就绪的方式部署与模型无关的开源代理框架。

Deep Agents 部署是为开放世界而构建的。它基于 [Deep Agents——](https://docs.langchain.com/oss/python/deepagents/overview?ref=blog.langchain.com) 一个开源的、与模型无关的代理框架。代理框架与内存紧密相关，这意味着选择开源框架就意味着您拥有自己的内存，而不是将其锁定在专有框架中或绑定到单一模型。

#### 线束工程 → 生产

在过去的几个月里， [“接口工程”](https://blog.langchain.com/the-anatomy-of-an-agent-harness/) 作为一门学科兴起，其目的是构建接口，将生命周期模型（LLM）转化为智能体。这些接口包含编排逻辑、工具和技能，它们构成智能体的基础，同时允许构建者提供自定义指令、工具和技能，以便根据自身用例定制接口。

要投入生产，需要经过以下几个步骤：

- 以多租户、可扩展的方式部署代理编排逻辑和内存。
- 设置沙箱，以便每个代理会话都启动一个沙箱。
- 搭建与代理交互的端点，从 MCP 到 A2A，再到其他用于人机交互、记忆等的端点。

今天，我们将所有这些步骤整合到一个命令中： `deepagents deploy`

#### What are you deploying?

使用 `deepagents deploy` 可以部署自定义代理。您需要指定一些参数：

- `model` ：要使用的大型语言模型。Deep Agents 可与任何模型或模型提供商配合使用，包括 OpenAI、Google、Anthropic、Azure、Bedrock、Fireworks、Baseten、Open Router 和 Ollama。有关更多信息，请参阅我们的 [模型](https://docs.langchain.com/oss/python/deepagents/models?ref=blog.langchain.com) 文档。
- `AGENTS.md` ：这是代理的核心指令集，您可以在其中指定在会话开始时加载的指令。
- `skills` ：这些是 [代理技能](https://agentskills.io/?ref=blog.langchain.com) ，允许使用专业知识（通过 Markdown 文件）和执行操作（通过运行脚本）。请参阅我们的 [技能文档](https://docs.langchain.com/oss/python/deepagents/skills?ref=blog.langchain.com) 了解更多信息。
- `mcp.json` ：这些是代理可以使用 MCP 协议（HTTPS/SSE）调用的工具。
- `sandbox` ：如有需要，您可以指定一个 [沙盒](https://docs.langchain.com/oss/python/deepagents/sandboxes?ref=blog.langchain.com) 环境供代理执行任务和运行技能。Deep Agents 默认集成了 Daytona、Runloop、Modal 或 LangSmith 沙盒。任何沙盒提供商均可与 Deep Agents 配合使用；请参阅我们的 [实施指南](https://docs.langchain.com/oss/python/contributing/implement-langchain?ref=blog.langchain.com#sandboxes) 。

![](https://storage.ghost.io/c/97/88/97889716-a759-46f4-b63f-4f5c46a13333/content/images/2026/04/Screenshot-2026-04-09-at-8.31.40---AM.png)

#### Deployment

在底层， `deepagents deploy` 将您的 Deep Agent 与它自己的 [LangSmith Deployment](https://docs.langchain.com/langsmith/deployment?ref=blog.langchain.com) 服务器捆绑在一起。这是一个可用于生产环境且可水平扩展的服务器。

它会启动一个拥有 30 多个端点的服务器，其中包括以下端点：

- MCP；因此您可以将已部署的代理称为工具
- A2A；因此，您可以在多代理设置中调用已部署的代理。
- [代理协议](https://github.com/langchain-ai/agent-protocol?ref=blog.langchain.com) ；因此您可以轻松编写美观的用户界面来与已部署的代理进行交互。
- [人机交互](https://docs.langchain.com/oss/python/deepagents/human-in-the-loop?ref=blog.langchain.com) ；因此，您可以为智能体在无人干预的情况下可以或不可以执行的操作添加限制。
- [内存端点](https://docs.langchain.com/oss/python/deepagents/memory?ref=blog.langchain.com) ；因此您可以轻松访问代理的短期或长期记忆。

![](https://storage.ghost.io/c/97/88/97889716-a759-46f4-b63f-4f5c46a13333/content/images/2026/04/Screenshot-2026-04-09-at-8.31.19---AM.png)

#### Open Ecosystem

`deepagents deploy` 的关键环节之一是融入开放的生态系统。具体来说：

- 我们使用 `deepagents` ，这是一个完全开源、采用 MIT 许可证的工具框架，支持 [Python](https://github.com/langchain-ai/deepagents?ref=blog.langchain.com) 和 [TypeScript。](https://github.com/langchain-ai/deepagentsjs?ref=blog.langchain.com)
- 我们使用 [开放标准](https://agents.md/?ref=blog.langchain.com) AGENTS.md 来指定代理指令。
- 我们使用 [开放标准](https://agentskills.io/?ref=blog.langchain.com) Agent Skills 来为代理人提供专业知识。
- 我们与所有模型提供商集成，让您拥有完全的控制权。无需受限于 Anthropologie，您可以根据任务需求选择最佳模型组合，甚至包括开源模型。
- 我们与所有沙箱提供商集成，因此您可以完全控制它。
- 我们通过 [MCP](https://a2a-protocol.org/latest/?ref=blog.langchain.com) 、 [A2A](https://a2a-protocol.org/latest/?ref=blog.langchain.com) 和 [Agent Protocol](https://github.com/langchain-ai/agent-protocol?ref=blog.langchain.com) （开放标准）公开代理。
- 您可以自行托管 LangSmith 部署，这允许您托管和拥有自己的内存。

#### 与 Claude Managed Agents 相比

[Claude Managed Agents](https://platform.claude.com/docs/en/managed-agents/overview?ref=blog.langchain.com) 是近期推出的另一款极具竞争力的产品。虽然其高层架构（包括基础架构、代理服务器和沙箱）与 Claude Managed Agents 类似，但 Claude Managed Agents 采用封闭式生态系统，造成了极强的客户锁定。

![](https://storage.ghost.io/c/97/88/97889716-a759-46f4-b63f-4f5c46a13333/content/images/2026/04/Screenshot-2026-04-09-at-8.50.43---AM.png)

#### Memory

开放生态系统对代理框架和代理平台至关重要的核心原因是内存。

代理框架与内存紧密相关（Sarah Wooders [就此写过一篇精彩的文章](https://x.com/sarahwooders/status/2040121230473457921?s=20&ref=blog.langchain.com) ）。框架的关键作用是管理上下文（内存本质上就是上下文）。随着框架越来越多的部分变得封闭，被 API 锁定，你的内存也会随之封闭。

实际上，从一个模型切换到另一个模型非常容易（当然，你可能需要稍微调整一下提示，但并不难）。因此，仅模型 API 本身并不会造成太大的锁定（正如我们最近看到的从 OpenAI 到 Anthropic 的迁移）。

当你开始将内存捆绑到这些 API 背后时——无论是短期还是长期——都会造成大量的锁定。

Imagine creating an internal SDR agent. It starts basic, but as it interacts with users it learns on the fly. This memory accumulates - but it’s all behind a closed API. If you want to move off of that harness, or off that model - that would mean reseting your agent’s memory, starting from scratch.

It’s even worse for agents that you expose to your customers. You build an external facing sales agent, that builds up memory of the clients it interacts with. All of these memories are behind a closed API. These memories are part of a data flywheel you should be building to make your customer’s experience better over time. But they are no longer yours - they belong to whomever owns that closed API.

`deepagents deploy` stores memory in a standard format ([AGENTS.md](http://agents.md/?ref=blog.langchain.com), skills, and other files), allows you to query them directly via API, and if you self host ensures that memory always remains in your databases only.

#### Try out an open harness

Building agents on top of a proprietary harness and creates an incredible amount of lock in. We believe in a world where agent building and deployment should be easy, but you still have a choice of model selection and you still own your own memory.

If you believe in that as well, try out `deepagents deploy` today.

#### 主旨概括

这篇文章主要介绍了**Deep Agents Deploy 的 Beta 版本**：它把 “开发一个代理” 到 “把代理生产化部署” 之间的复杂步骤，压缩成一个命令`deepagents deploy`。  
作者强调，它最大的价值不只是 “部署快”，更在于**开放生态、模型无关、内存可自持**，从而避免像封闭式代理平台那样造成严重锁定。

##### 1. 发布内容：把代理部署简化成一个命令

- Deep Agents Deploy 被定位为：**目前最快捷的方式之一**，可以把一个**生产就绪**、**模型无关**的开源代理框架部署起来。  
- 它基于开源框架**Deep Agents**，面向 “开放世界” 设计，而不是绑定某一家模型厂商或专有平台。  
- 作者的核心主张是：**代理框架和内存密不可分**，选开源框架，本质上也是在选择 “自己掌控内存”，而不是把记忆锁进封闭系统里。

##### 2. 为什么需要它：代理从原型到生产，通常很麻烦

文章先解释了当前 “代理工程（原文作‘接口工程’）” 的背景：

- 最近几个月，围绕 LLM 构建智能体的 “接口 / 框架工程” 快速兴起。  
- 这些接口通常会提供：
  - 编排逻辑
  - 工具调用
  - 技能系统
  - 自定义指令
- 但真正上线到生产环境，通常还要补齐 3 类关键能力：
  - **可扩展的多租户部署**：托管代理编排逻辑和内存
  - **沙箱环境**：每个代理会话启动独立沙箱
  - **交互端点**：如 MCP、A2A，以及人机交互、记忆访问等接口

作者想解决的问题很直接：  
- 以前这些步骤要分开搭，**现在整合成一个命令**：`deepagents deploy`

##### 3. 部署时需要提供什么：代理的几个核心组成部分

使用`deepagents deploy`时，需要提供一些关键配置，文章逐项做了说明：

- `model`：指定要使用的大模型  
  - 支持范围很广，包括**OpenAI、Google、Anthropic、Azure、Bedrock、Fireworks、Baseten、Open Router 和 Ollama**
  - 这体现了它的 “**模型无关**” 定位

- `AGENTS.md`：代理的核心指令集  
  - 用于定义会话开始时加载的规则和行为

- `skills`：代理技能  
  - 可以通过**Markdown 文件**提供专业知识
  - 也可以通过**运行脚本**来执行操作

- `mcp.json`：代理可调用的 MCP 工具配置  
  - 基于**MCP 协议（HTTPS/SSE）**

- `sandbox`：沙箱环境  
  - 用于让代理执行任务和运行技能
  - 默认已集成**Daytona、Runloop、Modal、LangSmith Sandbox**
  - 也支持接入其他沙箱服务商

可以理解为：  
- `AGENTS.md`决定 “这个代理应该怎么思考和做事”  
- `skills`决定 “它会什么”  
- `mcp.json`决定 “它能调用哪些外部工具”  
- `sandbox`决定 “它在哪里安全执行任务”

##### 4. 部署后得到什么：一个可生产使用、可横向扩展的服务

文章说明，`deepagents deploy`底层会把你的 Deep Agent 和它自己的**LangSmith Deployment 服务器**打包在一起。

它的特点是：

- **可用于生产环境**
- **支持水平扩展**
- 会启动一个有**30 多个端点**的服务器

这些端点包括：

- **MCP**
  - 让已部署代理可以被其他系统当作工具调用

- **A2A**
  - 让它能在多代理体系中被其他代理调用

- **Agent Protocol**
  - 方便开发 UI，与代理交互

- **人机交互端点**
  - 可以限制代理哪些操作能自动做、哪些不能自动做

- **内存端点**
  - 可直接访问代理的短期记忆和长期记忆

这意味着，部署后得到的不是一个 “只能聊天的机器人”，而是一个带完整接口层、可集成到企业系统中的代理服务。

##### 5. 它为什么强调 “开放生态”：不只开放代码，更开放标准和基础设施

这一部分是全文重点。作者列出 Deep Agents Deploy 的 “开放性” 体现：

- 使用的是**完全开源、MIT 许可证**的`deepagents`
  - 并且同时支持**Python 和 TypeScript**

- 代理指令采用开放标准**AGENTS.md**

- 代理技能采用开放标准**Agent Skills**

- 集成**所有模型提供商**
  - 不必被单一厂商绑定
  - 可以根据任务选择不同模型，甚至使用开源模型

- 集成**所有沙箱提供商**
  - 运行环境也不被锁死

- 通过**MCP、A2A、Agent Protocol**这些开放标准暴露代理能力

- 支持**自行托管 LangSmith Deployment**
  - 这意味着你可以真正 “拥有自己的内存”

作者的立场很明确：  
- 开放生态的意义，不是 “看起来自由”，而是让企业对模型、部署方式、工具协议和记忆数据都有控制权。

##### 6. 与 Claude Managed Agents 的对比：核心不是功能像不像，而是谁掌控数据和记忆

文章点名对比了**Claude Managed Agents**：

- 作者承认，两者在高层架构上其实相似：
  - 都有基础设施
  - 都有代理服务器
  - 都有沙箱

- 但他认为 Claude Managed Agents 的问题在于：
  - 它是**封闭生态系统**
  - 会带来**很强的客户锁定（lock-in）**

换句话说，表面上两者都能部署代理，  
但作者更关心的是：  
- 你到底是在 “部署自己的代理”，还是 “租用别人平台里的代理能力”。

##### 7. 为什么 “内存” 才是最大锁定点：模型可切换，记忆却很难迁移

这是文章论证最核心的一段。

###### 7.1 作者的核心判断

- 代理框架最关键的职责之一，就是管理上下文
- 而**内存本质上就是上下文**
- 所以，一旦框架封闭，内存也会被一起封闭

###### 7.2 为什么模型本身反而没那么可怕

- 作者认为，从一个模型切换到另一个模型，通常并不难  
- 可能只需要稍微调整提示词  
- 文中还举到近来的现实例子：
  - **从 OpenAI 迁移到 Anthropic**已经说明，单纯模型 API 本身并不会带来特别强的锁定

###### 7.3 真正难迁移的是 “带记忆的代理”

只要你把短期或长期记忆绑定到封闭 API 后面，锁定就会急剧加深。

作者举了两个非常具体的例子：

- **内部 SDR 销售代理**
  - 一开始很简单
  - 但随着与用户互动，它会持续学习并积累记忆
  - 如果这些记忆都在封闭 API 背后，那么一旦你想迁移框架或模型，就等于：
    - **重置代理记忆**
    - **从零开始**

- **面向客户的外部销售代理**
  - 它会积累与客户互动的历史记忆
  - 这些记忆本应成为持续优化客户体验的 “数据飞轮”
  - 但如果存在封闭 API 里，这些资产实际上就不再完全属于你

作者想表达的是：  
- 企业真正宝贵的，不只是调用了哪个模型  
- 而是代理在长期运行中形成的 “可持续学习能力” 和 “用户关系记忆”

##### 8. Deep Agents Deploy 如何解决 “内存被锁住” 的问题

针对上面的风险，文章给出的方案是：

- 将内存存储为**标准格式**
  - 如`AGENTS.md`、`skills`和其他文件

- 提供 API，允许你**直接查询这些记忆**

- 如果选择**自托管**
  - 那么记忆会始终保留在**你自己的数据库**里

这意味着：

- 你的代理逻辑不是黑盒
- 你的记忆资产不是平台私产
- 未来想换模型、换框架、换部署方式，迁移成本会更低

##### 9. 结尾呼吁：不要在专有代理框架上积累长期锁定

文章最后给出一个明确结论：

- 在专有 harness（代理承载框架）上构建代理，会带来**极高的锁定成本**
- 作者相信，更好的世界应该是：
  - 构建代理很容易
  - 部署代理也很容易
  - 但你仍然能自由选择模型
  - 同时保有自己的内存

因此，他呼吁认同这一理念的开发者去尝试**Deep Agents Deploy**。
