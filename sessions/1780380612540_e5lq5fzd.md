#### 总结

Shopify 的 AI 编程实践核心不是“用哪个工具”，而是**把 AI 当成团队工程基础设施**：

1. **统一入口**：用 LLM Proxy 管理 Claude、Copilot、Cursor 等工具，统一控成本、看用量、换模型。
2. **并行 Agent**：大任务拆开，让多个 Claude Code 同时干不同模块，人负责审查和合并。
3. **反复自我批判**：架构方案不要信第一版，让 AI 多轮找漏洞、修正方案。
4. **接入真实系统**：通过 MCP 让 AI 访问文档、CLI、数据库、GitHub、Slack 等真实工具。
5. **共享上下文**：把 `CLAUDE.md` 提交到仓库，写清项目规则、命令、目录结构。
6. **限制权限**：允许改代码、跑测试；禁止 push、deploy、删库、读 secrets。
7. **人转向策略**：AI 负责更多执行，人更多判断需求、架构、用户流程。

---

#### 解读

##### 1. AI 编程的关键不是“聊天”，而是“工程化”

很多人用 AI 还停留在：

> 我问一句，AI 答一句。

Shopify 的做法是：

> 把 AI 接进研发流程，像接 CI/CD、监控、权限系统一样管理。

这意味着 AI 不再只是个人效率工具，而是团队级生产力系统。

---

##### 2. 多 Agent 并行，本质是“让 AI 分工”

以前一个工程师写代码是串行的：

> 先写登录，再写支付，再写测试，再写文档。

现在可以变成：

> 一个 AI 改登录，一个 AI 写支付测试，一个 AI 更新文档。

人不再从零写，而是像“技术负责人”一样：

- 看 diff
- 判断质量
- 取舍方案
- 合并结果

---

##### 3. `CLAUDE.md` 很重要

它相当于给 AI 的“项目说明书”。

里面不该写长篇大论，只放最关键的信息：

- 技术栈
- 常用命令
- 目录结构
- 代码规范
- 禁止事项

重点是：**让团队里的所有 AI 都遵守同一套规则。**

---

##### 4. AI 越强，人越要会判断

AI 写代码越来越快后，真正稀缺的不是“敲代码”，而是：

- 需求对不对？
- 用户流程顺不顺？
- 架构能不能撑住？
- 哪个方案值得做？
- 哪些代码应该删掉？

所以瓶颈从：

> 写不出来

变成：

> 不知道该写什么、不知道该不该写。

#### 我的意见

##### 最值得学的 3 点

###### 1. 先建统一入口

团队别每个人随便用不同 AI 工具，否则成本、权限、数据都难管。

应该尽早做：

- 统一模型入口
- 统一日志
- 统一权限
- 统一成本统计

---

###### 2. 必须写 `CLAUDE.md`

这是最简单、最便宜、最立竿见影的做法。

不需要复杂系统，先在仓库放一个 60 行以内的说明文件，就能明显提升 AI 输出质量。

---

###### 3. 权限一定要收紧

AI 可以帮你改代码，但不能让它随便：

- 部署
- 删除数据
- 读取密钥
- 推送主分支
- 执行危险命令

AI 应该是“实习工程师”，不是“超级管理员”。

---

#### 一句话结论

**AI 编程的下一阶段，不是比谁 prompt 写得好，而是比谁能把 AI 更安全、更系统地嵌进研发流程。**

## 结构化（1）

### 2026-06-02 07:07:19

##### 主旨概括

文章总结了 Shopify 面向 **2.3 万名工程师**使用 Claude Code 等 AI 编程工具的配置思路：核心不是简单“让 AI 写代码”，而是通过统一入口、并行 agent、真实系统接入、权限控制和团队上下文管理，把 AI 变成可控的工程协作基础设施。

---

##### 1. 统一 AI 入口：先搭 LLM Proxy

Shopify 没有把工程团队绑定在某一个 AI 工具上，而是先搭了一层统一的 **LLM proxy / gateway**。

- Claude Code、Copilot、Cursor 等工具都通过同一个入口访问模型。
- 后端可以接入 OpenAI、Anthropic、Google 等不同模型供应商。
- 好处是：
  - 统一统计用量；
  - 控制成本；
  - 做模型路由；
  - 未来更换模型时，工程师不用重搭工作流。

**简单理解：**  
不是每个工具各自直连模型，而是先经过公司统一网关，方便管理和切换。

---

##### 2. 大任务用 Parallel Agents：不要只当聊天框

文章强调，不要把 Claude Code 当成单个聊天窗口使用。面对复杂任务时，应拆成多个子任务，让多个 agent 并行工作。

例如一个大功能可以这样分工：

- 一个 agent 修改认证逻辑；
- 一个 agent 编写 payment flow 测试；
- 一个 agent 更新 API 文档。

人的角色不再是逐行写代码，而是：

- 查看 diff；
- 判断输出是否靠谱；
- 丢掉错误结果；
- 合并可用部分。

**关键点：**  
AI 负责并行探索和执行，人负责审查、筛选和整合。

---

##### 3. 架构问题用 Critique Loop：让 AI 自我审查

写代码可以多 agent 并行，但架构决策更适合让一个 agent 进行多轮反思和批判。

推荐的 prompt 思路是：

1. 先给出方案；
2. 批判该方案在规模扩大时可能出现的问题；
3. 基于批判修订方案；
4. 再次批判修订版；
5. 最后给出每个决策的置信度。

**核心建议：**  
不要急着采用 Claude 的第一版答案，要让它先找出自己方案里的漏洞，再逐步改进。

---

##### 4. 让 Claude 访问真实系统：接入 MCP

Shopify 开源了 `shopify-dev-mcp`，让 Claude Code 能直接接触真实开发环境，而不是只停留在文本层面。

它可以帮助 Claude：

- 查询最新文档；
- 验证 GraphQL schema；
- 运行 Shopify CLI；
- 处理产品、metafields、themes；
- 执行 bulk operations 等批量操作。

其他团队也可以接入自己日常使用的 MCP，例如：

- GitHub；
- Slack；
- 数据库；
- 内部文档系统。

**意义：**  
AI 不只是“凭记忆回答”，而是能查真实资料、运行真实命令、验证真实系统状态。

---

##### 5. 把 CLAUDE.md 提交到 Git：共享团队上下文

文章建议把 `CLAUDE.md` 当作团队共享上下文，提交到代码仓库中，让所有 agent 都能看到同一套项目规则。

内容应控制在 **60 行以内**，只放最重要的信息，例如：

- 技术栈；
- 常用命令；
- 目录结构；
- 硬性规则。

原文特别提醒：  
不要塞太多标准和说明，因为这些内容每次都会进入上下文，过多会拖慢每一轮响应。

**本质：**  
`CLAUDE.md` 是把团队里的隐性知识显性化，让 AI 按团队习惯工作。

---

##### 6. 权限先收紧：可逆操作交给 AI，不可逆操作留给人

Agent 可以被允许做一些低风险操作，例如：

- 读文件；
- 改代码；
- 跑测试；
- 执行 lint；
- 查看 git status；
- 查看 diff；
- commit。

但高风险操作应直接禁止，例如：

- push；
- deploy；
- 删除数据库；
- `rm -rf`；
- 读取 `.env`；
- 访问 secrets。

**原则：**  
默认可以接受 AI 的编辑，但任何不可逆、高风险操作都必须由人来决定。

---

##### 7. 工程师时间分配变化：从执行转向策略验证

原文提到，Shopify 的工程时间分配正在发生变化：

- 过去：**70% 执行，30% 策略**；
- 现在：**70% 策略，30% 执行**。

当 AI 能写更多代码后，人的价值不再主要是“敲代码”，而是判断：

- 用户流程是否合理；
- 需求是否成立；
- 架构应该怎么选；
- 哪个方案更值得做。

文章提到的 **20% productivity gain**，并不是来自更快完成同一个方案，而是来自更快尝试 **10 个不同方案**。

**关键变化：**  
AI 编程的瓶颈正在从“写不出来”，转向“是否知道该写什么、该选什么方案”。

---

##### 总结

Shopify 的做法说明，真正有效的 AI 编程不是简单给工程师发一个 Claude Code，而是要建立一整套工程化机制：统一入口、并行 agent、真实系统接入、共享上下文、严格权限和策略优先。  
未来拉开团队差距的，不只是 AI 写代码的速度，而是团队能否更快验证方向、做出更好的技术和产品决策。

- 处理 bulk operations

这说明 AI coding 的下一个关键不只是模型能力，而是：

> AI 是否能接触真实上下文、真实工具、真实系统状态。

没有 MCP / 工具接入的 AI，很容易停留在“凭记忆写代码”。  
接入真实系统后，它才更像一个能工作的工程助理。

---

###### 1.5 CLAUDE.md 是“团队隐性知识显性化”的抓手

把 `CLAUDE.md` 提交到 git，本质不是写提示词，而是把团队共识沉淀下来：

- 技术栈
- 常用命令
- 目录结构
- 硬规则
- 禁止事项
- 测试方式
- 代码风格

但重点是：**控制在 60 行以内。**

这很关键。  
因为上下文不是越多越好，AI 每一轮都要读取这些内容。太多规则会带来：

- 成本增加
- 响应变慢
- 注意力稀释
- 模型抓不住重点
- 输出反而变差

所以 `CLAUDE.md` 的本质是：  
**用极简规则约束 agent，而不是把公司 wiki 全塞进去。**

---

###### 1.6 权限设计决定 AI Agent 能不能进入生产级工作流

Shopify 的思路是：

允许 agent：

- 读文件
- 改代码
- 跑测试
- lint
- 看 git status
- 看 diff
- commit

禁止 agent：

- push
- deploy
- 删除数据
- `rm -rf`
- 读取 `.env`
- 读取 secrets
- 做不可逆操作

这套设计说明：

> AI Agent 要进入真实工程流，必须先做权限边界，而不是先追求全自动。

真正成熟的自动化不是“什么都让 AI 做”，而是：

- 可逆操作交给 AI
- 不可逆操作交给人
- 高频低风险任务自动化
- 高风险关键动作人工确认

---

###### 1.7 AI 编程让人的时间从执行转向策略验证

原文提到一个重要变化：

> 工程时间从 70% 执行、30% 策略，变成 70% 策略、30% 执行。

这可能是整篇最有价值的观点。

AI 写代码以后，人的瓶颈不再是：

- 会不会写
- 写得快不快
- 能不能实现

而变成：

- 这个需求是否成立？
- 用户流程是否合理？
- 架构选择是否正确？
- 哪个方案值得做？
- 哪些代码不该写？
- 哪些复杂度不该引入？
- 如何验证商业假设？

也就是说，AI 不是简单把“写代码”加速，而是把人推向更高阶的判断工作。

##### 2. 高价值信息深挖

###### 2.1 LLM Proxy 是 AI 工程化的基础设施

很多团队会直接从 Cursor、Claude Code、Copilot 开始，但这会导致几个问题：

| 问题 | 后果 |
|---|---|
| 工具分散 | 无法统一管理成本和权限 |
| 模型绑定 | 换模型成本高 |
| 上下文不可控 | 每个人喂给 AI 的信息不同 |
| 缺乏审计 | 不知道 AI 访问了什么、改了什么 |
| 成本黑箱 | 无法按团队、项目、任务统计消耗 |

LLM Proxy 的价值在于把这些问题集中管理。

它不是一个“高级功能”，而是当团队规模扩大后必须出现的中间层。

可类比为：

- API Gateway 之于微服务
- IAM 之于云服务
- CI/CD 之于工程交付
- CRM 之于销售流程

未来 AI 团队也需要自己的：

> AI Gateway + Context Layer + Permission Layer + Observability Layer

---

###### 2.2 Parallel Agents 的核心不是“多开几个窗口”，而是任务可分解性

并行 agent 能发挥作用，前提是任务可以被清晰拆分。

适合并行的任务：

- 单元测试补充
- API 文档更新
- 前端组件改造
- 数据结构迁移草案
- 多语言 i18n 修改
- lint / 类型修复
- 分模块重构
- PR review 辅助
- 兼容性检查

不适合粗暴并行的任务：

- 核心架构设计
- 强耦合模块改造
- 复杂状态管理
- 业务规则含糊的需求
- 需要大量产品判断的功能
- 涉及安全、支付、权限的关键路径

所以 parallel agents 不是越多越好，而是要看：

- 任务边界是否清晰
- 上下文是否隔离
- 输出是否容易 review
- 失败是否可回滚
- 多个 agent 之间是否会互相覆盖

---

###### 2.3 Critique Loop 是 AI 时代的“架构评审增强器”

对产品开发来说，最值得迁移的不是某个 prompt，而是 critique loop 的思维。

你可以把它用于：

###### 产品方案

```text
先给一个功能方案。
然后批判这个方案在用户体验、转化率、留存、实现复杂度上的问题。
再基于批判修订。
最后给出最值得验证的 3 个假设。
```

###### 商业模式

```text
先设计一个商业模式。
然后批判其获客成本、毛利、复购、渠道依赖、规模化风险。
再修订。
最后给出关键验证指标。
```

###### 增长策略

```text
先给增长方案。
再批判渠道可持续性、转化漏斗、内容供给、预算风险。
然后修订。
最后输出 30 天实验计划。
```

###### 技术架构

```text
先给架构方案。
批判其在 scale、安全、成本、维护性、团队能力匹配上的问题。
修订后再次批判。
最后给出每个决策的置信度。
```

这类 prompt 的价值在于：  
它把 AI 从“答案生成器”变成“思考对手”。

---

###### 2.4 MCP 的本质是让 AI 从“语言系统”进入“操作系统”

没有 MCP，AI 主要依赖：

- 训练记忆
- 用户贴上下文
- 静态代码片段
- 猜测 API 行为

有 MCP 后，AI 可以：

- 查实时文档
- 调用内部工具
- 查询数据库
- 读取任务系统
- 检查 GitHub PR
- 调用 Slack 记录
- 运行 CLI
- 验证 schema
- 触发测试

这意味着 AI 的角色变化了：

| 阶段 | AI 角色 |
|---|---|
| 无工具 | 问答助手 |
| 有代码上下文 | 编程助手 |
| 有 MCP | 工作流助手 |
| 有权限系统 | 半自动员工 |
| 有审计与回滚 | 可生产化 agent |

所以对产品和商业系统构建者来说，MCP 的真正价值不是“炫技”，而是打通：

> AI → 工具 → 数据 → 操作 → 反馈

###### 2.5 手工记忆管理可能比自动 RAG 更有效

热门回复里提到一个很有价值的观点：

> 手工管理记忆，分话题用 markdown 保存，实际比 RAG + 向量数据库 + 自动记忆好用。

这背后有一个重要现实：  
很多团队盲目上 RAG，但效果差，原因通常不是技术不够，而是知识本身没有被整理。

常见问题：

- 文档过时
- 文档互相矛盾
- 粒度太碎
- 没有优先级
- 没有业务背景
- 没有“当前有效版本”
- 自动记忆记了一堆垃圾
- 真正重要的信息没被写进去

因此，对小团队而言，更实用的做法可能是：

```text
先用 markdown 手工沉淀关键知识
再按项目 / 话题 / 决策分类
再接入 AI
最后才考虑 RAG 或向量数据库
```

不要一开始就追求复杂知识库。  
先保证“知识是干净的、当前有效的、被人认可的”。

##### 4. 反方与张力

###### 4.1 “Shopify 2.3 万工程师”的说法可能需要谨慎看待

原文来自推文转述，里面有一些表述可能带有传播性夸张，比如：

- “23,000 engineers”
- “automate 96% coding”
- “exact config you can copy”

这些数字和措辞需要二次验证。

但即使数字有夸张，背后的工作流仍然有参考价值：

- AI gateway
- parallel agents
- critique loop
- MCP
- repo-level context
- permission boundary
- 策略时间增加

所以重点不是相信每个数字，而是吸收方法论。

---

###### 4.2 多 agent 并行会带来管理复杂度

并行 agent 听起来很美，但也有副作用：

- diff 冲突增加
- 上下文不一致
- 代码风格漂移
- 多个 agent 重复劳动
- review 成本上升
- 人类被迫处理大量半成品
- 低质量输出反而拖慢进度

如果任务拆分能力不强，多 agent 不是提效，而是制造噪音。

适用前提：

- 代码结构清晰
- 模块边界明确
- 测试覆盖足够
- review 流程成熟
- 人能快速判断输出质量

---

###### 4.3 CLAUDE.md 太少不够，太多又拖慢

这里有一个张力：

- 信息太少：AI 不懂项目约束
- 信息太多：上下文污染，响应变慢，重点稀释

所以最佳实践不是“写越详细越好”，而是：

> 把稳定、重要、高频、强约束的信息写进去。

不适合放进去：

- 长篇业务历史
- 过时规范
- 低频细节
- 大段 API 文档
- 模糊价值观
- 团队口号
- 临时需求

适合放进去：

- 技术栈
- 命令
- 目录
- 禁止事项
- 输出格式
- 代码硬规则

---

###### 4.4 MCP 连接真实系统后，能力提升与风险同步提升

MCP 的价值在于让 AI 能操作真实系统。  
但风险也在于它能操作真实系统。

风险包括：

- 误读数据
- 泄露敏感信息
- 错误执行命令
- 调用过时工具
- 修改错误资源
- 访问超出权限的数据
- 把测试环境和生产环境混淆

所以 MCP 必须配合：

- 权限隔离
- 环境隔离
- 审计日志
- 人工确认
- 操作白名单
- secret 防护
- 回滚机制

否则 MCP 会从生产力工具变成事故入口。

---

###### 4.5 AI 让策略更重要，但不代表执行不重要

“70% 策略、30% 执行”容易被误解为：以后代码不重要了。

更准确的理解是：

> AI 降低了执行成本，但没有消除执行质量的重要性。

甚至因为生成代码变快，团队更需要：

- 更强测试
- 更强架构约束
- 更强代码审查
- 更强产品判断
- 更强数据验证
- 更强版本管理

AI 会放大人的判断力，也会放大团队的混乱。

##### 5. 情境化落地

###### 5.1 个人开发者怎么落地

如果你是独立开发者，不需要一开始搭复杂 gateway。可以先做：

1. 在每个项目根目录创建 `CLAUDE.md` 或 `AGENTS.md`
2. 把技术栈、命令、目录、硬规则写进去
3. 用 Claude Code / Cursor 处理小任务
4. 大任务拆成多个分支或多个终端
5. 每次只让 AI 改一个清晰模块
6. 禁止 AI 读取 `.env`
7. 每次看 diff，而不是盲目接受
8. 用 critique loop 做架构和产品判断

个人最重要的是：

> 别把 AI 当外包，先把自己变成会调度 AI 的产品 / 技术负责人。

---

###### 5.2 3-10 人创业团队怎么落地

推荐优先做 5 件事：

###### 第一，建立统一项目上下文

每个 repo 都有：

- `CLAUDE.md`
- README
- 常用命令
- 测试说明
- 禁止事项

###### 第二，建立 AI 使用规范

明确：

- 哪些任务可以交给 AI
- 哪些任务必须人工 review
- 哪些信息不能喂给 AI
- 哪些操作禁止 AI 执行

###### 第三，建立 prompt 模板库

例如：

- 架构评审模板
- PR review 模板
- 测试生成模板
- 产品方案 critique 模板
- 数据分析模板

###### 第四，优先接入高频工具

可以考虑 MCP 或简单脚本接入：

- GitHub
- Linear / Jira
- Slack / 飞书
- Notion / Confluence
- 数据库只读视图
- 内部 API 文档

###### 第五，把 AI 用在“多方案验证”而不是只用来赶工

例如让 AI 同时生成：

- 3 个 landing page 版本
- 3 个 pricing 方案
- 3 个 onboarding flow
- 3 个技术实现方案
- 3 组 A/B test 假设

目标不是更快写完一个方案，而是更快排除错误方案。

###### 5.3 中大型团队怎么落地

中大型团队需要更系统化：

###### 基础设施层

- LLM Gateway
- 统一模型路由
- 成本监控
- 权限控制
- 日志审计
- prompt 版本管理
- 上下文管理

###### 工程工作流层

- repo-level context
- agent 权限边界
- PR review agent
- test generation agent
- documentation agent
- CI/CD 集成
- sandbox 环境

###### 安全与治理层

- secret scanning
- PII 过滤
- 操作白名单
- 风险操作人工确认
- 生产环境隔离
- 数据访问分级
- 合规审计

###### 组织层

- AI 使用培训
- 最佳实践沉淀
- prompt 模板共享
- 成本归属机制
- AI 代码质量评估
- 人类 review 责任制

###### 结论一：AI 编程不是工具问题，而是系统问题

更应该问：

> 我的团队是否有统一入口、上下文、权限、审计、成本和工作流？

###### 结论二：AI 的核心价值不是更快写代码，而是更快验证方案

20% productivity gain 不一定来自更快敲完同一个方案，而是来自：

> 更快尝试 10 个方案，淘汰 9 个，留下 1 个。

---

###### 结论三：人类角色正在从 coder 变成 reviewer、architect、product strategist

AI 越强，人越需要负责：

- 判断
- 取舍
- 验证
- 审查
- 约束
- 定义问题

---

###### 结论四：上下文管理会成为 AI 团队的新护城河

`CLAUDE.md`、MCP、内部文档、prompt 模板、权限规则，本质都在解决同一个问题：

> 如何让 AI 在正确上下文中做正确的事。

---

###### 结论五：AI 自动化的边界应该是“可逆性”

一句话原则：

```text
可逆的，交给 AI。
不可逆的，留给人。
高频低风险，自动化。
低频高风险，人工确认。
```

---

##### 7. 一句话总结

Shopify 这套做法真正值得学习的不是 Claude Code 本身，而是它把 AI 编程从“个人提效工具”升级成了“团队级工程系统”：统一入口、并行 agent、批判循环、真实工具接入、共享上下文、权限边界，以及从执行转向策略验证的工作方式。
