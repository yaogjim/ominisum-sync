## 分析要点

- **核心高价值点**：将消息、补丁、审查、审批和工作流统一存储为带签名的事件，使人类与代理共享身份模型、上下文和可追溯审计记录。
- **留存建议**：选择性存档，适合作为智能体协作空间与可信审计架构的产品案例（提出了将人员、代理、代码和对话统一为可签名事件的架构思路，对Agent工作空间设计具有参考价值。）

**知识要点**

- 分散在聊天、代码托管、持续集成和代理工具中的上下文，会在系统衔接处持续损失并限制代理能力。
- 统一的签名事件模型可将协作记录、代码变更和审批过程纳入同一可搜索、可审计的数据层。
- 让代理成为工作空间中的平等身份主体，需要同时提供密钥、频道、权限边界和完整审计轨迹。

**行动项**

- 查看Buzz代码仓库和文档，评估其事件模型、自托管中继及现有Agent适配方式。
- 选择一个功能分支进行小规模试验，将对话、补丁、持续集成结果和审查记录放入同一频道。
- 重点验证代理权限作用域、私密数据隔离、审计完整性和令牌效率。

### 我们为什么这么热闹

昨天我们发布了 buzz。它是一个开源工作空间，通过一个加密身份系统，将人员、代理、对话和代码置于同等地位。我们构建它是为了减少对 Slack 和 GitHub 的依赖，并且我们分享它，以便任何人都能做同样的事情。

它解决的最大问题是上下文。如今，团队将工作分散在聊天工具、代码托管平台、持续集成系统以及如今一堆不断变化的代理工具上。每个衔接点都会丢失信息……而代理工具对此感受最深。它们无法处理自己看不到的信息。

我们比大多数人更早察觉到这一点。Block 正在将自身重塑为一个智能体。Goose，我们于 2025 年初开发并开源的代理基底，每天在公司内部广泛应用，我们探索得越深，工具之间的衔接问题就越成为瓶颈。Buzz 解决了我们遇到的很多问题。

buzz 将所有内容存储为带签名的事件，存储在您自行托管的中继节点上。每条消息、补丁、审查、工作流步骤和审批都被如此存储。一条记录对应一次搜索。人员和代理拥有相同类型的身份：各自的密钥、频道以及审计跟踪。buzz 上的代理是团队中平等的一员。它可以搜索历史记录、打开代码库、发送补丁、审查代码、运行工作流和编辑画布。它所做的一切都经过签名且可追溯，这建立了信任和问责制。

我们秉持的一些原则：

1. 自我主权：运行你自己的中继。拥有你的域名和数据。随身携带你的密钥。
2. 开源：Apache 2.0 协议，基于 nostr 构建，模型无关。支持 goose、Codex 和 Claude 代码。无锁定，包括对我们的锁定。
3. 一个场景：功能分支成为一个频道。补丁、持续集成结果、审查以及合并决策与塑造它们的对话位于同一个对话线程中。代码审查成为一种带有永久记录的对话。

还很早！频道、线程、私信、画布、媒体、搜索、审计日志、工作流以及桌面应用今天都已可用。完整的 Git 托管功能正在搭建中。移动端和推送功能即将推出。审批流程已部分完成。每个工作区都通过单个中继节点运行，因此中继节点间的联邦化是实现我们设计所指向的完全去中心化的最清晰路径。

更大的工作还在前方：对代理进行更严格的作用域控制，以便它们能在某些内容保持私密的工作空间中运行；为不想自行管理基础设施的团队提供托管选项；令牌效率（我们在此已做了大量工作）；以及基于开放规范的工作流和代理生态系统。能够进行交易的代理似乎是我们下一步发展的自然方向。

我们认为 Buzz 是真正的社交型 AI。到目前为止，这个类别指的是人们与 AI 伙伴聊天、AI 填充人类的信息流或聊天内容，或是智能体在人们旁观时相互交流。而人们和智能体作为同一网络中平等的成员共同协作，似乎是第一个有趣且持久的版本。

我们将在 Buzz 上运行越来越多的 Block。这是我们最关心的第一个测试。第二个是它对你是否有用。一切都是开放的。来和我们一起构建吧！

## 结构化（1）

### 2026-07-23 05:23:50

#### 《我们为什么这么热闹》内容总结

Buzz 是 Block 推出的开源协作工作空间，旨在把人类、AI 智能体、对话与代码统一到同一套可追溯系统中，减少团队对 Slack、GitHub 等分散工具的依赖。其核心愿景是：让人和智能体成为协作网络中地位平等、可信且可问责的成员。

##### 1. 要解决的核心问题：上下文割裂

- 现代团队的工作分散在聊天、代码托管、持续集成（CI）和各种 AI 智能体工具中。
- 信息每经过一次工具切换，就可能丢失部分上下文。
- 这一问题对智能体尤其严重：**它们无法理解或处理自己看不到的信息**。
- Buzz 因此试图把沟通、代码、审查、工作流和审批放进同一系统，形成完整且可搜索的工作记录。

##### 2. 项目背景：Block 的智能体化实践

- Block 正尝试将自身重塑为一个更依赖 AI 智能体运行的组织。
- 公司在**2025 年初**开发并开源了智能体基础平台**Goose**，目前已在 Block 内部被广泛日常使用。
- 随着应用深入，团队发现不同工具之间的衔接逐渐成为主要瓶颈，Buzz 正是针对这些实际问题构建的解决方案。

##### 3. Buzz 如何运作

- Buzz 将消息、代码补丁、审查意见、工作流步骤和审批等内容，统一保存为**带数字签名的事件**。
- 数据存放在用户自行托管的**中继节点（Relay）**上，团队可以掌握自己的基础设施和数据。
- 人类与智能体使用相同类型的身份体系，包括：
  - 独立密钥
  - 专属频道
  - 完整审计记录
- 智能体可以像普通团队成员一样：
  - 搜索历史记录
  - 打开代码库
  - 提交补丁
  - 审查代码
  - 执行工作流
  - 编辑协作画布
- 智能体的每项操作都会被签名和追踪，从而建立信任、责任归属与审计能力。

##### 4. 两项核心原则

###### 自我主权

- 团队可以运行自己的中继节点。
- 用户拥有自己的域名、数据和身份密钥。
- 身份与数据不必被绑定在单一平台内。

###### 开源且无平台锁定

- Buzz 采用**Apache 2.0**开源协议。
- 系统基于开放协议**Nostr**构建，并且不绑定特定 AI 模型。
- 目前支持**Goose、Codex 和 Claude Code**。
- 用户既不会被传统平台锁定，也不会被 Buzz 自身锁定。

##### 5. 典型案例：把功能分支变成频道

Buzz 可以将一个代码功能分支直接对应为一个协作频道：

- 相关代码补丁、CI 结果、审查意见和合并决定都放在同一对话线程中。
- 团队讨论与最终代码修改不再分散在聊天工具和代码平台之间。
- 代码审查因此变成一场具有永久记录、可搜索且可追溯的对话。

##### 6. 当前进展与去中心化方向

Buzz 仍处于早期阶段，但目前已经提供：

- 频道与线程
- 私信
- 协作画布
- 媒体功能
- 搜索
- 审计日志
- 工作流
- 桌面应用

仍在推进的功能包括：

- 完整的 Git 托管能力正在开发。
- 移动端和推送通知即将推出。
- 审批流程目前仅完成了一部分。
- 当前每个工作区通过单个中继节点运行；未来通过中继节点之间的**联邦化互联**，逐步实现完整的去中心化架构。

##### 7. 下一阶段的重点

团队计划继续解决以下问题：

1. **更严格的智能体权限控制**  
   让智能体只能访问被授权的内容，从而适用于部分信息必须保密的工作空间。

2. **托管服务**  
   为不愿自行管理服务器和中继节点的团队提供托管选项。

3. **提升 Token 效率**  
   减少智能体读取和处理上下文时的 Token 消耗；团队表示已在这一方向投入大量工作。

4. **建设开放生态**  
   基于开放规范发展工作流和智能体生态系统，避免依赖单一厂商。

5. **支持智能体交易**  
   作者认为，能够自主进行交易的智能体可能是 Buzz 下一步的自然发展方向。

##### 8. 对 “社交型 AI” 的重新定义

作者认为，现有 “社交型 AI” 通常只是以下几种形式：

- 人类与 AI 伙伴聊天；
- AI 为人类生成信息流或聊天内容；
- 多个智能体相互交流，人类在旁观看。

Buzz 提出的不同方向是：**让人类和智能体成为同一网络中的平等成员，共同沟通、开发和决策。**作者认为，这可能是更有价值、也更持久的社交型 AI 形态。

##### 9. 实际验证与开放邀请

- Block 计划逐步将更多内部工作迁移到 Buzz，把公司自身作为第一个重要测试场景。
- 第二个测试标准是：Buzz 是否也能真正帮助外部团队。
- 项目代码和技术体系均保持开放，作者邀请开发者共同参与建设：
  - 官网：&lt;https://buzz.xyz>
  - GitHub：&lt;https://github.com/block/buzz>

##### 10. 评论区的主要关注点

- 有开发者提出，可通过自托管的去中心化 Git 节点补充 Buzz 的 Git 能力。
- 有用户希望官方提供面向初学者的视频或分步安装指南。
- 这些反馈也反映出 Buzz 当前最受关注的问题：**如何完善去中心化 Git、降低部署门槛，并让普通团队更容易上手。**

#### 《我们为什么这么热闹》精炼解读

##### 一句话判断

**Buzz 真正想做的，不是另一个 Slack 或 GitHub，而是把 “身份、上下文、代码、执行与审计” 统一成一套面向人类与智能体的协作基础设施。**

它押注的核心变化是：

> 当智能体从 “被调用的工具” 变成 “持续参与工作的成员”，传统 SaaS 之间的上下文断裂，会成为比模型能力更大的瓶颈。

---

##### 一、启发

###### 1. AI 产品的瓶颈正在从 “模型能力” 迁移到 “上下文连续性”

今天多数智能体并不是不会做，而是：

- 看不到 Slack 中的历史讨论；
- 不知道某次架构决策为什么发生；
- 无法把 GitHub、CI、审批系统里的状态串起来；
- 一次会话结束后，缺乏稳定、可检索的组织记忆；
- 无法判断自己看到的信息是否完整、可信、仍然有效。

因此，下一代 AI 工作系统的竞争重点可能不是单纯的模型效果，而是：

> **谁能以更低成本，向智能体提供完整、可信、可授权、可追溯的上下文。**

这意味着 AI 产品架构要从 “Prompt + Model” 升级为：

```text
身份系统
+ 事件记录
+ 权限边界
+ 上下文检索
+ 工具执行
+ 人类审批
+ 审计与追责
```

---

###### 2. “Agent-native” 不是增加一个聊天机器人，而是重构工作对象

Buzz 最重要的设计，不是让 AI 出现在聊天框里，而是让智能体拥有：

- 独立身份；
- 独立密钥；
- 可访问的频道；
- 可执行的工具；
- 可提交的补丁；
- 可参与的审查；
- 可追踪的行为记录。

这将智能体从一个 UI 功能，转变为一个组织主体。

但需要进一步区分：

> **身份平等，不代表权限平等；参与平等，也不代表决策权平等。**

智能体可以和人使用同一种身份、事件与审计模型，但其权限、预算、审批要求和责任边界仍应不同。

---

###### 3. “功能分支即频道” 代表工作流与对话流的合并

传统软件研发中，同一项工作的上下文分散在：

- 需求文档；
- Slack 讨论；
- Issue；
- Git 分支；
- Pull Request；
- CI 日志；
- Code Review；
- 发布审批。

Buzz 提出的 “功能分支成为频道”，本质上是在改变协作的主键：

| 传统组织方式 | Buzz 式组织方式 |
|---|---|
| 按工具组织信息 | 按工作对象组织信息 |
| 对话、代码、审批分离 | 全部进入同一事件线程 |
| 人工拼接上下文 | 系统天然保留因果链 |
| AI 需要跨系统猜测 | AI 可直接读取完整工作记录 |

真正值得迁移的不是 “频道” 这个功能，而是：

> **让每一个业务对象成为上下文容器。**

例如：

- 一个客户机会就是一个频道；
- 一个事故就是一个频道；
- 一个功能分支就是一个频道；
- 一份合同就是一个频道；
- 一次招聘就是一个频道；
- 一个退款争议就是一个频道。

---

###### 4. 开放协议可能成为多智能体生态的中间层

Buzz 选择开源、模型无关并基于开放协议，意味着它试图避免绑定某一个模型或智能体产品。

如果这个方向成立，未来的协作栈可能分成五层：

```text
身份层：人和智能体是谁
数据层：发生了什么，以何种事件记录
上下文层：谁可以看到哪些历史
执行层：智能体可以调用哪些工具
治理层：什么需要审批，谁承担责任
```

模型本身将成为可替换的执行组件，而组织上下文与治理规则才是更稳定的资产。

---

##### 二、高价值信息深挖

###### 1. Buzz 的核心不是 “统一工作台”，而是 “事件化组织记忆”

“所有内容都存储为带签名的事件” 是整个产品最关键的技术选择。

这相当于把组织中的行为统一抽象为事件：

```text
消息发送
代码补丁
审查意见
CI 结果
工作流执行
人工批准
智能体调用
合并决策
```

事件化的价值包括：

1. **可追溯**：知道谁在何时做了什么；
2. **可检索**：不同工具产生的信息进入统一索引；
3. **可重放**：可以恢复一项工作的演进过程；
4. **可组合**：工作流可以订阅并响应事件；
5. **可审计**：智能体的行为不再是黑箱式会话；
6. **可迁移**：数据不必被某个前端产品垄断。

从产品架构看，这比简单地给 Slack、GitHub 加连接器更彻底，因为它试图让事件本身成为系统事实来源。

---

###### 2. 加密签名解决的是 “来源与完整性”，不是 “正确与安全”

Buzz 强调每个行为都经过签名，这确实能回答：

- 谁发起了行为；
- 记录是否被篡改；
- 某个智能体是否执行过某个动作；
- 某次审批是否真实存在。

但签名不能证明：

- 智能体的判断是正确的；
- 操作符合业务政策；
- 输入数据没有被污染；
- 权限授予是合理的；
- 签名者没有被盗用；
- 代码补丁没有安全漏洞。

所以完整的信任体系不能只有签名，还需要：

```text
签名与来源
+ 最小权限
+ 密钥轮换与撤销
+ 策略引擎
+ 沙箱执行
+ 人类审批
+ 异常检测
+ 预算和速率限制
```

一个重要判断是：

> **可追溯不等于可信，可审计不等于可控制。**

---

###### 3. 真正困难的问题不是记录上下文，而是 “选择上下文”

把所有事件统一存储，只解决了 “信息存在” 的问题，没有完全解决：

- 当前任务需要哪些信息；
- 哪些历史已经失效；
- 哪些信息智能体有权访问；
- 哪些内容应该摘要而不是原文注入；
- 哪些决策是最终结论，哪些只是讨论过程；
- 如何避免提示词注入藏在历史消息里。

因此，Buzz 提到 “令牌效率”，背后其实是一个更大的上下文工程问题：

```text
原始事件流
→ 权限过滤
→ 相关性检索
→ 状态聚合
→ 冲突处理
→ 摘要压缩
→ 引用原始证据
→ 注入智能体
```

长期看，组织不会直接把完整历史塞给模型，而是需要生成不同的 “上下文投影”：

- 面向开发智能体的代码与架构投影；
- 面向管理者的状态与风险投影；
- 面向审计人员的操作证据投影；
- 面向客户支持的用户历史投影。

---

###### 4. 智能体身份必须包含 “运行时身份”，而不只是一个名字和密钥

如果一个智能体拥有稳定身份，但其背后的模型、提示词、工具和权限不断变化，那么 “它是谁” 仍然不够清晰。

高质量的智能体审计至少应记录：

- 智能体身份；
- 模型及版本；
- 系统提示或策略版本；
- 可调用工具版本；
- 本次获得的权限；
- 引用的上下文及来源；
- 发起的工具调用；
- 人工审批节点；
- 产生的输出和副作用；
- 成本、Token 与执行时长。

否则，同一个 “Agent A” 今天和明天可能表现完全不同，却共享同一身份和声誉。

---

###### 5. “可交易智能体” 意味着组织治理将延伸到经济权限

文章提出 “能够进行交易的代理” 可能是下一步，这比调用 API 更敏感。

一旦智能体可以：

- 购买服务；
- 支付供应商；
- 调配算力；
- 下单采购；
- 签署合同；
- 对外报价；
- 在智能体之间结算；

系统就必须增加经济治理层：

```text
身份 → 权限 → 预算 → 交易规则 → 审批 → 结算 → 争议处理
```

关键能力包括：

- 单笔与周期预算；
- 商户或交易对象白名单；
- 风险分级；
- 多签或人工审批；
- 可撤销授权；
- 欺诈检测；
- 法律主体映射；
- 责任归属与争议处理。

因此，“Agent Commerce” 并不是简单给智能体一个钱包，而是给它建立一套类似企业财务内控的体系。

---

###### 6. 商业机会不一定来自软件席位，而来自治理与托管

Buzz 宣称无锁定、可自托管、开源，这会削弱传统 SaaS 的数据锁定，但并不意味着没有商业价值。

潜在商业层包括：

- 托管中继节点；
- 企业级身份与权限；
- 合规、审计与数据驻留；
- 密钥托管与恢复；
- 智能体运行沙箱；
- 策略与审批引擎；
- 跨中继节点联邦服务；
- 企业搜索与上下文压缩；
- 智能体市场；
- 交易结算与抽成。

更强的护城河可能不是 “数据无法导出”，而是：

> **组织在平台上积累的工作流、权限政策、事件模式、智能体信誉和生态连接。**

##### 三、可迁移清单

###### 1. 产品设计清单

- [ ] 不要只增加 AI 聊天框，要重新定义 AI 在工作流中的角色。
- [ ] 以 “任务、客户、分支、订单” 等业务对象组织上下文。
- [ ] 将对话、状态变化、执行结果和审批记录关联到同一对象。
- [ ] 为智能体提供稳定身份，而不是共享一个通用机器人账号。
- [ ] 区分 “可读、可建议、可执行、可批准、可交易” 五类能力。
- [ ] 所有高风险动作都应支持人工确认与撤销机制。
- [ ] 输出必须附带证据、来源与操作记录。
- [ ] 支持模型替换，避免把组织上下文绑定到单一模型。
- [ ] 将智能体失败后的恢复路径视为一等产品能力。

###### 2. 技术架构清单

- [ ] 建立统一事件模型，而不是只依赖点对点 API 集成。
- [ ] 给每个事件记录主体、时间、对象、类型和来源。
- [ ] 区分原始事件与面向查询生成的状态投影。
- [ ] 设计事件版本、幂等性、撤销和冲突处理机制。
- [ ] 建立细粒度权限和作用域控制。
- [ ] 支持密钥轮换、撤销、恢复与离职交接。
- [ ] 对智能体工具调用进行沙箱、预算和速率限制。
- [ ] 将模型、提示词、工具、策略版本纳入审计记录。
- [ ] 在检索阶段执行权限过滤，而不是检索后再过滤。
- [ ] 防御历史上下文中的提示词注入和恶意事件。

###### 3. 商业系统清单

- [ ] 判断客户购买的是 “AI 能力”，还是 “上下文整合与治理”。
- [ ] 从高频、高上下文损耗的工作流切入。
- [ ] 计算工具切换与信息重建产生的隐性成本。
- [ ] 以周期时间、返工率和人工接管率衡量价值。
- [ ] 开源时提前设计托管、合规、治理等商业层。
- [ ] 不要依赖数据囚禁，要建立工作流与生态黏性。
- [ ] 在引入交易型智能体前，先解决预算、责任与风控。
- [ ] 将迁移成本和退出能力写入产品承诺，建立信任。

###### 4. 智能体治理清单

- [ ] 每个智能体有独立身份，不共享凭据。
- [ ] 默认最小权限，按任务临时提升权限。
- [ ] 读取权限与执行权限分离。
- [ ] 生产环境权限与测试环境权限分离。
- [ ] 代码提交权与合并批准权分离。
- [ ] 支付发起权与支付批准权分离。
- [ ] 高风险操作必须双重确认。
- [ ] 智能体权限可以即时撤销。
- [ ] 每次行为可关联到明确的人类负责人。
- [ ] 定期复核长期未使用的智能体和权限。

##### 四、反方与张力

###### 1. 统一上下文与工具专业化的张力

把聊天、代码、审查和工作流统一起来很有吸引力，但 Slack、GitHub、Linear 等工具之所以分化，是因为不同场景需要高度专业化的交互。

潜在风险是：

- “一体化” 最终变成低质量的大杂烩；
- 统一事件模型压平了领域差异；
- 用户仍会回到更成熟的专业工具；
- 系统最终仍要维护大量双向同步。

更现实的路径可能不是立即替代所有工具，而是：

> **先成为跨工具的上下文与治理层，再逐步吸收高价值交互。**

---

###### 2. 去中心化与企业管理的张力

自托管、密钥所有权和联邦化提升了数据主权，但企业通常还需要：

- 集中权限管理；
- 统一身份回收；
- 数据防泄漏；
- 法务留存；
- 全局搜索；
- 内容删除；
- 管理员恢复；
- 跨地区合规。

去中心化并不会自动降低治理成本，反而可能带来：

- 密钥丢失；
- 身份撤销困难；
- 跨节点一致性问题；
- 搜索碎片化；
- 垃圾信息和滥用；
- 数据删除与永久记录冲突。

文章也承认当前每个工作区仍依赖单个中继节点，因此 “完全去中心化” 目前更多是架构方向，而非已经实现的状态。

---

###### 3. 永久记录与隐私权的张力

永久记录有利于审计，但也可能记录：

- 无效讨论；
- 敏感个人信息；
- 错误推断；
- 被撤回的意见；
- 受法律保护的内容；
- 不应长期保留的模型输入。

因此必须回答：

- 是否支持逻辑删除或加密擦除；
- 如何执行数据保留期限；
- 如何处理 “被遗忘权”；
- 智能体生成的错误事实如何更正；
- 摘要是否会延续已删除信息。

---

###### 4. “智能体平等成员” 与责任归属的张力

智能体可以参与工作，但目前不能自然承担法律和组织责任。

需要明确：

- 智能体提交错误代码，谁负责；
- 智能体越权读取数据，谁承担后果；
- 智能体批准交易，授权人是谁；
- 模型供应商、平台方与使用企业如何划分责任；
- 开源智能体的行为是否有稳定责任主体。

因此更稳健的表述不是 “智能体与人完全平等”，而是：

> **智能体应成为可识别、可授权、可审计的协作主体，但责任最终仍需要映射到人或法人。**

---

###### 5. 开源、无锁定与商业护城河的张力

开源有利于采用和信任，但会带来：

- 商业化路径不清晰；
- 云厂商快速托管；
- 大客户自行部署；
- 产品能力容易被复制；
- 网络效应尚未形成时增长较慢。

Buzz 若想建立长期优势，可能需要依赖：

- 企业部署体验；
- 联邦网络；
- 智能体生态；
- 工作流标准；
- 企业治理能力；
- 开发者社区；
- 交易与信誉网络。

---

##### 五、情境化落地

##### 场景：一个 20～50 人的 AI 产品开发团队

###### 当前问题

团队使用：

- Slack 讨论需求；
- Notion 保存文档；
- Linear 管理任务；
- GitHub 开发和审查；
- CI/CD 执行测试；
- Claude Code、Codex 等智能体辅助开发。

典型损耗是：

- 智能体不知道需求为什么改变；
- PR 看不到关键业务讨论；
- 工程师需要反复向不同智能体解释背景；
- 架构决策无法稳定沉淀；
- 智能体修改代码后，责任和上下文不完整。

---

###### 最小可行改造：不要立刻替换全部工具

选择一个边界明确、可衡量的流程：

> **“从功能需求到代码合并” 作为首个试点。**

为每个功能创建唯一工作对象，并关联：

```text
需求
→ 讨论
→ 架构决策
→ 功能分支
→ 智能体任务
→ 代码补丁
→ CI 结果
→ 人工审查
→ 合并审批
```

###### 智能体权限建议

| 能力 | 默认策略 |
|---|---|
| 搜索项目历史 | 允许，但按项目权限过滤 |
| 读取代码库 | 允许 |
| 创建分支 | 允许 |
| 提交补丁 | 允许 |
| 运行测试 | 允许，限制资源预算 |
| 打开 PR | 允许 |
| 审查代码 | 允许，但标记为智能体意见 |
| 合并主分支 | 禁止或必须人工批准 |
| 访问生产密钥 | 禁止 |
| 生产部署 | 必须人工审批 |
| 对外交易 | 默认禁止 |

---

###### 30 天试点步骤

###### 第 1 周：建立事件模型

先只定义最关键的事件：

```text
feature.created
requirement.updated
decision.recorded
branch.created
agent.assigned
patch.submitted
ci.completed
review.submitted
approval.granted
branch.merged
```

避免一开始记录所有行为，否则会迅速形成噪声。

###### 第 2 周：接入现有工具

不要强迫团队迁移全部工作界面，先接入：

- GitHub；
- Slack 或现有聊天工具；
- CI；
- 一个编码智能体。

统一生成工作对象 ID，保证信息可以被串联。

###### 第 3 周：加入权限和审批

至少实施：

- 独立智能体身份；
- 工具白名单；
- 项目级读取权限；
- 分支级写入权限；
- 合并人工批准；
- 全量工具调用日志。

###### 第 4 周：评估业务价值

重点衡量：

| 指标 | 目标 |
|---|---|
| 人工重复解释上下文的时间 | 明显下降 |
| 从需求确认到首个可用补丁的时间 | 缩短 |
| PR 因需求误解导致的返工率 | 下降 |
| 智能体任务一次完成率 | 提升 |
| 人工接管率 | 下降但不追求归零 |
| 每项功能的上下文检索成本 | 下降 |
| 越权或错误执行事件 | 保持为零或可控 |

---

##### 六、对 AI 产品与商业系统构建者的最终判断

Buzz 提供的最重要启发，不是 “去做一个开源 Slack”，而是三点：

1. **上下文将成为 AI 时代的核心基础设施。**
2. **智能体需要独立身份、权限、记忆和审计，而不只是一个对话入口。**
3. **未来的工作系统将围绕业务对象和事件流组织，而不是围绕孤立工具组织。**

但真正决定这类系统能否成立的，不是界面有多少功能，而是能否同时解决以下五个问题：

```text
完整上下文
× 精确权限
× 低成本检索
× 可控执行
× 清晰责任
```

任何一项接近于零，智能体都很难成为真正可靠的组织成员。

> **最值得迁移的策略：不要先追求 “全自动智能体公司”，先把一个高价值工作流改造成可识别、可检索、可授权、可审计的事件系统。**

## 通俗精炼（1）

### 2026-09-18 10:48:40

#### Buzz：让人类与 AI 代理在同一工作空间协作

Block 发布开源工作空间 Buzz，试图把聊天、代码、审查和自动化流程统一到一个可追溯的上下文中。其核心主张是：AI 代理不应只是外挂工具，而应与人类拥有同类身份、权限和记录，成为团队的正式成员。

##### 解决工具割裂造成的上下文丢失

团队工作通常分散在 Slack、GitHub、持续集成系统和多种代理工具中，信息在平台切换时不断损失。人类尚可自行补足背景，代理却无法处理看不到的信息。Block 在内部广泛使用其开源代理框架 Goose 后，认为这种割裂已成为智能体协作的主要瓶颈。

Buzz 将功能分支直接变成频道，让讨论、补丁、测试结果、代码审查和合并决策保留在同一线程中，从而使代码开发成为一段完整、可搜索的协作记录。

##### 签名事件让代理行为可追溯

Buzz 把消息、补丁、审批和工作流步骤存储为加密签名事件，并运行在用户自行托管的中继节点上。人和代理都拥有密钥、频道及审计轨迹；代理可以搜索历史、读取代码库、提交补丁、审查代码和运行工作流，其操作均可验证和追责。

项目采用 Apache 2.0 协议，基于 Nostr、模型无关，已支持 Goose、Codex 和 Claude Code，强调数据自有、基础设施自托管和避免供应商锁定。

##### 愿景明确，但产品仍处早期

频道、私信、搜索、画布、审计日志、工作流和桌面端已经可用，完整 Git 托管、移动端、推送及审批能力仍在建设。后续难点包括代理权限隔离、跨中继联邦化、托管服务和令牌效率。

作者将 Buzz 定义为“真正的社交型 AI”：不是人与 AI 聊天或围观代理互动，而是人与代理在同一网络中平等协作。Block 将首先在自身业务中扩大使用，以验证这一模式能否成为开放的智能体工作基础设施。
