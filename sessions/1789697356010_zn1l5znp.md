## 分析要点

- **核心高价值点**：工程型Agent的效果不只取决于模型能力，更取决于能否获得分层、及时、可重复且可归因到具体原因的反馈。
- **留存建议**：重点精读并长期存档，可作为构建工程型Agent反馈环境的案例与方法参考（提出了可迁移的密集反馈框架，并以数值正确性、并发诊断和内核优化三个跨层案例展示Agent如何参与复杂基础设施工程。）

**知识要点**

- 密集反馈并非堆积日志，而是让正确性、系统行为和性能反馈分别回答计算是否正确、时间花在哪里、何种方案在何种条件下更优。
- 本地验证用于尽早淘汰错误方案并定位责任层，端到端测试用于确认局部收益能否转化为真实服务提升且不引入回归。
- 可将既有内核经验提炼为记录适用条件、变换方法、资源约束和验证证据的优化骨架，并通过实验持续更新。

**行动项**

- 为工程Agent建立正确性测试、微基准、执行轨迹、运行时事件和端到端指标组成的分层反馈环境。
- 要求每次优化先形成可检验假设，再选择对应验证方法，并以正确性、稳定性和端到端性能作为联合验收标准。
- 建立优化骨架库，记录每项优化的适用输入、资源约束、实现变换、消融结果和生产验证证据。

## 正文

在我们开发 GLM 的过程中，模型有时会展现出令我们惊讶、甚至令我们不安的能力。

2025 年 10 月，我们开始研究如何增强其网络安全能力。我们当时的推理很直接：网络安全是编程的自然延伸。一个能够理解复杂代码的模型，也应该能够理解其中的漏洞。我们没有预料到接下来会发生什么。不到一年，我们的安全合作伙伴利用 GLM 在真实世界的代码库中发现了数千个漏洞。该模型开始重塑网络安全，同时也带来了此前不存在的危险。为了负责任地使用这一能力，我们不得不设计一个可信访问计划。

最近一次让我们感到震撼的时刻，来自一个更为根本性的转变：GLM 正越来越多地帮助构建 AI 本身。我们目睹该模型完成了一项基础设施任务，而这项任务此前需要一个经验丰富的基础设施工程师团队花费数周才能完成。当我们意识到这项工作将直接改变下一代模型的训练方式时，我们更加确信：我们的继任者正是我们自己正在创造的 AI 系统。

坦率地说，在 GLM-4.7 之前，我们内部使用 GLM 进行编码多多少少带着一种义务感。毕竟，它是我们自己的作品。那时，编码领域的产品市场契合度尚未到来。如今，GLM-5.3 已成为团队每个人日常编码中不可或缺的伙伴，并且正在稳步走向取代我们。如果这一趋势持续下去，在足够的算力和足够的时间下，它的终点将是一个能够完全自主地设计并训练自己后继者的系统。这就是所谓的递归自我改进，即 RSI。

我们还没有到达那一步，但它的早期形态已经出现。本文记录了其中一个早期案例。

将一个模型从在新硬件上的首次成功运行，推进到能够可靠处理生产流量的高性能推理服务，是一项重大的系统工程任务。GLM-5.3-Flash 的发布也遵循了同样的路径。我们在一个由超过 10 万块国产 AI 加速器组成的集群上，从零构建了一套完整的生产级推理服务。GLM-5.3-Flash 的所有生产推理都运行在这套系统上。

这并不容易。此前没有人部署过如此规模的中国制造加速器集群。我们面临相对有限的芯片内存容量和带宽，同时还需要支持一种新的模型架构、100 万 token 的上下文窗口以及多模态请求。生态系统尚不成熟，内核支持不完整，许多本应有文档记录的内容只能靠猜测。最终，这项工作完成了。它并非仅由一个基础设施工程师团队完成。大部分工作是由一个由 GLM-5.3 驱动的 Infra Agent 完成的。

接下来发生的事情已经为人所熟知。GLM-5.3-Flash 以匿名模型名称 Ox-Alpha 在 OpenCode 和 OpenRouter 上通过真实使用进行了测试。上线一周内，它就成为这两个平台上使用量最高的模型，在六天内处理了超过 62 万亿 token。

我们实施了一系列激进的内存优化，包括以计算换带宽、以通信换设备内存的定制方案。最终形成的技术栈融合了多项关键技术：针对线性注意力和 LM Head 的节点内张量并行、ReplaySSM、W8A8 量化、使用 INT8/FP8/BF16 的混合精度缓存量化，以及 Layer Split。在此基础上，我们引入了编码-预填充-解码（EPD）分离式架构。这些优化共同将端到端服务性能提升了约 3 倍。硬件利用效率和每 token 成本均达到了与主流 NVIDIA GPU 相当的水平。

在整个优化过程中，Infra Agent 的反馈循环持续运行，使 GLM-5.3-Flash 从初始模型适配到生产就绪仅用了不到两周时间，最终将端到端吞吐量提升至初始基线的三倍。图 1 展示了 GLM-5.3-Flash 从首次成功运行到生产上线的性能轨迹。

在整个过程中，我们逐渐意识到，Infra Agent 的工程有效性不仅取决于模型的代码生成与推理能力，更取决于系统能否持续提供可追溯到具体原因的有用反馈。代码库只提供静态上下文。推理系统中的数值差异、性能回退和未达成的优化目标，往往源于跨多个层的动态交互，包括内核实现、并行策略、通信行为、内存管理和服务编排。

即使一个 agent 能够理解整个代码库，在变更之后，诸如“数值精度测试失败”“TTFT 增加了 30%”或“输出吞吐量下降了 20%”这样的反馈，仍然会让它难以确定哪一层应当负责、为什么它当前的假设是错误的，以及接下来应该测试什么。端到端指标可以告诉 agent 结果变差了，但无法解释原因。

#### **从端到端指标到可归因反馈**

传统推理系统优化并不缺少测试、日志、性能分析工具或微基准测试。但这些通常分散在不同的工具和工程阶段中。经验丰富的工程师会根据负载测试的结果来决定下一步观察什么，逐步检查内核输出、执行时间线、通信事件或线程状态，并将来自不同工具的信息关联起来。

对于智能体而言，除非这些观察和验证方法被组织成可直接访问、可重复的工作流，否则它实际能利用的反馈仍然十分稀疏。它可能知道吞吐量未达到目标，却仍然无法确定：

- 是某个特定内核耗时过长，还是计算设备处于空闲状态？
- KV Transfer 本身太慢，还是更高层的调度未能及时推进传输？
- 优化在哪些输入形状下有效，又在什么条件下出现回退？

单一的端到端指标无法回答这些问题。因此，我们将正确性测试、运行时日志、执行轨迹、运行时事件、微基准测试和端到端指标纳入智能体的迭代工作流，把整个系统优化过程拆解为可在本地观测和验证的步骤。内核级对比验证数值正确性。微基准测试衡量特定输入条件下的局部性能。执行轨迹和运行时事件揭示计算、等待与通信之间的时序关系。智能体可以针对当前假设选择合适的验证方法，而不必在每次改动后都等待完整的服务部署和端到端负载测试。

我们将这种方法称为“密集反馈”。这里的“密集”并不意味着尽可能多地向智能体投喂日志和指标，而是强调三个特征。

这三个特性共同决定了反馈是否具有可操作性。正确性反馈回答的是：“计算是否正确？”系统行为反馈识别的是：“时间花在哪里？”性能反馈确定的是：“哪种方法效果更好，以及在什么条件下？”验证方法不必遵循固定的顺序。它们应当与当前的假设相匹配，以便每个实验都能回答一个具体的问题。

在此过程中，本地验证与端到端测试承担着不同的角色。前者尽早剔除错误或无效的改动，并识别出值得继续推进的候选方案。后者则确认局部收益能否转化为真实的线上服务提升，以及拟议的改动是否会在实际工作负载下引入新的回归问题。

基于这些原则，GLM-5.3-Flash 的发布建立了一个由工程师、Infra Agent 和实验环境共同参与的优化闭环。工程师负责定义目标与系统边界。Agent 负责分析、提出假设并实施代码改动。实验环境则提供分层、及时且可验证的反馈。三者协同，将过去依赖工程师经验串联起来的诊断过程，转变为 Agent 能够持续执行的工程工作流。

这一进展既包括直接提升吞吐量的性能优化，也包括那些虽未立即提升吞吐量、但对系统正确可靠上线至关重要的缺陷修复。以下三个案例展示了密集反馈如何帮助智能体确保系统“计算正确”、解释“为什么运行不够快”，并探索“如何让它运行得更快”。

#### **正确性反馈：帮助智能体判断模型计算是否正确**

推理性能优化必须以数值正确性为基础。对智能体而言，验证首先要准确确定推理引擎执行哪些计算。高层并行策略会改变内核输入的分区方式、所采用的执行路径以及结果的合并方式。仅在未分区条件下测试内核输出，不足以覆盖其在实际部署中的行为。

为解决这一问题，我们建立了从推理引擎并行策略到内核实现的映射，将系统级部署配置转换为内核级任务，使智能体能够逐一验证。这一映射帮助智能体识别并行配置涉及哪些内核、输入如何分区，以及哪些计算路径需要与未分区的实现进行对比。

在此基础上，我们让智能体比较不同分区与未分区执行路径之间的数值精度。对于相同的输入，在对齐计算语义和输出位置后，它检查不同执行方法的结果是否满足数值误差容限。这将并行配置、内核路径和观测到的误差联系了起来。一旦测试暴露出差异，智能体可以继续排查相应的分区方案和计算路径，而不必在整个模型层面重新开始诊断。

正是在这个内核验证过程中，我们发现了 KDA 内核的上下文并行（CP）路径中存在数值精度问题。CP 与非 CP 结果之间的差异将调查引向了并行执行所引入的状态传播与合并计算。

CP 分区需要合并来自不同上下文分片的状态。其核心计算可以简化如下：

```
M = tl.dot(M_chunk, M)     # Merge state transformations across shards
S_next = tl.dot(M, S) + H  # Update the initial state for the next shard
```

在原始实现中， `tl.dot` 默认采用 TF32 计算以获得更好的性能，即使其输入为 FP32。这种较低的计算精度导致误差在变换合并和状态更新过程中不断累积，并且在长上下文场景下变得更加明显。

修复方法是显式地为这两个操作设置 `input_precision="tf32x3"` 。这将三个 TF32 Tensor Core 操作组合起来以产生更高精度的结果，在减少累积误差的同时尽可能保留 Tensor Core 的性能优势。

在这种情况下，反馈环境在问题浮现之前就已开始发挥作用。从并行策略到内核的映射定义了需要测试的内容。分区路径与非分区路径之间的对比暴露了数值差异。对计算精度的分析解释了差异的来源。回归测试为验证变更提供了持续的基础。对于智能体而言，这一工作流将系统级并行设计转化为可执行、可追溯的正确性任务。在本地验证之后，候选实现仍需回到目标部署环境，进行模型级精度和服务性能的最终验收测试。

#### **系统行为反馈：定位 KV 传输并发瓶颈**

对于系统级性能问题，明确定义的测试场景和性能约束为智能体提供了识别异常和选择分析方向的起点。

我们的推理优化工程师为智能体定义了测试场景，包括仅 Prefill、Prefill + KV Transfer 和仅 Decode，以隔离不同执行阶段及其组合的性能影响。他们还为每个场景设定了验收标准。例如，在相同工作负载下，Prefill + KV Transfer 与仅 Prefill 基线之间的性能差距不应超过 5%。

然而，智能体发现某些场景下的性能差距超过了 20%。这一反馈将调查范围缩小到 KV Transfer 引入的额外开销和并发交互。随后，智能体详细检查了 KV Transfer 时间线，并发现了一个异常：在这些场景中，Python 侧的 KV Transfer 执行从未与 DeepEP dispatch/combine 调用区间重叠。

这一观察促使智能体深入调查 DeepEP 与 Mooncake Transfer 之间的并发问题，沿着调用链追踪至 Python/C++ 边界。在我们使用的 DeepEP v1.2.1 版本中， `intranode_dispatch` 和 `intranode_combine` 均未显式释放 Python GIL。此外，当 dispatch 需要获取接收到的 token 数量时，它会在 CPU 上等待 GPU 返回该信息。

关键在于，进入 C++ 并不会自动释放 GIL。当这些调用持有锁时，同一进程中负责 Mooncake Transfer 的 Python 线程无法及时获取 GIL。因此，传输任务的调度和提交被延迟，减少了 KV Transfer 与后续计算重叠的机会。即使底层传输机制支持异步执行，上层提交的阻塞也可能导致预期的并行性无法充分实现。

源代码还提供了直接对比： `internode_dispatch` 在同一版本中已经显式释放了 GIL，并附有注释说明，这是为了避免 CPU 等待期间阻塞其他线程中的 KV Transfer。这进一步支持了 agent 对节点内路径的判断。

关键修复是在相关的 C++ 执行区间内释放 GIL，使 Mooncake Transfer Python 线程能够及时推进其任务。该修复必须同时针对时间线和原始性能约束进行验证。前者检查调度和传输是否获得了与计算重叠的机会；后者则判断这一改动是否提升了实际服务性能。在相同测试条件下，修复后 Prefill + KV Transfer 与单独 Prefill 之间的性能差距降至 1% 以下。

在这种情况下，性能约束首先将“未达预期”转化为一个明确定义的测试差异。随后，时间线将调查范围缩小到两个组件之间的并发问题。最后，代码分析精确定位了 GIL 被持有的范围。密集的反馈将端到端性能、跨层运行时行为和具体实现细节连接起来，为智能体分析的每一步提供了证据。

#### **性能反馈：基于现有内核优化专长，将其转化为系统级收益**

内核优化必须回答两个问题：如何判断一项优化是否有效，以及在哪里找到有前景的优化方向。

首先，内核性能必须在推理引擎的实际执行环境中进行评估。例如，给一个计算内核分配更多资源可能会缩短其自身的执行时间，但同时留给 KV Transfer 内核的资源更少，最终拖慢整个流水线。因此，智能体必须超越单个内核的延迟，在目标工作负载、资源约束、任务重叠和端到端收益的背景下确立正确的优化目标。

其次，大量优化经验蕴含在来自 SGLang、Flash Linear Attention 和 DeepGEMM 等项目的手写内核中。智能体需要从这些代码中提取优化技术及其适用条件，针对当前内核和目标硬件制定候选方案，并通过实验验证其实际效果。现有代码提供优化方向；系统反馈则决定这些优化在实践中是否成立。

我们让由 GLM-5.3 驱动的 Infra Agent 从不同代码库、编程语言和硬件平台中的现有内核中学习优化技术。通过增量实验和消融实验，它将这些技术提炼为包含适用条件、变换方法、资源约束和验证证据的“优化骨架”。对于新内核，Agent 从这些骨架出发，然后利用性能分析和分层测试重新评估分块、内存访问和资源分配策略。经过验证的变更及其适用条件会反馈到骨架库中。工程师主要负责定义目标和约束，并审查涉及数值语义、并发行为和生产风险的关键变更。

图 4 展示了具有代表性的 KDA Decode 内核的性能演变过程。引入 ReplaySSM 以计算换内存，导致内核执行时间首次增加，即从 v0 到 v1。随后，智能体的除法优化将 v1 的执行时间缩短了 9.6%。接下来，在收到计算是主要瓶颈的反馈后，Infra Agent 发现原始实现沿 V 维度进行分块，导致相同的 FP32 归一化和门控计算被重复执行四次。它将这些分块合并为单个线程块，使共享的中间结果常驻寄存器，并用单次 warp 级归约替代了冗余的逐分块计算。通过牺牲部分并行性，它从源头消除了冗余计算，相比 v2 实现了 1.71 倍的加速。

在这种情况下，由 GLM-5.3 驱动的 Infra Agent 从现有实现中提取优化经验，并将其应用于运行自身推理的内核。从骨架出发，它调整每个组件，使用分层验证来决定保留哪些更改，并依靠端到端性能来确定其实际价值。经过验证的洞见随后回流到骨架库中。该模型由此参与了自身推理系统的优化，而每次部署所积累的经验也减少了下一轮优化所需的工程投入。

#### **让反馈驱动行动，用实验检验假设**

这三个案例共同表明，反馈的价值不在于数量，而在于它是否能帮助智能体回答当前问题。大量非结构化日志可能掩盖关键信号。覆盖不完整的性能分析可能导致错误归因。在微基准测试中有效的优化未必能转化为端到端收益。因此，构建反馈环境不仅仅需要提供测试、日志和性能数据，还需要明确每类观测能够支持哪些判断、其局限是什么，以及哪些结论必须通过进一步实验来确认。

工程师在这一过程中承担三项关键职责：定义优化目标和系统约束，构建智能体可直接使用的反馈环境，以及审查涉及系统架构、异步并发和生产风险的关键变更。在这一框架内，智能体提出假设、实施变更并运行实验，然后利用反馈来保留、修正或否定当前方案。正确性、稳定性和端到端性能共同构成最终验收标准。

回顾 GLM-5.3-Flash 的发布过程，kernel 中的数值精度 bug、跨越 Python/C++边界的并发问题，以及关键 kernel 的性能优化，各自代表了不同层面的工程挑战。通过本地测试、跨层观察和分层基准测试，最初模糊的异常现象被逐步转化为可测试的工程假设。复杂的系统问题被分解为一系列可观察、可实验验证、结果可归因的迭代。正是在这一反馈循环中，agent 的编码与推理能力转化为可验证的工程进展。

当然，我们尚未达到递归式自我改进。选择目标、设置边界和评估风险仍然是人类的职责。我们相信，在未来很长一段时间内，人类应继续坚守这条底线。但那些数字——两周、三倍吞吐量、十万块加速器——告诉我们，这一边界上的进展不会仅仅因为我们希望它放缓就真的放缓。

##### 核心总结

##### 通俗解读

###### 1. “密集反馈” 不是日志越多越好，而是让错误能被定位

只告诉 Agent“吞吐量下降了 20%”，类似于只告诉医生 “病人不舒服”：它知道结果有问题，却不知道病因在哪里。推理系统横跨内核、并行策略、通信、内存和服务调度，任何一层都可能造成退化。

文章所说的 “密集反馈”，核心是把大问题拆成可验证的小问题：

- 正确性测试回答 “算得对不对”；
- 执行轨迹回答 “时间耗在哪里”；
- 微基准测试回答 “某项局部优化是否有效”；
- 端到端测试回答 “局部收益能否真正改善线上服务”。

例如，KV 传输性能异常最初只表现为整体性能差距超过 20%。时间线进一步显示传输与计算没有重叠，代码追踪最终定位到 C++ 调用未释放 Python GIL，阻塞了传输线程。修复后，性能差距降到 1% 以下。**真正让 Agent 有效的，不只是推理能力，而是每一步猜测都能被实验确认或否定。**

###### 2. 局部更快，不等于整个系统更快

推理服务是多个任务共享资源的流水线。某个内核单独运行得更快，可能因为占用了更多计算或内存资源，反而妨碍 KV 传输等其他任务，使整体吞吐量下降。

因此，文章采用两层验证：

1. 用本地测试快速淘汰错误或无效方案；
2. 用真实负载确认优化能否转化为端到端收益，并检查是否带来新的回归。

这说明基础设施优化不能只追求漂亮的单项跑分。**系统级最优往往需要牺牲局部指标，甚至像 ReplaySSM 那样先增加某个内核的执行时间，以换取更低的内存压力和更好的整体表现。**

###### 3. 这更像 “自我优化的早期环节”，还不是完整的递归自我改进

GLM 确实参与优化了承载自身推理的内核和服务系统，优化经验还会沉淀到 “骨架库”，降低下一轮工程成本。这构成了一个有限闭环：

> 模型提出修改 → 实验环境反馈 → 保留有效改动 → 推理成本下降、部署能力提高。

但严格的递归自我改进通常意味着系统能自主设定改进目标、设计或训练更强的后继模型，再由后继模型继续改进。本文中的 Agent 尚不能独立完成这些环节，尤其没有自主决定架构、训练目标、资源配置和安全边界。因此，**它展示的是 “AI 辅助改进 AI 基础设施”，而非已经实现自主递归升级。**

##### 辩证思考

文章最有说服力之处，是没有把成果简单归因于 “模型更聪明”，而是具体展示了 Agent 如何借助数值对比、执行时间线、代码分析和端到端测试定位问题。TF32 精度累积、GIL 阻塞 KV 传输、KDA 内核冗余计算这三个案例覆盖了正确性、并发与性能优化，因果链条相对完整。**“高质量、可归因的反馈环境是工程 Agent 发挥能力的关键条件” 这一判断，具有较强的实践可信度。**

1. 将业务目标转成明确的验收约束；
2. 将系统状态拆成分层、可重复的观测与实验；
3. 保存“什么方法在什么条件下有效”的经验，而不只是保存代码修改。

现有替代方案是专家在人肉切换日志、Profiler、测试和部署环境。机会在于建立连接“异常—假设—实验—证据”的中间层，但前提是任务足够重复、系统可观测，而且错误试验的成本可控。安全、医疗或资金系统中，仅提高迭代速度远远不够。

## 口播总结（1）

### 2026-09-18 10:03:42

GLM 团队认为，递归自我改进的早期形态已经出现。所谓递归自我改进，是指人工智能逐步参与设计、优化，甚至训练自己的后继系统。它还没有真正实现完全自主，但 GLM 已经开始帮助建设运行自身所需的推理基础设施。

最典型的案例，是 GLM-5.3-Flash 的生产部署。团队要在超过十万块国产人工智能加速器组成的集群上，从零搭建推理服务。这套系统既要支持一百万 token 的超长上下文，也要处理多模态请求。同时，芯片内存和带宽有限，软件生态还不成熟，内核支持和技术文档也不完整。

过去，这类工作通常需要一支经验丰富的基础设施团队投入数周。此次，大部分工作由 GLM-5.3 驱动的基础设施智能体完成。系统从初步适配到可以承载生产流量，用时不到两周，端到端吞吐量提升到最初基线的三倍。最终，硬件利用效率和每个 token 的成本，也达到了与主流英伟达图形处理器相当的水平。

上线后的真实流量验证了这套系统。GLM-5.3-Flash 曾以匿名名称 Ox-Alpha 在两个平台接受测试。上线一周内，它成为两个平台使用量最高的模型，六天处理的 token 超过六十二万亿。

不过，真正值得关注的，不只是模型能写多少代码，而是团队如何让智能体解决复杂的系统工程问题。

推理系统的性能问题，往往横跨多个层次。可能是计算内核不够快，也可能是并行策略、通信、内存管理或服务调度出了问题。端到端指标只能告诉智能体，系统变慢了，却不能解释为什么变慢。

比如，吞吐量下降百分之二十，原因可能是某个内核执行太久，也可能是设备在等待数据。数据传输太慢，也可能不是传输机制本身的问题，而是上层调度没有及时发起任务。只给智能体一个最终分数，就像只告诉工程师汽车速度下降了，却不提供发动机、变速箱和油路的数据。

为此，团队建立了所谓的“密集反馈”环境。这里的密集，不是把海量日志全部丢给智能体，而是让每一次反馈都能帮助回答一个具体问题。

这类反馈主要解决三件事。第一，计算结果对不对。第二，运行时间到底花在了哪里。第三，哪一种优化更有效，以及它在什么条件下才有效。

本地测试负责尽早淘汰错误方案。端到端测试则负责确认，局部收益能不能真正转化为线上服务收益。工程师定义目标和边界，智能体分析问题、提出假设并修改代码，实验环境再提供及时、分层而且可验证的反馈。三者由此形成持续循环。

第一个案例，是发现数值精度问题。

模型在真实部署中会采用上下文并行，也就是把长上下文切分到不同设备上计算。不同分片产生的状态，最后还要合并。如果只测试没有切分的计算路径，就可能漏掉并行执行中的错误。

团队因此把系统级并行配置映射到具体内核，让智能体逐项比较分区路径和非分区路径的结果。测试发现，一个关键内核在上下文并行时存在精度偏差，而且上下文越长，误差越明显。

原因是状态合并时，部分计算默认使用了速度更快、但精度较低的格式。误差在多次状态变换中不断累积。修复方案是改用由三次低精度运算组合出的更高精度计算方式。这样既减少了累计误差，也尽量保留了专用计算单元的性能优势。

这个案例说明，正确性不能只在整个模型的输出端检查。只有把并行策略、内核路径和数值误差对应起来，智能体才能知道问题到底发生在哪一层。

第二个案例，是定位数据传输的并发瓶颈。

工程师分别测试了模型的预填充阶段、预填充加键值缓存传输，以及单独解码。所谓键值缓存，是模型处理上下文时保存的中间状态。团队设定的目标是，加入缓存传输后，性能损失不应超过百分之五。但测试中，部分场景的差距超过了百分之二十。

智能体分析执行时间线后发现，缓存传输始终没有与后续计算重叠。继续沿调用链排查，问题最终落在 Python 和 C 加加的交界处。

某些底层调用没有主动释放 Python 的全局解释器锁，也就是限制多个 Python 线程同时执行的机制。底层代码在等待图形处理器返回信息时，仍然占着这把锁。结果是，负责缓存传输的 Python 线程无法及时提交任务。即使底层传输本来支持异步执行，上层的阻塞也让并发失效。

修复方式，是在相关的 C 加加执行区间主动释放这把锁。修复后，同样测试条件下，加入缓存传输造成的性能差距，从超过百分之二十降到了百分之一以内。

第三个案例，是优化运行模型自身的计算内核。

智能体从多个现有项目和不同硬件平台的手写内核中提取优化经验，再通过增量实验和消融实验，判断这些方法适用于什么条件。一次优化中，智能体发现，原有实现把数据分成多块处理，导致相同的归一化和门控计算重复执行四次。

它重新合并分块，让共享的中间结果留在寄存器里，并用一次线程组级归约替代多次重复计算。这个方案牺牲了一部分并行性，却从源头消除了冗余。最终，相比上一版本，相关内核实现了一点七一倍的加速。

这三个案例共同说明，智能体的工程能力并不只取决于模型有多聪明。更关键的是，系统能不能把模糊的异常，转化为可测试的假设，再用实验给出可以追溯原因的反馈。日志越多，不一定越有用。局部基准测试变快，也不代表整个服务一定变快。

GLM 团队强调，这还不是真正的递归自我改进。目标如何选择，边界如何设定，风险如何评估，仍然由人类负责。但不到两周完成生产适配、把吞吐量提高到三倍，并运行在十万块加速器上的结果，已经表明一个重要趋势：人工智能不再只是被部署的模型，也正在成为建设下一代人工智能系统的工程参与者。

## 深度解读-口播（1）

### 2026-09-30 11:50:42

人工智能能不能参与改进运行自己的系统？GLM 团队报告的一个案例显示，模型已经能承担大量推理基础设施工作。不过，真正值得注意的，不只是模型会写代码，而是它能否通过实验，弄清楚哪里错了、为什么慢，以及怎样改才有效。

这里说的推理基础设施，就是模型训练完成后，接收用户请求、运行计算并返回答案的一整套系统。让模型在新芯片上成功运行一次，与让它稳定、快速地服务大量用户，是两回事。后者需要解决计算精度、内存分配、设备通信和任务调度等一系列问题。

据团队介绍，他们为 GLM 五点三 Flash 构建了一套生产级推理服务，运行在超过十万块国产人工智能加速器组成的集群上。这项工作面临不少限制：芯片内存容量和带宽相对有限，还要支持新的模型架构、百万级上下文和多模态请求。相关工具和文档也不够成熟。

大部分工程工作，由 GLM 五点三驱动的基础设施智能体完成。所谓智能体，就是能够分析问题、修改代码、调用工具并运行实验的模型系统。团队报告，从最初适配到具备上线条件，用了不到两周；经过一系列优化，端到端吞吐量达到初始基线的三倍。也就是说，整个服务单位时间内能够处理的工作量，显著增加了。

但这些成果，并不意味着模型已经可以完全自主地改进自己。理解这个案例，关键要看团队怎样让智能体获得有用的反馈。

假设智能体修改了一段代码，测试只告诉它：“服务变慢了。”这个结果有用，却远远不够。究竟是某个计算步骤耗时太长，还是设备在等待？是数据传输慢，还是传输任务根本没有及时启动？仅靠一个总指标，无法区分这些原因。

经验丰富的工程师，会结合日志、执行时间线和局部测试，一层层排查。团队所做的，是把这套诊断方法组织成智能体可以直接使用、重复执行的工作流。

他们称之为“密集反馈”。这里的密集，不是把更多日志塞给模型，而是让反馈能回答具体问题：计算对不对，时间花在哪里，以及某种优化在什么条件下有效。

三个工程案例，能把这件事讲清楚。

第一个案例，是发现计算精度问题。

为了处理很长的上下文，系统会把输入分成多个片段，并行计算，再合并中间状态。但一个计算内核在不分片时算得对，不代表分片以后仍然算得对。

团队先建立了部署配置与底层计算路径之间的对应关系。智能体因此知道，某种并行方式究竟涉及哪些计算，应该拿哪些结果进行比较。

对比之后，智能体发现，某条分片计算路径与未分片路径的结果存在差异。继续排查，问题落在合并状态的两个矩阵运算上：原始实现默认采用一种速度更快、但精度较低的计算方式。误差在反复合并和状态更新中累积，上下文越长，问题越明显。

修复办法，是明确指定更高精度的计算方式，同时尽量保留硬件的加速优势。之后，还要通过回归测试，以及实际部署环境中的模型精度和性能测试。

这个案例说明，正确性反馈不能只说“答案不对”。它还要把差异对应到具体计算路径，才有可能找到原因。

第二个案例，是看似能并行、实际上却被阻塞的数据传输。

模型处理请求时，会缓存一部分中间计算结果，供后续生成使用。这些缓存通常叫作键值缓存，也叫 KV 缓存。在不同处理阶段之间，缓存可能需要传输。理想情况下，传输可以与后续计算同时进行，减少等待。

工程师设定了一个明确标准：在相同负载下，加入缓存传输后，与只处理输入的基线相比，性能差距不应超过百分之五。但智能体发现，有些场景的差距超过了百分之二十。

这就把一个笼统的“速度不够快”，变成了可以追查的异常。

智能体检查执行时间线后发现，传输任务没有与某些计算调用重叠。沿着调用链继续检查，原因出在 Python 的全局解释器锁。这是一种限制线程执行的锁。在相关调用持有这把锁时，另一个负责提交传输任务的线程，只能等待。

于是，即便底层传输支持异步执行，上层任务没有及时提交，预期中的并行仍然无法发生。

修复是在相关执行区间内释放这把锁。团队随后同时检查两件事：时间线上，传输是否获得了与计算重叠的机会；整体测试中，性能是否真的改善。最终，在相同测试条件下，原来超过百分之二十的差距，降到了百分之一以下。

这说明，底层具备并行能力，不等于整个系统真的在并行。跨层观察，才能找到阻塞发生在哪里。

第三个案例，则提醒我们：局部更快，不一定意味着整体更快。

某个计算内核如果占用更多硬件资源，自身运行时间可能缩短，却也可能挤占数据传输所需的资源，拖慢整个服务。因此，智能体不能只盯着单个计算步骤的耗时。

团队让智能体从已有的高性能实现中学习优化方法，再通过实验确认这些方法的适用条件。在一个关键内核里，反馈显示主要瓶颈是计算。智能体进一步发现，同一组归一化和门控计算，因为分块方式的关系，被重复执行了四次。

它调整分块方式，让中间结果能够共享。虽然牺牲了部分并行性，却消除了冗余计算。与上一个版本相比，这个内核获得了一点七一倍的加速。

但局部测试仍不是最后的裁判。局部验证负责尽早淘汰错误方案，完整服务测试负责确认：这些收益能否转化为真实用户请求下的性能提升，有没有引入新的问题。

所以，这个案例呈现的，不是一个脱离人类、自行升级的模型，而是一个分工明确的工程闭环。工程师确定目标、系统边界和风险要求；智能体提出假设、修改代码、运行实验；实验环境提供能够追溯原因的反馈。涉及架构、并发和生产风险的关键改动，仍然需要人类审查。

最值得记住的是，人工智能的工程能力，不只取决于它能写出多好的代码，也取决于它能否获得可验证、可归因的反馈。模型参与改进自身基础设施，已经出现了实际案例；但距离完全自主设计和训练下一代模型，仍有重要边界。决定目标、设置约束和评估风险，在这个案例中依然是人类的职责。
