#### 📦 Install

Download the firmware for your platform from the [release](https://github.com/sipeed/picoclaw/releases) page.

```
git clone https://github.com/sipeed/picoclaw.git

cd picoclaw
make deps

# Build, no need to install
make build

# Build for multiple platforms
make build-all

# Build for Raspberry Pi Zero 2 W (32-bit: make build-linux-arm; 64-bit: make build-linux-arm64)
make build-pi-zero

# Build And Install
make install
```

**Raspberry Pi Zero 2 W:** Use the binary that matches your OS: 32-bit Raspberry Pi OS → `make build-linux-arm` (output: `build/picoclaw-linux-arm`); 64-bit → `make build-linux-arm64` (output: `build/picoclaw-linux-arm64`). Or run `make build-pi-zero` to build both.

You can also run PicoClaw using Docker Compose without installing anything locally.

```
# 1. Clone this repo
git clone https://github.com/sipeed/picoclaw.git
cd picoclaw

# 2. First run — auto-generates docker/data/config.json then exits
docker compose -f docker/docker-compose.yml --profile gateway up
# The container prints "First-run setup complete." and stops.

# 3. Set your API keys
vim docker/data/config.json   # Set provider API keys, bot tokens, etc.

# 4. Start
docker compose -f docker/docker-compose.yml --profile gateway up -d
```

```
# 5. Check logs
docker compose -f docker/docker-compose.yml logs -f picoclaw-gateway

# 6. Stop
docker compose -f docker/docker-compose.yml --profile gateway down
```

The `launcher` image includes all three binaries (`picoclaw`, `picoclaw-launcher`, `picoclaw-launcher-tui`) and starts the web console by default, which provides a browser-based UI for configuration and chat.

```
docker compose -f docker/docker-compose.yml --profile launcher up -d
```

Open [http://localhost:18800](http://localhost:18800) in your browser. The launcher manages the gateway process automatically.

```
# Ask a question
docker compose -f docker/docker-compose.yml run --rm picoclaw-agent -m "What is 2+2?"

# Interactive mode
docker compose -f docker/docker-compose.yml run --rm picoclaw-agent
```

**4. Telegram command menu (auto-registered at startup)**

PicoClaw now keeps command definitions in one shared registry. On startup, Telegram will automatically register supported bot commands (for example `/start`, `/help`, `/show`, `/list`) so command menu and runtime behavior stay in sync. Telegram command menu registration remains channel-local discovery UX; generic command execution is handled centrally in the agent loop via the commands executor.

If command registration fails (network/API transient errors), the channel still starts and PicoClaw retries registration in the background.

**1. Create a bot**

- Create an application → Bot → Add Bot
- Copy the bot token

**2. Enable intents**

- In the Bot settings, enable **MESSAGE CONTENT INTENT**
- (Optional) Enable **SERVER MEMBERS INTENT** if you plan to use allow lists based on member data

**3. Get your User ID**

```
{

      "enabled": true,
      "token": "YOUR_BOT_TOKEN",
```

- OAuth2 → URL Generator
- Scopes: `bot`
- Bot Permissions: `Send Messages`, `Read Message History`
- Open the generated invite URL and add the bot to your server

**Optional: Group trigger mode**

By default the bot responds to all messages in a server channel. To restrict responses to @-mentions only, add:

```
{
  "channels": {
    "discord": {
      "group_trigger": { "mention_only": true }
    }
  }
}
```

You can also trigger by keyword prefixes (e.g. `!bot`):

```
{
  "channels": {
    "discord": {
      "group_trigger": { "prefixes": ["!bot"] }
    }
  }
}
```

**WhatsApp** (native via whatsmeow)

PicoClaw can connect to WhatsApp in two ways:

- **Native (recommended):** In-process using [whatsmeow](https://github.com/tulir/whatsmeow). No separate bridge. Set `"use_native": true` and leave `bridge_url` empty. On first run, scan the QR code with WhatsApp (Linked Devices). Session is stored under your workspace (e.g. `workspace/whatsapp/`). The native channel is **optional** to keep the default binary small; build with `-tags whatsapp_native` (e.g. `make build-whatsapp-native` or `go build -tags whatsapp_native ./cmd/...`).
- **Bridge:** Connect to an external WebSocket bridge. Set `bridge_url` (e.g. `ws://localhost:3001`) and keep `use_native` false.

**Configure (native)**

```
{
  "channels": {
    "whatsapp": {
      "enabled": true,
      "use_native": true,
      "session_store_path": "",
      "allow_from": []
    }
  }
}
```

If `session_store_path` is empty, the session is stored in `&lt;workspace&gt;/whatsapp/`. Run `picoclaw gateway`; on first run, scan the QR code printed in the terminal with WhatsApp → Linked Devices.

##### Environment Variables

You can override default paths using environment variables. This is useful for portable installations, containerized deployments, or running picoclaw as a system service. These variables are independent and control different paths.

Variable Description Default Path

`PICOCLAW_CONFIG` Overrides the path to the configuration file. This directly tells picoclaw which `config.json` to load, ignoring all other locations. `~/.picoclaw/config.json`

`PICOCLAW_HOME` Overrides the root directory for picoclaw data. This changes the default location of the `workspace` and other data directories. `~/.picoclaw`

**Examples:**

```
# Run picoclaw using a specific config file
# The workspace path will be read from within that config file
PICOCLAW_CONFIG=/etc/picoclaw/production.json picoclaw gateway

# Run picoclaw with all its data stored in /opt/picoclaw
# Config will be loaded from the default ~/.picoclaw/config.json
# Workspace will be created at /opt/picoclaw/workspace
PICOCLAW_HOME=/opt/picoclaw picoclaw agent

# Use both for a fully customized setup
PICOCLAW_HOME=/srv/picoclaw PICOCLAW_CONFIG=/srv/picoclaw/main.json picoclaw gateway
```

##### Workspace Layout

PicoClaw stores data in your configured workspace (default: `~/.picoclaw/workspace`):

```
~/.picoclaw/workspace/
├── sessions/          # Conversation sessions and history
├── memory/           # Long-term memory (MEMORY.md)
├── state/            # Persistent state (last channel, etc.)
├── cron/             # Scheduled jobs database
├── skills/           # Custom skills
├── AGENTS.md         # Agent behavior guide
├── HEARTBEAT.md      # Periodic task prompts (checked every 30 min)
├── IDENTITY.md       # Agent identity
├── SOUL.md           # Agent soul
└── USER.md           # User preferences
```

##### Skill Sources

By default, skills are loaded from:

1. `~/.picoclaw/workspace/skills` (workspace)
2. `~/.picoclaw/skills` (global)
3. `<current-working-directory>/skills` (builtin)

For advanced/test setups, you can override the builtin skills root with:

```
export PICOCLAW_BUILTIN_SKILLS=/path/to/skills
```

- Generic slash commands are executed through a single path in `pkg/agent/loop.go` via `commands.Executor`.
- Channel adapters no longer consume generic commands locally; they forward inbound text to the bus/agent path. Telegram still auto-registers supported commands at startup.
- Unknown slash command (for example `/foo`) passes through to normal LLM processing.
- Registered but unsupported command on the current channel (for example `/show` on WhatsApp) returns an explicit user-facing error and stops further processing.

PicoClaw runs in a sandboxed environment by default. The agent can only access files and execute commands within the configured workspace.

###### Protected Tools

When `restrict_to_workspace: true`, the following tools are sandboxed:

Tool Function Restriction

`read_file` Read files Only files within workspace

`write_file` Write files Only files within workspace

`list_dir` List directories Only directories within workspace

`edit_file` Edit files Only files within workspace

`append_file` Append to files Only files within workspace

`exec` Execute commands Command paths must be within workspace

Even with `restrict_to_workspace: false`, the `exec` tool blocks these dangerous commands:

- `rm -rf`, `del /f`, `rmdir /s` — Bulk deletion
- `format`, `mkfs`, `diskpart` — Disk formatting
- `dd if=` — Disk imaging
- Writing to `/dev/sd[a-z]` — Direct disk writes
- `shutdown`, `reboot`, `poweroff` — System shutdown
- Fork bomb `:(){ :|:& };:`

PicoClaw can perform periodic tasks automatically. Create a `HEARTBEAT.md` file in your workspace:

```
# Periodic Tasks

- Check my email for important messages
- Review my calendar for upcoming events
- Check the weather forecast
```

The agent will read this file every 30 minutes (configurable) and execute any tasks using available tools.

For long-running tasks (web search, API calls), use the `spawn` tool to create a **subagent**:

```
# Periodic Tasks

## Quick Tasks (respond directly)

- Report current time

## Long Tasks (use spawn for async)

- Search the web for AI news and summarize
- Check email and report important messages
```

**Key behaviors:**

Feature Description

**spawn** Creates async subagent, doesn't block heartbeat

**Independent context** Subagent has its own context, no session history

**message tool** Subagent communicates with user directly via message tool

**Non-blocking** After spawning, heartbeat continues to next task

```
Heartbeat triggers
    ↓
Agent reads HEARTBEAT.md
    ↓
For long task: spawn subagent
    ↓                           ↓
Continue to next task      Subagent works independently
    ↓                           ↓
All tasks done            Subagent uses "message" tool
    ↓                           ↓
Respond HEARTBEAT_OK      User receives result directly
```

The subagent has access to tools (message, web\_search, etc.) and can communicate with the user independently without going through the main agent.

```
{
  "heartbeat": {
    "enabled": true,
    "interval": 30
  }
}
```

Option Default Description

`enabled` `true` Enable/disable heartbeat

`interval` `30` Check interval in minutes (min: 5)

**Environment variables:**

- `PICOCLAW_HEARTBEAT_ENABLED=false` to disable
- `PICOCLAW_HEARTBEAT_INTERVAL=60` to change interval

- 接入不同大模型

- 很适合便宜开发板、SBC、小主机

## 产品-最佳实践（1）

### 2026-03-12 07:08:24

下面给你一个**具体实例**，并基于该实例提炼出**PicoClaw 的最佳实践**。

---

##### 实例：把一台闲置安卓手机变成家庭消息型 AI 助手

###### 场景
你有一台旧安卓手机，希望它：
- 7×24 小时运行
- 通过**Telegram**跟你对话
- 能做基础问答、简单搜索、日程 / 记录类任务
- 成本尽量低、部署尽量轻

###### 方案选择
基于 PicoClaw 的特点，最佳落地方式是：

- **运行环境**：安卓手机 + Termux
- **交互通道**：Telegram
- **模型配置**：主模型用一个稳定的云端 LLM
- **搜索工具**：先启用 DuckDuckGo，后续再接 Tavily/Brave
- **部署方式**：先单机直跑，不上 Docker

---

##### 精炼最佳实践

###### 1. 先选 “最小可用链路”
对这个实例，最优先组合是：

**Termux + PicoClaw 二进制 + Telegram + DuckDuckGo**

原因：
- 部署最简单
- 不依赖复杂网关和容器
- Telegram 配置成本最低
- DuckDuckGo 无需 API Key，适合先跑通

---

###### 2. 通道优先选 Telegram
虽然 PicoClaw 支持很多渠道，但在个人助手场景下：
- **Telegram 最适合做第一入口**
- 配置简单，只要 bot token
- `allow_from`可直接限制访问用户
- 运维成本远低于 LINE / WeCom / WhatsApp webhook 类方案

**建议**：第一阶段不要同时接多个渠道，先把一个渠道打磨稳定。

---

###### 3. 模型配置要 “一个主模型 + 清晰别名”
例如：
- `model_name: gpt4`
- 实际指向某个稳定模型，如`openai/gpt-5.2`

这样做的好处：
- 后续替换底层 provider 时，不影响 agent 默认配置
- 降低迁移成本
- 配置更统一

**实践建议**：
- 默认只保留 1 个主模型
- 第二个模型作为备用，不要一开始堆很多 provider

---

###### 4. 工具能力从 “无密钥可用” 开始
在这个实例里，搜索工具建议：
1. **先开 DuckDuckGo**
2. 稳定后再加 Tavily / Brave
3. 自建能力（如 SearXNG）放到后期

原因：
- 先验证 “助手是否真的有用”
- 避免一开始把问题复杂化到 API、配额、网络和搜索质量上

---

###### 5. 严格限制访问权限
消息型 AI 助手一旦接入 IM，**权限控制是第一优先级**。

在 Telegram 中应配置：
- `allow_from: [" 你的用户 ID"]`

这是最关键的安全最佳实践之一。  
**不要**在未限制访问者的情况下直接暴露机器人。

---

###### 6. 工作目录与配置分离
建议明确这两部分：
- `~/.picoclaw/config.json`：配置
- `~/.picoclaw/workspace`：工作区 / 数据区

这样做的价值：
- 升级二进制不影响业务数据
- 容易备份和迁移
- 出问题时更容易排查

---

###### 7. 控制 agent 复杂度，避免旧手机过载
虽然 PicoClaw 很轻量，但旧手机依然资源有限。建议：
- `max_tool_iterations`不要设太高，先用默认或更低值
- 不要同时开过多通道
- 不要一开始就加大量自动化任务

核心原则：
> 先把 “稳定响应” 做好，再追求 “复杂能力”。

---

###### 8. 优先用 “消息助手” 场景，而不是重型自动化
在旧手机上，最适合 PicoClaw 的任务是：
- 问答
- 搜索总结
- 备忘记录
- 轻量计划管理

不建议一开始就做：
- 大规模爬取
- 长链路自动化
- 重度多工具调用

因为这些更依赖网络、模型时延和外部系统稳定性，而不是 PicoClaw 本身。

---

###### 9. 采用 “两阶段部署”
**阶段 1：跑通**
- 本地启动
- 命令行验证
- Telegram 收发正常

**阶段 2：稳定化**
- 增加开机自启
- 增加日志检查
- 增加备用模型或搜索 API

这比 “一次性全配置完” 成功率高很多。

---

##### 这个实例下的推荐配置思路

简化理解就是：

- **设备**：旧安卓手机
- **部署**：Termux 直接运行 PicoClaw
- **模型**：1 主 1 备
- **搜索**：DuckDuckGo
- **通道**：只开 Telegram
- **安全**：只允许自己访问
- **目标**：低功耗、稳定在线、轻量可用

---

**PicoClaw 的最佳实践不是一开始把功能开满，而是在超轻量设备上先构建一条 “最小、稳定、安全、可维护” 的助手链路。**
