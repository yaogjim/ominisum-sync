## 分析要点

- **核心高价值点**：将状态机的每次确定性转换保存为独立 derivation，可让分支执行只计算新增步骤，并自动复用此前全部状态。
- **留存建议**：精读并存档，重点保留其可复现状态机与增量构建思路（文章以完整原型、命令输出和性能测试展示了如何将确定性状态转换映射为可缓存的 Nix derivation，具有较强的技术启发和迁移价值。）

**知识要点**

- Nix 的惰性求值允许递归属性集形成近似无限的树，访问属性路径相当于按需执行一串计算步骤。
- 把前一状态的存档作为下一 derivation 的输入，可以用 Nix store 保存可复现的状态历史，并复用公共前缀。
- 超长输入序列会依次受到求值调用深度、Linux 单参数长度和串行构建成本限制，可改用文件传入序列规避参数上限。

**行动项**

- 运行 nes-nix 示例，验证相同输入前缀是否复用相同 store path，并测试从中间状态分支的增量成本。
- 选择一个确定性工作流或状态机，将每次状态转换建模为独立 derivation，评估 Nix store 作为持久化缓存的可行性。
- 处理长序列时改用 sequenceFile，并基准测试是否应禁用 substituter 或优先本地构建。

## 正文

One of the most surprising aspects of the Nix language is that it is *lazy*, especially if you have never used a lazy language before. This laziness is what makes much of [Nixpkgs](https://github.com/NixOS/nixpkgs) possible, and its complexity.

One of the simplest ways to observe the laziness is by understanding that only the attributes you access are evaluated.

```
$ nix eval --expr 'let pkgs = 
   { hello = "hi"; broken = throw "never forced"; }; 
   in pkgs.hello'
"hi"
```

The more whackier version of this is you can have *endless* recursion in an attribute set. Nixpkgs is filled with these bottomless attribute sets:

```
$ nix eval -f '<nixpkgs>' 'pkgs.hello' --raw
/nix/store/18bbdvag5v2f3d4y37pdbkzvh7s71cw4-hello-2.12.2

$ nix eval -f '<nixpkgs>' 'pkgs.pkgs.pkgs.hello' --raw
/nix/store/18bbdvag5v2f3d4y37pdbkzvh7s71cw4-hello-2.12.2

$ nix eval -f '<nixpkgs>' 'pkgs.python3Packages.pkgs.hello' --raw
/nix/store/18bbdvag5v2f3d4y37pdbkzvh7s71cw4-hello-2.12.2
```

The same store path every time. `pkgs` contains itself, and so does every package set inside it. 🤯

If laziness is what lets a recursive attribute set terminate, then the recursion doesn’t have to bottom out **at all**:

```
$ nix eval --expr \
    'let countdown = n: { value = n; next = countdown (n + 1); };
     in (countdown 0).next.next.next.value'
3
```

That attribute set is infinitely deep. Indexing three levels into it costs exactly three levels of evaluation, and the rest of the infinite tree is never built because nobody asked.

So an attribute path is a walk through a lazily-generated tree. Which made me wonder: what if the attribute path were *input to something*? 🤔

I decided to take that idea and make the attribute path a sequence of button presses in [Super Mario Bros. 3](https://en.wikipedia.org/wiki/Super_Mario_Bros._3). Each node in the tree is a frame of the game, and each child is a button press that produces a new frame. Game states are recursive by nature.

```
$ nix build '.#level1.rightb.rightb.rightab.rightb'
$ file -L result
result: PNG image data, 256 x 240, 8-bit/color RGB, non-interlaced
```

`.rightb` is right + B, which in Super Mario Bros. 3 is “run right”. `.rightab` is run and jump. The output is the frame you’d be looking at if you’d pressed those buttons in that order, on real hardware, in that game.1 1 The prefix `.#level1` is a precanned sequence of button presses that gets you to the start of level 1-1.

Append `.play` anywhere along the path and you get the whole run stitched into a recording:

Super Mario Bros. 3 running in an emulator: the title screen, the 1/2-player menu, the World 1 map, then Mario running right and jumping in level 1-1

The coolest thing though is that every one of those frames **is a separate derivation in my store**.

The code is at [fzakaria/nes-nix](https://github.com/fzakaria/nes-nix). It is generalized and the ROM is a flake input you point wherever you like for any other game.

The flake computes a derivation based on the attribute path such that each press is its own derivation, and it takes **the previous press’s savestate as an input**. Each derivation *never* re-emulates its ancestors’ frames.2 2 A screenshot of the frame is also produced, which is used when we want to stitch a video sequence together.

The practical consequence is that the store becomes the emulator’s savestate history:

```
# 3 derivations, cold
$ nix build '.#game.start4.wait2.right'
# 1 derivation, prefix reused
$ nix build '.#game.start4.wait2.left'
# 1 derivation, all of it reused
$ nix build '.#game.start4.wait2.right.right'
```

Branching off the middle of a hundred-press run costs one press as does appending to the end of it.

We can look at it the other way. The dependency graph *is* the input sequence, so we can ask Nix what buttons produced a frame:

```
$ nix-store --query --tree 
     $(nix eval --raw '.#game.start.wait4.start.drvPath')
/nix/store/32n4ni0zg01b9c9v64x67am37rdmmr9y-nes-start.drv
└───/nix/store/j5vy3385pgs9dzw0y7sdrdmn7xnrxgji-nes-wait4.drv
    └───/nix/store/w4zz5aqj5zxqhnialabdc7p3sy80v6dc-nes-start.drv
        └───/nix/store/k9wfz8w5157d0xdwaw1vvhf019dvw5s0-nes-boot.drv
```

So what is `.play` actually doing?

Almost nothing. Every frame along the path is already sitting in the store as the output of its own press, so the recording never emulates anything. It is a directory of symlinks to the frames for `ffmpeg` to process.

```
$ nix build '.#level1.rightb.rightb.rightab.play'
$ ls -l result/frames | head -4
0000.png -> /nix/store/3p2fxwngh…-nes-boot
0001.png -> /nix/store/4ha88l0dk…-nes-start
0002.png -> /nix/store/nh4zfsq6x…-nes-wait4
0003.png -> /nix/store/ghbgn28f1…-nes-start
```

How far can we take this input-sequence game input idea?

Nix **by default** gives out at around 2,400 presses, with:

```
$ nix eval --raw ".#game.right.right.right…drvPath"
error: stack overflow; max-call-depth exceeded
```

`max-call-depth` defaults to 10,000 and evaluating each press costs roughly four nested calls.

It’s a guard against runaway recursion, not a structural limit, and we can raise it to 10 million and get 20,000 presses:

```
$ ulimit -s unlimited
$ nix eval --raw --option max-call-depth 10000000 \
      ".#game.$(
        python3 -c 'print(".".join(["right"]*20000))')
      .drvPath"
/nix/store/p4nm0a4p4k9bdjqsag1jj0baah9mj6hb-nes-right.drv
```

20,000 presses, takes roughly fourteen seconds to evaluate on my laptop. The cost is linear in the number of presses, and it is roughly 0.7ms “per press”.

The next bottleneck though is that the kernel gives out at 21,845 presses on my machine. An attribute path is a single `argv` element, and Linux caps the size of the argument list in total and individual arguments.

The per-argument limit is 131,072 bytes (`MAX_ARG_STRLEN`), and each press is six bytes long (`right.`), so 21,845 presses is the maximum that can be passed to `nix eval` as a single argument.

The escape hatch is to stop passing the run as an argument. and we can feed in the input-sequence as from a file:

```
$ nix build --impure --expr \
    '(builtins.getFlake (toString ./.))
      .packages.x86_64-linux.game.sequenceFile 
        ./runs/world1-1.txt'
```

This produces the byte-identical derivation to the equivalent attribute path, so a run kept in a file still shares the same store paths.

All of this was to simply *evaluate* the Nix expression. Now we have to build it. Although Nix is great at building derivations in parallel, the recursion here is tail-recursive and therefore serial.

I benchmarked the build time of a growing list of button presses and the cost is also linear, as we would expect, with the number of presses. The cost per press is roughly 1.27 seconds with substituters enabled and 0.28 seconds with them disabled. The round-trips cost for checking whether the derivation is in the cache costs noticeably more than emulating the frames does.3 3 We can set `preferLocalBuild` or `allowSubstitutes` if we want to avoid this cost.

We’re used to the attribute path being a *name*, simply a coordinate into a catalogue of things that exist. Laziness means it’s really a *program*: a sequence of steps the evaluator walks, generating whatever it needs as it goes.

Nixpkgs happens to use that machinery to describe software, but nothing about it requires that the tree be a catalogue at all. Coupled with the fact that the store turns out to be a decent persistence layer for reproducible state-machines, makes a our “package manager” reasonable to use for playing Mario. 🍄

## 结构化（1）

### 2026-08-17 05:17:46

#### 《Super Mario Derivations》精炼总结

Nix 的惰性求值让“属性路径”不只是查找包的名称，还可以成为一段按需执行的程序。作者借此把《超级马里奥兄弟 3》的每次按键和游戏画面做成独立的 Nix derivation，使 Nix Store 变成可复用、可分支的模拟器存档历史。

##### 1. Nix 的惰性求值与无限属性集

- Nix 只会计算实际访问的属性。即使同一属性集中存在会报错的值，只要没有访问它，表达式仍能正常运行：

  ```nix
  let pkgs = {
    hello = "hi";
    broken = throw "never forced";
  };
  in pkgs.hello
  ```

  结果为 `"hi"`，`broken` 不会被求值。

- Nixpkgs 中存在递归属性集，`pkgs` 可以包含自身，因此以下路径最终都指向同一个 `hello-2.12.2` Store 路径：

  ```text
  pkgs.hello
  pkgs.pkgs.pkgs.hello
  pkgs.python3Packages.pkgs.hello
  ```

- 惰性求值还允许构造理论上无限深的属性树：

  ```nix
  countdown = n: {
    value = n;
    next = countdown (n + 1);
  };
  ```

  访问 `(countdown 0).next.next.next.value` 时，只计算所需的三层并返回 `3`，其余无限结构不会被创建。

##### 2. 把属性路径变成马里奥按键序列

作者把“沿属性路径逐层访问”的过程映射成《超级马里奥兄弟 3》的操作：

- 树中的每个节点代表一帧游戏状态。
- 每个子属性代表一次按键。
- 按键后生成新的游戏状态和画面。

例如：

```bash
nix build '.#level1.rightb.rightb.rightab.rightb'
```

其中：

- `level1`：预设按键序列，将游戏带到世界 1-1 的起点。
- `rightb`：同时按右键和 B，即向右奔跑。
- `rightab`：同时执行向右、奔跑和跳跃。

最终产物是一张 **256×240 的 PNG 截图**，代表按顺序完成这些操作后看到的游戏画面。

##### 3. 每次按键都是独立的 derivation

项目代码位于 `fzakaria/nes-nix`，并不局限于马里奥；ROM 被设计成 Flake 输入，因此也可以替换为其他 NES 游戏。

其核心机制是：

1. 每次按键对应一个独立 derivation。
2. 当前 derivation 以前一次按键产生的模拟器存档为输入。
3. 每一步同时输出新的存档和当前画面截图。
4. 新步骤不需要重新模拟之前的所有帧。

因此，一段操作可以形成可分支的状态树。例如在同一个“向右奔跑”状态之后，可以分别派生出：

- 跳跃；
- 按 A；
- 继续向右；
- 其他任意操作。

##### 4. Nix Store 成为模拟器存档历史

由于每个按键状态都会保存到 Nix Store，已有操作前缀可以直接复用：

```bash
# 首次构建，需要生成 3 个 derivation
nix build '.#game.start4.wait2.right'

# 复用已有前缀，只需生成 left
nix build '.#game.start4.wait2.left'

# 再向已有路径末尾追加 right，只需生成新增步骤
nix build '.#game.start4.wait2.right.right'
```

实际效果是：

- 从一段上百次按键的中间状态创建分支，只需计算新的那一次按键。
- 在已有序列末尾继续追加，也只需计算新增按键。
- 相同状态会共享完全相同的 Store 路径。

反过来，derivation 的依赖图也记录了输入序列。使用 `nix-store --query --tree`，可以从最终画面追溯出产生它的操作，例如：

```text
boot → start → wait4 → start
```

##### 5. `.play` 只是整理已有帧，不会重新模拟

在任意操作路径后追加 `.play`，可以将整段游戏过程合成为录像：

```bash
nix build '.#level1.rightb.rightb.rightab.play'
```

但 `.play` 本身几乎不执行模拟，因为每一帧早已由各自的按键 derivation 生成并存放在 Nix Store 中。

它主要做两件事：

1. 创建一个按时间编号的帧目录；
2. 用符号链接指向 Store 中已有的 PNG，再交给 `ffmpeg` 处理。

例如：

```text
0000.png -> /nix/store/...-nes-boot
0001.png -> /nix/store/...-nes-start
0002.png -> /nix/store/...-nes-wait4
0003.png -> /nix/store/...-nes-start
```

因此，制作录像只是整理和编码已有画面，而不是重新运行整段游戏。

##### 6. 属性路径长度与求值性能限制

###### Nix 默认递归深度

默认情况下，Nix 大约在 **2,400 次按键**后出现：

```text
stack overflow; max-call-depth exceeded
```

原因是：

- `max-call-depth` 默认为 **10,000**；
- 每次按键求值大约消耗 **4 层嵌套调用**。

这只是防止失控递归的保护机制，并非 Nix 的结构性极限。

将递归深度提高到 **10,000,000** 后，作者成功求值了 **20,000 次按键**：

- 总耗时约 **14 秒**；
- 平均每次按键约 **0.7 毫秒**；
- 总成本随按键数量线性增长。

###### Linux 命令行参数限制

在作者的机器上，进一步的瓶颈出现在约 **21,845 次按键**：

- 属性路径作为一个单独的命令行参数传递；
- Linux 单个参数上限 `MAX_ARG_STRLEN` 为 **131,072 字节**；
- `right.` 每次占约 **6 字节**；
- 因此最多约能容纳 **21,845 次**按键。

解决方法是把操作序列保存到文件中：

```bash
nix build --impure --expr \
  '(builtins.getFlake (toString ./.))
   .packages.x86_64-linux.game.sequenceFile
   ./runs/world1-1.txt'
```

通过文件输入生成的 derivation 与等价属性路径生成的 derivation **字节完全相同**，所以仍可共享相同的 Store 路径和缓存。

##### 7. 构建过程仍然是串行的

Nix 通常擅长并行构建，但这里每一步都依赖前一步的存档，因此整个按键序列本质上是串行的，无法并行模拟。

实测构建成本同样随按键数量线性增长：

| 构建方式 | 每次按键约耗时 |
|---|---:|
| 启用 substituter／缓存查询 | 1.27 秒 |
| 禁用 substituter | 0.28 秒 |

启用缓存反而更慢，是因为查询远程缓存的网络往返成本明显高于模拟一帧本身。可以通过 `preferLocalBuild` 或 `allowSubstitutes` 等设置减少这类开销。

##### 8. 核心结论

通常人们把 Nix 属性路径看成包目录中的“坐标”，例如通过名称找到某个软件包。但在惰性求值下，属性路径实际上可以是一段程序：求值器沿路径逐步执行，并只生成当前需要的状态。

Nixpkgs 只是把这种机制用于描述软件；它同样可以描述任何可复现的状态机。由于 Nix Store 能持久化、缓存和共享每一步状态，这个“包管理器”也可以合理地承担马里奥模拟器的存档与执行系统。

## 口播总结（1）

### 2026-09-17 00:24:48

Nix 最让人意外的特性之一，是惰性求值。也就是说，只有真正访问到的内容才会被计算。正是这个特性，让一串看似普通的属性名称，可以变成一段程序，甚至变成超级马里奥的按键操作。

先看惰性求值是什么意思。假设一个属性集合里有两个值。一个是正常字符串，另一个一旦计算就会抛出错误。如果只读取正常的那个值，整个表达式仍然可以顺利运行。因为出错的属性从未被访问，也就根本不会求值。

更特别的是，Nix 可以处理没有尽头的递归属性集合。比如，一个对象包含当前数字，也包含指向下一个对象的属性。下一个对象又包含再下一个对象，如此无限延伸。如果从零开始，沿着“下一个”连续访问三次，得到的就是三。Nix 只生成实际经过的三层。剩下那棵无限深的树，并不会真的被创建。

Nix 的软件包集合也大量使用这种结构。软件包集合里可以包含它自身，内部的其他包集合也可以再次指向同一个集合。因此，无论沿着这种自引用走多少层，最后访问同一个软件包，得到的仍然是同一条存储路径。

由此可以换一种方式理解属性路径。它不只是目录中的一个坐标，更像是沿着一棵惰性生成的树行走。作者于是想到，既然每一步都可以触发计算，那能不能把属性路径解释成超级马里奥的按键序列？

在这个实验里，树上的每个节点代表游戏的一个状态，也就是一帧画面。每条通往子节点的边，则代表一次操作，比如向右、奔跑，或者奔跑并跳跃。于是，一条类似“关卡一、向右奔跑、再次向右奔跑、奔跑并跳跃”的属性路径，就成了一串游戏输入。Nix 构建这条路径后，会输出依次按下这些按键时所看到的游戏画面。

真正关键的设计，是每一次按键都对应一个独立的“派生项”。派生项是 Nix 对一次可复现构建任务的描述。每个按键派生项，都把前一步的游戏即时存档作为输入，再生成新的即时存档和截图。它不需要从开机画面重新模拟，也不会反复执行之前的所有按键。

这样一来，Nix 存储区就变成了模拟器的存档历史。如果已经运行过一百次按键，现在想从中间某一步改走另一条路线，只需要计算新的那一次按键。前面的状态都可以复用。继续在现有路线末尾增加一个按键，同样只需要新增一步。

这很像一棵不断分叉的游戏时间线。共同的前缀只保存一次，后面的不同操作形成不同分支。反过来查看某个画面的依赖关系，还能追溯出产生这幅画面的完整按键序列。换句话说，依赖图本身就是游戏操作记录。

如果想生成整段录像，也不需要重新模拟。因为沿途的每一帧已经分别存在 Nix 存储区里。所谓的播放功能，基本上只是建立一组指向这些截图的链接，再交给视频工具按顺序合成。录像是在整理已有结果，而不是重新玩一遍游戏。

当然，这个实验也暴露了实际限制。Nix 默认大约处理到两千四百次按键时，会触发最大调用深度限制。这个限制主要是为了防止失控递归，并不是这种结构本身的上限。作者提高限制后，成功求值了两万次按键。在他的笔记本上，这大约需要十四秒，平均每次按键约零点七毫秒，求值成本随按键数量线性增长。

接下来遇到的瓶颈反而来自操作系统。整条属性路径被当作一个命令行参数传入，而 Linux 对单个参数的长度有限制。以“向右”操作的路径文本计算，大约两万一千八百四十五次按键就会达到上限。解决办法是把按键序列放进文件，而不是塞进命令行。文件形式生成的派生项与等价的属性路径完全相同，因此仍然能共享已有的存储结果。

真正构建游戏状态时，成本也是线性增长的。虽然 Nix 擅长并行构建，但这里每一步都依赖上一步的存档，所以整条链只能串行执行。作者测得，关闭远程缓存查询时，每次按键约需零点二八秒。启用缓存查询后，反而约需一点二七秒。原因是检查缓存的网络往返开销，比模拟这一小段游戏还要高。

这个实验最值得记住的，不是 Nix 居然能玩马里奥，而是对属性路径的重新理解。惰性求值让属性路径不再只是一个名称，而是一连串按需执行的步骤。再加上 Nix 存储区能够保存和复用可重现的状态，它就不只是软件包管理工具，也可以成为一种持久化、可分叉、可追溯的状态机。

## 深度解读（1）

### 2026-09-17 00:36:26

#### 当“属性路径”变成程序：Nix 展示了一种可复用的状态机

这篇文章最有价值的地方，不是“用包管理器玩马里奥”的奇技淫巧，而是它把 Nix 的惰性求值和存储机制重新解释成了一套**状态机执行与历史复用系统**。

##### 路径不只是名字，也可以是一段执行轨迹

通常我们把 `pkgs.hello` 理解为目录中的坐标。但在 Nix 中，属性只有被访问时才求值，因此递归属性集可以无限延伸：系统不需要生成整棵树，只需计算实际走过的路径。

作者据此把每个游戏状态定义为树上的节点，把 `.rightb.rightab` 这样的属性路径解释为连续按键。每次按键都是一个 derivation，以上一次的模拟器存档为输入，输出新的存档和画面。于是，一条属性路径同时具有三种身份：

- 它是输入序列；
- 它是状态转换的执行计划；
- 它还是可查询的依赖图，能够反推出某一画面由哪些按键产生。

这比一般的“命令序列”多了一层重要能力：**执行历史本身被固化为可复用的计算图**。从一百步游戏过程的中间分叉，只需计算新的那一步；在已有路径末尾追加动作，也只增加一个 derivation。生成录像时甚至不必重新模拟，只需把存储中已有的逐帧结果链接起来。

##### 真正可迁移的是“确定性状态机 + 增量缓存”

这种模式与事件溯源、增量计算和 Merkle DAG 有共同机制：状态由前一状态和新事件确定，相同前缀自然共享结果。它适合模拟器，也可能适用于编译流水线、可复现实验、数据变换，乃至工具调用路径稳定的智能体评测。

但关键前提不是“Nix 很灵活”，而是任务必须具有**确定性的状态转换、可序列化的中间状态，以及较高的分支复用率**。惰性求值避免了提前生成无限状态树，却没有消除实际走过路径的线性成本；如果外部环境不断变化、状态巨大，或几乎没有重复前缀，复用价值会明显下降。探索大量分支时，状态空间依然可能爆炸。

##### 缓存并非越细越好

文章的性能数据还揭示了一个更普遍的工程判断：计算粒度过细时，基础设施成本可能超过计算本身。作者测得每次按键本地构建约需 0.28 秒，启用远程 substituter 后反而约为 1.27 秒，因为检查缓存的网络往返比模拟一帧更贵。长序列还会撞上求值递归深度与 Linux 单参数长度限制。

因此，这个实验带来的产品与架构启示不是“把一切拆成最小步骤”，而是：**应根据重算成本、缓存查询成本和分支复用概率选择状态边界**。Nix 证明了包管理器可以被看成可复现状态机的平台；马里奥则把它的能力与边界同时暴露了出来。
