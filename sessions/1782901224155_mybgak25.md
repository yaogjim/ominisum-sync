## 正文

**宝玉**

Q：我们公司有十几个微服务，现在想让开发用 AI Agent 来做系统设计和编码。问题是一个 user story 经常需要多个微服务协作，Agent 必须了解每个服务的职责边界和业务概念才能做出合理的设计。我们打算把所有微服务放到一个 workspace 下，每个服务配上自己的文档，让 AI 自己去处理。这种方式合理吗？有没有更好的实践？

A：用好 Agent 的关键是两点：上下文的质量，和验证的闭环。

先说上下文质量。

放在一个 workspace 下是目前社区比较推荐的做法。

monorepo 天然适合和 AI 配合，因为 Agent 可以在一个地方同时看到 schema 定义、API 协议、各个服务的实现代码。如果因为历史原因确实不方便合成 monorepo，有个折中方案叫虚拟 monorepo，就是把多个仓库 clone 到同一个本地目录下。

除了放在一起，文档也是很好的让Agent获取上下文的方式，最好给 Agent 一张地图，加上按需加载：  
1\. 根目录放一份总的 AGENTS.md(或 CLAUDE.md)当索引用，列清楚有哪些服务、各自负责什么、要改某个服务就去读它目录下的文档。  
2\. 每个微服务自己目录里再放一份,写清自己的职责边界和业务概念,这其实就是 DDD 里的 bounded context。  
3\. 让 Agent 先看根索引，定位到相关的那几个服务，再去加载它们的细节。

不过要注意文档要及时更新，尤其是微服务协议变更了，一定要及时更新文档，否则会误导。

能从代码或规格自动生成的，就别手写。手写文档迟早会和代码对不上，而像 OpenAPI 这种机器可读的接口规格，一份东西既是文档，又能拿去生成 mock 和测试。

除了文档，还有一个很多人忽略的上下文来源：协议测试代码。高质量的 contract test 本身就是最准确的活文档，它精确地描述了服务之间实际的交互协议，比人写的文档更不容易过时，因为错了测试就无法通过。你如果已经有 OpenAPI spec 或者 Pact 契约文件，这些对 Agent 理解服务边界非常有价值。

再说验证。微服务场景下验证是最麻烦的部分，因为一个 user story 可能涉及好几个服务协作，你不可能让 Agent 每改一行代码就把整个系统跑起来做端到端测试。

一个实用的思路是：每个微服务提供 mock server 或者基于 OpenAPI spec 自动生成的模拟服务。Agent 写完代码后可以在本地跑 contract test 验证自己的改动有没有破坏和其他服务的协议约定，不需要依赖线上真实的 API 或者完整的集成环境。这样 Agent 就能形成一个“写代码→跑测试→自我修正”的闭环，不需要人在过程中频繁干预。

想再进一步,建议了解一下契约测试(consumer-driven contract testing，常用工具是 Pact)。思路是调用方把自己实际用到的接口形状记下来，生成一个契约文件，被调方再去验证自己能不能满足这个契约。

简单说：workspace 统一提供全局视图，分层文档 + 协议测试提供精准上下文，mock server + contract test 提供验证闭环。这三层搭好，Agent 处理跨微服务的系统设计就比较靠谱了。

#### 深度总结

这篇内容的核心观点：**让 AI Agent 做跨微服务设计和编码，关键不是“把代码都丢给它”，而是给它高质量上下文，并让它能自我验证。**

##### 1. 上下文：要有“全局地图 + 局部细节”

微服务多了以后，Agent 最大的问题不是不会写代码，而是：

- 不知道每个服务负责什么；
- 不知道业务概念边界；
- 不知道服务之间怎么交互；
- 容易读错、读多、读偏上下文。

比较好的做法是：

```text
统一 workspace / 虚拟 monorepo
├── AGENTS.md：全局索引
├── service-a/
│   └── AGENTS.md：服务职责、边界、业务概念
├── service-b/
│   └── AGENTS.md
└── service-c/
    └── AGENTS.md
```

根目录文档负责告诉 Agent：

- 有哪些服务；
- 每个服务大概负责什么；
- 改某类需求时应该看哪些服务。

每个服务内部文档负责说明：

- 服务职责；
- 业务边界；
- 核心概念；
- 对外接口；
- 依赖关系。

这本质上是在给 Agent 建一张 **系统地图**。

---

##### 2. 文档：最好机器可读、可验证

文章特别强调：**手写文档容易过期，过期文档会误导 Agent。**

所以，能自动生成的就不要手写，比如：

- OpenAPI；
- Protobuf；
- GraphQL Schema；
- Pact 契约文件；
- contract test；
- mock server 配置。

这些东西比普通文档更可靠，因为它们不仅能读，还能跑、能测、能验证。

尤其是 **协议测试代码**，它其实是最准确的“活文档”。

---

##### 3. 验证：Agent 必须有闭环

只让 Agent 写代码不够，还要让它能自己检查：

```text
理解需求
→ 修改代码
→ 运行测试
→ 发现错误
→ 自我修正
```

微服务场景下，不能每次都启动完整系统做端到端测试，所以更现实的方式是：

- 每个服务提供 mock server；
- 使用 OpenAPI 自动生成模拟服务；
- 使用 contract test 验证服务之间协议是否兼容；
- 使用 Pact 做消费者驱动契约测试。

这样 Agent 不需要依赖完整环境，也能判断自己改得对不对。

---

#### 深入浅出解读

可以把 Agent 想成一个新来的高级工程师。

如果你只把十几个微服务代码仓库丢给他，他会懵：

> “我该看哪个服务？  
> 这个接口是谁调用的？  
> 这个字段能不能改？  
> 这个业务概念到底属于哪个服务？”

所以你不能只给代码，还要给他：

##### 1. 地图

告诉他系统长什么样。

比如：

| 服务 | 职责 |
|---|---|
| user-service | 管用户资料 |
| order-service | 管订单 |
| payment-service | 管支付 |
| inventory-service | 管库存 |

这能防止 Agent 胡乱跨服务设计。

---

##### 2. 规则

告诉他哪些事情归哪个服务管。

比如：

- 用户余额不应该由订单服务直接改；
- 支付状态以支付服务为准；
- 库存扣减必须走库存服务接口。

这就是所谓的 **bounded context，限界上下文**。

通俗说就是：

> 谁家的事，谁负责。

---

##### 3. 合同

服务之间调用接口，本质上像签合同。

比如订单服务调用支付服务：

```json
POST /payments
{
  "orderId": "123",
  "amount": 100
}
```

如果支付服务突然要求多传一个字段，而订单服务不知道，系统就会出问题。

所以要用 OpenAPI、Pact、contract test 这类东西，把“合同”写清楚，并且自动检查。

---

##### 4. 考试

Agent 写完代码后，不能靠感觉。

必须让它考试：

- 单元测试；
- 契约测试；
- mock server 测试；
- 局部集成测试。

只有能自己测试、自己修正，Agent 才不是“代码生成器”，而是接近“自动开发助手”。

---

#### 关键实践框架

一句话总结：

> **统一视图，分层上下文，机器可读协议，自动验证闭环。**

可以拆成四步：

##### 第一步：统一代码视图

优先：

```text
monorepo
```

如果做不到：

```text
虚拟 monorepo：多个 repo clone 到同一个 workspace
```

目的不是强行改组织结构，而是让 Agent 能看到相关服务。

---

##### 第二步：建立 Agent 索引

根目录放：

```text
AGENTS.md / CLAUDE.md
```

内容要短、准、可导航：

```markdown
# 系统服务索引

## user-service
负责用户身份、资料、权限。

## order-service
负责订单创建、取消、状态流转。

## payment-service
负责支付发起、回调、退款。

## 修改建议
- 涉及订单状态：看 order-service
- 涉及付款：看 payment-service
- 涉及用户权限：看 user-service
```

---

##### 第三步：每个服务写边界文档

每个服务目录下也放一份：

```text
service/AGENTS.md
```

重点写：

- 这个服务负责什么；
- 不负责什么；
- 核心领域对象；
- 对外 API；
- 依赖哪些服务；
- 修改时必须跑哪些测试。

不要写长篇大论，要像路标。

---

##### 第四步：建设验证闭环

最重要的是让 Agent 能跑：

```bash
npm test
go test ./...
mvn test
pytest
pact test
contract test
```

并告诉 Agent：

```markdown
修改本服务后必须运行：
1. 单元测试
2. contract test
3. OpenAPI schema 校验
```

没有验证闭环，Agent 很容易“看起来写对了，实际跑不通”。

---

#### 辩证思考

##### 1. 把所有微服务放进 workspace 是必要条件，不是充分条件

统一 workspace 有价值，因为它给 Agent 全局视角。

但它也有风险：

- 上下文太大；
- token 消耗暴涨；
- Agent 读到无关信息；
- 错误文档污染判断；
- 复杂度反而上升。

所以关键不是“让 Agent 看见所有东西”，而是：

> 让 Agent 在正确时机，看正确内容。

也就是 **按需加载上下文**。

---

##### 2. 文档不是越多越好，而是越准越好

很多团队的问题不是没文档，而是：

- 文档过期；
- 文档太散；
- 文档和代码不一致；
- 文档写得像作文，不像导航。

对 Agent 来说，坏文档比没文档更危险。

更可靠的顺序应该是：

```text
可执行测试 > 机器可读规格 > 简明索引文档 > 长篇手写文档
```

---

##### 3. Agent 会放大系统治理水平

如果微服务本身边界清晰、接口规范、测试完善，Agent 会很好用。

如果系统本来就是：

- 服务职责混乱；
- 接口随意变更；
- 没有契约测试；
- 没有领域边界；
- 全靠老员工脑子记；

那 Agent 不会神奇地解决问题，反而会把混乱放大。

所以引入 Agent，本质上也是一次工程治理体检。

---

##### 4. AI Agent 不是替代架构设计，而是倒逼架构显性化

过去很多系统知识藏在：

- 老员工经验里；
- Slack/飞书聊天里；
- 历史需求里；
- 隐性约定里。

Agent 用不好，常常不是模型不够聪明，而是组织知识没有结构化。

要让 Agent 有效工作，公司必须把隐性知识变成：

- 服务地图；
- 边界文档；
- API 规格；
- 契约测试；
- mock 环境；
- 自动化验证。

这其实会反过来提升团队工程质量。

---

#### 最精炼结论

让 AI Agent 做跨微服务开发，最佳实践不是简单地“把所有代码放一起”。

真正有效的是三层体系：

```text
1. 统一 workspace：给全局视图
2. 分层文档 + 协议规格：给精准上下文
3. mock server + contract test：给验证闭环
```

最终目标是：

> Agent 不只是能读代码，而是能理解边界、遵守契约、跑测试、自我修正。

## 结构化（1）

### 2026-07-22 09:37:58

##### 主旨概括

对于拥有十几个微服务、且一个 User Story 经常跨多个服务的团队，把代码统一放进一个 workspace 是合理起点，但关键不只是让 Agent“看到所有代码”，而是同时做好**高质量上下文**与**可自动验证的闭环**。较可靠的组合是：**统一 workspace + 分层文档与契约 + Mock/契约测试**。

##### 1. 统一代码视图：Monorepo 或“虚拟 Monorepo”

- **Monorepo 更适合 AI Agent**：Agent 能在同一位置查看数据库 Schema、API 协议及各服务实现，更容易完成跨服务设计。
- 如果历史原因导致仓库无法合并，可以采用**虚拟 Monorepo**：
  - 保留各自独立仓库；
  - 将多个仓库 clone 到同一个本地目录；
  - 让 Agent 在统一 workspace 中访问它们。
- 重点不是物理上必须合仓，而是给 Agent 提供一个可导航的**全局系统视图**。

##### 2. 分层组织文档，让 Agent 按需加载

建议为 Agent 提供一张“系统地图”，而不是一次性塞入全部资料：

1. **根目录设置总索引**
   - 放置 `AGENTS.md` 或 `CLAUDE.md`；
   - 列出全部服务、各自职责，以及修改某项功能时应查看哪些服务文档。

2. **每个微服务维护自己的说明**
   - 在服务目录内放置独立的 `AGENTS.md`；
   - 说明职责边界、核心业务概念、上下游依赖；
   - 本质上对应 DDD 中的 **Bounded Context（限界上下文）**。

3. **让 Agent 分阶段读取**
   - 先读取根目录索引；
   - 判断当前任务涉及哪些服务；
   - 再加载相关服务的详细文档和代码。

这种方式可以减少无关信息进入上下文，避免 Token 消耗过大和上下文污染。

##### 3. 文档应尽量机器可读、自动生成

- 微服务接口或协议发生变化时，文档必须同步更新，否则会直接误导 Agent。
- 能从代码或规格中自动生成的内容，不应依赖手写，因为手写文档很容易与实际实现脱节。
- 推荐使用 **OpenAPI** 等机器可读规格：
  - 既可以作为接口文档；
  - 也能生成客户端、Mock 服务和测试；
  - 更容易保持文档、代码与验证逻辑一致。

##### 4. 协议测试是更可靠的“活文档”

除了普通文档，Agent 还应重点读取服务间的协议测试资产：

- 高质量的 **Contract Test（契约测试）**能精确描述服务之间真实的交互方式。
- 相比人工文档，契约测试不容易悄悄过时：如果接口不兼容，测试就会失败。
- 已有的 **OpenAPI Spec**、**Pact 契约文件**等，都是 Agent 理解服务边界和调用关系的重要上下文。

换言之，Agent 能访问所有代码，并不代表它真正理解服务边界；**机器可读、可执行、可验证的契约**通常比纯 Markdown 更可靠。

##### 5. 用 Mock 与契约测试建立验证闭环

跨微服务任务最困难的部分是验证：一个 User Story 可能涉及多个服务，不可能让 Agent 每改一处代码，就启动整个系统并执行完整端到端测试。

实用做法是：

- 每个微服务提供 **Mock Server**；
- 或基于 OpenAPI Spec 自动生成模拟服务；
- Agent 完成修改后，在本地运行 Contract Test；
- 检查改动是否破坏与其他服务约定的接口；
- 不必依赖线上真实 API 或完整集成环境。

由此形成自动闭环：

> 写代码 → 运行测试 → 发现问题 → 自我修正

这样可以减少开发者在 Agent 工作过程中的频繁介入。

##### 6. 进一步采用消费者驱动契约测试

可进一步引入 **Consumer-Driven Contract Testing（消费者驱动契约测试）**，常用工具是 **Pact**。

其基本流程是：

1. 接口调用方记录自己实际使用的请求与响应结构；
2. 生成契约文件；
3. 接口提供方用该契约验证自己的实现；
4. 若提供方的变更无法满足调用方需求，测试立即失败。

例如，订单服务依赖用户服务返回 `userId` 和 `status`，那么订单服务可生成对应契约；用户服务修改接口时，必须验证仍能满足这份契约，从而提前发现跨服务兼容性问题。

##### 7. 实践中的风险与补充建议

热门回复补充了几个现实问题：

- 微服务全部放进一个 workspace 后，可能出现**上下文窗口膨胀、Token 消耗和无关信息污染**。
- Agent“看得到所有代码”不等于理解业务，仍需要清晰的领域拆分和可导航的系统地图。
- 不一定必须使用真正的 Monorepo：将相关服务放在同级目录，并在各服务的 `AGENTS.md` 中写明业务边界和依赖关系，也能取得类似效果。
- 最重要的是坚持**按需加载**，避免 Agent 随意读取不相关服务。
- 最终效果也取决于模型能力，以及现有微服务边界是否清晰；如果系统本身存在大量历史债务，应先梳理领域和依赖关系。

##### 结论

较稳妥的三层方案是：

1. **统一 workspace**：通过 Monorepo 或虚拟 Monorepo 提供全局视图；
2. **分层、精准的上下文**：根目录索引、服务级文档、OpenAPI 和契约文件按需加载；
3. **自动验证闭环**：使用 Mock Server、Contract Test 和 Pact，让 Agent 能自主测试并修正。

这三层搭建完善后，AI Agent 才能更可靠地处理跨微服务的系统设计与编码任务，而不是仅仅“读到很多代码”。

## 口播总结（1）

### 2026-08-03 01:19:33

#### 让 AI Agent 参与微服务设计与编码，关键不只是把代码放在一起

如果一家公司有十几个微服务，希望让 AI Agent 参与系统设计和编码，真正的关键有两点：第一是给它高质量、分层次的上下文；第二是建立自动验证和自我修正的闭环。下面会按照这个思路，说明如何组织代码、文档和测试，让 Agent 更可靠地处理跨微服务的需求。

##### 首先，给 Agent 一个统一但清晰的全局视图

核心结论是：把相关微服务放到同一个 workspace 里，通常是合理的；如果条件允许，monorepo，也就是“单一代码仓库”，会更适合和 AI Agent 配合。

原因很简单。一个跨服务的需求，往往同时涉及数据库结构，也就是 schema，服务之间的 API 协议，以及多个服务的具体实现代码。如果这些内容都在同一个地方，Agent 就能更容易地看到完整关系，而不是只理解其中一个服务。

比如，一个用户故事可能需要订单服务、库存服务和支付服务一起配合。Agent 不仅要知道订单服务怎么写，还要知道库存服务提供什么接口，支付服务返回什么结果，以及这些服务之间如何传递数据。monorepo 可以把这些信息放在一个统一视图里。

如果因为历史原因，暂时不能真正合并成一个 monorepo，也可以采用一个折中方案，叫“虚拟 monorepo”。做法是：保留多个独立仓库，但把它们分别拉到同一个本地目录下。这样，代码仓库没有物理合并，Agent 仍然可以在一个工作区里查看多个服务。

不过，统一放在一起并不等于把所有内容一次性塞给 Agent。内容太多，反而可能造成上下文窗口被撑爆，或者让 Agent 读到大量无关信息，产生上下文污染。因此，统一视图还必须配合按需加载。

##### 接下来，用分层文档给 Agent 一张“系统地图”

核心结论是：文档不能只是堆在各个服务旁边，而应该分层组织，让 Agent 先找到方向，再读取具体细节。

第一层，是放在根目录的总索引文件。可以叫 `AGENTS.md`，也可以叫 `CLAUDE.md`。这份文件不需要写完所有技术细节，主要负责说明系统里有哪些服务、每个服务负责什么，以及如果要修改某个服务，应该进一步阅读哪个目录下的文档。

第二层，是每个微服务目录里的专属说明。这里要写清楚这个服务的职责边界、核心业务概念、依赖哪些其他服务，以及哪些事情不应该由它负责。

这种“一个服务对应一个业务边界”的做法，在领域驱动设计，也就是 DDD 里，叫作“限界上下文”。通俗地说，就是明确一个服务负责理解和处理哪些业务概念，同时明确它不负责哪些事情。

第三步，是让 Agent 按需读取。它应该先看根目录的总索引，判断一个需求可能涉及哪几个服务；然后只加载这些服务的详细文档、代码和协议，而不是无差别地扫描整个系统。

这样做的实际意义是，既让 Agent 看得到全局关系，又避免它被不相关的服务干扰。对于微服务数量较多的系统，这一点尤其重要。否则，Agent 虽然“看得到所有代码”，却未必真正理解服务之间的边界。

还要特别注意，文档必须跟着系统一起更新。尤其是微服务之间的协议发生变化时，如果文档没有同步修改，Agent 得到的就可能是错误信息。

因此，能够从代码或规格自动生成的内容，尽量不要完全依赖手写。比如 OpenAPI，它是一种机器可读的接口描述格式，既可以作为接口文档，也可以用来生成模拟服务和测试。这样可以减少文档和实际代码逐渐偏离的问题。

##### 更重要的是，让机器可读的协议成为可靠上下文

核心结论是：除了普通文档，协议规格和协议测试，往往是 Agent 理解微服务边界最可靠的上下文。

普通说明文档可以告诉 Agent，一个服务在业务上负责什么。但真正决定服务能否协作的，往往是接口协议：请求需要哪些字段，返回什么数据，哪些错误情况必须处理，以及调用顺序有什么要求。

OpenAPI 规格就是一种重要的机器可读资产。它不仅能帮助 Agent 理解 API，还能进一步生成 mock server，也就是模拟服务，以及相关测试。

协议测试代码同样非常重要。它可以被看作一份“活文档”，因为它描述的是服务之间实际执行的交互规则，而不是人凭印象写下来的说明。

比如，调用方期待库存服务返回某个字段，协议测试就会明确记录这一点。如果库存服务修改了返回结构，测试就可能失败。也就是说，协议一旦不符合预期，系统会立刻暴露问题。正因为如此，高质量的协议测试通常比普通手写文档更不容易过时。

如果系统里已经有 OpenAPI 规格，或者已经使用 Pact 这类契约文件，那么这些内容对 Agent 理解服务职责和边界都非常有价值。

##### 然后，建立“写代码、跑测试、自我修正”的闭环

核心结论是：微服务场景下，不能要求 Agent 每修改一行代码，就启动整个系统进行端到端测试；更实用的做法，是让每个服务都能独立验证自己是否破坏了跨服务协议。

原因在于，一个 user story 可能涉及多个服务。如果每次修改都要依赖线上真实 API，或者启动完整的集成环境，测试会非常慢，也很难稳定。Agent 也就无法快速判断自己的修改是否正确。

一个实用方案是，让每个微服务提供 mock server，或者根据 OpenAPI 规格自动生成模拟服务。

这样，Agent 写完代码后，可以在本地运行协议测试，检查自己的改动是否仍然符合其他服务的约定。它不需要连接线上真实服务，也不需要每次都启动完整系统。

理想的工作过程是这样的：Agent 先理解需求和相关服务边界，然后修改代码；接着运行本地协议测试；如果测试失败，就根据错误信息调整实现；调整后再次测试。最终形成“写代码、跑测试、自我修正”的闭环，减少人在中间频繁介入。

这也是让 Agent 从“会生成代码”变成“能完成工程任务”的关键。没有验证环节，Agent 只是提出一个看起来合理的方案；有了自动验证，它才有机会确认方案是否真的符合系统约定。

##### 进一步了解契约测试，强化服务之间的约束

核心结论是：如果想把跨微服务验证做得更扎实，可以引入契约测试，尤其是消费者驱动的契约测试，也就是 consumer-driven contract testing。

它的基本思路是：调用方，也就是消费者，先把自己实际使用的接口形式记录下来，生成一份契约文件。然后，被调用方，也就是提供服务的一方，负责验证自己的实现是否满足这份契约。

举个简单的例子。订单服务调用库存服务时，订单服务可能只依赖库存服务返回的库存数量和商品编号。它可以把自己真正需要的请求格式和返回格式记录成契约。库存服务随后验证自己的接口是否满足这份要求。

这里常用的工具是 Pact。它能帮助调用方和被调用方围绕实际使用的接口建立明确约定。

这样做的好处是，服务之间不需要依赖一份过于宽泛的文档，而是直接验证“调用方真正需要什么”。一旦某个服务的修改破坏了这份约定，契约测试就会发现问题。

##### 最后，把整个方法归纳成三层

核心结论是：让 Agent 可靠处理跨微服务的系统设计，最好同时搭建三层能力。

第一层，是 workspace 提供全局视图。它让 Agent 可以在同一个地方看到多个服务、接口协议、数据结构和实现代码。首选是 monorepo；无法合并时，也可以使用虚拟 monorepo。

第二层，是分层文档和协议测试提供精准上下文。根目录的 `AGENTS.md` 或 `CLAUDE.md` 负责导航；每个服务自己的文档负责说明职责边界和业务概念；OpenAPI 等机器可读规格，以及协议测试，则负责提供更准确、更不容易过时的细节。

第三层，是 mock server 和 contract test 提供验证闭环。Agent 不必每次都启动完整系统，而是可以在本地快速检查自己的改动有没有破坏服务之间的协议。

需要注意的是，workspace 只是基础设施，不是全部答案。微服务数量较多时，不能让 Agent 无差别扫描所有文档和代码。必须做好领域拆分、文档索引和按需加载，否则就可能出现 token 窗口过大、上下文污染，或者 Agent 被无关服务误导的问题。

##### 记住这几个结论

最后，可以记住五点。

第一，Agent 能不能做好微服务设计，关键不只是模型能力，更取决于上下文质量和验证闭环。

第二，monorepo 或虚拟 monorepo 能提供统一视图，但不能代替清晰的服务边界。

第三，根目录索引加服务级文档，可以让 Agent 先定位范围，再按需加载细节。

第四，OpenAPI、协议文件和协议测试，是比普通手写说明更可靠的机器可读上下文。

第五，mock server 加 contract test，可以让 Agent 形成“写代码、跑测试、自我修正”的工程闭环，从而更稳妥地处理跨多个微服务的需求。

#### AI 跨微服务开发的关键，不是“看到全部代码”，而是系统能否被导航和验证

这篇内容最值得保留的判断是：**Agent 的工程能力主要受两件事限制——能否获得恰当的上下文，以及能否快速验证自己的改动。** 把十几个微服务放进同一 workspace，只解决了“有权访问”的问题，并没有自动解决“知道该看什么、相信什么”的问题。

##### Workspace 是搜索空间，不是系统地图

Monorepo 或“虚拟 monorepo”的价值，在于让 Agent 能同时检索接口、schema 和实现，减少跨仓库操作成本。但代码都在眼前，不等于 Agent 理解了服务边界。一次性暴露所有服务，反而可能造成上下文污染：相似概念被混淆，历史实现被误当成当前规范，无关代码挤占注意力。

因此，根目录的 `AGENTS.md` 更像一套路由机制：先说明有哪些服务、各自负责什么、彼此如何依赖，再指引 Agent 按任务加载局部信息。每个服务内部的文档则定义业务概念、职责边界和修改约束。**好的上下文工程不是提供最多信息，而是让 Agent 用最低成本找到当前决策所需的信息。**

这也解释了为什么“手工维护文档优先级”并不等于没有获得 AI 收益。服务边界本来就是组织需要明确表达的知识；AI 只是把过去依赖资深工程师记忆的隐性架构，逼成了可查询的显性资产。

##### 最有价值的文档，是会因错误而失败的文档

文章对 OpenAPI、Pact 契约和 contract test 的强调，比“统一 workspace”更重要。普通文档过期后通常无人察觉，而机器可读规格可以生成 mock、驱动测试，并在实现偏离约定时直接报错。它既为 Agent 提供上下文，也成为判断结果是否正确的依据。

这形成了 Agent 真正需要的闭环：

> 定位相关服务 → 修改代码 → 启动 mock → 运行契约测试 → 根据失败结果修正。

没有这个闭环，Agent 只是更快地产生候选代码；有了闭环，它才可能在较少人工介入下完成迭代。对复杂工程任务而言，**可自动验证性往往比模型一次写对的概率更重要。**

不过，契约测试只能证明接口形状和交互约定没有被破坏，不能证明系统设计合理。跨服务事务的一致性、数据归属、权限边界、性能退化和异常补偿，仍需要明确的业务不变量、架构决策记录以及更高层测试。尤其是“系统设计”和“按既定设计编码”不应混为一谈：后者更容易被闭环约束，前者仍包含大量无法由接口契约裁决的取舍。

##### AI 落地会暴露的，其实是架构债务

如果团队无法回答某个概念归哪个服务、哪个接口定义才权威、一次变更如何在本地验证，那么问题不只是 Agent 不够聪明，而是系统本身缺少可操作的边界。AI 在这里像一场压力测试：它会迅速暴露文档漂移、契约缺失、环境依赖和领域划分含混。

更稳妥的落地方式不是先把所有仓库塞给 Agent，而是选几类典型的跨服务 user story 做试点，观察它能否准确找到相关服务、需要加载多少上下文、契约测试能拦住哪些错误，以及最终仍需人工判断什么。由此补齐系统地图、机器可读契约和局部验证工具。

最终值得建设的不是一个“什么都能看见”的 Agent，而是一套**人和 Agent 都能导航、约束并验证的工程系统**。这套基础设施即使暂时不用 AI，也会降低新人上手、跨团队协作和服务变更的成本。
