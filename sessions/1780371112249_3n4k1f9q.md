## 分析要点

- **核心高价值点**：强调中间状态应存放在脚本变量、文件系统或结构化存储等“基底”中，而不是回灌到编排器上下文，从而避免重建单智能体上下文瓶颈。
- **留存建议**：长期保留（文章提供了较完整的多智能体系统设计框架，包含拓扑、通信、治理、故障模式和落地检查清单，适合作为构建 Agent 工作流的参考资料。）

**知识要点**

- 多智能体系统的核心故障通常来自运行时协调、上下文传播和权限边界，而不是单个智能体推理能力不足。
- 六种常见编排拓扑包括顺序流水线、协调器-工作节点、并行扇出合并、生成器-验证器、共享状态和对抗性辩论。
- 生产级多智能体系统需要明确输出契约、权限范围、失败行为、人类审批门和可观测性机制。
- 上下文污染、级联故障、范围蔓延、静默替换和协调死锁是多智能体系统的主要故障模式。
- 是否使用多智能体应取决于任务是否具备独立并行路径、上下文窗口压力、对抗性验证需求、长任务检查点和可复用流程价值。

**行动项**

- 在设计多智能体工作流前，先绘制任务依赖图，区分顺序阶段和可并行扇出任务。
- 为每个 Agent 定义角色、工具权限、输入范围、JSON 输出契约和失败处理策略。
- 在关键写入共享状态前增加验证器或评估器，降低上下文污染和级联失败风险。
- 为不可逆操作设置人工审批门，并通过 CLAUDE.md 或系统提示固化权限与错误处理规则。
- 优先从 3-7 个 Agent 的小规模工作流开始，验证编排收益是否超过协调成本。

#### 模块 1：多智能体系统实际上是什么

---

#### 单元和运行时

智能体是一个单元：一个 LLM 实例，拥有自己的系统提示词、工具集、记忆窗口，有时还拥有自己的模型。多智能体系统是一种运行时：一种协调两个或多个智能体、在它们之间路由任务、处理交接并执行治理层的机制。

这种区别很重要，因为多智能体系统中的大多数故障是运行时故障，而非智能体故障。单个智能体通常能够正确推理。系统在协调、上下文传播和权限边界方面出现故障。

#### 为什么单个代理会失效

单个代理处理大型任务时会遇到三个硬性限制：

- 上下文饱和度： 每一个中间结果都会占用上下文窗口。在大规模场景下，智能体是基于自身大量的历史记录进行推理，而非实际问题。
- 串行瓶颈： 代理一次执行一个步骤。本可并行的 200 个文件迁移却串行运行数小时。
- 脆弱恢复： 如果代理在任务中途崩溃或漂移，整个任务将重新启动。没有检查点。

多智能体系统通过在孤立的智能体之间分配工作、在任何智能体的上下文之外存储中间状态以及添加阶段级别的恢复点，解决这三个问题。

#### 模块 2：Claude 的三种编排原语

在选择拓扑结构之前，请先了解 Claude Code 提供的三个协调原语。选错适合这项工作的原语是最常见的架构错误。

决策规则：

- 使用子代理，当您需要一两个独立的调查并向单个会话汇报时。
- 使用 agent teams 当队友需要直接与彼此以及与你沟通，无需经过中央编排器。
- 使用动态工作流当编排本身需要可重复执行时，计划必须能够在上下文限制下保持有效，或者任务需要数小时到数天。

#### 模块 3：六种编排拓扑结构

你构建的每个多智能体系统都会使用六种拓扑结构之一或它们的组合。将拓扑结构与问题匹配，而非与框架匹配。

#### 顺序流水线

以链式排列的代理。代理 A 生成输出，将其传递给代理 B，代理 B 再将其传递给代理 C。

```markdown
text[Agent A: Parse] -> [Agent B: Analyze] -> [Agent C: Format]
```

使用场景： 工作严格依赖。每个步骤必须在前一步完成后才能开始。数据只有一条路径，便于调试。

Claude 实现: 提示链在单个动态工作流脚本中。每个阶段运行一个子代理，等待完成，将结果作为输入传递给下一阶段。

故障模式： 延迟加剧。如果 Agent B 运行缓慢，整个流程将等待。请勿用于处理具有独立并行路径的工作。

---

#### 2\. 协调器-工作节点（中心-分支）

一个协调器代理接收顶层任务，将其分解为子任务，并将每个子任务分配给一名专业工作者。工作者将结果返回给协调器，协调器进行综合。

```markdown
text[Coordinator]
             /      |       \
[Security]  [Perf]  [Auth]   [Coverage]
             \      |       /
              [Coordinator: Synthesize]
```

使用场景： 工作分解为不同的专业领域。路由逻辑在规划阶段稳定且可预知。

Claude 实现： 这是 Claude 动态工作流的默认形态。工作流脚本是协调者；子代理是执行者。Claude 将分解逻辑写入脚本，而非对话中。

故障模式： 协调器存在单点故障。如果协调器的上下文填满或漂移，整个系统会降级。解决方法是让协调器的职责范围缩小：仅进行分解和路由，不进行领域推理。

---

#### 3\. 并行扇出带合并

多个代理同时处理独立的子任务。合并步骤收集并协调它们的输出。

```markdown
text[Orchestrator]
   |  |  |  |
 [A][B][C][D]   <- simultaneous
   |  |  |  |
[Merge + Reconcile]
```

适用场景： 子任务之间无依赖。典型使用场景：审计 200 个文件、查询多个数据源、同时进行五次 bug 类调查。

Claude 实现： Claude 的动态工作流默认最多运行 16 个并发代理。设计工作流阶段，确保扇出任务真正独立。结果存储在脚本变量中，而非编排器的上下文。

性能提升： 并行执行可将无步骤依赖的任务的处理时间减少 60-80%。

故障模式： 合并逻辑是难点。如果代理返回不一致的模式或冲突的结果，简单的合并会产生无效数据。在编写扇出之前设计输出契约。

---

#### 4\. 生成器-验证器

一个代理生成输出。第二个代理根据显式标准对其进行评估。结果反馈给生成器。循环运行直到输出通过或达到最大迭代次数。

```markdown
text[Generator] -> [Verifier] -> passes? -> done
     ^              |
     |-- feedback --| fails? -> iterate
```

使用场景： 输出质量至关重要且评估标准可以明确地写下来。测试编写、安全发现、迁移计划。

Claude 实现： 两阶段动态工作流。阶段 1 并行运行生成器代理。阶段 2 对每个生成器输出运行独立验证器代理。只有通过验证的输出才会被合并。这是所有 Claude 动态工作流默认内置的对抗性验证。

故障模式: 如果核实者的标准模糊，就会变成橡皮图章。请在工作流提示中，将核实标准写为明确、可检查的规则。

---

#### 5\. 共享状态

代理通过一个它们都可以直接读写的持久化存储进行协调。没有中央编排器来路由消息；共享存储就是协调机制。

```markdown
text[Agent A] ---|
[Agent B] ---|--> [Shared Store: Markdown / JSON / DB]
[Agent C] ---|
```

使用时机：Agents 逐步基于彼此的发现进行构建。一个 Agent 发现的上下文信息对处理相同问题的其他方来说是立即可用的。

Claude 实现： 实际上，这是一个 git worktree 中的文件系统或结构化文档文件夹。我的生产环境 Claude Code 配置采用这种方式：每一个决策、每一个计划、每一个已完成的事项都以 Markdown 文件的形式存入结构化文档文件夹。下游代理会自动获取这些文件。

故障模式: 上下文污染（模块 5 中介绍）。代理将错误发现写入共享存储。每个下游代理将其视为基准事实。错误在整个系统中传播。

---

#### 6\. 辩论（对抗性多智能体）

两个或多个代理从对立的立场攻击同一问题。裁判代理（或编排者）调和辩论结果。

```markdown
text[Agent: Find Issues] -> claim
[Agent: Refute Issues] -> counter-claim
[Judge: Reconcile] -> verified finding
```

使用时机： 你需要在发现到达你之前，这些发现能够经受住对抗性压力的考验。安全审计、迁移风险评估、任何假阳性或假阴性会带来实际成本的工作。

Claude 实现：Claude 动态工作流原生包含这种模式。“代理从独立角度处理问题。其他代理随后尝试反驳他们发现的内容。运行过程会迭代直到答案收敛”。你无需显式编写辩论逻辑；它作为工作流验证阶段的一部分运行。

---

#### 模块4：通信架构

代理如何传递信息是大多数系统的薄弱环节。设计决策不在于使用哪种消息格式，而在于代理是直接通信还是通过一个中间件进行通信。

---

#### 直接通信 vs. 底层通信

生产系统中的实用规则

> 代理不应直接相互通信。它们应向共享内存层写入数据并从中读取数据。规范知识应集中存储在一个位置。每个代理都应在明确的角色、明确的工具和明确的输出条件下独立运作。

Claude 的动态工作流默认实现基于基底的通信。中间结果存在于脚本变量中，而非任何代理的上下文窗口中。这就是为什么编排脚本是 JavaScript 在架构上很重要的原因：脚本变量是基底。

---

#### 输出契约

生产系统中的每个代理都需要一个明确的输出契约：一个定义它必须返回的确切内容的模式。如果没有它，合并步骤和下游代理将不得不猜测他们收到的内容。

```javascript
/ Example output contract for a security audit agent
{
  "finding_id": "string",
  "file_path": "string",
  "line_number": "number",
  "severity": "critical | high | medium | low",
  "description": "string",
  "confirmed": "boolean",
  "suggested_fix": "string"
}
```

在你的工作流程提示中强制执行此操作

```markdown
Return results in this exact JSON schema. If a field cannot be populated, return null for that field. Do not add fields not in the schema.
```

---

#### 上下文窗口预算

每个智能体都有一个有限的上下文窗口。在多智能体系统中，你需要同时管理一组上下文窗口。重要的设计决策：

- 保持编排器的范围窄小。 编排器应进行分解和路由。领域推理属于专业代理。范围狭窄的编排器不会将未使用的领域知识填充到其上下文中。
- 限制代理接收的内容。 只传递代理完成其特定任务所需的内容。不要向需要三个文件的代理传递完整的文件树。
- 对短期记忆使用热路径限制。 在代理循环中，仅保留活跃上下文中最近的 3-5 次交互。将较旧的上下文丢弃到共享存储中。

#### 模块5：故障模式

这些是五个摧毁生产多智能体系统的失败。每一个都是可预测且可预防的。

---

#### 上下文污染

一个代理向共享存储写入错误输出（幻觉结果、错误模式、损坏状态）。下游代理将其视为事实并基于此进行构建。错误在整个流程中不断累积。

生产中的迹象： 看似合理但无法追溯到实际文件内容的发现。针对同一文件自信地相互矛盾的代理。

预防:

- 在每个写入点进行模式验证。没有代理会将原始文本写入共享存储；所有内容都必须经过类型化模式的处理。
- 验证代理在输出到达共享存储之前检查它们，而不是之后。
- 人工审核关卡在一个阶段的结果为下一阶段奠定基础之前。

---

#### 2\. 级联故障

一个代理失败。编排器未隔离故障，而是将错误结果路由到下游。基于失败输出构建的代理也会失败。缺乏适当编排的多代理系统，其已记录的失败率为41-86.7%。

预防:

- 断路器：如果代理返回错误或空输出，停止该分支，不转发。
- 流程检查点处的置信度评分：低于阈值的输出不通过。
- 来自多个代理的独立发现：单个失败无法破坏整个运行，如果其他代理独立得出相同或不同的结论。

---

#### 3\. 范围蔓延

编排器的分解过于宽泛。代理对其任务的解读过于宽泛。一个被指派负责“审计代码库”的代理开始编辑它本不该触碰的文件。

预防:

- 每个代理在其任务提示中都有明确的、有边界的范围：路径、文件类型、允许的操作。
- 编辑策略：只读，除非明确授予特定路径的写入权限。
- Anthropic 自身的设计指导原则：最小化占用，仅请求必要的权限，优先选择可逆操作。

---

#### 4\. 静默替换

代理无法完成某个步骤（API 调用失败、文件不可读），并在 try/catch 块中悄无声息地插入占位数据。它报告成功。流水线将占位符视为真实结果。

预防: 在 CLAUDE.md 或您的工作流的代理系统提示中：

```markdown
 Error Handling
- NEVER substitute mock or placeholder data for a real result
- If a step fails, report the error and halt this agent's execution
- A fallback is acceptable ONLY if explicitly logged as a fallback with the reason
```

---

#### 5\. 协调死锁

两个代理互相等待。代理 A 无法继续，直到代理 B 完成。代理 B 无法开始，直到代理 A 写入共享存储。工作流停滞。

预防:

- 工作流脚本中的显式依赖图。Claude 的编排脚本在代码中编码依赖关系，而非隐式的对话顺序。
- 每次调用代理时设置超时。如果代理在 X 秒内未返回，编排器将标记其为失败并绕过它。
- 设计阶段在展开之前必须真正独立。依赖映射是模块8的飞行前检查清单。

---

#### 模块 6 :治理层

每个多智能体系统都需要三个结构层才能可靠运行：

治理层是区分演示系统和生产系统的关键。

---

#### 治理层的功能

1. 权限范围: 每个代理都有一个声明的权限集。安全审计代理仅拥有只读访问权限。迁移代理仅对特定路径拥有写访问权限。任何代理的权限都不应超出其任务所需的范围。
2. 人在回路门： 定义哪些操作在执行前需要人工审批。不可逆操作（文件删除、生产环境 API 调用、模式迁移）总是需要经过人在回路门。
3. Audit trails: Every agent decision, every action, every tool call gets logged with the agent ID and the reasoning that led to it. When something breaks, you need to replay exactly what happened. 审计跟踪： 每个代理决策、每个操作、每次工具调用都会被记录，包含代理 ID 以及导致该决策/操作/调用的推理过程。当出现问题时，需要精确重放当时发生的情况。
4. 爆炸半径限制： 定义任何单个代理在行为不当情况下可能造成的最大破坏范围。文件系统写入限定在工作树内，而非仓库根目录。API 调用限制在预发布环境，且无明确的生产环境访问权限。

---

#### 在 Claude 动态工作流中实施治理

治理层转化为三个具体的工件：

```markdown
CLAUDE.md rules (apply to all agents in the session):

t## Agent Permissions
- Read access: entire repository
- Write access: only paths listed in the task prompt
- Shell commands: only commands on the approved list
- Network: no external calls unless the task prompt specifies an endpoint

## Error Handling
- Silent failures are not permitted
- Every error must be reported before halting

## Irreversible Action Policy
- Database writes require explicit approval in the task prompt
- File deletions require explicit approval in the task prompt
- No production API calls without "production: true" in the task prompt
```

#### 模块 7：生产中的五种 Claude 原生模式

这些是 Anthropic 记录的五种模式，这些模式源自 Claude 生产系统中可靠运行的实践。每一种模式都直接对应一个动态工作流结构。

---

#### 模式1：提示链

1. 将一个复杂任务分解为一系列更简单的提示。前一个的输出成为下一个的输入。每一步都足够小，使得代理能够可靠地完成它。
2. 何时使用： 任务具有明确的顺序阶段。文档处理（先提取，再分析，然后总结）、数据转换管道、代码生成后进行测试，然后进行审查。

Claude 工作流形态

```markdown
Phase 1: Parse and extract -> Phase 2: Analyze -> Phase 3: Generate report
```

每个阶段都是一次独立的代理调用。阶段1的输出通过脚本变量成为阶段2的输入。

---

#### 模式2：路由

1. 分类器代理读取输入并将其路由到相应的专科医生。分类器不处理任务，仅负责路由。
2. 何时使用： 任务以异构流的形式到达。编码任务分配给代码代理，安全问题分配给安全代理，文档问题分配给文档代理。

Claude 工作流形态

```markdown
text[Classifier Agent: reads task, returns agent_type]
    |
    -> dynamic dispatch to [Security | Code | Performance | Documentation]
```

在工作流脚本的路由逻辑中实现调度

#### 模式3：并行化

同时向多个代理分发独立的子任务，最后合并结果。

适用场景：子任务之间没有依赖。审计多个文件、搜索多个数据源、同时运行多个分析类别。

Claude 工作流形态

```javascript
/ Workflow script structure
const files = getFilesInScope();
const results = await Promise.all(
  files.map(file => runAgent({ task: 'audit', scope: file }))
);
const merged = mergeAndDeduplicate(results);
```

动态工作流最多可运行16个并发代理。与顺序链式调用相比，令牌使用量减少60-90%，因为中间结果保留在脚本变量中。

---

#### 模式 4：编排器-子代理

1. 编排器接收高级别目标，将其分解为子任务，分配给专门的子代理，并综合它们的输出。
2. 何时使用： 工作需要多个专家领域。需要安全专家、性能专家和覆盖率专家同时进行的代码库审计。

Claude 工作流形态

```markdown
[Orchestrator: decompose goal into subtasks]
    |
    [Security Agent] [Perf Agent] [Coverage Agent]
    |                |             |
    [Orchestrator: synthesize findings]
```

编排器的唯一工作是分解与合成。领域推理属于专家。

---

#### 模式5：评估器-优化器

1. 生成器代理生成输出。评估器代理根据明确的标准对其进行评分。评分和反馈返回给生成器。循环直到输出通过或达到最大迭代次数。
2. 何时使用： 输出质量至关重要，且评估标准可被明确写入规则。安全发现不能是误报。迁移计划必须通过对抗性审查。测试用例必须覆盖指定的边缘情况。

Claude 工作流形态

```markdown
Phase 1: Generator agent produces initial output
Phase 2: Evaluator agent scores against criteria schema
  - Score >= threshold: forward to output
  - Score < threshold: feedback -> Phase 1 with iteration count + 1
Phase 3: Max iterations reached: flag for human review

Set a hard max iteration count (3-5). Without it, the loop can run indefinitely on ambiguous evaluation criteria.
```

#### 实用架构：动态工作流 + 代理团队

对于大多数生产工程任务，该架构结合了两个 Claude 原语：

1. 外层: 动态工作流 Claude 编写编排脚本。该脚本处理分解、扇出、结果收集和阶段排序。中间状态存储在脚本变量中。该工作流可重新运行：将其另存为斜杠命令，整个编排流程就变成了一个团队命令。

3. 对于需要代理间通信的任务：代理团队 当专科医生需要直接互相发送消息（而不仅仅是向协调器汇报）时，请使用 Claude Code 的代理团队。每个团队成员都是一个拥有独立上下文的完整 Claude Code 会话。他们通过邮箱进行沟通。团队负责人进行协调，不进行微观管理。

- 代理级下钻：任务提示，当前状态，目前输出
- 能够暂停、重新启动单个代理或停止整个工作流
- 在会话中从检查点恢复

对于坐席团队，每个团队成员会话均可独立检查。您可以直接与队友互动，无需经过负责人。

#### 模块 10：扩展与成本控制

多智能体系统没有线性成本曲线。成本随智能体数量复合增长。

#### Token 成本架构

多智能体系统中的 Token 使用来自三个来源：

1. 编排规划: 编写工作流脚本或分解任务会预先消耗令牌。这是按任务固定的，而非按代理固定。
2. 代理执行： 每个代理读取其任务，读取其输入文件，调用工具，并生成输出。成本随代理数量增加而增加。
3. 合成： 编排器读取所有代理输出并进行合成。成本随总输出量变化。

动态工作流通过将中间结果保存在脚本变量中而不是将它们全部传递到编排器的上下文中，从而降低了合成成本。

#### 3-7代理规则

保持团队规模小。每个工作流阶段3-7名成员。除此之外，建立层级结构：每组设一名团队负责人，团队负责人向全局编排器汇报。扁平化架构中，若协调层有20名以上成员，会产生二次方的沟通成本和协调死锁风险。

#### 模块 11 : 决策指南：何时构建多智能体

最昂贵的错误是为一项单个优秀智能体（或单个优秀功能）就能处理的任务构建多智能体系统。

#### 构建多智能体时

- 该任务具有真正独立的并行路径（并且您可以列举它们）
- 该任务超出了单个代理的上下文窗口，无法无损总结
- 你需要对抗性验证（经得起反驳的发现比单次验证的发现更有价值）
- 该作业运行数小时到数天，且需要检查点恢复
- 该流程是可重复的（审计、迁移、测试生成），并且编排本身应是一个可复用的工件
- 不同阶段需要真正不同的专业专长或工具集

#### 当保持单代理时

- 该任务是串行的，没有并行性
- 该工作在一个上下文窗口中适配得很舒适
- 协调开销将超过执行时间
- 您仍然在快速构建和修改系统（多智能体架构重构成本高昂）

#### 最大的单一架构错误

将所有代理结果通过编排器的上下文回传。一旦你这样做，你就用额外的网络跳数重建了单代理上下文瓶颈。中间状态属于底层（脚本变量、文件系统、结构化文档），而不是在编排器的对话历史中。

> 编排器的上下文应该包含计划和最终合成。仅此而已。

#### 如何构建多智能体工作流：精炼版

##### 一、内容总结

这篇文章核心讲的是：

> 多智能体系统的关键，不是“多放几个 Agent”，而是**如何编排、隔离上下文、控制权限、验证结果**。

单智能体的问题主要有三个：

1. **上下文爆炸**：任务越长，历史越多，推理越容易被污染。
2. **串行低效**：很多任务本可并行，却被一个 Agent 顺序执行。
3. **恢复困难**：中途失败，往往只能重来。

多智能体的价值在于：

- 把任务拆给不同专家 Agent；
- 并行执行；
- 中间状态放在外部存储，而不是塞进某个 Agent 的上下文；
- 通过验证器、治理层、检查点降低失败风险。

---

##### 二、深入浅出解读

##### 1. 多智能体不是“群聊”

很多人以为多智能体就是：

> Agent A 跟 Agent B 聊，Agent B 再跟 Agent C 聊。

这其实很危险。

因为一个 Agent 的错误、幻觉、偏见，会直接污染另一个 Agent。

更好的方式是：

> Agent 不直接互相传话，而是把结果写到一个“中间层”。

这个中间层可以是：

- 脚本变量；
- JSON 文件；
- Markdown 文档；
- 数据库；
- 文件系统。

这样可以验证、过滤、追踪。

---

##### 2. 编排器只负责“调度”，不要负责“思考”

一个好的多智能体系统通常是这样：

```text
编排器：拆任务、分配任务、合并结果
专家 Agent：做具体专业工作
验证 Agent：检查结果是否可靠
治理层：控制权限、错误处理、人工审批
```

编排器不应该什么都干。

否则它又会变成一个“大号单智能体”，重新遇到上下文爆炸问题。

---

##### 3. 常见的 6 种工作流结构

###### 1）顺序流水线

```text
解析 -> 分析 -> 总结
```

适合步骤强依赖的任务。

例如：

- 文档提取；
- 数据清洗；
- 代码生成后测试再审查。

缺点：慢，一个环节卡住全局卡住。

---

###### 2）协调器 + 工作者

```text
协调器
 ├─ 安全 Agent
 ├─ 性能 Agent
 ├─ 测试 Agent
 └─ 文档 Agent
```

适合多领域任务。

例如代码审计：

- 安全看漏洞；
- 性能看瓶颈；
- 测试看覆盖率；
- 文档看说明是否完整。

---

###### 3）并行扇出 + 合并

```text
文件 A -> Agent
文件 B -> Agent
文件 C -> Agent
最后统一合并
```

适合大量独立任务。

例如：

- 扫描 200 个文件；
- 批量迁移代码；
- 多数据源查询。

关键点：必须提前定义输出格式，否则最后合并会乱。

---

###### 4）生成器 + 验证器

```text
生成结果 -> 验证结果 -> 不合格则重做
```

适合对质量要求高的任务。

例如：

- 安全漏洞确认；
- 测试用例生成；
- 数据迁移方案；
- 代码修复方案。

核心是：验证标准必须明确。

---

###### 5）共享状态

多个 Agent 共同读写一个存储。

```text
Agent A \
Agent B  -> 共享文档 / 数据库 / 文件系统
Agent C /
```

适合逐步积累知识的任务。

风险是：一个错误写进去，后面的 Agent 都会把它当真。

所以必须有验证机制。

---

###### 6）对抗辩论

```text
Agent A：提出问题
Agent B：反驳问题
Judge：判断是否成立
```

适合高风险任务。

例如：

- 安全审计；
- 风险评估；
- 架构决策；
- 迁移方案评审。

好处是能减少“看起来很对，其实是错的”这种结果。

---

##### 4. 最大风险：上下文污染

最危险的情况是：

> 一个 Agent 产生了错误结果，写入共享状态，其他 Agent 全部基于这个错误继续推理。

结果就是：

- 错误被放大；
- 系统越来越自信；
- 最后输出一堆貌似合理但不可追溯的结论。

解决办法：

- 每个 Agent 必须按固定 JSON 输出；
- 结果写入共享存储前必须验证；
- 关键阶段加人工审核；
- 不允许模糊、随意、自由格式输出。

---

##### 5. 生产系统必须有治理层

多智能体系统不能只看“能不能跑”，还要看：

- 谁能读什么？
- 谁能写什么？
- 谁能删文件？
- 谁能调用 API？
- 失败时是停止，还是偷偷用假数据？
- 哪些操作必须人工确认？

治理层的作用就是控制风险。

尤其要禁止：

> 失败后静默填充假数据。

比如：

```text
API 调用失败，但 Agent 编了一个结果继续往下跑。
```

这是生产系统大忌。

---

##### 6. 什么时候该用多智能体？

适合用多智能体的场景：

- 任务可以并行；
- 单 Agent 上下文不够；
- 需要多个专业视角；
- 需要对抗性验证；
- 任务很长，需要检查点恢复；
- 流程会反复使用，比如审计、迁移、测试生成。

不适合用多智能体的场景：

- 任务很简单；
- 任务强串行；
- 一个 Agent 就能搞定；
- 还在快速试错；
- 编排成本大于执行收益。

##### 三、我的意见

我认同文章的核心观点：

> 多智能体的本质是“工程系统”，不是“多开几个聊天窗口”。

真正重要的不是 Agent 数量，而是：

1. **任务拆分是否合理**
2. **上下文是否隔离**
3. **输出格式是否稳定**
4. **结果是否验证**
5. **权限是否受控**
6. **失败是否可恢复**

如果没有这些，多智能体只会更乱、更贵、更难调试。

我的建议是：

###### 小任务：用单 Agent

不要过度设计。

###### 中等任务：用流水线或生成器-验证器

先把质量做稳。

###### 大任务：用编排器 + 专家 Agent + 验证器

并且一定要有：

- 输出契约；
- 共享状态；
- 权限控制；
- 失败处理；
- 人工审核点。

一句话总结：

> 多智能体不是为了“更智能”，而是为了让复杂任务更可控、更并行、更可靠。

## 结构化（1）

### 2026-06-02 03:48:00

#### 《如何构建多智能体工作流》精炼总结

本文核心观点：**多智能体系统的关键不在“智能体有多聪明”，而在“运行时如何协调它们”**。如果上下文、权限、通信和验证设计不好，多智能体不仅不会扩展，反而会因污染、死锁、级联失败而崩溃。

---

##### 1. 多智能体系统的本质：智能体是“单元”，系统是“运行时”

文章首先区分了两个概念：

- **智能体**：一个独立的 LLM 实例，拥有自己的系统提示词、工具、上下文窗口和可能不同的模型。
- **多智能体系统**：协调多个智能体工作的运行时，负责任务路由、交接、权限和治理。

作者强调，多智能体系统的大多数失败不是因为单个智能体不会推理，而是因为：

- 协调机制混乱；
- 上下文传播失控；
- 权限边界不清；
- 中间状态管理不当。

###### 为什么单智能体会失效？

单智能体处理大型任务时有三个硬限制：

1. **上下文饱和**  
   中间结果越积越多，智能体最后是在“历史记录”上推理，而不是在真实问题上推理。

2. **串行瓶颈**  
   例如迁移 200 个文件，本可以并行处理，却被单智能体串行执行数小时。

3. **脆弱恢复**  
   如果中途崩溃或跑偏，整个任务往往要重来，没有阶段性检查点。

多智能体系统的价值在于：  
**把任务分给隔离的智能体，把中间状态放在智能体上下文之外，并设置阶段级恢复点。**

---

##### 2. Claude Code 的三种编排原语

文章介绍了 Claude Code 中三类多智能体协调方式：

| 原语 | 含义 | 状态存放位置 | 是否可复用 | 规模 |
|---|---|---|---|---|
| 子代理 | 主会话生成的独立 Claude 实例，只向编排器汇报 | 主会话上下文 | 否 | 每轮几个 |
| 代理团队 | 多个 Claude Code 会话，由团队负责人协调，可互发消息 | 各自会话上下文 | 否 | 多个并行会话 |
| 动态工作流 | Claude 编写 JavaScript 编排脚本，由独立运行时执行 | 脚本变量 | 是，可保存为斜杠命令 | 最多 1000 个代理 / 16 并发 |

关键判断：

- 小规模临时任务：可用子代理；
- 需要代理之间直接沟通：用代理团队；
- 需要可复用、可扩展、可观测的生产流程：优先用动态工作流。

---

##### 3. 六种常见编排拓扑

###### 3.1 顺序流水线

结构类似：

```text
[Agent A: Parse] -> [Agent B: Analyze] -> [Agent C: Format]
```

适合：

- 任务有严格先后依赖；
- 每一步必须等上一步完成；
- 数据只有一条路径，便于调试。

风险：

- 延迟会逐步放大；
- 如果中间某个代理慢，整个流程都被阻塞；
- 不适合有大量独立并行任务的场景。

---

###### 3.2 协调器-工作节点

结构类似：

```text
[Coordinator]
   /   |   \
[Security] [Perf] [Auth]
   \   |   /
[Coordinator: Synthesize]
```

适合：

- 任务可拆成多个专业领域；
- 路由逻辑稳定，比如安全、性能、覆盖率分别分析。

Claude 动态工作流默认接近这种形态：  
**工作流脚本是协调者，子代理是执行者。**

风险：

- 协调器是单点故障；
- 如果协调器上下文填满或漂移，整个系统会降级。

解决方式：

- 协调器只负责拆解和路由；
- 专业推理交给专家代理。

---

###### 3.3 并行扇出 + 合并

结构类似：

```text
[Orchestrator]
   | | | |
  [A][B][C][D]  同时执行
   | | | |
[Merge + Reconcile]
```

适合：

- 子任务之间没有依赖；
- 如审计 200 个文件、查询多个数据源、同时调查多个 bug。

重要数据：

- 并行执行可让无依赖任务的处理时间减少 **60%-80%**。
- Claude 动态工作流默认最多支持 **16 个并发代理**。

风险：

- 合并逻辑复杂；
- 如果不同代理输出格式不一致，最终合并结果会混乱。

解决方式：

- 在扇出前设计明确的输出契约。

---

###### 3.4 生成器-验证器

结构类似：

```text
[Generator] -> [Verifier] -> 通过则结束
      ^             |
      |---反馈重试---|
```

适合：

- 输出质量很重要；
- 可以明确写出评估标准；
- 如安全发现、测试编写、迁移计划。

关键要求：

- 验证器不能只做“橡皮图章”；
- 验证标准必须明确、可检查。

例如：

- 安全发现必须能对应具体文件、行号和漏洞原因；
- 测试用例必须覆盖指定边界条件。

---

###### 3.5 共享状态

结构类似：

```text
[Agent A] ---|
[Agent B] ---|--> [Shared Store: Markdown / JSON / DB]
[Agent C] ---|
```

适合：

- 多个代理需要基于彼此发现逐步推进；
- 共享存储可以是 Markdown 文件、JSON、数据库或 git worktree 文件系统。

作者自己的生产配置案例：

- 每个决策、计划、已完成事项都写入结构化 Markdown 文档文件夹；
- 下游代理自动读取这些文件。

风险：

- **上下文污染**。  
  如果一个代理把错误发现写入共享存储，后续代理会把它当作事实，错误会扩散到整个系统。

---

###### 3.6 辩论 / 对抗性多智能体

结构类似：

```text
[Agent: Find Issues] -> claim
[Agent: Refute Issues] -> counter-claim
[Judge: Reconcile] -> verified finding
```

适合：

- 安全审计；
- 风险评估；
- 假阳性或假阴性成本很高的场景。

核心思想是：  
**让发现先经受反驳，再交给用户。**

Claude 动态工作流原生包含这种对抗性验证模式。

---

##### 4. 通信架构：不要让代理直接污染彼此上下文

文章认为，代理通信方式是系统最脆弱的部分。

###### 两种通信方式

| 方式 | 工作方式 | 风险 |
|---|---|---|
| 直接通信 | Agent A 直接把输出发给 Agent B 的上下文 | B 会继承 A 的错误、偏差和幻觉 |
| 底层介导通信 | 代理写入共享存储，其他代理读取 | 上下文更可控，错误更容易隔离 |

生产系统中的实用规则：

> 代理不应直接相互通信，而应通过共享内存层读写数据。

在 Claude 动态工作流中，中间结果保存在 **JavaScript 脚本变量** 中，而不是保存在某个代理的上下文窗口里。  
这也是动态工作流用 JavaScript 编排的重要原因：**脚本变量就是通信底层。**

---

##### 5. 输出契约：每个代理都必须按固定格式返回

生产系统中的每个代理都需要明确的输出契约，即规定它必须返回什么字段。

例如安全审计代理的输出可以是：

```json
{
  "finding_id": "string",
  "file_path": "string",
  "line_number": "number",
  "severity": "critical | high | medium | low",
  "description": "string",
  "confirmed": "boolean",
  "suggested_fix": "string"
}
```

提示词中应明确要求：

```markdown
Return results in this exact JSON schema.
If a field cannot be populated, return null.
Do not add fields not in the schema.
```

这样可以避免：

- 合并阶段猜测字段含义；
- 下游代理误读输出；
- 不同代理返回格式不一致。

---

##### 6. 上下文窗口预算：编排器越窄越好

多智能体系统中，不只是一个上下文窗口，而是一组上下文窗口。

关键设计原则：

1. **编排器职责要窄**  
   只做分解、路由和最终综合，不做领域推理。

2. **只给代理必要信息**  
   例如只需要 3 个文件的代理，不应传整个文件树。

3. **短期记忆只保留热路径**  
   活跃上下文中只保留最近 **3-5 次交互**，旧上下文放入共享存储。

---

##### 7. 五大生产故障模式

###### 7.1 上下文污染

一个代理写入错误输出，下游代理把它当事实继续构建。

生产迹象：

- 发现看似合理，但无法追溯到实际文件；
- 多个代理对同一文件给出自信但矛盾的结论。

预防：

- 写入共享存储前做 schema 验证；
- 输出进入共享存储前由验证代理检查；
- 关键阶段设置人工审核门。

---

###### 7.2 级联故障

一个代理失败，编排器却继续把错误结果传给下游，导致后续代理一起失败。

重要数据：

- 缺乏适当编排的多智能体系统，记录失败率可达 **41%-86.7%**。

预防：

- 设置断路器：错误或空输出不继续传递；
- 在检查点做置信度评分；
- 用多个代理独立验证，避免单点失败毁掉全局。

---

###### 7.3 范围蔓延

代理任务边界不清，开始做不该做的事。  
比如被要求“审计代码库”的代理，开始编辑不该碰的文件。

预防：

- 明确路径、文件类型、允许操作；
- 默认只读，除非明确授予写权限；
- 最小权限原则，优先可逆操作。

---

###### 7.4 静默替换

代理遇到失败后，用占位数据代替真实结果，并报告成功。

比如：

- API 调用失败；
- 文件不可读；
- 代理却返回 mock 数据。

预防规则：

```markdown
- NEVER substitute mock or placeholder data for a real result
- If a step fails, report the error and halt
- Fallback is acceptable only if explicitly logged
```

---

###### 7.5 协调死锁

两个代理互相等待，导致工作流停滞。

例如：

- A 等 B 完成；
- B 又等 A 写入共享存储。

预防：

- 在工作流脚本中写清楚依赖图；
- 每次代理调用设置超时；
- 扇出前确认任务真的独立。

---

##### 8. 治理层：生产系统和演示系统的分水岭

文章认为可靠的多智能体系统需要三层：

| 层 | 作用 | 缺失后果 |
|---|---|---|
| 编排器 | 分解任务、分配专家、综合结果 | 重复工作、任务冲突 |
| 专业代理 | 执行限定范围任务 | 无法并行，单上下文瓶颈 |
| 治理层 | 控制访问权限、执行条件和审计记录 | 权限失控、输出未验证 |

治理层包含三类能力：

1. **权限范围**  
   安全审计代理只读；迁移代理只对特定路径可写。

2. **人在回路门控**  
   删除文件、数据库写入、生产 API 调用等不可逆操作必须人工批准。

3. **爆炸半径限制**  
   限制单个代理出错时能造成的最大破坏范围。

---

##### 9. Claude 原生五种生产模式

###### 9.1 提示链

适合明确顺序任务：

```text
提取 -> 分析 -> 总结
```

常见于：

- 文档处理；
- 数据转换；
- 代码生成后测试和审查。

---

###### 9.2 路由

由分类器代理判断任务类型，然后分配给专家。

例如：

```text
编码任务 -> 代码代理
安全问题 -> 安全代理
文档问题 -> 文档代理
```

分类器只负责路由，不负责处理任务。

---

###### 9.3 并行化

多个独立子任务同时执行，最后合并。

示例：

```javascript
const results = await Promise.all(
  files.map(file => runAgent({ task: 'audit', scope: file }))
);
const merged = mergeAndDeduplicate(results);
```

重要数据：

- 动态工作流最多 **16 个并发代理**；
- 相比顺序链式调用，Token 使用量可减少 **60%-90%**，因为中间结果留在脚本变量中。

---

###### 9.4 编排器-子代理

编排器负责拆解和综合，专家代理负责领域推理。

适合：

- 代码库审计；
- 同时需要安全、性能、测试覆盖等专家的任务。

---

###### 9.5 评估器-优化器

生成器先产出，评估器按标准打分，不合格则反馈重试。

关键要求：

- 设置最大迭代次数，通常 **3-5 次**；
- 否则在模糊标准下可能无限循环。

---

##### 10. 从零设计多智能体系统的流程

文章给出了一套可重复的设计方法。

###### 步骤 1：任务分解

先用一句话写出顶层任务，再拆出所有操作，并判断：

- 是否依赖其他操作输出；
- 是否可以并行执行。

最后得到一个带依赖箭头的阶段图。

---

###### 步骤 2：识别专家代理

每个操作都要定义：

- 代理角色；
- 工具访问权限；
- 输出 JSON schema；
- 失败行为。

避免设计“什么都做”的通用代码代理。  
这本质上只是一个上下文臃肿的单代理。

---

###### 步骤 3：设计传播方式

大多数系统应采用底层介导通信：

- 动态工作流用脚本变量；
- 代理团队用共享文件系统。

如果多个代理写入同一个位置，下游再读取，就必须在读取前增加验证步骤。

---

###### 步骤 4：治理合同

在写工作流提示前，先写 `CLAUDE.md` 规则，包括：

- 权限；
- 错误处理；
- 人工审批；
- 不可逆操作策略。

---

###### 步骤 5：飞行前检查清单

运行前应确认：

- 在 git worktree 或特性分支工作，不直接动主分支；
- 每个代理权限范围明确；
- 每个写共享存储的代理都有输出契约；
- 关键路径上的生成器都有验证器；
- 不可逆操作有人工审批；
- 所有循环设置最大迭代次数；
- 失败必须显式报告，不能静默替换；
- 运行前检查 token 预算。

---

##### 11. 推荐架构：动态工作流 + 专家子代理

作者推荐多数生产工程任务采用：

###### 外层：动态工作流

负责：

- 任务拆解；
- 并行扇出；
- 结果收集；
- 阶段排序；
- 中间状态保存到脚本变量；
- 可保存为可复用的斜杠命令。

###### 内层：专家子代理

每个子代理都有：

- 限定范围的系统提示；
- 指定文件路径；
- 明确输出模式；
- 失败策略。

如果任务需要代理之间直接互发消息，则使用 Claude Code 的代理团队。

---

##### 12. 可观测性：用 `/workflows` 监控运行状态

Claude Code 的 `/workflows` 命令可以查看：

- 每个阶段状态：运行中、完成、失败；
- 每个代理的任务提示、当前状态和输出；
- 暂停、重启单个代理或停止整个工作流；
- 从检查点恢复。

对于代理团队，每个成员会话也可以独立检查，并可直接互动。

---

##### 13. 扩展与成本控制

多智能体成本不是线性增长，而是会复合增长。

Token 成本主要来自：

1. **编排规划**  
   写工作流脚本或任务分解的前置成本。

2. **代理执行**  
   每个代理读取任务、输入文件、调用工具并生成输出。

3. **结果合成**  
   编排器读取所有代理输出并综合。

动态工作流通过把中间结果保存在脚本变量中，降低了合成成本。

###### 3-7 代理规则

文章建议：

- 每个工作流阶段保持 **3-7 个成员**；
- 超过后应建立层级结构；
- 扁平架构中，如果协调层超过 **20 个成员**，会产生二次方沟通成本和死锁风险。

---

##### 14. 什么时候该用多智能体，什么时候不该用？

###### 适合构建多智能体的情况

- 任务有真正独立的并行路径；
- 单个代理上下文窗口装不下；
- 需要对抗性验证；
- 作业运行数小时到数天，需要检查点恢复；
- 流程可重复，如审计、迁移、测试生成；
- 不同阶段需要真正不同的专业能力或工具。

###### 应保持单代理的情况

- 任务是串行的，没有并行性；
- 一个上下文窗口就能舒服完成；
- 协调开销大于执行收益；
- 系统仍在快速试错，多智能体重构成本太高。

---

##### 15. 最大的架构错误

文章最后强调，最大的错误是：

> 把所有代理结果都通过编排器上下文回传。

这样等于重新制造了单代理上下文瓶颈，只是多了网络跳数。

正确做法是：

- 中间状态放在底层：脚本变量、文件系统、结构化文档；
- 编排器上下文只保留计划和最终综合；
- 专业推理交给专家代理。

---

##### 总结

构建多智能体工作流的核心不是“多放几个 Agent”，而是设计一套可靠的运行时系统。真正重要的是：**清晰的拓扑、底层介导通信、严格输出契约、有限上下文、权限治理、验证机制和可观测性**。只有这些基础设施到位，多智能体系统才会从 demo 走向生产。

#### 如何构建多智能体工作流：精炼版

##### 1. 启发

###### 1.1 多智能体的核心不是“更多 Agent”，而是“运行时设计”

文章最重要的观点是：

> Agent 是执行单元，多智能体系统是协调运行时。

很多人以为多智能体就是让多个 AI 同时干活，但真正决定系统可靠性的不是单个 Agent 有多聪明，而是：

- 谁来分解任务？
- 谁来分配任务？
- 中间状态放在哪里？
- Agent 之间如何通信？
- 谁来验证结果？
- 失败后如何恢复？
- 权限如何限制？

这意味着，多智能体系统更像是一个 **分布式软件系统**，而不是一个简单的 Prompt 技巧。

---

###### 1.2 单 Agent 的瓶颈，本质是上下文、串行和恢复能力

单 Agent 适合短任务，但面对复杂工程任务会遇到三类硬限制：

| 问题 | 表现 | 多智能体解决方式 |
|---|---|---|
| 上下文饱和 | 历史信息塞满窗口，推理质量下降 | 拆分上下文，每个 Agent 只看必要信息 |
| 串行瓶颈 | 可并行任务被一个 Agent 顺序执行 | 并行扇出，多个 Agent 同时处理 |
| 脆弱恢复 | 中途失败要重来 | 阶段化、检查点、局部重试 |

因此，多智能体不是为了“更智能”，而是为了获得：

- 并行性
- 隔离性
- 专业化
- 可恢复性
- 可验证性

---

###### 1.3 编排器不应该是“超级大脑”，而应该是“调度器”

文章反复强调：

> 编排器只负责分解、路由和合成，不负责领域推理。

这是一个非常关键的产品/系统设计原则。

错误做法：

```text
Orchestrator = 规划 + 分析 + 推理 + 汇总 + 决策 + 记忆所有中间结果
```

正确做法：

```text
Orchestrator = 拆任务 + 分配任务 + 收集结构化结果 + 做最终合成
```

领域推理应该交给专业 Agent：

- 安全 Agent
- 性能 Agent
- 测试 Agent
- 文档 Agent
- 数据分析 Agent
- 代码迁移 Agent

编排器一旦吸收太多细节，就会重新变成单 Agent 瓶颈。

---

##### 2. 高价值信息深挖

##### 2.1 多智能体最大的架构问题：上下文污染

多智能体不是天然更可靠，反而更容易出现“污染传播”。

典型路径：

```text
Agent A 产生错误发现
  ↓
写入共享存储
  ↓
Agent B/C/D 当作事实继续推理
  ↓
错误被放大
  ↓
最终报告看起来非常完整，但基础事实是错的
```

这比单 Agent 幻觉更危险，因为多 Agent 会制造一种“群体验证过”的错觉。

###### 应对原则

所有写入共享状态的信息，必须经过：

1. **Schema 约束**
2. **验证器检查**
3. **来源可追溯**
4. **必要时人工审核**

不要让 Agent 随意写自然语言结论进入共享知识库。

更好的方式是结构化输出：

```json
{
  "finding_id": "string",
  "file_path": "string",
  "line_number": "number",
  "severity": "critical | high | medium | low",
  "description": "string",
  "evidence": "string",
  "confirmed": "boolean",
  "suggested_fix": "string"
}
```

关键不是“让 Agent 写得更清楚”，而是让系统只能接受符合契约的结果。

---

##### 2.2 Agent 之间不要直接聊天，应该通过“底层介质”通信

文章提出了一个非常实用的原则：

> Agent 不应直接把结果塞进另一个 Agent 的上下文，而应通过共享存储、脚本变量、数据库、文件系统等中间层通信。

###### 直接通信的问题

```text
Agent A → Agent B
```

风险：

- Agent B 继承 Agent A 的偏见
- Agent B 继承 Agent A 的幻觉
- 上下文越来越脏
- 难以调试
- 难以回放
- 难以验证

###### 底层介质通信

```text
Agent A → Structured Store → Agent B
```

优势：

- 可验证
- 可审计
- 可重放
- 可局部重试
- 可隔离错误
- 不污染上下文

对于产品和工程系统，这个原则可以迁移为：

> 不要让 AI 之间自由对话，要让它们围绕结构化状态协作。

---

##### 2.3 输出契约是多智能体系统的“API”

每个 Agent 都应该像一个微服务一样，有明确接口。

包括：

- 输入是什么？
- 输出是什么？
- 输出字段有哪些？
- 哪些字段必填？
- 失败时返回什么？
- 是否允许不确定？
- 是否允许修改文件？
- 是否需要引用证据？

如果没有输出契约，合并阶段就会变成灾难：

```text
Agent A 返回 Markdown
Agent B 返回 JSON
Agent C 返回散文
Agent D 返回带猜测的结论
Merge Agent 被迫猜测
```

最后结果会变得不可控。

###### 高价值原则

> Prompt 是接口文档，Schema 是执行约束。

对于重要任务，应该始终要求：

```text
Return results in this exact JSON schema.
If a field cannot be populated, return null.
Do not add fields not in the schema.
Do not infer missing evidence.
```

---

##### 2.4 多智能体的六种典型拓扑

###### 1. 顺序流水线

适合强依赖任务。

```text
Parse → Analyze → Format
```

适合：

- 文档处理
- 数据转换
- 报告生成
- 代码生成后测试再审查

不适合：

- 大量独立任务
- 文件批量扫描
- 多方向调查

风险：

- 延迟累积
- 中间一步失败，全链路暂停

---

###### 2. 协调器-工作节点

一个协调者拆任务，多个专家执行。

```text
Coordinator
 ├─ Security Agent
 ├─ Performance Agent
 ├─ Test Agent
 └─ Documentation Agent
```

适合：

- 多领域代码审计
- 产品需求评审
- 商业分析
- 系统设计审查

风险：

- 协调器成为单点故障
- 协调器上下文膨胀

解决方式：

- 协调器只做调度
- 专家只看必要上下文
- 专家输出结构化结果

---

###### 3. 并行扇出 + 合并

多个 Agent 同时处理独立任务。

```text
File A → Agent A
File B → Agent B
File C → Agent C
File D → Agent D
        ↓
      Merge
```

适合：

- 扫描 200 个文件
- 多渠道信息收集
- 多 Bug 线索调查
- 批量测试生成
- 数据源并行查询

价值：

- 大幅缩短执行时间
- 降低单 Agent 上下文压力

风险：

- 合并复杂
- 输出不一致
- 重复结果多
- 冲突结果难处理

前提：

> 先设计合并规则，再设计并行任务。

---

###### 4. 生成器-验证器

一个 Agent 生成，一个 Agent 审查。

```text
Generator → Verifier → Pass?
     ↑          ↓
     └ Feedback ┘
```

适合：

- 安全审计
- 测试生成
- 迁移计划
- 产品方案评审
- Prompt 优化
- SQL/代码生成

关键：

验证器必须有明确标准。

错误标准：

```text
请检查这个方案是否合理。
```

正确标准：

```text
请根据以下规则逐项检查：
1. 是否覆盖所有边界条件？
2. 是否引用真实文件路径？
3. 是否存在不可逆操作？
4. 是否包含回滚方案？
5. 是否有未经验证的假设？
```

---

###### 5. 共享状态

Agent 通过共享文档、数据库、JSON、Markdown 等协作。

```text
Agent A ─┐
Agent B ─┼→ Shared Store
Agent C ─┘
```

适合：

- 长周期项目
- 研究型任务
- 产品知识库建设
- 代码库迁移
- 决策记录系统

风险：

- 错误知识进入共享层后被广泛传播
- 多个 Agent 写入冲突
- 知识版本混乱

治理方式：

- 写入必须结构化
- 重要事实必须带来源
- 关键状态需验证
- 共享知识区分草稿/确认/废弃

---

###### 6. 辩论式多智能体

多个 Agent 从不同立场审查同一问题。

```text
Proposer → Claim
Critic → Counter-claim
Judge → Reconcile
```

适合：

- 风险评估
- 商业决策
- 安全审计
- 投资分析
- 产品战略
- 架构选型

核心价值：

> 用对抗性压力提高结论可信度。

尤其适合“错误代价高”的场景。

---

##### 3. 可迁移清单

##### 3.1 判断是否需要多智能体

适合多智能体的任务：

- 有清晰的并行子任务
- 单 Agent 上下文不够用
- 任务运行时间长，需要检查点
- 需要多个专业视角
- 需要对抗性验证
- 任务会重复执行，值得沉淀成工作流
- 输出质量要求高，不能只靠一次生成

不适合多智能体的任务：

- 任务很短
- 完全串行
- 一个上下文窗口能解决
- 协调成本大于执行收益
- 需求还在频繁变化
- 只是为了“看起来高级”

##### 3.2 多智能体设计前清单

在写 Prompt 之前，先回答这些问题：

###### 任务分解

- 顶层目标是什么？
- 需要哪些子任务？
- 哪些任务必须顺序执行？
- 哪些任务可以并行执行？
- 哪些任务需要人工确认？

###### Agent 定义

每个 Agent 都要定义：

- 角色
- 输入
- 输出
- 工具权限
- 可访问范围
- 失败行为
- 是否可写入文件
- 是否需要验证器

###### 通信设计

- Agent 是否直接通信？
- 是否通过共享存储？
- 中间状态存在哪里？
- 谁能读？
- 谁能写？
- 谁来验证写入内容？

###### 输出契约

每个 Agent 必须有：

- JSON Schema
- 必填字段
- 失败字段
- 证据字段
- 置信度字段
- 不确定时的返回方式

###### 治理规则

必须明确：

- 哪些操作只读？
- 哪些路径可写？
- 哪些命令可执行？
- 哪些操作需要人工审批？
- 失败后是否允许 fallback？
- 是否允许使用 mock 数据？
- 是否允许访问外部网络？

##### 4. 反方与张力

##### 4.1 多智能体不是默认更好

多智能体系统有明显成本：

- 架构复杂
- 调试困难
- token 成本更高
- 合并逻辑复杂
- 失败路径更多
- 权限管理更难
- 结果不一致更常见

所以反方观点是：

> 很多所谓多智能体系统，其实只是把一个本来简单的问题复杂化了。

如果任务本身没有明显并行性、专业分工或验证需求，单 Agent + 好工具 + 好上下文管理可能更优。

---

##### 4.2 多智能体提升的是吞吐，不一定提升判断质量

并行扫描 200 个文件，多智能体很有价值。

但对于一个高度抽象的战略判断，比如：

```text
我们是否应该进入某个市场？
```

简单增加 Agent 数量不一定提升质量。

如果所有 Agent 使用类似模型、类似资料、类似假设，那么所谓“辩论”可能只是同质化观点的重复。

要提升质量，需要引入：

- 不同角色
- 不同信息源
- 不同评估标准
- 不同利益立场
- 不同失败假设

否则只是“多份相似答案”。

---

##### 4.3 共享状态既是优势，也是污染源

共享状态可以解决上下文不足，但也可能成为“错误放大器”。

张力在于：

| 目标 | 风险 |
|---|---|
| 让 Agent 共享发现 | 错误发现被当作事实 |
| 让 Agent 复用上下文 | 上下文污染 |
| 让系统有记忆 | 过期信息影响判断 |
| 让任务可持续推进 | 错误持续积累 |

因此共享状态要分层：

```text
Raw Findings       原始发现
Validated Facts    已验证事实
Decisions          决策记录
Rejected Claims    被否定假设
Open Questions     待确认问题
```

不要把所有内容都放进一个“共享知识库”。

---

##### 4.4 验证器也会失效

生成器-验证器模式看起来可靠，但前提是验证器标准明确。

验证器失效的情况：

- 标准太模糊
- 验证器和生成器使用同样错误假设
- 验证器没有访问原始证据
- 验证器只检查格式，不检查事实
- 验证器为了完成任务而橡皮图章式通过

所以验证器不能只是：

```text
请检查是否正确。
```

而应该是：

```text
请根据原始文件、明确规则、失败条件逐项验证。
```

---

##### 4.5 自动化和人工审核之间的张力

多智能体系统越自动化，越需要治理。

特别是以下操作不应完全交给 Agent：

- 删除文件
- 修改数据库
- 调用生产 API
- 改动权限系统
- 执行财务操作
- 发送真实用户通知
- 大规模代码迁移合并

高价值原则：

> AI 可以准备动作，但不可逆动作需要人类授权。

---

##### 5. 情境化落地

##### 5.1 场景一：代码库安全审计

###### 推荐拓扑

```text
Orchestrator
 ├─ Auth Security Agent
 ├─ Input Validation Agent
 ├─ Dependency Risk Agent
 ├─ Secret Scan Agent
 └─ Permission Review Agent
        ↓
Verifier Agents
        ↓
Final Risk Report
```

###### 工作流

1. 编排器确定审计范围
2. 按领域并行分配任务
3. 每个 Agent 输出结构化风险项
4. 验证器检查证据是否真实
5. 合并去重
6. 按严重程度生成报告
7. 高危项进入人工审核

###### 关键规则

- 所有 Agent 只读
- 每个发现必须包含文件路径和证据
- 无证据不得标记 confirmed
- 高危发现必须由第二个 Agent 验证

---

##### 5.2 场景二：产品需求评审

###### 推荐拓扑

辩论式 + 协调器-专家模式。

```text
PM Agent：需求完整性
UX Agent：用户体验
Tech Agent：技术可行性
Data Agent：指标和实验
Risk Agent：风险与边界情况
     ↓
Judge Agent：合成 PRD Review
```

###### 每个 Agent 的关注点

| Agent | 关注内容 |
|---|---|
| PM Agent | 目标、用户、场景、优先级 |
| UX Agent | 路径、摩擦、认知负担 |
| Tech Agent | 实现复杂度、依赖、风险 |
| Data Agent | 指标、埋点、实验设计 |
| Risk Agent | 滥用、合规、边界情况 |

###### 输出结构

```json
{
  "issue": "string",
  "category": "product | ux | tech | data | risk",
  "severity": "high | medium | low",
  "evidence": "string",
  "recommendation": "string",
  "open_question": "string | null"
}
```

###### 价值

这比让一个 Agent 直接“评审 PRD”更稳定，因为它强制引入多视角。

---

##### 5.3 场景三：商业系统诊断

例如诊断一个 SaaS 产品增长停滞。

###### 推荐拓扑

```text
Coordinator
 ├─ Acquisition Agent
 ├─ Activation Agent
 ├─ Retention Agent
 ├─ Revenue Agent
 ├─ Pricing Agent
 └─ Customer Feedback Agent
        ↓
Debate / Challenge
        ↓
Synthesis
```

###### 每个 Agent 只看对应材料

- Acquisition：渠道数据、广告投放、SEO
- Activation：注册到 aha moment 的路径
- Retention：留存、使用频率、功能使用
- Revenue：付费转化、ARPU、MRR
- Pricing：套餐、付费墙、竞品
- Feedback：客服、访谈、NPS、工单

###### 最终输出

```text
1. 最大瓶颈在哪里？
2. 证据是什么？
3. 反证是什么？
4. 哪些假设未验证？
5. 未来两周应该做哪些实验？
6. 哪些事情不应该做？
```

这可以把“泛泛而谈的商业建议”转化为可验证的诊断系统。

---

##### 5.4 场景四：大规模代码迁移

例如从 REST API 迁移到 GraphQL，或从旧框架迁移到新框架。

###### 推荐拓扑

顺序流水线 + 并行扇出 + 验证器。

```text
Phase 1: Inventory
Phase 2: Migration Plan
Phase 3: Parallel File Migration
Phase 4: Test Generation
Phase 5: Verification
Phase 6: Human Review
```

###### 关键设计

- Inventory Agent：扫描受影响文件
- Planner Agent：生成迁移计划
- Migration Agents：按模块并行修改
- Test Agent：生成测试
- Verifier Agent：检查行为一致性
- Human Gate：合并前审批

###### 必须有的治理

- 写权限限制在特定路径
- 每个修改必须可 diff
- 不允许删除文件，除非明确授权
- 测试失败不得继续合并
- 每个阶段都可回滚

---

##### 5.5 场景五：内容生产系统

例如批量生成高质量行业报告。

###### 推荐拓扑

```text
Research Agents
 ├─ Market Research
 ├─ Competitor Research
 ├─ User Pain Research
 └─ Trend Research
        ↓
Fact Verifier
        ↓
Writer Agent
        ↓
Editor Agent
        ↓
Critic Agent
        ↓
Final Publisher
```

###### 重点

内容系统最容易出现幻觉，因此必须：

- 原始资料和观点分离
- 事实和推测分离
- 引用来源
- 验证关键数据
- 批判性审稿
- 人工终审

不要让写作 Agent 自己研究、自己判断、自己写、自己审。

---

##### 6. 最核心的架构原则

可以把全文压缩成 10 条原则：

1. **先判断是否真的需要多智能体。**
2. **多智能体系统的核心是编排，不是 Agent 数量。**
3. **编排器只做分解、路由、合成，不做深度领域推理。**
4. **Agent 之间尽量不要直接通信，而是通过结构化共享状态通信。**
5. **每个 Agent 都必须有明确输出契约。**
6. **共享状态必须验证后写入，否则会造成上下文污染。**
7. **关键输出必须经过验证器或对抗性审查。**
8. **权限最小化，默认只读，写操作需明确授权。**
9. **不可逆操作必须有人类审批。**
10. **中间状态不要塞回编排器上下文，而应放在脚本变量、文件系统或数据库中。**

---

##### 7. 对 AI/产品开发者的最大启发

如果你在构建 AI 产品，不要把多智能体理解成一个炫技功能，而要理解成一种 **AI 工作流操作系统**。

真正有价值的不是：

```text
我有 10 个 Agent。
```

而是：

```text
我有一套可重复、可审计、可验证、可恢复、权限受控的智能工作流。
```

未来优秀的 AI 产品，很可能不是单个超级聊天框，而是围绕具体业务流程设计的多智能体运行时：

- 有任务图
- 有角色分工
- 有状态管理
- 有权限治理
- 有验证机制
- 有人工关卡
- 有成本控制
- 有失败恢复

这才是多智能体系统真正值得关注的地方。

### 2026-09-18 01:02:55

#### 多智能体的关键不是增加“员工”，而是建立可治理的运行时

这篇文章最值得保留的判断，是把**智能体**与**多智能体运行时**分开：前者负责推理和执行，后者负责拆解任务、传递状态、控制权限、隔离失败与恢复进度。许多所谓“模型不够聪明”的问题，其实是系统把任务分错了、让错误状态继续传播，或把所有结果重新塞回协调器，最终重建了单智能体的上下文瓶颈。

##### 先画依赖图，再决定需要几个智能体

多智能体并不天然优于单智能体。它只在三类约束明显时成立：任务存在真正独立的并行路径；工作量超过单个上下文窗口；结果需要独立验证或长时间运行后的检查点恢复。

因此，正确的起点不是挑框架或创建角色，而是把任务画成依赖图：哪些步骤必须串行，哪些可以并行，哪里需要合并，哪些结果一旦错误会污染后续阶段。拓扑只是依赖关系的实现——严格依赖用流水线，独立任务用扇出，异构输入用路由，高风险输出用生成器—验证器。

这也解释了一个常见误区：为了“专家协作”设置十几个角色，却让它们顺序阅读同一批材料。系统增加了通信成本和误差来源，并没有获得并行性或信息增量。

##### 可靠性来自确定性的外壳，而非更多模型投票

文章提出让中间状态进入脚本变量、文件或数据库，而不是代理之间直接转述，这是重要方向。更准确地说，**共享存储不会自动消除错误，它提供的是可检查、可隔离和可重放的边界**。

输出契约能验证字段、类型和完整性，却无法证明内容真实。一个格式完美的错误结论，仍会污染所有下游代理。因此关键结果还需要来源定位、证据引用、独立复核与写入前验证。验证器也不能被视为天然独立：如果生成器与验证器使用相同模型、相同材料和相似提示，它们可能共享盲点；“辩论”增加的是压力测试，不是真实性保证。

更可迁移的设计原则是：**用确定性程序管理概率性节点**。代码负责依赖、超时、重试、断路器、权限和状态转换；模型只承担难以规则化的判断。协调器应尽量窄，只保留计划和最终合成，而不参与每个领域的详细推理。

##### 真正的产品机会在治理与可观测性

如果把多智能体看成工作流基础设施，核心需求就不再是“创建更多 Agent”，而是任务图、结构化状态、证据追踪、权限控制、人工审批和失败恢复。尤其要防止“静默替换”：调用失败后填入占位数据并报告成功，往往比显式失败更危险。

文章给出的具体性能提升、失败率和规模数字缺少实验条件，且作者自述仅使用多智能体两天，不宜当作生产证据。但它提供了一套有用的评审框架：**只有当并行收益、上下文隔离或验证价值足以覆盖协调成本时，才应升级为多智能体系统。** 否则，一个工具完善、边界清楚的单智能体，通常更便宜，也更可靠。
