**Sebastian Raschka**

### Claude Code 的真正核心秘诀（可能）不是模型

原来 Claude Code 的源代码今天被泄露了。我在 GitHub 上看到了几个 TypeScript 代码库的快照。出于法律原因，我不想在此处提供链接，但这里有一些有趣的学习要点可以从中学习到。

当然，这可能是常识，即 Claude Code 在编码方面比 Claude 网页聊天表现更佳，因为它不仅仅是在聊天界面上添加了一个 Shell，而是一个经过精心设计的工具，具备一些出色的提示词和上下文优化功能。

我还应该说明，虽然很多优质的编码性能来自模型本身，但我认为 Claude Code 表现如此出色的原因是这个软件框架。这意味着，如果我们引入其他模型（例如 DeepSeek、MiniMax 或 Kimi）并针对这些模型对其进行适当优化，我们也会获得非常出色的编码性能。

不管怎样，下面是一些有趣的小知识，为了教育目的，以便更好地理解代码代理是如何工作的。

### Claude Code 构建一个实时仓库上下文

这可能是最明显的一点，但当你开始进行提示时，Claude 会加载主 Git 分支、当前 Git 分支、最近的提交等内容，以及 CLAUDE.md 文件作为上下文。

### 2\. 积极的提示缓存重用

似乎存在一种类似边界标记的机制，用于分隔静态内容和动态内容。这意味着，为了确保稳定性，静态部分会被全局缓存，从而使得耗时的部分不需要每次都重新构建和重新处理。

### 3\. 工具比“上传文件聊天”更好

该提示似乎要求模型使用专用的 Grep 工具，而不是通过 Bash 调用 grep 或 rg，推测是因为专用工具具有更好的权限处理能力和（或许）更好的结果收集能力。

还有一个专门用于文件发现的 Glob 工具。最后，它还提供了一个 LSP（语言服务器协议）工具，用于调用层次结构、查找引用等。与聊天界面相比，这应该是一个很大的“提升”，（我认为）后者更多地将代码视为静态文本。

### 4\. 最小化上下文膨胀

最大的问题之一当然是处理代码仓库时上下文大小有限。当与代理进行来回交互、重复读取文件、处理日志文件、较长的 Shell 输出等情况时，这一问题尤为明显。

Claude Code 中有大量底层架构设计来减少这种冗余。例如，他们确实实现了文件读取去重功能，该功能会检查文件是否未被修改，如果未被修改，则不再重新处理这些文件。

此外，如果工具结果确实变得过大，它们会被写入磁盘，而上下文仅使用预览加上文件引用。

并且，当然，类似任何现代的 LLM UI，它会自动截断长上下文，并在需要时执行自动压缩（/总结）。

### 5\. 结构化会话内存

Claude Code 为当前对话维护一个结构化的 Markdown 文件，包含类似以下的章节：

- 会话标题
- 当前状态
- 任务规范
- 文件和功能
- 工作流
- 错误与修正
- 代码库和系统文档
- 学习收获
- 关键成果
- 工作日志

我觉得这有点像我们人类编写代码的方式，在这个过程中我们会记录笔记和总结。

### 6\. 它使用分叉和子代理

Claude Code 并行化工作时使用子代理，这可能并不令人惊讶。这基本上是它长期以来相比 Codex 的卖点之一（直到 Codex 最近也添加了子代理支持）。

在这里，分叉代理在保持感知或可变状态的同时复用父代理的缓存。因此，这使得系统能够执行摘要生成、记忆提取或背景分析等辅助工作，而不会污染主代理循环。

### 为什么这可能感觉和使用效果都比在 Web UI 中编码更好

总的来说，Claude Code 比普通网页界面表现更好的原因，并非是提示工程或更优的模型。而是上述这些在性能和上下文处理方面的细微改进。当然，还有一个便利之处，就是可以将所有内容在电脑上整理得井井有条，而不是向聊天界面上传文件。

## 结构化（1）

### 2026-04-01 06:37:12

#### Claude Code 更强，作者认为关键可能不只是模型，而是整套 “代码代理框架”

作者基于泄露出的代码快照，提出一个核心判断：Claude Code 在编程上的优势，很大一部分可能来自工程设计、上下文管理和工具链，而不只是底层模型本身。换句话说，如果把类似框架优化到其他模型上，也可能获得很强的编码效果。

##### 1. 作者的基本观点：强的不只是模型，更是 “系统设计”

- 作者看到 Claude Code 的一些 TypeScript 代码快照后，认为它并不是 “聊天界面 + Shell” 这么简单。
- 它更像是一个专门为代码任务设计的代理系统，重点在于：
  - 更好的提示词设计
  - 更强的上下文组织
  - 更高效的工具调用
- 作者明确承认：模型能力当然重要，但 Claude Code 之所以表现突出，**软件框架本身可能是关键原因**。
- 作者进一步推测：如果把这套机制适配到其他模型，比如**DeepSeek、MiniMax、Kimi**，也可能得到很强的编码表现。

##### 2. 它会自动构建 “实时仓库上下文”

- Claude Code 在开始工作时，不只是读用户当前一句话，而是会主动加载和当前代码仓库相关的重要信息。
- 这些上下文包括：
  - 主 Git 分支
  - 当前 Git 分支
  - 最近的提交记录
  - `CLAUDE.md`文件
- 这意味着它在 “开工前” 就已经对项目状态有基础了解，不像普通聊天界面那样主要依赖用户手动贴代码。
- 通俗理解：这有点像一个新加入项目的工程师，先看分支、最近改动和项目说明，再开始写代码。

##### 3. 它会积极复用提示缓存，减少重复成本

- 文中提到，Claude Code 似乎使用了类似 “边界标记” 的机制，把内容区分成：
  - 静态内容
  - 动态内容
- 这样做的好处是：
  - **静态部分可以全局缓存**
  - 不需要每次都重新构建和处理
- 关键意义在于 “稳定” 和 “节省计算开销”。
- 例如：项目结构说明、长期不变的仓库背景信息，没必要在每次对话里重复塞给模型。

##### 4. 专用工具比 “上传文件聊天” 更适合做编码

- 作者认为，Claude Code 强的一点是它不是把代码单纯当文本处理，而是给模型配了专门工具。
- 文中提到的工具包括：
  - **Grep 工具**：专门用于搜索，而不是通过 Bash 去直接调用`grep`或`rg`
  - **Glob 工具**：专门用于发现文件
  - **LSP 工具**：支持调用层级、查找引用等代码级操作
- 作者推测，专用工具的优势可能在于：
  - 权限控制更好
  - 结果收集更规范
  - 对代码语义理解更强
- 尤其是**LSP（语言服务器协议）**很重要，因为它能处理 “谁调用了谁”“某个函数被哪里引用” 这类结构化问题，而不是只做关键词匹配。
- 作者认为，这相比普通 Web 聊天界面是一个很大的提升，因为后者更像把代码当作静态文本来看。

##### 5. 它非常重视控制上下文膨胀

- 作者指出，代码代理最大的问题之一就是**上下文窗口有限**。
- 当任务变复杂时，很容易被这些内容挤爆：
  - 来回对话历史
  - 重复读取文件
  - 日志文件
  - 很长的 Shell 输出
- Claude Code 为了解决这个问题，做了不少底层优化，比如：

###### 5.1 文件读取去重

- 它会检查文件是否发生修改。
- 如果文件没变，就不会反复重新处理。
- 这能避免模型一次次 “重新读老内容”。

###### 5.2 大结果落盘，只保留预览

- 如果工具返回结果太大，就**写入磁盘**。
- 真正放进上下文里的，只是：
  - 结果预览
  - 文件引用
- 这样可以显著减小上下文占用。
- 文末热门回复还特地纠正了这一点，确认原意是：**大结果写入磁盘，上下文只保留预览和文件引用**。

###### 5.3 自动截断和压缩

- 像很多现代 LLM 产品一样，它也会：
  - 自动截断过长上下文
  - 在需要时自动压缩 / 总结
- 这相当于给长期对话做 “瘦身”，让模型把注意力集中在当前最重要的信息上。

##### 6. 它维护结构化的会话记忆

- Claude Code 会为当前对话维护一个结构化的 Markdown 文件，里面包含多个固定栏目，例如：
  - 会话标题
  - 当前状态
  - 任务规范
  - 文件和功能
  - 工作流
  - 错误与修正
  - 代码库和系统文档
  - 学习收获
  - 关键成果
  - 工作日志
- 作者觉得这很像人类程序员的工作方式：一边写代码，一边记笔记、整理问题和总结进展。
- 这样做的价值在于：
  - 保持任务连续性
  - 降低遗忘关键约束的概率
  - 让后续步骤更有条理

##### 7. 它会使用分叉和子代理并行处理任务

- Claude Code 支持使用**子代理（sub-agents）**并行化工作。
- 作者说，这一直是它相对 Codex 的一个卖点，不过**Codex 最近也加入了子代理支持**。
- 这些分叉代理会：
  - 复用父代理的缓存
  - 保持一定的状态感知
  - 负责辅助性工作
- 典型用途包括：
  - 生成摘要
  - 提取记忆
  - 做背景分析
- 关键好处是：这些辅助工作不会 “污染” 主代理的核心执行循环。
- 通俗理解：像主程序员带着几个助手分头查资料、做总结，最后把精炼结果交回主线处理。

##### 8. 为什么它用起来会比 Web 聊天界面更好

- 作者最后总结认为，Claude Code 的优势**不只是提示词或模型更强**，而是来自很多看似细小、但组合起来很有效的工程优化：
  - 更完整的仓库上下文
  - 更积极的缓存复用
  - 更专业的代码工具
  - 更严格的上下文控制
  - 更结构化的会话记忆
  - 子代理并行协作
- 同时，它还有一个很实际的优势：
  - 用户可以在本地电脑上有条理地管理文件和工作流
  - 不必频繁往网页聊天框里上传文件

##### 9. 热门回复里的补充与争议

- 这篇文章并不是 “定论”，评论区里也有一些不同看法。

###### 9.1 关于 “是否建立索引”

- 有回复指出：**Claude Code 并不会自己构建索引**。
- 对方根据官方课程认为，它更像是 “聪明地使用`grep`和`ls`”。
- 作者随后回应：
  - 这看起来有道理
  - 可能是**LSP 服务器在做一部分索引工作**
  - 但不是 Claude Code 框架本身在建立索引

###### 9.2 关于 “秘诀到底是模型还是工程”

- 有评论者认为：这里体现的是扎实工程，但并没有特别出人意料的秘密，**真正的秘诀还是模型本身**。
- 作者则保持相对开放态度：
  - 认可模型确实很强
  - 但怀疑 Claude Code 的优势未必完全来自模型
  - 更可能是 “模型 + 工程框架” 的组合效果

##### 10. 文章结论

- 这篇文章最核心的结论是：**Claude Code 的优秀体验，可能主要来自一整套围绕编码场景打造的工程系统，而不只是模型更聪明。**
- 它真正做好的，是把代码任务中最麻烦的几件事处理掉了：
  - 自动理解仓库背景
  - 减少重复上下文
  - 用专用工具操作代码
  - 管理长期记忆
  - 并行处理辅助任务
- 这也意味着，未来代码代理之间的竞争，可能不只是 “谁的模型更强”，还包括 “谁的上下文系统、工具系统和代理架构更成熟”。
