## 正文

**Steve (Builder.io)**

介绍 /visual-plan - 一种为 Claude Code 和 Codex 生成丰富、可视化计划的技能

Claude Code 中的规划模式非常棒。

但当它在我的终端里给我展示这么长的 Markdown 格式文章时，我总是看得走神。

我发现使用可复用的组件可以制作出好得多的视觉方案。

所以我制作了一个名为 \`/visual-plan\` 的技能。

它以 MDX 格式生成计划，包含视觉化、交互式组件。图表、交互式 API 规范、架构设计变更、带注释的代码，甚至可平移和缩放的线框图。

所以对于任何 UI 工作，你可以先查看线框图，对它进行评论，迭代，然后让代理工作。

我发现这是一个更直观的界面，便于推理代理正在做什么。

这多少受到了那篇关于 HTML 比 Markdown 更好的热门帖子的启发。

但是 HTML 写起来可能很慢且冗长，而且提交到代码仓库里也不好看。

这真的让我觉得人类和工程正进入一个新的抽象阶段，在这个阶段中我们在计划层面思考问题。

只要计划好，代理在执行计划时会变得越来越可靠。

几乎达到了我们信任 C 编译器能够可靠地将代码编译为汇编的程度。

计划是新的中间表示。

我还制作了一个与此相反的技能，名为 \`/visual-recap\`。

代理工作完成后，它会为你总结它所做的一切。

同样的思路：线框图、交互式 API 规范和差异、模式、带注释的代码等。

所以现在，当你查看代理为你做的事情，或者查看别人代码的拉取请求时，你可以看到可视化的总结，而不是仅仅阅读一大段文字。

它完全是免费开源的。你可以在我的 GitHub 上找到它。

会在回复中链接到它，因为我们都知道这些算法在处理链接方面有多笨。

## 解读（1）

### 2026-06-17 02:12:11

#### 深度总结

Steve 提出了一个开源技能：`/visual-plan`。

它的核心作用是：  
把 Claude Code / Codex 的“文字规划”变成 **可视化、可交互的计划文档**。

传统方式是 AI 在终端里输出一大段 Markdown，信息密度高，但阅读负担重。  
`/visual-plan` 改用 MDX 生成更丰富的计划内容，包括：

- 架构图
- 交互式 API 规范
- 带注释代码
- UI 线框图
- 可平移、缩放的设计草图
- 架构变更说明

尤其在 UI 开发中，人可以先看线框图、评论、修改，再让 AI 执行。

他还做了反向技能：`/visual-recap`。  
当 AI 完成任务后，它会用可视化方式总结改动，帮助人理解：

- AI 做了什么
- 改了哪些代码
- 架构或接口有什么变化
- PR 里真正发生了什么

Steve 的核心判断是：

> 人类和工程正在进入一个新的抽象阶段：  
> 我们不再只是在“写代码”，而是在“设计计划”。  
> 计划正在成为新的中间表示。

就像人类信任 C 编译器把 C 代码编译成汇编一样，未来人类可能会越来越信任 AI 把“计划”执行成代码。

---

#### 深入浅出解读

过去的开发流程大概是：

```text
人写代码 → 机器执行
```

后来变成：

```text
人写需求 → AI 写代码
```

但这仍然有问题：  
如果需求只是几段文字，AI 容易理解偏，人也不容易检查。

Steve 想解决的是中间这一层：

```text
人提出目标 → AI 生成可视化计划 → 人审查计划 → AI 执行代码
```

这里最重要的不是“可视化好看”，而是 **可视化降低理解成本**。

比如：

- 看一大段文字描述页面布局，很累；
- 直接看线框图，一眼就懂；
- 看 API 文档文字说明，很抽象；
- 看交互式接口规范，更容易发现问题；
- 看代码 diff，很细碎；
- 看视觉化 recap，更容易把握整体变化。

所以 `/visual-plan` 的价值在于：  
它把 AI 的“思考过程”和“执行意图”变得更容易被人类检查。

这其实是 AI 编程里非常关键的一步：  
不是让 AI 更快写代码，而是让人更容易判断：

> AI 到底打算怎么做？  
> 它有没有误解我？  
> 它的方案是否合理？  
> 我能不能放心让它继续？

---

#### 核心洞察

##### 1. Markdown 不够用了

Markdown 简洁，但表达复杂系统时能力有限。  
架构、交互、UI、流程、API，用纯文字描述容易失真。

Steve 的观点是：  
未来 AI 工具输出的不应只是“文本”，而应是更接近产品设计稿、架构图和工程蓝图的内容。

---

##### 2. 计划比代码更重要

以前程序员直接控制代码。  
现在 AI 可以写大量代码，人类的重点会逐渐前移到：

- 定义目标
- 审查计划
- 约束边界
- 判断方案
- 验收结果

也就是说，人类从“代码工人”变成“计划审查者”和“系统设计者”。

---

##### 3. 计划成为新的中间表示

“中间表示”可以理解为连接两端的桥梁。

过去：

```text
高级语言 → 编译器 → 机器码
```

未来可能是：

```text
人类意图 → 可视化计划 → AI 生成代码
```

如果这个计划足够清晰、结构化、可验证，AI 执行就会更可靠。

---

#### 辩证思考

##### 积极面

###### 1. 降低沟通成本

可视化计划能让产品、设计、工程、AI 之间更容易对齐。  
尤其适合复杂 UI、系统架构和 PR 审查。

###### 2. 提升 AI 可控性

AI 最大的问题之一是“看似懂了，其实偏了”。  
可视化计划让人可以在执行前发现偏差，减少返工。

###### 3. 改变软件开发工作流

未来开发可能不再是“先写代码”，而是：

```text
先共识计划，再自动执行
```

这会让工程管理、代码审查、需求分析发生变化。

---

##### 风险面

###### 1. 好看的计划不等于正确的计划

可视化容易制造“确定感”。  
图画得清楚，不代表架构合理；  
线框图漂亮，不代表实现简单；  
API 规范完整，不代表边界正确。

人可能被视觉表达迷惑，放松判断。

###### 2. 计划与代码可能脱节

如果计划没有和实际代码、测试、类型系统绑定，它可能变成另一种“漂亮文档”。

最危险的是：

```text
计划看起来对，代码实际不对
```

所以可视化计划必须和真实执行结果、测试、diff、CI 结合。

###### 3. 抽象层越高，错误越隐蔽

从代码上升到计划，效率更高，但也更容易忽略细节。  
计划中的一个模糊点，可能被 AI 扩展成大量错误代码。

因此，人类不能只看大图，还要保留关键细节审查能力。

---

#### 我的判断

`/visual-plan` 的意义不只是一个工具，而是代表 AI 编程范式的变化：

> 人类从“写代码”转向“审计划”；  
> AI 从“回答问题”转向“执行蓝图”；  
> 软件开发从“文本驱动”转向“结构化、可视化计划驱动”。

但它真正能不能成为主流，取决于三点：

1. 计划是否足够准确；
2. 计划是否能和代码执行强绑定；
3. 人是否能在更高抽象层保持判断力。

简言之：

> 可视化计划会让 AI 编程更好用，  
> 但不能替代工程判断。  
> 它是新的方向，不是最终答案。

## 结构化（1）

### 2026-06-18 11:54:24

##### 主旨概括

Steve（Builder.io）推出了一个开源技能 **`/visual-plan`**，用于让 Claude Code 和 Codex 生成更直观的“可视化计划”，替代冗长的 Markdown 文字计划。核心观点是：未来人与 AI 代理协作时，重点会逐渐转向“先把计划做好”，再让代理可靠执行。

---

##### 1. 背景：纯 Markdown 计划太长，阅读体验差

- Claude Code 的“规划模式”很有用，但生成的计划通常是很长的 Markdown 文档。
- 作者表示，在终端里阅读这种长篇文字计划时，很容易走神、看不进去。
- 因此，他希望用更直观的方式展示 AI 代理准备做什么。

---

##### 2. 解决方案：推出 `/visual-plan`

- Steve 制作了一个名为 **`/visual-plan`** 的技能。
- 它可以用 **MDX** 格式生成计划，并加入可复用的视觉化、交互式组件。
- 相比普通 Markdown，它能把计划展示得更像一个可视化设计稿或交互式说明文档。

---

##### 3. `/visual-plan` 能生成哪些内容

`/visual-plan` 支持生成多种视觉化内容，包括：

- **图表**
- **交互式 API 规范**
- **架构设计变更说明**
- **带注释的代码**
- **可平移、可缩放的线框图**

例如在做 UI 相关工作时，可以先让 AI 生成线框图，开发者查看后提出意见、反复迭代，最后再让代理开始真正编码。

---

##### 4. 核心价值：让人更容易理解和审查 AI 的计划

- 作者认为，可视化计划比大段文字更适合帮助人类理解 AI 代理的思路。
- 特别是在 UI、架构、API 等场景中，图形化表达能更快发现问题。
- 一个回复中有人担心这种方式会增加 token 消耗；Steve 回应说：
  - **MDX 比 HTML 更节省 token**
  - 可复用组件也能进一步减少重复内容
  - 在线框图阶段发现问题，比代码生成后再发现问题更高效

---

##### 5. 更大的判断：计划正在成为新的“中间表示”

- Steve 认为，人类与工程开发正在进入一个新的抽象阶段：
  - 人类更多在“计划层面”思考问题；
  - AI 代理负责根据计划执行。
- 他将“计划”类比为一种新的 **中间表示（Intermediate Representation）**。
- 类似于我们信任 C 编译器能把 C 代码可靠编译成汇编代码，未来只要计划足够好，AI 代理执行计划也会越来越可靠。

---

##### 6. 配套技能：`/visual-recap`

- 除了 `/visual-plan`，Steve 还制作了反向技能 **`/visual-recap`**。
- 它用于在 AI 代理完成任务后，生成一份可视化总结。
- 总结内容同样可以包括：
  - 线框图
  - 交互式 API 规范与差异
  - 架构模式
  - 带注释的代码
- 这样用户在查看 AI 完成的工作，或审查别人提交的 PR 时，不必只读大段文字，而可以通过可视化摘要快速理解变更。

---

##### 7. 开源与反馈

- `/visual-plan` 是 **免费且开源** 的，作者表示可以在他的 GitHub 上找到。
- 热门回复中，不少开发者表示这个工具很有用，因为他们也觉得 Codex 或 Claude 的长篇计划读起来很累。
- 有用户形容，凌晨看那些“像博士论文一样长”的计划很痛苦，而这个技能能明显改善阅读体验。
