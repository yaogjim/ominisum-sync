## 产品-最佳实践（1）

### 2026-03-19 10:48:44

可以。你这段内容里，最值得展开的 “实例” 其实不是某一句观点，而是一套很具体的 AI 开发工作流：

- `Opus`负责`plan/design`
- `GPT`负责`execute`
- 在同一会话里随时切换模型
- 用终端多路复用和编辑器把 “思考 - 实现 - 验证” 串起来

如果把它变成一个可落地的最佳实践，我建议用一个具体场景来讲：

**实例：一周内做一个 AI Newsletter 精选站**
目标是做一个网站，每周抓取 / 整理 20 条高质量 AI 链接，自动生成摘要、标签、推荐理由，并发布成网页和邮件。

这和你给的内容高度贴合，因为原文本身就在讨论：
- 高密度信息筛选
- newsletter 作为产品形态
- AI 辅助编程不是 “全自动”，而是 “分工协作”

下面我直接给 “这套实例之上的最佳实践”。

**一、先定分工：不要让一个模型从想法一路写到上线**
最佳实践不是 “哪个模型最强就全交给它”，而是强制分层：

- `Opus`做高层设计：产品目标、信息架构、数据流、页面结构、技术方案比较
- `GPT`做落地执行：建目录、写代码、补测试、修 bug、改文案、做重构
- 人负责拍板：优先级、风格判断、是否值得做、哪里该停

一个很实用的原则是：

- `Opus`产出 “不会直接进仓库的内容”
- `GPT`产出 “准备提交到仓库的内容”

这样能明显减少 “模型把前期草稿直接写成正式代码” 的混乱。

**二、具体执行范式：先让 Opus 产出 4 份文档，再让 GPT 开工**
以这个 newsletter 站点为例，先让`Opus`一次性给出四类结果：

- 产品定义：这个站点解决什么问题，用户是谁，和普通资讯站有什么不同
- 系统设计：抓取、清洗、摘要、存储、发布的流程图
- 页面设计：首页、归档页、单篇页、订阅页的结构和重点模块
- 实施计划：按天拆成可执行任务，区分 MVP 和非 MVP

一个好的提示方式不是 “帮我做个网站”，而是：

```text
你是资深产品架构师。请为一个 AI newsletter 精选站设计 MVP。
要求：
1. 用户每周看到 20 条高质量链接，每条有标题、摘要、标签、推荐理由
2. 支持网页展示和邮件导出
3. 一周内完成首版
4. 技术栈尽量简单，适合单人开发
请输出：
- 用户问题定义
- 功能优先级表
- 信息架构
- 技术方案比较
- 风险点
- 7 天执行计划
```

这一步的最佳实践是：

- 不要一上来要代码
- 先要 “约束条件”
- 先收敛，再生成

因为很多 AI 开发失败，不是写不出代码，而是前面没定义好边界。

**三、把规划文档压缩成 “执行契约”，再交给 GPT**
这是最容易被忽略、但最关键的一步。

不要把 Opus 的长篇分析原样丢给 GPT。  
要先人工压缩成一份简短、明确、可执行的`execution brief`，例如：

```text
项目：AI Newsletter 精选站 MVP

目标：
- 展示每周 20 条 AI 链接
- 每条内容包含：title, url, summary, tags, why_it_matters
- 支持网页浏览和导出 markdown 邮件稿

技术栈：
- Next.js
- SQLite
- 简单后台脚本抓取 / 导入
- Tailwind

本轮只做：
1. 首页列表
2. 单篇详情页
3. 本地数据读写
4. markdown 导出脚本

不做：
- 登录
- 推荐算法
- 自动邮件发送
- 爬虫调度系统

要求：
- 目录结构清晰
- 每一步改动可验证
- 先建最小骨架，再逐步补功能
```

最佳实践是：

- 给 GPT 的不是 “灵感”，而是 “边界”
- 明确`做什么 / 不做什么`
- 强制它分步提交，而不是一口气生成全项目

**四、在 CLI 里切模型时，要按 “节点” 切，不要按 “情绪” 切**
很多人切模型是这种模式：

- 写着写着觉得不顺，就换
- 看到某模型输出更华丽，就换
- 某模型答非所问，就全盘重来

这不是最佳实践。  
最佳实践是按任务节点切换：

- `需求不清` → 切`Opus`
- `架构摇摆` → 切`Opus`
- `开始搭骨架` → 切`GPT`
- `出现具体报错` → 切`GPT`
- `需要重构模块边界` → 切`Opus`
- `需要补测试和修边角` → 切`GPT`

也就是说：

- 抽象问题，用擅长抽象的模型
- 具体问题，用擅长执行的模型

**五、终端最佳实践：一个 pane 只承担一种角色**
你提到`Ghotty + Cmux`，这类终端组合真正的价值，不是 “酷”，而是把上下文隔离开。

在这个 newsletter 项目里，推荐至少 4 个 pane：

- `Pane 1`：主开发会话，给 GPT 执行任务
- `Pane 2`：运行 dev server 和日志
- `Pane 3`：数据库 / 脚本 / 导入导出验证
- `Pane 4`：给 Opus 做设计、重构、评审

最佳实践：

- 不要在同一个 pane 里既讨论设计又跑命令
- 不要让模型在日志噪音里持续对话
- 每个 pane 保持单一职责，方便回看和追溯

这会显著降低 “上下文污染”。

**六、代码生成的最佳实践：让 GPT 先搭骨架，再填细节**
以首页列表页为例，不要让 GPT 一次写完整站点。正确做法是分三轮：

第一轮：只搭项目骨架
- 页面路由
- 数据类型定义
- 假数据读取
- 最小渲染

第二轮：补核心逻辑
- markdown 或 JSON 数据导入
- 列表页展示
- 详情页渲染
- 标签筛选

第三轮：补工程质量
- 错误处理
- 类型收紧
- 单元测试
- README 和脚本说明

这是最佳实践，因为：

- 第一轮主要验证方向对不对
- 第二轮验证功能通不通
- 第三轮才考虑 “像不像产品”

很多人一开始就要 “完整漂亮可上线版本”，结果通常是：
- 文件太多
- 风格不一致
- 改一处坏三处
- 最后无法维护

**七、最佳实践不是 “让 AI 多写”，而是 “让 AI 多验证”**
在这个实例里，最推荐你加入的规则是：

每完成一个模块，都要求模型回答这三个问题：

- 这一步具体改了什么
- 怎么验证它是对的
- 最大风险是什么

例如做完 “markdown 导出脚本” 后，要求 GPT 输出：

```text
1. 新增了什么文件
2. 输入输出格式是什么
3. 如何用一个示例数据跑通
4. 哪些边界情况还没覆盖
```

这是非常有效的 best practice，因为 AI 真正容易出错的，不是 “不会写”，而是 “写完假装没问题”。

**八、对 “AI 编程时代结束了” 这类观点，最佳实践是反着用**
你给的回复区里有个很关键的观点：  
真正稀缺的不是 “写代码速度”，而是架构经验、坏味道直觉、方向判断。

所以在这个实例上，最佳实践不是追求：
- 一句话生成全站
- 一夜写完 1 万行
- 模型替代工程判断

而是追求：

- 人来做取舍，AI 来做放大
- 人来定结构，AI 来补实现
- 人来发现坏味道，AI 来快速试错

具体到这个 newsletter 项目，人的关键价值在：

- 到底做 “链接精选” 还是 “观点精选”
- 首页强调 “高密度” 还是 “可读性”
- 摘要长度怎么控制
- 推荐理由是否统一模板
- 哪些功能第一周坚决不做

这部分如果不由人主导，再强的模型也只能高效率地产生中庸方案。

**九、一个可直接套用的最优工作流**
如果你要把这套方法真正用起来，我建议直接照这个顺序：

- 第 1 步：用`Opus`出`PRD + IA + 技术方案 + 7 天计划`
- 第 2 步：人工压缩成一页`execution brief`
- 第 3 步：用`GPT`只搭 MVP 骨架
- 第 4 步：每做完一个模块就本地验证
- 第 5 步：遇到结构问题，再切回`Opus`做重构建议
- 第 6 步：最后让`GPT`统一补测试、文档、脚本

这一套里最重要的不是工具名，而是四个原则：

- 先设计，后实现
- 先边界，后生成
- 先骨架，后细节
- 先验证，后扩展

**十、如果只提炼成一句最佳实践**
基于你提供的这个实例，我认为最值得记住的一句是：

- 把 AI 当成 “分工明确的团队成员”，不要当成 “全能外包商”。

`Opus`负责 “想清楚”，`GPT`负责 “做出来”，你负责 “决定什么值得做、什么现在不做”。

如果你愿意，我下一步可以直接继续给你两种更具体的版本：

1. 把这个实例写成一份`可直接复制使用的 Prompt 模板`
2. 把这个实例展开成一套`AI 编程工作流 SOP（从想法到上线）`
