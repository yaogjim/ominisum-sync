Preserve pi skills for Cursor runs

#### pi-cursor-sdk

一个 pi 提供程序扩展，使 pi 能够通过本地的 `@cursor/sdk` 代理运行时使用 Cursor 模型。

如果您希望在 pi 内使用 Cursor 的模型目录，同时保留 pi 的原生模型选择器、SDK 暴露的思考控制、会话恢复、上下文显示以及默认页脚用户体验，那么请使用此扩展。

#### Quick start

1. Install the package:

```
pi install npm:pi-cursor-sdk
```

Or install from GitHub:

```
pi install https://github.com/fitchmultz/pi-cursor-sdk
```

1. Start pi with a Cursor model:

```
pi --model cursor/composer-2-5
```

1. 在 pi 中，运行 `/login` ，选择 `使用 API 密钥` ，选择 `Cursor` ，并粘贴你的 Cursor SDK API 密钥。

如果 pi 启动时没有密钥，请在 `/login` 之后运行 `/cursor-refresh-models` ，以无需重启 pi 即可刷新完整的实时 Cursor 模型目录。在 pi 中，使用 `/model` 选择另一个 Cursor 模型。

#### Requirements

- Node.js 22.19+
- pi 0.76.0 or newer
- 一个通过 `/login` 保存的 Cursor SDK API 密钥，可作为 `CURSOR_API_KEY` 使用，或通过 pi 的 `--api-key 传递`

不需要全局安装 `@cursor/sdk` 。该软件包依赖确切的 `@cursor/sdk@1.0.17` ，因此常规的软件包安装会引入该扩展构建和测试时使用的 SDK 版本。Cursor SDK 当前依赖 `sqlite3@^5.1.7` ，其安装过程中可能会输出已弃用的间接 `node-gyp@8` 依赖警告，例如 `inflight` 、 `rimraf` 、 `glob` 、 `npmlog` 、 `gauge` 、 `are-we-there-yet` 以及 `tar@6` 。这些警告并非致命，且来自闭源的 Cursor SDK 依赖边界；该软件包无法强制 npm 覆盖到消费者项目中。如果您从自己控制的根目录 `package.json` 进行安装，可以选择根级覆盖，例如 `"overrides": { "sqlite3": "6.0.1" }` ；pi 软件包安装仍将遵循 npm 的常规间接依赖规则。该软件包声明 pi 的最低版本为 0.76.0，无最高对等版本限制，因此在该扩展重新发布之前更新 pi 的用户不会被阻止尝试现有扩展。 当前验证基准是 pi 0.78.0 加上 Cursor SDK 1.0.17；旧版本的 pi 或 Cursor SDK 兼容路径不再维护。

#### Install

##### Global install

```
pi install npm:pi-cursor-sdk
```

Alternative GitHub install:

```
pi install https://github.com/fitchmultz/pi-cursor-sdk
```

##### Project-local install

如果您希望将包记录到当前项目的 `.pi/settings.json` 中而非全局 pi 设置中，请使用 `-l` ：

```
pi install -l npm:pi-cursor-sdk
```

用于从这个代码仓库进行开发：

```
npm install
pi -e . --model cursor/composer-2-5
```

`pi-cursor-sdk` 传递显式 API 密钥到 Cursor SDK。它不重复使用 Cursor 代理 CLI 登录、Cursor 桌面登录或由 `代理状态` 显示的 Cursor 订阅/OAuth 状态。

可以使用来自 Cursor Dashboard → Integrations 的用户 API 密钥，或来自 Team settings 的服务账号 API 密钥。Cursor SDK 不支持团队管理员 API 密钥。然后使用以下方法之一配置密钥。

Preferred setup:

```
pi --model cursor/composer-2-5
```

Then, inside pi:

1. Run `/login`.
2. Select `Use an API key`.
3. Select `Cursor`.
4. 粘贴您的 Cursor SDK API 密钥。
5. 密钥保存在 pi 的原生 `~/.pi/agent/auth.json` 中。

如果 pi 启动时没有密钥，备用 Cursor 模型仍然会被注册，因此 `/login` 仍然可用。在执行 `/login` 之后，备用模型运行可以使用存储的密钥，而 `/cursor-refresh-models` 会刷新从 Cursor SDK 中发现的完整实时 Cursor 模型目录，且无需重启 pi。

注意：如果 `/login` 显示 `Cursor ✓ key in models.json` ，但你尚未保存 Cursor 密钥且 `CURSOR_API_KEY` 未设置，该状态属于 pi 身份验证状态限制。进行 Cursor 运行仍然需要真实的 Cursor SDK API 密钥。

Environment setup:

```
export CURSOR_API_KEY="your-key"
pi --model cursor/composer-2-5
```

One-shot setup:

```
pi --api-key "your-key" --model cursor/composer-2-5 --cursor-no-fast -p "Say ok only."
```

Discovery 使用 pi 的原生分辨率顺序来处理此扩展： `--api-key` ，存储在 `~/.pi/agent/auth.json` 中的 `cursor` 密钥，然后是 `CURSOR_API_KEY` 。

为避免每次 pi 启动时进行实时 `Cursor.models.list` 网络往返，已发现的目录会被缓存在磁盘上的 `~/.pi/agent/cursor-sdk-model-list.json` （权限为 `0600` ，以 API 密钥指纹作为键——密钥本身不会被存储）。在缓存 TTL 内的热启动会跳过网络请求，并且在需要 Cursor 操作时才加载 `@cursor/sdk` ； `/cursor-refresh-models` 始终绕过缓存并刷新实时目录。如果刷新失败，优先使用之前缓存的目录而非通用的捆绑回退版本。

```
# Cache lifetime in milliseconds (default 86400000 = 24h).
PI_CURSOR_SDK_MODEL_CACHE_TTL_MS=3600000 pi --model cursor/composer-2-5

# Disable the cache and always discover live.
PI_CURSOR_SDK_DISABLE_MODEL_CACHE=1 pi --model cursor/composer-2-5
```

不要将 API 密钥存储在 `~/.pi/agent/cursor-sdk.json` 中。该文件仅用于非机密的扩展状态，例如 Cursor 快速默认设置。 `PATH` 仅用于可执行文件查找，不应包含 API 密钥。

List Cursor models:

```
pi --list-models cursor
```

Expected behavior:

- 使用有效密钥后，Cursor 模型会出现在 `cursor` 提供方下
- 如果 discovery 无法验证身份或连接到 Cursor，pi 可能仍然会显示备用 Cursor 模型；在通过 `/login` 添加身份验证后，备用模型运行可以使用已保存的密钥，并且 `/cursor-refresh-models` 会刷新实时目录

Smoke test:

```
pi --model cursor/composer-2-5 --cursor-no-fast --no-session --mode json \
  -p "Reply exactly PI_CURSOR_MODEL_OK and nothing else."
```

预期：最终助手文本为 `PI_CURSOR_MODEL_OK` 。如果身份验证缺失或无效，pi 应提示你通过 `/login` 、 `CURSOR_API_KEY` 或 `--api-key` 配置 Cursor SDK API 密钥。

通过 `/model` 交互式选择 Cursor 模型，或在命令行传递模型：

```
pi --model cursor/composer-2-5
pi --model cursor/gpt-5.5@1m
pi --model cursor/gpt-5.5@272k
pi --model cursor/claude-opus-4-8@300k
```

How to read model IDs:

- `cursor/...` 是本扩展注册的 Cursor 提供者
- `@1m` 、 `@272k` 和 `@300k` 是上下文窗口变体
- `:medium` 、`:high` 和 `:xhigh` 是 pi 思考级别后缀，用于 Cursor SDK 提供可由 pi 控制的思考参数的模型

带有 pi 思考控制的示例

```
pi --model cursor/gpt-5.5@1m:medium
pi --model cursor/gpt-5.5@272k:xhigh
pi --model cursor/gpt-5.5@1m --thinking medium
```

仅 Cursor 参数不会被编码为 pi 模型 ID。Cursor `context` 成为 pi 可见的模型变体，因为它会改变 pi 的原生 `contextWindow` ；Cursor `fast` 和 Cursor SDK 对话模式是扩展状态，而非模型身份。别名模型 ID 对仅 Cursor 状态（例如 fast 默认值）使用其选定的 SDK ID，并对由底层 Cursor 基础模型作为键的旧默认值提供读取回退。

#### Thinking support

所有 Cursor SDK 模型都应被视为具备思考能力的 Cursor 模型。 `pi --list-models` 输出中的 `thinking` 列含义更窄：它仅表示 pi 可以为该模型控制 Cursor SDK 思考参数。

对于 Cursor 暴露 `reasoning` 、 `effort` 或布尔型 `thinking` 参数的模型，pi 的原生思考控制映射到 Cursor SDK 参数：

- `推理=无|低|中|高|极高`
- `effort=低|中|高|超高|最大`
- `thinking=false|true` 用于布尔思维模型

对于同时具备 `thinking` 和 `effort` 的 Claude 模型，当 `pi thinking off` 时，会发送 `thinking=false` 并省略 `effort` 。

在 `pi --list-models` 中， `thinking=no` 表示 pi 无法通过 `--thinking` 、最终的 `:medium` 模型后缀或 shift+tab 来控制模型的思考级别。这并不意味着 Cursor 模型无法思考。

某些 Cursor SDK 模型不会暴露 `reasoning` 、 `effort` 或 `thinking` 参数供扩展设置。Cursor 的思考功能仍由模型启用/支持，Cursor 可能仍会发出思考增量。当 SDK 发出这些增量时，扩展会通过 pi 的原生思考渲染来呈现它们。

#### Fast mode

快速偏好设置会根据所选的 Cursor SDK 模型 ID 或别名进行记忆并存储：

- 在当前会话中使用 `pi.appendEntry()`
- 在 `~/.pi/agent/cursor-sdk.json 中全局地`

在单次运行中，强制开启或关闭快速模式，而不更改已保存的默认设置：

```
pi --model cursor/gpt-5.5@1m --cursor-fast -p "Say ok only"
pi --model cursor/composer-2-5 --cursor-no-fast -p "Say ok only"
```

Composer 2 和 Composer 2.5 默认使用快速模式。使用 `--cursor-no-fast` 可进行单次无快速模式的 Composer 运行。在打印模式（ `-p` ）下， `--cursor-no-fast` 为静默模式，且不会写入 `~/.pi/agent/cursor-sdk.json` 文件。

在交互模式下，当快速模式启用时，页脚仅显示快速模式；当处于非默认状态时，页脚仅显示 Cursor 模式。快速模式和计划模式共享一个 Cursor 状态值，因此它们不会相互覆盖：

```
cursor fast
cursor plan
cursor fast · plan
```

如果您看不到 `cursor fast` ，快速模式已关闭。如果您看不到 `cursor plan` ，Cursor SDK 模式为默认 `agent` 模式。

Cursor SDK 对话模式是仅针对 Cursor 的扩展状态。它不是 pi 模型变体，不是 pi 的思考/推理，不是 Cursor `fast` ，也不是 pi 的独立只读计划模式扩展。

默认模式是 `agent` 。启动一个单次运行以特定模式：

```
pi --model cursor/composer-2-5 --cursor-mode agent
pi --model cursor/composer-2-5 --cursor-mode plan
```

交互式地更改会话模式:

```
/cursor-mode agent
/cursor-mode plan
/cursor-mode
```

维护人员可以在 Cursor 模型会话中运行 `/cursor-tools` ，以打印当前桥接启用状态、引导清单启用状态、有效 `PI_CURSOR_SETTING_SOURCES` ，以及可调用表面快照（主机工具摘要及当前 `pi__*` 名称）。查看 Cursor 内部使用清单 。

当创建新的本地 Cursor SDK 代理时，扩展通过 `Agent.create({ mode })` 初始化模式。扩展还会在每次 `agent.send(..., { mode })` 调用时发送有效的 Cursor 模式，因此 `/cursor-mode` 和 `--cursor-mode` 即使在重用池化的 SDK 代理时仍然是事实来源。

Cursor SDK `plan` 模式可以生成面向计划的输出以及 Cursor 待办事项/计划活动，但这些回放卡片保持仅显示状态。它们不会驱动 pi 的计划模式扩展、pi 待办事项或活跃工具状态。

#### Images

最新用户消息中的图片被转发到 Cursor。历史图片不包含在对话记录中，仅以 `[image omitted from transcript]` 占位符的形式出现，因此关于早期图片的后续问题应重新附上图片或包含文字描述。该扩展支持为 Cursor 模型提供 `text` 和 `image` 输入，因为 Cursor 的 SDK 接受图片消息，且 Cursor 模型预计支持这些输入。

See Cursor 工具在 pi 中的呈现 以获取关于可调用工具与仅展示工具、MCP 目录限制、JSONL ID 模式，以及 pi 切换与 Cursor 环境 MCP 的区别的简明指南。

Cursor 运行使用本地 Cursor SDK 代理，带有两个独立的工具界面：

- **Cursor 原生界面：** Cursor 本地代理工具、Cursor 设置、插件以及已配置的 Cursor MCP 服务器。这些仍然由 Cursor SDK 本地代理路径所拥有。
- **pi 桥接界面：** pi-cursor-sdk 通过每次运行的本地回环 MCP 桥接暴露可桥接的活跃 pi 工具，当桥接启用且当前 pi 工具注册表已暴露工具时。

桥接能力会为每次 Cursor 运行从 `pi.getActiveTools()` 和 `pi.getAllTools()` 中捕获快照，包括当 pi 暴露这些工具时的每个工具的提示指南。Cursor 仅在当前运行中暴露活跃的可桥接 pi 工具时，才会将其视为无冲突的 MCP 名称，例如 `pi__sem_reindex` 。Pi 会话输出、工具卡片、确认信息、钩子、渲染器、历史记录和中止行为使用真实的 pi 工具名称，例如 `sem_reindex` 。桥接将 Cursor 的 MCP 调用加入队列，发出标准的 pi `toolCall` ，等待匹配的 pi `toolResult` ，并将该结果解析回同一个活跃的 Cursor SDK 运行中，不会创建新的 `Agent` ，除非该运行已被释放、中止或取消。桥接不会直接调用 pi 工具的 `execute()` 处理程序。

重叠的内置 pi 工具（ `read` 、 `bash` 、 `write` 、 `edit` 、 `grep` 、 `find` 、 `ls` ）默认隐藏，因为 Cursor 本地代理已具备原生等效工具。扩展/自定义工具以及 pi 活动工具注册表中存在的不重叠的活动工具通常保持可见。桥接在启用时还会将 `cursor_ask_question` 暴露为 `pi__cursor_ask_question` ，使 Cursor 能够通过 pi 界面向用户提问，而非静默选择默认值。当 pi 加载了可见的 Agent 技能时，该扩展会为 Cursor 重写 pi 的技能目录，并将 `cursor_activate_skill` 暴露为 `pi__cursor_activate_skill` ；Cursor 应使用列出的技能名称调用该桥接工具，以在应用技能前加载完整的 `SKILL.md` 和捆绑资源列表。如果桥接被禁用，目录仍然可用，并指示 Cursor 回退到直接读取列出的 `SKILL.md` 路径。

Cursor 原生工具重放与桥接层分离。重放卡片是仅用于显示的已记录 Cursor SDK 活动。它们从不重新运行 Cursor 端命令、重新应用 Cursor 编辑、调用 MCP 服务器或修改 pi 状态。See Cursor 原生工具重放 。

Bridge controls:

```
# Roll back to Cursor SDK tools/settings/MCP only; do not expose active pi tools through the bridge.
PI_CURSOR_PI_TOOL_BRIDGE=0 pi --model cursor/composer-2-5

# Opt in to also expose overlapping pi tool names through the bridge.
PI_CURSOR_EXPOSE_BUILTIN_TOOLS=1 pi --model cursor/composer-2-5

# Override Cursor SDK MCP tool-call timeout, including bridged pi tools and configured Cursor MCP servers.
PI_CURSOR_MCP_TOOL_TIMEOUT_SECONDS=7200 pi --model cursor/composer-2-5
PI_CURSOR_MCP_TOOL_TIMEOUT_MS=7200000 pi --model cursor/composer-2-5

# Override known MCP initialize/listTools timeouts on first send (default 10s).
PI_CURSOR_MCP_CONNECT_TIMEOUT_SECONDS=5 pi --model cursor/composer-2-5
PI_CURSOR_MCP_CONNECT_TIMEOUT_MS=5000 pi --model cursor/composer-2-5

# Disable bootstrap callable-surface manifest (on by default).
PI_CURSOR_TOOL_MANIFEST=0 pi --model cursor/composer-2-5

# Emit scrubbed bridge diagnostics as JSONL to stderr with prefix [pi-cursor-sdk:bridge].
PI_CURSOR_PI_TOOL_BRIDGE_DEBUG=1 pi --model cursor/composer-2-5
```

在启动时，会默认注入一个紧凑的 **可调用工具界面** 块到 Cursor 提示中，使模型能够看到主机工具类别、当前运行的 `pi__*` 桥接名称，并收到一条提醒：已配置的 Cursor MCP 服务器是在运行时发现的（而非通过 pi 的工具目录）。可通过设置 `PI_CURSOR_TOOL_MANIFEST=0` 禁用此功能。

`PI_CURSOR_PI_TOOL_BRIDGE=0` 是受支持的回滚标志，可完全禁用桥接。该桥接还将 `false` 、 `off` 、 `none` 、 `no` 和 `disabled` 视为关闭； `1` 、 `true` 、 `on` 、 `yes` 和 `enabled` 视为开启。 `PI_CURSOR_EXPOSE_BUILTIN_TOOLS=1` 选择启用暴露 Cursor 已具有原生等效项的重叠 pi 工具名称。已安装的 Cursor SDK 默认使用 60 秒的 MCP 协议，且没有公开的每服务器超时选项。pi-cursor-sdk 默认在两个方向上覆盖了该默认行为：MCP `callTool` 请求被延长至 3600 秒，以支持长时间运行的本地 MCP 工具（包括 pi 桥接和已配置的 Cursor MCP 服务器）；而首次发送时已知的 MCP initialize/listTools 请求则缩短至 10 秒，以便不可用的已配置 MCP 服务器快速失败，而不是阻塞整整一分钟。未知的 Cursor SDK MCP 协议超时堆栈保持 SDK 默认值而不缩短。 覆盖工具调用超时，使用 `PI_CURSOR_MCP_TOOL_TIMEOUT_MS` 或 `PI_CURSOR_MCP_TOOL_TIMEOUT_SECONDS` ，并为首次发送的初始化/listTools 超时使用 `PI_CURSOR_MCP_CONNECT_TIMEOUT_MS` 或 `PI_CURSOR_MCP_CONNECT_TIMEOUT_SECONDS` 。 `PI_CURSOR_PI_TOOL_BRIDGE_DEBUG=1` 默认关闭，会将类型化的、经过允许列表筛选的、已清理的单行 JSONL 记录输出到 `process.stderr` 。这些记录是操作诊断信息，而非匿名遥测数据：它们有意包含工具名称、安全的关联 ID、桥接运行状态、暴露的 pi↔MCP 名称对、排队的请求、结果解析、拒绝、取消和待处理数量。它们不得包含端点 URL、端点路径组件、端点令牌、原始参数/结果、标准输出/标准错误负载、文件内容、Cursor 设置输出、API 密钥、承载令牌、Cookie、会话凭证或密钥。当工具名称本身为敏感信息时，请勿启用或分享桥接调试日志。

#### Fallback models

如果没有从 `/login` 、 `CURSOR_API_KEY` 或 `--api-key` 获取到密钥，则模型发现失败或返回无模型，此时扩展会注册一个最新审核过的 Cursor SDK 模型目录的捆绑回退快照，并在可能时通知交互式用户。

回退快照包含 Composer 2.5 (`composer-2.5` 和 `composer-2-5`)、Composer 2、GPT、Claude、Gemini、Grok、Kimi 以及经过审核的 `Cursor.models.list()` 输出所暴露的其他模型 ID。确切的已检入快照位于 `src/cursor-fallback-models.generated.ts` 。

实际的 Cursor 运行仍然需要来自 `/login` 、 `CURSOR_API_KEY` 或 `--api-key` 的密钥。如果您在启动后添加身份验证，请执行 `/cursor-refresh-models` 以刷新完整的实时 Cursor 模型目录，而无需重启 pi。

#### Limits

- **仅本地 Cursor SDK 代理。** 此扩展不使用 Cursor 云代理。云 pi 工具桥接不在范围内，因为它需要独立的身份验证、传输、生命周期和远程信任设计。
- **pi 工具桥是本地的，由 MCP 支持。** 可桥接的活跃 pi 工具通过经过令牌化处理的 `127.0.0.1` MCP 端点向本地 Cursor 代理暴露；排除内部 Cursor 重放活动名称，默认隐藏重叠的内置 pi 工具。设置 `PI_CURSOR_PI_TOOL_BRIDGE=0` 以禁用该功能，或设置 `PI_CURSOR_EXPOSE_BUILTIN_TOOLS=1` 以也暴露重叠的内置工具。
- **Cursor 运行状态可以跨越工具使用轮次。** 在一个 pi 会话中，该扩展会在兼容的后续轮次中重复使用一个 Cursor SDK 代理，并在上下文仍然匹配时发送增量提示。当上下文出现分歧、执行压缩或进行 `/tree` 导航后、API 密钥变更时、发送错误之后或会话关闭时，扩展会重新创建代理。对于桥接的 pi 工具，匹配的 pi `toolResult` 会解析为相同的活跃 Cursor SDK 运行，无需创建新的 `Agent` ，除非该运行已被释放、中止或取消。重放还可以将一个活跃的 Cursor SDK 运行拆分为多个 pi `toolUse` 轮次以进行展示。
- **最终助手文本是最后一个非空文本部分。** Composer 响应可以生成一条助手消息，包含早期进度 `text` 、思考/工具元数据，以及稍后的最终 `text` 报告。需要最终答案的用户应从末尾扫描助手消息内容，并使用最后一个非空 `text` 部分，而非第一个。
- **Cursor 设置源默认全选。** 该扩展默认传递 `local.settingSources: ["all"]` ，因此已配置的 Cursor MCP 服务器、插件工具、项目/用户设置以及相关的 Cursor 原生功能都可像在 Cursor 中一样使用。为缩小加载范围，可设置以逗号分隔的列表，例如 `PI_CURSOR_SETTING_SOURCES=project,user,plugins` 。要禁用环境设置源，可设置 `PI_CURSOR_SETTING_SOURCES=none` 。直接的 Cursor SDK 引导日志（设置、技能、钩子加载兼容性警告及类似内容）会被抑制，以免污染终端用户界面（TUI）。
- **当 Cursor 加载相同规则时，Cursor 模型上不会重复 AGENTS.md / CLAUDE.md。** Pi 会发现全局和项目上下文文件（ `AGENTS.md` 、 `CLAUDE.md` 以及大小写变体），除非你以 `-nc` 开头启动。在 `cursor/*` 模型上，该扩展仅移除通过 `before_agent_start` 钩子与 Cursor `settingSources` 重叠的 `<project_instructions>` 块： `user` 对应 `~/.pi/agent/AGENTS.md` ， `project` 对应仓库/父级 `AGENTS.md` 和 `CLAUDE.md` （已验证 Cursor 行为：本地代理加载项目 `AGENTS.md` 和 `CLAUDE.md` 并与 Cursor 规则并行）。 `~/.pi/agent/CLAUDE.md` 不会被剥离（Cursor 用户规则使用 `~/.claude/CLAUDE.md` ，而非 pi 的代理目录）。当设置 `PI_CURSOR_SETTING_SOURCES=none` 或仅使用 `plugins` 时，pi 上下文保持完整。设置 `PI_CURSOR_PRESERVE_PI_AGENTS_MD=1` 以保留重复注入。
- **Max Mode 不是手动的 pi 变体。** Cursor 的 SDK 可能会为需要它的模型自动启用 Max Mode。该扩展仅宣传 SDK 目录所公开的确切上下文窗口变体，否则使用保守的、由 SDK 衍生的默认/非 Max 上下文窗口。
- **输出 token 限制较为保守。** Cursor SDK 模型元数据目前不直接公开输出 token 限制。
- **pi 中的令牌使用量是近似值。** Cursor SDK 的使用事件包括累积的内部代理/工具/缓存工作，因此原始的 Cursor SDK 计数器不会被复制到 pi 的使用量中。该扩展在 `输入` / `输出` 中报告近似的 pi 会话活动，包括分段运行的工具调用和已使用的工具结果，而 `totalTokens` 跟踪用于上下文显示和压缩的可回放的 Cursor 提示/上下文估计值。

#### Troubleshooting

您可能看到回退启动模型，或者 Cursor SDK API 密钥缺失/无效。此扩展不会复用 Cursor Agent 命令行/桌面版的登录。在交互式 pi 中，运行 `/login` ，选择 `使用 API 密钥` ，选择 `Cursor` ，粘贴密钥，然后运行 `/cursor-refresh-models` 。

当身份验证配置完成后，若 Cursor 运行失败，pi 现在会显示经过处理的提供程序详细信息，而不仅仅是 `Cursor SDK 运行失败` 。通用 SDK 失败情况包含安全的运行元数据，例如模型 ID、短运行 ID 前缀以及可用时的持续时间。重试前，请查看红色提示条或助手错误消息以获取该详细信息。

中止的运行现在在可确定时会包含可能的原因，例如 `Cancelled: prompt interrupted.`（用户取消）或 `Cancelled: Cursor SDK run was cancelled.`（SDK 端取消）。

Cursor SDK 连接层的网络故障（例如 `ConnectError: read ETIMEDOUT` 或 `ConnectError: [aborted] read ECONNRESET` ）会以经过清理的重试提示形式呈现，而非导致 pi 崩溃。请检查您的连接并重试；持续失败可能表明 Cursor 服务或网络存在临时问题。

Cursor SDK 本地代理从 Cursor 设置源和内联 SDK 配置中加载 MCP 服务器。此扩展默认启用所有 Cursor 设置源，因此缺少网络搜索工具通常意味着它未在 Cursor 中进行配置，或者运行时使用了缩小/禁用覆盖（例如 `PI_CURSOR_SETTING_SOURCES=none` ）启动。

已知的 SDK 边界：某些本地 Cursor 网页搜索活动不会通过实时的 `onDelta` 、 `onStep` 或 `run.stream()` 工具事件发出。当这种情况发生时，pi 只能在 `run.wait()` 完成后从本地代理的转录记录中重建卡片，因此 **Cursor 网页搜索** 卡片可能会在助手文本之后出现，而不是作为实时进行中的卡片。缓冲所有助手文本直到 `run.wait()` 完成会使顺序更美观，但会破坏正常的流式传输，因此 pi 不会这样做。

许多运行过程从未将网页活动以可重放的 SDK 工具完成情况或本地转录网页工具记录的形式暴露出来。模型可能仍然会通过内部的 Cursor 网页工具进行回答，或者仅在助手文本/思考过程中提及搜索。在这种情况下，pi 无法渲染工具卡片，因为没有可重放的已完成 SDK 工具调用有效载荷。在排查问题时，使用 `npm run debug:provider-events` 捕获一次运行；如果 `on-delta.jsonl` 、 `on-step.jsonl` 、 `stream-events.jsonl` 、 `coordinator-events.jsonl` 和 `display-decisions.jsonl` 中没有已完成的或转录的网页工具数据，则该限制存在于 Cursor SDK 表层，而非 pi 的重放注册中。

**Web fetch:**`pi-cursor-sdk` can display `webFetchToolCall` 转录记录 and web-fetch 形状的 MCP/主机补全 when Cursor reports them. It cannot make Cursor expose or execute a `WebFetch` 工具. If Cursor's current local SDK 工具集 does not include WebFetch, pi cannot fetch a URL through Cursor web fetch; use an allowed browser/shell/MCP 工具 instead.

pi 扩展切换和 pi 的 MCP 目录不控制 Cursor 环境 MCP。本地 Cursor 代理从 Cursor 设置源加载 MCP 服务器（默认情况下为 `PI_CURSOR_SETTING_SOURCES=all` ），包括 `~/.cursor/mcp.json` 。要移除服务器，请编辑或清空该文件（或 Cursor MCP 设置）并重启 pi 会话，或使用 `PI_CURSOR_SETTING_SOURCES=none` 或逗号分隔的子集来缩小/禁用源。查看 Cursor 工具在 pi 中显示 。

本地 pi 桥接仅暴露那些在当前 pi 会话中处于激活状态且在 Cursor 启动时存在于 pi 工具注册表中的工具。默认情况下，它不暴露 Cursor 已有原生等效工具的名称重叠的 pi 工具（ `read` 、 `bash` 、 `write` 、 `edit` 、 `grep` 、 `find` 和 `ls` ）。如果您有意希望 Cursor 同时看到 Cursor 原生工具和名称重叠的内置 pi 工具，请选择启用：

```
PI_CURSOR_EXPOSE_BUILTIN_TOOLS=1 pi --model cursor/composer-2-5
```

```
PI_CURSOR_PI_TOOL_BRIDGE=0 pi --model cursor/composer-2-5
```

```
PI_CURSOR_MCP_CONNECT_TIMEOUT_SECONDS=5 pi --model cursor/composer-2-5
PI_CURSOR_MCP_CONNECT_TIMEOUT_MS=5000 pi --model cursor/composer-2-5
```

- **模型文本回显：** Assistant `text` 块包含类似 `Tool call` 、 `Cursor activity` 或 `call cursor-replay-…` 的行，没有匹配的 `toolCall` 块 —— Cursor 模型生成了 pi 提示词转录格式，而非调用 SDK 工具。请参见 以纯文本形式列出的工具调用（#40 分类） 。
- **回放 vs 执行：** `cursor-replay-*` ID 和中性 **Cursor MCP** 活动卡片是仅用于显示的已记录 Cursor 结果；它们不会重新运行浏览器/MCP 工作。请参见 Cursor 原生工具回放 。
- **运行失败/被丢弃的工具：** 带有清理后详情的红色提示框可能表示 SDK 失败（#55）。已启动但未完成的 Cursor 工具在运行失败/中止、未生成助手文本或涉及外部/有副作用的工具时，会显示中性的 **Cursor … 未完成** 活动卡片，并附带明确的原因；不完整的快速本地发现启动（ `read` 、 `grep` 、 `glob` 、 `ls` ）仅在成功生成文本的运行后可用于调试，以避免过时的 SDK 启动事件生成红色回答后卡片；针对同一漏洞的维护者调试仍在 **#52** 中（ `PI_CURSOR_SDK_EVENT_DEBUG=1` ）。
- **硬网络崩溃：** pi 因未捕获的 Cursor SDK `ConnectError` 退出，而非显示过滤后的重试/认证错误 —— 捕获堆栈/会话尾部作为进程保护回归问题，而非 #40 文本回显。

```bash
pi install npm:pi-cursor-sdk
```

### 2026-06-01 10:07:15

#### pi-cursor-sdk 项目总结

`pi-cursor-sdk` 是一个 pi 编程代理扩展，用来在 pi 中调用本地 Cursor SDK 模型。它让用户可以在 pi 里使用 Cursor 的模型目录，同时保留 pi 原生的模型选择、思考控制、会话恢复、图片输入、工具桥接和界面体验。

---

##### 1. 项目定位与核心用途

该项目是一个 **pi provider extension**，通过本地 `@cursor/sdk` agent runtime，让 pi 可以运行 Cursor 模型。

关键能力包括：

- 在 pi 中使用 Cursor 模型，例如：
  ```bash
  pi --model cursor/composer-2.5
  ```
- 支持 pi 原生 `/model` 模型切换。
- 支持 Cursor SDK 暴露的 thinking / reasoning 控制。
- 支持 fast mode、plan mode。
- 支持图片输入。
- 支持通过本地 MCP 桥接调用 pi 工具。
- 不依赖全局安装 `@cursor/sdk`，项目内固定依赖：
  - `@cursor/sdk@1.0.16`

当前验证基线：

- `pi 0.78.0`
- `Cursor SDK 1.0.16`

最低要求：

- Node.js `22.19+`
- pi `0.76.0+`

---

##### 2. 安装与快速开始

可以通过 npm 或 GitHub 安装：

```bash
pi install npm:pi-cursor-sdk
```

或：

```bash
pi install https://github.com/fitchmultz/pi-cursor-sdk
```

启动 Cursor 模型：

```bash
pi --model cursor/composer-2.5
```

首次使用需要配置 Cursor SDK API Key：

1. 在 pi 中运行：
   ```text
   /login
   ```
2. 选择 `Use an API key`
3. 选择 `Cursor`
4. 粘贴 Cursor SDK API Key

如果 pi 启动时还没有 key，登录后可以运行：

```text
/cursor-refresh-models
```

刷新完整的 Cursor 在线模型目录，无需重启 pi。

---

##### 3. API Key 与认证方式

该扩展 **不会复用** Cursor Agent CLI、Cursor Desktop 登录状态或 Cursor 订阅 OAuth 状态。

支持三种认证来源，优先级为：

1. 命令行参数：
   ```bash
   pi --api-key "your-key" --model cursor/composer-2.5
   ```
2. pi 原生保存的 key：
   ```text
   ~/.pi/agent/auth.json
   ```
3. 环境变量：
   ```bash
   export CURSOR_API_KEY="your-key"
   ```

推荐方式是通过 `/login` 保存 API Key。

注意：

- Cursor SDK 需要的是 **Cursor Dashboard → Integrations** 中的用户 API Key，或 Team settings 中的 service account API Key。
- Team Admin API Key 不受 Cursor SDK 支持。
- 不要把 API Key 存到：
  ```text
  ~/.pi/agent/cursor-sdk.json
  ```
  该文件只用于保存非敏感扩展状态，例如 fast mode 默认值。

---

##### 4. 模型发现、缓存与备用模型

扩展会通过 Cursor SDK 拉取模型目录，并缓存在本地：

```text
~/.pi/agent/cursor-sdk-model-list.json
```

缓存特性：

- 默认缓存时间：`24 小时`
- 文件权限：`0600`
- 使用 API Key 指纹作为缓存键
- 不保存 API Key 本身

可配置缓存时间：

```bash
PI_CURSOR_SDK_MODEL_CACHE_TTL_MS=3600000 pi --model cursor/composer-2.5
```

禁用缓存：

```bash
PI_CURSOR_SDK_DISABLE_MODEL_CACHE=1 pi --model cursor/composer-2.5
```

如果没有 key、模型发现失败或 Cursor 网络不可达，扩展会注册内置 fallback 模型快照。

fallback 模型包括：

- Composer 2.5
- Composer 2
- GPT
- Claude
- Gemini
- Grok
- Kimi
- 其他 Cursor SDK 已审核模型

但实际运行 Cursor 模型仍然需要有效 API Key。

列出 Cursor 模型：

```bash
pi --list-models cursor
```

##### 5. 模型 ID 与上下文窗口

示例模型 ID：

```bash
pi --model cursor/composer-2.5
pi --model cursor/gpt-5.5@1m
pi --model cursor/gpt-5.5@272k
pi --model cursor/claude-opus-4-8@300k
```

模型 ID 含义：

- `cursor/...`：由该扩展注册的 Cursor provider
- `@1m`、`@272k`、`@300k`：上下文窗口变体
- `:medium`、`:high`、`:xhigh`：pi thinking level 后缀

例如：

```bash
pi --model cursor/gpt-5.5@1m:medium
pi --model cursor/gpt-5.5@272k:xhigh
```

也可以用参数指定 thinking：

```bash
pi --model cursor/gpt-5.5@1m --thinking medium
```

##### 6. Thinking / Reasoning 支持

项目说明中强调：所有 Cursor SDK 模型都应视为“具备思考能力”，但 pi 是否能控制 thinking level 取决于 Cursor SDK 是否暴露相关参数。

pi 可映射的 Cursor SDK 参数包括：

- `reasoning=none|low|medium|high|extra-high`
- `effort=low|medium|high|xhigh|max`
- `thinking=false|true`

如果 `pi --list-models` 中显示：

```text
thinking=no
```

并不表示模型不能思考，只表示 pi 不能通过 `--thinking`、`:medium` 后缀或快捷键控制它的思考级别。

##### 7. Fast Mode 与 Cursor Mode

###### Fast Mode

可以用命令开启或关闭：

```bash
pi --model cursor/gpt-5.5@1m --cursor-fast -p "Say ok only"
pi --model cursor/composer-2.5 --cursor-no-fast -p "Say ok only"
```

也可以在交互模式中使用：

```text
/cursor-fast
```

fast 偏好会按 Cursor base model 记住，并保存到：

```text
~/.pi/agent/cursor-sdk.json
```

Composer 2 和 Composer 2.5 可能默认启用 fast。若想单次关闭：

```bash
--cursor-no-fast
```

###### Cursor SDK Mode

默认模式是：

```text
agent
```

支持切换为 plan：

```bash
pi --model cursor/composer-2.5 --cursor-mode plan
```

交互中可用：

```text
/cursor-mode agent
/cursor-mode plan
```

页脚状态示例：

```text
cursor fast
cursor plan
cursor fast · plan
```

需要注意：Cursor SDK 的 plan mode 只影响 Cursor 输出和计划活动，不等同于 pi 自己的 plan-mode 扩展、todo 或工具状态。

##### 8. 图片输入支持

该扩展会把最新用户消息中的图片转发给 Cursor。

限制：

- 只转发最新消息中的图片。
- 历史图片不会保留在 transcript 中。
- 历史图片会显示为：
  ```text
  [image omitted from transcript]
  ```

因此，如果后续问题还需要引用之前的图片，需要重新附图或用文字描述图片内容。

##### 9. pi 工具桥接与 Cursor 工具体系

Cursor 运行时有两套工具表面：

###### 1. Cursor 原生工具表面

包括：

- Cursor local-agent 工具
- Cursor settings
- Cursor plugins
- Cursor MCP servers

这些由 Cursor SDK local agent 自己管理。

###### 2. pi 工具桥接表面

`pi-cursor-sdk` 可以通过本地 loopback MCP bridge，把当前 pi 会话中可桥接的活跃工具暴露给 Cursor。

特点：

- 每次 Cursor run 开始时，从 pi 获取工具快照：
  - `pi.getActiveTools()`
  - `pi.getAllTools()`
- Cursor 看到的工具名会做防冲突处理，例如：
  ```text
  pi__sem_reindex
  ```
- pi UI 中仍使用真实工具名，例如：
  ```text
  sem_reindex
  ```
- 桥接不会直接调用 pi 工具的 `execute()`，而是通过 pi 的正常 toolCall / toolResult 流程。

默认隐藏与 Cursor 原生工具重叠的 pi 内置工具：

- `read`
- `bash`
- `write`
- `edit`
- `grep`
- `find`
- `ls`

如果确实想暴露这些重叠工具：

```bash
PI_CURSOR_EXPOSE_BUILTIN_TOOLS=1 pi --model cursor/composer-2.5
```

禁用 pi 工具桥接：

```bash
PI_CURSOR_PI_TOOL_BRIDGE=0 pi --model cursor/composer-2.5
```

---

##### 10. MCP 超时与桥接调试

Cursor SDK 默认 MCP 协议超时为 `60 秒`。该扩展进行了调整：

- MCP `callTool` 默认扩展到 `3600 秒`
- MCP 初始化 / listTools 首次连接默认缩短到 `10 秒`

可自定义工具调用超时：

```bash
PI_CURSOR_MCP_TOOL_TIMEOUT_SECONDS=7200 pi --model cursor/composer-2.5
```

或：

```bash
PI_CURSOR_MCP_TOOL_TIMEOUT_MS=7200000 pi --model cursor/composer-2.5
```

自定义首次连接超时：

```bash
PI_CURSOR_MCP_CONNECT_TIMEOUT_SECONDS=5 pi --model cursor/composer-2.5
```

开启桥接诊断日志：

```bash
PI_CURSOR_PI_TOOL_BRIDGE_DEBUG=1 pi --model cursor/composer-2.5
```

诊断日志会输出到 stderr，前缀为：

```text
[pi-cursor-sdk:bridge]
```

但日志经过清洗，不应包含 API Key、token、cookie、文件内容、stdout/stderr 原始负载等敏感信息。

---

##### 11. Cursor 原生活动回放

Cursor native tool replay 是一个 **显示增强功能**。

它可以在 pi 中显示 Cursor SDK 记录的活动卡片，例如工具调用、搜索或计划活动。

但这些 replay card 是只读的：

- 不会重新运行 Cursor 命令
- 不会重新应用 Cursor 编辑
- 不会调用 MCP server
- 不会修改 pi 状态

部分 Cursor web search / web fetch 活动只有在 Cursor SDK 暴露了可回放数据时才能显示。若 SDK 没有提供完成的 tool-call payload，pi 无法生成对应工具卡片。

---

##### 12. Cursor 设置来源

默认情况下，扩展会加载全部 Cursor setting sources：

```text
PI_CURSOR_SETTING_SOURCES=all
```

这意味着会加载：

- Cursor MCP servers
- plugin tools
- project settings
- user settings
- 其他 Cursor 原生能力

可以缩小范围：

```bash
PI_CURSOR_SETTING_SOURCES=project,user,plugins pi --model cursor/composer-2.5
```

完全禁用：

```bash
PI_CURSOR_SETTING_SOURCES=none pi --model cursor/composer-2.5
```

如果某些 MCP server 很慢或不可用，首次回复前可能会被其连接过程拖慢。可以通过缩短连接超时或禁用相关 setting sources 来规避。

---

##### 13. 会话复用与运行状态

在同一个 pi session 中，扩展会尽量复用一个 Cursor SDK agent，以支持多轮对话和工具使用。

会在以下情况重新创建 agent：

- 上下文发生分歧
- 会话压缩后
- `/tree` 导航后
- API Key 变化
- send 出错后
- session 关闭时

对于桥接的 pi 工具，工具结果会回传到同一个实时 Cursor SDK run，而不是新建 Agent，除非该 run 已被释放、取消或中止。

---

##### 14. 主要限制

该扩展的边界很明确：

- 只支持 **本地 Cursor SDK agents**
- 不使用 Cursor cloud agents
- 不支持云端 pi 工具桥接
- Cursor native replay 只是显示，不会执行动作
- Cursor plan / todo 活动不是 pi 的 plan-mode 或 todo 控制
- Cursor SDK 模型元数据目前不直接暴露输出 token 限制
- pi 中显示的 token usage 是近似值

此外，Max Mode 不是手动 pi 变体。Cursor SDK 可能会自动为需要的模型启用 Max Mode。

##### 15. 常见问题与排查

###### 看不到完整 Cursor 模型

可能原因：

- 没有配置 Cursor SDK API Key
- API Key 无效
- 模型发现失败
- 当前显示的是 fallback 模型

处理方式：

```text
/login
```

配置 key 后运行：

```text
/cursor-refresh-models
```

###### 网络错误

例如：

```text
ConnectError: read ETIMEDOUT
ConnectError: [aborted] read ECONNRESET
```

扩展会显示经过清洗的重试提示，而不是让 pi 崩溃。

建议检查网络后重试。

###### fast / plan 状态怎么看

如果页脚没有：

```text
cursor fast
```

说明 fast mode 当前关闭。

如果页脚没有：

```text
cursor plan
```

说明 Cursor SDK mode 是默认的 agent mode。

###### Cursor MCP 工具没出现

可能原因：

- Cursor 中未配置该 MCP server

##### 6. 模型发现与缓存机制

扩展按以下优先级解析 API Key：

1. `--api-key`
2. `~/.pi/agent/auth.json` 中保存的 Cursor Key
3. `CURSOR_API_KEY`

为减少每次启动时请求 Cursor 模型目录，模型列表会缓存在：

```text
~/.pi/agent/cursor-sdk-model-list.json
```

特点：

- 文件权限为 `0600`；
- 以 API Key 指纹作为键；
- 不保存 API Key 本身；
- 默认缓存时间为 `24 小时`，即 `86400000 ms`。

修改缓存 TTL：

```bash
PI_CURSOR_SDK_MODEL_CACHE_TTL_MS=3600000 pi --model cursor/composer-2-5
```

禁用缓存，始终实时发现模型：

```bash
PI_CURSOR_SDK_DISABLE_MODEL_CACHE=1 pi --model cursor/composer-2-5
```

手动刷新模型目录：

```text
/cursor-refresh-models
```

##### 7. 模型选择与模型 ID 规则

列出 Cursor 模型：


```bash
pi --model cursor/composer-2-5
pi --model cursor/gpt-5.5@1m
pi --model cursor/gpt-5.5@272k
pi --model cursor/claude-opus-4-8@300k
```

模型 ID 含义：

- `cursor/...`：由该扩展注册的 Cursor 提供方；
- `@1m`、`@272k`、`@300k`：上下文窗口变体；
- `:medium`、`:high`、`:xhigh`：pi 的思考级别后缀。

带思考控制的示例：

```bash
pi --model cursor/gpt-5.5@1m:medium
pi --model cursor/gpt-5.5@272k:xhigh
pi --model cursor/gpt-5.5@1m --thinking medium
```

##### 8. 思考能力支持

扩展认为所有 Cursor SDK 模型都可能具备思考能力，但 `pi --list-models` 中的 `thinking` 列含义更窄：

- `thinking=yes`：pi 可以控制该模型的 Cursor SDK 思考参数；
- `thinking=no`：pi 不能通过 `--thinking`、模型后缀或快捷键控制思考级别。

这并不代表模型不能思考。

pi 的思考控制会映射到 Cursor SDK 暴露的参数，例如：

- `reasoning`：无、低、中、高、极高；
- `effort`：低、中、高、超高、最大；
- `thinking`：`false` / `true`。

对于部分 Claude 模型，如果同时有 `thinking` 和 `effort`：

- 当 pi 的 thinking 关闭时，会发送 `thinking=false`；
- 同时省略 `effort`。

###### Fast 模式

可单次关闭：

- 当前会话中；
- 全局文件 `~/.pi/agent/cursor-sdk.json` 中。

```bash
pi --model cursor/composer-2-5 --cursor-mode agent
```

```text

/cursor-mode plan
/cursor-mode
```

- Cursor SDK 的 `plan` 模式只影响 Cursor 运行方式；
- 它不会驱动 pi 自身的计划模式、pi 待办事项或工具状态。

##### 11. pi 工具与 Cursor 工具桥接

该扩展提供两套工具界面：

###### Cursor 原生工具界面

由 Cursor SDK 本地代理控制，包括：

- Cursor 本地代理工具；
- Cursor 设置；
- Cursor 插件；
- Cursor MCP 服务器。

###### pi 桥接工具界面

扩展通过本地回环 MCP 桥接，把当前 pi 会话中的可桥接工具暴露给 Cursor。

特点：

- 使用 `127.0.0.1` 本地 MCP 端点；
- 只暴露当前活跃且可桥接的 pi 工具；
- Cursor 看到的工具名类似 `pi__sem_reindex`；
- pi 内部仍使用真实工具名，例如 `sem_reindex`；
- 桥接不会直接调用 pi 工具的 `execute()`，而是通过 pi 的标准 `toolCall` / `toolResult` 流程完成。

默认隐藏与 Cursor 原生工具重叠的 pi 内置工具：

- `read`
- `bash`
- `write`
- `edit`
- `grep`
- `find`
- `ls`

如需暴露这些重叠工具：

```bash
PI_CURSOR_EXPOSE_BUILTIN_TOOLS=1 pi --model cursor/composer-2-5
```

禁用 pi 工具桥接：

```bash
PI_CURSOR_PI_TOOL_BRIDGE=0 pi --model cursor/composer-2-5
```

##### 12. MCP 超时与桥接控制

默认行为：

- Cursor SDK 原本 MCP 工具调用超时为 `60 秒`；
- 该扩展将 `callTool` 超时提高到 `3600 秒`；
- 首次 MCP `initialize/listTools` 超时缩短到 `10 秒`，避免不可用 MCP 服务器长时间阻塞。

修改工具调用超时：

```bash
PI_CURSOR_MCP_TOOL_TIMEOUT_SECONDS=7200 pi --model cursor/composer-2-5
```

或：

```bash
PI_CURSOR_MCP_TOOL_TIMEOUT_MS=7200000 pi --model cursor/composer-2-5
```

修改连接初始化超时：

```bash
PI_CURSOR_MCP_CONNECT_TIMEOUT_SECONDS=5 pi --model cursor/composer-2-5
```

或：

```bash
PI_CURSOR_MCP_CONNECT_TIMEOUT_MS=5000 pi --model cursor/composer-2-5
```

开启桥接调试日志：

```bash
PI_CURSOR_PI_TOOL_BRIDGE_DEBUG=1 pi --model cursor/composer-2-5
```

调试日志会输出经过清理的 JSONL，不应包含 API Key、Cookie、令牌、文件内容等敏感信息。但如果工具名本身敏感，不建议开启或分享日志。

##### 14. 使用限制与重要行为

###### 仅支持本地 Cursor SDK 代理

该扩展不使用 Cursor 云代理。

原因是云端 pi 工具桥接需要额外设计：

- 独立认证；
- 远程传输；
- 生命周期管理；
- 远程信任边界。

###### Cursor Agent 可复用

在同一个 pi 会话中，扩展会尽量复用 Cursor SDK Agent。

但以下情况会重新创建 Agent：

- 上下文不匹配；
- 会话压缩；
- `/tree` 导航；
- API Key 改变；
- 发送错误；
- 会话关闭；
- 运行被释放、中止或取消。

###### 最终助手文本取最后一个非空文本段

Composer 响应中可能包含：

- 早期进度文本；
- 思考内容；
- 工具元数据；
- 最终回答文本。

如果程序需要最终答案，应从消息末尾向前找最后一个非空 `text`，而不是取第一个文本段。

###### Token 用量是近似值

Cursor SDK 的使用事件包含内部代理、工具、缓存等工作，因此扩展不会原样复制 Cursor SDK 的 token 计数。

pi 中展示的是近似的会话输入 / 输出活动量。

###### 看到回退模型或认证失败

- 没有配置 Cursor SDK API Key；
- API Key 无效；
- 误以为 Cursor 桌面端登录可复用。


- `ConnectError: read ETIMEDOUT`
- `ConnectError: [aborted] read ECONNRESET`

pi 扩展开关和 pi 的 MCP 目录不控制 Cursor 环境 MCP。

Cursor 本地代理会从 Cursor 设置源加载 MCP，例如：

如需移除或修改，应调整 Cursor MCP 设置，并重启 pi 会话。

|---|---|
| 模型目录缓存 | 减少启动等待和网络依赖 |
| API key 指纹做缓存 key | 避免泄露密钥，同时区分不同账户权限 |
| fallback models | 即使认证未完成，也让用户能看到可用路径 |
| 手动刷新命令 | 用户登录后无需重启 |
| 无最高 pi 版本限制 | 减少升级阻塞 |

可迁移启发：

> 对依赖第三方模型/平台的 AI 产品，应设计“实时发现 + 本地缓存 + 降级快照 + 手动刷新”的模型目录机制。

---

###### 2. 认证设计：不要复用模糊状态，要建立明确凭证边界

项目明确说明：

- 不复用 Cursor 桌面登录
- 不复用 Cursor Agent CLI 登录
- 不复用 OAuth/subscription 状态
- 必须使用 Cursor SDK API key
- key 可来自：
  - pi `/login`
  - `CURSOR_API_KEY`
  - `--api-key`

这体现了一个重要原则：

> 对 Agent 工具系统来说，认证必须可解释、可审计、可重复，不应依赖隐式登录状态。

尤其在商业系统中，如果凭证来源混乱，会带来：

- 用户不知道哪个账号在执行
- 权限边界不清
- 团队计费不透明
- 安全事故难追踪
- debug 成本极高

---

###### 3. 工具桥接：Agent 产品的核心系统设计

pi-cursor-sdk 把 pi 工具通过本地 loopback MCP 暴露给 Cursor Agent：

- Cursor 看到的是 `pi__tool_name`
- pi 实际执行仍用原工具名
- 桥接层不直接调用工具 `execute()`
- 而是发出标准 pi `toolCall`
- 等待 pi `toolResult`
- 再把结果传回同一个 Cursor SDK run

这个设计很关键。

它没有绕过 pi 的原生工具生命周期，而是尊重原系统的：

- 权限确认
- 工具卡片
- 渲染器
- hooks
- 历史记录
- 中止行为
- 用户可见状态

可迁移原则：

> 做 Agent 工具桥接时，不要直接调用底层函数，而要接入宿主系统的标准工具生命周期。

否则会破坏审计、权限、UI、一致性和安全边界。

---

###### 4. 重叠工具默认隐藏：避免双工具系统冲突

项目默认隐藏这些 pi 工具：

- `read`
- `bash`
- `write`
- `edit`
- `grep`
- `find`
- `ls`

原因是 Cursor 本地 Agent 已经有原生等效工具。

这背后的产品判断是：

> 当两个 Agent 系统都有类似工具时，不要盲目全部暴露，否则模型会混淆“该调用谁”。

这对多 Agent、多工具系统非常关键。  
工具越多并不一定越强，可能导致：

- 调用路径不稳定
- 权限边界模糊
- 重复执行
- UI 卡片混乱
- 调试困难
- 模型选择错误工具

因此该项目默认隐藏重叠工具，只暴露扩展/自定义工具。

---

###### 5. fast / plan / thinking 被分层处理

项目区分了三类状态：

| 类型 | 是否模型 ID 的一部分 | 说明 |
|---|---:|---|
| context window | 是 | 会影响 pi 原生 `contextWindow` |
| thinking level | 部分是 | 可通过后缀或 `--thinking` 控制 |
| fast mode | 否 | Cursor 状态，不是模型身份 |
| Cursor mode：agent/plan | 否 | Cursor SDK 对话模式，不等同于 pi plan mode |

这是一个很好的抽象设计。

不是所有参数都应该塞进模型 ID。  
只有会影响系统级能力描述、上下文窗口、调度策略的，才适合成为模型变体。

可迁移原则：

> 在设计 AI 产品的模型选择器时，要区分“模型身份”“运行偏好”“会话状态”“一次性参数”。

否则用户会面对爆炸式模型列表，例如：

- `gpt-x-fast`
- `gpt-x-slow`
- `gpt-x-plan`
- `gpt-x-thinking-high`
- `gpt-x-thinking-high-fast-plan`

这会让产品不可用。

---

###### 6. 工具回放与真实执行必须严格区分

README 多次强调：

- Cursor 原生工具 replay card 只是展示
- 不会重新执行命令
- 不会重新应用编辑
- 不会调用 MCP
- 不会修改 pi 状态

这对 AI Agent 产品非常关键。

因为用户看到“工具卡片”时，天然会以为系统执行了某些操作。  
如果 replay、transcript、actual execution 混在一起，会引发严重误解。

可迁移原则：

> AI 产品的 UI 必须明确区分“模型声称做了什么”“系统记录显示做过什么”“当前真实执行了什么”。

##### 四、反方与张力

###### 1. 集成越深，依赖越重

pi-cursor-sdk 的价值来自深度接入 Cursor SDK，但风险也来自这里：

- Cursor SDK 是闭源边界
- 依赖特定版本 `@cursor/sdk@1.0.17`
- SDK 事件可能不完整
- 某些 Web Search 活动不会实时暴露
- MCP 行为受 Cursor 本地代理影响
- Max Mode、输出 token 等元数据不完全透明

张力：

> 深度集成能带来体验优势，但也会把产品可靠性绑定在第三方 SDK 的不透明行为上。

商业产品要考虑：

- 是否能接受不可控依赖？
- 是否有降级策略？
- 是否有替代 provider？
- 是否能观测第三方 SDK 行为？
- 用户出问题时是谁负责？

---

###### 2. 本地桥接增强能力，也扩大安全面

本地 MCP bridge 能让 Cursor 调用 pi 工具，这是强能力，但也带来风险：

- 工具权限边界更复杂
- 名称冲突可能引发误调用
- 本地端口暴露需要 token 化
- 调试日志可能泄漏工具名称
- 长超时工具可能造成资源占用
- Cursor 原生 MCP 与 pi MCP 目录不一致，用户容易误解

张力：

> 工具互操作越强，越需要权限、审计、命名空间、可见性和回滚机制。

项目提供了这些缓解手段：

- 默认只走 127.0.0.1
- token 化 MCP endpoint
- 默认隐藏重叠工具
- `PI_CURSOR_PI_TOOL_BRIDGE=0` 可禁用桥接
- 调试日志脱敏
- 工具命名加 `pi__` 前缀
- 不直接调用 pi 工具 execute

---

###### 3. 用户体验一致性与真实系统复杂性之间的冲突

pi 试图保留：

- 原生模型选择器
- 原生 thinking 控制
- 默认页脚
- 工具卡片
- 会话恢复
- 上下文显示

但 Cursor SDK 又有自己的：

- fast mode
- plan mode
- local tools
- MCP servers
- settings sources
- replay transcript
- model metadata

两套系统重叠，会产生认知负担。

例如：

- Cursor plan mode 不等于 pi plan mode
- Cursor fast 不是模型变体
- pi `thinking=no` 不代表模型不会思考
- Cursor 原生工具卡片不代表当前重新执行
- pi MCP 目录不控制 Cursor MCP 环境

张力：

> 为了保持用户熟悉体验，系统必须隐藏复杂性；但为了可调试和可信，又必须暴露足够细节。

这是所有 AI Agent 产品都会遇到的核心难题。

---

###### 4. 流式体验与事件完整性之间的冲突

README 提到某些 Cursor web search 事件无法实时暴露，只能在 `run.wait()` 后从 transcript 重建。

如果为了顺序完美，可以缓冲所有助手文本，等工具卡片重建后再显示。  
但项目选择不这么做，因为会破坏流式体验。

这是典型产品取舍：

| 选择 | 优点 | 缺点 |
|---|---|---|
| 实时流式输出 | 用户感知快 | 工具卡片可能滞后 |
| 完成后统一渲染 | 顺序更美观 | 等待时间长，像卡住 |

项目选择优先流式体验。

可迁移原则：

> 对 Agent 产品来说，实时感通常比日志顺序完美更重要，但必须解释延迟卡片的原因。

##### 五、情境化落地

###### 场景 1：你在做一个 AI 编程助手

可以借鉴 pi-cursor-sdk 的架构：

```text
你的产品 UI / CLI
    ↓
模型 Provider 抽象层
    ↓
第三方 Agent Runtime，例如 Cursor SDK / Claude Code / OpenAI Agents
    ↓
本地工具系统 / MCP / 项目上下文
    ↓
统一工具卡片、权限、日志、会话恢复
```

关键落地动作：

1. 不要只做模型 API wrapper。
2. 把第三方 runtime 当成一个独立执行环境接入。
3. 为每个 runtime 设计 provider adapter。
4. 工具调用必须接入你自己的权限和 UI 生命周期。
5. 模型能力、运行模式、上下文窗口要显式建模。
6. 提供 fallback、缓存、debug、回滚开关。

---

###### 场景 2：你在做企业内部 Agent 平台

你可以把该项目的方法迁移为“多 Agent 运行时网关”：

```text
企业 Agent Gateway
    ├── OpenAI Provider
    ├── Anthropic Provider
    ├── Cursor Local Agent Provider
    ├── 内部代码工具 Provider
    ├── 内部知识库 MCP
    └── 审计 / 权限 / 成本 / 会话层
```

尤其值得借鉴：

- 工具 namespace，例如 `internal__jira_create`
- 默认隐藏高风险或重复工具
- 所有工具调用必须经过统一审计
- replay 与 execute 分离
- 密钥来源分层
- 模型目录缓存
- 跨平台 smoke test
- 调试日志脱敏
- 长任务超时可配置

企业 Agent 平台最怕的是“模型偷偷调用了某个工具但没人知道”。  
这个项目的设计重点刚好是在降低这种风险。

---

###### 场景 3：你在做 AI IDE 或开发者工具

可直接迁移的产品能力：

###### 模型选择器设计

不要只列模型名，而要展示：

- provider
- context window
- thinking controllable
- fast support
- plan support
- image input support
- tool compatibility
- fallback/live 状态

###### 状态栏设计

仅显示用户当前需要知道的状态：

```text
cursor fast
cursor plan
cursor fast · plan
```

默认状态不显示，避免噪声。

###### Debug 体验

提供命令：

```text
/tools
/provider-debug
/refresh-models
/show-setting-sources
/disable-bridge
```

让高级用户能自救，而不是只能报 bug。

---

###### 场景 4：你在构建可商业化的 AI Agent SaaS

虽然 pi-cursor-sdk 是本地扩展，但商业 SaaS 也可以借鉴其思想。

尤其是三层能力：

```text
体验层：模型选择、流式输出、工具卡片、会话恢复
执行层：Agent runtime、工具调用、MCP、上下文
治理层：认证、权限、审计、缓存、错误处理、调试、回滚
```

很多 AI SaaS 只做了体验层，demo 很漂亮，但一进入企业场景就崩：

- 权限不可控
- 工具不可审计
- 出错无法复现
- 模型目录变化不可控
- 第三方服务失败没有降级
- 本地/云端上下文混乱
- 不知道哪个 Agent 做了什么

该项目的价值在于展示了一个更工程化的方向：

> AI Agent 商业系统的护城河，不是接入更多模型，而是把模型、工具、上下文、权限、状态和调试做成可靠系统。

---

##### 六、最值得带走的 10 条原则

1. **模型不是产品，Agent Runtime 才是产品化核心。**
2. **不要强行替换已有生态，优先设计桥接层。**
3. **工具调用必须走宿主系统生命周期，不能绕过权限与审计。**
4. **模型身份、运行模式、上下文窗口、思考级别要分层建模。**
5. **第三方模型目录要有实时发现、缓存、fallback 和手动刷新。**
6. **认证状态必须显式，不要依赖桌面登录或模糊 OAuth 状态。**
7. **工具回放不等于工具执行，UI 必须清晰区分。**
8. **默认隐藏重叠工具，避免模型在多工具系统中混淆。**
9. **Agent 产品的质量壁垒在错误处理、脱敏日志、跨平台测试和回滚机制。**
10. **深度集成带来体验优势，也带来第三方 SDK 不透明依赖，必须设计降级和边界。**
