## 分析要点

- **核心高价值点**：将并行智能体工程建立在任务隔离、操作系统级推送锁、全局危险操作护栏和生产数据库只读权限之上，可显著降低规模化协作风险。
- **留存建议**：保留其中可迁移的工作流、安全隔离和协作方法，具体工具与订阅信息需另行核验（包含工作树隔离、跨模型审查、技能固化、权限护栏、ADR和生产库只读访问等可复用实践。）

**知识要点**

- 单步重复操作适合固化为文本片段，多步骤重复流程适合封装为可调用技能。
- 中大型项目可用Git工作树隔离并行智能体，并通过锁机制串行化合并、验证、推送和部署。
- 重要架构决策应写入ADR，记录决定、原因和当时状态，帮助后续智能体理解代码中无法直接体现的背景。

**行动项**

- 为智能体配置磁盘清理、Git历史覆盖和密码管理器访问等危险操作护栏。
- 选择一次中型代码变更，尝试用不同模型实现与审查，并合并去重审查结果。
- 为生产数据库创建只读角色，并仅向智能体开放完成现实核查所需的最小权限。

**David Ondrej**

### 智能体工程配置（经过2000+小时实践）

过去三年里，我投入了远超 2000 小时的时间与 AI 一起编程，并亲自采访了智能体工程领域中最具生产力的一些人物。

以下是我截至2026年第三季度完整的智能体工程配置。

#### 界面

这意味着 UI / CLI 是你与智能体交互的方式。我的主要界面是 bb。

它是开源的，完全免费，并且允许你在单个 GUI 中使用任何订阅、任何智能体、任何模型。Codex、Claude Code、Pi、Cursor CLI、OpenCode、Grok Build、Hermes，全部都在同一个 UI 中。

像 Codex 或 Cursor 这类应用的问题在于，它们只允许使用自己的模型和自己的订阅。目标是花最少的钱获得最多的令牌。

您喜欢 Codex 或 Cursor 应用中的所有功能都包含在 bb 中，而且它每周都在改进（此外，它完全开源且 100%免费使用）。

我经常使用的另一个工具是 cmux。

当你启动一个新的 cmux 工作区时，你可以像在 tmux 中一样分割屏幕（这也是它名字相似的原因），在每个窗格中启动不同的终端，并且还内置了浏览器。

cmux 的不足之处在于当你有很多代理和工作区时。左侧边栏确实不是合适的工具。对于同时处理几件事来说还可以，但对于大规模严肃的智能体工程工作来说，它并不是最佳选择。

我使用 Ghostty 作为我的终端，因为它非常快速且原生。

在 Ghostty 中，你可以运行 Herdr，它基本上就是 tmux，但面向智能体，是智能体的后端运行时。非常精简，非常轻量，常驻于终端中，当智能体完成任务时，其状态会显示在左侧：完成、空闲、阻塞、运行中。

跟踪 AI 智能体的状态至关重要。我的预测是，在未来 3 到 6 个月内，这种“智能体状态跟踪”将变得越来越重要，因为你将不再与单个智能体对话。你将与一个管理众多工作智能体的管理智能体对话。

最后一个我必须提到的界面是 Corral，这是我自己开发的产品。

与其在代理完成时随意切换（在 Herdr 中，没有真正的顺序），每个代理都有优先级。就像任务有不同的优先级/重要程度一样。当 P1 代理完成时，他会排到最前面。当 P1 代理已经运行完毕时，你绝不应该去响应 P4 代理。（是的……我确实需要把 corral 开源。还没顾上呢。）

#### 模型与订阅

你想要用最少的钱获得最多的 token。这应该是每一位 Agentic 工程师的主要目标之一（在把事情搞定之后）。

目前主要有4种订阅方案，而且没错……两个月后这可能就完全不一样了。

目前最划算的交易是 OpenCode Go。它只要 10 美元，就能让你使用 Kimi K3、Grok 4.6、GLM 5.3、DeepSeek V4 Pro 以及许多其他模型……但它没有 Fable 5 和 GPT-5.6 Sol 这类顶级模型（而且使用限制也比较小）

所以，如果你预算稍微宽裕一点，可以这样做：

- 30 美元——购买 OpenCode Go + ChatGPT Plus（20 美元）
- 50 美元——在此基础上，再加 20 美元的 Claude Code 订阅。
- $70——再加上 Cursor 每月 20 美元，你就拥有了所有订阅中最低的档位。
- $110——OpenCode 加上其中一个高级套餐。ChatGPT 的 100 美元套餐会比 Claude 更划算。事实就是如此。OpenAI 拥有更多的算力，他们更愿意为此提供补贴。
- $210——直接两个100美元的套餐都买了吧。
- 如果你真的非常认真（像我一样），那就把所有的 200 美元套餐（Codex、Claude、Cursor）都拿下，因为那些是 20 倍用量，而且这些套餐给你的性价比最高。

顺便说一句……Cursor 的套餐被严重低估了。Cursor，也就是 Grok，因为 SpaceX 的收购，将会成为一个非常棒的订阅。SpaceXAI 拥有大量算力，所以他们可以玩补贴游戏。而且——我认为——Cursor/Grok 套餐给你的是 Cursor 和 Grok Bot 各自独立的额度，这简直太不可思议了。

Grok Bot 正迅速成为人们与智能体互动的新方式，所以拥有 Cursor 订阅从未像现在这样重要（不是恰饭哈哈，这是事实）。而且，新模型——Grok 4.7——马上就要来了。

无论如何， 千万不要按 API 定价付费。那是市面上最不划算的交易。直接买订阅就好。

很明显，云端代理就是未来。Cursor、Amp、Devin、Codex……这些公司都在把一切押注在云端代理上。

这是 Cursor 内部云端代理合并 PR 的占比：今年年初大约在 10-15%，现在已接近 60%。而且这是合并后的 PR，是真正被使用的东西。很快这个数字会达到 70%，然后是 80%，最后是 90%。

在本地机器上运行所有代理的问题在于它不具备可扩展性。你无法同时运行数百个代理。只需几个代理决定同时运行你的整个测试套件，你的电脑就会开始发出奇怪的噪音（即使是我那台价值 7000 美元的 MacBook Pro 也会吃力）。

云端代理为你提供隔离的环境、持久的会话、稳定的互联网和电力访问。如果你合上笔记本电脑，你就会失去你的会话。互联网中断几分钟，执行框架就无法自行恢复。

现有云端代理解决方案的问题在于其令人发指的生态系统锁定程度。设置环境和所有密钥需要花费大量时间，然后你就被锁定了：你的会话在那里，你受制于他们的定价，并且你把所有数据都交给了他们。即使他们不在此之上训练模型，也有太多其他方式可以利用你的数据。

解决方案是拥有你自己的服务器。而且多亏了 AI，这只需要大约 10 分钟就能设置好（说真的）。只需获取一台 VPS，在上面运行 Herdr，然后通过 SSH 连接即可。

Herdr 为您提供持久的代理会话，而 SSH 让您可以从手机、笔记本电脑等任何设备连接。您真的可以用几美元实现云端代理的 80/20 效果，而且没有锁定风险。

#### 构建您自己的云端环境

我的 VPS 使用的是 Hostinger，KVM2 套餐就足够了。这里我想强调的重点是……您不需要成为 VPS、DevOps、Linux 方面的专家，完全不需要。

只需用简单的英语与您的代理对话即可！！！

在接下来的视频中，我将全程现场演示整个搭建过程。一个 cmux 工作区，左侧面板是一个编码代理（运行 Grok 4.6 的 Cursor CLI），右侧是一个空白终端面板。

我的 cmux 技能让代理能够找到另一个面板并在其中运行命令。我亲自 SSH 登录到全新的 VPS，然后告诉代理“了解那台服务器的一切，并搭建开发环境。Herdr、Node.js、Python 3、Git”。

它在几秒钟内分析了 VPS，安装了所有内容，启动了 Herdr，然后安装了 Pi Agent，在我的 MacBook 上找到了一个 OpenRouter 密钥，并自行完成了整个设置。经过几次简短提示后，我让 Pi 运行了 GPT-5.6 Sol，并启动了第二个会话运行 Fable，两者都在云端、我自己的 VPS 上，拥有完整的 root 权限。

如果我的电脑或 Wi-Fi 出了什么问题……如果我的 MacBook 爆炸了，这些代理仍会继续运行。完整的分步演示在视频中。

还有一个关于速度的技巧……我用 SuperWhisper 来口述。你们大多数人读到这里时，打字速度大概是每分钟 40 或 50 个词。那真的很慢。

但是！你可以以每分钟 250 词以上的速度说话。一个语音 AI 工具（比如 Superwhisper、Glaido、Whispr Flow）能立刻让你的提示词发送速度快 3 到 4 倍。用起来吧，别犯傻。

#### 工具集

第一个要提到的工具是 Pi Agent，它是最厉害的。

这是最精简的工具集：只有 4 个工具，始终以 YOLO 模式运行，支持任何模型、任何提供商。非常优雅，超级可配置，这就是为什么这么多人在 Pi 之上构建。它是开源的，完全免费，只需前往

pi.dev 即可获取。不容商量。这是我放在 VPS 上的第一个工具集。

Cursor CLI。 非常被低估，因为你可以使用所有模型：Grok、GPT 模型、Anthropic 模型、Kimi。你可以标记技能，还可以预发送消息。整体来说是个很棒的工具集。

下一类工具集，我称之为“自我改进型”工具集。

最受欢迎的两个是 Hermes Agent 和 Prime Agent。这适用于你不知道自己在做什么的情况。如果一项任务有很多不确定性，需要大量摸索，那就使用自我改进型工具集，因为它会创建技能，并随着时间与你一起进步。

最后，经典之作，Claude Code 和 Codex。我给它们设置了别名。很多人每天都要敲 \`claude --dangerously-skip-permissions\`。极其缓慢，极其低效。我输入 \`cc\` 就能启动 Claude Code 并绕过权限；输入 \`cx\` 就能以 YOLO 模式启动 Codex。

你必须为经常运行的长命令创建全局别名。这是智能体工程的基本法则之一：如何在相同时间内完成更多工作？

#### 技能

我的技能仓库上个月爆火了。（参见

github.com/davidondrej/skills ）它也是完全免费、开源的，诸如此类。

与 Agentic Engineering 最相关的 SKILLs 包括：

\*(1) /total-review

- 它会运行另外两个技能，/gpt-review 和/fable-review，这两个技能会审查你刚刚用 GPT-5.6 Sol 和 Fable 5 所做的代码更改，然后将两份列表去重，合并成一份真正重要的问题清单。这就像让你所有最聪明的朋友审查你的求职申请，而他们只给你指出最大的问题。在中等至大型更改上运行它，尤其是当由不同模型构建时。如果 Grok 4.6 完成了工作，你希望一个完全不同的模型来审查它。

重要提示：任何你重复足够多次的内容都应该成为预设。

如果是单步操作，使用文本替换。我把它们做成了 Raycast 片段。“用简单英语简短回答。”“把你之前的回答变得更简单、更简短。”“暂存所有文件，写一条清晰的提交信息，推送到 GitHub。”

如果是多步骤工作流，就把它变成一个技能。

(2) /ask-then-build

- 我每天在开始任何构建之前都会使用这个技能。与其说“让这个兼容 Windows”然后让模型默默做出你之后可能会后悔的重要架构决策，不如让它带你逐一审视主要决策，并提供选项。AI 模型擅长编码，擅长实现。但它们没有品味。它们没有良好的判断力。作为人类，你需要保持对这些方面的掌控。

(3) /deepapi

- 这个技能是我用来做任何深度研究、任何爬取、任何网络相关工作的工具。Codex 和 Claude Code 自带基本的网络搜索功能，但没有爬取能力，也没有深度研究功能，而且很容易被屏蔽。运行 8 次快速网络搜索并给我前 3 个选项，爬取 Twitter，爬取 GitHub，找到 3 种联系某人的方式。我团队里的每个人都在用。必备工具。

(4) 护栏与推送锁

- 这个比较枯燥，但绝对必不可少，而且你只需要设置一次。全局代理护栏是一个工具调用前的钩子，确保你的代理永远不会清空磁盘、永远不会覆盖 Git 历史、永远不会碰你的密码管理器。还有推送锁，用于当你并行运行 15 个以上代理时：在整个系统上设置一个操作系统级的内核锁。合并、验证、推送、CI、部署、健康检查。

不要安装我所有的技能。只拿你需要的那些就行。

#### 工作树

工作树基本上是将你的主检出副本复制到一个单独的文件夹中，并在那里创建一个新的 Git 分支，这样代理就可以完全隔离地并行工作。

在小型项目中，这绝对是过度设计。保持在一个分支上，工作速度会更快。

在中等至大型项目中，你随时运行着 20-30 个以上的代理，这根本无法避免。没有工作树，代理们就会互相冲突，撤销彼此的更改，互相争斗。BB 的另一个优点：它内置了工作树功能。它记得在我的大型仓库中，我总是希望基于 origin/main 创建一个新的工作树。

#### 其他代理工程技巧

知道何时使用每种模型。

- 设计计划或启动新项目？用 Fable。它最具天才的火花。修复深层、严重的错误？用 GPT-5.6 Sol，最大推理力度。日常聊天？用 Grok 4.6 高配。智能几乎相同，但价格便宜 2 倍，速度快 2 倍。前端？用 Kimi K3。
- 当有重大新模型发布时，留出一天时间只使用那个模型。别听推特上的。自己试试。

知道何时该审查。

- 我不会对每个改动都进行全面审查。一个小的前端调整会直接上线。
- 而且绝对不要做递归审查。如果你告诉模型“找出 5 个最大的问题”，即使代码库完全没问题，它也会找出 5 个问题。这些模型会凭空捏造出想象中的 bug。

发送前。

- 通常我知道代理下一步会做什么，所以我会提前排队消息：“实施计划”、“对此运行 Fable 审查”、“现在修复那些问题”。
- 有时是2条消息，有时是6条。
- 永远不要使用不允许你预先发送消息的工具。

子代理被过度使用了。

- 很多人只是把额度浪费在它们上面。我在自己掌控时才会使用它们。我想选择子代理中运行哪个模型，因为我知道自己有哪些订阅和额度。
- 未来是一个管理者代理启动多个工作代理，但你仍然需要设计那个系统：规则、权限、以及启动子代理的条件。我不希望 Anthropic 或 OpenAI 的某个人替我做这个决定。

ADR。

- 这就是你将决策写入代码库的方式。/docs/adr 是我在任何项目中最早创建的文件夹之一。
- 每个核心架构决策都会有一个简短的文件：决定了什么、为什么这样决定，以及当时项目的状态。有些事情可以从代码中读到，但不是所有事情都能。
- 那些无法从代码中读到的内容应该被记录下来，这样未来的智能体和人类就能立刻理解为什么项目会以这种方式构建。

测试。

- 当前模型会让你的仓库被测试撑爆：单元测试、集成测试、数据库测试，哪怕是最小的仓库，毫无意义也要硬塞。
- 如果你让模型添加测试，它会加一大堆。如果你告诉它“不要加测试”，它还是会加一些，最后刚好落在合适的量上。

生产数据库访问。

- 任何有实际使用的产品都需要这样做……创建一个只读的 Postgres 角色，然后把那个权限给你的代理。
- 不要给他们写权限。只需一次不可逆的更改，你就会后悔莫及。
- 但完全没有权限也是个错误。有了只读权限，你可以对每个功能进行现实核查。这在生产环境中真的会发生吗？人们真的在使用这个功能吗？我真希望自己能早点这么做。

追踪你的智能体生产力。

- 我们刚刚在 Vectal Labs 下发布了一个新的开源仓库，名为
  [agentic-productivity](https://github.com/vectal-labs/agentic-productivity)。它可以追踪你的提交、智能体会话以及用户提示。
- 单独来看，每个指标都不够好，但把这三者结合起来并观察长期趋势，你就能看出自己是否真的在成为一名更优秀的智能体工程师。

这就是目前的现状。一个月后，情况可能就会不同。这一切都在不断变化。

#### 智能体工程配置：从 “单人对话” 走向 “多智能体生产系统”

##### 核心观点

作者基于 2000+ 小时 AI 编程实践认为，智能体工程的竞争重点正在从 “选择最强模型”，转向：

> **用更低成本调度更多智能体，并通过隔离、优先级、安全护栏和流程标准化，让它们稳定并行工作。**

未来的交互模式不再是人与单个智能体对话，而是由一个 “管理智能体” 协调大量工作智能体。

##### 一、交互与调度界面

作者的界面组合是：

- **bb**：统一管理不同订阅、智能体和模型，避免被单一平台锁定。
- **cmux**：多终端与浏览器并排操作，适合中小规模并行任务。
- **Ghostty + Herdr**：作为轻量终端和智能体运行时，跟踪运行、完成、空闲、阻塞等状态。
- **Corral**：按 P1～P4 优先级排列已完成任务，防止注意力被低价值结果抢占。

核心判断是：**当智能体数量增加后，状态跟踪和任务优先级比聊天界面本身更重要。**

##### 二、模型与订阅策略

作者主张以 “最低成本获得最多 Token” 为目标：

- 优先购买模型订阅套餐，而非按 API 调用量付费。
- 通过 OpenCode、ChatGPT、Claude、Cursor 等订阅组合覆盖不同模型。
- 重度用户可购买高档套餐，利用更高额度降低单位成本。
- 根据任务动态选择模型，而不是固定使用一个模型。

作者的模型分工建议：

| 任务 | 推荐方向 |
|---|---|
| 项目设计、方案规划 | 偏创造力和架构能力的模型 |
| 深层 Bug、复杂推理 | 高推理模型 |
| 日常开发与沟通 | 速度快、成本低的通用模型 |
| 前端开发 | 前端表现更好的专用模型 |
| 代码审查 | 使用与开发阶段不同的模型 |

这些模型名称、价格和额度变化极快，应以实时测试为准。

##### 三、云端智能体是规模化基础

本地运行多个智能体存在明显瓶颈：算力争抢、环境冲突、断网中断、设备关闭后任务停止。

云端智能体的主要价值包括：

- 环境隔离；
- 会话持久化；
- 可同时运行更多任务；
- 可从手机、电脑等多设备接入；
- 本地设备离线后仍可继续执行。

但商业云端智能体存在平台锁定、迁移成本和数据风险。作者建议采用折中方案：

> **租用 VPS，自行部署 Herdr，通过 SSH 连接，以较低成本获得大部分云端智能体能力。**

##### 四、工具选择原则

作者推荐的工具分为三类：

1. **精简型工具**：Pi Agent  
   工具少、配置灵活，支持多模型和多提供商，适合作为基础运行环境。

2. **通用编码工具**：Cursor CLI、Claude Code、Codex  
   通过命令别名减少重复输入，提高启动效率。

3. **自我改进型工具**：Hermes Agent、Prime Agent  
   适合需求不明确、需要持续探索的任务，可自动沉淀技能。

核心原则是：**重复命令做成别名，单步操作做成文本片段，多步骤流程做成技能。**

##### 五、关键技能与流程标准化

作者最常用的技能包括：

###### 1. 多模型代码审查

`/total-review`使用两个不同模型分别审查代码，再合并、去重问题清单。适合中大型改动，尤其适合 “开发模型” 和 “审查模型” 交叉验证。

###### 2. 先问清楚，再实现

`/ask-then-build`要求智能体在编码前列出关键决策和备选方案，由人类确认后再执行。

原因是：**模型擅长实现，但不一定具备产品品味和长期架构判断。**

###### 3. 深度网络研究

`/deepapi`用于搜索、抓取和深度研究，弥补普通编码智能体网络能力不足的问题。

###### 4. 安全护栏与推送锁

- 阻止删除磁盘、覆盖 Git 历史、访问密码管理器等危险行为。
- 多智能体并行时，通过系统级锁串行执行合并、测试、推送、CI 和部署。

##### 六、并行开发与工作树

Git Worktree 可让每个智能体在独立目录和分支中工作，避免互相覆盖代码。

- **小项目**：单分支更简单，Worktree 可能是过度设计。
- **中大型项目**：当同时运行 20～30 个智能体时，Worktree 几乎是必需品。

本质上，Worktree 是多智能体开发的 “环境隔离层”。

##### 七、工程实践原则

###### 审查要有边界

不是每个小改动都需要全面审查，也不要递归要求模型不断 “再找几个问题”。模型为了满足数量要求，可能制造并不存在的 Bug。

###### 提前排队消息

如果已知后续步骤，可以预先发送 “实施方案 — 审查 — 修复” 等指令，减少等待和人工切换。

###### 谨慎使用子智能体

子智能体并非越多越好。应明确：

- 何时允许启动；
- 使用哪个模型；
- 有什么权限；
- 消耗哪类额度；
- 结果如何验证。

###### 用 ADR 保存决策背景

在`/docs/adr`中记录核心架构决策，包括决定、原因和当时的项目状态。代码能表达 “怎么做”，ADR 用来解释 “为什么这样做”。

###### 控制测试数量

模型容易过度生成测试。测试应围绕真实风险和关键路径，而不是追求数量。

###### 生产数据库只开放只读权限

让智能体读取真实数据，可以验证功能是否真正被使用；但不应授予写权限，以避免不可逆事故。

###### 衡量长期生产力

同时追踪：

- 代码提交；
- 智能体会话；
- 用户提示词。

单项指标意义有限，但组合观察长期趋势，可以判断智能体工程效率是否真正提升。

##### 八、对产品与组织的启示

这套方法的本质不是 “更快写代码”，而是构建一套新的研发操作系统：

1. **模型层**：按任务路由不同模型；
2. **运行层**：云端持久运行与环境隔离；
3. **调度层**：状态跟踪、优先级和任务队列；
4. **协作层**：Worktree、审查、合并和部署；
5. **治理层**：权限、护栏、ADR 和生产数据控制；
6. **度量层**：跟踪智能体对真实交付效率的贡献。

##### 总结

作者的核心经验可以归纳为一句话：

> **智能体工程的瓶颈正在从代码生成，转移到任务编排、环境隔离、成本管理、安全治理和人类决策质量。**

真正高效的系统不是让 AI 完全自主，而是让人类掌握架构、品味和权限边界，把可重复执行的工作交给智能体。

> 注意：文章中的模型、价格、产品关系及时间预测高度时效化；“YOLO 模式”、跳过权限检查、云端 Root 权限等做法风险较高，生产环境应配合最小权限、沙箱、审计和人工审批。

文章中更成熟的一组经验，是把人的判断放在智能体最不擅长的位置：重要决策先询问再构建；架构选择写入 ADR；中大型改动由不同模型交叉审查；生产数据库只开放只读权限；危险操作通过全局护栏拦截。

这里的共同机制是：**不要依赖模型每次都“做对”，而要让系统限制它能够做错的范围。**模型可以快速实现方案，却不知道团队真正重视兼容性、维护成本还是交付速度，也无法从代码本身恢复当初决策的业务背景。ADR 因此不只是给人看的文档，也是在为未来智能体提供长期记忆。

作者对审查的提醒同样重要：审查并非越多越好。要求模型“找出五个问题”，它往往会为了满足数量而制造可疑问题。更合理的做法是按变更风险决定审查深度，并让异构模型检查彼此的盲区，而不是递归审查到看似万无一失。

##### 长期方法可信，具体结论要降权

“云端智能体合并 PR 占比从约 10%—15%升至近60%”是一个强信号，但文中只有 Cursor 内部图表，不能直接推出行业终局必然是90%。自建 VPS 也并非天然优于厂商云：它降低锁定，却把密钥管理、补丁、备份和入侵响应转交给用户；让拥有 root 权限的 Agent 自动配置环境，更需要最小权限和可复现基础设施。

同样，“永远不要按 API 付费”只适用于个人高用量、订阅允许相应使用方式的阶段。企业若需要可计量成本、服务等级、数据边界和集中审计，API 反而可能更合适。

## 口播总结（1）

### 2026-09-20 00:33:27

智能体工程真正的变化，不是模型又聪明了多少，而是工作方式正在从“和一个智能体聊天”，转向“同时管理许多智能体”。作者在两千多个小时的实践后认为，效率的关键不只是选模型，而是建立一套能并行、能恢复、可审查、有护栏的工程系统。

先说交互界面。作者主要使用一个叫 BB 的开源工具，把 Codex、Claude Code、Cursor 命令行工具等不同智能体和订阅，集中到同一个图形界面里。这样做的目的，是避免被单一厂商锁定，也方便根据任务切换模型。

但智能体一多，单纯并排打开许多终端就不够了。你必须知道每个智能体是正在运行、已经完成、处于空闲，还是遇到了阻塞。作者使用 Herdr 之类的终端工具追踪状态，还为智能体设置优先级。高优先级任务完成后，应当先处理，而不是被低价值任务不断打断。

这背后的判断是，未来人类不会逐一盯着每个工作智能体。更可能的模式，是你和一个管理智能体沟通，再由它调度许多执行任务的智能体。所以，状态、优先级、权限和调度规则，会变得和模型能力一样重要。

接下来是运行环境。作者认为，云端智能体会逐渐成为主流。根据他引用的 Cursor 内部数据，年初由云端智能体完成并最终合并的代码变更，占比大约只有百分之十到百分之十五，后来已经接近百分之六十。

本地运行的问题是无法大规模扩展。几个智能体同时跑完整测试，就可能让一台高配置电脑不堪重负。笔记本合上、网络短暂中断，也可能导致会话丢失。云端环境则可以提供隔离的运行空间、持续会话，以及稳定的网络和电力。

不过，商业云端智能体也有明显代价。环境配置、密钥、会话和数据都被放进特定平台，迁移困难，定价也受制于厂商。作者的折中方案，是租一台虚拟专用服务器，也就是 VPS，再通过安全远程连接工具 SSH 使用它。这样即使本地电脑关机，智能体仍能继续工作。

作者曾让智能体直接检查一台全新的服务器，安装 Node.js、Python、Git 和智能体运行工具，再启动多个模型会话。整个过程只需要少量自然语言指令。这个案例想说明的不是运维知识已经不重要，而是智能体可以大幅降低搭建私人云端环境的门槛。

模型和订阅的选择，也应服从同一个目标：先把事情做成，再用尽可能少的钱获得尽可能多的可用量。作者更偏好订阅，而不是按接口调用量付费。不过，他也强调，价格和套餐变化很快，具体组合可能两个月后就过时。真正稳定的原则，是不要把工作流绑定在单一模型上，并亲自测试新模型，而不是只看社交媒体上的评价。

工具配置好以后，更重要的是把重复经验固化下来。作者把单步操作做成文本快捷指令，例如让智能体简短回答，或者自动整理提交信息。多步骤流程则做成可重复调用的“技能”。

其中一个关键技能，是“先问再构建”。比如你要求软件兼容 Windows，不要让模型默默做出一连串架构决策。更好的做法，是让模型先列出关键选项，再由人类决定。作者的判断很直接：模型擅长实现，但不一定有品味和判断力。架构取舍仍然需要人类掌控。

另一个技能是交叉审查。中大型修改完成后，可以让两个不同模型分别检查，再合并并去除重复问题。如果一段代码由 Grok 完成，就尽量换另一类模型审查，减少相同盲点。不过，审查不能无限递归。你若反复要求模型找出五个问题，即使代码已经没有明显缺陷，它也可能为了完成任务而编造出五个可疑问题。

并行工作还需要隔离。中大型项目同时运行二三十个智能体时，作者会使用 Git 工作树。它相当于为每个智能体创建独立文件夹和独立分支，避免彼此覆盖或撤销修改。小项目则不必这样做，因为额外结构反而会拖慢速度。

权限控制同样不能省。作者建议设置全局护栏，禁止智能体清空磁盘、改写 Git 历史或访问密码管理器。多个智能体同时合并和部署时，还要用系统级锁，把合并、验证、推送、持续集成、部署和健康检查串行化。

生产数据库可以给智能体只读权限，但不要给写权限。完全不给权限，会失去用真实数据验证功能的机会；给了写权限，一次不可逆操作就可能造成严重后果。只读角色是在现实核查和安全之间的折中。

还有一类容易被忽略的信息，必须写进代码仓库。作者会建立“架构决策记录”，简称 ADR。每个关键决定都留下一个短文件，说明决定了什么、为什么这样决定，以及当时的项目背景。代码能告诉未来的智能体系统是怎样实现的，却不一定能解释为什么要这样实现。

最终，成熟的智能体工程不是同时打开更多聊天窗口，而是把智能体当成一个需要调度的工程团队。最值得记住的三点是：用云端和工作树实现持续、隔离的并行执行；用技能、交叉审查和架构记录沉淀判断；再用权限护栏、只读数据和部署锁控制风险。模型和工具会不断更换，但这套关于调度、复用和安全的思路，更可能长期有效。

### 2026-09-30 11:50:35

用人工智能编程，关键不只是选一个更聪明的模型，而是把任务分配、运行环境、审查和权限管理组织起来。戴维·翁德雷在投入两千多小时实践后，给出的核心经验是：让智能体承担更多执行工作，同时把重要决策和工作节奏掌握在人手里。

先看一个变化。当你只用一个智能体时，主要工作是提问、等待、看结果。但当十几个智能体同时运行，你面对的就不再是一段对话，而是一套需要调度的工作系统。

哪个任务还在运行？哪个被卡住了？哪个已经完成，等你处理？这些状态必须看得见。而且，完成顺序不等于处理顺序。一个低优先级任务先完成，不应该抢走你对重要任务的注意力。

所以，作者选择界面时，看重的不只是聊天体验。他主要使用名叫 bb 的开源工具，把不同智能体、模型和订阅放进同一个界面。他还使用 Herdr 这样的终端工具，跟踪智能体是运行中、空闲、阻塞，还是已经完成。

作者自己开发的另一个工具，则进一步按优先级排列任务。这里最值得记住的不是工具名字，而是一个原则：并行工作越多，越需要清楚的状态和优先级，而不是不停切换窗口。

不过，界面解决了调度问题，还没有解决算力问题。

几个智能体一起运行完整测试，就可能让本地电脑吃不消。作者认为，云端智能体的重要性会继续上升，因为云端可以提供隔离的环境和持续运行的会话，不必依赖你的笔记本一直开着。

文中引用了一个具体变化：在 Cursor 内部，云端智能体贡献并被合并的代码修改，占比从年初大约百分之十到十五，升到了接近百分之六十。这些不是仅仅生成出来的代码，而是已经被接受、进入项目的修改。作者把它视为云端趋势的证据，至于比例还会继续升到多高，则是他的预测。

但云端也有代价。你花时间配置环境和密钥后，会话、数据和收费方式都可能被绑定在一家平台上。

作者的替代方案，是租一台自己的虚拟服务器，在上面运行智能体，再通过安全的远程连接，从电脑或手机接入。这样，即使本地电脑断网，服务器上的任务仍能继续。这里的重点是：把任务运行的位置，与自己查看和指挥任务的位置分开。

费用也要单独考虑。在作者当时的比较中，订阅比按接口调用量付费更划算。他追求的是，在把事情做好的前提下，用较少的钱获得更多可用额度。不过，他也强调，这些套餐和模型变化很快，具体购买组合可能两个月后就不再适用。

有了运行环境，下一步才是让工作流程真正稳定下来。

作者最看重的一类流程，是先问清楚，再动手。比如，你只说一句“让这个项目兼容 Windows”，智能体就可能自行决定一系列架构选择。而这些决定，可能正是你后来最难撤回的部分。

他的做法是，在开始构建前，让智能体列出主要决策、提供选项，再由人确认。按他的判断，模型擅长实现，但重要选择不能全部交给模型默默完成。

这些选择还应该写进代码库。作者使用架构决策记录，也就是为每个核心决定留下一份简短说明：决定了什么，为什么这样决定，以及当时项目处于什么状态。代码能告诉后来的人“系统怎么运行”，却不一定能告诉他们“当初为什么这么设计”。

另一个值得固定下来的流程，是代码审查。对于中等到大型修改，作者会让不同模型分别检查，再把两份结果去重，合成真正重要的问题清单。尤其当代码由一个模型生成时，他倾向于让另一个模型审查。

但他不会对每个小改动都做全面审查，也反对无休止地反复检查。如果你要求模型“必须找出五个最大问题”，模型可能为了凑足数量，把并不存在的漏洞说成问题。

所以，审查的目标是发现真实风险，不是让问题清单越来越长。

这些重复工作，都适合做成预设。单步操作，比如简化回答、整理提交信息，可以用文本快捷片段。多步骤操作，比如先讨论方案、再实现、再审查，则可以封装成技能，也就是供智能体重复执行的一套流程。

最后，智能体越多，隔离和权限边界就越重要。

小项目只有少量并行任务时，作者认为不必把流程搞得太复杂。但在中大型项目里，如果同时运行二三十个智能体，就需要 Git 工作树。你可以把它理解为：给不同任务分配独立的工作目录和分支，避免智能体修改同一份文件，互相覆盖成果。

工作隔离之外，还要有操作护栏。作者设置了执行前检查，限制清空磁盘、覆盖代码历史、访问密码管理器等危险操作。多个智能体并行时，他还使用系统级的锁，协调合并、验证、推送和部署，避免关键操作同时发生。

生产数据库尤其需要明确边界。作者建议给智能体只读权限，而不是写入权限。这样，智能体可以核查真实使用情况，判断一个功能是否真的被用户使用，却不能直接修改生产数据。

判断这套系统有没有用，也不能只看生成了多少代码。作者会结合代码提交、智能体会话和用户提示，观察长期趋势。单个指标都不够，合起来才更有机会看出效率是否真正提高。

最值得带走的，是这三点：用状态和优先级管理并行任务，用预设和决策记录减少重复与误解，用隔离和权限边界控制风险。工具和模型会不断更换，但把人的判断放在关键位置，才是这套智能体工程方法的主线。
