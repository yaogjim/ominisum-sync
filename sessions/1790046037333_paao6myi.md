## 分析要点

- **核心高价值点**：多问题隔离需要适配底层架构：纯注意力模型可用注意力掩码，而含循环层的Qwen3.5需让各问题独立成行，再复用状态缓存，不能只靠掩码保证隔离。
- **留存建议**：精读并保留，作为本地决策模型接入、评估与选型的技术参考（提供可运行的部署示例、结构化决策接口、问题隔离机制及校准和硬件性能说明，可复用于分类、路由和评分类AI应用。）

**知识要点**

- Kev以LoRA适配器和指针头完成决策，指针头根据选项与决策位置的隐藏状态计算概率，而不是依赖生成文本标签。
- 温度校准可以改善概率质量而不改变最高概率选项；接口中的confidence也不等于实测准确率，评估时应区分准确率、Brier分数和校准误差。
- 模型选型需要同时考虑泛化与推理后端：文中Qwen3.5版本在Apple Silicon上受DeltaNet参考实现限制，低延迟场景可考虑仍保留的Qwen3版本。

**行动项**

- 按Quick Start启动Kev-4B本地服务，用示例请求验证choice、noul和score三类输出；服务无认证，保持本地访问，外部开放前添加认证。
- 使用Playground的Packed vs separate与Permute功能，在实际业务样例上检查多问题合并的一致性和选项顺序敏感性。
- 在目标硬件和业务样例上比较候选模型的延迟、准确率与概率校准表现，避免仅依据参数规模或项目汇总成绩选型。

#### Kev

Small Jev-like decision models you can train and run yourself.

Kev is a family of small decision models built on Qwen3.5 and based on the architecture described in [Jev's Architecture Unmasked](https://archerhume.com/posts/jevs-architecture-unmasked). You can use the pretrained weights or train your own. The API matches TypeSafe's [System One](https://docs.typesafe.ai/api), so you can point their Python SDK at your local server.

#### Highlights

- 0.8B, 4B, and 9B models, with training code and evaluation data.
- Yes/no (`noul`), multiple-choice (`choice`), and rating (`score`) questions in the same request.
- Questions share the input text but can't read each other.
- Runs on CUDA, ROCm, and Apple Silicon. The 4B and 9B models fit a 32 GB Mac using bf16; see Serving Performance for what to expect on a Mac.
- A web playground for trying your own inputs and checking how option order affects the answers. Or try Kev-4B and Kev-0.8B in the browser at [huggingface.co/spaces/jaredpalmer/kev](https://huggingface.co/spaces/jaredpalmer/kev), no install needed.

Kev playground

#### Quick Start

You'll need Python 3.12+ and [uv](https://docs.astral.sh/uv/).

```
git clone https://github.com/jaredpalmer/kev.git && cd kev
uv sync --extra serve
KEV_DTYPE=bf16 uv run --extra serve python -m kev.serve --run jaredpalmer/kev-4b --port 8009
```

This starts Kev-4B locally. The first run downloads the adapter and base model. `--run` also accepts a local checkpoint directory or a Hub revision, such as `jaredpalmer/kev-4b@qwen3` for the previous generation.

In another terminal, send it a ticket:

```
curl -s localhost:8009/v1/systemone -H 'content-type: application/json' -d '{
  "state": "Shoes arrived two weeks late and in the wrong size. Also I see two charges on my card.",
  "model": "kev-latest",
  "questions": {
    "department":  {"type": "choice", "instructions": "Which team should handle this?",
                    "criteria": {"returns": "Exchanges, refunds, wrong or damaged items",
                                 "shipping": "Delivery status, delays, lost packages",
                                 "billing": "Charges, invoices, payment problems"}},
    "escalate":    {"type": "noul",  "instructions": "Does this need urgent human attention?"},
    "frustration": {"type": "score", "instructions": "How frustrated is the customer?",
                    "criteria": ["Calm", "Frustrated", "Very angry"]}
  }}'
```

Example response from Kev-4B, running in bf16 on an Apple M5:

```
{
  "model": "kev-latest",
  "answers": {
    "department":  { "type": "choice", "choice": "returns", "confidence": 0.21,
                     "probabilities": { "returns": 0.47, "shipping": 0.28, "billing": 0.25 } },
    "escalate":    { "type": "noul", "noul": 0.93 },
    "frustration": { "type": "score", "score": 1.44, "confidence": 0.78,
                     "legend": { "0": "Calm", "1": "Frustrated", "2": "Very angry" },
                     "probabilities": { "0": 0.00, "1": 0.56, "2": 0.44 } }
  },
  "usage": { "input_tokens": 101, "output_tokens": 161 },
  "latency_ms": 495
}
```

The ticket mentions a return, a late delivery, and a billing problem, and the department probabilities say so. That is the point of getting probabilities back instead of a single label.

##### Python

The TypeSafe SDK is included in `uv sync --extra serve`:

```
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

client = TypeSafeClient(
    api_key="local",
    base_url="http://127.0.0.1:8009",
    model="kev-latest",
)
response = client.system_one(
    state="I was charged twice. Please fix this ASAP.",
    questions={
        "billing": Noul(instructions="Is this ticket about billing?"),
        "tone": Choice(
            instructions="What is the customer's tone?",
            criteria={"calm": None, "frustrated": None, "angry": None},
        ),
        "urgency": Score(
            instructions="How urgent is this ticket?",
            criteria=["can wait", "this week", "today"],
        ),
    },
)
print(response.nouls["billing"].noul)
print(response.choices["tone"].choice)
print(response.scores["urgency"].score)
```

##### Playground

With the server still running, open another terminal. You'll need Node 20.9+:

```
cd playground
npm install
npm run dev -- -p 3001
```

Open [localhost:3001](http://localhost:3001), load a preset, and edit the text and questions. Press `⌘↵` to run it. "Packed vs separate" compares asking all questions at once with asking them one at a time. "Permute" runs a Choice question with six option orders. There are also presets for testing question isolation and fake delimiter tokens.

There's a [chess demo](http://localhost:3001/chess), too. The board is the input, legal moves are Choice options, and a Score question rates the position. You can play against Kev or let it play itself. Games are saved in `localStorage`.

Kev-9B trails Jev by 3.5 points on the new-source development set (0.822 vs 0.857) and scores 0.852 on the test set, which Jev hasn't been run on. We don't know which datasets Jev was trained on, so this isn't a controlled comparison of the two architectures.

All three models were updated on 2026-09-21 with a short second training pass on generated examples: policy cases with explicit day counts, and cases whose deciding evidence was removed, trained toward a uniform answer. On the test set this moved Kev-9B from 0.837 to 0.852 (95% CI +0.8 to +2.9 points), Kev-4B from 0.832 to 0.837, and Kev-0.8B from 0.668 to 0.684. The previous weights are at revision `v7-base`. Details and costs are in the model cards and PLAN.md.

Probabilities are calibrated by default. Each checkpoint stores a temperature (about 2.1–2.4) fitted on its in-distribution development set, and the pointer head applies it when the model is loaded. It never changes an answer: on new sources Kev-9B's calibration error goes from 0.106 to 0.042 and its confident errors (wrong answers with probability ≥ 0.9) from 8.7% to 4.0%, about Jev's 3.7%, with accuracy identical. Set `KEV_TEMPERATURE=1.0` for the raw logits. The accuracy numbers in the table are the same either way; the Brier numbers are for the raw logits.

One optional setting: `KEV_DATE_FACTS=1` appends the number of days between any two absolute dates found in the state ("June 26, 2026 is 8 days before July 4, 2026"). Kev can't subtract dates reliably but it can use a stated day count: on the deadline policy questions Kev-9B goes from 0.80 to 0.90 (Jev 0.93). The table above doesn't use it.

#### API

##### POST /v1/systemone

`state` is the text to evaluate. Each question has instructions and, where needed, a set of answers to choose from.

Type Criteria Answer

`noul` Optional descriptions for `true` and `false` `noul`: probability of yes

`choice` 1–255 option names, each with a description or `null` `choice`: most likely option; `probabilities` and `confidence`

`score` 2–255 descriptions, ordered from lowest to highest `score`: mean level index, starting at 0; `legend`, `probabilities`, and `confidence`

For Choice with `K > 1` options, confidence is `(p_max − 1/K) / (1 − 1/K)`. A single option has confidence 1. Score confidence measures how close the distribution is to its most likely level. It's an approximation of TypeSafe's formula, which isn't public. Neither field is a measured accuracy rate.

Objects and arrays are converted to labeled text. Delimiter-like strings in user input are escaped before tokenization. Invalid requests return `422`. `usage.output_tokens` counts tokens in the serialized answers, not generated tokens.

Method Path Purpose

`GET` `/v1/models` Loaded model and checkpoint information

`POST` `/v1/systemone/permute` Run one Choice question with different option orders

`POST` `/v1/systemone/separate` Run each question in its own forward pass

The server binds to `127.0.0.1` and has no authentication. Keep it local unless you add authentication yourself.

Each checkpoint is a rank-16 LoRA adapter and a small pointer head on a Qwen base model. On an attention-only base (Qwen3), the state and questions go into one token sequence:

```
<state> …state…
<q> instructions <opt> option 1 </opt> <opt> option 2 </opt> … <decide>
<q> instructions <opt> option 1 </opt> <opt> option 2 </opt> … <decide>
```

The attention mask lets a token read the state and its own question, but not other questions or future tokens. Each question's position IDs restart just after the state. This lets the model process the state once and answer each question independently.

Qwen3.5 mixes attention layers with Gated DeltaNet layers, which are recurrent and ignore attention masks. For those models, each question runs as its own row: the state followed by that question, with the same positions as above. The rows are independent, so isolation is exact, and the server computes the state once and reuses its cache for every row. On attention-only models the two forms give identical probabilities (`tests/test_model.py`).

The pointer head scores each option's `</opt>` hidden state against the question's `<decide>` hidden state. A softmax turns those scores into probabilities. Because `<decide>` comes last, it can attend to the full option list.

Training uses cross-entropy on the correct answer. The adapter and head are trained together; the rest of the base weights stay fixed. Training examples and API requests use the same text format. No Jev outputs were used for training.

Asking questions together or separately produces probabilities within 4e-6 in the fp32 tests. This does **not** mean option order is irrelevant: options within a question can still affect one another. See the model code and parity tests.

#### Serving Performance

On CUDA and ROCm, install `flash-linear-attention` for the Qwen3.5 models (the Modal image does this); a five-question request takes tens of milliseconds on an H100 and MI300X.

On Apple Silicon there are no fast kernels for the DeltaNet layers, so PyTorch runs reference code. Median model time in bf16 on an M5, five questions with three options each on a \~230-token state:

Model Time Previous generation on the same request

Kev-0.8B 329 ms Kev-0.6B (Qwen3): 123 ms

Kev-4B 779 ms Kev-4B (Qwen3), `jaredpalmer/kev-4b@qwen3`: 174 ms

Kev-9B about 2 s Kev-8B (Qwen3): about 300 ms

If you serve on a Mac and need low latency, use the Qwen3 models for now. An MLX backend for the Qwen3.5 models is the next planned change.

For the attention-only models the server merges the LoRA weights in fp32 before casting, uses SDPA attention on Apple GPUs, pads MPS inputs to 64-token buckets, and caches the state prefix for repeated requests (four states of at least 384 tokens by default). With a repeated 772-token state, Kev-4B (Qwen3) answers in 242 ms instead of 861 ms.

You can disable these with `KEV_MERGE=0`, `KEV_ATTN=eager`, `KEV_SHAPE_BUCKET=1`, and `KEV_PREFIX_CACHE=0`. On 24 new-source records, bf16 probabilities differed from fp32 by at most 0.017, with no change in the highest-probability answer. That is a small check, not a guarantee for every input.

#### Training

The released models use `decision-v7`: 10,000 examples from ten public datasets, 896 generated policy examples, and 1,680 examples from 60 generated rule structures. All train for two epochs with LoRA rank 16 and cross-entropy. The learning rate is `1e-4` for 0.8B and `5e-5` for 4B/9B. For Qwen3.5 bases the adapter also covers the DeltaNet projections; `kev.train` picks the right targets from the model config.

```
# sanity run, ~1 minute
uv run python -m kev.train --n_per_source 40 --accum 4 --out runs/smoke

# Kev-0.8B (~20 min on one H100; the Mac path works but is slow for Qwen3.5 bases)
uv run python -m kev.train --suite evals/v7/decision-v7 --base Qwen/Qwen3.5-0.8B-Base --base_revision dc7cdfe2ee4154fa7e30f5b51ca41bfa40174e68 \
    --epochs 2 --lr 1e-4 --batch 8 --dtype bf16 --p_none_pair 0.25 --device cuda --out runs/kev-0.8b

# the Kev-4B recipe (one H100 via Modal, ~1 h; see below). Swap in Qwen/Qwen3-4B-Base for the previous generation.
uv run python -m kev.train --suite evals/v7/decision-v7 --base Qwen/Qwen3.5-4B-Base --base_revision 1001bb4d826a52d1f399e183466143f4da7b741b \
    --epochs 2 --lr 5e-5 --batch 4 --accum 2 --dtype bf16 --checkpointing 1 --p_none_pair 0.25 --device cuda --out runs/kev-4b
```

The released models were trained on public datasets and generated policy examples. If your questions look different — your own routing categories, your own escalation rules, another language — a short fine-tune on a few hundred labelled examples usually helps more than any prompt change.

Put your examples in a JSONL file, one request per line. It's the same shape as an API request, plus a `label` on every question:

For `choice` the label is the option name, for `noul` it's `true` or `false`, and for `score` it's the level's position starting at 0. Keep 10–20% of the file aside for evaluation.

Then start from a released checkpoint with `--init_from`:

```
uv run python -m kev.train --data train.jsonl --base Qwen/Qwen3.5-4B-Base --init_from jaredpalmer/kev-4b \
    --epochs 2 --lr 2e-5 --batch 1 --accum 8 --dtype bf16 --checkpointing 1 --device cuda --out runs/mine

uv run python -m kev.benchmark --run runs/mine --data heldout.jsonl --out runs/mine-eval
KEV_DTYPE=bf16 uv run --extra serve python -m kev.serve --run runs/mine --port 8009
```

`--init_from` loads the adapter and pointer head from the released model before training, so you keep what Kev already knows and add your domain on top. Starting from the base model instead throws that away: in one user's test on 836 support-tool decisions, a fine-tune from the base scored 0.33 on Kev's own evaluation set, against 0.84 for the released model; the same data with `--init_from` kept 0.83 there and reached 0.88 on the new domain. Use a smaller learning rate than the from-scratch recipe (`2e-5` is a good start), and pick `--base` to match the checkpoint you start from; the trainer checks that the base, revision, LoRA rank, and head size agree before it loads anything.

`--batch 1 --accum 8` in bf16 fits the 0.8B model on a 4 GB GPU. The benchmark reports accuracy, Brier score, and calibration per question type, so you can see which of your questions the fine-tune helped. The checkpoint you started from is recorded in `runs/mine/training_config.json`.

Use `uv run python -m kev.train --help` for all training options. The released models don't use the optional `--perm_kl` or `--ord_w` losses. The model cards have the training settings and dataset lists; PLAN.md records what was tried and what helped.

On a Mac, run one training job at a time. Two jobs on the same Apple GPU are much slower. Use Modal for longer runs.

If you work with a coding agent, the `kev-finetune` skill does all of this on Modal without a local GPU: it interviews you, finds the questions your code already asks Jev or TypeSafe, converts labels you have or generates enough with any LLM to measure a gain, fine-tunes from a released checkpoint, fits the temperature on a held-out slice, scores the result against the baseline, deploys a System One endpoint, and tears it all down. Install it with `npx skills add jaredpalmer/kev@kev-finetune`; the README is the same recipe for humans.

##### Modal

Each trial gets its own H100. The study keeps running if you disconnect, and you can download the results when it finishes:

```
uv run modal token new                                    # once; opens the browser
KEV_GPU=T4 uv run modal run modal_app.py::smoke           # end-to-end check, ~1 minute of GPU

uv run modal deploy modal_app.py                          # once; studies run on the deployed app and survive disconnects
uv run modal run modal_app.py::study \
    --suite evals/v7/decision-v7 --plan experiments/v7-final.json \
    --name my-study --transfer evals/v4/transfer-v4 --budget 30 --timeout 7200
uv run modal run modal_app.py::pull --name my-study       # results -> runs/my-study, ranked
```

Study plans list training settings. Each trial saves the settings, code hashes, dataset hashes, and results. Choose models using the development results, not the locked test. After choosing a final candidate, you can read its test results once:

```
uv run modal run modal_app.py::locked_test --trial my-study/00-trial-0 --name my-candidate   # one read, ever
```

#### Evaluation

The evaluation data under `evals/` is frozen: dataset versions and file checksums are recorded in each manifest. Large training files are downloaded from [the Hub mirror](https://huggingface.co/datasets/jaredpalmer/kev-suites) and checked against those hashes.

```
uv run python -m kev.benchmark --run jaredpalmer/kev-4b --suite evals/v4/transfer-v4 --out runs/my-eval      # out of domain
uv run python -m kev.benchmark --run jaredpalmer/kev-4b --suite evals/v9/transfer-v9 --out runs/my-eval-v9   # + MMLU-Pro, buried states, unknowable items
uv run python -m kev.benchmark --run jaredpalmer/kev-4b --suite evals/v7/decision-v7 --out runs/my-eval-id   # in distribution
uv run python -m kev.benchmark --remote http://127.0.0.1:8009 --suite evals/v4/transfer-v4 --out runs/my-remote   # any System One endpoint
```

These commands use development data. Test data requires `--allow-test`. The benchmark reports accuracy, Brier score, calibration error, the share of decisions you could automate at a 5% error budget, option-order changes, and question isolation. `transfer-v9` adds 10-way MMLU-Pro, records buried among unrelated text, and "unknowable" records whose deciding evidence was removed; for those it reports how often the model still answers with at least 0.9 confidence (Kev-9B 5%, Jev 9%, Kev-8B 26%). Published accuracy numbers use fp32 evaluation, not the bf16 serving path.

`evals/external/` holds two other projects' test sets converted to this format, with their published live Jev results: [SemIf](https://github.com/TheoLeeCJ/SemIf) 's 144 authored decisions (Kev-9B 0.917, Jev 0.965) and [scienthoon](https://github.com/scienthoon/jev-ood-calibration) 's 900 support tickets (Kev-9B 0.952 on routing and 0.911 on tone, Jev 0.897 and 0.914).

`kev.jev` runs the same questions against Jev through Vercel AI Gateway. `kev.compare` compares two saved runs with paired bootstrap confidence intervals. For the full experiment history, see PLAN.md and the leaderboard.

#### Limitations

- Calibration is by a single temperature fitted in distribution. As served, Kev-9B assigns at least 0.9 probability to a wrong answer on 4.0% of new-source questions (Jev 3.7%); a fixed temperature can't reorder confidences, so the share of decisions you can automate at a 5% error budget (0.45–0.57) is still below Jev's 0.70. Test it on your own data before choosing a probability threshold.
- Fine-tuning can make the base model worse at individual tasks. Date arithmetic is the clearest case: the untrained Qwen3.5-9B base gets 0.82 on the `deadline` policy questions and the first Kev-9B got 0.72 ([issue #8](https://github.com/jaredpalmer/kev/issues/8)). Training on examples that state the day count, plus `KEV_DATE_FACTS=1`, recovers it (0.90). Knowledge questions (MMLU 0.74 vs Jev 0.90; MMLU-Pro 0.52 vs 0.84) are the remaining large gap, and they're set by the base model: a Kev trained on the 35B-A3B mixture-of-experts base didn't move them (PLAN.md).
- The current models are slow on Apple Silicon (see Serving Performance) and need `transformers >= 5.17`.
- Changing option order can change an answer. Question isolation doesn't prevent this.
- Training uses at most 384 state tokens and 1,024 tokens for the state plus one question. Serving allows 8,192 tokens for the state plus one question; longer context wasn't covered by training.
- The server handles one request at a time. It caches repeated state text, but doesn't batch requests from different callers.

## 产品-功能解读和应用（1）

### 2026-09-22 03:00:37

#### 一、讲了什么？

Kev 是一组基于 Qwen3.5 构建的轻量级 “决策模型”，目标不是生成长篇文字，而是把一段共享上下文转化为结构化判断。它支持三类问题：

- **Noul**：判断 “是或否”，返回 “是” 的概率。
- **Choice**：从多个选项中选择，并返回各选项概率。
- **Score**：在有序等级上评分，返回期望分数、等级概率和置信度。

Kev 提供 0.8B、4B、9B 三种规模，可在 CUDA、ROCm 和 Apple Silicon 上本地运行，也能通过兼容 TypeSafe System One 的 API 接入现有应用。模型由冻结的 Qwen 基座、LoRA 适配器和指针式决策头组成。

它的关键特点是：多个问题可以共享同一段输入，但问题之间彼此隔离；输出不仅有最终答案，还有概率分布；检查点默认保存温度校准参数，以减少 “过度自信”。项目还提供训练代码、评测数据、网页 Playground、选项顺序测试以及本地服务能力。

本质上，Kev 是把大语言模型从 “开放式写作工具” 压缩成 “可部署、可评估、可校准的概率决策引擎”。

#### 二、有什么用？

##### 1. 它解决的不是 “怎么说”，而是 “该怎么判”

传统大语言模型更像一位知识丰富、表达能力很强的顾问。你给它一张客户工单，它可能回复：

> 这位客户似乎遇到了重复扣费、配送延迟以及尺码错误等多个问题，建议优先联系售后团队……

这段话看起来合理，但对业务系统并不友好。系统真正需要的通常是：

- 应该分给哪个部门？
- 是否立即升级人工？
- 客户有多愤怒？
- 每个判断有多大把握？
- 判断不确定时该怎么办？

Kev 更像一块专门制作的 “仪表盘”。它不写长报告，而是直接给出可被程序消费的结果：

```json
{
  "department": {
    "choice": "returns",
    "probabilities": {
      "returns": 0.47,
      "shipping": 0.28,
      "billing": 0.25
    }
  },
  "escalate": {
    "noul": 0.93
  },
  "frustration": {
    "score": 1.44
  }
}
```

生成模型强调语言质量，决策模型强调答案空间、概率、稳定性和可执行性。两者的区别，就像 “让医生自由描述病情” 和 “让医生填写标准化诊断表”：前者信息丰富，后者更容易接入分诊、风控、统计和自动化流程。

##### 2. 概率比单一标签更有业务价值

如果模型只返回 “退换货”，业务系统会误以为问题已经完全明确。但示例中三个部门的概率分别是：

- 退换货：0.47
- 配送：0.28
- 账单：0.25

这意味着客户实际上同时提到了三个问题，只是退换货相对更可能成为主处理部门。

概率分布像天气预报。天气应用说 “明天下雨”，和说 “明天下雨概率为 52%”，是两种完全不同的信息。前者迫使你把世界理解为非黑即白；后者允许你根据损失大小做决策：

- 普通内部标签：52% 也可以自动采用。
- 涉及退款：可能要求概率达到 85%。
- 涉及封号或拒绝交易：可能要求达到 95%，否则转人工。
- 多个选项接近：可以创建联合工单，或者让人工复核。

因此，概率不是输出的装饰，而是连接模型判断与业务风险的桥梁。

##### 3. 校准让 “80%” 尽量接近真实的 80%

模型很容易 “声音很大，但不一定正确”。未经校准的模型可能经常给出 95% 的概率，但这些答案实际上只有 75% 正确。这就像一名员工每次都斩钉截铁地说 “我确定”，久而久之，管理者无法再把他的语气当作可信依据。

Kev 默认使用温度缩放来校准概率。可以把它想象成给汽车仪表盘重新校表：它不会改变汽车往哪个方向开，也不会改变最高概率选项，却会让速度表的读数更接近真实速度。

例如，校准前：

```text
退换货 0.94，配送 0.04，账单 0.02
```

校准后可能变成：

```text
退换货 0.71，配送 0.18，账单 0.11
```

最终选择仍然是 “退换货”，但系统不再被虚假的高置信度误导。仓库给出的实验结果也体现了这一点：校准不改变准确率，却明显减少高置信度错误。

需要特别注意，Kev 返回的`confidence`不是 “这个答案实际有多大概率正确”。Choice 的 confidence 是相对于随机猜测基线归一化后的领先程度；Score 的 confidence 则衡量概率是否集中于某个等级。它们适合做相对判断，但不能直接当作真实准确率。用于高风险决策时，应优先基于验证集重新建立 “预测概率 — 实际正确率” 的关系。

##### 4. 多问题共享上下文，节约计算又防止互相污染

现实任务经常要求围绕同一段文本回答多个问题。例如，对一份保险理赔材料同时判断：

- 是否符合保险范围？
- 是否疑似欺诈？
- 应交给哪个审核队列？
- 风险等级是多少？
- 是否缺少关键证据？

最笨的方法是把材料重复发送五次。这样会重复处理长上下文，增加延迟和成本。

Kev 采用 “共享状态、独立问题” 的结构。可以把输入文本想象成一本公共档案，每位审核员都可以阅读档案，但审核员之间不能偷看彼此的答卷。这样既复用公共信息，又避免前一个问题及其选项暗示后一个问题。

在纯注意力模型上，Kev 通过注意力掩码实现隔离；在包含 Gated DeltaNet 循环层的 Qwen3.5 上，因为循环状态不会遵守普通注意力掩码，所以每个问题作为独立的一行执行，同时复用状态缓存。两种实现追求同一个目标：每个问题只依据共享状态和自己的题目作答。

这对实验可信度很重要。如果 “是否紧急” 的问题能看到 “客户情绪：非常愤怒” 的其他问题或答案，它可能受到额外暗示。问题隔离可以减少这种隐性串扰。

##### 5. 指针式决策比自由生成更适合封闭选项

Kev 不要求模型生成选项名称，再去解析文本。它让一个小型指针头直接给候选项打分：比较每个选项结束位置的隐藏状态与决策位置的隐藏状态，然后通过 softmax 得到概率。

可以把它理解成考试中的选择题答题卡：

- 基础模型负责阅读材料、理解题目和选项；
- 指针头负责给 A、B、C、D 打分；
- softmax 把分数转换成概率；
- 系统直接读取最高分选项。

这样避免了很多生成式接口常见的问题：

- 输出了不存在的标签；
- 标签拼写变化；
- JSON 格式损坏；
- 解释很多却没有明确结论；
- 生成内容被提示注入干扰；
- 需要额外解析自然语言。

它尤其适合标签空间明确、需要稳定结构化输出的业务。

##### 6. 小模型和本地部署带来控制权

Kev 的模型规模从 0.8B 到 9B，核心价值不只是 “小”，更是可控：

- 数据可留在本地或私有云；
- 延迟、吞吐和成本可以自行规划；
- 可以固定模型版本，避免云端模型静默升级；
- 可以查看训练、评测和服务代码；
- 可以围绕自己的政策与标签进行训练；
- 可以对概率、阈值、错误类型做独立审计。

选择模型时可以把它们看作不同级别的员工：

- **0.8B**：便宜、轻量，适合简单筛选、边缘设备或高吞吐低风险任务。
- **4B**：综合平衡，通常应作为默认起点。
- **9B**：更重，但在泛化能力和概率质量更重要时更合适。

不过，小模型并不意味着任何机器上都一定更快。Qwen3.5 使用 DeltaNet 层，在 Apple Silicon 上缺少成熟的快速内核，仓库给出的测试显示其速度可能显著慢于上一代纯注意力 Qwen3 模型。因此，模型选择必须结合准确率、校准、硬件内核和实际延迟测试，而不能只看参数量。

#### 三、怎么用？

##### 场景：构建一套客户工单自动分诊系统

假设一家电商每天收到数万条工单，内容可能同时包含物流、退款、商品质量、重复扣款和情绪投诉。目标是：

1. 识别主要负责部门；
2. 判断是否涉及账单；
3. 判断是否需要紧急人工介入；
4. 评估客户情绪；
5. 对不确定或高风险案例进行人工复核。

下面按照从需求定义到生产上线的完整过程实施。

##### 第一步：确认任务是否适合决策模型

Kev 最适合满足以下条件的任务：

- 输入是一段文本或可转成文本的对象；
- 输出可以表示为布尔判断、有限选项或有序评分；
- 业务希望获得概率，而不只是标签；
- 需要稳定 JSON，而不是开放式回答；
- 同一输入需要回答多个相互独立的问题。

不适合直接交给 Kev 的任务包括：

- 写一封完整的道歉邮件；
- 生成长篇调查报告；
- 总结未知数量的事件；
- 从文本中抽取任意结构、任意数量的实体；
- 需要调用工具、多轮规划和执行的复杂代理任务。

实际系统通常应采用组合架构：Kev 负责判断和路由，生成式模型负责解释、总结或起草回复，业务规则负责执行最终动作。

##### 第二步：定义业务标签，而不是先写提示词

先明确系统允许采取哪些动作。例如工单主部门定义为：

| 标签 | 业务含义 |
|---|---|
| `returns` | 退货、换货、退款、商品错误或损坏 |
| `shipping` | 延迟、丢件、配送状态 |
| `billing` | 重复扣款、发票、支付失败 |
| `account` | 登录、账号、安全或权限 |
| `other` | 无法归入以上类别 |

标签描述应尽量满足三个原则：

1. **边界清楚**：不要同时设置 “退款” 和 “售后” 这种高度重叠的类别。
2. **可执行**：每个标签都应对应一个真实处理队列或动作。
3. **覆盖异常**：保留`other`、`unknown`或人工复核出口，避免模型被迫乱选。

评分问题也要定义等级含义。例如情绪等级：

```text
0：平静，只描述事实
1：不满，表达抱怨或催促
2：愤怒，使用强烈批评、威胁投诉或要求立即处理
```

有序等级必须从低到高排列，因为 Kev 的 Score 会返回等级索引的概率加权平均值。假设三个等级的概率是：

```text
P (0)=0.05，P (1)=0.35，P (2)=0.60
```

则分数为：

```text
0×0.05 + 1×0.35 + 2×0.60 = 1.55
```

它不是凭空生成的连续分数，而是离散等级分布的期望值。

##### 第三步：选择模型和运行环境

默认从 Kev-4B 开始：

- 如果 4B 已达到准确率和延迟目标，不必盲目升级。
- 如果新业务来源、复杂政策判断或概率校准更重要，再测试 9B。
- 如果任务非常简单，或者设备资源受限，可测试 0.8B。
- 如果主要运行在 Mac 且低延迟优先，可以比较上一代 Qwen3 版本，因为 Qwen3.5 的 DeltaNet 层在 Apple Silicon 上暂时缺少高性能内核。

不能只比较总准确率，还应比较：

- 每个类别的召回率和精确率；
- 高风险错误率；
- 新数据来源上的泛化能力；
- Brier Score 或其他概率质量指标；
- P50、P95 和 P99 延迟；
- 峰值显存或统一内存占用；
- 并发吞吐；
- 选项顺序变化下的稳定性。

##### 第四步：启动本地服务

准备 Python 3.12 以上版本和`uv`，然后执行：

```bash
git clone https://github.com/jaredpalmer/kev.git
cd kev
uv sync --extra serve
KEV_DTYPE=bf16 uv run --extra serve python -m kev.serve \
  --run jaredpalmer/kev-4b \
  --port 8009
```

第一次启动会下载 Qwen 基础模型、LoRA 适配器和决策头。服务默认绑定`127.0.0.1`，没有身份认证，这适合本地开发，但不能直接暴露到公网。

生产部署至少应在外层增加：

- TLS；
- API 身份认证；
- 请求限流；
- 输入长度限制；
- 审计日志；
- 敏感信息脱敏；
- 超时和熔断；
- 模型版本固定；
- 健康检查和灰度发布；
- 对输入、输出和日志的访问控制。

##### 第五步：把一段工单拆成多个独立问题

请求可以设计为：

```json
{
  "state": "鞋子晚到了两周，尺码也不对，而且我的银行卡出现了两笔相同扣款。请立刻处理。",
  "model": "kev-latest",
  "questions": {
    "department": {
      "type": "choice",
      "instructions": "哪个团队应作为该工单的主要负责人？",
      "criteria": {
        "returns": "换货、退款、尺码错误、商品错误或损坏",
        "shipping": "配送进度、延误、丢件",
        "billing": "扣款、发票、支付问题",
        "account": "账号、登录、安全或权限",
        "other": "无法归入以上类别"
      }
    },
    "billing_related": {
      "type": "noul",
      "instructions": "该工单是否涉及账单、支付或扣款问题？"
    },
    "escalate": {
      "type": "noul",
      "instructions": "该工单是否需要紧急人工处理？"
    },
    "frustration": {
      "type": "score",
      "instructions": "客户当前的负面情绪有多强？",
      "criteria": [
        "平静，只描述事实",
        "不满，出现抱怨或催促",
        "愤怒，强烈批评、威胁投诉或要求立即处理"
      ]
    }
  }
}
```

调用接口：

```bash
curl -s http://127.0.0.1:8009/v1/systemone \
  -H 'content-type: application/json' \
  -d @request.json
```

这里有一个重要设计原则：**Choice 用于互斥的主决策，Noul 用于可并存的属性。**

一张工单可以同时涉及配送和账单，所以不能只依赖一个主部门标签。较合理的设计是：

- 用 Choice 选主责任部门；
- 用多个 Noul 判断是否同时涉及账单、物流、欺诈等属性；
- 根据这些属性创建协作任务。

这能避免把复杂现实强行压成单一分类。

##### 第六步：把模型概率变成业务动作

不要简单地执行 “最高概率选项”。应建立明确的决策策略。例如：

```text
若账单相关概率 ≥ 0.85：
    添加 billing 标签

若紧急升级概率 ≥ 0.90：
    进入人工紧急队列

若主部门最高概率 ≥ 0.75，且第一名与第二名差值 ≥ 0.25：
    自动路由到第一名

若最高概率在 0.50 到 0.75 之间：
    路由到第一名，但进入抽样复核

若最高概率 < 0.50，或前两名差值 < 0.10：
    转人工分诊

若情绪分数 ≥ 1.5：
    提高响应优先级
```

阈值不能凭感觉决定。正确方法是利用历史验证集逐步计算：

1. 收集真实工单及人工确认标签；
2. 运行模型，保存所有概率；
3. 按概率区间分桶，如 0.5～0.6、0.6～0.7；
4. 统计每个区间的真实准确率；
5. 计算不同阈值下自动处理比例与错误成本；
6. 根据业务损失选择阈值。

例如，普通部门误分一次成本较低，可以把自动化阈值设为 0.70；涉及退款、封禁或拒付时，错误成本高，阈值可能需要达到 0.95，并增加规则校验。

##### 第七步：评估准确率之外的概率质量

仅看准确率会掩盖严重问题。两个模型都可能有 85% 准确率：

- 模型甲在错误时通常只给 55% 概率；
- 模型乙在错误时经常给 99% 概率。

模型甲更适合自动化，因为系统能识别其犹豫并转人工。模型乙则会制造危险的高置信度错误。

因此应同时评估：

###### 准确率

最高概率选项是否正确。

###### Brier Score

衡量预测概率与真实结果之间的平方误差，越低越好。它同时惩罚错误和过度自信。

###### 预期校准误差

例如，模型给出约 80% 概率的一组案例，实际是否约有 80% 正确。

###### 高置信度错误率

统计错误答案中有多少仍然给出 90% 以上概率。这通常比总体准确率更贴近生产风险。

###### 覆盖率 — 风险曲线

只自动处理概率大于某阈值的案例时：

- 能覆盖多少工单？
- 剩余自动处理案例的错误率是多少？

这能直接回答 “自动化 60% 工单时，错误率有多高”。

Kev 的检查点默认带有温度参数。需要查看原始 logits 时，可以设置：

```bash
KEV_TEMPERATURE=1.0
```

但生产环境不应仅因原始概率看起来更 “确定” 就关闭校准。

##### 第八步：测试选项顺序偏差

问题彼此隔离，不代表同一问题内部的选项顺序没有影响。模型可能偏爱靠前、靠后或特定表达方式的选项。

可以调用排列测试接口，对同一个 Choice 使用多种选项顺序：

```text
POST /v1/systemone/permute
```

重点观察：

- 调换顺序后最高概率选项是否变化；
- 同一语义的概率波动有多大；
- 某个位置是否系统性获得更高概率；
- 描述长度是否造成偏差。

如果顺序敏感，应采取以下措施：

1. 让选项描述长度和信息密度尽量接近；
2. 避免某个选项包含明显更多关键词；
3. 验证时随机化选项顺序；
4. 对关键任务进行多次排列并汇总概率；
5. 将顺序不稳定视为不确定信号，必要时转人工。

仓库中的 Playground 可以直观看到 packed、separate 和 permute 等测试结果，适合在正式接入前调试问题定义。

##### 第九步：验证问题隔离和输入安全

可以对同一组问题分别测试：

- 一次性共同提交；
- 每个问题单独提交；
- 改写其他问题，但保持目标问题不变。

仓库提供：

```text
POST /v1/systemone/separate
```

理论上，共同提交与独立提交应得到几乎一致的概率。如果业务测试出现明显差异，应检查：

- 模型或服务版本是否一致；
- 是否使用了不同温度参数；
- 输入序列是否被截断；
- 浮点精度是否不同；
- 是否存在缓存或批处理实现问题。

用户输入中的伪分隔符也是安全重点。例如用户故意写入`&lt;q>`、`&lt;opt>`或`&lt;decide>`，不应被解释为系统结构。Kev 会在分词前转义类似分隔符的字符串，但生产系统仍需做长度限制、日志隔离和异常输入测试。结构转义只能保护输入边界，不能替代完整的安全工程。

##### 第十步：处理日期、规则和外部事实

小模型通常不擅长精确日期减法。例如规则是 “签收后 14 天内可退货”，文本出现两个绝对日期时，模型可能理解政策，却算错天数。

Kev 可通过：

```bash
KEV_DATE_FACTS=1
```

在状态中追加两个绝对日期之间的天数，例如：

```text
2026 年 6 月 26 日比 2026 年 7 月 4 日早 8 天
```

这体现了一个重要架构原则：不要强迫语言模型承担它不擅长的确定性计算。更可靠的做法是：

1. 程序解析日期；
2. 程序计算天数；
3. 把计算结果作为明确事实提供给模型；
4. 模型负责把事实与政策条件结合起来判断。

同理，金额计算、汇率转换、数据库查询、库存状态和权限判断，都应尽可能由确定性工具完成，再让模型做语义决策。

##### 第十一步：需要时训练自己的版本

当通用模型无法理解企业特有政策、行业标签或文本风格时，可以进行领域训练。Kev 的检查点主要包含：

- 冻结的 Qwen 基础模型；
- rank-16 LoRA 适配器；
- 小型指针决策头；
- 校准温度和相关配置。

训练采用正确选项上的交叉熵，LoRA 与决策头一起训练，基础模型主体保持冻结。训练数据与线上 API 使用相同的 “状态 — 问题 — 选项” 格式，这减少了训练与服务之间的格式偏差。

领域数据应包含：

1. 常见正例；
2. 明确反例；
3. 容易混淆的边界案例；
4. 缺少决定性证据的案例；
5. 新来源、新文风和新渠道数据；
6. 选项顺序随机化版本；
7. 长文本、错别字、口语和恶意输入；
8. 时间、金额及政策阈值附近的案例。

尤其重要的是 “证据被移除” 的反事实样本。假设原始文本因为 “重复扣款” 而属于账单问题，删除这句话后，模型不应继续高概率选择账单。这类样本能迫使模型依据真实证据，而不是数据集中的表面模式。

训练完成后，应把数据分为：

- 训练集；
- 开发集，用于模型选择和温度校准；
- 测试集，只在最终版本确定后使用；
- 新来源测试集，用于评估迁移能力。

不能反复查看测试集再修改模型，否则测试集会逐渐变成隐形训练集，最终指标失去可信度。

##### 第十二步：形成生产闭环

上线后记录：

- 模型与检查点版本；
- 输入来源；
- 问题定义版本；
- 完整概率分布；
- 实际采取的动作；
- 是否转人工；
- 人工最终标签；
- 用户申诉与后续结果；
- 延迟、错误码和资源使用情况。

再按周期分析：

- 哪些类别最容易混淆；
- 哪些新渠道导致性能下降；
- 哪些高置信度错误损失最大；
- 自动化覆盖率是否提升；
- 概率是否随时间失去校准；
- 政策变化是否导致标签定义过时。

最终形成 “预测 — 执行 — 人工纠正 — 评估 — 再训练” 的闭环。模型本身只是一个部件，真正产生业务价值的是围绕它建立的决策系统。

#### 四、如何迁移？

##### 1. 抽象出通用结构

Kev 背后的核心模式可以抽象为：

```text
共享状态
→ 一组相互隔离的问题
→ 有限、明确的答案空间
→ 每个答案的概率分布
→ 基于风险阈值采取动作
→ 收集真实结果并反馈
```

这比某个具体模型更重要。只要一个问题能被表达为 “在给定上下文下，从有限行动中做概率判断”，就可以迁移这一模式。

其中五个核心要素是：

1. **State：事实状态**  
   原始文本、结构化字段、工具计算结果和必要背景。

2. **Question：决策问题**  
   系统到底要判断什么，必须清晰、单一、可验证。

3. **Options：行动空间**  
   允许选择的类别、布尔结果或有序等级。

4. **Probability：不确定性表达**  
   不只给结论，还要给出对各结论的相信程度。

5. **Policy：行动策略**  
   如何根据概率、风险和成本自动执行或转人工。

模型只是完成中间的概率映射；业务价值主要来自前后的状态构造和行动策略。

##### 2. 横向迁移到不同业务领域

###### 内容审核

共享状态是一篇帖子，问题可以是：

- 是否含仇恨言论；
- 是否包含个人隐私；
- 是否属于诈骗；
- 主要违规类型是什么；
- 严重程度是多少。

这里不应只做一个互斥分类，因为一篇内容可能同时涉及多个违规属性。可以使用多个 Noul 判断并存风险，再用 Choice 决定主审核队列，用 Score 判断严重程度。

###### 金融风控

共享状态包括交易描述、设备信息、时间和历史统计，问题包括：

- 是否疑似盗刷；
- 是否需要二次验证；
- 应采用放行、验证、人工审核还是拒绝；
- 风险等级是多少。

模型概率不能直接等同于违约率或欺诈率，必须在真实金融数据上重新校准，并结合金额和客户等级设置不同阈值。

###### 医疗分诊

共享状态是患者描述、症状和基础指标，问题包括：

- 是否出现高危症状；
- 应去急诊、门诊还是居家观察；
- 紧急程度是多少。

由于错误代价极高，模型更适合作为辅助分诊，不应成为无监督的最终诊断者。概率应触发升级机制，而不是替代专业人员。

###### 企业合规

共享状态是合同、邮件或交易材料，问题包括：

- 是否涉及受限制地区；
- 是否包含异常付款条件；
- 是否违反内部政策；
- 应由哪个合规团队复核。

日期差、金额阈值和名单匹配应由规则引擎计算，模型负责解释模糊语言与政策语义。

###### 软件工程

共享状态是缺陷报告、日志和堆栈信息，问题包括：

- 属于前端、后端、基础设施还是数据问题；
- 是否可能是安全漏洞；
- 是否阻塞发布；
- 严重级别是多少。

模型可以负责分诊，但重现验证、依赖查询和版本比对应交给确定性工具。

##### 3. 纵向迁移到完整决策系统

最初可以只用 Kev 做标签预测，随后逐步向上扩展：

###### 第一层：预测

输入文本，输出标签和概率。

###### 第二层：路由

根据概率把任务送到不同队列。

###### 第三层：风险控制

根据错误成本设置不同阈值和人工复核机制。

###### 第四层：工具协同

先通过程序计算日期、金额、地理位置或数据库事实，再交给模型判断。

###### 第五层：解释生成

把决策结果、证据和政策条款交给生成模型，产生面向用户或审核人员的说明。

###### 第六层：持续学习

利用人工纠正、新来源数据和高损失错误进行再训练与重新校准。

这条纵向路径说明：决策模型不需要独自完成所有工作。它最适合作为系统中的 “概率判断层”，上接事实与工具，下接政策与执行。

##### 4. 从模型架构迁移到产品架构

Kev 的 “共享状态、问题隔离” 不仅是模型优化，也可以迁移为产品设计原则。

例如，一份贷款申请需要经过收入审核、欺诈审核、合规审核和信用审核。所有审核模块共享申请材料，但应分别作出判断，避免一个模块的初步结论污染其他模块。最后再由聚合层综合多个独立判断。

这类似司法系统中的独立证人：每个人都看同一组证据，但不能先统一口径。独立判断能帮助系统识别分歧，而分歧本身就是重要信号。

如果四个判断器中三个认为低风险、一个认为高风险，不应简单取多数，而应进一步判断：

- 高风险问题是否属于 “一票否决”；
- 该判断器在此类案例上的历史可靠性；
- 是否缺失关键证据；
- 是否需要人工仲裁。

因此，问题隔离最终导向的是更清晰的责任边界和更可审计的系统。

##### 5. 从概率输出迁移到组织决策

概率思维不仅用于机器模型，也可以用于团队管理。

传统评审经常要求成员只给结论：“上线” 或 “不上线”。更好的方式是同时记录：

- 上线成功概率；
- 主要失败模式；
- 每种失败的损失；
- 哪些新增证据会改变判断；
- 何时需要升级审批。

这相当于把 Kev 的输出结构迁移到组织决策：

```text
候选行动 + 概率分布 + 风险成本 + 阈值策略
```

团队由此从 “争论谁的观点更强势”，转向 “比较不同判断的证据、概率和损失”。

##### 6. 从静态分类迁移到动态决策

很多团队把分类模型当作终点，其实分类只是决策链的中间结果。真正需要优化的是预期损失：

```text
预期损失 = 各种结果发生概率 × 对应业务成本
```

假设一个交易有 8% 的欺诈概率：

- 若金额只有 10 元，直接放行可能更划算；
- 若金额为 10 万元，则应触发验证或人工审核。

同一个概率，在不同上下文中对应不同动作。由此可见，模型不应该硬编码业务决策。模型负责估计，策略层负责取舍。

这种分离还能让系统在不重新训练模型的情况下适应业务变化。例如旺季人工审核能力不足，可以暂时提高转人工阈值；高风险时期则可以降低阈值，加强审查。

##### 7. 从提示工程迁移到评测工程

Kev 最值得迁移的理念之一，是把注意力从 “写一个更聪明的提示词” 转向 “建立一个可信的评测系统”。

应持续构建以下测试矩阵：

| 维度 | 典型测试 |
|---|---|
| 语义一致性 | 同义改写后结论是否稳定 |
| 选项顺序 | 调换选项位置后是否偏移 |
| 证据敏感性 | 删除决定性证据后概率是否下降 |
| 无关信息 | 添加噪声后是否保持判断 |
| 来源迁移 | 邮件、聊天、电话转写是否一致 |
| 概率校准 | 预测概率是否匹配真实正确率 |
| 高风险错误 | 是否存在极度自信的错误 |
| 性能 | 长文本、并发和缓存下的延迟 |
| 安全 | 伪分隔符、超长输入和恶意文本 |
| 漂移 | 新政策、新产品和新用户群上的变化 |

提示词可以改善局部表现，但评测体系决定你是否知道它真的改善了。

##### 8. 识别不应迁移的边界

这一模式并非万能。以下场景不应强行套用：

- 答案空间无法提前定义；
- 任务依赖大量外部检索；
- 需要长链条规划和连续工具调用；
- 输出必须包含原创内容；
- 需要精确数学、日期或数据库事实；
- 决策不可逆且缺乏人工兜底；
- 没有足够真实数据验证概率质量。

遇到这些场景，应采用混合系统：

```text
规则与工具提供确定性事实
→ 决策模型进行概率判断
→ 生成模型负责解释与交互
→ 人类处理高风险和低置信度案例
```

最终可迁移的不是 “使用 Kev” 这一具体动作，而是一套更成熟的智能系统观：把开放式语言能力收束为清晰问题，把模糊判断表示为概率，把概率转换为有风险边界的行动，再用真实结果不断校准整个系统。

## 深度解读-口播（1）

### 2026-09-30 12:20:32

Kev 想解决的，不是让小模型更会聊天，而是让它更适合做明确的判断：一段文本应该归到哪一类，是否需要人工介入，或者某个指标应该打几分。它的特点是，既给答案，也给各个答案的概率，而且可以自己训练、自己部署。

这个项目基于千问三点五，提供八亿、四十亿和九十亿参数三个版本。理解它的价值，可以从一张客服工单开始。

假设客户说：“鞋子晚到了两周，尺码也不对，而且我的银行卡被扣了两次钱。”

面对这段话，系统可能需要同时判断三个问题：交给哪个部门，是否紧急升级，以及客户有多生气。

Kev 可以在同一个请求里回答这三种问题。它支持是非判断、单项选择，以及有顺序的等级评分。

项目给出的示例中，模型把退换货部门排在第一位，但概率只有百分之四十七。物流部门是百分之二十八，账单部门是百分之二十五。

这组概率比一个孤零零的“退换货”标签更有信息量。因为客户确实同时提到了三个部门的问题，第一名并没有压倒性的优势。

同一份结果里，模型认为需要紧急人工关注的概率是百分之九十三。对情绪的判断，则主要落在“沮丧”和“非常愤怒”之间。

这里最值得记住的是：Kev 不只是把文本塞进某个类别，还把判断中的不确定性表达出来。

不过，把多个问题一起提交，会不会导致问题之间互相干扰？比如，问了“是否紧急”，就影响模型对客户情绪的判断？

这是 Kev 架构里专门处理的一点。多个问题可以共享同一段输入，但每个问题不能读取其他问题的内容。

你可以把它想成几位评审，都看同一份材料，却不能偷看彼此的题目。这只是帮助理解的比喻，实际依靠的是模型内部的隔离机制。

千问三点五有些层会沿着输入序列传递内部状态，不能只靠限制注意力，就阻止问题之间的信息流动。因此，Kev 把每个问题放进独立的处理行里。共享文本先计算一次，再复用已经算好的内部状态。

这样既保持问题隔离，也减少重复处理。在项目的高精度测试中，一起问和分开问得到的概率，差异非常小。

但这里有个边界：问题之间隔离，不代表同一道选择题里的选项互不影响。改变选项排列顺序，仍然可能改变结果。项目的网页试验界面，专门提供了打乱选项顺序的测试功能。

Kev 也不是通过生成一段长回答，再从里面提取结论。它在基础模型上增加了一个小型评分模块，直接给候选答案打分，再转成概率。训练时，主要更新轻量的适配参数和评分模块，基础模型的大部分权重保持不变。项目还明确说明，没有使用 Jev 的输出作为训练数据。

接下来，真正重要的问题是：这些概率有多可信？

先看选对答案的能力。在模型没有训练过的数据来源上，九十亿参数版本的测试准确率是百分之八十五点二，四十亿版本是百分之八十三点七，八亿版本是百分之六十八点四。

这说明，在这套评测里，四十亿版本已经接近九十亿版本，而最小模型的差距更明显。但这些成绩来自特定评测集，不等于换到任何业务场景，都能达到同样的准确率。

项目还把 Kev 和托管模型 Jev 做了比较。不过，作者不知道 Jev 用过哪些训练数据，而且 Jev 没有运行同一套测试集。因此，这不是两个架构之间严格受控的优劣比较。

再看概率本身。

选对答案，和正确表达把握大小，是两回事。一个模型可能经常选对，却也会在答错时表现得过分自信。

Kev 默认会做概率校准。通俗地说，就是根据开发集上的表现，调整概率的尖锐程度，让模型不要轻易把一个判断说得太满。

这种校准不会改变哪个选项排名第一，所以准确率不变。但在新数据来源上，九十亿版本那些“选错了，却给出至少百分之九十概率”的高自信错误，占比从百分之八点七降到了百分之四。

这也是为什么，不能只盯着最终标签，还要看概率分布。

同时要注意，接口里另有一个叫“置信度”的字段。这个字段是根据概率分布计算出来的指标，并不是经过测量的正确率。置信度是零点八，不能直接理解成“这个答案有百分之八十的机会正确”。

概率校准也没有解决所有推理短板。项目发现，Kev 不擅长可靠地计算两个日期之间相隔多少天，但如果直接告诉它天数，它就更容易正确应用期限规则。

因此，项目提供了一个可选功能：发现输入里的绝对日期后，补充日期之间的天数。在期限政策题上，这让九十亿版本的准确率从百分之八十提高到百分之九十。前面介绍的总体评测成绩，没有开启这个功能。

最后看部署。小模型能放进自己的电脑，不代表在所有硬件上都同样快。

项目建议多数人从四十亿版本开始。更重视准确率和概率质量，可以选九十亿版本；更在意模型体积，可以选八亿版本。四十亿和九十亿版本，都能以项目所用的精度格式运行在三十二吉字节内存的 Mac 上。

不过，在苹果芯片上，千问三点五的部分计算层还缺少快速实现。这会让新模型比旧一代慢不少。

在项目的 M5 测试中，同样处理五个问题，新版四十亿模型的模型计算时间中位数约为零点七八秒，旧版四十亿模型约为零点一七秒。因此，如果在 Mac 上最看重低延迟，作者目前建议使用旧版千问三模型，而不是单纯追求最新版本。

部署还有一个直接的安全边界：服务器默认只监听本机，而且没有身份认证。如果要开放到网络上，需要自己加认证，不能直接裸露服务。

Kev 最有价值的地方，是把文本判断做成了可本地运行、能批量提问、还能返回概率的专用工具。使用时，要分清答案、概率和置信度，也要记住：问题隔离不代表选项顺序无关，评测表现也不代表所有场景下的可靠性。选模型时，除了大小和准确率，还要看实际硬件上的速度。
