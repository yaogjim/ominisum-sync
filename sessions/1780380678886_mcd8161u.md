## 分析要点

- **核心高价值点**：多智能体设计的核心不是堆叠提示词，而是通过明确角色、独立上下文和受限工具来降低单代理复杂度。
- **留存建议**：短期参考后可删除
- **不足**：内容来自社交媒体线程，包含较多未经验证的产品能力、未来日期和案例引用，证据链薄弱，不适合作为长期权威资料。

**知识要点**

- 单代理能力过多会导致上下文拥挤、工具混乱和注意力分散，多智能体可通过专业化缓解该问题。
- 协调器应负责委派、汇总和输出格式控制，而不是亲自执行具体领域任务。
- 专家代理应限制工具权限，只访问完成其职责所需的信息，以提升可控性和可审计性。
- 多智能体系统只有在任务可并行、可专业化或需要模型分层升级时才值得引入。

**行动项**

- 若尝试多智能体架构，先选择一个可并行拆分的小任务，设计一名协调员和三名专家。
- 在实际采用文中 Claude 托管代理、agent\_toolset、Dreaming 等能力前，逐项查验 Anthropic 官方文档。
- 为每个代理定义一句话职责、可用工具、输入范围和输出格式，避免角色重叠。
- 运行实验时重点观察委派链路、成本、延迟和错误来源，判断是否真的优于单代理方案。

#### 为什么一名经纪人会遇到瓶颈。

你构建了一个代理。它起作用了。所以你给它分配了更多的任务。

添加研究能力。添加报告撰写功能。添加数据分析。添加一个审核步骤。每一次添加都使系统提示更长、工具列表更大，并且上下文窗口更拥挤。

然后有一天，你发现这个智能体变得越来越慢、越来越困惑，在它曾经能轻松完成的任务上表现得更差。这不是模型的问题，而是架构的问题。

单个代理只有一个上下文窗口，而你附加的每一项能力都会争夺相同的有限注意力。当复杂度超过一定程度时，一个同时处理十项工作的通才，其表现会比十个每个只做一项工作的专家更差。

修复是一个团队的工作。而不是更大的提示 - 而是分工。

![Image](https://pbs.twimg.com/media/HJEtYubWEAANm1E?format=png&name=large)

有三个事实定义了该架构，直接来自文档： 最多 20 个独特的代理在花名册中，每个都有自己的独立的隔离上下文窗口 ，所有代理共享一个文件系统。 独立思考，共享工作空间——这正是让团队能够并行工作而不混乱的原因。

#### 决策与设计

> 01\. 确认你确实需要一个团队

不要因为多智能体听起来很厉害就使用它。它会消耗更多 token，并且增加协调开销。当以下三种情况之一成立时才使用它：

- 并行化。工作被分解为独立的子任务——独立的日志文件，独立的代码模块。单个代理按顺序执行这些任务；而团队可以同时执行这些任务。
- 专业化。 不同的问题需要不同的专业知识——安全审查员、文档撰写者、定价模型师——而一个在这些角色间进行上下文切换的通才会削弱所有这些专业工作的质量。
- 升级大部分工作很简单，但有些子任务却意外地困难。团队会将困难的子任务转移到更强大的模型上处理，而不是在每一步都为它付费。

> 02\. 在你开始写任何内容之前明确角色

多智能体设计即组织设计。在编写任何代码之前，先在纸上勾勒团队结构：一名协调员，以及一组专家，每个人都有明确的职责。

将其锚定在真实模式中。Anthropic 记录的事件响应示例：主导代理开展调查，子代理同时分散到 部署历史、错误日志、指标和支持工单——同时进行。

四名专科医生、一名协调员，原本对单个代理而言是串行的工作现在并行进行。

为每个角色命名，为其赋予一个一句话的职责描述，记录其模型和工具。如果两个角色有重叠，将它们合并。 更少、更敏锐的专家胜过众多模糊的专家。

> 03\. 选择每个角色对应的模型 - 这就是节省所在的地方

最容易被人们忽视的一点是：团队中的每个代理都可以运行不同的模型。你不会被锁定在一个模型上。

Every 的 Spiral 项目的生产模式证明了这一点——他们使用 Haiku 作为协调器，并使用 Opus 作为写作子代理。

![Image](https://pbs.twimg.com/media/HJEvBltXoAAJccQ?format=png&name=large)

协调器仅负责路由和排序，这是快速低成本的模型能够很好完成的。而需要大量资源的繁重工作，仅在真正需要的专业人员那里开展。

将模型与任务匹配。按角色混合不同层级是影响成本和速度的最大单一杠杆。

#### 组建团队

> 04\. 设置托管代理

每个多智能体请求都在 Claude 托管智能体上运行，并且需要 beta 头部信息 managed-agents-2026-04-01。SDK 会自动设置该头部信息。

为什么选择托管代理而非你自己的配置？因为当团队需要远程运行、扩展到大量用户、共享文件系统和持久化状态时，你就会面临基础设施问题——会话、内存、安全、沙箱。

Managed Agents 处理所有这些工作，因此您只需设计团队即可。 安装 Anthropic SDK，从控制台设置您的 API 密钥，即可开始使用。

![Image](https://pbs.twimg.com/media/HJEwJTuWgAAA6Vs?format=jpg&name=large)

> 05\. 将每个专家创建为其自身的代理

构建专家，自下而上。每个都是拥有自身模型、提示词和范围限定工具集的独立智能体。创建它们并保留它们的智能体 ID——协调器将引用这些 ID。

关键的领域是： 严格限定每个专家的工具范围。 在‘食谱’的销售提案示例中，研究人员获得网络搜索权限，图书管理员仅获得文件阅读权限，而定价建模师仅能看到规则文件和座位数量。

每个代理只处理其工作所需的内容，不多也不少——这使得它保持专注，并且整个系统可审计。

> 06\. 创建协调员并申报花名册

现在，主代理。您可以通过设置多代理字段（列出其可能委派的子代理 ID），将代理标记为协调器。配置刻意简洁：

```plaintext
name: Engineering Lead
model: claude-opus-4-7
system: >
  You coordinate engineering work. Delegate code review
  to the reviewer agent and test writing to the test agent.
tools:
  - type: agent_toolset_20260401
multiagent:
  type: coordinator
  agents:
    - type: agent
      id: $REVIEWER_AGENT_ID
    - type: agent
      id: $TEST_WRITER_AGENT_ID
```

那个 agent\_toolset\_20260401 工具正是让协调器具备委派能力的关键。该列表最多可包含 20 个条目。

![Image](https://pbs.twimg.com/media/HJEztEiW8AA2La0?format=jpg&name=large)

你可以固定特定的代理版本、引用最新版本，或者使用{"type": "self"}让协调器生成自身的副本以实现递归并行化。

> 07\. 以管理者而非执行者的身份撰写协调者的提示

这是团队成败的关键所在。协调者的系统提示不应该尝试完成工作，而应该描述如何委派工作。

一个好的协调者提示应说明：这是你的专家，每个专家的职责是什么，如何决定谁负责什么任务，以及如何整合他们的成果。它需要考虑顺序和综合，而不是领域细节——这些细节由专家负责。 如果您正在向协调器中写入领域指令，那么该内容应该放在子代理中

以下是事件响应团队的一个真实协调员提示——请注意，它本身从不自行调查任何事情，只负责路由和综合

```plaintext
You are the incident-response coordinator. You do NOT
investigate anything yourself. Your only job is to delegate
to your specialists and synthesize what they return.

Your specialists:
- deploy_agent  → reviews recent deploy history for changes
- logs_agent    → searches error logs for anomalies
- metrics_agent → checks dashboards for abnormal patterns
- tickets_agent → scans support tickets for user reports

How to work:
1. When an incident arrives, delegate to ALL FOUR
   specialists in parallel — do not wait for one before
   starting the next.
2. Give each specialist only the incident description and
   the time window. Nothing else.
3. When results return, look for correlation across them
   (e.g. a deploy that lines up with a log spike and ticket
   surge points to a root cause).
4. If one specialist's finding is unclear, send it a
   follow-up — it remembers its previous turn.

Output format:
- ROOT CAUSE: one sentence, or "unconfirmed"
- EVIDENCE: one bullet per specialist that contributed
- RECOMMENDED ACTION: one clear next step

Never include raw logs or full ticket text in your final
answer — synthesize, do not dump.
```

每一行都涉及委派、关联和输出形态。实际的日志检索和指标读取工作由专业人员负责，这是它们应在的地方。

#### 运行，观察，改进

> 08\. 理解团队如何沟通

当你运行协调器时，其机制具体且值得了解

协调器委派的每个子代理都会生成其自己的会话线程 - 一个具有自身历史记录的上下文隔离的事件流。协调器在主线程中进行报告；随着协调器的委派，新线程在运行时出现。 关键的是，对话线程是持久的：协调器可以向之前调用过的代理发送跟进消息，并且该代理会保留其之前所有对话轮次的内容。

![Image](https://pbs.twimg.com/media/HJEyqz_XIAEiWTJ?format=png&name=large)

设计时需要考虑的一个硬性约束： 协调器只能进行一级深度的委派。 深度大于 1 的情况将被忽略。 专家无法管理自己的子团队。这是故意的——它使系统可预测且可追溯。

> 09\. 在 Claude 控制台中查看整个过程

生产型多智能体系统与实验型系统之间的区别在于可观测性。

每次运行都会在 Claude 控制台中生成完整的跟踪记录： 哪个代理做了什么、按什么顺序以及原因。 您可以查看每个委派决策，检查每个子代理的推理过程，端到端地跟踪整个流程。

![Image](https://pbs.twimg.com/media/HJEzzkCWIAAqkvD?format=png&name=large)

当结果出错时，追踪信息会告诉你哪位专家出现了失误，以及问题是出在任务分配还是专家本身。不要盲目管理团队——阅读追踪信息。

> 10\. 调整到20并添加共享内存

一旦小团队开始运作，就对其进行扩展。添加专家，直到团队规模达到20名代理的上限，让协调员同时覆盖所有成员。

然后通过共享内存形成闭环。当多个子代理在同一领域工作时，Dreaming 功能可以聚合它们共同学到的知识，并将共享见解发布到团队级别的内存存储中 ——这是单个代理会话无法单独实现的。

这个团队不仅仅是并行工作；随着时间的推移，它作为一个整体会变得更聪明。

这就是 Netflix 的平台团队在生产环境中运行的内容：多代理编排处理来自数百个同时进行的构建 ，并行子代理在数千个应用程序中发现反复出现的问题——这种工作在单代理设置中会完全是串行的。

#### 经纪人团队导致崩溃的错误 。

- 当一个代理就能完成工作时组建团队。 多代理成本更高且协调更慢。如果工作无法并行化、专业化或升级，你只是无谓地增加了复杂性。
- 一个亲自完成工作的协调器。 如果主导代理拥有领域指令而非委派逻辑，你构建了一个臃肿的单一代理，它穿着团队外衣。
- 工具范围松散。 当每个专家都能接触到所有工作时，注意力会分散，追踪变得不可读。将每个代理的职责范围准确限定在其本职工作上。
- 对抗深度-1 限制。 协调器仅向下委托一级。设计隐藏的子协调器层级会浪费时间——因为深度被忽略了。
- 盲目运行。 存在控制台跟踪，以便您可以查看哪个代理执行了什么操作。跳过它，您将无法调试具有动态组件的系统。

---

#### 结论：

大多数人会不断地往一个智能体中堆砌更多能力，看着它变慢并性能下降，进而得出结论，认为智能体还未准备好。

组建团队的人会拥有一些不同的东西：一个负责委派任务的协调者、在各自专业领域并行工作的专家、他们协作使用的共享文件系统，以及一个随着时间推移能让整个团队变得更敏锐的内存存储。

选择一项可以拆分为并行部分的任务。确定三名专家和一名协调员。先构建这个小团队。 仅这一点就会改变你的代理能够处理的工作量。

#### 一、总结

这篇文章讲的是：**不要把所有能力塞进一个 Claude Agent，而是把它拆成“一个协调员 + 多个专家”的团队。**

核心观点：

- 单个 Agent 能力越多，提示词越长、工具越杂、上下文越乱，性能会下降。
- 多 Agent 架构通过**分工**解决问题：
  - 协调员负责分派任务、汇总结果；
  - 专家 Agent 各自处理特定任务；
  - 最多可配置 20 个 Agent；
  - 每个 Agent 有独立上下文，但共享文件系统。
- 适合多 Agent 的场景：
  - 任务可以并行；
  - 需要不同专业能力；
  - 部分任务需要更强模型，其余任务可用便宜模型。
- 关键做法：
  1. 先确认是否真的需要团队；
  2. 明确角色；
  3. 给不同角色选择不同模型；
  4. 用托管 Agent 降低基础设施成本；
  5. 给每个专家限定工具；
  6. 创建协调员；
  7. 协调员只负责委派，不亲自干活；
  8. 注意只能一级委派；
  9. 用控制台追踪运行过程；
  10. 从小团队逐步扩展到最多 20 个 Agent。

#### 二、通俗解读

##### 1. 单 Agent 像“全能员工”

一开始，一个 Agent 可以做很多事：

- 查资料；
- 写报告；
- 分析数据；
- 检查错误；
- 总结结论。

但问题是：  
**事情越多，它越容易乱。**

就像一个员工同时做产品、研发、测试、销售、客服，最后每件事都做不好。

---

##### 2. 多 Agent 像“公司团队”

更好的方式是组团队：

| 角色 | 负责什么 |
|---|---|
| 协调员 | 分配任务、汇总结果 |
| 研究员 | 查资料 |
| 分析师 | 做数据分析 |
| 审核员 | 检查风险 |
| 文档员 | 写报告 |

每个人只做自己擅长的事。  
这样更快、更清晰，也更容易排查问题。

---

##### 3. 协调员不是“超级员工”

文章反复强调：

> 协调员不要亲自干活，只负责管理。

比如事故排查：

- 日志 Agent 查错误日志；
- 指标 Agent 看监控；
- 工单 Agent 看用户反馈；
- 部署 Agent 查最近发布记录；
- 协调员只负责把这些结果合起来，判断根因。

这才是多 Agent 的正确用法。

---

##### 4. 工具权限要收紧

每个 Agent 不应该拥有所有工具。

例如：

- 研究员可以联网搜索；
- 文件管理员只能读文件；
- 定价 Agent 只能看价格规则；
- 审核 Agent 只能看安全相关内容。

这样做的好处：

- 更专注；
- 更安全；
- 更容易审计；
- 更不容易跑偏。

---

##### 5. 不要为了炫技而多 Agent

多 Agent 不是万能药。

如果任务本身很简单，单 Agent 就够了。  
强行拆成团队，只会：

- 增加成本；
- 增加延迟；
- 增加调试难度。

---

#### 三、我的意见

我认同文章的核心观点：  
**未来 Agent 的重点不是“一个 Agent 更强”，而是“多个 Agent 更会协作”。**

但落地时要注意三点：

##### 1. 先从小团队开始

不要一上来就做 20 个 Agent。  
建议从：

> 1 个协调员 + 3 个专家

开始就够了。

例如：

- 协调员；
- 搜索 Agent；
- 分析 Agent；
- 写作 Agent。

跑通之后再扩展。

---

##### 2. 角色边界比模型更重要

很多人会纠结用什么模型。  
但更关键的是：

- 谁负责什么；
- 谁不能做什么；
- 工具权限怎么限制；
- 输出格式怎么统一。

角色设计不好，再强的模型也会乱。

---

##### 3. 一定要做可观测性

多 Agent 系统最怕的问题是：

> 出错了，但不知道是谁错了。

所以必须记录：

- 谁接到了任务；
- 谁调用了工具；
- 谁返回了什么；
- 协调员为什么这样汇总。

否则系统越复杂，越不可控。

---

#### 四、一句话结论

**单 Agent 适合简单任务；多 Agent 适合复杂、可拆分、可并行的任务。**

真正有效的多 Agent 系统，不是堆更多 Agent，  
而是设计清楚：

> 谁负责决策，谁负责执行，谁能用什么工具，最后如何汇总。
