#### 《为什么我转向 Pi Agent》精炼总结

Pi Agent 的核心优势不在于默认功能更多，而在于它提供了一个**几乎可以任意修改的智能体运行框架（harness）**：用户和智能体都能通过扩展改变工具、上下文、工作流、会话管理乃至界面。它既能作为轻量编码助手，也能作为构建本地或云端 AI 产品的底层运行时。

##### 1. 编码智能体的效果差距，关键在使用方式

作者认为，Claude Code、Codex 等主流编码智能体的基础能力已经越来越接近，真正的差距来自用户是否充分利用其运行框架，例如：

- 如何编写 `CLAUDE.md`、`AGENTS.md` 等项目说明；
- 如何把代码库整理成适合智能体理解和操作的结构；
- 如何用 Hooks 设置权限、检查和自动化行为；
- 如何保存任务状态，让长时间任务不偏离目标；
- 如何安全地并行运行多个会话。

成熟的配置方式，可能让使用效果产生 **10 倍甚至 100 倍**的差距。作者的并行会话方案可同时安全运行 **10～15 个智能体会话**，而这些方法大多也适用于 Pi。

##### 2. Pi 与 Claude Code、Codex 的根本区别

Claude Code、Codex、OpenCode 虽然都提供 CLI、SDK 和 Hooks，但用户通常只能在预留范围内扩展，无法真正修改框架内部的运行方式。

例如：

- Claude Code 有动态工作流，但 Codex 用户不能直接把同样的能力写进 Codex 内部；
- Hooks 可以在工具调用前检查权限，却未必能修改工具调用后的结果；
- 用户只能使用官方开放的事件和接口，很多 GitHub Issue 中提出的定制需求无法实现。

Pi 的设计理念则是：**框架应该适应用户，而不是让用户适应框架。**

##### 3. Pi 默认极简，但可以扩展几乎所有部分

Pi 默认只提供 4 个核心工具：

1. 运行 Bash 命令；
2. 读取文件；
3. 写入文件；
4. 编辑文件。

它默认没有子智能体、智能体团队或 MCP，功能看似简单，但通过 **Extension（扩展）** 可以修改或增加：

- 工具与命令快捷方式；
- 模型供应商；
- 系统提示词和上下文；
- Hooks 与权限逻辑；
- 会话管理；
- 终端命令和 UI；
- 子智能体、计划模式、浏览器控制、计算机操作等能力。

更重要的是，扩展既可以由开发者编写，也可以让 Pi 自己生成和修改。Pi 知道当前加载了哪些扩展，也了解扩展 API，因此具备一定的“自我进化”能力。

##### 4. 动态修改自身：天气组件与工作流案例

作者演示了让 Pi 在输入框上方显示天气信息：

1. 直接告诉 Pi，希望在界面中显示天气；
2. Pi 自动阅读扩展文档；
3. 编写天气组件扩展；
4. 用户执行 `/reload`；
5. 新界面立即生效。

类似地，用户可以从 Pi 的扩展目录安装其他人开发的功能，例如：

- MCP 适配器；
- Chrome 浏览器访问；
- “向用户提问”工具；
- 子智能体与计划模式；
- 动态工作流；
- 计算机操作；
- 模拟 Claude Code 或 Codex 使用体验的完整扩展。

安装动态工作流扩展后，用户既可以在提示词中使用 `workflow` 关键词触发，也可以通过 `/workflow` 打开类似 Claude Code 的工作流界面。

##### 5. Pi Hyper：通过处理工具输出大幅节省 Token

作者重点介绍了一个名为 **Pi Hyper** 的扩展。它会拦截工具调用结果，只把真正相关的信息返回给智能体。

例如，普通 `git log` 可能返回：

- Commit Hash；
- 作者；
- 日期；
- 正文；
- 大段 Diff。

Pi Hyper 可以预处理这些结果，只保留任务需要的部分。作者称，在部分测试中：

- 某类 Git 输出可减少约 **96%**；
- 其他测试中，Token 消耗可降低约 **80%～90%**。

这种能力在 Claude Code 或 Codex 中较难实现，因为它们的一些工具调用前 Hooks 只能追加信息，不能直接重写工具返回结果。

##### 6. OpenClaw 为什么选择 Pi 作为底层

OpenClaw 最初主要负责连接 Slack、Web 界面等入口，而把 Pi 用作核心智能体运行时。

它可以复用 Pi 已有的：

- Agent Loop（智能体循环）；
- 大模型调用能力；
- 会话管理；
- 工具执行机制。

同时再扩展：

- MCP；
- 记忆系统；
- 子智能体；
- ACP；
- 其他产品专用能力。

如果底层采用 Claude Code SDK 或 Codex CLI，这种深度修改会更加困难。因此，**Pi 的开放式框架是 OpenClaw 选择它的重要原因**。

##### 7. 三个扩展开发案例

###### 7.1 自动注入 Git 上下文

开发者可以在项目或用户目录下创建 `.pi/extensions`，然后用 TypeScript 编写扩展。

例如，在智能体启动前运行 Git 命令，获取：

- 当前分支；
- 可用 Worktree；
- 未暂存修改；
- 最近提交记录。

随后通过 `before_agent_start` Hook，把摘要追加到系统提示词中。这样即使要求 Pi“不要调用工具”，它仍能直接回答当前仓库状态。

###### 7.2 增加读取剪贴板工具

通过 `pi.register_tool` 注册新工具，并定义：

- 名称；
- 标签；
- 描述；
- 参数；
- 实际执行函数。

完成后，Pi 就可以根据用户指令读取剪贴板内容。这说明扩展不仅能调整提示词，也能直接增加新的操作能力。

###### 7.3 用小模型建立权限闸门

针对团队中不同成员拥有不同数据权限的情况，作者设计了一个权限检查扩展：

1. 用户发送请求；
2. 请求暂不进入主智能体；
3. 使用便宜、快速的小模型，如 Haiku，先判断“允许”或“拒绝”；
4. 模型同时输出判断理由；
5. 若拒绝，则直接终止请求；若允许，主智能体才继续执行。

权限规则可写在根目录的 `permission.md` 中。例如规定“只有 Jason 可以访问收入数据”。当其他用户询问“6 月收入是多少”时，界面会直接显示无权访问，不让主智能体接触或处理该请求。

##### 8. Pi 不只是编码助手，更是一套 AI 产品开发组件

Pi 仓库提供了 **5 类底层包/组件**，可按产品需求组合使用：

1. **AI 包**  
   类似 Vercel AI SDK，用于调用不同大模型，并提供 OAuth 能力，让用户连接 Claude Code、Codex 等订阅。

2. **Agent 包**  
   提供基础 Agent Loop，可理解为带有轻量智能体循环的模型流式调用能力。

3. **Coding Agent 包**  
   在前两者基础上加入读写文件、编辑、Bash、会话管理、上下文压缩、扩展系统和 SDK。它类似 Claude Code Agent SDK，但可自由替换模型并深度修改。

4. **TUI 包**  
   把编码智能体包装成终端用户界面。

5. **实验性任务调度组件**  
   用于定时任务，或把任务委派给不同的 Pi Agent 进程。

开发者可以只使用模型调用层，也可以直接使用完整的 Coding Agent SDK 来搭建产品。

##### 9. 构建本地智能体产品

如果智能体运行在用户自己的电脑上，Pi Coding Agent SDK 已提供大部分基础能力，开发者主要需要增加：

- 自定义扩展；
- 专属 UI；
- 任务触发器；
- 产品级工具和交互逻辑。

作者提到一个基于 Pi 构建的本地编码智能体案例，它增加了：

- 更接近 Claude Code、Codex 的工具能力；
- 终端内编辑器式界面；
- 会话发布功能；
- 可分享的 URL 和二维码。

这说明 Pi 不只适合个人脚本，也能支撑较完整的本地智能体产品。

##### 10. 构建 Web 托管智能体时的改造重点

Pi Coding Agent SDK 默认与本地文件系统结合较紧。如果要构建 Web 托管产品，智能体运行在共享后端，而每个用户拥有独立沙箱，就需要额外处理：

- 不直接使用本地文件形式的会话管理；
- 将会话状态存入数据库；
- 自行管理上下文压缩；
- 包装 Bash、读取、写入和编辑工具；
- 确保所有操作都发生在对应用户的沙箱内；
- 通过工具代理限制用户可访问的资源。

这些问题并非 Pi 独有，即使使用 Claude Code Agent SDK，也需要进行类似的隔离和持久化设计。

##### 11. Web 产品中的资源加载与护栏

在 Web 应用中，开发者可以使用资源加载器为每个智能体会话指定：

- 工作目录；
- 扩展目录；
- 可加载的 Skills；
- 自定义工具；
- 内联扩展；
- 安全护栏。

作者举例设计了一个 Guardrail 扩展，用来阻止某些危险 Bash 命令；同时注册了一个返回模拟 MRR（月度经常性收入）数据的工具。

随后通过 `createAgentSession` 创建会话，并根据智能体产生的不同事件，在前端展示消息、工具调用和执行结果。这样可以为不同用户或任务配置不同的技能与权限。

##### 12. 用 Pi 构建“自主经营公司”的智能体系统

作者使用同一套 Pi SDK 构建了一个类似 Post AI/Posia 的托管式系统，希望让智能体自动启动和运营公司。

该系统：

- 以 Pi Coding Agent SDK 作为运行时；
- 拆分为 **11 个不同智能体**；
- 使用一个协调器统一分配任务；
- 围绕任务实体组织流程；
- 持久化保存状态和上下文；
- 通过工具代理访问外部能力。

这一案例体现了 Pi 的最大价值：它不仅能作为一个可定制的编码工具，还能成为复杂、多智能体 AI 产品的基础设施。

##### 总结

Pi Agent 的主要竞争力是**极简内核、完整扩展能力和可嵌入式 SDK**。如果只需要开箱即用的编码助手，Pi 未必天然优于 Claude Code 或 Codex；但如果需要修改智能体运行机制、降低 Token 消耗、建立复杂权限、设计专属 UI，或构建本地及云端 AI 产品，Pi 提供了更高的自由度。

#### 为什么转向 Pi：从极简编码代理到可自我改造的 Agent 底座

文章从一个现实差距讲起：同样使用 Claude Code、Codex 一类编码代理，只在终端里发出提示词、等待结果的人，与能够配置项目上下文、钩子、护栏、任务状态和并行会话的人，实际效果可能相差十倍甚至百倍。沿着“代理运行框架能否被用户真正改造”这条线索，作者解释了 Pi 的特殊之处，并进一步展示如何以 Pi 为底座，搭建一个可以启动和运营公司的多代理系统。

##### 编码代理越来越相似，真正的差别转向了运行框架

在进入 Pi 之前，作者先谈到自己使用 Claude Code、Codex 等编码代理的经验。现代编码代理的能力并不只取决于模型，也取决于围绕模型搭建的运行框架，也就是文中反复提到的 harness。项目里的 `CLAUDE.md` 或 `agent.md` 应该怎样写，代码库如何整理得更适合代理工作，钩子和护栏如何设置，长时间任务怎样保存状态，以及如何同时运行多个会话而不把项目弄乱，这些都会直接影响最终效果。

作者为此制作了一份 Claude Code Playbook，记录自己的提示词模式、项目上下文配置、钩子、护栏和长任务状态管理方法。其中他特别提到一套并行会话配置：它不是只能同时运行一两个代理会话，而是可以安全地并行运行10到15个会话。尽管这份材料以 Claude Code 命名，其中的大部分原则并不依赖某个特定代理，因为 Claude Code 的许多功能，在 Pi 中也能找到相应的软件包或扩展。

这也引出了作者近几周对“Claude Code 和 Codex 哪个更好”这一问题的回答：它们已经越来越接近，很难再说存在本质差别。Claude Code、Codex、OpenCode 都提供了 SDK 或命令行工具，开发者可以把它们包装起来，构建新的 Agent 系统。但问题在于，这些工具虽然强大，用户通常无法深入修改其内部运行框架。

Claude Code 和 Codex 仍各有自己的独特功能。如果 Claude Code 提供了某种动态工作流，Codex 用户不能简单要求 Codex 把同样的机制直接实现到自身框架里，反过来也一样。它们虽然逐渐开放了钩子系统，但钩子通常只能让用户在某些事件发生时插入程序化行为，例如会话启动时运行一段逻辑，或者在代理调用工具前检查权限。

作者举了一个典型用法：每次 Claude Code 准备调用工具时，钩子可以自动读取用户写好的权限规则，并返回允许或拒绝。这已经很有用，却仍然受到框架预先开放的事件和接口限制。GitHub issue 中还有许多用户希望修改、但现有钩子做不到的场景。Pi 的设计正是从这里与其他编码代理分开。

##### Pi 只提供四个基本工具，却允许用户修改几乎整个框架

Pi 的核心理念是，运行框架应当适应用户，而不是要求用户反过来适应框架。它默认提供的编码代理非常精简，只有四个关键工具：运行 Bash 命令、读取文件、写入文件和编辑文件。默认状态下没有子代理、没有 Agent Team，甚至没有内置 MCP。

这种简陋不是因为 Pi 无法提供更多功能，而是因为它把功能扩展权交给了用户。Pi 提供了一套 extension 机制，人类用户或代理本身都可以编写扩展文件，修改编码代理的运行方式。它开放的范围覆盖工具、上下文、钩子、会话管理、命令、用户界面等多个部分。用户可以增加新的工具、命令快捷方式和大模型提供商，也可以使用大量事件钩子编写新的程序逻辑。

连终端界面本身也可以修改。作者展示了一个简单实验：他要求 Pi 在提示词输入框附近显示天气信息，让它帮助定制自己的界面。Pi 会先读取扩展文档，再自行编写一个天气组件扩展。扩展生成后，用户执行 `/reload`，Pi 就会立即重新加载刚刚创建的运行框架，天气信息随即出现在提示词输入框上方。

这个天气组件只是界面层面的一个小例子。更重要的是，Pi 知道当前已经加载了哪些扩展，也知道扩展应当怎样编写，因此用户可以在运行过程中要求它修改自己。许多时候，人并不需要先学会扩展 API，只要描述想要的功能，Pi 就可以读取文档、编写扩展并在重新加载后使用。

Pi 还有一个扩展软件包目录。虽然默认版本没有子代理、MCP 或浏览器能力，但社区已经实现了大量可以直接安装的功能，包括 MCP 适配器、Chrome 浏览器访问、向用户提问的工具、子代理、计划模式、动态工作流和计算机操作能力等。

作者以动态工作流扩展为例：复制对应软件包、运行安装命令，再重新加载 Pi 后，用户就可以在提示词中使用与工作流有关的关键词来触发功能，也可以输入 `/workflow` 打开工作流界面。实际体验与 Claude Code 中的对应功能非常接近。甚至还有一些软件包会把 Pi 配置成类似 Claude Code 或 Codex 的形态，把其他运行框架中的特殊工具一次性带进来；另有扩展允许用户在代理运行时操作 DOM。

作者也承认，社区扩展不一定都制作得足够成熟。但由于 Pi 自身能够读取并改写扩展，技术上仍可以要求代理继续完善它们。这种能力让一些难以在封闭框架中实现的功能成为可能。

##### Pi Hyper从工具返回结果入手，直接压缩代理消耗的上下文

作者特别介绍了一个名为 Pi Hyper 的软件包。它会捕获各种工具调用的钩子，例如 Bash 命令执行后的返回结果，并在内容交给代理之前进行预处理，只留下真正相关、必要的信息。

例如，代理运行 `git log` 查看近期提交时，原始命令可能返回每次提交的哈希值、作者、日期、正文和 diff 块。Pi Hyper 会先清理这些内容，把无关部分移除，只向代理展示当前任务真正需要的信息。按照作者给出的数据，仅这一处理就可能让这类返回内容减少约96%；在其他测试中，token 消耗也能减少80%到90%。

这一案例说明了 Pi 扩展机制与普通钩子的差异。在 Claude Code 或 Codex 中，工具调用前的钩子往往只能向调用过程追加信息，未必能够直接改写工具返回结果。Pi 则允许扩展深入到这一层，在信息进入代理上下文之前改变它。

作者认为，正是这套丰富的扩展系统，使 Pi 成为构建 Agent 产品的实用底座。OpenClaw 最初也是沿着这条路线搭建的：它主要开发了连接 Slack、网页界面等应用的网关，同时把 Pi 作为核心 Agent 运行时，利用其代理循环、模型接入和会话管理，再继续扩展 MCP、记忆、子代理、ACP 等功能。如果改用 Claude Code SDK 或 Codex CLI，这种程度的定制会困难得多。

##### 从 Git 上下文到权限闸门，扩展可以直接改变代理的工作方式

为了说明扩展并不难写，作者连续展示了三个例子。

第一个例子是在代理每次启动时，自动注入当前 Git 仓库的信息。用户只需要在项目目录或根目录中创建 `.pi` 文件夹，再在其中建立 `extensions` 文件夹，放入 TypeScript 扩展文件。扩展中的 Git 函数会运行相关命令，收集当前分支、已有 worktree、未暂存改动和近期提交，再把这些内容整理成 Git 摘要。

接下来，扩展监听 `before_agent_start` 事件，在代理启动前修改系统提示词，把 Git 摘要追加到预设系统提示词之后。此后每次加载 Pi，代理都会自动获得这部分上下文。作者因此可以直接问它当前的 Git 信息，并明确要求“不要使用工具回答”；Pi 仍然能够回答，因为信息在会话开始前已经被写入上下文。

第二个例子是为 Pi 增加读取剪贴板的工具。扩展通过 `pi.register_tool` 注册工具名称、标签、描述和参数，再定义实际执行函数。配置完成后，作者复制了前一个 Git 上下文扩展的内容，然后询问 Pi：“我的剪贴板里有什么？”代理便会调用这个新工具读取剪贴板。

第三个例子更接近真实团队环境：在用户消息进入主代理之前，增加一道权限检查。作者设想，同一个 Agent 系统可能由多名团队成员使用，而每个人能够访问的信息级别不同。与其让消息直接进入代理，或者让主代理自行判断用户是否有权访问，不如先调用一个便宜、速度快的小模型进行检查。请求安全时，会话照常继续；如果请求涉及不应访问的信息，就直接停止，不再运行主代理。

这个权限扩展同时使用了 Pi 的 coding agent 包和 Pi AI 包。前者提供扩展 API，后者让开发者能够方便地调用不同大模型。作者选择 Haiku 作为权限判断模型，要求它输出“允许”或“拒绝”，并给出判断理由。权限判断所需的信息由两部分组成：根目录中用户自行维护的 `permission.md` 策略文件，以及用户刚刚发送的请求。

会话开始时，扩展先加载权限策略。此后每当用户发送消息，界面上会显示正在进行权限检查，并等待小模型返回结果。如果结果为拒绝，界面就展示拦截信息，完全跳过主代理；如果允许，则继续原来的流程。

作者在测试用的 `permission.md` 中规定，只有 Jason 可以获取营收数据。随后他向 Pi 询问六月份的营收，权限模型立即拦截请求，并显示用户无权访问营收信息。整个过程中，敏感请求没有被交给主代理处理。这说明 Pi 的扩展并不只是增加一个外围小工具，而是可以真正改变消息进入代理、工具被调用以及会话是否继续的方式。

##### Pi 的五层软件包让它不只是编码工具，也能成为产品基础设施

在作者看来，Pi 更大的价值并不是作为另一个终端编码代理使用，而是作为 AI 产品的基础运行时。Pi 的代码仓库包含五类不同层次的软件包，开发者可以根据产品需要选用。

第一类是 AI 包。它类似 Vercel AI SDK，用来调用不同的大语言模型，并包含 OAuth 相关能力，可以让应用用户连接 Claude Code、Codex 等订阅。即使不使用完整的 Pi 编码代理，开发者也可以单独用这个包在自己的应用中发起模型调用。

第二类是 agent 包，它提供核心代理循环。作者把它类比为带有一个小型 Agent Loop 的流式文本生成函数。

第三类是 coding agent 包。它建立在 AI 包和代理核心循环之上，同时带有读取、写入、编辑和 Bash 等基础工具，以及会话管理、上下文窗口压缩、扩展系统和 SDK。它在定位上近似 Claude Code Agent SDK，但内部可以完整定制，也能够连接用户选择的模型。

第四类是 TUI 包，它负责把 coding agent 包装成终端用户界面。第五类则是一个仍较实验性的调度类软件包，可用于建立定时任务，或者把任务委派给不同的 Pi Agent 进程。

这种分层意味着，开发者不必把整个 Pi 原样嵌入产品。只需要模型调用时可以采用 AI 包；需要代理循环时可以加入 agent 包；如果要构建运行在用户电脑上的完整本地代理，则可以直接使用 coding agent SDK，再按需求添加扩展、定制界面和任务触发器。

作者提到的 Oh My Pi 就是一个建立在 Pi 软件包之上的本地编码代理。它增加了许多新工具，使性能更接近 Claude Code 和 Codex；终端中还带有类似编辑器的用户界面。它甚至允许用户发布某一段对话会话，生成可以扫描的二维码或可分享的 URL，供其他人查看。这表明，Pi 不只能搭建一个简单命令行助手，也可以支持相当复杂的本地 Agent 产品。

##### 从本地文件系统迁移到网页沙箱，Post AI被拆成11个代理

作者随后把重点转向自己搭建的 Post AI 复刻版。这是一个网页托管的 Agent 系统，目标是自主启动并运营一家公司，底层运行时使用的仍然是 Pi coding agent SDK。

不过，Pi coding agent SDK 默认与本地文件系统结合得很紧。对于运行在用户自己电脑上的代理，这种设计很方便；但网页托管产品的 Agent 实际运行在共享的后端基础设施上，而不同用户必须拥有彼此隔离的沙箱。只要代理需要写文件或执行 Bash 命令，系统就必须确保操作发生在当前用户自己的沙箱中。

因此，网页产品不能完全照搬 Pi 默认的会话管理。Pi 原有的 Session Manager 会把会话直接保存在电脑上的日志文件中，托管服务则更适合把会话信息存进数据库，并自行管理上下文压缩。默认的 Bash、编辑、读取和写入工具也需要再包一层，把所有操作转发到对应用户的沙箱。作者指出，即使换成 Claude Code Agent SDK，网页部署同样需要处理这些基础设施问题。

在具体实现中，他仍然使用 Pi coding agent 包，但通过默认的 Resource Loader 为不同 Agent 会话加载额外扩展和技能。例如，他定义了一个护栏扩展，用来阻止代理运行某些 Bash 命令；又定义了一个获取 MRR 的工具，并用模拟结果进行演示。

Resource Loader 可以接收代理应当工作的目录，也可以指定扩展和技能文件所在的目录。开发者能够决定是否自动加载 `.pi` 文件夹里的扩展和技能，也可以传入直接写在代码中的自定义扩展。作者把前面定义的护栏扩展和额外技能一起交给 Resource Loader，以此控制每个 Agent 会话究竟可以使用哪些能力。

随后，程序通过创建 Agent Session 的函数，把自定义工具和 Resource Loader 一并传入。Agent 运行时产生不同事件，网页前端再根据事件类型展示对应信息，从而形成用户可以持续对话的聊天式 Agent 界面。

最终，作者用同一套 Pi SDK 搭建了 Post AI 的复刻系统。这个托管式 Agent 产品被拆分为11个不同代理，外部还有一个围绕任务实体构建的协调器。系统会持久化任务状态和上下文，并通过工具代理层控制各个 Agent 对外部能力的使用。

从最初的四个基础工具，到能够修改界面、过滤工具返回、注入 Git 上下文、执行权限判断，再到支撑11个代理协作的网页产品，Pi 的价值并不在于默认功能比其他编码代理更多。恰恰相反，它从一个极简框架开始，把工具、上下文、会话、界面和运行流程都开放出来，让开发者能够按产品需求逐层改造。作者转向 Pi 的原因，也正是这种从“使用一个编码代理”走向“掌握并重建整个 Agent 运行框架”的能力。

##### 首先，Pi 不只是一个编码助手，更是一个可以改造的代理框架

首先，Pi Agent 的本质仍然是一个编码代理。也就是说，它可以读写文件、运行命令，并根据用户指令完成编程任务。

作者认为，到了现在，Claude Code、Codex 等主流编码代理，在日常使用体验上已经越来越接近。单纯比较“谁更会写代码”，差别没有过去那么明显。真正让作者选择 Pi 的原因，是 Pi 的内部运行框架可以被用户深度修改。

这里的“运行框架”，英文通常叫 harness。它不只是模型本身，还包括工具调用、上下文管理、会话管理、界面，以及代理怎样一步步完成任务。

其他编码代理通常也提供 SDK，也就是软件开发工具包，或者 CLI，也就是命令行工具。开发者可以在外面包一层，做出新的代理系统。但问题是，内部框架本身通常不能随意改变。

比如，Claude Code 可能有自己的动态工作流功能。Codex 用户不能简单地告诉 Codex：“请把这个动态工作流直接加入你的内部框架。”反过来也一样。

这些产品虽然逐渐开放了钩子机制。所谓“钩子”，就是在某些事件发生时自动执行一段程序，比如会话开始时，或者代理准备调用工具之前，先检查一次规则。

这种方式确实能增加一些控制能力。比如，代理每次准备运行命令时，先检查用户写好的权限规则，再决定允许还是拒绝。但钩子能干预的场景仍然有限。很多用户想修改的环节，并没有开放出来。

##### 接下来，Pi 的核心理念是让框架适应用户

Pi 的设计理念很直接：不是要求用户适应固定的代理框架，而是让代理框架适应用户。

Pi 默认提供的功能非常少。它只有四个关键工具：运行 Bash 命令、读取文件、写入文件和编辑文件。它默认没有子代理，没有代理团队，也没有内置 MCP。

MCP 可以理解为一种连接外部工具和服务的标准方式。Pi 默认不把这些功能全部塞进来，反而让系统保持轻量，然后通过扩展来增加能力。

Pi 的扩展，指的是一段可以加载到代理中的程序。用户可以自己写，代理也可以帮助用户写。扩展能够修改的范围非常广，包括工具、上下文、钩子、会话管理、命令界面，甚至整个用户界面。

作者演示了一个很直观的案例。他让 Pi 在输入框上方显示天气信息。Pi 会先读取扩展文档，然后自动写出一个天气组件。用户输入斜杠加上“reload”，也就是重新加载命令，Pi 就会立即启用刚刚创建的界面扩展。

这说明，Pi 不只是“使用扩展”，还可以在运行过程中帮助自己创建和修改扩展。

##### 更进一步，Pi 可以通过扩展复刻其他代理的功能

虽然 Pi 默认功能很少，但它已经有一个扩展包目录。用户可以从里面安装别人写好的功能。

目前，很多 Claude Code 和 Codex 的常用能力，都已经有人做成了 Pi 扩展。比如 MCP 适配器、浏览器访问、让代理主动询问用户的工具、子代理、计划模式、动态工作流，以及电脑操作能力。

以动态工作流为例，用户只要安装对应扩展，然后重新加载 Pi，就可以在提示词里加入相关关键词，或者输入工作流命令，获得接近 Claude Code 的使用体验。

甚至还有一些扩展，可以把 Pi 变得更像 Claude Code 或 Codex，把其他代理中的工具和操作方式一起带过来。

当然，作者也提醒，有些扩展的质量可能并不一样。但即使如此，用户仍然可以直接让 Pi 帮忙修改，甚至重新构建这些扩展。

##### 一个关键案例：Pi Hyper 可以显著减少无用信息

Pi 的扩展能力，最有价值的地方之一，是它可以修改工具调用产生的结果，而不只是附加一些新信息。

作者举了 Pi Hyper 这个扩展作为例子。它会拦截 Bash 命令的调用结果，然后先进行清理，只把真正有用的信息返回给代理。

例如，代理运行 Git log 查看最近提交时，原始结果可能包含提交哈希、作者、日期、正文以及大量差异内容。很多信息对当前任务其实没有帮助。

Pi Hyper 会把这些内容压缩，只留下关键部分。作者表示，在某类提交记录测试中，展示出来的无关信息最多可以减少百分之九十六；在其他测试中，输入给模型的令牌数量，也就是模型需要处理的文本量，减少了百分之八十到百分之九十。

这意味着，代理看到的信息更聚焦，模型消耗的上下文更少，长期任务也可能更加稳定。

作者认为，这类能力在 Claude Code 或 Codex 中更难实现。因为它们的工具调用钩子，往往只能在调用前增加信息，而不能直接修改工具返回的结果。

##### 然后，OpenClaw 正是利用了这种可扩展性

OpenClaw 选择 Pi 作为基础，核心原因就是 Pi 能够被深度改造。

OpenClaw 最初主要负责连接应用、Slack 和网页界面。Pi 则作为背后的代理运行时，负责代理循环、大语言模型调用和会话管理。

在这个基础上，开发者还可以继续加入 MCP、记忆系统、子代理、ACP 等组件。也就是说，Pi 提供了一个可用的代理核心，而具体产品需要什么功能，可以由开发者自行拼装。

作者认为，如果使用 Claude Code 的 SDK 或 Codex 的 CLI 来做同样的事情，很多底层行为很难修改。Pi 的扩展系统，则让这类定制更加直接。

##### 接下来，看三个具体的扩展示例

第一个例子，是让代理自动了解当前 Git 仓库的状态。

开发者可以在项目目录，或者用户根目录下，创建一个名为“.pi”的文件夹，再在里面建立“extensions”扩展目录。然后，用 TypeScript 写一个扩展。

这个扩展会运行 Git 命令，收集当前分支、工作树、未提交修改和最近提交等信息，再把这些内容整理成一段 Git 摘要，自动添加到代理的系统提示中。

这样一来，代理每次启动时，就天然知道当前代码仓库的状态。作者甚至可以要求它“不调用任何工具，直接告诉我 Git 信息”，代理也能回答。

第二个例子，是添加剪贴板工具。

开发者只需要注册一个新工具，定义工具名称、描述和参数，再写出读取剪贴板的函数。之后，用户复制一段内容，就可以直接让 Pi 读取剪贴板，而不是手动粘贴。

第三个例子，是建立权限闸门。

假设一个团队共同使用代理，但不同成员能访问的数据不同。开发者可以在代理真正处理请求之前，先调用一个便宜、快速的小模型进行权限判断。

作者使用 Haiku 作为这个权限模型，让它根据一份名为“permission.md”的规则文件，判断请求是允许还是拒绝。如果判断为危险或越权，就立即阻止整个会话；如果允许，才继续交给主代理处理。

作者设置的案例是：只有 Jason 可以查看收入数据。当普通用户询问六月收入时，Pi 会先进行权限检查，然后显示请求被阻止，而不会让主代理继续处理。

这说明，权限控制不一定要完全交给主模型，也可以在代理外面增加一道独立的安全检查。

##### 更重要的是，Pi 的价值不止在编码，还在于搭建人工智能产品

作者认为，Pi 真正强大的地方，不只是把它当作一个现成的编码助手来用，而是把它作为其他人工智能产品的底层组件。

Pi 的代码仓库中包含多个重要软件包。

第一个是 AI 软件包。它可以调用不同的大语言模型，也提供 OAuth 授权机制。OAuth 可以理解为一种让用户授权应用访问自己订阅服务的方式。借助它，开发者可以在自己的应用中调用模型，甚至让用户连接自己的相关订阅。

第二个是 Agent 软件包。它提供了代理循环，也就是让模型不断思考、调用工具、读取结果，再继续执行的基本流程。

第三个是 Coding Agent 软件包。它把代理循环、模型调用、读写文件、运行命令、会话管理、上下文窗口管理，以及扩展系统组合在一起。它的定位类似 Claude Code 的 Agent SDK，但可以连接不同模型，也允许开发者深度修改。

第四个是 TUI 软件包。TUI 是终端用户界面，意思是在命令行窗口里提供交互界面。它可以把编码代理包装成一个完整的终端应用。

第五个是用于调度的实验性软件包。它可以安排定时任务，也可以把任务分发给不同的 Pi 进程。

这套软件生态的意义是，开发者可以根据自己的产品需要，只挑选其中一部分能力，而不是从零开始搭建整个代理系统。

##### 最后，Pi 既适合做本地代理，也适合做网页产品

如果要做一个运行在用户自己电脑上的本地代理，Pi 的编码代理软件包已经提供了大部分基础能力。开发者只需要继续添加自己的扩展、界面和任务触发方式即可。

作者还展示了一个基于 Pi 构建的本地编码代理。它增加了更多工具，提供了类似编辑器的终端界面，还可以把某次对话发布出去，让其他人通过二维码或网址查看。

但如果要做一个运行在网页上的代理产品，就需要额外处理一些问题。

原因是，Pi 默认依赖本地文件系统。代理读写文件、运行 Bash 命令和保存会话，默认都发生在用户自己的电脑上。

而网页产品通常运行在共享的后台基础设施上。每个用户都应该拥有彼此隔离的沙盒，也就是独立、安全的运行空间。

因此，开发者需要把默认的会话管理改成数据库存储，并自己管理上下文。同时，还要给读、写、编辑文件和运行命令的工具包一层，让它们只能在当前用户的沙盒中执行。

作者指出，这并不是 Pi 独有的问题。即使使用 Claude Code 的 Agent SDK，开发网页代理时也需要处理类似的本地文件系统和用户隔离问题。

在他的网页代理示例中，开发者可以通过资源加载器指定代理工作目录、加载哪些扩展和技能，还可以加入自定义护栏。比如，禁止代理运行某些危险的 Bash 命令；或者添加一个查询月度经常性收入的工具，并返回模拟结果。

基于同一套 Pi SDK，作者还做了一个 Posia 的复刻版本。它是一个可以自主启动和运营公司的代理系统，底层使用 Pi 的编码代理 SDK 作为运行时。

这个系统被拆分成十一种不同的代理，并由一个协调器统一管理。协调器负责任务实体、状态和上下文的持久化，以及工具代理。简单来说，就是把一个复杂的长期业务拆成多个代理，再用一个中心系统持续追踪它们的工作进度。

#### 结尾回顾

最后，记住四个最重要的结论。

第一，Pi 和其他编码代理的主要差别，不是默认写代码能力，而是内部框架能不能被深度修改。

第二，Pi 默认只有四个基础工具，但通过扩展可以加入子代理、浏览器、动态工作流、权限控制等几乎所有需要的能力。

第三，Pi 的扩展可以修改工具调用结果和用户界面。像 Pi Hyper 这样的工具，能够大幅减少代理需要处理的无关信息。

第四，Pi 不只是一个编码助手，也是一套可以用来搭建本地代理、网页代理，甚至自主运营业务系统的开发基础。
