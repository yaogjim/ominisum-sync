Graphiti is a framework for building and querying temporal context graphs for AI agents. Unlike static knowledge graphs, Graphiti's context graphs track how facts change over time, maintain provenance to source data, and support both prescribed and learned ontology — making them purpose-built for agents operating on evolving, real-world data.

Unlike traditional retrieval-augmented generation (RAG) methods, Graphiti continuously integrates user interactions, structured and unstructured enterprise data, and external information into a coherent, queryable graph. The framework supports incremental data updates, efficient retrieval, and precise historical queries without requiring complete graph recomputation, making it suitable for developing interactive, context-aware AI applications.

Use Graphiti to:

- Build context graphs that evolve with every interaction — tracking what's true now and what was true before.
- Give agents rich, structured context instead of flat document chunks or raw chat history.
- Query across time, meaning, and relationships with hybrid retrieval (semantic + keyword + graph traversal).

Graphiti temporal walkthrough

A **context graph** is a temporal graph of entities, relationships, and facts — like *"Kendra loves Adidas shoes (as of March 2026)."* Unlike traditional knowledge graphs, each fact in a context graph has a validity window: when it became true, and when (if ever) it was superseded. Entities evolve over time with updated summaries. Everything traces back to **episodes** — the raw data that produced it.

What makes Graphiti unique is its ability to autonomously build context graphs from unstructured and structured data, handling changing relationships while preserving full temporal history.

A context graph contains:

Component What it stores

**Entities** (nodes) People, products, policies, concepts — with summaries that evolve over time

**Facts / Relationships** (edges) Triplets (Entity → Relationship → Entity) with temporal validity windows

**Episodes** (provenance) Raw data as ingested — the ground truth stream. Every derived fact traces back here

**Custom Types** (ontology) Developer-defined entity and edge types via Pydantic models

#### Why Graphiti?

Traditional RAG approaches often rely on batch processing and static data summarization, making them inefficient for frequently changing data. Graphiti addresses these challenges by providing:

- **Temporal Fact Management:** Facts have validity windows. When information changes, old facts are invalidated — not deleted. Query what's true now, or what was true at any point in time.
- **Episodes &amp; Provenance:** Every entity and relationship traces back to the episodes (raw data) that produced it. Full lineage from derived fact to source.
- **Prescribed &amp; Learned Ontology:** Define entity and edge types upfront via Pydantic models (prescribed), or let structure emerge from your data (learned). Start simple, evolve as patterns appear.
- **Incremental Graph Construction:** New data integrates immediately without batch recomputation. The graph evolves in real-time as episodes are ingested.
- **Hybrid Retrieval:** Combines semantic embeddings, keyword (BM25), and graph traversal for low-latency, high-precision queries without reliance on LLM summarization.
- **Scalability:** Efficiently manages large datasets with parallel processing, pluggable graph backends, suitable for enterprise workloads.

Graphiti's ingestion pipelines are designed for high concurrency. By default, concurrency is set low to avoid LLM Provider 429 Rate Limit Errors. If you find Graphiti slow, please increase concurrency as described below.

Concurrency controlled by the `SEMAPHORE_LIMIT` environment variable. By default, `SEMAPHORE_LIMIT` is set to `10` concurrent operations to help prevent `429` rate limit errors from your LLM provider. If you encounter such errors, try lowering this value.

If your LLM provider allows higher throughput, you can increase `SEMAPHORE_LIMIT` to boost episode ingestion performance.

The `mcp_server` directory contains a Model Context Protocol (MCP) server implementation for Graphiti. This server allows AI assistants to interact with Graphiti's context graph capabilities through the MCP protocol.

Key features of the MCP server include:

- Episode management (add, retrieve, delete)
- Entity management and relationship handling
- Semantic and hybrid search capabilities
- Group management for organizing related data
- Graph maintenance operations

The MCP server can be deployed using Docker with Neo4j, making it easy to integrate Graphiti into your AI assistant workflows.

##### Database Configuration

Database names are configured directly in the driver constructors:

- **Neo4j**: Database name defaults to `neo4j` (hardcoded in Neo4jDriver)
- **FalkorDB**: Database name defaults to `default_db` (hardcoded in FalkorDriver)

As of v0.17.0, if you need to customize your database configuration, you can instantiate a database driver and pass it to the Graphiti constructor using the `graph_driver` parameter.

```
from graphiti_core import Graphiti
from graphiti_core.driver.neo4j_driver import Neo4jDriver

# Create a Neo4j driver with custom database name
driver = Neo4jDriver(
    uri="bolt://localhost:7687",
    user="neo4j",
    password="password",
    database="my_custom_database"  # Custom database name
)

# Pass the driver to Graphiti
graphiti = Graphiti(graph_driver=driver)
```

##### Quick Start

```
from openai import AsyncOpenAI
from graphiti_core import Graphiti
from graphiti_core.llm_client.azure_openai_client import AzureOpenAILLMClient
from graphiti_core.llm_client.config import LLMConfig
from graphiti_core.embedder.azure_openai import AzureOpenAIEmbedderClient

# Initialize Azure OpenAI client using the standard OpenAI client
# with Azure's v1 API endpoint
azure_client = AsyncOpenAI(
    base_url="https://your-resource-name.openai.azure.com/openai/v1/",
    api_key="your-api-key",
)

# Create LLM and Embedder clients
llm_client = AzureOpenAILLMClient(
    azure_client=azure_client,
    config=LLMConfig(model="gpt-5-mini", small_model="gpt-5-mini")  # Your Azure deployment name
)
embedder_client = AzureOpenAIEmbedderClient(
    azure_client=azure_client,
    model="text-embedding-3-small"  # Your Azure embedding deployment name
)

# Initialize Graphiti with Azure OpenAI clients
graphiti = Graphiti(
    "bolt://localhost:7687",
    "neo4j",
    "password",
    llm_client=llm_client,
    embedder=embedder_client,
)

# Now you can use Graphiti with Azure OpenAI
```

**Key Points:**

- Use the standard `AsyncOpenAI` client with Azure's v1 API endpoint format:`https://your-resource-name.openai.azure.com/openai/v1/`
- The deployment names (e.g., `gpt-5-mini`, `text-embedding-3-small`) should match your Azure OpenAI deployment names
- See `examples/azure-openai/` for a complete working example

Make sure to replace the placeholder values with your actual Azure OpenAI credentials and deployment names.

The Gemini reranker uses the `gemini-2.5-flash-lite` model by default, which is optimized for cost-effective and low-latency classification tasks. It uses the same boolean classification approach as the OpenAI reranker, leveraging Gemini's log probabilities feature to rank passage relevance.

Graphiti can use any OpenAI-compatible `/v1` endpoint for LLM inference via `OpenAIGenericClient` — both **hosted providers** (DeepSeek, Together, OpenRouter, Fireworks, etc.) and **local servers** (Ollama, vLLM, llama.cpp, LM Studio). Local servers are ideal for privacy-focused applications or avoiding API costs. The example below uses Ollama; for any other provider, point `base_url` at its endpoint and set the appropriate `api_key` and `model`.

**Note:** Use `OpenAIGenericClient` (not `OpenAIClient`) for these endpoints. It is optimized for local models with a higher default max token limit (16K vs 8K) and handles structured outputs across compatible providers.

Install the models:

```
ollama pull deepseek-r1:7b # LLM
ollama pull nomic-embed-text # embeddings
```

```
from graphiti_core import Graphiti
from graphiti_core.llm_client.config import LLMConfig
from graphiti_core.llm_client.openai_generic_client import OpenAIGenericClient
from graphiti_core.embedder.openai import OpenAIEmbedder, OpenAIEmbedderConfig
from graphiti_core.cross_encoder.openai_reranker_client import OpenAIRerankerClient

# Configure Ollama LLM client
llm_config = LLMConfig(
    api_key="ollama",  # Ollama doesn't require a real API key, but some placeholder is needed
    model="deepseek-r1:7b",
    small_model="deepseek-r1:7b",
    base_url="http://localhost:11434/v1",  # Ollama's OpenAI-compatible endpoint
)

llm_client = OpenAIGenericClient(config=llm_config)

# Initialize Graphiti with Ollama clients
graphiti = Graphiti(
    "bolt://localhost:7687",
    "neo4j",
    "password",
    llm_client=llm_client,
    embedder=OpenAIEmbedder(
        config=OpenAIEmbedderConfig(
            api_key="ollama",  # Placeholder API key
            embedding_model="nomic-embed-text",
            embedding_dim=768,
            base_url="http://localhost:11434/v1",
        )
    ),
    cross_encoder=OpenAIRerankerClient(client=llm_client, config=llm_config),
)

# Now you can use Graphiti with local Ollama models
```

Ensure Ollama is running (`ollama serve`) and that you have pulled the models you want to use.

Graphiti depends on structured (JSON) output for entity/edge extraction and deduplication, and works best with models and providers that reliably honor it (OpenAI, Anthropic, Gemini). Reliability varies across OpenAI-compatible providers and especially on smaller or local models, so `OpenAIGenericClient` exposes a `structured_output_mode`:

- `"json_schema"` (default): requests native structured output via `response_format`. Best on capable models and providers that enforce the schema via constrained decoding.
- `"json_object"`: requests plain-JSON mode and injects the schema into the prompt instead. Use this for providers/models that don't reliably honor `json_schema` — including some local servers that accept the `json_schema` request but don't actually constrain output to it, where `json_object` can be *more* reliable.

When using smaller or local models:

- Prefer the most capable model you can run. Very small models frequently emit JSON that doesn't match the requested schema, which surfaces as extraction failures.
- Responses wrapped in Markdown ```` ```json ```` code fences are stripped automatically.
- Keep `SEMAPHORE_LIMIT` low (see above) — local servers and some providers have limited concurrency.

#### Telemetry

Graphiti collects anonymous usage statistics to help us understand how the framework is being used and improve it for everyone. We believe transparency is important, so here's exactly what we collect and why.

When you initialize a Graphiti instance, we collect:

- **Anonymous identifier**: A randomly generated UUID stored locally in `~/.cache/graphiti/telemetry_anon_id`
- **System information**: Operating system, Python version, and system architecture
- **Graphiti version**: The version you're using
- **Configuration choices**:
  - LLM provider type (OpenAI, Azure, Anthropic, etc.)
  - Database backend (Neo4j, FalkorDB, Kuzu, Amazon Neptune Database or Neptune Analytics)
  - Embedder provider (OpenAI, Azure, Voyage, etc.)

We are committed to protecting your privacy. We **never** collect:

- Personal information or identifiers
- API keys or credentials
- Your actual data, queries, or graph content
- IP addresses or hostnames
- File paths or system-specific information
- Any content from your episodes, nodes, or edges

This information helps us:

- Understand which configurations are most popular to prioritize support and testing
- Identify which LLM and database providers to focus development efforts on
- Track adoption patterns to guide our roadmap
- Ensure compatibility across different Python versions and operating systems

By sharing this anonymous information, you help us make Graphiti better for everyone in the community.

The Telemetry code may be found here.

export GRAPHITI_TELEMETRY_ENABLED=false
```

**Option 2: Set in your shell profile**

```

## 通俗精炼（1）

### 2026-07-15 05:50:09

#### Graphiti：为 AI Agent 构建可实时演化的 “长期记忆”

##### 一句话总结

Graphiti 是一个开源的**时序上下文图谱引擎**：它把对话、业务数据和外部信息持续整理为实体、关系与事实，并记录每条事实的**生效时间、失效时间及原始来源**，让 AI Agent 同时理解 “现在是什么” 与 “过去发生过什么”。

##### 它解决了什么问题

传统 RAG 通常把文档切成静态片段，通过向量检索寻找相似内容。面对用户偏好、订单状态、企业政策等持续变化的信息时，容易出现：

- 新旧事实混杂，无法判断哪个仍然有效；
- 数据更新需要批量重建索引或重新摘要；
- 文档片段缺少明确的实体关系；
- 答案难以追溯到原始数据。

Graphiti 将这些信息组织成持续更新的图谱，更适合需要**长期记忆、实时上下文和历史查询**的 Agent。

##### 核心数据模型

Graphiti 的上下文图谱由四部分组成：

- **实体（节点）**：用户、商品、组织、政策、概念等，摘要可持续更新。
- **事实 / 关系（边）**：如 “用户喜欢某品牌”，并附带有效时间窗口。
- **Episode（来源记录）**：原始对话、文本或结构化数据，所有事实都可回溯至此。
- **自定义类型（Ontology）**：可用 Pydantic 预先定义实体和关系，也可让结构从数据中逐步形成。

当事实发生变化时，旧事实不会被删除，而是被标记为失效，从而保留完整历史。

##### 关键能力

###### 1. 时序事实管理

系统自动处理事实的新旧更替，可回答：

- 现在什么是真的？
- 某个时间点什么是真的？
- 某项信息何时发生变化？

###### 2. 增量实时更新

新数据写入后直接融入现有图谱，无须重新计算整个图谱，适合高频交互和动态业务数据。

###### 3. 混合检索

同时结合：

- 语义向量检索；
- BM25 关键词检索；
- 图关系遍历；
- 基于图距离的结果重排。

相比单纯向量检索，它更容易找到语义相关且关系准确的上下文。

###### 4. 来源可追溯

每个实体和关系都能追溯到原始 Episode，便于解释、审计和纠错。

###### 5. 灵活的领域建模

既可以预先规定用户、订单、产品等业务类型，也可以先低成本接入数据，再根据实际模式逐步完善 Schema。

##### 与传统 GraphRAG 的区别

| 维度 | 传统 GraphRAG | Graphiti |
|---|---|---|
| 核心场景 | 静态文档总结与问答 | 动态 Agent 上下文与长期记忆 |
| 数据更新 | 批处理、周期性重建 | 连续、增量更新 |
| 时间处理 | 简单时间戳 | 明确的时序有效期与历史保留 |
| 冲突处理 | 依赖 LLM 重新总结 | 自动让旧事实失效 |
| 检索方式 | 依赖社区摘要和 LLM | 语义、关键词、图遍历混合检索 |
| 查询性能 | 常为数秒以上 | 通常可做到亚秒级 |
| 自定义类型 | 支持有限 | 可通过 Pydantic 定义 |
| 适应动态数据 | 较弱 | 较强 |

本质上，GraphRAG 更像 “理解一批文档”，Graphiti 更像 “维护一个持续变化的事实世界”。

##### Graphiti 与 Zep 的关系

- **Graphiti**：开源核心引擎，负责构建和查询单个上下文图谱。
- **Zep**：基于 Graphiti 的商业化托管平台，提供大规模运行、用户与会话管理、治理、监控、安全和 SLA。

选择建议：

- 需要高度定制、可自托管，并具备工程运维能力：选择**Graphiti**。
- 需要开箱即用、低延迟、企业安全与规模化保障：选择**Zep**。

##### 技术与接入方式

Graphiti 基于 Python 3.10+，默认使用 OpenAI 完成 LLM 推理和向量化，也支持 Azure OpenAI、Gemini、Anthropic、Groq 等服务。

图数据库支持：

- Neo4j；
- FalkorDB / FalkorDB Lite；
- Amazon Neptune；
- Kuzu，但已标记为弃用方向。

项目还提供：

- **MCP Server**：让 AI 助手通过 MCP 管理实体、关系、Episode 和检索；
- **REST API**：基于 FastAPI 对外提供服务；
- **Docker Compose**：快速启动 Neo4j 或 FalkorDB 环境。

##### 产品价值与适用场景

Graphiti 特别适合：

- 个性化 AI 助手与用户长期记忆；
- 客服、销售等持续更新客户状态的 Agent；
- 企业政策、组织关系和业务状态查询；
- 需要事实审计与来源追溯的 AI 系统；
- 多轮任务中持续维护人物、事件和关系的智能体。

它的核心产品价值不是 “检索更多内容”，而是让 Agent 获得一个**有结构、懂时间、可追溯且持续演化的上下文层**。

##### 采用时需要注意

Graphiti 是引擎而非完整平台，自建时仍需补齐用户体系、权限治理、监控、可视化和生产运维能力。同时，数据摄取依赖 LLM 与 Embedding 服务，吞吐量、成本和稳定性会受到模型限流影响，需要通过并发参数进行调优。

##### 最终判断

Graphiti 把 Agent Memory 从 “保存聊天记录” 升级为 “维护动态事实图谱”。对于信息频繁变化、需要历史追踪和关系推理的 Agent，它比静态 RAG 更合适；但如果业务只是对稳定文档进行问答，引入时序图数据库可能增加不必要的架构复杂度。

## 结构化（1）

### 2026-07-15 09:29:03

#### Graphiti：为 AI Agent 构建实时知识图谱

Graphiti 是一个开源的**时间型上下文图谱引擎**，用于让 AI Agent 持续理解不断变化的用户、事实和外部数据。它区别于传统静态知识图谱和批处理式 RAG，能够实时更新信息、保留历史记录和数据来源，并通过语义、关键词和图关系进行高效检索。

##### 一、Graphiti 解决的问题

传统 RAG 通常把文档切成文本块，再通过向量检索返回相关内容，存在以下局限：

- 数据更新依赖批处理，实时性较差；
- 难以表达实体之间的复杂关系；
- 事实变化后，旧信息通常会被覆盖或丢失；
- 查询历史状态和信息来源较困难；
- 依赖 LLM 总结，延迟可能达到数秒甚至几十秒。

Graphiti 面向的是**持续变化、需要实时交互和历史追溯的 AI 应用**，例如：

- 个人或企业 AI 助手；
- 具备长期记忆的 Agent；
- 实时客户服务系统；
- 需要追踪政策、产品或用户偏好变化的应用。

---

##### 二、什么是时间型上下文图谱

上下文图谱由实体、关系、事实和原始数据组成。与普通知识图谱不同，每条事实都带有明确的时间有效期。

例如：

> “Kendra 喜欢 Adidas 鞋（截至 2026 年 3 月）。”

如果之后她改为喜欢 Nike，Graphiti 不会直接删除旧事实，而是：

- 将 “Kendra 喜欢 Adidas” 标记为失效；
- 新增 “Kendra 喜欢 Nike”；
- 保留完整的历史变化过程；
- 允许查询 “当前情况” 或 “过去某个时间点的情况”。

###### 图谱的主要组成

| 组成部分 | 作用 |
|---|---|
| **实体（Entities）** | 人、产品、政策、概念等节点，实体摘要会随时间更新 |
| **事实 / 关系（Facts / Relationships）** | 以 “实体 → 关系 → 实体” 的三元组表示，并带有时间有效窗口 |
| **事件片段（Episodes）** | 输入的原始文本、对话或结构化数据，是事实的来源和依据 |
| **自定义类型（Custom Types）** | 开发者可通过 Pydantic 模型定义实体类型和边类型 |

Graphiti 会将从非结构化文本和结构化数据中提取出的事实，连接回产生它们的原始事件片段，从而实现完整的数据溯源。

---

##### 三、Graphiti 的核心特点

###### 1. 时间事实管理

每个事实都有有效时间范围：

- 记录事实何时开始成立；
- 记录何时被新事实取代；
- 旧事实只会失效，不会被删除；
- 支持查询当前状态和历史状态。

这种机制可以避免 Agent 把过时信息误认为当前事实。

###### 2. 数据来源可追溯

Graphiti 中的实体和关系都可以追溯到对应的原始事件片段，例如：

- 一次用户对话；
- 一份企业文档；
- 一条外部信息；
- 一段结构化 JSON 数据。

因此，Agent 不仅能回答 “是什么”，还可以进一步回答 “这个结论来自哪里”。

###### 3. 支持预定义和自动学习的本体

Graphiti 支持两种图谱结构设计方式：

- **预定义本体（Prescribed Ontology）**：开发者通过 Pydantic 模型提前定义实体和关系类型；
- **学习型本体（Learned Ontology）**：让图谱结构根据输入数据自动形成。

这使系统可以先快速开始，再根据实际数据逐步完善结构。

###### 4. 增量式实时构建

新增数据会直接整合进现有图谱，无需对整个图谱重新计算。图谱会随着每次事件输入持续演化，适合：

- 高频用户交互；
- 实时业务数据；
- 持续变化的企业知识；
- 长期运行的 AI Agent。

###### 5. 混合检索

Graphiti 将多种检索方式结合起来：

- **语义检索**：理解文本含义；
- **关键词检索（BM25）**：匹配明确词语；
- **图遍历**：沿着实体和关系查找相关内容；
- **图距离重排序**：根据节点之间的关系距离优化结果。

这种方式能够在不依赖 LLM 逐步总结的情况下，获得较低延迟和较高精度的结果。

###### 6. 面向大规模数据

Graphiti 支持：

- 高并发数据摄入；
- 并行处理；
- 可插拔的图数据库后端；
- 面向企业工作负载的扩展能力。

---

##### 四、Graphiti 与传统 GraphRAG 的区别

| 对比项 | GraphRAG | Graphiti |
|---|---|---|
| 主要用途 | 静态文档总结 | 动态、持续变化的 Agent 上下文 |
| 数据处理 | 批量处理 | 连续增量更新 |
| 知识结构 | 实体聚类与社区摘要 | 带有效期的实体、事实、事件片段和社区 |
| 检索方式 | 依赖 LLM 顺序总结 | 语义、关键词和图检索混合 |
| 数据适应性 | 较低 | 较高 |
| 时间处理 | 基本时间戳 | 显式双时间追踪，并自动使旧事实失效 |
| 矛盾处理 | 依赖 LLM 判断 | 自动失效旧事实，同时保留历史 |
| 查询延迟 | 数秒到几十秒 | 通常低于 1 秒 |
| 自定义实体类型 | 不支持或有限 | 支持通过 Pydantic 自定义 |
| 可扩展性 | 中等 | 针对大规模数据优化 |

Graphiti 的重点不是对静态文档做一次性总结，而是持续维护 “现在是什么、过去是什么，以及为什么这样判断”。

##### 五、Graphiti 与 Zep 的关系

##### 九、数据库配置方式

Graphiti 可以通过驱动程序指定不同数据库后端和数据库名称。

###### Neo4j

Neo4j 默认数据库名为`neo4j`。如需自定义，可以创建驱动：

```python
from graphiti_core import Graphiti
from graphiti_core.driver.neo4j_driver import Neo4jDriver

driver = Neo4jDriver (
    uri="bolt://localhost:7687",
    user="neo4j",
    password="password",
    database="my_custom_database",
)

graphiti = Graphiti (graph_driver=driver)
```

###### FalkorDB

FalkorDB 默认数据库名为`default_db`，也支持自定义：

```python
from graphiti_core import Graphiti
from graphiti_core.driver.falkordb_driver import FalkorDriver

driver = FalkorDriver (
    host="localhost",
    port=6379,
    username="falkor_user",
    password="falkor_password",
    database="my_custom_graph",
)

graphiti = Graphiti (graph_driver=driver)
```

此外，FalkorDB Lite 支持嵌入式部署，但要求 Python **3.12+**。

###### Kuzu

Kuzu 可以直接使用本地路径：

```python
from graphiti_core import Graphiti
from graphiti_core.driver.kuzu_driver import KuzuDriver

driver = KuzuDriver (db="/tmp/graphiti.kuzu")
graphiti = Graphiti (graph_driver=driver)
```

###### Amazon Neptune

Neptune 需要同时配置 Neptune 地址和 Amazon OpenSearch Serverless 地址：

```python
from graphiti_core import Graphiti
from graphiti_core.driver.neptune_driver import NeptuneDriver

driver = NeptuneDriver (
    host="<NEPTUNE_ENDPOINT>",
    aoss_host="<AMAZON_OPENSEARCH_SERVERLESS_HOST>",
    port=8182,
    aoss_port=443,
)

graphiti = Graphiti (graph_driver=driver)
```

从**v0.17.0**开始，如果需要自定义数据库配置，应先实例化数据库驱动，再通过`graph_driver`传入`Graphiti`。

##### 十二、总体评价与适用场景

Graphiti 的核心价值是把 AI Agent 的记忆从 “聊天记录或文档片段” 升级为一个能够随时间变化的结构化知识系统：

### 2026-08-03 01:32:08

#### Graphiti：为 AI 智能体构建实时知识图谱

这份材料介绍了 Graphiti，一个用于构建和查询“时间型上下文图谱”的开源框架。听完后，你可以了解它如何记录事实变化、追溯信息来源，并把用户对话、企业数据和外部信息，持续整合成适合 AI 智能体使用的上下文。

##### 一、Graphiti 要解决什么问题

首先，Graphiti 的核心目标，是让 AI 智能体不只会查静态文档，还能理解不断变化的现实世界。

传统知识图谱通常记录“谁和谁有什么关系”，但不一定记录这条关系在什么时候成立、什么时候失效。Graphiti 则专门为动态数据设计。它会持续接收新的对话、结构化数据和非结构化文本，并把这些信息整合到一个可以查询的图谱中。

这里的“上下文图谱”，可以理解成一张会随着时间变化的关系网络。它不仅记录实体和关系，还记录每条事实的有效时间，以及事实来自哪段原始数据。

比如，图谱可以记录：“截至二零二六年三月，Kendra 喜欢 Adidas 的鞋。”如果后来她的偏好发生变化，Graphiti 不会简单删除旧信息，而是标记旧事实何时失效，再记录新的偏好。这样，系统既能回答“她现在喜欢什么”，也能回答“她过去曾经喜欢什么”。

##### 二、上下文图谱由哪些部分组成

接下来，具体看一张 Graphiti 上下文图谱包含什么。

第一类是实体，也就是图谱里的节点。实体可以是人、产品、政策、概念，或者其他业务对象。每个实体都有一个会随着新信息不断更新的摘要。

第二类是事实和关系，也就是图谱里的边。它们通常表示“实体指向另一个实体”的三元组关系。比如，“Kendra喜欢Adidas鞋”。每条关系都有时间范围，表示它从什么时候开始成立，又在什么时候被新的事实取代。

第三类是事件，也叫 Episode。它指的是系统实际接收到的原始数据，比如一段聊天记录、一条业务记录或一份文本。所有从数据中推导出来的实体和关系，都可以追溯到这些原始事件。这就保留了完整的来源链路，也就是常说的溯源能力。

第四类是自定义类型，也就是开发者可以按照自己的业务定义实体类型和关系类型。Graphiti 使用 Pydantic 模型来描述这些类型。Pydantic 可以简单理解为一种用代码明确规定数据结构和字段格式的工具。

Graphiti 还支持两种建立结构的方式。一种是“预先定义”，由开发者提前规定有哪些实体和关系。另一种是“从数据中学习”，让系统先从实际数据里发现结构，再逐步完善。这样，项目可以先从简单方案开始，等数据模式稳定后再增加更严格的类型定义。

##### 三、Graphiti 和传统 RAG 有什么不同

更重要的是，Graphiti 不同于常见的检索增强生成，也就是 RAG。

RAG 的基本思路，是从文档库里找出相关文本片段，再把这些片段交给大语言模型生成答案。它适合查找相对稳定的资料，但面对频繁更新的数据时，通常需要批量处理、重新总结，效率可能不高。

Graphiti 采用的是增量更新。新的数据一到，就可以直接加入图谱，不必每次都重新计算整个图谱。这样，图谱能够随着用户每一次互动逐步演化。

它还使用混合检索。混合检索结合了三种方式：第一是语义搜索，也就是根据含义寻找相近内容；第二是关键词搜索，材料中提到的 BM25 就是一种常见的关键词相关性算法；第三是图遍历，也就是沿着实体之间的关系查找信息。

这三种方式结合起来，可以同时处理“意思相近”“关键词匹配”和“关系链路”这几类问题。相比只依赖大语言模型进行长篇总结，它更适合低延迟、高精度的查询。

材料还把 Graphiti 与 GraphRAG 做了对比。GraphRAG 更偏向静态文档总结，通常采用批处理，并依靠大语言模型生成实体聚类和社区摘要。Graphiti 则更关注实时变化的上下文，持续处理新数据，并明确记录事实的有效时间和历史变化。

在时间处理方面，GraphRAG 通常只是做基础的时间标记，而 Graphiti 支持更明确的双时间追踪。通俗地说，就是既关注事实内容本身的有效时间，也关注系统什么时候接收到、处理了这条信息。

在矛盾信息处理方面，GraphRAG 往往需要让大语言模型判断哪种总结更合理。Graphiti 则会自动让旧事实失效，同时保留旧事实的历史记录。这样，历史不会因为新信息出现而消失。

材料给出的性能描述是，GraphRAG 的查询延迟可能从几秒到几十秒不等，而 Graphiti 通常可以做到亚秒级，也就是一秒以内。不过，实际速度仍然取决于具体部署方式、数据规模和硬件配置。

##### 四、Graphiti 能为 AI 智能体带来什么

Graphiti 的用途，可以概括为三个方面。

第一，它可以构建会随着每次互动变化的上下文图谱。智能体不仅知道“现在是什么情况”，还可以知道“之前发生过什么变化”。

第二，它可以向智能体提供结构化上下文，而不是只提供一堆文档片段，或者一长串未经整理的聊天记录。这样，智能体更容易理解人物、事件和关系之间的联系。

第三，它可以支持跨时间、跨语义和跨关系的查询。比如，用户可以询问某个客户当前的偏好，也可以追问偏好是何时改变的，以及这个结论来自哪次对话或哪条业务记录。

Graphiti 的特点还包括：事实有明确的有效时间；每条信息都可以追溯到原始事件；数据可以实时增量写入；检索结合语义、关键词和图关系；同时还支持并行处理和可插拔的图数据库后端，因此可以面向更大规模的数据集。

##### 五、Graphiti 和 Zep 的关系

接下来，需要区分 Graphiti 和 Zep。

Graphiti 是开源的、可以自行部署的时间型上下文图谱引擎。它负责构建和查询单个或具体业务中的上下文图谱。

Zep 则是在 Graphiti 基础上提供的托管型上下文基础设施。它面向生产环境，负责管理大量用户或实体对应的上下文图谱，并提供治理、低延迟检索和上下文组装能力。

简单来说，Graphiti 更像是一个灵活的开源核心。开发者可以自己选择数据库、部署方式和周边系统，但也需要自己处理用户管理、会话管理、监控和运维。

Zep 更像是一个开箱即用的平台。它内置用户、线程和消息存储，还提供图谱可视化、调试日志、接口日志，以及 Python、TypeScript 和 Go 的 SDK。材料中提到，Zep 在规模化生产场景下可以提供低于两百毫秒的检索性能，并且配套企业级的服务等级协议、支持和安全保障。

所以，如果希望快速获得完整的企业级平台，可以选择 Zep。如果希望使用开源核心，并且愿意自行建设和维护周边系统，则可以选择 Graphiti。

##### 六、安装 Graphiti 需要什么

在安装方面，Graphiti 要求 Python 三点一零或更高版本。

它支持多种图数据库后端，包括 Neo4j、FalkorDB、Amazon Neptune，以及已经被标记为弃用的 Kuzu。使用 Amazon Neptune 时，还需要配合 Amazon OpenSearch Serverless，作为全文搜索后端。

默认情况下，Graphiti 使用 OpenAI 提供大语言模型推理和文本嵌入，也就是把文本转换成可用于相似度搜索的向量。开发者也可以选择 Google Gemini、Anthropic 或 Groq 等其他模型服务。

基础安装包叫作 `graphiti-core`，可以通过 pip 安装，也可以使用 uv 添加。若选择 FalkorDB、Kuzu、Neptune，或者其他模型供应商，还需要安装对应的额外依赖。

其中，FalkorDB 还提供嵌入式的 FalkorDB Lite 版本。不过，嵌入式版本要求 Python 三点一二或更高。

##### 七、快速开始和部署方式

Graphiti 提供了一个完整的快速开始示例。

这个示例会演示如何连接 Neo4j、Amazon Neptune、FalkorDB 或 Kuzu；如何初始化图谱索引和约束；如何把文本和结构化 JSON 数据添加为事件；如何使用混合检索查找关系；如何通过图距离对搜索结果重新排序；以及如何使用预定义的搜索配方查找实体。

如果不想手动安装数据库，也可以使用 Docker Compose。启动默认配置，可以运行 Neo4j 相关服务；使用 FalkorDB，则可以启用对应的 FalkorDB 配置。这样能更快搭建一个本地测试环境。

项目还提供两个服务层。

一个是 MCP Server。MCP，也就是模型上下文协议，可以让 AI 助手通过统一协议访问外部工具和数据。Graphiti 的 MCP 服务支持添加、获取和删除事件，管理实体和关系，进行语义搜索与混合搜索，还支持数据分组和图谱维护。它可以通过 Docker 与 Neo4j 一起部署，从而接入 AI 助手工作流。

另一个是 REST 服务。它位于项目的 server 目录中，使用 FastAPI 构建，提供通过接口访问 Graphiti 的方式。

##### 八、并发设置会影响数据写入速度

Graphiti 的数据写入流程支持较高并发，但默认并发数设置得比较保守。

原因是，写入一条事件时，系统可能需要调用大语言模型。如果同时发起太多请求，模型供应商可能返回四二九错误，也就是请求频率超过限制。

控制并发数量的环境变量叫 `SEMAPHORE_LIMIT`。默认值是十，表示同时进行的操作数量通常限制在十个左右。

如果频繁遇到四二九错误，就应该降低这个值。如果模型供应商允许更高的吞吐量，则可以提高它，从而加快事件导入速度。也就是说，这个参数需要在“速度”和“供应商限流”之间取得平衡。

##### 九、数据库和模型服务可以自定义

从零点一七点零版本开始，如果需要自定义数据库配置，可以先创建对应的数据库驱动，再把它传给 Graphiti。

Neo4j 默认使用名为 `neo4j` 的数据库。FalkorDB 默认使用名为 `default_db` 的数据库。开发者也可以在创建驱动时指定自定义数据库名称。

Kuzu 可以指定本地数据库文件路径。Amazon Neptune 则需要配置 Neptune 地址，并提供 Amazon OpenSearch Serverless 的地址。项目也支持开发者贡献新的图数据库驱动。

在模型服务方面，Graphiti 支持 Azure OpenAI。使用时，需要通过 Azure 的 OpenAI 兼容接口创建标准的异步 OpenAI 客户端，然后分别配置大语言模型客户端和文本嵌入客户端。配置中的模型名称，必须与 Azure 中实际部署的名称一致。

材料给出的示例使用了 GPT 五 mini 作为模型，以及 `text-embedding-3-small` 作为嵌入模型。这里的名称只是示例，实际使用时需要替换成自己的 Azure 部署名称、资源地址和密钥。

Graphiti 也支持 Google Gemini，用于大语言模型推理、文本嵌入，以及交叉编码器重排序。要启用这些功能，需要配置 Google API 密钥，并分别设置相应的模型客户端、嵌入器和重排序组件。

##### 十、最后总结

最后，记住四个最重要的结论。

第一，Graphiti 是一个面向 AI 智能体的开源时间型上下文图谱引擎，重点处理不断变化的数据。

第二，它不仅记录实体和关系，还记录事实何时成立、何时失效，以及事实来自哪段原始数据。

第三，它区别于传统 RAG 的关键，是实时增量更新、混合检索和历史保留，而不是定期批量总结静态文档。

第四，Graphiti 是灵活的开源核心，适合愿意自行部署和开发周边系统的团队；Zep 则提供托管式、企业级的完整上下文基础设施。

## 深度解读（1）

### 2026-09-18 00:30:39

#### Graphiti 的关键价值：把 Agent 记忆从“资料检索”变成“可追溯的状态管理”

Graphiti 最值得关注的，不是“用知识图谱替代 RAG”，而是对 Agent 记忆问题做了更准确的定义：**现实信息会变化，系统不仅要记住事实，还要知道事实何时有效、被什么取代，以及依据来自哪里。**

##### 真正缺失的不是更多上下文，而是时间与状态

传统 RAG 通常把文档切块后检索。它适合回答“资料里写过什么”，却难以处理“现在什么是真的”。例如，用户过去偏好 Adidas、后来改买 New Balance；企业退款政策也可能经历多次调整。如果检索同时召回新旧记录，模型只能依靠语义和上下文猜测，容易把历史事实误当成当前状态。

Graphiti 给关系设置有效期：新信息出现后，旧事实失效但不删除，因此既能查询当前状态，也能还原历史。它还保留产生事实的原始 episode，使每个实体和关系都能回溯来源。

这实际接近事件溯源系统：**原始交互是事件流，图中的实体与关系是由事件推导出的当前视图。** 这个连接比“图数据库更适合 Agent”更有解释力——Agent memory 本质上开始承担业务状态系统的职责，而不再只是一个向量库。

##### 图结构的价值，在于约束检索而非堆积知识

Graphiti 同时使用语义检索、关键词匹配和图遍历。语义相近只能说明两段内容“像”，关系路径则可以限定人物、产品、组织和事件之间的具体联系。对长期运行的客服、销售助理、个人助理和企业流程 Agent，这种约束可能显著减少主体混淆，并支持“某客户在某次沟通后为什么改变需求”一类跨时间查询。

但其收益高度依赖上游抽取质量。实体消歧错误会把两个人合并，关系抽取错误会把推测固化成事实；现实中的矛盾也未必意味着旧事实被新事实取代——不同来源、适用地区和权限范围都可能造成表面冲突。所谓“自动失效”解决的是明确更新，不等于自动完成真相判断。

##### 这是基础设施方向，不是开箱即用的记忆产品

仓库明确区分了 Graphiti 与商业产品 Zep：前者提供时态图引擎，用户管理、治理、调试、性能保障和规模化运维仍需自行建设。这也揭示了较清晰的商业分层：开源核心负责验证数据模型，托管服务出售低延迟、治理与可靠性。

对产品团队而言，最值得验证的不是“是否要上知识图谱”，而是：**业务错误是否主要来自信息过期、主体关系混乱或无法追溯来源？** 如果只是静态文档问答，Graphiti 很可能增加数据库、模型调用和运维成本；如果 Agent 必须长期理解不断变化的人与业务状态，它才可能成为关键组件。

README 声称具备亚秒级检索和领先的 Agent Memory 效果，但页面本身没有充分展示基准条件。更稳妥的评估方式，是用真实更新、冲突和历史追问构建测试集，比较它与“向量检索＋结构化状态表”的准确率、延迟和维护成本。Graphiti 提出的核心问题是成立的，但图是否是最佳答案，仍应由具体状态复杂度决定。

- Graphiti采用语义向量、BM25关键词和图遍历组成的混合检索，并支持按图距离进行结果重排。
- 新数据可以增量写入图谱，无需完整重算；被更新的旧事实不会删除，而是失效并保留历史记录。

###### 行动项
- 使用Neo4j或FalkorDB启动本地后端，安装graphiti-core并运行仓库中的Quickstart示例。
- 导入一组包含事实变更的文本或JSON事件，验证当前状态查询、历史查询和来源追溯能力。
- 通过MCP服务器接入现有AI助手，并根据LLM限流情况调整SEMAPHORE_LIMIT进行吞吐测试。
