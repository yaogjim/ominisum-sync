## 分析要点

- **核心高价值点**：根据是否需要登录态来选择浏览器模式：需要登录用Chrome插件，不需要登录或重视轻量化则用内置浏览器。
- **留存建议**：短期参考后可保留，适合作为Codex浏览器模式选型备忘（提供了Chrome插件模式与内置浏览器模式的使用场景、优劣对比和选型规则，对实际使用Codex有参考价值）

**知识要点**

- Chrome插件模式可继承本机Chrome的Cookie、登录会话和扩展，适合登录态任务和企业内部工具自动化。
- 内置浏览器模式资源消耗更低，适合公开网页抓取、本地前端调试和频繁浏览器操作。
- 内置浏览器不继承登录态，且可能因浏览器指纹异常在部分强风控网站上登录失败。
- Codex的Annotation Mode可直接在页面元素上批注并转化为修改指令，适合前端可视化调试。
- Codex通常会按优先级选择工具：专用插件优先，其次Chrome登录态，再其次内置浏览器。

**行动项**

- 将需要登录态的数据抓取或后台操作任务优先交给Chrome插件模式处理。
- 将公开网页抓取、本地页面调试和高频轻量任务优先放到内置浏览器模式中执行。
- 在使用Chrome插件模式执行批量任务前，评估本机内存和CPU占用，避免长时间运行导致卡顿或状态不同步。
- 前端调试时尝试使用内置浏览器的Annotation Mode进行可视化批注修改。

## 正文

**宝玉**

Codex 操作浏览器有两种模式，一种是 Chrome 插件，一种是内置浏览器。用了一段时间之后，我总结一下两者的差异和各自适合的场景。

【1】先说一个被低估的用法：拿 Codex 当爬虫

传统爬虫用 requests 或者 Playwright 无头模式去请求页面，现在风控越来越严，指纹检测、行为分析、验证码轮番上阵，很多网站一看你是程序化请求直接拦截。Codex 的浏览器不一样，它操作的是真实浏览器，有完整的渲染引擎、真实的用户代理、正常的 JavaScript 执行环境，在网站看来就是一个普通用户在浏览页面。

配合 /goal 模式，你设定一个目标（比如“把这个网站上所有产品的名称、价格、评分抓下来存成 CSV”），Codex 会自己规划步骤、翻页、处理异常，不需要你一步步指挥。这比自己写爬虫脚本省事得多。

但 Codex 有两种浏览器模式，特性完全不同，选对了事半功倍。

【2】Chrome 插件模式：能力强，但吃资源

用 @Chrome  
调用的 Chrome 插件模式，核心优势是一个字：登录态共享。

它直接运行在你自己的 Chrome 浏览器里，继承你所有的 Cookie、登录会话、已安装的扩展。那些需要登录才能访问的内容，比如付费订阅的文章、企业内部的管理后台、CRM 系统里的客户数据、需要登录的社交平台，Chrome 插件都能直接访问，因为对网站来说，就是你本人在操作浏览器。

Codex 在 Chrome 里工作时会把任务放进独立的标签页分组，不会打断你正在看的页面。它还支持 DevTools 协议，能抓性能数据、看网络请求、调试 Console 错误。

但代价也很明显：资源消耗相当大。Chrome 本身就是内存大户，每个标签页都是独立进程。Codex 的 Chrome 插件在上面再加一层操控逻辑，截图、DOM 解析、指令交互全在跑，内存和 CPU 占用会非常高。机器配置不行的话（比如 8G 内存的笔记本），跑起来能明显感觉到卡顿，拿来做批量爬虫任务就更难受了。长时间运行还容易出现截图延迟、状态不同步的问题。

另外 Chrome 插件目前只支持 macOS 和 Windows，Linux 用户暂时用不了。它也不支持无头模式，Chrome 窗口必须保持打开状态。

适合的场景：需要登录态的短期任务。比如登录某个平台抓一批数据、在内部工具上批量操作、从 CRM 导出信息。

【3】内置浏览器模式：轻快，但有局限

用 @Browser  
调用的内置浏览器，是 Codex 自带的沙盒浏览器环境。

它最大的优势是轻量。不需要启动整个 Chrome，资源消耗小很多，响应速度快，适合需要频繁操作浏览器的场景。

但它有一个根本性的限制：没有你的登录态。不继承 Cookie、不继承浏览器扩展、不继承已保存的会话。打开一个需要登录的页面，你得在内置浏览器里重新登录。而且有些反爬严格的网站，对这种非标准浏览器环境的检测更敏感。我试过在内置浏览器里登录 X，反复失败，大概率是因为 X 的风控识别出了异常的浏览器指纹。

内置浏览器真正出彩的地方是前端开发调试。它有一个标记模式（Annotation Mode），你可以直接在渲染好的页面上选中某个元素或者框选一个区域，写上“这个按钮往上移”“字体加粗”“这个间距太大了”之类的批注，Codex 会把这些批注当作可执行指令来处理。这比用文字描述“第三行第二个按钮的 margin-top 减少 8px”直观太多了。

配合 Developer Mode，内置浏览器还能跑性能分析、抓网络请求、看 Console 输出，对本地开发服务器的调试非常友好。

适合的场景：公开页面的数据抓取、本地开发调试、不需要登录态的网页操作。

【4】怎么选

简单说：需要登录的用 Chrome 插件，不需要登录的用内置浏览器。如果你的机器配置有限又需要大量抓取公开数据，内置浏览器是更好的选择。如果目标网站必须登录才能看到内容，或者反爬很严需要真实浏览器指纹，那只能用 Chrome 插件，但要有心理准备面对资源消耗。

Codex 自己也会根据任务判断应该用哪种浏览器。它的优先级是：有专用插件（比如 Jira、GitHub 的集成）就用插件，需要登录态就用 Chrome，其余情况用内置浏览器。

当然浏览器的用途远不止爬虫。我觉得内置浏览器做前端调试的体验比很多专门工具都好，标记模式配合 Codex 的理解能力，几乎是“指哪改哪”。Chrome 插件在自动化操作企业内部工具方面也很实用，比如定期从后台导数据、批量更新记录。这些场景还有不少值得挖掘的空间，大家可以根据自己的实际需求去试试。

#### Codex 两种浏览器模式：深度总结与解读

##### 一、深度总结

Codex 操作浏览器有两种方式：

| 模式 | 核心优势 | 核心短板 | 适合场景 |
|---|---|---|---|
| **Chrome 插件模式`@Chrome`** | 继承真实 Chrome 登录态、Cookie、扩展，像真人操作 | 占内存、耗 CPU、不支持无头、依赖系统 Chrome | 登录后数据抓取、企业后台操作、CRM / 内部系统自动化 |
| **内置浏览器模式`@Browser`** | 轻量、快、适合频繁网页操作和前端调试 | 没有登录态，部分网站风控更容易识别 | 公开网页抓取、本地前端调试、无需登录的任务 |

文章的核心判断：

> **需要登录态，用 Chrome 插件；不需要登录态，用内置浏览器。**

更细一点：

- **做爬虫**：Codex 可以像真人一样操作真实页面，比传统 requests / Playwright 更不容易被简单拦截。
- **做自动化**：Codex 可通过`/goal`自己规划步骤，比如翻页、提取数据、保存 CSV。
- **做前端调试**：内置浏览器的标记模式很强，可以直接圈选页面元素并提出修改要求。
- **做企业工具操作**：Chrome 插件更适合，因为它能继承登录状态和真实浏览器环境。

Codex 默认选择逻辑大致是：

```text
有专用集成插件 → 优先用插件
需要登录态 → 用 Chrome
其他网页任务 → 用内置浏览器
```

---

##### 二、深入浅出解读

可以把这两种模式理解成：

###### 1. Chrome 插件模式：像 “你本人亲自上网”

它用的是你自己的 Chrome。

所以：

- 你登录过的网站，它也能访问；
- 你装过的扩展，它也能用；
- 网站看到的就是一个正常用户。

但问题是：

- Chrome 本来就吃资源；
- Codex 再控制它，会更吃资源；
- 长时间、大批量任务容易卡。

**一句话：能力强，但重。**

---

###### 2. 内置浏览器模式：像 “Codex 自带的小浏览器”

它不是你的 Chrome，而是 Codex 自己的浏览器环境。

所以：

- 启动快；
- 占资源少；
- 适合公开网页、前端页面调试。

但它没有你的登录信息。

所以：

- 需要重新登录；
- 某些网站可能认为它 “不像真人浏览器”；
- 严格风控网站可能登录失败。

**一句话：轻快，但身份感弱。**

---

##### 三、最实用的选择方法

###### 看一个问题就够了：

> 这个任务需不需要你的登录状态？

如果需要：

```text
用 @Chrome
```

比如：

- 抓取付费文章；
- 操作企业后台；
- 导出 CRM 数据；
- 分析登录后的社交平台页面。

如果不需要：

```text
用 @Browser
```

比如：

- 抓公开网页数据；
- 调试本地前端页面；
- 检查网页性能；
- 批量访问无需登录的页面。

---

##### 四、辩证思考

###### 1. Codex 当爬虫，确实强，但不是 “万能反爬神器”

它像真人浏览器，能绕过一部分简单反爬。

但高级风控看的是：

- 行为轨迹；
- 操作频率；
- 浏览器指纹；
- IP 风险；
- 登录环境；
- 账号历史。

所以 Codex 只是降低门槛，不是彻底绕过风控。

---

###### 2. 自动化越强，合规边界越重要

用 Codex 抓数据很方便，但不代表所有数据都能抓。

需要注意：

- 网站服务条款；
- 隐私数据；
- 账号权限；
- 数据使用目的；
- 企业内部合规要求。

尤其是登录后数据、CRM、后台信息，自动化操作更要谨慎。

> 技术能做，不等于应该做。

---

###### 3. Chrome 插件代表 “真实能力”，内置浏览器代表 “效率能力”

两者不是谁替代谁，而是分工不同：

- Chrome 插件解决 “身份真实性”；
- 内置浏览器解决 “效率和轻量化”。

真正高效的用法，是根据任务切换，而不是固定使用一种模式。

---

###### 4. 最值得关注的不是爬虫，而是 “可视化自动化”

文章里最有价值的点，其实不只是抓数据。

更重要的是：

> Codex 开始把 “看网页、理解页面、操作页面、修改页面” 连起来了。

尤其是内置浏览器的标记模式，让前端调试从：

```text
用文字描述问题
```

变成：

```text
直接圈出来，让 AI 改
```

这会显著降低网页开发和自动化操作的门槛。

---

##### 五、一句话结论

> **Chrome 插件适合 “需要身份” 的任务，内置浏览器适合 “追求轻快” 的任务；Codex 的真正价值，是把浏览器从展示工具变成了可被 AI 理解和执行的操作界面。**

#### Codex 浏览器两种模式：Chrome 插件 vs 内置浏览器

##### 核心结论

Codex 操作浏览器主要有两种方式：

- **Chrome 插件模式（@Chrome）**：能力更强，适合需要登录态、真实浏览器环境的任务，但资源消耗大。
- **内置浏览器模式（@Browser）**：更轻量、速度快，适合公开网页抓取和前端调试，但不共享登录态。

简单选择原则：

> **需要登录用 Chrome 插件；不需要登录用内置浏览器。**

---

##### 一个被低估的用法：把 Codex 当爬虫

传统爬虫容易被网站风控拦截，比如指纹检测、行为分析、验证码等。

Codex 操作的是真实或接近真实的浏览器环境，能够正常渲染页面、执行 JavaScript，看起来更像普通用户浏览网页。

配合 `/goal` 模式，可以直接给 Codex 一个目标，例如：

> 把网站上的产品名称、价格、评分抓下来，整理成 CSV。

Codex 会自动规划步骤、翻页、处理异常，比手写爬虫脚本更省事。

---

##### Chrome 插件模式：适合登录态任务

###### 优点

Chrome 插件模式最大的优势是：

> **共享你的真实 Chrome 登录状态。**

它可以继承：

- Cookie
- 登录会话
- 浏览器扩展
- 已保存状态

因此适合访问：

- 付费订阅内容
- 企业后台
- CRM 系统
- 社交平台
- 需要登录的网站

此外，它还能通过 DevTools 协议查看网络请求、性能数据和 Console 错误。

###### 缺点

主要问题是资源消耗大：

- Chrome 本身占内存高
- Codex 还要额外截图、解析 DOM、执行指令
- 长时间运行可能出现卡顿、截图延迟、状态不同步

另外限制包括：

- 目前仅支持 macOS 和 Windows
- 不支持无头模式
- Chrome 窗口必须保持打开

###### 适合场景

- 登录后抓取数据
- 企业内部工具自动化
- CRM 信息导出
- 批量后台操作
- 需要真实浏览器指纹的网站

---

##### 内置浏览器模式：适合轻量任务和前端调试

###### 优点

内置浏览器是 Codex 自带的沙盒浏览器，优势是：

- 启动快
- 资源占用低
- 操作响应更轻快
- 适合频繁网页操作

它尤其适合前端开发调试。

通过 **Annotation Mode 标记模式**，可以直接在页面上圈选元素并写批注，例如：

- “这个按钮往上移”
- “字体加粗”
- “这个间距太大了”

Codex 可以理解这些可视化反馈并执行修改，体验接近“指哪改哪”。

###### 缺点

最大限制是：

> **不共享你的登录态。**

它不继承：

- Cookie
- 浏览器扩展
- 已登录会话

所以访问需要登录的网站时，要重新登录。而且部分风控严格的网站，可能会识别出异常浏览器环境，导致登录失败。

###### 适合场景

- 公开网页数据抓取
- 不需要登录的网页操作
- 本地前端开发调试
- 性能分析
- 网络请求排查
- Console 错误调试

---

##### 如何选择

| 场景 | 推荐模式 |
|---|---|
| 需要登录态 | Chrome 插件 |
| 抓取公开网页 | 内置浏览器 |
| 机器配置有限 | 内置浏览器 |
| 企业后台自动化 | Chrome 插件 |
| 前端页面调试 | 内置浏览器 |
| 网站反爬严格 | 优先 Chrome 插件 |
| 长时间批量轻量任务 | 内置浏览器 |

---

##### Codex 的默认判断逻辑

Codex 自身也会根据任务选择工具，大致优先级是：

1. 有专用插件就用专用插件，例如 Jira、GitHub 集成
2. 需要登录态就用 Chrome
3. 其他情况用内置浏览器

---

##### 总结

Codex 的浏览器能力不只是爬虫工具，更是自动化操作和前端调试工具。

- **Chrome 插件**：像真人一样操作你的浏览器，适合登录态和企业工具自动化。
- **内置浏览器**：轻快灵活，适合公开数据抓取和前端开发调试。

真正的关键不是哪个更强，而是根据任务选择合适模式。
