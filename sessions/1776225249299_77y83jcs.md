### 三省六部幻觉：为什么"虚拟公司"式多Agent架构在工程上不成立

一个在AI社区广泛流传的架构思路，正在让大量团队走弯路。

#### 先说结论

如果你正在考虑把多个AI Agent分别命名为"产品经理"、"架构师"、"测试工程师"，让它们像公司部门一样传递文档、协作完成任务——请停下来。

这个模式看起来很直觉，逻辑上似乎很合理，但它在工程上有根本性的缺陷。更重要的是，Anthropic、OpenAI、Google三家厂商在构建自己的Agent系统时，没有一家采用这个模式。

这不是巧合。

#### 什么是"三省六部"式架构

![Image](https://pbs.twimg.com/media/HF1iMQEb0AA8tnX?format=jpg&name=large)

这个比喻指的是一类在社区里广泛流行的多Agent设计思路，在不同框架和文章里有不同名字：role-based agents、virtual team、CrewAI式分工、MetaGPT式组织——本文统称"三省六部"。

核心模式是：把一个复杂任务拆解成若干职能，每个Agent扮演一个角色——PM负责需求、Tech Lead负责架构、Dev负责实现、QA负责测试。任务在Agent之间流转，像一条流水线。

这个模式在图示上非常好看。它满足了人类对"分工协作"的直觉，也让"AI团队"这个概念变得具象可解释。CrewAI等框架正是因此积累了大量用户。

问题在于，它解决的是人类的瓶颈，不是AI的瓶颈。

#### 为什么这个类比从根本上是错的

人类需要分工，是因为：

- 单个人的注意力有限，无法同时处理所有信息
- 人有专业壁垒，学习切换成本高
- 人与人之间需要接口来协调

但LLM的特性完全不同：

- 同一个模型既能写PRD又能写代码，没有"职业边界"
- 模型的瓶颈不是注意力广度，而是推理深度和信息完整性
- 模型之间没有"文化"和"默契"来补偿信息损耗

给Agent贴上"产品经理"的标签，不会让它更专业——但会让它拒绝越界。一个被框死在"测试工程师"角色里的Agent，看到架构层的问题可能直接跳过，因为"不在我职责范围内"。最有价值的推理往往发生在边界上，而三省六部模式在系统层面封死了这个可能性。

角色扮演制造了假边界。这是第一个问题。

#### 第二个问题：信息在流转中死亡

![Image](https://pbs.twimg.com/media/HF1iOwBasAENF4s?format=jpg&name=large)

三省六部模式里，Agent A产出一个文档，传给Agent B。

这个过程传递的是结论，不是推理过程。

B拿到文档，重新理解，重新建立上下文。原始意图在衰减，隐含假设在丢失，每次传递都在累积误差。工作流越长，最终输出越"局部正确但整体漂移"——每个节点看起来合理，但整体已经偏离了最初的目标。

人类组织靠会议、文化、非正式沟通来补偿这个信息损耗。Agent之间没有这些机制。

这里有一个常见的反驳：三家厂商的解法（progress.txt、spec文件、runbook）不也是"传文件"吗？区别在哪？

区别在于谁在写、写给谁、怎么更新。

三省六部的信息流转是角色间的单向交接：A写完交给B，B不再回头，A也不知道B怎么用了这份文档。信息被压缩成结论，推理过程丢失，接棒就是断点。

外部状态文件是同一任务的增量日志：执行主体在每个checkpoint时往同一份记录里追加，下一个session读取的是任务的完整历史，不是上一个"同事"的输出结论。写状态的人和读状态的人是同一个角色，只是时间不同。信息不是被"压缩传递"的，是被"连续积累"的。

这个区别决定了推理链能不能跨session保持连续。

大量token被浪费在Agent之间的"交接文件"上，而不是用于实际推理。你得到的是一个模拟公司行为的系统，而不是一个解决问题的系统。

#### 三家厂商实际怎么做的

值得注意的是，当Anthropic、OpenAI、Google真正构建自己的生产级Agent系统时，他们的工程文档里几乎找不到"角色扮演"或"部门分工"的字眼。

Anthropic：上下文工程 + 显式状态文件

Anthropic内部把"Prompt Engineering"升级成了"Context Engineering"：问题不是怎么写好一个prompt，而是什么样的token配置最能产生想要的行为。

在构建Claude Code和Research系统时，他们面对的核心挑战是：Agent必须在离散的session里工作，每个新session对之前发生的事情没有任何记忆。他们的比喻是"轮班工程师"——每个新班次的工程师到岗时对上一班的工作一无所知。

解法不是让Agent扮演不同角色，而是：

- claude-progress.txt：一个跨session的工作日志，Agent在每个session结束时更新，下一个session开始时读取
- Git history：作为状态锚点，记录每一个增量变化
- Initializer Agent：只在第一个session运行，建立环境、展开feature list、写好runbook，供后续所有session使用

![Image](https://pbs.twimg.com/media/HF1iUAObcAAeRKG?format=jpg&name=large)

关键洞察：推理链的连续性不靠模型"记住"，靠显式的外部状态来锚定。

他们同时发现，把"model能力假设"硬编码进harness是危险的。Sonnet 4.5有"context anxiety"——快到context limit时会提前收尾，于是harness里加了context reset。但Opus 4.5这个行为消失了，reset变成了死重量。这说明：harness需要随模型迭代而演化，任何"永久解法"都只是当前阶段的工程妥协。

在多Agent的Research系统里，Anthropic的架构是orchestrator-worker：一个lead agent分解任务、协调subagent，subagent并行探索不同方向，结果回流给lead agent综合。他们发现token消耗量本身就解释了80%的性能差异——多Agent的价值不是"分工"，而是用更多token覆盖更大的搜索空间。

这里有一个容易混淆的地方：Anthropic的subagent看起来也像"分工"，但本质完全不同。三省六部是职能性分工——不同角色承担不同工种，PM做完传给Dev，Dev做完传给QA，每个角色只处理流水线的一段。Anthropic的subagent是功能性并行——多个相同性质的agent同时搜索不同方向，没有"下一棒"，结果全部汇聚回同一个orchestrator综合。前者是接力赛，后者是同时撒网捞鱼。

OpenAI：压缩 + 技能 + 结构化规格文件

![Image](https://pbs.twimg.com/media/HF1igOQa0AAm-6J?format=jpg&name=large)

OpenAI给出的长任务原则更直接：在任务开始时就为continuity做规划。

他们的Codex实验里，工程师给agent一个spec文件（冻结目标，防止agent"做出了很impressive但方向错误的东西"），让它生成milestone-based plan，然后用一个runbook文件告诉agent如何操作。这个runbook同时也是共享记忆和审计日志。

结果：GPT-5.3-Codex跑了约25小时不间断，完成了一个完整的设计工具，保持了全程的连贯性。

Server-side compaction作为默认primitive，不是紧急fallback。多步骤任务里，previous\_response\_id让model能在同一个thread里继续工作，而不是每次重建上下文。

他们还引入了Skills概念——可复用的、版本化的指令集，挂载进container，让agent执行特定任务时有稳定的操作规范。这不是"角色"，是工具和操作规程，是本质上不同的东西。

Google：1M 上下文 + 上下文驱动开发

Google的方向是硬扩窗口：Gemini的1M token context是明确的差异化策略。他们的逻辑是：之前被迫使用的RAG切片、丢弃旧消息等技术，在足够大的窗口下可以被"直接放进去"所取代。

但他们自己也承认这不够用。Google在Gemini CLI推出了Conductor扩展，核心思路和Anthropic如出一辙：把项目意图从聊天窗口里移出来，放进代码库里的持久化Markdown文件。哲学是："不依赖不稳定的聊天记录，依赖正式的spec和plan文件。"

Gemini 3还引入了Thought Signatures机制：在长session里保存推理链的关键节点，防止"reasoning drift"——长context里逻辑前后不一致的问题。

#### 真正的架构原则是什么

从三家的工程实践中，可以提炼出几个共同的原则：

推理链不能断，只能分叉再合并。 多Agent的正确用法不是流水线，而是一个主agent持有完整意图，子调用是为了深挖某个子问题，结果回流给主agent，不是传给下一个agent。

显式外部状态，不靠模型记住。 progress.txt、git history、spec文件、数据库——形式不重要，原则是：推理链的关键节点必须外化到持久存储里，而不依赖模型在context window里"记住"。

多Agent的价值是并行覆盖，不是分工。 Anthropic Research系统的结论很清楚：性能提升主要来自于"花了更多token"，而不是来自"分工更合理"。多Agent适合breadth-first类任务——需要同时探索多个独立方向的场景。不适合需要连续推理、深度依赖上下文的场景。

![Image](https://pbs.twimg.com/media/HF1iccrbEAAzvIp?format=jpg&name=large)

验证Agent是否定者，不是接棒者。 如果要用多Agent做质量控制，正确的设计是让一个Agent专门找另一个Agent的问题，而不是"传递工作成果"。对抗性检验，不是流水线传递。

工具是工具，不是角色。 给Agent配什么工具（bash、文件读写、搜索、代码执行）远比给它贴什么标签重要。工具决定了Agent能做什么；角色标签只是约束它愿意做什么。

#### 那三省六部为什么会流行？

因为它好解释。

"这个Agent是PM，那个是QA"——这句话任何人都能理解。它满足了人类对AI系统可解释性的渴望，也满足了管理层对"AI像团队一样工作"的想象。

![Image](https://pbs.twimg.com/media/HF1ipNobAAAXyyr?format=jpg&name=large)

它还好展示。用流程图画出来，有部门、有箭头、有交接，非常直观。

但好解释和好展示，和工程上是否成立是两件事。

更深层的原因是：大多数采用这个模式的团队，并没有真正面对过"上下文在多Agent间传递时的损耗"这个问题。他们的任务可能不够复杂，或者问题被其他因素掩盖了。等到任务复杂度上来，系统开始出现诡异的"局部正确整体错误"时，问题才会暴露。

#### 实践建议

最好的多Agent系统，不像公司。它更像一个思考者的多次草稿——同一个大脑，在不同维度上展开推理，最终合并成一个连贯的结论。

从这个原则出发：

不要问"我需要几个Agent"，要问"这个任务的信息依赖结构是什么"。

如果任务需要连续推理、上下文高度依赖（比如写一个复杂功能的设计文档），单Agent + 好的context engineering通常优于多Agent。

如果任务需要同时探索多个独立方向（比如同时研究10个竞品的不同模块），多Agent并行是合理的——每个subagent的任务相互独立，信息损耗代价最小。这正是Anthropic Research系统token量解释80%性能差异背后的原因：不是分工让它更好，是更大的搜索覆盖让它更好。

如果任务跨越多个session，外部状态文件是必须的。一份有效的状态文件应该包含四类信息：

- 任务目标（不变，session开始时读取，防止漂移）
- 已完成的步骤（追加，不覆盖，保留完整历史）
- 当前状态（覆盖，反映最新进展）
- 已知的坑（追加，避免下一个session重复踩）

这四类信息分开维护，合在一起就是"下一个自己"需要的完整上下文。

如果要加验证环节，让验证Agent的唯一任务是找问题，不是"接棒继续做"。对抗性检验，不是流水线传递。

![Image](https://pbs.twimg.com/media/HF1ikoiasAANbQw?format=jpg&name=large)

最后：模型能力在快速提升，今天harness里需要的workaround，六个月后可能变成死重量。Anthropic已经验证了这一点——Sonnet 4.5的context anxiety在Opus 4.5里消失了，为它设计的context reset随即变成了无用代码。保持架构的可演化性，比选一个"完美架构"更重要。

![Image](https://pbs.twimg.com/media/HF1itofaYAAB9TE?format=jpg&name=large)

三省六部是一个让人感觉良好但工程上代价高昂的错觉。它的真正成本不是直接的失败，而是让你的系统在复杂度上升时，以一种难以诊断的方式退化——每个节点都"看起来在工作"，但整体在漂移。

等你发现问题的时候，流水线已经很长了。

## 通俗精炼（1）

### 2026-04-15 03:54:09

#### 三省六部式多 Agent，为何是 “好看但不好用” 的工程幻觉

##### 核心结论

把多个 AI Agent 分别设成 “产品经理、架构师、开发、测试”，像公司部门一样传文档、接力协作，这种设计很直观，但在工程上通常不成立。

原因很简单：这种模式解决的是 “人类团队协作” 的问题，不是 “模型完成任务” 的问题。真实生产环境里，Anthropic、OpenAI、Google 都没有采用这种 “虚拟公司” 式流水线架构。

##### 问题一：角色分工会人为制造边界

人类需要分工，是因为注意力有限、专业壁垒高、协作成本大；但 LLM 并没有严格的职业边界。

给 Agent 贴上 “PM” 或 “测试” 的标签，不会让它更专业，反而可能让它只盯住自己那一段，不敢越界思考。可很多关键洞察，恰恰出现在需求、架构、实现、验证这些边界交叉处。

##### 问题二：信息在交接中不断损耗

“Agent A 写文档给 Agent B” 看似合理，但传过去的往往只是结论，不是完整推理过程。

结果就是：每一棒都在重新理解上下文，隐含假设不断丢失，最终容易出现 “局部都对，但整体跑偏” 的情况。流程越长，偏差越大。

##### 大厂的真实做法：不是角色接力，而是状态连续

三家的共同思路不是 “角色扮演”，而是让同一个任务的上下文持续积累：

- Anthropic：用`progress.txt`、Git history、runbook 这类外部状态文件维持跨 session 连续性
- OpenAI：用 spec、runbook、压缩机制、skills 保证长任务不中断、不跑偏
- Google：用超长上下文 + 持久化 spec/plan 文件，避免依赖脆弱的聊天记录

本质上，他们都在做一件事：**把关键上下文外化，确保推理链不断裂。**

##### 多 Agent 真正适合的场景

多 Agent 不是不能用，而是不适合 “流水线分工”。

它真正有价值的场景是：**并行探索多个相对独立的问题**。比如同时研究多个竞品、多个技术方向、多个假设空间。此时多 Agent 的优势来自更大的搜索覆盖，而不是 “像公司一样分工更合理”。

简单说：

- 需要连续深度推理：优先单 Agent
- 需要并行探索多个方向：适合多 Agent
- 需要质量控制：让验证 Agent 专门 “找错”，而不是 “接着做”

##### 真正值得遵循的架构原则

###### 1. 推理链不能断
任务可以分叉，但最后必须回到一个主 Agent 汇总，而不是一个角色接一个角色传下去。

###### 2. 关键状态必须外部化
不要指望模型 “自己记住”，要把目标、进度、当前状态、已知坑写进持久化文件。

###### 3. 工具比角色更重要
决定 Agent 能力的，是它能否搜索、读写文件、执行代码，而不是它叫 “PM” 还是 “QA”。

###### 4. 架构要能随模型演化
很多今天必要的 workaround，半年后可能就是负担。不要追求 “永久正确” 的架构，要追求 “容易调整” 的架构。

##### 为什么这种模式还这么流行

因为它特别容易解释、容易画图、容易向管理层展示。

“这个是 PM Agent，那个是 QA Agent” 听起来很合理，也很像现实公司协作。但**好解释，不等于工程上有效**。很多团队一开始感觉顺畅，只是因为任务还不够复杂，问题还没暴露。

##### 实践建议

如果你在设计 Agent 系统，建议优先问自己：

- 这个任务是 “连续推理型”，还是 “并行搜索型”？
- 哪些信息必须跨 session 保留？
- 是否真的需要多个 Agent，还是一个 Agent + 更好的上下文工程就够了？

一个更稳妥的经验法则是：

- 复杂设计、写方案、改代码：`单 Agent + 强上下文管理`
- 多方向调研、并行探索：`主 Agent + 多个并行子 Agent`
- 质量校验：`独立验证 Agent 专门找问题`

##### 一句话总结

“三省六部” 式多 Agent 最大的问题，不是它完全不能跑，而是它会在复杂度上升后，**以一种很难排查的方式持续退化**：每个节点都看起来正常，但整体越来越偏。真正可靠的 Agent 架构，不像一个公司，更像一个持续思考、持续记录、持续收敛的大脑。

## 结构化（1）

### 2026-04-15 06:04:30

#### 《三省六部幻觉：为什么 “虚拟公司” 式多 Agent 架构在工程上不成立》总结

这篇文章的核心观点是：把多个 AI Agent 按 “产品经理、架构师、测试工程师” 这类公司角色来分工协作，看起来合理，但在工程上往往是错误方向。  
作者认为，Anthropic、OpenAI、Google 的实际做法都说明：**高效的 Agent 系统依赖的是上下文连续性、显式状态和并行探索，而不是 “模拟公司组织结构”。**

##### 1. 文章开篇结论：别把 Agent 设计成 “虚拟公司”

- 社区里很流行一种多 Agent 架构：给不同 Agent 分配不同职能，像公司部门一样传文档、做交接。
- 作者开门见山指出：**这种模式有根本性缺陷**，会让很多团队在复杂任务上走弯路。
- 一个重要佐证是：**Anthropic、OpenAI、Google 三家厂商在自家 Agent 系统中，都没有采用这种 “虚拟公司式分工” 架构。**
- 作者强调：这不是偶然，而是因为这种设计本身不符合 LLM 的工作方式。

##### 2. 什么是 “三省六部” 式架构

- 文中把这类设计统称为 “三省六部” 模式，常见叫法包括：
  - `role-based agents`
  - `virtual team`
  - `CrewAI`式分工
  - `MetaGPT`式组织
- 它的基本思路是：
  - PM Agent 负责需求
  - Tech Lead Agent 负责架构
  - Dev Agent 负责实现
  - QA Agent 负责测试
  - 任务像流水线一样在不同 Agent 之间流转
- 这种模式之所以流行，是因为：
  - 很符合人类对 “分工协作” 的直觉
  - 流程图很好画，展示起来很清晰
  - “AI 团队” 这个概念很容易让人理解
- 但作者指出：**它解决的是人类组织的问题，不是 AI 系统的问题。**

##### 3. 为什么这种类比从根上就错了

###### 3.1 人类需要分工，但 LLM 不一样

作者先解释人类为什么需要部门分工：

- 单个人注意力有限，无法同时处理太多信息
- 人有专业壁垒，跨领域切换成本高
- 人与人之间必须靠接口和流程协调

但 LLM 的特点不同：

- **同一个模型既能写 PRD，也能写代码，没有天然职业边界**
- 它的瓶颈不是 “不会跨岗”，而是：
  - 推理深度不够
  - 信息不完整
  - 上下文不连续
- 多个 Agent 之间也没有人类组织里的 “文化、默契、非正式沟通” 来补足信息损耗

###### 3.2 “角色标签” 会制造假边界

- 给 Agent 贴上 “产品经理” 或 “测试工程师” 的角色标签，并不会让它真的更专业。
- 反而会让它被职责限制住，不去处理本该处理的问题。
- 比如：
  - 一个被限定为 “测试工程师” 的 Agent，发现了架构层问题，可能直接忽略，因为 “这不属于我的职责”。
- 作者认为，**很多真正有价值的推理，恰恰发生在角色边界处**，而这种架构会把这种可能性直接封死。

##### 4. 更严重的问题：信息在交接中不断丢失

###### 4.1 交接传的是结论，不是思考过程

- 在 “三省六部” 模式里，Agent A 写一份文档交给 Agent B。
- 问题是：B 接收到的通常只是结论，不是完整推理过程。
- 于是 B 必须重新理解上下文，原始意图、隐含假设、判断过程都会衰减。
- 每多一次传递，就多一层误差。
- 最终就会出现一种典型问题：**每一步看起来都对，但整体已经偏离目标。**

###### 4.2 人类能补偿，Agent 不行

- 人类组织里，信息损耗可以靠会议、闲聊、文化共识、反复确认来弥补。
- 但 Agent 之间没有这些机制。
- 所以一旦靠 “文档交接” 推进任务，误差会不断积累。

###### 4.3 为什么状态文件不等于 “交接文件”

作者专门回应了一个常见反驳：  
“Anthropic、OpenAI、Google 不也在用`progress.txt`、`spec`、`runbook`这类文件吗？”

关键区别在于：

- **三省六部的文档**：是 A 写给 B 的交接结果，信息被压缩成结论
- **厂商实践里的状态文件**：是同一个任务在不同时间点的连续记录，是 “同一个执行主体给未来的自己留下的完整历史”

也就是说：

- 前者是 “换人接棒”
- 后者是 “自己续跑”

这直接决定了推理链能不能跨 session 保持连续。

###### 4.4 token 被浪费在 “模拟组织行为” 上

- 作者指出，这种架构会把大量 token 消耗在：
  - 写交接文档
  - 读交接文档
  - 重建上下文
- 而不是用于真正解决问题的推理。
- 最终得到的不是一个高效的问题求解系统，而是一个**很像公司开会、但不一定真能干活的系统**。

##### 5. 三家大厂实际是怎么做的

##### 5.1 Anthropic：上下文工程 + 显式状态文件

- Anthropic 把 “Prompt Engineering” 升级为**“Context Engineering”**。
- 核心问题不是 “prompt 怎么写”，而是：**该如何组织 token，才能让模型持续产出正确行为。**

###### 他们面临的问题

- Agent 需要跨多个离散 session 工作
- 新 session 对之前发生的事情没有记忆
- Anthropic 把这个问题比作 “轮班工程师交接”

###### 他们的解决方案

- `claude-progress.txt`：跨 session 工作日志，每次结束更新，下次开始先读
- `Git history`：作为状态锚点，记录每次增量变化
- `Initializer Agent`：只在第一个 session 运行，负责搭环境、拆 feature、写 runbook，供后续使用

###### 关键结论

- **推理链连续性不能靠模型 “记住”，而要靠外部状态显式保存。**

###### 模型能力会变化，harness 也要跟着变

- 文中举了一个具体例子：
  - `Sonnet 4.5`有 “context anxiety” 问题：接近上下文上限时，会提前收尾
  - 因此 Anthropic 加了`context reset`
  - 但到了`Opus 4.5`，这个问题消失了
  - 之前设计的 reset 机制反而变成 “死重量”
- 说明一个重要现实：
  - **没有一劳永逸的 Agent 架构**
  - harness 和流程必须随着模型能力演进

###### 多 Agent 在 Anthropic 里是怎么用的

- 他们的 Research 系统采用的是**orchestrator-worker**模式：
  - 一个 lead agent 负责分解任务、协调工作
  - 多个 subagent 并行探索不同方向
  - 最后结果回流给 lead agent 汇总
- 他们发现：**token 消耗量本身就能解释 80% 的性能差异。**
- 也就是说，多 Agent 的价值主要不在 “角色分工更合理”，而在于：
  - 能同时探索更多路径
  - 覆盖更大搜索空间

###### 和 “三省六部” 本质区别

- 三省六部：职能性分工，像接力赛，一棒传一棒
- Anthropic：功能性并行，像撒网，不同 agent 同时查不同方向，再统一汇总
- 作者用一句话概括：
  - **前者是接力赛，后者是同时撒网捞鱼。**

##### 5.2 OpenAI：压缩 + Skills + 结构化规格文件

- OpenAI 的原则更直接：**长任务一开始就要为连续性做规划。**

###### Codex 的做法

- 给 agent 一个`spec`文件，先冻结目标
  - 防止模型做出 “看起来很厉害但方向错了” 的东西
- 再生成基于里程碑的计划
- 用`runbook`文件规定如何执行
- `runbook`同时承担：
  - 共享记忆
  - 审计日志

###### 重要案例

- 文中提到：**GPT-5.3-Codex 连续运行约 25 小时，完成了一个完整的设计工具，并保持了全过程连贯性。**

###### 技术机制

- `server-side compaction`被当成默认能力，不是紧急补救措施
- `previous_response_id`让模型可以在同一 thread 里连续工作，而不是每次从头重建上下文

###### Skills 不是角色

- OpenAI 引入了`Skills`：
  - 可复用
  - 可版本化
  - 可挂载进 container
  - 用来规范特定任务的执行方式
- 作者强调：
  - **Skills 是工具和操作规程，不是 “角色扮演”。**
  - 两者本质不同。

##### 5.3 Google：超大上下文 + 上下文驱动开发

- Google 的路线更偏向 “硬扩窗口”。
- `Gemini`提供了**1M token context**，这是其重要差异化能力。

###### 他们的判断

- 过去很多不得不做的技术手段，比如：
  - RAG 切片
  - 丢弃旧消息
- 在足够大的上下文窗口下，可以改成 “直接全部放进去”。

###### 但 Google 也承认：仅靠大窗口不够

- 在`Gemini CLI`中，他们推出了`Conductor`扩展。
- 核心思路和 Anthropic 很接近：
  - 把项目意图从聊天记录中拿出来
  - 放进代码库里的持久化 Markdown 文件
- 它依赖的是：
  - 正式的`spec`
  - 正式的`plan`
- 而不是不稳定的聊天历史

###### 额外机制

- `Gemini 3`引入了**Thought Signatures**
- 用来保存长 session 中推理链的关键节点
- 目的是防止**reasoning drift**，也就是长上下文下前后逻辑逐渐不一致

##### 6. 三家实践提炼出的共同原则

作者从 Anthropic、OpenAI、Google 的做法中，总结出几条真正有效的架构原则：

###### 6.1 推理链不能断，只能 “分叉再合并”

- 正确的多 Agent 方式不是流水线传递，而是：
  - 主 Agent 持有完整意图
  - 子 Agent 处理某个子问题
  - 结果回流到主 Agent
- 不能让任务一棒一棒交给不同角色，否则上下文会断。

###### 6.2 必须有显式外部状态

- 可以是：
  - `progress.txt`
  - `git history`
  - `spec`
  - 数据库
- 形式不重要，关键是：
  - 重要推理节点要持久化
  - 不能只依赖模型临时记忆

###### 6.3 多 Agent 的价值在 “并行覆盖”，不在 “角色分工”

- 多 Agent 更适合需要广度搜索的任务
- 比如同时调研多个方向、多个竞品、多个方案
- 不适合那种：
  - 需要长期连续推理
  - 强依赖完整上下文
  - 中间判断层层依赖前文的任务

###### 6.4 验证 Agent 应该是 “挑错者”，不是 “接棒者”

- 如果要做质量控制，正确做法是：
  - 让一个 Agent 专门找另一个 Agent 的漏洞
- 而不是让 QA Agent 接着 Dev Agent 的输出继续往下做
- 核心是：
  - **对抗性检验**
  - 不是流水线式传递

###### 6.5 工具比角色更重要

- 真正决定 Agent 能力的是：
  - 能不能调用`bash`
  - 能不能读写文件
  - 能不能搜索
  - 能不能执行代码
- 角色标签更多只是限制它 “愿不愿意做”
- 工具决定 “它能不能做”。

##### 7. 为什么这种错误架构仍然很流行

作者认为主要有三个原因：

###### 7.1 它太好解释了

- “这个 Agent 是 PM，那个是 QA”—— 任何人一听就懂。
- 这满足了人类对 AI 系统 “可解释性” 的需求。

###### 7.2 它太好展示了

- 画流程图时非常直观：
  - 有部门
  - 有箭头
  - 有交接
- 对管理层和产品展示都很友好。

###### 7.3 很多团队还没碰到复杂度门槛

- 在简单任务下，这种架构的问题不一定会暴露
- 但任务一复杂，信息损耗和整体漂移就会出现
- 典型表现是：
  - 每个节点单看都 “像在工作”
  - 最终结果却整体错误
- 作者认为，这正是它最危险的地方：**问题来得晚，而且很难诊断。**

##### 8. 实践建议：应该怎样设计 Agent 系统

###### 8.1 先看任务的信息依赖结构，不要先想 “要几个 Agent”

- 作者建议，不要先问：
  - “我要不要配 PM、架构师、测试工程师各一个？”
- 而应该问：
  - **这个任务的信息依赖关系是什么？**
  - **它更需要连续推理，还是更需要并行搜索？**

###### 8.2 连续推理任务：优先单 Agent + 好的上下文工程

- 如果任务高度依赖上下文连续性，比如：
  - 写复杂功能设计文档
  - 做深入方案推演
  - 进行多轮代码修改
- 那么通常：
  - **单 Agent + 良好 context engineering**
  - 会优于多角色流水线

###### 8.3 并行探索任务：适合多 Agent

- 如果任务天然可以拆成多个相对独立的方向，比如：
  - 同时研究 10 个竞品的不同模块
  - 并行搜索多个技术方案
- 那么多 Agent 并行是合理的
- 这里的收益来自：
  - 覆盖面更大
  - 搜索空间更广
- 而不是因为 “分工像公司”。

###### 8.4 跨 session 任务：必须有状态文件

作者还给出了一个很实用的建议：  
一份有效的外部状态文件应包含四类信息：

- **任务目标**：不变，防止 session 漂移
- **已完成步骤**：追加记录，不覆盖，保留完整历史
- **当前状态**：可覆盖，反映最新进展
- **已知的坑**：追加记录，避免重复踩坑

作者认为，这四类信息组合起来，才构成 “下一个自己” 真正需要的完整上下文。

###### 8.5 如果加验证环节，就让验证者只负责挑错

- 验证 Agent 的职责应非常明确：
  - 专门发现问题
  - 不负责接着往下做
- 这样才能形成有效的对抗性检查，而不是增加一次新的信息交接。

###### 8.6 架构要能演化，不要追求永久完美方案

- 模型能力变化很快，今天必须的 workaround，半年后可能就成负担。
- 文章再次用 Anthropic 的例子说明：
  - `Sonnet 4.5`需要`context reset`
  - 到`Opus 4.5`时，这个机制就失去意义
- 所以比起找一个 “完美架构”，更重要的是：
  - **保持系统可演化、可调整。**

##### 9. 结尾观点：这种架构最危险的成本，是 “悄悄退化”

- 作者最后总结：
  - “三省六部” 是一种让人感觉良好、也很好展示的设计幻觉
  - 但它在工程上的代价很高
- 它最危险的地方不在于会立刻失败，而在于：
  - 随着系统复杂度上升
  - 整体性能会以一种难以诊断的方式慢慢退化
- 最终表现就是：
  - 每个节点都 “看起来在工作”
  - 但整个系统已经偏离目标很远
- 等你意识到问题时，流程链条往往已经太长，很难回头修正。

##### 10. 一句话提炼

- **不要把多 Agent 系统设计成 “模拟公司协作”，而要把它设计成 “同一个思考过程的外化、延续和并行探索”。**
- 真正关键的不是 “角色分工”，而是：
  - 推理链连续
  - 外部状态明确
  - 并行探索合理
  - 架构可持续演化。

## 产品-最佳实践（1）

### 2026-04-15 07:37:08

#### 三省六部式多 Agent 不成立：一个具体工程实例与最佳实践

##### 先给结论

如果你要做的是一个**跨多个 session、上下文强依赖、需要持续推理和校验的软件任务**，那么最佳实践通常不是：

- PM Agent 写 PRD
- Architect Agent 写设计
- Dev Agent 写代码
- QA Agent 接着验收

而是：

- **一个主 Agent 持有完整目标和完整上下文**
- **必要时调用多个子 Agent 并行探索局部问题**
- **所有关键推理节点写入外部状态文件**
- **验证 Agent 只负责挑错，不负责接棒开发**

---

#### 具体实例

假设你要让 Agent 完成下面这个真实任务：

> 在一个已有电商系统中，实现 “退款申请审批流” 功能。  
> 要求包括：
> - 用户发起退款申请
> - 商家审核
> - 平台可介入仲裁
> - 退款状态要写入数据库
> - 后台页面展示审批流
> - 补充接口测试与回归验证
> - 任务可能跨 3~5 次 session 完成

这是一个非常典型的**高上下文依赖任务**，因为它同时依赖：

- 现有数据库结构
- 订单状态机
- 后端接口规范
- 前端页面逻辑
- 权限模型
- 测试基线
- 历史代码风格和项目约束

这种任务，最怕的不是 “不会写”，而是**中途漂移**。

---

#### 错误示范：三省六部式流水线

很多团队会自然设计成这样：

##### 流程

1. `PM Agent`读取需求，输出 PRD
2. `Architect Agent`根据 PRD 输出技术方案
3. `Dev Agent`根据技术方案写代码
4. `QA Agent`根据代码和方案写测试报告

##### 看起来有什么好处

- 角色清晰
- 流程直观
- 图很好画
- 很像真实公司协作

##### 但它会怎么失败

###### 1. 信息在交接中被压缩

`PM Agent`产出的是 “需求结论”，不是完整推理过程。  
`Architect Agent`接到的是二手理解。  
`Dev Agent`接到的是三手抽象。  
到最后，代码可能每一步都 “局部合理”，但整体偏离真实目标。

例如：

- PM 写了 “支持平台仲裁”
- Architect 理解为 “增加一个仲裁状态”
- Dev 实现成 “管理员可直接改退款状态”
- QA 只验证了状态能改，没验证仲裁证据链

每一步都没明显错，但最终功能不对。

###### 2. 角色标签会制造盲区

比如`QA Agent`被限定成 “测试工程师”，它可能只测接口返回值，不会回头指出：

- 数据模型设计不合理
- 状态机不可逆
- API 语义不一致
- 审批流缺少审计字段

因为这些 “看起来不是 QA 的职责”。

###### 3. 跨 session 时上下文断裂

如果任务分 4 次完成，下一次 session 里新的 Agent 实际并不 “记得” 前面发生了什么。  
它只能读取交接文档，而交接文档往往是摘要，不是完整历史。

于是问题会变成：

- 为什么这个字段要这样设计？
- 为什么拒绝退款后还能再次提交？
- 为什么前端展示逻辑和数据库状态不一致？

这些关键约束，很容易在交接中丢失。

---

#### 正确做法：主 Agent + 外部状态 + 并行子探索

对于这个 “退款审批流” 任务，更合理的架构是下面这样。

##### 架构原则

###### 1. 一个主 Agent 持有完整意图

主 Agent 从头到尾负责：

- 理解任务目标
- 理解代码库现状
- 维护计划
- 记录决策
- 综合子任务结果
- 最终判断是否完成

它不是 “某个角色”，而是**任务拥有者**。

###### 2. 子 Agent 只做局部探索

当遇到可以并行的问题时，主 Agent 可以派出子 Agent 去探索，例如：

- 子 Agent A：梳理订单和退款相关数据库表
- 子 Agent B：检查后台管理端现有审批页面组件
- 子 Agent C：盘点已有测试框架与可复用测试样例

这些子 Agent 的结果都**回流给主 Agent**，而不是互相交接。

###### 3. 外部状态文件承担连续性

不要把连续性寄托在 “模型记住了什么”，而要写入明确的状态文件。

例如：

- `spec/refund-approval.md`：冻结目标和边界
- `runbook/refund-approval-runbook.md`：记录执行方法和验证步骤
- `progress/refund-approval-progress.md`：记录当前进展、历史决策、已知问题

---

#### 这个实例下的最佳实践

##### 一、先冻结目标，而不是先分角色

在开始前，先写一份最小可执行规格文件，例如：

```md
# Refund Approval Spec

## Goal
为现有电商系统增加退款申请审批流，支持用户申请、商家审核、平台仲裁、状态可追踪。

## In Scope
- 新增退款申请接口
- 新增退款审批状态流转
- 后台展示审批记录
- 增加必要数据库字段或表
- 增加接口测试

## Out of Scope
- 不重构整个订单系统
- 不新增消息通知中心
- 不改动支付网关逻辑

## Acceptance Criteria
- 用户可提交退款申请
- 商家可审核通过 / 拒绝
- 平台可介入仲裁
- 所有关键操作有审计记录
- 相关接口测试通过
```

###### 为什么这是最佳实践

因为它解决的是**方向漂移**问题。  
很多 Agent 失败，不是能力不够，而是做出了 “看起来很厉害但不是你要的东西”。

---

##### 二、把进展写成 “增量历史”，不要写成交接摘要

推荐维护一份`progress`文件，结构如下：

```md
# Refund Approval Progress

## Task Goal
实现退款申请审批流，保持与现有订单状态机兼容。

## Completed Steps
- 已确认订单表`orders`不适合直接承载审批历史
- 已决定新增`refund_requests`与`refund_events`两张表
- 已确认后台已有可复用的审批时间线组件
- 已完成退款申请接口草案

## Current Status
正在实现商家审核接口，并补充状态流转校验。

## Decisions
- 审批历史采用事件表，不把完整历史压缩进订单主表
- 平台仲裁必须记录操作人、原因、证据链接
- 拒绝退款后允许用户在补充材料后再次发起申请

## Known Pitfalls
- 现有订单取消逻辑会误判退款完成态
- 后台列表页默认筛选条件可能漏掉 “仲裁中” 状态
- 接口幂等性需要单独验证
```

###### 为什么这是最佳实践

因为下一次 session 需要的不是 “上一位同事写了什么总结”，而是：

- 目标是什么
- 做过什么
- 为什么这么做
- 现在卡在哪
- 哪些坑不要再踩

这才是能跨 session 延续推理链的最小集合。

---

##### 三、并行只用于 “可独立探索” 的问题

这个实例里，适合并行的任务包括：

- 搜索所有与退款相关的历史代码
- 盘点现有状态机枚举及其调用点
- 调查后台审批 UI 可复用组件
- 汇总测试框架中的 fixture 和 helper

不适合并行流水线传递的任务包括：

- “设计写完再交给开发”
- “开发写完再交给测试”
- “前一个 Agent 定义完含义，后一个 Agent 不再回头验证”

###### 判断标准

如果一个子任务的输出是**事实收集、方案比对、局部搜索**，适合并行。  
如果一个子任务的输出会成为**后续连续推理的唯一依据**，不要把它做成接力棒。

---

##### 四、让验证 Agent 做 “否定者”，不要做 “接棒者”

在这个退款审批流例子中，正确的验证 Agent 提示词应该类似：

```md
请不要继续实现功能。
你的唯一目标是尽可能找出当前方案和实现中的问题，重点检查：
- 状态机是否存在不可恢复或非法跳转
- 审计字段是否完整
- 平台仲裁是否有越权风险
- 数据模型是否支持历史追踪
- 测试是否遗漏幂等性、并发和回归场景
```

###### 为什么这是最佳实践

因为 “继续做下去” 和 “专门挑错” 是两种完全不同的认知模式。  
如果你让验证 Agent 同时承担 “检查” 和 “推进”，它往往会偏向于把任务做完，而不是严格发现问题。

---

##### 五、工具优先于角色

在这个例子里，比 “你是架构师 / 开发 / 测试” 更重要的是 Agent 是否拥有这些能力：

- 搜索代码库
- 读取数据库 schema
- 运行测试
- 比较 diff
- 更新状态文件
- 执行脚本验证接口

###### 最佳实践做法

给主 Agent 配：

- 代码搜索工具
- 文件读写工具
- 测试执行工具
- git diff /history 读取能力

给验证 Agent 配：

- 只读代码与测试运行能力
- 缺陷报告输出能力

不要靠角色身份驱动行为，要靠**可用工具 + 明确目标**驱动行为。

---

##### 六、所有关键决策都要可追溯

在这个退款流程任务中，有几类决策必须显式记录：

- 为什么新增表，而不是在订单表上打补丁
- 为什么允许拒绝后重新申请
- 为什么仲裁需要独立事件记录
- 为什么某些状态不允许前端直接展示为 “退款成功”

###### 最佳实践

把这些决策写进：

- `spec`：记录稳定目标与边界
- `progress`：记录动态决策与当前状态
- `git commit`或变更说明：记录实际实现落点

这样当后续要改需求时，Agent 或人类都能回溯 “当初为什么这么做”。

---

#### 推荐的执行模板

下面是这个实例可以直接套用的一套简化流程。

##### 第 1 步：主 Agent 建立任务骨架

产出 3 份文件：

- `spec/refund-approval.md`
- `runbook/refund-approval-runbook.md`
- `progress/refund-approval-progress.md`

---

##### 第 2 步：主 Agent 扫描代码库并形成初始判断

输出内容包括：

- 涉及哪些模块
- 哪些地方不能轻易改
- 需要哪些数据库变更
- 已有测试基线在哪里

---

##### 第 3 步：并行派出子 Agent 做局部探索

例如：

- 子 Agent A：退款相关表结构与状态字段盘点
- 子 Agent B：后台审批页面组件复用性分析
- 子 Agent C：现有测试框架覆盖情况盘点

主 Agent 统一汇总结论。

---

##### 第 4 步：主 Agent 做唯一方案收敛

主 Agent 根据所有探索结果，形成：

- 最终数据模型
- 状态流转规则
- 接口草案
- UI 改动点
- 测试计划

这一步不要拆成流水线交接。

---

##### 第 5 步：主 Agent 实施，持续更新 progress

每完成一个 checkpoint，就写入：

- 完成了什么
- 当前做到哪里
- 改了哪些关键文件
- 还有什么风险未消除

---

##### 第 6 步：验证 Agent 只做挑错

重点检查：

- 状态机漏洞
- 权限漏洞
- 审计缺失
- 边界条件遗漏
- 测试盲区

发现问题后回流给主 Agent，由主 Agent 决定修复方案。

---

#### 一套可直接复用的判断框架

当你不确定该不该用多 Agent 时，可以先问这 5 个问题：

##### 1. 这个任务是 “连续推理” 还是 “并行搜索”？

- 连续推理为主：优先单主 Agent
- 并行搜索为主：适合 orchestrator-worker

##### 2. 子任务之间是否强依赖上下文？

- 强依赖：不要流水线拆角色
- 弱依赖：可以并行探索

##### 3. 任务是否跨多个 session？

- 如果是：必须有外部状态文件
- 如果不是：也建议至少有 spec 和 progress

##### 4. 你需要的是 “推进” 还是 “挑错”？

- 推进：主 Agent
- 挑错：验证 Agent
- 不要混用

##### 5. 你设计的是 “工作分工”，还是 “信息结构”？

如果答案是前者，通常已经偏向三省六部幻觉了。  
更好的问题应该是：

> 哪些信息必须始终由同一个主体持有？  
> 哪些问题可以独立搜索后再汇总？

---

#### 最终可落地的最佳实践清单

##### 推荐做法

- 用**一个主 Agent**持有完整目标、计划和上下文
- 用**外部状态文件**维持跨 session 连续性
- 用**子 Agent 并行探索独立问题**，不要做角色流水线
- 用**验证 Agent 专门找错**，不要让它接棒继续开发
- 用**spec /progress/runbook /git history**共同构成任务记忆
- 用**工具能力**定义 Agent 边界，而不是用 “职位名称” 定义边界
- 定期清理随着模型升级失效的 workaround，保持 harness 可演化

##### 避免做法

- 不要按 PM / Architect / Dev / QA 做固定串行交接
- 不要让关键信息只存在聊天记录里
- 不要把 “交接文档” 当成连续推理的替代品
- 不要把验证环节设计成 “顺手检查一下”
- 不要把 “好解释的流程图” 误当成 “工程上有效的系统”

---

#### 一句话总结

在这个 “退款审批流” 实例里，最好的多 Agent 方案不是模拟一家虚拟公司，而是构建一个**始终由同一主脑掌握意图、通过外部状态延续记忆、按需并行搜索、最终统一收敛**的系统。

#### 《三省六部幻觉：为什么 “虚拟公司” 式多 Agent 架构在工程上不成立》精炼提炼

##### 一、启发

- **不要把 “组织学直觉” 误当成 “系统设计原则”**  
  人类公司需要分工，是因为注意力、专业壁垒、沟通成本；LLM 不受这些约束，真正瓶颈是**推理深度、上下文完整性、状态连续性**。

- **多 Agent 的价值不在 “角色分工”，而在 “搜索并行”**  
  真正有效的多 Agent，不是 PM→Dev→QA 的流水线，而是一个主 Agent 保持完整意图，多个子 Agent 并行探索，再由主 Agent 汇总。

- **工程里最贵的不是 token，而是 “隐性漂移”**  
  三省六部式架构的危险，不是明显报错，而是每一步都看似合理，最终整体偏离目标。这类系统在 demo 阶段常常 “看起来不错”，在复杂任务里才暴露脆弱性。

- **外部状态比角色设定重要一个数量级**  
  `spec`、`progress.txt`、`runbook`、`git history`这些 “显式状态锚点”，比 “你现在扮演架构师” 更决定系统能否稳定完成长任务。

- **Agent 架构不是一次性设计，而是随模型能力演化的运营系统**  
  今天为模型缺陷设计的 workaround，半年后可能成为性能负担。架构要追求 “可演化”，而不是 “概念上完美”。

##### 二、高价值信息深挖

###### 1. 这篇文章真正批判的，不是多 Agent，而是 “接力式多 Agent”

核心不是 “多 Agent 不行”，而是：

- **职能型接力**：A 做完交给 B，B 再交给 C  
- **功能型并行**：多个子 Agent 同时探索，统一回流给 orchestrator

两者差异极大：

| 维度 | 三省六部式 | 厂商实践式 |
|---|---|---|
| 结构 | 流水线接力 | 主脑 + 并行分叉 |
| 信息传递 | 结论交接 | 状态累积 + 结果回流 |
| 风险 | 上下文衰减、责任边界僵化 | token 成本上升，但意图连续 |
| 适用任务 | 低复杂度、展示型流程 | 高复杂度、探索型与长任务 |

这里最关键的洞察是：  
**LLM 系统的首要目标，不是模拟组织协作，而是保护推理链连续性。**

---

###### 2. “角色” 是解释层，不是能力层

给 Agent 贴上 “产品经理”“测试工程师” 的标签，本质上做了两件危险的事：

- **压缩问题视角**：Agent 倾向只看 “职责内” 的信息
- **抑制跨边界推理**：最有价值的问题往往出现在需求、架构、实现、验证的交界处

这对商业系统尤其重要。现实里很多高价值决策都不是单一职能问题，而是：

- 功能设计影响商业模式
- 技术方案影响单位经济模型
- 测试反馈反过来揭示需求假设错误
- 用户增长问题本质可能是产品结构问题

所以，**角色标签会增强系统可解释性，但削弱系统跨域推理能力。**

---

###### 3. “文件传递” 与 “状态锚定” 看似相似，实则完全不同

文章里一个非常关键、很容易被忽略的点是：

- 三省六部式的文档，是**角色间的交接物**
- 厂商实践里的`spec` / `progress` / `runbook`，是**同一任务主体跨时间的状态锚点**

区别在于：

- 前者传的是 “摘要后的结论”
- 后者保留的是 “任务历史 + 当前状态 + 后续约束”

这意味着，真正有价值的不是 “写文档”，而是**把任务状态设计成可持续恢复、可追加、可审计、可回放的结构**。

对于 AI 产品和商业系统构建，这几乎可以抽象成一个总原则：

> 一个可靠的 AI 系统，本质上不是 prompt system，而是 state system。

---

###### 4. 多 Agent 性能提升，很可能只是因为 “花了更多 token”

这是全文最值得商业决策者警惕的一点。

很多团队看到多 Agent 变强，会自然归因于：

- 分工更合理
- 结构更先进
- 组织更像人类团队

但 Anthropic 的观察更朴素：  
**性能提升的主要解释变量，可能只是 token 消耗更多，搜索覆盖更大。**

这带来两个商业层面的重要提醒：

- 你看到的 “架构收益”，可能只是 “算力堆出来的收益”
- 如果不分离 “结构增益” 和 “资源增益”，就会高估架构本身的价值

对产品负责人来说，这意味着不能只问：

- “效果变好了没有？”

还要问：

- “是因为架构更优，还是因为 token 花得更多？”
- “这个提升能否在单位成本上成立？”
- “是否存在更简单、成本更低的替代方案？”

---

###### 5. 长任务系统的核心能力不是聪明，而是 “不中断”

从 OpenAI、Anthropic、Google 的实践看，真正难的不是一次生成，而是：

- 跨 session 保持目标一致
- 长时任务防漂移
- 能恢复、能审计、能回滚
- 在模型能力变化时持续适配

这和商业系统建设高度一致。  
一个能跑 5 分钟的 AI demo，不等于一个能跑 25 小时、可被团队接管、可复盘、可升级的生产系统。

所以，这篇文章对产品 / 商业系统构建者的深层启发是：

> AI 应用的护城河，越来越不在 “单次回答有多惊艳”，而在 “任务系统能否稳定延续”。

##### 三、可迁移清单

##### 你可以直接迁移到项目中的设计原则

- **先判断任务依赖结构，再决定 Agent 数量**
  - 高上下文依赖、连续推理任务：优先单 Agent
  - 多方向独立探索任务：适合多 Agent 并行

- **让一个主 Agent 持有完整意图**
  - 目标冻结
  - 关键约束固定
  - 子任务回流统一汇总
  - 避免子 Agent 之间互相接棒

- **把状态外化，不把记忆寄托在上下文窗口**
  - `spec.md`：目标与边界
  - `progress.md`：已完成步骤与历史
  - `runbook.md`：操作规程与约束
  - `pitfalls.md`：已知坑与禁止事项

- **把 “技能” 做成可复用操作模块，而不是角色设定**
  - 代码修改规范
  - 测试执行规范
  - 调研输出模板
  - 上线检查清单

- **验证环节用 “否定者 Agent”，不用 “接棒者 Agent”**
  - 专门负责找漏洞、反例、遗漏
  - 不负责继续生产内容
  - 降低 “带着错误继续往前跑” 的风险

- **持续评估架构的单位成本**
  - 每个 Agent 增加了多少 token 消耗
  - 带来了多少质量提升
  - 是否只是冗余包装了单 Agent 可完成的任务

##### 四、反方与张力

###### 1. 三省六部式并非毫无价值，它有很强的 “组织可接受性”

反方最强论点不是 “它工程更优”，而是：

- 更容易向老板解释
- 更容易让团队理解系统流程
- 更方便做产品演示和售卖
- 更符合人类对 “协作” 的认知框架

这意味着它在**销售、培训、PoC、内部共识建立**上有价值。  
问题不在于不能用，而在于**不能把展示层逻辑误当执行层逻辑**。

---

###### 2. 角色化有时可以作为 “认知约束器”

虽然角色经常制造假边界，但在某些低风险场景下，它也有作用：

- 让输出风格更稳定
- 限制 Agent 过度发散
- 用于教学、模板化流程、固定格式任务

也就是说，角色不是绝对有害，而是：

- 在**高复杂度、强依赖、长链任务**里有害
- 在**低复杂度、强格式、弱依赖任务**里可能有效

张力在于：  
**越像生产系统，越不能依赖角色；越像展示 / 模板系统，角色越有实用价值。**

---

###### 3. 大上下文窗口并不自动解决问题

Google 走的是 “更大 context” 路线，但文章也指出：

- context 变大，不等于逻辑就不漂移
- 信息都塞进去，不等于系统就会更稳定
- 长 session 仍需要 thought signatures、正式 spec、持久状态文件

所以反过来要警惕一种新幻觉：

> 从 “多 Agent 幻觉” 切换成 “超长上下文幻觉”。

本质问题仍然是：  
**你有没有把任务状态设计清楚。**

---

###### 4. 单 Agent 也不是银弹

单 Agent 的问题同样存在：

- 容易路径依赖
- 容易陷入单一思路
- 缺乏外部对抗性校验
- 对复杂搜索任务覆盖不足

因此更准确的结论不是 “单 Agent 更好”，而是：

> 连续推理靠单主脑，并行探索靠多分叉，质量保障靠独立否定者。

这比 “单 Agent vs 多 Agent” 更接近真实工程选择。

---

##### 五、情境化落地

##### 场景 1：你在做 AI Coding / 开发代理

###### 不建议
- PM Agent 写 PRD
- Architect Agent 写设计
- Dev Agent 改代码
- QA Agent 跑测试

这套流程非常像公司，但会不断丢失上下文，最后出现：
- 代码实现局部合理
- 设计约束被稀释
- 测试覆盖不到真实风险
- 整体偏离原始目标

###### 建议做法
- 一个主 Agent 持有`spec.md`
- 子 Agent 并行做：
  - 方案 A/B 比较
  - 某模块代码阅读
  - 风险点排查
  - 测试案例补全
- 所有结果回流给主 Agent 汇总决策
- 每轮结束更新`progress.md`

###### 适合的文件结构
```md
/spec.md
/progress.md
/runbook.md
/pitfalls.md
```

---

##### 场景 2：你在做 AI 产品经理工作流

###### 不建议
让 “市场分析 Agent → 用户研究 Agent → PRD Agent → 增长 Agent” 串行传递。

因为产品决策的关键不是文档生产，而是：
- 用户价值判断
- 商业约束权衡
- 技术可实现性
- 路线优先级取舍

这些是强耦合问题，不适合流水线式拆分。

###### 建议做法
- 主 Agent 持有统一产品目标、用户画像、业务约束
- 多个子 Agent 分别并行探索：
  - 竞品策略
  - 用户场景
  - 定价模式
  - 风险假设
- 主 Agent 汇总成一个统一决策框架，而不是拼接几份 “部门报告”

---

##### 场景 3：你在做商业系统或内部运营自动化

###### 如果任务是标准、重复、低依赖
例如：
- 报表清洗
- 工单分类
- FAQ 回复
- 标准审核流

可以保留一定 “角色感”，因为重点是流程清晰与可治理。

###### 如果任务是策略、诊断、跨模块优化
例如：
- 漏斗转化诊断
- 增长策略生成
- 销售流程重构
- 客诉背后的系统性问题排查

更适合：
- 单主脑持有全局业务上下文
- 子 Agent 并行检索不同证据
- 独立校验 Agent 专门找反例

---

##### 场景 4：你在搭建自己的 AI Agent 平台或产品

你可以把这篇文章转成 5 条平台能力要求：

- **状态层**：支持任务目标、进度、坑点、当前状态的持久化
- **编排层**：支持主 Agent 分叉并回收子任务结果
- **技能层**：支持可版本化、可挂载的操作规范
- **审计层**：支持过程可回放、结果可追责
- **演化层**：支持随着模型变化调整 harness，而不是把 workaround 写死

如果你做平台，这些能力比 “支持多少种角色模板” 重要得多。

---

##### 一句话结论

**“虚拟公司式多 Agent” 本质上是在用人类组织想象设计 AI 系统；而生产级 Agent 架构的核心，不是分工是否像公司，而是推理链是否连续、状态是否外化、并行是否真正提升搜索覆盖。**

##### 对你这类长期关注者的最实用提醒

- 如果你关注的是**AI 产品落地**：优先设计状态系统，而不是角色系统  
- 如果你关注的是**开发效率**：优先保护上下文连续性，而不是增加流程节点  
- 如果你关注的是**商业可行性**：优先衡量 token 成本与质量增益，而不是迷信架构名词  
- 如果你关注的是**长期系统建设**：优先追求可演化的 harness，而不是一次性 “最优架构”
