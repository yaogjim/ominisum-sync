## 解读（1）

### 2026-04-14 04:01:52

#### 总结

这条内容主要表达了两层意思：

1. 作者在对比市面上优秀的开源 Agent / Agent Harness 框架后，复盘了自己正在做的工程，发现存在不少问题。  
2. 因此决定调整方向：不再“从零造轮子”为主，而是基于成熟框架做二次开发，这样更省力，效果也可能更好。

补充的热门回复则提到一个相关观点：很多时候不是人“不行”，而是因为“决策疲劳”导致判断质量下降，做得越久、决定越多，越容易选择默认方案或干脆停摆。

---

#### 解读

##### 1. 这其实是在讲“工程现实”

很多开发者一开始做 Agent 工程，都会想自己搭一套完整的 harness（调度、工具调用、记忆、上下文管理、评估、观测等）。  
但真正做下去会发现：

- 组件很多，链路很长
- 调试很痛苦，问题不好定位
- 稳定性、扩展性、评测体系都很难一次做好
- 别人已经踩过的大量坑，自己还要再踩一遍

所以作者的结论很现实：**自己从头做，不一定最优；站在成熟框架上改，往往更高效。**

##### 2. “二开”不是认输，而是更成熟

这里的“基于优秀框架进行二开”，本质上不是放弃创新，而是把精力放在更有价值的地方：

- 通用能力，交给成熟框架
- 差异化能力，自己重点打磨
- 少花时间补基础设施，多花时间做真正有竞争力的功能

换句话说，**不是不做，而是换一种更聪明的做法。**

##### 3. 热门回复点出了一个关键问题：决策疲劳

作者回复里说“很多时候发现自己做决策的质量非常低”，这很真实。  
做 Agent 工程时，几乎每天都在做决定：

- 用哪个模型
- 用哪种工具调用协议
- 记忆怎么设计
- 多 Agent 还是单 Agent
- 状态怎么持久化
- 评测指标怎么定

当决策太多时，大脑会进入“省电模式”：

- 要么沿用默认方案
- 要么迟迟定不下来
- 要么频繁推翻之前的选择

所以他最终决定参考优秀开源方案，某种程度上也是在**降低决策成本**。这其实是很健康的工程思路。

---

#### 我的意见

我比较认同作者的方向调整。

- **早期阶段**：优先借助成熟开源框架，快速验证思路，比自己从零搭全套更划算。  
- **中期阶段**：找到真正不满足需求的部分，再局部重写或深度定制。  
- **长期阶段**：只有当你已经非常清楚“现有框架哪里不行”，再考虑自己造核心轮子。  

简单说：

> **先借力，再发力；先跑通，再做深。**

如果是做 Agent Harness，这类基础设施尤其适合这样做。因为它不是“能跑就行”，而是很考验稳定性、可维护性和可观测性。自己全做，成本非常高。

另外，关于“决策疲劳”，我的建议也很直接：

- 重要技术决策尽量放在精力最好的时间做
- 能标准化的就标准化，减少重复选择
- 先设定评判标准，再选方案，不要凭感觉反复摇摆
