## 分析要点

- **核心高价值点**：将复杂任务拆成多个独立上下文的子代理，并通过对抗性验证和合成步骤降低目标漂移、自我偏好和代理懒惰。
- **留存建议**：长期保留（文章系统介绍了Claude Code动态工作流的适用场景、常见模式和实践技巧，对构建多智能体任务编排有较高参考价值。）

**知识要点**

- 动态工作流适合长时间、大规模并行、高结构化或需要验证的复杂任务，不适合所有常规编码任务。
- 常见模式包括分类-执行、扇出-合成、对抗性验证、生成-过滤、锦标赛和循环直到完成。
- 动态工作流可用于代码迁移、深度研究、事实核查、候选排序、规则提炼、根因调查和大规模分类。
- 工作流可设置token预算，并可与/goal、/loop结合，用于周期性或持续性任务。
- 通过隔离不同代理权限，可以降低不可信输入导致高权限操作风险。

**行动项**

- 尝试为一个复杂代码审查任务设计扇出-合成加对抗性验证工作流。
- 将近期重复出现的Claude修正问题整理为CLAUDE.md规则，并用验证代理复核。
- 在使用动态工作流前评估任务是否真的需要额外token和多代理编排。
- 为研究、事实核查或批量排序类任务准备可复用的工作流模板。

上周，我们发布了

[动态工作流](https://code.claude.com/docs/en/workflows)在 Claude Code 中。Claude 现在可以编写自己的

[框架](https://code.claude.com/docs/en/glossary#agentic-harness)

实时地，为当前任务定制的。

虽然默认的 Claude Code 工具是为编码而构建的，但它对许多其他类型的任务也很有用，因为事实证明，许多任务类似于编码任务。但对于某些类型的任务，我们必须在 Claude Code 之上构建自定义工具以实现最佳性能，例如研究、安全分析、代理团队或代码审查。

工作流允许你动态创建工具，使 Claude 能够原生地在 Claude Code 中解决所有这些问题以及更多问题。你还可以与他人共享和复用这些工作流。

在本文中，我将介绍我的初步工作流程经验和心得，以便你能充分利用。

话虽如此，最佳实践仍在发展中！动态工作流常常使用更多的令牌，因此，仔细考虑何时以及如何使用它们。 Note：这篇文章也

[可在 Claude 博客上查看](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)

#### 示例提示

在深入探讨技术细节之前，我想先从一些示例提示开始，让你思考工作流的可能性：

- 使用工作流，查看我最近的 50 个会话，从中提取我反复出现的错误修正，并将重复出现的错误修正转化为 CLAUDE.md 规则

- 审阅我的博客文章草稿，使用工作流对照代码库验证每一个技术声明；我不想发布任何错误的内容。

#### 动态工作流如何工作

动态工作流执行一个 JavaScript 文件，其中包含一些特殊函数，这些函数有助于生成和协调

[子代理](https://code.claude.com/docs/en/sub-agents):

![Image](https://pbs.twimg.com/media/HJ0t9PDbQAAYqh-?format=jpg&name=large)

动态工作流还包括标准的 JavaScript 函数，例如 JSON、Math 和 Array，以帮助处理数据。

了解到动态工作流可以决定代理使用哪些模型以及子代理是否在自己的工作树中运行，这一点尤为有用，因为这使 Claude 能够选择所需的智能级别和隔离程度。

如果工作流被中断（例如通过用户操作或退出终端），恢复会话将允许工作流从上次中断处继续。

#### 为什么动态工作流

当你要求默认的 Claude 代码框架执行任务时，它需要在同一个上下文窗口中同时进行规划和执行。对于许多编码任务，这非常有效，但在处理长时间运行、大规模并行和/或高度结构化的对抗性任务时，它有时会出现故障。

这是因为 Claude 在单个上下文窗口中处理复杂任务的时间越长，就越容易受到几种特定失败模式的影响：

- 代理式懒惰指的是当 Claude 在完成一个特别复杂的、多部分的任务之前就停止，并在取得部分进展后宣称任务完成，例如在安全审查中处理了 50 项中的 20 项。
- 自我偏好偏差指的是 Claude 的倾向于偏好自己的结果或发现，尤其是当被要求根据评分标准对其进行验证或评判时。
- 目标漂移指的是在多轮过程中对原始目标的保真度逐渐降低，尤其是在压缩后。每个总结步骤都是有损的，边缘情况要求或“不要做 X”的约束条件等细节可能会丢失。

创建工作流有助于通过编排拥有各自上下文窗口和专注且独立目标的独立 Claude 来应对这些。

#### 动态 vs 静态工作流

你可能之前已经使用 Claude Agent SDK 或 claude -p 创建了一个静态工作流，来协调多个 Claude Code 实例协同工作。

但由于静态工作流需要处理所有边缘情况，它们通常更通用。借助 Claude Opus 4.8 和动态工作流，Claude 现在已经足够智能，可以为您的使用场景编写一个量身定制的自定义工具。

![Image](https://pbs.twimg.com/media/HJ1Dc3waUAA8Eeo?format=png&name=large)

### 使用动态工作流时的有用模式

你只需让 Claude 创建一个动态工作流，或者使用触发词“ultracode”来确保 Claude Code 创建一个工作流，即可开始使用动态工作流。

但构建一个关于动态工作流如何运作的心理模型，将帮助你理解何时使用它们，以及如何通过提示来引导 Claude。

当构建工作流时，Claude 可能会使用并组合一些常见的模式：

![Image](https://pbs.twimg.com/media/HJ0u_2cbMAA3ufP?format=jpg&name=large)

分类-执行

使用分类器代理来决定任务类型，然后根据任务路由到不同的代理或行为。或者，在最后使用一个分类器来确定输出。

扇出-合成

将任务拆分为多个较小的步骤，在每个步骤上运行一个代理，然后综合这些结果。这在以下情况特别有用：当存在大量较小的步骤时，或者当每个步骤都能受益于其独立的干净上下文窗口，从而避免相互干扰或交叉污染。综合步骤是一个屏障——它等待所有“扇出”代理完成，然后将它们的结构化输出合并为一个结果。

对抗性验证

对于每个生成的代理，运行一个单独的生成代理，以对抗的方式根据评分标准或准则验证其输出。

生成-过滤

围绕一个主题生成若干想法，然后通过评分标准或核实进行筛选，去除重复项，并仅返回质量最高、经过验证的想法。

锦标赛

与其分配工作，不如让智能体竞争完成任务。生成 N 个智能体，每个智能体都采用不同的方法尝试相同的任务。然后，提示词或模型使用一个评判智能体以成对的方式评判结果，直到产生一个获胜者。

循环直到完成

对于工作量未知的任务，循环生成代理，直到满足停止条件（没有新发现，或者日志中不再有错误），而不是固定次数的迭代。

### 用例

创造性地思考何时以及如何让 Claude Code 创建动态工作流。我发现，工作流有时对非技术工作甚至更有用。

![Image](https://pbs.twimg.com/media/HJ018ZjbcAA4nFm?format=png&name=large)

#### 迁移和重构

[Bun](https://bun.com/) 是通过工作流从 Zig 重写为 Rust 的。你可以阅读更多关于该过程的实现细节，在

[Jarred 的 X 帖子](https://x.com/jarredsumner/status/2060050578026189172)

。

关键是将任务分解为一系列需要操作的步骤，例如调用点、失败的测试、模块等。为工作树中的每个修复创建一个子代理来执行修复，然后让另一个代理进行对抗性审查，最后合并这些修复。可以考虑告诉代理不要使用资源密集型命令，这样你就可以最大程度地并行化操作，而不会耗尽机器上的资源。

#### 深度研究

我们在 Claude Code 中发布了一项深度研究技能（/deep-research），该技能采用动态工作流。具体而言，它会展开网络搜索、获取来源、对抗性验证其主张，并综合生成一份带引用的报告。

但是你可以进行这类研究，而不仅仅是网页搜索。例如，让 Claude 基于 Slack 中的上下文编写一份状态报告，或者让它通过深入探索代码库来研究某个功能如何工作。

#### 深度核实

![Image](https://pbs.twimg.com/media/HJ0vMJ8acAAM9Uo?format=jpg&name=large)

另一方面，如果你有一份报告，需要检查并查证它引用的每一个事实性主张的来源，你可能需要生成一个工作流程：首先由一个代理识别所有事实性主张，然后派生出一个子代理来详细检查每一个。你还可以让一个核实代理检查源子代理，以确保其来源质量高。

#### 排序

![Image](https://pbs.twimg.com/media/HJ0wACFbMAAAvWl?format=jpg&name=large)

你可能有一个需要按某种定性衡量标准排序的项目列表，你认为 Claude Code 擅长评估该标准，例如：按 bug 严重程度排序的支持工单。但如果尝试在一个提示中对 1000+行进行排序，质量会下降且超出上下文范围。相反，可以采用竞赛式方法、两两比较代理的流程（比较判断比绝对评分更可靠），或者并行分桶排序后合并。每次比较都是独立的代理，因此确定性循环维持竞赛树状结构，只有运行顺序保留在上下文中。

#### 记忆与规则遵循

![Image](https://pbs.twimg.com/media/HJ0wF76acAAyRMo?format=jpg&name=large)

如果您有一组特定的规则，即使将其放入 CLAUDE.mds 中，您发现 Claude 会遗漏或难以处理这些规则，那么可以创建一个工作流，其中包含必须由验证代理检查的规则列表——每个规则对应一个验证代理。创建一个持怀疑态度的角色子代理来审查这些规则，以确保它们符合要求，这将有助于避免过多的误报。

反向也适用：挖掘你最近的会话和代码审查评论中你反复进行的修正，使用并行代理对这些修正进行聚类，对抗性地验证每个候选（这条规则是否能防止真实的错误？），然后将这些幸存者提炼回一个

[CLAUDE.md](http://claude.md/)。

#### 根本原因调查

调试时，当你提出几个独立假设并测试它们时效果最佳，但如果只使用一个上下文窗口，Claude 可能会遇到自我偏好偏差。 工作流可以从结构上通过部署代理来防止这种情况，这些代理从不相交的证据中生成假设。例如，为日志、文件和数据分别部署代理。然后，每个假设都可以接受一组验证者和反驳者的审查。

这不仅仅用于代码。工作流可用于销售（为什么三月份的销售额下降了？）、数据工程（为什么这个数据流水线失败了？）或任何事后分析活动。

#### 大规模分类与优先级排序

![Image](https://pbs.twimg.com/media/HJ0wNb8bUAA33h5?format=jpg&name=large)

每个团队都有一个支持队列、bug 报告，或者其他一些无法完全由人工处理的积压工作。

分类筛选工作流会对每个项目进行分类，与已跟踪的内容去重，并采取行动。这可能意味着尝试修复或升级到人工用户。

分类工作流的一个有用模式是隔离。这包括禁止读取不可信公共内容的代理执行高权限操作，这些操作改由负责处理信息的代理执行。

将分类工作流与/loop 配对，以让 Claude 持续执行此操作。

#### 探索与品味

工作流程在探索解决方案的不同方法时可能会很有用，尤其是在涉及主观品味（如设计或命名）的情况下，这时会从评分标准中获益。

尝试让 Claude 探索一些解决方案，并为评审代理提供一个关于什么是好的解决方案的评分标准。当评审代理觉得自己满足了这些标准时，任务就完成了。解决方案也可以根据该评分标准通过竞赛进行排序或选择。

#### 评测

你可以通过在工作树中启动独立的代理来针对特定任务运行轻量级评估，然后启动比较代理，根据评分标准比较和评分特定输出。例如，根据特定标准评估并改进你创建的某项技能。

#### 模型与智能路由

创建一个针对你的任务调优的分类器智能体，该智能体可决定使用哪个模型。当你的任务涉及大量工具调用，且执行前的研究能够确定最适合该任务的模型时，这种智能体将非常有帮助。

例如，对于“解释身份验证模块（auth module）如何工作”这一任务，最佳模型取决于身份验证模块中有多少文件以及代码库的结构。分类器代理可以进行这项研究，然后根据任务的预期复杂度路由到 Sonnet 或 Opus。

#### 什么时候不应该使用动态工作流

工作流是新兴事物。虽然在许多用例中它能产生超出预期的成果，但并非每项任务都需要使用工作流，而且可能最终会消耗显著更多的 token。

最好以创造性的方式使用工作流，以你之前未曾尝试的方式来推动 Claude Code 的应用。对于常规编码任务，试着问问自己，它真的需要更多的计算资源吗？例如，大多数传统编码任务并不需要 5 人的评审小组。

### 构建动态工作流的技巧

提示工程

针对动态工作流，使用我们上面描述的特定技巧进行详细提示词，能产生最佳效果。

工作流不仅仅用于大型任务。你可以提示模型使用一个“快速工作流”。例如，你可以对一个假设进行快速的对抗性审查。

与/goal 和/loop 结合

当使用可重复的工作流（例如分类、研究或核实）时，将它们与/loop 结合以定期运行，并使用/goal 设置严格的完成要求。

Token 使用预算

你可以为动态工作流设置明确的 token 使用预算，以限制任务使用的 token 数量。你可以用预算提示它，例如：“使用 10k tokens”，这将设置上限。

保存和分享动态工作流

你可以在工作流菜单中按 “s” 键保存工作流。你可以将这些工作流提交到 \~/.claude/workflows 或者通过技能进行分发。

![Image](https://pbs.twimg.com/media/HJ0wWqbasAAcvgu?format=jpg&name=large)

通过技能分享它们时，请将您的 JavaScript 工作流文件放入技能和文件夹中，并在

[SKILL.MD](http://skill.md/) 中引用它们。为了提高灵活性，您可能希望提示 Claude 将技能中的工作流视为模板而不是需要逐字运行的脚本。

![Image](https://pbs.twimg.com/media/HJ0wbLFbIAAu2FH?format=jpg&name=large)

#### 《Claude Code 动态工作流》深度总结与解读

##### 一句话总结

**动态工作流让 Claude Code 不再只是“一个 AI 做完整任务”，而是能临时搭建一套“多代理协作系统”，把复杂任务拆给多个 Claude 分工、竞争、验证、汇总，从而提升长任务、复杂任务、研究任务和审查任务的可靠性。**

---

##### 1. 深度总结

###### 1.1 核心变化：从单代理到多代理编排

传统 Claude Code 更像是：

> 一个 Claude 在一个上下文里：理解任务 → 制定计划 → 执行 → 总结。

动态工作流则变成：

> Claude 先根据任务生成一个 JavaScript 工作流，再用这个工作流调度多个子代理完成任务。

这些子代理可以：

- 使用不同模型；
- 拥有独立上下文；
- 在独立工作树中运行；
- 并行执行；
- 互相验证；
- 最后由汇总代理整合结果。

本质上，Claude Code 从“工具使用者”升级为“临时组织架构设计者”。

---

###### 1.2 为什么需要动态工作流？

单个 Claude 长时间处理复杂任务时，容易出现三类问题：

| 问题 | 含义 |
|---|---|
| 代理型惰性 | 做到一半就以为完成了 |
| 自我偏好偏差 | 更容易相信自己之前的判断 |
| 目标漂移 | 多轮压缩后忘记原始要求和约束 |

动态工作流通过多个独立代理缓解这些问题：

- 生成代理负责提出方案；
- 验证代理负责挑错；
- 汇总代理负责整合；

它不是让一个 AI 更努力，而是让多个 AI 结构化协作。

- A 负责看日志；

- C 负责复现；
- D 负责提出假设；
- E 负责反驳这些假设；
- F 负责汇总最终结论。

这样做的好处是：

> 不把所有事情塞进一个脑子里，而是让不同角色专注做不同事。

###### 2.2 它解决的不是“能不能做”，而是“能不能稳定做好”

很多任务单个 Claude 也能做，但质量不稳定。

例如：

- 1000 条工单排序；

- 文章中每个技术声明核查；

- 信息多；
- 步骤多；
- 容易漏；
- 容易自我确认；
- 需要交叉验证。

动态工作流的价值就是把“复杂任务”变成“多个可控的小任务”。

> 如果任务需要拆分、并行、验证、比较、循环，就适合动态工作流。

- 大规模研究；
- 事实核查；
- 代码重构；
- 安全分析；
- 根因调查；
- 简历/工单/bug 排序；
- 创意生成与筛选；

不适合：

- 简单代码修改；
- 小 bug 修复；
- 普通问答；
- 明确且短小的任务；

> AI 生成能力很强，但自我纠错能力仍不可靠。

##### 4. 辩证思考

###### 4.1 优点：它显著提升复杂任务可靠性

动态工作流的最大价值是结构化。

它通过：

- 拆分降低复杂度；
- 并行提高效率；
- 独立上下文减少污染；
- 对抗验证减少幻觉；
- 循环机制避免半途而废。

对于复杂任务，它比单代理更接近真实团队协作。

---

###### 4.2 风险：复杂性本身也会制造新问题

动态工作流不是越多代理越好。

潜在问题包括：

- token 成本显著增加；
- 子代理之间结果可能冲突；
- 汇总阶段可能丢失细节；
- 评审代理也可能误判；
- 工作流设计不好会放大错误；
- 过度自动化可能带来安全风险。

尤其在处理不可信内容时，如果代理既能读取外部内容，又能执行高权限操作，就可能产生安全隐患。

所以需要权限隔离。

---

###### 4.3 关键不在“多代理”，而在“好流程”

多代理只是形式。

真正重要的是：

- 是否有清晰目标；
- 是否有明确评分标准；
- 是否有停止条件；
- 是否有反向验证；
- 是否控制资源预算；
- 是否区分生成、判断、执行权限。

如果没有这些，多代理只会变成“多个 AI 一起胡说”。

---

###### 4.4 人类角色不会消失，而是前移

动态工作流越强，人类越不需要亲自做每一步。

但人类仍要负责：

- 定义目标；
- 设定边界；
- 提供判断标准；
- 决定资源预算；
- 审核最终结果；
- 承担责任。

也就是说，人类从“执行者”变成“任务设计者”和“最终裁决者”。

---

##### 5. 最精炼结论

动态工作流的本质是：

> 让 Claude Code 为复杂任务临时生成一套多代理协作系统。

它适合：

- 大规模；
- 长周期；
- 多步骤；
- 需验证；
- 需比较；
- 需持续循环的任务。

它不适合：

- 简单；
- 短小；
- 明确；
- 低价值任务。

最重要的使用原则是：

> 简单任务用单代理，复杂任务用工作流；  
> 生成交给一个代理，验证交给另一个代理；  
> 不是追求更多 AI，而是设计更好的协作结构。

#### Claude Code 动态工作流：深度总结与解读

##### 一、深度总结

**动态工作流**是 Claude Code 的新能力：  
Claude 不再只是“执行任务”，而是可以**根据任务现场生成一套临时工具/流程/子代理体系**，用多个独立 Claude 协同完成复杂任务。

> 单个 Claude 在一个上下文里长期处理复杂任务时，容易懒惰、偏见、跑偏；动态工作流通过“拆分任务 + 多代理协作 + 对抗验证”提升可靠性。

##### 二、核心机制

动态工作流本质上是一个 **JavaScript 编排脚本**，可以：

- 创建多个子代理；
- 给不同代理分配不同目标；
- 决定每个代理使用什么模型；
- 决定代理是否在独立工作树中运行；
- 并行执行、循环执行、验证结果、合并输出；
- 中断后可恢复。

一句话：

> 它让 Claude Code 从“一个人干活”，变成“临时组建一个专家小队干活”。

##### 三、为什么需要动态工作流？

普通 Claude Code 在复杂任务中有三类典型失败：

###### 1. 代理式懒惰

任务还没彻底完成，就提前宣布完成。  
例如安全审查 50 项，只检查了 20 项就结束。

###### 2. 自我偏好偏差

Claude 容易相信自己的判断。  
尤其在“自评”“验证自己结论”时，容易放水。

###### 3. 目标漂移

任务越长，越容易忘记最初约束。  
尤其经过多轮总结后，细节会丢失。

动态工作流通过多个独立上下文的子代理，把这些问题结构性拆开。

##### 四、常见工作流模式

###### 1. 分类-执行

先判断任务类型，再选择不同处理路径。  
适合客服工单、bug 分类、模型路由。

###### 2. 扇出-合成

把大任务拆成很多小任务并行处理，最后统一汇总。  
适合研究、代码审查、大规模资料处理。

###### 3. 对抗性验证

一个代理产出，另一个代理专门挑错。  
适合事实核查、安全审查、技术文章验证。

###### 4. 生成-过滤

先大量生成方案，再筛选、去重、评分。  
适合命名、创意、产品方案。

###### 5. 锦标赛

多个代理用不同方法解决同一问题，再两两比较选优。  
适合主观判断、排序、设计方案选择。

###### 6. 循环直到完成

不预设次数，而是持续迭代，直到满足停止条件。  
适合调试、根因分析、日志排查。

##### 五、典型应用场景

###### 1. 代码迁移与重构

把迁移任务拆成模块、调用点、测试失败项；

###### 2. 深度研究

并行搜索资料、提取来源、验证主张，最后生成带引用报告。

###### 3. 深度核实

识别报告中的事实性声明，逐条查证来源。

###### 4. 大规模排序

例如简历筛选、bug 严重性排序、支持工单优先级排序。  
比起一次性评分，成对比较或锦标赛更可靠。

###### 5. 规则提炼与遵循

从过往会话中发现反复修正的问题，提炼成 CLAUDE.md 规则；  
也可以让验证代理逐条检查规则是否被遵守。

不同代理从日志、代码、数据、历史事件中提出假设；

###### 7. 分类与优先级处理

处理海量工单、bug、反馈，去重、归类、升级或尝试修复。

###### 8. 探索与品味任务

如命名、设计、方案选择。

###### 9. 模型智能路由

先用分类代理判断任务复杂度，再决定使用 Sonnet、Opus 等模型。

- 明确、短平快的问题；
- 不值得消耗大量 token 的任务；
- 不需要多人协作式判断的任务。

核心判断标准：

> 如果一个任务不需要拆分、验证、并行、长期迭代，就没必要上工作流。

##### 3. 为什么需要动态工作流：解决单上下文任务的局限

普通 Claude Code 在一个上下文窗口中同时规划和执行任务。对常规编码任务通常足够，但对复杂、长期、并行、对抗性任务容易出问题。

主要失败模式包括：

###### 3.1 代理式懒惰

Claude 可能在复杂任务未完成时提前宣称完成。

例子：

- 安全审查本应检查 **50 项**，但只完成 **20 项**就说完成了。

###### 3.2 自我偏好偏差

Claude 往往更相信自己已经生成的结论，尤其是在让它自我评分、自我验证时。

###### 3.3 目标漂移

多轮任务中，Claude 可能逐渐偏离最初目标。尤其经过总结压缩后，细节会丢失，例如：

- 边界条件
- “不要做某事”的限制
- 特殊验收要求

动态工作流通过拆分任务，让多个拥有独立上下文窗口和明确目标的子代理协作，降低这些问题。

---

##### 4. 动态工作流 vs 静态工作流

过去用户也可以通过 Claude Agent SDK 或 `claude -p` 创建静态工作流，协调多个 Claude Code 实例。

动态工作流的不同之处在于：

- 它不是预先固定流程，而是可由 Claude 根据当前任务实时生成。
- 它可以动态决定任务拆分方式、模型选择、验证策略和停止条件。
- 更适合任务结构不确定、需要探索或反复调整的场景。

---

##### 5. 常见工作流模式：Claude 如何组织多个代理

文章总结了几种常见动态工作流模式。

###### 5.1 分类-执行

先用分类器代理判断任务类型，再路由到不同代理或处理流程。

适合：

- 支持工单分类
- bug 类型判断
- 根据任务复杂度选择模型

也可以在最后用分类器判断输出是否合格。

---

###### 5.2 扇出-合成

把任务拆成许多小任务，并行交给多个代理处理，最后统一合成结果。

适合：

- 大量独立步骤
- 每个子任务需要干净上下文
- 避免不同子任务之间互相污染

例子：

- 分别检查多条事实声明
- 并行分析多份简历
- 并行修复多个测试失败点

---

###### 5.3 对抗性验证

生成一个结果后，再派另一个代理专门挑错、核验、质疑。

适合：

- 安全审查
- 技术文章核查
- 商业计划评估
- 规则遵循检查

---

###### 5.4 生成-过滤

先围绕一个主题生成大量候选，再根据评分标准筛选、去重、验证，只保留高质量结果。

适合：

- 命名
- 设计方案
- 创意头脑风暴
- 产品方案筛选

---

###### 5.5 锦标赛

让多个代理用不同方法解决同一任务，再由评审代理两两比较，最终选出获胜方案。

适合：

- 主观方案选择
- 命名评选
- 设计评审
- 多种实现路线比较

---

###### 5.6 循环直到完成

对于工作量未知的任务，不固定迭代次数，而是持续运行，直到满足停止条件。

停止条件可以是：

- 没有新发现
- 日志中不再出现错误
- 验证器认为标准已满足

适合：

- 调试
- 根因分析
- 大规模分类
- 持续队列处理

---

##### 6. 主要用例：动态工作流能做什么

###### 6.1 迁移和重构

动态工作流适合把大型迁移任务拆成许多可并行处理的步骤。

重要案例：

- **Bun 使用工作流从 Zig 重写为 Rust。**

典型做法：

1. 将任务拆为调用点、失败测试、模块等子任务。
2. 为每个修复创建一个子代理。
3. 让另一个代理进行对抗性审查。
4. 最后合并修复。

作者还建议：可要求代理不要使用资源密集型命令，以便最大化并行度，避免耗尽本机资源。

---

###### 6.2 深度研究

Claude Code 发布了 `/deep-research` 技能，内部采用动态工作流。

它会：

- 展开网络搜索
- 获取来源
- 对主张进行对抗性验证
- 综合生成带引用的报告

不仅限于网页搜索，也可用于：

- 根据 Slack 内容写状态报告
- 深入代码库研究某个功能如何工作

---

###### 6.3 深度核实

如果已有一份报告，需要检查其中每个事实性主张，可以用工作流完成：

1. 一个代理识别所有事实性主张。
2. 为每个主张派生子代理检查来源。
3. 再用核实代理检查来源质量。

适合防止文章、报告或技术文档中出现错误内容。

---

###### 6.4 排序任务

当需要按定性标准排序大量项目时，单个提示容易质量下降或超出上下文。

例子：

- 按 bug 严重程度排序支持工单。
- 对 **1000+ 行**内容排序时，直接一次性排序效果会变差。

可采用：

- 两两比较代理
- 锦标赛排序
- 并行分桶排序后合并

文章指出：比较判断通常比绝对评分更可靠。

---

###### 6.5 记忆与规则遵循

如果 Claude 经常忘记 `CLAUDE.md` 中的规则，可以创建验证工作流：

- 每条规则由一个验证代理检查。
- 再用怀疑型审查代理减少误报。

反向也可以：

- 挖掘最近会话和代码审查评论中反复出现的修正。
- 聚类这些修正。
- 对抗性验证每条候选规则是否真的能防止错误。
- 最终提炼回 `CLAUDE.md`。

---

###### 6.6 根本原因调查

调试或复盘时，最好让不同代理基于不同证据独立提出假设，避免单一上下文中的自我偏好偏差。

例子：

- 一个代理分析日志。
- 一个代理分析文件。
- 一个代理分析数据。
- 然后用验证者和反驳者审查每个假设。

这不仅适用于代码，也适用于：

- 销售：为什么三月份销售额下降？
- 数据工程：为什么数据流水线失败？
- 事故复盘：某问题的重复根因是什么？

---

###### 6.7 大规模分类与优先级排序

适合处理团队中大量积压内容，例如：

- 支持队列
- bug 报告
- 用户反馈
- 待处理任务

工作流可以：

- 对每个项目分类
- 与已跟踪内容去重
- 自动修复或升级给人工处理

安全上，作者特别提到“隔离”模式：

- 读取不可信公共内容的代理不应执行高权限操作。
- 高权限操作交给专门处理信息的代理。

还可以与 `/loop` 搭配，让 Claude 持续处理队列。

---

###### 6.8 探索与品味类任务

动态工作流也适合主观判断任务，例如设计、命名、方案探索。

做法：

1. 让 Claude 探索多个方案。
2. 给评审代理明确评分标准。
3. 当评审代理认为标准满足时结束。
4. 可通过锦标赛选择最优方案。

---

###### 6.9 评测

可以让多个独立代理在工作树中对某项任务运行轻量级评估，再由比较代理按标准打分。

适合：

- 评估某项 Claude 技能
- 比较多个输出
- 改进提示词或工作流

---

###### 6.10 模型与智能路由

可以创建分类器代理，根据任务复杂度选择模型。

例子：

- 对“解释身份验证模块如何工作”这一任务：
  - 如果 auth 模块文件少、结构简单，可路由到 Sonnet。
  - 如果文件多、结构复杂，可路由到 Opus。

这种方式适合工具调用多、需要先研究再决定模型的任务。

---

##### 7. 什么时候不该使用动态工作流

动态工作流虽然强大，但不是所有任务都需要。

不建议使用的情况：

- 常规、简单编码任务。
- 不需要并行、审查或复杂拆解的任务。
- 使用工作流带来的 token 成本高于收益时。

作者提醒：大多数传统编码任务并不需要“5 人评审小组”。

---

##### 8. 构建动态工作流的实用技巧

###### 8.1 提示要具体

使用动态工作流时，最好明确指定模式和要求，例如：

- 使用对抗性验证。
- 使用快速工作流。
- 使用扇出-合成。
- 设置停止条件。
- 明确评分标准。

工作流并不只适合大任务，也可以用于小任务，例如对某个假设做一次快速对抗性审查。

---

###### 8.2 与 `/goal` 和 `/loop` 结合

对于可重复任务，如分类、研究、核实：

- 用 `/loop` 定期运行。
- 用 `/goal` 设置严格完成条件。

---

###### 8.3 设置 token 预算

动态工作流可能消耗更多 token，因此可以明确设置预算。

例如提示：

> 使用 10k tokens。

这会为任务设置 token 上限。

---

###### 8.4 保存和分享工作流

可以在工作流菜单中按 `s` 保存工作流。

保存位置或分发方式：

- 提交到 `~/.claude/workflows`
- 通过技能分发

通过技能分享时：

- 将 JavaScript 工作流文件放入技能文件夹。
- 在 `SKILL.MD` 中引用。
- 建议让 Claude 将其视为“模板”，而不是必须逐字运行的脚本，以保持灵活性。

---

##### 9. 总结：动态工作流打开了 Claude Code 的新用法

动态工作流是一种扩展 Claude Code 的新方式，让它能针对复杂任务临时搭建多代理协作框架。它尤其适合研究、核查、排序、根因分析、重构、评测和主观方案选择等任务，但使用时要注意 token 成本，并判断任务是否真的需要额外计算资源。

文章介绍了 Claude Code 新发布的“动态工作流”能力：Claude 可以根据当前任务实时编写并执行适配任务的工作流，从而更好地处理复杂、并行、长期或需要验证的任务。动态工作流不仅适用于编码，也适合研究、审查、排序、根因分析、创意评选等多种场景，但会消耗更多 token，需要合理使用。

##### 1. 动态工作流是什么

动态工作流允许 Claude 在 Claude Code 中动态创建工具和流程，用来协调多个子代理完成任务。

- 它通过执行一个 JavaScript 文件来运行，文件中包含特殊函数，用于生成、调度和协调子代理。
- 工作流也支持常见 JavaScript 能力，如 `JSON`、`Math`、`Array`，方便处理数据。
- Claude 可以决定：
  - 每个子代理使用什么模型；
  - 子代理是否在独立工作树中运行；
  - 是否需要更高智能模型或更强隔离。
- 如果工作流被用户中断或终端退出，恢复会话后可以从中断处继续执行。
- 工作流可以保存、共享和复用。

---

##### 2. 为什么需要动态工作流

默认 Claude Code 在一个上下文窗口里同时做规划和执行，适合很多编码任务，但面对复杂任务时容易失败。

主要问题包括：

- **代理型惰性**：任务很复杂时，Claude 可能只完成一部分就声称完成。  
  例如安全审查中，本应检查 50 项，却只检查了 20 项。
- **自我偏好偏差**：Claude 容易偏向自己生成的结论，尤其是在让它评判自己结果时。
- **目标漂移**：长任务经过多轮总结和压缩后，原始目标、边界条件或“不做某事”的约束可能丢失。

动态工作流通过让多个独立 Claude 子代理分别处理独立目标，降低这些问题的影响。

---

##### 3. 示例任务：动态工作流能做什么

文章给出了一些典型提示，说明动态工作流的用途很广：

- 复现一个大约 **每 50 次运行失败 1 次** 的 flaky test，并不断提出和验证理论，直到找到可行解释。
- 查看最近 **50 个会话**，提取用户反复修正 Claude 的错误，并转化为 `CLAUDE.md` 规则。
- 分析过去 **6 个月 Slack #incidents**，找出没有被提交工单的重复根因。

- 将代码库中的 `User` 模型统一重命名为 `Account`。
- 检查博客草稿中的每个技术声明，并对照代码库验证，避免发布错误内容。

动态工作流的核心差异在于：

- 不需要提前写死流程；
- Claude 可以根据任务实时生成合适的工作流；
- 可以动态选择模型、代理数量、验证方式和执行策略；
- 更适合未知规模、需要探索或需要对抗性验证的任务。

##### 5. 常见工作流模式

###### 5.1 分类-行动

先用分类器代理判断任务类型，再路由到不同代理或行为。

- 适合支持工单、bug 报告、任务分流等场景。
- 也可以在最后使用分类器判断输出质量或归类结果。

###### 5.2 扇出与合成

把大任务拆成很多小任务，分别交给多个代理处理，最后合成结果。

- 适合大量小步骤任务。
- 每个代理有独立上下文，减少相互干扰。
- 合成步骤会等待所有子代理完成，再整合结构化输出。

###### 5.3 对抗性验证

一个代理生成结果，另一个独立代理专门挑错和验证。

- 适合代码审查、安全分析、事实核查、报告验证。
- 可以减少 Claude 偏向自己结论的问题。

###### 5.4 生成-筛选

先生成大量想法，再按标准筛选、去重和验证，只保留最佳结果。

- 适合命名、设计方案、创意探索等任务。

###### 5.5 锦标赛

多个代理用不同方法解决同一任务，再通过评判代理进行两两比较，最终选出优胜者。

- 适合主观判断、排序、方案选择。
- 比绝对打分更可靠。

###### 5.6 循环直到完成

对于工作量未知的任务，不预设固定轮次，而是持续运行，直到满足停止条件。

- 停止条件可以是：
  - 没有新发现；
  - 日志中不再出现错误；
  - 所有验证通过。

###### 6.9 轻量评估

可以通过动态工作流对某项技能或输出做轻量级评估。

例如：

- 在独立工作树中启动多个代理完成任务；
- 再启动比较代理；
- 根据评分标准给不同输出打分和改进。

---

###### 6.10 模型与智能路由

可以创建分类器代理，根据任务复杂度决定使用哪个模型。

例如，用户问“解释 auth 模块如何工作”时，分类器可以先研究：

- auth 模块有多少文件；
- 代码库结构有多复杂；
- 任务是否需要深入推理。

然后再决定使用 Sonnet 或 Opus。

---

##### 7. 什么时候不该使用动态工作流

动态工作流并非适合所有任务。

作者提醒：

- 工作流可能显著增加 token 消耗；
- 常规编码任务通常不需要复杂工作流；
- 不要为了简单任务安排过多代理或评审。

例如，大多数普通编码任务并不需要一个由 **5 名评审人员** 组成的评审小组。

更适合使用动态工作流的场景是：

- 长时间运行；
- 大规模并行；
- 需要强验证；
- 需要独立假设；
- 任务结构复杂或目标容易漂移。

- 扇出与合成；

- 锦标赛；
- 循环直到完成；
- 快速工作流。

工作流不只适合大型任务，也可以用于小任务。  
例如，可以要求 Claude 用“快速工作流”对一个假设做简短的对抗性审查。

---

###### 8.2 与 `/goal` 和 `/loop` 结合

对于重复性任务，如分类、研究、核实，可以：

- 用 `/goal` 设置硬性完成要求；
- 用 `/loop` 定期或持续运行工作流。

###### 8.3 设置 token 预算

可以给动态工作流设置明确 token 上限。

例如提示：

> 使用 10k 个 token。

这样可以限制任务最多消耗约 **10,000 token**。

###### 8.4 保存和共享工作流

工作流可以保存和分发：

- 在工作流菜单中按 `s` 保存；
- 保存到 `~/.claude/workflows`；
- 或通过技能进行共享。

- 最好提示 Claude 把工作流当作模板，而不是必须逐字执行的脚本。

动态工作流是扩展 Claude Code 的新方式，它让 Claude 能按任务实时设计流程、调度子代理、并行处理、互相验证和合成结果。它特别适合复杂研究、大规模分类、重构迁移、根因分析、事实核查和创意评选，但由于会消耗更多 token，使用前应判断任务是否真的需要额外计算资源。

##### 2. 高价值信息深挖

###### 2.1 动态工作流解决的不是“效率问题”，而是“复杂任务可靠性问题”

文章中提到单个 Claude 在复杂任务中容易出现三类失败：

| 失败模式 | 含义 | 商业/产品类比 |
|---|---|---|
| 代理式懒惰 | 做了一部分就宣布完成 | 员工只完成 40% 工作却写了漂亮汇报 |
| 自我偏好偏差 | 偏爱自己的方案、结论和判断 | 方案制定者自己做评审，天然护短 |
| 目标漂移 | 多轮执行后忘记原始约束 | 项目做着做着偏离最初战略目标 |

动态工作流的关键价值在于：

> 把复杂任务拆成多个独立上下文，让不同代理承担不同角色，从结构上降低偏差。

这和企业管理中的“职责分离”非常像：

- 执行者不做最终评审；
- 研究者不直接下结论；
- 生成方案的人不负责唯一裁决；
- 审核者需要基于明确标准进行对抗性验证。

这说明 AI 工作流不是简单的自动化脚本，而更像一种 **机器组织设计**。

---

###### 2.2 动态工作流的本质：让 AI 临时生成“任务专用操作系统”

Claude Code 的动态工作流可以执行 JavaScript 文件，并通过特殊函数协调多个子代理。

更重要的是，它可以动态决定：

- 创建几个子代理；
- 每个代理的目标是什么；
- 每个代理使用什么模型；
- 是否使用独立工作树；
- 哪些任务并行；
- 什么时候停止；
- 如何合成结果。

因此，它的本质不是“多开几个 Claude”，而是：

> AI 为每个任务实时生成一套专属的操作系统。

例如：

- 调试问题时，它生成“假设生成 — 证据验证 — 对抗反驳 — 修复尝试”的系统；
- 做研究时，它生成“资料搜索 — 来源提取 — 事实核验 — 报告合成”的系统；
- 做招聘筛选时，它生成“简历评分 — 分桶排序 — 前十复核 — 面试问题生成”的系统；
- 做商业计划评审时，它生成“投资人视角 — 客户视角 — 竞争对手视角 — 风险评估”的系统。

这对于产品设计很重要：

> 好的 AI 产品不该只问用户“你想让我做什么”，还应该自动判断“这个任务需要什么组织结构”。

###### 2.3 关键模式：动态工作流的几个底层“组织模板”

文章中提到的模式非常值得抽象成通用认知模型。

###### 1. 分类-执行

先判断任务类型，再选择执行路径。

适用于：

- 客服工单分流；
- Bug 严重性判断；
- 销售线索评级；
- 内容审核；
- 用户反馈归类。

产品启发：

> 很多 AI 系统不该直接回答，而应先分类，再路由。

---

###### 2. 扇出-合成

把任务拆成多个子任务并行完成，最后合成结果。

适用于：

- 深度研究；
- 大规模代码审查；
- 市场调研；
- 竞品分析；
- 文档事实核验。

商业启发：

> 当任务天然可以拆分时，并行代理比单个长上下文更可靠。

---

###### 3. 对抗性验证

一个代理生成，另一个代理专门质疑。

适用于：

- 安全审查；
- 投资决策；
- PRD 评审；
- 技术方案评审；
- 内容发布前核查。

关键价值：

> AI 最容易犯错的地方，不是不会生成，而是不会怀疑自己。

---

###### 4. 生成-过滤

先大量生成，再通过标准筛选。

适用于：

- 命名；
- 创意；
- 产品功能点；
- 增长实验；
- 营销文案；
- 商业模式备选方案。

产品启发：

> AI 创意任务不要追求“一次生成最佳答案”，而要设计“生成池 + 评审器”。

---

###### 5. 锦标赛

多个代理用不同方法解决同一问题，再两两比较选优。

适用于：

- 复杂算法实现；
- 品牌命名；
- 策略方案选择；
- 提案比选；
- 设计方向评估。

关键点：

> 比较判断往往比绝对评分更可靠。

这在商业判断里同样成立：  
人和 AI 都更擅长回答“哪个更好”，而不是精确回答“这个是 8.3 分还是 8.7 分”。

---

###### 6. 循环直到完成

不是固定迭代次数，而是直到满足停止条件。

适用于：

- Debug；
- 数据清洗；
- 根因调查；
- 安全扫描；
- 长期监控；
- 工单处理。

产品启发：

> AI Agent 的完成标准不应只是“跑完一次”，而应是“满足可验证的终止条件”。

##### 4. 反方与张力：动态工作流不是万能解

###### 4.1 Token 成本与收益的张力

动态工作流会显著增加 token 使用量。

因此不是所有任务都值得使用它。

适合使用的任务通常具有以下特征：

- 任务复杂；
- 需要并行探索；
- 需要验证；
- 容易出现偏差；
- 结果价值高；
- 人工成本高；
- 错误代价高。

不适合使用的任务：

- 简单代码修改；
- 明确的小问题；
- 低风险内容生成；
- 已有成熟脚本能解决的问题；
- 不需要多角色评审的普通任务。

一句话判断：

> 如果任务失败的代价低，就不一定需要工作流；  
> 如果任务错误但看起来正确的代价高，就很适合工作流。

---

###### 4.2 多代理不必然更聪明，也可能制造复杂性

动态工作流容易让人产生一种错觉：

> 代理越多，结果越好。

但实际未必。

可能出现的问题包括：

- 多个代理重复劳动；
- 评审标准不清导致输出混乱；
- 合成代理丢失重要细节；
- 过度验证导致成本失控；
- 子代理各自结论冲突；
- 工作流设计本身成为新的错误源。

因此关键不是“多代理”，而是：

> 是否有清晰的角色、边界、标准和停止条件。

---

###### 4.3 对抗性验证也有局限

让一个 AI 质疑另一个 AI，可以减少自我偏好偏差，但不能彻底消除错误。

尤其在以下场景中需要谨慎：

- 法律判断；
- 医疗建议；
- 投资决策；
- 安全漏洞确认；
- 高风险生产环境操作；
- 涉及真实用户权益的自动决策。

更可靠的设计是：

```markdown
AI 生成 → AI 反驳 → AI 核验 → 人类审批 → 小范围执行 → 监控反馈
```

---

###### 4.4 工作流复用与动态生成之间存在张力

静态工作流的优势：

- 可控；
- 可审计；
- 可测试；
- 适合稳定流程。

动态工作流的优势：

- 灵活；
- 适应任务；
- 适合未知问题；
- 适合探索性任务。

产品设计上不应二选一，而应组合：

```markdown
高频稳定任务 → 静态工作流
低频复杂任务 → 动态工作流
高价值不确定任务 → 动态生成 + 人类审核
```

- 安全审查；
- 根因分析；
- 商业计划评审；
- 大规模候选人筛选；
- 事实核验；
- 架构迁移；
- 数据异常调查。

不适合动态工作流的任务：

```markdown
低复杂度 + 低风险 + 结果容易检查
```

例如：

- 改一个按钮文案；
- 写一个简单 SQL；
- 生成一段普通营销文案；
- 查询一个明确事实。

---

##### 6. 最值得带走的结论

###### 结论一：AI Agent 的下一步是“组织化”

单个 Agent 像一个聪明个体。  
动态工作流像一个临时组建的项目团队。

未来高价值 AI 系统会越来越像：

```markdown
任务经理 + 专家团队 + 审核机制 + 记忆系统 + 自动复盘
```

---

###### 结论二：验证能力比生成能力更稀缺

很多 AI 系统失败，不是因为不会生成，而是因为：

- 不知道自己错了；
- 不知道哪里需要查证；
- 不知道什么时候该停止；
- 不知道如何接受反驳。

所以工作流里的“对抗性验证”“事实核验”“评审代理”非常关键。

---

###### 结论三：最有价值的 AI 产品会沉淀工作流，而不是只沉淀 Prompt

Prompt 是一次性的指令。  
Workflow 是可复用的组织能力。

未来团队的 AI 资产可能不只是：

```markdown
Prompt Library
```

而是：

```markdown
Workflow Library
Agent Role Library
Evaluation Criteria Library
Decision Playbook
```

---

###### 结论四：动态工作流适合处理“人类组织中本来就需要多人协作”的任务

如果一个任务在人类团队里本来就需要：

- 研究员；
- 执行者；
- 审核者；
- 反方；
- 决策者；
- 项目经理；

那么它大概率适合动态工作流。

---

##### 7. 一句话总结

> Claude Code 的动态工作流不是简单地让 AI 更会写代码，而是让 AI 学会为复杂任务临时搭建一套组织结构。  
> 对产品和商业系统来说，真正值得迁移的是：任务拆解、角色分工、对抗验证、循环完成和经验沉淀。

## 深度解读（1）

### 2026-09-18 00:57:23

#### 动态工作流的价值，不是“更多智能体”，而是把思考过程变成可执行结构

这篇文章最值得关注的，并不是 Claude Code 能同时调用多个子代理，而是它能**针对当前任务，临时编写一套执行框架**：决定如何拆分工作、使用什么模型、是否隔离代码分支、怎样验证结果，以及满足什么条件才停止。相比预先写死的自动化脚本，这更像是模型根据问题现场搭建了一支临时团队和一套协作制度。

标题所说“适用于所有任务”略显夸张。文章真正证明的是：动态工作流适合那些**任务规模大、形状事先不确定，且错误代价较高**的场景，例如偶发故障复现、技术事实核查、事故根因调查、批量排序和大型重构。普通编码任务通常并不值得为此付出数倍 token 和协调成本。

##### 单一上下文的问题，本质上是执行与监督混在了一起

文章列出的三种失败很有解释力：任务过长时，模型会提前宣布完成；会偏爱自己提出的答案；经过多轮压缩后，还可能遗失最初的边界条件。这并不只是“模型不够聪明”，而是让同一个上下文同时承担计划、执行、记忆和验收，本身就缺少制衡。

动态工作流提供的各种模式，实际上分别对应不同的控制机制：

- “扇出—合成”把大量子任务放入干净上下文，降低相互干扰；
- “生成—验证”把创作者与评审者分开，减少自我认可；
- “循环直到完成”用明确停止条件替代模型凭感觉收工；
- “锦标赛”和两两比较，把困难的绝对评分转化为相对判断；
- 权限隔离则让读取外部不可信内容的代理无法直接执行高风险操作。

这说明，多代理真正的收益不一定来自“集体智慧”，而是来自**职责分离、状态隔离和可检查的流程约束**。它更接近软件工程中的测试、权限和流水线，而不是模拟一场热闹的会议。

但这种制衡也有边界。多个代理可能共享同一种模型偏差，评审代理也未必比生成代理更接近事实。真正可靠的验证仍要落到独立证据上：测试结果、原始来源、可复现日志或人工抽查。增加代理数量只能提高覆盖率，不能自动制造真相。

##### 模糊知识工作开始具备“可编排性”

文章中最有迁移价值的例子，是从历史会话和代码审查里提取反复出现的纠错，再把经过验证的规则写回 `CLAUDE.md`。这形成了一个闭环：**执行产生纠错，纠错沉淀为规则，规则再进入后续执行与验收。**类似方法也适用于客服队列、事故复盘、销售异常分析和内容事实核查。

由此看，动态工作流的长期机会不只是一个“多代理按钮”，而是一层知识工作的运行系统：目标、预算、权限、证据、停止条件和人工升级机制都可被显式管理。对产品设计而言，关键界面可能不是聊天框，而是让用户看见任务如何拆分、哪一步缺少证据、成本花在哪里，以及何时需要人工接管。

一个合理的演进路径是：先用动态工作流探索未知任务，观察哪些步骤稳定有效；再把高频流程固化为静态工作流或产品功能。**动态工作流适合发现流程，静态工作流适合规模化流程。**是否值得采用，最终不该看代理数量，而应比较它相对单代理或人工流程，是否以可接受成本提高了完成率、可追溯性和错误发现率。
