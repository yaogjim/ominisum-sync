## 分析要点

- **核心高价值点**：将Agent使用从“写prompt”提升为“设计可验证、可记忆、可分工的执行循环”。
- **留存建议**：长期保留（文章提炼了AI Agent循环工程的关键组件和风险边界，可作为设计自动化开发工作流的参考框架。）

**知识要点**

- Loop Engineering强调构建能自动发现任务、执行、检查、记账并决定下一步的系统，而不是人工逐轮prompt。
- Automations、Worktrees、Skills、Connectors、Sub-agents和Memory构成Agent循环的核心基础设施。
- 写代码的Agent不应自行判断任务完成，需要独立检查者或验证机制。
- Memory应落在磁盘、repo或任务系统中，而不是仅存在于上下文窗口里。
- 循环越自动化，越需要人类工程师保持验证能力、代码理解和独立判断。

**行动项**

- 为自己的AI开发流程设计一个最小Loop：任务输入、执行、验证、记录和下一步决策。
- 在项目中尝试使用git worktree隔离多个Agent并行修改。
- 为项目补充SKILL.md或类似知识文件，减少Agent重复推理项目背景。
- 建立独立验证环节，避免让生成代码的Agent自己判定完成。
- 将Agent执行历史和下一步计划写入持久化文件或任务系统。

## 解读（1）

### 2026-06-09 10:24:35

#### 深度总结

这篇内容讲的是：**AI 编程正在从“写 prompt”进入“搭循环系统”阶段。**

过去，人负责一轮轮提示 AI：  
> 写代码 → 看结果 → 再提示 → 再修改。

现在，Claude Code / Codex 这类工具开始支持一种新模式：  
> 人不再手动 prompt，而是设计一个自动循环，让 AI 自己发现任务、执行、检查、记录、推进下一步。

Addy Osmani 把它叫做 **Loop Engineering，循环工程**。

核心观点一句话：

> 未来厉害的不是会写 prompt 的人，而是会搭 AI 工作循环的人。

---

#### 什么是 Loop Engineering？

简单说，就是把 AI 变成一个“自动干活系统”。

它不只是回答问题，而是可以：

1. 定时启动；
2. 找到要做的任务；
3. 分配给不同 agent；
4. 写代码；
5. 自测或交给另一个 agent 检查；
6. 记录进度；
7. 决定下一步；
8. 必要时开 PR、关联 ticket、通知团队。

人从“操作员”变成“系统设计者”。

---

#### 循环系统的 6 个关键零件

##### 1. Automations：心跳

让 agent 定时跑起来。

例如：

- 每天检查 issue；
- CI 挂了自动修；
- PR 有评论自动处理；
- 任务没完成就继续跑。

它解决的是：**AI 不再需要人每次手动叫醒。**

---

##### 2. Worktrees：隔离工作区

用 `git worktree` 给不同 agent 分配独立代码副本。

好处是：

- 多个 agent 可以并行工作；
- 彼此不会互相覆盖文件；
- 出错也更容易回滚。

它解决的是：**多个 AI 同时干活时互相踩踏的问题。**

---

##### 3. Skills：项目知识

通过 `SKILL.md` 这类文件，把项目规则、架构、约定写清楚。

否则 agent 每次都像失忆一样重新猜：

- 项目怎么启动？
- 代码风格是什么？
- 哪些目录不能动？
- 测试怎么跑？

它解决的是：**AI 每轮都从零理解项目的问题。**

---

##### 4. Connectors：外部连接

基于 MCP 等机制，让 agent 能连接：

- GitHub / GitLab；
- Linear / Jira；
- 数据库；
- Slack；
- Staging API；
- CI 系统。

这会带来巨大差异：

普通 AI 只能说：  
> 这是修复方案。

接入系统后的 AI 可以：  
> 我已修复、开 PR、关联 ticket、CI 通过，并通知了频道。

它解决的是：**AI 从“建议者”变成“执行者”。**

---

##### 5. Sub-agents：分工与互审

写代码的 agent 和检查代码的 agent 要分开。

因为：

> 写代码的模型给自己打分，往往会手软。

所以需要：

- 一个 agent 写；
- 一个 agent 审；
- 甚至另一个小模型判断是否达成目标。

它解决的是：**自我验证不可靠的问题。**

---

##### 6. Memory：外部记忆

这是最不起眼但最关键的一点。

模型本身会忘。  
所以记忆不能只放在上下文里，而要落到外部：

- Markdown 文件；
- issue board；
- Linear ticket；
- repo 文档；
- changelog。

核心句：

> Agent 会忘，repo 不会。

它解决的是：**AI 每次运行都断片的问题。**

---

#### 深入浅出地理解

可以把 Loop Engineering 想成：

##### 以前：你在指挥一个实习生

你每次都要说：

> 你去看这个文件。  
> 改这里。  
> 跑测试。  
> 报错了再修。  
> 现在提交 PR。

你很累，因为每一步都要盯。

---

##### 现在：你在设计一条生产线

你定义好：

- 什么时候启动；
- 从哪里拿任务；
- 谁负责写代码；
- 谁负责检查；
- 怎么判断完成；
- 怎么记录进度；
- 出错怎么办；
- 成功后通知谁。

然后系统自己转。

这就是从 **prompting** 到 **loop engineering** 的变化。

---

#### 最重要的警告

文章最后强调：循环系统很强，但它没有替你解决三个核心问题。

##### 1. 验证仍然是你的责任

AI 说 done，不代表真的 done。

尤其是无人看管的循环，可能只是：

> 自动化地犯错。

所以最终还是需要人建立可靠验证：

- 测试；
- 代码审查；
- 指标监控；
- 回滚机制；
- 安全边界。

---

##### 2. 你的理解可能会腐烂

AI 写得越快，你越容易失去对代码的掌控。

最后会出现一种尴尬：

> 项目是我的，但里面很多代码我看不懂。

短期效率变高，长期可能变成技术债。

---

##### 3. 你可能失去判断力

最危险的是：系统太顺了，人开始照单全收。

AI 开 PR，你合并；  
AI 说修好了，你相信；  
AI 说测试通过，你放心。

久而久之，工程师从决策者变成审批机器。

---

#### 辩证思考

##### Loop Engineering 是进步

它确实代表软件开发的新阶段。

因为它把 AI 从“聊天工具”推进到“工作流执行系统”。

真正的价值不再是单次回答，而是持续完成任务：

- 自动修 bug；
- 自动补测试；
- 自动更新文档；
- 自动处理 PR 评论；
- 自动维护项目状态。

这会大幅提高工程效率。

---

##### 但它不是工程师的替代品

循环能执行，但不天然理解业务目标。  
循环能产出代码，但不天然保证正确。  
循环能自检，但不天然具备责任感。

所以人的角色没有消失，只是变化了：

> 从写每一行代码，变成设计系统、设定边界、定义标准、承担判断。

---

##### 未来更重要的能力

不是“会不会问 AI”，而是：

1. 能不能把目标拆成可验证任务；
2. 能不能设计可靠循环；
3. 能不能让 agent 有记忆、有工具、有边界；
4. 能不能识别 AI 产出的错误；
5. 能不能保持对系统的理解。

也就是说，工程师会更像：

> 架构师 + 流程设计师 + 审计员 + 最终责任人。

---

#### 一句话结论

**不要只学怎么 prompt AI，要学怎么搭 AI 循环。**

但更重要的是：

> Build the loop, stay the engineer.  
> 循环可以自动转，但工程判断不能外包。

## 结构化（1）

### 2026-06-11 09:31:21

##### 主旨概括

文章认为，AI 编程正在从“人不断写 prompt 指挥 agent”转向“人设计自动循环系统，让 agent 自己找任务、执行、检查并推进下一步”。这种方式被称为 **Loop Engineering（循环工程）**，但作者提醒：循环可以自动化很多流程，工程师仍必须负责验证、理解和判断。

---

##### 1. 从 Prompt 到 Loop：人的角色变了

Claude Code 负责人表示，他现在已经不再一轮轮地 prompt Claude，而是让一个“循环”去 prompt Claude、判断下一步该做什么。

Addy Osmani 将这种模式称为 **Loop Engineering**：

- 过去：人不断输入 prompt，指导 AI 做每一步。
- 现在：人搭建一个系统，让它自动：
  - 找任务
  - 分发任务
  - 检查结果
  - 记录进度
  - 决定下一步
  - 调用 agent 执行

换句话说，人的工作从“亲自指挥 AI”变成了“设计一个会自动指挥 AI 的循环系统”。

---

##### 2. 循环工程的五个核心零件

作者认为，Claude Code 和 Codex 现在已经具备了循环工程所需的五个关键组件。

###### 2.1 Automations：循环的“心跳”

Automations 负责让系统定时自动运行，并处理任务流转。

关键能力包括：

- 定时启动任务
- 自动发现问题
- 自动分流结果
- 有结果就进入 Triage 收件箱
- 没结果就归档

文中提到两个例子：

- `/loop`：按周期反复运行。
- `/goal`：一直运行到某个可验证条件成立才停止。

重要的是，每一轮完成后，会由一个独立的小模型判断任务是否真的完成。写代码的 agent 不能给自己打分，因为它可能“手软”。

---

###### 2.2 Worktrees：避免多个 agent 互相踩代码

通过 `git worktree`，可以给每个并行运行的 agent 分配一份独立的代码 checkout。

这样做的好处是：

- 每个 agent 在自己的工作区修改代码。
- 不会多个 agent 同时改同一份文件。
- 从机制上减少冲突和混乱。

---

###### 2.3 Skills：让 agent 不再每次从零理解项目

`SKILL.md` 用来保存项目知识，相当于把项目背景、规则、约定写在外部文件里。

它的作用是：

- 让 agent 每次运行时能快速理解项目。
- 避免像“金鱼”一样每轮都重新猜项目结构。
- 降低重复推理成本。

如果没有 Skills，循环每一轮都可能从零开始重新理解项目。

---

###### 2.4 Connectors：让循环连接真实工作系统

Connectors 建在 MCP 之上，让循环能够接入外部系统，例如：

- issue tracker
- 数据库
- staging API
- Slack

这会带来很大差别：

- 没有 Connectors：agent 只能说“这是修复方案”。
- 有 Connectors：agent 可以自己开 PR、关联 ticket、跑 CI，CI 绿了之后再通知 Slack 频道。

也就是说，agent 不只是给建议，而是能进入真实研发流程。

---

###### 2.5 Sub-agents：写代码和检查代码要分开

作者强调，写代码的 agent 和检查代码的 agent 应该分离。

原因很简单：

- 写代码的模型给自己打分往往不够严格。
- 独立检查可以减少“自我确认”的问题。
- 更接近真实工程里的开发与 code review 分工。

---

##### 3. 第六个关键组件：Memory

除了五个核心零件，作者认为还有一个不起眼但极其重要的东西：**memory（记忆）**。

这个记忆可以是：

- 一个 markdown 文件
- 一块 Linear board
- 其他持久化记录系统

它需要记录：

- 已经做过什么
- 当前进展如何
- 下一步要做什么

原因是：模型每次运行后都会忘记上一次的状态，所以记忆不能只放在 context 里，而要落到磁盘或外部系统中。

作者用一句话总结：

> agent 会忘，repo 不会。

---

##### 4. 循环工程无法替你解决的三个问题

虽然循环可以让 agent 更自动化、更高效，但作者提醒，有三件事仍然必须由工程师负责。

###### 4.1 验证仍然是你的责任

没人盯着的循环，也可能在没人盯着的时候犯错。

“done”只是 agent 的声明，不代表任务真的完成。

所以工程师仍然要负责：

- 验证结果
- 检查代码质量
- 确认业务逻辑正确
- 确认没有隐藏问题

---

###### 4.2 你对代码的理解可能会变差

循环越快地交付那些你没有亲手写的代码，你和代码之间的距离就越远。

这会带来一个问题：

- 项目跑得更快了。
- 但你可能越来越看不懂自己的项目。

热门回复里也有人提到类似感受：

> 有几个文件现在完全是 agent 写的，我改都不敢随便改，怕动一行崩一片。速度是快了，但“我的项目里有些地方我自己看不懂”这感觉挺别扭的。

---

###### 4.3 最舒服的姿势往往最危险

当循环自己顺畅运转后，人很容易变成“照单全收”。

风险在于：

- 不再主动判断
- 不再保持技术观点
- 不再质疑 agent 的输出
- 逐渐把工程责任交给系统

但作者认为，工程师不能放弃自己的位置。

---

##### 5. 最后的核心提醒

作者用一句话总结循环工程的正确态度：

> Build the loop, stay the engineer.

也就是说：

- 循环可以由你来搭建；
- 自动化可以帮你推进很多工作；
- 但工程判断、验证责任和系统理解，仍然必须由你承担。

## 深度解读（1）

### 2026-09-18 00:53:54

#### 从 Prompt 到 Loop：AI 编程的瓶颈正在转向验收与控制

这段内容最值得保留的，不是“Claude Code 负责人已经不写 prompt”这个吸睛说法，而是它指出了一次工作重心迁移：**人不再逐轮指导模型，而是设计一个能够持续发现任务、执行、检查并决定下一步的闭环。**

这与其说是提示词技巧升级，不如说是把 AI 从交互工具改造成生产系统。

##### 真正的进步，是把隐含协调变成显式机制

文中列出的组件，解决的是 agent 长时间运行时几个非常具体的问题：

- Automations 提供触发、停止条件和任务分流；
- Worktrees 隔离并行修改，避免多个 agent 相互覆盖；
- Skills 把项目约束和知识外置，减少每轮重新推断；
- Connectors 让模型能操作 issue、CI、数据库和通知系统；
- Sub-agents 分离执行与检查；
- Memory 在对话之外保存进度与决策。

其中最关键的其实是后两项：**执行者不能独占评价权，状态也不能只存在于上下文里。**模型的上下文再长，仍不是可靠的项目账本；另一个模型负责验收，也只是降低“自说自话”的概率，并不天然构成独立证明。真正可靠的循环，需要把任务状态、操作记录、验收证据和失败原因留在 repo、测试系统或工单中。

因此，“loop engineering”的核心并非让 agent 多跑几轮，而是把目标、状态、权限、反馈和终止条件工程化。这个认识也能迁移到客服、运营、研究等场景：只要 AI 开始跨步骤行动，产品设计重点就会从对话体验转向工作流控制。

##### 生成成本下降，理解债务开始累积

循环可以加快交付，却不会自动提高正确性。“CI 绿了”只能证明预设测试通过，无法证明需求理解正确、边界完整或架构仍然合理。若测试和实现都由相近模型生成，二者还可能共享同一种误解。

更隐蔽的问题是**理解债务**。传统技术债通常表现为代码难改；理解债务则是系统仍在高速变化，但团队已经说不清某些模块为什么这样设计。热门回复里“有些文件完全由 agent 写，我不敢随便改”，正是这种风险的早期信号。短期吞吐量上升，可能以未来定位故障、重构和承担责任的能力为代价。

所以人的角色并没有消失，而是上移了：定义可证伪的完成条件，决定哪些操作可以自动执行，抽查关键决策，并维护系统级理解。高风险改动不能只看 agent 的 done，而应要求可追溯证据，例如测试覆盖、行为差异、回滚方案和人工审查。

##### 下一阶段的稀缺能力，不是更会“催模型”

这篇帖子提供的是一套有解释力的实践框架，而不是已经被严格验证的行业定律。但它揭示的方向值得重视：**当代码生成越来越便宜，稀缺资源会变成高质量目标、可信验收、运行可观测性，以及人对系统的持续理解。**

对产品而言，机会也未必是再做一个 agent，而可能是补齐循环的控制面：跨工具状态管理、权限边界、证据化验收、异常升级和理解债务监测。需要验证的核心假设不是“用户是否想要更自动”，而是他们是否愿意把关键流程交给系统，以及什么证据足以让他们放心放手。
