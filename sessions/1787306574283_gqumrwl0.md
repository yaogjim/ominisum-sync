## 分析要点

- **核心高价值点**：筛选AI创业问题时，不只判断模型当前能否完成任务，更应诊断其失败是否可由私有数据、领域知识、工具、验证器和业务流程构成的系统壁垒补足。
- **留存建议**：精读并保留其中的选题判断、规格设计与反馈闭环框架（与AI Agent开发和创业选题高度相关，包含可复用的任务筛选、系统编排、可执行规格和验证闭环框架。）

**知识要点**

- 复杂Agent的能力不仅取决于模型，还取决于上下文、工具、技能、评估器和编排机制。
- 长时间运行的Agent需要形成“目标—执行—观察—验证—修正—再执行”的稳定闭环，而非简单增加Agent数量。
- 可执行规格通过既有行为、测试和输入输出约束，为Agent实现与验证软件提供机器可检查的目标。

**行动项**

- 用当前最强通用模型测试候选业务任务，记录成功率，并优先分析接近1%的重要任务为何失败。
- 为Agent流程补齐明确目标、工具权限、验证器、失败恢复机制和持续反馈闭环。
- 将需求改写为包含输入输出、验收标准、测试用例和行为约束的可执行规格。

**AlexZ**

### Jeff Dean 的「1% 法则」：AI 时代，真正稀缺的已经不是写代码

最近看了 Jeff Dean 在 YC Startup School 2026 的一场对谈。

Jeff Dean 讲了很多东西：TPU、推理芯片、Context Engineering、长时间运行的 Agent、多 Agent、创业机会，以及 AI 时代工程师真正应该培养的能力。

如果把这些内容拆开来看，好像都是不同的话题。

但把它们连接起来，我看到的其实是同一件事：

当 AI 开始接管“执行”，工程的重心正在不断向上移动。

过去我们的核心能力是：

> 我能不能把这件事做出来？

现在正在变成：

> 我能不能定义一个值得解决的问题，并构造一个系统，让 AI 自己把它做出来？

这可能是 AI Coding 发展到今天以后，一个非常重要的变化。

#### 一、Jeff Dean 的「1% 法则」

这篇访谈里，我认为最值得创业者注意的，是 Jeff Dean 提出的一个非常有意思的判断标准。

如果你正在寻找一个 AI 创业方向，可以先拿最强的通用模型去测试。

如果模型已经能够完成这个任务 20%，这可能反而不是一个特别好的信号。

因为这意味着某种能力已经开始出现在通用模型里。

随着模型继续扩大、数据继续增加、训练方法继续改进，也许六个月或者一年以后，模型自己就把剩下的问题吃掉了。

Jeff Dean 的建议恰恰相反：

去寻找那些今天最好的通用模型成功率只有 0%～1% 的问题。

我觉得这就是所谓的：

### 1% 法则

它不是说“做到 1% 就够了”。

而是在告诉创业者：

不要站在基础模型能力扩张的正前方。

如果 GPT、Claude、Gemini 今天已经能够完成一件事情的 20%，你真正的竞争对手可能根本不是另一家创业公司。

而是六个月以后的 GPT、Claude、Gemini。

这也是今天很多所谓 AI Wrapper 最大的问题。

它们做的事情，本质上只是：

> 把模型已经拥有的能力包装成一个 UI。

模型升级一次，产品价值就被吃掉一层。

真正有意思的问题，恰恰是：

为什么模型在这里成功率只有 1%？

可能是它缺少私有数据；

可能是它缺少行业知识；

可能是它不知道企业内部工具怎么使用；

可能是它没有足够长的上下文；

可能是任务需要持续几天；

可能是没有可靠的验证器；

也可能是整个任务根本不是一个模型调用，而是一条复杂的业务流水线。

这些地方，才是 AI 应用真正可以建立工程壁垒的地方。Jeff Dean 也特别提到，领域数据、专门训练的模型以及通用模型无法获得的个人或业务信息，都可能让小团队形成明显优势。

### 二、模型正在从「产品」退回「发动机」

Jeff Dean 在这场访谈里讲了一句话，我非常认同：

模型只是系统的一部分。

真正能够解决复杂问题的 AI 系统，还需要 Retrieval、Tools、Memory、Context，以及整个 Agent 的 Orchestration。

这也是我这一年使用 AI Coding 越来越明显的感觉。

我现在已经很少把 Claude Code、Codex 这一类东西理解成“代码生成器”。

代码生成其实是整个系统里最不重要的部分之一。

真正重要的是：

它知道什么？

它能看到什么？

它可以操作什么？

它有哪些 Skills？

它如何知道自己做错了？

失败以后怎么恢复？

执行十分钟以后，它还记不记得最初的目标？

执行三天以后，系统还能不能保持正确方向？

所以我现在更愿意把一个 Agent 的能力粗略理解为：

智能体能力 = 模型 × 上下文 × 工具 × 技能 × 评估器 × 编排

模型只是其中一个乘数。

而且越来越可能不是最值得应用开发者优化的那个乘数。

因为模型这一层，Google、OpenAI、Anthropic 会疯狂替我们优化。

应用开发者真正有机会建立差异的，反而是后面的东西。

这也是为什么我认为，AI 应用开发正在经历一个非常明显的迁移：

提示工程 → 上下文工程 → 智能体工程 → 系统工程

最后我们会重新回到那个计算机行业已经讲了几十年的词：

系统工程。

只不过这一次，系统里面多了一种具有推理能力的软件组件。

### 三、真正重要的不是 Agent 数量，而是闭环

Jeff Dean 还谈到了一个现在特别热门的问题：

长时间运行的 Agent。

他认为未来 Agent 完全可能围绕一个复杂问题连续运行几天，甚至几周；例如让 Agent 把一个大型软件系统重新实现成另一种语言，以获得更好的性能或安全属性。

但这里有一个今天所有做 Agent 的人都会遇到的问题。

Agent 做前十步的时候可能很好。

做到第三十步开始有点奇怪。

做到第五十步已经不知道自己在哪里了。

Jeff Dean 对这个问题的解释也非常有意思：

当 Agent 逐渐离开模型训练分布中熟悉的区域，它的性能就会开始下降。

解决办法不是简单地“再给它更多 Token”。

而是通过 Skills、Guidelines，把 Agent 尽可能限制在一条它知道如何行动的路径上；或者让多个 Agent 搜索不同解法，再通过另一个 Agent 或 Evaluator 判断哪个方案值得继续。

这和我对 Agent Team 的理解非常接近。

最近大家特别喜欢一件事情：

堆智能体。

10 个代理。

50 个代理。

100 个代理。

仿佛 Agent 数量等于智能。

我其实越来越不相信这个方向。

100 个没有反馈系统的 Agent，只是把一个人的混乱并行化成了一百份。

真正应该追求的不是：

> 多少个智能体？

而是：

> 这个循环有多好？

也就是：

目标 → 执行 → 观察 → 验证 → 修正 → 再执行

这个循环能不能稳定运行？

如果这个 Loop 稳定，一个 Agent 就可以干非常复杂的事情。

如果这个 Loop 不稳定，一百个 Agent 只会更快地产生垃圾。

所以我之前一直说：

Agent 本身只是一个内循环。

真正重要的是把它嵌入更大的业务外循环。

开发、测试、Code Review、部署、监控、用户反馈、Bug、再次开发……

整个业务 Loop 一旦被接起来，Agent 才真正进入了生产系统。

这时候我们做的已经不再是 Chatbot。

而是在造一台机器。

### 四、AI 越会写代码，Specification 反而越重要

Jeff Dean 在访谈里还提到了一个我觉得非常关键、但很容易被忽略的变化：

AI 越强，Specification 反而越重要。

过去我们也一直强调：

写程序之前应该先想清楚程序到底要干什么。

但过去执行代码的是人。

人类工程师拥有大量隐含上下文，可以理解模糊要求，也可以主动追问。

Agent 不一样。

当需求描述不清楚的时候，它必须猜。

而 Agent 越能写代码，“猜错以后产生的代码量”反而越恐怖。

因此 Jeff Dean 认为，清晰描述目标的重要性实际上提高了。

他举了一个特别好的例子：

为什么今天 AI 做代码跨语言迁移通常效果很好？

比如：

Python → Go。

因为原来的 Python 程序，本身就是一份极其详细的 Specification。

行为已经存在。

测试已经存在。

输入输出已经存在。

Agent 可以：

迁移实现，

迁移测试，

运行测试，

比较行为差异，

继续修正，

直到两个系统行为趋于一致。

所以这里真正重要的甚至不是“代码迁移”。

而是：

Specification 是否可以执行。

这也是我越来越看好 Executable Spec 的原因。

未来的软件开发，很可能不再是：

> 需求 → 程序员 → 代码

而会逐渐变成：

> 意图 → 可执行规格 → 智能体 → 实现 → 验证

人类慢慢退出 Implementation。

但是人类不会退出软件工程。

恰恰相反。

人的位置会上移。

从 Programmer 变成：

问题设计师 / 规格设计师 / 系统架构师 / 验证者。

### 五、这也是为什么我越来越觉得 Rust 是 AI 友好语言

这件事情继续推演下去，就又回到了我最近一直思考的 Rust 问题。

我之前说过一句比较夸张的话：

> Rust 是 AI 的汇编语言。

很多人第一反应可能是：

Rust 这么复杂，怎么可能对 AI 友好？

但如果未来主要负责写代码的不是人，而是 Agent，那么判断一种语言是否“友好”的标准可能也会改变。

过去所谓 Developer Friendly，通常意味着：

语法简单、

写得快、

约束少、

容易上手。

但是 Agent 不怕语法复杂。

Agent 真正怕的是：

它做错了，却没人告诉它错在哪里。

从这个角度看，Rust 的所有权、借用、生命周期、类型系统、Trait、Send/Sync，以及大量编译期约束，反而构成了一个非常强的机器反馈系统。

AI 写一段代码。

cargo check。

错。

编译器告诉它为什么错。

修改。

再检查。

再修改。

Clippy。

测试。

Miri。

消毒剂。

基准测试。

整个开发过程天然就可以形成一个机器可执行的反馈 Loop。

当然，Rust 编译器绝不是程序正确性的完整证明器。

能够通过编译，不等于程序一定正确。

但 Rust 做了一件非常重要的事情：

它把大量原本存在于程序员脑子里的隐式约束，变成了机器可以检查的显式约束。

而 AI 软件工程恰恰最需要这样的东西。

所以我越来越觉得：

类型系统的价值正在因为 AI 而重新上升。

以前类型系统主要帮助“人少犯错误”。

未来类型系统可能还有另一个重要角色：

> 帮助 AI 知道自己什么时候犯了错误。

这完全是两种不同的语言设计价值。

### 六、代码不再稀缺以后，真正稀缺的是 Taste

访谈里还有一个问题特别好。

主持人问 Jeff Dean：

假设未来每个创业者都可以同时运行几十、上百个 Agent，所有代码都可以让 Agent 完成。

那么什么能力会变得最稀缺？

Jeff Dean 的答案是：

品味。

也就是：

你让这些 Agent 去做什么？

我认为这是整个访谈最重要的一句话之一。

过去软件世界里，一个想法可能很有价值，仅仅因为实现它需要五十个工程师干两年。

当实现成本下降一百倍以后，这层壁垒就消失了。

于是问题重新变成：

什么值得做？

如果给你 100 个工程师，你让他们干什么？

如果给你 1000 个 Agent，你让它们干什么？

如果未来一次可以生成一百万行正确代码：

你想生成什么？

这时候真正稀缺的东西，不再是 Coding。

甚至未必是 Engineering。

而是：

判断力。

问题意识。

审美。

领域经验。

对未来的理解。

Jeff Dean 建议一个很有意思的训练方法：

定期写下你认为未来十二个月会变得重要的事情。

十二个月以后再回来检查：

哪些判断发生了？

哪些没发生？

哪些事情别人做出来了？

哪些方向根本没人关心？

长期重复这个过程，其实就是在训练自己的 Taste。

我特别喜欢这个方法。

因为 Taste 并不是什么玄学。

Taste 本质上也是大量预测之后形成的压缩经验。

所以我一直认为：

可以把执行交给 AI，

可以把代码交给 AI，

可以让 AI 帮我搜索、整理、验证、实现，

但是有一件事情不能轻易交出去：

思考。

AI 可以替我写。

但不能替我决定：

什么值得写。

### 七、Jeff Dean 真正厉害的，其实一直不是写代码快

Jeff Dean 的职业生涯里有两个很经典的故事。

2001 年，他和 Sanjay Ghemawat 算了一下，发现 Google 当时整个搜索索引已经可以放进机器内存，于是很快把搜索系统从磁盘方案切到了内存方案。

搜索因此获得了巨大的速度提升。

2013 年 Google 的深度学习语音识别开始真正变得好用。

Jeff Dean 又做了一次简单计算：

如果每个用户每天只使用几分钟语音识别，需要的计算资源可能让 Google 的服务器规模大幅增加。

于是问题不再是：

怎样继续优化 CPU 上的语音模型？

而变成：

为什么一定要用 CPU？

后来才有了 TPU 这条路线。第一代 TPU 针对机器学习核心计算进行了专门化，在当时获得了数量级上的能耗和延迟优势。

这两个故事真正有意思的地方，并不是 Jeff Dean 写代码特别快。

而是他会不断问：

我们是不是默认接受了一个其实已经失效的前提？

搜索为什么必须依赖磁盘？

机器学习为什么必须跑在通用 CPU 上？

芯片为什么一定要求每个晶体管都极度可靠？

AI 为什么必须只是一个模型？

Agent 为什么只能运行十分钟？

软件为什么一定由人来写？

这些问题表面看起来跨越了几十年的计算机技术。

但背后的思维模式其实完全一样：

不要在旧系统里寻找 10% 的优化。

先问：

> 有没有可能换一种问题定义，直接得到 10 倍甚至 100 倍的变化？

Jeff Dean 自己也把这种方法描述为回到 First Principles，不被今天的解决方案锚定，并寻找数量级级别的性能或能力变化。

这可能才是所谓工程师真正的“第一性原理”。

### 八、我理解的 AI Native，不是会用 AI 写代码

所以如果让我总结这场访谈，我觉得 Jeff Dean 实际上描述了一种正在出现的新型工程师。

我暂且把它叫做：

### AI 原生工程师

他最重要的能力已经不再是亲自完成每一步。

而是能完成几次关键的抽象。

第一层：

找到值得解决的问题。

第二层：

把模糊目标变成 Specification。

第三层：

把 Specification 变成 AI 可以执行的任务。

第四层：

为 Agent 提供上下文、工具和技能。

第五层：

建立 Evaluator 和反馈闭环。

最后：

让系统自己运行。

于是软件开发正在从：

编程

变成：

编排。

再进一步：

变成：

自动化。

最终可能变成：

软件工厂。

我们不再亲自制造每一颗螺丝。

我们设计生产线。

### 九、真正的机会，就藏在那 1% 里面

再回到 Jeff Dean 的那个问题。

为什么是 1%？

因为 1% 意味着：

模型已经足够聪明，可以成为基础设施；

但这个问题又复杂到，单独一个模型根本解决不了。

这其实是一个非常有意思的甜蜜点。

如果模型成功率是 0%，也许技术还没有成熟。

如果已经是 80%，那可能根本不需要创业公司了。

而 1% 意味着：

AI 已经能够提供某些基本能力，

但是整个系统还没有被发明出来。

缺少上下文。

缺少数据。

缺少工具。

缺少技能。

缺少评估器。

缺少工作流。

缺反馈闭环。

缺一个真正理解这个领域的人，把所有东西连接起来。

这就是创业者和工程师可以存在的地方。

所以未来真正值得寻找的，也许不是：

> AI 还能帮人做什么？

而应该反过来问：

> 今天最强的 AI，在哪些真正重要的问题上仍然几乎什么都做不了？

然后继续追问：

它为什么做不了？

如果答案不是“模型还不够聪明”，

而是：

缺少工程系统，

缺少领域知识，

缺少反馈，

缺少环境，

缺少边界，

缺少验证，

那么那里可能就存在一家公司。

甚至可能存在一个新的软件基础设施层。

这也是我越来越相信的一件事情：

AI 革命最终不会只是模型革命。

模型会逐渐成为电力。

真正改变世界的，是后来围绕电力建立起来的工厂、机器、生产线和城市。

而我们今天正在做的 Agent、Harness、Context、Skill、Evaluator、Executable Spec……

很可能就是 AI 时代最早的那些：

齿轮、传送带和生产线。

代码当然还重要。

但代码已经不再是终点。

甚至越来越不是稀缺资源。

真正稀缺的是：

你知道应该让机器生产什么。

## 结构化（1）

### 2026-08-21 10:00:13

#### 文章精炼总结：Jeff Dean 的「1% 法则」

文章认为，随着 AI 接管越来越多的代码执行工作，工程师的核心价值正从“亲自实现”上移到“定义问题、设计规格、搭建系统和验证结果”。未来真正稀缺的不是代码，而是找到值得解决的问题，并让 AI 持续、可靠地完成任务的判断力与系统能力。

##### 一、「1% 法则」：寻找模型几乎做不到的重要问题

Jeff Dean 建议，创业者应优先寻找当前最强通用模型成功率仅为 **0%～1%** 的任务，而不是模型已经能完成 20% 的任务。

- 如果 GPT、Claude、Gemini 已能完成某项任务的 **20%**，剩余问题可能在半年或一年后被模型升级直接解决。
- 只把现有模型能力包装成 UI 的 AI Wrapper，容易随着基础模型升级而失去价值。
- 模型成功率只有约 1%，往往不是因为模型完全不够聪明，而是缺少：
  - 私有或行业数据；
  - 企业内部工具；
  - 足够长的上下文；
  - 长时间持续执行能力；
  - 可靠的验证器；
  - 完整的业务工作流与反馈闭环。

这些缺失环节，正是创业公司可以建立工程壁垒的地方。领域数据、专门训练的模型，以及通用模型无法获得的个人或业务信息，都可能成为小团队的优势。

##### 二、模型正在从“产品”变成“发动机”

复杂 AI 系统不能只依赖模型，还需要检索、工具、记忆、上下文和智能体编排。

文章将智能体能力概括为：

> **智能体能力 = 模型 × 上下文 × 工具 × 技能 × 评估器 × 编排**

模型只是其中一个乘数。Google、OpenAI、Anthropic 等公司会持续优化模型，而应用开发者更有机会在其他部分建立差异。

AI 应用开发的重点正在逐步迁移：

> **提示工程 → 上下文工程 → 智能体工程 → 系统工程**

因此，Claude Code、Codex 等工具不应只被看作“代码生成器”。更关键的问题是：它知道什么、能操作什么、如何发现错误、失败后如何恢复，以及运行数天后能否仍然保持正确方向。

##### 三、Agent 的关键不是数量，而是反馈闭环

未来的 Agent 可能围绕复杂任务连续运行几天甚至几周。例如，将一个大型软件系统迁移到另一种语言，以改善性能或安全性。

但长时间运行会带来明显问题：

- 前十步可能表现很好；
- 到第三十步开始偏离；
- 到第五十步可能已经忘记目标。

原因之一是 Agent 逐渐进入模型训练数据中不熟悉的区域。解决方法不是单纯增加 Token，而是：

- 用 Skills 和 Guidelines 限制行动路径；
- 让多个 Agent 探索不同方案；
- 通过另一个 Agent 或 Evaluator 选择、验证结果。

文章反对盲目堆叠几十或上百个 Agent。没有反馈系统的 100 个 Agent，只是把混乱并行放大。

真正重要的是稳定运行以下循环：

> **目标 → 执行 → 观察 → 验证 → 修正 → 再执行**

此外，还要把 Agent 的内部循环接入更大的业务循环：

> **开发 → 测试 → Code Review → 部署 → 监控 → 用户反馈 → Bug → 再开发**

做到这一步，系统才不再只是聊天机器人，而是一台可以进入生产环境的“机器”。

##### 四、AI 越会写代码，Specification 越重要

AI 生成代码的能力越强，清晰描述目标的重要性反而越高。

人类工程师能利用隐含上下文理解模糊要求，也会主动追问；Agent 面对不清楚的需求时只能猜测。它写代码越快，猜错后产生的错误代码就可能越多。

文章以跨语言迁移为例：

> **Python → Go**

这类任务通常效果较好，因为原有 Python 程序本身就是一份详细、可执行的规格：

- 已有明确行为；
- 已有输入输出；
- 通常已有测试；
- Agent 可以迁移实现和测试；
- 运行测试并比较行为差异；
- 持续修改，直到新旧系统表现趋于一致。

因此，关键不是“代码迁移”，而是规格能否被执行和验证。未来软件开发流程可能变为：

> **意图 → 可执行规格 → 智能体 → 实现 → 验证**

人类会逐步退出具体实现，但不会退出软件工程，而是上移为问题设计师、规格设计师、系统架构师和验证者。

##### 五、为什么 Rust 可能是一种“AI 友好语言”

传统上，“开发者友好”意味着语法简单、约束少、容易上手。但当主要写代码的是 Agent 时，语言是否友好的判断标准可能改变。

Agent 不一定怕复杂语法，它更怕的是：

> 做错了，却没有系统明确告诉它错在哪里。

Rust 的所有权、借用、生命周期、类型系统、Trait、Send/Sync 和编译期约束，可以形成强大的机器反馈系统：

1. AI 编写代码；
2. 运行 `cargo check`；
3. 编译器指出问题；
4. AI 修改并再次检查；
5. 继续使用 Clippy、测试、Miri、消毒剂和基准测试验证。

Rust 编译通过并不代表程序一定正确，但它把许多原本存在于程序员脑中的隐性约束，转化成机器可以检查的显性约束。

因此，类型系统未来不仅帮助“人少犯错误”，还可以帮助 AI 识别自己何时犯错。

##### 六、代码不再稀缺后，真正稀缺的是“品味”

当创业者可以同时运行几十甚至上百个 Agent，代码实现成本大幅下降后，最稀缺的能力将变成 **Taste（品味）**，即：

> 你决定让这些 Agent 去做什么。

过去，一个想法可能因为需要 50 名工程师开发两年而具有壁垒；当实现成本下降 **100 倍**，这种壁垒就会消失。此时更重要的是：

- 什么问题值得解决；
- 哪些需求真正重要；
- 如果有 100 个工程师或 1,000 个 Agent，应该让它们做什么；
- 如果能生成 100 万行正确代码，究竟应该生成什么。

真正稀缺的能力将是判断力、问题意识、审美、领域经验和对未来的理解。

Jeff Dean 提出的训练方法是：

1. 定期写下未来 12 个月可能变得重要的事情；
2. 12 个月后复盘哪些判断实现了；
3. 检查哪些方向由别人做成、哪些无人关心；
4. 长期重复，训练自己的判断与品味。

文章强调，执行、搜索、整理、验证和实现可以交给 AI，但“什么值得做”不能轻易交出去。

##### 七、Jeff Dean 的核心能力：重新定义问题

文章通过两个案例说明，Jeff Dean 的优势不只是写代码快，而是能够发现旧前提已经失效。

###### 案例 1：搜索索引从磁盘转向内存

**2001 年**，Jeff Dean 和 Sanjay Ghemawat 计算后发现，Google 当时的整个搜索索引已经可以放入机器内存，于是将搜索系统从磁盘方案切换到内存方案，使搜索速度大幅提升。

关键问题不是继续优化磁盘，而是：

> 搜索为什么必须依赖磁盘？

###### 案例 2：从 CPU 转向 TPU

**2013 年**，Google 的深度学习语音识别逐渐实用。Jeff Dean 估算发现，即使每个用户每天只使用几分钟语音识别，也可能让 Google 所需的服务器规模大幅增长。

于是问题从“如何继续优化 CPU 上的模型”变成：

> 机器学习为什么一定要运行在通用 CPU 上？

这推动了 TPU 路线。第一代 TPU 针对机器学习核心计算进行专门化，在当时取得了**数量级的能耗和延迟优势**。

这些案例体现了同一种第一性原理思维：

- 不被现有方案锚定；
- 质疑默认前提；
- 不只追求旧系统中的 10% 优化；
- 寻找能够带来 10 倍甚至 100 倍变化的新问题定义。

##### 八、AI 原生工程师：从编程转向编排

文章将未来的新型工程师称为“AI 原生工程师”。其核心能力不是亲自完成每一步，而是完成几层关键抽象：

1. 找到值得解决的问题；
2. 把模糊目标变成清晰的 Specification；
3. 把规格转化为 AI 可以执行的任务；
4. 为 Agent 提供上下文、工具和技能；
5. 建立 Evaluator 和反馈闭环；
6. 让系统能够持续、自动运行。

软件开发将逐渐经历以下变化：

> **编程 → 编排 → 自动化 → 软件工厂**

工程师不再亲自制造每一颗“螺丝”，而是负责设计生产线。

##### 九、真正的创业机会藏在“1%”里

“1%”代表一个特殊的甜蜜点：

- 如果成功率是 **0%**，技术可能尚未成熟；
- 如果成功率已达 **80%**，可能不再需要专门的创业公司；
- 如果成功率约为 **1%**，说明模型已经能提供基础能力，但完整系统尚未被发明。

这类任务通常还缺少上下文、数据、工具、技能、评估器、工作流、反馈闭环，以及真正理解行业的人。

因此，寻找机会时不应只问：

> AI 还能帮助人做什么？

更应该问：

> 今天最强的 AI，在哪些重要问题上仍然几乎什么都做不了？为什么？

如果原因不是模型智力不足，而是缺少工程系统、领域知识、环境、边界和验证机制，那么那里可能诞生一家新公司，甚至形成新的软件基础设施层。

##### 核心结论

文章把基础模型比作“电力”：模型本身会逐渐成为通用基础设施，真正改变世界的将是围绕它建立的工厂、机器、生产线和城市。

Agent、Context、Skill、Evaluator、Harness 和 Executable Spec，可能就是 AI 时代早期的齿轮、传送带和生产线。代码依然重要，但它越来越不是终点，也不再是最稀缺的资源；真正稀缺的是：

> **知道应该让机器生产什么，并设计一个能让它可靠生产出来的系统。**

## 口播总结（1）

### 2026-09-17 00:21:22

当人工智能开始接管“执行”，工程师最重要的能力正在上移。过去的问题是，能不能把东西做出来。现在更关键的问题是，能不能找到值得解决的事，给出清晰规格，再构造一套系统，让人工智能自己完成、检查和修正。

杰夫·迪恩给人工智能创业者提出了一个很有启发性的判断标准，可以叫作“百分之一法则”。

寻找方向时，可以先让最强的通用模型尝试目标任务。如果模型已经能完成百分之二十，这未必是好消息。因为这种能力已经出现在通用模型里。随着模型升级，剩余问题可能在半年或一年后被模型直接解决。创业公司的真正竞争对手，也许不是同行，而是下一代通用模型。

相反，更值得研究的，是模型成功率接近百分之一的重要任务。这里的重点不是“做到百分之一就够了”，而是追问：模型为什么几乎做不了？

原因可能是缺少企业私有数据，缺少行业知识，不会操作内部工具，也可能是上下文不够长，任务要持续几天，或者没有可靠的检查机制。还有一种可能，是这件事根本不是调用一次模型就能完成的，而是一条复杂的业务流程。

这正是应用团队建立壁垒的地方。模型已经足够强，可以成为基础设施；但完整系统还没有被发明出来。企业需要补上数据、工具、工作流、验证机制和领域经验。只把现有模型套进一个界面的产品，很容易在模型升级后失去价值。

理解这一点，就会发现，模型更像发动机，而不是整辆车。

一个真正能解决复杂问题的智能体，也就是能够观察环境并采取行动的人工智能系统，不只取决于模型。它还取决于模型能看到什么信息，能使用什么工具，掌握哪些技能，如何判断自己做错了，以及失败后怎样恢复。

尤其是长时间运行的智能体。它刚开始可能表现很好，执行到第三十步开始偏离，到第五十步已经忘记最初目标。问题往往不是信息容量不够，而是智能体逐渐走出了模型熟悉的范围。

因此，简单增加更多计算量，或者堆积几十上百个智能体，并不能自动解决问题。一百个没有反馈机制的智能体，只是把一份混乱并行复制成一百份。

真正重要的是闭环。系统先明确目标，再执行任务；执行后观察结果，用测试或评估器验证；发现偏差后修正，然后继续执行。如果这个循环稳定，一个智能体就能完成很复杂的工作。如果循环不稳定，智能体越多，制造错误的速度反而越快。

这个闭环还要接入真实业务。以软件开发为例，智能体不能只负责生成代码。它还要进入测试、代码审查、部署、监控、用户反馈和缺陷修复的全过程。到了这一步，我们做的就不再是聊天机器人，而是一台可以持续运转的生产机器。

人工智能越会写代码，清晰的规格说明反而越重要。

人类工程师面对模糊需求，可以依靠经验补全信息，也可以主动追问。智能体遇到模糊需求时，只能猜。它的编码能力越强，一旦猜错，就越可能快速生成大量错误代码。

代码跨语言迁移之所以常常效果不错，就是因为原来的程序本身已经是一份非常详细、而且可以运行的规格说明。比如把一个 Python 程序迁移到 Go 语言。原程序的行为已经存在，输入和输出已经确定，测试也可能已经具备。智能体可以迁移实现和测试，运行测试，比较差异，再不断修正。

这说明，未来真正重要的可能是“可执行规格”。开发流程会从“需求交给程序员，再变成代码”，逐渐转向“人的意图变成可执行规格，再由智能体实现和验证”。人类会减少亲自编写每一行代码，但不会退出软件工程。人的位置会向上移动，成为问题设计者、规格设计者、系统架构师和验证者。

这也解释了为什么强类型语言可能在人工智能时代变得更有价值。以 Rust 为例，它的语法和规则对人来说可能比较复杂，但智能体并不害怕复杂。智能体真正害怕的是，犯错以后没有明确反馈。

Rust 的类型系统、所有权规则和编译期检查，可以把许多隐含约束变成机器能够检查的显式约束。智能体写完代码，可以运行检查；编译器指出错误后，它再修改、再测试。当然，通过编译不代表程序一定正确。但这种持续、明确、可执行的反馈，非常适合智能体工作。类型系统过去主要帮助人少犯错误，未来还可能帮助人工智能知道自己什么时候犯了错误。

当代码生产成本大幅下降，最稀缺的能力会进一步变化。杰夫·迪恩给出的答案是“品味”。这里的品味，不只是审美，而是判断什么值得做。

如果每个人都可以调动上百个智能体，写出大量正确代码，那么实现能力本身就不再构成足够高的壁垒。真正拉开差距的，会是问题意识、领域经验、判断力，以及对未来的理解。

一种训练方法是，定期写下自己认为未来十二个月会变得重要的事情。一年后再回来检查：哪些判断发生了，哪些没有发生；哪些方向被别人做出来了，哪些根本没人需要。长期重复这个过程，就是在训练判断力。所谓品味，并不完全是玄学，它也可以理解为大量预测和反馈之后形成的压缩经验。

杰夫·迪恩过去的工作也体现了同一种思维方式。他曾发现，谷歌的搜索索引已经可以放进内存，于是问题不再是怎样继续优化磁盘访问，而是为什么还要依赖磁盘。后来面对语音识别带来的巨大计算需求，他追问的也不是怎样继续压榨通用处理器，而是为什么机器学习一定要运行在通用处理器上。这种重新定义问题的思路，推动了专用人工智能芯片的发展。

关键不是在旧系统里寻找百分之十的改进，而是检查旧前提是否已经失效，并寻找十倍甚至一百倍的变化。

所以，人工智能时代真正值得寻找的，不只是“人工智能还能帮人做什么”，而是：今天最强的人工智能，在哪些重要问题上仍然几乎无能为力？它做不了，究竟是因为模型不够聪明，还是因为缺少数据、工具、领域知识、反馈闭环和可执行规格？

如果缺少的是后面这些东西，那里就可能存在一家新公司，甚至可能出现一层新的软件基础设施。模型会逐渐像电力一样普及。真正创造巨大价值的，是围绕电力建立起来的机器、工厂和生产线。

代码仍然重要，但代码不再是终点。真正稀缺的，是知道应该让机器生产什么，以及怎样让这台机器长期、可靠地运行。

## 深度解读（1）

### 2026-09-17 00:38:54

#### AI 应用的壁垒，不在模型不会做，而在系统能否让它可靠地做

这篇文章最值得保留的，不是“代码不再重要”或“品味最稀缺”这些醒目结论，而是一个更具体的判断：**当模型逐渐接管执行，价值会向任务定义、约束表达和结果验证迁移。** 不过，文中的“1% 法则”更适合作为寻找问题的起点，而不是机械的创业筛选公式。

##### 关键不是成功率低，而是为什么低

文章建议寻找通用模型成功率只有 0%—1% 的重要任务，因为成功率已经达到 20% 的能力，可能很快被下一代模型补齐。这个提醒有价值：如果产品只是把模型已有能力套上一层界面，确实很容易被基础模型升级吞没。

但**低成功率本身不代表机会**。它也可能意味着需求不存在、任务无法清晰定义，或者当前技术根本不可用。真正需要判断的是失败原因：

- 如果缺的是企业私有数据、业务权限、工具连接和行业知识，应用公司可能建立长期优势；
- 如果缺的是可自动检查的结果、异常恢复和跨天运行能力，机会在工作流与系统工程；
- 如果只是模型推理能力不足，那么创业公司既难补齐，也可能在模型升级后失去价值。

反过来，模型已有 20% 成功率也未必危险。在医疗、财务、客服等场景，剩余的 80% 往往不是“再聪明一点”，而是异常处理、合规责任、组织协同与客户信任。这些部分可能比模型能力更难被替代。因此，判断机会时应测试的不是单次任务准确率，而是：**端到端结果能否交付、错误能否被发现、失败能否恢复，以及企业是否愿意为责任闭环付费。**

##### AI 越能执行，模糊需求的代价越高

文章对可执行规格的强调，比“多 Agent”更有长期意义。Agent 的危险并不是不会生成，而是能以极高速度沿着错误目标持续生成。需求中的一个歧义，过去可能造成程序员半天返工；在自动化系统里，它可能迅速扩散成大量代码、错误决策和外部操作。

代码跨语言迁移效果较好，正好说明了这一点：旧代码、测试和输入输出共同构成了一份可执行规格，Agent 可以反复比较行为并修正。真正可迁移的原则不是“Rust 更适合 AI”，而是：**环境提供的机器反馈越密集、越明确，Agent 越容易形成可靠闭环。** 强类型、编译器、测试、模拟器和业务规则引擎，本质上都在把人脑中的隐含约束变成机器可检查的信号。

这也揭示了多 Agent 叙事的误区。增加 Agent 数量只是增加搜索宽度；如果没有判定优劣的评估器，它只会更快地产生更多候选答案。可靠性来自“执行—观察—验证—修正”的闭环，而不是代理数量。

##### “品味”最终要落实为可校准的判断

当实现成本下降，稀缺资源确实会从产能转向选择：解决哪个问题、接受什么代价、如何定义“完成”。但品味并非抽象直觉，而是经过反馈校准的资源配置能力。文章提到定期记录未来十二个月的判断，再回看哪些实现、哪些落空，是一个朴素但有效的方法。

对产品经理而言，更值得建立的是一套持续更新的“判断账本”：当时相信什么、依据是什么、哪些变量会推翻结论、后来结果如何。**AI 可以压低执行成本，却不会自动提高选题质量；相反，执行越便宜，错误方向被规模化的速度越快。**

因此，真正值得寻找的未必是“模型只能做到 1%”的任务，而是那些**价值足够高、失败原因可工程化解决、结果可以验证，并且闭环数据会持续改善系统**的任务。那里才可能存在不会随着下一次模型升级一起消失的产品。

## 默认总结（1）

### 2026-09-18 01:13:42

##### 一句话看懂

文章借 Jeff Dean 的访谈提出：当 AI 逐渐接管写代码等“执行”工作，真正稀缺的将是选对问题、写清规格，并搭建数据、工具、验证与反馈闭环的能力。

##### 关键内容

- **“1% 法则”**：据作者转述，创业者应关注通用模型目前几乎做不成、但并非完全不可行的重要任务；若模型已能完成较大部分，产品可能很快被下一代模型取代。这里的“1%”是选题思路，不是严格门槛。
- **模型只是发动机**：复杂 AI 产品还依赖私有数据、上下文、工具、记忆、技能、评估器和工作流。壁垒不只是套一层界面，而是把这些部分组成可靠系统。
- **Agent 贵在闭环而非数量**：关键是“执行—观察—验证—修正”能否持续稳定运行。没有反馈机制，增加 Agent 只会并行制造错误。
- **人的角色向上移动**：AI 越会编码，目标和可执行规格越重要；工程师将更多负责问题定义、架构和验收。作者进一步认为，Rust 等约束强、机器反馈明确的语言可能更适合 Agent。

##### 通俗解读

这不是说“代码已不重要”，而是说代码供给变便宜后，**决定做什么、怎样证明做对了**更值钱。文章启发性强，适合 AI 产品与工程从业者细读；但它是作者对访谈的整理和延伸，尤其“1% 法则”、Rust 判断与“品味”结论应视为经验性观点，而非已验证定律。
