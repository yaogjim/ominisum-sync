## 正文

**jolestar**

看到还有人把 CLAUDE.md/AGENTS.md 当作一个银弹，研究怎么写。但实际上，如果你的 Agent harness 做的足够，AGNETS.md 只应该写自己的项目和个人偏好，以及给它的职责，而不是通用知识以及工作方法。

分享一个我自己的 AGNETS.md 的方案：

1\. 全局的 \~/.agents/AGNETS.md 只写了本地仓库的约定目录和 worktree 约定目录，并且让 Agent clone 前先查一下本地是否存在。

代码仓库路径：  
\~/repos/github.com/org\_name/repo\_name  
Worktree路径：  
\~/worktrees/github.com/org\_name/repo\_name/branch\_name

这样多个 Agents 不会把项目和 worktree 到处放，也方便清理。

2\. 项目的 .agents/AGENTS.md 放项目概览，文档路径以及一些特殊要求。比如禁止滥用 fallback。

3\. AgentHome 的 .agents/AGENTS.md，放它的角色和职责。比如是否有合并代码权限，PR/Review/CI/Deploy 工作流要求。

如果是 Codex，我会给每个 Agent 创建一个专用的 AgentHome 目录，然后在那个目录下启动 Codex，然后告诉它项目目录。这样 Codex 就会先加载 AgentHome 下的 AGENTS.md。 而 holon 中，则自动内置了这套机制。

#### 深度总结

这条内容的核心观点是：

> **CLAUDE.md / AGENTS.md 不是“银弹”，不要把它写成万能说明书。真正关键的是 Agent harness（运行框架/工作流支撑）是否足够完善。**

作者认为，`AGENTS.md` 应该只承载**项目相关、个人偏好、角色职责**这些“上下文信息”，而不应该塞入大量通用知识、通用方法论。

作者给出的实践方案是分层管理：

##### 1. 全局 AGENTS.md：只管本地环境约定

例如规定：

```text
代码仓库路径：
~/repos/github.com/org_name/repo_name

Worktree 路径：
~/worktrees/github.com/org_name/repo_name/branch_name
```

作用是：

- 避免多个 Agent 到处乱 clone 项目
- 统一目录结构
- 方便清理和管理
- clone 前先检查本地是否已有仓库

##### 2. 项目 AGENTS.md：写项目上下文

放在项目的 `.agents/AGENTS.md` 中，主要写：

- 项目概览
- 文档位置
- 特殊约束
- 禁止事项

例如：

> 禁止滥用 fallback。

也就是告诉 Agent：这个项目是什么、该看哪里、有哪些坑别踩。

##### 3. AgentHome AGENTS.md：写角色和权限

每个 Agent 可以有自己的工作目录，即 AgentHome。

其中的 `.agents/AGENTS.md` 用来定义：

- 这个 Agent 的角色
- 是否有合并代码权限
- PR / Review / CI / Deploy 流程要求
- 它能做什么，不能做什么

如果用 Codex，作者会给每个 Agent 创建专属 AgentHome，并在该目录启动 Codex，让它先加载角色说明，再指定项目目录。

作者提到，自己的 holon 系统已经内置了这套机制。

#### 深入浅出解读

很多人现在把 `CLAUDE.md` / `AGENTS.md` 当成“魔法咒语”：

> 只要写得足够好，Agent 就会变聪明。

但作者的意思是：

> **不是文档越长越好，而是系统设计要清楚。**

可以类比成公司管理：

- `全局 AGENTS.md`：公司办公制度，比如文件放哪、仓库在哪
- `项目 AGENTS.md`：某个项目的说明书，比如业务背景、技术文档、特殊禁忌
- `AgentHome AGENTS.md`：某个员工的岗位职责，比如能不能审批、能不能上线、负责哪块

如果你把所有东西都塞进一个文件里，就像让员工入职时背一本几百页的公司百科：

- 信息太杂
- 重点不清
- 容易冲突
- Agent 反而更容易做错

真正高效的方式是：

> **该系统管的交给系统，该项目说明的写项目，该角色约束的写角色。**

---

#### 关键洞察

##### 1. 文档不是能力，流程才是能力

`AGENTS.md` 本身只是提示词文件。

它不能替代：

- 目录规范
- 权限管理
- 工作流编排
- 多 Agent 协作机制
- CI/CD 约束
- Review 机制

如果底层 harness 不行，文档写得再漂亮，也只是“人工补丁”。

##### 2. AGENTS.md 应该越具体越好

好的 `AGENTS.md` 不应该写：

> 你是优秀工程师，请认真分析，写高质量代码。

这种话太通用，价值有限。

更应该写：

> 本项目禁止使用 fallback 掩盖错误。  
> API 文档在 docs/api.md。  
> 合并前必须跑 pnpm test。  
> worktree 必须放在指定路径。

也就是：

> 少写空话，多写约束；少写理念，多写事实。

##### 3. Agent 需要“组织结构”，不是只需要提示词

作者强调的其实是 Agent 工程化：

- 文件该放哪
- 多个 Agent 如何隔离
- 谁有权限合并
- 谁负责 review
- 谁能 deploy
- 如何避免重复 clone
- 如何避免污染仓库

这说明 AI 编程正在从“单次对话”走向“长期协作系统”。

---

#### 我的辩证思考

##### 赞同之处

作者的观点很重要：  
**不要迷信 CLAUDE.md / AGENTS.md。**

现在很多人把提示词文件当作万能解法，本质上还是“Prompt 崇拜”。

但真实工程里，可靠性来自系统设计：

- 明确边界
- 明确权限
- 明确流程
- 明确上下文
- 明确失败处理

这比写一堆“请你仔细思考”更有用。

---

##### 需要补充的一点

不过，也不能低估 `AGENTS.md` 的价值。

对于个人开发者或小团队来说，一个写得好的 `AGENTS.md` 仍然很有帮助，因为它可以快速沉淀：

- 项目背景
- 编码规范
- 常见坑
- 测试命令
- 部署流程

问题不在于写不写，而在于：

> **不要把它写成百科全书，也不要指望它解决所有工程问题。**

---

##### 更合理的原则

可以用一句话概括：

> **AGENTS.md 负责“告诉 Agent 必须知道什么”，harness 负责“保证 Agent 按规则做事”。**

二者关系应该是：

| 层级 | 作用 |
|---|---|
| Harness | 提供流程、权限、环境、自动化 |
| AGENTS.md | 提供上下文、偏好、职责、约束 |
| Agent | 在边界内完成任务 |

---

#### 最终结论

`CLAUDE.md / AGENTS.md` 不是万能提示词，而是 Agent 工程体系中的一小部分。

真正成熟的做法是：

1. **全局文件管环境约定**
2. **项目文件管项目上下文**
3. **AgentHome 文件管角色职责**
4. **harness 管流程、权限和执行保障**

一句话：

> **不要试图用一个文档解决所有问题；要用分层系统管理 Agent。**

#### AGENTS.md 不是银弹，关键在 Agent Harness

##### 核心是把稳定规则工程化

这套思路的重点不是研究如何写出更复杂的指令文件，而是明确配置边界：通用能力和方法沉淀进 Harness，项目差异与权限职责留在 `AGENTS.md`。这样能减少重复提示和规则冲突，也更适合多 Agent 并行协作。其成立前提是 Harness 已具备足够完整的流程与能力支持。
