## 正文

**Barret李靖**

看了一晚上 Claude Code 泄露的代码，结合常见的记忆管理框架，把记忆模块做了一些分析。

Tulving 老爷子在 1972 年提出了记忆系统的框架设计，至今仍在广泛使用，他把记忆分为三类：1）情境记忆（episodic memory），我干了啥，用来记录过去；2）语义记忆（semantic memory），我知道啥，用来提炼规律；3）以及程序化记忆（procedural memory），我会做啥，用来决定行动。

这些记忆之间是存在相关性的，例如我经历的事情（情景记忆）会慢慢遗忘细节，储存在脑海中的是提炼后的规律和知识，也就是压缩成了语义记忆；而我知道的东西又会逐渐内化为行动的指引，变成一种“知道怎么做”的能力，这就是程序化记忆；程序化记忆反过来又会指导行动，从而产生新的经历。三者构成了一个不断循环的过程：经历 → 知识 → 技能 → 新的经历。

Claude Code Memory 在这几块都有对应的实践，例如每轮次的对话它会以 jsonl 格式做储存，这是情境记忆；同时在对话过程中还会有 SessionMemory 做实时蒸馏，相当于一边发生一边做初步整理。

每轮次结束后，它会 fork 出一个子 Agent（extractMemories）去提取值得持久化的内容，写入带 YAML 头的 MD 文件，这一层对应语义记忆，把零散对话压缩成可复用的知识。更有意思的是它还有一个 autoDream 机制，会在后台做整合和修剪，把碎片化的内容重新组织、合并、更新，这一步很像记忆的巩固过程。

很多框架都没有实现程序化记忆，而 Claude Code 做了。它有一个 feedback 的记忆类型，不仅记录了不要做什么（用户的纠正），还会记录哪些做法是对的（用户的确认），这些都是经验化的技能记录。多数系统只考虑负反馈，Claude Code 兼顾了正向确认，让 Agent 不至于越学越保守，这一点非常关键。

相比 LangMem/Mem0/Zep/EverMemOS/MemOS 这些框架，Claude Code 肯定弱的像个菜鸡😄。它有很多能力是明显不足的，例如：不支持语义化召回（用 LLM 扫 metadata 代替向量检索，上限 200 个文件）、遗忘策略比较粗（24 小时 or 5 轮对话触发整合）、无关联网络（记忆是孤立文件），等等。

真要像 EverMemOS/MemOS 那样追求全量记忆，工程和架构复杂度会直线上升，就拿 EverMemOS 来说，光基础设施就包含了 MongoDB/Elasticsearch/Milvus/Redis，更别说其他的附带依赖了。这类框架更适合做个人长期记忆管理。

另外也去对比了下 OpenClaw，它的记忆实现也非常有意思。它不追求全量记忆，而是优先解决“记忆什么时候该被用”。它把记忆拆成了三层：全局层、工作区层、任务层，逐层收敛，只在必要的时候才把上下文拉进来。

在 OpenClaw 眼里，记忆不是资产，正确使用记忆的能力才是。所以它的设计更侧重于重建临时的记忆网络。

放在这个视角下再去看 Claude Code，就会发现它其实选了一条更偏执行的路径。

对它来说，看清问题全貌也没那么重要。它解决问题的方式，更像人类工程师 debug，一边看、一边改、一边跑、一边修正，在行动中逐步逼近答案。

在这个过程中，Memory 的作用就是一个“防遗忘机制”，保证关键上下文不会在多轮试错中丢失。

## 默认总结（1）

### 2026-04-02 02:31:54

一句话说，Claude Code 的记忆系统并不是 “最强大脑”，而是一个服务于持续干活和不忘关键上下文的 “工程型记忆助手”。

##### 极简内容
- **核心框架**：作者用 Tulving 的三分法拆解 Claude Code 记忆：情境记忆 = 对话与过程记录，语义记忆 = 从对话中提炼出的可复用知识，程序化记忆 = 做事经验与反馈。
- **Claude Code 做法**：对话存`jsonl`，会话中实时蒸馏，结束后由子 Agent 抽取长期记忆，还用`autoDream`做后台整合与修剪。
- **亮点**：它不只记 “别做什么”，也记 “什么做对了”，即把正负反馈都沉淀成程序化记忆，避免 Agent 越学越保守。
- **短板**：语义召回弱、遗忘机制粗、缺少记忆关联网络，和 Mem0、Zep、EverMemOS、MemOS 这类长期记忆框架比，能力明显不完整。
- **定位差异**：作者认为 Claude Code 走的不是 “全量记忆” 路线，而是 “边做边修正” 的执行路线，Memory 本质上是防遗忘而非全知系统。

##### 辩证评价
Claude Code 的优势不在记得多，而在记得刚好够用，因此更适合高频执行型任务。  
但这种轻量设计也意味着它难以支撑复杂、长期、强关联的个人知识网络。

##### 高价值 / 反常识
真正决定 Agent 水平的，未必是 “存了多少记忆”，而是 “何时调用、如何压缩、怎样转成行动”。  
很多人只盯长期记忆库，作者却指出：对编码 Agent 来说，防止多轮试错中丢上下文，可能比构建完美记忆图谱更重要。

## 结构化（1）

### 2026-04-02 02:32:34

#### 主旨概括

这篇文章从经典记忆理论出发，分析了 Claude Code 的记忆模块设计，认为它虽然不像专业记忆框架那样 “强大全面”，但在 “边执行边记忆、避免多轮试错中丢失关键上下文” 这件事上，走出了一条很实用的工程路径。

#### 1. 用认知科学框架理解 AI 记忆

- 作者先引用 Tulving 在 1972 年提出的记忆系统框架，把记忆分为三类：
  - **情境记忆（episodic memory）**：记录 “我经历了什么”，偏向保存过去的事件。
  - **语义记忆（semantic memory）**：记录 “我知道什么”，偏向沉淀规律和知识。
  - **程序化记忆（procedural memory）**：记录 “我会怎么做”，偏向形成行动能力。
- 三类记忆不是孤立存在，而是会不断转化：
  - 经历会被抽象成知识；
  - 知识会进一步内化成技能；
  - 技能又会指导新的行动，产生新的经历。
- 作者把这个过程概括为一个循环：
  - **经历 → 知识 → 技能 → 新的经历**

#### 2. Claude Code 如何对应这三类记忆

- Claude Code 在**情境记忆**上，做法是把每一轮对话以**`jsonl`格式**保存下来，用来记录发生过什么。
- 同时，它在对话过程中还有**SessionMemory**做实时蒸馏，相当于一边对话、一边整理重点，避免信息完全散落。
- 在**语义记忆**上，每轮对话结束后，会 fork 一个子 Agent —— **`extractMemories`**：
  - 提取值得长期保留的内容；
  - 写入带**YAML 头的 Markdown 文件**。
- 这一步的本质，是把零散的对话压缩成之后还能复用的知识，这和人类把经历总结成经验很像。
- 更进一步，Claude Code 还有一个**autoDream**机制：
  - 在后台对记忆做整合、修剪、合并、更新；
  - 类似于人类记忆里的 “巩固” 过程。
- 也就是说，Claude Code 不只是 “存对话”，还在尝试做 “整理” 和 “长期沉淀”。

#### 3. Claude Code 一个比较特别的点：做了程序化记忆

- 作者认为，很多记忆框架并没有真正实现**程序化记忆**，但 Claude Code 做了。
- 它有一种**feedback**类型的记忆，记录的不只是 “不要做什么”，还包括 “什么做法是对的”：
  - **负反馈**：用户指出错误、纠正行为；
  - **正反馈**：用户确认某种做法有效、合理。
- 这一点很关键，因为很多系统只记 “踩坑”，容易让 Agent 越学越保守，最后变得不敢行动。
- Claude Code 同时保存正反两类经验，相当于不只记 “禁区”，也记 “可行路径”，更接近真正的技能学习。
- 可以简单理解为：
  - 不是只告诉 AI “别这样做”；
  - 还会告诉它 “这样做是对的，下次可以继续用”。

#### 4. 和专业记忆框架相比，Claude Code 仍然明显偏弱

- 作者把 Claude Code 和**LangMem、Mem0、Zep、EverMemOS、MemOS**等框架做对比，结论是：Claude Code 的记忆能力并不强，甚至 “像个菜鸡”。
- 它主要有几个明显短板：
  - **不支持语义化召回**：不是靠向量检索找相关记忆，而是用 LLM 扫 metadata 来代替。
  - **召回上限较低**：最多只看**200 个文件**。
  - **遗忘 / 整合策略比较粗糙**：大致是**24 小时**或**5 轮对话**触发一次整合。
  - **缺少关联网络**：记忆更像一个个孤立文件，而不是相互连接的知识图谱。
- 换句话说，Claude Code 更像 “够用就行” 的记忆系统，而不是追求精细化、全量化管理的体系。

#### 5. 为什么 Claude Code 没走 “全量记忆” 路线

- 作者指出，如果真要做到 EverMemOS、MemOS 那种 “全量记忆”，工程复杂度会迅速上升。
- 以**EverMemOS**为例，基础设施就包括：
  - **MongoDB**
  - **Elasticsearch**
  - **Milvus**
  - **Redis**
- 还不算其他附带依赖，整体系统会很重。
- 因此，这类框架更适合做**个人长期记忆管理**，而不一定适合像 Claude Code 这样强调即时执行和问题求解的场景。
- 作者的意思是：Claude Code 不是做不到更复杂，而是它选择了另一条更轻、更偏执行的路线。

#### 6. OpenClaw 提供了另一种记忆思路：重点不是 “记住”，而是 “何时使用”

- 作者还拿**OpenClaw**做了对比，认为它的记忆实现也很有代表性。
- OpenClaw 不追求全量保存，而是优先解决一个更实际的问题：
  - **记忆应该在什么时候被调用？**
- 它把记忆拆成三层：
  - **全局层**
  - **工作区层**
  - **任务层**
- 这样做的好处是逐层收敛，只在必要的时候把相关上下文拉进来，避免信息过载。
- 在 OpenClaw 的设计理念里：
  - 记忆本身不是最重要的资产；
  - **正确使用记忆的能力**才更重要。
- 所以它更强调临时重建一张适合当前任务的 “记忆网络”。

#### 7. 作者对 Claude Code 的最终判断：它更像一个会边做边修的工程师

- 从这个角度回看 Claude Code，作者认为它选择的是一条**更偏执行**的路线。
- 它不追求一开始就看清全貌，也不强依赖庞大的长期记忆体系。
- 它更像人类工程师调试问题的方式：
  - 一边看；
  - 一边改；
  - 一边跑；
  - 一边修正。
- 在这个过程中，Memory 的核心价值不是 “构建完美知识库”，而是作为一种**防遗忘机制**：
  - 保证关键上下文不会在多轮试错中丢失；
  - 让系统能在连续行动中逐步逼近答案。
- 这也是作者对 Claude Code 记忆设计的核心评价：**不一定最强，但非常贴合实际执行场景。**

#### 总结一句

Claude Code 的记忆系统并不属于 “最完整、最先进” 的那类方案，但它把情境、语义、程序化记忆串了起来，尤其重视在执行过程中保住关键上下文，因此更像一个 “会记重点、边干边学” 的工程型 Agent。
