Key Takeaways:  
Changing Developer Workflow (1:22 - 3:51): Coding agents like Claude Code have moved developers from manual, low-level implementation toward higher-level product strategy. The focus has shifted from writing every line of code to managing and refining outputs from increasingly capable models.  
The Rise of Proactive Agents (6:37 - 9:00): The introduction of Claude Tag marks a shift toward multiplayer, proactive agentic workflows in tools like Slack. It can monitor bugs, draft PRs, and retain team memory, currently landing over 65% of product PRs for the Anthropic team.  
Rethinking Software Engineering Norms (3:51 - 6:37): The speakers argue that traditional practices, such as avoiding rewrites or long-term waterfall planning, are becoming outdated. They emphasize the value of product sense, prototyping, and rapid iteration using high-quality test suites.  
Safety and Trust (30:57 - 37:53): A major portion of the discussion covers Auto Mode and safety. Anthropic has heavily invested in evals and red-teaming to mitigate risks like prompt injection and data exfiltration, making it the recommended way to handle long-running agentic tasks safely.  
Cultural Impact (38:13 - 41:50): The team encourages developers to be more ambitious and stop "negotiating against themselves." They suggest that because implementation is now cheaper, teams should focus on building the "bigger things" they previously thought were impossible or too resource-intensive.  
Future Outlook:  
Looking ahead, the speakers are excited about models becoming better interaction design partners (44:28) and continuing to bridge the gap between abstract ideas and production-ready software.

## 结构化（1）

### 2026-07-22 03:51:54

#### 文章精炼总结

Claude Code 团队认为，编码智能体正在把软件开发从“人工逐行实现”转向“人负责目标、判断与产品品味，AI负责大量执行和验证”。随着实现成本显著下降，团队需要重新思考重写、代码审查、安全机制和协作方式，并把精力投入到过去因成本过高而不敢尝试的更大目标上。

##### 1. 编码智能体改变了开发者的日常工作

- Claude Code 发布不到一年半，能力已从“需要开发者逐个确认权限、紧盯每一步”，发展到可以承接大量琐碎实现工作。
- 新一代模型 Claude Fable 已能一次性完成不少功能，开发者的主要工作逐渐变为：
  - 判断应该做什么；
  - 明确产品体验；
  - 检查和优化模型输出；
  - 提高项目的质量与 ambition（目标规模）。
- AI并没有让软件工程变得“毫无压力”，而是提高了可实现目标的上限：开发者可以做更大的项目，但也需要承担更多思考和决策工作。

##### 2. 产品判断力比手工实现能力更重要

- 传统流程往往是产品经理调研客户、跨团队讨论约半年，再写完整需求文档和技术方案，最后才开始编码。
- 现在，从想法到产品的周期可能由过去的 **6～12个月缩短到约1周**。
- 因此，工程师需要加强商业判断和产品品味，重点思考：
  - 什么真正值得做？
  - 什么能改善用户体验？
  - 什么能对业务产生实质影响？
- 但在基础设施等领域，细节正确性和工程执行力仍然非常重要。

##### 3. “不要重写系统”的旧经验正在失效

- 过去软件工程强调尽量避免重写，但在AI辅助开发下，重写的成本和风险明显下降。
- 前提是拥有高质量测试套件：团队可以根据现有代码和测试，同时生成多个新实现，再比较并选择最可靠的版本。
- 现有代码库本身也可以视为一份“可执行规格说明”，因为它往往是唯一完整记录所有分支逻辑的地方。
- 案例：团队已经把 **Bun相关实现重写为Rust版本**，并在内部实际使用。

##### 4. Claude Tag：从个人编码走向团队协作

Claude Tag 是运行在 Slack 等团队协作工具中的智能体，代表 Claude Code 从个人工具向“多人、主动式智能体”演进。

其核心特点包括：

1. **默认支持多人协作**：产品、设计和工程人员可以在同一会话中共同指导智能体完成PR。
2. **主动执行任务**：可以持续监控频道中的错误报告，自动修复、创建PR，并通知最近修改相关代码的工程师。
3. **团队记忆**：会记住频道内的规则与偏好，例如“处理宕机问题，但忽略普通警告”。
4. **连接公司上下文**：可搜索Slack、代码库和指标系统，回答发布时间、功能设计和业务数据等问题。

内部版本的 Claude Tag 已提交并合入 Anthropic 产品工程团队约 **65%的产品PR**。复杂且需要反复互动的任务仍更适合 Claude Code，Claude Tag 则更适合持续监控和后台主动执行。

##### 5. 用内部试用和真实留存决定优先级

- 当开发成本降低后，“应该做什么”反而成为最难的问题。
- Anthropic采用强烈的内部试用（dogfooding）文化：
  - 员工每天使用自己的产品；
  - 遇到产品不支持的需求时，优先改进产品，而不是绕开它；
  - 正式发布前先交给内部员工和早期客户使用，并鼓励尖锐反馈。
- 功能必须达到明确的活跃度和留存标准才能公开发布；如果体验不够完善，用户会流失，也意味着功能不应上线。

**意外成功案例：远程控制**

团队最初并不完全理解远程控制功能的价值，但上线后发现大量用户会让笔记本持续运行 Claude Code，再通过手机在沙发等更舒适的环境中控制本地会话，因此团队开始进一步强化这一使用方式。

##### 6. 代码审查正逐步自动化

- 核心模块仍设置代码负责人，涉及系统提示词等关键区域的修改必须由人工批准。
- 外围代码越来越多地交由 Claude Code Review 自动审查，同时结合：
  - 自动化测试；
  - CI/CD；
  - 可控测试环境；
  - 用于解释复杂PR的辅助文档或演示。
- 团队用了 **6个月以上**逐步建立信任，而不是立刻移除人工审核。
- 每次事故后，团队都会：
  1. 找到导致事故的PR；
  2. 更新自动审查规则；
  3. 将该PR加入评测集；
  4. 确保未来版本不会在同类问题上退化。
- 只有当自动审查在特定文件范围内持续捕获全部已知问题时，团队才会考虑取消人工审核。

##### 7. 用评测体系建立对新模型的信任

- 新模型不能只凭主观体验上线，而要运行完整评测集，并确认其表现严格优于上一代模型。
- Anthropic同时使用：
  - 公司级通用评测；
  - Claude Code团队的产品专项评测；
  - 外部测试人员和红队构造的恶意环境。
- 评测首先关注能力，例如模型能否在拿到任务描述和完整代码库后：
  - 正确修改代码；
  - 修复缺陷；
  - 通过全部测试。
- 其次关注用户体验行为，例如避免：
  - 任务未完成就问“是否继续”；
  - 无故提示用户该休息或睡觉；
  - 执行两步就提前停止。
- 用户反馈会被转化为新的评测项目，从而不断扩大覆盖范围。

##### 8. 前沿模型需要更少、更柔和的提示词

- 针对 Opus 4.8、Fable 等前沿模型，Claude Code的系统提示词长度减少了约 **80%**。
- 团队发现，旧提示词常常过度约束模型：
  - 太多示例会限制模型创造性；
  - 太多“禁止做什么”可能与用户指令冲突；
  - “永远验证”“必须执行”等绝对规则通常存在例外。
- 新方法倾向于：
  - 提供充分上下文；
  - 减少硬性命令；
  - 让模型根据任务规模和风险作判断。
- 例如，重大前端改动通常应运行应用并检查体验，但仅修改一处文案时，不一定需要完整验证流程。
- 不同能力的模型仍使用不同系统提示词；较旧模型保留更详细的指令，只有前沿模型能够依赖自身判断力。

##### 9. 工具设计强调“少而通用”

- 团队倾向于减少工具数量，避免功能重叠，让模型更容易判断何时调用哪个工具。
- 一些专用搜索工具已被移除，改由模型使用 Bash 等通用能力完成。
- 文件编辑工具之所以保留，主要是为了给新用户提供清晰的可视化确认界面，而不一定是模型本身必须依赖它。
- 总体而言，工具设计既需要评测，也高度依赖内部实际使用，更像一门需要持续观察和调整的“生物学”，而非完全确定的“物理学”。

##### 10. Auto Mode：长时间任务的安全执行方式

- Anthropic内部几乎所有人都使用 Auto Mode，并将其视为执行长期智能体任务时比“完全放开权限的YOLO模式”更安全的选择。
- Auto Mode会在每次工具或Bash调用时，由分类模型结合以下信息判断是否允许：
  - 用户当前指令；
  - 完整对话上下文；
  - 工具调用内容；
  - 沙箱和网络访问需求。
- 例如，用户明确要求“推送到GitHub”时可允许 `git push`；如果用户说“不要推送”，即使Claude主动尝试，也会被拦截。
- 团队已投入：
  - **数千项安全评测**；
  - 多轮外部红队测试；
  - 针对提示注入、数据外泄和恶意输入的对抗环境。
- 团队强调它并非能拦截 **100%** 的风险，但在主要风险类别上，出错概率已低于普通人工权限审核。
- Auto Mode从当年 **1月起**就在Anthropic内部使用，并经过持续加固。

其他安全机制还包括：

- 为 Claude Tag 设置独立身份和凭证，方便审计；
- 仅允许可信设备进行远程控制；
- 使用“凭证注入”：智能体能调用 Datadog 等服务，但无法直接读取真实密钥，真实凭证只在请求发出时由代理注入。

##### 11. 人的价值转向更高目标与跨职能判断

- 如果开发者只做过去同样的工作，而这些工作如今只需一句提示词，确实可能产生失落感。
- 团队认为解决方式不是与AI竞争手工实现，而是提高目标：
  - 尝试过去做不起的系统重写；
  - 建造更复杂的产品；
  - 提高质量标准；
  - 更快验证大胆想法。
- 产品经理的角色也变得更加综合，往往同时承担工程、设计和项目协调工作；发现缺口后，可以先用Claude做原型，再邀请专业人员完善。

##### 12. Claude令人意外的用途与当前局限

**视频编辑案例**

Thariq把演讲视频、幻灯片录像、音频和HTML版演示文稿交给 Fable，仅用一次详细提示，就让它：

- 转录完整视频；
- 识别幻灯片录像中的自动更新弹窗；
- 放弃有问题的录像，改为直接渲染HTML幻灯片；
- 动态追踪并裁剪演讲者在舞台上的位置；
- 自动组合画面、字幕、动画和图形；
- 调用 FFmpeg、Remotion 等工具完成编辑。

最终结果已经接近可直接发布的质量。

**仍然不足的地方**

- 视觉设计与用户体验“品味”还不够好；
- 能按详细规格实现功能，但间距、布局和交互往往不够精致；
- 容易沿用现有应用的常见设计模式，尚未成为真正优秀的前沿AI交互设计伙伴；
- 与现实世界、科学实验和复杂物理任务的结合仍有很大提升空间。

##### 13. 值得借鉴的文化与个人项目

Anthropic建议其他团队借鉴两点：

1. **尽量公开信息**：Claude Tag在公开频道中能获取更多上下文，从而提高回答和执行准确率。
2. **不要提前替自己否定方案**：不要仅凭直觉假设“成本太高”或“必然存在取舍”，应先尝试大胆方案，让真实限制通过实践显现。

团队成员还分享了用Claude完成的趣味项目：

- 制作以自己和朋友为角色的 **2D《街头霸王》式游戏**，由Claude调用图像或视频模型生成精灵动画，并自动判断帧质量和碰撞箱。
- 为攀岩伙伴制作定制应用，记录攀岩项目，并根据成员所在地、直飞航班、难度等级、住宿和停车点到岩壁的步行距离，自动规划攀岩旅行。

##### 14. 观众问答：评测工具与记忆机制

- 对于评测工具，团队认为主要瓶颈并非缺少平台，而是用户很难构建真正高质量的评测数据；未来更值得投入的是总结和分享评测方法。
- Claude Tag目前采用**频道级共享记忆**：
  - 每个频道中的Claude共享同一份记忆；
  - 单次会话可以把重要信息写回主记忆；
  - 当前实现形式是每个频道对应一个 **Markdown文件**。
- 团队仍在持续研究更可扩展的记忆架构和实验方案。

## 细节还原（1）

### 2026-07-28 06:21:03

#### 从逐行盯着权限提示，到代理提交65%的产品PR

Claude Code在不到一年半的时间里，从Claude Sonnet 3.7发布时的一个功能条目，逐渐变成Anthropic内部重组软件开发流程的核心工具。Cat Wu、Thariq Shihipar与主持人Simon Willison沿着这段变化，讲到Fable带来的能力跃迁、Claude Tag进入团队协作、代码审查与安全机制如何建立，以及开发者为什么必须重新调整自己的 ambition。

##### Fable上线之际，开发者已经从“逐步监督”退到了更高一层

访谈开始前约一分半钟，Simon Willison发现Fable重新对他开放了。他开玩笑说，在场的人如果想立刻离开去消耗Fable额度，他也不会介意，但随后把话题拉回Claude Code本身：这款产品在上一年2月发布，当时只是Claude Sonnet 3.7发布内容中的一个条目，至今还不到一年半。

Cat Wu回忆，Claude Code与Sonnet 3.7刚推出时，使用者必须密切盯住它的每一步操作。她会非常仔细地阅读每一个权限提示，经常拒绝，并反复追问它有没有检查某个文件、有没有漏看另一处内容。随着模型一代代提升，团队才逐渐能够后退一步，把琐碎的实现工作交给Claude，把自己的时间放到更有创造性的判断上：既然Claude Code已经可以完成大量实现，那么真正需要人思考的，就变成了应该为用户提供什么样的体验。

Fable又带来一次更明显的跃迁。Cat观察到，许多功能现在可以一次提示直接完成，也就是所谓的“oneshot”。Thariq对这种变化有更个人化的记忆：Opus 4刚出来时，一位好友发消息让他试试Claude Code，他试完后的第一反应是，自己现在得去Anthropic工作了。可即使在Opus 4时期，用户仍要不断处理权限提示；后来Auto Mode变得如此自然，以至于他已经很难回忆起过去反复点击“允许”的日子。

能力提高以后，工作并没有简单变轻松。Thariq要求自己做出比以往更高质量的成果，例如用Claude编辑视频时，成品必须在几小时内达到Anthropic品牌团队的严格要求，否则这项工作就不值得做。Simon也有类似感受：软件工程反而变得更难了，因为工具能够支撑的项目规模扩大后，开发者对自己的预期也提高了。过去不敢接的工作现在可以接，但人的任务变成了更密集、更疲惫的思考。

##### 六个月的规格文档让位于一周原型，连“不要重写”也不再是铁律

Cat认为，变化最明显的并不只是写代码的速度，而是工程师所需能力的重心。两年前，一种典型流程是：产品经理先访问客户，再花六个月与跨职能团队达成一致，写出完整的产品需求文档和详细实现方案，之后第一行代码才会出现。如今，从产生想法到把东西做出来，时间可能已经从六到十二个月缩短为一周。

这使产品判断和商业判断变得更重要。实现成本下降以后，团队面对的关键问题不再只是“能不能做出来”，而是“什么值得做”“什么会真正改变业务”。Cat因此建议工程师主动培养产品品味与商业意识。她也保留了一个边界：基础设施工作依旧非常依赖严密执行，细节不能因为代理能力提高而被忽略。

Thariq提出的变化更直接：过去被视为危险的软件重写，现在可能是一件好事。传统工程经验常说不要重写系统，但他现在支持重写，前提是项目有一套可靠的测试。重写甚至会反过来迫使团队补齐测试，因为原有代码库本身就是一份规格，有时还是唯一完整的规格——没有任何一个人能记得代码库中所有分支与行为，但代理可以把代码库当作现成的行为描述，从中提炼出新的实现。

Anthropic内部已经把Bun用Rust重写，新版本也在实际运行。Simon进一步描述了代理时代的另一种做法：先建立高质量测试，再并行生成三种实现，最后选择最准确的一种。原型制作也变得极其便宜，他甚至会在参加会议时直接用手机做出一个原型，等有空时再接着推进。过去“重写浪费成本”“原型需要专门安排时间”这样的经验，并没有完全失效，但它们背后的成本结构已经改变了。

##### Claude Tag进入Slack后，代理开始主动接活并记住整个团队的偏好

如果说Claude Code主要改变个人与代理的协作，Claude Tag则被Anthropic视为它面向团队的延伸。它最先被放进Slack，有三个重要特征。

首先，它默认是多人协作的。Claude Tag进入一个频道后，最初提出需求的人、同事、设计师和工程师都能在同一会话中补充意见，共同推动一个PR。其次，它不是等人每次点名才工作，而是可以持续执行规则。例如，团队可以要求它监控频道里的每一条错误报告，自动提交修复PR，再找到最后修改过相关代码的工程师并标记对方。这个要求一旦设置，就会在频道生命周期内持续生效。第三，它拥有团队记忆。如果团队告诉它，只需要调查服务中断，不必处理普通警告，它会用自然语言记住这一偏好，并在以后为频道里的所有成员继续执行。

Anthropic内部版本的Claude Tag，当时已经提交了产品工程团队65%的产品PR。Cat强调，这不是Claude Code被完全取代：最复杂、需要人与代理反复迭代的任务，仍适合在Claude Code中完成；Claude Tag更适合主动、异步地处理不断出现的错误和常规任务，不再要求工程师为每个问题手动启动一个Claude Code会话。

它也不只用于编码。访谈开始前，团队曾直接问Claude Tag，Fable到底什么时候发布。它会搜索公司Slack，整理谁说过什么。作为企业内部搜索引擎，它已经掌握大量产品上下文；连接事件数据仓库后，还能回答指标问题。营销团队也可以询问某个功能的工作方式。即使提问者不写代码，Claude Tag仍能克隆代码库，理解功能，展示功能界面，甚至生成一段实际操作录屏。

一个功能从想法进入生产，也可以在同一会话中连续流动。Cat举例说，她可能先在协作工具里提出一个新功能，让Claude Tag完成第一版，再要求它分享最终实现的录屏；随后设计师进入同一会话调整，最后工程师把它推到生产环境。团队还没有完全解决多人共同控制同一个代理会话时的所有社会协作问题，但成员会观察同事如何使用Claude，并逐渐形成规范。Thariq发现，公开使用也有培训作用：当所有人都能看到别人怎样指挥代理时，整个团队的使用水平会一起提高，人也会更在意自己公开提交的工作质量。

实现变便宜以后，优先级反而更难判断。Anthropic的办法之一是高强度“dogfooding”，也就是每天使用自己做的产品。内部人员遇到产品暂时不支持的需求时，不急着寻找替代方案，而是直接修产品，让它支持这个需求。产品对外发布前，会先提供给Anthropic内部人员和一批早期客户，团队希望收到尽可能坦率、甚至残酷的反馈，再持续迭代。

他们还设置了明确的内部门槛：功能必须达到一定的活跃用户数和留存水平，才会对外发布。工程师因此知道自己需要达到什么指标。如果一个功能不够完善，用户会流失，那么这项功能就不应该发布。

远程控制就是一次出乎Cat预料的验证。它允许用户用手机或浏览器连接本地CLI中运行的Claude Code会话。Cat自己通常直接在手机上发起云端任务，不依赖本地环境，因此最初不理解这个功能，甚至认为大家应该搭建远程开发环境。但上线之后，许多人形成了一套具体习惯：晚上给笔记本接上电源，打开多个远程控制会话，锁住屏幕，再躺到沙发上用手机继续控制Claude Code。实际使用量改变了她的判断，团队也开始继续强化这条工作流。

##### 代码审查从人工把关开始，再用事故和评测一点点扩大自动化边界

Claude生成越来越多代码后，代码审查不能简单取消。Anthropic根据代码的重要程度分层处理：系统提示词和产品核心区域都有明确的代码所有者，相关PR必须获得负责人批准；每个PR还会经过自动代码审查。面对复杂改动，提交者可能额外制作一个解释性材料，帮助其他人理解PR。团队同时大量投资于测试、CI/CD和可供Claude操作的验证环境，让Claude Code能够测试Claude Code本身。

目标虽然是尽量减少人工介入，但核心区域仍保留人工代码所有者。外围改动则越来越多地交给Claude Code Review完整审查。这并非一夜之间完成，而是经历了六个多月的积累。最初所有代码都由人审查；当团队确认自动审查对某些文件中的问题能够做到全部捕获后，才逐步取消这些区域的人工检查。

每次发生事故，团队还会回看导致事故的PR，研究代码审查为什么没有拦住它，再更新审查规则。同时，这些PR会被加入评测集，以确保未来调整代码审查系统时，不会重新失去这种识别能力。Cat承认，把人移出代码审查循环听起来很可怕，但真正提供信心的不是一句“模型很强”，而是几个月持续建设的验证基础设施。

同一套评测思想也用于新模型替换。新模型到来时，团队会运行完整评测集，确认Fable在相关任务上严格优于Opus 4.8，才把它接入产品。评测既有Anthropic层面的，也有Claude Code团队自己的。基础目标是能力：给模型完整任务说明和整个代码库，它能否作出正确决定、修复错误并通过所有测试。

但能力并不等于体验。团队还在建立行为评测，因为用户会被一些看似小的行为激怒。例如，Claude Code工作一段时间后说“该睡觉了”，或者完成五项任务中的两项后停下来询问是否继续，都会破坏使用体验。团队会根据用户反馈给这些问题排序，再逐项建立评测。覆盖率还没有达到100%，但每个真实反馈都可能成为新的长期检查项。

Fable和Opus 4.8还促使Claude Code的系统提示词缩短约80%，不过这只适用于最前沿模型，旧模型仍使用较完整的版本。团队发现，较早的模型需要很多例子，而新模型可能会被例子限制；删除例子之后，它反而能提出比示例更好的做法。提示方式也从大量“不要做什么”的硬约束，转向提供更丰富的上下文和更少但更准确的指令。

Cat用“始终验证前端改动”说明了硬规则的问题。这条规则大约90%的时候正确，但如果用户只是要求把一个字符串替换成另一个字符串并更新测试，强制运行完整验证可能并不合适。团队一度想把规则改成“较大的用户体验改动才运行本地应用”，但马上又遇到新的问题：什么才算“大”？模型也可能希望检查小改动。她因此建议，写提示词时要考虑一个善意的人可能怎样误解它，尽量把规则软化到在所有情境中都准确，因为系统提示会在100%的会话中出现。

这实际上是在依赖前沿模型的判断力。一年前的模型未必能判断何时需要验证，如今Fable与Opus级别的模型开始能够承担这部分判断。大型模型有时还会比小模型更节省总token，因为困难任务如果交给小模型，可能需要更长的反复尝试。团队因此不再假定“小任务就一定应该使用便宜模型”。

模型也开始为其他模型写提示词。工作流功能中，Claude不仅会提示单个子代理，还会为多个子代理设计编排方式，给每一个代理生成详细任务说明。Thariq甚至会把Gemini API交给Claude，让Claude替他提示图像模型，因为Claude写图像提示比他本人更勤快。Simon据此提出，Claude Code的系统提示词和工具提示本身就是产品文档，希望Anthropic公开这些内容及其版本差异，Thariq答应记录这个功能请求。

工具设计则朝着更少、更通用的方向发展。Thariq曾加入“询问用户”工具，让Claude在需要时向用户提问，但这种工具很难单纯依靠评测判断好坏，也涉及用户偏好。团队后来删除了专门的grep和glob搜索工具，让Claude直接使用原生Bash能力。

文件编辑工具仍然保留，主要原因不只是模型能力，而是用户界面。Claude调用专门工具时，产品能够确定它正在修改文件，进而展示清晰的差异界面，询问用户是否批准。新用户很依赖这种可见性。对于长期使用Auto Mode的人，这个专门工具可能已经没有必要，但为了保留易理解的交互体验，团队没有立即删除它。

##### Auto Mode用分类器、沙箱和凭证代理，为长时间运行的代理划出边界

Simon长期关注提示词注入。他知道，一旦外部内容能够告诉Claude Code做什么，就可能造成严重后果，但他仍经常使用风险更高的YOLO模式，并因此感到不安。访谈时，他说自己大约从三周前开始把Auto Mode设为默认，只是还不够了解它的安全边界。

Cat给出的建议非常明确：Anthropic内部几乎所有人都使用Auto Mode，它是让Claude Code安全执行长时间任务的推荐方式。团队已经进行了大量高强度测试，建立数千项评测，还委托多个外部红队构造含有提示词注入和恶意输入的环境，尝试诱导Claude Code执行危险操作。他们针对发现的问题逐一缓解，并计划公开相关评测。

她同时收回了可能过强的表述：Auto Mode并不能捕获100%的问题，任何安全系统都不该作出这种保证。但在团队最关心的提示词注入、数据外泄等主要风险类别上，它的风险已经远低于一般人工审查者。

Auto Mode的核心并不是静态的允许或拒绝列表。Claude每次执行一个轮次或Bash调用时，会有一个Sonnet分类器同时检查工具调用、会话上下文和用户指令。权限判断因此会随任务变化。如果用户明确要求把代码推送到GitHub，系统可以允许`git push`；如果用户明确说不要推送，即使Claude因为积极主动而尝试操作，Auto Mode也会拦截并提示出来。

它还与沙箱协同。沙箱本身有很多边缘情况，难以完全通过确定性规则覆盖。当某个操作需要越过沙箱，例如发起网络请求时，Auto Mode会判断这个请求是否符合当前任务，再决定是否允许。用户原本会看到的权限提示，基本都进入了这套判断过程。

Anthropic从当年1月起就在内部使用Auto Mode，并与公司的对齐和安全防护团队共同加固。它也是Claude Tag能够在Slack中运行的基础。Slack机器人会读取反馈频道和员工消息，攻击面比个人编码会话更宽；Thariq因此直言，很多团队不应该轻易自己制作AI Slack机器人，因为其中存在大量注入路径。Claude Tag依靠Auto Mode、模型训练和其他多层防御共同降低风险，而不是只依赖一道防线。

团队还让Claude Tag能够使用独立身份与凭证，不必冒充具体员工。这使它的行为更容易审计。远程控制支持可信设备，远程环境则支持动态凭证注入。比如，Claude Code需要访问Datadog时，代理本身不必持有真实Datadog凭证；它发起请求后，系统才在代理不可见的情况下即时插入凭证。Simon把它理解为一种代理替换模式：代码使用占位token请求指定API，代理服务器在最后一刻换成真正的token。他认为这种做法明显合理，并已经在越来越多系统中看到。

##### 当实现工作被模型接走，人的补偿方式不是怀旧，而是提高目标

工具能力迅速提高，也让一些开发者感到失落：曾被视为专业核心的实现工作，正越来越多地由模型完成。Thariq承认这种感受真实存在。如果一个人只想继续完成LLM出现以前的同一份工作，而那份工作现在只需要写一个提示，确实容易产生空洞感。

他的应对方式是提高目标。Cat、Ken和Boris经常提醒团队，Anthropic增长很快，他们必须站在能力边缘，做出自己最好的工作。当一件事推进得很慢时，Thariq会问自己能不能更快、能不能更有野心，而答案经常是再次尝试Claude，因为即使上一次尝试失败，也可能只是当时使用的模型较旧。

他以Jared为例：Jared曾在奥克兰的公寓里手写大量Zig代码，用约一年时间完成工作，几乎不出门，也从中获得乐趣。现在，Jared又用Rust重写整个Bun，同样做得很投入。实现手段发生变化后，他没有重复过去的任务，而是选择了规模更大的挑战。Thariq认为，人们通常都有一些一直想做、想学、想变得更好的事情，现在的回答可以更直接：“那就做吧。”

Cat描述的产品工作也不再有稳定边界。团队里的产品人员同时承担工程、设计和产品职责，哪里存在从好想法到用户交付之间的缺口，就去填哪里。如果一个想法没有激发工程师去做，产品人员就先把它做出来，放进notebook，用原型推动别人把它生产化；如果设计看起来不对，就参考一个类似页面先做第一版，再找注重细节的人补齐；如果公司内部需要知道Claude Code、Claude Tag和Co-work即将发布什么，就自动整理整个发布日历，异步收集状态，避免反复打扰同事，再把精炼、完整的更新发送到三个内部公告频道。

这种工作方式的核心不是“产品经理也写代码”，而是持续寻找当前最大的交付缺口，然后尽可能自动化解决。

Fable编辑会议视频的案例，把这种能力表现得最具体。Thariq在ACM Agentic会议做完演讲后，想把视频交给传播团队，但主办方迟迟没有剪完。他索要原始材料，对方发来三份内容：自己在台上讲话的视频、演示文稿画面以及音频文件，并对他说“祝你好运”。

Thariq把这些文件连同HTML版演示文稿一起交给Fable，只用一次较完整的提示要求它剪成成片。Fable先转录整段视频，随后发现录制的幻灯片画面有问题，中途出现过自动更新弹窗。它没有继续使用这条画面，而是判断演讲进行到哪一页，再直接调用HTML源展示对应幻灯片。

舞台视频中，Thariq只占画面很小一部分，而且讲话时不断走动。Fable便动态裁切画面，持续跟踪他在舞台上的位置，再把人物、幻灯片和字幕组合起来。之后他要求增加一些动画和图形，Fable继续使用FFmpeg和Remotion等工具完成。这个结果已经接近可以直接发布，而且基本来自一次提示。

不过，Cat仍然不满意模型的设计与用户体验品味。详细说明一个功能怎样运行时，Fable通常可以照做，但边距可能不对，界面也还不够令人愉悦。它倾向于依赖现有应用的设计惯例，而前沿AI产品仍有大量全新交互方式没有被发明。Simon把这种同质感称为“Opus审美”：有时看一眼界面，就知道它是Opus设计的。Cat希望未来模型不仅执行设计规格，还能成为交互设计的思考伙伴。

Thariq则希望Claude更多进入真实世界，例如编排实验、解决科学问题，而不是把能力限制在编码活动中。现场有人提到刚推出的Claude Science，他说明那是合作团队负责的产品，自己并不了解具体情况。

##### “不要和自己讨价还价”，再把省下来的能力用来做荒诞项目

谈到Anthropic有哪些值得其他公司借鉴的文化习惯，Cat首先提到公开信息。Claude Tag在公开频道中效果最好，因为它能够搜索所有有权限访问的公开频道，获得更多上下文，进而提高答案准确率。如果公司的讨论大量锁在私密空间中，它的团队记忆和搜索能力都会受到限制。

Thariq强调的则是一句联合创始人常说的话：“We don’t negotiate against ourselves.”也就是不要在行动前先和自己讨价还价。人很容易在脑中想象各种权衡，再据此劝退自己；Anthropic更倾向于先问：“如果我们就是去做呢？”如果某种权衡真的存在，就应要求它通过事实显现，而不是因为听起来合理，就提前把雄心削掉。

这对有25年软件经验的Simon形成了明显冲击。他过去形成的直觉是，默认答案应该是“不”，因为一切都有成本，一切都是权衡。如今，实现成本的变化迫使他重新审视这些直觉。

两位嘉宾最后分别分享了一个因为Claude而得以动手的“荒诞项目”。Thariq正在做一款《街头霸王》式的2D格斗游戏，自己和朋友都是游戏角色。Claude Code负责提示Gemini和Seedance一类模型生成视频动画，还能逐帧检查动画质量。角色使用类似《街头霸王2》的2D精灵图，Claude不仅能生成动作，还能判断拳头位于什么位置，并直接画出JSON格式的碰撞框。Thariq还不确定会不会公开游戏，但答应至少可以展示截图。

Cat的项目更贴近日常。她喜欢攀岩，朋友们也经常一起攀岩，于是他们用Claude Code做了一款小应用，记录每个人正在挑战的攀岩项目。Claude Workflows还被用来做旅行研究和安排团队外出活动：寻找能容纳所有人的场地，研究各个攀岩目的地，检查是否有从所有成员所在地出发的直飞航班，再到Mountain Project筛选符合大家难度等级的路线，并寻找Airbnb。

Cat不喜欢徒步，因此“从停车地点到岩壁的接近路线必须很短”也是重要条件。Claude会把这一偏好加入筛选。过去她需要在Mountain Project中逐页点击，如今只需输入所有人的需求，就能得到一个为他们定制的应用。Simon把它形容为“给攀岩做了一个氛围编程版Jira”，Cat表示正是如此。

观众最后追问了两个仍未解决的问题。有人询问Anthropic是否会提供评测数据集和代理可观测性工具。Cat说团队考虑过，但真正的限制通常不是工具，而是客户需要花很长时间才能建立高质量评测。如何设计优秀评测，本身是一种稀缺技能；Anthropic会继续内部投入，也希望将最佳实践对外分享。

另一个问题聚焦Claude Tag的记忆。Thariq解释，当前记忆按频道划分：每个频道中的Claude共享一份主记忆，各个实例拥有自己的会话，会话内容又可以回写主记忆。具体实现暂时很简单，就是每个频道对应一个Markdown文件。团队一直在做记忆实验，因为记忆怎样组织、哪些内容应当保留，结果往往并不符合直觉。它还远不是一个已经定型的问题。

## 口播总结（1）

### 2026-08-03 00:59:37

#### Claude Code、Claude Tag，以及 Anthropic 如何重塑软件开发

这场对谈的核心是：随着编程智能体越来越强，软件开发正在从“人亲手写每一行代码”，转向“人决定该做什么，再让智能体完成和验证实现”。你将听到这种变化如何影响产品规划、团队协作、代码审查、安全机制，以及开发者对自身角色的理解。

##### 首先，开发者正在从写代码，转向做判断

最明显的变化是，开发者不再需要紧盯智能体的每一步操作，而是可以把更多具体实现交给模型。

Claude Code 是 Anthropic 推出的编程智能体。它不只是回答编程问题，还能读取代码、修改文件、运行命令和测试，并持续完成一个相对完整的任务。产品刚推出时，使用者往往要仔细检查每一次权限请求，不断提醒它查看某个文件，或者纠正它的行动方向。

但随着模型升级，人的位置逐渐后移。开发者开始把重复、琐碎的实现工作交给 Claude，把精力放在更重要的问题上，比如用户真正需要什么，产品体验应该怎样设计，以及什么功能最值得做。

到了 Fable 这一代模型，团队发现，不少功能已经可以“一次完成”。也就是说，给出一个足够清楚的任务后，模型可能一次就做出接近可用的结果。

不过，这并不意味着软件工程变简单了。恰恰相反，工具提高了开发者对自己的要求。以前因为时间和人力有限，很多想法不会进入实施阶段。现在实现成本下降，团队反而要追求更高质量、更大范围的成果。真正费力的部分，越来越不是敲代码，而是思考和判断。

##### 接下来，产品判断力正在变得比手工实现更重要

第二个变化是，软件开发的重心从执行能力，转向产品判断力和商业判断力。

过去，一个产品经理可能先访谈客户，再花几个月协调团队、撰写需求文档和技术方案，最后才开始写第一行代码。现在，从想法到原型的时间，可能从半年甚至一年，缩短到一周。

这意味着，工程师也需要回答过去更偏向产品经理的问题：这个功能到底值不值得做？它能不能真正改善用户体验？它对业务有什么影响？

当然，在基础设施等对稳定性要求很高的领域，细节执行仍然非常重要。但在大多数产品开发中，原型制作和快速迭代的成本已经显著降低。团队可以先做出东西，再通过真实反馈判断方向，而不是在动手之前进行漫长规划。

一个很有代表性的观点是，过去被视为危险的“重写”，现在可能重新变得合理。传统软件工程强调不要轻易重写系统，因为重写成本高，还容易遗漏原有逻辑。但如果项目拥有高质量测试，智能体就可以根据现有代码和测试快速生成多个新版本，再由团队比较哪一种实现最准确。

原有代码库本身也可以被看作一份规格说明。它保存了大量没有写进文档的分支逻辑和实际行为。模型可以读取这份“活的规格”，帮助团队提炼、迁移甚至重写系统。对谈中提到，团队内部已经尝试用 Rust 语言重写 Bun 的相关实现，并实际投入使用。

所以，新的开发方式不是盲目重写，而是依靠完善测试，把重写变成一种可验证、可比较的工程选择。

##### 然后，Claude Tag 把个人智能体变成了团队成员

如果说 Claude Code 主要服务于个人开发者，那么 Claude Tag 的重点就是多人协作。

Claude Tag 是一个生活在 Slack 等团队协作工具里的智能体。它有三个关键特点。

第一，它默认支持多人参与。同一个 Slack 频道里的产品、设计和工程人员，都可以接着同一次任务继续交流和修改。

第二，它可以主动工作。团队可以告诉它：“持续监控这个频道里的错误报告，发现问题后起草一个代码修改请求，再通知最后改过相关代码的工程师。”之后，它会一直执行这条规则，不需要每次都有人重新启动。

第三，它拥有团队记忆。比如团队可以告诉它，只处理系统故障，不处理一般警告。它会在这个频道之后的任务中继续遵守这一偏好。

这里的“PR”，也就是 Pull Request，可以理解为一份等待审核和合并的代码修改申请。Anthropic 表示，内部版本的 Claude Tag 已经完成并合并了产品工程团队大约百分之六十五的 PR。这个数字意味着，它已经不只是一个偶尔使用的辅助工具，而是参与了团队大部分日常代码变更。

两种工具的分工也比较清楚。复杂任务仍然适合在 Claude Code 中，由人和智能体反复讨论、互动调整。Claude Tag 则更适合后台持续工作，比如处理错误报告、搜索公司内部信息、查询产品指标，或者帮助市场团队理解一个功能。

实际协作时，产品人员可以先让 Claude Tag 做出第一版，再让它录制演示。设计人员接着提出修改意见，最后由工程师完成上线。这种公开协作还有一个额外作用：团队成员可以观察别人如何使用智能体，学习更好的提问和工作方式。

##### 更重要的是，功能优先级仍然要靠真实使用来决定

当开发功能变便宜以后，最困难的问题并没有消失，只是从“能不能做”变成了“应该先做什么”。

Anthropic 的做法是高度强调内部试用，也就是常说的“dog-fooding”。这个词指的是，一家公司先让自己人每天使用自己的产品。如果团队想完成某件事，却发现产品不支持，他们不会立刻绕开，而是优先把产品补好。

新功能会先在 Anthropic 内部和部分早期客户中推出。团队希望得到尽可能直接、甚至尖锐的反馈，然后持续修改，直到用户真的愿意长期使用。

他们还会观察活跃用户数和留存率。留存率可以简单理解为，用户试过之后是否还会继续回来。如果一个功能不够顺畅，用户很快就会放弃，这通常说明它还不适合公开发布。

远程控制就是一个出乎预料的案例。这个功能允许用户通过手机或浏览器，连接本地命令行里正在运行的 Claude Code。最初，部分产品人员并不理解它的必要性，认为用户直接在云端启动任务就可以了。

但功能推出后，许多人会在晚上给笔记本电脑接上电源，让多个本地任务继续运行，再坐在沙发上用手机远程控制。真实使用证明，这不是一个小众需求，而是一种非常自然的新工作方式。于是团队开始进一步投入。

这个案例说明，即使开发成本下降，团队也不能只靠想象判断功能价值。真正的优先级，仍然要从使用行为中产生。

##### 代码审查正在自动化，但信任必须逐步建立

接下来是质量控制。核心结论是，Anthropic 希望减少人工审查，但不会一次性把控制权全部交给模型。

对系统核心部分，他们仍然设置“代码负责人”。代码负责人对某一关键区域的质量负责，任何涉及这些部分的修改，都必须得到他们批准。

与此同时，每一个 PR 都会经过自动代码审查。团队还依靠测试、持续集成和持续部署系统，检查代码是否通过验证。持续集成和持续部署，通常简称 CI 和 CD，可以理解为每次修改代码后，由自动化系统负责构建、测试，并检查它是否适合进入生产环境。

对于系统外围、风险较低的修改，Claude 已经可以承担全部审查工作。但这种信任不是突然获得的。团队经历了半年以上的积累：先让人审查所有修改，再观察模型在哪些文件和任务上能够稳定发现问题。只有当自动审查持续可靠时，才逐步取消对应的人工环节。

如果某次代码修改导致事故，团队会回头分析造成事故的 PR，更新审查规则，并把这个案例加入“评测集”。

评测，也就是 eval，是一组用来检验模型能力的标准任务。它类似模型的考试题库。以后每次更换模型或修改系统，团队都会重新运行这些任务，确保表现没有退步。

因此，新模型并不是仅凭主观感受上线。Anthropic 会同时运行公司级评测和 Claude Code 团队自己的评测，检查新模型是否比旧模型更强。除了功能正确性，他们也开始评估使用感受。比如，用户不喜欢模型做了一半就问“要不要继续”，也不喜欢它突然说“该睡觉了”。这类行为同样会被写进评测，成为需要修正的问题。

不过，团队也明确表示，他们无法获得百分之百的确定性。评测的作用，是不断扩大覆盖范围，降低退步风险，而不是证明模型永远不会犯错。

##### 系统提示词正在变短，工具也在变少

随着前沿模型的判断力提高，指导模型工作的“系统提示词”反而可以变得更短。

系统提示词，是产品在后台提供给模型的一组长期指令，用来规定模型的角色、工具和行为方式。对 Claude Code 来说，新一代前沿模型的系统提示词已经减少了大约百分之八十。

原因之一是，旧模型需要大量示例，才能模仿正确做法。但对 Fable 和 Opus 4.8 这样的模型来说，过多示例有时会限制创造力。

另一个原因是，团队过去写了太多“绝对不许做”或者“永远必须做”的规则。这些规则可能在九成情况下成立，却在剩下的一成情况下制造冲突。

例如，“修改前端后必须验证”通常是合理的。但如果任务只是改一个词，而且测试也同步更新，完整启动应用可能没有必要。与其让模型无条件遵守硬规则，不如提供背景，让它判断什么时候需要更全面的验证。

这套做法依赖模型自身的判断能力。因此，只有能力最强的新模型使用大幅精简后的提示词，较旧或较小的模型仍然保留详细说明。

工具设计也遵循类似原则。团队倾向于减少工具数量，提供更通用的能力，而且每个工具都应该有清楚、独立的用途。比如，他们移除了一些专门的文件搜索工具，改为让 Claude 使用通用命令。

不过，文件编辑工具仍然保留，因为界面可以明确展示 Claude 修改了哪个文件，并询问用户是否批准。对于刚开始使用的用户，这种可见、可控的体验依然很重要。

##### 安全方面，Auto Mode 是推荐方式，但不是绝对保险

当智能体可以长时间运行、执行命令并接触公司数据时，安全就变得格外重要。

Anthropic 推荐使用 Auto Mode，也就是自动模式，处理长时间任务。这个模式不是简单地取消所有权限确认，而是让另一个分类模型持续判断每次工具调用是否合理。

它会结合当前对话、用户指令和具体命令来做决定。比如用户明确要求把代码推送到 GitHub，它可以允许相关操作；如果用户明确说不要推送，它就应该阻止 Claude 自行行动。

自动模式还会配合“沙箱”。沙箱可以理解为一个隔离环境，用来限制程序能够访问的文件、网络和系统资源。当某个操作需要突破沙箱，比如访问外部网络时，自动模式会再次判断这是否符合用户意图。

Anthropic 还进行了大量安全评测和红队测试。红队测试就是请人主动扮演攻击者，想办法诱导系统犯错。他们重点关注两类风险。

第一类是提示注入，也就是恶意内容偷偷夹带指令，诱导智能体忽视真正用户的要求。

第二类是数据外泄，也就是智能体把不该发送的信息传到外部。

团队表示，自动模式无法阻止百分之百的攻击，但在这些主要风险上，它的失误率已经低于普通人工审查者。这个模式从一月份开始就在 Anthropic 内部使用，并经过持续加固。

Claude Tag 的安全难度更高，因为 Slack 里很多人都可能影响它。为此，团队让 Claude 可以拥有独立身份和独立权限，方便追踪和审计它做过什么。

他们还采用“凭据注入”。简单来说，智能体可以使用某项服务，却看不到真正的密码或访问令牌。只有在它发出合法请求时，代理系统才会临时替换成真实凭据。这样，即使智能体受到恶意提示影响，敏感凭据也不容易被直接读取和泄露。

所以，Auto Mode 的目标不是让风险消失，而是通过模型判断、沙箱、权限、评测和凭据隔离，构成多层防线。

##### 人的价值没有消失，而是需要更大的目标

谈到开发者的失落感，嘉宾承认，这种感受是真实的。如果一个人只想完成过去同样的工作，而那项工作现在只需要一句提示，那么确实容易怀疑自己的价值。

他们给出的答案是：提高目标，而不是守住旧的工作方式。

实现成本下降后，开发者应该尝试过去因为时间、人力或技能限制而不敢做的项目。重点不再是证明自己能亲手写多少代码，而是能否提出更有价值的问题，设定更高的质量标准，并把更大的事情真正做出来。

产品经理的角色也在变化。在 Claude Code 团队里，产品、工程和设计的边界越来越模糊。产品人员有想法但暂时没有工程师接手时，可以先做出原型；设计不够完善时，可以先参考已有页面生成第一版，再请专业设计师优化；团队沟通成本上升时，也可以自动收集状态和整理发布计划。

他们把产品工作的核心概括为：找出好想法和交付给客户之间还缺什么，然后尽量把中间环节自动化。

Anthropic 还有一句内部文化原则，叫“不和自己讨价还价”。意思是，不要只在脑中想象各种代价，然后提前说服自己放弃。先尝试更有野心的方案，让真正的限制通过实践显现出来。

这和传统软件工程“默认拒绝、处处权衡”的直觉有明显冲突。但当实现成本发生变化，过去形成的很多经验也需要重新检验。

##### Claude 已经能做出意外成果，但设计品位仍是短板

一个令人意外的案例，是用 Claude 编辑完整的演讲视频。

嘉宾拿到了舞台录像、演示文稿录像和音频文件，又提供了网页版幻灯片源码。他只给出一次较完整的提示，Fable 就转录了整场演讲，并发现演示录像中出现了自动更新弹窗。

模型没有继续使用有瑕疵的录像，而是判断演讲进行到哪一页，直接调用网页源码重新显示幻灯片。它还会根据演讲者在舞台上的移动动态裁切画面，跟踪人物位置，加入字幕、动画和图形，并使用专业视频工具完成合成。

这个案例的重要之处，不是 Claude 会调用某一个视频软件，而是它能理解最终目标，发现素材问题，再主动改换实现方法。

但目前它仍然不够擅长设计和用户体验。只要人给出详细规格，它通常能把功能做对；可是间距、界面细节和整体愉悦感还不够稳定。它也容易沿用已有应用的常见设计风格，而不是创造适合前沿人工智能产品的新交互方式。

团队希望未来的模型不只是执行设计要求，还能成为交互设计的思考伙伴。更长远的期待，则是让模型与现实世界互动，帮助组织科学实验，解决不只属于编程的问题。

##### 最后，从有用工具到个人兴趣项目

这些工具也让许多过去不值得投入时间的小项目变得可行。

一位嘉宾正在制作二维格斗游戏，把自己和朋友做成角色。Claude 会调用图像和视频模型生成动画，检查每一帧效果，还能判断拳头的位置，自动生成碰撞区域。

另一位嘉宾热爱攀岩，便用 Claude Code 做了一个朋友之间使用的小应用，记录大家正在挑战的路线。工作流还会研究适合所有人的攀岩目的地，比较直达航班、住宿、路线难度，以及从停车点到岩壁的步行距离。最后得到的不是面向大众的标准产品，而是完全按照这群朋友偏好制作的私人应用。

在观众问答中，团队还谈到了评测和记忆。

对于评测工具，他们认为，目前最大的限制往往不是缺少软件，而是用户很难建立高质量评测集。怎样选出有代表性的案例、怎样判断模型是否真的进步，才是更需要培养的能力。

至于 Claude Tag 的团队记忆，目前主要按 Slack 频道保存。每个频道拥有共享记忆，具体形式是一份 Markdown 文本文件。单次会话还可以把新的重要信息写回频道记忆。团队也在继续研究更适合长期扩展的记忆机制。

##### 结尾回顾

最后，有五点最值得记住。

第一，编程智能体正在把开发者从手工实现推向更高层次的产品判断。代码写得更快以后，决定做什么，比亲手怎么做更重要。

第二，Claude Tag 展示了团队智能体的新形态。它能主动监控任务、保留团队记忆，并参与多人协作；在 Anthropic 的产品工程团队中，它已经完成并合并了大约百分之六十五的代码修改申请。

第三，自动化不能脱离验证。高质量测试、持续集成、代码负责人和长期评测，是团队逐步减少人工审查的基础。

第四，安全不是一个开关，而是多层防线。自动模式、沙箱、动态权限、红队测试和凭据隔离共同降低风险，但没有任何机制能够保证百分之百安全。

第五，人的角色正在从执行者转向目标设定者。面对能力更强的模型，真正有价值的选择不是只做过去那些事，而是提高标准，扩大 ambition，也就是去完成以前因为成本太高而不敢尝试的项目。

#### 代码成本下降后，稀缺的变成判断、验证与组织上下文

访谈中最值得注意的，不是 Claude 又能完成多少代码，而是 Anthropic 团队的工作方式已经围绕一个新前提重组：**实现正在从主要瓶颈，变成可快速试错、并行生成的资源。**

##### 产品判断没有被削弱，反而更容易暴露

当一个想法从提出到原型不再需要半年，而可能只需一周，传统的“先写完整 PRD、充分对齐、再开始开发”就不再总是经济。更合理的方式可能是先做出几个版本，让真实体验帮助团队澄清需求。

但实现便宜并不意味着决策也便宜。相反，团队能同时尝试的方向越多，**选择什么、不选择什么，以及用什么证据停止投入**就越重要。Anthropic 的做法是内部高强度试用，并以活跃度和留存设置发布门槛。这比“大家觉得不错”更可靠，也说明 AI 并未消灭产品管理，而是把工作重心从协调开发资源，推向假设设计、体验判断和验证标准。

“不要自己替现实拒绝一个大胆方案”是一种有价值的文化修正，但不能演变成无限扩张需求。旧时代容易因实现太贵而过早放弃；新时代则可能因实现太便宜而制造大量无人需要的软件。

##### “重写变得可行”的前提，是行为能够被验证

访谈提出了一个颇有冲击力的判断：过去被视为工程禁忌的重写，如今可能是好选择。模型可以把旧代码库当作隐含规格，配合测试套件快速生成多个实现，再比较准确性与质量。

真正改变重写经济性的并非代码生成本身，而是**验证成本能否同步下降**。如果系统有完整测试、清晰边界和可复现环境，重写确实可以从高风险豪赌变成受控实验；但若业务规则散落在人工流程、线上异常和少数员工记忆里，旧代码就不是完整规格，模型只会更快复制误解。迁移、兼容、性能和运维风险也不会自动消失。

因此，可迁移的结论不是“应该多重写”，而是：高质量测试与评估正在从工程保障升级为组织资产，它决定了团队能否真正兑现 AI 的速度。

##### 团队级 Agent 的难点不是聊天，而是成为可信的组织参与者

Claude Tag 最有意义的变化，是从被动工具变成常驻于 Slack 的主动协作者：持续监控缺陷、生成 PR、保留频道记忆，并允许多人共同修正。据称它已完成 Anthropic 产品工程团队 65% 的 PR，但这是内部口径，仍需结合 PR 规模、事故率和人工返工量理解。

更重要的是，实现这一比例靠的不只是模型能力，还包括公开频道、代码所有者、持续评估、事故回灌、独立身份、凭证代理和权限审计。**企业 Agent 的产品边界，实际上由组织的信息结构与安全设施共同决定。**频道越公开，Agent 上下文越完整；但隐私、权限污染与提示注入风险也越大。

这提示了一个更长期的机会：真正有壁垒的未必是又一个 Agent 界面，而是帮助企业建立可评估的任务、可控的权限、可追溯的记忆和持续更新的验证集。模型会快速迭代，能够证明“哪些工作可以安全放手”的系统，才更可能成为稳定基础设施。
