## 正文

**宝玉**

飞书 CLI 开源了，为什么 AI Agent 时代，大家都在做命令行工具？

飞书刚开源了一个命令行工具 lark-cli，能让 AI Agent 直接操作飞书：发消息、查日历、写文档、建多维表格、发邮件、管任务。你跟 AI 说一句话，它自己去操作飞书完成任务。

类似的 CLI 还很多，三周前 Google 也开源了 gws，让 AI Agent 操作 Google Workspace。2026 年了，所有想接入 AI Agent 的产品，都在做 CLI。

【1】先说 CLI 是什么

CLI（Command Line Interface），就是你在电脑上打开一个黑底白字的终端窗口，敲一行命令，回车，电脑帮你干活。

比如你要查今天的日程，不用打开飞书 App 找日历，敲一行：  
lark-cli calendar +agenda  
日程就列出来了。

没有按钮，没有图标，没有花哨的界面。CLI 比图形界面早了二十多年，在 Windows 时代逐渐没什么人用了。但 AI Agent 时代，又火起来了。

【2】为什么 AI Agent 时代，大家都在做 CLI

AI Agent 要干活，就得有操作工具的能力。你让 AI 帮你订会议室，它需要能访问日历系统。你让它帮你整理客户数据，它需要能读写表格。你让它帮你部署代码，它需要能跑部署命令。

总得有一个接口让 AI 去调用。API 也能做这件事，但 CLI 有一个 API 不具备的优势：CLI 是自描述的。AI 碰到一个陌生的 CLI，敲一下 --help 就知道有哪些能力、怎么用、参数怎么填。API 不行，AI 得先拿到文档、弄清端点、搞懂认证方式，才能动手。CLI 自带说明书，AI 拿来就能用。

而且 CLI 天然是用文本交互的，输入是文字，输出也是文字。AI 最擅长处理的就是文字。反过来，让 AI 操作 GUI 就绕远了，得截图、用视觉模型识别按钮在哪、再模拟鼠标去点，一行命令能搞定的事拆成四步，每步都可能出错。对 AI 来说，CLI 就是天然的操作界面。

【3】那 MCP 和技能呢

让 AI Agent 操作外部服务，现在主流有三种方式：MCP、CLI、技能（Skills）。三者不是互相替代的关系，各管一件事。

CLI 是实际干活的工具。装完之后终端里就能跑命令，查日历、发消息、建表格，都是 CLI 在执行。

MCP 也是让 AI 操作外部服务的，但方式不同。MCP 是提前把工具清单注册给 AI，AI 随时能调用，但清单本身常驻上下文窗口（可以理解为 AI 的“工作记忆”，空间有限）。就算 AI 暂时不用某个工具，它的描述也占着空间。CLI 是 AI 需要的时候自己去终端敲命令，用完就走，不占上下文。

另一个区别是组合能力。CLI 可以靠管道和参数组合出没预设过的操作，比如：

lark-cli calendar agenda --next-week \| grep“张三” \| wc -l  
一行命令就能查出下周和张三有几个会。MCP 的每个能力都需要提前注册，要实现同样的效果，得单独定义一个新工具。  
不过 MCP 有自己的适用场景。在不支持命令行的环境里（比如 Cursor、Claude 桌面端），MCP 是唯一选择。两者各有所长：能访问终端的场景用 CLI 更轻量灵活，不能访问终端的场景靠 MCP。

技能是给 Agent 看的说明书。它不干活，但告诉 Agent 这个 CLI 有哪些命令、什么场景该用什么参数、出错了怎么处理。没有技能文件 Agent 也能用 CLI，靠 --help 自己摸索。有了技能文件，Agent 一上来就知道该怎么操作，成功率高得多。

简单说：CLI 是手，MCP 是另一种手，技能是肌肉记忆。飞书这次开源的项目，CLI 和技能一起提供。

【4】怎么给 AI 写好一个 CLI

不是随便写个命令行工具 AI 就能顺畅地用。如果你想给自己的产品做一个面向 AI 的 CLI，飞书的设计有几个值得参考的地方。

第一，help 文本是你最重要的文档。AI 碰到不认识的 CLI，第一件事就是运行 --help。你的 help 文本就是工具说明书、参数规格、使用指南三合一。别写那种“Usage: myctl deploy \[flags\]”就完事的帮助信息，要写清楚每个参数干什么、什么时候用、有什么默认值。飞书 CLI 还有一个 schema 命令，可以快速查询任何 API 方法的参数、请求体、响应结构、支持的身份和权限范围。AI 看到这些信息就能自己决定怎么调用。

第二，支持 dry-run，这是为 AI 设计的安全网。AI 会自己做决策，有时候它理解错了你的意图，或者匹配到了不该动的数据。dry-run 相当于一个“预览”机制。

举个例子，你让 AI 帮你删除飞书多维表格里上个月的过期数据。如果直接执行，删错了就没了。加上 --dry-run，AI 会先跑一遍，返回类似这样的结果：“将要删除以下 47 条记录：2025-05 的过期任务 23 条，已归档项目 24 条。未做任何实际修改。”你看了觉得没问题，再让它去掉 --dry-run 真正执行。Google 的 gws 也做了同样的设计，它的技能文件里甚至写死了一条规则：对所有写入和删除操作，必须先 dry-run。

第三，错误信息要能指导下一步操作。人看到“Permission denied”会自己去查文档。AI 看到“Permission denied”就卡住了。飞书 CLI 的做法是：告诉 AI 你缺了什么权限，顺便把申请权限的命令也给出来。比如 lark-cli auth login --scope“calendar:calendar:readonly”。AI 看到就能自己修复问题，继续干活。为 AI 设计的 CLI，每一条错误信息都应该包含三个要素：哪个参数出了问题、具体错在哪里、下一步应该执行什么命令来修复。

第四，返回结构化数据，控制好输出量。飞书 CLI 支持 json、csv、table 等多种输出格式。对人来说 table 更顺眼，对 AI Agent 来说 json 更可靠。好的 CLI 不只是能跑通，还要方便被别的工具消费。同时要控制输出量。AI 的上下文窗口有限，如果一个命令返回一万行日志，上下文就炸了。飞书 CLI 提供了分页参数（--page-limit）和过滤参数，让 AI 能拿到它需要的那部分数据就好。

不管你是设计 CLI 的人还是用 CLI 的人，记住这条：让 Agent 动手之前，先让它 dry run 一遍。

【5】装完之后，你动嘴，Agent 动手

装完之后用起来就是：你说一句话，Agent 去操作飞书把事情办了。

你开完会，跟 AI 说“把刚才会议里提到的所有待办都提出来，该发文档的发文档，该建任务的建任务”。AI 读会议纪要，拆解出待办事项，然后逐条执行：用 lark-cli doc create 在飞书里建文档，用 lark-cli task create 建任务并指派给对应的人，用 lark-cli im send 把结果通知到群里。整个过程你只说了一句话，Agent 在终端里跑了一串命令。而且因为有 dry-run，你可以让它先预览一遍要建哪些任务、发给谁，确认没问题再真正执行。

你要约一个五人跨时区的会，跟 AI 说“帮我看看下周大家什么时候有空”。AI 去查每个人的日历和时区，推荐几个时间段，你选一个，会就建好了。

你甚至可以让 AI 在飞书文档里直接帮你写初稿，你在文档里留评论提意见，AI 读完评论自己改。整个协作过程不用离开飞书。

安装也简单，npm install -g @larksuite/cli 装 CLI，npx skills add [https://github.com/larksuite/cli](https://github.com/larksuite/cli) -y -g 装技能文件。你甚至不用自己记这两步，把项目地址 [https://github.com/larksuite/cli](https://github.com/larksuite/cli) 发给 Agent，让它自己安装、自己学会怎么用。

【CLI 的回归】

过去四十年，计算机的界面进化方向一直是从 CLI 到 GUI，从文字到图标，从键盘到触屏，对人越来越友好。

AI Agent 时代，方向反过来了，软件的用户变成了 AI Agent。CLI 这个为文字世界设计的接口，恰好是 AI 最顺手的工具。

既然 Agent 成了软件新的用户增长点，那么像飞书提供 CLI 也不稀奇，与其等着社区来写 MCP 适配层，不如直接做一个 AI 原生的 CLI，完全开源，无需注册审批，让所有 AI Agent 都能接入。

这也带来一个绕不开的问题：Agent 的权限怎么给？不给权限，什么都做不了；权限太高，又怕 Agent 理解错意图干出不可逆的事。毕竟还做不到让 Agent 代你审批、代你发全员邮件。dry-run 能兜住一部分风险，但真正要让 Agent 在企业里大规模跑起来，权限体系、审计追踪、人机协作的边界，都还在摸索中。

但换个角度想，当年我们把公司的钱从保险柜搬到网银，把合同从纸质搬到电子签，也都是一步步摸索出来的。CLI 和 dry-run，可能就是这个过程里的第一步。

而飞书做这件事，其实有一个别人不太容易复制的优势：它本身在企业协作领域已经足够成熟，消息、文档、日历、审批、多维表格、任务，这些能力都是现成的。现在把这些能力通过 AI 原生的 CLI 全部开放出来，大概率会成为国内对 AI Agent 最开放、最友好的企业级接入入口。这件事的价值不止是多一个工具，更像是真正在为 Agent 时代搭建企业级基础设施，把权限、审计、组织能力开放给整个生态，对行业落地 AI Agent 会是很关键的一步。

## 通俗精炼（1）

### 2026-03-30 10:47:42

#### 飞书开源 CLI 的核心意义

##### 一句话总结
在 AI Agent 时代，CLI（命令行工具）正在重新变重要，因为它比 GUI 更适合 AI 操作，也比传统 API 更容易被 AI 理解和调用。飞书开源 `lark-cli`，本质上是在为 AI Agent 提供一个可直接“动手干活”的企业协作入口。

##### 为什么 AI Agent 偏爱 CLI

###### 1. CLI 天然适合 AI
CLI 的输入输出都是文本，而 AI 最擅长处理文本。  
相比之下，如果让 AI 操作 GUI，就要先识别界面、定位按钮、再模拟点击，链路更长、出错更多。

###### 2. CLI 比 API 更容易上手
CLI 通常自带 `--help`，AI 遇到陌生工具时，可以先看帮助信息，快速知道有哪些命令、参数怎么传。  
而 API 往往还需要额外查文档、理解认证和接口规则，使用门槛更高。

###### 3. CLI 组合能力更强
CLI 可以通过管道、参数自由组合，快速完成复杂任务。  
这意味着 AI 不必每种需求都依赖预先定义好的能力，而是能临时拼装出新的操作流程。

##### CLI、MCP、技能 三者分别是什么

###### 1. CLI：真正执行任务的“手”
负责查日历、发消息、建文档、创建任务等具体动作，是实际干活的工具。

###### 2. MCP：另一种接入方式
MCP 也是让 AI 调用外部工具，但需要提前把能力注册给 AI。  
优点是适合不能访问终端的环境；缺点是占用上下文、灵活性较弱。

###### 3. 技能（Skills）：给 Agent 的操作说明书
技能本身不执行任务，而是告诉 Agent：  
什么场景该用什么命令、参数怎么传、出错后怎么处理。  
它能显著提升 Agent 的调用成功率。

##### 面向 AI 的 CLI 应该怎么设计

###### 1. `help` 文档要写得足够清楚
对 AI 来说，`--help` 就是第一份说明书。  
帮助信息越完整，AI 越容易正确调用工具。

###### 2. 必须支持 `dry-run`
`dry-run` 是 AI 时代非常关键的安全机制。  
它让 Agent 在真正执行写入、删除等高风险操作前，先预演一遍结果，降低误操作风险。

###### 3. 错误信息要能指导修复
不能只报错，还要告诉 AI：  
错在哪、缺什么权限、下一步该执行什么命令来修复。  
这样 Agent 才能自己继续完成任务，而不是卡住。

###### 4. 输出要结构化且可控
对 AI 来说，`json` 比表格更容易处理。  
同时还要支持分页、过滤，避免返回过多内容，把上下文窗口“撑爆”。

##### 飞书这件事为什么重要

###### 1. 它不是单点工具，而是企业协作能力的统一出口
飞书本身已经覆盖消息、文档、日历、任务、多维表格等高频协作场景。  
一旦这些能力通过 CLI 开放出来，AI Agent 就能直接在企业工作流里执行任务。

###### 2. 它可能成为 AI Agent 的企业级基础设施
相比只提供单一接口，飞书这次更像是在搭建一套 AI 原生的企业接入层，核心价值不只是“能用”，而是把权限、审计、组织协作等能力一并开放给 Agent 生态。

##### 仍然存在的挑战

###### 1. 权限控制
不给权限，Agent 什么都做不了；  
权限给太多，又可能带来误操作甚至不可逆风险。

###### 2. 审计与人机边界
未来企业真正大规模使用 Agent，还需要逐步解决：  
谁授权、谁审批、谁追踪、哪些事必须由人确认。

##### 结论

###### CLI 的回归，本质是“软件用户变了”
过去软件界面是为人设计的，所以 GUI 越来越主流；  
现在软件开始需要服务 AI Agent，而 CLI 恰好是最适合 AI 的操作界面。

飞书开源 `lark-cli`，不只是发布一个工具，而是在抢占 AI Agent 时代企业软件的新入口。

#### 主旨概括

这篇文章的核心观点是：**在 AI Agent 时代，CLI（命令行工具）重新变得重要，因为它比 GUI 更适合 AI 操作，也比传统 API 更容易被 AI 快速理解和调用**。  
飞书开源 `lark-cli`，本质上是在把自身的企业协作能力，以一种更适合 AI Agent 使用的方式开放出来。

##### 1. 飞书开源 CLI，目的就是让 AI 直接“动手做事”

- 飞书开源了命令行工具 `lark-cli`，让 AI Agent 可以直接操作飞书能力，包括：
  - 发消息
  - 查日历
  - 写文档
  - 建多维表格
  - 发邮件
  - 管任务
- 用户只需要用自然语言下达指令，AI 就可以自己调用工具去完成任务。
- 类似做法不只飞书一家，**Google 三周前也开源了 `gws`**，用于让 AI Agent 操作 Google Workspace。
- 作者判断：**到 2026 年，几乎所有想接入 AI Agent 的产品，都会去做 CLI。**

##### 2. 什么是 CLI，以及它为什么在今天重新流行

- CLI（Command Line Interface）就是在终端里输入命令，让电脑执行任务。
- 例如查今天日程，不用打开 App 点来点去，只需要敲一行命令：
  ```bash
  lark-cli calendar +agenda
  ```
- CLI 没有按钮、图标和复杂界面，虽然它比图形界面（GUI）更早出现，并在 Windows 时代逐渐边缘化，但在 AI Agent 时代又重新流行起来。
- 原因很简单：**CLI 对人可能不够友好，但对 AI 非常友好。**

##### 3. 为什么 AI Agent 时代，大家都在做 CLI

###### 3.1 AI 要干活，必须有“可调用的工具”

- AI Agent 如果想真正做事，就必须能操作外部系统。
- 比如：
  - 订会议室，需要访问日历系统
  - 整理客户数据，需要读写表格
  - 部署代码，需要执行部署命令
- 所以，产品必须给 AI 提供一个“接口”去调用能力。

###### 3.2 CLI 比 API 更适合 AI 的关键原因：它是“自描述”的

- API 当然也能让 AI 调用服务，但 CLI 有一个明显优势：**自带说明书**。
- AI 遇到陌生 CLI，只要执行 `--help`，就能知道：
  - 有哪些命令
  - 参数怎么写
  - 能做什么事
- 而 API 通常需要额外文档，AI 还得先搞清楚：
  - 接口地址
  - 认证方式
  - 请求参数
- 所以作者认为：**CLI 是 AI 拿来就能用的工具，API 则需要先“学会”再用。**

###### 3.3 CLI 是文本交互，天然匹配 AI 的能力

- CLI 的输入是文字，输出也是文字。
- AI 最擅长理解和处理文字，因此 CLI 是它最顺手的操作界面。
- 相反，如果让 AI 操作 GUI，就会变得更绕：
  - 先截图
  - 再用视觉模型识别按钮
  - 再模拟鼠标点击
- 原本一行命令能完成的事情，可能要拆成 4 步，而且每一步都可能出错。
- 所以从效率和稳定性来看，**CLI 比 GUI 更适合 AI Agent。**

##### 4. CLI、MCP、技能（Skills）分别是什么关系

作者强调：**这三者不是互相替代，而是分工不同。**

###### 4.1 CLI：真正执行任务的“手”

- CLI 是实际干活的工具。
- 安装后，AI 可以直接在终端执行命令，完成查日历、发消息、建表格等操作。
- 比如：
  - `lark-cli doc create`
  - `lark-cli task create`
  - `lark-cli im send`

###### 4.2 MCP：另一种接入外部服务的方式

- MCP 也是让 AI 调用外部能力，但它是**预先把工具清单注册给 AI**。
- 优点是 AI 随时可用，不需要临时摸索。
- 缺点是这些工具描述会常驻在上下文窗口里，占用 AI 的“工作记忆”。
- CLI 则不同：**需要时再调用，用完即走，不持续占上下文。**

###### 4.3 CLI 的组合能力更强

- CLI 可以通过管道和参数自由组合，做出预设之外的操作。
- 文中举的例子是：
  ```bash
  lark-cli calendar agenda --next-week | grep "张三" | wc -l
  ```
- 这一行命令就可以查出：**下周和张三有几个会**。
- 如果用 MCP，实现类似能力，往往要单独再定义一个新工具。
- 这说明：**CLI 更灵活，更适合临场组合。**

###### 4.4 MCP 也有不可替代的场景

- 如果环境本身不支持命令行，例如：
  - Cursor 某些场景
  - Claude 桌面端
- 那么 MCP 可能就是唯一可用方案。
- 作者的结论是：
  - **能访问终端时，用 CLI 更轻、更灵活**
  - **不能访问终端时，用 MCP 更合适**

###### 4.5 技能（Skills）：给 Agent 看的“操作说明书”

- 技能本身不执行任务，它的作用是告诉 Agent：
  - CLI 有哪些命令
  - 什么场景该用什么参数
  - 报错时怎么处理
- 没有技能文件，AI 也能靠 `--help` 自己摸索；
- 但有技能文件后，AI 上手更快，成功率更高。
- 作者用一句话总结三者关系：
  - **CLI 是手**
  - **MCP 是另一种手**
  - **技能是肌肉记忆**
- 飞书这次开源的项目，**CLI 和技能文件是一起提供的。**

##### 5. 面向 AI 设计 CLI，应该怎么做

作者认为，**不是随便写个命令行工具就能让 AI 顺畅使用**，飞书的设计有几个值得借鉴的点。

###### 5.1 `--help` 是最重要的文档

- AI 遇到陌生 CLI，第一步几乎一定是先跑 `--help`。
- 所以帮助信息不能只写简单的用法格式，而要尽量写清楚：
  - 参数含义
  - 适用场景
  - 默认值
- 飞书 CLI 还提供了 `schema` 命令，可以快速查询：
  - API 方法参数
  - 请求体结构
  - 响应结构
  - 支持的身份和权限范围
- 这能帮助 AI **自己判断怎么调用**。

###### 5.2 必须支持 `dry-run`，这是 AI 的安全网

- 因为 AI 会自主决策，所以它也可能理解错需求，误操作数据。
- `--dry-run` 就像预演机制：先告诉你“准备做什么”，但不真正执行。
- 文中举了一个很具体的例子：
  - 如果让 AI 删除飞书多维表格里上个月过期数据
  - 它可以先用 `--dry-run`
  - 返回类似结果：
    - 将要删除 **47 条记录**
    - 其中 **2025-05 的过期任务 23 条**
    - **已归档项目 24 条**
    - **未做任何实际修改**
- 你确认无误后，再让 AI 真正执行。
- Google 的 `gws` 也采用了相同思路，甚至在技能文件中明确规定：**所有写入和删除操作都必须先 dry-run。**

###### 5.3 错误信息必须能指导 AI 下一步怎么修复

- 人看到 `Permission denied`，通常会自己找文档解决；
- 但 AI 看到这种模糊错误，很可能就卡住了。
- 飞书 CLI 的做法更适合 AI：
  - 告诉它缺少什么权限
  - 顺便给出补救命令
- 例如：
  ```bash
  lark-cli auth login --scope "calendar:calendar:readonly"
  ```
- 作者认为，面向 AI 的错误信息应该至少包含三部分：
  - 哪个参数有问题
  - 具体错在哪里
  - 下一步应该执行什么命令修复

###### 5.4 输出要结构化，还要控制信息量

- 飞书 CLI 支持多种输出格式：
  - `json`
  - `csv`
  - `table`
- 对人来说，`table` 更直观；
- 对 AI Agent 来说，**`json` 更可靠，更容易继续处理**。
- 同时输出量也要控制好，因为 AI 的上下文窗口有限。
- 如果一个命令直接吐出上万行日志，AI 的上下文可能就被占满了。
- 为此，飞书 CLI 提供了：
  - 分页参数 `--page-limit`
  - 过滤参数
- 这样 AI 就能只拿到真正需要的数据。

##### 6. 装完之后，用户“动嘴”，Agent“动手”

###### 6.1 会议纪要到任务分发，可以自动串起来

- 一个典型场景是：你开完会后，对 AI 说一句：
  - “把刚才会议里提到的所有待办都提出来，该发文档的发文档，该建任务的建任务。”
- AI 就会：
  - 读取会议纪要
  - 拆出待办事项
  - 用 `lark-cli doc create` 创建文档
  - 用 `lark-cli task create` 创建任务并分派负责人
  - 用 `lark-cli im send` 把结果通知到群里
- 整个过程，用户只说一句话，剩下都由 Agent 在终端里跑命令完成。
- 而且仍然可以先 `dry-run`，预览“将建哪些任务、发给谁”。

###### 6.2 跨时区约会也能自动处理

- 另一个例子是：你对 AI 说“帮我看看下周大家什么时候有空”。
- AI 可以去查：
  - 每个人的日历
  - 每个人的时区
- 然后推荐几个可行时段，用户选一个后，会议就自动建好了。

###### 6.3 AI 还能直接在飞书里参与文档协作

- 你甚至可以让 AI 先在飞书文档里写初稿；
- 你在文档里直接留评论；
- AI 读完评论后，再继续修改内容。
- 这样整个协作流程都在飞书内完成，不用切换系统。

###### 6.4 安装门槛也比较低

- 安装 CLI：
  ```bash
  npm install -g @larksuite/cli
  ```
- 安装技能文件：
  ```bash
  npx skills add https://github.com/larksuite/cli -y -g
  ```
- 作者特别强调一点：**甚至不用用户自己记这些命令**。
- 只要把项目地址 `https://github.com/larksuite/cli` 发给 Agent，AI 就可以自己安装、自己学习怎么用。

##### 7. CLI 的回归，本质是“软件用户变了”

- 过去 40 年，软件界面的演化方向一直是：
  - 从 CLI 到 GUI
  - 从文字到图标
  - 从键盘到触屏
- 本质上，这些变化都是为了让“人”更容易使用软件。
- 但在 AI Agent 时代，软件的新用户开始变成 AI。
- 对 AI 来说，CLI 这种文字化接口，反而是最自然、最高效的形式。
- 所以作者认为：**CLI 的回归，不是倒退，而是因为用户对象从人变成了 Agent。**

##### 8. 飞书为什么做这件事，以及它的行业意义

###### 8.1 飞书直接做 AI 原生 CLI，比等别人做适配更主动

- 既然 Agent 会成为新的软件使用者，飞书直接提供官方 CLI 就很合理。
- 这样做的好处是：
  - 不用等社区做 MCP 适配层
  - 能直接提供更完整、更原生的接入能力
  - 完全开源、无需注册审批，方便各种 AI Agent 接入

###### 8.2 真正难的，不是能不能接，而是权限怎么管

- 作者也指出一个绕不开的问题：**Agent 权限怎么给**。
- 权限不给，Agent 什么都做不了；
- 权限给太高，又怕它理解错意图，做出不可逆操作。
- 比如目前显然还很难放心让 Agent：
  - 代替你审批
  - 代替你发全员邮件
- `dry-run` 只能兜住一部分风险，真正要在企业里大规模落地，还要继续解决：
  - 权限体系
  - 审计追踪
  - 人机协作边界

###### 8.3 飞书的优势在于，它本身就有完整的企业协作能力

- 飞书和很多单点工具不同，它已经具备一整套成熟能力，包括：
  - 消息
  - 文档
  - 日历
  - 审批
  - 多维表格
  - 任务
- 现在它把这些能力通过 AI 原生 CLI 开放出来，作者认为这很可能会成为：
  - **国内对 AI Agent 最开放**
  - **最友好的企业级接入入口**
- 这件事的价值，不只是“多了一个工具”，更像是在为 Agent 时代建设基础设施，把企业级能力和权限体系开放给整个生态。

##### 结尾总结

- 文章的结论可以概括为：**AI Agent 时代，CLI 之所以重新流行，是因为它天然适合 AI 的工作方式：可读、可调、可组合、低上下文负担。**
- 飞书开源 `lark-cli`，不仅是在发布一个工具，更是在尝试搭建 AI Agent 接入企业系统的基础设施；而 `dry-run`、结构化输出、可修复错误提示等设计，也说明未来“面向 AI 设计软件接口”会成为一个重要方向。
