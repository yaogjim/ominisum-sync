- **核心高价值点**：根据任务是否需要登录状态、桌面应用控制或前端开发反馈循环，选择Chrome扩展、Computer Use或内置浏览器。

**知识要点**

- Computer Use通过视觉和鼠标键盘操作图形界面，覆盖面广但速度慢，适合无API的桌面应用。

- 内置浏览器是隔离沙盒，适合本地开发、页面预览、视觉bug复现和前端迭代。

## 正文

**宝玉**

Codex 操控电脑的三种方式。Codex 团队成员 Jason 今天写了一篇详细指南，把三者的区别和适用场景理清楚了，这里做个精简版。

【1】Computer Use：最广，也最慢

Computer Use 让 Codex 像人一样看屏幕、点鼠标、敲键盘，操作你电脑上的任何图形界面应用。Spotify、Xcode、系统设置、iOS 模拟器，甚至 iPhone Mirroring 都能控制。

代价是慢。结构化插件可以直接调 API，Computer Use 得一步步看界面、找按钮、等响应、再检查结果。但它能搞定没有 API 的应用，这是其他方式做不到的。

Mac 和 Windows 的体验差距很大：Mac 上 Codex 可以在后台静悄悄地操作，你继续用自己的电脑不受影响；Windows 上它必须占据前台，操作期间你没法用那台机器。

Jason 举了个例子：有次他的快递被偷了，Amazon 说要等 25 分钟才能接通客服。他让 Codex 每五分钟检查一次聊天窗口，客服出现后改为每分钟一次，自动完成退款流程。他去洗了个澡，回来退款已经办好了。

【2】Chrome 扩展：带着你的登录状态

Chrome 扩展让 Codex 使用你已登录的浏览器会话，包括 cookies、账号状态和已有标签页。Gmail、LinkedIn、Salesforce、公司内部后台，这些需要登录才能用的工具，Chrome 扩展是对的选择。

它还能同时控制多个标签页，在一个标签里读信息，到另一个标签里对比，再到第三个标签完成操作。Computer Use 也能操作浏览器，但它只认屏幕坐标，Chrome 扩展理解的是浏览器层面的上下文。

Jason 用它跑了一个长期任务：每天让 Codex 通过 Chrome 检查他的 Twitter 私信、浏览相关新闻、收集反馈，把有价值的内容存到本地文件，但不发任何消息。  
要注意的是，网站会把 Codex 的点击和表单提交当作你本人的操作。研究、浏览、起草可以自动化，但发送、发布、付款这类操作最好留给自己确认。

【3】内置浏览器：给开发者的沙盒

内置浏览器住在 Codex 的对话线程里，你和 Codex 共享同一个渲染页面。它不带任何登录状态和 cookies，是个完全隔离的环境。

这反而成了开发场景的优势。它的主场是本地开发服务器、文件预览、公共网页、响应式布局检查和视觉 bug 复现。Codex 可以改代码、操作页面、截图、再跑一遍，形成紧密的反馈循环。

Jason 最喜欢的功能是标注：你可以直接在页面上点击某个元素留评论，比如"这个层级反了""这个按钮间距不够"，Codex 会拿着截图和元素上下文去改代码，改完重新打开同一个页面等你下一轮标注。比来回传截图和文字描述高效得多。

【选哪个？】

简单记：任务需要登录状态用 Chrome，需要操作桌面应用用 Computer Use，在做前端开发用内置浏览器。如果有现成的插件或 MCP 能完成任务，优先用结构化工具，视觉控制是最后手段。

## 解读（1）

### 2026-06-17 02:12:11

#### Codex 操控电脑的三种方式：深度总结、通俗解读与辩证思考

##### 一、深度总结

Codex 操控电脑主要有三种方式：

| 方式 | 核心能力 | 最适合场景 | 主要缺点 |
|---|---|---|---|
| **Computer Use** | 像人一样看屏幕、点鼠标、敲键盘 | 操作桌面软件、无 API 的应用 | 慢，依赖视觉界面 |
| **Chrome 扩展** | 使用你的浏览器登录状态和标签页 | Gmail、LinkedIn、Salesforce、内部系统等网页任务 | 容易被网站视为“本人操作” |
| **内置浏览器** | 在隔离沙盒里打开网页，与 Codex 共享页面 | 前端开发、本地预览、视觉调试 | 没有登录态，不适合私人账号操作 |

核心判断逻辑：

> **有 API / 插件 / MCP，优先用结构化工具；没有再用视觉控制。**

因为结构化工具更快、更稳定、更可控；视觉操作更通用，但更慢、更脆弱。

---

##### 二、深入浅出解读

可以把这三种方式理解成三种“助手形态”。

###### 1. Computer Use：像真人远程操作你的电脑

它就像一个人在你电脑前：

- 看屏幕；
- 找按钮；
- 点鼠标；
- 输入文字；
- 检查结果。

所以它最万能。

比如：

- 操作 Xcode；
- 调系统设置；
- 控制 iOS 模拟器；
- 使用没有 API 的老旧软件；
- 处理客服聊天窗口。

但它的问题也很明显：

> 它不是“直接知道按钮在哪”，而是像人一样慢慢看、慢慢点。

所以它**最广，但最慢**。

另外，Mac 和 Windows 体验不同：

- **Mac**：Codex 可以后台操作，你还能继续用电脑；
- **Windows**：Codex 往往要占用前台，你暂时不能正常使用那台机器。

---

###### 2. Chrome 扩展：带着你的登录状态办网页事

Chrome 扩展的最大价值是：

> 它能使用你已经登录的浏览器状态。

也就是说，你登录了 Gmail、Twitter、LinkedIn、Salesforce 或公司后台，Codex 就能在这些页面中帮你阅读、整理、比对、填写草稿。

它比 Computer Use 操作浏览器更强，因为它理解的是浏览器上下文，而不只是屏幕坐标。

适合：

- 查邮件；
- 整理私信；
- 浏览新闻；
- 收集反馈；
- 对比多个标签页内容；
- 起草回复或报告。

但风险也在这里：

> 网站会把 Codex 的点击、提交、发布当成你本人操作。

所以：

- 读取、整理、起草，可以自动化；
- 发送、付款、发布，最好人工确认。

---

###### 3. 内置浏览器：开发者调试网页的沙盒

内置浏览器不是用来登录你私人账号的。

它没有 cookies，没有登录状态，是一个隔离环境。

但这正适合开发。

比如你正在做一个网页，Codex 可以：

1. 修改代码；
2. 打开本地页面；
3. 查看效果；
4. 截图分析；
5. 修复视觉 bug；
6. 再刷新验证。

尤其适合前端开发，因为你可以直接在页面上标注：

- “这里间距太小”；
- “这个按钮位置不对”；
- “这个层级反了”；
- “移动端布局崩了”。

Codex 看到标注和页面上下文后，就能直接改代码。

这比“截图 + 文字描述 + 来回沟通”高效很多。

---

##### 三、一句话选择指南

> **登录网页任务，用 Chrome 扩展；桌面应用任务，用 Computer Use；前端开发调试，用内置浏览器。**

更进一步：

```text
有结构化工具/API/MCP → 优先用
需要登录态网页 → Chrome 扩展
需要操作桌面软件 → Computer Use
需要开发调试网页 → 内置浏览器
实在没有更好办法 → 视觉控制
```

---

##### 四、辩证思考

###### 1. 通用性和效率是矛盾的

Computer Use 最通用，因为它像人一样操作任何界面。

但正因为它像人，所以慢、易错、依赖界面变化。

结构化工具正好相反：

- 不通用；
- 但高效、稳定、可控。

所以未来的最佳模式不是“全靠 AI 看屏幕”，而是：

> **能调 API 就调 API，不能调 API 再模拟人。**

视觉操作是兜底能力，不是首选能力。

---

###### 2. 自动化越强，权限边界越重要

Chrome 扩展很强，因为它继承了你的登录状态。

但这也意味着风险更高。

AI 一旦能代表你点击、提交、发送、购买，它就不只是“助手”，而是在一定程度上拥有了你的行为能力。

所以关键不是“能不能自动化”，而是：

> **哪些动作可以自动化，哪些必须人类确认。**

合理边界应该是：

- AI 负责收集、分析、起草；
- 人负责确认、发布、付款、授权。

---

###### 3. AI 正从“回答问题”变成“完成流程”

这三种能力说明一个趋势：

> AI 不再只是聊天工具，而是在变成数字世界的执行者。

过去 AI 主要是：

- 解释；
- 总结；
- 写代码；
- 回答问题。

现在 AI 开始能：

- 操作软件；
- 浏览网页；
- 等待客服；
- 调试页面；
- 处理跨应用流程。

这意味着未来的生产力提升，不只是“写得更快”，而是：

> **很多低价值、重复性、跨界面的流程，可以被 AI 接管。**

---

##### 五、最终结论

Codex 的三种电脑操作方式，本质上对应三类需求：

- **Computer Use**：解决“任何界面都能操作”的问题；
- **Chrome 扩展**：解决“带登录态处理网页任务”的问题；
- **内置浏览器**：解决“开发调试高效反馈”的问题。

真正重要的不是记住三种工具，而是理解选择原则：

> **越结构化越优先，越接近真实用户操作越要谨慎。**

## 结构化（1）

### 2026-06-18 11:52:25

##### 主旨概括

文章总结了 Codex 操控电脑的三种方式：**Computer Use、Chrome 扩展、内置浏览器**。三者适用场景不同：需要登录状态用 Chrome，操作桌面应用用 Computer Use，做前端开发和页面调试用内置浏览器。

---

##### 1. Computer Use：覆盖最广，但速度最慢

**Computer Use** 让 Codex 像真人一样操作电脑：看屏幕、移动鼠标、点击按钮、输入文字。

###### 关键点

- 可操作几乎所有图形界面应用，例如：
  - Spotify
  - Xcode
  - 系统设置
  - iOS 模拟器
  - iPhone Mirroring
- 优点是适用范围广，尤其适合**没有 API 或插件支持的应用**。
- 缺点是速度慢：
  - 需要识别界面
  - 找按钮
  - 等页面响应
  - 再检查操作结果
- 相比之下，结构化插件或 API 可以直接调用，效率更高。

###### Mac 与 Windows 的差异

- **Mac**：Codex 可以在后台操作，用户仍可继续使用电脑。
- **Windows**：Codex 必须占据前台，操作期间用户基本不能使用那台机器。

###### 案例

Jason 曾经快递被偷，Amazon 客服需要等待约 **25 分钟** 才能接通。  
他让 Codex 每 **5 分钟** 检查一次客服聊天窗口，客服出现后改为每 **1 分钟** 检查，并自动完成退款流程。  
他去洗澡，回来时退款已经处理好了。

---

##### 2. Chrome 扩展：适合需要登录状态的网站任务

**Chrome 扩展** 可以让 Codex 使用你当前浏览器中的登录状态，包括 cookies、账号信息和已打开的标签页。

###### 适用场景

适合操作需要登录的网站或后台系统，例如：

- Gmail
- LinkedIn
- Salesforce
- 公司内部管理后台

###### 关键优势

- 能使用用户已有的登录状态，不需要重新登录。
- 能同时控制多个标签页：
  - 在一个标签页读取信息
  - 到另一个标签页对比内容
  - 再到第三个标签页完成操作
- 比 Computer Use 更理解浏览器环境：
  - Computer Use 主要识别屏幕坐标
  - Chrome 扩展理解浏览器层面的上下文

###### 案例

Jason 用 Chrome 扩展运行长期任务：

- 每天检查 Twitter 私信
- 浏览相关新闻
- 收集反馈
- 把有价值的信息保存到本地文件
- 但不自动发送任何消息

###### 注意事项

网站会把 Codex 的点击、提交表单等行为视为**用户本人操作**。  
因此：

- 研究、浏览、起草可以交给 Codex
- 发送、发布、付款等高风险操作，最好由用户自己确认

---

##### 3. 内置浏览器：适合开发者的隔离沙盒

**内置浏览器** 位于 Codex 的对话线程中，用户和 Codex 共享同一个渲染页面。

###### 关键特点

- 不携带登录状态
- 不使用 cookies
- 是一个隔离环境

这看似限制，但对开发场景反而很有用。

###### 适用场景

特别适合：

- 本地开发服务器调试
- 文件预览
- 公共网页查看
- 响应式布局检查
- 视觉 bug 复现

###### 开发反馈循环

Codex 可以：

1. 修改代码
2. 打开页面查看效果
3. 截图或检查页面
4. 再次修改代码
5. 重新运行验证

这样能形成很紧密的开发闭环。

###### 标注功能案例

Jason 最喜欢的是页面标注功能。用户可以直接在页面上点击某个元素并留言，例如：

- “这个层级反了”
- “这个按钮间距不够”

Codex 会结合截图和元素上下文去修改代码，改完后重新打开同一个页面，等待用户继续标注。  
这比反复传截图、用文字描述问题更高效。

---

##### 4. 如何选择这三种方式？

可以按任务类型简单判断：

| 需求 | 推荐方式 |
|---|---|
| 需要使用登录状态、cookies、账号会话 | Chrome 扩展 |
| 需要操作桌面软件或没有 API 的图形界面应用 | Computer Use |
| 做前端开发、页面调试、视觉检查 | 内置浏览器 |
| 有现成插件、API 或 MCP 能完成任务 | 优先使用结构化工具 |

---

##### 5. 核心结论

Codex 操控电脑的三种方式各有分工：  
**Computer Use 最通用但慢，Chrome 扩展最适合登录后的网页任务，内置浏览器最适合开发调试。**

如果任务能通过插件、API 或 MCP 等结构化工具完成，应优先使用这些方式；只有在没有更直接手段时，才使用视觉控制。
