## 分析要点

- **核心高价值点**：将代理任务隔离在编号工作树中，并通过机器级构建锁和FIFO落地队列串行化检查、变基与推送，可系统性降低并行代理的推送竞态、重复构建和共享资源测试抖动。
- **留存建议**：建议精读并存档，可作为本地并行编码代理协作与安全落地的实施参考（提供了可直接部署的工具、完整命令体系、配置示例、流程约束及明确的适用边界。）

**知识要点**

- 并行编码代理可以在独立Git工作树中执行任务，再通过本地FIFO队列串行完成检查、变基和推送。
- 预推送钩子可强制代理通过统一落地命令，并以明确分支名的紧急环境变量保留人工逃生通道。
- 本地队列只协调单台机器，检查命令耗时会直接形成吞吐瓶颈，且该工具不提供安全边界或人工审查。

**行动项**

- 在适用项目中安装claude-code-merge-queue并运行init，检查自动生成的配置、Claude设置和预推送钩子。
- 配置integrationBranch、checkCommand、端口和工作树规则，用两个并行代理验证构建锁与FIFO落地流程。
- 将land交给代理执行，将promote保留为人工操作，并测量完整检查命令对每小时落地次数的影响。

Claude Code Merge Queue — the local, zero-cost merge queue for parallel Claude Code agents

**The local, zero-cost merge queue for parallel Claude Code agents.** Several agents land, build, and test at the same time — this serializes it so push races, redundant heavy builds, and shared-resource test flakiness can't happen.

#### ⚡ Quickstart

```
npm install --save-dev claude-code-merge-queue   # or: pnpm add -D / yarn add -D / bun add -d
npx claude-code-merge-queue init
```

Terminal demo: npm install --save-dev claude-code-merge-queue, then npx claude-code-merge-queue init — writes the config, CLAUDE.md, the WorktreeCreate hook, and land/sync/promote/preview scripts

#### ⚙️ Configuration

Everything lives in one file — see `examples/claude-code-merge-queue.config.mjs` for every field with comments. The short version:

```
export default {
  branchPrefix: "lane/",               // lane/1, lane/2, ...
  worktreeSuffix: "-lane-",            // ../your-repo-lane-1
  portBase: 3000,                      // lane n gets portBase + n
  integrationBranch: "main",           // where agents land — see below
  productionBranch: null,              // set this for a two-stage model — see below
  protectedBranches: [],               // extra branches beyond the two above; most repos need none
  regenerableFiles: [],                // files a build tool rewrites — never block a rebase on these
  symlinks: [".env", ".env.local", "node_modules"],
  buildOutputDirs: ["dist", "build", ".next"], // preview never copies these onto your checkout
  checkCommand: "npm run check",       // what actually gates a landing — see below
  checksRequired: true,                // false = deliberately run with none; see below
};
```

A malformed config (empty branch names, a negative port, `productionBranch` equal to `integrationBranch`,...) fails loud with every problem listed, the moment any command loads it — not a mysterious failure three steps later.

Command What it does

`claude-code-merge-queue hook worktree-create` A Claude Code `WorktreeCreate` hook. Plugs Claude Code Merge Queue's numbered lanes into Claude's *native* worktree creation.

`claude-code-merge-queue build-lock -- <cmd>` Runs `<cmd>` — your build — serialized across every lane, machine-wide.

`claude-code-merge-queue land` Rebases and pushes your lane onto the integration branch through a FIFO queue, so two lanes are never mid-push at once. Agents run this themselves.

`claude-code-merge-queue sync` Fast-forwards your main checkout so a dev server actually sees what just landed — and re-installs dependencies if the lockfile changed.

`claude-code-merge-queue promote` Ships the integration branch to production. **Human-only** — never in an agent's instructions, never automated.

`claude-code-merge-queue preview` Instantly mirrors a lane's live working tree — uncommitted changes included — onto the main checkout, so you can look at it without a build.

`claude-code-merge-queue port` Prints a lane's dev-server port, derived from its own directory name.

`claude-code-merge-queue prune` Removes already-landed sibling lane worktrees on demand.

A pre-push hook makes `land` non-optional: a direct `git push` straight to the integration branch is rejected, with the actual command to run instead, and the same hook runs `checkCommand` before allowing a landing through — no checkCommand configured means every push fails by default. There's a way out for every block (see 🚨 The emergency hatch), but it takes naming the specific branch, not a generic flag.

- **`claude-code-merge-queue.config.mjs`** — `integrationBranch` and `checkCommand` auto-detected.
- **`CLAUDE.md`** (or appends to yours) — tells Claude Code to land its own work once green, without being asked.
- **`.claude/settings.json`** — the `WorktreeCreate` hook wired in, without touching anything else already there.
- **`.husky/pre-push`** — created or appended to, *if* you already have Husky. If you don't, `init` tells you rather than silently writing to the untracked `.git/hooks/pre-push`.
- **`package.json` scripts** — `land`, `sync`, `promote`, `preview`,`preview:restore`, skipping any you've already defined yourself.
- **`claude-code-merge-queue-preflight.mjs`** — a self-contained safety net that runs before `land` / `sync`, so a stale branch fails with a real diagnosis instead of a bare `command not found`.

Every blocked push — the integration branch, `productionBranch`, anything in `protectedBranches` — has a real way through it. One env var, no prompts, no second factor to remember:

```
CLAUDE_CODE_MERGE_QUEUE_EMERGENCY_PUSH=1 git push origin HEAD:main
```

This is a convention, not a hard guarantee: it stops mistakes and stray pushes, not an adversarial agent that sets the var itself.

- **No human reviews any of this before it lands.**`checkCommand` passing is the only gate — a real test suite and `echo ok` look identical to this tool. Want a human on every change? This is missing that step on purpose.
- **Locks are crash-safe by PID liveness, not a timeout.**`kill -9` anything mid-claim and the next process notices the PID is dead and reclaims it — no stale locks, no timeout to tune.
- **One machine, not a fleet.** The FIFO queue lives in local temp storage — two machines landing at once just get git's ordinary non-fast-forward rejection.
- **Not a security boundary.** Every guardrail here stops mistakes and convention drift, not an adversarial agent — shell access always means `git push --no-verify` or editing the config on purpose.
- **A slow `checkCommand` is a real throughput ceiling.** The FIFO lock holds for its entire duration — a 3–4 minute suite caps you well under 20 landings/hour.
- **Rebase conflicts abort, they never guess.**`git rebase --abort` on any conflict, working tree left clean — CLAUDE.md tells the agent to resolve it and re-run `land`.

#### Claude Code Merge Queue 项目总结

该项目是一个**本地、零成本的合并队列工具**，用于协调多个并行运行的 Claude Code Agent。它通过串行化构建、测试、变基和推送流程，避免推送竞争、重复构建以及共享资源导致的测试不稳定。

##### 1. 快速开始

安装方式：

```bash
npm install --save-dev claude-code-merge-queue
# 或 pnpm add -D / yarn add -D / bun add -d
```

初始化项目：

```bash
npx claude-code-merge-queue init
```

初始化命令会自动配置项目所需的钩子、脚本和 Claude Code 设置。

---

##### 2. 核心工作方式

项目将不同 Claude Code Agent 的工作安排到编号明确的 **lane（工作车道）** 中，例如：

- `lane/1`
- `lane/2`
- `lane/3`

每个 Agent 在独立的 Git worktree 中工作，之后通过本地 FIFO（先进先出）队列依次完成：

1. 变基到集成分支；
2. 运行检查或测试；
3. 推送代码；
4. 更新主工作目录。

这样可以确保同一时间不会有多个 Agent 同时推送，减少以下问题：

- 多个 Agent 同时 push 产生冲突；
- 多个 Agent 重复运行耗时构建；
- 多个工作区共享端口或资源，导致测试不稳定；
- 不同 Agent 的代码未同步就直接合并。

---

##### 3. 配置方式

所有配置集中在一个文件中：

```text
examples/claude-code-merge-queue.config.mjs
```

核心配置示例：

```js
export default {
  branchPrefix: "lane/",
  worktreeSuffix: "-lane-",
  portBase: 3000,
  integrationBranch: "main",
  productionBranch: null,
  protectedBranches: [],
  regenerableFiles: [],
  symlinks: [".env", ".env.local", "node_modules"],
  buildOutputDirs: ["dist", "build", ".next"],
  checkCommand: "npm run check",
  checksRequired: true,
};
```

主要字段含义：

- `branchPrefix`：工作分支前缀，例如 `lane/1`。
- `worktreeSuffix`：工作树目录后缀，例如 `../your-repo-lane-1`。
- `portBase`：端口起始值。第 `n` 个 lane 使用 `portBase + n`。
- `integrationBranch`：Agent 最终合并到的集成分支，通常是 `main`。
- `productionBranch`：生产分支，可用于配置“两阶段发布”流程。
- `protectedBranches`：额外需要保护的分支。
- `regenerableFiles`：构建工具会自动重写、因此不应阻止变基的文件。
- `symlinks`：需要在工作树之间共享或链接的目录和文件，例如 `.env`、`.env.local` 和 `node_modules`。
- `buildOutputDirs`：构建输出目录，例如 `dist`、`build` 和 `.next`。预览时不会将这些目录覆盖到主工作区。
- `checkCommand`：决定代码能否进入队列的检查命令，例如 `npm run check`。
- `checksRequired`：是否必须执行检查。设置为 `false` 表示明确关闭检查。

###### 配置校验

如果配置存在明显问题，例如：

- 分支名为空；
- 端口号为负数；
- `productionBranch` 与 `integrationBranch` 相同；

工具会在加载配置时一次性报告全部错误，而不是等到执行几步之后才出现难以理解的失败。

##### 4. 与 GitHub Merge Queue 的区别

| 对比项 | Claude Code Merge Queue | GitHub Merge Queue |
|---|---|---|
| 运行位置 | 本地机器 | GitHub 云端 |
| 适用范围 | 任意仓库、任意计划 | 主要面向 GitHub Enterprise Cloud 私有仓库 |
| 成本 | 免费，本机运行 | 消耗 GitHub Actions 分钟数 |
| 合并方式 | 直接变基并推送 | 通常依赖 Pull Request |
| 核心目标 | 串行合并、合并前检查、保持历史整洁 | 类似 |

该工具并不依赖 Pull Request，而是让 Agent 在本地直接完成变基和推送。

---

##### 5. 主要命令

###### `worktree-create`

```bash
claude-code-merge-queue hook worktree-create
```

这是 Claude Code 的 `WorktreeCreate` 钩子，用于将项目的编号 lane 接入 Claude Code 原生工作树创建流程。

###### `build-lock`

```bash
claude-code-merge-queue build-lock -- <cmd>
```

在所有 lane 之间串行执行构建命令。

例如：

```bash
claude-code-merge-queue build-lock -- npm run build
```

这样可以避免多个 Agent 同时执行耗时且占用大量资源的构建。

###### `land`

```bash
claude-code-merge-queue land
```

Agent 使用该命令将当前 lane：

1. 变基到集成分支；
2. 按 FIFO 队列等待；
3. 执行检查；
4. 推送到集成分支。

该机制保证任意时刻不会有两个 lane 同时处于推送过程中。

###### `sync`

```bash
claude-code-merge-queue sync
```

将主工作区快速前移到最新已合并内容，使开发服务器能够看到刚刚落地的代码。如果锁文件发生变化，还会重新安装依赖。

###### `promote`

```bash
claude-code-merge-queue promote
```

将集成分支发布到生产分支。

该命令是**仅限人工执行**的操作，不会放入 Agent 指令中，也不会自动执行。

###### `preview`

```bash
claude-code-merge-queue preview
```

将某个 lane 当前工作树的内容立即镜像到主工作区，包含尚未提交的修改。它适合快速查看效果，不需要先构建整个项目。

###### `port`

```bash
claude-code-merge-queue port
```

根据 lane 的目录名称计算并输出对应的开发服务器端口。

###### `prune`

```bash
claude-code-merge-queue prune
```

按需删除已经完成合并的旧 lane 工作树。

---

##### 6. 自动生成和接入的项目文件

执行 `init` 后，项目会根据已有内容进行补充，尽量不覆盖用户已有配置。

主要包括：

- **`CLAUDE.md`**  
  创建或追加说明，告诉 Claude Code 在检查通过后主动执行 `land`。

- **`.claude/settings.json`**  
  接入 `WorktreeCreate` 钩子，同时保留原有设置。

- **`husky/pre-push`**  
  如果项目已使用 Husky，则创建或追加 pre-push 钩子。  
  如果没有 Husky，工具会提示用户，而不会悄悄创建未跟踪的 `.git/hooks/pre-push` 文件。

- **`package.json` scripts**  
  自动添加 `land`、`sync`、`promote`、`preview` 和 `preview:restore` 等脚本，但不会覆盖用户已经定义的同名脚本。

- **`claude-code-merge-queue-preflight.mjs`**  
  一个独立的安全检查脚本，在 `land` 或 `sync` 前运行，帮助诊断过期分支等问题，而不是只返回模糊的“命令不存在”。

此外，项目还会自动检测：

- `integrationBranch`
- `checkCommand`

---

##### 7. 推送保护与检查机制

项目提供 pre-push 保护，防止直接向集成分支推送。

例如，直接执行：

```bash
git push origin main
```

会被拒绝，并提示用户改用正确的 `land` 命令。

以下分支都会受到保护：

- 集成分支；
- `productionBranch`；
- `protectedBranches` 中配置的分支。

###### 检查命令是唯一的自动门槛

如果配置了：

```js
checkCommand: "npm run check"
```

那么只有检查通过后，代码才允许进入落地流程。

如果没有配置 `checkCommand`，默认情况下所有推送都会失败，从而避免在未定义质量门槛时误合并。

不过，该工具**不会进行人工代码审查**。例如，真正的测试套件与下面的命令在工具看来没有区别：

```bash
echo ok
```

因此，项目是否具备有效的质量控制，取决于用户配置的 `checkCommand`。

---

##### 8. 紧急推送机制

当正常流程被阻塞时，可以针对具体分支使用环境变量绕过保护：

```bash
CLAUDE_CODE_MERGE_QUEUE_EMERGENCY_PUSH=1 git push origin HEAD:main
```

该机制具有以下特点：

- 不需要交互式确认；
- 不需要额外记忆复杂的参数；
- 必须明确指定目标分支；
- 不能仅靠一个通用的“强制模式”绕过所有保护。

但它只是**防误操作机制，不是安全边界**。拥有 shell 权限的恶意 Agent 仍然可以执行：

```bash
git push --no-verify
```

或者直接修改配置文件。

---

##### 9. 锁与队列的可靠性

项目使用基于进程 PID 存活状态的锁，而不是固定超时。

例如：

1. 某个进程获取锁后异常退出；
2. 下一个进程发现原 PID 已不存在；
3. 自动回收该锁并继续执行。

因此，即使中途执行 `kill -9`，也不会长期留下需要手动清理的过期锁，也不需要调整超时时间。

---

##### 10. 冲突处理方式

如果变基过程中发生冲突，工具不会擅自猜测或自动修改代码，而是：

1. 执行 `git rebase --abort`；
2. 保持工作树干净；
3. 让 Agent 解决冲突；
4. 解决后重新执行 `land`。

这种设计优先保证代码状态可控，避免自动合并造成隐蔽错误。

---

##### 11. 已知限制

###### 只能在单台机器上运行

队列数据存储在本地临时目录中，适用于单机多 Agent 场景。

如果两台机器同时尝试落地，工具无法协调它们，最终只能依赖 Git 的普通 non-fast-forward 拒绝机制。

###### 不是安全边界

所有保护措施主要用于：

- 防止误操作；
- 减少流程偏差；
- 强制团队遵循约定。

它无法抵御具有完整 shell 权限并且主动绕过规则的 Agent。

###### 检查时间会限制吞吐量

FIFO 锁会在整个 `checkCommand` 执行期间持续占用。

如果检查套件每次耗时 **3～4 分钟**，那么整体吞吐量会被限制在**每小时 20 次落地以内**，实际速度还可能更低。

###### 没有自动人工审批

只要 `checkCommand` 通过，代码就可能进入集成分支。该工具特意不包含“每次变更都必须由人审核”的步骤。

---

##### 12. 项目定位与许可证

该项目适合希望在本地运行多个 Claude Code Agent，并需要统一协调以下流程的团队或个人：

- 独立工作树管理；
- 构建资源互斥；
- 测试与检查；
- 变基；
- 顺序推送；
- 集成分支发布。

## 口播总结（1）

### 2026-08-03 00:39:45

#### Claude Code 本地合并队列：让多个智能体并行工作而不互相干扰

这款名为 Claude Code Merge Queue 的工具，解决的是一个实际问题：多个 Claude Code 智能体同时开发时，如何避免抢着推送代码、重复执行重型构建，以及因共享资源引发测试波动。听完这份总结，你可以了解它的工作方式、主要功能、安全机制，以及它明确存在的限制。

##### 首先，它解决的核心问题是什么

核心结论是：它让多个智能体并行开发，但把构建、检查和代码落地这些容易冲突的环节排成队列，依次执行。

这里的“合并队列”，就是让代码变更按照先来后到的顺序接受检查，再进入主分支。“落地”则是把某个智能体完成的代码，经过变基和测试后，推送到集成分支。

每个智能体会在独立的 Git 工作树中工作。工作树可以理解为同一个代码仓库的多个独立工作目录。工具把这些目录称为“车道”，并用 lane 1、lane 2 这样的编号区分。各个车道可以同时写代码，但需要共享资源时，就由队列协调。

这套方案完全运行在本机，不依赖云端服务，也不需要为每次合并消耗 GitHub Actions 的运行时间。安装时，可以使用 npm、pnpm、yarn 或 bun。以 npm 为例，安装开发依赖后，再运行初始化命令即可。

##### 接下来，所有规则都集中在一个配置文件里

核心结论是：项目的分支、端口、构建检查和共享文件规则，都由一个配置文件统一管理。

配置中可以指定车道分支的前缀，以及各个工作树目录的命名方式。还可以设置基础端口。例如基础端口是三千，那么第几个车道就使用基础端口加上自己的编号，避免多个开发服务器争抢同一个端口。

配置还要区分“集成分支”和“生产分支”。集成分支是智能体日常提交代码的目标，比如 main。生产分支是可选的，适合采用“两阶段发布”的项目：先把代码放进集成分支，再由人决定何时发布到生产分支。

此外，还可以配置受保护分支、可重新生成的文件、需要建立符号链接的目录，以及构建输出目录。像环境变量文件和 node_modules，可以在各车道之间通过符号链接共享。dist、build 和 Next.js 的构建目录则不会在预览时复制到主工作区，避免无意义的大量文件操作。

真正决定代码能否落地的是检查命令，也就是 checkCommand。它通常会运行测试、类型检查或代码规范检查。默认理念是“必须检查”：如果没有配置检查命令，推送会直接失败。只有明确把 checksRequired 设为 false，才表示项目有意不设置检查门槛。

配置错误也会尽早暴露。比如分支名为空、端口为负数，或者生产分支和集成分支相同，工具会在任何命令读取配置时立刻列出全部问题，而不是等到后续步骤才以模糊错误失败。

##### 和 GitHub 的合并队列相比，它更轻量，但目标相似

核心结论是：两者都希望串行处理代码落地、先测试后合并，并保持提交历史整洁；区别在于，这款工具完全在本地运行。

GitHub 的合并队列通常要求先创建拉取请求。对于私有仓库，相关能力还可能依赖 Enterprise Cloud，并且每次排队尝试都会消耗 GitHub Actions 时间。

Claude Code Merge Queue 不要求拉取请求。它直接在本机完成变基、检查和推送，支持任何套餐和仓库，单次落地的额外云端运行成本为零。

不过，这种轻量化也意味着它没有内置人工审核。工具故意省略了“每次变更必须由人批准”这一步。代码能否进入集成分支，只取决于检查命令是否通过。

##### 更重要的是，它提供了一套完整的本地协作命令

首先是创建工作树的钩子。它能接入 Claude Code 原生的工作树创建流程，自动把新的智能体安排到编号车道中。

接下来是 build-lock，也就是构建锁。它会在整台机器范围内串行执行指定的构建命令。这样，多个车道不会同时争用同一个缓存、数据库或其他共享资源。

最关键的命令是 land，也就是落地。它通过先进先出的队列处理车道代码。先进先出，简称 FIFO，意思是谁先申请，谁先执行。land 会把当前车道变基到集成分支，再执行检查并推送，从而确保不会有两个车道同时处于推送过程。设计上，智能体应当在工作完成并通过检查后，自己运行这个命令。

sync 命令用于同步主工作区。它会把主工作区快进到刚刚落地的版本。如果依赖锁文件发生变化，它还会重新安装依赖，确保本地开发服务器看到的是最新代码。

promote 命令用于把集成分支发布到生产分支。这个操作明确只应由人执行，不能写进智能体的指令，也不应自动触发。

preview 命令负责预览。它会把某个车道当前的工作目录快速映射到主工作区，连尚未提交的改动也包括在内，因此无需先完成构建就能查看效果。需要恢复时，还可以使用对应的 restore 命令。

此外，port 命令会根据车道目录名计算并输出开发服务器端口。prune 命令则用于清理已经完成落地的其他车道工作树。

##### 为了防止绕过队列，它会接管推送入口

核心结论是：工具通过 Git 的 pre-push，也就是“推送前钩子”，阻止智能体直接向受保护分支推送。

如果有人直接执行 git push，把代码送到集成分支，推送会被拒绝，并提示应该使用哪条 land 命令。这个钩子还会在允许落地前运行检查命令。因此，land 不是一个可有可无的建议，而是默认必须经过的流程。

初始化时，工具会自动识别集成分支和检查命令，并创建或补充若干项目文件。它会更新 Claude 的项目说明，让 Claude Code 知道代码通过检查后应该自行落地；也会在 Claude 设置中接入工作树创建钩子，同时保留已有配置。

如果项目已经使用 Husky，也就是一种常见的 Git 钩子管理工具，初始化过程会创建或追加 pre-push 文件。如果项目没有 Husky，它会明确提醒，而不是悄悄把脚本写入可能未被版本控制的 Git 钩子目录。

它还会为 package.json 添加 land、sync、promote 和 preview 等脚本，但不会覆盖项目已经定义的同名脚本。另外，一个独立的预检脚本会在 land 和 sync 之前运行。如果分支状态过旧，它会给出具体诊断，而不是只报一个难以理解的“找不到命令”。

##### 所有拦截机制都有紧急出口，但它不是安全边界

核心结论是：受保护分支可以在紧急情况下直接推送，但必须明确表示这是一次紧急操作。

具体做法是设置名为 `CLAUDE_CODE_MERGE_QUEUE_EMERGENCY_PUSH` 的环境变量，并将它设为一，然后执行 Git 推送，同时明确写出目标分支。例如，要推送到 main，就必须明确指定 main，而不是只使用一个泛化的跳过检查选项。

这种设计可以减少误操作，也能阻止随手执行的直接推送。但是，它只是一套协作约定，不是强制性的安全防线。拥有终端权限的智能体或用户，仍然可以主动设置这个环境变量、使用 `git push --no-verify`，或者直接修改配置。

换句话说，它防的是疏忽和流程漂移，不是有意绕过规则的对手。

##### 最后，要清楚它的能力边界

第一，没有人工审核。检查命令是唯一门槛。对工具来说，一套严格的完整测试，和一条只输出“成功”的命令，看起来没有区别。如果项目要求每次改动必须由人审查，这款工具并没有提供那个步骤。

第二，它只协调一台机器，而不是一个机器集群。队列保存在本机临时目录中。如果两台机器同时向同一分支落地，它们不会共享队列，只会遇到 Git 普通的“非快进推送被拒绝”。

第三，锁虽然可靠，但不会提升检查速度。锁通过进程编号，也就是 PID，判断持锁进程是否仍然存活，而不是依赖超时。即使某个进程被强制终止，下一个进程也能发现原进程已经死亡，并自动回收锁，不需要调整超时时间。

但检查命令会在整个执行期间一直占用队列。如果一套测试需要三到四分钟，那么每小时的落地次数会明显低于二十次。测试越慢，整体吞吐量越低。

第四，遇到变基冲突时，工具不会自行猜测如何解决。它会执行 rebase abort，也就是中止变基，并保持工作区干净。之后由智能体解决冲突，再重新运行 land。

这款工具采用 MIT 许可证，允许自由使用、修改、分叉和重新命名。

##### 值得记住的几个结论

第一，它让多个 Claude Code 智能体并行开发，同时把构建、测试和推送串行化，避免资源冲突和推送竞争。

第二，它完全运行在本机，不要求拉取请求，也不消耗 GitHub Actions 的合并队列运行时间。

第三，land 和推送前钩子共同保证代码先检查、再落地；promote 则明确保留给人类执行。

第四，它没有人工审核，也不是安全边界。检查命令的质量，直接决定了落地门槛的质量。

第五，它最适合单机、多智能体的开发环境。测试速度仍然决定吞吐量，多台机器之间也不会共享同一个队列。

## 深度解读（1）

### 2026-09-18 00:15:16

#### 多个 AI 同时写代码后，真正的瓶颈变成了“如何安全落地”

这个项目解决的不是“让 Claude Code 写得更快”，而是一个更靠后的问题：**当多个代理并行工作时，代码生成可以并行，集成过程却不能完全并行。**

不同代理可以待在各自的 Git worktree 中，使用不同端口互不干扰；但它们若同时构建、测试、rebase 和 push，就会争用本机资源、重复执行重型任务，甚至让两个本来正确的改动因共享测试环境而随机失败。`claude-code-merge-queue` 的做法很直接：保留开发阶段的并行性，只把必须互斥的环节串行化——构建使用机器级锁，合入则进入 FIFO 队列，依次完成 rebase、检查和 push。

##### Agent 工作流需要协议，而不只是提示词

项目最值得借鉴的不是某条命令，而是它把“请代理谨慎操作”改造成了**默认不可绕过的执行路径**。

例如，pre-push hook 会拒绝直接推送集成分支，并告诉代理应运行哪个命令；没有配置检查命令时默认拒绝，而不是默认为通过；配置错误在加载时一次性暴露；锁不依赖超时，而是检查持锁进程是否仍然存活；遇到 rebase 冲突则中止并恢复干净状态，不让代理自行猜测如何合并。紧急绕过仍然存在，但必须明确写出目标分支和环境变量。

这反映出一个重要的产品判断：**自主代理的可靠性，越来越取决于环境是否把正确行为做成“最省力的路径”，而不是代理能否始终理解并遵守长篇说明。** 提示词负责表达意图，工具则应负责状态检查、资源隔离、失败恢复和权限边界。对其他 Agent 产品，这套思路同样适用于数据库迁移、部署、文件写入和外部 API 调用。

##### 它协调的是可信代理，不是替代质量治理

这个工具也清楚地暴露了边界：合入前没有人工审查，唯一门槛是 `checkCommand`。真实测试套件和 `echo ok` 对它没有区别。因此，它能保证的是“流程按顺序执行”，不能保证改动正确，更不能保证代理没有恶意。拥有 shell 权限的代理仍可使用 `--no-verify`、修改配置或主动设置紧急变量。

性能边界也很明确：检查期间队列一直被占用，如果测试耗时四分钟，理论吞吐量就低于每小时十五次；队列状态只保存在本机，两台机器同时工作时仍只能依赖 Git 的非快进拒绝。它更适合**单机、可信、并发度有限的本地代理环境**，而不是团队级分布式发布系统。

真正值得关注的趋势是：随着编码代理从单任务走向并行协作，新的基础设施机会不会只在“更强的模型”，还会出现在代理之间的调度、隔离、验证与交付协议上。生成代码正在变便宜，而**决定哪些动作可以并行、哪些必须串行，以及失败后如何回到可恢复状态**，会成为更稀缺的工程能力。

## 默认总结（1）

### 2026-09-18 01:19:36

##### 一句话看懂

这是一个给并行 Claude Code 智能体使用的本地合并队列：把构建、测试和推送依次执行，避免多个智能体同时操作造成冲突、重复构建或测试不稳定。

##### 关键内容

- 工具运行在开发者自己的机器上，不要求创建 PR，也不消耗 GitHub Actions 分钟；各智能体在独立 worktree“车道”工作，完成后通过 FIFO（先到先执行）队列变基并推送到集成分支。
- 它可统一分配端口、串行构建、同步主目录、预览未提交改动，并用 pre-push 钩子阻止绕过队列的直接推送；正式发布命令被设计为仅由人工执行。
- 合并是否放行只取决于配置的 `checkCommand`。工具**不包含人工审查**，也无法判断测试是否充分；紧急环境变量、`--no-verify` 等方式仍可绕过限制。
- 主要局限是仅协调单机：多台机器并发时仍靠 Git 拒绝非快进推送；检查期间会一直占用队列，测试越慢，合并吞吐量越低；变基冲突会中止，交给智能体处理。

##### 通俗解读

它更像“单机交通指挥”，不是安全系统：能减少多个智能体抢着推代码的操作事故，却不能保证代码质量或阻止主动绕过规则。若你正在一台机器上并行运行多个 Claude Code 智能体，值得细读配置与限制；普通单智能体或必须人工审查的团队，实用价值较小。
