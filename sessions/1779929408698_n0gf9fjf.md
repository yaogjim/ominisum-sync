### 回答 · 2026-05-28 00:49:12

可以的，你的记忆大概率没错：**yetone 的 Yansu 应该不是开源项目**。但 “用 DeepSeek 分析了一下架构” 不一定是指看了源码，更可能是指：

> 下载 Yansu 客户端后，对应用包 / 二进制 / 前端资源 / 运行时特征做静态或动态分析，然后把结果喂给 DeepSeek，让它帮忙判断技术栈和架构。

这类分析通常只能推断 “用什么框架、前后端如何通信、大概模块结构”，不能等同于完整源码级架构分析。

---

##### 一、为什么不开源也能看出它用了 Wails？

Wails 的应用通常有一些比较明显的特征。

Wails 是一个 Go 桌面应用框架，常见结构是：

```text
Go 后端
  ├─ 业务逻辑
  ├─ 本地文件 / 系统 API
  ├─ 数据库 / 网络请求
  └─ 暴露方法给前端调用

前端
  ├─ React / Vue / Svelte / Solid / 原生 JS 等
  ├─ 打包后的 JS/CSS/HTML
  └─ 通过 Wails runtime 调用 Go 方法

运行容器
  ├─ macOS: WKWebView
  ├─ Windows: WebView2
  └─ Linux: WebKitGTK
```

所以如果你拿到一个已经打包的 App，就有可能看到：

- 可执行文件里有`wails`字符串；
- 前端资源里有`wailsjs`、`runtime`、`window.go`等痕迹；
- macOS app bundle 里有被嵌入的 JS / CSS / HTML；
- Go 编译信息里能看到 module 依赖；
- 运行时表现像 “本地 Go 后端 + WebView 前端”。

---

##### 二、可能的分析路径

以 macOS 为例，如果从`https://yansu.app/`下载到`.dmg`或`.zip`，安装后一般会得到类似：

```text
Yansu.app
└── Contents
    ├── Info.plist
    ├── MacOS
    │   └── Yansu
    ├── Resources
    └── Frameworks
```

可以做这些检查。

###### 1. 看 App 包结构

```bash
cd /Applications/Yansu.app
find Contents -maxdepth 3 -type f | sed's#^\./##'
```

如果里面有明显的前端资源，例如：

```text
index.html
assets/index-xxxx.js
assets/index-xxxx.css
```

那基本可以判断它不是纯原生 App，而是 WebView 类架构。

---

###### 2. 看二进制文件类型

```bash
file /Applications/Yansu.app/Contents/MacOS/Yansu
```

可能会看到：

```text
Mach-O 64-bit executable arm64
```

然后可以看动态链接：

```bash
otool -L /Applications/Yansu.app/Contents/MacOS/Yansu
```

如果是 Wails，通常不会像 Electron 那样带一个巨大的 Chromium，而是使用系统 WebView，所以体积和依赖结构会更 “轻”。

---

###### 3. 搜索 Wails 痕迹

```bash
strings /Applications/Yansu.app/Contents/MacOS/Yansu | grep -i wails | head -50
```

如果看到类似：

```text
github.com/wailsapp/wails/v2
wails/runtime
wailsjs
```

那基本就很明显了。

也可以搜：

```bash
strings /Applications/Yansu.app/Contents/MacOS/Yansu | grep -i "github.com" | head -100
```

Go 程序常常会把一些 module 路径、panic 信息、符号名等编译进二进制里。

---

###### 4. 用`go version -m`看 Go module 信息

如果它是 Go 编译出来的二进制，可以试：

```bash
go version -m /Applications/Yansu.app/Contents/MacOS/Yansu
```

很多 Go 程序会暴露构建信息，例如：

```text
/path/to/Yansu: go1.22.x
        path    ...
        mod     ...
        dep     github.com/wailsapp/wails/v2 ...
        dep     ...
```

如果这里出现`github.com/wailsapp/wails/v2`，那就能比较直接地确认它用了 Wails。

不过注意：开发者可以通过构建参数裁剪或隐藏部分信息，所以没有看到不代表一定不是。

---

###### 5. 看前端资源

可以找资源文件：

```bash
find /Applications/Yansu.app/Contents -iname "*.js" -o -iname "*.html" -o -iname "*.css"
```

如果找到打包后的 JS，可以 grep：

```bash
grep -R "wails" /Applications/Yansu.app/Contents/Resources 2>/dev/null | head
grep -R "window.go" /Applications/Yansu.app/Contents/Resources 2>/dev/null | head
grep -R "runtime" /Applications/Yansu.app/Contents/Resources 2>/dev/null | head
```

Wails 生成的前端绑定经常会有类似调用：

```js
window.go.SomePackage.SomeMethod (...)
```

或者导入：

```js
import { EventsOn, EventsEmit } from "../wailsjs/runtime/runtime"
```

这会暴露出前端如何调用 Go 后端。

##### 三、DeepSeek 在这里可能怎么用？

“用 DeepSeek 分析” 通常不是 DeepSeek 直接访问了闭源仓库，而是人把分析材料丢给它，例如：

1. App 文件目录树；
2. `go version -m`输出；
3. `strings | grep`的结果；
4. 前端 JS 片段；
5. `Info.plist`内容；
6. 网络请求抓包摘要；
7. 运行时日志；
8. 截图、配置文件、包大小等。

然后问 DeepSeek：

> 根据下面这些文件结构和字符串，判断这个桌面应用可能用了什么技术栈？

或者：

> 这些 JS 代码里出现`window.go.main.App.Method`，这是什么框架？

DeepSeek 很可能会回答：这是 Wails 的典型结构。

##### 五、能分析到什么程度？

如果没有源码，一般可以分析到：

###### 可以比较可靠地判断

- 是否是 Wails / Electron / Tauri / Flutter / Qt / 原生；
- 后端语言可能是 Go；
- 前端框架可能是 React / Vue / Svelte 等；
- 是否使用 WebView；
- 前端和后端通信方式；
- 部分暴露给前端的 Go 方法名；
- 一些第三方依赖；
- API endpoint；
- 本地数据存储位置；
- 是否有 SQLite、LevelDB、配置文件等。

###### 很难准确判断

- 真实业务模块边界；
- 完整后端代码结构；
- 私有算法；
- 服务端架构；
- 数据库 schema 的全部设计；
- 状态机实现；
- 内部权限模型；
- 构建流水线；
- 未暴露的 Go 方法。

所以 “分析 Yansu 架构” 更准确地说应该是：

> 基于发布产物推断 Yansu 客户端的技术栈和大致运行架构。

而不是：

> 读了 Yansu 的源码并理解了完整架构。

##### 六、为什么会判断 “Go 后端 + JS 前端”？

因为 Wails 的核心模式就是这样：

```text
JS 前端界面
    ↓
Wails runtime / JS bindings
    ↓
Go 方法调用
    ↓
本地业务逻辑 / 网络请求 / 文件系统 / 数据库
```

例如前端可能会调用：

```js
window.go.main.App.GetSettings ()
window.go.main.App.SaveNote (content)
window.go.main.App.Login (token)
```

这些方法对应 Go 里被绑定的 struct 方法。

Go 侧可能类似：

```go
type App struct {}

func (a *App) GetSettings () Settings {
    //...
}

func (a *App) SaveNote (content string) error {
    //...
}
```

Wails 构建时会生成前端绑定，让 JS 可以直接调用 Go 方法。

所以只要前端包里暴露了类似绑定，就很容易看出 “后端 Go + 前端 JS” 的组合。

---

##### 七、需要注意的边界

这类分析最好只做：

- 技术栈识别；
- 安全研究；
- 性能和架构学习；
- 兼容性排查；
- 公开发布产物的元信息分析。

不要做：

- 绕过授权；
- 破解功能限制；
- 反编译还原源码并传播；
- 提取密钥；
- 未授权访问服务端 API；
- 分发修改版客户端。

尤其是闭源商业应用，分析时要尊重作者许可和法律边界。

### 回答 · 2026-05-28 00:52:16

下面按 “**合法授权 / 学习研究 / 自己写的程序或明确允许分析的程序**” 这个前提，讲一下：一个用**Go + Wails**编写并打包后的桌面程序，如何借助 DeepSeek 做技术栈识别、结构分析和行为理解。

核心思路是：

> DeepSeek 本身不是逆向工具，它更像 “分析助手”。  
> 你先用常规工具提取目录结构、字符串、Go 构建信息、前端资源、日志、网络行为等材料，再让 DeepSeek 帮你归纳架构、解释调用链、识别框架特征。

---

#### 1. Wails 程序打包后大概长什么样？

Wails 是典型的：

```text
Go 后端逻辑
    +
前端 JS/HTML/CSS
    +
系统 WebView
```

运行模式大致是：

```text
前端界面 React/Vue/Svelte/ 原生 JS
        ↓
Wails JS runtime
        ↓
window.go.xxx.xxx 调用
        ↓
Go 方法
        ↓
本地文件 / 数据库 / 网络请求 / 系统 API
```

打包后，通常会有这些痕迹：

- 二进制是 Go 编译产物；
- 可能包含`github.com/wailsapp/wails/v2`；
- 前端资源里可能有`wailsjs`；
- JS 里可能有`window.go.xxx`；
- macOS 用`.app`；
- Windows 用`.exe`，依赖 WebView2；
- Linux 可能依赖 WebKitGTK。

---

#### 2. 分析目标可以分成几类

建议你把 “逆向分析” 拆成几个相对温和、合法的技术目标：

##### 可以做的分析

- 判断是否使用 Wails；
- 判断 Go 版本和依赖；
- 判断前端框架：React / Vue / Svelte 等；
- 分析前后端通信方式；
- 分析暴露给前端的 Go 方法名；
- 分析配置文件和本地数据目录；
- 分析网络请求域名和接口形态；
- 分析日志格式；
- 分析应用整体模块边界。

##### 不建议做的事情

- 绕过授权、会员、许可证；
- 提取私钥、token、密钥；
- 修改二进制绕过限制；
- 未授权调用服务端接口；
- 还原并传播闭源代码；
- 绕过加密或安全校验。

---

#### 3. 静态分析：先收集证据

下面以 macOS / Linux / Windows 分别举例。

---

##### 3.1 macOS：分析`.app`

假设程序是：

```bash

```

###### 查看包结构

```bash

```

可以把结果保存：

```bash
find /Applications/MyApp.app -maxdepth 5 -type f > files.txt
```

```text
MyApp.app/
└── Contents/
    ├── Info.plist
    ├── MacOS/
    │   └── MyApp
    ├── Resources/
    └── Frameworks/
```

---

###### 查看二进制类型

```bash
file /Applications/MyApp.app/Contents/MacOS/MyApp
```

可能输出：

```text
Mach-O 64-bit executable arm64
```

或者：

```text
Mach-O universal binary with 2 architectures
```

---

###### 查看动态依赖

```bash
otool -L /Applications/MyApp.app/Contents/MacOS/MyApp
```

如果是 Wails，通常不会像 Electron 那样携带完整 Chromium，而是使用系统 WebView。

###### 查看 Info.plist

```bash
plutil -p /Applications/MyApp.app/Contents/Info.plist
```

- 权限声明；
- URL Scheme；
- app 名称；

#### 4. 判断是不是 Go 程序

Go 编译的二进制通常可以用：

```bash
go version -m ./MyApp
```

macOS 例子：

```bash
go version -m /Applications/MyApp.app/Contents/MacOS/MyApp
```

如果成功，可能看到：

```text
/Applications/MyApp.app/Contents/MacOS/MyApp: go1.22.5
        path    example.com/myapp
        mod     example.com/myapp    devel
        dep     github.com/wailsapp/wails/v2 v2.9.1
        dep     github.com/go-sql-driver/mysql ...
        dep     github.com/mattn/go-sqlite3 ...
```

如果出现：

```text
dep github.com/wailsapp/wails/v2
```

基本可以判断用了 Wails。

如果没有输出，也不代表不是 Go。开发者可能做了裁剪、混淆、去符号或者使用了特殊构建参数。

#### 6. 找前端资源

Wails 程序通常会把前端构建产物嵌入 Go 二进制，或者以资源形式打包。

有些情况下能直接看到：

```text
index.html
assets/index-xxxxx.js
assets/index-xxxxx.css
```

可以查找：

```bash
find . -iname "*.js" -o -iname "*.html" -o -iname "*.css"
```

```bash
find /Applications/MyApp.app/Contents -iname "*.js" -o -iname "*.html" -o -iname "*.css"
```

如果找到了 JS 文件，可以搜索：

```bash
grep -R "wails" ./ 2>/dev/null | head
grep -R "wailsjs" ./ 2>/dev/null | head
grep -R "window.go" ./ 2>/dev/null | head
grep -R "runtime.EventsOn" ./ 2>/dev/null | head
```

常见 Wails 前端调用痕迹：

```js
window.go.main.App.GetConfig ()
window.go.main.App.SaveSettings (data)
window.go.main.App.ListProjects ()
```

或者：

```js
import { EventsOn, EventsEmit } from "../wailsjs/runtime/runtime";
```

这些信息可以帮助你推断：

- Go 端暴露了哪些方法；
- 前端有哪些页面；
- 前端调用后端的边界在哪里；
- 应用大概有哪些业务模块。

```text
[粘贴片段]
```

#### 8. 分析 Go 二进制中的符号

如果 Go 程序没有去符号，可以看到较多函数名。

##### Linux /macOS

#### 11. 分析 Wails 前后端绑定

Wails 的一个关键点是：Go 方法可以暴露给 JS。

Go 端可能类似：

```go
type App struct {}

func (a *App) GetSettings () Settings {
    return settings
}

func (a *App) SaveSettings (s Settings) error {
    return save (s)
}
```

前端可能调用：

```js
window.go.main.App.GetSettings ()
window.go.main.App.SaveSettings (settings)
```

如果 bundle 里能搜到这些调用，就能建立一个表：

| 前端调用 | 可能的 Go 方法 | 可能功能 |
|---|---|---|
| `window.go.main.App.GetSettings ()` | `App.GetSettings` | 获取配置 |
| `window.go.main.App.SaveSettings ()` | `App.SaveSettings` | 保存配置 |
| `window.go.main.App.ListFiles ()` | `App.ListFiles` | 读取本地文件 |
| `window.go.main.App.ExportData ()` | `App.ExportData` | 导出数据 |

你可以让 DeepSeek 帮你整理：

```text
请把下面这些 window.go 调用整理成表格：
1. 方法名；
2. 参数；
3. 返回值推测；
4. 可能对应的业务模块；
5. 风险点或需要进一步验证的地方。

调用列表如下：

window.go.main.App.GetSettings ()
window.go.main.App.SaveSettings (e)
window.go.main.App.ListProjects ()
window.go.main.App.OpenFileDialog ()
window.go.main.App.ExportProject (t)
```

#### 16. 一个完整的最小化流程

假设你有一个授权分析的 Wails 应用：

```bash
./MyApp
```

可以这样做：

```bash
mkdir analysis
cd analysis

# 1. 文件类型
file ../MyApp > file.txt

# 2. Go 构建信息
go version -m ../MyApp > go-version.txt 2>&1

# 3. 字符串
strings ../MyApp > strings.txt

# 4. 过滤关键线索
grep -Ei "wails|wailsjs|window.go|github.com|go1\.|sqlite|webview|webkit|EventsOn|EventsEmit" strings.txt > key-strings.txt

# 5. 如果有解包后的资源目录
find ../-maxdepth 5 -type f > files.txt

# 6. 搜 JS 痕迹
grep -R "window.go" ../ 2>/dev/null > window-go.txt
grep -R "EventsOn" ../ 2>/dev/null > events-on.txt
grep -R "EventsEmit" ../ 2>/dev/null > events-emit.txt
```

然后把这些文件的关键内容喂给 DeepSeek。

#### 17. DeepSeek 分析时的几个技巧

##### 17.1 不要一次塞太多

二进制字符串、bundle JS 可能非常大。建议先筛选：

```bash
grep -Ei "wails|window.go|EventsOn|EventsEmit|github.com|sqlite|api|config|sync|auth" strings.txt
```

然后分批发送。

##### 17.2 要求它标注 “证据等级”

你可以这样要求：

```text
请把每个结论按证据强度分类：

- 中：根据调用名和依赖推断；
```

这样可以避免 LLM 一本正经地胡猜。

```text
请不要过度推断。对于无法确认的内容，请明确标注 “不确定”。
```

##### 17.4 要求它给出 “进一步验证命令”

```text
请针对每个推断给出后续可验证的命令或观察方法。
```

#### 19. 从 “逆向” 角度能得到什么，得不到什么？

##### 通常能得到

- 技术栈；
- 打包框架；
- Go 版本；
- 一部分依赖；
- 前端路由；
- 前端页面组件线索；
- 部分 API 地址；
- 部分 Go 暴露方法名；
- 事件名；
- 本地配置和数据目录；
- 大致模块划分。

##### 通常得不到或不可靠

- 完整 Go 源码；
- 精准包结构；
- 完整业务逻辑；
- 服务端内部架构；
- 数据库完整设计；
- 未暴露给前端的私有方法；
- 构建流水线；
- 开发者真实设计意图。

所以更准确的说法是：

> 基于发布产物进行架构推断，而不是完整源码级逆向。
