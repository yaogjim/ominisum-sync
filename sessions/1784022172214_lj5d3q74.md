- 任务验证基础设施应同时覆盖一键启动、界面或接口驱动、回归检查、证据生成与可审阅发布。

#### 文章主旨

`verifier-setup`是一个**一次性初始化工具**：它不负责直接验证某项开发任务，而是为代码仓库搭建一套可重复使用的验证体系，让后续`/verify`能在代码发布前启动应用、执行操作、收集截图或视频，并将证据附到 PR 中。

##### 1. 最终要交付的 3 类成果

完整运行后，仓库应具备：

1. **`/verify`验证技能**
   - 默认路径：`.claude/skills/verify/SKILL.md`
   - 定义单次任务的验证流程：
     1. 启动 verifier 子代理；
     2. 操作应用；
     3. 生成截图或视频证据；
     4. 创建 PR，并在 PR 中嵌入证明材料。

2. **一键启动开发环境**
   - 脚本：`scripts/dev-local.sh`
   - 技能文档：`.claude/skills/dev-local/SKILL.md`
   - `/verify`依赖它可靠地启动完整应用栈。

3. **与应用类型匹配的驱动工具**
   - Web 应用默认使用`playwright-cli`。
   - API、CLI 等非 Web 项目则使用具体工具，如`curl`、HTTP 脚本或已构建的命令行程序。

> 核心区别：`verifier-setup`负责**搭建验证能力**，而`/verify`才负责**执行具体验证**。

##### 2. 第一步：先盘点仓库，避免重复建设

创建任何文件前，要检查仓库是否已经具备相关能力，重点包括：

- 启动应用的方式，如：
  - `scripts/dev-local.sh`
  - Makefile、Procfile
  - `docker-compose`
  - `package.json`脚本
- 已有的验证 SOP 或技能。
- 浏览器、API、CLI 等操作驱动。
- 单元测试、端到端测试及其他检查。
- 隔离沙箱或云环境配置。
- 验证证据的保存与发布方式，如 GitHub Release、对象存储或 CI Artifacts。

对每项能力只能做三种选择：

- **直接复用**
- **补充或扩展**
- **确实缺失时再新建**

原则是：**识别能力，而不是只查固定文件名；绝不能盲目覆盖已有配置和团队手工修改。**

##### 3. 第二步：从仓库中确认真实运行信息

生成`/verify`前，需要查清并记录以下事实：

- **应用类型**
  - Web：有浏览器界面和开发服务器。
  - API：提供 HTTP 接口，但没有 UI。
  - CLI：通过终端命令操作。
  - 桌面或移动应用：使用对应测试工具。

- **启动方式**
  - 记录实际启动命令、URL 和端口。
  - 如果没有一键启动方式，再调用`dev-local-setup`创建，不能在这里临时手写。

- **认证方式**
  - 判断核心流程是否必须登录。
  - 如果已有 session/auth helper，就记录下来；否则标为`n/a`。

- **回归检查命令**
  - 从`package.json`、Makefile、`turbo.json`等配置中读取真实命令。
  - 常见检查包括类型检查、Lint、单元测试和已有 E2E 测试。

- **证据上传方式**
  - 默认方案：通过`gh release upload`上传到`pr-evidence` GitHub prerelease，生成可审查的视频链接。
  - 也可沿用仓库已有的存储桶或 CI Artifact 机制。

重点是：**启动命令、端口、认证和测试命令都必须来自仓库实际情况，不能靠惯例猜测。**

##### 4. 第三步：补齐启动、驱动和证据目录

###### 开发环境

- 如果已有可用的一键启动方式，就直接复用并读取其服务、端口和命令。
- 只有缺少必要服务时才扩展。
- 如果完全不存在，则调用`dev-local-setup`生成开发环境，不在本技能中自行拼装。

###### 操作驱动

- **Web 项目**
  - 安装或确认`playwright-cli`技能。
  - 还要确保实际二进制可调用：

    ```bash
    npx --yes @playwright/cli --version
    ```

  - 如果缺失，应安装 CLI 及 Chrome channel，避免 “文档假设已安装、实际运行却找不到工具” 的问题。

- **非 Web 项目**
  - 确认对应工具存在，例如 API 使用 HTTP 客户端，CLI 项目使用已构建的可执行程序。
  - 不需要强行安装浏览器工具。

###### 证据目录

确保`evidence/`已加入`.gitignore`，避免截图、视频等临时证明文件直接进入 Git 历史。

##### 5. 第四步：选择验证运行环境

系统需要向用户提供两种模式，默认推荐本地模式：

###### 本地模式（推荐）

- 使用机器上的单套开发环境，例如：

  ```bash
  scripts/dev-local.sh up
  ```

- 配置简单，适合一次只验证一个任务。

###### Sandbox 模式（crabbox）

- 每个代理拥有独立的云端沙箱。
- 适合：
  - 多个验证任务并行运行；
  - 应用只能使用固定端口；
  - 应用一次只能运行一个实例。

如果选择 Sandbox 但尚未配置，则通过`crabbox-setup`初始化；之后可在隔离环境中使用`cbx.sh pw`操作应用。

最终选择写入生成技能的默认`RUN_MODE`，另一种模式仍保留为备用说明。

##### 6. 第五步：确认驱动并生成`/verify`

需要明确告知用户检测到的驱动，并进行确认：

- Web 项目默认：`playwright-cli`
- API 项目示例：`curl`或 HTTP 脚本
- CLI 项目：项目本身构建出的命令行程序

生成规则如下：

- 如果已经存在验证技能或 SOP：
  - 在原文件上更新仓库相关信息；
  - 补齐占位符；
  - 保留团队手工添加的内容，不能覆盖重建。

- 如果不存在：
  - 将`assets/verify.template.md`复制到仓库技能目录，例如：

    ```text
    .claude/skills/verify/SKILL.md
    ```

  - 填写全部占位符：

    - `STACK_UP`
    - `APP_URL`
    - `RUN_MODE`、`RUN_MODE_NOTE`
    - `DRIVER`、`DRIVER_INSTRUCTION`
    - `AUTH_HELPER`、`AUTH_INSTRUCTION`
    - `EXERCISE`
    - `REGRESSION_CMDS`
    - `EVIDENCE_UPLOAD`
    - `DATE`

还要删除不适用的内容。例如，CLI 项目应删除浏览器和视频相关步骤，改成执行命令并断言标准输出。

生成的`/verify`应控制在**一屏以内**：它是代理执行的简洁 SOP，不是长篇说明文。

##### 7. 第六步：提交并告知用户如何使用

应将以下改动一并提交：

- `/verify`技能
- 必要的`/dev-local`脚本与技能文档
- 驱动技能
- `.gitignore`中关于`evidence/`的修改
- 其他确实需要的配置

完成后，需要向用户说明：

- **使用时机**：在打开 PR 前，或被要求验证时执行`/verify`。
- **前提条件**：应在包含目标改动且代码已经提交的分支上运行。
- **默认运行模式**：本地还是 Sandbox，以及如何切换。
- **一次性依赖**：例如 Docker、GitHub CLI 的`gh auth`等。

##### 8. 核心设计原则

- **先检查，后创建**：已有能力优先复用或扩展。
- **适配而不覆盖**：保留团队现有配置和手工修改。
- **先准备依赖，再生成技能**：启动脚本、驱动和证据目录必须先可用，避免`/verify`运行时才发现缺工具。
- **按项目类型裁剪**：
  - Web 单体或 Monorepo 可采用浏览器操作、截图和视频流程。
  - CLI 项目只需执行命令并验证输出，无须套用浏览器方案。
- **初始化必须可重复执行**：每一步都应具备幂等性；已有且正常的内容不应重复生成。
- **职责清晰**：`verifier-setup`只搭建验证系统，真正的任务验证由`/verify`完成。

#### 深度总结

`verifier-setup`不是执行测试，而是给仓库搭建一套**“发版前自证有效”**的验证基础设施。

它最终交付三项能力：

1. **`/verify`**：按任务执行验证的标准流程  
   > 独立验证代理 → 操作应用 → 生成截图 / 视频 → 将证据嵌入 PR
2. **`/dev-local`**：一条命令启动完整开发环境。
3. **验证驱动**：Web 默认使用`playwright-cli`；API、CLI 等则使用对应工具。

核心流程是：

> 先盘点已有能力 → 获取仓库真实信息 → 补齐启动器、驱动和证据目录 → 选择本地或沙箱模式 → 生成仓库专属`/verify` → 提交配置

其原则是：

- **按能力盘点，不按文件名判断**
- **能复用就复用，能扩展就不重建**
- **先配好工具，再生成流程**
- **配置来自仓库事实，不靠模板猜测**
- **按项目类型裁剪，不搞一刀切**

---

#### 深入浅出地解读

它相当于给项目安装一套**“验货流水线”**：

- `dev-local`：把产品开机；
- 驱动工具：模拟用户实际操作；
- `/verify`：规定如何验货；
- 截图、视频、日志：留下验货凭证；
- PR：让审查者直接看到结果。

两种运行方式：

| 模式 | 适用场景 |
|---|---|
| 本地 | 单任务、简单、成本低，默认推荐 |
| 沙箱`crabbox` | 多代理并行、端口冲突、需要环境隔离 |

关键价值不只是 “跑过测试”，而是建立：

> **代码变更 → 实际运行 → 可见证据 → PR 审查**

---

#### 辩证思考

##### 价值

- 把 “应该能用” 升级为 “有证据证明能用”。
- 将验证流程固化进仓库，减少口头约定与人工遗漏。
- 独立验证代理可降低开发者 “自己证明自己” 的偏差。
- 强调幂等和复用，适合成熟、异构项目。

##### 局限

- **截图和视频证明 “发生过”，不等于证明 “完全正确”**。
- 本地环境可能与 CI、生产环境不一致。
- SOP 中硬编码的端口、命令、认证方式会随项目演进而失效。
- 同一套代理、提示词和环境可能产生 “伪独立验证”。
- 证据上传还涉及密钥、隐私和存储成本。

##### 结论

这套方案最适合充当**验证编排层**，而不是替代自动化测试。更稳妥的体系应是：

> **单元测试保证局部逻辑，集成测试保证系统协作，`/verify`保证真实操作与可审查证据，CI 负责持续执行和准入。**

真正重要的思想是：**工程交付不能只提交代码，还要提交 “它确实有效” 的证据链。**

这份技能的核心作用，是把一个代码仓库准备成“可验证”的状态。执行一次之后，仓库就会拥有启动应用、驱动应用、收集证据，并在提交代码前运行验证流程所需的工具和文档。你将了解到，它会检查哪些已有能力、如何选择本地或云端沙盒，以及最终会生成哪些可复用的文件。

##### 首先，明确它做什么，不做什么

核心结论是：`verifier-setup` 是“搭建验证环境”的工具，不是“现在就执行验证”的工具。

通俗地说，它负责把以后运行 `/verify` 所需的基础设施准备好。真正的任务验证，要等设置完成之后，再由 `/verify` 按照具体任务执行。

完整流程通常是：先启动一个验证子代理，然后驱动应用完成操作，再截取截图或录制视频作为证据，最后创建一个带有证据的 Pull Request，也就是代码合并请求。

执行完成后，仓库应当留下三类主要成果。

第一类，是一个 `/verify` 技能文件。默认路径是：

`.claude/skills/verify/SKILL.md`

它是一份针对当前仓库定制的验证操作手册，里面会写清楚如何启动应用、如何操作、如何完成回归检查，以及如何上传验证证据。

第二类，是一个 `/dev-local` 技能和启动脚本。默认包括：

`scripts/dev-local.sh`

以及：

`.claude/skills/dev-local/SKILL.md`

它们负责用一条命令启动本地开发环境。`/verify` 依赖这套启动方式。

第三类，是应用所需的驱动技能。对于网页应用，默认安装或确认 `playwright-cli` 技能。它负责通过浏览器自动化操作网页。对于非网页应用，则要确认对应的 HTTP 客户端、命令行工具，或者其他具体操作工具已经存在。

##### 接下来，先盘点仓库已有的能力

核心结论是：在创建任何文件之前，必须先检查仓库已经有什么，不能因为文件名不同就误以为能力不存在。

也就是说，要寻找的是“能力”，而不是固定的文件名。已有设置可以直接复用，也可以补充扩展。只有确实缺失时，才重新创建。不能直接覆盖已经能工作的配置。

首先，要找应用的启动方式。它可能是一个启动脚本，也可能是 Makefile 或 Procfile 中的目标，还可能是 Docker Compose 配置，或者 `package.json` 里的脚本。只要能启动应用，都算有效。

接着，要找是否已经有验证流程。它可能来自之前运行过这个技能，也可能是团队自己编写的测试或操作规范。

然后，要确认是否存在应用驱动工具。网页应用可能已经配置了浏览器自动化工具；API 服务可能有 HTTP 客户端；命令行工具可能已经有可执行文件。

还要检查已有的测试和回归检查，例如类型检查、代码风格检查、单元测试和端到端测试。这里的“端到端测试”，指的是从真实使用流程出发，检查整个应用链路是否正常。

此外，还要查看是否已有隔离环境配置，也就是为不同代理或不同任务分别启动独立应用实例的沙盒配置。

最后，还要确认验证证据应该放在哪里，以及如何生成一个供代码审查者查看的链接。默认方式是创建 GitHub 的预发布版本，也就是 prerelease，然后使用 `gh release upload` 上传证据。仓库也可以使用对象存储或持续集成系统的构建产物，只要最终能产生可审查的链接即可。

这一步的关键，不是简单列一遍文件，而是判断每项能力应该“原样复用、适配扩展，还是重新创建”。

##### 更重要的是，要找出仓库的真实运行事实

核心结论是：生成的 `/verify` 文档必须写入当前仓库的真实信息，不能照搬默认假设。

首先要判断应用属于哪一类。

如果是网页应用，就要确认它是否有浏览器界面、开发服务器，以及具体端口。如果是 API 或服务，就要确认 HTTP 接口。如果是命令行程序，就要确认如何调用构建好的可执行文件。也可能是桌面应用或移动应用。应用类型会决定验证时使用什么驱动工具。

接着，要确定启动命令、服务依赖，以及应用地址和端口。如果仓库已经有启动方式，就从现有配置中读取这些信息。如果完全没有，后续会通过 `dev-local-setup` 生成启动脚本，而不是在这里手工编写一套新的启动逻辑。

还要确认主要流程是否需要登录。如果需要，就要找出验证代理可以使用的登录辅助工具，也就是能够创建会话或取得登录状态的工具。如果不需要登录，就明确记录为“不适用”。

随后，要整理快速回归检查命令。这些命令可能来自 `package.json`、Makefile、`turbo.json` 或其他配置文件。最终生成的验证技能会直接写入这些真实命令。

最后，确定证据如何上传。默认方案是通过 GitHub 预发布版本上传，但如果仓库已经有稳定的云存储或持续集成产物机制，就优先复用现有方式。

##### 然后，按检查结果补齐缺失部分

核心结论是：每一步都要根据前面的盘点结果决定是否行动；如果已有能力可用，就复用或补充，而不是重新生成。

对于开发环境，如果仓库已经有可用的启动脚本、Makefile 目标、Compose 配置或包管理脚本，就直接使用它，并读取启动命令、端口和服务信息。只有完全没有启动方式时，才通过 `dev-local-setup` 创建一套。

对于网页应用，要安装或确认 `playwright-cli` 技能，同时检查浏览器驱动本身是否真的能运行。可以通过下面这条命令检查：

`npx --yes @playwright/cli --version`

如果浏览器驱动或 Chrome 浏览器通道缺失，就要安装它们。这样可以避免一种常见问题：文档里假设浏览器已经存在，但实际运行验证时却找不到浏览器。

对于非网页应用，则不需要浏览器技能，而是确认具体操作工具已经存在。例如，API 服务要有可用的 HTTP 客户端，命令行程序要有已经构建好的可执行文件。

此外，还要确保仓库有 `evidence/` 目录，并且这个目录被加入 Git 忽略配置。截图、视频等验证产物应该放在那里，避免把临时证据直接提交进源代码仓库。

这些检查应该是幂等的。所谓幂等，就是重复执行不会破坏已有结果；已经配置好的部分应当成为无操作，而不是被重新覆盖。

##### 接下来，选择验证运行在哪里

核心结论是：验证默认推荐在本地运行，但也可以选择云端沙盒，具体取决于是否需要并行任务或隔离环境。

第一种方式是本地运行。它会在当前机器上启动一套开发环境，典型命令是：

`scripts/dev-local.sh up`

这种方式最简单，适合一次只处理一个任务。因此，除非有特殊需求，否则推荐把本地模式作为默认运行模式。

第二种方式是沙盒，也叫 `crabbox`。它会为每个代理提供一个隔离的云端环境，适合多个验证流程并行运行，或者仓库只能使用固定端口、单实例环境的情况。

如果选择沙盒模式，而仓库还没有准备好，就需要通过 `crabbox-setup` 进行配置。生成的验证技能会通过 `cbx.sh pw` 在沙盒内部驱动应用。

最终，生成的 `/verify` 技能会记录你选择的模式作为默认的 `RUN_MODE`。另一种模式也会保留为文档中的备用方案，方便之后切换。

##### 然后，确认驱动工具，并生成验证技能

核心结论是：在生成 `/verify` 之前，必须先确保驱动工具、启动器和证据目录已经准备好。

对于网页应用，默认驱动是 `playwright-cli`。设置过程需要向用户说明当前检测到的驱动，并请用户确认。对于非网页应用，则要明确说出实际使用的工具，例如 `curl`、某个 HTTP 脚本，或者构建好的命令行程序。

如果仓库已经有验证技能或验证操作手册，就在原文件上更新。更新时要刷新仓库相关的信息和占位内容，同时保留团队已经手工添加的内容，不能整份覆盖。

如果仓库还没有，就把：

`assets/verify.template.md`

复制到仓库约定的技能目录，通常是：

`.claude/skills/verify/`

然后填入所有真实信息，包括：

- 应用启动命令，也就是 `STACK_UP`；
- 应用地址，也就是 `APP_URL`；
- 运行模式和运行模式说明；
- 驱动工具及其使用方式；
- 登录辅助工具及登录说明；
- 应该执行的回归检查命令；
- 证据上传方式；
- 生成日期。

不适用的分支要删掉。例如，非网页项目不需要保留浏览器操作、截图和视频相关内容。最终的 `/verify` 技能应该尽量控制在一屏左右，因为它是一份供代理执行的操作规范，不是一篇长篇说明文档。

##### 最后，提交变更并告诉使用者怎么运行

核心结论是：设置完成后，要把生成的技能和相关配置提交到仓库，并明确告诉使用者下一步怎么用。

需要提交的内容可能包括：

- 新生成或更新的 `/verify` 技能；
- `/dev-local` 技能；
- `scripts/dev-local.sh` 启动脚本；
- `.gitignore` 中对 `evidence/` 的修改；
- 其他必要的驱动或沙盒配置。

然后告诉使用者，应该在代码变更已经提交的分支上，在打开 Pull Request 之前运行：

`/verify`

也可以在有人明确要求验证时运行。

同时，要说明当前选择的是本地模式还是沙盒模式，以及怎样切换到另一种模式。还要提醒一次性前置条件，例如是否需要安装 Docker，或者是否需要先完成 GitHub 命令行工具 `gh` 的身份认证，才能上传验证证据。

##### 需要记住的几个原则

第一，先检查，再创建。无论是开发启动器、浏览器驱动、端到端测试、证据目录，还是验证技能，都要先盘点已有配置，能复用就复用，能扩展就扩展，不能随意覆盖。

第二，发现事实，不要凭经验猜测。启动命令、端口、登录方式和回归检查，都必须来自当前仓库的真实配置。

第三，先准备工具，再生成文档。启动器、驱动工具和证据目录要先可用，这样生成的 `/verify` 才不会在执行时因为缺少工具而失败。

第四，按项目类型控制复杂度。网页项目可以使用完整的浏览器、视频和证据流程；命令行项目则应当采用输出结果断言等更适合自身的验证方式。

第五，要区分设置和执行。`verifier-setup` 负责搭建和配置；真正运行任务、操作应用并产出证明，则由之后的 `/verify` 完成。

#### AI 编程的下一道门槛：把“能验证”做成仓库能力

这份文档不是在提出新的测试框架，而是在定义一套 `verifier-setup` 技能：先调查项目，再补齐启动环境、操作工具与证据发布方式，最终生成仓库专属的 `/verify` 流程。它最值得关注的判断是：**AI 能否可靠完成工程任务，不只取决于代码生成能力，还取决于仓库是否向它提供了一条可重复、可观察、可举证的验证路径。**

##### 验证环境正在成为产品的一部分

传统项目通常把运行知识分散在 README、脚本、个人经验和 CI 配置中。人类工程师可以临时补足缺口，Agent 却容易在端口、登录状态、服务依赖或浏览器驱动上失效。文档因此要求先确保三个条件：一条命令启动应用、一个确定可用的操作驱动、一个可供评审的证据出口。

这相当于为仓库增加了一层“机器可操作界面”。`dev-local` 回答如何启动，Playwright、HTTP 客户端或 CLI 回答如何操作，`/verify` 则规定如何检查、记录并提交结果。**当这些信息从隐性经验变成仓库内的固定协议，Agent 才可能从“写出看似合理的补丁”升级为“完成可复核的工程交付”。**

对团队而言，这套能力也不只服务 AI。新人接手、远程协作、故障复现和 PR 评审都会受益。值得观察的长期机会不是再造一个通用 Agent，而是帮助不同仓库自动生成并维护这种“验证契约”：真实启动命令是什么、核心流程如何执行、哪些回归检查必须通过、证据怎样关联到具体提交。

##### 关键方法不是生成模板，而是先识别现有能力

文档反复强调“寻找能力，而不是寻找指定文件名”：已有 Makefile、Docker Compose 或 package script 就复用；已有验证规范则增量修改；只有真正缺失时才创建。这一点比最终模板更重要。

工程自动化常见的问题，是工具为了获得一致性而覆盖团队原有约定，结果产生两套入口和逐渐失真的配置。这里采用的是**能力盘点—补齐缺口—固化事实**：端口、认证方式、检查命令都从仓库中发现，而不是按惯例猜测；操作还应幂等，重复执行不能破坏手工改动。这种策略可以迁移到 AI 生成 CI、部署脚本和项目文档等场景：高质量自动化首先要理解已有系统，而不是急于搭建自己的系统。

##### “有证据”不等于“已证明正确”

流程要求 Agent 驱动应用、生成截图或视频，并把证据嵌入 PR，这能显著改善评审体验，也能暴露“测试通过但界面不可用”之类的问题。但截图和视频主要证明某条路径曾经成功，不足以证明边界条件、数据一致性或安全性。反过来，单元测试也无法证明真实交互可用。

因此，这套方案真正有效的地方，是把三类信号组合起来：**可执行的用户流程、自动化回归检查、与提交绑定的可审查证据**。其中任何一项单独存在，都可能制造虚假的确定性。

文档本身仍是一份规范，并未给出采用后的故障率或交付效率数据。更值得验证的问题是：当仓库拥有这种验证契约后，Agent 任务的一次通过率、人工复核时间和回归遗漏是否显著改善。若答案成立，未来衡量“AI-ready repository”的关键指标，可能不再只是文档和测试覆盖率，而是它能否让一个陌生执行者独立启动、操作、判断并证明结果。
