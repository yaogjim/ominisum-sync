## 分析要点

- **核心高价值点**：最有价值的是“仓库即记录系统”的原则：凡是不以版本化工件进入代码仓库的知识，对智能体都等于不存在。
- **留存建议**：长期保留（文章提供了智能体优先软件工程的系统性框架，包含组织知识、约束架构、反馈回路和熵治理等高复用方法，适合作为后续搭建AI开发流程的参考。）

**知识要点**

- AGENTS.md 应作为目录页而非百科全书，采用渐进式披露来节省上下文资源
- 通过自定义 linter、结构测试和 CI 机械化执行架构不变量，比口头规范更适合智能体协作
- 优化目标应从人类可读扩展为智能体可读，让日志、UI、指标和文档都能被模型直接推理
- 智能体会复制已有好坏模式，因此需要黄金规则和持续垃圾回收机制抑制代码库熵增
- 高吞吐智能体开发下应重新思考合并门控，降低等待成本并依赖快速纠错和自动化背压机制

**行动项**

- 审视当前项目中散落在聊天、文档和个人记忆中的知识，优先迁移到仓库内可版本化文档
- 为代码库建立最小化 AGENTS.md 入口和分层文档索引，避免把规则堆成超长提示词
- 补充可被智能体利用的 lint、结构测试和 CI 规则，把审查意见逐步转成机器可执行约束
- 为本地开发环境增加可观测性、UI 驱动和隔离运行能力，增强智能体自验证闭环
- 建立定期扫描坏模式和自动提交重构 PR 的清理流程，降低 AI 生成代码的长期漂移风险

## 正文

### 工程技术：在智能体优先的世界中利用 Codex \| OpenAI

https://openai.com/zh-Hans-CN/index/harness-engineering/

在过去五个月里，我们的团队一直在进行一项实验：构建并交付一款软件产品的内部 beta 版， **其中没有一行代码是人工编写的** 。

该产品有内部日常活跃用户和外部 Alpha 测试者。它经历了交付、部署、故障和修复的整个过程。与众不同的是，每一行代码 — 从应用逻辑、测试、CI 配置、文档、可观察性到内部工具 — 全都是由 Codex 编写的。据估计，我们只用了手工编写代码所需的大约 1/10 的时间就完成了这项工作。

**人类掌舵。智能体执行。**

我们有意选择这一限制，以便构建必要的内容，从而将工程速度提升数个数量级。我们用了几周的时间来交付最终达到一百万行代码的项目。为此，我们需要了解，当软件工程团队的主要工作不再是编写代码，而是设计环境、明确意图和构建反馈回路，从而使 Codex 智能体能够可靠地工作时，会发生哪些变化。

这个帖子要说的是，在我们与智能体团队一起从零开始打造一款全新产品的过程中，所能学到的经验教训 — 哪些地方出了问题，哪些问题相互叠加，以及如何最大化利用我们唯一真正稀缺的资源：人类的时间和注意力。

#### 我们从一个空的 Git 代码仓库开始

首次提交到一个空的代码仓库是在 2025 年 8 月下旬。

初始架构 — 包括代码仓库结构、CI 配置、格式化规则、包管理器设置和应用框架 — 是在一小套现有模板的指导下，由 Codex CLI 使用 GPT‑5 生成的。就连指导智能体如何在代码仓库中工作的初始 AGENTS.md 文件本身也是由 Codex 编写的。

该系统没有预存任何人工编写的代码。从一开始，代码仓库就由智能体塑造。

五个月后，该代码仓库已经拥有约一百万行代码，从应用逻辑、基础设施、工具、文档到内部开发者工具应有尽有。在那段时间内，大约有 1,500 个 Pull Request 被打开与合并，而推动 Codex 的仅仅是一个由三名工程师组成的小团队。这相当于平均每位工程师每天处理 3.5 个 PRs 的吞吐量，而且令人惊讶的是，随着团队规模扩大到现在的七名工程师，吞吐量甚至还 *增加* 了。重要的是，这并非为了输出而输出：该产品已在数百名内测用户那里投入使用，其中包括每天都在使用的内测高级用户。

在整个开发过程中，人类从未直接直接贡献过任何代码。这成为团队的核心理念： **不手动编写代码** 。

#### 重新定义工程师的角色

由于缺乏人工编码的实践， **工程师工作的重点转向了系统、架构和杠杆作用** 。

早期进展比我们所预期的要慢，而这并不是因为 Codex 不具备相应的能力，而是因为环境的规范不够明确。该智能体缺乏实现高级目标所需的工具、抽象层和内部结构，因而无法取得进展。我们工程团队的主要任务成了协助智能体完成有用的工作。

在实践中，这意味着采用深度优先的工作方式：将更大的目标拆解为更小的构建模块（设计、代码、评审、测试等），提示智能体去构建这些模块，并使用它们去解锁更复杂的任务。当事情进行不顺利时，解决方案基本上再也不会是“再努力一点”。因为取得进展的唯一方式是让 Codex 来完成工作，而人类工程师则总是介入这项任务并追问：“究竟还需要什么样的能力，我们又该如何让这个能力对智能体来说既清晰可读又可强制执行？”

人类几乎完全通过提示与系统交互：工程师描述任务，运行智能体，并允许其打开一个 Pull Request。为了推动 PR 的完成，我们会指示 Codex 在本地审核其自身的更改，在本地和云端请求额外的特定智能体审查，对任何人工或智能体给出的反馈做出响应，并循环往复，直到所有智能体审核人员都满意为止（这实际上是一个 [Ralph Wiggum 循环 ⁠](https://ghuntley.com/loop/) ）。Codex 直接使用我们的标准开发工具（gh、本地脚本和嵌入代码仓库的技能）来收集情境，而无需人工将内容复制粘贴到 CLI 中。

人类可以审核 Pull Request（合并请求），但并非必须这样做。随着时间的推移，我们已将几乎所有的审核工作调整为用智能体对智能体的方式来处理。

#### 提高应用程序的可读性

随着代码吞吐量的增加，我们的瓶颈变成了人工 QA 能力。由于人类的时间和注意力是固定的限制因素，我们一直在努力通过令应用程序的 UI、日志和应用指标等内容对 Codex 直接可读，从而为智能体增加更多功能。

例如，我们令应用程序可以根据 git worktree 启动，因此 Codex 可以为每次更改启动并驱动一个实例。我们还将 Chrome DevTools 协议接入智能体运行时，并创建了用于处理 DOM 快照、屏幕截图和导航的技能。这使 Codex 能够复现错误、验证修复，并直接推理 UI 的行为。

我们经常看到单次 Codex 运行在单个任务上持续工作超过六个小时（通常是在人类睡眠时间）。

#### 我们将代码仓库设为记录系统

情境管理是使智能体在大型和复杂任务中有效发挥作用的最大挑战之一。我们学到的最早经验教训之一很简单： **要给 Codex 的是一张地图，而不是一本 1,000 页的说明书。**

我们尝试了“一个大型的 [`AGENTS.md` ⁠](https://agents.md/) ”方法。可想而知，这是一次失败的尝试：

- **情境是一种稀缺资源。** 一个巨大的指令文件会挤掉任务、代码和相关文档 — 因此智能体要么会错过关键约束条件，要么开始针对错误的约束条件进行优化。
- **过多的指导反而变得** ***无效*** **。** 当一切都 "重要"时，一切都不重要了。智能体最终会在本地进行模式匹配，而不是有意识地进行导航。
- **它会立即腐烂。** 一本庞杂的手册会变成陈旧规则的坟场。智能体无法判断哪些信息仍然有效，一旦人类停止维护它，此文件就会悄然成为一个颇具吸引力的麻烦源头。
- **这很难核实。** 单个 blob 不适合进行机械检查（覆盖率、新鲜度、所有权、交叉链接），因此漂移是不可避免的。

因此，我们不再将 `AGENTS.md` 视为百科全书，而是将其视为 **内容目录** 。

代码仓库的知识库位于一个结构化了的 `docs/` 目录中，此目录被当作记录系统来使用。一份简短的 `AGENTS.md` （大约 100 行）被注入到情境中，主要用作地图，并指向其他地方更深层次的真实信息来源。

代码仓库内知识存储布局。

设计文档已被编目和索引，其中包括验证状态和一套核心理念，定义了智能体优先的操作原则。 [架构文档 ⁠](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html) 提供域和包分层的顶层地图。一份高质量的文档会对每个产品领域和架构层进行评分，并随着时间的推移追踪差距。

计划被视为一流的工件。临时轻量计划用于小幅变更，而复杂工作则记录在 [执行计划 ⁠](https://cookbook.openai.com/articles/codex_exec_plans) 中，并附带进度和决策日志，这些日志会被提交到代码仓库。活跃计划、已完成计划和已知的技术债务都已进行版本控制并集中存放，使智能体能够在不依赖外部情境的情况下运行。

这实现了 **渐进式披露** ：智能体从一个小而稳定的切入点开始，并被指导下一步该去哪里查看，而不是一开始就被淹没。

我们严格执行这一点。专职的 linter 和 CI 作业会验证知识库的更新状况、是否已交叉链接且结构正确。一个定期运行的“doc-gardening”智能体会扫描那些不再反映真实代码行为的过时或废弃文档，并发起修复用的 Pull Request。

#### 目标是智能体的可读性

随着代码库的发展，Codex 的设计决策框架也需要随之演变。

由于该代码仓库完全由智能体生成，因此我们首先针对 *Codex* 的 *可读性* 进行了优化。就像团队会努力提升代码对新入职工程师的可导航性一样，我们的人类工程师的目标也是让智能体能够 **直接从代码仓库** 推理出完整的业务领域。

从智能体的角度来看，它在运行时无法在情境中访问的任何内容都是不存在的。存储在 Google Docs、聊天记录或人们头脑中的知识都无法被系统访问。代码仓库本地的、已版本化的工件（例如，代码、Markdown、模式、可执行计划）就是它所能看到的全部。

我们了解到，随着时间的推移，我们需要将越来越多的情境推送到仓库中。那次让团队在架构模式上达成一致的 Slack 讨论？如果智能体无法发现它，那么它就会像迟了三个月入职的新员工一样，对其一无所知。

为 Codex 提供更多情境意味着要组织和展示正确的信息，好令智能体能够基于这些信息进行推理，而不是用临时指令使其不堪重负。就像你会在产品原则、工程规范和团队文化（包括表情符号偏好）方面为新队友提供引导一样，将这些信息提供给智能体会带来更一致的输出。

这一框架明确了许多取舍。我们倾向于选择那些可以完全内化于在仓库中进行推理的依赖项和抽象。对智能体来说，通常被称为“枯燥”的技术，由于其可组合性、API 稳定性和在训练集里的表现，往往更容易建立模型。在某些情况下，让智能体重新实现部分功能子集比绕过公共库中不透明的上游行为更便宜。例如，我们没有引入通用的 `p-limit` 风格包，而是投入使用了我们自己的带并发的 map 辅助函数：它与我们的 OpenTelemetry 仪表紧密集成，具备 100% 的测试覆盖率，并且其行为完全符合我们的运行时预期。

将系统的更多部分转化为智能体可以检查、验证并直接修改的形式，可以直接提高杠杆效应 — 这不仅适用于 Codex，也适用于其他智能体（例如 Aardvark) 也在参与代码库的开发。

#### 规范架构与品味

仅靠文档本身，是没法保持完全由智能体生成的代码库的连贯性的。 **通过强制执行不变量，而非对实施过程进行微观管理，我们令智能体能够快速交付，而且不会削弱基础。** 例如，我们要求 Codex [在边界处解析数据形状 ⁠](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/) ，但不规定具体实现方式（模型似乎偏好 Zod，但我们没有指定特定库）。

智能体在具有 [严格边界和可预测结构 ⁠](https://bits.logic.inc/p/ai-is-forcing-us-to-write-good-code) 的环境中最为高效，因此我们围绕一个严格的架构模型构建了该应用。每个业务域都划分为一组固定的层，依赖方向经过严格验证，并且仅允许有限的一组边。这些约束是通过自定义的 linter（当然是由 Codex 生成的！）和结构测试机械地强制执行的。

下图展示了规则：在每个业务领域内（例如应用设置），代码只能“向前”依赖于一组固定的层（Types → Config → Repo → Service → Runtime → UI）。横切关注点（认证、连接器、遥测、功能标志）通过一个单一的显式接口进入：Providers。其他任何内容都不被允许，并将通过自动化方式强制执行。

题为“具有明确交叉界限的分层领域架构”的图表。在业务逻辑域内存在以下模块：Types → Config → Repo，以及 Providers → Service → Runtime → UI，底部是 App Wiring + UI。一个 Utils 模块位于界限之外，并向 Providers 提供输入。

这种架构通常要等到你拥有数百名工程师时才会推迟。对于编码智能体来说，这是一个早期的先决条件：有了约束，速度才不会下降，架构才不会漂移。

在实践中，我们通过自定义的代码检查器和结构测试来强制执行这些规则，并辅以一小组“品味不变式”。例如，我们通过自定义 lint 静态地强制执行结构化日志记录、模式和类型的命名约定、文件大小限制，以及特定平台的可靠性要求。由于这些 lint 是自定义的，我们编写错误信息时会在智能体情境中注入修复指令。

在以人为本的工作流程中，这些规则可能会让人感到迂腐或束缚。有了智能体，它们就成了倍增器：一旦编码，它们就能立即应用于所有地方。

同时，我们还明确指出了哪些地方需要限制，哪些地方不需要限制。这类似于领导一个大型工程平台组织：在中央层面强制执行边界，在本地层面允许自主权。你非常重视界限、正确性和可重复性。在这些边界内，你允许团队或智能体在解决方案的表达方式上拥有很大的自由。

生成的代码不总是符合人类的风格偏好，这也没关系。只要输出是正确的、可维护的，并且对未来的智能体运行而言清晰易读，就可以算作达标。

人类的品味会不断反馈到系统中。审查评论、重构的 Pull Request 和面向用户的 Bug 会被记录为文档更新，或直接编码到工具中。当文档不够完善时，我们会将规则转化为代码

#### 吞吐量改变了合并的理念

随着 Codex 的吞吐量增加，许多传统的工程规范变得不再有效。

该代码仓库在运行过程中尽量减少阻塞合并门。Pull Request 的生命周期很短。测试偶发失败通常通过后续重跑来解决，而不是无限期地阻碍进展。在一个智能体吞吐量远超人类注意力的系统中，纠错成本低，而等待成本高。

在低吞吐量环境中，这样做是不负责任的。而在这里，这通常是正确的选择。

#### “智能体生成”实际上意味着什么

当我们说代码库是由 Codex 智能体生成的，我们指的是整个代码库。

智能体的产出包括：

- 产品代码与测试
- CI 配置和发布工具
- 内部开发者工具
- 文档和设计历史
- 评估框架
- 审阅评论和回复
- 管理代码仓库本身的脚本
- 生产仪表板定义文件

人类始终参与其中，但工作的抽象层次与过去不同。我们优先处理工作，将用户反馈转化为验收标准，并对结果进行验证。当智能体遇到困难时，我们将其视为一个信号：识别缺失的内容 — 工具、指导与约束、文档 — 并将其反馈到代码仓库中，始终由 Codex 自己编写修复。

智能体可以直接使用我们的标准开发工具。他们会拉取审查反馈、在行内回复、推送更新，并且经常压缩并合并他们自己的 Pull Request（合并请求）。

#### 不断提高的自主水平

随着越来越多的开发环节被直接编码到系统中 — 包括测试、验证、审查、反馈处理和恢复 — 该代码仓库最近跨过了一个重要门槛，使 Codex 能够端到端地驱动一个新功能。

给定一个提示，智能体现在可以：

- 验证代码库的当前状态
- 重现已报告的漏洞
- 录制一个演示故障的视频
- 实施修复措施
- 通过运行应用程序来验证修复
- 录制第二个视频，演示解决方案
- 打开 Pull Request
- 回应智能体和人类反馈
- 检测并修复构建故障
- 仅在需要判断时才交由人工处理
- 合并更改

此行为在很大程度上取决于此代码仓库的具体结构和工具，不应在没有类似投入的情况下假定它可以泛化 — 至少目前还不行。

#### 熵与垃圾收集

**完全自主的智能体也引入了新的问题。** Codex 会复现代码仓库中已存在的模式 — 甚至包括那些不均衡或不够理想的模式。随着时间的推移，这不可避免地导致漂移。

最初，人类是手动处理这个问题的。我们的团队过去每周五（占一周的20%）都要花时间清理“AI 残渣”。不出所料，那并不具备可扩展性。

相反，我们开始将我们称为“黄金原则”的内容直接编码到代码仓库中，并建立了一个循环清理流程。这些原则是带有主观意见的机械规则，旨在保持代码库的可读性和一致性，以便将来运行智能体。例如：(1) 我们更倾向于使用共享的实用程序包，而不是手工编写的辅助工具，以便将不变式集中管理；(2) 我们不会使用“YOLO 式”探测数据 — 我们会验证边界，或依赖类型化的 SDK，这样智能体就不会意外地基于猜测的结构进行构建。我们会定期运行一组后台 Codex 任务，扫描偏差、更新质量等级，并发起有针对性的重构 Pull Request。其中大多数都可以在一分钟内完成审查并自动合并。

其功能类似于垃圾回收。技术债务就像一笔高息贷款：不断地以小额贷款的方式偿还债务，总比让债务不断累积，再痛苦地一次解决要好得多。人类的品味一旦被捕捉，就会持续应用于每一行代码。这也使我们能够每天发现并解决不良模式，而不是让它们在代码库中传播数天或数周。

#### 我们仍在学习的内容

到目前为止，这一策略在 OpenAI 的内部发布和采纳过程中表现良好。为真实用户打造真实产品，帮助我们将投资锚定在现实中，并引导我们实现长期的可维护性。

我们尚不清楚的是，在一个完全由智能体生成的系统中，架构连贯性会如何随着时间的推移而演变。我们仍在学习人类的判断力在哪些方面能发挥最大作用，以及如何对这种判断力进行编码，使其发挥更大作用。我们也不知道，随着时间的推移，模型的功能不断增强，这一系统将如何演变。

显而易见的是：构建软件仍然需要纪律，但纪律更多地体现在支撑结构上，而不是代码上。保持代码库一致性的工具、抽象和反馈回路变得越发重要。

**我们当前最棘手的挑战集中在设计环境、反馈回路和控制系统方面** ，帮助智能体实现我们的目标：大规模构建和维护复杂、可靠的软件。

随着像 Codex 这样的智能体在软件生命周期中占据越来越大的比重，这些问题将变得更加重要。我们希望通过分享一些早期的经验教训，帮助你理清投入精力的方向，以便 你可以直接开始构建 。

#### 概念 2：机械化执行

#### 核心思想

> 通过强制执行不变量，而非对实施过程进行微观管理

- 横切关注点必须通过 Providers 进入

Error: File exceeds 500 lines.

#### 概念 5：吞吐量改变合并理念

#### 原文要点

当 Codex 的吞吐量远超人类注意力时，传统的工程规范变得不再有效。

核心转变： **纠错成本低，等待成本高。**

#### 具体变化

##### PR 生命周期缩短

- 1,500 个 PR / 5 个月 / 3 人 = 人均每天 3.5 个 PR
- PR 不再是需要精雕细琢的大作，而是快速流动的小变更
- 扩展到 7 人后吞吐量仍在增长（说明瓶颈不在人数）

##### 合并门控最小化

- 尽量减少阻塞合并的门
- 测试偶发失败 → 后续重跑解决，不无限期阻塞
- 在低吞吐量环境中这是不负责任的；在高吞吐量环境中这通常是正确的

##### 智能体审查智能体

- 人类可以审核 PR，但 **不是必须的**
- 随着时间推移，几乎所有审核都调整为智能体对智能体
- Ralph Wiggum 循环：Codex 本地审核 → 请求额外智能体审查 → 对反馈做出响应 → 循环直到所有审核通过

#### 来自其他文章的补充

实战结论：

- ❌ 每次改动跑全量测试
- ✅ 优化迭代速度，快速发现和修复问题
- ✅ 便宜模型（Sonnet/Haiku）做子任务，贵模型（Opus）做编排

长时间自主执行需要：

1. 文件系统 + git 追踪持久化工作
2. **Ralph Loop** 拦截退出，在新上下文窗口中重注入原始提示词
3. 规划 + 自我验证分解目标为步骤

当编码从手写转向引导生成时，开发者偏好作为选型标准的重要性下降。组织可能基于 harness 的质量和"AI 友好度"来选择技术栈 → 技术栈趋向收敛。

#### 关键洞察

这个概念的本质是一个 **经济学问题** ：

```
传统模式：人力贵 + 吞吐量低 → 每个 PR 都要精心审查 → 阻塞门多
Harness 模式：智能体便宜 + 吞吐量高 → 快速迭代修复 → 阻塞门少
```

前提条件：必须有足够的 **背压机制** （测试、lint、结构检查）来保证基本质量，否则就不是"快速迭代"而是"快速腐烂"。

#### 概念 3：熵管理与垃圾回收

#### 问题

智能体会复现仓库中已存在的模式—— **包括坏模式** 。

随着时间推移，不可避免地产生漂移（drift）：

- 重复的辅助函数散落各处
- 不一致的错误处理风格
- 基于猜测的数据结构（YOLO 式探测）
- 过时的文档与实际代码不符

#### 失败方案：人工清理

> 团队每周五花 20% 时间清理"AI 残渣"。不出所料，不具备可扩展性。

##### "黄金规则"（Golden Rules）

带主观意见的机械规则，编码进仓库：

1. **共享实用程序包 &gt; 手写辅助工具** — 不变式集中管理
2. **不做 YOLO 探测** — 在边界验证数据，或使用类型化 SDK
3. **偏好自有实现的关键子集** — 与自有遥测集成、100% 测试覆盖、行为完全可预测

##### 垃圾回收流程

```
定期后台 Codex 任务
  → 扫描偏差
  → 更新质量评分
  → 发起重构 PR
  → 大多数 1 分钟内审查 + 自动合并
```

#### 类比

技术债 = 高息贷款

- ✅ 每天小额偿还（持续垃圾回收）
- ❌ 累积到痛苦时一次性清偿（重写/大重构）

#### 关键洞察

> 人类的品味一旦被捕捉（编码为规则），就会持续应用于每一行代码。

品味的传播路径：

```
人类审查评论 → 文档更新 → lint 规则 → 自动应用于所有代码
```

## 摘要（1）

### 2026-04-07 07:42:09

#### Harness Engineering：综合总结与通俗解读

##### 一、综合总结

这几份内容共同描述了一种新的软件工程范式：**在“智能体优先”的世界里，工程师的核心工作不再是亲手写代码，而是搭建一个让 AI 智能体稳定、高效、可持续地产出代码的“工程操作系统”**。  
OpenAI 将这种方法概括为一种新的工程思路，可以称为：

> **Harness Engineering = 设计环境 + 明确意图 + 构建反馈回路，让智能体可靠完成软件开发。**

###### 这套方法的核心结论

- **代码不再是唯一主战场，环境才是。**
- **人类不再主要“编码”，而是主要“编排”。**
- **决定智能体表现上限的，不只是模型能力，更是仓库结构、文档质量、工具可见性、约束设计与反馈闭环。**
- **系统的目标，不是让 AI“更努力”，而是让 AI“更容易做对”。**

###### OpenAI 实验给出的强信号

在这套模式下，一个仅有 3 名工程师的团队：

- 从空仓库起步
- 5 个月做到约 **100 万行代码**
- 全过程约 **1500 个 PR**
- **没有人工直接编写代码**
- 估算只用了传统手写开发约 **1/10 的时间**

这说明：  
**当工程体系围绕智能体重构后，软件生产率可能出现数量级提升。**

---

##### 二、这套方法到底在改变什么

###### 1. 工程师角色被重新定义

传统工程中，工程师的主要动作是：

- 写代码
- 改代码
- Review 代码
- 调试代码

而在 Harness Engineering 中，工程师更像：

- **系统设计师**：设计仓库结构、架构边界、规则体系
- **任务拆解者**：把大目标拆成智能体能完成的小任务
- **环境构建者**：让应用、日志、指标、UI 都能被智能体直接理解
- **反馈回路设计者**：让 lint、测试、CI、文档、可观测性形成闭环
- **规则固化者**：把“人的判断”转化成“机器可执行的规则”

一句话说：

> **以前工程师直接生产代码，现在工程师生产的是“让代码自动产生的条件”。**

---

##### 三、七个核心思想的整合提炼

##### 1. 仓库就是智能体的“世界边界”

多个内容都在强调同一句话：

> **不在仓库里的东西，对智能体来说就不存在。**

这意味着：

- Slack 讨论，智能体看不到
- Google Docs，智能体看不到
- 团队成员脑中的默会知识，智能体看不到
- 只有仓库中的代码、Markdown、规则、计划、脚本，智能体才真正“知道”

因此，仓库不只是放代码的地方，而是：

- 事实记录系统
- 决策记忆系统
- 规范发布系统
- 智能体推理的唯一地基

###### 直接带来的实践变化

- `AGENTS.md` 不再是长篇说明书，而是**目录页**
- 真正的知识进入 `docs/`，并且结构化存储
- 执行计划、设计决策、产品规格、质量评分、技术债状态，都进入版本控制
- 文档不是“附属品”，而是智能体工作的输入材料

**本质上，团队是在把“组织记忆”仓库化。**

---

##### 2. 文档不是越多越好，而是要“可导航、可验证、可维护”

这些内容特别反对“大而全”的说明文档。

因为对智能体来说，超大指令文件会带来三个问题：

- **挤占上下文**：说明太多，真正与任务相关的信息反而装不下
- **迅速腐烂**：人一旦不维护，就会失真
- **无法机械验证**：你不知道哪些内容过期了、哪些内容没人负责

所以它们提出一种更好的方式：

###### 渐进式披露（Progressive Disclosure）

不是一上来把全部知识塞给智能体，而是：

- 先给一个简短入口
- 告诉它“去哪里看下一层信息”
- 让它按需加载上下文

这和给新人入职非常像：

- 不是一口气讲完公司全部知识
- 而是先给地图，再按场景深入

**结论是：智能体需要地图，不需要百科全书。**

---

##### 3. 真正可靠的不是“提醒”，而是“机械执行”

这是所有材料中最重要的思想之一。

文档可以告诉智能体“应该怎样做”，但真正能长期维持质量的，是：

- lint
- 结构测试
- CI 校验
- 自动化检查
- 可执行规则

也就是：

> **不要靠“记得遵守”，要靠“违规就过不了”。**

###### 这套思想的关键转变

传统做法常常是：

- 写一份规范
- 希望大家遵守
- Review 时靠人指出问题

Harness Engineering 的做法则是：

- 把规范转成可执行规则
- 把架构边界转成结构测试
- 把代码风格偏好转成 linter
- 把修复建议直接写进报错信息
- 让智能体自行发现错误并修复

这就形成了一个闭环：

**生成 → 检查 → 定位 → 修复 → 再检查**

而且是机器自己循环，不必持续占用人力。

###### 一个特别有价值的点

这里不是用规则去微观管理“怎么写每一行代码”，而是：

- 严格控制边界
- 放宽边界内实现自由

也就是说：

- **中央层面强约束**
- **局部层面高自主**

这很像优秀的平台治理，而不是死板流程控制。

---

##### 4. 优化目标从“人类可读”转向“智能体可推理”

传统工程长期强调：

- 人类读起来舒服
- 风格统一
- 抽象优雅

而这些内容提出：在智能体优先的环境里，更重要的是：

> **代码、文档、工具、运行信号，是否能让智能体准确推理。**

这意味着几项明显偏好：

###### 偏好“无聊技术”

所谓“无聊技术”，不是差，而是：

- API 稳定
- 社区成熟
- 训练集中覆盖充分
- 行为容易预测
- 组合关系清晰

对智能体来说，这种技术比“花哨但复杂”的工具更友好。

###### 必要时宁可自己实现关键子集

因为某些第三方库：

- 黑盒行为多
- 抽象复杂
- 不透明
- 难与本地遥测或约束体系对齐

这时，自己实现一个小而清晰、100% 测试覆盖、完全可控的子集，反而更便宜。

这背后的原则是：

> **不是追求“最省代码”，而是追求“最容易被智能体稳定理解和修改”。**

---

##### 5. 要让智能体不仅“看代码”，还要“看见程序在运行”

这是非常关键的一步升级。

这些材料反复指出，瓶颈不是代码生成，而是**验证能力**。

如果智能体只能改代码，不能直接观察程序运行结果，它就像蒙着眼工作。  
所以他们做了大量“让应用对智能体可读”的改造：

- 应用可按 `git worktree` 启动独立实例
- 接入 Chrome DevTools 协议
- 支持 DOM 快照、截图、导航
- 把日志、指标、追踪暴露给智能体
- 可用 LogQL / PromQL / TraceQL 查询系统状态

这使得智能体可以自己完成很多以前必须人做的事：

- 复现 bug
- 观察 UI 异常
- 验证修复
- 看性能指标是否达标
- 检查关键用户旅程耗时

换句话说：

> **最强的智能体，不是最会写代码的智能体，而是最会“验证结果”的智能体。**

---

##### 6. 吞吐量变了，合并策略也必须变

在传统团队里，PR 往往被看成“要尽量一次做对”的交付单元。  
但在智能体高吞吐场景里，这种思维会失效。

原因是：

- 智能体产出速度很高
- 修复成本很低
- 人类注意力才是稀缺资源
- 等待和阻塞比返工更贵

于是逻辑变成：

> **纠错成本低，等待成本高。**

###### 这带来的工程观念变化

- PR 生命周期变短
- 合并门控尽量减少
- 偶发测试失败不必无限阻塞
- 审查大量转为“智能体审查智能体”
- 人类更多只在需要判断和取舍时介入

当然，这不是“放弃质量”，而是建立在另一个前提之上：

###### 前提：必须有足够强的背压机制

也就是要有：

- lint
- 结构约束
- 测试
- CI
- 文档校验
- 质量评分
- 自动回收机制

否则就不是“快速迭代”，而是“快速腐烂”。

---

##### 7. AI 会复制好模式，也会复制坏模式，所以必须做“垃圾回收”

这是整个体系里非常现实、也非常容易被忽视的一点。

智能体会学习仓库中已有模式。  
如果仓库里已经有：

- 重复 helper
- 不一致的错误处理
- 猜测式数据结构
- 过时文档
- 命名混乱

那智能体会把这些继续放大。

所以他们发现，必须像运行内存垃圾回收一样，给代码库做**持续性的熵管理**。

###### 解决方法：把“品味”编码成规则

他们提出“黄金规则”：

- 共享工具优先于重复手写
- 不做 YOLO 式数据探测
- 边界上必须验证数据形状
- 关键能力宁可做可控子集，也不包裹黑盒

然后通过后台智能体定期执行：

- 扫描偏差
- 更新质量评分
- 自动发起重构 PR
- 快速审查并合并

这意味着：

> **技术债不再是“项目后期再说”的问题，而是每天自动偿还的小额债务。**

---

##### 四、用更通俗的话解释：这到底像什么

如果把传统软件开发比作“工匠手作”，那么 Harness Engineering 更像是：

###### 传统模式
工程师像厨师，亲自切菜、炒菜、调味、装盘。

###### Harness 模式
工程师更像餐厅运营者：

- 设计厨房布局
- 规定备料标准
- 配置烹饪流程
- 设置质检机制
- 培训自动化设备
- 只在关键口味判断时出手

结果是：

- 单道菜是否完美，不再完全依赖某位厨师手艺
- 整个系统可以更稳定、更大规模地出餐
- 真正贵的资源，从“做菜时间”变成“设计体系的能力”

也就是说：

> **你不再靠“更努力地写代码”提效，而是靠“更聪明地设计生成代码的系统”提效。**

---

##### 五、这套方法最有价值的几个认知升级

##### 1. AI 时代的软件工程，本质上是“上下文工程”

关键不是“你提示词写得多漂亮”，而是：

- 信息放在哪里
- 是否结构化
- 是否能按需获取
- 是否是最新的
- 是否可被工具验证
- 是否能和代码、测试、日志连起来

所以，未来很多工程能力会转化为：

- 知识组织能力
- 规则设计能力
- 环境建模能力
- 反馈回路设计能力

---

##### 2. 最强约束不是束缚，而是杠杆

很多人直觉上觉得：  
给 AI 越大自由度，它越聪明。

但这些材料提出了一个反直觉结论：

> **解空间越大，智能体犯错概率越高；约束越清晰，智能体反而越可靠。**

所以：

- 架构边界不是拖慢速度，而是保护速度
- 规则不是限制创造力，而是减少偏航
- 明确约束不是保守，而是为了规模化稳定产出

---

##### 3. 文档的终点不是“写出来”，而是“被智能体消费”

传统文档常常是写给人看的。  
但在这里，文档必须同时满足：

- 能被智能体发现
- 能被智能体理解
- 能与代码和规则交叉验证
- 过时后能被自动识别

因此文档的价值标准变了：

- 不是“内容全不全”
- 而是“能不能进入自动化闭环”

---

##### 4. 未来的工程竞争力，可能来自“harness 质量”

这些内容隐含着一个非常深远的判断：

以后组织之间的差异，未必主要是“谁模型更强”，而可能是：

- 谁的仓库更适合智能体工作
- 谁的架构更清晰
- 谁的规则更可执行
- 谁的反馈闭环更完整
- 谁的文档更结构化
- 谁能更快把人的判断固化为系统能力

也就是说，竞争力可能从“代码水平”部分转向：

> **AI 可操作性的系统设计水平。**

---

##### 六、这套方法的适用前提与边界

这些内容并没有说“任何团队立刻都能这么做”。  
它其实非常依赖一整套基础设施投入。

###### 要想接近这种模式，至少要具备：

- 清晰的仓库结构
- 明确的架构边界
- 完整的 lint / CI / 测试体系
- 结构化文档体系
- 可观测性接入
- 可复现实验环境
- 持续的知识维护机制
- 对技术债的自动化治理

所以它不是“装个 AI 插件就能实现”的事。  
它更像是：

> **围绕 AI 重新设计软件工程体系。**

---

##### 七、对团队和个人最实用的启发

即使你现在做不到“零手写代码”，也可以立刻吸收这套方法中的很多精华。

###### 对团队的启发

- 把关键决策从聊天工具搬进仓库
- 缩短 `AGENTS.md`，把它变成导航页
- 把架构规则机械化，而不是写在 Confluence 里
- 给 lint 错误信息加上“怎么修”
- 建立技术债持续清理机制，而不是周期性大扫除
- 优先增强智能体的验证能力，而不只是生成能力

###### 对工程师个人的启发

未来更值钱的能力，可能包括：

- 抽象与分层能力
- 把模糊目标拆成机器可执行任务的能力
- 设计反馈回路的能力
- 把个人品味转成团队规则的能力
- 构建“智能体友好型”代码库的能力

---

##### 八、一句话结论

**Harness Engineering 的本质，不是“让 AI 替你写代码”，而是“把软件工程从手工生产，升级为可编排、可验证、可持续优化的智能体生产系统”。**

它真正回答的问题是：

- 当代码几乎可以无限生成时，什么才是稀缺资源？
- 当产能不再是瓶颈时，工程纪律应该放在哪里？
- 当人类不再直接写代码时，如何仍然保持系统的连贯性、可靠性与可维护性？

这些内容给出的答案很清楚：

> **稀缺的是人的时间与判断力。  
> 纪律不应主要体现在手写代码上，而应体现在环境、约束、文档、工具和反馈回路上。**

---

##### 九、最简版提炼

如果把全部内容压缩成 6 句话，可以概括为：

1. **AI 时代，工程师的核心工作从写代码转向设计系统。**
2. **仓库必须成为智能体唯一可信的知识源。**
3. **文档要短入口、深链接、可验证，不能做成巨型说明书。**
4. **真正长期有效的是机械约束，而不是口头规范。**
5. **高吞吐场景下，等待比返工更贵，因此流程要围绕快速闭环设计。**

## 结构化（1）

### 2026-04-07 10:56:09

#### Harness 工程的主旨概括

这篇文章的核心观点是：在“智能体优先”的软件开发模式下，工程师的主要职责不再是亲手写代码，而是为 AI 设计好环境、规则和反馈回路，让它能稳定、持续地完成开发工作。  
OpenAI 用一个真实项目证明，这种方式不仅可行，而且在合适的工程体系下，开发效率可以达到传统方式的约 10 倍。

##### 1. 实验背景：用 Codex 从零构建真实产品

- OpenAI 团队在过去 **5 个月**里做了一项内部实验：从一个**空 Git 仓库**开始，构建并交付一款真实可用的软件产品。
- 这个项目的特点是：**没有一行代码由人手写**，包括：
  - 应用逻辑
  - 测试
  - CI 配置
  - 文档
  - 可观测性配置
  - 内部工具
- 项目最终规模达到约 **100 万行代码**，共经历了完整的软件生命周期：**开发、部署、故障、修复**。
- 团队最初只有 **3 名工程师**，却在这期间完成了约 **1,500 个 Pull Request**，相当于**人均每天 3.5 个 PR**；扩展到 **7 人**后，吞吐量还在增加。
- 产品并不是“为了演示而演示”，而是已经被**数百名内测用户**实际使用，其中还有**每天都在使用的重度用户**。
- 官方估算：整个项目只用了传统手写代码方式大约 **1/10 的时间**。

##### 2. 工程师角色变化：从“写代码的人”变成“设计系统的人”

- 在这种模式下，工程师的核心工作转向：
  - 设计环境
  - 明确目标和约束
  - 搭建反馈回路
  - 拆分任务并验证结果
- 文章强调，进展缓慢时，问题通常**不是模型不够强**，而是：
  - 环境不够清晰
  - 工具不够齐全
  - 抽象层不够合理
  - 约束不够明确
- 团队形成了一个重要原则：**“不手动编写代码”**。  
  一旦遇到问题，不是人自己下场补代码，而是反过来追问：  
  **“还缺什么能力、规则或上下文，才能让 Codex 自己完成？”**
- 实际流程上，人类主要通过提示词和工具驱动系统：
  - 描述任务
  - 运行智能体
  - 让它发起 PR
  - 再让它自己审查、响应反馈、修复问题，循环推进

通俗来说，工程师更像“导演”和“系统设计师”，而不是“打字员”。

##### 3. 提高智能体的可操作性：让应用、UI 和日志都能被 AI 直接读取

- 随着代码生成速度提升，瓶颈变成了**人工 QA 能力不足**。
- 团队的解决思路不是增加更多人工测试，而是让 Codex 能直接“看见”和“操作”应用：
  - 支持按 **git worktree** 启动独立实例
  - 接入 **Chrome DevTools 协议**
  - 提供 DOM 快照、截图、导航等能力
- 这样 Codex 可以自己完成：
  - 复现 bug
  - 观察 UI 行为
  - 修改代码
  - 重启应用
  - 再次验证修复是否生效
- 可观测性方面，他们还让 Codex 能直接使用：
  - **LogQL** 查询日志
  - **PromQL** 查询指标
  - 追踪（trace）数据进行性能分析
- 因此，一些以前必须人工做的要求变得可自动执行，比如：
  - “确保服务启动时间在 **800ms** 以内”
  - “四个关键用户路径中，任何一个跨度都不能超过 **2 秒**”
- 文章提到，Codex 单次运行经常可以持续工作 **6 小时以上**，而且通常发生在人类睡觉的时候。

这意味着 AI 不只是“写代码”，而是在独立完成“发现问题—修复问题—验证修复”的闭环。

##### 4. 仓库即记录系统：对智能体不可见的知识，等于不存在

- 作者提出一个非常关键的原则：  
  **“不在仓库里的东西，对智能体来说不存在。”**
- 对人类有用但不在仓库里的知识，例如：
  - Google Docs
  - Slack 讨论
  - 团队成员脑中的经验
  对智能体都不可见。
- 因此，团队把代码仓库本身变成了**唯一可信的记录系统**，把知识按结构化方式沉淀进去，比如：
  - `AGENTS.md`：作为简短目录页，约 **100 行**
  - `ARCHITECTURE.md`：架构地图
  - `docs/design-docs/`：设计文档
  - `docs/exec-plans/`：执行计划与进度日志
  - `docs/product-specs/`：产品规格
  - `QUALITY_SCORE.md`、`RELIABILITY.md`、`SECURITY.md` 等质量与治理文档
- 他们特别反对“超大 AGENTS.md”的做法，原因有三点：
  1. **挤占上下文**：说明书太长，会挤掉真正与任务相关的信息  
  2. **难维护**：一旦过时，智能体无法判断哪些规则还有效  
  3. **难验证**：巨型文档不适合做机械检查，漂移不可避免
- 更有效的方式是“**渐进式披露**”：
  - 先给一个小而稳定的入口
  - 再引导智能体按需读取更深的文档

可以理解成：与其给 AI 一本 1000 页手册，不如给它一张地图，让它按需查阅。

##### 5. 目标不是“人类可读”，而是“智能体可推理”

- 传统工程常强调“代码要让人容易看懂”，但在智能体优先的环境里，更重要的是：  
  **代码仓库要让 AI 容易推理。**
- 文章指出，智能体看不到的东西就等于不存在，所以越来越多上下文必须被编码进仓库：
  - 架构原则
  - 产品规范
  - 设计决策
  - 团队习惯
  - 工程文化
- 这也影响了技术选型。团队倾向选择所谓“**无聊但稳定的技术**”：
  - API 稳定
  - 可组合性强
  - 训练数据中覆盖充分
- 一个具体例子是：他们没有引入通用的 `p-limit` 风格库，而是自己实现了一个支持并发的 `map` 辅助函数，因为这样能获得：
  - 与自家 **OpenTelemetry** 更紧密的集成
  - **100% 测试覆盖**
  - 更符合自身运行时预期的行为
- 结论是：如果第三方库行为过于黑盒，**自己实现一个小而可控的子集，可能比“适配它”更便宜。**

这背后的逻辑很实用：AI 更擅长处理清晰、稳定、边界明确的系统，不擅长猜隐藏逻辑。

##### 6. 通过机械化约束保持架构稳定，而不是靠人盯人

- 文章强调，仅靠文档无法让一个完全由智能体生成的代码库长期保持一致。
- 更有效的方法是：**把不变量写成可执行规则**，交给 linter、测试和 CI 自动检查。
- 他们的架构采用严格分层，每个业务域内部依赖只能按固定方向流动：

`Types → Config → Repo → Service → Runtime → UI`

- 横切能力（如认证、连接器、遥测、功能标志）必须通过统一入口 **Providers** 引入。
- 这些约束由：
  - 自定义 linter
  - 结构测试
  - CI 检查
 进行强制执行。
- 除了架构约束，还有“品味不变式”，例如：
  - 强制结构化日志
  - 约束 schema 和类型命名
  - 限制文件大小
  - 平台特定可靠性要求
- 一个很有代表性的实践是：  
  **错误信息里直接写修复建议**，让智能体能根据报错自动纠正，而不是只告诉它“错了”。

作者认为，对人类来说这些规则可能显得教条；但对智能体来说，它们反而是效率放大器。  
因为一旦规则被编码，AI 就能在整个仓库里一致执行。

##### 7. 吞吐量变化后，传统合并理念不再适用

- 随着 Codex 吞吐量大幅提升，团队发现很多传统工程习惯不再合适。
- 关键变化是：  
  **在智能体高吞吐场景中，纠错成本低，而等待成本高。**
- 因此，他们采用了更快的合并策略：
  - PR 生命周期尽量短
  - 尽量减少阻塞式合并门
  - 测试偶发失败优先通过后续重跑解决，而不是长期卡住进度
- 文章明确说明：  
  在低吞吐团队里，这种做法可能是不负责任的；  
  但在高吞吐、可快速修复的智能体系统里，往往反而是更合理的策略。
- 审查流程也越来越“智能体对智能体”：
  - Codex 先本地自审
  - 请求其他智能体审查
  - 根据反馈继续修改
  - 循环直到通过
- 人类可以审查，但**不再必须参与每一次变更**。

也就是说，软件交付的节奏从“谨慎地一次做对”，变成了“快速流动、快速纠偏”。

##### 8. 自主能力提升：智能体已经能端到端完成一个功能闭环

- 随着测试、验证、反馈处理、恢复机制不断被编码进系统，Codex 已经能完成较完整的开发闭环。
- 给它一个提示后，它现在可以：
  - 验证代码库当前状态
  - 复现 bug
  - 录制故障演示视频
  - 实施修复
  - 运行应用验证修复结果
  - 录制修复后的视频
  - 打开 PR
  - 响应人类和智能体反馈
  - 检测并修复构建失败
  - 仅在需要人为判断时才升级给人工
  - 最终完成合并
- 但作者也提醒：这种能力**高度依赖特定仓库结构和前期工程投入**，并不能简单推广到任何团队。

换句话说，AI 的“自主”不是白来的，而是靠大量工程化建设“养出来”的。

##### 9. 熵管理与垃圾回收：AI 会复制好模式，也会复制坏模式

- 文章很诚实地指出：智能体会复用仓库中已有模式，**包括错误或低质量模式**。
- 一开始，团队靠人工每周五花掉约 **20% 时间**清理“AI 残渣”，但这显然不可扩展。
- 后来他们改为把“黄金原则”直接编码进仓库，例如：
  - 优先使用共享工具包，而不是到处手写辅助函数
  - 不做“YOLO 式”数据探测，而是在边界做验证，或使用类型化 SDK
- 同时运行后台 Codex 任务，自动做这些事：
  - 扫描偏差
  - 更新质量评分
  - 发起针对性重构 PR
- 这些重构 PR 大多数可以在 **1 分钟内**完成审查并自动合并。
- 作者把这比作**垃圾回收**：
  - 技术债像高息贷款
  - 最好每天小额偿还
  - 不要拖到最后一次性爆发

这部分的重点是：AI 生成代码的速度越快，治理和清理机制就越重要。

##### 10. 文章的最终结论：软件开发的纪律仍然重要，只是重心变了

- 作者最后强调，软件开发并没有因为 AI 变得“随便”。
- 相反，**纪律依然重要**，只是纪律不再主要体现在“手写代码有多规范”，而体现在：
  - 环境设计是否清晰
  - 反馈回路是否完整
  - 工具和约束是否有效
  - 代码仓库是否对智能体可读、可推理、可验证
- 他们仍在继续学习的问题包括：
  - 完全由智能体生成的系统，长期架构一致性会怎样演化
  - 人类判断力最该放在哪些环节
  - 随着模型能力增强，这套系统会如何改变
- 但可以确定的是：  
  **未来的软件工程，越来越像是在构建“让 AI 能可靠工作的生产系统”。**

##### 11. 一句话提炼全文

- **Harness Engineering 的本质，是把“写代码”升级为“设计一套让智能体持续产出高质量代码的工程系统”。**
