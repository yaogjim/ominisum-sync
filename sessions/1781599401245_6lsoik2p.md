#### 高质量 Coding协作链（从目标到完成）

![Image](https://pbs.twimg.com/media/HK20B41a0AEZtT0?format=png&name=large)

四个维度看分工

Plan = 蓝图（What/Order）：后续三者都读它、执行它、推进它

Subagent = 执行单元（Who）：派给隔离上下文的子代理，主上下文不被污染

Loop = 时间维度（When）：让长任务按节奏自动回来推进下一阶段

Goal = 经济维度（How much）：在拆解时就决定每段用什么模型最省

典型协作场景

场景 1：小改动 — 啥都不用，直接做。

场景 2：中等任务（30 分钟级）

头脑风暴 → 制定计划 → 执行计划（主代理自己一步步执行）

场景 3：大型多任务项目（要质量）

写作计划

subagent-driven-development（每任务派 implementer 子代理 →spec 评审子代理 → code quality 评审子代理）

场景 4：多个互不相干的 bug/失败

dispatching-parallel-agents（一个独立问题派一个 agent，并行跑，不需要完整plan）

场景 5：超长任务（几小时/跨会话）

writing-plans → /loop 30m（每次loop读 plan 三件套，推进下一阶段，更新progress.md）

场景 6：成本敏感的复杂目标/goal 先路由 → 对需要高阶推理的部分 writing-plans → subagent 执行（goal在最上层做经济决策，省下来的 token 会被记录）

#### 几个易混淆的点

1.Plan ≠ Goal：Goal 是"路由决策层"（怎么省），Plan是"执行蓝图"（怎么做）。Goal 产出的子任务列表可以喂给 Plan。

2.Loop 不创造进展，只推进：它读已有的 plan，按节奏往下走。 3.没有 plan，loop没东西可推。 4.Subagent 不是必须：executing-plans是主Agent自己干， 5.subagent-driven-development才派子代理。有Subagent能力时优先用后者，质量更高。

6.Plan 是契约：subagent 的 prompt、loop 、goal的路由结果，都引用同一个 plan 文件，保证三方对齐。

#### 深度总结

这篇内容的核心是：**用 Dynamic Workflow 把大模型从“单个 Agent 做事”升级为“项目组式协作”**。

它不是一个全新的底层技术，而是一套更成熟的 **Agent 工程范式**：通过计划、子代理、循环、目标路由等机制，让模型能同时调度大量 SubAgent，并行完成复杂任务。

##### 一句话概括

> Dynamic Workflow 的本质，是让 AI 像项目经理一样，把复杂任务拆开、分派、并行执行、持续推进、控制成本、最后验证结果。

---

#### 核心框架

##### 1. Plan：计划

解决问题：**做什么，按什么顺序做**

形式通常是一个 Markdown 文档：

- 任务拆解
- 步骤列表
- checkbox 进度
- 阶段目标

它相当于整个任务的“施工图纸”。

---

##### 2. SubAgent：子代理

解决问题：**谁来做每一步**

特点是：

- 每个任务派一个独立 Agent
- 每个 Agent 有隔离上下文
- 主 Agent 不亲自做细节，只负责协调
- 适合并行处理大量任务

这就像把一个人单干，变成一个临时项目组。

---

##### 3. Loop：循环

解决问题：**什么时候继续推进**

Loop 本身不创造结果，它只是定期回来检查：

- plan 进度如何
- 当前阶段是否完成
- 下一步该做什么
- 是否更新 progress

它更像一个“定时项目经理”。

---

##### 4. Goal：目标与成本路由

解决问题：**每一步花多少钱，用什么模型**

Goal 负责判断：

- 哪些任务需要强模型
- 哪些任务可以用便宜模型
- 哪些任务值得并行
- 哪些任务应该压缩成本

它是经济决策层。

---

#### 四者关系

| 模块 | 作用 | 类比 |
|---|---|---|
| Plan | 定义做什么、怎么做 | 蓝图 |
| SubAgent | 定义谁来执行 | 工人/专家 |
| Loop | 定义何时推进 | 项目节奏 |
| Goal | 定义成本与模型选择 | 预算经理 |

简化理解：

> Plan 管“事”，SubAgent 管“人”，Loop 管“时间”，Goal 管“钱”。

---

#### 使用场景总结

##### 小任务

直接让主 Agent 做即可。

不需要 Plan、SubAgent、Loop。

---

##### 中等任务

适合：

1. 先头脑风暴
2. 再写计划
3. 主 Agent 按步骤执行

---

##### 大型项目

适合：

- 写详细 Plan
- 每个任务派 SubAgent
- 再由评审 Agent 检查质量
- 最后统一合并

典型场景：

- 大规模代码迁移
- 全仓库 bug hunt
- 安全审计
- 多模块重构
- 复杂网站生成

---

##### 多个无关问题

适合直接并行派发多个 Agent。

例如：

- 10 个独立 bug
- 20 个测试失败
- 多个文件独立分析

---

##### 超长任务

适合：

- 写 plan
- 开 loop
- 定时推进
- 更新 progress.md

适合跨小时甚至跨会话任务。

---

#### 深入浅出解读

以前用 AI 编程，像是：

> 你雇了一个聪明程序员，让他从头做到尾。

现在 Dynamic Workflow 更像是：

> 你雇了一个技术负责人，他会临时组建一个团队，有人写代码，有人查 bug，有人做评审，有人管进度，有人控预算。

这就是变化的关键。

单 Agent 的问题是：

- 上下文容易爆
- 长任务容易忘
- 多文件任务效率低
- 复杂任务容易漏
- 一个思路容易自嗨

多 Agent 工作流的优势是：

- 可以并行
- 可以分工
- 可以复核
- 可以隔离上下文
- 可以扩大搜索广度

所以作者说它像 “Wide Research”，不是单点深挖，而是广泛探索后再收敛。

---

#### 关键判断

这篇文章真正有价值的地方，不是“100+ Agent 很酷”，而是指出了一个趋势：

> Agent 能力正在从炫技概念，走向工程规范。

Skill、SubAgent、Goal、Loop、Dynamic Workflow 这些词表面不同，本质都在解决同一类问题：

- 如何拆任务
- 如何分配执行
- 如何保持上下文干净
- 如何持续推进
- 如何控制成本
- 如何提高可靠性

也就是说，AI Coding 正在从“聊天式编程”走向“流程化软件工程”。

---

#### 辩证思考

##### 它的价值

Dynamic Workflow 确实能显著提升复杂任务的处理能力。

尤其在这些场景里非常有用：

- 任务规模大
- 文件数量多
- 需要交叉验证
- 需要并行搜索
- 需要长期推进
- 需要多角色协作

它让 AI 不只是“回答问题”，而是开始“组织生产”。

---

##### 它的问题

但也不能神化。

100+ Agent 并不等于 100 倍效率。

可能带来：

- token 成本暴涨
- 重复劳动增加
- 输出质量参差不齐
- 协调成本上升
- 最终整合困难
- 错误被批量放大

如果没有清晰 Plan，多 Agent 只会制造混乱。

如果没有验证机制，并行结果也可能只是“并行地产生幻觉”。

---

##### 真正的门槛

未来竞争重点不是“谁能拉起更多 Agent”，而是：

> 谁能设计更好的工作流。

包括：

- 任务怎么拆
- 角色怎么分
- 哪些并行，哪些串行
- 哪些用强模型，哪些用便宜模型
- 如何评审
- 如何合并
- 如何防止跑偏

Agent 数量不是核心，**组织能力才是核心**。

---

#### 最精炼结论

Dynamic Workflow 不是魔法，而是把 AI 使用方式工程化。

它解决的不是“模型会不会做”，而是：

> 如何让模型更稳定、更并行、更可控、更经济地做复杂任务。

短期看，它会疯狂烧 token。

长期看，它代表 AI Coding 从个人助手，走向自动化项目团队。
