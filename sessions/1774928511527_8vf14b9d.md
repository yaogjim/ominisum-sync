## 正文

**Onur Solmaz**

acpx v0.4 发布了代理工作流，或者我喜欢称之为 " 代理图 "

它允许你在 ACP（代理客户端协议） 之上创建基于节点的工作流，以通过确定性步骤驱动任何编码代理（Codex、Claude Code、pi）

这让你能够自动化日常的、机械性的基础工作，例如对新收到的 PR、错误报告中的 bug 等进行分类处理...

例如，OpenClaw 每天收到 300\~500 个新 PR。其中很多质量不高，但它们仍然与实际问题相关，所以你必须以某种方式处理它们

你需要：

提取意图  
基于意图对它们进行聚类  
弄清楚提议的变更是否合理，或者它们是否只是草率的本地解决方案，就像只捉苍蝇而不排干沼泽一样  
如果 PR 质量过低或意图不明确，关闭它们  
对它们进行 AI 审核，并处理出现的任何问题  
如果这些改动不成熟，就重构它们  
解决冲突  
等等...

这样，当 PR 提交给维护者时，所有例行工作都已完成，剩下的唯一事情就是决定（a）合并，（b）向 PR 作者提供反馈，或（c）亲自接手 PR 工作

几个月以来我就想实现这个功能，自从 Codex 变得这么好用以来。OpenAI 的模型现在很擅长评估实现质量，所以我发现自己一遍又一遍地重复着我上面写过的相同步骤。

我也尝试过将所有这些内容放入一个提示词中。但我认为存在一些工作流不应该是一个提示词，而应该是在同一个会话中的一系列提示词。

这是因为和人类一样，LLMs 容易受到启动效应的影响。我认为，将所有步骤放在同一个提示中并置于上下文开头，通常会产生次优结果，相比之下，逐步向模型透露意图则会更好。

创建这样的工作流还能对代理应该执行的每个步骤提供更多的可观测性。代理在每个步骤结束时生成 JSON，这种结构化数据可用于在仪表板上以更简便的方式监控同时运行的数千个代理。

类似的功能已在例如 n8n、langflow 等工具中被引入。但据我所知，它们并没有像我这样集成 ACP。

我想要一种全新的方法，并构建一个我可以按照自己意愿自由开发的 API，因此我在 acpx 内部创建了一个新的工作流 API

该视频来自工作流运行查看器，但这不是你构建工作流的地方。你可以通过使用 acpx flow TypeScript API 来构建它。查看 acpx 仓库中的 examples/pr-triage。

在构建那个之前，我从一个包含我设想的流程的 Mermaid 图表的 Markdown 文件开始。这个 Markdown 文件充当了流程的规范，我通过反复尝试构建了这个工作流。我将这个过程称为"workflow tuning"

我开始逐个处理 acpx 仓库的 PR，调整流程，逐步扩展到更多的 PR。最后，当我觉得有把握时，我在 acpx 仓库中所有外部开放的 PR 上并行运行了它。我相信这周它已经为我节省了好几个小时。

我的下一个目标，如果得到认可，是在云代理上设置这个，以便它能够实时处理 OpenClaw 仓库每天收到的 300\~500 个 PR，当它们到来时

我相信这将为全球所有开源项目维护者节省无数小时，并使收集和吸纳来自所有人的外部贡献变得容易得多！

## 通俗精炼（1）

### 2026-03-31 03:41:38

#### acpx v0.4 在讲什么？

##### 核心结论
acpx v0.4 新增了“代理工作流 / 代理图”能力：可以把一个复杂任务拆成多个确定性步骤，用节点式流程去驱动编码代理（如 Codex、Claude Code 等）自动执行。

##### 它解决了什么问题
作者想解决的是大量重复、机械性的开发协作工作，尤其是 PR 处理。  
比如面对每天数百个新 PR，系统可以自动完成这些基础动作：

- 提取 PR 意图
- 按意图聚类
- 判断方案是否合理
- 关闭低质量或意图不清的 PR
- 进行 AI 审核
- 必要时重构代码
- 解决冲突、推动 CI 通过

这样，真正交给维护者时，只剩下最后的关键决策：合并、反馈，或者自己接手。

##### 为什么不是“一个超级提示词”？
作者认为，很多工作流不适合塞进一个 prompt，而应该拆成同一会话里的多轮步骤。  
原因是大模型也会受到“启动效应”影响：一次性给太多要求，结果反而可能变差；分步骤逐步引导，通常更稳、更好。

##### 这个方案的价值
相比单纯让 AI 自由发挥，这种工作流方式有两个明显优势：

- **更可控**：每一步都明确，执行更稳定
- **更可观测**：每一步结束都产出 JSON，方便监控、调试和大规模并行运行

这意味着它不仅能自动化任务，还能成为一个可监控、可调优的生产系统。

##### 作者是怎么做出来的
作者先用一个包含 Mermaid 图的 Markdown 文件定义流程，把它当作“工作流规格说明”。  
然后通过不断试跑、调整流程、扩大适用范围，完成所谓的“workflow tuning（工作流调优）”。

最终，这套流程已经在 acpx 仓库的外部 PR 上并行运行，并且作者认为它一周就节省了自己好几个小时。

##### 更大的想象空间
作者下一步希望把它部署到云端代理上，实时处理 OpenClaw 每天 300~500 个 PR。  
如果这类系统成熟，价值不只是提升个人效率，而是可能显著减轻开源维护者的负担，让外部贡献更容易被吸收。

##### 一句话总结
这次发布的本质，不是一个普通新功能，而是把“AI 写代码”进一步推进到“AI 按流程处理开发协作工作”，让代理从单次执行工具，变成可编排、可监控、可规模化的工作系统。
