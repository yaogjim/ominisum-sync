## 分析要点

- **核心高价值点**：不要直接让Agent写代码，而应先用强模型生成并比较Plan，明确阶段目标和验收标准后再执行。
- **留存建议**：短期参考后可归档保留（提供了较清晰的Coding Agent使用流程，尤其是先规划、分阶段执行、最后Review的工作方法，可作为实践参考。）

**知识要点**

- Coding Agent的效果高度依赖前期需求整理和方案规划，开头走偏会导致后续修正成本很高。
- 多Agent更适合用于方案发散和交叉参考，执行阶段需要收束上下文并控制方向。
- 复杂任务应拆成多个Phase，并为每个阶段设定要求、素材引用和验证方法。
- 最终Review应聚焦是否符合设计要求以及代码质量，而不是让多个Agent无限交叉修改。

**行动项**

- 下次开发新功能时，先整理需求并让2-3个Coding Agent分别生成Plan。
- 人工比较不同Plan后，选定主方案并吸收其他方案优点。
- 复杂任务建立Markdown规划文档，拆分Phase并写明验收标准。
- 执行过程中按阶段人工审核，最后用强模型做代码Review。

## 正文

**宝玉**

用好 Coding Agent，重点是两头，尤其是开头的部分，如果一开始就走偏了后面怎么改都改不好。

比如我要开发一个新功能，首先不是直接叫给 Agent 去写，会把需求简单整理一下，发给三个不同的 Agent（Codex、Claude Code、Cursor），打开 Plan 模式去帮我写 Plan，这里要用最好的模型。

都写完了之后我去看看谁的最好，以及其他版本有什么可取的地方。GPT 5.5 和 Claude Opus 4.7 并不是谁总是最好，选好了设计后，再把另外两个设计也发给它，让它借鉴一下。当然都不满意就要反复调整提示词多轮讨论。

如果是简单的 Plan，直接就可以开始做了。

如果是复杂的 Plan，让它设计成几个 Phases，每个 phase 说清楚要求和验证的方法，保存成一个 Markdown 文档，把相关的素材也都引用上。

偷懒一点就用 /goal 把 plan 文件发给它，让它按照 Phases 执行，担心 Agent 跑偏就每一步完成人工去审核一下，及时纠偏。

写代码有条件当然用最好的模型，但如果像节约成本，便宜一点的模型也是可以的，毕竟设计好了、有明确的验收标准，偏不到哪里去。

最后代码 Review 不需要太多 Agent 去，GPT-5.5 这种就够了，重点是看是不是符合设计要求以及代码质量有没有问题。

这其实很像一个几个高水平的架构师，一人出一套系统设计方案，你来拍板，然后交给程序员去执行，最后让高水平的程序员或者架构师 review 一下代码。

## 解读（1）

### 2026-06-02 06:01:50

#### 总结

宝玉的核心观点：

> 用好 Coding Agent，关键在“两头”：**开头的方案设计** 和 **结尾的代码 Review**。  
> 尤其是开头，如果方向错了，后面越改越乱。

他的流程是：

1. **先写需求，不急着让 Agent 写代码**
2. 把需求发给多个 Agent：如 Codex、Claude Code、Cursor
3. 让它们分别出 Plan，用最强模型做设计
4. 人来比较、筛选、整合最佳方案
5. 复杂任务拆成多个 Phase，并写清楚验收标准
6. 执行阶段可以用便宜模型，但要按 Plan 走
7. 最后用强模型做 Review，看是否符合设计和代码质量要求

一句话：

> 多 Agent 适合用来“发散思路”，但执行和交付必须“收束”。

---

#### 解读

这其实是在说：

##### 1. 不要一上来就让 AI 写代码

很多人用 Coding Agent 的方式是：

> “帮我实现一个 XX 功能。”

然后 AI 开始写，写着写着就偏了。

问题在于：  
**需求没想清楚，AI 只会更快地把错误放大。**

所以第一步应该是：

> 先让 AI 帮你想方案，而不是直接写代码。

---

##### 2. 多个 Agent 的价值在“出主意”

不同模型的思路不一样：

- 有的设计稳
- 有的考虑边界情况多
- 有的实现路径简单
- 有的架构感更强

所以让多个 Agent 各出一版方案，就像请几个架构师开会。

但最后必须由人来拍板。

否则多个 Agent 互相改代码，很容易变成：

> 代码越来越多，问题越来越复杂。

---

##### 3. Plan 比代码更重要

一个好 Plan 应该包括：

- 要做什么
- 分几步做
- 每一步怎么验证
- 哪些资料要参考
- 最终验收标准是什么

Plan 清楚了，后面即使用便宜模型写代码，也不容易跑偏。

因为它不是自由发挥，而是在按图施工。

---

##### 4. Review 是最后一道保险

代码写完后，不是让一堆 Agent 反复改。

而是让强模型重点检查：

- 是否符合最初设计
- 有没有明显 bug
- 代码质量是否过关
- 有没有过度实现

重点是“验收”，不是继续发散。

---

#### 我的意见

我很认同这个方法。

用 Coding Agent 最忌讳的是：

> 没方案、没边界、没验收标准，只让 AI 一路写。

这样看似快，实际很容易返工。

更好的方式是：

```text
人负责方向和判断
AI 负责方案补充、执行和检查
```

简单说：

- **开头要慢一点**：把需求和方案想清楚
- **中间要稳一点**：按阶段执行，及时检查
- **结尾要严一点**：Review 是否符合目标

最值得记住的是这句话：

> Agent 可以帮你跑得更快，但你必须先确保方向是对的。

## 结构化（1）

### 2026-06-02 07:06:48

##### 主旨概括

宝玉认为，用好 Coding Agent 的关键在“开头”和“结尾”，尤其是开头的需求规划。如果一开始方向错了，后面再怎么修改代码都很难补救。

##### 1. 不要一上来就让 Agent 写代码

开发新功能时，宝玉不会直接让 Agent 开始编码，而是先把需求简单整理清楚。

他的做法是：

- 把需求发给多个 Coding Agent，例如：
  - Codex
  - Claude Code
  - Cursor
- 让它们进入 Plan 模式，各自写一份方案
- 这个阶段要使用最好的模型，因为设计质量决定后续执行效果

##### 2. 多个方案对比，人工拍板

不同模型并不是永远某一个最好，比如 GPT-5.5 和 Claude Opus 4.7 各有强弱。

宝玉会：

- 对比多个 Agent 写出的 Plan
- 选出其中最好的设计
- 把其他方案中有价值的部分补充进去
- 如果都不满意，就继续调整提示词，多轮讨论

核心思想是：**让多个 Agent 发散思路，但最终由人来收束和决策。**

##### 3. 简单任务直接执行，复杂任务要分阶段

如果 Plan 很简单，可以直接让 Agent 开始做。

如果 Plan 比较复杂，则应该让 Agent 拆成多个 Phases，每个阶段都要写清楚：

- 目标是什么
- 具体要求是什么
- 如何验证完成效果
- 相关素材和引用信息

最好把这些内容保存成一个 Markdown 文档，作为后续执行依据。

##### 4. 执行阶段要按 Plan 推进，必要时人工审核

执行时，可以把 Plan 文件通过 `/goal` 发给 Agent，让它按照不同 Phase 逐步完成。

如果担心 Agent 跑偏，可以在每一步完成后进行人工审核：

- 检查是否符合当前阶段目标
- 发现问题及时纠偏
- 避免错误累积到后面

##### 5. 编码阶段不一定非要最贵模型

如果预算充足，写代码当然可以用最好的模型。

但如果想节约成本，也可以用便宜一些的模型。原因是：

- 前期设计已经明确
- 验收标准已经写清楚
- Agent 的执行空间被限制住了
- 跑偏的概率会小很多

也就是说，**高质量 Plan 可以降低执行阶段对模型能力的依赖。**

##### 6. 最后 Review 要聚焦质量和设计一致性

代码 Review 不需要很多 Agent 一起交叉审查，宝玉认为用 GPT-5.5 这类强模型就足够。

Review 的重点是：

- 代码是否符合最初设计
- 是否满足验收标准
- 代码质量是否存在问题

原文引用推文也提到：  
“让不同的 agent 交叉 review 的后果就是代码越改越多。”

这说明多 Agent Review 容易导致过度修改，最终交付阶段应该收束，而不是继续发散。

##### 7. 类比：像多个架构师出方案，一个团队执行

宝玉把这个流程类比为传统软件开发：

- 几个高水平架构师分别出系统设计方案
- 人类负责人选择最合适的一版
- 程序员根据方案执行
- 最后由高水平程序员或架构师做代码 Review

这个类比说明：  
**多 Agent 最适合用于前期发散设计，执行和交付阶段则要强调统一、收束和质量控制。**

##### 8. 相关回复补充观点

热门回复中也有类似观点：

- 多 Agent 的优势在于“发散视野”
- 但执行和交付环节需要“收束”
- 有用户提到实践方式：
  - Claude Code 写方案
  - Codex 做 Review
  - 用状态机处理长流程和多轮对话
  - 用本地 ledger 解决记忆和 tracing

宝玉也回应说，多 Agent 除了能拓宽视角，还能隔离上下文，但最终交付仍然必须收束。
