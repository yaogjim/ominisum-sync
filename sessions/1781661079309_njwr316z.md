## 解读（1）

### 2026-06-17 02:12:11

#### 深度总结

这条内容的核心是：**Maka 很适合作为学习 Agent 工程化的样本**。

表面上，讨论的是 DeepSeek 的缓存优化，目的是省 token 成本；但实际推进过程中，暴露出一系列 Agent Runtime 的核心问题：

- **Prompt prefix 如何保持稳定**
- **Tool schema 如何标准化**
- **历史上下文如何做预算**
- **Usage / Cost 如何准确统计**
- **Cache miss 如何定位和解释**
- **是否应该裁剪历史上下文**

其中最重要的反直觉发现是：

> **砍掉历史上下文，不一定省钱，反而可能更贵。**

原因是：  
旧对话虽然占 token，但它可能帮助保持 prompt 结构稳定，从而提高缓存命中率。  
如果盲目裁剪历史，可能导致缓存失效，最终总成本上升。

所以 Maka 团队把默认滑窗裁剪改成了 **可选项 opt-in**。

---

#### 深入浅出解读

很多人以为做 Agent 就是：

> 写个循环：LLM 思考 → 调工具 → 返回结果 → 再思考。

但真正产品化后，会发现难点不在“能跑”，而在“稳定、便宜、可解释”。

##### 1. 缓存不是简单省 token

大模型缓存依赖前缀稳定。  
如果每次请求的 prompt 前半部分都变来变去，缓存就很难命中。

所以要优化的不只是长度，而是：

- prompt 顺序稳定
- 工具定义稳定
- 历史组织稳定
- 请求结构稳定

##### 2. 上下文不是越短越好

直觉上：

> 历史越短，token 越少，成本越低。

但现实可能是：

> 历史被砍后，缓存 miss 增多，反而更贵。

这说明 Agent 成本优化不是单点优化，而是系统工程。

##### 3. Agent Runtime 才是真正的难点

Agent 的核心不只是“智能”，还包括：

- 如何管理上下文
- 如何控制成本
- 如何复用缓存
- 如何记录 usage
- 如何解释异常
- 如何让行为可预测

这些都是从 demo 走向产品必须解决的问题。

---

#### 我的辩证思考

##### 价值

Maka 这类开源项目的意义在于：  
它把 Agent 工程中的“隐性问题”暴露出来。

很多教程只展示理想路径，而真实工程里最有价值的是：

- 失败案例
- 性能权衡
- 成本计算
- 缓存命中率
- 设计取舍

这些才是学习 Agent 的关键。

##### 局限

但也要注意：

> DeepSeek 缓存优化经验，不一定能完全迁移到所有模型和平台。

不同模型厂商的缓存策略、计费方式、上下文处理机制不同。  
所以不能机械套用“保留历史更省钱”这个结论。

更准确的说法是：

> 上下文裁剪必须基于实测，而不是基于直觉。

##### 启发

做 Agent 产品时，应避免两种极端：

###### 极端一：只追求智能

只关心模型能力，不关心成本、延迟、稳定性。  
结果是 demo 很惊艳，产品不可用。

###### 极端二：只追求省 token

盲目裁剪上下文、压缩 prompt。  
结果可能破坏缓存、降低效果，甚至增加成本。

真正成熟的 Agent Runtime，需要在以下几者之间平衡：

- 效果
- 成本
- 延迟
- 稳定性
- 可解释性
- 可维护性

---

#### 一句话结论

**Agent 工程的难点，不是让模型“动起来”，而是让它在真实产品中稳定、便宜、可控地运行。**

##### 主旨概括

作者认为 **Maka 很适合用来学习 Agent 工程实践**，因为它的开发过程透明，能看到一个 Agent 从简单循环走向真实产品时会遇到的核心 runtime 问题。文章重点以 DeepSeek 缓存优化为例，说明 Agent 工程并不只是“省 token”，而是涉及上下文、缓存、成本计算等复杂问题。

---

##### 1. Maka 适合学习 Agent 的原因：开发过程透明

- 作者提到，Maka 最近有一个 core dev 提了关于 **DeepSeek 缓存优化** 的 issue。
- 整个过程非常透明：
  - **1 个 issue**
  - **8 个 PR**
  - 从多个方向逐步推进优化：
    - usage 归一化
    - request prefix 稳定化
    - archive 压缩历史

相关项目链接：  
[github.com/jackwener/maka-agent/issues/19](https://github.com/jackwener/maka-agent/issues/19)

---

##### 2. 表面是省 token，实际暴露 Agent Runtime 核心问题

这个优化一开始看起来像是为了节省 token 费用，但真正做起来后，会遇到很多 Agent 产品化中的关键工程问题：

- **Prompt prefix 如何保持稳定**
- **Tool schema 如何标准化 / canonicalize**
- **历史上下文如何做预算管理**
- **usage 和 cost 如何准确计算**
- **cache miss 如何解释和定位**

这些问题说明，Agent 的难点不只是写一个简单的 agent loop，而是要处理完整运行时系统中的各种细节。

---

##### 3. 反直觉发现：砍历史不一定省钱

作者提到一个实际测试中的反直觉结论：

> 砍掉历史上下文，并不一定能省钱。

具体表现是：

- 原本以为删除旧 turn 可以减少 token，降低成本。
- 但实测发现，砍掉旧 turn 后反而导致 **cache miss 增加**。
- cache miss 增多后，总成本反而更贵。
- 因此团队把 **滑动窗口 trim** 改回了 **opt-in**，即默认不强制开启，需要用户主动选择。

这个案例说明，在 Agent runtime 中，成本优化不能只看 token 数量，还要考虑缓存命中率。

---

##### 4. 作者的核心观点：Agent 产品化会遇到真实工程问题

作者强调，这类问题是把 Agent 做成产品时必然会遇到的：

- 成本控制
- 上下文管理
- 缓存策略
- 工具 schema 稳定性
- prompt 结构一致性
- runtime 行为可解释性

因此，Maka 的价值在于它展示了 Agent 工程从实验到产品化的真实过程。

---

##### 5. 热门回复中的相关观点

###### 5.1 Ponytail：减少 Agent 过度写代码

有回复提到 Ponytail 项目，认为它和 Codex 很适合搭配使用。

核心理念是：

> “The best code is the code you never wrote.”  
> 最好的代码，是你根本不用写的代码。

回复者认为，GPT 经常会在没有明确要求时写大量防御性、兜底代码，导致过度工程化。Ponytail 的思路是强制 Agent 先判断是否真的需要写新代码，从而减少不必要的代码生成。

###### 5.2 Pi 可能成为 Agent 领域的 Android

- Pi 被类比为 **Agent 领域的 Android**。

---

###### 5.3 Deli AutoResearch SKILL：用协议管理长周期任务

还有回复提到 DeepSeek 资深研究员陈德里开源的个人项目 **Deli AutoResearch SKILL**。

关键信息：

- 项目以单一的 **SKILL.md 协议文件** 形式存在。
- 本身不包含可执行代码。
- 主要通过协议来指导 AI 处理长周期任务。
- 涉及能力包括：
  - 状态持久化
  - 防死循环 Anti-Loop
  - 心跳守护进程 Heartbeat Watchdog
- 该项目还发布了由智能体完全自主撰写的第四篇综述论文。

这篇内容通过 Maka 的 DeepSeek 缓存优化案例，展示了 Agent 工程的真实复杂度：**不是简单减少 token 就能降低成本，缓存命中、上下文稳定性、工具 schema 标准化等都直接影响系统表现和费用**。Maka 的透明开发过程让它成为学习 Agent runtime 和产品化工程问题的一个好案例。
