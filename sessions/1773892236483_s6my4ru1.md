  交互入口会从单一聊天窗口，转向操作系统层、浏览器层、协同软件层和 SaaS 内嵌层的竞争。**为什么**：谁更接近任务触发点，谁更容易成为默认代理。

- **用户习惯变化**  
  用户会从 “问问题” 转向 “下达任务”，从 “容忍试错” 转向 “要求可靠、可审计、可回滚”。**为什么**：Agent 进入工作流后，评价标准从趣味性切换为 SLA。

- **监管变化**  
  数据权限、系统控制、自动化操作、录屏 / 隐私、企业审计要求会越来越重。**为什么**：Agent 一旦接触桌面、浏览器和企业数据，就进入高监管敏感区。

- **基础设施变化**  
  MCP、A2A、工具协议、浏览器自动化标准、OS 原生 Agent API 可能逐步统一。**为什么**：一旦标准形成，中间适配层的独占性会下降。

- **最重要的 1 到 3 个变量**  
  1. **Agent 通用执行能力提升**；  
  2. **入口向 OS / 协同平台 / 浏览器平台集中**；  
  3. **标准化协议与工具基础设施成熟**。  
  **为什么**：这三个变量分别决定 “能不能做”“在哪里做”“是不是还需要中间层来做”。

#### 五、动态推演：一级影响

围绕最重要变量，直接推演如下：

- **当 Agent 通用执行能力提升时，哪些能力增强**  
  浏览器操作、文件处理、代码执行、界面理解、长链任务拆解会显著增强。**为什么**：这些原来需要定制技能或人工兜底的能力，会逐步由通用模型和通用工具链吸收。

- **哪些成本下降**  
  技能开发成本、工作流编排成本、任务试错成本、模型切换成本会下降。**为什么**：通用 Agent 越强，越少需要为每个场景单独写逻辑和封装接口。

- **哪些动作更便宜、更快、更标准化**  
  网页抓取、表单填写、文档处理、系统命令调用、搜索汇总、知识整理会被标准化。**为什么**：这些任务重复性高、结构明确，最容易进入通用工具和标准协议。

- **哪些原本稀缺的能力开始贬值**  
  “把模型接上工具”“把浏览器自动化包进客户端”“多模型适配”“内嵌运行时” 这类能力会开始贬值。**为什么**：它们从产品差异项逐渐变成行业默认配置。

- **当入口向头部平台集中时，会发生什么**  
  操作系统、浏览器、企业协同平台会试图把 Agent 原生化，中间宿主层的独立价值被压缩。**为什么**：入口方天然想拿走任务分发权和用户关系。

- **当协议标准化时，会发生什么**  
  技能、工具、模型适配的迁移成本下降，用户更容易在平台之间切换。**为什么**：一旦切换成本下降，中间层就更难维持高溢价。

#### 六、动态推演：二级影响

- **哪些供给会增加**  
  类似的 Agent 宿主、桌面助手、浏览器代理、企业自动化平台会大量增加。**为什么**：一旦底层能力标准化，创业门槛和大厂复制门槛同时下降。

- **哪些门槛会下降**  
  构建多 Agent 框架、接入工具协议、封装浏览器自动化、部署本地模型的门槛都会下降。**为什么**：开源组件、标准协议、云服务会把技术门槛模块化。

- **哪些中间角色会被削弱**  
  纯 “模型中转层”、纯 “工具编排层”、纯 “桌面壳” 会被削弱。**为什么**：如果平台自身可以直接调用模型和工具，中间胶水层会失去议价权。

- **哪些服务会被平台化、基础设施化、内生化**  
  MCP 接入、多模型路由、浏览器自动化、任务调度、权限弹窗、审计日志、轻量记忆会被平台化。**为什么**：这些高频共性能力最终都会成为基础设施，而不是独立利润池。

- **用户是否更容易自己做，或者转向头部平台**  
  是，尤其是中大型企业和开发者用户。**为什么**：当标准化成熟后，企业会优先选自己已有平台内生能力，或直接选操作系统 / 协同平台原生 Agent，而不是再接受一层新的宿主。

- **主路径、次路径、例外情况**  
  - **主路径**：通用能力上涨，中间层压缩，价值向入口和企业上下文迁移。**为什么**：控制任务触发和组织数据的一方更接近不可替代资源。  
  - **次路径**：若平台整合不足，独立 Agent 宿主在特定垂直场景仍可存活。**为什么**：复杂行业流程和合规要求可能让平台通用方案不够深。  
  - **例外情况**：如果悟空能成为钉钉内默认 Agent 操作系统，而不是单独 App，它可能反向强化。**为什么**：一旦绑定组织工作流，它就不再是中间层，而是入口的一部分。

#### 七、动态推演：三级影响

- **当通用能力被压平后，剩下什么仍然稀缺**  
  剩下真正稀缺的是：  
  1. **组织级上下文和权限图谱**；  
  2. **高价值任务流的深度嵌入**；  
  3. **复杂交付和失败兜底能力**；  
  4. **可信治理与审计能力**。  
  **为什么**：这些不是 “会不会做”，而是 “能不能在真实组织里被允许做、持续做、规模做”。

- **哪些价值会升值，哪些会贬值**  
  - **升值**：任务入口、组织数据、身份权限、跨系统编排、行业 know-how、可审计交付。**为什么**：通用模型越强，越需要高质量上下文和可靠执行边界。  
  - **贬值**：通用工具封装、多模型接入、基础浏览器自动化、轻量技能市场。**为什么**：这些能力供给快速增加，差异化持续下降。

- **这个对象会失去什么、保住什么、强化什么**  
  - **会失去**：作为 “先进技术展示型桌面 Agent 壳” 的溢价。**为什么**：这类能力最容易被复制和平台吸收。  
  - **会保住**：如果继续依附钉钉组织体系，它能保住企业工作入口中的一部分任务控制权。**为什么**：组织关系和协同入口不是轻易迁移的。  
  - **会强化**：若其能力被嵌入钉钉消息流、审批流、文档流、工作台流，它会强化为 “企业任务执行中枢”。**为什么**：此时它绑定的是流程，不是壳。

#### 八、价值迁移与产业格局

- **价值会从哪里流出**  
  价值会从独立的 Agent 壳层、纯技能分发层、通用工具封装层流出。**为什么**：这些层的技术壁垒最先被标准化和基础设施化侵蚀。

- **会迁移到谁那里**  
  主要迁移到三类主体：  
  1. **入口方**：操作系统、浏览器、协同平台；  
  2. **上下文掌控方**：拥有组织数据、工作流和权限图谱的平台；  
  3. **复杂交付方**：能深入垂直行业做闭环解决方案的服务商。  
  **为什么**：未来价值不在 “能调用工具”，而在 “谁定义任务、拥有上下文、承担结果”。

- **未来利润中心更靠近哪里**  
  更靠近**入口 + 组织能力 + 行业 know-how + 复杂交付**，而不是单纯平台中间层。**为什么**：通用平台会拿走基础设施利润，剩下溢价属于控制真实业务结果的人。

- **行业最终更可能集中还是分散**  
  底层通用能力会集中，垂直交付层会分散。**为什么**：模型、协议、基础工具趋于寡头化；但行业流程碎片化，导致场景层仍有长尾空间。

- **该对象未来更接近利润中心，还是成本中心**  
  这取决于它是否能从 “独立客户端” 升级成 “钉钉内部默认 Agent 层”。  
  - **主路径**：若只是独立桌面客户端，它会逐步滑向成本中心。**为什么**：它承担集成和维护，却难独占用户关系。  
  - **次路径**：若成为钉钉原生工作流基础设施，它可重返利润中心附近。**为什么**：此时它绑定的是组织执行，而非技术壳。  
  - **例外情况**：若它在特定高价值行业场景形成深度闭环，也可能作为垂直利润点存在。**为什么**：行业复杂度能阻止通用平台完全替代。

#### 九、机会分层判断

- **这是什么类型的机会**  
  它本质上是一个**中间层向入口层跃迁的阶段性机会**，不是纯平台级机会，也不是纯基础设施级机会。**为什么**：它当前站位仍在中间层，但它的想象空间来自向企业入口和执行中枢上移。

- **属于大机会、小机会、过渡机会，还是伪机会**  
  我的判断是：  
  - **对阿里 / 钉钉内部而言**：这是一个**大机会中的关键拼图**。**为什么**：它能帮助钉钉争夺 AI 时代的企业工作入口。  
  - **对独立复制者而言**：这是一个**过渡机会**。**为什么**：独立做同类宿主，长期容易被平台吞噬。  
  - **对不掌握入口和企业关系的创业团队而言**：如果只做 “类似悟空壳”，接近**伪机会**。**为什么**：看似热闹，实则很难留住利润。

- **是 “大机会少、小机会多”，还是 “少数巨头通吃”，还是 “长尾广泛存在”**  
  更可能是 “**底层少数巨头通吃，场景层小机会很多**”。**为什么**：底层入口、模型、协议会高度集中，但垂直行业和复杂流程的适配会长期分散。

- **更适合创业、产品布局、投资、职业进入，还是仅适合短期参与**  
  - **创业**：适合做垂直流程 Agent，不适合泛化复制悟空。**为什么**：泛化层竞争会被大厂和平台吃掉。  
  - **产品布局**：适合已有入口的平台公司布局。**为什么**：只有掌握流量和组织关系，才有机会吃到迁移后的价值。  
  - **投资**：更适合投 “场景闭环 + 行业数据 + 交付能力” 团队。**为什么**：这是未来残余高毛利区域。  
  - **职业进入**：非常适合进入 Agent 基础设施、企业自动化、权限治理、垂直流程设计。**为什么**：这些方向在未来 3-5 年会持续需要。  
  - **短期参与**：适合做实验和能力储备，但不宜误判为长期独立平台红利。**为什么**：热度高不等于结构性利润成立。

#### 十、风险与反例

- **这套分析成立的关键前提**  
  1. 通用 Agent 能力继续快速提升；  
  2. 工具协议和执行基础设施持续标准化；  
  3. OS、浏览器、协同平台加速原生 Agent 化；  
  4. 企业仍然优先使用已有协同平台承载 AI。  
  **为什么**：这些前提共同决定中间层会不会被压缩。

- **最可能推翻结论的现实因素**  
  最有力的推翻因素是：通用 Agent 在真实复杂任务上的可靠性提升慢于预期。**为什么**：如果执行可靠性长期不过关，那么高集成宿主和人工兜底体系的价值会维持更久。

- **哪些反方观点最有力量**  
  1. “桌面端是最强入口，独立 Agent 客户端会长期成立。”  
     这有力量，因为本地权限、屏幕、应用控制天然在桌面。**为什么**：如果 OS 不亲自下场，桌面宿主的确有持续性。  
  2. “企业不会把高风险权限交给通用平台，反而更需要专门中间层治理。”  
     这也有力量，因为合规和审计可能让中间层成为必须存在的一层。**为什么**：不是所有基础设施化都会导致层消失，有些层会因监管被强化。  
  3. “钉钉本身就是入口，因此悟空不是中间层，而是入口延伸。”  
     这是最强反例。**为什么**：若悟空被产品化为钉钉能力，而非独立 App，它的战略地位会被重新估值。

- **哪些地方容易因为 “逻辑正确” 而忽视 “现实阻力”**  
  1. 低估企业迁移惯性。**为什么**：组织流程改变比技术成熟慢得多。  
  2. 低估安全与审批的复杂性。**为什么**：很多自动化不是不能做，而是不能放开做。  
  3. 高估标准协议带来的真正可替换性。**为什么**：技术可替换不等于采购可替换。  
  4. 低估钉钉生态内部协同对产品渗透的帮助。**为什么**：大平台内部资源协同常常能弥补技术中间层的先天弱点。

#### 十一、最终结论

- **一句话本质判断**  
  悟空不是一个普通 AI App，而是阿里试图抢占 “企业 Agent 执行中枢” 的产品雏形；但如果它停留在独立桌面宿主层，长期会被平台化力量压缩。**为什么**：它今天的价值主要来自集成复杂度，未来的价值只能来自入口控制和组织嵌入。

- **最核心的因果链**  
  模型与工具能力提升 → 通用执行能力上升 → 中间封装层标准化 → 独立宿主溢价下降 → 价值向入口、组织上下文、复杂交付迁移。**为什么**：当 “会不会做” 不再稀缺，“在哪里触发、凭什么被信任、如何承担结果” 就成为新的稀缺点。

- **最值得押注的部分**  
  最值得押注的是它与钉钉组织体系、审批流、消息流、文档流、工作台流的深度融合，而不是桌面客户端本身。**为什么**：真正稳固的不是技术壳，而是嵌入工作结构后的默认性和迁移成本。

- **最不该高估的部分**  
  最不该高估的是 Tauri/Rust 架构先进性、多 Agent 宿主形态、内嵌运行时、基础自动化能力。**为什么**：这些会提升产品完成度，但大概率会成为行业标配，而非长期护城河。

- **如果要行动，应该顺势做什么**  
  应该顺势把悟空从 “客户端产品” 推进为 “钉钉内生 Agent 层”：深嵌审批、知识、表单、消息、协同、组织权限，并聚焦高频高价值任务闭环。**为什么**：只有变成企业工作流基础设施，它才不会在下一轮标准化中掉入成本中心。

- **如果要规避，应该避免什么**  
  应该避免把它当作一个泛化 Agent 市场或通用技能商店来经营，也应避免押注 “技术壳本身会长期产生高利润”。**为什么**：通用能力会迅速拥挤，真正难以替代的从来不是壳，而是入口、上下文和结果责任。

## 产品-产品技术PMF（1）

### 2026-03-19 10:33:37

这不是一个 “AI 聊天 App”，而是一套以桌面端为核心入口的 Agent 宿主平台。基于你提供的逆向信息，我的判断是：阿里 / 钉钉的 “悟空” 本质上在押注一个更大的方向 —— 把企业协作入口、桌面操作系统能力、浏览器自动化、LLM 编排、多渠道触达，收束成一个可持续扩展的 “企业级 AI 执行层”。

**核心判断**
- `Wukong`的产品本质不是单一助手，而是 “企业 AI Agent OS / Agent Runtime Platform”。
- 其真实竞争对手不是普通 AI 聊天产品，而是`Claude Desktop + MCP 生态`、`OpenAI/Codex 类本地代理`、`微软 Copilot + Windows 系统能力`、以及大量 RPA / 工作流平台。
- 从架构上看，它明显不是 demo 导向，而是按 “长期平台化” 思路设计：多引擎、多工具、多渠道、多运行时、多安全层。
- 从 PMF 角度看，它最有希望先打穿的不是 C 端泛助手，而是 “高频办公自动化 + 企业知识处理 + 内外部系统协同” 的准垂直场景。
- 最大机会在于 “钉钉生态 + 企业权限 / 组织 / 流程 / 消息分发” 形成闭环；最大风险在于 “能力太全，场景不聚焦，用户感知价值可能被稀释”。

**一、产品定位分析**
- 这是一个 “桌面 AI Agent 控制台”，而不是传统意义上的 IM 内嵌 Bot。
- 产品目标显然是把 AI 从 “回答问题” 推进到 “代表用户执行任务”，包括读文件、开网页、调应用、调模型、跑脚本、发消息、定时执行。
- `real-cli`、`browser-runtime`、`skills`、`MCP`、多渠道模块同时存在，说明它不是只服务一个前端界面，而是一个统一 Agent Runtime，桌面端只是最强入口。
- `channels/dingtalk/slack/whatsapp`的存在说明其设计目标是 “一次定义能力，多渠道分发触达”，这和传统桌面助手完全不同，更像企业任务执行中台。
- 命名上 “Real Loop / Spark Loop / Soul / Skills / Device” 说明团队在构建一整套 Agent 世界观，不是简单拼装开源组件。

**二、目标用户与真实需求**
更可能的首批核心用户，不是普通消费者，而是以下几类：

- 企业知识工作者：要处理文档、表格、PPT、网页信息搜集、跨系统复制粘贴、周期性任务。
- 管理者 / 项目负责人：希望 AI 做信息汇总、提醒、跨群 / 跨渠道同步、日报周报生成、任务跟进。
- 中后台运营 / 销售 / 招聘 / 客服：大量 “半结构化任务”，最适合浏览器自动化 + 文件处理 + 定时任务。
- 开发者 / 高级用户：会接受`CLI/MCP/ 本地模型 / 技能安装`，愿意把它当半个工作台来用。
- 企业 IT / 组织管理员：关注权限、审计、隔离、模型接入和内外网部署。

它解决的核心 Job-to-be-done 可以概括为三类：
- “帮我理解信息”：文档解析、网页阅读、图像理解、搜索聚合。
- “帮我执行动作”：浏览器操作、脚本执行、UI 自动化、定时任务。
- “帮我连接组织”：钉钉消息卡片、Slack/WhatsApp、设备注册、云端能力联动。

**三、产品战略意图**
从架构反推，阿里 / 钉钉可能在同时做三件事：

- 抢占桌面 Agent 入口  
  通过 macOS 原生客户端，把 AI 从聊天框推到系统级能力层。谁掌握桌面执行层，谁更可能成为 “真正可用” 的 Agent 平台。
- 抢占企业 Agent 基础设施标准  
  通过`skills + MCP + 多模型 + 多渠道`，试图定义一个企业内部 Agent 的装配方式。
- 抢占钉钉未来的人机交互入口  
  如果 AI 能直接在钉钉组织、消息、流程、文件、账号体系里工作，钉钉就不再只是协作软件，而是企业 AI 操作系统的上层入口。

**四、技术架构判断：成熟度很高，且明显偏平台化**
我对这套架构的评价是：方向正确、工程品味较好、边界意识强，且明显为长期演进留足了空间。

1. 技术路线选择
- 选择`Tauri + Rust + WRY/WebKit`而不是 Electron，说明他们把性能、资源占用、安全性、可分发性放在很高优先级。
- 主程序纯 Rust，意味着核心 runtime、进程管理、权限控制、协议适配、状态机等关键层都在可控栈里。
- 浏览器自动化独立为`browser-runtime`微服务，而不是硬塞进主进程，说明他们在做 “隔离 + 解耦 + 可替换”。

2. 架构分层质量
- `agent/runtime`、`gateway`、`channels`、`model_provider`、`skills`、`system`、`rpc`分层清楚，说明它不是 “先写功能再补架构”。
- `spark_loop/allspark`使用 DDD 分层，这在国内 AI 应用里并不常见，通常意味着团队希望把复杂业务规则沉淀为长期可维护系统。
- `session_approval_memory`、`sandbox_policy_loader`、`sensitive_paths`这类模块命名非常 “产品化”，说明不是只做功能，而是考虑用户长期使用中的信任与稳定性。

3. 运行时策略
- 内嵌`Bun + Node + Python + Chromium + 本地模型`，是典型的 “自包含运行时” 思路，优点是交付稳定、环境一致、降低用户安装门槛。
- 缺点也很明显：安装包重、更新复杂、平台适配成本高、签名和安全审计难度更高。
- 但对 Agent 产品来说，这个选择是合理的，因为 “能跑起来” 比 “安装包轻” 更重要。

4. 多 Agent 宿主平台
- 同时支持`Spark/Claude/Gemini/Codex/Local/Builtin`，这是非常关键的战略设计。
- 这意味着悟空不把自己绑定成某个模型的 UI，而是做 “模型与代理能力的编排层”。
- 一旦这个抽象做稳，它的护城河就不只是模型，而是任务执行框架、权限系统、技能生态和组织分发能力。

**五、技术亮点与产品价值映射**
几个最有价值的技术点，不只是工程亮点，而是直接对应产品价值：

- `MCP 原生支持`  
  这让它具备外部工具扩展能力，意味着未来企业内部任何系统都能被接成 Agent 能力。
- `Skills 系统`  
  技能安装、启停、删除、渐进式发现，本质上是在做 “企业版插件市场”。
- `Browser Runtime + Playwright`  
  这是最现实的执行层，很多企业系统没有 API，但都有 Web 页面，浏览器自动化可以迅速形成落地场景。
- `Cron + 多渠道`  
  说明它不是一次性问答，而是具备 “持续性代理” 能力，能从同步助手进化为异步任务代理。
- `Human-in-the-Loop + Sandbox`  
  这决定它能不能进入企业场景。没有审批、记忆和沙箱，Agent 只能演示，不能上生产。

**六、PMF 分析：有潜力，但必须先聚焦**
如果只看能力，悟空非常强；但 PMF 不看能力总量，而看 “某类用户是否愿意高频使用并离不开”。

我认为它最可能的 PMF 路径是：

- 先在高频办公场景找到强需求闭环  
  如：搜集信息 -> 整理文档 -> 生成汇报 -> 发送到钉钉 / Slack -> 定时跟进。
- 再在企业场景建立 “可信执行” 心智  
  用户不仅问它，还敢让它去操作文件、网页、系统、应用。
- 最后通过技能 / MCP / 组织分发形成平台效应  
  当企业开始沉淀自己的技能包和 Agent 流程时，迁移成本就会很高。

当前它的 PMF 优势：
- 钉钉天然有组织、消息、权限、审批、流程基础设施。
- 企业办公场景天然存在大量重复性、高频、半结构化任务。
- 桌面 Agent 比纯 Web Agent 更容易触达 “最后一公里” 的真实执行。
- 多模型兼容降低了单模型依赖风险，也利于企业差异化部署。

当前它的 PMF 风险：
- 场景过宽，用户不一定能快速理解 “我到底该拿它干什么”。
- 权限多、能力深，首次使用门槛偏高，容易变成高级用户玩具。
- 如果技能生态不足，自带能力再多，也会卡在 “看起来强，日常用不起来”。
- 浏览器自动化和 UI 自动化虽然强，但稳定性、权限弹窗、页面变化、反爬限制都会影响体验。
- 如果企业数据权限、审计、模型合规没有形成产品化方案，规模化落地会受阻。

**七、商业价值与护城河**
它未来真正的护城河，不会是 “哪个模型更聪明”，而是以下四层：

- 组织护城河：钉钉账号体系、企业通讯录、审批、群消息、工作流。
- 执行护城河：桌面权限、浏览器自动化、系统调用、脚本和定时任务。
- 生态护城河：技能包、MCP 服务器、渠道分发、第三方工具接入。
- 安全护城河：沙箱、审批记忆、凭证管理、策略配置、合规接入。

如果做成，商业模式也很清晰：
- 企业席位订阅：按活跃用户、Agent 数量、调用次数收费。
- 高级执行能力套餐：浏览器自动化、跨应用控制、定时代理、团队共享技能。
- 企业模型与私有部署：本地模型、专有知识库、专线 / 私有云接入。
- 技能市场抽成或生态服务费。
- 面向钉钉生态伙伴的开发平台收费。

**八、从产品落地看，最应该先打的场景**
如果我是产品负责人，我不会先讲 “全能 Agent OS”，而会优先打下面 3 个场景包：

- 办公文档代理  
  PDF/Word/Excel/PPT 的解析、改写、摘要、汇总、生成、分发。这个场景天然高频，也最容易体现本地文件 + 钉钉消息联动价值。

  用`cron + channels + approval`做提醒、日报、舆情跟踪、客户线索收集、竞品监控、例行检查。这个场景一旦跑通，粘性会很强。

**九、对架构的产品级评价**
整体上，这是一个 “为未来 3-5 年演进预埋得比较完整” 的架构，而不是短期冲量产品。

## 产品-技术开发实现（1）

### 2026-03-19 10:35:14

这不是一个 “AI 聊天 App”，而是一个典型的 “Agent OS / Agent Host” 雏形。产品上，它在做的是：把模型、工具、运行时、权限、安全、多渠道分发，统一封装成一个桌面 Agent 平台；技术上，它选择了`Tauri + Rust + WebView + Sidecar Runtime`，本质是用原生宿主承载多种 AI 引擎和自动化能力。

**产品解读**
- `Wukong`的真正产品定位不是助手，而是 “多 Agent 宿主平台”：既能跑自研`Spark`，又能接`Claude/Codex/Gemini/MCP`，说明它的核心壁垒不是单模型，而是统一运行与分发层。
- 它明显面向 “高价值任务流” 而非闲聊：浏览器自动化、Shell、文件解析、定时任务、跨渠道消息，组合起来就是企业知识工作自动化。
- 钉钉基因很强：`AI Card + Stream + Slack/WhatsApp`说明它不是单端产品，而是 “桌面调度中心 + 多渠道触达终端”。
- 内置`Bun/Node/Python/Chromium/Qwen`的意义很大：降低环境依赖，提升开箱即用率，这是 Agent 产品落地的关键，不然安装门槛会直接打掉使用率。
- `preview/full`技能分级、`skill_injection_policy`、`HITL`审批记忆，说明它在解决 Agent 产品最核心的矛盾：能力越强，越需要控制感和可解释性。

**技术架构判断**
- `Tauri + Rust`是正确方向：比 Electron 更省内存、更易做系统级能力集成，适合长期演进为重型 Agent 客户端。
- 前端放 WebView，核心能力放 Rust，浏览器自动化拆成独立 TS 微服务，这是很务实的 “三层分工”：
  - UI 层：快迭代
  - Orchestrator 层：高稳定、高安全
  - Tool Runtime 层：高隔离、易替换
- `real_loop + spark_loop`说明内部已经有 “双引擎” 思路：一个偏通用执行编排，一个偏自研 Agent 内核。这比把所有逻辑塞进单循环更容易演化。
- `DDD`分层不是形式主义，在 Agent 系统里尤其重要：`session/memory/tool/sandbox/model-provider/channel`都是强边界模块，不分层后期一定失控。
- `SQLite + CoreData + CloudKit + encrypted prefs`是桌面端合理组合：本地低延迟、系统能力强、部分云同步可选，不会一上来全依赖远端。

**最值得肯定的设计点**
- `Model Provider`抽象做得对：`MaaS/Qwen/OpenAI`统一到 streaming、tools、parallel tool calls，这决定了以后能否低成本切模型。
- `Skill + Built-in Tool + MCP`三层扩展体系很完整：
  - Built-in Tool：核心能力，可靠可控
  - Skill：面向场景封装
  - MCP：外部生态接入
- `session_approval_memory`很关键。好的 Agent 不只是能申请权限，而是能 “记住你的授权偏好”，减少重复打扰。
- `sandbox_policy_loader + sensitive_paths + PromptGuardrails`说明其安全不是只做 UI 弹窗，而是在执行链路做控制。
- 事件流`TaskStart -> ToolUse -> PermissionRequest -> Complete/Error`是标准可观测 Agent 生命周期，利于审计、调试和回放。

**潜在风险与难点**
- 多运行时内嵌很强，但运维复杂度高：`Rust + Bun + Node + Python + Chromium + local Qwen`会带来包体、升级、兼容性和漏洞修复压力。
- `UI automation + AppleScript + ScreenCapture`能力很强，但 macOS 权限模型和系统升级很容易造成功能脆弱。
- 多 Agent 共存的最大问题不是 “能不能接”，而是 “上下文和工具调用语义能否统一”，否则用户体验会割裂。
- 本地模型和云模型混用时，任务路由很难：哪些任务本地跑、哪些上云、何时回退，需要有明确策略，否则成本和体验都不稳。
- 技能生态若缺少强审核机制，会很快走向提示词注入、恶意自动化、越权访问等问题。

**最佳实践：如果你要做同类产品，建议这样设计**

- **1. 宿主架构**
  - 用`Rust/Tauri`做主进程，所有高权限能力都经由 Rust Command Gateway 暴露。
  - 浏览器自动化、代码执行、OCR / 多媒体处理尽量拆 sidecar 或独立子进程，不直接嵌进 UI 进程。
  - 例子：
```text
UI (WebView)
  -> Gateway (Tauri commands)
    -> Agent Runtime
      -> Tool Router
        -> sidecar-browser /sandbox-shell/file-parser /model-provider
```

- **2. 工具调用协议统一**
  - 给所有工具定义统一 schema：`name/input/output/error/cost/permission_scope/artifact_refs`。
  - 例子：`browser_screenshot`和`parse_file`都返回标准化`artifact`，方便后续消息引用和审计。
```json
{
  "tool": "parse_file",
  "input": {"path": "/tmp/a.pdf"},
  "output": {"text": "...", "artifacts": [{"id": "file_123", "type": "text/plain"}]},
  "permission_scope": "file.read:/tmp",
  "duration_ms": 842
}
```

- **3. 权限系统不要只做弹窗**
  - 权限应至少分 4 层：`read`、`write`、`execute`、`automation/control`。
  - 增加 session 级、workspace 级、永久级授权记忆；高风险操作永远不自动放行。
  - 例子：
    - 读取桌面文件：可 “本会话允许”
    - 执行 shell：每次确认
    - 控制第三方 App：强提醒 + 录审计日志

- **4. 记忆系统分层**
  - 不要把所有对话都塞向量库。至少拆成：
    - `session memory`：当前任务上下文
    - `approval memory`：授权偏好
    - `profile memory`：用户长期偏好
    - `task artifact store`：文件、截图、下载物
  - 例子：用户说 “默认用中文回复” 属于 profile；“允许读取这个项目目录” 属于 approval；“本次要整理这份 PDF” 属于 session。

- **5. 模型路由策略**
  - 设计显式的任务路由器，不要让模型自己随意决定。
  - 例子：
    - 本地模型：摘要、分类、OCR 后整理
    - 云大模型：复杂推理、长规划、多工具编排
    - 专项模型：文生图 / 视频
```text
if task in {summarize, classify} and context_size < threshold:
    use local_qwen
elif task requires tool planning or long reasoning:
    use cloud_qwen/openai
elif task == image_generation:
    use text2image provider
```

- **6. 技能系统要 “场景化封装”**
  - 技能不是工具列表，而是场景工作流模板。
  - 好的技能应包含：适用域名 / 应用、权限需求、失败回退、输出格式、监控指标。
  - 例子：`12306-train-query`不是单纯打开网页，而是：
    - 检查登录状态
    - 识别查询条件
    - 执行搜索
    - 提取车次结果
    - 失败时回退到页面截图 + DOM 摘要

- **7. 可观测性必须内建**
  - 每个任务记录：模型、prompt hash、工具链路、权限决策、耗时、token、失败节点。
  - 给调试工作台做三种视图：
    - Timeline
    - Tool I/O
    - Permission Trace
  - 这比 “看日志文件” 有效得多，尤其适合 Agent 调试。

**从产品竞争看，Wukong 的真正优势**
- 不是模型能力，而是 “系统能力 + 企业连接 + 可控自动化 + 多端分发”。
- 对阿里 / 钉钉来说，这条路线比做一个单纯聊天入口更有壁垒，因为它更接近企业生产力操作系统。
- 如果后续补强`MCP 生态、团队协作、任务回放、组织级权限策略`，它会从个人助手升级为企业 Agent 平台。

**一句话结论**

## 产品-最佳实践（1）

### 2026-03-19 10:36:39

可以。基于你这份对`Wukong`的逆向分析，我建议不要泛泛谈 “架构先进”，而是落到一个可执行的 Agent 场景上，再从这个场景里提炼最佳实践。

我用一个具体实例来讲：

**实例：用户让 Wukong 自动完成 “竞品信息收集并发到钉钉群”**

用户输入：
“帮我收集今天 3 家竞品的官网更新、新闻动态和招聘变化，整理成一份摘要，下午 6 点自动发到钉钉群里。”

这个需求，正好能覆盖你文中提到的核心能力：
- `real_loop` / `spark_loop`：Agent 主循环与任务编排
- `browser-runtime`：浏览器自动化
- `internet-search`、`read_url_v2`：搜索与网页读取
- `cron_*`：定时任务
- `channels/dingtalk`：钉钉消息分发
- `memory/sqlite.rs`：长期记忆与任务状态
- `session_approval_memory`：权限审批记忆
- `SandboxV2Config`：执行隔离
- `skills`：按站点注入技能

下面给出这个实例之上的最佳实践。

**一、先把任务拆成 “可审计的工作流”，不要让 Agent 直接一把梭**
- 最佳做法是把任务拆成`搜索 -> 抓取 -> 提取 -> 汇总 -> 审批 -> 定时发送`六步，而不是让大模型自由发挥。
- 你这套架构里最适合承接这个的是`gateway/service.rs + agent/runtime/real_loop/commands.rs`，由 Rust 侧做强编排，模型只负责 “决策” 和 “摘要”，不要负责 “执行细节”。
- 原因是：浏览器、消息发送、定时任务都属于高风险动作，必须有稳定状态机，不能完全依赖 Prompt。
- 实践上，每一步都生成事件：`TaskStart -> PreToolUse -> PostToolUse -> PermissionRequest -> TaskComplete/TaskError`，这样日志、回放、审计都成立。

**二、工具调用要 “白名单化”，而不是 “能力越多越好”**
- 在这个实例里，Agent 实际只需要开放：
  - `internet-search`
  - `read_url_v2`
  - `browser_start`
  - `browser_screenshot`
  - `cron_create/update`
  - `dingtalk ai_card send`
- 不应该默认开放`execute_shell`、全量文件访问、任意 UI 自动化。
- 最佳实践是按任务上下文生成最小工具集，这和你文中`skill_injection_policy = explicit/auto`很契合。
- 具体建议：默认`explicit`，只有当模型明确说明 “为什么需要这个工具” 时，才切到更高权限。

**三、浏览器自动化必须走 “双通道策略”：优先读取，失败再操作**
- 这个竞品收集任务里，大部分网页信息其实不需要真实点击交互，优先走：
  - `internet-search`
  - `read_url_v2`
  - `reader_html_content`
- 只有遇到动态渲染、登录后可见、反爬页面，才降级到`browser-runtime + Playwright`。
- 这是最佳实践，因为浏览器自动化成本高、稳定性差、易受 DOM 改动影响。
- 所以建议在`browser-runtime/src/browser/client-actions.ts`之上增加一个策略层：
  - `readable_page -> content parser`
  - `interactive_page -> playwright action`
- 这样能显著降低 token、CPU、失败率和权限暴露面。

**四、权限审批不要只做 “弹窗确认”，要做 “记忆化授权”**
- 这个场景里有两个高风险动作：
  - 定时发送到钉钉群
  - 首次访问外部网站并做自动化采集
- 最佳实践不是每次都问，而是结合`session_approval_memory.rs`做分级授权：
  - 一次性允许：仅本次任务有效
  - 对该网站长期允许：例如`example.com`
  - 对该群发送长期允许：例如某个钉钉群 ID
  - 永久拒绝某类动作
- 这样既保留 HITL，又不会把体验做成 “权限弹窗模拟器”。
- 更进一步，授权粒度要绑定 “动作 + 目标 + 时效”，例如：
  - `send_message` + `group_123` + `until 2025-12-31`
  - 而不是模糊地 “允许钉钉发送消息”

**五、记忆系统只记 “结构化事实”，不要把整段对话全塞进长期记忆**
- 在这个实例中，长期需要记住的是：
  - 竞品名单
  - 信息源 URL
  - 用户偏好的摘要格式
  - 钉钉发送目标
  - 定时规则
  - 权限决策
- 不建议把每次网页抓到的大段原文或整个聊天上下文长期存 SQLite。
- 最佳实践是把`memory/service.rs + sqlite.rs`分成三类存储：
  - `UserPreference`
  - `TaskConfig`
  - `ExecutionArtifact`
- 摘要类内容保留 hash、来源、时间戳、抽取结果即可；原始网页内容可以短期缓存，不进入长期记忆。
- 这样更利于合规、检索和控制存储膨胀。

**六、多模型路由要按任务阶段选型，不要 “一个模型跑全链路”**
- 你文中显示它支持`MaaS/Qwen/OpenAI`，这类架构的最佳实践就是分工：
  - 规划阶段：高推理模型
  - 网页抽取阶段：便宜、快的模型或规则解析
  - 最终汇总阶段：质量更高的生成模型
- 比如这个实例可以这么路由：
  - 任务规划：`Qwen / OpenAI reasoning model`
  - 页面摘要：轻量模型
  - 最终日报润色：高质量模型
- 再配合你文中的`prompt_cache_hit_tokens`和 streaming，能降低成本和首字延迟。
- 如果做得更成熟，建议在`model_provider`层引入 “阶段路由策略”，不要让上层业务自己挑模型。

**七、定时任务必须做幂等和补偿，不然消息系统一定出事故**
- 这个场景很容易出现：
  - 18:00 触发了两次
  - 抓取失败后仍然发送空消息
  - 钉钉发送成功但状态没写回数据库，随后重复补发
- 所以`cron/store/job_store.rs`、`run_store.rs`、`delivery_store.rs`的最佳实践是：
  - 每次任务运行生成唯一`run_id`
  - 每次消息发送生成唯一`delivery_id`
  - 渠道层按`delivery_id`去重
  - 发送前校验摘要是否完整
  - 失败后有重试上限和退避策略
- 这在多渠道分发里尤其重要，因为 Slack、钉钉、WhatsApp 的重试语义不一致。

**八、渠道输出要做 “统一中间格式”，不要让每个渠道各拼各的**
- 这个实例最终要发到钉钉群，但未来很可能也要同步到 Slack。
- 最佳实践是先生成一个统一消息模型，例如：
  - 标题
  - 摘要段落
  - 来源链接
  - 风险提示
  - 执行时间
- 然后在`channels/dingtalk/ai_card.rs`、`slack.rs`里分别渲染。
- 不要让 Agent 直接输出 “钉钉卡片 JSON” 或 “Slack markdown”，否则一旦扩展渠道，Prompt 和模板都会失控。
- 也就是说，模型只产出语义内容，渠道层负责表现格式。

**九、内置技能与站点能力要 “站点隔离”，不要共享隐式上下文**
- 你文中提到`mbb-skills`针对特定网站，比如`12306`、`ctrip`、`dianping`。
- 套到这个竞品收集场景，最佳实践是：每个站点技能都应该声明自己的：
  - 适用域名
  - 可执行动作
  - 输入输出 schema
  - 是否需要登录
  - 是否允许自动提交表单
- 这样`skill_snapshot.rs`做技能注入时，不会把 “携程订票技能” 错误暴露给 “企业官网信息采集” 任务。
- 本质上，技能不是插件目录，而是 “受约束的能力声明”。

**十、桌面级 Agent 一定要把 “可见性” 做成产品特性，而不是调试功能**
- 对用户来说，这类 Agent 最怕 “它在背后做了什么我不知道”。
- 所以这个实例里，界面上至少应该持续展示：
  - 当前步骤
  - 正在访问哪个站点
  - 调用了哪个工具
  - 为什么需要权限
  - 下一次定时执行时间
- 这和你文中的`agui_stream.rs`很匹配，建议把它做成 “实时执行时间线”，而不是只在日志文件里可见。
- 最佳实践是：每个工具调用都能回放，每个外部动作都有用户可理解的解释文案。

**如果把这些最佳实践压缩成一套落地原则，就是这 5 条**
- 先工作流，后智能体：高风险动作必须由状态机编排，不交给 LLM 自由发挥。
- 先最小权限，后动态提权：工具、路径、渠道都按任务最小化开放。
- 先读取解析，后自动化操作：能抓 HTML 就不要上浏览器，能 API 就不要点页面。
- 先结构化记忆，后全文记忆：长期保存配置与事实，不保存冗余上下文。
- 先统一语义层，后多渠道渲染：消息内容与渠道格式解耦。
