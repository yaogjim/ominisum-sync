#### Dagu

Dagu is a lightweight, self-contained alternative to Airflow or Cron with Web UI. It supports Linux / Mac / Windows. Define [DAGs](https://en.wikipedia.org/wiki/Directed_acyclic_graph) in a simple, declarative YAML format. It natively supports shell commands, Docker containers, Kubernetes Jobs, remote commands via SSH, external coding-agent CLIs through `harness.run`, and more through Dagu Actions.

It was designed to be easy to use, self-contained, and require no coding, making it ideal for small teams.

**Highlights:**

- Single binary file installation.
- Declarative YAML format for defining DAGs.
- Web UI for visually managing, retrying, and monitoring pipelines.
- Use existing scripts or tools without any modifications.
- Self-contained, with no need for a DBMS.
- Built-in MCP support for AI agents to manage workflows.
- Run external coding-agent CLIs through `harness.run` when workflows need AI assistance.

#### Performance

Dagu stores state in local files. How much it can run depends on the machine and the workload. CPU, memory, disk, workflow characteristics, queue settings, and worker capacity all matter.

- **Throughput:** On one machine, Dagu can run thousands of workflow runs per day when the hardware and workflow shape fit the workload.
- **Load control:** Use queues, concurrency limits, resource limits, and optional distributed workers to decide how many runs execute at once and where they run.

Use Case How Dagu Helps

ETL and data operations Turn data extraction scripts, SQL queries, dbt commands, and data-processing runbooks into observable pipelines with durable execution.

Cron and legacy script management Turn complex jobs with interdependencies into maintainable DAGs with a UI, automatic logging, retries, and notifications instead of opaque cron jobs and bash scripts.

Media conversion Run `ffmpeg` for video transcoding and format conversion. Thanks to Dagu's file-backed nature, workers can run heavy conversions in parallel without single machine bottlenecks or external databases.

Infrastructure and server automation Run any command or script over SSH on remote servers, keeping logs, results, and notifications in one place.

GitHub-driven workflows Trigger workflows from GitHub events. This is useful for running automation on private infrastructure without exposing your servers to the public internet.

Container and Kubernetes workflows Run Docker containers and Kubernetes Jobs as steps in your workflows without building a custom control plane around containers.

Customer support automation Run self-service support tools that non-engineering teams can use to run approved workflows for running diagnostics, querying databases, and performing common support tasks without escalating to engineering.

IoT and edge workflows Run sensor polling, local ML inference, data preprocessing, backups, offline sync, health checks, etc. Dagu keeps these jobs close to the data source while still providing Web UI visibility.

Model Server Execution Best for

**Local single-server** `dagu start-all` on one machine. Same machine. Development, small scheduled workloads, edge jobs, and simple internal automation.

**Self-hosted** Dagu server on your infrastructure. Local execution or distributed workers on your infrastructure. Teams that need ownership of infrastructure.

**Managed Server** Full managed Dagu server in a dedicated, isolated gVisor instance on GKE. Managed instance. Teams that want Dagu operated for them without running the server themselves.

**Hybrid** Full managed Dagu server. Private workers in your infrastructure over mTLS. Docker steps, private networks, specialized hardware, or data-local work.

#### Key Features

- **Observability:** Shared workflows and scheduling with clear visualizations, status tracking, and logs in the Web UI.
- **Language-agnostic:** No framework required. Define workflow steps using shell commands, Docker containers, Kubernetes Jobs, SQL queries, HTTP requests, and any other tool via official and third-party Dagu Actions.
- **Reproducibility:** Reproducible runs with pinned tools, plus automatic installation and caching on workers—eliminating the need to manually install dependencies on the server or workers.
- **Built-in Approvals:** The Human-in-the-loop steps for manual approvals, review, and intervention in any workflow.
- **MCP Server:** Built-in MCP server for authoring and running workflows via AI agents like Claude Code, Codex, Gemini CLI, Pi, OpenCode, and more.
- **External CLI Harness:** You can run coding-agent CLIs (Claude Code, Codex, Gemini CLI, Pi, OpenCode, etc.) with a built-in harness action or custom harness definition.
- **Secret management:** Built-in secret management with secure log masking, preventing credentials from leaking into logs or the Web UI.
- **Self-host or managed:** Self-hosted via a single binary that runs on Linux, macOS, and Windows. Includes an optional distributed worker mode for scaling out execution across machines.
- **Permission Control:** RBAC and SSO support for team environments, controlling who can view, run, and edit workflows through granular permissions and audit logging.

#### Architecture

Dagu can run in three configurations:

**Standalone:** A single `dagu start-all` process runs the HTTP server, scheduler, and executor. Suitable for single-machine deployments.

**Coordinator/Worker:** The scheduler enqueues jobs to a local file-based queue, then dispatches them to a coordinator over gRPC. Workers long-poll the coordinator for tasks, execute DAGs locally, and report status back. Workers can run on separate machines and are routed tasks based on labels.

**Headless:** Run without the web UI (`DAGU_HEADLESS=true`). Useful for CI/CD environments or when Dagu is managed through the CLI or API only.

```
Standalone:

  ┌─────────────────────────────────────────┐

  │  File-based storage (logs, state, queue)│
```

```
    description: Customer or account identifier

  - name: change_scope
    type: string
```

#### Custom Actions

Custom Actions are inline reusable wrappers defined with the top-level `actions` field. They expand to built-in actions during DAG load, so you can wrap a common shell, HTTP, SQL, or other pattern behind a typed interface with validated input.

See Custom Actions and the YAML Specification for the exact `actions`, `action`, and `run` field behavior.

Dagu Actions are official action packages maintained in the `dagucloud` GitHub organization. They use the same action package runtime as third-party action packages, but callers use the short form `action: name@version`.

Dagu Action Purpose

`node-script@v1` Run small JavaScript transforms or glue code with action-owned Node.js

`python-script@v1` Run small Python transforms or glue code with action-owned Python and optional requirements

`dbt@v1` Run dbt Core commands with action-owned Python and adapter requirements

`duckdb@v1` Run DuckDB SQL through the DuckDB CLI without adding DuckDB to the core binary

`ffmpeg@v1` Run FFmpeg conversion, transcoding, probing, and stream-processing tasks

`github-cli@v1` Run GitHub issue, pull request, release, repository, and API automation through `gh`

`rclone@v1` Run portable copy, sync, check, list, and storage-management workflows through rclone

Versions are required. Pin production workflows to a version tag or commit SHA. See Official Dagu Actions for the current Dagu Action list and exact input/output contracts.

For non-official packages, use Third-Party Actions such as `action: owner/repo@version`. They contain a `dagu-action.yaml` manifest and a DAG entrypoint, run as sub-DAGs, and are transferred to distributed workers as workspace bundles after the reference is resolved. See Third-Party Actions for package layout and reference formats.

##### Authentication

Dagu supports three top-level authentication modes, configured via `DAGU_AUTH_MODE`:

- **`none`** — No authentication
- **`basic`** — HTTP Basic authentication
- **`builtin`** — JWT-based authentication with user management, API keys, per-DAG webhook tokens, and optional OIDC/SSO integration

When using `builtin` auth, five roles control access:

Role Capabilities

`admin` Full access including user management

`manager` Create, edit, delete, run, stop DAGs; view audit logs

`developer` Create, edit, delete, run, stop DAGs

`operator` Run and stop DAGs only (no editing)

`viewer` Read-only access

API keys can be created with independent role assignments. Audit logging tracks all actions.

- TLS for the HTTP server (`DAGU_CERT_FILE`, `DAGU_KEY_FILE`)
- Mutual TLS for gRPC coordinator/worker communication (`DAGU_PEER_CERT_FILE`, `DAGU_PEER_KEY_FILE`, `DAGU_PEER_CLIENT_CA_FILE`)
- Secret management with three providers: environment variables, files, and [HashiCorp Vault](https://www.vaultproject.io/)

##### Production Hardening

For self-hosted production deployments, treat network exposure and execution boundaries as the primary controls:

- Prefer `auth.mode: builtin` for any shared or network-exposed instance. Use `basic` only for simple private setups, and avoid `none` outside isolated local development.
- Keep `metrics: private` unless the metrics endpoint is reachable only on a trusted private network.
- Bind Dagu to loopback or a private interface when possible. If you must use `0.0.0.0`, place it behind a trusted reverse proxy, TLS, and network-level access controls.
- Leave `terminal.enabled: false` unless the instance is admin-only and tightly scoped.
- In distributed deployments, set `peer.insecure=false` and configure peer TLS when coordinator and workers communicate across host or network boundaries.
- Treat Docker socket mounts, root containers, and host-level executors as privileged access to the underlying machine.

See Server Configuration, Docker deployment, and Distributed execution for the operator-focused guidance.

- `dagu_worker_info` — Worker heartbeat labels as key/value metadata
- `dagu_worker_heartbeat_timestamp_seconds` — Last worker heartbeat timestamp

##### Structured Logging

JSON or text format logging (`DAGU_LOG_FORMAT`). Logs are stored per-run with separate stdout/stderr capture per step.

##### Notifications

- Email notifications on DAG success, failure, or wait status via SMTP
- Per-DAG webhook endpoints with token authentication

#### Artifacts

Artifact browser in dark mode

Dagu runs can write arbitrary files into `DAG_RUN_ARTIFACTS_DIR`, and Dagu stores them per run as Artifacts. In the Web UI, operators can browse the file tree, preview Markdown, text, and image files inline, and download any artifact when they need the raw file.

This is useful for generated reports, screenshots, charts, exported JSON or CSV files, and other outputs that do not fit simple key/value outputs.

See the Artifacts documentation and the Web UI guide for the full artifact browser workflow and screenshots.

- **Cron scheduling** with timezone support and multiple schedule entries per DAG
- **Overlap policies**: `skip` (default — skip if previous run is still active), `all` (queue all), `latest` (keep only the most recent)
- **Catch-up scheduling**: Automatically runs missed intervals when the scheduler was down
- **Zombie detection**: Identifies and handles stalled DAG runs (configurable interval, default 45s)
- **Retry policies**: Per-step retry with configurable limits, intervals, and exit code filtering
- **Lifecycle hooks**: `onInit`, `onSuccess`, `onFailure`, `onAbort`, `onExit`, `onWait`
- **Preconditions**: Gate DAG or step execution on shell command results
- **High availability**: Scheduler lock with stale detection for failover

#### Distributed Execution

The coordinator/worker architecture distributes DAG execution across multiple machines:

- **Coordinator**: gRPC server that manages task distribution, worker registry, and health monitoring
- **Workers**: Connect to the coordinator, pull tasks from the queue, execute DAGs locally, report results
- **Worker labels**: Route DAGs to specific workers based on labels (e.g., `gpu=true`, `region=us-east-1`)
- **Health checks**: HTTP health endpoints on coordinator and workers for load balancer integration
- **Queue system**: File-based persistent queue with configurable concurrency limits

```

# Start workers (on separate machines)
DAGU_WORKER_LABELS=gpu=true,memory=64G dagu worker
```

#### Dagu：面向小团队的轻量级工作流引擎

##### 一句话总结

Dagu 是一个本地优先、单文件部署、无需数据库的工作流编排工具，可理解为**轻量版 Airflow + 可视化 Cron + AI Agent 工作流管理能力**，适合小团队、内部自动化、边缘计算和轻量数据任务。

---

##### 核心定位

Dagu 主要解决的是：  
**把零散脚本、定时任务、数据处理、运维命令、AI Agent 调用等，统一编排成可观测、可重试、可审批的 DAG 工作流。**

它强调：

- 单二进制文件安装
- YAML 声明式定义工作流
- 自带 Web UI
- 不依赖 PostgreSQL、Redis、RabbitMQ 等外部组件
- 支持本地、分布式 worker、托管服务等多种部署方式

---

##### 与 Airflow / Cron 的区别

###### 相比 Airflow

Airflow 通常需要 Web Server、Scheduler、Worker、PostgreSQL、Redis/RabbitMQ、Python Runtime 等多个组件，部署和维护成本较高。

Dagu 则更轻：

- 一个`dagu start-all`即可启动
- 状态、日志、队列都基于本地文件
- 更适合小团队和内部自动化场景
- 不要求写 Python DAG 代码

###### 相比 Cron

Cron 适合简单定时任务，但缺少依赖编排、日志、重试、审批、可视化和权限控制。

Dagu 可以把复杂 Cron 脚本升级为：

- 有依赖关系的 DAG
- 有运行状态和日志
- 支持失败重试
- 支持通知和人工审批
- 可通过 Web UI 管理

---

##### 主要能力

###### 1. 声明式工作流

使用 YAML 定义 DAG，例如：

```yaml
steps:
  - id: hello
    run: echo "hello from Dagu"
```

支持步骤依赖、并行执行、参数输入、失败重试、超时、定时调度、补偿处理等能力。

---

###### 2. Web UI 可视化管理

Dagu 提供可视化界面，用于：

- 查看 DAG 结构
- 查看运行状态
- 查看步骤日志
- 重试失败任务
- 浏览运行产物 artifacts
- 管理队列、远程节点、审计日志等

这让非工程团队也能更安全地运行内部自动化任务。

---

###### 3. 多类型任务执行

Dagu 不绑定某种语言或框架，支持多种执行方式：

- Shell / PowerShell 脚本
- Docker 容器
- Kubernetes Job
- SSH 远程命令
- HTTP 请求
- SQL 查询
- Redis 操作
- Python 脚本
- LLM Chat Completion
- 外部 AI 编码 Agent CLI

---

###### 4. AI Agent 集成

Dagu 内置 MCP Server，可让 Claude Code、Codex、Gemini CLI 等 AI Agent：

- 读取工作流状态
- 修改或预览 DAG 配置
- 启动、排队、重试、停止任务

同时支持通过`harness.run`调用外部 AI 编码工具，把 AI 审查、生成、修复等动作纳入自动化流程。

---

###### 5. 本地优先与无数据库架构

Dagu 将状态、日志、队列存储在本地文件中，不强依赖外部 DBMS。

优势是：

- 部署简单
- 运维成本低
- 适合边缘设备、私有环境、小团队
- 更容易自托管

但性能上也取决于机器配置、磁盘、并发设置和工作流复杂度。

#### Dagu 深度总结与解读

##### 一、深度总结

**Dagu 是一个轻量级、本地优先的工作流引擎**，定位在**Airflow 与 Cron 之间**：

> 比 Cron 更可视、更可靠；比 Airflow 更轻、更易部署。

它的核心特点是：

- **单二进制部署**：无需 PostgreSQL、Redis、RabbitMQ 等外部组件。
- **YAML 声明式定义 DAG**：不用写复杂框架代码。
- **自带 Web UI**：可查看流程图、日志、产物、运行状态，并支持重试、停止、审批。
- **本地文件存储状态**：日志、队列、运行状态都落在文件系统。
- **支持多种执行方式**：
  - Shell 命令
  - Docker 容器
  - Kubernetes Job
  - SSH 远程命令
  - SQL 查询
  - HTTP 请求
  - LLM / AI Agent 调用
- **内置 MCP Server**：AI Agent 可以读取、修改、执行工作流。
- **可单机，也可分布式 Worker 扩展**。
- **适合小团队、边缘设备、内部自动化、数据任务、脚本治理**。

一句话：

> Dagu 想把 “散落的脚本、Cron、运维命令、数据任务” 变成可视、可追踪、可重试、可审批的工作流。

---

##### 二、深入浅出解读

###### 1. 它解决什么问题？

很多团队都有这种情况：

```bash
每天跑几个脚本
定时执行一些数据同步
运维同学手动 SSH 上服务器执行命令
Cron 里塞满任务
失败了没人知道
日志散落各处
任务之间依赖关系不清楚
```

Dagu 做的事就是：

> 把这些 “黑盒脚本” 整理成 “白盒流程”。

例如：

```yaml
steps:
  - id: extract
    run: ./extract.sh

  - id: transform
    run: ./transform.sh
    depends: extract

  - id: load
    run: ./load.sh
    depends: transform
```

这表示：

```text
先抽取数据 → 再转换 → 最后加载
```

并且你可以在 Web UI 里看到：

- 哪一步成功
- 哪一步失败
- 失败日志是什么
- 是否重试
- 是否需要人工审批
- 输出文件在哪里

---

###### 2. 它和 Cron 的区别

| 对比 | Cron | Dagu |
|---|---|---|
| 定时执行 | 支持 | 支持 |
| 任务依赖 | 弱 | 强 |
| 可视化 | 无 | 有 |
| 日志管理 | 分散 | 集中 |
| 失败重试 | 需手写 | 内置 |
| 人工审批 | 无 | 支持 |
| 多步骤流程 | 麻烦 | 原生支持 |

Cron 像是一个闹钟。

Dagu 像是一个带看板、日志、审批、重试机制的任务调度中心。

---

###### 3. 它和 Airflow 的区别

| 对比 | Airflow | Dagu |
|---|---|---|
| 部署复杂度 | 高 | 低 |
| 依赖服务 | 多 | 几乎无 |
| 学习成本 | 高 | 低 |
| 适合规模 | 中大型数据平台 | 小团队 / 轻量自动化 |
| 工作流定义 | Python | YAML |
| 本地优先 | 弱 | 强 |

Airflow 更像大型工厂生产线。

Dagu 更像小团队的自动化控制台。

---

###### 4. 典型使用场景

Dagu 适合：

- 数据 ETL
- 替代复杂 Cron
- 运维自动化
- 定时备份
- 视频转码
- IoT / 边缘计算任务
- 内部工具平台
- 客服自助诊断流程
- GitHub 事件触发内部任务
- AI Agent 辅助执行代码审查、Issue 创建等流程

不太适合：

- 超大规模数据平台
- 极高吞吐调度系统
- 强事务型工作流
- 对数据库级一致性要求极高的场景

---

##### 三、核心价值

Dagu 的最大价值不是 “能跑命令”，而是：

> 让原本不可见、不可控、不可审计的自动化任务，变得可见、可控、可治理。

它补齐了脚本自动化中最缺的几个环节：

- **可观察性**
- **失败恢复**
- **依赖编排**
- **权限控制**
- **人工审批**
- **统一入口**
- **AI Agent 接入**

---

##### 四、辩证思考

###### 优点

1. **极简部署**
   - 单文件即可运行，降低运维门槛。

2. **非常实用**
   - 能直接复用已有脚本，不要求重写系统。

3. **本地优先**
   - 适合私有环境、边缘设备、内网任务。

4. **比 Cron 更工程化**
   - 有日志、UI、依赖、重试、审批。

5. **AI 友好**
   - 内置 MCP，顺应 AI Agent 管理工程系统的趋势。

---

###### 局限

1. **文件存储有边界**
   - 简单可靠，但在高并发、大规模、多租户场景下不如数据库架构稳健。

2. **生态不如 Airflow 成熟**
   - Airflow 在大数据生态、插件、社区经验上仍更强。

3. **YAML 适合简单流程，不适合复杂逻辑**
   - 流程太复杂时，YAML 可能变得难维护。

4. **AI Agent 接入有风险**
   - 让 AI 修改和执行工作流，需要严格权限、审计和审批机制。

---

##### 五、我的判断

Dagu 的定位很清晰：

> 它不是要取代 Airflow，而是要取代 “混乱的 Cron + 手写脚本 + 人肉运维”。

如果你是：

- 小团队
- 内部自动化较多
- 不想维护复杂调度系统
- 已有大量 Shell/Python/SQL/ 运维脚本
- 想快速获得 Web UI、日志、重试、审批能力

那么 Dagu 很值得尝试。

但如果你是：

- 大型数据平台
- 工作流数量巨大
- 强依赖复杂调度、元数据管理、数据血缘
- 需要成熟企业级生态

Airflow、Dagster、Argo Workflows 可能更合适。

---

##### 六、一句话结论

**Dagu 是一个 “轻量、实用、本地优先” 的工作流引擎，最适合把小团队的脚本、Cron 和运维流程升级成可视化、可治理的自动化系统。**

#### Dagu 项目精炼总结

Dagu 是一款面向小团队的**本地优先、轻量级工作流引擎**，可视为 Airflow 或 Cron 的简化替代方案。它通过声明式 YAML 定义 DAG，单个二进制即可运行，无需数据库，并提供 Web UI、分布式执行和 AI Agent 管理能力。

##### 1. 核心定位与亮点

- 支持 **Linux、macOS、Windows**，可通过单个二进制文件部署。
- 使用简单的 YAML 定义任务、依赖关系、调度和重试，无需编写特定框架代码。
- 自带 Web UI，可查看任务状态与日志，并进行重试、停止和人工审批。
- 状态、日志和任务队列默认保存在本地文件中，**无需 PostgreSQL、Redis、RabbitMQ 等外部服务**。
- 可直接复用现有脚本和工具，无需改造。
- 原生支持：
  - Shell 命令与脚本
  - Docker 容器
  - Kubernetes Job
  - SSH 远程命令
  - SQL、HTTP 请求及第三方 Dagu Actions
  - 通过 `harness.run` 调用 Codex、Claude Code、Gemini CLI 等编程 Agent
- 内置 MCP Server，允许 AI Agent 读取状态、修改工作流和控制运行。

相比传统编排系统可能需要维护 Web Server、Scheduler、Worker、PostgreSQL、Redis/RabbitMQ、Python Runtime 等 **6 个以上组件**，Dagu 可通过一个 `dagu start-all` 进程提供主要能力。

##### 2. 性能与负载控制

Dagu 使用本地文件保存状态，实际性能取决于 CPU、内存、磁盘、工作流类型、队列设置和 Worker 数量。

- 在硬件和任务结构合适时，单机每天可运行**数千次工作流**。
- 可通过以下机制控制负载：
  - 队列
  - 并发限制
  - 资源限制
  - 分布式 Worker
  - Worker 标签路由

它更强调轻量部署和可控扩展，而不是依赖复杂的外部基础设施。

##### 3. 主要应用场景

###### 数据与 ETL

可将数据抽取脚本、SQL、dbt 命令和数据处理流程组合成可观察、可重试的流水线。

###### Cron 与旧脚本改造

把存在依赖关系的 Cron 或 Bash 任务转为 DAG，并获得：

- Web UI
- 自动日志
- 失败重试
- 通知
- 运行状态追踪

###### 媒体转换

可并行运行 `ffmpeg` 等重型转码任务。借助分布式 Worker，可避免所有处理都集中在单机上。

###### 基础设施自动化

通过 SSH 在远程服务器运行部署、诊断和维护命令，并集中保存日志与结果。

###### GitHub 驱动的自动化

可由 GitHub 事件触发私有基础设施中的任务，而不必把内部服务器直接暴露到公网。

###### 容器与 Kubernetes

可将 Docker 容器和 Kubernetes Job 直接作为工作流步骤，无需自行构建容器控制平台。

###### 客服、IoT 与边缘计算

- 为非工程团队提供经过审批的诊断、数据库查询和支持工具。
- 在靠近数据源的位置执行传感器采集、本地 ML 推理、预处理、备份、离线同步和健康检查。

##### 4. 快速安装与运行

Dagu 支持脚本、Homebrew、Docker 和 Helm 等安装方式。

```bash
# macOS / Linux
curl -fsSL https://raw.githubusercontent.com/dagucloud/dagu/main/scripts/installer.sh | bash

# Homebrew
brew install dagu

# Docker
docker run --rm \
  -v ~/.dagu:/var/lib/dagu \
  -p 8080:8080 \
  ghcr.io/dagucloud/dagu:latest dagu start-all
```

Kubernetes 可使用 Helm 安装，但持久化存储需要支持 **ReadWriteMany（RWX）** 的 StorageClass。

最简单的工作流 `hello.yaml`：

```yaml
steps:
  - id: hello
    run: echo "hello from Dagu"
```

运行方式：

```bash
dagu start hello.yaml
dagu start-all
```

随后访问：

```text
http://localhost:8080
```

脚本安装器还可通过向导完成 PATH 配置、后台服务安装和初始管理员账号创建；Homebrew、Docker、Helm 等方式默认不包含该向导。

##### 5. AI Agent 与 MCP 支持

Dagu 运行后会通过 HTTP 服务暴露内置 MCP 端点：

```text
http://localhost:8080/mcp
```

支持 MCP 的聊天或编程 Agent 可以通过以下工具管理工作流：

- `dagu_read`：读取 DAG、运行状态和相关信息。
- `dagu_change`：预览或应用工作流修改。
- `dagu_execute`：启动、入队、重试或停止任务。

如果仅需要 AI 辅助编写工作流，可为 Claude Code、Codex、Gemini CLI 等安装 Dagu 编写技能：

```bash
gh skill install dagucloud/dagu dagu
```

此外，`harness.run` 可在工作流内部直接调用编程 Agent。例如先让 Codex 审查 README，将结果保存为文件；再等待人工审批；审批通过后自动创建 GitHub Issue。

##### 6. 部署模式

Dagu 支持从单机到混合部署的多种模式：

| 模式 | 服务位置 | 任务执行位置 | 适用场景 |
|---|---|---|---|
| 本地单机 | 一台机器运行 `dagu start-all` | 同一台机器 | 开发、小规模定时任务、边缘任务 |
| 自托管 | 用户自己的基础设施 | 本机或私有分布式 Worker | 需要完全掌控基础设施的团队 |
| 托管服务 | 运行于 GKE 上隔离的 gVisor 实例 | 托管实例 | 不希望自行维护服务器的团队 |
| 混合模式 | Dagu 托管服务 | 用户私有网络中的 Worker，通过 mTLS 连接 | 私有网络、专用硬件、数据本地化、Docker 任务 |

托管实例不会开放 Docker daemon 或 Docker socket。需要运行 Docker 步骤时，应使用自托管部署，或连接具有 Docker 权限的私有 Worker。

##### 7. 许可与团队能力

- **社区自托管版**：无需许可证密钥，但服务器、存储、网络、升级和 Worker 均由用户维护。
- **自托管商业许可证**：增加 SSO、RBAC、审计日志和事件 SaaS 集成。
- **Dagu 托管实例**：自带托管许可证，也可连接用户基础设施中的私有 Worker。

##### 8. 关键功能

- **可观察性**：Web UI 提供调度、状态、日志和流程可视化。
- **语言无关**：可运行 Shell、容器、Kubernetes Job、SQL、HTTP 及其他工具。
- **可复现运行**：可固定工具版本，并在 Worker 上自动安装和缓存依赖。
- **人工审批**：在流程中加入暂停、审核和人工干预节点。
- **密钥管理**：内置 Secret 管理和日志脱敏，避免凭据泄漏。
- **横向扩展**：单机运行，也可通过分布式 Worker 扩展到多台机器。
- **权限管理**：商业能力包括细粒度 RBAC、SSO 和审计日志。
- **Dagu Actions**：以结构化方式复用官方或第三方动作。
- **Agent 集成**：既能通过 MCP 让 AI 管理 DAG，也能在步骤中运行外部编程 Agent。

##### 9. 三种运行架构

###### 独立模式

一个 `dagu start-all` 进程同时运行：

- HTTP Server / Web UI
- Scheduler
- Executor
- 基于文件的日志、状态和队列

适合单机和小型部署。

###### Coordinator / Worker 模式

1. Scheduler 将任务写入本地文件队列。
2. 任务通过 gRPC 分发到 Coordinator。
3. Worker 长轮询 Coordinator 获取任务。
4. Worker 在本地执行 DAG，并回报状态、心跳和日志。
5. 可根据 Worker 标签，将任务路由到指定机器。

适合多机器执行、专用硬件或私有网络场景。

###### Headless 模式

设置：

```text
DAGU_HEADLESS=true
```

即可在无 Web UI 的情况下运行，适用于 CI/CD，或仅通过 CLI/API 管理的环境。

##### 10. 参数化工作流

Dagu 可定义带类型的参数，并在 Web UI 中自动生成输入表单。参数也可作为环境变量传递给步骤。

例如：

```yaml
params:
  - name: customer_id
    type: string
    description: Customer or account identifier

  - name: change_scope
    type: string
    enum:
      - metadata_only
      - permissions
      - full_account
    default: metadata_only

  - name: dry_run
    type: boolean
    default: true
```

这适合制作面向运营、客服等非工程人员的安全自助工具，例如限制修复范围并默认启用“仅演练”模式。

##### 11. 工作流示例与执行能力

###### 并行执行

```yaml
steps:
  - id: extract
    run: ./extract.sh

  - id: transform_a
    run: ./transform_a.sh
    depends: extract

  - id: transform_b
    run: ./transform_b.sh
    depends: extract

  - id: load
    run: ./load.sh
    depends: [transform_a, transform_b]
```

其中 `transform_a` 和 `transform_b` 会在 `extract` 完成后并行运行，最后由 `load` 汇总。

###### 自动重试

```yaml
retry_policy:
  limit: 3
  interval_sec: 30
```

表示失败后最多重试 **3 次**，每次间隔 **30 秒**。

###### 工具自动安装与缓存

```yaml
tools:
  - jqlang/jq@jq-1.7.1
```

Dagu 会在 DAG 运行前安装指定版本的可移植 CLI，将其加入 `PATH`，并在各 Worker 上缓存；默认通过 aqua 提供工具安装能力。

###### Docker、Kubernetes 与 SSH

```yaml
# Docker
container:
  image: node:20-alpine
run: npm run build
```

```yaml
# Kubernetes Job
action: kubernetes.run
with:
  namespace: production
  image: my-registry/batch-processor:latest
  resources:
    requests:
      cpu: "2"
      memory: "4Gi"
```

```yaml
# SSH 部署
action: ssh.run
with:
  host: prod-server.example.com
  user: deploy
  command: cd /var/www && git pull && systemctl restart app
```

###### 子 DAG 组合

复杂流程可拆成 `extract`、`transform`、`load` 等子 DAG，再通过 `dag.run` 组合，并将上一步输出传给下一步，以提升复用性和可维护性。

###### 调度与故障处理

```yaml
schedule:
  - "0 */6 * * *"

overlap_policy: skip
catchup_window: "5h"
timeout_sec: 3600
```

该配置表示：

- 每 **6 小时**执行一次。
- 若上一次仍在运行，则跳过新任务。
- 调度器中断后，可补跑 **5 小时**内错过的任务。
- 单次执行最长 **3600 秒**。

还可配置失败通知和退出清理，例如失败时执行 `notify-team.sh`，任务结束时执行 `cleanup.sh`。

##### 12. 内置 Actions

Dagu 将简单 Shell 命令放在 `run:` 中，结构化能力放在 `action:` 中。主要内置动作包括：

| Action | 用途 |
|---|---|
| `run:` | 执行 Bash、Shell、PowerShell 或自定义脚本 |
| `exec` | 不经 Shell 解析，直接执行进程 |
| `noop` | 作为输出或人工审批占位步骤 |
| `log.write` | 写入结构化日志 |
| `docker.run` / `container.run` | 运行容器，支持认证、挂载和资源限制 |
| `kubernetes.run` / `k8s.run` | 执行 Kubernetes Job |
| `ssh.run` | 通过 SSH 执行远程命令 |
| `sftp.upload` / `sftp.download` | 通过 SFTP 传输文件 |
| `http.request` | 发起带认证、请求头和请求体的 HTTP 请求 |
| `chat.completion` | 执行大模型对话补全 |
| `harness.run` | 运行 Claude Code、Codex、Copilot、OpenCode、Pi 等 Agent CLI |
| `postgres.query/import` | 查询或导入 PostgreSQL 数据 |
| `sqlite.query/import` | 查询或导入 SQLite 数据 |
| `redis.&lt;operation>` | 执行 Redis 操作 |

##### 总结

Dagu 的主要优势是以**单文件部署、声明式 YAML、本地文件存储和 Web UI**，为现有脚本增加调度、依赖、重试、审批、日志和监控能力。它尤其适合不想维护 Airflow 式复杂基础设施的小团队，同时也能通过分布式 Worker、MCP 和 Agent Harness 扩展到多机执行及 AI 驱动的自动化场景。
