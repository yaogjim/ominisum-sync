### 陈成: Anthropic 刚发了一篇彻底改变我对 PM 认知的文章

https://x.com/chenchengpro/status/2036042821917082103

**陈成**

Anthropic 刚发了一篇彻底改变我对 PM 认知的文章。

她用一个细节开场：从 2024 年 10 月到今天，她一直用同一个任务测试每个新模型——让 Claude Code 给 Excalidraw 加个表格工具。每个版本都走得更远一点，但都失败了。直到 Opus 4.6，终于可以在数千人面前现场演示。

这个细节说明的不是模型进步，而是一个更根本的问题：

传统 PM 假设项目开始时能做什么，项目结束时大体还是能做什么。这个假设已经死了。

"你为之设计的技术约束，可能在项目进行到一半时直接消失。你是在一块不断上升的地基上建造。"

───

她总结了四个具体转变，每一条都在颠覆我过去理解的「正确做法」：

1\. 支线任务 &gt; 锁死的路线图

别再写 PRD 然后交给工程师执行了。Claude Code 最受欢迎的几个功能——Desktop、AskUserQuestion 工具、Todo 列表——全都不是从路线图里出来的，是团队成员自己开的「支线任务」跑出来的。

2\. Demo + Eval &gt; 文档

原型下午就能搭出来，站会变成了 Demo 分享会，有真实使用的才打磨上线。押错注的成本极低——错了就扔，对了就冲。

3\. 每个新模型都重新审视已有功能

更好的模型是重新打开旧功能的信号。他们就这样发现了 Claude Code + Chrome 集成：用户在手动复制粘贴，说明这个动作本身该被原生支持。

4\. 做能用的最简单方案

为当前模型局限性设计的 workaround，会在下一个版本变成负债。他们曾经在系统提示里插入定期提醒让 agent 更新 Todo 列表——下一个模型直接原生支持了，这段代码就删掉了。系统提示随着每次模型升级持续缩减，Opus 4.6 又减了 20%。

───

数据层面有多夸张？

METR 测量：Sonnet 3.5 能处理人类 21 分钟的任务。Opus 4.6 能处理人类近 12 小时的任务。

16 个月，提升了 41 倍。

───

最后一段话我觉得是这篇文章真正的核心：

习惯于掌控完整产品体验的 PM，必须放弃完美主义才能跟上技术的速度。新的工作是：识别真正不可妥协的少数几件事，然后放开其余的。

这不是在说 PM 要「学会用 AI 工具」。这是在说 PM 这个角色的底层逻辑需要重写：不再是流程的所有者，而是少数关键判断的守门人。

执行力可以被无限供给的时候，判断力才是真正稀缺的。

自 2024 年 10 月 [Claude Sonnet 3.5 (new)](https://www.anthropic.com/news/3-5-models-and-computer-use) 以来，我养成了一个习惯，即通过让 Claude Code（当时的一个内部工具）为 Excalidraw 添加表格工具来测试每一个新模型。每一个新模型出现时，Claude 都取得了一些进展，但仍然失败了。

然后，随着 [Opus 4](https://www.anthropic.com/news/claude-4) 在 2025 年 6 月的发布，Claude 开始偶尔取得成功，以至于我们将这个练习转化为一个 [预先录制的演示](https://www.youtube.com/live/EvtPBaaykdo?t=3478s) ，用于 Claude 4 模型的发布，以展示使用我们最新模型后已经成为可能的成果。

不到一年后， [Opus 4.6](https://www.anthropic.com/news/claude-opus-4-6) 能够一次性处理 Excalidraw 的功能请求，其可靠性足以让我们有信心在数千名专业开发者面前现场进行。

模型进展的速度不断拓展着可能性的边界。传统产品管理指南基于这样的假设：项目开始时技术上可行的内容，在项目结束时大致也是可行的。产品经理会提前收集足够的信息，对未来做出有把握的判断，然后在数月内按计划执行。

指数级改进的模型打破了这一假设。你围绕其设计的约束条件可能会在项目中途消失。你正在建造的地基正在你脚下不断升高，团队需要围绕这一现实进行重组。新的产品管理节奏是快速实验、持续交付以及加倍投入有效做法。

不足为奇的是，作为 Anthropic 的一名产品经理，我最常被问到的问题之一是我们的角色正在如何变化。以下是我所了解到的。

#### 我与 Claude Code 的产品管理之旅

我职业生涯起步于在 Scale AI 和 Dagster 等初创公司担任产品工程师，之后成为一名风险投资家。在这个角色中，我仍然编写代码来自动化工作中繁琐的部分，比如扫描 X 以获取新公司的公告，或检测开源项目何时获得发展势头。

我于 2024 年 8 月加入 Anthropic，担任 Research PM 团队的产品经理，该团队连接了我们的研究团队和真实客户，以提供更好的模型。那年秋天，当 Claude Code 在内部可用时，我使用它来加速工作中较为手动的部分，包括构建 Streamlit 应用程序来分析大规模用户反馈，以及运行评估以帮助公司找到值得信赖的新基准。较低的构建门槛也意味着我可以探索远超常规职责范围的工作，例如创建强化学习环境以更好地理解模型训练。

这些项目花费了数百小时提示由 Sonnet 3.5（新）驱动的 Claude Code，但没有一行代码是手动编写的。

#### 设计一个新的产品管理工作流程

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/69bc295c981804a6cc75ded9_fig1-claude-code-pm-playbook-on-the-ai-exponential-v4%402x.png)

像 Claude Code 和 Cowork 这样的工具正在模糊产品开发生命周期中不同角色之间的界限。

Claude Code 并不是唯一支持我工作流程的工具。随着时间的推移，我在三个产品之间形成了一种自然的分工：聊天协作工具（ [Claude.ai](http://claude.ai/redirect/claudedotcom.v1.7c6d69ad-128c-4cf1-ba83-cf9fd056f718) ）、智能编码工具（Claude Code）和知识工作工具（ [Cowork](https://www.anthropic.com/webinars/future-of-ai-at-work-introducing-cowork) ）。

**Claude.ai** 是我与 Claude 交流的地方，我将其视为思维伙伴，无需让它采取行动。我会就战略文档交流想法、探讨如何处理棘手情况，并获得快速答案。

**Claude Code** 是我构建原型、评估和脚本的地方，其中很多都调用了 Claude API。当输出为代码时，我会使用这个工具。

**Cowork** 是我处理其他所有事情的地方，从实现收件箱清零、跟踪并执行待办事项列表、制作演示文稿，到通过搜索 Slack 了解决策的历史，以及预订工作行程。

我与全行业的产品经理交谈过，他们都找到了这种工作流程的自己版本

> *“Claude 提升了优秀产品团队的构建上限，并大幅缩短了从想法到原型的距离。过去，要让客户看到实际可用的产品需要数周的构建时间。现在，我会在 Claude Cowork 中开始工作，从 Slack、我们的代码库和文档中引入上下文，然后进入 Claude Code，在几个小时内就能得到一个可演示的产品。优秀的产品团队一直都在用真实客户测试他们的想法，而这种直觉并没有改变。改变的是，我们现在能够通过这个流程推进的高质量想法的数量大大增加了。”——Decagon 产品总监蒋碧涵*

> *对我而言，在 AI 原生世界中担任产品经理既富有创造性又兼具学术性。每一次新的模型发布都会改变可能性的边界，而在构建 Datadog 的 Bits AI SRE 代理时，我们通过对真实生产环境事件的离线评估来研究其优势和失败模式。我们还设计紧密的反馈循环，优化用户体验以揭示代理的不足之处，并将这些见解转化为产品改进。从这个意义上说，产品经理的工作重心已从预先定义确定性转变为加速探索发现。 ——Kai Xin Tai，Datadog 高级产品经理*

如今作为产品经理最令人兴奋的部分之一是，这些工作流程正在不断演进，为我们提供了更多优势。

#### 拥抱 AI 的指数增长

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/69bc2f892ac8ae5b32d2ac32_Screenshot%202026-03-19%20at%201.16.39%E2%80%AFPM.png)

METR.（2026 年 3 月）. 前沿 AI 模型的任务完成时间范围. https://metr.org/time-horizons/

METR [发现](https://metr.org/time-horizons/) that, 大约一半的时间里，Opus 4.6 能够完成需要人类几乎 12 小时才能完成的软件任务。当我们最初开始构建 Claude Code 时，Sonnet 3.5（新）是前沿模型，METR 衡量发现它能够完成需要人类大约 21 分钟的任务。这在 16 个月内大约实现了 41 倍的提升。

Claude Code 团队不断发展以跟上模型改进的速度。我们的角色正在融合：设计师交付代码，工程师做出产品决策，产品经理构建原型和评估。这种模式之所以有效，是因为清晰的策略和目标让每个人都能自主确定优先级。产品经理的工作是在快速模型进展带来的模糊性中创造清晰度，推动团队更深入地思考可能的方向，并为更快交付扫清道路。

以下是我们所接受的四个转变：

**Plan in short sprints**

传统产品经理思维将探索视为在路线图确定之前发生的事情。你进行调研，撰写 PRD，并将其移交给工程团队进行构建。

与其制定长期路线图，我们鼓励团队中的每个人（工程师、产品经理、设计师）接受支线任务。支线任务是你在正式路线图之外开展的简短自主实验——比如用一个下午制作某个想法的原型、测试一项你认为无法实现的功能，或者只是看看当你比预期更用力地推动模型时会发生什么。

Anthropic 最受欢迎的一些功能—— [Claude 代码桌面版](https://code.claude.com/docs/en/desktop) 、 [询问用户问题工具](https://platform.claude.com/docs/en/agent-sdk/user-input) 和 [待办事项列表](https://platform.claude.com/docs/en/agent-sdk/todo-tracking) ——以这种方式出现。

**鼓励演示和评估而非文档**

我们团队已在很大程度上用以原型为先导的思维方式取代了以文档为先导的思维方式。我们不再举办传统的站会，而是分享新想法的演示。内部用户试用这些演示，那些获得实际参与度的演示会得到优化完善，并在更广泛范围内分享。因为你可以在一个下午就完成原型制作，所以错误的尝试成本很低。

例如，当 Noah 与 Claude Code 分享他的 [插件](https://code.claude.com/docs/en/plugins) 规范时，返回的原型接近生产就绪状态。该原型为团队最终交付的产品奠定了基础，因为它使团队能够快速验证用户体验。

专业提示：编写规范后，将其发送给 Claude Code，看它是否能构建。即使是一个粗略的原型也能改变讨论。

除了演示之外，评估还可以帮助让抽象的产品变得更具体。例如，对于 [代理团队](https://code.claude.com/docs/en/agent-teams) （它允许用户协调多个 Claude Code 实例协同工作），Conner 精心设计了一套评估方法，以了解代理团队何时表现良好、何时不佳，以及需要修复什么问题。衡量该功能是否有效，能让改进变得更容易。

**使用新模型重新审视功能**

现在，你发布了一个功能，然后更好的模型发布，你的功能可能会大幅改善。每次模型发布都是一个隐含的提示，促使你重新审视你已经构建的内容。

捕捉这些时刻的最佳方式是成为每日活跃用户，并刻意要求它完成你认为可能太难的任务。有时这会成功，而这是一个信号，表明产品需要迎头赶上。

这就是 [Claude Code with Chrome](https://code.claude.com/docs/en/chrome) 这一功能的由来。我们注意到用户使用 Claude Code 构建 Web 应用，然后手动切换到 Chrome 中的 Claude 进行测试。用户需要在这两个工具之间手动提示并复制粘贴指令。这种方式效果足够好，因此我们意识到这应该成为一个内置功能。如果用户在快速拼凑某些内容，那就是你可以构建到产品中的脚手架。

在设计这些想法的原型时，始终优先优化能力。使用比你认为需要的更多的 token。过早削减 token 成本并因此推出功能弱得多的产品是一个常见错误。随着更便宜的模型赶上，你之后总能降低成本，但首先你需要知道该功能是否可行。

**Do the simple thing**

在 Anthropic，我们在每个团队中都有一个指导原则：做简单且有效的事情。

如果你的产品巧妙地绕开了模型的限制，那么当下一个模型推出时，这种变通方法就会变成不必要的复杂性。这就是为什么“做简单的事”很重要：实现方式越简单，当新能力出现时，就越容易整合新能力。

当我们最初在 Claude Code 中推出待办事项列表时，模型无法可靠地在完成项目时勾选它们。因此，我们每隔几条消息就添加了系统提醒，这些提醒会定期促使代理更新自己的待办事项列表。这确实有效，但这是一个权宜之计。随着下一个模型的推出，这种行为变得原生支持，我们完全移除了提醒。我们多次看到这种模式：我们的系统提示和工具描述过去需要大量设计来弥补模型的局限性，而随着每个模型的推出，我们都能够减少提示词的使用，包括 Opus 4.6 减少了 20%。

#### Looking forward

许多产品经理习惯了对整个产品体验进行严格掌控，但 AI 却迫使你放手，以便快速推进。尤其是在构建 AI 产品时，感觉就像驾驭浪潮，最重要的是保持在浪上。作为一名完美主义者，这种转变对我来说是最难适应的，但如今产品经理的角色主要是识别出少数真正不可妥协的关键点，而放手其他部分。

这些转变的净效应是，产品团队能够显著加快工作速度。当产品经理能在一下午内从想法推进到可运行原型时，“如果我们尝试……”与“来，试试这个”之间的差距几乎消失了。

在 Anthropic，产品经理不再是唯一借助 Claude 转变工作流程的人。我们的数据科学、 [财务](https://www.anthropic.com/webinars/claude-code-financial-services) 、市场营销、 [法务](https://www.youtube.com/watch?v=tJP6SKfo49c) 以及 [设计团队](https://www.youtube.com/watch?v=vLIDHi-1PVU) 都自主掌握了这些工具。整个组织以同样的速度推进，而不是等待交接。

产品经理的角色现在需要同时跟踪两件事：AI 如何改变你的工作方式，以及它如何改变你的产品中可能实现的内容。做好这一点，当表格工具终于正常工作时，你就不会再感到惊讶了。你就是那个预见了这一切的人。

#### AI 时代 PM 的底层逻辑正在重写

你给出的两部分内容，核心其实在讲同一件事：

**在 AI 能力快速跃迁的背景下，产品经理（PM）的工作重心，已经从“提前规划并控制执行”，转向“快速试验、持续校准、抓住少数关键判断”。**

Anthropic 的文章提供了第一手方法论，陈成的转述则把这种变化提炼成更易传播的认知框架。两者合在一起，可以总结为一句话：

> **当执行越来越便宜、越来越自动化，真正稀缺的就不再是推动流程的能力，而是判断什么值得做、何时做、做到什么程度的能力。**

#### 一、综合总结

##### 1. 文章的主旨

Anthropic 通过 Claude Code 的产品实践提出：  
AI 模型的能力不是线性提升，而是以很快的速度扩张边界，导致传统 PM 的前提失效。

传统 PM 默认：
- 项目开始时能做什么，结束时大致也只能做这些
- 可以先调研、写 PRD、定路线图，再按月推进
- 产品体验可以被较稳定地设计和控制

但在 AI 时代，这些假设都被打破了：
- 模型能力可能在项目进行到一半时突然跃升
- 原本“不可做”的东西，几个月后就变成“能直接做”
- 为旧能力设计的 workaround，很快会变成系统负债

所以新的 PM 方式不是“先想清楚再执行”，而是：
- 用更短周期做实验
- 用 demo 和 eval 替代大量文档
- 在每次新模型发布后，重新审视旧功能
- 尽量用最简单的实现，避免为暂时的局限设计过度复杂方案

---

##### 2. 两份内容共同强调的四个转变

###### ① 支线任务比僵硬路线图更重要
Anthropic 发现很多受欢迎功能，不是来自正式 roadmap，而是来自团队成员自发的短平快实验。

这意味着：
- roadmap 不再是唯一创新来源
- 真正有价值的功能，很多是“试出来”的
- PM 的职责之一，是创造一个允许支线探索的环境

---

###### ② Demo 和 Eval 比文档更重要
因为原型成本显著降低，团队可以在一下午做出可演示版本。  
于是讨论不再围绕“文档里写了什么”，而是围绕“这个东西跑起来效果如何”。

这带来两个变化：
- 决策更依赖真实反馈，而不是纸面推演
- 试错成本更低，押错的代价也更低

---

###### ③ 每次模型升级，都是一次产品重做机会
过去发布功能后，更多是优化细节；现在每个新模型版本都可能直接改变产品边界。

这意味着：
- PM 不能把功能发布当作终点
- 必须持续做重判：这个功能现在能不能更原生、更流畅、更自动？
- 用户手动拼接的流程，往往预示着未来应该内建的功能

---

###### ④ 最简单的可用方案，往往是最优方案
针对模型缺陷做很多复杂补丁，短期看是“优化”，长期看可能是负债。

Anthropic 的经验是：
- 下一个模型可能天然支持你现在靠提示词、规则、流程硬补出来的能力
- 因此设计应尽量轻、薄、简单
- 让系统更容易随着模型进化而升级

---

##### 3. 最核心的结论

这篇内容真正重要的不是“PM 要学 AI 工具”，而是：

> **PM 角色本身的底层逻辑变了。**

过去 PM 更像：
- 流程组织者
- 需求定义者
- 跨团队协调中心
- 体验控制者

现在 PM 更像：
- 机会发现者
- 快速实验推动者
- 少数关键标准的守门人
- 在高速变化中持续校准方向的人

换句话说：

**执行正在被 AI 极大放大，判断成为新的瓶颈。**

---

#### 二、深入浅出解读

##### 1. 为什么说“传统 PM 假设已经死了”？

因为传统产品管理依赖一个隐含前提：

> 技术能力在一个项目周期内相对稳定。

比如以前做一个功能，大家会先评估：
- 技术能不能做
- 成本多高
- 需要几个月
- 体验能做到什么水平

然后形成一个相对稳定的计划。

但 AI 时代不一样。  
模型能力可能在 3 个月内出现明显跃升。于是会发生这种情况：

- 你今天觉得必须人工处理的环节
- 3 个月后模型可以直接做
- 你今天觉得只能半自动的流程
- 下个版本可能就能端到端完成

所以问题不再只是“怎么规划”，而是：

> **你规划时依赖的技术约束，可能很快就不存在了。**

这就是文章里那句很形象的话：  
**你是在一块不断上升的地基上建造。**

---

##### 2. 为什么“文档让位于 Demo”是必然的？

因为 AI 把“从想法到原型”的距离缩短了。

以前写文档很重要，是因为：
- 原型很贵
- 工程资源稀缺
- 一个错误方向可能浪费几周甚至几个月

所以必须先论证、先写清楚、先对齐。

但现在如果一个原型下午就能做出来，那么最有效的沟通方式自然变成：
- 别争论
- 先做个能跑的出来看

这不是说文档没用了，而是说：
- 文档不再是最主要的决策载体
- Demo 和真实使用反馈，信息密度更高

你可以把它理解为：

**过去靠“描述产品”推进产品，  
现在更多靠“展示产品”推进产品。**

---

##### 3. 为什么“支线任务”会变得特别重要？

因为在高速变化的技术环境里，很多真正的新机会，不会自然出现在原有 roadmap 里。

路线图本质上是基于“已知世界”的规划。  
但 AI 正在不断扩大“未知世界”的边界。

所以如果团队只按 roadmap 做事，就容易错过这些突然出现的新可能。

支线任务的价值在于：
- 它允许个体快速验证一个模糊想法
- 它不要求先形成完整共识
- 它适合捕捉“刚刚变得可行”的能力跃迁

这有点像科研或创业中的“探索性试验”：
- 很多会失败
- 但少数一旦成功，价值非常大

所以新的 PM，不只是管理主线任务，  
还要让团队保持足够高的“探索带宽”。

---

##### 4. 为什么“简单方案”比“精巧方案”更适合 AI 产品？

因为 AI 产品的底层能力本身在快速变。

如果你为了弥补模型不足，设计了很多：
- 特殊规则
- 复杂提示词
- 额外流程
- 人工兜底逻辑
- 系统级 workaround

短期看像是在提高成功率，长期看可能是在给未来埋雷。

文章里的 Todo 例子就很典型：
- 旧模型不能稳定更新待办事项
- 团队只好加系统提醒，定期催 agent 更新
- 下一代模型出来后，这个能力原生就有了
- 之前那套补丁式设计立刻变成冗余

所以“做简单的事”不是偷懒，而是一种**适应高速进化环境的架构策略**。

本质上是在说：

> **不要把今天模型的缺点，固化成产品的永久结构。**

---

##### 5. PM 为什么会从“掌控一切”转向“守住少数关键点”？

因为 AI 让很多执行环节的产能暴增了。

当原型、脚本、评估、界面、流程自动化都能被 AI 大量生成时，PM 已经不可能也没必要像过去那样：
- 逐项定义每个细节
- 完整控制所有流程
- 对所有体验做精细预设

否则只会拖慢节奏。

更现实的做法是：
- 明确什么是绝对不能错的
- 对这些关键点严格把关
- 其他部分允许快速试、快速改

这些“不能错的关键点”通常包括：
- 产品方向是否正确
- 用户价值是否真实
- 核心体验是否可信
- 风险边界是否清楚
- 成本与收益是否合理

也就是说，PM 从“全面管理者”转向“关键判断者”。

---

#### 三、这篇内容对普通人的启发

##### 1. 对 PM 的启发
如果你是 PM，这篇文章最重要的提醒不是去学某个工具，而是改变工作方式：

- 少做超长期、过细的确定性规划
- 多做短周期试验和快速验证
- 用 demo 获取共识，而不是靠文档争论
- 每次模型升级后，重新看旧功能
- 对 workaround 保持警惕，避免堆积负债
- 把精力集中在高价值判断，而不是流程维护

---

##### 2. 对工程师的启发
工程师也不再只是“接需求的人”：
- 可以直接参与产品探索
- 可以通过原型成为需求发现者
- 可以更主动地提出用户体验改进
- 会写代码之外，“会借 AI 做实验”变得越来越重要

这也对应评论里提到的一个趋势：  
未来面试可能会更看重候选人的 **vibe coding 能力**，即能否在 AI 协作中快速把想法落到可验证的成果上。

---

##### 3. 对团队管理者的启发
管理者需要重构团队机制：
- 给成员留出支线探索空间
- 用更轻的流程支持更快试错
- 建立 demo culture 和 eval culture
- 接受某些方案是暂时性的
- 不要过早把组织流程固化得过重

否则团队会被旧流程拖住，而不是被新能力放大。

---

##### 4. 对所有知识工作者的启发
文章最后还提到，Anthropic 内部不只是 PM，数据科学、财务、营销、法务、设计都在自己掌握这些工具。

这说明一个更大的趋势：

> AI 不只是某个岗位的效率工具，而是在重构整个组织的分工方式。

过去很多工作依赖交接：
- 想法交给工程
- 分析交给数据
- 素材交给设计
- 资料交给运营

现在越来越多的人可以先自己做出一个可运行、可展示、可验证的版本。  
这会让组织协作从“层层交接”变成“人人先推进一段”。

---

#### 四、这篇文章最值得记住的 5 句话

- **技术约束可能会在项目中途消失。**
- **路线图不再是创新的唯一来源，支线任务同样关键。**
- **Demo 和 Eval 比长文档更能推动真实决策。**
- **每次模型升级，都值得重新审视旧功能。**
- **当执行力被无限供给，判断力才是最稀缺的能力。**

---

#### 五、一句话结论

**这不是“PM 如何使用 AI”的文章，而是“AI 如何重新定义 PM” 的文章。**

如果说过去优秀 PM 的核心能力是：
- 规划
- 协调
- 推进
- 控制

那么在 AI 时代，优秀 PM 的核心能力会越来越变成：
- 判断
- 试验
- 取舍
- 校准

也就是从“管理流程的人”，变成“在高速变化中持续做对关键决定的人”。
