## 正文

**Frad**

分享一个这两天折腾下来，价值 $73.76 的网络优化 prompt：

\# 角色  
你是一名远程网络维护助手。现在有一位"现场配合人"(下称"对方")坐在路由器旁、具备登录路由器后台的条件。你的工作是:先取得路由器的 SSH 访问权限,然后尽量自助地完成网络监控、异常分析与验证,只在 SSH 拿不到的地方才请对方配合。

\# 核心工作原则(优先级,从高到低)  
1\. 最优先:取得路由器的 SSH 访问权限。  
2\. 拿到 SSH 后,凡是能通过 SSH(只读地)获取的信息与监控,都由你自己完成,不要让对方手动翻菜单、逐条回贴。  
3\. 只有 SSH 确实拿不到的信息或操作,才请对方配合。把对对方的打扰降到最低。  
4\. 遇事先查最新资料:不要依赖本提示词里写死的指标或命令。需要具体的判定特征、诊断方法或处置方案时,先做 web search 获取最新信息,再据此行动并给出方案。  
5\. 凡结论与改动必有验证(eval):网络问题关键,不能凭"感觉好了",一切都要用可量化的数据闭环证明。

\# 两条铁律(任何时候都不得违背)  
1\. 优先自助、最小打扰:能用 SSH 自己拿到的,就自己拿;不要无谓地让对方代劳。  
2\. 不擅自改动:任何会修改配置、重启、断网、隔离设备、清理文件,或有破坏性/会影响他人的操作,都必须先把"要做什么、风险、如何回滚"讲清楚,得到对方明确同意后,才执行或指导对方执行。只读的诊断命令可以自己在 SSH 里跑。

\# 关于网络信息(本提示词不预置任何拓扑)  
\- 本提示词不包含任何具体网络信息(IP/网段、网关、设备型号、MAC、运营商、公网地址、端口规划等),这些都在运行时通过 SSH 自行发现。  
\- 运行时发现的敏感细节(地址、型号、凭据等)不要在对话中无谓地大段公开,够用即可。

\# 阶段一:取得 SSH 访问权限(最优先)  
本阶段即"辅助对方开启路由器访问权限",由对方在后台亲手开启,你负责指导:  
1\. 指导对方在路由器管理后台开启 SSH 服务。  
2\. 请对方提供连接所需信息(主机地址、端口、用户名)与凭据;更推荐:让对方把你的公钥加入,改用密钥登录而非明文密码。  
3\. 确认你能成功 SSH 登录,具备只读诊断所需权限即可开展工作。  
4\. 协助对方为 SSH 做基本安全加固(强密码或仅密钥、限制来源等)。  
5\. 涉及后台开关的开启/设置,由对方亲手点击;你只负责说明位置与步骤。

\# 阶段二:监控网络、分析异常问题(基于 SSH 自助进行)  
目标:通过网络分析,发现并定位网络中的各类异常。异常分两类,都要覆盖:  
\- 流量 / 安全类:异常流量与外联、未知或可疑设备、异常连接行为等。  
\- 性能 / 体验类:延迟、抖动、丢包、卡顿、网页打不开、网速不达标等。很多性能问题根因隐蔽,用户自己几乎想不到,常规测速工具(如 Speedtest)也测不出来——你的价值正是不靠猜、分层逐项地系统排除。

不要依赖写死的指标或命令——判定特征与诊断 / 处置方法会随时间和场景变化。正确做法:  
1\. 先通过 SSH 确认路由器的系统 / 固件与可用工具,决定你能用哪些命令。  
2\. 针对当前情况先做 web search 获取最新信息:可用的只读诊断工具、各类异常的识别方法与特征,以及排查中遇到的任何陌生域名 / IP / 进程 / 端口 / 设备,逐个查证其归属与风险。  
3\. 用查到的方法,通过 SSH 只读地采集多维数据:在线设备、各设备流量、活动连接(conntrack)、DNS 查询、防火墙 / 系统日志、接口与链路状态、延迟 / 丢包 / 抖动、无线环境等。  
4\. 分层、逐项排除,定位根因:  
\- 按链路分层缩小范围:本机 → Wi-Fi / 无线层 → 主路由器 / 有线层 → 上级 / 光猫 → 公网,逐层判断问题出在哪一层,不漏项、不靠猜。  
\- 对每个怀疑点做针对性、可复现的测量,而不是只看一次综合测速。下面是容易被忽视、用户自己根本想不到的隐蔽根因举例(仅举例,具体方法先 web search 当前做法):  
· Wi-Fi 信道 / 同频干扰:带宽看着正常,但 ping 网关几十毫秒且死活降不下来;换信道 / 频宽后可能直接降到个位数。需看无线环境、邻居占用、信号与协商速率,并在空闲 / 满载下分别测网关延迟与抖动。  
· Bufferbloat(缓冲膨胀):上传或下载打满时延迟暴涨、网页都打不开,而单独跑 Speedtest 完全正常。需用"负载下延迟"(latency under load)的方法测,而非普通测速。  
\- 同时建立"正常基线",把明显偏离基线的挑出来(异常高 / 低流量、陌生外联、未知设备、可疑域名或端口、异常延迟丢包、反复重连或报错等),定位到具体的设备 / 连接 / 进程 / 链路。  
5\. 给出解决方案:先 web search 该问题的最新处置 / 优化 / 整流 / 换信道 / 加固做法,整理成方案;涉及改动的部分按铁律 2 先讲清并征得同意,再执行或指导对方执行。

\# 阶段三:验证与评估(eval —— 网络问题关键,必做闭环)  
网络问题影响面大、回退成本高,任何结论与改动都必须有可量化验证,不能凭"感觉好了":  
1\. 改动前先定义成功标准:把"修好"翻译成可测量指标并写下来(例如负载下网关延迟 / 抖动低于某值、丢包为 0、可疑外联消失、目标设备流量回归正常、上传打满时网页仍能打开等)。  
2\. 留底基线:用与后续完全一致的方法、相同负载与时段,先测一组"改动前"数据。  
3\. 执行改动:按铁律 2 征得同意,并提前备好回退方案;优先选可逆、影响最小的改动,尽量在低峰时段操作。  
4\. 同条件复测"改动后",与基线对比;同时检查其他层 / 其他指标有没有变差(确认无回归)。  
5\. 判定:  
\- 达标且无回归 → 视为解决;再持续观察一段时间确认稳定(不要只看改动那一刻),并把最终状态 / 配置记录下来。  
\- 未达标或出现回归 → 立刻按铁律 2 回退到改动前,带着新数据重新分析、换方案,再走一轮排查—改动—验证。  
6\. 每一项独立改动都单独验证,避免多个改动同时上、分不清是谁起的作用。

\# 仅在这些情形请对方配合(SSH 拿不到的部分)  
\- 独立设备的后台:Wi-Fi AP、光猫 / 上级设备等有各自管理界面、从主路由器 SSH 看不到的,请对方登录那些设备查看。  
\- 需要物理查看的:线缆、指示灯、设备铭牌型号、设备是否真的在线等。  
\- 终端设备本机检查:电脑 / 手机 / IoT / 摄像头等设备上的本地排查与清理。  
\- 需要在后台点击开启或关闭的开关(SSH 只读不改的部分),由对方亲手操作。

\# 收尾再次强调  
\- 再次:优先用 SSH 自助获取信息与监控,只有 SSH 拿不到的才请对方配合,尽量少打扰对方。  
\- 再次:不擅自做任何改动——改配置、重启、断网、隔离、清理都要先讲清并经对方同意;只读诊断可自行进行。  
\- 再次:很多问题根因隐蔽、常规测速测不出,要分层、逐项系统排除,不靠猜、不漏项;遇到具体特征或方法先 web search 最新资料再给方案。  
\- 再次:每个结论与改动都要做 eval —— 先定可量化标准、测基线、改完同条件复测对比、确认达标且无回归再收尾,否则回退重来。  
\- 目标顺序:先拿到 SSH 访问权限 → 网络分析定位根因 → 改动 → eval 验证闭环。

##### 一、总结

这篇内容分享了一个“网络优化/排障 Agent Prompt”，核心目标是：

> 让 AI 像远程网络维护工程师一样，通过 SSH 自助诊断路由器和网络问题，尽量少麻烦现场人员，并且所有改动都必须验证闭环。

它主要做了三件事：

1. **先拿 SSH 权限**
   - 让现场人员开启 SSH。
   - AI 通过 SSH 自己查看路由器状态。
   - 尽量不用人工截图、翻菜单。

2. **基于 SSH 做网络诊断**
   - 查设备、流量、连接、DNS、日志、延迟、丢包、Wi-Fi 干扰等。
   - 覆盖两类问题：
     - 安全类：可疑设备、异常外联、异常流量。
     - 性能类：卡顿、延迟、丢包、Bufferbloat、Wi-Fi 干扰。

3. **所有结论都要验证**
   - 改动前先测基线。
   - 改动后同条件复测。
   - 有问题就回滚。
   - 不靠“感觉好了”。

---

##### 二、通俗解读

这个 prompt 的本质是：

> 把 AI 从“聊天建议者”，变成“远程网络排障助手”。

它最重要的几个设计点：

###### 1. 先拿 SSH，是为了减少人工成本

普通排障经常是：

> “你点这里、截图给我、再点那里、再发我看看……”

非常低效。

有了 SSH 后，AI 可以自己查：

- 哪些设备在线
- 谁占用流量
- 有没有异常连接
- 路由器日志有没有报错
- Wi-Fi 是否拥堵
- 延迟和丢包在哪一层出现

这就是“让 AI 自己干活”。

---

###### 2. “只读诊断”很关键

它强调：

> 能看就先看，不要一上来就改。

因为网络设备很敏感，随便改可能导致：

- 断网
- 设备掉线
- 配置丢失
- 家人/公司其他人受影响

所以它规定：

- 查日志、看状态、测延迟：可以直接做。
- 改配置、重启、隔离设备：必须先说明风险，并获得同意。

这点很专业。

---

###### 3. 不只看 Speedtest

很多网络问题，测速是看不出来的。

比如：

- **Bufferbloat**
  - 平时测速很快。
  - 但一上传文件，网页就打不开。
  - 问题是“满载时延迟暴涨”。

- **Wi-Fi 干扰**
  - 宽带没问题。
  - 但无线信道太挤，ping 网关都很高。
  - 换信道可能立刻改善。

所以这个 prompt 要求：

> 分层排查，不靠猜。

从：

```text
终端设备 → Wi-Fi → 路由器 → 光猫 → 运营商 → 公网
```

一层层定位问题。

---

###### 4. eval 验证闭环是亮点

它不是“改完觉得好了就结束”，而是要求：

```text
定义目标 → 测改动前 → 改动 → 测改动后 → 对比 → 不行就回滚
```

这让 AI 的排障更像工程实践，而不是随口建议。

---

##### 三、我的意见

这个 prompt 的价值不在于“命令写得多”，而在于它定义了一个好的工作流程。

我认为它最有价值的地方是：

1. **目标清晰**
   - 先 SSH，再诊断，再修改，再验证。

2. **边界明确**
   - 只读可以自助。
   - 破坏性操作必须授权。

3. **强调验证**
   - 网络问题不能凭感觉，要靠数据。

4. **适合 Agent 化**
   - 如果接入 SSH、日志分析、测速工具、知识搜索，就能变成真正可用的网络维护 Agent。

但也有一个前提：

> 这个 prompt 适合有工具权限的 AI Agent，不适合普通只聊天的 AI。

如果 AI 不能真的 SSH、不能执行命令、不能持续监控，那它只能给建议，不能真正“维护网络”。

这是一个把 AI 网络排障流程工程化的 prompt：  
**先拿权限，自助诊断，谨慎改动，数据验证。**

## 结构化（1）

##### 主旨概括

这篇内容分享了一个“远程网络维护助手”的 Prompt，核心价值是让 AI Agent 像专业网络工程师一样，通过 **优先获取 SSH 权限、尽量自助诊断、谨慎改动、量化验证** 的流程，系统排查网络问题。  
它强调：网络优化不能靠感觉，也不能一上来乱改配置，而要用数据、分层排查和验证闭环来解决问题。

---

##### 1. 角色设定：AI 是远程网络维护助手

文章中的 Prompt 设定 AI 的角色是：

- 一名远程网络维护助手；
- 现场有一位“现场配合人”，坐在路由器旁边；
- 现场人员可以登录路由器后台，但 AI 的目标是尽量减少对方操作；
- AI 首要任务是取得路由器的 **SSH 访问权限**；
- 拿到 SSH 后，尽量通过 SSH 自己完成监控、分析和验证。

简单来说：  
**现场人员只负责必要的开关和授权，AI 负责真正的排查和分析。**

---

##### 2. 核心原则：先拿 SSH，少打扰人，不乱改配置

Prompt 里明确了几个优先级：

1. **最优先取得 SSH 权限**  
   只有拿到 SSH，AI 才能高效读取路由器状态、日志、连接、流量等信息。

2. **能自己查就自己查**  
   拿到 SSH 后，所有只读信息都由 AI 自己获取，不让现场人员手动翻菜单、截图、复制数据。

3. **只有 SSH 查不到时才请人配合**  
   例如光猫、AP、终端设备、线缆、指示灯等，需要现场或其他后台才能确认。

4. **遇到具体问题先查最新资料**  
   不依赖固定命令或过时经验，遇到陌生 IP、域名、进程、端口、设备型号时，先 web search 查证。

5. **所有结论和改动必须验证**  
   网络问题不能靠“感觉好多了”，必须用数据证明。

---

##### 3. 两条铁律：自助诊断 + 不擅自改动

文章特别强调两条不能违反的规则：

###### 3.1 优先自助，最小打扰

如果能通过 SSH 自己拿到信息，就不要让现场人员代劳。  
比如：

- 在线设备列表；
- 活动连接；
- DNS 查询；
- 系统日志；
- 防火墙日志；
- 接口状态；
- 延迟、丢包、抖动数据。

这些都应该尽量由 AI 通过 SSH 自己查看。

###### 3.2 不擅自改动

任何可能影响网络的操作，都必须先说明并征得同意，包括：

- 修改配置；
- 重启设备；
- 断网；
- 隔离设备；
- 清理文件；
- 调整防火墙；
- 改 Wi-Fi 信道；
- 开关服务。

执行前必须说明：

- 要做什么；
- 有什么风险；
- 如何回滚；
- 是否会影响其他人。

只有只读诊断命令可以直接运行。

---

##### 4. 阶段一：先取得 SSH 访问权限

第一阶段是让现场人员配合开启 SSH。

主要步骤包括：

1. 指导对方进入路由器管理后台，开启 SSH 服务；
2. 让对方提供连接信息：
   - 主机地址；
   - 端口；
   - 用户名；
   - 登录凭据；
3. 更推荐使用 **公钥登录**，而不是明文密码；
4. 确认 AI 能成功 SSH 登录；
5. 做基本安全加固，例如：
   - 强密码；
   - 仅允许密钥登录；
   - 限制来源 IP；
6. 后台里的开关或设置由现场人员亲自点击，AI 只负责指导。

这一阶段的目标很明确：  
**先建立安全、可用、尽量只读的远程诊断入口。**

---

##### 5. 阶段二：通过 SSH 监控网络并分析异常

拿到 SSH 后，AI 开始自助分析网络问题。文章把异常分成两大类。

###### 5.1 流量 / 安全类异常

包括：

- 异常流量；
- 可疑外联；
- 未知设备；
- 异常连接行为；
- 可疑域名或端口；
- 不明进程；
- 异常 DNS 查询。

例如：  
如果某个摄像头突然大量连接陌生海外 IP，AI 应该通过连接记录、DNS 日志、设备信息等判断它是否异常。

###### 5.2 性能 / 体验类异常

包括：

- 延迟高；
- 抖动大；
- 丢包；
- 卡顿；
- 网页打不开；
- 网速不达标；
- 满速测试正常但实际体验差。

文章特别指出，很多网络问题很隐蔽，用户自己想不到，普通 Speedtest 也测不出来。

---

##### 6. 排查方法：分层定位，不靠猜

Prompt 要求 AI 按网络链路逐层排查：

1. 本机；
2. Wi-Fi / 无线层；
3. 主路由器 / 有线层；
4. 上级设备 / 光猫；
5. 公网。

每一层都要有可复现的测量，而不是只跑一次测速。

###### 例子一：Wi-Fi 信道或同频干扰

表现可能是：

- 带宽看起来正常；
- 但 ping 网关几十毫秒；
- 延迟怎么都降不下来。

可能原因是：

- Wi-Fi 信道拥堵；
- 邻居网络干扰；
- 频宽设置不合理；
- 信号质量差；
- 协商速率异常。

处理思路是：

- 查看无线环境；
- 观察邻居信道占用；
- 测空闲和满载时的网关延迟；
- 必要时调整信道或频宽；
- 调整后再复测。

###### 例子二：Bufferbloat，缓冲膨胀

表现可能是：

- 单独跑 Speedtest 很正常；
- 但上传或下载一打满，网页就打不开；
- 延迟突然暴涨。

文章强调，这种问题不能只看普通测速，而要测试：

- 负载下延迟；
- 满上传时的延迟；
- 满下载时的延迟；
- 抖动和丢包。

也就是看网络在压力下是否仍然稳定。

---

##### 7. 诊断时要建立“正常基线”

AI 不只是找异常，还要建立当前网络的正常基线。

需要关注的偏离包括：

- 某台设备流量异常高或异常低；
- 出现陌生外联；
- 出现未知设备；
- 访问可疑域名；
- 连接异常端口；
- 延迟或丢包异常；
- 设备反复重连；
- 系统日志频繁报错。

通过这些数据，AI 要把问题定位到具体的：

- 设备；
- 连接；
- 进程；
- 链路；
- 配置项。

---

##### 8. 阶段三：所有改动必须做 eval 验证闭环

文章最强调的一点是：  
**网络问题必须可量化验证，不能凭感觉收尾。**

完整流程包括：

###### 8.1 改动前定义成功标准

先把“修好”变成具体指标，例如：

- 负载下网关延迟低于某个值；
- 抖动低于某个值；
- 丢包为 0；
- 可疑外联消失；
- 某设备流量恢复正常；
- 上传打满时网页仍能打开。

###### 8.2 改动前留基线

用相同方法、相同负载、相同时段，先测一组改动前数据。

###### 8.3 执行改动

执行前要：

- 征得对方同意；
- 说明风险；
- 准备回退方案；
- 优先选择可逆、影响小的操作；
- 尽量在低峰时段执行。

###### 8.4 改动后同条件复测

改动后要用相同条件再测一次，对比前后数据。

同时还要确认：

- 其他指标没有变差；
- 没有引入新的问题；
- 没有影响其他设备。

###### 8.5 根据结果判断

如果达标且无回归：

- 视为解决；
- 持续观察一段时间；
- 记录最终状态和配置。

如果未达标或出现新问题：

- 立即回退；
- 带着新数据重新分析；
- 换方案再验证。

文章还强调：  
**每一项独立改动都要单独验证，不要一次改很多项，否则无法判断到底是哪一项起作用。**

---

##### 9. 什么时候才需要现场人员配合？

只有 SSH 拿不到的信息或操作，才请现场人员参与。

包括：

- 独立设备后台，例如 AP、光猫、上级路由；
- 物理检查，例如线缆、指示灯、铭牌型号；
- 终端设备本机检查，例如电脑、手机、摄像头；
- 后台开关操作，例如开启或关闭某些服务；
- 需要人工确认设备是否真的在线。

核心原则仍然是：  
**能远程自助就不打扰人，必须人工参与时才请对方做。**

---

##### 10. 热门回复中的观点

文章下方有几条值得注意的评论：

- 有人提到 Karpathy 式 agent loop 的方向是对的，但如果每个 agent 都单独循环，每轮都从零开始，无法积累经验；共享记忆可能是让多个 agent 形成复利系统的关键。
- 有评论认为，“只读诊断”这个约束非常重要，因为网络 agent 最怕一上来就改配置。
- 也有人调侃这个 Prompt 写得很长，但核心确实是在规范 AI 的排障流程。

其中一条评论总结得比较到位：  
**先跑基线、负载下延迟和回退条件，再排障，才像真正的网络诊断。**

---

##### 总结

这篇文章本质上不是单纯分享一个网络优化技巧，而是给 AI Agent 设计了一套完整的网络维护工作流：

1. 先取得 SSH 权限；
2. 尽量自助读取数据；
3. 分层排查网络问题；
4. 遇到问题先查最新资料；
5. 不经同意不做改动；
6. 每个结论和改动都要用数据验证；
7. 最后形成可回滚、可复现、可量化的闭环。

它的核心价值在于：  
**让 AI 不只是“帮忙看网络”，而是按照专业工程化流程完成远程网络诊断与优化。**

```md
3. 说明改动内容、风险和回滚方式；
4. 获得明确授权；
5. 执行单一改动；
6. 同条件复测；
7. 对比前后结果；
8. 判断是否达标；
9. 不达标则回退；
10. 记录最终状态。
```

---

###### 3.7 输出格式

可以要求 Agent 每轮输出：

```md
## 当前阶段
正在做什么。

## 已知事实
基于数据确认的信息。

## 待验证假设
按照可能性排序。

## 下一步只读操作
准备采集什么。

## 需要你配合的事项
如果没有，就写“暂无”。

## 风险动作
如有改动，列出风险和回滚方式。

## 验证标准
如何判断是否有效。
```

##### 4. 反方与张力：这条 Prompt 也有潜在问题

###### 4.1 Prompt 太长，不一定代表更强

热门回复里有人说“你写得多，你赢了”，这是一个真实张力。

长 Prompt 的问题：

- 模型可能抓不住重点；
- 执行时容易漏规则；
- 成本高；
- 对简单问题显得笨重；
- 不同模型遵循能力不同；
- 实际工具权限不一定支持。

所以它更适合高风险、复杂、需要多轮操作的任务。  
如果只是简单查一个配置，可能不需要这么重。

更好的做法是拆成：

- 系统级原则；
- 阶段性 Playbook；
- 当前任务上下文；
- 工具权限说明；
- 输出格式。

---

###### 4.2 “先 web search 最新资料”有利也有弊

优点：

- 避免命令过时；
- 适配不同设备；
- 可以查陌生域名、进程、端口；
- 能跟上最新安全风险。

缺点：

- 搜索结果可能不可靠；
- 可能引入噪音；
- 可能过度依赖网页；
- 排障效率变低；
- 网络不通时无法搜索；
- 搜索资料和设备实际固件不匹配。

更稳的方式是：

> 先识别本地系统和可用工具，再搜索与该设备、固件版本高度匹配的资料。

---

###### 4.3 SSH 权限本身就是风险

Prompt 把“获取 SSH”放在最高优先级，是合理的，但也存在风险：

- 凭据泄露；
- 暴露管理端口；
- 弱密码；
- 错误开放公网 SSH；
- Agent 误操作；
- 日志中出现敏感信息；
- 权限过高。

因此实际落地时需要加上安全约束：

- 优先密钥登录；
- 临时账号；
- 最小权限；
- 限制来源 IP；
- 禁止公网暴露；
- 任务完成后关闭或撤销权限；
- 不在对话里明文展示敏感信息。

---

###### 4.4 “只读诊断”也不一定完全无害

有些只读命令也可能带来风险：

- 高频采样造成性能压力；
- 扫描命令触发安全设备；
- 抓包可能采集隐私数据；
- 查询日志可能暴露敏感信息；
- 大量 conntrack 查询可能影响低端路由器性能。

所以“只读”不等于“零风险”。

更准确的原则是：

> 默认只读、低频、低负载、最小必要采集。

---

###### 4.5 Agent 的执行能力取决于工具，而不是 Prompt 本身

这条 Prompt 想象的是一个可以：

- SSH；
- 执行命令；
- 搜索网页；
- 分析日志；
- 记录基线；
- 对比结果；
- 与用户协作；

的 Agent。

如果模型只有聊天能力，没有真实工具调用，那它只能指导用户，不能自助完成。

因此产品实现里，Prompt 只是其中一部分，还需要：

- SSH 工具；
- 命令执行沙箱；
- 凭据管理；
- 日志解析；
- 长期记忆；
- 权限控制；
- 审批流程；
- 结果评估模块。

这也呼应热门回复中提到的 Shared Memory：

> 单个 Agent 每次循环都从零开始，只有共享记忆和历史基线，系统才会复利。

##### 5. 情境化落地：如何把这套方法用于 AI / 产品开发 / 商业系统构建？

###### 5.1 用在 DevOps Agent

目标：让 Agent 远程排查线上故障。

可改写为：

```md
你是一名远程 DevOps 维护助手。
第一优先级是取得只读观测权限，包括日志、监控、trace、配置快照和部署历史。
能通过系统自助获取的信息，不要让工程师手动复制。
任何重启、回滚、扩容、改配置、删数据操作，都必须先说明风险、影响范围和回滚方式，并获得明确同意。
所有结论必须通过指标验证，包括错误率、延迟、吞吐、资源占用和用户影响范围。
```

适用场景：

- 服务 500 错误；
- 接口变慢；
- 数据库连接池爆满；
- 内存泄漏；
- 发布后异常；
- 第三方 API 故障。

核心 Eval：

- P95/P99 延迟；
- 错误率；
- CPU/内存；
- 请求成功率；
- 队列积压；
- 用户投诉量。

---

###### 5.2 用在产品增长 Agent

目标：让 Agent 分析转化率下降。

结构类似：

1. 先接入数据源；
2. 不要让运营手动截图；
3. 分层分析漏斗；
4. 找异常 cohort；
5. 提出假设；
6. 小流量实验；
7. 指标验证。

示例：

```md
你是一名增长分析助手。
优先接入埋点、广告平台、订单系统和用户行为数据。
不要让用户手动导出截图，能查询的数据自行查询。
按照曝光、点击、注册、激活、留存、付费分层定位。
任何改预算、改投放、改价格、改页面的动作，都必须先说明预期收益、风险和回滚方式。
每次实验必须定义成功指标和护栏指标。
```

成功标准：

- 注册转化率提升；
- CAC 不上升；
- 留存不下降；
- 支付成功率不下降；
- 投诉率不升高。

---

###### 5.3 用在客服 Agent

目标：减少人工客服反复问用户信息。

传统客服 Agent 经常问：

- 你的订单号是多少？
- 你什么时候买的？
- 你遇到什么问题？
- 截图发一下？
- 再试试？

更好的设计是：

> Agent 先接入订单、物流、支付、售后、历史对话，再决定是否问用户。

可迁移原则：

```md
你是一名客服排障助手。
优先通过系统查询订单、物流、支付、库存、用户历史反馈。
不要让用户重复提供系统已经知道的信息。
只有系统查不到、需要用户确认或需要物理状态的信息，才询问用户。
涉及退款、补偿、取消订单、修改地址等动作，必须说明影响并获得确认。
每次处理后验证用户问题是否解决，并记录原因分类。
```

---

###### 5.4 用在数据分析 Agent

目标：让 Agent 自动分析业务异常。

```md
你是一名业务数据分析助手。
优先接入数据库、BI、埋点系统和历史报表。
先建立正常基线，再识别异常。
不要直接给结论，先拆解维度：时间、渠道、地区、用户类型、设备、版本、活动、价格。
任何写库、改口径、刷新生产报表的动作，都必须获得授权。
每个结论都要给出支持数据和可复现查询方式。
```

适用场景：

- GMV 下滑；
- 留存变差；
- 退款率升高；
- 新用户减少；
- 某渠道 ROI 异常；
- 某版本崩溃率升高。

---

###### 5.5 用在个人知识管理 Agent

目标：让 Agent 不只是聊天，而是维护个人信息系统。

```md
你是一名个人知识系统维护助手。
优先读取已有笔记、任务、日历、邮件和项目记录。
不要让我重复描述你已经能查到的信息。
只读分析可以自行进行。
涉及删除、归档、发送邮件、改日程、创建公开内容的动作，必须先确认。
每次整理后要验证：是否减少重复、是否保留来源、是否能被检索。
```

这类 Agent 的关键不是“总结能力”，而是：

- 有记忆；
- 有索引；
- 有权限边界；
- 有可回滚操作；
- 有持续改进。

---

##### 6. 最值得抽象出的产品公式

这条 Prompt 可以抽象成一个通用 Agent 公式：

```md
高价值 Agent = 
稳定上下文入口
+ 最小打扰的人机协作
+ 只读优先的安全边界
+ 分层诊断方法
+ 动作前授权
+ 可量化 Eval
+ 变更后回滚机制
+ 长期记忆与基线沉淀
```

或者更简化：

> 接入环境 → 自助观察 → 分层定位 → 小步改动 → 量化验证 → 记录沉淀。

---

##### 7. 对 AI 产品开发者的直接启发

如果你正在做 AI Agent 产品，可以重点思考这几个问题：

1. 你的 Agent 有没有真实数据入口，还是只靠用户口述？
2. 它能不能自助观察环境，而不是不断让用户截图？
3. 它的默认权限是只读，还是一上来就能乱改？
4. 它知道什么时候必须请求人类授权吗？
5. 它是否有明确的分层排障方法？
6. 它是否每次行动都有成功标准？
7. 它是否会建立改动前基线？
8. 它是否能同条件复测？
9. 它是否有回滚方案？
10. 它是否能把这次经验沉淀为下次的共享记忆？

如果答案大多是否定的，那么你的 Agent 可能还只是一个“会说话的界面”。  
如果答案大多是肯定的，它才开始接近“可托付的工作系统”。
