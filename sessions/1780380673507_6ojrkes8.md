##### 一、总结

这篇内容讲的是：

> 让 Codex 回顾你过去的使用记录，找出你反复让 AI 做的事情，并把它们沉淀成 **Skill** 或 **Subagent**。

常见重复任务包括：

- CI 报错排查
- PR Review
- 写 Changelog
- Debug
- 文档更新
- 发布准备
- 测试失败分类

核心 Prompt：

```text
Look through my recent Codex sessions and identify repeated workflows or repeated asks.
For anything I keep doing manually, suggest:
1. a skill if it is a reusable workflow
2. a custom subagent if it is a bounded role or investigation task

Focus on practical things like CI failures, PR reviews, changelogs, docs updates, release prep, debugging, and test triage.
Create the useful ones only. Keep them simple.
```

---

##### 二、解读

###### 1. 本质：把重复提问变成工具

很多开发者每天都在重复问 AI：

> “这个 CI 为什么挂了？”  
> “帮我看下 PR。”  
> “帮我写 changelog。”

这些其实不是一次性问题，而是**重复工作流**。

如果每次都重新描述，就会：

- 浪费时间
- 浪费 token
- 输出不稳定
- 难以积累经验

所以更好的方式是：  
把高频任务整理成固定的 **Skill** 或 **Subagent**。

---

###### 2. Skill 和 Subagent 的区别

| 类型 | 适合什么 | 关键词 |
|---|---|---|
| Skill | 固定流程、可复用操作 | 怎么做 |
| Subagent | 明确角色、单一任务 | 谁来做 |

简单理解：

- **Skill**：像 SOP，例如“CI 排查流程”
- **Subagent**：像专员，例如“测试失败分析员”

例子：

```text
CI 失败排查 → Skill
PR 审查员 → Subagent
发布前检查流程 → Skill
Bug 调查员 → Subagent
```

---

###### 3. 这个 Prompt 好在哪里

它有几个很实用的设计点：

- **基于真实历史**：不是凭空生成，而是看最近会话
- **强制分类**：必须判断是 Skill 还是 Subagent
- **聚焦高频场景**：CI、PR、文档、发布、调试等
- **限制产出数量**：只做有用的，保持简单

这能避免 AI 乱生成一堆“看起来高级、实际没用”的东西。

---

##### 三、我的意见

这个思路很有价值。

因为 AI 编程助手真正的效率提升，不只是“回答一次问题”，而是：

> 把你的重复工作习惯，逐步固化成可复用能力。

但我建议别一上来就搞复杂 Agent 系统。

更实际的做法是：

1. 先让 Codex 总结高频任务
2. 选 3 个最常用的
3. 做成简单 Skill
4. 用一段时间再优化

优先沉淀这些：

- CI 失败排查
- PR Review
- Changelog 生成
- Bug 调查
- Release Checklist

一句话：

> 不要让 AI 每次重新理解你；要让 AI 慢慢学会你的工作方式。

##### 主旨概括

这篇内容介绍了一个提升 Codex 使用效率的方法：让 Codex 回顾你过去的会话，找出反复出现的任务，并把它们沉淀成可复用的 **Skills** 或 **Subagent**。核心思想是：不要每次都重复写类似 prompt，而是把高频工作流抽象出来，提升一致性、减少 token 浪费。

---

##### 1. 开发者常见问题：重复提问本质上是未抽象的工作流

很多开发者在使用 AI 编程助手时，会反复提出类似请求，例如：

- “CI 为什么挂了？”
- “帮我 review 这个 PR”
- “写一下 changelog”
- “追踪这个 bug”
- “清理这个 diff”

这些看似普通的 prompt，其实往往代表着固定的工作流程。  
如果每次都手动重新描述，不仅浪费 token，也容易导致输出风格和质量不稳定。

---

##### 2. 解决思路：把重复任务沉淀成 Skills 或 Subagent

文章建议让 Codex 查看你最近的会话历史，识别那些反复出现的工作模式，并判断它们适合沉淀成哪一类能力：

###### Skills：适合“可复用工作流”

适用于多步骤、有固定流程的任务，重点是“怎么做”。

例如：

- CI 故障排查流程
- PR review 标准流程
- changelog 生成流程
- release prep 发布准备流程

###### Subagent：适合“边界清晰的角色或调查任务”

适用于单一职责、可委派的任务，重点是“谁来做”。

例如：

- 专门负责调查测试失败原因的 agent
- 专门做文档更新检查的 agent
- 专门分析某类 bug 的 agent

简单理解：

> Skill 更像“标准操作流程”；Subagent 更像“专门负责某件事的虚拟同事”。

---

##### 3. Prompt 设计的关键细节

文章强调，这个 prompt 并不是让 AI 随便想象，而是有明确工程设计。

###### 1）数据源明确

要求 Codex 基于：

> recent Codex sessions

也就是最近的 Codex 会话历史，而不是凭空生成建议。  
这样可以保证输出更贴近用户真实工作习惯。

###### 2）强制二分类

Prompt 要求 Codex 在两类结果中做选择：

1. 如果是可复用工作流，就建议做成 skill  
2. 如果是有边界的角色或调查任务，就建议做成 custom subagent

这样可以避免 AI 输出模糊、泛泛而谈的建议。

###### 3）聚焦高频开发场景

文章列出了几个实用场景，用来收窄 Codex 的搜索范围：

- CI failures：CI 失败
- PR reviews：PR 审查
- changelogs：变更日志
- docs updates：文档更新
- release prep：发布准备
- debugging：调试
- test triage：测试分类与排查

###### 4）控制生成质量

Prompt 中加入了限制：

> Create the useful ones only. Keep them simple.

意思是：

> 只创建真正有用的，保持简单。

这样可以防止 AI 过度生成一堆低价值、复杂但没必要的 Skills 或 Subagent。

---

##### 4. 可直接复制使用的 Prompt

##### 2. 高价值信息深挖

###### 2.1 Skills 与 Subagent 的本质区别

原文区分了两个概念：

| 类型 | 适合对象 | 关键词 | 本质 |
|---|---|---|---|
| Skill | 可复用工作流 | 怎么做 | 标准操作流程 |
| Subagent | 有边界的角色/调查任务 | 谁来做 | 专门角色/专家代理 |

###### Skill：适合沉淀“流程”

例如：

- “当 CI 失败时，按日志 → 最近提交 → 依赖变更 → flaky test → 修复建议的顺序排查”
- “写 changelog 时，根据 commit/PR diff 自动分类为 feature/fix/breaking change”
- “清理 diff 时，优先找无关格式化、调试代码、未使用变量、重复逻辑”

Skill 的重点是：

> 遇到某类任务时，按照稳定步骤执行。

它更像 SOP、清单、工作流模板。

---

###### Subagent：适合沉淀“角色”

例如：

- `ci-debugger`：专门分析 CI 失败
- `pr-reviewer`：专门做代码审查
- `release-manager`：专门检查发布准备
- `test-triage-agent`：专门判断测试失败是代码问题、环境问题还是 flaky

Subagent 的重点是：

> 你不用告诉它每一步怎么做，只需要委派一个边界清晰的任务。

它更像一个低配但专注的虚拟同事。

---

###### 2.2 这个 prompt 的工程设计亮点

原始 prompt 不复杂，但设计上很克制。

###### ① 数据源明确

> Look through my recent Codex sessions

它没有让 AI 凭空想象“我可能需要什么 skill”，而是从最近会话中提取真实重复模式。

这很关键。

因为很多自动化失败，不是技术问题，而是源头数据不真实。  
如果 AI 只是泛泛建议，最后会产出一堆“看起来合理但没人用”的模板。

高质量抽象必须来自真实行为数据。

---

###### ② 强制二分类

> suggest:  
> 1. a skill if it is a reusable workflow  
> 2. a custom subagent if it is a bounded role or investigation task

它让 AI 必须判断：

- 这是流程？
- 还是角色？
- 是可复用 SOP？
- 还是可委派任务？

这个设计可以避免 AI 产出模糊建议，例如：

> “你可以优化 CI 流程。”  
> “你可以创建一个代码审查助手。”

这些都太泛。

真正有用的是：

- 什么任务值得沉淀？
- 应该沉淀为 Skill 还是 Subagent？
- 触发条件是什么？
- 输入输出是什么？
- 执行步骤是什么？

---

###### ③ 场景聚焦

原文列了七个高频开发场景：

- CI failures
- PR reviews
- changelogs
- docs updates
- release prep
- debugging
- test triage

这不是随便列的，而是在限定搜索空间。

AI 一旦搜索空间太大，就容易给出泛化、臃肿、不实用的建议。  
限定场景之后，AI 更容易产出可落地结果。

---

###### ④ 质量约束

> Create the useful ones only. Keep them simple.

这是整个 prompt 里最重要的一句。

因为 AI 很容易过度生成：

- 十几个没人用的 agents
- 复杂命名
- 过多流程
- 看似完整但执行成本高的系统

而这句话在提醒 AI：

> 不要为了系统化而系统化，只沉淀真正高频、有价值、简单可用的部分。

这其实也是构建 AI 工作流的原则：

**小而稳定，比大而全更重要。**

##### 3. 可迁移清单

这套方法不只适用于 Codex，也适用于任何 AI/产品/商业系统构建场景。

###### 3.1 识别重复任务清单

你可以定期问自己或 AI：

- 我最近反复让 AI 做什么？
- 哪些任务每次都要重新解释？
- 哪些任务有固定输入、固定步骤、固定输出？
- 哪些任务虽然复杂，但角色边界很清晰？
- 哪些 prompt 经常只改几个变量？
- 哪些人工判断其实有可复用标准？
- 哪些任务反复发生但质量不稳定？

---

###### 3.2 判断该沉淀为 Skill 还是 Subagent

###### 适合沉淀为 Skill 的任务

满足以下特征：

- 有稳定流程
- 多步骤
- 每次做法类似
- 输入输出结构清晰
- 更关注“怎么做”

例子：

- 内容选题分析流程
- 用户访谈总结流程
- 竞品分析流程
- PRD 梳理流程
- 销售线索评分流程
- 周报生成流程
- 投放数据复盘流程

---

###### 适合沉淀为 Subagent 的任务

满足以下特征：

- 有明确角色
- 边界清晰
- 需要持续判断
- 可以被委派
- 更关注“谁来负责”

例子：

- 增长分析师
- 用户研究员
- 代码审查员
- 财务风控审查员
- 法务合规检查员
- 客服质检员
- 内容编辑
- 产品 QA

---

##### 4. 反方与张力

###### 4.1 自动记忆并不总是可靠

热门回复里有一个观点很重要：

> 手工管理记忆，分话题用 markdown 保存，可能比 RAG、向量数据库、自动记忆更好用。

这指出了一个现实问题：

AI 自动记忆常见缺陷：

- 重要信息没记住
- 不重要的信息记一堆
- 过时信息没有清理
- 缺少主题归类
- 调用时上下文不准
- 很难知道它到底记了什么

所以，“让 AI 回顾历史会话”有价值，但不能完全依赖自动记忆。

更稳妥的方式是：

> AI 负责发现模式，人负责确认和归档。

---

###### 4.2 抽象过度会降低效率

不是所有重复任务都值得沉淀。

有些任务虽然重复，但变化太大；  
有些任务频率高，但价值低；  
有些任务沉淀成本大于收益。

比如热门回复调侃：

> 最应该被沉淀为 skill 的话是“继续”。

这其实指出了一个问题：

AI 可能会识别出表层重复，而不是深层工作模式。

用户经常说“继续”，不代表“继续”本身值得产品化。  
真正应该识别的是“继续”背后的任务类型：

- 继续写代码？
- 继续分析？
- 继续 debug？
- 继续扩写文档？
- 继续补测试？

所以，沉淀能力时要避免把表层词频当成真实需求。

---

###### 4.3 开发者不只是要答案，也要理解 why

另一个回复提到：

> 大多数开发者问 why，是因为他们需要理解代码背后的原因，才能改得更好。

这很关键。

如果 Skill/Subagent 只追求自动完成，可能会损害学习和理解。  
尤其在代码场景中，开发者并不只是想让 AI 修 bug，而是想知道：

- 为什么失败？
- 为什么这样改？
- 有没有更好的设计？
- 这个改动有什么副作用？
- 是否破坏长期架构？

所以好的 Agent 不应该只是执行，还要解释。

##### 5. 情境化落地

###### 5.1 个人开发者怎么用

你可以每周让 Codex/Claude/Cursor 做一次“会话回顾”。

示例 prompt：

```text
请回顾我最近的 AI 编程会话，识别我反复请求的任务类型。

对于每个重复任务，请判断：
1. 如果它是可复用工作流，请建议沉淀为 Skill
2. 如果它是边界清晰的角色或调查任务，请建议沉淀为 Subagent

重点关注：
- CI 失败
- PR review
- changelog
- 文档更新
- release 准备
- debugging
- test triage
- 代码重构
- diff 清理

只保留真正高频、有用、简单的建议。

请输出：
- 名称
- 类型：Skill/Subagent
- 触发场景
- 输入
- 执行步骤
- 输出
- 是否值得优先沉淀：高/中/低
```

###### 5.2 团队怎么用

团队可以每两周做一次 AI 工作流复盘。

流程如下：

1. 收集团队成员最近常用 prompt
2. 聚类重复任务
3. 判断 Skill 还是 Subagent
4. 只选择 Top 3 高频任务
5. 写成共享 markdown
6. 放到团队仓库或内部知识库
7. 每月清理一次过时内容

建议命名结构：

```text
/ai-workflows
  /skills
    ci-failure-debugging.md
    changelog-generation.md
    pr-review-checklist.md
  /subagents
    ci-debugger.md
    release-manager.md
    test-triage-agent.md
```

###### 5.3 一个 Skill 模板

```markdown
# Skill: CI Failure Debugging

## 触发场景
当 CI pipeline 失败，需要快速定位原因并给出修复建议。

## 输入
- CI 日志
- 最近 commit
- 相关测试文件
- package/dependency 变更
- 环境配置

## 执行步骤
1. 识别失败阶段：install/build/test/lint/deploy
2. 提取关键错误日志
3. 判断是否为环境问题、依赖问题、代码问题或 flaky test
4. 对比最近相关 diff
5. 给出最小修复方案
6. 如果不确定，列出需要进一步验证的信息

## 输出
- 失败原因摘要
- 可能根因排序
- 建议修复方案
- 风险提示
- 下一步验证命令
```

---

###### 5.4 一个 Subagent 模板

```markdown
# Subagent: PR Reviewer

## 角色
你是一个专注于代码质量、可维护性和潜在风险的 PR Reviewer。

## 任务边界
只审查当前 PR，不重写整个系统，不引入无关架构建议。

## 关注重点
- 逻辑错误
- 边界条件
- 安全风险
- 性能问题
- 可读性
- 测试覆盖
- 破坏性变更

## 输入
- PR diff
- 相关 issue
- 测试结果
- 项目代码规范

## 输出格式
1. 总体评价
2. 必须修改的问题
3. 建议优化的问题
4. 测试补充建议
5. 是否建议 merge
```

##### 6. 最值得带走的结论

这条内容背后的方法论可以总结为一句话：

> 不要只把 AI 当问答工具，要把你和 AI 的重复协作模式沉淀成资产。

真正有长期价值的不是某一次 prompt，而是：

- 你有哪些高频任务？
- 哪些任务可以流程化？
- 哪些任务可以角色化？
- 哪些流程可以复用？
- 哪些判断可以标准化？
- 哪些上下文应该被保存？
- 哪些能力可以变成团队资产？

AI 工具的效率差距，未来可能不在于谁会写更华丽的 prompt，  
而在于谁能更快把重复工作抽象成：

- Skill
- Subagent
- Checklist
- Template
- SOP
- Internal Tool

最终，AI 编程助手不只是帮你写代码，  
而是帮你发现自己的工作模式，并把它们变成可复用系统。
