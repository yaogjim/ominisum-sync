## 分析要点

- **核心高价值点**：语言失配可能让模型在完全错误时仍高度自信，因此不能仅靠置信度阈值兜底，应在推理前识别语言并路由到适配模型。
- **留存建议**：保留为低延迟决策模块的选型、评测与部署参考，采用前需在目标业务数据上验证。（包含可执行的调用与部署示例，并明确揭示语言失配、概率校准、选项预算和领域微调等关键限制，具有可复用的工程参考价值。）

**知识要点**

- 严格适当评分规则训练不等于开箱即用的概率校准；文中模型仍存在过度自信，需要使用留出数据按问题类型和选项数量拟合温度。
- 多语言服务的延迟不仅取决于前向推理：默认只保留一个热模型时，语言切换会触发秒级重载，预加载或增加常驻模型数量可避免这一开销。
- 高选项数分类受到选项提示令牌预算约束；增加选项预算会挤占状态文本空间，也可采用先粗分类、再细分类的层级决策。

**行动项**

- 用目标业务样本分别评测基础检查点和适配检查点，检查准确率、校准误差与业务基线，避免将领域微调结果当成通用零样本能力。
- 部署混合语言服务时预加载实际需要的检查点，或设置合适的常驻数量，并测量语言切换时的延迟及显存占用。
- 依赖置信度自动执行前，在留出数据上拟合温度并验证阈值；超过50个选项时，测试扩大选项预算或两阶段层级分类。

**Multilingual, non-autoregressive System 1 decision engine.** Typed decisions over 100+ languages in a single forward pass — 33 ms — trained with reinforcement learning against strictly proper scoring rules (RLCD), with a router that picks the right checkpoint per request.

[![Laya versus TypeSafe Jev: accuracy on shared public datasets, every application workflow, all 51 languages, speed, calibration, and the cost of not preloading](https://raw.githubusercontent.com/NandhaKishorM/laya/main/assets/laya_vs_jev_full.png)](https://raw.githubusercontent.com/NandhaKishorM/laya/main/assets/laya_vs_jev_full.png)

Laya evaluates typed questions (`choice`, `score`, `noul`) over any state (text, email, ticket or JSON document) in **a single forward pass** — 33 ms for one question, 7.2 ms/question batched, measured on a T4. No text generation, so nothing to parse and nothing to hallucinate.

Three checkpoints, and a `Router` that picks between them per request:

encoder params context use it for

[`laya`](https://huggingface.co/convaiinnovations/laya) ModernBERT-large 421M 512 English

[`laya-multilingual`](https://huggingface.co/convaiinnovations/laya-multilingual) mmBERT-base 322M 1024 100+ languages, 2x faster

[`laya-typed-decisions`](https://huggingface.co/convaiinnovations/laya-typed-decisions) ModernBERT-large 421M 1024 the typed-decisions workflows

Laya ships three checkpoints. The built-in **`Router`** is the recommended entry point: it evaluates any state in any language, automatically detects scripts and languages in sub-milliseconds, and dispatches to the optimal checkpoint in a single forward pass.

```
import laya
from laya import Router

# Preload checkpoints into memory for instant sub-35ms routing
router = Router(preload=True)

# 1. State in any language or schema
state = {
    "from": "user@acme.com",
    "subject": "Duplicate charge on invoice #4411",
    "body": "Hi, we were billed twice for March. Please refund the duplicate today or we will cancel our plan."
}

# 2. Define your typed questions
questions = {
    "department": {
        "type": "choice",
        "instructions": "Which department should handle this request?",
        "criteria": {
            "billing": "invoices, payments, refunds",
            "technical": "bugs, outages, system errors",
            "sales": "pricing, new contracts",
            "other": "everything else"
        }
    },
    "urgency": {
        "type": "score",
        "instructions": "How urgent is this request?",
        "criteria": ["not urgent", "soon", "critical deadline or blocking issue"]
    },
    "churn_risk": {
        "type": "noul",
        "instructions": "Does the user threaten to cancel or leave?"
    },
    "refund_requested": {
        "type": "noul",
        "instructions": "Does the user explicitly request a refund?"
    }
}

# 3. English state -> automatically routed to laya (ModernBERT-large, 39.5 ms)
res_en = router.predict(state, questions)
print("Department :", res_en["answers"]["department"]["choice"])  # -> billing (confidence: 0.94)
print("Routing    :", res_en["routing"]["model"])                 # -> english

# 4. Hindi state -> automatically routed to laya-multilingual (mmBERT-base, 32.8 ms)
res_hi = router.predict({"body": "मुझसे दो बार शुल्क लिया गया, कृपया पैसे वापस करें।"}, questions)
print("Department :", res_hi["answers"]["department"]["choice"])  # -> billing (confidence: 0.86)
print("Routing    :", res_hi["routing"]["model"])                 # -> multilingual

# 5. Explicit override when you want a specific checkpoint
res_td = router.predict(state, questions, model="typed-decisions")
```

The English checkpoint collapses on non-Latin scripts (Khmer scores **0.000 accuracy at 0.952 confidence**). Because the model stays confident while being wrong, confidence gating cannot save you. `Router` detects the script in &lt;0.5 ms pure Python before the forward pass.

A cold checkpoint build costs seconds; language detection costs microseconds. At the default `max_loaded=1`, traffic that alternates languages rebuilds a model on *every* request (measured at a 7.4 s median reload on CPU and 10.3 s on T4).

For a server or production app, preload:

```
# Every checkpoint resident in memory; language flips cost detection only (<1 ms)
router = Router(preload=True)
router = Router(preload=True, device="cuda")

# Or preload only the specific checkpoints you serve:
router.preload(["english", "multilingual"])

# If your app already built an agent, attach it to avoid duplicate VRAM:
router.attach("english", existing_agent)

# Manage resident memory (default keeps 1 hot, LRU eviction)
router = Router(max_loaded=2)       # keep two hot
router.unload()                     # free memory
```

If you only need a single checkpoint for a dedicated pipeline, you can load models directly:

```
import laya

# 1. Load a specific checkpoint directly from the hub
agent = laya.load("convaiinnovations/laya")                           # English root
agent_ml = laya.load("convaiinnovations/laya", subfolder="multilingual") # 100+ languages
agent_td = laya.load("convaiinnovations/laya", subfolder="typed-decisions")

# 2. Run all questions in ONE single forward pass (~35 ms on GPU)
result = agent.predict(state, questions)
answers = result["answers"]

print("Department :", answers["department"]["choice"])   # -> billing (confidence: 0.94)
print("Urgency    :", answers["urgency"]["score"])        # -> 1.84 / 2.0
```

Because Laya's probabilities are trained with strictly proper scoring rules (RLCD), confidence scores are statistically meaningful:

```
dept = answers["department"]["choice"]
conf = answers["department"]["confidence"]

if conf >= 0.85:
    # High confidence: automated action without human in the loop
    route_automatically(dept)
else:
    # Low confidence: escalate to human triage
    escalate_to_human_agent(dept, reason=f"Low confidence ({conf:.2f})")
```

On DAIR Emotion, Jev assigned **zero probability to the true label on 16% of examples** — a hard failure for anything branching on confidence.

- **High-cardinality label spaces (&gt;20 options at default settings):** On Banking77, Jev scores 0.870 (on 72 labels) while Laya scores 0.425 (on 77 labels at default 256-token head budget). This is an architectural token-budget constraint: options share a fixed `head_max_len` budget (192 tokens on English, 256 on multilingual), so 77 options receive only \~3 to 4 tokens per label, causing text to become indistinguishable. Jev supports up to 255 options out-of-the-box. While `laya-multilingual` supports 1,024 context (and up to 8,192 in the encoder) and you can raise `agent.cfg["head_max_len"] = 512` at runtime, Jev is currently better suited for 50+ options in a single prompt without tuning.
- **Soft distribution matching:** On typed-decisions, while Laya achieves higher argmax accuracy (0.766 vs 0.727), Jev achieves higher soft accuracy (0.580 vs 0.471) against the teacher's full probability distributions.
- **Out-of-the-box raw calibration:** Before temperature scaling, the base checkpoint has higher raw ECE (0.213 vs 0.144). Laya achieves its 0.081 ECE after domain temperature fitting.

##### Calibration

Both checkpoints are over-confident as shipped. Refitting one temperature per (question type, option count) on held-out data moves mean ECE **0.466 -&gt; 0.081** (`laya`) and **0.314 -&gt; 0.106** (`laya-multilingual`). `laya-multilingual` ships with no fitted temperatures at all, so fit them before relying on its probabilities.

##### Honest limits

- **The base checkpoints are near chance on typed-decisions zero-shot** -- 0.362 and 0.352 against a 0.318 random baseline and a 0.461 majority-class baseline. The 0.766 figure comes from the checkpoint fine-tuned on that benchmark's own training split. Laya is a fast base to specialise, not a zero-shot decision engine.
- **High-cardinality choice questions and token budgets:** Sequences split into an option prompt budget (`head_max_len`) and the remaining document/state budget (`max_len - head_max_len`):
  - `laya` (English) defaults to 512 context (`head_max_len = 192`, \~320 tokens for state).
  - `laya-multilingual` and `laya-typed-decisions` default to 1,024 context (`head_max_len = 256`, \~768 tokens for state; mmBERT-base encoder supports up to 8,192 with RoPE). At default settings, a 77-option question like Banking77 allocates only `(256 - 16) // 77` ≈ 3–4 tokens per label, which causes accuracy to fall off sharply (0.425 vs Jev's 0.870). If evaluating 50+ options in a single question:
  1. Raise `agent.cfg["head_max_len"] = 512` and `agent.cfg["max_len"] = 1024` (or up to 2048 / 4096 / 8192) so every option has enough tokens to remain distinct.
  2. Or split large option sets into a two-step coarse-to-fine hierarchical choice.
- Ordinal `score` questions are the weakest primitive (SST-5 0.372).
- `laya` collapses outside English; `laya-multilingual` is weaker on English. Route, or pick deliberately.

#### Fine-Tuning

Fine-tune Laya on your own domain data. The notebook runs on Kaggle's free 2xT4 GPUs and does the whole loop: build the dataset, train with RLCD (proper-scoring-rule rewards, GRPO-style policy gradient), fit calibration temperatures, evaluate, and push the result to the Hub.

- **`notebooks/laya_finetune_typed_decisions_2xT4_kaggle.ipynb`**

Fine-tuning is where most of the value is. On the typed-decisions benchmark the base checkpoints score near chance zero-shot (0.36 and 0.35 against a 0.318 random baseline), while the fine-tuned checkpoint reaches **0.766** on the same 2,000 decisions -- above TypeSafe Jev's published 0.727 and above the 0.735 teacher self-agreement ceiling. Treat Laya as a fast base to specialise, not as a zero-shot decision engine.

Runtime on 2xT4 is roughly 4-5 hours for 4 epochs over \~30k questions.

## 解读（1）

### 2026-09-21 02:07:23

##### 核心总结

Laya 是一个面向分类、评分和真假判断的开源决策模型，不生成自然语言，而是一次前向计算直接输出结构化结果及置信度。项目提供英文、多语言和特定任务微调三个检查点，并通过路由器按语言自动选模；在 T4 GPU、模型已预加载的前提下，单问题约需 33—40 毫秒，批量处理可降至约 7 毫秒 / 题。项目基准显示其在部分任务上兼具速度、准确率和校准优势，但这些能力高度依赖**正确路由、领域微调、温度校准和选项数量**：基础模型在复杂 typed-decisions 基准上接近随机，高置信度也未必代表可靠。

##### 通俗解读

###### 1. 它更像 “高速判定器”，不是聊天模型

Laya 只处理三类结构化问题：

- `choice`：从若干选项中选一个，如工单属于财务还是技术部门；
- `score`：按等级评分，如紧急程度；
- `noul`：输出某件事为真的概率，如用户是否威胁退订。

这类设计省去了 “让大模型先写一句话，再从话里解析答案” 的过程，因此速度更快，输出格式也更稳定。一次调用还可以同时判断部门、紧急度、退款请求和流失风险。

但 “无文本生成，所以不会幻觉” 应作狭义理解：**它不会编造一段答案，却仍可能分类错误，甚至非常自信地犯错。**原文给出的典型例子是，英文模型处理高棉语时准确率为 0，却仍有 95.2% 的置信度。

###### 2. 路由器不是附属功能，而是可靠性的关键

英文模型在英语任务上更强，多语言模型覆盖范围更广；没有一个模型在所有语言上都最好。因此系统先识别文字脚本和语言，再决定调用哪个检查点。

这样做之所以重要，是因为错误模型的置信度并不能稳定发出警告：如果英文模型面对不认识的文字仍然高置信，事后设置 “低于 0.8 才转人工” 也救不了。**必须在推理前选对模型，而不能只依赖推理后的置信度。**

同时，生产环境需要预加载模型。默认只保留一个热模型时，语言交替可能触发数秒级重载；预加载后才是宣传中的几十毫秒延迟。换言之，**33 毫秒是特定部署方式和硬件下的结果，不是任意安装后的默认体验。**

###### 3. “置信度可用于自动化” 有严格前提

项目采用适合概率预测的评分规则训练，希望 0.9 的置信度在长期统计上接近 90% 正确率。但原文自己的实验也显示，模型出厂时普遍过度自信：英文模型经温度校准后，ECE 才从 0.466 降至 0.081；多语言模型甚至没有附带拟合好的温度参数。

因此，按置信度自动审批、拦截或转人工之前，仍应使用目标业务的留出数据重新校准。**训练方法有利于概率质量，不等于概率天然适用于任何领域。**

##### 辩证思考

原文最有说服力之处，是没有只展示最佳数字，而是明确披露了关键失败条件：基础模型在 typed-decisions 上低于多数类基线，0.766 的成绩来自使用该基准训练集微调后的专用模型；面对 50 个以上选项时性能明显下降；序数评分是弱项；多语言概率未经校准。这些限制与模型架构能够相互解释，而不是简单归咎于 “数据不够”。

不过，项目的核心定位应更准确地理解为：**一个适合专项微调的高速结构化分类框架，而非开箱即用的通用零样本决策引擎。**基础检查点在 typed-decisions 上只有约 0.34—0.36，随机基线为 0.318，多数类基线为 0.461；高分主要来自同一基准训练集上的微调。这能证明模型学得动、推理快，但不足以证明它能直接迁移到新的业务领域。更有说服力的证据应包括跨组织、跨时间或完全未参与调参的数据测试。

与 TypeSafe Jev 的比较也不能视为严格对照实验。原文已说明 Jev 的数据来自第三方发布，双方的样本量和提示词可能不同，Laya 团队也没有直接访问 Jev API。因此 “快 7.8 倍” 或部分任务领先，只能作为参考。尤其在 Banking77 这类高选项任务上，Jev 为 0.870、Laya 为 0.425，说明 Laya 的固定提示预算形成了实际架构瓶颈；增加 token 预算或分层分类可能改善结果，但原文没有给出调整后的对应成绩，不能把 “可调” 当作 “已经解决”。

最后，“不生成文本，因此不会幻觉” 是有传播力但容易误导的表述。Laya 确实避免了格式漂移和生成式编造，却无法避免**语义误判、分布外失效和错误校准**。对低风险工单分流，这种高速模型很有价值；对安全拦截、欺诈识别或自动审批，则必须配合领域验证、持续校准、异常语言检测和人工兜底。其优势在于把错误变得更结构化、更容易测量，而不是消除错误。

##### 二、推荐方式：使用 Router

```python
router = Router (
```

```python
department = answers ["department"]["choice"]
```

##### 六、在 Web 后端中提供服务

例如在 FastAPI 项目中，可以在应用启动时初始化一次 Router：

```python
from contextlib import asynccontextmanager
from typing import Any

from fastapi import FastAPI
from pydantic import BaseModel
from laya import Router


router: Router | None = None


@asynccontextmanager
async def lifespan (app: FastAPI):
    global router

    # 如果服务器有 CUDA，可设置 device="cuda"
    router = Router (
        preload=True,
        device="cuda"
    )

    yield

    if router is not None:
        router.unload ()


app = FastAPI (lifespan=lifespan)


class DecisionRequest (BaseModel):
    state: dict [str, Any]


QUESTIONS = {
    "department": {
        "type": "choice",
        "instructions": "这个请求应该由哪个部门处理？",
        "criteria": {
            "billing": "账单、付款、退款和发票",
            "technical": "系统故障、产品错误和接口问题",
            "sales": "购买、价格、新合同和套餐升级",
            "other": "其他问题"
        }
    },
    "urgent": {
        "type": "noul",
        "instructions": "这个请求是否需要立即处理？"
    }
}


@app.post ("/decisions")
def make_decisions (request: DecisionRequest):
    assert router is not None

    result = router.predict (
        request.state,
        QUESTIONS
    )

    return {
        "answers": result ["answers"],
        "routing": result ["routing"]
    }
```

调用接口：

```bash
curl -X POST http://localhost:8000/decisions \
  -H "Content-Type: application/json" \
  -d '{
    "state": {
      "subject": "重复扣款",
      "message": "我被扣了两次钱，请立即退款"
    }
  }'
```

###### 服务部署建议

- Router 应作为进程级单例创建；
- 不要在每个 HTTP 请求中重新加载模型；
- 一张 GPU 上先从单个推理进程开始压测；
- 多进程部署会让每个进程各自加载一份模型，占用更多显存；
- 高并发时应使用限流、请求队列或受控的推理 worker；
- 如果应用存在多个语言，优先使用`preload=True`；
- 上线前分别测量冷启动延迟、单请求延迟和批量吞吐。

##### 九、设计问题时的注意事项

###### 1. 选项描述要具体

不推荐：

```python
"criteria": {
    "a": "财务",
    "b": "技术",
    "c": "其他"
}
```

更推荐：

```python
"criteria": {
    "billing": "支付失败、重复扣款、退款、发票和账单问题",
    "technical": "系统故障、接口异常、登录失败和产品功能错误",
    "other": "不属于财务或技术的问题"
}
```

模型不仅依赖标签名称，也依赖选项描述。

###### 2. 一个问题只表达一个判断目标

不推荐：

```python
"instructions": "判断用户是否愤怒、是否要退款以及是否会取消订阅"
```

应拆成三个`noul`问题：

```python
{
    "is_angry": {
        "type": "noul",
        "instructions": "用户是否表现出明显愤怒？"
    },
    "refund_requested": {
        "type": "noul",
        "instructions": "用户是否明确要求退款？"
    },
    "churn_risk": {
        "type": "noul",
        "instructions": "用户是否表示要取消订阅或停止使用？"
    }
}
```

这些问题仍可在一次前向计算中处理。

###### 3. 避免一次提供过多分类选项

Laya 对几十个甚至 50 个以上选项的单次分类存在 token 预算限制。若业务有很多类别，例如 100 个工单意图，建议采用分层分类：

1. 先判断大类：财务、技术、账户、销售；
2. 再在对应大类中判断具体子类。

例如：

```text
第一层：technical
第二层：login_failure /api_error/outage /configuration
```

这通常比一次直接从 100 个标签中选择更可靠。

---

##### 十、上线前必须做自己的验证

不要直接把项目主页上的准确率和置信度阈值照搬到你的系统。建议准备一份人工标注的业务数据，至少测试：

- 每个类别的准确率、召回率和混淆情况；
- 中文、英文及中英文混合输入；
- 很短、很长、拼写错误和噪声输入；
- 没有足够信息的输入；
- 新类别和分布外输入；
- 不同置信度区间中的真实正确率；
- 低频但高风险的错误。

尤其要注意：Laya 不生成文字，但仍然可能**高置信度分类错误**。涉及封号、付款、退款、安全拦截或法律合规时，不应只依赖一次模型输出。

---

##### 推荐的落地架构

```text
前端 / 业务系统
       │
       ▼
输入清洗与敏感信息处理
       │
       ▼
Laya Router（启动时预加载）
       │
       ├── 高置信度、低风险 → 自动执行
       ├── 中等置信度       → 记录并有限自动化
       └── 低置信度或高风险 → 人工审核
       │
       ▼
保存输入、结果、置信度、路由信息和最终人工结论
       │
       ▼
周期性评估并调整问题描述和业务阈值
```

最简单的接入方式就是：**应用启动时创建`Router (preload=True)`，把业务对象整理成`state`，将判断需求定义为`questions`，调用`router.predict ()`，再根据答案和置信度驱动现有业务流程。**

详述 laya 整个系统

### 回答 · 2026-09-21 04:03:18

下面从**定位、组件、数据流、模型、路由、决策原语、训练、校准、部署、性能、局限与生产架构**几个层面完整说明 Laya。

> 以下内容基于该项目当前 README 和基准报告。部分底层实现细节，例如状态序列化格式、决策头具体网络结构和 RLCD 的全部损失公式，并未在页面中完整公开，因此不会把推测当作事实。

---

#### 一、Laya 是什么

Laya 是一个：

- 多语言；
- 非自回归；
- 基于编码器；
- 输出结构化概率；
- 面向分类与决策；
- 可自行部署；

的 “System 1” 决策引擎。

这里的 “System 1” 强调的是**快速、直接判断**，而不是多步推理。

它和普通大语言模型的差别是：

| 生成式大模型 | Laya |
|---|---|
| 逐 token 生成文本 | 一次前向传播输出决策 |
| 可能返回格式不稳定的自然语言 | 固定返回结构化字段 |
| 经常需要解析 JSON 或标签 | 直接返回标签、分数和概率 |
| 适合生成、解释和多步推理 | 适合分类、打分、真假判断 |
| 延迟通常受输出长度影响 | 延迟主要受输入和问题数量影响 |
| 可能产生文本幻觉 | 不产生文本，但仍可能误判 |

因此，更准确地说，Laya 不是聊天机器人，也不是通用推理模型，而是一个**可以快速专业化的结构化决策模型框架**。

适合的场景包括：

- 客服工单分流；
- 邮件意图分类；
- 请求紧急度判断；
- 流失风险识别；
- 是否申请退款；
- 垃圾邮件与钓鱼检测；
- Prompt Injection、越狱检测；
- 内容安全审核；
- 将任务路由到小模型或大模型；
- 对 JSON 状态做业务分类。

---

#### 二、整个系统的总体架构

可以把 Laya 看成六层：

```text
┌──────────────────────────────────────────────┐
│ 1. 业务层                                    │
│ 工单、邮件、Prompt、用户请求、JSON 状态       │
└──────────────────────┬───────────────────────┘
                       │ state + questions
                       ▼
┌──────────────────────────────────────────────┐
│ 2. Router 路由层                             │
│ 文字脚本检测、语言判断、模型选择、缓存管理    │
└──────────────────────┬───────────────────────┘
                       │ 选择检查点
                       ▼
┌──────────────────────────────────────────────┐
│ 3. Checkpoint 模型层                         │
│ English / Multilingual / Typed Decisions     │
└──────────────────────┬───────────────────────┘
                       │ 编码状态与问题
                       ▼
┌──────────────────────────────────────────────┐
│ 4. 决策原语层                                │
│ choice /score/noul                        │
└──────────────────────┬───────────────────────┘
                       │ 概率与分布
                       ▼
┌──────────────────────────────────────────────┐
│ 5. 校准与输出层                              │
│ 温度缩放、置信度、路由元数据、结构化结果      │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│ 6. 业务执行层                                │
│ 自动处理 / 转人工 / 拦截 / 路由 / 记录日志    │
└──────────────────────────────────────────────┘
```

一次业务调用的核心形式是：

```python
result = router.predict (state, questions)
```

其中：

- `state`是需要判断的业务状态；
- `questions`是需要模型回答的结构化问题；
- `Router`决定使用哪个模型；
- 所有问题尽量在一次前向传播中处理；
- 结果以结构化字典返回。

---

#### 三、输入系统：State 与 Questions

##### 1. State：需要评估的对象

`state`可以是简单文本，也可以是结构化 JSON。

例如客服工单：

```python
state = {
    "ticket_id": "T-4411",
    "from": "user@acme.com",
    "subject": "Duplicate charge",
    "body": (
        "We were billed twice for March."
        "Please refund the duplicate today or we will cancel."
    ),
    "plan": "enterprise",
    "account_age_days": 700
}
```

这说明 Laya 的输入不局限于一句 Prompt。它可以把邮件正文、标题、用户属性和其他业务字段作为一个状态来判断。

不过，要注意上下文长度限制。Laya 并不适合把无限长的日志、整本合同或超长对话直接送进去。

---

##### 2. Questions：需要模型做出的决策

问题通过字典定义：

```python
questions = {
    "department": {
        "type": "choice",
        "instructions": "Which department should handle this request?",
        "criteria": {
            "billing": "invoices, payments and refunds",
            "technical": "bugs, outages and system errors",
            "sales": "pricing, contracts and upgrades",
            "other": "everything else"
        }
    },
    "urgency": {
        "type": "score",
        "instructions": "How urgent is this request?",
        "criteria": [
            "not urgent",
            "should be handled soon",
            "critical deadline or blocking issue"
        ]
    },
    "refund_requested": {
        "type": "noul",
        "instructions": "Does the user explicitly request a refund?"
    },
    "churn_risk": {
        "type": "noul",
        "instructions": "Does the user threaten to cancel or leave?"
    }
}
```

同一个状态可以同时被问多个问题。

这是 Laya 的一个重要特征：不是每一个判断都单独跑一次模型，而是把多个问题组织在同一次调用中处理。

---

#### 四、三种决策原语

Laya 把业务判断统一为三种原语：

1. `choice`
2. `score`
3. `noul`

这三种原语构成了它的结构化输出系统。

---

##### 1. `choice`：多选一分类

用于从候选项中选择一个结果。

```python
"department": {
    "type": "choice",
    "instructions": "哪个部门应该处理这个请求？",
    "criteria": {
        "billing": "付款、扣款、退款和发票",
        "technical": "系统故障、接口错误和产品问题",
        "sales": "价格、新合同和套餐升级",
        "other": "其他请求"
    }
}
```

典型输出包括：

- 得分最高的标签；
- 每个候选标签的概率；
- 顶部标签的置信度。

概念上可能是：

```python
{
    "choice": "billing",
    "confidence": 0.94,
    "probabilities": {
        "billing": 0.94,
        "technical": 0.02,
        "sales": 0.01,
        "other": 0.03
    }
}
```

实际字段应以所安装版本的返回结果为准。

适用场景：

- 部门路由；
- 意图分类；
- 新闻分类；
- 主题归类；
- 模型选择；
- 风险类型判断。

---

##### 2. `score`：有序等级评分

用于评估有明确顺序的等级。

```python
"urgency": {
    "type": "score",
    "instructions": "请求有多紧急？",
    "criteria": [
        "不紧急",
        "需要尽快处理",
        "严重阻塞或存在明确截止时间"
    ]
}
```

它不是普通无序分类。三个选项之间具有等级关系：

```text
不紧急 < 尽快处理 < 严重阻塞
```

输出通常包括：

- 每一级的概率分布；
- 分数的期望值；
- 置信度。

例如三档评分可以得到类似：

```python
{
    "score": 1.84,
    "confidence": 0.88,
    "distribution": [0.03, 0.10, 0.87]
}
```

如果等级按`0、1、2`解释，那么`1.84 / 2.0`代表模型认为结果非常接近最高等级。

适用场景：

- 工单紧急度；
- 用户挫败程度；
- 内容危害严重度；
- 风险等级；
- 满意度；
- 告警优先级。

README 也明确指出，`score`是当前相对较弱的原语。例如 SST-5 有序分类上的成绩只有约`0.372`，因此重要评分业务必须用自己的数据验证。

---

##### 3. `noul`：真假事件概率

`noul`返回某一陈述为真的概率：

```python
"refund_requested": {
    "type": "noul",
    "instructions": "用户是否明确要求退款？"
}
```

输出是：

```python
{
    "noul": 0.892
}
```

其含义是：

```text
P (用户明确要求退款) = 89.2%
```

适用场景：

- 是否存在退款请求；
- 是否威胁取消服务；
- 是否是垃圾邮件；
- 是否存在钓鱼行为；
- 是否为越狱提示；
- 是否存在人身威胁；
- 是否需要人工审核。

`noul`最接近二分类，但它强调输出的是校准后的`P (true)`，而不是只给出 Yes/No。

---

#### 五、三个模型检查点

Laya 当前提供三个主要检查点。

| 检查点 | 编码器 | 参数量 | 默认上下文 | 主要用途 |
|---|---:|---:|---:|---|
| `laya` | ModernBERT-large | 421M | 512 | 英文 |
| `laya-multilingual` | mmBERT-base | 322M | 1024 | 100 多种语言 |
| `laya-typed-decisions` | ModernBERT-large | 421M | 1024 | 特定 typed-decisions 工作流 |

---

##### 1. 英文检查点

加载方式：

```python
import laya

agent = laya.load ("convaiinnovations/laya")
```

特点：

- 英语任务表现较强；
- 默认上下文为 512；
- 在非英语，特别是非拉丁文字上可能严重失效；
- 不能依靠置信度判断它是否读懂了输入。

项目给出的极端例子是：

- 英文模型处理高棉语；
- 准确率为`0.000`；
- 置信度却达到`0.952`。

这说明它可能**非常自信地犯错**。

---

##### 2. 多语言检查点

加载方式：

```python
agent_ml = laya.load (
    "convaiinnovations/laya",
    subfolder="multilingual"
)
```

特点：

- 支持 100 多种语言；
- 采用 mmBERT-base；
- 参数量约 322M；
- 默认上下文 1024；
- 在项目基准中速度比英文模型更快；
- 多语言能力明显强于英文检查点；
- 英语任务上的表现通常略弱于英文检查点。

项目基准中，可用语言数的定义是 “准确率超过随机水平 3 倍”：

- 英文检查点：51 种语言中 23 种可用；
- 多语言检查点：51 种语言中 45 种可用；
- Router：51 种语言中 45 种可用。

需要特别注意：README 表示多语言检查点发布时没有完整拟合温度参数。如果业务依赖其概率值，应使用自己的验证集重新校准。

---

##### 3. Typed Decisions 检查点

加载方式：

```python
agent_td = laya.load (
    "convaiinnovations/laya",
    subfolder="typed-decisions"
)
```

这个检查点面向项目的 typed-decisions 工作流做过专项微调。

它在该基准上的表现明显高于两个基础检查点：

| 模型 | 准确率 |
|---|---:|
| `laya-typed-decisions` | 0.766 |
| 英文基础模型 | 0.362 |
| 多语言基础模型 | 约 0.342 |
| 多数类基线 | 0.461 |
| 随机猜测 | 0.318 |

这组数据说明两件事：

1. Laya 的模型架构可以通过专项训练获得较好的任务能力；
2. 基础模型并不是强大的通用零样本决策器。

`0.766`并非基础模型开箱即用的结果，而是使用该 typed-decisions 基准训练集微调后的结果。因此，它更能证明 “可专业化能力”，不能直接证明在任意新业务上都有`76.6%`准确率。

---

#### 六、Router 路由系统

Router 是 Laya 整个系统里非常关键的组件。

推荐入口：

```python
from laya import Router

router = Router (preload=True)
```

GPU：

```python
router = Router (
    preload=True,
    device="cuda"
)
```

调用：

```python
result = router.predict (state, questions)
```

---

##### 1. Router 为什么必要

英文模型在英语上通常更好，多语言模型在非英语上更稳。问题是，模型即便读不懂一种语言，也可能返回很高置信度。

因此不能采用下面这种做法：

```text
先让英文模型预测
    ↓
如果置信度低，再换多语言模型
```

因为英文模型在高棉语等输入上可能 “高置信度、零准确率”。

正确做法是：

```text
先检测文字和语言
    ↓
再决定调用哪个模型
    ↓
最后执行模型前向传播
```

Router 的价值就在于**推理前路由**。

---

##### 2. Router 的路由过程

按照 README，Router 会在不执行神经网络前向传播的情况下，使用纯 Python 完成：

- 文字脚本检测；
- 拉丁文字比例分析；
- 语言识别；
- 检查点选择。

例如：

```python
decision = router.route (
    {"body": "Der Kunde wurde zweimal belastet"},
    questions
)

print (decision.reason)
```

可能返回：

```text
Latin script but language looks like 'de', not English
```

对天城文等非拉丁文字，路由原因可能是：

```text
non-Latin script (devanagari, 100% of letters);
the English checkpoint cannot read it
```

Router 的检测耗时低于约`0.5 ms`，远低于模型推理本身。

公开页面清楚描述了英文与多语言模型之间的语言路由；对于 typed-decisions 检查点的全部自动选择条件，当前页面没有完整说明。若业务明确需要该检查点，建议显式指定：

```python
result = router.predict (
    state,
    questions,
    model="typed-decisions"
)
```

---

##### 3. 路由元数据

每个结果都附带路由信息：

```python
result ["routing"]
```

示例：

```python
{
    "model": "multilingual",
    "repo": "convaiinnovations/laya/multilingual",
    "reason": (
        "non-Latin script"
        "(devanagari, 100% of letters);"
        "the English checkpoint cannot read it"
    )
}
```

这对生产审计很重要。建议日志中至少记录：

- 使用的模型；
- 模型仓库或版本；
- 路由原因；
- 输入语言；
- 结果置信度；
- 最终人工结论。

---

#### 七、模型加载与内存管理

模型的推理速度和加载速度是两件完全不同的事情。

##### 1. 冷加载

如果模型没有驻留内存，构建检查点可能需要数秒。

README 报告的中位重载时间为：

- CPU：约`7.4 秒`；
- T4 GPU：约`10.3 秒`。

所以宣传中的约 33 毫秒延迟，是指：

- 模型已经加载；
- 一般使用 T4 GPU；
- 执行的是热推理；
- 不包含冷启动和模型下载。

---

##### 2. 默认惰性加载

```python
router = Router ()
```

默认通常只保留一个热模型，即：

```text
max_loaded = 1
```

如果请求流量在英语和其他语言之间来回切换，就可能出现：

```text
英语请求 → 加载英文模型
中文请求 → 卸载英文，加载多语言模型
英语请求 → 卸载多语言，重新加载英文模型
```

这样每次语言切换都可能产生 7～10 秒的模型重载延迟。

---

##### 3. 全部预加载

生产环境推荐：

```python
router = Router (preload=True)
```

GPU：

```python
router = Router (
    preload=True,
    device="cuda"
)
```

这样所有需要的检查点常驻内存，语言切换只需要执行亚毫秒级的路由逻辑。

代价是：

- 更高内存或显存占用；
- 更长应用启动时间；
- 多进程时每个进程可能复制一份模型。

项目没有在当前页面给出三个检查点的精确显存总占用，因此部署前应自行测量。

---

##### 4. 只预加载指定模型

如果业务只服务英文与多语言，不需要 typed-decisions：

```python
router = Router (max_loaded=2)
router.preload (["english", "multilingual"])
```

也可以设置保留两个热模型：

```python
router = Router (max_loaded=2)
```

这通常使用 LRU 方式管理常驻模型。

---

##### 5. 挂接已有 Agent

如果项目已经创建了 Agent，可以避免重复加载：

```python
router.attach ("english", existing_agent)
```

这对于控制显存占用很有价值。

---

##### 6. 卸载

```python
router.unload ()
```

可以在应用关闭、模型切换或释放资源时调用。

---

#### 八、端到端推理流程

一次完整的调用可以理解为：

```text
1. 接收 state
2. 接收 questions
3. Router 检测脚本和语言
4. Router 选择检查点
5. 检查检查点是否已加载
6. 必要时加载或从缓存中取出模型
7. 将状态、问题、选项组织为模型输入
8. 编码器执行一次前向传播
9. 各决策原语产生概率或分布
10. 应用已有的校准参数
11. 组装 answers
12. 附加 routing 元数据
13. 返回结构化结果
```

代码示例：

```python
from laya import Router

router = Router (preload=True, device="cuda")

state = {
    "subject": "重复扣款",
    "body": "我被扣了两次钱，请退款，否则我会取消订阅。"
}

questions = {
    "department": {
        "type": "choice",
        "instructions": "应该由哪个部门处理？",
        "criteria": {
            "billing": "付款、扣款、退款和发票",
            "technical": "故障、接口错误和系统异常",
            "sales": "购买、价格和合同",
            "other": "其他请求"
        }
    },
    "refund_requested": {
        "type": "noul",
        "instructions": "用户是否明确要求退款？"
    },
    "churn_risk": {
        "type": "noul",
        "instructions": "用户是否表示要取消服务？"
    }
}

result = router.predict (state, questions)

print (result ["answers"])
print (result ["routing"])
```

#### 九、上下文与 Token 预算

Laya 的一个关键架构限制，是输入 token 预算需要在两部分之间分配：

```text
总上下文预算
    ├── 问题和候选选项预算：head_max_len
    └── 状态或文档预算：max_len - head_max_len
```

---

##### 1. 英文模型默认预算

英文模型默认：

```python
max_len = 512
head_max_len = 192
```

因此大致为：

```text
问题和候选项：192 token
状态或文档：约 320 token
```

如果状态很长，后面的内容可能无法被完整使用。

---

##### 2. 多语言与 Typed Decisions 默认预算

多语言和 typed-decisions 默认上下文为 1024。README 给出的默认问题头预算是：

```python
head_max_len = 256
```

因此大约：

```text
问题和候选项：256 token
状态或文档：约 768 token
```

多语言 mmBERT 编码器通过 RoPE 可以支持更长上下文，最高可扩展到 8192；但实际可用长度还需要考虑：

- 检查点设置；
- 显存；
- 推理延迟；
- 训练时长度分布；
- 业务效果。

能配置更长，不代表模型在超长文本上的效果一定与默认长度相同。

---

#### 十、高基数标签空间问题

Laya 对大量候选项的单个`choice`问题存在明显限制。

例如 Banking77 有 77 个意图标签。默认：

```text
head_max_len = 256
```

扣除其他提示 token 后，每个标签只有大约：

```text
(256 - 16) // 77 ≈ 3～4 token
```

这意味着候选项的描述会被严重压缩，很多标签变得难以区分。

基准结果：

| 模型 | Banking77 |
|---|---:|
| Jev | 0.870，使用 72 个标签 |
| Laya | 0.425，使用 77 个标签 |

这是架构上的 token 预算问题，不只是模型 “没训练好”。

---

##### 解决方案一：扩大预算

例如：

```python
agent.cfg ["head_max_len"] = 512
agent.cfg ["max_len"] = 1024
```

也可以在模型和硬件允许时尝试更长上下文。

但调整后必须重新测试：

- 是否截断状态；
- 显存是否足够；
- 推理延迟增加多少；
- 准确率是否真的改善。

README 没有给出扩大预算后 Banking77 的完整对照成绩，所以不能假设调整后一定达到 Jev 的水平。

---

##### 解决方案二：分层分类

如果有 100 个意图，可以先分大类：

```text
第一层：
billing /technical/account /sales/other
```

再根据大类做第二层：

```text
billing：
duplicate_charge /refund/invoice /payment_failed
```

这样每个问题的选项数量更少，也更符合 Laya 的结构。

---

#### 十一、非自回归设计与性能

Laya 不逐 token 生成答案，而是直接计算决策结果，所以延迟不随输出文本长度增长。

项目在单块 T4 GPU 上报告：

| 单次调用中的问题数 | 英文模型 | 多语言模型 |
|---:|---:|---:|
| 1 | 39.5 ms | 32.8 ms |
| 5 | 84.5 ms | 40.1 ms |
| 10 | 158.6 ms | 72.3 ms |
| 50 | 771 ms | 337 ms |

十个问题时：

- 英文模型约`15.9 ms / 问题`；
- 多语言模型约`7.2 ms / 问题`。

这说明一次状态上批量评估多个问题，比每个问题单独调用更高效。

报告的吞吐量为：

```text
103～332 个问题 / 秒
```

需要注意这里的 “批处理” 主要是指**一次调用中包含多个问题**。跨请求动态批处理是否存在，以及并发情况下如何调度，应根据 SDK 源码和实际压测确认。

预加载后的 CPU 延迟在 README 中约为：

```text
193～464 ms
```

所以 CPU 可以使用，但无法达到 T4 上约 33 毫秒的速度。

---

#### 十二、RLCD 训练系统

项目称 Laya 使用 RLCD 训练，并结合：

- 严格适当评分规则；
- GRPO 风格策略梯度；
- 概率分布奖励；
- 后续温度校准。

README 没有在当前页面完整列出所有数学公式，但可以解释其核心意图。

---

##### 1. 为什么使用严格适当评分规则

普通分类训练往往只关心：

```text
最高概率的标签是否正确
```

但生产决策不仅关心标签，还关心概率：

```text
0.95 是否真的比 0.60 更可靠？
```

严格适当评分规则的核心性质是：

> 当模型报告其真实相信的概率分布时，其期望得分最高。

它试图防止模型为了获得奖励而随意夸大或压低概率。

例如，一个事件真实发生概率是 70%，理想情况下模型应报告接近：

```text
P (true) = 0.70
```

而不是为了 “看起来坚定” 报告 0.99。

---

##### 2. RLCD 在系统中的作用

按照项目描述，RLCD 用强化学习方式优化结构化决策分布，而不是训练模型生成长文本。

训练目标涉及：

- 正确选择标签；
- 更合理地分配候选项概率；
- 降低错误但高置信的结果；
- 让`choice`、`score`和`noul`输出可以用于下游决策。

但是，采用严格适当评分规则并不意味着发布模型天然校准。README 自己的结果也显示检查点仍然过度自信，因此后处理校准仍然必要。

---

##### 3. 领域微调

项目提供了微调 Notebook：

```text
notebooks/laya_finetune_typed_decisions_2xT4_kaggle.ipynb
```

该流程包括：

1. 构建领域数据集；
2. 使用 RLCD 训练；
3. 使用 proper-scoring-rule 奖励；
4. 执行 GRPO 风格策略梯度；
5. 拟合温度参数；
6. 在验证集上评估；
7. 推送检查点到 Hugging Face Hub。

项目报告的训练规模为：

- 约 30,000 个问题；
- 4 个 epoch；
- 2 张 T4；
- 大约 4～5 小时。

这一流程是 Laya 的核心价值之一，因为项目明确承认：**基础检查点的复杂零样本 typed-decisions 能力不强，主要价值来自领域专业化。**

#### 十三、概率校准系统

Laya 输出概率，但概率是否可信需要通过校准衡量。

---

##### 1. 什么是校准

如果某一批预测的置信度都在 0.8 左右，那么理想情况下，这批预测应有约 80% 是正确的。

如果模型总是输出 0.95，但实际只有 60% 正确，就是过度自信。

---

##### 2. ECE

项目使用 ECE，即 Expected Calibration Error，衡量预测置信度与实际正确率之间的偏差。

一般来说：

```text
ECE 越低越好
```

项目报告，在留出数据上为每个：

```text
问题类型 × 选项数量
```

拟合温度参数后：

| 模型 | 校准前 ECE | 校准后 ECE |
|---|---:|---:|
| 英文检查点 | 0.466 | 0.081 |
| 多语言检查点 | 0.314 | 0.106 |

这表示后处理温度缩放明显改善了概率质量。

不过，typed-decisions 的另一张基准表列出的原始 ECE 是：

| 模型 | ECE |
|---|---:|
| typed-decisions | 0.213 |
| 英文基础模型 | 0.175 |
| 多语言基础模型 | 0.285 |
| Jev | 0.144 |

这些数字来自不同评估设置，不能简单混为一张表。关键结论是：

- 原始模型仍可能过度自信；
- 温度拟合能明显改善 ECE；
- 多语言发布检查点据称没有附带完整温度拟合；
- 生产阈值必须用自身业务数据验证。

---

##### 3. 温度缩放的作用

温度缩放通常不会改变最高概率标签，而是调整概率分布的尖锐程度。

概念上：

```text
校准前：
billing = 0.98
technical = 0.01
other = 0.01

校准后：
billing = 0.82
technical = 0.09
other = 0.09
```

标签仍然是`billing`，但置信度变得更接近真实正确率。

#### 十四、基准结果如何理解

##### 1. 多语言路由基准

项目报告：

| 任务 | 英文模型 | 多语言模型 | Router |
|---|---:|---:|---:|
| MASSIVE 英语意图 | 0.783 | 0.657 | 0.783 |
| MASSIVE 其他 13 种语言 | 0.306 | 0.451 | 0.451 |
| XNLI 英语 | 0.860 | 0.843 | 0.860 |
| XNLI 其他 14 种语言 | 0.521 | 0.731 | 0.731 |

这说明 Router 的目标不是创造一个比所有模型都强的新模型，而是为不同输入选择更合适的检查点：

```text
英语 → 英文模型
其他语言 → 多语言模型
```

因此 Router 的结果通常接近对应场景中更好的那个模型。

---

##### 2. 英文任务

项目报告：

| 任务 | 英文模型 | 多语言模型 |
|---|---:|---:|
| AG News | 0.947 | 0.937 |
| BoolQ | 0.830 | 0.787 |
| DAIR Emotion | 0.573 | 0.513 |
| Prompt Injection | 0.698 | 0.578 |
| SST-5 有序评分 | 0.372 | 0.282 |

其中：

- AG News、BoolQ 在训练混合中；
- DAIR Emotion、Prompt Injection、SST-5 是留出任务；
- Prompt Injection 的样本量只有 116；
- `0.698`的注入检测准确率并不足以让它单独成为高风险安全防线。

---

##### 3. Typed Decisions 基准

400 个案例、2,000 个决策、四个工作流：

| 模型 | Accuracy | Soft Accuracy | Brier | ECE | Score MAE |
|---|---:|---:|---:|---:|---:|
| typed-decisions | 0.766 | 0.471 | 0.062 | 0.213 | 0.242 |
| 英文基础模型 | 0.362 | 0.332 | 0.316 | 0.175 | 0.694 |
| 多语言基础模型 | 0.342 | 0.326 | 0.439 | 0.285 | 0.687 |
| Jev 1.13.0 | 0.727 | 0.580 | 0.148 | 0.144 | 0.391 |
| 教师自一致性上限 | 0.735 | — | — | — | — |
| 多数类 | 0.461 | — | — | — | — |
| 随机猜测 | 0.318 | — | — | — | — |

typed-decisions 检查点的优势：

- Argmax 准确率更高；
- Brier 分数更好；
- score MAE 更低；
- 在四个工作流上均胜出。

它的不足：

- Soft Accuracy 低于 Jev；
- 原始 ECE 高于 Jev；
- 需要温度校准；
- 成绩来自该基准训练集上的专项微调。

按原语：

| 原语 | 准确率 |
|---|---:|
| `noul` | 0.857 |

项目报告 Laya 单问题推理约比 Jev 快 7.8 倍，但 README 同时说明：

- Jev 数字来自第三方发布；
- Laya 团队没有 TypeSafe API 访问权限；
- 双方样本量和提示可能不同；

#### 十七、如何将概率变成业务动作

不要直接采用：

```python
if probability > 0.5:
    execute_irreversible_action ()
```

更合理的是按风险分层。

```python
department = result ["answers"]["department"]["choice"]
confidence = result ["answers"]["department"]["confidence"]
refund_prob = result ["answers"]["refund_requested"]["noul"]

if confidence >= 0.90:
    assign_ticket (department)
elif confidence >= 0.70:
    suggest_department_to_human (department)
else:
    send_to_manual_triage ()

if refund_prob >= 0.90:
    create_refund_review_case ()
```

对于不可逆或高风险动作，例如：

- 自动退款；
- 封禁账户；
- 拒绝交易；
- 删除内容；
- 报警；
- 法律合规决定；

即便置信度很高，也应保留规则验证或人工审核。

#### 十八、服务化时的注意事项

##### 1. 模型应作为进程级单例

不要这样做：

```python
@app.post ("/predict")
def predict (request):
    router = Router (preload=True)
    return router.predict (...)
```

因为每个请求都会重复加载模型。

应在应用启动时创建一次：

```python
router = Router (preload=True, device="cuda")
```

然后所有请求复用。

---

##### 2. 多进程会复制模型

例如使用：

```bash
uvicorn app:app --workers 4
```

通常意味着四个进程各自持有模型，可能导致显存不足。

GPU 推理服务应先考虑：

- 单推理进程；
- 外部请求队列；
- 并发限制；
- 受控批处理；
- 多 GPU 时按 GPU 划分 worker。

---

##### 3. 需要记录模型版本

生产日志应包含：

```json
{
  "model": "multilingual",
  "repository": "convaiinnovations/laya/multilingual",
  "model_revision": "固定 commit 或 tag",
  "routing_reason": "non-Latin script",
  "question_schema_version": "triage-v3",
  "confidence": 0.87,
  "final_human_label": "billing"
}
```

如果始终使用浮动的最新版本，模型升级后可能难以解释行为变化。

#### 十九、Laya 的主要优势

##### 1. 输出天然结构化

无需从自然语言中解析：

```text
“我认为可能是 billing，置信度较高……”
```

而是直接得到：

```python
{
    "choice": "billing",
    "confidence": 0.94
}
```

---

##### 2. 一次处理多个判断

同一个工单可以同时判断：

- 部门；
- 紧急度；
- 退款请求；
- 流失风险；
- 是否需要人工处理。

这比反复调用生成式模型更适合高吞吐分类服务。

---

##### 3. 推理速度快

热加载 T4 环境下：

- 单问题约 33～40 毫秒；
- 十个问题约 72～159 毫秒；
- 多语言模型批量可达约 7.2 毫秒 / 问题。

---

##### 4. 可自托管

许可证为：

```text
Apache 2.0
```

模型可部署在自己的服务器中。相比外部闭源 API：

- 数据可以留在内部网络；
- 没有按 token 计费；
- 可固定版本；
- 可以领域微调；
- 可以自行控制校准与阈值。

但 “自托管成本为 0” 只意味着没有外部 API 单次调用费，并不意味着没有 GPU、运维、存储和监控成本。

---

##### 5. 可解释的路由元数据

Router 会告诉你：

- 选择了哪个模型；
- 为什么选择；
- 使用了哪个仓库。

这比隐式地把所有输入送到同一个模型更容易审计。

---

#### 二十、Laya 的主要局限

##### 1. 基础模型不是强零样本决策引擎

基础检查点在 typed-decisions 基准上约为：

```text
0.34～0.36
```

而：

```text
随机基线：0.318
多数类基线：0.461
```

也就是说，在该复杂任务上，基础模型甚至低于多数类策略。

真正较好的`0.766`来自专项微调检查点。

---

##### 2. 高置信度不等于正确

英文模型处理不支持的文字时，可能：

```text
准确率 = 0
置信度 = 95.2%
```

所以必须结合：

- 推理前语言路由；
- 领域校准；
- 分布外检测；
- 人工兜底。

---

##### 3. 多语言模型的英语能力略弱

多语言能力与英语专项能力之间存在权衡，因此 Router 比 “所有输入都用多语言模型” 更合理。

---

##### 4. 高选项数表现不佳

默认配置下，50 个以上选项应谨慎。77 个标签会受到明显 token 预算限制。

---

##### 5. `score`是较弱原语

有序评分比二分类和一般选择题更难，重要评分任务需要专项训练。

---

##### 6. 上下文有限

Laya 不是长文档理解系统。长文档可能需要：

- 提取相关字段；
- 分块；
- 规则预处理；
- 先摘要再判断；
- 将结果聚合。

---

##### 7. 不进行多步推理

Laya 适合快速判断，不适合：

- 复杂数学推导；
- 长链条法律推理；
- 多工具规划；
- 代码生成；
- 需要引用证据的分析报告；
- 复杂代理行为。

这类任务应交给生成式或推理型模型，Laya 可以负责判断是否需要调用这些模型。

---

#### 二十一、最合理的产品定位

综合项目公开数据，Laya 最合理的定位不是：

> 安装后即可对任何业务做高准确率零样本决策。

而是：

> 一个能快速输出结构化概率、支持多语言路由，并可通过领域数据进行专项微调和校准的轻量决策基础设施。

它最适合作为系统中的：

- 第一层分流器；
- 低成本预判器；
- 规则系统补充；
- 大模型调用前置路由器；
- 人工审核排序器；
- 高频结构化分类服务。

不应直接把它当成：

- 最终安全裁决者；
- 通用推理代理；
- 无需验证的风控模型；
- 完全可信的概率来源。

---

#### 二十二、完整使用范式

最推荐的完整生命周期是：

```text
1. 定义业务目标
   ↓
2. 把目标拆成 choice /score/noul
   ↓
3. 设计清晰的 instructions 和 criteria
   ↓
4. 使用 Router 进行语言和检查点路由
   ↓
5. 用历史业务数据做离线评估
   ↓
6. 对概率执行温度校准
   ↓
7. 为不同风险等级设置阈值
   ↓
8. 低风险高置信结果自动化
   ↓
9. 低置信或高风险结果转人工
   ↓
10. 保存人工结果作为反馈数据
   ↓
11. 进行领域微调
   ↓
12. 定期监控漂移并重新校准
```

一句话总结整个系统：

> **Laya 把文本或 JSON 状态与一组类型化问题组合起来，由 Router 在推理前选择英文、多语言或专项检查点，再通过一次非自回归前向传播输出 choice、score 和 noul 决策，最后用校准概率、阈值和人工审核驱动真实业务。**

## 深度解读-口播（1）

### 2026-09-30 12:17:55

Laya 想解决的问题，不是让人工智能写出更好的回答，而是让人工智能更快地做出明确决定：这封邮件该交给谁，工单有多紧急，用户有没有流失风险。理解这个项目，最重要的是分清两件事：它确实能很快地输出结构化判断，但这不等于它面对任何新任务，都能直接做出可靠决定。

我们先看一个具体场景。

一位客户发来邮件，说三月份被重复扣款，要求今天退还多收的钱，否则就取消订阅。传统生成式模型可能会先写一段分析，再输出结论。业务系统还要从这段文字里提取部门、紧急程度和退款要求。

Laya 的做法不同。你先定义好要问的问题，以及每个问题允许怎样回答。模型读取邮件后，直接返回对应的判断，不需要生成一段自由文本。

这些判断主要分成三类。

第一类是从给定选项里做选择。比如，这封邮件应该交给财务、技术、销售，还是其他部门。

第二类是按等级打分。比如，把紧急程度分成“不紧急”“需要尽快处理”和“有关键期限或阻塞问题”，再输出预期等级。

第三类是判断一个条件成立的概率。比如，客户是否明确要求退款，是否威胁取消订阅。

这样一来，结果可以直接进入业务流程，不必再解析一段自然语言。不过，项目介绍里说“不生成文字，就没有幻觉”，需要限定理解：它避免了自由生成带来的编造内容和格式问题，但分类、评分和概率判断，仍然可能出错。

Laya 的速度优势，也来自这种工作方式。它不逐字生成答案，而是通过一次模型前向计算输出判断。项目在英伟达 T 四显卡上的测试显示，多语言模型回答一个问题约需三十三毫秒；十个问题一起处理时，平均每个问题约七点二毫秒。

这里要记住比较前提：这是特定显卡和测试设置下的结果，不是任何电脑、任何部署方式都能达到的延迟。

接下来是这个项目很有价值的一点：它不只提供一个模型，还提供一个路由器，负责先判断请求适合交给哪个模型。

项目有英文、多语言和专门针对结构化决策任务微调的三个模型版本。这里的微调，就是用特定任务的数据继续训练，让模型适应那类判断。

为什么要先选模型，而不是让模型回答之后，再看置信度够不够高？

因为模型可能非常自信地犯错。

项目测试中，英文模型面对高棉语任务，准确率为零，却给出了百分之九十五点二的置信度。这意味着，如果系统只采用“置信度高就自动处理”的规则，就会放行一批看似可靠、实际错误的判断。

路由器因此在模型计算之前，先识别文字系统和语言。它不仅能区分英文与非拉丁文字，也会检查使用拉丁字母的内容是不是德语等其他语言，再选择合适的模型。

项目宣称多语言模型覆盖一百多种语言，但覆盖范围不等于每种语言都同样可靠。在实际测试的五十一种语言中，有四十五种达到了项目设定的可用标准：准确率超过随机猜测的三倍。

所以，多语言支持不能只看宣传中的语言数量，还要看具体语言上的测试结果。路由的意义，也不只是提速，而是避免把输入交给明显不适合的模型。

不过，部署时还有一个容易忽略的条件。

模型判断本身只需几十毫秒，不代表整个请求也只需几十毫秒。路由器默认只保留一个已加载模型。如果请求不断在不同语言之间切换，就可能反复卸载、重新加载模型。

项目测得，这种重新加载的中位耗时，在中央处理器上约七点四秒，在 T 四显卡上约十点三秒。原本几十毫秒的判断，就可能变成数秒的等待。

生产服务如果需要频繁切换模型，应提前把需要的模型加载到内存或显存中，或者允许同时保留多个模型。代价是占用更多资源，收益是避免语言切换时反复加载。

换句话说，推理速度和服务响应速度不是一回事。要兑现低延迟，部署方式必须配合。

最后，也是使用 Laya 前最需要看清的部分：它的判断能力和概率可靠性，都有边界。

项目有一项包含两千次决策的测试。专门微调后的模型，准确率达到百分之七十六点六。但两个基础模型只有百分之三十几，甚至低于“每次都选最常见答案”所达到的百分之四十六点一。

而且，那项较好的成绩，来自使用该测试任务自身的训练部分进行微调。它不能证明，模型面对一个从未训练过的新业务，也有同样的表现。项目自己也明确承认：Laya 更适合作为一个快速、可进一步专门训练的基础，而不是开箱即用的通用决策引擎。

概率也需要单独验证。

模型输出百分之九十的置信度，理想情况下，意味着大量类似判断中，大约九成是正确的。如果实际正确率远低于九成，模型就是过度自信。

项目采用了鼓励模型报告真实概率的训练方法，但实测显示，基础模型出厂时仍然过度自信。用独立验证数据进行概率校准后，情况才明显改善。多语言模型还没有随附拟合好的校准参数，因此，不能拿到一个概率数字，就直接把它当成可靠的自动化依据。

另一个限制是选项太多。默认设置下，七十七个选项会挤在固定的文本预算里，每个选项只分到大约三到四个词元。词元可以粗略理解为模型处理文字的小单位。选项描述被压缩得太短，就容易失去区别。

对于五十个以上选项的任务，项目建议增加选项的文本预算，或者拆成两步：先选大类，再选细类。这不是单纯调高置信度门槛就能解决的问题。

Laya 最值得记住的，是它把人工智能从“生成一段回答”，变成了“输出可以直接使用的判断”，并通过语言路由避免明显的模型错配。它的低延迟很有吸引力，但可靠性仍然依赖任务微调、概率校准和正确部署。真正需要验证的，不只是模型能多快给出答案，而是这个答案能不能放心地触发下一步行动。
