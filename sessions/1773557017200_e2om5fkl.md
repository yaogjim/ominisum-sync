### Autonomous context compression

https://x.com/masondrxy/status/2031798630177251514

**Mason Daugherty**

### Autonomous context compression

TL;DR: We’ve added a tool to the

[Deep Agents SDK](https://docs.langchain.com/oss/python/deepagents/overview) (Python) and

[CLI](https://docs.langchain.com/oss/python/deepagents/cli/overview)

that allows models to compress their own context windows at opportune times.

---

#### Motivation

[Context compression](https://blog.langchain.com/context-management-for-deepagents/) is an action that reduces the information in an agent’s working memory. Older messages are replaced by a summary or condensed representation of an agent’s progress that preserves what’s relevant to a task. This action is often necessary to accommodate finite context windows and reduce

[context rot](https://research.trychroma.com/context-rot)

.

Agent harnesses often control this by compacting at a fixed token threshold (\`deepagents\` uses

[model profiles](https://docs.langchain.com/oss/python/langchain/models#model-profiles) to compact at 85% of any given model’s context limit). This design is suboptimal because there are good times and bad times to compact:

- It is not ideal to compact when you’re in the middle of a complex refactor;
- It is better to compact when you are starting a new task or otherwise believe that prior context will lose relevance.

Many interactive coding tools feature a \`/compact\` command or similar, which allows users to manually trigger a context compression step at opportune times. We take this one step further in the latest release of \`deepagents\` and expose a tool to the agent that lets it trigger context compression itself. This enables more opportunistic compaction without requiring your application’s users to be aware of finite context windows or issue specific commands.

This tool is currently enabled in

[Deep Agents CLI](https://docs.langchain.com/oss/python/deepagents/cli/overview) and opt-in in the \`deepagents\` SDK.

We are generally bullish on the idea that harnesses should, where possible, “get out of the way” and take advantage of improvements in the underlying reasoning models. This is an instance of

[the bitter lesson](http://www.incompleteideas.net/IncIdeas/BitterLesson.html): can we give agents more control over their own context to avoid tuning their harness by hand?

#### When should we compact?

There is a variety of situations that could warrant a context compression action.

At clean task boundaries:

- A user signals that they are moving on to a new task for which earlier context is likely irrelevant
- The agent has finished a deliverable and the user acknowledges task completion

After extracting a result from a large amount of context:

- The agent has obtained a fact, conclusion, summary, or other result by consuming a significant amount of context, as in a research task

Before consuming a large amount of new context:

- The agent is about to generate a long draft
- The agent is about to read a large amount of new context

Before entering a complex multi-step process:

- The agent is about to start a lengthy refactor, migration, multi-file edit, or incident response
- The agent has produced a plan and is about to begin executing the steps

A decision has been made that supersedes prior context:

- New requirements have come to light that invalidate previous context
- There are many tangents or dead-ends that can be reduced to a summary

Enumerating all possible scenarios is not practical, but our observation is that people and LLMs can identify these scenarios and compact at opportune times, saving the need for a compaction step later on when the context window is nearing its limit. You can read the guidance we provide the model around this tool in its

[system prompt](https://github.com/langchain-ai/deepagents/blob/537ed6cf153f9f6e50546c9d8674c32587540942/libs/deepagents/deepagents/middleware/summarization.py#L91).

#### What happens when the tool is called?

The tool is parametrized the same as the existing Deep Agents

[summarization middleware](https://docs.langchain.com/oss/python/deepagents/harness#summarization): we retain recent messages (10% of available context) and summarize what comes before. Recent messages, including the call to the compaction tool and associated response, are retained in the recent context.

![Image](https://pbs.twimg.com/media/HDJhyofbwAAINV-?format=jpg&name=large)

See

[example trace](https://smith.langchain.com/public/0ff5b066-7377-4922-9269-927e29bd4aba/r).

#### How to use

The tool is implemented as a separate middleware, so you can enable it by adding it to the middleware list in \`create\_deep\_agent\`:

```python
from deepagents import create_deep_agent
from deepagents.backends import StateBackend
from deepagents.middleware.summarization import (
    create_summarization_tool_middleware,
)

backend = StateBackend  # if using default backend

model = "openai:gpt-5.4"
agent = create_deep_agent(
    model=model,
    middleware=[
        create_summarization_tool_middleware(model, backend),
    ],
)
```

See the SDK

[docs](https://docs.langchain.com/oss/python/deepagents/harness#context-management) for more details.

In the CLI, simply call \`/compact\` when you’re ready to trim context or move onto a new task.

#### Our experience with this feature

We tuned this feature to be conservative. Deep Agents

[preserves all conversation history](https://docs.langchain.com/oss/python/deepagents/harness#summarization) in its virtual filesystem, allowing for recovery of context post-summarization, but an erroneous context compression step is disruptive. We tested:

- A custom evaluation suite, in which we used (our own)
  [LangSmith traces](https://docs.langchain.com/langsmith/observability) to inject follow-up prompts to threads that do and do not warrant compaction;
- Terminal-bench-2, in which we did not observe any instances of autonomous compaction;
- Our own coding tasks in
  [Deep Agents CLI](https://docs.langchain.com/oss/python/deepagents/cli/overview).

In practice agents are conservative about triggering compaction, but when they do they tend to choose moments where it clearly improves the workflow.

Autonomous context compression is a small feature, but it points at a broader direction for agent design: giving models more control over their own working memory and fewer rigid, hand-tuned rules in the harness. If you’re building long-running or interactive agents, try it out in the Deep Agents SDK or CLI and let us know your feedback and what patterns you’d like to see it handle next.

#### 一、先说结论：这两份内容其实在讲同一件事

它们共同讨论的是一个 AI 编程/Agent 系统里非常核心、但经常被忽视的问题：

> **AI 不是“突然变笨了”，很多时候是它的“工作记忆”在错误的时机被压缩了。**

也就是说，当你和 AI 正在推进一个复杂任务——比如重构、多文件修改、迁移、研究总结——AI 需要依赖前面大量上下文来保持一致性。  
但模型的 context window（上下文窗口）是有限的，一旦接近上限，系统往往会自动做一件事：

> **压缩旧对话，把前面的长内容变成摘要。**

问题不在于“压缩”本身，而在于：

> **压缩发生的时机，常常不对。**

如果它恰好发生在复杂任务执行中途，之前讨论好的关键约束、设计方案、已否定路线、边界条件，就可能在压缩中被弱化、遗漏，最终导致 AI：

- 忘记刚刚讨论过的架构决策
- 把否掉的方案又提出来
- 改坏之前已经统一好的接口
- 在 refactor 中途“失忆”
- 明明 10 分钟前说好 A，现在又开始往 B 方向改

这正是 Leo 那条内容所说的“最尴尬的时刻”。

---

#### 二、两份内容分别贡献了什么

##### 内容 1（Leo）的价值：指出了“现象”和“使用者视角的直觉”

Leo 用非常贴近开发者体验的话，点出了问题的本质：

- 你不是感觉错了
- 不是模型突然智商掉线
- 很多时候是因为 **context compression（上下文压缩）在错误时间点触发了**

他进一步给出一个很实用的判断：

> **“什么时候压缩”本身，不应该只是一个系统层面的被动阈值动作，而应该是一个任务管理决策。**

比如这些时机更适合压缩：

- 一个任务做完了
- 已经拿到了阶段性结论
- 要切换到新任务了
- 要从一个上下文块进入另一个上下文块了

Leo 的实践建议也很直接：

> 给 Claude Code 之类的工具加一条规则：每完成一个任务，主动判断要不要压缩，而不是等系统强制压缩。

这个建议的本质是：

- 从“被动撑爆”
- 变成“主动整理”

这是非常典型的**工程化使用 AI 的思路**。

---

##### 内容 2（Deep Agents / Mason）的价值：给出了更系统的机制设计

第二份内容比 Leo 更底层、更系统，讲的是 Deep Agents 新增的一个能力：

> **让 agent 自己拥有触发 context compression 的工具。**

也就是说，不再只是由外部 harness（代理框架/调度外壳）在 token 到了 85% 时机械压缩，  
而是让模型自己在“它认为合适的时候”触发压缩。

这背后的设计逻辑非常清晰：

###### 传统做法
- 到阈值了就压缩
- 优点：简单、稳定、好实现
- 缺点：不知道当前任务处于什么阶段

###### 新做法
- 给 agent 一个“可以自己压缩上下文”的工具
- 让它在任务边界、结论提炼完成、准备开始大任务前等时刻主动压缩
- 优点：更符合任务结构
- 风险：压错了会打断工作流，所以要保守

Mason 的文章里列得很清楚：**适合压缩的场景**主要包括：

###### 1）干净的任务边界
- 用户明确切换新任务
- 一个交付物已完成，并被用户确认完成

###### 2）从大量上下文中提炼出结果之后
- 已经读了很多资料并得出结论
- 已经做完研究并提炼出摘要

###### 3）在即将消耗大量新上下文之前
- 要开始生成长文档
- 要读取大量新材料

###### 4）在开始复杂多步骤流程之前
- 即将开始大重构
- 即将开始迁移
- 即将开始多文件编辑
- 已经做好计划，准备执行

###### 5）当新决策覆盖了旧上下文时
- 新需求推翻了旧设定
- 之前有很多分叉、死路、试错，已经可以归纳收束

这其实是在把“压缩”从一个**被动内存管理动作**，升级成一个**任务编排动作**。

---

#### 三、两份内容合起来，揭示了一个更深层的问题

这不是一个“小功能优化”，而是在讨论：

> **Agent 的工作记忆到底应该由谁管理？**

传统方式里，记忆管理主要由外部系统控制：

- 上下文快满了，压缩
- 保留最近多少消息
- 旧消息统一摘要

这种方式本质上是**框架中心（harness-centric）**的。

而 Deep Agents 想推进的是一种更“模型中心”的思路：

> 尽量让模型自己参与管理自己的工作记忆。

这背后对应的是 Mason 提到的一个观点：

> harness 应该尽量“get out of the way”（别挡路），更多利用底层推理模型自身能力。

也可以理解为：

- 以前：人/框架替模型规定很多死规则
- 现在：给模型更多可调用工具，让它自己判断

这很符合当下 agent 设计的一个大趋势：

##### 从“硬编码流程”
走向
##### “模型主导的策略执行”

上下文压缩只是一个例子。  
未来同类问题还包括：

- 什么时候该查资料
- 什么时候该写计划
- 什么时候该暂停执行向用户确认
- 什么时候该缓存中间结果
- 什么时候该清理无关分支
- 什么时候该把决策写入长期记忆

所以，这个功能虽然表面上很小，但其实是在回答一个更大的方向问题：

> **Agent 不只是“会生成答案”，而是开始管理自己的认知过程。**

---

#### 四、为什么“错误时机的压缩”会这么伤

这个问题值得单独讲清楚，因为它是理解全文的关键。

AI 在复杂任务里并不是靠“真正理解全局”稳定推进的，它很大程度依赖于：

- 当前上下文中有哪些信息仍然可见
- 最近消息保留了哪些细节
- 摘要是否准确保留了关键约束

而复杂重构类任务往往有很多信息并不是“显性需求”，而是**对话中逐渐形成的决策背景**：

比如：

- “这个接口名不能动，因为线上依赖很多”
- “这次先不要动 DB schema”
- “之前讨论过，不采用事件总线方案”
- “优先兼容旧模块，性能优化第二阶段再做”
- “这里看起来重复，但实际上是为了隔离租户逻辑”

这些信息的特点是：

1. 它们非常重要  
2. 但往往不一定写在最终任务描述里  
3. 很可能只存在于前面几轮讨论中  
4. 一旦被压缩得太粗，就容易丢

所以压缩最怕的不是“少一点信息”，而是：

> **把真正关键的上下文，压成了模糊的、无判别力的摘要。**

例如原来是：

- 方案 A 被明确否定，因为迁移成本太高
- 方案 B 保留，因为兼容性最好

压缩后可能变成：

- 讨论过多种方案，最终选择兼容性优先的方向

这听起来没错，但已经失去了可执行的约束强度。  
于是 AI 后面又可能重新把 A 提出来。

这就是为什么用户体感会是：

> “它怎么把刚讨论好的东西忘了？”

实际上不是完全忘了，而是**被压缩成了不够精确的抽象层**。

---

#### 五、这件事本质上是“记忆管理问题”，不是单纯“模型能力问题”

很多人遇到这种情况，第一反应是：

- 模型不够聪明
- 模型推理差
- 新版本变笨了

但这两份内容都在提醒我们：

> 这类问题经常不是“智力问题”，而是“记忆调度问题”。

可以类比成人：

- 不是你不会做事
- 是你开会记录在最关键那一页被人总结成了一句废话

或者：

- 不是工程师不会重构
- 是 PM 把已经拍板的需求在整理纪要时写丢了

所以很多时候，提升 AI 编程体验，不一定先靠“更大的模型”，而是靠：

- 更好的上下文管理
- 更合理的任务边界
- 更明确的阶段性总结
- 更好的外部记忆结构
- 更合适的压缩时机

这也是热门回复里有人提到的那些经验为什么有效：

- 幻觉严重时新开窗口
- 把工作内容输出为外部文件
- 拆成小任务
- 用 SDD/Task 文件把状态外化

这些方法的共同点都是：

> **不要把全部关键状态都赌在当前对话窗口里。**

---

#### 六、Deep Agents 提出的方案，先进在哪

它先进的点不只是“能自动 compact”，而是它重新定义了 compact 的角色。

以前 compact 是：

- 被动回收内存
- 一种系统级 housekeeping

现在 compact 变成：

- 主动整理工作记忆
- 一种任务推进策略

这种变化很重要。

##### 以前的压缩逻辑像什么？
像手机提示你“存储快满了，自动清理缓存”。

##### 现在的压缩逻辑像什么？
像一个熟练工程师在做项目时主动整理笔记：

- 这个任务结束了，归档一下
- 这些试错已经有结论了，提炼成原则
- 下面要开新阶段了，先把旧阶段收束
- 马上要读很多新内容，先腾出认知空间

这就是“自主压缩”真正聪明的地方。

---

#### 七、但这套机制也有明显边界和风险

Mason 也很谨慎，明确说他们把这个功能调得很保守。原因是：

> **压缩一旦做错，比不压缩更糟。**

因为错误压缩会导致：

- 关键约束被摘要丢失
- 用户和 AI 之间的共享语境被破坏
- 后续执行偏航
- 用户必须重新“喂上下文”

所以这个功能不是“越积极越好”，而是：

> **宁可少压，也不要错压。**

他们测试里也提到，agent 实际上触发压缩是比较保守的，甚至在 terminal-bench-2 中没有观察到自主压缩实例。这说明：

- 模型具备判断能力
- 但目前仍然不够稳定到可以很激进地管理记忆
- 所以现阶段更像“在明显合适的时候帮一把”

这也解释了热门回复里有人的担忧：  
当前 AI 的“这种层次的思考”可能还不够强，最好有可视化侧栏，让用户确认压缩内容。

这个观点很有价值，因为它指出一个现实：

> **上下文管理不应完全黑箱化。**

用户脑中其实有大量“已经默认决定”的东西：

- 某个方向已经放弃
- 某个约束已经不重要
- 某个试验只是中间过程
- 某个问题后面再说

这些信息，用户往往不会逐条告诉 AI，  
但人自己是知道“该忘什么”和“不能忘什么”的。

AI 如果没有与用户共同维护这套记忆状态，就很容易压错。

---

#### 八、因此，最理想的未来可能不是“全自动压缩”，而是“半自动、可协作的记忆管理”

综合两份内容和回复区讨论，可以提炼出一个更成熟的方向：

##### 最优解可能不是：
- 全靠系统阈值自动压缩  
也不是
- 全靠模型自己决定压缩

##### 而是：
**模型判断 + 用户可见 + 外部状态文件 + 必要时人工确认**

也就是一种“协同式记忆管理”。

可以想象未来更好的 AI 编程界面应该有：

###### 1）可视化记忆面板
显示：
- 当前任务是什么
- 已确认的决策有哪些
- 已废弃方案有哪些
- 下一个执行阶段是什么
- 哪些内容会在压缩后保留

###### 2）任务边界化管理
每个任务有独立的：
- 目标
- 决策
- 约束
- 产出
- 状态摘要

###### 3）压缩前预览
AI 可以说：
- “我准备压缩上下文，保留以下关键决策，是否继续？”

###### 4）外部持久化记忆
关键内容不只存在聊天里，而要写入：
- spec
- task list
- decision log
- migration plan
- ADR（架构决策记录）
- scratchpad / state file

这才是真正可靠的长程协作方式。

---

#### 九、给普通用户的通俗解读：你该怎么理解这件事

一句话解释：

> **AI 聊天窗口不是它的大脑，更像它眼前的工作台。工作台满了，它会收拾；但如果在你做精密手术时乱收拾，就会出事。**

所以你和 AI 协作时，最重要的不是只会“提问”，而是要会：

- 分阶段工作
- 在节点处总结
- 把关键决策外化
- 主动重置/压缩上下文

你可以把 AI 使用方式，从“随便聊”升级成“项目协作”。

---

#### 十、如果你在做 AI 编程，这里有一套非常实用的操作原则

##### 1）把“任务完成时总结”变成习惯
每完成一个阶段，让 AI 输出：

- 已完成事项
- 关键设计决策
- 明确不做的内容
- 下一阶段计划
- 风险/待确认点

这样就算压缩发生，也更容易保住核心信息。

---

##### 2）复杂任务前，先产出 plan，再开始执行
例如：

- 重构目标
- 不可破坏的约束
- 文件范围
- 分步执行顺序
- 验收标准

因为“计划”本身就是最好的压缩锚点。

---

##### 3）把关键决策写到外部文件，不要只放在对话里
例如建立：

- `TASK.md`
- `DECISIONS.md`
- `MIGRATION_PLAN.md`
- `ARCHITECTURE_NOTES.md`

把下面这些写进去：

- 为什么选这个方案
- 哪些方案被否掉了
- 不要碰哪些模块
- 兼容性要求
- 当前进度

这样上下文压缩后，AI 还能重新读回来。

---

##### 4）任务切换时主动 compact / reset
不要把完全不同的任务混在一个长线程里。

更好的方式是：

- 一个任务收尾
- 总结并外化
- 再开新任务

这样 AI 的上下文会更干净。

---

##### 5）对“中途失忆”保持敏感
一旦发现 AI 开始：

- 重复被否决方案
- 忽略关键约束
- 偏离计划
- 改动不再连贯

就不要继续硬推。  
应立刻：

- 停下来总结当前状态
- 重申关键约束
- 必要时新开窗口
- 从外部任务文件重新加载状态

---

##### 6）用“小任务串联”，不要一次赌大任务
与其说：

- “帮我把整个系统重构完”

不如拆成：

- 第一步：梳理当前结构与约束
- 第二步：提出重构方案并比较
- 第三步：确认选型
- 第四步：先改路由层
- 第五步：再改 service 层
- 第六步：补测试与回归检查

这样上下文压力会小很多。

---

#### 十一、如果你是做 Agent / AI 产品的人，这里的产品启发很大

这两份内容对产品设计者尤其有启发。几个核心点：

##### 1）不要只按 token 阈值做机械压缩
因为 token 阈值与任务结构没有直接关系。

---

##### 2）压缩应该是“任务语义感知”的
也就是系统要知道：

- 现在是不是阶段切换
- 是否已经形成结论
- 是否要开始新的高消耗步骤
- 是否有新需求推翻旧背景

---

##### 3）压缩结果必须可恢复、可追溯
Deep Agents 里提到保留完整历史在虚拟文件系统中，这一点非常重要。  
否则压错一次就不可逆。

---

##### 4）记忆管理最好可见、可编辑、可确认
黑箱记忆管理会严重伤害用户信任。  
用户至少应该知道：

- 什么被保留
- 什么被摘要
- 什么被视为已失效

---

##### 5）“模型自治”不是彻底放权，而是逐步让模型参与系统控制
Autonomous context compression 是一个很典型的起点。  
未来同样可以扩展到：

- 自主存档决策
- 自主生成阶段总结
- 自主创建任务列表
- 自主请求确认
- 自主回溯关键文档

---

#### 十二、可以把这两篇内容浓缩成一句更大的判断

> **AI 编程真正的瓶颈之一，不是生成代码，而是如何在长时间协作中稳定维护“共享工作记忆”。**

谁能更好地解决这个问题，谁的 AI 编程体验就会更接近“靠谱搭档”，而不是“时灵时不灵的聊天机器人”。

---

#### 十三、最后给一个总括版总结

##### 核心观点
- AI 在复杂编程任务中“失忆”，常常不是模型变差，而是上下文压缩时机不对。
- 传统基于 token 阈值的自动压缩机制过于机械。
- 更好的方式是：在任务边界、结论形成后、开始大任务前等“语义上合适”的时机压缩。
- Deep Agents 的新能力，本质上是让 agent 参与管理自己的工作记忆。
- 这是 agent 设计从“外部硬规则”走向“模型主导策略”的一个缩影。

##### 对用户的启示
- 把任务切小
- 在阶段节点总结
- 将关键决策外部化
- 主动而不是被动地处理上下文

##### 对产品的启示
- 记忆管理应任务感知、可恢复、可视化、可协作
- 最佳方向不是纯手动或纯自动，而是人机协同的记忆治理
