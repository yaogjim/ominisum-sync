#### Factory.ai Missions：AI 编码竞争进入“自主工程”阶段

##### 核心观点

Factory.ai 推出的 Missions，代表 AI 编码工具正在从“对话式助手”升级为“自主工程系统”。竞争重点不再是谁补全更快，而是谁能独立完成一个真实、复杂、持续时间很长的工程项目。

##### 为什么值得关注

这套产品最重要的启发是：**没有一个模型能包打天下**。  
Factory.ai 按任务角色分配不同模型：

- 规划用强推理模型
- 写代码用高效编码模型
- 验证用理解精确的模型
- 调研用大上下文模型

本质上，它否定了“单一模型万能论”，强调的是**系统编排能力**，而不是单点模型能力。

##### 产品设计的关键亮点

###### 1. 多模型分工协作

不同环节使用不同模型，各自做最擅长的事。这样比让一个模型从头干到尾更合理，也更接近真实团队分工。

###### 2. 控制长任务中的上下文衰减

每个 worker 启动时都拿到干净上下文，避免长链路任务里注意力下降、质量变差。

###### 3. 验证不只是跑测试

验证层不仅检查代码测试，还会模拟用户操作浏览器，直接检查 UI 是否正常渲染。这说明它关注的是**真实可用性**，而不只是“代码看起来对”。

###### 4. 用 git 管理交接与恢复

整个流程通过 git 协调任务交接，失败后还能自动恢复。这说明产品已经在朝“工程系统”而不是“聊天工具”进化。

##### 数据说明了什么

Factory.ai 披露的数据很有说服力：

- 中位任务耗时 2 小时
- 37% 的任务超过 4 小时
- 14% 的任务超过 24 小时
- 最长任务持续 16 天

这说明它处理的已不是“写个函数”这种短任务，而是**跨模块、跨阶段、长周期**的真实工程工作。  
同时，高 token 消耗也意味着：这种系统的关键不是多说，而是**高密度、高效率地推进任务**。

##### 典型应用场景

它能处理的任务包括：

- 搭建一个 CRM
- 把 PHP 项目迁移到 TypeScript
- 给无文档 API 补全测试覆盖
- 把 COBOL 迁移到 Java Spring Boot

这些通常都是传统团队需要几周完成的项目，说明 AI 编码正在从“辅助编程”走向“承担项目”。

##### 更值得高看的一点

Factory.ai 没有只讲成功案例，也坦诚承认了还没解决的问题，比如：

- 并行度和协调成本如何平衡
- 长链路任务里的错误如何累积

这说明团队是在认真做产品和系统，而不是只做营销叙事。

## 解读（1）

### 2026-03-25 10:15:11

#### 总结

这段内容的核心意思是：

- AI 编程工具正在从“聊天式帮手”升级为“能独立完成项目的工程系统”。
- `Factory.ai Missions` 的关键思路，不是靠一个万能大模型，而是让不同模型分工协作。
- 系统设计重点放在：干净上下文、自动验证、Git 交接、失败恢复。
- 它瞄准的任务也变了：不是写小函数，而是做完整工程项目、迁移旧系统、补测试等复杂任务。
- 真正的竞争点，已经从“谁补全更快”变成“谁能把真实项目自主做完”。

#### 解读

##### 1. 为什么这件事重要？

以前很多 AI 编程产品，本质上还是“高级代码补全”或“会聊天的助手”：

- 你提问，它回答
- 你让它写代码，它写一段
- 出错了，还得你自己接着收拾

而 `Missions` 想解决的是另一类问题：

> 不是“帮我写一点”，而是“把这整个事做完”。

这意味着，AI 不只是生成代码，而是要像一个工程团队一样，完成：

- 规划
- 调研
- 编码
- 测试
- UI 检查
- 出错恢复
- 长时间持续推进

这就是“自主工程系统”和“对话助手”的本质区别。

---

##### 2. 最值得注意的点：不同环节用不同模型

这是文中最有价值的判断之一。

它反对一种常见幻想：

> “只要有一个足够强的大模型，就能包打天下。”

现实往往不是这样。因为不同任务，对模型能力要求完全不同：

- **规划**：需要强推理、会拆任务
- **编码**：需要速度、稳定性、代码习惯好
- **验证**：需要细致、准确、能发现问题
- **调研**：需要大上下文、信息整合能力强

所以最合理的方法不是“一个模型全上”，而是：

> 把模型当成不同岗位的人来用。

这更像真实公司里的分工：
- 有人负责设计方案
- 有人负责实现
- 有人负责测试
- 有人负责查资料

这个思路很朴素，但很可能比“追求单模型最强”更接近产品落地。

---

##### 3. 架构设计为什么高级？

文中提到几个架构细节，说明它不是在“拼 prompt”，而是在认真做工程系统。

###### 干净上下文
每个 worker 启动时拿到的是“干净上下文”。

通俗说，就是：

- 不让一个模型背着超长对话一路跑到底
- 避免上下文太长后，模型变笨、跑偏、偷懒

这是很现实的问题。长任务里，模型常常会出现：

- 忘了最初目标
- 被中间噪音干扰
- 临近上下文上限时草草收尾

所以“不断重置到清爽工作环境”，反而更稳。

###### 验证不只是跑测试
它不只看单元测试过没过，还会模拟用户操作浏览器检查 UI。

这很关键。因为很多 bug 不是代码能不能运行，而是：

- 页面布局错了
- 按钮能点但流程不通
- 功能技术上成功，用户体验上失败

如果 AI 只能写代码、不会验证真实效果，那离“完成任务”还差很远。

###### Git 作为交接机制
通过 Git 协调交接、失败自动恢复，也很聪明。

因为多 agent 协作最怕的是：

- 改乱了
- 覆盖彼此工作
- 失败后没法回退

用 Git 来做状态管理，本质上是把软件工程里最成熟的机制，拿来管理 AI 工作流。这比全靠 prompt 和记忆可靠得多。

---

##### 4. 为什么这些数据说明它不是玩具？

文中几组数据很能说明问题：

- 中位任务跑 `2 小时`
- `37%` 超过 `4 小时`
- `14%` 超过 `24 小时`
- 最长跑了 `16 天`

这说明它处理的不是“一次回答”，而是“长周期工程”。

同时还有两个信号：

- 每分钟消耗大量 token
- 单条消息很长，所以必须“少说话，说重点”

这和很多人对 AI 工具的理解不同。真正做复杂任务时，成本中心不在“能不能答一句漂亮的话”，而在：

- 能不能长时间稳定执行
- 能不能控制上下文成本
- 能不能把信息压缩成有效交接

换句话说，工程型 AI 拼的不是“表达”，而是“持续作业能力”。

---

##### 5. 用例变化，意味着行业进入新阶段

文中举的例子很典型：

- 建 CRM
- PHP 迁移 TypeScript
- 给无文档 API 补测试
- COBOL 迁移到 Java Spring Boot

这些都不是“demo 任务”，而是企业里真实、昂贵、耗时的工作。

这意味着 AI Coding 的战场已经变了：

- 过去比的是：补全快不快、对话顺不顺
- 现在比的是：能不能接住复杂、脏、旧、难的大项目

谁能处理这些任务，谁才更接近真正的生产力工具。

---

##### 6. 为什么“坦诚问题没解决”反而是加分项？

文中提到 Factory 也明确承认还有问题，比如：

- 并行带来的协调成本
- 长链路错误累积
- worker 粒度怎么划分更合理

这恰恰说明他们面对的是“真实世界问题”。

真正复杂的 agent 系统，不会没有问题。越是做深，越会遇到：

- 多个 agent 一起工作，效率未必更高
- 一步小错，可能后面越滚越大
- 分工太细，管理成本高；分工太粗，又容易失控

能把这些讲清楚，比单纯喊“我们全自动了”更可信。

#### 我的意见

##### 结论

我认同这篇内容的判断：

> AI 编程工具的下一阶段，核心不是更像聊天机器人，而是更像“可管理、可验证、可持续执行的工程系统”。

##### 我认为最重要的三点

- **多模型分工** 很可能是未来一段时间的主流路线，比“单模型万能”更现实。
- **验证层** 会成为 AI Coding 产品的真正壁垒，因为“写出来”不等于“做对了”。
- **工程编排能力** 会比模型能力本身越来越重要，尤其是在长任务、复杂项目里。

##### 也要保持冷静

不过，这类系统虽然方向对了，但离“大规模稳定替代工程团队”还有距离，主要卡在：

- 长任务中错误会累积
- 协作越复杂，调度成本越高
- 成本、延迟、稳定性还不够理想
- 很多项目真正难的不是写代码，而是理解业务和做取舍

所以我会把它看成：

> 不是“AI 已经完全会做工程”，而是“AI 开始具备做工程的系统雏形”。

##### 一句话判断

这不是一个“模型更强”的故事，而是一个“AI 软件工程体系开始成型”的信号。

如果你在做 AI Coding 产品，这类思路确实值得认真研究。

  在这种系统里必须“少说话、说重点”，因为上下文和 token 成本都非常昂贵。

##### 5. 应用场景已经不是小修小补，而是完整工程项目

- 典型用例不再是“帮我写个函数”这种零散需求。
- 而是直接面向完整项目，例如：
  - “帮我建一个 `CRM`”
  - “把 `PHP` 项目迁移到 `TypeScript`”
  - “给一个没有文档的 API 补全测试覆盖”
  - “把 `COBOL` 迁移到 `Java Spring Boot`”
- 这些任务原本通常需要传统团队花**几周时间**来完成。
- 也就是说，AI 编码系统的目标，已经从“辅助编程”转向“承担整段工程工作”。

##### 6. 一个加分点：它明确承认问题还没解决

- 作者特别认可 Factory.ai 的一点，是它没有只讲成果，也坦诚列出当前难题：
  - 并行度和协调开销之间如何平衡
  - 长链路任务中的错误如何累积
  - `worker` 粒度如何优化
- 这说明团队是在认真做产品、认真面对现实约束，而不是只做概念包装。

##### 7. 最终结论：AI Coding 的竞争维度已经变了

- 过去大家关注的是模型本身有多强、补全有多快。
- 现在更关键的是：
  - 能否把多个模型合理编排
  - 能否稳定推进长任务
  - 能否验证结果并自动恢复
  - 能否真正完成一个端到端项目
- 简单说，未来 AI 编码工具拼的不是“单点能力”，而是“自主完成真实工程的系统能力”。

## 产品-最佳实践（1）

### 2026-03-25 10:31:31

#### 在“PHP CRM 迁移到 TypeScript”这个实例上的最佳实践

基于你给的内容，最值得提炼的不是“选哪个最强模型”，而是：**把一个真实工程任务拆成多个角色，用不同能力的模型和不同的执行机制协同完成**。

下面我用一个具体实例来说明。

---

##### 实例设定

###### 项目目标
把一个运行了 6 年的 PHP CRM 系统，逐步迁移为 TypeScript 技术栈，要求：

- 不中断线上业务
- 保留核心客户、订单、跟进记录等数据
- 补齐历史缺失的测试
- 新系统可持续迭代
- 前后端都能被 AI Agent 持续接管

###### 原始情况
旧系统特点：

- PHP + MySQL
- 没有完整文档
- 控制器、SQL、模板逻辑耦合严重
- 测试覆盖率接近 0
- 部分接口只有前端页面在用，没有 API 文档
- 一些业务规则藏在 if/else 和数据库触发器里

###### 目标架构
迁移后系统：

- 后端：`NestJS + TypeScript`
- 前端：`React + TypeScript`
- 数据库：保留 MySQL，逐步重构 schema
- 测试：`Playwright + Vitest/Jest`
- CI/CD：基于 Git 分支和自动验证流水线

---

##### 为什么这个实例适合用“多角色 AI 编排”

因为这不是“写一个函数”，而是一个**长链路、跨模块、强验证依赖**的工程任务。  
如果只靠一个模型从头聊到尾，常见问题会是：

- 上下文越来越乱
- 早期假设没人校验
- 写代码的人顺手“脑补”业务逻辑
- 测试只验证 happy path
- UI 是否真的可用没人确认

所以最佳实践是：**规划、实现、验证、调研分离**。

---

##### 最佳实践一：按阶段分配模型角色，而不是押注单一模型

###### 推荐角色分工
针对这个 CRM 迁移项目，可以这样分：

| 角色 | 职责 | 更适合的能力 |
|---|---|---|
| Planner | 制定迁移路线、任务拆解、依赖排序 | 强推理、长链路规划 |
| Researcher | 阅读旧代码、找隐式规则、整理 API 行为 | 大上下文检索、总结 |
| Implementer | 写 TypeScript 服务、接口、页面、测试脚手架 | 高效编码、局部实现 |
| Verifier | 跑测试、跑浏览器、比对行为、检查回归 | 精确理解、严格校验 |
| Recovery/Coordinator | 失败重试、合并结果、控制 Git 交接 | 流程稳定性 |

###### 在这个实例中的具体做法
不要让一个 Agent 直接执行“迁移 CRM”。  
应该拆成例如：

1. 盘点 PHP 模块与数据库表
2. 提取“客户管理”业务流
3. 为旧系统补黑盒回归测试
4. 在 NestJS 中重建客户模块
5. 让新旧接口并行比对
6. 用浏览器自动化验证前端页面可操作性
7. 合并并发布到灰度环境

###### 关键原则
- **规划模型不直接写大量代码**
- **写代码的模型不负责宣布任务完成**
- **验证模型不依赖实现模型的自述**

这是整个系统可靠性的核心。

---

##### 最佳实践二：每个 Worker 都要使用“干净上下文”

文章里提到的一个非常关键的点是：**每个 worker 启动时拿到干净上下文**。  
这在 CRM 迁移这种任务里尤其重要。

###### 错误做法
一个 Agent 连续做这些事：

- 读老 PHP
- 猜业务规则
- 写 TS 接口
- 写前端表单
- 跑测试
- 修 Bug
- 最后自己说“完成了”

这样上下文会污染，模型很容易把“猜测”当“事实”。

###### 正确做法
每个子任务都重新注入最小必要上下文。

例如：

###### Worker A：旧系统行为提取
输入仅包含：

- `customer.php`
- `order.php`
- 相关 SQL
- 数据库 schema
- 线上关键页面访问路径

输出：

- 客户模块行为说明
- 输入输出字段
- 关键业务规则
- 未确认项列表

###### Worker B：TypeScript 实现
输入仅包含：

- Worker A 输出的行为说明
- 目标 NestJS 项目结构
- 编码规范
- 当前任务范围：只做客户查询与编辑

输出：

- DTO、Service、Controller、Repository
- 单元测试
- 变更说明

###### Worker C：验证
输入仅包含：

- 新旧接口地址
- 比对规则
- Playwright 场景
- 验收标准

输出：

- 差异报告
- 回归失败截图
- 可复现步骤

###### 这样做的收益
- 减少注意力漂移
- 降低错误传播
- 让每一步输出都更像“工件”，而不是“聊天记录”

---

##### 最佳实践三：先补“行为测试”，再做迁移

在这种遗留系统里，最危险的不是代码写不出来，而是**你以为自己理解了业务**。

###### 这个实例中的最佳顺序
不是先让 AI 重写 PHP 为 TypeScript。  
而是：

```text
先观察旧系统行为 -> 固化为测试 -> 再迁移实现
```

###### 推荐测试层次

###### 1. 黑盒接口回归测试
针对旧 PHP 系统已有接口，先录制行为：

- 查询客户列表
- 新建客户
- 编辑客户等级
- 搜索订单
- 提交跟进记录

哪怕旧系统没有测试，也要优先补这层。

###### 2. 页面级浏览器验证
因为很多 CRM 的真实逻辑藏在前端交互里：

- 某字段切换后另一个字段才显示
- 某角色登录后按钮才可见
- 提交前有前端校验
- 列表排序、分页、筛选一起工作

这些都不能只靠 API 测试验证。

###### 3. 新旧系统对照测试
迁移后的 NestJS 接口，不只要“能跑通”，还要对比：

- 返回字段是否一致
- 状态码是否一致
- 边界输入时行为是否一致
- 是否引入意外放宽/收紧校验

###### 最佳实践
- **先定义行为，再定义实现**
- **优先保留业务语义，不急着做结构美化**
- **迁移阶段允许代码不完美，但不允许行为失真**

---

##### 最佳实践四：任务拆分以“业务闭环”为单位，不以技术层为单位

###### 不推荐的拆法
- 一个 Agent 重写所有 Controller
- 一个 Agent 重写所有 Model
- 一个 Agent 重写所有前端页面

这会导致：

- 交付结果无法独立验证
- 依赖关系复杂
- 错误很晚才暴露

###### 推荐的拆法
按业务闭环拆，例如：

- 客户管理闭环
- 订单查询闭环
- 销售跟进闭环
- 发票导出闭环

每个闭环都包含：

- 数据模型梳理
- API 重建
- UI 页面迁移
- 测试补齐
- 新旧行为对比

###### 在 CRM 项目里的例子
一个适合的最小迁移单元是：

```text
客户列表页 + 客户详情页 + 客户编辑接口 + 相关权限校验 + 对应测试
```

因为这个单元：

- 用户可感知
- 可独立验收
- 可灰度发布
- 出问题容易回滚

---

##### 最佳实践五：所有交接都通过 Git 工件完成，不靠聊天记忆

文章中提到“通过 git 协调所有交接，失败自动恢复”，这点非常关键。

###### 在这个实例里怎么落地

每个 worker 的输出都应该是可追踪工件，例如：

- 一个特性分支
- 一组提交
- 一个 `migration-notes.md`
- 一个 `verification-report.md`
- 一组测试文件
- 一个失败截图目录

###### 推荐交接方式
不是说：

> 我已经把客户模块迁移好了，应该没问题。

而是交接：

- 分支：`feature/migrate-customer-module`
- 提交内容：DTO、Service、API、页面、测试
- 已验证项：列表查询、详情展示、编辑保存
- 未验证项：导入导出、复杂权限
- 已知风险：旧系统有数据库触发器逻辑尚未迁移

###### 最佳实践
- 每次任务结束必须产出可审查的 Git 结果
- 每次失败都保留现场，不覆盖错误上下文
- 每个阶段都能从某个 commit 恢复继续跑

这对于长达几小时甚至几天的任务尤其重要。

---

##### 最佳实践六：验证层必须独立，且覆盖“代码正确”之外的真实使用场景

这是很多团队最容易忽略的地方。

###### 只跑单元测试不够
在 CRM 场景里，代码层面通过并不代表用户可用。  
例如：

- 页面表单能渲染，但保存按钮被遮挡
- 数据提交成功，但列表页不刷新
- 权限判断正确，但某个角色菜单消失
- 中文字段长度超限导致 UI 换行错乱

###### 因此验证层至少包含三类检查

###### 1. 静态验证
- TypeScript 编译
- ESLint
- 单元测试
- 集成测试

###### 2. 动态行为验证
- API 回归测试
- 数据读写一致性检查
- 错误码和异常消息比对

###### 3. 用户视角验证
- 浏览器自动化
- 关键页面截图比对
- 表单可点击、可输入、可提交
- 多角色登录的权限路径检查

###### 在这个实例里的典型验收脚本
例如对“客户编辑页”：

- 打开客户详情页
- 点击编辑
- 修改客户等级和备注
- 保存
- 返回列表
- 重新打开详情页验证数据一致
- 使用不同角色账号重复操作
- 检查无权限角色是否被正确拦截

###### 原则
- **不要让实现者定义最终验收**
- **不要把“测试通过”误认为“任务完成”**
- **最终验收必须贴近用户操作**

---

##### 最佳实践七：控制提示词和上下文长度，少说话，只传必要信息

文章提到一个很重要的现实：这类系统会长时间高 token 消耗运行，所以一定要**少说话、说重点**。

###### 在这个实例里的提示词写法
不要这样：

> 请你全面分析这个 CRM 系统并完成从 PHP 到 TypeScript 的所有迁移，包括数据库、接口、前端、测试、部署，注意考虑所有边界情况。

这太宽，会导致模型泛化失控。

###### 更好的任务描述
例如给“客户模块实现 worker”的 prompt：

```markdown
任务：实现客户模块的 TypeScript 后端接口

范围：
- 只处理 customer list / detail / update
- 不处理导入导出
- 不修改数据库 schema

输入材料：
- docs/customer-behavior.md
- legacy/customer.php
- db/schema.sql
- api/contracts/customer.yaml

输出要求：
- NestJS controller/service/repository
- DTO 和输入校验
- 单元测试与集成测试
- migration-notes.md

验收标准：
- 通过 `pnpm test customer`
- 通过旧系统对照测试
- 不引入 breaking change

禁止：
- 不猜测未定义字段
- 不擅自新增业务规则
- 遇到不确定逻辑写入 `open-questions.md`
```

###### 最佳实践
- 一个 prompt 只做一件事
- 明确范围、输入、输出、验收、禁止项
- 所有“不确定”必须显式上报，不能隐式补全

##### 最佳实践八：对长链路任务设置“中间检查点”，不要一口气跑到最后

长任务最怕“最后 10% 才发现前面全错了”。

###### 在这个 CRM 迁移中的推荐检查点

###### Checkpoint 1：旧系统行为盘点完成
交付物：

- 模块边界
- 字段定义
- 权限矩阵
- 未确认规则

###### Checkpoint 2：回归测试基线建立
交付物：

- 旧系统黑盒测试
- 页面自动化脚本
- 样例数据集

###### Checkpoint 3：TypeScript 版本功能对齐
交付物：

- 新接口
- 新页面
- 通过基线测试

###### Checkpoint 4：灰度环境验证
交付物：

- 新旧流量对照
- 错误率报告
- 回滚方案

###### 好处
- 更早发现理解偏差
- 每阶段都能人工 review
- 失败可局部重试，不必整任务重跑

---

##### 最佳实践九：并行不是越多越好，优先降低协调成本

文章里也提到未解决问题之一：**并行度与协调开销的平衡**。

###### 这个实例中的常见误区
一下子开 10 个 worker 分别迁移 CRM 各模块，看起来很快，但实际会遇到：

- DTO 命名不一致
- 权限模型理解不一致
- 公共组件重复造轮子
- 数据库访问层风格冲突
- 最后合并成本极高

###### 更合理的并行方式
- 先串行完成一个“黄金路径”模块，比如客户管理
- 抽象出可复用规范后，再并行扩展到订单、跟进、发票

###### 推荐节奏
```text
先做模板模块 -> 沉淀规范 -> 再并行复制
```

###### 适合先统一的内容
- API 设计规范
- DTO 命名规则
- 错误处理格式
- 权限中间件模式
- 测试目录结构
- 页面组件库

---

##### 最佳实践十：把“未知问题”显式化，而不是假装自动化已经解决

这也是原文里非常值得学习的一点：**诚实列出未解决问题**。

###### 在这个实例中，必须单独维护一份风险清单
例如：

- 旧系统数据库触发器逻辑未完全迁移
- 某些接口返回依赖 session 隐式状态
- 某些权限规则只存在于前端模板判断
- 某些客户等级计算规则来自定时任务
- 历史脏数据可能导致新校验失败

###### 最佳实践
每个 worker 完成时，必须输出：

- 已确认事实
- 假设
- 未知项
- 风险等级
- 需要人工决策的问题

###### 原则
真正成熟的自主工程系统，不是“永远正确”，而是**知道自己哪里不确定**。

##### 一个可执行的最佳实践流程

下面是这个 CRM 迁移项目的一套推荐流程。

```markdown
1. Planner 建立迁移蓝图
   - 划分业务闭环
   - 排定依赖顺序
   - 定义验收标准

2. Researcher 分析旧系统
   - 提取模块行为
   - 识别隐式规则
   - 整理 open questions

3. Verifier 先为旧系统建立基线
   - 黑盒 API 测试
   - 浏览器自动化场景
   - 样例数据快照

4. Implementer 迁移一个最小闭环
   - 只实现客户模块
   - 补齐 TS 类型、校验、测试
   - 输出迁移说明

5. Independent Verifier 独立验收
   - 跑编译、单测、集成测试
   - 跑页面自动化
   - 做新旧行为对照

6. Coordinator 处理失败恢复
   - 记录失败原因
   - 生成下一轮任务输入
   - 基于 Git 分支继续推进

7. 复用模板扩展到下一个模块
   - 订单
   - 跟进记录
   - 发票
```

---

##### 这类任务最值得坚持的 6 条原则

- **按角色选模型，不迷信单模型通吃**
- **上下文最小化，worker 之间只交付工件**
- **先固化旧行为，再做迁移实现**
- **验证独立于实现，且必须包含浏览器级检查**
- **按业务闭环拆任务，而不是按技术层拆**
- **对未知保持显式记录，允许系统诚实地“不确定”**
