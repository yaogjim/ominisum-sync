## 分析要点

- **核心高价值点**：将图关系、向量、会话缓存和元数据整合进单个PostgreSQL记忆层，可显著降低智能体长期记忆基础设施的部署复杂度。
- **留存建议**：建议精读并存档，作为智能体长期记忆架构选型与原型验证资料（提供了可直接运行的快速入门、部署方案、记忆操作接口和多后端架构，可用于Agent记忆层选型与实验。）

**知识要点**

- Cognee将智能体记忆抽象为remember、recall、forget和improve四类操作，并支持会话记忆向永久知识图谱同步。
- 其检索层组合向量相似度与图关系推理，以同时处理语义匹配和结构化关联。
- PostgreSQL方案可统一承载图关系、pgvector向量、会话缓存和元数据，同时保留替换为Neo4j、Redis等专用后端的能力。

#### About Cognee

Cognee is an open-source AI memory platform for AI Agents. Ingest data in any format, and Cognee continuously builds a self-hosted knowledge graph that gives your agents persistent long-term memory across sessions. Cognee combines vector embeddings, graph reasoning, and cognitive-science-grounded ontology generation to make documents both searchable by meaning and connected by relationships that evolve as your knowledge does.

#### Quickstart

Let’s try Cognee in just a few lines of code.

##### Prerequisites

- Python 3.10 to 3.14

You can install Cognee with **pip**, **poetry**, **uv**, or your preferred Python package manager.

```
uv pip install cognee
```

```
import os
os.environ["LLM_API_KEY"] = "YOUR OPENAI_API_KEY"
```

Alternatively, create a `.env` file using our [template](https://github.com/topoteretes/cognee/blob/main/.env.template).

To integrate other LLM providers, see our [LLM Provider Documentation](https://docs.cognee.ai/setup-configuration/llm-providers).

Cognee's API gives you four operations — `remember`, `recall`, `forget`, and `improve`:

```
import cognee
import asyncio

async def main():
    # Store permanently in the knowledge graph (runs add + cognify + improve)
    await cognee.remember("Cognee turns documents into AI memory.")

    # Store in session memory (fast cache, syncs to graph in background)
    await cognee.remember("User prefers detailed explanations.", session_id="chat_1")

    # Query with auto-routing (picks best search strategy automatically)
    results = await cognee.recall("What does Cognee do?")
    for result in results:
        print(result)

    # Query session memory first, fall through to graph if needed
    results = await cognee.recall("What does the user prefer?", session_id="chat_1")
    for result in results:
        print(result)

    # Delete when done
    await cognee.forget(dataset="main_dataset")

if __name__ == '__main__':
    asyncio.run(main())
```

```
cognee-cli remember "Cognee turns documents into AI memory."

cognee-cli recall "What does Cognee do?"

cognee-cli forget --all
```

To open the local UI, run:

```
cognee-cli -ui
```

> **Note:** The MCP server launched by `cognee-cli -ui` runs inside a Docker container. Docker Desktop, Colima, or any OCI-compatible runtime with a working `docker` CLI is required. See Docker &amp; Colima Setup for details.

Prefer containers? Cognee publishes prebuilt images to Docker Hub on every push to `main`:[`cognee/cognee`](https://hub.docker.com/r/cognee/cognee) (the API server) and [`cognee/cognee-mcp`](https://hub.docker.com/r/cognee/cognee-mcp) (the MCP server).

Clone the repo, create a `.env` with at least `LLM_API_KEY`, then:

```
cp .env.template .env   # then edit .env and set LLM_API_KEY

# Start the API server (http://localhost:8000)
docker compose up

# Optional profiles (combine as needed):
docker compose --profile ui up        # + frontend on http://localhost:3000
docker compose --profile mcp up       # + MCP server on http://localhost:8001
docker compose --profile postgres up  # + Postgres/PGVector
docker compose --profile neo4j up     # + Neo4j
```

> The `cognee` and `cognee-mcp` services publish different host ports (`8000` vs `8001`), so you can run both at once.

```
# Create a minimal .env in the current directory
echo 'LLM_API_KEY="YOUR_OPENAI_API_KEY"' > .env

# API server
docker run --env-file ./.env -p 8000:8000 --rm -it cognee/cognee:main

# MCP server (HTTP transport)
docker pull cognee/cognee-mcp:main
docker run -e TRANSPORT_MODE=http --env-file ./.env -p 8000:8000 --rm -it cognee/cognee-mcp:main
```

See the MCP server README for SSE/stdio transports, optional extras, and MCP client configuration.

##### Claude Code

Install the [Cognee memory plugin](https://github.com/topoteretes/cognee-integrations/tree/main/integrations/claude-code) to give Claude Code persistent memory across sessions. The plugin captures prompts, tool traces, and assistant responses into session memory, injects relevant context on every prompt, and syncs session memory into the permanent knowledge graph at session end.

**Install** from the Claude Code marketplace. The recommended way is from your shell, *before* launching Claude Code, so the first `claude` launch is a clean session that bootstraps memory automatically:

```
# Add the marketplace and install the plugin (one-time, user-scoped)
claude plugin marketplace add topoteretes/cognee-integrations
claude plugin install cognee-memory@cognee

# Set env vars for your mode (see below), then launch
export LLM_API_KEY="sk-..."   # local mode; or COGNEE_BASE_URL + COGNEE_API_KEY for cloud
claude
```

**Local mode** (default) — the plugin bootstraps a local Cognee API at `http://localhost:8011`. Only `LLM_API_KEY` is required; the Cognee API key is auto-minted if absent:

```
export LLM_API_KEY="sk-..."
```

**Cognee Cloud or a remote server** — set both:

```
export COGNEE_BASE_URL="https://your-instance.cognee.ai"
export COGNEE_API_KEY="ck_..."
```

On startup you should see a "Cognee Memory Connected" system message.

The plugin hooks into Claude Code's lifecycle — `SessionStart` selects mode and sets up identity, `UserPromptSubmit` injects dataset-scoped context, `PostToolUse` captures tool traces, `Stop` writes the assistant's answer, `PreCompact` preserves memory across context resets, and `SessionEnd` triggers the final sync into the permanent graph.

See the [plugin README](https://github.com/topoteretes/cognee-integrations/tree/main/integrations/claude-code) for sessions, datasets, and full configuration.

Point any Python agent at a managed Cognee instance — all SDK calls route to the cloud:

```
import cognee

await cognee.serve(url="https://your-instance.cognee.ai", api_key="ck_...")

await cognee.remember("important context")
results = await cognee.recall("what happened?")

await cognee.disconnect()
```

Graph memory traditionally means operating a stack — a graph database for relationships, a vector database for embeddings, Redis for sessions, and a relational database for metadata — all deployed, secured, and paid for before an agent remembers anything. In cognee 1.0 you can run the entire memory layer on a single Postgres instance.

Memory layer Traditional stack cognee on Postgres

Relationships Neo4j or another graph database cognee's Postgres graph backend

Embeddings Dedicated vector database pgvector

Sessions Redis SQL session-cache backend

Metadata Relational database same Postgres

The graph still exists — it just lives inside the same Postgres-backed memory layer as the text, metadata, and embeddings, so retrieval moves between similarity and structure without crossing service boundaries. In our CI benchmarks, Postgres search ran \~10% faster than the separate graph-plus-vector setup.

Postgres is the default we recommend for most deployments, but you can still swap in dedicated backends when a workload needs them (Neo4j and Neptune for graphs, Redis for sessions, pgvector and LanceDB for vectors, plus Qdrant, ChromaDB, Weaviate, and Milvus via community adapters). Local development stays fully embedded — SQLite, LanceDB, and Kuzudb — with no extra services to stand up.

pip install "cognee[postgres]"
```

DB_PORT=5432

DB_PASSWORD=cognee

```

#### Benchmarks

We ran cognee against [BEAM](https://github.com/topoteretes/cognee), a long-context benchmark that tests whether a system can keep track of a long conversation as it changes — a more useful test for agent memory than typical needle-in-a-haystack benchmarks. Using only cognee's default settings and standard open-source features (no custom models, no BEAM-specific pipelines), we beat the previous state of the art at the 100K-token setting and matched it at 10M tokens.

Benchmark Setting cognee Previous SOTA Obsidian / RAG baseline

BEAM 100K tokens **0.79** (&gt;0.8 with per-question routing) 0.735 \~0.33

BEAM 10M tokens **0.67** 0.641 \~0.33

These numbers are a directional signal rather than a definitive measure — see the write-up for the full methodology, caveats, and what the results actually mean.

#### Cognee：面向 AI Agent 的开源长期记忆平台

##### 一句话概括

Cognee 为 AI Agent 提供可跨会话持续存在的 “长期记忆”：将多源数据转化为自托管知识图谱，并结合向量检索与关系推理，让 Agent 能记住历史、理解关联、复用经验并持续改进。

##### 核心能力

###### 1. 统一构建 AI 记忆

Cognee 支持摄取多种格式的数据，将其组织为由以下部分组成的记忆层：

- **向量嵌入**：按语义查找相似内容。
- **知识图谱**：建立实体、事件和关系之间的连接。
- **本体生成**：为知识赋予领域结构和语义约束。
- **会话记忆**：快速记录当前对话，并异步沉淀到长期记忆。

###### 2. 四个核心操作

- `remember`：保存信息，可写入会话缓存或长期知识图谱。
- `recall`：自动选择合适的检索策略，召回相关上下文。
- `forget`：删除指定数据或记忆。
- `improve`：根据反馈和新知识持续优化记忆结构。

其产品抽象较为简洁，本质上是把复杂的 RAG、图谱和会话存储封装为统一的 “记忆 API”。

##### 技术架构

###### 从多组件栈收敛到单一 Postgres

传统图记忆系统通常需要同时维护：

- Neo4j 等图数据库；
- 向量数据库；
- Redis 会话缓存；
- 关系数据库。

Cognee 1.0 可将关系、向量、会话和元数据统一放入**Postgres + pgvector**。这降低了部署、运维、安全与成本门槛，也减少了跨服务检索开销。

对于复杂场景，仍可替换为 Neo4j、Neptune、Redis、LanceDB、Qdrant、Milvus、Weaviate 等专用后端；本地开发则支持 SQLite、LanceDB 和 KuzuDB。

##### 典型应用

###### 客服 Agent

整合用户的账单、产品使用和客服历史，重建问题时间线，检索相似解决案例，并记录执行结果，避免重复犯错。

###### 企业知识大脑

统一公司内部多源数据，让不同 Agent 共享领域知识、上下文和经验，减少信息孤岛。

###### SQL Copilot 与专家经验复用

沉淀专家 SQL、数据结构和分析流程，将历史成功模式迁移到新的数据集，帮助初级分析师复用专家方法。

###### 编程 Agent 长期记忆

Cognee 提供 Claude Code 插件，可自动保存用户提示、工具调用和回答，并在后续会话中注入相关上下文；同时支持 MCP、Python、TypeScript 和 Rust。

##### 部署与生态

Cognee 同时支持：

- **本地运行与自托管**；
- **Docker / Docker Compose**；
- **Cognee Cloud 托管服务**；
- Modal、Railway、Fly.io、Render 等平台部署；
- API Server、MCP Server 与本地 UI。

Python 是主要入口，同时提供 TypeScript 和 Rust 客户端，便于嵌入不同技术栈。

##### 性能表现

在用于测试长对话记忆能力的 BEAM 基准中，项目公布的数据为：

| 场景 | Cognee | 此前 SOTA | Obsidian / RAG 基线 |
|---|---:|---:|---:|
| 100K tokens | 0.79 | 0.735 | 约 0.33 |
| 10M tokens | 0.67 | 0.641 | 约 0.33 |

官方强调，这些结果更适合作为方向性参考，而非最终结论，仍需结合测试方法和具体业务验证。

##### 产品价值与判断

Cognee 解决的核心问题不是 “如何存更多内容”，而是**如何让 Agent 形成可检索、可关联、可更新、可治理的长期记忆**。

其主要价值在于：

1. **降低 Agent Memory 的工程复杂度**：用统一 API 屏蔽图谱、向量和缓存细节。
2. **强化跨会话连续性**：让 Agent 不再每次从零开始。
3. **支持私有化与数据控制**：适合企业知识、客户数据等敏感场景。
4. **推动经验复用**：把执行结果和专家方法沉淀为可供多个 Agent 使用的组织资产。

总体来看，Cognee 更像是 Agent 时代的 “记忆基础设施层”，而非单纯的 RAG 工具。其竞争力取决于知识构建质量、召回准确率、多租户隔离能力，以及相较传统 RAG 的实际收益能否持续覆盖新增复杂度。

## 口播总结（1）

### 2026-08-03 01:41:27

#### Cognee：给 AI Agent 加上可持续的长期记忆

这份材料介绍的是开源 AI 记忆平台 Cognee。听完你可以了解：它怎样把各种数据整理成知识图谱，让 AI Agent 跨会话记住信息；它如何安装、部署和接入 Claude Code；以及它在实际案例和长文本基准测试中的表现。

##### 一、Cognee 解决的核心问题

**核心结论是：Cognee 让 AI Agent 拥有跨会话的长期记忆。**

普通的 AI 对话，往往只记得当前窗口里的内容。会话一结束，之前的背景、用户偏好和处理结果就可能丢失。Cognee 的作用，就是把文档、聊天记录、工具调用结果等不同格式的数据接收进来，持续整理成一个可以长期保存和查询的记忆系统。

这里有两个关键概念。

第一个是“向量嵌入”。简单说，就是把文字转换成能够表达语义的数字，这样系统可以按“意思相近”来搜索，而不只是匹配完全相同的关键词。

第二个是“知识图谱”。它不仅保存文字，还记录人物、事件、概念之间的关系。这样，AI 不只是找到一段相似文字，还能理解不同信息之间怎样连接。

Cognee 把向量搜索、图谱推理，以及借鉴认知科学的概念组织方式结合起来。随着知识不断增加，里面的关系也会持续更新。这样，文档既能按含义搜索，也能按照关系进行推理。

它的目标，可以概括成三点。

首先，是帮助企业建立统一的“公司大脑”，把不同来源的数据放在一起，让 Agent 使用企业自己的领域知识。

接下来，是让 Agent 能够学习和持续改进。它可以利用用户反馈管理上下文，也可以在不同 Agent 之间共享知识。

更重要的是，它还强调可靠性和可追溯性。材料提到，Cognee 支持用户或租户之间的隔离，能够追踪 Agent 的行为，并结合 OTEL，也就是开放式遥测机制，以及审计能力，帮助记录和检查系统运行过程。

##### 二、如何开始使用 Cognee

**核心结论是：Cognee 可以通过几行 Python 代码快速运行，也提供命令行和容器化方式。**

使用前，需要准备 Python 3.10 到 3.14。安装方式比较灵活，可以使用 pip、Poetry、uv，或者其他 Python 包管理器。

最基本的配置，是提供一个大语言模型的 API 密钥，也就是材料中提到的 `LLM_API_KEY`。配置完成后，Cognee 就能调用相应的大语言模型来处理和组织数据。

Cognee 的 API 主要围绕四个动作展开：记住、回忆、忘记和改进。

“记住”可以把信息永久存入知识图谱。比如告诉系统：“Cognee 可以把文档变成 AI 的记忆。”系统会完成数据添加、知识整理和改进等步骤。

它也支持会话记忆。比如记录“用户喜欢详细解释”。这类信息可以先快速保存在当前会话的缓存中，之后再同步到长期知识图谱。

“回忆”就是查询记忆。Cognee 会自动选择更合适的搜索方式，既可以查语义相近的内容，也可以利用知识关系来寻找答案。

如果查询指定了会话，它会先查当前会话记忆；如果当前会话里没有答案，再继续查询长期知识图谱。

“忘记”则用于删除已经不需要的数据。除此之外，Cognee 还提供“改进”操作，用来让记忆和知识组织不断优化。

如果不想写 Python，也可以使用命令行完成记住、查询和删除。例如，可以通过命令行保存一句话，再查询“Cognee 是做什么的”，或者删除全部记忆。

本地还可以启动一个用户界面。这个界面背后的 MCP 服务器，指的是一种让 AI 助手连接外部工具和数据的协议。不过，启动它需要 Docker Desktop、Colima，或者其他兼容 Docker 的容器运行环境。

##### 三、部署方式和 Claude Code 集成

**核心结论是：Cognee 既能在本地运行，也能通过 Docker、云服务和 Claude Code 插件使用。**

如果偏好容器，可以直接使用官方 Docker 镜像。API 服务默认使用本地的八千端口，前端界面可以使用三千端口，MCP 服务则可以使用八千零一端口。API 服务和 MCP 服务使用不同端口，因此可以同时启动。

它还提供数据库相关的可选配置，比如 PostgreSQL、PGVector 和 Neo4j。用户可以根据自己的部署规模和数据需求进行选择。

接下来是 Claude Code 集成。

Cognee 提供了一个记忆插件，可以让 Claude Code 在不同会话之间保留长期记忆。这个插件会捕获用户提示、工具调用轨迹和助手回复，把它们放进会话记忆中；同时，它还会在每次新提示到来时注入相关背景。

在会话结束时，插件会把会话记忆同步到永久知识图谱。即使上下文被压缩，它也会先保存重要记忆，避免信息在上下文重置时丢失。

插件会参与 Claude Code 的多个生命周期阶段。比如，会话开始时选择运行模式，用户发送提示时注入相关上下文，工具调用后记录轨迹，助手停止输出时保存回答，会话结束时完成最终同步。

本地模式是默认方式。它会在本地启动 Cognee API，地址是 `localhost:8011`，通常只需要提供大语言模型密钥。也可以连接 Cognee Cloud 或远程服务器，这时需要配置服务地址和 Cognee API 密钥。

如果连接成功，Claude Code 会显示“Cognee Memory Connected”，也就是记忆系统已经连接的提示。

##### 四、两个典型使用案例

###### 案例一：客服 Agent 处理复杂问题

**核心结论是：Cognee 可以把客户过去分散在财务、客服和产品系统里的信息串起来，帮助 Agent 给出更准确的处理方案。**

比如，用户说：“我的发票看起来不对，而且问题还没有解决。”

Cognee 会检查过去的沟通记录、曾经失败的处理动作、已经解决的案例，以及相关产品历史。然后，它会重建这次问题的时间线，寻找相似的已解决案例。

材料中的示例回答是：系统找到两起上个月解决的相似账单问题，原因是支付系统和发票系统之间存在同步延迟，而且修复已经应用到这个用户的账户。

这背后的关键，不只是“搜索一段答案”。Cognee 还会追踪每次处理的结果，并在 Agent 完成操作后更新记忆。这样，Agent 下次遇到类似问题时，可以复用有效方案，也能避免重复之前的错误。

###### 案例二：把专家经验传给 SQL Copilot

例如，用户问：“怎样根据这份数据计算客户留存率？”

Cognee 会寻找专家过去写过的 SQL 查询、工作流程、数据表结构，以及已经成功执行过的实现方式。接着，它会把当前数据集的结构和过去的案例进行匹配，再调整专家的逻辑，使它适合当前数据。

最终，Agent 不只是给出一段孤立的 SQL，而是复用专家曾经解决类似问题的方法。

当新的方案被验证成功后，这些经验还会继续写入记忆。长期来看，初级分析师就能借助积累的知识，完成接近专家水平的任务。

##### 五、Cognee 怎样组织记忆层

**核心结论是：Cognee 1.0 可以把原本分散的多种记忆组件，集中运行在一个 PostgreSQL 实例中。**

传统的 Agent 记忆系统通常需要多套基础设施。

图数据库负责保存实体之间的关系。向量数据库负责语义搜索。Redis 之类的缓存负责会话记忆。关系数据库则保存元数据，也就是描述数据本身的信息。

这意味着，在 Agent 真正记住任何内容之前，开发者可能已经要部署、维护和付费使用多个服务。

Cognee 1.0 的做法，是把这些功能集中到同一个 PostgreSQL 支持的记忆层里。图谱仍然存在，只是和文本、元数据、向量嵌入一起放在同一个系统中。这样，系统在相似度搜索和关系搜索之间切换时，不需要跨越多个服务。

材料提到，在持续集成环境的基准测试中，使用 PostgreSQL 的搜索方案，比独立的图数据库加向量数据库方案快大约百分之十。

PostgreSQL 是 Cognee 对大多数部署场景的默认推荐。不过，如果工作负载有特殊要求，也可以替换成专门的后端。例如，图数据库可以选择 Neo4j 或 Neptune；会话可以使用 Redis；向量数据库可以使用 PGVector 或 LanceDB。通过社区适配器，还能接入 Qdrant、ChromaDB、Weaviate 和 Milvus。

在本地开发时，则可以使用内嵌式方案，包括 SQLite、LanceDB 和 KùzuDB，不必先启动额外服务。

##### 六、云端、自托管和多语言客户端

**核心结论是：Cognee 提供托管云服务，也提供多种一键部署方案，还支持 Rust 和 TypeScript。**

如果不想维护基础设施，可以使用 Cognee Cloud，由服务方负责运行环境。

## 深度解读（1）

### 2026-09-18 00:30:33

#### Cognee 的真正价值：把“记忆”从检索功能变成 Agent 的运行层

Cognee 最值得关注的并不是“知识图谱 + 向量检索”这个技术组合，而是它试图把 Agent 记忆抽象成一套完整生命周期：**remember、recall、forget、improve**。这比常见的“把历史对话塞进向量库”前进了一步，因为长期记忆真正困难的不是存储，而是决定什么值得记、何时调用、如何修正，以及何时必须删除。

##### 记忆首先是策略，而不是数据库

Claude Code 插件展示了一个较完整的记忆闭环：会话开始时建立身份与数据范围，用户提问前注入相关上下文，工具执行后记录轨迹，上下文压缩前保存信息，会话结束后再同步到永久知识图谱。这些生命周期钩子，比“支持某种数据库”更能解释系统为何可能有效。

这里也暴露出关键挑战：如果 prompts、工具轨迹和回答都被持续写入，系统很容易把误解、失败尝试和过期偏好沉淀为“事实”。因此，所谓 improve 不能只是增加更多关系，而应包括来源追踪、置信度、时效性、冲突处理和结果反馈。客户支持案例中，真正有价值的也不是记住历史，而是区分“失败动作”和“已验证解决方案”，避免再次采取无效行动。

这意味着 Agent Memory 更像一种**带治理能力的状态管理系统**。`forget` 与租户隔离、审计和可追溯性不是附属功能，而是长期记忆能够进入企业场景的前提。

##### 单一 Postgres 的意义是降低采用门槛

Cognee 1.0 将关系、向量、会话和元数据统一放进 Postgres。项目声称其 CI 测试比图数据库与向量数据库分离的方案快约 10%，但这只是特定负载下的内部结果，不宜泛化。更确定的价值是：少部署 Neo4j、Redis 和独立向量库，就少了同步、权限、备份、故障恢复和跨服务查询等一整套成本。

这会显著扩大知识图谱记忆的适用范围。许多团队并非不需要关系推理，而是无法为尚未验证价值的 Agent 维护四套基础设施。先用 Postgres 验证需求，等规模或图查询复杂度确实超过边界后再替换专用后端，是更合理的产品路径。

##### 下一步竞争点不是“记得更多”，而是“记得可信”

BEAM 成绩——100K tokens 下 0.79、10M 下 0.67——说明混合记忆在长对话追踪上有潜力，但作者也明确称其为方向性信号。真实产品还需要验证：记忆是否减少重复错误、提高任务完成率；错误信息能否被纠正；跨会话收益是否抵得过延迟、成本和隐私风险。

因此，值得关注的机会并不只是再做一个 Memory SDK，而是做**记忆质量与治理层**：让团队看见某条记忆从何而来、为何被召回、影响了哪个动作、何时失效，并允许人工修订。长期看，Agent 的差异化可能不在模型知道多少，而在系统能否持续形成一份可验证、可更新、可遗忘的组织经验。
