## 分析要点

- **核心高价值点**：当输出集合可预先枚举时，可直接对单Token标签的logit做受限softmax，返回决策分布并跳过不必要的自回归生成。
- **留存建议**：精读并存档，可作为本地分类与路由系统的实现参考（包含可直接运行的SGLang实现、适用条件、标签设计规则和阈值决策思路，具有较强复用价值。）

**知识要点**

- 固定选项评分直接读取候选标签的下一Token logits，而结构化输出仍需逐Token生成完整对象。
- 候选概率仅是在限定选项内归一化的相对偏好，不能直接解释为模型真实正确率，必须用标注数据校准。
- 候选项宜映射为经过分词验证的单Token标签；选项不完备时应加入OTHER或ESCALATE逃生通道。

**行动项**

- 启动本地SGLang与Qwen模型，使用/tokenize验证每个候选标签均为单Token。
- 通过/v1/score读取候选标签分数并映射回业务选项，替代固定分类任务中的文本生成与解析。
- 在标注数据集上评估准确率并设定最高概率、领先幅度和人工审核阈值。

### 构建你自己的 Jev（100% 本地）

将开源 LLM 转变为快速本地决策引擎所需的一切，无需重新训练。内容涵盖下一 token 评分、带概率分布的固定选项、SGLang，以及在同一模型上与标准文本生成进行的实操基准测试。

---

许多 LLM 调用并不需要新生成的文本。应用程序已经知道可能的答案，只需要模型从中选择一个。

假设一张支持工单写道：“同一订阅我被扣了两次费。”

应用程序需要将其发送给三个团队之一：账单、技术支持或账户访问。

普通的 LLM 调用会要求模型写出一个答案。它可能返回一个句子、一个标签或一个 JSON 对象。应用程序等待该文本，解析它，并提取所选的团队。

![Image](https://pbs.twimg.com/media/HSm1UsNa8AA5lvl?format=jpg&name=large)

如果每个有效答案都已知，那就不必要了。

事实上，更好且更高效的方法是将同一个请求视为一个决策（Jev 就是这样做的）。应用程序将工单/查询和三个允许的答案提供给 Jev。然后模型一次性为每个答案返回一个分数（我们稍后会讨论具体如何做到这一点）：

```plaintext
billing             0.91
technical support   0.06
account access      0.03
```

此处以最高概率选择计费，应用程序代码实际上可以看到它获胜的强度。

这是 Jev 所具备的行为，我们将在本地复现。

我们将提供输入查询和允许的答案。在一次评分请求中，模型将返回一个决策和概率分布，而不会生成句子或 JSON 对象。

虽然 Jev 是闭源的，但这种推理模式已经在几个开源语言模型中可用。

更具体地说，我们将使用 SGLang（通过 /v1/score）来实现它，用 Qwen 和 DeepSeek 模型进行测试，并将其与结构化输出和普通文本生成进行对比。

![Image](https://pbs.twimg.com/media/HSnYuraaYAAQ63g?format=jpg&name=large)

先说明预期：本文复现的是推理路径，而非完整的 Jev 系统。Jev 还包含训练和校准工作，而评分端点并不提供这些内容。

---

### 固定答案评分不同于结构化输出

人们很容易将 Jev 的机制与结构化输出混淆，因为这两种方法都限制了应用程序接收到的内容，但它们在推理服务器内部所做的工作并不相同。

对于上面讨论的同一个支持工单，结构化输出可能会从模型得到以下输出：

```json
{"team": "billing"}
```

指定的模式阻止了无效对象，因此它不会自行选择团队。

然而，这还可以进一步改进，因为在底层，模型仍然逐个令牌地生成左花括号、字段名、值和右花括号。一旦生成完成，应用程序就会读取 team 字段。这个视频展示了这一过程：

[![视频](https://pbs.twimg.com/amplify_video_thumb/2101414186102493184/img/DC6tk4qvFBFFimx7.jpg)](https://x.com/_avichawla/status/2101563610644496464)[![视频](https://pbs.twimg.com/amplify_video_thumb/2101414186102493184/img/DC6tk4qvFBFFimx7.jpg)](https://x.com/_avichawla/status/2101563610644496464)

通过评分（Jev 就是这样做的），应用程序可以将这三个团队作为有效结果的完整列表提供。服务器可以读取每个结果的一个模型分数，并返回本文前面展示的分布。它不会生成 JSON 对象。

![Image](https://pbs.twimg.com/media/HSm3BpDbgAAUOlt?format=jpg&name=large)

然后我们可以返回所有三个值，而不是仅返回计费结果，这样应用程序代码就能以不同方式处理这两个结果：

```plaintext
Result 1                          Result 2
billing       0.91                billing       0.46
technical     0.06                technical     0.44
account       0.03                account       0.10
```

例如，在上述情况下，两者都会选择计费。

但第一个有明确的偏好，而第二个几乎是平局。应用程序可以自动路由第一张票，并在需要时将第二张发送审核。

此外，模型只会提供这些分数，而应用程序代码将为其下游使用设定规则。

例如，可能要求最高答案超过0.80，并且领先第二答案至少0.20。这些阈值存在于代码中，可以在其中进行测试和更改。

![Image](https://pbs.twimg.com/media/HSm2_dMbMAA6rpo?format=jpg&name=large)

0.91的值意味着计费在这三个选择上获得了91%的概率质量。这并不证明模型在91%的情况下是正确的。我们需要有标签的示例来衡量这一点。这就是我稍后将讨论的校准问题。

但与此同时，请记住，结构化输出会生成一个有效的对象。固定答案评分会返回应用程序已经知道的答案分布。

### LLM 如何生成第一个输出 token

在我们讨论如何将因果 LLM 转变为 Jev 风格的模型之前，最好先了解 LLM 中的常规生成步骤。

![Image](https://pbs.twimg.com/media/HSm6yGwaoAAnfso?format=jpg&name=large)

- 分词器首先将提示转换为 token ID。
- 模型处理该序列，并为下一个位置生成一个向量。
- 该向量为模型词汇表中的每个 token 都包含一个数值。例如，Qwen 的词汇表包含数万个 token，因此该向量包含数万个数值。

这些原始数字是 logits。logit 越大，表示模型越倾向于将该 token 作为下一个延续。这些值还不是概率。

在正常生成过程中，服务器会对这个向量应用模型的解码规则（温度等），选择一个 token，并将其追加到提示词中。

然后，模型会为下一个位置生成一个新的词汇表大小的向量。生成/解码会重复这个过程，直到遇到停止 token 或达到输出限制。

![Image](https://pbs.twimg.com/media/HSozL26bsAA33xt?format=jpg&name=large)

但当我们想要做出有界决策时，我们只关心第一个向量。

回想一下上面讨论的支持路由器示例。该应用程序接受三个答案：

```plaintext
billing
technical support
account access
```

在提示中，我们可以为每个答案分配一个简短的标签：

```plaintext
A = billing
B = technical support
C = account access
```

提示以请求一个标签结束。

```plaintext
Route the support ticket into exactly one category.

Ticket:
I was charged twice for the same subscription.

Allowed labels:
A = billing
B = technical support
C = account access

Return only the label.

Label:
```

“标签：”是提示中的最后文本。

因此，下一个位置就是模型通常会生成 A、B 或 C 的地方。

处理完这个提示后，模型将为该位置生成其通常的词汇量大小的向量。该向量将包含标记 A 的 logit、B 和 C 的 logits，以及词汇表中每个其他标记的 logits。

然后，评分路径可以执行四种操作：

![Image](https://pbs.twimg.com/media/HSm6tPPbwAAGsVc?format=jpg&name=large)

1. 找到 A、B 和 C 的标记 ID。
2. 读取词汇向量中这些位置上的三个 logit。
3. 忽略所有其他 logit。
4. 对选定的三个值应用 softmax。

如果选定的 logit 分别为 8.2、5.5 和 4.8，受限 softmax 会产生大约 0.91、0.06 和 0.03。我们可以将这些位置映射回账单、技术支持和账户访问。

归一化仅限于所声明的选项。我们并不是在问 A 在整个词表上是否具有 91% 的概率。

相反，我们是在问，在应用程序排除了所有其他响应之后，模型如何在 A、B 和 C 之间分配其偏好。

![Image](https://pbs.twimg.com/media/HSm7QlHaoAAK04I?format=jpg&name=large)

这是 SGLang 已经在 /v1/score 中实现的一项操作。

它将提示词输入模型，读取所请求的 token 位置，并返回它们的分数。这使我们无需修改 Qwen 实现并自行提取最终张量。

顺便说一句，答案使用 A、B 和 C，而不是直接对“billing”、“technical support”和“account access”这些词进行评分，原因在于一个可见的词不一定是一个 token。

例如：

- “billing”对于某个分词器来说可能是一个 token，而对于另一个分词器来说可能是多个 token。
- “technical support”肯定会跨越多个位置。

比较这些短语需要进行序列评分。模型必须对第一个 token 评分，将其追加，再对下一个 token 评分，并将这些值组合起来以得到完整短语的分数。长度也会成为比较的一部分。

但单 token 标签可以避免这个问题。每个选项都由同一输出位置上的一个词汇表条目表示，而语义含义仍然出现在提示中：

```plaintext
A = billing questions and payment problems
B = product errors and technical failures
C = login, password, and account access problems
```

模型在处理提示时会读取这些描述。标签只是我们之后检查其 logit 的那个 token。

我们仍然必须验证每个标签都是一个 token。

例如，tokenizer 通常会将前导空格编码为 token 的一部分。因此，字符串 "A" 和 " A" 可能具有不同的 token ID。

![Image](https://pbs.twimg.com/media/HSm8N0ca4AAwWPH?format=jpg&name=large)

聊天模板也可能在答案位置之前立即放置空白或控制 token。

为避免这种情况，请使用模型的聊天模板渲染完整提示。确定在答案位置期望的确切续写内容。将该续写内容发送到 /tokenize。如果它产生的不是单个 token，则拒绝该标签。

此标签映射保留在评分客户端内部。应用程序发送诸如 billing 和 technical\_support 之类的语义选项。它从不发送 token ID，也从不接收 A、B 或 C。这就是公共 API 保持独立于模型标签的含义。

最后，当列出的选项并非穷尽所有可能时，答案列表还需要一个逃生通道。

例如，如果安全事件到达一个仅提供账单、技术支持和账户访问的路由器，受限 softmax 仍会将所有概率质量分配给这三个错误选项。

为避免这种情况，当所有列出的选项都可能不正确时，添加 OTHER 或 ESCALATE。

### 使用 SGLang 实现本地评分端点

本地示例只需要一个推理服务器。SGLang 将 Qwen 加载到 GPU 内存中，并暴露其原生 HTTP 端点。我们的 Python 脚本直接向该服务器发送请求。

完整流程如下：

1. 使用 Qwen 模型启动 SGLang。
2. 将决策编写为带有字母标签的提示词。
3. 让 SGLang 对这些标签进行分词。
4. 向 /v1/score 发送一个请求。
5. 将返回的概率映射回各个选项。

![Image](https://pbs.twimg.com/media/HSm_Ko5a0AAiu2Q?format=jpg&name=large)

#### 步骤 1：使用 SGLang 启动 Qwen

创建一个 Python 环境并安装这里使用的两个包：

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install "sglang[all]==0.5.10.post1" "requests==2.34.2"
```

然后启动模型服务器：

```bash
python -m sglang.launch_server \
  --model-path Qwen/Qwen2.5-0.5B-Instruct \
  --host 127.0.0.1 \
  --port 30000
```

首次启动会从 Hugging Face 下载模型。后续启动会复用本地缓存。加载完成后，Qwen 会保留在内存中，SGLang 会监听端口 30000。

这个 SGLang 进程就是推理服务。在执行下面的客户端时，请保持它运行。

#### 步骤 2：定义选项并构建提示

使用以下代码创建 decide(.)py：

```python
import json
import requests

BASE_URL = "http://127.0.0.1:30000"
MODEL = "Qwen/Qwen2.5-0.5B-Instruct"

choices = {
    "A": "billing and payments",
    "B": "technical support",
    "C": "account access",
}

ticket = "I was charged twice for the same subscription."
choice_lines = "\n".join(
    f"{label} = {meaning}" for label, meaning in choices.items()
)

prompt = f"""Ticket:
{ticket}

Question:
Which category matches the ticket?

Allowed labels:
{choice_lines}

Return only the label.
Label:
"""

print(prompt)
```

该字典记录了每个答案的两种表示形式。

- A 是我们评分的 token。
- 而“billing”是返回给应用程序的含义。
- 在分词、评分和结果映射过程中，它们的顺序必须保持不变。

这是此处生成的确切提示：

```plaintext
Ticket:
I was charged twice for the same subscription.

Question:
Which category matches the ticket?

Allowed labels:
A = billing and payments
B = technical support
C = account access

Return only the label.
Label:
```

提示在“Label:”处结束。

我们希望得到模型对下一个可能出现的 token 的评分。我们并不要求 SGLang 生成那个 token。

#### 第 3 步：解析标签 token ID

将以下代码添加到提示下方：

```python
label_token_ids = []

for label in choices:
    response = requests.post(
        f"{BASE_URL}/tokenize",
        json={
            "model": MODEL,
            "prompt": label,
            "add_special_tokens": False,
        },
        timeout=30,
    )
    response.raise_for_status()
    token_ids = response.json()["tokens"]

    if len(token_ids) != 1:
        raise ValueError(
            f"{label!r} is not a single token: {token_ids}"
        )

    print(f"{label!r} -> {token_ids}")
    label_token_ids.append(token_ids[0])
```

SGLang 的 /tokenize 端点返回由 Qwen 的分词器生成的整数 ID。我们拒绝任何被拆分为多个 token 的标签。评分请求需要为每个答案提供一个词汇表位置。

对于 Qwen/Qwen2.5-0.5B-Instruct，这会打印：

```plaintext
'A' -> [32]
'B' -> [33]
'C' -> [34]
```

每个列表包含一个整数。因此我们知道每个标签占用一个 token。后续的评分请求将读取词汇表中的位置 32、33 和 34。

这一检查也防止我们假设不同模型之间的分词是相同的。一个在 Qwen 中有效的标签，在另一个分词器下可能会被拆分。

#### 步骤 4：向 SGLang 请求这三个概率

接下来添加评分请求：

```python
response = requests.post(
    f"{BASE_URL}/v1/score",
    json={
        "model": MODEL,
        "query": prompt,
        "items": [""],
        "label_token_ids": label_token_ids,
        "apply_softmax": True,
    },
    timeout=120,
)
response.raise_for_status()
score_response = response.json()

print(json.dumps(score_response, indent=2))
scores = score_response["scores"][0]
```

- 查询包含完整的提示词。
- 空的“items”表示我们对其后的位置立即进行评分。
- “label\_token\_ids”告诉 SGLang 从 Qwen 的词汇表大小的输出中读取哪三个条目。
- “apply\_softmax”会将这些条目归一化为概率。

响应只有一个分数列表，因为 items 只包含一个条目。我们针对同一个 Qwen checkpoint 运行了这个完全相同的提示，并得到：

```json
{
  "scores": [
    [
      0.67776233,
      0.310878605,
      0.011359035
    ]
  ]
}
```

这三个位置分别对应 A、B 和 C。在 softmax 之前，选中的 logits 分别为 25.277620、24.498226 和 21.188837。不同硬件和精度设置下可能会出现细微的数值差异。

官方端点参考说明，每个返回的列表都遵循 label\_token\_ids 的顺序。因此，我们的第一个分数属于 A，第二个属于 B，第三个属于 C。

#### 步骤 5：将模型标签转换回决策

使用映射代码完成脚本：

```python
probabilities = {
    choices[label]: float(score)
    for label, score in zip(choices, scores, strict=True)
}

decision = max(probabilities, key=probabilities.get)

print(
    json.dumps(
        {
            "decision": decision,
            "probabilities": probabilities,
        },
        indent=2,
    )
)
```

现在在第二个终端中运行脚本：

```json
// Output after running python decide.py

{
  "decision": "billing and payments",
  "probabilities": {
    "billing and payments": 0.6777623295783997,
    "technical support": 0.31087860465049744,
    "account access": 0.011359035037457943
  }
}
```

SGLang 在 /v1/score 背后执行该计算。一个 SGLang 进程对标签进行分词，运行一次 Qwen，并返回所选概率。

在这种情况下，计费胜出，但概率仅为0.678。如果策略要求达到0.70，则会将此工单发送进行审核，而不是自动执行路由。该阈值应来自对标注示例的评估。

### 测量评分延迟与自回归生成

上面的单请求示例展示了该机制。我还构建了一个小型应用程序，用于测试该机制在大量决策中的表现。

![Image](https://pbs.twimg.com/media/HSnKeh8aYAAQPdP?format=jpg&name=large)

部署的演示支持多个开放模型，例如 Qwen 3 4B、Qwen 2.5 0.5B 和 1.5B、SmolLM2 1.7B、TinyLlama 1.1B 以及 DeepSeek-R1-Distill-Qwen 1.5B。

![Image](https://pbs.twimg.com/media/HSnKtK-aAAAXDZ9?format=png&name=large)

Jev 风格的 lane 调用决策方法：

```python
result = engine.decide(request)

answer = result["answers"]["decision"]

choice = answer["choice"]

probabilities = answer["probabilities"]
```

在 decide() 方法内部，SGLang 通过 /v1/score 接收提示。该请求包含 A、B 和 C 的 token ID。

SGLang 运行提示，读取这三个下一个 token 的分数，对其进行归一化，然后停止。响应中不包含任何生成的 token。

标准 lane 在同一个引擎上调用生成方法：

```python
result = engine.generate_response(
    case["state"],
    case["question"],
    list(case["criteria"].items()),
    max_tokens=32,
)
```

该方法将相同的状态、问题和选项发送到 /v1/chat/completions。

### 如何选择正确的方法

评分并不能替代生成，因此 Jev 的方法仅适用于应用程序在推理之前定义了输出空间的情况。

一个兼容的工作负载理想情况下应具有一组有限且有意义的标签。每个标签应映射到一个不同的下游操作。

并且调用方只需一个标签及其概率分布，而不需要新的文本。

结构化输出有所不同，因为它定义了响应的语法，而解码器仍然逐个 token 生成字段名和值。

当这些值无法事先枚举时，应使用结构化生成，因为只有当候选值已知时，评分才会移除解码过程。

- 在推理前输出内容未知时生成。

## 结构化（1）

### 2026-09-20 09:55:44

#### 用 SGLang 将开源 LLM 变成本地固定选项决策引擎

文章介绍了一种类似 Jev 的本地推理方式：当答案范围事先已知时，不让大模型生成文本，而是直接读取它对各候选项的下一 token 评分，一次返回决策及概率分布。这样可减少生成和解析开销，但本文只复现了 Jev 的推理路径，不包括其专用训练、校准和评估体系。

##### 核心思路：把“生成答案”改成“候选项评分”

许多 LLM 任务本质上不是写作，而是在有限选项中做选择。例如，一张“同一订阅被扣费两次”的工单，只需被分配到：

- 账单
- 技术支持
- 账户访问

常规调用会让模型生成标签、句子或 JSON，应用程序再解析结果。Jev 风格的方法则直接向模型提供候选项，并返回类似下面的分布：

```text
billing             0.91
technical support   0.06
account access      0.03
```

应用程序不仅知道“账单”获胜，还能判断模型偏好是否足够明确。例如：

- `0.91 / 0.06 / 0.03`：可自动处理；
- `0.46 / 0.44 / 0.10`：接近平局，可转人工审核。

阈值由业务代码控制，例如要求第一名高于 `0.80`，且至少领先第二名 `0.20`。

##### 与结构化输出的区别

结构化输出可能返回：

```json
{"team": "billing"}
```

它能保证格式合法，但模型内部仍需逐 token 生成左括号、字段名、值和右括号。

固定选项评分则不生成 JSON，只读取模型在答案位置上对候选标签的评分。两者适用范围不同：

- **结构化输出**：约束输出格式，但具体内容可能无法提前枚举；
- **固定选项评分**：候选答案已知，只需选择并返回其概率分布；
- **普通生成**：需要产生事先未知的新文本。

因此，评分不能替代所有生成任务，只适合有限分类、路由、审核和筛选等场景。

##### 原理：只读取第一个下一 token 的 logits

因果语言模型处理完提示词后，会为词表中的每个 token 生成一个原始分数，即 **logit**。普通生成会选择一个 token，追加到上下文中，再重复计算，直到生成结束。

但在固定选项决策中，只需要第一个位置的分数。可以先把语义选项映射为短标签：

```text
A = billing
B = technical support
C = account access
```

提示最后要求模型返回标签：

```text
Label:
```

此时服务器：

1. 找到 A、B、C 对应的 token ID；
2. 从下一 token 的完整 logit 向量中取出这三个值；
3. 忽略词表中的其他 token；
4. 只对这三个 logit 做 softmax，得到归一化概率。

例如三个 logit 为 `8.2、5.5、4.8`，受限 softmax 后约为：

```text
A  0.91
B  0.06
C  0.03
```

这里的 `0.91` 表示：**在 A、B、C 三个候选中，A 获得了 91% 的概率质量**，并不等于模型有 91% 的真实正确率。真实可靠性必须通过带标签的数据评估和校准。

##### 为什么要使用 A、B、C 这样的标签

“billing”可能是一个 token，也可能被拆成多个 token；“technical support”几乎一定跨越多个位置。直接比较不同长度的短语，需要进行完整的序列评分，还会受到长度影响。

使用单 token 标签可以让所有选项在同一个输出位置上直接比较。模型仍能从提示中的描述理解标签含义，例如：

```text
A = billing questions and payment problems
B = product errors and technical failures
C = login, password, and account access problems
```

但实现时必须验证标签确实只占一个 token，因为：

- 不同模型的分词方式不同；
- `"A"` 与 `" A"` 可能对应不同 token；
- 聊天模板可能在答案前插入空格或控制 token。

稳妥做法是用模型的聊天模板渲染完整提示，再通过 `/tokenize` 检查答案位置预期出现的文本；若标签被拆成多个 token，就应拒绝或更换标签。应用程序只接触“账单”等语义选项，A、B、C 及 token ID 应封装在评分客户端内部。

##### 用 SGLang 在本地实现

文章使用 SGLang 的 `/v1/score` 接口和 Qwen 模型，基本流程是：

1. 启动本地 SGLang 推理服务器；
2. 将候选项映射为单 token 字母标签；
3. 调用 `/tokenize` 获取并验证标签 token ID；
4. 向 `/v1/score` 提交提示和标签 ID；
5. 将返回的概率映射回业务选项。

示例使用：

```text
Qwen/Qwen2.5-0.5B-Instruct
SGLang 0.5.10.post1
```

在该模型中，A、B、C 分别对应 token ID `32、33、34`。对“同一订阅被重复扣费”的工单评分后，得到：

```json
{
  "decision": "billing and payments",
  "probabilities": {
    "billing and payments": 0.6778,
    "technical support": 0.3109,
    "account access": 0.0114
  }
}
```

虽然“账单与支付”排名第一，但概率只有约 `0.678`。如果业务规则要求最高概率至少为 `0.70`，该工单就应转人工审核，而不是自动路由。阈值应根据真实标注样本确定，不能凭感觉设置。

##### 候选项不完整时必须提供退出选项

受限 softmax 会把全部概率强制分配给已列出的候选项。即使输入实际上属于“安全事件”，如果系统只提供账单、技术支持和账户访问，模型仍必须在这三个错误答案中选一个。

因此，只要候选列表可能不完整，就应增加：

- `OTHER`
- `ESCALATE`
- “无法判断”

这类逃生选项，避免系统在错误分类中表现出虚假的确定性。

##### 与普通文本生成的本地对比

作者还用同一个 SGLang 服务、同一个模型和同一块 GPU，对两条路径进行了比较：

- **Jev 风格评分**：调用 `/v1/score`，只计算 A、B、C 的下一 token 概率，不生成任何 token；
- **标准生成**：调用 `/v1/chat/completions`，最多生成 32 个 token，再从文本中解析允许的选项。

测试数据包含 100 个本地案例，覆盖支持路由、候选人筛选和费用审核。两条通道同时运行，共享 GPU、内存带宽和 SGLang 调度器，并由连续批处理协调。

文章展示的演示中，评分路径明显更快，原因是它在处理完提示后立即停止，省去了自回归生成和文本解析。不过原文没有给出具体延迟或吞吐量数字，因此只能确认其演示结果，不能据此推导固定的加速倍数。

##### 适用边界与结论

适合固定选项评分的任务通常满足三个条件：

- 推理前已经知道全部或大部分候选答案；
- 每个标签对应明确且不同的下游操作；
- 调用方只需要选择结果及概率分布，不需要新文本。

选择推理方式的原则是：

- **输出内容事先未知**：使用普通生成；
- **需要合法结构，但值无法完全枚举**：使用结构化输出；
- **候选集合已知，只需做选择**：使用固定选项评分。

文章证明，无需重新训练模型，也能借助 SGLang 的 `/v1/score`，把 Qwen、DeepSeek 等开源因果 LLM 变成本地决策引擎。但这只是 Jev 风格的推理机制，并未复现 Jev 的模型权重、RLCD 训练、概率校准或完整评估体系。

## 口播总结（1）

### 2026-09-21 00:13:02

很多大语言模型任务，其实不需要模型写出一段新文本。应用程序早已知道所有可能答案，只需要模型做一次选择。对于这类任务，把语言模型改造成一个本地决策引擎，通常比生成句子或 JSON 更直接，也更快。

例如，一张支持工单写着：“同一笔订阅，我被扣了两次费。”系统只允许把工单分到三个团队：账单、技术支持，或者账户访问。

常规做法，是让大语言模型生成一个标签、一句话，或者一个 JSON 对象。应用程序等待文本生成完成，再解析结果，找出模型选择了哪个团队。

但既然有效答案已经全部确定，生成整段文本其实是多余的。更合适的做法，是让模型直接给三个选项打分。比如，账单的概率是百分之九十一，技术支持是百分之六，账户访问是百分之三。应用程序不仅知道账单胜出，还能看出它赢得是否明确。

这就是 Jev 风格的推理方式。需要说明的是，Jev 本身是闭源系统。这里能用开源模型复现的，是它的评分推理路径，不是完整系统。Jev 还涉及专门训练、校准和评估，而这些并不会自动包含在普通评分接口里。

这种固定选项评分，和结构化输出并不相同。

结构化输出可以要求模型返回一个合法的 JSON，例如团队字段等于账单。这样可以避免格式错误。但在模型内部，它仍然要逐个词元生成左花括号、字段名、字段值和右花括号。所谓词元，就是模型处理文本时使用的基本单位。

固定选项评分则不生成 JSON。服务器直接读取模型对几个候选答案的偏好，并返回完整分布。

这个区别很重要。假设两张工单最终都选择账单。第一张的分布是账单百分之九十一，技术支持百分之六。第二张则是账单百分之四十六，技术支持百分之四十四。结果虽然相同，可信程度却完全不同。第一张可以自动路由，第二张接近平局，更适合交给人工审核。

应用程序还可以把规则写在代码里。例如，最高分必须超过百分之八十，而且要领先第二名至少二十个百分点，才能自动执行。这些阈值可以独立测试和调整。

不过，百分之九十一并不表示模型有百分之九十一的概率答对。它只表示，在给定的几个选项中，模型把百分之九十一的概率质量分给了这个答案。模型到底有多可靠，仍然需要用带有正确标签的数据进行评估和校准。

那么，语言模型是怎样直接完成评分的？

模型读完提示后，会为下一个位置计算一个很长的数字向量。词汇表中的每个词元，都对应一个原始分数，也就是 logit。分数越高，模型越倾向于把那个词元作为下一个输出。

常规生成会选择一个词元，把它接到提示后面，再计算下一个词元。这个过程不断重复，直到生成结束。这就是自回归生成。

固定选项决策只关心第一次计算出来的向量。

具体做法是，在提示中把三个语义选项分别映射成字母 A、B 和 C。A 代表账单，B 代表技术支持，C 代表账户访问。提示最后停在“标签”之后，正好让下一个位置对应 A、B 或 C。

服务器找到这三个字母在词汇表里的位置，读取对应的三个 logit，忽略其他所有词元，再通过 softmax 把三个分数归一化成概率。这样，一次模型前向计算就能得到决策和完整分布，不需要真正生成任何答案。

之所以使用 A、B、C，而不是直接给“技术支持”之类的短语评分，是因为一个可见的词组未必只占一个词元。“技术支持”可能被切成多个部分。比较多词元短语，需要逐步计算整段序列，长度也会影响分数。单词元标签则能保证所有候选项都在同一个输出位置上公平比较。

但这里有一个容易忽略的细节：必须验证每个标签确实是单个词元。字母 A 和前面带空格的 A，可能拥有不同的词元编号。聊天模板也可能自动插入空格或控制符。因此，实际部署时应该先用模型自己的聊天模板渲染提示，再用分词接口检查预期续写。如果标签被拆成多个词元，就应当换一个标签，而不能直接假设不同模型的分词方式相同。

应用程序本身不必接触这些词元编号。对外仍然使用“账单”“技术支持”这样的业务名称。字母标签和词元编号只保留在评分客户端内部。

还有一个重要的安全条件。如果列出的答案没有覆盖所有可能情况，就必须加入“其他”或“升级处理”这样的逃生选项。否则，即使输入是一场安全事件，模型也会被迫把全部概率分给账单、技术支持和账户访问这三个错误答案。

本地实现可以使用 SGLang 推理服务器。它把 Qwen 或 DeepSeek 等开源模型加载到显卡内存中，通过评分接口接收完整提示和候选标签的词元编号，然后返回归一化分数。

在原文的示例中，使用的是 Qwen 二点五、零点五 B 指令模型。针对重复扣费的工单，模型给账单和支付大约百分之六十七点八，技术支持大约百分之三十一点一，账户访问约百分之一点一。账单虽然胜出，但并不算特别稳。如果业务规则要求最高概率至少达到百分之七十，这张工单就应该进入审核，而不是自动路由。

为了比较速度，作者还让评分路径和普通生成路径共享同一台服务器、同一个模型、同一块显卡和同一个调度器。评分路径只读取下一词元中几个标签的分数，然后停止。普通路径则生成答案和简短解释，最多生成三十二个词元，再由程序从文本里解析选项。评分路径更快的根本原因，不是换了更小的模型，而是避免了应用程序并不需要的逐词生成循环。

不过，评分不能替代所有文本生成。它只适用于输出空间能在推理前完整定义的任务，例如工单路由、候选人筛选、费用审核，或者有限动作之间的选择。如果应用程序需要新的解释、摘要、开放式回答，或者候选值无法提前枚举，就仍然应该使用普通生成或结构化生成。

最值得记住的是：输出未知时，让模型生成；候选答案已知，而且只需要选择时，让模型评分。评分可以省掉文本生成和解析，还能提供候选项之间的相对强弱。但这些概率必须经过真实标注数据的校准，也必须为未知情况保留“其他”或“升级处理”的出口。

## 深度解读-口播（1）

### 2026-09-21 00:16:43

很多大语言模型调用，其实不需要生成新文本。应用程序早就知道所有可能的答案，只需要模型从中选一个。遇到这种任务，与其让模型写句子或生成 JSON，不如直接读取模型对各个选项的评分。这样既能减少生成开销，也能得到一整套概率分布。

比如，一张客服工单写着：“同一个订阅，我被扣了两次费。”系统只需要把它分到三个团队之一：账单、技术支持，或者账户访问。

普通做法是让大语言模型生成回答。模型可能输出一句话、一个标签，或者一个 JSON 对象。应用程序要等待生成完成，再解析文本，提取分类结果。

但所有合法答案既然已经确定，生成这些文本就显得多余。更直接的做法，是把工单和三个候选答案一起交给模型，让模型一次返回三个分数。比如，账单是百分之九十一，技术支持是百分之六，账户访问是百分之三。系统选择账单，同时也能看出，模型对这个选择有多强的偏好。

这就是 Jev 风格的决策方式。Jev 本身是闭源系统，但类似的推理路径已经可以用开源模型和本地推理服务器实现。文中的方案使用 SGLang 的评分接口，并测试了 Qwen 和 DeepSeek 等模型。需要说明的是，这只能复现 Jev 的评分机制，不包括 Jev 自己的训练、校准和评估体系。

这种固定答案评分，和结构化输出并不一样。

结构化输出可以要求模型返回一个合法的 JSON，例如 team 字段等于 billing。它能保证格式正确，但在底层，模型通常仍然要依次生成左花括号、字段名、字段值和右花括号。也就是说，解码器仍然在逐个生成词元。

固定答案评分则跳过了这段生成过程。系统事先给出全部候选项，直接读取模型对这些候选项的评分。它不仅能返回获胜答案，还能返回完整分布。

完整分布非常重要。假设两次分类都选择账单。第一次，账单的概率是百分之九十一，第二名只有百分之六。第二次，账单是百分之四十六，技术支持是百分之四十四。虽然结果相同，但含义完全不同。第一次偏好明确，可以自动处理。第二次接近平局，更适合交给人工复核。

应用程序还可以在代码中设置规则。比如，第一名必须超过百分之八十，而且至少领先第二名二十个百分点，系统才自动执行。否则就升级处理。这些规则不必写进提示词，可以直接测试和修改。

不过，概率的含义必须说清楚。账单得到百分之九十一，只表示在给定的几个选项中，模型把百分之九十一的概率质量分给了账单。这并不证明模型有百分之九十一的分类准确率。真实准确率和阈值，都需要用带有正确标签的数据进行评估和校准。

为什么只看一次评分，就能做出决策？关键在于大语言模型生成第一个词元时发生了什么。

提示词会先被分词器转换成词元编号。模型处理完整提示后，会为下一个位置输出一个很长的数值向量。这个向量覆盖词表里的每一个词元。每个原始数值叫作 logit。logit 越大，说明模型越倾向于把对应词元放在下一个位置。

正常生成时，服务器会根据温度等规则选择一个词元，把它接到提示后面。然后再次运行模型，预测下一个词元。这个过程不断重复，直到遇到停止标记，或者达到输出长度限制。

但对于固定选项决策，我们只关心第一次输出的向量。

具体做法是，先把三个语义选项映射成简短标签。比如，A 代表账单问题，B 代表技术支持，C 代表账户访问。提示词最后写成：“只返回一个标签。标签是……”模型接下来通常就该输出 A、B 或 C。

服务器不必真的生成这个标签。它只需要在完整词表的输出向量中，找到 A、B、C 对应的位置，取出三个 logit，忽略其他词元，再对这三个数值做 softmax 归一化。最终就能得到三个选项之间的概率分布。

这里的归一化，只发生在声明过的选项之间。它回答的问题不是“A 在整个词表中有多大概率”，而是“在其他回答都被排除后，模型如何在 A、B、C 之间分配偏好”。

之所以使用 A、B、C，而不是直接给“账单”或“技术支持”评分，是因为一个可见的词或短语，不一定只对应一个词元。“技术支持”很可能被拆成多个词元。给多词元短语评分，需要逐个计算，再组合成整个序列的分数，还会遇到长度差异问题。

单词元标签能避开这些麻烦。选项的完整语义仍然写在提示里，A、B、C 只是供系统读取分数的索引。

但单词元标签也不能想当然。不同模型使用不同分词器。同一个字母，在一个模型中可能是一个词元，在另一个模型中可能被拆开。前导空格也可能改变词元编号，聊天模板还可能在答案位置前插入空白或控制标记。

因此，可靠的实现必须先用模型自己的聊天模板渲染提示，再用同一个分词器检查预期答案。如果某个标签不是单一词元，就应该拒绝使用。应用程序对外仍然只暴露“账单”“技术支持”之类的语义选项，字母标签和词元编号都留在评分客户端内部。

还有一个常被忽略的风险：受限评分一定会把全部概率分给现有选项。假如系统只提供账单、技术支持和账户访问，而输入其实是一场安全事件，模型仍然会从三个错误答案中选一个。所以，只要候选项可能不完整，就应该增加“其他”或“升级处理”这样的逃生选项。

本地实现并不复杂。SGLang 可以把 Qwen 等开源模型加载到显卡内存，并开放评分接口。客户端先构造带有字母标签的提示，再确认每个标签只占一个词元，随后向评分接口提交提示和这些标签的词元编号。SGLang 只运行一次提示，读取指定位置的 logit，完成归一化，然后把概率返回给应用程序。

在文中的一次测试里，同一张重复扣费工单被分到三个选项。账单和付款得到大约百分之六十七点八，技术支持得到百分之三十一点一，账户访问得到百分之一点一。账单虽然获胜，但优势并不算特别稳。如果业务规则要求第一名至少达到百分之七十，这张工单就不会自动路由，而会进入审核。

作者还把这种评分方式和普通生成放在同一个本地环境中测试。两条路径使用同一台服务器、同一块显卡和同一个模型。评分路径读取 A、B、C 的下一个词元分数后立刻停止。普通生成路径则继续生成答案和简短解释，最多生成三十二个词元，然后再从文本中解析选项。评分路径更快的原因很直接：它省掉了调用方并不需要的自回归生成循环。

不过，评分不能取代所有生成任务。它只适合输出空间在推理前就已经明确的场景。理想任务应当有一组数量有限、含义清楚的标签，而且每个标签都对应明确的下游操作，例如客服路由、候选人筛选或费用审核。

如果答案内容无法提前枚举，就应该继续使用普通生成。如果需要的是固定语法，但字段值本身未知，可以使用结构化输出。只有在候选答案已经全部知道，而且应用程序只需要一个选择和概率分布时，固定答案评分才最合适。

最值得记住的是：很多所谓的大语言模型生成任务，本质上只是决策任务。候选答案已知时，第一个下一词元向量往往已经包含了所需的排名，没有必要再让模型生成整段文本。但这些分数只是候选项之间的相对偏好，真正用于自动决策之前，仍然需要完整的候选集合、合理的升级选项，以及基于标注数据的阈值和校准。
