## 分析要点

- **核心高价值点**：将Agent能力拆解为工具使用、规划与上下文工程、多Agent协作等层级，并强调多数场景应先把单Agent做到Level 2，而不是盲目堆Multi-Agent。
- **留存建议**：长期保留（文章系统梳理了AI Agent的等级、上下文工程、反思机制、多智能体拓扑和记忆分层，具有较强方法论价值和实践参考价值。）

**知识要点**

- Level 0裸LLM不应被视为真正Agent，至少需要具备自主工具调用能力才进入Level 1。
- Context Engineering关注的是在提问前为Agent筛选、裁剪和组织有效上下文，而不只是优化Prompt措辞。
- Reflection模式建议使用Producer和Critic两个不同Agent，通过迭代审查提升输出质量。
- Multi-Agent并非越复杂越好，常见拓扑包括单Agent、Peer-to-Peer和Supervisor等，应根据任务复杂度选择。
- Agent记忆可分为Session、State和Memory三层，分别对应会话上下文、任务状态和长期持久记忆。

**行动项**

- 为现有Agent工作流增加一个独立Critic角色，用不同system prompt审查输出。
- 检查当前Agent指令文件，补充项目状态、用户偏好、历史决策等上下文信息。
- 优先将单Agent完善到具备工具、Reflection和Memory的Level 2，再考虑引入Multi-Agent架构。
- 为Agent设计Session、State、Memory三层记忆策略，明确存储内容、时机和检索方式。

### Agentic Design Patterns：一本让我重新理解"Agent 到底是什么"的书

Antonio Gullí 是 Google 的工程总监。他写了本 453 页的书，把 AI Agent 开发拆成了 21 种设计模式。

但这不是一篇书评。我读这本书的动机很具体：我写过 Harness Engineering，写过 Clawdbot 的踩坑经验，写过"AI 智能体不是魔法"那篇从烧 Token 到真正好用的七个转折，每次写完之后都有一个没完全想透的问题：这些东西背后有没有一套可以复用的底层逻辑？

这本书给了我答案，而且比我想的更深。

#### 你写的可能根本不是 Agent

书里最狠的判断藏在 prologue 里。

大多数人在用的"AI"，只是 Level 0：裸 LLM，没有工具、没有记忆、不会行动。你问它 2025 年奥斯卡最佳影片是哪部，它猜。书里说得很直白：Level 0 的东西，不是 Agent。

往上走才是真 Agent。

Level 1：工具使用者。 Agent 开始用工具了：搜索、API、数据库。但它不光是"能调接口"，更要自己判断什么时候该调、调什么、结果怎么用。书里给了一个很具体的例子：用户问"最近有什么新剧"，Agent 自己意识到这条信息不在训练数据里，主动调搜索工具去找，然后合成结果。关键一步在"自己意识到"。不是人类告诉它"你去搜一下"，是它自己判断需要搜。这个判断能力，是 Level 1 的门槛。

Level 2：战略思考者。 多了两样东西：规划和 Context Engineering。书里定义了 Context Engineering：不做信息堆砌，做的是精心筛选、裁剪、打包上下文。例子很妙：用户要在两个地点中间找咖啡店。Agent 先调地图工具拿到一堆数据，然后自己判断"下一步只需要街道名称"，把地图输出裁剪成一个短列表，再喂给本地搜索工具。每一步都在做信息降噪。书里有一句话我反复看了几遍："要让 AI 达到最高准确率，必须给它短小、聚焦、有力的上下文。" Context Engineering 就是干这件事的。

到了这个级别，Agent 还能自我反思。干完活后自己审一遍，发现问题自己改。我后面会细讲。

Level 3：多 Agent 协作。 书的立场很明确：别老想着造一个全能 super agent。真正靠谱的做法是像搭团队一样，项目经理 Agent + 研究员 Agent + 设计师 Agent + 文案 Agent。书里举的例子是新产品发布：一个"项目经理 Agent"做总调度，下发任务给"市场研究 Agent"、"产品设计 Agent"、"营销 Agent"。关键是通信：Agent 之间怎么传数据、怎么同步状态、怎么处理冲突。这章画了六种通信拓扑结构，从最简单的单 Agent 到最灵活的自定义混合，每种适合什么场景都有说明。

看完这四个等级，我突然明白为什么很多人说"我的 Agent 不好用"。模型没问题，问题是你在把它当聊天机器人用，它可能连 Level 1 都没到。

![Image](https://pbs.twimg.com/media/HJFvrmWasAAukQa?format=jpg&name=large)

#### Context Engineering：书里最被低估的概念

我写过一篇 Harness Engineering，讲的是赛道的设计比引擎的马力更重要。看完这本书我发现，Context Engineering 就是 Harness Engineering 在 prompt 层面的映射。

传统的 Prompt Engineering 只管"你怎么问"。书里的 Context Engineering 管的是"问之前，Agent 的眼前摆着什么"。它包括四层信息：

第一层，system prompt。定义 Agent 是谁、什么语气、什么边界。大多数人只写了这一层。

第二层，外部数据。RAG 检索到的文档、工具调用的返回值、实时 API 数据。这是大部分人卡住的地方：知道要喂数据，但不知道怎么喂才不会把模型淹没。

第三层，隐式数据。用户身份、交互历史、环境状态。你没明说但 Agent 应该知道的东西。比如你跟 Agent 说"帮我给 John 发邮件确认明天的会议"，它应该知道你日历里明天的会议是什么、你和 John 是什么关系。

第四层，反馈回路。Agent 每次输出之后，自动评估质量、调整下次的上下文策略。书里把这叫"自动化的 context 优化"，Google 的 Vertex AI Prompt Optimizer 就是这个思路的工程化实现。

我读到这里的时候想起之前写那篇"AI 智能体不是魔法"，里面有一条经验是"你的智能体需要规则，而且是很多规则"。现在回头看，那些规则本质上就是 Context Engineering 的手工版，书里把它系统化了。

![Image](https://pbs.twimg.com/media/HJFxJJ-awAAA6G0?format=jpg&name=large)

#### Reflection：两个 Agent 真的比一个好

这是全书对我最有实战价值的一个 Pattern。

Reflection 的核心很简单：Agent 干完活后自己审一遍，发现问题自己改。但实现方式有讲究。书里明确说了：Producer 和 Critic 必须用两个不同的 Agent，给不同的 system prompt。 同一个 persona 审自己的东西，一定有盲区。你让同一个 LLM 先写代码再审查自己写的代码，它大概率会说"挺好的"。

书里给了一个完整的代码示例。Producer 的 prompt 是"你是一个 Python 开发者，写一个计算阶乘的函数，处理边界条件和异常"。Critic 的 prompt 是"你是一个吹毛求疵的高级工程师，逐行审查代码，检查 Bug、风格、遗漏的边界条件、可改进的地方。如果完美就输出 CODE\_IS\_PERFECT，否则列出所有问题"。然后是一个 for 循环：Producer 写代码 → Critic 审 → Producer 根据意见改 → Critic 再审 → 直到 Critic 说 CODE\_IS\_PERFECT 或者达到最大迭代次数。

就这么简单。但书里提醒了一个容易被忽略的成本问题：每次反射循环都是一次新的 LLM 调用，迭代次数越多越贵。而且随着对话历史膨胀，上下文窗口被前期版本和批评意见占满，实际可用的推理空间在缩小。所以 Reflection 的最佳实践是：设一个合理的最大迭代次数（书里用的是 3），一旦 Critic 满意就停，不要追求完美。

用途远不止写代码。写文章、做计划、总结文档、解决逻辑题，Producer-Critic 模型全都能套。书里列了七种应用场景，核心逻辑一样：先产出，后审查，再修正。

![Image](https://pbs.twimg.com/media/HJFxDFRaUAAfmRL?format=jpg&name=large)

#### Multi-Agent 不是越复杂越好

Multi-Agent Collaboration 这章我最喜欢的是那六种通信拓扑图。很多人一上来就搞复杂的，但其实大部分场景三种就够了：

单 Agent（独立执行）： 任务能拆成互不依赖的子问题，每个 Agent 自己搞定自己的。简单，好维护。

对等网络（Peer-to-Peer）： Agent 之间直接通信，没有中心控制节点。去中心化，容错性好，一个 Agent 挂了不影响全局。但协调成本高，容易乱。

Supervisor（中心调度）： 一个 Supervisor Agent 管一群 Worker Agent。分配任务、收集结果、解决冲突。层级清晰，好管理。但 Supervisor 是单点故障，也是性能瓶颈。

另外三种（Supervisor-as-Tool、层级式、自定义混合）是前三者的变体和组合。书里说得很实在：你需要的拓扑结构取决于你的任务复杂度。 任务越拆越碎，通信成本越高，到一定程度 Supervisor 模式反而比层级式更有效率。

我的体会是，很多人搭 Multi-Agent 的时候花了 80% 的时间在通信协议上，忘了问一个更基本的问题：这个任务真的需要多个 Agent 吗？ 书里写得很清楚，Level 2 的单 Agent + Reflection 往往已经够用了。Level 3 是给那些单 Agent 确实搞不定的场景准备的。

![Image](https://pbs.twimg.com/media/HJFwZ9rawAAZjsZ?format=jpg&name=large)

#### Memory 三层模型，我之前隐约感觉到了但没命名

Memory 这章我最有共鸣，因为我写 Obsidian + Claude 那两篇文章的时候，一直在琢磨一个问题：Agent 的记忆该怎么分层？

书里给了答案。

Session（会话层）： 当前对话的上下文窗口，这是最短的记忆，对话结束就没了。长上下文模型只是把这个窗口放大了，但本质上还是临时的，而且每次推理都要处理整个窗口，又贵又慢。

State（状态层）： 当前任务进行中的临时数据。比如"正在做的任务是什么"，"已经完成到哪一步""中间产生了哪些数据"。比 Session 长，但任务结束就清理，书里用 Google ADK 的 State 机制做了完整示例。

Memory（持久层）： 跨会话、跨任务的长期记忆。用户偏好、学到的经验、重要的历史决策，存数据库或向量库里，语义检索。书里强调了一个很重要的点：Memory 不只是存下来，还要设计"存什么、什么时候存、怎么检索"的一整套策略。存太多了噪声大，存少了不够用。

我之前写 Clawdbot 那篇文章里提到"状态文件"和"工作区文档"，本质上就是在手搓 State 层和 Memory 层，书里把这件事框架化了。

![Image](https://pbs.twimg.com/media/HJFx4NWbwAA4214?format=jpg&name=large)

#### 五种假设，第五个最离谱

书末提了五个关于 Agent 未来的假设，前四个还在合理推演范围内：

通用型 Agent 从写代码到管项目、深度个性化主动发现你的需求、具身智能走出屏幕进物理世界、Agent 成为独立经济实体。

第五个把我震住了：变形 Multi-Agent。 你只声明目标，比如"做一个卖精品咖啡的电商生意"。系统自动决定：先创建"市场研究 Agent"和"品牌 Agent"。跑了一轮数据后，自己判断品牌 Agent 不需要了，拆成三个新的："Logo 设计 Agent"、"建站 Agent"、"供应链 Agent"。如果建站 Agent 成了瓶颈，系统会自动复制出三个并行 Agent 同时干不同的页面。整个过程中，系统持续自动调优每个 Agent 的 prompt，不断重组团队架构。

书里管这叫"目标驱动的、自我变形的多 Agent 系统"。它不是在执行你写的计划，是在自己生成计划、自己调整计划、自己重组执行团队。

这让我想起 Karpathy 的 AutoResearch：写一个 program.md，定义目标、指标、边界，按"启动"。人类在循环外面。但这本书推得更远：连 Agent 团队怎么组建、怎么重组，都交给系统自己决定。人类只声明"要什么"。

![Image](https://pbs.twimg.com/media/HJFwzoYbcAAulEY?format=jpg&name=large)

#### 三件可以马上做的事

读完这本书，我有三个立刻可以落地的动作：

第一，给你现在的 Agent 加一个 Critic。 不管你是用 Claude Code、CrewAI 还是自己搭的框架，在你现有的 workflow 末尾加一步：让另一个 Agent（用不同的 system prompt）审查上一步的输出。代码生成加代码审查，文章撰写加事实核查，计划制定加可行性评审。多一次 LLM 调用，但质量提升往往翻倍。书里的 Producer-Critic 模式是即插即用的。

第二，开始做 Context Engineering，不只是 Prompt Engineering。 回头看你写给 Agent 的指令文件。如果全是"你要怎么做"的规则，缺少"你现在面对什么环境"的上下文，补上。告诉 Agent 它现在在哪个项目里、之前做过什么决定、用户偏好是什么。书里的 Context Engineering 那章和你的 AGENTS.md 是同一件事的两个表述。

第三，先别急着上 Multi-Agent。 把你的单 Agent 做到 Level 2：有工具、有 Reflection、有 Memory。书里反复强调，Level 2 的单 Agent 加上 Producer-Critic 和 Context Engineering，能覆盖绝大多数实际场景。Level 3 是给真正跨领域、多阶段、需要并行分工的任务准备的。大多数人的问题不是 Agent 不够多，是一个 Agent 都没调好。

这本书 453 页，Springer 2025 年出版。代码示例覆盖LangChain/LangGraph、Google ADK、CrewAI、OpenAI API。前言是 Google Cloud AI VP 写的，还有个 Goldman Sachs CIO 的推荐序，意外地好看。

但我推荐它的理由不是"全面"。是你读完会意识到一件事：你过去半年在 Agent 上踩的坑，都有人整理成模式了。你不需要再去发明 Reflection，不需要再去猜 Memory 该怎么分层，不需要再去试 Multi-Agent 该用哪种通信拓扑。

有人替你画了地图，剩下的就是走。

## 解读（1）

### 2026-06-02 07:43:49

#### 一、总结

这篇文章介绍了一本关于 **AI Agent 设计模式** 的书：  
Google 工程总监 Antonio Gullí 将 Agent 开发拆成了 **21 种设计模式**。

核心观点：

- 很多所谓的 AI Agent，其实只是 **普通聊天机器人**
- 真正的 Agent 需要具备：
  - 工具调用
  - 规划能力
  - 上下文管理
  - 反思修正
  - 记忆系统
  - 多 Agent 协作

作者认为，Agent 不是“让大模型回答问题”，而是要设计一套能 **判断、行动、反馈、优化** 的系统。

---

#### 二、解读

##### 1. 什么才是真 Agent？

文章把 Agent 分成几个等级：

| 等级 | 特征 | 是否像 Agent |
|---|---|---|
| Level 0 | 只会聊天，没有工具和记忆 | 不是 |
| Level 1 | 会主动使用工具 | 初级 Agent |
| Level 2 | 会规划、反思、管理上下文 | 实用 Agent |
| Level 3 | 多个 Agent 协作 | 高级 Agent |

一句话：

> 如果 AI 只是回答你，它不是 Agent；  
> 如果 AI 会判断该做什么、调用工具、检查结果，它才像 Agent。

---

##### 2. Context Engineering 比 Prompt 更重要

传统 Prompt Engineering 关注：

> “我该怎么问？”

Context Engineering 关注：

> “模型在回答前，应该看到什么信息？”

它包括：

- 系统角色
- 外部资料
- 用户历史
- 当前任务状态
- 输出后的反馈

通俗说：

> Prompt 是提问方式，Context 是给 AI 准备工作台。  
> 工作台乱，AI 再聪明也容易做错。

---

##### 3. Reflection：让另一个 Agent 来挑错

文章强调一个很实用的模式：

> 一个 Agent 负责生成，另一个 Agent 负责批评。

比如：

- A 写代码
- B 审代码
- A 根据意见修改
- B 再检查

重点是：

> 不要让同一个 Agent 自己审自己。  
> 人会自我合理化，模型也会。

这个模式简单，但非常有效。

---

##### 4. 多 Agent 不是越多越好

很多人一上来就搞多个 Agent 协作，但文章提醒：

> 多 Agent 会带来通信成本、协调成本和系统复杂度。

大多数场景下：

> 一个 Level 2 Agent + Reflection + Memory 已经够用。

多 Agent 更适合：

- 跨领域任务
- 多阶段任务
- 需要并行分工的复杂项目

不要为了“高级”而复杂化。

---

##### 5. Memory 要分层

Agent 的记忆分三层：

| 层级 | 含义 |
|---|---|
| Session | 当前对话记忆 |
| State | 当前任务状态 |
| Memory | 长期记忆 |

关键不是“都存下来”，而是：

> 存什么、什么时候存、怎么取出来。

否则记忆越多，噪声越大。

---

#### 三、我的意见

我觉得这篇文章最有价值的提醒是：

> Agent 不是一个模型，而是一套系统设计。

很多 Agent 不好用，不是模型不够强，而是缺少：

- 工具设计
- 上下文设计
- 状态管理
- 质量审查
- 记忆策略

如果现在要改进自己的 Agent，我建议按这个顺序来：

1. **先加工具**：让它能查资料、调用 API、读文件  
2. **再加 Critic**：让另一个 Agent 审查结果  
3. **然后做 Context Engineering**：别乱塞上下文，只给关键内容  
4. **最后再考虑多 Agent**：不要一开始就复杂化  

最重要的一句话：

> 先把一个 Agent 调好，再谈一群 Agent 协作。

## 结构化（1）

### 2026-06-02 07:55:03

##### 主旨概括

文章借 Antonio Gullí 的《Agentic Design Patterns》一书，重新梳理了“AI Agent 到底是什么”。作者认为，真正的 Agent 不是简单聊天机器人，而是具备工具使用、规划、上下文管理、反思、记忆甚至多 Agent 协作能力的系统。

---

##### 1. 很多人写的其实还不是 Agent

作者认为，很多所谓“AI Agent”只是 **Level 0：裸 LLM**，没有工具、没有记忆、不会行动，本质上仍是聊天机器人。

###### Agent 的四个等级

###### Level 0：裸 LLM

- 只有语言模型本身。
- 不能调用工具，也没有实时信息。
- 例如问它“2025 年奥斯卡最佳影片是哪部”，它只能猜。
- 书中明确指出：**Level 0 不是 Agent**。

###### Level 1：工具使用者

- Agent 能调用搜索、API、数据库等工具。
- 关键不只是“能调接口”，而是能自己判断：
  - 什么时候该调工具；
  - 调哪个工具；
  - 如何使用工具返回的结果。
- 例子：用户问“最近有什么新剧”，Agent 判断训练数据里没有最新信息，于是主动调用搜索工具，再整理答案。
- 关键门槛是：**Agent 自己意识到需要搜索，而不是人类告诉它去搜**。

###### Level 2：战略思考者

- 在工具使用基础上，增加了：
  - 规划能力；
  - Context Engineering；
  - 自我反思。
- Context Engineering 不是堆信息，而是筛选、裁剪、打包上下文。
- 例子：用户要在两个地点中间找咖啡店：
  1. Agent 先用地图工具获取大量数据；
  2. 再判断下一步只需要街道名称；
  3. 将地图结果裁剪为短列表；
  4. 再交给本地搜索工具。
- 核心原则是：**给 AI 短小、聚焦、有力的上下文，准确率才更高**。

###### Level 3：多 Agent 协作

- 不追求一个“万能 super agent”，而是像组团队一样分工。
- 例子：新产品发布项目中：
  - 项目经理 Agent 负责调度；
  - 市场研究 Agent 负责调研；
  - 产品设计 Agent 负责设计；
  - 营销 Agent 负责推广。
- 重点不只是分工，而是 Agent 之间如何：
  - 传递数据；
  - 同步状态；
  - 处理冲突。

作者总结：很多 Agent 不好用，不是模型差，而是还停留在聊天机器人阶段，可能连 Level 1 都没达到。

---

##### 2. Context Engineering 是被低估的核心能力

作者认为，Context Engineering 是全书最重要但容易被忽略的概念。它类似于作者之前提到的 Harness Engineering：不是只看模型能力，而是看你如何给模型设计“环境”和“输入条件”。

###### Prompt Engineering 与 Context Engineering 的区别

- Prompt Engineering 关注：**你怎么问**。
- Context Engineering 关注：**问之前，Agent 眼前摆着什么信息**。

###### Context Engineering 的四层信息

###### 第一层：System Prompt

- 定义 Agent 的身份、语气、能力边界。
- 例如：“你是一个严谨的 Python 工程师。”
- 大多数人只做到了这一层。

###### 第二层：外部数据

- 包括：
  - RAG 检索到的文档；
  - 工具调用结果；
  - 实时 API 数据。
- 难点是：不是简单把数据塞给模型，而是避免把模型“淹没”。

###### 第三层：隐式数据

- 用户没有明确说，但 Agent 应该知道的信息。
- 例如用户说：“帮我给 John 发邮件确认明天的会议。”
- Agent 应该知道：
  - 明天是哪场会议；
  - John 是谁；
  - 用户和 John 的关系；
  - 邮件应使用什么语气。

###### 第四层：反馈回路

- Agent 输出后，自动评估质量，并调整下一次上下文策略。
- 书中称为“自动化的 context 优化”。
- Google 的 Vertex AI Prompt Optimizer 就是这种思路的工程化实现。

作者认为，以前很多人给 Agent 写大量规则，其实就是在手工做 Context Engineering；这本书把它系统化了。

---

##### 3. Reflection：两个 Agent 往往比一个更可靠

Reflection 是作者认为最有实战价值的设计模式。

###### Reflection 的核心逻辑

Agent 完成任务后，不直接结束，而是进入审查和修改循环：

1. Producer Agent 先产出内容；
2. Critic Agent 审查内容；
3. Producer 根据批评意见修改；
4. Critic 再次审查；
5. 直到满意或达到最大迭代次数。

###### 为什么要两个 Agent？

书中特别强调：**Producer 和 Critic 必须是两个不同的 Agent，并使用不同的 system prompt**。

原因是同一个 persona 审查自己的产出容易有盲区。例如：

- 让同一个 LLM 写代码再审查代码，它可能会认为“挺好的”；
- 但如果换成一个“吹毛求疵的高级工程师”角色来审查，就更容易发现问题。

###### 书中的代码示例

Producer 的任务：

> 你是一个 Python 开发者，写一个计算阶乘的函数，处理边界条件和异常。

Critic 的任务：

> 你是一个吹毛求疵的高级工程师，逐行审查代码，检查 Bug、风格、遗漏的边界条件和可改进之处。如果完美就输出 CODE_IS_PERFECT，否则列出所有问题。

然后通过循环实现：

```text
Producer 写代码
→ Critic 审查
→ Producer 修改
→ Critic 再审
→ 直到 CODE_IS_PERFECT 或达到最大迭代次数
```

###### 成本提醒

Reflection 虽然有效，但有成本：

- 每次反思都是一次新的 LLM 调用；
- 迭代越多，费用越高；
- 对话历史变长后，会占用上下文窗口；
- 前期版本和批评意见太多，会压缩真正推理空间。

书中建议设置最大迭代次数，比如 **3 次**，满意就停止，不要追求无限完美。

###### 可应用场景

Reflection 不只适合写代码，也适合：

- 写文章；
- 做计划；
- 总结文档；
- 解决逻辑题；
- 做事实核查；
- 评审方案可行性。

核心都是：**先产出，再审查，再修正**。

---

##### 4. Multi-Agent 不是越复杂越好

书中讲了多 Agent 协作的六种通信拓扑。作者认为，大多数实际场景只需要其中三种。

###### 三种常见通信模式

###### 1. 单 Agent 独立执行

- 适合任务可以拆成互不依赖的小问题。
- 每个 Agent 只管自己的部分。
- 优点：
  - 简单；
  - 好维护；
  - 成本低。

###### 2. Peer-to-Peer 对等网络

- Agent 之间直接通信，没有中心控制节点。
- 优点：
  - 去中心化；
  - 容错性好；
  - 一个 Agent 挂了不影响整体。
- 缺点：
  - 协调成本高；
  - 容易混乱。

###### 3. Supervisor 中心调度

- 一个 Supervisor Agent 管理多个 Worker Agent。
- Supervisor 负责：
  - 分配任务；
  - 收集结果；
  - 解决冲突。
- 优点：
  - 层级清晰；
  - 易管理。
- 缺点：
  - Supervisor 是单点故障；
  - 也可能成为性能瓶颈。

###### 另外三种模式

另外三种包括：

- Supervisor-as-Tool；
- 层级式；
- 自定义混合。

它们本质上是前三种模式的变体和组合。

###### 作者的判断

多 Agent 的结构取决于任务复杂度。任务越拆越碎，通信成本越高。很多人花了 80% 时间设计通信协议，却忘了先问：

> 这个任务真的需要多个 Agent 吗？

作者认为，很多场景下，**Level 2 的单 Agent + Reflection 已经足够**。Level 3 适合那些真正跨领域、多阶段、需要并行分工的复杂任务。

---

##### 5. Memory：Agent 记忆应该分三层

作者对书中的 Memory 模型很有共鸣，因为它把 Agent 的记忆清晰分成三层。

###### 第一层：Session，会话层

- 当前对话的上下文窗口。
- 是最短期的记忆。
- 对话结束后通常就消失。
- 长上下文模型只是把窗口变大，但本质仍是临时记忆。
- 缺点是每次推理都要处理整个窗口，成本高、速度慢。

###### 第二层：State，状态层

- 保存当前任务进行中的临时数据。
- 例如：
  - 当前任务是什么；
  - 已经做到哪一步；
  - 中间产生了哪些数据。
- 比 Session 更持久，但任务结束后通常会清理。
- 书中用 Google ADK 的 State 机制做了完整示例。

###### 第三层：Memory，持久层

- 跨会话、跨任务长期保存的信息。
- 包括：
  - 用户偏好；
  - 学到的经验；
  - 重要历史决策。
- 通常存储在数据库或向量库中，并通过语义检索调用。

书中强调，Memory 不是简单“存下来”就行，而是要设计完整策略：

- 存什么；
- 什么时候存；
- 怎么检索；
- 如何避免噪声。

作者认为，自己之前做的“状态文件”和“工作区文档”，本质上就是手工实现 State 层和 Memory 层。

---

##### 6. 关于 Agent 未来的五个假设

书末提出了五个关于 Agent 未来的假设，其中前四个较容易理解，第五个最具想象力。

###### 前四个假设

1. **通用型 Agent**
   - 能从写代码扩展到管理项目。

2. **深度个性化 Agent**
   - 能主动发现用户需求，而不是只被动响应。

3. **具身智能**
   - Agent 走出屏幕，进入物理世界。

4. **Agent 成为独立经济实体**
   - Agent 可能拥有更独立的交易、决策和执行能力。

###### 第五个假设：变形 Multi-Agent

这是最震撼作者的一点。

用户只声明目标，例如：

> 做一个卖精品咖啡的电商生意。

系统会自动决定需要哪些 Agent：

1. 先创建“市场研究 Agent”和“品牌 Agent”；
2. 跑完一轮数据后，系统判断品牌 Agent 不够细；
3. 自动拆成：
   - Logo 设计 Agent；
   - 建站 Agent；
   - 供应链 Agent；
4. 如果建站 Agent 成为瓶颈，系统自动复制多个 Agent，并行完成不同页面；
5. 系统还会持续优化每个 Agent 的 prompt，并重组团队架构。

书中称之为：

> 目标驱动的、自我变形的多 Agent 系统。

它不是执行人类写好的计划，而是自己生成计划、调整计划、重组执行团队。人类只需要声明“要什么”。

---

##### 7. 读完后可以马上做的三件事

作者最后总结了三个立刻可落地的动作。

###### 第一，给现有 Agent 加一个 Critic

无论使用 Claude Code、CrewAI，还是自己搭框架，都可以在 workflow 末尾加一步审查。

例如：

- 代码生成后，加代码审查 Agent；
- 文章写完后，加事实核查 Agent；
- 计划制定后，加可行性评审 Agent。

虽然会多一次 LLM 调用，但质量往往明显提升。

###### 第二，开始做 Context Engineering

不要只写“你应该怎么做”的规则，也要告诉 Agent：

- 当前在哪个项目；
- 之前做过什么决定；
- 用户偏好是什么；
- 当前环境和限制是什么。

作者认为，Context Engineering 和 AGENTS.md 本质上是在做同一件事：为 Agent 组织有效上下文。

###### 第三，不要急着上 Multi-Agent

先把单 Agent 做到 Level 2：

- 有工具；
- 有 Reflection；
- 有 Memory；
- 有良好的上下文管理。

作者认为，多数人的问题不是 Agent 不够多，而是连一个 Agent 都还没调好。

#### 《Agentic Design Patterns》精炼拆解：重新理解 Agent 的底层逻辑

##### 一、核心启发

###### 1. Agent 不是“会聊天的 LLM”，而是“能判断、行动、修正的系统”

很多所谓 AI Agent，其实只是裸 LLM：

- 没有工具；
- 没有记忆；
- 没有状态；
- 没有反思；
- 没有行动能力；
- 不能自主判断下一步。

真正的 Agent，关键不在于“模型多强”，而在于它是否具备：

> 感知上下文 → 判断任务 → 调用工具 → 执行行动 → 评估结果 → 修正策略 的闭环能力。

这意味着，Agent 更像一个“业务系统”，而不是一个“Prompt”。

---

###### 2. Agent 的能力分层，决定了你的系统上限

文章中提到的四个 Level 很有价值：

| 层级 | 类型 | 核心能力 | 常见问题 |
|---|---|---|---|
| Level 0 | 裸 LLM | 回答问题 | 幻觉、无实时性、不会行动 |
| Level 1 | 工具使用者 | 自主判断是否调用工具 | 工具可用但调不好 |
| Level 2 | 战略思考者 | 规划、Context Engineering、Reflection、Memory | 单 Agent 复杂度上升 |
| Level 3 | 多 Agent 协作 | 多角色分工、通信、调度 | 协调成本高、系统脆弱 |

最重要的判断是：

> 大多数产品并不需要一开始就做 Level 3，多数场景先把 Level 2 做好就够了。

这对产品开发非常关键。很多团队一上来就做 Multi-Agent，其实是在用架构复杂度掩盖基础能力不足。

---

###### 3. Context Engineering 可能比 Prompt Engineering 更重要

Prompt Engineering 关注的是：

> 我该怎么问？

Context Engineering 关注的是：

> 在模型回答之前，它应该看到什么？

后者更接近真实产品开发。

因为在商业系统里，用户真正需要的不是一个“会回答的模型”，而是一个能理解：

- 用户是谁；
- 当前任务是什么；
- 已经发生了什么；
- 哪些信息可信；
- 哪些信息应该被忽略；
- 哪些工具可以使用；
- 当前业务目标是什么；

的智能工作流。

一句话：

> Prompt 是指令，Context 是环境。  
> 真正决定 Agent 质量的，是环境设计。

---

###### 4. Reflection 是最容易落地、性价比最高的 Agent Pattern

Producer-Critic 模型非常值得产品团队优先采用。

流程是：

```text
Producer 产出结果
↓
Critic 审查结果
↓
Producer 根据批评修正
↓
Critic 再审查
↓
直到通过或达到最大轮次
```

它的价值在于：

- 不改变原有工作流；
- 不需要复杂多 Agent 编排；
- 质量提升明显；
- 适用于代码、文案、计划、总结、分析、客服回复等大量场景。

但关键点是：

> Producer 和 Critic 必须是两个不同 persona，最好有不同 system prompt。

同一个 Agent 自审容易陷入“自我确认偏误”。

---

###### 5. Multi-Agent 的本质不是“多个智能体”，而是“组织设计”

多 Agent 系统不是简单地把几个 Agent 拼在一起，而是在设计一个数字组织。

你需要回答：

- 谁负责决策？
- 谁负责执行？
- 谁负责审查？
- 谁负责冲突解决？
- 状态如何同步？
- 任务如何拆分？
- 结果如何合并？
- 谁对最终结果负责？

因此，Multi-Agent 更接近：

> 组织结构设计 + 流程管理 + 信息流设计 + 质量控制。

它不是技术炫技，而是系统工程。

---

##### 二、高价值信息深挖

##### 1. Context Engineering 的四层结构

文章中总结的四层上下文非常重要，可以直接迁移到产品设计中。

###### 第一层：System Prompt

定义 Agent 的身份、边界、职责、语气和约束。

例如：

```text
你是一个 SaaS 产品增长顾问。
你的目标是帮助用户发现增长瓶颈，并给出可执行建议。
你不能编造数据。
如果信息不足，必须提出澄清问题。
```

这是很多人唯一会做的一层，但它远远不够。

---

###### 第二层：外部数据

包括：

- RAG 检索结果；
- 数据库信息；
- API 返回值；
- 搜索结果；
- 工具调用输出；
- 实时业务数据。

这里的难点不是“拿到数据”，而是：

> 如何筛选、压缩、排序、格式化后再交给模型。

模型不需要看到所有数据，它需要看到“当前任务最相关的数据”。

---

###### 第三层：隐式数据

这是很多 Agent 产品缺失的一层。

包括：

- 用户身份；
- 用户偏好；
- 历史交互；
- 当前项目状态；
- 用户所属公司；
- 已做过的决策；
- 已失败过的尝试；
- 业务上下文。

例如，用户说：

> 帮我写一封邮件给 John，确认明天会议。

真正好的 Agent 应该知道：

- John 是谁；
- 明天是哪场会议；
- 会议主题是什么；
- 用户和 John 的关系；
- 用户偏好的邮件语气；
- 是否需要附带议程。

这才是“像助手”的体验。

---

###### 第四层：反馈回路

这是 Agent 走向系统化的关键。

Agent 不只是完成一次任务，而是不断学习：

- 哪类上下文有效；
- 哪类信息是噪声；
- 哪些工具调用成功率高；
- 哪些回答用户经常修改；
- 哪些输出经常被 Critic 驳回；
- 哪些任务需要更多前置澄清。

这会让 Agent 从“单次响应系统”变成“可优化系统”。

---

##### 2. Memory 的三层模型

Agent 的记忆不能简单理解成“把历史聊天记录塞进去”。

更合理的是三层：

| 类型 | 作用 | 生命周期 | 示例 |
|---|---|---|---|
| Session | 当前对话上下文 | 对话结束即消失 | 本轮聊天内容 |
| State | 当前任务状态 | 任务结束后清理 | 当前任务进度、中间结果、待办项 |
| Memory | 长期记忆 | 跨任务、跨会话保留 | 用户偏好、历史决策、项目背景 |

###### 关键洞察

记忆系统的难点不是存储，而是策略：

```text
存什么？
什么时候存？
怎么更新？
怎么检索？
什么时候遗忘？
如何避免噪声污染？
```

没有策略的 Memory 会迅速变成垃圾场。

---

##### 3. Reflection 的商业价值

Reflection 不只是提高输出质量，它还能带来产品层面的价值：

###### 对用户而言

- 更少低级错误；
- 更高可信度；
- 更少人工返工；
- 更接近“交付物”而非“草稿”。

###### 对产品而言

- 可以形成质量控制模块；
- 可以记录 Critic 反馈作为优化数据；
- 可以降低幻觉风险；
- 可以增强用户信任；
- 可以将“审核”产品化。

###### 对企业系统而言

Reflection 可以变成自动化 QA：

```text
内容生成 → 合规审查
代码生成 → 安全审查
数据分析 → 逻辑审查
合同草拟 → 法务审查
客服回复 → 风险审查
产品方案 → 可行性审查
```

这比单纯追求更强模型更务实。

##### 三、可迁移清单

##### 1. 判断你现在的 Agent 到了 Level 几

可以用下面的问题自查：

###### Level 0：裸 LLM

- 是否只能回答问题？
- 是否不会主动调用工具？
- 是否没有记忆？
- 是否不能执行动作？
- 是否依赖用户明确告诉它每一步？

如果是，它不是 Agent，只是聊天机器人。

---

###### Level 1：工具使用者

检查：

- 是否可以调用搜索、数据库、API、代码执行器？
- 是否能自主判断什么时候该调用工具？
- 是否能理解工具返回结果？
- 是否能根据工具结果继续推理？
- 是否能在工具失败时换策略？

---

###### Level 2：战略思考者

检查：

- 是否能拆解任务？
- 是否能规划多步骤执行？
- 是否有状态管理？
- 是否有长期记忆？
- 是否有 Reflection 机制？
- 是否能压缩和筛选上下文？
- 是否能根据结果调整下一步？

---

###### Level 3：多 Agent 协作

检查：

- 是否存在不同角色 Agent？
- 是否有 Supervisor 或协调机制？
- 是否有任务分配逻辑？
- 是否有冲突处理机制？
- 是否有通信协议？
- 是否能合并多个 Agent 的结果？
- 是否有全局状态管理？

---

##### 2. 给现有 AI 产品加 Critic 的清单

可以马上落地：

```text
1. 找出当前工作流的关键输出
2. 为每类输出设计一个 Critic 角色
3. 给 Critic 写独立 system prompt
4. 明确 Critic 的审查维度
5. 设置最大迭代次数，建议 2-3 次
6. 如果通过，进入交付
7. 如果不通过，返回 Producer 修改
8. 记录 Critic 反馈，用于后续优化
```

###### 示例：文章生成 Critic

审查维度：

- 是否有事实错误；
- 是否逻辑连贯；
- 是否有重复表达；
- 是否有空泛观点；
- 是否符合目标读者；
- 是否有可执行建议；
- 是否有标题党或过度承诺。

---

###### 示例：代码生成 Critic

审查维度：

- 是否有 bug；
- 是否处理边界条件；
- 是否有安全风险；
- 是否符合项目规范；
- 是否可维护；
- 是否有测试；
- 是否存在性能问题。

---

###### 示例：商业方案 Critic

审查维度：

- 假设是否成立；
- 数据是否充分；
- 是否有执行路径；
- 是否考虑成本；
- 是否考虑竞争；
- 是否考虑失败风险；
- 是否能落地到具体动作。

##### 3. Context Engineering 检查清单

每次设计 Agent 时，问自己：

```text
这个 Agent 需要知道什么？
哪些信息是必须的？
哪些信息是噪声？
哪些上下文应该动态检索？
哪些上下文应该长期保存？
哪些上下文应该每次都传？
哪些上下文只在特定任务触发？
工具返回结果是否需要压缩？
历史记录是否需要摘要？
用户偏好是否需要记忆？
是否有机制评估上下文质量？
```

##### 4. Memory 设计清单

不要直接“保存所有历史”。

应该分层设计：

###### Session

保存：

- 当前对话；
- 本轮任务要求；
- 临时约束。

不保存：

- 无关闲聊；
- 已过期信息；
- 重复内容。

---

###### State

保存：

- 当前任务目标；
- 已完成步骤；
- 待完成步骤；
- 中间产物；
- 工具调用结果；
- 用户确认过的决策。

任务结束后：

- 有价值的信息转入 Memory；
- 临时数据清理。

---

###### Memory

保存：

- 用户长期偏好；
- 项目背景；
- 重要历史决策；
- 高频需求；
- 禁忌事项；
- 过去有效的方法；
- 过去失败的尝试。

同时要设计：

```text
写入规则
更新规则
遗忘规则
召回规则
冲突解决规则
```

##### 5. Multi-Agent 拓扑选择清单

###### 如果任务简单

用单 Agent。

适合：

- 单轮问答；
- 简单总结；
- 单一工具调用；
- 明确步骤任务。

---

###### 如果任务复杂但领域单一

用 Level 2 单 Agent + Reflection。

适合：

- 写代码；
- 写文章；
- 生成方案；
- 数据分析；
- 用户研究总结；
- 产品需求文档。

---

###### 如果任务涉及多个专业角色

用 Supervisor 模式。

适合：

- 新产品发布；
- 投研报告；
- 市场进入策略；
- 复杂内容生产；
- 跨部门流程自动化。

结构：

```text
Supervisor Agent
├── Research Agent
├── Analysis Agent
├── Writer Agent
├── Critic Agent
└── Execution Agent
```

---

###### 如果任务高度动态且不确定

再考虑复杂 Multi-Agent。

适合：

- 自动创业项目；
- 自动研究系统；
- 多阶段软件开发；
- 自主运营系统；
- 长周期项目管理。

##### 四、反方与张力

##### 1. Reflection 提升质量，但会增加成本和延迟

Reflection 的代价是：

- 更多 LLM 调用；
- 更高 token 成本；
- 更长响应时间；
- 更复杂的上下文管理。

所以它不适合所有场景。

适合：

- 高价值输出；
- 高风险任务；
- 需要交付质量的内容；
- 代码、安全、合规、财务等领域。

不适合：

- 低价值闲聊；
- 简单查询；
- 用户期待即时响应的场景；
- 对质量要求不高的轻任务。

核心权衡：

> 质量提升是否值得额外成本？

---

##### 2. Context 越多不等于效果越好

很多人以为上下文越多越好，但文章指出：

> 要让 AI 达到最高准确率，必须给它短小、聚焦、有力的上下文。

这和直觉相反。

过多上下文会导致：

- 模型注意力分散；
- 关键信息被稀释；
- 推理成本上升；
- 响应速度变慢；
- 幻觉风险增加；
- 引入过期或冲突信息。

所以 Context Engineering 的目标不是“多给信息”，而是“只给当前任务最有用的信息”。

---

##### 3. Multi-Agent 看起来高级，但可能制造更多问题

Multi-Agent 的风险包括：

- 通信成本上升；
- 状态同步困难；
- 结果冲突；
- 调试困难；
- 责任不清；
- 单点瓶颈；
- 系统不可预测。

很多时候，问题不是 Agent 不够多，而是：

```text
工具没设计好
上下文没设计好
状态没管理好
反思机制没有
记忆策略混乱
任务边界不清
```

在这些问题没解决之前，上 Multi-Agent 只会让系统更乱。

---

##### 4. 记忆让 Agent 更智能，也让系统更危险

Memory 有明显价值：

- 更个性化；
- 更连续；
- 更像真正助手；
- 更适合长期任务。

但也带来风险：

- 记错信息；
- 保存过期偏好；
- 隐私泄露；
- 错误记忆污染后续决策；
- 用户无法理解 Agent 为什么这么做；
- 记忆过多导致噪声。

因此，Memory 必须可控：

```text
可查看
可编辑
可删除
可过期
可解释
可授权
```

---

##### 5. 自我变形 Multi-Agent 很诱人，但目前仍有强不确定性

“目标驱动、自我变形的多 Agent 系统”想象力很大：

用户只说目标，系统自动创建、拆分、复制、重组 Agent 团队。

但现实挑战巨大：

- 目标如何形式化？
- 成功指标如何定义？
- 谁来约束成本？
- Agent 复制是否会失控？
- 错误策略如何及时停止？
- 任务边界如何管理？
- 人类何时介入？
- 责任如何归属？

这类系统更接近“自主经营系统”，不是简单工具。

真正落地前，需要强约束：

```text
预算上限
权限边界
人工审批点
日志审计
失败回滚
安全策略
阶段性评估
```

##### 场景三：企业内部知识助手

###### 常见误区

很多企业知识库 Agent 只是：

#### 最重要的结论

##### 1. Agent 是系统，不是 Prompt

Prompt 只是入口，真正的 Agent 由这些部分组成：

```text
模型
工具
上下文
状态
记忆
规划
反思
评估
权限
通信
反馈回路
```

---

##### 2. 先做 Level 2，再考虑 Level 3

大多数实际场景的最优解不是 Multi-Agent，而是：

```text
单 Agent
+ 工具使用
+ Context Engineering
+ State 管理
+ Memory
+ Reflection
```

这已经可以覆盖大量开发、内容、分析、运营、客服、知识管理场景。

---

##### 3. 最值得马上做的三件事

###### 第一，给现有 Agent 加 Critic

这是最快提升质量的方法。

---

###### 第二，重新设计 Context

不要只写“你要怎么做”，还要告诉 Agent：

```text
你在哪里？
你面对什么任务？
你知道哪些背景？
你应该忽略什么？
你可以调用哪些工具？
你之前做过什么决定？
```

---

###### 第三，建立 Memory 分层

区分：

```text
Session：当前对话
State：当前任务状态
Memory：长期记忆
```

不要把所有东西都塞进聊天上下文。

#### 一句话总结

> 真正的 AI Agent，不是一个更会说话的模型，而是一个具备上下文、工具、记忆、反思和行动闭环的可进化系统。  
> 产品开发的关键，不是盲目堆 Agent，而是先把单个 Agent 的系统能力做到位。

## 深度解读（1）

### 2026-09-18 01:00:05

#### Agent 的关键不是“会思考”，而是能否形成可控的行动闭环

这篇文章最值得保留的，不是把 Agent 分成四个等级，也不是 21 种模式本身，而是提供了一套更准确的判断方式：**Agent 不是套着人格提示词的聊天机器人，而是一个围绕目标持续获取信息、采取行动、保存状态并校正结果的系统。**

按这个标准，许多所谓 Agent 确实只是 Level 0：模型可以生成答案，却不能判断何时需要外部信息，更无法对现实世界产生可靠影响。真正的分界线不在“回答得像不像人”，而在于它能否完成一个闭环：识别信息缺口，选择工具，处理返回结果，执行下一步，并判断任务是否完成。

##### Context Engineering 本质上是注意力预算管理

文章对 Context Engineering 的强调，比“多 Agent”更有长期价值。模型能力再强，每次推理能有效处理的信息仍然有限。把全部历史记录、检索文档和工具返回值塞进去，不等于提供了更充分的信息，反而可能让关键约束被噪声淹没。

咖啡店案例说明了真正的工作：地图工具返回大量数据，但下一步搜索只需要街道名称，因此系统应当先压缩和转换信息。这里的核心不是“上下文越多越好”，而是**每一步只向模型暴露完成当前决策所必需的信息**。

这也重新定义了 Agent 产品中的“记忆”。Session、State 和长期 Memory 不是三种存储介质，而是三种生命周期和用途：对话内容用于眼前推理，任务状态用于恢复执行，长期记忆用于跨任务个性化。真正困难的从来不是存下来，而是决定什么值得存、何时失效、在什么场景下取回。用户身份、关系和历史决策尤其不能被简单视为“隐式数据”，还涉及授权、准确性与过期问题。

##### Reflection 有用，但“两个 Agent”不等于独立判断

Producer-Critic 模式的价值在于把生成与验收分开：先产出，再依据另一套标准审查。但文章所说“两个 Agent 真的比一个好”需要加一个限定。**不同 system prompt 可以减少角色惯性，却未必能消除同一模型的共同盲区。**如果生产者和批评者共享相似知识与推理缺陷，错误可能只是被重复确认。

因此，可靠的 Critic 不应只靠“更挑剔的人设”，还要尽量接入外部证据：代码用测试与静态分析，事实用检索和来源核验，计划用预算、时间和资源约束。评价标准越可执行，反思越有价值；否则循环三次可能只是增加成本和延迟。是否继续迭代，也应由缺陷类型和质量指标决定，而不是追求一句抽象的“完美”。

##### Multi-Agent 是组织设计，不是能力升级按钮

多 Agent 的真正适用条件，是任务确实存在并行性、专业上下文隔离或权限分工。否则，把一个任务拆给多个 Agent，新增的往往不是智能，而是通信协议、状态同步、冲突处理和故障恢复。

这也是那套等级模型容易误导之处：Level 3 未必天然优于 Level 2。一个工具完善、状态清晰、上下文受控且有外部验证的单 Agent，常常比复杂的“虚拟团队”更可靠。未来所谓自我变形的 Agent 组织，技术难点也不只是自动创建角色，而是如何判断重组确实提升了结果，以及失败后由谁追责、如何回滚。

对实际产品而言，更稳妥的路径不是先增加 Agent 数量，而是先建立可观测的单 Agent 闭环：记录它为何调用工具、用了哪些上下文、状态如何变化、Critic 发现了什么，以及每次改进增加了多少成本。**只有当数据证明瓶颈来自并行度或专业分工，而不是上下文、工具或评价机制时，Multi-Agent 才是答案。**
