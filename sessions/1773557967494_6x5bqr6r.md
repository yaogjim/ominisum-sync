#### 第一步：安装Ghostty（超级简单，3分钟）

在你的Mac终端（或者已经打开的Ghostty）里敲下面这行，回车：

```bash
brew install --cask ghostty
```

安装完直接在Spotlight搜索 Ghostty 打开它。 第一次打开可能会出现两个窗口（一个是下拉的幽灵终端），别担心，我们马上解决！

- Cmd + Shift + , → 重载配置（改完主题或分屏后一定要按！）
- Cmd + Q → 完全退出Ghostty（重启推荐用这个）

## 产品-最佳实践（1）

### 2026-03-16 03:23:19

可以。结合你提供的文章内容，我用一个很具体的场景来讲：

**实例：你要用 Claude Code 开发一个个人博客首页，左边让 Claude 写代码，右边实时调试，下面监控系统。**

在这个实例里，Ghostty 不只是 “好看终端”，而是一个真正的多窗口开发工作台。  
下面我直接给你一套更像 “能落地照做” 的最佳实践。

**具体实例**

假设你现在要做一个`Next.js`博客首页改版，目录叫：

```bash
~/projects/my-blog
```

你的目标是：
- 左侧主面板：运行`claude`，让 Claude Code 帮你改首页
- 右侧面板：运行开发服务器，看报错和日志
- 下方面板：运行`btop`，监控资源占用

你在 Ghostty 里的操作流程可以是：

```bash
cd ~/projects/my-blog
```

左侧主面板执行：

```bash
claude
```

右侧分屏执行：

```bash
npm run dev
```

下方分屏执行：

```bash
btop
```

如果还想看项目状态，可以再开一个面板执行：

```bash
git status
```

这样你就得到一个非常清晰的开发现场：

- 左边：Claude 负责生成和修改代码
- 右边：本地服务输出日志、编译信息、报错信息
- 下边：系统资源监控，防止终端卡顿或 dev server 吃满 CPU
- 额外面板：Git 状态确认改了什么

这就是文章里 “左 Claude、右 debug、下监控” 的最佳落地版本。

**在这个实例之上的最佳实践**

- **主面板永远留给 Claude**
  - 不要在 Claude 所在面板里混着跑`npm run dev`、`git log`、`ls`。
  - 最佳做法是让 Claude 面板只负责 “对话、执行任务、查看结果”，这样上下文最干净，不容易被日志冲掉。

- **日志面板固定职责**
  - 右侧面板专门跑：
    ```bash
    npm run dev
    ```
  - 这样 Claude 改完代码后，你不用切来切去找报错，编译结果始终在一个固定位置。
  - 这是分屏最核心的价值：**职责分离**。

- **把 “放大快捷键” 用于长输出场景**
  - 当 Claude 一次输出很多解释、重构方案、diff 或命令结果时，立刻按：
    - `Cmd + Shift + Enter`
  - 最佳实践不是 “看不清再忍着滚”，而是**长输出立刻全屏看**，看完再恢复。
  - 特别适合这几种情况：
    - Claude 给出长篇重构计划
    - 测试失败输出很多栈信息
    - 构建报错链很长

- **开发服务不要和 Claude 抢焦点**
  - 很多人会在 Claude 面板里临时跑`npm run dev`，结果日志不断刷新，把当前会话冲掉。
  - 更好的方式是：
    - Claude 面板只负责智能协作
    - `npm run dev`固定在右侧
    - 测试命令固定在另一个面板，比如：
      ```bash
      npm test
      ```
  - 这样信息结构非常稳定，效率比单窗口高很多。

- **把 Git 状态做成 “收尾检查面板”**
  - 每轮 Claude 改完代码后，到一个固定面板运行：
    ```bash
    git status
    git diff
    ```
  - 最佳实践是：**不要盲目接受 Claude 的改动**，而是每次都快速检查变更范围。
  - 尤其适合防止这些问题：
    - 改了不该改的文件
    - 误删样式
    - 改动超出你的原始需求

- **监控面板只在需要时打开**
  - `btop`很有用，但不需要永远盯着。
  - 最佳实践是：
    - 平时开着用于感知性能
    - 如果你只是轻量开发，可以关闭它，给 Claude 和日志留更多空间
  - 什么时候必须开：
    - 跑大型前端构建
    - Claude 执行大量命令
    - 机器开始发热、卡顿、风扇狂转

**推荐的面板布局**

针对这个博客开发实例，我建议你固定成下面的结构：

- 左侧大面板：`claude`
- 右上：`npm run dev`
- 右下：`git status` / `git diff`
- 需要时临时再加一个下方面板：`btop`

这个布局比 “平均分屏” 更实用，因为：

- Claude 面板最需要空间
- 日志次重要，但必须随时能看
- Git 检查需要存在感，但不需要太大
- 监控是辅助信息，不应抢主工作区

**命令组织的最佳实践**

如果你每天都这样工作，建议把启动流程标准化。  
例如每次进入项目先这样：

```bash
cd ~/projects/my-blog
```

然后按固定顺序开：

1. 左侧：`claude`
2. 右侧：`npm run dev`
3. 右下：`git status`
4. 需要时：`btop`

这样做的好处是：
- 每次工作区结构一致
- 大脑负担更低
- 出问题时你知道去哪个面板找信息

终端工作流最怕 “每次都临时想面板干什么”，固定下来效率会明显提高。

**基于你文章内容，最关键的 5 条实践原则**

- **一屏一职责**：Claude、日志、Git、监控分开，不混用
- **Claude 面板最大化**：把主要视觉空间留给 AI 协作
- **长输出就放大**：`Cmd + Shift + Enter`是高频核心键
- **每轮改动后看 Git**：先审查，再继续
- **配置稳定优先**：先用成熟`config`，不要一开始就自己魔改

**一个完整的高效开发回合示例**

你可以把一次实际工作理解成这样：

1. 在左侧 Claude 面板说：

2. Claude 修改代码后，你立刻看右侧`npm run dev`面板：
   - 有没有编译错误
   - 有没有 hydration warning
   - 有没有样式构建报错

3. 如果 Claude 输出很长，按：
   - `Cmd + Shift + Enter`
   查看完整方案和变更说明

4. 然后去 Git 面板执行：
   ```bash
   git diff
   ```
   检查它到底改了哪些文件

5. 如果机器开始卡，去`btop`看是不是 dev server 或构建进程占用过高
