#### GenOffice

An AI-native office suite for macOS and Windows: word processor, spreadsheet, presentations, and PDF — five Electron apps sharing one engine layer, built around AI editing as a first-class workflow rather than a bolted-on chat box.

#### Download

Signed installers built from `main`:

- **macOS** (Apple Silicon): [GenOffice-0.4.110-arm64.dmg](https://github.com/genspark-ai/genoffice/releases/download/v0.4.110/GenOffice-0.4.110-arm64.dmg)
- **Windows** (x64): [GenOfficeSetup-v0.4.110.exe](https://github.com/genspark-ai/genoffice/releases/download/v0.4.110/GenOfficeSetup-v0.4.110.exe)

Other versions are on the [Releases](https://github.com/genspark-ai/genoffice/releases) page.

#### Apps

App Product What it is

`apps/docs` **GenOffice Docs** `.docx` word processor. Byte-preserving round trip: only dirty paragraphs are regenerated (paragraph patch), everything else in the original file is kept byte-for-byte, so opening and saving never breaks layout in Word. Paginated view whose line metrics reproduce the original document's layout, tracked changes, comments, styles, equations, ink.

`apps/sheets` **GenOffice Sheets** `.xlsx` spreadsheet. UI built on the open-source [Univer](https://github.com/dream-num/univer) core (Apache-2.0) with a large layer of in-house extensions; xlsx import/export runs through an in-house Rust sidecar (calamine + IronCalc), charts are rendered in-house (Konva), plus pivot tables, slicers, conditional formatting, and formula tracing.

`apps/slides` **GenOffice Slides** `.pptx` presentations. In-house pptx parse/render/edit engine with masters, charts, cropping, ink, and text shaping (HarfBuzz metrics).

`apps/pdf` **GenOffice PDF** PDF viewer/editor on pdf.js + pdf-lib: annotations, forms, outlines, stamps, signatures, page operations, print.

`apps/shell` **GenOffice** The suite shell: home screen, tabbed hosting of the four editors, auto-update.

Every app embeds the same AI panel: block-granular AI editing with version snapshots and diffs in docs, a tool-calling agent over workbook/slide/PDF state in the others.

**AI providers.** The apps sign in to a Genspark account and route model calls through the Genspark service side; no model API key is stored locally.

#### Engine packages

All pure TypeScript, no Electron dependency, unit-tested (except the UI kit):

- `packages/docx-engine` — docx parsing → block tree (with `docxIndex` anchors and passthrough), OOXML fragment generation, byte-level paragraph patching.
- `packages/pptx-engine` / `packages/pptx-render` — pptx model and rendering.
- `packages/file-parse` — text extraction for AI attachments (office formats, text formats).
- `packages/agent-core` — the AI agent loop and skill composition shared by every app.
- `packages/ai-provider` — provider abstraction and streaming for the model backends.
- `packages/ai-search` — Genspark auth + web/image search tools.
- `packages/i18n`, `packages/ui`, `packages/project-store`,`packages/electron-utils` — shared i18n core, React UI kit, recent-files store, and Electron main-process helpers.

#### Development

```
npm install
npm run fixtures     # generate test .docx fixtures
npm test             # engine + app unit tests (docs/sheets/slides need no display)
npm run typecheck    # tsc --noEmit across every workspace
npm run dev          # all four editors + shell against Vite dev servers
npm run dev:docs     # a single app (same pattern works per workspace)
npm run dist:mac     # package macOS dmg (regenerates third-party notices)
npm run dist:win     # package Windows nsis installer
```

The sheets app additionally needs a Rust toolchain for its xlsx sidecar (`cargo` on PATH); `npm run build -w @genoffice/sheets` compiles it automatically.

Local UI/e2e driver scripts (Playwright + Electron, for local acceptance, not committed by default) live in `scripts/drivers/`.

```
open docx ─► archive original by hash (never touched)
          ─► docx-engine parses word/document.xml top-level elements (w:p / w:tbl / …)
          ─► Block tree, each block anchored by docxIndex + original XML slice
          ─► TipTap streaming editor (manual + AI editing, dirty tracking)
save      ─► dirty blocks → OOXML fragments (referencing existing styles only)
          ─► splice into original document.xml (untouched blocks keep original bytes)
          ─► repack zip; all other entries copied byte-for-byte
```

The same philosophy holds in sheets and slides: the original file is the source of truth, edits are applied as narrow patches, and everything the editor didn't touch survives the round trip untouched.

#### GenOffice：把 AI 深度嵌入 Office 编辑流程的开源办公套件

##### 一句话概括

GenOffice 是一套面向 macOS 和 Windows 的**AI 原生桌面办公套件**，覆盖文档、表格、演示文稿和 PDF。它的核心特色不是增加一个 AI 聊天框，而是让 AI 直接理解并修改文件内容，同时尽可能保持原始格式不变。

##### 产品组成

GenOffice 由 4 个编辑器和 1 个统一入口组成：

- **Docs**：编辑`.docx`，支持分页、样式、批注、修订、公式和手写内容。
- **Sheets**：编辑`.xlsx`，支持图表、数据透视表、切片器、条件格式和公式追踪。
- **Slides**：编辑`.pptx`，支持母版、图表、裁剪、手写和精细文本排版。
- **PDF**：支持阅读、批注、表单、盖章、签名及页面操作。
- **Shell**：统一首页、多标签页管理和自动更新。

##### 核心差异化：局部修改，不破坏原文件

GenOffice 将原始文件视为 “唯一事实来源”，只替换用户或 AI 真正修改过的部分。

以 Word 为例：

1. 打开文件后，完整保存原始文件。
2. 将文档解析成带原始位置索引的内容块。
3. 用户或 AI 编辑时，只标记发生变化的段落。
4. 保存时，仅重新生成这些段落。
5. 其余内容按原始字节保留。

这可以显著降低 Office 文件经过第三方编辑器保存后出现的**排版错乱、样式丢失或兼容性问题**。表格和演示文稿也采用类似的 “窄范围补丁” 思路。

##### AI 能力：从问答助手升级为操作代理

每个应用都内置同一套 AI 面板：

- Docs 支持按内容块进行 AI 编辑、版本快照和差异对比。
- Sheets、Slides 和 PDF 中，AI 可通过工具调用直接读取和操作文件状态。
- 底层共享统一的 Agent 循环、技能组合、流式输出和模型提供商抽象。

模型请求通过 Genspark 服务端转发，本地不保存模型 API Key；但这也意味着 AI 功能依赖 Genspark 账号及其云服务。

##### 技术架构

项目采用**Electron + TypeScript**构建，五个应用共享一套引擎层：

- 文档、演示文稿和文件解析拥有独立引擎。
- 表格 UI 基于开源 Univer，并通过 Rust 组件处理`.xlsx`导入与导出。
- PDF 基于 pdf.js 和 pdf-lib。
- AI、搜索、国际化、UI、文件管理等能力沉淀为共享包。
- 支持单元测试、类型检查、端到端测试及 macOS/Windows 打包。

整体架构强调：**编辑器 UI 与底层文件引擎解耦，多应用复用统一 AI 基础设施。**

##### 安全与开源策略

- 提供渲染器沙箱、IPC 校验、外部链接限制及 AI 内容威胁模型。
- 主体代码采用**Apache License 2.0**。
- `ee/`目录保留给未来企业版模块，使用单独的企业许可证。
- 品牌名称和 Logo 不随开源许可证授权，分叉项目需要更换品牌。

##### 产品判断

GenOffice 的真正价值不在于 “又一个 Office 替代品”，而在于两个设计选择：

1. **AI 是编辑流程的一部分**，能够直接执行结构化修改，而不只是生成文本建议。
2. **以文件兼容性为底线**，通过局部补丁减少对复杂 Office 文件的破坏。

从当前版本号、贡献者规模及桌面端技术路线看，项目仍偏早期。其后续竞争力主要取决于三点：复杂文件的兼容稳定性、AI 操作的准确与可控性，以及对微软 Office 核心工作流的替代程度。

## 口播总结（1）

### 2026-08-07 08:47:34

#### GenOffice 是什么

GenOffice 是一套面向 macOS 和 Windows 的 AI 原生办公软件，包含文字处理、电子表格、演示文稿和 PDF 工具。它最核心的特点有两个：一是把 AI 直接融入编辑流程，而不只是增加一个聊天框；二是尽量只修改用户真正动过的内容，避免破坏原文件的格式和布局。

接下来，你可以了解这套软件由哪些应用组成，AI 如何参与编辑，它怎样保护 Office 文件的原始结构，以及项目的开发、安全和授权方式。

#### 五个应用，共用一套核心能力

首先，GenOffice 实际上由五个桌面应用组成。它们都基于 Electron，也就是一种用网页技术开发跨平台桌面软件的框架，并且共享同一套底层引擎。

其中，四个应用负责具体编辑任务。

GenOffice Docs 是 Word 文档编辑器，处理的是 docx 文件。它支持分页显示、修订、评论、样式、公式和手写墨迹。它最特别的能力，是尽量保持文件原样。打开文档再保存时，软件只重新生成被修改过的段落，其他内容会按原始字节保留。简单说，就是没动过的地方尽可能一字节都不变，从而降低在微软 Word 中再次打开时出现错位或版式损坏的风险。

GenOffice Sheets 是 Excel 表格编辑器，处理 xlsx 文件。它的界面建立在开源的 Univer 核心之上，同时加入了大量自研功能。文件导入和导出由 Rust 编写的辅助程序处理，图表也由项目自己渲染。它支持数据透视表、切片器、条件格式和公式追踪等常见的高级功能。

GenOffice Slides 是 PowerPoint 演示文稿编辑器，处理 pptx 文件。它使用自研的解析、渲染和编辑引擎，可以处理母版、图表、图片裁剪、墨迹和文字排版。其中，文字排版会使用精确的字体度量，目的是尽量还原标题和正文的位置与效果。

GenOffice PDF 则是 PDF 查看和编辑工具。它支持批注、表单、书签式大纲、印章、签名、页面操作和打印。

第五个应用是 GenOffice Shell，也就是整套软件的统一外壳。它提供首页、标签页管理和自动更新，并在一个窗口中承载前面的四种编辑器。

项目提供从主代码分支构建并签名的安装包。原文列出的版本是 0.4.110，支持苹果芯片版 macOS 和六十四位 Windows，其他版本可以在项目的发布页面中找到。

#### AI 不是外挂聊天框，而是直接参与编辑

接下来是这套软件最重要的定位：AI 编辑属于核心工作流，而不是附加功能。

四个编辑器中都嵌入了同一套 AI 面板。在文字处理器里，AI 可以按内容块进行修改。所谓内容块，可以理解为段落、表格等相对独立的文档单元。系统还会保存版本快照，并展示修改前后的差异，让用户看清 AI 到底改了什么。

在表格、演示文稿和 PDF 中，AI 采用的是“工具调用智能体”模式。通俗地说，AI 不只是回答问题，还能读取当前文件的结构和状态，并调用相应的编辑工具来执行任务。例如，它可以针对工作簿、幻灯片或 PDF 的具体内容开展操作，而不是只生成一段供用户复制的文字。

所有应用共享同一个智能体循环和技能组合框架，也共享模型接入、流式输出、网页搜索和图片搜索等能力。这意味着不同编辑器虽然处理的文件不同，但 AI 的基础工作方式是一致的。

需要注意的是，使用 AI 时，用户要登录 Genspark 账户。模型请求会通过 Genspark 的服务端转发，本地不会保存模型服务的 API 密钥。API 密钥可以理解为访问外部 AI 模型服务的专用凭证。

#### 底层引擎如何分工

更进一步看，GenOffice 把核心能力拆成了多个独立软件包。这些引擎主要由 TypeScript 编写，不直接依赖 Electron，并且大多配有单元测试。这样做的好处是，文件解析、AI 智能体和界面等能力可以分开维护，也能被不同应用复用。

文档引擎负责解析 docx 文件，把内容转换成由段落、表格等组成的块状结构。它还能生成 Office 文件内部使用的 XML 片段，并完成精确到字节级别的段落替换。这里的 OOXML，指的是 Word、Excel 和 PowerPoint 文件内部使用的一套 XML 标记格式。

演示文稿引擎负责 pptx 的数据模型和页面渲染。文件解析模块负责从 Office 文档和普通文本中提取内容，供 AI 处理附件。智能体核心模块则负责各应用共享的 AI 执行循环和技能组合。

此外，项目还有模型服务抽象层、流式响应模块、搜索工具、国际化模块、React 界面组件、最近文件记录，以及 Electron 主进程的辅助工具。

从代码构成看，TypeScript 占约百分之九十四点三，是绝对主体。CSS 约占百分之三点一，Rust 约占百分之一点八，其余语言合计不到百分之一。

#### 开发和测试方式

接下来是项目的开发流程。核心结论是，这个代码库可以统一安装、测试和构建，也可以只启动其中一个编辑器。

开发者先通过 npm 安装依赖，再生成测试用的 docx 文件样本。项目提供统一的单元测试和类型检查命令。文档、表格和幻灯片应用的相关测试不需要显示器环境，因此也适合在自动化系统中运行。

开发时，可以一次启动四个编辑器和统一外壳，也可以单独启动 Docs 等某一个应用。项目还提供 macOS 的 DMG 安装包构建命令，以及 Windows 的 NSIS 安装程序构建命令。

表格应用有一项额外要求。因为 xlsx 文件的辅助处理程序使用 Rust 编写，所以开发者需要安装 Rust 工具链，并确保 cargo 命令可用。构建表格应用时，这部分辅助程序会自动编译。

项目还提供基于 Playwright 和 Electron 的本地界面与端到端测试驱动脚本。端到端测试，就是模拟用户从打开应用到完成操作的完整过程。这些脚本主要用于本地验收，默认不会被提交进代码库。

#### 为什么保存文档时不容易破坏原格式

更重要的是，GenOffice 把原始文件视为最终依据，并通过“小范围补丁”来保存修改。这是整套软件在文件兼容性方面的核心设计。

以 docx 文件为例。打开文档时，软件先根据文件哈希保存原始归档，并且不直接修改这份原件。随后，文档引擎解析内部的 document.xml，把顶层的段落、表格等元素转换成内容块。每个内容块都会记录自己在原文档中的位置，并保留对应的原始 XML 片段。

用户手动编辑或让 AI 修改时，系统会追踪哪些内容块已经变脏，也就是哪些部分真正发生了变化。

保存时，只有这些变脏的内容块会被重新生成为 OOXML 片段，而且会尽量引用文件中已经存在的样式。新片段随后被嵌回原始文档结构。没有改动的内容块继续保留原始字节，压缩包里的其他文件也会原样复制。

这意味着，编辑一个段落时，软件不会顺手重写整份 Word 文件。原文档中那些复杂但未被触碰的样式、布局和内部信息，更有机会完整保留下来。

表格和演示文稿也遵循类似原则。原始文件始终是信息来源，软件只把修改应用到尽可能小的范围，未被编辑的内容则在打开、修改和保存的往返过程中保持不变。

#### 安全、第三方组件和授权

最后来看安全与授权。

项目单独提供了安全说明，涉及渲染进程沙箱、进程间通信验证，以及外部链接访问控制。简单说，沙箱用于限制页面代码能够接触的系统资源；进程间通信验证用于检查应用内部不同模块之间传递的请求；外部链接控制则用于避免应用未经确认就打开不可信地址。

安全说明还包括针对 AI 生成内容的威胁模型，也就是预先分析 AI 内容可能带来的风险，并设计对应的防护边界。

项目可以自动生成第三方许可证汇总。运行时依赖采用 MIT、Apache 2.0 或 OFL 等许可证。随软件附带的 Liberation、Carlito、Caladea 和 Noto CJK 子集等字体，也采用 OFL 或 Apache 许可证。

GenOffice 主体代码使用 Apache 2.0 许可证，但有一个例外：名为“ee”的目录预留给未来的企业功能，适用单独的 GenOffice 企业许可证。

## 深度解读（1）

### 2026-09-18 00:11:15

#### GenOffice 的关键赌注：AI 办公的瓶颈不是生成，而是“不破坏原文件”

GenOffice 表面上是在重做 Word、Excel、PowerPoint 和 PDF，但这个项目最值得关注的并非“四件套加 AI”，而是它对一个真实障碍的判断：**AI 要进入严肃办公流程，首先必须让用户相信，修改是局部、可审查、可撤销的，未修改内容不会被意外破坏。**

##### 兼容性被设计成“最小改动”，而非重新导出

多数替代 Office 的产品会读取文件、转换成内部模型，再整体导出。问题是，即使用户只改了一句话，复杂样式、分页、批注、公式或第三方扩展也可能在转换中丢失。

GenOffice 对 `.docx` 采取了更保守的路径：保存原始压缩包和 XML，只把被修改的段落重新生成并拼回去，其余内容保持字节不变。表格和幻灯片也声称遵循相同原则——**原文件始终是真相来源，编辑器只提交窄范围补丁。**

这不只是工程优化，而是产品策略。它把“兼容 Office”从一个近乎无底洞的功能覆盖问题，改写成“没有触碰的东西就不要解释、更不要重建”。这与数据库增量更新、代码补丁的思想相似，特别适合 AI 编辑：模型通常只需要改摘要、措辞、公式或几页内容，没有理由重写整个文件。

但边界也很明确：字节级保留不等于视觉结果必然不变。一个段落变长仍会改变后续分页；表格公式、图表和母版之间还有复杂依赖。因此真正应验证的不是“能否打开常见文件”，而是大量复杂文件经过局部编辑和往返保存后，**未编辑对象的存活率、版式偏差和计算结果是否稳定**。README 给出的是有吸引力的架构主张，还不是充分的兼容性证据。

##### “AI 原生”体现在可控的操作单位

项目没有把聊天框当成 AI 原生的证明。文档编辑以区块为单位生成修改、保存版本并显示差异；表格、幻灯片和 PDF 则让代理通过工具调用操作结构化状态。两者共同解决的是：模型输出不能直接等同于文件结果，中间必须有明确的操作对象和审查界面。

这比“帮我写一份报告”更接近高频办公需求。用户真正想要的往往是：统一十处措辞、解释异常公式、调整指定页面、批量补充批注，同时能知道 AI 到底改了什么。**AI 办公的核心交互单位可能不是对话，而是带作用域、差异和回滚能力的变更集。**这一思路也可迁移到设计稿、代码、合同和业务配置等高价值资产。

##### 最值得验证的是信任闭环，而非功能数量

GenOffice 已覆盖多个编辑器、自研解析渲染引擎和共享代理层，野心很大，但产品成败未必取决于功能表能否追平微软。更关键的指标应是：用户是否敢让 AI 修改已有的重要文件，是否能快速理解并接受差异，失败后是否可可靠恢复。

还有一个容易忽略的限制：代码开放不等于 AI 本地化。模型请求会通过 Genspark 服务，客户端不保存模型密钥，因此敏感文档如何上传、保留和审计仍会影响企业采用。

GenOffice 最有价值的启示是：**在成熟文件生态中，AI 的机会不是先替代全部工具，而是先成为一个不破坏既有资产、行为可验证的编辑层。**如果其窄补丁架构能经受复杂真实文件的检验，这可能比再做一个全能聊天入口更接近 AI 办公的可靠起点。
