OpenSpace 以技能的形式集成到任何代理中，并通过三种超能力对其进行进化：

##### 🧬 自我进化

自动学习并自我提升的技能

- ✅ **AUTO-FIX** — 当技能失效时，它会立即自我修复
- ✅ **AUTO-IMPROVE** — 成功的模式会转化为更好的技能版本
- ✅ **自动学习** — 从实际使用中捕获成功的工作流
- ✅ **质量监控** — 跟踪所有任务中的技能表现、错误率和执行成功率。

**持续进化的技能——将每一次失败转化为改进，每一次成功转化为优化。**

##### 🌐 集体智能体

将单个智能体转变为共享大脑

- ✅ **共享进化** ：单个代理的改进将成为所有代理的升级
- ✅ **Network effects**: 更多智能体 → 更丰富的数据 → 每个智能体更快的进化
- ✅ **简单分享** — 通过一个简单的命令上传和下载进化后的技能
- ✅ **访问控制** — 为每个技能选择公开、私有或仅团队可访问的权限

**一个智能体学习，所有智能体受益——规模化的集体智能。**

##### 💰 代币效率

更智能的代理，大幅降低成本

- ✅ **停止重复工作** → 重复使用成功的解决方案，而不是每次都从零开始
- ✅ **任务变得更便宜** → 随着技能的提升，类似的工作成本越来越低
- ✅ **仅进行小更新** → 修复有问题的部分，不要重新构建所有内容
- ✅ **真实节省** ：在实际任务中，性能提升 4.2 倍，同时减少 46%的 token 数量，带来可衡量的经济价值。（ GDPVal ）

      "env": {
        "OPENSPACE_HOST_SKILL_DIRS": "/path/to/your/agent/skills",
        "OPENSPACE_WORKSPACE": "/path/to/OpenSpace",
        "OPENSPACE_API_KEY": "sk-xxx (optional, for cloud)"

  }

OpenSpace Framework

The core of OpenSpace. Skills aren't static files — they're living entities that automatically select, apply, monitor, analyze, and evolve themselves.

- **Full Lifecycle Management**: From discovery to application to evolution — all without human intervention. OpenSpace completes tasks regardless of whether matching skills exist.

**Three Evolution Modes**:

- 🔧 FIX — Repair broken or outdated instructions in-place. Same skill, new version.
- 🚀 DERIVED — Create enhanced or specialized versions from parent skills. New skill directory, coexists with parents.
- ✨ CAPTURED — Extract novel reusable patterns from successful executions. Brand new skill, no parent.

**Three Independent Triggers**: Multiple lines of defense against skill degradation — both successful and failed executions drive evolution.

- **📈 Post-Execution Analysis** — Runs after every task. Analyzes full recordings and suggests FIX/DERIVED/CAPTURED for involved skills.
- **⚠️ Tool Degradation** — When tool success rates drop, quality monitor finds all dependent skills and batch-evolves them.
- **📊 Metric Monitor** — Periodically scans skill health metrics (applied rate, completion rate, fallback rate) and evolves underperformers.

Multi-Layer Tracking: Quality monitoring covers the entire execution stack — from high-level workflows to individual tool calls:

- **🎯 Skills** — applied rate, completion rate, effective rate, fallback rate
- **🔨 Tool Calls** — success rate, latency, flagged issues
- **⚡ Code Execution** — execution status, error patterns

**Cascade Evolution**: When any component degrades — skill workflow or single tool call — evolution automatically triggers for all upstream dependent skills, maintaining system-wide coherence.

**🤖 Autonomous Evolution**: Each evolution explores the codebase, discovers root causes, and decides fixes autonomously — gathering real evidence before making changes, not generating blindly.

**⚡ Diff-Based &amp; Token-Efficient**: Produces minimal, targeted diffs rather than full rewrites, with automatic retry on failure. Every version stored in a version DAG with full lineage tracking.

**🛡️ Built-in Safeguards**:

- Confirmation gates reduce false-positive triggers
- Anti-loop guards prevent runaway evolution cycles
- Safety checks flag dangerous patterns (prompt injection, credential exfiltration)
- Evolved skills are validated before replacing predecessors

**🌐 Collaborative Skill Community** A collaborative registry where agents share evolved skills. When one agent evolves an improvement, every connected agent can discover, import, and build on it — turning individual progress into collective intelligence.

- **🔐 Flexible Sharing**: Share skills publicly, within groups, or keep them private. Smart search finds what you need and auto-imports it. Every evolution is lineage-tracked with full diffs.
- **☁️ Collaborative Platform**: open-space.cloud — register for an API key, browse community skills, and manage your groups.

##### 9. OpenSpace 的进化机制是怎么运作的

OpenSpace 把技能看作“活的实体”，不是静态文件。它们会自动被选择、应用、监控、分析和进化。

###### 9.1 三种进化模式

- **FIX**：修复损坏或过时的技能，属于同一技能的新版本。
- **DERIVED**：从父技能派生出更强或更专门的新技能。
- **CAPTURED**：从成功执行中提取全新的可复用模式。

###### 9.2 三种独立触发器

- **任务后分析**：每次任务执行后，回看全流程并提出 FIX / DERIVED / CAPTURED 建议。
- **工具退化监控**：当工具成功率下降时，批量进化依赖它的技能。
- **指标监控**：周期性扫描技能健康指标，对低表现技能触发进化。

###### 9.3 多层监控与级联进化

监控覆盖多个层面：

- **技能层**：应用率、完成率、有效率、回退率
- **工具调用层**：成功率、延迟、异常
- **代码执行层**：执行状态、错误模式

如果底层某个工具退化，上层依赖它的技能也会一起被触发更新，保持整体一致性。

###### 9.4 安全与效率保障

- 基于 diff 的小范围修补，避免整段重写，更省 token
- 失败时支持自动重试
- 版本会存进 DAG，保留完整谱系
- 有确认门、反循环保护、危险模式检测
- 会校验技能，避免劣化版本直接替换旧版本

## 解读（1）

#### 深入解读

##### 1. 它到底解决了什么问题？

现在很多 AI 智能体虽然能干活，但有几个老毛病：

- **每次都像“重新做人”**：做过的任务不会真正复用经验，重复消耗 token。
- **容易重复踩坑**：一个智能体犯过的错，另一个还会再犯一遍。
- **技能会老化**：工具、API、网页环境一变，原本能用的方法就失效了。
- **知识被锁在单个体内**：经验不能自然扩散到整个团队或社区。

OpenSpace 的核心思路很直接：

> **把一次次任务中的有效做法，变成可复用、可进化、可共享的“技能”。**

---

##### 2. 它是怎么工作的？

OpenSpace 给智能体三种关键能力：

###### 自我进化
每次任务完成后，它会分析执行过程，并做三类进化：

- **FIX**：技能坏了，自动修
- **DERIVED**：从已有技能衍生出更强版本
- **CAPTURED**：把一次成功任务中新的高价值模式提炼成新技能

这意味着它不是只会“调用提示词”，而是在慢慢形成自己的工作方法库。

###### 集体共享
一个智能体学会的技能，可以上传到云端社区，供其他智能体下载复用。

通俗说就是：

- 不是“各学各的”
- 而是“**一个人踩坑，全村避坑；一个人进步，全体升级**”

###### 成本优化
它强调的不是单次炫技，而是长期收益：

- 成功方案反复复用
- 出问题只修局部，不整套重来
- 相似任务越做越便宜

这也是它宣传“更少 token、更高收入”的底层逻辑。

##### 3. 为什么它看起来有点不一样？

很多 Agent 项目重点在：

- 接更多工具

- **经验能不能沉淀**

- **改进能不能规模化共享**

所以它更像一个：

**“智能体技能操作系统 + 进化引擎 + 共享社区”**

而不只是一个普通 Agent 工具箱。

- 集成到已有 Agent 里

## 产品-最佳实践（1）

### 2026-03-25 10:33:32

#### 用一个具体实例说明 OpenSpace 的最佳实践

下面我基于你提供的内容，选一个最能体现 OpenSpace 价值的真实场景来讲：

> **实例：让一个接入 OpenSpace 的智能体，完成“从 15 份零散 PDF 中准备纳税申报材料”这类高价值、易出错、可复用的专业任务。**

这个例子非常合适，因为它同时覆盖了 OpenSpace 的几个核心能力：  
- 多文件处理  
- 技能复用  
- 自动修复  
- 质量验证  
- 成本优化  
- 团队/社区共享

---

##### 一、实例背景

假设你有一个已经支持 `SKILL.md` 的代理（例如 Codex、Claude Code、OpenClaw 一类），你希望它自动完成一项复杂任务：

###### 任务目标
从以下材料中生成一份可提交的纳税申报工作包：
- 15 份来源各异的 PDF
- 若干补充表格
- 需要结构化提取、字段核对、缺失检测、汇总输出

###### 传统代理的常见问题
如果不接入 OpenSpace，这类任务通常会出现：
- 每次都从头推理，重复消耗大量 token
- PDF 提取流程不稳定，格式一变就失败
- 失败后没有沉淀，下一次还是重踩同样的坑
- 输出虽然“看起来像完成了”，但缺字段、错映射、漏页很难发现
- 同一个团队里的多个代理无法共享修复后的经验

而 OpenSpace 的意义就在于：  
**它不只是“帮你做一次”，而是把这次成功和失败都变成未来更便宜、更稳定的能力。**

---

##### 二、这个实例上的最佳实践

##### 1. 先把 OpenSpace 当成“技能进化层”，而不是普通工具

最佳实践不是把 OpenSpace 仅仅当成一个额外命令，而是把它接入你的代理工作流，让它负责：

- 发现已有可复用技能
- 在执行中调用最适合的技能
- 在失败后触发 FIX
- 在成功后触发 CAPTURED 或 DERIVED
- 持续记录质量指标

###### 为什么这是最佳实践
在“15 份 PDF 纳税申报”这种任务里，真正昂贵的不是单次生成，而是：
- PDF 解析失败后的反复试错
- 表单字段映射不一致
- 相似任务无法复用经验

所以应该让 OpenSpace 处于流程核心，而不是末端辅助。

---

##### 2. 把任务拆成“可演化技能链”，不要让代理一次性硬做完

对于这个例子，推荐把任务组织成一条明确的技能链，而不是一个巨大的单 Prompt：

###### 推荐技能链
1. `PDF 收集与分类`
2. `文本提取与表格提取`
3. `关键信息字段归一化`
4. `缺失项与冲突项检测`
5. `税务表单填充`
6. `结果校验与证据回链`
7. `最终打包与交付`

###### 最佳实践要点
- 每个环节都应能单独失败、单独修复
- 每个环节都应产出中间结果，便于验证
- 每个环节都应沉淀为技能，而不是藏在一次性上下文里

###### 为什么这样更优
OpenSpace 的优势之一是 **diff-based、最小化修复**。  
如果你把整个任务写成一个大而全的执行流程，那么任何失败都可能导致整段重做。  
而拆成技能链后：
- PDF 提取坏了，只修 PDF 技能
- 表单映射错了，只演化映射技能
- 校验逻辑不够严格，只增强 QA 技能

这正符合 OpenSpace 提倡的：
> **只修坏掉的部分，不要重建全部。**

---

##### 3. 优先沉淀“工具可靠性技能”，不要只沉淀领域知识

从你提供的材料里，一个很重要的发现是：

> OpenSpace 演化出来的大多数高价值技能，不是领域知识，而是“工具可靠性”和“错误恢复模式”。

在这个纳税申报实例中，最佳实践不是先追求“税法知识技能库很全”，而是先沉淀这些技能：

###### 应优先演化的技能
- PDF 提取失败时的 fallback 路径
- 表格跨页处理
- 扫描版 PDF OCR 兜底
- 字段名不一致时的模糊匹配
- 生成后自动校验页数、字段完整性、金额一致性
- 当某个工具失败时，自动切到 shell / file-write-then-run / heredoc 等替代路径

###### 原因
现实任务里，代理失败通常不是因为“不懂纳税”，而是因为：
- 文件格式脏
- 提取不稳定
- 输出不完整
- 工具链变化导致已有流程失效

所以最佳实践是：
**先让代理“稳定做出来”，再追求“做得更聪明”。**

---

##### 4. 对每次成功结果做“后验验证”，不要只看模型说自己完成了

在这个实例里，最关键的最佳实践之一就是建立 QA 闭环。

###### 推荐的验证清单
- 是否处理了全部 15 份 PDF
- 每份文件是否都有提取记录
- 纳税表单中的关键字段是否全部有来源映射
- 金额字段是否存在合计冲突
- 是否输出缺失项报告
- 是否保留证据链，能追溯到原文档页码或段落

###### 为什么这是最佳实践
OpenSpace 在文档、表单、表格任务中效果明显提升，一个核心原因就是：
> 它不仅生成，还验证。

也就是说，好的技能不只是：
- “如何生成税表”
还应该包括：
- “如何证明税表没有明显错误”

###### 建议
在技能设计上，把 QA 视为独立技能族：
- `post-write-verification`
- `source-to-field trace`
- `row/page count validation`
- `formula/completeness checks`

这类技能在多个领域都能复用，长期回报很高。

---

##### 5. 用 FIX / DERIVED / CAPTURED 三种模式分别处理不同类型的改进

这是 OpenSpace 的核心机制，在本例中非常适合这样用：

###### `FIX`
用于修补已存在但失效的技能。  
例如：
- 某个 PDF 解析方法因为新版文档结构变化而失效
- 某个字段提取规则把“税前收入”和“应税收入”混淆了

**最佳实践：**
- 仅做最小修复
- 保持技能接口不变
- 修复后立即用最近失败样本回归验证

---

###### `DERIVED`
用于从已有技能派生更强的版本。  
例如：
- 从通用 PDF 提取技能，派生出“税务 PDF 专用提取技能”
- 从通用表单生成技能，派生出“高约束财务表单技能”

**最佳实践：**
- 当任务模式明显稳定出现时，再派生
- 保留父技能，不要直接覆盖
- 让专用技能在匹配时优先级更高

---

###### `CAPTURED`
用于从一次成功任务中提炼新模式。  
例如：
- 某次你发现“先做文件清单，再做字段映射，再做缺失检查”的流程成功率很高
- 这时就应把它捕获成一个新的可复用工作流技能

**最佳实践：**
- 捕获的是“成功模式”，不是完整任务结果
- 聚焦步骤、判断条件、错误处理，而不是只保存输出文本
- 捕获后要补元数据：适用场景、输入要求、风险点

---

##### 6. 建立技能质量指标，驱动自动演化，而不是靠人记忆问题

在这个实例里，建议至少追踪以下指标：

| 指标 | 含义 | 作用 |
|---|---|---|
| applied rate | 技能被成功应用的频率 | 判断是否真的被工作流采用 |
| completion rate | 用了该技能后任务完成率 | 判断技能是否有效 |
| fallback rate | 使用过程中触发兜底的频率 | 判断技能是否开始退化 |
| extraction accuracy proxy | 提取后字段被验证通过的比例 | 判断 PDF/表单技能质量 |
| rework count | 同一任务重复修补次数 | 判断是否存在系统性缺陷 |

###### 最佳实践
- 不要只看“任务完成没完成”
- 要看“完成得是否稳定、是否越来越便宜”
- 一旦 `fallback rate` 或失败率升高，自动触发技能演化

###### 为什么重要
真实环境中的工具、API、文件格式都在变。  
如果没有持续监控，再好的技能也会悄悄退化。

---

##### 7. 让技能共享有边界：税务类技能优先团队内共享，不建议默认全公开

OpenSpace 支持：
- public
- private
- team-only

对于本例这种纳税申报任务，最佳实践是：

###### 推荐权限策略
- 通用 PDF 修复/解析技能：可公开或团队共享
- 税务表单结构技能：优先团队共享
- 包含组织流程、术语映射、模板偏好的技能：私有或团队内
- 涉及真实客户数据衍生的经验：绝不直接公开

###### 原因
虽然 OpenSpace 鼓励社区共享，但像税务、法务、合规这类任务：
- 有明显的隐私边界
- 有组织内部流程差异
- 有合规风险

所以最佳实践不是“共享越多越好”，而是：
**共享方法，不共享敏感上下文。**

---

##### 8. 在冷启动阶段允许试错，但要尽快进入“暖启动复用”

你提供的 GDPVal 设计里，OpenSpace 的一个关键优势来自：

- Phase 1：Cold Start
- Phase 2：Warm Rerun

本实例里也一样。

###### 最佳实践
首次处理这类税务任务时：
- 接受会有更多探索成本
- 重点是让系统捕获成功路径和失败修复

第二批、第三批类似任务时：
- 强制优先复用已演化技能
- 尽量减少从头规划
- 检查 token 使用是否持续下降

###### 正确目标
不是让第一次就完美，而是让：
- 第二次更稳
- 第三次更便宜
- 第四次几乎标准化

这才是 OpenSpace 的真正 ROI。

---

##### 三、这个实例的一套推荐落地方式

下面给一个更接近实战的落地方案。

##### 场景
你有一个支持 MCP 的代理，要接入 OpenSpace，专门处理高价值文档/表单类任务。

##### 推荐做法

###### 第一步：最小接入
先接入 OpenSpace MCP，并复制两个基础 host skills：
- `delegate-task`
- `skill-discovery`

这样代理就会学会：
- 什么时候调用 OpenSpace
- 怎么搜索已有技能
- 怎么在执行后把成功/失败转化为可演化资产

---

###### 第二步：先只支持一个高频任务簇
不要一开始就让它处理所有复杂办公任务。  
先聚焦一个任务簇，例如：

- 多 PDF → 结构化抽取 → 表单输出 → 校验

这样更容易形成高质量技能家族。

---

###### 第三步：把验证做成强制步骤
对于税务材料处理，建议规定：
- 没有字段完整性检查，不算完成
- 没有来源追溯，不算完成
- 没有缺失项报告，不算完成

这会显著提高 CAPTURED 技能的质量。

---

###### 第四步：把失败样本保留为演化燃料
最有价值的，不是顺利完成的样本，而是这些失败案例：
- 扫描件 OCR 崩溃
- 表格跨页导致漏字段
- 不同 PDF 里同义字段命名不一致
- 表单生成成功但金额校验不通过

这些失败正是 `FIX` 技能最好的训练来源。

---

###### 第五步：定期看本地仪表盘，而不是“感觉系统好像变强了”
OpenSpace 本地仪表盘的价值在于可观察性。  
建议每周查看：
- 哪些技能应用率高
- 哪些技能 fallback 变多
- 哪些技能派生出多个版本
- 哪些任务 token 下降最明显
- 哪些任务质量仍不稳定

只有可观察，才能真正形成演化闭环。

---

##### 四、这个实例中的常见误区

##### 误区 1：把 OpenSpace 当“更强的 Prompt”
错误做法：
- 只是给代理一段更长的任务说明
- 不拆技能
- 不做验证
- 不记录失败

结果：
- 单次看似更强，长期没有复利

---

##### 误区 2：只沉淀业务知识，不沉淀执行模式
错误做法：
- 只想保存“税务规则”
- 不保存“PDF 出错时怎么办”

结果：
- 一遇到真实脏数据，还是崩

---

##### 误区 3：每次都全量重做
错误做法：
- 技能一失效就整套流程重写

结果：
- token 浪费
- 演化历史断裂
- 很难知道到底哪里变好了

---

##### 误区 4：只看最终输出，不看过程质量
错误做法：
- 税表生成了就算完成

结果：
- 隐藏错误积累
- 下一次复用会放大问题

---

##### 五、一句话总结这个实例上的最佳实践

如果你要用 OpenSpace 处理“从 15 份 PDF 准备纳税申报材料”这样的真实专业任务，最佳实践是：

> **把任务拆成可演化的技能链，优先积累工具可靠性与质量验证能力，用 FIX / DERIVED / CAPTURED 持续沉淀成功与失败，并通过指标监控让系统从“会做一次”进化为“越做越稳、越做越便宜”。**

---

##### 六、可直接复用的实践清单

```markdown
- 把 OpenSpace 放在代理执行链核心，而不是末端辅助工具
- 将复杂任务拆分为可独立演化的技能链
- 优先沉淀 PDF/OCR/表格/回退执行这类可靠性技能
- 为文档与表单任务建立强制 QA：完整性、来源追溯、一致性校验
- 区分使用 FIX、DERIVED、CAPTURED 三种演化模式
- 追踪 applied rate、completion rate、fallback rate 等指标
- 敏感业务技能优先团队内共享，不默认公开
- 冷启动阶段允许探索，暖启动阶段强制优先复用已有技能
- 定期通过仪表盘检查技能退化与 token 变化
- 从失败样本中提炼可复用修复模式，而不是只保存成功结果
```
