## 正文

**yibie**

Search as Code：搜索架构的下一次范式转移

Perplexity 刚刚发布了一个新架构，叫 Search as Code（SaC）。听起来像又一个营销术语，但读完他们的研究文章后，我认为这可能是 2026 年 AI 基础设施领域最重要的架构决策之一。

核心思想一句话：AI agent 不再通过 function calling 一次一次地调搜索 API，而是直接写 Python 代码来编排整个搜索流水线。

一、问题：function calling 是一种"串行瓶颈"

传统的 AI 搜索架构是这样的：

模型发出查询 → 搜索引擎跑预设 pipeline → 返回结果 → 模型消费结果  
↑\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_↓  
每次搜索操作 = 一次 LLM inference 往返

这个架构在"用户问一个问题，AI 搜一次"的时代够用。但当 agent 需要完成一个涉及数百次检索的复杂任务时，问题就暴露了。Perplexity 的 Computer 产品中，单个任务可以在几分钟内触发数百甚至数千次检索操作。

每次操作都需要一次 LLM 往返——这就是"串行瓶颈"。更具体地说，传统架构有三个致命缺陷：

粗粒度的上下文。 如果模型只需要一条高度精准的信息，但只能用"重召回"的搜索端点，结果就是大量无关信息被灌进 context window，既浪费 token 又稀释信号。

无法利用领域知识。 模型在训练数据、Agent Skill、记忆中可能知道该怎么搜——比如何时混合词汇和语义信号、优先哪些来源、怎么聚合结果。但传统搜索 API 只暴露查询参数，模型无法把这些知识付诸行动。

控制流低效 + 上下文污染。 很多搜索工作流不是线性的——需要 fan-out、并行、去重。用 serial function calls 来实现这些操作不仅慢，还把大量中间状态扔进了 model context，导致性能退化，被迫频繁 compaction。

二、SaC 的方案：代码替代 function calls

Perplexity 的方案是彻底放弃 function calling 和 MCP 作为搜索接口。不是改进现有方案，而是换了一个完全不同的范式：

模型写 Python 代码 → 沙箱执行 → 代码直接调 Agentic Search SDK 的各个原子原语  
↓  
一次 LLM inference 可以编排上千次搜索操作

三层架构：

模型层（控制面）： 推理用户需求，分解任务，决定需要什么检索策略，生成 Python 代码来实现这些策略。

计算沙箱（执行层）： 提供安全的代码执行环境，处理控制流、批处理、重试、过滤、聚合等确定性操作。

Agentic Search SDK（原语层）： 把 Perplexity 的搜索栈拆解成可组合的原子原语——检索、排序、过滤、fan-out、渲染等。不是把一个搜索 API 打包成库，而是把整个搜索系统重新架构为模块化组件。

关键差异：在 SaC 中，模型不再调用搜索。模型编排搜索。

三、一个案例就够了：CVE 漏洞分析

Perplexity 在文章里给了一个具体的案例。任务：找 2023-2025 年间的 200+ 个高危 CVE，每个需要引用厂商自己的安全公告，包含受影响产品、修复版本，并证明修复版本与特定 CVE 相关。

SaC 的结果：

\- 准确率 100%  
\- Token 消耗从 288.7K 降到 42.9K——减少 85.1%  
\- 被测试的其他系统（OpenAI、Anthropic、Exa 等）准确率全部低于 25%

为什么差这么多？因为 SaC 让模型做了三件事，传统架构做不到：

把规则写进查询计划。 生成的代码直接编码了"只看厂商公告"的约束——NVD、MITRE、第三方聚合器被结构性排除在搜索之外。

用 LLM 做中间规划。 代码会先总结哪些厂商-年份组合产生了足够多的候选页面，请求针对性的查询优化，然后验证每条查询再执行。这不是 hardcode 的爬虫，而是 agent 在运行时通过代码定义的搜索策略。

用代码做结果验证。 搜索子程序找到了看似相关的页面，但任务要求"厂商原文中必须绑定一个 CVE + 一个受影响产品 + 一个修复版本"。代码显式定义了这个 schema，自动去重、拒绝聚合器 URL、丢弃弱版本证据，直到记录数达标。

四、基准测试：2.5 倍优势

Perplexity 在 5 个基准上对比了 SaC（用 GPT 5.5 high reasoning）和 OpenAI Responses API、Anthropic Managed Agents、Exa Agent、Parallel Tasks。  
Perplexity 在 5 个基准上对比了 SaC（使用 GPT 5.5 高推理能力）和 OpenAI 响应 API、Anthropic 托管代理、Exa Agent、并行任务。

SaC 在 5 个基准中赢了 4 个。在最难的 WANDR 基准（模拟"广泛研究"类专业任务）上，SaC 的分数是第二名的 2.5 倍。

成本-性能前沿图更直观：SaC 的低推理设置比所有非 SaC 系统都便宜，同时性能不输；中等推理设置在 $1/任务以下超过了所有竞争对手。

五、三个更深层的洞察

1\. "代码作为编排器 + 能力填充器"

SaC 不只是用代码调用已有能力。当搜索栈或 SDK 没有某个函数的原生能力时，模型可以在沙箱中动态实现。比如一个复杂正则——如果没有原生支持，传统方案是发一个近似查询，在 token 空间中过滤噪声结果。SaC 的做法是并行调 SDK 收集超集，代码去重，然后写额外的 Python 精确过滤。代码同时担任了"编排已有能力"和"制造缺失能力"两个角色。

2\. SDK 通过 autoresearch 自进化

Perplexity 没有手工设计 SDK。他们建了一个 autoresearch 循环，连续运行数周，自动提出和验证 SDK 改进——衡量延迟、代码生成质量、任务完成率。这个循环已经对 SDK 的结构和美学做了大量修改，在所有维度上都获得了显著收益。

这是 meta 层面的一个关键信号：构建 AI 原语的工具本身也需要是 AI 原生的。

3\. Agent Skills 的精简设计

教模型使用定制 SDK 是个难题——SDK 不在预训练数据里。Perplexity 的方案是精心调校的 Agent Skills，根文件不到 2000 token。重点不是列出所有函数（模型可以通过 runtime reflection 获得），而是提供简洁的、可泛化的指南和少量示例，教模型如何组合这些原子原语。

六、这意味着什么

Search as Code 是"代码作为编排器"这一更大范式在搜索领域的具体落地。我们在之前的文章里讨论过 Claude Code 动态工作流如何用 JS 编排子 agent，今天 SaC 展示了同样的原则如何应用到搜索基础设施上。

共同的模式：

\| 旧范式 \| 新范式 \|  
\|--------\|--------\|  
\| 串行 function calls \| 并行代码编排 \|  
\| 预设 pipeline \| 运行时组装 \|  
\| LLM 调 API \| LLM 写代码调原语 \|  
\| 上下文膨胀 \| 中间状态留在沙箱 \|  
\| 人设计接口 \| autoresearch 进化接口 \|

每一个维度都指向同一个方向：AI agent 的下一步不是更好的 function calling，而是根本不再用 function calling。

#### 总结

Perplexity 提出 **Search as Code（SaC）**：  
让 AI 不再一次次用 `function calling` 调搜索 API，而是 **直接写 Python 代码，在沙箱里编排搜索流程**。

核心变化：

> 从「LLM 调搜索」变成「LLM 写代码组织搜索」。

它解决的问题：

- 多次搜索时，function calling 太慢，容易变成串行瓶颈
- 搜索结果粗糙，浪费 token
- 中间过程塞进上下文，污染模型判断
- 复杂任务需要并行、去重、过滤、验证，传统 API 不够灵活

SaC 的架构：

1. **模型层**：理解任务，生成搜索代码  
2. **沙箱层**：安全执行代码，负责并行、过滤、聚合  
3. **SDK 层**：提供搜索、排序、过滤等原子能力  

案例中，SaC 在 CVE 漏洞检索任务里：

- 准确率：**100%**
- Token 消耗降低：**85.1%**
- 多项基准测试表现领先

---

#### 解读

传统搜索像这样：

> AI 问一次 → 搜一次 → 等结果 → 再问一次

复杂任务会非常低效。

SaC 更像这样：

> AI 先写一个搜索脚本 → 脚本自动批量搜索、筛选、验证、汇总

这就像从：

> 人工一条条查资料

变成：

> 写一个爬虫/分析程序自动查资料

区别在于，这个程序不是人写的，而是 **AI 临时生成的**。

它的优势主要有三个：

##### 1. 更快

代码可以并行执行大量搜索，不必每一步都等 LLM 决策。

##### 2. 更省 token

中间结果留在沙箱里，不全部塞进模型上下文。

##### 3. 更可控

代码可以写清楚规则，比如：

- 只看厂商官网
- 排除第三方聚合站
- 必须包含 CVE、产品、修复版本
- 自动去重和验证

这比普通搜索 API 更适合复杂研究任务。

#### 我的意见

我认为 SaC 的方向是对的。

未来 Agent 不应该只会「调用工具」，而应该会「编排工具」。  
也就是说，AI 的能力会从：

> 会用工具

升级到：

> 会写流程、会组织工具、会自动验证结果

不过它也有风险：

- 代码执行必须有严格沙箱
- 搜索 SDK 的设计很关键
- 生成代码出错会影响结果
- 基准测试来自 Perplexity，自家结果需要第三方验证

整体看，**Search as Code 可能是搜索 Agent 的重要进化方向**。  
它不是简单优化搜索 API，而是把搜索变成一种可编程、可组合、可自动验证的基础设施。

## 结构化（1）

### 2026-06-02 08:25:44

##### 主旨概括

文章认为，Perplexity 提出的 **Search as Code（SaC）** 可能代表 AI 搜索架构的一次重要范式转移：AI agent 不再通过一次次 function calling 调用搜索 API，而是直接编写代码来编排复杂搜索流程。  
这种方式可以显著降低 token 消耗、提升并行能力和任务准确率，尤其适合需要大量检索的复杂研究任务。

---

##### 一、传统 function calling 的问题：搜索变成“串行瓶颈”

传统 AI 搜索架构大致是：

> 模型提出查询 → 搜索引擎执行预设流程 → 返回结果 → 模型继续处理

这种模式在简单问答中可用，但在复杂任务中效率很低。比如 Perplexity 的 Computer 产品中，单个任务可能在几分钟内触发 **数百甚至数千次检索操作**，而每次操作都需要一次 LLM 推理往返，形成明显瓶颈。

主要问题有三点：

1. **上下文粒度太粗**
   - 模型可能只需要一条精确信息，却被迫调用“重召回”搜索接口。
   - 结果会把大量无关内容塞进 context window，浪费 token，也稀释有效信息。

2. **无法利用模型已有的领域知识**
   - 模型可能知道如何组合词汇搜索、语义搜索，或哪些来源更可靠。
   - 但传统搜索 API 只暴露有限查询参数，模型无法灵活执行自己的搜索策略。

3. **控制流低效，污染上下文**
   - 复杂搜索往往需要并行 fan-out、去重、过滤、聚合。
   - 用串行 function calls 实现这些流程不仅慢，还会把大量中间状态放进模型上下文，导致性能下降。

---

##### 二、SaC 的核心方案：让模型写代码来编排搜索

Perplexity 的 Search as Code 不是改良 function calling，而是直接换了一种接口范式：

> 模型生成 Python 代码 → 沙箱执行代码 → 代码调用 Agentic Search SDK 的原子能力

核心变化是：

> 模型不再“调用搜索”，而是“编排搜索”。

SaC 的三层架构包括：

###### 1. 模型层：负责决策与生成代码

模型理解用户需求，拆解任务，决定搜索策略，并生成 Python 代码来实现这些策略。

###### 2. 计算沙箱：负责执行与控制流

沙箱提供安全代码执行环境，处理：

- 并行搜索
- 批处理
- 重试
- 过滤
- 聚合
- 去重

这些确定性操作不再占用模型上下文。

###### 3. Agentic Search SDK：提供搜索原子能力

Perplexity 将搜索系统拆成可组合的模块，例如：

- 检索
- 排序
- 过滤
- fan-out
- 渲染

这不是简单把搜索 API 包成 SDK，而是把整个搜索栈重构成可被代码组合的搜索原语。

---

##### 三、案例：CVE 漏洞分析任务

文章引用了 Perplexity 的一个具体案例：

任务要求：

- 找出 **2023-2025 年间 200+ 个高危 CVE**
- 每个 CVE 都必须引用厂商自己的安全公告
- 包含受影响产品、修复版本
- 证明修复版本确实与对应 CVE 相关

SaC 的表现：

- **准确率：100%**
- **Token 消耗：从 288.7K 降到 42.9K**
- **Token 减少：85.1%**
- 其他被测试系统，包括 OpenAI、Anthropic、Exa 等，准确率均 **低于 25%**

SaC 表现更好的原因主要有三点：

###### 1. 把规则直接写进搜索计划

代码明确规定只搜索厂商公告，结构性排除：

- NVD
- MITRE
- 第三方聚合器

这样避免了不可靠或间接来源。

###### 2. 用 LLM 做中间规划

SaC 不是硬编码爬虫，而是让 agent 在运行时生成搜索策略。  
例如，代码会先判断哪些“厂商-年份”组合有足够候选页面，再优化查询并验证后继续执行。

###### 3. 用代码验证搜索结果

任务要求每条记录必须同时满足：

- 厂商原文
- 绑定一个 CVE
- 绑定一个受影响产品
- 绑定一个修复版本

代码会根据这个 schema 自动去重、拒绝聚合器 URL、丢弃弱证据，直到结果达标。

---

##### 四、基准测试：SaC 在复杂搜索中优势明显

Perplexity 在 5 个基准上测试了 SaC，并与以下系统对比：

- OpenAI Responses API
- Anthropic Managed Agents
- Exa Agent
- Parallel Tasks

测试基准包括：

- DSQA
- BrowseComp
- HLE
- WideSearch
- WANDR

结果：

- SaC 在 **5 个基准中赢了 4 个**
- 在最难的 WANDR 基准上，SaC 得分是第二名的 **2.5 倍**
- SaC 使用的是 **GPT 5.5 high reasoning**

成本表现也较强：

- SaC 的低推理设置比所有非 SaC 系统都便宜，同时性能不输
- 中等推理设置在 **每任务 1 美元以下**，性能超过所有竞争对手

##### 五、三个更深层的洞察

###### 1. 代码不仅是编排器，也是能力补全器

SaC 中的代码不只是调用已有搜索功能，还能弥补 SDK 不具备的能力。

例如，如果 SDK 不支持复杂正则过滤：

- 传统方案：发近似查询，再让模型在上下文中筛噪声
- SaC 方案：先并行收集候选结果，再用 Python 去重和精确过滤

因此，代码既能“编排已有能力”，也能“制造缺失能力”。

---

###### 2. SDK 可以通过 autoresearch 自我进化

Perplexity 没有完全手工设计 SDK，而是建立了一个 **autoresearch 循环**，连续运行数周，自动提出并验证 SDK 改进。

优化指标包括：

- 延迟
- 代码生成质量
- 任务完成率

这说明构建 AI 原语的工具本身，也需要采用 AI 原生的方式演化。

---

###### 3. Agent Skills 设计要精简

教模型使用定制 SDK 是难点，因为这些 SDK 不在模型预训练数据中。

Perplexity 的做法是使用精心设计的 Agent Skills：

- 根文件不到 **2000 token**
- 不列出所有函数
- 让模型通过 runtime reflection 获取函数信息
- 重点提供简洁、可泛化的指南和少量示例

目标是教模型如何组合搜索原语，而不是死记 API 文档。

---

##### 六、文章结论：AI 搜索接口可能不再是 function calling

文章认为，Search as Code 体现了一个更大的趋势：

> AI agent 的下一步，不是更好的 function calling，而是用代码作为编排器。

旧范式与新范式对比如下：

| 旧范式 | 新范式 |
|---|---|
| 串行 function calls | 并行代码编排 |
| 预设搜索 pipeline | 运行时动态组装 |
| LLM 调 API | LLM 写代码调原语 |
| 上下文膨胀 | 中间状态留在沙箱 |
| 人设计接口 | autoresearch 进化接口 |

简言之，SaC 的价值在于：让模型从“搜索 API 的使用者”变成“搜索流程的设计者和执行编排者”，从而更适合处理大规模、复杂、需要验证的研究型任务。

###### 1）Agent 的核心瓶颈，正在从「模型能力」转向「系统编排能力」

过去很多 AI 产品的默认架构是：

> LLM → function calling → API → 返回结果 → LLM 再判断下一步

这适合简单任务，但不适合复杂任务。

一旦任务需要大量检索、验证、聚合、去重、并行处理，function calling 会变成串行瓶颈。每次调用都要经过一次 LLM 推理往返，既慢、贵，又容易污染上下文。

Search as Code 的关键启发是：

> 未来高性能 Agent 不只是“会调用工具”，而是“会写代码编排工具”。

这意味着 AI 产品的竞争力，不只在于接入多少 API，而在于是否能把能力拆成可组合原语，并让模型用代码动态编排。

###### 2）代码是 Agent 的「外部工作记忆」和「执行控制层」

- 搜索结果
- 临时判断
- 候选列表
- 去重状态
- 多轮验证结果
- 错误尝试

这会导致 token 膨胀、信号稀释、推理退化。

SaC 的范式是：

> 让 LLM 负责规划，让代码负责执行，让沙箱承载中间状态。

这非常重要。

因为很多任务本质上不需要 LLM 每一步都参与。例如：

- 批量查询
- URL 去重
- 正则过滤
- 表格聚合
- schema 校验
- 重试逻辑
- 并发调度
- 排序打分
- 阈值筛选

这些都应该交给代码，而不是反复消耗 LLM 推理。

SaC 的核心不是“让模型写 Python”这么简单，而是 Perplexity 把搜索系统拆成了可组合的 Agentic Search SDK。

这背后真正有价值的是：

> 我该暴露一个什么 API 给模型？

> 我该把业务系统拆成哪些原语，让模型可以自由组合？

例如搜索系统里的原语可能是：

- retrieve
- rank
- filter
- fan-out
- deduplicate
- render
- verify
- cite

放到其他业务场景，也可以有类似设计。

##### 2. 高价值信息深挖

###### 1）SaC 的本质：从「调用式 AI」到「编排式 AI」

旧范式是：

> LLM 调用预设工具。

新范式是：

> LLM 写代码，动态组织工具、控制流程、制造中间能力。

这带来三个关键变化：

| 维度 | Function Calling | Search as Code |
|---|---|---|
| 执行方式 | 串行调用 | 代码编排，可并行 |
| 控制流 | 由 LLM 多轮决定 | 由代码一次性执行 |
| 中间状态 | 进入上下文 | 留在沙箱 |
| 能力边界 | API 给什么就用什么 | 可用代码补齐缺失能力 |
| 成本结构 | 多轮推理成本高 | 一次推理，批量执行 |
| 灵活性 | 受限于工具 schema | 可运行时组合策略 |

核心转变是：

> LLM 不再是每一步的执行者，而是任务计划和代码生成者。

---

###### 2）SaC 的真正优势不是搜索，而是「复杂任务的结构化闭环」

CVE 案例里，SaC 能做到高准确率，不是因为搜索引擎更强，而是因为它构建了一个闭环：

1. 明确任务规则  
   只看厂商公告，排除 NVD、MITRE、第三方聚合器。

2. 动态生成搜索计划  
   根据厂商、年份、产品、漏洞类型做 fan-out 查询。

3. 收集候选页面  
   批量检索，形成超集。

4. 代码化过滤  
   URL 去重、来源过滤、正则匹配、字段抽取。

5. schema 验证  
   必须同时包含 CVE、受影响产品、修复版本。

6. 证据绑定  
   修复版本必须与特定 CVE 有明确关系。

7. 不达标则继续搜索  
   直到记录数和证据质量满足要求。

这里有一个关键点：

> 高质量 Agent 不只是“回答问题”，而是“持续执行验证循环”。

很多 AI 产品失败，不是模型不知道答案，而是没有把任务拆成可执行、可验证、可迭代的流程。

###### 3）“代码作为能力填充器”是非常重要的产品设计思想

SaC 中一个深层洞察是：

> 当 SDK 没有某个能力时，模型可以在沙箱中临时写代码补齐。

例如：

- SDK 没有复杂正则过滤能力  
  → 模型写 Python 正则。

- SDK 没有某种去重逻辑  
  → 模型写哈希、相似度或 URL canonicalization。

- SDK 没有特定排序函数  
  → 模型写自定义评分。

- SDK 没有批处理策略  
  → 模型写并发调度。

这说明未来工具设计不一定要追求“大而全”。

更好的方式可能是：

> 提供稳定、低层、可组合的原语，把复杂性留给模型生成代码处理。

这类似软件工程里的 UNIX 哲学：

> 每个工具做好一件事，复杂任务通过组合完成。

---

###### 4）Agent Skills 的重点不是文档完整，而是认知压缩

Perplexity 的 Agent Skills 根文件不到 2000 token，这个细节很关键。

教模型使用新 SDK，不是把完整文档塞给它，而是提供：

- 核心心智模型
- 组合方式
- 少量高质量示例
- 常见策略
- 约束边界
- 反模式提醒

这对 AI 产品非常有启发。

很多团队在做 Agent 工具时，会给模型塞很长的工具说明，结果模型反而用不好。

更好的方式是：

> 文档不是给人看的完整说明书，而是给模型看的压缩操作指南。

Perplexity 没有完全手工设计 SDK，而是通过 autoresearch 循环自动测试和改进 SDK。

这意味着未来 AI 基础设施的设计可能不再是：

> 人设计接口 → 人写文档 → 人评估效果

> Agent 使用接口 → 系统记录失败模式 → 自动提出改进 → 基准验证 → 迭代 SDK

这对商业系统建设非常重要。

真正先进的 AI 系统，不只是使用 AI，而是具备：

- 自动评估
- 自动发现瓶颈
- 自动提出接口优化
- 自动回归测试
- 自动演化工具层

也就是说：

> AI 原生系统的接口本身，也应该被 AI 持续优化。

##### 3. 可迁移清单

下面是可迁移到 AI 产品、企业系统、内部自动化平台的设计清单。

###### A. 架构设计清单

| 问题 | 检查点 |
|---|---|
| 是否存在大量串行 function calling？ | 如果一个任务需要 10 次以上工具调用，就要考虑代码编排。 |
| 中间状态是否污染上下文？ | 临时变量、候选列表、日志、去重结果应留在执行环境，而不是塞进 prompt。 |
| API 是否过于粗粒度？ | 如果模型只能调用“万能搜索/万能查询”，说明原语拆分不够。 |
| 是否支持并发 fan-out？ | 复杂任务通常需要批量展开，而不是线性请求。 |
| 是否有沙箱执行层？ | 让模型生成代码，但必须在受控环境执行。 |
| 是否有 schema 验证？ | 高价值任务不能只靠自然语言判断，需要结构化校验。 |
| 是否能自动重试和补搜？ | Agent 应该根据验证结果继续执行，而不是一次性回答。 |

---

###### B. 工具/API 设计清单

设计给 Agent 用的工具时，应优先考虑：

1. **原子化**
   - 不要只暴露一个大而全 API。
   - 拆成检索、过滤、排序、验证、渲染、导出等原语。

2. **可组合**
   - 每个工具输入输出结构清晰。
   - 方便模型用代码串联。

3. **可观察**
   - 每次调用要返回状态、错误、耗时、结果数量、置信度。

4. **可验证**
   - 支持结构化 schema。
   - 支持字段级证据绑定。

5. **可反射**
   - 让模型可以 runtime 查询有哪些函数、参数、示例。

6. **可批量**
   - 支持 batch、parallel、streaming。
   - 不要让 Agent 只能一次处理一个对象。

7. **可约束**
   - 支持来源限制、权限限制、预算限制、时间限制。

###### C. Agent Skill 设计清单

给模型写工具使用指南时，重点不是长文档，而是高密度技能压缩。

一个好的 Agent Skill 应包含：

```markdown
1. 这个工具适合解决什么问题
2. 不适合解决什么问题
3. 推荐的工作流
4. 常见组合模式
5. 典型示例
6. 质量标准
7. 错误处理方式
8. 成本/延迟注意事项
9. 安全边界
10. 反模式
```

避免：

- 塞完整 API 文档
- 函数列表过长
- 缺少示例
- 缺少失败处理
- 缺少任务分解模式
- 只告诉模型“可以调用什么”，不告诉它“怎么组合”

##### 4. 反方与张力

###### 1）代码执行带来更大的安全面

让模型写代码，一定会引入新的风险：

- 沙箱逃逸
- 资源滥用
- 无限循环
- 恶意网络访问
- 敏感数据泄露
- 供应链攻击
- prompt injection 诱导生成危险代码

所以 SaC 的前提是强沙箱能力。

必须有：

- 网络访问白名单
- 文件系统隔离
- CPU/内存/时间限制
- 权限最小化
- 审计日志
- 代码静态检查
- 敏感信息脱敏
- 外部输入净化

否则，SaC 可能从“能力增强”变成“攻击面扩大”。

---

###### 2）模型生成代码的可靠性仍然是问题

模型会写代码，不代表代码总是正确。

常见问题包括：

- 边界条件遗漏
- 异常处理不足
- 并发 bug
- 错误过滤有效结果
- schema 设计不合理
- 对 SDK 函数误用
- 代码运行成功但逻辑错误

所以 SaC 不能只依赖“代码可运行”。

还需要：

- 单元测试
- 结果抽样验证
- 多轮自检
- 断言机制
- schema validation
- 运行时 tracing
- 失败回滚

高价值场景下，执行正确性比生成流畅性更重要。

---

###### 3）原语设计可能成为新的瓶颈

SaC 依赖高质量 SDK。

如果原语设计不好，模型生成代码也会很痛苦。

例如：

- 函数粒度混乱
- 输入输出不一致
- 缺少 batch 能力
- 错误信息不清晰
- 返回结构不可预测
- 工具之间难以组合
- 文档和实际行为不一致

这会导致模型虽然能写代码，但写出来的代码笨重、脆弱、不可维护。

所以 SaC 的竞争力不只是模型，而是：

> 模型 + 沙箱 + SDK 原语 + Skill 文档 + 自动评估体系的整体工程能力。

---

###### 4）并不是所有公司都需要自建 SaC

对很多团队来说，直接上 SaC 可能过度设计。

如果业务还处于早期阶段，问题可能不是 function calling 太慢，而是：

- 数据源没打通
- 业务规则不清楚
- 用户需求不稳定
- 评估体系缺失
- 工具调用都还没跑通

这时贸然引入 SaC，会增加系统复杂度。

更现实的路径是：

1. 先用 function calling 做 MVP。
2. 找出高频、多步骤、成本高的任务。
3. 对这些任务引入代码编排。
4. 再逐步抽象成 SDK 原语。
5. 最后建设自动评估和自进化机制。

---

###### 5）SaC 与 MCP/function calling 不是绝对替代关系

文章里强调 SaC 放弃 function calling 和 MCP 作为搜索接口，但在更广义产品系统里，它们可能是互补关系。

可以这样理解：

| 场景 | 更适合 |
|---|---|
| 简单工具调用 | function calling |
| 标准化跨应用集成 | MCP |
| 多步骤复杂控制流 | Search/Work as Code |
| 高风险确定性操作 | 人审 + 规则引擎 |
| 大规模后台任务 | Agent 生成代码 + 沙箱执行 |

所以更合理的判断是：

> SaC 不是消灭 function calling，而是把复杂工作流从 function calling 中解放出来。

##### 5. 情境化落地

###### 场景一：AI 研究助手 / 行业分析产品

###### 旧做法

用户问：

> 帮我分析 2024 年全球 AI 搜索市场主要玩家和商业模式。

系统可能这样做：

1. 搜索一次。
2. 返回若干网页。
3. LLM 总结。
4. 再补搜。
5. 再总结。
6. 上下文越来越长。

###### SaC 思路

让模型生成一个研究脚本：

```python
players = search_companies("AI search engine market 2024")
sources = fanout_search(players, queries=[
    "pricing",
    "funding",
    "traffic",
    "product features",
    "enterprise customers",
    "API revenue"
])
filtered = filter_sources(sources, allow_domains=["official", "sec", "credible media"])
evidence = extract_fields(filtered, schema=[
    "company",
    "business_model",
    "pricing",
    "funding",
    "traffic",
    "source_url"
])
ranked = verify_and_rank(evidence)
```

###### 产品价值

- 成本下降
- 可追踪证据
- 输出结构化
- 可复用研究流程
- 支持批量行业分析

---

###### 场景二：企业销售情报系统

###### 任务

销售想知道：

> 最近 90 天内，哪些目标客户出现了采购信号？

###### 可拆原语

- 公司列表读取
- 新闻搜索
- 招聘信息检索
- 财报/公告解析
- 技术栈识别
- 融资事件检测
- 关键词过滤
- 信号评分
- CRM 写回

###### SaC 编排方式

模型生成代码执行：

1. 批量读取目标账户。
2. 并发检索每家公司最近动态。
3. 过滤无关新闻。
4. 抽取采购信号：
   - 招聘某类岗位
   - 新开区域
   - 融资
   - 系统升级
   - 合规压力
   - 高管变动
5. 给每个账户打分。
6. 输出推荐跟进理由。
7. 写入 CRM。

###### 关键收益

> 销售情报不再是“AI 搜一下”，而是一个持续运行的信号发现系统。

---

###### 场景三：合规 / 法务检索系统

###### 任务

> 找出某行业在不同国家最新合规要求，并给出原文证据。

###### SaC 适配点

这类任务非常适合代码编排，因为它要求：

- 来源权威
- 引用原文
- 国家/地区维度
- 时间有效性
- 法规版本比对
- 条款级证据绑定

###### 工作流

1. 限定官方来源。
2. 按国家 fan-out。
3. 检索监管机构网站。
4. 提取法规标题、发布日期、适用范围。
5. 对比新旧版本。
6. 绑定条款原文。
7. 输出风险清单。

###### 注意事项

法务场景不能只靠 LLM 总结，必须有：

- 来源白名单
- 引用定位
- 原文链接
- 时间戳
- 版本号
- 人工复核入口

###### 场景四：内部 BI / 经营分析 Agent

###### 任务

> 分析过去 6 个月华东区 SMB 客户流失原因。

###### 传统 Agent 问题

如果通过 function calling 一步步查数据库，会出现：

- 多次 SQL 调用
- 大量中间表进入上下文
- 分析链路不可复用
- 难以审计
- 成本高

###### SaC 思路

让模型写代码：

1. 查询客户流失列表。
2. 拉取使用行为。
3. 拉取工单记录。
4. 拉取销售跟进记录。
5. 聚类流失原因。
6. 对每类原因计算占比。
7. 找典型案例。
8. 输出经营建议。

###### 关键原则

数据不要全部塞给 LLM。

应该是：

> 数据处理在代码里完成，LLM 只看聚合后的关键证据和异常样本。

---

##### 6. 给产品/技术团队的落地路线

###### 第一步：识别串行瓶颈任务

找出这些任务：

- 工具调用次数多
- token 成本高
- 中间状态复杂
- 结果需要验证
- 用户愿意为高质量结果付费

优先改造这些任务。

---

###### 第二步：从 function calling 迁移到 workflow code

不要一开始就做通用 SaC。

可以先针对一个具体高价值场景，让模型生成受限脚本。

例如：

- 只允许调用内部 SDK。
- 不允许任意网络访问。
- 不允许读写本地文件。
- 限制执行时间。
- 限制最大请求数。

---

###### 第三步：抽象业务原语

把业务系统拆成 Agent 可组合原语。

例如销售场景：

```text
get_accounts()
search_company_news()
extract_buying_signals()
score_account()
write_crm_note()
generate_outreach_angle()
```

合规场景：

```text
search_regulator_site()
extract_regulation_metadata()
compare_versions()
verify_clause_reference()
generate_risk_summary()
```

---

###### 第四步：建立评估集

没有评估集，SaC 很难稳定进化。

评估集应包括：

- 标准任务
- 正确答案
- 来源要求
- 成本指标
- 延迟指标
- 失败类型
- 人工评分规则

评估维度：

| 维度 | 指标 |
|---|---|
| 正确性 | 答案准确率、字段完整率 |
| 证据质量 | 是否引用原始来源 |
| 成本 | token、API 调用、执行时间 |
| 稳定性 | 多次运行结果一致性 |
| 鲁棒性 | 遇到缺失数据能否补救 |
| 安全性 | 是否越权、是否泄露敏感信息 |

---

###### 第五步：用失败案例反推 SDK 改进

每次 Agent 失败，都不要只改 prompt。

要问：

- 是不是缺少某个原语？
- 是不是函数粒度太粗？
- 是不是返回结构不清晰？
- 是不是错误信息不够？
- 是不是示例不够？
- 是不是模型不知道推荐组合方式？
- 是不是需要增加验证函数？

长期看，真正提升系统能力的是：

> 从 prompt engineering 转向 interface engineering。

---

##### 7. 一句话总结

Search as Code 的核心不是“让 AI 写搜索脚本”，而是揭示了下一代 Agent 架构的方向：

> LLM 负责规划和生成代码，沙箱负责执行和保存中间状态，SDK 原语负责提供可组合能力，评估系统负责持续进化。

对 AI 产品和商业系统构建者来说，最值得迁移的思想是：

> 不要只给 Agent 工具，要给它一套可编排、可验证、可进化的业务原语系统。

## 深度解读（1）

### 2026-09-18 00:58:50

#### Search as Code 的真正价值：把模型从“执行循环”中解放出来

这篇文章最值得保留的，不是“function calling 即将消失”，而是一个更准确的架构判断：**当任务需要大量检索、过滤和验证时，LLM 不应参与每一个执行步骤，而应一次性生成计划，把可确定执行的工作交给代码。**

传统 Agent 往往形成一个昂贵的循环：模型决定调用工具，工具返回结果，模型读取结果，再决定下一次调用。这个模式适合少量、不可预测的交互；但如果任务需要检索数百个对象，它会让每一步都经过模型推理和上下文传输。延迟与成本固然会上升，更麻烦的是，大量候选结果和中间状态会进入上下文，模型真正需要判断的证据反而被淹没。

Search as Code 的关键变化，是让模型输出一个**可执行的搜索计划**：并行查询哪些来源，如何过滤、去重、重试，满足什么证据结构才接受结果。代码在沙箱里完成循环与数据处理，只把少量异常、阶段性摘要或最终证据交还模型。换句话说，代码在这里不只是工具调用语法，而是模型生成的一种“控制流压缩格式”。

##### 真正的分界线不是代码与 API，而是判断与执行

CVE 案例很好地说明了这一点。任务要求每条记录同时具备厂商公告、CVE、受影响产品和修复版本。模型擅长理解这些语义约束并设计搜索策略，但不适合亲自阅读、记忆和比较数百条中间结果；Python 则很适合执行来源白名单、字段校验、URL 去重和停止条件。

因此，更可迁移的设计原则是：

- 让模型负责歧义较高的任务分解、查询改写和证据判断；
- 让代码负责循环、并行、集合运算、格式验证和状态保存；
- 只在结果不足、规则冲突或出现异常时重新调用模型。

这不仅适用于搜索，也适用于数据分析、客服工单归类、合规审查和批量运营。只要任务包含“大量同构操作＋少数语义决策”，就可能从逐步调用转向“模型生成程序、执行环境完成批处理”。

不过，文章所谓“根本不再使用 function calling”说得过头了。SaC 仍然需要 SDK 或其他接口访问搜索能力，只是把调用发生的位置从模型对话循环移到了沙箱程序。更准确地说，**function calling 从主要编排机制退化为边界接口**；对于支付、删除数据、授权等高风险且步骤较少的操作，显式工具调用反而更容易审计和控制。

##### 决定成败的是原语、验证器和运行时，不是让模型会写 Python

这套架构的产品机会也不在“给 Agent 一个代码解释器”这么简单。真正需要建设的是一套 Agent 友好的执行面：细粒度且可组合的原语、结构化返回值、来源与权限控制、可恢复状态，以及能检查证据是否满足要求的验证器。

文章提到不到 2000 token 的使用指南，也是一个有价值的信号：面向 Agent 的 SDK 不应依赖巨大的文档注入，而应让模型能通过反射发现能力，并用少量规则理解组合方式。接口是否容易被模型稳定生成和纠错，开始成为与“是否方便人类开发者”并列的设计指标。

但文中的性能数字应谨慎看待。100% 准确率、85.1% token 降幅和 2.5 倍领先均来自 Perplexity 自己的案例与基准描述，文章没有给出完整实验设置；底层模型、搜索索引、预算、评分规则和任务定制程度都可能影响结果。尤其是用自家深度集成系统对比通用 Agent，优势未必全部来自 SaC。

所以更值得验证的，不是“代码一定取代工具调用”，而是：**把多少中间状态移出模型上下文，能够在不降低可控性和证据质量的前提下，显著改善成本与成功率。**如果这个变量在更多真实任务上成立，Search as Code 才不只是搜索架构的优化，而会成为复杂 Agent 的通用执行模式。
