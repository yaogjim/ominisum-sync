## 正文

**witcheer ☯︎**

Hermes 代理 v0.4.0。我 24 小时不间断运行这个代理。以下是刚刚发生的变化。

/1/ 现在你可以将 Hermes 公开为一个与 OpenAI 兼容的 API 端点，具体是/v1/chat/completions。你的代理将成为一个模型。任何能够调用 OpenAI API 的系统现在都可以与你的 Hermes 实例交互，就像它是一个托管的 LLM 一样，只不过在其背后它具备工具、记忆、技能和定时任务。  
还有一个用于通过编程方式管理 cron 任务的 /api/jobs REST 端点。我有 15 个 cron 任务。能够通过 API 而不是通过聊天来创建和修改它们，这彻底改变了我的自动化界面。

/2/ 六个新的消息适配器在一次发布中。包括 Signal、钉钉、通过 Twilio 的短信服务、Mattermost、Matrix 以及一个通用 Webhook 适配器。这是在已有的 Telegram、Discord、Slack 和 WhatsApp 基础上新增的，现在总共有十个平台。

/3/ @file  
and @url  
上下文注入与制表符补全。输入@并开始输入文件名，按 Tab 补全，文件内容会被注入到你的消息中。URL 也一样。Claude Code 有这个功能，现在 Hermes 也有了。

/4/ 上下文压缩功能已完全重构。采用结构化摘要并进行迭代更新，而非之前“总结一切后即丢弃”的方式。新增了 token 预算尾部保护，确保最新的对话轮次在压缩中得以保留。

/5/ 四个新的提供方：GitHub Copilot（完整 OAuth）、阿里云 / DashScope、Kilo Code，以及 OpenCode Zen/Go。我使用的是 [http://Z.AI/GLM-5](http://Z.AI/GLM-5) ，这不会直接改变我的设置。但 Copilot 在 400k 上下文下颇具吸引力，对于拥有 GitHub 订阅且寻求高性价比智能体大脑的用户来说很有意思。

/6/ /queue 允许你在代理仍在工作时堆叠提示。而不是等待它完成，你可以输入下一条指令，它会被加入队列。在我的工作流程中，我需要查看 cron 输出，想要跟进三件事，过去每次都需要在每件事之间等待。

仍然感觉还为时过早。仍在摸索边界。但基础正快速变得稳固。

## 通俗精炼（1）

### 2026-03-25 02:05:55

#### Hermes Agent v0.4.0 核心总结

##### 这是什么
Hermes Agent v0.4.0 是一次非常大的版本升级，核心方向很明确：**把 AI 代理从“聊天工具”升级为“可接入、可编排、可长期运行的自动化系统”**。作者已经让它 24 小时持续运行，说明它正朝着真实生产力工具演进。

##### 这次更新最重要的变化
###### 1. AI 代理被“产品化”为 API
Hermes 现在可以直接暴露为 **兼容 OpenAI 的 `/v1/chat/completions` 接口**。  
这意味着任何原本支持 OpenAI API 的系统，都可以把 Hermes 当作一个“模型”来调用，但它背后不只是大模型，还带有：

- 工具调用能力
- 长期记忆
- 技能系统
- 定时任务

本质上，这是把“代理能力”封装成了标准 API，接入门槛大幅降低。

###### 2. 自动化能力明显增强
新增了 **`/api/jobs` REST 接口**，可以通过程序管理 cron 定时任务，而不是只能通过聊天设置。  
这对自动化来说非常关键：从“手动对话驱动”升级为“可编程控制”，更适合复杂工作流和企业场景。

###### 3. 多平台接入能力进一步扩展
这次一口气新增 6 个消息适配器，包括：

- Signal
- 钉钉
- Twilio 短信
- Mattermost
- Matrix
- 通用 Webhook

加上原有的 Telegram、Discord、Slack、WhatsApp，已经覆盖 **10 个平台**。  
这说明 Hermes 正在从单点工具变成一个“多渠道智能中枢”。

##### 产品体验上的关键升级
###### 4. 上下文输入更自然
新增 `@file` 和 `@url` 上下文注入，并支持 Tab 补全。  
用户只要输入 `@` 并选择文件或 URL，就能把内容直接注入对话，使用方式更接近开发者熟悉的工作流，降低了上下文组织成本。

###### 5. 长对话能力更稳
上下文压缩机制被重构，不再是简单“总结后丢弃”，而是改为：

- 结构化摘要
- 迭代更新
- 保留最新对话内容的 token 预算保护

这意味着代理在长期运行、长任务链路中会更稳定，不容易“失忆”或丢掉最近关键信息。

###### 6. 支持更多模型提供方
新增 4 个模型提供方，包括：

- GitHub Copilot
- 阿里云 DashScope
- Kilo Code
- OpenCode Zen/Go

其中 GitHub Copilot 的 **400k 上下文** 被特别提到，意味着在高性价比大上下文场景下，Hermes 的适配空间更大。

###### 7. 支持任务排队
新增 `/queue` 功能，允许代理还在执行时继续输入下一条指令。  
这提升了并行工作体验，特别适合查看结果后连续追加任务，不必每次等前一个动作完成。

##### 这背后的产品意义
###### 从“聊天助手”走向“操作系统”
这次更新最有价值的，不是单个功能点，而是整体方向：

- 对外可作为标准 API 接入
- 对内具备自动化与定时调度能力
- 对用户支持多平台触达
- 对长期运行增强上下文稳定性

换句话说，Hermes 正在变成一个 **可持续运行、可嵌入业务流程、可跨平台协作的 Agent 基础设施**。

##### 一句话结论
Hermes v0.4.0 的重点不是“更聪明”，而是 **更像一个真正可部署、可集成、可长期运行的 AI 代理系统**。  
如果你关心 AI Agent 在真实工作流中的落地，这次更新很值得关注。

##### 总体判断
这是一次很有含金量的版本更新，不是“多加几个功能”，而是在把 Hermes 往真正的 `Agent 基础设施` 推进。

- 是否会暴露本地工具和记忆能力
- 不同调用方是否有严格权限隔离
- 长期记忆、定时任务、外部接口之间是否会相互影响
- 运行在个人设备上时，安全边界是否足够清晰

换句话说，**能力越像“操作系统”，权限和隔离就越不能含糊**。
