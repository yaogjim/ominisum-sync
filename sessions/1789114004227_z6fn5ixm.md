## 分析要点

- **核心高价值点**：将语义发现、关键词排序和rg精确验证组合成分阶段检索链路，可减少Agent反复猜测关键词、读取无关文件及消耗上下文。
- **留存建议**：精读并存档，可作为本地检索工具选型及Agent检索流程设计的参考（文章提供了可直接执行的安装与接入步骤，并系统说明语义检索、BM25、RRF、rg和本地索引在Agent工作流中的组合方式。）

**知识要点**

- 模糊意图适合向量检索，词项相关性适合BM25，明确符号和原文验证适合rg，三者可按线索明确程度组合使用。
- RRF可融合向量检索与BM25的候选结果，在无需统一原始分数尺度的情况下完成去重和统一排序。
- 按代码符号和文档章节建立可定位的信息单元，并默认输出有限预览，有助于降低Agent的工具调用和Token消耗。

**行动项**

- 在一个真实代码仓库中安装zg、建立本地索引，并通过CLI和MCP分别测试自然语言检索。
- 设置相同任务，对比Agent使用标准搜索工具与zg时的正确率、工具调用数、输入Token和总耗时。
- 处理敏感代码或内部文档时优先使用本地Embedding，并确认未显式授权任何远程内容传输。

rg 凭借出色的性能与 穷尽式 匹配能力，已成为开发者和 Agent 检索本地内容的重要基础工具。对于函数名、配置名、错误信息或文档原文等明确目标，rg 能够提供快速、准确且可验证的结果。 随着 Agent 开始处理代码理解、故障定位、知识问答和资料分析等复杂任务，检索输入逐渐从明确的符号或文本，转变为对业务现象、实现意图和知识概念的自然语言描述。 这类查询与代码或文档中的实际表述往往缺乏直接的词汇对应。例如，“恢复主题偏好”的实现可能被定义为 hydratePreferences ，而用户询问的“ 访问权限 申请流程”，在文档中可能被表述为“账号授权与审批”。在缺少准确关键词时，仅依赖文本匹配容易遗漏相关内容；扩大搜索范围，又会产生大量缺少相关性排序的结果。 为定位所需信息，Agent 往往需要多轮构造查询、执行搜索并读取文件，再从分散的文本匹配中整理相关上下文。这不仅增加了工具调用、响应时间与上下文消耗，也可能导致 Agent 基于不完整的信息得出结论。 因此，本地内容检索需要在保留 rg 精确、快速和穷尽能力的基础上，进一步具备 语义发现、相关性排序与上下文组织能力 。这正是 zg 希望解决的问题。 What is zg？ 为解决上述问题，团队开源了 zg（zvec-grep） ：一套面向人与 Agent 的本地优先检索基础设施。zg 对代码、文档等本地内容进行提取、组织与索引，并通过 CLI 与 MCP 提供语义检索、 BM25 、混合检索和 rg 精确匹配能力，让本地检索从关键词匹配延伸至意图发现、相关结果排序与精确验证。 zg 的核心设计目标是 让分散在本地文件中的信息能够被高效发现和准确定位 ，设计宗旨包括： 全流程检索：面向从模糊探索、相关性收敛到精确验证的完整过程，提供语义检索、BM25、混合检索与 rg 等不同能力；让每个阶段都能采用适合的检索方式，减少关键词猜测、重复搜索与结果遗漏； 多文件格式支持：面向代码、文档与 结构化数据 等多类文件格式，采用可扩展的内容提取机制，并尽可能保留符号、标题、层级与元数据；让更多本地文件转化为结构清晰、可准确定位的检索内容，持续拓展 zg 可检索的信息边界； 上下文高效：对多路检索结果进行融合、排序并按需提供预览，同时保留来源与位置；让人与 Agent 更快获得任务所需的信息，减少无关内容带来的阅读、工具调用与 Token 消耗； 本地优先：文件扫描、索引与本地 Embedding 默认在设备内完成，远程内容传输必须经过显式授权；在保障隐私的同时，让用户始终掌握数据流向。 Why zg？ 基于上述设计目标，zg 的首个开源版本从代码与文本内容入手，提供 向量检索 、BM25 与 rg，支持通过 CLI 和 MCP 在 macOS、Linux 与 Windows 上使用，并具备本地 Embedding、嵌入式索引与 增量更新 能力。下面将从上手体验、检索与内容覆盖、检索效率与成本，以及本地运行与数据隐私四个方面展开。 三步上手，人与 Agent 即刻可用 zg 支持 macOS、Linux 和 Windows ，面向开发者提供 CLI ，面向 少走弯路，更省 Token 与时间 zg 关注的不只是单次查询速度，更是 Agent 完成整个任务所需的搜索轮次、Token 与时间。为减少反复尝试关键词、读取无关文件和拼接上下文产生的消耗，zg 对完整检索链路进行了针对性优化： 检索决策优化：通过 MCP 工具描述与使用指引，帮助 Agent 根据问题中是否存在明确关键词、位置或符号，选择适合的检索方式，并在信息充分时停止搜索，减少无效试探； 召回与排序优化：联合 BM25 与向量检索生成候选结果，通过 RRF（Reciprocal Rank Fusion）完成多路结果融合、去重与统一排序，让相关内容更早出现，减少无关文件读取； 内容组织优化：按代码符号、文档章节等结构提取可独立定位的 信息单元 ，并保留文件路径与来源位置，减少 Agent 从完整文件中手工拼接上下文的成本； 上下文输出优化：默认返回经过排序的紧凑结果与有限预览，需要时再读取完整内容，避免大量无关文本直接进入 Agent 上下文。 这些优化最终需要在完整任务中体现价值，而不只是让单次查询看起来更快。为此，团队在代码仓库问答 SWE-QA-Bench 和深度研究问答 BrowseComp-Plus 上进行了配对 A/B 评测。其中，SWE-QA-Bench 包含 20 个真实代码仓库问答任务，要求 ## 深度解读（1）

### 2026-09-18 00:03:17

#### zg 的价值不在“向量版 rg”，而在重构 Agent 的检索流程

zg 最值得关注的判断是：**Agent 检索本地内容，不应在关键词搜索和语义搜索之间二选一，而应是“模糊发现—相关性收敛—精确验证”的分阶段过程。**

rg 适合查找已知符号、报错原文和配置项，优势是快速、穷尽、结果可验证；但当问题是“主题偏好如何在启动时恢复”时，代码里可能只有 `hydratePreferences`，词汇无法直接对应。纯向量检索能发现语义相关内容，却可能遗漏精确标识符，或者给出“意思相近但并非实现位置”的结果。zg 因此把向量检索、BM25、RRF 融合排序和 rg 放在同一个入口中，让 Agent 先找到可能相关的模块，再用符号和原文确认。

这不是算法突破，多数能力都已有成熟方案；它的实际贡献是把它们组织成一套适合 Agent 使用的本地基础设施。

##### 检索质量之外，更重要的是上下文获取成本

文章的评测揭示了一个容易被忽视的变量：Agent 的效果不只取决于模型能力，也取决于它为了获得证据走了多少弯路。反复猜关键词、打开整份文件、拼接跨文件信息，会同时消耗工具调用、时间和输入 Token，还可能让模型在证据不完整时提前作答。

zg 试图优化的不是单次查询延迟，而是完成任务的总成本：按代码符号和文档章节切分、保留路径与位置、先返回有限预览、需要时再读取全文。其报告的结果中，最有意义的并非 BrowseComp-Plus 准确率从 98.67% 升到 99.00%——这个提升很小——而是输入 Token、工具调用和耗时均下降约四成。**当模型能力逐渐商品化，如何以更少上下文取得足够证据，可能成为 Agent 产品更稳定的差异点。**

不过，这些数字仍应谨慎看待：测试规模有限，索引成本未计入，而且是团队自测。SWE-QA-Bench“提升 1.50 分”也需要结合评分尺度判断。更值得验证的是，在频繁变化的大仓库、跨语言项目和低性能设备上，增量索引能否持续保持新鲜、低开销与高召回。

##### 本地优先不是附加卖点，而是进入真实组织的前提

代码、内部文档和研究资料通常无法默认上传云端。zg 将内容提取、Embedding、索引和检索都放在设备内，并通过 MCP 供多个 Agent 复用，这使它更接近一种“本地上下文层”，而不是某个聊天产品的搜索插件。16M 级模型若确实能在实际任务中接近大型远程 Embedding，其意义也不是模型更强，而是**检索质量已经可能在隐私、部署成本和延迟约束内达到可用阈值**。

因此，zg 当前最值得保留的认识是：**Agent 的检索能力不是再增加一个搜索工具，而是建立一条从意图发现到证据确认、同时受隐私与成本约束的完整链路。**谁能把这条链路做得可控、可追溯、足够便宜，谁才更可能成为 Agent 的长期基础设施。

## 口播总结（1）

### 2026-09-20 00:37:07

本地搜索真正的难点，已经不只是“文件里有没有某个词”，而是“当你不知道准确关键词时，能不能找到表达相近、真正相关的内容”。开源工具 zg 想解决的，就是从自然语言意图出发，发现本地代码和文档中的相关信息，再逐步缩小范围，直到精确定位。

传统工具 rg，也就是 ripgrep，非常擅长高速、穷尽式的文本匹配。搜索函数名、配置项、错误信息，或者一段确定的原文时，rg 快速、准确，结果也容易验证。但现在，人工智能 Agent 越来越多地参与代码理解、故障排查和知识问答。它收到的往往不是明确关键词，而是对现象或意图的自然语言描述。

比如，用户想找“程序启动时如何恢复主题偏好”。代码中的实现名称，却可能是英文函数 hydratePreferences。用户询问“访问权限申请流程”，文档里写的也可能是“账号授权与审批”。意思相近，字面却对不上。

如果只用关键词搜索，Agent 很容易漏掉相关内容。把搜索范围放大，又会得到大量没有相关性排序的结果。于是，Agent 只能反复猜关键词、执行搜索、打开文件，再手工拼接上下文。这样不仅增加工具调用、响应时间和输入 Token，也可能让 Agent 因为信息不完整而得出错误结论。

zg，也就是 zvec-grep，正是为这类问题设计的。它是一套面向人和 Agent 的本地优先检索工具。它会提取、组织并索引本地代码和文档，同时提供四类搜索能力。

语义检索负责理解“意思是否接近”，适合从模糊描述中发现线索。BM25 是一种经典的关键词相关性排序方法，适合找出词语匹配度较高的内容。混合检索会结合语义和关键词结果。最后，rg 继续负责精确匹配和穷尽验证。

这四种能力不是固定流水线。线索不足时，可以先做语义探索。获得函数名、术语或文件位置后，再转向精确搜索。如果一开始就知道目标符号，也可以直接使用 rg。关键不是用某一种搜索替代所有工具，而是让不同阶段使用更合适的检索方式。

zg 还会融合、去重并重新排序多路搜索结果。它使用一种叫作倒数排名融合的方法，把不同检索方式中排名靠前的内容综合起来，让更可能相关的结果优先出现。返回结果时，zg 默认只提供紧凑预览，同时保留文件路径和具体位置。只有确实需要时，Agent 才继续读取完整内容。

这意味着，zg 优化的并不只是一次查询有多快，而是完成整个任务要搜索多少轮、读取多少无关文件，以及消耗多少上下文。

为了让索引内容更容易定位，zg 会尽量按照原有结构进行切分。处理代码时，它可以提取符号、函数签名和层级信息。首个版本支持多种常见语言，包括 C 和 C 加加、Go、Java、JavaScript、TypeScript、Python 和 Rust，也支持 Vue 与 Svelte 组件。处理 Markdown 文档时，它会按照标题和章节组织内容。纯文本、HTML、XML、CSV、JSON、TOML 和 YAML 等文件，也可以进入索引。用户还可以通过路径、文件类型和忽略规则限制范围，避免内容越多，噪声也越多。

在使用上，zg 同时提供命令行工具和 MCP。MCP 可以理解为 Agent 调用外部工具的一套连接协议。安装后，zg 能自动发现 Codex、Claude Code、Cursor 和 OpenCode，并完成相关配置。基本流程只有三步：安装 zg，为当前工作区建立本地索引，然后通过命令行查询，或者让 Agent 直接调用。命令行和 Agent 可以复用同一份索引，不必重复构建。

团队还用两组任务比较了普通 Agent 工具和加入 zg 后的效果。实验保持 Agent、模型、提示词、运行环境和任务限制一致，zg 方案只增加预建索引、MCP 工具和使用指引。

第一组是代码仓库问答，包含二十个真实任务，需要跨文件定位实现并进行多步推理。按照团队公布的结果，使用 zg 后，工具调用减少超过一半，输入 Token 减少近一半，评审得分提高了一点五分。

第二组是深度研究问答，包含八十个问题，需要从大规模固定语料中整合多份文档证据。使用 zg 后，准确率从百分之九十八点六七提高到百分之九十九。输入 Token 减少百分之三十七点五六，工具调用减少百分之四十三点五二，Agent 耗时减少百分之三十八点五八。

不过，这些结果有一个重要前提：评测没有把首次建立索引的成本算进去。建立索引确实需要时间和计算资源，使用远程文本向量模型时，还可能产生调用费用。团队的理由是，索引可以被多次查询和多个 Agent 任务复用，之后也只需要增量处理发生变化的内容。因此，使用时间越长，首次成本越容易被摊薄。

另一个核心设计是本地优先。代码和内部文档可能包含敏感信息，所以 zg 默认在设备内完成文件扫描、内容提取、文本向量计算、索引和检索，不要求上传文件，也不依赖外部服务。

它内置十一种端侧模型，覆盖代码、文档、多语言和轻量运行等需求。默认模型规模约为一千六百万参数，本地缓存大约三十二兆字节，不需要显卡。团队给出的例子是，在配备苹果 M4 Pro 芯片的设备上，为一个包含三千四百五十七个文件的 Django 仓库建立完整索引，耗时不到半分钟。向量索引和 BM25 索引也都存放在设备内，不必额外部署数据库服务。

如果本地模型无法满足检索质量、多语言覆盖或设备资源要求，用户仍然可以选择远程模型。但远程功能不会自动启用。只有经过明确授权，相关文本或查询才会离开设备。

目前，zg 仍处于早期阶段。后续计划包括图检索、更好的查询规划与重排，支持 PDF、Word 和 PowerPoint，以及图片文字识别和跨模态检索。团队还希望继续降低资源占用，并把本地运行扩展到手机等受限设备。项目采用 Apache 二点零协议开源。

最值得记住的是，zg 并不是要取代 rg。它补上的是关键词搜索之前的“发现”和之后的“排序与组织”。当问题表达和文件原文不一致时，先用语义找到方向，再用关键词收敛，最后用 rg 精确验证。对 Agent 来说，这种完整的检索链路，有机会同时减少搜索轮次、上下文消耗和遗漏风险；而本地优先，则让效率提升不必以交出敏感数据为代价。

## 深度解读-口播（1）

### 2026-09-30 11:55:24

本地搜索最难的情况，往往不是文件里没有答案，而是你描述问题的方式，和文件里的写法对不上。刚刚开源的 ZG，就是想在精确文本搜索之外，补上按意思找内容、按相关性排序，以及组织上下文的能力。

理解这个问题，可以先看开发者常用的搜索工具 RG。只要你知道函数名、配置项，或者一段报错原文，RG 就能快速找出匹配位置。它的优势是精确，而且能够找全符合条件的文本。

但人工智能智能体，也就是能调用工具完成任务的 AI，越来越需要处理另一类问题。比如，用户问的是“访问权限申请流程”，文档里的标题却叫“账号授权与审批”。两者意思接近，字面却不一样。直接搜用户的话，可能什么也找不到。

这时，智能体往往要不断换关键词，反复搜索，再打开多个文件拼凑线索。搜索范围太窄，会漏掉答案；范围太宽，又会得到大量没有相关性排序的结果。时间和上下文空间都花掉了，最后还可能依据不完整的信息作出判断。

所以，ZG 的思路不是替代精确搜索，而是让本地检索同时具备两种能力：不知道准确名称时，能发现相关内容；找到线索以后，又能回到原文，精确核实。

这两种能力是怎么配合的？

ZG 提供了几种搜索方式。语义检索会把文本转换成能够表达含义的数值向量，用来寻找意思相近的内容。另一种叫 BM25，是根据词语匹配情况给结果评估相关性的方法。混合检索把这两路结果结合起来，而 RG 继续负责精确文本匹配。

比如，要找权限申请流程，可以先用自然语言发现“账号授权与审批”这份文档。拿到明确标题、术语或者代码符号后，再做精确搜索，确认具体位置。不过，这不是一套必须按顺序执行的流程。已经知道函数名，就可以直接精确搜索，不必先绕一圈语义检索。

ZG 还会尽量按内容结构建立索引。对支持结构解析的代码，提取函数、符号、签名和层级信息；对 Markdown 文档，按标题和章节组织；对其他文本和数据文件，切成能够定位的片段。

这里的关键，不只是“搜到了”，而是“搜到以后能直接用”。ZG 会融合多路结果，去重并排序，默认先给出紧凑的结果和有限预览，同时保留文件路径与来源位置。需要更多信息时，再读取完整内容。这样，智能体不必每次都打开一整份文件，从头寻找有用的几行。

目前，ZG 已经支持代码、常见文本文档，以及 JSON、CSV 等文本数据文件。原生处理 PDF、Word、演示文稿，以及图片识别和跨模态检索，则属于后续计划，不能当作现有能力。

这些设计有没有实际效果？文章给出了团队自己的配对评测。

一组评测包含二十个真实代码仓库问答任务，要求智能体跨文件定位实现，并完成多步推理。另一组包含八十个深度研究问题，要求从固定的大规模资料中检索、整合多份文档的证据。

每组实验保持智能体、模型、提示词、运行环境和任务限制一致。对照方案使用标准工具，ZG 方案则额外提供预先建立的索引、工具接口和使用指引。

按照团队报告，在代码仓库问答中，加入 ZG 后，工具调用减少超过一半，输入给模型的文本量减少接近一半，评审得分也有所提升。

在深度研究问答中，输入文本量减少约百分之三十八，工具调用减少约百分之四十四，智能体耗时减少约百分之三十九。准确率则从百分之九十八点六七，升到百分之九十九。

这组结果最值得注意的，不是准确率大幅跃升，而是在维持任务质量的同时，减少了搜索和阅读的消耗。ZG 优化的目标，也不只是让一次查询更快，而是让整个任务少走弯路。

不过，有一个重要前提：这些评测没有把预先建立索引的成本算进去。建索引需要时间和计算资源，使用远程向量化模型还会产生调用费用。团队的理由是，索引可以被多个查询和任务反复使用，之后只需增量处理变化的内容，初始成本会逐渐摊薄。因此，理解这些节省幅度时，要把索引可复用这个条件一起记住。

再看本地运行和隐私。

ZG 默认在设备内完成文件扫描、内容提取、文本向量化、索引和检索，不需要把内容上传到外部服务。索引采用嵌入式方式存储，也就是说，不必另外部署和维护一套数据库服务。

默认的轻量模型不需要显卡就能运行。文章举了一个具体例子：在搭载苹果 M 四 Pro 芯片的设备上，为一个包含三千四百多个文件的 Django 代码仓库完整建立索引，耗时不超过半分钟。

同一份本地索引，既可以供人在命令行里搜索，也可以通过工具接口供智能体使用，不需要各自再建一份。当前版本支持苹果、Linux 和 Windows 系统，也提供了自动配置部分常见智能体工具的安装能力。

如果本地模型无法满足检索质量、多语言覆盖或设备资源方面的要求，用户也可以选择远程向量化模型。但远程能力不会自动启用。按照文章的设计说明，相关文本或查询只有经过显式授权，才会离开设备。

归根结底，ZG 想补上的，是从“我大概知道要找什么”，到“我能找到并核实原文”之间的那段距离。语义检索负责发现线索，相关性排序和结构化片段负责减少阅读负担，精确搜索负责验证。它的价值，要放在完整任务里看，同时也要记住：索引有初始成本，部分文件格式仍在规划中，而本地处理是默认路径。
