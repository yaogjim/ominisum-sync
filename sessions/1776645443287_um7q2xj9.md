### 自动研究 💚 自动扩缩容

研究是不可预测的，研究工作量也是如此。研究人员或其代理可能需要数十或数百个 GPU 并行进行超参数搜索，然后降至一个 GPU 来调试问题，然后重新扩展到几个 8GPU 集群以进行验证——所有这些都在同一个工作会话中完成。

大型的长期预留资源能为你提供突发容量，但成本高昂：即使代理仍处于“思考…”状态（未被使用），你仍需为集群付费。而且大多数集群都难以使用。单个实例或工作站成本低且易于使用，却会迫使实验串行运行，拖慢迭代速度。

你真正想要的是两全其美：单机的易用性和成本控制，以及大型集群的突发容量。

而且不仅仅是计算量，还有计算的类型。调试 CUDA 错误需要一个交互式沙箱，在其中代理可以查看状态并快速迭代。12 小时的训练任务需要一个容错批处理任务，带有重试和检查点功能。超参数搜索需要数十个独立任务并行运行。

传统云基础设施迫使你和你的智能体只能选择一种模式并一直使用它。你真正需要的是让智能体自身实时决定计算资源的用量和类型，并让基础设施随之调整。

### 参数高尔夫

[OpenAI 的参数高尔夫挑战](https://openai.com/index/parameter-golf/)要求你将一个语言模型压缩成一个≤16 MB 的工件，该工件需在 8×H100 上运行且耗时不超过 10 分钟，同时最小化每字节的位数。由于 Modal 允许代理通过简单的 API 调用配置和释放 GPU，它能够自主扩展——在探索阶段启动数十个低成本的单 GPU 运行实例，在验证阶段运行 5 个并行的 8×H100 实验，在调试阶段转为串行执行，完成后缩减至零资源使用。下面，我们将详细介绍时间线，以及使用 Modal 带来的具体加速和效率优势。

#### 阶段1：从小规模开始进行流水线验证

该代理以任何优秀研究工程师都会采用的方式开始——进行冒烟测试。它通过 Modal 的 API（modal.Sandbox.create()）创建了一个单 GPU 沙箱，训练了一个 800 万参数的微小模型一轮，对其进行了量化，并进行了评估。在大约一小时内完成了四个快速实验，以确保整个流程端到端正常运行。基准 BPB：1.42。

我们通过比较相对于 8×H100 工作站（足以单独运行每个实验）的加速增益，以及相对于 40 GPU 集群（足以处理持续的并发负载）的效率节省，来总结结果。加速增益来自于同时运行超过工作站最大 GPU 数量的 GPU；效率节省则来自于运行的 GPU 数量少于集群总 GPU 数量。

![图像](https://pbs.twimg.com/media/HF495mPasAAuglz?format=png&name=large)

这个验证步骤没有获得加速，因为它从未使用超过 8 个 GPU，通常只用一两个。但这意味着与让集群约 98%处于空闲状态相比，节省了大量成本！

#### 第二阶段：横向扩展以进行广泛探索

随着工作流程的运行，代理需要探索搜索空间：模型大小、学习率、序列长度、训练时长。它启动了约 40 个独立的单 GPU 沙箱，并行运行——每个都是不同的超参数组合，每个都配备了一个 modal.Sandbox.create(gpu='H100') 调用。没有作业队列，没有资源分配配置，每个实验仅需一个函数调用。整个全面探索在 36 分钟的实际时间内完成。

从那里开始，研究聚焦于：另外 23 项单 GPU 实验，这些实验聚焦于最有前景的模型规模和学习率；随后进行了 4 次大胆的实验，进一步优化最佳配置。BPB 在三个子阶段中稳步下降：1.40，随后 1.37，再降至 1.34。探索阶段共进行了 68 项实验，总耗时约 14 个 GPU 小时，所有实验均在单 GPU 上进行。

![图像](https://pbs.twimg.com/media/HF4-LVzasAATEc4?format=png&name=large)

与工作站相比，这里的总体加速比不算显著，但峰值加速比实际上非常显著：在约 40 分钟内完成约 40 次运行，而不是 3 小时。这就是午餐后或游览 Mission Cliffs 后就能获得结果，与需要在晚上再次检查结果之间的区别。而且效率节省仍然非常显著。

#### 第3阶段：扩大规模以验证

到半夜的时候，代理已经清晰地了解了哪些架构效果最好。它需要进行全面验证。

因此，它从单 GPU 扩展到每个实验 8×H100。基础设施变更仅涉及一个参数：gpu='H100' 变为 gpu='H100:8'。没有新的集群配置，没有新的部署清单——Modal 以处理单 GPU 的相同方式处理多 GPU 配置。代理以全规模运行了前五的配置——5 × 8×H100，40 个 GPU 同时运行——并且 BPB 从 1.34 降至 1.14。

![图像](https://pbs.twimg.com/media/HF4-WL6asAQhj41?format=png&name=large)

在这里，我们看到 Modal 部署相比工作站的加速优势：核心实验在 4 小时内完成，而不是 20 小时。这就是你在同一个工作日内就能完成的工作和需要你等到周末才能完成的工作之间的区别。

效率提升现在很小。但这对集群来说是不现实的最佳情况！我们假设这次运行的资源配置是完美的。但就像打高尔夫球一样，

[研究不是完美的游戏](https://www.reddit.com/r/golf/comments/lwvwpf/fyi_golf_is_not_a_game_of_perfect_really_helped_me/)。因此，在实际操作中，研究人员要么资源配置不足而失去加速效果，要么资源配置过多而失去效率。

[Modal 保持 GPU 分配的完美优化](https://modal.com/blog/gpu-utilization-guide)

.

#### 阶段 4: 缩减规模以调试

然后智能体卡住了。模型训练得很好，但量化步骤——为了符合 16 MB 的预算而进行的 GPTQ 压缩——正在 CPU 上运行，耗时超过 45 分钟。10 分钟的评估窗口意味着提交甚至无法完成。瓶颈在于训练后的流程。

接下来是一段漫长的调试过程。这个代理首先尝试了明显的解决方案：延长超时时间。45 分钟，然后是 60 分钟、90 分钟，最后是两小时。在这个阶段，它 又回到了一次运行一到两个实验的状态因为在诊断顺序瓶颈时，并行是没有意义的。五个半小时，超过 60 个 GPU 小时，而且每次运行都超时了。

然后它完全改变了方法。它重写了量化步骤，使其能在 GPU 上运行。下一次实验总共在 52 分钟内完成，包括训练和量化过程。

![图像](https://pbs.twimg.com/media/HF4-lS5akAA0jio?format=png&name=large)

再次，调试有了适度的提速——尽管在某些情况下，策略可以并行实施。但效率提升非常显著。

#### 阶段5：重新扩容以完成

随着完整的流水线正常运行，该智能体进入了优化阶段。它首先进行了一轮验证——2 组并行的 8×H100 实验，以确认修复没有导致质量下降（BPB：1.1420）。随后，它扩展到 5 组并行的 8×H100 实验——每次使用 40 个 GPU，每组测试不同的架构、学习率调度、正则化方法和数据混合策略。Modal 的弹性配置功能意味着它可以通过简单的沙箱创建调用，在单个调试沙箱和 40 个同时运行的 GPU 之间进行扩展。

BPB 在三轮优化中逐步下降：1.1230，然后 1.1217，然后 1.1206。最后一轮使用 4×8×H100 的配置，结果为 1.1220 — 略有下降。该代理识别到收益递减，将资源缩放到零并停止。

![图像](https://pbs.twimg.com/media/HF4-0kMaEAAb6Uz?format=png&name=large)

在这个阶段，我们同时看到两种优势：当并行尝试策略时，我们能够达到实验吞吐量的峰值，相比工作站实现显著提速；但我们也可以调整吞吐量以随时间匹配实验需求，相比集群实现显著效率提升。

#### 自动扩缩容如何让 AI 代理“自己做研究”

##### 核心观点

这篇文章想说明一件事：**AI 代理做研究时，最需要的不是固定的大集群，而是能随任务变化自动增减的 GPU 资源**。  
因为研究过程本身非常不稳定——有时需要几十张卡并行搜索，有时只需要 1 张卡调试问题，如果一直养着大集群，会非常浪费。

##### Modal 解决了什么问题

Modal 提供的是一种 **按需调用、自动释放、可快速切换形态的 GPU 基础设施**。  
代理可以像写代码一样，直接决定要用 1 张 GPU、8 张 GPU，还是几十上百张 GPU；任务结束后资源自动回收，不会因为机器闲置而持续付费。

简单说，Modal 试图同时满足两点：

- **像单机一样简单易用**
- **像大集群一样能随时爆发扩容**

##### 文章里的实验案例

作者让 Claude Code 去做 OpenAI 的“参数高尔夫挑战”，目标是在严格的体积和运行时间限制下压缩模型。  
结果是：**15 小时内完成 113 次实验，消耗 238 个 GPU 小时，核心训练速度比单工作站快 5 倍，同时又避免了长期占用大集群的高成本。**

这说明 AI 代理不仅能自动做研究，也能**动态决定自己需要多少算力**。

##### 研究过程是怎么扩缩容的

###### 1. 先小规模验证

一开始，代理只用单 GPU 做冒烟测试，确认训练、量化、评估流程能跑通。  
这阶段几乎不需要加速，但能避免大集群长时间空转，**非常省钱**。

###### 2. 再大规模并行探索

流程跑通后，代理启动约 40 个单 GPU 实验并行搜索超参数。  
这样原本要排队跑很久的实验，可以在几十分钟内完成，明显提升了研究迭代速度。

###### 3. 然后扩到 8 卡做验证

找到较优方向后，再把单 GPU 切到 `8×H100` 做大规模验证。  
这里几乎只改一个参数，就能从小实验切到大实验，**避免了传统集群复杂配置**。

###### 4. 出问题时再缩回去调试

后面代理发现量化步骤太慢，成了瓶颈。  
这时并不需要继续大规模并行，而是退回少量资源做调试，直到把 CPU 量化改成 GPU 量化，才把整体流程跑顺。

###### 5. 最后重新扩容冲刺

问题解决后，再次扩到多组 `8×H100` 并行优化，持续提升结果。  
当收益开始变小，代理会自动停下，并把资源缩到零。

##### 这篇文章真正想表达的价值

文章不只是讲“GPU 能自动扩缩容”，而是在强调一个更大的趋势：  
**未来 AI 研究不只是人使用算力，而是代理自己调度算力。**

这意味着基础设施也要从“固定资源池”变成“实时响应代理需求的弹性系统”。  
谁能让代理低门槛地调用、切换、释放算力，谁就更适合承接下一代自动化研究工作流。

##### 一句话总结

**Modal 的核心价值，不是单纯提供 GPU，而是让 AI 代理像调用函数一样，按研究节奏动态使用算力，在“更快出结果”和“更少浪费成本”之间取得平衡。**

## 结构化（1）

### 2026-04-20 00:56:58

#### 自动扩缩容如何帮助 AI 代理做研究

这篇文章的核心观点是：AI 自动研究的关键，不只是“能不能跑实验”，而是“能不能按需、低成本地获得合适的 GPU 资源”。Modal 通过自动扩缩容，让代理在研究的不同阶段自由切换算力规模和计算模式，兼顾速度、成本和易用性。

##### 1. 问题背景：自动研究需要“弹性算力”
- AI 代理做研究时，计算需求并不稳定：有时要并行跑几十上百个实验，有时只需要 1 张 GPU 调试。
- 传统方案各有缺点：
  - 长期预留的大集群虽然能应对高峰，但即使空闲也要持续付费，成本高。
  - 单机或工作站便宜、好用，但实验只能串行执行，研究迭代很慢。
- 真正理想的方案，是同时具备：
  - 单机的低成本和易用性
  - 集群的弹性扩展能力
- 除了“算力多少”，研究还需要不同“计算形态”：
  - 调试 CUDA 错误时，需要交互式沙箱
  - 长时间训练时，需要可重试、可检查点恢复的批处理任务
  - 超参数搜索时，需要大量并行独立任务

##### 2. Modal 的解决思路：让代理自己决定用多少 GPU
- Modal 提供的是一种“按需分配、自动释放”的基础设施。
- 代理可以直接在代码里指定资源，例如：
  - 用 `@app.function(gpu='H100:8')` 启动训练任务
  - 用 `modal.Sandbox.create(gpu='H100:8')` 启动交互式沙箱
- 资源特点很明确：
  - GPU 几秒内即可启动
  - 从 1 张 GPU 扩展到几十或上百张 GPU，只需改一个参数
  - 任务结束后自动释放，避免集群空转带来的账单
- 为了让代理更容易使用，Modal 还专门提供了一套“技能模板”，教代理如何：
  - 启动交互式沙箱
  - 编写并运行训练作业
  - 使用存储卷
  - 编排并行子代理

##### 3. 实验任务：参数高尔夫挑战
- 文中展示的是 OpenAI 的“参数高尔夫挑战”。
- 目标要求很严格：
  - 把一个语言模型压缩到 `<=16 MB`
  - 在 `8×H100` 上运行
  - 总耗时不超过 `10 分钟`
  - 同时尽量降低每字节位数（BPB）
- Tony 给 Claude Code 配置了相关技能后，让它去做这项研究任务，然后自己去睡觉。
- `15 小时`后醒来时，代理已经：
  - 完成 `113 次实验`
  - 累计消耗 `238 个 GPU 小时`
  - 核心训练速度比单台工作站快 `5 倍`
  - 同时只用了专用集群资源的一小部分

##### 4. 阶段 1：先小规模验证流程是否可行
- 代理先采用研究工程师常见的做法：先做冒烟测试，验证整条流程是否跑通。
- 它通过 `modal.Sandbox.create()` 创建了单 GPU 沙箱，做了以下工作：
  - 训练一个 `800 万参数`的小模型 1 轮
  - 进行量化
  - 进行评估
- 结果：
  - 大约 `1 小时`内完成 `4 个`快速实验
  - 初始 BPB 为 `1.42`
- 这一阶段几乎没有加速收益，因为最多没超过 `8 GPU`，通常只用了 `1~2 GPU`。
- 但成本效率很高：如果用一个大集群来做这一步，大约 `98%` 的资源会处于空闲状态。

##### 5. 阶段 2：横向扩展，快速探索搜索空间
- 流程确认可用后，代理进入探索阶段，开始搜索：
  - 模型大小
  - 学习率
  - 序列长度
  - 训练时长
- 它先并行启动了约 `40 个`独立的单 GPU 沙箱，每个对应一组不同超参数。
- 这轮大规模探索只用了 `36 分钟`实际时间。
- 随后又进行了：
  - `23 个`更聚焦的单 GPU 实验
  - `4 次`更大胆的进一步优化实验
- 整个探索阶段的数据：
  - 共 `68 项实验`
  - 累计约 `14 个 GPU 小时`
  - 全部使用单 GPU
  - BPB 逐步从 `1.40` 降到 `1.37`，再降到 `1.34`
- 这阶段总体平均加速不算夸张，但峰值加速很明显：
  - 约 `40 次运行`在 `40 分钟`内完成
  - 如果依赖工作站，可能要 `3 小时`
- 文章强调，这种差别意味着：你可以午饭后就拿到结果，而不是晚上再回来查看。

##### 6. 阶段 3：扩大规模，验证最优方案
- 到了半夜，代理已经找到了最有希望的架构，需要做全规模验证。
- 它把资源从单 GPU 改成 `8×H100`，所做的基础设施修改只有一处：
  - `gpu='H100'` 改成 `gpu='H100:8'`
- 然后代理同时跑了前 `5` 个最佳配置：
  - `5 × 8×H100`
  - 共 `40 个 GPU`并行运行
- 效果：
  - BPB 从 `1.34` 大幅降到 `1.14`
  - 核心实验在 `4 小时`内完成
  - 如果用单台工作站，可能需要 `20 小时`
- 文章认为，这正是弹性扩缩容的价值：关键验证阶段可以瞬间放大算力，而不是被固定资源拖慢。

##### 7. 阶段 4：再缩回小规模，集中调试瓶颈
- 后来代理遇到新问题：模型训练本身没问题，但为了满足 `16 MB` 限制而做的 GPTQ 量化步骤在 CPU 上执行，耗时超过 `45 分钟`。
- 由于挑战要求评估窗口只有 `10 分钟`，因此提交根本无法完成。
- 代理开始进入调试模式：
  - 先尝试简单方案：延长超时时间
  - 从 `45 分钟`一路加到 `60 分钟`、`90 分钟`，最后到 `2 小时`
- 这段调试成本很高：
  - 回到一次只跑 `1~2 个实验`
  - 花了 `5.5 小时`
  - 消耗超过 `60 个 GPU 小时`
  - 但每次仍然超时
- 最终代理改变思路，重写量化流程，让它在 GPU 上执行。
- 改完后，下一次实验总耗时缩短到 `52 分钟`，而且包含了训练和量化全过程。
- 这一阶段说明：研究过程并不是一直扩容，很多时候更需要低并发、可交互、适合排错的环境。

##### 8. 阶段 5：问题解决后，再次扩容完成优化
- 当完整流程修好后，代理重新进入优化冲刺阶段。
- 它先做了一轮验证：
  - `2 组并行`的 `8×H100` 实验
  - 验证修复没有影响模型质量
  - BPB 为 `1.1420`
- 随后它进一步扩展到：
  - `5 组并行`的 `8×H100` 实验
  - 每次使用 `40 个 GPU`
  - 分别测试不同架构、学习率调度、正则化和数据混合策略
- 优化结果持续改善：
  - `1.1230`
  - `1.1217`
  - `1.1206`
- 最后一轮使用 `4×8×H100`，结果变成 `1.1220`，反而略差。
- 代理据此判断“收益递减”，于是主动把资源缩到 `0` 并停止运行。
- 这里体现出两类优势：
  - 需要并行试错时，可以快速拉高吞吐量
  - 不需要时，可以立刻缩容，避免浪费

##### 9. 文章结论：未来研究基础设施应当是“按需变化”的
- 文章借这个案例说明：AI 研究不是固定流程，而是一种高度不确定、不断切换节奏的工作。
- 因此，基础设施不该要求研究者或代理提前选定一种模式并一直坚持，而应让系统根据任务阶段自动变化。
- 用更直白的话说：
  - 探索时，多开一些便宜的小实验
  - 验证时，瞬间拉满 GPU
  - 调试时，再缩回少量资源慢慢查问题
  - 完成后，马上释放所有资源
- 作者认为，这种“自动研究 + 自动扩缩容”的组合，才更适合未来 AI 代理主导的研究流程。

##### 10. 一个直观例子
- 可以把整个过程理解成“打车而不是买车队”：
  - 只需要出门一次时，没必要长期养很多车
  - 高峰时一下叫来很多车，低谷时又全部离开，才最划算
- Modal 在这里扮演的，就是让代理“随叫随到、用完即走”地使用 GPU，而不是提前买下一整支长期闲置的集群。
