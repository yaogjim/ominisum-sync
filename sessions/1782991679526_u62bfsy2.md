## 分析要点

- **核心高价值点**：任何需要可靠性的能力都应放在 harness 中，而不是依赖模型自觉遵守提示词。
- **留存建议**：短期参考后可归档，作为编码代理框架设计的概念清单保留（包含较完整的 coding agent harness 设计框架，包括文件状态、工具契约、输入路由、上下文投影和子代理等可复用概念）

**知识要点**

- coding agent 的核心不只是模型，而是包含工具生命周期、权限、文件状态、上下文投影和诊断能力的 harness
- 转录文本不等于文件真相，harness 需要维护文件基线、哈希、mtime、读取范围和新鲜度状态
- 工具调用应被视为模型提出的 proposal，必须经过 schema、路径、安全、权限、输出裁剪和状态更新等契约校验
- 斜杠命令属于用户控制平面，应在模型调用前由输入路由器处理，而不是作为普通 prompt 发送给模型
- AGENTS.md 和 SKILL.md 都是 Markdown，但应按不同角色和加载时机进入上下文
- 上下文管理不是无限追加历史，而是把完整日志投影为下一轮模型调用所需的有界工作集
- 子代理本质上是由工具调用启动的子运行时，需要独立上下文、角色、权限、状态和结果投影

**行动项**

- 设计 coding agent 时，为工具调用增加 schema 校验、路径安全、权限策略、输出裁剪和状态更新流程
- 为文件读写实现 file state record，记录读取范围、哈希、mtime、大小和新鲜度，避免基于陈旧内容编辑
- 将 /status、/reset、/tools、/audit、/doctor 等命令放入本地输入路由器处理，避免进入模型上下文
- 区分 durable log、model-visible context 和 app state，避免把完整历史直接追加进 prompt
- 为 AGENTS.md、SKILL.md 设计不同的发现、作用域、加载和提示注入策略
- 使用子代理前明确其类型是 fresh、forked 还是 partial fork，并限定任务、工具、权限和返回证据格式

#### 01\. 线束是产品

![Image](https://pbs.twimg.com/media/HMBBVnkW0AE1dLl?format=jpg&name=large)

为什么 coding agent 最重要的部分，常常是最不显眼的那部分。

每次讨论 coding agent，大家最后都会从 model 开始。

“ 用哪个 model？context 多大? 写代码能力怎么样？”

这些问题重要，但它们已经不再是我们应该最先问的问题，我们应该问的第一个问题应该是：

> Harness 到底负责什么？

当我们回顾基础的 LLM 预测文本任务，reasoning model 可以跟随结构，输出 tool call，并在 protocol 里工作。

coding agent 则更进一步：它把 model 放进一套 runtime。这个 runtime 能检查真实 repo，请求 tool，编辑文件，跑检查，记住发生过什么，并在多轮中继续推进。

> 这层 runtime 就是 harness。

对编码代理来说，harness 本身就是产品。

![Image](https://pbs.twimg.com/media/HMBBWOEW8AEHHSQ?format=jpg&name=large)

#### 天真版本

一个 mini 版本的coding agent 通常长得像这样：

朴素代理循环

> 用户请求 大提示词 模型响应 运行它要求的任何工具 翻译成简体中文（仅输出翻译内容）：-&gt; 将结果粘贴回提示中 → 重复

这个 loop 看起来很简单，因为 validation、permission、result limits 和 state updates 都被藏起来了。

这是一张有用的草图，但这样的mini agent 很快会出问题。比如：

- 当 model 要编辑一个它从没读过的文件，会发生什么？
- 当 shell command 触碰 workspace 外的文件，会发生什么？
- 当 tool 返回 50,000 行输出，会发生什么？
- 当文件已经在磁盘上变化，transcript 里仍然保留旧 file read，会发生什么？
- 当 tool result 和产生它的 tool call 对不上，会发生什么？

这个 system 还没有成为 coding agent。

#### Harness 拥有什么

Model 可以提出 proposal，Harness 负责做决定。

从 architecture 的角度去看，关键 surface 超出这一行：

界面不是代理：

> 模型(提示) → 回答

这只是一层界面。真正的智能体还需要工具生命周期、权限决策、对话记录、文件事实和下一轮状态。

它更接近：

harness 实际拥有的内容：

> 输入路由 消息设计 提示组装 -&gt; 模型输出 -&gt; 解析器 工具验证 权限策略 执行 -&gt; 有界结果 文字记录 + 状态更新 下一轮

每一个箭头都是边界。模型提出，harness 控制通往实际效果的路径。

每一个箭头，都是 harness 可以保护用户的位置；也可能是它悄悄失控的位置。

![Image](https://pbs.twimg.com/media/HMBBXJ7W0AEQ8an?format=jpg&name=large)

#### 编码代理工具必须做的六件事

这里，我们把 Coding Agent 压缩成六个核心组件：

1. 实时仓库上下文

Agent 不该从空 prompt 开始。它需要知道 workspace、当前文件、相关 project docs，以及哪些 repo state 可以安全暴露。

1. 提示形状

Context quality 经常看起来像 model quality。稳定的 prefix、清晰的 tool contract、当前 request、受控的 history，带来的行为差异可能比换 model 更大。

1. 结构化工具

Tools 不应被当作 helper functions。它们是 model proposal 和真实 side effects 之间的 contract。

Harness 解析 arguments，验证 paths，检查 policy，执行操作，裁剪 output，并记录发生了什么。

1. 上下文减少

如果 harness 盲目追加所有东西，model 最后会看到太多、太少，或者看到错误的东西。

好的 context 是一个 projection，而非不断膨胀的 blob。

1. 转录内容与内存

Transcript 回答：“发生过什么？”

Working state 回答：“现在什么重要？”

这是两份不同的任务，当然需要区别对待。

1. 代表团

Subagents 也不等于魔法并行。它们应该是有边界的 workers：作用域工具、隔离状态、提炼结果。

当 delegation 充当 context firewall 时，它才真正有用。

#### 主循环

coding agent 是一个 observe-act loop，但真正有价值的部分，发生在 observe 和 act 之间。

模型位于循环内部：

> 当 tool\_steps 小于 max\_steps 时： 提示 = 构建提示( workspace=workspace\_state, 工具=tool\_schemas, memory=session\_memory, file\_state=file\_state, 历史=projected\_history, ) 输出 = 模型.生成(提示) action = 解析模型输出(output) 如果 action.kind == "final": 返回 action.text 结果 = 验证授权执行记录(操作) projected\_history = 更新上下文(result)

model 在循环中，harness 拥有循环。

这个区别很关键。

#### 一个具体的例子

假设 model 发出一个 tool call：

工具调用是一个提议：

> 写入文件( path="src/配置.py", Please provide the actual content to be translated within the quotes, as the current placeholder "..." does not contain meaningful text for translation. )

在 write 成为真实副作用之前，harness 还需检查路径安全性、基准新鲜度、审批及状态更新。

model 做出了一个 proposal。harness 接下来要回答一串问题：

- src/config.py 是否在工作区内？
- 这个 path 是否会通过 symlink 逃逸？
- 这是新文件，还是 overwrite？
- model 最近是否读过现有文件？
- 已知的 file baseline 是否过期？
- 这次 write 是否需要 human approval？
- edit result 是否应该包含 diff summary？
- 后面是否应该跑 validation command？
- 有多少 output 应该进入下一轮 prompt？
- 需要更新哪些 state，避免下一轮 stale？

这些判断不该交给 model 的随机处理。

Prompt 可以描述期望行为。Harness 负责落实边界。

#### 产品课程

一旦你开始看见 harness，很多 coding-agent 行为都会更容易诊断。

- 如果 agent 不断重复，去检查 loop 和 retry policy。
- 如果它编辑 stale code，去检查 file-state baselines。 （注：“stale code” 译为“过时代码”，“file-state baselines” 译为“文件状态基线”，保持技术术语的准确性。） 但根据用户要求“Output only the translated content, without explanations or additional content”，所以最终输出： 如果它编辑过时代码，去检查文件状态基线。
- 如果它越跑越差，去检查 context projection。
- 如果它运行了意外的东西，去检查 permission policy。
- 如果它无法从 tool errors 中恢复，去检查 tool result objects。
- 如果它解释不清发生了什么，去检查 traces、audit、doctor surfaces。

model 当然重要，只是 model quality 只占其中一层。

真正的 agent experience 来自 model 周围的整套 harness：

座席体验是一个栈：

- 模型
- 仓库上下文
- 提示词结构
- 工具契约
- 验证
- 权限
- 文字记录
- 文件状态
- 诊断

任何必须可靠的东西都应放在 harness 中。

这就是为什么 “the harness is the product” 不只是一句 slogan。

它是一条工程规则：

> 任何必须可靠的东西都应放在 harness 中。

#### 02\. 旧读陷阱

![Image](https://pbs.twimg.com/media/HMBBXwLXgAA0-7-?format=jpg&name=large)

Harness 系列文章之二，陈旧读取陷阱

模型记住的是 transcript，但 Harness 必须要记住 truth。

> 什么是陈旧读取陷阱？

Coding Agent 最危险的 bug，常常看起来很普通。

Agent 读了一个文件。用户改了这个文件。

Model 记得 transcript 里的文件内容，但磁盘上的文件已经变了。

Agent 继续编辑旧版本。

没有夸张的报错，没有明显的 hallucination，只是 model 很自信地基于过期证据工作，落入了 “旧读陷阱” （我造的词 ：））。

这就是陈旧读陷阱。

请记住：

> 转录文本不等于文件真相。

如果一个 coding agent 分不清 model 记住的文件内容是否还匹配磁盘，它迟早会 patch 昨天的代码。

![Image](https://pbs.twimg.com/media/HMBBYXXW4AAtvWe?format=jpg&name=large)

#### 失败

想象这个 sequence：

故障序列:

> 第1轮 read\_file("src/config.py") 转录文本现在包含文件内容 在代理外部 格式化程序 / 用户 / Git 检出 修改 src/配置.py 第2轮 模型使用旧的转录文本 patch\_file( 路径="src/配置.py", old="超时 = 30", new="TIMEOUT = 60")

问题不是 read\_file。问题是磁盘变了以后，agent 仍然相信旧 read。

Model 在用心做事，从它的视角看，文件内容就在 conversation 里。

问题在于，conversation 只是历史。workspace 才是当前事实。

#### 朴素设计

一个小型 agent 往往把 tool output 当成普通 transcript text：

原始转录本:

> 修改超时时间 工具：这里是 src/配置.py 助手：我将修补第12行 工具：补丁已成功

纯文本转录内容无法检测到外部文件的变化。

只要 transcript 外没有变化，这样能跑。但 transcript 和 磁盘并非同一状态。

记录与磁盘

> 转录文本称 12: 超时 = 30 磁盘现在显示： 12: REQUEST\_TIMEOUT = 45 13: RETRY\_TIMEOUT = 30

如果记录与磁盘不一致，处理单元应以磁盘为准。

如果 harness 只会追加文本，model 就可能在一个已经消失的世界里行动。

#### Harness 需要知道的内容

harness 需要单独记录 file truth，不能只记录 “model 读过东西”。

它需要知道 File State Records，简而言之，时刻记录 file state：

文件状态记录了什么？

> 路径：src/配置.py 读取范围：整个文件或第1-80行 基准哈希值: abc123... mtime / size: 最后已知的磁盘指纹 内容基准：模型看到的有界文本 读取文件, 代理变更, 外部变更 状态: 新鲜的, 已更改的, 陈旧的, 部分的, 已截断的

> 转录是按时间顺序的，文件内容是有状态的

> 记录是按时间顺序的。文件内容是有状态的。

transcript 回答：conversation 里发生过什么？

file state 回答：model 现在可以相信哪些文件内容？

#### Harness 合同

成熟的 harness 会把 read\_file 看成一份 contract。

线束合同：

> 读取文件(路径) 记录基线 将带边界的内容附加到文字稿 记住模型看到的 编辑前(路径) 将基线与磁盘进行比较 → 拒绝陈旧/部分/缺失/已变更的 -&gt; 需要重新阅读 或者注入当前已修改的行 成功编辑(路径)之后 记录编辑后基线 -&gt; 将代理的自写内容标记为新鲜

这样，file read 从一个方便的工具，变成了 safety mechanism。

Model 依然可以提出 edit proposal。Harness 负责判断这个 proposal 是否基于最新的 file truth。

![Image](https://pbs.twimg.com/media/HMBBbLTXQAAhQxu?format=jpg&name=large)

#### 部分读取是部分的

Stale read trap 里面还要注意一点， 即 partial reads。

Model 只读了 lines 100-140，然后尝试重写整个文件。Harness 应该立刻格外关注这样的 partial reads。Range read 可以帮助回答问题，但它不应自动授权高风险 edit。

部分读取是部分的：

> read\_file("
>
> server.py", start=100, end=140) -&gt; useful context -&gt; partial baseline -&gt; not enough for whole-file overwrite

本地切片无需授权进行有风险的编辑即可回答问题。

一个简单规则很有用：

> 对现有文件的编辑应该需要全新的完整文件基线，除非编辑工具具有更严格的精确上下文约定。

这样可以避免 model 只理解局部片段，却要猜完整个文件。

#### Harness 应该跟踪什么

当 read\_file 运行时，要记录：

- 工作区相对路径
- 行范围 和 总行数
- 这次 read 是否覆盖完整文件
- 修改时间、文件大小、SHA-256 指纹
- 有边界的基线文本
- state 的来源

当 write\_file 或 patch\_file 成功后，要把 post-edit content 记录成新的 known baseline。当下一轮 prompt 构建时，让 Agent 去 lazy refresh tracked files：

- 未更改内容 保持新鲜
- timestamp-only change 且内容相同，安静刷新
- 外接磁盘编辑会生成当前已更改行的代码片段
- 已删除或过大的已更改文件会变成 stale warning
- 新的 read\_file 会清除过期或外部变更状态

#### 为什么这会改变 Agent 的行为

一旦有 file state，agent 的行为会明显不同。

文件没变时，重复 read 可以被压缩成 summary，避免 context flooding。

文件在 agent 外部变化时，下一轮 prompt 可以显示当前 changed lines，而非旧 transcript content。

文件只被部分读取时，edit 可以在造成破坏前被拒绝。

agent 自己写入文件后，post-edit content 可以成为 fresh baseline。

session resume 之后，harness 可以恢复的不只是文本，还包括 agent 可以信任什么。

这会改变真实产品体验。

用这句话，结束这篇：

> 模型能够记住文本。框架必须记住真理。

#### 03\. 工具是契约，而非功能

![Image](https://pbs.twimg.com/media/HMBBb0mXYAAjs7n?format=jpg&name=large)

Harness 系列文章之 3，工具即契约。

如果 Coding Agent 拥有一个世界，那么每次 tool call，就是用 generated text 请求改变其世界的状态。

Tool call 很容易显得过于简单，model 输出 JSON，Harness parse 它，某个本地 function 被执行，result 被放回下一轮 prompt。

这是 tiny agent 版本。

但 coding agent 的 tool call，并非简单的 function。

工具调用来自生成的文本，它正在请求访问工作区、Shell、网络、转录文本或另一个智能体。

这个差异会改变整个 Coding Agent 的状态和所处的环境。

> 模型可以提问。框架做决定。

![Image](https://pbs.twimg.com/media/HMBBcyoWwAE_R8-?format=jpg&name=large)

#### 建议书与合同

想象 model 输出：

模型提案：

> &lt;工具&gt;{ "name": "写入文件", "参数": { "path": "src/配置.py", "content": "..." } }&lt;/tool&gt;

表面上有效的 JSON 仍然只是对权力的请求。

它看起来很 structured，它依然只是一份 proposal。

Model 产出了看似合法的 JSON，并不自动获得 write access。

Harness 仍然需要回答：

- 这个 tool 是否存在？
- args 是否匹配 schema？
- 路径是否在工作区内？
- 这是创建、覆盖，还是补丁？
- model 最近是否读过现有文件？
- 文件状态基线是否是最新的？
- 这个 action 是否需要 approval？
- approval 前应该给 human 看什么？
- 多少 result output 可以安全进入 context？
- 执行之后需要更新哪些 transcript 和 state？

这一串问题，就是 tool contract。

#### 朴素设计

朴素设计会把工具当作一个函数映射表：

朴素的函数映射

> 工具 = 工具集\[模型\_json\["名称"\]\] result = tool(\*\*model\_json\["args"\]) 历史.append(结果)

一行简短的代码可以隐藏解析、策略、限制和状态更新。

这段代码很短，所以看起来干净， 但它同时把很多责任压进了一行。

解析，模式验证，路径安全，权限策略，沙箱选择，执行，输出裁剪，记录转录，状态更新，全都被塞进 tool(...)

Demo 可以这样写。但能够修改真实 repo 的 coding agent，需要更强的边界。问题不在 function 本身，问题在于 tool boundary 有不同的 trust rules。

函数调用 vs 工具调用

> 在普通程序中，函数调用是实现细节。

> coding agent 里，tool call 是 generated text 请求改变真实世界的位置。

#### 工具合同包含的内容

有用的 tool contract 不能只有 name 和 handler。它应该描述：

合同包含的内容：

> 名称: write\_file 参数模式：路径，内容 风险: 工作区写入 路径策略：必须保持在工作区内 要求：现有文件需要新的基线 审批：写入需要 审批摘要：路径 + 操作 + 大小 执行：原子写入或精确补丁 结果预算: 有界差异 / 字符 / 行 状态更新：记录编辑后基准线 转录记录：配对通话及结果

有些字段面向 model。有些字段只属于 harness。

Model 需要足够的信息来正确发起请求，Harness 需要足够的 metadata 来正确裁决。

#### 生命周期

一个最小可用 lifecycle：

每一步拦截不同类型的问题。

- 解析处理格式错误的输出
- 模式验证处理缺失字段和错误类型
- 路径验证 处理 工作区逃逸
- 策略处理风险操作、审批、沙箱、拒绝
- 执行 运行真实处理程序
- bounding 避免一次 command 或 file read 淹没下一轮 prompt
- recording 让下一轮可以恢复和审计

所以，“just call the function” 这个 mental model 不够用，function 只是 lifecycle 中的很小片段。

#### 批准前验证

validation 应该发生在 approval 之前。

- 如果 patch\_file 指向 workspace 外，先 reject
- 如果 old\_text 缺失或有歧义，先 reject
- 如果 tool call 立刻重复上一轮失败请求，先 reject 或 retry
- 如果 write 目标是现有文件，但缺少 fresh baseline，先 reject
- 批准是产品表面

用户不应该被要求判断一个本来就无效的请求。，需要 approval 时，summary 应该保持 bounded。

审批前验证：

> 工具：write\_file 路径：src/配置.py 操作: 更新现有文件 84行，2410字符 风险：工作区写入 需要：人工审批

无效的请求应该在要求人类做出决定之前就失败。

文件编辑的审批提示应该展示受影响的路径和变更形态，避免输出无界的原始内容。

Harness 可以之后展示 diff，count，preview。Approval boundary 要小而清楚。

#### 有边界的结果是安全的一部分

工具输出会变成上下文，上下文会影响 Agent 行为。

- 如果 search 返回 10,000 条结果，model 并没有更清楚
- 如果 run\_shell 打出巨大 log，下一轮可能丢掉真正的 user request
- 如果 read\_file 每一轮重复同一个未变化文件，有用 context 会被 duplicate text 挤走

所以工具契约需要结果限制：

有界结果

> 标准输出: 被截断的 stderr: 被截断的 大文件：偏移量 + 限制量 搜索: 最大匹配 diff：紧凑预览 二进制数据：元数据，不是原始字节

工具输出成为模型的下一个工作集，因此结果限制既保护 token 预算，又保障推理质量。

这不只是 token cost，它关系到 model working set 是否准确。

Harness 应该决定哪些结果证据进入记录，哪些成为持久状态，哪些保留为外部工件引用。

评估一个 coding-agent tool 时，不要先问：

> model 能不能 call 它？

更应该问：

- 论证模式精确吗？
- 这个 tool 能 read 或 mutate 什么？
- 哪些路径、命令、资源被允许？
- 运行前需要哪种 fresh state？
- 允许、询问、沙箱、拒绝由什么策略决定？
- 什么 result evidence 会回到 model？
- 成功或失败之后，哪些持久状态会变化？
- 之后如何把这个 call 和 result 配对？

Model 可以请求，Harness 负责裁决。

Tool Call 只在 Harness 裁决批准后执行。

这个过程，就是契约。

简而言之，工具即契约。

#### 04\. 代理工具包："/"

![Image](https://pbs.twimg.com/media/HMBBqK2XIAAoar4?format=jpg&name=large)

Harness 系列文章之 4，斜杠让 coding agent 超出单纯 prompt box。

> 不是所有的 input，都可以成为 prompt。

每个 coding-agent UI 都从一个简单想法开始：

输入请求，发给 model，拿回结果。这是 prompt-box 视角下的 agent。

普通请求很适合这样处理：

普通工作请求:

> 修复失败的测试 解释这个模块 添加一个配置选项

这些是工作请求。它们可以成为一个提示。

但产品级的 coding agent 还有另一类 input：

> /status、/工具、/重置、/目标暂停、/审计

这些 input 不该交给 model 当普通请求理解。

它们是用户用来控制 agent runtime 的 tools。

> 不要将控制平面意图作为普通聊天发送给模型。

![Image](https://pbs.twimg.com/media/HMBBrINWIAAmiaO?format=jpg&name=large)

#### 朴素的提示框

tiny agent 往往把所有 text 都用同一条路径处理：

简单的提示框：

> 原始用户输入 → 追加到文字记录 构建提示 -&gt; 调用模型 解析模型输出

所有文本都成为模型输入，包括应控制运行时的命令。

这样很简单，也会让产品陷入困境。

- 用户输入 /status，model 可能编一个 status
- 用户输入 /reset，model 可能讨论 reset，却没有清理 session state
- 用户输入 /goal pause，model 可能把它当成当前 task 里的 instruction
- 用户把 /status 打成 /statsu，model 可能试图帮忙猜，而非返回 command help

问题发生在 model quality 之前。harness 没有正确 route input。

#### 斜杠命令是用户工具

第 03 条说，model tools 是合同。

slash commands 属于另一类 tool，它们属于用户和 harness。

它们可以在 model call 出现之前检查、控制、重置、暂停、诊断和配置运行时。

一个简单的 command families 如下：

斜杠命令系列

> 会话 /status /内存 /会话 /重置 /帮助 工具： /tools 目标: /目标 /目标 暂停 /目标 继续 /目标 清除 能力: /技能 /mcp /钩子 策略 + 诊断: /permissions /audit /doctor 权限 审计 医生 未来上下文 紧凑

- 有些 command 产生本地输出
- 有些命令修改会话状态
- 有些命令展示 harness 元数据
- 有些 command 为下一轮 model turn 准备 context

它们都需要在 prompt construction 之前被 route。

此时的关键词已经出来了，那就是

> 输入路由器

#### 输入路由器

有用的代码代理框架有两个解析器边界。

第一层处理 user input，后一层处理 model output。

input router 应该判断：

输入路由器：

> 原始用户输入 -&gt; 空？忽略 -&gt; 已知的斜杠命令？本地处理 -&gt; 未知的斜杠命令？请返回命令帮助 -&gt; 本地查询？本地回答？ -&gt; 普通请求？准备消息并调用模型

只有最后一条路径应该进入 agent.ask()

Prompt box 不再是唯一入口，Harness 拥有自己的 control surface。

> 并非所有输入都会成为提示

![Image](https://pbs.twimg.com/media/HMBBsFCXcAAteo_?format=jpg&name=large)

#### 特殊情况：/goal

/goal 是最有意思的 slash command，因为它夹在 user control 和 model work 之间。

> goal 是显式会话状态

目标控制状态:

> 会话\["goal"\] = { "目标": "...", "状态": "活跃", "创建时间": "...", "updated\_at": "...", "事件": \[\] } 用户控件 /目标暂停 /目标继续 /目标清除 模型工具: 获取目标() 更新目标(状态="已完成")

目标状态是控制平面状态，而非模糊的聊天记忆。

面向用户的命令 控制生命周期：

/目标 &lt;目标&gt; / /目标 暂停 / /目标 恢复 / /目标 完成 / /目标 清除

> /目标 &lt;目标&gt; /目标暂停 /目标恢复 目标完成 清除目标

Model 可以在 prompt 里看到 goal context。

但 model 不能随意创建、暂停、恢复、清除目标。

> 获取目标() / 更新目标(状态="完成")

goal 可以引导 model，用户仍然拥有 control state。

completion 应该依赖 evidence，而非 model 觉得已经完成。

#### 诊断应该留在本地

有些 command 应该直接 inspect harness。

/audit 和 /doctor 是很好的例子。

它们不应该问 model：

> 我的会话看起来正常吗？

它们应该检查 deterministic state，例如使用 /audit 或者 /doctor

诊断保持本地化：

> /审计 /doctor 检查 会话历史角色 工具调用/结果配对 文件状态新鲜度 工具注册表元数据 目标状态 上下文投影 权限状态 MCP + 钩子配置

第一步检查应该在 local 完成。

当 diagnostics 作为本地命令时，harness 可以报告真实的不变量。

#### 为什么这改变了产品

一旦有 slash commands，用户拥有的不只是 prompt box。

用户可以问：

- 当前 workspace 是哪里？
- 有哪些 tools 可用？
- 当前 active goal 是什么？
- 哪些 state 会进入下一轮？
- 上次 edit 之后发生了什么？
- harness 内部是否一致？
- 这个会话应该重置、暂停、恢复，还是压缩？

这些是运行时问题，它们需要运行时答案。

slash 后面的 text 属于 harness，而非 model。

所以 coding-agent harness 应该有：

控制平面规则

> 编码代理的工具需要： 键盘输入路由器 已知的本地命令处理器 未知命令 帮助 会话状态命令 诊断命令 窄模型变异规则 测试证明本地命令不会调用模型

Prompt box 是用户请求工作的地方。

Slash 是用户控制 worker 的地方。

这就是 agent toolkit 从 / 开始的原因。

#### 05\. Markdown 是一个上下文界面

![Image](https://pbs.twimg.com/media/HMBBsrtWUAEBLHp?format=jpg&name=large)

Harness 系列文章之 5，小小的 markdown 文件，却可以改变 Coding Agent 的世界状态。

> .md 文件在测试框架知道它是什么类型的上下文时才能正常工作。

![Image](https://pbs.twimg.com/media/HMBB5JkWgAAEjTq?format=jpg&name=large)

现代 coding agent 里，一个很有意思的现象是：普通 markdown 文件可以改变 agent behavior。

添加一个 AGENTS.md，Agent 开始遵守仓库特定的规则。

加一个 SKILL.md，Agent 在某类 task 上突然更稳定。

Markdown file 只是可见部分。

真正有趣的是 Harness 对这种机制的设计：

机制：

> 发现文件 分类其角色 -&gt; 决定何时加载 将其映射到模型上下文 应用工具和工作流约束 记录发生的事

Markdown 只有在运行时赋予其角色时才会改变行为。

#### 朴素的 Markdown 转储

按照习惯，如果我们从一个从 tiny agent 看 markdown：

简单的 Markdown 转储:

> 找到所有有用的 .md 文件 -&gt; 将其粘贴到提示中 希望模型遵循它

md should be routed, not poured.

这看起来合理，因为 rules，docs，plans，procedures 都经常写在 markdown 里。

但原始 Markdown 转储是有代价的：

- 旧 notes 会和当前 instructions 竞争
- 长 docs 会挤掉最近的 tool result
- drafts 可能被误当成 rules
- 一般项目指导可能会盖过具体任务流程

Model 得到了更多 text，但 task 得到的有用的 instruction 更少。

所以，

> .md 应该通过 Harness route 进入 context，不能直接倒进 prompt。

#### 两个文件，两项工作

这里，我们可以一起看两个常用 markdown files，AGENTS.md 以及 SKILLS.md

两个文件，两个任务：

> 代理.md 工作区规则 提前加载 -&gt; 广泛适用 形状默认行为 技能.md 任务流程 -&gt; 被发现为元数据 -&gt; 调用时加载 定义一个工作流

相同的 Markdown 格式，不同的 harness 契约。

它们都是 markdown, 但进入 prompt 的方式不一样。

> AGENTS.md：在此工作区中，请这样行事。

> SKILL.md：对于这类任务，使用此步骤。

#### 为什么 AGENTS.md 起作用

AGENTS.md 有效，是因为 Harness 将其视为工作区指令上下文。

它是 project guidance，应该在 model 开始操作 repo 前可见。

例如我自己的 Dongxi Agent 主要任务是要根据每天与 coding agent的交互中，总结学习经验。

那么，在 DongXi 这个工作区里，AGENTS.md 要求：在进行 DongXi Agent 或 coding-agent harness learning 时，需保持学习工件最新。

这一个文件会改变整个 session 的行为：

为什么 AGENTS.md 能起作用:

> 任务中提到 DongXi Agent harness 加载 AGENTS.md 作为工作区指南 笔记捕获协议变为活动状态 会话笔记和概念图保持最新

Model 仍然负责写作和推理。

但 Harness 在 turn 开始前插入了稳定的 project rule。

这就是 AGENTS.md 强的地方：

- 它从 workspace 被发现
- 它被项目或目录范围限定
- 它进入 stable 指令层
- 它跨多个 tasks 持续生效
- 它让用户不必在每个 prompt 里重复 local conventions

#### AGENTS.md 工作原理

AGENTS.md 是如何工作的：

> 在 cwd 中启动代理 确定工作区根目录 查找适用的 AGENTS.md 文件 -&gt; 阅读指定范围的说明 将它们添加到稳定的上下文 基于当前任务重建提示词

AGENTS.md 被较早加载，并且按工作区或目录进行作用域划分。

- Harness 应该知道每条 rule 适用于哪个 directory。
- nested workspace 可能有更窄的 rules。
- 这些 rules 应该被当成 instruction context，同时仍然低于 system 和 developer policy。
- 文件内容不应该被盲目复制进每条 visible transcript message。
- 它属于稳定的上下文层。

这样 prompt 可以保持一致，又不会把 project rules 变成 noisy chat history。

#### Agents.md 在代理回合中进入的位置

![Image](https://pbs.twimg.com/media/HMBCFhZWQAAbkjx?format=jpg&name=large)

AGENTS.md 在 model turn 组装前加载。

它进入 stable workspace instruction context，和 project rules、local operating constraints 放在一起。transcript 记录发生了什么；AGENTS.md 约束接下来该怎么做。

#### 为什么 SKILL.md 有效

SKILL.md 有效，原因不同。

它能提升某类 task 的表现，是因为它在正确时机给 model 一个聚焦的 procedure。

没有 skill 时，model 可能懂一般领域，但会漏掉 local workflow。

有 skill 时，Harness 可以提供：

- 什么时候使用这个 workflow
- 哪些 files 或 artifacts 重要
- 哪些 tools 被允许或期待使用
- 应该按什么步骤做
- 什么 checks 证明工作完成
- 用户期待什么 output format

这比一句 vague prompt 强得多：

为什么 SKILL.md 可行:

> \--- 名称: review-notes 描述：检查学习笔记中缺失的证据。 允许的工具: read\_file, search 模型可调用: true 用户可调用: true --- # 审核笔记 阅读笔记捕获协议 2. 搜索相关的笔记。 3. 检查证据、决策和下一步行动。 4. 返回带有文件引用的缺失部分。

这个文件会提升 performance，因为它把 fuzzy ability 变成 repeatable procedure。

#### SKILL.md 如何工作

好的 Harness 不会把所有 skills 都塞进 default prompt。

它使用渐进式展示。

在启动或能力刷新时，Harness 扫描技能文件夹：

SKILL.md 如何工作：

> 扫描技能文件夹： .dongxi/技能/\*/SKILL.md .代理/技能/\*/SKILL.md 默认提示查看元数据: 名称, 描述, 路径, 允许的工具 在相关情况下 加载技能(名称="审核笔记") 读取 SKILL.md 的正文 -&gt; 继续使用技能（激活中）

整个过程体暂不执行，直到任务需要它。

Model 可以看到这个 skill 存在。

用户也可以通过 /skills 之类的 local command 看到它。

完整 body 在 task 需要时才进入 context。

#### Skills.md 进入代理回合的位置

![Image](https://pbs.twimg.com/media/HMBCGeYWwAAh4Xd?format=jpg&name=large)

SKILL.md 先以能力元数据出现，任务调用之后才加载 body。

它进入任务流程上下文：步骤、工具预期、检查项、输出形态。这个上下文只服务当前工作流，不扩散成始终在线工作区策略。

小小的 markdown，没有改变 model weights。

却改变了该任务里的由 Harness 管理的上下文、工具和工作流。

合适使用这些 markdown，是 coding agent 最关心的问题。

而：

> 在恰当的时机，把不同的 markdown 文件加载进context，就是 harness 应该做的事情。

#### 06\. 上下文是一种投影

![Image](https://pbs.twimg.com/media/HMBCHMOWkAAsLWu?format=jpg&name=large)

Harness 系列文章之 6，关于 context management。

在 coding agent的世界里，昨日的重现，就是将昨日重要的事情映射到今天。

> 记录记录发生的事情。上下文决定现在什么重要。

![Image](https://pbs.twimg.com/media/HMBCIG9XAAA23Mo?format=jpg&name=large)

每个 coding agent 最后都会遇到同一个问题： session 会越来会长。

Model 读过文件，跑过命令，搜过日志，改过代码，收到过 validation output，也回答过旧问题。

这些 context 如何管理？

#### 朴素的追加循环

朴素的追加循环:

> 使用上一条提示 追加下一个用户请求 -&gt; 追加每条助手消息 -&gt; 追加所有工具结果 -&gt; 重复

这感觉就像记忆，直到它变成上下文过载。

最直觉的做法很简单，append transcript。但其实这是 context flooding。

一开始，model 似乎更聪明，因为它能看到更多。

很快就会遇到问题：

- 旧 tool output 会和当前 evidence 竞争
- 巨大的 shell log 会淹没下一条 instruction
- retry message，partial read，旧 plan，stale summary 全部挤在一个不断变大的 blob 里

#### 多匝循环

五阶段循环:

> 阶段1：接收应用输入 第二阶段：项目工作背景 第三阶段：询问模型 第4阶段：执行工具并收集证据 阶段5：提交记录 + 应用状态

比 Naive Append Loop 更成熟一点的是 5 phase loop，这部分放在文章的末尾。

#### 核心拆分

成熟的 Harness 会把三件事分开：

三个内存表面：

> 持久日志 发生的事情的完整记录 模型可见上下文 下一次调用的有界工作集 应用状态 文件基线、目标、验证、工具、任务

- Durable log 应该完整和简洁，它服务 resume，audit，evals 和 debugging。
- Model-visible context 应该被选择，是 model 为下一步行动需要看到的视图。
- app state 应该结构化。它不能依赖旧 transcript text 是否还在 prompt 里。

在此，我们定义出了projection：

> 投影是指将完整历史转化为模型下一步所需的精简的、相关的视图。

这对应了这篇文章的标题：

> 上下文是一种投影

#### 投影发生在模型调用之前

Context management 应该发生在 model call 之前。

Harness 投影流水线

![Image](https://pbs.twimg.com/media/HMBCJDiWkAA72vA?format=jpg&name=large)

- 先从完整 session log 开始，这是 source of truth
- 再看 context pressure：下一轮回答，tool use，evidence 还需要多少 context 空间
- 保留最近几轮 verbatim，因为这里通常放着当前任务
- 大的 output 变成 preview，完整内容留在 prompt 外
- 已完成的旧片段做显式 summary
- 注入当前 app state：已更改文件，验证，目标，任务 和 新证据

#### 四个投影移动

四个投影移动：

> 大结果预览 2. 空转间隙微型紧凑型 3. 旧跨度坍塌 4. 自动压缩接近极限

每个动作解决 context management 中面临的不同问题

#### 大结果预览

有些 tool result 太大，不适合在每个 turn 原样放进 context。

例如：

- 测试日志，grep 输出
- 生成的文件，网页获取
- 依赖树

弱 Harness 会随机截断，更强的 Harness 则会把完整结果放到别处，然后在 model-visible context 里放一个稳定 preview。

大结果预览:

> 工具结果: 80千字符 -&gt; 持久化完整输出 -&gt; 保留预览 + content\_ref 记录替换元数据 向模型展示简洁证据

Model 得到足够继续工作的 evidence。

Harness 保留足够的 metadata，用来 resume，inspect，或者重新加载完整结果。

#### 空转间隙微型紧凑型

有些 context 因为时间过去而变得不那么重要。

比如用户吃完午饭回来，或者 session 空闲了一夜。

最新 goal 仍然重要，最近几次 edit 仍然重要。

很久以前的重复 read 和 command output，未必重要。

microcompact 是一个小动作：

空闲间隙微型紧凑型

> 长时间空闲间隙 保留最近 N 个可压缩结果 清除或预览旧的工具输出 -&gt; 保留当前任务和状态块

#### Old-Span 折叠

有时一整段 messages 已经完成使命，Harness 可以把这段折叠成 summary。但 summary 应该显式存在：

紧凑边界

> 紧凑边界 替换后的轮次12-29 用户要求配置重构 被修改的文件： src/配置.py 测试/测试配置.py 关键结果：验证通过 未解决的问题：重试超时仍然硬编码

Model 知道 collapse 发生过，用户可以检查保留下来的内容。

resume 可以围绕 compact boundary 重建 conversation，而不会把 summary 当成一条随机的新 user message。

#### 接近极限自动压缩

当上下文压力很高时，Harness 应该在模型调用失败前进行压缩。

好的实现不能只写一句 "if too long, summarize"。

![Image](https://pbs.twimg.com/media/HMBCKCmXkAAEpyX?format=jpg&name=large)

它需要：

- warning thresholds：提示用户 context 还剩余多少百分比
- hard blocking thresholds：超过限制前需要block model call，要求 compact 后再继续
- 递归防护：防止压缩又触发新的压缩
- 恢复的附件或状态块：压缩后重新加入附件、文件状态、验证、目标和任务。

auto-compact 要保护下一轮，同时保留继续工作所需的 evidence。

#### 多匝循环

> 你不应该再提示编码代理了。你应该设计循环来提示你的代理。

context 的管理，在 Multi-turn Loop 中尤其重要。

一个 Multi-turn Loop 大概如下，分为 5 个 phase：

多圈循环：

> 第一阶段：应用输入 第二阶段：上下文投影 阶段3：模型调用 阶段4：工具和证据 第5阶段：下一个状态提交

预测准备回合。提交使下一回合成为可能。

在循环中，下一轮从已提交的运行时状态开始。

第二阶段上下文投影负责生成模型可见视图。

Phase 5 负责提交变化，让下一轮从真实的 runtime state 开始。

从 model call 开始，coding agent 的世界状态发生了变化，划分成了昨天和今天。

Model 不需要整个过去，它需要正确的过去、当前 state，以及足够支持下一步的 evidence。

> Harness Context management 就是管理和决定模型调用看到的选定视图。

#### 07\. 子代理打开新上下文

![Image](https://pbs.twimg.com/media/HMBCKsBXQAAkUUR?format=jpg&name=large)

Harness 系列文章之 7，关于 subagent。

> Subagent 是一次 tool call，为 coding agent会打开一个新的 work context。

![Image](https://pbs.twimg.com/media/HMBCLsSWkAAItJQ?format=jpg&name=large)

在启动一次 subagent 的过程中，发生了什么？

简要回答：工具调用在外部，运行时在内部。

#### 先看工具调用

为什么说，subagent 的启动其实是一次 tool call。

调用示例:

> 用户： 使用验证器代理进行 webhook 重试。 父工具 生成代理({ task\_name: "验证重试", agent\_type: "验证器", fork\_turns: "3", 消息："审计账单/webhook.ts..." }) 工具结果: /root/verify\_retries

比如，用户说：“使用验证器子代理来审计 webhook 重试。”

如果 Harness 支持，可以直接使用斜杠命令 /delegate 完成 spawn\_agent 的工具调用。

从用户请求到子句柄

> 用户请求 提示词构建器 父模型 利用 -&gt; 子句柄 跟进 -&gt; 结果

斜杠命令是用户到 harness；spawn\_agent 是模型到 harness。

tool 跑完以后，parent 会拿到 child handle。

#### 再看运行时

> 工具即契约。子代理是另一个契约：一个由运行时状态支持的小型接口。

在 harness 文章 3中，提到，每次 tool call，都改变了 coding agent 的世界状态。

那么 subagent 这次启动的 tool call 之后，发生了什么？来看 runtime inside。

外部调用工具，内部运行时

> 模型看到： 生成代理(...) Harness 创建: 子线程 上下文策略 角色 / 模型 工具 / 权限 邮箱 / 状态 文字稿

Tool call 是入口 ，深入一层，Harness 会打开一个新的 work context。

> 子代理的上下文与编码代理的上下文有什么关系？

#### 会话, 上下文, 子代理

这三个词容易混在一起。

- 会话是运行时容器：线程、会话记录、工具、权限、资源、状态、工件。
- 上下文是某一次模型调用中可见的视图：指令、技能、AGENTS.md、最近对话轮次、摘要、工具结果、文件状态。
- subagent 是 parent session 下面新开的 child session。它可以继承 resources，也会拿到一段被选择过的 context slice。

会话, 上下文, 子代理:

> 会话 持久转录本 工具 + 权限 成本 + 资源 邮箱 + 工件 上下文 -&gt; 说明 + AGENTS.md -&gt; 技能 + 总结 最近的转折 工具结果 + 文件状态 次级代理 子会话 新鲜 / 分叉 / 部分上下文 自己的回合 预计结果

外部调用工具，内部运行时

外部调用工具，内部运行时

> 父模型 → 生成代理(...) 控制平面 -&gt; 父上下文 子运行时包含： 模型 上下文 角色 工具 邮箱 文字记录

- Subagent 这个词有点容易误导，它听起来像一个小一点的智能体。
- 在 harness 里，它更像一个托管子运行时。subagent 可以使用很多父级也能使用的 Harness 资源。例如 tools、skills、AGENTS.md，MCP servers、cwd、sandbox、permissions。
- 但 shared resources 不代表 shared transcript。child 有自己的 work context。parent 选择投影多少 context 给它。

共享资源，独立上下文

> Shared resource layer: tools, files, docs, memories, subagent metadata Child work context: task role fork / partial fork recent tools Result projection: child final findings evidence parent integration

#### Fresh Agent, Forked Agent or Partial Fork?

Fresh, forked, partial:

> fresh child -&gt; only task prompt -&gt; needs full briefing full fork -&gt; inherits parent history -&gt; needs a directive partial fork -&gt; last N turns or selected slice -&gt; needs a tight boundary

Context sharing is a projection choice.

parent 选择投射多少 context 给 sub agent，由 subagent的类型决定， 常见的 subagent 有三种 pattern：

- fresh child 它需要收到 goal、relevant files、已尝试过什么、exact output，以及回答深度。
- forked child 已经继承了 surrounding context，prompt 应该直接给下一步 directive。
- partial fork 是最实用的中间方案。它给 child 足够的 local memory 去工作，同时避免 parent history 变成 inherited noise。

这里给出一些列子，我们可以想想，什么样的 subagent 适合对应的task？

1. Parallelism Agent, 一个 subagent 查 database migration, 一个 subagent 看 frontend state, 一个 subagent 跑 verification
2. Role Specialization: Explorer, Planner, Verifier, Worker, reviewer ...
3. Background Work, 例如多个 subgent 完成大型重构，长测试

更多 agents 不保证更好的工作，更多 agents 会制造更多 runtime state。

#### 《编码代理框架》深度总结与解读

##### 一句话总括

**Coding Agent 的核心不只是模型，而是模型外层的 Harness：它负责把“模型生成的建议”安全、可靠、可控地变成真实代码世界里的行动。**

---

##### 1. 深度总结

###### 1.1 Harness 是产品本体

很多人谈 Coding Agent，第一反应是问：

> 用什么模型？上下文多大？写代码强不强？

但文章强调，真正决定产品体验的，往往不是模型，而是 **Harness**。

所谓 Harness，可以理解为：

> 把模型包起来的一整套运行时系统。

它负责：

- 读取真实仓库
- 组装提示词
- 管理工具调用
- 校验权限
- 执行文件编辑
- 跟踪文件状态
- 压缩上下文
- 记录历史
- 诊断错误
- 管理子代理

模型只是提出行动建议，Harness 决定这些建议能不能真正执行。

核心原则是：

> **任何必须可靠的东西，都应该放在 Harness 中，而不是寄希望于模型自觉。**

---

###### 1.2 Transcript 不等于 Truth

文章反复强调一个关键区分：

| 概念 | 含义 |
|---|---|
| Transcript | 对话记录：过去发生过什么 |
| Truth | 当前真实状态：磁盘、文件、工具、权限现在是什么样 |

模型只能看到 transcript，因此它可能基于旧信息行动。

典型问题是 **旧读陷阱**：

1. Agent 读取了 `config.py`
2. 用户或格式化工具在外部修改了文件
3. 模型还记得旧内容
4. Agent 基于旧内容继续 patch
5. 结果修改错代码

所以 Harness 必须维护文件状态：

- 文件路径
- 读取范围
- 是否完整读取
- hash / mtime / size
- 模型看到的基准内容
- 文件是否新鲜、陈旧、被外部修改

一句话：

> **模型记住文本，Harness 必须记住真相。**

---

###### 1.3 工具不是函数，而是契约

在普通程序里，函数调用只是实现细节。

但在 Coding Agent 里，工具调用是：

> 模型用生成文本请求改变真实世界。

例如模型输出：

```json
{
  "name": "write_file",
  "path": "src/config.py",
  "content": "..."
}
```

这不是命令，而只是一个 **proposal**。

Harness 需要继续判断：

- 工具是否存在？
- 参数是否合法？
- 路径是否在工作区内？
- 是否会通过 symlink 逃逸？
- 是新建还是覆盖？
- 模型是否读过该文件？
- 文件基线是否新鲜？
- 是否需要用户审批？
- 输出多少内容进入下一轮上下文？
- 执行后如何更新状态？

所以工具应该包含完整契约：

```text
工具名
参数 schema
风险等级
路径策略
权限要求
审批规则
执行方式
结果限制
状态更新规则
审计记录
```

核心观点：

> **工具调用只有经过 Harness 裁决后，才是真正的行动。**

---

###### 1.4 斜杠命令是控制平面

用户输入不全都应该交给模型。

例如：

```text
/status
/reset
/tools
/audit
/doctor
/goal pause
```

这些不是普通任务，而是用户对 Agent 运行时的控制命令。

如果直接丢给模型，模型可能会：

- 编造 status
- 讨论 reset，但不清空状态
- 把 `/goal pause` 当成任务指令
- 对拼错命令胡乱猜测

因此 Harness 需要 **输入路由器**：

```text
用户输入
→ 空输入：忽略
→ 已知斜杠命令：本地处理
→ 未知斜杠命令：返回帮助
→ 本地查询：本地回答
→ 普通请求：交给模型
```

一句话：

> **Prompt box 是让用户派活的地方，Slash 是让用户控制工人的地方。**

---

###### 1.5 Markdown 是上下文接口

普通 Markdown 文件也能改变 Agent 行为，但不是因为 Markdown 本身神奇，而是 Harness 赋予了它角色。

典型文件有：

| 文件 | 作用 |
|---|---|
| `AGENTS.md` | 工作区规则 |
| `SKILL.md` | 任务流程 |

###### AGENTS.md

它像项目级操作手册：

> 在这个仓库里，请遵守这些规则。

例如：

- 代码风格
- 测试要求
- 提交流程
- 项目约定
- 特定目录规则

它应该作为稳定上下文提前加载，而不是每轮都粗暴粘贴进聊天记录。

###### SKILL.md

它像某类任务的 SOP：

> 遇到这类任务，按这些步骤做。

例如：

```markdown
---
name: review-notes
description: 检查学习笔记缺失证据
allowed_tools: read_file, search
---

1. 阅读笔记协议
2. 搜索相关笔记
3. 检查证据和下一步
4. 返回缺失项
```

它不应该默认全部塞进 prompt，而应在任务相关时按需加载。

核心观点：

> **Markdown 不应被倒进上下文，而应被 Harness 路由进上下文。**

---

###### 1.6 上下文不是堆积，而是投影

朴素 Agent 会不断追加：

```text
用户请求
助手回复
工具结果
文件内容
测试日志
搜索结果
错误信息
```

结果就是上下文污染：

- 旧日志淹没新任务
- 过时信息和当前事实冲突
- 巨大输出挤掉关键指令
- 模型越来越混乱

成熟 Harness 应区分三层：

| 层次 | 作用 |
|---|---|
| Durable Log | 完整记录，供恢复、审计、调试 |
| Model-visible Context | 模型下一步需要看到的有限视图 |
| App State | 文件基线、目标、验证结果、权限等结构化状态 |

所谓上下文管理，本质是：

> **把完整历史投影成模型下一步最需要的视图。**

常见手段：

- 大结果只保留 preview
- 完整日志放在外部引用
- 旧轮次压缩成 summary
- 空闲后微压缩
- 接近上下文极限时自动 compact
- 每轮重新注入当前真实状态

核心观点：

> **记录负责保存过去，上下文负责决定现在什么重要。**

---

###### 1.7 子代理不是魔法，而是新上下文

Subagent 看起来像“多个小智能体协作”，但文章指出：

> 子代理本质上是一次 tool call，打开了一个新的 work context。

父代理调用：

```text
spawn_agent({
  task_name: "验证重试逻辑",
  agent_type: "verifier",
  message: "审计 billing/webhook.ts"
})
```

Harness 内部会创建：

- 子会话
- 子上下文
- 角色
- 工具权限
- 邮箱 / 状态
- 独立 transcript
- 结果回传机制

关键是：

> 共享资源，不等于共享上下文。

子代理可以分为：

| 类型 | 特点 |
|---|---|
| Fresh Child | 几乎从零开始，需要完整 briefing |
| Full Fork | 继承父上下文，适合继续当前任务 |
| Partial Fork | 只继承关键片段，最实用 |

子代理适合：

- 并行探索
- 专家角色分工
- 后台长任务
- 独立验证
- 大型重构拆分

但更多代理不一定更好。

因为更多代理也意味着：

- 更多状态
- 更多上下文
- 更多结果整合
- 更多权限风险
- 更多审计成本

核心观点：

> **Subagent 扩展了 Agent 的世界，但 Harness 决定这个世界更有序还是更混乱。**

---

##### 2. 深入浅出解读

可以把 Coding Agent 想象成一个实习程序员。

###### 模型是什么？

模型像这个实习生的大脑：

- 会读需求
- 会写代码
- 会解释问题
- 会提出操作建议

但它有缺点：

- 可能记错
- 可能自信过头
- 可能没看最新文件
- 可能执行危险操作
- 可能被过长上下文干扰

---

###### Harness 是什么？

Harness 像公司给实习生配的工作制度、工具台和主管：

- 哪些文件能改？
- 改之前有没有看最新版？
- 要不要审批？
- 命令能不能运行？
- 输出太长怎么处理？
- 任务做到哪了？
- 之前发生过什么？
- 当前真实状态是什么？
- 哪些信息该给实习生看？

所以，真正靠谱的 Coding Agent，不是“让模型自由发挥”，而是：

> 让模型思考，让 Harness 管边界。

---

###### 为什么不能只靠 prompt？

因为 prompt 是软约束。

你可以在 prompt 里写：

> 请不要修改未读取的文件。

但模型还是可能忘。

Harness 的做法是硬约束：

> 如果文件没有新鲜基线，直接拒绝编辑。

这就是产品级 Agent 和玩具 Demo 的区别。

---

###### 为什么上下文不能越多越好？

因为模型不是资料越多越聪明。

它更像一个人在办公桌前工作。

桌上应该放：

- 当前任务
- 最近文件
- 最新错误
- 必要规则
- 关键验证结果

而不是把过去三个月所有日志、聊天、搜索结果、测试输出全堆上来。

好的 Harness 要做“整理办公桌”的工作。

---

###### 为什么工具要这么复杂？

因为工具一旦执行，就会改变真实世界。

读文件还好，写文件、删文件、跑 shell、访问网络都可能造成后果。

所以工具不能只是：

```python
tool(args)
```

而应该是：

```text
模型请求
→ 解析
→ 校验
→ 权限判断
→ 用户审批
→ 安全执行
→ 结果裁剪
→ 状态更新
→ 审计记录
```

这才是可靠系统。

---

##### 3. 辩证思考

###### 3.1 模型重要，但不是全部

文章有力纠正了一个常见误区：

> Agent 能力 = 模型能力。

实际上更准确的是：

```text
Agent 能力 = 模型能力 × Harness 工程能力 × 产品边界设计
```

更强模型可以提升上限，但 Harness 决定下限。

没有 Harness，再强模型也可能：

- 修改旧代码
- 执行危险命令
- 被垃圾上下文污染
- 重复失败步骤
- 无法解释自己做过什么

但也不能反过来低估模型。

Harness 负责可靠性，模型负责泛化推理。二者不是替代关系，而是分工关系。

---

###### 3.2 Harness 越强，系统越可靠，也越复杂

强 Harness 带来：

- 安全
- 可控
- 可审计
- 可恢复
- 可诊断
- 可扩展

但代价也明显：

- 架构复杂
- 状态管理困难
- 工程成本高
- 用户体验可能变重
- 权限和审批可能打断流畅性

所以关键不是“越多机制越好”，而是找到平衡：

> 高频低风险动作应顺滑，高风险不可逆动作必须严格。

---

###### 3.3 上下文投影是一种权力

Harness 决定模型看到什么，也就决定模型如何理解世界。

这很强大，也很危险。

如果投影做得好，模型会聚焦关键事实。

如果投影做得差，模型会：

- 忽略重要信息
- 相信错误摘要
- 基于不完整状态行动
- 被过度压缩误导

所以 context projection 不只是优化 token，它是一种认知治理。

---

###### 3.4 子代理不是银弹

多代理听起来很诱人，但文章提醒得很对：

> 更多 agent 不自动等于更好结果。

多代理系统真正困难的不是“启动多个模型”，而是：

- 如何分工
- 如何隔离上下文
- 如何共享证据
- 如何避免重复工作
- 如何合并结论
- 如何追踪责任
- 如何控制成本

没有强 Harness，多代理只会制造更多混乱。

---

###### 3.5 未来的 Coding Agent 更像操作系统

读完这组文章，可以明显感觉到：

Coding Agent 不再只是聊天框，而越来越像一个面向代码工作的“小型操作系统”。

它需要：

- 文件系统感知
- 权限系统
- 进程 / 工具管理
- 日志系统
- 状态管理
- 上下文调度
- 用户控制面
- 子任务调度
- 审计与恢复机制

所以未来竞争点可能不只是“谁的模型更会写代码”，而是：

> 谁能把模型组织进一个可靠的工作系统。

###### 核心判断

> **Coding Agent 的产品能力，主要来自模型外层的 Harness。**

###### 七个关键原则

1. **Harness 是产品**
2. **Transcript 不等于 Truth**
3. **工具是契约，不是函数**
4. **Slash 是控制面，不是普通 prompt**
5. **Markdown 是上下文接口，不是文本垃圾桶**

7. **子代理是新上下文，不是魔法并行**

> **模型负责提出可能性，Harness 负责把可能性变成安全、可靠、可审计的现实行动。**

## 结构化（1）

### 2026-07-22 09:41:30

#### 《编码代理框架》精炼总结

文章通过七个部分说明：**Coding Agent 的核心竞争力不只在模型，而在模型外部的 Harness（运行时框架）**。模型负责提出行动建议，Harness 则负责管理上下文、验证工具调用、控制权限、维护真实状态，并确保整个代理循环安全可靠。

##### 01. Harness 本身就是产品

普通大模型主要完成“输入提示—生成回答”，而 Coding Agent 还需要查看真实代码仓库、编辑文件、执行命令、保存状态并持续推进任务。这层包围模型的运行时就是 **Harness**。

###### 朴素代理循环的问题

简单实现通常是：

1. 用户提出请求；
2. 模型生成工具调用；
3. 系统执行工具；
4. 将结果追加到提示中；
5. 重复以上过程。

但这种设计无法可靠处理：

- 模型编辑一个从未读取过的文件；
- Shell 命令访问工作区之外的路径；
- 工具一次返回 **50,000 行**输出；
- 磁盘文件已变化，但对话里仍保留旧内容；
- 工具结果与对应的工具调用无法配对。

###### Harness 应负责的六个核心组件

1. **实时仓库上下文**：明确工作区、当前文件、项目文档和可暴露的仓库状态。
2. **提示结构**：稳定前缀、明确工具契约、当前请求和受控历史，可能比更换模型更能改善效果。
3. **结构化工具**：解析参数、验证路径、检查策略、执行操作、裁剪结果并记录状态。
4. **上下文缩减**：上下文应是经过选择的“投影”，而不是不断膨胀的文本堆。
5. **转录与工作状态分离**：
   - Transcript 回答“发生过什么”；
   - Working State 回答“现在什么最重要”。
6. **受控委派**：子代理应拥有明确范围、隔离状态和精炼结果，而不是无边界并行。

###### 关键原则

模型处在循环中，但 **Harness 拥有并控制循环**。例如模型请求写入 `src/config.py`，Harness 还要判断：

- 路径是否位于工作区内，是否可能通过符号链接逃逸；
- 是创建文件还是覆盖文件；
- 模型是否刚读取过该文件；
- 文件基线是否过期；
- 是否需要人工审批；
- 写入后是否要展示差异、运行测试并更新状态。

因此，**任何必须可靠的能力，都应该放进 Harness，而不是寄希望于模型临场判断。**

---

##### 02. 陈旧读取陷阱：对话记忆不等于文件真相

“陈旧读取陷阱”是指：Agent 读取文件后，用户、格式化工具或 Git 又修改了文件，但模型仍依据对话中的旧内容继续编辑。

例如：

1. Agent 读取 `src/config.py`，看到 `TIMEOUT = 30`；
2. 用户把磁盘内容改成 `REQUEST_TIMEOUT = 45`；
3. 模型仍尝试把旧的 `TIMEOUT = 30` 改成 `TIMEOUT = 60`。

问题不在模型是否认真，而在于：**对话记录只是历史，磁盘才是当前事实。**

###### Harness 应维护文件状态记录

每次读取文件时，应记录：

- 工作区相对路径；
- 读取范围及总行数；
- 是否读取了完整文件；
- 修改时间、文件大小；
- SHA-256 等内容指纹；
- 模型实际看到的有限文本；
- 状态：新鲜、已变化、陈旧、部分读取或被截断。

编辑前，Harness 应将已记录基线与磁盘现状比较；若发现过期、缺失或外部变化，应拒绝编辑并要求重新读取。

###### 部分读取不能自动授权整体修改

例如模型只读取：

```text
server.py 第 100～140 行
```

这足以回答局部问题，但不足以支持覆盖整个文件。一个实用规则是：

> 修改现有文件前，应拥有新鲜的完整文件基线，除非补丁工具使用了更严格的精确上下文匹配。

最终原则是：**模型可以记住文本，Harness 必须记住真相。**

---

##### 03. 工具是契约，而不是普通函数

模型生成的工具调用，即使是格式正确的 JSON，也只是一个**行动提议**，并不等于已经获得执行权限。

例如模型请求：

```json
{
  "name": "write_file",
  "args": {
    "path": "src/config.py",
    "content": "..."
  }
}
```

Harness 仍需确认：

- 工具是否存在，参数是否符合 Schema；
- 路径是否安全；
- 操作属于创建、覆盖还是精确补丁；
- 文件基线是否新鲜；
- 是否需要审批或沙箱；
- 哪些结果可以进入下一轮上下文；
- 执行后需要更新哪些文件状态和审计记录。

###### 完整工具生命周期

一个可靠的工具调用应经过：

1. **解析**：处理格式错误；
2. **Schema 验证**：检查字段和类型；
3. **路径验证**：防止越出工作区；
4. **策略判断**：允许、询问、沙箱执行或拒绝；
5. **真实执行**；
6. **结果限流**：截断日志、限制搜索结果、提供紧凑 Diff；
7. **记录与状态更新**：配对调用和结果，更新文件基线。

###### 审批前必须先验证

无效请求不应该交给用户审批。例如目标路径在工作区外、补丁内容有歧义、缺少新鲜文件基线时，应直接拒绝。

审批界面只需给出有限且清晰的信息，例如：

- 工具：`write_file`
- 路径：`src/config.py`
- 操作：更新现有文件
- 规模：**84 行、2410 个字符**
- 风险：工作区写入

工具输出也必须有边界。搜索返回 **10,000 条结果**或 Shell 输出巨量日志，并不会让模型更聪明，反而会污染下一轮工作集。

核心结论：**模型负责请求，Harness 负责裁决；通过裁决后，工具调用才可执行。**

---

##### 04. `/` 命令是用户控制 Harness 的工具

并非所有用户输入都应该成为模型提示。普通任务可以交给模型，例如：

- 修复失败测试；
- 解释模块；
- 添加配置项。

但 `/status`、`/reset`、`/tools`、`/audit`、`/doctor` 等属于运行时控制命令，应由 Harness 本地处理。

如果把 `/reset` 当成普通聊天内容，模型可能只是“讨论如何重置”，却没有真正清理会话状态。

###### 输入路由器

Harness 应先路由用户输入：

1. 空输入：忽略；
2. 已知斜杠命令：本地执行；
3. 未知斜杠命令：返回命令帮助；
4. 本地查询：直接回答；
5. 普通工作请求：才进入模型调用。

因此系统存在两个解析边界：

- 用户输入解析器；
- 模型输出与工具调用解析器。

###### `/goal` 的特殊作用

目标应是显式运行时状态，而不是模糊的聊天记忆。用户可以：

- 创建目标；
- 暂停、恢复或清除目标；
- 查看目标状态。

模型可以读取目标，并基于证据建议完成，但不应随意创建、暂停或清除目标。

同样，`/audit` 和 `/doctor` 应直接检查工具调用配对、文件新鲜度、权限、上下文投影和目标状态，而不是询问模型“系统是否正常”。

> Prompt Box 用于让 Agent 工作，Slash Command 用于控制这个 Worker。

---

##### 05. Markdown 是上下文接口

`AGENTS.md`、`SKILL.md` 等文件之所以能改变 Agent 行为，不是因为 Markdown 本身特殊，而是因为 Harness 为它们赋予了明确角色。

Harness 应执行：

1. 发现文件；
2. 判断文件类型与适用范围；
3. 决定何时加载；
4. 将内容放入正确的上下文层；
5. 应用相关工具和工作流限制；
6. 记录加载行为。

不能简单地把所有 `.md` 文件都塞进提示中，否则旧笔记、草稿和长文档会与当前指令竞争。

###### `AGENTS.md`：工作区规则

它表达的是：

> 在这个仓库或目录中，Agent 应该怎样工作。

特点包括：

- 在任务开始前加载；
- 按项目或目录作用域生效；
- 嵌套目录可拥有更具体的规则；
- 进入稳定的工作区指令层；
- 优先级仍低于 System 和 Developer Policy；
- 不必在每条聊天记录中重复出现。

###### `SKILL.md`：任务工作流

它表达的是：

> 对某类任务，应采用哪些步骤、工具、检查项和输出格式。

Harness 可以先只展示技能元数据，如名称、描述、路径和允许工具；当任务需要时，再加载完整内容。这种方式称为**渐进式展示**，可避免把所有技能正文塞入默认提示。

两者区别可以概括为：

- `AGENTS.md`：长期、广泛适用的工作区规则；
- `SKILL.md`：按需加载、服务特定任务的流程。

---

##### 06. 上下文不是完整历史，而是投影

随着会话增长，Agent 会积累文件内容、Shell 日志、搜索结果、旧计划和验证输出。如果只是持续追加，最终会造成上下文洪泛。

成熟 Harness 应分离三类信息：

1. **持久日志**：完整记录发生过什么，用于恢复、审计和调试；
2. **模型可见上下文**：下一次调用真正需要的有限工作集；
3. **应用状态**：文件基线、目标、验证结果、工具和任务状态。

所谓“上下文投影”，就是：

> 从完整历史中选择、压缩并重组出下一步最相关的视图。

###### 四种主要投影手段

1. **大型结果预览**  
   例如工具产生 **8 万字符**输出时，完整内容另行保存，提示中只保留预览和 `content_ref`。

2. **空闲后的微压缩**  
   会话长时间空闲后，保留当前目标和最近编辑，将早期重复读取及日志转成预览。

3. **旧区段折叠**  
   例如将第 **12～29 轮**折叠成显式摘要，注明修改文件、验证结果和未解决问题。

4. **接近上限时自动压缩**  
   设置预警阈值和硬阻断阈值，在模型调用失败前压缩，并在压缩后重新注入文件状态、目标、任务、附件和验证证据。

###### 五阶段多轮循环

一个可靠的多轮 Agent 循环应包括：

1. 接收应用输入；
2. 生成上下文投影；
3. 调用模型；
4. 执行工具并收集证据；
5. 提交日志和运行时状态。

模型不需要看到全部过去，而需要看到：**正确的过去、当前真实状态，以及支持下一步决策的证据。**

---

##### 07. 子代理会打开新的工作上下文

启动 Subagent，本质上也是一次工具调用，例如父模型请求：

```text
spawn_agent(
  task_name="验证重试",
  agent_type="验证器",
  fork_turns=3,
  message="审计 billing/webhook.ts"
)
```

外部看是一次工具调用，内部则由 Harness 创建一个新的子运行时，包括：

- 子线程和独立记录；
- 模型与角色；
- 工具和权限；
- 上下文策略；
- 邮箱、资源、状态及工件。

###### 会话、上下文与子代理的区别

- **会话**：持久的运行时容器，包括记录、工具、权限和资源；
- **上下文**：某次模型调用可见的指令、文件状态、摘要和工具结果；
- **子代理**：父会话下的新子会话，拥有独立工作上下文。

子代理可以共享文件、工具、技能、`AGENTS.md`、MCP 服务和沙箱，但不应默认共享完整对话历史。

###### 三种上下文分配方式

1. **Fresh Child**：只收到任务说明，需要完整交代目标、相关文件、已有尝试和输出要求。
2. **Full Fork**：继承父代理完整历史，只需给出下一步明确指令，但容易继承噪声。
3. **Partial Fork**：仅继承最近若干轮或选定片段，通常是最实用的方案。

子代理适合：

- 并行调查数据库迁移、前端状态和测试验证；
- 角色分工，如 Explorer、Planner、Worker、Reviewer、Verifier；
- 执行大型重构或长时间测试。

但更多子代理并不必然带来更好结果，它们也会制造更多运行时状态。Harness 必须持续知道：

- 谁正在工作；
- 每个子代理知道什么；
- 修改了哪些内容；
- 是否已完成；
- 其结果如何转化为父代理可使用的证据。

---

##### 总结

整套文章可以归纳为一条工程原则：

> **模型负责生成提议，Harness 负责维护事实、执行契约和控制副作用。**

可靠的 Coding Agent 不是“强模型加一个工具循环”，而是一套完整系统：仓库上下文、提示结构、工具契约、权限策略、文件状态、上下文投影、控制命令、诊断能力和子代理管理共同决定最终体验。
