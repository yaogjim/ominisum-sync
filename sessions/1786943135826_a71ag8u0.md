- **核心高价值点**：根据交互方向选择传输方式：双向低延迟场景用WebSocket，单向服务端推送用SSE，普通请求响应则优先采用HTTP。

**知识要点**

- HTML over WebSockets将渲染和主要状态放在服务端，客户端JavaScript主要负责通信、事件监听和DOM更新。
- WebSocket适合聊天、协作和游戏等高频双向交互；SSE适合通知、实时信息流和AI流式输出等单向推送。
- 持久连接和服务端会话状态会增加资源占用、水平扩展、重连与故障恢复方面的设计成本。

**行动项**

- 在实时功能设计阶段，先按请求响应、单向推送和双向交互三类需求选择HTTP、SSE或WebSocket。
- 采用WebSocket方案时，提前验证并发连接容量、状态共享、断线重连和故障恢复机制。
- 需要搜索引擎收录时，将关键内容放入首次服务端响应，不依赖后续WebSocket更新。

## 正文

Building a SPA (Single-page Application) is a complex puzzle: a JavaScript framework that draws the view, an API serving JSON, and 2 independent codebases forced to understand each other through contracts. It is an accepted, professionalized scenario. But being a standard does not make it the only way. I want to show you another approach, one that is not new but has gained traction over the years: **HTML over WebSockets**.

The idea is this: instead of sending JSON and assembling the HTML in the browser, the server sends the HTML already built and the client just places it where it belongs. All the rendering logic stays in the Back-End, in a single language, with no need for contracts or an API. This pattern is known as **hypermedia** or **HTML over the wire**. What matters about how the HTML travels is that it determines the **latency** and the **bidirectionality** of the communication. There are three variants:

- Over **HTTP**, request by request, like [htmx](https://htmx.org/) or [Unicorn](https://django-unicorn.com/).
- Over **SSE**, opening a one-way, continuous channel from server to client, like [Datastar](https://data-star.dev/).
- Over **WebSockets**, a permanent, bidirectional channel, like [Phoenix LiveView](https://hexdocs.pm/phoenix_live_view/Phoenix.LiveView.html) or [Django LiveView](https://django-liveview.andros.dev/).

The channel is so important that it determines the application's architecture and its communication pattern.

In this article I am going to talk about **HTML over WebSockets**: the **real-time and bidirectional** variant of the family. The one that lets you build a SPA with barely any JavaScript, in a single language, with no contracts and a single rendering engine. We will see what it is, how it works and when it pays off compared to its HTTP or SSE cousins.

#### Origin

**Chris McCord**, creator of Phoenix (the most popular framework in the Elixir ecosystem), presented at **ElixirConf 2019** a technology called [LiveView](https://hexdocs.pm/phoenix_live_view/Phoenix.LiveView.html). In just [15 minutes he built a Twitter clone that worked in real time](https://www.youtube.com/watch?v=MZvmYaFkNJI) **without adding any rendering JavaScript** or a popular framework (React, Angular, Vue...) to manage the View, proving that you could stay in the Back-End and be productive with a sweet hint of good performance. Since then the solution has grown popular, **inspiring other developers** to build HTML-over-WebSockets implementations in **other languages**. You can go back to the Back-End without giving up the good parts of the Front-End.

#### How does it work?

Even though it might not seem so at first, JavaScript is used on the client. Its job is not to render but to create a communication channel with WebSockets and place the received HTML in the right spot. Plus other secondary tasks like animations, event handling, etc.

McCord's solution is **not to send the Front-End a JSON, but HTML** that needs no preprocessing. That way we move the rendering load, and all its logic, to the Back-End. OK but... how do we get the server to send us new content immediately and without making a request? Easy: with WebSockets.

Let's review the **traditional** system from the introduction. From the web I make an HTTP request, the browser starts the action and gets a JSON with all the raw information in response. The next step is to interpret it and build the corresponding HTML.

With **HTML over WebSockets**, that same request travels over a permanent channel and the response is already assembled HTML, with no JSON in between. And since the channel never closes, the server can even **get ahead** and send changes without the client asking.

#### What are its advantages?

- There is only **one rendering engine**, cutting down complexity.
- You do not need to **build an API**: the server generates HTML and sends it to the client, with no middleman.
- **State lives on the server.** It is not memoryless request-response: there is a process per connected client that remembers where it is. It is the opposite of htmx, which is deliberately *stateless*.
- **Direct connection to the database**, with no JSON or GraphQL middleman.
- **Real real-time**: clients receive changes as fast as possible, without polling the server.
- **Broadcast**: the server can push changes to every connected client at once. Building a chat, a dashboard or a multiplayer game comes for free.
- Less traffic and less latency per action: a single persistent connection avoids repeating the TCP handshake and the HTTP headers on every interaction. It is not that "the WebSocket protocol is magically faster" (HTTP/2 and HTTP/3 have narrowed that gap a lot in request-response), it is that **you skip the round trip and send assembled HTML**.
- Build a **SPA with barely any JavaScript**, without heavy frameworks like React, Angular or Vue.
- Reasonable **SEO**: since the HTML is rendered on the server, the first load is indexable. Careful though, a crawler does not see the updates that arrive later over the WebSocket, so the important content must be in that first response.
- **Safer against injection**: since the server renders and escapes the HTML before sending it over the channel, an attempt to sneak in a `<script>` travels as inert text and reaches your neighbor's screen as plain letters, not as code. The same architecture that makes a chat trivial makes it immune to XSS.

#### What are its drawbacks?

- The server needs **more resources**: it keeps a WebSocket open and, usually, **each client's state in memory**. Scaling horizontally forces you to share that state (in Django, with **Channels + an ASGI server + Redis** as the channel layer). That said, the real problem only shows up with a large number of simultaneous clients, and careful design can mitigate it. My site has handled peaks of 600 simultaneous readers without trouble, running on hardware similar to a Raspberry Pi 3 with other services running alongside.
- **Latency**: with a lot of physical latency, the "instant" feel suffers.
- **It does not work offline**. If the connection drops, the site stops working. You have to design the reconnection experience and fault tolerance.
- **The initial learning curve is steeper** than dropping in a `<script>`: running a WebSocket server is not trivial, and you have to learn to handle the LiveView pattern.

#### SSE, the cheap option

WebSockets is powerful, but keeping a bidirectional channel open per client has a cost. And often you do not need it: if the flow is mostly **server to client** (notifications, a live feed, a dashboard, the tokens of an AI response), **Server-Sent Events (SSE)** are enough. It is the same idea, sending ready-made HTML over the wire, but over a plain HTTP channel that only goes one way.

It is the cheap option: the simplest infrastructure. By not keeping a stateful process per client, it is easier to load-balance and scale.

However, it has limitations:

- **It is one-way.** Only the server pushes. If the client wants to send something, there is no channel for it: it has to make a separate HTTP request.
- **Text only.** It carries UTF-8, no binary (WebSocket does).
- **Worse for heavy bidirectional work.** In a chat, collaborative editing or a game, that loose back-and-forth over HTTP weighs more than an always-open WebSocket.

htmx has an almost identical implementation in spirit with its [SSE extension](https://htmx.org/extensions/sse/). You declare the channel with an attribute and the HTML that arrives in each event places itself:

Under the hood it uses the browser's own `EventSource`, with reconnection included, and the server sends HTML fragments over `text/event-stream`. The same philosophy as this article, just changing the transport. Along the same lines is [Datastar](https://data-star.dev/), which unifies Alpine-style reactivity over SSE.

The quick rule: if you need **bidirectional**, low-latency communication (chat, collaboration, games), WebSocket; if you only **push from the server**, SSE is simpler and cheaper to operate.

#### Final notes

HTML over WebSockets is not the answer to everything, and none of these technologies is. The transport is dictated by your problem: if you need real-time back-and-forth (a chat, a live panel, something collaborative), WebSockets; if you only push from the server, SSE; if request-and-response is enough, htmx over HTTP.

Every project is its own world, with its own quirks and limits. If you take away one thing, let it be the idea underneath: send HTML instead of JSON, stay in a single language and cross the API, the contracts and half the Front-End off your list.

Trust a good architecture, not trendy frameworks or patterns.

## 结构化（1）

### 2026-08-17 05:17:46

#### HTML over WebSockets：用极少 JavaScript 构建实时 SPA

**文章主旨：**与其让浏览器接收 JSON 后再用 JavaScript 生成页面，不如由服务器直接渲染 HTML，并通过 WebSocket 持续发送给客户端。这样可以用单一后端语言、单一渲染引擎构建实时 SPA，减少 API、前后端契约和客户端状态管理。

##### 1. 核心思路：传 HTML，而不是 JSON

传统 SPA 通常包含三部分：

- JavaScript 框架负责渲染页面；
- 后端 API 返回 JSON；
- 前后端维护两套代码，并依赖接口契约保持一致。

HTML over the wire 则把渲染逻辑集中到服务器：服务器生成完整 HTML，浏览器只负责把它放到正确位置。根据传输方式，可分为：

| 传输方式 | 特点 | 代表方案 |
|---|---|---|
| HTTP | 一次请求、一次响应 | htmx、Unicorn |
| SSE | 服务器到客户端的单向持续推送 | Datastar |
| WebSocket | 永久、双向、实时通信 | Phoenix LiveView、Django LiveView |

文章重点讨论 **HTML over WebSockets**：适合需要低延迟、双向实时交互的应用。

##### 2. 起源：Phoenix LiveView

2019 年 ElixirConf 上，Phoenix 作者 Chris McCord 展示了 LiveView，并在 **15 分钟内构建了一个实时 Twitter 克隆**。

这个案例证明：即使不使用 React、Angular、Vue 等前端框架，也能主要依靠后端完成具有实时体验的应用。此后，LiveView 模式被 Ruby、Python、C#、PHP 等生态借鉴。

##### 3. 工作原理

###### 传统 SPA 流程

1. 浏览器发送 HTTP 请求，例如 `GET /api/article/2/`；
2. 服务器查询数据库；
3. 服务器生成并返回 JSON；
4. 浏览器解析 JSON；
5. JavaScript 渲染引擎生成 HTML。

###### HTML over WebSockets 流程

1. 浏览器建立 WebSocket 连接并完成认证；
2. 浏览器通过通道发送“我要 `/article/2/`”；
3. 服务器查询数据库；
4. 服务器用模板引擎直接生成 HTML；
5. 服务器返回 `&lt;article>...&lt;/article>` 等页面片段；
6. 浏览器将 HTML 放入对应位置。

WebSocket 连接不会在每次交互后关闭，因此服务器也能在客户端没有主动请求时直接推送更新，例如新聊天消息、仪表盘数据或多人游戏状态。

客户端仍然会使用少量 JavaScript，但职责主要是：

- 建立和维护 WebSocket；
- 接收并插入 HTML；
- 监听事件；
- 处理动画、重连等辅助任务。

真正的页面渲染和大部分状态逻辑都留在后端。

##### 4. 主要优势

- **只有一个渲染引擎**：避免服务端与客户端各维护一套渲染逻辑。
- **不必构建 JSON API**：服务器直接连接数据库并返回 HTML，减少 API、GraphQL 和接口契约。
- **状态集中在服务器**：通常每个客户端对应一个有状态进程，可以记住用户当前所处的位置和页面状态；这与刻意保持无状态的 htmx 不同。
- **真正实时**：无需轮询，服务器可以立即向客户端推送变化。
- **天然支持广播**：可同时通知所有在线用户，适合聊天、实时仪表盘和多人游戏。
- **减少重复通信开销**：持久连接避免每次交互都重复发送 HTTP 头和重新握手。作者强调，WebSocket 并非“协议本身神奇地更快”，HTTP/2 和 HTTP/3 已缩小差距；其优势主要来自持久连接、减少往返以及直接发送成品 HTML。
- **极少依赖 JavaScript**：无需 React、Angular、Vue 等大型前端框架，也能构建 SPA。
- **具备基本 SEO 能力**：首次响应由服务器生成，因此可被搜索引擎索引；但后续经 WebSocket 推送的内容通常不会被爬虫看到，重要内容应放在首屏响应中。
- **降低 XSS 注入风险**：服务器统一转义用户输入后再生成 HTML，例如恶意 `&lt;script>` 会作为普通文本显示，而不是代码执行。

##### 5. 局限与成本

- **服务器资源消耗更高**：需要为每个客户端保持 WebSocket，通常还要在内存中保存会话状态。
- **横向扩展更复杂**：多服务器部署时必须共享连接和状态。例如 Django 常需搭配 Channels、ASGI 服务器及 Redis channel layer。
- **大规模并发才会明显暴露压力**：作者的网站曾在接近 **Raspberry Pi 3 性能的硬件**上，与其他服务共同运行，并顺利承受 **600 名同时在线读者**。
- **受网络物理延迟影响**：用户距离服务器较远时，“即时”体验会下降。
- **无法离线工作**：连接断开后应用基本停止，需要专门设计自动重连和故障恢复。
- **学习和运维门槛较高**：运行 WebSocket 服务、管理客户端状态和理解 LiveView 模式，比简单引入一个 `&lt;script>` 更复杂。

##### 6. 现有框架生态

HTML over the wire 已覆盖多数主流语言，既有 WebSocket 实现，也有 HTTP、SSE 方案：

| 语言/生态 | 框架 | 传输方式 | 特点 |
|---|---|---|---|
| Elixir | Phoenix LiveView | WebSocket | 最成熟的代表；LiveView 1.0 于 **2024 年 12 月**发布 |
| Ruby | Hotwire（Turbo + Stimulus） | HTTP + WebSocket/SSE | Turbo 8 支持 DOM morphing |
| Ruby | Live / Lively | WebSocket | 纯 WebSocket、小众方案 |
| Python / Django | Django LiveView、Reactor、djust | WebSocket | 多个活跃实现；djust 使用 Rust VDOM |
| Python / Django | django-unicorn | HTTP/AJAX | 无服务器主动推送 |
| Python / Django | Tetra | AJAX + WebSocket | 基于 Alpine.js，仍较年轻 |
| C# / .NET | Blazor Interactive Server | SignalR/WebSocket | .NET 9 的服务端交互模式 |
| PHP / Laravel | Livewire 3 + Reverb | WebSocket | Reverb 是 Laravel 于 **2024 年**推出的官方 WebSocket 服务器 |
| 通用 JavaScript | htmx | HTTP，另有 WS/SSE 扩展 | 默认偏无状态 |
| 通用 JavaScript | Datastar | SSE | 以较简单、低成本的单向推送为重点 |

##### 7. WebSocket 与 SSE 如何选择

SSE 同样可以传输服务器生成的 HTML，但只提供从服务器到客户端的单向通道。

###### SSE 的优点

- 基于普通 HTTP，基础设施更简单；
- 通常不需要为每个客户端维护复杂的有状态进程；
- 更容易负载均衡和横向扩展；
- 浏览器原生 `EventSource` 支持自动重连。

###### SSE 的限制

- **只能服务器主动推送**；客户端发送数据时仍要另发 HTTP 请求；
- **只能传输 UTF-8 文本**，不能像 WebSocket 那样传输二进制数据；
- 不适合频繁双向通信，例如聊天、协作编辑和多人游戏。

###### 快速判断

- **频繁双向、低延迟交互**：选择 WebSocket，如聊天、协同编辑、游戏。
- **主要由服务器单向推送**：选择 SSE，如通知、实时动态、监控面板、AI 流式输出。
- **普通请求—响应即可**：选择 HTTP，例如 htmx。

##### 8. 结论

HTML over WebSockets 并非适合所有项目，但它提供了一种更简单的 SPA 架构：**由服务器生成 HTML，客户端只负责接收和更新 DOM**，从而减少 API、前后端契约和大量 JavaScript。

最终应根据通信模式选择技术，而不是追逐流行框架：双向实时用 WebSocket，单向推送用 SSE，普通交互用 HTTP。核心原则是让架构服务于实际问题。

## 口播总结（1）

### 2026-09-17 00:26:27

构建单页应用，也就是 SPA，通常意味着两套系统同时存在。浏览器端用 React、Vue 或 Angular 负责渲染，服务器端提供 JSON 数据，两边再通过接口和数据契约保持一致。但这并不是唯一选择。另一条路线是：服务器直接生成 HTML，通过 WebSocket 发给浏览器，浏览器只负责把内容放到正确位置。

这种模式叫作“HTML over the wire”，也就是通过网络传输已经生成好的 HTML。它最吸引人的地方，是把界面渲染逻辑集中到后端。开发者可以主要使用一种语言、一套模板系统和一个状态模型，不再需要单独维护一套 JSON 接口，以及前后端之间的大量数据约定。

传统 SPA 的一次交互，大致要经过这样的过程。浏览器先发出 HTTP 请求。服务器查询数据库，再返回 JSON。浏览器解析 JSON，调用前端渲染引擎，最后生成页面内容。

换成 HTML over WebSockets，流程就不同了。浏览器打开 WebSocket，完成连接和身份验证。之后，这条双向通道会一直保持。用户需要某篇文章时，浏览器只要发出一个简单的请求。服务器查询数据库，用模板引擎生成 HTML，再把完整的页面片段发回来。浏览器端的少量 JavaScript，只负责接收内容、插入页面和监听事件。

所以，这种方案并不是完全不用 JavaScript。JavaScript 仍然要建立连接、处理事件，有时还要负责动画。关键区别在于，它不再承担主要的业务状态和界面渲染。

WebSocket 的另一项价值，是服务器不必等待浏览器询问。只要数据变化，服务器就能主动推送更新。聊天消息、实时仪表盘、协同编辑和多人游戏，都很适合这种通信方式。

这条思路真正受到关注，一个重要节点是二零一九年的 ElixirConf。Phoenix 框架的创建者克里斯·麦科德，用 LiveView 在大约十五分钟内做出了一个实时运行的推特克隆。整个演示没有引入 React、Angular 或 Vue，也没有额外编写前端渲染代码。它证明了一件事：开发者可以把大部分工作留在后端，同时获得接近现代前端应用的实时体验。后来，不少语言和框架都实现了类似模式，例如 Elixir 的 Phoenix LiveView、微软的 Blazor Interactive Server，以及 Django 和 Laravel 生态中的相关方案。

这种架构首先减少了系统复杂度。界面只由服务器上的一套渲染引擎生成，不需要让前后端分别解释同一份业务规则。服务器还能直接使用数据库结果生成页面，中间不必再经过 JSON 或 GraphQL。

应用状态也可以保存在服务器端。服务器通常会为每个在线客户端维护相应状态，知道用户当前处于哪个页面、正在操作什么。相比每次请求都像第一次见面一样重新建立上下文，这种方式更适合连续、实时的交互。

性能优势需要准确理解。WebSocket 并不是天生具有某种神奇速度。现代的 HTTP 二点零和 HTTP 三点零，已经大幅缩小了协议本身的差距。WebSocket 的主要优势，是连接长期保持，不必在每次操作时重复发送完整的 HTTP 头信息，而且服务器可以主动推送，不用等待下一轮请求。这样往往能减少每次交互的额外开销和等待时间。

服务器渲染 HTML 也对搜索引擎比较友好。首次加载时返回的内容可以被索引。不过，搜索引擎爬虫通常看不到之后通过 WebSocket 推送的更新。因此，真正重要的内容仍然应该出现在第一次响应里。

安全方面，如果服务器正确进行了转义，用户输入的脚本会以普通文字显示，而不是作为代码执行。这能降低跨站脚本注入，也就是 XSS 的风险。但安全仍然取决于服务端模板和转义机制是否使用正确，不能仅凭架构就掉以轻心。

代价同样明显。服务器要为每个用户保持一个连接，往往还要在内存里保存状态。在线人数增加以后，横向扩容会更复杂。多个服务器之间可能需要借助 Redis 一类系统共享消息和状态。

不过，这个问题通常在大量用户同时在线时才会变得突出。作者自己的站点曾在类似树莓派三代的硬件上，同时服务大约六百名读者，而且机器上还运行着其他服务。这说明资源成本确实存在，但并不意味着所有项目一开始就需要庞大的基础设施。

网络条件也很重要。如果用户距离服务器很远，物理延迟仍会破坏“即时响应”的感觉。WebSocket 应用还不能天然离线工作。连接中断时，应用往往会失去主要功能，因此必须认真设计自动重连、故障提示和状态恢复。与此同时，部署 WebSocket 服务器，以及理解服务端状态模型，也有一定学习成本。

更重要的是，并非所有实时页面都需要 WebSocket。传输方式应该由交互模式决定。

如果信息主要从服务器流向浏览器，比如通知、实时新闻、监控面板，或者人工智能逐字生成的回答，那么服务器发送事件，也就是 SSE，通常更简单。SSE 建立的是单向持续连接。服务器可以不断推送文本和 HTML，浏览器还原生支持自动重连。它更容易进行负载均衡，运行成本也往往更低。

但 SSE 只能由服务器主动发送。浏览器要上传数据，仍然要另外发起 HTTP 请求。它也只支持文本，不像 WebSocket 那样可以直接传输二进制内容。因此，聊天、协同编辑和游戏这类频繁双向通信，通常更适合 WebSocket。

如果应用根本不需要持续推送，只是用户操作一次、服务器响应一次，那么普通 HTTP 已经足够。像 htmx 这样的工具，也能让服务器直接返回 HTML，同时保持相对简单、无状态的请求响应结构。

真正值得记住的，不是某个流行框架，而是架构背后的选择：浏览器未必一定要接收 JSON，再自己组装界面。服务器也可以直接发送 HTML，把渲染、状态和业务逻辑集中在一处。

需要低延迟的双向通信，就考虑 WebSocket。只需要服务器持续推送，就考虑 SSE。普通请求响应已经够用，就继续使用 HTTP。先看问题需要什么，再决定传输方式，而不是反过来追逐技术潮流。

## 深度解读（1）

### 2026-09-17 00:35:00

#### HTML over WebSocket：不是“消灭前端”，而是重新划分复杂度

这篇文章最值得保留的，不是“用 WebSocket 做 SPA”这一技术技巧，而是一个更普遍的架构判断：**如果服务端是界面的唯一数据源，浏览器也只是最终展示端，那么把 JSON 发给浏览器再重建 HTML，可能是一层没有必要的中间抽象。**

Phoenix LiveView 等方案选择让服务端直接生成 HTML 片段，经持久连接发送给浏览器；客户端只负责事件采集、DOM 更新和少量交互。这样，权限、状态、业务规则与渲染逻辑可以留在同一处，避免后端数据模型、API Schema、前端状态和组件视图长期漂移。其真正收益不是“少写 JavaScript”本身，而是**减少需要跨团队、跨语言同步的业务语义**。

##### 先判断交互形态，再决定传输协议

文章给出的 HTTP、SSE、WebSocket 三分法很实用，因为它把选型从框架偏好还原成了交互需求：

- 普通表单、后台管理和低频操作，用 HTTP 请求—响应即可；
- 通知、实时看板、信息流更新，以及 AI 的流式输出，通常只有服务端持续推送，SSE 更简单，也自带浏览器重连机制；
- 聊天、协同编辑、多人游戏等需要高频双向通信，WebSocket 才真正体现价值。

关键变量不是“是否实时”，而是**消息是否双向、频率多高、断线后如何恢复、客户端是否需要独立工作**。例如 AI 对话看似交互频繁，但单次生成过程主要是服务端向客户端推送 token，SSE 往往已经足够；只有加入实时协作、语音流或持续控制信号后，WebSocket 的收益才可能覆盖运维成本。

##### 它消除的是显式 API，却没有消除契约

文章声称这种模式“无需契约、无需管理客户端状态”，需要保留分寸。契约并没有消失，只是从 JSON Schema 转成了 DOM 定位规则、事件名称、组件生命周期和重连协议。输入框焦点、乐观更新、上传进度、浏览器历史以及断线期间的操作，仍然是客户端状态，只是框架替开发者隐藏了一部分。

复杂度也被转移到了服务端：每个连接可能对应一份会话状态，水平扩容需要共享消息或状态，部署和故障恢复必须处理连接迁移。文章用类似树莓派的硬件承载 600 个并发读者，只能说明轻负载场景可行，不能回答每个连接消耗多少内存、广播是否频繁、渲染开销多大等关键问题。

性能与安全优势同样不是自动获得的。HTML 可能比 JSON 更大，持久连接也没有消除一次交互所需的网络往返；服务端模板默认转义能降低 XSS 风险，但只要存在不安全 HTML、URL、属性或客户端脚本入口，就不能称为“免疫”。

##### 最适合的是“服务端拥有界面”的产品

这类架构尤其适合内部工具、运营后台、实时仪表盘、客服系统和协作型垂直应用：客户端主要是浏览器，SEO只依赖首屏，团队希望快速交付完整业务流程。相反，如果产品需要离线运行、复杂本地交互、移动端与第三方共同消费 API，或者前端本身就是高度独立的产品层，HTML over the wire 反而会限制边界。

因此，它不是 React 的普遍替代品，而是一种值得重新纳入选型的默认候选：**先确认是否真的需要独立客户端和通用数据 API；如果不需要，就不要仅因行业惯例而维护两套渲染逻辑。**

## 默认总结（1）

### 2026-09-18 01:15:37

##### 一句话看懂

文章介绍“通过 WebSocket 传 HTML”：由服务器生成页面片段并实时推送给浏览器，以较少 JavaScript 构建 SPA；它适合双向实时应用，但并非所有项目都值得采用。

##### 关键内容

- 浏览器仍需少量 JavaScript，用于维持 WebSocket、发送事件和插入 HTML；渲染与状态主要留在后端，因此可减少前后端两套渲染逻辑、JSON API 和数据契约。
- 长连接允许服务器主动推送更新，适合聊天、协作、游戏和实时面板。优势并非 WebSocket“天然更快”，而是连接持续存在，并省去部分重复请求流程。
- 代价是服务器要维护连接及客户端状态，横向扩容更复杂；高延迟或断网会明显影响体验，也需处理重连。
- 选型原则：需要低延迟双向通信用 WebSocket；只需服务器推送用更简单的 SSE；普通请求响应用 HTTP/htmx 即可。

##### 通俗解读

这不是“完全不用 JavaScript”，而是让前端少负责业务渲染。SEO也只对首次返回的 HTML 较友好，后续推送内容未必被爬虫看到。

**是否值得细读：**如果你在做实时应用或想简化前后端分工，值得；若只是普通内容站，掌握文末选型原则即可。
