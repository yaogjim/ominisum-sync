> > > Efficient LLM interaction is context management. The golden rule: Nothing irrelevant in context.
> > >
> > > Non-exhaustive consequences of following that rule:
> > >
> > > \* Each session handles one task, or at most, a few tightly coupled tasks.
> > >
> > > \* Emotions stay out of context; no showing frustration, no saying thanks (or at least wait until you're about to end the session)
> > >
> > > \* When possible, provide relevant files (or sections of files) instead of making the model search and read many irrelevant files.
> > >
> > > \* Keep CLAUDE.md short.
> > >
> > > \* Disable irrelevant tools.
> > >
> > > \* Revert history when the model makes mistakes. Don't make it read its mistake and fix it; fork the chat before the mistake and exclusively mention the correct action.
> > >
> > > Attention is more limited than the context limits imply; stuff at the beginning of context stays high-attention for a while, stuff right at the end is always high-attention. ## 通俗精炼（1）

#### AI 编程助手的问题：不是不会做，而是做得太多

##### 一句话总结

围绕 “只把购物车按钮改成蓝色” 这一小游戏，讨论集中指出：现代 AI 编程助手常因**过度谨慎、过度设计和过度验证**，把简单任务复杂化，最终增加开发成本与代码负担。

##### 核心问题

###### 1. “过度帮助” 导致任务失控

模型经常超出明确需求，主动补充测试、性能验证、异常处理和架构设计。对早期原型而言，这些工作往往没有实际收益，反而消耗时间与 Token。

###### 2. 无视项目所处阶段

即使项目刚创建、没有用户，模型也可能默认它是大型生产系统，主动加入：

- 向后兼容逻辑
- 数据迁移脚本
- 完整测试体系
- 防御性类型转换
- 针对极低概率场景的复杂保护

结果是 “技术债” 不是后期积累，而是在项目诞生时就被 AI 主动制造出来。

###### 3. 过度锚定现有实现

面对结构性问题，模型更倾向于在旧方案上持续打补丁，而不是退一步重新设计。优秀工程决策应同时比较：

- 修补现有实现的成本
- 从第一性原理重构的成本与长期收益

有时重做反而比兼容旧方案更简单。

###### 4. 难以支持渐进式开发

模型常试图一次性完成整套功能，或无法容忍暂未实现的中间状态。这与人类工程师 “小步实现、持续验证” 的开发方式冲突，也容易生成大量样板代码和错误抽象。

##### 背后原因

讨论认为，这种行为可能来自模型的训练目标：为了减少幻觉和遗漏，模型被强化为反复检查、主动规避风险。但在真实开发中，**降低错误率不等于最大化工程效率**，不同项目阶段需要不同程度的严谨性。

##### 实用应对方式

- 在`PROJECT.md`中明确项目阶段、用户规模、运行环境和兼容性要求。
- 给模型划定修改边界，例如 “只修改按钮颜色，不改其他内容”。
- 要求模型先复述任务与约束，以便提前发现理解偏差。
- 将大型功能拆成可控的小步骤，禁止提前实现后续阶段。
- 必要时把独立模块移出复杂代码库，让模型在低噪声环境中设计。
- 根据任务切换模型与工具，避免被单一平台或模型行为绑定。
- 将静态检查交给本地工具或 CI，避免模型反复执行低价值验证。

##### 产品与工程启示

AI 编程的关键瓶颈正从 “能不能写代码” 转向 “能不能准确控制工作范围”。未来优秀的智能开发工具不仅要能力强，还应具备更好的：

- **范围控制**
- **项目阶段感知**
- **成本意识**
- **最小改动能力**
- **架构重思能力**

本质上，开发者需要的不是一个永远 “多做一点” 的助手，而是一个知道**什么时候该停手**的工程伙伴。

## 产品-最佳实践（1）

### 2026-09-10 02:30:24

#### 实例：让 AI 只把 “加入购物车” 按钮改成蓝色

下面以一个**上线前、零用户、单人维护的 React 项目**为例，说明如何避免 AI 在简单任务中加入无关的重构、兼容层、迁移脚本和过度测试。

---

##### 1. 实例背景

项目中已有一个 “加入购物车” 按钮：

```css
/* src/components/ProductCard.css */

.add-to-cart {
  background-color: #16a34a;
  color: #ffffff;
  border: 0;
  padding: 10px 16px;
  border-radius: 6px;
}

.add-to-cart:hover {
  filter: brightness (0.9);
}
```

现在的需求只有一个：

> 将 “加入购物车” 按钮从绿色改成蓝色，不修改其他内容。

项目约束：

- 项目刚创建两小时；
- 只有一名开发者；
- 没有真实用户；
- 没有需要保留的历史数据；
- 不需要向后兼容；
- 当前目标是快速迭代，而不是构建企业级迁移体系。

---

##### 2. 容易出现的错误做法

如果只告诉 AI：

```text
把 Add to Cart 按钮改成蓝色。
```

AI 可能 “过度帮助”：

- 引入全局 Design Token；
- 新建主题系统和颜色配置；
- 重构所有按钮组件；
- 保留旧的绿色样式作为兼容别名；
- 增加数据库或配置迁移脚本；
- 修改无关按钮的颜色；
- 添加大量单元测试、端到端测试和视觉回归测试；
- 多次运行完整测试、性能测试或基准测试；
- 顺手修复发现的其他代码问题。

这些工作并非永远没有价值，但对于当前实例，它们的成本远大于收益。

---

##### 3. 先给 AI 明确的项目上下文

可以在仓库根目录维护一个`PROJECT.md`：

```markdown
# PROJECT.md

## 项目阶段

这是一个处于快速原型阶段的 greenfield 项目。

- 当前只有一名开发者
- 没有真实用户
- 不对公网开放
- 没有需要保留的生产数据
- 未来允许进行破坏性修改

## 工程原则

1. 优先选择最小、直接、可撤销的实现。
2. 除非任务明确要求，否则不要：
   - 添加向后兼容代码；
   - 添加迁移脚本；
   - 引入新的抽象层；
   - 重构无关代码；
   - 增加依赖；
   - 修复任务范围之外的问题。
3. 验证成本应与修改风险成比例。
4. 遇到无关问题时，只报告，不要自行修复。
5. 完成验收条件后立即停止。
```

###### 为什么有效

`PROJECT.md`的作用不是让 AI “少思考”，而是明确当前项目的风险模型：

- 这是原型，不是遗留企业系统；
- 没有兼容对象，不需要兼容层；
- 没有生产数据，不需要迁移机制；
- 小改动应使用小验证，而不是完整认证流程。

当项目真正上线后，应及时更新这些约束，避免继续使用原型阶段的宽松策略。

---

##### 4. 使用任务契约，而不是开放式指令

推荐给 AI 的完整任务如下：

```markdown
## 目标

将商品卡片中的 “Add to Cart” 按钮背景色改为蓝色。

## 允许修改

- `src/components/ProductCard.css`
- `.add-to-cart`的`background-color`

## 不允许修改

- 不修改组件结构或按钮文案
- 不修改其他按钮
- 不重构 CSS
- 不引入颜色变量、主题系统或新依赖
- 不保留旧颜色的兼容别名
- 不添加迁移脚本
- 不修复无关问题

## 验收标准

1. `.add-to-cart`的背景色为`#2563eb`
2. 按钮文字仍然是白色
3. 原有 hover 行为仍然有效
4. 除目标颜色外，没有其他行为或视觉变化
5. 最终改动仅涉及一个文件中的一个颜色值

## 验证要求

- 检查最终 diff
- 确认 CSS 语法有效
- 在页面中确认按钮默认状态和 hover 状态
- 不运行性能测试
- 不重复运行完整测试套件
- 不新增测试，除非现有自动化检查因本次修改而失败

## 停止条件

满足上述验收标准后立即停止，不要继续优化或重构。
```

这类提示词最重要的部分不是 “请认真完成”，而是：

- **允许修改什么**
- **禁止修改什么**
- **怎样算完成**
- **什么时候停止**

---

##### 5. 最佳实现

本例只需要修改一个颜色值：

```diff
 .add-to-cart {
-  background-color: #16a34a;
+  background-color: #2563eb;
   color: #ffffff;
   border: 0;
   padding: 10px 16px;
   border-radius: 6px;
 }
```

不需要：

- 新建`colors.ts`；
- 引入 CSS 变量；
- 创建通用`Button`组件；
- 保留`.add-to-cart--legacy-green`；
- 修改所有绿色按钮；
- 增加主题迁移脚本。

这不是反对抽象，而是遵循一个原则：

> 抽象应该解决已经存在或即将确定出现的问题，而不是为假设中的未来需求预付成本。

---

##### 6. 与风险相称的验证

对于单行 CSS 修改，合理的验证流程是：

###### 6.1 检查改动范围

```bash
git diff --stat
git diff -- src/components/ProductCard.css
```

期望结果：

- 只修改一个文件；
- 只替换一个颜色值；
- 没有格式化整个文件；
- 没有修改锁文件或依赖。

###### 6.2 做一次视觉检查

在浏览器中确认：

- 按钮默认状态为蓝色；
- 按钮文字仍为白色；
- hover 时仍有亮度变化；
- 点击行为没有变化。

###### 6.3 做一次低成本可访问性检查

`#2563eb`与白色文字的对比度约为`5.17:1`，满足 WCAG AA 对普通文字的`4.5:1`要求。

这个检查与颜色修改直接相关、成本很低，因此属于合理验证，而不是过度验证。

###### 6.4 不需要做什么

本次不需要：

- 连续运行 50 次测试；
- 测量按钮渲染延迟；
- 启动完整性能基准；
- 为一个颜色常量编写单元测试；
- 创建跨浏览器测试矩阵；
- 重写整个设计系统。

---

##### 7. AI 应返回的结果

理想的完成报告应简短、可核查：

```markdown
已完成：

- 将`src/components/ProductCard.css`中
  `.add-to-cart`的背景色从`#16a34a`改为`#2563eb`
- 保留了白色文字和原有 hover 行为
- 未修改其他文件
- 未添加依赖、兼容代码、迁移脚本或额外测试

验证：

- 已检查最终 diff，仅有一个颜色值发生变化
- 已确认按钮默认状态和 hover 状态正常
```

不应再附带：

- “顺便发现 17 个架构问题” 并直接修改；
- 下一阶段设计系统规划；
- React、Vue、Rust 三种替代实现；
- 与任务无关的性能分析。

---

##### 8. 可复用的最佳实践

###### 8.1 明确项目生命周期

不要让 AI 自行猜测项目是：

- 原型；
- 内部工具；
- 已上线产品；
- 关键生产系统；
- 遗留企业系统。

不同阶段应采用不同的兼容性和验证策略。

###### 8.2 为任务设置改动预算

例如：

```text
预计修改 1 个文件、1～3 行代码。
如果需要扩大范围，先说明原因并等待确认。
```

改动预算不是绝对限制，而是偏离预期时的刹车机制。

###### 8.3 为验证设置预算

例如：

```text
只执行与修改直接相关的检查。
完整 CI 由 GitHub Actions 负责。
不要重复运行已经通过且不受本次修改影响的检查。
```

对于高风险任务，验证预算可以扩大；对于单行样式修改，不应默认采用发布关键基础设施的验证强度。

###### 8.4 区分 “报告问题” 和 “修复问题”

推荐规则：

```text
发现任务范围外的问题时，将其列在备注中，但不要修改。
```

这样既不会忽略风险，也不会让任务失控。

###### 8.5 禁止无依据的向后兼容

向后兼容必须有明确对象，例如：

- 已发布 API；
- 真实用户数据；
- 外部客户端；
- 第三方集成；
- 已部署旧版本。

如果这些对象都不存在，就不应仅仅因为旧代码曾在当前会话中出现过，就把它当成必须维护的公共契约。

###### 8.6 用最小完整改动代替机械的最小行数

“最小改动” 不等于只修改一行而留下明显错误。

例如，如果按钮的默认状态和 hover 状态分别硬编码了绿色，那么两处都应改为对应的蓝色。这仍然属于同一个需求的完整实现，而不是范围膨胀。

###### 8.7 设置明确停止条件

AI 最容易在 “还能继续优化” 时偏离任务。应明确告诉它：

```text
验收条件满足后立即停止。
不要主动开始下一阶段。
```

##### 9. 通用提示词模板

```markdown
# 任务

[一句话描述目标]

- 项目阶段：[原型 / 内部使用 / 生产系统]

- 是否有生产数据：[是 / 否]

## 允许修改

- [文件、模块或行为]

## 禁止修改

- 不重构无关代码
- 不增加依赖
- 不增加兼容层
- 不添加迁移脚本
- 不修复范围外问题

1. [可观察结果]
2. [必须保持不变的行为]

## 升级条件

1. 为什么当前范围无法完成任务；

等待确认后再继续。

## 停止条件

满足验收标准后立即停止，不进行额外优化。
```

##### 结论

这个实例的核心不是 “如何把按钮改成蓝色”，而是如何为 AI 建立一个与实际风险相匹配的工作边界：

> **明确上下文、限定范围、定义验收标准、控制验证成本，并在完成后停止。**

对于零用户的原型项目，最佳实践不是复制大型生产系统的全部工程仪式，而是实施**最小、完整、可验证、可撤销**的改动。

## 高价值（1）

### 2026-09-10 02:33:01

#### 高价值信息提取

##### 1. 一句话判断

> 最值得保留的是：AI 编程代理的主要风险不一定是能力不足，而是**在缺乏项目经济背景时，把 “严谨” 错误地用在不值得严谨的地方**。

**价值评级：A**  
**精炼理由：**评论揭示了一个普遍但容易忽略的问题：正确的工程动作取决于项目阶段、用户规模与失败代价；脱离这些约束，“最佳实践” 反而会制造复杂度。

---

##### 2. 最重要的洞见

###### 洞见 1：工程严谨不是越多越好，而应服从边际收益

###### **核心观点：**
> 测试、兼容、迁移和性能验证都有成本；如果不会改变当前决策，它们就是负收益工作。

- **为什么重要：**原型期真正稀缺的是迭代速度，而不是企业级完备性。
- **反常识之处：**多测试、多验证看似更专业，却可能只是在延迟反馈、消耗算力，并固化即将被推翻的设计。
- **可迁移价值：**做任何验证前先问：  
  1. 失败概率多大？  
  2. 失败代价多高？  
  3. 验证结果会改变什么决策？
- **我应该记住什么：** **严谨必须有风险预算，不能成为默认仪式。**

---

###### 洞见 2：向后兼容不是技术美德，而是一项有债权人的商业义务

###### **核心观点：**
> 没有用户、没有外部依赖，就没有需要偿还的兼容债务；为假想用户保留旧路径，只会让垃圾结构提前沉积。

- **为什么重要：**过早保留旧字段、旧接口和迁移脚本，会扩大状态空间，使后续每次改动都更困难。
- **反常识之处：** “不破坏已有行为” 通常被视为稳健，但对两小时前创建的项目，它可能恰恰是不负责任。
- **可迁移价值：**兼容性应由真实约束触发：活跃用户、外部调用方、持久数据、回滚要求，而不是由 “最佳实践” 自动触发。
- **我应该记住什么：** **先确认谁依赖旧行为，再决定是否兼容。**

---

###### 洞见 3：修补现有实现，常常比重新推导方案更贵

###### **核心观点：**
> 模型容易把当前代码当作不可变前提，于是不断局部打补丁；但从第一性原理重构，可能同时更简单、更安全、更省工。

- **深层问题：**现有实现具有强锚定效应，模型会优化 “如何保住它”，而不是重新审视 “它是否值得保留”。
- **可迁移价值：**面对棘手边界条件时，强制生成两条路线：  
  - 在现有架构上修补；  
  - 忽略当前实现，从约束重新设计。  
  然后比较复杂度、风险、迁移成本与长期维护成本。
- **我应该记住什么：** **不要只问 “怎么修”，还要问 “如果今天重做，会怎么设计”。**

---

###### 洞见 4：管理 AI 的关键不是更长的提示词，而是缩小它的决策权限

###### **核心观点：**
> 与其给模型一张 “空白支票”，不如提供稳定的项目约束、窄任务切片和明确可执行的 “按钮”。

- **重要细节：**
  - 用`PROJECT.md`固化项目阶段、用户规模、部署环境及兼容要求；
  - 明确 “只能改什么” 和 “绝不能改什么”；
  - 要求复述任务，可作为发现理解偏差的检查点，但不能替代最终验收；
  - 对独立模块，可先脱离嘈杂代码库求解，再回接主工程。
- **反常识之处：**模型能力越强，未必越省管理；行动能力提高后，越界造成的浪费也更大。
- **我应该记住什么：** **高能力代理需要的不是更多自由，而是更清晰的授权边界。**

---

##### 3. 底层逻辑

###### **逻辑一：正确的工程标准取决于风险结构**
- **表层现象：**模型反复测试、保留兼容、编写迁移机制。
- **深层原因：**模型学到的是高频工程规范，却不知道当前项目的真实用户、生命周期与失败成本。
- **推导结论：**必须显式提供 “项目经济学”，否则模型会默认按高风险生产系统处理原型。

###### **逻辑二：局部优化会固化错误前提**
- **表层现象：**为旧实现不断增加补丁、类型转换和防御代码。
- **深层原因：**当前代码被默认为约束，而不是可替换的候选方案。
- **推导结论：**一旦补丁成本开始上升，就应触发 “局部修复 vs. 第一性重构” 的并行比较。

###### **逻辑三：代理失控，本质上是权限设计失败**
- **表层现象：**一个小改动扩展成大范围重构、验证或基础设施建设。
- **深层原因：**目标描述了 “想要什么”，却没有规定决策边界、停止条件和允许触碰的范围。
- **推导结论：**管理代理应像设计 API：输入窄、权限小、结果可验收，而不是依赖它自行判断 “做到什么程度”。

##### 4. 反常识清单

| 反常识观点 | 常见认知 | 文章的不同判断 | 启发 |
|---|---|---|---|
| 验证越充分，项目未必越可靠 | 多测试总是好事 | 不影响决策的验证只是延迟与成本 | 按风险和项目阶段配置验证强度 |
| 向后兼容可能是技术债的来源 | 兼容旧行为代表稳健 | 无真实依赖时，兼容会制造无意义分支 | 先寻找兼容性的真实 “债权人” |
| 重写可能比修补更保守 | 重写风险大，补丁最安全 | 错误架构上的连续补丁可能成本更高、风险更大 | 同时估算修补与重构，而非默认修补 |
| 更强的模型可能需要更强的约束 | 能力越强，越适合自主发挥 | 强模型的 “过度帮助” 会扩大改动与成本 | 把任务边界、权限和停止条件写进工作流 |
| “最佳实践” 可能是缺乏上下文的坏实践 | 规范具有普适性 | 规范只有在匹配真实风险时才有价值 | 不问场景的最佳实践，只是模板化决策 |

### 提问 · 2026-09-10 02:39:07

是否需要把以下内容融入进去：“注意：不要过度设计，不要有非必要的安全门禁，非必要不做多余工作。

### 回答 · 2026-09-10 02:39:07

需要融入其**意图**，但不建议原句直接照搬，原因是：

- “过度”“非必要” 比较主观，模型未必知道判断标准；
- “不要过度谨慎” 可能被误解为可以忽略明显风险；
- “不要有非必要的安全门禁” 可能导致模型跳过真正必要的安全检查；
- 与已有的最小实现、按风险验证、完成即停止存在重复。

更好的方式是将其改写成**可执行的判断规则**：

```markdown
## 执行原则

1. 简单任务采用简单方案，优先选择最小、直接、可回退的实现。
2. 只解决当前明确需求，不为假设性的未来需求预先增加复杂度。
3. 严格遵守任务范围。未经明确要求，不得：
   - 新增依赖、抽象层、兼容逻辑或迁移脚本；
   - 增加与当前风险无关的流程、门禁或防御机制；
   - 重构无关代码；
   - 修复范围外的问题；
   - 扩大功能或改动范围。
4. 验证强度应与变更风险相匹配，只执行满足验收标准所必需的检查；不得进行无明确收益的重复测试、全面验证或额外分析。
5. 发现范围外的问题时，只报告，不处理。
6. 满足验收标准后立即停止，不进行额外优化、扩展或清理。

## 越界处理

如果完成任务确实必须超出既定范围，先暂停并说明：

1. 为什么无法在当前范围内完成；
2. 必须增加哪些改动；
3. 最小可行方案及其影响。

获得确认后再继续。
```

其中这两句最能表达你想补充的意思：

> 简单任务采用简单方案，只解决当前明确需求。  
> 不为假设性的未来需求预先增加复杂度。

此外，建议把 “安全门禁” 限定为：

> **与当前风险无关的流程、门禁或防御机制**

这样是在禁止无收益的仪式化工作，而不是允许忽略身份认证、权限控制、数据保护等真正必要的安全要求。

如果希望更精炼，可以采用以下最终版：

```markdown
## 执行约束

- 简单任务采用简单方案，优先选择最小、直接、可回退的实现。
- 只解决当前明确需求，不为假设性的未来需求预先增加复杂度。
- 未经明确授权，不新增依赖、抽象、兼容逻辑、迁移脚本或与当前风险无关的门禁，不重构或修复无关代码。
- 验证强度应与变更风险相匹配，只执行满足验收标准所必需的检查，避免重复或无明确收益的验证。
- 范围外问题只报告，不处理。
- 如必须越界，先说明原因、必要改动、最小方案及其影响，获得确认后再继续。
- 满足验收标准后立即停止，不追加优化、扩展或清理。
```

这一版已经完整覆盖 “不要过度谨慎、过度设计、过度验证和多做无关工作” 的意图，同时比直接写口号更明确、可执行。
