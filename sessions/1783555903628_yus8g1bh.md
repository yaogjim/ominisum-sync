## 分析要点

- **核心高价值点**：将 Codex 主线程限定为协调者，并通过 GOALS.md、里程碑审计和证据要求维持长期任务的项目状态一致性。
- **留存建议**：长期保留，可作为 Codex 长周期项目协作模板参考（提供了较完整的长时间运行 AI 编程任务组织方法，包含路线图、里程碑、审查、本地验证和进度汇报机制）

**知识要点**

- 用 GOALS.md 记录里程碑、目标、范围、决策、阻塞和完成证据
- 一次只保持一个 Goal-mode 目标，避免多目标并行导致上下文漂移
- 主线程负责协调和决策，子线程或 subagent 负责具体实现、调查和验证
- 每个里程碑结束后独立审计路线图并运行代码审查
- 需要本机环境的测试可交给本地线程完成，如浏览器登录、Xcode、权限和模拟器
- 通过 What’s done、What’s next、Any blockers 三段式更新降低回看成本

**行动项**

- 在下一个 Codex 项目中创建 GOALS.md，并按里程碑维护目标、证据和阻塞
- 将主 Codex 线程限定为协调线程，具体实现任务拆给子线程或 subagent
- 在每个里程碑完成后安排独立路线图审计和 /review
- 为需要浏览器或本地凭据的验证建立本地测试线程
- 为多阶段项目维护 progress-dashboard.html 或类似状态看板

### 与 Codex 协作处理长时间运行的任务

Codex can work for long stretches, especially when a

[/goal](https://developers.openai.com/codex/use-cases/follow-goals) gives it a persistent objective. The harder part is staying oriented while it works for hours or days, uncovers new implementation details, and moves through several kinds of verification.

Early assumptions often change once implementation begins. The collaboration model needs to preserve the objective while giving both you and Codex room to revise the plan as new evidence appears.

Over the last few weeks, I have been using five practices:

1. Let Codex plan the work and maintain the roadmap.
2. Keep the main thread focused on coordination.
3. Audit the roadmap and review the code after each milestone.
4. Use local threads for Computer Use testing.
5. Report progress through concise updates and dashboards.

#### 1\. Let Codex plan the work and maintain the roadmap

I usually begin with a conversation rather than /plan mode. I describe what I am trying to build, dictate rough thoughts, share constraints, and let Codex ask questions until it has enough context to propose an initial plan.

This keeps the early discussion flexible. I do not need to turn half-formed ideas into a formal specification before Codex can start helping. It can interview me, reflect back what it understood, identify gaps, and gradually turn the conversation into a workable plan.

As the project takes shape, I ask Codex to set the current

[Goal](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex). Goal mode gives Codex a persistent objective, allowing it to keep working toward the same outcome across multiple turns until the goal is complete, blocked, or replaced.

I can set the goal myself with /goal, but I usually ask Codex to do it. Goal mode is exposed through the harness, so Codex can synthesize our conversation, the project context, and everything it has learned so far into a clear objective. It can also define the evidence required before considering that objective complete.

For larger projects, I ask Codex to write the broader roadmap into GOALS.md. This is a project convention rather than a built-in Codex feature, and the file can be named whatever you prefer.

I usually organize GOALS.md around milestones instead of a flat task list. Each milestone records:

- the intended outcome
- the work currently in scope
- important decisions
- known blockers
- the evidence required before moving on

Codex maintains the file as the project develops. New findings may change the scope of a milestone, introduce another one, or change the evidence required for completion.

Only one Goal-mode objective is active at a time. As milestones are completed, Codex updates GOALS.md, activates the next objective, and continues working toward it.

#### 2\. Keep the main thread focused on coordination

Once the roadmap exists, I keep the main thread focused on the objective, constraints, decisions, and current project state.

It decides what should happen next, delegates bounded tasks, and evaluates the results. It does not need to carry every implementation detail.

A worker may spend an hour reading unfamiliar code, trying several approaches, or tracing a failing test. The coordinator only needs the information that affects the wider project:

- what the worker learned
- what changed
- the supporting evidence
- what should happen next

[subagent](https://developers.openai.com/codex/subagents)

This becomes especially useful once several pieces of work are running in parallel. The main thread can continue coordinating the project while each investigation, implementation, or review remains easy to inspect.

#### 3\. Audit the roadmap and review the code after each milestone

GOALS.md reflects what was known when Codex last updated it. By the end of a milestone, the project has usually uncovered something new.

Before moving on, I ask another thread to compare the roadmap with the current state:

- 这个里程碑实际上完成了吗？
- 下一个目标仍然是正确的吗？
- 是否有遗漏的里程碑？
- 有新证据改变了工作顺序吗？
- 完成定义是否仍然适用？

我会在每个里程碑结束时以及每当新证据实质性地改变项目方向时进行这项审计。

I also run

[/审核](https://developers.openai.com/codex/cli/features#running-local-code-review) on the implementation.

假设登录流程的实现和远程测试已经完成。路线图审核可能会注意到，没有人在真实的已登录浏览器中测试过该流程。与此同时，/review 可能会发现，尽管远程测试通过，新路径仍错误地存储令牌。

协调者更新 GOALS.md，分配 token 修复任务，添加缺失的浏览器验证，然后才激活下一个里程碑。

通常我会将审核和评审放在单独的线程中。子代理可以执行相同的工作，但单独的线程会留下一个我之后可以查阅的可见记录。

#### 4\. 使用本地线程进行计算机使用测试

我的大多数 Codex 会话都在远程实例上运行，因此当我的笔记本电脑关闭时工作仍可继续。有些检查仍然依赖于我的本地机器：

- 已登录的浏览器
- 本地凭证
- Xcode
- macOS 权限
- iOS 模拟器

The remote coordinator can create a local thread for one of those checks. I apply the remote diff or check out the relevant branch or commit so the local thread tests the correct code.

The local thread operates the browser or application and returns screenshots, logs, and findings. When a check fails, a remote worker fixes the issue and the local thread tests again.

A typical loop looks like this:

1. A remote worker implements the sign-in flow.
2. Remote tests pass.
3. A local thread uses the
   [Codex Chrome extension](https://developers.openai.com/codex/app/chrome-extension).
4. The browser test reveals a redirect bug.
5. A remote worker fixes it.
6. The local thread repeats the check.

The project remains remote by default. My computer joins only for the checks that require it. The remote thread can also keep checking for the local thread to become available again when I reopen my laptop.

#### 5\. Report progress through concise updates and dashboards

Worker threads usually report on one task. When I return to the project, I need a view of the overall state:

- what is complete
- what changed
- what remains
- what needs a decision

I ask Codex to report whenever the project state changes, using three short sections:

What’s done What’s next Any blockers

Which is almost like having daily standup with Codex, albeit hourly.

Codex can send the same update through

[Slack](https://chatgpt.com/plugins/share/7a40dcb265994eaaa00d55a46f826394), either as a direct message or in a dedicated project channel.

[/side](https://developers.openai.com/codex/cli/slash-commands#start-a-side-conversation-with-side)

![Image](https://pbs.twimg.com/media/HMmUG2RbYAAsixv?format=jpg&name=large)

Getting a summary from the side thread

![Image](https://pbs.twimg.com/media/HMmUCIwboAAOsbb?format=jpg&name=large)

Asking the side thread to pass along my instructions to the main thread

I can then clarify an instruction, resolve a blocker, add context, or ask the side thread to send updated guidance back to the main thread.

For projects with several milestones or parallel workstreams, I also maintain a progress-dashboard.html. This is a custom project artifact rather than built-in Codex UI. It can show:

- the active goal
- completed milestones
- evidence
- blockers
- decisions
- recent updates

When I return after several hours, I can understand the state of the project without reading every worker thread. Codex can also deploy the dashboard as a Site so that it remains accessible remotely.

#### Summary

I use this structure when a project is likely to uncover new information, involve several independent pieces of work, or require evidence from more than one environment.

The workflow follows a simple cycle. Codex turns the initial conversation into a roadmap, activates one milestone, delegates the work, and checks the result before moving on. Local threads handle the checks that require my machine, while updates and dashboards help me return to the project without reconstructing everything from scratch.

The important part is keeping the project state current enough that the next decision reflects what Codex has actually learned.

#### 与 Codex 协作处理长时间运行任务：精炼总结

这篇文章讲的是：当 Codex 执行持续数小时甚至数天的复杂任务时，关键不是让它一直写代码，而是建立一套“项目协作机制”，让目标、路线图、验证证据和进度始终清晰。作者总结了 5 个实践，用来让 Codex 在长任务中保持方向，并根据新发现不断调整计划。

---

##### 1. 让 Codex 制定计划并维护路线图

作者通常不会一开始就进入 `/plan` 模式，而是先和 Codex 对话：

- 描述想做什么；
- 说出粗略想法；
- 分享限制条件；
- 让 Codex 继续追问，直到它理解上下文。

这样做的好处是：用户不需要一开始就写出完整规格说明，Codex 可以通过提问、复述理解、发现缺口，逐步把模糊想法整理成可执行计划。

###### 使用 Goal 模式保持长期目标

当项目逐渐清晰后，作者会让 Codex 设置当前 `/goal`：

- 一个时间只激活一个 Goal；
- Goal 对应当前里程碑；
- Codex 会持续朝这个目标工作，直到完成、阻塞或被替换；
- Codex 还可以定义“完成目标所需的证据”。

###### 用 `GOALS.md` 管理长期路线图

对于较大的项目，作者会让 Codex 创建并维护 `GOALS.md`，作为共享路线图。它不是 Codex 内置功能，而是一种项目约定。

`GOALS.md` 通常按“里程碑”组织，而不是简单任务清单。每个里程碑记录：

- 预期结果；
- 当前范围；
- 重要决策；
- 已知阻塞；
- 进入下一步前所需证据。

随着项目推进，Codex 会根据新发现更新这个文件，例如调整范围、增加新里程碑或修改完成标准。

---

##### 2. 让主线程专注于协调，而不是细节实现

一旦路线图建立，作者会让主线程只负责项目协调，包括：

- 当前目标；
- 约束条件；
- 关键决策；
- 项目状态；
- 下一步应该做什么。

具体实现细节可以交给 worker、子代理或新线程。

例如，一个 worker 可能花 1 小时阅读陌生代码、尝试多种方案、追踪失败测试，但主线程只需要知道：

- 它学到了什么；
- 改了什么；
- 有什么证据支持；
- 下一步建议是什么。

这种方式特别适合多个任务并行推进：主线程保持全局视角，每个调查、实现或评审任务则单独可查。

---

##### 3. 每个里程碑后审计路线图并审查代码

`GOALS.md` 反映的是 Codex 上一次更新时的认知，但项目推进后常会出现新信息。因此，作者会在每个里程碑结束后，让另一个线程检查路线图是否仍然准确。

审计问题包括：

- 这个里程碑真的完成了吗？
- 下一个目标仍然正确吗？
- 是否遗漏了新的里程碑？
- 是否有新证据改变了工作顺序？
- 完成定义是否还适用？

同时，作者还会对实现运行 `/review`。

###### 具体例子：登录流程

假设远程测试显示登录流程已经完成：

- 路线图审计可能发现：还没有人在真实的已登录浏览器中测试过；
- `/review` 可能发现：虽然远程测试通过，但新路径错误地存储了 token。

于是协调线程会：

1. 更新 `GOALS.md`；
2. 分配 token 修复任务；
3. 添加缺失的浏览器验证；
4. 确认证据齐全后，再启动下一个里程碑。

作者通常把“路线图审计”和“代码评审”放在独立线程中，这样之后可以回看完整记录。

---

##### 4. 用本地线程处理需要本机环境的测试

作者的大部分 Codex 会话运行在远程实例上，这样即使笔记本关闭，任务也能继续执行。但有些验证必须依赖本地机器，例如：

- 已登录的浏览器；
- 本地凭证；
- Xcode；
- macOS 权限；
- iOS 模拟器；
- 本机设备状态。

这时，远程协调线程会创建一个本地线程。用户在本机应用远程 diff，或切换到相关分支/提交，让本地线程测试正确版本的代码。

本地线程负责操作浏览器或应用，并返回：

- 截图；
- 日志；
- 测试发现。

###### 典型循环

以登录流程为例：

1. 远程 worker 实现登录功能；
2. 远程测试通过；
3. 本地线程使用 Codex Chrome 扩展进行浏览器测试；
4. 发现重定向 bug；
5. 远程 worker 修复；
6. 本地线程再次验证。

这样，项目默认仍在远程推进，只有必须依赖本机环境的检查才调用本地线程。

---

##### 5. 用简短更新和仪表盘报告进度

当 worker 线程很多时，用户回到项目后需要快速知道整体状态，而不是逐个阅读所有线程。

作者让 Codex 在项目状态变化时，用 3 个简短部分汇报：

- **What’s done**：已经完成什么；
- **What’s next**：下一步做什么；
- **Any blockers**：是否有阻塞。

这类似于和 Codex 做“小时级站会”。

Codex 也可以通过 Slack 发送这些更新，例如：

- 私信用户；
- 发到专门的项目频道。

如果用户需要补充指令，可以通过侧边线程说明，再让它把新指令传回主线程。

###### 使用 `progress-dashboard.html`

对于包含多个里程碑或并行工作流的项目，作者还会维护一个自定义的 `progress-dashboard.html`，用于展示：

- 当前活跃目标；
- 已完成里程碑；
- 验证证据；
- 阻塞问题；
- 已做决策；
- 最近更新。

这样用户隔几个小时回来后，不必重新阅读所有 worker 线程，也能快速恢复上下文。Codex 还可以把这个仪表盘部署成远程可访问的 Site。

---

##### 总体工作流

作者的长期任务协作流程可以概括为：

1. Codex 先通过对话理解需求；
2. 将需求整理成 `GOALS.md` 路线图；
3. 每次只激活一个 Goal，对应当前里程碑；
4. 主线程负责协调，worker 或子线程负责具体执行；
5. 每个里程碑结束后审计路线图并运行 `/review`；
6. 需要本机环境时，用本地线程测试；
7. 用简短更新、Slack 和仪表盘同步状态；
8. 只有当约定证据齐全后，才声明完成。

核心思想是：**让 Codex 不只是执行任务，而是持续维护项目状态，让下一步决策始终基于最新证据。**

### 2026-08-03 01:51:37

#### 与 Codex 协作处理长时间运行的任务

这篇内容介绍了一套让 Codex 长时间推进复杂项目的方法。你可以从中了解，怎样让 Codex 持续工作、及时调整计划，并在远程环境和本地设备之间完成验证，同时始终掌握项目进展。

##### 首先，让 Codex 制定计划，并持续维护路线图

核心做法是：不要一开始就把所有想法整理成正式需求，而是先和 Codex 进行一段对话，再让它把讨论逐步变成可执行的计划。

具体来说，用户通常不会直接进入 `/plan` 模式，而是先描述自己想做什么，讲出一些还不完整的想法、约束条件和担忧。Codex 会通过提问来补充信息，复述它的理解，并找出目前还缺少的内容。

这样做的好处是，早期想法不必一开始就被写成严密的规格说明。计划可以随着对话逐渐成形，也可以随着新证据出现而调整。

当方向比较明确后，就可以给 Codex 设置一个当前目标，也就是 `/goal`。这里的“目标模式”，可以理解为一个持续存在的任务目标。它允许 Codex 在多轮对话中，始终朝着同一个结果推进，直到目标完成、遇到阻塞，或者被新的目标替代。

这个目标可以由人直接设置，也可以让 Codex 根据之前的对话、项目背景和已经掌握的信息来总结。更重要的是，Codex 还可以同时说明：需要看到哪些证据，才能认为这个目标真的完成了。

对于较大的项目，可以把整体路线图写进一个叫作 `GOALS.md` 的文件里。这个文件名只是项目约定，不是 Codex 固定要求的功能，也可以换成其他名字。

路线图最好按照“里程碑”组织，而不是简单列出一长串任务。每个里程碑都记录五类信息：想达到的结果，目前包含哪些工作，已经作出的重要决定，已知的阻塞问题，以及进入下一步之前必须具备的证据。

随着项目推进，Codex 持续更新这份文件。新的发现可能会改变某个里程碑的范围，也可能增加新的里程碑，或者改变完成标准。

需要注意的是，同一时间只保留一个处于目标模式的活动目标。一个里程碑完成后，Codex 更新 `GOALS.md`，激活下一个目标，再继续工作。

##### 接下来，让主线程负责协调，不要塞进所有实现细节

核心结论是：主线程应该像项目协调者，而不是亲自处理每一个细节。

路线图建立之后，主线程主要关注当前目标、项目约束、关键决定和整体状态。它负责判断下一步做什么，把边界清楚的工作分派出去，再检查工作结果。

比如，一个工作线程可能花一个小时阅读陌生代码、尝试几种方案，或者追查一个失败的测试。主线程不需要接收这一个小时里的完整过程，只需要知道四件事：工作线程学到了什么，项目发生了什么变化，有哪些证据支持这个结论，以及下一步建议做什么。

这里的“工作线程”，可以理解为负责某一项具体调查、实现或审查的独立工作单元。Codex 也可以通过子代理，也就是专门执行限定任务的代理，来完成这些工作。

当多个任务并行进行时，这种分工尤其有用。主线程可以继续协调整体项目，而每项调查、实现和评审又都保持相对独立，方便检查。

简单说，主线程掌握方向和决策，其他线程负责深入执行。这样可以避免主线程被大量代码细节淹没。

##### 更重要的是，每个里程碑结束后都要审计路线图和代码

核心结论是：里程碑完成，并不代表路线图一定还准确，也不代表实现一定没有问题。因此，在进入下一阶段之前，必须重新检查计划和代码。

原因在于，`GOALS.md` 记录的是 Codex 上一次更新时所知道的情况。等一个里程碑真正做完，项目通常已经出现了新的信息。

所以，每个里程碑结束时，可以让另一个线程把路线图和项目当前状态进行对照，重点询问几个问题：

这个里程碑实际上完成了吗？

下一个目标仍然正确吗？

有没有遗漏的里程碑？

新的证据是否改变了工作顺序？

原来的完成标准现在还适用吗？

当新证据实质性地改变项目方向时，也应该重新进行一次审计。

除了审计路线图，还要对实现本身运行 `/review`。也就是让 Codex 专门检查代码和实现质量，而不是只看任务清单有没有被勾掉。

原文给了一个登录流程的例子。假设登录功能已经完成，远程测试也通过了。路线图审计可能发现，项目从来没有在一个真实的、已经登录的浏览器里测试过这个流程。与此同时，代码评审可能发现，虽然远程测试没有报错，但新的登录路径实际上错误地保存了令牌，也就是登录后用于保持身份的凭证。

这时，协调者就不能直接进入下一个里程碑。它应该先更新 `GOALS.md`，分配修复令牌存储问题的任务，并补上真实浏览器验证，确认这些问题都处理完之后，再激活下一阶段。

通常，路线图审计和代码评审会放在单独的线程里。这样做的好处是，审计过程会留下清晰、可回看的记录。子代理也能完成同样的工作，但独立线程更方便日后查阅、继续处理或复盘。

##### 然后，用本地线程完成依赖设备环境的测试

核心结论是：项目可以默认在远程环境中运行，但凡是依赖本地设备状态的检查，就交给本地线程处理。

很多 Codex 会话运行在远程实例上。这样即使笔记本合上，远程工作也可以继续。不过，有些验证必须依赖本地机器，例如已经登录的浏览器、本地凭证、苹果的 Xcode 开发工具、macOS 权限，以及 iPhone 或 iPad 模拟器。

这时，远程协调者可以创建一个本地线程。先把相关代码的改动应用到本地，或者切换到正确的分支和提交版本，确保本地测试的确是当前项目要验证的代码。

本地线程负责操作浏览器或应用，然后返回截图、日志和测试结果。如果测试失败，远程工作线程修复问题，本地线程再重新测试。

一个典型流程是这样的：

远程工作线程先实现登录流程。远程测试通过之后，本地线程使用 Codex 的 Chrome 扩展进行真实浏览器测试。测试发现登录后的跳转存在问题。远程工作线程修复这个问题，本地线程再重复检查，直到验证通过。

这里的重点是，项目仍然以远程环境为主。只有那些确实需要本地浏览器、桌面应用、权限、凭证或设备状态的检查，才让本地电脑参与。

如果笔记本暂时关闭，远程线程还可以继续工作，并在电脑重新打开后，继续等待本地线程可用，再完成剩余检查。

##### 最后，用简短更新和进度面板保持全局视野

核心结论是：每个工作线程只负责一项任务，但项目负责人需要随时看到整个项目的状态。

当你离开项目几个小时再回来时，最需要知道的通常不是每条讨论细节，而是四件事：哪些已经完成，最近改了什么，还剩下什么，以及哪些事情需要你做决定。

因此，可以要求 Codex 在项目状态发生变化时，只用三个简短部分汇报：

已经完成的内容。

接下来要做的事情。

当前存在的阻塞问题。

这有点像和 Codex 每小时进行一次简短的站会，但内容更精炼，也更容易快速恢复上下文。

这些更新还可以通过 Slack 发送。既可以直接发给个人，也可以发到专门的项目频道。

另外，也可以使用一个旁线程，也就是专门负责沟通和汇总的辅助线程。你可以让它总结当前状态，也可以把自己的新指示交给它，再由它传达给主线程。这样，当你想澄清要求、解决阻塞，或者补充背景时，不必重新阅读所有工作线程。

对于包含多个里程碑或多个并行工作流的项目，还可以维护一个 `progress-dashboard.html`，也就是项目进度面板。它不是 Codex 内置的界面，而是项目自定义的文件。

这个面板可以展示当前活动目标、已经完成的里程碑、对应证据、阻塞问题、关键决定和最近更新。这样，几小时后重新回来时，你不需要逐一阅读每个工作线程，就能快速理解项目现在进行到哪里。

如果需要，还可以把这个面板部署成一个 Site，让它能够从远程位置访问。

##### 把整套流程串起来

这套方法特别适合三类项目。

第一类，是项目很可能在执行过程中发现新信息。

第二类，是项目包含多个相互独立的工作部分。

第三类，是完成项目需要来自多个环境的证据，比如远程测试加本地浏览器测试。

整个流程可以概括为一个循环。

先通过对话，让 Codex 理解目标和约束，并形成初步计划。接着，把计划整理成按里程碑划分的路线图。然后只激活一个当前目标，把具体工作分派给不同线程或子代理。

完成一个里程碑后，先审计路线图，再评审代码，确认当前状态和完成证据都足够。涉及本地浏览器、桌面应用或设备权限的检查，就交给本地线程。项目状态发生变化时，用简短更新和进度面板记录下来。

在这个流程里，最重要的不是让路线图一开始就完美，而是让项目状态持续保持最新。只有这样，下一次决策才会真正反映 Codex 已经学到的新信息。

##### 可以直接交给 Codex 的启动要求

如果要把这套方法用于一个新项目，可以在新的 Codex 线程中提出这样的要求：

请把这个任务作为一个长期运行的项目来协调。先通过提问了解我要构建什么，让我用对话方式描述粗略想法和约束，再把讨论整理成初始计划。

创建 `GOALS.md` 作为共享路线图，并按照里程碑组织。每个里程碑都要写清预期结果、工作范围、重要决定、阻塞问题，以及进入下一阶段所需的证据。

同一时间只维护一个目标模式中的活动目标，而且这个目标必须对应当前里程碑。主线程只负责目标、约束、决定和项目状态。具体实现交给子代理或新的工作线程，并要求它们返回结论、改动和证据，而不是完整的过程记录。

对于之后可能需要查看、继续或评审的工作，使用独立线程。对于边界清楚、无需保留完整历史的工作，可以使用子代理。

每个里程碑完成后，用单独线程审计 `GOALS.md` 和项目当前状态，并运行 `/review` 检查实现。完成审计后，先更新路线图，再激活下一个目标。

凡是依赖浏览器、桌面应用、权限、本地凭证或设备状态的测试，都使用本地线程。项目状态发生变化时，只汇报“已经完成”“接下来做什么”和“当前阻塞”。

如果项目包含多个里程碑或多个工作线程，就维护 `progress-dashboard.html`。在约定的证据全部出现之前，不要宣布项目完成。

这套做法也可以进一步整理成一个可复用的 Codex 技能，例如命名为 `orchestrate-projects`，专门保存这套项目编排流程。

##### 最值得记住的几点

最后，回顾五个最重要的结论。

第一，先通过自然对话让 Codex 理解问题，再把讨论整理成里程碑路线图。不要要求一开始就写出完美规格。

第二，始终只保留一个活动目标，让 Codex 在清晰的当前目标下持续推进，同时用 `GOALS.md` 记录不断变化的项目状态。

第三，主线程负责协调和决策，具体调查、实现和评审交给独立线程或子代理，避免主线程被实现细节拖慢。

第四，每个里程碑完成后，都要重新审计路线图并运行代码评审。测试通过，不等于真实环境已经验证，也不等于实现没有隐藏问题。

第五，远程环境负责持续工作，本地线程负责设备相关测试；再通过简短更新、Slack 和进度面板，让你随时知道项目完成了什么、下一步是什么，以及哪里被卡住了。

## 深度解读（1）

### 2026-09-18 00:34:31

#### 长时间运行的 AI 编程，真正难的是维持“可验证的项目状态”

这篇文章最值得保留的，不是某条 Codex 指令，而是一套对 Agent 协作问题的重新定义：**当 AI 能连续工作数小时甚至数天，瓶颈就从“能否写出代码”转向“能否始终知道目标、进展与完成标准”。**

短任务可以依赖一段上下文；长任务却会不断产生新信息。实现时发现原有假设不成立、测试暴露遗漏、不同环境给出矛盾结果，最初计划必然过时。如果 Agent 只是忠实执行计划，它可能高效地走向错误终点。

##### 固定目标，但允许路线持续改写

作者采用了一个有价值的分层：用 Goal 保存当前必须达成的结果，用 `GOALS.md` 维护可变的项目路线图。后者按里程碑记录预期结果、范围、决策、阻塞项和验收证据，并随着发现更新。

关键不在文件格式，而在于区分两件容易混淆的事：

- **目标需要稳定**，否则 Agent 会被局部问题牵着走；
- **计划必须可变**，否则新证据无法进入决策。

同时只激活一个里程碑，也是在限制执行自由度。它让并行工作服务于同一个阶段性结果，避免多个线程各自优化、最后却无法汇合。这与传统项目管理相似，但 Agent 放大了其重要性：机器执行速度越快，方向偏差造成的返工也越快。

##### “完成”应由证据决定，而不是由任务状态决定

文章中最实用的机制，是每个里程碑结束后同时做两类检查：审计路线图是否仍然正确，以及审查代码是否真的可靠。

登录功能就是典型例子：远程测试通过，只能证明某些自动化路径成立；真实登录浏览器可能仍有重定向错误，代码审查还可能发现令牌存储不安全。于是“实现完成”与“目标完成”不再是同一件事。**完成标准必须明确要求相应环境中的证据，而不能只看 Agent 是否声称任务已做完。**

本地线程也应从这个角度理解。它不是远程 Agent 的补充算力，而是一个特殊验证环境，提供登录态、凭证、系统权限、Xcode 或模拟器等远程实例无法拥有的条件。人的电脑只在必要时加入闭环，使人工参与从持续盯盘变成提供稀缺环境与处理关键决策。

##### Agent 产品正在从聊天框变成项目控制面

主线程只保留目标、约束、决策和项目状态，具体探索交给工作线程；工作线程返回结论、改动和证据，而不是完整过程。简短进度更新和 HTML 仪表盘，则降低人离开数小时后的“重新理解成本”。

这暴露了一个明确的产品信号：`GOALS.md`、独立线程和自制仪表盘，实际上是在手工补齐 Agent 平台缺少的控制面。未来更重要的能力可能不是更长上下文，而是**可追踪的目标版本、证据绑定的里程碑、环境感知的验证、决策记录，以及异常时的升级机制**。

不过，这仍是一套个人实践，而非经过比较验证的最佳方案。让 Codex 自己维护路线图，也可能让错误假设在规划与执行之间自我强化。因此，独立审计、外部测试和可检查的证据不是附加流程，而是这套模式成立的前提。它最适合高不确定性、跨环境、可并行的工程项目；对边界清晰的小任务，则可能徒增协调成本。

## 默认总结（1）

### 2026-09-18 01:44:36

##### 一句话看懂

作者分享了一套让 Codex 连续工作数小时甚至数天的方法：用持续目标和里程碑路线图保持方向，通过分线程执行、阶段复核、本地测试和简短汇报，避免项目越做越偏。

##### 关键内容

- **先对话，再形成路线图**：让 Codex 通过提问理解需求，把尚不成熟的想法整理成计划；用 Goal 模式维持当前目标，并在自建的 `GOALS.md` 中记录各里程碑的范围、决策、阻碍和完成证据。
- **主线程只负责协调**：具体调查、编码和测试交给子代理或独立线程；它们只需回报结论、改动、证据及下一步，不必把全部过程塞进主线程。
- **每个里程碑后重新检查**：另开线程审计路线图是否仍符合项目现状，同时用 `/review` 检查代码。测试通过不等于真正完成，还要确认约定的证据齐全。
- **远程开发、本地验证**：大部分工作可在远程持续运行；涉及登录浏览器、凭证、Xcode、系统权限等环境时，再调用本地线程测试。进度统一按“已完成、下一步、阻碍”汇报，复杂项目可配仪表盘。

##### 通俗解读

核心不是让 Codex“一次写完”，而是把它当作能长期协作的项目团队：目标保持稳定，计划可随新证据调整，每一步都要验证。`GOALS.md` 和进度仪表盘是作者自定义做法，并非 Codex 内置功能。文章适合正在用 Codex 做多阶段、跨环境项目的人细读；若只是完成短小编码任务，参考其阶段复核和简短汇报方式即可。
