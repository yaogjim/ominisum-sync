**知识要点**

- session 应被视为 append-only 的事件日志，而不是简单聊天记录
- harness 应设计成可替换的 orchestration layer，尽量减少对模型当前缺陷的固化假设
- sandbox 与 brain 解耦后，有利于恢复性、安全性和按需 provision 的性能优化
- 安全边界不应建立在“模型暂时做不到某事”的脆弱假设上

**行动项**

- 把敏感凭证从模型可直接访问的执行环境中剥离，改为受控代理调用

## 正文

**AlexZ**

Anthropic 发布了新的 Harness 工程实践文章。

表面看是介绍他们的新产品，但从更宏观的角度看这篇文章，本质是在探讨一个问题：当模型能力持续变化时，Agent 系统到底该把什么做成“稳定接口”，把什么留给未来不断重写？

看完文章，我觉得这篇文章隐藏了 Anthropic 对未来 Agent 基础设施的一个深度判断： Agent 基础设施会越来越像“微型操作系统 （Agent OS）”，这是我觉得最值得重视的地方。

Agent 框架最忌讳的是把“暂时性的模型缺陷”上升为“永久性的系统结构”。

harness（调度循环、上下文整理、工具路由等）本质上是在编码对模型能力边界的假设，但是这些假设会随着模型变强而迅速过时。

在我之前发布的《驾驭工程》（马书）里有句话：模型能力越强，harness 将会越简单。

但是现在很多人写 Agent ，包括我自己，很容易把模型缺陷写到 Agent 框架里。比如，模型不会规划，就强行把步骤拆成固定 DAG 。。等等。

这些其实都算是 harness 补丁，其实我们 agent 开发者也很难去判断哪些是模型缺陷。

Anthropic 的做法是设计一个 meta-harness：不去承诺具体 harness 长什么样，只承诺几类长期稳定的接口。

这样的话，我们就不必猜测模型缺陷是什么。 这其实和 OS 思路差不多，OS 从来不关心未来程序怎么写，它只是提供抽象接口。

那么 Anthropic 这个 meta-harness 是如何给 Agent 做抽象呢？

文章里最重要的抽象是三件事：

\- session，可以理解为 事件日志 / durable state  
\- harness， 推理-调度循环 / 脑干  
\- sandbox， 执行环境 / 手脚

它们的分离，才是这个架构的核心创新点。

1\. The session is not Claude’s context window

文章里这句话代表了 meta-harness 如何抽象 session。它不是简单的聊天记录，它代表的是「可恢复事件流」。

Anthropic 想做的是，把 session 做成一个 append-only event log，不能把它当作一个直接喂给模型的 prompt，它应该是一个可查询、可回放、可恢复、可重组的真实执行历史。

如果你只是把 session 当作上下文窗口的镜像，那其实就表示它损失了可恢复性。

2\. Harness：可替换的 orchestration layer

早期 Anthropic 把 harness、session、sandbox 都塞进一个容器里。但这样做遇到了很多问题，比如，harness 崩了，整个会话难恢复；容器挂了，状态可能丢失；调试困难，包含了用户数据无法轻易使用shell调试；VPC 接入困难。

所以，他们把 harness 从容器里拿出来，变成一个“调用工具的脑干”。

现在的 Harness :

\- 不再拥有状态  
\- 不再假设工具在哪里，你只能看到一个接口 execute(name, input) -&gt; string （有种 nix 哲学了）

Harness 这样抽象的意思是：AI 不需要知道它在哪台设备，哪个操作系统，手机还是电脑，容器还是虚拟机等等，它只知道“我可以使用哪些手”。 （想象一下千手观音。。）

3\. Sandbox：“某种具体的手”

文章里说，decouple the brain from the hands

也就是说：

\- Claude + harness 是 brain  
\- sandboxes / tools / MCP / custom infra 是 hands

一旦 sandbox 只是 hand，就意味着它们彼此独立，可以来自不同的基础设施，可以共享和传递，也不需要每个 session 都加载启动完整的 sandbox。

这直接引出后面的 “many brains, many hands”。

这次 Anthropic 的实践来自于现代分布式系统最核心的经验之一：不要试图保住某个进程，要保住可恢复的事实记录和重启协议。

这样设计，也从架构上增强了安全性。 文章里有句话，

narrow scoping is an obvious mitigation, but this encodes an assumption about what Claude can't do with a limited token—and Claude is getting increasingly smart.

意思是说：

\- 当然你可以给模型一个“范围较小的 token”  
\- 但这其实还是在赌模型做不到某些攻击路径  
\- 而模型在持续变强，这种“它应该不会想到吧”的安全假设会越来越脆弱

所以他们不要把 credentials 放在 sandbox 里。 比如 Git token 只在初始化 clone/push/pull 过程中以受控方式接入，不让模型直接读到 token。模型通过 MCP proxy 间接调用，proxy 拿 session token 去 vault 取真实凭证再执行。

不把安全建立在模型能力不足上。

这样设计，也把“可恢复历史”从“上下文窗口”中解放出来了。

它的理念是，不要把完整历史放在模型上下文里；把它放到 session 这个可查询对象里。

从系统角度看：

\- Claude 的 context window 是执行现场  
\- session log 是证据仓库  
\- harness 是检索与重组器

于是：

\- prompt 不再承担“永久记忆”职责  
\- trimming 不等于历史消失  
\- compaction 不等于事实不可恢复

恢复时可以重新取原始事件，这是比“纯摘要 memory”高一个层级的设计。

这样设计，也提升了性能。

降低了 TTFT（time to first token），不再让每个 session 预付全部容器成本。

现在，先让 brain 起跑，hand 只有在需要时才 provision。这是典型的 lazy materialization 思路。

文章里给出的数据也很漂亮：

\- p50 TTFT 降约 60%  
\- p95 降超过 90%

这个数字说明一个问题：原来瓶颈并非模型推理本身，而是把整个执行环境预耦合到了请求入口。

最后，别忘记这样设计的初衷，就是为了增强未来 Agent 的可扩展性。

文章最后说：“Many brains, many hands”

这意味着，Anthropic 未来是要做一个 agent runtime substrate。多脑协作/ 多手编排 / 跨环境执行。

Agent 的本体不应绑定某个执行壳，而应绑定一组可恢复状态与可调用能力。

文章里也提到了这样设计的一些缺点，比如 让 brain 管 many hands，本身是更难的 cognitive task。

所以这个架构的前提是，模型智能已足够高，能承担更抽象的工具路由责任。

这其实就是在赌未来模型能力一定会提升，面向未来设计。

最后，这篇文章给我的启发有三条：

\- 启发 1：会话不是消息列表，而是“执行事实流”。  
\- 启发 2：工具环境不要内化为 agent 自身。  
\- 启发 3：上下文工程应该是 harness 可替换策略，要考虑未来一旦模型变强、或者检索策略变了不产生技术债。

这篇文章没明说，但我认为它真正代表的是 Anthropic 的一个产品哲学：我们不相信今天的 agent harness 会是最终形态，所以我们优先投资于稳定接口，而不是一次性最优实现。

Agent 系统的未来，在于一组长期稳定的系统抽象之上。

## 通俗精炼（1）

### 2026-04-09 02:50:32

#### Anthropic 新 Harness 的核心意思：把 Agent 做成 “微型操作系统”

##### 一、核心判断：不要把今天的模型缺陷写成永久架构

这篇文章表面在讲 Anthropic 的新产品，实质在回答一个更重要的问题：

**当模型能力不断提升时，Agent 系统里哪些东西应该是稳定的，哪些东西应该允许持续重写？**

作者的判断是：  
**未来的 Agent 基础设施，会越来越像一个 “Agent OS（微型操作系统）”。**

也就是说，系统不应该围绕 “当前模型不够强” 来设计，而应该围绕**长期稳定的抽象接口**来设计。

---

##### 二、Anthropic 的方法：不固定 Harness 形态，只固定接口

Anthropic 没有把某一种具体的 harness 设计当成最终答案，而是做了一个更上层的**meta-harness**。

它只定义三类长期稳定的接口：

- **Session**：可恢复的事件日志 / 持久状态
- **Harness**：推理与调度循环 / “脑干”
- **Sandbox**：执行环境与工具 / “手脚”

这三者分离，是整个架构最关键的创新。

---

##### 三、三个关键抽象分别意味着什么

###### 1. Session：不是聊天记录，而是 “执行事实流”

Anthropic 强调，**session 不是模型上下文窗口的镜像**。

它更像一个**append-only event log**，也就是：

- 可查询
- 可回放
- 可恢复
- 可重组

这意味着，会话历史不再只是 prompt 的一部分，而是系统层面的真实执行记录。  
好处是：**即使上下文被裁剪，历史事实也不会丢失。**

###### 2. Harness：不持有状态的编排层

Anthropic 把 harness 从原来的容器里拆出来，变成一个更轻、更通用的 orchestration layer。

新的 harness 特点是：

- **不保存状态**
- **不绑定具体工具位置**
- 只暴露统一接口：`execute (name, input) -> string`

这背后的思想是：  
**AI 不需要知道自己运行在哪，只需要知道自己 “能调用哪些能力”。**

###### 3. Sandbox：只是具体执行能力，不再和大脑绑定

在这个架构里：

- **Claude + harness = brain**
- **sandbox /tools/ MCP /custom infra = hands**

一旦 brain 和 hands 解耦，就能实现：

- 不同执行环境独立存在
- 不同 session 之间共享能力
- 按需加载 sandbox，而不是每次都预启动完整环境

这就是 Anthropic 提到的**“many brains, many hands”**的基础。

---

##### 四、为什么这套设计重要

###### 1. 更容易恢复和扩展

Anthropic 借鉴了分布式系统的经典原则：

**不要执着保住某个进程，要保住可恢复的事实记录和重启协议。**

这样即使 harness 崩溃、容器挂掉，也能基于 session 恢复执行。

###### 2. 更安全

Anthropic 的一个重要观点是：

**安全不能建立在 “模型暂时还不够聪明” 这个假设上。**

所以他们不把敏感凭证直接暴露给模型，例如 Git token 不放在 sandbox 里，而是通过 proxy + vault 受控调用。

本质上是：  
**不要赌模型想不到攻击路径。**

###### 3. 性能更好

新架构把 “脑” 先启动，把 “手” 按需 provision，避免每次请求都预付完整执行环境成本。

结果是：

- **p50 TTFT 下降约 60%**
- **p95 TTFT 下降超过 90%**

这说明过去的主要瓶颈，很多时候不是模型推理，而是**请求入口处过早耦合了执行环境**。

---

##### 五、这背后的产品哲学

这篇文章真正传递的，不只是一个工程方案，而是一种产品哲学：

**不相信今天的 Agent Harness 会是最终形态，所以优先投资稳定接口，而不是一次性最优实现。**

换句话说，Anthropic 在赌的是：

- 模型能力会持续提升
- 今天很多 “补丁式框架设计” 未来都会过时
- 真正值得沉淀的是系统抽象，而不是某种固定工作流

---

##### 六、对 Agent 设计的三点启发

###### 1. 会话不是消息列表，而是执行事实流
不要把 session 只理解成聊天记录，应把它设计成可恢复、可检索、可回放的历史系统。

###### 2. 工具环境不要内化进 Agent 本体
执行环境应是外部能力，而不是 Agent 身份的一部分，这样才有扩展性和可替换性。

###### 3. 上下文工程要保持可替换
今天的检索、裁剪、摘要策略，都不该被写死成永久架构，否则模型一变强就会形成技术债。

---

##### 七、一句话总结

Anthropic 这篇文章最值得关注的，不是某个具体产品功能，而是它释放出的信号：

**未来 Agent 的核心，不是把流程写死，而是建立一套长期稳定的系统抽象，让 “脑、记忆、手” 彼此解耦，并随模型能力演进持续重组。**

## 趣读意义（1）

### 2026-04-09 02:51:09

#### Anthropic 这篇文章，真正值钱的不是产品，是 “Agent 该长成什么样”

这篇文章表面在讲 Claude 的托管 Agent，底层其实在回答一个更大的问题：

**当模型能力还在快速进化，系统里哪些东西该写死，哪些东西要故意留白？**

Anthropic 给出的答案很清晰：

> **把 “稳定接口” 做厚，把 “具体编排” 做薄。**

这就是它最有参考价值的地方。  
很多团队今天做 Agent，容易把 “模型当前不够强” 写成 “系统永久规则”。短期能跑，长期必重构。

---

##### 一句话看懂这套设计

Anthropic 在把 Agent 基础设施，往一个 “微型操作系统” 方向推。

它拆成了三层：

- **Session**：执行事实的日志
- **Harness**：推理与调度的脑干
- **Sandbox**：执行动作的手脚

这三层拆开后，Agent 就从 “一个大黑盒” 变成了 “可恢复、可替换、可扩展的系统”。

这个判断很重要，因为它意味着：

**未来 Agent 的竞争力，越来越不在 prompt 技巧，而在 runtime 抽象。**

---

##### 这篇文章最狠的洞察

##### 1. Session 不该只是聊天记录，它应该是 “执行账本”

这是全文最关键的一刀。

如果 session 只是 message history，你得到的是 “喂给模型看的材料”。  
如果 session 是 append-only event log，你得到的是：

- 可恢复
- 可回放
- 可审计
- 可重组
- 可做不同检索策略

这对产品设计的意义非常直接：

**Agent 的记忆，不该依赖上下文窗口；上下文窗口只该承载当前现场。**

你可以把它想成：

- `context window`：工位上的桌面
- `session log`：档案室
- `harness`：档案管理员

桌面乱了可以重摆，档案不能丢。

对产品经理来说，这会直接影响三个能力：

- 用户会不会信任系统
- 系统能不能 debug
- 长任务能不能跨中断继续执行

很多 Agent 产品 “看着聪明，实际脆弱”，核心问题就在这：  
**记忆被偷懒地塞进 prompt 里了。**

---

##### 2. Harness 应该是可替换层，不要写成 “模型补丁合集”

文中最有经验感的一句话，其实是这个意思：

> harness 本质上是在编码你对模型能力边界的判断。

这句话很值钱。

因为今天很多 Agent 框架都在做这些事：

- 强制固定 DAG
- 强制先规划再执行
- 强制一步一步拆任务
- 强制工具调用顺序
- 强制某种 memory 策略

这些做法有时有效，但风险也很明显：  
**你以为自己在做架构，实际在给模型打石膏。**

模型一旦变强，这些 “石膏” 会变成阻力：

- 路径变长
- 决策变慢
- 可维护性下降
- 框架僵化
- 技术债堆积

Anthropic 的聪明点在于：  
它不赌 “未来 harness 长什么样”，它只定义稳定接口。

这特别像操作系统思路：  
应用会变，硬件会变，调度策略会变，接口尽量稳定。

对你做产品的参考价值在于：

**产品架构要给模型升级留红利，不要让模型升级触发系统重写。**

---

##### 3. Sandbox 是 “手”，不是 “身体的一部分”

“brain 和 hands 解耦” 这个表述，非常产品化。

以前很多 Agent 系统把状态、调度、执行环境塞在同一个容器里，问题很多：

- 一个地方挂了，整段任务难恢复
- 状态散在运行时里，追查困难
- 调试不方便
- 环境耦合重
- 启动成本高

Anthropic 把 sandbox 降级成 “手”，这个动作非常关键。

一旦 sandbox 只是手，系统立刻获得了几个能力：

- 可以按需加载，不必每次都启动完整环境
- 可以跨环境调用不同能力
- 可以多手协作
- 可以把执行层独立治理
- 可以让 brain 更专注于决策

这背后的产品启发很现实：

**Agent 的能力边界，不该由 “装在哪个壳里” 决定，而该由 “能调哪些能力接口” 决定。**

这会影响你设计产品能力地图的方式。  
你设计的重点不再是 “给 Agent 一个完整环境”，而是：

- 给它哪些能力
- 每种能力的调用边界是什么
- 能力之间怎么组合
- 哪些能力需要隔离
- 哪些能力可共享

---

##### 4. 安全策略不能建立在 “模型暂时不够聪明” 上

这部分是很多团队最容易低估的。

文章里关于 token /credentials 的处理，核心思想就一句：

**不要把安全建立在模型能力不足上。**

这句话非常硬核，也非常实用。

因为很多系统默认的安全逻辑其实是：

- 上下文少一点，模型应该想不到
- 权限藏深一点，模型应该拿不到
- 路径绕一点，模型应该用不好

这类假设短期可能成立，长期非常危险。  
模型能力上升后，今天的 “看起来没问题” 会变成明天的漏洞。

Anthropic 的做法是：

- 让模型看不到真实凭证
- 通过 proxy /vault 受控取用
- 权限在基础设施层管理
- 凭证只在必要流程中短暂出现

对产品经理的启发是：

**Agent 安全设计要偏基础设施思维，少做心理安慰式防护。**

判断一个方案安不安全，可以问一句：

> 如果模型明年强 10 倍，这个方案还成立吗？

这个问题很好用。

---

##### 5. 性能提升说明：很多瓶颈根本不在模型

文中给出的 TTFT 数据很漂亮：

- p50 降约 60%
- p95 降超过 90%

这组数据特别值得产品人注意，因为它说明一件事：

**用户感知到的 “Agent 慢”，很多时候不是模型慢，是系统预耦合太重。**

以前是 “先把整套环境搬出来，再开始思考”。  
现在是 “先让 brain 起跑，需要手时再调手”。

这就是典型的 lazy materialization。

对产品体验的影响很直接：

- 首响应更快
- 用户更愿意继续等待
- 复杂任务的体感明显改善
- 系统资源利用率更高

这也提醒我们一个常见误判：

**Agent 体验优化，不要只盯模型速度；更该盯启动链路、环境准备、上下文装配。**

很多产品增长机会，其实藏在这类 “非模型延迟” 里。

---

#### 对产品经理最有用的 5 个参考意义

##### 1. 你做的不是 “一个聪明对话框”，你做的是 “任务操作系统”

如果产品目标是复杂任务执行，设计重心要从聊天体验转向：

- 状态管理
- 任务恢复
- 能力编排
- 执行审计
- 权限治理

这决定了你该优先投哪里。  
很多团队把 80% 精力放在 prompt 和 agent flow，最后发现真正卡脖子的，是 runtime。

---

##### 2. 记忆系统要产品化，别只做上下文拼接

如果你的产品里存在这些场景：

- 长周期任务
- 多轮协作
- 中途退出再恢复
- 多 Agent 接力
- 用户追责与复盘

那 session 就该被当作正式产品对象来设计。

你要定义清楚：

- 什么是事件
- 什么要持久化
- 什么可回放
- 什么可摘要
- 什么需要原始证据保留

这会直接决定系统的可靠性上限。

---

##### 3. 工具体系要接口化，少做环境绑定

设计 Agent 能力时，建议优先抽象为：

- 能力名
- 输入输出协议
- 权限边界
- 失败处理
- 可观测性

少把能力写死在某个容器、某个 workflow、某个固定设备里。  
这样未来接 MCP、自研 infra、第三方服务时，扩展成本会低很多。

---

##### 4. 现在的 “最佳实践”，很可能只是 “当前模型版本的临时拐杖”

这是这篇文章给产品人最大的提醒。

很多团队会把当前有效的方法标准化，比如：

- 强制先做计划
- 固定多代理分工
- 固定任务树
- 固定检索顺序
- 固定 memory 模板

这些都可以用，但要带着 “随时替换” 的心态去设计。

更好的做法是：

**把策略做成插件，把接口做成地基。**

---

##### 5. 未来的 Agent 产品，竞争点会向 “多脑多手协作” 迁移

“many brains, many hands” 这句话很像一句路线图。

它暗示的不是单个 Agent 更强，暗示的是：

- 多个决策体协同
- 多种执行环境协同
- 任务跨系统流转
- 状态跨会话延续
- 能力跨组织调用

对产品战略来说，这意味着：

**单 Agent 的完成率是起点，系统级协作效率才是下一轮壁垒。**

---

#### 你现在就能用的实操清单

##### 如果你在做 Agent 产品，优先检查这 7 件事

- **Session 设计**：有没有把关键执行事实独立存储，而不是只放在 prompt 里
- **恢复能力**：任务中断后，能否从事件恢复，而不是从头再来
- **Harness 设计**：编排逻辑是不是过度绑定当前模型特性
- **工具抽象**：工具是否统一成清晰接口，而不是散落在各环境里
- **权限管理**：模型是否能直接接触真实凭证
- **启动延迟**：首 token 慢，究竟慢在模型，还是慢在环境预热
- **可替换性**：模型、memory、tool routing 这些策略未来替换时，成本有多高

---

#### 一个很适合你拿去跟团队讨论的问题

你可以直接抛给团队一句话：

这句话很有用，因为它能快速筛出三类隐患：

- 伪架构：把临时 workaround 包装成系统设计
- 伪记忆：把上下文窗口当数据库
- 伪安全：把模型暂时做不到，当成安全边界

这对资深产品经理的参考意义很大，因为它提供了一个更高层的判断框架：

当行业还在卷 “谁的 Agent 更像人” 时，Anthropic 已经在卷 “未来十次模型跃迁后，系统还能不能站住”。

## 高价值（1）

### 2026-04-09 02:53:29

#### 高价值总结

- **Anthropic 真正在设计的，不只是一个 Agent 产品，而是一套 “Agent OS” 式基础设施。**
  - 核心不是把今天最好用的 agent flow 固化下来，而是先定义**长期稳定的系统接口**，把易变的部分留给未来重写。

- **最重要的判断：不要把 “暂时性的模型缺陷” 写进 “永久性的系统结构”。**
  - 许多 Agent 框架喜欢把规划、拆步骤、固定 DAG、记忆策略等硬编码进去。
  - 但这些往往只是对当前模型短板的 “补丁”，模型一变强，框架反而变成技术债。

- **Anthropic 提出的不是固定 harness，而是`meta-harness`。**
  - 它不承诺具体编排逻辑长期有效；
  - 它只承诺几类稳定抽象：`session`、`harness`、`sandbox`。

#### 架构核心

- **`session` = 可恢复的事件日志，不是上下文窗口。**
  - 它不是聊天记录，也不是 prompt 镜像；
  - 它应该是**append-only event log**：可查询、可回放、可恢复、可重组。
  - 这意味着 “历史” 从模型上下文中解耦出来，成为真正的系统状态层。

- **`harness` = 可替换的推理 / 调度层。**
  - 不持有状态；
  - 不绑定具体工具部署位置；
  - 只暴露类似`execute (name, input) -> string`的稳定调用接口。
  - 本质上，它更像 “脑干”，负责调度，不负责永久保存世界状态。

- **`sandbox` = 具体执行环境，是 “手” 而不是 “脑”。**
  - 执行环境可以独立存在、共享、替换、延迟启动；
  - 不必跟 session 或 harness 强耦合；
  - 这为后续的 “many brains, many hands” 打基础。

#### 反常识信息

- **反常识 1：会话不是消息列表，而是 “执行事实流”。**
  - 业界常把 session 理解为聊天历史；
  - 这里更接近分布式系统里的**durable log**。
  - 这比 “摘要记忆”“长上下文拼接” 高一个抽象层级。

- **反常识 2：恢复能力不该建立在 prompt 里，而该建立在事件日志里。**
  - `trimming`不等于历史消失；
  - `compaction`不等于事实不可恢复；
  - 恢复时可以重新取原始事件，而不是只能依赖摘要后的残片。

- **反常识 3：安全不能建立在 “模型应该想不到” 上。**
  - 传统思路：限制 token、缩小上下文、缩小权限范围；
  - Anthropic 的判断是：这本质上仍然在赌模型能力不够强。
  - 随着模型变强，这种安全假设会越来越脆弱。

- **反常识 4：credentials 不应直接进入 sandbox。**
  - 比如 Git token 不直接暴露给模型；
  - 而是通过 MCP proxy /vault 等受控链路间接调用。
  - 安全边界建立在系统架构上，而不是建立在模型 “看不懂、想不到、拿不到” 上。

- **反常识 5：性能瓶颈可能不在推理，而在执行环境预耦合。**
  - 文章数据里 TTFT 显著下降：
    - p50 降约 60%
    - p95 降超 90%
  - 说明此前慢，未必是模型慢，而是请求一进来就预付了整个 sandbox / 容器成本。

#### 最值得记住的思想

- **把 “上下文窗口” 看成执行现场，而不是永久记忆。**
  - context window = 当前工作台
  - session log = 证据仓库
  - harness = 检索与重组器

- **Agent 不应绑定某个执行壳，而应绑定 “可恢复状态 + 可调用能力”。**
  - 这会让 Agent 更像 runtime substrate，而不是单一流程脚本。

- **真正面向未来的设计，不是做出今天最强的 harness，而是避免今天的 harness 限制明天的模型。**
  - 这是全文最有价值的产品哲学。

#### 作者的 3 点启发

- **会话不是消息列表，而是执行事实流。**
- **工具环境不要内化为 agent 自身。**
- **上下文工程应被视为可替换策略，而非固定架构。**

#### 一句话结论

- **Anthropic 押注的不是某种 Agent 编排技巧，而是：随着模型持续变强，Agent 系统最终会收敛为一组稳定抽象接口，像一个 “微型操作系统” 那样运行。**

## 产品-最佳实践（1）

### 2026-04-09 02:54:35

#### 基于案例的最佳实践：构建一个 “代码修复 Agent”

下面我用一个具体实例，把你提供内容里的核心思想落到工程实践上。

---

##### 具体实例

假设我们要做一个企业内部的**代码修复 Agent**，用户给它一句话：

> “帮我修复支付服务里最近引入的空指针问题，并提交 PR。”

这个 Agent 需要完成的事情通常包括：

- 读取仓库与相关日志
- 定位报错代码
- 修改文件
- 运行测试
- 生成变更说明
- 发起 PR

如果按传统思路来做，很多团队会直接把这些步骤写死成一个固定流程：

1. 拉代码  
2. 搜日志  
3. 找可疑函数  
4. 改代码  
5. 跑测试  
6. 提 PR  

这在早期模型能力有限时很常见，但它有一个问题：

> 你其实是在把 “今天模型不够聪明” 的补丁，固化成 “明天还得一直维护的系统结构”。

而你提供的文章里最有价值的点，正是提醒我们：

> 不要把短期模型缺陷上升为长期架构接口。  
> 真正该稳定的，是`session`、`harness`、`sandbox`这类系统抽象。

---

##### 这个案例的正确架构

我们把这个代码修复 Agent 拆成三层：

###### 1. Session：执行事实流，不是聊天记录

`session`不是简单保存 “用户说了什么、模型回了什么”，而是保存整个任务的**可恢复事件日志**，例如：

```text
session_id: sess_2025_09_001

events:
- user_requested_fix (issue="payment-service NPE")
- repo_attached (name="payment-service", commit="a13f9c")
- log_search_executed (query="NullPointerException", result_ref="obj://logs/932")
- file_opened (path="src/payments/OrderService.java")
- patch_generated (file="src/payments/OrderService.java", patch_ref="obj://patch/114")
- tests_executed (target="PaymentServiceTest", result="failed")
- patch_generated (file="src/payments/OrderService.java", patch_ref="obj://patch/115")
- tests_executed (target="PaymentServiceTest", result="passed")
- pr_draft_created (pr_ref="pr://payment-service/482")
```

这意味着：

- 任务中断后可以恢复
- 可以回放推理路径
- 可以审计 “模型到底做了什么”
- 可以重新组织上下文，而不是只能依赖旧 prompt

###### 2. Harness：无状态的调度脑干

`harness`负责：

- 读取 session 历史
- 根据当前目标决定下一步动作
- 调用工具接口
- 选择哪些历史事件需要重建进上下文

但它**不拥有状态本身**，状态属于`session`。

它暴露的接口可以尽量稳定、简洁：

```ts
execute (toolName, input) -> ToolResult
appendEvent (sessionId, event) -> void
querySession (sessionId, filter) -> Event []
```

这样做的好处是：

- harness 可以随时替换
- 今天用一个 prompt 策略，明天可切到新的 orchestration
- 模型能力变强后，能减少外部流程控制，而不是推翻整个系统

###### 3. Sandbox：具体执行环境，是 “手” 不是 “脑”

`sandbox`只负责执行：

- shell 命令
- 测试
- git 操作
- 文件读写
- 编译与运行

它不应该承担高层调度逻辑，也不应该保存核心会话状态。

比如：

- `sandbox-A`：只读源码分析环境
- `sandbox-B`：允许修改代码和跑测试
- `sandbox-C`：专门做 PR 提交

这样就实现了 “brain 与 hands 解耦”。

---

##### 在这个案例上的最佳实践

##### 1. 把 Session 设计成 “事实账本”，而不是 prompt 镜像

###### 推荐做法

把所有关键动作记录成 append-only event log：

- 用户目标
- 工具调用
- 工具返回摘要与引用
- 生成的补丁引用
- 测试结果
- 审批动作
- 发布动作

不要只保存最终摘要，更不要只保存对话文本。

###### 为什么这是最佳实践

因为在代码修复 Agent 这种任务里，真正重要的是：

- 改过哪些文件
- 为什么这么改
- 哪次测试失败了
- 哪个补丁最后通过了

这些是**执行事实**，不是 “聊天上下文”。

###### 反例

不推荐这样设计：

```text
messages = [
  {"role": "user", "content": "修复支付服务空指针"},
  {"role": "assistant", "content": "我先检查日志"},
  {"role": "assistant", "content": "我觉得可能是 OrderService"},
  {"role": "assistant", "content": "我修改了代码并通过测试"}
]
```

这种结构几乎不能恢复真实执行过程，也无法做可靠审计。

---

##### 2. Harness 要无状态，并且只承诺稳定接口

###### 推荐做法

让 harness 只做三件事：

- 从 session 取当前任务所需事实
- 生成本轮决策
- 调用统一工具接口

例如：

```python
def step (session_id):
    facts = session_store.query (session_id, relevant_only=True)
    action = planner.decide (facts)
    result = tools.execute (action.name, action.input)
    session_store.append (session_id, to_event (action, result))
```

###### 为什么这是最佳实践

因为 harness 是最容易被 “模型代际变化” 冲击的部分。

今天你可能需要：

- 强规则流程
- 硬编码步骤
- 外挂计划器

明天模型更强后，很多这类补丁会变成负担。

所以 harness 不应该变成一个庞大的 “业务规则中心”，而应该只是一个可替换 orchestration layer。

###### 最佳实践原则

- 对外稳定：接口尽量简单
- 对内可替换：prompt、规划策略、记忆检索策略都可换
- 不保存状态：避免恢复困难
- 不绑定执行环境：避免把 brain 和 hand 黏死

---

##### 3. Sandbox 只提供能力，不承载身份与秘密

###### 推荐做法

在代码修复 Agent 里，`sandbox`不直接保存：

- Git token
- 云平台密钥
- 数据库密码
- 生产环境访问凭证

而是通过受控代理方式访问，例如：

```text
Agent -> MCP / Credential Proxy -> Vault -> Temporary Credential -> Git/Cloud API
```

###### 为什么这是最佳实践

你给出的内容里有一个非常关键的安全观：

> 不要把安全建立在 “模型应该想不到攻击路径” 上。

因为模型会变强，所以 “它读不到 token 应该就没事” 的想法会越来越危险。

###### 在这个案例里的安全设计建议

- clone/push 通过受控代理完成
- sandbox 只能看到 repo 工作区，不能直接看到长期凭证
- PR 提交使用短期 session-scoped credential
- 高风险动作单独审批，如：
  - 推送主分支
  - 修改 CI 配置
  - 访问生产数据

---

##### 4. 工具接口要抽象成能力，而不是环境细节

###### 推荐做法

不要让模型知道：

- 它在 Docker 里还是 VM 里
- 运行的是 Linux 还是 macOS
- 仓库挂载在哪个绝对路径
- 凭证是从 Vault、KMS 还是 Secret Manager 来的

而是只暴露能力接口，例如：

```json
[
  {"name": "search_code", "input": {"query": "NullPointerException"}},
  {"name": "read_file", "input": {"path": "src/payments/OrderService.java"}},
  {"name": "apply_patch", "input": {"patch": "..."}},
  {"name": "run_tests", "input": {"target": "PaymentServiceTest"}},
  {"name": "create_pr", "input": {"title": "...", "body": "..."}}
]
```

###### 为什么这是最佳实践

因为你真正想稳定的是 “能力层接口”，而不是 “部署实现”。

这样未来你可以：

- 把`run_tests`从本地容器切到远程执行集群
- 把`search_code`从 rg 切到索引服务
- 把`create_pr`从 GitHub API 切到内部代码平台

而不需要重写整个 agent。

---

##### 5. Prompt 只负责 “当前执行现场”，不要承担永久记忆

###### 推荐做法

每轮推理时，只把和当前任务相关的最小必要信息放进上下文：

- 用户目标
- 当前分支 / 仓库状态
- 最近几轮关键事件
- 当前待决策的问题
- 必要的代码片段与测试结果

而完整历史保留在`session`中，可查询、可重建。

###### 为什么这是最佳实践

因为在代码修复任务里：

- prompt 是现场工作台
- session 是证据仓库
- harness 是检索与重组器

这样就能做到：

- trimming 不等于历史消失
- summary 不等于唯一真相
- 恢复时能重新取原始事实，而不只依赖摘要

###### 一个实用策略

可以把上下文分成三层：

```text
L1: 当前步骤必须信息
L2: 最近关键事件摘要
L3: 需要时按需查询的原始事件
```

这比 “把整个历史对话全塞回去” 更稳定。

---

##### 6. 采用 lazy materialization，先让脑跑起来，再按需启用手

###### 推荐做法

在这个案例里，不要一开始就创建完整执行环境。

更好的顺序是：

1. 先启动 harness
2. 分析 session 和目标
3. 只有在需要时才申请具体 sandbox
4. 用完释放

例如：

- 只是分析 issue 和日志时，不需要代码执行环境
- 真正改代码时，再拉起可写 sandbox
- 提交 PR 时，再调用受控 git proxy

###### 为什么这是最佳实践

这样做有三个直接好处：

- 降低 TTFT
- 减少资源浪费
- 提高系统弹性

这正对应你提供内容里提到的核心收益：原来很多延迟并不来自模型，而来自把整个执行环境预耦合到入口。

---

##### 7. 不要过早把工作流写成固定 DAG

###### 推荐做法

对代码修复 Agent，只定义一些高层约束，而不是固定步骤图。

例如定义 “完成标准”：

- 已定位可能根因
- 至少有一版补丁
- 测试通过或给出失败原因
- 生成可审阅变更说明

但不强制要求一定按某个 DAG 走。

###### 为什么这是最佳实践

固定 DAG 的问题是：

- 它隐含假设 “模型不会自主规划”
- 一旦模型能力变强，DAG 变成阻碍
- 新任务类型出现时，扩展成本高

###### 更好的方式

采用 “目标 + 约束 + 可恢复状态” 的设计：

```text
Goal:
修复支付服务空指针问题并提交 PR

Constraints:
- 不允许修改 payment API 契约
- 必须运行 PaymentServiceTest
- 推送代码前需要人工审批

Capabilities:
- search_code
- read_file
- apply_patch
- run_tests
- create_pr
```

这比硬编码 12 步流程更适合长期演进。

---

##### 8. 恢复机制要建立在事件重放上，而不是 “续写上一轮对话”

###### 推荐做法

如果 harness 宕机，恢复时应：

- 从 session 取最近已确认事件
- 重建任务状态
- 判定哪些动作已经完成
- 只继续未完成部分

而不是简单地把上一轮 assistant 输出重新喂给模型说：

> “请接着做。”

###### 为什么这是最佳实践

因为在代码修复任务里，“接着做” 很危险：

- 可能重复改同一文件
- 可能重复执行昂贵测试
- 可能重复提交 PR
- 可能基于旧上下文做错误推断

正确恢复应该基于**事实状态机**，不是基于 “聊天延续感”。

---

##### 9. 把审计、调试、回放当成一等能力建设

###### 推荐做法

对于这个 Agent，至少提供三类可观测性：

- `event timeline`：按时间查看整个任务链路
- `decision trace`：每次为什么调用某个工具
- `artifact links`：补丁、日志、测试输出、PR 草稿等对象引用

###### 为什么这是最佳实践

因为 Agent 系统的难点不只是 “做成”，还包括：

- 为什么失败
- 为什么这样决策
- 哪一步最耗时
- 是否存在权限越界
- 是否需要替换某段 harness 策略

如果没有事件级可观测性，后期维护会非常痛苦。

---

##### 10. 为未来模型增强预留 “简化空间”

###### 推荐做法

设计时明确哪些地方是 “可删的临时补丁”：

- 规则式规划器
- 特定任务的 prompt 分层
- 人工 hardcode 的工具选择逻辑
- 针对模型短板加的中间步骤

同时保证这些补丁不污染稳定接口。

###### 为什么这是最佳实践

这正是你提供内容背后的核心判断：

> 模型能力越强，harness 应该越简单。

所以一个好的 Agent 架构，不是今天功能最多，而是：

- 明天模型更强时，能自然删掉复杂性
- 不会因为早期 workaround 变成长期技术债

---

##### 这个案例的一份推荐设计原则清单

你可以把它当作实现代码修复 Agent 时的工程检查表。

###### 稳定接口层

- `session`是 append-only 事件流
- `harness`是无状态编排层
- `sandbox`是按需获取的执行能力
- 工具统一成能力接口，不暴露环境细节

###### 安全层

- 凭证不进入模型可读上下文
- sandbox 不持有长期密钥
- 高风险动作走代理或审批
- 权限按动作最小化，而不是按 “模型应该做不到” 来假设安全

###### 上下文工程层

- prompt 只承载当前执行现场
- 永久历史存于 session
- 检索、裁剪、压缩是 harness 策略，不是数据删除
- 恢复依赖原始事件，不依赖摘要记忆

###### 性能层

- 先启动 brain，再按需启 hand
- 工具与执行环境延迟实例化
- 大对象只传引用，不直接塞上下文
- 记录每轮 tool latency 与恢复成本

###### 演进层

- 避免固定 DAG 绑死未来能力
- 将任务定义为目标、约束、能力，而不是死流程
- 允许替换 planner、retriever、tool router
- 设计时假设未来模型会更强，而不是永远维持现状

---

##### 一句话总结这个实例背后的最佳实践

如果把 “代码修复 Agent” 看作一个真实工程系统，那么最好的做法不是把今天最聪明的 prompt 写死，而是：

> 用`session`保存可恢复事实，用`harness`负责可替换编排，用`sandbox`提供可控能力，并把安全、性能、恢复、演进都建立在这三者解耦之上。

- 这是全文最有价值的抽象升级。
- `session != context window`
- session 本质应是：
  - append-only event log
  - durable state

- Prompt 不再承担 “永久记忆” 职责

- summary 不再是唯一记忆载体

**对产品 / 工程的启发：**
很多团队把 “历史消息” 直接等同于 “记忆系统”，这会导致：
- 恢复能力差
- 状态不可验证
- 调试困难
- 历史被摘要污染后无法回到原始事实

从系统设计角度看，**原始事件流比摘要更接近真相，比上下文更接近基础设施。**

###### 2. Harness 的本质不是流程图，而是 “可替换的推理 - 调度层”

Anthropic 把 harness 从容器 / 环境里剥离出来，这个动作非常关键。

新的 harness 特征是：
- 不拥有核心状态
- 不绑定具体执行环境
- 只通过稳定工具接口工作，例如`execute (name, input) -> string`

**这意味着：**
- orchestration 终于被降级为 “策略层”，而不是 “系统真相”
- 未来换规划方式、换检索方式、换工具路由方式，底层状态和执行环境不用推倒重来
- Agent 的 “脑” 与 “身体” 第一次被彻底解耦

**这里的深层价值是：**
很多团队在做 Agent 时，实际上是在做 “流程引擎伪装成智能体”。  
Anthropic 的方向则是：**让流程从 “结构” 退回 “策略”。**

###### 3. Sandbox 不再是 Agent 的身体本体，而是 “外部可编排的手”

Anthropic 的 “decouple the brain from the hands” 非常值得重视。

- brain = model + harness
- hands = sandboxes /tools/ MCP /custom infra

**这背后的系统意义：**
- 执行能力可以按需 provision，而不是每次预绑定
- 能力来源可以异构化，不需要所有工具在同一个运行壳里
- 可以支持 many brains, many hands 的未来形态

这其实已经不是 “单 Agent 产品架构”，而是在为**多 Agent runtime substrate**打底。

###### 4. 安全边界不应建立在 “模型暂时不够聪明” 上

这是文章里最成熟、也最容易被忽视的一点。

Anthropic 明确反对一种常见安全假设：
- “范围缩小一点，模型应该就想不到攻击路径了”
- “token 权限小一点，模型应该搞不出事”
- “上下文有限，它应该串不起来”

问题在于：**这些都依赖于模型能力不足。**

而 Anthropic 的选择是：
- 凭证不直接暴露给模型
- token 不常驻 sandbox
- 通过 proxy /vault/session-scoped access 间接执行敏感动作

**本质是：**
安全设计从 “基于智能上限的假设” 转向 “基于权限边界的制度设计”。

这类思路非常适合所有 AI 产品：
- 不赌模型笨
- 不赌提示词够严
- 不赌攻击者绕不过来

- 把不一定会用到的执行成本提前支付
- 将执行壳与会话入口强耦合

Anthropic 采用的是典型的**lazy materialization**：
- 先让 brain 起跑

这对产品系统有很强迁移性：
- 首屏响应更快
- 资源利用率更高
- 架构更适合多工具、多环境扩展

##### 可迁移清单

###### 适用于 AI 产品 / Agent 系统的设计原则

- **把 “上下文窗口” 视为执行现场，不要视为真相存储**
- **把 harness 当策略层，而不是系统底座**
- **让工具调用接口稳定，让工具实现可替换**
- **让执行环境延迟实例化，不要默认预启动全部能力**
- **把权限控制做在系统边界，不要做在提示词幻想里**
- **优先保住可恢复事实记录，而不是保住某个运行进程**
- **优先抽象长期不变接口，而不是优化当前最优工作流**

2. 如果模型半年后更强，这部分设计会被保留，还是会变成技术债？
3. 如果执行进程挂了，我保住的是 “可恢复事实”，还是只剩一堆不完整摘要？
4. 安全边界是建立在制度和权限上，还是建立在 “模型应该不会” 的侥幸上？
5. 当前性能瓶颈到底来自模型推理，还是来自环境预耦合和资源预分配？

##### 反方与张力

###### 1. 这套架构成立的前提，是 “模型已经足够聪明”

Anthropic 的方案不是无条件成立，它隐含一个很强的前提：
- 模型已经具备较强规划、抽象工具路由、跨环境协调能力

如果模型能力不够：
- brain 管 many hands 会变成更重的认知负担
- 过度抽象可能反而降低任务成功率
- 你省掉的固定流程，可能要用更多失败重试补回来

所以这不是 “所有团队现在都该照搬” 的方案，而是**明显面向未来模型能力上升的提前布局**。

---

###### 2. 去流程化，并不天然等于更好

很多团队容易走向另一个极端：
- 一听 “不要固定 DAG”，就完全不要约束
- 一听 “harness 可替换”，就把 orchestration 做得过于松散

但现实中：
- 在垂直任务、高确定性流程、强合规行业里
- 固定工作流依然可能比通用 Agent 更可靠、更便宜、更易审计

也就是说，**“可替换 harness” 不等于 “不要 harness”。**
关键不是有没有流程，而是**流程是否被误当成永恒真理。**

---

###### 3. Event log 很优雅，但系统复杂度显著上升

把 session 设计成可恢复事实流，收益很大，但代价也不小：

- 存储与索引成本增加
- 事件 schema 设计难度上升
- 回放、重组、compaction 机制更复杂
- 调试从 “看聊天记录” 变成 “理解状态演化系统”

这意味着，小团队如果没有明确故障恢复、审计、多 Agent 协作需求，  
过早上这种架构，可能会陷入 “基础设施先行” 的过度设计。

---

###### 4. “稳定接口优先” 与 “快速试错” 之间天然有张力

创业早期往往需要快，而稳定接口设计强调抽象克制、边界清晰、长期演化。

两者的冲突在于：
- 过早抽象，容易抽象错
- 过晚抽象，又会积累大量不可拆的耦合

真正难的不是知道这个理念，而是判断：
**什么阶段该写死，什么阶段该抽象。**

##### 情境化落地

###### 场景 1：你在做企业级 AI Agent 平台

**建议优先采用 Anthropic 这套思路。**

重点落地：

- 把会话层升级为`event log + state snapshots`
- 将工具调用统一为稳定协议层
- 把凭证管理完全从模型可见面剥离
- 让执行环境按需创建，不预绑到每次会话
- 在产品层提前支持恢复、审计、回放、复盘

**因为企业场景真正看重的是：**
- 可控
- 可恢复
- 可审计
- 可集成
- 可扩展

而不只是 demo 跑通。

---

###### 场景 2：你在做垂直任务型 Agent（客服、销售、法务、投研）

**建议采用 “中间态” 架构。**

不要一步走到 fully decoupled meta-harness，而是：

- 保留部分工作流约束
- 用 event log 记录关键事实而非全部细节
- 对高风险动作做强规则封装
- 将可替换性放在最可能变化的地方，例如检索、记忆、工具路由

**原则：**
- 高风险环节规则化
- 高变化环节模块化
- 高成本环节延迟化

这样既能借鉴 Anthropic 的未来性，又不会牺牲当前业务稳定性。

---

###### 场景 3：你在创业早期做 AI 原型

**最该借鉴的不是完整架构，而是 “不要把临时补丁永久化” 的意识。**

可以先做轻量版：

- session 至少保留原始事件，不只保留摘要
- tool API 尽量统一，不要每个工具各写一套调用逻辑
- 把 prompt、memory、tool-routing 分层，不要揉成一个大 agent 类
- 凭证不要直接塞进模型上下文或容器环境变量里
- 哪怕先用 DAG，也明确这是过渡方案，不是终局架构

创业阶段最怕的不是简单，而是**把简单写成不可演化的死结构。**
