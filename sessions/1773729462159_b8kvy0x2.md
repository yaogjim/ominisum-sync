## 结构化（1）

### 2026-03-17 06:41:13

这篇内容的主旨是：作者用 `Tmux` 搭了一个最小可运行的多 Agent 协作框架，让 `Claude` 负责统筹、多个 `Codex` 分工执行，结果发现这种方式在简单实现下就已经“又快又好”。核心观点不是一开始追求完美，而是先把可跑通的协作闭环搭起来，再逐步升级。

- 第一部分：作者的核心发现
  - 作者认为 `Claude Pro` 套餐额度“不够用”，而 `Codex` 数量更多，且执行任务“漂亮又干净”。
  - 基于这个观察，他尝试让 `Claude` 做“大脑”，把多个 `Codex` 组织成一个协作团队。
  - 重点不是单个模型能力，而是通过分工提升整体效率。

- 第二部分：具体实现方式
  - 作者基于 `Tmux` 做了一个简单的 `TUI` 可视化 Agent Team。
  - 协作流程是：`Claude` 先做方案，再同时拉起 3 个 `Codex` 分别承担不同角色：
    - `tester`：测试
    - `coder`：编码
    - `reviewer`：评审
  - 这种分工在“简单实现”的情况下，已经表现出“又快又好”的效果。

- 第三部分：当前进展与下一步计划
  - 作者表示目前已经“跑通了最简单的框架”。
  - 接下来准备继续升级整个协作系统，让协同效果更好，并探索它的能力上限。
  - 后续还计划产出“保姆级教程”，说明这套方法会进一步产品化、教程化。

- 第四部分：作者提炼出的关键价值
  - 作者明确指出，最有价值的地方是：
    - 先跑通简单框架
    - 再持续升级优化
  - 也就是说，先验证“能不能协作起来”，再优化“协作得有多好”。

- 第五部分：评论区补充出的关键观点
  - `Allen Cao` 提到，核心在于把 `context` 的管控权放回用户/开发者手里。
  - 他举例说，自己做过 `handoff-session` 的 skill，本质思路类似：通过控制上下文和 session 现场，实现不同 `session`、`agent` 甚至不同设备之间的快速交接与协作。
  - `Dang` 则进一步总结，这条路的价值不在于一开始追求“完美协作”，而是先建立最小可运行的分工框架，例如：
    - 谁负责拆解
    - 谁负责实现
    - 谁负责测试
    - 谁负责 review
  - 一旦这个闭环跑通，后续优化重点就转向：
    - 吞吐量
    - 上下文切分
    - 角色边界
  - 他还强调：对独立开发者来说，这比单纯堆模型额度更重要。
