## 分析要点

- **核心高价值点**：Agent 记忆的核心不应只是存储历史对话，而应从执行过程里提炼可复用的行为策略和技能。
- **留存建议**：长期保留（文章提供了较完整的 Agent 长期记忆实践案例，包含 trace、policy、skill 的演化思路和本地记忆系统架构，适合作为后续研究 Agent Memory 与个人工作流自动化的参考。）

**知识要点**

- 传统 Agent 记忆方案多依赖对话存储与向量检索，容易出现信噪比低、记忆扁平、无法从错误中归纳策略等问题。
- MemOS 的 Reflect2Evolve 思路是将对话沉淀为 trace，再归纳为 policy，最后结晶为可复用 skill。
- 高频重复任务更容易形成稳定记忆和技能，单次偏好不一定会被立即固化。
- 本地记忆系统可结合 SQLite、FTS5、向量检索、RRF、MMR、时间衰减和 LLM 过滤提升记忆检索质量。
- 多 Agent 共享同一套记忆核心，可以避免切换工具导致记忆资产归零。

**行动项**

- 尝试安装 MemOS Local Plugin，并用一个高频任务测试 trace 到 skill 的沉淀效果。
- 将当前手写在 CLAUDE.md 中的固定规则区分为显性规则、可学习偏好和可沉淀技能。
- 设计至少两个跨 session 测试任务，验证 Agent 是否能在不重复提示的情况下调用历史经验。
- 观察 Viewer 中的 memory、experience、skill 和 support 数量，判断哪些任务值得长期训练。
- 对比现有 RAG 记忆方案，重点评估其是否具备策略归纳、版本演化和上下文区分能力。

**Yanhua**

### 这应该是目前最接近正解的 Agent 记忆方案

我在 CLAUDE.md 里写了 200 多行规则，就为了让 Agent 记住我是谁。

写作口吻、排版禁忌、配图风格，全靠我一条条手写进去，虽然每次开新 session，这些规则都在。但这不是 Agent 的记忆，这是我手写的说明书。

说明书是死的：我写下"不用破折号"，Agent 就不用。但它不知道为什么不用，不知道我纠正过它几次，不知道这个规则背后是"我觉得破折号让中文失去节奏感"这个判断。

我的 Agent 在执行规则，但它没有学会规则。

#### 现有的记忆方案，大部分在做“搜旧聊天”

这个问题不是没人注意到，ChatGPT 有 memory，Claude 有 project knowledge，市面上也有各种第三方记忆插件。

但仔细看，它们做的事情差不多：把你过去的对话或者你手动标记的信息存起来，建一个向量索引，下次聊的时候检索相关段落塞回 context。

能用，但有几个绕不开的问题。

第一，存的是原始对话，信噪比很低。你三个月前和 AI 闲扯的一段话被检索出来，模型得自己判断哪些有用，经常判断错。

第二，记忆是扁平的。所有信息平等存储，没有"这条比那条重要""这个结论已经被更新过"的层次。用得越久，噪音越多。

第三，不会从错误中学习。你纠正过 AI 十次同样的问题，它的"记忆"里有十条纠正记录，但没有归纳出"以后别再这样做"这个策略。

这些方案解决了"存"的问题，但没解决"学"的问题。

#### 装了 MemOS 的本地插件之后，Hermes 告诉我的一件事

装完 MemOS Local Plugin 之后，我问 Hermes："你现在记忆是保存在哪里的？"

它给了一个很清楚的回答：

![Image](https://pbs.twimg.com/media/HJib4obagAABbWd?format=jpg&name=large)

两条线：内置 memory 存在本地 JSON 文件里，是我主动告诉它的东西：名字、角色、偏好、写作规则。MemOS 是另一套独立的长期记忆系统，从对话中自动提取 trace（事件轨迹）、policy（行为规则）、world\_model（环境知识），然后把成熟的流程结晶成可调用的 skill。

Hermes 自己的总结比我解释得好："内置 memory 是我主动存的显性记事贴，MemOS 是后台自动学习积累的隐形记忆。"

这就是 MemOS 和上面那些方案最大的区别。它不是帮你存对话，它从你做事的过程里自动提炼策略。

MemOS 管这套叫 Reflect2Evolve。对话先沉淀为 trace，有价值的 trace 归纳成 policy（行为策略），成熟的 policy 再结晶为可复用的 skill。不是"记住你说过什么"，是"从你做事的过程里提炼出下次怎么做"。

#### 实测一：教它写推文

第一轮，我告诉 Hermes 我写 X 推文的习惯：不用破折号，开头直接抛观点不铺垫，要有活人感，不能有 AI 味，然后让它写一条关于 Context Engineering 的推文。

![Image](https://pbs.twimg.com/media/HJicShXasAA7MbY?format=jpg&name=large)

它写完之后，我纠正了一次："这个开头太平了，换一个更锐利的钩子。我的推文习惯是第一句就抛观点或抛冲突，不要铺垫。"

它立刻改了，第一句变成"暴论：Prompt Engineering 被高估了。"然后还回了一句："第一句就是观点，不留铺垫。"

![Image](https://pbs.twimg.com/media/HJiclQrbIAAEoNo?format=jpg&name=large)

到这里为止，和大部分 AI 助手没什么区别。真正的测试是下一步。

退出 Hermes。开新 session。这次我只说了一句话：

"帮我写一条 X 推文，主题是'Claude Code 的 CLAUDE.md 本质上是在做 Context Engineering'。"

没有重复任何偏好。没有提醒它我是谁。

然后我看到了这个：

![Image](https://pbs.twimg.com/media/HJict5rbcAALuBI?format=jpg&name=large)

它在写之前做了四件事：

1. 自动加载了一个叫 x-content-writing 的 skill
2. 使用 memos\_search 搜索了"X 写作风格上下文工程"，耗时 4.7 秒
3. 搜了 memos\_environment，找到我的 Obsidian vault 路径
4. 去我的 vault 里读了我之前实际发布过的 X 文章，摸节奏

然后它说："好，来写。读完你最近的 X 文章，摸一下节奏，直接开写。"

写出来的是这个：

> CLAUDE.md 不是配置。是 Context Engineering。每往里面写一行，你就在设计模型的上下文窗口。项目结构、编码偏好、红线禁忌，全是手工注入的工作记忆。Prompt 管"这次干什么"。CLAUDE.md 管"你是谁"。后端出身应该秒懂。微服务启动先拉注册中心配置，知道自己跟哪些服务打交道。CLAUDE.md 就是 Agent 的注册中心。每次 session 先读一遍，再干活。

零破折号，第一句直接抛观点，后端类比自然带出，没有"一文读懂"式的开头。

这不是它简单记住了我说过不用破折号，它从我的执行过程和已发布的文章里，提炼出了一套写作策略，然后在一个全新的 session 里自动应用。

这次我确实觉得和之前用的记忆方案不一样。

#### 实测二：做两个产品页，看风格有没有跨项目迁移

换一个更有分量的任务。

第一轮，我让 Hermes 给 ReddTrends（

www.reddtrends.com）做产品介绍页，明确要求：奶油白底配暖色、文案直接不要"赋能""一站式"、布局简洁、独立开发者感觉。它做出来之后我又纠正了 CTA 按钮的文案。

![Image](https://pbs.twimg.com/media/HJic493akAAGw4g?format=jpg&name=large)

然后退出，开一个新 session，让它给另一个产品 MoleUninstaller 做介绍页，只给了产品名和功能描述，不给任何风格指示。

![Image](https://pbs.twimg.com/media/HJidG8-akAEaqy6?format=jpg&name=large)

结果：MoleUninstaller 的页面走了一个完全不同的方向：深色底，英文主标题，橙色强调色，和 ReddTrends 的暖色独立开发者风格完全不同。

风格偏好没有跨项目迁移过来。

这说明 MemOS 的记忆不是简单的"用户上次说了奶油白底，以后都用奶油白底"，它会区分任务上下文。但反过来说，如果你期望它记住"我做所有产品页都用暖色系"，目前还做不到，这个粒度的偏好学习可能需要更多轮的积累。

#### 打开 Viewer，看看它学到了什么

跑完两轮实测之后，Viewer 里的数据变化很明显：

![Image](https://pbs.twimg.com/media/HJidd-ObkAE-iEV?format=jpg&name=large)

从最初的全零，到现在 47 条记忆、8 个任务、24 条经验（12 条已启用）、2 个技能、1 条环境认知。全部自动生成。

经验页里最有意思的几条：

![Image](https://pbs.twimg.com/media/HJidru6awAEk17u?format=jpg&name=large)

"Convert WeChat Official Account article to Xiaohongshu format"，support 25，已启用。这条经验被触发了 25 次，说明 MemOS 从我反复做的公众号转小红书任务里归纳出了策略。

"修改文件后通过浏览器导航验证""验证页面修改后无控制台错误"，这两条是做产品页时自动提炼出来的工程习惯。

技能页也有变化：

![Image](https://pbs.twimg.com/media/HJidxQubUAAOo39?format=jpg&name=large)

check\_obsidian\_vault\_path\_env 从 V1 升级到了 V2，support 从 1 变成 2。MemOS 在第二次遇到类似任务时，自动升级了技能版本。这就是 Reflect2Evolve 里"Evolve"的意思：技能不是一成不变的，用得越多越成熟。

三个模型各司其职：本地 Xenova 做 embedding（免费），DeepSeek V4 Flash 做摘要（便宜），DeepSeek V4 Pro 做技能进化（只在需要强推理时调用），贵的模型只用在刀刃上。

所有数据存在本机 SQLite，Viewer 只监听本地，零云依赖。做过 RAG 的可以看一眼检索管线：FTS5 全文 + 向量混合，过 RRF 融合排序、MMR 去重、14 天半衰期时间衰减，再过 LLM 过滤，这比"embedding + cosine similarity"复杂一个量级，但检索质量才是记忆有没有用的分水岭。

![Image](https://pbs.twimg.com/media/HJieAMKbYAAVgCR?format=jpg&name=large)

#### 一份核心，多 Agent 共用

还有一个设计值得提。OpenClaw 和 Hermes 共享同一套 Reflect2Evolve 核心，只是适配器不同。你在 Hermes 里积累的经验和技能，算法层面和 OpenClaw 是通的，记忆资产不会因为切换工具归零。

#### 用下来的真实感受

最让我意外的不仅仅是它记住了我的偏好，还有在第二个 session 里，它写推文之前自己跑了一串动作：加载 skill，搜索记忆，找到我的 vault，读我之前发过的文章，然后跟我说"读完你最近的文章，摸一下节奏"。

我当时的反应是：这不对啊，我没让你去读我的旧文章。

但它自己判断这件事该做，这个感觉和“帮我搜一下上次聊过什么”完全不同。

产品页那边就没这么惊喜了，ReddTrends 的暖色风格没有迁移到 MoleUninstaller 上。想想也合理，风格偏好只出现过一次，MemOS 的经验需要 support 次数积累才会固化成策略，一次不够。

所以目前的状态是：高频重复的任务效果很明显，偶发的偏好还不稳定。但方向我觉得没问题，我写了半年 CLAUDE.md，越写越觉得这活不该是人干的。

##### 一、深度总结

文章核心观点：

> 真正的 Agent 记忆，不应该只是“存下过去说过什么”，而应该能从用户的行为、纠正和任务过程中，自动提炼出可复用的策略。

作者认为，当前很多 AI 记忆方案本质上只是：

- 保存旧对话
- 建向量索引
- 下次检索相关内容
- 塞回上下文

这类方案解决的是“存储”，不是“学习”。

---

##### 二、作者认为传统记忆的问题

###### 1. 信噪比低

旧聊天里有大量无关内容，模型很难判断哪些真正重要。

###### 2. 记忆是扁平的

所有信息差不多平等存放，缺少重要性、优先级、更新关系。

###### 3. 不会从错误中学习

用户纠正 AI 十次，系统可能只是存下十条纠正记录，但不会总结出：

> 以后遇到类似任务，应该避免这个问题。

---

##### 三、MemOS 的关键不同

MemOS 不是简单保存对话，而是把对话和任务过程转化为三类东西：

| 类型 | 含义 |
|---|---|
| trace | 事件轨迹，记录发生了什么 |
| policy | 行为策略，总结以后该怎么做 |
| world_model | 环境知识，理解用户的工作环境 |
| skill | 成熟技能，可在未来任务中自动调用 |

它的机制叫：

> Reflect2Evolve  
> 反思并进化

简单说就是：

```text
对话经历 → 提炼经验 → 形成策略 → 固化技能 → 下次自动调用
```

这和普通 RAG 记忆的区别在于：

```text
普通记忆：记住你说过什么
MemOS：学会你通常怎么做
```

##### 五、技术设计亮点

作者提到 MemOS 的几个关键设计：

###### 1. 本地存储

所有数据存在本机 SQLite，隐私更可控。

###### 2. 混合检索

- FTS5 全文搜索

这让记忆检索质量更高。

不同任务用不同模型：

| 模型 | 作用 |

Hermes 和 OpenClaw 可以共享同一套记忆核心。

这意味着用户积累的经验不会因为换工具而清零。

#### 六、深入浅出解读

##### 这篇文章真正想说什么？

一句话：

> 好的 Agent 记忆，不该像聊天记录，而该像一个越来越懂你的助理。

普通 AI 的“记忆”像一个仓库：

```text
你说过什么，我都存起来。
下次需要时，我翻一翻。
```

但 MemOS 更像一个实习生逐渐成长：

```text
你怎么改稿，我记住。
你讨厌什么风格，我总结。
你反复做什么任务，我形成流程。
下次我主动按你的习惯来。
```

---

##### 为什么 CLAUDE.md 不够？

CLAUDE.md 本质上是用户手写说明书。

比如你写：

```text
不要用破折号。
```

Agent 会执行，但它不知道背后的原因。

而真正的记忆应该知道：

```text
用户不喜欢破折号，因为他觉得这会破坏中文节奏。
过去几次修改里，他都要求去掉破折号。
所以以后中文写作中默认避免。
```

区别是：

```text
规则执行 ≠ 习惯理解
```

---

##### 为什么“从错误中学习”很重要？

因为人与 AI 长期协作时，最烦的是重复纠错。

如果你每次都要说：

- 这个开头太平
- 不要 AI 腔
- 不要破折号
- CTA 文案太虚
- 页面改完要检查控制台

那 AI 其实没有成长。

真正有用的 Agent 应该做到：

> 被纠正一次，记住倾向；  
> 被纠正多次，形成策略；  
> 重复出现，固化技能。

#### 七、辩证思考

##### 1. MemOS 的方向是对的

它把记忆从“信息存储”推进到了“经验学习”。

这是 Agent 走向真正长期协作的关键。

未来 AI 助手的核心竞争力，很可能不是模型多聪明，而是：

> 它是否能在长期共事中越来越懂你。

---

##### 2. 但它还不是完美记忆

目前看，它对高频任务效果好，对低频偏好不稳定。

这其实合理。

如果一个偏好只出现一次，系统不应该立刻全局套用，否则会产生误判。

比如：

```text
这次产品页用暖色
```

不等于：

```text
我所有产品页都要用暖色
```

好的记忆系统必须在两者之间做判断。

这也是难点。

---

##### 3. 自动学习有价值，也有风险

Agent 主动读取旧文章、搜索 vault、调用技能，确实更像“聪明助理”。

但也带来问题：

- 它什么时候该主动行动？
- 它是否越权读取了资料？
- 用户是否清楚它调用了哪些记忆？
- 错误经验被固化后怎么办？
- 记忆能不能被编辑、撤销、降权？

记忆越强，越需要透明和可控。

---

##### 4. 记忆不是越多越好

真正重要的不是“存得多”，而是：

```text
知道什么该记
知道什么该忘
知道什么只在当前项目有效
知道什么是全局偏好
知道什么已经过期
```

所以 Agent 记忆的核心不是数据库，而是判断力。

---

#### 八、最终判断

MemOS 代表了一条更接近正确答案的路线：

```text
从保存对话 → 到提炼经验
从检索信息 → 到形成策略
从被动执行 → 到主动进化
```

但它仍处在早期阶段。

它最适合：

- 高频写作任务
- 固定工作流
- 长期项目协作
- 有明显纠错反馈的场景

暂时不适合期待它一次就理解所有深层偏好。

---

#### 九、一句话结论

> Agent 的好记忆，不是记住你说过的话，而是学会你做事的方式。

##### 2. 高价值信息深挖

##### 2.1 当前多数记忆方案的问题：解决了“存”，没解决“学”

文章对现有 AI memory 的批评很关键：

###### 问题一：原始对话信噪比低

很多系统只是把历史聊天存进去，再用向量检索找回来。

但问题是，过去聊天里有大量：

- 临时想法；
- 试错内容；
- 已经过时的判断；
- 随口表达；
- 和当前任务无关的信息。

如果系统只是把这些东西塞回 context，Agent 需要自己判断哪些有用。判断错了，记忆反而变成污染源。

###### 问题二：记忆是扁平的

普通记忆系统里，“一次闲聊”和“反复确认过的核心偏好”可能权重差不多。

但真实的人类偏好是有层级的：

- 有些是临时要求；
- 有些是项目级规则；
- 有些是用户长期偏好；
- 有些是已经被废弃的旧规则；
- 有些是反复出现后才应该固化的经验。

如果没有层级，记忆越多，系统越乱。

###### 问题三：不会从错误中归纳策略

最重要的是，普通 memory 可能会记住：

> 用户第 1 次说不要这样写。  
> 用户第 2 次说不要这样写。  
> 用户第 3 次说不要这样写。

但它不一定能归纳成：

> 以后写这类内容时，默认避开这种表达方式。

这就是“记录纠错”和“学习纠错”的区别。

---

##### 2.2 MemOS 的关键机制：Trace → Policy → Skill

文章里最有价值的概念是 MemOS 的 Reflect2Evolve：

```text
对话 / 行为过程
      ↓
Trace：事件轨迹
      ↓
Policy：行为策略
      ↓
Skill：可复用技能
```

这套机制的关键是，它不只是把内容存下来，而是把任务过程抽象成更高层级的经验。

###### Trace：发生过什么

例如：

- 用户要求写 X 推文；
- 用户强调不要破折号；
- 用户纠正开头太平；
- 用户要求第一句直接抛观点；
- Agent 修改后用户认可。

这是过程记录。

###### Policy：以后类似任务该怎么做

从多次 Trace 里，系统可能归纳出：

- 写 X 推文时，开头要直接给观点或冲突；
- 避免 AI 味；
- 不用破折号；
- 不要铺垫；
- 优先使用类比和具体场景。

这是行为策略。

###### Skill：可以被主动调用的能力

当策略足够成熟，就可以变成技能，比如：

- `x-content-writing`
- `convert-wechat-to-xiaohongshu`
- `check-obsidian-vault-path-env`
- `product-page-validation`

这时 Agent 不再只是“记得某些规则”，而是能够在任务开始前主动加载相关技能。

这一步非常关键，因为它意味着记忆从“被动检索”变成了“主动工作流”。

##### 3.1 如果你在做 Agent 产品，可以迁移这套记忆分层

不要只设计一个 memory 表。可以考虑分成：

| 层级 | 含义 | 示例 |
|---|---|---|
| Raw Event | 原始事件 | 用户纠正了一次文案 |
| Trace | 任务轨迹 | 一次完整的写推文流程 |
| Preference | 偏好 | 不喜欢破折号 |
| Policy | 策略 | X 推文第一句直接给观点或冲突 |
| Skill | 技能 | 自动生成符合用户风格的 X 推文 |
| Environment | 环境知识 | 用户 Obsidian vault 路径、项目目录 |
| Deprecated Memory | 废弃记忆 | 用户过去喜欢但现在不用的风格 |

关键不是“记得越多越好”，而是要让记忆能被升级、降权、废弃和版本化。

##### 3.2 判断一条记忆是否应该固化，可以看这几个信号

###### 记忆固化判断清单

一条信息是否应该从临时记忆升级为长期策略，可以看：

- 是否重复出现多次；
- 是否被用户明确纠正过；
- 是否跨任务出现；
- 是否带来更高质量输出；
- 是否被用户确认或接受；
- 是否有稳定语境；
- 是否和已有策略冲突；
- 是否存在过期风险。

例如：

```text
用户说一次“这次用奶油白底”
→ 项目级临时偏好，不应泛化。

用户多次在不同产品页中要求“奶油白底、暖色、独立开发者感”
→ 可以升级为用户级设计偏好。

用户多次纠正“不要用赋能、一站式”
→ 可以固化为长期文案禁忌。
```

##### 3.4 可以迁移到个人 AI 工作流的实践

如果你是个人开发者、内容创作者或产品负责人，可以这样做：

###### 第一步：减少手写大段静态规则

`CLAUDE.md`、custom instructions、project knowledge 仍然有用，但不要试图把所有东西都写死。

更好的做法是：

- 静态规则只写高优先级原则；
- 可迭代偏好交给记忆系统学习；
- 高频流程沉淀成技能；
- 项目级规则和用户级规则分开。

###### 第二步：刻意制造可学习反馈

如果你希望 Agent 学会你的风格，不要只说“写得不好”。

要给可归纳反馈：

```text
不好：这版不像我。

更好：这个开头太铺垫了。我的 X 推文习惯是第一句直接抛观点或冲突，不要先解释背景。

更好：这个文案有 AI 味，尤其是“赋能”“一站式”“重塑”这些词。以后做独立开发者产品页时默认避开。
```

###### 第三步：区分“一次性要求”和“长期偏好”

你可以明确告诉 Agent：

```text
这只是当前项目要求，不要迁移到其他项目。
```

或：

```text
这是我的长期偏好，以后类似任务都默认遵守。
```

这能显著降低错误泛化。

##### 4. 反方与张力

这篇内容很乐观，但里面也有一些值得警惕的地方。

---

##### 4.1 主动读取旧内容：方便还是越界？

作者提到 Agent 主动读取了他的 Obsidian vault 里的旧 X 文章来摸节奏。

这很惊喜，但也带来一个问题：

> Agent 是否应该在用户没有明确要求时，主动访问私人资料？

这取决于权限设计。

如果系统默认允许访问 vault，那么行为上没错。但产品体验上，用户可能会有类似作者的反应：

> 我没让你去读旧文章啊。

这里存在一个重要张力：

| 主动性 | 安全感 |
|---|---|
| Agent 越主动，越像真正的助手 | Agent 越主动，越可能让人感到越界 |
| 自动补全上下文，提高质量 | 自动访问资料，可能引发隐私担忧 |
| 少问用户，效率高 | 多问用户，控制感强 |

更好的设计可能是：

```text
我准备读取你最近 5 篇 X 文章来校准风格，是否继续？
```

或者设置权限等级：

- 永不自动读取；
- 任务相关时可读取；
- 读取前询问；
- 完全信任，自动执行。

---

##### 4.2 记忆越强，错误固化风险越高

如果 Agent 把错误经验也总结成 policy，就会变得更难纠正。

例如：

- 用户某次临时要求“语气夸张一点”；
- Agent 错误总结为“用户喜欢夸张标题”；
- 以后所有内容都变得浮夸。

所以长期记忆系统必须支持：

- 记忆审查；
- 记忆删除；
- 策略降权；
- 版本回滚；
- 冲突检测；
- 用户显式确认。

没有治理机制的记忆系统，后期可能会从“智能”变成“固执”。

---

##### 4.3 高频任务效果好，低频偏好效果不稳定

作者也承认：

> 高频重复任务效果明显，偶发偏好还不稳定。

这非常关键。

MemOS 这类系统最适合：

- 内容转写；
- 代码检查；
- 产品页生成；
- 固定发布流程；
- 客服 SOP；
- 数据分析模板；
- 周报生成；
- 设计 QA；
- 重复运营任务。

但对低频、模糊、一次性、强创意任务，记忆学习未必稳定。

例如：

- 一年做一次品牌重塑；
- 偶尔写一篇特殊风格文章；
- 临时换一个设计方向；
- 某个项目刻意不同于过去风格。

这时如果 Agent 过度依赖过去经验，反而会限制创造力。

##### 4.4 “最接近正解”不等于“已经正解”

文章标题说“最接近正解”，这个判断可以接受，但还需要保留谨慎。

一个成熟 Agent 记忆系统至少要解决：

1. 记忆从哪里来；
2. 记忆如何抽象；
3. 记忆如何验证；
4. 记忆如何过期；
5. 记忆如何冲突解决；
6. 记忆如何跨 Agent 迁移；
7. 记忆如何被用户审计；
8. 记忆如何避免隐私风险；
9. 记忆如何避免越权行动；
10. 记忆如何判断该不该泛化。

MemOS 解决了其中一部分，尤其是“从 trace 到 policy 到 skill”的方向。但完整答案还包括权限、治理、审计和可解释性。

### 2026-09-18 00:56:38

#### Agent 记忆的关键，不是保存更多，而是把经历编译成策略

文章最有价值的地方，不是证明 MemOS 已经是“正解”，而是把 Agent 记忆问题重新定义了：**真正有用的记忆，不只是找回过去的信息，而是让过去的纠正改变未来的行为。**

CLAUDE.md 代表显式规则，传统 RAG 代表对历史对话的检索。两者都能补充上下文，却不会自然完成从“发生过什么”到“以后该怎么做”的转换。MemOS 提出的 trace → policy → skill，则试图加入这一层：先记录任务轨迹，再归纳行为策略，最后把稳定策略固化成可调用技能。它更像把经验逐步“编译”为程序，而不是扩建聊天档案馆。

##### 真正困难的是归纳，而不是存储

推文测试体现了这种设计的吸引力。用户只纠正过一次开头方式，下一次新会话中，Agent 不仅检索偏好，还主动读取已发布文章、加载写作技能，再生成结果。这意味着记忆开始参与任务规划，而非仅作为背景材料被动注入。

但这仍只是一个案例，不能证明系统真的“学会了”。结果可能来自已保存规则，也可能主要来自临时模仿 Obsidian 中的文章；没有基线对照，也没有测试面对冲突样本、新主题和多次更新时是否稳定。因此，文章提供的是一个值得验证的架构方向，而不是充分的效果证据。

更准确地说，**Agent 是否拥有记忆，要看它能否减少重复纠正，同时避免把旧经验错误迁移到新任务。**“记得越多”甚至可能更差：过期结论、偶然偏好和错误操作一旦固化为 skill，影响会比检索出一段无关聊天更深。

##### 偏好必须有作用域，出现次数不能替代判断

两个产品页没有沿用同一种视觉风格，是文章里很重要的反例。它可能说明系统理解了项目差异，也可能只是相关记忆没有被召回，单次测试无法区分。真正需要解决的是记忆作用域：一条偏好究竟属于用户全局、某类任务、某个项目，还是某次交付？

“support 次数高就固化”只能作为弱信号。高频不等于正确：用户可能连续修补同一个错误，项目约束也可能被误判成长期偏好。成熟系统还需要记录来源、适用条件、反例、更新时间和置信度，并允许用户查看、修改、降级和回滚。否则，自动学习只是把手写规则的维护成本，换成更隐蔽的错误累积。

##### 记忆一旦能驱动行动，就成为权限系统

Agent 主动读取本地 vault 带来了惊喜，也暴露了另一面：当记忆能够触发工具、访问文件并升级技能，它管理的已不只是知识，而是行为权限。本地 SQLite 和零云依赖降低了数据外泄风险，却没有解决最小权限、错误调用、提示注入和技能污染。

因此，这类产品真正的竞争点不会是“存了多少条记忆”，而是四项能力：**归纳是否准确、作用域是否清楚、错误能否撤销、行动是否可审计。**更合理的评测指标也应是重复纠正率、错误迁移率、任务成功率，以及额外延迟和成本，而不是记忆或技能数量。

MemOS 展示了一个可信的方向：Agent 记忆正在从资料库走向持续学习的控制层。但越接近“会自己学”，记忆治理就越不是附属功能，而是产品本身。
