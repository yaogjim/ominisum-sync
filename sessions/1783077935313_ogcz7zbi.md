## 分析要点

- **核心高价值点**：将AI用于重构前的系统化问题梳理和可视化报告生成，而不是直接全自动改代码。
- **留存建议**：短期参考后可删除

**知识要点**

- 大型代码重构中，全自动AI改代码容易引入兼容逻辑或隐性问题，半自动流程更可靠。
- 可通过指定目标、架构分析skill和问题数量，让AI生成结构化重构问题清单。

**行动项**

- 在重构项目前先让AI生成按位置、问题、方案、优先级分类的问题清单。
- 对AI生成的重构建议进行人工review后再选择性实施。
- 尝试将长文档或问题清单转为可视化报告以提高阅读和决策效率。

**海拉鲁编程客**

最近使用 Kimi Code + K2.7 极速版辅助编码，分享一下使用体验。

背景: 来自大约 5w 行左右的 golang agent runtime 的重构。前期用 codex / cc 疯狂推代码之后进入了重构期。

用 codex / cc 压低代码行数，很难满足我想要的效果。比如 opus 4.8 反复背诵不知道从哪里学来的超过 300 行代码是不好的设计（我明明没有加这一条，记忆里面也没有），而超过 2000 行不能拆开的代码多了去了，这是本质复杂度。而 codex 在精简了一些之后反手又给我加了一些兼容代码。。。。

所以我回归了半自动的方案，用 kimi code 调研出报告，人工 review 之后开修，大致步骤如下

1\. 选择一个切入点

/goal 请你使用 hai-architecture skill 帮我系统整理 nil, 按照当前代码，当前位置，问题点，解决方案表格罗列一下。 有些可能是 nil 本身过度防御，有的地方可能是设计上有更好的方向。请你系统梳理之后，整理到 docs/architecture/nil-review.md ，要详细，分好类和优先级，整 50个点给我

使用 /goal 是为了确保能捞 50 个点，使用 hai-architecture 是为了打开格局，看看是不是有些 nil 是不是因为更上层的设计问题。

2\. 50个点的 markdown 看起来还是比较吃力的。可以做个简单的可视化优化一下咱们的阅读体验。

/skill:hai-visual-report docs/architecture/nil-review.md 做一下可视化

然后你就得到一个阅读体验比较好的问题清单，然后挑选一些问题开修就好了。

这里不得不吹一句，K2.7 极速版是真的快，两分钟可视化跑完（视频未加速），调研的时候没感觉有非常大的速度提升，到可视化报告这块速度很快，有明显的推背感。好处就是产出高了，坏处就是刷推少了。。。。。

## 解读（1）

### 2026-07-03 11:24:43

##### 一、深度总结

作者分享了用 **Kimi Code + K2.7 极速版** 辅助重构一个约 **5 万行 Go agent runtime 项目** 的经验。

核心观点：

> AI 写代码容易，AI 做大型重构很难；真正有效的方式不是全自动改代码，而是“AI 调研 + 人工判断 + 半自动修复”。

###### 1. 背景

项目已经经过一轮 Codex / Claude Code 等工具疯狂推代码，进入重构阶段。

但作者发现：

- **Codex / Claude Code 擅长生成代码**
- 但在复杂项目重构中，经常难以真正压缩复杂度
- 模型会机械遵循某些“经验规则”，比如：
  - “超过 300 行代码不好”
  - 但现实中有些 2000 行代码是因为业务本身复杂，不能简单拆
- 有些工具在精简代码后，又会加回大量兼容逻辑，导致复杂度反弹

所以作者放弃“让 AI 自动大改”，转向更稳的方式。

---

##### 二、作者的方法

###### 第一步：让 AI 做系统调研

作者让 Kimi Code 找出代码中与 `nil` 相关的问题：

```text
请系统整理 nil：
当前位置、问题点、解决方案
分类、优先级
整理 50 个点到文档
```

这里有两个关键：

- 用 `/goal`：确保 AI 真的产出足够多的问题点
- 用 `hai-architecture skill`：不是只看局部 bug，而是从架构层面看问题

作者关注的不只是：

> 这里有没有 nil panic？

而是进一步问：

> 为什么这里需要这么多 nil 防御？是不是架构设计有问题？

---

###### 第二步：把报告可视化

50 个问题点的 Markdown 文档不好读，于是作者继续让 Kimi Code 做可视化报告：

```text
/skill:hai-visual-report docs/architecture/nil-review.md 做一下可视化
```

结果得到一个更易读的问题清单。

然后作者再人工挑选值得修的问题，开始重构。

---

##### 三、深入浅出解读

这篇内容真正有价值的地方，不是“某个模型很快”，而是展示了一种更成熟的 AI 编程工作流。

###### 以前的用法

很多人这样用 AI：

```text
帮我重构这段代码
帮我优化这个文件
帮我改完整个模块
```

问题是：

- AI 可能理解不完整
- 改动范围太大
- 容易引入隐性 bug
- 看似代码变少了，实际风险变高了

---

###### 作者的用法

作者把 AI 当成：

> 架构助理 + 代码审计员 + 报告生成器

流程变成：

```text
AI 扫描问题
↓
AI 分类整理
↓
AI 可视化报告
↓
人类 review
↓
再决定怎么改
```

这比直接让 AI 重构更可靠。

因为大型系统里，很多复杂度不是“代码写得烂”，而是：

- 历史包袱
- 业务规则
- 兼容逻辑
- 并发状态
- 接口边界
- 架构欠债

这些东西 AI 不一定能直接判断，但 AI 很适合先帮人“把问题摊开”。

---

##### 四、关键洞察

###### 1. 大型重构不是简单删代码

代码行数少，不代表架构好。

有些代码可以删，有些代码不能删。

真正的问题是：

> 哪些复杂度是偶然复杂度，哪些复杂度是本质复杂度？

AI 经常分不清这一点。

---

###### 2. AI 更适合先做“问题发现”

相比直接修改代码，AI 更适合：

- 找重复逻辑
- 找 nil 防御过度的位置
- 找异常处理不一致的地方
- 找架构边界混乱处
- 总结问题模式
- 生成 review 报告

也就是说：

> 先让 AI 看病，再由人决定怎么治。

---

###### 3. 速度会改变工作方式

作者特别提到 K2.7 极速版很快。

快的意义不只是“省时间”，而是会改变节奏：

- 慢模型：一次任务要等很久，不敢频繁试错
- 快模型：可以快速生成报告、迭代视角、调整问题清单

速度越快，AI 越像实时协作者。

---

##### 五、辩证思考

###### 1. AI 编程不是越自动越好

全自动重构听起来很美，但风险很高。

尤其是 5 万行以上、有历史包袱的系统，AI 一口气大改，很可能：

- 破坏隐含约定
- 加入无用兼容代码
- 拆散本来合理的复杂逻辑
- 制造更隐蔽的问题

所以更现实的路线是：

> 小步快跑，人类掌舵，AI 执行和辅助判断。

---

###### 2. 速度重要，但不能替代判断

K2.7 极速版的速度是优势。

但在重构中，真正的瓶颈不只是生成速度，而是：

- 问题是否判断准确
- 优先级是否合理
- 改动是否安全
- 架构方向是否正确

快可以提高产出，但如果方向错了，也只是更快地产生问题。

---

###### 3. AI 的价值正在从“写代码”转向“理解代码”

过去大家关注：

> AI 能不能帮我写函数？

现在更关键的是：

> AI 能不能帮我理解一个复杂系统？

对于成熟项目来说，读代码、找问题、建文档、辅助决策，可能比写新代码更值钱。

---

##### 六、一句话结论

这篇分享的重点不是“Kimi 很快”，而是：

> 大型代码重构中，AI 最好的位置不是替你全自动改代码，而是帮你系统发现问题、组织信息、提升 review 效率；最终架构判断仍然要由人负责。

##### 主旨概括

作者分享了在一个约 **5 万行 Golang agent runtime 重构项目**中，使用 **Kimi Code + K2.7 极速版**辅助编码的体验：相比让 AI 全自动改代码，作者更倾向于“AI 调研出报告 + 人工 review + 再动手修改”的半自动重构方式。

---

##### 1. 使用背景：大型 Golang 项目进入重构期

- 作者正在重构一个约 **5w 行代码**的 **Golang agent runtime** 项目。

- 现在项目进入重构阶段，重点从“写更多代码”转向“压缩、整理、优化代码结构”。

---

##### 2. 全自动重构效果不理想

作者提到，直接让 Codex / Claude Code 帮忙减少代码行数，并不能达到理想效果：

- **Opus 4.8** 会反复强调“超过 300 行代码是不好的设计”，但作者认为：
  - 这条规则并不是自己设定的；
  - 也不在记忆里；

简而言之：  
> AI 全自动压缩代码容易机械套规则，甚至引入新的复杂度。

---

##### 3. 改用半自动方案：AI 调研，人类决策

作者最终回到“半自动”的重构方式：

1. 让 **Kimi Code** 先进行系统调研；
2. 输出问题报告；
3. 人工 review 后再决定怎么修改。

这样做的好处是：  
- AI 负责大范围扫描和整理问题；
- 人类负责判断优先级、确认设计方向；
- 避免 AI 直接大改代码带来隐性 bug。

---

##### 4. 第一步：选择切入点，让 AI 梳理 nil 问题

作者举了一个具体例子：从 `nil` 问题入手，让 Kimi Code 系统整理代码中的相关问题。


关键目的：

- 使用 `/goal`：确保 AI 能尽量挖出 **50 个问题点**；
- 使用 `hai-architecture skill`：不是只看局部代码，而是从更高层架构角度判断：
  - 哪些 `nil` 是过度防御；
  - 哪些是设计问题导致的；
  - 哪些可以通过更好的架构方向解决。

作者认为，50 个问题点的 Markdown 文档读起来仍然比较吃力，于是又让 AI 做可视化报告：

作者的核心经验是：

- 对于高复杂度、大规模代码重构，不建议完全交给 AI 自动修改；
- 更可靠的方式是：
  - AI 做调研、分类、报告和可视化；
