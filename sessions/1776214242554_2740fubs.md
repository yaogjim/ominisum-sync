**海拉鲁编程客**

继续分享一些 harness engineering 实际经验

坦白说，在做 haicode (一个我自用的 coding agent) 的过程中，我通过 Harness 方案借鉴了 Claude Code 的不少优秀设计。虽然功能复刻个七七八八，但整体使用体验始终不如 CC 丝滑，比如有的任务执行很顺，有的任务执行就不收敛。

我今天静下心来想了下，只有功能点对齐是不够的，必须深入对齐其底层机制，正好 k2.6-code 发布，跑通了一套“四步对齐法”，效果我觉得还行，分享一下希望对你有帮助。

haicode 目前有接近 10w 行 golang，要对齐 CC 50w 行ts，确实有点困难。通过人眼来对齐肯定是没什么可能性了，看不过来。

所以需要引入文档作为中间层来对齐，我选择的是 PRD 做事实层面的对齐。分四步走

第一步：PRD 宏观对齐（Gap Analysis）

Prompt 示例：「请帮我比对当前项目与上游 Claude Code 的源码，找出我们在架构和体验上还有哪些差距？重点关注 Agent Loop、上下文管理、Agent Teams 等核心模块。请将不完善的地方拆解成独立的 PRD，并输出到 docs/product-specs 目录中」

需要注意的是，不需要像我一样说的很规范，现在 k2.6 之类的国模都比较聪明，在实际使用的过程中可以用语音说很长的一些废话，意思到位，最后确保放入对应目录中就行了。

第二步：PRD 细化与反思（Deep Dive &amp; Questioning）

要求模型在 PRD 中明确标注“当前实现”与“上游实现”的具体差距（Delta），客观评价当前做得好的与不好的地方。

「请基于这里的 PRD结合上游源码，评价当前做得好的与不好的地方，提出你在分析过程中遇到的‘开放式问题’（例如设计意图、edge case）来问我。」

第三步：PRD 细化与反思（Deep Dive &amp; Questioning）

使用提示词：「对于你刚才提出的开放式问题，请你直接从上游 Claude Code 的代码库中寻找答案，并补充到 PRD 中」

这时候再进行人工审核。Harness 开发中 80% 的常规逻辑模型能快速搞定，但剩下 20% 决定体验的核心逻辑，必须依赖我们把 PRD 抠得足够细。

有的朋友可能会问我为啥咱不一步到位，把三步 PRD 生成的提示词写在一起？因为效果不好。精细一些的活，分开一步一步来效果比较可控。

第四步：转化执行计划（Actionable Plan）  
「请将所有梳理出的差距和 PRD 改写成具体的执行计划（Execution Plan），并放入 docs/exec-plans 目录」

然后就把 plan 目录拖到终端，让他开始干活。在 claude code 中每次干活时间还挺长的（ 没有调优的情况下，我看一个 todo 能干超过 30\~40min）

因为是每个月 199 的套餐，最终我验收了两个 plan，效果还不错。

但 cc + kimi 也有一些不爽的地方，估计 claude code 有 bug，有的时候给我弹 API Error: Claude Code is unable to respond to this request

另外在调试 haicode 这种智能体上面，我还用了其他的模型 GLM 5.1 / GPT 5.4 / Opus，我的感觉是模型

GLM 5.1, 比较稳扎稳打：在连带智能体调试的体验上还不错，不会乱飞。

GPT 5.4 / Codex (容易过度设计)：它有一种“工程兜底”的强迫症。有时候会情不自禁地发明一些超出 Claude Code 原本路线的解法，比如居然想用关键词来做意图检测，反而把简单问题复杂化了。

Opus 4.6 agent 调试agent最强：在代码拆解和逻辑洞察上的表现应该是最好的， 能够连带 提示词 + 工程一起改，效果最好，但但但但我分析了两天之后 5x 订阅掉了（不知道是相关性还是因果性）......血亏🤣

## 通俗精炼（2）

### 2026-04-15 00:50:42

#### 用 PRD 做中间层，把 Coding Agent 的 “功能对齐” 升级为 “体验对齐”

##### 核心观点

作者在做自用 coding agent `haicode`时发现：**仅仅把 Claude Code 的功能 “复刻出来” 还不够，真正决定体验的是底层机制是否对齐**。  
因此，他提出了一套更可落地的方法：**以 PRD 作为中间层，先做认知对齐，再做执行落地**。

##### 方法框架：四步对齐法

###### 1. 宏观对齐：先找差距
先让模型对比当前项目和上游系统源码，重点看`Agent Loop`、上下文管理、`Agent Teams`等核心模块，输出差距分析，并拆成独立 PRD。

**重点**：不是直接改代码，而是先形成结构化认知。

###### 2. 深入细化：把 “差多少” 说清楚
要求模型在 PRD 中明确写出：
- 当前实现是什么
- 上游实现是什么
- 两者具体差距（Delta）是什么
- 哪些地方做得好，哪些地方不足

这一步的价值是：**从 “感觉不像” 变成 “能明确指出哪里不像”**。

###### 3. 追问补全：让模型继续查证
针对分析中出现的开放式问题，比如设计意图、边界情况，再让模型直接回到上游代码库寻找答案，并补充回 PRD。

**作者强调**：这类精细工作不能一口气做完，拆步骤执行，效果更可控。

###### 4. 转成执行计划：从文档到落地
最后把所有 PRD 改写成具体的`Execution Plan`，放入执行目录，再交给 agent 实施。

本质上是把流程变成：

**源码理解 → PRD 对齐 → 差距澄清 → 执行计划 → 自动开发**

##### 作者的关键判断

###### 1. 80% 靠模型，20% 靠人把细节抠清
作者认为，Harness 开发中大部分常规逻辑模型都能快速完成；但真正影响体验的那 20%，往往是最难、最关键的部分，必须靠人把 PRD 打磨得足够细。

###### 2. 方法论有效，但前提是 “看得懂”
评论区也指出一个现实问题：  
**真正的瓶颈，往往不是有没有方法，而是你是否真的理解上游系统的设计意图。**

也就是说，这套方法适合有一定代码理解能力、产品抽象能力的人使用，否则 PRD 很容易变成 “自说自话”。

##### 对不同模型的实战感受

###### GLM 5.1：稳
优点是稳扎稳打，调试智能体时不容易 “乱飞”，适合工程推进。

###### GPT 5.4 / Codex：容易过度设计
优点是有较强的工程兜底意识；  
缺点是有时会引入不必要的复杂方案，把简单问题做重。

###### Opus 4.6：洞察最强
在代码拆解、逻辑分析、提示词与工程联动修改方面表现最好，适合高强度 agent 调试。  
但成本较高，持续使用代价明显。

##### 最值得借鉴的启发

###### 1. 不要直接对齐代码，要先对齐 “认知层”
PRD 在这里不是传统产品文档，而是**源码理解和工程执行之间的桥梁**。

###### 2. 复杂问题不要一步到位
越精细的任务，越适合拆成多个阶段，让模型逐步收敛，而不是一次性生成 “大而全” 答案。

###### 3. Agent 体验的核心，不在功能数量，而在机制质量
真正拉开差距的，往往不是 “有没有这个功能”，而是：
- 上下文怎么组织
- 任务怎么收敛
- 资源怎么分配
- 边界情况怎么处理

##### 一句话总结

这篇文章的本质不是在讲 “怎么抄 Claude Code”，而是在讲：  
**做 coding agent 时，真正有效的路径不是功能模仿，而是借助 PRD 把上游设计意图、系统差距和执行方案逐层对齐，最终把 “像不像” 变成 “为什么像、哪里不像、怎么补上”。**

#### 四步法做 Coding Agent 对齐

##### 核心观点

作者在开发自己的 coding agent `haicode` 时发现：**只复刻功能点不够，关键是对齐底层机制**。  
真正影响体验的，不是“有没有这个功能”，而是 Agent Loop、上下文管理、协作机制等底层设计是否一致。

---

##### 方法总结：四步 PRD 对齐法

###### 1. 先做宏观差距分析
先把自己的项目和上游产品（如 Claude Code）做整体对比，重点看核心模块差距。  
然后把这些差距拆成独立 PRD，作为后续改进的基础。

###### 2. 深挖差距，明确好坏
要求模型在 PRD 里写清楚：
- 当前实现是什么
- 上游实现是什么
- 二者差距在哪里

同时让模型提出分析中没想明白的开放问题，比如设计意图、边界情况。

###### 3. 让模型回源码里找答案
针对前一步提出的问题，不急着人工拍脑袋判断，而是让模型继续去上游代码库里找依据，再补回 PRD。  
之后再进行人工审核。

###### 4. 把 PRD 转成执行计划
最后把所有差距和 PRD，改写成可落地的 Execution Plan，直接交给 agent 执行。  
作者认为：**复杂工作分步骤做，比一口气生成全部内容更可控，效果也更好。**

###### 体验差异主要来自“最后 20%”

这部分必须依赖足够细的 PRD，不能只靠模糊描述。

###### 文档是人和代码之间的“中间层”
面对几十万行代码，靠人工逐行对齐几乎不现实。  
因此需要引入 PRD 作为事实对齐层，把“理解代码”转成“理解产品设计与差距”。

## 结构化（1）

### 2026-04-20 00:56:58

#### 主旨概括

这篇内容主要分享了作者在开发自用 coding agent `haicode` 时，总结出的一套“**四步 PRD 对齐法**”，用于向 Claude Code 的底层机制靠拢，而不只是表面功能复刻。核心观点是：**要想真正提升 agent 体验，关键不在功能点堆砌，而在于通过 PRD 把架构差距、设计意图和执行计划逐层拆清楚。**

##### 1. 背景：为什么需要“对齐底层机制”

- 作者在做 `haicode` 时，借鉴了 Claude Code 的不少 Harness 设计。
- 虽然很多功能已经“复刻得七七八八”，但实际体验仍然不稳定：
  - 有些任务执行得很顺；
  - 有些任务却“不收敛”，体验不如 Claude Code 丝滑。
- 作者反思后认为，**只对齐功能点不够，必须进一步对齐底层机制**。
- 现实难点在于代码规模差异很大：
  - `haicode` 目前约 **10 万行 Go**
  - Claude Code 约 **50 万行 TypeScript**
- 因此，靠人工逐行比对几乎不现实，必须引入一个“中间层”来帮助对齐，作者选择的是 **PRD（产品需求文档）**。

##### 2. 方法总览：用 PRD 作为中间层，分四步推进

- 作者提出了一套“**四步对齐法**”，核心思路是：
  - 先从宏观上找差距；
  - 再深入分析差距背后的原因；
  - 然后补齐开放问题；
  - 最后转成可执行计划。
- 这种方式的好处是：
  - 避免直接硬啃大规模源码；
  - 让模型围绕“事实层面的文档”工作，而不是凭感觉发挥；
  - 提高分析和执行的可控性。

##### 3. 第一步：PRD 宏观对齐（Gap Analysis）

- 第一步的目标是：**先找出当前项目与 Claude Code 在架构和体验上的核心差距**。
- 作者给出的提示词重点关注这些模块：
  - `Agent Loop`
  - 上下文管理
  - `Agent Teams`
- 输出要求是：**把每个不完善的点拆成独立 PRD，放到 `docs/product-specs` 目录**。
- 作者特别提到一个实践经验：
  - 不一定要把提示词写得非常正式；
  - 现在像 `k2.6` 这类模型已经足够聪明；
  - 实际中即使用语音说一大段“废话”，只要意思表达清楚、并指定好输出目录，也能工作。

##### 4. 第二步：PRD 细化与反思（Deep Dive & Questioning）

- 第二步要求模型在 PRD 中明确写清：
  - **当前实现**
  - **上游实现**
  - 两者之间的具体差距（`Delta`）
- 同时还要客观评价：
  - 当前哪些地方做得好；
  - 哪些地方做得不好。
- 更重要的是，作者要求模型主动提出“**开放式问题**”，例如：
  - 上游的设计意图是什么；
  - 某些 `edge case` 是怎么处理的。
- 这一步的意义在于：
  - 不只是“列差距”；
  - 而是逼着模型把理解盲区暴露出来，方便后续追问。

##### 5. 第三步：继续补齐开放问题，再人工审核

- 第三步本质上是承接第二步：
  - 对刚才提出的开放式问题，
  - 让模型**直接去上游 Claude Code 代码库里找答案**，
  - 然后回填到 PRD 中。
- 做完这一步后，再进行**人工审核**。
- 作者强调了一个很关键的判断：
  - Harness 开发中，**80% 的常规逻辑**，模型可以很快搞定；
  - 但决定最终体验的，往往是剩下那 **20% 的核心逻辑**。
- 这些关键部分不能只靠模型自动生成，必须把 PRD 抠得足够细。
- 作者还解释了为什么不把前三步合并成一个大提示词：
  - 因为“一步到位”的效果不好；
  - 这种精细活，**拆成多步更可控**。

##### 6. 第四步：把差距转成执行计划（Actionable Plan）

- 最后一步是把前面整理出的差距和 PRD，统一改写成**执行计划（Execution Plan）**。
- 输出目录是：`docs/exec-plans`
- 接着，作者会把 `plan` 目录直接拖到终端，让 Claude Code 开始干活。
- 从实际体验看：
  - 在 Claude Code 中，单次任务执行时间可能很长；
  - **在未调优情况下，一个 todo 能跑 30~40 分钟以上**。
- 成本方面，作者提到 Claude Code 是 **每月 199 美元套餐**。
- 实际结果上，作者最后验收了 **两个 plan**，并认为效果“还不错”。

##### 7. 使用过程中的问题与不足

- 作者也提到了一些实际使用的不爽点：
  - `Claude Code + kimi` 的组合并不总是稳定；
  - Claude Code 疑似存在 bug；
  - 有时会直接报错：
    - `API Error: Claude Code is unable to respond to this request`
- 这说明即便方法论有效，**工具链本身的稳定性依然会影响体验**。

##### 8. 不同模型在 agent 调试中的主观体验对比

作者还比较了多种模型在“调试智能体”场景下的表现：

###### GLM 5.1：稳扎稳打

- 作者认为 `GLM 5.1` 的特点是比较稳。
- 优点是：
  - 在“连带智能体调试”的场景里表现不错；
  - 不容易乱飞，比较踏实。

###### GPT 5.4 / Codex：容易过度设计

- 作者认为 `GPT 5.4 / Codex` 有一种“**工程兜底**”倾向。
- 表现为：
  - 容易主动发明一些超出 Claude Code 原始路线的方案；
  - 把本来简单的问题复杂化。
- 具体例子：
  - 居然会想用“**关键词做意图检测**”；
  - 这种做法偏离了原本的对齐目标。

###### Opus 4.6：调 agent 最强，但成本高

- 作者对 `Opus 4.6` 的评价最高：
  - 在代码拆解和逻辑洞察上表现最好；
  - 能同时修改**提示词 + 工程实现**，综合效果最佳。
- 但缺点也很明显：
  - 作者分析了两天后，**5x 订阅额度就用完了**；
  - 因此直呼“血亏”。
- 也就是说，Opus 虽强，但**性价比未必适合长期高强度使用**。

##### 9. 评论区补充：真正难点不只是方法论

- 热门回复中，有人认可“四步 PRD 对齐法”的方向是对的。
- 但也指出一个现实问题：
  - **90% 的人可能会卡在第一步**；
  - 因为“宏观对齐”本身就要求你先理解 **50 万行代码背后的设计意图**。
- 这条评论强调：
  - 真正瓶颈不只是方法论；
  - 更是**阅读理解能力**，对人如此，对 AI 也是。
- 另一个回复补充了 Harness 的几个核心难点：
  1. 目标到底是什么；
  2. 如何产出有效信息喂给 Agent 做评估；
  3. 如何在有限资源下使用 `context`、`tool call` 和并发。
- 还有人问 Go 生态里是否有合适框架，作者回复说：
  - TUI 用的是 `bubbletea`
  - 其他大部分内容是**自己造轮子**，或问 AI 有什么库可用。

##### 10. 文章可提炼出的核心启发

- **不要只对齐表层功能，要对齐底层机制。**
- **PRD 是源码对齐的有效中间层**，能把“看不懂的大工程”转成结构化问题。
- **复杂分析任务适合分步做，不适合一口气做完。**
- 在 agent / harness 工程里：
  - 常规部分可以交给模型；
  - 但体验关键点仍需要人把问题定义得足够细。
- 模型能力虽重要，但**稳定性、成本、可控性**同样重要。
