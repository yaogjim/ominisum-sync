## 正文

**Abhijith Neil Abraham**

停止使用 Docker 来沙箱化 AI 代理。

大多数人正在保护错误的东西。

Docker 和开发容器去除了很多使代理有用的特性。身份验证必须转发，API 密钥最终出现在环境变量中，更新意味着重新构建镜像，而且所有内容仍然共享同一个内核。

虚拟机提供更强的隔离性，但每个任务都要从零开始。你会失去机器上的本地上下文，并且每次都要付出冷启动的代价。

firejail 和 seccomp 提供帮助，直到代理需要安装软件包、运行构建工具，或者执行任何不在精心筛选的系统调用列表中的操作。

然后还有审批提示。它们适用于单个代理。一旦你有十个代理并行运行，每个人最终都会点击“允许全部”并继续他们的日常工作。

所有这些方法背后的假设是代理需要沙箱。

我认为代码需要沙箱。

代理是你选择、配置、认证并连接到的工具。风险部分是五秒钟前刚生成的模型生成的 Shell 命令。该命令可能包含漏洞、提示注入或某种完全恶意的内容。

Temenos ( [https://github.com/vitalops/temenos…](https://github.com/vitalops/temenos) ) 在那个边界处恰好分割系统。

代理驻留在主机上，能够访问认证、MCP 服务器、更新和模型 API。

执行在一个无 root 权限的 gVisor 沙箱内进行，该沙箱带有自己的用户空间内核。主机文件系统仅在你显式挂载的位置出现。网络访问可以通过一个标志关闭。

分离由工具链本身强制实施。

Claude 启动时不具备 Bash、Read、Write、Edit 或任何其他能直接接触主机的工具。模型可用的执行路径需经过沙箱。

这意味着扩展到代理集群，而无需陷入审批对话框中。

\`\`\`  
pip 安装 "temenos\[all\]"  
cd \~/code/my-repo  
Temenos Claude  
\`\` ⁠

信任代理

包含它生成的代码

其他一切都会自然地从中得出。

## 解读（1）

### 2026-06-10 02:55:52

#### 深度总结

这篇内容的核心观点是：

> **不要把 AI 代理本身关进沙箱，真正该隔离的是它生成并执行的代码。**

作者认为，常见方案都有问题：

| 方案 | 问题 |
|---|---|
| Docker / Dev Container | 认证、API Key、主机上下文处理麻烦；仍共享宿主机内核 |
| 虚拟机 | 隔离强，但冷启动慢，丢失本地开发上下文 |
| firejail /seccomp | 适合限制简单命令，但复杂构建、安装包时容易失效 |
| 人工审批弹窗 | 单代理可用，多代理并行时会沦为 “全部允许” |

作者提出的新边界是：

```text
信任 AI 代理本身
不信任它刚生成的代码和命令
```

Temenos 的做法是：

- AI 代理运行在宿主机上  
  - 可以访问认证信息
  - 可以连接 MCP 服务
  - 可以使用模型 API
  - 可以保持本地上下文
- 代码执行放进**无 root 权限的 gVisor 沙箱**
  - 有独立用户空间内核
  - 默认看不到宿主机文件系统
  - 文件访问必须显式挂载
  - 网络可关闭
- 工具链强制隔离  
  - Claude 默认没有直接操作宿主机的 Bash、Read、Write、Edit 权限
  - 所有执行路径都必须经过沙箱

一句话：

> **代理留在主机，代码关进笼子。**

---

#### 深入浅出解读

可以把 AI 代理想象成一个程序员助理。

传统做法是：

> 把 “助理本人” 关进一个隔离房间。

问题是，助理要工作就需要：

- 登录权限
- 项目文件
- 开发环境
- API 密钥
- 工具链
- 本地上下文

把它关太死，它就不好用了；放太开，又不安全。

作者的思路是换个角度：

> 助理本身不一定危险，危险的是它临时写出来、准备执行的那段命令。

比如模型可能生成：

```bash
rm -rf ~
```

或者被提示注入诱导执行恶意脚本。

所以更合理的做法是：

```text
AI 可以思考、规划、调用服务
但它要执行代码时，必须进隔离环境
```

这就像：

> 你可以让实习生提方案，但不能让他直接操作生产数据库；  
> 他要跑脚本，必须在测试沙箱里跑。

---

#### 关键洞察

##### 1. 沙箱边界应围住 “执行”，不是围住 “代理”

AI 代理需要上下文和权限才能有用。  
但模型生成的命令具有不确定性，所以执行层才是高风险点。

##### 2. Docker 不是万能安全边界

Docker 更像轻量运行环境，不是强安全沙箱。  
它共享宿主机内核，配置不当时风险很高。

##### 3. 审批机制不可扩展

一个代理时，人工审批还能看。  
十个代理并行时，人会疲劳，最后变成机械点击 “允许”。

##### 4. 安全应由工具链强制，而不是靠人自律

Temenos 的优势在于：

> 不让模型直接拿到危险工具，而是从架构上限制执行路径。

---

#### 辩证思考

##### 赞同之处

这个观点很有价值。

AI Agent 的安全问题，本质不是 “AI 是否可信”，而是：

> **不可预测的生成内容是否能直接触达真实系统。**

把执行层隔离出来，是更精准的安全设计。

尤其在多代理并行场景下，靠人工审批不现实，必须用默认安全的架构。

---

##### 需要警惕之处

但 “信任代理” 也不能绝对化。

AI 代理虽然作为程序运行在主机上，但它仍可能：

- 被提示注入诱导泄露信息
- 滥用已有认证上下文
- 调用外部 API 传出敏感数据
- 通过 MCP 工具间接影响宿主环境

所以更准确的说法应是：

> **相对信任代理框架，不信任模型输出与执行结果。**

代理也应有权限边界，只是不能简单粗暴地全部塞进 Docker。

---

#### 最精炼结论

> Docker 沙箱化 AI Agent，保护对象错了。  
> 真正危险的是模型刚生成的代码和命令。  
> 更好的架构是：  
> **代理在主机上保持能力，执行在强隔离沙箱中完成。**

最终原则：

```text
信任工具链
限制模型输出
隔离代码执行
最小化宿主暴露
```

这可能是 AI Agent 安全从 “人工审批” 走向 “架构约束” 的关键一步。

## 结构化（2）

### 2026-06-10 02:59:30

##### 主旨概括

作者认为：**不要再用 Docker 来沙箱化 AI 代理（Agent）**，因为真正需要被隔离的不是代理本身，而是代理刚生成并准备执行的代码或 Shell 命令。更合理的做法是：**信任代理，但把它生成的代码放进沙箱执行**。

---

##### 1. Docker 沙箱的问题：保护错了对象

作者指出，很多人用 Docker 或开发容器来限制 AI Agent，但这会削弱 Agent 的实用性：

- **身份认证需要转发**：Agent 要访问 GitHub、云服务、MCP 等资源时，需要把认证信息传进容器。
- **API Key 容易暴露**：密钥往往会被放到环境变量里，增加泄露风险。
- **更新麻烦**：工具或依赖更新后，通常需要重新构建镜像。
- **隔离不彻底**：Docker 仍然和宿主机共享同一个内核，安全边界有限。

简单说，Docker 看似把 Agent 关起来了，但同时也让 Agent 失去了很多 “像本地开发者一样工作” 的能力。

---

##### 2. 其他沙箱方案也各有缺陷

作者继续比较了几种常见方案：

###### 虚拟机 VM

- 隔离性比 Docker 更强。
- 但每个任务几乎都要从零开始。
- 会失去本机上下文，例如本地代码、配置、认证状态等。
- 每次启动都有明显的冷启动成本。

###### firejail /seccomp

- 可以限制系统调用，提升安全性。
- 但一旦 Agent 需要：
  - 安装软件包；
  - 运行构建工具；
  - 执行不在白名单里的系统调用；
  
  这些限制就会变得很碍事。

###### 审批提示

- 对单个 Agent 还可以用。
- 但如果有**10 个 Agent 并行运行**，用户很快就会疲于审批，最后往往直接点击 “允许全部”。

作者认为，这些方式的共同问题是：它们都默认 “Agent 本身需要被沙箱化”。

---

##### 3. 作者的核心观点：代码才需要沙箱

作者提出一个不同的安全边界：

> Agent 是你主动选择、配置、认证并连接的工具；真正危险的是模型几秒钟前生成的 Shell 命令或代码。

这些生成内容可能存在风险，例如：

- 有漏洞；
- 被提示注入影响；
- 含有恶意操作；
- 误删文件、泄露密钥、访问网络等。

因此，关键不是把整个 Agent 关进沙箱，而是让**Agent 保持在主机上正常工作**，但把它生成的代码放到安全环境里执行。

---

##### 4. Temenos 的方案：把安全边界放在 “执行代码” 处

作者介绍了工具**Temenos**：  
链接：https://github.com/vitalops/temenos

它的设计思路是：

- **Agent 留在宿主机上**
  - 可以访问认证信息；
  - 可以连接 MCP 服务器；
  - 可以使用模型 API；
  - 可以正常更新和使用本地上下文。

- **代码执行进入沙箱**
  - 执行环境是一个**无 root 权限的 gVisor 沙箱**；
  - gVisor 拥有自己的用户空间内核；
  - 宿主机文件系统只有在用户显式挂载的位置才可见；
  - 网络访问可以通过一个标志关闭。

这相当于让 Agent 仍然 “聪明且好用”，但它生成的高风险操作不能直接碰宿主机。

---

##### 5. 工具链强制隔离，减少人为审批负担

Temenos 的隔离不是靠用户不断点 “允许 / 拒绝”，而是由工具链强制执行：

- Claude 启动时默认没有：
  - Bash；
  - Read；
  - Write；
  - Edit；
  - 其他直接接触宿主机的工具。

- 模型可用的执行路径必须经过沙箱。

这样做的好处是：

- 可以支持多个 Agent 并行工作；
- 不需要用户陷入大量审批弹窗；
- 安全边界更清晰：Agent 能思考和调用工具，但代码执行被限制在沙箱内。

---

##### 6. 使用示例

作者给出的 Temenos 使用方式很简单：

```bash
pip install "temenos [all]"
cd ~/code/my-repo
temenos claude
```

含义是：

1. 安装 Temenos；
2. 进入本地项目目录；
3. 用 Temenos 启动 Claude；
4. Claude 仍能理解项目上下文，但执行命令时会经过沙箱。

---

##### 7. 结论：信任 Agent，隔离代码

作者最后总结：

> 信任代理，包含它生成的代码。

也就是说：

- **Agent 本身可以保留在宿主机上**，以便正常访问认证、上下文和工具；
- **Agent 生成的代码和命令必须被隔离执行**；
- 这样既能保留 AI Agent 的实用性，又能降低执行未知代码带来的风险。
