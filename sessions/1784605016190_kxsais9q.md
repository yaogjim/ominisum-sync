## 分析要点

- **核心高价值点**：以确定性AST解析构建非向量式代码知识图谱，并用EXTRACTED、INFERRED等标签标明每条关系的来源与推断性质。

**知识要点**

- 代码通过tree-sitter在本地生成实体及调用、导入、继承等关系，文档和媒体则需要语义模型处理。
- graphify query、path和explain分别支持自然语言子图检索、实体间最短路径追踪和单节点关系解释。
- 生成的graph.json、GRAPH\_REPORT.md和graph.html可供AI助手、浏览器及MCP服务复用，并支持提交到团队仓库后增量更新。

**行动项**

- 在代表性代码库运行graphify .，检查graph.html及graph.json中的跨文件关系和置信标签是否准确。
- 根据数据敏感性配置.graphifyignore与明确的推理后端，并核查查询日志设置后再用于真实项目。

Type `/graphify` in your AI coding assistant and it maps your entire project (code, docs, PDFs, images, videos) into a **knowledge graph** you can **query instead of grepping** through files.

- **Code maps for free, fully local.** Code is parsed with tree-sitter AST: deterministic, no LLM, nothing leaves your machine. (Docs, PDFs, images and video use your assistant's model, or a configured API key, for a semantic pass.)
- **Every edge is explained.** Each connection is tagged `EXTRACTED` (explicit in the source) or `INFERRED` (resolved by graphify), so you can tell what was read directly from what was inferred.
- **Not a vector index.** No embeddings, no vector store: a real graph you traverse. Ask a question, trace the path between two things, or explain one concept.

> Want this always-on, updating in the background across your code, docs, and meetings rather than only on demand? That is what we are building at **[graphify.com](https://graphify.com)**. You can join the waitlist there.

  Community: 2

Every edge carries a **confidence tag** (`EXTRACTED` = explicit in the source, `INFERRED` = derived by resolution), so you can tell what was read directly from what was inferred. `graphify query "<question>"` returns a scoped subgraph for a plain-language question, and `graphify path A B` traces how any two things connect.

> **Official package:** The PyPI package is `graphifyy` (double-y). Other `graphify*` packages on PyPI are not affiliated. The CLI command is still `graphify`.

**Step 1 — install the package:**

**Step 2 — register the skill with your AI assistant:**

```
graphify install
```

That's it. Open your AI assistant and type `/graphify .`

To install the assistant skill into the current repository instead of your user profile, add `--project`:

```
graphify install --project
graphify install --project --platform codex
```

Project-scoped installs write under the current directory, for example`.claude/skills/graphify/SKILL.md` or `.agents/skills/graphify/SKILL.md` (plus a `references/` sidecar the skill loads on demand), and print a `git add` hint for files that can be committed. Per-platform commands that support project-scoped installs accept the same flag, for example `graphify claude install --project` or `graphify codex install --project`.

> **PowerShell note:** Use `graphify .` not `/graphify .` — the leading slash is a path separator in PowerShell.

> **`graphify: command not found`?**`uv tool install` / `pipx install` put the `graphify` command in their tool bin dir (`~/.local/bin`). If your shell can't find it right after install — common on a fresh macOS + zsh setup — that dir isn't on your `PATH` yet: run `uv tool update-shell` (or `pipx ensurepath`), then open a new terminal. With plain `pip`, add `~/.local/bin` (Linux) or `~/Library/Python/3.x/bin` (Mac) to your PATH, or run `python -m graphify`.

> **Running with `uvx` / `uv tool run` instead of installing?** Name the package, not the command: `uvx --from graphifyy graphify install`. Plain `uvx graphify …` fails (`No solution found … no versions of graphify`) because `uv tool run` reads the first word as a *package*, and the package is `graphifyy` — the `graphify` command lives inside it.

> **Avoid `pip install` on Mac/Windows** if possible. The skill resolves Python at runtime from `graphify-out/.graphify_python`; if that points to a different environment than where `pip` installed the package, you'll get `ModuleNotFoundError: No module named 'graphify'`. `uv tool install` and `pipx install` isolate the package in their own env and avoid this entirely.

> **Git hooks and uv tool / pipx:**`graphify hook install` embeds the current interpreter path directly into the hook scripts at install time, so the post-commit hook fires correctly even in GUI git clients and CI runners where `~/.local/bin` is not on PATH. If you reinstall or upgrade graphify, re-run `graphify hook install` to refresh the embedded path.

> **Strict mode (Claude Code):**`graphify install --project --strict` makes the assistant actually use the graph. The default install *nudges* it to run `graphify query` before reading files; strict mode *blocks* the first raw source read of a session and redirects it to the graph, then reverts to the nudge (so it fires at most once per session and never gets stuck). Toggle at runtime with `GRAPHIFY_HOOK_STRICT=1` / `0`; the default install is unchanged (soft nudge).

This writes a small config file that tells your assistant to consult the knowledge graph for codebase questions, preferring scoped queries like `graphify query "<question>"` over reading the full report or grepping raw files.

- **Hook platforms** (Claude Code, Gemini CLI): a hook fires automatically before search-style tool calls (and, on Claude Code, before reading source files one by one via the Read/Glob tools) and nudges your assistant toward the graph path.
- **Instruction-file platforms** (Codex, OpenCode, Cursor, etc.): persistent instruction files (`AGENTS.md`, `.cursor/rules/`, etc.) provide the same query-first guidance.

`GRAPH_REPORT.md` is still available for broad architecture review.

**CodeBuddy** does the same two things as Claude Code: writes a `CODEBUDDY.md` section telling CodeBuddy to read `graphify-out/GRAPH_REPORT.md` before answering architecture questions, and installs `PreToolUse` hooks (`.codebuddy/settings.json`) that fire before Bash search commands and file reads, nudging toward `graphify query` instead.

**Codex** writes to `AGENTS.md` and also installs a `PreToolUse` hook in `.codex/hooks.json` that fires before every Bash tool call, same always-on mechanism as Claude Code.

**Kilo Code** installs the Graphify skill to `~/.config/kilo/skills/graphify/SKILL.md` and a native `/graphify` command to `~/.config/kilo/command/graphify.md`. `graphify kilo install` also writes `AGENTS.md` plus a native `tool.execute.before` plugin (`.kilo/plugins/graphify.js` + `.kilo/kilo.json` or `.kilo/kilo.jsonc` registration) so Kilo gets the same always-on graph reminder behavior through native `.kilo` config.

**Cursor** writes `.cursor/rules/graphify.mdc` with `alwaysApply: true`, so Cursor includes it in every conversation automatically, no hook needed.

To remove graphify from all platforms at once: `graphify uninstall` (add `--purge` to also delete `graphify-out/`). Or use the per-platform command (e.g. `graphify claude uninstall`).

- **God nodes** — the most-connected concepts in your project. Everything flows through these.
- **Surprising connections** — links between things that live in different files or modules. Ranked by how unexpected they are.
- **The "why"** — inline comments (`# NOTE:`, `# WHY:`, `# HACK:`), docstrings, and design rationale from docs are extracted as separate nodes linked to the code they explain.
- **Suggested questions** — 4–5 questions the graph is uniquely positioned to answer.
- **Confidence tags** — every inferred relationship is marked `EXTRACTED`, `INFERRED`, or `AMBIGUOUS`. You always know what was found vs guessed.

#### Ignoring files

Create a `.graphifyignore` in your project root — same syntax as `.gitignore`, including `!` negation.

**`.gitignore` is respected automatically.** graphify reads the `.gitignore` in each directory. If a `.graphifyignore` is also present, the two are **merged** — `.graphifyignore` patterns are evaluated last, so they win on conflicts (including `!` negations). Adding a `.graphifyignore` only ever excludes more; it never re-includes a file your `.gitignore` already excluded. Subdirectory scoping works the same way as git — an ignore file only affects its own subtree.

Pass `--no-gitignore` to `graphify extract` when git-ignored generated or transpiled code belongs in the graph. This disables `.gitignore` and `.git/info/exclude`; `.graphifyignore` still applies.

```
# .graphifyignore
node_modules/
dist/
*.generated.py

# only index src/, ignore everything else
*
!src/
!src/**
```

`graphify-out/` is meant to be committed to git so everyone on the team starts with a map.

**Recommended `.gitignore` additions:**

graphify-out/cost.json        # local only

```

> `manifest.json` is now portable — keys are stored as relative paths and re-anchored on load, so committing it is safe and avoids a full rebuild on first checkout.

**Workflow:**

1. One person runs `/graphify .` and commits `graphify-out/`.
2. Everyone pulls — their assistant reads the graph immediately.
3. Run `graphify hook install` to auto-rebuild after each commit (AST only, no API cost). This also sets up a git merge driver so `graph.json` is never left with conflict markers — two devs committing in parallel get their graphs union-merged automatically.
4. When docs or papers change, run `/graphify --update` to refresh those nodes.

The MCP server gives your assistant structured access: `query_graph`, `get_node`, `get_neighbors`, `shortest_path`, `list_prs`, `get_pr_impact`, `triage_prs`.

`--transport stdio` (the default) spawns one local server per developer. `--transport http` serves the same tools over the MCP Streamable HTTP transport, so a single shared process can serve the graph for the whole team — clients point their IDE MCP config at `http://<host>:8080/mcp` instead of running graphify locally.

Flag Default Purpose

`--transport {stdio,http}` `stdio` Transport to serve on

`--host` `127.0.0.1` HTTP bind host (use `0.0.0.0` to expose beyond localhost)

`--port` `8080` HTTP bind port

`--api-key` env `GRAPHIFY_API_KEY` Require `Authorization: Bearer <key>` (or `X-API-Key`)

`--path` `/mcp` HTTP mount path

`--json-response` off Return plain JSON instead of SSE streams

`--stateless` off No per-session state (for load-balanced / CI deployments)

`--session-timeout` `3600` Reap idle stateful sessions after N seconds (`0` disables)

The default `127.0.0.1` bind is loopback-only. Set `--host 0.0.0.0` **and** `--api-key` together when exposing on a shared host. Run it in a container:

```
docker build -t graphify .
docker run -p 8080:8080 -v "$(pwd)/graphify-out:/data" graphify \
  /data/graph.json --transport http --host 0.0.0.0 --api-key "$SECRET"
```

>
> ```
> python3 -m venv .venv && .venv/bin/pip install "graphifyy[mcp]"
> ```

#### Privacy

- **Code files** — processed locally via tree-sitter. Nothing leaves your machine. A code-only corpus requires no API key — `graphify extract` runs fully offline.
- **Video / audio** — transcribed locally with faster-whisper. Nothing leaves your machine.
- **Docs, PDFs, images** — sent to your AI assistant for semantic extraction (via the `/graphify` skill, using whatever model your IDE session runs). Headless `graphify extract` requires `GEMINI_API_KEY` / `GOOGLE_API_KEY` (Gemini), `MOONSHOT_API_KEY` (Kimi), `ANTHROPIC_API_KEY` (Claude), `OPENAI_API_KEY` (OpenAI), `DEEPSEEK_API_KEY` (DeepSeek), a running Ollama instance (`OLLAMA_BASE_URL`), AWS credentials via the standard provider chain (Bedrock - no API key needed, uses IAM), or the `claude` CLI binary (Claude Code - no API key needed, uses your Claude subscription). The `--dedup-llm` flag uses the same key.
- **Data residency** — `graphify extract` auto-detects which provider to use based on which API key is set (priority: Gemini → Kimi → Claude → OpenAI → DeepSeek → Azure → Bedrock → Ollama). For code with data-residency requirements, use `--backend ollama` (fully local) or pass an explicit `--backend` flag. Kimi (`MOONSHOT_API_KEY`) routes to Moonshot AI servers in China.
- **No telemetry**, no usage tracking, no analytics.
- **Query logging** — every `graphify query`, `graphify path`, `graphify explain`, and MCP `query_graph` call is logged to `~/.cache/graphify-queries.log` in JSON Lines format (timestamp, question, corpus, nodes returned, duration). Full subgraph responses are **not** stored by default. Set `GRAPHIFY_QUERY_LOG_DISABLE=1` to opt out, or `GRAPHIFY_QUERY_LOG=/dev/null` to silence without disabling the code path.

#### Troubleshooting

**`graphify: command not found` after installing** The CLI is installed but its bin directory isn't on your shell's `PATH`. Pick the fix for how you installed:

- **uv** (`uv tool install graphifyy`): the command lands in uv's tool bin dir (`~/.local/bin`), which a fresh macOS/zsh setup often doesn't have on `PATH`. Run `uv tool update-shell`, then open a new terminal. (Find the dir with `uv tool dir --bin`.)
- **pipx** (`pipx install graphifyy`): run `pipx ensurepath`, then open a new terminal.
- **pip** (`pip install graphifyy`): pip installs scripts to a user bin dir that may not be on `PATH` — add `~/Library/Python/3.x/bin` (macOS) or `~/.local/bin` (Linux) to your `PATH` in `~/.zshrc` / `~/.bashrc`, or just run `python -m graphify`.

**`uvx graphify …` or `uv tool run graphify …` fails to resolve `graphify`** The PyPI package is `graphifyy`; `graphify` is only the command it provides. `uv tool run` treats the first word as a *package name*, so it looks for a package called `graphify` and reports `No solution found … no versions of graphify`. Name the package explicitly: `uvx --from graphifyy graphify install` (same as `uv tool run --from graphifyy graphify install`). Or `uv tool install graphifyy` once and then call `graphify` directly.

**`python -m graphify` works but `graphify` command doesn't** Your shell's `PATH` doesn't include the bin directory the command was installed to. Prefer `uv tool install` / `pipx install` over plain `pip`, then run `uv tool update-shell` / `pipx ensurepath` and open a new terminal (see the install notes above).

**`/graphify .` causes "path not recognized" in PowerShell** PowerShell treats a leading `/` as a path separator. Use `graphify .` (no slash) on Windows.

**Graph has fewer nodes after `--update` or rebuild** If a refactor deleted files, the old nodes linger. Pass `--force` (or set `GRAPHIFY_FORCE=1`) to overwrite even when the rebuild has fewer nodes.

**`extract` exits with "extraction was incomplete... refusing to overwrite"** When an extraction pass crashes or a walk can't fully read the corpus, the run would be smaller than a complete one, so `graphify extract` refuses to overwrite a larger existing graph with the partial result (protecting your `graph.json`). Fix the underlying failure and re-run, or pass `--allow-partial` to overwrite anyway.

**Graph has duplicate nodes for the same entity (ghost duplicates)** Ghost duplicates (same symbol appearing twice — once from AST extraction with a source location, once from semantic extraction without) are now automatically merged at build time. If you see this in a graph built before v0.8.33, run a full re-extract to clean up:

```
graphify extract . --force
```

**Ollama runs out of VRAM / context window exceeded** The KV-cache window is auto-sized but may be too large for your GPU. Reduce it:

```
GRAPHIFY_OLLAMA_NUM_CTX=8192 graphify extract ./docs --backend ollama --token-budget 4000
```

**`LLM returned invalid JSON` / `Unterminated string` warnings** The model's JSON response hit its output-token limit and was cut off mid-string. graphify auto-recovers (it splits the chunk and re-extracts the halves, and an oversized single document is first sliced at heading/paragraph boundaries so the whole file is still covered), so these warnings are noisy but not data loss. To reduce the churn, raise the output cap or shrink each chunk's output:

```
GRAPHIFY_MAX_OUTPUT_TOKENS=16384 graphify extract . --mode deep   # lift the cap
graphify extract . --mode deep --token-budget 4000                # smaller input chunks -> smaller output
```

With a cloud gateway like OpenRouter, prefer `--backend openai` (set `OPENAI_BASE_URL`) over the Ollama shim — it's a cleaner OpenAI-compatible path. If the model has its own max-output ceiling, lowering `--token-budget` is the reliable lever.

**Graph HTML is too large to open in a browser (&gt;5000 nodes)** Skip HTML generation and use the JSON directly:

```
graphify cluster-only ./my-project --no-viz
graphify query "..."
```

**`graph.json` has conflict markers after two devs commit at once** Run `graphify hook install` — it sets up a git merge driver that union-merges `graph.json` automatically so conflicts never happen.

**Extraction returns empty nodes/edges for docs or PDFs** Docs, PDFs, and images require an LLM call — code-only corpora need no key. Check that your API key is set and the backend is correct:

```
ANTHROPIC_API_KEY=sk-... graphify extract ./docs --backend claude
```

**Skill version mismatch warning in your IDE** Your installed graphify version is different from the skill file. Update:

```
uv tool upgrade graphifyy
graphify install  # overwrites the skill file
```

**Claude Code prompt cache invalidated after every `graphify extract`** Graphify writes output files (`graph.json`, `graphify-out/`) into the workspace. If those paths aren't ignored, every write invalidates Claude Code's prompt cache, forcing a full re-upload at cache-write rates on the next turn. Add them to `.claudeignore`:

```
# .claudeignore
graph.json
graphify-out/
```

#### Graphify 项目精炼总结

Graphify 是一个**本地优先的知识图谱工具**：它能把代码、文档、SQL Schema、配置、PDF、图片及音视频统一映射为可查询的图谱，让 AI 编程助手通过“查图、找路径、解释节点”理解项目，而不是反复全文搜索。其核心特点是：**代码使用 AST 确定性解析、无需向量数据库、每条关系都有来源与置信度说明**。

##### 1. 核心理念：把整个项目变成可查询的真实图谱

- 在 Claude Code、Cursor、Codex、Gemini CLI 等助手中输入：

  ```bash
  /graphify .
  ```

  Codex 使用 `$graphify`；PowerShell 应直接运行 `graphify .`。

- Graphify 会将项目中的实体表示为节点，将调用、导入、继承、引用等关系表示为边。
- 它不是向量索引：
  - 不生成 Embedding；
  - 不依赖向量数据库；
  - 查询时直接遍历实体及关系构成的真实图。
- 每条边都会标记依据：
  - `EXTRACTED`：源文件中明确存在；
  - `INFERRED`：Graphify 通过名称或引用解析推导；
  - `AMBIGUOUS`：关系存在歧义。
- 因此用户可以区分“源码直接写明的事实”和“工具推断出的关系”。

##### 2. 代码与非代码内容的处理方式

###### 代码

- 使用 tree-sitter AST 在本地解析，过程确定、无需 LLM。
- 代码不会离开本机，纯代码项目可以完全离线构建图谱。
- 支持约 **36 种 tree-sitter 语法、约 40 种语言的跨文件关系解析**，包括 Python、JavaScript、TypeScript、Go、Rust、Java、C/C++、C#、Kotlin、Swift、PHP、Ruby、Lua、SQL、Shell、Vue、Svelte、Dart、Pascal 等。
- 可以解析：
  - 函数和方法调用；
  - 模块导入；
  - 类继承与混入；
  - 包依赖；
  - 跨文件符号引用；
  - SQL Schema、Terraform/HCL、MCP 配置和部分工程文件。

###### 文档与媒体

- Markdown、HTML、YAML、PDF、Office 文件、图片等会通过 AI 模型进行语义提取。
- 视频和音频可使用 `faster-whisper` 在本地转录。
- Google Docs、Sheets、Slides 需要借助 `gws` CLI 导出为 Markdown 辅助文件后再提取。
- 文档中的设计依据也能进入图谱，例如：
  - `# NOTE:`
  - `# WHY:`
  - `# HACK:`
  - Docstring；
  - ADR、RFC 和文档引用。

这些解释性内容会成为独立节点，并与其说明的代码相连。

##### 3. 构建后生成的文件

默认输出目录为：

```text
graphify-out/
├── graph.html
├── GRAPH_REPORT.md
└── graph.json
```

- `graph.html`：可在浏览器中交互浏览，支持点击、筛选和搜索节点。
- `GRAPH_REPORT.md`：总结关键概念、核心枢纽、意外联系及建议问题。
- `graph.json`：完整图谱数据，后续查询无需重新读取全部源文件。

图谱还会自动分析：

- **God nodes**：连接数量最多、贯穿项目的核心概念；
- **Communities**：通过 Leiden 算法发现的子系统或模块群；
- **Surprising connections**：不同文件或模块之间不明显的关联；
- **Suggested questions**：图谱最适合回答的 4～5 个问题；
- **Rationale**：代码背后的设计原因与文档依据。

##### 4. 查询、路径与解释能力

Graphify 提供三种主要查询方式：

```bash
graphify query "什么把认证模块和数据库连接起来？"
graphify path "UserService" "DatabasePool"
graphify explain "RateLimiter"
```

- `query`：根据自然语言问题返回一个范围受控的子图。
- `path`：查找两个实体之间的最短关系路径。
- `explain`：展示某个节点的来源、所属社区、连接数量和关系。

###### FastAPI 实例

对 FastAPI 代码库运行 Graphify 后，解释 `APIRouter` 可得到：

- 来源：`routing.py` 第 2210 行；
- 所属社区：Community 2；
- 连接度：47；
- 关系示例：
  - 使用 `RequestValidationError`，标记为 `INFERRED`；
  - 调用 `.get()`，标记为 `EXTRACTED`；
  - 被 `__init__.py` 导入，标记为 `EXTRACTED`。

查询 `FastAPI` 到 `ModelField` 的路径时，得到一条 **3 跳路径**：

```text
FastAPI
  --uses--> DefaultPlaceholder
  <--references-- get_request_handler()
  --references--> ModelField
```

这类结果可以帮助开发者理解跨模块依赖，而不必逐个打开文件。

##### 6. 安装与快速开始

最低要求：

- Python **3.10+**；
- 推荐使用 `uv`，也可使用 `pipx`。

PyPI 包名是 **`graphifyy`（两个 y）**，但安装后的命令仍是 `graphify`：

```bash
uv tool install graphifyy
graphify install
```

然后在 AI 助手中运行：

```bash
/graphify .
```

如果使用临时执行方式，需要明确包名：

```bash
uvx --from graphifyy graphify install
```

直接运行 `uvx graphify ...` 会失败，因为 PyPI 上的官方包不是 `graphify`。

###### 项目级安装

graphify install --project
graphify install --project --platform codex
```

项目级配置会写入仓库内，例如：

```text
.claude/skills/graphify/SKILL.md
.agents/skills/graphify/SKILL.md
```

这些文件可以提交到 Git，供团队共享。

##### 8. 常见工作流与命令

##### 9. 团队协作与 Git 自动更新

官方建议将 `graphify-out/` 提交到 Git，使团队成员拉取代码后立即拥有项目地图。

推荐流程：

1. 一名成员运行 `/graphify .`；
2. 提交 `graphify-out/`；
3. 其他成员拉取后即可直接查询；
4. 安装 Git Hook：

   ```bash
   graphify hook install
   ```

Hook 会：

- 在 Git commit 后自动重建 AST 图谱；
- 代码更新不产生 LLM API 成本；
- 安装 `graph.json` 合并驱动；
- 多名开发者并行提交时，对图谱执行并集合并，避免冲突标记。

```bash
/graphify --update
```

##### 12. 隐私、数据驻留与日志

- **代码文件**：完全在本地通过 tree-sitter 处理，不离开机器。
- **视频和音频**：可通过 `faster-whisper` 本地转录。
- **文档、PDF、图片**：需要语义模型处理；使用 `/graphify` 时通常复用 IDE 中的模型，Headless/CI 模式则需要配置相应后端。
- 可使用 Ollama 实现完全本地处理：

  ```bash
  graphify extract ./docs --backend ollama
  ```

- 云后端自动检测优先级为：

  ```text
  Gemini → Kimi → Claude → OpenAI → DeepSeek → Azure → Bedrock → Ollama
  ```

- 使用 Kimi 时，数据会路由到中国境内的 Moonshot AI 服务。
- 项目声明不包含遥测、使用跟踪或分析服务。

> **文档存在一处日志说明不一致：**环境变量章节称查询日志默认关闭、需通过 `GRAPHIFY_QUERY_LOG_ENABLE=1` 开启；后面的隐私章节却称查询默认写入 `~/.cache/graphify-queries.log`。实际使用时应以当前安装版本行为为准，并可设置 `GRAPHIFY_QUERY_LOG_DISABLE=1` 强制关闭。

##### 13. 文件忽略与大型图谱处理

- 自动尊重每个目录中的 `.gitignore`。
- 可用 `.graphifyignore` 进一步排除文件，语法与 `.gitignore` 相同。
- `.graphifyignore` 只能增加排除项，不能重新纳入已被 `.gitignore` 排除的文件。
- 如需包含被 Git 忽略的生成代码：

  ```bash
  graphify extract ./src --no-gitignore
  ```

- 当图谱超过约 **5000 个节点**、HTML 难以打开时，可跳过可视化：

  ```bash
  graphify cluster-only ./my-project --no-viz
  graphify query "..."
  ```

- `graph.json` 默认大小上限为 **512 MiB**，超大型项目可通过 `GRAPHIFY_MAX_GRAPH_BYTES` 调整。

##### 14. 常见问题

- **安装后找不到命令**：运行 `uv tool update-shell` 或 `pipx ensurepath`，然后重开终端。
- **PowerShell 不识别 `/graphify .`**：改用 `graphify .`。
- **更新后节点变少但无法覆盖**：重构删除文件后，可使用 `--force`。
- **提取不完整且拒绝覆盖**：这是为了避免用残缺图覆盖现有完整图；修复错误后重试，或使用 `--allow-partial`。
- **旧版本存在重复节点**：完整强制重建：

  ```bash
  graphify extract . --force
  ```

- **Ollama 显存不足**：降低上下文窗口，例如：

  ```bash
  GRAPHIFY_OLLAMA_NUM_CTX=8192 graphify extract ./docs --backend ollama
  ```

- **LLM 返回的 JSON 被截断**：Graphify 会自动拆分重试；也可提高输出上限或减小输入块。
- **文档/PDF 提取为空**：确认已配置模型后端和 API Key；纯代码解析不需要 Key。
- **Claude Code 缓存频繁失效**：将 `graph.json` 和 `graphify-out/` 加入 `.claudeignore`。

### 2026-08-03 01:45:47

#### Graphify：把整个代码库变成可查询的知识图谱

这份材料介绍了 Graphify，一个面向 AI 编程助手的本地知识图谱工具。听完你可以了解它如何把代码、文档、数据库结构和多媒体资料连成一张图，如何查询这些关系，以及它的安装方式、隐私边界和实际效果。

##### 一、它解决的核心问题：不用反复翻文件，也能理解整个项目

首先，Graphify 的核心结论是：它不是简单地搜索文件，而是把整个项目转换成一张可以查询和追踪的知识图谱。

通俗地说，一个大型代码库里，信息通常分散在源代码、配置文件、接口文档、数据库表结构、设计说明，甚至会议录音和视频里。Graphify 会把这些内容提取成节点和连接关系。节点可以是一个类、一个函数、一张数据库表，也可以是一段文档或一个设计概念。连接则可能表示“调用了”“导入了”“继承了”“引用了”或者“解释了”。

它与向量检索系统不同。Graphify 不使用嵌入，也不依赖向量数据库。它保存的是一张可以实际遍历的图。你可以直接问一个问题，可以追踪两个对象之间的路径，也可以单独解释某个概念。

例如，针对 FastAPI 代码库，Graphify 可以回答“什么连接了认证模块和数据库”，也可以追踪“FastAPI”和“ModelField”之间的最短路径。

这意味着，AI 助手不必每次都从头阅读一堆文件，而是可以先从图中找到相关范围，再深入查看具体内容。

##### 二、它如何构建这张图：代码本地解析，关系明确标注

接下来，Graphify 的重要特点是，它对代码使用一种叫作 Tree-sitter 的语法解析工具。简单说，Tree-sitter 能把源代码拆解成结构化的语法树，也就是抽象语法树，英文缩写是 AST。

这样做的好处是，代码关系主要通过确定性的程序分析得到，而不是让大语言模型猜测。代码解析完全在本地进行，不需要 API，也不会把代码发送到外部服务。

Graphify 还会给每条关系标注来源。标记为“EXTRACTED”，表示这条关系在源代码中明确存在，比如一个文件确实导入了另一个模块。标记为“INFERRED”，表示这条关系是 Graphify 通过解析和消歧推导出来的。还有“AMBIGUOUS”，表示关系存在不确定性。

因此，使用者可以区分：哪些内容是直接读到的，哪些内容是工具推断出来的。

它还会把代码中的注释和设计依据纳入图中。比如带有“NOTE”“WHY”或“HACK”的注释，以及架构决策记录和技术方案引用，都可以成为独立节点，并连接到它们所解释的代码。

这解决了一个常见问题：代码告诉你“怎么做”，但注释和设计文档往往才解释“为什么这样做”。

##### 三、运行一次后会得到什么：网页、报告和完整数据

更具体地说，第一次运行 Graphify 后，通常会得到三个主要文件。

第一个是 `graph.html`。它可以直接用浏览器打开。你可以点击节点、搜索内容，也可以筛选不同部分的关系。

第二个是 `GRAPH_REPORT.md`。它不是完整图，而是一份适合快速浏览的摘要。里面会列出项目里最重要的概念、跨文件的异常连接，以及图谱最适合回答的问题。

第三个是 `graph.json`。这是完整的图数据。之后查询时，可以直接使用它，不必重新读取整个项目。

Graphify 还会识别几个很有用的结构。

第一类是“God nodes”，也就是连接数特别多的核心节点。它们类似项目中的交通枢纽，可以帮助你快速看出大量代码都流经哪些概念。

第二类是“Communities”，也就是社区或子系统。Graphify 会根据连接关系把整张图划分成不同模块，并尝试给这些模块生成不依赖大语言模型的标签。

第三类是“Surprising connections”，也就是跨文件、跨模块、但不容易被人工发现的连接。它们会按照意外程度排序，帮助你发现隐藏的依赖。

##### 四、实际查询方式：问问题、找路径、解释节点

在实际使用中，Graphify 提供三种最基本的查询方式。

第一种是自然语言查询。比如问：“什么连接了注意力机制和优化器？”Graphify 会返回一个与问题相关的局部子图，而不是把整个项目都展示出来。

第二种是路径查询。你可以给出两个对象，要求 Graphify 找出它们之间的连接路径。

第三种是节点解释。你可以输入一个类名、函数名或概念名，让 Graphify 说明它来自哪里、属于哪个社区、连接了什么内容。

以 FastAPI 为例，查询 `APIRouter` 时，结果显示它位于 `routing.py` 文件第两千两百一十行左右，属于第二个社区，总共有四十七条连接。其中，它与 `RequestValidationError` 和 `Dependant` 的关系被标为推断关系；而它调用 `.get()`、以及从 `__init__.py` 导入的关系，则是从源代码中直接提取出来的。

另一个例子是查询 `FastAPI` 到 `ModelField` 的路径。Graphify 给出的最短路径有三跳，中间经过 `DefaultPlaceholder` 和 `get_request_handler()`。

这些结果的重要意义不只是“找到了答案”，而是同时展示了答案是怎样沿着项目结构推导出来的。

##### 六、效果如何：图结构在部分记忆和问答测试中表现突出

材料还给出了几组基准测试结果。需要注意，这些是项目提供的测试数据。

在同一个 LOCOMO 测试中，Graphify 的问答准确率是百分之四十五点三。supermemory 是百分之四十九点七，mem0 是百分之二十七点三。也就是说，Graphify 的召回能力很强，但在最终问答准确率上，并不是所有指标都领先。

这些系统使用了相同的测试框架、相同的模型和相近的预算。结果由一个评审模型判断，并用第二个评审模型进行盲验证。两个评审之间的一致率是百分之九十点六，Cohen’s kappa，也就是一种衡量评审一致性的统计量，为零点八一。

另外，Graphify 声称大多数系统在构建图谱时不需要按令牌支付大语言模型费用。对代码来说，这是因为解析主要由本地 AST 工具完成。

##### 七、安装和第一次使用：三十秒建立基本图谱

开始使用前，最低要求是 Python 三点一零或更高版本。项目推荐使用 `uv`，也可以使用 `pipx`。

需要特别注意，PyPI 上的官方包名是 `graphifyy`，最后有两个字母 y。安装后的命令名仍然是 `graphify`。其他名字相近的 PyPI 包，与这个项目没有关系。

一种推荐流程是先安装 `graphifyy`，然后运行 `graphify install`，把 Graphify 技能注册到你的 AI 编程助手里。接着，在项目目录中输入 `/graphify`，就会开始构建当前项目的图谱。

如果是 Codex，使用的是 `$graphify`。如果是在 Windows PowerShell 中，开头不要使用 `/graphify`，而应使用 `graphify .`，因为 PowerShell 会把开头的斜杠当成路径分隔符。

如果只想把技能安装到当前项目，而不是安装到个人环境，可以使用项目级安装选项。这样，配置会写入当前仓库，例如 `.claude/skills/graphify` 或 `.agents/skills/graphify`，便于团队提交到 Git。

##### 八、它适配哪些 AI 编程助手

Codex、Cursor、OpenCode 等平台，主要通过持久化规则文件实现同样的效果。例如 Cursor 会写入一个始终生效的规则文件，让每次对话都知道应该优先使用 Graphify。

跨框架使用时，可以安装到通用的 Agent Skills 目录。这样，支持这个规范的多个开发框架都可以发现同一个 Graphify 技能。

默认行为是“软提醒”。也就是说，助手会被建议先查询图谱，但仍然可以继续读取原始文件。Claude Code 还支持严格模式。严格模式会阻止一个会话第一次直接读取源文件，把它引导到图谱查询；之后恢复为普通提醒，避免一直被拦截。

##### 九、可选扩展和后端：按需要增加能力

Graphify 的基础安装并不包含所有功能。不同任务可以安装不同的额外组件。

如果需要读取 PDF、Word 和 Excel，可以安装相应扩展。如果需要视频和音频转录，可以安装视频扩展。如果需要 MCP，也就是一种让 AI 助手调用外部工具的协议，可以安装 MCP 扩展。

它还支持 Neo4j 和 FalkorDB 等图数据库导出或推送，支持 SVG、Leiden 社区检测，以及 SQL、PostgreSQL、Terraform、Pascal 和 BYOND DreamMaker 等专门能力。

语义提取可以使用多种后端，包括 Gemini、Claude、OpenAI 兼容接口、DeepSeek、Kimi、Azure、AWS Bedrock 和 Ollama。

如果使用 Ollama，或者使用本地的 OpenAI 兼容服务，可以让文档语义提取也在本机完成。代码本身无论如何都可以离线解析，不需要 API 密钥。

在没有 IDE 的服务器或 CI 环境中，可以直接运行 `graphify extract`，并明确指定后端。对于本地环境，也可以使用 `--backend ollama`；对于 AWS，则可以使用 Bedrock 的 IAM 身份认证，而不必配置 API 密钥。

##### 十、团队协作：提交图谱，并自动保持更新

Graphify 的设计目标之一，是让团队共享同一份项目地图。

推荐的工作流是：由一名成员运行一次 Graphify，然后把 `graphify-out` 目录提交到 Git。其他成员拉取代码后，AI 助手就可以直接读取已有图谱，不必每个人都重新构建。

如果安装 Git 钩子，Graphify 可以在每次提交后自动重新生成图谱。代码部分使用本地 AST 解析，因此自动更新不会产生 API 调用成本。

它还会设置一个 Git 合并驱动，帮助两个开发者在并行提交时合并 `graph.json`。这样可以避免图谱文件留下冲突标记。

当文档或论文发生变化时，可以使用更新模式，只重新提取变化的文件。对于代码重构，如果旧节点没有被正确清除，可以使用强制重建选项。

项目还支持 `.graphifyignore` 文件。它的语法与 `.gitignore` 类似，可以排除 `node_modules`、构建产物和生成文件。默认情况下，Graphify 会遵守项目已有的 `.gitignore`。

##### 十一、MCP 服务和共享访问

如果希望其他 AI 工具以结构化方式访问图谱，可以启动 Graphify 的 MCP 服务。

默认是标准输入输出模式，也就是每位开发者本地启动一个服务。它提供查询图、获取节点、获取邻居、查找最短路径，以及查询代码变更影响等工具。

Graphify 也支持 Streamable HTTP 模式。这样可以在一台服务器上启动一个共享进程，让团队里的多个 IDE 通过 HTTP 访问同一份图谱。

默认 HTTP 只绑定本机地址，也就是 `127.0.0.1`。如果要对外提供服务，需要绑定到更开放的地址，并同时配置 API 密钥。认证可以使用 Bearer Token，也可以使用 `X-API-Key`。

项目还支持把服务运行在 Docker 容器中。共享部署时，材料建议不要只开放网络地址，而要同时设置访问密钥。

##### 十二、隐私和数据处理边界

隐私方面，最重要的结论是：代码解析不需要离开你的机器。

代码通过 Tree-sitter 在本地处理，不需要 API，也不会被发送出去。视频和音频转录也可以在本地完成。

但文档、PDF 和图片的语义提取，可能会发送给 AI 助手当前使用的模型，或者你配置的云端后端。使用云端服务时，具体数据驻留位置取决于后端提供商。

如果有更严格的数据驻留要求，可以使用本地 Ollama，或者显式指定本地后端。材料还指出，Graphify 没有遥测、使用跟踪或分析系统。

查询日志默认关闭。如果用户主动开启，查询、路径和解释操作可以记录到本地的 JSON Lines 日志中。默认不记录完整的子图响应。用户也可以通过环境变量关闭日志，或者把日志输出指向空设备。

##### 十三、常见问题和使用提醒

安装后如果出现“找不到 `graphify` 命令”，通常不是安装失败，而是命令所在目录没有加入 PATH。

使用 `uv` 时，可以运行 `uv tool update-shell`，然后重新打开终端。使用 `pipx` 时，可以运行 `pipx ensurepath`。如果使用普通 `pip`，则需要手动把用户脚本目录加入 PATH。

如果使用 `uvx`，要写包名 `graphifyy`，而不是把 `graphify` 当成包名。正确思路是使用 `uvx --from graphifyy graphify install`。原因是：`graphifyy` 是包，`graphify` 只是包提供的命令。

如果更新后图谱节点变少，可能是重构删除了文件，或者更新过程不完整。Graphify 默认会保护已有的完整图谱，拒绝用一个不完整的结果覆盖它。修复问题后可以重新运行；确认需要覆盖时，再使用强制或允许部分结果的选项。

如果项目超过五千个节点，浏览器可能难以打开 HTML 图。此时可以跳过网页可视化，直接使用 `graph.json` 查询。

另外，Graphify 生成的文件可能会触发 Claude Code 重新上传工作区缓存。材料建议把 `graph.json` 和 `graphify-out` 加入 `.claudeignore`，减少不必要的缓存失效。

##### 十四、更多能力：从代码理解扩展到变更和工作记忆

除了基础的查询功能，Graphify 还提供一些更高级的命令。

它可以生成调用流程和架构 HTML，也可以生成 Markdown Wiki、Obsidian 知识库、SVG 图、GraphML 文件，或者导出到 Neo4j 和 FalkorDB。

它还支持添加论文、网页和视频，把外部资料并入现有图谱。

针对 GitHub 项目，`graphify prs` 可以展示拉取请求，也就是 PR 的持续集成状态、审查状态、工作树映射和图谱影响。它可以深入分析某个 PR，也可以对审查队列进行 AI 排序，还能找出共享同一社区的 PR，帮助识别潜在的合并顺序风险。

最近的功能还包括工作记忆。你可以保存一次问答结果，标记它是有用、走入死胡同，还是后来被修正。之后，`graphify reflect` 会把这些结果汇总成经验文档。当代码发生变化时，相关经验会被标记为需要重新验证。

##### 十五、项目本身和企业版本

Graphify 项目使用 `uv` 进行开发，主要用 Python 编写。贡献者可以克隆仓库，切换到 `v8` 开发分支，安装依赖并运行测试。

项目鼓励贡献真实项目上的使用案例。贡献者可以保存一次实际运行结果，写下图谱做对了什么、做错了什么，再提交改进。

材料最后提到，Graphify Enterprise 是在开源 Graphify 之上构建的持续运行版本。它的目标是把会议、文件、文档和代码都纳入同一张持续更新的工作知识图谱，而不是只在用户主动运行命令时才生成结果。

##### 最后，记住五件事

第一，Graphify 的核心不是向量搜索，而是一张可以查询和遍历的知识图谱。

第二，代码使用 Tree-sitter 在本地确定性解析，不需要大语言模型，也不会离开本机。

第三，每条关系都会标记为直接提取、推断或存在歧义，方便用户判断答案的可信来源。

第四，它可以把代码、文档、PDF、图片、数据库结构、视频和音频放进同一张图，但非代码资料的语义提取可能需要调用模型。

第五，Graphify 适配二十多个 AI 编程助手，支持团队共享、自动更新、MCP 服务和变更影响分析，目标是让 AI 先理解项目结构，再去阅读和修改具体文件。

## 深度解读（1）

### 2026-09-18 00:26:45

#### Graphify 的真正价值：让 AI 先查“关系地图”，再读源码

Graphify 最值得关注的，并不是把代码画成一张炫目的知识图谱，而是尝试改变编码 Agent 获取上下文的方式：**从临时 grep、逐文件阅读，转向查询一个预先构建、可追溯的关系索引。**

##### 图结构适合回答“它们为什么有关”

向量检索擅长找语义相近的片段，却不天然擅长回答“某个接口如何经过三层调用影响数据库”“两个模块通过什么依赖相连”。Graphify 用 tree-sitter 解析 AST，把调用、导入、继承和引用变成边，再提供 `query`、`path`、`explain` 等操作。对大型代码库而言，这类问题往往比“哪段代码与问题最相似”更重要。

更关键的是，它把边标记为 **EXTRACTED、INFERRED 或 AMBIGUOUS**。这不是装饰：Agent 最危险的错误，往往不是没找到信息，而是把推断当成事实。可追溯的关系能让人判断某个答案来自源码明示，还是实体消歧后的推断。

但它不应被理解为向量检索的全面替代品。AST 能稳定描述静态结构，却未必能还原动态分派、反射、运行时配置和隐式业务约定；文档、PDF 和媒体的语义抽取仍依赖模型。更合理的架构是：**图负责确定性关系，语义检索负责模糊召回，源码与运行数据负责最终验证。**

##### 真正的产品设计在“强迫使用”，不在生成图

许多代码地图失败，不是图不准确，而是生成后没人持续使用。Graphify 因此把自己嵌入 Claude Code、Cursor、Codex 等工具：在搜索或读取源码前提醒 Agent 先查图，甚至提供 strict mode 阻止首次直接读文件；同时用 Git hook 增量更新，并允许团队提交图文件。

这揭示了 Agent 基础设施的一条重要规律：**上下文资产只有进入决策路径、保持新鲜，才会产生价值。** 单独提供可视化页面远远不够，还要解决查询路由、更新触发、团队共享和失败回退。Graphify 正从“代码分析工具”走向“Agent 的上下文控制层”，其商业化方向——持续整合代码、文档和会议——也由此成立。

不过，强制 query-first 同样有风险：图若过期、抽取不完整或错误合并实体，Agent 可能被一个压缩后的世界模型误导。因此图应该缩小阅读范围，而不是取代源文件这个最终事实源。

##### 数据证明了潜力，还没有证明通用优势

项目公布的结果显示，Graphify 在 LOCOMO 的 recall@10 明显高于若干记忆产品，但 QA 准确率为 45.3%，仍低于 supermemory 的 49.7%；在 LongMemEval-S 上则与 dense RAG 持平。它说明图检索可能更容易召回相关关系，却尚未证明召回一定转化为更好的答案，而且这些记忆基准也不能直接替代真实代码维护任务。

另一个需要警惕的细节是隐私说明存在矛盾：一处称查询日志默认关闭，另一处又称每次查询都会写入本地日志、需主动退出。即使日志不上传，这种表述冲突也会削弱企业采用所需的信任。

因此，最值得验证的不是“知识图谱是否优于 RAG”，而是：**在跨模块排障、影响分析、架构问答和 PR 冲突识别等关系密集任务上，它能否稳定减少源码读取量，同时不降低正确率。**这才是 Graphify 从有趣工具走向基础设施的分界线。
