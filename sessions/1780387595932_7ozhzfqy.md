## 正文

**idoubi**

聊一聊 Agent 的存算分离架构设计👇

一个有灵魂，有记忆的 Agent，一次任务的生命周期包括以下步骤

1\. 用户输入 query（text + files）  
2\. Agent 读取提示词文件（soul.md，identify.md，user.md 等）  
3\. Agent 读取可用的工具和技能（tools，skills 等）  
4\. Agent 读取记忆（memory.md，memory\_search 查询）  
5\. Agent 构建上下文（prompt + tools + memory + query）  
6\. Agent 进入 Loop（LLM 调用 → 工具调用 → 观测 → 再推理）  
7\. Agent 交付结果（Artifacts）

什么需要存：提示词文件，工具和技能，对话记录，交付产物

什么需要算：上下文拼接，LLM 调用，工具调用

简单表示这个过程

fn(query, agent runtime) = artifacts  
fn(查询, 代理运行时) = 工件

我们可以把 agent 运行方式简单分为三类

1\. 本地裸机运行  
2\. 本地带沙盒（sandbox）运行  
3\. 云端多副本运行

\---

1\. 本地裸机运行，是 OpenClaw 之类 Agent 的常见模式。Agent 提示词文件、skills，对话记录（sessions）全部存在本地磁盘，Agent 执行任务时，会在固定 workspace 目录下运行，用户上传的文件、Agent 产出的文件全部落在同一个 workspace，Agent Loop 完全依赖本地文件构建上下文和执行工具调用，存跟算是一体的。

这种模式好处是足够简单，避免了额外的文件挂载开销，弊端在于安全性，比如 Agent Loop 执行了一个 exec(rm -rf /) 工具调用，很容易对宿主机产生破坏

2\. 本地带沙盒运行，是 Codex 之类的 Agent 的常见模式。主要解决两个问题。一是防止 Agent 越权操作，提高安全性；二是解决宿主机的依赖缺失导致工具调用异常的问题。

Agent Loop 执行工具调用时，涉及到敏感操作或者有外部依赖时，把宿主机的 workspace 目录挂载到 sandbox，在 sandbox 执行工具调用，输出产物自动同步到宿主机的 workspace 目录

这种模式下的存算分离，只在工具调用环节引入 sandbox 来动态计算，存储主要靠宿主机的文件系统

3\. 云端多副本运行，是 Manus 之类的工具型 Agent 的常见模式。主要特点是多租户，多任务，长时间运行

像 genspark claw，kimi claw，max claw 之类的托管版小龙虾，本质上是在云端多副本运行的助理型 Agent，每个用户有独立的提示词文件，动态安装的 skills，需要长期记忆

这类 claw 托管服务，最简单的实现方式是搭建一套 k8s 集群，在每个 pod 部署一套 Agent 框架（OpenClaw，harmes 等），通过 pvc 挂载云硬盘，实现对用户资料的持久化存储。通过负载均衡策略把每个用户的请求路由到固定的 pod，在同一个 pod 做 Agent Loop，存算是一体的，每个 Agent 有独立的运行空间。这种方案隔离性很好，不好的地方在于 pod 需要常驻，运行成本很高，难以规模化

\---

云端 Agent 需要规模化（scalable），必然要结合 serverless 架构做存算分离。计算层依赖 k8s 集群的调度机制动态扩缩容，水平扩展 Agent 网关的并发处理能力

存储层结合 Agent 的运行生命周期，不同阶段的产物用不同的存储方案，主要分为四种

1\. 热状态。Agent Loop 的 step，plan，游标等状态，用 kv（redis）来存，高性能，低延迟，用于异常重启后的断点恢复

2\. 对话和任务记录。在任务完成后用关系型数据库（postgres）来存

3\. 长期记忆。基于对话/任务记录做摘要，提取成记忆，用向量数据库（pgvector，milvus）来存

4\. 工作产物。包括用户上传的文件，Agent 输出的文件，系统内置的 tools，动态创建的 skills 等，用对象存储（s3，oss）来存

\---

以 FastClaw 为例，演示基于存算分离架构的云端 Agent 的运行过程👇

1\. 一套 k8s 集群，日常 2 个 pod，部署 fastclaw gateway，接收用户请求

2\. 负载均衡把用户请求路由到其中一个 pod，Agent 开始计算逻辑：

2.1 从 db 读取提示词文件（soul，identity，user）  
2.2 初始化 pod 内一个临时目录作为 workspace  
2.3 初始化 sandbox，挂载 workspace  
2.4 从对象存储下载用户资料和系统 skills 到 workspace  
2.5 调用 memory\_search 工具，从向量数据库查询记忆  
2.6 拼接上下文，调用 llm，解析工具  
2.7 在 sandbox 执行工具调用，读写 workspace 内的文件  
2.8 把 Agent Loop 过程中的状态设置为 checkpoint，保存到 kv  
2.9 Agent 输出结果给用户

3\. 通过惰性检查，把不活跃的 sandbox 关闭，关闭前把 sandbox 内 workspace 的文件上传到对象存储

以上的存算分离架构，计算层依赖 pod + sandbox，pod 水平扩容支持并发调用，sandbox 承接少量的工具调用，使用 e2b 作为 sandbox 可以做到秒级启动，构建 sandbox 池可以提高并发容错；存储层依赖 kv + db + vector db + oss 的组合使用，瓶颈在于 io 延迟

这套架构最大的挑战在于分布式多副本场景下的数据一致性，需要合理使用锁机制和负载均衡策略。

理解了这套架构，再去看 Manus，Claude managed agents 的实现，就很好理解了。

##### 一、总结

这篇内容讲的是：**Agent 要规模化，必须做“存算分离”**。

Agent 一次任务大致流程：

> 用户输入 → 读取提示词/工具/记忆 → 拼上下文 → LLM 推理 → 调工具 → 产出结果

其中：

| 类型 | 内容 |
|---|---|
| **存储** | 提示词、工具、技能、记忆、对话、文件、产物 |
| **计算** | 上下文拼接、LLM 调用、工具执行、Agent Loop |

作者把 Agent 运行方式分为三类：

1. **本地裸机运行**  
   简单，但不安全。

2. **本地沙盒运行**  
   工具调用放进 sandbox，更安全，适合 Codex 类产品。

3. **云端多副本运行**  
   面向多用户、多任务、长期运行，但如果每个用户常驻 Pod，成本很高。

所以云端 Agent 最终需要：

> **计算层弹性扩缩容，存储层统一持久化。**

---

##### 二、通俗解读

可以把 Agent 想成一个“会干活的员工”。

###### 1. 存算一体是什么？

就像员工把：

- 资料
- 工具
- 记忆
- 工作文件

全放在自己电脑里。

好处是简单，坏处是：

- 换台电脑就麻烦
- 多人协作难
- 扩容贵
- 容易把电脑搞坏

---

###### 2. 存算分离是什么？

就是：

> **资料放仓库，员工临时来干活，用完就走。**

对应到系统里：

| 现实类比 | 技术实现 |
|---|---|
| 临时员工 | Pod / Serverless |
| 隔离工位 | Sandbox |
| 短期状态 | Redis |
| 历史记录 | Postgres |
| 长期记忆 | 向量数据库 |
| 文件资料 | S3 / OSS |

这样计算资源不用一直开着，谁来任务谁启动，成本更低，也更容易扩容。

---

###### 3. 为什么难？

核心难点是：

> **多个计算节点同时读写同一份数据，怎么保证不乱？**

比如：

- A Pod 写了一版文件
- B Pod 同时也写了一版
- 最后该保留谁？

所以需要：

- 锁机制
- checkpoint
- 任务路由
- 文件同步
- 状态恢复

---

##### 三、我的意见

我认同作者的判断：

> **云端 Agent 想商业化，存算分离几乎是必选项。**

原因很简单：

1. **常驻 Pod 太贵**  
   用户不用时资源也在烧钱。

2. **Agent 天然需要持久记忆**  
   记忆、文件、技能不能绑死在某个容器里。

3. **Sandbox 是刚需**  
   Agent 会执行代码、读写文件，不隔离风险很高。

4. **真正的难点不是 LLM，而是工程系统**  
   包括状态管理、文件同步、权限隔离、成本控制、失败恢复。

---

##### 四、一句话结论

**Agent 产品的后半场，不只是拼模型能力，而是拼云端架构能力。**

更具体地说：

> 小规模靠 Pod 常驻能跑；  
> 大规模必须靠存算分离降成本、提并发、保稳定。

## 结构化（1）

### 2026-06-02 08:25:44

##### 主旨概括

文章讨论了 **Agent 的“存算分离”架构设计**：一个有记忆、有工具、有执行能力的 Agent，在云端规模化运行时，不能简单把存储和计算绑在一起，而需要把状态、记忆、文件、运行环境等拆开管理。  
作者通过本地运行、沙盒运行、云端多副本运行三种模式，对比说明为什么云端 Agent 最终需要走向 **serverless + 存算分离** 架构。

---

##### 1. Agent 一次任务的生命周期

一个完整的 Agent 任务，大致包括以下步骤：

1. 用户输入请求：包括文本和文件。
2. Agent 读取提示词文件：如 `soul.md`、`identity.md`、`user.md` 等。
3. Agent 读取可用工具和技能：如 `tools`、`skills`。
4. Agent 读取记忆：如 `memory.md` 或通过 `memory_search` 查询。
5. Agent 构建上下文：把提示词、工具、记忆、用户请求拼接起来。
6. Agent 进入循环执行：
   - 调用 LLM；
   - 调用工具；
   - 观察结果；
   - 再次推理。
7. Agent 交付结果：生成最终产物，即 `Artifacts`。

可以简单表示为：

```text
fn(query, agent runtime) = artifacts
fn(查询, 代理运行时) = 工件
```

也就是说，用户输入请求后，Agent 通过运行时环境完成推理、调用工具，并最终产出结果。

---

##### 2. 什么需要“存”，什么需要“算”

作者将 Agent 系统中的内容分为两类：

###### 需要存储的内容

包括：

- 提示词文件；
- 工具和技能；
- 对话记录；
- 用户上传文件；
- Agent 交付产物；
- 长期记忆。

###### 需要计算的内容

包括：

- 上下文拼接；
- LLM 调用；
- 工具调用；
- Agent Loop 中的推理和执行过程。

核心观点是：  
**存储内容应该持久化，计算过程应该可以动态调度和弹性扩缩容。**

---

##### 3. Agent 的三种运行方式

作者把 Agent 的运行方式分为三类：

1. 本地裸机运行；
2. 本地带沙盒运行；
3. 云端多副本运行。

这三种模式对应不同的安全性、成本和扩展能力。

---

##### 4. 模式一：本地裸机运行

这是类似 **OpenClaw** 这类 Agent 的常见模式。

###### 运行方式

- Agent 的提示词文件、技能、对话记录等都存在本地磁盘；
- 用户上传文件和 Agent 生成文件都放在固定的 `workspace` 目录；
- Agent Loop 完全依赖本地文件系统构建上下文和执行工具调用；
- 存储和计算是一体的。

###### 优点

- 架构简单；
- 不需要额外的文件挂载；
- 本地读写文件方便。

###### 缺点

安全风险较高。  
例如，如果 Agent 执行了类似：

```bash
rm -rf /
```

这样的危险命令，就可能直接破坏宿主机系统。

---

##### 5. 模式二：本地带沙盒运行

这是类似 **Codex** 这类 Agent 的常见模式。

###### 主要解决两个问题

1. 防止 Agent 越权操作，提高安全性；
2. 避免宿主机缺少依赖，导致工具调用异常。

###### 运行方式

当 Agent Loop 需要执行敏感操作，或者需要外部依赖时：

- 把宿主机的 `workspace` 目录挂载到 sandbox；
- 在 sandbox 中执行工具调用；
- 执行结果自动同步回宿主机的 `workspace`。

###### 特点

这种模式只是在工具调用环节引入 sandbox。  
本质上，主要存储仍然依赖宿主机文件系统，存算分离程度有限。

---

##### 6. 模式三：云端多副本运行

这是类似 **Manus** 这类工具型 Agent 的常见模式。

###### 适用场景

云端 Agent 通常具备以下特点：

- 多租户；
- 多任务；
- 长时间运行；
- 需要长期记忆；
- 每个用户有独立配置和技能。

例如：

- genspark claw；
- kimi claw；
- max claw；
- 托管版 OpenClaw。

这些本质上都是云端多副本运行的助理型 Agent。

---

##### 7. 云端 Agent 的简单实现：Pod 常驻方案

作者提到，最简单的云端实现方式是：

- 搭建一套 Kubernetes 集群；
- 每个 Pod 部署一套 Agent 框架，如 OpenClaw、harmes；
- 通过 PVC 挂载云硬盘，实现用户资料持久化；
- 通过负载均衡，把每个用户请求固定路由到某个 Pod；
- 在同一个 Pod 内完成 Agent Loop。

###### 优点

- 每个 Agent 有独立运行空间；
- 隔离性较好；
- 实现相对直观。

###### 缺点

- Pod 需要常驻；
- 运行成本很高；
- 难以规模化。

###### 作者的实际案例

作者年初做 OpenClaw 托管服务时：

- 在一套 K8s 集群中部署了 **500 个 Pod**；
- 每个 Pod 限制 **4GB 内存**；
- 日常运行 **18 台 4 核 16GB 服务器** 作为节点池；
- 每月成本接近 **5000 美元**；
- 几个月后 MRR 突破 **8000 美元**；
- 但扣除运营成本后，利润很低。

这个案例说明：  
**常驻 Pod 架构虽然简单，但成本压力很大，不适合大规模商业化。**

---

##### 8. 云端规模化的关键：Serverless + 存算分离

作者认为，云端 Agent 如果要规模化，必然要结合 serverless 架构做存算分离。

###### 计算层

计算层依赖 K8s 集群调度机制：

- 动态扩缩容；
- 支持水平扩展；
- 提升 Agent 网关的并发处理能力。

###### 存储层

存储层根据 Agent 生命周期中的不同产物，采用不同的存储方案。

---

##### 9. 存储层的四类数据

作者将存储层分为四类。

###### 1. 热状态

包括：

- Agent Loop 的 step；
- plan；
- 游标；
- 中间状态。

推荐使用：

```text
KV 存储，如 Redis
```

特点：

- 高性能；
- 低延迟；
- 可用于异常重启后的断点恢复。

---

###### 2. 对话和任务记录

任务完成后，将完整记录存入关系型数据库。

推荐使用：

```text
Postgres
```

适合存储：

- 对话历史；
- 任务记录；
- 用户会话；
- 可查询的结构化数据。

---

###### 3. 长期记忆

长期记忆通常来自对话和任务记录的摘要与提取。

推荐使用：

```text
向量数据库，如 pgvector、Milvus
```

适合支持：

- 语义检索；
- memory_search；
- 个性化记忆召回。

---

###### 4. 工作产物

包括：

- 用户上传文件；
- Agent 输出文件；
- 系统内置 tools；
- 动态创建的 skills。

推荐使用：

```text
对象存储，如 S3、OSS
```

适合存放大文件和可持久化资产。

---

##### 10. FastClaw 示例：存算分离架构下的运行流程

作者以 **FastClaw** 为例，说明云端 Agent 如何运行。

###### 基础架构

- 一套 K8s 集群；
- 日常运行 **2 个 Pod**；
- Pod 中部署 `fastclaw gateway`；
- Gateway 接收用户请求。

相比之前 500 个常驻 Pod 的方案，这种架构明显更轻量。

---

###### 具体执行流程

1. 用户请求进入系统；
2. 负载均衡将请求路由到某个 Pod；
3. Agent 开始执行计算逻辑；
4. 从数据库读取提示词文件：
   - `soul`；
   - `identity`；
   - `user`。
5. 在 Pod 内初始化临时目录作为 `workspace`；
6. 初始化 sandbox，并挂载 `workspace`；
7. 从对象存储下载：
   - 用户资料；
   - 系统 skills。
8. 调用 `memory_search` 工具，从向量数据库查询记忆；
9. 拼接上下文；
10. 调用 LLM；
11. 解析工具调用；
12. 在 sandbox 中执行工具调用，读写 `workspace` 文件；
13. 将 Agent Loop 中的状态设置为 checkpoint，并保存到 KV；
14. Agent 将结果输出给用户；
15. 通过惰性检查关闭不活跃 sandbox；
16. 关闭前，把 sandbox 内 `workspace` 文件上传回对象存储。

---

##### 11. 该架构的优势与瓶颈

###### 优势

计算层依赖：

- Pod；
- sandbox。

其中：

- Pod 可以水平扩容，支持并发调用；
- sandbox 承接少量工具调用；
- 如果使用 **e2b** 作为 sandbox，可以做到秒级启动；
- 构建 sandbox 池可以提升并发能力和容错能力。

###### 存储层依赖组合

包括：

- KV；
- DB；
- Vector DB；
- OSS。

这种组合可以分别处理状态、记录、记忆和文件资产。

###### 主要瓶颈

瓶颈在于：

```text
IO 延迟
```

也就是说，数据在数据库、对象存储、向量库、sandbox 和 Pod 之间频繁读写，会带来性能压力。

---

##### 12. 最大挑战：分布式数据一致性

作者强调，这套架构最大的挑战是：

```text
分布式多副本场景下的数据一致性
```

尤其是在多个 Pod、多个 sandbox、多个用户任务同时运行时，需要合理设计：

- 锁机制；
- 负载均衡策略；
- 状态同步；
- 文件读写冲突处理；
- checkpoint 恢复逻辑。

否则可能出现重复执行、状态错乱、文件版本冲突等问题。

---

##### 13. 总结

作者认为，理解了这套存算分离架构后，再看 **Manus**、**Claude managed agents** 这类云端 Agent 的实现，就会更容易理解。

整体来看，文章的核心结论是：

> 本地 Agent 可以存算一体，但云端 Agent 要实现多租户、低成本、高并发和长任务运行，必须走向存算分离：计算层弹性扩缩容，存储层按状态、记录、记忆和文件资产分层管理。

- 仍然主要依赖本地文件系统
- 存算分离不彻底
- 难以支持大规模多用户、多任务并发
- 更适合本地开发，而非云端托管

这种模式的关键是：

```text

工具调用在 sandbox 内执行
产物同步回宿主机 workspace
```

###### 2.3 为什么云端 Agent 必然走向 Serverless + 存算分离？

因为云端 Agent 的负载具有明显的不均匀性：

- 用户不是一直在线
- 任务不是一直执行
- 工具调用是间歇性的
- 长任务需要挂起和恢复
- 文件存储需要长期保留
- 计算资源只在执行时真正需要

如果让计算资源常驻，会造成巨大浪费。

所以合理架构应该是：

```text
存储长期存在
计算按需启动
状态可恢复
任务可迁移
资源可扩缩
```

也就是：

```text
Compute is ephemeral
Storage is persistent
```

计算层可以临时启动，任务结束后释放；  
存储层负责保存用户数据、记忆、文件、状态和产物。

##### 5. 反方与张力

###### 5.1 存算分离会增加系统复杂度

反方观点：

> 对很多早期团队来说，过早做存算分离可能是过度工程。

因为它会引入：

- 多数据库
- 分布式锁
- 文件同步
- 状态恢复
- Sandbox 生命周期管理
- 任务调度
- IO 延迟
- 一致性问题
- 成本监控复杂度

如果用户量很小，任务时间很短，直接用本地文件系统或单 Pod 架构可能更快。

适用判断：

| 阶段 | 架构选择 |
|---|---|
| Demo / 内部工具 | 本地裸机或单机 Docker |
| 早期 MVP | 单 Pod + 对象存储 + DB |
| 有真实用户 | Pod + Sandbox + Redis checkpoint |
| 多租户规模化 | Serverless + 存算分离 |
| 企业级 | 多副本 + 强隔离 + 审计 + 权限系统 |

---

###### 5.2 成本和体验之间存在张力

云端 Agent 如果完全按需启动，可以降低成本，但可能牺牲体验。

典型张力：

| 目标 | 问题 |
|---|---|
| 降低成本 | Sandbox 冷启动变慢 |
| 提高体验 | 需要常驻资源 |
| 强隔离 | 资源利用率下降 |
| 高并发 | 状态一致性变复杂 |
| 长任务 | 需要复杂 checkpoint |
| 文件持久化 | IO 延迟增加 |

所以架构设计不是单纯追求「最先进」，而是做权衡：

```text
成本 × 延迟 × 安全 × 一致性 × 可扩展性
```

---

###### 5.3 数据一致性是最大挑战之一

在分布式多副本环境下，同一个用户的任务可能被不同 Pod 处理。

如果没有控制好，会出现：

- 同一任务被重复执行
- workspace 文件版本冲突
- memory 被重复写入
- checkpoint 覆盖
- artifacts 丢失
- 用户看到过期状态

需要设计：

- 任务锁
- 用户级路由
- workspace version
- artifact version
- 幂等工具调用
- checkpoint 原子写入
- 文件上传前后的状态标记
- 任务状态机

---

###### 5.4 不是所有 Agent 都需要长期记忆

长期记忆很有吸引力，但也有风险：

- 错误记忆会污染后续任务
- 用户隐私风险变高
- 检索结果可能不相关
- 记忆更新策略复杂
- 删除和遗忘机制难做
- 企业客户可能不允许跨任务记忆

所以长期记忆需要谨慎设计。

建议将记忆分成：

```text
用户显式保存的记忆
系统自动提取的记忆
任务临时记忆
项目级记忆
组织级记忆
```

并提供：

- 查看
- 编辑
- 删除
- 关闭
- 作用域控制

##### 6. 情境化落地

###### 场景一：个人开发者做本地 Agent

适合架构：

```text
本地文件系统 + Docker Sandbox + SQLite/Postgres
```

重点不是规模化，而是：

- 安全隔离
- 文件读写体验
- 工具调用稳定性
- Prompt 管理
- 简单记忆系统

建议：

- workspace 独立目录
- 危险命令进入 Docker
- 对用户文件做备份
- 日志保存到本地 DB
- 产物按任务归档

---

###### 场景二：早期 SaaS Agent 产品

适合架构：

```text
少量常驻 Pod + Redis + Postgres + S3 + Sandbox
```

建议优先做：

- 用户任务表
- Agent Loop checkpoint
- 对象存储持久化
- Sandbox 隔离执行
- 任务状态可视化
- Artifact 管理
- 基础 memory_search

暂时可以不做：

- 复杂调度系统
- 大规模 serverless
- 多区域部署
- 高级权限体系
- 复杂多 Agent 协作

早期重点是验证：

```text
用户是否愿意为 Agent 交付的 artifact 付费
```

而不是先把架构做到极致。

---

###### 场景三：企业级 Agent 平台

适合架构：

```text
Agent Gateway
+ 多租户隔离
+ K8s / Serverless Compute
+ Sandbox Pool
+ Redis
+ Postgres
+ Vector DB
+ Object Storage
+ Audit Log
+ RBAC
```

必须关注：

- 租户隔离
- 权限控制
- 审计日志
- 数据留存策略
- 记忆可控
- 文件权限
- 工具白名单
- 网络访问控制
- 成本归因
- 任务可观测性

企业场景尤其要注意：

```text
Agent 不是越自主越好，而是越可控越好。
```

---

###### 场景四：长任务 Agent / 自动化 Agent

如果 Agent 要支持长时间运行，例如：

- 定时研究
- 自动写报告
- 自动监控竞品
- 自动处理客户请求
- 自动做数据分析
- 自动运营任务

则需要额外设计：

```text
Scheduler + Checkpoint + Event Queue + Artifact Versioning
```

关键能力：

- 定时触发
- 事件触发
- 任务暂停
- 任务恢复
- 任务取消
- 任务重试
- 中间结果保存
- 用户确认节点
- 失败告警
- 成本上限控制

这其实对应回复里提到的：

> dreaming 或任务自动化场景中的定时任务也很重要。

如果没有调度系统，Agent 很难从「被动问答」变成「主动执行」。

**Agent 产品的规模化瓶颈，不在 Prompt，而在运行时架构；真正的云端 Agent 需要把长期存在的存储和按需启动的计算分离，用 KV、数据库、向量库、对象存储和 Sandbox 共同支撑可恢复、可扩展、可交付的任务系统。**
