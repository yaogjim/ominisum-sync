## 正文

PDF 问答（QA）乍一看似乎很简单。获取一份文档，提取文本，分块，嵌入，然后在查询时检索正确的段落。对于简单查询，这个流程通常感觉足够。

但 PDF 很少仅仅是纯文本。它们通过布局、表格、标题和视觉分组来编码含义，而这正是许多问答系统开始失效的地方。在这篇文章中，我们将介绍一份结构复杂但小巧的药品副作用说明书。我们将围绕 LlamaIndex 的 [LiteParse](https://developers.llamaindex.ai/liteparse/) 框架（用于布局感知解析）、 [LanceDB](https://lancedb.github.io/lancedb/) （用于多模态检索）以及基于 Claude SDK 的代理来构建一个端到端的代理管道。这个代理会判断何时仅需文本信息，何时需要查看页面本身。

#### 为什么 PDF 问答比看起来更难

如果你曾经构建过一个 PDF 问答代理，你可能已经尝试过标准模式：提取文本、分块、嵌入，然后根据查询进行检索。这种方法对于简单查找来说效果相当不错，但一旦问题依赖于文档结构或多模态上下文，它就会失效。

考虑一个药物副作用表，其中“抑郁”既作为开处方的原因，也作为另一种药物的副作用出现。一旦解析器将该表展平为文本流，列标识就会丢失，而且无论如何进行提示工程都无法恢复它。数据的存储方式很重要。

另一种方法是将原始页面作为图像传递给视觉语言模型（VLM），并让模型在单次调用中同时处理解析和推理。这种方法避开了结构问题，但代价高昂：VLM 的推理过程每页成本高昂，在长文档中性能会下降，且难以进行系统性评估。根据 PDF 页面的复杂程度，在检索过程中，模型可能会聚焦到页面的错误部分。这是因为它将解析问题视为推理问题。

典型的 PDF 问答流程混淆了三个本应分开的关注点： **解析** （从文档中提取结构化内容）、 **检索** （为给定查询找出相关片段）和 **推理** （综合答案）。将这些合并到单个模型调用中会限制可扩展性、可调试性以及系统能够处理的问题范围。

#### LiteParse：本地、布局感知的 PDF 解析

[LiteParse](https://developers.llamaindex.ai/liteparse/) 是 LlamaIndex 的开源、布局感知的文档解析器。它于 2026 年 3 月发布，专门为智能代理工作流构建。它在本地运行，生成带有空间元数据的布局感知文本，下游组件可依赖这些文本。

LiteParse 中的核心设计决策是 **通过网格投影进行空间文本解析** 。大多数解析器试图将表格和结构化布局转换为 Markdown，但在处理合并单元格、多级标题和不规则网格时会失效。LiteParse 采用了不同的方法：它将提取的文本投影到虚拟字符网格上，从而保留原始页面的视觉布局。其假设是，LLMs 已经从训练数据中学会了如何读取空间格式的表格。因此，解析器的工作是忠实地保留该结构，而不是对其进行解读。

这对代理管道很重要，因为它将解析与推理分离。在典型的 OCR+代理流程中，代理接收展平文本，并且每次查询都必须推断布局、修复提取错误并重建结构。这项工作速度慢、成本高且不可重复。LiteParse 生成一个确定性的结构化基础——代理在此基础上进行推理，而非通过解析过程。

下面，我们列出与此流程相关的关键能力：

- **选择性 OCR** ：原生 PDF 文本提取是默认路径。OCR（通过 [Tesseract.js](https://tesseract.projectnaptha.com/) ）仅在无法提取文本或字符映射乱码的页面上触发。数字原生 PDF 完全跳过 OCR 阶段。
- **页面截图** ：LiteParse 通过 [PDFium](https://pdfium.googlesource.com/pdfium/+/master/README.md) 渲染高分辨率页面图像，同时进行文本提取。这实现了一种多模态回退机制：代理可以将视觉上复杂的页面升级到视觉模型处理，而无需重新处理文档。
- **结构化输出** ：结果包括每页文本、边界框、字体元数据和图像数据，以 JSON 格式呈现。下游的分块和嵌入操作作用于这种结构化表示，而非原始字符串。
- **本地执行** ：无需云依赖或 API 密钥。适用于处理敏感文档或在受限环境中部署的团队。

LiteParse 以 TypeScript/Python 库和 CLI 形式发布，可通过 npm、pip 或 Homebrew 安装。如需完整参考，请参阅 [文档](https://developers.llamaindex.ai/liteparse/) 。

#### Why LanceDB?

在这个工作流程中，LiteParse 每页生成两个输出：结构化文本和高分辨率截图。一种自然的存储模型是将每页视为表格中的一行——文本、嵌入向量和原始图像字节并排存储。LanceDB 使这种存储方式变得简单，因为它原生存储多模态数据。无需为图像单独配置向量数据库、元数据存储和对象存储。文本块、嵌入向量和页面截图存储在单个 Lance 表中。

这不仅带来了便利，还有实际的好处。由于图像与结构化元数据在同一行中进行版本管理，治理变得更加简单——检索层返回的内容与源文档实际包含的内容之间不存在偏差。在查询时，一次获取操作可以返回文本块及其嵌入向量以进行快速相似度搜索，或者当智能体需要视觉上下文时包含图像字节。检索层根据查询决定要获取什么内容，无需在多个存储后端之间进行协调。

LanceDB 也是本地嵌入式的，这与 LiteParse 的本地优先设计非常契合。完整流程（解析、存储和检索）在单台机器上运行，不依赖任何外部服务。并且 LanceDB 开箱即用支持向量搜索和混合搜索（向量+全文），这对于文档问答系统非常重要，因为在文档问答中，精确术语匹配和语义相似度适用于不同的查询类型。

#### 数据集：药品副作用情况说明书

本项目的数据集是来自 [MedStar Visiting Nurse Association](https://www.medstarhealth.org/-/media/project/mho/medstar/services/pdf/medication_side_effect_flyer.pdf) 的两页 PDF 文件。这是一份信息单页，它将 11 种药物类别映射到它们的通用名、商品名和常见副作用。

![](https://cdn.prod.website-files.com/69b2da72cae7eea2b0091d5f/69d3afd0210427e10021faee_medstar-snippet.png)

这份 PDF 并非没有固有结构。有三列： **用药原因** 、 **药品名称：通用名（商品名）** 和 **副作用** 。每一行代表一个药物类别（例如，“止痛”、“降血压”），而非单个药物。有些类别包含子标题——“降血压”将药物归类到血管紧张素转换酶抑制剂（ACE 抑制剂）、血管紧张素 II 受体拮抗剂（ARB）和利尿剂（Diuretics）下——还有几种药物完全没有商品名（吗啡、阿司匹林、肝素）。

虽然这是一份篇幅较小的文档，但对基于代理的问答系统而言，它提供了一个合理的难度水平。挑战是 *结构性的* ，而非与规模相关：

- **同义词不匹配** ：PDF 中使用了“恶心或呕吐”和“有助于缓解炎症”这类术语，而用户可能会询问“恶心”和“抗炎药”。精确的术语匹配失败；系统需要语义桥接。
- **列消歧** ：“Queasiness”同时作为 **药品原因 （类别名称）和 **副作用** 出现在止痛药物中。“呕吐”出现在五个不同的副作用列表和一个类别名称中。系统必须基于列位置而非字符串匹配来区分这些角色。**
- **近似重复的类别** ：“降低血压”和“降低血压和心率”是不同的类别，具有不同的药物和不同的副作用。一个将它们混淆的检索系统会产生错误的答案——特别是在否定或布尔值响应的问题上（例如： *头痛是否是氯沙坦所属类别的副作用？* ）
- **按类别划分的副作用** ：副作用是按类别列出的，而非按药物列出。系统不得编造源文档中未提及的按药物的区分。
- **跨类别推理** ： *哪些副作用在抗凝药物和降胆固醇药物之间存在重叠？* 需要从多个类别中检索并计算集合交集——这是单次向量搜索调用无法完成的。

评估套件（稍后介绍）针对这些具体挑战，涉及七个类别中的20个问题：直接查询、同义词解析、品牌/通用映射、跨类别推理、否定、聚合和消歧。

#### 预处理：从 PDF 到 LanceDB

预处理流程将原始 PDF 转换为 LanceDB 中可索引、可检索的行。它以单函数形式运行，包含四个阶段：解析、分块、截图和存储。完整实现位于 [processing.ts](https://github.com/run-llama/llamaindex-lancedb-medqa/blob/main/src/processing.ts) 中。

##### Parsing and Chunking

LiteParse 处理第一阶段。单个 `parse()` 调用会提取每页的布局感知文本——这里不需要 OCR，因为这是一个带有可提取文本的原生数字 PDF。然后，输出会经过 [Chonkie](https://github.com/chonkie-ai/chonkie) 的 `RecursiveChunker` ，将每页的文本分割成最多 4096 个字符的块。

TypeScript

```typescript
import { LiteParse } from "@llamaindex/liteparse";
import { RecursiveChunker } from "@chonkiejs/core";

const PARSER = new LiteParse();

async function parseAndChunk(filePath: string): Promise<Map<number, string[]>> {
  const result = await PARSER.parse(filePath);
  const chunker = await RecursiveChunker.create({ chunkSize: 4096 });

  const pages: Map<number, string[]> = new Map();
  for (const r of result.pages) {
    const chunks = await chunker.chunk(r.text);
    pages.set(r.pageNum, chunks.map((c) => c.text));
  }
  return pages;
}
```

对于这个两页的 PDF 文件，分块过程很简单直接——每页都符合分块大小限制，因此输出本质上是每页一个分块。LiteParse 在提取的文本中保留的空间布局使得列关系在分块中得以保留：代理仍然可以看到“头晕”位于“副作用”列下方，而非“用药原因”列下方。

##### Page Screenshots

同时，LiteParse 通过其 `screenshot()` API 渲染每个页面的高分辨率 PNG 截图。这些截图被存储到磁盘，并通过页码与其对应的文本块关联。

TypeScript

```typescript
const result = await PARSER.screenshot(filePath);
for (const r of result) {
  const imagePath = `screenshots/${basename}_page_${r.pageNum}.png`;
  await fs.writeFile(imagePath, r.imageBuffer);
}
```

这是多模态回退机制。当代理的基于文本的搜索返回的上下文不足时——例如，在涉及整个表格的聚合问题中——它可以检索页面截图并直接对视觉布局进行推理。

##### Embedding and Storage

每个文本块使用 Google 的 `gemini-embedding-2-preview` 模型（3072 维）进行嵌入，然后与元数据一起存储在 LanceDB 中。Lance 表的模式由 Arrow 类型定义：

TypeScript

```typescript
const schema = new arrow.Schema([
  new arrow.Field("id", new arrow.Utf8()),          // screenshot path (unique key)
  new arrow.Field("image", new arrow.Binary()),      // PNG bytes
  new arrow.Field(
    "vector",
    new arrow.FixedSizeList(3072, new arrow.Field("item", new arrow.Float32(), true)),
  ),
  new arrow.Field("text", new arrow.Utf8()),         // chunk text
]);
```

每一行都是一个块——它的文本、嵌入向量以及它来自的页面的截图，都集中在一个地方。图像字节以二进制列的形式直接存储在 Lance 表中，而不是作为文件路径或外部引用。这是一个很好的特性，因为一个查询可以返回用于相似度搜索的文本或用于视觉推理的图像，无需再次查询。

插入后，将在嵌入列上构建一个向量索引以支持快速的近似最近邻搜索。我们使用 HNSW-SQ（带标量量化的分层可导航小世界，Hierarchical Navigable Small World with Scalar Quantization），在这里效果很好，因为召回率很重要，并且这是一个小型数据集：

TypeScript

```typescript
await tbl.createIndex("vector", {
  config: lancedb.Index.hnswSq(),
});
```

对于更大规模的部署，LanceDB 还支持 IVF-PQ 索引，这些索引以牺牲部分召回率为代价，换取了显著更低的内存使用量——这在索引数百万个片段时更为合适。有关索引类型的比较，请参阅 [LanceDB 向量索引文档](https://docs.lancedb.com/indexing/vector-index) 。

这个完整的流程 – `解析 → chunk → screenshot → embed → upsert` – 作为单个命令行界面命令（ `bun run process <pdf>` ）运行。对于这个两页的 PDF，它在几秒钟内完成，并生成一个本地的 `.lancedb/` 目录，可供检索。

#### 代理：使用 Claude 进行检索+推理

在完成解析和存储后，最终层是一个能够查询数据并对其进行推理的代理。我们使用 [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) ——Anthropic 的开源 TypeScript SDK，用于在 Claude 之上构建代理应用程序。它提供与 Claude Code 相同的工具使用编排和多轮对话管理能力，并以库的形式对外提供。对于本项目而言，这是一个自然的选择：SDK 原生支持 TypeScript 中的 MCP 工具注册、扩展思考和流式处理。不过，你也可以始终将任何你选择的代理框架与 LanceDB 和 LiteParse 配对使用。

![](https://cdn.prod.website-files.com/69b2da72cae7eea2b0091d5f/69d4289834db54067e837732_agent-flow-liteparse-lancedb.png)

Claude Agent SDK 的核心抽象是 `query()` ：一个异步生成器，当代理思考、调用工具时以流的形式传输消息，并生成最终答案。代理通过系统提示、一组允许的工具以及可选的扩展思考进行配置。它管理自身的对话历史，因此多轮会话无需手动状态管理即可正常工作。

#### Defining the Tools

代理通过两个工具与 LanceDB 交互，这两个工具通过模型上下文协议（MCP）暴露。第一个工具是\`search\`——一种向量相似度搜索，它接收查询字符串，对其进行嵌入，并返回最匹配的文本块以及每个文本块的页面截图路径：

TypeScript

```typescript
const mcpSearchTool = tool(
  "search",
  "Search a knowledge base to find the answer to a user's question.",
  {
    query: z.string().describe("Search query"),
    chunkLimit: z.number().int().min(1).optional()
      .describe("Maximum number of text chunks to return."),
  },
  searchTool,
);
```

第二个是 `get_image` ——一个定向获取，用于检索特定页面截图的原始 PNG 字节。这是多模态升级路径：代理首先调用 `search` ，如果文本结果不足，就使用从搜索中返回的截图路径调用 `get_image` 以获取视觉上下文。

Python

```python
const mcpGetImageTool = tool(
  "get_image",
  "Get the full page screenshot associated with a search result.",
  { imagePath: z.string().describe("Path of the image to read") },
  getImageTool,
);
```

这两个工具通过 SDK 在单个 MCP 服务器上注册：

TypeScript

```typescript
export const retrievalMcp = createSdkMcpServer({
  name: "retrieval",
  version: "1.0.0",
  tools: [mcpSearchTool, mcpGetImageTool],
});
```

##### Configuring the Agent

代理配置将所有部分连接在一起。系统提示指示代理遵循两步检索策略——先进行文本搜索，必要时使用图像作为备选——并且要求所有回答必须严格基于检索到的内容，而非先前的医学知识。

TypeScript

```typescript
export const queryOptions: Options = {
  allowedTools: ["mcp__retrieval__*"],
  permissionMode: "default",
  systemPrompt: systemPrompt,
  mcpServers: {
    retrieval: retrievalMcp,
  },
  thinking: {
    type: "enabled",
    budgetTokens: 1024,
  },
};
```

##### The Query Loop

在运行时， `query()` 返回一个异步消息流。代理自主决定何时调用工具、运行多少轮搜索，以及何时拥有足够的上下文来回答：

TypeScript

```typescript
for await (const message of query({ prompt, options })) {
  if (message.type === "assistant") {
    // Agent is thinking, responding, or calling a tool
  } else if (message.type === "result") {
    // Final answer (or error)
  }
}
```

对于像" *多少种药物类别将'胃部不适'列为副作用？* "这样的问题，其追踪过程如下：

1. `search("胃部不适的副作用")`: 返回文本块，但向量搜索仅呈现了七个匹配类别中的几个。因此代理决定进行另一次工具调用来确认。
2. `get_image("screenshots/...page_1.png")`: 检索完整页面截图以直观扫描所有类别。
3. `get_image("screenshots/...page_2.png")` ：获取第 2 页。
4. **回应** ：在两个页面上统计了七个类别，基于视觉布局。

代理会 **逐问** 决定检索策略。简单查询需要一次 `search` 调用。跨类别推理可能需要两到三次。当仅靠文本无法判断时（例如，确定某个术语是作为列标题还是单元格值出现时），代理会调用 `get_image` 来检查页面的视觉布局。根据代理中底层模型的质量，可能需要更少或更多的工具调用才能生成最终答案。

##### Analysis

**系统的优势之处** ：代理在直接查询、歧义消除、否定处理、跨类别推理和同义词解析方面表现出色。这些能力需要精确的检索和多步推理——这正是分离式架构的设计目标。此外，代理还能正确区分近似重复的类别（例如“降低血压”与“降低血压和心率”），将用户语言映射到 PDF 术语（如“nausea”→“恶心或呕吐”），并计算跨类别集的交集。

**Where it struggles (and why)**:

**AG-01：“整个图表中列出的独特副作用总数是多少？”** – 该代理进行了 7 次搜索调用并检索了页面截图，但仍计算错误。问题的根本在于：向量搜索无法保证覆盖所有 11 个类别的全部内容，即使有图像回退，在密集的两页表格中统计 21 个独特项目并对近似重复项（如“皮疹”与“皮疹/潮红”）进行去重，对视觉模型而言也容易出错。在这种情况下，对规范化模式执行 SQL 查询（ `SELECT COUNT(DISTINCT side_effect) FROM ...`）会非常简单。

**AG-03：“有多少种药物类别将‘Upset stomach’列为副作用？”——** 类似问题：正确答案是 7，但智能代理少算了。对“upset stomach”进行文本搜索找到了一些匹配的类别，但并非全部七个。该智能代理尝试图像检索，但仍遗漏了“Upset stomach”出现在表格视觉密集区域的类别。

**BG-01：“Xanax 用于什么？”** – 代理需要将品牌名称 Xanax 解析为通用名称 Alprazolam，定位到“缓解神经紧张或助眠”类别，并返回该类别名称。查询链在检索步骤中失败——初始搜索未找到正确的片段，代理无法从该步骤恢复。

观察到以下一般模式：该流程能够很好地处理针对性、范围明确的问题，但在对整个文档进行全面聚合时存在困难。这是向量搜索作为检索机制的固有局限性——其设计目的是用于相关性排序，而非完整性。添加一个额外的结构化查询工具（基于从解析输出中导出的规范化模式的 SQL），可以通过允许代理决定最有用的内容来直接解决这一不足。

#### What We Learned

**结构保留复合** ：决定使用 LiteParse 的结构化文本输出（而非展平为 Markdown 或纯文本）在整个流程中取得了成效。列标识在分块过程中得以保留，检索返回了代理可信任的上下文，而那些会破坏纯文本流程的歧义消除问题正确率达到 100%。如果只能在文档问答系统的某一部分投入资源，应通过更好的解析优先投入上游数据质量。

**多模态回退值得这种复杂性** ：将页面截图与文本块一起存储在 LanceDB 中，在数据摄入时仅增加了最小的开销，但为代理提供了可靠的退路。一半的评估问题触发了图像检索——并非因为文本搜索完全失败，而是因为代理使用视觉上下文来验证或扩展文本结果。每次图像调用的成本更高，但替代方案是错误的答案。

**向量搜索追求相关性而非完整性** ：聚合失败让这一点变得很明确。当一个问题需要对文档进行全面覆盖（“统计所有列出 X 的类别”）时，向量相似度搜索无法保证能找出所有匹配的片段。这是近似最近邻检索的基本特性，而非实现中的错误。对于生产系统，将向量搜索与结构化查询工具（规范化模式上的 SQL）或图查询工具（可遍历路径的工具）结合使用，可以弥补这一不足。

**构建评估套件要尽早** ：这个包含 20 道题的评估与流水线本身同样有价值。它暴露了失败模式——近乎重复的类别名称、品牌到通用名的解析链、详尽计数——这些是手动测试无法发现的。每个类别都针对特定的架构挑战，这使得诊断失败究竟是解析问题、检索问题还是推理问题变得简单。

**本地优先的工具简化了迭代过程** ：LiteParse、LanceDB 和 Claude 代理 SDK 均为开源工具/软件包，它们可在本地运行，除嵌入和推理 API 外，无其他外部服务依赖。这使得开发循环变得高效：更改分块策略，重新运行 `bun run process` ，重新执行评估并比较分数。无需部署步骤，无需管理基础设施，也无冷启动问题。

## 结构化（1）

### 2026-04-10 11:18:00

#### 文章主旨

这篇文章的核心观点是：**PDF 问答难点不在 “把文字读出来”，而在 “保留文档结构并按问题选择合适的检索方式”**。作者通过**LiteParse + LanceDB + Claude Agent SDK**搭建了一条端到端流程，证明了 “结构化解析 + 多模态检索 + 代理推理” 比传统纯文本方案更可靠。

#### 1. 为什么 PDF 问答比看起来更难

- 传统 PDF QA 流程通常是：**提取文本 → 分块 → 向量化 → 检索回答**，对简单问题有效，但遇到表格、标题层级、页面布局时容易失真。
- 问题的根源是：**PDF 的含义不仅在文字里，还在布局里**。例如药品副作用表中，“抑郁” 既可能是 “用药原因”，也可能是 “副作用”；一旦表格被压平成普通文本，列关系就丢了。
- 另一种做法是直接把整页图像交给视觉语言模型（VLM）处理，但代价较高：
  - **每页推理成本高**
  - 长文档表现变差
  - 难以系统评估
  - 模型可能看错页面区域
- 作者认为，典型 PDF QA 常把 3 件事混在一起：
  - **解析**：从文档中提取结构化内容
  - **检索**：找到与问题相关的片段
  - **推理**：综合生成答案
- 这三者如果不分离，系统会变得**难扩展、难调试、也难稳定提升**。

#### 2. LiteParse 的作用：本地、保留布局的 PDF 解析

- LiteParse 是 LlamaIndex 推出的开源解析器，**2026 年 3 月发布**，特点是：
  - 布局感知
  - 本地运行
  - 适合智能代理工作流
- 它的关键设计不是把表格 “翻译” 成 Markdown，而是把文本投影到**虚拟字符网格**中，尽量保留原始页面的空间关系。
- 这背后的思路是：**LLM 本来就具备一定 “读表格” 的能力**，解析器更重要的职责是忠实保留结构，而不是提前替模型解释。
- 对代理系统的价值在于：**把解析和推理拆开**。代理不再每次都要从混乱文本里 “猜布局”，而是在一个确定、结构化的基础上推理。

##### LiteParse 的关键能力

- **选择性 OCR**
  - 默认优先直接提取原生 PDF 文本
  - 只有文本不可提取或乱码时，才启用`Tesseract.js`
  - 数字原生 PDF 可以完全跳过 OCR
- **页面截图**
  - 通过 PDFium 生成高分辨率页面图像
  - 为后续视觉回退提供基础，不必重新处理文档
- **结构化输出**
  - 输出包括：每页文本、边界框、字体信息、图像数据
  - 统一为 JSON 格式
- **本地执行**
  - 不依赖云服务和 API Key
  - 适合敏感文档和受限环境

#### 3. 为什么选择 LanceDB：把文本、向量和图像放在一起

- LiteParse 每页会产生两类结果：
  - 结构化文本
  - 页面截图
- 作者认为最自然的存储方式是：**每页或每个块作为一行，文本、向量、截图并排存储**。
- LanceDB 适合这个场景，因为它原生支持**多模态数据存储**，不需要把：
  - 向量数据库
  - 元数据存储
  - 对象存储
  分开维护。
- 这样做的实际好处：
  - **治理更简单**：检索结果和源文档内容一致，不容易 “漂移”
  - **查询更顺畅**：一次取回即可得到文本、向量，必要时还能拿到图像字节
  - **决策更灵活**：检索层可以根据问题决定要文本还是图像
- LanceDB 也是**本地嵌入式**数据库，与 LiteParse 的本地优先思路一致。
- 它开箱即用支持：
  - **向量搜索**
  - **混合搜索（向量 + 全文）**
- 这很适合文档问答，因为有些问题依赖语义相似，有些则更依赖**术语精确匹配**。

#### 4. 数据集：一份小而难的药品副作用 PDF

- 使用的数据集来自**MedStar Visiting Nurse Association**，是一份**两页 PDF**。
- 文档内容是：把**11 类药物**映射到：
  - 用药原因
  - 通用名 / 商品名
  - 常见副作用
- 文档有明确三列结构：
  - **用药原因**
  - **药品名称：通用名（商品名）**
  - **副作用**
- 每一行表示的是**药物类别**，不是单个药物。
- 一些特殊情况增加了难度：
  - 某些类别有子标题，如降血压下又分**ACE 抑制剂、ARB、利尿剂**
  - 某些药物没有商品名，如**吗啡、阿司匹林、肝素**

##### 这个数据集为什么难

- **同义词不匹配**
  - PDF 里写的是 “恶心或呕吐”，用户可能问 “恶心”
  - PDF 写 “有助于缓解炎症”，用户可能问 “抗炎药”
- **列消歧**
  - 同一词可能同时出现在 “原因” 和 “副作用” 列中
  - 例如 “Queasiness”“呕吐” 都会跨列出现
- **近似重复类别**
  - “降低血压” 和 “降低血压和心率” 看起来很像，但其实不同
- **副作用按类别列出**
  - 不是按单个药物列出，系统不能擅自细化
- **跨类别推理**
  - 例如问 “抗凝药和降胆固醇药有哪些共同副作用”，需要跨多类做集合运算，不是单次检索能解决

#### 5. 预处理流程：从 PDF 到 LanceDB

- 整体预处理分四步：
  - **解析**
  - **分块**
  - **截图**
  - **存储**
- 完整流程实现于`processing.ts`。

##### 5.1 解析与分块

- LiteParse 先解析 PDF，提取每页布局感知文本。
- 这个 PDF 是原生数字文档，因此**不需要 OCR**。
- 之后使用 Chonkie 的`RecursiveChunker`分块，块大小设为**4096 字符**。
- 因为原文只有两页且内容不长，所以最终几乎是：
  - **每页一个块**
- 关键价值在于：**分块后仍然保留列关系**。例如 “头晕” 仍能被看作位于 “副作用” 列，而不是 “用药原因” 列。

##### 5.2 页面截图

- LiteParse 同时通过`screenshot ()` API 为每页生成高分辨率 PNG。
- 截图保存到磁盘，并通过页码与文本块关联。
- 这就是所谓的**多模态回退机制**：
  - 先靠文本搜索
  - 如果不够，再让代理查看整页图像

##### 5.3 向量化与存储

- 每个文本块用 Google 的**`gemini-embedding-2-preview`**做嵌入。
- 向量维度是**3072 维**。
- Lance 表中每一行包含：
  - `id`
  - `image`（PNG 二进制）
  - `vector`
  - `text`
- 作者强调一个很实用的点：**图像直接以二进制列存表，而不是只存路径**，这样查询时可以一次返回视觉上下文，不需要二次读取。

##### 5.4 建索引与执行方式

- 向量列使用**HNSW-SQ**建索引。
- 适合这个小数据集，因为它更重视**召回率**。
- 对更大规模场景，LanceDB 也支持**IVF-PQ**，能用更低内存换取更大规模索引能力。
- 整个流程作为一个 CLI 命令执行：
  - `bun run process &lt;pdf>`
- 对这份**2 页 PDF**，几秒钟内就能完成，并生成本地`.lancedb/`数据目录。

#### 6. 代理层：Claude 如何做 “检索 + 推理”

- 解析和存储完成后，最后一层是代理。
- 作者使用的是**Claude Agent SDK**，这是 Anthropic 的开源 TypeScript SDK。
- 它支持：
  - 工具调用编排
  - 多轮对话管理
  - MCP 工具注册
  - 扩展思考
  - 流式输出

##### 6.1 两个核心工具

###### `search`
- 功能：根据查询做向量搜索
- 输入：查询字符串、可选返回块数
- 输出：最相关的文本块，以及对应页面截图路径

###### `get_image`
- 功能：按路径读取某个页面截图的原始 PNG 字节
- 作用：当文本不足时，代理可以升级到视觉上下文

- 这两个工具通过一个 MCP 服务器统一暴露给代理使用。

##### 6.2 代理策略

- 系统提示要求代理遵循两步策略：
  1. **先文本检索**
  2. **必要时再看图像**
- 并且要求回答必须**严格基于检索内容**，不能依赖模型已有的医学常识。

##### 6.3 实际查询示例

以问题 “**多少种药物类别把‘胃部不适’列为副作用？**” 为例：

- 第一步：`search (" 胃部不适的副作用 ")`
  - 找到部分相关类别，但不完整
- 第二步：`get_image (page_1)`
  - 查看第 1 页表格布局
- 第三步：`get_image (page_2)`
  - 再检查第 2 页
- 最终：代理通过视觉扫描两页，统计出答案

- 这说明代理会根据问题难度动态选择工具：
  - 简单问题：可能只需 1 次`search`
  - 跨类别问题：可能需要 2–3 次检索
  - 涉及列位置或表格整体关系时：会进一步调用`get_image`

- 难题会触发多轮调用，例如：
  - `XC-02`：**7 次 search + 2 次 image**
  - `AG-02`：**8 次 search + 1 次 image**
- 说明代理确实会根据问题复杂度增加取证步骤，而不是固定流程。

#### 8. 系统表现好的地方与薄弱点

##### 8.1 表现好的地方

- 在以下方面表现很强：
  - **直接查询**
  - **消歧**
  - **否定处理**
  - **跨类别推理**
  - **同义词解析**
- 例如它能正确区分：
  - “降低血压”
  - “降低血压和心率”
- 也能把用户表达映射到文档表达，如：
  - `nausea` → “恶心或呕吐”

##### 8.2 主要失败点

###### AG-01：统计整个图表里的独特副作用总数
- 问题要求统计**21 个独特副作用**
- 代理进行了**7 次搜索**并看了截图，但仍然算错
- 原因不是模型完全不会，而是：
  - 向量搜索不能保证覆盖所有**11 个类别**
  - 视觉模型在密集表格里做去重也容易错
  - 类似 “皮疹” 和 “皮疹 / 潮红” 这类近似重复项难规范化
- 作者指出：这种问题如果有结构化表，直接跑 SQL 会很简单，比如：
  - `SELECT COUNT (DISTINCT side_effect) FROM ...`

###### AG-03：有多少药物类别把 “Upset stomach” 列为副作用
- 正确答案是**7**
- 代理少算了
- 原因类似：搜索找到了部分匹配，但没覆盖全部；图像回退也没完全补齐

###### BG-01：Xanax 用于什么
- 这题要求：
  - 先把品牌名**Xanax**
  - 映射成通用名**Alprazolam**
  - 再定位到对应类别 “缓解神经紧张或助眠”
- 失败点发生在**检索阶段**：第一次搜索没找到正确片段，后续也无法恢复

#### 9. 作者总结的核心经验

##### 9.1 结构保留会产生 “连锁收益”

- LiteParse 保留下来的布局结构，不只是 “解析更好看”，而是直接影响后面所有步骤。
- 尤其在消歧题上，系统达到**100%**，说明结构化解析是整个流程成功的基础。
- 作者的建议很明确：**如果只能优先优化一处，就先优化解析质量。**

##### 9.2 多模态回退是值得的

- 将截图和文本块一起存入 LanceDB，增加的复杂度并不高。
- 但它显著增强了系统可靠性。
- 评估中，**一半的问题触发了图像检索**。
- 这些图像调用不一定是因为文本搜索完全失败，而是代理用视觉上下文来**验证或补足文本结果**。

##### 9.3 向量搜索适合 “相关性”，不适合 “完整性”

- 这篇文章最重要的一个结论是：
  - **向量搜索擅长找 “最相关的内容”**
  - **不擅长保证 “找全所有内容”**
- 所以对于 “统计全部”“列出所有”“做全局聚合” 类问题，单靠向量检索不够。
- 生产环境更适合加入额外工具，如：
  - **SQL 查询工具**
  - **图查询工具**

##### 9.4 评估集应该尽早搭建

- 这个**20 题评估集**的价值几乎和流程本身一样大。
- 它帮助作者定位问题到底出在：
  - 解析
  - 检索
  - 还是推理
- 例如品牌名映射失败、全局计数失败、近似类别混淆，这些问题靠随手试几题很难稳定暴露。

##### 9.5 本地优先让迭代更快

- LiteParse、LanceDB、Claude Agent SDK 都是开源、可本地运行的组件。
- 除了嵌入和推理 API，没有额外服务依赖。
- 这样开发者可以快速循环：
  - 改分块策略
  - 重新执行`bun run process`
  - 再跑评估
  - 比较分数变化

#### 10. 结论与启发

- 这篇文章想说明的不是 “某个模型最强”，而是：**PDF QA 的关键在架构设计**。
- 当文档包含表格、混合布局、半结构化内容时，最稳妥的路线是：
  - **先用 LiteParse 保住结构**
  - **再用 LanceDB 同时管理文本、向量和图像**
  - **最后让代理按需选择文本检索或视觉回退**
- 从结果看，这套方法对**定向查询、多步推理、消歧**很有效，但对**全量统计和完整覆盖型问题**仍有短板。
- 最终启发是：**构建 PDF 问答系统时，不仅要看它什么时候答对，更要清楚它什么时候会答错、为什么会答错。**

## 产品-最佳实践（1）

### 2026-04-10 11:20:04

#### Smart Parsing Meets Sharp Retrieval：基于药品副作用 PDF QA 的最佳实践示例

##### 背景概述

你提供的内容核心讲的是一个很典型但也很容易 “踩坑” 的问题：**PDF 问答并不只是文本检索问题，而是解析、检索、推理三件事的协同问题**。

为了把这个结论落到实处，下面我用文中那个**药品副作用说明书 PDF**作为一个具体实例，给出一套更适合落地的**最佳实践**。

---

##### 具体实例

###### 业务问题

用户提问：

> “有多少种药物类别将‘Upset stomach（胃部不适）’列为副作用？”

这是一个非常好的测试问题，因为它同时考验：

- 是否保留了 PDF 中的**列结构**
- 是否支持**术语同义映射**
- 是否能做**全局覆盖式统计**
- 是否知道什么时候应该用**向量检索**，什么时候不该只依赖它

---

##### 先看一个容易失败的做法

很多系统会这样处理：

1. 从 PDF 提取纯文本
2. 按固定长度切块
3. 向量化后存入向量数据库
4. 用户提问时做相似度检索
5. 让 LLM 根据返回片段回答

###### 问题在哪里

对于这个问题，这种做法很容易答错，原因有三点：

- **“Upset stomach” 可能分散在多个类别中**，向量检索返回的是 “最相关的几个”，不是 “所有命中的”
- 如果表格被压平成纯文本，模型可能不知道 “Upset stomach” 是在**副作用列**，还是出现在别的列
- 这是一个**统计问题**，本质更像数据库查询，而不是语义相似度匹配

也就是说：

> **相关性检索 ≠ 完整性检索**

---

##### 推荐的最佳实践

##### 1. 把 “解析、检索、推理” 彻底分层

###### 最佳实践

不要让一个模型在一次调用中同时完成：

- 解析 PDF 结构
- 找相关片段
- 生成答案

而应该拆成三层：

1. **解析层**：用 LiteParse 保留布局、表格、页码、边界框
2. **检索层**：用 LanceDB 存文本块、向量、截图，并区分检索模式
3. **推理层**：让代理只做 “选择工具 + 组合证据 + 生成回答”

###### 为什么这是最佳实践

因为这样可以明显提升：

- **可调试性**：错在解析、检索还是推理，一眼能定位
- **可扩展性**：后面可以单独替换 embedding、数据库、模型
- **稳定性**：避免模型每次都重新 “猜” 表格结构

---

##### 2. 在这个实例里，优先保留表格结构，而不是急着转 Markdown

###### 最佳实践

对于药品副作用说明书这类 PDF，解析后应保留：

- 页码
- 每个文本块的空间位置
- 列关系
- 页面截图
- 字体 / 布局元数据

而不是只保留一段段普通字符串。

###### 结合本例说明

像下面这些词，单看文本都可能歧义很大：

- “抑郁”
- “呕吐”
- “Queasiness”
- “Upset stomach”

它们可能出现在：

- 用药原因列
- 副作用列
- 类别标题
- 单元格内容

如果解析阶段把这些结构弄丢，后面检索再强也补不回来。

###### 结论

> **上游结构保真，比下游提示词优化更重要。**

---

##### 3. 用 LanceDB 存 “文本 + 向量 + 页面图像”，不要把图像放成孤立附件

###### 最佳实践

每个 chunk 对应一条统一记录，至少包含：

- `text`
- `vector`
- `page_num`
- `image`
- `source_id`
- `chunk_id`

###### 为什么这样设计更好

在这个实例里，代理一开始可能只需要文本检索；但当它发现：

- 结果不完整
- 列归属不明确
- 需要跨整页确认

它就应该立刻升级到页面图像。

如果图像和文本不在同一条记录或同一存储层里，会出现很多工程问题：

- 二次查询复杂
- 元数据对不上
- 版本不同步
- 检索结果和原文截图不一致

###### 推荐原则

> **把 “文本证据” 和 “视觉证据” 作为同一知识单元管理。**

---

##### 4. 针对这个问题，不要只给代理一个`search`工具

###### 最佳实践

至少准备三类工具，而不是只有向量搜索：

###### A. 语义检索工具
适合：

- 同义词查询
- 品牌名 / 通用名映射
- 模糊问法

例如：

- “Xanax 用于什么？”
- “哪些药和 nausea 有关？”

###### B. 图像获取工具
适合：

- 判断词出现在哪一列
- 做整页核对
- 表格跨区域检查

例如：

- “这个词是副作用还是用药原因？”
- “这个页面里还有没有漏掉的类别？”

###### C. 结构化查询工具
适合：

- 计数
- 去重
- 集合交集
- 否定验证
- 全文覆盖

例如本文这个问题：

> “有多少种药物类别将 Upset stomach 列为副作用？”

最稳妥的方式其实不是纯向量检索，而是：

1. 解析时把表格规范化为结构化记录
2. 把副作用拆成可查询字段
3. 用 SQL / 过滤表达式做精确计数

###### 一个更好的执行路径

对于这个问题，代理的决策逻辑应是：

1. 先用`search ("Upset stomach side effect")`做候选召回
2. 若问题类型被识别为 “count /aggregate”，优先调用结构化查询工具
3. 如结构化结果和文本证据不一致，再调用`get_image (page)`做核验

###### 结论

> **聚合类问题的第一工具不应是向量检索，而应是结构化查询。**

---

##### 5. 为 “表格型 PDF” 单独做规范化模式

###### 最佳实践

不要只保留 chunk 文本；应额外生成一张适合查询的规范化表，例如：

| category | generic_name | brand_name | side_effect |
|---|---|---|---|
| 止痛 | aspirin | Bayer | upset stomach |
| 止痛 | morphine | null | nausea or vomiting |
| 降胆固醇 | atorvastatin | Lipitor | upset stomach |

###### 在本例中的价值

这样一来，像下面这些问题都能直接变成结构化查询：

- “多少种药物类别将胃部不适列为副作用？”
- “抗凝药和降胆固醇药有哪些重叠副作用？”
- “头痛是否属于氯沙坦所属类别的副作用？”

###### 示例 SQL 思路

```sql
SELECT COUNT (DISTINCT category)
FROM medication_side_effects
WHERE LOWER (side_effect) = 'upset stomach';
```

如果副作用字段是列表拆分后的行式存储，这类问题会比让 LLM 看整页截图稳定得多。

---

##### 6. 让代理先判断 “问题类型”，再选择检索路径

###### 最佳实践

在进入工具调用前，先做一个轻量路由：

- `lookup`：直接事实查询
- `mapping`：品牌名 / 通用名映射
- `disambiguation`：列归属判断
- `aggregation`：计数、去重、全集扫描
- `reasoning`：交集、比较、否定、组合推理

###### 结合本例

“有多少种药物类别将‘Upset stomach’列为副作用？”  
应被归为：

- `aggregation`
- `requires_complete_coverage = true`
- `column_sensitive = true`

因此最优策略应是：

1. 结构化查询优先
2. 文本检索辅助解释
3. 图像只作核验，不作主要统计依据

###### 推荐原则

> **不要让代理每次都从零开始摸索；给它明确的问题路由策略。**

---

##### 7. 同义词要在检索前处理，不要完全依赖 embedding “自己懂”

###### 最佳实践

在医疗、药物、保险、法律等文档中，建议建立一个领域词汇映射层，例如：

- `nausea` → `nausea or vomiting`
- `anti-inflammatory` → `helps relieve inflammation`
- `upset stomach` ↔ `stomach upset` / `queasiness`（视文档语义定义）

###### 为什么重要

embedding 可以帮助 “接近”，但不能保证：

- 召回完整
- 区分术语角色
- 对计数场景稳定

###### 在本例中的做法

对于用户问题中的关键词：

1. 先做标准化
2. 再进行混合检索
3. 在回答中说明 “文档原始术语”

例如：

> 用户说 “胃部不适”，系统内部扩展匹配`Upset stomach`，但答案里仍引用 PDF 原文表述。

---

##### 8. 混合检索优于单一向量检索

###### 最佳实践

对于表格型 PDF，建议默认使用：

- **向量检索**：解决语义匹配
- **全文关键词检索**：保证术语精确命中
- **元数据过滤**：限制页码、列、类别

###### 在本例中的收益

如果只做向量检索，“Upset stomach” 可能只召回一部分相关类别；  
但如果同时有关键词匹配和字段过滤，覆盖率会更高。

###### 推荐检索逻辑

```text
候选召回 = 向量检索 Top-K + 关键词命中结果 + 结构化字段过滤结果
最终排序 = 相关性分数 + 列匹配权重 + 页内覆盖度
```

---

##### 9. 图像回退是 “校验机制”，不是 “万金油”

###### 最佳实践

页面截图非常有价值，但不应该被滥用。

更合理的策略是只在这些场景触发：

- 文本结果存在冲突
- 列归属不清
- 怀疑漏召回
- 需要看整页布局
- 表格跨页或密集区域难以从 chunk 判断

###### 为什么

因为图像推理的缺点仍然明显：

- 成本更高
- 速度更慢
- 难以保证计数精度
- 对密集表格容易漏看

###### 在本例中的建议

对于 “统计出现次数” 这种题目：

- 图像适合做**确认**
- 不适合做**主统计来源**

---

##### 10. 评估集要按 “失败模式” 设计，而不是只做几个样例问答

###### 最佳实践

你提供的文章里，最值得借鉴的一点是：  
**评估不是泛泛地测 “答得准不准”，而是针对具体风险点设计问题。**

建议评估维度至少包括：

- 直接查询
- 同义词改写
- 品牌名 / 通用名映射
- 列消歧
- 否定与缺失
- 跨类别推理
- 聚合与计数

###### 在本例上，推荐补强的评估问题

围绕 “Upset stomach” 这个实例，可以补出一组更强的测试题：

1. 哪些药物类别将`Upset stomach`列为副作用？
2. 一共有多少种类别包含`Upset stomach`？
3. `Upset stomach`是否只出现在副作用列？
4. `Queasiness`和`Upset stomach`是否属于同一语义项？
5. 止痛类和降胆固醇类是否都包含`Upset stomach`？
6. 是否有药物类别包含`Upset stomach`，但不包含`nausea or vomiting`？

这些问题能更准确地判断系统到底是：

- 召回不全
- 列识别错误
- 同义词映射不稳
- 推理链断裂

---

##### 一个更优的落地方案

##### 推荐架构

```text
PDF
 -> LiteParse（布局感知解析 + 截图）
 -> 双路输出
    -> A. Chunk + Embedding -> LanceDB
    -> B. 表格规范化 -> SQL / 结构化查询层
 -> Agent Router
    -> lookup /mapping -> 混合检索
    -> aggregation -> SQL 优先
    -> disambiguation -> 文本 + 图像核验
    -> reasoning -> 检索结果组合推理
```

---

##### 基于该实例的最佳实践清单

###### 设计层面

- **先保证解析质量，再优化提示词**
- **把 PDF QA 拆成解析、检索、推理三层**
- **表格类问题必须考虑结构化查询通道**
- **多模态是回退机制，不是默认主路径**

###### 数据层面

- **保存布局感知文本，不要只存纯文本**
- **文本、向量、截图放在同一知识单元中**
- **为表格文档额外构建规范化 schema**
- **保留页码、列信息、chunk 来源等元数据**

###### 检索层面

- **向量检索负责相关性，不负责完整性**
- **计数、全集扫描、去重问题优先走 SQL / 结构化查询**
- **混合检索优于单一 ANN 检索**
- **同义词标准化应在查询前完成**

###### 代理层面

- **先识别问题类型，再决定工具链**
- **图像只在不确定时触发**
- **回答必须显式绑定证据来源**
- **对无法覆盖全文的问题，应允许代理声明不确定性**

###### 评估层面

- **按失败模式建评测集**
- **聚合类问题单独监控**
- **品牌名到通用名链路要专项测试**
- **记录每题的工具调用路径，便于诊断系统短板**
