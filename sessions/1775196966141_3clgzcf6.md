## 正文

**Mason Daugherty**

### 开放模型已经跨越了一个门槛

TL;DR: 开源模型如 GLM-5 和 MiniMax M2.7 现在在核心代理任务——文件操作、工具使用和指令遵循——中已能与闭源前沿模型相媲美，以极低的成本和延迟。以下是我们的评估结果以及如何在 Deep Agents 中开始使用它们。

---

如果你通过大量开放基准测试跟踪开放模型的进展，这并不令人惊讶，例如

[SWE-Rebench](https://swe-rebench.com/) 和

[Terminal Bench 2.0](https://www.tbench.ai/leaderboard/terminal-bench/2.0)

。工具调用可靠，指令遵循一致。对于在生产环境中部署代理的开发人员来说，开放模型现在提供了一定程度的一致性和可预测性，这使得实际工作流更加可行。

#### 为什么开源模型

在探索开放式模型时，构建者和客户往往会关注几个关键因素： 成本、延迟和任务性能 。

从理论上讲，为每项任务使用处于最高推理水平的最智能前沿模型会非常理想。但在实际中，有两个限制因素使其不可行：成本和延迟。封闭型前沿模型在高吞吐量工作负载下的运行成本可能比开放模型高8到10倍，而且对于交互式产品中用户期望的响应时间而言，它们往往太慢。

![Image](https://pbs.twimg.com/media/HE6yQgWXQAANGaK?format=png&name=large)

为了便于理解定价：一个每天生成 10M tokens 的应用在 Opus 4.6 上每天成本约为 250 美元，而在 MiniMax M2.7 上每天约为 12 美元。这每年的差异约为 87,000 美元。

开放模型往往比封闭的前沿模型更小，并且可以在专业推理基础设施上加速——像

[Groq](https://groq.com/)，

[Fireworks](https://fireworks.ai/)

，以及

[Baseten](https://www.baseten.co/)

优化延迟和吞吐量，其水平远远超出大多数团队独自能实现的范围。

[OpenRouter data](https://openrouter.ai/z-ai/glm-5/performance)

显示，Baseten 上的 GLM-5 平均延迟为 0.65 秒，吞吐量为每秒 70 个 token，而 Claude Opus 4.6 的延迟为 2.56 秒，吞吐量为每秒 34 个 token。对于对延迟敏感的产品，这个差距很难通过工程手段弥补。

#### 我们如何评估

对于开源模型，我们开展了七项评估类别：文件操作、工具使用、检索、对话、记忆、摘要生成和“单元测试”。这些涵盖了检验基础能力的任务：模型能否可靠地调用工具、遵循结构化指令并操作文件？这些是决定模型是否能在智能体框架中使用的关键能力。

每个评估用例定义了成功断言（用于确定正确性的硬性失败检查）和效率断言（用于衡量模型是如何得出结果的软性检查）。我们报告四个指标：

- 正确性 — 模型解决的测试用例的比例：\`passed / total\`。分数为 0.68 时，意味着 68%的测试用例被正确解决。这是主要的质量指标。
- 求解率 — 是准确性和速度的综合度量。对于每个测试，我们计算 \`expected\_steps / wall\_clock\_seconds\`；失败的测试贡献值为零。最终得分是所有测试的平均值。越高越好——能够既正确又快速地解决任务的模型得分最高。
- 步骤比率 — 在所有测试中汇总的模型实际执行的代理步骤数与预期步骤数的对比：\`total\_actual\_steps / total\_expected\_steps\`。值为 1.0 表示模型使用的步骤数正好是预期的数量。大于 1.0 表示需要更多步骤（效率更低）；小于 1.0 表示需要的步骤数比最初预期的少。
- 工具调用比率 — 与步骤比率概念相同，但统计的是单个工具调用而非步骤。1.0为预算内，高于1.0为超预算，低于1.0为预算不足。

步骤比例和工具调用比例是效率指标。它们不影响测试是否通过，但能揭示模型如何经济地得出答案。一个能在2步而不是预期的5步内解决任务的模型既正确且高效。

#### DIY: 本地运行 Deep Agent 评估

我们的 CI 在 52 个按组组织的模型上运行相同的评估套件，其中包括一个\`open\`组（baseten:zai-org/GLM-5, ollama:minimax-m2.7:cloud, ollama:nemotron-3-super），该组在每个评估工作流中运行。你可以针对任何模型组：

```python
# Run evals against all open models
pytest tests/evals --model-group open

# Run against a specific model
pytest tests/evals --model baseten:zai-org/GLM-5
```

这使得在相同任务上，使用相同评分标准比较开放模型之间以及开放模型与封闭前沿模型变得简单直接。

### 在 Deep Agents SDK 中使用开源模型

切换到开放模型是一个单行修改：

```python
# pip install langchain-baseten
from deepagents import create_deep_agent

agent = create_deep_agent(model="baseten:zai-org/GLM-5")
```

```python
# pip install langchain-openrouter
from deepagents import create_deep_agent

agent = create_deep_agent(model="openrouter:minimax/minimax-m2.7")
```

就这样了。这个工具负责其余工作——它检测模型的上下文窗口大小，禁用不支持的模态，并将正确的身份信息注入系统提示，以便代理知道自己在处理什么。

同一个开源模型通常可以通过多个提供商获取。选择一个符合你的约束条件的提供商。例如，GLM-5 在 baseten（路径：zai-org/GLM-5）、fireworks（路径：fireworks/glm-5）或 ollama（路径：glm-5）上都有可用版本，适用于自托管。相同的模型，相同的框架，不同的基础设施。

LangChain 为最受欢迎的开放模型提供商提供支持。我们本次发布测试过的提供商包括：Baseten、Fireworks、Groq、OpenRouter 和 Ollama（cloud）。

#### 针对您的模型的工具级别调整

开放模型与封闭前沿模型相比，具有不同的上下文窗口、不同的工具调用格式和不同的失效模式。Deep Agents 能够利用并吸收这些差异，让你无需自行处理这些差异。

- 模型身份注入 — 系统提示会在运行时被修补，包含模型名称、提供方、上下文限制和支持的模态。代理知道自己的身份和能力。
- 上下文管理 — 压缩、卸载和摘要阈值适配模型的实际上下文窗口，而非硬编码的默认值。具有 4K 上下文的模型比具有 1M 上下文的 Opus 模型进行更激进的压缩。

#### Deep Agents CLI

每个模型也可以在 Deep Agents CLI 中使用。The

[Deep Agents CLI](https://github.com/langchain-ai/deepagents/tree/main/libs/cli) 是我们的开源编码代理，也是 Claude Code 的替代方案。

除了 Deep Agents SDK 中的所有功能外，CLI 支持运行时模型切换。 我们引入了一个新的中间件（

[ConfigurableModelMiddleware](https://github.com/langchain-ai/deepagents/blob/8be4a2ee3878a3e15c15d56fd64ba8db248a6328/libs/cli/deepagents_cli/configurable_model.py#L145)）以支持在会话过程中切换模型而无需重启代理。这使得诸如使用前沿模型进行规划和使用开放模型进行执行之类的模式成为可能。

你可以在会话中使用 \`/model\` 斜杠命令切换模型。这支持诸如使用前沿模型进行规划来启动任务，然后切换到更便宜的开放模型执行的模式：

#### 开源模型，已经够“能打”了

##### 核心结论
开源模型已经跨过一个关键门槛：在智能体最重要的基础能力上，如文件操作、工具调用和指令遵循，已经能接近甚至对标部分闭源前沿模型。

这意味着，开源模型不再只是“便宜的替代品”，而开始成为可以真正用于生产环境的选择。

##### 为什么这件事重要
企业和开发者选择模型，最看重三点：**成本、延迟、任务效果**。

闭源前沿模型虽然强，但现实问题很明显：
- **太贵**：高吞吐场景下，成本可比开源模型高 8 到 10 倍
- **太慢**：对交互式产品来说，响应速度常常不够理想

文章举了一个很直观的例子：同样是每天生成 1000 万 tokens，使用 Opus 4.6 每天约 250 美元，而 MiniMax M2.7 只要约 12 美元，一年能差出 **8.7 万美元**。

##### 开源模型的新变化
这次变化的重点不只是“能聊天”，而是它们在智能体工作流里的关键能力明显成熟了：

- **工具调用更稳定**
- **指令遵循更一致**
- **执行流程更可预测**
- **延迟更低，吞吐更高**

对真正做产品的人来说，这比单纯跑分更重要。因为智能体要落地，核心不是“最聪明”，而是“稳定、可控、能持续跑”。

##### 他们是怎么评估的
作者团队围绕智能体常见任务，做了 7 类评估，包括：

- 文件操作
- 工具使用
- 检索
- 对话
- 记忆
- 摘要生成
- 单元测试

主要看四个指标：
- **正确性**：任务做没做对
- **求解率**：做对的同时是否够快
- **步骤比率**：是否用更少步骤完成任务
- **工具调用比率**：是否高效调用工具

简单说，他们不只看“答对没”，还看“做得是否经济高效”。

##### 文章想表达的判断
作者的核心判断是：**开源模型现在已经适合做智能体执行层**。

尤其适合这些场景：
- 对成本敏感的产品
- 对响应速度要求高的交互式应用
- 需要大规模部署代理能力的团队
- 希望灵活切换模型和基础设施的开发者

换句话说，未来很可能不是“闭源替代开源”或“开源替代闭源”，而是：
**闭源模型负责高价值规划，开源模型负责大规模执行。**

##### 对产品和商业的启发
这件事的意义不只是技术进步，更是商业拐点：

1. **AI 产品的单位成本开始明显下降**  
   智能体能力不再只有大公司才能负担。

2. **产品体验更容易做好**  
   延迟下降后，交互式 AI 产品更容易达到可用标准。

3. **模型选择将更像“架构设计”**  
   不同模型按任务分工，而不是只追求“最强模型”。

4. **开源生态的话语权提升**  
   当开源模型在关键任务上“够用且便宜”，行业格局会被重新改写。

##### 一句话总结
这篇文章的核心不是“开源模型已经全面超越闭源”，而是：

**开源模型已经从“能用”进入“值得大规模部署”的阶段，尤其在智能体执行场景里，性价比优势开始真正兑现。**

## 结构化（1）

### 2026-04-03 06:18:20

#### 主旨概括

这篇文章的核心观点是：**开源模型已经跨过了“能不能用于智能体”的门槛**，在文件操作、工具调用、指令遵循等关键代理任务上，已经能和闭源前沿模型接近甚至相当。  
同时，它们在**成本和延迟**上优势明显，因此对需要在生产环境部署智能体的团队来说，正在变成更现实的选择。

##### 1. 为什么说开源模型值得重新评估

- 作者指出，开发者在选择模型时最关心的通常是三件事：**成本、延迟、任务表现**。
- 理想情况下，大家都想用最强的前沿模型完成所有任务，但现实中往往会被两个因素限制：
  - **太贵**
  - **太慢**
- 文中给了一个很直观的成本例子：
  - 一个每天生成 **1000 万 tokens** 的应用，
  - 如果使用 **Opus 4.6**，每天成本约 **250 美元**
  - 如果使用 **MiniMax M2.7**，每天成本约 **12 美元**
  - 一年下来差距大约 **8.7 万美元**
- 这说明：哪怕模型能力接近，只要价格差一个数量级，生产上的选择就会完全不同。

##### 2. 开源模型在速度上的优势也很明显

- 文章强调，开源模型通常更小，更容易在专业推理基础设施上被加速。
- 文中提到的提供商包括：
  - **Groq**
  - **Fireworks**
  - **Baseten**
- 作者引用 OpenRouter 数据举例：
  - **Baseten 上的 GLM-5**
    - 平均延迟约 **0.65 秒**
    - 吞吐量约 **70 tokens/秒**
  - **Claude Opus 4.6**
    - 平均延迟约 **2.56 秒**
    - 吞吐量约 **34 tokens/秒**
- 通俗理解就是：如果你的产品对响应速度敏感，比如聊天助手、交互式编程代理，这种差距很难靠后期工程优化补回来。

##### 3. 他们是怎么评估这些模型的

- 作者没有只看“考试分数”式基准，而是围绕智能体实际会做的事来评估。
- 一共做了 **7 类评估**：
  - 文件操作
  - 工具使用
  - 检索
  - 对话
  - 记忆
  - 摘要生成
  - “单元测试”
- 这些评估主要在检查几个关键问题：
  - 模型能不能**可靠调用工具**
  - 能不能**遵循结构化指令**
  - 能不能**正确操作文件**
- 文章认为，这些能力才是真正决定模型能否进入智能体工作流的基础。

##### 4. 评估看哪些指标

- 文中定义了两类判断：
  - **成功断言**：硬性判断任务是否完成
  - **效率断言**：软性判断模型完成任务的方式是否高效
- 他们主要报告了 **4 个指标**：

###### 正确性（Correctness）
- 计算方式：`passed / total`
- 例如得分 **0.68**，表示 **68% 的测试用例通过**
- 这是最核心的质量指标，代表模型“做没做对”。

###### 求解率（Solve Rate）
- 同时考虑**正确性和速度**
- 每个测试按 `expected_steps / wall_clock_seconds` 计算，失败任务记为 0
- 得分越高，说明模型不仅做对，而且做得快

###### 步骤比率（Step Ratio）
- 计算模型实际用了多少代理步骤，相比预期步骤是多还是少
- `1.0` 表示正好符合预期
- **大于 1.0**：步骤更多，效率偏低
- **小于 1.0**：步骤更少，效率更高

###### 工具调用比率（Tool Call Ratio）
- 思路和步骤比率一样，只是统计对象变成**工具调用次数**
- 用来观察模型是不是“过度调用工具”

- 作者特别强调：  
  **步骤比率和工具调用比率不会影响任务是否通过，但能反映模型完成任务是否经济、高效。**
- 例如，一个任务本来预计要 5 步，模型 2 步就做完了，那它不仅正确，而且效率更高。

##### 5. 结论：开源模型已经能承担核心代理任务

- 作者的总体判断是：**开源模型现在已经具备“可用于智能体”的一致性和可预测性**。
- 尤其是在这些关键任务上表现可靠：
  - 文件操作
  - 工具使用
  - 指令遵循
- 文章还提到，这个结论并不突然，因为此前多个开放基准已经释放过类似信号，比如：
  - **SWE-Rebench**
  - **Terminal Bench 2.0**
- 换句话说，现在的变化不是“开源模型偶尔做得不错”，而是它们已经开始在实际工作流中表现得**稳定可用**。

##### 6. 如何自己复现评估

- 作者提到，他们的 CI 会在 **52 个按组组织的模型** 上跑同一套评估。
- 其中有一个 `open` 组，包含：
  - `baseten:zai-org/GLM-5`
  - `ollama:minimax-m2.7:cloud`
  - `ollama:nemotron-3-super`
- 可以直接运行：

```python
# Run evals against all open models
pytest tests/evals --model-group open

# Run against a specific model
pytest tests/evals --model baseten:zai-org/GLM-5
```

- 这样做的意义是：  
  **可以在同一任务、同一评分标准下，公平比较开源模型之间，以及开源模型和闭源模型之间的差异。**

##### 7. 在 Deep Agents 里接入开源模型很简单

- 作者强调，切换到开源模型几乎只要改一行代码。

使用 GLM-5：

```python
# pip install langchain-baseten
from deepagents import create_deep_agent
agent = create_deep_agent(model="baseten:zai-org/GLM-5")
```

使用 MiniMax M2.7：

```python
# pip install langchain-openrouter
from deepagents import create_deep_agent
agent = create_deep_agent(model="openrouter:minimax/minimax-m2.7")
```

- 框架会自动处理很多麻烦事，包括：
  - 检测上下文窗口大小
  - 禁用模型不支持的模态
  - 把正确的模型身份信息注入系统提示中

- 同一个模型还可以通过多个提供商获取，例如 **GLM-5** 可以在：
  - **Baseten**
  - **Fireworks**
  - **Ollama**
  上使用  
- 这意味着你可以根据自己的需求选择：
  - 更低延迟
  - 更低成本
  - 自托管
  - 更适合现有基础设施的方案

##### 8. Deep Agents 做了哪些“适配层”工作

- 文章指出，开源模型和闭源模型之间常常有这些差异：
  - 上下文窗口不同
  - 工具调用格式不同
  - 失败模式不同
- Deep Agents 的作用，就是把这些差异“吸收掉”，让开发者不用自己逐个处理。

主要包括两类适配：

###### 模型身份注入
- 系统提示会在运行时补充：
  - 模型名称
  - 提供商
  - 上下文限制
  - 支持的模态
- 这样代理能够“知道自己是谁、能做什么”。

###### 上下文管理
- 压缩、卸载、摘要阈值不会写死，而是按模型真实上下文窗口动态调整
- 例如：
  - **4K 上下文模型** 会采用更激进的压缩
  - **1M 上下文的 Opus** 则不需要这么激进

- 简单理解就是：框架会替你针对模型差异做“工具级微调”。

##### 9. CLI 还支持会话中切换模型

- 除了 SDK，文章也介绍了 **Deep Agents CLI**，把它描述为一个开源编码代理，是 **Claude Code 的替代方案**。
- CLI 支持运行时切换模型，依靠的是一个新的中间件：
  - `ConfigurableModelMiddleware`
- 这样做的价值在于，可以把不同模型用在不同环节：
  - **先用强但贵的闭源模型做规划**
  - **再切换到便宜的开源模型做执行**
- 用户可以在会话中通过 `/model` 命令切换模型，不需要重启代理。
- 这是一个很实际的使用模式，因为很多任务中，“规划”并不需要一直用昂贵模型，“执行”更适合用低成本模型承接。

##### 10. 接下来他们想做什么

- 文章最后列出了一些接下来的方向：
  - 记录特定开源模型系列的框架调优模式
  - 测试多模型子代理配置  
    例如：**闭源前沿模型做编排器 + 开源模型做子代理**
- 作者想强调的是：
  - 开源模型已经不只是“能跑”，而是**已经适合智能体应用**
  - 下一步更重要的是建立一套**好的测试框架和评估方法**
  - 这样团队才能衡量：某个模型是否真的适合自己的具体任务

#### 总结

- 这篇文章的结论很明确：**开源模型已经从“实验可用”走到了“生产可考虑”**。
- 它们在智能体核心能力上已经具备可靠性，同时在：
  - **成本**上便宜很多
  - **延迟**上更有优势
  - **部署灵活性**上也更强
- 以 **GLM-5** 和 **MiniMax M2.7** 为代表的开源模型，正在让一种更现实的模式成为可能：  
  **用闭源模型负责高价值推理，用开源模型承担大规模执行。**
