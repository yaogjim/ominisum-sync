## 分析要点

- **核心高价值点**：将终端布局、普通进程控制和Agent生命周期控制分离，并依据idle、working、blocked、done等明确状态进行等待和协调，可显著降低多Agent自动化中的误操作与无限等待。
- **留存建议**：作为多编码智能体编排与终端自动化的实操参考长期保留（包含清晰的控制原语、状态模型、命令示例、异常处理和远程工作流程，可直接支持多Agent测试与审查系统的实现。）

**知识要点**

- Herdr将自动化职责拆分为Layout、Pane和Agent三层：布局负责终端拓扑，Pane负责原始终端进程，Agent负责已识别编码智能体及其生命周期。
- Agent状态检测应设置单一权威来源：完整生命周期钩子优先，否则使用前台进程识别与屏幕清单匹配，避免多个状态来源相互冲突。
- 全屏Agent的备用屏幕内容可能不进入宿主回滚区；读取失败时可改读可见区域，最终再让Agent将完整结果写入临时文件。

**行动项**

- 创建独立审查窗格，保存命令返回的pane\_id，再启动命名审查Agent并提交代码差异审查任务。
- 为Agent等待命令设置明确的目标状态和超时时间，并在blocked状态下读取界面后再决定发送按键。
- 用pane命令运行测试或监视进程，用agent命令处理编码智能体，避免把普通终端输出与Agent生命周期混为一谈。

## 正文

### Agent automation

https://herdr.dev/docs/agent-automation/

Herdr can act as an automation layer for coding agents. A script can control them, or one agent can create work for other agents, inspect their state, and collect their results. The important part is choosing the primitive that matches the job.

Primitive Responsibility

Layout (`workspace`, `tab`, and pane topology) Create and organize terminal locations.

Pane Control a raw terminal: run commands, send input, read output, and wait for output.

Agent Control a recognized coding agent by name or pane and lifecycle state.

A pane exists whether or not it contains an agent. An agent is the recognized process currently running inside a pane. `agent start` therefore requires an existing shell pane and never creates, splits, or moves layout.

Creating a workspace also creates its first tab and root pane; creating a tab creates its root pane. Use the returned pane ID for the first process, and split only when that layout needs another terminal.

Creation commands print JSON. Capture IDs from the response instead of predicting them:

```

created=$(herdr workspace create --cwd ~/project --label api --no-focus)

pane_id=$(printf '%s\n' "$created" | jq -r '.result.root_pane.pane_id')

split=$(herdr pane split "$pane_id" --direction right --no-focus)

review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')
```

`workspace create` returns `.result.workspace`, `.result.tab`, and `.result.root_pane`. `tab create` returns `.result.tab` and `.result.root_pane`. `pane split` returns the new pane as `.result.pane`.

Moving a pane to another workspace changes its workspace-qualified pane ID. After any `pane move`, continue with `.result.move_result.pane.pane_id`; the response keeps the old value at `.result.move_result.previous_pane_id`. A running process keeps its launch-time Herdr environment, but the old `HERDR_PANE_ID` remains an alias for that terminal, so `--current` stays safe. New commands can still resolve the agent by name after the move, but a wait already in progress ends with `agent_not_running`.

Use pane commands for shells, tests, servers, CI watchers, and other ordinary terminal processes. Use agent commands when Herdr needs to understand which agent is running or whether it is `working`, `blocked`, `done`, `idle`, or `unknown`.

#### Agent identity and launch

Section titled “Agent identity and launch”

A pane ID such as `w1:p2` identifies the terminal location. An agent name such as `reviewer` is a convenient alias for the current agent in that pane. Names must match `[a-z][a-z0-9_-]{0,31}` and be unique among live agents. The alias is cleared when that agent exits, is released, or is replaced; it does not permanently rename the pane.

Agent commands accept either a unique live name or the pane ID that currently hosts the agent.

An available shell pane is at its interactive shell prompt: the shell itself owns the foreground, with no foreground command, editor, or agent running. Return the pane to its prompt before calling `agent start`.

`--kind` selects a supported agent and its canonical executable. Supported kinds are `pi`, `claude`, `codex`, `gemini`, `cursor`, `devin`, `agy`, `cline`, `omp`, `mastracode`, `opencode`, `copilot`, `kimi`, `kiro`, `droid`, `amp`, `grok`, `hermes`, `kilo`, `qodercli`, and `maki`. Arguments after `--` are passed unchanged to that executable.

`agent start` returns only after Herdr detects the expected agent in the same terminal and marks it ready for interactive input. Startup waits for 30 seconds by default; `--timeout` must be greater than 3000 and no more than 300000 milliseconds.

```

herdr agent start reviewer --kind codex --pane "$review_pane" -- -m gpt-5.4
```

Agents launched manually are detected automatically and can be addressed by pane ID. Give one a name when a stable human-readable target is useful:

```

herdr agent get w1:p2

herdr agent rename w1:p2 reviewer
```

#### Choose the control surface

Section titled “Choose the control surface”

Goal Command

Run a shell command and submit it `pane run`

Send literal text without Enter `pane send-text`

Send terminal keys or modifier chords `pane send-keys`

Wait for text or a regular expression `pane wait-output`

Start a supported agent in an existing pane `agent start`

Submit a prompt, optionally waiting for it `agent prompt`

Send keys to an agent’s interactive UI `agent send-keys`

Wait for agent lifecycle state `agent wait`

`agent prompt` submits text plus encoded Enter and honors the terminal’s live bracketed-paste mode. It can prompt an agent that is already working. Use `agent send-keys` for interactions such as `esc`, `up`, `enter`, or `ctrl+c`; `escape` is accepted as an alias for `esc`. Use the pane input commands when you deliberately want raw terminal control.

Pane input addresses the terminal regardless of its current occupant. Agent input resolves the live agent and rejects the operation if that agent no longer controls the pane.

`agent prompt --wait` submits immediately. When the agent starts from a non-working state, Herdr first requires an observed lifecycle change within five seconds. If the state sequence does not advance, it returns `agent_prompt_stalled` instead of waiting indefinitely; a caller `--timeout` of five seconds or less returns the normal `timeout` error. After activity is observed, it waits for the requested settled status. It does not track individual turns. If the agent is already working, completion of that active turn may satisfy the wait. Standalone `agent wait` observes the current agent and returns immediately if its status already matches. Both commands default to `idle`, `done`, or `blocked`. Repeat `--until` to accept several exact states, for example `--until idle --until done`; use `--until unknown` explicitly when needed. On `agent prompt`, `--until` requires `--wait`.

`idle` means the agent is ready for input and its tab has been seen in the focused Herdr UI. `done` is the same underlying idle state after background work finishes, until that tab is focused or `pane focus` / `agent focus` targets it. Reading through the CLI does not mark it seen. `blocked` means Herdr recognized an approval or question UI. `unknown` means an agent is present but Herdr cannot classify its lifecycle confidently; it does not prove successful completion. Use exact `--until` states when that distinction matters.

`pane wait-output` does not interpret agent lifecycle. It polls the selected terminal snapshot and searches it immediately, so text that was already present can match. The default source name is `recent`; matching treats that source as unwrapped recent output from the latest 80 rendered terminal rows. `--lines` changes that row limit, and `--regex` uses Rust regular-expression syntax and matches one line at a time.

At the CLI, both `pane read` and `agent read` print terminal text directly. The default is UTF-8 text with ANSI escapes stripped; use `--format ansi` or `--ansi` to preserve terminal escapes where the source exposes them. The `detection` source is always plain text. For recent sources, `--lines N` selects the last N rendered terminal rows before optional unwrapping; without it, reads default to 80 rows. For `visible` and `detection`, omitting `--lines` returns the full snapshot, while specifying it keeps the last N newline-delimited lines. The socket API returns the text at `.result.read.text`.

#### Known caveat: alternate-screen output

Section titled “Known caveat: alternate-screen output”

Full-screen agents such as Claude Code and OpenCode may render in the terminal’s alternate screen. Alternate-screen rows do not enter Herdr’s host scrollback. `--lines` can only request more rows from the pane’s available screen and host scrollback; it cannot create missing history. If increasing `--lines` returns no additional response text, the pane is probably using the alternate screen and those response rows are no longer retained. A larger font or smaller pane makes this more likely.

Ask the agent for concise responses, enlarge the pane or use a smaller font, or use the agent’s own transcript and scrolling controls. After scrolling inside the agent, use `--source visible` to read the page it currently renders.

After that failed read, ask the agent to write its complete response as Markdown in a temporary directory and reply only with the file path, then read the file directly. Use this only as a fallback; do not request file output in the initial prompt.

Successful `agent start`, `agent prompt`, and `agent wait` commands return the current agent at `.result.agent`. `pane wait-output` returns `.result.pane_id`, `.result.matched_line`, and the matched snapshot at `.result.read`.

Wait commands have no default timeout and can wait indefinitely. On timeout or another server error, CLI commands print a JSON error to stderr and exit with status 1; invalid CLI syntax exits with status 2.

Start a helper, give it work, and wait for that work to settle:

```

split=$(herdr pane split --current --direction right --no-focus)

review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')

herdr agent start reviewer --kind codex --pane "$review_pane" -- -m gpt-5.4

herdr agent prompt reviewer "Review the current diff" --wait --timeout 120000

herdr agent read reviewer --source recent-unwrapped --lines 120
```

Wait for an agent to ask for input, inspect it, and interact with its UI:

```

herdr agent wait reviewer --until blocked --timeout 120000

herdr agent read reviewer --source recent-unwrapped --lines 80

herdr agent send-keys reviewer esc
```

Run an ordinary process and wait for its output without treating it as an agent:

```

herdr pane run w1:p3 "just test --watch"

herdr pane wait-output w1:p3 --regex "passed|failed" --timeout 120000
```

See the [CLI reference](https://herdr.dev/docs/cli-reference/) for the complete command and option list. Shell completions expose the same command tree interactively.

### Agents

https://herdr.dev/docs/agents/

Herdr is built for running more than one coding agent at a time. Each agent stays in a real terminal pane with its shell, logs, prompts, and running processes intact. Herdr tracks which panes contain agents, rolls their state up to tabs and workspaces, and lets you jump straight to the pane that needs attention instead of polling every terminal by hand.

To coordinate agents from scripts or from another agent, see [Agent automation](https://herdr.dev/docs/agent-automation/).

Automatic detection works out of the box for common coding agents. The important difference is not whether Herdr can see an agent. It is which signal is allowed to author `idle`, `working`, and `blocked`.

Agent State authority Integration role

Pi lifecycle hooks when installed; otherwise screen manifest state and session

OMP lifecycle hooks when installed state

GitHub Copilot CLI screen manifest session

Devin CLI screen manifest session

Kimi Code CLI lifecycle hooks when installed; otherwise screen manifest state and session

Hermes Agent lifecycle hooks when installed; otherwise screen manifest state and session

Qoder CLI screen manifest session

Droid screen manifest session

OpenCode lifecycle plugin when installed; otherwise screen manifest state and session

Kilo Code CLI lifecycle plugin when installed; otherwise screen manifest state and session

MastraCode lifecycle hooks when installed state and session

Claude Code screen manifest session

Codex screen manifest session

Cursor Agent CLI screen manifest session

Amp screen manifest none

Grok CLI screen manifest none

Antigravity CLI screen manifest none

Kiro CLI screen manifest none

Maki screen manifest none

Detected but less thoroughly tested: Gemini CLI and Cline. Unsupported agents still run normally as terminal processes. They just may not get rich state unless you add an integration or report state over the socket API.

Herdr first detects the foreground process in each pane. After that, each pane has one status authority.

For agents with complete lifecycle hooks, the integration is authoritative when it is installed and actively reporting for the running pane. Herdr uses those hook reports for `idle`, `working`, `blocked`, and session identity. It does not also run screen manifest fallback for that same lifecycle authority. This avoids two competing sources of truth.

For agents without complete lifecycle hooks, Herdr identifies the foreground process and reads the live bottom-buffer screen snapshot. It evaluates TOML manifests against that snapshot to classify `idle`, `working`, and `blocked`. For agents that emit them, manifests can also match terminal title and progress (OSC) sequences as detection evidence; when that evidence is absent, screen rules carry detection on their own.

The screen snapshot comes from the recent bottom of the pane buffer, not the scrolled viewport. If you scroll back in Herdr, detection still follows the live agent UI at the bottom.

Claude Code, Codex, GitHub Copilot CLI, Droid, Qoder CLI, and Cursor Agent CLI integrations are intentionally not lifecycle authorities. They provide native session identity for restore, but their hooks do not cover the whole lifecycle. They can miss permission approval results, escape interrupts, or other transitions. For those agents, Herdr still uses screen manifest detection.

#### VMs and sandbox wrappers

Section titled “VMs and sandbox wrappers”

On Linux and macOS, a host-visible wrapper can hide the real agent process from Herdr. Set `HERDR_AGENT=<agent>` on the wrapper command to tell Herdr which existing agent screen manifest to use. For example, run `HERDR_AGENT=claude fence -- claude` on Linux or `HERDR_AGENT=claude nono run --profile claude-code -- claude` on macOS. The hint is scoped to that foreground process; setting it only inside a VM or container is not visible to Herdr, and you should avoid exporting it globally unless every inherited foreground process should be treated as that agent.

Blocked detection is deliberately strict for screen-manifest agents. Herdr only marks `blocked` when the live bottom-buffer snapshot matches known visible approval, question, or permission UI. If no manifest rule matches for a known agent, Herdr falls back to `idle` and labels that fallback as `default_known_agent_idle_fallback` in explain output.

This means unusual new agent prompts may initially show as `idle` instead of `blocked` until Herdr learns that screen shape. Those interactions should not make Herdr send input or take destructive action; they only affect the visible status and waits.

#### Detection manifests

Section titled “Detection manifests”

Bundled manifests live inside Herdr. Herdr also checks herdr.dev for remote manifest updates and applies valid per-agent rule updates automatically without requiring a Herdr restart. Remote manifests are stored in Herdr’s state directory. Set `[update] manifest_check = false` to disable background remote manifest checks.

Local overrides can replace a remote or bundled manifest from the platform config directory:

```

~/.config/herdr/agent-detection/<agent>.toml
```

Local overrides always win. Without a local override, Herdr uses the newer compatible manifest between the cached remote manifest and the bundled manifest in the running binary. On debug builds, the same config helper may use a development directory such as `herdr-dev`. Invalid override files are ignored with a warning and Herdr falls back to the cached remote or bundled manifest for that agent.

Remote manifests patch detection rules for agents Herdr already knows how to identify. Adding a completely new agent still requires a Herdr binary update for process detection, labels, and integration behavior.

The running server loads active manifests into memory on startup. Automatic remote manifest updates reload that in-memory cache after new rules are written. Run `herdr server update-agent-manifests` to fetch remote manifest updates immediately and reload the running server. After editing a local override manually, restart Herdr or run `herdr server reload-agent-manifests` to apply the file to the running server.

Use `herdr agent explain` when a pane shows the wrong state:

```

herdr agent explain <target>

herdr agent explain --file screen.txt --agent codex --json
```

Live explain is evaluated by the running server, so it reflects the active manifest cache. The explain output shows the agent, final state, whether screen detection was skipped by a full lifecycle authority, manifest source and version, cached remote version, local override shadowing, remote update status, matched rule, visible evidence flags, matcher and region evidence for evaluated rules, skipped-update reason for transcript viewers, and the idle fallback reason when no rule matched.

Herdr can run inside tmux as the outer terminal environment. Agent detection does not inspect tmux sessions launched inside a Herdr pane. If a shell framework auto-enters tmux inside Herdr, Herdr sees `tmux` as the pane process instead of the agent behind it.

The sidebar rolls state upward.

A blocked agent makes its pane, tab, and workspace look blocked. A working agent makes the workspace look active. A done agent stays visible until you view it.

This is the main Herdr workflow: start several agents, let them work in parallel, and use the sidebar to see which project needs a decision, which one is still running, and which one is ready to review.

#### Direct integrations

Section titled “Direct integrations”

Install the integration for each agent you use; it gives Herdr hook or plugin reports instead of screen detection alone:

```

herdr integration install claude

herdr integration status
```

Each supported agent has its own integration name and behavior. See [Integrations](https://herdr.dev/docs/integrations/) for the per-agent details and the full install list.

#### Custom agent labels

Section titled “Custom agent labels”

You can rename an agent target for display:

```

herdr agent rename w1:p1 reviewer

herdr agent rename reviewer --clear
```

Targets accept a unique live agent name or the pane ID that currently hosts the agent. Terminal IDs and bare agent-kind labels are not accepted.

#### Custom status labels

Section titled “Custom status labels”

Integrations report lifecycle state as semantic state only. Add display customization separately with pane metadata tokens.

```

herdr pane report-agent w1:p1 \

  --source custom:indexer \

  --agent docs-bot \

  --state working

herdr pane report-metadata w1:p1 \

  --source custom:indexer-display \

  --token summary=indexing
```

`state` controls waits, notifications, and rollups. The `summary` token is display-only and can be used as `$summary` in an Agent sidebar row.

Agent sidebar rows can also opt into `terminal_title` or `terminal_title_stripped`; neither appears in the default rows. The first shows the latest safety-normalized OSC 0/2 terminal title. The second removes one recognized leading activity or spinner glyph and following whitespace. Herdr owns these values on the server; they are ephemeral across a cold restart and remain independent of metadata titles and semantic agent state. Spinner animation can therefore update the raw title without producing a pane update when the stripped text stays the same.

#### Attach directly to an agent

Section titled “Attach directly to an agent”

Attach your current terminal to one agent terminal instead of the full Herdr UI:

```

herdr agent attach reviewer
```

Detach with `ctrl+b q`. Send a literal `ctrl+b` with `ctrl+b ctrl+b`.

Scroll with the mouse wheel or plain page up/page down. Normal input jumps back to the bottom.

Use `--takeover` if another direct attach client already owns input:

```

herdr agent attach reviewer --takeover
```

Use `herdr terminal attach <terminal_id>` when you want the same direct attach behavior for a non-agent terminal.

#### 实例：用 Herdr 协调“实现、测试、审查”三个并行角色

##### 1. 实例目标

假设需要在远程项目 `~/projects/payments-api` 中实现以下需求：

> 为“创建支付”接口增加 `Idempotency-Key` 支持，避免客户端重试时产生重复支付。

验收条件：

1. 相同 `Idempotency-Key` 和相同请求体只能创建一次支付。
2. 相同 Key 搭配不同请求体时返回冲突错误。
3. 补充单元测试和集成测试。
4. 不改变现有无 Key 请求的行为。
5. 由一个 Agent 实现，另一个 Agent 独立审查，普通终端运行测试。

规划如下：

```text
Workspace: payments-api
└── Tab
    ├── implementer pane：Codex，负责实现
    ├── reviewer pane：Claude Code，负责只读审查
    └── test pane：普通 Shell，负责运行测试
```

这里刻意区分三种 Herdr 原语：

| 原语 | 在实例中的职责 |
|---|---|
| Layout | 创建 Workspace、Tab 和 Pane 拓扑 |
| Pane | 运行测试、服务、Shell 等普通终端进程 |
| Agent | 启动和控制 Herdr 能识别的编码 Agent，并等待其生命周期状态 |

> `agent start` 只会在已有的空闲 Shell Pane 中启动 Agent，不会自动创建、拆分或移动 Pane。

---

##### 2. 创建工作区并可靠获取 Pane ID

创建 Workspace 时会同时创建第一个 Tab 和根 Pane，因此根 Pane 可以直接交给实现 Agent 使用。

```bash
#!/usr/bin/env bash
set -Eeuo pipefail

repo="$HOME/projects/payments-api"

created=$(
  herdr workspace create \
    --cwd "$repo" \
    --label payments-api \
    --no-focus
)

impl_pane=$(
  printf '%s\n' "$created" |
    jq -r '.result.root_pane.pane_id'
)

review_split=$(
  herdr pane split "$impl_pane" \
    --direction right \
    --no-focus
)

review_pane=$(
  printf '%s\n' "$review_split" |
    jq -r '.result.pane.pane_id'
)

test_split=$(
  herdr pane split "$impl_pane" \
    --direction down \
    --no-focus
)

test_pane=$(
  printf '%s\n' "$test_split" |
    jq -r '.result.pane.pane_id'
)

printf 'implementer pane: %s\n' "$impl_pane"
printf 'reviewer pane:    %s\n' "$review_pane"
printf 'test pane:        %s\n' "$test_pane"
```

###### 最佳实践

- 始终从 Herdr 返回的 JSON 中读取 ID，不要预测 `w1:p1`、`w1:p2` 等编号。
- 创建 Workspace 后直接使用 `.result.root_pane.pane_id`，不要再额外创建一个无意义 Pane。
- `pane split` 返回的是新 Pane，位置在 `.result.pane.pane_id`。
- 在 `agent start` 前确认 Pane 位于交互式 Shell 提示符，没有前台命令、编辑器或其他 Agent。

##### 3. 启动实现 Agent 和审查 Agent

使用稳定、可读的 Agent 名称，而不是在后续命令中持续使用 Pane ID。

```bash
herdr agent start implementer \
  --kind codex \
  --pane "$impl_pane" \
  --timeout 60000 \
  -- -m gpt-5.4

herdr agent start reviewer \
  --kind claude \
  --pane "$review_pane" \
  --timeout 60000
```

Agent 名称应：

- 在当前存活的 Agent 中唯一；
- 符合正则 `[a-z][a-z0-9_-]{0,31}`；
- 作为当前 Agent 的临时别名，而不是 Pane 的永久名称。

例如：

```bash
herdr agent get "$impl_pane"
herdr agent get implementer
```

两种方式都能定位同一个存活 Agent，但后续自动化优先使用 `implementer` 和 `reviewer`。

###### 最佳实践

1. **Pane ID 表示位置，Agent 名称表示角色。**
2. Agent 退出、释放或被替换后，名称会自动清除。
3. 启动超时应显式指定；`agent start` 的默认等待时间为 30 秒。
4. 不要把 Agent 名称当成永久资源标识。
5. 如果 Agent 已经手动启动，可以先按 Pane ID 获取，再重命名：

```bash
herdr agent rename w1:p2 reviewer
```

##### 4. 给实现 Agent 下达有边界的任务

```bash
impl_prompt=$(cat <<'EOF'
请在当前仓库中实现“创建支付接口的 Idempotency-Key 支持”。

验收条件：
1. 相同 Idempotency-Key 和相同请求体只能创建一次支付。
2. 相同 Key 搭配不同请求体时返回冲突错误。
3. 无 Idempotency-Key 的现有行为保持不变。
4. 添加单元测试和集成测试。
5. 不提交 commit，不修改与本需求无关的文件。
6. 完成后简要列出修改文件、关键设计和仍存在的风险。

请直接检查仓库并完成实现，最终回复保持简洁。
EOF
)

impl_result=$(
  herdr agent prompt implementer "$impl_prompt" \
    --wait \
    --until idle \
    --until done \
    --until blocked \
    --timeout 600000
)

printf '%s\n' "$impl_result" | jq '.result.agent'
```

然后读取最近输出：

```bash
herdr agent read implementer \
  --source recent-unwrapped \
  --lines 120
```

##### 5. 正确理解等待结果

`agent prompt --wait` 返回，只表示 Agent 到达了某个被接受的生命周期状态，并不等同于“代码正确”或“任务成功”。

| 状态 | 含义 | 应对方式 |
|---|---|---|
| `idle` | Agent 已准备接收输入，并且对应 Tab 已被查看 | 可以继续下一步 |
| `done` | 后台工作已结束，但结果尚未被查看 | 通常可以继续，同时读取结果 |
| `blocked` | Agent 正在等待权限、批准或回答 | 先检查 UI，不要自动批准 |
| `unknown` | Herdr 无法可靠判断生命周期 | 不能视为成功，应检查 Agent 和检测规则 |
| `working` | Agent 仍在工作 | 继续等待，不要重复提交同一任务 |

之所以同时接受 `idle` 和 `done`，是因为二者可能因 Tab 是否已被查看而发生转换。

###### 避免错误关联 Agent 回合

Herdr 的等待针对当前 Agent 状态，而不是严格跟踪某个独立 Prompt 回合。如果 Agent 已经处于 `working`，新 Prompt 的等待有可能被当前正在执行的回合满足。

因此，在复用 Agent 前，先确认它已经稳定下来：

```bash
herdr agent wait implementer \
  --until idle \
  --until done \
  --timeout 300000
```

然后再提交下一项工作。

---

##### 6. Agent 被阻塞时的安全处理

如果实现 Agent 返回 `blocked`，先读取其界面：

```bash
herdr agent read implementer \
  --source recent-unwrapped \
  --lines 80
```

需要人工判断时，可以直接附加到该 Agent：

```bash
herdr agent attach implementer
```

退出直接附加：

```text
ctrl+b q
```

如果确认只是要关闭某个对话框，可以使用 Agent 级键盘输入：

```bash
herdr agent send-keys implementer esc
```

###### 最佳实践

- 不要检测到 `blocked` 后自动发送 `enter` 或批准权限。
- `agent send-keys` 适合 `esc`、`up`、`enter`、`ctrl+c` 等交互式 UI 操作。
- 正常自然语言输入使用 `agent prompt`。
- 只有明确需要原始终端控制时，才使用 `pane send-text` 或 `pane send-keys`。
- Agent 级输入会验证该 Agent 是否仍然控制 Pane，比直接向 Pane 发送按键更安全。

##### 7. 在普通 Pane 中运行测试

测试不是编码 Agent，因此应使用 Pane 命令，而不是 Agent 命令。

为防止 `pane wait-output` 匹配到历史输出，给本次测试生成唯一标记：

```bash
test_marker="__HERDR_TEST_$$_$(date +%s)__"

herdr pane run "$test_pane" \
  "just test; rc=\$?; printf '\n${test_marker}=%s\n' \"\$rc\""
```

等待本次测试的唯一结束标记：

```bash
test_result=$(
  herdr pane wait-output "$test_pane" \
    --regex "^${test_marker}=[0-9]+$" \
    --timeout 300000
)

printf '%s\n' "$test_result" |
  jq '.result | {pane_id, matched_line}'
```

解析退出码：

```bash
matched_line=$(
  printf '%s\n' "$test_result" |
    jq -r '.result.matched_line'
)

test_rc="${matched_line##*=}"

if [[ "$test_rc" != "0" ]]; then
  echo "Tests failed with exit code $test_rc" >&2

  herdr pane read "$test_pane" \
    --source recent-unwrapped \
    --lines 120

  exit 1
fi
```

###### 为什么不直接等待 `passed|failed`

`pane wait-output` 会立即搜索当前终端快照，旧文本也可能被匹配。例如：

```bash
herdr pane wait-output "$test_pane" \
  --regex "passed|failed"
```

如果 Pane 中残留上一次测试的 `passed`，命令可能立刻返回，形成假成功。唯一标记可以把等待与本次命令关联起来。

###### Pane 命令适用场景

应使用 Pane 控制：

- 测试命令；
- 开发服务器；
- CI watcher；
- 日志跟踪；
- 数据库迁移；
- 普通 Shell 脚本。

不要为了获得状态而把普通终端进程伪装成 Agent。

##### 8. 让审查 Agent 独立检查当前 Diff

测试提交到测试 Pane 后已经独立运行，因此可以同时让审查 Agent 开始工作：

```bash
review_prompt=$(cat <<'EOF'
请对当前工作区的未提交修改做独立代码审查。

重点检查：
1. Idempotency-Key 是否存在竞态条件。
2. 相同 Key、不同请求体是否可靠返回冲突。
3. 事务边界和唯一约束是否正确。
4. 错误处理是否泄露敏感信息。
5. 测试是否覆盖并发请求、重试和异常路径。
6. 是否引入与需求无关的改动。

保持只读，不修改代码。
按严重程度输出问题：critical、major、minor。
每个问题给出文件位置、原因和建议；如果没有阻断问题，请明确说明。
最终回复保持简洁。
EOF
)

review_result=$(
  herdr agent prompt reviewer "$review_prompt" \
    --wait \
    --until idle \
    --until done \
    --until blocked \
    --timeout 600000
)

printf '%s\n' "$review_result" | jq '.result.agent'

herdr agent read reviewer \
  --source recent-unwrapped \
  --lines 160
```

###### 最佳实践

- 实现和审查使用不同 Agent，降低自我审查偏差。
- 在 Prompt 中明确审查 Agent“只读”，避免其顺手修改代码。
- 审查结果不能替代测试结果。
- 测试通过也不能替代对事务、并发和安全边界的审查。
- Agent 状态完成不能替代对实际 Git Diff 的验收。

最终仍应执行：

```bash
git status --short
git diff --check
git diff --stat
git diff
```

##### 9. 处理全屏 Agent 输出丢失

Claude Code、OpenCode 等全屏 Agent 可能使用终端的 alternate screen。此时旧响应不会进入 Herdr 的主机滚动区，增加 `--lines` 也不一定能找回内容。

先尝试：

```bash
herdr agent read reviewer \
  --source recent-unwrapped \
  --lines 240
```

如果没有获得更多历史内容，可以在 Agent 内滚动，然后读取当前可见页面：

```bash
herdr agent read reviewer \
  --source visible
```

只有在读取失败后，才使用文件回退方案：

```bash
herdr agent prompt reviewer \
  "刚才的完整审查结果无法从终端历史中读取。请将完整结果写成 Markdown 文件放到临时目录，并且只回复该文件的绝对路径。" \
  --wait \
  --until idle \
  --until done \
  --timeout 120000
```

得到路径后直接读取文件：

```bash
cat /tmp/review-result.md
```

###### 最佳实践

1. 初始 Prompt 要求回复简洁，降低 alternate-screen 内容丢失概率。
2. 可以增大 Pane、减小字体，以保留更多可见行。
3. 优先使用 Agent 自己的滚动或 Transcript 能力。
4. 不要在第一次 Prompt 中就要求写文件；文件输出应作为读取失败后的回退方案。

##### 10. Agent 状态不准确时的诊断

如果 `reviewer` 明明在等待批准，却显示为 `idle`，或者长时间显示 `unknown`，使用：

```bash
herdr agent explain reviewer
```

也可以基于保存的屏幕内容离线检查：

```bash
herdr agent explain \
  --file screen.txt \
  --agent claude \
  --json
```

必要时立即更新检测清单：

```bash
herdr server update-agent-manifests
```

如果修改了本地覆盖文件，则重新加载：

```bash
herdr server reload-agent-manifests
```

本地检测规则覆盖位置为：

```text
~/.config/herdr/agent-detection/<agent>.toml
```

###### 检测最佳实践

- 安装可用的 Agent 集成：

```bash
herdr integration install claude
herdr integration status
```

- 理解“检测到 Agent”和“谁有权决定生命周期状态”是两回事。
- Claude Code、Codex 等 Agent 的部分原生集成主要提供会话身份，生命周期仍可能由屏幕清单判断。
- `unknown` 不表示成功。
- 屏幕清单的 `blocked` 检测有意保持严格；未知的新批准界面可能暂时被归类为 `idle`。
- 状态只用于等待、通知和界面汇总，不应触发自动执行破坏性操作。

如果 Agent 被 VM 或沙箱包装器隐藏，应在宿主机可见的包装命令上设置提示：

```bash

```

不要全局导出 `HERDR_AGENT`，否则其他继承该环境变量的前台进程也可能被误识别。

##### 11. Pane 移动后的标识处理

如果后续把审查 Pane 移到其他 Workspace，它的 Workspace 限定 Pane ID 会变化。

移动后必须从响应中读取新 ID：

```bash
move_result=$(herdr pane move ...)
new_review_pane=$(
  printf '%s\n' "$move_result" |
    jq -r '.result.move_result.pane.pane_id'
)
```

旧 ID 位于：

```text
.result.move_result.previous_pane_id
```

###### 最佳实践

- 移动后不要继续缓存旧 Pane ID。
- Agent 名称 `reviewer` 通常仍可作为稳定目标，因此自动化优先按 Agent 名称操作。
- 移动期间已经进行的 `agent wait` 会以 `agent_not_running` 结束，应使用新目标重新开始等待。
- 进程启动时获得的旧 `HERDR_PANE_ID` 仍会作为该终端的别名，因此进程内部使用 `--current` 仍然安全。

## 结构化（3）

### 2026-07-22 09:25:00

#### 用 Herdr 协调测试与代码审查

Herdr 是一个面向多编码代理的终端会话与自动化协调层：它可以让测试、服务器和多个 AI Agent 在不同窗格中并行运行，并通过脚本统一创建任务、跟踪状态、处理交互和收集结果。核心原则是：**终端进程用 Pane 控制，需要理解生命周期的编码代理用 Agent 控制。**

##### 1. 自动化的三层基本对象

Herdr 将自动化能力分为三类：

| 对象 | 主要职责 | 典型用途 |
|---|---|---|
| **Layout** | 创建和组织 workspace、tab、pane | 搭建测试、开发、审查所需的终端布局 |
| **Pane** | 控制原始终端，执行命令、发送输入、读取或等待输出 | Shell、测试、服务器、CI watcher |
| **Agent** | 按名称或窗格控制已识别的编码代理，并跟踪生命周期 | Codex、Claude Code 等代码实现或审查代理 |

需要特别区分：

- **Pane 始终是终端位置**，不管里面是否运行 Agent。
- **Agent 是 Pane 中当前被 Herdr 识别出的编码代理进程**。
- `agent start` 只能在已有、处于 Shell 提示符的 Pane 中启动 Agent，**不会自动创建、拆分或移动布局**。
- 创建 workspace 时会自动创建第一个 tab 和根 Pane；创建 tab 时也会创建根 Pane。因此，应优先使用返回的根 Pane，只有需要更多终端时才拆分。

---

##### 2. 创建布局时必须读取返回的 ID

Herdr 的创建命令会返回 JSON，应从结果中提取 Pane ID，而不是自行推测：

```bash
created=$(herdr workspace create --cwd ~/project --label api --no-focus)
pane_id=$(printf '%s\n' "$created" | jq -r '.result.root_pane.pane_id')

split=$(herdr pane split "$pane_id" --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')
```

各命令的关键返回字段：

- `workspace create`：`.result.workspace`、`.result.tab`、`.result.root_pane`
- `tab create`：`.result.tab`、`.result.root_pane`
- `pane split`：新 Pane 位于 `.result.pane`

移动 Pane 到另一个 workspace 后，其带 workspace 前缀的 ID 会改变：

- 新 ID：`.result.move_result.pane.pane_id`
- 旧 ID：`.result.move_result.previous_pane_id`

虽然旧的 `HERDR_PANE_ID` 仍可作为终端别名，因此 `--current` 仍然安全，但**移动前已经执行的 `agent wait` 会以 `agent_not_running` 结束**；移动后应使用新 Pane ID或 Agent 名称继续操作。

---

##### 3. Agent 的身份、命名与启动

Pane ID（如 `w1:p2`）标识终端位置；Agent 名称（如 `reviewer`）是当前 Agent 的易读别名。

Agent 名称必须：

- 匹配正则：`[a-z][a-z0-9_-]{0,31}`
- 在当前存活的 Agent 中唯一
- 最长 32 个字符

别名只属于当前 Agent；当 Agent 退出、被释放或替换后，名称会清除，不会永久重命名 Pane。

启动 Agent 前，目标 Pane 必须回到可用的交互式 Shell 提示符，不能有前台命令、编辑器或其他 Agent 正在运行。例如：

```bash
herdr agent start reviewer \
  --kind codex \
  --pane "$review_pane" \
  -- -m gpt-5.4
```

- `--kind` 指定支持的 Agent 及其标准可执行文件。
- `--` 后的参数会原样传给 Agent。
- Herdr 会等待目标 Agent 被识别并可接收交互输入。
- 默认启动等待时间为 **30 秒**。
- `--timeout` 必须大于 **3000 毫秒**，且不超过 **300000 毫秒**。

支持的 Agent 类型包括 `pi`、`claude`、`codex`、`gemini`、`cursor`、`devin`、`cline`、`opencode`、`copilot`、`kimi`、`kiro`、`droid`、`amp`、`grok`、`hermes`、`kilo`、`qodercli`、`maki` 等。

手动启动的 Agent 也能被自动检测，并可按 Pane ID 查询或重命名：

```bash
herdr agent get w1:p2
herdr agent rename w1:p2 reviewer
```

---

##### 4. 根据任务选择 Pane 或 Agent 命令

| 目标 | 命令 |
|---|---|
| 执行 Shell 命令并回车 | `pane run` |
| 发送文本但不回车 | `pane send-text` |
| 发送按键或组合键 | `pane send-keys` |
| 等待普通终端输出 | `pane wait-output` |
| 在已有 Pane 中启动 Agent | `agent start` |
| 向 Agent 提交提示词 | `agent prompt` |
| 操作 Agent 交互界面 | `agent send-keys` |
| 等待 Agent 生命周期状态 | `agent wait` |

选择原则：

- 测试、服务器、CI watcher 等普通进程使用 `pane`。
- 代码实现、审查等需要判断“正在工作、等待输入或已完成”的任务使用 `agent`。
- `pane` 输入直接作用于终端，不关心当前占用者是谁。
- `agent` 输入会先确认目标 Agent 仍控制该 Pane；若 Agent 已退出，则拒绝操作，更安全。

`agent prompt` 会发送文本并自动提交，也允许向正在工作的 Agent 继续发送提示。对于 `Esc`、方向键、回车或 `Ctrl+C` 等 UI 操作，应使用：

```bash
herdr agent send-keys reviewer esc
```

其中 `escape` 也可作为 `esc` 的别名。

---

##### 5. 理解 Agent 的生命周期状态

Herdr 主要跟踪以下状态：

- **working**：Agent 正在工作。
- **idle**：Agent 已准备好接收输入，且所在 tab 已在 Herdr UI 中被查看。
- **done**：后台工作已结束，但所在 tab 尚未被查看；聚焦该 tab 或 Pane 后会转为普通 idle。
- **blocked**：识别到审批、权限确认或提问界面，需要人工处理。
- **unknown**：确认 Agent 存在，但无法可靠判断状态；**不能视为成功完成**。

等待多个可接受状态时，可以重复使用 `--until`：

```bash
herdr agent wait reviewer \
  --until idle \
  --until done \
  --timeout 120000
```

默认等待的稳定状态是 `idle`、`done` 或 `blocked`；如需接受 `unknown`，必须显式写出。

###### `agent prompt --wait` 的行为

```bash
herdr agent prompt reviewer \
  "Review the current diff" \
  --wait \
  --timeout 120000
```

如果 Agent 原本不处于 working 状态，Herdr 会先要求在 **5 秒内观察到状态变化**：

- 未观察到进展时返回 `agent_prompt_stalled`，避免无限等待。
- 若调用方设置的总超时不超过 5 秒，则返回普通超时错误。
- 观察到活动后，再等待指定的稳定状态。

需要注意：Herdr 跟踪的是 Agent 当前生命周期，而不是严格对应某一轮提示词。因此，如果 Agent 本来已经在工作，当前活动轮次的结束也可能满足等待条件。

##### 6. 等待测试输出与读取终端内容

普通测试进程不应伪装成 Agent，可直接运行并等待输出：

```bash
herdr pane run w1:p3 "just test --watch"

herdr pane wait-output w1:p3 \
  --regex "passed|failed" \
  --timeout 120000
```

`pane wait-output`：

- 不解释 Agent 生命周期，只搜索终端快照。
- 会立即匹配已经存在的文本。
- 默认读取最近 **80 个渲染行**。
- `--lines` 可调整行数。
- `--regex` 使用 Rust 正则表达式，并逐行匹配。

读取命令默认：

- 输出 UTF-8 文本。
- 去除 ANSI 转义序列。
- 可使用 `--format ansi` 或 `--ansi` 保留终端样式。
- Socket API 中的文本位于 `.result.read.text`。

成功返回时：

- `agent start`、`agent prompt`、`agent wait`：当前 Agent 位于 `.result.agent`
- `pane wait-output`：返回 `.result.pane_id`、`.result.matched_line` 和 `.result.read`

等待命令默认**没有超时限制**，可能无限等待，自动化脚本中应主动设置 `--timeout`。服务器错误或超时会把 JSON 错误写入 stderr，并以状态码 **1** 退出；CLI 语法错误以状态码 **2** 退出。

##### 7. 代码审查与测试的典型协调流程

###### 让审查 Agent 并行工作

```bash
split=$(herdr pane split --current --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')

herdr agent start reviewer \
  --kind codex \
  --pane "$review_pane" \
  -- -m gpt-5.4

herdr agent prompt reviewer \
  "Review the current diff" \
  --wait \
  --timeout 120000

herdr agent read reviewer \
  --source recent-unwrapped \
  --lines 120
```

这一流程依次完成：

1. 创建独立审查 Pane。
2. 启动名为 `reviewer` 的 Codex Agent。
3. 提交“审查当前 diff”的任务并等待其稳定。
4. 读取最近 120 行审查结果。

###### 处理 Agent 的提问或审批请求

```bash
herdr agent wait reviewer \
  --until blocked \
  --timeout 120000

herdr agent read reviewer \
  --source recent-unwrapped \
  --lines 80

herdr agent send-keys reviewer esc
```

即先等待 Agent 阻塞，再查看界面，并通过按键处理交互。

##### 8. 全屏 Agent 的输出读取限制

Claude Code、OpenCode 等全屏 Agent 可能使用终端的 **alternate screen（备用屏幕）**。这部分内容不会进入 Herdr 的宿主终端滚动历史，因此：

- 增大 `--lines` 只能读取现有屏幕和宿主滚动区。
- 它无法恢复已经丢失的备用屏幕内容。
- 若增加 `--lines` 后仍没有更多文本，通常说明历史内容未被保留。
- 字体越大或 Pane 越小，越容易发生内容丢失。

建议依次采取：

1. 让 Agent 输出更精炼。
2. 放大 Pane 或缩小字体。
3. 使用 Agent 自带的历史记录和滚动功能。
4. 在 Agent 内滚动后，用 `--source visible` 读取当前显示页面。
5. 最后才让 Agent 把完整回答写入临时 Markdown 文件，并只返回文件路径，再直接读取文件。

文件输出只应作为兜底方式，**不建议在初始提示词中直接要求**。

##### 9. Herdr 如何识别 Agent 状态

Herdr 会先识别每个 Pane 的前台进程，然后为该 Pane 选择唯一的“状态权威来源”，主要有两种方式：

###### 生命周期 Hook 或插件

对于具有完整生命周期集成的 Agent，安装并主动上报的 Hook/插件负责提供：

- `idle`
- `working`
- `blocked`
- 会话身份

此时 Herdr 不再同时使用屏幕规则判断，避免出现两个相互冲突的状态来源。

###### 屏幕 Manifest 检测

对于没有完整 Hook 的 Agent，Herdr 会读取 Pane 底部的实时屏幕快照，并根据 TOML Manifest 判断状态。

- 检测始终基于实时底部缓冲区，而不是用户滚动后的视图。
- 即使在 Herdr 中向上滚动，状态检测仍跟随底部的实时 Agent UI。
- Claude Code、Codex、GitHub Copilot CLI、Droid、Qoder CLI、Cursor Agent CLI 等虽然可提供原生会话身份，但其 Hook 无法覆盖权限审批、Esc 中断等完整生命周期，因此仍以屏幕检测作为状态依据。
- Gemini CLI 和 Cline 已可检测，但测试相对不充分。
- 不支持的 Agent 仍可作为普通终端进程运行，只是可能没有丰富的状态信息。

---

##### 10. blocked 检测偏保守，避免误操作

对于使用屏幕 Manifest 的 Agent，Herdr 只有在实时底部界面明确匹配已知的审批、问题或权限提示时，才会标记为 `blocked`。

如果识别到一个已知 Agent，但没有任何规则匹配，Herdr 会回退到 `idle`，并在解释结果中标记：

```text
default_known_agent_idle_fallback
```

因此，某些新出现或非常规的交互界面可能暂时显示为 idle，而不是 blocked。这种设计只影响状态显示和等待逻辑，不应成为自动发送输入或执行破坏性操作的依据。

##### 11. Manifest 更新与状态诊断

Herdr 内置 Agent 检测 Manifest，也会从 `herdr.dev` 自动获取远程更新，无需重启即可更新已知 Agent 的检测规则。可在配置中关闭后台检查：

```toml
[update]
manifest_check = false
```

本地覆盖文件位于：

```text
~/.config/herdr/agent-detection/<agent>.toml
```

优先级为：

1. 本地覆盖
2. 较新的兼容远程缓存版本
3. Herdr 二进制内置版本

远程 Manifest 只能修补已有 Agent 的规则；增加全新 Agent 仍需升级 Herdr 二进制。

相关命令：

```bash
# 立即下载并加载远程规则
herdr server update-agent-manifests

# 修改本地规则后重新加载
herdr server reload-agent-manifests

# 解释某个 Agent 为何显示当前状态
herdr agent explain <target>

# 用文件模拟 Codex 屏幕并输出 JSON
herdr agent explain --file screen.txt --agent codex --json
```

`agent explain` 会展示最终状态、状态来源、Manifest 版本、匹配规则、可见证据和回退原因等信息，是排查错误状态的主要工具。

##### 12. 多 Agent 协作与界面汇总

Herdr 会把 Agent 状态从 Pane 向上汇总到 tab 和 workspace：

- blocked Agent 会让其 Pane、tab 和 workspace 显示为 blocked。
- working Agent 会使 workspace 显示为活跃。
- done Agent 会持续提示，直到用户查看它。

因此，典型工作方式是：

1. 在多个 Pane 中启动实现、测试和审查 Agent。
2. 让它们并行工作。
3. 通过侧边栏查看哪个项目仍在运行、哪个等待人工决策、哪个已经完成。
4. 直接跳转到需要关注的 Pane，而不是逐个终端轮询。

可安装 Agent 的直接集成以获得更可靠的状态上报：

```bash
herdr integration install claude
herdr integration status
```

还可以给 Agent 设置易读名称：

```bash
herdr agent rename w1:p1 reviewer
herdr agent rename reviewer --clear
```

自定义状态中，`state` 影响等待、通知和状态汇总，而 `summary` 只控制显示：

```bash
herdr pane report-agent w1:p1 \
  --source custom:indexer \
  --agent docs-bot \
  --state working

herdr pane report-metadata w1:p1 \
  --source custom:indexer-display \
  --token summary=indexing
```

Linux 或 macOS 上的沙箱包装器可能隐藏真实 Agent 进程，可在宿主可见的包装命令上设置：

```bash
HERDR_AGENT=claude fence -- claude
```

或：

```bash
HERDR_AGENT=claude nono run --profile claude-code -- claude
```

注意：

- 变量必须让 Herdr 在宿主机前台进程上可见。
- 只在 VM 或容器内部设置无效。
- 不应全局导出，除非所有继承它的前台进程都应被当成该 Agent。

Herdr 可运行在外层 tmux 中，但不会深入检查在 Herdr Pane 内再次启动的 tmux 会话。若 Shell 框架自动进入内层 tmux，Herdr 看到的将是 tmux，而非其后的 Agent。

##### 15. 本地、SSH 与移动端工作方式

Herdr 由后台会话服务器和一个或多个终端客户端组成。Pane 始终运行在服务器中，客户端只负责连接和渲染；通过 `Ctrl+B Q` 断开后，测试、服务器和 Agent 仍会继续运行。

###### 本地工作

在代码所在机器和项目目录中运行 `herdr`。它会自动启动或连接本地后台会话，无需手动管理 Socket。

###### 先 SSH，再运行 Herdr

```bash
ssh you@server
herdr
```

此模式类似远程 tmux：

- Shell、Herdr 服务器、Agent 和 Pane 都在远程机器运行。
- 可断开 SSH，之后重新连接并继续原会话。
- 适合手机、平板 SSH 客户端或习惯远程 Shell 的用户。

手机端无需专用 Herdr App 或 Web 控制台，普通 SSH 客户端即可；TUI 会适配窄屏。

###### 本地客户端直接连接远程 Herdr

```bash
herdr --remote workbox
herdr --remote ssh://you@server:2222
```

此时本地 Herdr 是轻量客户端，通过 SSH 启动或连接远程服务器，并把 UI 流式传回本地终端。

优势是可以桥接本地桌面能力，例如把本地剪贴板中的图片粘贴到远程会话。若先 SSH 再在服务器运行 Herdr，则远程 Herdr 无法访问本地桌面剪贴板。

可在 SSH 配置中保存重复目标：

```sshconfig
Host workbox
  HostName server.example.com
  User you
  Port 2222
```

然后直接执行：

```bash
herdr --remote workbox
```

###### 选择建议

- **本地开发**：使用 `herdr`
- **手机或传统远程 Shell**：先 `ssh`，再运行 `herdr`
- **希望远程会话具有本地体验及剪贴板桥接**：使用 `herdr --remote &lt;host>`

总体而言，Herdr 的最佳实践是：**将普通测试和服务交给 Pane，将代码实现与审查交给 Agent；通过明确的超时、状态等待和 JSON 返回值，把多个并行终端任务组织成可监控、可恢复的自动化流程。**

#### 用 Herdr 协调测试与审查

Herdr 是面向多编码智能体的终端会话与自动化工具：它让测试、服务器和多个 Agent 在独立窗格中持续运行，并通过脚本统一创建任务、识别状态、等待结果和处理人工确认。使用时的核心原则是：**布局用 Layout、普通终端任务用 Pane、需要理解生命周期的编码助手用 Agent**。

##### 1. 三类基础能力：布局、终端与 Agent

| 能力 | 主要职责 | 适用场景 |
|---|---|---|
| **Layout** | 创建和组织工作区、标签页、窗格 | 搭建测试、开发、审查所需的终端布局 |
| **Pane** | 操作原始终端，运行命令、发送按键、读取或等待输出 | Shell、测试、服务器、CI watcher 等普通进程 |
| **Agent** | 按名称或窗格控制编码 Agent，并跟踪其状态 | 启动 Codex、Claude 等，提交任务并等待完成或阻塞 |

- **窗格始终存在，Agent 只是窗格中当前被识别的进程。**
- `agent start` 不负责新建、分割或移动窗格，必须先准备一个处于 Shell 提示符的空闲窗格。
- 创建工作区会同时创建第一个标签页和根窗格；创建标签页也会生成根窗格。只有需要额外终端时才继续分割。

```bash
created=$(herdr workspace create --cwd ~/project --label api --no-focus)
pane_id=$(printf '%s\n' "$created" | jq -r '.result.root_pane.pane_id')

split=$(herdr pane split "$pane_id" --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')
```

创建类命令会返回 JSON，应从响应中提取真实 ID，不要自行猜测：

- `workspace create`：返回工作区、标签页和根窗格。
- `tab create`：返回标签页和根窗格。
- `pane split`：返回新窗格。

如果移动窗格，其工作区限定 ID 会变化，应改用 `.result.move_result.pane.pane_id`；旧 ID 保存在 `previous_pane_id` 中。已启动进程仍保留原环境，旧 `HERDR_PANE_ID` 也可作为别名，但正在进行的 `agent wait` 会以 `agent_not_running` 结束。

##### 2. Agent 的身份与启动

窗格 ID（如 `w1:p2`）表示终端位置；Agent 名称（如 `reviewer`）只是当前 Agent 的易读别名。

- 名称格式：`[a-z][a-z0-9_-]{0,31}`。
- 名称必须在仍运行的 Agent 中唯一。
- Agent 退出、释放或被替换后，别名会被清除，不会永久重命名窗格。
- Agent 命令既可使用唯一名称，也可使用承载它的窗格 ID。

启动前，目标窗格必须回到交互式 Shell 提示符，不能有前台命令、编辑器或其他 Agent。示例：

```bash
herdr agent start reviewer \
  --kind codex \
  --pane "$review_pane" \
  -- -m gpt-5.4
```

`--kind` 用于选择受支持的 Agent，涵盖 Codex、Claude、Gemini、Cursor、Devin、OpenCode、Copilot、Kimi、Kiro、Droid、Amp、Grok 等；`--` 后的参数会原样传给对应程序。

- `agent start` 会等待 Herdr 确认目标 Agent 已在同一窗格中启动并可交互。
- 默认启动等待时间为 **30 秒**。
- `--timeout` 必须大于 **3000 毫秒**，且不超过 **300000 毫秒**。
- 手动启动的 Agent 也能被自动识别，可再为其设置名称：

```bash
herdr agent get w1:p2
herdr agent rename w1:p2 reviewer
```

##### 3. 如何选择具体控制命令

| 目标 | 命令 |
|---|---|
| 在 Shell 中运行并提交命令 | `pane run` |
| 发送文本但不按 Enter | `pane send-text` |
| 发送按键或组合键 | `pane send-keys` |
| 等待普通终端输出 | `pane wait-output` |
| 在已有窗格中启动 Agent | `agent start` |
| 给 Agent 提交提示词 | `agent prompt` |
| 操作 Agent 的交互界面 | `agent send-keys` |
| 等待 Agent 生命周期状态 | `agent wait` |

关键区别：

- **Pane 输入**直接操作终端，不关心里面运行什么。
- **Agent 输入**会先确认目标 Agent 仍控制该窗格，否则拒绝操作。
- `agent prompt` 会发送提示词和 Enter，并兼容终端的 bracketed-paste 模式；即使 Agent 正在工作也可以继续提交。
- `agent send-keys` 适合发送 `esc`、`up`、`enter`、`ctrl+c` 等交互按键。

##### 4. 等待 Agent：理解 idle、done、blocked 和 unknown

`agent prompt --wait` 提交任务后可等待 Agent 进入指定状态。默认接受：

- **idle**：Agent 已可接收新输入，且其标签页已在 Herdr 界面中被查看。
- **done**：后台工作已完成，但对应标签页尚未被查看；聚焦后会变为普通 idle。
- **blocked**：Herdr 识别到审批、权限或提问界面，需要人工处理。
- **unknown**：确认存在 Agent，但无法可靠判断生命周期；**不能据此认为任务成功完成**。

可显式等待多个状态：

```bash
herdr agent prompt reviewer "Review the current diff" \
  --wait \
  --until idle \
  --until done \
  --timeout 120000
```

注意事项：

- 如果 Agent 原本不在工作，提交提示后 Herdr 要求在 **5 秒内**观察到状态变化；否则返回 `agent_prompt_stalled`，避免无限等待。
- 若调用方设置的超时不超过 5 秒，则返回普通超时错误。
- Herdr 跟踪的是 Agent 整体状态，不是单独的对话轮次；如果 Agent 提交前已经在工作，当前任务完成也可能满足等待条件。
- 单独执行 `agent wait` 时，如果当前状态已经匹配，会立即返回。
- 等待命令默认**没有超时时间**，可能无限等待，自动化脚本应主动设置 `--timeout`。

等待人工输入并处理界面的例子：

```bash
herdr agent wait reviewer --until blocked --timeout 120000
herdr agent read reviewer --source recent-unwrapped --lines 80
herdr agent send-keys reviewer esc
```

##### 5. 协调审查、测试与普通进程

一个典型审查流程是：新建窗格、启动审查 Agent、提交任务、等待稳定状态，再读取结果。

```bash
split=$(herdr pane split --current --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')

herdr agent start reviewer \
  --kind codex \
  --pane "$review_pane" \
  -- -m gpt-5.4

herdr agent prompt reviewer \
  "Review the current diff" \
  --wait \
  --timeout 120000

herdr agent read reviewer \
  --source recent-unwrapped \
  --lines 120
```

测试、服务器等普通进程不应伪装成 Agent，应直接等待终端输出：

```bash
herdr pane run w1:p3 "just test --watch"
herdr pane wait-output w1:p3 \
  --regex "passed|failed" \
  --timeout 120000
```

`pane wait-output` 的特点：

- 不判断 Agent 生命周期，只在终端快照中搜索文本或正则。
- 已经存在于屏幕中的文本也可能立即匹配。
- 默认搜索最近 **80 行**渲染内容。
- `--regex` 使用 Rust 正则语法，并逐行匹配。
- 成功时返回窗格 ID、命中行和对应快照。

##### 6. 读取输出及全屏 Agent 的限制

`pane read` 和 `agent read` 默认输出：

- UTF-8 文本；
- 去除 ANSI 转义序列；
- 最近输出默认读取 **80 行**。

如需保留终端样式，可用 `--format ansi` 或 `--ansi`。Socket API 中的文本位于 `.result.read.text`。

###### 全屏终端的已知问题

Claude Code、OpenCode 等全屏 Agent 可能使用终端的 **alternate screen（备用屏幕）**。这些内容不会进入 Herdr 的宿主滚动历史，因此：

- 增加 `--lines` 也无法恢复已经丢失的内容。
- 窗格较小或字体较大时，更容易丢失较早回复。
- 可让 Agent 回复更简洁、放大窗格、缩小字体，或使用 Agent 自带的历史记录与滚动功能。
- 在 Agent 内滚动后，可用 `--source visible` 读取当前显示页。

如果仍无法读取完整结果，最后的兜底方法是：让 Agent 将完整回复写入临时目录中的 Markdown 文件，并只返回文件路径，再直接读取该文件。**不要在最初提示中就要求文件输出，仅在读取失败时使用。**

##### 7. Agent 状态是如何识别的

Herdr 会先识别每个窗格的前台进程，然后为该窗格选择唯一的“状态权威来源”，避免多个机制同时给出冲突状态。

主要有两种方式：

1. **生命周期 Hook 或插件**
   - Agent 主动报告 `idle`、`working`、`blocked` 和会话信息。
   - 完整 Hook 正在工作时，它就是唯一权威，不再使用屏幕规则兜底。

2. **屏幕 Manifest 检测**
   - 读取窗格底部实时画面，根据 TOML 规则识别状态。
   - 滚动查看历史不会影响检测，Herdr 始终关注实时底部界面。
   - 对审批和权限提示采用严格匹配，只有看到已知的可见界面才标记为 `blocked`。

Claude Code、Codex、GitHub Copilot CLI、Droid、Qoder CLI、Cursor Agent CLI 等虽然可提供原生会话身份，但其 Hook 无法覆盖权限审批结果、Escape 中断等全部状态变化，因此 Herdr 仍以屏幕 Manifest 作为生命周期判断依据。

若已识别为已知 Agent，但没有规则命中，Herdr 会保守地回退为 `idle`，并在解释结果中标记 `default_known_agent_idle_fallback`。因此，Agent 出现一种全新交互界面时，初期可能被显示为 idle 而不是 blocked；状态只影响展示和等待，不应被用于自动发送危险输入。

##### 8. 虚拟机、沙箱和 tmux 的注意事项

Linux 或 macOS 上，宿主可见的包装进程可能隐藏真实 Agent。此时可通过环境变量提示 Herdr 使用哪个 Agent 的检测规则：

```bash
HERDR_AGENT=claude fence -- claude
HERDR_AGENT=claude nono run --profile claude-code -- claude
```

注意：

- 该变量必须设置在宿主可见的前台包装命令上，只在虚拟机或容器内部设置无效。
- 不建议全局导出，否则所有继承该变量的前台进程都可能被误认为对应 Agent。
- Herdr 可以运行在外层 tmux 中，但不会穿透检查 Herdr 窗格内部再次启动的 tmux；如果 Shell 自动进入 tmux，Herdr 看到的只会是 tmux 进程。

##### 9. 检测规则的更新与排错

Herdr 内置检测 Manifest，也会从 `herdr.dev` 自动获取已知 Agent 的规则更新，无须重启即可重新加载。可通过配置关闭后台检查：

```toml
[update]
manifest_check = false
```

本地覆盖文件位于：

```text
~/.config/herdr/agent-detection/<agent>.toml
```

优先级为：

1. 本地覆盖；
2. 较新的兼容远程 Manifest；
3. 当前 Herdr 二进制内置 Manifest。

相关命令：

```bash
# 立即获取远程更新并重载
herdr server update-agent-manifests

# 修改本地规则后重载
herdr server reload-agent-manifests

# 诊断错误状态
herdr agent explain <target>
herdr agent explain --file screen.txt --agent codex --json
```

远程规则只能更新 Herdr 已知 Agent 的检测方式；增加全新的 Agent 类型仍需要升级 Herdr 二进制。

##### 10. 多 Agent 协作与界面聚合

Herdr 会把窗格状态向上汇总到标签页和工作区：

- 任一 Agent 被阻塞，其窗格、标签页和工作区都会显示 blocked。
- 正在工作的 Agent 会让工作区显示 active。
- 已完成的 Agent 会保持 done，直到用户查看对应位置。

因此常见工作流是：同时启动多个实现、测试和审查 Agent，让其并行运行，再通过侧边栏直接找到：

- 哪个项目仍在执行；
- 哪个 Agent 正在等待审批或回答；
- 哪个任务已经完成、可以审查。

Agent 也可重命名以便脚本和人工操作：

```bash
herdr agent rename w1:p1 reviewer
herdr agent rename reviewer --clear
```

还可以将当前终端直接连接到某个 Agent：

```bash
herdr agent attach reviewer
```

- 使用 `Ctrl+B Q` 脱离，Agent 继续运行。
- 若已有其他客户端占用输入，可加 `--takeover`。
- 非 Agent 终端可使用 `herdr terminal attach &lt;terminal_id>`。

##### 11. 本地、SSH 与手机远程使用

Herdr 由后台会话服务器和一个或多个终端客户端组成。客户端断开后，窗格、Shell、测试和 Agent 仍会在服务器中运行。

###### 本地使用

在项目目录运行 Herdr，系统会自动启动或连接后台会话。通过 `Ctrl+B Q` 脱离，之后重新执行 `herdr` 即可恢复。

###### 先 SSH，再运行 Herdr

```bash
ssh you@server
herdr
```

适合：

- 已经在远程 Shell 中工作；
- 使用手机或平板 SSH 客户端；
- 希望获得类似 tmux 的简单持久会话。

手机不需要专用 Herdr App 或 Web 面板，普通 SSH 客户端即可；TUI 会适应窄屏。

###### 本地终端直接连接远端 Herdr

```bash
herdr --remote workbox
herdr --remote ssh://you@server:2222
```

此时本地 Herdr 是轻量客户端，通过 SSH 连接远端服务器。优势是可桥接本地桌面能力，例如把本机剪贴板中的图片粘贴到远端会话；若先 SSH 再在服务器运行 Herdr，则无法读取本地桌面剪贴板。

###### 选择建议

- 本地开发：`herdr`
- 手机或已进入远程 Shell：`ssh &lt;host>` 后运行 `herdr`
- 希望远程会话像本地一样，并使用本地剪贴板能力：`herdr --remote &lt;host>`

##### 12. 自动化脚本的关键实践

1. **始终解析创建命令返回的 JSON ID，不要预测窗格编号。**
2. **普通测试和服务使用 Pane；只有需要生命周期状态时才使用 Agent。**
3. **所有自动等待都设置明确超时，避免脚本无限挂起。**
4. **将 `unknown` 与成功完成区分开，不要把它当作 done。**
5. **遇到 blocked 时先读取界面，再发送按键，避免盲目自动批准。**
6. **窗格移动后更新 pane ID；不要继续依赖旧的工作区限定 ID。**
7. **全屏 Agent 输出缺失时先调整读取方式，文件输出仅作最后兜底。**
8. **利用多个窗格并行执行实现、测试和代码审查，再通过状态汇总集中处理异常。**

命令失败时，服务器错误或超时会向标准错误输出 JSON，并以退出码 **1** 结束；CLI 语法错误使用退出码 **2**，脚本可据此区分运行失败和参数错误。

#### 用 Herdr 协调实现测试与审查：内容总结

Herdr 是一个面向编码 Agent 的自动化与协调层，可以通过脚本或其他 Agent，统一管理多个终端、启动编码 Agent、执行测试、收集结果并跟踪任务状态。使用时应根据任务类型选择合适的控制对象：布局用 Workspace/Tab/Pane，普通命令用 Pane，编码 Agent 则用 Agent 控制。

##### 一、Herdr 的基本控制层次

Herdr 将自动化对象分为三类：

| 对象 | 主要职责 | 典型用途 |
|---|---|---|
| Workspace、Tab、Pane | 管理终端布局和拓扑结构 | 创建项目空间、标签页和终端窗格 |
| Pane | 控制原始终端 | 执行 Shell 命令、测试、启动服务器、读取输出 |
| Agent | 控制已识别的编码 Agent | 启动 Agent、发送提示、等待工作完成或阻塞 |

需要注意：

- **Pane 不一定运行 Agent**，它也可能只是普通 Shell 或测试进程。
- **Agent 是当前运行在某个 Pane 中、且被 Herdr 识别的进程**。
- `agent start` 只能在已有的 Shell Pane 中启动 Agent，**不会自动创建、拆分或移动布局**。
- 创建 Workspace 会同时创建第一个 Tab 和根 Pane；创建 Tab 也会创建根 Pane。
- 建议直接使用命令返回的 Pane ID，而不是自行猜测 ID。

###### 示例：创建工作空间并拆分审查 Pane

```bash
created=$(herdr workspace create --cwd ~/project --label api --no-focus)
pane_id=$(printf '%s\n' "$created" | jq -r '.result.root_pane.pane_id')

split=$(herdr pane split "$pane_id" --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')
```

返回结果中：

- `workspace create` 会提供 `.result.workspace`、`.result.tab` 和 `.result.root_pane`。
- `tab create` 会提供 `.result.tab` 和 `.result.root_pane`。
- `pane split` 会提供新 Pane：`.result.pane`。

如果 Pane 被移动到其他 Workspace，应继续使用：

```text
.result.move_result.pane.pane_id
```

旧 Pane ID 会保存在：

```text
.result.move_result.previous_pane_id
```

##### 二、Agent 身份与启动方式

###### 1. Pane ID 与 Agent 名称

- Pane ID 表示终端位置，例如：`w1:p2`。
- Agent 名称是便于人类识别的别名，例如：`reviewer`。
- Agent 名称必须符合：

```text
[a-z][a-z0-9_-]{0,31}
```

- 名称在当前存活的 Agent 中必须唯一。
- Agent 退出、释放或被替换后，名称别名会被清除，不会永久绑定到 Pane。
- Agent 命令可以通过唯一的 Agent 名称，或当前承载该 Agent 的 Pane ID 寻找目标。

###### 2. 启动前提

调用 `agent start` 前，目标 Pane 必须处于可用 Shell 提示符状态，即：

- 没有正在运行的前台命令；
- 没有编辑器或其他 Agent 占用终端；
- Shell 已回到交互式提示符。

支持的 Agent 类型包括：

`pi`、`claude`、`codex`、`gemini`、`cursor`、`devin`、`agy`、`cline`、`omp`、`mastracode`、`opencode`、`copilot`、`kimi`、`kiro`、`droid`、`amp`、`grok`、`hermes`、`kilo`、`qodercli` 和 `maki`。

启动示例：

```bash
herdr agent start reviewer \
  --kind codex \
  --pane "$review_pane" \
  -- -m gpt-5.4
```

启动命令会等到 Herdr 在目标终端中检测到预期 Agent，并确认其可以接收交互输入后才返回。

- 默认启动等待时间为 **30 秒**。
- `--timeout` 必须大于 **3000 毫秒**，且不超过 **300000 毫秒**。

对于手动启动的 Agent，Herdr 通常也能自动识别；如需稳定的名称，可以执行：

```bash
herdr agent get w1:p2
herdr agent rename w1:p2 reviewer
```

##### 三、根据任务选择控制命令

不同命令适用于不同类型的操作：

| 任务 | 命令 |
|---|---|
| 执行 Shell 命令并提交 | `pane run` |
| 发送原始文本但不按 Enter | `pane send-text` |
| 发送按键或组合键 | `pane send-keys` |
| 等待终端出现文本或正则匹配 | `pane wait-output` |
| 启动指定类型的编码 Agent | `agent start` |
| 向 Agent 提交提示词 | `agent prompt` |
| 向 Agent 交互界面发送按键 | `agent send-keys` |
| 等待 Agent 状态变化 | `agent wait` |

###### 关键区别

- `pane` 命令只关心终端本身，无论当前运行的是 Shell、测试程序还是 Agent。
- `agent` 命令会识别 Agent 身份和生命周期状态，因此适合判断 Agent 是工作中、空闲、完成还是被阻塞。
- `agent prompt` 会发送文本并自动编码 Enter，且会遵守终端当前的 bracketed-paste 模式。
- 对于 `Esc`、方向键、`Enter`、`Ctrl+C` 等交互操作，应使用 `agent send-keys`。

###### Agent 状态

Herdr 主要识别以下状态：

- **idle**：Agent 已准备好接收输入，并且其界面已被 Herdr 观察到。
- **done**：底层状态与 idle 相同，但后台工作已经结束；在用户查看前仍标记为 done。
- **blocked**：Agent 出现需要审批、确认或回答问题的界面。
- **unknown**：检测到 Agent，但无法确定其生命周期状态；不代表任务成功完成。

默认等待状态是 `idle`、`done` 或 `blocked`。如果必须区分状态，可以使用多个 `--until`，例如：

```bash
herdr agent prompt reviewer "Review the current diff" \
  --wait \
  --until idle \
  --until done \
  --timeout 120000
```

其中：

- `--wait` 会等待 Agent 进入目标状态；
- `agent prompt --wait` 会先观察 Agent 是否发生生命周期变化；
- 如果 5 秒内没有观察到状态推进，会返回 `agent_prompt_stalled`；
- `--until` 只有与 `--wait` 一起使用时才有效；
- `agent wait` 如果发现当前状态已经符合要求，会立即返回。

###### 典型的“启动审查 Agent 并等待”流程

```bash
split=$(herdr pane split --current --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')

herdr agent start reviewer \
  --kind codex \
  --pane "$review_pane" \
  -- -m gpt-5.4

herdr agent prompt reviewer "Review the current diff" \
  --wait \
  --timeout 120000

herdr agent read reviewer \
  --source recent-unwrapped \
  --lines 120
```

普通测试进程则不应当当作 Agent 处理：

```bash
herdr pane run w1:p3 "just test --watch"

herdr pane wait-output w1:p3 \
  --regex "passed|failed" \
  --timeout 120000
```

##### 四、读取终端输出时的注意事项

`pane read` 和 `agent read` 默认直接输出终端文本，并去除 ANSI 转义符。

常用选项：

- `--format ansi` 或 `--ansi`：保留 ANSI 转义符；
- `--source recent`：读取最近输出；
- `--source visible`：读取当前屏幕可见内容；
- `--lines N`：限制读取行数；
- `--regex`：使用 Rust 正则表达式逐行匹配。

默认情况下，最近输出最多读取终端最近渲染的 **80 行**。socket API 则通过：

```text
.result.read.text
```

返回文本内容。

##### 五、全屏 Agent 的 alternate-screen 限制

Claude Code、OpenCode 等全屏 Agent 可能使用终端的 **alternate screen**。这类内容不会进入 Herdr 主机的滚动历史，因此：

- 增大 `--lines` 不一定能读到更多历史输出；
- 如果扩大读取范围后仍没有新增内容，说明响应可能已不在主机滚动缓冲区中；
- 窗口较小或字体较大时，更容易出现该问题。

建议按以下顺序处理：

1. 要求 Agent 输出简洁内容；
2. 增大 Pane 或缩小终端字体；
3. 使用 Agent 自带的日志、转录和滚动功能；
4. 滚动 Agent 界面后，使用 `--source visible` 读取当前页面；
5. 如果仍无法读取，再要求 Agent 将完整回复写入临时目录，并只返回文件路径，然后直接读取文件。

最后一种方式只应作为兜底方案，不建议在初始提示中就要求 Agent 写文件。

##### 六、多 Agent 管理与状态检测机制

Herdr 的核心场景是同时运行多个编码 Agent：

- 每个 Agent 都运行在真实终端 Pane 中；
- Shell、日志、提示词和后台进程均保持不变；
- Herdr 会将 Pane 的状态汇总到 Tab 和 Workspace；
- 用户可以直接跳转到需要决策的 Pane，而不必逐个轮询终端。

状态在界面中的表现为：

- Agent 被阻塞：其 Pane、Tab 和 Workspace 都显示为 blocked；
- Agent 正在工作：Workspace 显示为 active；
- Agent 完成：仍会保留在界面中，直到用户查看。

这适合以下并行流程：

1. 一个 Agent 编写代码；
2. 一个 Agent 运行测试；
3. 一个 Agent 审查当前 diff；
4. 主控脚本或主 Agent 等待测试结果和审查意见；
5. 如果某个 Agent 被阻塞，再单独处理审批或问题。

##### 七、Agent 状态来源与检测优先级

不同 Agent 的状态来源不同：

- 有完整生命周期 Hook 的 Agent：优先使用 Hook 报告；
- 没有完整 Hook 的 Agent：通过前台进程识别，并分析终端底部屏幕快照；
- 屏幕检测使用的是 Pane 缓冲区底部的实时内容，而不是用户滚动后看到的历史视图。

部分 Agent 的具体情况如下：

- `pi`、`Devin`、`Hermes Agent` 等：在相应 Hook 可用时，可使用生命周期 Hook。
- `GitHub Copilot CLI`、`Qoder CLI`、`Droid`、`Claude Code`、`Codex`、`Cursor Agent CLI` 等：主要提供会话身份，生命周期仍依赖屏幕 Manifest。
- `OpenCode`、`Kilo Code`、`MastraCode` 等：在插件或 Hook 可用时使用生命周期信息。
- Gemini CLI 和 Cline 已被检测支持，但测试程度相对较低。
- 不支持的 Agent 仍可作为普通终端进程运行，但可能没有完整的状态识别能力。

###### 重要限制

Claude Code、Codex、GitHub Copilot CLI、Droid、Qoder CLI 和 Cursor Agent CLI 的集成并非完整生命周期权威来源，可能漏掉：

- 权限审批结果；
- Escape 中断；
- 其他状态转换。

因此，Herdr 对这些 Agent 仍使用屏幕 Manifest 检测。

##### 八、虚拟机、容器和沙箱包装器

在 Linux 或 macOS 上，某些包装器可能会隐藏真实 Agent 进程，使 Herdr 无法正确识别。

可以通过环境变量告诉 Herdr 当前前台进程实际对应的 Agent：

```bash
HERDR_AGENT=claude fence -- claude
```

或：

```bash
HERDR_AGENT=claude nono run \
  --profile claude-code \
  -- claude
```

注意：

- `HERDR_AGENT` 必须设置在 Herdr 主机可见的包装器命令上；
- 只在虚拟机或容器内部设置，Herdr 主机无法看到；
- 不建议全局导出，除非所有继承该环境变量的前台进程都是同一种 Agent。

对于依赖屏幕 Manifest 的 Agent，blocked 检测较为严格：只有当实时底部屏幕匹配已知的审批、问题或权限界面时，才会标记为 blocked。

如果出现 Herdr 不认识的新提示界面：

- Agent 可能暂时显示为 idle；
- 不应因此自动发送输入或执行破坏性操作；
- 这只影响状态显示和等待逻辑。

---

##### 九、检测 Manifest 的更新与诊断

Herdr 内置 Agent 检测 Manifest，也会从 `herdr.dev` 检查远程更新。

Manifest 的优先级如下：

1. 本地覆盖文件；
2. 缓存的远程 Manifest；
3. 当前运行版本内置的 Manifest。

本地覆盖文件位置：

```text
~/.config/herdr/agent-detection/<agent>.toml
```

本地覆盖始终优先。无效的覆盖文件会被忽略，并回退到缓存或内置版本。

相关命令：

```bash
herdr server update-agent-manifests
```

立即获取远程更新并重新加载。

```bash
herdr server reload-agent-manifests
```

重新加载手动编辑的本地 Manifest。

当 Agent 状态判断不正确时，可以使用：

```bash
herdr agent explain <target>
```

或分析文件中的屏幕内容：

```bash
herdr agent explain \
  --file screen.txt \
  --agent codex \
  --json
```

诊断结果可包含：

- 识别出的 Agent；
- 最终状态；
- 是否跳过屏幕检测；
- Manifest 来源和版本；
- 远程缓存版本；
- 本地覆盖是否生效；
- 匹配到的规则；
- 可见证据；
- 空闲状态的回退原因；
- 远程更新被跳过的原因。

---

##### 十、Tmux、直接连接与自定义标签

###### Tmux 限制

Herdr 可以运行在 tmux 外层环境中，但不会检查 Herdr Pane 内部启动的 tmux 会话。

如果 Shell 框架在 Herdr 内自动进入 tmux，Herdr 看到的可能只是 tmux 进程，而不是后面的 Agent，导致无法正确检测。

###### 安装直接集成

为常用 Agent 安装对应集成，可以获得 Hook 或插件提供的状态信息：

```bash
herdr integration install claude
herdr integration status
```

###### 自定义 Agent 名称

```bash
herdr agent rename w1:p1 reviewer
herdr agent rename reviewer --clear
```

###### 自定义状态和显示信息

语义状态会影响等待、通知和状态汇总；显示信息则可以单独配置：

```bash
herdr pane report-agent w1:p1 \
  --source custom:indexer \
  --agent docs-bot \
  --state working

herdr pane report-metadata w1:p1 \
  --source custom:indexer-display \
  --token summary=indexing
```

例如，`summary=indexing` 只是展示信息，不会改变 Agent 的语义状态。

此外，侧边栏还可以显示：

- `terminal_title`
- `terminal_title_stripped`

这些标题信息由 Herdr 临时维护，冷启动后不会保留。

###### 直接连接 Agent

可以直接连接某个 Agent，而不是打开完整 Herdr 界面：

```bash
herdr agent attach reviewer
```

退出连接：

```text
Ctrl+B Q
```

如果已有其他客户端占用输入控制权，可使用：

```bash
herdr agent attach reviewer --takeover
```

非 Agent 终端则使用：

```bash
herdr terminal attach <terminal_id>
```

##### 十一、Herdr 的持久化工作方式

Herdr 由后台会话服务器和一个或多个终端客户端组成：

- Pane 在后台服务器中持续运行；
- 客户端可以随时连接和断开；
- 客户端断开后，Agent、测试、服务器和日志仍然继续运行；
- 使用 `Ctrl+B Q` 可退出当前客户端但保留后台任务。

Herdr 应在代码所在的机器上运行，使用方式类似终端复用器。

---

##### 十二、远程开发的三种方式

###### 1. 直接 SSH 后运行 Herdr

```bash
ssh you@server
herdr
```

适合：

- 已经习惯在 SSH Shell 中工作；
- 使用手机或平板 SSH 客户端；
- 希望 Herdr 行为类似远程 tmux。

工作流程是：

1. SSH 登录代码和凭据所在的服务器；
2. 在服务器上启动 Herdr；
3. 使用 `Ctrl+B Q` 分离；
4. 断开 SSH；
5. 下次重新 SSH 后再次运行 Herdr。

###### 2. 使用本地薄客户端连接远程 Herdr

```bash
herdr --remote workbox
```

或：

```bash
herdr --remote ssh://you@server:2222
```

这种方式中：

- 本地 Herdr 只是薄客户端；
- 远程服务器运行实际的 Herdr 会话、Agent 和终端；
- UI 会通过 SSH 流式传回本地；
- 本地桌面能力，例如图片剪贴板粘贴，可以桥接到远程环境。

如果需要重复使用，可以写入 SSH 配置：

```text
Host workbox
    HostName server.example.com
    User you
    Port 2222
```

之后执行：

```bash
herdr --remote workbox
```

###### 3. 选择建议

- **本地开发**：直接运行 `herdr`。
- **已进入远程 SSH Shell，或使用手机 SSH**：执行 `ssh you@server` 后再运行 `herdr`。
- **希望本地终端像操作本地会话一样访问远程环境**：使用 `herdr --remote &lt;host>`。

总体而言，Herdr 通过“真实终端 Pane + Agent 生命周期状态 + 可脚本化命令”的组合，使测试、代码编写和审查可以并行执行，并能集中等待结果、发现阻塞点和处理需要人工决策的环节。

## 口播总结（2）

### 2026-08-03 00:37:54

#### 用 Herdr 协调测试与审查

Herdr 的核心作用，是把多个编程智能体、测试进程和普通终端统一组织起来，并让脚本或其他智能体自动分配任务、等待结果和处理卡点。听完这份总结，你可以了解怎样搭建工作区、启动审查智能体、监控测试，以及在本地、远程电脑甚至手机上继续同一套工作。

##### 首先，分清布局、终端和智能体

最重要的基础，是根据任务选择正确的控制对象。Herdr 把自动化能力分成三层：布局、终端窗格和智能体。

布局负责组织终端位置。Herdr 的结构从大到小是工作区、标签页和窗格。窗格可以理解为一个真实的终端窗口。创建工作区时，会自动得到第一个标签页和根窗格；创建标签页时，也会自动得到一个根窗格。只有确实需要第二个终端时，才应该继续拆分窗格。

窗格负责普通终端操作，比如运行测试、启动服务器、发送按键和等待日志。即使里面没有智能体，窗格本身也依然存在。

智能体则是窗格中正在运行、并且被 Herdr 识别出来的编程工具，比如 Claude Code、Codex、Gemini 或 Cursor。`agent start` 只会在现有窗格里启动智能体，不会替你创建、拆分或移动布局。因此，正确顺序是先准备好一个空闲的命令行窗格，再启动智能体。

这里还有一个关键细节：创建工作区、标签页或窗格时，Herdr 会返回 JSON，也就是便于程序读取的结构化结果。自动化脚本应该从结果中提取真实的窗格编号，而不是自己猜编号。移动窗格之后，它在工作区中的编号也会改变，后续操作要使用移动结果里返回的新编号。已经开始的等待操作，则可能因为这次移动而以“智能体未运行”结束。

##### 接下来，给智能体建立稳定身份

核心结论是：窗格编号代表终端位置，智能体名称代表当前运行在这个位置里的智能体，两者不要混为一谈。

例如，类似 `w1:p2` 的编号表示某个工作区中的某个窗格。`reviewer` 这样的名称，则可以作为审查智能体的易读别名。名称必须以小写字母开头，只能包含小写字母、数字、下划线或短横线，最长三十二个字符，而且不能和其他正在运行的智能体重名。

这个名称并不会永久重命名窗格。智能体退出、被释放或被替换后，别名也会清除。智能体命令既可以使用唯一名称，也可以使用当前承载它的窗格编号。

启动前，窗格必须停留在可交互的 Shell 提示符，也就是普通命令行提示符。前台不能还开着编辑器、命令或另一个智能体。`agent start` 会等待 Herdr 确认指定智能体确实已经在同一终端中运行，并进入可以交互的状态。默认启动等待时间是三十秒；自定义超时必须在三秒到五分钟之间。

Herdr 也能自动识别手动启动的常见智能体。识别后，可以再给它起一个稳定名称，方便脚本或人类继续操作。

##### 然后，为不同任务选择正确命令

核心原则很简单：普通进程使用窗格命令，需要理解智能体状态时使用智能体命令。

如果要运行测试、服务器、持续集成监视器或普通 Shell 命令，可以使用 `pane run`。只发送文字但不按回车，可以使用 `pane send-text`；发送回车、退出、组合键等终端按键，可以使用 `pane send-keys`；等待日志中出现某段文字，则使用 `pane wait-output`。

如果对象是编程智能体，就使用 `agent` 系列命令。`agent start` 负责启动；`agent prompt` 负责提交任务；`agent send-keys` 负责在交互界面里发送退出键、方向键、回车或中断组合键；`agent wait` 负责等待智能体进入特定状态。

这两类命令的区别非常重要。窗格输入会直接作用于终端，不管当前是谁占据它。智能体输入则会先确认目标智能体仍然控制着那个窗格。如果智能体已经退出，Herdr 会拒绝操作。这样更适合安全的自动化流程。

例如，审查代码时，可以先拆出右侧窗格，在里面启动一个名为 `reviewer` 的 Codex 智能体，然后提交“审查当前代码差异”这个任务，并等待最多两分钟。完成后，再读取它最近的输出。与此同时，另一个窗格可以运行持续测试，并等待日志里出现“通过”或“失败”。

##### 更重要的是，正确理解智能体状态

Herdr 的价值不只是发送命令，还在于理解智能体当前是在工作、等待输入，还是已经完成。

它主要使用四种状态。`working` 表示正在工作。`blocked` 表示出现了审批、权限确认或问题界面，需要人类处理。`idle` 表示已经可以接收新输入，并且对应标签页在 Herdr 界面中被查看过。`done` 表示后台工作已经结束，但这个完成结果还没有被查看；一旦聚焦到相应标签页或窗格，它会回到普通的空闲状态。

还有一种 `unknown`，表示 Herdr 确认智能体存在，但无法可靠判断生命周期。这个状态绝不能被当成任务成功完成的证据。

使用 `agent prompt` 加上等待选项时，Herdr 会立即提交提示词，然后等待目标进入指定的稳定状态。默认可接受的结果是空闲、完成或阻塞，也可以明确要求其中一个或多个状态。

但要注意，这种等待跟踪的是智能体整体状态，而不是某一次对话轮次。如果智能体提交任务前就已经在工作，那么当前工作结束也可能满足等待条件。单独使用 `agent wait` 时，如果目标已经处于指定状态，命令会立即返回。

为了避免无休止地等待，提交任务后，Herdr 会先观察状态是否在五秒内发生变化。如果没有出现活动迹象，会报告提示任务停滞。普通等待命令本身没有默认超时，因此自动化脚本最好显式设置超时。发生超时或服务器错误时，命令会输出结构化错误并以状态码一退出；命令语法无效时，状态码是二。

##### 测试日志和智能体输出，要用不同方式等待

核心结论是：日志匹配只看终端文字，不理解智能体是否真正完成；生命周期等待理解状态，但不保证抓到完整回答。

`pane wait-output` 会反复查看终端快照，寻找指定文字或正则表达式。正则表达式，就是按照规则匹配文字的模式。比如可以等待测试日志出现“passed”或“failed”。

它会立即搜索当前已有的文字，所以旧日志也可能直接命中。默认查看最近八十行终端内容，也可以增加行数。读取时默认使用 UTF-8 纯文本，并去掉终端颜色等 ANSI 控制字符；需要保留终端样式时，可以明确指定。

如果是智能体，则可以先使用 `agent wait` 等待它变成 `done`、`idle` 或 `blocked`，再读取终端内容。比如，审查智能体进入阻塞状态后，可以先读取它最近的输出，确认它是在询问权限还是提出问题，再发送退出键或其他交互按键。

因此，一个稳妥的协调流程通常是：测试进程用文字匹配，智能体用生命周期状态，最后再读取实际输出。不要只因为日志里出现某个词，就认定整个任务已经成功。

##### 全屏智能体可能丢失历史输出

这里有一个很重要的限制。Claude Code、OpenCode 等全屏智能体，可能使用终端的“备用屏幕”。备用屏幕可以理解为程序临时占用的一整页界面，其中的内容不会自动进入 Herdr 所在终端的历史滚动区。

这意味着，即使把读取行数调得很大，也不一定能找回已经离开屏幕的回答。如果增加行数后仍然没有更多内容，很可能不是 Herdr 没有继续读取，而是这些历史文字根本没有被终端保存。窗格较小或字体较大时，这个问题更容易发生。

优先的处理方式，是让智能体回答得更简短、扩大窗格，或者使用更小的字体。也可以先在智能体自身界面中向上滚动，再让 Herdr 读取当前可见页面。

如果仍然无法取得完整回答，可以在读取失败之后，要求智能体把完整结果写成临时目录里的 Markdown 文件，并且只回复文件路径，然后直接读取那个文件。但这只是补救方案，不应该在最初提示词里就要求文件输出。

##### 多智能体协调依赖可靠的状态检测

Herdr 可以同时运行多个编程智能体。每个智能体都留在真实终端窗格中，所以它的 Shell、日志、提示词和运行进程都会保留。Herdr 会把窗格状态逐级汇总到标签页和工作区，让使用者直接看到哪个项目仍在运行、哪个需要决策、哪个已经完成，而不必逐个终端检查。

状态判断主要有两种来源。

第一种是生命周期钩子或插件。它们由智能体集成主动报告空闲、工作、阻塞和会话身份。如果某个智能体安装了完整的生命周期集成，并且正在正常报告，Herdr 就把它作为唯一的状态权威，不再同时使用屏幕规则，避免两个来源互相冲突。

第二种是屏幕清单检测。Herdr 会识别终端前台进程，再查看窗格底部的实时屏幕内容，通过规则判断状态。这里查看的是终端缓冲区最底部的实时界面，而不是用户向上滚动后看到的历史页面。

Claude Code、Codex、GitHub Copilot CLI、Droid、Qoder 和 Cursor Agent CLI 的集成，可以提供会话身份等信息，但它们的钩子覆盖不了完整生命周期。例如，可能漏掉权限审批结果、退出键中断或其他状态变化。因此，Herdr 有意继续使用屏幕规则来判断这些智能体的工作、空闲和阻塞状态。

阻塞判断尤其严格。只有实时屏幕明确匹配已知的审批、问题或权限界面，Herdr 才会标记为阻塞。如果出现一种尚未识别的新提示界面，它可能暂时被当成空闲。这个误差只应该影响显示和等待，不能成为自动发送输入或执行破坏性操作的依据。

##### 遇到识别错误时，先诊断检测来源

如果智能体显示了错误状态，可以使用 `herdr agent explain`。它会说明最终状态、检测规则来自哪里、命中了哪条规则、看到了哪些证据，以及为什么在没有匹配规则时回退为空闲。

Herdr 内置了常见智能体的检测清单，也会从官方来源自动获取兼容的规则更新，不需要重启就能加载新的远程规则。用户还可以在配置目录中放置本地覆盖文件，本地规则的优先级最高。手动修改本地规则后，需要重启 Herdr，或者执行重新加载清单的命令。

远程规则更新只能修补 Herdr 已经认识的智能体。要支持一种全新的智能体，仍然需要升级 Herdr 本身，因为进程识别、显示标签和集成逻辑都要新增。

在 Linux 或 macOS 上，虚拟机、沙箱或包装程序可能遮住真正的智能体进程。这时，可以在宿主机可见的包装命令上设置 `HERDR_AGENT`，明确告诉 Herdr 应该使用哪种智能体的屏幕规则。这个提示必须设置在 Herdr 能看到的前台进程上，只在虚拟机或容器内部设置是无效的，也不应该无条件设成全局环境变量。

另外，Herdr 可以运行在 tmux 里面，但不会继续检查某个 Herdr 窗格内部再次启动的 tmux 会话。如果 Shell 框架自动进入内层 tmux，Herdr 看到的前台进程就只是 tmux，而不是后面的智能体。

##### 标签和附加功能让协作更清楚

智能体可以被重命名为 `reviewer`、`tester` 或其他易懂的名称，方便脚本和人类识别。语义状态和显示文字应该分开管理：状态决定等待、通知和工作区汇总；摘要之类的元数据只负责界面展示，不应该改变自动化判断。

如果只想进入某个智能体的终端，而不打开完整的 Herdr 界面，可以直接附加到该智能体。按 `Ctrl+B`，再按 `Q` 可以退出附加，但智能体仍会继续运行。鼠标滚轮、Page Up 和 Page Down 可以滚动历史，重新输入普通内容则会回到底部。如果已有其他直接附加客户端占用输入，可以使用接管选项。

##### 最后，Herdr 的会话可以跨设备持续运行

Herdr 的工作方式可以概括为一句话：在工作实际发生的机器上运行 Herdr，再从任何合适的地方连接过去。

它由后台会话服务器和一个或多个终端客户端组成。窗格、测试、服务器和智能体都运行在后台服务器中。客户端只负责显示和交互。因此，退出客户端不会结束任务。按 `Ctrl+B`，再按 `Q` 分离后，所有窗格都会继续运行；稍后重新打开 Herdr，就能回到同一会话。只有停止服务器，才会真正结束这些窗格。

本地开发时，直接在项目目录运行 Herdr 即可。

远程开发有两种主要方式。第一种是先用 SSH 登录代码和凭据所在的机器，再在那里启动 Herdr。这种体验类似在远程 Shell 中使用 tmux，特别适合手机或平板。手机不需要专门的 Herdr 应用，只要有普通 SSH 客户端，就能打开同一个持久会话。

第二种是在本地直接运行 `herdr --remote`，通过 SSH 连接远程 Herdr。此时，本地 Herdr 是一个轻量客户端，远程服务器负责实际工作。优点是体验更像本地应用，并且可以把本机的图片剪贴板能力桥接到远程会话。如果先 SSH 登录远程机器，再在那里启动 Herdr，远端程序就无法读取本机桌面剪贴板。

选择方法很简单：本地工作直接使用 Herdr；手机或已经身处远程 Shell 时，先 SSH 再启动 Herdr；希望远程会话保留本地终端体验和剪贴板能力时，使用远程客户端模式。

##### 最值得记住的五点

第一，先创建工作区、标签页和窗格，再启动智能体。`agent start` 不负责创建布局，而且目标窗格必须回到空闲的命令行提示符。

第二，普通测试、服务器和日志使用窗格命令；需要判断工作、完成或阻塞状态时，使用智能体命令。两种控制方式不要混用。

第三，`working`、`blocked`、`idle`、`done` 和 `unknown` 含义不同。尤其不要把 `unknown` 当成成功，也不要只凭终端里出现某个词就认定任务完成。

第四，全屏智能体的历史回答可能不会进入终端滚动区。应优先缩短回答、扩大窗格或使用智能体自身滚动；写入临时文件只作为读取失败后的补救。

第五，Herdr 的后台会话会持续运行。你可以让多个智能体并行审查和编码，让测试进程持续执行，然后从本地终端、远程 SSH 或手机上查看哪个任务仍在工作、哪个需要审批、哪个已经可以验收。

### 2026-09-20 00:26:02

Herdr 的核心价值，是把测试、审查和多个编码智能体，放进同一个可持续运行、可被脚本控制的终端系统里。真正需要掌握的，不是一长串命令，而是三个层次的分工：布局负责安排位置，窗格负责控制普通终端，智能体接口负责理解编码智能体的状态。

先说布局。Herdr 用工作区、标签页和窗格组织终端。创建工作区时，会同时创建第一个标签页和一个根窗格。创建标签页，也会自动得到一个根窗格。只有确实需要第二个终端时，才需要拆分窗格。

这里有一个容易犯的错误。启动智能体，并不会创建或拆分窗格。智能体只是某个现有窗格里正在运行的进程。因此，正确顺序是先创建或拆分窗格，再在其中启动智能体。

自动化脚本还应该使用创建命令返回的 JSON 数据，从响应中读取窗格编号，而不是自己猜编号。移动窗格以后，它的编号可能变化，也要继续使用移动结果中返回的新编号。这样可以避免脚本把命令发到错误的终端。

理解布局以后，下一步是选择正确的控制方式。普通测试、开发服务器、持续集成监视器和其他命令行程序，都应该用窗格命令控制。比如，在一个窗格里运行持续测试，然后等待输出中出现“通过”或“失败”。

代码审查智能体则不同。Herdr 不只需要读它的屏幕，还需要知道它正在工作、已经完成，还是正在等待批准。因此，启动、提问和等待编码智能体时，应该使用智能体命令。

可以把这理解为两种控制层次。窗格命令面对的是原始终端。它可以运行命令、输入文字、发送按键和搜索输出，不关心终端里是谁。智能体命令面对的是一个被 Herdr 识别出来的编码智能体。它会确认目标智能体仍然控制着那个窗格，并结合智能体的生命周期状态作出判断。

一个典型的测试与审查流程是这样的。先从当前窗格向右拆分一个新窗格，保存系统返回的窗格编号。然后在新窗格中启动一个代码审查智能体，并给它一个容易理解的名字，比如 reviewer，也就是审查者。接着提交“审查当前代码差异”这样的任务，并等待智能体进入稳定状态。最后，再读取它最近的终端输出。

与此同时，另一个窗格可以运行测试。测试不是编码智能体，所以不必使用智能体状态。脚本只需要等待终端输出匹配“通过”或“失败”。这样，测试和代码审查能够并行进行，但两者分别使用最适合自己的控制方式。

智能体的名字只是当前进程的别名，不会永久改变窗格名称。名称必须在仍然存活的智能体之间保持唯一。智能体退出、被释放或被替换以后，这个别名也会被清除。除了名称，也可以直接用当前承载智能体的窗格编号作为目标。

启动智能体之前，目标窗格必须停留在可用的交互式命令提示符。也就是说，前台不能还有编辑器、普通命令或另一个智能体。Herdr 启动智能体后，会等待它出现在同一个终端里，并确认已经可以接收交互输入。默认启动等待时间是三十秒。

自动化是否可靠，很大程度上取决于怎样理解智能体状态。Herdr 主要区分正在工作、空闲、完成、受阻和未知。

“正在工作”表示智能体仍在处理任务。“受阻”表示 Herdr 识别到了批准、权限或提问界面，需要人或上层智能体做决定。“空闲”表示智能体已经可以再次接收输入，而且相应标签页已在 Herdr 界面中被查看过。“完成”底层也是一种空闲状态，但表示后台工作刚结束，结果还没有被查看。读取命令行输出并不会自动把“完成”标记为已经查看。

“未知”尤其需要谨慎。它只表示 Herdr 确认智能体存在，但无法可靠判断生命周期。未知状态并不证明任务成功，也不能当作完成使用。如果自动化流程对结果有严格要求，就应该明确等待完成、空闲或受阻，而不是笼统接受任何停止变化的状态。

提交提示并等待时，还有一个重要限制。Herdr 等待的是智能体状态，不是某一次对话轮次。如果智能体原本已经在工作，那么当前活动任务结束，就可能满足等待条件，即使刚提交的新提示还没有形成一个独立、可辨认的回合。因此，复杂编排不能把一次等待简单理解为“这一条提示已经完整执行完毕”。

为了避免任务根本没有启动却无限等待，当智能体从非工作状态收到提示后，Herdr 会先要求在五秒内观察到状态变化。如果没有变化，就报告提示停滞。另一方面，等待命令本身通常没有默认超时，脚本最好主动设置合理的超时时间。超时或服务端错误会以错误信息返回，并使用非零退出状态，方便外层脚本处理失败。

状态识别的来源也值得理解。一部分智能体可以通过生命周期钩子或插件直接报告状态。另一些智能体则主要依靠屏幕内容识别。Herdr 会观察窗格底部的实时画面，根据已知界面判断智能体是在工作、空闲，还是等待批准。

为了避免误操作，受阻状态的识别是刻意保守的。只有屏幕明确匹配已知的批准、提问或权限界面时，Herdr 才会标记为受阻。遇到新的、尚未识别的提示界面，系统有时可能显示为空闲，而不是受阻。因此，状态可以帮助人找到需要关注的窗格，但不应该被用来自动发送危险输入或执行破坏性操作。

当状态判断不正确时，可以使用智能体解释功能。它会说明最终状态、采用了哪种识别来源、匹配了哪条规则，以及为什么退回到默认判断。检测规则可以远程更新，也可以用本地配置覆盖。这样，智能体界面变化后，不一定要等待整个 Herdr 程序升级。

读取审查结果时，还要留意全屏终端程序的限制。Claude Code、OpenCode 等工具可能使用终端的备用屏幕。备用屏幕中的旧内容不会进入 Herdr 的宿主滚动历史。即使把读取行数调大，已经消失的内容也不会凭空恢复。

比较稳妥的做法，是让智能体回答得简洁一些，扩大窗格，或者减小字体。如果智能体内部支持滚动，可以先在它的界面中滚动，再读取当前可见页面。如果这些办法都失败，可以追加要求，让智能体把完整回答写成临时目录中的 Markdown 文件，并且只回复文件路径，然后直接读取文件。这个方法适合作为补救，不应该在最初的提示中就默认要求文件输出。

Herdr 的运行方式也适合长时间并行任务。它由后台会话服务器和终端客户端组成。关闭或分离客户端后，窗格、测试、服务器和智能体仍会继续运行。之后重新连接，就能回到原来的现场。远程使用时，可以先通过 SSH 登录代码所在的机器，再运行 Herdr；也可以从本地终端把 Herdr 作为轻量客户端，通过 SSH 连接远端会话。前一种方式更像在远程机器上使用终端复用器，后一种方式还能利用本地剪贴板等桌面能力。

最值得记住的是，Herdr 并不是把所有终端活动都当成智能体。测试和服务器用窗格控制，代码审查者用智能体控制，布局则单独负责安排它们的位置。可靠的编排还要明确等待哪些状态、设置超时，并把“未知”与“完成”严格区分。做到这些，测试、审查和多个编码智能体就能真正并行运行，而人只需要关注已经完成或正在等待决定的地方。

#### 多智能体协作的难点不是并发，而是可观察、可寻址与可验收

Herdr最值得关注的并非“同时运行多个编码智能体”，而是它把多智能体协作拆成了三类不同对象：**布局负责安排工作位置，Pane负责控制终端进程，Agent负责表达智能体身份与生命周期状态**。这看似只是命令行设计，实际上避免了自动化系统里一个常见错误：把终端、进程、任务和智能体混成同一个概念。

例如，测试服务器只是普通进程，应使用 `pane run` 和输出匹配；代码审查智能体则需要 `agent prompt`、`agent wait` 来判断它是在工作、空闲还是等待授权。Pane即使没有智能体也存在，智能体退出后名字会被释放；移动Pane还会改变其位置ID。**稳定的协调系统必须承认基础设施、执行者与任务生命周期并不一致**，而不是假设“开一个窗口就等于创建了一项可靠任务”。

##### 真正困难的是状态可信度

文档花了大量篇幅解释 `idle`、`working`、`blocked`、`done` 和 `unknown`，这恰恰暴露了智能体自动化最重要的约束：系统看到的往往不是任务事实，而是界面迹象。

有完整生命周期钩子的智能体，可以直接报告状态；其他智能体只能通过前台进程和终端底部内容推断。陌生的授权提示可能被误判为空闲，`unknown` 不代表成功完成，`done` 也只是“后台工作结束且尚未被查看”的界面状态。更关键的是，`agent prompt --wait` **并不跟踪某个具体回合**：如果智能体原本就在工作，那一轮工作的结束也可能满足等待条件。

因此，Herdr适合回答“哪个智能体可能需要关注”，却不能单独证明“这项审查已经正确完成”。用于测试与审查时，可靠流程仍需加入任务级验收：限定超时、要求固定格式的结果、检查退出码或测试报告，并验证目标文件或提交确实发生了变化。生命周期状态是调度信号，不应被当成业务结果。

##### 输出丢失揭示了下一层产品机会

全屏智能体常使用终端的 alternate screen，历史回复可能不会进入宿主滚动区；增加读取行数也无法找回已经消失的内容。文档给出的兜底方法是让智能体把完整结果写入临时Markdown文件，再返回路径。

这个细节说明，多智能体工具目前更像“终端控制平面”，还不是完整的任务系统。真正有价值的下一层能力，不是继续增加可启动的智能体数量，而是建立**任务与产物之间的可靠关联**：每次委派拥有独立ID，状态变化对应具体回合，输出被持久化，审查结论能关联到代码版本、测试结果和批准记录。

在现阶段，Herdr最适合承担“注意力路由器”：让测试、服务和多个审查者持续运行，把等待输入、仍在执行和可供查看的工作集中呈现。它提高的是并行工作的可管理性，而非自动保证结果正确。对团队而言，值得验证的也不是“能否同时开更多Agent”，而是：**在加入明确产物契约和验收检查后，等待与切换成本是否真的下降，同时没有增加误判完成的风险。**

#### Herdr 的价值不在“多智能体”，而在把不可控终端变成可协调系统

Herdr 最值得关注的，并不是能同时启动多个编程 Agent，而是它把原本散落在终端里的进程、交互界面和等待状态，抽象成了一套可供脚本调用的控制面。其核心区分很清楚：**Layout 管空间，Pane 管终端，Agent 管可识别的智能体及其生命周期。**测试、服务器和 CI watcher 仍按普通进程控制；只有需要理解“工作中、完成、等待审批”等语义时，才使用 Agent 接口。

这看似是 API 设计细节，实际决定了自动化是否可靠。很多所谓多 Agent 工具把“创建窗口、启动模型、派发任务、判断完成”混成一个动作，一旦中间状态异常，就很难恢复。Herdr 则要求先创建 Pane、保存返回的 ID，再启动 Agent；移动 Pane 后还要使用新的 ID。它没有假装终端位置、进程身份和任务身份是同一件事。

##### 真正的瓶颈是状态可信度，而不是并行数量

Herdr 可以等待 Agent 进入 `idle`、`done`、`blocked` 或 `unknown`，并把状态汇总到 Pane、Tab 和 Workspace。这让一种实用工作流成为可能：主 Agent 修改代码，审查 Agent 检查 diff，普通 Pane 跑测试；操作者只处理被阻塞或已完成的任务。**当 Agent 数量增加，稀缺资源会从执行能力转向人的注意力，状态汇总本质上是在做注意力路由。**

但文档也坦率展示了边界：部分 Agent 有完整生命周期 Hook，另一些只能根据终端底部画面识别状态；陌生的授权提示甚至可能被误判为 idle。`unknown` 也不代表成功完成。全屏程序使用 alternate screen 时，历史输出还可能根本没有进入 scrollback。因而这些状态适合通知和导航，却不应直接授权删除、发布或合并等破坏性操作。

还有一个容易踩坑的语义：`agent prompt --wait` 等待的是状态稳定，而不是严格绑定某一轮请求；如果 Agent 已经在工作，当前任务结束就可能满足等待条件。需要强一致性的流水线，仍应让 Agent 产出可核验的文件、提交或测试报告，而不能只看到 `done` 就认为目标已经达成。

##### 它是协调底座，不是完整的多 Agent 产品

Herdr 没有提供任务依赖图、共享记忆、结果评测、冲突解决或权限策略，因此更准确的定位是**终端原生的 Agent 编排层**，而非会自行分工协作的“智能团队”。这反而是它的可迁移价值：保留 Claude Code、Codex 等现有工具的真实终端和会话，只统一启动、寻址、观察与介入方式。

对测试与审查场景，较稳妥的设计不是让 Agent 互相自由对话，而是让它们围绕明确工件协作：实现者生成 diff，审查者输出问题清单，测试进程提供确定性结果，人只在审批、冲突和异常状态出现时介入。**多 Agent 自动化能否成立，最终取决于状态信号和交付物是否可验证，而不是同时打开了多少个 Agent。**

Herdr 是一个面向编程智能体的终端编排工具：可在持久化窗格中并行启动测试、审查等任务，并统一发送指令、等待状态和收集结果。

##### 关键内容

- **先分清三层对象**：工作区/标签页/窗格负责终端布局；`pane` 命令控制普通终端进程，如测试、服务器；`agent` 命令控制 Herdr 已识别的编程智能体及其状态。启动智能体前必须先创建窗格，`agent start` 不会自动拆分布局。
- **典型审查流程**：新建或拆分窗格，保存命令返回的 pane ID；在其中启动 Codex、Claude 等智能体；用 `agent prompt --wait` 提交“审查当前改动”，待其进入 `idle`、`done` 或 `blocked` 后读取输出。普通测试则用 `pane run` 和 `pane wait-output`。
- **状态不等于结论**：`blocked` 表示需要批准或回答，`done` 表示后台任务完成但尚未查看，`unknown` 只表示无法可靠判断，不能视为成功。部分智能体依靠屏幕内容识别状态，可能把陌生提示误判为 `idle`。
- Herdr 会话在后台持续运行，可本地使用，也可通过 SSH 从电脑或手机重新连接；多个智能体的状态会汇总到侧边栏，方便定位谁在工作、谁需处理、谁已完成。

##### 通俗解读

Herdr 更像“带状态看板的 tmux”，而不是替你完成审查的智能体。它负责给不同助手分配终端、派任务并等待结果。全文屏应用的历史输出可能因 alternate screen 丢失；应先缩短回复或扩大窗格，必要时再让智能体把完整结果写入文件。

**是否值得细读：**若要写脚本自动协调多个编码智能体，尤其需可靠处理 ID、超时和状态，值得细读；若只是手动开一个智能体，掌握上述流程即可。
