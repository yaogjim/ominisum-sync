#### 恭喜您安装 Amp。本手册将帮助您充分利用它。

#### Why Amp?

Amp 是你的终端和编辑器的前沿编码代理。

- **多模型：** Opus 4.6、GPT-5.4、快速模型——Amp 使用所有这些模型，针对每个模型的优势。
- **主观的：** 你总是在使用 Amp 的优秀部分。如果我们不使用也不喜欢某个功能，我们就会将其废弃。
- **在前沿：** Amp 跟随模型的指引。不支持向后兼容，无遗留特性。
- **Threads:** 你可以保存和分享与 Amp 的交互。你不会在没有版本控制的情况下编写代码，对吧？

Amp 有 3 种模式： `smart` （无约束的最先进模型使用）、 `rush` （更快、更便宜，适用于小型、定义明确的任务）和 `deep` （针对复杂问题的深度推理与扩展思考）。

*想深入了解更多吗？继续关注我们的 Raising an Agent 播客 ，在那里我们会分享我们在构建 Amp 过程中学到的内容，并了解我们的 FIF 。*

#### Using Amp

##### Agent Modes

Amp has 3 modes:

- **`smart`** ：采用最先进的模型，不受限制，以实现最大能力和自主性。
- **`rush`**: 更快、更便宜且功能较弱，适用于小型、定义明确的任务。参见 Rush Mode
- **`deep`**: 深度推理，结合 GPT-5.4 对复杂问题进行扩展思考。

*还有一个隐藏的： `large` 模式*

请参阅 型号 以了解每种模式使用的型号。

通过打开命令面板（ `Ctrl+O` ）并输入 `mode` 来在命令行界面中切换模式。

##### How to Prompt

Amp 的 `smart` 模式目前使用 Claude Opus 4.6，具有最多 300k 输入上下文 token。为获得最佳效果，请遵循以下指南：

- 明确说出你想要什么。而不是“你能做 X 吗？”，尝试说“做 X”。
- 保持简短，保持专注。将非常大的任务分解为较小的子任务，每个线程一个子任务。不要要求代理在同一个线程中编写数据库迁移，就像它之前为某个文档页面修改 CSS 那样。
- 不要试图让模型猜测。如果您知道如何实现您希望代理完成的任务——应该查看哪些文件，应该运行哪些命令——把这些信息放在您的提示中。
- 如果你希望模型不编写任何代码，而只进行研究和规划，请这样说：“只规划如何实现这一点。不要编写任何代码。”
- 使用 `AGENTS.md` 文件 来指导 Amp 如何运行你的测试和构建步骤，并避免常见错误。
- 如果线程积累了过多的噪声，就放弃这些线程。有时会出现问题，带有错误消息的失败尝试会充斥上下文窗口。在这种情况下，通常最好从一个新线程和一个干净的上下文窗口开始。
- 告诉代理如何最好地检查其工作：要运行什么命令或测试，要打开哪个 URL，要查看哪些日志。反馈对代理的帮助和对我们的帮助一样大。

对话中的第一个提示非常重要，它为后续对话设定方向。我们鼓励您仔细斟酌这个提示。在 Amp 的编辑器扩展中，我们使用 `Cmd/Ctrl+Enter` 提交消息——这是一个提醒，要在提示中投入精力。在 Amp CLI 中， `Enter` 用于提交，您还可以使用 `Shift+Enter` （支持终端）或 `Ctrl+J` 插入换行符。

以下是我们在 Amp 中使用过的一些提示词示例：

- 使 `observeThreadGuidanceFiles` 返回 `Omit<ResolvedGuidanceFile, 'content'>[]` 并从其返回值中移除该字段，同时更新测试。请注意，该字段被省略是因为它在不需要文件内容的场景中使用，这减少了通过视图 API 传输的数据量。"( 查看线程 )

##### AGENTS.md

Amp looks in `AGENTS.md` files for guidance on codebase structure, build/test commands, and conventions.

File Examples

`AGENTS.md`  
在 cwd、父目录及子树中 架构、构建/测试命令、内部 API 概述、审查与发布步骤

`$HOME/.config/amp/AGENTS.md`  
`$HOME/.config/AGENTS.md` 个人偏好、设备特定命令以及你在提交到代码仓库之前在本地测试的指导

Amp 自动包含 `AGENTS.md` 文件：

- \`AGENTS.md\` 文件位于当前工作目录（或编辑器工作区根目录）以及父目录（直到 \`$HOME\`）中，始终会被包含。
- 子树中的 `AGENTS.md` 文件会在代理读取子树中的文件时被包含。
- 如果存在， `$HOME/.config/amp/AGENTS.md` 和 `$HOME/.config/AGENTS.md` 都会被包含。

如果目录中不存在 `AGENTS.md` 文件，但存在名为 `AGENT.md` （不带 S）或 `CLAUDE.md` 的文件，则会包含该文件。

在一个包含多个子项目的大型代码仓库中，我们建议保持顶层的 AGENTS.md 文件为通用格式，并针对每个子项目在子树中创建更具体的 AGENTS.md 文件。

要查看 Amp 正在使用的代理文件，请从命令面板中选择 agents-md list 。

###### Writing AGENTS.md Files

Amp 会主动为你生成 AGENTS.md 文件，如果该文件不存在的话。你可以手动创建或更新任何 AGENTS.md 文件，也可以通过让 Amp（ *“根据我在本线程中告诉你的内容更新 AGENTS.md”* ）来实现。

为了将其他文件作为上下文包含进来，请在代理文件中@提及它们。例如：

```markdown
See @doc/style.md and @specs/**/*.md.

When making commits, see @doc/git-commit-instructions.md.
```

- 相对路径相对于包含提及内容的代理文件进行解析。
- 绝对路径和 `@~/some/path` 也被支持。
- @-提及在代码块中会被忽略，以避免误报。
- 通配符模式被支持（例如 `@doc/*.md` 或 `@.agent/**/*.md` ）。

###### Granular Guidance

为了提供仅适用于处理特定文件时的指导，您可以在上述文件的 YAML 前置内容中指定 `globs` 。

例如，应用针对特定语言的编码规则：

1. 在你的 `AGENTS.md` 文件中的任何位置放置 `See @docs/*.md` 。
2. Create a file `docs/typescript-conventions.md` with:
   ```markdown
   ---
   globs:
     - '**/*.ts'
     - '**/*.tsx'
   ---
   
   Follow these TypeScript conventions:
   
   - Never use the `any` type
   - ...
   ```
3. Repeat for other languages.

被提及的带有 `globs` 的文件，只有当 Amp 已读取过匹配任一 glob 的文件时才会被包含（在上例中，即任一 TypeScript 文件）。如果未指定 `globs` ，则在 @-提及该文件时，该文件始终会被包含。

通配符隐式地前缀为 `**/` ，除非它们以 `../` 或 `./` 开头，在这种情况下，它们指的是相对于提及文件的路径。

Other examples:

- 前端特定指导: `globs: ["src/components/**", "**/*.tsx"]`
- Backend guidance: `globs: ["server/**", "api/**"]`
- Test guidance: `globs: ["*.test.ts", "__tests__/*"]`

###### Migrating to AGENTS.md

\#

- 来自 Claude 代码: `mv CLAUDE.md AGENTS.md && ln -s AGENTS.md CLAUDE.md`, 并对子树 `CLAUDE.md` 文件重复此操作
- 来自 Cursor： `mv .cursorrules AGENTS.md && ln -s AGENTS.md .cursorrules` 然后在 `AGENTS.md` 的任意位置添加 `@.cursor/rules/*.mdc` 以包含所有 Cursor 规则文件。
- 来自现有的 AGENT.md： `mv AGENT.md AGENTS.md` （可选 - 两个文件名仍然有效）

##### Handoff

Amp 在你保持线程短小并专注于单个任务时工作效果最佳

要在新线程中继续来自一个线程的工作，请使用命令面板中的 `handoff` 命令，以原始线程中的相关文件和上下文创建一个新线程。

为交接命令提供一些帮助，以引导新的提示。例如：

- `now implement this for teams as well, not just individual users`
- `execute phase one of the created plan`
- `check the rest of the codebase and find other places that need this fix`

请参阅 交接（不再进行压缩） 了解为什么 Amp 不支持压缩。

##### Referencing Other Threads

你可以在提示中通过主题 URL（例如 `https://ampcode.com/threads/T-7f395a45-7fae-4983-8de0-d02e61d30183` ）或主题 ID（例如 `@T-7f395a45-7fae-4983-8de0-d02e61d30183` ）引用其他 Amp 主题。

输入 `@@` 以搜索一个要提及的线程。

对于每个提到的线程，Amp 将读取并提取针对您当前任务的相关信息。这对于从之前的线程继续工作或复用该线程中的技术非常有用。

Examples:

- `Implement the plan from https://ampcode.com/threads/T-7f395a45-7fae-4983-8de0-d02e61d30183`
- `Apply the same fix from @T-7f395a45-7fae-4983-8de0-d02e61d30183 to the form here`

##### Finding Threads

Amp 可以搜索您过去的对话线程以及您所在工作区成员的对话线程，以找到相关对话。请 Amp 根据关键词、文件路径、代码仓库、作者、日期或任务查找对话线程。

Examples:

#### Tools

Amp 代表你运行工具和 shell 命令，以检查代码、运行测试并快速迭代。

为了保持工作流程的高效，Amp 内置了 **内置的权限规则** ，这些规则允许常见的开发命令（ `ls` 、 `git status` 、 `npm test` 、 `cargo build` 以及其他许多命令）\*\*无需提示\*\*即可运行。对于看起来具有破坏性或敏感性的命令，如 `git push` 或 `rm -rf` ，会先要求确认。

您可以准确地查看默认情况下允许的内容：

```
$ amp permissions list --builtin
```

这些默认值可以被您自己的规则覆盖。有关详细信息，请参阅 权限 。

Amp 对您工作区中的内容进行操作。不可信的代码库、MCP 服务器和其他外部输入可能会影响 Amp 的行为，包括在内置的允许列表中运行命令。如果您经常处理不可信的源，建议考虑收紧您的 权限 或使用隔离的开发环境。

##### Toolboxes

工具箱允许你使用简单脚本来扩展 Amp，而无需提供 MCP 服务器。

当 Amp 启动时，它会调用由环境变量 `AMP_TOOLBOX` 指定的目录中的每个可执行文件，并将环境变量 `TOOLBOX_ACTION` 设置为 `describe` 。

该工具预期会将其描述输出到 `stdout` ，以键值对列表的形式，每行一个。

```javascript
#!/usr/bin/env bun

const action = process.env.TOOLBOX_ACTION

if (action === 'describe') showDescription()
else if (action === 'execute') runTests()

function showDescription() {
    process.stdout.write(
        [
            'name: run-tests',
            'description: use this tool instead of Bash to run tests in a workspace',
            'dir: string the workspace directory',
        ].join('\n'),
    )
}
```

当 Amp 决定使用您的工具时，它会再次运行可执行文件，设置 `TOOLBOX_ACTION` 为 `execute` 。

该工具以相同格式在 `stdin` 上接收参数，然后执行其工作：

```javascript
function runTests() {
    let dir = require('fs')
        .readFileSync(0, 'utf-8')
        .split('\n')
        .filter((line) => line.startsWith('dir: '))

    dir = dir.length > 0 ? dir[0].replace('dir: ', '') : '.'

    require('child_process').spawnSync('pnpm', ['-C', dir, 'run', 'test', '--no-color', '--run'], {
        stdio: 'inherit',
    })
}
```

如果您的工具需要对象或数组参数，可执行文件可以将其 [工具模式](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#tool) 以 JSON 格式写入到 `stdout` 。在这种情况下，它也会以 JSON 格式接收输入。

我们建议使用工具来表达特定的、确定性的和项目特定的行为，例如：

- 查询开发数据库
- 在项目中运行测试和构建操作
- 以受控方式公开 CLI 工具

See the 附录 for the full technical reference.

##### Agent Skills

技能是包含指令和资源的软件包，用于教导代理执行特定任务。Amp 包含内置技能，您可以安装或创建自己的技能——无论是项目特定的（`.agents/skills/` ）还是用户级别的（ `~/.config/agents/skills/` ）。

###### Creating Skills

Amp 拥有一个内置的 `building-skills` 技能，该技能可以创建针对您的代码库、工作流和系统定制的技能。要创建一个，只需询问：

```
Create a skill for deploying to staging
```

请求一个“项目特定技能”以将其保存到当前项目，或一个“用户全局技能”以在所有项目中供个人使用。项目技能存储在 `.agents/skills/` 中，并且可以提交到 Git，以便团队自动获取这些技能。

技能优先级（先到先得）：

- `~/.config/agents/skills/`
- `~/.config/amp/skills/`
- `.agents/skills/`
- `.claude/skills/`
- `~/.claude/skills/`
- 插件、工具箱目录和内置技能

###### Installing Skills

你可以在 GitHub、内部代码仓库或任何带有 Git URL 的地方查找和分享技能。要安装技能，请使用命令面板（在命令行界面中使用 `Ctrl+O` ，在 VS Code 中使用 `Cmd+Shift+P` ）：

- **技能：添加** — 从 GitHub、git URL 或本地路径安装
- **技能: 列表** — 查看已安装的技能
- **技能：移除** — 移除一项技能

你也可以从命令行使用 `amp skill` 来管理技能，例如从 [amp-contrib](https://github.com/ampcode/amp-contrib) 添加 tmux:

```
amp skill add ampcode/amp-contrib/tmux
```

###### Skill Format

每个技能是一个目录，包含一个 `SKILL.md` 文件，带有 YAML frontmatter：

```markdown
---
name: my-skill
description: A description of what this skill does
---

# My Skill Instructions

Detailed instructions for the agent...
```

The `name` 和 `description` 始终对模型可见，并决定模型何时调用该技能。名称必须唯一——项目特定技能优先于用户级技能，且两者均覆盖内置技能。 `SKILL.md` 的其余内容仅在调用技能时按需加载。

技能可以包含同一目录中的打包资源（脚本、模板等），代理可以相对于技能文件访问这些资源。

###### MCP Servers in Skills

技能可以通过在技能目录中包含一个 `mcp.json` 文件来捆绑 MCP 服务器。当 Amp 启动时，服务器会启动，但它们的工具会保持隐藏状态，直到技能加载完成。这是使用 MCP 服务器的推荐方式——与直接将服务器添加到 Amp 配置中相比，这种方式可以保持工具列表整洁并减少上下文膨胀。

**示例 `mcp.json` （本地命令式服务器）：**

```json
{
    "chrome-devtools": {
        "command": "npx",
        "args": ["-y", "chrome-devtools-mcp@latest"],
        "includeTools": ["navigate_*", "take_screenshot", "click", "fill*"]
    }
}
```

**示例 `mcp.json` (远程 HTTP 服务器):**

```json
{
    "linear": {
        "url": "https://mcp.linear.app/sse",
        "includeTools": ["list_issues", "create_issue", "update_issue"]
    }
}
```

**Fields for local servers:**

- `命令` (`字符串`) — 要运行的命令
- `args` (`string[]`, 可选的) — 命令参数
- `env` (`对象`, 可选) — 环境变量

**Fields for remote servers:**

- `url` (`string`) — 服务器端点
- `headers` (`对象`, 可选) — 发送请求时附带的 HTTP 头信息

**Common fields:**

- `includeTools` (`string[]` ，可选但推荐) — 工具名称或 glob 模式，用于筛选要暴露的工具

##### Subagents

Amp 可以通过任务工具生成子代理，以处理需要独立执行的复杂任务。每个子代理都有自己的上下文窗口，并可使用文件编辑和终端命令等工具。

子代理在多步骤任务（可分解为独立部分）、产生大量完成后不再需要的输出的操作、不同代码区域的并行工作，以及协调复杂工作时保持主线程上下文清晰等场景中最为有用。

然而，子代理孤立工作——他们无法相互沟通，你无法在任务进行中指导他们，他们在没有你对话积累的上下文的情况下从头开始，而主代理只收到他们的最终总结，而非监控他们的逐步工作。

Amp 可能会自动为合适的任务使用子代理，或者您可以通过提及子代理或建议并行工作来鼓励使用它们。

##### Oracle

Amp 拥有一个强大的“第二意见”模型，该模型更适合复杂推理或分析任务，但代价是比主代理模型稍微慢一些、稍微贵一些，并且不太适合日常代码编辑任务。

该模型可供 Amp 的主要代理商使用，通过一个名为 `Oracle` 的工具，并且目前使用 GPT-5.4，推理级别为高。

主代理在调试或审查复杂代码段时，可以自主决定向 oracle 寻求帮助。由于成本较高且推理速度较慢，我们有意不强制主代理 *始终* 使用 oracle。

我们建议当你认为这会有帮助时，明确要求 Amp 的主要代理使用 Oracle。以下是我们自己使用 Amp 的一些示例：

- 使用 Oracle 查看上次提交的更改。我需要确保当空闲或需要用户输入时播放通知声音的实际逻辑没有改变。
- 询问 Oracle 是否没有更好的解决方案。
- 我在这些文件中有一个错误：…… 当我运行这个命令时会出现：…… 帮我修复这个错误。尽可能多地使用 Oracle，因为它很智能。
- 分析函数 `foobar` 和 `barfoo` 的使用方式。然后我希望你大量使用 Oracle 来弄清楚如何重构它们之间的重复代码，同时确保修改向后兼容。

See GPT-5 Oracle 公告 for more information.

##### Code Review

Amp 可以检查您的代码是否存在错误、安全问题、性能问题和代码风格违规——在 CLI 中运行 `amp review` ，或者直接让主代理审查您的修改。

###### Checks

检查是用户定义的评审标准，限定于代码库的特定部分。它们使你能够将团队约定、安全不变量以及代码检查工具无法捕获的最佳实践编码为规则。在代码评审期间，Amp 会为每个检查生成一个单独的子代理。

创建 Markdown 文件在 `.agents/checks/` 目录中，使用 YAML 前置内容：

Field Required Description

`name` Yes Identifier for the check

`description` No 列出检查项时显示的简要说明

`severity-default` No 默认严重程度： `low` 、 `medium` 、 `high` 或 `critical`

`tools` No 检查子代理可以使用的工具名称数组

**Example** (`.agents/checks/perf.md`):

```markdown
---
name: performance
description: Flags common performance anti-patterns
severity-default: medium
tools: [Grep, Read]
---

Look for these patterns:

- Nested loops over the same collection (O(n²) → O(n) with a Set/Map)
- Repeated `array.includes()` in a loop
- Sorting inside a loop
- String concatenation in a loop (use array + join)

Report the line, why it matters, and how to fix it.
```

检查可以在项目和全局位置中定义：

- `.agents/checks/` — 适用于整个代码库
- `api/.agents/checks/` — 仅适用于 `api/ 下的文件`
- `$HOME/.config/amp/checks/` 或 `$HOME/.config/agents/checks/` — 应用于所有评审的全局检查

项目内的检查会覆盖来自父目录和全局检查的同名检查。

##### MCP

您可以使用 [MCP（模型上下文协议）](https://modelcontextprotocol.io) 服务器添加额外的工具，这些服务器可以是本地的或远程的。

对于大多数使用场景，我们建议 在技能中捆绑 MCP 服务器 通过 `mcp.json` 而不是将它们添加到用户设置中。这能保持工具列表整洁并仅在需要时加载 MCP 工具。

如果通过技能加载 MCP 不适用（如果它必须始终在上下文窗口中可用），请通过命令行界面或在您的 配置文件 中添加它：

```
$ amp mcp add context7 -- npx -y @upstash/context7-mcp
$ amp mcp add linear https://mcp.linear.app/sse
```

MCP 服务器使用与 技能中的 MCP 服务器 相同的配置字段—— `command` / `args` / `env` 用于本地服务器， `url` / `headers` 用于远程服务器。在配置文件中，设置 `amp.mcpServers` 并使用 `${VAR_NAME}` 语法表示环境变量：

```json
"amp.mcpServers": {
    "playwright": {
        "command": "npx",
        "args": ["-y", "@playwright/mcp@latest", "--headless"]
    },
    "linear": {
        "url": "https://mcp.linear.app/sse"
    },
    "sourcegraph": {
        "url": "${SRC_ENDPOINT}/.api/mcp/v1",
        "headers": { "Authorization": "token ${SRC_ACCESS_TOKEN}" }
    }
}
```

许多远程服务器通过 OAuth 自动处理认证。对于需要手动认证的服务器，请直接传递 headers 或使用 手动 OAuth 注册 。

当相同的 MCP 服务器名称出现在多个位置时，Amp 使用此优先级（从高到低）：

1. CLI flags (`--mcp-config`)
2. User/workspace config (`amp.mcpServers`)
3. 技能（仅在上方未配置时加载）

这意味着，如果需要的话，你可以用自己的配置覆盖技能提供的 MCP 服务器。

###### Workspace MCP Server Trust

MCP 服务器在工作区设置中（`.amp/settings.json` ）需要明确的批准才能运行。这防止了不可信的代码在你打开项目时自动执行。

当工作区 MCP 服务器正在等待审批时，您将在 `amp mcp doctor` 的输出中看到 `awaiting approval` 。要批准：

```
$ amp mcp approve my-server
```

在命令行界面中，当工作区服务器首次被检测到时，你会被提示批准。

在您的全局设置（ `~/.config/amp/settings.json` ）中或通过 `--mcp-config` 传递的 MCP 服务器不需要审批。

###### MCP Best Practices

过多可用的工具可能会降低模型性能，因此，为获得最佳效果，请有所选择：

- 将 MCP 服务器打包到技能中 ，而不是全局添加它们——工具会一直保持隐藏状态，直到技能加载。
- 使用暴露少量高级工具且带有高质量描述的 MCP 服务器。
- 禁用你未使用的 MCP 工具，或者考虑改用命令行工具。

###### OAuth for Remote MCP Servers

一些 MCP 服务器（如 [Linear](https://linear.app/changelog/2025-05-01-mcp) ）支持自动 OAuth 客户端注册。当你添加此类服务器时，Amp 会在启动时自动在浏览器中启动 OAuth 流程。

**手动 OAuth 客户端注册**

对于需要手动配置 OAuth 客户端的服务器：

1. 在服务器的管理界面中创建一个 OAuth 客户端，使用：
   - Redirect URI: `http://localhost:8976/oauth/callback`
   - 您的用例所需的范围
2. 将 MCP 服务器添加到你的配置中:

```
$ amp mcp add my-server https://example.com/.api/mcp/v1
```

1. 注册您的 OAuth 凭证：

```
$ amp mcp oauth login my-server \
  --server-url https://example.com/.api/mcp/v1 \
  --client-id your-client-id \
  --client-secret your-client-secret \
  --scopes "openid,profile,email,user:all"
```

启动时，Amp 将打开您的浏览器以完成认证流程。

OAuth 令牌安全地存储在 `~/.amp/oauth/` 中，并且在需要时自动刷新。

如果服务提供方令牌过期或被撤销，清除存储的 OAuth 凭证并让 Amp 下次启动时重新验证身份

```
$ amp mcp oauth logout my-server
```

##### Permissions

调用工具之前，Amp 会检查用户的权限列表中第一个匹配的条目，以决定是否运行该工具。

如果没有找到匹配项，Amp 会扫描其内置的权限列表，如果在该列表中也未找到匹配项，则拒绝该工具的使用。

匹配的条目告诉 Amp 要么允许工具使用而无需询问，要么直接拒绝工具使用，要么询问操作员，要么将决策委托给另一个程序。

对于新的权限自定义，优先使用 插件 API 。我们预计插件将很快取代 Amp 的内置权限系统，并且我们计划发布一个兼容插件，以执行当前 `amp.permissions` 格式中编写的规则。

权限在您的 配置文件 中的 `amp.permissions` 条目下进行配置：

```json
"amp.permissions": [
  // Ask before running command line containing git commit
  { "tool": "Bash", "matches": { "cmd": "*git commit*" }, "action": "ask"},
  // Reject command line containing python or python3
  { "tool": "Bash", "matches": { "cmd": ["*python *", "*python3 *"] }, "action": "reject"},
  // Allow all playwright MCP tools
  { "tool": "mcp__playwright_*", "action": "allow"},
  // Ask before running any other MCP tool
  { "tool": "mcp__*", "action": "ask"},
  // Delegate everything else to a permission helper (must be on $PATH)
  { "tool": "*", "action": "delegate", "to": "my-permission-helper"}
]
```

###### Using Permissions in the CLI

使用 `amp permissions edit` ，你可以通过编程方式和交互方式编辑你的权限规则，使用 `$EDITOR` 。

该 `amp permissions test` 命令评估权限规则，而不实际运行任何工具，从而提供了一种安全的方式来验证你的规则是否按预期工作。

```
$ amp permissions edit <<'EOF'
allow Bash --cmd 'git status' --cmd 'git diff*'
ask Bash --cmd '*'
EOF
$ amp permission test Bash --cmd 'git diff --name-only'
tool: Bash
arguments: {"cmd":"git diff --name-only"}
action: allow
matched-rule: 0
source: user
$ amp permission test Bash --cmd 'git push'
tool: Bash
arguments: {"cmd":"push"}
action: ask
matched-rule: 1
source: user
```

执行 `amp permissions list` 会以 `amp permissions edit` 所理解的相同格式显示已知的权限规则：

```
$ amp permissions list
allow Bash --cmd 'git status' --cmd 'git diff*'
ask Bash --cmd '*'
```

请参考 `amp permissions --help` 的输出，以获取所有可用操作的完整列表。

###### 将权限决策委托给外部程序

如需完全控制，你可以让 Amp 在调用工具之前先调用另一个程序：

```json
{ "action": "delegate", "to": "amp-permission-helper", "tool": "Bash" }
```

现在每次 Amp 想要运行 shell 命令时，它都会调用 `amp-permission-helper` ：

```python
#!/usr/bin/env python3
import json, sys, os

tool_name = os.environ.get("AGENT_TOOL_NAME")
tool_arguments = json.loads(sys.stdin.read())

# allow all other tools
if tool_name != "Bash":
    sys.exit(0)

# reject git push outright - stderr is passed to the model
if 'git push' in tool_arguments.get('cmd', ''):
    print("Output the correct command line for pushing changes instead", file=sys.stderr)
    sys.exit(2)

# ask in any other case
sys.exit(1)
```

错误代码和 stderr 用于告知 Amp 如何继续。

#### CLI

安装 并登录后，运行 `amp` 以启动 Amp CLI。

不带任何参数时，它将以交互模式运行：

```
$ amp
```

如果您将输入通过管道传递给 CLI，它会在交互模式中将该输入用作第一条用户消息：

```
$ echo "commit all my changes" | amp
```

使用 `-x` 或 `--execute` 来启动 CLI 进入执行模式。在此模式下，它会向代理发送提供给 `-x` 的消息，等待代理完成其回合，打印其最终消息，然后退出：

```
$ amp -x "what files in this folder are markdown files? Print only the filenames."
README.md
AGENTS.md
```

(Note: 执行模式 (`amp -x`) 仅消耗付费积分，不消耗 广告支持的免费套餐 积分，因为我们不能在程序化或非交互场景中展示广告。)

你也可以在使用 `-x` 时进行管道输入：

```
$ echo "what package manager is used here?" | amp -x
cargo
```

如果你想在使用可能需要审批的工具的代理中使用 `-x` ，请确保要么使用 `--dangerously-allow-all` ，要么 配置 Amp 以允许它们 ：

```
$ amp --dangerously-allow-all -x "Run `sed` to replace 2024 with 2025 in README."
Done. Replaced 8 occurrences of 2024 in README.md
```

当你重定向 stdout 时，执行模式会自动开启：

```
$ echo "what is 2+2?" | amp > response.txt
```

当你管道输入并提供一个带有 `-x` 的提示时，代理可以看到两者：

````
$ cat ~/.vimrc | amp -x "which colorscheme is used?"
The colorscheme used is **gruvbox** with dark background and hard contrast.

```vim
set background=dark
let g:gruvbox_contrast_dark = "hard"
colorscheme gruvbox
```
````

您可以使用 `--mcp-config` 标志与 `-x` 命令一起，来指定一个 MCP 服务器而无需修改您的配置文件。

```
$ amp --mcp-config '{"everything": {"command": "npx", "args": ["-y", "@modelcontextprotocol/server-everything"]}}' -x "What tools are available to you?"
```

##### Shell Mode

##### Streaming JSON

Amp 的命令行界面支持流式 JSON 输出格式，每一行一个对象，输出到标准输出，用于程序化集成和实时对话监控。

使用带有 `--execute` 模式的 `--stream-json` 标志以流式 JSON 格式而非纯文本输出。如果您希望在 JSON 输出中包含助手思考块，请添加 `--stream-json-thinking` （这会扩展模式且与 Claude Code 不兼容）。

Basic usage with argument:

```
$ amp --execute "what is 3 + 5?" --stream-json
```

结合 —stream-json 与 `amp threads continue`

```
$ amp threads continue --execute "now add 8 to that" --stream-json
```

With stdin input:

```
$ echo "analyze this code" | amp --execute --stream-json
```

您可以在附录中找到 JSON 输出的模式

输入也可以通过标准输入使用 `--stream-json-input` 标志提供。每行标准输入都是一个完整的 JSON 对象。例如，你可以使用 `jq -c` 将文本加图像消息作为单行发出：

```
$ jq -c . <<'EOF' | amp -x --stream-json --stream-json-input
{
  "type": "user",
  "message": {
    "role": "user",
    "content": [
      {
        "type": "text",
        "text": "what do you see?"
      },
      {
        "type": "image",
        "source_path": "file:///Users/alice/images/example.jpg",
        "source": {
          "type": "base64",
          "media_type": "image/jpeg",
          "data": "..."
        }
      }
    ]
  }
}
EOF
```

标志 `--stream-json` 需要 `--execute` 模式。它不能独立使用。 `--stream-json-input` 需要 `--stream-json` ，而 `--stream-json-thinking` 隐含 `--stream-json` 。

使用 `--stream-json-input` 时， `--execute` 的行为会发生改变，即 Amp 只有在助手完成且标准输入已关闭时才会退出。

这允许程序化使用 Amp CLI 与多条用户消息进行对话。

```bash
#!/usr/bin/env bash

send_message() {
  local text="$1"
  echo '{"type":"user","message":{"role":"user","content":[{"type":"text","text":"'$text'"}]}}'
}

{
  send_message "what's 2+2?"
  sleep 10

  send_message "now add 8 to that"
  sleep 10

  send_message "now add 5 to that"
} | amp --execute --stream-json --stream-json-input
```

请参阅 附录 以了解输出结构、示例输出及更多使用示例。

  **Type:**`number`, **Default:**`300`

- **`amp.mcpPermissions`**
  **Type:**`array`, **Default:**`[]`
  允许或阻止匹配指定模式的 MCP 服务器。第一个匹配的规则将被应用。如果没有规则匹配某个 MCP 服务器，该服务器将被允许。
  - **远程 MCP 服务器** ：使用 `url` 键指定服务器端点的匹配条件
  - **本地 MCP 服务器** ：使用 `command` 和 `args` 键以匹配一个可执行命令及其参数
  Here are some examples:
  ```json
  "amp.mcpPermissions": [
    // Allow specific trusted MCP servers
    { "matches": { "command": "npx", "args": "* @playwright/mcp@*" }, "action": "allow" },

  ]
  ```
  以下规则将阻止所有 MCP 服务器：
  ```json
  "amp.mcpPermissions": [
    { "matches": { "command": "*" }, "action": "reject" },
    { "matches": { "url": "*" }, "action": "reject" }
  ]
  ```
- **`amp.agent.deepReasoningEffort`**
  **类型:**`string`, **默认:**`"high"`, **选项:**`"medium"` \| `"high"` \| `"xhigh"`
  新的深度模式线程的默认推理强度。在 CLI 中，Alt+D 更新此设置。
- **`amp.updates.mode`**
  **Type:**`string`, **Default:**`"auto"`
  控制更新检查行为： `"warn"` 显示更新通知， `"disabled"` 关闭检查， `"auto"` 自动运行更新。注意：设置环境变量 `AMP_SKIP_UPDATE_CHECK=1` 将覆盖此设置并禁用所有更新检查。
- **`amp.windowsPasteHook.enabled`**
  **Type:**`boolean`, **Default:**`true`
  启用 Windows `Ctrl+V` 剪贴板钩子集成，以在 CLI 中实现可靠的文本和图像粘贴。如果禁用，Amp 将回退到终端原生的粘贴行为和命令面板剪贴板操作。环境变量覆盖： `AMP_WIN_PASTE_HOOK_ENABLED` （开/关覆盖）和 `AMP_WIN_PASTE_HOOK_PATH` （二进制文件路径覆盖）。

#### Amp 使用手册总结

##### 一、Amp 是什么

Amp 是一个面向终端和编辑器的 AI 编码代理，核心目标是帮开发者更高效地写代码、改代码、查问题、做研究。  
它强调三点：**多模型协同、只保留最好用的能力、持续跟随前沿模型演进**。

##### 二、Amp 的核心价值

Amp 提供 3 种主要模式，适配不同任务：

- **smart**：最强能力，适合复杂开发任务
- **rush**：更快更便宜，适合小任务和明确任务
- **deep**：更强推理能力，适合复杂分析和深度思考

简单说，Amp 不是单一模型工具，而是一个会根据任务调用不同能力的 “智能开发助手”。

##### 三、如何开始使用

使用方式很直接：

- 先在官网安装`Amp CLI`
- 可在命令行中直接运行
- 也支持连接主流 IDE，如**JetBrains、VS Code、Neovim、Zed**

这意味着 Amp 不要求你切换工作流，而是嵌入你已有的开发环境中。

##### 四、如何更有效地提问

Amp 的效果很大程度取决于提示词质量，原则很明确：

- **说清楚目标**，不要模糊表达
- **任务拆小**，一个线程只做一件事
- **补充上下文**，例如相关文件、命令、实现思路
- **明确限制**，比如 “只做规划，不写代码”
- **告诉它如何验证结果**，比如跑哪些测试、看哪个页面

本质上，Amp 更像一个高能力同事：你给的任务越清晰，它完成得越好。

##### 五、线程机制：把 AI 协作流程化

Amp 非常强调**Threads（线程）**，你可以保存、分享、引用历史对话。  
这相当于把 AI 协作从 “一次性聊天” 升级为 “可追踪、可交接、可复用” 的工作流。

几个关键能力：

- **handoff**：把一个任务平滑交接到新线程
- **引用历史线程**：复用之前的方案或修复逻辑
- **搜索历史线程**：按关键词、文件、作者、日期查找
- **归档线程**：清理活跃列表，但保留可追溯性

对团队协作来说，这能显著减少重复沟通和重复试错。

##### 六、AGENTS.md：给 Amp 写 “工作说明书”

`AGENTS.md`是 Amp 的关键机制之一，可以理解为给 AI 的项目操作手册。  
它主要告诉 Amp：

- 项目结构是什么
- 构建和测试命令是什么
- 编码规范和注意事项是什么
- 不同子项目需要遵守什么特殊规则

如果项目复杂，还可以通过不同目录下的`AGENTS.md`做更细粒度的约束。  
价值在于：**把团队经验沉淀成可重复调用的 AI 上下文**。

##### 七、扩展能力：工具、技能、MCP

Amp 不只是聊天和改代码，它还能通过多种方式扩展能力：

###### 1. 工具箱（Toolboxes）
可以用简单脚本给 Amp 增加项目专属能力，例如统一跑测试、查数据库、调用内部工具。

###### 2. 技能（Skills）
把某类任务封装成能力包，比如 “部署到测试环境”“生成特定格式文档”。  
适合沉淀团队固定流程。

###### 3. MCP 服务器
通过模型上下文协议接入更多外部工具和服务。  
适合连接 GitHub、Linear、浏览器工具、内部服务等。

一句话概括：Amp 不只是 “会写代码”，而是在往 “可编排的开发代理平台” 演进。

##### 八、一些高级能力

Amp 还提供了一些更强的辅助能力：

- **Subagents**：把复杂任务拆给多个子代理并行处理
- **Oracle**：调用更强推理模型做复杂分析、调试和审查
- **Librarian**：跨 GitHub 或私有仓库做代码研究
- **Painter**：生成或编辑图片，用于 UI 原型、图标、截图处理
- **Code Review**：对代码做缺陷、安全、性能和规范检查

这说明 Amp 的定位已经超出 “代码补全”，更接近一个多角色 AI 工程系统。

##### 九、使用中的关键原则

手册反复强调几个实践原则：

- 保持任务短、专注、单线程
- 上下文脏了就开新线程
- 尽量告诉 Amp 如何检查结果
- 对工具权限保持警惕，尤其是面对不可信代码库时
- 少而精地配置工具，避免让模型上下文过载

这背后的思路很产品化：**不是让 AI 无限制发挥，而是用合适的结构提升稳定性和可控性**。

##### 十、核心结论

Amp 的本质不是一个 “AI 编程插件”，而是一个围绕开发工作流设计的**智能代理系统**。  
它的重点不只在 “生成代码”，而在于：

- 把 AI 使用过程结构化
- 把团队知识沉淀成可复用规则
- 把多模型、多工具、多线程协作整合进开发流程

如果说普通 AI 编码工具解决的是 “写得更快”，那 Amp 想解决的是：**如何让 AI 更系统地参与真实的软件开发工作。**

Amp 是一个面向终端和编辑器的智能编码代理，核心特点是 “多模型协作 + 线程化工作流 + 可扩展工具体系”。这篇手册主要讲清楚：如何安装和使用 Amp、怎样高效提问，以及如何通过`AGENTS.md`、技能、MCP、子代理等机制把它真正用进日常开发中。

##### 1. Amp 是什么，为什么值得用

- Amp 是一个运行在终端和编辑器里的编码代理，定位是 “前沿编码助手”。
- 它支持多种模型协同工作，包括**Opus 4.6、GPT-5.4 和更快的轻量模型**，会根据任务选择各自擅长的能力。
- 产品理念很明确：
  - **主观取舍**：只保留团队自己认可、常用的功能。
  - **追随前沿**：不强调向后兼容，不背历史包袱。
  - **线程化工作**：支持保存、分享交互记录，类似给 AI 工作流加上 “版本管理”。

**关键模式：**
- `smart`：最强能力、限制最少，适合复杂开发任务。
- `rush`：更快、更便宜，适合小而明确的问题。
- `deep`：用于复杂问题的深度推理和扩展思考。
- 文中还提到一个隐藏模式：`large`。

##### 2. 如何开始使用

###### 安装方式

- 官方安装入口：`ampcode.com/install`
- 推荐在**macOS、Linux、WSL**中用 CLI 安装，因为支持：
  - 通过**Bun 自动更新**
  - 更快启动

**CLI 安装命令：**
```bash
curl -fsSL https://ampcode.com/install.sh | bash
```

**首次交互运行：**
```bash
amp
```

- 如果需要，也可以通过`npm`安装。

###### IDE 集成

Amp 可以接入多种开发环境：

- **JetBrains**（IntelliJ、WebStorm、GoLand 等）：
  - 安装 CLI 后执行`amp --jetbrains`
- **Neovim**：
  - 安装 CLI 和 Amp Neovim 插件，再运行`amp`
- **VS Code / Cursor / Windsurf 等**：
  - 安装 CLI，打开编辑器后运行`amp`
- **Zed**：
  - 安装 CLI，打开 Zed 后运行`amp`

**连接 IDE 的方法：**
- 打开命令面板`Ctrl+O`
- 选择`ide connect`

##### 3. 三种模式怎么选

Amp 把不同任务分给不同模式处理：

###### `smart`
- 使用最先进模型，强调最大能力和自主性。
- 当前说明中提到，`smart`模式使用**Claude Opus 4.6**，并支持**最多 300k 输入上下文 token**。

###### `rush`
- 更快、更便宜，但能力较弱。
- 更适合：
  - 小任务
  - 定义清晰的工作
  - 不需要复杂推理的修改

###### `deep`
- 适合复杂问题。
- 结合**GPT-5.4**做更深入的推理和分析。

**切换方式：**
- 在命令面板`Ctrl+O`中输入`mode`

##### 4. 如何给 Amp 提示，效果最好

这是全文最重要的一部分之一。官方建议很明确：**提示要明确、短小、聚焦。**

###### 高效提示的核心原则

- **直接说目标**  
  不要问 “你能不能做 X”，而要直接说 “做 X”。

- **任务要聚焦**  
  大任务拆成多个小任务，一个线程只做一件事。  
  例如，不要在同一线程里一边改数据库迁移，一边改文档页 CSS。

- **不要让模型猜**
  如果你知道：
  - 要看哪些文件
  - 要跑哪些命令
  - 应该检查什么  
  就直接写在提示里。

- **只研究不写代码时要明确说明**
  例如：
  - “只规划如何实现，不要写任何代码。”

- **告诉它如何验证结果**
  比如：
  - 跑什么测试
  - 打开什么 URL
  - 看哪些日志

- **线程太吵就重开**
  如果失败日志、错误信息过多，占满上下文窗口，通常重新开一个新线程更有效。

- **第一条提示最关键**
  因为它会决定后续整个线程的方向。

###### 文中给出的典型提示案例

手册里给了很多实际例子，说明 Amp 不只是能 “写代码”，还能 “读代码、查历史、分析 diff、规划重构、做 UI 调整”。

例如：

- 修改函数返回类型并同步更新测试  
  例子里提到把`observeThreadGuidanceFiles`改为返回  
  `Omit&lt;ResolvedGuidanceFile, 'content'>[]`，并说明这样做是为了**减少通过视图 API 传输的数据量**。

- 运行构建并修复错误  
  - “运行`&lt;build command>`并修复所有错误”

- 打开本地页面并优化 UI  
  - “查看`&lt;local development server url>`，让组件更简洁，并经常通过截图 URL 检查效果”

- 用`git blame`找出谁加了某个标题

- 把**5 个文件**转成 Tailwind，并让**每个文件用一个子代理处理**

- 查看`git diff --staged`，移除调试语句

- 用`git log`找到相关提交，再修改对应功能

- 运行`psql`，把数据库中所有`threads`重新分配给某个邮箱前缀为`thorsten`的用户

这些例子说明：Amp 的最佳用法是让它接管 “明确、可执行、有验证路径” 的开发任务。

##### 5. `AGENTS.md`：让 Amp 理解你的项目

`AGENTS.md`是 Amp 的一个核心机制，相当于给代理写 “项目说明书”。

###### 它能放什么内容

- 代码结构说明
- 构建 / 测试命令
- 内部 API 概览
- 审查 / 发布流程
- 个人偏好
- 本地设备上的特殊命令

###### Amp 会自动读取哪些文件

它会自动包含以下位置的说明文件：

- 当前工作目录中的`AGENTS.md`
- 父目录中的`AGENTS.md`（一直向上找到`$HOME`）
- 子树中的`AGENTS.md`（当代理读取该子树里的文件时）
- 如果存在：
  - `$HOME/.config/amp/AGENTS.md`
  - `$HOME/.config/AGENTS.md`

如果没有`AGENTS.md`，但有以下文件，也会读：
- `AGENT.md`
- `CLAUDE.md`

###### 大仓库怎么组织

官方建议：
- 顶层`AGENTS.md`写通用规则
- 各子项目在各自子目录再写更具体的`AGENTS.md`

###### 如何查看 Amp 当前用了哪些代理说明文件

- 在命令面板里运行：`agents-md list`

##### 6. 如何编写更细粒度的`AGENTS.md`

Amp 支持通过`@`引用其他文档，把更多上下文拉进来。

###### 基本写法

例如在`AGENTS.md`里写：

```md
See @doc/style.md and @specs/**/*.md.
When making commits, see @doc/git-commit-instructions.md.
```

含义是：
- 引入样式文档
- 引入规范文档
- 提交代码时参考提交规范

###### 支持的能力

- 相对路径
- 绝对路径
- `@~/some/path`
- glob 通配符，如：
  - `@doc/*.md`
  - `@.agent/**/*.md`

###### 按文件类型或目录精细生效

可以在被引用文件里写 YAML frontmatter，用`globs`限定在什么情况下生效。

例如 TypeScript 规则：

```md
---
globs:
  - '**/*.ts'
  - '**/*.tsx'
---
Follow these TypeScript conventions:
- Never use the `any` type
```

意思是：
- 只有当 Amp 已经读取过`.ts`或`.tsx`文件时，这份规则才会被自动纳入上下文。

文中还给了其他例子：

- 前端规则：
  - `globs: ["src/components/**","**/*.tsx"]`
- 后端规则：
  - `globs: ["server/**","api/**"]`
- 测试规则：
  - `globs: ["*.test.ts","__tests__/*"]`

###### 从其他规则体系迁移

手册也给了迁移建议：

- 从`CLAUDE.md`迁移：
```bash
mv CLAUDE.md AGENTS.md && ln -s AGENTS.md CLAUDE.md
```

- 从 Cursor 的`.cursorrules`迁移：
```bash
mv .cursorrules AGENTS.md && ln -s AGENTS.md .cursorrules
```

并可在`AGENTS.md`中加入：
```md
@.cursor/rules/*.mdc
```

##### 7. 线程、交接与复用历史上下文

Amp 非常强调 “线程化工作”。

###### Handoff：把一个线程的工作交给新线程

如果一个线程做得太长、太杂，可以用`handoff`开新线程，并带上相关上下文。

适合的交接提示包括：

- “现在把这个功能也支持 teams，不只是 individual users”
- “执行已创建计划的第一阶段”
- “检查代码库其他地方还有没有同类问题”

###### 引用其他线程

你可以在提示里引用历史线程：

- 用 URL
- 用线程 ID，如：
  - `@T-7f395a45-7fae-4983-8de0-d02e61d30183`

输入`@@`可以搜索线程。

Amp 会读取被引用线程里的相关信息，用于当前任务。

###### 查找线程

可以按以下条件搜索：

- 关键词
- 文件路径
- 仓库
- 作者
- 日期
- 任务编号

例如：
- 查找讨论 monorepo 迁移的线程
- 找出改过`src/server/index.ts`的线程
- 找到某人关于 indexing logic 的线程
- 查过去一周自己的线程
- 找处理 task 142 的线程

###### 归档线程

归档后：
- 不再出现在活跃列表
- 但网页仍可查看
- 仍能被`@`引用

命令：
- `thread: archive and exit`

##### 9. 工具与权限：Amp 能做什么、哪些要确认

Amp 可以代表你运行工具和 shell 命令，比如：

- 检查代码
- 跑测试
- 构建项目
- 加速迭代

###### 内置权限规则

Amp 内置了很多常见开发命令的免确认执行规则，比如：

- `ls`
- `git status`
- `npm test`
- `cargo build`

这些一般**无需提示确认**。

但对于敏感或破坏性命令，如：
- `git push`
- `rm -rf`

则会先确认。

###### 查看默认允许规则

```bash
amp permissions list --builtin
```

###### 风险提醒

官方特别提醒：
- Amp 会对工作区内容进行操作
- 不可信代码库、MCP 服务器、外部输入都可能影响代理行为

所以如果你经常处理不可信来源，建议：
- 收紧权限
- 或使用隔离开发环境

##### 10. Toolboxes：用脚本给 Amp 增加工具

Toolbox 是一种轻量扩展方式，不必专门搭 MCP 服务器。

###### 工作方式

- Amp 启动时，会调用`AMP_TOOLBOX`指定目录中的每个可执行文件
- 环境变量`TOOLBOX_ACTION=describe`时，脚本要输出自己的描述
- 真正执行时，`TOOLBOX_ACTION=execute`

###### 适合用来做什么

官方建议 Toolbox 用于一些：
- **确定性强**
- **项目特定**
- **边界清晰**

的动作，比如：

- 查询开发数据库
- 运行项目里的测试和构建
- 以受控方式暴露 CLI 工具

简单理解：如果你的团队总是要执行一类固定操作，把它封成工具会比让模型自由拼 shell 命令更稳定。

##### 11. Skills：给代理打包 “能力模块”

Skill 可以理解为 “可复用的任务包” 或 “能力插件”。

###### 它是什么

一个 Skill 是包含：
- 指令
- 资源
- 脚本
- 模板

的目录，用来教代理做特定事情。

Amp 自带内置技能，也支持你创建自己的技能。

###### 存放位置

- 项目级：`.agents/skills/`
- 用户级：`~/.config/agents/skills/`

###### 如何创建技能

Amp 内置了一个`building-skills`技能，你可以直接说：

- “Create a skill for deploying to staging”

然后选择：
- 项目特定技能
- 用户全局技能

###### 技能优先级

文中给出的优先级是 “先到先得”，顺序包括：

- `~/.config/agents/skills/`
- `~/.config/amp/skills/`
- `.agents/skills/`
- `.claude/skills/`
- `~/.claude/skills/`
- 插件、工具箱目录和内置技能

###### 安装技能

可从 GitHub、内部仓库或任意 Git URL 安装。

常见命令：
- `技能：添加`
- `技能：列表`
- `技能：移除`

CLI 例子：
```bash
amp skill add ampcode/amp-contrib/tmux
```

###### Skill 文件格式

每个技能目录里要有`SKILL.md`，包含 YAML frontmatter：

```md
---
name: my-skill
description: A description of what this skill does
---
```

其中：
- `name`
- `description`

始终对模型可见，并决定模型什么时候调用这个技能。

##### 12. Skill + MCP：按需加载高级工具

手册建议：如果要用 MCP 服务器，**最好把它打包进 Skill 里**，而不是直接全局配置。

###### 为什么这么做

因为这样可以：
- 保持工具列表整洁
- 减少上下文膨胀
- 只有在技能被加载时才暴露工具

###### `mcp.json`支持两类服务器

###### 本地命令式服务器
示例中用`npx`启动`chrome-devtools-mcp`，并只暴露少量工具，如：
- `navigate_*`
- `take_screenshot`
- `click`
- `fill*`

###### 远程 HTTP 服务器
例如：
- `https://mcp.linear.app/sse`

并限制只暴露：
- `list_issues`
- `create_issue`
- `update_issue`

###### 核心字段

本地服务器：
- `command`
- `args`
- `env`

远程服务器：
- `url`
- `headers`

通用字段：
- `includeTools`

##### 13. 子代理、Oracle、Librarian、Painter：Amp 的高级能力

###### 子代理（Subagents）

适合：
- 多步骤但可拆解的复杂任务
- 需要并行处理不同代码区域
- 大量中间输出不适合塞满主线程上下文的工作

优点：
- 有独立上下文窗口
- 能并行工作

限制：
- 子代理之间不能互相沟通
- 用户不能中途直接指导每个子代理
- 主代理只看到最终总结，不会实时看到过程

###### Oracle：第二意见模型

Oracle 是一个更强的 “分析 / 推理” 模型，当前使用：
- **GPT-5.4**
- **高推理级别**

特点：
- 更适合复杂推理和分析
- 比主代理更慢、成本更高
- 不适合日常大量代码编辑

官方建议在以下场景明确要求使用 Oracle：
- 检查最近一次提交的逻辑有没有变化
- 判断是否存在更优方案
- 分析复杂错误
- 重构重复代码并确保兼容性

###### Librarian：跨仓库搜索和读代码

Librarian 是一个专门用来搜索远程代码仓库的子代理。

支持：
- GitHub 上所有公开代码
- 你的私有 GitHub 仓库
- Bitbucket Enterprise

适合：
- 跨仓库研究问题
- 阅读框架或依赖库源码
- 调查 API 是否近期变更

例如：
- 调查文档发布后如何部署到`X.Y.sourcegraph.com`
- 研究 Zod 某个报错的内部原因
- 检查某个服务 API 端点近期是否改动、何时合并

###### Painter：图像生成与编辑

Painter 由**Gemini 3 Pro Image**驱动。

可用于：
- 生成 UI 原型
- 生成应用图标
- 制作主视觉图
- 对截图做编辑，比如打码敏感信息

支持：
- 在提示里`@`最多引用**3 张参考图片**，用于风格指导或编辑

##### 14. Code Review 和 Checks：让审查更制度化

###### Code Review

可以直接运行：

```bash
amp review
```

或者让主代理审查改动。

它会检查：
- 错误
- 安全问题
- 性能问题
- 风格问题

###### Checks：把团队规则写成审查规则

Checks 是用户定义的代码审查标准，用于补充静态检查工具捕捉不到的团队约定或安全不变量。

###### 存放位置

- `.agents/checks/`：整个代码库
- `api/.agents/checks/`：只针对`api/`下文件
- `$HOME/.config/amp/checks/`
- `$HOME/.config/agents/checks/`：全局适用

###### 示例规则

文中给了一个性能检查示例：

```md
---
name: performance
description: Flags common performance anti-patterns
severity-default: medium
tools: [Grep, Read]
---
```

检查内容包括：

- 对同一集合做嵌套循环，可能导致**O (n²)**，建议改成`Set/Map`
- 在循环里反复`array.includes ()`
- 在循环里排序
- 在循环里字符串拼接，建议用数组 + `join`

这类规则的价值是：把团队经验系统化，不靠人记忆。

##### 15. MCP：给 Amp 接更多外部工具

MCP（模型上下文协议）允许 Amp 使用本地或远程服务器提供的工具。

###### 添加方式

CLI 示例：

```bash
amp mcp add context7 -- npx -y @upstash/context7-mcp
amp mcp add linear https://mcp.linear.app/sse
```

也可在配置文件里用`amp.mcpServers`配置。

###### 配置示例

文中给了 3 个示例：
- `playwright`：本地命令式服务器
- `linear`：远程服务
- `sourcegraph`：带`Authorization`头的远程服务

并支持`${VAR_NAME}`形式引用环境变量。

###### 加载优先级

同名 MCP 服务器如果在多个位置定义，优先级从高到低是：

1. CLI flags（`--mcp-config`）
2. 用户 / 工作区配置（`amp.mcpServers`）
3. 技能里带的 MCP

这意味着：你可以用自己的配置覆盖技能里的默认配置。

###### 工作区 MCP 的安全审批

如果 MCP 服务器是在工作区设置`.amp/settings.json`中配置的，需要明确批准后才会运行，防止不可信项目自动执行外部工具。

查看状态：
```bash
amp mcp doctor
```

批准：
```bash
amp mcp approve my-server
```

###### 最佳实践

官方建议：
- 尽量把 MCP 打包到 Skill 里
- 工具不要太多
- 尽量暴露少量高价值、高层级工具
- 不用的 MCP 工具就禁用

##### 16. OAuth 与远程 MCP 认证

某些远程 MCP 服务（如 Linear）支持自动 OAuth 注册，Amp 会在启动时自动拉起浏览器完成认证。

如果服务需要手动注册 OAuth 客户端：
