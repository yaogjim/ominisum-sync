## 分析要点

- **核心高价值点**：将生产环境中的追踪、反馈和失败案例持续转化为评估数据集，形成代理迭代闭环。
- **留存建议**：长期保留（文章系统梳理了代理从构建、测试、部署、监控到治理的完整生命周期，可作为AI Agent工程化实践的参考框架。）

**知识要点**

- 代理开发生命周期可拆分为构建、测试、部署、监控四个核心环节，并通过迭代形成闭环。
- 代理测试不应等到上线后才开始，应在部署前建立代表性任务数据集、指标和实验流程。
- 生产级代理通常需要持久化执行、人在回路、沙箱环境、上下文中心和可观测追踪能力。
- 监控代理不仅要看延迟、成本和错误率，还要跟踪工具调用、任务完成质量、策略遵循和用户反馈。
- 当组织内存在多个代理时，需要治理成本、工具访问、审计轨迹、复用资产和发现机制。

**行动项**

- 为当前或计划中的AI Agent项目绘制构建、测试、部署、监控四阶段清单。
- 建立一组代表性任务和边界案例，作为代理版本迭代的基础评估集。
- 为生产代理接入完整追踪、用户反馈、成本监控和工具调用审计。
- 梳理哪些工具调用需要人在回路审批，尤其是涉及客户、资金、敏感数据和生产系统的操作。
- 将提示词、技能、检索上下文和工具配置进行版本化管理，便于复用和治理。

## 正文

**Harrison Chase**

### 代理开发生命周期

每个人都想要发布代理。

最优秀的组织已经弄清楚如何反复、安全且系统地做到这一点。他们尽早发布，从实际使用中学习，并快速迭代。他们不将代理视为一次性的演示或孤立的项目。

相反，他们构建了一个代理开发生命周期，通过将实验转化为一个可重复的系统，用于随时间持续交付、学习和改进，从而创造动力。

该生命周期包含四个部分：

构建 → 测试 → 部署 → 监控

![Image](https://pbs.twimg.com/media/HH5Hlrxb0AAgSeJ?format=jpg&name=large)

这个命令是有意为之的。测试应该在代理进入生产环境之前开始，而不是之后。团队需要在部署前测试代理，以受控方式部署它们，监控它们在生产环境中的表现，并将这些经验反馈到下一个构建和评估周期中。

对于单个代理，这个过程可以保持轻量级。当涉及多个代理时，这就变成了基础设施和治理方面的挑战。团队需要共享的方式来控制成本、管理工具访问、检查工具调用、重用上下文，并决定在何处需要人类参与。

让代理单次工作与将构建代理作为一种可重复实践之间的区别，源于拥有正确的开发生命周期。

#### 构建

构建阶段是团队决定他们正在创建什么样的代理系统以及他们想要使用的抽象级别。

这里有各种各样的工具。有些工具是代码优先的，而其他工具则是无代码或低代码的。有些专注于抽象化，而其他工具则专注于为代理提供一个包含提示词、工具、技能和状态的工作环境。

![Image](https://pbs.twimg.com/media/HH5Hojja8AAE3w9?format=jpg&name=large)

在代码优先的视角下，团队通常会采用开源框架和工具。在 LangChain 生态系统中，这些包括

[LangChain](https://www.langchain.com/langchain)，

[LangGraph](https://www.langchain.com/langgraph)

，以及

[Deep Agents](https://www.langchain.com/deep-agents)

。在 LangChain 之外，例子包括 CrewAI 和 Claude Agents SDK。

这些工具在栈的不同层次运作。

代理框架主要关注抽象概念。它们帮助开发者组合模型调用、工具、提示词、检索、结构化输出和代理循环。LangChain 和 CrewAI 是该类别的示例。

代理运行时专注于执行。它们支持需要状态、控制流、持久性和人工干预的代理。LangGraph 是 LangChain 生态系统中最清晰的示例。它为你提供了一种构建能够分支、循环、暂停、恢复并随时间持久化状态的代理系统的方法。

智能体驾驭专注于执行。它们提供智能体执行长期运行任务所需的周边结构：提示词、技能、MCP 服务器、钩子、中间件，有时还包括文件系统。深度智能体和 Claude 智能体 SDK 是这种模式的示例。

这些区别很重要，因为“构建代理”可以有不同的含义。

对于简单应用，它可能只涉及定义工具调用循环。对于更复杂的智能体，它可能涉及编写提示词、定义技能、连接 MCP 服务器、配置中间件，以及设置智能体随时间可以检索或更新的上下文。

无代码构建

构建阶段中也存在无代码和低代码的部分。像 LangSmith Fleet、Claude Cowork 和 n8n 这样的工具让更多人能够参与智能代理开发。这一点很重要，因为理解所需工作流程的人未必就是编写代码的人。

![Image](https://pbs.twimg.com/media/HH5Hq3Va4AAj9bu?format=jpg&name=large)

同时，无代码工具并未消除对工程控制的需求。随着系统变得越来越复杂，团队通常需要能够在代码中扩展或覆盖行为的方法。钩子和中间件在此尤为重要，因为它们允许团队在工具调用、上下文处理、审批、身份验证或业务规则周围添加自定义逻辑，而无需从头重新构建每个代理。

最好的构建环境能够让简单的事情变得简单，让复杂的事情成为可能。它们让领域专家能够编辑提示词、技能和上下文，同时仍然让工程师能够控制那些需要可靠、可测试且受管理的部分。

#### 测试

在代理被部署之前，团队需要一种方法来确定它是否真的就绪。

这并不意味着在任何人使用该代理之前就构建一个完美的评估套件。实际上，这很少是现实的。这确实意味着拥有足够的评估机制，以捕捉明显的失败情况、比较版本，并避免盲目地发布变更。

![Image](https://pbs.twimg.com/media/HH5HtItakAAyLFO?format=jpg&name=large)

大多数评估工作流以包含代表性任务的小型数据集开始。一些示例来自预期用例，而其他示例来自手动测试、内部试用、支持工单、先前的跟踪记录或已知的边缘情况。随着时间的推移，生产环境中的跟踪记录会使这些数据集更加完善，但测试应该在生产环境部署前就开始。

数据集和指标

数据集是团队保存其学习成果的方式。没有这些数据集，在及时变更、模型升级或工具更新后，同样的失败往往会再次出现。

合适的指标取决于任务。

在某些情况下，存在明确的真实答案。代理是否提取了正确的值？是否选择了正确的标签？是否更新了正确的字段？这些任务可以直接衡量其正确性。

其他时候，不存在单一的基准事实答案。智能体可能需要撰写响应、总结对话、决定是否升级，或完成存在多种有效路径的任务。在这些情况下，团队更多依赖基于标准的评估。评估的关键问题包括：响应是否有依据、智能体是否遵循了策略、是否请求了澄清，以及是否高效完成任务且未进行不必要的工具调用。

实验

实验是连接数据集和指标与迭代的桥梁。它们使团队能够在相同的评估集上比较提示词、模型、检索策略、工具架构和编排模式。随着时间的推移，这些实验会显示智能体是在改进还是在退化。

目标不是在第一天就创建一个完美的评估套件。目标是从一个实用的开始，并持续改进它。最有价值的评估数据集来自最具挑战性的用例：首先来自开发阶段和内部试用，然后是生产阶段。

模拟

模拟是测试的另一个重要部分。

许多智能体是多轮对话系统。它们不只是回答单个问题，而是会进行对话、收集信息、调用工具、更新状态，并处理歧义。对于这些智能体而言，单轮评估是不足的。团队需要多轮评估和模拟端到端交互。

语音代理是一个明显的例子，但这种模式更为广泛。任何基于一系列对话轮次进行操作的代理都可能需要模拟。支持代理可能需要处理愤怒的客户、询问跟进问题、查询订单状态，并决定是否需要升级处理。编码代理可能需要检查代码仓库、进行修改、运行测试，并响应用户反馈。内部运营代理可能需要在采取行动前收集缺失信息。

良好的测试实践帮助团队系统地改进代理，而无需依赖直觉。它们将预期行为转化为数据集，将数据集转化为实验，再将实验转化为系统的更好版本。部署后，监控提供真实世界的示例，这些示例能增强这些评估的效果。

#### 部署

一旦代理被构建并评估，它需要一个能够可靠运行的环境。

对于简单的代理，部署可能看起来与部署传统应用程序类似。但许多代理需要的不仅仅是无状态服务器。它们需要长时间运行、调用工具、等待人工输入、写入文件、从中断中恢复，并在多次交互或任务中维护状态。

![Image](https://pbs.twimg.com/media/HH5HwI9bkAAxMoP?format=jpg&name=large)

这就是为什么运行时很重要。

生产代理运行时通常需要支持持久化执行和人在回路模式。持久化执行是指代理能够检查点进度并在发生故障时恢复，而不会丢失工作。人在回路是指代理在需要审批、澄清或审核时能够暂停。

对于这个，有现成的解决方案。

[LangSmith 部署](https://docs.langchain.com/langgraph-platform) 提供用于部署和管理深度智能体（Deep Agents）和 LangGraph 智能体的基础设施。AWS AgentCore 是另一个针对智能体的托管运行时示例。一些团队也会在 Temporal 等系统之上构建自己的运行时，特别是当他们已经在栈的其他部分使用 Temporal 处理长时间运行的工作流时。

沙箱

许多代理也需要专用的执行环境。

代理越来越需要编写代码、执行代码、检查文件、转换文档或与文件系统交互。在这些情况下，团队需要决定工作发生的位置。沙箱是一种常见的解决方案。它们提供隔离的执行环境并具备文件系统访问权限，同时减少错误或不安全行为的影响范围。

示例包括

[LangSmith Sandboxes](https://www.langchain.com/blog/introducing-langsmith-sandboxes-secure-code-execution-for-agents/)、Daytona 和 E2B。

不是每个代理都需要完整的沙箱环境。在某些情况下，代理只需要一个存储和检索文件的地方。一个虚拟文件系统就足够了。Deep Agents 通过允许代理将文件用作工作内存（而不必在沙箱中执行任意代码）来支持这种模式。在底层，该文件系统可能由 PostgreSQL 或 S3 等系统提供支持。

上下文中心

部署的另一个经常被忽视的部分是管理提示和上下文。

代理的一些最重要部分并非传统的应用代码。提示词、检索上下文、技能和任务指令可能需要比应用本身更频繁地变更。它们也可能需要由非工程师人员进行编辑。

那产生了对提示或上下文中心的需求：一个用于存储、版本化、审查和更新代理非代码部分的地方。这允许团队无需完全部署即可调整代理行为，并且让领域专家掌控他们最了解的上下文。

实际上，部署不仅仅是在服务器上放置一个代理。而是要为代理提供其完成实际工作所需的运行时环境、执行环境和上下文管理系统。

#### 显示器

一旦代理被部署，团队需要了解它们在生产环境中的实际行为。

这就是监控代理与传统软件监控的不同之处。像延迟、成本、错误率和正常运行时间这样的指标仍然重要，但它们只是其中一部分。代理可以返回技术上成功的响应，但任务本身仍然可能失败。它可能调用错误的工具、依赖错误的上下文、跳过必要的审批步骤，或者生成听起来合理但错误的答案。

![Image](https://pbs.twimg.com/media/HH5HzAoasAERUIX?format=jpg&name=large)

为了理解那些失败，团队需要跟踪记录。

追踪记录捕获智能体的完整轨迹：它接收的输入、发起的模型调用、调用的工具、接收的输出，以及它产生的最终响应或行动。这是你理解智能体实际行为所需的详细程度。

这就是我们主张的原因

[代理可观测性赋能代理评估](https://www.langchain.com/blog/agent-observability-powers-agent-evaluation)，以及为什么

[代理改进循环始于追踪](https://www.langchain.com/blog/traces-start-agent-improvement-loop)

。如果无法看到轨迹，就无法可靠地调试行为，也无法将这些失败转化为未来的评估。

信号

监控还应包括从这些迹线中采集信号。

其中一些信号可能来自以 LLM 作为法官的评估器。例如，法官可以对智能体是否回答了用户问题、遵循了策略、使用了正确的语气或完成了任务进行评分。其他信号可能更简单。正则表达式可以检测是否出现了所需短语、是否调用了禁止的工具，或是否出现了已知的失败模式。

这些信号的用途不仅仅是质量检查。它们还可以成为产品分析的一种形式。它们可以告诉你用户要求座席执行哪些任务，座席在哪些环节卡住，用户纠正的频率有多高，以及用户在哪些地方察觉到错误。

反馈

反馈是监控的另一个核心部分。

仅存储轨迹是不够的。团队还需要将反馈与这些轨迹一起存储。这些反馈可以来自 LLM 评审、基于正则表达式的信号、人工评审人员，或通过 API 收集的直接用户反馈。例如，在 LangSmith 中，团队可以直接将用户反馈附加到底层运行中，从而更容易将“用户不满意”与“代理在三步之前使用了错误的工具”关联起来。

仪表盘

最后，团队需要能够揭示随时间推移趋势的仪表盘和警报。

一个实用的座席仪表板可跟踪使用情况、反馈、延迟、成本、工具调用、评估分数以及重复出现的故障模式等指标。当重要阈值被突破时（例如延迟上升、成本增加、工具失效、用户反馈下降或政策违规激增），应触发警报。

良好的监控不仅仅是了解系统是否正常运行。它还包括了解代理是否在以正确的方式做正确的工作，以及是否在随着时间不断改进。

最强大的监控系统会直接反馈到评估中。重要跟踪数据成为数据集示例，重复故障成为指标，而生产行为则成为下一轮改进的基础。

#### 迭代

最优秀的组织能够快速且系统地推进代理开发生命周期。

他们不会在发布前等待一个完美的代理。相反，他们构建一些有用的东西，进行足够的测试以了解其行为，以受控方式部署，监控其在生产环境中的表现，并将这些经验反馈到下一个版本中。

那并不意味着粗心地运输。关键在于拥有可见性。

拥有数据集、实验、追踪、反馈和仪表盘的团队可以直接从真实的真实使用中学习。他们可以在大规模推出之前测试变更，识别生产环境中出现的问题，将失败转化为评估，并在不依赖猜测的情况下改进智能体。

这就是团队如何爬山，以及代理系统如何随时间改进。

最有效的团队会找到困难的示例，理解代理为何失败，并调整提示词、工具配置、检索策略、模型、中间件或工作流。他们重新运行评估，部署更好的版本，而监控则为他们提供下一批边界情况和失败案例。

在企业内部，挑战在于使该循环在团队间可重复。

如果每个团队都必须从零开始构建自己的评估框架、部署基础设施、追踪系统、反馈流程和仪表盘，智能体开发将进展缓慢。最有效的组织会投入资源建设共享基础设施，以便团队能够完成整个生命周期，而无需不断重新开发基础系统。

这就是使代理开发生命周期成为可操作的实践。

#### 治理

治理围绕整个代理开发生命周期展开。

对于单个代理，轻量级的控制可能就足够了。随着组织部署更多的代理，治理变得必要。没有治理，团队很快会面临代理难以发现、难以监控、运行成本高昂，以及不清楚允许做什么的情况。

![Image](https://pbs.twimg.com/media/HH5H2uFaQAEs8Gu?format=jpg&name=large)

成本

第一个治理挑战是成本。

代理可能会变得成本高昂，因为它们可能涉及多次模型调用、长上下文窗口、重复使用工具、重试或长时间运行。组织需要通过预算、使用情况监控、警报以及对哪些代理、团队、模型或工具产生成本的可见性，来跟踪和管理相关支出。

工具访问

第二个治理挑战是工具访问。

代理很有用，因为它们能够采取行动，但这也带来了风险。团队需要围绕代理可访问的工具、访问条件以及代表的用户，制定明确的控制措施。

这就是审计跟踪变得重要的地方。如果代理调用工具，组织应该能够检查是哪个代理发起了调用、使用了什么输入、产生了什么输出，以及哪个用户或策略授权了该操作。工具调用往往是代理行为驱动业务影响的关键环节，因此需要具备可观察性和可审查性。

人在回路中是另一个重要的治理机制。

并非所有工具调用都应完全自动化。某些操作应暂停以等待人工审核，尤其是在涉及客户、金融系统、敏感数据或生产基础设施时。人机闭环工作流在从一开始就设计到系统中的情况下效果最佳。

可发现性

第三个治理挑战是可发现性和重用。

随着组织构建更多代理，它们也会积累更多可复用资产，如提示词、技能、工具、检索源、策略，甚至其他代理。如果没有良好的发现和治理机制，团队往往会重复创建这些组件，导致不一致。共享上下文和共享代理需要可被发现、可复用且可被治理。

这对技能来说尤为重要。一项技能可以编码工作流程、写作风格、特定领域的流程或工具使用说明。如果一个团队已经构建了一项良好的技能，另一个团队应该能够找到它，而不是从头编写一个新版本。

良好的治理不是为了减慢团队的速度。而是关于在智能体系统规模扩大时，让快速迭代成为可能，同时不失去可见性、控制力和一致性。

#### 结论

最优秀的组织已经开始以这种方式运作。它们会早期发布，但不会盲目发布。它们在部署前进行评估，在部署后监控行为，并持续利用所学知识改进下一版本。

这就是让代理开发可重复的原因。这也使代理能够从演示版本过渡到可靠的生产系统。

## 通俗精炼（1）

### 2026-05-12 04:28:29

#### 代理开发生命周期：从 Demo 到可靠生产系统

##### 核心观点

真正优秀的组织，不是把 AI Agent 当成一次性 Demo，而是建立一套可重复、可治理、可持续优化的 **代理开发生命周期**。

这个生命周期包括四个阶段：

> **构建 → 测试 → 部署 → 监控**

关键在于：**先测试，再部署；上线后持续监控，并把真实反馈反哺下一轮迭代。**

---

##### 一、构建：明确代理形态与抽象层级

构建阶段要决定：要做什么样的 Agent，用什么工具和架构来实现。

常见工具分为几类：

- **代理框架**：用于组合模型、工具、提示词、检索、结构化输出等，例如 LangChain、CrewAI。
- **代理运行时**：支持状态、分支、循环、暂停、恢复、持久化等复杂执行逻辑，例如 LangGraph。
- **代理工作环境**：提供提示词、技能、MCP、文件系统、中间件等，让 Agent 能完成长期任务，例如 Deep Agents、Claude Agents SDK。
- **无代码/低代码工具**：让业务专家也能参与构建，例如 LangSmith Fleet、Claude Cowork、n8n。

好的构建环境应该做到：

> 简单任务足够简单，复杂系统也能扩展和工程化。

---

##### 二、测试：上线前先建立基本可信度

Agent 不能等上线后才发现问题，部署前就应进行评估。

测试不要求一开始就完美，但至少要有：

- 代表性任务数据集
- 明确的评估指标
- 版本对比实验
- 多轮对话/任务模拟

评估方式包括两类：

1. **有标准答案的任务**  
   例如字段提取、分类、状态更新，可直接衡量准确率。

2. **无唯一答案的任务**  
   例如总结、客服回复、是否升级处理，需要基于标准评估：是否有依据、是否遵守策略、是否高效、是否误用工具。

测试的价值在于：

> 把经验沉淀为数据集，把数据集变成实验，把实验推动系统持续变好。

---

##### 三、部署：不只是把 Agent 放到服务器上

生产级 Agent 往往不同于普通应用，它可能需要：

- 长时间运行
- 调用工具
- 等待人工审批
- 写入或读取文件
- 从失败中恢复
- 在多次交互中保持状态

因此，部署需要三类关键能力：

###### 1. 运行时

支持持久化执行、状态恢复、人工介入等能力。  
例如 LangSmith Deployments、AWS AgentCore，或基于 Temporal 自建。

###### 2. 沙箱或文件系统

当 Agent 需要写代码、执行代码、处理文件时，需要隔离环境，避免风险扩散。  
例如 LangSmith Sandboxes、Daytona、E2B。

###### 3. 上下文中心

提示词、技能、检索内容、任务指令往往比代码变化更频繁，也可能由非工程人员维护。

因此需要一个地方统一管理：

- 存储
- 版本控制
- 审核
- 更新
- 权限管理

---

##### 四、监控：看见 Agent 真实行为

传统监控只看延迟、成本、错误率、可用性是不够的。

Agent 可能技术上“成功返回”，但实际上：

- 没完成任务
- 调错工具
- 用错上下文
- 跳过审批
- 生成看似合理但错误的答案

因此需要 **轨迹追踪**。

追踪应记录 Agent 的完整执行链路：

- 用户输入
- 模型调用
- 工具调用
- 工具结果
- 中间决策
- 最终输出或动作

同时还需要采集信号：

- LLM 评审分数
- 正则检测
- 人工审核
- 用户反馈
- 成本、延迟、工具失败率等指标

好的监控系统不只是发现故障，而是帮助团队理解：

> Agent 是否以正确方式完成了正确任务。

---

##### 五、迭代：用真实使用推动持续进化

优秀团队不会等 Agent 完美才发布，而是：

1. 构建一个有用版本
2. 做基础测试
3. 受控上线
4. 监控真实表现
5. 把失败案例转化为评估集
6. 优化提示词、工具、模型、检索、流程
7. 再次评估和部署

这形成一个持续改进闭环。

真正的关键不是“快速上线”，而是：

> 快速上线但不盲目上线，有数据、有追踪、有反馈、有控制。

---

##### 六、治理：规模化之后的核心挑战

当组织内 Agent 数量增加后，治理变得非常重要。

主要治理问题包括：

###### 1. 成本治理

Agent 可能因多轮模型调用、长上下文、重试、长任务而快速增加成本。  
需要预算、成本监控、告警和归因能力。

###### 2. 工具访问治理

Agent 能调用工具，也意味着它能产生真实业务影响。

需要明确：

- 哪个 Agent 能调用哪些工具
- 在什么条件下调用
- 代表哪个用户调用
- 是否需要人工审批
- 调用过程是否可审计

###### 3. 可发现与复用

组织会积累大量可复用资产：

- 提示词
- 技能
- 工具
- 检索源
- 策略
- 其他 Agent

如果缺少发现和复用机制，团队会重复造轮子，导致不一致和低效率。

治理的目标不是降低速度，而是：

> 在规模化时保持可见性、控制力和一致性。

---

##### 总结

Agent 从 Demo 走向生产，核心不是单点技术，而是一套完整的开发生命周期。

最成熟的组织会做到：

- 尽早发布，但不盲目发布
- 部署前评估
- 部署后监控
- 用真实反馈持续改进
- 建设共享基础设施和治理体系

最终，Agent 开发会从一次性项目，变成一种可重复、可扩展、可管理的工程实践。

## 结构化（2）

### 2026-05-12 04:30:43

##### 主旨概括

文章提出：**优秀组织不是把智能代理（Agent）当作一次性 Demo，而是建立一套可重复的“代理开发生命周期”**，通过持续构建、测试、部署、监控和迭代，让代理系统逐步从实验走向可靠生产。

这个生命周期核心是：**构建 → 测试 → 部署 → 监控 → 迭代**，并由治理机制贯穿始终，确保成本、权限、复用和风险可控。

---

##### 1. 代理开发生命周期：从一次成功到可重复交付

代理开发生命周期包括四个主要阶段：

> **构建 → 测试 → 部署 → 监控**

关键点：

- **测试要在上线前开始**，而不是等生产环境出问题后再补救。
- 团队应先小范围发布，从真实使用中学习，再快速迭代。
- 单个代理可以比较轻量；但多个代理同时存在时，就会变成基础设施和治理问题。
- 团队需要统一管理：
  - 成本
  - 工具访问权限
  - 工具调用审计
  - 上下文复用
  - 人工介入机制

简单说，**让一个代理偶尔跑通不难，难的是让开发代理成为组织内可重复、可管理的能力。**

---

##### 2. 构建：决定代理的形态和抽象层级

构建阶段要明确：团队要做什么类型的代理，以及使用多高层级的工具和抽象。

常见工具分为几类：

###### 代码优先工具

LangChain 生态中的例子包括：

- **LangChain**
- **LangGraph**
- **Deep Agents**

生态外的例子包括：

- **CrewAI**
- **Claude Agents SDK**

这些工具处在不同层级：

| 类型 | 作用 | 示例 |
|---|---|---|
| 代理框架 | 组合模型调用、工具、提示词、检索、结构化输出和代理循环 | LangChain、CrewAI |
| 代理运行时 | 支持状态、控制流、持久化、人工干预 | LangGraph |
| 代理执行环境/支撑结构 | 提供提示词、技能、MCP 服务器、钩子、中间件、文件系统等 | Deep Agents、Claude Agents SDK |

文章强调，“构建代理”含义并不单一：

- 简单代理：可能只是定义一个工具调用循环。
- 复杂代理：可能需要提示词、技能、MCP 服务器、中间件、长期上下文等。

---

##### 3. 无代码与低代码：让业务专家参与，但仍需工程控制

无代码和低代码工具可以让非工程人员参与代理开发。

文章提到的例子包括：

- **LangSmith Fleet**
- **Claude Cowork**
- **n8n**

它们的价值在于：

- 真正懂业务流程的人，不一定会写代码。
- 领域专家可以编辑提示词、技能和上下文。
- 工程师仍然可以通过代码控制关键逻辑。

但无代码并不意味着不需要工程能力。随着系统变复杂，团队仍需要：

- 钩子 Hooks
- 中间件 Middleware
- 工具调用控制
- 审批逻辑
- 身份验证
- 业务规则

理想的构建环境应该是：

> **简单的事情足够简单，复杂的事情也能实现。**

---

##### 4. 测试：上线前先知道代理是否可靠

代理上线前，团队需要判断它是否“足够好”。

这并不意味着一开始就建立完美评估体系，而是要做到：

- 能发现明显失败
- 能比较不同版本
- 能避免盲目发布

测试通常从一个小型代表性数据集开始，数据来源包括：

- 预期使用场景
- 手动测试
- 内部试用
- 客服工单
- 过去的追踪记录
- 已知边缘案例

随着生产使用增加，真实追踪记录会继续丰富测试数据集。

---

##### 5. 数据集和指标：把经验沉淀下来

数据集是团队保留学习成果的方式。

如果没有数据集，常见问题会反复出现，例如：

- 修改提示词后旧问题复发
- 升级模型后行为退化
- 更新工具后出现相同失败

不同任务适合不同指标：

###### 有明确答案的任务

可以直接衡量正确性，例如：

- 是否提取了正确字段
- 是否选择了正确标签
- 是否更新了正确数据

###### 没有唯一答案的任务

需要基于标准评估，例如：

- 回答是否有依据
- 是否遵循策略
- 是否请求澄清
- 是否高效完成任务
- 是否避免不必要的工具调用

---

##### 6. 实验：比较版本，推动持续改进

实验用于连接数据集、指标和迭代。

团队可以在相同评估集上比较：

- 不同提示词
- 不同模型
- 不同检索策略
- 不同工具架构
- 不同编排方式

目标不是第一天就做出完美评估体系，而是：

> **先建立一个实用版本，再持续改进。**

最有价值的评估数据通常来自最困难的案例：

1. 开发阶段发现的问题  
2. 内部试用中的问题  
3. 生产环境中的真实失败  

---

##### 7. 模拟：多轮代理不能只做单轮测试

很多代理不是回答一个问题就结束，而是需要多轮交互。

例如代理可能需要：

- 对话
- 收集信息
- 调用工具
- 更新状态
- 处理模糊问题

因此，单轮评估不够，需要端到端模拟。

文章举了几个例子：

- **语音代理**：需要模拟完整对话流程。
- **客服代理**：可能要安抚愤怒客户、追问信息、查询订单、判断是否升级人工。
- **编码代理**：可能要检查代码仓库、修改代码、运行测试、响应反馈。
- **内部运营代理**：可能要先收集缺失信息，再执行操作。

好的测试实践能把预期行为转化为数据集，再转化为实验，最终推动系统改进。

---

##### 8. 部署：代理需要的不只是普通服务器

代理构建并评估后，需要可靠运行环境。

简单代理可能像普通应用一样部署，但复杂代理往往还需要：

- 长时间运行
- 调用工具
- 等待人工输入
- 写入文件
- 从中断中恢复
- 在多次交互中维护状态

因此，运行时很重要。

生产级代理运行时通常需要支持：

- **持久化执行**：代理可以保存进度，失败后恢复，不丢失任务。
- **人在回路**：需要审批、澄清或审核时，代理可以暂停等待人工处理。

文章提到的部署和运行时方案包括：

- **LangSmith 部署**：用于部署和管理 Deep Agents 与 LangGraph 代理。
- **AWS AgentCore**：面向代理的托管运行时。
- **Temporal**：一些团队会基于它构建自己的长任务运行时。

---

##### 9. 沙箱：为代理提供安全执行环境

很多代理需要：

- 编写代码
- 执行代码
- 检查文件
- 转换文档
- 访问文件系统

这时需要沙箱来隔离执行环境，降低错误或不安全行为的影响范围。

文章提到的沙箱例子：

- **LangSmith Sandboxes**
- **Daytona**
- **E2B**

但不是所有代理都需要完整沙箱。

有些代理只需要一个虚拟文件系统，用来存储和检索文件。例如：

- **Deep Agents** 支持把文件作为工作记忆使用。
- 底层可以由 **Postgres** 或 **S3** 提供支持。

---

##### 10. 上下文中心：管理提示词、技能和任务指令

代理的重要部分不一定是传统代码，而是：

- 提示词
- 检索上下文
- 技能
- 任务指令

这些内容可能比应用代码变化更频繁，也可能需要由非工程师编辑。

因此团队需要一个“提示词或上下文中心”，用于：

- 存储
- 版本管理
- 审查
- 更新

这样可以让团队不必完整重新部署应用，也能调整代理行为。

部署代理并不只是把程序放到服务器上，而是要提供：

- 运行时环境
- 执行环境
- 上下文管理系统

---

##### 11. 监控：不仅看系统是否运行，还要看任务是否完成

代理上线后，团队需要知道它在真实环境中表现如何。

传统监控指标仍然重要，例如：

- 延迟
- 成本
- 错误率
- 可用性

但对代理来说还不够。因为代理可能技术上“成功返回”，但实际上任务失败，例如：

- 调用了错误工具
- 使用了错误上下文
- 跳过审批流程
- 生成听起来合理但实际错误的答案

因此，团队需要完整追踪记录。

追踪记录应包括：

- 用户输入
- 模型调用
- 工具调用
- 工具输出
- 最终回复或行动

没有轨迹，就很难调试代理，也无法把失败转化为未来评估数据。

---

##### 12. 信号、反馈和仪表盘：把监控变成改进依据

监控还应从追踪中提取信号。

信号可以来自：

- **LLM 评审器**：判断是否回答问题、遵守策略、语气正确、完成任务。
- **规则或正则表达式**：检测是否调用了禁止工具、是否出现特定失败模式。

这些信号不仅用于质量检查，还能变成产品分析，例如：

- 用户最常要求代理做什么
- 代理在哪些步骤卡住
- 用户多久纠正一次代理
- 用户在哪里感知到错误

反馈来源包括：

- LLM 评审
- 正则信号
- 人工审核
- 用户直接反馈

例如在 **LangSmith** 中，可以把用户反馈直接附加到底层运行记录上，从而分析“用户不满意”与“代理三步前用了错误工具”之间的关系。

仪表盘应持续跟踪：

- 使用量
- 用户反馈
- 延迟
- 成本
- 工具调用
- 评估分数
- 重复故障模式

当出现以下情况时，应触发警报：

- 延迟上升
- 成本增加
- 工具失效
- 用户反馈下降
- 策略违规激增

---

##### 13. 迭代：快速发布，但不能盲目发布

优秀组织不会等代理完美才发布，而是：

1. 构建一个有用版本  
2. 做足够测试  
3. 受控部署  
4. 监控真实表现  
5. 把经验反馈到下一版  

这不是草率上线，关键是要有可见性。

拥有以下能力的团队，可以从真实使用中学习：

- 数据集
- 实验
- 追踪
- 反馈
- 仪表盘

他们可以：

- 在大规模发布前测试变更
- 识别生产问题
- 把失败案例转化为评估数据
- 不靠猜测改进代理

有效团队会分析代理为何失败，并调整：

- 提示词
- 工具配置
- 检索策略
- 模型
- 中间件
- 工作流

然后重新运行评估，部署更好版本，再从监控中获得下一批边界案例。

##### 14. 治理：让多个代理可控、可复用、可审计

治理贯穿整个生命周期。

单个代理可能只需要轻量控制，但当组织部署多个代理时，治理变得必要。否则会出现：

- 代理难以发现
- 难以监控
- 成本失控
- 权限边界不清

###### 成本治理

代理成本可能很高，因为它可能涉及：

- 多次模型调用
- 长上下文窗口
- 重复工具调用
- 重试
- 长时间运行

组织需要：

- 预算管理
- 使用量监控
- 成本警报
- 按代理、团队、模型、工具查看成本来源

###### 工具访问治理

代理能采取行动，因此也带来风险。

团队需要明确：

- 哪个代理能访问哪些工具
- 在什么条件下可以调用
- 代表哪个用户执行
- 哪些操作必须人工审批

工具调用需要审计，包括：

- 哪个代理发起调用
- 输入是什么
- 输出是什么
- 哪个用户或策略授权了操作

涉及客户、金融系统、敏感数据、生产基础设施的操作，尤其适合引入人在回路审批。

###### 可发现性与复用

随着代理变多，组织会积累大量可复用资产：

- 提示词
- 技能
- 工具
- 检索源
- 策略
- 其他代理

如果没有发现和治理机制，团队会重复造轮子，导致不一致。

尤其是“技能”很重要，因为它可以封装：

- 工作流
- 写作风格
- 领域流程
- 工具使用说明

如果一个团队已经构建了好技能，其他团队应该能够找到并复用，而不是从零重写。

好的治理不是拖慢团队，而是让团队在规模化时仍能快速迭代，并保持可见性、控制力和一致性。

##### 15. 结论：代理从 Demo 走向生产，靠的是生命周期系统

最优秀的组织已经开始采用这种方式：

- 尽早发布，但不盲目发布
- 上线前做评估
- 上线后做监控
- 持续用真实反馈改进下一版

这套机制让代理开发变得可重复，也让代理从演示项目逐步变成可靠的生产系统。

最终，成功的关键不是某一次代理表现很好，而是组织拥有一套能持续学习、持续改进、可治理、可扩展的代理开发生命周期。

##### 1. 代理开发生命周期：从一次成功到可重复成功

- 代理开发不应是孤立项目，而应形成系统化流程。
- 生命周期包含四个阶段：

  > **构建 → 测试 → 部署 → 监控**

- 顺序很重要：  
  - 代理上线前就要测试，而不是上线后才发现问题。  
  - 上线后要监控真实表现，并把经验反馈到下一轮构建和评估中。
- 对单个代理来说流程可以轻量；但当组织有多个代理时，就会变成基础设施和治理问题，例如：
  - 成本控制
  - 工具访问权限
  - 工具调用审计
  - 上下文复用
  - 人工审批机制

##### 2. 构建：选择合适的抽象和工具

构建阶段决定要创建什么类型的代理，以及使用多高层次的开发抽象。

###### 代码优先工具

常见工具包括：

- LangChain 生态：
  - **LangChain**
  - **LangGraph**
  - **Deep Agents**
- 其他生态：
  - **CrewAI**
  - **Claude Agents SDK**

这些工具处在不同层次：

| 类型 | 关注点 | 示例 |
|---|---|---|
| 代理框架 | 组合模型调用、工具、提示词、检索、结构化输出、代理循环 | LangChain、CrewAI |
| 代理运行时 | 状态、控制流、持久化、人工干预 | LangGraph |
| 代理执行环境/工作环境 | 长任务执行所需的提示词、技能、MCP 服务器、钩子、中间件、文件系统 | Deep Agents、Claude Agents SDK |

###### 不同复杂度的代理构建

- 简单代理：可能只是一个工具调用循环。
- 复杂代理：可能需要：
  - 编写提示词
  - 定义技能
  - 连接 MCP 服务器
  - 配置中间件
  - 管理长期上下文

##### 3. 无代码和低代码构建：让业务专家参与

无代码/低代码工具让非工程人员也能参与代理开发，例如：

- **LangSmith Fleet**
- **Claude Cowork**
- **n8n**

关键点：

- 懂业务流程的人不一定会写代码，因此需要让领域专家能编辑提示词、技能和上下文。
- 但无代码工具不能替代工程控制。
- 当系统复杂后，仍需要通过代码扩展或覆盖行为。

###### 钩子和中间件的重要性

钩子和中间件可以帮助团队在以下环节加入自定义逻辑：

- 工具调用
- 上下文处理
- 审批流程
- 身份验证
- 业务规则

理想的构建环境应做到：

> 简单的事情简单做，复杂的事情也能做。

---

##### 4. 测试：上线前判断代理是否准备好

测试不是要求一开始就有完美评估体系，而是要有足够机制避免盲目发布。

###### 测试数据来源

初始评估数据集通常来自：

- 预期用例
- 手动测试
- 内部试用
- 支持工单
- 过去的追踪记录
- 已知边界情况

生产数据会逐渐丰富数据集，但测试必须在部署前开始。

---

##### 5. 数据集和指标：沉淀团队经验

数据集是团队保存经验的方式。否则，提示词调整、模型升级或工具更新后，相同错误可能反复出现。

###### 有明确答案的任务

可以直接衡量正确性，例如：

- 是否提取了正确值？
- 是否选择了正确标签？
- 是否更新了正确字段？

###### 没有唯一答案的任务

例如：

- 写回复
- 总结对话
- 判断是否升级处理
- 完成有多条路径的任务

这类任务更依赖标准化评估，例如：

- 回答是否有依据？
- 是否遵守策略？
- 是否请求澄清？
- 是否高效完成任务？
- 是否进行了不必要的工具调用？

---

##### 6. 实验与模拟：让迭代有依据

###### 实验

实验用于在同一评估集上比较不同方案，例如：

- 提示词
- 模型
- 检索策略
- 工具架构
- 编排模式

目标不是第一天就完美，而是先建立实用评估，再持续改进。

###### 模拟

很多代理是多轮对话系统，单轮评估不够。

需要模拟端到端交互，例如：

- **语音代理**：处理多轮语音交流。
- **客服代理**：面对愤怒客户、追问信息、查订单、判断是否升级。
- **编码代理**：检查代码仓库、修改代码、运行测试、响应反馈。
- **内部运营代理**：行动前收集缺失信息。

好的测试可以把“预期行为”转化为数据集，再转化为实验，最终推动代理版本改进。

##### 7. 部署：不只是把代理放到服务器上

代理部署通常比传统应用更复杂，因为很多代理需要：

- 长时间运行
- 调用工具
- 等待人工输入
- 写入文件
- 从中断中恢复
- 跨多轮交互维护状态

###### 运行时能力

生产代理运行时通常需要支持：

- **持久化执行**：故障后能从检查点恢复，不丢失进度。
- **人在回路**：需要审批、澄清或审核时可以暂停。

相关工具示例：

- **LangSmith Deployments**
- **AWS AgentCore**
- 基于 **Temporal** 自建运行时

---

##### 8. 沙箱、文件系统与上下文中心

###### 沙箱

当代理需要写代码、执行代码、检查文件、转换文档时，需要隔离环境降低风险。

示例：

- **LangSmith Sandboxes**
- **Daytona**
- **E2B**

###### 虚拟文件系统

不是所有代理都需要完整沙箱。有些只需要存取文件。

例如：

- **Deep Agents** 支持代理把文件作为工作记忆。
- 底层可由 **PostgreSQL** 或 **S3** 支持。

###### 上下文中心

代理的重要部分不一定是传统代码，而是：

- 提示词
- 检索上下文
- 技能
- 任务指令

这些内容可能比应用代码变化更频繁，也可能由非工程人员维护。

因此需要“提示词/上下文中心”来：

- 存储
- 版本化
- 审查
- 更新

这样团队无需完整重新部署，也能调整代理行为。

##### 9. 监控：看清代理在生产中的真实行为

传统监控指标仍然重要，例如：

- 延迟
- 成本
- 错误率
- 正常运行时间

但代理还可能出现“技术上成功、任务上失败”的情况，例如：

- 调用了错误工具
- 使用了错误上下文
- 跳过必要审批
- 生成看似合理但错误的答案

###### 追踪记录

要理解代理行为，必须记录完整轨迹，包括：

- 输入内容
- 模型调用
- 工具调用
- 工具输出
- 最终响应或动作

没有轨迹，就难以调试，也无法把失败转化为后续评估案例。

##### 10. 信号、反馈和仪表盘

###### 信号

可以从追踪中提取质量信号，例如：

- 用 LLM 作为评审，判断代理是否回答问题、遵守策略、语气正确、完成任务。
- 用正则表达式检测：
  - 必要短语是否出现
  - 禁止工具是否被调用
  - 已知失败模式是否发生

这些信号不仅用于质量检查，也可用于产品分析，例如：

- 用户最常要求代理做什么？
- 代理在哪些环节卡住？
- 用户多久纠正一次代理？
- 用户在哪里感知到错误？

###### 反馈

反馈来源包括：

- LLM 评审
- 正则信号
- 人工审核
- 用户通过 API 提交的反馈

例如在 **LangSmith** 中，可以把用户反馈直接附加到底层运行记录上，从而关联：

> “用户不满意”与“三步之前代理调用了错误工具”。

###### 仪表盘和警报

实用仪表盘应跟踪：

- 使用量
- 用户反馈
- 延迟
- 成本
- 工具调用
- 评估分数
- 重复故障模式

当出现以下情况时应触发警报：

- 延迟上升
- 成本增加
- 工具失效
- 用户反馈下降
- 策略违规激增

2. 做足够测试
3. 受控部署
4. 监控生产表现
5. 将经验反馈到下一版

这不是草率上线，关键在于有可见性。

具备以下能力的团队可以更快改进：

- 数据集
- 实验
- 追踪
- 反馈
- 仪表盘

- 提示词
- 工具配置
- 检索策略
- 模型
- 中间件
- 工作流

代理成本可能很高，因为它们可能涉及：

- 长上下文窗口

组织需要：

- 预算管理

代理能采取行动，因此必须管理风险。

需要明确：

- 什么条件下可访问

同时要有审计跟踪，记录：

- 哪个代理调用了工具
- 输入是什么

###### 可发现性和复用

组织代理增多后，会积累很多可复用资产：

- 技能
- 工具

懂业务流程的人往往不是工程师；但复杂 Agent 又不能完全交给无代码平台，否则权限、审批、工具调用、上下文污染都会失控。

**反常识之处：**  
无代码不是“替代工程”，而是把工程能力下沉给业务，同时保留关键控制点。

**可迁移价值：**  
适用于企业内部工具平台、低代码系统、数据分析平台、自动化运营平台。  
理想结构是：**业务可配置，工程可约束，平台可治理**。

**我应该记住什么：**  
> 简单的事情要让非工程师完成，危险的事情必须由工程机制兜底。

---

###### 洞见 5：当 Agent 从一个变成多个，问题会从产品问题变成组织基础设施问题

###### **核心观点：**  
> 单个 Agent 可以轻量开发；多个 Agent 并存时，真正的挑战变成成本、权限、审计、复用、上下文管理和治理。

**为什么重要：**  
企业不是缺一个 Demo，而是缺一套能让多个团队安全复用、持续迭代的底座。

**反常识之处：**  
很多组织把 Agent 当应用项目管理；文章指出它更像一种新型软件生产体系，需要共享基础设施。

**可迁移价值：**  
和早期微服务、数据平台、机器学习平台类似：  
当数量增加，平台化、标准化、治理能力会成为速度的前提。

**我应该记住什么：**  
> 规模化之后，治理不是减速器，而是加速器。

---

##### 3. 底层逻辑

###### **逻辑一：真实使用产生最有价值样本，样本反过来改进系统**

- **表层现象：** 最好团队会早发布、快迭代。  
- **深层原因：** Agent 的失败模式无法完全靠预设想象，必须从真实任务中暴露。  
- **推导结论：** 核心能力不是“上线前调优”，而是把生产失败转化为评估集、指标和下一版改进。

---

###### **逻辑二：Agent 是行为系统，不是文本生成器**

- **表层现象：** Agent 需要工具调用、状态、权限、文件系统、人类审批、长期任务恢复。  
- **深层原因：** Agent 不只是回答问题，而是在环境中执行动作。  
- **推导结论：** 生产级 Agent 必须具备运行时、沙箱、审计、权限、持久化和人在回路机制。

---

###### **逻辑三：复杂度上升后，局部效率会让位于系统治理**

- **表层现象：** 多个团队各自构建 Agent 会造成重复、成本失控、权限混乱。  
- **深层原因：** Agent 的关键资产如提示词、技能、工具、上下文、策略具有复用价值，也具有风险外溢性。  
- **推导结论：** 企业级 Agent 能力必须平台化：共享评估、部署、监控、反馈、权限和资产发现机制。
