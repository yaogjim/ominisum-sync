> **摘要**：文章围绕 AI Agent 场景下的密钥泄露风险，提出用 HTTP/HTTPS 凭证代理替代传统直接下发密钥的模式。核心做法是让 Agent 通过本地代理访问外部服务，由代理层注入凭证、统一审计与策略控制，从而隔离 Agent 与真实密钥。

## 分析要点

- **核心高价值点**：最有价值的点是把“Agent 不可信”作为前提，重新定义密钥管理边界：不要把密钥交给 Agent，而是在所有出站 HTTPS 流量的底层统一做代理注入与策略控制。
- **留存建议**：长期保留（提出了面向 AI Agent 的凭证隔离新架构，兼具问题定义、设计思路与实现细节，适合作为后续安全设计参考。）

**知识要点**

- 传统面向确定性程序的密钥分发模式不适合易受提示注入影响的 AI Agent。
- 凭证代理的核心价值在于将 Agent 与真实凭证解耦，在网络出口层统一附加认证信息。
- 利用 HTTPS\_PROXY 和本地可信 CA，可在 API、CLI、SDK、MCP 等多种调用路径下统一接管出站请求。
- 完整方案不仅依赖代理设置，还要求网络层强制所有出站流量经过代理，避免 Agent 绕过控制面。
- MITM 型代理虽然增强了可观测性和策略控制能力，但也带来证书信任、兼容性与安全边界的新挑战。

**行动项**

- 评估你当前的 Agent 系统是否存在“直接向 Agent 暴露 API Key/OAuth Token”的风险点，并梳理外部服务访问路径。
- 将文中“凭证不交给 Agent、只在出口层注入”的思路纳入你的 Agent 安全架构设计清单。
- 验证现有运行环境是否支持 HTTPS\_PROXY、网络出口锁定和本地 CA 信任链，以判断该方案的适配成本。
- 进一步调研证书固定、非标准客户端和绕过代理场景，确认该架构在生产环境中的边界条件。

### Agent Vault：开源凭证代理和代理保管库

一段时间以来，行业一直面临一个重大问题：我们如何在不允许代理读取任何密钥的情况下，为代理提供对服务的安全访问？

[Agent Vault](https://github.com/Infisical/agent-vault)，一个开源的 HTTP 凭证代理和密钥库。

在

[@infisical](https://x.com/@infisical), 我们每月处理数十亿个密钥，这些密钥将应用配置和密钥数据发送到需要它们的团队、CI/CD 流水线以及服务器/应用程序。我们见识过从基于身份的集中式密钥管理到自动化

[密钥轮换](https://infisical.com/docs/documentation/platform/secrets-mgmt/concepts/secrets-rotation)

和

[动态密钥](https://infisical.com/docs/integrations/dynamic-secrets)

方案，用于即时生成密钥。因此，当我们最初考虑代理如何与密钥交互时，我们认为传统的密钥管理技术就足够了。我们大错特错。

本文探讨了我们对该问题的思考方式，以及为何认为 Agent Vault 在 AI 时代恰好契合机密管理的形式。希望本文能引人入胜，并对其他可能需要为自己的代理设计机密管理解决方案的人有所帮助；您甚至可以考虑

[Agent Vault](https://github.com/Infisical/agent-vault) for a spin.

### 挑战

当今的计算范式并非为代理设计，而是为传统工作负载设计的。这里的问题在于，代理（无论是编码代理还是沙箱执行代理）的运作方式与我们以往所见的任何事物都存在根本差异；它们具有非确定性，且易于操纵，这打破了传统系统所依赖的许多假设。

比如，密钥管理领域过去十年的做法一直是直接从集中式密钥库向工作负载交付密钥；这对执行路径固定的程序效果良好，但当程序被诱导以其作者从未预料到的方式使用这些密钥时，这种做法就会失效。

考虑这种攻击向量：一个恶意行为者

[提示注入](https://en.wikipedia.org/wiki/Prompt_injection) 一个代理，指示它扫描并返回代理环境中可用的机密；代理服从并将机密暴露回调用者。无论是 RAG 管道中的被污染文档，还是工具调用引入的恶意网页（指示代理将机密转发到攻击者控制的端点），代理都有多种被提示注入的方式，使其成为一个极易受攻击的表面。不幸的是，即使有足够的

[安全护栏](https://render.com/articles/what-s-the-best-way-to-implement-guardrails-against-prompt-injection)

到位，也无法保证代理不会被操纵以泄露其机密。

这是凭证泄露的问题凭证泄露并且，如果发生这种情况，攻击者将拥有执行数据泄露数据泄露 ，这是一个相关问题，他们现在可以利用被泄露的凭证访问有价值的数据。正如你所料，成功操纵具备电子邮件功能的代理的攻击者，可以窃取代表用户读取和发送电子邮件所需的凭证——非常可怕。

### 早期解决方案

我们接触过的大多数团队都实施了基本的防护措施、安全控制以及更多传统的规避措施，以缓解凭证泄露风险。此类措施的一个例子是为代理提供尽可能短期的凭证，例如如果对于支持 OAuth2 的 API，使用访问/刷新令牌模式是可行的；这种短暂性也可以通过自动化

[密钥轮换](https://infisical.com/docs/documentation/platform/secret-rotation/overview)以及

[动态密钥](https://infisical.com/docs/documentation/platform/dynamic-secrets/overview)

方案。

在这种情况下，如果攻击者能够获取到暴露的凭证，那么他们只能在有限的时间段内使用它。然而，这是不理想的，因为这些措施并没有改变凭证仍然可能被外泄的事实。

最优秀的团队会开发自己的定制管道系统来防范凭证泄露。例如，Anthropic 的

[Managed Agents](https://www.anthropic.com/engineering/managed-agents) 架构博客描述了为代理构建一个专门的代理服务，该服务从保险库中获取凭证并将其附加到通过该代理的出站请求中；该博客提到，框架从未知晓这些凭证。

[sandboxed agent to control plane architecture](https://browser-use.com/posts/two-ways-to-sandbox-agents)

[credential brokering](https://vercel.com/changelog/safely-inject-credentials-in-http-headers-with-vercel-sandbox)

[outbound workers](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/configuration/outbound-workers/)

Browser Use 是一家为 AI 代理提供网页浏览器的基础设施公司，采用沙箱化代理到控制平面架构，该架构通过一个专用服务路由代理请求，该服务在代理层注入凭证。最近几天，我们还看到云服务提供商推出了各自特定于提供商的解决方案，例如 Vercel 的凭证代理或 Cloudflare 的出站 Worker，这些方案仅在其特定生态系统内运行。

这是一个强烈信号，表明向传统工作负载传递密钥的旧模式对代理不起作用。这也是一个强烈信号，表明这不是每个团队都应该独自解决的问题。

### 解决方案

当你考察最佳团队如何构建和使用安全代理时，你会注意到他们在代理和凭证之间划定了信任边界。毕竟，如果代理不能被信任安全处理凭证，那么最初为什么要给它任何凭证呢？或许更合理的做法是在代理和它试图访问的服务之间的代理层中代理凭证。这正成为我们整个行业目前正逐步走向的主要方法： 凭证代理 .

简而言之，代理不应被信任直接访问任何密钥。相反，应该由其他实体代表代理持有密钥，并在代理通过它发送请求时将其附加到边缘。edge

### 代理保管库

今天，我们宣布

[Agent Vault](https://github.com/Infisical/agent-vault)，一个处于研究预览阶段的开源项目，其核心理念很简单：agents 永远不应该首先看到底层的密钥。

借助 Agent Vault，我们正在重新思考代理应如何使用密钥，并以代理为优先，同时考虑到人类因素。我们认为密钥库和/或密钥存储将持续存在，但为适应代理操作人体工程学而交付密钥的方式将发生巨大变化。

代理（至少在当前状态下）不能被信任直接持有密钥，因此每个代理旁必须部署一个专用的正向 HTTP 代理，无论是通过专用服务、sidecar 还是出口层；以安全地代理凭证，使其能够访问外部世界。部署此代理后，你可以检查经过代理的请求，并且在未来，可以应用防火墙规则来限制通过代理的流量。

Agent Vault 项目是对一种趋势的早期洞察，我们认为包括 Anthropic、

[Brex](https://x.com/pedroh96/status/2046604993982009825) 以及一些开源项目也意识到的是，将代理与其凭证分离。

尽管我们预计 Agent Vault 的形态在未来一年会发生变化，并且还有大量工作要做，以便在代理环境中更易于设置，但我们认为这代表了在如何正确思考 AI 代理的密钥管理，以及具体地说如何为它们进行设计的人体工程学方面的根本性进步。

### 工作原理

Agent Vault 以可移植二进制文件形式提供，它同时作为服务器和命令行界面(CLI)客户端；它是一种专用服务，也可部署为 Docker 容器。你可以在本地与类似 Claude Code 的编码代理一起使用 Agent Vault，或部署到你的虚拟专用服务器(VPS)，与你自定义的代理基础设施一起运行。

如果您正在运行沙箱代理，我们建议您在靠近代理的位置部署一个 Agent Vault 实例，并为代理提供对特定保险库的访问权限（更多内容将在下文介绍）。

在 Agent Vault 中，我们介绍四个构建块：保险库、凭证、服务和代理。

- 保管库是一个用于存储凭证的安全逻辑容器，其提供的服务定义了代理如何通过它转发请求。
- 凭证是存储在保管库中的敏感值，Agent Vault 会将其附加到代理请求中。这可以是 API 密钥、数据库凭证、密码或任何其他敏感材料。
- 服务是一个主机，例如
  api.stripe.com 代理可以通过代理库访问的主机。当向库中添加服务时，您需要指定该服务的主机名和认证方案（例如 Bearer、API Key 等）；您可以指定用于服务认证的库凭证，或者省略并将代理视为直通模式。当代理发出代理请求时，代理库会将目标主机与库中的服务进行匹配，附加配置的凭证，并转发请求。
- 代理表示像 Claude Code、OpenClaw、Hermes 这样的 AI 代理，或者一个拥有自己凭证的自定义代理；如果您打算通过用户颁发的服务令牌将保险库访问权限委派给代理系统，这种构建并不总是必需的。

为了使用 Agent Vault，您首先需要创建一个保管库，向其中添加凭证，并指定哪些服务可以通过该保管库访问以及对这些服务如何进行认证。从那里，您创建一个带有代理令牌的代理，配置沙箱代理的环境以信任 Agent Vault 的 CA 证书，并设置 HTTPS\_PROXY 环境变量以指向保管库；其格式为 HTTPS\_PROXY=&lt;agent\_credential&gt;:vault@agent-vault\_url.com。这样，它会指示大多数语言的 HTTP 客户端、CLI 和运行时将流量重定向到代理，并在 TLS 层配置信任，以便代理将保管库接受为有效的上游服务。最后，您在网络层切断所有出站流量的访问，以便只有 Agent Vault 实例可从沙箱或容器化环境访问。

最终结果是这样的流程：

1. 代理调用 CLI 命令、SDK 方法、MCP 工具，或向 LLM 或 API 服务发起 API 调用，例如
   api.anthropic.com。
2. 该请求通过 Agent Vault 被自动路由，而代理对此一无所知。
3. Agent Vault 拦截请求，附加凭证，应用任何预定义规则，并将请求转发到目标。
4. 好了。请求回到代理，代理完成其工作。它从未看到底层的秘密，并且/或者必须修改其工作流程。

虽然 Agent Vault 的初步设计使用起来有些笨拙，我们本希望有更多时间来优化开发者体验，特别是在代理开始通过它转发请求的配置设置方面；但 AI 领域的发展速度极快，我们认为最好开源这项技术，并与社区合作逐步改进，使其在所有代理用例中都能无缝工作，因为每个用例都有其独特之处。

### 设计架构

在设计 Agent Vault 时，我们首先考虑的是代理通常如何在沙箱环境内外与外部服务交互；实际情况是，可用的选项太多了：API、CLI、SDK、MCP。在构建代理 vault 时，我们本可以设计另一个“MCP 网关”（剧透：我们确实用

[Agent Sentinel](https://infisical.com/docs/documentation/platform/agent-sentinel/overview)）但这只会适用于使用 MCP 的代理，而代理可能使用其他三种方法中的任何一种来调用外部服务。必须找到另一种方法，一种与接口无关的解决方案，来代理出站流量的凭证。

人们意识到，无论代理是调用 API、通过 CLI 执行命令、使用 SDK 还是调用 MCP 工具，每个请求最终都会变成一个出站 HTTPS 连接。接口在栈的上层分化，在底层汇聚。管理凭证最理想的位置是在接口之下，即在所有代理流量实际共享的那一层——HTTPS 本身。

#### 界面下方操作

因此，与引入另一个类似 SDK 的特定于接口的抽象不同，Agent Vault 在更低的一层运作，作为一个本地正向代理，代理所指向的 HTTPS\_PROXY。这只是一个你设置的环境变量，大多数运行时和工具已经能够识别它。事实上，这与 curl、Python、Node、Go 以及大多数 HTTP 客户端多年来支持的机制是相同的。

配置完成后，代理发出的每个出站请求都将经过保管库，无论其发起方式如何。需要注意的是，仅设置此环境变量并不能保证流量会通过代理，因为代理可能会取消设置该变量，这仅仅是一种用于引导合规客户端的措施；在完整部署中，必须对网络进行锁定，以确保所有出站流量都被强制通过 Agent Vault。

#### 请求实际如何流转

当代理尝试访问类似

api.stripe.com，其 HTTP 客户端使用 HTTP CONNECT 建立到 Agent Vault 的隧道。在传统代理中，该隧道保持不透明，仅转发加密流量。对于凭证代理而言，该模型失效，因为在不查看请求的情况下无法注入头信息。

为解决此问题，Agent Vault 终止 TLS。它使用本地可信证书颁发机构，将自身标识为上游服务，允许代理与它建立安全连接，并通过隧道以明文形式发送请求。

在那时，Agent Vault 可以匹配请求，剥离代理附加的任何凭证，从其加密存储中注入正确的凭证，并通过适当的验证建立到真实上游的新 TLS 连接。MITM 架构意味着，未来 Agent Vault 可以扩展类似防火墙的功能，以在参数级别分析请求并对请求采取行动。

响应沿相同路径返回，从代理的角度来看，一切都没有变化；它发出了一个正常的 HTTPS 请求并收到了一个正常的响应。区别在于它最初从未处理过凭证。

#### 为什么这有效

因为这发生在应用层之下，集成面缩减至几乎为零，而策略在任何地方都变得一致。白名单、速率限制、审计日志和每个代理凭证范围界定可以在 API、CLI、SDK 以及代理使用的任何其他接口上统一实施，无需要求这些层中的每一层都理解密钥。

有几个细节使其实用。代理在 CONNECT 握手期间通过会话令牌验证请求，确保每个请求都限定于特定的代理上下文。上游目标在连接时固定，防止请求中途重定向，并且代理的所有出站连接都通过标准 TLS 验证重新建立。用于拦截的证书颁发机构被视为敏感材料，并受到与凭证本身相同的模型保护。

所有这一切归根结底是一个简单的理念：如果一个代理无法被信任持有凭证，就不应该拥有这些凭证。

#### Agent Vault：给 AI Agent 上“保险箱”的开源方案

##### 一句话总结
Agent Vault 的核心理念是：**不要把真实密钥直接交给 Agent**，而是通过一个中间代理层代为保管和注入凭证，让 Agent 能访问外部服务，但看不到底层密钥。

##### 背景问题：传统密钥管理不适合 Agent
过去的密钥管理方式，默认程序是可预测、可控制的，因此可以直接把密钥发给应用使用。  
但 AI Agent 不一样：它具有**非确定性、易受提示注入操控**的特点，一旦被诱导，就可能主动泄露环境中的密钥，进而带来数据泄露和账号滥用风险。

##### 现有方案：能缓解，但治标不治本
很多团队会采用短期凭证、自动轮换、动态密钥等办法，降低密钥泄露后的危害。  
这些方法虽然有用，但本质上仍然默认 Agent “拿到过密钥”，所以问题没有真正解决，只是把风险窗口缩短了。

##### Agent Vault 的解法：让 Agent 永远接触不到密钥
Agent Vault 是一个开源的 HTTP 凭证代理和密钥库。  
它的思路是：**由 Agent Vault 替 Agent 持有密钥**，当 Agent 发出请求时，Agent Vault 在请求转发过程中自动附加认证信息。这样 Agent 本身无需知道密钥内容，也无法直接读取。

##### 工作机制：在 HTTPS 层统一代理
Agent Vault 部署在 Agent 附近，通常通过 `HTTPS_PROXY` 接管所有出站请求。  
无论 Agent 是通过 API、CLI、SDK 还是 MCP 调用外部服务，最终都会变成 HTTPS 请求。Agent Vault 就在这一层拦截请求、匹配目标服务、注入正确凭证，再把请求转发出去。

##### 为什么它重要
这种方式的价值在于，它把“密钥安全”从具体工具和接口中抽离出来，变成一个统一的基础设施能力。  
好处包括：
- Agent 不直接持有密钥，显著降低泄露风险
- 不依赖特定接口，适配 API、CLI、SDK、MCP 等多种场景
- 更容易统一做白名单、审计、限流和访问控制

##### 文章的核心判断
作者认为，**“凭证代理（credential brokering）”会成为 Agent 时代密钥管理的主流方向**。  
这代表一种重要转变：从“把密钥发给工作负载”，转向“让工作负载通过受控代理使用密钥”。

##### 当前局限
Agent Vault 仍处于研究预览阶段，还不够成熟。  
它也并非适用于所有场景，例如某些环境不会遵守 `HTTPS_PROXY`，某些供应商 SDK 还会做 TLS 证书固定，这都会影响其通用性。

##### 结论
Agent Vault 的意义不只是一个开源工具，而是提出了一种更适合 AI Agent 的安全架构：  
**Agent 负责调用，代理层负责持钥和注入。**  
这让 Agent 能继续“做事”，但不再轻易成为密钥泄露的入口。

## 结构化（1）

### 2026-04-24 04:43:40

#### Agent Vault 文章精炼总结

Agent Vault 的核心主张是：**AI 代理不应该直接拿到真实密钥**，而应通过一个专门的“凭证代理层”去访问外部服务。  
文章认为，传统的密钥管理方式适合确定性程序，但对容易被提示注入操控的 AI 代理来说，已经不够安全。

##### 1. 问题背景：传统密钥管理不适合 AI 代理

- 过去常见做法是：从集中式密钥库直接把密钥发给应用、服务器、CI/CD 等工作负载。
- 这种模式对“执行路径固定”的传统程序有效，但**对 AI 代理无效**，因为代理具有：
  - 非确定性；
  - 易受提示注入（Prompt Injection）影响；
  - 可能被诱导以开发者意料之外的方式使用密钥。
- 作者所在团队 @Infisical 表示，他们**每月处理数十亿个密钥**，因此原本以为传统密钥管理经验足够，但实践证明并非如此。

##### 2. 核心挑战：代理可能被操控，主动泄露机密

- 文章举了一个典型攻击场景：
  - 攻击者通过提示注入，让代理扫描并返回当前环境里的机密；
  - 代理如果服从，就会把密钥暴露给调用者。
- 这种攻击可能来自：
  - 被污染的 RAG 文档；
  - 工具调用中引入的恶意网页；
  - 引导代理把密钥发往攻击者控制端点的指令。
- 即使有安全护栏，也**无法完全保证代理不会泄密**。
- 一旦凭证泄露，问题就从“泄露”升级成“数据外泄”：
  - 攻击者可用泄露的凭证直接访问有价值数据；
  - 比如一个有邮件能力的代理被攻破后，攻击者可能获得能**代用户读写邮件**的凭证。

##### 3. 早期应对方式：能缓解风险，但解决不彻底

- 常见缓解方案包括：
  - 给代理发**短期凭证**；
  - 对支持 OAuth2 的服务使用 **access token / refresh token** 模式；
  - 自动轮换密钥；
  - 动态生成临时密钥。
- 这些方法的好处是：
  - 即使凭证被盗，攻击者可利用的时间窗口更短。
- 但问题在于：
  - **密钥仍然会暴露给代理本身**；
  - 只是“泄露后损害变小”，并没有从根本上消除泄露可能。

##### 4. 行业内的演进方向：把代理和凭证隔离开

- 一些领先团队已经开始自建“凭证代理”架构，让代理**从头到尾都看不到真实凭证**。
- 文中提到的案例包括：
  - **Anthropic Managed Agents**：通过专门代理服务，从保险库取凭证并附加到出站请求中；
  - **Browser Use**：采用沙箱代理到控制平面的架构，在专用服务层注入凭证；
  - **Vercel** 的凭证代理；
  - **Cloudflare** 的出站 Worker。
- 文章认为，这说明了两点：
  - 传统“直接把密钥交给工作负载”的模式，对代理不适用；
  - 这不是每个团队都该各自重复造轮子的问题。

##### 5. Agent Vault 的核心方案：凭证代理（Credential Brokering）

- Agent Vault 的基本理念是：
  - **代理永远不应该先看到底层密钥**；
  - 应由另一个可信实体替代理持有密钥；
  - 代理发请求时，由这个实体在边缘自动附加凭证。
- 换句话说：
  - 不信任代理持有密钥；
  - 只允许代理“发起访问意图”，不让它直接接触访问凭证。
- 作者认为，这是一种更适合 AI 时代的密钥管理方式。

##### 6. Agent Vault 是什么：一个开源 HTTP 凭证代理与保管库

- Agent Vault 是一个**研究预览版**的开源项目。
- 它可以作为：
  - 可移植二进制；
  - CLI 客户端；
  - 服务器；
  - Docker 容器部署。
- 支持的使用方式包括：
  - 本地搭配类似 Claude Code 的编码代理；
  - 部署到 VPS 中，配合自定义代理基础设施。
- 推荐在沙箱代理附近部署一个 Agent Vault 实例，让它成为代理访问外部网络的唯一出口。

##### 7. 它的四个核心构件

文章将 Agent Vault 抽象为 4 个基础组件：

###### 7.1 保管库（Vault）

- 是存储凭证的安全逻辑容器。
- 同时定义代理可以通过它访问哪些服务。

###### 7.2 凭证（Credential）

- 是存放在 Vault 中的敏感值。
- 可以是：
  - API Key；
  - 数据库凭证；
  - 密码；
  - 其他敏感信息。

###### 7.3 服务（Service）

- 指代理允许访问的主机，例如 `api.stripe.com`。
- 配置服务时需要指定：
  - 主机名；
  - 认证方案（如 Bearer、API Key 等）；
  - 关联使用的 Vault 凭证，或设置为直通模式。

###### 7.4 代理（Agent）

- 指 Claude Code、OpenClaw、Hermes 等 AI 代理，或自定义代理系统。
- 某些场景下，如果用用户签发的服务令牌委托访问，也可以不显式使用这一层。

##### 8. 基本工作流程：代理发请求，但看不到密钥

- 使用 Agent Vault 时，大致流程是：
  1. 创建一个 Vault；
  2. 向其中添加凭证；
  3. 配置允许访问的服务及认证方式；
  4. 为代理创建 agent token；
  5. 让沙箱环境信任 Agent Vault 的 CA 证书；
  6. 设置环境变量：  
     `HTTPS_PROXY=&lt;agent_credential>:vault@agent-vault_url.com`
  7. 从网络层切断其他出站流量，只允许访问 Agent Vault。
- 最终效果是：
  - 代理调用 CLI、SDK、MCP 工具或 API；
  - 请求自动被 Agent Vault 接管；
  - Agent Vault 注入凭证并转发；
  - 响应再返回给代理；
  - **代理始终没有直接接触真实密钥**。

##### 9. 为什么它选择在 HTTPS 层工作，而不是做另一个 MCP 网关

- 作者强调，代理访问外部服务的方式很多：
  - API；
  - CLI；
  - SDK；
  - MCP。
- 如果只做一个 MCP 网关，只能覆盖使用 MCP 的场景。
- 但无论上层接口怎样变化，最终几乎都会落到**出站 HTTPS 连接**。
- 因此 Agent Vault 选择在**接口之下、HTTPS 这一层统一处理凭证**：
  - 兼容性更强；
  - 不依赖某一种代理框架或工具协议；
  - 可以统一实施策略。

##### 10. 技术实现要点：通过本地正向代理接管 HTTPS 请求

- Agent Vault 作为一个本地正向代理工作，依赖大多数运行时都支持的 `HTTPS_PROXY` 机制。
- 文中提到，这一方式已被许多工具长期支持，例如：
  - `curl`
  - Python
  - Node
  - Go
  - 大多数 HTTP 客户端
- 但作者也明确提醒：
  - **仅设置 `HTTPS_PROXY` 不足以强制代理走代理层**；
  - 因为代理可能主动取消这个环境变量；
  - 所以还必须从网络层做封锁，确保所有出站流量只能经过 Agent Vault。

##### 11. 更底层的原理：TLS 终止与中间代理（MITM）方式

- 当代理访问例如 `api.stripe.com` 时，会先通过 HTTP CONNECT 与 Agent Vault 建立隧道。
- 普通代理只透明转发加密流量，但这样无法修改请求、也无法插入认证头。
- 所以 Agent Vault 采用的做法是：
  - **终止 TLS**；
  - 使用本地可信 CA 证书，把自己伪装成上游服务；
  - 让代理与它建立安全连接；
  - 读取明文请求后，再：
    - 匹配目标服务；
    - 去掉代理自己附带的凭证；
    - 从加密存储中注入正确凭证；
    - 再与真实上游建立新的 TLS 连接。
- 这样做的意义是：
  - 代理无需知道密钥；
  - 未来还能扩展防火墙能力，对请求参数做更细粒度检查。

##### 12. 为什么作者认为这种方式有效

- 因为它在应用层之下工作，所以：
  - 集成成本更低；
  - 不需要每个 API、CLI、SDK、MCP 都单独适配；
  - 可以统一做策略控制。
- 可统一实现的能力包括：
  - 白名单；
  - 速率限制；
  - 审计日志；
  - 按代理范围限定凭证权限。
- 文中还提到几个安全细节：
  - 代理在 CONNECT 握手阶段通过**会话令牌**认证；
  - 上游目标在连接时固定，防止请求中途被重定向；
  - 所有对外连接都重新经过标准 TLS 校验；
  - 用于拦截的 CA 证书本身也被视为敏感材料，并按高敏感级别保护。

##### 13. 当前状态与后续计划：开源研究预览，仍在快速演进

- Agent Vault 当前是**研究预览版**，并且已开源。
- 作者明确表示：
  - 它仍是实验性服务；
  - 未来几个月内，形态、易用性、安全性、可扩展性都可能有较大调整。
- 近期路线图包括：
  - 降低自托管门槛；
  - 更好地适配不同代理和编排场景；
  - 增强安全性；
  - 增加更多凭证能力和防火墙功能。

##### 14. 文末讨论中的重要补充

- 有评论指出：某些厂商 SDK/API 会固定 TLS 证书或公钥（certificate pinning），这会阻止这种中间代理方式。
- 作者回应的态度比较务实：
  - 承认 **这套方法并不适用于所有情况**；
  - 也有环境未必会遵守 `HTTPS_PROXY`；
  - 但他认为这是目前见过的**最通用、最正确方向的架构演进**之一。

##### 15. 一句话理解全文

- 这篇文章想表达的是：**对 AI 代理来说，真正安全的做法不是“把密钥给得更短、更快轮换”，而是“尽量根本不给代理看到密钥”**。  
- Agent Vault 就是围绕这个理念，提供了一个开源的、基于 HTTP/HTTPS 代理层的凭证保管与注入方案。
