## 正文

If you have ever had a long coding session in a coding agent like [Pi](https://pi.dev/), Claude Code, or Codex, you will have triggered a compaction. In this post we explain how compaction works and when Pi needs to compact.

#### An LLM conversation

Large language models (LLMs) have limited [context windows](https://en.wikipedia.org/wiki/Context_window). The context window is what the model can "see" while producing a response. The [transformer architecture](https://en.wikipedia.org/wiki/Transformer_%28deep_learning%29) used by LLMs limits how much input they can process. The input for a coding agent session includes all the previous messages and tool calls, and this keeps growing as you work. Once it exceeds the context window, the LLM rejects the request.

When working interactively with a coding agent like Pi, the agent sends requests to an LLM and receives responses. Each request includes a system prompt, loaded files such as [`AGENTS.md`](https://agents.md/), tool definitions, and the conversation history.

A coding agent's first LLM request contains this initial context, along with a first user message.

```
request 1:
[system][tools][user]
```

This starts a turn. The LLM may first return an assistant message containing tool calls. The agent program executes them and sends a new request to the LLM containing the complete conversation, now including the tool results. We get back another assistant message. The turn is finished when the assistant has completed generating output.

```
after request 1:
[system][tools][user][assistant: tool call][tool result][assistant]
                     <------------------->     ^        <--------->
                     returned by LLM           |        returned by LLM
                                               |
                                     produced by the agent
```

We continue working, and send another message.

```
request 2:
[system][tools][user][assistant: tool call][tool result][assistant][user]
                                                                     ^
                                                               new user message
```

Each turn expands the conversation. Eventually, the history exceeds the context limit. The next request then returns an error such as `Request exceeds the maximum size`.

```
[system][tools][user][assistant][....][tool result][user]
                                                      ^
                                             exceeds context window
```

#### Handling context overflow

When we cannot continue with the existing conversation as-is, we have two choices.

1. We can start a new, empty conversation without the accumulated context. This discards the history, including prior decisions and unresolved work. It might still be a good idea to do, because [the performance of LLM outputs decrease as the context size grows](https://www.trychroma.com/research/context-rot).
2. We can create a smaller representation of the conversation context, since we want to keep this conversation going. That is what compaction does.

#### Compaction

In theory, there are many ways to implement compaction. For example, we can write a deterministic function which keeps some of what is in the conversation and discards the rest. In practice, though, implementations of compaction use an LLM request to summarize the conversation history.

Compaction replaces part of the history with a compressed representation, leaving room for additional messages and tool calls.

```
[system][tools][compaction result][user]
                                    ^
                               new message
```

#### Pi's implementation

Let's look more closely at how Pi specifically [implements compaction](https://pi.dev/docs/latest/compaction#summary-format).

When conversations grow too long, Pi uses compaction to summarize older content while preserving recent work. Compaction is triggered when the context limit is nearing the total size of the context window. It can also be manually triggered using the `/compact` command.

Pi checks for auto-compaction after a turn ends. Until then, each request extends the existing prompt and can reuse its cached prefix. Pi may also compact mid-turn, if it encounters a context overflow error.

When compacting, Pi retains some number of recent messages unchanged.

```
before compaction:
[system + tools][older turns][recent retained messages]
```

The number of retained messages varies because Pi uses a [configurable token budget](https://pi.dev/docs/latest/compaction#when-it-triggers). Pi's current default of 20 thousand tokens comes out to roughly 5 to 20 turns. All the messages before this cut point are extracted and serialized, and will be summarized.

#### Pi's compaction prompt

The ideal outcome of a good summarization for a coding agent is like a handoff briefing from one shift to the next. Pi's compaction prompt focuses on the fact that there is a lot in the existing context that is no longer relevant. We should only keep around what is still important context for the next LLM request.

Pi therefore sends a different request for compaction than for regular conversation.

1. The system prompt used in the standalone compaction request is different. Instead of telling the LLM "you are an expert coding assistant", we tell the LLM ["you are a context summarization assistant."](https://github.com/earendil-works/pi/blob/47610217098d9ba8f22d223fa7c1413f9f5fd759/packages/coding-agent/src/core/compaction/utils.ts#L152-L158)
2. The user message in the compaction request is also different. It requests ["a structured summary of this conversation branch for context when returning later."](https://github.com/earendil-works/pi/blob/47610217098d9ba8f22d223fa7c1413f9f5fd759/packages/coding-agent/src/core/compaction/compaction.ts#L463-L498) The prompt specifies sections for goal, progress and key decisions.
3. It's a standalone request that doesn't use any of the existing conversation history, which means it can use a different LLM model without incurring any unnecessary cost.

The result of the compaction is appended to the Pi session as a compaction entry, and the session can now continue. After the compaction request, the context has been compressed.

```
after compaction:
[system][tools][summary][recent turns][new user message]
```

There is now room in the conversation context for many more messages.

Pi stores the compaction summary as plain text in the session. This keeps the compacted context readable and [portable](https://earendil.com/posts/session-portability), since we can switch models in Pi and continue using the summary.

#### Compaction and prompt caching

[Prompt caching](https://earendil.com/posts/prompt-caching) is used by LLM providers to make repeated requests in the same conversation less expensive. In an active coding session, we pay less for the context that has already been generated by the model. This caching requires an exact prefix match, so compacting a session will break the prompt cache.

```
cached before compaction:
[system][tools][older history][recent retained turns]
<-------------------- cached prefix -------------------->

first request after compaction:
[system][tools][summary][recent retained turns][new user message]
<-- reusable -->^
                |
        first changed token
                |
                +-- everything after this point must be recomputed
```

The retained turns contain the same tokens, but they now follow a different prefix. Their previous cached state therefore cannot be reused.

New requests after compaction will benefit from prompt caching again.

#### Experiment

Since Pi is extensible and malleable, you can replace its compaction with your own. To test a different compaction mechanism, ask Pi to create an extension with a custom compaction prompt.

## 结构化（1）

### 2026-08-17 05:17:46

#### Pi 的上下文压缩（Compaction）机制

Pi、Claude Code、Codex 等编程智能体在长时间工作后，会因大模型的上下文窗口有限而无法继续容纳完整对话。**Compaction 通过总结较早的内容、保留近期消息来缩短上下文，使会话能够继续。**

##### 1. 为什么需要压缩

- 大语言模型只能处理有限长度的输入，即“上下文窗口”。
- 编程智能体每次请求都会携带：
  - 系统提示词；
  - `AGENTS.md` 等已加载文件；
  - 工具定义；
  - 之前的用户与助手消息；
  - 工具调用及执行结果。
- 每轮交互都会让上下文不断增长。一旦超过模型限制，请求就会报错，例如：`Request exceeds the maximum size`。
- 此外，即使尚未达到上限，模型输出质量也可能随着上下文变长而下降。

##### 2. 上下文溢出时的两种处理方式

当原有会话无法继续时，通常有两种选择：

1. **开始全新会话**
   - 能彻底清空上下文；
   - 但会丢失之前的决策、任务进度和未解决问题。

2. **压缩现有会话**
   - 将较早的对话转化为更短的摘要；
   - 保留仍然重要的信息和近期工作；
   - 为后续消息及工具调用腾出空间。

实际实现中，Compaction 通常不是简单地机械删除消息，而是调用一次 LLM 来总结历史内容。

##### 3. Pi 如何触发 Compaction

Pi 会总结较早的内容，同时原样保留最近的工作记录。

触发方式包括：

- **自动触发**：通常在一轮对话结束后检查上下文是否接近上限；
- **溢出触发**：如果一轮尚未结束就出现上下文超限错误，Pi 也可能立即压缩；
- **手动触发**：用户可使用 `/compact` 命令。

Pi 默认使用可配置的 Token 预算决定保留多少近期消息：

- 当前默认保留约 **2 万 Token**；
- 大约相当于 **5～20 轮对话**，具体数量取决于每轮内容长度。

压缩前后的结构可简化为：

```text
压缩前：
[系统与工具][较早对话][近期消息]

压缩后：
[系统与工具][历史摘要][近期消息][新用户消息]
```

##### 4. Pi 的摘要提示词设计

Pi 把好的压缩摘要视为一次“**交接班简报**”：下一位接手者不必知道所有历史细节，只需要掌握继续工作所必需的信息。

因此，Pi 会发起一个独立的摘要请求：

- 系统角色从“专业编程助手”改为“**上下文总结助手**”；
- 用户请求要求生成“**供之后恢复工作使用的结构化会话摘要**”；
- 摘要重点包含：
  - 当前目标；
  - 已完成的进展；
  - 关键决策；
  - 后续仍需处理的事项。

该请求不直接沿用原会话历史结构，因此可以选用不同的 LLM 模型，避免不必要的成本。生成结果会作为一条 Compaction 记录追加到 Pi 会话中。

##### 5. 压缩结果如何保存

- 历史摘要以**纯文本**形式存储在 Pi 会话中；
- 近期对话仍保持原样；
- 会话因此获得更多可用上下文空间；
- 纯文本摘要具有较好的可读性和可移植性，即使之后切换模型，也能继续使用。

##### 6. Compaction 对提示词缓存的影响

LLM 服务商通常使用提示词缓存来降低连续请求的成本，但缓存要求请求拥有**完全一致的前缀**。

压缩会改变上下文前部：

```text
压缩前：
[系统][工具][旧历史][近期对话]

压缩后：
[系统][工具][摘要][近期对话]
```

虽然近期对话的文本没有变化，但它们之前的前缀已被摘要替换，因此：

- 原有缓存从第一个变化的 Token 开始失效；
- 后续内容需要重新计算；
- 第一次压缩后的请求成本可能上升；
- 此后的新请求又可以基于新前缀重新享受缓存。

##### 7. Pi 支持自定义压缩机制

Pi 具有较强的扩展性，用户可以替换默认的 Compaction 实现。例如，可以让 Pi 创建一个扩展，使用自定义的摘要提示词，从而测试不同的压缩策略、摘要格式或模型。

## 口播总结（1）

### 2026-09-17 00:25:46

在 Pi、Claude Code 或 Codex 这类编程智能体里持续工作很久，迟早会遇到一个问题：对话越来越长，最终超过大语言模型能够一次处理的范围。所谓“压缩”，就是把较早的对话整理成一份更短的摘要，同时保留最近的工作，从而让会话继续进行。

要理解压缩，先要理解“上下文窗口”。上下文窗口，就是模型生成回答时能够看到的全部输入。它不仅包括用户刚刚发出的消息，还包括系统提示词、工具定义、加载的项目文件、之前的所有对话，以及工具调用和工具返回的结果。

一次编程任务，往往还不只包含一次请求。比如，用户让智能体修改代码。模型先决定读取某个文件，于是发出工具调用。智能体程序执行工具，把文件内容返回给模型。模型可能接着搜索代码，再调用一次工具。直到模型给出完整结果，这一轮交互才算结束。

问题在于，每次请求通常都会带上完整的历史记录。随着工作继续，上下文会不断增长。等它超过模型的上限，下一次请求就会被拒绝，出现类似“请求超过最大尺寸”的错误。

这时有两种选择。

一种是直接开始新会话。这样最干净，也可能改善模型在超长上下文中的表现。但代价很明显：之前做过什么、为什么这样设计、哪些问题还没有解决，都会一起丢失。

另一种选择，就是压缩上下文。它不保留全部原文，而是为早期对话制作一个更小的替代版本。可以把它理解成换班时的工作交接：接班的人不需要重听此前的每一句话，但必须知道目标是什么，已经完成了什么，做过哪些关键决定，以及接下来还有什么问题。

理论上，压缩可以用固定规则完成。例如，只保留某些消息，删除其余内容。但实际系统通常会再调用一次大语言模型，让模型总结此前的对话。压缩完成后，较早的历史被摘要替代，最近的消息则保持原样。这样既释放了空间，也尽量延续了当前任务。

Pi 的具体做法是，在上下文即将接近容量上限时自动压缩。用户也可以通过“斜杠 compact”命令手动触发。

通常情况下，Pi 会在一轮交互结束后检查是否需要自动压缩。这样，在一轮尚未结束时，每次工具调用都可以继续沿用原来的上下文。如果某一轮进行到一半，模型突然返回上下文溢出错误，Pi 也可以在这一轮中途启动压缩。

压缩时，Pi 不会把所有内容都变成摘要。它会原样保留一部分最近消息，因为当前正在修改的代码、刚刚出现的错误和最新指令，往往需要完整细节。更早的内容才会被提取出来，交给模型总结。

保留多少近期内容，不是按固定消息数量计算，而是按 token 预算计算。token 是模型衡量文本长度的基本单位。Pi 当前的默认预算是二万个 token，大致相当于保留最近五到二十轮对话。具体能保留多少轮，取决于每一轮有多长。

用于压缩的提示词，也不同于普通的编程提示词。正常工作时，系统会告诉模型，它是一名专业的编程助手。执行压缩时，系统则会告诉模型，它是一名上下文总结助手。它的任务不是继续写代码，而是为以后恢复工作生成一份结构化交接摘要。

这份摘要重点记录几个方面：当前目标、已经取得的进展，以及关键决定。压缩提示还特别强调，旧上下文里有大量信息已经不再重要，不应该为了完整而全部保留。真正需要留下的，是下一次请求仍然会用到的信息。

这次压缩是一个独立的模型请求。需要总结的旧对话会被整理后作为材料送入，而不是继续沿用原来的完整会话结构。因此，Pi 可以选择另一个模型来完成总结，不必让主模型承担额外成本。生成的摘要会作为一条压缩记录写回 Pi 的会话。

压缩之后，新的上下文大致由系统提示、工具定义、压缩摘要，以及原样保留的最近对话组成。由于旧历史已经大幅缩短，会话又有了继续容纳新消息和工具调用的空间。

Pi 还会把摘要保存成普通文本。这一点很重要。普通文本既方便人阅读，也不依赖某个特定模型。即使之后切换模型，新模型仍然可以读取这份摘要，继续完成同一个任务。

不过，压缩并非完全没有代价。一个主要代价来自“提示缓存”。

模型服务商通常会缓存一段对话中重复出现的前缀。因为连续请求往往都从同样的系统提示、工具定义和历史记录开始，已经处理过的部分可以重复利用，从而降低成本。

但这种缓存通常要求前缀完全一致。压缩之后，原来的早期历史被换成了摘要。即使最近几轮的文字没有变化，它们前面的内容也已经不同。因此，从第一个发生变化的 token 开始，原有缓存就无法继续复用。压缩后的第一次请求，通常需要重新计算更多内容。

好消息是，这种损失主要发生在压缩切换的时候。随着压缩后的会话继续进行，新的上下文前缀再次稳定下来，后续请求又可以重新利用提示缓存。

所以，Pi 的压缩本质上是在三件事之间做平衡：避免超出上下文窗口，尽可能保留任务连续性，同时接受一次缓存失效和部分细节损失。最值得记住的是，压缩不是简单删除旧消息，而是把旧对话改写成一份面向后续工作的交接摘要。摘要是否抓住目标、进展和关键决定，直接决定了长时间编程会话能不能顺利延续。

## 深度解读（1）

### 2026-09-17 00:35:37

#### 上下文压缩不是“省 Token”，而是在重写代理的工作记忆

这篇文章真正有价值的地方，不是再次说明大模型有上下文上限，而是把编码代理的一次“压缩”拆成了可理解的工程过程：**系统提示、工具定义、已加载文件、对话和工具结果会不断累积；接近上限时，Pi 将较早的历史总结成一份交接文档，同时原样保留最近约 2 万 Token 的消息。**

这意味着，压缩并非无损整理，而是一次会影响后续判断的状态迁移。

##### 对话历史与任务状态不是一回事

未经处理的会话是一份事件日志：尝试过哪些命令、看过哪些文件、走过哪些弯路，都按时间堆积。但代理继续工作真正需要的，通常是另一种信息：当前目标、已经完成什么、为何做出某个决定、还有哪些问题未解决。

Pi 的压缩提示因此要求生成包含目标、进展和关键决策的结构化摘要，效果类似“上一班工程师给下一班的交接”。这个设计揭示了一个更普遍的问题：**长时间运行的 AI 代理，需要的不是无限保存聊天，而是持续把事件转换为可恢复的任务状态。**

更大的上下文窗口只能推迟这一步，不能消除它。历史越长，相关信息越容易被无关细节淹没；文章也指出，模型表现可能随上下文增长而下降。对复杂任务而言，“全部都看见”不等于“知道什么最重要”。

##### 压缩时机是质量、成本与连续性的三方权衡

Pi 通常在一轮结束后检查是否需要自动压缩，只有发生上下文溢出时才在轮次中途处理。这不只是实现细节：一轮内持续追加消息，可以复用模型服务商的提示缓存；一旦用摘要替换旧历史，前缀发生改变，原有缓存便失效，后续内容需要重新计算。

因此，压缩至少同时承担三种成本：不压缩会增加上下文费用并可能降低表现；压缩会丢失信息；压缩本身还会打断缓存。固定 Token 阈值只是一个容易实现的折中，未必是最佳策略。更成熟的代理应考虑任务阶段和信息密度：刚完成架构决策、仍在排查偶发故障时，旧记录的价值显然不同；长篇重复日志与一句关键约束，也不应仅按长度等价处理。

##### 真正的可靠性瓶颈，是“遗漏后无法察觉”

Pi 将摘要保存为普通文本，因此可读、可编辑，也能跨模型继续使用；压缩请求还是独立调用，可以选择更便宜或更擅长总结的模型。这些都提高了系统的可移植性。

但文章没有深入处理最危险的问题：摘要一旦漏掉隐含约束、失败原因或未完成事项，后续模型通常不知道自己缺了什么。语言流畅的摘要可能制造虚假的连续性。因此，评估压缩不能只看摘要是否简洁，而应看任务能否正确续接，例如：

- 关键决策及理由是否保留；
- 未解决问题、失败尝试和待验证假设是否可恢复；
- 文件修改、命令结果与当前环境状态是否准确；
- 摘要中的结论能否回溯到原始记录。

对产品设计而言，机会不只是“写一个更好的总结 Prompt”，而是建立一套可检查的连续性协议：把稳定约束写入项目文件，把代码状态交给 Git，把待办和决策单独保存，并允许用户在重要阶段查看、修订或确认压缩结果。其替代方案本来就包括 `AGENTS.md`、任务系统、提交记录和临时笔记；新能力只有在明显减少长任务中的失忆与返工时，才构成真实价值。

**代理的长期可靠性，最终取决于它能否把过程历史提炼成可信状态，而不是能容纳多长的聊天记录。**

## 默认总结（1）

### 2026-09-18 01:15:05

##### 一句话看懂

Pi 的“压缩（compaction）”会在对话接近上下文上限时，用 LLM 把较早内容总结成精简交接记录，同时保留近期消息，让编码会话得以继续。

##### 关键内容

- LLM 能读取的上下文有限，而系统提示、工具定义、历史消息及工具结果会不断累积；超限后，请求将直接报错。
- Pi 通常在一轮结束后自动检查是否需要压缩，也可用 `/compact` 手动触发；若一轮尚未结束就溢出，也会立即压缩。
- 压缩时，Pi 默认原样保留约 2 万 token 的近期内容（约 5—20 轮），再通过一次独立的 LLM 请求，将更早记录整理为包含目标、进展和关键决定的结构化摘要。
- 摘要以纯文本存入会话，方便切换模型；代价是原有提示缓存因前缀改变而失效，压缩后的首次请求需要重新计算，之后才会再次积累缓存。

##### 通俗解读

它类似“换班交接”：不是简单删除旧对话，而是把仍有用的信息写成交接单。不过摘要可能丢失细节，也会暂时增加调用成本。文章适合想了解 Pi 上下文管理、缓存机制或准备自定义压缩插件的用户细读；普通使用者掌握上述机制即可。
