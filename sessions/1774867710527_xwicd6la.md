## 通俗精炼（1）

### 2026-03-30 10:47:42

#### Claude Code 省 Token 的实用方法

##### 核心结论
这篇内容的重点是：**很多 token 浪费，并不是来自真正的编码任务，而是来自冗余上下文、过长输出和不必要的高强度模式**。  
作者通过调整工作流，把 token 使用量降低了 **60%**，同时没有影响开发效率。

##### 一、先定位：到底是谁在消耗 token
建议先运行 `/context` 做一次快速检查。  
它可以帮助你看清 token 主要消耗在什么地方，比如：

- 系统提示词
- MCP 工具
- memory 文件
- 默认加载的上下文内容

作者第一次检查时就发现：**还没开始写代码，35% 的上下文空间已经被占用了**。  
这说明，很多浪费发生在任务开始之前。

##### 二、精简上下文，减少“固定成本”
重点是管理好每次会话都会自动带上的内容。

###### 1. 精简 `Claude.md`
这个文件会在每次会话中加载，因此内容越多，token 消耗越高。  
可以在里面加入明确规则，例如：

- 回复尽量简洁
- 去掉不必要的客套话
- 减少无效输出

本质上，就是让模型从源头上“少说废话”。

###### 2. 管理会话内容
上下文不是越多越好。  
如果历史信息堆积太多，会持续推高 token 消耗，也会降低重点信息的密度。  
所以要定期清理和控制会话上下文。

##### 三、不要滥用高成本模式
`Opus` 和 `Ultrathink` 虽然能力强，但并不适合长期默认开启。

很多人误以为“思考越深越好”，但实际并非如此。  
更合理的方式是：

- 只在复杂任务上使用高强度模式
- 普通任务用更轻量的方式处理
- 把深度思考留给真正高价值的问题

核心原则：**把高 token 成本留给少数关键场景。**

##### 四、不要直接喂原始日志
原始命令输出往往有几千行，直接发给 Claude 很容易让单次对话 token 暴涨。  
更好的做法是：

- 先过滤日志
- 再压缩输出
- 只保留关键报错和必要信息

文中提到可使用开源工具 **RTK（Rust Token Killer）**，先对命令输出做过滤和压缩，再发送给模型。

##### 五、这套方法的本质
这套节省 token 的方法，本质上可以概括为三件事：

- **先诊断**：用 `/context` 找出浪费点
- **再瘦身**：精简默认上下文和回复风格
- **后分级**：只在必要时使用高成本模型和深度思考

##### 一句话总结
**省 token 不是靠“少用 AI”，而是靠把上下文、输出和推理强度都控制在真正需要的范围内。**

## 结构化（1）

### 2026-03-30 10:56:40

#### 文章主旨

这篇内容主要讲：如果你在使用 Claude Code 时发现 token 消耗太快，可以通过优化上下文、控制模型使用方式、压缩日志输出来显著降低成本。作者自己通过一套工作流，把 token 使用量减少了约 60%，同时没有影响开发速度。

#### 1. 先检查：到底是谁在消耗 token

- 作者建议先运行 `/context` 做一次快速自检。
- 这个命令可以直接看出 token 主要消耗在哪些部分，比如：
  - 系统提示词
  - MCP 工具
  - 内存文件
- 作者第一次检查时发现：**在还没真正开始编码前，上下文空间就已经损失了 35%**。
- 这说明很多 token 并不是花在“真正写代码”上，而是被前置上下文和配置占用了。

**通俗理解：**
就像手机流量还没开始看视频，后台程序已经先偷偷用了三分之一流量，所以第一步不是“少用”，而是先查“谁在偷跑”。

#### 2. 精简上下文：减少每次会话的固定开销

- 作者强调要认真管理上下文，尤其是精简 `Claude.md` 文件。
- 因为这个文件会在**每一次会话中都被加载**，如果内容太长，就会持续增加固定 token 成本。
- 作者建议在里面加入一条规则：要求模型尽量**简洁回答**，去掉不必要的客套话，减少无效 token。
- 除了文件内容本身，也要注意会话管理，避免把太多历史内容一直带在上下文里。

**例子：**
如果你在 `Claude.md` 里写了很多冗长规则，比如长篇风格说明、重复约束、无关背景资料，那么每次对话都会重复付费。  
更高效的做法是只保留必要规则，例如：
- 回答简洁
- 优先直接给方案
- 非必要不展开解释

#### 3. 控制模型强度：不要默认一直开“高功耗模式”

- 作者提醒：**不要过度使用 Opus 和 Ultrathink**。
- 虽然 `Ultrathink` 和 `Opus` 很强，但如果频繁开启，token 消耗会上升很快。
- 很多人默认认为“思考越多，结果越好”，但作者认为并不是所有任务都需要深度思考。
- 深度推理更适合复杂、关键、难度高的问题，而不是每个小任务都开满配置。

**通俗理解：**
这有点像电脑开“性能模式”跑所有程序。写个小脚本、改个文案也用最高档，当然会更耗资源。  
简单任务用轻量模式，复杂任务再上强模型，更省 token。

#### 4. 不要直接把原始日志丢给 Claude

- 作者特别指出：**不要直接发送原始日志或原始命令输出**。
- 因为命令行输出往往动辄**几千行**，如果原样贴进对话，一次就可能让 token 暴增。
- 解决办法是使用开源工具 **RTK（Rust Token Killer）**，先对命令输出做：
  - 过滤
  - 压缩
  - 精简
- 再把处理后的内容发给 Claude。

**例子：**
比如构建失败时，终端可能输出 3000 行内容，但真正关键的可能只有：
- 报错文件名
- 报错行号
- 最后一段堆栈信息
- 关键异常信息

如果把 3000 行全贴进去，会浪费大量 token；如果只保留核心报错，Claude 依然能定位问题，但成本低很多。

#### 5. 最终效果与核心方法总结

- 作者通过这套流程，**把 token 使用量降低了 60%**。
- 核心思路可以概括为 4 点：
  - 先用 `/context` 找出 token 消耗来源
  - 精简 `Claude.md` 和会话上下文
  - 非必要时不要滥用 `Opus` 和 `Ultrathink`
  - 日志和命令输出先压缩再发送，不要原样粘贴

#### 结论

这篇文章的重点不是“少用 Claude”，而是“更聪明地用 Claude”。真正有效的节省方式，主要来自减少无效上下文、避免过度推理，以及压缩高体积输入，这些做法既能控成本，也不会明显拖慢开发效率。
