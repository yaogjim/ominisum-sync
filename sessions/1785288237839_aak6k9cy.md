## 正文

Over the past half year or so, I’ve been writing an internal doc for our engineers trying to distill two years of Postgres battles into a somewhat cohesive document. While I love [the Postgres manual](https://www.postgresql.org/docs/18/index.html), I find it’s hard to turn to when shit hits the fan because it’s just so darn comprehensive. I thought this might be useful for others and would appreciate feedback (or other tidbits that you’ve learned running Postgres in production).

Before starting Hatchet, while I was familiar with SQL, the extent of my knowledge was basically: if a query is slow, you need an index. That’s the starting point for this doc; I’m going to assume you’re familiar with SQL basics, rows, tables, and know roughly what an index is.

*And if Claude is writing all of your queries, this might be a waste of time! I recommend [supabase/agent-skills](https://github.com/supabase/agent-skills)*

##### The simple stuff: good reads, writes and schemas

Let’s start with the basics: queries and schemas at low volume.

###### Writing a good schema

After you’re deployed, schemas are by far the hardest to change moving forward, so it’s worth spending some time on them. I’d recommend building your schema iteratively: start with a rough approximation for your tables and primary keys, then write some queries on those tables based on your application needs. You can approximate this with some questions: *Is this a high-read and/or high-write table? What are the most common filters on reads? Which columns am I updating the most?*

If you want to be more formal about it, you can look into [database normalization](https://www.digitalocean.com/community/tutorials/database-normalization) into 1NF/2NF/3NF, but I’ve found normal forms to sometimes be at odds with query efficiency and ease of use, which is critical when you’re moving fast—sometimes it’s just easier to dump data into a `jsonb` column.

My rules of thumb for schemas are:

- Use identity columns (auto-incrementing integers, slightly more performant than `bigserial`) or built-in UUIDs for primary keys
- Always use `timestamptz`
- Always use primary keys
- Use foreign keys with cascading deletes for low-volume tables, particularly where database consistency and correctness are important. Careful at higher volume.

###### Writing good read queries

Let’s start with `SELECT` queries. A useful—albeit slightly inaccurate—mental model for fast selects is: under the hood, Postgres is either going to find a single row in a table very quickly, or it’s going to read every single row in your table using something called a *sequential scan* 😞.

It’s going to find a single row very quickly when you filter by:

- An explicit index
- A unique constraint (just a special case of index)
- A primary key (these are automatically indexed in Postgres)

Indexes by default use a `btree` implementation. It’s most helpful to think of indexes as just another table in Postgres, with data stored in a specific format which is optimized for lookups (more on this later). These trees are great because finding a single row happens in approximately `log(n)` time, where `n` is the number of rows in the table—in other words, really fast.

When Postgres can’t use an index, it’ll use something called a sequential scan, or `seq scan`. Seq scans are much slower than index lookups, but modern databases are so fast at loading rows into memory that you probably won’t even notice at first: seq scans on tables with less than 20k rows are pretty much instant.

###### Writing performant joins

For inner joins, there’s rarely an argument for not using primary keys as the inner join; it usually speaks to a schema design or normalization problem. Treat `ON` clauses with the same respect as a `WHERE` clause—the same principles apply. Use an index.

###### Compound indexes and aligning ORDER BY to your indexes

Often the first slow query in your application will be a list query across a large table. Something like:

```
SELECT *
FROM documents
WHERE organization_id = <uuid>
  AND created_at >= NOW() - INTERVAL '1 day'
ORDER BY created_at DESC
LIMIT 50;
```

In this case, you can use a compound index—a sensible one might be:

```
CREATE INDEX CONCURRENTLY idx_documents_org_created
    ON documents (organization_id, created_at DESC);
```

In more complex cases, a good rule of thumb is: the `ORDER BY` columns should be the last columns in the index, and you should align columns to the ordering in the `ORDER BY`. Note that Postgres can scan btrees in both directions, so sometimes the `DESC` is irrelevant—but for compound indexes it’s good practice. More information [here](https://www.cybertec-postgresql.com/en/benefits-of-a-descending-index).

###### Writing good write queries

The premise of successful writes is:

1. **Keep transactions short.** Don’t go querying an external service in the middle of a transaction unless you have a really good reason to.
2. **Be careful of the rows you’re locking** for writing; in other words, only lock what you need. Every time you update a row, you’re taking out a lock on that row for a short period of time until the transaction commits.

As your system gets busier, you’re going to start noticing the impact of locks more. In particular, you might try to create an index at some point in the future with a simple `CREATE INDEX` command: turns out this locks your table and prevents inserts and updates! When creating an index on an existing large table, always use `CREATE INDEX CONCURRENTLY`.

###### Migrations

Getting really good at writing migrations is an important technical advantage: it helps you iterate much faster and increases your uptime. As a starting point, try to keep migrations additive (in other words, don’t delete or remove columns) and run them in a transaction wherever possible; this will make rollbacks and partial migrations much easier to deal with. As you get more advanced, you can start looking into [expand and contract](https://martinfowler.com/bliki/ParallelChange.html) migrations.

The simplest mental model for good migrations is: does this block all of my writes, or does it not? Creating an index without `CONCURRENTLY` blocks all your writes, so you might see downtime. Generally, operations which call `ALTER TABLE` should be worth a second look; for example, adding a new check constraint to a very large table can block your writes as well (unless you add it with the `NOT VALID` keyword).

###### Connection management

Every time you execute a transaction or query against your database, you’re utilizing a connection. Connections are expensive in a number of dimensions (cpu and memory), and high connection churn can lead to a lot of unnecessary resource waste, so connections should be long-lived. Connection storms (when you start using up a ton of new connections at the same time) can also lead to very hard to debug edge cases related to internal Postgres locks.

Because of all these connection footguns, external connection poolers like pgbouncer are great! If you can’t add this for whatever reason, in-memory connection poolers are a great second option. For example, because Hatchet is open-source, we don’t assume that all user databases use connection poolers, so we use [pgxpool](https://pkg.go.dev/github.com/jackc/pgx/v5/pgxpool) (an in-memory connection pool for Go) for this purpose.

##### Intermediate: the query planner, bulk updates, and autovacuum

###### Introducing the leakiest of abstractions, the query planner

At a certain point, your queries might become complex enough that a simple index won’t cut it (and you shouldn’t endlessly add indexes to your tables—they come with overhead). The queries might involve many `JOIN` statements or different types of joins where the correct path for querying the data isn’t clear.

At this point, you will need to concern yourself with the *query planner*. At best, the query planner is a [leaky abstraction](https://www.joelonsoftware.com/2002/11/11/the-law-of-leaky-abstractions/). It’s an internal implementation, and you have virtually no control over it, but you have to know its spontaneous and sometimes irrational behavior. It’s like working with an LLM!

The query planner looks at the query you pass in, and it figures out how it should translate your query into a set of internal operations in the database. For example, it might look at your query, and realize that it needs to use an index. In an ideal world, the query planner would know, for every query and set of parameters, the perfect plan to use. But the query planner is operating on limited information, and sometimes it doesn’t pick the best option.

This limited information is the table statistics. You can actually query it directly in Postgres:

```
SELECT *
FROM pg_stats
WHERE tablename = 'mytable';
```

These statistics are collected for every `ANALYZE`. This also happens when autovacuum is run (see below), so more frequent autovacuums also mean that your query statistics will be more up to date. A common reason why your query is behaving improperly is not analyzing frequently enough.

The reason I think it’s useful to view queries as binary—they either seq scan or they don’t seq scan—is: the more you micro-optimize a query, the more of a risk you take that the query planner goes rogue. If you stick to querying by primary keys and indexes, the query planner will have a much easier time.

Let’s say that there’s nothing obviously wrong in your query, but it’s still slow—how do you go about debugging this? Some Postgres database providers (like Google CloudSQL) will sample your queries and save slow ones—but many don’t. This is where `EXPLAIN ANALYZE` is your friend. This outputs the query plan for the query and executes the query (careful running this in production—you can use `EXPLAIN` without `ANALYZE` to get a query plan), and then compares its estimates based on the table statistics to the actual number of rows scanned. I usually place my sql query in a file, prefix it with `EXPLAIN (ANALYZE, COSTS, VERBOSE, BUFFERS, FORMAT JSON)` and run:

```
psql -XqAt -f explain.sql -d $DATABASE_URL > analyze.json
```

And then use [explain.dalibo.com](https://explain.dalibo.com/) to visualize the execution plan.

###### Sometimes it just makes sense to seq scan

There are cases where you think an index should be used, but the query planner is still seq scanning anyway, despite table statistics being up to date and the index being valid. In these cases, Postgres is usually estimating that the cost of the seq scan will be smaller than the cost of the index scan. Index scans do come with some overhead; indexes are stored separately from the actual data in the table (called the heap)—finding all of the rows in the heap can be expensive!

Unless you can dramatically restructure your query, you might have to accept that it’s going to seq scan, or think about something like partitioning (more on that below).

###### Writing lots of data

Let’s say your application is scaling and you need to write a lot of data fast. Each query has some overhead associated with it (separate from the connection overhead we talked about before): this includes the round-trip time to the database, the time it takes the internal application connection pool to acquire a connection, and the time it takes Postgres to process the query (including a set of [internal Postgres locks](https://github.com/postgres/postgres/blob/master/src/backend/storage/lmgr/README) which can be bottlenecks in high-throughput scenarios).

To reduce this overhead, we can pack a batch of rows into each query. The simplest way to do this is to send all queries to the Postgres server at once in an implicit transaction (in Go, we can use `pgx` to execute a `SendBatch`). Batching is very powerful: we found that it can \~10× your throughput. I wrote more about this plus some other tips for writing data quickly [here](https://hatchet.run/blog/fastest-postgres-inserts).

###### Default autovacuum settings can kill your database

Autovacuum is a critical operation in Postgres databases that sometimes needs to be tuned, especially in high-write scenarios. The autovacuum daemon is responsible for a number of things, including cleaning up dead tuples and managing transaction ids.

What’s a *dead tuple*? A tuple is an instance of a row on the filesystem. Every time you update or delete a row, a version of that row is left in Postgres until all transactions which started before that row was updated or deleted have committed or rolled back. These rows which can no longer be read by any transactions are *dead tuples*.

If you’re writing data quickly enough, sometimes autovacuum can’t keep up, which will get you into a very unhealthy state, very quickly. You’ll see this when you query for active processes on the database:

```
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    query_start,
    now() AS now,
    state,
    now() - query_start AS duration,
    LEFT(query, 200) AS query
FROM pg_stat_activity
WHERE state != 'idle'
  AND query NOT ILIKE '%pg_stat_activity%'
ORDER BY duration DESC;
```

If you see an autovacuum query running for more than \~1 hour, you might want to consider changing your autovacuum settings! See [this article](https://www.cybertec-postgresql.com/en/tuning-autovacuum-postgresql/) for more information.

It’s worth monitoring this: if you use up all transaction ids in the system before they can be reclaimed by autovacuum, you’ll reach a dreaded state called **transaction id wraparound**. This will mean a big chunk of downtime.

###### Other types of bloat

Besides dead tuples, there are two other kinds of bloat you’ll often encounter in a busy Postgres system:

1. Table bloat caused by partially filled pages. Postgres stores rows on pages on disk, each of which are 8kb in size. When Postgres can’t fit new rows onto an existing page, it creates a new one. But when dead tuples are reclaimed, this can lead to pages not being entirely filled, which can increase the disk usage of Postgres, sometimes significantly. The best way to avoid table bloat is by tuning autovacuum before you’re bloated. But there are some extensions to help with bloated tables, like `pg_repack`, because the built-in Postgres `VACUUM FULL` is rarely a good idea. Note that Postgres 19 is getting `REPACK...CONCURRENTLY`, which I haven’t tested, but seems like potentially a good solution for concurrent table repacking.
2. Index bloat is a special case of table bloat, and is similarly solved by good autovacuum settings. But Postgres has a built-in command for dealing with this, which is `REINDEX INDEX CONCURRENTLY`.

##### Some advanced stuff

I wanted to end with a set of advanced Postgres features which have been particularly useful for us at Hatchet.

###### FOR UPDATE SKIP LOCKED

The best way to think about this Postgres feature is that it reserves the rows that you’re selecting for use in your transaction without interfering with other queries. We use it primarily for implementing our [job queue](https://hatchet.run/blog/multi-tenant-queues); a single-query queue in Postgres can be implemented like this:

```
-- name: PopTasks :many
WITH eligible_tasks AS (
    SELECT *
    FROM tasks
    WHERE status = 'QUEUED'
    ORDER BY id ASC
    FOR UPDATE SKIP LOCKED
    LIMIT 100
)
UPDATE tasks
SET status = 'RUNNING'
FROM eligible_tasks
WHERE tasks.id = eligible_tasks.id
RETURNING tasks.*;
```

It’s also very useful in cases where you’re doing many independent updates of rows, or you’re managing leases on objects in your system across many instances of your application (for example, we use this to distribute tenant leases across Hatchet engines).

###### Partitioning

Postgres has built-in partitioning which allows you to subdivide your tables based on row values, like timestamps or hashes. This can be incredibly useful for time-series data (in our case, historical task data) because:

1. Each partition can be autovacuumed independently, allowing you to scale up autovacs on your table
2. Deleting old data is near-instant—you simply drop the table partition, rather than iterating through rows

Partitioning does come with drawbacks: there can be overhead on read queries if Postgres doesn’t prune partitions during the planning phase (something that Postgres has gotten much better at in recent releases).

I’ve written more about our experience with partitioning [here](https://hatchet.run/blog/postgres-partitioning).

###### Tricks for large table migrations

(note that this isn’t referring to a database migration, but rather moving large amounts of data from one table to another, which we find ourselves doing a few times a year)

If you try to migrate really large tables, it can take many hours to copy data in a single transaction. This isn’t good—long-running transactions prevent autovacuum from doing its job properly, and therefore make the entire system bloated with dead tuples. Also if you want to keep writing to the old tables, the new table won’t see the new data.

So we need to figure out how to migrate data safely without a transaction, with new writes (after the migration has started) being copied to the new table. One of the tricks we’ve learned is to use Postgres triggers and run a large batched backfill outside of a transaction, using unique constraints on the primary key to prevent duplicate writes.

#### Postgres 生产环境生存指南：从索引到高并发扩展

##### 一句话总结

Postgres 扩展的关键，不只是“慢查询加索引”，而是系统性管理 **Schema、查询计划、事务与锁、连接、批量写入、Autovacuum、分区和在线迁移**。

---

##### 一、基础：设计好表、查询与事务

###### 1. Schema 决定长期成本

数据库上线后，Schema 往往最难修改，应根据读写模式迭代设计：

- 主键使用自增 `identity` 或原生 UUID。
- 时间字段统一使用 `timestamptz`。
- 所有表都应有主键。
- 低流量、强一致性场景可使用外键和级联删除；高流量场景需谨慎。
- 不必机械追求范式，快速迭代时可适当使用 `jsonb`。

###### 2. 读查询的核心是避免无效全表扫描

Postgres 通常通过以下方式快速定位数据：

- 主键
- 唯一约束
- 显式索引

小表的顺序扫描通常很快，但随着数据增长会迅速成为瓶颈。JOIN 的 `ON` 条件与 `WHERE` 条件同样重要，最好关联主键或有索引的字段。

###### 3. 复合索引要匹配过滤与排序

对于“按租户过滤、按时间排序”的列表查询，可建立：

```sql
CREATE INDEX CONCURRENTLY idx_documents_org_created
ON documents (organization_id, created_at DESC);
```

一般原则是：

- 过滤字段放前面。
- `ORDER BY` 字段放在复合索引后面。
- 索引方向尽量与排序方向一致。

###### 4. 写入要控制事务与锁

- 事务越短越好。
- 不要在事务中调用外部服务。
- 只锁定真正需要修改的行。
- 大表新增索引必须优先使用 `CREATE INDEX CONCURRENTLY`，避免阻塞写入。

---

##### 二、迁移与连接：避免人为制造宕机

###### 1. 数据库迁移应尽量“只增不减”

迁移应优先采用：

- 新增字段或结构，而非立即删除。
- 能放进事务的迁移尽量放进事务。
- 使用 Expand–Contract 模式分阶段升级。
- 执行 `ALTER TABLE` 前先判断是否会阻塞全表写入。
- 大表新增约束可先使用 `NOT VALID`，再异步验证。

核心判断只有一个：**这个操作会不会阻塞所有写入？**

###### 2. 连接应复用，而不是频繁创建

数据库连接消耗 CPU 和内存，连接风暴还可能触发内部锁问题。建议：

1. 优先使用 PgBouncer 等外部连接池。
2. 无法使用时，至少采用应用内连接池。
3. 保持连接长生命周期，限制最大连接数和突发创建。

---

##### 三、进阶：理解查询计划与批量写入

###### 1. 查询优化不能脱离 Query Planner

Postgres 查询规划器根据表统计信息选择索引扫描、顺序扫描和 JOIN 策略，但统计信息可能不准确或过时。

排查慢查询时应：

- 查看 `pg_stats`。
- 确保 `ANALYZE` 足够频繁。
- 使用 `EXPLAIN` 查看执行计划。
- 使用 `EXPLAIN ANALYZE` 对比预估行数与实际行数，但注意它会真正执行查询。

与其过度微调 SQL，不如优先让查询围绕主键和明确索引展开，降低规划器选错方案的概率。

###### 2. 顺序扫描不一定是错误

当查询需要返回大量数据时，索引扫描可能比顺序扫描更贵，因为索引和真实数据分别存储，回表读取存在成本。

因此，优化目标不是“消灭所有顺序扫描”，而是确认规划器的成本判断是否合理。若查询天然需要扫描大量数据，可考虑重构查询或分区。

###### 3. 高吞吐写入依赖批处理

每条 SQL 都有网络往返、连接获取和数据库内部处理开销。将多行数据批量提交，可以显著摊薄固定成本，文中实践显示吞吐量可能提升约 **10 倍**。

---

##### 四、Autovacuum：最容易被低估的生产风险

###### 1. 为什么必须调优

Postgres 更新或删除数据时，不会立即清除旧版本，而是产生“死元组”。Autovacuum 负责回收这些空间，并管理事务 ID。

高写入场景下，如果默认配置跟不上：

- 死元组持续堆积。
- 查询和磁盘使用恶化。
- 表和索引膨胀。
- 极端情况下发生事务 ID 回卷，导致严重停机。

应持续监控长时间运行的 Autovacuum；如果持续超过约一小时，需要检查配置和系统负载。

###### 2. 表与索引膨胀的处理

- 最佳方案是提前调优 Autovacuum，而不是事后治理。
- 表膨胀可考虑 `pg_repack`。
- `VACUUM FULL` 通常锁表严重，不宜轻易使用。
- 索引膨胀可使用 `REINDEX INDEX CONCURRENTLY`。

---

##### 五、高级能力：队列、分区与大表迁移

###### 1. 用 `FOR UPDATE SKIP LOCKED` 实现并发任务队列

它可以让多个 Worker 并发领取任务：已被其他事务锁定的任务会被跳过，而不是等待。

适合：

- 数据库任务队列
- 多实例任务分发
- 租约与资源抢占
- 大量相互独立的行更新

###### 2. 分区适合时序与历史数据

按时间或哈希拆分大表的主要收益：

- 各分区可独立执行 Autovacuum。
- 删除历史数据时可直接删除分区，速度远快于逐行删除。
- 降低单表持续膨胀的压力。

代价是查询规划更复杂；如果无法有效进行分区裁剪，读取可能产生额外开销。

###### 3. 大表迁移不要使用单个超长事务

超长事务会阻碍 Autovacuum，并导致新旧表数据不同步。更安全的方式是：

1. 通过 Trigger 将迁移期间的新写入同步到新表。
2. 在事务外分批回填历史数据。
3. 使用主键唯一约束避免重复写入。
4. 完成校验后再切换读写流量。

---

##### 最终实践清单

- Schema 围绕真实读写模式设计。
- 查询优先走主键、索引和合理的复合索引。
- 保持事务短小，严格控制锁范围。
- 在线建索引使用 `CONCURRENTLY`。
- 使用连接池，避免连接风暴。
- 用 `EXPLAIN` 和统计信息定位慢查询。
- 高吞吐写入优先批处理。
- 持续监控并调优 Autovacuum。
- 时序大表考虑分区。
- 大表迁移采用触发器、批量回填和唯一约束。

> 核心理念：Postgres 的生产稳定性，来自对“阻塞、锁、膨胀和后台维护”的持续管理，而不是不断增加索引。

## 结构化（1）

### 2026-07-30 09:21:27

#### 《Postgres 生存指南》精炼总结

本文总结了作者两年运行生产级 Postgres 的实战经验：性能优化不能只靠“慢查询就加索引”，还要系统处理表结构、查询计划、锁、连接、批量写入、Autovacuum、分区和大表迁移。核心原则是让查询路径尽量简单、事务尽量短，并提前防范高并发下的阻塞与膨胀。

##### 一、适用范围与 ORM 提醒

- 文章面向掌握 SQL、表、行和索引基础，但缺乏生产环境调优经验的开发者。
- ORM 在早期很方便，但规模扩大后，许多优化必须突破 ORM 抽象层并直接编写 SQL。
- 可使用 Prisma TypedSQL 等方案；Hatchet 的 Go 技术栈使用 `sqlc`，兼顾原生 SQL 与类型安全。

---

##### 二、基础：设计好表结构、读写查询与连接

###### 1. 表结构是最难修改的部分

数据库上线后，Schema 往往比代码更难调整，因此应结合实际查询迭代设计：

- 表是高读、高写，还是两者都有？
- 查询最常用哪些过滤条件？
- 哪些字段更新最频繁？

规范化到 1NF、2NF、3NF 有助于保持一致性，但有时会降低查询效率和开发速度；在适当场景下，将数据放入 `jsonb` 可能更简单。

作者的经验规则：

- 主键使用 identity 自增列或 Postgres 内置 UUID；identity 通常比 `bigserial` 略高效。
- 时间字段统一使用 `timestamptz`。
- 每张表都应有主键。
- 低数据量、强调一致性的表可使用外键和级联删除；高数据量场景要谨慎，以免产生锁和性能问题。

###### 2. 高效读取：尽量让 Postgres 使用索引

可以用一个简化模型理解查询：

1. Postgres 通过索引快速找到目标行；
2. 或使用顺序扫描（Seq Scan）读取整张表。

能够快速定位数据的条件包括：

- 显式索引；
- 唯一约束，本质上也是索引；
- 主键，Postgres 会自动为其建立索引。

默认 B-tree 索引的查找复杂度约为 `log(n)`。无法利用索引时，数据库可能进行顺序扫描；不过现代数据库读取内存很快，**少于约 2 万行的表即使顺序扫描通常也几乎是即时的**。

###### 3. JOIN 条件也要重视索引

- 对内连接而言，被连接的一侧通常应通过主键关联。
- 如果 JOIN 长期不通过主键或索引完成，可能说明 Schema 或规范化设计存在问题。
- `ON` 条件应像 `WHERE` 条件一样认真优化，必要时为关联字段建立索引。

###### 4. 复合索引要匹配过滤和排序顺序

常见的大表列表查询：

```sql
SELECT *
FROM documents
WHERE organization_id = <uuid>
  AND created_at >= NOW() - INTERVAL '1 day'
ORDER BY created_at DESC
LIMIT 50;
```

可建立复合索引：

```sql
CREATE INDEX CONCURRENTLY idx_documents_org_created
ON documents (organization_id, created_at DESC);
```

经验规则：

- 过滤列通常放在前面；
- `ORDER BY` 使用的列放在索引后部；
- 索引列的排序方向尽量与 `ORDER BY` 对齐。
- B-tree 可以正向或反向扫描，因此单列索引中 `DESC` 有时并不重要，但复合索引中最好明确对应排序方式。

###### 5. 写入性能的关键：短事务、少锁行

- 事务应尽可能短。
- 除非有充分理由，不要在事务中调用外部服务，否则会让锁长期无法释放。
- 更新一行时，该行会被锁定直到事务提交，因此只锁真正需要修改的数据。
- 在已有大表上直接执行 `CREATE INDEX` 会阻塞插入和更新，应使用：

```sql
CREATE INDEX CONCURRENTLY ...
```

###### 6. 数据库迁移应减少阻塞

推荐的迁移方式：

- 尽量采用“增加式迁移”，先新增内容，不急于删除列或旧结构。
- 能放进事务的迁移尽量放进事务，便于回滚和处理部分失败。
- 更复杂的系统可以采用 expand-and-contract：先扩展新结构、兼容新旧版本，再切换并移除旧结构。

判断迁移风险时，首先问：

> 这个操作是否会阻塞所有写入？

需要特别检查：

- 未使用 `CONCURRENTLY` 的索引创建会阻塞写入。
- `ALTER TABLE` 相关操作可能持有强锁。
- 在超大表上新增检查约束可能阻塞写入，可先使用 `NOT VALID` 添加，再单独验证。

###### 7. 连接应复用，不要频繁创建

数据库连接会消耗 CPU 和内存，高频创建、销毁连接会浪费资源。“连接风暴”还可能触发难以排查的 Postgres 内部锁问题。

建议：

1. 优先使用外部连接池，如 `pgbouncer`；
2. 无法部署外部连接池时，至少使用应用内连接池；
3. Hatchet 使用 Go 的 `pgxpool`，因为其开源部署环境不能假设用户一定配置了外部连接池。

---

##### 三、中级：查询规划器、批量写入与 Autovacuum

###### 1. 查询规划器依赖统计信息，可能选错方案

复杂查询包含多个 JOIN 或多种连接方式时，单纯加索引可能不够，而且索引本身也会增加写入与存储成本。

查询规划器会把 SQL 转换成具体执行步骤，但它并不知道所有真实情况，只能根据表统计信息估算成本：

```sql
SELECT *
FROM pg_stats
WHERE tablename = 'mytable';
```

统计信息由 `ANALYZE` 收集，Autovacuum 也会触发分析。因此，查询计划异常的常见原因之一是：

- 分析不够频繁；
- 表统计信息已经过时；
- 规划器估计行数与真实行数差距过大。

作者建议尽量通过主键和明确索引查询，减少规划器“自由发挥”的空间，而不是对复杂查询进行过度微调。

###### 2. 使用 `EXPLAIN ANALYZE` 定位慢查询

`EXPLAIN ANALYZE` 会执行查询，并展示：

- 规划器预计扫描的行数；
- 实际扫描的行数；
- 使用了顺序扫描还是索引扫描；
- 各步骤的耗时和缓冲区使用情况。

作者常用：

```sql
EXPLAIN (ANALYZE, COSTS, VERBOSE, BUFFERS, FORMAT JSON)
...
```

再通过 `explain.dalibo.com` 可视化执行计划。

注意：

- `EXPLAIN ANALYZE` 会真正执行 SQL，在生产环境中应谨慎。
- 如果只想查看预计计划，可使用不带 `ANALYZE` 的 `EXPLAIN`。

###### 3. 顺序扫描不一定是错误

即使索引存在、统计信息也准确，Postgres 仍可能选择顺序扫描，因为：

- 索引与表数据分开存储；
- 索引找到位置后，还要回到实际数据区（Heap）读取记录；
- 如果查询会返回表中的大量行，反复访问 Heap 的成本可能高于直接扫描整表。

因此，有些场景应接受顺序扫描；若成本过高，则需要重构查询或考虑分区，而不是强行让数据库使用索引。

###### 4. 大量写入应使用批处理

每条 SQL 都存在固定开销，包括：

- 应用与数据库之间的网络往返；
- 从连接池获取连接；
- Postgres 解析、执行查询；
- 获取内部锁。

优化方式是把多行数据放进一次请求，或一次性发送一批查询，并在隐式事务中执行。Hatchet 的实践表明，**批处理可将吞吐量提高约 10 倍**。

###### 5. 默认 Autovacuum 配置可能拖垮数据库

Postgres 更新或删除数据时，不会立即覆盖旧记录，而是留下旧版本。所有可能读取旧版本的事务结束后，这些记录才成为“死元组（dead tuples）”，再由 Autovacuum 清理。

如果写入速度过快，Autovacuum 跟不上，会导致：

- 大量死元组堆积；
- 表和索引膨胀；
- 查询性能下降；
- 事务 ID 无法及时回收。

可通过 `pg_stat_activity` 检查正在运行的 Autovacuum。若发现一次 Autovacuum **持续超过约 1 小时**，通常应检查并调整配置。

更严重的情况是事务 ID 耗尽并发生 **transaction ID wraparound**，这可能造成大范围停机。

###### 6. 其他膨胀问题

###### 表膨胀

Postgres 将数据存放在磁盘页中，每页大小为 **8 KB**。死元组被清理后，页面可能留下无法充分利用的空洞，导致磁盘占用明显增加。

处理建议：

- 最好的方式是在膨胀发生前调好 Autovacuum。
- 已经严重膨胀时，可考虑 `pg_repack`。
- 内置的 `VACUUM FULL` 通常不是理想选择，因为锁影响较大。
- 原文提到 Postgres 19 将加入 `REPACK ... CONCURRENTLY`，可能提供并发重组方案。

###### 索引膨胀

索引膨胀是类似问题，同样应优先通过合理的 Autovacuum 避免。已经发生时，可使用：

```sql
REINDEX INDEX CONCURRENTLY ...
```

在尽量不阻塞业务的情况下重建索引。

---

##### 四、高级实践

###### 1. 用 `FOR UPDATE SKIP LOCKED` 实现并发任务领取

该功能会锁定当前事务选中的行，但自动跳过其他事务已经锁定的行，适合：

- 多个 Worker 并发领取任务；
- 独立批量更新数据；
- 多个应用实例之间分配租约。

Hatchet 的任务队列示例：

```sql
WITH eligible_tasks AS (
  SELECT *
  FROM tasks
  WHERE status = 'QUEUED'
  ORDER BY id ASC
  FOR UPDATE SKIP LOCKED
  LIMIT 100
)
UPDATE tasks
SET status = 'RUNNING'
FROM eligible_tasks
WHERE tasks.id = eligible_tasks.id
RETURNING tasks.*;
```

多个 Worker 执行这条语句时，会各自领取尚未被锁定的任务，减少重复处理和相互阻塞。

###### 2. 使用分区管理时间序列或历史数据

Postgres 可以按照时间戳、哈希等字段将一张逻辑表拆分成多个分区。对历史任务等时间序列数据尤其有用：

- 每个分区可独立执行 Autovacuum，提升清理能力；
- 删除旧数据时可直接删除整个分区，几乎瞬间完成，而不必逐行 `DELETE`；
- 单个分区更小，部分查询和维护操作更轻量。

缺点是：如果规划阶段无法正确进行分区裁剪，读取查询可能产生额外开销。不过新版本 Postgres 在这方面已有明显改进。

###### 3. 大表数据迁移要避免单个超长事务

这里指把大量数据从旧表迁移到新表，而不是普通的 Schema Migration。

若在一个事务中复制超大表，可能持续数小时，并带来两个问题：

- 长事务会阻碍 Autovacuum 清理旧版本，造成大量死元组；
- 迁移期间旧表仍有新写入，新表无法自动得到这些增量数据。

Hatchet 使用的方案是：

1. 在旧表上建立触发器，将迁移开始后的新写入同步到新表；
2. 在事务外分批回填历史数据；
3. 在主键上设置唯一约束，避免触发器写入与批量回填产生重复记录；
4. 回填完成并验证后，再切换业务流量。

---

##### 五、核心结论

- Schema 要围绕实际查询和更新模式设计，因为上线后最难修改。
- 索引应服务于过滤、JOIN 和排序，但不要无止境添加索引。
- 保持事务短小，只锁必要的行；生产大表建索引必须优先考虑 `CONCURRENTLY`。
- 通过连接池和批处理降低固定开销，批处理可能带来约 **10 倍吞吐提升**。
- 理解查询规划器，使用 `EXPLAIN ANALYZE` 对比估算与实际结果。
- 高写入系统必须主动监控和调优 Autovacuum，避免死元组、表膨胀和事务 ID 回卷。
- 更复杂的并发队列、历史数据管理和大表迁移，可分别借助 `FOR UPDATE SKIP LOCKED`、分区、触发器与分批回填实现。

## 口播总结（1）

### 2026-08-03 00:50:59

#### Postgres 生产环境生存指南

这份指南总结了 Hatchet 团队两年运行 Postgres 的实战经验。你将了解怎样设计表结构、优化读写和迁移、排查慢查询，以及如何应对自动清理、数据膨胀、分区和大表搬迁等生产问题。

##### 开始之前：不要被工具的抽象层限制

这里所说的 Postgres，就是 PostgreSQL，一种常用的关系型数据库。整份指南的出发点很朴素：查询慢了，不只是“加一个索引”这么简单，还要理解表结构、锁、查询计划和数据库内部维护机制。

如果项目使用 ORM，也就是“对象关系映射”工具，把程序对象自动转换成数据库操作，这些建议仍然有效。不过，系统规模变大以后，很多优化只有直接编写 SQL 才能完成。因此，ORM 最好允许开发者越过抽象层，在必要时使用原生 SQL。Hatchet 的 Go 技术栈使用的是 sqlc，用 SQL 生成类型安全的代码。

##### 首先，表结构要围绕真实查询来设计

核心结论是：表结构上线以后最难修改，所以要尽早根据实际读写模式反复调整，而不是只追求形式上的完美。

设计一张表时，可以先问三个问题。这张表是读得多，还是写得多？读取时最常用哪些过滤条件？哪些字段更新得最频繁？先做出大致结构和主键，再写几条真实业务查询，观察这种设计是否顺手。

更正式的方法，是参考第一、第二和第三范式，也就是把数据拆分得更规范，减少重复和依赖。但作者提醒，严格规范化有时会牺牲查询效率和开发速度。业务快速变化时，把部分结构化数据放进 jsonb 字段，也就是可以直接存储和查询 JSON 的二进制字段，反而可能更实用。

具体来说，作者有四条经验。

第一，主键可以使用 identity 自增整数，或者 Postgres 内置的 UUID。identity 与传统的 bigserial 类似，但性能略好。

第二，时间字段统一使用 timestamptz，也就是带时区信息的时间戳，减少跨时区处理中的歧义。

第三，每张表都要有主键。

第四，低数据量表可以使用外键和级联删除，优先保证一致性和正确性。但到了高并发、高数据量场景，级联操作可能带来更大的锁和性能风险，需要谨慎。

##### 接下来，读查询的关键是避免不必要的全表扫描

理解快速查询，可以先用一个略微简化的模型：Postgres 要么借助索引快速找到目标行，要么执行顺序扫描，从头到尾读取整张表。

主键、唯一约束和显式创建的索引，都能帮助数据库快速定位数据。Postgres 默认使用 B 树索引。可以把索引理解成一份按特定方式整理过的辅助数据，它专门用于查找。数据量即使增长很多倍，B 树需要增加的查找步骤也很有限。

如果无法使用索引，Postgres 可能选择顺序扫描，也叫 seq scan。它会逐行读取表，通常比索引查找慢。不过，小表上未必能感觉到差异。作者的经验是，少于大约两万行的表，即使顺序扫描，通常也接近瞬间完成。因此，优化重点应该放在不断增长的大表上。

连接查询也遵循同样的原则。对于内连接，通常应该用主键作为被连接表的匹配条件。如果做不到，往往说明表结构或规范化设计需要重新考虑。对待 JOIN 后面的 ON 条件，要像对待 WHERE 条件一样认真：尽量让匹配字段有索引。

##### 复合索引必须和过滤、排序方式配合

列表查询往往是应用里最早变慢的一类查询。比如，从文档表中筛选某个组织过去一天创建的内容，再按创建时间倒序排列，只取最新五十条。

这种情况下，可以建立复合索引，也就是一个索引同时包含多个字段。合理的顺序是先放组织编号，再放创建时间，并让创建时间与查询的倒序排列保持一致。

更一般地说，排序字段通常应该放在复合索引的最后，并与 ORDER BY 的字段顺序和方向对齐。B 树本身可以正向或反向扫描，所以单字段索引有时不必特别写明降序。但在复合索引中，明确对齐排序方向通常更稳妥。

##### 写入方面，最重要的是缩短事务和减少锁

核心结论是：事务越短越好，而且只锁真正需要修改的数据。

事务可以理解为一组要么全部成功、要么全部失败的数据库操作。不要在事务执行到一半时调用外部服务，除非确实有充分理由。外部请求一旦变慢，事务就会长时间占用连接和锁。

每次更新一行数据，Postgres 都会暂时锁住这一行，直到事务提交。系统负载较低时，这种影响不明显；并发上升以后，锁等待会迅速变成性能瓶颈。

一个典型陷阱是在已有的大表上直接执行普通的创建索引命令。这样可能锁住整张表，阻止插入和更新。正确做法是使用并发创建索引，也就是 `CREATE INDEX CONCURRENTLY`，尽量让建索引过程不阻塞正常写入。

##### 数据库迁移要优先考虑是否会阻塞所有写入

好的迁移能力可以提高迭代速度，也能减少停机时间。最基本的原则是：迁移尽量只做增加，不要立刻删除字段；可以放进事务的迁移，尽量放进事务。这样一旦失败，更容易整体回滚，也不容易留下只完成一半的状态。

判断一项迁移是否安全，可以先问一句：它会不会阻塞全部写入？

不使用并发模式创建索引，就可能阻塞写入。涉及 `ALTER TABLE` 的操作，也应该额外检查。比如，在一张非常大的表上新增检查约束，可能为了验证历史数据而长时间锁表。可以先用 `NOT VALID` 添加约束，暂时不检查已有数据，再选择合适的时间完成验证。

更复杂的场景，可以采用“先扩展、再收缩”的分阶段迁移思路，避免新旧版本切换时一次性破坏兼容性。

##### 连接不是免费的，需要复用和集中管理

每次执行查询或事务，都要占用数据库连接。连接会消耗 CPU 和内存，频繁建立和销毁连接也会造成浪费。大量新连接同时涌入，也就是所谓的“连接风暴”，还可能触发难以排查的 Postgres 内部锁问题。

因此，连接应该尽量长期复用。比较理想的方式，是使用 PgBouncer 这样的外部连接池。连接池会维护一批可重复使用的连接，而不是让每个请求都重新连接数据库。

如果无法部署外部连接池，也可以使用应用进程内的连接池。Hatchet 为了兼容不同用户环境，在 Go 服务中使用 pgxpool，避免假设所有用户都已经部署了外部连接池。

##### 更进一步，要理解查询规划器为什么会选错路线

查询复杂以后，单纯增加索引往往不够，而且索引也不能无限添加。索引会占用空间，还会增加写入和维护成本。

这时需要理解查询规划器。查询规划器是 Postgres 内部负责“决定怎样执行 SQL”的组件。它会判断使用哪个索引、以什么顺序连接表，或者是否直接顺序扫描。

问题在于，规划器并不知道数据的全部真实情况，只能根据表统计信息做估算。这些统计信息由 `ANALYZE` 收集，自动清理运行时也会更新。统计信息如果过时，规划器就可能低估或高估某些条件会返回多少行，进而选择不合适的执行方案。

这也是为什么作者建议，尽量围绕主键和清晰的索引写查询。查询越依赖细微的成本估算，规划器临时改变方案的风险就越高。

如果查询看起来没有明显错误，却依然很慢，可以使用 `EXPLAIN ANALYZE`。它会真正执行查询，并展示执行计划，同时比较规划器预计扫描的行数和实际扫描的行数。这里要特别小心：因为它会执行 SQL，在生产环境运行修改类语句可能造成实际影响。如果只想查看估算计划，可以使用不带 `ANALYZE` 的 `EXPLAIN`。

##### 有时候，顺序扫描反而是合理选择

即使索引有效，统计信息也很新，Postgres 仍可能坚持顺序扫描。这不一定是错误。

原因是，索引和真实表数据分开存储。真实数据所在的区域常被称为 heap，也就是表的数据堆。通过索引找到很多记录以后，数据库还要回到数据堆中逐条读取。如果需要返回的行很多，这种来回查找可能比直接把整张表顺序读一遍更贵。

因此，如果无法大幅重写查询，有时就应该接受顺序扫描。再进一步，可以考虑分区，让每次查询只扫描更小的一部分数据。

##### 大量写入时，批处理可以显著提升吞吐量

每条 SQL 都有固定开销，包括应用和数据库之间的往返时间、从连接池获取连接的时间，以及 Postgres 解析和执行查询、获取内部锁的时间。

减少这些开销的有效方式，是把多行数据打包进一次请求，而不是每行发送一条查询。也可以一次把一批操作发送给 Postgres，在隐式事务中处理。

Hatchet 的实践发现，批处理可以把写入吞吐量提高到原来的大约十倍。在 Go 中，他们使用 pgx 的批量发送能力。这个案例说明，性能问题不一定出在单条插入本身，也可能出在大量重复的网络和调度开销上。

##### 更重要的是，默认自动清理设置可能拖垮数据库

Autovacuum，也就是自动清理，是 Postgres 最关键的后台维护机制之一。高写入场景下，默认配置不一定够用。

要理解它，先要知道“死元组”。元组可以简单理解为数据行在磁盘上的一个版本。Postgres 更新或删除一行时，旧版本不会马上消失，因为较早开始的事务可能还需要读取它。等所有相关旧事务结束后，这个版本就不再可能被读取，成为死元组。

Autovacuum 会清理这些死元组，同时回收和管理事务编号。如果写入和更新速度太快，自动清理可能跟不上，数据库会在很短时间内积累大量无效数据。

作者建议持续查看数据库中的活动进程。如果发现一次自动清理已经运行了一个小时以上，就应该考虑检查并调整配置，而不是任由它持续堆积。

更危险的问题是事务编号回绕。Postgres 的事务编号数量有限，如果旧编号来不及被自动清理回收，最终可能进入回绕风险状态。为了保护数据，数据库可能被迫限制操作，造成大范围停机。

##### 自动清理跟不上，还会带来表和索引膨胀

除了死元组，繁忙的 Postgres 系统还常见两种空间膨胀。

第一种是表膨胀。Postgres 把数据存放在磁盘页面中，每页大小是八 KB。当前页面放不下新行时，就会创建新页面。死元组被清理后，原来的页面可能只剩一部分有效数据，却仍然占用完整空间。时间久了，磁盘使用量会显著增加。

避免表膨胀的最好办法，是在膨胀发生前调好自动清理。已经严重膨胀时，可以考虑 pg_repack 之类的扩展来重新整理表。内置的 `VACUUM FULL` 通常会带来较强的锁定影响，所以作者认为它很少是理想选择。Postgres 十九计划加入并发重整能力，但作者尚未实际测试。

第二种是索引膨胀，本质上与表膨胀类似。除了提前调好自动清理，还可以使用 `REINDEX INDEX CONCURRENTLY`，在尽量不影响业务的情况下并发重建索引。

##### 高级能力之一：跳过已锁定的数据，构建并发任务队列

`FOR UPDATE SKIP LOCKED` 可以理解为：当前事务选中并预留一批数据，同时自动跳过已经被其他事务锁住的行，而不是停下来等待。

Hatchet 主要用它实现任务队列。例如，一次选出最早的一百条“排队中”任务，锁住这些任务，并跳过已经被其他工作进程领取的记录。随后，在同一条数据库操作中把状态改成“运行中”，再返回任务内容。

这样，多个工作进程可以同时领取任务，又不会重复处理同一批记录。这个能力也适合大量彼此独立的行更新，或者在多个应用实例之间分配租约。Hatchet 就用它把不同租户的租约分配给不同执行引擎。

##### 分区适合时间序列和历史数据

Postgres 内置分区功能，可以根据时间、哈希值等条件，把一张逻辑大表拆成多个物理分区。

对时间序列数据来说，分区有两个主要好处。首先，每个分区可以独立进行自动清理，维护压力不必全部集中在一张巨表上。其次，删除旧数据非常快。与其逐行删除几百万条历史记录，不如直接删除对应的旧分区。

Hatchet 把这套方法用于历史任务数据。

分区也有代价。如果查询规划阶段没有成功进行“分区裁剪”，也就是没有提前排除无关分区，读取查询就可能多出额外开销。好消息是，较新的 Postgres 版本已经明显改善了分区裁剪能力。

##### 最后，大表搬迁不要塞进一个超长事务

这里说的大表迁移，不是普通的表结构变更，而是把大量数据从一张表搬到另一张表。

如果在单个事务中复制整张巨表，操作可能持续很多小时。超长事务会阻止 Autovacuum 正常回收旧数据，造成大量死元组和系统膨胀。与此同时，如果旧表仍在接收写入，新表也无法自然获得迁移开始之后的新数据。

Hatchet 的解决办法分为三部分。

首先，使用触发器。触发器就是数据库在旧表发生写入时自动执行的逻辑，用它把迁移期间的新数据同步到新表。

接下来，不使用一个覆盖全程的巨型事务，而是在事务外进行大批量、分批次的历史数据回填。

最后，在新表主键上设置唯一约束。这样，即使触发器同步和历史回填碰到同一条数据，也能阻止重复写入。

这套方法同时解决了三个问题：避免超长事务、允许旧表继续写入，并保证新表不会出现重复记录。

##### 最值得记住的五个结论

第一，表结构要围绕真实读写模式设计。主键、时间类型和索引策略，最好在上线前认真确定。

第二，查询优化不只是增加索引。要让过滤、连接和排序方式与索引匹配，也要理解顺序扫描有时反而更便宜。

第三，事务要短，锁要少。大表建索引和修改约束时，尤其要先判断是否会阻塞全部写入。

第四，高写入系统必须重视连接池、批处理和 Autovacuum。批处理可能带来数量级的吞吐提升，而自动清理跟不上，则可能导致膨胀甚至事务编号回绕和停机。

第五，面对任务队列、历史数据和大表搬迁，可以分别考虑跳过锁定行、表分区，以及“触发器加分批回填加唯一约束”这些高级方案。它们的共同目标，都是让数据库在持续提供服务的同时完成扩展和维护。

## 深度解读（1）

### 2026-09-18 00:16:48

#### PostgreSQL 真正的扩展瓶颈：不是“慢查询”，而是失控的工作量

这篇文章的价值不在于提供某个新技巧，而是把两年生产事故压缩成一个更可靠的判断框架：**数据库是否稳定，取决于每次操作触碰多少数据、占用资源多久，以及产生的维护债务能否被及时清理。**“查询慢就加索引”只覆盖了其中很小一部分。

##### 索引不是答案，限制工作范围才是

复合索引 `(organization_id, created_at DESC)` 之所以能改善列表查询，不只是因为“有索引”，而是它同时匹配了过滤与排序，让 PostgreSQL 可以直接定位某个组织的最新记录，不必扫描、排序大量候选行。

但文章也提醒：顺序扫描并非天然错误。若查询会返回表中很大比例的数据，通过索引找到记录后再访问实际数据页，可能比连续读取整张表更贵。真正该观察的是执行计划中**估算行数与实际行数的偏差**：统计信息过期，优化器就可能基于错误世界做出正确计算。因此 `EXPLAIN ANALYZE` 与及时 `ANALYZE`，往往比继续堆索引更重要。

这也揭示了 ORM 和 AI 生成 SQL 的边界：它们能降低表达查询的成本，却不能替你理解数据分布、锁竞争和访问路径。抽象可以隐藏语法，无法消除数据库的物理约束。

##### 写入问题本质上是“时间 × 并发”的问题

文章中最值得保留的原则是：**事务越长，系统中被占用和无法回收的资源越多。**在事务里调用外部服务、一次迁移数小时、更新过多行，都会延长锁持有时间；更隐蔽的是，长事务还会阻止旧版本记录被 autovacuum 回收。

PostgreSQL 更新数据时通常不会原地覆盖，而会留下旧版本。高写入系统若产生旧版本的速度超过清理速度，就会出现表膨胀、索引膨胀，极端时甚至触发事务 ID 回卷并导致停机。因此 autovacuum 不是后台卫生工作，而是写入能力的一部分。文章给出的“一小时以上需警惕”等阈值只能作为告警线索，具体仍取决于表规模、写入速率和 vacuum 进度。

同一原则也解释了几个有效做法：批量写入通过摊薄网络往返和连接开销提升吞吐；短事务减少锁竞争；连接池抑制连接风暴；大表回填应分批执行，而不是包进一个巨型事务。作者观察到批处理可带来约 10 倍吞吐，但这是场景数据，不宜直接当成普遍结论。

##### 数据库设计也是迭代能力设计

迁移是否阻塞写入，比迁移语句能否执行更值得关注。`CREATE INDEX CONCURRENTLY`、先扩展再收缩的 schema 迁移，以及用 `NOT VALID` 延后大表约束校验，本质上都在把一次高风险切换拆成可回滚、可观察的小步骤。

分区也不只是查询优化：时间序列数据分区后，可以独立 vacuum，并通过删除分区近乎瞬时地清理历史数据。`FOR UPDATE SKIP LOCKED` 则让多个 worker 并发领取任务而不互相等待，适合任务队列和租约分配；但它适用于可跳过、可重试的工作，并不能替代所有需要严格顺序或公平性的队列系统。

对产品与技术决策而言，最重要的启发是：**数据库可扩展性很少来自某次“性能优化”，更多来自从一开始就把访问范围、事务时长、数据生命周期和无停机变更设计成明确约束。**这些约束一旦进入 schema、迁移规范和监控体系，就会直接转化为更快、更安全的产品迭代能力。

##### 一句话看懂

这是一份基于两年生产实践的 PostgreSQL“生存指南”：性能优化不只是加索引，还要同时管好查询、锁、连接、自动清理和迁移。

##### 关键内容

- **先打好基础**：按常见查询方式设计表和索引；多条件筛选与排序可使用复合索引。事务应尽量短，只锁必要行；大表建索引宜用 `CREATE INDEX CONCURRENTLY`，避免阻塞写入。
- **慢查询要看执行计划**：PostgreSQL 会根据统计信息选择索引扫描或全表扫描，后者不一定是错误。可用 `EXPLAIN ANALYZE` 对比预估与实际，但在生产环境执行需谨慎。
- **高写入场景重在批量与清理**：作者实践中，批量写入曾把吞吐量提高约 10 倍；同时必须调优并监控 autovacuum，否则“死行”堆积，严重时可能触发事务 ID 回卷并造成停机。
- **规模扩大后的工具**：`FOR UPDATE SKIP LOCKED` 可实现并发任务队列；分区表便于清理历史数据；超大表搬迁可用触发器同步新写入，再分批回填。

##### 通俗解读

索引不是万能加速器：它会增加写入和维护成本，查询命中大量数据时，全表扫描反而可能更便宜。文中的许多规则是作者的经验建议，并非所有业务都应照搬。
