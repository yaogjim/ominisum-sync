#### The Discovery

几小时前，Anthropic [宣布了为 Claude 开发的生成式用户界面](https://x.com/claudeai/status/2032124273587077133) 。交互式小部件——滑块、图表、动画——在 claude.ai 的对话中内联渲染。不是图片，也不是代码块，而是在聊天中运行 JavaScript 的动态 HTML 应用。

这并不令人意外。Vercel 和其他公司已经推动生成式 UI 有一段时间了，我知道 Anthropic 也会在这方面有所动作。这也不是我第一次深入研究 Anthropic 的实现细节——我之前已经 逆向工程了他们的沙箱架构 ，并撰写过关于他们 沙箱 的文章。

我带着一个明确的目的访问了 claude.ai：了解他们是如何确切实现的。我最终为 [pi](https://github.com/badlogic/pi-mono) ，这个基于终端的编码代理，构建了我自己的版本。

#### 第一部分：询问 Claude 关于其自身的用户界面

##### The Tool, Not the Markdown

我的第一个假设是错误的。我以为 Claude 在其 Markdown 响应中输出 HTML，并且前端正在内联渲染这些 HTML。Claude 纠正了我：

> 哈，没错！你难住我了 - 这根本不是“markdown 输出的一部分”。我调用了一个名为 `show_widget` 的工具，并将 HTML 作为参数传递。

So it’s a **工具调用** . The same mechanism as web search or file operations. The HTML is a parameter payload, not streamed text. Here’s the shape Claude described:

```json
{

  "i_have_seen_read_me": true,

  "title": "snake_case_identifier",

  "loading_messages": ["First loading message", "Second loading message"],

  "widget_code": "...styles...\n...html content...\n..."

}
```

Four parameters:

- **`i_have_seen_read_me`** - 一个布尔强制函数。Claude 必须首先调用一个 `read_me` 工具来加载设计指南，然后才能使用 `show_widget` 。这是一个用于文档合规性的编译时检查。
- **`title`** - 一个用于小部件的蛇形命名（snake\_case）标识符
- **`loading_messages`** - 1-4 个短字符串，在小部件渲染时显示（即你在内容出现前看到的“Spinning up particles…”这类消息）
- **`widget_code`** - 原始 HTML 片段。不包含 `<!DOCTYPE>` ，不包含 `<html>` ，不包含 `<head>` ，不包含 `<body>` 。只包含内容。

在 Claude 可以调用 `show_widget` 之前，它必须调用 `read_me` 并带有一个 `modules` 参数：

```json
{

  "modules": ["interactive", "chart"]

}
```

可用的模块： `diagram` ， `mockup` ， `interactive` ， `chart` ， `art` 。

每个模块提供不同的设计指南 - `chart` 模块提供 Chart.js 模式， `art` 模块提供插图规则， `mockup` 模块提供 UI 组件标记。Claude 完美地描述了这一点：

> 这是一个惰性文档系统——而不是一开始就将整个设计系统导入到我的上下文中（这会让每条消息都需要消耗大量资源），而是只按需加载相关的子集。

这是 **应用于模型自身指令的渐进式披露** 。基础系统提示保持简洁；当任务需要时，专业知识按需加载。

##### 不是内嵌框架 - 实时 DOM 注入

我注意到小部件在 Claude 流式传输其响应时实时渲染（ **实时** ）。滑块和卡片在 Claude 完成生成 `widget_code` 参数之前就出现了。这不是内联框架的工作方式 - 内联框架在渲染前需要完整的 HTML。

Claude 最初声称它是一个沙箱化的 iframe，但我反驳道：

> 它在我的屏幕上实时渲染，这意味着它以某种方式处理 HTML 的部分渲染。它不是一个沙箱。

Claude 的修订分析：

> 流式行为完全暴露了这一点。如果它是一个沙箱化的 iframe，它必须等待完整的 HTML 之后才会渲染。但你看到的是，随着 token 流式传入，它就开始渲染。这只有在它是 **直接注入到父页面的 DOM 中** 时才可能发生。

The evidence:

- **CSS 变量起作用** - `var(--color-text-primary)` 正确解析，因为是同一个文档，同一个级联
- **`sendPrompt()` 可用** - 父页面上的一个函数，可被注入代码访问
- **背景是透明的** - 没有 iframe 容器，只有 DOM 中的节点
- **无加载闪烁** - 无 iframe 边框，无滚动条，无白色背景框

“沙箱”几乎可以肯定只是父页面上的一个 **内容安全策略** ，限制 `script src` 标签可以从哪些 CDN 域名加载：

- `cdnjs.cloudflare.com`
- `cdn.jsdelivr.net`
- `unpkg.com`
- `esm.sh`

##### How It Differs from Artifacts

这是这次对话中的一个关键见解：

Artifacts Visualizer (`show_widget`)

**Purpose** 交付成果 - 你保留、下载、分享的文件 内联增强 - 对话流程的一部分

**Display** 带有下载按钮的侧边栏 聊天内联，透明背景

**Libraries** 封闭的预捆绑库集合 来自 CDN 白名单的任何库，实时下载

**Persistence** Survives across sessions 短暂的，与消息相关联

**Trigger** 给我构建一个计算器 给我解释复利是如何运作的

CDN 节点至关重要。构建产物拥有固定的可用库集合。可视化器会实时从 CDN 下载 Chart.js、D3、Three.js 等所需的库。这就是 CSP 允许列表存在的原因：它是针对任意 CDN 请求的安全边界。

##### The Streaming Architecture

综合以上内容，以下是 Claude.ai 呈现生成式 UI 的方式：

1. LLM 开始生成 `show_widget` 工具调用
2. 参数 `widget_code` 按令牌逐个流式传输为 JSON 字符串块
3. 客户端对部分内容进行增量式 HTML 解析
4. DOM 节点通过 `innerHTML` 或类似方法被实时插入到页面中
5. CSS 变量会立即解析（同一文档）
6. `style` 块和 HTML 结构按出现顺序渲染
7. `脚本` 标签在流传输完成后执行一次（这就是为什么脚本放在最后）
8. CDN 库异步加载；图表/交互在脚本运行后激活

这解释了一条设计指南：“将代码结构化为有用内容尽早出现： `style` （简短）→ 内容 HTML → `script` 最后。”内容将渐进式渲染；脚本在最后激活它。

#### Part 2: Building It for Pi

##### The Problem

[Pi](https://github.com/badlogic/pi-mono) 是一个基于终端的编码代理（如果你好奇的话，我已经 对比过所有命令行界面的编码代理 ）。终端渲染文本，（现代终端还能渲染）内联图像。 **没有办法在终端中渲染带有 JavaScript 的交互式 HTML** 。当你需要 `<canvas>` 、 `<input type="range">` 或 Chart.js 时，你需要一个浏览器引擎。

My initial options were:

1. **终端图像协议** （Sixel、Kitty 图形）- 渲染 HTML 到截图，内联显示。无交互性。
2. **本地 Web 服务器 + 浏览器** - 在本地主机(localhost)上提供 HTML 服务，自动打开浏览器标签页。完全交互性，但会退出终端。
3. **TUI 近似** - 解析 HTML，渲染一个简化的文本版本。极其有限。

这些都没有匹配 Claude.ai 的体验。

##### Enter Glimpse

然后我发现了 [Glimpse](https://github.com/hazat/glimpse) ——一个原生 macOS 微 UI 库。它通过一个小型的 Swift 二进制文件和 Node.js 封装器，在 50 毫秒内打开一个 WKWebView 窗口。没有 Electron，没有浏览器，没有运行时依赖。

Key capabilities:

- **原生 WKWebView** - 完整的浏览器引擎（CSS、JS、Canvas、CDN 库）
- **50 毫秒以下的启动时间** - 感觉瞬间完成
- **双向 JSON** - `window.glimpse.send(data)` 将数据从页面发送回 Node.js
- **窗口模式** - 悬浮、无边框、透明、点击穿透、跟随光标
- **`setHTML()`** - 在运行时替换页面内容
- **`send(js)`** - 在 WebView 中执行 JavaScript

这就是缺失的部分。一个真正的浏览器引擎，可从 pi 扩展中生成，具备双向通信功能。

##### The Extension Architecture

Pi 扩展是 TypeScript 模块，可注册自定义工具、订阅生命周期事件并渲染自定义 TUI 组件。架构：

```plaintext
LLM generates show_widget tool call

            │

            ▼

   ┌───────────────────┐

   │ message_update    │──── streaming: intercept partial tool call JSON

   │    event          │     extract widget_code, open Glimpse window early

   └────────┬──────────┘     feed partial HTML as tokens arrive

            │

            ▼

   ┌───────────────────┐

   │  tool_call        │──── complete: final widget_code available

   │    event          │

   └────────┬──────────┘

            │

            ▼

   ┌───────────────────┐

   │   execute()       │──── reuse streaming window or open fresh

   │                   │     wait for user interaction or window close

   └────────┬──────────┘     return interaction data as tool result

            │

            ▼

   ┌───────────────────┐

   │  renderCall       │──── TUI: "show_widget compound interest 800×600"

   │  renderResult     │──── TUI: "✓ compound interest 800×600"

   └───────────────────┘
```

##### 两个工具，模仿 Claude 的模式

**`visualize_read_me`** - 惰性文档加载器。按模块（交互、图表、原型、美术、示意图）返回设计指南。LLM 在其第一个小部件之前静默调用此函数，仅将相关指南加载到上下文中。

```typescript
pi.registerTool({

  name: "visualize_read_me",

  label: "Read Guidelines",

  description: "Returns design guidelines for show_widget...",

  promptGuidelines: [

    "Call visualize_read_me once before your first show_widget call.",

    "Do NOT mention the read_me call to the user.",

  ],

  parameters: Type.Object({

    modules: Type.Array(StringEnum(AVAILABLE_MODULES)),

  }),

  async execute(_toolCallId, params) {

    return {

      content: [{ type: "text", text: getGuidelines(params.modules) }],

      details: { modules: params.modules },

    };

  },

});
```

**`show_widget`** - 接收 HTML/SVG 代码，通过 Glimpse 打开原生 macOS 窗口，返回用户交互数据。

```typescript
pi.registerTool({

  name: "show_widget",

  label: "Show Widget",

  description: "Show visual content in a native macOS window...",

  parameters: Type.Object({

    i_have_seen_read_me: Type.Boolean(),

    title: Type.String(),

    widget_code: Type.String(),

    width: Type.Optional(Type.Number()),

    height: Type.Optional(Type.Number()),

    floating: Type.Optional(Type.Boolean()),

  }),

  async execute(_toolCallId, params, signal) {

    const { open } = await import(GLIMPSE_PATH);

    const win = open(wrapHTML(params.widget_code), {

      width: params.width ?? 800,

      height: params.height ?? 600,

      title: params.title.replace(/_/g, " "),

    });

    return new Promise((resolve) => {

      win.on("message", (data) => {

        resolve({ content: [{ type: "text", text: `User data: ${JSON.stringify(data)}` }] });

      });

      win.on("closed", () => {

        resolve({ content: [{ type: "text", text: "Window closed." }] });

      });

    });

  },

});
```

##### Custom TUI Rendering

Pi 扩展可以提供 `renderCall` 和 `renderResult` 函数用于自定义终端显示。而不是直接输出原始 HTML 到终端中，我们展示简洁的摘要：

```typescript
renderCall(args, theme) {

  const title = args.title.replace(/_/g, " ");

  return new Text(

    theme.fg("toolTitle", theme.bold("show_widget ")) +

    theme.fg("accent", title) +

    theme.fg("dim", ` ${args.width}×${args.height}`),

    0, 0

  );

},

renderResult(result, { isPartial, expanded }, theme) {

  if (isPartial) return new Text(theme.fg("warning", "⟳ Widget rendering..."), 0, 0);

  const details = result.details;

  let text = theme.fg("success", "✓ ") + theme.fg("accent", details.title);

  if (expanded && details.messageData) {

    text += "\n" + theme.fg("dim", `  Data: ${JSON.stringify(details.messageData)}`);

  }

  return new Text(text, 0, 0);

},
```

#### 第3部分：流式挑战

##### The Goal

在 claude.ai 上，小部件会随着 tokens 流式输入而逐步渲染。HTML 在视觉上逐步构建——你会看到样式应用、结构形成，卡片和表格逐步显现，最后当 `script` 执行时，图表会弹出。

我们想要同样的体验：Glimpse 窗口应该尽早打开，并实时显示正在构建的内容。

##### How Pi Streams Tool Calls

Pi 的 AI 层（pi-ai）将来自所有服务提供商（Anthropic、OpenAI、Google 等）的流式事件归一化为统一格式：

```typescript
type AssistantMessageEvent =

  | { type: "toolcall_start"; contentIndex: number; partial: AssistantMessage }

  | { type: "toolcall_delta"; contentIndex: number; delta: string; partial: AssistantMessage }

  | { type: "toolcall_end";   contentIndex: number; toolCall: ToolCall; partial: AssistantMessage }
```

关键发现： **pi-ai 已经在每个 delta 上解析部分 JSON** 。查看 Anthropic 提供商的源代码：

```javascript
block.partialJson += event.delta.partial_json;

block.arguments = parseStreamingJson(block.partialJson);
```

`partial.content[index].arguments` 是一个渐进式解析的对象。在每一个 `toolcall_delta` 上，我们都可以读取 `arguments.widget_code` 并获取到目前为止累积的 HTML - 不需要部分 JSON 解析器库。

我们最初从 npm 安装了 `partial-json` ，在发现这一点之前立即将其卸载。

##### Attempt 1: setHTML() on Every Delta

第一种方法：监听 `message_update` ，检测 `show_widget` 工具调用的流式传输，打开一个 Glimpse 窗口，并在每次增量时调用 `win.setHTML(wrappedHTML)` 。

```typescript
pi.on("message_update", async (event) => {

  const raw = event.assistantMessageEvent;

  if (raw.type === "toolcall_delta" && streaming) {

    const block = raw.partial.content[raw.contentIndex];

    const html = block.arguments?.widget_code;

    if (html && html.length > 20) {

      streaming.window.setHTML(wrapHTML(html));

    }

  }

});
```

**结果** ：成功了！窗口打开并显示内容正在加载。但界面极其卡顿。每次调用 `setHTML()` 都会替换整个文档——整页重排、滚动位置丢失、未样式化内容闪烁。每 80 毫秒，整个页面都会闪烁。

##### 尝试 2: Shell 页面 + innerHTML 通过 JS Eval

而不是替换整个文档，我们用一个 shell HTML 页面打开了一次窗口，其中包含一个空的 `<div id="root">` 。然后我们使用 `win.send()` （在 WebView 中执行 JavaScript）来仅更新该容器的 innerHTML：

```typescript
// Shell HTML loaded once - contains a <div id="root"> and a script

// that defines window._setContent(html) to update root's innerHTML

function shellHTML() {

  return `...

    <div id="root"></div>

    // _setContent: sets root.innerHTML to the provided html

  ...`;

}

// On each delta, eval JS to update content

streaming.window.send(`window._setContent('${escapeJS(html)}')`);
```

**结果** ：更好 - 没有完全替换整个文档。但仍然卡顿。 `innerHTML` 替换所有子节点，因此每次更新时现有内容都会被销毁并重新创建。没有视觉连续性。

##### 尝试 3: 朴素的 DOM 追加

我们尝试跟踪之前的内容长度，并且只追加新的子节点：

```typescript
window._setContent = function(html) {

  var root = document.getElementById('root');

  var tmp = document.createElement('div');

  tmp.innerHTML = html;

  // Only append nodes beyond what we already have

  for (var i = root.childNodes.length; i < tmp.childNodes.length; i++) {

    var node = tmp.childNodes[i].cloneNode(true);

    node.style.animation = '_fadeIn 0.3s ease both';

    root.appendChild(node);

  }

  // Update the last existing node (it was probably incomplete)

  // ...

};
```

**结果** ：元素出现但 **从未淡入** 。问题：浏览器在解析不完整内容时会自动闭合未闭合的 HTML 标签。 `<div class="cards"><div class="c">` 变为：

```html
<div class="cards">

  <div class="c"></div>  <!-- browser auto-closed this -->

</div>
```

在下次内容更丰富的更新中，树结构发生了根本性的变化——不是“在末尾追加新节点”，而是一个完全不同的树。追加逻辑无法追踪真正新增的节点。

##### 尝试 4: morphdom - DOM 差异计算（解决方案）

我们引入了 [morphdom](https://github.com/patrick-steele-idem/morphdom) ，一个快速的 DOM 差异比较库（如 Marko 等框架使用）。morphdom 不替换 innerHTML，而是比较新旧 DOM 树并应用 **最小化补丁** ——更新已更改的节点，添加新节点，保留未更改的节点。

```typescript
function shellHTML() {

  // Returns a full HTML document with:

  // 1. A _fadeIn CSS animation (opacity 0→1, translateY 4px→0)

  // 2. morphdom loaded from cdn.jsdelivr.net

  // 3. A _setContent(html) function that:

  //    - Buffers calls until morphdom loads (_morphReady flag)

  //    - Creates a target div with the new HTML

  //    - Calls morphdom(root, target) with callbacks:

  //      onBeforeElUpdated: skip if from.isEqualNode(to)

  //      onNodeAdded: apply _fadeIn animation to new elements

  return `...`;

}
```

The morphdom callbacks:

- **`onBeforeElUpdated`** ：如果旧节点和新节点相同（ `isEqualNode` ），则完全跳过更新。现有内容在 DOM 中保持不变。
- **`onNodeAdded`** ：当真正新的节点出现在树中时，应用 CSS `_fadeIn` 动画——0.3 秒 缓动，轻微的 translateY 以实现“上滑”效果。

**加载竞态条件** ：morphdom 从 CDN 异步加载。如果 `_setContent` 在它加载之前被调用，这个调用会悄无声息地不执行任何操作。我们通过一个待处理缓冲区解决了这个问题：

```javascript
window._morphReady = false;

window._pending = null;

window._setContent = function(html) {

  if (!window._morphReady) { window._pending = html; return; }

  // ... morphdom diffing

};

// On morphdom load, flush:

onload="window._morphReady=true;

  if(window._pending){window._setContent(window._pending);window._pending=null;}"
```

##### Script Execution

`innerHTML` 不会执行 `脚本` 标签。当完整的 HTML 到达时（在 `toolcall_end` 时），我们需要激活这些脚本（Chart.js 初始化、事件监听器等）：

```javascript
window._runScripts = function() {

  document.querySelectorAll('#root script').forEach(function(old) {

    var s = document.createElement('script');

    if (old.src) { s.src = old.src; }

    else { s.textContent = old.textContent; }

    old.parentNode.replaceChild(s, old);

  });

};
```

这将每个 `脚本` 标签克隆为一个新元素（浏览器将执行该新元素），并替换惰性的原始标签。

##### String Escaping

一个微妙但关键的细节：HTML 内容通过 `win.send()` 作为 JavaScript 字符串字面量被注入。这意味着我们需要进行转义：

```typescript
function escapeJS(s: string): string {

  return s

    .replace(/\\/g, '\\\\')      // backslashes

    .replace(/'/g, "\\'")         // single quotes (our string delimiter)

    .replace(/\n/g, '\\n')        // newlines

    .replace(/\r/g, '\\r')        // carriage returns

    .replace(/<\/script>/gi, '<\\/script>');  // closing script tags

}
```

The `<\/script>` replacement prevents the browser from interpreting a literal `/script` inside our JavaScript string as closing the outer script block.

#### Part 5: What We Learned

##### Claude 的生成式 UI 比看起来更简单

它不是一个特殊的渲染引擎。它是一个返回 HTML 的工具调用，该 HTML 以令牌流的形式通过增量解析注入到 DOM 中。其复杂性在于 **设计指南** ——数千个关于颜色、排版、深色模式、流式友好结构以及何时使用每种模式的规则的令牌。

##### 2\. The read\_me 模式非常出色

按需将文档懒加载到模型的上下文中是一种值得借鉴的模式。与其使用庞大的系统提示，不如仅在任务需要时加载专业知识。我们的扩展采用了相同的架构：5个模块，有选择地加载。

##### 3\. DOM 差异计算解决流式传输的流畅性

你不能仅仅对每个令牌使用 `innerHTML` - 这会导致整页闪烁。你不能天真地追加节点 - 部分 HTML 解析会创建不可预测的树结构。你需要 DOM 差异计算（morphdom、idiomorph 或类似工具）来应用最小补丁，并仅对真正新的节点进行动画处理。

##### 4\. Glimpse 使终端代理可视化

终端不需要渲染 HTML。它需要 **生成** 一个能够渲染 HTML 的组件。Glimpse 的 50 毫秒以下的 WKWebView 窗口通过双向 JSON 通信完美地弥合了这一差距。终端仍然是终端；视觉内容则获得了一个真正的浏览器引擎。

##### 5\. pi-ai 的标准化流式事件是黄金

Pi 的 AI 层将所有提供商的流式事件标准化为 `toolcall_start` / `toolcall_delta` / `toolcall_end` ，并使用逐步解析的 `arguments` 。这意味着无论模型是 Anthropic、OpenAI、Google 还是其他任何提供商，流式处理方法的工作方式完全相同。我们不需要部分 JSON 解析器——pi-ai 已经实现了这一点。

#### 文章主旨

这篇文章讲的是：作者先逆向分析了 Claude 在聊天中 “边生成边显示交互式 UI” 的实现方式，然后把类似能力移植到了一个终端代理`pi`中。核心价值在于，它不仅解释了 Claude 的生成式 UI 是怎么工作的，还展示了如何用一套接近的架构在本地终端环境里复现这种体验。

##### 1. 作者的发现：Claude 的生成式 UI 不是 Markdown，而是工具调用

- 作者一开始以为，Claude 是在 Markdown 回复里直接输出 HTML，然后前端把 HTML 内联渲染出来。
- 实际上不是这样。Claude 自己说明：它调用的是一个名为`show_widget`的工具，HTML 只是这个工具的参数之一，而不是普通回复文本。
- `show_widget`的参数结构包含 4 个关键字段：
  - `i_have_seen_read_me`：布尔值，表示 Claude 必须先读取设计文档
  - `title`：小部件标题，使用蛇形命名
  - `loading_messages`：1-4 条加载提示语
  - `widget_code`：原始 HTML 片段，不包含完整页面结构
- 在调用`show_widget`之前，还必须先调用`read_me`，并传入模块名，例如：
  - `interactive`
  - `chart`
  - `diagram`
  - `mockup`
  - `art`
- 作者认为，这是一种 “按需加载文档” 的机制：不是把全部设计系统一次性塞进模型上下文，而是根据任务只加载相关模块，从而节省上下文资源。

##### 2. Claude 的 UI 是如何实时渲染的：不是 iframe，而是直接注入 DOM

- 作者观察到，Claude 的小部件会在回答流式生成时同步出现，也就是 HTML 还没完全生成完，滑块、卡片等内容就已经开始显示。
- 这说明它不是普通的沙箱`iframe`，因为`iframe`通常要等完整 HTML 到齐后才能渲染。
- 作者据此推断：Claude 更可能是把生成中的 HTML 直接注入到父页面 DOM 中。
- 支撑这一判断的证据包括：
  - CSS 变量能直接生效，比如`var (--color-text-primary)`能正确解析
  - 注入内容能访问父页面函数，比如`sendPrompt ()`
  - 背景透明，没有明显 iframe 容器痕迹
  - 没有 iframe 常见的白屏、边框、滚动条闪烁
- 所谓 “沙箱” 更可能只是内容安全策略（CSP），限制脚本只能从指定 CDN 加载，例如：
  - `cdnjs.cloudflare.com`
  - `cdn.jsdelivr.net`
  - `unpkg.com`
  - `esm.sh`

##### 3. 它和 Artifacts 的区别：一个是交付物，一个是对话内增强

作者特别强调了 Claude 的生成式 UI 和 Artifacts 不一样，区别主要有：

- **Artifacts**
  - 用于产出可保留、下载、分享的文件
  - 显示在侧边栏
  - 使用预打包好的封闭库集合
  - 能跨会话保留
  - 适合 “给我做一个计算器” 这种明确产物型需求
- **Visualizer / `show_widget`**
  - 是聊天过程中的内联增强
  - 显示在对话流中，背景透明
  - 可实时从 CDN 下载需要的库，比如`Chart.js`、`D3`、`Three.js`
  - 是短暂的，与当前消息绑定
  - 更适合 “解释复利怎么运作” 这类需要边讲边展示的场景

简单说：Artifacts 更像 “成品文件”，而`show_widget`更像 “边解释边展示的互动演示”。

##### 4. Claude 的流式渲染架构：先内容，后脚本

作者总结了 Claude.ai 渲染生成式 UI 的完整流程：

- LLM 开始生成`show_widget`工具调用
- `widget_code`作为 JSON 字符串的一部分，按 token 流式输出
- 客户端对部分 HTML 进行增量解析
- DOM 节点被实时插入页面
- CSS 立即生效，因为和主页面在同一个文档里
- `style`和 HTML 结构先显示出来
- `script`在流结束后再执行
- 脚本执行后，图表和交互能力才被激活
- CDN 上的库异步加载，比如`Chart.js`

这也解释了为什么设计规范要求代码顺序是：

```html
style -> HTML 内容 -> script 放最后
```

因为这样能让用户先看到结构和样式，再看到图表、动画等 “激活后的效果”。

##### 5. 作者为什么要自己做一套：终端里没法直接跑交互式 HTML

- 作者开发的`pi`是一个终端里的编码代理。
- 终端虽然能显示文本，现代终端甚至能显示图片，但无法直接运行带 JavaScript 的交互式 HTML。
- 如果要支持：
  - `&lt;canvas>`
  - `&lt;input type="range">`
  - `Chart.js`
  这类能力，就必须借助浏览器引擎。
- 作者一开始考虑过 3 种方案：
  - 终端图片协议（Sixel、Kitty 图形）：只能显示截图，不能交互
  - 本地 Web 服务器 + 浏览器：能交互，但会跳出终端
  - TUI 近似渲染：只能显示很简化的文本版 HTML，能力太弱
- 这些方案都无法复现 Claude 的体验。

##### 6. 关键突破：用 Glimpse 给终端补上浏览器能力

- 作者找到一个 macOS 原生微型 UI 库`Glimpse`，它通过 Swift 二进制和 Node.js 封装，能在**50 毫秒内**打开一个`WKWebView`窗口。
- 它的优势包括：
  - 原生`WKWebView`，支持完整浏览器能力：CSS、JS、Canvas、CDN 库
  - 启动速度低于**50ms**
  - 支持双向 JSON 通信：页面可通过`window.glimpse.send (data)`发消息回 Node.js
  - 可创建悬浮、无边框、透明、点击穿透、跟随光标的窗口
  - 支持`setHTML ()`动态替换页面内容
  - 支持`send (js)`在 WebView 中执行 JavaScript
- 作者认为，这就是终端场景里最接近 Claude 体验的缺失拼图：一个轻量、快速、可交互的浏览器内核。

  - 艺术
  - 示意图

- 当用户在窗口中操作后，可把交互数据再传回代理。

###### 7.3 终端中的展示方式

- 为避免把大量原始 HTML 直接打印在终端，作者用`renderCall` / `renderResult`自定义了更紧凑的显示方式。
- 比如终端里只显示：
  - `show_widget compound interest 800×600`
  - `✓ compound interest 800×600`

这样既保留信息，又不会污染终端界面。

##### 8. 最大难点：如何实现 “流式渲染”，而不是等全部生成完再显示

作者想复刻 Claude 的关键体验：窗口要尽早打开，内容要随着 token 到来一点点长出来。

###### 8.1 一个重要发现：`pi-ai`已经能解析部分 JSON

- `pi-ai`会把不同模型提供商的流式事件统一为：
  - `toolcall_start`
  - `toolcall_delta`
  - `toolcall_end`
- 更关键的是，它已经在每个 delta 上做了部分 JSON 解析。
- 也就是说，在`toolcall_delta`阶段，就能直接拿到：
  - `arguments.widget_code`
- 作者本来还装了`partial-json`包，后来发现根本不需要，又把它卸载了。

##### 9. 作者的 4 次尝试：从卡顿到可用

###### 9.1 尝试 1：每次增量都`setHTML ()`

- 做法：每当收到新的 HTML 片段，就调用一次`win.setHTML ()`
- 结果：能工作，但非常卡
- 原因：
  - 每次都在替换整个文档
  - 页面会整体重排
  - 滚动位置丢失
  - 出现闪烁
- 作者形容为：大约每**80ms**整页闪一次

###### 9.2 尝试 2：固定壳页面 + `innerHTML`

- 做法：先加载一个 shell 页面，里面只有一个`&lt;div id="root">`，然后不断通过 JS 更新`root.innerHTML`
- 结果：比整页替换好，但还是卡
- 原因：`innerHTML`依然会销毁并重建所有子节点，视觉连续性差

###### 9.3 尝试 3：朴素 DOM 追加

- 做法：比较新旧内容长度，只往后追加新的节点
- 结果：新增元素没有按预期淡入，也无法稳定工作
- 根本问题：浏览器在解析不完整 HTML 时会自动补全标签，导致 DOM 树结构在下一次更新时可能彻底变化
- 例如：
  ```html
  <div class="cards"><div class="c">
  ```
  浏览器可能会自动变成：
  ```html
  <div class="cards">
    <div class="c"></div>
  </div>
  ```
- 因此，“只在末尾追加节点” 这个思路并不可靠

###### 9.4 尝试 4：`morphdom`做 DOM 差异更新（最终方案）

- 作者最终引入了`morphdom`，这是一个高效的 DOM diff 库。
- 它不会粗暴替换`innerHTML`，而是比较新旧 DOM 树，然后只打最小补丁：
  - 更新变化的节点
  - 添加真正新增的节点
  - 保留未变化的节点
- 这样带来 3 个好处：
  - 页面不闪
  - 旧内容保持稳定
  - 新内容可以平滑淡入
- 作者还给新增节点加了`_fadeIn`动画：
  - 时长**0.3 秒**
  - 有轻微上移动画（`translateY`）
- 此外还处理了一个加载竞态问题：
  - `morphdom`是从 CDN 异步加载的
  - 如果`_setContent ()`调用得太早，会失效
  - 作者增加了`_pending`缓冲区，等库加载完再把内容补上

##### 10. 脚本为什么要最后执行：`innerHTML`不会运行`&lt;script>`

- 即使 HTML 渲染出来了，里面的`&lt;script>`标签也不会因为`innerHTML`插入而自动执行。
- 所以在`toolcall_end`阶段，作者会额外运行一个`_runScripts ()`：
  - 找出`#root`下所有`script`
  - 克隆成新的`script`元素
  - 用新元素替换旧元素
- 浏览器就会真正执行这些脚本，从而：
  - 初始化`Chart.js`
  - 绑定事件监听器
  - 激活动画和交互
- 完整流式流程大致是：
  - `toolcall_start`：识别到`show_widget`
  - `toolcall_delta`：每隔约**150ms**防抖后更新 HTML
  - 第一次更新时打开 Glimpse 窗口
  - 后续更新通过`morphdom`打补丁
  - `toolcall_end`：注入最终 HTML，执行脚本
  - `execute ()`：复用已有窗口，等待用户交互、关闭窗口，或**120 秒**超时

##### 11. 一个容易忽略但很关键的细节：字符串转义

- 作者通过`win.send ()`把 HTML 作为 JavaScript 字符串发送到 WebView 中执行。
- 因此必须正确转义：
  - 反斜杠`\`
  - 单引号`'`
  - 换行符
  - 回车符
  - `&lt;/script>`
- 尤其是把`&lt;/script>`替换成`<\/script>`很关键，否则浏览器可能会把它误判为外层脚本结束，导致代码注入失败。

##### 12. 作者还提取了 Claude 的真实设计指南，并复原了模块系统

- 作者通过浏览器开发者工具查看网络请求，在响应体里直接拿到了完整的`read_me`工具结果。
- 里面包含的是 Anthropic 提供给 Claude 的原始设计指南，不是 Claude 自己概括后的版本。
- 通过多次请求不同模块组合，作者提取了全部 5 个模块的内容，并统计了响应大小：
  - `["interactive"]`：**19K**
  - `["chart"]`：**22K**
  - `["mockup"]`：**19K**
  - `["art"]`：**17K**
  - `["diagram"]`：**59K**
- 所有模块共享同一个核心部分，然后再叠加各自的专用章节。
- 作者写脚本对这些内容进行拆分、去重、重组，结果得到：
  - **10 个独特章节**
  - 可以重组并几乎完全复现所有模块响应
  - **4/5**完全字节级一致
  - **1 个**只有一个空白字符差异

##### 13. 这些设计指南有多细：不是简单建议，而是成熟的生产设计系统

作者强调，这套规范非常严格，不是 “做得漂亮点” 这么简单。

###### 13.1 核心规则

- 流式优先：`style -> HTML -> script`
- 不要用渐变、阴影、模糊，因为在流式 DOM 更新时容易闪烁
- 不要写 HTML 注释`&lt;!-- comments -->`，会浪费 token，还影响流式体验
- 字重只允许**400**和**500**，禁止**600**或**700**
- 文案统一使用句首大写，避免全大写或标题式大写
- 颜色必须通过 CSS 变量使用
- 必须兼容深色模式
- CDN 只能从指定白名单加载

###### 13.2 调色板

- 有 9 个色阶，每个色阶包含**7 个色标**
- 例如：
  - 紫色：`#EEEDFE -> #CECBF6 -> #AFA9EC -> #7F77DD -> #534AB7 -> #3C3489 -> #26215C`
  - 青绿色：`#E1F5EE -> #9FE1CB -> #5DCAA5 -> #1D9E75 -> #0F6E56 -> #085041 -> #04342C`
  - 珊瑚色：`#FAECE7 -> #F5C4B3 -> #F0997B -> #D85A30 -> #993C1D -> #712B13 -> #4A1B0C`
- 还有非常具体的规则：
  - 颜色是表达 “语义”，不是单纯表示顺序
  - 每个小部件最多只用**2-3 个色阶**
  - 彩色背景上的文字必须选同色阶中的深色值，不能直接用纯黑

###### 13.3 SVG 与图表规则

- SVG 部分包含非常工程化的要求，例如：
  - ViewBox 最终检查清单
  - 字体宽度校准表
  - 预定义 CSS 类
  - 使用`context-stroke`继承描边色
  - 连接线要显式写`fill="none"`，否则 SVG 默认是黑色填充
- 图表模块是最大的一部分，甚至总结出：
  - 导致大多数图表失败的两个关键规则
  - 用 “动词导向” 而不是 “名词导向” 来选择图表表达方式  
    比如：
    - “LLMs 如何工作” 更适合说明型图表
    - “Transformer 架构” 更适合结构型图表

#### 总结

这篇文章最有价值的地方，不只是 “复刻了 Claude 的生成式 UI”，而是把背后的关键机制讲清楚了：Claude 很可能是通过工具调用 + DOM 增量注入 + 脚本延迟执行 + CDN 白名单的方式，在聊天流中实现了实时交互式 UI。作者进一步把这套思路迁移到终端代理`pi`中，借助 Glimpse 和`morphdom`，尽量复现了相似的流式体验。

从结果看，这既是一次技术逆向分析，也是一个很实用的工程实现案例：它说明生成式 UI 不一定只能出现在网页聊天里，终端工具同样可以通过 “外接浏览器能力” 获得接近的交互表现。

##### 实例：做一个 “复利计算器” 生成式 UI，并在终端代理中实时渲染

> “请用一个可交互的小部件解释复利是怎么增长的，并让我调整本金、年利率和年限。”

目标体验是：

- 模型不是输出一大段 Markdown
- 而是调用`show_widget`
- 小部件在**流式生成过程中就开始显示**
- 用户可以拖动滑块、看到图表变化
- 交互结果再回传给代理，继续对话

这正好对应你提供文章中的关键路线：

1. 先调用`visualize_read_me`加载必要设计指南
2. 再调用`show_widget`
3. 在`toolcall_delta`阶段就读取部分`widget_code`
4. 提前打开 Glimpse/WKWebView 窗口
5. 用 DOM diff 而不是整页替换，实现渐进渲染
6. 最终执行脚本，激活 Chart.js 和交互逻辑

##### 一、这个实例的推荐工具调用流程

###### 1. 先读取最小必要文档

对于 “复利计算器” 这种场景，建议只加载：

```json

}
```

原因：

- `interactive`：提供滑块、输入控件、交互规范
- `chart`：提供图表绘制规范和 Chart.js 相关模式
- 不额外加载`art`、`diagram`、`mockup`，避免上下文膨胀

###### 2. 再发起`show_widget`

```json
    "Calculating growth paths...",
    "Preparing interactive chart..."
```

这里的设计重点不是 “能跑就行”，而是要符合**流式渲染友好**的结构。

##### 二、这个实例中最好的`widget_code`组织方式

最佳顺序应始终是：


不要把脚本放前面，也不要让样式散落在内容后面。

- `style`先到，页面一出现就有基础视觉
- `HTML`随流式输出逐步成形，用户能尽早看见骨架与内容
- `script`最后执行，避免在 DOM 尚不完整时初始化失败

##### 三、基于该实例的最佳实践

##### 1. 工具设计最佳实践

- **先读文档，再出界面**：像`i_have_seen_read_me`这样的门槛很有价值，它把 “设计规范遵循” 变成了可验证约束，而不是提示词里的软要求。
- **模块按需加载**：复利计算器只需`interactive + chart`，这是典型的 “渐进式披露” 实践，可减少上下文占用与模型偏航。
- **工具语义要清晰**：`visualize_read_me`负责 “拿规范”，`show_widget`负责 “渲染界面”，职责分离能让模型更稳定。
- **返回值要为下一轮对话服务**：用户调整滑块后，返回结构化 JSON，而不是模糊文本，便于模型继续解释 “为什么 8% 和 20 年会出现这种曲线”。

---

##### 2. 流式渲染最佳实践

- **尽早打开窗口**：在`toolcall_delta`阶段一旦拿到可用的`widget_code`片段，就先创建窗口，提升 “即时感”。
- **不要每次`setHTML ()`替换整页**：这会导致重排、闪烁、滚动丢失，用户体验很差。
- **不要简单用`innerHTML`全量覆盖**：虽然比整页替换好一点，但仍然会销毁旧节点，无法保留视觉连续性。
- **优先使用 DOM diff/morphing**：例如`morphdom`，它能保留未变化节点，只更新真正变化的内容，最适合流式 HTML 场景。
- **对更新做 debounce**：例如 100–150ms。太频繁会卡顿，太慢又失去流式感，这个区间通常较平衡。

---

##### 3. HTML 结构最佳实践

- **内容优先于脚本**：先让用户看到标题、滑块、容器，再在末尾激活图表和监听器。
- **初始内容要 “可见”**：即使脚本尚未执行，也要先渲染出控件框架和说明文字，而不是空白壳子。
- **避免复杂视觉特效**：文章里提到渐变、阴影、模糊在流式 diff 中容易闪烁；像复利计算器这类工具型 UI，更应强调稳定、清晰。
- **用设计系统变量，不写死主题**：优先使用`var (--color-text-primary)`、`var (--color-background-secondary)`，保证和宿主环境风格一致。
- **脚本标签放最后**：特别是依赖 CDN 库时，这能减少初始化时机错误。

---

##### 4. 脚本执行最佳实践

- **流式阶段只更新结构，不急于执行脚本**：因为脚本如果在 HTML 未完成时运行，很容易绑定失败或重复初始化。
- **在`toolcall_end`后统一激活脚本**：这是最稳妥的激活时机。
- **重新插入`&lt;script>`以触发执行**：因为通过`innerHTML`注入的脚本默认不会执行，这一点很关键。
- **为第三方库异步加载做缓冲**：例如`morphdom`或 Chart.js 尚未加载时，应先缓存更新，等就绪后再 flush。

示意逻辑：

```js
window._pending = null;
window._morphReady = false;

window._setContent = function (html) {
  if (!window._morphReady) {
    window._pending = html;
    return;
  }
  // 执行 DOM diff
};

window._runScripts = function () {
  document.querySelectorAll ('#root script').forEach (function (old) {
    var s = document.createElement ('script');
    if (old.src) s.src = old.src;
    else s.textContent = old.textContent;
    old.parentNode.replaceChild (s, old);
  });
};
```

---

##### 5. 安全与健壮性最佳实践

- **严格限制 CDN 白名单**：像文章中那样只允许可信源，是 “允许动态加载库” 前提下的必要安全边界。
- **对注入字符串做转义**：如果通过`win.send ("window._setContent ('...')")`注入 HTML，必须转义反斜杠、引号、换行和`&lt;/script>`。
- **避免任意脚本拼接**：对模型输出的 HTML/JS，最好增加最基本的校验层，例如限制外链域名、限制危险 API。
- **设置超时和关闭兜底**：窗口关闭、120 秒超时、用户无交互，都应该能正常 resolve，不让工具调用悬挂。
- **脚本执行只做一次或可重入**：避免`toolcall_end`和`execute ()`阶段重复初始化，造成双重绑定和重复图表实例。

推荐的转义函数：

```ts
function escapeJS (s: string): string {
  return s
    .replace (/\\/g, '\\\\')
    .replace (/'/g, "\\'")
    .replace (/\n/g, '\\n')
    .replace (/\r/g, '\\r')
    .replace (/<\/script>/gi, '<\\/script>');
}
```

---

##### 6. 用户体验最佳实践

- **终端里显示摘要，不显示原始 HTML**：例如`show_widget compound interest 800×600`，这比输出大段代码更可用。
- **视觉上先给骨架，再给增强**：复利小部件应先显示标题、控件和占位区，图表稍后出现是可接受的。
- **加载文案要短、具体、有动作感**：如`Calculating growth paths...`比泛泛的`Loading...`更有体验。
- **交互回传应有意义**：例如回传`{ principal, rate, years }`，让模型继续回答 “如果把年限从 20 改到 30，增长为什么更明显”。
- **避免双开窗口**：如果流式阶段已经打开窗口，`execute ()`应复用它，而不是再打开一个新的。

##### 7. 针对这个 “复利计算器” 实例的落地建议

## 产品-技术开发实现（1）

### 2026-03-26 10:21:28

这篇内容的价值不在 “复刻了 Claude 的 UI”，而在于它揭示了生成式 UI 的一条很强的产品 / 技术路线：把 UI 当成工具调用结果，而不是文本格式化结果。

- 产品上，这是从 “生成内容” 升级到 “生成交互能力”
- 技术上，这是从 “渲染 markdown” 升级到 “流式执行一个受控前端运行时”
- 架构上，核心不是 HTML，而是`tool + streaming + constrained runtime + lazy guidelines`

**产品解读**

- `show_widget`不是展示层小技巧，而是能力边界重划：LLM 不再只回答，而是直接交付 “可操作界面”，适合解释、模拟、配置、教育、决策辅助。
- `read_me -> show_widget`是非常成熟的产品设计：先按需加载规范，再允许生成，既省上下文，又降低失控概率。这本质上是 “给模型做运行前依赖注入”。
- `Artifacts`和`Visualizer`的区分非常关键：前者是 “产物型体验”，后者是 “会话增强型体验”。很多团队做 AI UI 时把两者混在一起，结果既不适合保存，也不适合即时交互。
- 流式渲染的真正价值不是炫技，而是降低等待焦虑。用户先看到结构，再看到激活后的交互，感知延迟明显更低。
- 终端版实现说明了一个产品原则：不要执着于 “完全同形态复制”，而要找到当前载体里的 “最小可用交互宿主”。这里的`WKWebView + native shell`就是正确取舍。

**技术解读**

- 最核心判断很准：这不是 markdown inline render，而是工具参数里的`widget_code`。这决定了安全模型、流式模型、调试方式都完全不同。
- `lazy module loading`是最佳实践。把`interactive/chart/art/...`拆成模块，比把整套设计系统塞进 system prompt 更可扩展，也更便宜。
- 直接 DOM 注入而非 iframe，换来了三件事：CSS 变量共享、宿主函数调用、实时渐进渲染。但同时也引入更高安全风险，需要更强 CSP 和代码约束。
- 流式 UI 的关键不是 “每次更新 HTML”，而是 “每次做最小 DOM patch”。作者从`setHTML`到`innerHTML`再到`morphdom`，这条演进路径非常合理。
- `script`最后执行是对流式生成最友好的约束：先稳定视觉骨架，再激活行为层。这个顺序应写进生成规范，而不是靠模型自觉。

**最值得借鉴的设计模式**

- **工具化 UI 输出**
  - 不让模型在自然语言里混 HTML
  - 用强 schema 约束参数：`title/loading_messages/widget_code/size`
  - 好处：可校验、可审计、可回放、可灰度

示例：
```json
{
  "name": "show_widget",
  "input": {
    "i_have_seen_read_me": true,
    "title": "compound_interest_simulator",
    "loading_messages": ["Calculating growth...", "Rendering chart..."],
    "widget_code": "<style>...</style><div>...</div><script>...</script>",
    "width": 800,
    "height": 600
  }
}
```

- **按需加载规范**
  - 先调用`visualize_read_me (["chart"])`
  - 再允许生成图表类 widget
  - 避免把 mockup、art、diagram 全塞进上下文

最佳实践：
```ts
if (!session.loadedModules.has ("chart")) {
  await callTool ("visualize_read_me", { modules: ["chart"] });
}
await callTool ("show_widget", payload);
```

- **Shell + Incremental Patch**
  - 首次只加载一个稳定 shell
  - 后续只 patch `#root`
  - 绝不频繁整页替换

示例：
```js
window._setContent = function (html) {
  const target = document.createElement ("div");
  target.id = "root";
  target.innerHTML = html;
  morphdom (document.getElementById ("root"), target, {
    onBeforeElUpdated (from, to) {
      return !from.isEqualNode (to);
    },
    onNodeAdded (node) {
      if (node.nodeType === 1) node.style.animation = "_fadeIn .3s ease both";
    }
  });
};
```

- **脚本延迟激活**
  - 流式阶段只渲染结构和样式
  - 完整 HTML 到齐后再执行脚本
  - 避免半成品脚本报错、重复绑定、库未加载完成

示例：
```js
window._runScripts = function () {
  document.querySelectorAll ("#root script").forEach ((oldNode) => {
    const s = document.createElement ("script");
    if (oldNode.src) s.src = oldNode.src;
    else s.textContent = oldNode.textContent;
    oldNode.parentNode.replaceChild (s, oldNode);
  });
};
```

**如果我是产品 / 技术负责人，我会怎么落地**

- **场景优先级**
  - 第一批只做 3 类：`calculator/simulator`、`chart/explainer`、`form/configurator`
  - 不要一开始就开放任意 HTML 小应用生成，风险和维护成本太高

- **协议设计**
  - 把`show_widget`拆成两层：
  - `show_widget_preview`：流式视觉骨架
  - `show_widget_interactive`：最终可交互版本
  - 好处：更好控时序、脚本权限、失败回退

- **安全边界**
  - 禁止任意外链，只允许白名单 CDN
  - 禁止访问宿主敏感 API，使用显式桥接 API，如`sendPrompt`、`sendData`
  - 对 HTML 做 sanitizer；对 JS 做 capability whitelist，而非全开放

- **状态回传**
  - 不要让 widget 任意发消息，定义固定事件协议
  - 例如：`submit`, `change`, `close`, `error`

示例：
```json
{
  "type": "submit",
  "widget": "compound_interest_simulator",
  "payload": {
    "principal": 10000,
    "rate": 0.08,
    "years": 20
  }
}
```

- **失败回退**
  - widget 渲染失败时，自动退回文本解释或静态截图
  - 这是终端、多平台、弱网环境下必须有的兜底

**文章里最强的几个工程启发**

- `partial.content [index].arguments`已经是渐进解析对象，这个洞察非常重要：很多团队会重复造 partial JSON parser，浪费复杂度。
- 生成式 UI 的关键监控指标不是 “是否成功渲染”，而是：
  - 首帧时间
  - 可感知内容出现时间
  - 最终可交互时间
  - 脚本激活失败率
  - 用户交互回传率
- 设计规范里限制渐变、阴影、重字重，不是审美偏好，而是为了流式 patch 稳定性。这是 “生成式场景下的设计系统” 与普通设计系统最大的不同。

**这套方案的风险点**

- 直接 DOM 注入的安全风险高于 iframe，尤其在宿主页面暴露能力函数时
- CDN 依赖带来不可控性：版本漂移、加载失败、时延抖动
- 流式 HTML 在不完整标签状态下天然不稳定，必须依赖 diff/morph，而不能假设 “append 即可”
- widget 一旦过于复杂，会变成 “临时生成的前端应用”，调试、追踪、回归测试都会迅速变重

**最佳实践结论**

- 把生成式 UI 当 “工具协议” 做，不要当 “富文本渲染” 做
- 把设计系统拆成可按需加载的模块，不要全量塞 prompt
- 把流式更新做成 DOM patch，不要整页替换
- 把脚本执行放到最终态，不要边流边跑
- 把宿主能力做成最小桥接 API，不要让生成代码直接碰宿主环境
