构建 AI 驱动的界面通常意味着解析模型输出、制定规范以及编写胶水代码，而胶水代码在模型改变想法的那一刻就会失效。JSON Render 通过为模型提供一个严格的契约来省去这些麻烦：你定义的组件目录，以及它必须输出的规范格式。模型选择使用哪些组件、以什么顺序以及使用什么内容。你的渲染器将该输出直接映射到用户界面。

第一部分介绍了核心原语（schema、catalog、registry），并以 React 作为渲染目标。本文采用相同的架构，借助 Remotion 构建 Code Roast：一个从任何公开的 GitHub 仓库中提取真实数据并生成 Wrapped 风格吐槽视频的工具。人工智能分析该仓库，并决定包含哪些场景、按什么顺序，内容来自其实际发现的信息。每个仓库都会得到不同的结果。

如果你想先了解完整的概念背景，请 从第一部分开始 。如果你对 json-render 模型比较熟悉，并且想看到它应用到视频中，请继续阅读。

#### Setup

为了跟随本指南，请在本地设置项目：

1. Clone repo: `git clone git@github.com:kenzic/code-roast-wrapped.git`
2. Install dependancies: `cd code-roast-wrapped && npm install`
3. Switch to demo branch: `git checkout -b demo origin/demo`

演示分支已经具备 GitHub 集成、Remotion 场景组件和页面级连接。您需要添加目录、注册中心和播放器包装器。

#### Github Integration

打开 `./lib/github.ts` 。它从仓库中获取代码、提交统计、贡献者、编程语言以及其他元数据（如所有者和描述）。该数据直接作为生成吐槽内容的上下文传递给 Claude。

#### Build the catalog

该目录定义了可用的组件及其属性类型。结合该模式，它是模型与前端之间的契约。

打开 `./lib/catalog.ts` 并将第一个组件添加到 `roastComponentDefinitions` 中。

```c
// object key name should match component name
  RoastOpener: {
    // The description is critical for helping the LLM understand when to use the component
    description:
      "Full-screen opener with repo + owner and a sharp roast tagline.",
    // props with types gives the llm a clear understanding of what data it can provide the component. 
    props: z.object({
      repoName: z.string(),
      ownerName: z.string(),
      tagline: z.string(),
    }),
    type: "scene",
    defaultDuration: SCENE_DURATION_FRAMES,
  },
```

这将 `RoastOpener` 定义为 AI 必须遵循的严格契约。它告诉模型这个组件是什么、何时使用它，以及它确切可以输出哪些属性。由于目录是模型唯一允许使用的词汇，这个对象通过将 AI 限制为使用类型化的、已知的组件，既指导生成过程，又防止无效的 UI 出现。

现在添加剩余组件。最终目录应该如下所示：


#### Build the registry

目录就位后，注册表将 AI 生成的规范映射到实际的 UI 组件。每个键都与目录中的一个键相匹配。当渲染器在规范中看到 `RoastOpener` 时，它会调用相应的函数并传递 props。

Open `./lib/registry.tsx`.

```c
/**
RoastOpener → <RoastOpenerScene />
CrimeStat → <CrimeStatScene />
ShameTimeline → <ShameTimelineScene />
HallOfFame → <HallOfFameScene />
Verdict → <VerdictScene />
*/
// When the render sees "RoastOpener" it invokes the function and passes the props from the spec
export const componentRegistry: ComponentRegistry = {
  RoastOpener: ({ clip }) => (
    <RoastOpenerScene {...(clip.props as RoastOpenerProps)} />
  ),
  CrimeStat: ({ clip }) => (
    <CrimeStatScene {...(clip.props as CrimeStatProps)} />
  ),
  ShameTimeline: ({ clip }) => (
    <ShameTimelineScene {...(clip.props as ShameTimelineProps)} />
  ),
  HallOfFame: ({ clip }) => (
    <HallOfFameScene {...(clip.props as HallOfFameProps)} />
  ),
  Verdict: ({ clip }) => <VerdictScene {...(clip.props as VerdictProps)} />,
};
```

#### Wire up the player

`WrappedPlayer` 是一个轻量级包装器，它将你的时间线规范连接到 Remotion 的 `Player` 。它不直接硬编码合成设置，而是直接从规范中读取时长、帧率和尺寸。无论模型生成什么，播放器都会反映它。来自 `@json-render/remotion` 的 `渲染器` 在运行时处理繁重的工作，使用 `componentRegistry` 解析动态引用，将规范的场景图转换为 React 组件。

Add to `./components/wrapped-player.tsx`:

```c
/** Renders a timeline spec with Remotion Player and @json-render/remotion Renderer. */
// WrappedPlayer is a React component that takes a single prop 'spec' of type TimelineSpec
export const WrappedPlayer = ({ spec }: { spec: TimelineSpec }) => {
  // Check if the 'composition' property exists on the 'spec' object
  if (!spec.composition) {
    // If there is no 'composition', render nothing (null)
    return null;
  }
  // If 'composition' exists, render the Remotion Player component
  return (
    <>
      <Player
        // Set the component to render as the custom Renderer from @json-render/remotion
        component={Renderer}
        // Pass inputProps to the Renderer including the timeline spec and registered components
        inputProps={{
          spec, // The TimelineSpec object for rendering
          components: componentRegistry, // The collection of registered components for dynamic rendering
        }}
        durationInFrames={spec.composition.durationInFrames}
        // Define the frames per second for the composition
        fps={spec.composition.fps}
        compositionWidth={spec.composition.width}
        compositionHeight={spec.composition.height}
        controls
        autoPlay
        style={{ width: "100%" }}
      />
    </>
  );
};
```

一旦播放器有了规范，它就会处理其余部分。时长、帧率、尺寸和播放均源自模型生成的内容。你可以在此查看一个 [示例规范](https://gist.github.com/kenzic/3be12bd94edc6b855d473a74fb094020) 。

#### Prompt

GitHub 集成提供数据。JSON 渲染设置定义了模型可以使用的组件。提示词是视频被塑造的地方。当提交仓库链接时，API 获取 GitHub 数据，并且 `catalog.prompt()` （位于 `./lib/catalog.ts` ）构建一个结构化提示词，该提示词告诉模型有哪些场景组件可用，并根据在仓库中找到的内容指示模型选择、排序和填充这些组件。

#### Conclusion

Code Roast 之所以能工作，是因为 AI 不是在填充模板。它在选择展示什么。每个代码仓库都会获得不同的场景序列，因为模型会决定哪些组件适配、以什么顺序以及包含什么内容。

JSON Render 不会改变你编写 React 的方式或 Remotion 渲染视频的方式，而是改变了驱动它的因素。目录是你的约束层：模型只能输出你定义的内容。注册表是你的映射层：无论模型输出什么，播放器都知道如何渲染。在这两者之间，AI 决定了视频中真正应该包含的内容。

那就是“UI 作为 AI 的函数”在实践中的样子。不是一个附加到静态页面的聊天机器人，而是一个模型输出即为界面状态的流程。

AI 辅助 UI 和 AI 驱动 UI 之间的差距不是一种设计理念，而是一种架构决策。这是实现它的一种方式。

#### 用 JSON Render + Remotion 做 AI 视频：精炼总结

##### 核心观点

这篇文章讲的是：**如何让 AI 不只是“写内容”，而是直接“决定视频界面长什么样”**。  
作者用 `JSON Render` 和 `Remotion` 搭了一个工具 `Code Roast`，可以读取任意公开 GitHub 仓库的数据，再由 AI 自动生成一个类似 Wrapped 风格的“吐槽视频”。

##### 关键方法

###### 1. 用“组件目录”约束 AI 输出
作者没有让模型自由生成前端代码，而是先定义了一套**可用的视频场景组件**，比如开场、数据吐槽、时间线、亮点、最终判词等。

这样做的意义是：
- AI 只能在你提供的组件里做选择
- 每个组件的字段和类型都被严格规定
- 避免模型输出不合法、无法渲染的内容

本质上，这是在给 AI 一个**可控的输出契约**。

###### 2. 用“注册表”把 AI 结果映射成真实视频
AI 输出的是一个 JSON 规格，不是直接生成页面或视频代码。  
注册表的作用，就是把这些 JSON 里的组件名，映射到真实的 Remotion 场景组件上。

也就是说：
- AI 决定“用什么场景、什么顺序、填什么内容”
- 前端负责“把这些决定渲染出来”

这样可以把**内容决策**和**渲染实现**彻底分开。

###### 3. 用播放器按规格直接渲染
播放器不会写死视频配置，而是直接读取 AI 生成的规格，例如：
- 视频时长
- 帧率
- 分辨率
- 场景顺序

结果就是：**模型输出什么，播放器就渲染什么**。  
这让视频生成流程变成了一种“由 AI 驱动的界面系统”。

##### 整体流程

###### 数据到视频的链路
整个链路非常清晰：

1. 从 GitHub 仓库抓取真实数据  
2. 把这些数据作为上下文交给模型  
3. 模型根据组件目录，生成视频 JSON 规格  
4. 注册表把规格映射到 Remotion 组件  
5. Player 按规格渲染最终视频

因此，每个仓库生成的视频都不同，因为**AI 会根据仓库特点，动态决定讲什么、怎么讲**。

##### 文章的真正价值

###### 这不是“AI 填模板”，而是“AI 组织界面”
作者最想表达的一点是：

传统做法里，AI 只是往固定模板里填词；  
而这里，AI 真正在决定：
- 展示哪些内容
- 用哪些场景
- 先后顺序是什么

也就是说，**界面不再是静态设计好的，界面本身成了模型输出的一部分**。

##### 对产品和架构的启发

###### 从“AI 辅助 UI”走向“AI 驱动 UI”
这篇文章的核心启发是：

- `catalog` 是约束层：限制 AI 只能输出什么
- `registry` 是映射层：保证输出一定能被渲染
- AI 则负责在约束内做内容和结构决策

所以，AI 驱动 UI 的关键不在于提示词写得多花，而在于**架构是否把“生成自由”与“工程可控”结合起来**。

##### 一句话总结

**这篇文章本质上是在展示一种新型 UI 架构：前端先定义边界，AI 在边界内生成界面规格，最终由渲染器把规格变成真实视频。**  
它的意义不只是做了一个 AI 视频工具，而是提供了一种“让 AI 成为界面生成引擎”的通用方法。
