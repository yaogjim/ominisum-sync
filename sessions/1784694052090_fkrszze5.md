## 正文

**yibie**

推荐这个思路。Google 工程师 Matt Rickard 提出了一个概念叫"mini-app spec"——用可执行的小型浏览器制品来替代纯文本 spec。Markdown 为人类可读性赢了，但它对 agent 不是最强的合约。Mini-app spec 把 prose、结构化数据、原型行为、注解和对账检查装进一个东西里。核心思想就一句："spec 最高的工作是在实现不断变化时，保住你最初的意思。"

Mini-App Spec 的不合理有效性

HTML 是新的 Markdown。但 mini-app 是新的 HTML。

今天 agent 的工作流很简单：写一个 Markdown spec，让 agent 构建，然后人工检查结果是否匹配原始意图。Anthropic 的 Thariq 说得很对：HTML 改善了信息密度和阅读便利性。但更深层的问题是对账。

Mini-app spec 是一个小型的、浏览器原生的制品，它把 prose、结构化数据、原型行为、注解和检查结合在一起。

最好的 spec 格式是把意图和实现保持得最近的格式。Markdown 赢了，因为人类可以读它——不是因为它对 agent 是最强的合约。它干净、便携、容易编辑、高效。但它的结构大多是隐含的：需求、约束和边缘情况坍缩成 prose 和项目符号。

Spec 的最高工作是：在实现不断变化时，保住你最初的意思。

这就是为什么很多人更倾向于一个快速原型而非文档。原型携带着 prose 会丢失的行为。但原型和 spec 通常分开存在——原型展示了感觉是什么样的；spec 记录了想要的是什么。一个 mini-app 把它们放在一起。

对账检查

Mini-app spec 不只是对 Markdown spec 的美化。它引入了自动检查：

• 模板对账。把模板写成 React 组件的 props，这样它们不会从约定格式漂移。没有缺失的章节、没有回退。更新自动传播到下游消费者。  
• 文件树对账。Spec 中的包和文件是否存在？有多余的吗？  
• 测试对账。Mini-app spec 不替代单元测试或集成测试。它回答元问题：spec 中的测试存在吗？它们在通过吗？你能按需运行它们吗？  
• 配置和密钥对账。Spec 通常包含应用需要的配置键，但不包含值。比如 Service A 需要一个 OPENAI\_API\_KEY。Spec 可以报告这个密钥是否存在并绑定到了正确的地方。

工作流三层

\| 层级 \| 做法 \|  
\|------\|------\|  
\| Markdown loop \| 写 spec，构建实现，人工比对 \|  
\| HTML loop \| 写更丰富的 spec，构建实现，用更好的可视化人工比对 \|  
\| Mini-app loop \| 建模意图，嵌入原型，构建实现，运行对账检查 \|

Markdown loop 是今天大多数人的做法。HTML loop 加了可视化密度——你能看到它应该长什么样。Mini-app loop 是最高的——你不仅能看到，还能机械地对账意图是否被实现了。

下一步是让这个制品足够可执行，能参与到构建循环中。注解可以关闭另一个环：人类可以在精确渲染的子树上画圈或指向——"这个不对"——然后 agent 修复那一个点而不是整个东西。

## 结构化（1）

### 2026-07-22 04:17:02

##### 主旨概括

“Mini-app spec”主张用**可执行的浏览器小应用**替代纯文本 Markdown 规格说明，将文字、结构化数据、交互原型、注解和自动检查整合在一起。它的核心目标是：**当实现不断变化时，仍能保留并验证最初的产品意图。**

##### 1. Markdown Spec 的局限

当前常见的 Agent 开发流程是：

1. 人类编写 Markdown spec；
2. Agent 根据 spec 构建产品；
3. 人工检查结果是否符合原始需求。

Markdown 干净、便携、易编辑，适合人类阅读，但并不是约束 Agent 的最强“合约”。其主要问题是：

- 需求、约束和边界情况大多藏在自然语言中；
- 结构往往是隐含的，Agent 容易漏掉或误解；
- 实现发生变化后，只能依赖人工反复对照。

HTML 虽然提高了信息密度和可视化效果，但仍未解决最关键的**意图与实现如何自动对账**的问题。

##### 2. 什么是 Mini-app Spec

Mini-app spec 是一个**浏览器原生、可执行的小型制品**，将以下内容放在同一个载体中：

- 文字需求（prose）
- 结构化数据
- 可交互的原型行为
- 人工注解
- 自动对账检查

传统方式中，原型负责展示“产品应该是什么感觉”，spec 负责记录“产品需要实现什么”，两者通常彼此分离。Mini-app spec 则把原型和规格说明合并，使**产品意图尽可能贴近实际实现**。

##### 3. Mini-app Spec 的四类对账检查

Mini-app spec 不只是把 Markdown 做得更美观，而是引入可自动执行的检查机制。

###### 模板对账

将模板定义为 React 组件的 props，确保实现不会偏离约定格式：

- 检查是否缺少章节；
- 防止模板退回旧版本；
- 更新后自动同步给下游使用者。

###### 文件树对账

核对 spec 中声明的代码结构与真实项目是否一致：

- 指定的包和文件是否存在；
- 是否缺少必要文件；
- 是否出现未声明的多余文件。

###### 测试对账

Mini-app spec 不替代单元测试或集成测试，而是检查更高层的问题：

- spec 中要求的测试是否真实存在；
- 这些测试当前是否通过；
- 是否能够按需直接运行。

###### 配置与密钥对账

spec 可以声明应用需要哪些配置项，但不保存密钥值，并自动检查它们是否正确绑定。

例如：如果 Service A 需要 `OPENAI_API_KEY`，mini-app spec 可以报告：

- 该密钥是否已经配置；
- 是否绑定到了正确的服务或位置。

##### 4. Agent 工作流的三个层级

| 层级 | 工作方式 | 特点 |
|---|---|---|
| Markdown loop | 编写 spec → 构建实现 → 人工比对 | 当前最普遍，但主要依赖人工检查 |
| HTML loop | 编写更丰富的 spec → 构建实现 → 可视化比对 | 信息密度更高，能看到产品应有的样子 |
| Mini-app loop | 建模意图 → 嵌入原型 → 构建实现 → 自动对账 | 不仅能看，还能机械化验证意图是否实现 |

Mini-app loop 的提升不只是“展示得更好”，而是让 spec 本身参与构建和验收流程。

##### 5. 下一步：用精确注解闭环修改

未来可以让 mini-app spec 进一步参与 Agent 的修复过程。人类能够直接在具体渲染区域上圈选或指出：

> “这个地方不对。”

Agent 随后只修复对应的组件或渲染子树，而不是重新理解和修改整个项目，从而减少误改并提高迭代效率。

##### 6. 社区反馈与相关实践

- `@Dash` 表示，团队计划在当周周末开源一个同时支持 **Claude Code** 和 **Codex** 的桌面版本；该回复获得 **246 个赞、94 条评论**。
- `@Michael Guo` 提到正在使用 `lavish`，其思路同样是将 Agent 的文字输出可视化，并通过 annotation 进行评阅。
- 其他讨论认为，类似方法已经被部分开发者用于模型分析和实际产品开发，说明这一思路并不局限于学术研究，也具有较强的工程实践价值。

##### 核心结论

Mini-app spec 的价值在于把 spec 从一份“供人阅读的静态文档”，升级为一个**可展示、可交互、可检查、可参与构建的执行载体**。它不是要取代测试，而是帮助人类和 Agent 持续确认：**最终实现有没有偏离最初意图。**

## 口播总结（1）

### 2026-08-03 01:28:23

#### 推荐这个思路：让规格说明变成可执行的小型应用

这份材料介绍了一种面向人工智能代理，也就是 agent 的新型规格说明方法，叫作“Mini-App Spec”，可以理解为“小型应用规格”。你将了解到：为什么单纯的 Markdown 文档不够用，Mini-App Spec 如何把意图、原型和自动检查放在一起，以及它怎样帮助人类和 agent 更准确地对齐目标。

##### 首先，传统 Markdown 规格说明的优势和局限

核心结论是：Markdown 很适合人类阅读，但不一定是 agent 最强的工作合约。

Markdown 是一种用纯文本写作的格式。它干净、便携、容易编辑，也很适合写需求文档。今天大多数人的工作方式，都是先写一份 Markdown 规格说明，再让 agent 根据它构建产品，最后由人来检查实现结果是否符合最初的意图。

问题在于，很多关键内容并没有被明确写出来。需求、约束条件和边缘情况，往往都被压缩进段落和项目符号里。人类可以根据上下文理解它们，但 agent 未必能准确识别这些隐含结构。

所以，Markdown 的成功，主要是因为人类读起来方便，而不是因为它天然适合充当 agent 的精确合约。

##### 接下来，为什么原型比文档更接近真实意图

核心结论是：一个快速原型，通常比单纯的文字文档携带更多信息。

文字可以描述产品想要达到什么目标，但它不一定能说明产品具体应该怎么运行。原型则能直接展示交互行为、页面状态和使用感觉，这些内容往往是 prose，也就是自然语言文字，很难完整表达的。

但传统工作中，原型和规格说明通常是分开的。原型展示“它应该是什么感觉”，规格说明记录“我们想要什么”。两者一旦分离，就容易出现偏差。

Mini-App Spec 的做法，就是把这两部分放进同一个小型应用里。它不是一份单纯的文档，而是一个浏览器原生的小型制品，里面同时包含几类内容：

第一，是自然语言描述，也就是 prose。  
第二，是结构化数据，让关键要求变得更明确。  
第三，是可以运行或查看的原型行为。  
第四，是注解，方便人类直接指出某个具体问题。  
第五，是自动检查，用来核对实现有没有偏离规格。

这样一来，产品的“文字意图”和“实际表现”就不会轻易分家。

##### 更重要的是，规格说明的最高任务是守住原始意图

核心结论是：规格说明最重要的工作，不是把文档写得漂亮，而是在实现不断变化时，尽量保住最初的意思。

实际开发中，实现会持续变化。页面会调整，文件会增加，配置会修改，测试也会更新。如果规格说明只是静态文字，那么它很容易和最终实现逐渐脱节。

Mini-App Spec 试图解决的，就是这种“对账”问题。这里的“对账”，不是财务上的核算，而是把规格说明中的要求，和实际代码、文件、测试以及配置逐项比对，确认它们仍然一致。

这也是为什么有人会更喜欢先做一个快速原型，而不是只写一份长文档。原型可以保留交互和行为，补足文字容易丢失的部分。Mini-App Spec 则进一步把原型和规格说明合并起来。

##### 然后，Mini-App Spec 如何进行自动对账

Mini-App Spec 不只是给 Markdown 加上更漂亮的界面。它真正重要的地方，是加入了多种可以自动运行的检查。

###### 第一类是模板对账

核心结论是：模板可以被固定下来，避免不同实现逐渐偏离约定。

具体做法是，把模板写成 React 组件的参数。React 是一种常见的前端界面开发技术，而组件参数可以理解为：使用这个模板时，必须明确传入哪些内容。

这样，模板中的结构就不再只是口头约定。系统可以检查有没有缺少章节，有没有偷偷使用回退方案，也可以让模板更新自动传递给下游使用者。

###### 第二类是文件树对账

核心结论是：规格说明可以检查它要求的文件和目录是否真的存在。

例如，规格中写明了某个包、某个文件，或者某种目录结构，系统就可以自动确认这些内容有没有被创建。同时，它也可以发现项目中是否出现了规格之外的多余文件。

这能帮助团队及时发现：不是文件没写，就是实现偷偷增加了规格没有要求的内容。

###### 第三类是测试对账

核心结论是：Mini-App Spec 不会取代单元测试或集成测试，但它可以检查测试本身是否被落实。

单元测试，是针对某个小功能进行验证；集成测试，则是检查多个模块组合起来是否正常。

Mini-App Spec 进一步追问几个元问题，也就是关于测试体系本身的问题：规格中提到的测试是否真的存在？这些测试现在是否通过？需要时能不能直接运行？

所以，它不是替代测试，而是确认“规格要求的测试”没有停留在文字里。

###### 第四类是配置和密钥对账

核心结论是：规格说明可以检查应用需要的配置是否存在，并且是否绑定到了正确的位置。

比如，某个服务需要一个名为 `OPENAI_API_KEY` 的配置键。规格说明不需要直接写出密钥的真实值，但可以检查这个键是否存在，以及它有没有被正确连接到对应的服务。

这样既保留了安全边界，又能发现配置遗漏。对于依赖多个外部服务的应用来说，这种检查尤其有用。

##### 再来看，三种不同的工作循环

这套方法可以被理解为三个逐步升级的工作循环。

第一种，是 Markdown 循环。做法是：写规格说明，构建实现，再由人手动比较实现是否符合文档。这是目前大多数人的工作方式。

第二种，是 HTML 循环。做法是：写一份信息更丰富的规格说明，构建实现，再通过更直观的可视化界面进行人工比较。它提升了信息密度，也让人更容易看到产品应该长什么样。

第三种，是 Mini-App 循环。做法是：先对意图进行建模，再把原型嵌入规格说明，接着构建真正的实现，最后运行自动对账检查。

这三种方式的差别，可以简单理解为：

Markdown 循环，主要是“写下来，再人工看”。  
HTML 循环，变成“写下来，再更直观地看”。  
Mini-App 循环，则是“写下来、展示出来，再机械地检查它有没有被正确实现”。

它不仅让人看到产品是什么样，还能自动核对规格中的要求是否真的落到了实现中。

##### 最后，下一步是让规格说明参与整个构建过程

核心结论是：未来的 Mini-App Spec 不应只是被动地展示结果，而应该足够可执行，能够直接参与开发循环。

其中一个重要方向，是加入注解功能。人类可以在精确渲染出来的某个区域上画圈、指向，或者直接标记一句：“这个地方不对。”

这样，agent 就能针对被指出的那一小块进行修复，而不是重新理解和修改整个应用。

这会让反馈变得更具体。过去，人类可能只能说“整体感觉不对”，agent 需要重新猜测问题在哪里。现在，人类可以直接指出某个页面区域、某个组件，或者某个具体行为，减少来回沟通的成本。

材料中的一些回复，也体现了这个方向正在被实践。有开发者提到，他们准备开源一款同时支持 Claude Code 和 Codex 的桌面版工具。还有人分享说，类似的方法已经被用于观察模型行为变化，例如通过模型输出测量模型指纹。另一些工具则尝试把 agent 的文字结果视觉化，并支持人类直接做注解和评阅。

##### 回顾：最值得记住的四点

第一，Markdown 的优势是人类容易阅读，但它对需求结构、约束和边缘情况的表达，往往不够明确。

第二，原型比文字更能保留真实的交互行为，但传统做法中，原型和规格说明通常彼此分离。

第三，Mini-App Spec 把自然语言、结构化数据、原型行为、注解和自动检查放在同一个浏览器原生制品中。

第四，规格说明最重要的任务，是在实现持续变化时，守住最初的意图。Mini-App Spec 通过模板、文件、测试、配置和密钥等多种对账机制，让这种一致性检查尽可能自动完成。

## 深度解读（1）

### 2026-09-18 00:23:53

#### Mini-app spec 的价值，不是文档更漂亮，而是让“意图漂移”可被发现

这套思路真正值得关注的，并非“用 HTML 替代 Markdown”，而是重新定义了规格说明的职责：**spec 不只是把需求交给开发者或 Agent，而要在实现持续变化时，帮助团队判断最初的意图是否仍被保留。**

Markdown 擅长低成本表达，却把大量结构藏在自然语言里。“支持空状态”“使用统一模板”“必须配置某个密钥”，人能结合上下文理解，Agent 却可能遗漏、误解，或在后续修改中悄悄破坏。今天常见的循环是：写文档、生成代码、人工检查。问题不只在生成质量，而在最后的“是否符合”缺少稳定、可执行的判断依据。

##### 从描述需求，转向对账意图

Mini-app spec 将文字、结构化数据、交互原型、注解和检查放入同一个浏览器制品。它比传统原型更进一步：原型只能展示“应该是什么感觉”，mini-app 还可以检查实现是否仍满足约定。

文章列举的检查很具体：文件与包是否存在、模板是否缺少必需部分、spec 中声明的测试是否存在并通过、配置键是否正确绑定。这些并不替代单元测试或集成测试，而是在其上增加一层“元验证”：**我们承诺要验证的东西，真的被实现并持续验证了吗？**

对 Agent 工作流而言，这一点尤其重要。人类开发者通常会主动补齐模糊之处，Agent 更倾向于完成当前指令，却未必维护跨多轮修改的一致性。可执行 spec 相当于把部分产品记忆从对话和文档中移出来，变成机器能够反复核对的外部状态。

##### 真正的边界在于：意图能否被编码

这套方法不会自动解决需求质量。文件存在、测试通过、组件结构一致，都容易机械检查；“页面让人信任”“流程足够简单”“推荐结果有帮助”则不能仅靠 spec 判定。如果团队把容易检查的代理指标当成完整意图，mini-app 反而会制造虚假的确定性。

它还可能带来新的“双份实现”：一套产品代码，加一套日渐复杂的规格应用。若两者共享过多实现，检查会变成“自己证明自己”；若完全独立，维护成本又可能超过收益。因此更合理的应用范围，是高频变化、多人或多 Agent 协作，并且存在大量可明确表达约束的项目，而不是所有需求都先做一个小应用。

##### 产品机会是“意图的持续对账层”

现有工具分别管理文字、设计稿、代码、测试和反馈，真正缺失的是它们之间的映射。更有价值的产品未必是又一个 spec 编辑器，而是让某条需求能够关联到界面区域、代码实体、测试与运行状态；当人圈选一个渲染节点说“这里不对”时，Agent 能定位相关约束，而不是重新解释整份文档。

这意味着 PM 的产出也可能变化：从写一份交接文档，转向维护一组**可展示、可注释、部分可验证的意图**。Mini-app spec 是否会成为标准形式尚未确定，但它指出了一个更持久的方向：在 Agent 能快速生成实现之后，稀缺能力将从“把需求写出来”，转向“让需求在多轮生成和修改中仍可追踪、可核对”。

## 默认总结（1）

### 2026-09-18 01:49:48

##### 一句话看懂

文章推荐一种面向 AI Agent 的“mini-app spec”：把文字需求、交互原型和自动检查做成可执行的浏览器小应用，让实现变化时仍能核对并保留最初意图。

##### 关键内容

- **Markdown 的局限**：它便于人读写，但需求、约束和边缘情况多藏在自然语言里，Agent 实现后仍要人工逐项比对。
- **mini-app spec 不只是更漂亮的 HTML**：它同时容纳说明文字、结构化数据、可操作原型、批注和检查，让“想做什么”与“实际做成什么”靠得更近。
- **自动对账是核心**：可检查约定的模板章节是否缺失、文件是否存在、spec 提到的测试是否存在并通过，以及所需配置或密钥是否正确绑定；但它**不能替代单元测试和集成测试**。
- 作者设想，人可以直接圈出渲染结果中的问题，让 Agent 定点修复，而非重新理解整份文档。

##### 通俗解读

这里的 mini-app 不是手机“小程序”，而是一份能在浏览器运行、还能自检的需求说明书。它的价值主张是把“文档、样品、验收清单”合为一体。不过原文主要是在提出方法和工作流，尚未提供充分的效果数据。
