**idoubi**

让 Claude Code 分析了一遍 claude-code-sourcemap 源码，把逻辑全部抽离出来，写了个 open-agent-sdk，用于替代 claude-agent-sdk

使用 claude-agent-sdk 做过 Agent 产品的都知道，其本质是在 claude code 的基础上套了一层壳，做成 sdk 给第三方接入，可以加速 Agent 产品的开发，但是弊端也很明显：

1\. claude-agent-sdk 依赖 claude code，而 claude code 是不开源的，一切都是黑盒调用，出了问题你没法修

2\. claude-agent-sdk 接到的 query，需要创建 claude code 进程去处理，开销很大，不适合云端规模化调用

在 Claude Code 源码基础上实现的 open-agent-sdk

1\. 完全兼容 claude-agent-sdk 的接口形式，只需换个包名即可快速替换

2\. 完全开源，你可以接入到你的 Agent 后做定制化修改，不再是黑盒调用

3\. 函数调用，不依赖本地 cli 进程，没有额外的开销，云端 Agent 高并发不愁

## 通俗精炼（1）

#### idoubi 发布 open-agent-sdk：开源替代 claude-agent-sdk

##### 文章核心

作者通过让 Claude Code 分析 `claude-code-sourcemap` 源码，将其中的 Agent 逻辑抽离出来，开发了一个新的开源项目：`open-agent-sdk`。

它的目标是替代 `claude-agent-sdk`，用于更灵活、高效地开发 Agent 产品。

项目地址：  
https://github.com/shipany-ai/open-agent-sdk

---

##### claude-agent-sdk 的问题

作者认为，`claude-agent-sdk` 虽然能加速 Agent 产品开发，但存在明显缺陷：

1. **依赖闭源 Claude Code**  
   Claude Code 本身不开源，调用逻辑是黑盒，出问题很难排查和修复。

2. **运行成本较高**  
   每次处理 query 都需要创建 Claude Code 进程，资源开销大，不适合云端高并发、大规模调用。

---

##### open-agent-sdk 的优势

`open-agent-sdk` 基于 Claude Code 的源码逻辑重新实现，主要特点包括：

1. **接口兼容**  
   基本兼容 `claude-agent-sdk` 的接口，迁移时只需替换包名。

2. **完全开源**  
   开发者可以自由查看、修改和定制逻辑，避免黑盒依赖。

3. **无 CLI 进程开销**  
   通过函数调用实现，不依赖本地 Claude Code CLI 进程，更适合云端 Agent 高并发场景。

4. **MIT 协议**  
   项目采用 MIT 开源协议，方便商业和个人项目使用。

## 解读（1）

##### 一、内容总结

这条推文主要在介绍一个开源项目：**open-agent-sdk**。

作者表示：

- 他让 Claude Code 分析了 `claude-code-sourcemap` 的源码；
- 将其中的核心逻辑抽离出来；
- 写了一个新的 SDK：`open-agent-sdk`；
- 目标是替代官方的 `claude-agent-sdk`。

项目地址：

> https://github.com/shipany-ai/open-agent-sdk

作者认为 `claude-agent-sdk` 有几个问题：

1. **依赖 Claude Code**
   - Claude Code 本身不开源；
   - 出问题很难定位和修改。

2. **调用成本较高**
   - 每次处理 query 都需要启动 Claude Code 进程；
   - 本地 CLI 进程开销大；
   - 不适合云端高并发场景。

而 `open-agent-sdk` 的特点是：

1. **接口兼容**
   - 和 `claude-agent-sdk` 的接口形式类似；
   - 理论上只需要换包名就能迁移。

2. **完全开源**
   - 可以查看源码；
   - 可以二次开发和定制。

3. **函数调用**
   - 不依赖本地 CLI 进程；
   - 减少额外开销；
   - 更适合云端部署和高并发 Agent 产品。

---

##### 二、深入浅出解读

可以把这件事理解成：

> 原来的 `claude-agent-sdk` 像是一个遥控器，但真正干活的是背后的 Claude Code。  
> 现在 `open-agent-sdk` 想把背后那套干活逻辑重新做成一个开源版本，让大家可以直接拿来用。

###### 1. 为什么有人想替代 `claude-agent-sdk`？

因为它虽然方便，但有明显限制。

如果你用它做 Agent 产品，比如：

- AI 编程助手；
- 自动化任务 Agent；
- 云端代码生成服务；
- 多用户同时调用的 Agent 平台；

那么你会遇到几个问题：

###### 黑盒问题

`claude-agent-sdk` 背后依赖 Claude Code，但 Claude Code 不开源。

这意味着：

- 你不知道内部具体怎么处理；
- 出 bug 只能等官方修；
- 想深度定制也很难；
- 云端部署时可控性差。

###### 性能问题

原来的方案需要启动 Claude Code 进程。

这类似于：

> 每来一个请求，就临时打开一个完整应用来处理。

这种方式在个人电脑上还可以接受，但如果放到云端、高并发场景，就会变得比较重：

- 启动慢；
- 占资源；
- 不易横向扩展；
- 成本更高。

---

###### 2. `open-agent-sdk` 想解决什么？

它想把 Agent SDK 变成更轻、更透明、更可控的形态。

###### 从“启动进程”变成“调用函数”

原来像这样：

```text
用户请求 → 启动 Claude Code 进程 → 处理任务 → 返回结果
```

现在希望变成：

```text
用户请求 → 直接调用 SDK 函数 → 处理任务 → 返回结果
```

后者明显更适合服务端使用。

###### 从“黑盒”变成“开源”

开源之后，开发者可以：

- 看源码；
- 改逻辑；
- 加功能；
- 修 bug；
- 适配自己的模型或工具链。

这对做 Agent 产品的人很有吸引力。

---

##### 三、我的意见

我觉得这个项目的方向是有价值的，尤其适合想做 **云端 Agent 产品** 的开发者。

###### 优点

- **降低接入成本**：如果真的兼容 `claude-agent-sdk`，迁移会比较方便。
- **提升可控性**：开源代码更容易调试和定制。
- **更适合服务端**：不依赖 CLI 进程，对高并发更友好。
- **有利于生态发展**：社区可以基于它做更多 Agent 框架和产品。

###### 但也要注意几个风险

###### 1. 法律和授权风险

作者提到基于 `claude-code-sourcemap` 分析源码并抽离逻辑。

这可能涉及：

- 反编译；
- 源码还原；
- 许可证边界；
- 商业产品使用风险。

如果要在正式商业项目里使用，建议先确认：

- 项目许可证是否清晰；
- 是否存在侵权风险；
- 是否依赖 Anthropic 未授权的内部逻辑。

###### 2. 稳定性风险

开源项目早期通常会有：

- bug；
- 文档不完善；
- 接口变动；
- 边界场景处理不够成熟。

如果是生产环境，最好先做充分测试。

###### 3. 兼容性风险

虽然作者说“完全兼容”，但实际可能还是会有细节差异，比如：

- 工具调用行为；
- 上下文管理；
- 文件系统操作；
- 流式输出；
- 错误处理；
- 权限控制。

迁移时不能只换包名就直接上线，最好逐项验证。

---

##### 四、结论

`open-agent-sdk` 的核心价值是：

> 把原本依赖 Claude Code 黑盒进程的 Agent SDK，变成一个开源、轻量、可定制、适合云端部署的 SDK。

如果你只是个人使用 Claude Code，可能感知不大。

但如果你在做：

- Agent 平台；
- AI 编程助手；
- 云端自动化工具；
- 多用户 AI 开发服务；

那这个项目值得关注。

不过，正式商用前需要重点评估：

- 法律合规；
- 项目成熟度；
- 兼容性；
- 安全性；
- 维护活跃度。
