- **核心高价值点**：最有价值的是把智能体系统拆成五个必须协同设计的工程层次，避免把文件系统、bash 或提示词当作万能核心抽象。
- **留存建议**：长期保留（提供了构建智能体软件的五层系统框架，兼具架构视角与工程落地参考价值。）

**知识要点**

- 优化单个组件无法替代系统级设计，智能体软件本质上仍是系统工程问题。
- 生产级智能体需统一考虑代理逻辑、数据上下文、安全边界、交互界面和基础设施五层。
- 权限控制应由工具与系统配置强制执行，而不是依赖提示词约束模型行为。
- 智能体效果提升很多时候来自数据层和上下文工程优化，而不只是模型升级。
- 多入口界面下的身份认证与访问控制必须保持一致，否则容易产生系统性漏洞。

**行动项**

- 用五层框架审视现有智能体项目，检查是否在数据、安全和接口层存在架构短板。
- 将记忆、知识和会话状态从文件系统迁移到结构化数据库或对象存储方案中。
- 把高风险工具访问改为基于角色和审批流的显式授权，而不是仅靠提示词限制。
- 为不同界面建立统一的身份映射和访问控制策略，避免渠道间权限漂移。
- 参考 Dash 的实现，选一个真实任务做端到端最小可运行原型验证。

## 正文

**Ashpreet Bedi**

### 系统工程：构建有效的智能体软件

20世纪40年代初，贝尔实验室正在建设国家电话网络，这是当时世界上最复杂的技术系统。数百万个交换机、电缆、继电器和话务员必须协同工作。工程师们发现了一个将成为持续80年的教训：你不能通过优化单个组件来优化整个系统。整个系统的行为（呼叫路由、可靠性、容量和成本）来自于各个部分之间的相互作用。他们需要一种专注于组件之间相互作用的学科。

他们称之为系统工程。

智能体软件生态系统正在重复催生该领域的同样错误。当前的治理工程浪潮将要求你使用文件系统进行存储和内存管理，然后试图通过在数据库之上构建虚拟文件系统来规避其局限性。它将要求你使用 bash 作为通用工具，然后迫使你为每个请求创建沙箱来处理安全问题。这些是只优化单个部分而不考虑整个系统的症状。而我们却在未花一分钟询问这是否是正确方法的情况下就认同了这一做法。

### 软件工程是系统工程

编码代理降低了编写代码的门槛，但并没有降低生产软件的要求。软件工程一直以来都是系统工程，如果你正在构建代理型软件，你的系统需要连接这五个层次：

1\. 智能体工程 : 你的智能体或多智能体逻辑及执行流程。

模型、系统指令、工具配置、交接、上下文管理、可观测性。这是你定义你的代理的行为、运行方式和响应方式的地方。你的代理的行为在可能的情况下应具有确定性，在不可能的情况下应具有可观测性。

2\. 数据工程 ：你的代理的能力仅限于它能获取的上下文，而上下文本质上就是数据。记忆、存储、知识：都应该用数据工程原则来管理。这意味着精心设计的模式、结构化查询、用于快速读写的数据库、用于长期存储的对象存储，以及保持你的知识和记忆更新的管道。这些模式已有数十年历史。使用它们。

3\. 安全工程：认证、RBAC、治理、数据隔离、审计跟踪。

你的代理的能力由其工具定义，这些工具应通过基于 JWT 的权限进行范围界定。只读访问不是提示指令，而是工具配置。操作应设置审批层级：读取操作可自由执行，写入操作需用户审批，敏感操作需管理员签署确认。大多数操作应被记录，且在产品整个生命周期内均可查询。

并且请隔离请求。一个用户的上下文泄露到另一个用户那里属于数据泄露，而非漏洞。这会带来严重后果，并且有法律保护用户数据。因此，在共享沙箱中使用基于文件系统的内存可能不是个好主意。

4\. 界面工程 ：用户和其他代理如何与你的代理交互。

REST API、Slack、MCP 服务器、终端。在过去，你只有一个 API 和一个客户端。现在你有多个界面，每个都有自己的身份系统。Slack 用户 ID 不是你的产品用户 ID。以另一个代理身份进行身份验证的 MCP 客户端不是人类用户。界面工程旨在确保你的身份验证、策略和访问控制在代理可访问的每个界面上保持一致。

5\. 基础设施工程 ：你如何运行和扩展你的软件。容器、云部署、水平扩展。通常称为 DevOps。

好消息：这其中 95%的内容与运行其他任何服务完全相同。复用现有模式，它们会很好地满足你的需求。5%的不同之处在于：代理请求耗时更长（增加你的负载均衡器超时时间），响应是流式的（需考虑使用 SSE 或 WebSocket），而最好的代理是主动的（计划任务、后台执行）。这些都不是新的内容。

AI 工程师的关键突破口在于认识到智能体软件其实就是普通软件，其业务逻辑被智能体所取代，并且接口从请求/响应模式转变为跨多个界面的流式传输。

系统工程是使这些部件协同工作的学科，并且是构建能够正常工作的智能体软件的关键。

当从系统视角审视你的软件时，正确的决策变得显而易见，你不再纠结于 MCP 与 CLI 的选择。你给你的代理提供范围明确的工具，而非不受限制的 bash 访问权限。你将会话、内存和知识存储在数据库中，而非文件中。

当你孤立地设计某一层时，你会继承那些会在系统其余部分中层层传递的约束，并且你会浪费时间和资源来修补这些约束。当你从系统的角度出发设计时，每一层都会相互强化。

### 实践中的系统工程

我不能做出这么大的断言而不提供给你可运行的代码。

[Dash is an open-source, self-learning data agent](https://github.com/agno-agi/dash). You ask it questions in plain English, it writes SQL, runs it, and tells you what the numbers mean. Simple enough to clone and adapt. Real enough to demonstrate all five layers.

以下是 dash 中各层的工作方式：

#### 代理工程

Dash 是一个代理团队。负责人将请求分配给两名专家：一名负责查询数据（只读）的分析师，以及一名负责构建计算资产（如视图和汇总表）的工程师。每位专家获得相同类型的工具，但这些工具与不同的功能关联。分析师的 SQL 工具连接到只读数据库引擎。工程师的 SQL 工具连接到作用域限定为单个模式的可写引擎。相同的界面，不同的权限，由配置而非提示决定。指令在运行时由表元数据和业务规则组装而成。

#### 数据工程

六重上下文，以及学习工具。

原始的 LLMs 在编写 SQL 时很快就遇到了瓶颈：表结构缺乏含义，数据类型具有误导性，部落知识缺失，且无法从错误中学习。Dash 通过六个层次的扎实上下文解决了这些问题：

- 表元数据（模式，列，关系）
- 人工标注（指标、定义、业务规则）
- 查询模式（已知可工作的 SQL）
- 机构知识（文档，维基）
- 经验教训（错误模式及已发现的修复方法）
- 运行时上下文（实时模式检查）

这些层为两个系统提供输入：

- 第一个是精心整理的知识：表模式、验证过的查询以及加载到 PostgreSQL 中的业务规则。
- 第二个是已发现的学习成果：代理在遇到问题时保存的错误模式和修复方法，并在未来的查询中调用这些内容。

学习循环很简单：代理运行一个查询，出现类型错误，诊断并修复，然后保存该修复。下次遇到类似的列时，就能一次做对。当工程师创建新视图时，系统会将模式和示例查询记录到知识库中。分析师在下次搜索时发现该内容，并开始使用它。查询100比查询1更好，不是因为模型得到了改进，而是因为数据层得到了优化。

#### 安全工程

由系统强制执行，而非提示。

生产环境中的 Dash 使用基于角色的访问控制（RBAC）并进行 JWT 验证。每个查询都限定在\`user\_id\`范围内。一个评估套件直接测试这些边界：它促使代理泄露凭证、执行破坏性 SQL 以及跨越模式边界，然后验证它们无法做到这些。

安全性是一个跨层测试的系统属性。分析师的只读访问是 PostgreSQL 的连接参数。数据库本身会拒绝写入，无论模型生成什么内容。工程师可以写入，但只能写入到单一模式中：查询级别的防护机制会阻止任何针对源数据的操作。

#### 接口工程

Dash 提供 REST API、Slack 机器人、网页 UI 和 CLI 等多种使用方式。每种界面处理身份的方式不同：Slack 将线程时间戳映射到会话，API 在生产环境中使用 JWT 令牌。但这四种方式都使用相同的代理、相同的工具和相同的知识。

你的身份验证和访问控制需要在所有界面上都有效，因为代理不知道它是从哪个界面被调用的。

#### 基础设施工程

最小的 Python 容器。用于本地开发的 Docker Compose。部署到您选择的云平台。通过标准 ASGI 服务器使用 SSE 进行流式传输。95%的内容与其他任何服务完全相同。5%的不同部分（更长的超时时间、流式传输、定时任务）由标准工具处理。

你可以克隆它，运行 \`docker compose up\`，并拥有整个系统。

一个命令，五层，得益于系统工程，成就了一个可用产品。

Here's the link for reference:

[https://github.com/agno-agi/dash](https://github.com/agno-agi/dash)

#### 文章主旨

这篇文章的核心观点是：**构建智能体软件，不能只盯着模型、工具或某一个局部优化，而要用 “系统工程” 的视角统筹设计整个系统。**  
作者认为，智能体软件本质上仍然是软件系统，真正决定成败的是各层之间能否协同，而不是单个组件是否 “看起来很强”。

##### 1. 为什么要用系统工程看智能体软件

- 作者先回顾了**20 世纪 40 年代初贝尔实验室**建设国家电话网络的经验。面对当时世界上最复杂的技术系统，他们发现：**优化单个组件，不等于优化整个系统**。
- 电话网络的整体表现，如**呼叫路由、可靠性、容量和成本**，并不是某个零件单独决定的，而是来自各部分之间的配合。
- 这也是 “系统工程” 诞生的原因：它关注的不是孤立部件，而是**部件之间的相互作用**。

**对应到今天的智能体软件，作者认为行业正在重复类似错误：**
- 用**文件系统**做存储和记忆管理，后面再想办法补漏洞；
- 用**bash**作为通用工具，之后再为每个请求单独做沙箱来补安全问题；
- 这些做法本质上都是：**先优化局部，再被系统性问题反噬**。

##### 2. 智能体软件其实仍然是 “普通软件系统”

- 作者强调：**编码代理降低了写代码门槛，但没有降低生产级软件的要求。**
- 软件工程一直都是系统工程；到了智能体时代，这一点没有变，只是**业务逻辑更多由智能体承担，交互方式更多变成流式、多界面**。
- 真正的突破不是 “把模型接上去”，而是认识到：  
  **智能体软件 = 普通软件 + 智能体驱动的业务逻辑 + 跨多个界面的流式交互。**

##### 3. 构建智能体软件必须打通的五层体系

###### 3.1 智能体工程：定义代理如何行动

- 这一层包括：**模型、系统指令、工具配置、任务交接、上下文管理、可观测性**。
- 重点不是让智能体 “看起来聪明”，而是让它：
  - **能确定性地执行的地方尽量确定性；**
  - **不能确定的地方必须可观测、可追踪。**

**通俗理解：**
- 不是只写一句提示词让它 “自己发挥”，而是要明确它能做什么、怎么做、出错后怎么查。

###### 3.2 数据工程：智能体能力上限取决于上下文质量

- 作者明确指出：**记忆、存储、知识，本质上都是数据问题。**
- 因此应该用成熟的数据工程方法处理：
  - 设计清晰的 schema；
  - 使用结构化查询；
  - 用数据库做高频读写；
  - 用对象存储做长期保存；
  - 用数据管道持续更新知识和记忆。

**关键观点：**
- 智能体不是 “因为模型强所以强”，而是**因为上下文设计得好，所以更可靠**。
- 作者甚至直说：这些方法已经存在了几十年，**直接复用成熟模式即可**。

###### 3.3 安全工程：权限必须由系统强制，而不是靠提示词约束

- 这一层包括：**认证、RBAC、治理、数据隔离、审计日志**。
- 作者强调几个关键原则：
  - 工具权限应由**JWT**等机制明确限制；
  - “只读访问” 应该由系统配置决定，而不是写在 prompt 里；
  - 操作应分级：
    - **读取可自动执行**
    - **写入需用户审批**
    - **敏感操作需管理员确认**
  - 大多数操作都应记录，且全生命周期可审计。

**特别重要的一点：**
- **用户上下文泄露到其他用户，不是普通漏洞，而是数据泄露。**
- 因此，作者明确反对在共享沙箱里用**基于文件系统的记忆**来承载用户上下文，因为这很容易导致隔离失效。

###### 3.4 界面工程：多入口下仍要保证身份与策略一致

- 智能体软件通常不只有一个入口，可能同时有：
  - **REST API**
  - **Slack**
  - **MCP Server**
  - **终端 / CLI**
- 问题在于，不同入口的身份体系往往不同：
  - Slack 用户 ID 不等于产品用户 ID；
  - 另一个代理通过 MCP 调用时，也不一定代表人类用户。

**所以这一层的目标是：**
- 无论从哪个入口调用，
- **认证、权限策略、访问控制都要保持一致。**

###### 3.5 基础设施工程：95% 和传统服务没区别

- 作者认为，这部分通常就是大家熟悉的**DevOps / 容器 / 云部署 / 水平扩展**。
- 这里有一个非常鲜明的数据判断：

**95% 的内容和运行普通服务完全一样。**  
**只有 5% 不同，主要体现在：**
- 智能体请求更慢，所以要**提高负载均衡器超时时间**；
- 响应是流式的，所以要考虑**SSE 或 WebSocket**；
- 优秀的代理往往是主动的，所以需要**定时任务和后台执行**。

**结论：**
- 这些都不是新问题，不需要为 “AI” 重新发明一整套基础设施。

##### 4. 用系统视角设计，很多争论会自然消失

- 作者认为，一旦从系统角度看问题，很多选择其实很清楚：
  - 不会纠结**MCP 还是 CLI**这种表层问题；
  - 不会给代理开放无限制的**bash**权限；
  - 会把**会话、记忆、知识**放进数据库，而不是散落在文件里。
- 如果你只设计某一层，就会把局部限制传导到整个系统，最后花很多时间 “打补丁”。
- 如果从系统出发设计，各层会相互支撑，而不是相互拖累。

##### 5. 实际案例：Dash 如何把五层真正串起来

作者为了证明这不是空谈，给出了一个开源项目案例：**Dash**。  
它是一个**自学习的数据智能体**：用户用自然语言提问，Dash 会写 SQL、执行查询，再解释结果。

项目地址文中给出：`https://github.com/agno-agi/dash`

###### 5.1 Dash 的智能体工程：多代理协作，但权限不同

- Dash 不是单一代理，而是一个**代理团队**：
  - 一个负责人分配任务；
  - 一个分析师负责**只读查询数据**；
  - 一个工程师负责**创建视图、汇总表等计算资产**。
- 两者使用的是**同类型工具**，但绑定到不同权限：
  - 分析师的 SQL 工具连接到**只读数据库引擎**；
  - 工程师的 SQL 工具连接到**限定单一 schema 的可写引擎**。

**关键案例：**
- 同样是 SQL 工具，能力不同不是靠 prompt 提醒 “你别乱写”，  
  而是靠**配置决定权限边界**。

###### 5.2 Dash 的数据工程：六层上下文 + 学习闭环

作者指出，原始 LLM 在写 SQL 时很容易遇到问题，比如：
- 表结构缺乏业务含义；
- 数据类型会误导模型；
- 团队里的 “潜规则知识” 没法直接拿到；
- 模型也不会自动从错误中持续学习。

为了解决这些问题，Dash 提供了**六层上下文**：

1. **表元数据**：schema、列、关系  
2. **人工标注**：指标定义、业务规则  
3. **查询模式**：已验证可运行的 SQL  
4. **机构知识**：文档、Wiki  
5. **经验教训**：错误模式和已知修复方法  
6. **运行时上下文**：实时 schema 检查

这些内容被输入到两个系统里：
- 一个是整理好的知识库：如 schema、验证过的 SQL、业务规则，存入 PostgreSQL；
- 另一个是学习库：代理在出错后保存 “错误模式 + 修复方式”，供以后复用。

**非常关键的例子：**
- 代理第一次运行 SQL 出现类型错误；
- 它诊断并修复问题；
- 然后把修复方法存下来；
- 下次遇到类似列时，就能直接一次做对。

作者用一句话概括效果：  
**“第 100 次查询比第 1 次更好，不是因为模型升级了，而是因为数据层优化了。”**

###### 5.3 Dash 的安全工程：直接测试代理能否 “作恶”

- 在生产环境中，Dash 使用：
  - **RBAC**
  - **JWT 验证**
  - **按`user_id`进行查询范围限制**
- 更重要的是，它有一个评估套件，专门测试安全边界，例如诱导代理去：
  - 泄露凭证；
  - 执行破坏性 SQL；
  - 越过 schema 边界访问数据。

**结果验证的不是 “模型说它不会”，而是 “系统让它做不到”。**

具体做法包括：
- 分析师账号的只读权限由**PostgreSQL 连接参数**硬性限制；
- 即使模型生成写入 SQL，数据库本身也会拒绝；
- 工程师虽然可写，但也只能写到**单个 schema**；
- 查询层还有额外防护，防止操作源数据。

###### 5.4 Dash 的界面工程：四种入口，共用同一套核心能力

- Dash 支持多种入口：
  - **REST API**
  - **Slack 机器人**
  - **Web UI**
  - **CLI**
- 它们虽然身份处理方式不同，例如：
  - Slack 用线程时间戳映射会话；
  - API 在生产环境里使用 JWT；
- 但四种入口背后都复用：
  - **同一个代理系统**
  - **同一套工具**
  - **同一份知识库**

**这说明界面可以多样，但底层的认证和访问控制逻辑必须统一。**

###### 5.5 Dash 的基础设施工程：一个命令就能启动整套系统

- Dash 的基础设施设计刻意保持简单：
  - **最小化 Python 容器**
  - **Docker Compose 用于本地开发**
  - **部署到任意云平台**
  - **通过标准 ASGI 服务器 + SSE 实现流式输出**
- 作者再次强调：
  - **95% 和普通服务一样**
  - 只有更长超时、流式返回、定时任务这些差异
  - 而这些都可以用**标准工具**处理

**很直观的案例：**
- 你只需要运行`docker compose up`，
- 就能把整个五层系统启动起来。

##### 6. 文章结论

- 智能体软件的难点，不在于 “模型够不够聪明”，而在于**五层系统能否协同工作**。
- 真正有效的做法是：
  - 把权限做成系统约束，而不是提示词约束；
  - 把记忆和知识放进数据库，而不是文件系统；
  - 把多界面接入后的身份、权限、审计统一起来；
  - 在传统软件工程基础上，只针对智能体特性补上那**5%**的差异。
- 作者最终想表达的是：  
  **系统工程不是可选项，而是构建真正可用、可扩展、可治理的智能体软件的关键。**
