## 正文

昨晚，我的项目路演又被拒了。这次只是预面试，问题不在于我的产品。我的产品已经有月度经常性收入（MRR），也已经有用户每天都在使用。

得到的反馈很简单： *“你们到底需要资金做什么？”*

每当我尝试发展自己的想法时，总会听到这样的说法。精益求精已经融入我的血液。我开发过一些你可能用过的工具，比如 [websequencediagrams.com](https://websequencediagrams.com) ，也开发过一些你可能没用过的小众产品，比如 [eh-trade.ca](https://eh-trade.ca) 。这种对效率的执着追求成就了成功的自筹资金，但说实话，很多风投都 *讨厌* 这一点。

将成本控制在接近零的水平，与获得一百万美元融资但消耗速度极快，所获得的资金周转时间完全相同。这种方式压力更小，架构极其简洁，并且让你有充足的时间找到产品与市场的契合点，而无需承受董事会的压力。

如果你厌倦了现代“企业”的千篇一律的模板，那么这里就是我打造几乎零成本运营公司的详细指南。

#### Use a lean server

2026 年推出 Web 应用程序的简单粗暴的方法是启动 AWS，配置 EKS 集群，设置 RDS 实例，配置 NAT 网关，然后在没有一个用户查看你的登录页面之前，每月意外花费 300 美元。

明智的做法是租用一台虚拟专用服务器（VPS）。

我做的第一件事就是找个便宜又可靠的服务器。别用 AWS，你根本用不上，而且他们的控制面板简直就是个迷宫，处处都是为了推销升级服务。我用的是 Linode 或者 DigitalOcean，每月也就 5 到 10 美元。

1GB 内存对现代 Web 开发人员来说听起来可能很吓人，但如果你清楚自己在做什么，那就足够了。如果需要一些缓冲空间，只需使用交换文件即可。

image.png

目标是处理请求，而不是维护基础设施。只有一台服务器时，你就能准确地知道日志在哪里，确切地知道服务器崩溃的原因，以及如何重启它。

#### Use a lean language

现在你面临一些限制。你只有 1GB 的内存。你 *可以* 选择 Python 或 Ruby 作为主要的后端语言——但为什么要这么做呢？你会占用一半的内存，仅仅用于启动解释器和管理 `gunicorn` 工作进程。

I write my backends in Go.

Go 在 Web 任务方面性能远超其他语言，它是强类型的，而且——对于 2026 年来说至关重要的是——它对语言学习者 (LLM) 来说极其易于理解。但 Go 真正的魔力在于部署过程。它没有 `pip install` 依赖项的地狱，也不需要虚拟环境。你只需在笔记本电脑上将整个应用程序编译成一个静态链接的二进制文件， `scp` 其传输到你那台 5 美元的服务器，即可运行。

以下是用 Go 语言编写的完整、可用于生产环境的 Web 服务器的示例。无需任何臃肿的框架：

```
package main

import (
    "fmt"
    "net/http"
)

func main() {
    http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintf(w, "Hello, your MRR is safe here.")
    })
    
    // This will comfortably handle 10,000s of requests per second
    // on a potato.
    http.ListenAndServe(":8080", nil) 
}
```

#### 使用本地 AI 执行长时间运行的任务

如果你家里有显卡，你就已经拥有 *无限的* AI 积分了。

我在开发 eh-trade.ca 时遇到了一个具体问题：我需要对数千家公司进行深入的定性股票市场研究，并汇总大量的季度报告。最简单的解决方法是把所有数据都交给 OpenAI API。我可能要花几百美元购买 API 额度，结果却发现提示循环中存在逻辑错误，导致我不得不重新运行整个批处理。

相反，我用的是在一张从 Facebook Marketplace 上淘来的、积满灰尘的 900 美元显卡（RTX 3090，24GB 显存）上运行 VLLM。当然，这是一笔前期投资，但我再也不用为批量处理向 AI 提供商支付任何费用了。

对于本地人工智能，您有一条独特的升级路径：

- **先从 Ollama 开始。** 它只需一条命令即可完成设置（ `ollama run qwen3:32b` ），并可让您立即尝试数十种模型。它是迭代提示的理想环境。
- **生产环境应迁移到 VLLM。** 一旦系统运行正常，Ollama 就会成为并发请求的瓶颈。VLLM 会将 GPU 锁定到单个模型，但由于采用了 PagedAttention 技术，速度 *大幅* 提升。系统架构应确保同时发送 8 或 16 个异步请求。VLLM 会将这些请求批量加载到 GPU 内存中，所有 16 个请求的处理时间与处理单个请求的时间大致相同。
- **对于更高级的操作，请使用 Transformer Lab。** 如果您需要进行任何模型预训练或微调， [Transformer Lab](https://lab.cloud/) 可以让您在本地硬件上轻松完成。

为了管理这一切，我构建了 [laconic](https://github.com/smhanov/laconic) ，这是一个专门针对在受限的 8K 上下文窗口中运行而优化的智能研究工具。它像操作系统的虚拟内存管理器一样管理 LLM 上下文——它会将对话中无关的信息“分页”出去，只在活动的 LLM 上下文窗口中保留绝对最关键的事实。

我还使用 [llmhub](https://github.com/smhanov/llmhub) ，它将任何 LLM 抽象为一个简单的提供程序/端点/apikey 组合，无论模型是在我的办公桌下运行还是在云端运行，都能优雅地处理文本和图像 IO。

#### 使用 OpenRouter 实现快速/智能 LLM

并非 *所有事情* 都能在本地完成。有时，你需要像 Claude 3.5 Sonnet 或 GPT-4o 这样最先进的推理算法，才能实现面向用户的低延迟聊天交互。

与其费力地管理 Anthropic、Google 和 OpenAI 的账单账户、API 密钥和速率限制，我只需使用 OpenRouter。你只需在代码中编写一个与 OpenAI 兼容的集成，即可立即访问所有主流前沿模型。

更重要的是，它支持无缝回退路由。如果 Anthropic 的 API 在周二下午宕机（这种情况确实会发生），我的应用会自动回退到等效的 OpenAI 模型。我的用户不会看到任何错误提示，我也无需编写复杂的重试逻辑。

#### 用 Copilot 代替那些被大肆宣传的 AI IDE

每周都有价格高得离谱的新模型发布。我经常听说开发者每月花费数百美元订阅 Cursor 服务或购买 Anthropic API 密钥，仅仅为了让 AI 帮他们编写样板代码。

与此同时，我整天都在使用 Claude Opus 4.6，但我的账单每月却几乎不到 60 美元。我的秘诀是什么？我利用了微软的定价模式。

我在 2023 年购买了 GitHub Copilot 的订阅，将其集成到标准的 VS Code 中，之后就一直使用至今。我也尝试过 Cursor 和其他一些花哨的衍生版本，它们曾经凭借智能编码功能短暂地超越了 Copilot，但 Copilot Chat 总能迎头赶上。

这里有个你可能没注意到的诀窍：微软居然能按请求收费，而不是按令牌收费。而所谓的“请求”，其实就是我在聊天框里输入的内容。就算客服花了半个小时仔细检查我的整个代码库，映射依赖关系，修改数百个文件，我也只需要支付大约 0.04 美元。

最佳策略很简单：编写极其详细的提示，并设定严格的成功标准（无论如何，这都是最佳实践），告诉代理“继续运行直到所有错误都得到修复”，按下回车键，然后去泡杯咖啡，让萨蒂亚·纳德拉补贴你的计算成本。

#### Use SQLite for everything

我总是用 `sqlite3` 作为主要数据库来启动新项目。听我解释，这并不像你想的那么疯狂。

企业思维认为你需要一个进程外数据库服务器。但事实是，本地 SQLite 文件通过 C 接口或内存进行通信的速度比通过 TCP 网络跳转到远程 Postgres 服务器快几个数量级。

“但是并发性怎么办？”你可能会问。很多人认为 SQLite 每次写入都会锁定整个数据库。这是错误的。你只需要启用预写式日志（WAL）。在打开数据库时执行一次以下编译指示：

```
PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;
```

搞定！读者不再阻塞写者，写者也不再阻塞读者。现在，您只需在 NVMe 驱动器上的单个 `.db` 文件上操作，即可轻松处理数千个并发用户。

由于实现用户身份验证通常是启动基于 SQLite 的新项目时最令人头疼的部分，我开发了一个库： [smhanov/auth](https://github.com/smhanov/auth) 。它可以直接与您使用的任何数据库集成，并管理用户注册、会话和密码重置。它甚至允许用户使用 Google、Facebook、X 或他们公司特定的 SAML 提供商登录。没有臃肿的依赖项，只有简洁、可审计的代码。

#### Conclusion

科技行业想让你相信，打造一家真正的企业需要复杂的协调、巨额的每月 AWS 账单和数百万美元的风险投资。

It doesn't.

只需一台 VPS、静态编译的二进制文件、用于批量 AI 任务的本地 GPU 硬件以及 SQLite 的高速性能，你就能快速启动一个高度可扩展的创业项目，每月成本甚至低于几杯咖啡。这为你的项目提供了无限的资金储备，让你有时间真正解决用户的问题，而不是为资金消耗速度而担忧。

## 通俗精炼（1）

### 2026-04-13 06:28:51

#### 用极简技术栈，跑出多家高收入小公司

##### 核心观点

作者的核心主张很简单：**创业早期不需要复杂基础设施，也不需要高额融资**。  
只要用足够轻、足够稳的技术方案，就能以极低成本跑起一个真正赚钱的业务，把时间和精力放在找到产品市场匹配，而不是 “堆架构” 上。

##### 为什么要极简

作者认为，很多创业公司一开始就上 AWS、Kubernetes、RDS 等 “企业级” 方案，本质上是**过度建设**。  
这会带来两类问题：

- 成本过高，产品还没验证就先背上固定支出
- 系统过于复杂，团队大量时间耗在运维而不是用户价值上

相比之下，**低成本、低复杂度 = 更长的生存时间 + 更高的试错效率**。

##### 作者的技术选择

###### 1. 服务器：一台便宜 VPS 就够了

作者建议直接用 Linode、DigitalOcean 这类**5~10 美元 / 月的 VPS**，而不是一上来就用 AWS。  
理由是：

- 足够便宜，试错成本低
- 架构简单，问题定位更直接
- 对早期产品来说，真正目标是 “先把请求处理好”，不是搭基础设施秀肌肉

一句话：**先解决业务问题，再解决规模问题。**

###### 2. 后端语言：用 Go，追求低资源占用和易部署

作者偏爱 Go，核心原因有三点：

- 性能高，内存占用低，适合小机器
- 强类型，代码更稳定
- 部署简单，可直接编译成单个二进制文件上传运行

这背后的逻辑不是 “Go 最先进”，而是：  
**在资源有限时，选能省机器、省运维、省部署成本的语言。**

###### 3. AI 任务：能本地跑，就别一直烧 API

对于大批量、长时间运行的 AI 任务，作者建议尽量本地化。  
他用一张二手高性能显卡跑本地模型，替代反复购买云端 API 调用。

他的判断是：

- 小规模试验可以先用 Ollama
- 稳定生产可转向 VLLM 提升并发效率
- 需要训练或微调时再上更专业工具

本质上，这是一种**“用一次硬件投入，换长期边际成本下降”**的思路。

###### 4. 前沿模型调用：用 OpenRouter 做统一入口

并不是所有 AI 场景都适合本地模型。  
如果要做面向用户的高质量对话体验，仍然需要调用 Claude、GPT 等先进模型。

作者选择 OpenRouter，原因是：

- 用一套兼容 OpenAI 的接口接入多家模型
- 减少多平台账号、计费和限流管理成本
- 某家模型服务故障时可自动切换，提升稳定性

也就是说：**本地模型负责降本，云端模型负责体验，统一路由负责灵活性。**

###### 5. 开发工具：Copilot 比高价 AI IDE 更划算

作者认为，很多开发者在 AI 编码工具上花了太多钱。  
他的做法是使用 GitHub Copilot + VS Code，而不是订阅更昂贵的 AI IDE。

关键原因不是功能绝对最强，而是：  
**性价比足够高，且能完成大部分编码辅助工作。**

##### 数据库选择：SQLite 不是玩具

###### 为什么作者推荐 SQLite

作者强调，SQLite 完全可以作为很多新项目的主数据库。  
理由包括：

- 本地文件读写极快
- 不需要单独部署数据库服务
- 配置简单，维护成本低

只要开启 WAL 模式，SQLite 的并发能力就会比很多人想象中更强。

###### 适用边界

作者的观点不是 “SQLite 永远最好”，而是：  
**在产品早期、写压力不极端时，SQLite 往往是最省事、最划算的方案。**

评论区也有人提醒：如果写入非常频繁，PostgreSQL 可能更合适。  
这说明作者提倡的是**按阶段选型**，而不是教条主义。

##### 文章真正想表达的，不只是技术

这篇文章表面在讲技术栈，实际上在讲一种创业观：

###### 1. 不要把 “专业” 误解为 “复杂”

很多团队把复杂架构当成成熟的象征，  
但作者认为，真正成熟的做法是：**用最小代价支撑真实业务。**

###### 2. 早期最稀缺的不是技术，而是生存时间

如果每月基础设施成本很低，创业者就拥有更长的试错窗口。  
这意味着你可以更从容地打磨产品，而不是被融资和现金流倒逼。

###### 3. 创业初期应优先优化 “效率”，而不是 “面子工程”

一台 VPS、Go、SQLite、本地 GPU，这套组合听起来不 “豪华”，  
但作者强调：**能赚钱、能迭代、能长期活下去，才是好架构。**

##### 一句话总结

这篇文章的核心不是 “某个技术更厉害”，而是：  
**创业早期，用最简单、最便宜、最可控的技术，把产品跑起来，比追求大而全的企业级架构更重要。**

## 结构化（1）

### 2026-04-13 06:30:33

#### 文章主旨

这篇文章的核心观点是：**做一家能赚钱的软件公司，并不一定需要昂贵的云架构、复杂的企业级工具或风投资金**。作者用自己的经验说明，靠一套**每月约 20 美元**的精简技术栈，也能同时运营多家**MRR 达到 1 万美元级别**的公司。

#### 1. 为什么作者坚持 “极简创业”

- 作者提到，自己的项目已经有**MRR**，也有用户每天在用，但路演时仍被投资人质疑：“**你们到底需要资金做什么？**”
- 他认为，**把成本压到接近 0**，效果其实相当于拿到一大笔融资但极度省钱地使用：都能换来足够长的 “生存时间” 去寻找产品市场匹配。
- 这种方式的好处是：
  - 压力更小；
  - 架构更简单；
  - 不用被董事会和融资节奏牵着走。
- 作者的立场很明确：**重点应该是服务用户，而不是维护一套昂贵又复杂的基础设施。**

#### 2. 服务器：别一上来就 AWS，用便宜 VPS 就够了

- 作者批评很多人一开始就上 AWS、EKS、RDS、NAT 网关，还没用户就先烧钱。
- 他举的典型场景是：**还没人访问登录页，每月就可能 “意外花掉 300 美元”**。
- 他的建议是直接租一台便宜可靠的**VPS**，如：
  - `Linode`
  - `DigitalOcean`
- 成本大约是：**每月 5 到 10 美元**。
- 即使只有**1GB 内存**，作者也认为够用：
  - 如果需要缓冲，可以加**swap（交换文件）**；
  - 单机的好处是日志、故障原因、重启方式都很清楚。
- 核心思想：**你要处理的是请求，不是基础设施。**

#### 3. 后端语言：作者首选 Go，因为轻、快、好部署

- 在只有**1GB 内存**的前提下，作者不建议用 Python 或 Ruby 作为主后端：
  - 解释器和进程管理本身就会吃掉很多内存。
- 他选择**Go**，理由有 3 个：
  - **性能高**，做 Web 服务非常合适；
  - **强类型**，代码更稳；
  - 对当下的**LLM/AI 辅助编程**也更友好。
- 作者尤其强调 Go 的部署体验：
  - 不需要处理`pip install`、虚拟环境等依赖地狱；
  - 直接在本地编译成一个**静态二进制文件**；
  - 用`scp`传到服务器就能跑。
- 他还给出一个极简 Web 服务示例，并表示这种简单 Go 服务在很普通的机器上也能轻松处理：
  - **每秒数万请求（10,000s of requests per second）**

简单理解：**Go 的优势不只是 “跑得快”，更重要的是 “省心、省资源、上线简单”。**

#### 4. AI 任务：能本地跑就别一直买 API

- 作者在做`eh-trade.ca`时，需要对**数千家公司**做定性研究，并总结大量季报。
- 如果全交给 OpenAI API，不仅可能要花**几百美元**，而且一旦提示词逻辑有问题，整批任务可能要重跑，成本会继续放大。
- 他的做法是：买一张二手显卡本地跑模型。
  - 设备：**RTX 3090**
  - 显存：**24GB**
  - 价格：**900 美元**
- 这是一笔前期投入，但之后批量 AI 任务几乎不再需要持续支付 API 费用。

##### 本地 AI 的推荐路线

- **先用 Ollama**
  - 一条命令就能启动，例如：`ollama run qwen3:32b`
  - 适合快速试模型、调提示词。
- **生产环境换成 VLLM**
  - Ollama 在并发请求下容易成为瓶颈；
  - VLLM 借助**PagedAttention**，吞吐高很多；
  - 系统设计上应一次发**8 或 16 个异步请求**；
  - 这些请求可被批量送入 GPU，**16 个请求的总耗时接近 1 个请求**。
- **需要训练或微调时用 Transformer Lab**
  - 方便在本地硬件上做预训练或微调。

##### 作者自己的工具

- `laconic`
  - 一个研究型 AI 工具，针对**8K 上下文窗口**做优化；
  - 工作方式类似 “虚拟内存管理”，把不重要的信息 “分页” 出去，只保留当前最关键的信息。
- `llmhub`
  - 把任何 LLM 抽象成统一的`provider/endpoint/apikey`形式；
  - 无论模型在本地还是云端，都能统一处理文本和图像输入输出。

#### 5. 云端大模型：需要时再接入，用 OpenRouter 降低复杂度

- 作者并不是完全排斥云端模型。
- 他的观点是：**不是所有事都适合本地模型**。如果需要面向用户的低延迟高质量对话，还是要用顶级模型，比如：
  - `Claude 3.5 Sonnet`
  - `GPT-4o`
- 他选择用**OpenRouter**，而不是分别管理 Anthropic、OpenAI、Google 的账号、密钥和限流规则。
- OpenRouter 的价值主要有两个：
  - 提供**OpenAI 兼容接口**，接入简单；
  - 支持**自动回退路由**。
- 例如：
  - 如果 Anthropic 在某个时间段宕机，
  - 系统可以自动切换到 OpenAI 的同级模型，
  - 用户不会看到报错，
  - 开发者也不用自己写复杂的重试逻辑。

一句话概括：**本地模型负责便宜批处理，云端顶级模型负责关键交互体验。**

#### 6. AI 编程工具：作者更推荐 Copilot，而不是昂贵 AI IDE

- 作者提到，很多开发者为了 AI 编程，每月在 Cursor 或 Anthropic API 上花**几百美元**。
- 但他自己几乎整天用**Claude Opus 4.6**，月账单却通常**不到 60 美元**。
- 关键原因是他利用了**GitHub Copilot**的计费方式：
  - 微软更像是按 “**请求**” 收费，而不是严格按 token 收费；
  - 他举例说，即使 AI 花了半小时审查整个代码库、改了几百个文件，成本也可能只有**约 0.04 美元**。
- 他的最佳实践是：
  - 写**非常详细**的提示；
  - 设定**严格的成功标准**；
  - 直接告诉代理：“**继续运行直到所有错误修复完成**”；
  - 然后让 AI 长时间执行。
- 核心意思：**与其追求花哨 IDE，不如利用成熟工具和更划算的计费模式。**

#### 7. 数据库：大多数新项目，SQLite 就够了

- 作者说自己做新项目时，**总是先用 SQLite**。
- 他认为很多人默认需要独立数据库服务，这是 “企业思维” 带来的惯性。
- 他的论点是：
  - 本地 SQLite 文件通过 C 接口或内存访问；
  - 比通过 TCP 去连远程 Postgres，速度要快**几个数量级**。
- 针对大家最常见的质疑 —— 并发问题 —— 他给出了解法：
  - 开启**WAL（预写日志）**
  - 设置：
```sql
PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;
```
- 开启后效果是：
  - **读不会阻塞写**
  - **写也不会阻塞读**
- 他认为，在**NVMe**硬盘上的单个`.db`文件，也能轻松支撑：
  - **数千并发用户**

##### 身份认证方案

- 作者还写了一个库：`smhanov/auth`
- 功能包括：
  - 用户注册
  - 会话管理
  - 密码重置
  - 第三方登录
- 支持的登录方式包括：
  - Google
  - Facebook
  - X
  - 企业 SAML
- 他强调这个库的特点是：**依赖少、代码简洁、容易审计。**

#### 8. 结论：真正的 “跑道” 来自低成本，而不是融资

- 作者最后再次强调：**科技行业常让人误以为，真正的公司必须依赖复杂协作、大额 AWS 账单和风投支持。**
- 但他的结论是：**并不需要。**
- 只要有下面这套组合，就能非常低成本地启动并运营高可扩展的业务：
  - 一台便宜**VPS**
  - **Go**编译出的静态二进制
  - 本地**GPU**跑批量 AI
  - **SQLite**做主数据库
- 这样做的结果是：
  - 月成本低到可能还不如几杯咖啡；
  - 项目拥有更长的试错时间；
  - 创业者可以把精力放在**解决真实用户问题**上，而不是担心烧钱速度。

#### 9. 评论区里的补充观点与争议

##### 认同的声音

- 很多评论者表示赞同，认为：
  - VPS + Go + SQLite 确实是做小型创业项目的高性价比方案；
  - 过去很多人本来就是这样做项目的，只是后来被 “大厂云服务” 带偏了。
- 有人补充自己的实践：
  - 用**Cloudflare Workers**可以**每月 5 美元**托管很多网站；
  - 有人用本地 GPU + SQLite + Python 跑多服务系统，**40 天生成 34,000 个策略**；
  - 通过先用免费模型、再用付费 API 兜底，AI 成本从**每天 0.63 美元降到 0.02 美元**。

##### 不同意见

- 也有人提出明显风险：
  - 单机架构在**稳定性、可扩展性、安全性**方面存在上限；
  - 一旦业务爆发，迟早还是要升级到更复杂架构。
- 关于数据库，也有人指出：
  - SQLite 虽然适合很多场景，但在**高写入压力**下会遇到瓶颈；
  - 同样在廉价硬件上，**PostgreSQL**有时能提供更稳定的吞吐。
- 还有人认为：
  - Go 很好，但 Python 生态更丰富、招聘更容易；
  - Docker/Kubernetes 虽然更重，但在团队协作和后期扩展上更有优势。

#### 一句话总结

作者想表达的不是 “永远别用云、别用企业架构”，而是：**在产品还没证明自己之前，先用最便宜、最简单、最可控的方式活下来；等真的增长了，再升级也不迟。**
