## 解读（1）

### 2026-07-03 11:35:52

##### 一、深度总结

这条内容的核心观点是：

> **小团队做 Agent，不要从零手搓完整系统，而应基于成熟开源框架，构建适合自己业务场景的 Agent Harness。**

具体来说：

- **Agent 落地难，不是模型不够强，而是基础设施太耗人。**
  很多团队还没拿到业务反馈，就已经被工具调用、状态管理、上下文组织、任务拆解、执行循环等底层工程拖垮。

- **小团队最优策略：借力开源资产。**
  比如基于 `pi` 这样的开源 Agent 架构，进行二次开发，而不是自己从零搭建完整 Agent。

- **真正拉开差距的不是“会不会调模型”，而是 Harness 设计能力。**
  也就是：如何把业务需求，转化成 Agent 可执行、可控制、可迭代的工作系统。

- **Agent 产品的竞争力来自两部分：**
  1. 用户看得见的：交互体验、UI/UX、响应效果；
  2. 用户看不见的：工具选择、流程编排、上下文管理、任务边界、失败处理。

- **一切设计都要贴合业务。**
  Agent 不是炫技项目，而是服务具体业务目标的工程系统。

---

##### 二、深入浅出解读

可以把 Agent 项目理解成“造一辆车”。

很多人一开始想的是：

> 我要自己造发动机、轮胎、底盘、方向盘、导航系统。

结果还没开上路，团队就累死了。

更聪明的做法是：

> 直接使用成熟底盘和零件，然后根据自己的业务场景，改装成适合送外卖、跑长途、越野或载人的车。

这里的：

- **开源 Agent 框架** = 底盘和基础零件；
- **Harness** = 把模型、工具、任务、记忆、流程、交互串起来的业务外壳；
- **业务需求** = 这辆车到底要干什么；
- **工程师能力差距** = 谁更会把通用框架改造成真正可用的业务系统。

所以，重点不是“我能不能写一个 Agent”，而是：

> 我能不能让 Agent 在具体业务里稳定、可控、高效地产生价值。

---

##### 三、关键概念：什么是 Harness？

在这里，**Harness** 可以理解为：

> 包裹和驱动 Agent 的业务运行系统。

它负责把大模型能力真正接入业务流程，包括：

- 什么时候调用模型；
- 给模型什么上下文；
- 允许它使用哪些工具；
- 如何拆解任务；
- 如何检查结果；
- 出错后如何恢复；
- 怎样让用户更自然地交互；
- 如何让系统持续迭代。

一句话：

> **模型只是大脑，Harness 是神经系统、工具箱和操作流程。**

---

##### 四、这条内容真正想表达的判断

作者其实在说：

> Agent 时代，工程师的核心竞争力正在从“写代码”转向“设计 AI 工作流和业务系统”。

未来重要的能力不是单纯会：

- 调 API；
- 写 prompt；
- 接一个模型；
- 做一个聊天框。

而是会：

- 理解业务；
- 抽象流程；
- 设计工具；
- 控制 Agent 行为；
- 优化交互体验；
- 利用开源框架快速验证；
- 把 AI 能力变成真实业务产出。

---

##### 五、辩证思考

###### 1. 不手搓是对的，但不能只会“套壳”

基于开源框架开发，能节省大量时间，尤其适合小团队。

但风险是：

> 只会调框架，不懂底层原理，最后会被框架限制。

所以正确姿势是：

- 初期：用开源框架快速验证；
- 中期：理解其架构和边界；
- 后期：根据业务逐步改造关键模块。

---

###### 2. Harness 很重要，但不是万能药

很多 Agent 项目失败，不只是因为缺 Harness，也可能是：

- 业务场景不成立；
- 用户需求不刚性；
- 自动化价值不明显；
- 模型能力还不稳定；
- 成本高于收益；
- 数据和权限无法打通。

所以，不能把所有问题都归因于“框架没选好”。

真正关键的是：

> 先找到高频、明确、可验证、能产生收益的业务场景。

---

###### 3. Agent 落地需要“产品 taste”，不只是工程能力

作者提到 taste 很重要，这是非常关键的一点。

因为 Agent 产品不是传统软件。

它的体验取决于：

- 它问不问废话；
- 它会不会打断用户；
- 它能不能主动补全信息；
- 它出错时是否可理解；
- 它的行动边界是否清晰；
- 用户是否信任它继续操作。

这类能力不只是技术问题，也是产品判断和交互设计问题。

---

##### 六、最终结论

小团队做 Agent，最现实的路线是：

> **不要从零造 Agent，而是基于成熟开源框架，围绕具体业务设计专属 Harness。**

未来真正有价值的工程师，不只是会写代码的人，而是能把：

> 业务理解 + Agent 架构 + 工具调用 + 交互体验 + 产品 taste

融合起来，做出真正可落地系统的人。

## 结构化（1）

### 2026-07-23 10:09:06

> **主旨：** 小团队不应从零“手搓”完整的 Agent，而应复用成熟的开源基础设施，集中精力打造适配具体业务的 **Agent Harness（运行与业务编排层）**。未来工程师的核心差异，将体现在把业务需求转化为交互、工具、流程和体验设计的能力上。

##### 1. Agent 项目难落地的主要原因

- 很多团队在获得真实业务反馈前，就把大量时间耗在自建 Agent Harness 等基础设施上。
- Cursor、Claude Code 等产品展示了 AI 编程的能力，但要让 Agent 真正进入业务，仍需要完善其工具调用、任务流程、交互方式和运行环境。
- 对资源有限的小团队而言，重复开发底层能力通常成本高、验证慢，也容易偏离实际业务价值。

##### 2. 更适合小团队的方法：基于开源项目二次开发

- 作者建议直接利用成熟的开源资产，再构建面向特定领域的 Harness，而不是从头实现完整 Agent。
- 文中以开源项目 **[pi](https://github.com/earendil-works/pi)** 为例：
  - 架构极简；
  - Agent 的核心结构较完整；
  - 便于理解、修改和二次开发；
  - 适合成为垂直业务 Agent 的底座。
- 作者正在 pi 之上，结合 Grok Build 进行 Harness 设计，并认为 Grok 的表现有些接近 Claude Opus 的风格。

##### 3. 真正拉开差距的是 Harness 设计能力

Harness 的价值不只是“套一个框架”，而是把业务需求转化为 Agent 可以稳定执行的系统，重点包括：

- **交互设计：** 用户如何提出需求，Agent 如何追问、反馈和确认。
- **工具选择：** Agent 应接入哪些搜索、代码、数据库或业务系统工具。
- **流程编排：** 任务如何拆解、执行、检查和纠错。
- **设计品味（Taste）：** 如何取舍功能、复杂度和使用体验。
- **UI/UX：** 既包括用户看得见的界面，也包括看不见但能感受到的响应方式、稳定性和流畅度。

这些设计都必须贴合具体业务，而不是为了技术完整而堆叠功能。

##### 4. 后续实践与社区观点

- 作者随后整理了“如何学习 pi，以及如何让 Agent 接入业务”的完整方法，并开源了配套项目 **`pi-docs-playbook`**。
- 其使用思路是：把这套材料交给能力较强的 Coding Agent，让它按照正确的项目地图阅读代码、主动询问业务需求，再进行针对性扩展。
- 热门回复用一个形象比喻概括了这一观点：

> 不要在房间里从零手搓一台电脑，而应购买机壳和成熟零件进行组装。真正决定 Agent 能否落地的是 Harness，底层模型更像是在选择“显卡”。

##### 5. 核心结论

小团队最有效的路线是：

1. 选择结构清晰、可扩展的开源 Agent 项目作为底座；
2. 尽快接入真实业务并获取用户反馈；
3. 把资源投入到业务流程、工具连接、交互和 UI/UX 上；
4. 通过领域化 Harness 形成真正的产品壁垒，而不是重复建设通用基础设施。
