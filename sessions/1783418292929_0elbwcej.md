#### Installation

oh-my-openagent ships in two editions of the same product:

- **Ultimate Edition (omo for OpenCode)** — full omo. 11 agents, 54+ lifecycle hooks, 5 built-in MCPs, all slash commands, Team Mode, ulw-loop, ultrawork, hashline edits — everything.
- **Light Edition (omo for Codex CLI)** — the portable components that fit Codex's plugin system: `rules`, `comment-checker`, `git-bash`, `lsp`, `ultrawork`, `ulw-loop`, `start-work-continuation`, and `telemetry`, plus plugin-scoped MCPs for `grep_app`, `context7`, `codegraph`, `git_bash`, and `lsp`, and the shared `ast-grep` skill. No agent orchestration and no `team_*` tools — Codex CLI's own surface does that work.

Pick the edition(s) you want.

##### Telemetry

Anonymous telemetry is enabled by default to track active installations (DAU/WAU/MAU). For both products, a single event is sent **at most once per UTC day per machine** using a SHA256-hashed installation identifier (never the raw hostname), and PostHog person profiles are not created. The main plugin emits `omo_daily_active` from plugin load (`plugin_loaded`) and CLI run (`run_started`) sources; the Codex CLI Light edition emits `omo_codex_daily_active` from two sources (`install_completed` and `session_start`).

Opt out per product:

- Main plugin: set `"telemetry": false` in oh-my-openagent config, `OMO_DISABLE_POSTHOG=1`, or `OMO_SEND_ANONYMOUS_TELEMETRY=0`
- Codex CLI Light edition: `OMO_CODEX_DISABLE_POSTHOG=1` or `OMO_CODEX_SEND_ANONYMOUS_TELEMETRY=0` (the global flags also disable Codex)

##### Skill-Embedded MCPs

MCP servers eat your context budget. We fixed that.

Skills bring their own MCP servers. They spin up on demand, scoped to the task, and go away when done. The context window stays clean.

The harness problem is real. Most agent failures aren't the model's fault; it's the edit tool.

> *"None of these tools give the model a stable, verifiable identifier for the lines it wants to change... They all rely on the model reproducing content it already saw. When it can't - and it often can't - the user blames the model."*
>
> \- [Can Bölük, The Harness Problem](https://blog.can.ac/2026/02/12/the-harness-problem/)

Inspired by [oh-my-pi](https://github.com/can1357/oh-my-pi), we built **Hashline**. Every line the agent reads comes back tagged with a content hash:

```
11#VK| function hello() {
22#XJ|   return "world";
33#MB| }
```

The agent edits by referencing those tags. If the file has changed since the last read, the hash won't match and the edit is rejected before any corruption. No whitespace reproduction. No stale-line errors.

Grok Code Fast 1: **6.7% → 68.3%** success rate, just from changing the edit tool.

#### Uninstallation

To remove oh-my-openagent:

1. **Remove the plugin from your OpenCode config**
   Edit `~/.config/opencode/opencode.json` (or `opencode.jsonc`) and remove either `"oh-my-openagent"` or the legacy `"oh-my-opencode"` entry from the `plugin` array:
   ```
   # Using jq
   jq '.plugin = [.plugin[] | select(. != "oh-my-openagent" and . != "oh-my-opencode")]' \
       ~/.config/opencode/opencode.json > /tmp/oc.json && \
       mv /tmp/oc.json ~/.config/opencode/opencode.json
   ```
2. **Remove configuration files (optional)**
   ```
   # Remove plugin config files recognized during the compatibility window
   rm -f ~/.config/opencode/oh-my-openagent.jsonc ~/.config/opencode/oh-my-openagent.json \
         ~/.config/opencode/oh-my-opencode.jsonc ~/.config/opencode/oh-my-opencode.json
   
   # Remove project config (if exists)
   rm -f .opencode/oh-my-openagent.jsonc .opencode/oh-my-openagent.json \
         .opencode/oh-my-opencode.jsonc .opencode/oh-my-opencode.json
   ```
3. **Verify removal**
   ```
   opencode --version
   # Plugin should no longer be loaded
   ```
4. **Remove omo-codex (Codex CLI Light edition)**
   ```
   npx lazycodex-ai uninstall
   # backward-compatible alias:
   npx lazycodex-ai cleanup
   
   omo uninstall --platform=codex
   # backward-compatible alias:
   omo cleanup --platform=codex
   ```
   The uninstall command removes managed `sisyphuslabs` Codex cache/marketplace state, strips `omo@sisyphuslabs` plugin and hook-state blocks from `~/.codex/config.toml` after writing a backup, and removes agent TOML links listed in the install manifest. If a specific project still has old project-local Codex plugin state, run the command from that project or pass `--project <path>`; it repairs known project-local `.codex/config.toml` conflicts and reports project-local `.codex` artifacts without deleting project-owned files.

#### oh-my-openagent 总结：面向复杂代码库的 AI 编程编排器

##### 一句话概括

**oh-my-openagent** 是一个开源 AI 编程 Agent 编排工具，核心目标是：  
让开发者不再纠结用 Claude、Codex、Kimi、GPT、Gemini 等哪个模型，而是通过一个统一框架，把多个模型、多个 Agent、代码工具和工作流组织起来，自动完成复杂开发任务。

它的理念是：**未来不是押注单一模型，而是编排所有模型。**

---

##### 它解决什么问题

当前 AI 编程工具存在几个痛点：

- **模型割裂**：Claude Code、Codex、Cursor、OpenCode 等各自封闭，切换成本高。
- **配置复杂**：Agent、模型、MCP、规则、权限、工作流都需要手动调。
- **复杂代码库表现不稳定**：AI 容易改错行、丢上下文、任务做到一半停下。
- **单 Agent 能力有限**：复杂任务需要规划、搜索、实现、审查、调试等多角色协作。

oh-my-openagent 试图成为一层“AI 编程操作系统”，把这些能力统一封装。

---

##### 产品形态：两个版本

###### 1. Ultimate Edition：面向 OpenCode

这是完整版本，功能最全。

主要包含：

- 11 个专业 Agent
- 54+ 生命周期 Hook
- 内置 MCP 工具
- Team Mode 多 Agent 协作
- ultrawork / ulw 自动工作模式
- Hashline 精准代码编辑
- LSP、AST-Grep、Tmux 等深度集成

安装方式：

```bash
bunx oh-my-openagent install
```

---

###### 2. Light Edition：面向 Codex CLI

这是轻量版本，适配 OpenAI Codex CLI 插件体系。

主要包含：

- 规则注入
- Comment Checker
- Git Bash
- LSP
- ultrawork
- ulw-loop
- 任务续跑
- 遥测
- 部分 MCP 能力

但不包含完整 Agent 编排和 Team Mode。

安装方式：

```bash
npx lazycodex-ai install
```

---

##### 核心功能亮点

###### ultrawork：一条命令启动完整工作流

用户只需要输入：

```bash
ultrawork
```

或：

```bash
ulw
```

系统会自动调用相关 Agent、工具和模型，持续推进任务，直到完成。

这是项目最强调的核心体验：**少配置、少干预、自动干活。**

---

###### 多 Agent 编排：像组建 AI 开发团队

Ultimate 版本中包含多个角色化 Agent：

- **Sisyphus**：主调度者，负责规划、分派任务、推进完成。
- **Hephaestus**：深度执行者，负责复杂实现。
- **Prometheus**：战略规划者，会先访谈用户，再制定方案。
- **Oracle / Librarian / Explore**：分别负责架构、文档搜索、代码搜索等任务。

用户不需要手动选择模型，系统会根据任务类型自动路由到合适模型。

---

###### Team Mode：真正的多 Agent 并行协作

Team Mode 支持一个 Lead Agent 带多个成员 Agent 并行工作。

典型场景包括：

- **hyperplan**：让多个“挑刺型 Agent”从不同角度审查方案。
- **security-research**：多个安全 Agent 并行审计代码和构造 PoC。

它更像是一个 AI 开发小队，而不是单个聊天机器人。

---

###### Hashline：减少 AI 改错代码的问题

传统 AI 修改代码时，常依赖行号或文本匹配，容易因为文件变化导致改错位置。

Hashline 给每一行代码加上内容哈希，例如：

```text
11#VK| function hello() {
22#XJ| return "world";
33#MB| }
```

Agent 修改时必须引用这些带哈希的行。  
如果文件内容已经变化，修改会被拒绝，避免污染代码。

这是该项目非常重要的工程化能力。

---

###### LSP / AST-Grep / MCP：让 Agent 更像 IDE 工程师

项目集成了多种开发工具能力：

- **LSP**：代码诊断、跳转定义、查找引用、重命名。
- **AST-Grep**：基于语法树的代码搜索和批量改写。
- **MCP**：网页搜索、官方文档搜索、GitHub 代码搜索。
- **Tmux**：支持交互式终端、调试器、REPL、TUI。

这些能力让 Agent 不只是“生成代码”，而是能更准确理解和操作真实代码库。

---

##### 差异化定位

oh-my-openagent 的核心差异不是“又一个 AI 编程助手”，而是：

> 它把模型、Agent、上下文、工具、编辑器能力、任务循环和团队协作整合成一个统一的 Agent Harness。

简单说：

- Cursor 更像 AI IDE；
- Claude Code 更像单模型编程助手；
- oh-my-openagent 更像 **多模型、多 Agent 的编程编排层**。

---

##### 隐私与遥测

项目默认开启匿名遥测，用于统计 DAU / WAU / MAU。

特点：

- 每台机器每天最多发送一次事件。
- 使用 SHA256 哈希安装 ID。
- 不上传原始主机名。
- 不创建 PostHog 用户画像。

用户可以通过配置或环境变量关闭遥测。

---

##### 路线图

项目正在从“OpenCode 插件”演进为支持多个 Agent Harness 的通用框架。

未来重点包括：

- 支持 OpenCode、Codex、Pi、Claude Code 等更多平台。
- 拆分 TypeScript 核心逻辑、MCP 服务、技能、适配层。
- 让同一套能力可以复用到不同 AI 编程环境中。

---

##### 产品经理视角解读

这是一个典型的 **AI Coding Workflow Infrastructure** 项目。

它抓住了一个关键趋势：

> 单个模型的能力差距会越来越小，真正的竞争点会转向 Agent 编排、上下文管理、工具调用、代码编辑可靠性和任务闭环能力。

如果说大模型是“发动机”，oh-my-openagent 想做的是“赛车底盘 + 自动驾驶系统”。

它的价值不在于替代某个模型，而在于把多个模型组织成一个可持续工作的开发系统。

---

##### 总结

oh-my-openagent 是一个面向高级开发者和复杂代码库的开源 AI 编程编排工具。

它的核心卖点是：

- 多模型协同，而非绑定单一供应商；
- 多 Agent 并行，而非单助手对话；
- 深度工程化工具链，而非简单代码生成；
- 自动任务推进，而非频繁人工提示；
- 面向复杂代码库，而非只做 Demo 级开发。

适合重度 AI 编程用户、开源工具爱好者、复杂项目维护者，以及希望搭建 AI 开发工作流的团队尝试。

##### 具体实例：给一个大型 TypeScript 商城项目新增「优惠券叠加」功能

假设你维护一个已有项目：

```text
acme-shop/
├── apps/
│   ├── web/              # React / Next.js 前端
│   └── api/              # Node.js/ Fastify 后端
├── packages/
│   ├── pricing/          # 价格计算逻辑
│   ├── coupons/          # 优惠券规则
│   └── shared/
├── tests/
└── AGENTS.md
```

你的目标是：

> 给商城系统新增「优惠券叠加」功能：  
> 用户可以同时使用一个满减券和一个会员券，但不能同时使用两个满减券。需要更新后端校验、价格计算、前端展示、测试用例和文档。

这个任务涉及多个模块、规则校验、测试和潜在回归，非常适合使用`oh-my-openagent`的多代理、LSP、规则注入、`ultrawork`、`hyperplan`、`ulw-loop`等能力。

如果你同时使用 OpenCode 和 Codex CLI：

不要使用：


因为`omo`可能解析到另一个无关 npm 包。应使用：

##### 2. 让 Agent 帮你安装，而不是手动猜配置

- 安装的是 Ultimate、Light 还是 Both
- 修改了哪些配置文件
- 是否配置了 provider auth
- 是否启用了 Team Mode
- 是否启用了 telemetry
- 如何卸载或回滚

##### 3. 先建立安全工作区

在让 Agent 修改代码之前，先创建干净分支：

```bash
git checkout -b feat/coupon-stacking

```


不要让 Agent 在未知状态下开始大规模改动。

```text
1. Inspect git status.
2. Run baseline lint, test, and typecheck.

```

##### 4. 用`AGENTS.md`和`.omo/rules/**`固化项目规则

`oh-my-openagent`支持自动注入`AGENTS.md`和`.omo/rules/**`，这能让 Agent 每次执行任务时都理解项目约束。

示例`AGENTS.md`：

```md
# Project Rules

## General

- Use TypeScript strict mode.
- Do not introduce new runtime dependencies without approval.
- Preserve public API compatibility unless explicitly requested.
- Prefer small, reviewable commits.

## Testing

- Any pricing logic change must include unit tests.
- Any coupon behavior change must include integration tests.
- Frontend behavior changes must include component tests or story updates.

## Comments

- Do not add obvious comments.
- Comments should explain business rules, not restate code.
```

示例`.omo/rules/coupons.md`：

```md
# Coupon Rules

- A cart may contain at most one `fixed_amount` coupon.
- A cart may contain at most one `percentage` coupon.
- A `member_discount` coupon can stack with one `fixed_amount` coupon.
- Expired coupons must be rejected before price calculation.
- Coupon validation must happen server-side.
- Frontend may preview discounts but must not be the source of truth.
```

###### 最佳实践

规则文件应该写业务约束，而不是写实现细节。

好的规则：

```text
会员券可以和满减券叠加，但两个满减券不能叠加。
```

差的规则：

```text
在 coupons.ts 第 38 行加一个 if。
```

##### 6. 复杂任务先用`hyperplan`，不要直接开写

对于「优惠券叠加」这种跨前后端、测试、业务规则的任务，建议先让 Agent 规划。

示例 prompt：

```text
hyperplan

We need to implement coupon stacking in this TypeScript monorepo.

Business rules:
- A user can stack one fixed amount coupon with one member discount coupon.
- A user cannot stack two fixed amount coupons.
- Expired coupons must be rejected before calculation.
- Backend validation is the source of truth.
- Frontend should display the stacked discount breakdown.

Please:
1. Inspect the codebase.
2. Identify affected modules.
3. Ask clarifying questions if needed.
4. Produce an implementation plan.
5. Identify risky areas and regression cases.
6. Do not modify code yet.
```

###### 最佳实践

让`hyperplan`或规划 Agent 先输出：

- 受影响文件
- 数据模型变化
- API 变化
- 价格计算逻辑变化
- 测试策略
- 回滚方案
- 风险点

不要接受只有一句话的计划，例如：

```text
I will update coupon logic and tests.
```

应该要求类似：

```text
Plan:
1. Inspect packages/coupons for current validation model.
2. Inspect packages/pricing for discount application order.
3. Update coupon compatibility matrix.
4. Add unit tests for allowed and rejected combinations.
5. Update API response to include discount breakdown.
6. Update frontend cart summary.
7. Run lint, typecheck, unit tests, and integration tests.
```

##### 7. 用`ultrawork`执行，但给清晰边界

```text
Implement the coupon stacking feature according to the approved plan.

- Do not introduce new dependencies without asking.
- Do not refactor unrelated modules.
- Do not change formatting-only files.
- Keep changes reviewable.
```

- 明确验收标准
- 明确禁止事项
- 明确测试要求
- 明确是否允许改 API
- 明确是否允许新增依赖
- 明确最终需要什么证据

##### 11. 使用`ulw-loop`做持续收敛

- 哪些测试必须通过

##### 12. 用 Hashline 思维避免陈旧编辑

Ultimate Edition 中的 Hash-Anchored Edit Tool 用内容 hash 标识行，能减少 stale-line 错误。

在多人或多 Agent 并行时，最佳实践是要求 Agent：

```text
Before editing a file that was recently changed:
1. Re-read the latest file content.

3. Do not apply patches based on stale snippets.

```

###### 最佳实践

尤其是这些文件要谨慎：

```text
apps/web/src/components/CartSummary.tsx
```

因为多个 Agent 可能同时想改它们。

##### 13. Comment Checker：避免 AI 味注释

优惠券逻辑可能需要注释，但不要让 Agent 写无意义注释。

不推荐：


## 结构化（1）

### 2026-07-22 09:33:54

#### 文章精炼总结

**oh-my-openagent（原 oh-my-opencode，简称 OMO）是一个面向复杂代码库的开源 AI 编程代理框架，核心理念不是押注单一模型，而是统一编排 Claude、GPT、Kimi、GLM 等模型协同完成任务。** 项目主打“安装后输入 `ultrawork` 即可工作”，通过多代理协作、自动模型路由和工程工具集成，让任务持续执行直到完成。

##### 1. 项目定位：用开放编排替代单一厂商锁定

项目认为，未来不会由某一家模型提供商长期垄断，模型会越来越便宜、越来越强，因此更重要的是建立一个能够自由组合不同模型的开放框架，而不是被限制在 Claude Code 等封闭生态中。

其宣传重点包括：

- 无需手动管理 Claude Code、Codex 和各种开源模型的工作流。
- 项目已经预设代理、模型分工和工程工具，用户只需安装并输入 `ultrawork` 或 `ulw`。
- 项目声称使用 **Kimi K2.6 + GPT-5.5**，已经可以取得优于原生 Claude Code 的效果。
- README 称 Anthropic 因该项目而限制 OpenCode，但这是项目方自己的说法。

##### 2. 用户案例与实际反馈

文章列出了多项用户评价，用来说明其在大型、持续性任务上的能力：

- 有用户称，工具在 **一天内处理了 8,000 个 ESLint 警告**。
- 有用户将一个 **4.5 万行的 Tauri 应用，一夜之间转换为 SaaS Web 应用**；代理先进行需求访谈，再给问题评分和建议，第二天已得到基本可用的网站。
- 一位量化研究人员评价：如果 Claude Code 用 7 天完成相当于人类 3 个月的工作，Sisyphus 可在 1 小时内完成，并会持续工作到任务结束。
- 还有用户让代理添加游戏的蹲伏动画，自己去散步，回来后查看结果。
- 部分用户表示因此取消了 Cursor 订阅，认为开源 AI 编程体验已发生明显变化。

这些内容属于用户评价和项目宣传，并非统一基准测试结果。

##### 3. 两种版本：Ultimate 与 Light

oh-my-openagent 提供同一产品的两个版本：

| 版本 | 适用平台 | 核心能力 |
|---|---|---|
| **Ultimate Edition** | OpenCode | 完整 OMO：**11 个代理、54+ 生命周期钩子、5 个内置 MCP**、全部斜杠命令、Team Mode、`ulw-loop`、Hashline 编辑等 |
| **Light Edition** | OpenAI Codex CLI | 提供可移植组件，包括规则注入、评论检查、Git Bash、LSP、`ultrawork`、`ulw-loop`、任务续接和遥测，但不包含 OMO 自己的代理编排及 `team_*` 工具 |

Light 版不再重复实现 Codex CLI 已经提供的代理能力，而是重点补充工程工具和工作规范。它还包含 `grep_app`、Context7、CodeGraph、Git Bash、LSP 等插件级 MCP，以及共享的 AST-Grep 技能。

##### 8. 核心功能概览

###### `ultrawork` / `ulw`

用户只需输入一个关键词，即可激活完整执行流程。代理会自动拆解、并行处理并持续推进，不在中途停下。

项目给出的低成本订阅组合示例为：

- ChatGPT：**20 美元/月**；
- Kimi Code：**19 美元/月**；
- GLM Coding Plan：**10 美元/月**。

###### 主要工程能力

- **IntentGate**：先分析用户真实意图，减少对字面命令的误解。
- **LSP 集成**：支持诊断、定义跳转、引用查找、符号查询和工作区重命名。
- **AST-Grep**：可在 **25 种语言**中执行结构化代码搜索与重写。
- **后台代理**：可并行启动 **5 个以上专家代理**，并保持主上下文简洁。
- **Ralph Loop / Ulw Loop**：持续循环执行，直到任务和证据审计都完成。
- **Todo Enforcer**：代理空闲时自动推动其继续处理待办。
- **Comment Checker**：减少冗余、机械化的 AI 风格注释。
- **规则注入**：每次提示都自动加载 `AGENTS.md` 和 `.omo/rules/**`。
- **Tmux 集成**：允许代理操作 REPL、调试器和 TUI，并保持交互式会话。
- **`/init-deep`**：为大型项目生成分层的 `AGENTS.md`，提高上下文和 Token 使用效率。
- **Claude Code 兼容**：已有的 hooks、commands、skills、MCP 和插件可继续使用。

##### 9. “纪律代理”及模型分工

Ultimate 版通过多个专用代理协同工作，主要角色包括：

###### Sisyphus：总协调者

推荐模型包括：

- `claude-opus-4-7`；
- `kimi-k2.6`；
- `glm-5.1`。

它负责规划、分派任务、并行调度和持续推进，目标是不在任务完成前停止。

###### Hephaestus：自主深度执行者

默认面向 `gpt-5.5`。用户只需给出目标，不必提供详细步骤；它会自行探索代码库、研究现有模式并完成端到端实现。

###### Prometheus：战略规划者

在修改代码前进入访谈模式：

- 询问需求；
- 识别范围和约束；
- 生成详细执行计划；
- 避免过早开始编码。

项目强调每个代理都会按模型特点进行调优，用户通常无需手工切换模型。

##### 10. Team Mode：真正的多代理协作

Team Mode 是 Ultimate 版的可选功能，可将单一主代理加子代理的模式，升级为可通信的并行团队：

- 由一个 Lead Agent 领导；
- 最多可有 **8 个并行成员**；
- 使用 `team_create`、`team_send_message`、`team_task_create`、`team_status` 等工具协作；
- 可在 tmux 中实时查看各成员的工作状态。

建立在 Team Mode 上的两项能力：

- **hyperplan**：由 **5 个对抗性审查代理**从不同角度批判计划，在编码前发现问题。
- **security-research**：由 **3 个漏洞猎手 + 2 个 PoC 工程师**并行审计代码，并根据实际可利用性评估严重程度。

该模式默认关闭，需要时再启用。

##### 11. 自动任务分类与模型路由

Sisyphus 分派任务时，不直接指定具体模型，而是选择任务类别，再由框架自动映射到最适合的模型：

| 类别 | 适用任务 |
|---|---|
| `visual-engineering` | 前端、UI/UX、设计 |
| `deep` | 自主研究和端到端执行 |
| `quick` | 单文件修改、拼写修复等小任务 |
| `ultrabrain` | 高难度逻辑和架构决策 |

其中 `ultrabrain` 默认路由到 **GPT-5.5 xhigh**。这种设计减少了用户手工选择模型的负担。

##### 12. MCP、上下文控制与 Hashline 编辑

传统 MCP 服务器会长期占用上下文。项目采用“技能内嵌 MCP”方式：

- MCP 随技能按需启动；
- 只服务当前任务；
- 任务完成后退出；
- 避免无关工具持续占用上下文窗口。

项目还认为，许多代码代理失败并非模型不够聪明，而是编辑工具缺乏稳定、可验证的行标识。为此引入 **Hashline**：

```text
11#VK| function hello() {
22#XJ| return "world";
33#MB| }
```

每一行都带有内容哈希，代理通过标签引用要修改的代码。系统会验证编辑时对应内容是否仍然有效，从而减少并发修改或文件变化导致的“旧行定位错误”，提升复杂代码库中的修改可靠性。

##### 总结

oh-my-openagent 的核心价值不是提供又一个聊天式编码工具，而是构建一个开放的“多模型、多代理工程执行层”：自动选择模型、并行调度专家、接入 LSP/AST-Grep/MCP/Tmux，并通过循环执行和 Hashline 等机制提高任务完成率。完整能力集中在 OpenCode Ultimate 版；Codex Light 版则更轻量，主要为 Codex CLI 补充规则、工程工具和持续执行能力。
