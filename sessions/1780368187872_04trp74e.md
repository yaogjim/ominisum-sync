#### 加载数据

我们使用 LlamaIndex 的目录读取工具导入文档。它可以读取多种数据格式，包括 Markdown、PDF、Word 文档、PowerPoint 演示文稿、图片、音频和视频。

```python
from llama_index.core import SimpleDirectoryReader

loader = SimpleDirectoryReader(
    input_dir=docs_dir,
    required_exts=[".pdf"],
    recursive=True
)

docs = loader.load_data()
documents = [doc.text for doc in docs]
```

我们在这里使用一个简单的 PDF 目录读取器来实现解释性，但在实际应用中，您的数据摄取管道可能会从多个具有不同格式和预处理步骤的数据源中获取数据。

#### 2） 生成二进制嵌入

接下来，我们生成文本嵌入（使用 float32 类型）并将其转换为二进制向量，从而使内存和存储减少 32 倍。

```python
import numpy as np
from llama_index.embeddings.huggingface import HuggingFaceEmbedding

embed_model = HuggingFaceEmbedding(
    model_name="BAAI/bge-large-en-v1.5",
    trust_remote_code=True,
    cache_folder='./hf_cache'
)

for context in batch_iterate(documents, batch_size=512):
    # Generate float32 vector embeddings
    batch_embeds = embed_model.get_text_embedding_batch(context)
    # Convert float32 vectors to binary vectors
    embeds_array = np.array(batch_embeds)
    binary_embeds = np.where(embeds_array > 0, 1, 0).astype(np.uint8)
    # Convert to bytes array
    packed_embeds = np.packbits(binary_embeds, axis=1)
    byte_embeds = [vec.tobytes() for vec in packed_embeds]

    binary_embeddings.extend(byte_embeds)
```

这被称为二进制量化。

#### 3\) 向量索引

二进制量化完成后，我们将向量存储并索引到 Milvus 向量数据库中，以实现高效检索。

```python
from pymilvus import MilvusClient, DataType

# Initialize client and schema
client = MilvusClient("milvus_binary_quantized.db")
schema = client.create_schema(auto_id=True, enable_dynamic_fields=True)

# Add fields to schema
schema.add_field(field_name="context", datatype=DataType.VARCHAR)
schema.add_field(field_name="binary_vector", datatype=DataType.BINARY_VECTOR)

# Create index parameters for binary vectors
index_params = client.prepare_index_params()
index_params.add_index(
    field_name="binary_vector",
    index_name="binary_vector_index",
    index_type="BIN_FLAT",  # Exact search for binary vectors
    metric_type="HAMMING"   # Hamming distance for binary vectors
)

# Create collection with schema and index
client.create_collection(
    collection_name="fastest-rag",
    schema=schema,
    index_params=index_params
)

# Insert data to index
client.insert(
    collection_name="fastest-rag",
    data=[
        {"context": context, "binary_vector": binary_embedding}
        for context, binary_embedding in zip(batch_context, binary_embeddings)
    ]
)
```

索引是专门的数据结构，有助于优化数据检索操作的性能。

#### 4\) 检索

在检索阶段，我们：

- 嵌入用户查询并对其应用二进制量化
- 使用汉明距离作为搜索度量来比较二进制向量。
- 检索前5个最相似的块。
- 将检索到的块添加到上下文。

This is the implementation:

```python
# Generate float32 query embedding
query_embedding = embed_model.get_query_embedding(query)
# Apply binary quantization to query
binary_query = binary_quantize(query_embedding)

# Perform similarity search using Milvus
search_results = client.search(
    collection_name="fastest-rag",
    data=[binary_query],
    anns_field="binary_vector",
    search_params={"metric_type": "HAMMING"},
    output_fields=["context"],
    limit=5  # Retrieve top 5 similar chunks
)

# Store retrieved context
full_context = []
for res in search_results:
    context = res["payload"]["context"]
    full_context.append(context)
```

#### 5\) Generation

Moving on, we build a generation pipeline using the Kimi-K2 instruct model, served on the fastest AI inference by Groq.

We specify both the query and the retrieved context in a prompt template and pass it to the LLM.

```python
from llama_index.llms.groq import Groq
from llama_index.core.base.llms.types import (
    ChatMessage, MessageRole )

llm = Groq(
    model="moonshotai/kimi-k2-instruct",
    api_key=groq_api_key,
    temperature=0.5,
    max_tokens=1000
)

prompt_template = (
    "Context information is below.\n"
    "---------------------\n"
    "CONTEXT: {context}\n"
    "---------------------\n"
    "Given the context information above think step by step "
    "to answer the user's query in a crisp and concise manner. "
    "In case you don't know the answer say 'I don't know!'.\n"
    "QUERY: {query}\n"
    "ANSWER: "
)

query = "Provide concise breakdown of the document"

prompt = prompt_template.format(context=full_context, query=query)
user_msg = ChatMessage(role=MessageRole.USER, content=prompt)

# Stream response from LLM
streaming_response = llm.stream_complete(user_msg.content)
```

## 解读（1）

### 2026-06-02 02:43:07

##### 1. 内容总结

这篇文章讲的是：  
用**二进制量化 Binary Quantization, BQ**把 RAG 中的向量从`float32`压缩成`0/1`二进制，从而让向量存储更省内存，最高约**节省 32 倍**。

流程：

1. 读取文档，例如 PDF。
2. 生成普通浮点向量 embedding。
3. 把向量转成二进制向量。
4. 存入 Milvus，并用汉明距离检索。
5. 找到相关文档后，交给 LLM 生成回答。

作者称：  
在 PubMed 3600 万 + 向量上，检索耗时`<30ms`，整体响应`<1s`。

---

##### 2. 通俗解读

###### 什么是二进制量化？

普通向量像这样：

```text
[0.23, -0.71, 1.42, 0.05]
```

二进制量化后变成：

```text
[1, 0, 1, 1]
```

规则很简单：

```text
大于 0 → 1
小于等于 0 → 0
```

原来每个数字是`float32`，占 32 bit。  
现在每个数字只占 1 bit。

所以理论上：

```text
32 bit → 1 bit
内存减少约 32 倍
```

---

###### 为什么检索会更快？

普通向量检索要算余弦相似度、点积等，计算较重。

二进制向量只需要比较：

```text
两个 0/1 向量有多少位不同
```

这叫**汉明距离 Hamming Distance**。

例如：

```text
A = 10110
B = 10011
不同位置有 2 个
汉明距离 = 2
```

距离越小，越相似。

---

###### RAG 中它解决了什么问题？

RAG 的瓶颈之一是：

```text
向量太多 → 占内存大 → 检索慢 → 成本高
```

二进制量化的价值是：

```text
更小的向量
更快的搜索
更低的存储成本
更适合大规模检索
```

尤其适合千万级、亿级向量库。

---

##### 3. 我的意见

###### 优点

二进制量化是一个非常实用的工程技巧。

它的核心价值不是 “更聪明”，而是：

```text
更省、更快、更能扩展
```

对于大规模 RAG 系统，很有意义。

---

###### 但要注意

二进制量化会损失信息。

原来的向量包含细微信息：

```text
0.01 和 9.8 都会变成 1
-0.01 和 -7.5 都会变成 0
```

所以它可能带来：

```text
召回质量下降
语义细节损失
排序不够精确
```

实际生产中，通常不会只靠它一步完成检索。

更常见做法是：

```text
二进制向量快速召回候选
再用原始向量或 reranker 精排
最后交给 LLM 生成
```

---

##### 结论

**二进制量化适合做大规模 RAG 的第一层快速检索。**

但它不是完整答案。

推荐理解为：

```text
BQ = 让向量检索更省钱、更快的基础设施组件
不是 RAG 的全部
```

如果追求极致速度和低成本，值得用。  
如果追求最高准确率，最好搭配重排、权限过滤、多源检索一起用。

## 结构化（1）

##### 主旨概括

文章介绍了一种让 RAG 系统显著降低内存占用的技术：**二进制量化（Binary Quantization, BQ）**。通过把常规 `float32` 向量转换成二进制向量，向量存储和检索层可实现约 **32 倍内存效率提升**，并能在大规模数据上实现高速检索。

---

##### 1. 背景：为什么要用二进制量化优化 RAG

- RAG 系统通常需要存储大量文本向量，用于后续相似度检索。
- 常规嵌入向量多为 `float32` 类型，占用内存较大。
- 二进制量化将向量压缩为只包含 `0/1` 的二进制表示，从而大幅减少存储和内存开销。
- 文章提到，多家公司已在实际系统中使用类似技术：
  - **Perplexity**：用于搜索索引
  - **Azure**：用于搜索管道
  - **HubSpot**：用于 AI 助手

核心效果：  
> 使用二进制量化后，RAG 向量层可以实现约 **32 倍内存优化**。

---

##### 2. 示例目标：构建一个高速 RAG 系统

文章通过一个完整示例展示如何实现该技术。

目标是构建一个 RAG 系统，可以：

- 查询 **3600 万+ 向量**
- 检索耗时低于 **30 毫秒**
- 生成回答耗时低于 **1 秒**

使用的技术栈包括：

| 组件 | 用途 |
|---|---|
| LlamaIndex | RAG 编排与数据读取 |
| Milvus | 向量数据库 |
| Kimi-K2 | 大语言模型 |

##### 3. 整体工作流程

系统流程分为 4 个主要步骤：

1. **导入文档并生成嵌入向量**
2. **将 float32 向量转换为二进制向量**
3. **把二进制向量存入 Milvus 并创建索引**
4. **根据用户查询检索相关文档，再交给 LLM 生成回答**

简单理解就是：

> 先把文档压缩成更省内存的二进制向量，再用这些向量做快速相似度搜索，最后让大模型基于检索到的上下文回答问题。

##### 5. 生成二进制嵌入：实现 32 倍压缩的关键

接下来，系统先使用 HuggingFace 模型生成普通文本嵌入，再进行二进制量化。

使用的嵌入模型是：

```text
BAAI/bge-large-en-v1.5
```

量化过程大致是：

1. 生成 `float32` 向量
2. 判断每个数值是否大于 0
3. 大于 0 转为 `1`，否则转为 `0`
4. 将二进制位打包成字节存储

核心代码逻辑：

```python
binary_embeds = np.where(embeds_array > 0, 1, 0).astype(np.uint8)
packed_embeds = np.packbits(binary_embeds, axis=1)
```

通俗理解：

> 原本每个向量维度要用 float32 存储，现在只用 1 个 bit 表示正负方向，因此存储占用大幅下降。

这就是文章所说的 **Binary Quantization（二进制量化）**。

---

##### 6. 向量索引：用 Milvus 存储和检索二进制向量

完成二进制量化后，系统将向量存入 Milvus。

重要设置包括：

- 向量字段类型：`BINARY_VECTOR`
- 索引类型：`BIN_FLAT`
- 距离度量：`HAMMING`

其中，**汉明距离（Hamming Distance）** 用来比较两个二进制向量之间有多少位不同。

例如：

```text
向量 A: 10110
向量 B: 10011
不同位数为 2，因此汉明距离为 2
```

汉明距离越小，说明两个向量越相似。

文章中的索引设置：

```python
index_type="BIN_FLAT"
metric_type="HAMMING"
```

关键点：

- Milvus 专门支持二进制向量索引。
- 索引可以提升大规模向量检索性能。
- 二进制向量配合汉明距离，可以实现更快、更省内存的搜索。

---

##### 7. 检索阶段：查询也要做二进制量化

当用户输入问题时，系统会：

1. 生成用户查询的普通向量
2. 对查询向量进行二进制量化
3. 用汉明距离在 Milvus 中搜索
4. 返回最相似的前 5 个文本块
5. 将这些文本块作为上下文交给大模型

示例中设置：

```python
limit=5
```

也就是检索 **Top 5** 个最相关片段。

核心思路：

> 文档向量和查询向量都被转成二进制形式，然后用汉明距离快速比较相似度。

---

##### 8. 生成阶段：用 Kimi-K2 基于上下文回答

检索到相关文档后，系统将这些上下文和用户问题一起放入 Prompt，再交给大语言模型生成回答。

#### 如何使 RAG 32 倍内存高效：精炼解读

##### 1. 启发

这篇内容的核心不是“又一个更快的 RAG Demo”，而是一个更重要的产品与系统启发：

> **在 AI 产品中，很多性能瓶颈并不一定要靠更大的模型解决，而可以通过基础设施层的表示压缩、索引优化和检索策略解决。**

二进制量化，Binary Quantization，简称 BQ，本质上是把原本 `float32` 的向量表示压缩成二进制向量。

原始向量通常是：

```text
[0.12, -0.47, 0.98, ...]
```

二进制量化后变成：

```text
[1, 0, 1, ...]
```

如果用 `float32`，每个维度需要 32 bit；如果转成 binary，每个维度只需要 1 bit。

所以理论上可以获得：

```text
32x 内存 / 存储压缩
```

这对于大规模 RAG 系统非常关键。因为在企业级应用里，真正昂贵的不只是 LLM 调用，还有：

- 向量索引存储成本
- 检索延迟
- 多租户权限过滤
- 大规模数据同步
- rerank 成本
- 上下文窗口管理
- 数据更新与失效机制

BQ 的价值在于：**它把向量检索层的成本大幅压低，让系统有更多预算投入到更重要的生产级能力上。**

##### 2. 高价值信息深挖

###### 2.1 二进制量化解决的不是“生成质量”，而是“检索基础设施效率”

原文容易让人误以为 BQ 可以直接让 RAG 效果变好。

更准确地说：

> **BQ 提升的是向量检索层的存储效率和查询速度，但不保证检索质量一定提升。**

它的作用主要在三层：

| 层级 | BQ 影响 |
|---|---|
| 存储层 | 大幅降低向量占用空间 |
| 检索层 | 使用 Hamming Distance，计算更快 |
| 成本层 | 降低内存、磁盘和索引成本 |

但它不会直接解决：

- chunk 切分质量差
- 文档权限复杂
- 查询意图理解错误
- 相似度召回不准
- LLM 幻觉
- 多源数据冲突
- 长上下文排序问题

所以 BQ 是一个优秀的“底层优化器”，不是完整的 RAG 解决方案。

---

###### 2.2 32 倍压缩是理论上成立，但生产中要看整体账

原文说内存效率提升 32 倍，这是基于：

```text
float32 = 32 bits
binary = 1 bit
```

如果一个 embedding 是 1024 维：

```text
float32 存储：1024 × 32 bit = 32768 bit = 4096 bytes
binary 存储：1024 × 1 bit = 1024 bit = 128 bytes
```

压缩比例：

```text
4096 / 128 = 32x
```

但在生产中，真实成本还包括：

- metadata 存储
- 文档原文存储
- chunk ID
- 权限字段
- 索引结构开销
- 数据库内部存储开销
- reranking 阶段的额外向量或文本处理
- cache 层
- 查询日志和监控

所以更准确的表达是：

> **向量本体可以压缩约 32 倍，但整个 RAG 系统的存储成本不会完整下降 32 倍。**

这点对产品和商业系统建设很重要，因为不能只看 benchmark，要看总拥有成本，TCO。

---

###### 2.3 BQ 的关键代价：语义信息损失

二进制量化的代码逻辑非常简单：

```python
binary_embeds = np.where(embeds_array > 0, 1, 0)
```

意思是：

- 大于 0 的维度变成 1
- 小于等于 0 的维度变成 0

这会丢掉大量信息。

例如：

```text
0.01 -> 1
9.87 -> 1
-0.02 -> 0
-8.41 -> 0
```

它只保留方向符号，不保留强度大小。

这意味着：

| 原始 float 向量 | 二进制向量 |
|---|---|
| 保留方向与幅度 | 只保留符号 |
| 表达更细腻 | 表达更粗糙 |
| 检索更准确 | 检索更快更省 |
| 成本更高 | 成本更低 |

所以 BQ 的核心 trade-off 是：

> **用部分语义精度换取大规模检索效率。**

这对产品决策很关键。如果你的业务是高召回、高准确场景，比如法律、医疗、金融风控，不能只追求 32x 压缩；如果是大规模候选召回、粗筛、推荐、知识库初筛，BQ 非常适合。

---

###### 2.4 BQ 更适合作为“第一阶段召回”，而不是最终排序

更成熟的架构通常不是：

```text
Binary Vector Search -> 直接给 LLM
```

而是：

```text
Binary Vector Search 粗召回
        ↓
Float Vector / BM25 / Hybrid Search 补充召回
        ↓
Cross-Encoder / LLM Reranker 精排
        ↓
权限过滤 / 新鲜度过滤 / 业务规则过滤
        ↓
送入 LLM 生成
```

也就是说，BQ 最适合放在召回链路前段，用来快速从海量数据里筛出候选集。

例如：

```text
3600 万文档
    ↓ BQ 快速召回 top 1000
    ↓ reranker 精排 top 20
    ↓ context compressor 压缩 top 5
    ↓ LLM 生成答案
```

这样既保留了速度，又避免直接使用低精度向量导致答案质量下降。

- 法律条款细节

