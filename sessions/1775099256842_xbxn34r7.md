We live in a time where it’s easier to vibe code your own mobile app than to find an existing one that you like. So let’s build an app that can:

1. **Create workouts** by selecting an exercise and then the number of sets and reps.
2. **Track workouts** live by tapping each exercise set to complete it.
3. **Measure progress** via a calendar and charts for each exercise.

I’ll walk you through how to build it in 3 steps below.

#### 1\. Define the requirements with Claude

Always ask Claude to ask you questions when defining the requirements together

Let’s start by pasting this prompt into Claude:

> Let’s work together on requirements for a mobile fitness app. I want three screens:
>
> 1. **Add/edit workouts:** Create workouts and add exercises with sets and reps
> 2. **Workout session:** Track workouts in real-time, tap to complete sets
> 3. **Calendar:** See which days you worked out and view workout details
>
> This is the basics, but let’s work on the spec together. I want you to stay crisp on the requirements, and if you have any questions, ask them in a numbered list.

The most important part of this prompt is

**“If you have any questions, ask them in a numbered list.”**

I always include this line when discussing requirements with Claude so that it can ask me questions to make the spec better. Here are a few example questions and answers:

1. Claude: Do you want a rest timer?  
   Me: Yes, also let me customize it in settings.
2. Claude: Do you want automatic deload after failed sets?  
   Me: No, let’s keep it simple.

After Claude gets the spec to a state that you’re happy with, ask it to:

“ **Split the spec into design and technical requirements. Don’t be too detailed on the design requirements so that it has room to flex.”**

Include the last line because Pencil (our AI designer) is better at design than Claude. 🙂 Let’s cover that next.

As the models get better, I’ve gotten lazier in my prompts (and worse at spelling)

## 产品-最佳实践（1）

### 2026-04-02 03:10:20

#### 基于实例的最佳实践：用 Claude + Pencil + Claude Code 做一款移动健身 App

下面我基于你提供的文章内容，选取一个更具体、可落地的实例来展开：  
**做一个 “训练记录页（Workout Session）”**，并给出围绕这个实例的一套最佳实践。

---

##### 一、具体实例

我们要做的页面是：

> 用户开始一次训练后，进入 “训练记录页”，可以看到当天训练内容，点击每一组来标记完成，查看休息倒计时，并在训练结束后保存记录。

这个页面看似简单，但其实最容易暴露一个 AI 做产品时的常见问题：  
**需求不清、设计过度、实现脱节。**

所以，这正好适合作为一个完整示例。

---

##### 二、这个实例下的推荐工作流

文章里给出的整体流程是：

1. 用 Claude 明确需求
2. 用 Pencil 产出设计
3. 用 Claude Code 完成实现

在这个实例中，最佳实践不是 “让 AI 一把梭全做完”，而是：

> **先把单一关键场景做深，再扩展到完整 App。**

也就是说，不要一开始就让 AI 同时设计 “训练创建页 + 训练记录页 + 日历页 + 图表页 + 设置页”。  
更好的方式是先拿 “训练记录页” 打通闭环。

---

##### 三、最佳实践 1：先把需求问透，再让 AI 写规格

文章里提到一个非常重要的方法：

> “如果你有问题，请用编号列表提问。”

这是最佳实践中的关键。因为很多产品失败，不是因为 AI 不会写，而是因为人没有把问题定义清楚。

###### 推荐写法

你可以这样给 Claude 下需求：

```markdown
我们一起定义一个移动健身 App 的 “训练记录页” 需求。
这个页面用于用户在训练过程中实时记录每一组动作的完成情况。

基础需求：
1. 显示今天的训练计划
2. 每个动作展示组数、次数、重量
3. 用户点击某一组后可标记为完成
4. 完成一组后自动开始休息计时
5. 用户可以结束本次训练并保存记录

请你保持需求清晰简洁。
如果你有任何不确定的地方，请用编号列表向我提问。
```

###### 为什么这是最佳实践

因为这会迫使 Claude 帮你补齐关键决策，例如：

- 一组完成后是否允许撤销？
- 休息计时器默认多久？
- 是每个动作独立计时，还是全局计时？
- 是否支持跳过某组？
- 训练中途退出是否自动保存？

这些问题如果不提前明确，后面设计和开发都会反复返工。

###### 实际建议

在这个实例里，至少要先回答这 6 个问题：

1. 完成一组后是否允许取消完成
2. 休息计时是否自动开始
3. 休息时长是否支持用户自定义
4. 训练中断时如何保存
5. 历史训练记录是否可编辑
6. 一次训练结束的判定规则是什么

---

##### 四、最佳实践 2：规格要拆成 “设计需求” 和 “技术需求”

这是你提供内容里非常值得保留的一点。

###### 为什么要拆

因为设计工具和代码工具擅长的事情不同：

- **Pencil**更适合处理界面层次、视觉表达、交互氛围
- **Claude Code**更适合处理数据结构、状态流转、业务逻辑

如果你给 Pencil 一大堆技术约束，它反而容易做得僵硬；  
如果你给 Claude Code 一堆模糊的审美描述，它就容易实现偏差。

###### 在这个实例里的拆法

###### 设计需求

```markdown
- 页面用于实时记录训练过程
- 突出 “当前动作” 和 “未完成 / 已完成组” 的状态差异
- 休息计时器要足够显眼，但不能喧宾夺主
- 用户单手操作要方便，主要点击区域要大
- 页面要给人专注、干净、有节奏感的感觉
```

###### 技术需求

```markdown
- 训练包含多个 exercises，每个 exercise 包含多个 sets
- set 状态包含：pending /completed/skipped
- 点击 set 后更新状态为 completed，并记录完成时间
- 完成 set 后自动创建 rest timer
- 页面退出时自动保存 session 草稿
- 训练完成后生成 workout history 记录
```

###### 最佳实践总结

> **设计描述抽象一些，技术描述明确一些。**  
> 这样才能让两个 AI 工具各自发挥长处，而不是互相干扰。

---

##### 五、最佳实践 3：先让 Pencil 设计 “关键状态”，不要只设计静态页面

很多人让 AI 设计界面时，只会说：

> “帮我设计一个漂亮的训练页。”

这通常会得到一个 “看起来不错，但不能真正开发” 的结果。

###### 在这个实例里，真正应该让 Pencil 输出的是 4 类状态

###### 1. 默认训练中状态
- 展示训练标题
- 当前动作卡片
- 各组待完成状态
- 底部结束训练按钮

###### 2. 某组已完成状态
- 已完成组有明显视觉反馈
- 下一组获得视觉引导
- 休息计时器开始显示

###### 3. 休息计时状态
- 倒计时清晰可见
- 支持跳过休息
- 不影响继续记录下一组

###### 4. 训练完成确认状态
- 弹出总结页或确认弹层
- 显示完成动作数、训练时长、总组数

###### 推荐给 Pencil 的提示方式

```markdown
请为一个移动健身 App 设计 “训练记录页”，输出 4 个关键状态界面：

1. 初始训练状态
2. 某一组完成后的状态
3. 休息计时中的状态
4. 训练结束确认状态

要求：
- 强调单手操作
- 点击区域明确
- 界面现代、克制、清爽
- 不要过度炫技
- 优先保证状态清晰，而不是堆砌视觉元素
```

###### 为什么这是最佳实践

因为产品不是 “一个页面”，而是 “一组状态转换”。  
你只有把状态设计清楚，Claude Code 才能顺畅实现。

---

##### 六、最佳实践 4：实现时先做状态模型，再做 UI

这是很多 AI 辅助开发里最容易犯的错：  
先让 Claude Code 直接生成页面代码，结果 UI 很快出来了，但状态逻辑混乱。

在这个训练记录页实例里，最佳实践是：

> **先定义数据结构和状态流转，再生成界面。**

###### 推荐先定义的数据模型

```ts
type SetStatus = "pending" | "completed" | "skipped";

interface WorkoutSet {
  id: string;
  reps: number;
  weight?: number;
  status: SetStatus;
  completedAt?: string;
}

interface Exercise {
  id: string;
  name: string;
  sets: WorkoutSet [];
}

interface WorkoutSession {
  id: string;
  workoutName: string;
  startedAt: string;
  exercises: Exercise [];
  restTimerSeconds?: number;
  isFinished: boolean;
}
```

###### 然后定义关键动作

```markdown
- toggleSetComplete (setId)
- skipSet (setId)
- startRestTimer (seconds)
- cancelRestTimer ()
- saveWorkoutDraft ()
- finishWorkout ()
```

###### 为什么这是最佳实践

因为一旦这些定义清楚了：

- UI 怎么画都行
- 技术栈怎么换都行
- Claude Code 实现时也更稳定
- 后续加 “历史记录”“统计图表” 也容易复用

换句话说：

> **先建业务骨架，再铺视觉皮肤。**

---

##### 七、最佳实践 5：给 Claude Code 的任务要小而明确

不要一次性下这种命令：

> “把整个健身 App 做出来，要漂亮、可上架。”

这种提示往往会导致：

- 代码结构混乱
- 页面很多但不可维护
- 状态管理半成品
- 视觉和实现对不上

###### 更好的拆分方式

在这个实例里，可以按下面顺序交给 Claude Code：

###### 第一步：只生成页面骨架
```markdown
请先实现训练记录页的静态结构，不接真实数据。
包含：
- 顶部标题
- 动作列表
- 每组按钮
- 底部结束训练按钮
```

###### 第二步：接入本地状态
```markdown
请为训练记录页接入本地状态管理：
- 点击某组可切换 completed
- 完成一组后显示休息计时器
- 支持跳过休息
```

###### 第三步：补齐持久化
```markdown
请加入本地存储：
- 页面退出自动保存训练草稿
- 返回页面后恢复训练进度
```

###### 第四步：补齐完成逻辑
```markdown
请加入训练完成逻辑：
- 点击结束训练后生成历史记录
- 清空当前 session
- 跳转到训练总结页
```

###### 最佳实践原则

> **一次只让 AI 解决一个层次的问题。**

这样更容易：
- 调试
- review
- 回滚
- 迭代优化

---

##### 八、最佳实践 6：移动端产品一定要提前约束交互细节

文章主题是 “移动 App”，所以这个实例里还有一个非常重要的最佳实践：

> **不要只描述功能，要同时描述移动端交互约束。**

###### 在训练记录页里必须提前明确的移动端细节

- 每组按钮的点击区域要足够大
- 底部主操作按钮要固定，方便单手操作
- 长列表滚动时，当前训练信息不能完全消失
- 训练中误触的恢复路径要简单
- 动画反馈要快，不能拖慢记录节奏

###### 推荐加入到需求里的说明

```markdown
这是一个高频点击的移动页面，请优先考虑：
- 单手操作便利性
- 大点击区域
- 快速视觉反馈
- 尽量减少确认弹窗
- 在运动场景下可快速读懂信息
```

###### 为什么这很重要

因为 “健身时使用” 的场景和普通工具 App 不一样：

- 用户可能在喘气
- 手上可能有汗
- 注意力不集中
- 操作需要尽可能少思考

所以这个页面最重要的不是 “好看”，而是：

> **高压场景下仍然顺手。**

---

##### 九、最佳实践 7：验收时不要只看 “能跑”，要看 “场景闭环”

在这个实例中，很多人做完后会停留在：

- 页面能打开
- 按钮能点
- 数据能保存

但这还不够。

###### 更好的验收方式

用一个真实训练流程来走查：

###### 验收场景
“今天做胸推训练，共 3 个动作，每个动作 4 组。用户完成第 1 个动作前两组后离开 App，10 分钟后回来继续训练，最后结束训练并在历史页看到这次记录。”

###### 需要验证的点

- 中途退出后是否恢复正确
- 已完成组状态是否准确
- 休息计时是否合理
- 训练结束后是否正确写入历史
- 历史页是否能看到这次训练详情

###### 最佳实践结论

> **验收要围绕完整用户任务，而不是孤立功能点。**

##### 十一、最后的结论

基于你提供的文章内容，这个实例上的最佳实践可以归纳成一句话：

> **不要让 AI 一次性 “生成一个完整 App”，而要让它围绕一个真实核心场景，先把需求、状态、设计和实现逐层打通。**

对于这个 “训练记录页” 实例，最重要的不是代码生成速度，而是这 5 点：

- 先让 AI 提问，把需求问清楚
- 设计需求和技术需求分开写
- 设计时覆盖关键状态，而非单页效果图
- 开发时先建状态模型，再做界面
- 验收时用真实用户流程检查闭环

这样做出来的产品，才更接近 “可用、可扩展、可继续迭代” 的移动 App，而不只是一个看起来不错的 Demo。
