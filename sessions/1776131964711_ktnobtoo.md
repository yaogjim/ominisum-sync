## 正文

**岚叔**

Anthropic 出了一篇多 Agent 协作模式指南，总结了 5 种架构和适用场景。

总之不要让协调复杂度超过任务本身的复杂度，干货很足，分享总结如下：

1\. Generator-Verifier（生成-验证）  
一个 Agent 出活，另一个 Agent 审核。审不过就打回重写，循环直到通过。  
适用：代码生成+测试、事实核查、合规检查。  
陷阱：验证标准不明确，就是自欺欺人。

2\. Orchestrator-Subagent（编排-子代理）  
一个主 Agent 当组长，拆任务、派活、汇总。Claude Code 用的就是这个。  
适用：任务边界清晰，子任务之间不太依赖。  
陷阱：组长是信息瓶颈，信息传递之间容易丢失。

3\. Agent Teams（团队模式）  
每个 Agent 是长期存在的"同事"，持续积累领域上下文，不是用完就丢。  
适用：大型代码库迁移，每个 Agent 负责一块独立服务。  
陷阱：Agent 之间如果共享资源，可能会冲突。

4\. Message Bus（消息总线）  
Agent 通过发布/订阅事件交互，不是直接调用。新 Agent 插进来不用改已有连线。  
适用：安全告警流水线，事件类型越来越多。  
陷阱：调试难，一个告警经过 5 个 Agent，出事了追链路很痛苦。

5\. Shared State（共享状态）  
没有中央协调者。所有 Agent 读写同一个数据库/文件系统，靠共享信息间接协作。  
适用：多 Agent 联合研究，一个人的发现另一个人直接用。  
陷阱：反应式循环——A 写了，B 读了再写，A 又读又写，无限烧 token。

核心建议： 从最简单的开始，看哪里卡住了再升级。不要一上来就选最复杂的。

这篇值得每个做 Agent 架构的人收藏。

## 结构化（1）

### 2026-04-14 03:55:26

#### 文章主旨

这篇内容总结了 Anthropic 提出的 5 种多 Agent 协作架构，以及各自适用的场景和常见陷阱。核心观点很明确：**先用最简单的协作方式，只有在真正遇到瓶颈时再升级，不要让协作复杂度超过任务本身。**

##### 1. 背景与核心判断

- 文章围绕“多 Agent 如何协作”展开，总结了 **5 种典型架构模式**。
- 作者认为这篇指南很有参考价值，尤其适合正在设计 Agent 系统或多智能体工作流的人。
- 最重要的一条原则是：**架构越复杂，协调成本越高**，如果协调本身比任务还复杂，就得不偿失。

##### 2. 模式一：Generator-Verifier（生成-验证）

- 这种模式是：**一个 Agent 负责生成结果，另一个 Agent 负责审核**。
- 如果审核不过，就打回重做，直到满足要求为止。
- 适合的场景包括：
  - **代码生成 + 测试**
  - **事实核查**
  - **合规检查**
- 关键风险在于：**如果验证标准不清楚，审核就会变成“走流程”**，表面上有检查，实际上并不能保证质量。
- 例子：比如写代码时，一个 Agent 生成函数，另一个 Agent 跑测试并检查规范；测试不过就继续返工。

##### 3. 模式二：Orchestrator-Subagent（编排-子代理）

- 这种模式里，**主 Agent 像组长一样负责拆分任务、分派工作、最后汇总结果**。
- 文中提到：**Claude Code 用的就是这种模式**。
- 它更适合：
  - **任务边界清晰**
  - **子任务之间依赖较少**
- 主要问题是：**主 Agent 容易成为信息瓶颈**。
- 一旦所有信息都要经过“组长”中转，就容易出现：
  - 信息丢失
  - 理解偏差
  - 汇总不完整
- 可以理解成一个项目经理负责所有沟通，效率高时很好，但一旦信息量太大，就容易卡住。

##### 4. 模式三：Agent Teams（团队模式）

- 这里的 Agent 不再是“临时工”，而是**长期存在、持续积累上下文的成员**，像固定团队里的“同事”。
- 适合的场景是：
  - **大型代码库迁移**
  - **每个 Agent 负责一块相对独立的服务**
- 这种方式的优势是：每个 Agent 对自己负责的领域越来越熟，不需要每次都从头理解。
- 但风险在于：**如果多个 Agent 需要共享资源，就可能发生冲突**。
- 例子：一个负责用户系统、一个负责支付系统、一个负责基础设施，长期协作会更稳定；但如果同时改同一份配置或数据库资源，就可能互相影响。

##### 5. 模式四：Message Bus（消息总线）

- 这种模式下，Agent 之间**不是直接互相调用**，而是通过“发布/订阅事件”来协作。
- 好处是扩展性强：**新增一个 Agent 时，不需要改已有连接关系**。
- 特别适合：
  - **安全告警流水线**
  - **事件类型会持续增加的系统**
- 典型问题是：**调试很难**。
- 文中给了一个很直观的例子：**一个告警如果经过 5 个 Agent 才完成处理，出了问题后会非常难追踪到底是哪一环出了错**。
- 简单说，它很适合“事件很多、参与方很多”的系统，但排查问题的成本会明显上升。

##### 6. 模式五：Shared State（共享状态）

- 这种模式**没有中央协调者**，所有 Agent 都通过读写同一个数据库或文件系统来间接协作。
- 它适合：
  - **多 Agent 联合研究**
  - 一个 Agent 的发现能立刻被另一个 Agent 使用
- 优点是共享方便，信息流动快。
- 但最大陷阱是：**反应式循环**。
- 文中举的风险链条很典型：
  - **A 写了内容**
  - **B 读到后再写**
  - **A 又读到 B 的更新继续写**
  - 最后不断循环，**无限消耗 token**
- 也就是说，这种模式虽然灵活，但如果没有约束机制，特别容易出现“互相刺激、越跑越多”的失控情况。

##### 7. 作者给出的总建议

- 设计多 Agent 架构时，**不要一开始就选择最复杂的方案**。
- 更合理的做法是：
  - 先从最简单的模式开始
  - 观察真正卡住的地方
  - 再逐步升级架构
- 这条建议本质上是在提醒：**多 Agent 不是越多越强，关键是是否真的解决了问题**。

##### 8. 相关讨论中的补充信息

- 热门回复里有人提到，自己终于理解了 **Claude Code token 消耗过快、账单爆炸** 的一个可能原因。
- 其中提到一个环境变量：`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`。
- 回复者观察到：
  - 开启这个变量后，**缓存似乎一直维持在 5 分钟**
  - 移除后，情况发生变化
- 另有用户提到，使用 `claude --resume` 时，发现 Claude Code CLI 曾尝试分析目录下**大量 Markdown 文档**，导致自己 **5 小时额度很快用完**。
- 这些讨论虽然不属于原文主体，但侧面说明了：**在 Agent 系统里，协作链路、扫描范围、上下文管理不当，确实可能带来明显的 token 成本问题。**

##### 9. 一句话结论

- 这篇总结最有价值的地方，不只是列出 **5 种多 Agent 架构**，而是强调了一个实用判断标准：**选“够用”的，不选“最复杂”的。**
