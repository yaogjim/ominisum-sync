#### OpenWorker

**[openworker.com](https://openworker.com)** · Download · [Issues](https://github.com/andrewyng/openworker/issues)

> **Beta** - OpenWorker is in open beta: fully usable, updates itself, and we're actively polishing rough edges. [Issues](https://github.com/andrewyng/openworker/issues) welcome.

**AI that gets your everyday tasks done.** OpenWorker is an open-source AI coworker that lives on your desktop and delivers **finished work**, not just chat: a polished document, a Slack reply with the numbers, an updated calendar, a triaged inbox.

It runs on your machine and doesn't lock you into any model: bring your own API key for OpenAI, Anthropic, Google, or an open-weight provider, or run fully local with Ollama. Your data leaves your machine only through the model and integrations *you* choose.

[How OpenWorker works](https://openworker.com)

#### Download

[**⬇ macOS (Apple Silicon)**](https://download.openworker.com/mac) macOS 12+ · signed &amp; notarized · auto-updates

[**⬇ Windows 10/11 (x64)**](https://download.openworker.com/windows) builds are not yet code-signed, so SmartScreen will warn; signing is in progress

Open the app, add a model key (or point it at Ollama), and ask for something real.

1. Tell OpenWorker the outcome you want - "prepare a customer brief," "untangle my calendar," "draft a report," "check where the release stands across Jira and GitHub."
2. It breaks the task into steps and works across your desktop, files, and connected apps.
3. Before anything consequential - sending a message, changing a calendar, running a command - it checks in and you approve or redirect.
4. You get the finished deliverable, not a to-do list.

Under the hood:

```
┌────────────────────────────────────────────────┐
│              OpenWorker desktop app            │  native shell + GUI
├────────────────────────────────────────────────┤
│           local agent server (Python)          │  engine · tools · connectors - built on aisuite
├───────────────┬────────────────┬───────────────┤
│  your files   │   your tools   │  your model   │  everything runs with your keys,
│  & terminal   │ 25+ connectors │  any provider │  on your machine
└───────────────┴────────────────┴───────────────┘
```

- **Produce real deliverables** - documents, spreadsheets, reports, and web pages land as files you can open and share.
- **Work from Slack** - mention `@OpenWorker` in a channel; a session opens on your desktop, the work happens with your tools, and the answer comes back as a thread reply.
- **Use your everyday tools** - 25+ integrations including GitHub, Slack, Jira, Notion, Linear, HubSpot, Outlook, monday.com, Gmail, and Google Calendar, plus your **terminal and local files**. Any tool reachable over [MCP](https://modelcontextprotocol.io/) plugs in too, with per-tool control.
- **Run on a schedule** - automations for recurring work: a morning brief, a weekly report, a standing watch over a channel. Runs land in the app with full transcripts.
- **Ask before acting** - writes, sends, and shell commands are approval-gated. Unattended runs park their asks in an inbox instead of acting on their own.

Model access is yours: pick a provider, paste your key, switch anytime. Supported out of the box:

**OpenAI · Anthropic · Google Gemini · Inkling (Thinking Machines) · GLM (Z.ai) · DeepSeek · Kimi (Moonshot) · Qwen · MiniMax · Mistral · Grok (xAI)** - plus open-weight models via **Together** and **Fireworks**, and fully local models via **Ollama**.

A curated model list marks what we've verified for tool-calling work. Adding any model string works at your own risk.

#### Privacy

OpenWorker is local-first. Everything lives on your machine: the agent loop, your conversations, connector tokens, and model keys - all in the app's local secret store. The only cloud piece is a small service that brokers OAuth handshakes for connectors. You can always use the App without signing-in - use the connectors via manually-created credentials/API-keys.

Prerequisites: Python 3.10+, Node 20+, and (for the desktop shell) the Rust toolchain via [rustup](https://rustup.rs/).

```
git clone https://github.com/andrewyng/openworker
cd openworker

# 1. One-time bootstrap - creates the Python venv at .venv
#    (on Windows, run from Git Bash or WSL)
bash packaging/setup_dev_env.sh

# 2. Start the local agent server
.venv/bin/openworker-server --cwd ~/some/project --port 8765
#    (Windows: .venv\Scripts\openworker-server.exe)

# 3. In a second terminal, start the UI
cd surfaces/gui
npm install
npm run dev        # browser UI on the Vite dev port
```

To run the full desktop app instead of the browser UI, replace step 3 with `npm run tauri dev` (from `surfaces/gui/`) - the Tauri shell launches the window and supervises the server itself.

Tests: `.venv/bin/pytest` (server), `npm test` and `npm run e2e` in `surfaces/gui` (GUI unit + hermetic end-to-end). Desktop bundles are built with `packaging/build_dmg.sh` / `packaging/build_windows.ps1`.

#### Repository layout

Directory What's in it

`coworker/` Python backend - agent engine, model providers, connectors, MCP client, memory, automations

`surfaces/gui/` Desktop app - React UI + Tauri shell that supervises the server

`stt/` Speech-to-text sidecar (Rust) for voice input

`packaging/` Installer builds (macOS DMG, Windows), auto-update manifest, dev bootstrap

`docs/` Design specs and decision logs

`tests/` Backend test suite

OpenWorker's engine is built on [**aisuite**](https://github.com/andrewyng/aisuite), a lightweight Python library providing a unified chat-completions API across LLM providers and an agents layer with tools, toolkits, and MCP support. If you want to build your own agent harness rather than use ours, start there; this repo is a working reference for what aisuite can carry.

OpenWorker was originally developed inside the aisuite repository before moving to its own home here; thanks to the aisuite contributors whose work it builds on.

OpenWorker 是一款**开源、桌面端、本地优先的 AI 助手**，目标不是陪用户聊天，而是直接完成实际工作并交付文档、表格、报告、消息回复等成果。它支持多种云端或本地大模型，并在发送消息、修改日历、执行命令等关键操作前征求用户批准。

  - “准备一份客户简报”
  - “整理我的日历”
  - “起草一份报告”
  - “检查 Jira 和 GitHub 上的版本发布进度”

## 口播总结（1）

### 2026-08-03 01:14:00

#### OpenWorker：把人工智能变成真正做事的桌面同事

OpenWorker 是一个开源的桌面人工智能协作者。它不只陪你聊天，而是会根据目标拆解任务，操作文件、终端和各种工作软件，最后交付一份可以直接使用的成果。接下来可以了解它能做什么、怎样保证安全和隐私，以及它的技术结构和开发方式。

##### 一、它解决的不是“回答问题”，而是“完成任务”

OpenWorker 的核心定位，是让人工智能直接把日常工作做完。

通俗地说，你不用一步步告诉它该点哪里、该查什么，只要描述想要的结果。比如，你可以说：“准备一份客户简报”“整理一下我的日历”“起草一份报告”，或者“检查 Jira 和 GitHub 上这个版本的进展”。

OpenWorker 会把目标拆成多个步骤，然后跨越你的桌面、文件和已连接的应用去执行。最后交给你的，不是一张待办清单，而是一份已经完成的交付物，比如文档、表格、报告或网页文件。

项目目前处于公开测试阶段。它已经可以使用，会自动更新，但开发团队仍在持续打磨细节，也欢迎用户提交问题。

##### 二、它可以连接日常办公工具

接下来，重点看它具体能在哪里工作。

OpenWorker 支持二十五种以上的集成工具，包括 GitHub、Slack、Jira、Notion、Linear、HubSpot、Outlook、monday.com、Gmail 和 Google Calendar。除了这些软件，它还可以使用你的终端和本地文件。

如果某个工具可以通过 MCP 接入，通常也能接入 OpenWorker。MCP 可以理解成一种让人工智能连接外部工具和服务的通用方式，而且每个工具都可以单独控制权限。

它也能从 Slack 开始工作。你只要在频道里提到“@OpenWorker”，桌面端就会打开一个工作会话。任务会使用你已经连接的工具执行，最后结果会以线程回复的形式返回到 Slack。

这样一来，OpenWorker 更像一个能在多个工作场景之间移动的同事，而不是只存在于聊天窗口里的问答机器人。

##### 三、重要操作必须先征得同意

更重要的是，OpenWorker 不会默认替你做所有有风险的动作。

在发送消息、修改日历、运行命令等关键操作之前，它会先向你确认。你可以批准，也可以重新指示它怎么做。

这意味着它既能自动推进任务，又不会在你完全不知情的情况下随意发消息、改数据或执行命令。

它还支持定时自动化。例如，你可以设置每天生成一份早间简报，每周输出一份报告，或者持续关注某个频道。定时任务的运行记录会进入应用，并保留完整的文字记录。

如果是无人值守运行，系统遇到需要确认的操作时，不会擅自执行，而是把请求停在收件箱里，等待你处理。

##### 四、它可以按计划运行，也可以持续产出文件

OpenWorker 的目标不是给出一个建议，而是产出可以打开、编辑和分享的文件。

例如，任务完成后，文档、电子表格、报告和网页都可以直接落地为文件。你可以在本地打开它们，也可以继续修改或分享。

这也是它和普通聊天机器人比较明显的区别：普通聊天往往停留在文字回复，而 OpenWorker 试图把回复进一步变成实际工作成果。

##### 五、模型由用户自己选择

OpenWorker 不把用户锁定在某一个人工智能模型上。

你可以使用 OpenAI、Anthropic、Google Gemini、Inkling、GLM、DeepSeek、Kimi、Qwen、MiniMax、Mistral 或 Grok 等服务，也可以通过 Together 和 Fireworks 使用开放权重模型。除此之外，还可以通过 Ollama 在本地运行模型。

使用时，你只需要提供对应的模型服务密钥，或者把 OpenWorker 指向本地的 Ollama。

项目提供了一份经过筛选的模型列表，用来标记哪些模型已经验证过适合工具调用，也就是能够比较稳定地操作外部工具。不过，用户也可以手动填写其他模型名称，只是这样做需要自行承担兼容性风险。

所以，模型选择权在用户手里。你可以根据能力、价格、隐私要求和部署方式随时切换。

##### 六、它采用“本地优先”的隐私设计

在隐私方面，OpenWorker 的核心结论是：大部分内容都保存在你的电脑上。

代理运行循环，也就是负责规划和执行任务的核心程序，保存在本地。你的对话、连接器的登录令牌，以及模型密钥，也都保存在应用的本地秘密存储中。

所谓“本地优先”，并不代表任何数据都绝不会离开电脑。数据只会通过你选择的模型服务和集成工具离开本机。比如，你选择了某个云端模型，任务内容就可能发送给那个模型；如果你连接了 Slack、GitHub 等服务，相关操作也会通过这些服务完成。

OpenWorker 还使用一个规模较小的云端服务来协助完成连接器的 OAuth 授权。OAuth 可以理解为一种不直接交出密码、而是授权应用访问服务的登录方式。

另外，使用 OpenWorker 不一定要登录它自己的账户。你也可以手动创建凭据或使用 API 密钥来连接工具。

##### 七、桌面应用由几个本地部分组成

从技术结构看，OpenWorker 大致分成三层。

第一层是桌面应用。它使用原生桌面外壳和图形界面，负责呈现窗口和交互。

第二层是本地代理服务器，使用 Python 编写。它负责任务引擎、模型调用、工具连接器、记忆和自动化等核心工作。

第三层是你提供的资源，包括本地文件、终端、外部工具和人工智能模型。这些部分通常都使用你自己的密钥，并在你的机器上协同运行。

桌面应用使用 Tauri 外壳。Tauri 是一种用于构建桌面应用的技术，它负责启动窗口，并监督本地代理服务器的运行。项目还包含一个使用 Rust 编写的语音转文字组件，用于语音输入。

##### 八、普通用户可以直接下载安装

如果只是使用 OpenWorker，不需要自己编译代码。

目前它提供 macOS 和 Windows 版本。macOS 版本要求使用 Apple Silicon 芯片，并且系统版本至少是 macOS 12。这个版本已经完成签名和公证，也支持自动更新。

Windows 版本支持 Windows 10 和 Windows 11，面向 x64 设备。不过目前 Windows 构建版本还没有完成代码签名，因此系统的 SmartScreen 可能会发出警告，签名工作仍在进行中。

安装应用后，添加一个模型服务密钥，或者连接到 Ollama，然后直接提出一个真实任务，就可以开始使用。

##### 九、开发者可以从源码运行

对于开发者来说，OpenWorker 是一个开源项目，可以从代码仓库获取并在本地运行。

开发环境需要 Python 3.10 或更高版本、Node.js 20 或更高版本。如果要运行完整的桌面外壳，还需要通过 rustup 安装 Rust 工具链。

基本流程是：先克隆项目，然后运行项目提供的初始化脚本。这个脚本会创建 Python 虚拟环境。接着启动本地代理服务器，再启动图形界面。

界面可以直接以浏览器形式运行，也可以使用 Tauri 启动完整的桌面应用。项目同时提供服务器测试、界面单元测试和端到端测试。端到端测试的意思是，模拟用户从头到尾操作一遍，检查整个系统是否正常。

如果要构建桌面安装包，项目还提供 macOS 的 DMG 构建脚本和 Windows 的构建脚本。

##### 十、代码仓库的主要组成

仓库本身也按照功能进行了划分。

`coworker` 目录是 Python 后端，包含代理引擎、模型提供商、连接器、MCP 客户端、记忆和自动化功能。

`surfaces/gui` 是桌面应用部分，主要包括 React 图形界面和负责管理服务器的 Tauri 外壳。

`stt` 是语音转文字组件，使用 Rust 编写。

`packaging` 负责安装包构建、自动更新清单和开发环境初始化。

`docs` 保存设计规格和决策记录，`tests` 则保存后端测试。

这样的结构说明，OpenWorker 不只是一个界面项目，它同时包含人工智能代理、工具连接、桌面应用、语音输入和发布打包等完整部分。

##### 十一、底层依赖 aisuite

OpenWorker 的核心引擎建立在 aisuite 之上。

aisuite 是一个轻量级 Python 库，提供统一的聊天补全接口。简单说，它试图用相近的方式调用不同人工智能服务商的模型，减少开发者为每家模型分别适配的工作。

aisuite 还提供代理层、工具、工具包和 MCP 支持。因此，开发者如果不想直接使用 OpenWorker，也可以把 aisuite 当作参考，自己构建一套人工智能代理系统。

OpenWorker 最初是在 aisuite 仓库内部开发的，后来才独立成现在的项目。项目也特别感谢了 aisuite 的贡献者。

##### 十二、项目欢迎贡献，但有明确边界

最后看项目协作方式。

OpenWorker 欢迎用户提交问题，也欢迎开发者提交拉取请求，也就是把自己的代码修改提交给项目维护者审核。

提交功能修改时，项目要求附上截图，说明修改前哪里有问题，以及修改后如何解决。

不过，项目团队目前仍然按照内部规划持续开发。因此，有些功能可能已经在开发中，或者某些提议与项目方向不一致，这类提交不一定会被接受。

项目采用 MIT 许可证。这是一种相对宽松的开源许可证，具体授权内容以仓库中的许可证文件为准。

##### 结尾：最值得记住的五点

最后，用五句话回顾 OpenWorker。

第一，它的目标不是陪你聊天，而是根据目标拆解任务，并交付文档、报告、表格等实际成果。

第二，它可以连接二十五种以上的日常工具，包括 GitHub、Slack、Jira、Notion、Gmail 和 Google Calendar，也能使用本地文件与终端。

第三，它会对发消息、改日历、运行命令等关键操作进行确认；即使是定时任务，也不会在需要批准时擅自行动。

第四，它支持多家云端模型、开放权重模型和 Ollama 本地模型，用户可以自己选择模型和密钥。

第五，它采用本地优先的设计。代理、对话、密钥和连接信息主要保存在本机，但数据仍可能通过用户选择的模型服务和外部集成工具传输。

## 深度解读（1）

### 2026-09-18 00:20:19

#### OpenWorker 的真正命题：AI 助手的竞争正从“会回答”转向“可托付”

OpenWorker 最值得关注的，不是又多了一个桌面 Agent，而是它对 AI 工作产品做出了一个明确判断：**用户要的不是任务建议，而是可以直接交付的结果。**因此，它把输出定义为文档、表格、网页、Slack 回复、日历更新或整理后的收件箱，而不是一份“你接下来应该怎么做”的清单。

这看似只是产品表述，实际改变了评价标准。聊天产品主要衡量回答质量；工作 Agent 则要看任务完成率、人工介入次数、结果可修改性，以及出错后能否定位和恢复。模型能力仍然重要，但只有接入文件、终端和业务系统后，能力才可能转化为劳动成果。

##### 桌面不是一种界面，而是执行与信任的边界

OpenWorker 将 Agent 引擎、会话、密钥和连接器令牌放在本机，支持读取本地文件、调用终端，并连接 Slack、Jira、GitHub、Notion、Gmail 等二十多个工具。Slack 可以成为任务入口，但实际执行仍发生在桌面端。这种设计把“从哪里提出请求”与“在哪里持有权限并执行”分开了。

它解决的是 Agent 产品最棘手的矛盾：**要完成真实工作，就必须获得广泛上下文和操作权限；权限越大，用户越难放心托付。**本地运行减少了额外的数据汇集，也让个人文件、凭证和操作记录更容易留在用户控制范围内。不过，“本地优先”不等于数据绝不离开设备：选择云端模型和第三方连接器时，相关数据仍会发送给这些服务，项目也保留了一个用于 OAuth 握手的云端组件。

更关键的是权限设计。发送消息、修改日历和执行命令前都要审批；定时任务遇到高风险操作时，会把请求停在收件箱中。这不是附属安全功能，而是当前 Agent 可用性的核心机制：它用可见的暂停点换取更大的行动范围。

##### 真正需要优化的是“监督成本”

审批机制也暴露了尚未解决的问题。如果每一步都要确认，Agent 只是把“亲自操作”变成“不断批准”；如果批准太少，又可能造成误发消息、错误修改或危险命令。产品的关键变量因此不是自动化程度越高越好，而是：

- 哪些动作可以低风险自动执行；
- 哪些动作应在提交前集中预览；
- 用户纠正一次后，系统能否稳定记住边界；
- 失败时是否能解释过程、撤销操作并恢复现场。

OpenWorker 的完整执行记录、按工具控制和审批收件箱，已经指向这个方向，但仓库页面尚未提供真实完成率、审批频率或用户留存数据。它证明了架构可以成立，还没有证明这种交互成本已经足够低。

##### 模型正在成为可替换部件，但并未完全商品化

项目支持多家模型服务、开放权重模型和 Ollama，并建立在统一模型接口 aisuite 之上。这个选择传递出另一个重要信号：Agent 产品的长期价值可能更多沉淀在**工具连接、权限控制、任务状态、记忆、可恢复性和交付物质量**上，而不是绑定某一家模型。

但“可切换模型”也有边界。项目专门标注经过工具调用验证的模型，说明不同模型在规划稳定性、参数生成和长任务执行上仍有明显差异。统一 API 可以降低切换成本，却不能抹平行为质量。

因此，OpenWorker 目前更像一份值得研究的开源产品假设，而非已经验证的商业答案：**AI 同事能否成立，最终不取决于它能接多少模型和应用，而取决于用户是否能用足够低的监督成本，把一类真实任务持续交给它。**
