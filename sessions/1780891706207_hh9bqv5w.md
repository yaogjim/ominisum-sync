## 分析要点

- **核心高价值点**：将设计稿转化为可版本管理的文本资产，并用Git diff驱动Agent理解设计变更，是非常实用的AI协作模式。
- **留存建议**：长期保留（提供了较完整的AI辅助UI设计到MVP实现的迭代流程，并包含本地化Claude Design工具链的实践线索，适合作为AI开发工作流参考。）

**知识要点**

- Claude Design输出HTML、CSS、React和data.js，比传统Figma设计稿更适合AI理解和后续代码实现。
- AI开发MVP时应先限制功能范围，让Agent聚焦实现可运行的最小版本，再小步迭代。
- 设计问题应回到设计稿层修改，再通过Git diff和截图让Agent同步实现，而不是直接在代码里修补。
- UI实现适合使用Claude Opus等设计遵循能力更强的模型，非UI功能可用其他Coding Agent配合。
- 设计系统是Claude Design发挥价值的重要前提，可让开发者更多关注UX而非重复处理UI规范。

**行动项**

- 尝试使用Claude Design生成一个简单App的HTML/CSS/React/data.js设计稿，并提交到Git进行版本管理。
- 用Claude Opus或类似Coding Agent基于设计稿实现一个只含UI功能的MVP，控制首版范围。
- 建立“设计稿修改—Git diff—Agent实现—运行反馈”的小步迭代流程。
- 评估并试用文中提到的baoyu-design项目，判断是否适合集成到本地Cursor工作流。
- 为自己的项目整理基础Design System，以便后续AI生成设计时保持一致性。

## 正文

**宝玉**

之所以研究 Claude Design，是因为最近摸索出一套不错的开发模式：

1\. 先用 Claude Design 去设计 App 的 UI 和 UX，第一版本越简单越好。

Claude Design 交付的结果是 HTML + CSS + React + data.js，通过 CSS 一下就可以看清楚设计系统的颜色系统、尺寸规范，通过 React 可以看清楚组件结构，通过 data 可以知道数据结构什么样子。

这几个组合可比 figma 对于 AI 来说友好多了，尤其是 data.jsx，这是一般的设计 App 不会有的，但对开发特别重要的。

还有一个优势就是交付的结果都是文本格式的，可以一起提交到 git 做版本管理，用 git diff 就可以清楚的让 AI 知道设计稿修改了什么。

2\. 把 Claude Design 生成设计稿交给 Claude Opus 4.8 去实现一个 MVP，第一个版本只实现 UI 功能，告诉它技术栈（比如 AppKit 而不是 SwiftUI），通过几个小版本的迭代，让它逐步完善。比如第一个版本只是主界面

之所以不用 GPT，是因为 Opus 在 UI 实现上比 GPT 好太多，同样的设计稿，GPT 实现的各种细节问题的，不能很好的遵守设计稿。

之所以不一下子实现太多功能，是因为功能越少 Agent 越容易聚焦，做出来效果越好。所以怎么拆分版本，也是用好 Coding Agent 的一种能力。

非 UI 的功能，用什么模型没有那么大差别，所以我也会用 Codex 配合非 UI 工作。

3\. 每次生成一个版本，要让它可以运行，无论是 Agent 还是人都是需要即时反馈的，有了反馈才知道方向对不对，才知道下一步要做什么。

人在测试的时候，能发现各种问题，代码问题就让 Agent 去修改，UI 设计有问题不是马上修改代码，而是要去 Claude Design 去修改设计稿，设计稿修改完了，把设计稿下载回去，替换本地的设计稿文件。

设计稿替换后，让 Agent 去 git diff 分析一下变更，给它个截图，都不用多说它就知道怎么改了。

4\. 版本稳定后继续新一轮迭代

当设计的功能做完之后，不一定是要马上去设计新的功能，而是可以重新审查一下实现的代码，重构优化一下。

比如我在第一版实现后，让 Opus 4.8 去做了性能分析，看性能问题在哪，然后告诉我当前用 NSScrollView，内容一多就内存暴涨，建议 NSTableView。

我心想这不应该是一开始就该考虑到的么！不管怎么样亡羊补牢也不算晚。

性能优化完就继续加功能，更新设计稿，让 Agent 参考新设计稿优化功能。

## 解读（1）

### 2026-06-08 04:06:15

#### 深度总结

这篇内容讲的是一套 **AI 辅助软件开发的新工作流**：  
先让 AI 做设计，再让 AI 写代码，中间通过可运行版本和 Git diff 持续迭代。

核心不是“让 AI 一次性做完整产品”，而是：

> **把设计、实现、反馈、迭代拆成小步，让 AI 在明确上下文中高质量工作。**

---

##### 1. 核心开发流程

###### 第一步：用 Claude Design 做 UI / UX 初稿

Claude Design 输出的不是传统设计稿，而是：

- `HTML`
- `CSS`
- `React`
- `data.js`

这比 Figma 更适合 AI 和开发，因为：

- CSS 能直接体现颜色、尺寸、设计规范
- React 能体现组件结构
- data.js 能体现数据结构
- 全部是文本，可进 Git
- Git diff 能清楚显示设计变更

因此，Claude Design 的价值不只是“画界面”，而是生成一套 **可被 AI 理解、可被代码实现、可被版本管理的设计资产**。

---

###### 第二步：用 Claude Opus 实现 MVP

作者会把设计稿交给 Claude Opus 去实现第一个版本。

但重点是：

> **第一版只做 UI，不做复杂功能。**

原因是：

- 功能越少，Agent 越聚焦
- 越容易符合设计稿
- 越容易跑起来
- 越容易发现问题

作者认为，Opus 在 UI 实现上明显优于 GPT；而非 UI 功能，则模型差距没那么大，可以用 Codex 等工具配合完成。

---

###### 第三步：每个版本都必须可运行

作者强调：

> **无论人还是 Agent，都需要即时反馈。**

每次生成版本，都要能运行。  
运行之后，人测试发现问题：

- 如果是代码问题：让 Agent 改代码
- 如果是设计问题：回 Claude Design 改设计稿
- 改完设计稿后同步到本地
- 让 Agent 看 Git diff 和截图，再更新实现

这里的关键是：

> 不要直接在代码里修设计问题，而是先修设计源头。

这样可以保证设计稿和代码长期一致。

---

###### 第四步：稳定后再继续迭代

功能完成后，不急着加新功能，而是先做：

- 代码审查
- 性能分析
- 架构优化
- 重构

例如作者让 Opus 分析性能，发现 `NSScrollView` 在内容多时内存暴涨，建议换成 `NSTableView`。

这说明 AI 不只是写代码，也可以参与工程质量优化。

---

##### 2. 作者为什么研究 Claude Design？

因为原流程有一个痛点：

> Claude Design 在网页端，设计稿需要反复导出、下载、解压、替换，本地开发体验很差。

于是作者开始研究 Claude Design 的内部机制，试图把它本地化，集成进本地 Agent 工作流。

后来他发现：

- Claude Design 的核心逻辑很多在浏览器前端
- 可以分析出 Prompt、Skills、初始组件等
- 再适配 Cursor 的工具能力
- 就能在本地复现类似 Claude Design 的效果

最终形成了一个本地 Skill：  
可以在 Cursor 中运行类似 Claude Design 的能力，并支持网页标记、评论、修改。

---

#### 深入浅出解读

这套方法可以理解为：

> **把 AI 当成一个“设计 + 前端 + 工程助理团队”，但你要给它清晰流程和小任务。**

传统流程是：

```text
产品想法 → Figma 设计 → 开发实现 → 测试反馈 → 修改
```

作者的新流程是：

```text
想法
↓
Claude Design 生成可代码化设计稿
↓
Claude Opus 按设计稿实现 MVP
↓
运行测试
↓
发现问题
↓
改设计稿或改代码
↓
Git diff 告诉 AI 变化
↓
继续迭代
```

它的厉害之处在于：

##### 1. 设计稿变成了“代码友好型资产”

Figma 对人友好，但对 AI 和程序不一定友好。  
Claude Design 输出的是文本代码，AI 更容易理解。

这意味着设计不再只是“图片”，而是：

- 结构清楚
- 样式清楚
- 数据清楚
- 可追踪变化
- 可直接转实现

---

##### 2. 小步快跑，比一次性生成更可靠

作者反复强调：

> 不要让 Agent 一口气做太多。

AI 写代码最大的问题不是不会写，而是容易在复杂任务里失焦。

所以更好的方式是：

```text
先主界面
再交互
再数据
再性能
再功能扩展
```

这其实和传统工程里的敏捷开发很像，只是执行者变成了 AI Agent。

---

##### 3. Git diff 成了 AI 的“变更说明书”

以前设计稿改了，开发要问：

- 哪里改了？
- 为什么改？
- 改了多少？
- 是视觉改动还是结构改动？

现在设计稿是文本，直接用 Git diff 就能看到变化。  
AI 看 diff 后，就知道该改代码哪里。

这大幅降低了沟通成本。

---

##### 4. Design System 是前提

作者在回复里补充了一个重要观点：

> Claude Design 真正好用的前提，是你有自己的 Design System。

也就是说，AI 不应该每次重新发明 UI 风格。  
如果颜色、字号、间距、组件规范已经在设计系统里定义好，AI 就能少纠结 UI，多关注 UX。

更好的方向是：

```text
Design System 定义 UI 规范
Claude Design 生成 UX 和界面结构
Agent 负责实现和迭代
```

---

#### 辩证思考

##### 这套方法的价值

###### 1. 它把 AI 开发从“生成代码”推进到“生成流程”

很多人用 AI 写代码，只是让它补函数、改 bug。  
作者这套方法更进一步：让 AI 参与完整产品迭代。

它不是单点工具，而是一条链路：

```text
设计 → 实现 → 运行 → 反馈 → 修改 → 重构
```

这才是 AI Coding 真正有价值的地方。

---

###### 2. 它降低了个人开发者做产品的门槛

过去一个人做 App，要懂：

- 产品
- 交互
- UI
- 前端
- 后端
- 性能
- 测试

现在 AI 可以承担很多执行工作。  
人更像是导演：

- 定方向
- 拆任务
- 看结果
- 做判断
- 控制质量

这会显著提高独立开发者、小团队的生产力。

---

###### 3. 它强调“反馈闭环”，这是关键

AI 开发最怕的是：

> 任务很大、反馈很晚、错误积累。

作者的方法要求每个版本都能运行，就是为了快速暴露问题。  
这比盲目追求“一次生成完整项目”更靠谱。

---

##### 这套方法的局限

###### 1. AI 仍然不能替代产品判断

有评论指出得很准确：

> Claude 能生成界面，但不一定知道这个界面是否应该存在。

AI 可以帮你做 UI，但不一定能判断：

- 用户真正要解决什么问题
- 这个流程是否必要
- 这个功能有没有价值
- 用户为什么要用它

所以，产品判断仍然需要人负责。

---

###### 2. 对使用者要求并不低

这套流程看似自动化，但其实需要使用者具备较强能力：

- 会拆分版本
- 懂设计系统
- 能判断 UI 好坏
- 能读懂代码结构
- 能测试和反馈
- 能管理 Git diff
- 知道什么时候该重构

也就是说，AI 降低了执行成本，但没有消除专业判断。

---

###### 3. 工具链仍然碎片化

作者之所以折腾本地 Claude Design，是因为现有工具割裂：

- Claude Design 在网页
- Cursor 在本地
- Claude Desktop 体验不足
- Codex、Opus、GPT 各有长短

未来真正理想的状态应该是：

```text
设计、编码、调试、标注、版本管理、运行反馈
全部在一个统一环境里完成
```

目前还没有完全成熟。

---

#### 最终结论

这篇内容真正值得学习的不是某个工具，而是一种方法：

> **用 AI 做产品开发，不是让它一次性完成全部，而是建立一套可设计、可实现、可运行、可反馈、可迭代的闭环。**

最关键的三点是：

1. **设计稿要代码化**：让 AI 看得懂、改得动、可 diff  
2. **任务要小步化**：让 Agent 聚焦，降低失控概率  
3. **反馈要即时化**：每一版都能运行，问题及时暴露  

一句话概括：

> 未来高效开发者的核心能力，不是单纯会写代码，而是会组织 AI、拆分任务、管理反馈，并在关键节点做正确判断。

## 结构化（1）

### 2026-06-11 09:35:25

##### 主旨概括

作者研究 Claude Design，是因为他摸索出了一套“AI 辅助设计 + AI 辅助开发”的高效开发流程：先用 Claude Design 生成可读、可版本管理的设计稿，再交给 Coding Agent 实现和迭代。后来为了减少网页与本地切换的麻烦，他进一步研究并复刻了 Claude Design 的本地运行方式，做成了可在 Cursor 中使用的 Skill。

---

##### 1. 用 Claude Design 先做 App 的 UI / UX 设计

作者的开发流程第一步，是先用 **Claude Design 设计 App 的 UI 和 UX**，而且第一版要尽量简单。

Claude Design 输出的设计稿包含：

- `HTML`
- `CSS`
- `React`
- `data.js / data.jsx`

这些内容相比 Figma 更适合 AI 理解：

- 通过 **CSS** 可以看清颜色系统、尺寸规范等设计系统；
- 通过 **React** 可以理解组件结构；
- 通过 **data.js / data.jsx** 可以了解数据结构，这对开发非常重要；
- 所有内容都是文本格式，可以提交到 **Git** 做版本管理；
- 后续修改时，可以通过 **git diff** 让 AI 清楚知道设计稿哪里变了。

作者认为，这种“文本化设计稿”比传统设计工具对 AI 更友好。

---

##### 2. 把设计稿交给 Claude Opus 4.8 实现 MVP

##### 2. 最重要的洞见

###### 洞见 1：对 AI 来说，HTML / CSS / React / data 比 Figma 更像“设计稿”

###### **核心观点：**  
> 传统设计稿是给人看的；文本化、结构化、带数据模型的设计稿，才是给 AI 用的。

**为什么重要：**

**可迁移价值：**  
凡是要让 AI 参与的流程，都应尽量从“视觉/二进制/隐式知识”转为：

- 文本化
- 结构化
- 可 diff
- 可版本管理
- 可运行

**我应该记住什么：**  
> AI 时代的交付物，不只是给人审美，更要给 Agent 执行。

###### **核心观点：**  
> 使用 Coding Agent 的能力，不只是会写 prompt，而是会把任务拆成它能稳定完成的小版本。

**为什么重要：**  
作者强调第一版只实现 UI，功能越少，Agent 越容易聚焦，结果越好。  
这本质上是降低搜索空间：任务越窄，模型越不容易发散、遗漏、幻觉。

**可迁移价值：**

- 写代码：先 UI，再功能，再性能
- 写文章：先结构，再段落，再润色

###### **核心观点：**

**为什么重要：**  
这避免了代码和设计逐渐漂移。  
设计稿是“事实源”，代码是实现结果；如果直接改代码，长期会失去一致性。

**反常识之处：**  
很多 AI 开发会进入“截图—指出问题—让模型直接修代码”的循环，看似快，实则容易制造混乱。

**可迁移价值：**

- 产品需求不要散落在聊天记录里
- 设计规范不要散落在代码补丁里
- 数据口径不要散落在报表里
- 组织决策不要散落在会议口头表达里

> AI 可以加速执行，但不能替代事实源管理。

> 不要长时间停留在抽象讨论里，要尽快制造可观察反馈。

## 深度解读（1）

### 2026-09-18 00:55:01

#### AI 开发真正缺的，不是更会画界面的模型，而是可执行的设计契约

这篇内容最有价值的地方，不是比较 Opus、GPT 或 Codex 谁更擅长 UI，而是展示了一种正在成形的开发方式：**把设计从供人观看的静态稿，变成 Agent 可以读取、比较和执行的代码资产。**

Claude Design 输出 HTML、CSS、React 和数据文件。CSS 表达颜色、间距等规范，React 暴露组件层次，`data.js` 则补上界面背后的数据结构。相比 Figma，这些文本不仅更容易进入模型上下文，还能提交 Git，通过 diff 精确描述一次设计变更。于是“按新设计改一下”不再依赖截图和自然语言猜测，而可以变成：哪些组件、样式与数据发生了变化，应如何映射到原生实现。

这相当于在设计和代码之间建立了一份**机器可读的中间协议**。它未必是最终产品代码，却同时承担原型、规格和沟通媒介的作用。对 AI 开发而言，这可能比单纯提升模型能力更重要：Agent 的问题往往不是不会写，而是输入模糊、变更不可追踪、验收标准不明确。

##### 小步迭代的本质，是控制 Agent 的搜索空间

作者反复强调第一版只做主界面、每一版都必须能运行。这不只是工程习惯，也是对 Agent 工作特性的适配。

任务越大，模型需要同时处理的设计决策、技术约束和潜在错误越多；一次生成很多功能，看似节省轮次，实际会让偏差相互叠加。把版本拆小，并在每轮加入运行结果、截图和人工体验，相当于不断缩小下一步的搜索范围。**版本拆分因此不再只是项目管理能力，而成为 AI 编程中的上下文设计能力。**

但文中的性能案例也暴露了这种方法的边界：Agent 先用 `NSScrollView` 完成功能，直到复盘时才发现数据量增加会导致内存暴涨，随后改用 `NSTableView`。小步交付擅长保证局部可见结果，却不天然保证架构正确。性能、数据规模、可访问性和状态复杂度等非功能约束，不能都留到“做完再优化”；其中会导致大范围返工的部分，仍应提前进入设计契约和验收场景。

##### Design System 能减少 UI 决策，却不能替代 UX 判断

作者在回复中补充了一个关键前提：Claude Design 最适合已有 Design System 的团队。原因很直接——品牌、颜色、组件状态和尺寸规范已经确定后，模型不必每次重新“创作”视觉语言，只需在有限规则中组合，输出会稳定得多。

不过，这并不意味着团队自然就能聚焦 UX。模型可以快速生成一个整洁流程，却无法仅凭生成能力回答：这个界面是否应该存在，用户为什么在此刻执行这一步，现有流程的真正阻力是什么。**Design System 约束的是表达方式，不负责证明需求与流程正确。**用户研究、任务验证和行为数据仍位于生成流程之前与之后。

##### 值得关注的机会是“设计—实现闭环”

作者最终把 Claude Design 搬到 Cursor，本质上是在修补工具链断点：网页与本地来回切换、导出解压、替换文件，再通知 Agent 修改。Cursor 的页面标记、可选模型和本地 Agent 恰好把这些步骤串联起来。

这提示的产品机会并非再做一个 AI 画图工具，而是建立**可标注、可版本化、可执行、能同步回代码的设计工作区**。它的竞争力不只取决于首稿多漂亮，更取决于变更能否低损耗地传播到实现，以及团队能否持续审查这一过程。真正值得验证的指标，是需求到可运行版本的周期、设计变更造成的返工量，以及 Agent 对设计规范的遵守率，而不是生成页面的数量。

- AI开发MVP时应先限制功能范围，让Agent聚焦实现可运行的最小版本，再小步迭代。
- 设计问题应回到设计稿层修改，再通过Git diff和截图让Agent同步实现，而不是直接在代码里修补。
- UI实现适合使用Claude Opus等设计遵循能力更强的模型，非UI功能可用其他Coding Agent配合。
- 设计系统是Claude Design发挥价值的重要前提，可让开发者更多关注UX而非重复处理UI规范。
