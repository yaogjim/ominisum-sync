> **摘要**：文章复盘 camelAI 将编码代理从常驻虚拟机迁移至 Cloudflare Durable Objects 的三次重构：以 SQLite 和 R2 持久化文件，用显式工具与 JavaScript 隔离执行替代 bash，从而降低成本、延迟和凭证风险。

## 分析要点

- **核心高价值点**：将开放式 bash 环境收敛为显式能力接口，不仅隔离凭证和控制执行边界，还能迫使产品沉淀高频任务的一流路径，并提升低成本模型的稳定性。
- **留存建议**：建议精读并存档，作为低成本持久化代理和受控代码执行架构的案例（提供了从虚拟机代理迁移到持久化对象、分层文件存储和受控 JavaScript 执行环境的完整演进路径，架构取舍明确且有开源代码可供核查。）

**知识要点**

- 可将代理的推理进程与命令执行环境分离，使代理无需等待沙箱启动，并允许执行资源按需休眠或替换。
- 小文件存入 Durable Object 的 SQLite，大文件转存 R2 并保留指针，可将持久化从常驻基础设施转化为存储数据。
- 使用短生命周期 V8 isolate 执行代理生成的 JavaScript，并预加载受控方法，可避免将真实凭证暴露给代理沙箱。

**行动项**

- 盘点现有 Agent 对 bash 的调用，将高频文件操作、部署和构建任务整理为显式工具接口。
- 设计 SQLite 与对象存储结合的分层文件系统原型，并验证文件大小阈值、持久化和版本管理流程。
- 对比虚拟机沙箱与短生命周期隔离执行方案的启动延迟、单位任务成本、令牌消耗和任务成功率。

**Miguel Salinas**

### 我们重写了我们的代理，使其完全运行在一个持久化对象中，并使用了 Pi、代理 SDK 和代码模式

我们最近完成了将 camelAI 代理从虚拟机迁移出来的工作。该代理现在运行在

[Cloudflare Durable Object](https://developers.cloudflare.com/durable-objects/)，其文件系统存储在 SQLite 和 R2 中，并且使用 JavaScript 而非 bash 进行编写。大多数团队在完整的 Linux 虚拟机或容器沙箱中运行编码代理，我们过去也是如此。

我们想要不再使用虚拟机，因为为每个用户提供一台带有附加磁盘的持续运行的机器成本太高，难以扩展。困难的是，编码代理程序默认运行在 Linux 系统上。它们被训练为使用 bash，而我们部署的框架需要完整的虚拟机，因此实现这一目标经历了三次重新设计。这种权衡的结果是，代理程序现在只能执行我们已构建明确方法的任务，这听起来有局限，但对产品是有利的。

我是 Miguel，camelAI 的首席技术官。我们的代码库最近开源了，所以这篇文章中的所有内容都是你可以在以下地址阅读的代码：

[github.com/qaml-ai/camelAI](https://github.com/qaml-ai/camelAI)。我会在后续内容中链接到相关文件。以下是进展情况。

#### 步骤零：虚拟机时代

我们在 Claude 代码框架上启动了项目，该框架需要完整的虚拟机才能运行。我们尝试了几家虚拟机提供商，但没有一家满足我们的持久化和性能要求，最终

[构建了我们自己的容器服务](https://camelai.com/blog/we-tried-every-container-service-then-built-our-own)。那篇帖子仍然存在，但我们不再运行任何相关基础设施了。

容器服务运行良好，但它很笨重。为每个用户配备一台始终在线的虚拟机成本很高，将每个用户的文件存储在高速挂载磁盘上同样成本高昂。扩展该服务意味着需要扩展配备真实磁盘的真实机器，而在我们目标的用户数量下，这将变得极其昂贵。因此，与其在虚拟机编排上耍小聪明，我们开始设计一个根本不需要虚拟机的方案。

#### 步骤一：将代理从虚拟机中取出

[pi](https://github.com/badlogic/pi-mono)

[我们自己的 harness](https://github.com/qaml-ai/camelAI/blob/main/workers/main/src/chat-thread-do.ts)

持久化对象是一种小型有状态计算实例，在 Cloudflare 的边缘节点上启动，靠近创建它的用户。每个聊天线程都拥有自己的持久化对象，与将所有请求路由到集中式虚拟机主机相比，这本身就降低了延迟。

在这个阶段我们保留了虚拟机，但代理不再驻留在其中。当需要执行命令时，它会远程调用虚拟机。Anthropic 描述了其托管代理的同样分离，即大脑与手分离。这给我们带来了一些很好的属性：

- 代理在虚拟机启动完成之前就开始响应，因为它不等待机器启动。
- 虚拟机可以在代理继续工作时进入休眠状态，或者如果该回合不需要任何命令，将根本不会再醒来。
- 一个大脑可以控制多只手。单个代理可以同时操作多个虚拟机。

我们把这些称为项目。每个项目都配有一个用于执行命令的虚拟机（VM），以及一个通过

[Cloudflare Artifacts](https://developers.cloudflare.com/artifacts/)，这是一种与 Git 兼容的存储，您可以从 Worker 即时配置。代理实际上并不知道自己在 VM 外部运行。它仍然有 bash，并且像其他任何编码代理一样工作。

问题在于，这只是固定了延迟，而没有解决其他问题。我们仍然每个用户一台虚拟机，因此仍然存在原始设计中所有的成本和扩展问题。

#### 步骤二：删除 VM

下一个版本保留了相同的项目结构，但移除了其背后的虚拟机。每个项目现在由

[一个存在于持久化对象内部的文件系统](https://github.com/qaml-ai/camelAI/blob/main/workers/main/src/workspace-filesystem-do.ts)，并使用

[R2](https://developers.cloudflare.com/r2/)

作为后端来处理较大的文件。

我们没有发明这个。Cloudflare 的代理团队开发了

[Shell](https://www.npmjs.com/package/@cloudflare/shell)，一个面向 Workers 的实验性文件系统和执行运行时，并且我们大量复用了他们的代码。其原理很简单。持久化对象的存储是一个容量上限为 10 GB 的 SQLite 数据库，每行有最大尺寸。小文件直接存储在 SQLite 行中。超过约 1.5 MB 的文件会被写入 R2，而 SQLite 行仅存储一个指针。对代理来说，它看起来像一个普通的文件系统，但底层是数据库和对象存储，因此持久化存储的是数据而非我们必须保持运行的基础设施。

版本历史仍然通过 Artifacts 进行管理，因此每个项目都保留了 Git 历史记录，而无需我们托管 Git 服务器。

#### 第三步：删除 bash

移除 bash 感觉很激进。编码代理被训练倾向于使用 bash，而 bash 正是所有人最初在虚拟机中运行它们的原因。这也是一个超出成本范畴的问题。拥有 bash 和网络访问权限的代理要执行任何有用操作都需要凭证，而我们尝试使用认证代理 URL 的做法变得棘手且难以实施。

因此我们移除了它。代理不再使用 bash，而是编写 JavaScript，通过执行

[代码模式](https://blog.cloudflare.com/code-mode/)以及 Cloudflare 的

[动态 Worker 加载器](https://blog.cloudflare.com/dynamic-workers)

每次执行都在一个全新的 V8 隔离实例中运行，该实例在毫秒级时间内启动，仅使用几兆字节的内存。沙箱预先加载了用户的数据连接以及

[平台能做的所有事情的方法](https://github.com/qaml-ai/camelAI/blob/main/workers/main/src/code-mode-tools.ts)

凭证永远不会进入沙箱。代理调用连接的方法，认证在我们这边进行。

当你查看代理实际使用 bash 做什么时，放弃它的成本比你想象的要低。大部分是文件操作，代理有原生工具来处理这些。我们给它提供读取、写入和编辑功能，以及我们自己的

[grep 和 glob 实现](https://github.com/qaml-ai/camelAI/blob/main/workers/main/src/pi-container-tools.ts)这涵盖了 80-20 法则。其余的是针对特定任务的特定命令，而这些命令已成为明确的方法：

- 通过代理进行的 wrangler 部署变成了我们完全控制的 deploy\_project 方法。由于我们确切知道部署何时发生，我们可以对其进行挂钩并自动打开实时预览。以前，我们不得不嗅探经过代理的 wrangler 流量来猜测哪个线程部署了内容。
- 构建用户的应用程序和运行 Python 笔记本成为了他们自己的方法，两者均由短期容器支持。

[Cloudflare 沙箱 SDK](https://github.com/cloudflare/sandbox-sdk)

坦率地说，不足之处在于我们必须预判代理需要什么。在 bash 中，代理可以自己解决问题。而现在，如果某个功能缺失，我们必须添加它。实际上，这种压力对产品是有益的，因为它迫使我们思考用户在做什么，并为其构建一条一流的路径，而不是让代理即兴发挥。

也有一个意外的好处。Bash 是开放式的，而廉价模型在开放式环境中难以应对。使用较少的明确方法时，它们的表现明显更好，这一点很重要，因为保持 camelAI 的低成本运行是这种架构的关键所在。

#### 这让我们处于何种境地

技术栈现在由以下组件构成：用于代理及其文件系统的 Durable Objects、用于大文件的 R2、用于 Git 历史记录的 Artifacts、作为框架的 pi，以及用于执行的、带有动态 Workers 的代码模式。它的部署方式与其他任何 Cloudflare 应用程序相同，并且无需管理外部容器服务。

Dynamic Workers 按执行次数计费，而非按运行时长每秒计费。数千次执行的成本约等于我们之前评估过的服务上几分钟的容器运行时间成本。延迟很低，因为所有服务都在靠近用户的边缘节点运行，而扩展（服务）是 Cloudflare 的职责，而非我们的问题。

用户仍然构建和部署全栈应用到线上 URL，代理仍然读取、写入、grep 和部署。从用户角度来看，没有任何变化。

## 结构化（2）

### 2026-07-30 09:03:53

#### camelAI：将编码代理迁移到持久化对象，并移除 VM 与 Bash

camelAI 经过三次架构重构，将编码代理从“每位用户一台持续运行的虚拟机”，迁移为完全运行在 **Cloudflare Durable Objects** 上的无服务器系统。新架构以 SQLite、R2 和 Artifacts 持久化数据，并让代理通过 JavaScript 和明确的方法执行任务，从而显著降低成本、延迟和扩展难度。

##### 0. 虚拟机时代：成本高，难以规模化

camelAI 最初基于需要完整 Linux 环境的 Claude 编码框架运行，因此必须为每位用户提供一台虚拟机或容器。

- 团队尝试过多家 VM 服务商，但都无法同时满足持久化和性能需求，最后自行搭建了容器服务。
- 这种方式虽然可用，但非常笨重：
  - 每位用户都需要一台持续在线的 VM；
  - 用户文件需要放在高速挂载磁盘上；
  - 扩容意味着增加真实服务器和真实磁盘。
- 当用户规模增长时，成本会变得难以承受，因此团队决定重新设计一个**完全不依赖虚拟机**的方案。

##### 1. 将“代理大脑”移出虚拟机

第一步是把代理本身迁移到 **Cloudflare Durable Object**，但暂时保留 VM 用来执行命令。

- Durable Object 是运行在 Cloudflare 边缘节点的小型有状态计算实例。
- 每个聊天线程拥有独立的 Durable Object，因此请求无须统一发送到中心化的 VM 主机，延迟更低。
- 代理需要执行 Bash 命令时，再远程调用 VM，形成“**大脑与手分离**”的架构。

这种拆分带来了几个好处：

1. 代理无需等待 VM 启动，就可以先开始回复。
2. 代理工作期间，VM 可以休眠；若本轮对话不需要执行命令，VM 甚至无需唤醒。
3. 一个代理可以同时控制多台 VM。

团队将这种工作单元称为“项目”。每个项目包括一台执行命令的 VM，以及通过 **Cloudflare Artifacts** 管理的 Git 兼容存储。

不过，这一阶段只改善了启动延迟，并没有解决核心问题：**仍然需要为每位用户维护一台 VM，成本和扩展压力依旧存在。**

##### 2. 删除 VM：用 SQLite 和 R2 构建文件系统

第二次重构彻底移除了项目背后的虚拟机，将每个项目的文件系统放入 Durable Object。

该方案大量复用了 Cloudflare 代理团队开发的实验性项目 **Shell**，底层存储规则如下：

- Durable Object 的存储本质上是一个容量上限为 **10 GB** 的 SQLite 数据库。
- 小文件直接保存在 SQLite 数据行中。
- 超过约 **1.5 MB** 的大文件存入 **R2**，SQLite 中只保留对应指针。
- 对代理而言，它仍像在操作普通文件系统；但平台实际持久化的是数据，而不是一台必须持续运行的机器。

项目版本历史继续由 **Artifacts** 管理，因此每个项目仍保留完整的 Git 历史，同时团队不需要自行托管 Git 服务器。

##### 3. 删除 Bash：改用 JavaScript 和明确方法

移除 VM 后，团队进一步删除了 Bash。原因不仅是成本，也包括安全与权限管理：

- 编码代理通常被训练成依赖 Bash，这也是很多团队必须提供完整 Linux 环境的原因。
- 但一旦代理拥有 Bash 和网络访问能力，执行有用任务时就需要各种凭证。
- 团队尝试过认证代理 URL，但实现复杂且难以可靠控制。

新方案让代理改为编写 **JavaScript**：

- 代码通过 Code Mode 和 Cloudflare 的动态 Worker 加载器执行。
- 每次执行都会启动一个全新的 **V8 隔离实例**。
- 实例可在**毫秒级**启动，只占用**几 MB 内存**。
- 沙箱预加载用户的数据连接和平台能力，但凭证永远不会进入沙箱。
- 代理只调用平台提供的方法，真正的认证过程由 camelAI 后端完成。

##### 4. 用原生工具和专用方法替代 Bash

团队发现，代理使用 Bash 的大部分场景其实只是文件操作，因此没有必要保留完整 Shell。

按照“二八法则”，平台提供以下原生能力即可覆盖大多数需求：

- 读取文件；
- 写入文件；
- 编辑文件；
- `grep` 搜索；
- `glob` 文件匹配。

剩余的特定命令则被改造成平台明确控制的方法。例如：

- 原本通过 `wrangler` 完成的部署，改为 `deploy_project` 方法。
  - 平台现在能够准确知道部署何时发生；
  - 可以自动挂钩流程并打开实时预览；
  - 过去则需要分析代理的 `wrangler` 流量，猜测是哪个线程触发了部署。
- 构建用户应用和运行 Python Notebook 也被封装为专用方法。
  - 这些任务仍可借助短期容器执行；
  - 但不再需要为每位用户维持长期运行的 VM。

##### 5. 限制反而改善了产品与模型表现

移除 Bash 的明显缺点是：团队必须提前预判代理需要哪些能力。

- 在 Bash 环境中，代理可以临时想办法解决问题。
- 在新架构中，如果缺少某项能力，团队必须为其新增明确的方法。

但这种限制也带来两项收益：

1. **产品路径更清晰**  
   团队被迫理解用户真正要完成的任务，并为高频场景设计稳定、可控的一流流程，而不是让代理自由拼凑命令。

2. **低成本模型表现更好**  
   Bash 是高度开放的环境，便宜的小模型往往难以稳定应对。工具数量减少、方法更加明确后，这些模型反而表现更好，有助于维持 camelAI 的低成本运行。

##### 6. 最终技术栈与实际效果

目前 camelAI 的核心技术栈包括：

| 组件 | 用途 |
|---|---|
| Durable Objects | 运行代理并承载项目文件系统 |
| SQLite | 存储小文件和文件元数据 |
| R2 | 存储超过约 1.5 MB 的大文件 |
| Artifacts | 保存 Git 历史记录 |
| Pi | 代理运行框架／Harness |
| Code Mode + Dynamic Workers | 执行代理生成的 JavaScript |

最终效果是：

- 无需维护外部容器服务；
- 整套系统可以像普通 Cloudflare 应用一样部署；
- Dynamic Workers 按**执行次数**而非按运行时长计费；
- **数千次执行**的成本，大约只相当于此前评估的容器服务运行**几分钟**；
- 服务运行在靠近用户的边缘节点，延迟较低；
- 基础设施扩容由 Cloudflare 负责，而非 camelAI 团队。

对用户而言，产品体验基本没有变化：代理依旧可以读取、写入、搜索、构建和部署代码，用户仍能将全栈应用发布到线上 URL。

##### 社区讨论与补充

- 有人质疑，用 JavaScript 代替 Bash 是否会大幅增加 Token 消耗。
- camelAI CTO Miguel Salinas 表示，结果恰恰相反：由于常见操作被封装为预制函数，Token 使用量反而略有下降。
- 团队也正在基于自己的 Harness 训练模型，希望重新获得一部分模型在 Bash 环境中的能力和性能。

#### 主旨概括

camelAI 将编码代理从“每位用户一台持续运行的虚拟机”，重构为完全运行在 **Cloudflare Durable Objects** 中的无虚拟机架构，并以 **JavaScript 执行模式取代 bash**。这次迁移显著降低了成本与延迟，也把代理从“自由执行任意命令”转变为“调用明确、可控的产品能力”。

##### 背景：为什么放弃虚拟机

- camelAI 最初基于 Claude 的编码代理框架，需要完整 Linux 虚拟机才能运行。
- 但为每位用户长期维持一台虚拟机及高速挂载磁盘：
  - 成本高；
  - 扩展困难；
  - 需要自行管理真实机器、磁盘和容器基础设施。
- 团队最终没有继续优化虚拟机编排，而是经过 **三次重新设计**，从根本上移除对虚拟机和 bash 的依赖。
- 项目代码已开源：[`github.com/qaml-ai/camelAI`](https://github.com/qaml-ai/camelAI)。

##### 步骤零：虚拟机与自建容器时代

- 团队尝试过多家虚拟机服务商，但其持久化能力和性能都无法满足要求，于是自建了容器服务。
- 该服务虽然可用，却十分笨重：
  - 每位用户都需要一台始终在线的虚拟机；
  - 用户文件需要存放在高速挂载磁盘上；
  - 用户规模扩大时，必须同步增加真实服务器和磁盘。
- 结论是：这种架构在目标用户规模下会变得极其昂贵，因此必须摆脱虚拟机。

##### 步骤一：将“代理大脑”移出虚拟机

团队先把代理本身迁移到 **Cloudflare Durable Objects**，但暂时保留虚拟机作为远程命令执行环境。

- 每个聊天线程拥有一个独立的 Durable Object，并运行在靠近用户的 Cloudflare 边缘节点上，从而降低延迟。
- 代理负责推理和响应，需要执行命令时才远程调用虚拟机，相当于将“**大脑**”与“**双手**”分离。
- 这种分离带来三项好处：
  1. 代理无需等待虚拟机启动，即可先开始回复；
  2. 代理工作时，虚拟机可以休眠；若当前对话不需要命令，虚拟机甚至不必启动；
  3. 一个代理可以同时控制多台虚拟机。

团队将工作空间称为“项目”。项目仍有虚拟机用于执行命令，并通过 Cloudflare Artifacts 保存兼容 Git 的版本历史。代理感知不到自己已在虚拟机外运行，仍可像普通编码代理一样使用 bash。

**局限：**这一阶段只改善了启动延迟，并未解决根本成本问题，因为本质上仍是“每位用户一台虚拟机”。

##### 步骤二：彻底删除虚拟机

随后，团队移除项目背后的虚拟机，将文件系统直接放入 Durable Object 中。

###### 文件存储方式

- Durable Object 的持久化存储是一个容量上限为 **10 GB** 的 SQLite 数据库。
- 小文件直接存入 SQLite。
- 超过约 **1.5 MB** 的文件写入 **Cloudflare R2**，SQLite 中只保存对应指针。
- 对代理而言，它仍像在使用普通文件系统；但实际持久化的是数据库和对象存储中的数据，而不是一台必须持续运行的机器。

该方案大量复用了 Cloudflare 代理团队开发的实验性文件系统和执行运行时 **Shell**。

###### 版本管理

- Git 版本历史继续由 **Cloudflare Artifacts** 管理。
- 每个项目都能保留完整历史记录，但团队无需自行托管 Git 服务器。

##### 步骤三：删除 bash，改用 JavaScript

移除 bash 是最激进的一步，因为编码模型通常经过大量 bash 使用训练，而 bash 也是编码代理依赖 Linux 虚拟机的重要原因。

###### 为什么 bash 也是安全和管理问题

- 具有 bash 和网络访问能力的代理，需要凭证才能完成部署等实际操作。
- 如果把凭证交给代理或通过认证代理 URL 间接访问，会带来复杂的权限控制和安全风险。
- 因此，团队选择让代理不再直接接触凭证和任意 shell 环境。

###### 新的执行方式

- 代理改为编写 **JavaScript**。
- 代码通过 **Code Mode** 和 Cloudflare 的 **Dynamic Worker Loader** 执行。
- 每次执行都进入一个全新的 V8 隔离实例：
  - 启动时间为毫秒级；
  - 只占用几 MB 内存；
  - 沙箱预加载用户的数据连接和平台提供的方法；
  - 凭证始终保留在平台侧，不会进入沙箱。
- 代理只调用平台暴露的方法，认证由 camelAI 负责完成。

###### 用原生工具覆盖常见 bash 操作

团队发现，代理使用 bash 时，大多数操作只是文件处理，因此为其提供了：

- 读取文件；
- 写入文件；
- 编辑文件；
- 自研的 `grep`；
- 自研的 `glob`。

这些能力覆盖了大部分常见需求，符合“**80/20 法则**”。剩余命令则被封装为明确的产品方法，例如：

- `wrangler deploy` 被替换为受平台完全控制的 `deploy_project`：
  - 平台能准确知道部署发生的时间；
  - 可以自动挂接流程并打开实时预览；
  - 不再需要通过监听网络流量猜测哪个对话线程执行了部署。
- 构建用户应用和运行 Python Notebook 被封装为独立方法，底层仅在需要时启动短期容器。

##### 权衡：能力更受限，但产品反而更可控

删除 bash 后，代理无法再自行尝试任意命令。如果缺少某项能力，团队必须提前添加相应方法。

这种限制看似是缺点，却产生了两项正面效果：

1. **促进产品化**  
   团队必须真正理解用户需求，并为高频任务建立稳定的一流流程，而不是让代理临场拼凑命令。

2. **提升低成本模型的表现**  
   bash 是高度开放的环境，便宜的小模型往往难以稳定处理；当可用能力变成数量较少、含义明确的方法后，小模型表现明显更好，有助于保持 camelAI 的低运行成本。

团队也在其 harness 上训练自己的模型，希望重新获得部分模型在 bash 环境中的能力。

##### 最终技术栈与效果

当前架构主要由以下组件组成：

| 用途 | 技术 |
|---|---|
| 代理运行与文件系统 | Cloudflare Durable Objects |
| 大文件存储 | Cloudflare R2 |
| Git 版本历史 | Cloudflare Artifacts |
| 代理框架 | Pi |
| 代码执行 | Code Mode + Dynamic Workers |
| 特殊任务 | 按需启动的短期容器 |

最终收益包括：

- 不再管理外部虚拟机或长期运行的容器服务；
- 所有服务都运行在靠近用户的边缘节点，延迟更低；
- 扩容由 Cloudflare 负责，而不是 camelAI 自行维护基础设施；
- Dynamic Workers 按**执行次数**计费，而不是按运行时长逐秒计费；
- **数千次 Dynamic Worker 执行的成本，大约只相当于原先候选服务中几分钟的容器运行费用。**

##### 对用户而言：体验基本不变

尽管底层架构被完全重写，用户仍然可以：

- 构建全栈应用；
- 将应用部署到公开 URL；
- 让代理读取、写入和搜索文件；
- 让代理执行部署。

也就是说，用户体验基本没有变化，但后台已经从“持续运行的 Linux 虚拟机”转变为“边缘持久化对象、对象存储和短时隔离执行环境”。

##### 社区反馈

- 也有人质疑 JavaScript Code Mode 是否会消耗更多 Token。
- 作者回应称，结果恰恰相反：由于常见操作被封装为预制函数，代理不必反复生成具体命令，**Token 使用量反而略有下降**。

## 口播总结（1）

### 2026-08-03 00:46:00

#### 主旨概览

camelAI 团队把编码代理从持续运行的 Linux 虚拟机中彻底迁出，改为运行在 Cloudflare 的持久化对象里，并用 JavaScript 代码执行取代 bash。接下来，你会听到这套架构为什么要重写、经历了哪三个阶段，以及它如何降低成本、延迟和扩展难度。

#### 起点：虚拟机能用，但成本难以承受

首先，最初的 camelAI 和多数编码代理一样，运行在完整的 Linux 虚拟机中。

这里的“编码代理”，可以理解为一个能读取文件、修改代码、执行命令并部署应用的人工智能程序。虚拟机，也就是 VM，则是一台通过软件模拟出来的完整计算机。

camelAI 最早采用 Claude 的代码框架。这个框架依赖完整的虚拟机。团队尝试过多家虚拟机服务商，但它们都无法同时满足持久化和性能要求，于是团队自己搭建了一套容器服务。

这套系统虽然能正常工作，却过于笨重。每个用户都需要一台持续在线的虚拟机，还要配备高速挂载磁盘，用来长期保存文件。用户越多，就需要越多真实服务器和真实磁盘，成本会迅速上升。

因此，团队最终得出一个结论：继续优化虚拟机调度解决不了根本问题。真正需要做的，是设计一套完全不依赖长期虚拟机的架构。

#### 第一步：让代理的大脑离开虚拟机

接下来，团队先把代理本身迁移到了 Cloudflare Durable Objects，也就是“持久化对象”中。

持久化对象可以理解为一个体积很小、能够保存状态的计算单元。它会运行在靠近用户的 Cloudflare 边缘节点上。每个聊天线程都有自己的持久化对象，不必把所有请求都发送到一个集中的虚拟机服务，因此延迟更低。

这一阶段，虚拟机还没有被删除，但代理已经不住在虚拟机里了。只有当代理需要执行命令时，才会远程调用虚拟机。作者把这种设计形容为“大脑和手分离”：代理是负责思考的大脑，虚拟机是负责执行命令的手。

这种分离带来了三个直接好处。

第一，代理不用等待虚拟机启动，就能先开始回复用户。

第二，如果当前任务不需要执行命令，虚拟机可以继续休眠，甚至完全不必启动。

第三，一个代理可以同时控制多台虚拟机，也就是一个大脑可以指挥多只手。

当时，每个项目仍然配有一台执行命令的虚拟机，并通过 Cloudflare Artifacts 保存版本。Artifacts 是一种兼容 Git 的存储服务。Git 则是常见的代码版本管理系统，用来记录文件的修改历史。

不过，这次改造主要解决了等待虚拟机启动带来的延迟，并没有解决成本问题。因为从整体上看，仍然是每个用户对应一台虚拟机，原有的扩展压力依然存在。

#### 第二步：删除虚拟机，用数据存储替代持续运行的机器

再接下来，团队真正移除了项目背后的虚拟机。

核心变化是，每个项目的文件系统都被放进持久化对象内部。所谓文件系统，就是代理看到的文件夹、代码文件和其他项目资料。对代理来说，它仍然像在操作普通磁盘，但底层已经不再是一块持续挂载的真实硬盘。

这套设计大量复用了 Cloudflare 代理团队开发的 Shell。它是一个面向 Workers，也就是 Cloudflare 轻量计算环境的实验性文件系统和执行运行时。

具体来说，持久化对象的存储底层是一套 SQLite 数据库。SQLite 是一种轻量级数据库，可以直接把数据保存在数据库记录中。每个持久化对象最多可以保存十 GB 数据，但单条数据库记录有大小限制。

因此，小文件直接存进 SQLite。超过大约一点五 MB的文件，则写入 R2。R2 是 Cloudflare 的对象存储服务，适合保存较大的文件。SQLite 中只保留一个指向该文件的地址。

这意味着，系统持久保存的是数据，而不是一台必须持续运行的机器。项目仍然拥有看起来正常的文件系统，但团队不再需要为每位用户维护虚拟机和挂载磁盘。

与此同时，代码版本历史继续交给 Artifacts 管理。这样，每个项目依然保留完整的 Git 历史，却不需要团队自己托管 Git 服务器。

#### 第三步：移除 bash，改为执行 JavaScript

更重要的是，团队随后删除了 bash。

bash 是 Linux 中常见的命令行环境。编码代理通常接受过大量相关训练，习惯通过 bash 读取文件、搜索内容、运行程序和部署应用。它也是许多团队必须为编码代理提供完整虚拟机的主要原因。

但 bash 不只是成本问题。一个能使用 bash、还能访问网络的代理，如果要调用外部服务，通常就需要拿到登录凭证或密钥。camelAI 团队曾尝试通过带认证能力的代理网址来处理这些权限，但整个方案变得复杂，而且难以严格控制。

因此，他们改用“代码模式”。也就是不让代理生成 bash 命令，而是让它编写 JavaScript，再通过 Cloudflare 的动态 Worker 加载器执行。

每次执行都会启动一个全新的 V8 隔离实例。V8 是运行 JavaScript 的引擎，而隔离实例可以理解为一个临时、相互隔绝的小型沙箱。它可以在毫秒级时间内启动，只占用几 MB 内存。

安全方面，沙箱会预先加载用户的数据连接，以及平台允许代理调用的方法，但真实凭证不会进入沙箱。代理只负责调用方法，身份验证则由 camelAI 平台完成。这样，代理能够完成任务，却接触不到用户的密钥。

#### 明确工具替代了大部分 bash 操作

移除 bash 听起来限制很大，但团队发现，代理日常使用 bash 所做的大部分事情其实并不复杂。

很多操作只是读取、写入、编辑和搜索文件。因此，camelAI 直接为代理提供了这些原生工具，还自行实现了 grep 和 glob。

grep 可以理解为在大量文件中搜索文字。glob 则是按照文件名规则查找一组文件。比如，找出项目里所有以 JavaScript 为后缀的文件。

这些明确工具已经覆盖了大多数常见需求，也就是所谓的“八二法则”：少数高频功能，解决了绝大部分任务。剩下的特殊命令，则被改造成专门的方法。

例如，过去代理会通过 wrangler 命令部署 Cloudflare 项目。现在，这个过程被替换为团队完全控制的“部署项目”方法。因为系统可以准确知道部署何时发生，所以能够自动挂接后续流程，并直接打开实时预览。

以前，团队只能监测代理产生的 wrangler 网络流量，再反推是哪个聊天线程触发了部署。改为明确方法后，整个过程更清楚，也更容易控制。

再比如，构建用户应用和运行 Python 笔记本，也分别被封装成专门的方法。它们底层仍会使用短期容器，但只在具体任务发生时临时启动，不再需要为每个用户维护一台长期在线的机器。

#### 限制变多，反而改善了产品和模型表现

当然，这种架构也有明显代价：团队必须提前预判代理需要做什么。

在开放的 bash 环境里，代理可以自己组合命令、临时寻找解决办法。改成明确方法以后，如果缺少某项能力，就必须由团队补充相应工具。

不过，作者认为，这种压力反而对产品有利。它迫使团队认真理解用户的真实需求，并为高频任务设计稳定的一流流程，而不是让代理每次都临场发挥。

还有一个意外收获。bash 是一个高度开放的环境，成本较低、能力较弱的模型往往不容易应对。工具数量减少，而且每个方法都定义得更明确以后，这些便宜模型的表现反而明显提高。

这一点对 camelAI 很重要。因为这套架构的目标不仅是减少基础设施成本，也包括降低模型调用成本。

在评论中，有人担心，让代理编写 JavaScript 会不会消耗更多令牌。作者的回答是，结果出人意料地并没有。由于常用操作都被封装成预制函数，代理不必反复生成复杂命令，令牌使用量甚至略有下降。

作者还提到，团队正在基于自己的代理运行框架训练模型，希望重新获得一部分过去针对 bash 优化的能力。

#### 最终架构：持久化对象、R2、Artifacts、Pi 和代码模式

最后，camelAI 现在的技术栈可以分成几个部分。

代理和项目文件系统运行在 Durable Objects，也就是持久化对象中。

较大的文件存放在 R2 对象存储里。

Git 版本历史由 Cloudflare Artifacts 管理。

代理运行框架使用 Pi。这里的框架，可以理解为负责组织模型、工具调用和执行流程的核心程序。

实际执行则使用代码模式和动态 Workers。代理编写 JavaScript，由短暂启动的隔离环境执行。

整套系统现在可以像普通 Cloudflare 应用一样部署。团队不再需要管理外部的、长期运行的容器服务。

成本结构也发生了变化。动态 Workers 按执行次数收费，而不是按照容器持续运行的秒数收费。根据团队的比较，数千次动态执行的成本，大约只相当于他们此前评估过的容器服务运行几分钟的费用。

延迟也更低，因为相关服务运行在靠近用户的边缘节点。至于如何随着用户增加而扩展，则交给 Cloudflare 负责，不再是 camelAI 团队自己维护服务器的问题。

最关键的是，用户体验没有明显变化。用户仍然可以让代理读取和修改代码、搜索文件、构建全栈应用，并把应用部署到线上地址。改变的是底层架构，而不是用户完成任务的方式。

#### 最值得记住的四个结论

最后，回顾四个重点。

第一，camelAI 放弃虚拟机的根本原因，是每个用户长期占用一台机器和高速磁盘，成本太高，也难以大规模扩展。

第二，团队分三步完成迁移：先让代理与虚拟机分离，再把文件系统迁入持久化对象，最后用 JavaScript 代码执行取代 bash。

第三，新架构把小文件存入 SQLite，把大文件存入 R2，并通过 Artifacts 保留 Git 历史。系统长期保存的是数据，而不是持续运行的基础设施。

第四，删除 bash 虽然限制了代理的自由度，却提升了安全性、可控性和低成本模型的表现。通过明确的工具和专用方法，用户原有的开发与部署体验基本不变，而系统的成本、延迟和扩展压力都显著降低。

### 2026-09-18 00:13:50

#### 从“给代理一台电脑”到“给代理一组能力”

camelAI 这次重写最值得关注的，并不是把虚拟机换成了 Cloudflare Durable Objects，而是**重新定义了编码代理的运行环境：它不再拥有一台通用 Linux 电脑，而只拥有产品明确允许、能够观测和计费的一组能力。**

这看似削弱了代理，实际可能更接近可规模化的产品形态。

##### 真正昂贵的不是推理，而是长期保留“整台电脑”

传统编码代理通常绑定虚拟机或容器，因为模型熟悉 bash，也可以临时安装工具、处理未知任务。但对多用户产品来说，这意味着每个用户都需要持续运行的计算实例、挂载磁盘和凭证环境。即便机器休眠，状态保存、启动延迟和资源编排仍然存在。

camelAI 先把“脑”和“手”拆开：代理运行在 Durable Object 中，需要执行命令时再调用虚拟机。这样可以提前响应、一脑多手，却没有改变每用户一台机器的成本基础。真正的转折发生在第二、三次重构：文件被存成 SQLite 与 R2 中的数据，执行则变成按次启动的 V8 隔离实例。**系统持久化的是用户状态，而不是承载状态的基础设施。**

这使成本单位从“机器运行了多久”转为“实际执行了多少次”。对大量间歇使用、文件规模有限的项目，这种经济模型明显更合理。所谓边缘节点带来的低延迟反而是次要收益；启动速度和闲置成本的消失更关键。

##### 移除 bash，本质是从开放式行动转向能力调用

最有启发性的判断是：代理常用 bash，并不等于产品必须提供完整 bash。团队发现大部分操作只是读写文件、编辑、grep、glob；剩余高频任务可以收敛成 `deploy_project`、构建应用、运行 Python 等明确方法。

这种约束带来三个连锁收益：

- 凭证无需进入代理沙箱，认证由平台完成；
- 部署等关键动作变得可识别、可审计，也能挂接预览等产品流程；
- 较便宜的模型面对少量明确方法时，往往比面对开放式 shell 更稳定，甚至减少工具选择和命令生成所需的 token。

因此，这不只是安全沙箱设计，也是一种产品设计：**把代理的“自由发挥”改造成平台可保证质量的一等路径。**过去系统只能从网络流量中猜测代理是否完成了部署，现在部署本身就是一个有语义的动作。

##### 这条路线成立的边界，是任务能否被稳定枚举

文章容易让人产生“虚拟机已经不必要”的错觉，但 camelAI 实际上没有彻底消灭通用计算：应用构建和 Python notebook 仍由短期容器完成。它只是把昂贵、开放的环境移出了常驻主路径。

这套架构适合目标相对明确的应用构建产品，不一定适合研究型编程、复杂调试或需要临时安装任意依赖的代理。它还依赖 Cloudflare 的计费、容量限制和专有运行时，长期成本与迁移难度尚未得到证明。

真正值得验证的变量是：**用户任务中有多少能被少量能力覆盖，剩余长尾出现得多快，以及新增能力的维护成本是否低于保留通用环境的成本。**如果高频任务集中，这种“受限代理”会比通用代理更便宜、更可靠；如果任务持续发散，团队最终可能重新造出一个不完整的操作系统。

这也是更广泛的代理产品机会：竞争优势未必来自给模型更多权限，而可能来自识别用户真正反复完成的工作，并把它们压缩成安全、可观测、可组合的能力接口。

##### 一句话看懂

camelAI 把编码代理从“每个用户一台 Linux 虚拟机＋bash”改造成运行于 Cloudflare Durable Objects 的轻量架构，以更低成本和延迟换取受控但较弱的通用执行能力。

##### 关键内容

- **迁移动机**：常驻虚拟机及高速磁盘成本高、难扩展；第一阶段仅把代理“大脑”移到 Durable Object、远程控制虚拟机，改善了启动延迟，但没有解决成本问题。

- **核心取舍**：代理不能再随意调用 Linux 命令，缺少能力时需开发者补充接口；但作者认为，这提升了安全性、可控性，也让较便宜的模型更容易稳定完成任务。
