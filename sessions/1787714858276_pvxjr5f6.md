> **摘要**：文章提出以受治理的代码仓库作为智能体项目的持久基底，将规范状态、派生投影、分层指令、角色契约、有界心跳、独立验证与溯源组合起来，使模型可替换、工作可续接且状态可审计。

## 分析要点

- **核心高价值点**：将持久化的项目状态与可替换的模型、会话和执行组件分离，让代码仓库而非聊天上下文承担机构记忆与连续性。
- **留存建议**：精读并存档，作为持久化Agent项目架构的设计参考（提出了较完整且可迁移的智能体项目架构，涵盖状态、角色、执行、验证、溯源和人类治理，适合后续设计Agent系统时反复调用。）

**知识要点**

- 项目应区分规范状态与派生投影：前者保存事件、证据和决策，后者提供摘要、队列及上下文包，并可从规范记录重新生成。
- 角色应被定义为可执行合约，明确读取范围、决策权限、可修改状态、必需产物、证据要求、升级条件和完成标准。
- 智能体通过有界心跳执行单元工作，并由独立验证器决定状态转换是否被接受，以降低长期上下文依赖和错误继承。

**行动项**

- 选择一个Agent项目，将项目目标、当前阶段、规范来源、决策记录、验收标准、阻塞项和未解决问题写入受版本控制的仓库。
- 为构建者、评审者和验证者分别建立角色契约，明确权限边界、输入状态、输出工件及完成条件。
- 实现一次最小心跳流程：读取状态、领取有界任务、执行、验证、记录状态增量并退出。

## 正文

**Yohei**

### 构建以代码仓库为中心的模块化智能体技术栈

我一直在为智能体工作收敛到一个模块化架构，其中持久单元是项目，而非模型、对话、IDE 会话或单个智能体。

项目以受治理的代码仓库形式呈现，其中包含足够的操作状态，使人类或智能体能够在极少前置上下文的情况下进入，确定当前状态，承担有界角色，执行工作，验证结果，并为下一个进入者留下清晰的状态转换记录。

传统的交互模型大致如下：

```text
human → prompt → agent → output → human
```

大部分工作上下文仍保留在会话中。人类在工具、模型和对话之间延续连续性。

我当前的架构更接近于：

```text
human ↔ Chief of Staff ↔ project managers ↔ workers / reviewers ↔ shared project state
```

核心的区分在于持久化的项目状态与可替换的执行组件 。模型、代理、工具、界面和会话都可以更换。代码仓库保留了项目的状态、规则、证据、决策、历史记录和核实机制。

该架构在特定意义上受到

[ActiveGraph](https://activegraph.ai/) 的启发：底层记录是首要的，而当前视图只是该记录的一种投影。应用于智能体工作时，这意味着有用的输出不会仅仅停留在对话文本层面。它会成为结构化的事件、工件、决策、主张、实验、检查结果或状态转换，并带有足够的溯源信息，以便日后审查。

#### 仓库作为项目基底

在此设置中，GitHub 的功能不仅限于代码托管。仓库是共享的运作环境，人类与多个代理通过它与同一项目进行交互。

根据项目的不同，仓库可能包含源代码、规格说明、模式、问题、研究声明、来源指针、实验运行、决策记录、验收标准、队列、测试、生成的投影、审批状态、工具策略以及机器可读的元数据。

关键问题不在于是否每一份上下文都被保留，而在于一个有能力的新代理能否重建项目的运作状态：

```text
‣ the project’s objective and current phase;
‣ the accepted state and its evidentiary basis;
‣ the source hierarchy and canonical records;
‣ prior attempts and material failures;
‣ decisions and unresolved implications;
‣ open questions, blockers, and dependencies;
‣ invariants, permissions, and approval boundaries;
‣ available roles and tools;
‣ the next bounded areas of useful work;
‣ the mechanisms by which a proposed change can be evaluated.
```

聊天仍然作为临时工作记忆发挥作用。它不是权威的项目记录。

我不会尝试持久化每个模型生成的每一个令牌。大多数对话内容只是脚手架。持久的信息集中在状态转换中，例如：

这些记录作为结构化的线索发挥作用。它们压缩了工作的物质轨迹，而无需未来的代理重放完整的对话。优化目标不是穷尽记忆，而是低成本、可靠的延续。

```text
decision → evidence → resulting state → unresolved implications
hypothesis → experiment → observation → result → confidence
task → implementation → verification → artifact
failure → diagnosis → newly discovered constraint
```

#### 规范状态与派生投影

代码仓库区分了底层记录与由该记录生成的视图。

规范层可包含 Git 历史、仅追加事件、已接受记录、决策对象、来源引用、不可变运行产物、实验输出、已验证声明，或其他持久状态转换。

投影层包含该状态的便捷表示形式：README 摘要、当前状态页面、仪表板、队列、索引、任务列表、报告、简报，以及为智能体准备的上下文包。

投影可能会过期或不完整。其价值在于保持可追溯到更持久的底层基座，从而能够从中重新生成、比较或质疑。

这是我最初通过 ActiveGraph 开发出的架构模式：

```text
event history → projection logic → current state
```

将底层历史视为首要对象，可以提供重放、溯源、谱系、分支、轨迹比较，以及重建特定状态为何存在的能力。它还使得将当前解释与产生该解释的证据和事件分离开来成为可能。

并非每个代码仓库都真正运行在 ActiveGraph 上。较小的项目可以通过 Git、结构化文件、确定性脚本、测试和规范的提交历史来实现相同的状态模型。在更丰富的项目中，代码仓库本身可以成为一个 ActiveGraph，其中包含以下各项之间的显式关系：

```text
people → agents → tasks → events → 
claims → experiments → artifacts → 
decisions → sources → results → open questions
```

一旦这些关系变得显式，系统就能回答更有用的操作性问题：哪些结论依赖于一个有争议的假设，哪些实验支持某个主张，哪个决策改变了轨迹，哪些未解决的问题阻塞了最多下游工作，哪些结果已被独立复现，或者从较早状态分叉后会有何不同。

#### 分层指令架构

智能体行为由多个不同的指令层组合而成，而非编码在单一的大型提示中。

有效的指令栈大致如下：

```text
global operating rules + role skill + project contract + current task
```

![Image](https://pbs.twimg.com/media/HPITuCXaEAAua-I?format=jpg&name=large)

全局操作层包含一组不变量，这些不变量在不同项目中保持相对稳定。其中包括保留来源信息、区分证据与推断、将机密信息排除在提示和代码仓库之外、明确表示不确定性、对重大操作要求适当的权限，以及优先使用持久的项目状态而非隐藏的对话记忆。

角色层包含可复用的操作流程。审查者拥有审查协议。研究者拥有来源处理、实验设计、主张形成和不确定性处理的方法。项目经理拥有状态协调与委派循环。验证者拥有明确的证伪或验收流程。参谋长拥有组合层面的注意力路由流程。

项目契约包含特定于单个代码仓库的信息：使命、本体论、来源层级、规范状态边界、不变量、模式、角色定义、工具权限、变更边界、审批策略、验收标准、升级规则以及完成定义。

任务上下文提供了最狭窄且最短暂的层次：当前目标、相关文件、近期变更、依赖、约束、要求的输出，以及任何截止日期或审批状态。

这种分离使得同一个审查者或研究者技能能够在多个代码仓库中运作，而无需将这些仓库强制纳入同一模式。项目特定的真实信息保留在项目本地，而通用操作方法保持可复用。

当项目变得持久时，初始引导阶段会建立最低可行的运行环境：项目简报、规范源码边界、主要不变量、验收标准、权限、阶段结构和路由指令。

根代理指令文件保持相对紧凑。它充当更具体契约的索引：

```text
work type X → load contract A
state class Y → load policy B
generated artifact Z → apply validation procedure C
```

Codex、Claude、Cursor、ChatGPT 及其他工具专属的指令文件包含适配器信息和路由逻辑，而非项目规则的独立副本。规范策略集中保存在一处，减少各界面之间的语义偏差。

对重要规则的修改也以项目变更的形式呈现。这些修改可追溯、可审查，并保留在历史记录中，而非通过更新提示词悄然引入。

#### 模型通过薄适配器接入

我在不同类型的工作中使用不同的模型和界面：ChatGPT、Codex、Claude、Replit、本地代理、GitHub 原生自动化以及专用连接器。我不会将每个界面视为独立的机构记忆。

每个模型通过一个轻量适配器进入同一项目。该适配器建立：

```text
‣ agent identity and assigned role;
‣ available tools and credentials;
‣ read and mutation permissions;
‣ canonical instruction entry points;
‣ relevant project or task context;
‣ the mechanism for recording results.
```

在可直接访问文件系统的情况下，代理读取代码仓库。在仅支持远程访问的情况下，代理使用 GitHub 或其他结构化连接器。外部系统尽可能通过官方 API、CLI 或连接器访问，浏览器交互作为结构化程度较低的备选方案。

适配器不维护自身对项目真实状态的版本。其功能是将模型连接到项目现有的状态和契约。

这使得模型替换的破坏性大大降低。Claude 会话无需保留 Codex 无法获取的知识，特定的 Codex 对话也不会成为架构决策的唯一持有者。持久性知识被外部化到项目环境中。

#### 角色作为可执行合约

系统使用诸如构建者、研究员、评审者、验证者、审计者、项目经理和参谋长等角色。这些角色主要不是人格设定，而是可执行的运营合约。

角色合约定义了：

```text
‣ which state the agent reads;
‣ which questions it is responsible for answering;
‣ which decisions it may make;
‣ which tools it may invoke;
‣ which state it may modify;
‣ which artifacts it must produce;
‣ what evidence it must record;
‣ when it must escalate;
‣ what constitutes completion.
```

构建者可以实施有边界的变更，但无权修改验收标准。评审者可以检查和质疑工件，但不得对其进行修改。验证者可以依据确定性合约评估拟议的状态转换。项目经理可以创建和排序任务，同时委派实施工作。审计者可以检查来源、政策合规性以及真相源的完整性，但不参与常规执行。

互换性源于将项目记忆与角色行为外部化。模型提供推理与执行能力；代码仓库与角色契约则提供制度背景、权威与程序。

#### 心跳作为有界控制循环

持久化状态提供了连续性，但并不产生行动。执行层采用有界心跳：即短控制循环，在此循环中，代理唤醒、协调状态、执行有限量的工作、记录结果，然后退出。

典型的心跳遵循如下结构：

```text
identify role and authority
→ inspect assignments, approvals, and changed state
→ reconcile current state against project objectives
→ select or claim one bounded unit of work
→ execute or delegate
→ verify and record the resulting state transition
→ exit
```

有界的执行窗口减少了对长期上下文的依赖，并限制了未记录假设的累积。项目状态在心跳之间承载连续性。

不同角色在不同分辨率层级上运作。窄范围智能体可以在特定实现或研究任务中执行更深层次的工作。宽范围智能体使用较浅的循环，因为它们的职责是协调而非直接执行。

由此产生的层级结构大致如下：

```text
Chief of Staff heartbeat
→ determine which projects require attention

Project Manager heartbeat
→ determine the next useful project-level action

Worker / Researcher heartbeat
→ execute bounded work

Reviewer / Verifier
→ evaluate the resulting artifact or claim

Repository
→ record the accepted state transition
```

心跳可以被调度、事件触发或手动调用。其共同要素是在有界的执行范围内进行重复的状态协调。

#### 项目管理与参谋长统筹

每个持久化代码仓库可包含一个项目经理角色，负责解读本地状态、安排工作顺序、识别阻塞项、将任务委派给专业代理，并协调已完成产出。

项目经理能访问比参谋长更深入的项目上下文。其运作知识通过项目契约、状态记录、决策、问题和任务图保留在代码仓库内部。

参谋长通过较小的项目组合视图跨项目运作。该视图可能包含：

```text
‣ active projects and objectives;
‣ current phase and owner;
‣ latest material state change;
‣ blockers and stale work;
‣ pending approvals;
‣ unresolved decisions;
‣ recommended next action;
‣ project-level health or confidence indicators.
```

参谋长不会将所有项目的内部上下文整合到一个中央提示中。它负责分配注意力。当某个项目需要更深入的分析时，它会将该任务委派给该代码仓库的项目经理，后者基于项目的本地状态和合约进行操作。

其控制循环大致如下：

```text
observe portfolio → detect attention requirement → dispatch → 
reconcile outcome → escalate judgment
```

这避免了将顶层协调器变成第二个记录系统或日益脆弱的全局上下文窗口。

#### 核实作为独立的系统层

多智能体执行在以下情况下变得不可靠：每个智能体在未进行独立检查的情况下，直接继承前一个智能体的结论。

在此架构中，核实是状态转换机制的一部分。根据项目的不同，核实可通过模式、类型系统、测试、持续集成、确定性验证器、允许路径规则、状态转换约束、校验和、预注册实验谓词、独立复现或结构化审查来实现。

相关的执行模式是：

```text
agent proposes change → verifier evaluates contract → accepted state changes
```

当错误状态转换的代价足以证明分离的合理性时，生成与接受是分开的操作。

这一区别在智能体能够修改自身工作流程、指令、评估器或编排逻辑时变得尤为重要。自我修改不会仅仅因为修改智能体报告成功就被接受。修改后的状态需要根据提议修改范围之外的不变量进行评估，或由独立授权的核实方进行验证。

核实同样适用于研究和推理产物。一个主张可以关联到：

```text
claim
← evidence
← source or experiment
← method and version
← run or artifact
← assumptions
← producing agent or action
← confidence and epistemic status
```

因此，主张不仅仅是一个句子。它是一个具有可追溯谱系的有状态对象。

#### 显式认知状态

代码仓库区分不同类别的知识，而非将所有智能体生成的材料归入单一的“已知”类别。

根据项目的不同，记录可能带有如下状态：

```text
proposed / observed / reproduced / accepted /disputed /
superseded / unresolved / inferred / source-backed / speculative
```

置信度、权威性、敏感性和证据基础也可以保持明确。

这一点很重要，因为新接入的智能体需要区分已验证的不变量、临时性解释、未解决的冲突以及缺乏支持的假设。同时，这也防止一份精心整理的综合结论悄然取代其依据的较弱证据。

在规模化应用中，非结构化的 AI 输出会累积成不可靠的文本档案。结构化的来源追踪与认知状态标注，使同样的材料能够作为可审查的机构记忆发挥作用。

#### 人类输入作为持久控制状态

我的角色从在代理之间手动传递上下文，转向系统中仍难以形式化的部分：目标、优先级、品味、约束、歧义消解、关键审批以及方向变更。

参谋长和项目经理会揭示这些输入杠杆作用最大的节点。在项目组合层面，接口可以保持精简：

```text
‣ what requires attention
‣ which projects are blocked
‣ which decisions require judgment
‣ which priorities have changed
‣ which work can proceed autonomously
```

当人类决策的影响超出当前对话范围时，它便成为持久的项目记录。该决策随后可影响未来的任务、审批、验收标准及智能体行为，而无需在每个会话中重复陈述。

人类仍是控制架构的一部分，但不再是项目记忆的传输层。

#### 会话输出作为状态增量

一个完成的智能体会话所产生的，不仅仅是即时请求的产物，还包括一份清晰可读的状态增量。

根据具体工作内容，该增量可能包括实现、测试、实验证据、更新的主张、决策记录、新发现的约束、失败的方法、源代码指针、未解决的问题、变化的置信度或限定的下一步行动。

复合循环如下：

```text
execute → record clues → update state → verify → continue from the new state
```

这改变了重复使用代理的经济性。上下文加载逐渐变得更加便宜，因为先前的工作已体现在环境中，而非通过人工简报反复重建。

该架构可概括为：

```text
project substrate
=
canonical state
+ derived projections
+ layered instructions
+ role contracts
+ model adapters
+ bounded heartbeats
+ verification
+ provenance
+ human governance
```

ActiveGraph 的影响不在于每个代码仓库都需要 ActiveGraph 运行时。而在于项目被视为不断演进、可重放的系统，其当前状态源自持久化的工作记录。

这些模型提供了可变的推理和执行能力。代码仓库提供了连续性。技能和契约提供了运行行为。心跳提供了动态。核实和溯源提供了信任。项目经理在本地进行协调。参谋长跨项目分配注意力。人类的判断改变了其余技术栈运行所依据的目标和约束。

## 通俗精炼（1）

### 2026-08-26 03:28:20

#### 构建以代码仓库为中心的模块化智能体技术栈

##### 一句话总结

将**项目仓库**而非模型、对话或单个智能体，作为 AI 协作的长期载体：模型负责推理与执行，仓库负责保存状态，角色契约约束权限，验证机制决定变更能否被接受。

##### 核心转变：从 “会话驱动” 到 “项目驱动”

传统模式依赖人类在不同模型、工具和对话之间传递上下文：

```text
人类 → 提示词 → 智能体 → 输出 → 人类
```

新的模式更像一个模块化组织：

```text
人类 ↔ 参谋长 ↔ 项目经理 ↔ 执行者 / 评审者 ↔ 共享项目状态
```

模型、工具和会话都可以替换；项目的目标、规则、证据、决策和历史则持续保存在仓库中。

##### 仓库：项目的 “机构记忆”

GitHub 不再只是代码托管工具，而是人类与多智能体共同工作的操作环境。仓库可保存：

- 代码、需求、验收标准与任务队列
- 决策、实验、证据、失败记录与开放问题
- 权限、角色、工具策略和审批边界
- 测试结果、运行产物及机器可读元数据

目标不是保存所有聊天内容，而是让新智能体无需完整历史对话，也能快速重建项目状态并继续工作。

##### 状态设计：底层记录与上层视图分离

系统分为两层：

- **规范状态**：Git 历史、事件、决策、实验结果、来源和已验证结论，是可信底座。
- **派生投影**：README、状态页、看板、报告、任务列表和智能体上下文包，是便于使用的当前视图。

核心逻辑是：

```text
事件历史 → 投影逻辑 → 当前状态
```

投影可能过期，但必须能追溯、验证并从底层记录重新生成。这使项目具备重放、分叉、比较和解释能力。

##### 智能体：通过角色契约参与项目

角色不是人格提示，而是可执行的职责与权限边界。每个角色需要明确：

- 读取和修改哪些状态
- 可以做出哪些决策
- 可以调用哪些工具
- 必须产出哪些材料和证据
- 何时完成、何时升级给人类

例如，构建者可以实现功能但不能修改验收标准；评审者可以提出质疑但不能直接改产物；验证者负责判断变更是否符合确定性规则。

##### 指令与模型：分层、解耦、可替换

智能体的指令由四层组成：

```text
全局规则 + 角色技能 + 项目契约 + 当前任务
```

ChatGPT、Claude、Codex、Cursor 等模型通过轻量适配器接入仓库。适配器只负责身份、权限、工具和上下文路由，不维护一套独立的 “项目真相”。

因此，模型可以替换，关键知识不会被锁在某次对话或某个工具中。

##### 执行机制：用短周期心跳持续推进

智能体不依赖超长会话，而通过 “心跳” 完成有限工作：

```text
识别角色与权限
→ 检查任务和项目状态
→ 领取一个边界清晰的任务
→ 执行或委派
→ 验证并记录状态变化
→ 退出
```

项目状态负责跨会话延续，短周期执行则减少上下文膨胀和未记录假设。

##### 协作层级：局部管理与全局调度

- **执行者 / 研究员**：完成具体任务。
- **评审者 / 验证者**：独立检查结果。
- **项目经理**：理解单个仓库的深层状态，拆解任务、处理阻塞并协调角色。
- **参谋长**：只查看跨项目摘要，识别优先级、阻塞和待决事项，再将工作路由给对应项目经理。

参谋长不吸收所有项目细节，从而避免形成庞大、脆弱的全局上下文。

##### 信任机制：生成与验收分离

智能体提出变更，不代表变更自动成为项目事实：

```text
智能体提出变更 → 验证器检查契约 → 接受并更新状态
```

验证方式可以包括测试、CI、Schema、类型系统、路径限制、独立复现和结构化评审。结论还应标注其认知状态，例如：

```text
提议 / 已观察 / 已复现 / 已接受 / 有争议 / 已取代 / 未解决 / 推测
```

这能避免未经验证的 AI 文本逐渐变成貌似可信的 “组织知识”。

##### 人类角色：从搬运上下文转向高价值判断

人类不再负责在智能体之间转述项目背景，而主要处理：

- 目标与优先级
- 品味与取舍
- 模糊性和冲突
- 高风险审批
- 约束及方向调整

重要的人类判断会被写入仓库，成为后续任务、权限和验收标准的一部分。人类仍是控制系统的核心，但不再充当项目记忆的运输层。

##### 最终架构

```text
项目基底
=
规范状态
+ 派生投影
+ 分层指令
+ 角色契约
+ 模型适配器
+ 有界心跳
+ 独立验证
+ 来源追踪
+ 人类治理
```

其本质是把 AI 项目变成一个**可持续、可追溯、可验证、可替换执行组件的长期运行系统**：仓库提供连续性，智能体提供执行力，验证机制提供可信度，人类负责目标与关键判断。

## 解读（1）

### 2026-08-26 03:39:59

#### 一、深度总结

##### 核心命题

> **智能体系统真正需要持久化的，不是某个模型或对话，而是项目本身。**

模型、会话和工具只是可替换的执行者；代码仓库则成为项目的**长期记忆、制度、证据库与控制中心**。

##### 架构主线

```text
人类治理
  ↕
参谋长：跨项目分配注意力
  ↕
项目经理：理解项目、拆解与调度
  ↕
执行者 / 研究者 / 评审者 / 验证者
  ↕
共享仓库：记录并承载项目状态
```

其关键组成是：

1. **仓库即项目底座**  
   保存目标、规则、任务、决策、证据、失败、权限、测试和历史，使新智能体无需重放全部聊天，也能接手工作。

2. **历史是事实，摘要是投影**  
   底层事件、提交和证据是规范记录；README、看板、报告只是可重新生成的当前视图。

3. **指令分层，而非一个巨型提示词**  
   ```text
   全局规则 + 角色能力 + 项目契约 + 当前任务
   ```
   通用能力可以复用，项目事实仍留在本地。

4. **模型通过薄适配器接入**  
   适配器只规定身份、工具、权限、入口和结果写回方式，不另建一套 “项目真相”。

5. **角色是权限合约，不是人格扮演**  
   每个角色明确：读什么、改什么、交付什么、如何验收、何时升级。

6. **心跳是短周期控制循环**  
   智能体每次只完成一个有边界的任务：读取状态、执行、验证、记录、退出；连续性由仓库承担。

7. **生成与接受分离**  
   ```text
   智能体提出变更 → 独立验证 → 状态正式更新
   ```
   测试、审查、复现和规则校验共同构成可信边界。

8. **知识必须标注认知状态**  
   区分 “推测、观察、复现、接受、争议、失效”，避免 AI 生成的流畅文字被误当成事实。

9. **人类负责价值判断，而非搬运上下文**  
   人类提供目标、优先级、品味、约束与关键审批；重要判断写回仓库，成为长期控制状态。

##### 本质上的四个转变

| 从 | 到 |
|---|---|
| 对话中心 | 项目中心 |
| 保存聊天 | 保存关键状态变化 |
| 智能体自报完成 | 独立验证后接受 |
| 人类传递上下文 | 仓库承载连续性 |

最终目标不是 “记住一切”，而是：

> **让任何合格的新智能体，都能低成本、可信地恢复项目现场并继续工作。**

---

#### 二、深入浅出地解读

可以把这套系统理解成一家制度成熟的公司：

- **模型**：临时员工，随时可以更换；
- **仓库**：档案室、制度手册、任务看板和审计系统；
- **角色契约**：岗位职责与权限；
- **心跳**：一次短工作班次；
- **验证器**：质检与审批；
- **项目经理**：负责一个项目的调度；
- **参谋长**：决定多个项目中哪里最需要注意；
- **人类**：董事会，决定方向与不可形式化的价值判断。

传统方式的问题是：员工离开后，经验也随聊天窗口消失。  
该架构则要求每次工作都留下结构化 “交接单”：

```text
做了什么
→ 依据是什么
→ 如何验证
→ 项目状态如何变化
→ 还遗留什么问题
```

因此，真正重要的不是 AI 能连续聊多久，而是项目能否在多次换人、换模型、换工具后仍然稳定推进。

---

#### 三、辩证思考

##### 值得肯定

- **方向正确**：把智能体从 “聪明聊天工具” 升级为 “受治理的协作成员”。
- **可替换性强**：避免项目知识被某个模型、平台或会话绑架。
- **更适合长期复杂任务**：尤其适用于软件开发、研究、审计及合规工作。
- **可信度更高**：证据、权限、验证和历史共同约束幻觉与越权。

##### 需要警惕

1. **结构化本身有成本**  
   小项目若引入完整角色、事件图和审批链，可能治理成本高于执行收益。

2. **仓库不天然等于真相**  
   错误信息一旦被结构化，只会变成更正式的错误；关键仍是来源质量与验证独立性。

3. **验证可能产生 “同源幻觉”**  
   若执行者和验证者使用相同模型、提示与资料，其错误可能高度相关，并非真正独立。

4. **Git 并非所有状态的最佳载体**  
   它适合代码和可审计文件，但高频事件、复杂关系、实时队列可能更适合数据库或事件图；仓库可做权威入口，不必包办一切。

5. **人类瓶颈不会消失，只会转移**  
   人类从传话者变成目标和审批者，但模糊目标、权限设计及价值冲突仍无法完全自动化。

##### 我的判断

这套架构最重要的贡献，不是提出 “多智能体层级”，而是确立了一个原则：

> **智能体可以自治执行，但项目状态必须制度化；输出可以由 AI 生成，真相不能由 AI 单方面宣布。**

实践中应渐进采用：

```text
先做好状态文件、任务边界、测试和决策记录
→ 再增加角色权限与独立评审
→ 复杂度足够高时，再引入事件图和多层调度
```

**最优方案不是最复杂的智能体组织，而是用最低治理成本，实现可靠接力、清晰问责与可验证推进。**

## 结构化（1）

### 2026-08-26 03:41:06

#### 《构建以代码仓库为中心的模块化智能体技术栈》总结

文章提出一种以**项目代码仓库**为持久核心的多智能体架构：模型、会话和工具都可以替换，而项目的状态、规则、证据、决策与历史长期保存在仓库中。其目标是让任何新接入的人或智能体都能快速接手、完成有边界的工作，并留下可验证、可追溯的状态变化。

##### 1. 从 “会话中心” 转向 “项目中心”

传统智能体工作模式是：

```text
人类 → 提示词 → 智能体 → 输出 → 人类
```

- 大部分上下文停留在聊天会话中。
- 人类需要在不同模型、工具和对话之间手动传递信息，充当 “项目记忆”。

作者采用的新模式是：

```text
人类 ↔ 参谋长 ↔ 项目经理 ↔ 执行者 / 评审者 ↔ 共享项目状态
```

核心区别在于：

- **项目状态是持久的**，模型和智能体只是可替换的执行组件。
- 仓库负责保存制度化记忆，包括规则、证据、决策、历史和验证方式。
- 聊天仅作为临时工作记忆，不能成为权威项目记录。

---

##### 2. 代码仓库是项目的共同运行环境

GitHub 不再只是代码托管平台，而是人类和多个智能体共同工作的 “项目基底”。仓库可以包含：

- 源代码、规格、数据模式与测试；
- 任务、队列、验收标准和审批状态；
- 研究主张、来源、实验记录和运行产物；
- 决策记录、失败经验、工具策略；
- 仪表板、报告以及机器可读元数据。

衡量仓库设计是否有效的关键，不是 “是否保存了所有上下文”，而是新智能体能否快速重建：

- 项目目标、当前阶段与已接受状态；
- 结论所依据的证据和权威来源；
- 历史尝试、重大失败与未解决问题；
- 阻塞项、依赖、权限和审批边界；
- 可用角色、工具及下一项有价值的工作；
- 如何验证某项变更是否正确。

---

##### 3. 不保存全部对话，只保存关键状态转换

作者不会持久化模型生成的每一个 token，因为大部分对话只是完成任务所需的临时 “脚手架”。真正值得保存的是工作的物质轨迹，例如：

```text
决策 → 证据 → 结果状态 → 未解决影响
假设 → 实验 → 观察 → 结果 → 置信度
任务 → 实现 → 验证 → 工件
失败 → 诊断 → 新发现的约束
```

这种方法让后续智能体不必重放全部聊天，也能理解项目为何发展到当前状态。优化目标不是 “无限记忆”，而是实现**低成本、可靠的工作延续**。

---

##### 4. 区分规范状态与派生视图

仓库中的信息被分为两层：

###### 规范层：权威底层记录

可以包括：

- Git 历史与仅追加事件；
- 已接受的决策和记录；
- 来源引用、实验输出；
- 不可变运行产物；
- 已验证的声明和状态转换。

###### 投影层：方便使用的当前视图

可以包括：

- README 摘要；
- 当前状态页、仪表板；
- 队列、任务列表和索引；
- 报告、简报；
- 为智能体生成的上下文包。

投影可能过期或不完整，因此必须能够追溯到底层记录，并支持重新生成或质疑。其基本模式来自 ActiveGraph：

```text
事件历史 → 投影逻辑 → 当前状态
```

将事件历史视为首要对象，可以实现：

- 重放和恢复历史状态；
- 查看数据与结论的来源谱系；
- 对项目进行分支和轨迹比较；
- 解释某个状态为何形成；
- 区分 “当前解释” 与 “支撑解释的证据”。

小项目不一定需要真正运行 ActiveGraph，可通过 Git、结构化文件、确定性脚本、测试和规范提交历史实现类似机制。大型项目则可以显式建立关系图：

```text
人 → 智能体 → 任务 → 事件 → 主张 → 实验
→ 工件 → 决策 → 来源 → 结果 → 开放问题
```

这样系统便能回答：某结论依赖哪些争议假设、哪些实验支持某主张、哪个问题阻塞最多下游任务，以及哪些结果已经被独立复现。

---

##### 5. 用分层指令替代单一巨型提示词

智能体的有效指令由多个层次组合：

```text
全局运行规则 + 角色技能 + 项目契约 + 当前任务
```

各层职责不同：

- **全局规则**：通用安全与工作原则；
- **角色技能**：研究、构建、评审等可复用方法；
- **项目契约**：本项目的事实、边界和验收标准；
- **当前任务**：本次需要完成的有限工作。

项目初始化时，应建立最低可行运行环境，包括项目简报、权威信息源、核心不变量、权限、阶段结构和验收标准。

根指令文件只负责索引和路由：

```text
工作类型 X → 加载契约 A
状态类别 Y → 加载策略 B
生成工件 Z → 应用验证流程 C
```

Codex、Claude、Cursor、ChatGPT 等工具的专属指令文件只保存适配逻辑，不各自复制项目规则。重要规则的修改也要作为仓库变更提交，以便追踪和审查，而不是悄悄修改提示词。

---

##### 6. 不同模型通过 “薄适配器” 接入

作者会根据任务使用 ChatGPT、Codex、Claude、Replit、本地智能体、GitHub 自动化和专用连接器，但不会让每个工具形成独立的项目记忆。

每个模型通过轻量适配器接入同一项目，适配器负责明确：

- 智能体身份与角色；
- 可用工具和凭证；
- 读取、修改权限；
- 权威指令入口；
- 当前项目或任务上下文；
- 结果的记录方式。

有文件系统访问能力时，智能体直接读取仓库；只能远程访问时，则通过 GitHub、官方 API、CLI 或结构化连接器工作。浏览器操作只作为结构化程度较低的备选方式。

适配器本身不保存另一套 “项目真相”，因此模型替换不会破坏连续性。例如，关键架构决策不能只存在于某次 Claude 或 Codex 对话中，而必须外部化到仓库。

---

##### 7. 角色不是人格设定，而是可执行合约

系统中的角色包括：

- 构建者；
- 研究员；
- 评审者；
- 验证者；
- 审计者；
- 项目经理；
- 参谋长。

每个角色合约需要明确：

- 读取哪些状态；
- 回答哪些问题；
- 可以做哪些决策；
- 能调用哪些工具；
- 可以修改哪些内容；
- 必须产出什么工件和证据；
- 何时需要升级给更高权限角色；
- 什么条件代表任务完成。

例如：

- **构建者**可以实现有边界的变更，但不能自行修改验收标准。
- **评审者**可以检查、质疑工件，但不直接修改它。
- **验证者**按照确定性契约判断变更能否被接受。
- **项目经理**创建、排序和委派任务，但不必亲自执行。
- **审计者**检查来源、政策合规性和权威记录完整性，不参与常规执行。

模型提供推理与执行能力；仓库和角色契约则提供权威、制度背景与操作程序。

---

##### 8. 用 “心跳” 驱动有边界的执行

持久状态只能提供连续性，不能自动产生行动，因此系统使用短周期的 “心跳” 控制循环：

```text
确认角色与权限
→ 检查任务、审批和状态变化
→ 对照项目目标协调当前状态
→ 领取一个有边界的工作单元
→ 执行或委派
→ 验证并记录状态转换
→ 退出
```

心跳的价值在于：

- 减少对超长上下文窗口的依赖；
- 限制未记录假设不断积累；
- 让每次执行都短小、清晰、可检查；
- 由项目状态在两次心跳之间保持连续性。

不同层级采用不同粒度：

```text
参谋长心跳
→ 判断哪些项目需要关注

项目经理心跳
→ 判断项目下一步最有价值的行动

执行者 / 研究员心跳
→ 完成一项有边界的工作

评审者 / 验证者
→ 检查工件或主张

代码仓库
→ 记录被接受的状态转换
```

心跳可以定时运行、由事件触发，也可以由人手动调用。

---

##### 9. 项目经理管本地，参谋长管项目组合

每个长期项目仓库可拥有一个项目经理，负责：

- 解读项目本地状态；
- 安排任务顺序；
- 识别阻塞项；
- 委派专业智能体；
- 协调并整合已完成的产出。

参谋长则跨项目运作，只维护精简的项目组合视图，例如：

- 活跃项目及其目标；
- 当前阶段和负责人；
- 最近的重要状态变化；
- 阻塞或停滞工作；
- 待审批事项；
- 未解决决策；
- 推荐的下一步行动；
- 项目健康度或置信度。

其控制循环是：

```text
观察项目组合
→ 发现需要关注的问题
→ 分派给对应项目经理
→ 协调处理结果
→ 将关键判断升级给人类
```

参谋长不会把所有项目细节塞进一个中央提示词中，否则它会变成第二套记录系统，并形成脆弱的超大上下文。

---

##### 10. 核实是独立的系统层

多智能体系统最危险的情况，是后一个智能体未经检查便继承前一个智能体的结论。因此，作者将核实设计为状态转换的必要环节：

```text
智能体提出变更
→ 验证者依据契约检查
→ 通过后才更新已接受状态
```

核实方式可以包括：

- 数据模式和类型系统；
- 自动测试与持续集成；
- 确定性验证器；
- 允许修改的路径规则；
- 状态转换约束和校验和；
- 预注册实验判定条件；
- 独立复现和结构化评审。

当错误代价较高时，“生成变更” 和 “接受变更” 必须由不同步骤或角色完成。尤其是智能体修改自己的指令、评估器或编排逻辑时，不能仅凭其自报成功就接受，而应由外部不变量或独立验证者检查。

研究主张同样必须具备完整谱系：

```text
主张
← 证据
← 来源或实验
← 方法与版本
← 运行记录或工件
← 假设
← 产生该主张的智能体或行动
← 置信度与认知状态
```

---

##### 11. 显式标注知识的认知状态

仓库不会把所有 AI 生成内容都视为 “已知事实”，而是标注不同状态，例如：

```text
提议 / 已观察 / 已复现 / 已接受 / 有争议
已取代 / 未解决 / 推断 / 有来源支持 / 推测
```

必要时还应记录：

- 置信度；
- 权威等级；
- 敏感性；
- 证据基础。

这使新智能体能够区分：

- 已验证的不变量；
- 临时解释；
- 尚未解决的冲突；
- 缺乏支持的假设。

如果不做区分，大量非结构化 AI 输出最终只会形成不可靠的文本档案；加入来源追踪和认知状态后，它们才能成为可审查的机构记忆。

---

##### 12. 人类负责判断，而不再负责传递记忆

在该架构中，人类的职责从 “手动搬运上下文” 转向较难形式化的部分：

- 目标与优先级；
- 品味和方向；
- 约束与歧义消解；
- 关键审批；
- 战略变化。

参谋长和项目经理负责把最需要人类判断的节点暴露出来。人类只需关注：

- 哪些事项需要注意；
- 哪些项目被阻塞；
- 哪些决策需要判断；
- 优先级发生了什么变化；
- 哪些工作可以继续自主推进。

如果一项人类决策会影响未来任务，它就应写入仓库，成为持久控制状态，并进一步影响审批、验收标准和智能体行为。这样，人类仍处于控制回路中，但不再是项目记忆的传输层。

---

##### 13. 每次会话都应留下 “状态增量”

一次智能体会话结束时，除了交付直接产物，还应留下清晰的状态增量，例如：

- 实现与测试；
- 实验结果和证据；
- 更新后的主张或置信度；
- 决策记录；
- 新发现的约束；
- 失败方法；
- 来源指针；
- 未解决问题；
- 有边界的下一步行动。

整体循环为：

```text
执行 → 记录线索 → 更新状态 → 验证 → 从新状态继续
```

随着历史工作不断沉淀在仓库中，后续智能体加载上下文的成本会越来越低，无需人类反复进行项目简报。

---

##### 14. 架构总览与实际应用

整套技术栈可以概括为：

```text
项目基底
=
规范状态
+ 派生投影
+ 分层指令
+ 角色合约
+ 模型适配器
+ 有界心跳
+ 独立核实
+ 来源溯源
+ 人类治理
```

ActiveGraph 带来的关键思想，并不是要求每个项目都使用特定运行时，而是把项目视为一个**持续演进、可重放、可分叉、可比较的系统**，当前状态必须源自持久的工作记录。

作者给出的实际工作方式是：

- 通过远程 Codex 的语音或文字与参谋长沟通；
- 参谋长向不同项目经理分配任务；
- 项目经理再把工作交给执行者或实施者；
- 参谋长和每个项目都拥有独立代码仓库；
- 因为项目记忆不依赖某台设备或某次会话，所以可以几乎在任何地方免手持地推进工作。

**最终分工是：模型提供推理和执行能力，仓库提供连续性，角色与契约提供行为边界，心跳驱动行动，核实与溯源建立信任，项目经理负责本地协调，参谋长负责跨项目注意力分配，人类则负责目标、约束与关键判断。**

## 深度解读（1）

### 2026-09-18 10:17:43

#### 智能体真正需要的不是更长记忆，而是可接管的项目状态

这套架构最值得保留的判断，不是“用多个智能体分工”，而是**把持久化单位从模型和对话改成项目**。模型、IDE、会话乃至具体智能体都可能频繁更换，真正需要连续存在的是项目的目标、约束、决策、证据和已验证结果。

今天许多智能体产品仍依赖人来维持连续性：把上一轮背景重新讲给新模型，解释哪些方案失败过，再提醒它不能改什么。作者试图让代码仓库承担这种“机构记忆”，使新智能体只需读取项目状态，就能确定自己有什么权限、下一步做什么，以及结果如何验收。**人不再充当上下文搬运工，而主要负责目标、优先级、品味和关键审批。**

##### 关键不是保存所有对话，而是记录状态为什么改变

文章对“长期记忆”做了一个重要修正：完整保存聊天记录既昂贵，也未必有用。对话大多是推理脚手架，值得持久化的是压缩后的工作轨迹，例如：

> 假设 → 实验 → 观察 → 结论 → 置信度  
> 失败 → 诊断 → 新发现的约束

这实际上把事件溯源用于智能体协作。README、任务列表和仪表盘只是当前状态的投影；更可靠的基础是决策、实验、提交、来源和验证记录。摘要即使过期，也可以由底层记录重新生成或质疑。

这比简单的“把文档放进 Git”更进一步：它要求每次会话留下可供下一位参与者接管的**状态增量**。衡量系统质量的标准也随之变化——不是智能体当轮回答多精彩，而是陌生智能体能否低成本恢复项目状态并继续推进。

##### 多智能体系统的核心风险，是结论未经核实就层层继承

作者把“生成”和“接受”分成两个动作：

> 智能体提出变更 → 验证者依据合约检查 → 项目接受新状态

这可能是整套架构里最重要的可靠性设计。多智能体并不会自动带来更高质量；如果后一个智能体直接继承前一个智能体的结论，错误只会获得更多形式上的背书。因此，角色不应只是人格提示，而应是权限明确的执行合约：构建者可以修改实现，但不能修改验收标准；评审者可以质疑，但不能直接改写产物。

同样，研究结论也不能只以一段流畅文本存在，而要标明它是“观察到的”“已复现的”“有来源支持的”，还是“推测性的”。**智能体规模化之后，最大的资产不是生成内容，而是内容的认知状态与证据谱系。**

##### 机会在“项目控制层”，但适用边界很明确

从产品角度看，潜在机会不是再做一个万能聊天入口，而是建立连接 GitHub、Linear、Notion、CI 和不同模型的项目控制层：维护规范状态，生成上下文包，管理权限与审批，并记录每次状态转换的证据。

最适合率先验证的场景，是软件研发、实验研究和合规工作——任务可拆分、产物可留痕、验收相对明确，错误传播的代价也足够高。关键指标应是新智能体接管时间、重复简报成本、错误状态被接受的比例，以及回滚和审计能力，而不是调用了多少智能体。

不过，文章主要提供的是架构主张，而非效果证据。它可能退化为昂贵的文档官僚体系；自动检查也常常只能验证格式和测试，无法验证方向与事实。真正的瓶颈最终会从上下文窗口转移到：**能否定义高质量的状态模式、角色边界和验收机制。**仓库只是实现载体，“项目是否变得可接管、可质疑、可验证”，才是这套思路真正值得检验的地方。

## 口播总结（1）

### 2026-09-20 00:21:49

构建长期运行的智能体系统，关键不是找到一个永远不换的模型，也不是保存所有聊天记录。更重要的，是把“项目”变成真正持久的单元。模型、工具、界面和会话都可以更换，但项目的目标、规则、证据、决策和历史，必须留在一个可追溯、可验证的环境里。

作者选择的项目基底，是受治理的代码仓库。这里的代码仓库不只是存放代码，也相当于项目的共享工作空间。它可以保存规格说明、研究结论、来源、实验结果、决策记录、验收标准、任务队列、测试、审批状态，以及机器可读的元数据。

传统的人机协作通常是，人提出提示，智能体完成任务，再把结果交还给人。大量上下文只存在于当前对话中。换一个模型、工具或者会话，人就得重新解释项目背景。换句话说，人类实际上承担了项目记忆的搬运工作。

以代码仓库为中心的架构则不同。人类通过参谋长协调多个项目，项目经理负责理解某个项目的具体状态，执行者和研究员承担有边界的任务，评审者和验证者检查结果。所有角色都围绕同一份共享项目状态工作。

这里最核心的区分，是持久的项目状态，与可以替换的执行组件。Claude、Codex、ChatGPT、本地智能体，甚至交互界面，都只是接入项目的执行工具。真正的连续性来自代码仓库。

判断一个仓库是否保存了足够的状态，不是看它有没有记录每一句对话，而是看一个新接入的智能体，能否迅速回答几个关键问题。项目要实现什么，目前处于哪个阶段。哪些结果已经被接受，证据是什么。哪些来源属于权威记录。以前尝试过什么，为什么失败。还有哪些阻塞、依赖和未解决问题。智能体有什么权限，哪些决定必须交给人类。下一步有哪些范围明确的工作，以及结果应该怎样验证。

聊天仍然有用，但它只适合作为临时工作记忆，不应该成为权威的项目记录。作者也不主张保存模型生成的每一个词。大部分对话只是完成工作的脚手架。真正值得持久化的，是状态变化。

例如，一项决策依据了什么证据，决策之后项目状态发生了什么变化，又留下了哪些未解决影响。一个假设如何被实验检验，观察到了什么结果，置信度因此怎样变化。一项任务产生了什么实现，经过什么验证，最终留下了哪些工件。一次失败又暴露了什么新的约束。

这种记录方式压缩了工作的实质轨迹。未来的智能体不需要重放全部对话，也能理解项目为什么走到今天。目标不是拥有无穷无尽的记忆，而是用较低成本实现可靠延续。

为了做到这一点，仓库还要区分“规范状态”和“派生视图”。

规范状态是更底层、更可靠的记录，例如 Git 历史、只追加的事件、正式接受的决策、来源引用、不可变的实验产物，以及经过验证的主张。

派生视图则是为了方便阅读而生成的摘要，例如项目说明、当前状态页面、仪表板、任务列表、简报，或者专门给智能体准备的上下文包。

派生视图可能过期，也可能遗漏信息，所以不能被当作最终真相。它的价值在于，可以追溯到更稳定的底层记录，也可以从底层记录重新生成。这种思路受到 ActiveGraph 的启发。简单说，就是先保存事件历史，再根据规则生成当前状态。当前状态不是凭空出现的，而是过去一系列事件的结果。

这样一来，系统不仅能告诉你“现在是什么状态”，还能回答“为什么会形成这个状态”。它也可以追查，某个结论依赖了哪个有争议的假设，哪些实验支持了某项主张，哪个决定改变了项目轨迹，哪些未解决问题阻塞了最多后续工作，以及哪些结果已经被独立复现。

不过，持久状态只能提供连续性，并不会自动产生行动。为此，作者设计了所谓的“心跳”。心跳是一次短暂而有边界的控制循环。

每次心跳中，智能体先确认自己的角色和权限，再检查任务、审批和最新变化。接着，它把当前状态与项目目标进行对照，只领取一项范围明确的工作。完成后，它验证结果，记录这次状态变化，然后退出。

这种短循环有两个好处。第一，它减少了对超长上下文的依赖。第二，它限制了未经记录的假设不断累积。连续性由项目状态承担，而不是由一个永不结束的智能体会话承担。

不同角色的心跳范围也不同。执行者可以深入处理一个具体的实现或研究任务。项目经理负责识别下一项最有价值的项目级行动，并安排任务顺序。参谋长则跨项目分配注意力，关注哪些项目停滞了，哪里需要审批，哪些决策必须由人类判断。

参谋长不会把所有项目的细节都塞进一个巨大的中央提示中。需要深入分析时，参谋长把问题交给对应项目的项目经理。项目经理再依据本地仓库中的状态和规则采取行动。这样可以避免顶层协调器变成另一个脆弱的记录系统。

角色本身也不是人格扮演，而是一份可以执行的工作合约。合约要明确，智能体可以读取哪些状态，负责回答什么问题，能调用哪些工具，能修改哪些内容，必须留下什么证据，什么时候需要升级给人类，以及怎样才算完成。

例如，构建者可以实施范围明确的变更，但不能自行修改验收标准。评审者可以检查和质疑工件，但不应该直接修改被评审内容。项目经理可以创建和排序任务，却把具体实施委派给专业智能体。审计者负责检查来源、规则合规性和权威记录的完整性，但不参与日常执行。

模型接入项目时，则通过一个轻量适配器。适配器只负责说明智能体是谁、承担什么角色、拥有哪些工具和权限、从哪里读取规范指令，以及怎样记录结果。适配器不应该另存一套项目真相。这样更换模型时，破坏性会小得多。某次 Claude 对话不会掌握 Codex 无法获得的关键知识，某个临时会话也不会成为架构决策的唯一保存地点。

整套系统能否可信运行，还取决于一个常被忽略的部分，也就是独立核实。

多智能体协作最危险的情况，是后一个智能体直接继承前一个智能体的结论，却不做检查。于是一个错误会沿着任务链不断放大。在这套架构中，智能体只负责提出变更，验证者依据预先定义的合约检查变更。只有通过检查，项目的正式状态才会更新。

核实可以由测试、持续集成、类型系统、路径权限、状态转换约束、校验和、结构化评审或独立复现完成。尤其当智能体能够修改自己的指令、评估器或编排逻辑时，不能因为它声称修改成功，就自动接受结果。修改必须由范围之外的不变量，或者独立授权的验证方来检查。

研究结论也一样。一个主张不应该只是仓库里的一句话。它还要关联证据、来源或实验、使用的方法和版本、运行产物、前提假设、生成它的智能体，以及当前置信度。

因此，仓库还需要显式区分不同的认知状态。某项内容究竟只是提议，还是已经观察到；是独立复现过，还是正式接受；是存在争议，已经被取代，仍未解决，还是仅仅出于推测。新进入的智能体必须能够区分已验证的事实、暂时解释和缺乏支持的假设。

在人类这一侧，角色也发生了变化。人不再负责在多个智能体之间手工搬运上下文，而是专注于机器难以形式化的部分，包括目标、优先级、品味、约束、歧义处理、关键审批和方向调整。

当一项人类决策会影响未来工作，它就应该成为持久的项目状态。后续任务、权限和验收标准可以直接继承这项决策，而不用在每次会话中重新说明。人类仍然处于控制系统之中，但不再充当项目记忆的传输层。

这套架构最值得记住的，是三个认识。

第一，真正应该持久化的不是智能体，而是项目。模型负责提供可变的推理和执行能力，代码仓库负责提供连续性。

第二，不必保存所有对话。应该保存可追溯的状态变化，以及形成这些变化的证据、决策、实验和失败。

第三，智能体生成结果与系统接受结果，是两件不同的事。只有把角色权限、独立核实、来源谱系和人类治理纳入项目结构，多智能体协作才可能从一次性的自动化，变成可以长期延续、替换组件并可靠审查的工作系统。
