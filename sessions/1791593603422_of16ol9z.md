## 分析要点

- **核心高价值点**：区分继承主代理上下文的分叉子代理与不继承其上下文的独立子代理，让任务延续和独立审查采用不同的上下文策略。
- **留存建议**：选择性阅读并保留设计清单，模型性能与成本判断不作为决策依据（包含可复用的子代理管理需求：上下文继承与隔离、人工介入、代理预设、并发与嵌套限制、会话持久化。）

**知识要点**

- 子代理可以继承主代理在分叉时的上下文，也可以仅接收初始任务提示；独立上下文适合需要减少既有判断影响的审查任务。
- 子代理管理需要同时考虑运行状态可见性、人工介入、并发数量、嵌套深度和历史持久化，而不只是提供启动代理的接口。
- 代理预设可以绑定模型与思考强度；机会式模式由主代理自行决定是否委派，编排者模式则让主线程专注委派与用户沟通。

**行动项**

- 将上下文继承与隔离、状态查看、人工介入、并发及嵌套上限整理为现有Agent工具的功能检查清单。
- 针对快速事务与研究规划分别配置代理预设，明确各自的模型和思考强度。
- 检查子代理历史是否随主会话持久化，并测试进程中断后的会话恢复。

### 我自己写了一个 pi 子代理管理器，原因如下

任何在这里关注我的人都知道，我是 Pi 的超级粉丝。就是那个编码编辑器。 虽然我不会在第二段就偏离主题开始对 Pi 疯狂吹捧，但只需说一句就够了：我喜欢能够按照自己的喜好改造这个编码工具，而且我在各种任务上做了足够多的客观和主观测试，发现 pi 明显比 claude code 或 codex cli 更快完成大多数任务，成本也低得多，原因就是它对上下文的膨胀要小得多。

#### 直到 26 年上半年：子代理 = 对我来说太花哨了

今年上半年的大部分时间里，我并不是子代理的重度用户，尽管我一开始就能看到围绕 OpenClaw 这类狂野西部式工具，或者 GasTown 这类软件工厂式东西，到处弥漫着那种“代理编排”精神病。

话虽如此，Claude/Copilot CLI/Codex 默认配备的子代理使用量（是的，Copilot CLI 从早期就有可靠的子代理机制）在我看来，在某些任务中越来越明显地有用。所有那些“我正在启动一个独立的代理来研究/审查/监控这个东西”的做法，越来越可靠、实际上不再是垃圾、越来越有用，而且我开始看到模型对此也有了更好的掌握。我认为 GPT 5.3 / Opus 4.5 代模型可以使用子代理，因为这当然只是另一次工具调用，所以它们知道“如何握住工具”，但并不真正以子代理范式来思考工作，但随着我们来到 GPT 5.6 / Opus/Sonnet 5 代，模型更好地知道如何将自身的另一个实例用作独立代理。它们知道何时分叉上下文，何时以全新上下文启动独立会话等等。有了 Claude 5.5 和 GPT 6 代，我认为模型已经准备好以子代理模式被常规使用了。事实上，我认为将它们用作子代理比检出工作树、自己充当子代理的编排者更好。

（需要说明的是，“agent orchestration”已经演变成了两种含义——一种是更高层次的，比如通过 Conductor、T3 Code 等工具运行多个 Claude Code 副本，最好是在 worktree 中运行；但我这里说的是同一个 harness 实例中的同一个会话在内部创建多个线程）

#### 运行 subagent 的最佳方式

Claude 和 Codex 内置了对 subagent 的支持。Pi 没有。它可以通过 sub-shell 调用来进一步发起“pi”调用，但那并不完全是 subagent。

As most people using Pi trying out subagents would have had, I started using subagents originally with

[@nicopreme](https://x.com/@nicopreme)'s version \`npm:pi-subagents\` He was the first to make a subagent extension, and with the first mover advantage it is the most popular one out there and works really well.

说实话，在 Opus 5.5 和 GPT 6.1 Sol 发布之前，我完全算不上是子代理这种范式的重度用户。原因（上面已经暗示过，但这里具体展开）——

1. 虽然任何模型只要运行框架提供了子代理类型的工具就能使用它们，但在 Fable 和 Astra 发布之前，没有哪个模型真正“懂得”如何利用子代理来最大化自身的生产力。它们并不擅长在这样一个抽象层次上运作——即能够再运行 5 个自身的副本，而不会因 git 冲突、端口冲突之类的问题而互相绊倒。从某种意义上说，Fable/Astra 是第一批“资深软件工程师”级别的模型，能够有效地将任务拆解为多层级的工作流并高效地编排它
2. 但是；Fable 和 Astra 在无限制的子代理工作流中运行成本非常高（无论是美元，还是订阅额度的消耗速度）。如果你让 Fable/Astra 无限制地创建子代理，它们会在 20 分钟内吃掉 $200 套餐的额度窗口。出于同样的原因，人们也大肆调侃 /ultracode 和 /workflow 之类的东西，Claude 不得不发布一个修复，使得仅仅在提示词中说出“workflow”就不应该启动 20 个 Fable 并让你每分钟花掉 $100。

最新这一代，Opus 5.5 和 6.1 Sol，实际上是第一批在经济上可行、能够将子代理作为一项功能正确使用的模型。因此我越来越成为那种在提示词末尾写上“use subagents”的人。（这就是促使模型使用它们所需的全部操作）

#### 理想的子代理用户体验

让我不要试图说服你，说我比 Boris 或 Tibo 更懂得如何制作一个编码运行框架，但我可以告诉你我的品味和偏好。

the 'Claude' UX of viewing the subagents

- the agents show up near the input box, clicking ← arrow opens a list of agents, you can see their status (running/paused/errored) and you can open to see what they are doing
- manually steer subagents by dropping into a subagent's tree and type something to it

the Codex principle of /root/based paths to name subagents

- /root is the main agent. /root/task-1 is a subagent "forked" from root that inherits the context upto the point of its forking
- /task-2 is an "independent" subagent that is not forked from root. root can send it an initial prompt but its context is not 'tainted' and it can run adversarial reviews for example

the pi-subagents flexibility to set subagent defaults

- a subagent is a lot like a pi session itself; when spawing a subagent you pick which model it'll run with, what thinking level and so on; what I like about both the pi-subagent extensions is that you can create predefined "agents" that have these things set. you can use a luna-based low thinking fast agent to do quick logistical tasks (git push); and use a chonky unhallucinating model like fable/astra to research or create major refactor plans
- we should have the ability to create these predefined agents instead of having to rely on what the main model wants to use for its subagent or prompting it everytime like "use an opus subagent to research this..."

... that and a few more things

- ability to define how deep nested subagents to allow (3 levels is what I like, but it should be an option)
- how many parallel subagents can be allowed to run
- the entire history (of all subagents) all stored in the single .jsonl file. so that the whole parephernelia can be resumed from a crash/killed shell or old session
- have multiple models specified for an agent; and it will pick whichever one is available (provider is enabled) and allowed (via scoped models)
- have two modes: opportunistic: the main model will use subagents if it thinks it wants to, orchestrator: the main thread will always spin up subagents for all tasks and itself stay free to talk to you!

## 通俗精炼（1）

### 2026-10-10 00:47:47

#### 为什么作者为 Pi 自己写了一个子代理管理器

作者原本觉得，让多个 AI 代理协同写代码有些花哨，但随着模型更擅长拆分任务、协调工作，他开始频繁使用子代理。Pi 又是他最喜欢的编码工具，却没有内置子代理支持，因此他最终自己写了一个管理器。**他的核心诉求不是“多开几个 AI”，而是让子代理可观察、可干预、可配置，并能控制成本、恢复会话。**

##### 1. 为什么坚持用 Pi，而不是直接使用 Claude Code 或 Codex？

作者喜欢 Pi，主要有两个原因：

- **可以按自己的工作习惯改造工具。**
- **在他自己的测试中，多数任务完成得更快，成本也更低。**

他认为，第二点与 Pi 的“上下文膨胀”更少有关。上下文就是模型处理任务时需要读取的对话、代码、工具输出等信息。如果这些内容不断堆积，后续调用就要反复处理越来越多的信息，增加时间与费用。作者认为 Pi 在这方面更节制。

不过，这些比较来自作者的客观测试和主观体验；文章没有提供任务集、测试方法或具体数据，不能直接当作普遍成立的性能排名。

##### 2. 作者为什么从怀疑子代理，转向经常使用它？

**子代理，是主代理为某项工作启动的另一个 AI 执行单元。**例如，主代理负责实现功能，同时让子代理研究代码、做审查或监控某个过程，之后再接收它的结果。

作者态度的变化，背后有两个不同的问题：模型是否会用，以及用起来是否划算。

###### 从“会调用工具”，到“会安排工作”

早期模型即使能够调用子代理工具，也不代表它知道怎样合理分工。它可能会启动多个副本，却没有处理好任务之间的关系，导致代理修改同一处代码、产生 Git 冲突，或启动服务时争抢同一个端口。

作者认为，后来模型开始更清楚地判断：

- 什么任务值得交给另一个代理；
- 什么时候应该让子代理继承当前上下文；
- 什么时候应该让它从一个干净的上下文开始；
- 怎样把任务拆成多层级工作流，而不是简单地同时启动几个副本。

他把文中称为 Fable、Astra 的模型视作一个能力转折点：它们开始像资深工程师一样，能够有效拆分和协调工作。

###### 从“有能力”，到“经济上可行”

但能力提升并不等于适合日常使用。**如果主代理不加限制地启动大量高成本子代理，费用和订阅额度可能迅速耗尽。**

作者举例称，Fable/Astra 的无限制子代理工作流，可能在约 20 分钟内耗尽一个 200 美元套餐的额度窗口。这里说的是订阅使用额度，不是精确测算“20 分钟花掉 200 美元现金”。他还提到，一些工作流会启动大量昂贵代理，甚至需要修正“仅因提示词出现 workflow 就过度启动代理”的行为。

在作者看来，最新一代的 Opus 5.5 和 GPT 6.1 Sol，才让“正确使用子代理”和“经济上可行”同时成立。因此，他现在经常只在提示词末尾补一句“use subagents”，让模型自行决定如何分工。

**这些模型能力与成本判断主要是作者的体验和评价，文章没有提供统一的基准测试来验证。**

##### 3. 他要解决的是会话内部协作，不是管理多个独立编码窗口

文章特意区分了“代理编排”的两种含义：

| 方式 | 谁来协调、怎样运行 |
|---|---|
| 管理多个独立编码代理 | 用户借助 Conductor、T3 Code 等工具运行多个 Claude Code 实例，通常放在不同的 Git worktree 中 |
| 在同一会话内部启动子代理 | 主代理在同一个运行框架中创建多个执行分支，分配任务并接收结果 |

Git worktree 可以理解为：同一个仓库拥有多个工作目录，让不同任务分别改代码，减少彼此干扰。“运行框架”则是包围模型的那层软件，负责工具调用、上下文和会话管理。

**作者关注的是第二种：让主代理在一个会话内部负责分工，而不是由用户手动充当多个 AI 的调度员。**

Claude 和 Codex 已有内置子代理支持，Pi 没有。Pi 虽然能通过子 shell 再启动一个 Pi 进程，但单纯“另开一个进程”，并不等于拥有完善的子代理管理体验。

作者最初使用的是 `npm:pi-subagents`，也提到另一个 `@tintinweb/pi-subagents` 扩展。他认可这些现有扩展，但自己的偏好与需求更多，最终决定另做一个管理器。

##### 4. 理想体验之一：看得见进度，也能直接介入

作者喜欢 Claude 的子代理界面：代理显示在输入框附近，可以打开列表，查看正在运行、暂停或出错等状态，再进入某个代理查看它正在做什么。

他还希望能够**直接进入某个子代理的执行分支，给它补充指令或纠正方向**，而不必所有沟通都经过主代理。

这解决的是一个实际问题：当几个代理同时工作时，用户不能只能等待最后结果。某个代理理解错了任务，或者卡在错误上，用户应该能及时发现并干预。

###### 用路径表达代理关系与上下文来源

作者还喜欢 Codex 用路径命名代理的方式：

- `/root`：主代理。
- `/root/task-1`：从主代理分叉出来的子代理，继承分叉时已有的上下文。
- `/task-2`：独立启动的子代理，接收初始任务，但不继承主代理此前的完整上下文。

**“继承上下文”和“独立上下文”适合不同的工作。**

继承上下文的代理已经知道前面的讨论与判断，适合继续完成相关任务；独立代理不会直接沿用主代理已有的推理，更适合做挑错、质疑方案的审查。作者希望用后一种方式，减少审查者被原方案带偏的风险——但这并不意味着它因此就一定正确。

##### 5. 理想体验之二：事先定义代理，而不是每次临时指定

在作者看来，一个子代理很像一个独立的 Pi 会话：启动时应当能选择模型、思考强度等配置。

他希望把这些配置保存成预定义代理。例如：

- 用速度快、思考强度低的代理处理 `git push` 之类的简单操作；
- 用能力更强、作者认为更少出现幻觉的模型，做研究或制定大型重构计划。

**这样，用户可以事先规定“哪类工作由哪类代理承担”，不必完全依赖主模型临时选择，也不必每次提示“请用某某模型研究这个问题”。**

作者还希望，一个预定义代理可以配置多个候选模型。运行时，再根据提供商是否启用，以及当前配置允许使用哪些模型，选出可用的一个。这样代理的职责可以保持稳定，不会因为某个模型暂时不可用，就需要重新配置整套工作方式。

##### 6. 理想体验之三：限制规模、保存历史，并提供两种工作模式

除了交互与配置，作者还提出几项运行控制需求。

###### 限制代理的数量与嵌套深度

子代理还可能继续创建自己的子代理。作者希望用户可以分别设置：

- **最大嵌套深度**：他个人偏好三层，但应当可配置。
- **最大并行数量**：限制同一时间运行多少个子代理。

这两个限制控制的是不同事情：前者防止任务一层层向下扩张，后者防止同时运行过多代理。它们有助于约束工作流规模，但文章没有证明，仅靠这两个限制就能解决代码冲突或所有成本问题。

###### 把整个代理体系的历史放在一起

作者希望主代理和所有子代理的历史，都保存在同一个 `.jsonl` 文件中。JSONL 可以理解为一种按行记录数据的日志格式。

目的不是单纯方便存档，而是：**终端被关闭、进程崩溃，或重新打开旧会话时，能够恢复整个协作过程，而不只是主代理的对话。**文章提出的是会话恢复需求，并未说明外部操作是否都能完整恢复。

###### 在两种协作模式之间切换

| 模式 | 主代理如何工作 |
|---|---|
| **按需使用子代理**（opportunistic） | 主代理自己处理任务，只在认为有必要时启动子代理 |
| **专职编排**（orchestrator） | 主线程把任务交给子代理执行，自己保持空闲，继续与用户沟通和协调 |

第二种模式尤其体现了作者的偏好：主代理不只是埋头执行任务，也应当始终充当用户可以交流的协调者。

##### 结论：他要的是一套可管理的协作机制

作者已经把自己的管理器发布到 npm，并邀请有相同需求的人使用；文章没有给出该新包的明确名称，也没有逐项展示功能验证结果。

这篇文章最值得抓住的区别是：**启动多个 AI 实例，只是子代理能力的起点；真正好用的管理器，还要决定它们继承什么信息、使用什么模型、能扩张到多大，以及用户如何查看、干预和恢复它们的工作。**作者自行开发，正是为了把这些控制权做进 Pi。
