## 分析要点

- **核心高价值点**：将子代理保留为可持续跟进的会话，而非每次返工都新建会话，可复用已建立的任务上下文并减少重复输入成本。
- **留存建议**：精读并存档，重点提取委派规则和持久子代理实现方式（提供了可复用的协调器—执行器分工框架、CLAUDE.md 委派规则及跨工具 tmux 协作方案，对编码 Agent 工作流有直接实践价值。）

**知识要点**

- 协调器负责澄清需求、冻结规范、架构决策、审查和最终交付，执行器负责实现、测试、重构等边界清晰的机械性工作。
- 持久子代理能在返工时延续原有上下文，避免重新读取文件和重复推导，并提高上下文缓存的利用率。
- tmux 的窗格控制、capture-pane 与 wait-for 信号可以充当跨 Claude Code、Codex、Gemini CLI 等工具的轻量通信和完成回调层。

**行动项**

- 在 CLAUDE.md 中加入协调器与执行器的委派规则，并明确禁止执行器递归生成子代理。
- 选择一个真实编码任务，先冻结规格文件，再由较便宜模型执行，由前沿模型审查和决定是否合入。
- 用 tmux split-window、send-keys、capture-pane 和 wait-for 搭建一个跨编码代理的持久会话实验。

### 我之前用 Fable 用错了...

[![视频](https://pbs.twimg.com/amplify_video_thumb/2079154897896038400/img/hWr3MqzOoIBw1uO7.jpg)](https://x.com/jasonzhou1993/status/2079161411746570385)[![视频](https://pbs.twimg.com/amplify_video_thumb/2079154897896038400/img/hWr3MqzOoIBw1uO7.jpg)](https://x.com/jasonzhou1993/status/2079161411746570385)

早上你打开 Claude Code，给 Fable 5 一个实际任务，到午餐时间你已经达到了限制。

大多数人会将其解读为“配额太小”。我认为这是相反的信号：

> 你正在为一个模型支付高昂的价格，而一个更便宜的模型本可以同样出色地完成这项工作。

Fable 5，GPT-5.6 Sol Max——它们非常强大，但运行缓慢且成本高昂。随着前沿技术不断进步，前沿模型不再是编写代码的工具，而是成为决定编写什么代码的东西。

这现在是官方推荐的做法，而非权宜之计。使用大模型作为规划者，使用较小的模型作为执行者。

从经济角度看，这很难反驳：Sonnet 5 的价格约为 Fable 5 的 20%，并且性能大致相当于几个月前地球上最强的模型 Opus 4.8。你并没有降级。你现在支付的是 2026 年的价格，购买的却是春季时的尖端技术。

#### 两种配置——并且为什么只有其中一种很便宜

Claude Code 自己的文档描述了两种来做这件事的方法，并且这两种方法听起来是等效的：

1\. Advisor. Sonnet 5 is the main driver. It does the work, and occasionally makes a tool call out to Fable 5 to review its plan and hand back advice.

2\. 编排器。Fable 5 是主智能体。它提问、制定计划、冻结规范，并在较小模型上启动工作智能体以执行。

Devin 实际上两个都运行了。他们一直在推出一个名为 Devin Fusion 的框架，该框架声称在约 35%更低成本的情况下，达到 Fable-5 级或更高的性能，方法是将不同类型的任务路由到不同模型。剥离品牌后，Fusion 本质上是：Claude 代码的 Fable 5 编排器 + Sonnet 5 workers。

![Image](https://pbs.twimg.com/media/HNqfR3bbsAAG6YV?format=jpg&name=large)

他们的结论毫不含糊。编排器模式胜出，原因是代币记账，而非智能：

> 顾问必须阅读主代理的完整对话历史才能给出有用的内容。工作人员只接收任务。

顾问调用每次都会发送新的输入 token。Worker 调用访问缓存的上下文 — 并且缓存的 token 成本大约是新输入 token 的 10%。顾问模式会悄无声息地按照前沿费率向你收取重复阅读自己对话记录的费用，一遍又一遍。

#### 大家理解错的一点是：子代理应该是持久的

这就是大多数 orchestrator 配置悄悄流失资金而无人察觉的地方。

传统上，当 Claude Code 或 Codex 生成子代理时，它会即时启动一个新的会话。子代理执行任务，返回最终消息后终止。然后主代理读取结果，发现有问题，需要修改——于是它再次调用任务工具，该工具会生成一个全新的、无上下文的子代理。该代理重新读取相同的文件，重新推导相同的理解，并再次消耗相同的 token。

Devin calls the fix a sidekick. The sub-agent is a persistent session. Feedback goes back as a follow-up message to the same agent, which still has everything it learned — and all of that context is now cached, so it's nearly free.

![Image](https://pbs.twimg.com/media/HNqfZHaaQAAONtc?format=jpg&name=large)

如果你使用 Claude Code，你已经具备了这个。这实际上就是代理团队是什么：

- 你可以提示 Claude Code 使用代理团队，而不是一次性子代理。
- The new version ships a SendMessage tool, so the main agent can message an existing session.
- When a teammate finishes, it stays resumable until it gets a shutdown request.
- When you start a team session, you can specify the model per agent.

因此，Fable 5 作为协调器，Sonnet 5 作为执行器，支持持久化和缓存预热，今日即可使用，无需基础设施。

#### 开启它的20行

你可以通过在你的 CLAUDE.md 中添加一个 delegation-rules 部分来获取完整的工作流程。我的大致内容是：

```markdown
# Delegation Rules

You are the **coordinator**: design, decide, review, land. Delegate hands-on execution and well-scoped research to **executor subagents** (Agent tool, `model: sonnet`).

## Role check first

- If your prompt starts with `ROLE: EXECUTOR` — or you were spawned by another agent at all — you are an **executor**: ignore the rest of this file, do the work order yourself, **never spawn subagents**. If blocked or the order is ambiguous, report back instead of delegating.
- Coordinator: start every executor prompt with `ROLE: EXECUTOR — do the work yourself; do not spawn subagents.`

## Delegate (default for hands-on work)

- Implementation from a frozen spec; refactors; migrations
- Bug fixes, CI/lint/type failures, tests, dependency bumps, tooling
- Read-heavy exploration — fan out parallel executors, each returns a distilled summary
- Git mechanics (rebase, conflicts, merge workflow) — mechanics only, after the coordinator decides to land

## Keep in the coordinator

- Design, architecture, naming, UX judgment; tasks where writing the spec IS the work
- Tiny edits (~<20 lines) — delegation overhead loses
- Session tools (MCP, secrets), releases/publishes/version bumps
- The land decision, pre-land gates (review clean, CI green, proof), and review of all executor output — never delegated, never skipped

## How

- Complex work: freeze the spec as a md file in `/tasks` first; executor prompts reference it. Small work: full work order inline in the prompt, no spec file.
- Executor prompts are self-contained (context, constraints, expected output) — subagents don't see your conversation.
- Review output before accepting; re-delegate failures with the error context included.
- Heuristic: prompt reads as a work order → delegate; writing it forces decisions → coordinator.
```

它明确说明了三件事：

1. What gets delegated — implementation, refactors, test writing, anything mechanical.
2. What stays with the coordinator — design, planning, architecture decisions, and tiny one-line edits (where delegation costs more than doing it).
3. 道路检查 — 子代理被告知它是子代理，因此它不会递归生成自己的嵌套代理。这一行比看起来更重要。

In practice: I ask it to design and build a to-do app. It asks me clarifying questions, plans, and for anything non-trivial writes a frozen spec into a task folder so there's no ambiguity left for the executor. Then it spawns a Sonnet 5 sub-agent whose prompt is basically "your role is executor, do the work yourself, don't spawn sub-agents, read the spec first, implement."

而且因为这是 Sonnet 5，其实现速度显著快于观看 Fable 5 输入它的过程。

规则文件位于 AI Builder Club 技能仓库中 - 直接复制到你自己的 CLAUDE.md。

#### Tmux 实现跨 harness 的代理团队

This is where the neat story breaks down. In reality, most of us run several agents: Codex, Gemini CLI, Open code, Kimi K3, etc.

Ideally you'd use the best coordinator you have - Claude Code or Codex on the top model - and then be free to pick any harness for the workers.

The Codex team has been quietly good about this. They shipped a Codex plugin for Claude Code that lets you delegate tasks to a Codex agent. Install the plugin, add OpenAI Codex, reload, and now you can say "delegate to a Codex agent to improve the UI of the to-do app at this URL." It gives you a small set of commands: codex rescue (Codex as a sub-agent), codex review (Codex reviews the git diff), codex result (fetch output from a specific session), codex cancel, and codex transfer (fork the conversation history over to the Codex side).

---

Codex 桥很棒。但是如果你想和 Gemini CLI、Groq、Pi 代理、OpenClaw 或者其他任何工具对话呢？

有一个通用的答案，而且它比所有这些都要早：tmux。

tmux 是一个终端多路复用器。它启动持久的终端会话，并且——这是关键部分——它允许你以编程方式读取和操作任何一个会话。

在右侧的新窗格中启动代理：

```text
tmux split-window -h "claude 'build me X'"
```

发送它一条跟进消息（.1 = 屏幕上的第二个窗格）：

```text
tmux send-keys -t .1 "tell me a joke"
tmux send-keys -t .1 Enter
```

读取屏幕上的内容并打印出来

```text
tmux capture-pane -p -t .1
```

That's the whole trick. Once you see it, the idea lands: you can just tell your agent to use tmux to start agent sessions the same way a human would — and through that, drive literally any coding agent as a real teammate.

一个难点是：工人如何告知您工作已完成？

启动会话很简单。通知才是实际的问题。

tmux 提供了一种为此目的的信号原语。窗格可以发送一个命名信号，另一个进程可以阻塞直到该信号触发：

```text
# in the worker's instructions: when finished, run
tmux wait-for -S task-done

# in the orchestrator, this blocks until that fires
tmux wait-for task-done && tmux capture-pane -p -t .1
```

所以你指示子代理：当你完成时，触发这个信号。协调器在后台运行等待命令，当工作完成时，命令返回并将输出传回。这是任意两个代理之间的真实完成回调。

#### 《我之前用 Fable 用错了》精炼总结

文章认为，前沿大模型不应再承担所有编码工作，而应负责**规划、决策和审查**，再把具体实现交给更便宜、更快的小模型。真正高效的配置是：**Fable 5 做协调器，Sonnet 5 等模型做持久化执行器**，借助上下文缓存降低成本。

##### 1. 用完配额不一定是配额太少，而是模型用错了

- Fable 5、GPT-5.6 Sol Max 等前沿模型能力强，但速度慢、成本高。
- 如果让它们直接完成所有编码任务，很容易快速耗尽额度；这并不一定说明额度不足，而可能说明：**本可由便宜模型完成的工作，被昂贵模型包办了。**
- 更合理的分工是：
  - **大模型负责“写什么”**：需求澄清、规划、架构、规范和验收。
  - **小模型负责“怎么写”**：实现、重构、测试、修复等机械性工作。
- 经济上也更划算：**Sonnet 5 的价格约为 Fable 5 的 20%**，但性能已大致相当于几个月前最强的 Opus 4.8，相当于用当下低价购买不久前的顶尖能力。

##### 2. 两种协作模式：顾问模式与编排器模式

Claude Code 文档提出了两种看似相近的配置：

###### 顾问模式

- Sonnet 5 是主代理，负责实际工作。
- 遇到关键问题时，调用 Fable 5 审查计划并提出建议。

###### 编排器模式

- Fable 5 是主代理，负责提问、规划、确定并冻结规范。
- 随后启动 Sonnet 5 等较小模型，完成具体任务。

Devin 的 Fusion 框架同时尝试了这两种方式，并通过按任务类型路由模型，实现了**约低 35% 的成本，同时达到 Fable 5 级或更高性能**。其核心可以概括为：**Fable 5 编排器 + Sonnet 5 执行器。**

##### 3. 编排器更省钱，关键不在智能，而在 Token 计算方式

编排器模式胜出的主要原因是上下文和缓存成本：

- 顾问每次提供有效建议前，都要重新阅读主代理的完整对话历史。
- 这些历史会被反复作为新的输入 Token 计费。
- 执行器只需接收明确的任务说明，不必读取整个主对话。
- 执行器还可以复用已缓存的上下文，**缓存 Token 的成本约为新输入 Token 的 10%**。

因此，顾问模式的隐藏成本是：不断按前沿模型的高价格，让它重复阅读同一段历史；编排器模式则把昂贵模型的使用集中在真正需要决策的环节。

##### 4. 子代理不应是一次性的，而应保持会话

传统子代理通常是临时会话：

1. 主代理启动一个子代理。
2. 子代理读取文件、理解任务并返回结果。
3. 主代理发现问题后再次委派。
4. 系统却启动一个全新的子代理，重新读文件、重新理解上下文并再次消耗 Token。

Devin 的解决方案是把子代理变成**持久化助手**：

- 修改意见继续发给同一个子代理。
- 子代理保留已经获得的项目知识。
- 上下文进入缓存后，后续交互成本很低。

Claude Code 已支持类似机制：

- 使用“代理团队”，而不是一次性子代理。
- 通过 `SendMessage` 向已有会话发送后续任务。
- 队友完成工作后仍保持可恢复状态，直到收到关闭请求。
- 启动团队时，可以为不同代理指定模型。

因此，无需额外基础设施，就能实现：**Fable 5 协调、Sonnet 5 执行、子代理持久化、上下文缓存预热。**

##### 5. 用委派规则明确协调器与执行器的边界

作者建议在 `CLAUDE.md` 中加入约 20 行的 `delegation-rules`，核心包含三部分。

###### 应委派给执行器的工作

- 已有明确规范的功能实现
- 重构、迁移和依赖升级
- Bug 修复
- CI、Lint、类型错误和测试问题
- 工具配置及重复性操作
- 大量阅读和探索任务
- 已决定合并后的 Git 机械操作

###### 应由协调器保留的工作

- 需求澄清、设计和架构
- 命名与用户体验判断
- 编写和冻结任务规范
- 审查执行器的结果
- 确认测试、CI 和验收条件
- 最终是否合并、发布的决定
- 少于约 **20 行**的微小修改，因为委派成本可能高于直接完成

###### 防止子代理递归委派

执行器的提示词要明确写明：

> `ROLE: EXECUTOR — 自己完成工作，不要再生成子代理。`

这可以避免子代理继续创建嵌套代理，造成失控的成本和复杂度。若任务不明确或执行器被阻塞，应直接向协调器反馈，而不是自行再次委派。

##### 6. 实际案例：设计并开发待办事项应用

作者让 Fable 5 设计和构建一个待办事项应用，流程如下：

1. Fable 5 先提出澄清问题。
2. 完成规划和架构判断。
3. 对非简单任务，在 `/tasks` 目录写入一份“冻结规范”。
4. 启动 Sonnet 5 子代理，并要求其阅读规范、直接实现、不要再生成代理。
5. Fable 5 审查执行结果，并根据错误信息把修改任务继续交给同一执行器。

这样既避免了实现歧义，也让 Sonnet 5 以明显更快的速度完成编码，不必等待 Fable 5 慢速生成全部代码。

##### 7. 用 tmux 连接不同平台的编码代理

现实中，开发者往往同时使用 Claude Code、Codex、Gemini CLI、OpenCode、Kimi K3 等工具。理想状态是：

- 用能力最强的模型担任协调器。
- 根据任务自由选择不同工具作为执行器。

Codex 已提供 Claude Code 插件，支持：

- `codex rescue`：让 Codex 充当子代理
- `codex review`：审查 Git diff
- `codex result`：获取指定会话结果
- `codex cancel`：取消任务
- `codex transfer`：把对话历史分叉到 Codex

对于没有专用插件的工具，作者建议使用 **tmux**。它可以创建持久终端，并通过命令操作任意代理会话，例如：

```bash
# 在新窗格中启动代理
tmux split-window -h "claude 'build me X'"

# 发送后续消息
tmux send-keys -t .1 "tell me a joke"
tmux send-keys -t .1 Enter

# 读取代理输出
tmux capture-pane -p -t .1
```

其本质是：让协调器像人一样，通过终端启动、追问和读取其他编码代理，从而把任意 CLI 代理变成可持续沟通的队友。

##### 8. 用 tmux 信号解决“任务完成通知”

启动代理并不难，真正的问题是协调器如何知道执行器已经完成任务。

tmux 提供了等待和触发命名信号的机制：

```bash
# 执行器完成后触发
tmux wait-for -S task-done

# 协调器等待信号，再读取输出
tmux wait-for task-done && tmux capture-pane -p -t .1
```

这样就形成了跨代理的真实完成回调：

1. 协调器启动执行器并等待。
2. 执行器完成后发送 `task-done` 信号。
3. 协调器收到信号后读取结果并继续审查。

作者已将该方案封装为 **Open Agent Teams**：

- 项目地址：&lt;https://github.com/AI-Builder-Club/skills/blob/main/skills/open-agent-teams/SKILL.md>
- 包含技能文件、脚本，以及可复制到 `CLAUDE.md` 或 `AGENTS.md` 的授权和委派规则。

##### 9. Orca 将多代理编排做成可视化产品

tmux 方案灵活，但偏底层。Orca 则把类似能力直接集成到应用界面中：

- 可以点击进入任意子代理会话，并直接继续对话。
- 子代理完成后，会自动把结果反馈给主代理。
- 提供看板视图、Token 使用追踪和移动端体验。
- 支持在 Codex、Claude Code、OpenCode 等代理之间协调。
- 完全开源、免费，作者已将其作为日常多代理协作工具。

##### 核心结论

最有效的 AI 编程方式不是让最强模型亲自写完所有代码，而是让它负责**澄清、规划、决策和验收**，再由便宜、快速且可持久复用上下文的模型执行。进一步结合明确的委派规则、持久子代理、缓存以及 tmux 或 Orca 等跨工具编排方式，可以在保持前沿模型质量的同时，显著降低成本并提升开发速度。

## 口播总结（1）

### 2026-08-03 01:42:38

#### 我之前用 Fable 用错了：让大模型做规划，让小模型做执行

这篇材料的核心观点是：如果你很快用完了 Fable 5 这类顶级模型的额度，问题可能不是配额太小，而是你把昂贵的模型用在了不该做的执行工作上。接下来我们会了解，怎样用大模型负责规划和决策，用更便宜的模型负责具体实现，从而在保持效果的同时，大幅降低成本。

##### 首先，顶级模型更适合决定“做什么”，而不是亲自做完所有事情

核心结论是：前沿模型应该更多扮演规划者和协调者，而不是普通的代码执行员。

通俗地说，Fable 5、GPT-5.6 Sol Max 这样的模型非常强，但它们的运行速度慢，价格也高。如果让它们从头到尾阅读文件、修改代码、运行测试，那么大量额度都会消耗在重复性的操作上。

材料中给出了一个很有代表性的价格对比。Sonnet 5 的价格，大约只有 Fable 5 的百分之二十左右，但性能大致已经达到了几个月前最强模型 Opus 4.8 的水平。

这意味着，使用 Sonnet 5 并不等于明显降级。你只是没有继续用今天最昂贵的模型，去完成几个月前顶尖模型已经能够胜任的工作。

所以，真正合理的组合是：让 Fable 5 负责理解需求、制定方案、做架构判断和最终检查；让 Sonnet 5 负责实现方案、修改文件、补测试和处理各种机械工作。

##### 接下来，两种代理配置听起来相似，但成本差别很大

材料介绍了两种常见方式。

第一种叫“顾问模式”。在这种模式下，Sonnet 5 是主代理，负责主要工作。遇到重要问题时，它再调用 Fable 5，让 Fable 5 检查计划并给出建议。

第二种叫“编排器模式”。这里，Fable 5 是主代理。它负责提问、制定计划、冻结需求规范，然后启动一个或多个较小的模型，让这些模型按照计划执行任务。

核心结论是：编排器模式通常更划算。原因不一定是它更聪明，而是它更节省输入代币。代币可以简单理解为模型处理和计费的文字单位。

在顾问模式中，Fable 5 每次被调用，都可能需要重新阅读主代理完整的对话历史。相当于它反复阅读同一大段材料，而且每次都按昂贵的新输入来计费。

而在编排器模式中，执行代理通常只接收一份明确的任务说明。它不需要读取主代理此前的全部思考过程。更重要的是，如果上下文已经被缓存，后续调用的缓存代币成本大约只有新输入代币成本的十分之一。

Devin 推出的 Devin Fusion，采用的也基本是这种思路。它把不同类型的任务路由给不同模型，宣称用低约百分之三十五的成本，达到 Fable 5 级别甚至更高的表现。把品牌名称去掉以后，它的基本结构就是：用 Fable 5 做编排器，用 Sonnet 5 做执行代理。

##### 更重要的是，子代理不应该每次都重新开始

这是很多编排系统悄悄浪费成本的地方。

传统做法是，主代理生成一个临时子代理。子代理执行任务，返回最终结果，然后结束会话。主代理读完结果后，发现还有问题，于是再次调用任务工具。

问题在于，第二次调用往往会生成一个全新的子代理。这个新代理没有上下文，只能重新读取相同的文件，重新理解项目背景，再重新消耗一遍代币。

材料把更好的做法称为“持久化子代理”，或者说 sidekick，也就是长期存在的协作伙伴。

它不会在第一次回复后立即终止。主代理发现问题时，会向同一个子代理发送后续消息。这样，子代理已经学到的内容都还在，而且相关上下文已经进入缓存，后续沟通的成本就会接近于零。

Claude Code 现在已经具备实现这一点的能力。它提供了 SendMessage 工具，主代理可以向已经存在的代理会话发送消息。一个代理完成任务后，也不会立刻消失，而是可以保持可恢复状态，直到收到关闭请求。启动团队会话时，还可以为不同代理指定不同模型。

因此，今天就可以使用这样的配置：Fable 5 做协调器，Sonnet 5 做执行器，再配合持久化会话和缓存上下文，不需要额外搭建基础设施。

##### 然后，用一套简单规则明确谁负责什么

材料建议把一套 delegation rules，也就是“委派规则”，写进项目的 CLAUDE.md 文件里。这个文件可以理解成给编码代理看的项目工作守则。

核心原则是：协调器负责设计、决策、审查和最终合并；执行代理负责动手实现和范围明确的研究工作。

适合交给执行代理的任务，包括按照已经确定的规范实现功能、重构代码、迁移项目、修复漏洞、处理测试、解决持续集成和代码检查错误、升级依赖，以及进行大量阅读型的代码探索。

而以下工作应该留在协调器手里：产品设计、系统架构、命名、用户体验判断，以及那些本身就需要先写清楚规范的任务。非常小的修改，例如少于二十行的简单编辑，也不值得专门启动代理，因为启动代理的成本可能比直接修改还高。涉及密钥、会话工具、发布和版本升级的操作，也应该由协调器负责。最后的合并决定、上线前检查，以及对执行代理产出的审查，都不能委派出去。

复杂任务最好先把规范写成任务文件，放在项目的任务目录里。执行代理只需要读取这份已经冻结的规范，然后按要求完成。简单任务则可以直接把完整指令写进提示词里。

这里还有一条看似简单、实际上非常重要的规则：执行代理必须明确知道自己是执行代理，并且不能继续创建下一级代理。这样可以避免代理不断递归地生成代理，造成失控和额外开销。

材料中的实际案例是：用户让主代理设计并开发一个待办事项应用。主代理先提问、规划，并在复杂部分把需求写成冻结的任务规范。然后，它启动 Sonnet 5，告诉这个执行代理：你的角色是执行者，先阅读任务规范，自己完成实现，不要再生成其他代理。

由于 Sonnet 5 不需要像 Fable 5 那样一边思考一边慢慢输入，具体实现速度会明显更快。

##### 但是，不同代理工具之间还需要一座桥

前面的方案主要发生在 Claude Code 内部。现实中，很多人会同时使用 Codex、Gemini CLI、OpenCode、Kimi K3 等不同的编码代理工具。

理想状态是，让你最强的工具负责协调，再自由选择其他工具来完成具体工作。

材料提到，Codex 团队已经提供了 Claude Code 的 Codex 插件。安装之后，主代理可以直接把任务交给 Codex 代理，例如让它改进某个待办事项应用的界面。这个插件还提供了几个常用操作：把 Codex 当作子代理调用，让 Codex 检查代码差异，获取某个会话的结果，取消任务，或者把当前对话历史转交给 Codex。

但如果你想调用 Gemini CLI、Groq、Pi 代理、OpenClaw，或者其他没有现成插件的工具，就需要更通用的方法。

这里用到的是 tmux。tmux 是一种终端多路复用器。简单说，它可以启动多个持久存在的终端会话，而且允许程序以编程方式读取和操作这些会话。

主代理可以在右侧新窗格里启动另一个编码代理，再通过命令向它发送后续消息，也可以读取这个窗格当前显示的内容。这样一来，主代理就能像人类一样，启动一个代理、给它布置任务、继续追问，再读取它的工作结果。

它的关键价值在于：不管对方是 Claude、Codex、Gemini，还是其他命令行工具，只要能在终端里运行，就有机会被当成真正的团队成员来调用。

##### 任务完成通知，比启动代理更难

启动一个工作会话并不复杂，真正麻烦的是：执行代理完成后，协调器怎么知道它已经完成？

材料给出的解决方案，是使用 tmux 的信号机制。

可以在执行代理的指令中规定：任务完成后，发送一个名为“task-done”的信号。协调器则在后台等待这个信号。一旦信号触发，等待命令就会返回，协调器再读取执行代理的终端输出，把结果接着传回主流程。

这实际上就是代理之间的完成回调。它让不同工具、不同会话之间，不只是简单地“开一个窗口”，而是能够形成真正的任务交接。

材料作者还把这套 tmux 方法封装成了一个叫 Open Agent Teams 的技能，其中包括技能文件、执行脚本，以及可以放进 CLAUDE.md 或 AGENTS.md 的委派规则。这样，用户可以直接复制这套思路，而不必从零开始搭建。

##### 最后，集成式工具正在把这套方法变得更容易

如果说 tmux 是一种灵活但偏手工的办法，那么 Orca 这类代理开发环境，就把代理编排直接做进了界面。

Orca 提供了开箱即用的编排能力。用户可以点击进入任何一个子代理，在那里继续对话；子代理完成任务后，也会自动向主代理报告。

除此之外，它还提供看板视图、代币使用跟踪和移动端体验。这些功能不需要用户自己拼接脚本，因此比单纯使用 tmux 更直观，也更适合日常使用。材料还提到，Orca 完全开源且免费，并且在过去几周增长很快，作者已经把它作为日常与代理沟通的工具。

作者还参加过一次与 Orca 创始人的深度工作坊，了解他们如何在 Orca 项目本身持续提交数百次代码变更，以及如何在 Codex、Claude Code 和 OpenCode 之间进行协调。

这说明，代理团队并不只是一个节省几美元的技巧。它正在逐渐变成一种实际的软件开发工作方式。

##### 结尾：最值得记住的四件事

第一，顶级模型不一定应该亲自写完所有代码。更合理的分工是，让它负责理解需求、规划方案、做架构决策和最终审查。

第二，较小的模型不代表明显降级。Sonnet 5 的价格大约只有 Fable 5 的百分之二十，但已经接近几个月前顶尖模型的能力。

第三，编排器模式通常比顾问模式更省钱。让小模型直接接收明确任务，可以避免昂贵模型反复读取完整对话历史。

第四，子代理最好保持持久化。重复创建没有上下文的新代理，会反复消耗代币；让同一个代理继续工作，则可以利用已有的缓存上下文，降低后续沟通成本。

最后，如果工具之间没有直接集成，可以用 tmux 连接它们；如果希望获得更完整、更直观的体验，也可以使用集成式的代理团队工具。整体思路只有一句话：大模型负责决定做什么，小模型负责把决定变成代码。

这也修正了一个常见判断：额度很快耗尽，未必代表套餐不够，可能意味着模型分工和信息流设计有问题。文中引用 Devin Fusion“成本降低约 35%”以及不同模型的价格、能力对比，但没有提供完整测试条件，因此具体数字只能视为作者或厂商主张；机制本身却值得独立验证。

###### 真正关键的是持久执行者，而不是更多子代理

很多多代理方案只完成了“拆任务”，没有保留执行者的工作记忆。子代理修完一次问题便退出；返工时再启动新会话，于是它要重新读代码、恢复背景、推导约束。表面上是在并行，实际却反复支付冷启动成本。

文章提出的 persistent sidekick 更重要：让同一个执行会话接收后续反馈，使已读文件、失败原因和实现细节继续留在上下文中，并尽可能命中缓存。这与真实团队类似——让原开发者修复评审意见，通常比临时换一个人重新接手更有效。

不过，持久化并非越久越好。上下文可能积累错误假设，任务之间也可能互相污染。更合理的管理单位不是“永不关闭的代理”，而是**围绕一个稳定目标持续存在、在目标完成后主动销毁的会话**。

###### 编排能力正在成为独立产品层

文中的 tmux 方案证明，跨 Claude Code、Codex、Gemini CLI 等工具协作，并不一定需要模型厂商先统一协议：持久终端、消息注入、完成信号和输出抓取，已经能拼出最小可用的控制面。但 tmux 更像概念验证，真正的产品机会在其上层：任务状态、权限隔离、成本追踪、失败恢复、产物验收和人工接管。

对产品设计更有启发的是那条任务边界：**“写任务说明仍需做判断”就留给强模型；“说明已经足够明确”才交给执行模型。** 这意味着编排效果最终取决于规格能否冻结、验收标准是否明确，而不只是模型路由是否聪明。未来代理开发工具的竞争，也许不会只看谁接入了最多模型，而会看谁能让任务交接更少丢失信息、返工更便宜、结果更容易验证。
