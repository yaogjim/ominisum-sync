##### 一、总结

AirOps 分享的核心是：  
**AI 产品不要只堆复杂工作流，而要转向 Agent 化。**

关键点：

- **模型只是“引擎”**，真正重要的是外层系统：  
  **工具、上下文、记忆、约束、护栏**
- 用 **Markdown 文件** 来编排 Agent，而不是写复杂代码
- 用多个 **Subagent** 分工：
  - 品牌合规
  - 文案生成
  - 品牌资料管理
- 产品优化要持续追踪新的摩擦点：  
  **解决一个问题后，瓶颈会转移**
- 效果：  
  **Token 消耗减少 80%，速度提升 10 倍**

---

##### 二、解读

###### 1. “Harness Engineering” 是重点

可以理解成：

> AI 模型像汽车发动机，但车能不能跑，靠的是整套车身、方向盘、刹车、导航和安全系统。

也就是说，真正的 AI 产品能力，不只是模型强不强，而是：

- 给它什么上下文
- 让它调用什么工具
- 如何限制它别乱来
- 如何让它记住重要信息
- 如何拆分任务，让不同 Agent 专门干不同事

---

###### 2. Markdown 编排 Agent 很有启发

不用一上来就做复杂系统。  
很多时候，**清晰的 Markdown 规则文档**，就能管理：

- 角色设定
- 工作流程
- 品牌规范
- 输出格式
- 注意事项

这比复杂的 RAG、自动记忆、工作流编辑器更直接、更可控。

---

###### 3. Subagent 的意义是“专业分工”

不要让一个 Agent 什么都干。  
比如主 Agent 负责写内容，品牌 Agent 负责检查风格，合规 Agent 负责把关。

这样更像一个小团队，而不是一个万能机器人。

---

##### 三、我的意见

我认为这条信息最有价值的一点是：

> 做 AI 产品，重点不是“接入更强模型”，而是设计更好的使用环境。

当前很多 AI 应用失败，不是模型不够强，而是：

- 上下文混乱
- 记忆不可控
- 工具调用不稳定
- 规则写不清
- 工作流太复杂

所以更务实的路线是：

1. 先用 Markdown 管好规则和上下文  
2. 再拆分 Subagent 做专业分工  
3. 最后持续优化摩擦点和成本  

一句话：

> 未来 AI 产品的竞争力，不在“谁用了最强模型”，而在“谁最会驾驭模型”。

##### 主旨概括

这篇内容总结了 AirOps 在 Claude 大会上的分享：他们从复杂的 workflow builder 转向 agent-based approach，并提出“harness engineering（驾驭工程）”的思路。核心观点是：AI 模型只是“引擎”，真正决定产品效果的是围绕模型的工具、上下文、记忆、约束和质量控制体系。

---

##### 1. AirOps 的转型：从工作流构建器到 Agent 方法

AirOps 原本使用较复杂的 workflow builder，但后来转向更灵活的 agent-based approach。

关键变化包括：

- 不再主要依赖复杂代码或流程图来编排 AI 工作流。
- 改用 **markdown 文件来组织和编排 agent**。
- 让 agent 更像一个可被配置、可协作的系统，而不是一条固定流程。

通俗理解：  
过去像是在搭一条固定流水线；现在更像是组织一个 AI 团队，每个成员有自己的职责和规则。

---

##### 2. “Harness Engineering”：模型只是引擎，周边系统才是关键

文章中最重要的比喻是 **harness engineering**。

它把 AI 模型比作赛车的“引擎”，但光有引擎并不能直接上路。真正让 AI 产品稳定运行的，是围绕模型的一整套系统：

- **Tools：工具**
- **Context：上下文**
- **Guardrails：安全和质量边界**
- **Memory：记忆**
- **Constraints：约束条件**

也就是说，AI 产品的竞争力不只是选了哪个大模型，而是如何设计模型周围的“驾驭系统”。

---

##### 3. 用 Subagents 提升输出质量

AirOps 通过拆分多个 subagents 来保证最终内容质量。

文中提到的例子包括：

- **Brand compliance subagent**：检查内容是否符合品牌规范。
- **Writer subagent**：负责具体写作。
- **Brand kit subagent**：专门管理品牌资料和品牌语气。

其中一个关键细节是：  
AirOps 没有每次都把大量品牌文档塞进主 agent，而是把 **Brand Kit 单独拆成 subagent**。这样可以让主 agent 更轻量，也能减少混乱和 token 消耗。

---

##### 4. 持续追踪摩擦点：解决一个问题后，问题会转移

作者提到一个很重要的产品思路：  
**每次解决一个问题后，friction point（摩擦点）会移动。**

也就是说，AI 产品优化不是一次性完成的。你解决了速度问题，可能接下来会暴露质量问题；你解决了质量问题，可能又会出现成本问题。

因此团队需要持续追踪新的瓶颈，不断优化系统。

---

##### 5. 结果数据：效率提升非常明显

AirOps 的方法带来了很直接的效果：

- **Token 消耗减少 80%**
- **速度提升 10 倍**

这说明合理的 agent 架构和上下文管理，不只是理论上更优，也能明显降低成本、提升性能。

## 综合-启发一下（1）

### 2026-06-02 07:59:41

#### AirOps 从 Workflow Builder 转向 Agent-Based：精炼解读

##### 一句话总结

AirOps 的核心启发不是“用 Agent 替代工作流”，而是：**AI 产品的竞争力正在从模型调用，转向围绕模型构建一整套可控、可维护、可迭代的 Harness Engineering 系统。**

> 模型是引擎，真正让产品跑起来的是：上下文、工具、记忆、约束、子任务分工、质量控制与持续优化机制。

---

##### 1. 启发

###### 1.1 从「流程编排」转向「能力编排」

传统 workflow builder 的思路是：

> 先定义步骤，再让 AI 执行每一步。

Agent-based approach 的思路更接近：

> 先定义目标、角色、上下文和边界，再让不同 Agent 协作完成任务。

这意味着 AI 产品的设计重心发生了变化：

| 旧范式 | 新范式 |
|---|---|
| Workflow / SOP / 流程图 | Agent / Subagent / 角色协作 |
| 代码化逻辑 | Markdown / Prompt / Context 文件 |
| 固定步骤 | 动态决策 |
| 单一模型输出 | 多 Agent 校验、补全、约束 |
| 工具是附属品 | 工具、上下文、约束成为核心产品能力 |

真正重要的不是“有没有 Agent”，而是：**Agent 周围的系统是否足够稳定、可控、可迭代。**

---

###### 1.2 Harness Engineering 是 AI 产品的新抽象

AirOps 提到的 “Harness Engineering” 很值得重视。

可以理解为：

> 不要只关注模型本身，而要设计一套能驾驭模型的工程系统。

这个系统包括：

- Tools：模型可以调用哪些工具？
- Context：模型知道哪些背景？
- Memory：哪些信息需要长期保留？
- Guardrails：什么事情绝不能做错？
- Subagents：不同能力如何分工？
- Evaluation：如何判断输出好坏？
- Feedback Loop：如何持续改进？

在这个框架下，AI 产品经理或开发者真正要问的不是：

> “用哪个模型？”

而是：

> “我如何让模型在一个具体业务场景里稳定产生高质量结果？”

---

###### 1.3 Markdown 可能成为 Agent 系统的低代码配置层

AirOps 用 Markdown 文件编排 Agent，而不是写复杂代码，这个细节很有价值。

这代表一种趋势：

> AI 应用的部分“业务逻辑”会从代码迁移到文本配置、知识文件、角色说明和上下文文档中。

Markdown 的优势在于：

- 易读
- 易改
- 非工程人员也能参与
- 适合存储上下文、规则、品牌规范、任务说明
- 版本管理方便
- 比复杂 workflow UI 更灵活

这也解释了为什么有用户反馈：

> 手工用 Markdown 管理记忆，反而比 RAG、自动记忆更好用。

因为很多场景里，问题不是“知识检索不到”，而是：

- 哪些信息重要？
- 哪些信息过期？
- 哪些规则优先级更高？
- 哪些上下文应该被显式提供？
- 哪些记忆不该被自动写入？

手工 curated context 在早期产品里，往往比全自动 memory 更可靠。

---

##### 2. 高价值信息深挖

###### 2.1 “Token 减少 80%，速度提升 10 倍”背后可能不是模型变强，而是系统变聪明

这个结果很关键。

很多人优化 AI 产品时，第一反应是：

- 换更强模型
- 加更长上下文
- 接更多 RAG
- 上更多 Agent

但 AirOps 的案例说明，真正的优化可能来自：

- 减少无效上下文
- 拆分任务
- 独立处理品牌约束
- 把重复判断交给 Subagent
- 让主 Agent 不再背负所有职责
- 使用结构化文件替代冗长 prompt
- 将固定知识模块化复用

这背后的产品原则是：

> 不要让一个大模型在一个巨大的上下文里完成所有事情，而是让多个更小、更明确的上下文系统协同工作。

---

###### 2.2 Subagent 的本质不是“多个 Agent 更高级”，而是职责隔离

AirOps 提到的几个 Subagent：

- Brand Compliance
- Writer
- Brand Kit

这个拆法非常重要。

它不是为了炫技，而是在做软件工程里很经典的事情：

> 单一职责原则。

如果把所有职责塞给一个主 Agent，会出现几个问题：

- Prompt 越来越长
- 规则互相冲突
- 输出不稳定
- 品牌规范容易遗漏
- 质量检查和内容生成混在一起
- 修改一处规则影响整个系统

拆成 Subagents 后，可以形成更清晰的架构：

```text
主 Agent：理解任务与调度
Writer Agent：生成内容
Brand Kit Agent：提供品牌规范与上下文
Brand Compliance Agent：检查是否符合品牌要求
```

这类似传统软件里的：

- Controller
- Service
- Validator
- Config
- Policy Engine

所以 Agent 系统不是抛弃工程思想，而是把工程思想迁移到了 AI-native 架构中。

---

###### 2.3 “Friction point 会移动”是做 AI 产品的核心规律

AirOps 提到：

> 每次解决问题后，friction point 会移动，要持续 chase friction。

这句话非常重要。

AI 产品开发中，瓶颈往往不是一次性解决的，而是不断迁移：

```text
一开始：模型不会做
然后：模型能做但不稳定
然后：输出质量不一致
然后：上下文太长、成本太高
然后：速度慢
然后：用户不信任
然后：团队难维护
然后：规模化交付困难
```

所以 AI 产品不是“搭好一个 workflow 就结束”，而是一个持续追踪摩擦点的过程。

真正有竞争力的团队，会不断问：

- 用户当前最卡在哪里？
- 是输入太复杂？
- 是输出不可用？
- 是审核成本太高？
- 是模型幻觉？
- 是上下文缺失？
- 是品牌/合规风险？
- 是成本太高？
- 是等待时间太长？
- 是无法规模化复用？

AI 产品的迭代重点，不是盲目加功能，而是持续消除当前最大的 friction。

##### 3. 可迁移清单

下面是可以迁移到自己 AI 产品或商业系统中的实践清单。

###### 3.1 Agent 系统设计清单

在设计一个 Agent 系统时，不要只写一个大 prompt，可以拆成以下模块：

```text
目标：这个 Agent 最终要完成什么？
角色：它应该以什么身份工作？
输入：它需要哪些信息？
工具：它可以调用哪些外部能力？
上下文：它必须知道哪些业务背景？
约束：它不能违反哪些规则？
输出：它应该以什么格式交付？
检查：如何判断输出是否合格？
回退：失败时如何处理？
记忆：哪些信息要保存，哪些不要？
```

---

###### 3.2 Harness Engineering 清单

围绕模型构建 Harness，可以从这几个层面入手：

| 模块 | 关键问题 |
|---|---|
| Model | 用哪个模型？是否需要多个模型？ |
| Context | 哪些上下文必须显式提供？ |
| Tools | Agent 需要调用哪些工具？ |
| Memory | 哪些信息应该长期保留？ |
| Guardrails | 哪些风险必须被约束？ |
| Subagents | 哪些职责应该拆开？ |
| Evaluation | 如何自动/半自动评估质量？ |
| Observability | 如何追踪失败原因？ |
| Cost Control | 如何减少 token 和调用次数？ |
| Latency | 如何缩短响应时间？ |

###### 3.4 Subagent 拆分清单

判断是否需要拆 Subagent，可以问：

- 这个任务是否包含多个明显不同的职责？
- 生成和审核是否混在一起？
- 是否有一类规则经常被遗漏？
- 是否有某些上下文每次都很长，但不一定都需要？
- 是否有某个环节需要独立优化？
- 是否有些任务可以并行？
- 是否有些判断应该由更便宜/更快的模型处理？

常见拆分方式：

| Subagent 类型 | 适用场景 |
|---|---|
| Research Agent | 搜集资料、提炼事实 |
| Writer Agent | 内容生成 |
| Editor Agent | 润色和结构优化 |
| Compliance Agent | 法务、品牌、政策审核 |
| Brand Agent | 品牌语气、用词、视觉规范 |
| Data Agent | 查询数据库、分析指标 |
| Planner Agent | 拆解任务、制定执行路径 |
| Critic Agent | 反向挑错、质量评估 |

##### 4. 反方与张力

###### 4.1 Agent-based 不一定总比 Workflow 好

虽然 AirOps 从复杂 workflow builder 转向 Agent-based approach，但这不意味着 workflow 已经过时。

在以下场景中，传统 workflow 可能更合适：

- 流程稳定
- 输入输出明确
- 合规要求强
- 每一步必须可审计
- 错误成本高
- 不需要模型自主判断
- 用户更希望可控而非灵活

例如：

- 财务审批
- 医疗流程
- 法律合同审核
- 大型企业内部合规
- 金融风控流程

这些场景中，“可预测性”比“智能灵活性”更重要。

更现实的方向可能是：

> Workflow 负责确定性骨架，Agent 负责不确定性任务。

---

###### 4.2 Markdown 编排虽灵活，但也可能变成新的混乱源

Markdown 的好处是低门槛，但风险也明显：

- 文件越来越多
- 版本冲突
- 上下文重复
- 规则互相矛盾
- 难以权限管理
- 缺少结构化验证
- 非工程人员随意修改导致系统漂移

所以 Markdown 适合早期探索和中小规模系统，但到一定复杂度后，需要引入：

- schema
- lint
- version control
- approval workflow
- test cases
- evaluation benchmark
- change log

否则，Markdown 也会从“简单配置层”变成“文本债务”。

---

###### 4.3 Subagent 会提升质量，也可能增加系统复杂度

多个 Subagent 的风险包括：

- 调用链变长
- 延迟增加
- 成本增加
- 调试困难
- 错误传播
- Agent 之间互相误解
- 输出格式不一致
- 难以定位失败源头

因此，Subagent 不是越多越好。

一个实用原则是：

> 只有当某个职责足够独立、重复出现、且明显影响质量时，才值得拆成 Subagent。

---

###### 4.4 自动记忆 vs 手工记忆：并不是技术先进就一定更好

热门回复中提到：

> 手工管理记忆，分话题用 Markdown 保存，比 RAG+向量数据库和自动记忆效果更好。

这个观点很有现实意义。

RAG 和自动记忆的问题在于：

- 检索不一定精准
- 重要信息不一定被召回
- 垃圾信息可能被召回
- 过期信息难处理
- 模型不知道信息优先级
- 用户难以理解为什么用了某条记忆

手工记忆的问题是：

- 维护成本高
- 依赖人的纪律
- 不适合海量数据
- 难以实时更新

所以更好的方案可能是混合式：

```text
高价值、长期、稳定规则：手工 Markdown 管理
大量、动态、事实资料：RAG 管理
用户偏好和行为信号：半自动记忆
过期和冲突信息：需要显式治理机制
```

##### 5. 情境化落地

###### 5.1 如果你在做内容生成产品

可以这样落地：

```text
主 Agent：理解用户需求，规划内容结构
Research Agent：收集事实、竞品、行业信息
Writer Agent：生成初稿
Brand Kit Agent：提供品牌语气、禁用词、目标人群
Compliance Agent：检查敏感表达、夸大承诺、品牌一致性
Editor Agent：优化表达、标题、CTA
```

关键不是让模型“多写几版”，而是把内容生产中的不同质量环节拆出来。

可优化指标：

- 首版可用率
- 人工修改时间
- 品牌一致性得分
- 事实错误率
- 生成成本
- 平均响应时间

---

###### 5.2 如果你在做企业内部 AI 助手

不要一开始就上复杂自动记忆和全量 RAG。

可以先做：

```text
/company_context
  公司介绍.md
  产品线.md
  组织结构.md
  常见术语.md

/policies
  报销制度.md
  销售话术规范.md
  客户隐私规则.md

/agents
  hr_assistant.md
  sales_assistant.md
  support_assistant.md
  compliance_checker.md
```

先用显式 Markdown 建立高质量上下文，再逐步引入 RAG。

优先解决：

- 员工不知道问什么
- AI 回答不符合公司语境
- 制度信息过期
- 不同部门说法不一致
- 无法追踪答案依据

---

###### 5.3 如果你在做 AI SaaS 产品

可以把 Harness Engineering 当成产品护城河。

不要只卖“接入大模型”，而要卖：

- 行业上下文
- 工作流经验
- 默认规则
- 专业模板
- 评估体系
- 审核机制
- 可靠工具链
- 可配置 Agent
- 成本和速度优化

也就是说，用户真正买的不是模型能力，而是：

> “这个系统是否懂我的业务，并且能稳定帮我完成任务。”

---

###### 5.4 如果你是个人开发者或小团队

最小可行落地方式：

1. 不要急着做复杂 Agent 平台。
2. 先选一个高频痛点场景。
3. 用 Markdown 写清楚：
   - 角色
   - 任务
   - 上下文
   - 输出格式
   - 禁止事项
   - 好坏案例
4. 先用一个主 Agent 跑通。
5. 记录每次失败原因。
6. 把反复出现的问题拆成独立模块。
7. 当某类检查经常失败时，再拆 Subagent。
8. 统计 token、耗时、人工修改量。
9. 持续 chase friction。

一个简单版本：

```text
第 1 周：单 Agent + Markdown prompt
第 2 周：加入品牌/规则文件
第 3 周：加入审核 Agent
第 4 周：加入评估指标和失败日志
第 5 周：优化 token 和响应速度
```

---

##### 6. 最值得带走的结论

1. **AI 产品的核心不是模型，而是模型周围的 Harness。**
2. **Agent-based 的价值在于职责分离，而不是简单增加 Agent 数量。**
3. **Markdown 正在成为一种轻量级 AI 系统配置语言。**
4. **手工 curated context 在很多场景下比盲目 RAG 更可靠。**
5. **Workflow 没有消失，它会和 Agent 形成混合架构。**
6. **AI 产品迭代的关键是持续追踪 friction point。**
7. **真正的护城河来自业务上下文、质量控制、工具链和反馈循环。**

最终可以把这套思路浓缩成一句话：

> 不要只做一个会调用模型的产品，而要做一个能持续驾驭模型、约束模型、增强模型并让模型稳定产出业务价值的系统。
