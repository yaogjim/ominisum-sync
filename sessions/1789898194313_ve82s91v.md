## 分析要点

- **核心高价值点**：将生成、决策与执行拆开：生成模型负责研究和写作，Jev负责有限选项中的路由与评分，代码负责执行和结果核验。
- **留存建议**：建议精读并存档，重点保留决策层拆分方法、路由器示例与安全边界设计（包含可复用的Agent决策层架构、十步搭建流程、代码示例、异常处理和多个部署场景，对Agent开发与成本优化有直接参考价值。）

**知识要点**

- 适合交给专用决策模型的是高频、结构化且选项预定义的路由、评分、审批和升级任务，精确停止条件仍应由代码控制。
- Agent每次状态变化后都应重新生成当前可用动作集合，避免决策模型从已经失效的菜单中选择。
- 模型置信度不能证明操作已经完成，完成状态应通过独立检查、持久化进度、幂等处理及审批边界验证。

**行动项**

- 选择现有Agent中的一个重复决策点，使用Choice、Score或Noul建立最小路由实验。
- 按任务记录决策成本、总成本、延迟、错误分支率和人工复核率，并用标注样本校准置信度阈值。
- 为路由流程加入操作次数与支出上限、进度保存、重复处理防护、完成检查和发布前人工审批。

#### 01\. 找到你的代理中 Jev 可以接管的那个部分

Jev 是 TypeSafe AI 的 System One 模型 ：你提供信息和预定义问题，它返回带有概率的类型化答案。它无法撰写你的简报、生成代码，或用散文解释其推理过程。

[TypeSafe 的发布文章](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

从一个这样的任务开始：

> 研究三款新的 AI 代理工具，并起草明天的简报。保存草稿供我审阅。

这个任务包含若干决策：我们是否有足够的来源？下一个执行者是谁？草稿是否已准备好供审阅？

这些就是 Jev 的候选事项。获取来源、撰写段落和保存文件仍然属于你的工具和生成模型。一条精确的规则，例如执行十次操作后停止，则应属于代码。

对于 GrokBot 风格的首席参谋，保存的交接内容可以供给现有的工作器使用。连接该工作器要在下面的独立设置之后进行；你无需代理团队即可完成首次运行。

#### 04\. 将请求转化为已保存的交接

chief.py

chief.py在 jev-starter 内、.venv 外创建

。使用纯文本编辑器，并保存为确切的文件名，而不是

.txt。

```text
import json
import os
from getpass import getpass
from pathlib import Path
from uuid import uuid4
from typesafe_sdk import Choice, TypeSafeAPIError, TypeSafeClient

if not os.environ.get("TYPESAFE_API_KEY"):
    os.environ["TYPESAFE_API_KEY"] = getpass("TypeSafe API key: ").strip()

goal = input("Goal: ").strip()
if not goal:
    raise SystemExit("Enter a goal.")
notes = input("Completed work: ").strip() or "Nothing yet."
state = {"goal": goal, "completed_work": notes}

try:
    with TypeSafeClient(model="jev-1.13.0") as client:
        result = client.system_one(
            state=state,
            questions={
                "next_worker": Choice(
                    instructions="Choose the next step for a research briefing.",
                    criteria={
                        "research": "Collect evidence still needed for the goal.",
                        "write": "Draft the briefing from sufficient evidence.",
                        "review": "Goal unclear, outside scope, or work complete.",
                    },
                )
            },
        )
except TypeSafeAPIError as error:
    raise SystemExit(f"API error {error.status}; see Step 8.")

answer = result.choices["next_worker"]
destination = "review"
if answer.choice in {"research", "write"} and answer.confidence >= 0.85:
    destination = answer.choice

folder = Path(__file__).resolve().parent / "queue" / destination
folder.mkdir(parents=True, exist_ok=True)
job = folder / f"{uuid4().hex}.json"
payload = dict(state, choice=answer.choice, confidence=answer.confidence,
               destination=destination, status="queued")
job.write_text(json.dumps(payload, indent=2, ensure_ascii=False), encoding="utf-8")
print("Saved handoff:", job)
```

在 macOS/Linux 上运行：

```text
.venv/bin/python chief.py
```

在 Windows 上运行：

```text
.\.venv\Scripts\python.exe chief.py
```

在提示时粘贴你的 API 密钥——终端会将其隐藏。 对于目标 ，请输入为明天的简报比较三个 AI 代理工具 。对于已完成的工作，请输入尚未收集任何来源。

你的结果： 一个已保存的交接 ：包含完整文件路径的消息。打开该 JSON 文件：其中包含你的请求、进度、Jev 的选择、置信度和目标位置。 每次运行都会在 queue/research、queue/write 或 queue/review 下创建一个新文件。这些是本地任务队列；已保存的任务会等待工作进程来消费它

API 调用和错误处理遵循

[SDK 使用指南](https://docs.typesafe.ai/sdk/python/usage)。我将初始审核阈值设为 0.85 - 请使用你工作流中的标注示例进行调整。置信度并非准确率百分比。

#### 05\. 提出有导向性的问题

三种答案类型对应不同的用途：

Jev gives you three question types, each built for a different kind of decision:

- Choice 从列表中选择一个选项。用于类似这样的问题：“接下来应该由谁工作？”它会返回所选选项、其概率分布以及置信度。
- Score 根据你定义的量表评估某事物。用于类似这样的问题：“这个来源的相关性有多高？”它会返回该量表上的一个值，以及概率和置信度。
- Noul 回答一个是或否的问题。用于类似这样的问题：“这个请求需要发布吗？”它会返回从 0 到 1 的“是”的概率。

定义一个相关性评分，包含三种描述：不相关、部分相关、直接回答问题。其数值结果范围为 0 到 2，包括小数。Noul 接近 0.5 表示对是/否不确定。

[评分](https://docs.typesafe.ai/primitives/score) ·

[Noul](https://docs.typesafe.ai/primitives/noul)

![Image](https://pbs.twimg.com/media/HSgs9sCXYAEaXNH?format=jpg&name=large)

一个有用的细节：Jev 看不到你的问题 ID。 将字段命名为 safe\_to\_publish 不会贡献任何指令。将实际需求放在问题中，并清晰地描述每个选项。

[选项文档](https://docs.typesafe.ai/primitives/choice)

同时提供证据。“研究员完成了”告诉 Jev 的信息比来源、发现和剩余缺口要少。将这些字段与原始请求分开保存。

[状态文档](https://docs.typesafe.ai/concepts/state)

![Image](https://pbs.twimg.com/media/HSgtBJgWgAEGBgE?format=jpg&name=large)

#### 07\. Stop paying for questions to wait on each other

Your dispatcher may need a worker, an urgency score, and an approval check. If all three can inspect the same state, send them together.

TypeSafe 支持并行问题和推测分支：询问可能的后续操作，然后仅使用与所选分支相关的答案。 问题之间无法读取彼此的答案。如果某个决策需要最新的搜索结果，请先执行搜索。

[并行评估模式](https://docs.typesafe.ai/patterns/fan-out)

浏览器示例暴露了另一个瓶颈。其优化后的运行时将浏览器协议调用的中位数从 1,092 次降至 101 次 ，同时任务时间中位数在三组匹配对比中下降了 25%。两个版本使用了相同的模型。

这些更改包括在一次读取中收集页面状态，并避免为不相关的动画进行新的预测。在花钱使用更快的模型之前，先检查重复的工具调用。

#### 08\. Give overnight work somewhere to stop

For a morning briefing, I'd allow source collection and draft creation, then stop at review. Publishing should require a separate permission check.

The application also needs an action limit, a spending limit, and saved progress. After an interruption, it should inspect the last completed action before repeating anything. A confident answer cannot prove that a file was saved or a message was sent.

Browser Use 在 Jev 选择 DONE 后独立检查结果。将这种分离机制借鉴到你自己的完成检查中。

[Agent loop](https://github.com/browser-use/jev-ultrafast/blob/main/jev_ultrafast/agent.py)

![Image](https://pbs.twimg.com/media/HSgtVN2XgAEydLO?format=jpg&name=large)

Once the local router works, use this brief to connect your existing agents:

> 阅读 TypeSafe 技能并检查我的 worker 接口。将
>
> chief.py 的 JSON 队列连接到现有的研究和写作处理器。防止重复处理。每次操作后保存进度。添加调用和支出限制、不确定时审查，以及草稿存在的完成检查。将发布保持在审批之后。明确识别缺失的连接器。

If the starter fails, use the error to choose the fix:

- Python 命令缺失： 完成 Python 安装并重新打开终端。
- 模块缺失： 使用相同的 .venv 解释器重复 SDK 安装。
- 401： 替换 API 密钥并重新运行。
- 422： 对照粘贴的代码检查命名的请求字段。
- 429 / 529： 允许退避；如果速率限制或过载持续存在，稍后重试。

SDK 提供重试；如果 API 错误仍然存在，脚本会停止。

## 结构化（1）

### 2026-09-20 09:55:44

#### Jev 智能体决策层：从本地路由器到实际应用的 10 步指南

文章的核心观点是：**不要让昂贵的大模型处理智能体中的每一次选择、评分和判断。**生成模型负责研究、规划和写作，Jev 负责快速路由、评分、审批或升级，代码负责执行，从而提高速度并降低成本。

##### 1. 先找出适合交给 Jev 的决策

Jev 是 TypeSafe AI 的 **System One 决策模型**：它读取当前状态，回答预先定义的问题，并返回结构化结果、概率与置信度。

它不适合写报告、生成代码或用长文解释推理，而适合处理反复出现的小判断，例如：

- 资料是否足够？
- 下一步交给研究员、写作者还是审核者？
- 来源相关性有多高？
- 草稿是否可以进入审核？

获取资料、撰写内容和保存文件仍应由工具或生成式大模型完成；“执行十次后停止”这类明确规则，则应直接写进代码。

##### 2. 先在 Playground 验证单个决策

可以先输入一个简单任务状态，例如：

- 目标：比较三款 AI 智能体工具，形成晨间简报。
- 当前进度：尚未收集资料。
- 可用角色：研究员、写作者。
- 限制：只能保存草稿，不得发布。

然后让 Jev 从“研究、写作、审核”中选择下一步。再把状态换成真实研究笔记，观察决定是否改变。

这一阶段的目的不是搭建完整智能体，而是验证：**状态信息和选项定义能否让 Jev做出合理路由。**

##### 3. 接入 API，建立最小运行环境

文章建议使用 Python 3.12 及以上版本：

1. 创建独立虚拟环境。
2. 安装官方 `typesafe-sdk`。
3. 从 TypeSafe 账户获取 API 密钥，并将密钥放在源代码之外。
4. 如使用编码代理，也可安装 TypeSafe 官方技能作为集成说明；Jev 本身仍通过 API 调用。

如果要运行 Browser Use 示例，还需要 TypeSafe 和 OpenRouter 两类密钥。

##### 4. 把判断结果保存为任务交接

示例脚本 `chief.py` 接收两个输入：

- 当前目标；
- 已完成的工作。

它调用 Jev，让其从 `research`、`write`、`review` 中选择下一站，并将结果保存为 JSON 文件，其中包括：

- 原始目标和进度；
- Jev 的选择；
- 置信度；
- 实际目标队列；
- 当前任务状态。

文件会进入 `queue/research`、`queue/write` 或 `queue/review`，形成最简单的本地任务队列，供后续工作进程消费。

示例中，只有当 Jev 选择“研究”或“写作”且置信度不低于 `0.85` 时，任务才会自动转交；否则进入人工审核。作者提醒：**置信度并不等于准确率百分比**，实际阈值应使用自己工作流中的标注样本校准。

##### 5. 根据决策类型设计问题

Jev 提供三类结构化问题：

- **Choice**：从预设选项中选择，如“下一步由谁处理？”
- **Score**：按自定义量表评分，如“该来源与问题的相关性有多高？”
- **Noul**：回答是或否，返回“是”的概率；接近 `0.5` 表示不确定。

设计问题时要注意两点：

1. **字段名本身不是提示词。**把字段叫作 `safe_to_publish`，不会自动告诉 Jev 安全发布的标准，必须在问题和选项说明中写清要求。
2. **状态要包含证据。**“研究员已完成”信息不足，最好提供来源、具体发现和剩余缺口，并与原始请求分开保存。

##### 6. 每次状态变化后重建“可选菜单”

Browser Use 的关键做法是：每次点击后重新读取页面，生成当前可操作控件列表，再让 Jev 从最新列表中选择。需要填写文本时，则由小型语言模型生成输入内容。

同样的原则也应应用到其他智能体：

- 只列出当前真实存在且可用的工作者；
- 选择研究材料时加入当前来源 ID；
- 工具改变状态后立即刷新选项。

否则，决策模型可能是在从“昨天的菜单”中选择，导致操作对象已不存在或状态已经过期。

##### 7. 并行决策，并减少重复工具调用

如果“选择工作者、判断紧急程度、检查是否需要审批”都依赖同一份状态，可以一次并行提交，而不是逐个等待。

但并行问题之间不能读取彼此的答案。如果某项判断依赖最新搜索结果，就必须先完成搜索，再发起判断。

文章还强调，系统瓶颈不一定来自模型本身。Browser Use 的优化版本通过一次性读取页面状态、忽略无关动画等方式，将浏览器协议调用中位数从 **1,092 次降至 101 次**；在三组配对比较中，任务时间中位数下降 **25%**，且前后使用的是同一模型。因此，在购买更快模型之前，应先检查是否存在重复工具调用。

##### 8. 为自动运行设置停止条件和安全边界

对于自动生成晨间简报，作者建议：

- 可自动完成资料收集和草稿生成；
- 到“审核”阶段停止；
- 发布必须经过独立的权限检查。

系统还应具备：

- 操作次数上限；
- 支出上限；
- 每步保存进度；
- 防止重复消费同一任务；
- 中断后检查最后完成的动作；
- 不确定时转人工审核；
- 独立验证文件是否真的保存、消息是否真的发送。

原因是：**Jev 高置信度地判断“任务完成”，并不能证明外部操作确实成功。**Browser Use 也会在 Jev 选择 `DONE` 后单独检查结果，决策与完成验证不应混为一谈。

常见故障可按错误处理：

- Python 命令不存在：完成安装后重启终端；
- 模块缺失：用同一个虚拟环境重新安装 SDK；
- `401`：检查或更换 API 密钥；
- `422`：核对请求字段和代码；
- `429/529`：退避并稍后重试。

##### 9. 正确理解速度和成本数据

Browser Use 与 Jev 的航班示例声称：

- 找到航班约用 **7 秒**；
- Jev 相关费用约 **0.0039 美元**；
- 记录了约 **90,558 个 Jev 输入 token**。

但这些数据有明确边界：

- 费用不包含浏览器本身的成本；
- 计时从初始页面观察之后开始；
- 不包括运行后的全新核验；
- 示例只找到航班结果，并未预订机票。

Vercel 的 fx 团队还报告，Jev 在安全分类任务中比 GPT-5.6-luna 快约 **5—18 倍**，并称准确率有所提升。但这只是分类器对比，不代表整个智能体也能获得相同比例的加速。

作者因此建议按“完成一个任务的总成本”衡量，而不是只看单次判断价格。一个廉价但错误的路由，可能让后续工作者走错分支，造成更高总成本。

##### 10. 四类已有应用

###### 浏览器控制

Browser Use 使用 Jev 选择下一步动作和正确页面元素，演示中约 7 秒找到航班，Jev 成本约 0.0039 美元。浏览器负责执行，Jev 只负责在当前动作空间中做选择。

###### 研究论文分类

案例中，Jev 对 **1,018 篇 AI 论文**进行分类：

- 分类总成本：**0.08 美元**；
- 每篇端到端延迟中位数：**256 毫秒**；
- 论文摘要另由 DeepSeek V4 Flash 完成，成本为 **3.99 美元**。

这体现了“不同环节使用不同模型”：生成模型负责摘要，Jev 根据标题、摘要和 24 个候选主题完成分类。案例发布者同时说明，在正式替换原有分类方案前仍需继续评估结果。

###### 邮件分流

另一案例中，Jev 在数秒内分类 **500 封邮件**，成本约 **0.035 美元**。可将“回复、研究、等待、审核”定义为选项，再把结果连接到相应文件夹或邮件代理。

###### 模型路由与上下文压缩

LangChain 使用 Jev 根据任务复杂度，在便宜模型和能力更强的推理模型之间路由。

类似方法还可用于上下文压缩：为每次工具调用评分，丢弃无关内容，而不是让大模型重新生成摘要。文中引用的案例称，其 Claude 会话上下文从接近 **100 万 token** 压缩到约 **8.6 万 token**；这是案例报告，而非文章提供的普遍性能保证。

##### 核心结论：把“生成、决策、执行”拆开

文章主张将智能体划分为三层：

1. **生成式大模型**：研究、规划、写作；
2. **Jev**：路由、评分、审批、升级；
3. **代码和工具**：执行动作、保存结果、验证完成。

真正的价值不只是某个低成本演示，而是识别出：许多昂贵的大模型调用其实并不需要生成文本，只需要在已知选项中做判断。实践时应从一个高频、重复、边界明确的决策开始，测量准确性、延迟和单个已完成任务的总成本，再逐步替换下一个决策环节。

## 口播总结（1）

### 2026-09-21 00:13:02

搭建人工智能代理时，真正昂贵的，往往不只是写作和推理，而是夹在工作流程里的大量小判断。比如，下一步该搜索资料，还是开始写作？结果是否足够可靠？任务应该交给便宜模型，还是更强的推理模型？原文的核心判断是：不要让大型语言模型处理每一次选择。让生成模型负责研究、规划和写作，让 Jev 负责路由、评分、批准或升级，再让普通代码执行决定。

Jev 不是聊天机器人。它是 TypeSafe AI 推出的一种快速决策模型。你向它提供当前状态、一个明确问题，以及预先定义好的选项。它返回结构化答案、概率分布和置信度。Jev 不负责撰写简报，也不负责生成代码，更不会用长篇文字解释推理。它只做一件事：根据当前信息，从你允许的选项中作出判断。

可以用一份晨间简报来理解这种分工。任务是比较三款人工智能代理工具，并把草稿保存下来供人审阅，不能直接发布。

这个任务看似简单，内部却有很多分叉。资料够不够？下一步该交给研究员，还是写作者？草稿是否已经可以审阅？这些小判断适合交给 Jev。至于搜索资料、撰写段落和保存文件，仍然由工具、生成模型和代码完成。如果规则非常确定，比如最多执行十次操作，那么直接写进代码，不必调用模型。

实际使用时，可以先在 Jev 的测试界面中输入任务状态。比如，目标是比较三款工具；目前还没有收集任何来源；可用工作节点是研究员和写作者；草稿只能保存，不能发布。然后问：“接下来应该由哪个工作节点执行？”可选答案包括研究、写作和审查。

在没有资料时，Jev 应该把任务交给研究员。等状态更新为“已有充分证据”后，它可能改为选择写作。如果目标含糊，或者工作已经完成，则转入人工审查。这个例子展示了关键机制：Jev 不包办工作，而是决定工作接下来流向哪里。

原文建议，第一次接入应用程序接口，也就是 API 时，不要立刻搭建复杂的多代理团队。先做一个独立的任务路由器。程序接收目标和已完成的工作，调用 Jev，再把结果保存成一个本地任务文件。文件中记录原始请求、当前进度、Jev 的选择、置信度，以及任务最终进入研究、写作还是审查队列。之后，现有的工作进程再去消费这些任务。

示例程序设置了百分之八十五的置信度门槛。只有 Jev 选择研究或写作，而且置信度达到门槛时，任务才会自动流转。否则就进入审查队列。不过，百分之八十五的置信度并不等于百分之八十五的准确率。真正的门槛，应该根据自己工作流程中的标注样本来校准。

要让这类决策可靠，问题必须写得具体。Jev 支持三类常见判断。第一类是从选项中选择，例如决定下一位执行者。第二类是按自定义量表评分，例如判断一个来源是无关、部分相关，还是直接回答问题。第三类是回答是或否，并返回“是”的概率，例如判断一项请求是否需要发布。

这里有一个容易忽视的细节：字段名称本身不能代替指令。即使把字段命名为“可以安全发布”，也不意味着 Jev 自动理解安全标准。真正的要求必须写进问题，并清楚描述每个选项。状态信息也要具体。“研究员已经完成”几乎没有提供有效证据。更好的状态应该包含来源、主要发现，以及尚未填补的缺口。

另一个重要原则，是让选项随环境变化。Browser Use 的浏览器代理每完成一次点击，网页上可操作的按钮和输入框都可能改变。因此，它会重新观察页面，生成一份最新的可用操作清单，再让 Jev 从中选择。首席参谋式代理也应该采用同样的方法：只提供当前真实存在、而且现在可用的工作节点；工具改变状态后，立即刷新选项。否则，模型选择的可能是“昨天的菜单”。

性能优化也不只是换一个更快的模型。Browser Use 的报告显示，通过一次性收集页面状态，并避免因为无关动画反复预测，浏览器协议调用的中位数从一千零九十二次降到一百零一次。在三组匹配对比中，任务用时的中位数下降了百分之二十五，而且前后使用的是同一个模型。这说明，在购买更昂贵的推理能力之前，应该先检查系统是否存在重复的工具调用。

自动代理还必须知道在哪里停下。以晨间简报为例，可以允许系统自动收集资料和生成草稿，但到审查环节就停止。正式发布必须单独授权。应用还应设置操作次数上限、支出上限，并在每次动作后保存进度。系统中断后，要先检查最后一个已经完成的动作，避免重复搜索、重复写文件或重复发送消息。

尤其要注意，模型自信地说“完成了”，并不能证明文件真的保存成功，也不能证明消息真的发出去了。Browser Use 在 Jev 选择“完成”之后，还会独立检查结果。判断完成和验证完成，应该是两个分开的环节。

原文列举了几个实际案例。Browser Use 使用 Jev 选择下一步操作和网页元素，据报告在大约七秒内找到了航班，Jev 相关费用约为零点零零三九美元。但这个数字不包含浏览器本身的成本。计时从初始页面观察之后开始，也不包含运行后的全新核验，而且代理只是找到航班，并没有完成订票。

另一个案例中，Jev 对一千零一十八篇人工智能论文进行了主题分类。分类总成本约为零点零八美元，每篇论文的端到端延迟中位数为二百五十六毫秒。不过，生成论文摘要另用了其他模型，花费约三点九九美元。还有人用 Jev 在几秒内分类五百封邮件，费用约三点五美分。Jev 也可以在多个模型之间路由任务，把简单请求交给便宜模型，把复杂任务交给更强的推理模型。

这些案例真正说明的，不是某一个惊人的速度或价格，而是一种新的代理架构。生成模型负责创造内容，Jev 负责在有限选项中判断下一步，代码负责可靠地执行和验证。

最值得记住的是，从一个高频、重复的小决策开始，而不是一次改造整个系统。先测量它的准确性、延迟，以及每个已完成任务的总成本。因为一次便宜但错误的路由，可能让后续工作走错方向，最终比决策本身贵得多。把“思考”“决定”和“执行”拆开，才有机会构建更快、更便宜，也更容易检查的人工智能代理。

## 深度解读-口播（1）

### 2026-09-21 00:16:43

Jev 最值得关注的地方，不是它能像聊天机器人一样生成内容，而是它把智能体里的“小判断”单独拿了出来。大型语言模型负责研究、规划和写作；Jev 负责路由、评分、审批和升级；普通代码负责执行决定。这样的分工，有机会让智能体更快、更便宜，也更容易检查。

想象一个自动生成晨间简报的智能体。它需要收集资料、撰写草稿，再把草稿交给人审核。真正消耗资源的，不只是写作本身。每完成一步，系统都要判断：资料够不够？接下来该交给研究员，还是写作者？草稿能否进入审核？如果每个判断都调用一次大型生成模型，成本和延迟会迅速累积。

Jev 就是用来处理这类判断的。它是 TypeSafe AI 提供的系统一型模型。你把当前状态、明确的问题和预先定义好的选项交给它，它会返回一个结构化答案，包括所选选项、概率分布和置信度。它不能替你写简报，也不会生成代码或长篇解释。它更像一个快速调度层。

因此，第一步不是把整个智能体交给 Jev，而是找出一个反复出现、选项明确的决策点。比如，让 Jev 在“继续研究”“开始写作”和“转交审核”之间选择。搜索资料仍由研究工具完成，写作仍交给生成模型。如果规则非常精确，例如执行十次操作后必须停止，那就直接写进代码，不需要模型判断。

从零开始时，可以先在 TypeSafe 的测试界面里验证这个决策。给它一段状态：目标是比较三款人工智能代理工具；目前还没有收集资料；可用工作者是研究员和写作者；草稿必须保存供审核，不能直接发布。然后问它，下一步应该由谁执行。

接着改变状态，加入真实的研究笔记，再观察选择是否变化。这个小实验能帮助你确认，选项描述是否清楚，输入的信息是否足以支撑判断。

本地接入时，需要启用接口权限的 TypeSafe 账户、接口密钥，以及 Python 三点一二或更高版本。安装官方开发工具包后，可以写一个简单的调度脚本。脚本读取目标和当前进度，调用 Jev，再把结果保存成一个本地的 JSON 任务文件。

例如，Jev 选择继续研究，任务就进入研究队列；选择写作，就进入写作队列；如果结果不确定，或者置信度低于设定门槛，就进入人工审核队列。原文示例把门槛设为零点八五，但这只是起点。置信度并不等于准确率百分比，真正的阈值应该根据你自己的标注案例调整。

Jev 支持三类常见判断。Choice 是从预设选项中选择一个，适合决定下一位执行者。Score 是按照自定义量表评分，例如判断资料与问题有多相关。Noul 用来回答是或否，并返回“是”的概率。概率接近零点五，通常意味着模型并不确定。

提问方式非常关键。Jev 看不到字段名称背后的含义。即使字段叫“可以安全发布”，这个名字本身也不会成为指令。你必须在问题中写清判断标准，并准确描述每个选项。同时，不能只告诉它“研究已经完成”，而要提供来源、主要发现和仍然缺失的信息。

Browser Use 的浏览器智能体提供了一个重要设计思路：每执行一步，都重新生成当前可用的操作菜单。网页上的按钮、输入框和链接会不断变化。如果 Jev 仍然从旧选项中选择，就像拿着昨天的菜单点今天的菜。

同样的原则也适用于任务调度。只把当前在线并且可用的工作者列为选项。选择研究资料时，附上当前来源的标识。工具改变状态之后，立即刷新候选动作。Jev 的优势建立在一个前提上：提供给它的选项必须真实、完整，而且是最新的。

还要避免让多个相互独立的问题排队等待。如果选择工作者、评估紧急程度和检查是否需要审批，都能读取同一份状态，就可以并行发送。只有当后一个判断依赖新的搜索结果时，才应该先完成搜索。

很多性能问题其实不在模型，而在重复的工具调用。Browser Use 的一项优化，在使用相同模型的情况下，把浏览器协议调用的中位数从一千零九十二次降到一百零一次。三组配对测试中，任务耗时的中位数下降了百分之二十五。优化方式包括一次性读取页面状态，以及不为无关动画重新预测。换句话说，在购买更快、更贵的模型之前，先检查系统有没有反复读取同一份信息。

安全边界同样重要。对于晨间简报，可以允许系统自动收集来源并生成草稿，但应该停在审核环节。发布必须经过单独授权。系统还需要操作次数上限、支出上限和持续保存的进度。发生中断后，要先检查最后一个已经完成的动作，避免重复执行。

尤其要记住，高置信度只表示 Jev 对自己的选择较确定，并不能证明文件真的保存了，或者消息真的发送了。决策和完成验证必须分开。Browser Use 会在 Jev 判断任务完成之后，再独立检查结果。这个机制值得直接借鉴。

一些案例说明了这种分工适合什么场景。Browser Use 报告称，Jev 帮助浏览器代理在大约七秒内找到航班，模型费用约为零点零零三九美元。不过，这个价格不包含浏览器本身的成本；计时从首次页面观察之后开始，也不包含运行后的全新核验。它找到的是航班结果，并没有完成订票。

另一个案例用 Jev 分类了一千零一十八篇人工智能论文。分类费用约为零点零八美元，每篇论文的端到端延迟中位数是二百五十六毫秒。但论文摘要由另一个模型生成，摘要费用约为三点九九美元。这正说明，应该按整个任务核算成本，而不能只看某一次便宜的判断。

类似用法还包括给五百封邮件分类，在回复、研究、等待和审核之间分流；或者根据任务难度，把简单请求交给便宜模型，把复杂请求交给推理能力更强的模型。

最值得记住的是，Jev 不是另一个聊天机器人，而是智能体中的快速决策层。让大型模型负责真正需要生成和推理的工作，让 Jev 处理重复的选择、评分和审批，再让代码执行结果。实践时，从一个高频决策开始，测量准确性、总成本和完成率，然后再替换下一个决策点。
