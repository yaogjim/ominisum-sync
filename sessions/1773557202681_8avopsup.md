Hermes Agent

**The self-improving AI agent built by [Nous Research](https://nousresearch.com).** It's the only agent with a built-in learning loop — it creates skills from experience, improves them during use, nudges itself to persist knowledge, searches its own past conversations, and builds a deepening model of who you are across sessions. Run it on a $5 VPS, a GPU cluster, or serverless infrastructure that costs nearly nothing when idle. It's not tied to your laptop — talk to it from Telegram while it works on a cloud VM.

Use any model you want — [Nous Portal](https://portal.nousresearch.com), [OpenRouter](https://openrouter.ai) (200+ models), [z.ai/GLM](https://z.ai), [Kimi/Moonshot](https://platform.moonshot.ai), [MiniMax](https://www.minimax.io), OpenAI, or your own endpoint. Switch with `hermes model` — no code changes, no lock-in.

**A real terminal interface** Full TUI with multiline editing, slash-command autocomplete, conversation history, interrupt-and-redirect, and streaming tool output.

**Lives where you do** Telegram, Discord, Slack, WhatsApp, Signal, and CLI — all from a single gateway process. Voice memo transcription, cross-platform conversation continuity.

**A closed learning loop** Agent-curated memory with periodic nudges. Autonomous skill creation after complex tasks. Skills self-improve during use. FTS5 session search with LLM summarization for cross-session recall. [Honcho](https://github.com/plastic-labs/honcho) dialectic user modeling. Compatible with the [agentskills.io](https://agentskills.io) open standard.

**Scheduled automations** Built-in cron scheduler with delivery to any platform. Daily reports, nightly backups, weekly audits — all in natural language, running unattended.

**Delegates and parallelizes** Spawn isolated subagents for parallel workstreams. Write Python scripts that call tools via RPC, collapsing multi-step pipelines into zero-context-cost turns.

**Runs anywhere, not just your laptop** Six terminal backends — local, Docker, SSH, Daytona, Singularity, and Modal. Daytona and Modal offer serverless persistence — your agent's environment hibernates when idle and wakes on demand, costing nearly nothing between sessions. Run it on a $5 VPS or a GPU cluster.

**Research-ready** Batch trajectory generation, Atropos RL environments, trajectory compression for training the next generation of tool-calling models.

#### Quick Install

```
curl -fsSL https://raw.githubusercontent.com/NousResearch/hermes-agent/main/scripts/install.sh | bash
```

Works on Linux, macOS, and WSL2. The installer handles everything — Python, Node.js, dependencies, and the `hermes` command. No prerequisites except git.

> **Windows:** Native Windows is not supported. Please install [WSL2](https://learn.microsoft.com/en-us/windows/wsl/install) and run the command above.

After installation:

```
source ~/.bashrc    # reload shell (or: source ~/.zshrc)
hermes              # start chatting!
```

If you're coming from OpenClaw, Hermes can automatically import your settings, memories, skills, and API keys.

**During first-time setup:** The setup wizard (`hermes setup`) automatically detects `~/.openclaw` and offers to migrate before configuration begins.

**Anytime after install:**

```
hermes claw migrate              # Interactive migration (full preset)
hermes claw migrate --dry-run    # Preview what would be migrated
hermes claw migrate --preset user-data   # Migrate without secrets
hermes claw migrate --overwrite  # Overwrite existing conflicts
```

What gets imported:

- **SOUL.md** — persona file
- **Memories** — MEMORY.md and USER.md entries
- **Skills** — user-created skills → `~/.hermes/skills/openclaw-imports/`
- **Command allowlist** — approval patterns
- **Messaging settings** — platform configs, allowed users, working directory
- **API keys** — allowlisted secrets (Telegram, OpenRouter, OpenAI, Anthropic, ElevenLabs)
- **TTS assets** — workspace audio files
- **Workspace instructions** — AGENTS.md (with `--workspace-target`)

See `hermes claw migrate --help` for all options, or use the `openclaw-migration` skill for an interactive agent-guided migration with dry-run previews.

##### 1. 项目定位：一个“会成长”的 AI Agent
文章一开始强调，Hermes Agent 是一个**自我改进型 AI 代理**，最大特点是自带学习机制。

  - 从经验中创建技能

  - 主动推动自己保存知识
  - 搜索过去的对话记录
  - 跨会话建立对用户的长期理解

###### 通俗理解
比如你让它反复帮你做“每周整理行业资讯”的任务，它不只是每次重新开始，而是可能逐渐总结出更好的步骤，形成自己的“技能模板”。

## 产品-产品技术PMF（1）

### 2026-03-19 10:51:18

这是一个非常有 “独立产品 + 基础设施平台” 气质的项目：`NousResearch/hermes-agent`不只是一个 AI Agent 客户端，而是在尝试定义一种 “可持续成长的个人 / 团队代理操作系统”。它的核心差异不是 “能调用很多工具”，而是把长期记忆、技能沉淀、跨平台入口、可调度执行、可迁移部署、模型无锁定这些能力，组合成一个长期在线的 Agent Runtime。若一句话定义：它卖的不是一次性问答，而是 “一个会随着使用而变强、可随处访问、可低成本常驻的个人代理基础设施”。

**一、产品判断**
- 产品定位很清晰：面向重度 AI 用户、开发者、研究者和技术团队，提供 “长期在线、跨终端、可学习、可自动化” 的 Agent 操作环境。
- 与常见 AI 助手的区别不在 UI，而在 “闭环能力”：记忆、技能生成、自我改进、跨会话召回、调度执行、子代理并行、云端常驻。
- 它不是 ToC 大众消费品，更像是 “高级用户的 Agent IDE + Runtime + Personal Infra”。
- 从信息组织看，项目已经在讲一个完整叙事：可运行、可扩展、可研究、可迁移、可部署、可训练，这说明它有意同时覆盖开源社区、开发者生态和研究场景。
- 最大亮点是 “agent that grows with you” 这个价值主张，抓住了当前 Agent 产品里最稀缺但最容易形成粘性的能力：长期个体化。

**二、核心用户与场景**
- 第一核心用户：独立开发者、AI power users、开源玩家。他们需要本地 / 云端可控、模型可切换、能接 Telegram/CLI、能自动执行复杂工作流的代理。
- 第二核心用户：研究团队 / Agent infra 开发者。他们会关注 trajectory generation、RL environment、tool-calling 训练和多模型兼容。
- 第三核心用户：小团队运维 / 增长 / 内容 / 分析岗位。对日报、周报、巡检、数据抓取、定时任务、多平台通知很敏感。
- 最适配场景不是 “聊聊天”，而是四类高频高价值任务：长期记忆协作、个人工作流自动化、远程云端代理、研究与训练数据生成。
- 它对轻度用户的吸引力有限，因为初始配置、模型选择、工具权限、安全理解都有门槛。

**三、PMF 分析**
- PMF 最强的市场不是大众助手，而是 “对 AI 代理有持续使用需求、并愿意配置环境的人群”。
- 它满足了这类用户几个非常明确的痛点：会话割裂、模型锁定、仅本地运行、记忆不可靠、复杂任务不可复用、自动化碎片化。
- 如果用户已经从 ChatGPT/Claude 桌面端进阶到 “我希望助手记住我、会调用工具、能在 Telegram 上找它、还能定时做事”，Hermes 的产品价值会陡增。
- 其 PMF 信号主要体现在：多入口一致体验、迁移 OpenClaw、支持 200+ 模型、低成本部署、技能系统、研究接口。这些都在服务真实重度需求，而不是噱头。
- 但 PMF 仍偏 “窄而深”，更像一条强垂直赛道。它距离大规模普及还有明显障碍：安装复杂、价值理解成本高、记忆效果难量化、安全边界复杂、用户成功路径偏长。

**四、产品优势**
- 真正的差异化来自能力组合，而不是单点功能。很多产品有 memory，有些有 tool use，有些有 Telegram bot，但很少有人把这些做成统一运行时。
- 模型无锁定是非常强的战略点。它直接对冲了上层模型厂商的挤压，也给用户保留了成本和性能优化空间。
- 多终端统一入口很强：CLI、Telegram、Discord、Slack、WhatsApp、Signal 等，让代理从 “应用” 变成 “身份”。
- 学习闭环如果做实，会带来极强留存，因为用户会逐渐把自己的工作方式沉淀进去，迁移成本自然提高。
- 云端 / 容器 / SSH/Modal/Daytona 等部署能力说明它不把自己局限为桌面工具，而是在争夺 “Agent 基础设施层”。

**五、主要问题与风险**
- 最大风险不是功能不够，而是产品心智过重。用户第一次接触时，会同时看到模型、工具、权限、技能、记忆、cron、gateway、terminal backend，认知负担很大。
- “自我学习 / 自我改进” 是高吸引力概念，但也是高风险承诺。若技能生成质量不稳定、记忆召回不准、用户画像出错，会迅速损害信任。
- 安全与权限模型是商业化前最关键的阻碍。能执行 shell、跨平台接入消息、允许远程访问，一旦权限设计或默认配置不佳，风险极高。
- 多平台支持带来体验碎片化风险。CLI、消息平台、语音、计划任务、远程终端，这些路径非常容易出现 “都能用，但没有一个足够顺滑”。
- 对普通用户来说，价值兑现周期偏长。很多能力需要积累使用历史后才体现，首日激励可能不足。

**六、技术架构判断**
- 从描述看，Hermes 的技术架构是一个典型的 Agent Runtime 分层体系：模型层、工具层、记忆层、技能层、会话层、调度层、接入层、执行环境层。
- 模型层做了 provider abstraction，这很关键，能保持上层 Agent loop 稳定，底层替换 OpenAI、Anthropic、OpenRouter、Kimi 等不改业务逻辑。
- 工具与 terminal backend 的抽象做得比较完整，尤其 local/Docker/SSH/Modal/Daytona/Singularity 这些执行后端，说明它在认真解决 “Agent 到底在哪里干活” 的问题。
- 记忆部分大概率是 “结构化用户画像 + 文本记忆 + 会话检索 + 摘要压缩” 的混合方案，再叠加技能作为 procedural memory。
- 子代理并行与 RPC 式 Python 脚本调用，说明其内核在尝试从 “单轮工具调用” 升级到 “可编排任务执行系统”。
- 研究接口如 trajectory compression、RL env、Atropos integration，意味着它既是产品，也是数据生产系统，这对研究型组织很有吸引力。

**七、技术上最有价值的护城河**
- 第一是长期记忆与技能系统的闭环数据。这类数据天然具备强个体化，别人很难复制。
- 第二是多后端执行抽象。真正稳定地让 Agent 在本地、容器、SSH、serverless 持续执行，是非常难做但很有壁垒的工程。
- 第三是多入口会话统一。如果用户在 CLI 发起任务、在 Telegram 查看进展、由 cron 定时推送结果，这种跨介质连续性会带来强迁移成本。
- 第四是研究与生产双栈能力。很多竞品只能做消费端产品，Hermes 同时能为下一代模型训练提供轨迹数据和环境，战略位置更高。

**八、竞品与市场位置**
- 相比 ChatGPT/Claude desktop：Hermes 更像 “可编排、可私有部署、可跨平台、可成长的代理容器”，但在开箱即用和消费级体验上弱很多。
- 相比 AutoGPT / 开源 agent 框架：Hermes 更产品化，不只是 SDK，而是完整运行系统。
- 相比 Open Interpreter、OpenHands、Cursor 类产品：Hermes 更强调长期陪伴型 Agent 和多入口持续运行，而不是单一代码任务。
- 相比 Zapier/Make + LLM：Hermes 更自由、更个性化，但标准化和可靠性不如 workflow 平台。
- 它处在一个有意思的位置：不是纯研究框架，也不是纯聊天助手，而是 “个人 Agent OS”。

**九、商业化潜力**
- 最自然的商业化不是卖代码，而是卖托管能力、团队协作、安全控制、企业连接器、可观测性和稳定 SLA。
- 开源版本适合承接开发者和社区，商业版可做：
- `Cloud Hosted Hermes`：一键部署、持久化环境、可视化任务面板、托管记忆 / 技能 / 日志。
- `Team Hermes`：多成员共享技能、权限管理、审计日志、共享工作流、知识空间。
- `Enterprise Connectors`：Notion、Jira、Linear、Salesforce、Slack Admin、内部 MCP 网关。
- `Agent Ops Console`：任务追踪、成本分析、失败重试、审批流、安全策略。
- 研究侧还可以卖数据管线、环境、trajectory tooling，服务实验室和模型团队。

**十、当前产品最应该优化的不是 “再加功能”，而是三条转化路径**
- 第一条：`个人云端代理`。一句话卖点是 “你的 AI 助手 24/7 在线，Telegram 一句消息就能做事，还会记住你”。
- 第二条：`开发者自动化代理`。一句话卖点是 “本地 / 远程终端 + 多工具 + 可复用技能，替代零散脚本和临时提示词”。
- 第三条：`团队例行任务代理`。一句话卖点是 “日报、巡检、备份、审计、抓取与通知自动执行”。
- 现在文案覆盖很全，但略像 “全能型平台说明书”，不利于快速建立首要认知。
- 建议首页和文档首屏按 “人群 × 场景” 重构，而不是按功能模块堆叠。

**十一、我对产品策略的判断**
- 这个项目最适合走 “开源拉新 + 云服务变现 + 研究生态加成” 的路线。
- 不建议过早面向大众市场，因为它天然是高能力密度产品，应该先在高频重度用户中形成口碑和范式。
- 真正决定成败的不是功能总数，而是 “首次 30 分钟能否让用户感受到跨平台 + 记忆 + 自动化三件事一起生效”。
- 如果这三件事能被体验到，留存会很强；如果只是装好一个 CLI 聊聊天，它会沦为又一个 agent shell。

**十二、精炼结论**
- `Hermes-agent`是一个定位明确、技术野心大、差异点成立的 Agent Runtime 产品。
- 它的核心价值不是 “会调工具”，而是 “把代理做成一个持续成长、跨平台常驻、可迁移部署的个人基础设施”。
- PMF 已经在开发者 / 研究者 / 高阶 AI 用户这个细分市场显现，属于 “深需求、强粘性、窄人群” 的早期成立状态。
- 最大挑战是产品复杂度、安全信任和价值首屏呈现；最大机会是成为 “个人 / 团队 Agent OS” 的默认开源底座。
- 如果后续聚焦 2-3 条高价值场景，强化 onboarding、记忆可信度和云托管体验，它有机会从 “厉害的开源项目” 升级为 “真正有商业穿透力的 Agent 平台”。

可以。基于你提供的`NousResearch/hermes-agent`介绍，我用一个 “真实可落地” 的场景来讲，并在这个场景上给出最佳实践。

**具体实例**

假设你是一个独立开发者，维护一个在线 SaaS 产品，你希望让 Hermes 帮你完成这几类工作：

- 每天早上汇总 GitHub issue、服务器告警和昨日用户反馈
- 在 Telegram 上随时给你回复项目状态
- 定时执行备份、日志巡检、周报生成
- 在处理复杂任务后，把可复用流程沉淀成 skill
- 长期记住你的偏好，比如 “Bug 优先级高于新功能”“汇报先结论后细节”

你的部署方式是：

- Hermes 跑在一台`$5 VPS`上
- 你平时主要通过`Telegram`和`CLI`
- 模型先用`OpenRouter`，后续随时切换
- 开启`cron`、`memory`、`skills`、`gateway`

这个实例很适合 Hermes，因为它的强项正是：

- 多平台连续对话
- 定时自动化
- 跨会话记忆
- 从任务中生成和改进 skills
- 不绑定本地电脑

**最佳实践**

- **先把 Hermes 当 “长期工作的代理”，不要只当一次性聊天工具**
  - 这个项目最有价值的不是单轮问答，而是 “记忆 + 技能 + 定时 + 多入口” 形成闭环。
  - 在这个例子里，Hermes 不只是帮你查一次日志，而是逐渐学会 “你要看什么日志、什么异常要立刻提醒、什么内容适合汇总成日报”。

- **部署上优先 “云端常驻 + 手机入口”，不要只跑本地 CLI**
  - 最佳做法是让 Hermes 常驻在 VPS，上面跑`hermes gateway`，你通过 Telegram 发消息。
  - 这样它可以持续执行 cron、管理长期上下文、保持工作连续性。
  - CLI 则用于复杂调试、配置和手动干预；消息平台用于日常指挥。

- **一开始只开放必要工具，避免 “全工具默认开启”**
  - 比如这个场景下，第一批只开：
    - 文件与终端相关工具
    - GitHub / 项目监控相关工具
    - cron
    - memory /skills
  - 不要上来就给所有高权限工具，尤其是可能执行破坏性命令或访问敏感目录的工具。
  - 原因很简单：Hermes 越强，误操作成本越高；最佳实践是按任务逐步扩权。

- **把 “审批策略” 设计成分级，而不是完全放开**
  - 这个仓库内容里提到 approval / `/approve` `/deny`，这类机制非常关键。
  - 在这个实例中，建议这样分级：
    - 读操作默认允许：查日志、读配置、读 issue
    - 低风险写操作可审批后执行：生成日报、写分析文件、更新非关键文档
    - 高风险操作必须显式审批：删除文件、改生产配置、执行部署、清数据库
  - 最佳实践不是`--yolo`常开，而是只在可回滚、可控的环境里临时使用。

- **把 “记忆” 限定为高价值偏好和长期事实，不要让它记一切**
  - Hermes 的 memory 很强，但最佳实践不是无节制积累。
  - 在这个例子里，适合长期记忆的内容是：
    - 你的偏好：报告格式、优先级规则、常用部署方式
    - 项目稳定信息：仓库位置、服务结构、告警阈值
    - 协作习惯：先确认再改线上、先做 dry-run
  - 不适合长期记忆的是：
    - 一次性的临时实验
    - 容易过时的短期口头决定
    - 敏感临时凭证
  - 原则：只记 “未来还会反复用到” 的东西。

- **把高频复杂任务沉淀成 skills，而不是每次重新 prompt**
  - 比如你每周都要做一次 “系统巡检 + 风险摘要 + 待办清单”，最佳实践不是每次都重新描述流程。
  - 更好的做法是让 Hermes 在几次成功执行后，形成一个 skill，例如：
    - `weekly-ops-review`
    - 自动检查 CPU / 内存 / 错误日志 /issue/ 待处理 PR
    - 输出格式固定为：结论、风险、建议、是否需要我批准操作
  - 这样做的价值是：
    - 降低上下文成本
    - 提高输出稳定性
    - 让代理真正 “越用越懂你”

- **cron 任务只做 “可验证、可恢复、可通知” 的自动化**
  - 在这个场景里，很适合自动化的是：
    - 每天 8:30 发日报到 Telegram
    - 每晚 2:00 备份数据库并回传结果
    - 每周一生成上周 issue 分类总结
  - 不建议直接自动化的是：
    - 自动发版
    - 自动修改生产配置
    - 自动合并高风险代码
  - 最佳实践是：cron 先产出报告和建议，再由你审批关键动作。

- **模型选择要按任务分层，不要 “一个最强模型跑全部”**
  - Hermes 支持多模型切换，这一点很实用。
  - 在这个实例里可以这样分层：
    - 日报、总结、普通问答：便宜模型
    - 排查复杂故障、跨日志推理、长链任务：更强模型
    - 自动化脚本生成或严谨变更分析：高质量模型
  - 这样能显著控制成本，同时保留关键任务质量。

- **多平台接入时，先确定 “主入口”，避免上下文混乱**
  - Hermes 支持 Telegram、Discord、Slack、WhatsApp、Signal、CLI。
  - 最佳实践不是全部一起上，而是先规定：
    - Telegram：日常沟通与通知
    - CLI：复杂调试与本地操作
  - 否则很容易出现不同入口同时发任务，导致中断、优先级冲突或上下文分裂。

- **为 Hermes 建立明确的 “工作目录” 和项目上下文文件**
  - 仓库里提到`AGENTS.md`、Context Files 这类能力，这非常重要。
  - 在这个实例中，最佳实践是给你的 SaaS 项目放一份明确上下文，例如：
    - 项目结构
    - 启动命令
    - 测试命令
    - 禁止操作
    - 部署规则
    - 常见故障排查步骤
  - 这样 Hermes 每次进入项目时，不需要重新猜你的规范。

**把这个实例落成一个推荐工作流**

你可以把 Hermes 的工作方式设计成下面这样：

1. VPS 上常驻`hermes gateway`
2. 通过 Telegram 收到每天早报
3. Hermes 每晚自动巡检并生成摘要
4. 发现异常时先发消息给你，不直接改生产
5. 你回复 “分析原因并给出修复方案”
6. Hermes 调用工具收集日志、代码、监控数据
7. 对重复出现的诊断流程，沉淀为 skill
8. 对你的审批偏好、输出格式偏好，写入 memory
9. 复杂修复时切到 CLI，进行更细粒度控制

这个流程背后的最佳实践核心是：

- 自动化负责 “发现问题、准备信息、执行低风险流程”
- 人负责 “批准高风险动作、做最终决策”
- 技能负责 “复用成功经验”
- 记忆负责 “长期贴合你的风格”

**一个具体的高质量用法示例**

假设每天早上 8:30，Hermes 在 Telegram 给你发：

- 昨日新增 12 个 issue，其中 3 个为高优先级
- 生产环境出现 2 次 5xx 峰值，时间点为 02:14 和 02:19
- 数据库备份成功，耗时 7 分钟
- 建议优先排查支付服务重试逻辑
- 是否让我继续收集支付服务相关日志与最近变更？

这就是 Hermes 的最佳使用方式之一：

- 它先做信息收集和初步判断
- 它不给你无边界地自动执行高风险动作
- 它把下一步变成一个清晰审批点
- 你批准后，它再深入执行
- 这类排查如果反复发生，就变成一个 skill

**最容易踩的坑**

- 把 Hermes 当成普通聊天机器人，没用上 memory /skills/cron
- 一开始开放过多工具权限
- 没有审批边界，导致代理能直接执行危险操作
- 没有项目上下文文件，导致每次都要重新解释仓库规则
- 什么都记进 memory，最后记忆污染
- 所有任务都用最贵模型，成本失控
- 多平台同时混用，却没有主入口和通知策略
