## 正文

**Robert Youssef**

🚨 关于: 每个主要的 AI 代理框架都在解决错误的问题。

他们正在扩展上下文窗口。

但问题不在于能力，而在于代理所阅读的内容中90%是结构性噪声，这些噪声会主动损害推理。

同济大学和斯坦福大学的研究人员刚刚发表了这一证明：一个能够学习过滤主 AI 所看到内容的 7B 模型，该模型完全通过任务是否成功来训练。

当 AI 代理浏览网页时，它读取的原始 DOM 树中超过 90%是结构噪声——广告、样式脚本、导航元素、冗余标签。

在搜索环境中，每一个检索步骤都会使上下文充斥着干扰性段落。

随着代理执行更多步骤，这种噪声会累积。

关键信息被埋没。模型开始产生幻觉，因为它忘记了三步前发生的事情。

更大的上下文窗口并不能解决这个问题。它们只是给了噪声更多空间。

就连前沿模型也并非免疫。

&gt; Gemini-3.0-flash on WebArena: 36.4%的成功率（在完整上下文下）  
&gt;&gt;&gt; Gemini-3.0-flash on DeepSearch: 53.9%

这些是最先进的系统，在长时间任务中因信噪比下降而失效。

研究人员构建了第二个小型模型，其唯一任务是控制主模型看到的内容。

ContextCurator 是一个 7B 开源模型，位于环境和主要推理模型之间。

在每一步，它读取原始观测数据，积极地去除噪声，保留研究人员所谓的“推理锚点”——这些数据点在局部上不相关但在全局上具有因果关系，然后将工作记忆重写为高信号压缩表示形式。

主模型从不接触原始噪声。它只看到 ContextCurator 决定的重要内容。

ContextCurator 通过强化学习进行训练，仅使用一个信号：任务是否成功或失败？没有人工制定的规则。

没有带标签的示例。

仅仅成果导向学习跨越数千条路径。

结果:  
→ WebArena (Gemini-3.0-flash): 36.4% → 41.2% 的成功率，8.8% 更少的 token  
→ DeepSearch（Gemini-3.0-flash）：成功率从 53.9%提升至 57.1%，46.7K → 6.6K tokens（减少 8 倍）  
→ GPT-4o-mini with ContextCurator: 12.7% → 21.8% (+72%相对增益)  
→ 7B ContextCurator vs GPT-4o 作为策展人：竞争持平，更少的 token

最后的结果才是重要的。

一个专门针对上下文整理训练的 7B 参数开源模型，其上下文管理性能与 GPT-4o 相当。

前沿模型从 ActiveContext 获得 11%的相对增益。小型模型获得 72%。

较小的模型几乎完全依赖于上下文质量才能成功。

前沿模型对噪声具有一定的固有鲁棒性。

他们之间的差距很大程度上是数据质量问题而不是智能问题。

大多数框架将上下文管理视为被动检索，即检索与当前查询文本上相似的内容。

这一做法失败是因为文本相似性和因果必然性不是一回事。

步骤8中代理所需的东西，可能是它在步骤2中遇到的、当时看起来无关紧要的某个事物。

被动检索会漏掉它。经过强化学习训练的策展人学会了保留它。

上下文窗口不是瓶颈。你放入其中的内容才是瓶颈。

## 通俗精炼（1）

### 2026-04-20 00:36:46

#### AI 代理真正的问题：不是上下文太小，而是噪声太多

##### 核心观点

这篇内容的核心结论是：  
**当前很多 AI agent 框架努力扩展上下文窗口，但真正限制效果的，不是“能读多少”，而是“读进去的大部分内容都是噪声”。**

换句话说，AI 不是看得不够多，而是看了太多没用的信息，导致推理被干扰、记忆被稀释、任务成功率下降。

##### 为什么会失效

在真实任务中，AI agent 读取的内容里，往往有大量无关信息，比如：

- 网页中的广告、导航栏、样式代码、冗余标签
- 搜索过程中的无关段落
- 多步任务里不断累积的历史干扰信息

结果是：

- 关键信息被埋没
- 模型更容易遗忘前面重要内容
- 推理链条变脆弱
- 幻觉和错误决策增加

所以，**更大的上下文窗口，不一定解决问题，反而可能只是给噪声更大空间。**

##### 研究提出了什么方法

研究人员提出了一个叫 **ContextCurator** 的方法。

它本质上是一个专门负责“整理上下文”的小模型，放在环境和主模型之间，作用是：

- 先读取原始信息
- 主动过滤噪声
- 保留真正重要的“推理锚点”
- 把信息压缩成高信号的工作记忆，再交给主模型

重点在于：  
**主模型不再直接面对原始脏数据，而是只看被筛选后的高质量上下文。**

##### 训练方式有什么特别

这个模型并不是靠人工规则或人工标注训练出来的，而是通过强化学习完成：

- 不告诉它“哪些内容重要”
- 不提供人工整理好的答案
- 只用一个结果信号：任务成功还是失败

也就是说，它是通过大量任务试错，自己学会“什么信息该保留”。

这很重要，因为它说明：  
**上下文管理可以从“静态检索”升级为“面向任务结果的主动策展”。**

##### 效果如何

实验结果显示，这种方法能同时提升效果和效率：

- WebArena 成功率从 **36.4% 提升到 41.2%**
- DeepSearch 成功率从 **53.9% 提升到 57.1%**
- token 使用量大幅下降，某些场景减少 **8 倍**
- 在小模型上提升更明显，`GPT-4o-mini` 成功率从 **12.7% 提升到 21.8%**

这说明两点：

1. **上下文质量对 agent 成败影响极大**
2. **小模型和大模型的差距，很多时候不只是“智能差距”，也是“输入质量差距”**

##### 对产品和行业的启发

这篇文章最大的启发是：

**AI agent 的下一阶段竞争，不只是更大模型、更长上下文，而是更强的上下文治理能力。**

对产品设计和系统架构来说，这意味着：

- 不要把“检索更多内容”当成默认正确答案
- 要重视信息筛选、压缩、优先级排序
- 要从“相关性检索”走向“任务导向的上下文编排”
- agent 的性能优化重点，可能在“输入治理层”，而不只是“推理模型层”

##### 一句话总结

**AI agent 目前的关键瓶颈，不是上下文窗口不够大，而是输入内容太脏、太乱、太吵；谁能先解决上下文噪声问题，谁就更可能做出真正可用的 agent。**

## 结构化（1）

### 2026-04-20 00:56:58

#### 主旨概括

这篇内容的核心观点是：**AI 代理当前的主要瓶颈，不是上下文窗口不够大，而是输入内容里“噪声太多”**。与其一味扩展上下文，不如先训练一个专门的“小模型”过滤无关信息，让主模型只看真正重要的内容。

#### 1. 问题出在哪里：不是能力不足，而是上下文被噪声淹没

- 作者认为，当前主流 AI agent 框架解决错了方向：都在想办法扩大上下文窗口。  
- 但真正的问题是，代理读到的内容里，**约 90% 是结构性噪声**，这些内容会直接干扰推理。  
- 例如在网页环境中，原始 DOM 树里大量内容是：
  - 广告
  - 样式和脚本
  - 导航栏
  - 重复标签
- 在搜索场景里，每多检索一步，上下文里就会混入更多干扰段落，导致：
  - 关键信息被埋没
  - 模型忘记几步前的重要内容
  - 更容易出现幻觉

**通俗理解**：就像一个人做题时，题目旁边被塞满广告、菜单和无关说明。即使给他更大的草稿纸，也不代表他更容易做对题，因为真正的问题是“看到的垃圾信息太多”。

#### 2. 研究提出的办法：让一个 7B 小模型先做“上下文整理”

- 同济大学和斯坦福大学的研究人员提出了一个方案：  
  在主推理模型前面，加一个专门负责“筛内容”的模型，叫 **ContextCurator**。  
- 这个模型是一个 **7B 开源模型**，位置处于：
  - 外部环境 / 原始观测数据
  - 主推理模型  
  之间。
- 它每一步会先读取原始信息，然后：
  - 主动移除噪声
  - 保留真正重要的“推理锚点”
  - 把工作记忆重写成高信号、压缩后的表示
- 所谓“推理锚点”，指的是：  
  **当下看起来不重要，但对后续任务成败有因果作用的信息**。

**举例**：代理在第 2 步看到一个看似普通的页面提示，到了第 8 步才发现那其实是完成任务的关键。如果只按“和当前问题是否相似”来检索，这类信息很可能会被漏掉；而 ContextCurator 的目标是把这类信息提前保留下来。

#### 3. 它是怎么训练的：不靠人工规则，只看任务成败

- ContextCurator 通过**强化学习**训练。  
- 训练时只用一个信号：**任务最终成功还是失败**。  
- 研究没有依赖：
  - 人工写的过滤规则
  - 人工标注示例
- 也就是说，它不是被教“什么看起来像重点”，而是通过大量任务路径，自己学会：  
  **哪些信息值得保留，哪些信息应该丢掉。**

这说明它学到的不是“文本表面相似性”，而是更接近“对任务有没有帮助”的筛选能力。

#### 4. 实验结果：成功率提高，同时 token 大幅下降

研究给出的结果比较明确，说明“先整理上下文”确实有效：

- **WebArena + Gemini-3.0-flash**
  - 原始成功率：**36.4%**
  - 使用 ContextCurator 后：**41.2%**
  - 同时 **token 减少 8.8%**
- **DeepSearch + Gemini-3.0-flash**
  - 成功率：**53.9% → 57.1%**
  - token：**46.7K → 6.6K**
  - 相当于 **减少约 8 倍**
- **GPT-4o-mini + ContextCurator**
  - 成功率：**12.7% → 21.8%**
  - 相对增益约 **72%**
- **7B ContextCurator vs GPT-4o 作为“策展人”**
  - 效果**基本持平**
  - 但 **token 更少**

这些结果说明，一个只有 **7B 参数**、专门做上下文管理的开源模型，在这个任务上可以做到接近 GPT-4o 级别的效果。

#### 5. 研究传达出的更大结论：差距可能更多是“数据质量问题”

- 作者据此提出一个重要判断：  
  **很多模型表现差，不一定主要是“智能不够”，而是“喂进去的信息质量太差”。**
- 研究中提到：
  - 前沿模型从 ActiveContext 中获得 **11% 的相对增益**
  - 小模型获得 **72% 的相对增益**
- 这说明：
  - 小模型尤其依赖高质量上下文
  - 强模型对噪声更有一定鲁棒性
  - 但二者差距，很大一部分可能来自**上下文质量**而不是纯粹能力差异

换句话说，**把信息整理好，可能比单纯换一个更大的模型更划算**。

#### 6. 为什么传统检索方式不够：相似文本不等于关键因果信息

- 文章批评了当前很多框架的默认做法：  
  把上下文管理理解成“被动检索”——也就是找和当前查询文字最相似的内容。
- 但问题在于：
  - **文本相似性 ≠ 因果必要性**
- 有些对任务真正关键的信息，在当前步骤看上去并不相关，甚至和当前查询词不相似；但它在后面会决定任务是否成功。
- 被动检索容易错过这类内容；而通过强化学习训练的 ContextCurator，则更可能学会保留它们。

**一句话总结这部分**：  
传统方法是在找“像不像当前问题”，而这项研究要找的是“以后会不会决定成败”。

#### 7. 结论：上下文窗口不是瓶颈，放进去的内容才是

- 文章最后的核心结论是：  
  **真正的瓶颈不是上下文窗口大小，而是上下文内容质量。**
- 扩大窗口，并不能自动提升效果；如果噪声也一起扩大，只会让模型更难推理。
- 因此，更值得投入的方向可能是：
  - 上下文筛选
  - 工作记忆压缩
  - 任务导向的信息保留机制

#### 8. 评论区补充信息

- 作者在评论区贴出了论文链接：`arxiv.org/pdf/2604.11462`
- 有回复者提到，他在完全不同的实验方向里也得出类似结论：  
  **同一个模型、同样规则下，仅仅改变输入质量，结果就会明显不同。**
- 还有人用一句很形象的话概括这个问题：  
  **我们像是在让模型“读懂气氛”，却没有先让它“听清对话”。**
