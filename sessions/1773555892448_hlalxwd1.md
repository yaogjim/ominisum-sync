## 分析要点

- **核心高价值点**：acpx把不同编码Agent统一到ACP协议下，提供持久会话、命名会话、排队执行和结构化输出，明显优于传统PTY抓取式集成。
- **留存建议**：短期参考，按需保留（涉及ACP、acpx与dotclaude的安装方式、能力边界和典型命令，适合作为后续试用时的参考索引）

**知识要点**

- acpx是面向ACP的无头CLI，可统一调用Codex、Claude等Agent并支持持久化会话
- dotclaude提供面向Claude Code的插件市场，覆盖review、gitflow、refactor、superpowers等场景
- ACP方式强调结构化协议通信，减少对终端字符流抓取的脆弱依赖
- 多Agent协作可通过命名会话、并行任务流和分层review提升开发流程组织性

**行动项**

- 先在一个小型仓库中试装acpx，验证持久会话、命名会话和JSON输出是否符合自己的自动化需求
- 若已使用Claude Code，可挑选dotclaude中的review或superpowers插件做一次真实任务演练
- 对比ACP集成与原始PTY集成在稳定性、权限控制和可观测性上的差异，再决定是否纳入主工作流

#### Plugin Structure

Each plugin follows Claude Code's standard plugin structure:

```
plugin-name/
├── .claude-plugin/
│   └── plugin.json          # Plugin metadata (required)
├── commands/                # Slash commands (optional, legacy)
│   └── command-name.md
├── agents/                  # Agent definitions (optional)
│   └── agent-name.md
├── skills/                  # Skill definitions (optional)
│   └── skill-name/
│       ├── SKILL.md         # Main skill file
│       └── references/      # Detailed reference materials
├── hooks/                   # Hook configurations (optional)
│   └── hooks.json
├── scripts/                 # Utility scripts (optional)
└── README.md                # Plugin documentation (optional)
```

Modern plugins use **skills-based architecture** where each skill is a directory containing:

- `SKILL.md` - Main skill file with YAML frontmatter
- `references/` - Detailed reference materials for progressive disclosure

**Skills registered as commands in plugin.json:**

```
{
  "commands": [
    "./skills/skill-name/"
  ]
}
```

#### acpx

> ⚠️ `acpx` is in alpha and the CLI/runtime interfaces are likely to change. Anything you build downstream of this might break until it stabilizes.

> ACP coverage status: see ACP Spec Coverage Roadmap.

Your agents love acpx! 🤖❤️ They hate having to scrape characters from a PTY session 😤

`acpx` is a headless CLI client for the [Agent Client Protocol (ACP)](https://agentclientprotocol.com), so AI agents and orchestrators can talk to coding agents over a structured protocol instead of PTY scraping.

One command surface for Pi, OpenClaw ACP, Codex, Claude, and other ACP-compatible agents. Built for agent-to-agent communication over the command line.

- **Persistent sessions**: multi-turn conversations that survive across invocations, scoped per repo
- **Named sessions**: run parallel workstreams in the same repo (`-s backend`, `-s frontend`)
- **Prompt queueing**: submit prompts while one is already running, they execute in order
- **Cooperative cancel command**: `cancel` sends ACP `session/cancel` via queue IPC without tearing down session state
- **Soft-close lifecycle**: close sessions without deleting history from disk
- **Queue owner TTL**: keep queue owners alive briefly for follow-up prompts (`--ttl`)
- **Fire-and-forget**: `--no-wait` queues a prompt and returns immediately
- **Graceful cancel**: `Ctrl+C` sends ACP `session/cancel` before force-kill fallback
- **Session controls**: `set-mode` and `set <key> <value>` for `session/set_mode` and `session/set_config_option`
- **Crash reconnect**: dead agent processes are detected and sessions are reloaded automatically
- **Prompt from file/stdin**: `--file <path>` or piped stdin for prompt content
- **Config files**: global + project JSON config with `acpx config show|init`
- **Session inspect/history**: `sessions show` and `sessions history --limit <n>`
- **Local status checks**: `status` reports running/dead/no-session, pid, uptime, last prompt
- **Client methods**: stable `fs/*` and `terminal/*` handlers with permission controls and cwd sandboxing
- **Auth handshake**: stable `authenticate` support via env/config credentials
- **Structured output**: typed ACP messages (thinking, tool calls, diffs) instead of ANSI scraping
- **Any ACP agent**: built-in registry + `--agent` escape hatch for custom servers
- **One-shot mode**: `exec` for stateless fire-and-forget tasks

```
$ acpx codex sessions new
$ acpx codex "find the flaky test and fix it"

[thinking] Investigating test suite for flaky failures
```

#### Session behavior

- Prompt commands require an existing saved session record (created via `sessions new` or `sessions ensure`).
- Prompts route by walking up from `cwd` (or `--cwd`) to the nearest git root (inclusive) and selecting the nearest active session matching `(agent command, dir, optional name)`.
- If no git root is found, prompts only match an exact `cwd` session (no parent-directory walk).
- `-s <name>` selects a parallel named session during that directory walk.
- `sessions new [--name <name>]` creates a fresh session for that scope and soft-closes the prior one.
- `sessions ensure [--name <name>]` is idempotent: it returns an existing scoped session or creates one when missing.
- `sessions close [name]` soft-closes the session: queue owner/processes are terminated, record is kept with `closed: true`.
- Auto-resume for cwd scope skips sessions marked closed.
- Prompt submissions are queue-aware per session. If a prompt is already running, new prompts are queued and drained by the running `acpx` process.
- Queue owners use an idle TTL (default 300s). `--ttl <seconds>` overrides it; `--ttl 0` keeps owners alive indefinitely.
- `--no-wait` submits to that queue and returns immediately.
- `cancel` sends cooperative `session/cancel` to the running queue owner process and returns success when no prompt is running (`nothing to cancel`).
- `set-mode` and `set` route through queue-owner IPC when active, otherwise they reconnect directly to apply `session/set_mode` and `session/set_config_option`.
- `<mode>` values for `set-mode` are adapter-defined; unsupported values are rejected by the adapter (commonly `Invalid params`).
- `exec` is always one-shot and does not reuse saved sessions.
- Session metadata is stored under `~/.acpx/sessions/`.
- Each successful prompt appends lightweight turn history previews (`role`, `timestamp`, `textPreview`) to session metadata.
- `Ctrl+C` during a running turn sends ACP `session/cancel` and waits briefly for `stopReason=cancelled` before force-killing if needed.
- If a saved session pid is dead on the next prompt, `acpx` respawns the agent, attempts `session/load`, and transparently falls back to `session/new` if loading fails.

See docs/CLI.md.

##### 1. 从“单模型助手”到“多代理团队”

以前的 AI 编程通常像这样：

- 用户提问
- 一个模型回答
- 如果不放心，就手工切到另一个模型再问一次

这本质上是“人工切模型”。

也就是：

- 主 agent 负责主线任务
- 次级 agent 负责审查、补充、验证、质疑
- 不同 agent 各看自己擅长的部分

Frad 提到的“训练茧房”是个很有洞察力的说法。

通俗讲，一个模型会有这些问题：

- 某些代码风格偏好很固定
- 某些 bug 类型特别敏感，某些特别迟钝
- 某些架构方案容易过度自信

- 对自己刚产出的内容更容易“自洽”

所以如果：
- Claude 写代码
- 还是 Claude 自己审代码

那它可能会陷入“自我一致性陷阱”。

而如果：
- Claude 写
- Gemini 查
- Codex 补
- Security reviewer 再扫

问题暴露率通常会更高。

这就是多模型协同的实际价值。

---

##### 3. 为什么“结构化协议”比“抓终端输出”更关键

这个点非常技术，但值得讲明白。

###### PTY scraping 的问题

如果你让 agent A 调 agent B，但只是通过终端字符输出来沟通，会遇到：

- 输出很花
- 颜色/格式混杂
- 一会儿是日志，一会儿是正文
- 不容易判断“什么时候结束”
- 不容易知道“这段是不是工具调用结果”
- 不容易把结果再传给下游 agent

这很像让机器去“看人类屏幕录像”然后猜发生了什么。

###### ACP + acpx 的改进

结构化协议意味着：

- 哪条是 thinking
- 哪条是 tool call
- 哪条是 completed
- 哪条是 diff
- 哪条是 final answer

都能清楚标识。

这带来的不是“小优化”，而是**范式切换**：

> 从“脆弱的人类界面自动化”，变成“稳定的程序级 agent 通信”。

这也是为什么 acpx 的潜力不只是“更方便”，而是可能成为 agent orchestration 的基础设施。

#### 四、dotclaude 和 acpx 合起来，能形成什么样的工作流

这里举几个比较容易理解的典型场景。

---

##### 场景 1：Claude 主写，Gemini 复审

这是 Frad 帖子里的直接例子。

流程可能是：

1. 你在 Claude Code 中完成一轮修改
2. 触发一个 acpx 能力
3. Claude 通过 acpx 调用 Gemini
4. Gemini 检查最近的变更是否存在：
   - 逻辑漏洞
   - 回归风险
   - 边界条件遗漏
   - 风格与接口不一致
5. 结果回流给 Claude
6. Claude 再决定是否修补

本质上就是：

> Claude = 实现者，Gemini = 外部审稿人

---

##### 场景 2：多 reviewer 并行检查一个 PR

结合 dotclaude 的 `review` 能力，可以形成这种模式：

- code-reviewer 看代码质量与可维护性
- security-reviewer 看漏洞风险
- tech-lead-reviewer 看架构与技术债
- ux-reviewer 看交互与用户体验

如果再引入 acpx，就可以进一步想象：

- 某些 reviewer 可以不是同模型
- 可以跨 agent 调用不同 ACP-compatible 模型来分别审查

这时的 review 不再是“一个大模型一次性扫一遍”，而更像：

> 一个小型虚拟评审委员会。

---

##### 场景 3：Plan-Execute-Review 的闭环开发

结合 `superpowers` + `review` + acpx，可以形成完整流水线：

1. brainstorming：把需求说清楚
2. writing-plans：拆解实现方案
3. executing-plans：让 agent team 去做
4. review：多角色审查结果
5. 再通过外部 agent 交叉复核
6. github/create-pr：自动生成 PR
7. gitflow/finish-release：进入发布流程

这已经不是“AI 帮我写一段代码”了，而是：

> AI 参与整个软件交付链条。

---

##### 场景 4：同仓库并行多个工作流

acpx 的 named sessions 很适合这个：

- `backend` 会话修 bug
- `frontend` 会话改 UI
- `docs` 会话写文档
- `release` 会话准备发版

每个会话有自己的上下文，不互相污染。

这点很像你给不同 agent/team member 分配了不同任务线程。

对真实项目来说，这非常实用，因为它解决了一个老问题：

> 一个 agent 上下文太长以后，容易混任务、串语义、上下文污染。

session 化之后，工作流更接近真实团队分工。

#### 五、从产品视角看：这套东西到底解决了哪类人痛点

---

##### 1. 对重度 AI 编程用户

如果你已经在同时用：

- Claude Code
- Codex
- Gemini CLI
- Cursor/Copilot 等

那你最大的痛点通常不是“没有模型可用”，而是：

- 切换成本高
- 会话状态不统一
- 自动化困难
- 缺少统一工作流

acpx 的价值就在于统一入口。

---

##### 2. 对团队工程化用户

如果你的目标不是偶尔写点代码，而是想把 AI 真正接入团队开发流程，那么你需要：

- 审查流程
- 计划拆解
- 规范提交
- PR/Issue 自动化
- 质量门禁
- 多角色协作

dotclaude 正是在补这些“工程化缺口”。

---

##### 3. 对 Agent 平台/编排系统开发者

如果你在做更上层的 agent orchestration，acpx 的意义更大：

- 它不是某个单点功能
- 而是一种 agent 通信基础层

你可以在此之上做：

- 多 agent 调度器
- 自动 code review pipeline
- agent router
- 模型仲裁系统
- 多模型投票机制
- specialized worker agents

#### 六、这套方案的真正先进之处

---

##### 1. 它不只是“插件很多”

很多人看到 dotclaude 会先觉得：“哦，就是 Claude Code 的插件大全。”

但更深一层看，它的先进点在于：

> 它在尝试把 Claude Code 从“单体助手”改造成“可编排的 agent 工作台”。

也就是说，重点不是插件数量，而是背后的设计思想：

- skill-based architecture
- agent specialization
- progressive disclosure
- workflow orchestration
- quality gates
- plan/execute/review 闭环

---

##### 2. acpx 不只是“一个 CLI 工具”

很多 CLI 工具都能“调用另一个命令”，但 acpx 不一样。

它真正的价值在于：

- **stateful session**
- **queue-aware execution**
- **structured protocol**
- **multi-agent abstraction**
- **repo-scoped routing**

这些能力加起来，它更像是一个：

> 面向 coding agents 的“会话总线 + 调度层 + 协议适配层”。

---

##### 3. 这套思路符合未来趋势

未来 AI 开发工具很可能不是“谁家模型更强”这么简单，而是：

- 谁能更好地**组织多个模型**
- 谁能更好地**让代理协作**
- 谁能更好地**把能力嵌入工程流程**
- 谁能更好地**实现结构化可自动化的 agent 通信**

从这个角度看：

- acpx 是偏基础设施
- dotclaude 是偏工作流产品化
- Frad 的帖子是在提示大家：这个方向已经开始能用了

#### 七、可能的局限与注意点

综合三份内容，也要看到一些现实限制。

---

##### 1. acpx 还在 alpha

仓库里明确写了：

> acpx is in alpha and the CLI/runtime interfaces are likely to change

所以这意味着：

- 接口可能变
- 下游封装可能要跟着适配
- 生产级稳定性还需要观察

也就是说，它很有前景，但还不是“完全稳定的基础设施”。

---

##### 2. 依赖底层 agent 自身能力

acpx 是统一调度层，但最终效果仍取决于底层 agent：

- Claude Code 是否安装并可用
- Codex CLI 是否正常
- Gemini CLI 的 ACP 支持是否稳定
- 不同 agent 对 ACP 支持深浅不同

因此，理论上“统一入口”，实践上还是会存在：
- adapter 差异
- 功能支持差异
- 模式/权限/输出差异

---

##### 3. 多模型协作不等于自动更优

“突破训练茧房”是有价值的，但不应神化。

多模型协作也有可能带来：

- 成本更高
- 延迟更大
- 结论冲突
- 审查意见太多太散
- 编排复杂度上升

所以关键不只是“接更多模型”，而是：

> 在正确的节点调用正确的 agent。

例如：
- 关键 PR 合并前做交叉审查很值
- 改一个小文案就没必要叫 3 个模型来投票

---

##### 4. 手动 approve 场景需要具体验证

热门回复里有人问：

> “这个能用在需要手动 approve 的场景吗”

这其实问到了一个很实际的问题：
- 真实企业环境里，很多工具调用需要权限审批
- ACP/acpx 是否能很好地处理 interactive approval / permission gating
- 非交互模式下是 deny、fail 还是 approve-all
- 会不会影响自动化流畅度

从 acpx 文档看，它有权限策略支持，比如：
- approve-all
- approve-reads
- deny-all
- non-interactive-permissions

说明它**考虑到了权限控制问题**，但具体在你自己的 agent 栈里是否顺畅，还是要测试。

#### 八、如果用最通俗的话解释，这套体系像什么

你可以这样理解：

---

##### 以前的 AI 编程方式

像是你雇了一个很聪明的实习生：

- 你让他写代码
- 写完让他自己检查
- 不放心时你再另找一个人手工问一遍

问题是流程碎、重复、低效。

---

##### acpx + dotclaude 之后

更像你有了一个小型虚拟研发团队：

- Claude 当主程
- Gemini 当外部评审
- security reviewer 当安全专家
- tech lead reviewer 当架构负责人
- superpowers 当项目经理
- git/github/gitflow 当工程流程机器人

而 acpx 就像这个团队内部的：

> “统一沟通系统 + 工单流转系统 + 会话系统”

这就是它真正的价值。

#### 九、一个高质量结论

综合三份内容，可以得出这样的结论：

> **acpx 提供了基于 ACP 的通用 agent-to-agent 通讯与会话管理能力，解决了多 agent 协作中“如何稳定调用、如何持久会话、如何结构化交互”的基础问题；dotclaude 则把这种能力嫁接到 Claude Code 的插件和工作流体系里，进一步形成可直接用于代码评审、计划拆解、工程自动化与多角色协作的实用开发环境。Frad 的推荐帖本质上是在提示：AI 编程正在从“单模型问答”走向“多代理、多模型、结构化协作”的阶段，而 acpx + dotclaude 是这个方向上很有代表性的早期实践。**
