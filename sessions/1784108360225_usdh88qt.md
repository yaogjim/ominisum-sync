---

Running a model locally is only the first step. To build useful AI applications you need a set of higher-level building blocks. PrivateGPT provides that layer as an open-source API following the Claude API model — so you can build private AI products without rebuilding the same backend primitives from scratch, and without depending on cloud APIs.

Production-tested: PrivateGPT powers Zylon, the on-premise AI platform providing Private AI to enterprises across the globe.

```
Your app / agent / workflow / UI
              |
        PrivateGPT API
              |
OpenAI-compatible inference server (Ollama, llama.cpp, vLLM, …)
```

> PrivateGPT does **not** run models itself. It connects to any OpenAI-compatible inference server via `OPENAI_API_BASE`. If it implements `/v1/chat/completions` and `/v1/models`, it works.

PrivateGPT ships a built-in workbench UI for testing and demos, available at `/ui`. The API is the actual product.

---

- Standard messages API (streaming, async, token counting)
- File and artifact ingestion
- Retrieval with citations and agentic RAG
- Built-in tools mirroring the Claude API (web search, web fetch, code execution)
- Custom tools and MCP connectors
- Structured access to databases and CSVs
- Embeddings and orchestration

#### Quickstart

> For Docker, full installation options, and model configuration see the [full Quickstart guide](https://docs.privategpt.dev/getting-started/quickstart).

**Prerequisites:** You need a running OpenAI-compatible LLM server. [Ollama](https://docs.privategpt.dev/providers/ollama) is the easiest starting point.

**1. Install PrivateGPT**

```
# macOS
brew tap zylon-ai/tap
brew install private-gpt
```

```
# Linux
curl -LsSf https://astral.sh/uv/install.sh | sh

uv tool install --python 3.11 \
  --find-links https://wheels.privategpt.dev/packages/ \
  "private-gpt[core]"
```

```
# Windows
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

uv tool install --python 3.11 `
  --find-links https://wheels.privategpt.dev/packages/ `
  "private-gpt[core]"
```

**2. Start your LLM server**

```
# Example with Ollama
ollama pull qwen3.5:35b         # LLM (~24 GB)
ollama pull mxbai-embed-large   # Embeddings (~670 MB)
ollama serve
```

**3. Run PrivateGPT**

```
# macOS / Linux
OPENAI_API_BASE=http://localhost:<llm-port>/v1 \
  OPENAI_EMBEDDING_API_BASE=http://localhost:<embedding-port>/v1 \
  private-gpt serve
```

```
# Windows (PowerShell)
$env:OPENAI_API_BASE = "http://localhost:<llm-port>/v1"
$env:OPENAI_EMBEDDING_API_BASE = "http://localhost:<embedding-port>/v1"
private-gpt serve
```

**4. Open the UI**

Go to [http://localhost:8080/ui](http://localhost:8080/ui). The API is at `http://localhost:8080` and follows the [Anthropic API](https://docs.privategpt.dev/api-reference/api-reference) spec.

The UI is useful for:

- Sending messages.
- Selecting models from /v1/models.
- Uploading documents.
- Testing retrieval with citations.
- Enabling tools per chat.
- Configuring databases, MCP connectors, skills, and custom tools.
- Inspecting requests and responses through the API Debugger.

This UI is a demonstrator, not the core product. Developers are expected to build their own applications on top of the API. That said, the UI is intentionally polished enough for demos, videos, internal pilots, and quick local usage.

PrivateGPT started as a proof of concept in 2023: a script that let you chat with your documents, fully offline, with no data leaving your machine. It went viral on GitHub, crossed 50K stars, and became one of the most-watched AI repos of that year.

That early version made one thing clear: there was serious demand for private, local AI that worked without cloud dependencies.

PrivateGPT 1.0 is the evolution of that idea — rebuilt from the ground up as a proper API layer for private AI applications.

These projects make it possible to run and serve models locally. They answer: *how do I run a model?*

PrivateGPT answers the next question: *how do I build a useful AI application on top of that model?*

```
Ollama / LM Studio / LocalAI / vLLM / llama.cpp  =  local inference layer
PrivateGPT                                        =  local AI application API layer
```

Use them together. Run your model with whichever inference server you prefer, then point PrivateGPT at it.

Both are valuable, but they are app-first experiences focused on chat and enterprise search. PrivateGPT is API-first. It provides the standardized local backend underneath those products — not the final product itself.

```
Onyx / Open WebUI  =  self-hosted AI applications
PrivateGPT         =  API layer for building self-hosted AI applications
```

#### PrivateGPT：把本地模型变成可用 AI 产品的开源 API 层

##### 一句话概括

PrivateGPT 不是模型运行工具，也不是最终聊天产品，而是连接**本地模型与上层 AI 应用**的开源后端：提供 RAG、文档解析、工具调用、MCP、数据库查询等通用能力，帮助开发者快速构建私有化 AI 产品。

##### 核心定位

其架构可以理解为：

> 应用、Agent、工作流或 UI → PrivateGPT API → 本地推理服务 → 本地模型

PrivateGPT 自身不运行模型，而是连接 Ollama、llama.cpp、vLLM、LM Studio 等兼容 OpenAI 接口的推理服务。对上层应用则主要参考 Claude API 设计，降低应用集成和迁移成本。

##### 主要能力

- **模型交互**：消息、流式输出、异步处理、Token 统计。
- **知识库与 RAG**：文件上传、PDF / 文档解析、向量检索、引用溯源、Agentic RAG。
- **工具与 Agent**：网页搜索、网页抓取、代码执行、自定义工具、MCP 连接器。
- **结构化数据**：数据库查询、Text-to-SQL、CSV 与表格分析。
- **模型扩展**：Embedding、结构化输出、推理能力及多模态支持。
- **开发调试**：内置 Workbench UI，可测试模型、文档检索、工具调用和 API 请求。

##### 产品边界

| 产品 | 核心作用 |
|---|---|
| Ollama、vLLM、llama.cpp | 负责运行和提供模型推理 |
| PrivateGPT | 提供构建 AI 应用所需的标准化 API 与通用能力 |
| Open WebUI、Onyx | 面向用户的聊天、搜索等完整应用 |
| Zylon | 面向企业的部署、治理、运维与合规平台 |

内置 UI 主要用于演示、调试和内部试点，**API 才是核心产品**。开发者通常需要在其上构建自己的应用、Agent 或工作流。

##### 集成与适用场景

PrivateGPT 可作为 Claude Desktop、Claude Code、Microsoft 365、n8n、VS Code、Cline 等工具的本地后端，适合：

- 数据不能离开本地或内网的组织；
- 需要私有知识库和可追溯问答的应用；
- 希望统一接入多种本地模型的开发团队；
- 需要构建内部 Agent、数据分析或自动化工作流的企业。

##### 成熟度与限制

项目始于 2023 年的离线文档问答原型，GitHub Star 已超过 5 万；当前 1.0 版本已重构为面向生产的 API 层，并被 Zylon 企业平台实际采用。

主要限制包括：

- Skills 能力仍处于基础阶段；
- 暂不支持 Prompt Caching；
- 不提供 OAuth、组织体系等平台级能力；
- 视觉与结构化输出效果依赖底层模型和推理服务；
- 企业级高可用、权限、审计和运维并非开源版重点。

##### 商业模式与选择建议

PrivateGPT 提供开源开发底座；Zylon 则在其上增加 Kubernetes 部署、推理集群、负载均衡、RBAC、LDAP、审计日志、监控、企业连接器及离线运行等能力。

- **选 PrivateGPT**：需要灵活、开源、API-first 的本地 AI 应用底座。
- **选 Zylon**：需要完整的企业部署、治理、合规、运维与商业支持。

##### 核心价值判断

PrivateGPT 解决的不是 “如何在本地运行模型”，而是更接近产品落地的问题：

> **模型已经运行起来后，如何低成本地把它变成真正可用、可集成的私有 AI 应用。**

### 提问 · 2026-07-15 09:56:07

https://github.com/zylon-ai/private-gpt 如何 和 https://github.com/tobi/qmd 整合在一起 使用  ？

### 回答 · 2026-07-15 09:56:07

可以整合，最合适的方式是把**qmd 当作检索工具，通过 MCP 接入 PrivateGPT**。

##### 推荐架构

```text
你的应用 / PrivateGPT Workbench
              ↓
       PrivateGPT API
        ↙           ↘
本地 LLM 推理服务     qmd MCP Server
(Ollama/vLLM 等)          ↓
                    Markdown 文档索引
```

职责划分：

- **PrivateGPT**：消息 API、模型调用、工具编排、Agent、权限入口。
- **qmd**：Markdown 文件的本地索引与搜索。
- **Ollama/vLLM**：真正运行大语言模型。

需要注意：**qmd 不是 OpenAI Embedding API 服务**，因此不能把`OPENAI_EMBEDDING_API_BASE`直接指向 qmd。正确方式是 MCP、Custom Tool，或者应用端先检索再把结果交给 PrivateGPT。

---

#### 方案一：通过 MCP 接入，推荐

##### 1. 安装并初始化 qmd

按照 qmd 仓库当前 README 安装。安装后先确认命令：

```bash
qmd --help
```

将 Markdown 目录加入 qmd。命令名称可能随版本变化，大致流程是：

```bash
qmd collection add ~/Documents/notes --name notes
qmd embed
```

先独立验证搜索：

```bash
qmd search "项目部署方式"
qmd query "项目部署方式"
```

具体参数请以以下命令的输出为准：

```bash
qmd collection --help
qmd query --help
qmd mcp --help
```

---

##### 2. 启动 qmd MCP Server

如果 qmd 当前版本支持 MCP，一般是：

```bash
qmd mcp
```

很多本地 MCP Server 默认使用**stdio transport**。这适合 Claude Desktop，但 PrivateGPT 的远程 MCP Connector 通常需要一个 URL，也就是 SSE 或 Streamable HTTP。

因此需要在中间增加一个 stdio-to-HTTP 网关。

###### 使用 supergateway 转换

先确认 qmd 路径：

```bash
command -v qmd
```

然后运行：

```bash
npx -y supergateway \
  --stdio "$(command -v qmd) mcp" \
  --port 8090
```

启动日志一般会输出实际 MCP 地址，常见形式是：

```text
http://127.0.0.1:8090/sse
```

较新版本也可能提供 Streamable HTTP 地址，例如：

```text
http://127.0.0.1:8090/mcp
```

**以 supergateway 启动日志给出的 URL 为准。**

如果 qmd 本身已经支持 HTTP transport，例如`--transport http`、`--port`一类参数，就不需要 supergateway，直接使用 qmd 提供的 HTTP MCP 地址即可：

```bash
qmd mcp --help
```

---

##### 3. 启动 PrivateGPT

例如使用 Ollama：

```bash
ollama pull qwen3.5:35b
ollama pull mxbai-embed-large
ollama serve
```

然后启动 PrivateGPT。端口要根据你的 Ollama 配置填写：

```bash
OPENAI_API_BASE=http://localhost:11434/v1 \
OPENAI_EMBEDDING_API_BASE=http://localhost:11434/v1 \
private-gpt serve
```

访问：

```text
http://localhost:8080/ui
```

虽然通过 qmd 检索时不一定需要 PrivateGPT 自己的 Embedding，但 PrivateGPT 的原生文件摄取 / RAG 功能仍可能需要配置 Embedding 模型。

---

##### 4. 在 PrivateGPT 中配置 qmd MCP

进入 Workbench UI，找到类似以下位置：

```text
Settings / Connectors / MCP
```

创建一个 MCP Connector：

```text
Name: qmd
URL:  http://127.0.0.1:8090/sse
```

如果网关提供的是 Streamable HTTP，则填写：

```text
http://127.0.0.1:8090/mcp
```

保存后检查 PrivateGPT 是否成功发现 qmd 暴露的工具。具体工具名称取决于 qmd 版本，可能包括搜索、查询、读取文档等工具。

在聊天中启用 qmd Connector，然后测试：

```text
请使用 qmd 搜索我的 Markdown 知识库，
查找所有与 PrivateGPT 部署有关的内容。
回答时标注来源文件路径。
```

为了避免模型跳过工具，可以使用更明确的提示词：

```text
回答前必须先调用 qmd MCP 工具搜索本地 Markdown 文档。
只能依据检索结果回答；如果没有找到，请明确说明没有找到。
回答末尾列出引用的文件路径。
```

#### 通过 PrivateGPT API 调用

PrivateGPT 参考 Claude Messages API，远程 MCP 通常可以通过`mcp_servers`传入。

示意请求：

```bash
curl -N http://localhost:8080/v1/messages \
  -H "content-type: application/json" \
  -H "anthropic-version: 2023-06-01" \
  -d '{
    "model": "你的模型名称",
    "max_tokens": 1500,
    "messages": [
      {
        "role": "user",
        "content": "必须先使用 qmd 搜索本地文档，然后回答：PrivateGPT 应该如何部署？回答中列出来源文件路径。"
      }
    ],
    "mcp_servers": [
      {
        "type": "url",
        "name": "qmd",
        "url": "http://127.0.0.1:8090/sse"
      }
    ]
  }'
```

如果你的 PrivateGPT 版本要求 MCP beta header，可以补充：

```bash
-H "anthropic-beta: mcp-client-2025-04-04"
```

不同版本的字段、Header 或 MCP transport 可能略有差异。最准确的办法是在 Workbench 的**API Debugger**中成功调用一次，然后复制它生成的请求。

---

#### Docker 网络注意事项

如果 PrivateGPT 运行在 Docker 中，而 qmd MCP 网关运行在宿主机，那么容器里的：

```text
127.0.0.1
```

指向的是 PrivateGPT 容器本身，不是宿主机。

macOS/Windows 通常使用：

```text
http://host.docker.internal:8090/sse
```

Linux Docker 可以增加：

```yaml
extra_hosts:
  - "host.docker.internal:host-gateway"
```

然后同样使用：

```text
http://host.docker.internal:8090/sse
```

另外，网关需要监听容器可以访问的地址，而不仅是`127.0.0.1`。如果 supergateway 支持 host 参数，可设置为：

```text
0.0.0.0
```

但不要把未认证的 MCP 服务直接暴露到公网。qmd 能读取本地文档，暴露服务意味着可能泄露文件内容。

生产环境更适合：

- 将 qmd 和 PrivateGPT 放进同一个 Docker 网络；
- 只允许 PrivateGPT 访问 qmd；
- 为 MCP 网关增加认证；
- 对 qmd 可索引目录使用只读挂载；
- 不对公网开放 qmd MCP 端口。

---

#### 方案二：应用端先调用 qmd，再调用 PrivateGPT

如果你使用的本地模型工具调用能力较弱，或者 MCP 接口暂时不兼容，可以采用更稳定的 “两阶段检索”。

流程：

```text
用户问题
   ↓
应用执行 qmd query
   ↓
得到 Markdown 片段和文件路径
   ↓
作为上下文发送给 PrivateGPT
   ↓
模型生成最终答案
```

Python 示例：

```python
import subprocess
import requests

question = "PrivateGPT 应该如何部署？"

result = subprocess.run (
    ["qmd", "query", question],
    capture_output=True,
    text=True,
    check=True,
)

context = result.stdout

payload = {
    "model": "你的模型名称",
    "max_tokens": 1500,
    "messages": [
        {
            "role": "user",
            "content": f"""
请仅根据下面由 qmd 检索出的资料回答问题。
如果资料不足，请明确说明。
回答时保留文件名或文件路径作为引用。

问题：
{question}

qmd 检索结果：
{context}
""",
        }
    ],
}

response = requests.post (
    "http://localhost:8080/v1/messages",
    headers={
        "content-type": "application/json",
        "anthropic-version": "2023-06-01",
    },
    json=payload,
    timeout=120,
)

response.raise_for_status ()
print (response.json ())
```

这种方式的优点：

- 不依赖模型是否会正确调用工具；
- 调试简单；
- 可以控制返回数量、上下文长度和文件白名单；
- 很容易做缓存和权限过滤。

缺点是它不是完全 Agentic：每次都先搜索，而不是由模型自主决定是否搜索。

---

#### 方案三：把 qmd 封装成 PrivateGPT Custom Tool

如果不想使用 MCP，可以写一个服务端工具，例如：

```python
def search_markdown (query: str) -> str:
    result = subprocess.run (
        ["qmd", "query", query],
        capture_output=True,
        text=True,
        check=True,
        timeout=30,
    )
    return result.stdout
```

向模型暴露为：

```json
{
  "name": "search_markdown",
  "description": "搜索本地 qmd Markdown 知识库并返回相关文档片段和路径",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "需要搜索的问题或关键词"
      }
    },
    "required": ["query"]
  }
}
```

这种方案可以增加：

- 用户级目录权限；
- 查询日志；
- 超时控制；
- 最大返回字数；
- 文件路径脱敏；
- Collection 白名单；
- 查询结果缓存。

但实现和维护成本高于直接使用 MCP。

---

#### 不建议重复维护两套索引

PrivateGPT 自身已经有文件摄取和 RAG，qmd 也维护 Markdown 索引。通常不要把同一批文件同时交给二者索引，除非有明确需求，否则会带来：

- 重复占用磁盘和计算资源；
- 文档更新不同步；
- 搜索结果不一致；
- 引用格式不同；
- 难以判断实际使用的是哪一个检索系统。

可以从下面两种模式中选择。

##### 模式 A：qmd 负责 Markdown 检索

适合已经用 qmd 管理笔记、代码文档或知识库的情况：

```text
Markdown → qmd 索引 → MCP → PrivateGPT
```

PrivateGPT 主要负责模型和 Agent 编排。

##### 模式 B：PrivateGPT 原生 RAG

适合需要处理 PDF、Office 文档、上传文件和统一引用管理的情况：

```text
文件 → PrivateGPT ingestion → PrivateGPT RAG
```

此时不需要 qmd。

也可以进行分工：

- Markdown、代码库文档、个人笔记：qmd；
- PDF、Word、上传附件、企业材料：PrivateGPT 原生 RAG；
- 在系统提示词中告诉模型如何选择工具。

---

#### 实际推荐

如果只是本机试验：

1. qmd 建立 Markdown 索引；
2. 运行`qmd mcp`；
3. 用 supergateway 转成 HTTP/SSE；
4. 在 PrivateGPT Workbench 添加 MCP Connector；
5. 使用工具调用能力较好的本地模型；
6. 提示模型在回答前调用 qmd，并输出文件路径。

如果用于生产：

1. qmd 与 PrivateGPT 分别部署为服务；
2. 通过内网 MCP HTTP 接入；
3. 增加认证、目录权限和查询审计；
4. 限制 qmd 能访问的文件范围；
5. 对检索结果做长度限制和 Prompt Injection 防护；
6. 对工具调用失败设置应用端检索兜底。

核心结论是：

> **不要把 qmd 当作 PrivateGPT 的模型或 Embedding 后端；应当把 qmd 当作一个本地知识检索工具，通过 MCP 接入 PrivateGPT。**

## 口播总结（1）

### 2026-08-03 01:25:46

#### 这是什么：给本地模型补上“应用层”

这份材料介绍的是开源项目 PrivateGPT。简单来说，它不负责训练或运行大模型，而是连接本地模型服务器，为开发者提供一整套构建私有 AI 应用所需要的接口和功能。

听完这份介绍，你可以了解三件事：PrivateGPT解决什么问题，怎样把它和本地模型搭配起来，以及它与完整的企业级 AI 平台 Zylon 有什么区别。

##### 首先，PrivateGPT解决的是“模型之上怎么做应用”

核心结论是：只把模型运行在本地，还不等于拥有一个真正可用的 AI 应用。

通俗地说，Ollama、llama.cpp、vLLM 这类工具，主要解决的是“怎样运行模型”。但一个完整的应用还需要处理文件上传、知识库检索、工具调用、数据库查询、用户请求、流式输出等问题。

PrivateGPT提供的，就是这一层公共能力。它是一个开源的 AI 应用 API 层，允许开发者在本地模型之上，构建聊天助手、知识库问答、智能代理、数据分析工具，甚至企业内部的私有 AI 产品。

它的 API 参考了 Claude，也就是 Anthropic 的 AI 接口规范。这样一来，开发者可以使用比较标准化的消息接口，而不必为每个本地模型服务重新开发一套后端。

PrivateGPT已经在 Zylon 的企业级本地 AI 平台中经过生产环境验证。也就是说，它不只是一个实验脚本，而是被用于真实的企业 AI 基础设施。

##### 接下来，理解它和模型服务器的关系

核心结论是：PrivateGPT本身不运行大模型，它负责连接外部的、兼容 OpenAI 接口的推理服务器。

这里的“推理服务器”，可以理解为真正加载模型、接收问题并生成答案的软件。常见选择包括 Ollama、llama.cpp、vLLM、LM Studio 和 LocalAI。

只要这个服务器支持两个基本接口：一个是聊天接口，另一个是模型列表接口，PrivateGPT通常就可以连接使用。连接地址通过环境变量 `OPENAI_API_BASE` 配置。嵌入模型，也就是把文字转换成向量、帮助系统进行搜索的模型，则可以通过单独的地址配置。

所以，两者的分工很清楚：

第一层，是 Ollama 或 vLLM 这样的本地推理层，负责运行模型。

第二层，是 PrivateGPT 这样的应用 API 层，负责把模型变成可以被程序、代理和工作流使用的 AI 能力。

例如，材料给出的入门方案是使用 Ollama。用户可以准备一个大约二十四 GB 的三百五十亿参数级别模型，同时准备一个大约六百七十 MB 的嵌入模型。然后启动 Ollama，再让 PrivateGPT指向对应的接口地址。

这说明，PrivateGPT并不替你解决硬件问题。你仍然需要准备能够运行模型的机器，以及相应的显存、内存和存储资源。

##### 然后，看看它提供了哪些核心能力

核心结论是：PrivateGPT把构建本地 AI 应用时最常见的基础模块集中到了一个 API 中。

第一类能力，是标准消息接口。它支持普通对话、流式输出，也就是边生成边返回内容；支持异步处理，还支持统计输入和输出的 token 数量。Token 可以简单理解为模型处理文字时使用的基本计量单位。

第二类能力，是文件和知识库处理。用户可以上传文件、PDF 和其他文档，系统能够提取内容，建立嵌入，并进行检索。

其中一个重要功能叫 RAG，中文通常称为“检索增强生成”。它的意思是：模型回答问题前，先从用户提供的资料中找相关内容，再根据这些内容组织答案。PrivateGPT还支持带引用的检索，让回答能够指出依据来自哪些资料。

它还支持“智能代理式 RAG”。也就是说，系统不只是机械地搜索一次，而是可以根据问题拆分任务、选择检索方式，再逐步生成答案。

第三类能力，是工具调用。PrivateGPT内置了类似 Claude 的工具，包括网页搜索、网页内容抓取和代码执行。开发者也可以接入自定义工具，让模型调用企业内部的服务。

第四类能力，是数据访问。它可以连接数据库，对数据库进行查询；也可以处理 CSV 等表格数据，并结合代码执行完成分析。

此外，它还提供嵌入模型管理和流程编排能力，并支持结构化输出。所谓结构化输出，就是让模型按照预先规定的字段和格式返回结果，而不是只输出一段散文。

##### 更重要的是，它可以连接代理、工具和外部系统

核心结论是：PrivateGPT不只服务于聊天窗口，也可以作为各种 AI 代理和开发工具背后的本地后端。

它支持 MCP。MCP 可以理解为一种让 AI 统一连接外部工具和数据源的协议。PrivateGPT既能接入远程 MCP 服务器，也能把 MCP 能力放到自己的 API 中。

它还支持 skills，也就是可以复用的任务技能或操作流程。不过材料说明，这部分目前属于基础支持，仍然不是完全成熟的能力。

在兼容性方面，PrivateGPT已经覆盖了现代 AI 应用 API 中的大部分基础功能，包括模型选择、消息接口、流式响应、批量或异步处理、文件导入、文档检索、引用、工具调用、数据库查询、表格分析、MCP、结构化输出和扩展思考等。

但也有几项限制需要注意。

技能能力目前只是基础支持。视觉能力取决于所连接的模型是否支持图像理解。结构化输出同样取决于底层模型的能力。另一方面，PrivateGPT目前不支持提示词缓存，也不支持 Claude API 中与组织管理相关的 OAuth 和组织功能。

这意味着，它更适合做本地、私有、开发者主导的 AI 应用后端，而不是直接复制云端平台的全部企业账户体系。

##### 再看它自带的工作台界面

核心结论是：PrivateGPT提供了一个方便测试和演示的网页界面，但真正的产品核心是 API。

安装并启动后，用户可以在本机的八零八零端口访问服务，在 `/ui` 路径打开工作台。

这个界面可以用来发送消息，选择模型，上传文档，测试带引用的检索，按对话启用不同工具，还可以配置数据库、MCP 连接器、技能和自定义工具。

它还提供 API 调试器，用来查看请求和响应。这对于开发者排查问题、理解接口行为很有帮助。

不过，官方特别强调，这个界面不是 PrivateGPT 的核心产品。它更像一个打磨得比较好的演示工具，适合视频演示、内部试点和快速本地使用。

如果要做正式产品，开发者应该直接基于 PrivateGPT API，开发自己的应用、代理、工作流或用户界面。

##### 接下来，看看它能接入哪些现有工具

核心结论是：许多原本支持本地 OpenAI 兼容模型的工具，也可以把 PrivateGPT当作本地后端。

材料列举的集成对象包括 Claude Desktop，也就是 Claude 的桌面应用；Cowork；Microsoft Word、Excel、Outlook 和 PowerPoint 的 Claude 插件；n8n 工作流平台；OpenCode；以及一些代码工具和开发环境。

具体来说，Claude Code 可以使用本地模型作为终端里的智能编程后端。Claude Desktop 和 Cowork 可以连接到私有模型。Microsoft 365 相关工具则可以在 Word、Excel、Outlook 和 PowerPoint 中使用私有 AI。

另外，n8n、OpenClaw、Hermes Agent、Visual Studio Code 和 Cline 等工具，也属于可以配合本地 OpenAI 兼容服务使用的生态。

因此，PrivateGPT的价值不只是“自己提供一个聊天页面”，而是把本地模型接入开发者已经在使用的代理、编辑器和自动化系统。

##### 然后，回到项目的起点

核心结论是：PrivateGPT起初只是一个离线文档问答脚本，后来才发展成完整的 AI 应用 API 层。

这个项目开始于二零二三年。当时它只是一个让用户和本地文档聊天的小脚本，所有数据都可以留在自己的机器上，不依赖云服务。

这项早期项目后来在 GitHub 上迅速传播，获得了超过五万颗星，也成为当年最受关注的人工智能项目之一。

这个结果说明，用户对“真正私有、可以本地运行、没有云端依赖的 AI”有很强的需求。

PrivateGPT 1.0 的方向，就是在这个基础上重新构建。它不再只是一个文档聊天工具，而是试图回答更进一步的问题：

模型已经运行起来之后，怎样围绕它开发一个真正有用的 AI 应用？

##### 更进一步，理解它与其他项目的区别

核心结论是：PrivateGPT是 API 优先，而不是应用优先。

Ollama、LM Studio、LocalAI、vLLM 和 llama.cpp，主要属于本地推理层。它们负责让模型运行起来。

Onyx 和 Open WebUI，则更像可以直接使用的自托管 AI 应用，重点是聊天和企业搜索。

PrivateGPT处在这两类项目之间，但角色不同。它不是最终面向普通用户的聊天产品，也不是单纯的模型运行工具，而是为开发者提供标准化后端的应用层。

可以把它理解成：你用喜欢的推理服务器运行模型，再把 PrivateGPT接在上面；之后，自己的应用、代理和工作流通过 PrivateGPT提供的接口使用这些模型能力。

##### 最后，区分 PrivateGPT 和 Zylon

核心结论是：PrivateGPT提供开源的本地 AI 应用层，而 Zylon提供围绕它构建的完整企业级 AI 基础设施。

PrivateGPT本身主要负责消息处理、文档导入、工具调用、检索、引用、数据库访问、表格分析、MCP、技能和自定义工具。

Zylon则是在这个基础上，继续补充企业真正需要的部署、治理和运维能力。

例如，Zylon集成了基于 NVIDIA Triton 和 vLLM 的推理服务，用来运行开放权重模型。它还提供并发处理、批量处理和负载均衡，帮助系统在更大规模下运行。

在部署方面，Zylon支持自包含的 Kubernetes 部署，并打包和维护二十多个生产服务。它还提供安装、更新、模型选择和平台配置所需的命令行工具。

在企业管理方面，Zylon包括 API 网关、工作区应用、LDAP 和 Active Directory 集成、基于角色的权限管理，也就是 RBAC。

在运维与合规方面，它提供遥测、可观测性、运行监控，以及用于审计和合规的 SIEM 日志。

在数据连接方面，它可以接入 SharePoint、Confluence、FTP 和 Samba。它还支持完全隔离的环境，也就是不连接外部云服务的 air-gapped 部署。

此外，Zylon还集成了 n8n 社区版，用于工作流自动化。

所以，如果目标是获得一个开源的本地 AI 应用 API，PrivateGPT就比较合适。

如果需求还包括企业级部署、权限治理、用户管理、系统监控、数据连接、审计、隔离运行和商业支持，那么对应的是 Zylon 这样的完整平台。

##### 结尾：四点记住 PrivateGPT

最后，可以把整份材料浓缩成四个结论。

第一，PrivateGPT不是大模型本身，也不负责直接运行模型。它连接 Ollama、vLLM、llama.cpp 等兼容 OpenAI 接口的推理服务器。

第二，它的核心价值是提供本地 AI 应用所需要的公共能力，包括消息接口、文档导入、RAG 检索、引用、工具调用、数据库查询、表格分析、MCP 和自定义工具。

第三，它是 API 优先的开发者基础设施。自带的网页工作台适合测试、演示和内部试点，但正式产品通常应该建立在它的 API 之上。

第四，PrivateGPT与 Zylon的定位不同。PrivateGPT是开源的应用 API 层；Zylon则在它之上提供面向企业的部署、治理、运维、集成和合规能力。

## 深度解读（1）

### 2026-09-18 00:29:21

#### PrivateGPT 的真正机会：成为本地 AI 栈的“应用接口层”

PrivateGPT 最值得关注的变化，不是又增加了 RAG、MCP 或代码执行，而是它重新定义了自己在技术栈中的位置：**不负责运行模型，也不直接做最终应用，而是填补两者之间长期被低估的一层。**

Ollama、llama.cpp、vLLM 解决“如何在本地提供模型推理”；聊天、知识库和办公助手解决具体场景；PrivateGPT 则把消息、文档摄取、引用检索、工具调用、数据库查询、结构化输出等能力封装成统一 API。它实际上提出了一个判断：随着基础模型和推理服务器逐渐可替换，真正反复消耗开发成本的，会是模型之上的应用基础设施。

##### 两套兼容接口，构成一个可替换的中间层

项目的边界设计很有意思：向下连接任何支持 `/v1/chat/completions` 和 `/v1/models` 的 OpenAI 兼容推理服务，向上则参考 Claude API，为应用提供消息、工具、文件和 MCP 等接口。

这使上下两端能够分别演进。企业可以从 Ollama 换到 vLLM，或者更换具体模型，而不必重写应用；现有的 Claude Desktop、Microsoft 365 插件、n8n 和编码工具，也有机会改接私有后端。**它卖的不是某个模型的能力，而是迁移自由和集成复用。**

但兼容性本身并不自动形成护城河。项目列表中的视觉、结构化输出等能力仍取决于底层模型，工具调用在不同模型上的可靠性也可能差异很大。真正需要验证的不是“接口能否接通”，而是切换模型后，任务质量、延迟、错误处理和权限边界能否保持稳定。

##### “本地运行”与“企业可用”之间仍有巨大距离

README 对开源版与商业版 Zylon 的划分，反而揭示了这个市场最真实的成本。PrivateGPT 提供开发原语；Zylon 收费解决 Kubernetes 部署、并发与负载均衡、身份权限、审计日志、监控、企业数据连接器和离线运维。

这说明企业购买“私有 AI”，通常不是为了把请求从云端移到一台本地机器，而是为了获得**可治理、可审计、可持续运行的完整系统**。即使模型完全本地化，只要开启网页搜索、远程 MCP 或外部工具，数据仍可能越过安全边界。因此，“私有”最终是一套数据流和权限策略，而不是部署地点。

这也解释了其开源商业模式：用 API 层降低开发者试用门槛，再在组织部署与治理环节收费。50K GitHub stars 能证明开发者兴趣，却不能直接证明受监管企业的付费需求；“已用于全球企业”的说法也缺少客户规模和运行指标，仍应视为厂商主张。

##### 值得跟踪的是控制点，而非功能清单

如果本地模型继续成熟，这类中间层可能成为新的基础设施控制点：上层产品不再绑定某家模型厂商，下层推理也被标准接口商品化。对产品团队而言，最值得验证的需求不是再做一个本地聊天 UI，而是：**组织是否愿意围绕统一 API 建立模型切换、工具授权、数据访问和审计机制。**

PrivateGPT 已经把这些问题放进了同一张架构图，但尚未证明自己会成为标准答案。它的价值在于准确指出：本地 AI 的主要瓶颈，正在从“模型能否跑起来”转向“应用能否被可靠、安全地长期运行”。
