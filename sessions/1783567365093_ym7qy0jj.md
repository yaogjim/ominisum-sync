- **核心高价值点**：将Agent Mode拆成“身份与发现”和“页面到代理通信”两层，精准补足Web Bot Auth与WebMCP之间的空白。
- **留存建议**：长期保留，适合作为AI Agent浏览器交互和代理原生Web设计的参考材料（提出了较完整的代理原生Web分层框架，涵盖身份声明、能力发现、页面到代理通信和权限治理，具有较高长期参考价值）

**知识要点**

- Web Bot Auth解决服务器侧代理身份验证，但页面JavaScript通常无法感知代理身份
- WebMCP主要支持代理调用页面暴露的工具，但不解决页面主动请求代理的问题

- Agent Mode Layer 2设想通过navigator.agentMode.request实现页面向代理发送结构化任务并接收结果
- 页面到代理的通道需要模式开启、站点授权和代理审批循环三重安全门控

**行动项**

- 跟踪WebMCP、Web Bot Auth和相关浏览器Agent API的标准进展
- 为自己的Web应用梳理代理访问场景，设计可供Agent读取的发现文件和低摩擦路径
- 评估现有工具中依赖复制粘贴、截图点击、MCP私有桥接的流程，寻找可标准化的接口
- 在内部原型中尝试实现简化版Agent-Mode头部、能力发现文件和页面内代理请求按钮

## 正文

#### 代理模式：代理原生网络

*一个稻草人提案，使得代理浏览器能够向网站表明自身身份，网站可以回应，并且你可以在不离开页面的情况下，将代理工作交给代理处理。*

**TL;DR**

- 现在，代理通过内置浏览器（Codex、Claude Code、Cursor）浏览网页，但对每个网站而言，它们看起来就像使用鼠标的人类用户：网页无法分辨、无法适应，也无法回应。每一个需要桥梁的工具都会自行破解。
- **Agent Mode** 是一个包含两个层次的试探性提案。第一层：浏览器宣告代理（一个 `Agent-Mode` 头部加上 `navigator.agentMode`），网站通过一个功能发现文件（CLI、MCP 服务器、待安装的技能）进行响应。第二层：页面在每个网站权限和代理自身的审批循环之后，将工作（“起草这封邮件的回复”）交给代理处理，响应随后返回页面。
- 要求：代理制造者交付第一层（一个工作冲刺周期），应用开发者发布其发现文件，工具开发者聚焦于共享界面。

#### 1\. The weird relay

如果你关注过 Dan Shipper 的 Codex 原生应用，你已经看到了这个方向：在代理内部运行而非在其旁边运行的应用。如果你自己尝试过，构建自己的应用并在 Codex、Claude Code 或 Cursor 中运行，你也会遇到这个缝隙。它会以微小的形式出现。

你可能在过去一周内做过这样的事情。一个代理正在构建你的应用，它内部的浏览器（从 Codex、Claude Code 或 Cursor 内部驱动的那个）正指向它刚刚修改过的页面。你正在查看同一个页面。定价卡片下方的间距有问题，于是你切换到终端，向一个模型输入“定价卡片下方的间距不对，按钮下方的第二个（间距）”，而该模型在它控制的浏览器中打开了这些确切像素的截图。

双方正在看着同一样东西，你正在向其中一方用散文的形式描述它。代理有眼睛。页面有结构。他们之间没有握手，所以人类玩起了传话游戏。

中继并非小众的困扰，因为代理内置浏览器正成为默认界面。Claude Code 驱动一个代理，光标驱动一个代理，Codex 打开你的应用以检查自身工作。对于它们访问的每个页面，这些代理都与使用鼠标的人难以区分：页面渲染出人类界面，代理截图，按坐标点击，滚动，再次截图。这是一台为了无人受益而模仿人类的机器。

工具已经开始注意到这一点。现在大多数开发工具都包含某种设计注释模式：在代理浏览器中指向一个元素，输入注释，反馈就会进入代理的上下文。这些功能确实有效，它们有效的原因正是中继的弊端所在：你直接与内容交互，而不是描述它。但每一种都是单一供应商的构建版本，仅集成到一个浏览器中，只为单一用途（设计反馈）服务。那扇门后还有更多内容。

我认为这个解决方案是一种背后有标准支撑的模式：浏览器宣告有代理正在运行，而页面获得一个用于回应的通道。标注不再是各厂商专属的特性，而是成为共享接口的一种应用。本文的其余部分就是本提案。

如果你想找到人们需要页面到代理路径的证据，看看现在有多少人正在手动构建这个路径。

- **DialKit** (Josh Puckett) 在您的页面上添加一个实时调试面板：在浏览器中调整弹簧、缓动函数和颜色，然后通过将提示复制到您的代理中来带回这些值。
- **Agentation**（Benji Taylor）是一个用于实时页面的注释工具栏：点击一个元素，输入反馈，获取带有代理可 grep 的真实 CSS 选择器的 Markdown 内容。它附带一个可选的 MCP 服务器以实现实时同步。
- **Impeccable** (Paul Bakaus) 是一个设计质量卓越的工具，其实时模式会向你的页面注入脚本，因此你可以点击任何元素并以通俗的语言请求变更。
- **RiffRec**（我的）记录一个产品会话：屏幕、旁白、点击、控制台错误、网络结果，写入本地文件供代理后续解析。
- **ui.sh**（Tailwind CSS 团队）将设计风格植入代理所在的终端，并在你正在运行的应用程序中嵌入一个反馈小部件，以便你可以在应用程序内部指向设计。

统计这些传输方式：复制粘贴、每个工具的 MCP 服务器、注入的本地主机脚本、磁盘文件、嵌入式小部件。没有共享的，也没有标准的。列表中的任何工具都无法检测到代理正在查看页面，也无法向代理推送消息；每个人都在独自构建相同的桥梁。这就是标准出台前一年的生态系统的样子。

#### 3\. 两个标准，以及它们之间的差距

你可能会觉得这已经被涵盖了。附近有两项重大的努力正在进行。

**Web Bot Auth** 是 HTTP 层的身份验证。由 Cloudflare 主导的一组 IETF 草案（得到 OpenAI、Amazon 和 Akamai 的支持），其验证功能已在 Cloudflare 的边缘节点运行：代理通过密码学方式对出站请求进行签名（RFC 9421 消息签名；`Signature-Agent` 头指向签名者的公钥目录），因此服务器可以验证“这确实是 OpenAI 的代理”，而非信任可伪造的用户代理字符串。这就像边境的护照检查，真实且正在运行，但对页面不可见：签名在边缘或源站进行验证，当你的 JavaScript 运行时，身份验证过程已完成。DialKit 无法询问 CDN 谁在浏览。

**WebMCP** 是页面层的能力。这是谷歌和微软工程师提出的 W3C 提案，目前正在 Chrome 原型试用中：你的页面调用 `navigator.modelContext.registerTool()` 来暴露结构化工具（“search\_flights”、“add\_to\_cart”：一个名称、一个 JSON 模式和一个执行回调函数），而浏览器内的代理会调用这些工具，而非通过截图点击你的用户界面。这就像网页中的服务柜台。但方向是固定的：代理调用页面。页面直到工具触发才会知道代理的存在，并且它无法发起对话。

不同的层级、不同的标准机构，彼此之间没有相互参考。而在它们之间，未被揭示的是第2节中每个工具都在努力实现的工作流：

1. **没有页面能够检测到客户端代理。** 身份存在于服务器看到的头部信息中；页面的 JavaScript 无法获取到任何内容。
2. **没有页面可以向代理发送请求**代理可以调用已注册的工具；页面永远无法发起。

(相邻的规范也不涵盖它：llms.txt 让爬取器指向内容，AGENTS.md 向代码代理介绍一个仓库。代理读取的是文件，而非实时页面可使用的频道。)

#### 4\. 第一层：浏览器承认它

那么，这就是一个初步构想。代理模式有两个层次，第一个层次刻意设计得比较小：身份与发现。在实际中，它的表现如下：

代理模式需用户主动开启，且按会话生效。它并非持续开启，因此无法转为拦截状态；由用户或其管理策略决定是否开启。当开启时，会发生三件事：

- **请求携带一个头部信息。** 就像……一样简单 `Agent-Mode: on; agent="Claude-code"; interactive=true`. 当涉及加密证明时，它可以与 Web Bot Auth 签名一起使用；这里的重点不是证明，而是服务器可以适应的声明性上下文。
- **页面接收到一个信号。** 一个 `navigator.agentMode` 属性（代理名称、版本、是否有人在场）加上一个变化事件。前端代码终于可以分支：来自边界的身份到达车间。
- **网站可进行回应。** 一个发现文件，例如 `/.well-known/agent-mode.json`，其中网站声明其代理能力：这里是我们的 CLI，这里是我们的 MCP 服务器，这里是您的代理可以安装的一项技能，这里是跳过营销介绍的路径。代理在到达时会读取该文件，而不是从像素中推断所有内容。

网站在第一天会如何使用这个功能？去掉 Cookie 横幅和引导流程，转而渲染信息密集视图而非动画视图。预发布应用可以为来访的 Agent 提供测试凭证。文档网站可以提供一项技能而非 README 文件：在 Agent 模式下浏览 DialKit，你的 Agent 离开时已经知道如何连接它。

两种担忧，定价诚实。网站能否利用这个信号来屏蔽代理？它们已经在尝试了，通过用户代理嗅探（user-agent sniffing）和机器人启发式方法（bot heuristics）；诚实模式（honest mode）并没有增加太多屏蔽能力，它主要是终结了伪装。这会不会变成监视？它识别的是代理主动声明的模式，而非个人；这里没有任何可以用来识别人类身份的信息。真正的权衡是，处于代理模式的代理会放弃隐蔽性，而隐蔽性从来都不是构建工具的基础。

Layer 1 is boring on purpose: a header, a navigator property, a JSON file. A vendor could ship it in a sprint, which is the point.

#### 5\. 第2层：页面获得语音

仅检测不会删除中继。页面现在可以向代理打招呼；但它仍然无法说任何有用的内容。第二层是通道：页面向驱动它的代理发送结构化请求。流程，在细节之前：

稻草人 API 是一个调用：

```
const reply = await navigator.agentMode.request({
  intent: "draft-reply",
  summary: "Draft a response to this email thread",
  context: { thread, tone: "brief" }
});
```

使用 JavaScript 和 React SDK（`useAgent()`）作为人们构建的工具的语法糖。这 `await` 很重要：通道是往返的。当代理完成时，响应会返回页面，这样应用就能根据答案采取行动，而不是指望工作在屏幕外的某个地方完成。通过它传递的内容是什么：

- **Cora** 在电子邮件对话线程中放置一个“让你的代理生成回复”按钮：该应用将对话线程和请求交给用户自己的代理处理，而不是运行其自身的模型或要求你粘贴相关上下文。当代理完成后，草稿会重新回到撰写框中。
- **Agentation's** 注释不再是剪贴板搬运的内容：你标记实时页面，反馈会附带选择器信息进入代理的队列。这就是第 1 节中的中继，已删除。
- **DialKit** 新增了一个“应用”按钮：你在浏览器中调整的弹簧常数会作为结构化的变更请求传递到代码库，而非粘贴的提示。

注意这种反转。WebMCP 允许代理调用页面；Layer 2 允许页面询问代理。它们是互补的，最终可能会整合到一个标准中；`navigator.modelContext`（其作者将基于事件的 `window.agent` 作为未来工作暂存）或独立存在，这是一场命名之争，而这个稻草人论点会欣然认输。

#### 6\. 你正在输入的异议

一个可以向你的代理发送请求的页面是一个带有精美 SDK 的提示注入漏斗。这是一个设计问题，而非一个脚注，因此 Agent Mode 表明立场：三个门，全部为强制性的。

1. **模式门。**Layer 2 在代理模式之外不存在。不存在环境暴露；是人类或其控制策略为本次会话开启了该功能。
2. **站点授权。** 页面按源请求通道，而中间件进行中介，就像今天摄像头和麦克风权限的工作方式一样。你的 agent 浏览器知道你授予了哪些站点权限，而其他所有都被拒绝。
3. **审批循环。** 每个请求都作为不可信输入到达，其权限不超过输入到代理提示框中的建议：它会经过与其他所有代理操作相同的权限和审批流程。不会仅凭页面的说法执行任何操作。

那就是纵深防御，而这也伴随着一个妥协：这是一份设计契约，目前还没有人对其进行过实战检验。提示词注入在这里并未得到解决；它只是被遏制了。如果你想攻击稻草人，就从这里下手：这是最坚固的承重墙。

#### 7\. The ask

整个提案被简化为一个小小的第一步，这就是它可能真正发生的原因。

- **代理创建者** （Cursor、Anthropic、OpenAI、Google）：发布第一层。发送头部，暴露 `navigator.agentMode`，读取知名文件。这是一个工作冲刺，且它之上的每一层都阻塞在你这里。
- **应用开发者** : 发布发现文件并设计你的代理路径。决定访问代理应该看到、跳过和被告知的内容。你今天可以启发式地检测代理并适应得很差；当信号真实时，要准备好适应良好。
- **工具开发者** ：聚合。DialKit、Agentation、Impeccable、RiffRec 以及下个月推出的任何产品，每个都在维护一个私有桥接；瞄准一个共享界面，并将定制化传输作为备用方案。

这个讨论应该在哪里进行？说实话，完全开放。WebMCP 背后的 W3C 小组是最接近的“篝火”（即讨论聚集地），如果大家对此有共鸣，就可以跟进一个规范仓库。目前，这篇文章是一个稻草人提案，而请求是请你在公开场合将其彻底剖析。

网络为它曾遇到的每一位新读者发展出了相应的浏览模式：打印样式表、手机出现时的响应式视口、阅读模式、屏幕阅读器以及无障碍树。最新的读者每天出现上千次，投入真金白银，而我们却仍让它眯着眼睛看像素，假装是真人。代理模式就是网络在做它一直以来都在做的事，只是在适应读者需求上慢了一步。

## 结构化（1）

#### 《Agent Mode: The Agent-Native Web》精炼总结

文章提出一个“Agent Mode（代理模式）”草案：让浏览器中的 AI 代理能主动向网站表明“我是代理”，网站也能识别并提供适合代理使用的接口。核心目标是减少人类在网页、终端和代理之间反复复制、描述、转述的低效“中继”过程，让网页与代理直接协作。

---

##### 1. 当前问题：人类成了网页和代理之间的“调制解调器”

现在 Codex、Claude Code、Cursor 等工具中的代理会通过内置浏览器访问网页，但网站无法知道访问者是 AI 代理还是人类。

- 代理只能像人一样“看截图、点坐标、滚动页面”，网页也只能渲染给人看的 UI。
- 典型场景：代理正在修改网页，你也在看同一个页面；你发现“定价卡片下方间距不对”，却只能切到终端，用文字告诉代理。
- 实际上，代理已经“看见”页面，页面也有结构，但两者之间没有正式通信通道。

作者认为，这种模式很荒谬：**机器被迫模仿人类操作，却没有任何一方真正受益。**

---

##### 2. 生态现状：大家都在重复造“桥”，但没有标准

很多工具已经意识到网页到代理之间缺少通道，于是各自做了私有方案。

文中列举了多个案例：

- **DialKit（Josh Puckett）**  
  在页面中加入实时调试面板，用户调整动画弹簧、缓动、颜色后，再把提示复制给代理。

- **Agentation（Benji Taylor）**  
  提供页面注释工具栏，用户点击元素、写反馈，生成包含真实 CSS 选择器的 Markdown，方便代理 grep 和修改代码；还可选配 MCP 服务器同步。

- **Impeccable（Paul Bakaus）**  
  向页面注入脚本，让用户点击元素并用自然语言要求修改。

- **RiffRec（作者自己的工具）**  
  记录产品使用过程，包括屏幕、旁白、点击、控制台错误、网络结果，并写入本地文件供代理分析。

- **ui.sh（Tailwind CSS 团队）**  
  将设计风格带入代理所在终端，并在运行中的应用里嵌入反馈组件，让用户能直接在应用内指出设计问题。

这些方案使用的传输方式五花八门：复制粘贴、MCP 服务器、本地主机脚本、磁盘文件、嵌入式组件等。  
问题是：**没有一个共享标准，网站也无法检测到“代理正在访问页面”，更无法主动向代理发送请求。**

---

##### 3. 现有标准还不够：Web Bot Auth 和 WebMCP 各解决一半

作者指出，虽然已有两个相关标准方向，但都没有覆盖“页面主动和代理沟通”的需求。

###### Web Bot Auth：解决服务器识别代理，但页面看不见

- 由 **Cloudflare** 主导，属于 IETF 草案方向。
- 得到 **OpenAI、Amazon、Akamai** 等支持。
- 使用 **RFC 9421 HTTP 消息签名**，通过 `Signature-Agent` 头指向签名者公钥目录。
- 服务器可验证“这确实是 OpenAI 的代理”，而不是依赖容易伪造的 User-Agent。

但问题是：  
身份验证发生在 CDN 边缘或源站层，等页面 JavaScript 运行时，验证过程已经结束。  
所以网页前端代码仍然无法知道：**当前是不是代理在浏览。**

###### WebMCP：允许代理调用页面工具，但方向是单向的

- 由 Google 和微软工程师提出，属于 W3C 提案。
- 目前在 Chrome 中有原型试用。
- 页面可通过 `navigator.modelContext.registerTool()` 暴露工具，例如：
  - `search_flights`
  - `add_to_cart`

这样代理可以调用页面提供的结构化工具，而不是截图点击 UI。

但它的方向是：**代理调用页面**。  
页面不能主动发现代理，也不能主动向代理发起请求。

###### 文章指出的空白

现有体系缺少两件事：

1. 页面无法检测客户端是否有代理。
2. 页面无法向代理发起请求。

这正是 Agent Mode 想补上的缺口。

---

##### 4. Agent Mode 第一层：让浏览器承认“我是代理”

作者提出 Agent Mode 的第一层：**身份与发现**。  
设计刻意保持简单，目标是让厂商可以在一个开发冲刺周期内实现。

开启 Agent Mode 后，会发生三件事：

###### 1）请求携带代理模式头部

例如：

```http
Agent-Mode: on; agent="Claude-code"; interactive=true
```

它不是为了取代加密证明，而是给服务器一个明确上下文：  
当前访问者是代理模式下的浏览器。

如果需要强身份验证，也可以和 Web Bot Auth 配合。

###### 2）页面 JavaScript 能读取代理信号

浏览器暴露：

```js
navigator.agentMode
```

其中可包含：

- 代理名称
- 版本
- 是否有人类在场
- 状态变化事件

这样前端终于可以根据访问者是否为代理做不同处理。

###### 3）网站提供发现文件

例如：

```text
/.well-known/agent-mode.json
```

网站可在其中声明：

- 可用 CLI
- MCP 服务器
- 可安装技能
- 代理专用路径
- 跳过营销介绍或引导页的入口

###### 网站可以怎么用？

文章举例：

- 关闭 Cookie 横幅和新手引导。
- 给代理展示信息密集型页面，而不是动画丰富的人类界面。
- 预发布应用可给代理提供测试凭证。
- 文档站点可以直接提供“技能”，而不是让代理读 README 猜用法。

作者强调：  
**第一层故意很“无聊”——一个 header、一个 navigator 属性、一个 JSON 文件。正因为简单，才可能真正落地。**

---

##### 5. Agent Mode 第二层：让页面能“开口”请求代理

仅让页面知道“有代理”还不够，真正重要的是建立一个双向通道：  
**页面可以向正在驱动它的代理发送结构化请求，并等待代理返回结果。**

作者给出一个假想 API：

```js
const reply = await navigator.agentMode.request({
  intent: "draft-reply",
  summary: "Draft a response to this email thread",
  context: {
    thread,
    tone: "brief"
  }
});
```

这里的关键是 `await`：  
页面不是把任务扔出去就结束，而是等待代理完成后，把结果返回页面。

###### 示例 1：邮件应用 Cora

在邮件线程中，页面提供按钮：

> “让你的代理生成回复”

点击后：

- 页面把邮件线程和语气要求交给用户自己的代理。
- 代理生成草稿。
- 草稿返回页面并填入撰写框。

这意味着应用不必自己运行模型，也不需要用户复制上下文给代理。

###### 示例 2：Agentation 注释

用户在页面上标记元素并写反馈，反馈带着真实 CSS 选择器直接进入代理队列。  
原本“复制 Markdown 到终端”的步骤被删除。

###### 示例 3：DialKit 应用动画参数

用户在浏览器中调好参数：

- stiffness: 210
- damping: 18
- duration: 0.32s
- scale: 1.04

然后点击“应用”，这些结构化参数直接发给代理，由代理写入代码库。  
不再需要复制粘贴提示词。

作者认为，第二层与 WebMCP 是互补关系：

- WebMCP：代理调用页面。
- Agent Mode Layer 2：页面请求代理。

---

##### 6. 安全问题：页面请求代理可能变成提示注入入口

作者承认，页面向代理发送请求本质上可能成为“提示注入漏斗”。  
因此 Agent Mode 必须有强制安全边界。

文章提出三道门：

###### 第一门：模式门

Layer 2 只在 Agent Mode 开启时存在。  
必须由用户或管理策略为当前会话主动开启，不能默认暴露。

###### 第二门：站点授权

页面必须按来源申请权限，类似今天浏览器中的摄像头、麦克风权限。

- 某个站点被允许，才能向代理发送请求。
- 其他站点默认被拒绝。

###### 第三门：代理审批循环

页面发来的每个请求都被视为不可信输入。  
它不能直接执行操作，必须经过代理本身已有的权限和审批流程。

也就是说，页面说“请修改代码”并不等于代理会立刻修改代码。

作者坦率表示：  
这不能彻底解决提示注入，只是把风险限制在设计边界内。  
如果要攻击这个提案，安全机制就是最关键的承重点。

---

##### 7. 作者的呼吁：先实现第一层，再走向共享标准

作者最后把请求分成三类对象：

###### 对代理厂商

包括 Cursor、Anthropic、OpenAI、Google 等：

- 发布 Layer 1。
- 发送 `Agent-Mode` header。
- 暴露 `navigator.agentMode`。
- 读取 `/.well-known/agent-mode.json`。

作者认为这是一个“一个 sprint 可实现”的小步骤，但后续生态都依赖它。

###### 对应用开发者

- 发布自己的发现文件。
- 设计代理访问路径。
- 明确代理应该看到什么、跳过什么、被告知什么。

换句话说：不要再让代理从像素和人类界面里猜。

###### 对工具开发者

包括 DialKit、Agentation、Impeccable、RiffRec 等：

- 不要继续维护各自私有桥接。
- 应该共同瞄准一个共享接口。
- 自定义传输方式可以作为备用方案，而不是长期主路径。

---

##### 8. 总结：Agent Mode 是网页适应新“读者”的下一步

作者把 AI 代理视为网络的新型读者。  
过去网页已经适应过不同读者和设备：

- 打印样式表
- 移动端响应式布局
- 阅读模式
- 屏幕阅读器
- 无障碍树

现在，AI 代理每天大量访问网页，但网页仍然要求它们“眯着眼睛看像素，假装自己是真人”。

因此，Agent Mode 的本质不是给代理特权，而是让网页像过去适配手机、屏幕阅读器一样，开始适配 AI 代理这一新访问者。

## 口播总结（1）

### 2026-08-03 01:47:12

#### 代理模式：让网页真正适应代理

这篇文章提出了一个名为“Agent Mode，也就是代理模式”的试探性方案。它想解决一个越来越明显的问题：代理虽然能打开网页，却仍然被迫假装成人类，用截图、鼠标和坐标操作页面。接下来，我们会了解这种“中继”为什么低效，现有标准缺了什么，以及代理模式准备如何用两个层次把这条通道建立起来。

##### 一、现在的网页代理，像是在隔着人传话

首先，核心问题是：代理能看见网页，但网页不知道它面对的是代理；代理也没有一条直接的通道，把自己的工作结果交还给页面。

想象这样一个场景。一个代理正在帮你开发应用。它通过 Codex、Claude Code 或 Cursor 内置的浏览器，打开刚刚修改过的页面。你也在看同一个页面。你发现定价卡片下面的间距不对，于是切回终端，对代理描述：“按钮下面第二段间距有问题。”

代理确实有“眼睛”，可以截图。网页也有结构，知道哪些元素是什么。但两边没有握手，也没有共同的通信接口。于是，人类只能充当中继，把页面上的问题用自然语言转述给代理。

这就是文章所说的“奇怪的中继”：代理在浏览器里截图、点击、滚动，再截图；人类在旁边观察，然后把反馈复制到终端。机器明明可以直接处理信息，却被迫模仿使用鼠标的人类。

这个问题并不小众。越来越多的开发工具，都在内置浏览器中运行代理。代理会打开你的应用，检查自己的工作，但对每个网站来说，它看起来仍然和普通人类用户一样。网页只能渲染人类界面，代理只能从像素中猜测页面内容。

一些工具已经开始修补这条断裂的通道。比如，设计注释工具允许你在代理浏览器中指向某个元素、输入反馈，然后把反馈送回代理上下文。这样做有效，是因为你直接对页面内容进行操作，而不是靠文字描述页面。

但问题在于，这些能力都是各家工具单独实现的。它们通常只支持某一个浏览器，服务于某一个场景，比如设计反馈。文章认为，更好的方向应该是建立一个共享标准：浏览器主动声明“这里有代理正在运行”，网页获得一个可以回应的通道。

接下来，文章先用几个现有工具说明，这种需求已经真实存在。

##### 二、许多工具都在各自修建同一座桥

这一部分的核心结论是：生态里已经出现了很多“页面到代理”的桥梁，但它们彼此不通用，也没有统一标准。

通俗地说，大家都遇到了同一个问题：如何让代理知道页面上的具体元素、状态和反馈？只是每个团队都在用自己的方式解决。

比如，DialKit 提供实时调试面板。你可以直接在浏览器里调整动画的弹簧参数、缓动函数和颜色，然后把这些结果复制进代理。

Agentation 是一个实时页面注释工具。你点击某个元素，输入反馈，它会生成带有真实 CSS 选择器的 Markdown 内容。CSS 选择器，就是网页中用来精确定位元素的规则。这个工具还可以选择配合 MCP 服务器使用。MCP，也就是模型上下文协议，可以让代理与外部工具和服务交换结构化信息。

Impeccable 可以向页面注入脚本。你点击页面上的元素，用日常语言提出修改要求，代理就能据此处理。

RiffRec 记录完整的产品操作过程，包括屏幕、旁白、点击、控制台错误和网络结果，最后写成本地文件，供代理之后解析。

Tailwind CSS 团队的 ui.sh，则把设计风格带进代理所在的终端，同时在正在运行的应用里嵌入反馈组件。这样，用户可以直接在应用内部指出设计问题。

这些工具使用的传输方式各不相同。有的靠复制粘贴，有的靠各自的 MCP 服务器，有的注入本地脚本，有的写入磁盘文件，还有的依赖嵌入式组件。

这些案例说明，需求已经很明确。但它们也暴露出一个事实：没有共享接口。现有工具无法统一检测“代理是否正在查看页面”，也无法用标准方式向代理推送消息。每家公司都在独自建桥，而且桥只能连接自己的工具。

有了这些背景，下面就能看出，为什么现有的两个重要标准仍然没有完全解决问题。

##### 三、两个相关标准，各自解决了一半

更重要的是，当前已经有两项重要工作，但它们处在不同层次，彼此之间仍然存在空隙。

第一项是 Web Bot Auth。它解决的是 HTTP，也就是网页请求这一层的身份验证问题。

简单说，代理可以对发出的请求进行密码学签名。服务器据此验证：“这确实是某个代理提供商的代理”，而不是只相信一个容易伪造的用户代理字符串。这个方案由 Cloudflare 主导，形成了 IETF 草案，并得到 OpenAI、亚马逊和 Akamai 的支持。它使用了 RFC 9421 消息签名，`Signature-Agent` 头部则指向签名者的公钥目录。

这相当于在网络边境进行护照检查。身份是真实的，而且已经可以在 Cloudflare 的边缘节点运行。

但它的问题是：网页里的 JavaScript 看不到这个身份。请求在边缘节点或服务器那里完成验证，等网页代码开始运行时，身份信息已经留在服务器层了。像 DialKit 这样的页面工具，仍然无法询问 CDN：“现在是谁在浏览这个页面？”

第二项是 WebMCP。它解决的是页面能力这一层。

WebMCP 是谷歌和微软工程师提出的 W3C 提案，目前正在 Chrome 原型中试用。网站可以通过 `navigator.modelContext.registerTool()` 注册结构化工具。比如，网页可以提供“搜索航班”或“加入购物车”这样的工具，并为工具定义名称、JSON 数据格式和执行回调。JSON 是一种机器容易读取的数据格式。

这样，浏览器里的代理就能直接调用网页提供的工具，而不是靠截图和坐标点击。它更像是网页为代理准备了一个服务柜台。

但 WebMCP 的方向是单向的：代理可以调用网页上的工具，网页却不能检测代理是否存在，也不能主动向代理发起请求。

所以，两个标准之间形成了一个缺口：

- Web Bot Auth 让服务器知道代理是谁，但页面 JavaScript 看不到这个身份。
- WebMCP 让代理调用页面工具，但页面不能主动找到代理，更不能请代理处理任务。
- `llms.txt` 可以告诉爬取器去哪里找内容。
- `AGENTS.md` 可以向代码代理介绍一个代码仓库。

但这些都不是实时网页和代理之间的双向通道。代理读到的是文件，页面仍然无法在运行过程中直接呼叫代理。

文章提出的 Agent Mode，正是想把这两个缺口连接起来。

##### 四、第一层：让浏览器承认“代理正在这里”

代理模式的第一层，核心结论是：先不要急着让网页控制代理，只要让浏览器和页面知道“代理正在运行”，并让网站提供适合代理使用的入口。

它刻意设计得很小，只有三个基本部分。

首先，请求中携带一个声明代理模式的头部。可以把它理解成一句简单的自我介绍，例如：“代理模式已开启，这是 Claude Code，当前有人类用户在场。”

其次，页面可以读取一个 `navigator.agentMode` 属性。这里的 `navigator` 是浏览器提供给网页的环境接口。这个属性可以包含代理名称、版本，以及是否有人类在场等信息。页面还可以监听变化事件，知道代理模式是否被打开或关闭。

最后，网站提供一个发现文件。文章建议使用类似 `/.well-known/agent-mode.json` 的地址。这个文件就像网站给代理准备的说明卡，里面可以写清楚：

- 网站提供哪些命令行工具，也就是 CLI；
- 有没有 MCP 服务器；
- 有没有可以安装的技能；
- 代理应该走哪个更直接的页面入口。

代理打开网站时，就不必只靠截图和像素猜测，而是可以先读取这份说明。

这样一来，网站就能根据代理模式做出更合适的回应。比如，它可以去掉 Cookie 横幅和新手引导，把动画化的展示页面换成信息更密集的版本。预发布应用可以给代理提供测试凭证。文档网站也可以直接提供一项可安装的技能，而不是只展示一份 README 文件。

文章还举了一个假想的邮箱应用例子。代理打开网站后，网站可以提供更适合代理的收件箱视图，也可以直接告诉代理：“这里有一个邮箱 MCP 服务器，可以这样安装；这里有一项处理邮件的技能；如果你需要快速读取收件箱，可以访问一个结构化的 JSON 入口。”

这里需要强调，代理模式必须由用户主动开启，而且只对当前会话生效。它不是一直处于开启状态，也不是一种隐蔽的拦截机制。是否开启，由用户或用户设定的管理策略决定。

这种设计也回应了两个担忧。

第一个担忧是，网站会不会利用代理信号来屏蔽代理？文章认为，网站现在已经会通过用户代理字符串和各种机器人判断来识别代理。诚实地声明身份，主要是结束伪装，并不会显著增加网站的封锁能力。

第二个担忧是，这会不会变成一种监视？方案识别的是代理主动声明的运行模式，不是某个具体人的身份。它不提供用来识别人类用户的个人信息。

第一层之所以“无聊”，正是因为它要尽可能容易落地：一个请求头，一个浏览器属性，再加一个 JSON 文件。文章认为，代理厂商应该能在一个工作冲刺周期内完成它。

不过，仅仅让网页知道代理在场，还不能消除传话问题。于是，文章进一步提出第二层。

##### 五、第二层：让页面可以把工作交给代理

第二层的核心结论是：页面不仅要检测代理，还应该能向代理发送结构化请求，并在代理完成任务后接收结果。

这里的“结构化请求”，不是一段模糊的聊天文字，而是带有明确意图和上下文的数据。比如页面可以发出这样的请求：“请为这封邮件起草回复。”同时附上邮件线程和语气要求。

流程可以这样理解：

第一，用户在页面上发起某项请求。

第二，页面通过代理模式通道，把任务意图和必要上下文交给用户自己的代理。

第三，代理按照自己的权限与审批流程处理。

第四，任务完成后，结果返回页面，由页面继续完成后续操作。

文章用邮箱应用 Cora 举例。邮件页面可以放一个“让你的代理生成回复”的按钮。用户点击后，应用把当前邮件对话交给用户自己的代理，而不是自己运行模型，也不要求用户手动复制邮件内容。

代理生成草稿后，结果会回到邮件撰写框。用户可以检查、修改，再决定是否发送。

这和现在的中继方式不同。当前的做法可能是：用户复制邮件内容，切到终端，告诉代理任务，再把代理生成的文字复制回网页。第二层希望把这段来回搬运直接消除。

Agentation 也可以因此升级。用户在实时页面上标注一个元素，反馈信息和元素的真实选择器就能直接进入代理队列，不再需要复制剪贴板内容。

DialKit 还可以增加一个“应用”按钮。用户在浏览器里调整动画参数后，参数会作为结构化变更请求交给代理，由代理把这些数值写回代码。比如，刚度、阻尼、持续时间和缩放比例，都可以作为明确字段传递，而不是拼成一段提示词。

这里还有一个重要关系：WebMCP 和 Agent Mode 第二层并不冲突。

WebMCP 是“代理调用页面”。页面提供工具，代理去使用。

Agent Mode 第二层是“页面询问代理”。页面把工作交给代理，代理返回结果。

一个负责页面向代理开放能力，另一个负责页面向代理发出请求。文章认为，它们未来可能整合进同一个标准，也可能保持独立。当前的名称并不是最重要的，关键是双向通道必须存在。

##### 六、安全边界：三道门，而不是页面说了算

接下来，文章正面回应一个关键异议：如果页面可以向代理发请求，那会不会变成一个精致的提示词注入渠道？

提示词注入，简单说，就是网页中的恶意文字试图操纵代理，让代理执行用户并未真正授权的事情。文章没有声称 Agent Mode 已经解决了这个问题，而是提出三道强制性的门。

第一道门，是代理模式门。

第二层通道只有在代理模式已经开启时才存在。页面不能在用户没有选择的情况下，偷偷暴露一个代理接口。必须是人类用户，或者用户设定的控制策略，明确为本次会话打开代理模式。

第二道门，是网站授权。

页面要按网站来源申请通道权限，浏览器或中间件负责管理这些权限。这类似摄像头和麦克风权限：用户可以允许某个网站访问，也可以拒绝；代理浏览器要知道哪些网站被授予权限，其他网站默认不能使用。

第三道门，是代理自己的审批循环。

页面发来的每一项请求，都只能被当作不可信输入。它不能因为自己说“请发送邮件”就直接获得执行权限。请求仍然要经过代理原有的权限判断和审批流程，就像其他代理操作一样。

因此，真正执行操作前，至少要经过这样的判断：

- 代理模式是否由用户开启；
- 当前网站是否获得授权；
- 代理是否批准这一次具体请求。

这是一种纵深防御。它并没有消除提示词注入，只是把风险限制在几道明确的边界之内。

文章也承认，这是整个提案最需要实战检验的部分。三道门看起来合理，但还没有经过充分验证。如果要批评这个方案，最应该从这里开始，因为它是最关键、也最薄弱的承重墙。

##### 七、谁来推动这件事

最后，文章把行动分成三类参与者。

首先是代理制造者，包括 Cursor、Anthropic、OpenAI 和 Google 等团队。

它们需要先交付第一层：在请求中发送代理模式头部，暴露 `navigator.agentMode`，并读取网站的发现文件。文章认为，这一层规模不大，应该可以在一个工作冲刺周期内完成。而第二层的进一步发展，都建立在第一层已经存在的基础上。

接下来是应用开发者。

网站需要发布自己的发现文件，并认真设计代理访问路径。开发者要决定：代理来到这里时，应该看到什么，哪些流程可以跳过，哪些信息需要直接提供。过去，网站可能只是用启发式方法猜测代理身份，结果往往适应得很差。今后，如果身份信号变得真实，网站就应该更主动地为代理设计界面。

更重要的是工具开发者。

DialKit、Agentation、Impeccable、RiffRec，以及未来出现的类似产品，不应该继续各自维护私有桥梁。它们可以把共享接口作为主要路径，把自定义传输方式作为备用方案。这样，工具就不必为每一个代理浏览器重复开发一套连接机制。

至于这个讨论应该在哪里进行，文章认为可以保持开放。WebMCP 背后的 W3C 工作组，是目前最接近的讨论聚集地。如果这个想法得到认可，后续可以建立公开的规范仓库。

文章最后把代理模式放回网页发展的历史中。

网络曾经为不同读者逐步发展出不同的浏览方式：有打印样式表，方便打印；有响应式视口，适应手机；有阅读模式，减少干扰；有屏幕阅读器和无障碍树，帮助不同用户理解页面。

代理已经每天大量出现，也在投入真实的计算资源和资金。但网页仍然让它们眯着眼睛看像素，假装自己是人类。

代理模式的目标，就是让网络继续做它过去一直在做的事情：面对新的读者，提供适合这种读者的表达方式。只是这一次，网页适应代理的速度需要更快一些。

##### 结尾：四点值得记住

最后，用四个结论回顾全文。

第一，今天的网页代理普遍被迫模拟人类操作。它们截图、点击、滚动，而网页不知道对面是代理。人类因此成了传话人。

第二，现有方案已经证明了“页面和代理直接沟通”是有需求的，但 DialKit、Agentation、Impeccable、RiffRec 和 ui.sh 等工具都在各自建桥，彼此没有共享标准。

第三，Agent Mode 试图分两步解决问题。第一层是身份与发现，让浏览器声明代理在场，让网站提供适合代理的入口。第二层是通信通道，让页面把具体任务交给代理，并接收代理返回的结果。

第四，安全不能靠页面自称可信来保证，而要依赖三道门：用户开启代理模式，网站获得授权，代理对每次请求进行审批。这个方案还没有被充分实战检验，但它提出了一个清晰、可讨论的方向：让网络从“代理也能勉强使用”，走向真正的“代理原生网络”。

## 深度解读（1）

### 2026-09-18 00:33:47

#### 代理原生 Web 缺的不是更会点击的 AI，而是页面与代理之间的协议

今天的浏览器代理虽然能看网页、点按钮，却仍像一个被迫使用鼠标的人：页面明明有 DOM、业务状态和结构化数据，代理却要截图识别；用户和页面明明都在与同一个代理协作，却只能靠复制粘贴、终端提示词和私有 MCP 服务传话。

文章最有价值的贡献，是准确指出了现有标准之间的一块空白：**Web Bot Auth 让服务器识别代理，WebMCP 让代理调用页面工具，但没有机制让页面知道代理正在场，也不能由页面向代理发起请求。**这不是接口命名问题，而是缺失了一种交互方向。

##### 第一层真正解决的是“能力协商”

作者提出的 `Agent-Mode` 请求头、`navigator.agentMode` 和 `/.well-known/agent-mode.json` 看似朴素，意义却不小：网站不必再猜访问者是不是代理，代理也不必从像素中推断网站提供了什么能力。

它更像一次能力协商。网站可以告诉代理：“这里有 MCP 服务、CLI、可安装技能和机器友好的数据入口”；页面也可以跳过 Cookie 弹窗、营销动画和新手引导，直接展示高密度视图。

不过，这种声明只能用于**体验适配与能力发现**，不能充当可信身份或授权依据，因为请求头可以伪造。需要验证代理身份时，仍要结合 Web Bot Auth。这个边界决定了第一层容易落地：它不试图一次解决认证、安全和执行，只先结束“所有工具各造一座桥”的浪费。

最可能率先采用它的也不是整个消费互联网，而是开发工具、本地应用、设计协作和企业内部系统。这些场景中，用户、页面与代理目标一致，复制上下文的成本又足够高。普通网站是否愿意配合，则取决于代理流量能否带来交易、留存或成本下降；有些网站反而会选择限制它。

##### 第二层可能改变 AI 功能的产品边界

更激进的部分是让页面调用用户自己的代理。例如邮件产品不再自己运行模型，而是把线程和“起草回复”的请求交给用户已登录、已有上下文的代理，再把结果接回编辑框。

这意味着应用可以从“每家都内置一个 AI”转向“调用用户选择的智能运行时”。如果成立，产品竞争的重点会从模型包装转向：谁能定义更好的任务、提供恰当上下文，并把结果安全地接回工作流。它也可能降低应用方的推理成本，减少用户在多个助手之间重复配置身份、偏好和资料。

但这仍是待验证的主张。现有替代方案——应用内模型、复制粘贴、浏览器扩展和 MCP——虽然割裂，却更容易控制责任边界。页面向代理发请求，本质上也为提示注入增加了一条正式入口。作者提出的“主动开启、按来源授权、逐次审批”只能控制通道，不能判断请求是否在诱导代理泄露其他标签页、代码库或私人数据。真正可用的标准还需要细粒度能力范围、最小化上下文、来源可追踪、可撤销授权、执行预览和审计记录；否则用户很快会陷入审批疲劳。

因此，近期最值得下注的不是某个具体 API，而是**结构化的页面—代理桥接层**。产品团队可以先在高频“人工传话”场景中验证：它是否显著减少复制粘贴和错误、用户愿意授予哪些权限、哪些请求会被拒绝。若这些指标成立，Agent Mode 才不只是更优雅的技术接口，而可能成为 Web 从“供人操作”走向“供人与代理共同操作”的一次真实界面迁移。

## 默认总结（1）

### 2026-09-18 01:44:50

##### 一句话看懂

文章提出尚未落地的 **Agent Mode**：让浏览器主动告知网站“当前由 AI 代理操作”，并允许网站在用户授权后把任务直接交给代理，减少截图、点击和复制粘贴。

##### 关键内容

- **现有交互很低效**：Codex、Claude Code、Cursor 等代理访问网页时，看起来与普通用户无异，只能识别像素、模拟点击；页面也无法直接把元素、参数或反馈传给代理。
- **第一层是身份与能力发现**：浏览器发送 `Agent-Mode` 请求头，向页面暴露 `navigator.agentMode`；网站则通过统一 JSON 文件提供 CLI、MCP 服务、技能或更适合代理的页面入口。
- **第二层是双向任务通道**：页面可向代理发送结构化请求，例如“根据邮件线程起草回复”，代理完成后把结果返回页面。它与 WebMCP 的“代理调用网页工具”方向相反但互补。
- **安全问题尚未解决**：作者要求必须经过“用户开启模式、按网站授权、代理逐次审批”三道门，但承认这只能约束提示词注入风险，尚未经过实战验证。

##### 通俗解读

这不是已经发布的标准，而是一份供讨论的“稻草人提案”。它想把现在各工具私建的桥梁，变成类似摄像头权限那样的浏览器公共接口。
