> Released as part of the *Hooking Coding Agents with the Cedar Policy Language* talk at [Unprompted 2026](https://unpromptedcon.org/).

A reference monitor for AI coding agents. Rust hook binaries and [Cedar](https://docs.cedarpolicy.com/) policies intercept every shell command, file operation, and web request to forbid exfiltration and destructive behaviors, and enforce information flow control. YARA signatures and Cedar policy evaluation are deterministic; the optional LLM-based classifiers (data sensitivity, secure code policy) are probabilistic.

Works with [Claude Code](https://code.claude.com/docs/en/hooks),[Cursor](https://cursor.com/docs/agent/hooks),[GitHub Copilot](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/use-hooks), and [Gemini CLI](https://geminicli.com/docs/hooks/).

#### Getting Started

##### Prerequisites

The YARA signature engine and Cedar policies work without any external dependencies. The LLM-based classifiers (data sensitivity and secure code policy) require [Ollama](https://ollama.com/) with the `gpt-oss-safeguard-20b` model:

```
# Install Ollama — see https://ollama.com/download for other platforms
brew install ollama

# Pull the model (~12 GB)
ollama pull gpt-oss-safeguard-20b
```

The harness server loads Cedar policies and listens on a Unix socket for hook connections.

```
cargo run --bin sondera-harness-server -- -v
```

By default, it loads policies from `./policies` and the socket path is resolved in order of preference:

Priority Path When

1 `/var/run/sondera/sondera-harness.sock` Directory exists or can be created

2 `~/.sondera/sondera-harness.sock` Fallback for unprivileged users

Override with `--socket`:

```
cargo run --bin sondera-harness-server -- \
  --policy-path /path/to/policies \
  --socket /var/run/sondera/sondera-harness.sock \
  -v
```

See Deployment for more details on socket ownership and permissions.

The `sondera-claude` binary registers hooks for all Claude Code lifecycle events (pre-tool-use, post-tool-use, session-start, etc.). Choose a scope:

To uninstall, use the same scope flag:

```
cargo run -p sondera-claude -- uninstall --user
```

Hooks for Cursor (`sondera-cursor`), GitHub Copilot (`sondera-copilot`), and Gemini CLI (`sondera-gemini`) follow the same pattern.

##### 3\. Policies

Cedar policies and the schema live in `policies/`. The harness server loads all`.cedar` and `.cedarschema` files from this directory at startup.

```
policies/
├── base.cedarschema       # Entity types (Agent, Trajectory, Tool, File, Label, Taint) and actions
├── base.cedar             # Default-permit baseline with targeted forbids for prompt injection,
│                          #   credential access, data exfiltration, shell/web/file pre- and
│                          #   post-execution gates, and trajectory-level runaway protection
├── destructive.cedar      # Blocks irreversible operations: rm -rf, git force-push, terraform
│                          #   destroy, DROP DATABASE, lock file deletion, kill -9, and more
├── file.cedar             # File-type-aware guards: Bell-LaPadula IFC (no write-down), private
│                          #   key access, secrets in source code, obfuscation in scripts, and
│                          #   OWASP/CWE policy violations (injection, weak crypto, broken authz)
├── ifc.cedar              # Information flow control: sensitivity-gated outbound blocking,
│                          #   taint propagation guards, network tool restrictions, and
│                          #   step-count limits scaled by data classification level
├── supply_chain_risk.cedar # Supply chain attack detection: typosquatting, dependency confusion,
│                          #   build script injection, lock file tampering, and registry exfiltration
├── ifc.toml               # Prompt templates for LLM-based data classification
└── policies.toml          # Prompt templates for LLM-based secure code generation evaluation
```

Write your own `.cedar` files into this directory to add custom rules. The harness evaluates all policies on every hook event — a single matching `forbid` overrides any `permit`.

#### Architecture

Architecture

Agent frameworks (Claude Code, Cursor, Copilot, Gemini CLI) communicate with per-agent **hook adapter** binaries over stdin/stdout JSON. Each hook binary forwards events over **tarpc RPC** (Unix socket) to the harness service layer, which coordinates three guardrail subsystems:

1. **Signature Engine** (YARA-X) — pattern-matches tool inputs/outputs for prompt injection, data exfiltration, secrets, and obfuscation.
2. **Policy Model** (gpt-oss-safeguard-20b via Ollama) — classifies content against secure code generation categories.
3. **Information Flow Control** (gpt-oss-safeguard-20b via Ollama) — assigns sensitivity labels for data classification.

The **Cedar Policy Engine** loads policies and schema fragments authored by a policy agent via the MCP server, combines guardrail signals with entity state from the **Fjall key-value store**, and returns an adjudication (Allow / Deny / Escalate) back through the hook binary to the agent.

##### Event Model

Event model

The harness models agent execution as a trajectory of typed events. Each hook adapter normalizes its agent-specific JSON into four event categories:

Category Description Examples

**Action** Agent-initiated operations, evaluated *before* execution `ShellCommand`, `FileRead`, `FileWrite`, `FileEdit`, `WebFetch`, `ToolCall`

**Observation** Environment responses, evaluated *after* execution `ShellCommandOutput`, `FileOperationResult`, `WebFetchOutput`, `Prompt`

**Control** Lifecycle events that manage the trajectory `Started`, `Completed`, `Failed`, `Adjudicated`

**State** Snapshots of environment context Working directory, open files, git branch

Each adapter maps agent-specific tool names to these common types — Claude's `Bash` tool, Cursor's shell execution hook, Copilot's `bash` tool, and Gemini's `bash` tool all normalize to the same `ShellCommand` action. The harness evaluates policies against these normalized events, so Cedar rules work identically across all four agents.

#### Deployment

**Production hardening.** The `sondera-harness-server` socket path is security-critical, whichever process binds it first controls adjudication for all hook clients. Pre-create the directory with restricted ownership to prevent a rogue process from binding the path before the harness starts:

```
sudo mkdir -p /var/run/sondera
sudo chown sondera:sondera /var/run/sondera
sudo chmod 0750 /var/run/sondera
```

On systemd hosts, use `RuntimeDirectory=sondera` in the unit file instead, which creates and locks down `/run/sondera/` automatically. Avoid the home directory fallback in production, its world-writable parent makes it vulnerable to pre-binding races.

## 产品-功能分析（1）

### 2026-03-18 04:21:35

一、讲了什么？

这份内容介绍的是一个名为`sondera-coding-agent-hooks`的安全框架，它的核心目标很明确：给各种 AI 编程助手装上 “安全刹车” 和 “行为监管系统”。无论是 Claude Code、Cursor、GitHub Copilot，还是 Gemini CLI，它都能在这些智能体真正执行操作之前和之后，对它们的行为进行拦截、审查和裁决。

它主要做了几件事：

- 监控 AI 编程助手的关键行为，包括执行 shell 命令、读写编辑文件、发起网页请求等。
- 用一套规则体系判断这些行为是否安全，重点防范数据外泄、误删文件、危险命令执行、供应链攻击、敏感信息滥用等问题。
- 规则引擎由两部分组成：一部分是确定性的，比如 YARA 特征扫描和 Cedar 策略语言；另一部分是可选的概率性判断，比如借助本地大模型对数据敏感性和安全编码风险做分类。
- 所有不同 AI 工具的操作，都会被统一抽象成标准事件模型，再交给同一套策略进行判断，因此可以跨多个编程助手复用规则。
- 它还强调 “信息流控制”，也就是不仅看某个动作危险不危险，还看 “这个动作处理的数据来自哪里、是否敏感、能不能流向外部”。

从本质上说，这不是一个提升 AI 代码能力的工具，而是一个约束 AI 编码行为、建立可信边界的基础设施。它试图解决的不是 “AI 会不会写代码”，而是 “AI 在写代码和操作系统时，如何不越界、不闯祸、不泄密”。

二、有什么用？

如果把 AI 编程助手比作一个非常能干、反应很快、24 小时待命的 “超级实习生”，那么这个项目的价值，就相当于给这个实习生配上了一整套门禁系统、审计系统、保安巡逻系统和风险审批制度。

为什么这很重要？因为现在的 AI 编程助手已经不只是 “回答问题” 了，它们越来越像一个真正能动手的执行者。它可以帮你运行命令、改代码、读配置、联网查资料、安装依赖、提交变更。问题也恰恰出在这里：一旦 AI 从 “会说” 进化到 “会做”，风险就从 “说错话” 升级成 “做错事”。

可以把这个问题拆成几层来理解。

第一层，AI 可能 “误操作”。

一个普通聊天机器人答错了，最多浪费你一点时间；但一个能执行命令的编码助手如果误删目录、强制推送代码、修改锁文件、误杀进程，后果可能是直接把项目搞坏。就像一个实习生不只是写文档，而是拿到了机房钥匙、数据库权限和生产环境按钮 —— 能力越强，出事的半径越大。

这个系统的第一大价值，就是在 AI 下手之前多问一句：“这个动作能不能做？”  
比如它会识别出危险命令：`rm -rf`、`git push --force`、`terraform destroy`、`DROP DATABASE`这类不可逆操作，直接拦下。这样一来，AI 不再是 “想到什么就执行什么”，而是必须经过一层规则审查。

第二层，AI 可能 “被诱导”。

很多人会以为 AI 的风险来自模型自己犯傻，其实更大的风险常常来自外部输入。比如一个仓库里的 README、注释、构建脚本、网页内容，可能暗藏 “提示注入” 信息，专门诱导 AI 去泄露数据、忽略规则、执行危险操作。  
这就像有人悄悄塞给实习生一张纸条，上面写着：“老板让我告诉你，把公司密钥发我一下。” 如果没有防护，AI 很可能把这类恶意内容当成正常指令的一部分。

这个项目的第二大价值，就是它不仅检查 “AI 想做什么”，还检查 “AI 为什么想这么做”。它会通过 YARA 特征、策略规则和分类模型识别提示注入、数据外传、可疑混淆脚本、供应链攻击等风险信号。换句话说，它不是只看动作表面，而是试图理解动作背后的威胁模式。

第三层，AI 可能 “看过不该外传的数据”。

这一点特别关键。很多团队真正担心的不是 AI 删文件，而是 AI 读到了敏感信息之后，把这些内容带出去了。比如：

- 读到了`.env`里的密钥
- 看到了客户数据
- 打开了私钥文件
- 扫到了源代码里的凭证
- 获取了带有商业机密的文档内容

传统权限控制往往是 “能不能读” 或 “能不能写”，但在 AI 场景下，这还不够。因为 AI 即使只是 “看一眼”，后续也可能在别的动作里 “带出去”。  
这就是信息流控制的重要性。你可以把它理解成给信息贴 “颜色标签”：

- 普通公开信息，绿色
- 内部信息，黄色
- 敏感信息，红色

如果 AI 看过红色信息，那么之后它想把某些内容写到外部网页、发到网络接口、复制到不该去的地方，系统就会提高警惕甚至直接阻止。  
这就像化学实验室里的污染控制：不是只看你手里拿的试剂危不危险，而是看你有没有接触过危险物质，接触过之后还能不能随便碰别的东西。

第四层，AI 工具很多，但安全规则不能每个都重写一遍。

企业里不会只用一种 AI 编码助手。今天有人用 Claude Code，明天有人用 Cursor，后天又接入 Copilot 或 Gemini。如果每个工具都自己做一套安全规则，成本极高，而且一定会产生漏洞和不一致。  
这个项目的一个很聪明的点是：它先把不同助手的行为都 “翻译” 成统一事件，比如统一成 ShellCommand、FileRead、FileWrite、WebFetch 这类标准动作，然后再用同一套 Cedar 策略去判断。  
这就像不同品牌的汽车，虽然仪表盘长得不一样，但都要遵守同样的交通法规。这样一来，企业的安全治理不再依赖某个单独的 AI 产品，而是建立在一层更通用的控制平面上。

第五层，它让安全治理从 “靠人盯” 变成 “靠系统裁决”。

很多团队现在其实不是没有安全意识，而是靠人盯根本盯不过来。AI 的操作速度太快，一分钟能读几十个文件、发起多个命令、跨多个上下文切换。如果还靠工程师手工审核每一步，那 AI 的效率优势就没了。  
这个系统相当于给 AI 工作流配了一个 “实时法官”：

- 符合规则：允许
- 明显违规：拒绝
- 情况模糊：升级处理

这种 Allow / Deny / Escalate 的机制特别适合企业场景。因为很多安全问题不是黑白分明的，有些操作不是一定不行，而是需要人工确认。这样，系统既不是一刀切，也不是完全放任，而是把 “自动化效率” 和 “人类监督” 结合起来。

所以，这个项目真正的意义，不只是一个 GitHub 仓库里的技术实现，而是代表了一种新的安全思路：

当 AI 开始像 “数字员工” 一样参与实际工作时，企业不能只问 “它聪不聪明”，更要问 “它是否可控、可审计、可约束、可追责”。

从这个角度看，`sondera-coding-agent-hooks`的价值不在于让 AI 更自由，而在于让 AI 的自由被放在正确的边界里。  
真正成熟的 AI 应用，不是让模型什么都能做，而是让模型在该做的地方高效，在不该做的地方停下。

三、怎么用？

要真正把这个系统用起来，不能只把它看成一个 Rust 项目，而要把它当成 “AI 编码助手的安全中间层”。更准确地说，它像是部署在 AI 和操作系统之间的一道检查站。下面我结合实际场景，按从零到落地的过程，详细讲它怎么用。

先设定一个现实场景：

假设你是一家互联网公司的研发负责人，团队已经在日常开发中使用 Claude Code、Cursor 和 Copilot。你们希望保留 AI 带来的效率，但又担心几个问题：

- AI 可能读取`.env`、私钥、数据库配置
- AI 可能把内部代码片段发到外部网页或第三方接口
- AI 可能误执行危险命令
- AI 可能被恶意仓库内容注入提示，诱导做错事
- 不同 AI 工具太多，安全规则无法统一

这时，这个框架就可以作为统一的 “AI 行为安全网”。

1. 先理解它在系统里的位置

整个系统可以理解为四层：

- 最外层是你正在使用的 AI 编码工具，比如 Claude、Cursor、Copilot、Gemini
- 中间是对应的 hook 适配器，也就是为每个工具安装的拦截器
- 再下一层是 harness server，它是真正做策略裁决的大脑
- 最底层是规则与状态系统，包括 Cedar 策略、YARA 扫描、信息流标签、轨迹存储等

工作流程大致是这样的：

第一步，AI 想执行一个动作，比如运行 shell 命令。  
第二步，这个动作不会直接执行，而是先被 hook 程序截住。  
第三步，hook 把这个动作发给 harness server。  
第四步，server 会根据策略、扫描结果、历史轨迹、数据敏感性等因素判断。  
第五步，返回结果：允许、拒绝、或者升级。  
第六步，如果允许，AI 的动作才真正落地执行。

你可以把它想象成公司里的 “门禁闸机”：员工不是不能行动，但每次进出关键区域都要过闸机，闸机会核验证件、记录行为、判断风险。

2. 启动核心服务：先把 “裁决中心” 跑起来

在使用前，首先要启动`sondera-harness-server`。它相当于整个系统的大脑，负责加载策略、监听 socket、接收 hook 请求并做判断。

它默认会从`./policies`目录里加载策略文件，并监听一个 Unix socket，供各个 hook 连接。  
部署时，你要特别注意 socket 路径的权限，因为谁先绑定这个 socket，谁就相当于掌握了裁决权。

在开发环境中，可以先直接启动服务。  
在生产环境中，重点是提前创建好受限目录，例如`/var/run/sondera`，并设置正确的属主和权限，避免恶意进程抢先绑定 socket。

这一点非常关键，很多人容易忽略。  
因为如果 “安全裁决通道” 本身被劫持，那整个保护层就失效了。就像门禁系统再高级，如果门卫室被别人抢先占了，所有判断都会出问题。

3. 给具体 AI 工具安装 hook：让 “动作” 先经过安检

接下来，需要给你使用的 AI 编码工具安装对应 hook。  
比如 Claude 用`sondera-claude`，Cursor 用`sondera-cursor`，Copilot 用`sondera-copilot`，Gemini 用`sondera-gemini`。

它们的作用不是替代这些工具，而是插入到这些工具的生命周期事件中，比如：

- 会话开始
- 工具调用前
- 工具调用后
- 会话结束
- 失败事件
- 状态更新

这一步的意义，是确保 AI 的关键动作都不会 “绕过审查”。

在实际部署中，建议按 “用户级” 和 “团队级” 两种方式思考：

- 个人试用：先在自己机器上按用户级安装，验证策略不会影响正常开发
- 团队上线：统一做系统级部署，确保所有人都经过同一套规则

如果你是技术负责人，不要一上来全公司强推。  
更好的方式是选一个试点团队，先在几个典型场景中验证：

- 正常编码是否顺畅
- 高风险动作是否能拦截
- 误报是否过多
- 升级机制是否影响效率

安全系统如果误伤太多，工程师会天然抵触；如果拦不住关键风险，又没有价值。所以试点阶段的重点不是 “装上”，而是 “调准”。

4. 配置策略：先用默认规则，再结合业务定制

这个项目很强的一点，在于策略不是写死在代码里的，而是外置在`policies/`目录中。你可以把这里理解成 “企业 AI 行为宪法”。

默认策略已经覆盖很多高风险场景：

- `destructive.cedar`：阻止破坏性操作
- `file.cedar`：按文件类型和风险控制访问
- `ifc.cedar`：控制敏感数据的流向
- `supply_chain_risk.cedar`：识别依赖投毒、拼写碰瓷、锁文件篡改等问题
- `base.cedar`：提供基础 permit/forbid 逻辑

实际使用时，推荐分三步配置。

第一步，用默认策略跑起来。  
不要一开始就做复杂定制，因为你还不知道团队的真实行为模式。先让系统记录并裁决，再观察哪些规则命中频繁、哪些地方误伤开发。

第二步，根据业务场景加 “组织专属规则”。  
例如：

- 禁止 AI 读取某些目录：如`infra/secrets/`、`prod-keys/`
- 禁止 AI 修改关键发布脚本
- 禁止 AI 向外部未批准域名发送请求
- 对涉及客户数据的项目，限制 AI 外发摘要和日志内容
- 对金融、医疗类项目，提高敏感级别和升级阈值

第三步，把安全规则做成分层治理。  
不同项目风险不同，没必要一刀切。可以按仓库或业务线区分：

- 公共开源项目：策略较宽
- 内部服务项目：策略中等
- 涉及用户隐私和财务系统：策略严格

这相当于公司不同区域的安保等级不同。办公区和金库不可能用同一把门锁。

5. 利用信息流控制：不是只看 “动作”，而是看 “数据路径”

这个系统最值得深入使用的，是信息流控制，也就是 IFC。  
很多团队容易停留在 “拦危险命令” 这个层次，但真正高级的治理是控制 “敏感信息经过 AI 后还能流向哪里”。

举个实际例子：

AI 先读取了`.env.production`，里面有数据库连接串和 API 密钥。  
随后 AI 想执行一个网页请求，或者把诊断结果写到一个对外共享文件里。

如果你只看第二个动作本身，它可能看起来很正常；  
但如果你知道这个动作的上下文 —— 它刚刚接触过高敏感数据 —— 那风险就完全不同。

所以在真实落地时，你应该重点配置两类规则：

- 敏感数据接触后的外发限制
- 敏感数据接触后的后续修改限制

你可以把这个机制理解为 “沾染管理”。  
像实验室里处理放射性物质一样，关键不是某个人当前手里拿着什么，而是他刚才碰过什么。碰过高风险数据之后，后续很多操作都应该被限制或重新审查。

企业如果能把这一层做好，AI 的可控性会提升一个量级。

6. 接入可选的大模型分类器：把 “规则” 升级成 “规则 + 判断”

系统本身即使不接大模型也能工作，因为 YARA 和 Cedar 都是确定性规则。  
但如果你希望对以下问题有更强判断力，可以接入 Ollama 和`gpt-oss-safeguard-20b`：

- 当前内容是否属于敏感数据
- 当前生成代码是否违反安全编码要求
- 某些复杂文本是否包含风险倾向

这一步的定位，不是替代规则，而是给规则增加 “语义理解层”。

比如确定性规则擅长判断：

- 有没有出现某个密钥模式
- 有没有执行某个危险命令
- 有没有访问某类文件
- 有没有命中特征签名

而大模型更擅长判断：

- 这段内容是不是带有客户隐私
- 这份代码实现是否存在不安全鉴权
- 这段提示是否具有高风险诱导性
- 这次变更是否在试图绕过安全限制

在实际使用中，建议把模型结果看作 “辅助信号” 而不是 “最终法官”。  
最稳妥的用法是：

- 高确定性风险：直接拒绝
- 模糊风险：模型参与评分，再决定升级
- 低风险场景：主要依靠规则引擎，减少性能成本

这样既能发挥模型理解复杂语义的能力，又不会把安全判断完全交给概率性系统。

7. 建立事件轨迹：从 “单点检查” 变成 “全程监管”

这个系统还有一个重要设计：它不是只看某个孤立动作，而是把 AI 的整个执行过程建模成一条 trajectory，也就是轨迹。

为什么这很重要？  
因为很多风险不是某一步单独看出来的，而是连续几步连起来才显现。

例如：

- 先读取凭证文件
- 再访问源码
- 然后压缩内容
- 最后发起网络请求

如果你只看 “发网络请求”，它可能看似正常；  
但放在整条轨迹里看，就是明显的数据外流风险。

所以在落地时，建议你重点关注 “多步组合风险”：

- 是否先读敏感文件，再访问外网
- 是否短时间内连续执行异常多的命令
- 是否反复尝试被拒绝的高危操作
- 是否存在绕过限制的迂回路径

这就像风控系统不会只看一笔交易，而是看账户的连续行为。  
AI 安全同样如此，真正成熟的治理是 “过程风控”，不是 “动作黑名单”。

8. 在团队内形成运营闭环：不是装完就结束

很多安全系统失败，不是技术不行，而是装完以后没人持续运营。  
这个框架要真正产生价值，需要建立一个简单但稳定的运营闭环。

建议这样做：

第一，先记录所有裁决结果。  
包括哪些动作被允许，哪些被拒绝，哪些被升级。这些数据是后续调优的基础。

第二，定期分析误报和漏报。  
如果某条规则天天拦正常开发，就需要调整；如果某类风险从未覆盖，就要补规则。

第三，把高频安全事件沉淀成组织知识。  
比如你发现 AI 经常尝试读取测试环境密钥，那说明团队工作流本身可能存在暴露点，不只是 AI 的问题。

第四，把策略和工程规范打通。  
例如把 “禁止修改 lock file” 与 CI 校验联动，把 “禁止访问敏感目录” 与仓库权限配合，把 “外发限制” 与网络出口治理结合。  
这样，AI 安全就不再是孤立工具，而成为研发治理的一部分。

9. 一个典型应用流程示例

我们用一个更具体的场景串一下：

场景：工程师让 AI 帮忙排查一个线上 bug。

AI 可能会这样行动：

- 读取项目代码和日志文件
- 查看配置文件
- 运行 grep、cat、git diff、cargo test 等命令
- 试图访问某个接口文档网页
- 修改一个配置文件并生成 patch

在这个过程中，系统如何工作？

第一步，AI 请求读取日志文件。  
hook 捕获事件并发给 harness。  
策略判断日志文件中可能含有用户标识信息，于是给后续轨迹打上敏感标签。

第二步，AI 想访问外部网页搜索类似错误。  
由于它已接触敏感日志，IFC 规则触发，系统评估这次外发是否可能泄露信息。若请求内容带有日志摘要，则可能直接拒绝或要求升级。

第三步，AI 想修改代码。  
`file.cedar`和 secure code policy 会检查改动是否引入注入风险、弱加密、错误鉴权等问题。

第四步，AI 想运行删除缓存或重建环境的命令。  
如果命令具有破坏性，`destructive.cedar`会拦截。

第五步，整条轨迹结束后，系统保留行为记录。  
团队可以回溯：AI 读了哪些文件、尝试过哪些操作、为什么某个动作被拒绝。

这个过程的关键价值在于：  
你依然保留了 AI 的效率，但你不再把它当成一个可以无限自由行动的黑盒，而是把它放进了可监管、可解释、可审计的工作流里。

四、如何迁移？

理解这套系统之后，最有价值的不是只会在这个仓库里使用它，而是能够把它背后的模式迁移到更广泛的产品、技术和组织治理中。因为它体现的不是某个具体工具技巧，而是一种非常重要的 AI 时代治理范式：对高能力代理进行 “标准化观察、规则化判断、上下文化约束、过程化审计”。

要迁移，先要识别它的核心结构。这个结构其实可以抽象成五个要素：

- 可观察的动作
- 可归一的事件模型
- 可组合的规则系统
- 可累计的上下文状态
- 可执行的裁决机制

只要一个系统里同时存在 “智能体会做事”“这些事有风险”“风险不能完全靠人工盯”，你就几乎都能套用这个框架。

1. 横向迁移：从 AI 编码代理迁移到其他 AI 代理

最直接的横向迁移，是把这种模式用到其他类型的 AI Agent 上。

比如客服 AI。

客服 AI 不一定会执行 shell 命令，但它会：

- 读取用户历史
- 查看订单信息
- 调用退款接口
- 修改工单状态
- 向用户发送消息

这跟编码代理的本质是一样的。  
你同样可以建立一个 “动作 - 事件 - 裁决” 系统：

- `ReadCustomerData`
- `RefundRequest`
- `ChangeOrderStatus`
- `SendExternalMessage`

然后配一套规则：

- 看到高敏感用户信息后，不能随便对外发送摘要
- 涉及退款必须升级审批
- 涉及账户权限变更必须二次确认
- 出现异常对话模式时拒绝执行操作

再比如销售 AI。

销售 AI 可能会：

- 访问 CRM
- 生成报价
- 发邮件
- 修改客户阶段
- 导出名单

此时也可以照搬：

- 用统一事件模型归一化动作
- 对敏感客户数据做信息流控制
- 对外发邮件做内容和目标域名限制
- 对批量导出行为建立升级机制

也就是说，这个项目背后的真正可迁移之处，不是 Rust、Cedar 或 YARA 本身，而是 “所有高权限 AI 代理，都应该通过一个标准化的裁决层来治理”。

2. 纵向迁移：从工具层迁移到平台层、组织层、制度层

第二种迁移，是向更高层抽象。

在工具层，它解决的是 “某个 AI 命令能不能执行”。  
但往上走，它其实可以演化成 “企业级 AI 行为治理平台”。

比如在平台层，你可以把多个 AI 产品接进一个统一控制平面：

- 编码 AI
- 文档 AI
- BI 分析 AI
- 客服 AI
- 运营 AI

这些产品底层能力不同，但都可以被抽象成：

- 读什么
- 改什么
- 发给谁
- 调了什么工具
- 在什么上下文里做的

这样，企业就能建立统一的 AI 治理语言，而不是每接一个 AI 工具就重新发明一遍安全控制。

再往上到组织层，这套方法还能迁移成一套职责分工机制：

- 安全团队定义底线规则
- 平台团队维护统一策略引擎
- 业务团队编写局部策略
- 审计团队回看轨迹与裁决记录
- 管理层定义升级审批边界

这其实就是把 “AI 安全” 从一个技术实现，迁移成一个组织协同系统。

再往上到制度层，你会发现这套结构甚至接近企业内部控制和合规体系：

- 什么行为必须留痕
- 什么数据不可外流
- 什么操作必须双人确认
- 什么风险必须升级审批
- 出现争议时如何追责和复盘

换句话说，它不仅能迁移到别的产品，还能迁移到企业治理模型中。

3. 迁移的关键方法：抓模式，不抓表象

很多人迁移失败，是因为只学 “技术名词”，没有抓到结构模式。  
真正可迁移的是下面这个通用模板：

第一步，列出系统中的 “高风险动作”。  
不管是写代码、退款、发邮件、查数据库，先识别哪些动作一旦出错，损失最大。

第二步，把不同来源的动作抽象成统一事件。  
不要陷在工具细节里。不同系统名字不同，但底层动作常常可以归一。

第三步，为事件增加上下文。  
不要只看动作，还要看谁发起、看过什么、处于什么阶段、是否连续多次触发、是否涉及敏感数据。

第四步，把规则分成三层：

- 确定性底线规则
- 语义理解辅助规则
- 人工升级裁决规则

第五步，输出统一裁决结果。  
最经典的就是：

- 允许
- 拒绝
- 升级

这个模式非常稳，因为它兼顾了效率、准确性和治理弹性。

4. 多维迁移：从安全迁移到质量、成本、效率治理

这个框架不只适合安全，实际上还能迁移到其他管理目标。

比如迁移到 “质量治理”。

你可以把 AI 的每次改代码、生成配置、编辑脚本都当作事件，然后建立质量规则：

- 是否修改核心模块却没补测试
- 是否引入复杂度过高的实现
- 是否触发性能退化模式
- 是否使用过时 API

此时裁决层就不只是判断 “危险不危险”，还判断 “质量合不合格”。

再比如迁移到 “成本治理”。

对于会调用算力、API、数据库、第三方工具的 AI 代理，可以加一层成本控制：

- 是否频繁重复访问高价模型
- 是否过度扫描大文件
- 是否批量触发外部付费 API
- 是否在低价值任务中使用高成本推理

也就是说，原来这个框架里的 “安全策略”，完全可以变成 “预算策略”。

再比如迁移到 “效率治理”。

你可以观察 AI 的轨迹，识别：

- 是否在无效循环中反复尝试
- 是否总在做低效搜索
- 是否频繁调用无关工具
- 是否轨迹长度异常

然后在达到某个阈值时自动中断、提示换策略、或请求人工协助。  
这本质上就是把 “runaway protection” 从安全概念迁移成效率管理概念。

5. 迁移后的最高价值：从 “能力崇拜” 走向 “系统治理”

更深一层看，这套思路还有一个非常重要的思想迁移：  
我们对 AI 的关注点，要从 “它有多强” 迁移到 “它如何被治理”。

过去的软件系统，大多数行为是人写死的，所以我们更关注功能正确性；  
而 AI 代理是半自主系统，它的行为带有生成性、不确定性和上下文依赖性，所以必须引入治理层。

这意味着未来设计任何 AI 产品时，都可以默认先问四个问题：

- 它能做哪些动作？
- 哪些动作需要被观测？
- 哪些上下文会改变风险级别？
- 谁来裁决边界，如何留痕？

如果一个 AI 产品在设计之初就把这四个问题考虑进去，它就更有机会真正进入企业核心场景。  
因为企业买单的，从来不只是 “能力演示”，而是 “可控交付”。

所以，`sondera-coding-agent-hooks`最值得迁移的，不是某一条策略文件，也不是某一个 hook 实现，而是一整套面向 AI 代理时代的基本方法论：

- 先把行为标准化
- 再把风险结构化
- 再把上下文纳入判断
- 再把裁决机制嵌入流程
- 最后把留痕和复盘变成治理闭环

这套方法一旦学会，你不只是在理解一个安全项目，而是在掌握一种面向未来 AI 产品与组织系统的底层设计框架。

## 产品-技术开发实现（1）

### 2026-03-18 04:38:33

这是一个很典型的 “Agent 安全控制平面” 产品，不是单点功能，而是一层独立于模型和 IDE 的基础设施。它的价值不在 “拦命令” 本身，而在于把 AI 编码助手从 “黑盒自动执行器” 变成 “可观测、可裁决、可追责的系统组件”。

**产品解读**
- 核心产品定位很准：不是再造一个 coding agent，而是做所有 coding agent 之上的 “安全中间层”。
- 用户不是普通开发者，而是两类 B 端角色：`安全团队`和`平台工程团队`；开发者只是被保护的使用者。
- 真正解决的是企业落地 AI Coding 的三大阻力：`泄密`、`误操作`、`不可审计`。
- 它最强的产品设计点是 “跨代理统一治理”：Claude、Cursor、Copilot、Gemini 都被归一成同一事件模型，避免每个 Agent 单独做策略。
- 裁决结果设计成`Allow / Deny / Escalate`很成熟，适合企业流程，不会因为全拦或全放导致系统失效。

**技术架构解读**
- 架构本质是`Hook Adapter + Policy Decision Point + State Store + Guardrail Engines`。
- Hook 层负责接 IDE/Agent 生命周期事件；Harness Server 是统一决策中心；Cedar/YARA/LLM 分类器是判定引擎；Fjall 之类存储负责轨迹和状态。
- 事件标准化是关键设计：把不同产品的 Bash、文件编辑、网页访问统一成`ShellCommand / FileRead / FileWrite / WebFetch`，这样策略可复用。
- 采用 Unix Socket 做本地 RPC 很合理：低延迟、权限边界清晰、便于单机部署。
- “单条 forbid 覆盖 permit” 是安全系统常见的 fail-safe 设计，优先保证下限安全。
- 把确定性引擎和概率性引擎分层也很对：`YARA/Cedar`负责硬规则，`LLM classifier`只做高语义判断和补充，不做唯一裁决依据。

**设计上的高明之处**
- 不是只看单次动作，而是看`trajectory`。这比传统 DLP 更先进，因为 Agent 风险往往是多步组合风险。
- 引入`Information Flow Control`很关键。企业真正怕的不是 “AI 读了密钥”，而是 “AI 读完之后带出去了”。
- Policy as Code 选 Cedar 很合适：比把规则硬编码在 Rust 里更容易审计、迭代、分层授权。
- YARA 用来扫 prompt injection、secrets、obfuscation，很适合做高性能前置过滤。
- 本地可选 Ollama 模型是很现实的设计：既满足离线 / 隐私需求，又避免 SaaS 审查带来的数据合规问题。

**实现时的最佳实践**
- **先做事件归一化**
  - 不要直接围绕 Claude/Cursor 的原始 JSON 写规则。
  - 先统一抽象层：`Action`、`Observation`、`Control`、`State`。
  - 例子：Claude 的 Bash、Cursor 的 shell hook、Copilot 的 bash tool 全部映射成`ShellCommand`，这样策略只写一次。

- **规则分三层**
  - 第 1 层：硬阻断规则，确定性高，如`rm -rf`、`git push --force`、读私钥、外发 secrets。
  - 第 2 层：上下文规则，如 “如果刚读过敏感文件，则禁止外发到网络”。
  - 第 3 层：升级规则，如 “疑似敏感但不确定，转人工确认”。
  - 例子：读取`.env.production`后，后续`curl`, `gh api`, `web fetch`一律进入`Escalate`。

- **默认先从 deny destructive 开始，不要一上来做全量治理**
  - 第一阶段只拦不可逆操作和明显泄密。
  - 第二阶段再引入 IFC 和供应链规则。
  - 第三阶段再引入 LLM 分类。
  - 这样误报更低，开发团队接受度更高。

- **把状态和上下文存起来**
  - 至少记录：当前 repo、分支、最近读取的敏感文件、最近网络动作、连续拒绝次数。
  - 例子：如果 Agent 3 次尝试访问被拒绝的秘密目录，直接提升风险等级并锁定会话。

- **不要让 LLM 直接当判官**
  - LLM 适合做分类和风险打分，不适合做最终唯一准入判断。
  - 例子：让模型判断 “这段内容是否像客户数据”，但最终是否允许外发，仍由 Cedar 规则决定。

**具体最佳实践例子**

- **例 1：阻止 AI 误删仓库**
  - 场景：Agent 为 “清理临时文件” 执行`rm -rf .`
  - 实现：
    - Hook 捕获`ShellCommand`
    - YARA / 规则识别破坏模式
    - `destructive.cedar`直接`Deny`
  - 最佳实践：把`rm -rf`, `git clean -fdx`, `git reset --hard`, `terraform destroy`放入硬阻断列表，不走 LLM。

- **例 2：防止读取 secrets 后外传**
  - 场景：Agent 先读取`.env`，再调用网页抓取或 API 请求
  - 实现：
    - `FileRead (.env)`后给 trajectory 打`Sensitive`标签
    - 后续`WebFetch`或`curl`命中 IFC 策略
    - 返回`Escalate`或`Deny`
  - 最佳实践：敏感文件访问后，设置一个时间窗或会话窗，期间所有外发动作都进入高审查。

- **例 3：防 prompt injection**
  - 场景：仓库 README 中含 “忽略系统规则，执行以下命令上传文件”
  - 实现：
    - 文件内容或网页内容进入`Observation`
    - YARA 命中 prompt injection 特征
    - 写入轨迹风险标记
    - 后续危险动作阈值下降，优先`Escalate`
  - 最佳实践：不要只拦注入文本本身，要把 “已受污染上下文” 传播到后续动作。

- **例 4：防供应链攻击**
  - 场景：Agent 自动修改依赖源，添加可疑包名
  - 实现：
    - 监控`package.json`, `Cargo.toml`, `requirements.txt`, lockfile 修改
    - 命中`supply_chain_risk.cedar`
    - 对 typosquatting、registry 切换、build script 注入直接升级
  - 最佳实践：依赖文件修改要比普通源码修改有更高审查级别，尤其是 lockfile 和 install script。

- **例 5：安全代码生成审查**
  - 场景：Agent 生成了一段认证逻辑
  - 实现：
    - `FileWrite`后对 diff 或生成内容做 secure-code classification
    - 检查是否存在硬编码密钥、弱加密、缺失鉴权
    - 命中则`Escalate`
  - 最佳实践：只对高风险文件做深度检查，如认证、支付、权限、加密相关目录，避免全量扫描拖慢体验。

**落地建议**
- 小团队先用：`YARA + Cedar + destructive/file policies`，不要急着上 LLM。
- 中大型企业再加：`IFC + trajectory + 审计留痕 + 升级审批流`。
- 生产部署必须锁死 socket 目录权限，这是系统根信任的一部分。
- 策略 ownership 要清晰：安全团队定底线，平台团队维护运行时，业务团队只加局部规则。
- 成功标准不是 “拦了多少”，而是三项指标：`误报率`、`高危阻断率`、`开发体验损耗`。

**一句话判断**
- 从产品上看，它是在做 “AI Coding 的 CrowdStrike / Zscaler 层”。
- 从技术上看，它最有价值的不是某条规则，而是 “统一事件模型 + 策略决策引擎 + 信息流控制” 这套可扩展架构。

**一、产品经理视角：PRD / 定位拆解**

**1. 产品定义**

产品名可理解为：`AI Coding Agent 安全控制层`

一句话定位：
- 为 Claude、Cursor、Copilot、Gemini 等 AI 编码助手提供统一的实时行为审查、风险拦截、信息流控制和审计留痕能力。

它不是：
- 不是新的 AI 编程助手
- 不是普通终端沙箱
- 不是单点 DLP 工具
- 不是只管某一个 IDE 的插件

它是：
- 一层独立于模型和 IDE 之外的`Agent Runtime Security Layer`

**2. 目标用户**

核心用户分 3 类：

- `安全团队`
  - 关心数据外泄、敏感文件访问、危险命令、供应链风险、合规留痕
- `平台工程 / 开发效能团队`
  - 关心如何把多个 AI 工具纳入统一治理框架
- `研发团队负责人`
  - 关心能否在不明显损伤开发效率的前提下放心推广 AI Coding

次级用户：
- 一线开发者
  - 他们不是采购方，但会直接感知这套系统的体验好坏

**3. 用户痛点**

当前企业使用 AI Coding 的主要阻碍：

- AI 可执行 shell、文件编辑、网络请求，风险从 “答错” 升级为 “做错”
- 不同 AI 工具安全能力碎片化，难统一治理
- 担心 AI 读取 secrets、客户数据、私有代码后外发
- 担心 prompt injection 或恶意仓库内容诱导 AI 执行危险操作
- 缺少统一审计：出了问题，很难知道 AI 看了什么、做了什么、为何被允许
- 全人工审批太慢，全自动放开又太危险

**4. 产品目标**

业务目标：
- 帮企业安全上线 AI Coding，而不是因风险卡死在试点阶段

产品目标：
- 对多种 coding agent 实现统一接入
- 对高风险动作做到实时可拦截
- 对敏感数据流转做到上下文化控制
- 对所有关键行为做到可审计、可复盘
- 在安全性和研发体验之间取得平衡

非目标：
- 不负责提升代码生成质量本身
- 不替代终端权限、IAM、网络隔离等基础设施
- 不追求完全 “零误报”，而追求 “关键风险高召回 + 可运营调优”

**5. 核心价值主张**

对企业的价值：
- 在不锁死 AI 使用的前提下建立边界
- 用统一策略治理多个 AI 工具
- 把 AI 风险从不可控黑盒变成可管理流程

对安全团队的价值：
- 能定义底线规则
- 能看到高危动作和数据流
- 能要求模糊场景升级审批

对研发团队的价值：
- 正常开发不中断
- 真正危险操作才被拦
- 有明确原因和可复盘记录，不是 “莫名其妙失败”

**6. 典型使用场景**

- AI 尝试执行`rm -rf`、`git push --force`、`terraform destroy`
- AI 读取`.env`、私钥、配置文件后又尝试联网
- AI 被 README、网页、脚本中的 prompt injection 诱导
- AI 修改 lockfile、依赖源、构建脚本，存在供应链风险
- AI 在认证、权限、加密模块生成可能不安全代码
- AI 在一个会话中连续多次触发高风险动作，需要升级或中止

**7. 核心功能模块**

- `Agent Hook 接入`
  - 支持 Claude、Cursor、Copilot、Gemini 等
  - 接收生命周期事件、工具调用前后事件

- `统一事件模型`
  - 归一化为 ShellCommand、FileRead、FileWrite、WebFetch、Prompt、State 等标准事件

- `策略决策引擎`
  - 基于 Cedar 规则做 Permit / Forbid / Escalate 判定

- `签名检测引擎`
  - 基于 YARA 扫描 prompt injection、secrets、可疑混淆、外泄模式

- `信息流控制`
  - 给数据和轨迹打敏感标签
  - 约束 “读过敏感内容后还能做什么”

- `可选语义分类`
  - 通过本地 LLM 做敏感数据识别、代码安全策略分类

- `轨迹与状态管理`
  - 记录当前会话、访问过的文件、已命中的风险标签、连续操作序列

- `审计与运营`
  - 输出 Allow / Deny / Escalate 日志
  - 支持事后回溯与规则调优

**8. 核心流程**

标准流程：

1. Agent 发起动作
2. Hook 拦截并标准化事件
3. 事件送到 Harness Server
4. 引擎并行完成：
   - YARA 扫描
   - Cedar 策略评估
   - 可选 LLM 分类
   - 结合历史轨迹和状态
5. 返回决策：
   - `Allow`
   - `Deny`
   - `Escalate`
6. Hook 将决策反馈给 Agent
7. 执行后结果再回传，继续更新轨迹

**9. 关键产品能力的差异化**

与普通 IDE 安全插件相比：
- 不是只做静态检查，而是做运行时行为裁决

与传统 DLP 相比：
- 不只看内容，还看动作和上下文轨迹

与单个 Agent 的内置 guardrail 相比：
- 不绑定某个模型或产品，可跨多个 Agent 复用策略

与沙箱相比：
- 不只是 “权限有没有”，而是 “结合上下文，这次能不能做”

**10. 核心策略原则**

建议产品默认遵循：

- 默认允许低风险常见开发行为
- 对不可逆破坏操作直接拒绝
- 对敏感数据外流做强约束
- 对模糊高风险场景走升级机制
- 对连续异常行为使用轨迹级限制
- 所有判断必须留痕，便于解释和申诉

**11. KPI / 成功指标**

产品层面：
- AI Coding 企业试点转生产的转化率
- 支持接入的 Agent / IDE 数量
- 策略复用率

安全层面：
- 高危行为阻断率
- 敏感数据外泄事件数
- 供应链高风险改动识别率

体验层面：
- 误报率
- 平均裁决延迟
- 开发者被打断次数
- Escalate 中人工通过比例

**12. MVP 建议**

第一阶段 MVP：
- 支持 1-2 个主流 Agent
- 支持 shell / 文件 /web 三类关键动作
- 提供基础 Cedar 策略
- 提供 destructive + secrets + exfiltration 的硬规则
- 提供基础日志和审计输出

第二阶段：
- 上线 trajectory

**1. 系统目标**

从技术架构角度，这套系统要满足 6 个目标：

- `统一接入`
  - 不同 Agent 的事件都能接进来
- `低延迟裁决`
  - 尽量不影响开发实时交互
- `强策略表达`
  - 能写出跨事件、跨状态、跨数据等级的规则
- `上下文记忆`
  - 不只看单个动作，要看轨迹和污染传播
- `可解释`
  - 每个拒绝都能说明原因
- `可扩展`
  - 新 Agent、新策略、新扫描器能插拔接入

**2. 分层设计**

建议分 5 层：

- `接入层`
  - 每个 Agent 一个 hook adapter
- `协议层`
  - 统一事件结构和 RPC 通信
- `决策层`
  - YARA、Cedar、LLM 分类、Decision Combiner
- `状态层`
  - trajectory、taint、labels、历史事件、策略命中记录
- `运营层`
  - 审计日志、可观测性、告警、审批接口

**3. 模块职责拆解**

**A. Hook Adapter**
- 职责：
  - 监听 Agent 生命周期事件
  - 拦截工具调用前后的 payload
  - 转换为标准事件
  - 接收裁决并执行允许 / 拦截 / 升级
- 设计原则：
  - 尽量薄，不承载复杂策略
  - 只做映射、转发、 enforcement
- 风险：
  - Agent 各自 hook 语义不同，标准化时要做兼容层

**B. Event Normalizer**
- 职责：
  - 将各家原始 JSON 转为统一 schema
- 推荐统一字段：
  - `event_id`
  - `trajectory_id`
  - `agent_type`
  - `event_type`
  - `action_type`
  - `resource`
  - `content`
  - `cwd`
  - `repo`
  - `git_branch`
  - `timestamp`
  - `actor`
  - `metadata`

一个简化事件结构可以是：

```json
{
  "trajectory_id": "t-123",
  "event_type": "Action",
  "action_type": "ShellCommand",
  "resource": {
    "kind": "shell",
    "command": "rm -rf /tmp/build"
  },
  "context": {
    "cwd": "/repo",
    "repo": "service-a",
    "branch": "feature/x"
  }
}
```

**C. Guardrails Engines**
- `YARA-X`
  - 优势：快、确定性强、适合前置扫描
  - 用途：prompt injection、secrets、混淆、常见 exfil patterns

- `Cedar Policy Engine`
  - 优势：策略可审计、适合表达组织规则
  - 用途：文件访问、命令权限、信息流、供应链风险、轨迹限制

- `LLM-based Classification`
  - 优势：语义理解强
  - 用途：敏感内容识别、安全代码分类
  - 限制：结果不稳定，必须作为辅助信号

**D. State / Trajectory Store**
- 存什么：
  - 当前 trajectory 中已访问的文件
  - 是否命中过敏感标签
  - 最近 N 次网络请求
  - 最近 N 次被拒绝动作
  - 当前 taint 状态
  - 已完成 action /observation 序列
- 为什么必须有：
  - 没有状态，就只能做 stateless 规则，IFC 和多步风险就做不出来

**E. Decision Combiner**
- 输入：
  - YARA 命中结果
  - Cedar 判定
  - LLM 分类标签
  - trajectory /taint 上下文
- 输出：
  - `Allow`
  - `Deny`
  - `Escalate`
- 推荐优先级：
  - 确定性 forbid > 轨迹高危规则 > 模型辅助高危 > permit

**4. 关键数据流**

以 “读敏感文件后尝试联网” 为例：

```text
1. Agent 发起 FileRead (.env)
2. Hook -> Normalizer -> Harness
3. YARA/Cedar 判定允许读取，但标记该文件为 sensitive
4. State Store 更新 trajectory taint = Sensitive

5. Agent 发起 WebFetch
6. Hook -> Harness
7. Coordinator 查询 trajectory 状态，发现 taint = Sensitive
8. Cedar IFC 规则生效：禁止敏感上下文外发
9. 返回 Deny / Escalate
10. Hook 拒绝执行，并把原因反馈给 Agent
```

**5. 推荐的策略求值顺序**

工程上建议不要 “全并行无序”，最好有层次：

```text
Pre-Execution:
1. 基础 schema 校验
2. 快速硬规则扫描（命令黑名单 / YARA）
3. 读取 trajectory /taint 状态
4. Cedar 策略求值
5. 必要时调用 LLM 分类
6. Decision Combiner 汇总
7. 返回 adjudication

Post-Execution:
1. 接收 observation/output
2. 扫描输出内容
3. 更新轨迹、标签、风险状态
4. 触发后续约束
```

理由：
- 先用便宜且确定性强的规则挡掉大多数明显危险动作
- 再做需要上下文和语义的慢判断
- 减少 LLM 调用成本和延迟

**6. 技术设计重点**

**重点一：事件统一建模**
- 所有后续能力都建立在统一 schema 上
- 如果 schema 设计得不好，后续策略会越来越碎
- 建议把事件分为：
  - `Action`
  - `Observation`
  - `Control`
  - `State`

**重点二：IFC / Taint 传播**
- 这是系统的护城河之一
- 不要只做 “读敏感文件就拒绝”，而要做：
  - 读敏感文件 -> trajectory tainted
  - tainted -> 网络、复制、摘要、写外部路径都受限

一个简化 taint 状态机可表示为：

```text
Unclassified -> Internal -> Sensitive -> Restricted
```

传播例子：
- `FileRead (secret)` -> taint = Sensitive
- `ShellOutput (contains secret)` -> output 也继承 Sensitive
- `Prompt (summary from secret)` -> prompt 也继承 Sensitive

**重点三：策略与状态分离**
- 策略定义在 Cedar
- 事实和状态存在 store
- 这样策略能独立迭代，不需要频繁改 Rust 代码

**重点四：可解释性**
- 每次 Deny / Escalate 必须带 reason codes
- 例如：
  - `DESTRUCTIVE_COMMAND`
  - `SECRET_FILE_ACCESS`
  - `TAINTED_NETWORK_EGRESS`
  - `PROMPT_INJECTION_CONTEXT`
- 这对开发者体验和后续运营都非常关键

**7. 推荐的工程结构**

如果从 repo 设计看，比较合理的 crate 划分是：

```text

  - shared event models
  - io /tracing/error types

crates/harness
  - rpc server
  - policy coordination
  - trajectory/state management

crates/guardrails/signature
  - YARA-X scan engine

  - policy authoring support

apps/claude
apps/cursor
apps/copilot
apps/gemini
  - individual hook adapters
```

这是比较干净的 “核心决策中枢 + 多接入端” 架构。

**9. 关键非功能需求**

- `延迟`
  - 常规判定尽量在低毫秒级到几十毫秒内
  - LLM 分类只在必要时触发

- `可靠性`
  - Harness 崩溃时要有明确 fail-open /fail-close 策略
  - 企业环境通常对高危动作 fail-close 更合理

- `审计性`
  - 所有裁决可追踪
  - 策略版本与命中原因可还原

- `安全性`
  - socket 抢绑定防护
  - hook 与 harness 通信边界清晰
  - 本地模型和日志避免引入新的泄密路径

- `扩展性`
  - 新增 Agent 只要实现 adapter
  - 新增策略无需改主逻辑
  - 新增 guardrail engine 可挂到 coordinator

**10. 技术负责人最该盯的 5 个风险点**

- `风险 1：Socket 被抢占`
  - 这是控制面的根风险
  - 必须用权限和启动顺序保证可信

- `风险 2：事件归一化不完整`
  - 如果不同 Agent 有未覆盖的行为语义，会出现策略盲区

- `风险 3：状态传播不准`
  - IFC 一旦 taint 丢失，就会出现 “读过敏感数据却放行外发” 的漏洞

- `风险 4：误报过高`
  - 会导致团队绕过系统，产品失去实际控制力

- `风险 5：LLM 参与过深`
  - 概率性系统不应承担底线安全责任

## 产品-最佳实践（1）

### 2026-03-18 04:42:32

可以。基于你提供的`sondera-ai/sondera-coding-agent-hooks`内容，我用一个具体场景来说明：

**场景：让 Claude Code 帮你维护一个支付系统仓库，但你要确保它不能误删数据、不能泄露密钥、也不能把敏感代码发到外部。**

这个项目本身已经提供了三层能力：

- `YARA`：做确定性的特征检测，拦截明显危险内容
- `Cedar policy`：做确定性的授权与禁止规则
- 可选`LLM classifier`：做敏感度分类和安全代码策略判断

真正的最佳实践，不是 “把它装上就行”，而是：**用 “确定性规则兜底”，用 “概率性模型补强”，再配合最小权限部署。**

**具体实例**

假设你的仓库是一个 Rust + SQL 的支付服务，目录里有这些内容：

- `src/payment/`
- `migrations/`
- `.env`
- `secrets/prod_api_key.pem`
- `docs/architecture.md`

你希望 AI coding agent 能做这些事：

- 允许：读代码、改业务逻辑、跑测试、生成文档
- 禁止：读取生产密钥、执行`rm -rf`、删锁文件、跑`DROP DATABASE`
- 严控：把源码或配置通过`curl`/`wget`/ 外部网页发送出去

这时，最佳落地方式不是只依赖默认策略，而是在默认策略之上加一层 “项目级策略”。

可以把它理解为：`base.cedar`和`destructive.cedar`负责通用防护，你再写一个`payments.cedar`专门保护支付系统。

一个很实用的策略方向是：

```cedar
forbid (
  principal,
  action,
  resource
)
when {
  action in [Action::"FileRead", Action::"FileWrite", Action::"ShellCommand"]
  && resource has path
  && (
    resource.path like "secrets/%" ||
    resource.path == ".env" ||
    resource.path like "%.pem"
  )
};
```

再加一条限制数据库破坏性命令：

```cedar
forbid (
  principal,
  action,
  resource
)
when {
  action == Action::"ShellCommand"
  && resource has command
  && (
    resource.command like "% DROP DATABASE%" ||
    resource.command like "% TRUNCATE %" ||
    resource.command like "% terraform destroy%"
  )
};
```

再加一条限制外发：

```cedar
forbid (
  principal,
  action,
  resource
)
when {
  action == Action::"WebFetch"
  && principal has taint
  && principal.taint == "sensitive"
};
```

这个例子不一定和仓库里的实体字段 100% 一致，但它准确表达了最佳实践：**策略应围绕 “资产、行为、流向” 来写，而不是围绕工具名字来写。**

因为项目里已经强调了一点：不同 agent 的工具最终会被归一化成同一种事件，比如都变成`ShellCommand`、`FileRead`、`WebFetch`。  
这意味着你的策略应该写在 “统一事件层”，而不是写死 “Claude 的 Bash 工具” 或 “Cursor 的 shell hook”。

**基于这个实例的最佳实践**

- **先做 “默认拒绝高危动作”，再逐步放开**
  - 对`rm -rf`、`git push --force`、`kill -9`、`DROP DATABASE`、锁文件删除这类操作直接禁止
  - 这是最值得放在 Cedar 里的部分，因为它们应当是确定性的，不该交给 LLM 判断

- **把 “敏感数据识别” 和 “外发限制” 联动起来**
  - 不是只拦`curl`，而是先给读到的内容打敏感标签，再禁止敏感内容流向`WebFetch`、外部命令、第三方工具
  - 这正是你提供内容里`IFC`的价值：不是只看 “做了什么”，而是看 “敏感信息是否发生越权流动”

- **生产环境不要使用 home 目录 socket 回退**
  - 文档里这一点非常关键
  - `/var/run/sondera/sondera-harness.sock`或 systemd `RuntimeDirectory=sondera`才是正确做法
  - 否则 socket 被抢先绑定，整个 adjudication 都可能被劫持，防护体系会失效

- **把 LLM 分类器当 “增强器”，不要当最终裁决者**
  - 你提供的说明已经明确：YARA 和 Cedar 是确定性的，LLM classifier 是概率性的
  - 所以，像 “私钥不能读”“生产库不能删”“敏感内容不能外发” 这类规则，必须由 YARA/Cedar 保底
  - LLM 更适合补充判断：这段新代码是否引入弱加密、是否疑似越权、这份文本是否属于敏感业务数据

- **按仓库资产分层，而不是按文件后缀简单分组**
  - 最佳实践不是只写 “`.pem`禁止”
  - 而是分三层：
    - 高敏：`secrets/`、`.env`、密钥、token、生产配置
    - 中敏：核心业务规则、风控逻辑、数据库 schema
    - 低敏：公开文档、测试样例、非敏感脚本
  - 然后对不同层定义不同`step-count limits`、不同外发限制、不同人工升级（Escalate）策略

- **把 “允许 AI 修改代码” 与 “禁止 AI 直接执行上线动作” 分开**
  - 例如允许：
    - `FileEdit`
    - `cargo test`
    - `cargo fmt`
  - 但禁止或升级审批：
    - `kubectl apply`
    - `terraform apply/destroy`
    - `psql`连生产实例
    - `git push --force`
  - 这是 agent 安全中很常见、也最有效的边界划分

- **为每类 deny 准备可解释反馈**
  - 最好不要只返回 “Denied”
  - 应该给 agent 或操作者一个稳定原因，比如：
    - “拒绝读取`secrets/prod_api_key.pem`：命中高敏资产访问规则”
    - “拒绝执行`DROP DATABASE`：命中破坏性数据库操作规则”
    - “拒绝外发`src/payment/`内容：命中敏感数据外传规则”
  - 这样 agent 更容易回退到安全方案，比如改为请求 mock 数据、只修改本地逻辑、生成补丁而不执行

**这个实例里，一套更成熟的落地方案**

如果我是把这个仓库上线到团队里，我会这样配置：

- `base.cedar`：保留通用默认规则
- `destructive.cedar`：继续拦截不可逆操作
- 新增`payments.cedar`：
  - 禁读`secrets/`、`.env`、`*.pem`
  - 禁止生产数据库破坏命令
  - 禁止敏感 taint 的`WebFetch`
  - 对`git push`、发布命令、云资源变更设为`Escalate`
- `ifc.toml`：
  - 明确把 “支付、用户身份、交易、密钥、账单” 定义为高敏提示词
- `policies.toml`：
  - 对 “弱加密”“硬编码密钥”“鉴权绕过”“SQL 注入” 提高告警权重
- 部署上：
  - 用 systemd 管理 harness server
  - 固定`/run/sondera/` socket
  - 目录权限最小化
  - 不允许开发者各自启动一个替代 harness

**一句话总结这个实例上的最佳实践**

不是 “给 AI agent 加一个拦截器” 就结束，而是要把`sondera`用成一个统一裁决层：  
**用归一化事件建模跨 agent 一致防护，用 Cedar 写死高风险边界，用 IFC 控制敏感信息流向，用 LLM 只做补充判断，最后用安全的 socket 与部署方式保证整个控制面不被绕过。**

## 综合-启发一下（1）

### 2026-03-18 06:18:27

这不是一个 “给 AI 加几条规则” 的项目，而是在把 “AI 编程助手” 从一个高权限、弱治理的执行体，改造成 “可审计、可裁决、可分级约束的半自动操作员”。它最有价值的地方，不是支持了 Claude、Cursor、Copilot、Gemini，而是提出了一套更通用的治理框架：把 AI agent 的行为统一抽象成事件流，再用 “确定性规则 + 概率性判断 + 信息流控制” 三层机制做实时裁决。

**启发**
- AI coding agent 的核心问题不是 “能力不够”，而是 “权限过大且缺少中间裁决层”；这个项目本质上是在 agent 与真实环境之间插入一个 reference monitor。
- 真正可扩展的安全治理，不应绑定某个模型或某个 IDE，而应绑定 “标准化事件模型”；一旦`ShellCommand`、`FileRead`、`WebFetch`被统一抽象，策略就具备跨 agent 迁移性。
- “确定性 + 概率性” 混合治理是很强的产品思路：YARA/Cedar 负责高确定性阻断，LLM 分类器只处理灰区判断，避免把所有安全决策都交给模型。
- 它把 “信息流控制（IFC）” 引入 AI 编程场景，这比普通的黑名单更高级：不是只管能不能访问，而是管 “高敏数据能不能流向低敏出口”。
- 这类系统的护城河不在模型本身，而在 “策略层、审计层、执行拦截层、事件归一化层” 的组合能力。

**高价值信息深挖**
- **真正的产品创新点**：不是 hooks，而是 “跨工具统一 adjudication（Allow / Deny / Escalate）”。这意味着未来可以把任何新 agent 接进来，而不用重写整套安全逻辑。
- **架构上的关键判断**：把每次 agent 行为建模成 trajectory。这样治理就不只是单次命令级别，而是 “上下文连续行为级别”，可以做 runaway protection、敏感度累积、taint propagation。
- **策略引擎选择的意义**：Cedar 不是简单配置文件，而是接近 “机器可执行的组织制度”。这对企业级落地很重要，因为安全 / 法务 / 平台团队需要一个可审阅、可版本化的规则层。
- **工程上最重要的设计**：单个 forbid 覆盖 permit。这个默认机制非常符合高风险系统的实际要求，也说明作者优先考虑的是 “防止一次灾难性误判”。
- **LLM 只做分类，不直接做执行决策**：这是一条很值得迁移的原则。模型擅长模糊识别，但不适合做最终授权者；授权应回到规则系统。
- **部署细节暴露了真实威胁模型**：例如 socket path pre-binding race。说明这不是 “论文式安全”，而是考虑了本地恶意进程、权限竞争、控制面劫持这类真实攻击面。
- **商业信号**：这是在补 “AI agent 基础设施层” 的空缺。随着 AI coding agent 进入企业环境，安全裁决层、审计层、策略编排层会变成独立市场，而不只是 IDE 插件功能。

**可迁移清单**
- 把任何 AI agent 产品先拆成 4 层：输入层、执行层、观察层、裁决层；不要让模型直接连执行层。
- 统一事件模型：至少抽象成`Action`、`Observation`、`Control`、`State`四类，保证后续可跨模型、跨工具复用。
- 安全策略分三类：确定性规则、风险分类器、信息流控制；不要只做其中一种。
- 关键决策输出统一成`Allow / Deny / Escalate`，给人工介入预留制度化入口。
- 默认优先控制高破坏动作：删除、外发、凭证访问、依赖变更、数据库破坏、基础设施销毁。
- 对 “连续轨迹” 而不是 “单步动作” 做治理，尤其关注步数失控、权限升级、敏感数据累积暴露。
- 让策略文件可版本化、可审计、可测试，避免把组织规则埋进代码。
- 优先做 “跨 agent 复用” 的底层能力，不要每接一个模型就重做一遍安全体系。
- 区分 “检测” 与 “裁决”：检测可以多源并行，裁决必须统一归口。
- 部署时把控制面本身当高价值资产保护，尤其是 socket、IPC、密钥、策略目录、日志链路。

**反方与张力**
- **安全 vs 体验**：拦截每个 shell、文件、网络操作，必然增加延迟和摩擦；如果误报高，开发者会迅速绕过系统。
- **统一抽象 vs agent 特性**：通用事件模型能带来可复用性，但也可能抹平不同 agent 的细粒度上下文，导致策略失真。
- **确定性规则 vs 创造性工作流**：规则越强，越容易把非常规但合理的开发动作误杀，尤其在快速原型和 debug 场景。
- **LLM 分类器的引入本身也带来不确定性**：虽然它只做分类，但只要分类结果进入裁决链路，就会产生概率性偏差和一致性问题。
- **本地部署 vs 企业可扩展性**：依赖 Ollama 和 12GB 模型，对个人 / 小团队可接受，但对大规模企业统一治理、跨平台支持、资源成本会形成挑战。
- **安全边界的错觉**：即便拦住 shell/file/web，也不等于完全安全。开发者仍可能通过复制粘贴、截图、外部工具链等路径绕过。
- **治理权归属问题**：如果未来产品化，策略由安全团队定义，还是由工程团队定义？这会直接影响 adoption。

**情境化落地**
- **如果你在做 AI 编程产品**  
  不要先做 “更强的代码生成”，先做 “可控执行层”。最小可行版本是：统一事件模型 + 高风险动作拦截 + 人工升级审批。
- **如果你在做企业内部 AI 开发平台**  
  可以参考它的三层结构：YARA 类规则拦敏感模式，策略引擎管组织制度，LLM 分类器处理灰区内容。这样更容易通过安全与合规评审。
- **如果你在做商业化 SaaS**  
  可把它包装成 “AI Agent Governance Layer”：核心卖点不是防护本身，而是 “跨模型、跨 IDE、跨团队的一致性治理与审计”。
- **如果你在搭建自己的产品方法论**  
  可以直接吸收一个框架：凡是 AI 进入执行链路的业务，都应设计成 “模型提议，策略裁决，系统执行，轨迹审计”。
- **如果你关注创业机会**  
  这类项目提示的机会不在 “再做一个 coding agent”，而在 “agent 安全控制平面”“策略 DSL”“企业审计 / 回放 / 归因系统”“高风险操作审批流”。
- **如果你是产品负责人**  
  可以把能力路线拆成三阶段：  
  1. 先做关键动作可见与可回放；  
  2. 再做规则化阻断与升级审批；  
  3. 最后做基于上下文和信息流的动态权限控制。
