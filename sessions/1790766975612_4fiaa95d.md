## 分析要点

- **核心高价值点**：页面反复刷新不一定源于反自动化检测：将“加载中或状态未知”误判为“未登录”，也会导致程序重复导航并打断登录流程。
- **留存建议**：选择性保留故障分类、登录状态处理和验证边界，绕过脚本仅作待验证线索（后段包含可复用的故障分类、避免重复导航的状态判断、刷新循环诊断和业务成功确认方法，对浏览器Agent工程具有参考价值。）
- **不足**：全文重复较多，多种方案已被反馈失效；行为识别及浏览器指纹相关主张缺少可核查证据，不能作为稳定解决方案直接采信。

**知识要点**

- 排查自动化失败时，应区分平台身份与访问限制、网页交互与业务确认、本地程序与驱动错误；超时本身不能证明触发了反爬。
- 登录状态应区分已在登录或验证页、状态未知或加载中、明确未登录，避免在状态不明时反复跳转。
- 点击成功、出现消息气泡或上传完成不等于业务成功；应依据本次新增消息的送达或已读标记确认结果，短时页面观察也不能证明长期稳定。

**行动项**

- 检查登录处理分支：加载中或状态未知时等待并复查，仅在明确未登录且不在登录页时执行导航。
- 监听主框架导航并设置刷新循环诊断阈值，触发后停止自动操作、保留页面；将阈值标注为本地诊断配置而非平台规则。
- 对明确的验证、访问频率和次数限制提示暂停任务，并分别验证首页、登录和实际业务流程，不以局部短时测试宣称完整修复。

#### 网站对抗 DevTools / 自动化RPA 的原理

```
function checkDevTools() {
    const aLargeObjectOrArray = [{}] // 一个很大的、控制台打印时需要处理很长时间的对象
    let printStartTime = new Date()
    console.table(aLargeObjectOrArray) // 某个在控制台开启情况下会特别耗时的动作
    let printEndTime = new Date()
    // 判断打印前后，时间差是否大于某个值（可能是个经验值）- 控制台未打开的情况下，打印日志应当是不耗时的
    // 如果打印所耗费时间过长，就认为控制台打开了
    if (printEndTime - printStartTime > 50) {
        return true
    }
    // 否则正常执行
    return false
}
```

实际代码比上方代码复杂，见 [https://github.com/theajack/disable-devtool](https://github.com/theajack/disable-devtool) - 这个库甚至判断了vConsole

我大概说下我的解决步骤

#### 解决步骤

1. 页面加载前，把console相关函数覆盖为空函数  
   主要用到的Puppeteer的API是： [https://pptr.dev/api/puppeteer.page.evaluateonnewdocument](https://pptr.dev/api/puppeteer.page.evaluateonnewdocument)  
   对应到Playwright的API似乎是： [https://playwright.dev/java/docs/api/class-page#page-add-init-script](https://playwright.dev/java/docs/api/class-page#page-add-init-script)  
   把要执行的函数，通过这两个API传进去

因此需要在页面中执行类似

```
console.log = () => {}
```

这样的函数

1. 函数被覆盖后，不能让对方网站检测到我们覆盖了相关函数  
   步骤1中我们覆盖了页面中的原生方法console.log，但这个覆盖是可以被轻松检测的；对方网站可以执行：

```
console.log.toString()
```

或

```
Function.prototype.toString.call(console.log)
```

来检测函数是不是被我们覆盖掉的。（我看了下Boss直聘代码， **会上报有关“函数是否被覆盖”的数据埋点** ）

console.log

- 没有被覆盖掉的情况下，如上代码执行后返回值为 `function log() { [native code] }`
- 被覆盖掉的情况下（假设是按步骤1覆盖的），如上代码执行后返回值为 `() => {}`

一般的检测逻辑是检查返回值中是否包含 `[native code]`

为此需要覆盖函数原型上的 原生方法 `Function.prototype.toString` ，来防止对方网站判断。需要做的大致逻辑：

```
const originFunctionPrototypeToString = Function.prototype.toString
Function.prototype.toString = function toString(...args) {
    if (this === console.log) {
        return `function log() { [native code] }`
    }
    else {
        return originFunctionPrototypeToString.apply(this, args)
    }
}
```

同样，我们也要避免“覆盖函数原型上的 原生方法 `Function.prototype.toString` ”这个动作被对方网站发现 - 因为对方网站可以再执行：

```
Function.prototype.toString.toString()
```

或

```
Function.prototype.toString.call(Function.prototype.toString)
```

来检测函数是不是被我们覆盖掉的。因此需要进一步处理。

#### 最终完整的需要在页面初始化时即执行的函数

下方代码是AI生成的，考虑得更完整一些

```
() => {
  (() => {
    "use strict";
    /* -------------------------------------------------------
     * 1. 保存原生 Function.prototype.toString
     * ----------------------------------------------------- */
    const nativeFunctionToString = Function.prototype.toString;

    /* -------------------------------------------------------
     * 2. WeakMap：函数 → 伪原生源码
     * ----------------------------------------------------- */
    const nativeSourceMap = new WeakMap();

    /* -------------------------------------------------------
     * 3. 注册伪原生源码
     * ----------------------------------------------------- */
    const registerNativeSource = (fn, source) => {
      try {
        nativeSourceMap.set(fn, source);
      } catch (_) {}
    };

    /* -------------------------------------------------------
     * 4. 劫持 Function.prototype.toString
     * ----------------------------------------------------- */
    Object.defineProperty(Function.prototype, "toString", {
      configurable: true,
      writable: true,
      value: function toString() {
        if (nativeSourceMap.has(this)) {
          return nativeSourceMap.get(this);
        }
        return nativeFunctionToString.call(this);
      },
    });

    /* -------------------------------------------------------
     * 5. 伪装 Function.prototype.toString 自身
     * ----------------------------------------------------- */
    registerNativeSource(
      Function.prototype.toString,
      nativeFunctionToString.toString(),
    );

    /* -------------------------------------------------------
     * 6. stealthify：包装函数但保持“原生外观”
     * ----------------------------------------------------- */
    const stealthify = (obj, prop, handler) => {
      const original = obj[prop];
      if (typeof original !== "function") return;

      const wrapped = function (...args) {
        return handler.call(this, original, args);
      };
      const namePropertyDescriptor = Object.getOwnPropertyDescriptor(
        wrapped,
        "name",
      );
      // 处理函数 name 属性
      Object.defineProperty(wrapped, "name", {
        ...namePropertyDescriptor,
        value: prop,
      });
      // 保留 prototype（某些函数有）
      try {
        Object.setPrototypeOf(wrapped, Object.getPrototypeOf(original));
      } catch (_) {}

      // 注册伪原生源码（直接复用原函数的 native 表现）
      registerNativeSource(wrapped, nativeFunctionToString.call(original));

      // 用 defineProperty 保持 descriptor 接近原生
      const desc = Object.getOwnPropertyDescriptor(obj, prop);
      Object.defineProperty(obj, prop, {
        ...desc,
        value: wrapped,
      });
    };

    /* -------------------------------------------------------
     * 7. 示例：stealth console.log / debug / info
     * ----------------------------------------------------- */
    const filterConsoleArgs = (args) =>
      args.map((arg) => {
        if (arg && typeof arg === "object") {
          // 防止 getter / Proxy / 大对象触发
          return {};
        }
        return arg;
      });

    ["log", "debug", "info", "warn", "error", "dir", "table", "debug"].forEach(
      (name) => {
        stealthify(console, name, (original, args) => {
          // ❗不传递原始对象，避免 DevTools / CDP 展开
          return original.apply(console, filterConsoleArgs(args));
        });
      },
    );

    /* -------------------------------------------------------
     * 8. 防御性补丁（可选但强烈建议）
     * ----------------------------------------------------- */

    // 防止检测 toString 被替换
    registerNativeSource(
      registerNativeSource,
      "function registerNativeSource() { [native code] }",
    );
  })();
}
```

经过如上处理，网站应该就跳不走了

#### BTW

我有注意到其它竞品 - 一键职达（macOS版本），没有受此影响（但用户主动开启DevTools依然会跳走），而且使用过程中会弹出程序请求自动控制的权限

因此我怀疑：

1. 通过“打印日志检测时间差来判断浏览器是否开启DevTools/是否正在被自动化控制”，仅适用于基于CDP实现的自动化 - 一旦产生CDP会话，console里的内容就一定会被处理，从而产生处理时间上的开销，导致被检测到
2. 一键职达（macOS版本）是通过macOS相关API或功能实现的浏览器自动化，而非我们使用的基于CDP实现（由Puppeteer/Playwright封装）的自动化

我是 [AntiDebug\_Breaker](https://github.com/0xsdeo/AntiDebug_Breaker) 插件的作者，实际上核心解决方案并没有多复杂，主要是解决两个方法即可：

- console.table
- performance.now

在之前我写过一篇文章： [JS逆向系列-无感绕过一类运行时间差反调试](https://mp.weixin.qq.com/s/JZu-fknVdEpaI5anzSlLjg) ，在这篇文章中我详细讲述了为什么要hook掉console.table，而hook performance.now的原因实际上是因为boss增强了 [disable-devtool](https://github.com/theajack/disable-devtool) 这个库的检测机制，没错，boss采用的就是这个库的反调试。

当然了，boss不止增强了这一处的检测机制，但在这里我也并不想多说其他增强点，我主要是来分享解决方案的，下面是可使用油猴注入的版本：

```
// ==UserScript==
// @name         AntiAnti Hook
// @namespace    https://github.com/0xsdeo/Hook_JS
// @version      0.2
// @description  反Hook检测
// @author       0xsdeo
// @match        *://*/*
// @run-at       document-start
// @icon         data:image/gif;base64,R0lGODlhAQABAAAAACH5BAEKAAEALAAAAAABAAEAAAICTAEAOw==
// @grant        none
// ==/UserScript==

(function () {
    'use strict';

    // 必须返回随时间递增的值，否则会被时序检测（t1===t2）判定为 hook 并触发内存炸弹
    const navStart = (typeof performance !== 'undefined' && performance.timing)
        ? performance.timing.navigationStart
        : Date.now();

    console.table = function () {};

    performance.now = function () {
        return Date.now() - navStart;
    };

    const methods = ['console.table', 'performance.now'];

    function initAntiAntiHook() {
        try {
            const hookedFunctions = new Map();
            for (let methodPath of methods) {
                let ref = window;
                let parts = methodPath.split('.');
                try {
                    for (let i = 0; i < parts.length - 1; i++) {
                        ref = ref[parts[i]];
                        if (!ref) break;
                    }
                    if (ref) {
                        const fn = ref[parts[parts.length - 1]];
                        if (typeof fn === 'function') {
                            hookedFunctions.set(fn, parts[parts.length - 1]);
                        }
                    }
                } catch (e) {}
            }

            if (hookedFunctions.size === 0) return;

            let temp_toString = Function.prototype.toString;
            Function.prototype.toString = function () {
                if (this === Function.prototype.toString) {
                    return 'function toString() { [native code] }';
                } else if (this === Function.prototype.constructor &&
                    hookedFunctions.has(Function.prototype.constructor)) {
                    return 'function Function() { [native code] }';
                } else if (hookedFunctions.has(this)) {
                    const funcName = hookedFunctions.get(this);
                    return `function ${funcName}() { [native code] }`;
                }
                return temp_toString.apply(this, arguments);
            };

            const hookedMethodNames = new Map();
            methods.forEach(path => {
                let ref = window;
                let parts = path.split('.');
                try {
                    for (let i = 0; i < parts.length - 1; i++) {
                        ref = ref[parts[i]];
                        if (!ref) break;
                    }
                    if (ref) {
                        const fn = ref[parts[parts.length - 1]];
                        if (typeof fn === 'function') {
                            hookedMethodNames.set(path, fn);
                        }
                    }
                } catch (e) {}
            });

            const objectHooksMap = new Map();
            methods.forEach(path => {
                const parts = path.split('.');
                const rootParts = parts[0] === 'window' ? parts.slice(1) : parts;
                if (rootParts.length < 2) return;
                const rootName = rootParts[0];
                const remaining = rootParts.slice(1);
                const fn = hookedMethodNames.get(path);
                if (!fn) return;
                if (!objectHooksMap.has(rootName)) objectHooksMap.set(rootName, []);
                objectHooksMap.get(rootName).push({ remaining, fn });
            });

            if (!objectHooksMap.has('Function')) objectHooksMap.set('Function', []);
            const existsToString = objectHooksMap.get('Function')
                .some(({ remaining }) => remaining.join('.') === 'prototype.toString');
            if (!existsToString) {
                objectHooksMap.get('Function').push({
                    remaining: ['prototype', 'toString'],
                    fn: Function.prototype.toString
                });
            }

            let property_accessor = Object.getOwnPropertyDescriptor(HTMLIFrameElement.prototype, "contentWindow");
            let get_accessor = property_accessor.get;

            Object.defineProperty(HTMLIFrameElement.prototype, "contentWindow", {
                get: function () {
                    let iframe_window = get_accessor.apply(this);

                    iframe_window = new Proxy(iframe_window, {
                        get: function (target, property, receiver) {
                            if (typeof property === 'string') {
                                for (const [fullPath, fn] of hookedMethodNames.entries()) {
                                    if (fullPath.endsWith('.' + property) ||
                                        fullPath === property) {
                                        return fn;
                                    }
                                }
                                if (objectHooksMap.has(property)) {
                                    const obj = Reflect.get(target, property, target);
                                    if (obj !== null && (typeof obj === 'object' || typeof obj === 'function')) {
                                        objectHooksMap.get(property).forEach(({ remaining, fn }) => {
                                            let ref = obj;
                                            try {
                                                for (let i = 0; i < remaining.length - 1; i++) {
                                                    ref = ref[remaining[i]];
                                                    if (!ref) return;
                                                }
                                                ref[remaining[remaining.length - 1]] = fn;
                                            } catch (e) {}
                                        });
                                    }
                                    return obj;
                                }
                            }
                            const value = Reflect.get(target, property, target);
                            if (typeof value === 'function') {
                                return value.bind(target);
                            }
                            return value;
                        },
                    });

                    return iframe_window;
                }
            });

        } catch (e) {
            console.error('AntiAnti_Hook: 初始化失败', e);
        }
    }

    initAntiAntiHook();

})();
```

#### 问题现象

- 或者登录成功后，开始投递时 **页面不断刷新/闪退**

#### BOSS检测机制揭秘

根据 [GitHub Discussion #250](https://github.com/loks666/get_jobs/discussions/250) 和实际逆向分析，BOSS使用了以下检测手段：

##### 1\. disable-devtool 库（核心）

BOSS集成了开源反调试库 `disable-devtool` ，主要通过以下方式检测：

```
// BOSS的检测逻辑（简化版）
function checkDevTools() {
    let start = performance.now()
    console.table(largeObject)  // DevTools打开时执行很慢
    let end = performance.now()
    if (end - start > 50) {     // 超过50ms就认为DevTools开着
        window.location.href = 'about:blank'  // 跳转到空白页！
    }
}
```

##### 2\. CDP远程调试端口检测

#### 最终解决方案

##### 核心原理

```
┌──────────────────────────────────────────────────────────┐
│ 之前（失败）：Playwright自带Chromium → 秒被检测           │
│ 之前（失败）：CDP connectOverCDP → --remote-debugging-port│
│ 现在（成功）：launchPersistentContext + 系统Chrome        │
│              + 反检测脚本 + 持久化Profile                  │
└──────────────────────────────────────────────────────────┘
```

##### 三个关键改动

**1. PlaywrightManager.java — 用 `launchPersistentContext` 代替 `launch`**

```
// 错误做法（会被检测）
browser = playwright.chromium().launch(...)
context = browser.newContext(...)

// 正确做法（不会被检测）  
context = playwright.chromium().launchPersistentContext(
    profileDir,  // 持久化Profile目录
    new BrowserType.LaunchPersistentContextOptions()
        .setExecutablePath("C:/Program Files/Google/Chrome/Application/chrome.exe")
        .setLocale("zh-CN")
        .setTimezoneId("Asia/Shanghai")
);
```

**2. 反检测脚本 — hook `console.table` 和 `performance.now`**

```
// 关键hook 1：覆盖console.table（BOSS用它检测DevTools）
console.table = function() {};
console.table.toString = function() { 
    return 'function table() { [native code] }'; 
};

// 关键hook 2：降低performance.now精度（BOSS检测微秒级时间差）
performance.now = function() {
    return Date.now() - performance.timeOrigin;
};
```

**3. 不暴露CDP调试端口**

Chrome启动参数中 **绝对不能** 包含 `--remote-debugging-port` 。

#### 常见问题

##### Q: 启动后Chrome打开了但BOSS页面一片空白？

A: 等几秒让页面加载。如果持续空白，关闭Chrome和命令行，重新运行 `start.bat` 。

##### Q: BOSS登录后又被踢出去了？

A: 确保是用项目自己打开的Chrome（不要用你自己平时用的Chrome）。`.chrome-profile` 文件夹里的登录态是独立的。

##### Q: 投递到一半停下了？

A: 可能是遇到滑块验证。在Chrome窗口里手动拖一下滑块，程序会自动检测并继续。

##### Q: 想完全重置？

A: 删除项目目录下的 `.chrome-profile` 文件夹，重新运行 `start.bat` 。

##### Q: 投递成功率低？

A: 检查以下几点：

- 是否已登录目标平台
- 关键词是否合理（不要太宽泛）
- 查看 `target/logs/get-jobs.log` 日志了解具体错误

async def guard(page):
    if page.is_closed():
        raise RuntimeError("任务页面已关闭")

    body = await page.locator("body").inner_text(timeout=5000)
    if "verify-slider" in page.url or CHALLENGE.search(body):
        raise RuntimeError("发现验证或访问频率提示，暂停并人工处理")
    if LIMIT.search(body):
        raise RuntimeError("平台提示次数限制，停止本轮任务")

#### BOSS 直聘自动化为何会跳转、刷新：反调试检测、行为风控与程序自身问题

这篇 GitHub 讨论围绕一个问题展开：为什么用 Playwright、Puppeteer 等工具操作 BOSS 直聘时，页面会回退、跳到空白页或不断刷新？讨论从控制台反调试检测，逐步延伸到浏览器自动化信号、鼠标与输入行为、操作系统指纹，以及程序自身的登录逻辑。**最重要的结论是：这些现象可能来自不同原因，局部修复不等于解决全部风控；讨论中没有得到充分验证、长期稳定的通用方案。**

##### 1. 页面“被关闭”，可能是网站跳转，也可能是程序反复导航

发帖者最初观察到：手动操作 Playwright 打开的浏览器时，页面可以正常使用；一旦由程序控制，或通过 CDP 连接浏览器，就会出现页面回退，看起来像“被关闭”。

后续反馈进一步区分了几种情况：

- 有人解决了首页打不开，但打开岗位页、开始投递时，又出现持续刷新。
- 有人安装反检测脚本后暂时正常，但打开开发者工具仍会跳走。
- 有人后来发现，刷新循环至少有一部分来自自己的程序：页面还没加载完，就被判断为未登录，于是再次跳转登录页。

**因此，“空白页”“刷新”“等待超时”只是现象，不能单凭这些现象断定触发了哪一种反爬机制。** 网站主动跳转、登录或验证限制、本地代码重复导航，都可能造成相似表现。

##### 2. 最早定位的机制：通过控制台打印的耗时判断是否被调试

多位参与者将问题指向反调试库 `disable-devtool`，其中一位插件作者称，BOSS 对该库做了额外增强。不过，这些判断主要来自参与者的代码分析和测试，讨论本身没有提供完整、可独立复现的验证过程。

这里的“反调试”，指的是网站尝试发现用户是否打开开发者工具、连接调试器，并据此中断访问。它与识别自动化并不完全相同，但两者可能使用相同的浏览器调试能力。

###### 为什么打印日志也能暴露调试状态？

讨论给出的简化逻辑是：

1. 记录当前时间。
2. 用 `console.table` 打印一个较复杂的对象。
3. 再次记录时间。
4. 如果打印耗时超过某个阈值，就认为开发者工具或调试连接已启用，随后执行页面跳转。

关键在于：**打印一个对象，并不总是只输出一行文字。** 在某些调试状态下，浏览器需要处理对象内容，供控制台展示或调试客户端读取。复杂对象、属性访问及展开处理，可能增加耗时。

原文示例使用 **50 毫秒**作为判断阈值，但这是简化代码里的示例值，不能当作 BOSS 当前统一采用的规则。

###### 第一轮解决思路：让检测动作失去效果

最初的方案是在网站脚本运行前，替换 `console.log`、`console.table` 等方法，让它们不执行原来的打印动作。

注入时间很重要：如果网站已经运行检测，或者已经保存了原始函数引用，再替换就可能来不及。因此，参与者建议使用 Puppeteer 的 `evaluateOnNewDocument` 或 Playwright 的 `addInitScript`，在页面初始化阶段执行补丁。

原文较完整的代码并非把所有日志都直接关闭，而是将传入的对象替换成空对象，再调用原有方法，试图避免复杂对象被调试器处理。

###### 第二轮问题：网站也能检查函数有没有被替换

JavaScript 可以用 `Function.prototype.toString` 查看函数的字符串表示。原生浏览器方法通常显示类似：

```text
function log() { [native code] }
```

而直接替换成空函数后，可能显示：

```text
() => {}
```

因此，方案又增加了一层：让被替换的方法在接受检查时，仍返回“看起来像原生函数”的字符串。

但网站也可以继续检查 `toString` 自己是否被替换，甚至通过 iframe——页面内嵌的另一个页面环境——取得另一套函数来交叉检查。后续脚本因此加入了函数映射、属性处理和 iframe 相关补丁。

**这形成了持续加码的对抗：隐藏一次修改，网站可以换一个角度检查这次隐藏。** 它并不是替换一两个函数后就永久解决的问题。

###### 后续补丁为什么还处理 `performance.now`？

另一位参与者认为，关键不只在 `console.table`，还包括高精度计时函数 `performance.now`。其脚本用基于 `Date.now` 的时间值替代原有计时，并强调不能简单返回固定值，否则可能触发另一种时序异常检查。

这反映出检测可能同时关注“某个动作花了多久”和“计时函数是否表现异常”。但**降低计时精度不等于消除所有延迟，也不意味着替代函数完全符合原生行为**。

实际反馈同样不一致：有人表示补丁有效，有人仍会跳转，也有人报告某些方案运行一段时间后出现内存崩溃。插件作者后来承认，检测机制可能已经更新，需要继续修改。

##### 3. CDP 的问题，不应简单归结为“开了远程调试端口”

**CDP（Chrome DevTools Protocol）**是外部程序控制、调试 Chromium 浏览器的一套接口。Playwright、Puppeteer 等工具的部分控制能力与它有关。

讨论中有两个不同层次的判断：

- 早期参与者怀疑：建立 CDP 会话后，控制台内容会被处理，增加耗时，进而触发检测。
- 后续参与者提出更具体的实验：分别观察“只连接调试端口”和“发送 `Runtime.enable` 后”的页面变化。

`Runtime.enable` 可以理解为启用页面运行时的调试事件通知。这个实验试图区分：**究竟是连接本身、某项协议命令，还是连接后发生的数据处理，造成了可检测差异。**

讨论末尾提到的 Patchright，是对 Playwright 部分行为做了修改的工具。材料称，其补丁涉及避免使用 `Runtime.enable`、调整控制台相关协议行为和启动参数。但这只能说明它处理了一些已知自动化信号，不能证明所有问题都由这些信号引起。

另有参与者观察到，一款 macOS 自动化产品没有同样的问题，而且会申请系统自动控制权限，于是推测它使用了操作系统层面的控制，而非 CDP。**这是根据产品表现作出的推测，并非对其实现的确认。**

##### 4. 更深一层的风险：平台可能检查操作过程，而不只是浏览器身份

讨论后来转向 BOSS 企业端。一位参与者声称，自己分析过其公开加载到浏览器的代码，发现网站会收集鼠标轨迹、按键事件、中文输入法事件和屏幕刷新节奏，并使用 WebAssembly 加载小型神经网络分析输入行为。

WebAssembly，简称 **WASM**，是一种可以在浏览器中运行编译后程序的技术；这里被描述为用于执行本地行为分析。

**这些是参与者关于企业端的技术观察，不能直接推断候选人端也采用了完全相同的机制。** 原文也承认，没有仔细验证候选人端当下是否如此。

###### 为什么“最后输入了同样的文字”还不够？

真人使用中文输入法时，浏览器通常能看到一连串过程：按键、拼音输入、候选词组合、文字确认上屏。这个过程涉及 **IME，即输入法编辑器**，以及对应的组合输入事件。

直接注入 Unicode 字符，或者复制粘贴整段文字，最终内容可能相同，但中间过程不同。例如，页面可能收到文字变化，却缺少相应的按键和输入法组合事件。

参与者因此认为：

- 动作慢、每天操作少，不足以证明行为像真人。
- 鼠标轨迹、按键顺序、输入间隔及输入法过程，也可能成为判断依据。
- 过于均匀、流畅的输入不一定更自然；真人会停顿、选词、纠错。

有人展示了调用系统原生输入法的概念验证，并考虑用词库辅助分词，对词库外内容退化为单字输入。但这只是局部能力演示，不是长期通过风控的证明。

围绕是否开源，参与者还有一项判断：如果大量用户复用同一种输入节奏，算法可能形成共同“指纹”，反而更容易被识别。因此，有人倾向只开放底层事件注入机制，而不公开完整的输入行为算法。

##### 5. OCR 和坐标点击能减少浏览器补丁，但无法自动消除环境指纹

另一条路线是视觉自动化：通过截图和 **OCR（文字识别）**找到按钮、岗位和输入框，再用坐标点击，而不是读取网页结构或依赖浏览器调试接口。

这种方式属于 **CUA（计算机使用代理）**的一种思路：像用户一样看屏幕、操作鼠标和键盘。

有人断言它可以规避所有检测，但另一位参与者用企业端实践指出：**操作方式像真人，不代表运行环境像普通用户。**

###### 改浏览器声明，不能改变真实渲染结果

浏览器会暴露许多可用于区分环境的特征，例如：

- 字体渲染出的像素差异；
- WebGL 图形渲染结果；
- 可用语音、语言能力等环境信息。

这些通常被称为“浏览器指纹”。参与者举例说明：即便把 Linux 浏览器的 UA——浏览器对外声明的系统和版本信息——改成 Windows 或 macOS，其字体和图形渲染仍可能体现 Linux 特征，造成“声明与实际表现不一致”。

持续拦截检测函数、返回预制结果也有维护成本：网站换了检测代码，补丁就可能需要重做。

###### 为什么有人主张使用原生 Windows／macOS 会话？

参与者建议通过原生 Windows 或 macOS 环境运行浏览器，再利用 RDP、VNC 等远程桌面方式获取画面、控制操作。其理由是：浏览器真实运行在该系统上，不必靠大量补丁伪装系统特征。

也有人提出在容器中运行 Windows，再配合指纹浏览器。讨论对此的顾虑主要是镜像体积、资源占用和分发复杂度：**如果目标只是帮助个人投递简历，为此部署一套重型环境，工程成本可能过高。**

原生系统方案仍然只是降低某些环境差异，并不保证行为分析、访问限制或账号风控全部失效。

##### 6. 最有价值的工程修复：先消除程序自己制造的刷新循环

讨论后段的一份实现记录，较明确地承认了验证边界。它同时更换了部分浏览器驱动行为，并修正登录流程，没有声称已经确认刷新由某个检测机制单独导致。

###### 原来的循环怎样发生？

原有逻辑可能是：

> 页面还没加载完 → 找不到登录标记 → 判断为未登录 → 跳转登录页 → 新页面又没加载完 → 再次跳转。

这样，程序会不断打断扫码、验证和正常加载。即使网站没有主动反制，也能出现类似“反爬导致持续刷新”的现象。

修复后的关键是区分状态：

- **已在登录页或验证页：保留当前位置。**
- **加载中或状态未知：等待后重新检查，不立即导航。**
- **明确未登录，且不在登录页：才进入登录入口。**
- 重复点击“打开登录”时，优先复用现有页面，而不是重新创建、跳转。

###### 刷新循环检测的作用是止损，不是破解

该实现监听主页面导航，并设置诊断阈值：

- 12 秒内至少出现 6 次导航；
- 或同一路径至少出现 4 次。

达到条件后，程序提示异常并停止自动操作。**它不会阻止网站自己的 JavaScript 刷新；这些数字也只是项目自定的诊断阈值，不是 BOSS 的风控规则。**

浏览器方面，该实现采用 Patchright、可见的 Chrome／Edge、原生窗口尺寸和固定的专用持久化目录，以复用登录状态并调整部分驱动行为。

但其测试范围很有限：公开首页和登录页分别观察了 **20 秒**，没有再次出现循环刷新；**没有做真实账号的长时间验收**。准确的表述只能是“改善了当时的刷新问题”，不能说“破解了全部反爬”。

##### 7. 自动化是否成功，还需要区分页面状态、程序错误和业务结果

末尾的工程材料强调，不应把所有失败都塞进“反爬”这个解释：

| 问题类型 | 常见表现 | 合理处理方向 |
|---|---|---|
| 登录、验证与访问限制 | 登录页、安全验证、操作频繁、次数上限 | 保留页面，暂停任务；人工处理，达到限制则停止 |
| 网页交互与业务确认 | 弹窗遮挡、按钮暂不可用、消息出现但未送达 | 等待实际可用状态，处理页面分支，确认业务结果 |
| 本地程序与驱动错误 | 页面对象已关闭、操作旧标签页、回调异常 | 根据出错阶段修复代码和页面生命周期 |

例如，`Timeout 8000ms exceeded` 只表示等待条件没有在 8 秒内满足，不能独立证明触发了反爬。

同样，**点击发送、出现消息气泡、完成文件上传，都不等于业务成功。** 材料提出，应记录发送前的消息状态，再等待本次新增消息的送达或已读标记，而不是仅凭界面变化计数。

其他容易混淆的边界也被明确指出：

- 持久化浏览器目录能保存登录状态，但会话仍可能过期；目录包含敏感认证信息，不应随源码分享。
- 项目默认每日 50 次尝试、5—10 秒随机间隔，只是应用配置，不是官方额度或经过验证的“安全阈值”。
- 未发现验证文案，不等于已经登录或一定能继续操作。
- 项目没有验证当前请求签名的完整生成与绑定规则，因此不能把固定 Cookie 或旧签名当作通用方案。

原文最后的“正确流程是”部分已经截断，不能据此还原未提供的完整发送流程。

这篇材料是多人讨论，不是一份结论统一的技术报告。里面混合了可用思路、个人测试、未经充分验证的断言，以及带有“完全指南”口吻的方案。

其中一份指南主张：使用系统 Chrome、持久化浏览器目录、替换 `console.table` 和 `performance.now`，并避免暴露 CDP 远程调试端口，就能完成修复。它还列出具体检测属性、上报码和修改文件清单。

但发帖者回应：类似办法早已尝试，希望提交的是**实际修改并测试过的 PR，而不是 AI 生成的答案**。这个分歧提醒读者：写得完整、术语具体，不代表方案已经被验证。

阅读这些结论时，最重要的是保留三项区别：

- **暂时打开页面，不等于长期完成登录、投递和消息发送。**
- **企业端发现的机制，不等于候选人端已经采用相同机制。**

## 深度解读-口播（1）

### 2026-09-30 11:37:21

BOSS直聘的自动化页面为什么会突然变成空白，或者不停刷新？这场讨论最值得记住的判断是：相似的故障，未必来自同一个原因。网站的反调试检测、行为风控，以及自动化程序自身的错误，都可能让页面看起来“被关掉了”。

讨论最初的现象很具体。发帖者发现，用自动化工具打开浏览器后，如果只是手动操作，页面可以正常使用。但一旦由程序控制，或者通过浏览器的远程调试通道连接，页面就可能回退。

这里的远程调试通道，简称为 CDP。可以把它理解成程序与浏览器之间的一条控制通道。程序通过这条通道，读取页面、执行脚本，或者控制页面交互。

一位参与者给出的解释是，网站可能不是直接识别“谁在控制浏览器”，而是在检测控制台处理信息时留下的时间差。

控制台是浏览器开发者工具里查看日志的地方。网站可以向控制台输出一个很大的对象，再测量输出前后花了多长时间。如果开发者工具没有开启，这个动作可能很快。如果控制台正在处理对象内容，耗时就可能增加。

讨论里的简化示例，用了五十毫秒作为判断门槛。这个数字只是示例，不能当成 BOSS 当前实际使用的固定规则。关键在于，网站可以利用执行耗时，间接判断是否存在调试活动。

这也解释了一种看似矛盾的情况：用户没有主动打开开发者工具，自动化连接却仍然触发了检测。有参与者推测，调试通道启用某些功能后，也会处理控制台信息，从而产生额外开销。不过，具体是哪一步触发，需要单独测试，不能只凭“连接后跳转”就下结论。

围绕这类检测，讨论中出现了几种补丁思路。有人尝试在页面脚本运行前，替换控制台输出函数。也有人认为，还需要处理浏览器用于精细计时的函数。

但问题并没有到此结束。网页还可以反过来检查：这些函数是不是被改过了？

浏览器原生函数在转换成文字时，通常会带有原生代码的标记。一个后来替换进去的普通函数，可能显示出不同内容。因此，修改检测函数之后，还可能遇到“检测修改行为”的第二层检查。

这场讨论里，最有价值的不是某段代码看起来多完整，而是后续反馈。有用户说，首页打不开的问题解决了，但打开岗位页面又开始不断刷新。也有人反馈，脚本后来重新失效，甚至出现停留一段时间后内存崩溃的情况。

所以，这些补丁更像是针对某个版本、某条检测路径的局部修复，而不是一次性解决全部问题。

再往下看，讨论从“调试工具有没有开启”，转向了另一个问题：操作过程像不像真人。

一位研究过 BOSS 企业端的参与者声称，他在网页代码中看到了鼠标轨迹、按键时序、中文输入法事件等采集逻辑，还看到了通过浏览器中的小型神经网络模型分析输入行为的实现。

这里要保留一个重要边界：这些是参与者对企业端的研究陈述，不能直接当成求职者端已经采用同样检测的证据。

不过，他举出的中文输入案例很容易理解。真人通过拼音输入中文时，浏览器收到的不只是最终的汉字。通常还会收到按键按下、松开，以及输入法开始组合、更新候选内容、结束组合等一串事件。

如果程序直接把汉字塞进输入框，最后显示的文字可以完全一样，中间的事件序列却可能不同。也就是说，结果像真人，不代表过程像真人。

这也是为什么，“操作慢一点”并不必然解决问题。速度只是一个维度，输入过程和鼠标行为可能是另外的维度。

有人因此提出，用屏幕识别配合坐标点击，尽量不通过网页内部接口操作。但其他参与者提醒，视觉操作也不能自动消除环境差异。

例如，程序运行在 Linux 环境中，却声称自己是 Windows 或苹果电脑，字体渲染和图形渲染的结果可能仍然不一致。这类差异就是所谓的环境指纹。

因此，绕开一条调试通道，不等于所有行为和环境信号都消失了。至于“高度拟人就完全无法分辨”的说法，讨论没有提供足够证据支持这种保证。

不过，这场讨论后面还有一个更务实的转折：有些刷新循环，确实是程序自己制造的。

一位后来分享改动的参与者，指出了这样的循环：页面还没有加载完成，程序暂时找不到登录标记，于是认定用户未登录，再次跳转到登录页。页面重新加载，程序又找不到标记，于是再次跳转。

这个过程中，即使网站没有主动拦截，自动化程序也会不停打断自己。

对应的修复，是把几种状态分开。如果已经在登录页或验证页，就保留当前位置。如果页面正在加载，或者状态暂时未知，就等待后重新检查。只有明确确认未登录，而且不在登录页，才执行跳转。

他们还增加了短时间内反复导航的检测。一旦发现循环，就停止自动操作。但这个措施只是让程序停手，并不能禁止网站自己的脚本继续刷新。

这位参与者对验证结果也说得很克制：改动后，公开首页和登录页分别观察二十秒，没有再次出现循环刷新；但没有完成真实账号的长时间验收。因此，只能说当时的问题得到改善，不能说已经破解全部反爬机制。

这也给整场讨论划出了最重要的证据边界。一次等待超时，只能说明没有等到目标状态，不能独立证明触发了反爬。一次成功打开页面，也不能证明后续投递和聊天会一直正常。

真正值得记住的是：先区分网站限制、页面交互问题和本地程序错误，再判断该修哪里。局部补丁有效，不代表长期有效；企业端的研究，也不能直接套用到求职者端。比起“永远检测不到”的承诺，更可靠的是明确测试范围、确认业务结果，并在遇到验证或次数限制时停止继续操作。
