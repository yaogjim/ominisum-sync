**Dens Sumesh**

### 为 Mintlify 的 AI 助手构建虚拟文件系统

RAG 很棒，直到它不再如此。

我们的助手只能检索与查询匹配的文本片段。如果答案分布在多个页面中，或者用户需要的精确语法不在 Top-K 结果中，它就会陷入困境。我们希望它能像浏览代码库那样探索文档。

代理是

[正在向文件系统汇聚，将其作为主要交互界面](https://arxiv.org/abs/2601.11672)因为 grep、cat、ls 和 find 正是代理所需的全部工具。如果每个文档页面都是一个文件，每个章节都是一个目录，代理就可以搜索精确字符串、读取完整页面，并独立遍历目录结构。我们只需要一个能镜像实时文档站点的文件系统。

#### 容器瓶颈

最直接的方法是直接给代理一个真实的文件系统。大多数框架通过启动一个隔离的沙箱并克隆代码仓库来解决这个问题。我们已经在异步后台代理中使用沙箱，在这些场景中延迟是事后考虑的，但对于用户正盯着加载转圈的前端助手来说，这种方法就不适用了。我们的 p90 会话创建时间（包括克隆 GitHub 仓库和其他设置）约为 46 秒。

除了延迟之外，用于阅读静态文档的专用微型虚拟机带来了严重的基础设施成本。

每月 850,000 次会话，即使是最低配置（1 个 vCPU、2 GiB 内存、5 分钟会话时长），每年成本将超过 70,000 美元，基于

[Daytona 的每秒沙箱定价](https://www.daytona.io/pricing)（每个 vCPU 每小时 0.0504 美元，每个 GiB 内存每小时 0.0162 美元）。更长的会话时长会使成本翻倍。（这是基于一种非常简单的方法，真正的生产工作流可能会采用热池和容器共享，但核心观点仍然成立）

我们需要文件系统工作流即时且低成本，这意味着重新思考文件系统本身。

#### 模拟一个 Shell

这个代理不需要真实的文件系统；它只需要一个虚拟文件系统的假象。我们的文档已经被索引、分块并存储在 Chroma 数据库中，以支持我们的搜索功能，因此我们构建了 ChromaFs：一个虚拟文件系统，它会拦截 UNIX 命令并将其转换为针对同一个数据库的查询。会话创建时间从约 46 秒降至约 100 毫秒，并且由于 ChromaFs 复用了我们已付费的基础设施，每次对话的边际计算成本为零。

![Image](https://pbs.twimg.com/media/HE3LCGwacAA_9B0?format=jpg&name=large)

ChromaFs 架构

ChromaFs 基于

[just-bash](https://github.com/vercel-labs/just-bash) 由 Vercel Labs（致敬

[Malte](https://x.com/cramforce)

！，这是一个用 TypeScript 重新实现的 bash，支持 grep、cat、ls、find、cd 等命令。just-bash 提供了一个可插拔的 IFileSystem 接口，因此它处理所有的解析、管道和标志逻辑，而 ChromaFs 将每个底层文件系统调用转换为 Chroma 查询。

```typescript
export class ChromaFs implements IFileSystem {
  private files = new Set<string>();
  private dirs = new Map<string, string[]>();

  async readFile(path: string): Promise<string> {
     this.assertInit();
     const normalized = normalizePath(path);

    // Serve from cache or fetch from Chroma
    const slug = normalized.replace(/\\.mdx$/, '').slice(1);

    // Pages are chunked in Chroma. Reassemble them on the fly:
    const results = await this.collection.get<ChunkMetadata>({
      where: { page: slug },
      include: [IncludeEnum.documents, IncludeEnum.metadatas],
    });

    const chunks = results.ids
      .map((id, i) => ({
        document: results.documents[i] ?? '',
        chunkIndex: parseInt(String(results.metadatas[i]?.chunk_index ?? 0), 10),
      }))
      .sort((a, b) => a.chunkIndex - b.chunkIndex);

    return chunks.map((c) => c.document).join('');

  }

  // Enforce completely stateless, read-only interaction
  async writeFile(): Promise<void> { throw erofs(); }
  async appendFile(): Promise<void> { throw erofs(); }
  async mkdir(): Promise<void> { throw erofs(); }
  async rm(): Promise<void> { throw erofs(); }
}
```

#### 它是如何工作的

自举目录树

ChromaFs 需要在代理运行任何命令之前知道存在哪些文件。我们将整个文件树作为一个 gzipped JSON 文档（\_\_path\_tree\_\_）存储在 Chroma 集合中：

```json
{
  "auth/oauth": { "isPublic": true, "groups": [] },
  "auth/api-keys": { "isPublic": true, "groups": [] },
  "internal/billing": { "isPublic": false, "groups": ["admin", "billing"] },
  "api-reference/endpoints/users": { "isPublic": true, "groups": [] }
}
```

在初始化时，服务器会获取并解压缩该文档，生成两个内存中的结构：一个存储文件路径的 \`Set&lt;string&gt;\`，以及一个将目录映射到子项的 \`Map&lt;string, string\[\]&gt;\`。

构建完成后，ls、cd 和 find 命令在本地内存中解析，无需网络调用。目录树会被缓存，因此针对同一个站点的后续会话会完全跳过 Chroma 获取。

访问控制

注意到 isPublic 和 groups 字段在路径树中。在构建文件树之前，ChromaFs 会根据当前用户的权限修剪文件树，并对所有后续的 Chroma 查询应用匹配过滤器。

在真实的沙箱环境中，这种级别的用户级访问控制需要管理 Linux 用户组、chmod 权限，或者为每个客户层级维护隔离的容器镜像。而在 ChromaFs 中，在 buildFileTree 运行前只需进行几行过滤操作即可实现。

从片段重新组装页面

Chroma 中的页面被分割成块以进行嵌入，因此当代理执行 cat /auth/oauth.mdx 时，ChromaFs 获取所有与页面 slug 匹配的块，按块索引排序，并将它们合并成完整页面。结果会被缓存，因此在 grep 工作流中的重复读取不会两次访问数据库。

不是每个文件都需要存在于 Chroma 中。我们为存储在客户 S3 存储桶中的大型 OpenAPI 规范注册了按需解析的惰性文件指针。代理在 /api-specs/ 路径下看到 v2.json 文件，但只有在执行 cat 命令时才会获取文件内容。

每次写入操作都会抛出 EROFS（只读文件系统）错误。代理可以自由探索，但永远无法修改文档，这使得系统是无状态的，无需会话清理，也不存在一个代理破坏另一个代理的视图的风险。

#### 优化 Grep

cat 和 ls 的虚拟化很简单，但是如果 grep -r 直接扫描网络上的每个文件，速度会太慢。我们拦截了 just-bash 的 grep，使用 yargs-parser 解析标志，并将它们转换为 Chroma 查询（对于固定字符串使用$contains，

[$regex](https://x.com/search?q=%24regex&src=cashtag_click) 用于模式）

Chroma 充当粗略过滤器，识别哪些文件可能包含命中内容，我们将这些匹配的块批量预取到 Redis 缓存中。从那里，我们重写 grep 命令以仅针对匹配的文件，并将其交还给 just-bash 用于精细过滤器的内存中执行，这意味着大型递归查询在毫秒内完成。

```typescript
const chromaFilter = toChromaFilter(
  scannedArgs.patterns,
  scannedArgs.fixedStrings,
  scannedArgs.ignoreCase
);

// 1. Coarse Filter: Ask Chroma for slugs matching the string/regex
const matchedSlugs = await chromaFs.findMatchingFiles(chromaFilter, slugsUnderDirs);
if (matchedSlugs.length === 0) return { stdout: ‘’, exitCode: 1 };

// 2. Prefetch: Pull the chunked files into local cache concurrently
await chromaFs.bulkPrefetch(matchedSlugs);

// 3. Fine Filter: Narrow the arguments to ONLY the resolved hits
const matchedPaths = matchedSlugs.map((s) => ‘/’ + s + ‘.mdx’);
const narrowedArgs = [...args, ...matchedPaths]; // e.g. ["-i", "OAuth", "/docs/auth.mdx"]

// 4. Exec: Let the in-memory RegExp engine format the final output
return execBuiltin(narrowedArgs, ctx);
```

ChromaFs 驱动着数十万用户的文档助手，每天处理超过 3 万次对话。通过在我们现有的 Chroma 数据库之上用虚拟文件系统替代沙箱，我们实现了即时会话创建、零边际计算成本以及内置的 RBAC，且无需任何新的基础设施。

## 通俗精炼（1）

### 2026-04-03 08:06:00

#### 为 Mintlify 的 AI 助手构建虚拟文件系统

##### 核心结论

Mintlify 发现：**传统 RAG 适合 “找片段”，但不适合 “像人一样查文档”**。  
为了解决这个问题，他们没有给 AI 助手真的开一个沙箱文件系统，而是做了一个**虚拟文件系统 ChromaFs**，让助手 “以为自己在读文件”，本质上却是在查询已有的文档数据库。

这样做带来了三个直接结果：**响应更快、成本更低、权限控制更简单**。

##### 问题是什么

RAG 的问题在于，它只能返回 “最相关的几个片段”。  
但真实的文档问答里，答案常常会出现这些情况：

- 信息分散在多个页面
- 用户需要的是精确语法，而不是模糊语义
- 助手需要自己浏览目录、逐页查找、全文搜索

换句话说，助手需要的不是 “被动检索”，而是像程序员查代码一样：**能`ls`、能`cat`、能`grep`、能`find`**。

##### 为什么不用真实沙箱

最直观的做法，是给每个会话启动一个隔离环境，再把文档仓库克隆进去。  
但这个方案有两个明显问题：

###### 延迟太高

Mintlify 的真实数据里，创建一次沙箱会话大约要**46 秒**。  
对于前端实时助手来说，这几乎不可接受。

###### 成本太高

如果每月有**85 万次会话**，哪怕是最小配置的虚拟机，**年成本也会超过 7 万美元**。  
如果会话时间更长，成本还会继续翻倍。

所以他们的目标很明确：**既要文件系统体验，又不能真的运行文件系统。**

##### 他们怎么做的

Mintlify 构建了一个叫**ChromaFs**的系统。  
它并不创建真实文件，而是把 Shell 命令翻译成对 Chroma 数据库的查询。

简单说就是：

- `cat`：去数据库里把某一页对应的多个 chunk 取出来，再拼成完整页面
- `ls` / `cd` / `find`：直接在内存里的目录树中完成
- `grep`：先让数据库粗筛，再在内存中做精筛

对 AI 来说，它像是在操作文件系统；  
对系统来说，它只是高效地复用了原有的检索基础设施。

##### 关键设计亮点

###### 1. 启动快

他们把整站文档路径树预先存成一个压缩 JSON。  
会话初始化时只需拉取一次并解压，就能快速生成目录结构。

结果是：**会话创建时间从 46 秒降到约 100 毫秒**。

###### 2. 页面按需拼装

因为文档原本就是按 chunk 存在 Chroma 里，  
所以读取页面时，系统会：

1. 找到对应页面的所有 chunk
2. 按顺序排序
3. 拼成完整文档返回

这样既兼容原有 RAG 架构，又能给代理完整页面视图。

###### 3. 内置权限控制

路径树里直接带有`isPublic`和`groups`等字段。  
系统在生成目录树前，就能按用户权限过滤可见文件。

这比真实 Linux 沙箱里做用户组、权限位、隔离镜像要简单很多。  
本质上是：**把复杂的系统权限问题，转成了数据过滤问题。**

###### 4. Grep 被专门优化

全文搜索最容易慢。  
所以他们没有让`grep -r`真的去 “扫所有文件”，而是分两步：

- 先让 Chroma 做粗筛，快速找出 “可能命中” 的文件
- 再把这些文件拉到缓存里，用内存正则做精筛

这样大规模递归搜索也能在毫秒级完成。

##### 这件事的本质价值

这篇文章最值得借鉴的，不是 “做了个虚拟文件系统”，而是背后的产品与工程思路：

- **不是复制真实系统，而是模拟用户真正需要的能力**
- **不是新增基础设施，而是复用已有能力栈**
- **不是追求技术完整性，而是追求交互效率和单位成本最优**

本质上，Mintlify 不是在 “造一个文件系统”，  
而是在给 AI 助手造一个**最小可用的工作环境**。

##### 一句话总结

**Mintlify 用虚拟文件系统替代真实沙箱，让 AI 助手像浏览本地文档一样查资料，从而把响应时间从 46 秒压到 100 毫秒，并几乎把新增算力成本降为零。**

## 结构化（1）

### 2026-04-03 09:31:51

#### 主旨概括

这篇文章讲的是：Mintlify 为了解决传统 RAG 在文档问答中的局限，没有继续依赖慢且贵的沙箱文件系统，而是基于已有的 Chroma 数据库，做了一个“虚拟文件系统” `ChromaFs`。  
这样一来，AI 助手就能像浏览代码仓库一样查文档，同时把会话创建时间从约 46 秒压缩到约 100 毫秒，成本也大幅下降。

##### 1. 为什么单靠 RAG 不够用

- 传统 RAG 只能返回“最相关的文本片段”，但当答案分散在多个页面，或者关键语法没有进入 Top-K 检索结果时，助手就容易答不准。
- 作者希望助手像“逛代码库”一样工作：能自己 `grep`、`cat`、`ls`、`find`，主动探索文档结构，而不只是被动拿片段。
- 核心思路是：把每个文档页面看成一个文件、每个章节看成一个目录，让代理通过“文件系统”来理解和查找文档。

##### 2. 真实沙箱方案为什么不可行

- 最直接的做法，是给代理一个真实文件系统，比如启动隔离沙箱并克隆仓库。
- 但这种方法对前端实时助手来说太慢了：其 `p90` 会话创建时间大约是 **46 秒**，其中包括克隆 GitHub 仓库和初始化环境。
- 成本也很高：
  - 每月约 **850,000 次会话**
  - 即使最低配置是 **1 个 vCPU、2 GiB 内存、5 分钟会话**
  - 按 Daytona 的单价计算，**每年成本超过 70,000 美元**
- 如果会话时间再延长，成本还会继续翻倍。
- 所以作者的结论是：如果想同时做到“即时响应”和“低成本”，就不能继续把文件系统理解成“真实容器中的磁盘目录”。

##### 3. 他们的解决方案：模拟一个 Shell

- Mintlify 并没有真的创建文件系统，而是构建了一个虚拟文件系统 **ChromaFs**。
- 它的本质是：**拦截 UNIX 命令，然后把这些命令翻译成对 Chroma 数据库的查询**。
- 因为文档原本就已经被索引、分块并存到 Chroma 中，所以这个方案直接复用现有基础设施。
- 效果非常明显：
  - 会话创建时间从 **约 46 秒降到约 100 毫秒**
  - 由于复用了已有系统，**每次对话的边际计算成本接近于零**
- 可以把它理解成：用户和代理以为自己在用 shell，其实底层根本不是磁盘，而是数据库。

##### 4. ChromaFs 是怎么实现的

- ChromaFs 基于 Vercel Labs 的 **just-bash**，这是一个用 TypeScript 实现的 bash，支持 `grep`、`cat`、`ls`、`find`、`cd` 等命令。
- `just-bash` 提供了可插拔的 `IFileSystem` 接口，因此：
  - 命令解析、管道处理、参数逻辑由 `just-bash` 负责
  - ChromaFs 只负责把底层文件系统调用映射成 Chroma 查询
- 例如在 `readFile(path)` 中：
  - 先把路径转成页面 slug
  - 再从 Chroma 中取出该页面对应的所有 chunk
  - 按 `chunk_index` 排序后重新拼成完整页面内容
- 同时，它明确禁止任何写操作：
  - `writeFile`
  - `appendFile`
  - `mkdir`
  - `rm`
- 这些操作都会抛出 **`EROFS`（只读文件系统）** 错误，保证代理只能读、不能改。

##### 5. 它如何先“生成目录树”

- 在代理执行任何命令前，ChromaFs 需要先知道有哪些“文件”和“目录”存在。
- 为此，系统把整个文档路径树存成一个压缩过的 JSON 文档 `__path_tree__`，放在 Chroma 集合里。
- 文中给出的示例包括：
  - `auth/oauth`
  - `auth/api-keys`
  - `internal/billing`
  - `api-reference/endpoints/users`
- 初始化时，服务端会获取并解压这个 JSON，然后构建两个内存结构：
  - 一个 `Set&lt;string>`：存文件路径
  - 一个 `Map&lt;string, string[]>`：存目录到子项的映射
- 这样做的好处是：
  - `ls`、`cd`、`find` 都可以直接在内存中执行
  - **不需要网络请求**
  - 而且目录树会缓存，同一站点后续会话甚至可以跳过这一步

##### 6. 访问控制是如何内建进去的

- 路径树里除了路径本身，还存了权限信息，比如：
  - `isPublic`
  - `groups`
- 在构建文件树前，ChromaFs 会根据当前用户权限把不该看到的文件先“剪掉”。
- 后续所有 Chroma 查询也会带上相同的过滤条件。
- 这比真实沙箱简单很多：
  - 不需要维护 Linux 用户组
  - 不需要配置 `chmod`
  - 不需要为不同客户层级维护隔离镜像
- 在 ChromaFs 里，只需要在 `buildFileTree` 前做几行过滤逻辑，就能完成用户级 RBAC（基于角色的访问控制）。

##### 7. 页面内容如何从分块中还原

- 因为文档在 Chroma 中是按 chunk 存储的，所以当代理执行 `cat /auth/oauth.mdx` 时：
  - 系统会查询该页面的所有 chunk
  - 按块序号排序
  - 再拼回完整页面
- 为了提升性能，拼好的结果也会缓存。
- 这样如果后续 `grep` 流程又要重复读取同一页面，就不会再打数据库。
- 文章还提到一个很实用的设计：**惰性文件指针**。
  - 有些大型 OpenAPI 规范文件其实存放在客户的 S3 存储桶中
  - 代理在 `/api-specs/` 下能“看到”像 `v2.json` 这样的文件
  - 但只有真正执行 `cat` 时，系统才会去取文件内容
- 这说明虚拟文件系统不要求所有文件都提前在 Chroma 里，只要“看起来存在”并能按需加载即可。

##### 8. 他们重点优化了 `grep`

- `cat`、`ls` 的虚拟化相对简单，但 `grep -r` 是难点。
- 如果像真实文件系统那样一个文件一个文件地扫网络内容，会非常慢。
- 因此他们专门拦截了 `grep`：
  - 用 `yargs-parser` 解析参数
  - 把查询条件转换成 Chroma 过滤器
  - 固定字符串用 **`$contains`**
  - 模式匹配用 **`$regex`**
- 整个流程分 4 步：
  1. **粗过滤**：先让 Chroma 找出“可能命中”的文件
  2. **预取**：把这些命中的 chunk 文件批量拉到 Redis 缓存
  3. **缩小范围**：把 `grep` 的目标缩成已命中的文件集合
  4. **精过滤**：再交回 `just-bash`，用内存中的正则引擎做最终匹配和格式化输出
- 结果是：**大规模递归查询也能在毫秒级完成**。
- 这相当于把数据库当作“粗筛器”，再把 shell 当作“精筛器”，兼顾速度和准确性。

##### 9. 最终效果与落地情况

- ChromaFs 已经用于 Mintlify 的文档助手，服务规模不小：
  - 覆盖 **数十万用户**
  - 每天处理 **超过 3 万次对话**
- 它带来的几个核心收益是：
  - **即时会话创建**
  - **零边际计算成本**
  - **内置 RBAC 权限控制**
  - **不需要新增基础设施**
- 用一句话概括这套方案：  
  他们不是让 AI 去适应昂贵又缓慢的真实文件系统，而是直接把数据库伪装成文件系统，让代理以自己最擅长的 shell 方式工作。

##### 10. 一个通俗例子帮助理解

- 传统 RAG 像是你问图书管理员一个问题，对方只递给你几张“可能相关”的摘录卡片；如果答案散落在不同章节，你就容易拼不起来。
- ChromaFs 更像是直接把整座图书馆“伪装成文件夹”交给 AI：
  - 它可以先 `ls` 看目录
  - 再 `find` 找章节
  - 用 `grep` 搜关键词
  - 最后 `cat` 把整页内容读完
- 虽然底层并不是真书架，而是数据库，但对代理来说，体验就像在真实文件系统中查资料一样自然。
