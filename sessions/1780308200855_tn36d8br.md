#### 2026 年的 Codex 实际上是什么

大多数人仍然认为 Codex 是更智能的自动补全。事实并非如此。

- Codex 是一个全功能代理式软件开发平台。 它可以读取你的代码库，编写和测试代码，审查拉取请求，控制你的 Mac 桌面，浏览网页，生成图像，安排重复任务，并在跨会话中记住你的偏好。
- 这需要的思维转变是重大的。你不再是那个写代码的人。你成为审查由永不疲倦的初级工程师团队编写的代码的人。

大多数开发者安装 Codex 后，连续两周发送单行提示，得到平庸的结果，然后放弃。他们从未配置过 AGENTS.md。

他们从不编写 Skill。他们从不使用子代理（sub-agents）。 他们使用 5%的表面积并根据这 5%来评判工具。

本课程涵盖其余的95%。

#### 五个表面

在安装任何内容之前，请了解 Codex 的运行位置。你选择的平台决定了你对其工作的跟进程度以及代码的运行位置。

CLI 用于脚本化工作流、单任务工作和无头自动化。你的代码永远不会离开你的机器，除非你主动推送它。开源，使用 Rust 构建，支持在 macOS、Windows 和 Linux 上运行。

IDE 扩展用于具有精确文件上下文的交互式编辑。可安装在 VS Code、Cursor、Windsurf 或 JetBrains 中。使用您的 CLI 认证，无需单独登录。

桌面应用是多线程工作流、应用内浏览器、电脑使用、目标模式、应用快照和自动化的家园。2026 年 2 月在 macOS 上发布，2026 年 3 月 4 日在 Windows 上发布。

Cloud 用于异步后台任务、并行拉取请求以及在你休息时处理工作。任务在沙箱容器中运行，这些容器预加载了你的 GitHub 仓库。不会阻塞你的本地机器。

应用内浏览器和计算机使用用于 UI 验证、前端迭代和端到端测试。Codex 打开您的本地开发服务器，与之交互，对结果进行截图，并验证代码变更产生了正确的视觉输出。

一个真实的工作流使用多个层面：

- 脚本化事物的命令行界面
- 用于交互式功能开发的集成开发环境
- 无需监控的并行任务云服务
- 目标驱动的长期运行任务应用

选择界面的主要因素是你希望多紧密地跟进代理的工作。如果你希望实时监控所做的更改，命令行界面（CLI）或集成开发环境（IDE）会将工作保存在你的机器上并随时呈现在你面前。如果你更愿意进行更长的会话并在结束时进行查看，云（Cloud）就是更合适的选择。

#### 心智模型：代理，而非自动补全

表面清理完毕后，下一步是理解工作单元。

工作单元是任务，而不是轮次。输出是 PR，而不是聊天响应。

少想“写一个实现 X 的函数”，多想“实现功能 Y，这里是约束条件，完成后运行测试”

每个 Codex 任务都遵循相同的内部循环。Codex 读取你的任务和上下文，生成内部计划，逐步执行，并检查自己的工作。

不要再把 Codex 看作编码助手。 要开始把它看作你上午给他们做简报、下午进行审查的初级工程师团队。

实际应用中的一个真实例子是：WorkOS 的开发人员现在会在去喝早咖啡前，先安排好四到五个 Codex 任务。等他们重新坐下时，已经有两到三个已完成的 PR 等待审核，这些工作原本要占用他们 30%到 40%的工作时间。

截至2026年5月的当前型号：

- GPT-5.5（默认） — 处理大多数任务，与之前相同的延迟，但完成相同工作时 token 数量显著减少
- GPT-5.3-Codex — 专为长时间自主运行、大型重构和并行云扇出设计；比之前的 Codex 专家快 25%
- GPT-5.5 Pro — 最高推理能力；仅适用于专业版、商业版和企业版计划
- Codex Mini — 永久免费，适用于学习

默认保持 Codex 使用 GPT-5.5。对于需要 Codex 长时间自主运行的大型代理任务，切换到 GPT-5.3-Codex。

#### 入门：你的第一个真实会话

实现一个可用的 Codex 会话的最快路径遵循五个步骤。忘记 FizzBuzz 教程。从真实的代码库开始。

步骤 1：安装命令行界面（CLI）。

```bash
On Mac or Linux:
curl -fsSL https://chatgpt.com/codex/install.sh | sh

On Windows (PowerShell):
powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"

Or via npm: npm i -g @openai/codex
```

---

步骤 2: 打开一个真实项目。

导航到一个你已经熟悉的低风险代码仓库。这很重要。

当你能够识别输出内容并发现错误时，Codex 的表现会更好。在不熟悉的代码库上进行初次会话的工作会产生不可预测的结果。

```bash
cd your-existing-project
codex
```

当提示时，使用你的 ChatGPT 账号登录。你的浏览器会自动打开。点击继续并返回终端。

---

步骤 3: 在做任何其他事情之前运行 /init

大多数教程都会跳过的是这一个命令。Codex 会扫描你的目录和 Git 历史记录，识别语言、框架、构建命令和测试命令，并搭建一个 AGENTS.md 文件，其中填充了它发现的内容。

```bash
/init
```

检查生成的文件，调整任何错误的地方，然后提交它。该项目未来的每个 Codex 会话都将自动读取它。

---

步骤 4: 给 Codex 一个定向任务。

在让它修改之前，先让它解释代码库。这能建立你对它加载的上下文的信心。

```markdown
> Explain how authentication works in this project. Walk me through the relevant files and the flow from login to session creation.
```

查看输出。如果它准确描述了你的实际代码库，那么它就具备了所需的上下文。如果它模糊或错误，那么你的 AGENTS.md 需要更多细节。

---

步骤 5：给它一个小的、真实的任务。 选择一些具体且有界限的事情。

```markdown
A real example from production use:

> Add stronger credit card number validation to the checkout flow.
> Card numbers must contain only digits after removing spaces and dashes,
> must be 12 to 19 digits long, and must pass a Luhn check.
> Keep the change minimal and consistent with the existing code style.
> Write tests that cover valid and invalid card numbers and run them before finishing.
```

这是 Codex 提示词的正确形式：特定的文件上下文、预期结果、约束条件和明确的验证步骤。查看它返回的 diff。现在你已经正确使用 Codex 了。

---

步骤 6：安装桌面应用程序。 从 OpenAI 网站下载。使用相同的 ChatGPT 账户登录。

步骤 7：安装 IDE 扩展。 搜索 "OpenAI Codex" 在你的编辑器的扩展面板中。它会自动读取你的 CLI 认证信息。

步骤 8：连接 GitHub。 进入 Codex 应用程序的设置并连接你的 GitHub 账户。在使用云任务之前，至少关联一个代码仓库。

---

事物的位置：

- \~/.codex/config.toml : 主配置: 审批模式, 沙箱模式, MCP 服务器, 模型默认值
- \~/.codex/AGENTS.md : 个人的 AGENTS.md，适用于所有项目

- &lt;project&gt;/.codex/config.toml：项目范围的配置（仅受信任的项目）

#### AGENTS.md：你仓库中最重要的文件

既然你已经有了一个可用的会话，下一步是让每一个未来的会话都以相同的质量开始。这正是 AGENTS.md 所做的。

1. AGENTS.md 是将平庸的 Codex 输出与一致的高质量输出区分开来的单一文件。
2. 它是位于你的代码仓库根目录下的一个纯 Markdown 文件。每次 Codex 会话在你的项目中启动时，代理会在执行任何其他操作之前自动读取它。
3. 它是一个开放标准。Codex、Cursor、Gemini CLI、Windsurf 和 GitHub Copilot 都会读取它。只需编写一次，你工具链中的每个代理都会读取相同的事实来源。

解析顺序： Codex reads \~/.codex/AGENTS.md (主级别，所有项目) plus &lt;project&gt;/AGENTS.md (项目级别)。AGENTS.override.md 文件在每个级别上优先。总限制为 32 KiB。

---

输入什么：

- 技术栈、框架、语言版本、包管理器
- 确切的构建、测试和开发命令；可复制粘贴，而非“运行常规测试”
- 文件结构规范和命名规则
- 样式和模式规则
- 禁区：不可触摸的内容
- 发布要求：CI、PR 规范、部署机制

---

什么不能放入：

- 密钥或凭证（该文件处于版本控制中）
- 模糊的指导（“写整洁代码”对代理来说毫无意义）
- 重复你的 README 的文档

保持在500字以内。冗余会将有用的上下文挤出模型的工作记忆。

---

一个可用的模板：

```markdown
# Project DNA

## Stack
- Next.js 15 (App Router), TypeScript strict
- Tailwind CSS + shadcn/ui, Supabase, SWR

## Commands
- Install: pnpm install
- Dev: pnpm dev
- Test: pnpm test
- Lint + fix: pnpm lint:fix
- Type check: pnpm typecheck
- Build: pnpm build

## Conventions
- kebab-case files, PascalCase components
- Server components by default; "use client" only when needed
- Data fetching only via /lib/data wrappers
- No direct Supabase calls from components
- No "any" types. Strict TS.

## What NOT to touch
- /lib/billing (Stripe). Ask before modifying.
- /supabase/migrations. Never edit existing migrations.
```

- 验证 Codex 是否正在读取它：请提示总结你已加载的当前指令
- 对于大型单仓库，在子目录中放置额外的 AGENTS.md 文件。
- 位于 packages/api/AGENTS.md 的文件，对于该包内的任务，优先于根级文件。
- 运行 Codex trust . 以启用项目级别的 .codex/配置.toml。 这可防止恶意克隆的仓库暗中配置 Codex。

#### 命令行界面深度解析

设置好 AGENTS.md 后，接下来需要掌握的是命令行界面(CLI)本身。大多数用户只知道输入 codex 命令，却忽略了那些能让它真正强大的命令。

---

有四个命令覆盖了95%的实际日常使用。

codex 打开交互式模式，用于与你的代码库进行探索、迭代和双向对话。

codex exec "" 运行 Codex 非交互式地。它将输出到 stdout 并在完成后退出。这是适用于任何可编写脚本的强大工具：

```bash
codex exec "add jsdoc to all exported functions in /src/lib/format.ts"
codex exec --json "audit dependency security and report as markdown"
cat error_log.txt | codex exec "explain this stack trace and propose a fix"
git diff HEAD~1 | codex exec "explain this diff in plain English"
codex exec --model gpt-5.3-codex "refactor /lib/data to use SWR everywhere"
```

将 Wire exec 集成到 Git 钩子、CI 流水线和 cron 任务中。它是所有自动化工作的基础组件。

codex resume --last 从你上次停止的地方继续。每个会话都会被存储：

```bash
codex resume --last "now do the follow-up"
codex resume --last "now write tests for the function you just added"
codex resume --all   # search all sessions across directories
```

codex cloud 管理异步云任务，相关内容见下方的云部分。

---

有用的标志:

- JSONL 事件流，用于管道传输到其他工具
- \--model &lt;name&gt; : 选择 GPT-5.5 或 GPT-5.3-Codex
- \--推理级别&gt; : 低、中或高
- \--search : 允许在任务期间进行网络搜索
- \-C &lt;dir&gt; : 在不同的工作目录中运行
- \--sandbox &lt;模式&gt; : 覆盖本次会话的沙箱模式
- \--approval &lt;policy&gt; : 覆盖本次会话的审批策略

#### 沙箱和审批

CLI 赋予你强大的能力。沙箱控制 Codex 无需请求即可行使的权限范围。正确配置这一点可让你的工作流程保持高效，同时避免风险。

沙箱是控制 Codex 能做和不能做的事情的边界。 正确设置它可以避免意外。

三种沙箱模式：

1. workspace-write (默认) : 在工作区内部读写，常规命令，除非允许否则无网络。几乎总是使用此选项。
2. 只读 ：只读，无写入，无 Shell。用于代码审查和探索。
3. danger-full-access：无限制。几乎从不使用。仅保留给经过测试和验证的自动化操作。

---

两个审批政策：

- 不可信的 — 在每个不可信命令前询问。适用于学习或在不熟悉的项目中使用。
- 按需（默认） — 自动批准常规的沙箱命令，在任何突破沙箱边界的操作前请求确认。

auto\_review 是一个审核子代理，它会根据你的 AGENTS.md 自动批准或拒绝。 通过在配置中设置 approvals\_reviewer = "auto\_review" 来启用它。适用于长时间异步任务和目标模式，在这些场景中你不想监控每一个步骤。

```bash
Starter ~/.codex/config.toml:
sandbox_mode = "workspace-write"
approval_policy = "on-request"
model = "gpt-5.5"
reasoning_effort = "medium"

[approvals]
trusted_commands = [
  "git status", "git diff", "git log",
  "pnpm install", "pnpm test", "pnpm lint", "pnpm typecheck"
]
```

添加不断请求你批准的命令。切勿添加任何破坏性内容。

#### 有效地提示 Codex

沙箱已配置，会话正在运行。下一个关键因素是提示质量，它对输出的影响比其他任何变量都大。

Codex 输出质量的唯一最大杠杆是提示词结构。模糊的提示词会生成模糊的代码。

框架： 告知，展示，描述，提醒。

- 告诉它你想要的结果，而不是方法
- 显示它示例输入和预期输出
- 描述要使用的 API、库和模式。
- 提醒它注意 AGENTS.md 中的约定

不是每次都需要全部四个。小 bug 修复可能只需要 Tell 和 Remind。新功能通常需要全部四个。

1. 单变更规则： Codex 在处理一件事上的表现比处理五件事好得多。“修复认证漏洞、添加测试、重构用户仓库以及更新 README”这种任务结果是随机的。将同样的工作拆分为四个提示则是可靠的。
2. 务必先制定计划 对于任何非平凡的事情：“先制定计划，在我批准之前不要编写代码。花三十秒审查计划胜过花三十分钟调试错误的实现。”
3. 明确指定失败行为。 如果任其发展，Codex 会以任何必要的方式让测试通过：

---

```markdown
If tests fail after your initial implementation:
- DO NOT modify the test to make it pass
- DO NOT add try/catch to hide the error
- Stop, write a summary of what failed and why, wait for my input.
```

明确约束上下文。 指定要读取的特定文件。“不要读取或修改其他任何内容。如果您需要其他地方的信息，请询问我。”

推理努力程度

- 低 ：琐碎的编辑、格式设置、简单重构
- 中等（默认）：大部分功能开发和错误修复
- 高 : 架构决策，困难调试，大型多文件重构

#### 目标模式

一旦单任务提示变得自然，下一阶段就是给 Codex 一个多日目标，并让它自行安排工作顺序。

目标模式适用于规模太大、无法逐项简要说明，但足够连贯以实现单一目标的工作。 它于 2026 年 5 月变得稳定。

```bash
codex goal "Migrate the test suite from Jest to Vitest.
One PR per package, no PRs over 500 lines. Run tests after each PR.
Don't open the next PR until the previous passes CI.
Stop and report when all packages migrate."
```

---

使用这些命令管理正在运行的目标：

1. Codex 目标状态：查看活跃的目标及其进度
2. Codex 目标日志 &lt;id&gt; : 查看 Codex 到目前为止所做的操作
3. codex goal pause &lt;id&gt; : 暂停执行并等待你的输入
4. codex 目标恢复 &lt;id&gt; : 从暂停处继续
5. codex 目标 取消 &lt;id&gt; : 停止并丢弃该目标

从有边界的目标开始。“最多 5 个 PR”，直到你信任 Codex 如何解读你的目标。一个失控的目标自信地做错事是最坏的结果。

始终与以下约束绑定：最大 PR 数量、每个 PR 的最大代码行数、PR 之间的 CI 门禁以及明确的停止条件。对任何未在 AGENTS.md 中涵盖的架构决策暂停。对任何破坏性 API 变更暂停。

#### 技能：可重复使用的工作流

目标模式处理大型项目。技能处理每个项目中都会出现的重复微工作流。如果你发现自己在不同会话中重复相同的指令，这就是你编写技能的信号。

Skill 是一个打包为目录的可复用工作流：SKILL.md 文件中的说明，以及可选的资源和脚本。

Codex 通过名称和描述发现技能。只有当某个任务触发该技能时，才会加载完整指令。你可以拥有 50 个零上下文成本的技能，直到其中一个被触发。

---

技能所在之处：

- 个人 ：
  [$HOME](https://x.com/search?q=%24HOME&src=cashtag_click)/.agents/skills/ ： 跨项目，反映你的工作方式，无论仓库如何
- 团队 ：repo 中的.agents/skills/路径：项目特定、版本控制、与协作者共享

---

SKILL.md 格式

```markdown
---
name: open-pr
description: Standard PR-opening workflow. Use when the user asks
  to open a PR, push a branch, or finish a feature.
---

When opening a PR:
1. Confirm the working branch is not main.
2. Ensure at least one commit since main.
3. Push the branch to origin.
4. Open a PR with conventional commit title and structured body.
5. Apply labels and request review from codeowners.
```

---

#### 每个高级用户都应该首先掌握的三项技能：

1. open-pr 是标准的 PR 工作流程：检查分支、推送、创建带有结构化正文的 PR、应用标签并请求审核。是日常工作中最常用的技能。
2. new-feature 读取 PRD 和 AGENTS.md，识别可复用的现有组件，输出计划，等待审批，实施，测试，并通过 open-pr Skill 打开 PR。如果 PRD 中有任何内容不明确，在生成代码前会先询问。
3. 调查是诊断不修复技能。它确认可复现性，读取相关代码路径，形成假设（“我认为 X 发生是因为 Y”），并以 Markdown 格式输出假设和验证计划。 它不执行修复。 输出是理解内容，而非代码。

调查技能很重要，因为如果你允许，Codex 每次都会跳过根本原因分析。它会直接跳到修复方案，而那个修复方案往往是错误的。强制先调查是提升调试输出质量的唯一最大改进。

#### 子代理与并行性

能力处理可重复的工作流。子代理处理并行的工作流。这种区别很重要，因为并行处理不当会产生更多问题而非解决问题。

子代理是一个独立的、隔离的代理实例。 它在自己的上下文中运行，返回一个摘要，并且它的上下文会被丢弃。它与 Skill 不同，Skill 在主代理的上下文中运行。

---

#### 三种子代理是合适工具的模式：

1. Exploration : 生成一个子代理来读取 30 个文件并进行总结；读取操作在它的上下文中进行，而不是在你的上下文中
2. 并行实现 ：五个独立的特性作为五个并发子代理，每个都有自己的上下文和计划
3. 验证 ：新的审核子代理不会因为刚刚编写了代码而带有偏见

---

自定义子代理在 .codex/agents/&lt;name&gt;.md 中定义：

```markdown
---
name: code-reviewer
description: Senior-engineer code review of a diff or PR.
model: gpt-5.5
reasoning_effort: high
tools: [read, grep, bash]
---

You are a senior engineer reviewing code for clarity, correctness,
and conformance to AGENTS.md.
Output: must fix, should fix, nice to have.
Be terse. Quote line numbers. Suggest fixes.
```

- 子代理寻址于 2026 年 3 月发货。通过昵称@ 与正在运行的子代理进行对话。
- 当多个并行运行且你想重定向其中一个而不影响其他时，很有用。
- 扇出模式：生成 N 个子代理，并行处理独立任务并汇总结果。
- 五个任务在最慢任务所需的时间内完成。经验法则：如果一个任务在主要场景中所需时间少于30秒，就在那里完成。

#### Codex Cloud：大规模异步工作

桌面应用程序支持你的本地和交互式工作。云是你在以下情况时会选择使用的：当工作过于庞大，无法在单个交互式会话中处理，或者当你希望在专注于其他工作时，多个任务能够并行运行。

Codex Cloud 是一项功能，它能将 Codex 从一个快速编码助手转变为一个可以水平扩展的初级工程团队。

提交任务后，Codex 会启动一个预加载了你的仓库的沙箱，进行工作、运行测试，并打开一个 PR。不会阻塞你的本地机器。

---

提交单个任务：

```bash
codex cloud submit --task "Add Sentry tags to /lib/integrations/stripe.ts"
```

并行任务；核心模式：

```bash

```

二十分钟后，四个 PR 已打开。审查、分类处理、合并。

CSV 扇出 让你可以提交一个任务文件，Codex 将它们以并行云代理的形式分发出去并进行进度跟踪：

#### GitHub 集成

云任务以 PR 的形式进入你的代码仓库。GitHub 集成决定了这些 PR 如何被审查，以及 Codex 如何融入你现有的 CI/CD 流水线。

Codex 和 GitHub 在三个层面上集成：代码仓库环境、拉取请求评审以及用于 CI/CD 的 codex-action。

代码仓库环境是基础。在 Codex 设置中关联 GitHub 代码仓库后，云任务将克隆该代码仓库，在沙箱容器中运行任务，并将结果作为分支或拉取请求推送。每个云任务都会自动读取 AGENTS.md 文件。

拉取请求评审以两种方式工作：

- 提及@codex，在任何 PR 评论中进行审查。Codex 以眼睛 emoji 回应以确认收到，然后发布一份聚焦于严重问题的结构化评论，这些问题已根据你的 AGENTS.md 进行检查。
- 开启自动评论，使 Codex 在每个新的 PR 上自动发布，无需手动触发。

在 Codex 发布评论后，要求它直接在 PR 评论线程中修复已标记的问题。它会将修复提交到同一分支并更新 PR。

codex-action 是一个官方的 GitHub Action，它可以在任何触发器（推送、定时触发、创建 issue 或打开 PR）下，在您的 CI/CD 管道中运行 Codex CLI。这是将 Codex 集成到无需人工参与的完全自动化管道中的推荐方式。

#### 自动化：无人值守工作

GitHub 集成处理当有人打开拉取请求（PR）时发生的情况。自动化处理完全不需要人员参与时发生的情况。

自动化任务是在专用工作树中运行的已安排的 Codex 任务。 从自动化面板设置它们：名称、项目、提示词、调度和执行环境。

线程复用功能于2026年4月推出。自动化可在多次运行中复用线程，积累上下文并随时间变得更智能。

每个项目都应该具备的三个入门级自动化

1. 每周依赖审查（周一凌晨 6 点）： 运行 pnpm outdated 和 pnpm audit。报告严重、重要和次要的发现。自动 PR 安全的次要和补丁升级。不要处理严重或重要更新；这些需要人工决策。
2. 每日 Sentry 分类处理（工作日上午 8 点）： 获取过去 24 小时按错误指纹分组的错误。对于每个出现次数 3 次或以上的分组，识别文件和行号，查看相关代码，确定根本原因。提交分类处理报告。仅进行诊断，不提供修复。
3. 每周陈旧 PR 清理（周五下午 5 点）： 列出超过 7 天未处理的已打开 PR。对于每个 PR，判断它是在等待你的处理、等待审核还是已陈旧，并发布提醒评论。不要关闭或合并任何 PR。

终止任何输出不再被读取的自动化程序。 一个好的自动化程序节省一个你本来就肯定会做的重复性任务，生成一个可扫描的单一输出，并且不会在无人值守的情况下执行破坏性操作。

#### MCP 集成

自动化与您代码仓库中的内容协同工作。MCP 服务器扩展 Codex，使其能够与仓库之外的所有内容协同工作。

```bash
codex mcp add context7 -- npx -y @upstash/context7-mcp
```

```bash
[mcp.servers.context7]
```

#### 验证：如何真正信任 Codex 输出

以上所有表面都会产生输出。核实决定了你实际能够交付的输出量。

---

生成已解决。验证是瓶颈。

五个并行的云 PR 就意味着有五个引入 bug 的机会。如果没有验证层，你的吞吐量将受限于你阅读 PR 的速度。

核心问题是谄媚。编写代码的模型倾向于认为自己是正确的。 让它审查自己的工作，大多数时候都会得到一个点赞。

---

#### 两个结构性修复：

1. 自动审核（在 Codex 中） 是 Codex 内置的审核子代理。全新上下文，不对之前的输出进行投入，更有可能标记真实问题。
2. 跨提供方核实（黄金标准）指 Codex 编写代码，Claude 进行代码审查。跨提供方能够发现特定于某一模型家族的盲点。这是生产代码的最小可行核实习惯。

---

计算机用于行为验证缩小了测试通过与实际可用之间的差距。让 Codex 打开开发服务器，点击相关流程，截图结果，并将其与你的 PRD 进行对比。

每个 PR 上的最小可行习惯： 在你自己打开 diff 之前，使用不同的模型进行自动审核。先阅读审核摘要。只有当审核结果干净时才打开 diff；然后阅读是为了感受，而非检查正确性。对于 UI 变更，查看截图。

#### 配方: 实战验证的模式

已建立验证习惯，以下是开发者通过 Codex 最常执行的任务的端到端模板。

1. 实现一个功能： 使用新功能技能。阅读 PRD 和 AGENTS.md。先做计划，等待审批。测试正常流程和一个错误场景。如果有任何不明确的地方，在生成代码前先询问。
2. 修复一个 bug： 首先使用调查技能。仅进行诊断。输出复现步骤、根本原因假设和验证计划。确认后再进行修复。
3. 重构：使用 grep 列出所有位置。输出迁移计划。等待审批。所有现有测试必须未经修改通过。如果测试需要更新，说明测试本身有问题；停止并报告。一个 PR。
4. 第三方集成： 将其放在 /lib/integrations/\[name\].ts 文件中。添加环境变量到 .env.example。本 PR 中无 UI。以草稿形式打开，用于针对外部服务进行手动测试。
5. 测试回填： 输出覆盖正常、边界和错误用例的测试计划。等待审批。所有测试必须在现有生产代码上通过。不得修改生产代码。
6. 依赖升级: 阅读版本间的发布说明。列出重大变更。等待审批。更新并应用代码变更。运行测试直至通过。
7. 目标模式启动： 绑定最大 PR 数量、每个 PR 的最大代码行数、PR 之间的 CI 门禁以及明确的停止条件。在 AGENTS.md 中未提及的架构决策处暂停。任何破坏性 API 变更处暂停。

---

#### 常见错误

这些模式涵盖了常见的成功。下面的部分涵盖了常见的失败；解释大多数糟糕的 Codex 体验的十个错误。

1\. 模糊的任务。 指定具体的成果、文件和限制条件。如果无法具体化，该任务尚未准备好进行简报。

2\. 没有 AGENTS.md。 写一个。即使是一个糟糕的，也比没有好。

3\. 跳过计划。“先制定计划”对于任何非平凡的事情。

4\. 多任务提示。 每个提示对应一个任务。使用子代理或云任务进行并行工作。

5\. 从危险级全权限访问开始。工作区写入和按需是除经过测试的自动化流程外所有内容的合适默认设置。

6\. MCP 和插件过多。保持列表精简。禁用你不经常使用的项。

7\. 自我审查. 使用 auto\_review 或完全不同的工具。编写代码的模型倾向于它。

8\. 将编译成功视为正确性。 包含行为验证。使用 Computer Use 进行用户界面变更。

9\. 过度并行化。 仅对独立工作进行并行化。共享文件必须进行序列化。

10\. 无界目标 最多 PR 数量、最多代码行数、最长时间、明确的停止条件。目标模式在你给初级工程师的那种约束下最有用。

##### 1. Codex 的定位变了

以前的 AI 编程工具像是：

> 你写代码，它帮你补几行。

现在作者描述的 Codex 更像是：

> 你分配任务，它自己读项目、写代码、跑测试、开 PR，你负责审查。

所以开发者角色也变了：

- 以前：亲自写代码
- 现在：写需求、定规则、审结果

一句话：  
**你从“码农”变成了“技术负责人”。**

---

##### 2. `AGENTS.md` 是核心

`AGENTS.md` 就像给 AI 的“项目入职手册”。

里面应该写：

```md
- 项目用什么技术栈
- 怎么安装依赖
- 怎么跑测试
- 代码风格是什么
- 哪些文件不能碰
- PR 有什么要求
```

不要写：

```md
- 写干净代码
- 注意质量
- 自己看着办
```

因为这些太空泛，AI 不知道具体标准。

一句话：  
**没有 `AGENTS.md`，Codex 就像没入职培训的新员工。**

---

##### 3. 好提示词决定结果上限

差提示词：

```md
修一下支付问题
```

好提示词：

```md
修复 checkout 中信用卡校验逻辑：

要求：
- 去掉空格和短横线后，只能包含数字
- 长度 12 到 19 位
- 必须通过 Luhn 校验
- 保持现有代码风格
- 增加有效和无效卡号测试
- 完成后运行测试
```

差别在于：  
**好提示词给了目标、边界、验收标准。**

---

##### 4. 不要一次塞太多任务

错误做法：

```md
修 bug、加测试、重构用户模块、更新 README
```

正确做法：

```md
第一步：只定位 bug 原因，不修改代码。
第二步：确认方案后再修复。
第三步：补测试。
第四步：更新文档。
```

Codex 更适合：

> 一个清晰任务，一个明确结果。

---

##### 5. Cloud 和 Goal Mode 适合“批量派活”

比如你可以同时让 Codex 做：

```md
- 修 pricing 页面错别字
- 给列表加 loading 状态
- 更新 README
- 给 Stripe 错误加 Sentry 标签
```

它们互不影响，就适合并行。

但如果多个任务会改同一批文件，就不要并行，否则容易冲突。

一句话：  
**独立任务并行，相关任务串行。**

---

##### 6. 最重要的是验证

作者强调：

> 生成代码已经不难，难的是确认代码真的对。

所以不能只看：

```md
测试通过
编译成功
```

还要看：

```md
- 代码逻辑是否合理
- 是否破坏现有设计
- UI 是否真的正常
- 是否有边界情况
- 是否需要另一个模型复查
```

尤其是 AI 自己写完再自己审，容易“自我感觉良好”。

更好的方式：


- **浏览器/计算机使用能力**：适合前端验证、端到端测试、截图检查。

选择界面的关键是：你想多紧密地跟进 Codex 的工作。  
想实时看修改，用 CLI 或 IDE；想让它后台跑完再看，用 Cloud。

##### 5. `AGENTS.md` 是最重要的项目文件

`AGENTS.md` 决定 Codex 每次会话是否能稳定产出高质量结果。

- 它是项目根目录下的 Markdown 文件。
- Codex 每次启动都会优先读取它。
- 它也是开放标准，Codex、Cursor、Gemini CLI、Windsurf、GitHub Copilot 都能读取。

###### 应该写入

- 技术栈、框架、语言版本、包管理器；
- 精确的构建、测试、开发命令；
- 文件结构、命名规则；
- 代码风格和架构模式；
- 禁止修改的区域；
- 发布、CI、PR 要求。

###### 不应该写入

- 密钥或凭证；
- “写整洁代码”这类模糊指导；
- README 的重复内容。

建议控制在 500 字以内，总限制为 32 KiB。

##### 6. CLI 的核心用法

大多数日常场景主要靠 4 类命令完成。

```bash
codex
```
进入交互式模式。

```bash
codex exec "add jsdoc to all exported functions in /src/lib/format.ts"
```
执行一次性非交互任务。

```bash
codex resume --last
```
恢复上次会话。

```bash
codex cloud submit --task "fix typo in pricing page"
```
提交云端异步任务。

常用参数包括：

- `--model`：选择模型；
- `--reasoning`：设置推理强度；
- `--search`：允许联网搜索；
- `-C &lt;dir>`：指定工作目录；
- `--sandbox`：覆盖沙箱模式；
- `--approval`：覆盖审批策略。

---

##### 7. 沙箱和审批：效率与安全的边界

沙箱决定 Codex 不经批准能做什么。

###### 三种沙箱模式

- **workspace-write**：默认模式，可在工作区读写，适合大多数情况。
- **read-only**：只读，适合代码审查和探索。
- **danger-full-access**：无限制，几乎不应使用。

###### 两种审批策略

- **untrusted**：每个不可信命令前询问，适合新手或陌生项目。
- **on-request**：默认策略，常规命令自动执行，越界操作需确认。

还可以启用 `auto_review` 审核子代理，让它根据 `AGENTS.md` 自动批准或拒绝操作，适合长时间异步任务。

---

##### 8. 高质量提示词的结构

Codex 输出质量最大的杠杆是提示词结构。

作者提出四部分框架：

1. **告诉**：说明想要的结果，而不是具体实现方法。
2. **展示**：给出示例输入和预期输出。
3. **描述**：指定要使用的 API、库和模式。
4. **提醒**：强调 `AGENTS.md` 中的约定。

###### 关键原则

- 每个提示只做一件事。
- 非简单任务先让 Codex 制定计划，不要直接写代码。
- 明确失败时的行为，例如测试失败后不要修改测试掩盖问题。
- 限定上下文和文件范围，避免它乱读乱改。

---

##### 9. 目标模式：处理大型连续任务

目标模式适合“过大但目标统一”的工作，例如迁移测试框架。

示例：

```bash
codex goal "Migrate the test suite from Jest to Vitest.
One PR per package, no PRs over 500 lines.
Run tests after each PR.
Don't open the next PR until the previous passes CI.
Stop and report when all packages migrate."
```

使用目标模式时必须设置边界：

- 最大 PR 数量；
- 每个 PR 最大代码行数；
- PR 之间必须通过 CI；
- 明确停止条件；
- 架构决策或破坏性 API 变更时暂停询问。

---

##### 10. Skill：可复用工作流

Skill 是可复用的任务说明包，适合重复出现的小型工作流。

它通常由一个目录和 `SKILL.md` 文件组成，可放在：

- `$HOME/.agents/skills/`：个人跨项目技能；
- 仓库内 `.agents/skills/`：团队共享技能。

作者建议优先建立三类技能：

1. **open-pr**：检查分支、提交、推送、创建 PR、加标签、请求审核。
2. **investigate**：只诊断不修复，输出复现步骤、根因假设和验证计划。
3. **new-feature**：用于规范新功能开发流程。

其中，调查技能非常重要，因为 Codex 往往会跳过根因分析直接修复，导致修错方向。

---

##### 11. 子代理：并行与独立审查

子代理是独立的代理实例，拥有自己的上下文，完成后只返回摘要。

适合三类场景：

- 多个独立功能并行开发；
- 独立验证；

##### 15. GitHub 集成与自动化

Codex 与 GitHub 有三层集成：

1. **仓库环境**：云任务克隆仓库并读取 `AGENTS.md`。
2. **PR 审查**：Codex 可自动评论 PR，也可根据评论修复问题。
3. **codex-action**：在 GitHub Actions 中运行 Codex CLI，用于 CI/CD 自动化。

###### 推荐的三个自动化任务

1. **每周依赖审查**  
   周一早上运行 `pnpm outdated` 和 `pnpm audit`，自动 PR 安全的小版本或补丁升级。

2. **每日 Sentry 分类处理**  
   工作日上午分析过去 24 小时错误，出现 3 次以上的错误要定位文件和行号，只诊断不修复。

3. **每周陈旧 PR 清理**  
   找出超过 7 天未处理的 PR，判断状态并发布提醒，不自动关闭或合并。

好的自动化应节省确定会做的重复任务，输出可扫描结果，并避免无人值守的破坏性操作。

##### 18. 验证：信任 Codex 输出的关键

作者强调：生成代码已经不是瓶颈，验证才是瓶颈。

问题在于：写代码的模型往往倾向于认为自己正确，让它自审通常不可靠。

###### 两个结构性解决方案

1. **自动审核**  
   用独立上下文的审核子代理审查 PR。

2. **行为验证**  
   对 UI 改动，让 Codex 打开开发服务器、点击流程、截图，并对比需求。

推荐习惯：

- 在自己看 diff 前，先用不同模型或 auto_review 审查；
- 审核干净后再看 diff；
- UI 变更必须看截图或行为验证结果。

##### 19. 常见实战模式

作者总结了几类常见任务模板：

- **实现功能**：先读 PRD 和 `AGENTS.md`，先计划，获批后写代码，测试正常和错误路径。
- **修复 bug**：先用调查技能，只诊断不修复，确认根因后再改。
- **第三方集成**：放在 `/lib/integrations/[name].ts`，更新 `.env.example`，先开草稿 PR。
- **测试回填**：先输出测试计划，获批后写测试，不修改生产代码。
- **依赖升级**：先读发布说明，列出破坏性变更，获批后更新并跑测试。
- **目标模式**：绑定 PR 数量、行数、CI 门禁和停止条件。

##### 20. 十类常见错误

文中列出的典型失败原因包括：

1. 任务太模糊；
2. 没有 `AGENTS.md`；
3. 一个提示里塞多个任务；
4. 让 Codex 自我审查；
5. 把“编译通过”误认为“功能正确”；
6. 缺少行为验证；
7. 过度并行化；
8. 共享文件并行修改导致冲突；
9. 目标模式没有边界；
10. 没有明确停止条件。

核心建议：像管理初级工程师一样管理 Codex，给清晰任务、边界、验收标准和审查流程。
