## 分析要点

- **核心高价值点**：Agent不能与执行容器绑定，session、harness、sandbox必须分层，才能支持恢复、治理、观测和长期运行。
- **留存建议**：长期保留，适合作为理解Agent运行时架构和产品组织形态的参考材料（文章系统梳理了Agent基础设施中的session、sandbox、harness、control plane与data plane分层，对Agent产品架构设计有长期参考价值）

**知识要点**

- Agent系统应区分session、harness/workflow与sandbox，避免将记忆、控制、凭证和执行环境混在同一生命周期中
- session不等于context window，长期运行Agent需要durable session、event log、approval、policy、resume与replay等机制
- Agent架构将进一步分化为control plane和data plane，前者负责规划治理，后者负责执行和环境承载
- 多Agent产品形态会分化为面向工程用户的coding workflow和面向普通用户的数字员工组织界面

**行动项**

- 研究Anthropic Managed Agents、Vercel Open Agents和Cube Sandbox的架构设计
- 在设计Agent系统时显式拆分session、workflow/harness和sandbox对象
- 评估现有Agent产品是否具备durable session、observability、approval和policy能力
- 将control plane与data plane分层作为Agent基础设施设计原则

## 正文

**Tianyu Fan**

### 当 agent 足够强之后，我们该如何把它们组织起来

一个有趣的现象是，之前大家讨论“agent loop的底层”的时候，通常是在讨论一个模型，而到了现在，大家讨论的loop的底层逐渐从模型转为了cc/codex，也就是把强大的coding agent本身当成一个可wrap的“LLM”看待。

这样的转变是由于，强大的代码agent本身能够轻易的跨领域到其他任务，例如搜索数据，阅读报告，分析材料等。那么当 agent loop的底层不再只是一个会回答问题的模型，而是一个可以持续承担责任、接收上下文、产出中间成果并参与交接流的数字执行体，什么样的技术、什么样的系统结构、什么样的协作界面、什么样的组织方式，才真正配得上这样一种新的劳动单元？

#### 第一个技术共识（刚达成）：sandbox/session/harness的严格分离

这几周看下来，我越来越觉得最重要的技术共识其实已经非常明确了，那就是 agent 不能直接“住”在执行容器里，因为只要脑、记忆、工具调度、凭证、文件系统和执行环境被塞进同一个生命周期里，系统马上就会退化成一只非常昂贵、非常脆弱、同时也非常难治理的“宠物容器”，而anthropic有一个很有意思的比喻：工作单元应该是牛马（cattle）而不是宠物（pet）\[3\]。

从这个意义上来说，最近我们看到了很多新东西，腾讯 Cube Sandbox\[1\]、Vercel Open Agents\[2\]、Anthropic Managed Agents\[3\] 其实都在回答同一个问题，也就是为什么 agent 和执行环境必须拆开，为什么 session、workflow、sandbox 这些东西必须被视为不同层级的对象。因为只有拆开之后，session 才可能成为可恢复的、连续性的载体，harness 或 workflow 才可能成为真正意义上的控制器（手柄），而 sandbox 才能被降回它一双手+一套执行底座的本来面目，而不是同时兼任大脑/记忆/控制器。

Anthropic 上周宣布Managed Agents\[3\]时，把系统拆成 \`session\`、\`harness\`、\`sandbox\` 三层，我本来觉得这事只是一个命名上的清晰化(A家传统lol），现在反思了一下，只有在这种严格的分层之下，session 才能够脱离context独立存在，sandbox 才可以被即用即弃，provider（cc/codex) 才能在不破坏整套产品语义的情况下独立演进，policy、approval、observability 这些原本很难加进去的治理能力，才终于有稳定的插入点.

Vercel Open Agents\[2\]（很喜欢这个） 把整个agent系统直白地写成 \`Web -&gt; Agent workflow -&gt; Sandbox VM\`，也是在表达同一件事，也就是交互、控制和执行三个功能根本不该混在一个生命周期里，否则一切高阶能力都会被请求周期和执行环境反向绑死，也就是现在cc/codex直接用上之后的核心问题。

所以sandbox的快速迭代就会变的更重要，Cube Sandbox\[1\]/E2B这类沙盒把 execution substrate 这件事真正往基础设施问题推进了一大步，KVM MicroVM、E2B 兼容、快照恢复、网络隔离这些事没那么fancy，但确实是agent infra的重要组成部分，它们决定了上层产品到底能不能真的托管一个 long-horizon agent，能不能让 agent 在零信任的前提下持续运行。

TLDR: Anthropic 托管型代理\[3\] 解决 agent 运行时架构，Vercel 开放型代理\[2\] 解决云参考实现，Cube 沙箱\[1\] 解决沙箱层的执行基础设施。

#### 第二个技术共识（已达成）：session 不等于 context window

第二个共识是 session 不能等于上下文窗口，因为真正进入生产之后，agent 面对的不是几十轮对话，而是几小时、几天、甚至持续运行的工作，context window 只够承载推理过程，却远远不够承载系统记忆。当 CC 把 session 放到模型上下文之外，当 OpenAI 推出 Workspace Agents\[4\] 并强调云端持续运行、跨入口协作、审批和治理的时候，agent的目标是成为长期运行实体，而长期运行实体意味着你必须拥有 durable session、hosted control plane、run/event log、approval、policy、resume、replay 这些原本只会在分布式系统或 workflow engine 里认真讨论的概念。

一个例子是openrouter，openrouter可以把context在不同的模型之间传来传去，这是LLM作为agent loop底层时的router。那么到了agent作为agent loop底层的时代，新router面对的也不会只是message，而是逐渐变成 \`session\`、\`run\`、\`event\`、\`sandbox\`、\`handoff\`、\`approval\` 这些互相独立的系统对象。

#### 第三个技术共识：control plane 和 data plane 会彻底分层

2025年的时候大家更习惯把 agent 理解成一个会调工具的单体程序，仿佛只要把 shell、browser、filesystem、search、diff 这些能力挂到模型后面，再加一层 prompt 约束，问题就算解决了，但现在更合理的看法其实应该是 agent、workflow、harness 这一层负责控制平面，也就是负责目标理解、步骤规划、工具决策、权限治理和失败恢复，而 sandbox、filesystem、browser、shell、network 这一层负责数据平面，也就是负责真正执行命令、承载文件、暴露端口、执行网络访问和快照恢复，这种分层一旦成立，很多以前混在一起的问题就会被重新组织起来，因为模型升级不一定要碰执行环境，sandbox 替换、agent loop执行、session 恢复也变成了越来越独立的部分。

这也正是为什么我越来越觉得谁先把控制平面和执行平面拆清楚，谁就更容易在上层攒出稳定且丝滑的 agent-as-worker 产品。

#### agent成为一等公民后的产品

分离control、data和agent的产品越来越多，但就像cursor从tab tab tab到与agent对话然后做任何事一样，想要做同一件事，但不同的交互体验会带来完全不同的用户。最近很喜欢 Multica\[5\]、Slock\[7\]，写的时候也看到

[@turingou](https://x.com/@turingou)发布了 wanman\[6\]（还没来得及试用）。

同样叫多 agent 协作/一个agent是一个数字员工，感觉背后至少已经分成了两条路，一条更偏 coding，也就是默认用户愿意接触代码、仓库、CLI、runtime、日志和工程化工作流，另一条更偏 \`ordinary-user-oriented\`，也就是默认用户并不想理解 agent infrastructure，而只是“更便宜的雇一个人”，甚至不在乎是真人还是数字员工。

斯洛克、马尔蒂卡

Multica\[5\]

[@MulticaAI](https://x.com/@MulticaAI) 的核心体验不是“来和一个聪明助手聊天”，而是启动 daemon+拉个看板开始发任务，这很像github issue的可视化进程，并把发任务这件事做得非常简单和容易。

Slock\[7\]

[@istdrc](https://x.com/@istdrc) 也类似，虽然它的表现层更像 IM，但它也并不是“聊天更顺滑”的聊天助手，而是在把 agent 放进协作流里，让 channel、DM、上下文、任务和持续协同之类的功能成为UI界面就能感知到的东西。

完美

wanman\[6\]

[@turingou](https://x.com/@turingou) 把多 agent 系统包装成一种普通人也能理解的组织故事，完全不提daemon/runtime，而是说这里有一个 CEO/一个 marketing，它们组成一个可以持续运转的 agent matrix，而人类可以逐渐退到观察者和干预者的位置上去。这有点像coze和n8n/langchain的区别。

回到标题，如何组织起来这点我觉得永远不会有答案，或者说永远有不同的答案。因为飞书、微信、github、钉钉、slack、discord、telegram、邮件管理各有各的组织方式，5个agent、50个agent和500个agent又有不同。但表面上完全不同的产品线的底层都在共享同一套技术前提，也就是 durable session、hosted control plane、agent-sandbox separation、policy和 observability。

## 通俗精炼（1）

### 2026-04-27 08:02:39

#### 当 Agent 足够强之后，关键不再是 “模型”，而是 “组织方式”

##### 核心观点

随着 Coding Agent 能力增强，Agent 已经不只是一个会回答问题的模型，而更像一个可以持续工作、交接任务、调用工具、产出成果的 “数字执行体”。

因此，接下来的重点不是单个 Agent 有多聪明，而是：**如何把 Agent 作为一种新型劳动单元，稳定、安全、可治理地组织起来。**

---

##### 一、Agent 运行架构的共识：Session / Harness / Sandbox 必须分离

过去很多系统会把模型、记忆、工具、凭证、文件系统、执行环境都塞进一个容器里，这会导致系统脆弱、昂贵、难治理。

新的共识是三层分离：

- **Session**：承载长期状态、任务连续性和恢复能力  
- **Harness / Workflow**：负责控制流程、调度、审批、治理  
- **Sandbox**：只负责执行命令、访问文件、运行代码等底层能力  

这样做的好处是：

- Session 可以长期存在，不依赖单次上下文窗口
- Sandbox 可以即用即弃，更安全、更低成本
- Agent Provider 可以独立升级，不破坏产品语义
- 权限、审批、日志、观测等治理能力有稳定插入点

代表方向包括：

- **Anthropic Managed Agents**：定义运行时架构
- **Vercel Open Agents**：提供云端参考实现
- **Cube Sandbox / E2B**：提供安全执行基础设施

---

##### 二、Session 不等于 Context Window

文章强调，真正生产级 Agent 面对的不是几十轮对话，而是持续数小时、数天甚至更久的工作。

所以，**上下文窗口只能承载短期推理，不能承载长期记忆和工作状态。**

生产级 Agent 需要的是 durable session，也就是可持久化、可恢复、可追踪的工作会话，包含：

- Run / Event Log
- Resume / Replay
- Approval / Policy
- Handoff
- Sandbox 状态
- 跨模型、跨入口协作能力

这意味着未来的 Agent Router 不再只是转发 message，而是要管理更复杂的系统对象：`session`、`run`、`event`、`approval`、`handoff`等。

---

##### 三、Control Plane 和 Data Plane 会彻底分层

过去大家容易把 Agent 看成 “模型 + 工具调用” 的单体程序。

但未来更合理的架构是：

###### Control Plane：控制平面

负责：

- 理解目标
- 拆解任务
- 规划步骤
- 调度工具
- 权限治理
- 失败恢复

###### Data Plane：数据平面

负责：

- 执行命令
- 管理文件系统
- 浏览器操作
- 网络访问
- 端口暴露
- 快照恢复

这种分层会让系统更稳定：模型升级、Sandbox 替换、Session 恢复、Agent Loop 优化都可以相对独立演进。

谁能先把这两层拆清楚，谁就更容易做出真正可靠的**Agent-as-Worker**产品。

---

##### 四、Agent 成为一等公民后，产品形态开始分化

当 Agent 不再只是聊天助手，而是数字员工，产品形态会出现不同路线。

###### 路线一：面向开发者和工程场景

这类产品默认用户理解代码、仓库、CLI、Runtime、日志、工程流。

典型形态更像：

- GitHub Issue
- 看板
- Workflow
- Daemon
- 多 Agent 协作任务流

例如**Multica**：不是让用户和助手聊天，而是启动后台进程，通过看板分配任务。

###### 路线二：面向普通用户和组织场景

这类产品隐藏基础设施复杂度，让用户感觉像是在 “雇佣一个人”。

例如：

- **Slock**：把 Agent 放进 IM、Channel、DM、任务上下文中
- **wanman**：用 CEO、Marketing 等组织角色包装多 Agent 系统，让普通用户理解 “数字公司” 的协作方式

这类产品的重点不是展示 Runtime，而是构建用户熟悉的组织叙事。

---

##### 五、组织 Agent 没有唯一答案

作者认为，“如何组织 Agent” 不会有标准答案。

因为不同协作工具本身就有不同组织范式：

- 飞书
- 微信
- GitHub
- Slack
- Discord
- Telegram
- 邮件

同时，5 个 Agent、50 个 Agent、500 个 Agent 的组织方式也完全不同。

但无论产品表层怎么变化，底层技术前提正在趋同：

- Durable Session
- Hosted Control Plane
- Agent-Sandbox Separation
- Policy
- Observability

---

##### 总结

Agent 足够强之后，竞争焦点会从 “单个模型能力” 转向 “系统组织能力”。

未来真正重要的是：  
**能否把 Agent 当作长期运行、可治理、可协作、可交接的数字劳动单元来设计。**

这要求产品和技术同时完成一次升级：  
从 “聊天助手” 走向 “数字员工”，从 “模型调用” 走向 “Agent 操作系统”。

## 结构化（1）

### 2026-04-27 08:05:49

#### 《当 agent 足够强之后，我们该如何把它们组织起来》精炼总结

文章核心观点是：当 coding agent 变得足够强，它们不再只是 “模型的外壳”，而更像可以持续工作的 “数字执行体”。因此，未来的关键问题不只是让 agent 更聪明，而是如何把 agent、执行环境、会话、权限、协作界面和组织方式系统化地拆分与管理。

---

##### 1. agent loop 的底层正在变化：从 “模型” 变成 “强 agent”

过去讨论 agent loop 的底层，通常是在讨论一个大模型如何循环思考、调用工具、完成任务。

但现在，很多人开始把**Claude Code / Codex 这类强大的 coding agent 本身**，当成一个可以被包装、调用的 “LLM” 来看待。

原因是：

- 强 coding agent 已经不只会写代码；
- 它们可以跨领域完成任务，比如：
  - 搜索数据；
  - 阅读报告；
  - 分析材料；
  - 产出中间结果；
  - 接收上下文并继续推进工作。

因此，agent 正在从 “回答问题的模型” 变成一种新的劳动单元：  
**可以持续承担责任、参与交接、长期运行的数字执行体。**

---

##### 2. 技术共识一：必须严格分离`session /harness/sandbox`

作者认为，近期最重要的技术共识是：  
**agent 不能直接 “住” 在执行容器里。**

如果把以下东西都塞进同一个容器生命周期里：

- 大脑；
- 记忆；
- 工具调度；
- 凭证；
- 文件系统；
- 执行环境；

系统就会变成一个昂贵、脆弱、难治理的 “宠物容器”。

Anthropic 用了一个比喻：  
**工作单元应该像 “牛马 cattle”，而不是 “宠物 pet”。**  
意思是：执行环境应该可替换、可销毁、可恢复，而不是被精心照顾的唯一容器。

---

###### 2.1 三层结构：`session /harness/sandbox`

Anthropic Managed Agents 将系统拆成三层：

```text
session /harness/sandbox
```

这三层分别对应：

- **session**：承载持续性和可恢复性；
- **harness /workflow**：负责控制流程，相当于 “手柄” 或控制器；
- **sandbox**：只负责执行，是 “一双手” 和执行底座。

这种拆分的好处是：

- session 可以脱离模型上下文独立存在；
- sandbox 可以即用即弃；
- provider，如 Claude Code / Codex，可以独立升级；
- policy、approval、observability 等治理能力有稳定插入点。

---

###### 2.2 Vercel Open Agents 的结构也体现同一思路

Vercel Open Agents 将系统写成：

```text
Web -> Agent workflow -> Sandbox VM
```

这说明：

- Web 是交互层；
- Agent workflow 是控制层；
- Sandbox VM 是执行层。

作者认为，交互、控制和执行不应该混在一起。  
否则，高阶能力会被请求周期和执行环境限制住。

---

###### 2.3 Sandbox 正在变成 agent 基础设施

Cube Sandbox、E2B 这类产品正在把 sandbox 推向基础设施层。

它们关注的能力包括：

- KVM MicroVM；
- E2B 兼容；
- 快照恢复；
- 网络隔离；
- 安全执行环境。

这些能力看起来不炫酷，但决定了：

- agent 能不能长期运行；
- agent 能不能在零信任环境下执行任务；
- 上层产品能不能真正托管 long-horizon agent。

作者总结：

- **Anthropic Managed Agents**：解决 agent 运行时架构；
- **Vercel Open Agents**：提供云端参考实现；
- **Cube Sandbox**：解决沙箱执行基础设施。

---

##### 3. 技术共识二：`session`不等于`context window`

第二个关键共识是：  
**session 不能等同于模型上下文窗口。**

因为真正进入生产环境后，agent 面对的不是几十轮对话，而是：

- 几小时的任务；
- 几天的任务；
- 持续运行的工作流。

模型的 context window 只适合承载短期推理过程，无法承担长期系统记忆。

---

###### 3.1 长期运行的 agent 需要 durable session

当 agent 成为长期运行实体时，系统需要引入很多过去属于分布式系统或 workflow engine 的概念：

- durable session：持久会话；
- hosted control plane：托管控制平面；
- run /event log：运行记录与事件日志；
- approval：审批；
- policy：策略；
- resume：恢复；
- replay：重放。

OpenAI Workspace Agents 强调的云端持续运行、跨入口协作、审批和治理，也是在朝这个方向发展。

---

###### 3.2 agent 时代的新 router 不再只路由 message

作者举了 OpenRouter 的例子。

在 LLM 作为 agent loop 底层时，OpenRouter 主要是在不同模型之间传递 context。

但当 agent 本身成为 agent loop 底层时，router 面对的不再只是 message，而是更复杂的系统对象，例如：

```text
session /run/event /sandbox/handoff /approval
```

也就是说，未来的 agent router 要管理的是一套完整的工作系统，而不只是聊天消息。

---

##### 4. 技术共识三：`control plane`和`data plane`会彻底分层

过去，很多人把 agent 理解成一个会调工具的单体程序。

只要给模型挂上：

- shell；
- browser；
- filesystem；
- search；
- diff；

再加一些 prompt 约束，就认为问题解决了。

但作者认为，现在更合理的结构是：  
**控制平面和数据平面必须拆开。**

---

###### 4.1 控制平面负责 “决策和治理”

控制平面包括：

- agent；
- workflow；
- harness。

它们负责：

- 理解目标；
- 规划步骤；
- 决定调用什么工具；
- 管理权限；
- 处理失败恢复。

---

###### 4.2 数据平面负责 “真实执行”

数据平面包括：

- sandbox；
- filesystem；
- browser；
- shell；
- network。

它们负责：

- 执行命令；
- 承载文件；
- 暴露端口；
- 网络访问；
- 快照恢复。

---

###### 4.3 分层后的好处

一旦控制平面和数据平面分离，很多问题会更清晰：

- 模型升级不一定影响执行环境；
- sandbox 可以独立替换；
- agent loop 可以独立演进；
- session 恢复机制可以独立设计。

作者认为，谁能先把这两层拆清楚，谁就更容易做出稳定、顺滑的**agent-as-worker**产品。

---

##### 5. agent 成为一等公民后的产品形态

随着 agent、control plane、data plane 被拆分，越来越多产品开始围绕 “agent 是一个数字员工” 来设计。

但不同产品的交互方式会带来完全不同的用户群体。

作者认为，目前大致分成两条路线：

---

###### 5.1 面向工程用户的 coding 路线

这一类产品默认用户愿意理解：

- 代码；
- 仓库；
- CLI；
- runtime；
- 日志；
- 工程化工作流。

它更接近开发者工具链。

---

###### 5.2 面向普通用户的数字员工路线

另一类产品更偏向普通用户：

- 用户不需要理解 agent infrastructure；
- 只需要像 “便宜雇一个人” 一样发任务；
- 甚至不关心对方是真人还是数字员工。

这类产品重点不在技术可见性，而在组织和协作体验。

---

##### 6. 典型产品案例

###### 6.1 Multica：像看板一样给 agent 发任务

Multica 的核心体验不是 “和智能助手聊天”，而是：

- 启动 daemon；
- 拉出一个看板；
- 直接发任务。

作者认为它很像**GitHub issue 的可视化进程版**，把 “给 agent 分配任务” 这件事做得简单、直观。

---

###### 6.2 Slock：把 agent 放进协作流

Slock 的表现层更像 IM 工具，但它并不是单纯让聊天更顺滑。

它的重点是把 agent 放进团队协作流，让这些东西在 UI 中变得可感知：

- channel；
- DM；
- 上下文；
- 任务；
- 持续协同。

也就是说，agent 不只是一个聊天对象，而是协作空间中的参与者。

---

###### 6.3 wanman：用 “组织故事” 包装多 agent 系统

wanman 把多 agent 系统包装成普通人能理解的组织结构。

它不强调：

- daemon；
- runtime；
- infra。

而是说这里有：

- 一个 CEO；
- 一个 marketing；
- 一个持续运转的 agent matrix。

人类可以逐渐退到：

- 观察者；
- 干预者。

作者认为，这有点像**Coze 和 n8n / LangChain 的区别**：  
前者更面向普通用户的组织想象，后者更面向技术工作流。

---

##### 7. 最终判断：组织 agent 没有唯一答案，但底层技术前提会趋同

作者认为，“如何组织 agent” 不会有唯一答案。

因为不同协作工具本身就有不同组织方式：

- 飞书；
- 微信；
- GitHub；
- 钉钉；
- Slack；
- Discord；
- Telegram；
- 邮件。

同时，agent 数量不同，组织方式也会不同：

- 5 个 agent；
- 50 个 agent；
- 500 个 agent。

但无论产品形态多么不同，底层都会共享一套共同技术前提：

- durable session；
- hosted control plane；
- agent-sandbox separation；
- policy；
- observability。

---

##### 总结

这篇文章的核心结论是：  
当 agent 变得足够强，它们会从 “模型工具” 升级为 “数字员工”。要真正组织和管理这些数字员工，关键不是单纯提升模型能力，而是建立清晰的系统架构：持久 session、控制平面、执行沙箱、治理策略和可观测性。

未来不同产品会用不同方式组织 agent：有的像开发者工作流，有的像 IM 协作，有的像公司组织架构。但无论外层体验如何变化，底层都会越来越依赖同一套 agent infrastructure。
