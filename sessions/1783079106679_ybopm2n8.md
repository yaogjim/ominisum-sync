## 分析要点

- **核心高价值点**：将多代理协作的关键落在“明确交接文件”和“顺序编排”上，而不是简单堆叠多个代理。
- **留存建议**：短期参考后可选择归档（包含可直接复用的 Claude Code 多代理配置模板和交接流程设计，可作为搭建自动化编码流水线的参考。）

**知识要点**

- 多代理流水线可按规划、编码、测试、评审拆分职责，降低单一代理上下文膨胀带来的质量下降。
- 通过 .pipeline/spec.md、changes.md、test-results.md、review.md 等文件作为阶段交接物，可让后续代理基于明确上下文工作。
- 评审代理保持只读权限，有助于避免其直接修改代码掩盖问题，只输出 SHIP、NEEDS WORK 或 BLOCK 结论。
- Claude Code 斜杠命令可作为轻量编排器，依次调用子代理并检查交接文件是否存在。

**行动项**

- 在测试仓库中创建 planner、coder、tester、reviewer 四个 Claude Code 子代理配置文件。
- 实现一个 /ship 命令，按顺序执行规划、编码、测试和评审，并在失败或开放问题处暂停。
- 先从 Planner 与 Coder 两阶段流水线试运行，稳定后再加入 Tester 和 Reviewer。
- 评估自动生成代码的质量、测试有效性和人工 review 成本，决定是否长期采用该流程。

#### 为什么一个管道优于一堆代理

一个包办一切的代理会用规划、代码、测试和评审笔记填满其上下文窗口，直到质量下降。

四位专家各自处于一个清晰、狭窄的情境中。

关键在于交接文件每个代理写入其输出，以便下一个可以读取：规划器在 .pipeline/spec.md，编码者读取它并写入 .pipeline/changes.md，依此类推。

按顺序运行它们的编排器是一个单独的斜杠命令。这就是全部内容：四个子代理、一个命令、一个用于交接的共享文件夹。

#### 代理 1：规划器（子代理，opus）

规划师从不编写代码。它将模糊的功能请求转化为具体的规范，使编码人员可以无需猜测地遵循。

创建 .claude/agents/planner.md:

```markdown
---
name: planner
description: Turns a feature request into an implementation spec. Use as the first stage of the feature pipeline.
tools: Read, Grep, Glob, Write
model: opus
---

You are a planning specialist. You do NOT write implementation code.

Given a feature request:
1. Read the relevant parts of the codebase to understand current patterns.
2. Write a spec to `.pipeline/spec.md` containing:
   - Files to create or modify, with exact paths
   - The interface or function signatures needed
   - Edge cases the implementation must handle
   - Which existing patterns to follow (name the file to copy from)
3. Flag anything ambiguous as an OPEN QUESTION at the top of the spec.

Keep the spec tight. The Coder reads this and nothing else, so leave
no gaps and invent no requirements that weren't asked for.
```

规划运行于 opus 因为这个阶段为后续的所有工作设置了质量上限。无论编码者水平多高，模糊的需求规格都会产生模糊的代码。

#### 代理2：编码者（子代理，十四行诗）

程序员阅读规格说明并编写实现代码。它不做规划，也不审查自己的工作，只按照规格说明进行构建。

创建 .claude/agents/coder.md:

```markdown
---
name: coder
description: Implements the spec at .pipeline/spec.md. Use as the second stage of the feature pipeline, after the planner.
tools: Read, Write, Edit, Grep, Glob, Bash
model: sonnet
---

You are an implementation specialist.

1. Read `.pipeline/spec.md` in full. If it has OPEN QUESTIONS, stop and
   surface them instead of guessing.
2. Implement exactly what the spec describes. Follow the patterns it
   names. Do not add features it didn't ask for.
3. Write a short summary to `.pipeline/changes.md`: which files changed,
   what each change does, and anything the Tester should focus on.

You write code that matches the repo. You do not refactor unrelated
code or "improve" things outside the spec's scope.
```

Sonnet 是这里的正确选择：按照清晰的规格说明进行实施，正是 Sonnet 最擅长处理的成本与质量平衡的工作。

在.pipeline/changes.md 文件中的交接说明，能让测试人员瞄准正确的测试对象，而不是盲目测试。

#### 代理3：测试者（子代理，十四行诗）

测试人员查看变更内容，编写证明该功能有效的测试用例，然后执行这些测试。

创建 .claude/agents/tester.md:

```markdown
---
name: tester
description: Writes and runs tests for changes described in .pipeline/changes.md. Third stage of the feature pipeline.
tools: Read, Write, Edit, Grep, Glob, Bash
model: sonnet
---

You are a test specialist.

1. Read `.pipeline/changes.md` to see what was built and where.
2. Read the changed files and the spec at `.pipeline/spec.md`.
3. Write tests covering: the happy path, the edge cases the spec named,
   and at least one failure case. Match the repo's test framework.
4. Run the tests. If any fail, write the failures to
   `.pipeline/test-results.md` and STOP. Do not fix the code yourself.
5. If all pass, note that in `.pipeline/test-results.md`.

You test behavior, not implementation details. A failing test means
the pipeline pauses for the Reviewer, not that you patch around it.
```

#### Agent 4: 审核员（子代理，Opus）

最后一道关卡。评审者会查看流水线生成的所有内容，并在任何内容到达主分支之前给出评审结论。

创建 .claude/agents/reviewer.md:

```markdown
---
name: reviewer
description: Final review of the full pipeline output. Fourth and last stage before human sign-off.
tools: Read, Grep, Glob, Bash
model: opus
---

You are a senior reviewer. You are read-only. You do not edit code.

1. Read the spec, the changes summary, and the test results from
   `.pipeline/`.
2. Run `git diff` to see the actual changes.
3. Assess: does the code match the spec? Are the tests meaningful or
   superficial? Any security, performance, or correctness issues?
4. Write a verdict to `.pipeline/review.md`:
   - VERDICT: SHIP / NEEDS WORK / BLOCK
   - For NEEDS WORK or BLOCK, list exactly what to fix and where.

Be the last line of defense. If the tests are green but the code is
wrong, say BLOCK. Green tests are not the same as correct behavior.
```

只读工具意味着评审人员无法通过编辑来掩盖问题，只能进行判断。

#### 编排器：一条命令运行全部四个

现在这个组件将四个独立代理整合成一个流水线。一个斜杠命令按顺序调用它们，每个代理接收前一个代理写入的交接文件。

创建 .claude/commands/ship.md:

```text
Run the full feature pipeline for: $ARGUMENTS

Execute these stages in order. Do not skip ahead. After each stage,
confirm the handoff file exists before starting the next.

1. Delegate to the `planner` subagent with the feature request above.
   Wait for `.pipeline/spec.md`.
2. If the spec has OPEN QUESTIONS, stop and show them to me. Otherwise
   delegate to the `coder` subagent. Wait for `.pipeline/changes.md`.
3. Delegate to the `tester` subagent. Wait for `.pipeline/test-results.md`.
   If tests failed, stop and show me the failures.
4. Delegate to the `reviewer` subagent. Show me `.pipeline/review.md`.

Report the final verdict. Do not merge anything. Leave the branch for
my morning review.
```

然后一行代码就启动了整个流程：/ship add rate limiting to the login endpoint.

#### 如何构建“4 人 AI 代理团队”自动交付功能

##### 一、深度总结

这篇内容的核心观点是：

> **真正有效的 AI 开发流程，不是堆很多代理，而是让代理形成“流水线”。**

作者提出一个 4 阶段 AI 代理团队：

```text
规划者 → 编码者 → 测试者 → 评审者
```

每个代理只负责一件事，并通过共享文件完成交接：

| 阶段 | 代理 | 职责 | 输出文件 |
|---|---|---|---|
| 1 | Planner 规划者 | 把模糊需求变成清晰规格 | `.pipeline/spec.md` |
| 2 | Coder 编码者 | 按规格实现代码 | `.pipeline/changes.md` |
| 3 | Tester 测试者 | 写测试、跑测试 | `.pipeline/test-results.md` |
| 4 | Reviewer 评审者 | 最终审查，不改代码 | `.pipeline/review.md` |

核心机制不是“AI 很聪明”，而是：

> **拆分角色 + 限定上下文 + 文件交接 + 顺序编排。**

作者认为，一个全能代理容易把规划、编码、测试、审查混在一起，导致上下文污染、质量下降。而多个专业代理各自处理窄任务，效果更稳定。

最后，通过一个 `/ship xxx` 命令启动完整流程，例如：

```bash
/ship add rate limiting to the login endpoint
```

系统会自动执行：

1. 生成规格；
2. 编写代码；
3. 编写并运行测试；
4. 审查结果；
5. 留给人类最终确认。

作者还顺带推广了 Teamly，称它可以把这种交接和编排托管化，不只适用于代码，也适用于营销、研究、客服等团队型任务。

---

##### 二、深入浅出解读

这套方法本质上是在模仿真实软件团队。

普通用 AI 写代码，常见方式是：

```text
我提需求 → AI 写代码 → 我检查 → 我让它改 → 我再检查
```

问题是：  
**人依然是项目经理、测试员、审查员，AI 只是打字员。**

作者提出的方式是：

```text
我只提需求 → AI 团队自动分工 → 我早上看结果
```

###### 为什么要拆成 4 个代理？

因为软件开发本来就不是一个动作，而是多个动作：

- 需求要先说清楚；
- 代码要按需求实现；
- 测试要验证功能；
- 审查要防止低质量代码混入。

如果让一个 AI 一次完成全部，它容易：

- 自己脑补需求；
- 写完代码后自我确认；
- 测试写得很表面；
- 忽略安全、性能、边界问题。

拆成 4 个角色后，每个代理的任务更窄，判断标准更清楚。

###### 最关键的是“交接文件”

这篇文章最有价值的不是具体代码，而是这个思想：

```text
每个阶段都必须留下可读、可检查、可追踪的交接物。
```

比如：

- 规划者留下规格；
- 编码者留下改动说明；
- 测试者留下测试结果；
- 评审者留下最终意见。

这样后一个代理不是“重新猜一次”，而是基于前一个代理的产出继续推进。

###### 它解决的真正问题

不是“让 AI 更聪明”，而是：

> **让 AI 工作流更可控。**

它降低了几个风险：

- 需求丢失；
- 上下文混乱；
- 代理互相不知道对方做了什么；
- 测试和审查流于形式；
- 人类必须全程盯着。

---

##### 三、这篇内容的核心价值

可以浓缩成一句话：

> **AI 代理团队的关键不是数量，而是流程设计。**

更具体地说，有 4 个启发：

1. **先规划，再编码**  
   不要一上来就让 AI 写代码。

2. **角色越清楚，结果越稳定**  
   规划者不写代码，评审者不改代码。

3. **交接物比聊天记录更重要**  
   文件化的规格、变更、测试、审查，才方便追踪。

4. **自动化不等于无人监管**  
   最后仍然需要人类早上审查，而不是自动合并。

---

##### 四、辩证思考

###### 1. 这套流程很有价值，但不是银弹

它适合：

- 小到中等规模功能；
- 需求相对明确的迭代；
- 有测试体系的项目；
- Claude Code / Cursor / 类似 Agent 工作流。

但不适合：

- 架构级大改；
- 高风险金融、医疗、安全代码；
- 需求高度模糊的探索性任务；
- 测试体系很差的老项目。

AI 可以自动推进，但不能替代工程判断。

---

###### 2. 多代理不一定更好，关键是边界

很多人以为：

```text
代理越多 = 越智能
```

其实可能相反。

如果没有清晰交接，多代理会变成：

```text
多个 AI 各说各话，最后人类收拾残局
```

所以真正重要的是：

```text
清晰职责 + 明确输入 + 明确输出 + 停止条件
```

这比“用了几个代理”更关键。

---

###### 3. 流水线会提高稳定性，也可能制造僵化

优点是规范、可追踪、可复用。

缺点是如果规划阶段错了，后面所有阶段都会沿着错误方向高效执行。

也就是说：

> **流水线不会自动保证方向正确，只会让执行更顺畅。**

所以 Planner 阶段尤其关键，必要时应该先让人确认规格，再进入编码。

---

###### 4. AI 审查不能替代人类责任

Reviewer 很有用，但它仍然是模型判断。

它可能漏掉：

- 业务逻辑漏洞；
- 隐性安全风险；
- 用户体验问题；
- 长期维护成本；
- 与产品目标不一致的实现。

因此最终应是：

```text
AI 给出候选结果，人类做最终责任判断。
```

而不是：

```text
AI 通过了，所以直接上线。
```

---

##### 五、我的结论

这篇内容真正值得学习的不是 Teamly，也不是具体配置文件，而是一个工作流原则：

> **把 AI 从“聊天工具”升级成“流程节点”。**

最小可行实践可以从两步开始：

```text
Planner → Coder
```

稳定后再加：

```text
Tester → Reviewer
```

最终形成：

```text
需求输入
  ↓
规格文件
  ↓
代码实现
  ↓
测试结果
  ↓
审查结论
  ↓
人类确认
```

最精炼地说：

> **不要让 AI 一口气干完所有事。  
> 让它们像团队一样分工、交接、互相约束。**

##### 主旨概括

文章介绍了一套“4 人 AI 代理流水线”：**规划者 → 编码者 → 测试者 → 评审者**，通过自动交接文件和一个统一命令，让 AI 在夜间独立完成一个功能开发流程。核心观点是：**真正提升效率的不是堆很多代理，而是让代理按顺序交接、各司其职。**

---

##### 1. 为什么“流水线”比“一堆代理”更有效

作者认为，很多人虽然用了多个 AI 代理，但仍然是手动调度：今天让一个代理评审，明天让另一个生成测试，彼此不知道上下文，最终人仍然是瓶颈。

更好的方式是建立一个固定流程：

```text
Planner → Coder → Tester → Reviewer
规划者 → 编码者 → 测试者 → 评审者
```

关键机制是使用共享交接文件夹：

```text
.pipeline/
```

每个代理把自己的输出写入文件，下一个代理读取这些文件继续工作。例如：

- 规划者写入：`.pipeline/spec.md`
- 编码者读取 spec，并写入：`.pipeline/changes.md`
- 测试者读取 changes，并写入：`.pipeline/test-results.md`
- 评审者综合所有信息，写入：`.pipeline/review.md`

这样每个代理只处理自己负责的阶段，避免一个代理上下文过长导致质量下降。

---

##### 2. 代理 1：规划者 Planner，负责把需求变成规格

规划者使用更强的模型 **Opus**，因为它决定后续工作的质量上限。

它不写代码，只做规划，主要任务是：

- 阅读代码库相关部分，理解现有模式
- 生成实现规格文档：`.pipeline/spec.md`
- 明确要创建或修改的文件路径
- 写清函数接口、边界情况、应参考的现有代码模式
- 如果需求不明确，在文档顶部标记 `OPEN QUESTION`

文章强调：如果规格模糊，即使编码者很强，也容易产出模糊代码。

---

##### 3. 代理 2：编码者 Coder，按规格实现功能

编码者使用 **Sonnet**，因为它适合在清晰规格下完成实现，性价比高。

编码者的职责是：

- 完整读取 `.pipeline/spec.md`
- 如果发现 `OPEN QUESTIONS`，停止，不自行猜测
- 严格按照规格实现代码
- 不额外添加需求之外的功能
- 不重构无关代码
- 将改动总结写入：`.pipeline/changes.md`

总结内容包括：

- 改了哪些文件
- 每个改动做了什么
- 测试者需要重点关注什么

---

##### 4. 代理 3：测试者 Tester，编写并运行测试

测试者同样使用 **Sonnet**。

它会读取：

- `.pipeline/changes.md`
- `.pipeline/spec.md`
- 实际修改过的代码文件

然后编写测试，覆盖：

- 正常路径，即 happy path
- 规格中提到的边界情况
- 至少一个失败场景

测试者还会运行测试，并将结果写入：

```text
.pipeline/test-results.md
```

如果测试失败，它只记录失败信息并停止，不自行修复代码。作者强调：测试者负责验证行为，不应该绕过问题去改代码。

---

##### 5. 代理 4：评审者 Reviewer，作为最后关卡

评审者使用 **Opus**，并且是只读角色，不能修改代码。

它会读取：

- `.pipeline/spec.md`
- `.pipeline/changes.md`
- `.pipeline/test-results.md`
- `git diff`

评审重点包括：

- 代码是否符合规格
- 测试是否真正有效，而不是表面覆盖
- 是否存在安全、性能、正确性问题

最终输出到：

```text
.pipeline/review.md
```

评审结论有三种：

- `SHIP`：可以交付
- `NEEDS WORK`：需要修改
- `BLOCK`：阻塞，不能合并

作者特别指出：**测试通过不代表行为一定正确**，如果代码逻辑有问题，即使绿灯也应判定为 `BLOCK`。

---

##### 6. 编排器：用一条命令串起四个代理

作者用一个 Claude Code 斜杠命令来运行整条流水线：

```text
/ship add rate limiting to the login endpoint
```

示例需求是：给登录接口添加限流。

这个命令会依次执行：

1. 调用 Planner，生成 `.pipeline/spec.md`
2. 如果有 `OPEN QUESTIONS`，停止并展示问题
3. 调用 Coder，生成 `.pipeline/changes.md`
4. 调用 Tester，生成 `.pipeline/test-results.md`
5. 如果测试失败，停止并展示失败
6. 调用 Reviewer，生成 `.pipeline/review.md`
7. 展示最终结论，但不自动合并代码

这样用户可以晚上启动任务，第二天早上查看结果和评审意见。

---

##### 7. 作者推荐的托管运行方式：Teamly

文章后半部分介绍作者使用的工具 **Teamly**，它是一个面向 AI 代理团队的云托管服务。

作者认为 Teamly 适合这个流程，因为它已经内置了类似的交接机制：

- 自动协调多个代理
- 在代理之间传递上下文
- 维护共享简报
- 不需要用户自己搭建 `.pipeline` 文件和编排器

它不仅能用于代码开发，也可以用于：

- 营销团队
- 研究团队
- 客服支持团队

也就是说，同样的“规划 → 执行 → 检查”交接逻辑，可以应用到不同类型的工作中。

---

##### 8. Teamly 的团队定制功能

文章提到 Teamly 新推出了“我的团队”功能，可以通过 **3 个问题**组建团队。

用户还可以控制：

- 语音规则

- 团队规模：2–4 个代理

Teamly 会解释为什么选择这些专家，而不是直接给模板化团队。用户也可以一键替换代理或编辑简报。

---

##### 9. 试用与成本信息

作者提到 Teamly 提供免费试用：

- 可免费试用 **3 天**

---

##### 10. 结论：关键不是代理数量，而是交接机制

文章最后总结：一堆代理和真正流水线的区别在于 **交接**。

有效配置是：

```text
四个专家代理 + 共享文件夹 + 一个顺序编排命令
```

建议从简单版本开始：

1. 先搭建 Planner 和 Coder
2. 跑通两阶段流程
3. 稳定后加入 Tester
4. 最后加入 Reviewer

最终目标是：睡前启动一个功能开发任务，早上喝咖啡时查看代码、测试结果和评审结论。

#### 四代理流水线：靠自动交接完成从需求到评审

文章提出，与其让多个 AI 代理零散工作，不如建立“规划→编码→测试→评审”的顺序流水线。核心不在代理数量，而在标准化交接：每个代理只负责一个环节，通过共享文件传递结果，由编排器自动推进；最终仍由人决定是否合并代码。

##### 分工缩小上下文，避免单个代理质量衰减

一个代理同时处理规划、代码、测试和评审，容易因上下文过载而遗漏问题。作者建议配置四个专职代理：

- **规划者（Opus）**：阅读代码库，把模糊需求写成 `.pipeline/spec.md`，明确文件路径、接口、边界情况和参考模式；存在歧义时标记开放问题，不自行补需求。
- **编码者（Sonnet）**：严格按规格实现，不做无关重构，并将改动摘要写入 `changes.md`。
- **测试者（Sonnet）**：覆盖正常路径、边界和失败场景；失败时记录到 `test-results.md`，但不自行修代码。
- **评审者（Opus）**：只读检查规格、代码差异和测试质量，评估正确性、安全与性能，给出 `SHIP / NEEDS WORK / BLOCK` 结论。

规划和终审使用能力更强的模型，实施与测试则用 Sonnet 平衡成本和质量。

##### 编排器负责顺序执行，也负责及时停下

一个 `/ship` 命令依次调用四个代理，并检查每阶段的交接文件。若规格存在开放问题或测试失败，流程立即暂停；评审通过后也不自动合并，只保留分支供人工晨间确认。这种设计把“绿测”与“代码正确”区分开，并为自动化设置明确边界。

##### 真正可复用的是交接机制

作者建议先搭建规划者与编码者，稳定后再加入测试和评审。文末推广 Teamly：其托管服务用协调器自动分配任务、共享上下文，并将同类流程扩展到营销、研究和客服。其商业主张是降低自建基础设施与编排成本，但“一夜交付功能”仍取决于需求清晰度、代码库复杂度和人工终审质量。
