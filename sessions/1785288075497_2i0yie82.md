The labs in this tutorial run on an attached playground with four hosts wired into three networks:

- `local` - your workstation. Sits on both the **home** `192.168.0.0/24` and the **public** `203.0.113.0/24` networks.
- `remote` - a public-facing bastion / gateway on the **public** `203.0.113.0/24` network, also connected to a private **vpc** `172.16.0.0/24`.
- `private` - an internal-only service (a database, an OpenSearch cluster) on the **vpc** `172.16.0.0/24`. Not reachable from the **public** network.

You can `ssh` from `local` to `remote` by hostname or IP address - the `local` host key is already trusted on the `remote` machine:

```sh
ssh remote

ssh 203.0.113.30
```

#### Local Port Forwarding

Starting from the one that I use the most. Oftentimes, there might be a service listening on `localhost` or a private interface of a remote machine that I can only SSH to via its public IP. And I desperately need to access this port from my local machine. A few typical examples:

- Accessing a private remote database (MySQL, Postgres, Redis, etc) from your laptop using your favorite UI tool.
- Using your browser to access a web application exposed only to a private network.
- Accessing a container's port from your laptop without publishing it on the server's public interface.

All of the above use cases can be solved with a single `ssh` command:

```sh
ssh -L [local_addr:]local_port:remote_addr:remote_port [user@]sshd_addr
```

The `-L` flag indicates we're starting a *local port forwarding*. What it actually means is:

- On your local machine, the SSH client will start listening on `local_port` (likely, on `localhost`, but *it depends* - [check the `GatewayPorts` setting](https://linux.die.net/man/5/sshd_config#GatewayPorts)).
- Any traffic to this port will be forwarded to `remote_addr:remote_port`, reached from the remote machine you SSH-ed to.

Because the service is bound to the loopback interface, it cannot be reached over the network. From the local host, try to hit the `remote` host's public address:


But from the inside of the remote host, the very same service works just fine:

```sh

```

```
Hello from the remote host (localhost-only service).
```

**And here is the trick:** back on the local host, bind the remote's `localhost:80` to the local's `localhost:8080` using local port forwarding:

```sh
ssh -f -N -L 8080:localhost:80 203.0.113.30
```

#### Local Port Forwarding with a Bastion Host

It might not be obvious at first, but the `ssh -L` command allows forwarding a local port to a remote port on *any machine*, not only on the SSH server itself. Notice how the `remote_addr` and `sshd_addr` may or may not have the same value:

```sh
ssh -L [local_addr:]local_port:remote_addr:remote_port [user@]sshd_addr
```

A remote SSH server used to access private destinations is usually called a [*bastion or jump host*](https://en.wikipedia.org/wiki/Bastion_host). This is how I visualize this scenario in my head:

SSH Tunnels visualized - local port forwarding with a bastion host.

I often use the above trick to call endpoints that are accessible from the *bastion host* but not from my laptop (e.g., using an EC2 instance with private and public interfaces to connect to an OpenSearch cluster or any other service deployed fully within a VPC).

The `local` workstation has no route into the VPC, so it cannot talk to the `private` host directly. From the local host:


#### Local Port Forwarding to a Loopback Port via a Jump Host

The bastion trick from Lab 2 is handy, and its command is (relatively) easy to remember, but it has a significant limitation. In `ssh -L local_port:remote_host:remote_port bastion_host`, the SSH session terminates **on the bastion**, and the bastion opens the second hop to `remote_host:remote_port`. That works only as long as the private service is bound to the remote's *external* network interface, (i.e., the bastion can reach it *from the outside*).

But services can also be bound to `127.0.0.1` - a database admin console, a metrics or profiling endpoint, an application's debug port, etc. A loopback-bound port answers only on the host's *own* loopback, so neither the bastion nor anything else on the network can reach it. The forward has to be resolved **on the remote host itself**.

The way to do that is to use the `remote_host` as the target address in the `ssh -L` command, but when the remote is only reachable through a bastion, you will need to use an extra flag - `-J bastion_host`.

Instead of terminating the SSH session on the bastion,[`-J` (ProxyJump)](https://man.openbsd.org/ssh#J) jumps *through* the bastion and terminates the session **on the remote host**. The `-L` destination is then resolved from the remote's point of view, so `localhost` means the remote's own loopback:

```sh
ssh -J [user@]jumphost -L [local_addr:]local_port:localhost:remote_port [user@]remote_host
```

The bastion still only relays the bytes for the jump - your real SSH session is established between the local and the remote hosts, making it possible to access the remote's loopback.

SSH Tunnels visualized - local port forwarding to a loopback port via a jump host.

This is how I reach an local-only debug or admin port that a service binds to `127.0.0.1`. Even though the port is invisible to the whole network, a single `ssh -J ... -L` from my laptop makes it show up on a local port of my machine as if the service were running right next to me.

Lab 3: Local Port Forwarding to a Loopback Port via a Jump Host 👨🔬

This lab reuses the bastion topology from Lab 2, but this time the `private` host also runs a second web server bound to its **loopback** at `127.0.0.1:9000` - think of an internal debug or metrics port that must never be exposed on the network.

The Lab 2 approach forwards to the private host's *external* network address. The bastion can open that hop, but there is nothing listening on `172.16.0.40:9000` - the debug port lives on the loopback, not on the network interface. So a `-L 8082:172.16.0.40:9000` forward through the bastion would only get a connection refused.

Instead, we need to make the SSH session "jump through" the bastion (using `-J bastion`) and terminate **on the `private` host**, forwarding to `localhost:9000`, which the `private` host then resolves to its own loopback. From the local host:

```sh
ssh -f -N -J 203.0.113.30 -L 8082:localhost:9000 172.16.0.40

#            jump host            target_port    target_host
```

#### Remote Port Forwarding

Another popular (but rather inverse) scenario is when you want to momentarily expose a local service to the outside world. Of course, for that, you'll need a *public-facing ingress gateway server*. And the good news is that any public-facing server with an SSH daemon on it can be used as such a gateway:

```sh
ssh -R [remote_addr:]remote_port:local_addr:local_port [user@]gateway_addr
```

The above command looks no more complicated than its `ssh -L` counterpart. But there is a pitfall...

**By default, the above SSH tunnel will allow using only the gateway's localhost as the remote address.**In other words, your local port will become accessible only from inside the gateway server itself, which is most likely not what you actually need. For instance, I typically want to use the gateway's public address as the remote address to expose my local services to the public Internet. For that, the SSH server needs to be configured with the [`GatewayPorts yes`](https://linux.die.net/man/5/sshd_config#GatewayPorts) setting.

Here is what remote port forwarding can be used for:

- Exposing a dev service from your laptop to the public Internet for a quick demo.
- Exposing your homelab to the public Internet (for arbitrary purposes).
- Tunneling your local browser's debugging port to a remote and/or sandboxed coding agent.

Here is how the remote port forwarding can be visualized:

Use `ssh -f -N -R` to run the port-forwarding session in the background.

#### Remote Port Forwarding to a Home or Private Network

Similar to local port forwarding, remote port forwarding has its own *bastion or jump host* mode. But this time, the machine with the SSH client (e.g., your dev laptop) plays the role of the jump host. In particular, it allows exposing ports of a home (or private) network reachable from your laptop to the outside world through a remote SSH server acting as an ingress gateway:

```sh
ssh -R [remote_addr:]remote_port:local_addr:local_port [user@]gateway_addr
```

Looks almost identical to the simple remote SSH tunnel, but the `local_addr:local_port` pair becomes the address of a device in the home network. Here is how it can be depicted on a diagram:

SSH Tunnels visualized - remote port forwarding to home network.

I typically use my laptop as a thin client and the actual development happens on a remote server. Sometimes, such a remote server can reside in my home network and have no or restricted Internet access (for extra isolation). This is when I may want to rely on remote port forwarding to expose a service from a home server to the public Internet, using my laptop that can access both the internal dev server and the remote SSH server (ingress gateway) as a jump host.

#### Dynamic Local Port Forwarding

This forwarding mode is less transparent for the clients, but it is also significantly more flexible than regular local port forwarding. Instead of wiring a local port to a single remote destination (like `ssh -L` does),**dynamic (local) port forwarding** turns the SSH client into a local [SOCKS proxy](https://en.wikipedia.org/wiki/SOCKS). Any application that can speak SOCKS can then send traffic through it, choosing the actual destination host and port *per connection* - they will be sent over to the SSH server, which will resolve the destination and establish the connection:

```sh
ssh -D [local_addr:]local_port [user@]sshd_addr
```

When the `-D` flag is used, the SSH client on your machine starts a SOCKS proxy listening on `local_port` (on `localhost` by default). Each connection made through the proxy is forwarded to whatever address the SOCKS client asks for, reached from the `sshd_addr` machine.

In other words, it's like `ssh -L`, but you don't have to specify a single `remote_addr:remote_port` upfront, because the SOCKS protocol allows specifying the destination at the beginning of each connection (via a few extra bytes sent right before the payload). One (local) proxied port gives you access to *every* host and port reachable from the (remote) SSH server.

SSH Tunnels visualized - dynamic local port forwarding (SOCKS proxy).

Here is what dynamic port forwarding can be used for:

- Calling APIs in a private network through a bastion, without a separate tunnel per service.
- Browsing internal web apps in a remote network via a single jump host.
- Reaching a fleet of VPC endpoints from your laptop through one EC2 instance.

Tip

Use `ssh -f -N -D` to run the SOCKS proxy in the background.

With `ssh -L`, reaching both private hosts would have meant two separate tunnels (one per `remote_addr:remote_port`). A single `ssh -D` proxy covers the whole network behind the bastion.

#### Dynamic Remote Port Forwarding

Just like `ssh -L` has a dynamic sibling in `ssh -D`, the `ssh -R` command has its own dynamic mode. If you drop the fixed destination from `-R` and pass only a port, OpenSSH turns the **SSH server** itself into a SOCKS proxy. It's the exact mirror of `-D`: this time the proxy lives on the gateway, and every connection made through it is tunneled back to the `ssh` client and resolved from *its* point of view:

```sh
ssh -R [bind_address:]port [user@]gateway_addr
```

The `-R` flag **with no destination means**:

- On the remote gateway, the SSH server starts a SOCKS proxy listening on `port` (on the gateway's `localhost` by default, or on all interfaces with `GatewayPorts yes`).
- Each connection made through the proxy is tunneled back to the `ssh` client and forwarded to whatever address the SOCKS client asks for, reached from the client's side.

It's like a regular `ssh -R`, but you don't have to choose a single `local_addr:local_port` upfront. One proxy on the gateway exposes *every* host and port reachable from the `ssh` client - for example, an entire home network.

SSH Tunnels visualized - dynamic remote port forwarding (SOCKS proxy).

Note

Remote dynamic forwarding requires OpenSSH 7.6 or newer on the client. As with a regular `ssh -R`, binding the proxy to a non-loopback address on the gateway needs `GatewayPorts yes` in its `sshd_config`.

Tip

Use `ssh -f -N -R` to run the SOCKS proxy in the background.

#### Summarizing

Here is a quick recap and a couple of mnemonics to help you memorize the SSH tunneling commands:

- **Local port forwarding** (`ssh -L`) makes a remote service available on a local port.
- **Remote port forwarding** (`ssh -R`) makes a local service available on a remote port.
- **Dynamic local port forwarding** (`ssh -D`) turns the local `ssh` client into a SOCKS proxy.
- **Dynamic remote port forwarding** (`ssh -R` with no destination) turns the `sshd` server into a SOCKS proxy.
- Local port forwarding (`ssh -L`) implies it's the `ssh` client that starts listening on a new port.
- Remote port forwarding (`ssh -R`) implies it's the `sshd` server that starts listening on an extra port.
- The word **local** can mean either the **SSH client machine** or an internal host accessible from it.
- The word **remote** can mean either the **SSH server machine (sshd)** or any host accessible from it.
- The mnemonics are *ssh **-L** **l** ocal:remote* and *ssh **-R** **r** emote:local* and it's always the left-hand side that opens a new port.

SSH 隧道可以把一个网络位置不可达的服务，通过 SSH 连接“映射”到另一台机器上。

常见用途包括：

- 从本地访问远程 VPC 内的数据库或 Web 服务
- 在本地浏览器访问远程开发机的服务
- 将家庭网络中的服务临时暴露到公网
- 通过堡垒机访问内网主机
- 使用 SOCKS 代理访问整个远程网络

---

##### 一、SSH 隧道的核心规则

###### 1. `-L`：远程服务映射到本地

```bash
ssh -L [本地地址:]本地端口:远程地址:远程端口 user@SSH服务器
```

记忆方式：

```text
-L local:remote
```

含义：

1. SSH 客户端在本地监听一个端口；
2. 本地访问该端口的流量，通过 SSH 发送到远端；
3. 远端 SSH 服务器负责连接目标地址。

示例：

```bash
ssh -f -N -L 8080:localhost:80 203.0.113.30
```

效果：

```text
访问本地 localhost:8080
    ↓
通过 SSH
    ↓
访问远程主机的 localhost:80
```

适合：

- 访问远程数据库
- 访问远程内网 Web 服务
- 访问远程机器上未对外暴露的容器端口
- 访问仅绑定在远程 `127.0.0.1` 的服务

---

##### 二、通过堡垒机访问内网服务

如果本地无法访问内网主机，但 SSH 堡垒机可以访问，就可以让堡垒机代为连接：

```bash
ssh -L 8081:172.16.0.40:80 203.0.113.30
```

效果：

```text
本地 localhost:8081
    ↓
SSH 堡垒机 203.0.113.30
    ↓
内网服务 172.16.0.40:80
```

这里需要注意：

- SSH 登录的机器是堡垒机；
- `172.16.0.40:80` 是堡垒机视角下可访问的目标；
- 本地不需要拥有到 VPC 的直接路由。

###### 特殊情况：目标服务只监听 `127.0.0.1`

如果内网服务只绑定在目标主机的回环地址，例如：

```text
127.0.0.1:9000
```

那么堡垒机无法直接访问它。这时不能简单使用：

```bash
ssh -L 8082:172.16.0.40:9000 bastion
```

应使用 `-J`（ProxyJump），让 SSH 会话最终建立在目标主机上：

```bash
ssh -J 203.0.113.30 \
  -L 8082:localhost:9000 \
  172.16.0.40
```

区别在于：

- 普通 `-L`：目标地址从 SSH 服务器的视角解析；
- `-J`：堡垒机只负责跳转，真正的 SSH 会话终止在目标主机；
- 因此目标主机上的 `localhost` 才能正确指向它自己的回环接口。

---

##### 三、`-R`：将本地服务映射到远程

```bash
ssh -R [远程地址:]远程端口:本地地址:本地端口 user@网关服务器
```

记忆方式：

```text
-R remote:local
```

含义：

1. SSH 服务器在远程监听一个端口；
2. 远程访问该端口的流量，通过 SSH 返回本地；
3. SSH 客户端负责连接本地目标服务。

示例：

```bash
ssh -f -N -R 0.0.0.0:8080:localhost:80 203.0.113.30
```

效果：

```text
远程网关 0.0.0.0:8080
    ↓
通过 SSH
    ↓
本地 localhost:80
```

适合：

- 将本地开发服务临时提供给他人访问
- 将家庭网络服务暴露到公网
- 将本地浏览器调试端口提供给远程开发环境
- 让没有公网入口的内网服务通过公网网关对外提供访问

---

##### 四、远程端口转发的关键配置

`-R` 默认通常只会让远程 SSH 服务器自己的 `localhost` 能访问该端口，外部机器无法直接访问。

如果希望远程网关的公网地址也能访问，需要在远程 `sshd_config` 中配置：

```text
GatewayPorts yes
```

修改后重启 SSH 服务。

同时还需要检查：

- 云安全组
- 防火墙规则
- 网关监听地址
- 端口是否暴露给不可信用户

生产环境中应尽量限制监听地址和访问来源，避免意外开放内网服务。

---

##### 五、远程转发到家庭或私有网络

本地电脑可以同时访问：

- 家庭内网设备
- 公网 SSH 网关

此时本地电脑可以充当“中间跳板”，把家庭网络服务映射到公网网关：

```bash
ssh -f -N \
  -R 0.0.0.0:8081:192.168.0.10:80 \
  203.0.113.30
```

效果：

```text
公网网关:8081
    ↓
SSH 隧道
    ↓
本地可访问的家庭设备 192.168.0.10:80
```

关键点：

- `192.168.0.10` 是从 SSH 客户端，也就是本地电脑的视角解析；
- 远程网关本身不需要能够访问家庭网络；
- 本地电脑负责连接家庭设备并转发数据。

---

##### 六、`-D`：动态本地 SOCKS 代理

```bash
ssh -D [本地地址:]本地端口 user@SSH服务器
```

示例：

```bash
ssh -f -N -D 1080 203.0.113.30
```

效果：

```text
本地 SOCKS5 代理 localhost:1080
    ↓
通过 SSH
    ↓
由远程服务器访问目标地址
```

与 `-L` 的区别：

- `-L`：提前指定一个固定的目标地址和端口；
- `-D`：只建立一个代理，客户端每次连接时自行指定目标；
- 一个 `-D` 代理可以访问远程服务器能够访问的多个主机和端口。

例如：

```bash
curl --socks5-hostname localhost:1080 172.16.0.40:80
```

适合：

- 访问整个 VPC 网络
- 通过堡垒机浏览多个内网 Web 服务
- 访问多个内网 API
- 避免为每个目标服务单独建立 `-L` 隧道

注意：使用方必须支持 SOCKS 代理，例如 `curl` 需要使用 `--socks5-hostname`。

---

##### 七、`-R` 的动态模式：远程 SOCKS 代理

如果 `-R` 不指定固定的本地目标，只指定远程端口：

```bash
ssh -f -N -R 0.0.0.0:1080 203.0.113.30
```

那么远程网关会启动一个 SOCKS 代理。

效果：

```text
远程网关:1080
    ↓
通过 SSH
    ↓
由本地电脑访问目标地址
```

这相当于 `-D` 的反向版本：

- `-D`：代理在本地，目标由远程解析；
- `-R` 动态模式：代理在远程，目标由本地解析。

适合：

- 让远程环境访问家庭网络
- 让远程服务器访问本地电脑可达的多个服务
- 一次性暴露整个家庭网段，而不是单个端口

要求：

- 客户端 OpenSSH 版本通常需要 7.6 或更高；
- 远程绑定非回环地址时，同样需要 `GatewayPorts yes`。

---

##### 八、常用参数

###### `-N`

只建立隧道，不执行远程命令，也不打开 Shell：

```bash
ssh -N ...
```

###### `-f`

认证成功后，将 SSH 进程放到后台运行：

```bash
ssh -f ...
```

端口转发常用组合：

```bash
ssh -f -N -L ...
ssh -f -N -R ...
ssh -f -N -D ...
```

---

##### 九、最终记忆口诀

###### 端口方向

```text
-L：远程服务 → 本地端口
-R：本地服务 → 远程端口
-D：本地 SOCKS 代理
-R 无目标地址：远程 SOCKS 代理
```

###### 命令记忆

```text
ssh -L local_port:remote_host:remote_port ssh_host
ssh -R remote_port:local_host:local_port ssh_host
```

最重要的规则是：

> **哪一侧写在命令左边，哪一侧就会新开监听端口。**

- `-L` 左边是本地，所以本地监听；
- `-R` 左边是远程，所以远程监听。

此外，要区分：

- `SSH 服务器`：你实际连接的那台机器；
- `目标主机`：最终想访问的机器；
- `目标地址从谁的视角解析`：决定隧道是否能访问成功。

## 结构化（1）

### 2026-07-30 09:21:27

SSH 隧道利用标准 `ssh` 命令，在本机、远程网关与私有网络之间安全转发端口，可用于访问 VPC 内部服务、远程主机的本地端口，或将家庭网络服务临时暴露到外部。核心记忆法是：`-L` 把**远程服务带到本地**，`-R` 把**本地服务带到远程**，`-D` 则提供可访问多个目标的 SOCKS 代理。

##### 1. 实验网络结构

文章通过 4 台主机和 3 个网络演示 SSH 隧道：

- **internal**：家庭网络设备，位于 `192.168.0.0/24`，公网无法访问。
- **local**：本地工作站，同时连接：
  - 家庭网络 `192.168.0.0/24`
  - 公共网络 `203.0.113.0/24`
- **remote**：公网堡垒机/网关：
  - 公网地址：`203.0.113.30`
  - 同时连接私有 VPC：`172.16.0.0/24`
- **private**：VPC 内部服务，如数据库、OpenSearch，公网无法直接访问，例如 `172.16.0.40`。

本地可以直接 SSH 到远程网关：

```bash
ssh 203.0.113.30
```

后台运行隧道时常用：

```bash
ssh -f -N ...
```

其中，`-f` 表示转入后台，`-N` 表示不执行远程命令，只建立转发。

---

##### 2. 本地端口转发：`ssh -L`

###### 核心作用

把**远程可访问的服务**映射到**本机端口**：

```bash
ssh -L [本地地址:]本地端口:远程地址:远程端口 [用户@]SSH服务器
```

工作方式：

1. SSH 客户端在本机监听 `本地端口`。
2. 发往该端口的流量经 SSH 隧道传到 SSH 服务器。
3. SSH 服务器再连接 `远程地址:远程端口`。

典型用途：

- 从笔记本访问远程私有 MySQL、Postgres、Redis。
- 在本地浏览器打开仅限远程私网访问的网站。
- 访问服务器上的容器端口，而不把该端口公开到公网。

###### 案例 1：访问远程主机的 localhost 服务

远程主机有一个仅监听 `127.0.0.1:80` 的 Web 服务，因此无法通过公网地址 `203.0.113.30:80` 访问。

建立转发：

```bash
ssh -f -N -L 8080:localhost:80 203.0.113.30
```

之后，本地访问：

```bash
curl localhost:8080
```

即可得到：

```text
Hello from the remote host (localhost-only service).
```

更明确的写法是：

```bash
ssh -f -N -L localhost:8080:localhost:80 203.0.113.30
```

即：**本机 `localhost:8080` → 远程主机视角下的 `localhost:80`**。

---

##### 3. 通过堡垒机访问 VPC 内部服务

`-L` 的转发目标不一定是 SSH 服务器自身，也可以是 SSH 服务器能够访问的其他主机：

```bash
ssh -L 本地端口:目标主机:目标端口 堡垒机
```

此时，堡垒机负责建立到目标服务的“第二跳”。

###### 案例 2：通过公网堡垒机访问私有服务

本地无法直接访问 VPC 内的：

```text
172.16.0.40:80
```

但公网堡垒机 `203.0.113.30` 可以访问它，因此执行：

```bash
ssh -f -N -L 8081:172.16.0.40:80 203.0.113.30
```

然后在本地访问：

```bash
curl localhost:8081
```

结果：

```text
Hello from the private VPC host (172.16.0.40).
```

这里需要区分：

- SSH 服务器：`203.0.113.30`
- 实际转发目标：`172.16.0.40:80`

这类方式适合通过公网 EC2 堡垒机访问 VPC 内的 OpenSearch、数据库等服务。

---

##### 4. 通过跳板机访问目标主机的 localhost：`-J`

上一种堡垒机方案有一个限制：堡垒机必须能通过网络接口访问目标端口。如果目标服务仅监听目标主机的 `127.0.0.1`，堡垒机就无法直接连接。

例如，私有主机 `172.16.0.40` 的调试服务仅监听：

```text
127.0.0.1:9000
```

此时需要使用 `-J`（ProxyJump），让 SSH 会话经过堡垒机，但最终终止在私有主机：

```bash
ssh -J [用户@]跳板机 \
  -L [本地地址:]本地端口:localhost:远程端口 \
  [用户@]目标主机
```

###### 案例 3：访问私有主机的回环端口

```bash
ssh -f -N \
  -J 203.0.113.30 \
  -L 8082:localhost:9000 \
  172.16.0.40
```

本地访问：

```bash
curl localhost:8082
```

结果：

```text
Hello from the private VPC host's loopback-only debug port (127.0.0.1:9000).
```

关键区别：

- 普通堡垒机转发：SSH 会话终止在堡垒机，由堡垒机访问目标地址。
- `-J` 跳转：堡垒机只转发 SSH 数据，真正的 SSH 会话终止在目标主机。
- 因此命令里的 `localhost:9000` 指的是**私有目标主机自己的回环接口**。

---

##### 5. 远程端口转发：`ssh -R`

###### 核心作用

把**本地或本地可访问的服务**映射到**远程网关端口**：

```bash
ssh -R [远程地址:]远程端口:本地地址:本地端口 [用户@]远程网关
```

工作方式：

1. SSH 服务端在远程网关监听 `远程端口`。
2. 访问该端口的流量经隧道回到 SSH 客户端。
3. SSH 客户端再连接 `本地地址:本地端口`。

典型用途：

- 临时把笔记本上的开发服务发布到公网。
- 把家庭实验室服务暴露到外部。
- 把浏览器调试端口提供给远程或沙箱中的编码代理。

###### `GatewayPorts` 配置

默认情况下，远程转发端口通常只绑定到网关的 `localhost`，只能从网关内部访问。

若要监听公网或其他网络接口，SSH 服务端的 `sshd_config` 需要允许：

```text
GatewayPorts yes
```

然后可显式绑定：

```text
0.0.0.0:端口
```

这会使服务对网关可达网络开放，使用时应同时考虑防火墙和访问控制。

###### 案例 4：把本机 localhost 服务发布到远程网关

本地服务仅监听：

```text
127.0.0.1:80
```

建立远程转发：

```bash
ssh -f -N \
  -R 0.0.0.0:8080:localhost:80 \
  203.0.113.30
```

之后，其他能够访问远程网关的主机可以请求：

```bash
curl 172.16.0.30:8080
```

得到：

```text
Hello from your local workstation (localhost-only service).
```

即：**远程网关 `:8080` → 本地工作站 `localhost:80`**。

---

##### 6. 将家庭或私有网络服务暴露到远程

远程转发的目标不一定是 SSH 客户端本机，也可以是客户端能够访问的其他设备：

```bash
ssh -R 远程端口:家庭网络主机:服务端口 远程网关
```

在这种场景中，本地工作站同时连接家庭网络和公网，相当于“反向跳板机”。

###### 案例 5：发布家庭网络中的内部服务

内部设备的服务地址为：

```text
192.168.0.10:80
```

远程网关无法直接访问家庭网络，但本地工作站可以。由本地工作站建立隧道：

```bash
ssh -f -N \
  -R 0.0.0.0:8081:192.168.0.10:80 \
  203.0.113.30
```

之后，通过远程网关访问：

```bash
curl 172.16.0.30:8081
```

结果：

```text
Hello from the internal home-network host (192.168.0.10).
```

这里的 `192.168.0.10` 是从 **SSH 客户端，即本地工作站的网络视角**解析和连接的。

---

##### 7. 动态本地端口转发：`ssh -D`

###### 核心作用

`-L` 每条隧道只能预先绑定一个固定目标，而 `-D` 会在本地创建一个 SOCKS 代理：

```bash
ssh -D [本地地址:]本地端口 [用户@]SSH服务器
```

特点：

- SOCKS 代理默认监听本机。
- 客户端可为每次连接指定不同的目标主机和端口。
- 目标地址由远程 SSH 服务器访问。
- 一个代理即可访问 SSH 服务器能连接的所有主机，无需为每个服务单独建隧道。

典型用途：

- 经堡垒机调用多个私网 API。
- 浏览多个内部 Web 应用。
- 通过一台 EC2 访问整个 VPC 中的多个端点。

###### 案例 6：用一个 SOCKS 代理访问多个 VPC 主机

在本地启动代理：

```bash
ssh -f -N -D 1080 203.0.113.30
```

使用支持 SOCKS 的客户端访问私有主机：

```bash
curl --socks5-hostname localhost:1080 172.16.0.40:80
```

得到：

```text
Hello from the private VPC host (172.16.0.40).
```

同一个代理还能访问另一台私有主机：

```bash
curl --socks5-hostname localhost:1080 172.16.0.50:80
```

相比之下，使用 `-L` 访问这两台主机通常需要建立两条独立隧道；`-D` 一条代理即可覆盖堡垒机背后的整个网络。

需要注意：使用方必须支持 SOCKS，例如 `curl` 要加：

```text
--socks5-hostname
```

---

##### 8. 动态远程端口转发：`ssh -R` 不指定目标

如果 `-R` 后只提供监听端口、不提供固定目标，OpenSSH 会在远程网关上建立 SOCKS 代理：

```bash
ssh -R [绑定地址:]端口 [用户@]远程网关
```

它是 `-D` 的镜像：

- SOCKS 代理运行在远程网关。
- 代理流量经 SSH 隧道回到本地客户端。
- 目标地址从本地客户端的网络视角连接。
- 一个代理可以访问本地客户端能够访问的所有主机和端口。

要求：

- 客户端需要 **OpenSSH 7.6 或更高版本**。
- 若要让代理绑定到远程网关的非回环接口，仍需在 `sshd_config` 中设置：

```text
GatewayPorts yes
```

###### 案例 7：通过远程 SOCKS 代理访问整个家庭网络

本地工作站执行：

```bash
ssh -f -N -R 0.0.0.0:1080 203.0.113.30
```

远程侧的主机可通过该代理访问家庭网络设备：

```bash
curl --socks5-hostname \
  172.16.0.30:1080 \
  192.168.0.10:80
```

还可以访问本地工作站自己的回环服务：

```bash
curl --socks5-hostname \
  172.16.0.30:1080 \
  127.0.0.1:80
```

因此，一条动态远程隧道即可向远程侧提供本地工作站所能访问的整个网络，而不必为每个家庭设备分别配置 `-R`。

---

##### 9. 四种模式对照

| 模式 | 命令 | 监听端口位于 | 主要作用 |
|---|---|---|---|
| 本地端口转发 | `ssh -L` | SSH 客户端/本机 | 把远程服务带到本地 |
| 远程端口转发 | `ssh -R` | SSH 服务端/远程网关 | 把本地服务带到远程 |
| 动态本地转发 | `ssh -D` | 本机 SOCKS 代理 | 访问远程侧可达的多个目标 |
| 动态远程转发 | `ssh -R`，不指定目标 | 远程 SOCKS 代理 | 访问本地侧可达的多个目标 |

##### 10. 记忆方法

- `-L`：**Local listens**，由本地 SSH 客户端开启新端口。
- `-R`：**Remote listens**，由远程 SSH 服务端开启新端口。
- `ssh -L local:remote`：本地端口连接远程目标。
- `ssh -R remote:local`：远程端口连接本地目标。
- 始终是参数的**左侧地址和端口负责监听**。
- “本地”既可能指 SSH 客户端本机，也可能指客户端能访问的内网设备。
- “远程”既可能指 SSH 服务器本身，也可能指服务器能访问的私有网络主机。

## 口播总结（2）

### 2026-08-03 00:28:45

#### SSH 隧道实用指南

SSH 隧道的核心作用，是借助一条 SSH 连接，把原本无法直接访问的网络服务安全地转发出来。听完这份总结，你可以分清本地转发、远程转发和动态转发，理解跳板机的作用，并记住常用参数的判断方法。

#### 先理解基本场景

首先，SSH 虽然是一项历史很久的技术，但依然非常实用。只用系统自带工具，往往一条命令，就能访问云内网服务、打开远程开发机上的本地端口，或者把家庭网络里的服务临时暴露到外部。

原文用四台主机来说明这些场景。

第一台叫“本地主机”，也就是你的工作电脑。它既能访问家庭网络，也能访问公网。

第二台叫“远程主机”，通常是一台有公网地址的服务器。它运行着 SSH 服务端，也就是 sshd。它还可能同时连接某个私有云网络。

第三台是私有云里的内部主机。这里的私有云网络，也就是 VPC，可以简单理解为云上的内部局域网，公网无法直接访问。

第四台是家庭或其他私有网络里的内部设备，比如开发服务器、存储设备或者打印机。它同样不能被公网直接访问。

接下来所有 SSH 隧道，本质上都在回答两个问题：哪一端新开监听端口，以及流量最终从哪台机器去访问目标服务。

#### 本地端口转发：把远程服务带到本机

首先看最常用的本地端口转发，参数是大写的 `L`。

核心结论是：`ssh -L` 会在你的本机打开一个端口，再把进入这个端口的流量，通过 SSH 连接送到远端。

命令的记忆顺序是：本地监听地址和端口，接着是目标地址和端口，最后是要登录的 SSH 服务器。可以简单记成：`L` 代表“本地监听，本地通向远程”。

一个典型案例是，远程服务器上有个网站，只监听 `127.0.0.1` 的 80 端口。`127.0.0.1` 叫回环地址，也就是通常所说的 `localhost`。绑定在这里的服务，只能由这台机器自己访问，外部网络连不上。

这时，可以在本机执行本地转发，让本机的 8080 端口对应远程服务器的 `localhost` 80 端口。命令的核心写法是：

`ssh -L 8080:localhost:80 远程服务器`

建立连接后，访问本机的 `localhost:8080`，看到的就是远程服务器上那个原本只允许本机访问的网站。

如果只想建立隧道，不需要交互式登录，可以加上 `-N`。如果还想让它进入后台运行，可以再加 `-f`。因此常见组合是 `ssh -f -N -L`。

#### 通过跳板机访问私有网络

接下来，本地转发的目标不一定就是 SSH 服务器本身。SSH 服务器也可以充当“堡垒机”或“跳板机”，英文常叫 bastion host 或 jump host。

核心结论是：只要跳板机能访问某个内部服务，你就可以把本地端口，通过跳板机，转发到那台内部主机。

例如，你的电脑无法直接访问 VPC 里的 `172.16.0.40`，但公网跳板机可以访问它。此时，可以让本机的 8081 端口，转发到内部主机的 80 端口：

`ssh -L 8081:172.16.0.40:80 公网跳板机`

这样，本机访问 `localhost:8081`，流量会先进入跳板机，再由跳板机连接私有云中的目标服务。

这里最重要的一点是：SSH 服务器和最终目标可以是两台不同的机器。跳板机负责接收 SSH 连接，并替你完成第二段网络访问。

#### 通过跳板机访问目标主机的 localhost

更重要的是，上一种方法有一个限制：跳板机必须能通过网络地址访问目标端口。

如果内部主机上的调试接口、管理后台或监控端口，只绑定在它自己的 `127.0.0.1` 上，跳板机就无法直接连接。因为目标主机的回环端口，只对目标主机自己可见。

这时要使用 `-J`，也就是 ProxyJump，中文可以理解为“通过跳板机建立真正的 SSH 会话”。

它和普通跳板转发的区别是：普通方式让 SSH 会话停在跳板机上，再由跳板机访问目标；`-J` 则只是让跳板机中转数据，真正的 SSH 会话最终建立在你的电脑和内部目标主机之间。

例如，私有主机的 `localhost:9000` 上运行着一个内部调试服务。可以执行：

`ssh -J 公网跳板机 -L 8082:localhost:9000 私有主机`

这里的 `localhost:9000` 是从私有主机的角度解释的，所以它指向私有主机自己的回环端口。建立隧道后，本机访问 8082，就能打开那个原本对整个网络都不可见的调试服务。

#### 远程端口转发：把本地服务送到远端

接下来是方向相反的远程端口转发，参数是大写的 `R`。

核心结论是：`ssh -R` 会在远程 SSH 服务器上打开一个端口，并把进入这个端口的流量，通过隧道送回本地。

可以把它记成：`R` 代表“远程监听，远程通向本地”。

例如，你的电脑上有一个只监听 `localhost:80` 的开发网站，希望通过公网服务器的 8080 端口访问它。命令逻辑是：

`ssh -R 远程监听地址:8080:localhost:80 公网服务器`

如果希望公网服务器在所有网络接口上监听，可以把远程监听地址写成 `0.0.0.0`。完整示例是：

`ssh -R 0.0.0.0:8080:localhost:80 公网服务器`

这样，其他能访问该公网服务器的机器，就可以通过服务器的 8080 端口，访问你电脑上的本地网站。

不过这里有一个关键配置。默认情况下，远程转发通常只监听网关服务器自己的 `localhost`，也就是只有服务器内部能访问。若要监听公网接口，SSH 服务端的配置文件中需要启用 `GatewayPorts yes`。

和本地转发一样，远程转发也可以配合 `-f -N` 在后台运行。

#### 把家庭或私有网络里的服务转发到远端

远程转发的目标，也不一定是 SSH 客户端电脑本身。它还可以是客户端电脑能够访问的其他内部设备。

核心结论是：此时，你的电脑相当于跳板机。公网网关收到流量后，通过 SSH 隧道把流量送到你的电脑，再由你的电脑访问家庭网络中的目标设备。

例如，家庭网络里有一台内部服务器，地址是 `192.168.0.10`，80 端口提供服务。你的电脑可以访问它，但公网服务器不能。

这时，可以执行：

`ssh -R 0.0.0.0:8081:192.168.0.10:80 公网服务器`

建立隧道后，其他机器访问公网服务器的 8081 端口，实际上访问到的是家庭网络内部主机的 80 端口。

这里，目标地址 `192.168.0.10` 是从 SSH 客户端，也就是你的电脑这一侧解析和访问的。换句话说，只要你的电脑能访问目标，远程网关就有机会通过隧道间接访问它。

#### 动态本地转发：在本机建立 SOCKS 代理

接下来是更灵活的动态本地转发，参数是大写的 `D`。

核心结论是：`ssh -D` 不再把一个本地端口固定连接到一个远程目标，而是直接在本机建立一个 SOCKS 代理。

SOCKS 是一种通用代理协议。使用它的应用程序，可以在每次连接时自行指定目标主机和端口。因此，同一个代理端口可以访问多台机器和多个服务。

命令形式很简单：

`ssh -D 本地端口 SSH服务器`

例如：

`ssh -D 1080 公网跳板机`

执行后，本机的 `localhost:1080` 就成为 SOCKS 代理。浏览器、命令行工具或其他支持 SOCKS 的程序，可以通过它访问所有跳板机能够访问的目标。

原文的案例中，本机原本无法直接访问 VPC 里的两台内部主机。但通过同一个 1080 端口的 SOCKS 代理，两台主机都能访问，不需要分别创建两条 `ssh -L` 隧道。

它和普通本地转发的区别很清楚：`ssh -L` 一条隧道通常对应一个固定目标，而 `ssh -D` 的一个代理端口，可以覆盖跳板机后面的整个可达网络。

代价是，发起请求的应用程序必须支持 SOCKS。比如使用 curl 时，需要明确指定 SOCKS 代理参数。

#### 动态远程转发：在远程网关建立 SOCKS 代理

最后一种是动态远程转发。它仍然使用 `-R`，但不再写固定的目标地址和目标端口，只提供一个远程监听端口。

核心结论是：这种写法会让远程 SSH 服务器变成 SOCKS 代理。通过这个代理发出的请求，会沿 SSH 隧道回到客户端，再从客户端所在网络访问目标。

命令形式是：

`ssh -R 远程监听地址:代理端口 公网网关`

例如：

`ssh -R 0.0.0.0:1080 公网网关`

此时，网关的 1080 端口就是 SOCKS 代理。使用这个代理的机器，可以访问所有 SSH 客户端能够访问的地址，包括客户端所在的家庭网络，甚至客户端自己的 `localhost` 服务。

原文案例中，只建立一个这样的代理，就既能访问家庭网络里的 `192.168.0.10`，也能访问客户端电脑自己的回环服务。普通的固定远程转发如果要覆盖多个目标，通常需要创建多条隧道；动态远程转发只需要一个代理。

这种功能要求客户端使用 OpenSSH 7.6 或更高版本。和普通 `ssh -R` 一样，如果希望代理监听网关的非回环地址，也需要服务端启用 `GatewayPorts yes`。

#### 最值得记住的结论

最后，回顾五个最重要的判断方法。

第一，`ssh -L` 是本地端口转发。它在 SSH 客户端这一侧监听新端口，让远程服务出现在本机。

第二，`ssh -R` 是远程端口转发。它在 SSH 服务端这一侧监听新端口，让本地或家庭网络里的服务出现在远端。

第三，`ssh -D` 会在本机建立 SOCKS 代理。一个代理端口，就能访问 SSH 服务器所能到达的多个目标。

第四，`ssh -R` 如果只写监听端口、不写固定目标，就会在远程服务器建立 SOCKS 代理，让远端通过隧道访问客户端一侧的整个可达网络。

第五，最简单的口诀是：`L` 表示“本地到远程”，`R` 表示“远程到本地”。命令中冒号左边的一侧负责打开新端口。判断隧道类型时，不要先纠结流量经过哪些机器，只要先问一句：“这个新端口到底开在本地，还是开在远程？”通常就不会选错。

SSH 隧道最容易混淆的地方，不是命令本身，而是两个问题：新端口到底开在哪台机器上，目标地址又是从哪台机器的视角访问。只要抓住这两点，本地转发、远程转发和动态转发就不难记。

先说最常用的本地端口转发，也就是 SSH 的大写 L 参数。它的作用，是把远端服务映射到自己电脑的一个本地端口。

ssh，横杠大写 L，八零八零冒号 localhost 冒号八十，远程服务器地址。

执行后，SSH 客户端会在你的电脑上监听八零八零端口。访问自己电脑的 localhost 八零八零，流量就会穿过 SSH 隧道，到达远程服务器的 localhost 八十端口。一个原本只能在服务器内部访问的网站，就像运行在你的电脑上一样。

这里有一个重要细节。本地转发的目标，不一定是 SSH 服务器本身，也可以是 SSH 服务器能够访问的其他机器。

假设你的电脑无法直接进入某个私有网络，但一台公网堡垒机同时连接了这个私有网络。你可以让本地八零八一端口，通过堡垒机，转发到私有地址一七二点一六点零点四零的八十端口。此时，堡垒机负责发起第二段连接。也就是说，目标地址是从堡垒机的网络视角访问的。

不过，如果真正的目标服务只监听在私有主机自己的 localhost 上，普通堡垒机转发就不够了。因为堡垒机也访问不到另一台机器的回环地址。

这时要使用大写 J 参数，也就是 ProxyJump。SSH 连接只是经过堡垒机，最终终止在私有主机上。然后再把目标写成 localhost。这样，localhost 指的就是私有主机自己，而不是堡垒机。这个区别对于调试端口、管理后台、监控接口等只允许本机访问的服务尤其重要。

接下来是远程端口转发，也就是大写 R 参数。它和本地转发方向相反：本地转发是在自己电脑上开新端口；远程转发是在 SSH 服务器上开新端口，再把流量送回本地。

例如，你的笔记本上有一个只监听 localhost 八十端口的开发服务。你希望通过一台公网服务器临时发布它，可以执行：

ssh，横杠大写 R，零点零点零点零冒号八零八零冒号 localhost 冒号八十，公网服务器地址。

这表示公网服务器监听八零八零端口。进入这个端口的流量，会沿着 SSH 隧道返回你的笔记本，再访问笔记本的 localhost 八十端口。

这里有一个常见陷阱。默认情况下，远程转发通常只绑定在公网服务器自己的 localhost 上。结果是只有服务器内部能访问，外部用户仍然连不上。如果要监听零点零点零点零，也就是服务器的所有网络接口，SSH 服务端通常需要启用 GatewayPorts yes。否则，即使命令看起来正确，也无法真正对外开放。

远程转发的目标也不一定是笔记本自己。它还可以是笔记本能够访问的家庭服务器或内网设备。此时，笔记本同时连接内网和公网 SSH 服务器，相当于充当中间桥梁。公网侧的请求先经过 SSH 隧道到达笔记本，再由笔记本连接内网目标。

如果要访问的目标很多，逐个建立固定端口转发会很麻烦。这时可以使用动态转发。

横杠大写 D 会在本地建立一个 SOCKS 代理。例如，通过某台堡垒机，在本地开启一零八零端口。支持 SOCKS 的浏览器或命令行工具连接这个代理后，可以自行指定每次请求的目标。目标连接由远程 SSH 服务器发起，所以凡是那台服务器能够访问的私有地址，原则上都能通过同一个代理访问。

它和大写 L 的区别是，大写 L 会提前固定一个目标地址和端口；大写 D 则用一个代理覆盖多个目标。代价是使用它的应用程序必须支持 SOCKS 协议。

动态转发也有反向版本。大写 R 后面如果只写监听地址和端口，不写固定目标，远程 SSH 服务器就会变成一个 SOCKS 代理。通过这个代理发出的请求，会穿过隧道，交给 SSH 客户端一侧去连接。这样，一个远程代理就能访问客户端所在的整个家庭网络。这个功能要求客户端使用 OpenSSH 七点六或更新版本；如果代理要绑定到远程服务器的非回环地址，同样需要启用 GatewayPorts。

记忆 SSH 隧道时，只问两个问题就够了。大写 L，表示本地这一侧监听，流量去往远端可达的目标；大写 R，表示远程服务器监听，流量回到客户端可达的目标。命令中冒号左边描述新开的监听端口，右边描述流量最终要去的地方。只要先确定谁负责监听，再确定目标从哪一侧访问，绝大多数 SSH 隧道命令都能顺着逻辑写出来。

#### SSH 隧道真正该记住的，不是参数，而是“谁监听、谁访问”

这篇文章最有价值的不是罗列 `-L`、`-R`、`-D`，而是提供了一套稳定的判断模型：**先确定新端口开在哪台机器上，再确定目标地址由哪台机器去访问。** 一旦抓住这两点，大多数命令都不必死记。

##### `-L` 与 `-R`，本质是重新安排网络可达性

`ssh -L` 在本地 SSH 客户端一侧监听端口，流量穿过隧道后，由 SSH 服务端一侧连接目标。典型场景是：笔记本无法直接访问 VPC 内的数据库，但一台堡垒机可以，于是把数据库“映射”为本机的 `localhost:8080`。

`ssh -R` 正好相反：端口开在远端 SSH 服务器上，连接目标则从本地客户端一侧发起。因此，藏在家庭网络或开发机 `localhost` 上的服务，可以经一台公网服务器向外提供。

这里容易混淆的“local”和“remote”，并不总指命令两端那两台主机，也可以指它们各自能访问的其他设备。更准确的记忆方式是：

- `-L`：**本地监听，远端出站**
- `-R`：**远端监听，本地出站**

这比“左边写什么、右边写什么”更有迁移性，因为它直接解释了网络路径。

##### 堡垒机与目标机不是一回事

文章最值得保留的细节，是对 `-L` 和 `-J` 差异的解释。

如果执行：

```bash
ssh -L 8080:172.16.0.40:80 bastion
```

SSH 会终止在堡垒机，由堡垒机连接 `172.16.0.40:80`。但如果目标服务只绑定在目标机的 `127.0.0.1`，堡垒机仍然无法访问，因为 loopback 只属于目标机自己。

此时需要 `-J` 让堡垒机只负责中继，真正的 SSH 会话终止在目标机：

```bash
ssh -J bastion -L 8080:localhost:9000 target
```

这里的 `localhost` 才会被解释为目标机自身。**决定可达性的不是地址长什么样，而是谁在解析并连接这个地址。** 这个判断也适用于容器调试、远程开发机、沙箱内 AI 编码代理等场景。

##### 动态转发把“一条映射”升级为“一种访问能力”

固定转发一次只连接一个目标；`-D` 则在本地建立 SOCKS 代理，让应用逐次指定目的地。只要 SSH 服务器能够访问，一个代理就可以覆盖整段私有网络。动态 `-R` 是其镜像：代理开在远端，但目标从客户端所在网络访问。

这揭示了 SSH 隧道长期不过时的原因：它不是某个云平台的专用功能，而是一个轻量、可组合的**网络能力搬运工具**。当开发环境越来越远程化、沙箱化，它反而更有用。

不过，“能打通”不等于“应该公开”。尤其 `-R 0.0.0.0:...` 配合服务端 `GatewayPorts yes`，可能把无鉴权的调试、管理或浏览器控制端口直接暴露出去。默认只绑定 loopback 往往是一种保护；若确需公网访问，还应限制来源、防火墙规则和服务自身认证。**SSH 隧道最强的地方是绕开网络边界，而这也正是它最大的风险。**
