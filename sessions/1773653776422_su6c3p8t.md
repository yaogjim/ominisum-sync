## 分析要点

- **核心高价值点**：最有价值的是把大量专业化Agent人格、流程、交付物与多工具安装集成打包为可直接复用的工程资产。
- **留存建议**：短期参考并归档，适合作为AI代理模板库和工具接入索引保留（包含大量可直接复用的代理角色定义、安装方式与多工具集成说明，适合后续检索）

**知识要点**

- 可将不同职能的Agent按开发、设计、营销、产品、测试等领域模块化组织
- 通过转换与安装脚本把同一套Agent定义适配到Claude Code、Copilot、Cursor等多种工具
- Agent设计强调身份设定、工作流、交付物、成功指标，而不仅是单条Prompt

**行动项**

- 挑选与你当前工作流最相关的3-5个Agent，先在一个真实项目中小范围试用
- 参考其Agent模板结构，为你自己的高频任务定制内部专用Agent
- 评估其多工具安装脚本与目录规范，决定是否纳入团队开发环境标准化配置

> **A complete AI agency at your fingertips** - From frontend wizards to Reddit community ninjas, from whimsy injectors to reality checkers. Each agent is a specialized expert with personality, processes, and proven deliverables.

---

Born from a Reddit thread and months of iteration, **The Agency** is a growing collection of meticulously crafted AI agent personalities. Each agent is:

- **🎯 Specialized**: Deep expertise in their domain (not generic prompt templates)
- **🧠 Personality-Driven**: Unique voice, communication style, and approach
- **📋 Deliverable-Focused**: Real code, processes, and measurable outcomes
- **✅ Production-Ready**: Battle-tested workflows and success metrics

**Think of it as**: Assembling your dream team, except they're AI specialists who never sleep, never complain, and always deliver.

---

```
# Copy agents to your Claude Code directory
cp -r agency-agents/* ~/.claude/agents/

# Now activate any agent in your Claude Code sessions:
# "Hey Claude, activate Frontend Developer mode and help me build a React component"
```

Each agent file contains:

- Identity &amp; personality traits
- Core mission &amp; workflows
- Technical deliverables with code examples
- Success metrics &amp; communication style

Browse the agents below and copy/adapt the ones you need!

```
# Step 1 -- generate integration files for all supported tools
./scripts/convert.sh

# Step 2 -- install interactively (auto-detects what you have installed)
./scripts/install.sh

# Or target a specific tool directly
./scripts/install.sh --tool cursor
./scripts/install.sh --tool copilot
./scripts/install.sh --tool aider
./scripts/install.sh --tool windsurf
```

See the Multi-Tool Integrations section below for full details.

##### Supported Tools

- **[Claude Code](https://claude.ai/code)** — native `.md` agents, no conversion needed → `~/.claude/agents/`
- **[GitHub Copilot](https://github.com/copilot)** — native `.md` agents, no conversion needed → `~/.github/agents/` + `~/.copilot/agents/`
- **[Antigravity](https://github.com/google-gemini/antigravity)** — `SKILL.md` per agent → `~/.gemini/antigravity/skills/`

**Faster runs (parallel)** — On multi-core machines, use `--parallel` so each tool is processed in parallel. Output order across tools is non-deterministic. Works with both interactive and non-interactive install: e.g. `./scripts/install.sh --interactive --parallel` (pick tools, then install in parallel) or `./scripts/install.sh --no-interactive --parallel`. Job count defaults to `nproc` (Linux), `sysctl -n hw.ncpu` (macOS), or 4; override with `--jobs N`.

```
./scripts/convert.sh --parallel                    # convert all tools in parallel
./scripts/convert.sh --parallel --jobs 8           # cap parallel jobs
./scripts/install.sh --no-interactive --parallel   # install all detected tools in parallel
./scripts/install.sh --interactive --parallel      # pick tools, then install in parallel
./scripts/install.sh --no-interactive --parallel --jobs 4
```

## 结构化（1）

### 2026-03-16 09:33:44

这篇文章主要介绍了一个名为 `agency-agents` 的开源项目：它把 AI 助手做成了“专业分工明确的团队”，覆盖开发、设计、营销、产品、测试等多个领域。核心价值不在于“一个万能提示词”，而在于“很多有角色、有流程、有交付标准的专家型 AI agent”。

- 项目定位与核心理念
  - `agency-agents` 想做的是“一整家 AI 代理公司”，让用户像组建团队一样调用不同领域的 AI 专家。
  - 每个 agent 都强调 4 点：专业化、人格化、可交付、可落地。
  - 作者强调，这不是简单的 prompt 模板集合，而是带有身份设定、工作流程、输出样例、成功指标的完整 agent 系统。
  - 项目起源于 Reddit 讨论，经过数月迭代，并已在真实生产环境中打磨。

- agent 的组织方式与能力范围
  - 项目把 agent 按 division（事业部）组织，覆盖面非常广：工程、设计、付费投放、销售、营销、产品、项目管理、测试、支持、XR、游戏开发、学术叙事等。
  - 例如工程类包括：前端开发、后端架构、移动开发、AI 工程、DevOps、安全、数据库优化、SRE 等。
  - 设计与增长类包括：UI Designer、UX Researcher、Brand Guardian、Whimsy Injector、Reddit Community Builder、SEO Specialist、Douyin/Kuaishou/Bilibili 等中国平台专家。
  - 还有很多细分角色，如：`AI Citation Strategist` 专门做 AEO/GEO、提升品牌在 ChatGPT、Claude、Gemini、Perplexity 中的可见性。

- 每个 agent 具体包含什么
  - 每个 agent 文件通常包含：身份与性格、核心使命、工作流、技术交付物示例、成功指标、沟通风格。
  - 这意味着它不仅告诉你“该做什么”，还告诉你“怎么做、做到什么算好”。
  - 文中举的例子很直观：
    - `Evidence Collector`：默认找出 3–5 个问题，并要求视觉证据；
    - `Reddit Community Builder`：强调先做社区的有价值成员，而不是硬广营销；
    - `Whimsy Injector`：强调有趣的设计必须服务功能或情绪目标，甚至提到“庆祝动画可将任务完成焦虑降低 40%”。

- 典型使用场景：像拼团队一样协作
  - 项目不仅支持单个 agent 使用，还强调多 agent 协同。
  - 例子 1：做一个产品时，可以同时搭配 `Frontend Developer`、`Backend Architect`、`Growth Hacker`、`Rapid Prototyper`、`Reality Checker`，实现从开发到上线质检的完整链路。

  - 文中还给出一个完整案例：`Nexus Spatial Discovery Exercise`，8 个 agent 同时参与，最终在一次会话中产出统一的产品方案。

## 产品-技术开发（1）

### 2026-03-16 09:50:06

这是一个典型的“AI Agent as Productized Expertise”项目：不是卖模型能力，而是把“角色、流程、交付物、成功标准”封装成可复用的工作单元。它的价值不在提示词多，而在把专业服务标准化、模块化、可安装化。

**产品解读**
- 核心产品定位很清晰：`AI 代理市场 + 多工具分发层 + 团队协作方法论`，覆盖从开发、设计、增长到运营的完整职能链。
- 真正的产品创新点不是“144 个 agent”，而是把 agent 从一次性 prompt 升级成“可调用的岗位资产”。这比普通 prompt library 更接近 SaaS 的服务目录。
- 用户价值有三层：`快速调用专家能力`、`降低跨职能协作成本`、`把经验沉淀为组织资产`。这对独立开发者、小团队、AI-native 公司都成立。
- 增长机制也设计得好：角色名强记忆点、GitHub 易 fork、Reddit 易传播、支持多工具安装，天然具备社区裂变属性。
- 风险同样明显：agent 数量增长后会出现选择困难、角色重叠、质量不一致、上下文切换成本高，最终影响实际采用率。

**技术解读**
- 技术上它不是“复杂 agent runtime”，而是“内容规范化 + 多平台编译/分发”。本质是一个 agent spec 转换器。
- 仓库主体是 Markdown/规则文件，`convert.sh` 和 `install.sh` 是关键基础设施：前者做格式适配，后者做目标工具安装。这种架构很轻，维护成本低，扩展快。
- 设计理念很先进：把 agent 视为“跨平台 DSL”。同一份源定义，编译成 Claude/Copilot/Cursor/Aider/Windsurf/Qwen 等不同消费格式。
- 这说明作者抓住了现阶段 AI 工具生态的真实问题：不是模型不够强，而是上下游工具协议割裂，用户缺的是“统一人设与流程资产迁移能力”。
- 但它目前更像“静态 agent 包管理器”，不是“动态多 agent orchestration 平台”。也就是说，定义多，调度浅，执行闭环仍依赖宿主工具和人工触发。

**设计与实现上的最佳实践**
- `单一源定义，多个目标编译`
  - 最佳实践：维护一个 canonical agent schema，例如：
  ```yaml
  name: frontend-developer
  role: Frontend Developer
  goals:
    - build UI
    - optimize performance
  inputs:
    - task
    - codebase_context
  outputs:
    - patch
    - review_notes
  success_metrics:
    - lighthouse > 90
    - no a11y blockers
  tone: pragmatic
  ```
  - 再生成 `.md`、`.mdc`、`CONVENTIONS.md`、`SKILL.md` 等格式，避免手工维护多份内容漂移。

- `角色定义必须包含交付物，不只有人设`
  - 这个项目做对了：identity 之外还有 workflow、deliverables、success metrics。
  - 最佳实践例子：不要写“你是资深产品经理”；要写“输出 PRD、优先级矩阵、验收标准、风险列表”。

- `安装层与内容层解耦`
  - agent 内容在 `agency-agents/`，适配逻辑在 `scripts/` 和 `integrations/`，这是正确分层。
  - 最佳实践：未来可继续拆成：
    - `agents/`：源定义
    - `schemas/`：校验规则
    - `builders/`：目标平台转换器
    - `installers/`：目标平台安装器

- `项目级安装优先于全局安装`
  - 对 Cursor、Aider、Windsurf、OpenCode 采用 project-scoped 是对的，因为 agent 应跟随项目上下文。
  - 最佳实践：企业环境下增加 `team-scoped` 层，比如仓库内 `.ai/agents/`，随代码审计、版本管理、PR 一起走。

- `并行转换/安装`
  - `--parallel` 很实用，说明作者意识到 agent 规模扩大后，工具链效率会成为体验瓶颈。
  - 最佳实践：并行执行时要补三个能力：失败重试、日志聚合、目标工具结果校验。

**如果我是产品负责人，会怎么继续做**
- 第一优先级不是继续加 agent，而是做“Agent Discovery”
  - 现在最大问题是丰富，但难选。
  - 最佳实践：
    - 按任务入口推荐 agent，而不是按岗位枚举
    - 支持“输入目标 → 自动推荐 agent team”
    - 提供 starter packs，比如“0-1 SaaS 上线包”“增长实验包”“技术尽调包”

- 第二优先级是做“组合编排”
  - 目前更像单 agent catalog，下一步应支持 team workflow。
  - 示例：
  ```text
  用户需求 -> Product Manager 产出 PRD
           -> Software Architect 产出架构
           -> Frontend Developer/Backend Architect 分别实现
           -> Code Reviewer + Reality Checker 做发布门禁
  ```
  - 最佳实践：把 agent 间输入输出契约定义清楚，如 PRD schema、API spec schema、test checklist schema。

- 第三优先级是做“质量评估系统”
  - agent 多了以后，最怕“看起来专业，实际不可用”。
  - 最佳实践：
    - 每个 agent 配 benchmark task
    - 记录通过率、人工采纳率、修改率、交付时长
    - 给 agent 打版本和质量分
  - 例如：
  ```json
  {
    "agent": "frontend-developer",
    "version": "1.4.2",
    "task_success_rate": 0.81,
    "human_accept_rate": 0.67,
    "avg_iterations": 2.3
  }
  ```

- 第四优先级是做“企业级治理”
  - 真正进入团队后，会遇到 prompt 合规、品牌一致性、安全边界问题。
  - 最佳实践：
    - 增加 org policy overlay
    - 定义禁止行为、合规约束、输出模板
    - 支持不同组织对同一 agent 的定制继承

**一个更成熟的实现范式**
- 可以把这个项目升级成三层架构：
  - `Agent Spec Layer`：统一定义角色、能力、输入输出、约束
  - `Execution Layer`：适配 Claude/Cursor/Copilot/Qwen 等运行环境
  - `Evaluation Layer`：评估 agent 在真实任务中的效果
- 这样它就从“agent 仓库”变成“agent 操作系统”。

**具体最佳实践例子：如何定义一个高质量 Agent**
```md
# Product Manager

## Mission
Turn ambiguous product ideas into shippable, measurable plans.

## Inputs
- business goal
- target user
- constraints
- existing product context

## Outputs
- PRD
- prioritized backlog
- success metrics
- launch risks

## Workflow
1. Clarify objective and constraints
```

## 产品-最佳实践（1）

### 2026-03-16 09:52:33

可以。基于这个仓库的核心理念，我建议不要把它理解成“很多厉害提示词的集合”，而要把它当成“可协作的岗位系统”。

我用一个具体实例来讲：

**实例：做一个 SaaS 产品官网 + 注册漏斗的首版上线**

假设你要在 2 周内上线一个 AI 简历优化工具的官网，目标是：
- 清晰讲清产品价值
- 有注册转化
- 页面性能合格
- 上线后能持续优化

这时，不要只启用一个 `Frontend Developer` agent 一把梭，而是按职责拆成一个最小协作组：

- `Product Manager`
- `UI Designer`
- `Frontend Developer`
- `Technical Writer`
- `Reality Checker`

如果要再进一层，可以补：
- `UX Researcher`
- `Analytics Reporter`
- `SEO Specialist`

**最佳实践，不是在“多用 agent”，而是在“先定边界，再定交接”**

你可以按下面这套方法跑。

**1. 先用一个 agent 定义任务，不要让所有 agent 同时发散**
最先启用的应该是 `Product Manager`，不是 `Frontend Developer`。

原因很简单：
- 如果目标不清楚，后面的设计、开发、文案都会各自优化各自的东西
- 多 agent 最大的问题不是能力不够，而是产出不对齐

在这个实例里，`Product Manager` 应先输出：
- 目标用户是谁
- 首页唯一核心 CTA 是什么
- 页面结构怎么排
- MVP 范围是什么，不做什么

例如：
- 用户：正在找工作的 0-5 年职场人
- 首页主目标：注册并上传简历
- 页面结构：Hero / 社会证明 / 功能亮点 / 使用步骤 / FAQ / CTA
- 本期不做博客、不做多语言、不做复杂价格页

这是最佳实践里的第一条：

- 让一个“负责人 agent”先产出单一事实源，避免多 agent 同时定义问题

**2. 每个 agent 只负责一种交付物，不要让角色重叠**
很多人用 agent 失败，是因为让每个 agent 都去“顺便想一下”。

比如在这个项目里，推荐这样分工：

- `Product Manager`：输出 PRD、页面目标、信息架构、验收标准
- `UI Designer`：输出视觉层级、组件样式、色彩和版式建议
- `Frontend Developer`：把页面实现为真实可运行代码
- `Technical Writer`：打磨文案，确保表达清晰、可信、具体
- `Reality Checker`：按“是否可上线”标准做最终审查

这样做的好处是：
- 每个 agent 的输出容易判断好坏
- 出问题时知道该回退到哪个角色修改
- 不会出现“设计 agent 改了文案策略，开发 agent 又重写结构”这种混乱

对应的最佳实践是：

- 一个 agent 对应一种明确 deliverable，而不是对应一个模糊阶段

**3. 交接必须结构化，否则多 agent 会互相污染**
这个仓库强调 agent 的 personality，但在实际协作里，真正重要的是“上下文交接格式”。

在这个例子里，推荐每轮交接都固定成 4 段：

- 目标
- 输入
- 输出格式
- 约束

例如给 `UI Designer` 的交接可以是：

```text
目标：为 AI 简历优化工具官网设计首版桌面端 + 移动端视觉方案
输入：
1. Product Manager 输出的页面结构
2. 品牌关键词：专业、可信、轻快
3. CTA：立即上传简历
输出格式：
1. 每个页面区块的视觉目标
2. 设计 token 建议（颜色/字体/间距）
3. 组件清单
4. 对 Frontend Developer 的实现说明
约束：
- 首屏必须 5 秒内理解价值
- 不做复杂插画系统
- 优先保证转化，不追求炫技
```

这背后的最佳实践是：

- agent 之间传递“结构化任务单”，不要只传一句“你接着做”

**4. 先产出中间件文档，再产出代码**
这个仓库里很多 agent 都有流程和 deliverables，这其实说明一件事：最佳使用方式不是直接要最终答案，而是先拿中间产物。

在这个实例中，正确顺序应该是：

- `Product Manager` 产出首页 PRD
- `Technical Writer` 产出文案草案
- `UI Designer` 产出组件和视觉规范
- `Frontend Developer` 再开始写代码
- `Reality Checker` 最后验收

而不是：
- 一上来让 `Frontend Developer` “直接做个 landing page”

为什么？
因为 landing page 成败往往不是代码质量决定的，而是：
- 信息顺序
- 文案说服力
- CTA 是否单一
- 视觉层级是否聚焦

所以这里的最佳实践是：

- 把 agent 用在“减少返工”上，不只是“加快生成”上

**5. 用“验收标准”驱动 agent，而不是用“风格偏好”驱动**
很多人会对 agent 说：
- 做高级一点
- 做得像 SaaS 大厂
- 文案更有感觉
- 页面更有质感

这种说法最容易导致结果漂移。

在这个例子里，更好的说法是：

- Hero 区必须在 1 个标题 + 1 个副标题内讲清“上传简历后得到什么”
- 页面首屏必须包含主 CTA
- Lighthouse Performance 移动端至少 85+
- CTA 点击路径不超过 2 步
- FAQ 至少回答“隐私安全吗”“适合哪些人”“免费吗”

所以最佳实践是：

- 把 agent 管理成“对指标负责的岗位”，不是“对感觉负责的创意人格”

**6. 最后一定要有一个反方 agent 做上线拦截**
这个仓库里我认为最有价值的一类 agent，不是生成型 agent，而是像 `Reality Checker`、`Code Reviewer`、`Accessibility Auditor` 这种“反方角色”。

在这个官网项目里，`Reality Checker` 应该专门检查：

- 页面有没有转化断点
- 文案是不是夸大承诺
- 移动端是否可用
- CTA 是否清晰
- 加载是否过重
- 是否缺少隐私说明
- 表单失败态有没有处理

这一步非常关键，因为多 agent 协作最常见的问题是：
- 每个人都产出很多内容
- 但没人对“能不能上线”负责

所以最佳实践是：

- 在多 agent 流程里，必须有一个默认唱反调、默认挑问题的最终审批角色

**把这个实例落成一套推荐工作流**

如果你真的要照着用，我建议按这个顺序：

**阶段 1：定义**
- 用 `Product Manager` 明确目标用户、CTA、页面结构、MVP 边界

**阶段 2：内容**
- 用 `Technical Writer` 先写文案，而不是让开发顺手填字

**阶段 3：设计**
- 用 `UI Designer` 基于文案和结构做视觉与组件方案

**阶段 4：实现**
- 用 `Frontend Developer` 按既定结构实现，不重新定义需求

**阶段 5：审查**
- 用 `Reality Checker` 做发布前审查
- 有条件再加 `Accessibility Auditor` 和 `Code Reviewer`

这比“开 5 个 agent 一起 brainstorm”更稳，因为它符合真实团队协作方式。

**一句话总结这个仓库的最佳实践**
最好的使用方式，不是把 agent 当“更花哨的 prompt”，而是把它们组织成：
- 明确角色
- 明确交付物
- 明确交接格式
- 明确验收标准

这样它们才会从“会说话的专家人设”，变成“真的能协作的生产系统”。
