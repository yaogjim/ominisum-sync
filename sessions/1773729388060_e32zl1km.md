## 正文

**陈成**

OpenAI Codex Subagents 今天 GA 了，读完文档梳理几个关键架构细节。

代理的分工设计

内置三类代理，职责不同：

• default：通用兜底  
• worker：执行导向，负责实现和修复  
• explorer：只读探索，专门 trace 代码路径

你也可以自定义，放 TOML 文件到 .codex/agents/ 就行。每个 agent 可以单独配：

• model + model\_reasoning\_effort（贵的模型留给高推理任务）  
• sandbox\_mode（explorer 设 read-only，fixer 才放开写权限）  
• 独立挂载 mcp\_servers（给文档查询 agent 接 docs MCP，不污染主进程）

并发控制

\[agents\]  
max\_threads = 6 # 默认值，最大并发线程数  
max\_depth = 1 # 子代理不能再派生子代理

max\_depth = 1 是个有意思的设计选择——防止失控的递归调用链，同时还是允许水平扩展。

CSV 批处理（实验性）

spawn\_agents\_on\_csv 这个工具有点意思，每行一个 worker，并行跑完导出结果：

csv\_path: /tmp/components.csv  
instruction: "Review {path} owned by {owner}.  
Return JSON via report\_agent\_job\_result."  
output\_csv\_path: /tmp/review-results.csv

结果 CSV 包含 job\_id、status、last\_error、result\_json。适合批量 audit 场景——100 个文件扔进去，每个 worker 独立跑，最后合并。

审批继承机制

子代理继承父 session 的沙箱策略，包括运行时的 /approvals 改动和 --yolo 标志。在非交互模式下，碰到需要新审批的操作直接报错返回给父流程，不会挂起等待。

整体感受

这套设计的核心是隔离 + 并行：不同职责的 agent 用不同的模型和权限，exploration 和 implementation 分开跑，避免上下文污染（context rot）。跟 Claude Code 的子代理实现很像，属于同一方向的收敛。

实际用的话，PR review 场景最直接：explorer 先 map 代码路径，reviewer 并行跑安全+质量+测试，docs\_researcher 查 API 文档，主进程等三个都完成再汇总。比串行跑快很多，context 也更干净。

## 结构化（1）

### 2026-03-17 06:41:13

这篇内容主要在讲：OpenAI Codex 的 Subagents 已经正式可用，它的核心设计思路是把不同任务拆给不同代理，并通过“隔离 + 并行”提升效率、减少上下文污染。作者认为，这套机制很适合代码审查、批量分析这类工程场景。

- 1. 代理如何分工
  - Codex 内置了 3 类代理：`default` 负责通用兜底，`worker` 偏执行，主要做实现和修复，`explorer` 偏只读探索，专门用来追踪代码路径。
  - 这种设计本质上是把“查问题”和“动代码”分开，避免一个代理既要理解全局、又要修改实现，导致上下文混乱。
  - 除了内置代理，也支持自定义代理，只要把 TOML 文件放到 `.codex/agents/` 目录即可。

- 2. 每个代理可以独立配置什么
  - 每个 agent 都能单独设置模型和推理强度，比如把更贵、更强推理的模型留给复杂任务。
  - 沙箱权限也可以分开配：例如 `explorer` 用 `read-only`，只负责看代码；真正修复问题的 agent 再开放写权限。
  - 还可以给不同 agent 单独挂载 `mcp_servers`，比如专门给文档查询代理接文档 MCP，避免污染主流程环境。
  - 这说明 Subagents 不是简单“多开几个助手”，而是让每个助手拥有不同能力边界。

- 3. 并发控制的设计
  - 配置里有两个关键参数：
    - `max_threads = 6`：默认最多并发 6 个线程
    - `max_depth = 1`：子代理不能继续派生子代理
  - 作者特别提到 `max_depth = 1` 很有意思，因为它限制了递归式扩张，防止代理链条失控。
  - 同时，它又保留了水平并发能力，也就是可以同时开多个代理干活，但不让它们无限套娃。

- 4. CSV 批处理能力
  - 实验性工具 `spawn_agents_on_csv` 支持按 CSV 批量启动代理：CSV 每一行对应一个 worker，并行执行后再统一导出结果。
  - 示例里输入是：
    - `csv_path: /tmp/components.csv`
    - `instruction: "Review {path} owned by {owner}. Return JSON via report_agent_job_result."`
    - `output_csv_path: /tmp/review-results.csv`
  - 输出结果 CSV 会包含 `job_id`、`status`、`last_error`、`result_json`。
  - 这个能力很适合批量审计场景。比如把 100 个文件一次性丢进去，每个 worker 各自审查，最后再统一汇总结果。

- 5. 审批和权限如何继承
  - 子代理会继承父 session 的沙箱策略，也会继承运行时通过 `/approvals` 做的修改，以及 `--yolo` 标志。
  - 在非交互模式下，如果子代理遇到需要新增审批的操作，不会停在那里等人确认，而是直接报错并返回给父流程。
  - 这意味着整套机制在自动化流水线里更可控，不容易因为等待人工审批而卡死。

- 6. 作者的整体判断和应用场景
  - 作者认为，这套架构最核心的价值就是“隔离 + 并行”：
    - 不同职责用不同代理
    - 不同代理用不同模型和权限
    - 把探索（exploration）和实现（implementation）拆开
  - 这样做能减少“context rot”（上下文腐烂/污染），让每个代理只处理自己该处理的事。
  - 作者还提到，这个方向和 Claude Code 的子代理实现很像，说明行业方案正在收敛。
  - 在实际应用中，作者认为最直接的场景是 PR review：
    - `explorer` 先梳理代码路径
    - `reviewer` 并行检查安全、质量、测试
    - `docs_researcher` 去查 API 文档
    - 主进程等三个结果回来后再统一汇总
  - 相比串行执行，这样会明显更快，而且上下文更干净。
