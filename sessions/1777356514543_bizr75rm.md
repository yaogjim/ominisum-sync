#### What We're Building

一个贷款收入核实流程分3步：

1. **提取** 结构化数据从 4 份文档（贷款申请表、W-2、工资条、银行对账单）中使用 E [xtract](https://developers.llamaindex.ai/python/cloud/llamaextract/getting_started/sdk/)

3. **生成** 一个包含提取结果、置信度分数、验证检查和处理器建议的独立 HTML 报告

示例文件使用了一个模拟借款人（Sarah M. Chen），其中 W-2 表显示 **68,500 美元** （上一年度），而工资单年化为 **72,000 美元** （本年度）。这一差额与年中加薪相符，但仍需证明材料。银行对账单还包含了工资之外无法解释的 Zelle/Venmo 存款。Claude 发现了这两处异常。

#### 步骤 1: 定义提取模式

每个文档类型都有一个 Pydantic 模型。 `description` 字段指导 Extract 在每个文档中需要查找什么：

```html
from pydantic import BaseModel, Field

class LoanApplication(BaseModel):

    borrower_name: str = Field(description="Full name of the borrower (first middle last)")

    ssn: str = Field(description="Social Security Number (format: XXX-XX-XXXX)")

    date_of_birth: str = Field(description="Date of birth (MM/DD/YYYY)")

    current_address: str = Field(description="Full current residential address")

    employer_name: str = Field(description="Name of current employer")

    position: str = Field(description="Job title or position")

    monthly_income: float = Field(description="Monthly base income in dollars")

    loan_amount: float = Field(description="Requested loan amount in dollars")

    property_address: str = Field(description="Address of the property being purchased")

    property_value: float = Field(description="Estimated property value or purchase price")

class W2Form(BaseModel):

    employee_name: str = Field(description="Full employee name (first and last)")

    employee_ssn: str = Field(description="Employee Social Security Number")

    employer_name: str = Field(description="Employer name and address")

    employer_ein: str = Field(description="Employer Identification Number (EIN)")

    wages_tips_other: float = Field(description="Box 1: Wages, tips, other compensation")

    federal_tax_withheld: float = Field(description="Box 2: Federal income tax withheld")

    social_security_wages: float = Field(description="Box 3: Social security wages")

    medicare_wages: float = Field(description="Box 5: Medicare wages and tips")

class PayStub(BaseModel):

    employee_name: str = Field(description="Employee name (may be in LAST, FIRST format)")

    employer_name: str = Field(description="Employer or company name")

    pay_period_start: str = Field(description="Start date of pay period")

    pay_period_end: str = Field(description="End date of pay period")

    pay_date: str = Field(description="Payment date")

    gross_pay: float = Field(description="Current period gross pay in dollars")

    net_pay: float = Field(description="Current period net pay (take-home) in dollars")

    ytd_gross_pay: float = Field(description="Year-to-date gross pay in dollars")

    ytd_net_pay: float = Field(description="Year-to-date net pay in dollars")

    federal_tax: float = Field(description="Current period federal income tax withheld")

    pay_frequency: str = Field(description="Pay frequency: weekly, biweekly, semi-monthly, or monthly")

class BankStatement(BaseModel):

    account_holder_name: str = Field(description="Name on the account")

    account_number: str = Field(description="Account number (may be partially masked)")

    statement_period_start: str = Field(description="Statement period start date")

    statement_period_end: str = Field(description="Statement period end date")

    opening_balance: float = Field(description="Beginning balance in dollars")

    closing_balance: float = Field(description="Ending balance in dollars")

    total_deposits: float = Field(description="Total deposits/credits in dollars")

    total_withdrawals: float = Field(description="Total withdrawals/debits in dollars")
```

非常直接。你定义你关心的字段，添加描述以便模型知道要提取什么，而 Extract 会处理其余部分，无论它是一份 15 页填写了 AcroForm 的 1003 表格，还是一份合成的 reportlab 工资单。

#### Step 2: Extract with Extract

上传每个文档，运行启用了 [置信度分数和引用](https://developers.llamaindex.ai/python/cloud/llamaextract/features/options/) 的提取，并轮询结果：

```html
import time

from llama_cloud import LlamaCloud

client = LlamaCloud()  # uses LLAMA_CLOUD_API_KEY env var

def extract_document(client, file_path, schema_class, label=""):

    """Upload a document, extract with schema, return (result_dict, metadata_dict)."""

    file_obj = client.files.create(file=file_path, purpose="extract")

    job = client.extract.create(

        file_input=file_obj.id,

        configuration={

            "data_schema": schema_class.model_json_schema(),

            "tier": "agentic",

            "cite_sources": True,

            "confidence_scores": True,

        },

    )

    while job.status not in ("COMPLETED", "FAILED", "CANCELLED"):

        time.sleep(3)

        job = client.extract.get(job.id)

    if job.status != "COMPLETED":

        raise RuntimeError(f"Extraction failed for {label}: {job.status}")

    result = job.extract_result or {}

    detailed = client.extract.get(job.id, expand=["extract_metadata"])

    return result, metadata
```

The `agentic` 层级处理所有四种文档格式，无需任何格式特定的配置。您将获得结构化的 JSON，其中包含每个字段的置信度分数以及指向源文档中精确文本和边界框的来源引用。

这是 W-2 表返回的内容：

置信分数和引用在这里特别有用。在生产系统中，你应该在任何低置信度的提取结果进入验证步骤之前，将其标记出来以进行人工审核。

#### 步骤 3: 使用 Claude 交叉验证收入

这是最酷的部分。与其编写脆弱的比较规则，我们将所有四个提取结果发送给 Claude，让它推理跨文档的收入一致性。定义输出模式:

```html
from typing import Literal

from anthropic import Anthropic

class IncomeCheck(BaseModel):

    check_name: str = Field(description="E.g. 'Stated Income vs W-2 Wages'")

    doc_a_label: str

    doc_a_value: str

    doc_b_label: str

    doc_b_value: str

    passed: bool

    reasoning: str

    check_type: Literal["income", "employer", "deposit"]

class IncomeMetrics(BaseModel):

    stated_annual_income: float

    w2_annual_income: float

    annualized_pay_stub: float

    monthly_income: float

    income_trend: str

    unexplained_deposits: float

class LoanProcessorDecision(BaseModel):

    checks: list[IncomeCheck]

    metrics: IncomeMetrics

    decision: Literal["COMPLETE", "REVIEW", "FLAG"]

    decision_reasoning: str
```

然后调用 Claude 并使用结构化输出

```html
def validate_income_with_llm(app_data, w2_data, stub_data, stmt_data):

    client = Anthropic()

    prompt = f"""You are a mortgage loan processor performing income verification.

Cross-validate the income information across these four documents...

Document 1 — Loan Application: {json.dumps(app_data, indent=2)}

Document 2 — W-2 (prior year): {json.dumps(w2_data, indent=2)}

Document 3 — Pay Stub (current): {json.dumps(stub_data, indent=2)}

Document 4 — Bank Statement: {json.dumps(stmt_data, indent=2)}

Perform these checks:

1. Stated Income vs W-2 (flag if >10% discrepancy)

2. Stated Income vs Pay Stub Annualized

3. W-2 vs Pay Stub Annualized (income trend)

4. Pay Stub Net Pay vs Bank Deposits (unexplained deposits)

5. Employer Name Consistency"""

    response = client.messages.parse(

        model="claude-sonnet-4-6",

        max_tokens=4096,

        messages=[{"role": "user", "content": prompt}],

        output_format=LoanProcessorDecision,

    )

    return response.parsed_output
```

Claude 返回了一个结构化决策。以下是验证输出的样子：

#### 自动化贷款收入核验：LlamaParse + Claude 的文档处理方案

##### 一句话总结

文章展示了如何用 **LlamaParse Extract 提取贷款文档数据**，再用 **Claude 进行跨文档收入一致性验证**，最终自动生成贷款处理报告，把原本耗时的人工核验流程压缩到几分钟。

##### 背景：房贷审核的核心痛点

房贷处理员大量时间花在“读文件、抄数字、核对一致性”上。

一份贷款档案通常超过 500 页，包含贷款申请表、W-2、工资单、银行流水等多种文件。审核重点是确认收入是否一致，例如：

- 申请表里的申报收入
- W-2 上的年度工资
- 工资单上的当前薪资
- 银行流水中的实际入账

如果存在加薪、额外存款、雇主名称不一致等情况，都需要人工发现并记录。

##### 方案概览：三步完成自动核验

该流程分为三步：

1. **结构化提取**  
   使用 LlamaParse Extract 从贷款申请表、W-2、工资单、银行流水中提取关键字段。

2. **交叉验证**  
   使用 Claude 对不同文档中的收入、雇主、存款模式进行逻辑核对。

3. **生成报告**  
   自动输出 HTML 报告，包含提取结果、置信度、验证结论和处理建议。

##### 第一步：定义提取字段

开发者为不同文档类型定义 Pydantic 数据模型，例如：

- 贷款申请表：借款人姓名、SSN、雇主、月收入、贷款金额
- W-2：雇员姓名、雇主、年度工资、税款
- 工资单：工资周期、总收入、净收入、年初至今收入
- 银行流水：账户名、余额、总存款、总支出

每个字段通过描述告诉模型“应该找什么”，LlamaParse 会自动适配不同格式的 PDF、表格和表单。

##### 第二步：用 LlamaParse Extract 提取数据

系统上传文档后，通过 LlamaParse 的 agentic 模式进行提取，并返回：

- 结构化 JSON 数据
- 字段级置信度分数
- 来源引用
- 原文位置和边界框

这对生产系统很关键：低置信度字段可以先进入人工复核，避免错误数据直接进入自动判断流程。

##### 第三步：用 Claude 做收入一致性判断

文章没有采用写死的规则，而是把四份文档的结构化数据交给 Claude，让它像贷款处理员一样分析。

Claude 会检查：

- 申报收入 vs W-2 收入
- 申报收入 vs 工资单年化收入
- W-2 vs 工资单收入趋势
- 工资单净收入 vs 银行入账
- 雇主名称是否一致

并输出结构化结果，包括：

- 每项检查是否通过
- 异常原因
- 收入指标
- 最终决策：完成、待审核或标记风险

##### 示例结果：Claude 发现了两类异常

示例借款人 Sarah M. Chen 的材料中：

- W-2 显示年收入为 **68,500 美元**
- 当前工资单年化收入为 **72,000 美元**

Claude 判断这可能是年中加薪导致，并非明显欺诈，但仍需要补充加薪证明。

##### 主旨概括

本文介绍了如何用 **LlamaParse / Extract + Claude Agent SDK** 搭建一个自动化房贷收入核验流程：先从贷款相关文档中提取结构化数据，再由 Claude 跨文档比对收入一致性，最后生成可供贷款处理员使用的 HTML 审核报告。

该方案适合处理房贷、保险理赔、合同审查、合规审计等大量依赖文档核对的工作流，能把原本耗时数小时的人工核验压缩到几分钟内。

---

##### 1. 背景：房贷收入核验为什么适合自动化

房贷处理员大量时间花在重复性文档处理上：

- 行业估计显示，**手动处理文档占房贷处理员 40%-60% 的工作时间**。
- 一份平均房贷档案通常超过 **500 页**。
- 文档类型复杂，包括：
  - 贷款申请表
  - W-2 税表
  - 工资单
  - 银行对账单
  - 纳税申报单
  - 评估报告
  - 产权文件等

核心难点是：**同一收入信息必须在多个来源中互相印证**。

例如，审核人员需要确认：

- 贷款申请表中的申报收入是否合理；
- W-2 中的上一年度收入是否匹配；
- 工资单体现的当前收入是否一致；
- 银行对账单中的工资入账是否符合收入模式；
- 是否存在无法解释的额外存款。

---

##### 2. 本文要构建的系统

文章构建了一个自动化贷款收入核验流程，分为三步：

1. **提取数据**  
   使用 LlamaParse / Extract 从 4 类文档中提取结构化信息：
   - 贷款申请表
   - W-2
   - 工资单
   - 银行对账单

2. **交叉验证**  
   使用 Claude 对提取结果进行跨文档推理，包括：
   - 收入一致性检查
   - 雇主名称匹配
   - 银行存款模式分析

3. **生成报告**  
   输出一个独立的 HTML 报告，内容包括：
   - 文档提取结果
   - 字段置信度分数
   - 验证检查结果
   - 贷款处理建议

---

##### 3. 示例案例：借款人 Sarah M. Chen

文章使用了一个模拟借款人 **Sarah M. Chen** 的案例。

关键数据如下：

- W-2 显示上一年度收入：**68,500 美元**
- 当前工资单年化收入：**72,000 美元**
- 两者存在差额，但可解释为“年中加薪”
- 银行对账单中还出现了工资之外的额外存款：
  - Zelle：**800 美元**
  - Venmo：**750 美元**
  - 合计无法解释存款：**1,550 美元**

Claude 最终识别出两个需要关注的问题：

- W-2 与当前工资单存在收入差异，需要提供加薪证明；
- 银行账户中存在 1,550 美元无法解释的额外存款，需要说明资金来源。

##### 4. 第一步：定义提取模式

系统先为每种文档定义一个 **Pydantic 数据模型**，告诉 Extract 需要提取哪些字段。

例如：

###### 贷款申请表需要提取

- 借款人姓名
- 社保号
- 出生日期
- 当前住址
- 雇主名称
- 职位
- 月收入
- 贷款金额
- 房产地址
- 房产价值

###### W-2 表需要提取

- 员工姓名
- 员工社保号
- 雇主名称
- 雇主 EIN
- 工资、奖金及其他收入
- 联邦税预扣金额
- 社保工资
- Medicare 工资

###### 工资单需要提取

- 员工姓名
- 雇主名称
- 工资周期
- 发薪日期
- 税前工资
- 税后工资
- 年初至今收入
- 支付频率

###### 银行对账单需要提取

- 账户持有人姓名
- 账号
- 对账周期
- 期初余额
- 期末余额
- 总存款
- 总支出

这种方式的好处是：

##### 5. 第二步：用 Extract 提取结构化数据

系统将每份文档上传到 LlamaCloud，并启用：

- **agentic tier**
- **来源引用 cite_sources**
- **置信度分数 confidence_scores**

Extract 会输出结构化 JSON，同时为每个字段提供：

- 提取出的字段值；
- 置信度；
- 来源文本；
- 文档中的位置边界框。

这对生产环境很重要。  
例如，如果某个收入字段的置信度较低，系统可以在进入 Claude 验证前先标记给人工复核。

文章强调，agentic 层可以处理多种格式的文档，不需要针对每类文件单独写复杂规则。

---

##### 6. 第三步：用 Claude 交叉验证收入

与其写大量容易失效的固定规则，文章选择将四类文档的提取结果交给 Claude，让它进行跨文档推理。

Claude 需要完成的检查包括：

1. **贷款申请收入 vs W-2 收入**  
   如果差异超过 10%，需要标记。

2. **贷款申请收入 vs 工资单年化收入**  
   检查当前工资是否支持申报收入。

3. **W-2 vs 工资单年化收入**  
   判断收入趋势，例如是否可能因为加薪导致差异。

4. **工资单净收入 vs 银行入账**  
   检查银行存款是否符合工资发放模式。

5. **雇主名称一致性**  
   判断不同文档中的雇主是否匹配。

精炼理由：这篇文章表面是 LlamaParse + Claude 的贷款收入核验教程，真正有价值的是它展示了一种可迁移的 AI 工作流架构：**先把非结构化材料变成带置信度和出处的结构化事实，再让 LLM 做跨源一致性判断，而不是把所有任务混成一个黑箱。**

---

##### 2. 最重要的洞见

###### 洞见 1：AI 文档自动化的核心不是“提取”，而是“跨来源一致性验证”

###### **核心观点：**  
> 贷款审核最难的不是从单个文件里读出收入数字，而是判断多个文件中的数字是否能互相解释。

**为什么重要：**  
很多文档自动化项目会把重点放在 OCR、表格解析、字段抽取上，但真实业务风险往往藏在**不同文件之间的关系**里：

- 贷款申请写年收入 72,000 美元；
- W-2 显示去年收入 68,500 美元；
- 工资单年化后是 72,000 美元；
- 银行流水中还有 Zelle/Venmo 额外存款。

单看任何一个文档都不一定有问题，真正的判断来自组合：  
**这是收入造假？正常加薪？还是需要补充证明？**

**反常识之处：**  
常见做法是追求“单文档抽取准确率”。但在高风险流程里，单点准确不够，关键是**跨文件关系是否闭环**。

**可迁移价值：**  
这个逻辑适用于：

- 保险理赔：事故报告、医院账单、维修单、照片是否一致；
- 合同审查：主合同、补充协议、发票、付款记录是否一致；
- 财务审计：发票、银行流水、采购订单、收货单是否一致；
- 招聘背调：简历、社保记录、学历证明、推荐信是否一致。

**我应该记住什么：**  
> 文档自动化的高价值区域，不在“读出字段”，而在“发现字段之间解释不了的地方”。

---

###### 洞见 2：好的 LLM 工作流应该把“事实提取”和“判断推理”分开

###### **核心观点：**  
> Extract 负责结构化事实，Claude 负责跨文档推理；这比直接把所有 PDF 扔给 LLM 更稳健。

**为什么重要：**  
文章里的架构不是“一个大模型端到端处理所有事”，而是分工明确：

1. **LlamaParse / Extract**  
   从贷款申请、W-2、工资单、银行流水中提取结构化字段；
2. **置信度分数 + 引用来源**  
   判断字段是否可靠，并保留原文证据；
3. **Claude structured outputs**  
   基于结构化数据做一致性判断；
4. **HTML 报告**  
   输出可审计、可交付、可复核的结果。

这避免了一个常见问题：  
如果直接让 LLM 阅读所有文档并下结论，结果可能很聪明，但难以追溯，出错后也难以定位。

**反常识之处：**  
很多人以为大模型越强，越应该端到端包办。  
但在严肃业务中，更好的方式反而是：  
**限制大模型的自由度，让它只在最适合的环节发挥推理能力。**

**可迁移价值：**  
可以抽象成一个通用 AI 系统设计原则：

> 非结构化输入 → 结构化事实 → 规则/模型推理 → 可审计输出

适合任何需要准确性、责任链和合规性的场景。

**我应该记住什么：**  
> 不要让 LLM 同时承担“看清事实”和“解释事实”两个职责；先固化事实，再让它判断。

---

###### 洞见 3：置信度和引用不是锦上添花，而是进入生产系统的门槛

###### **核心观点：**  
> 在贷款审核这类场景中，提取结果必须带置信度和来源引用，否则无法安全进入自动验证环节。

**为什么重要：**  
文章轻描淡写提到：  
> 在生产系统中，任何低置信度提取结果都应该在进入验证步骤前标记给人工审核。

这是非常关键的一句话。

如果字段本身提错了，再聪明的 LLM 也只是在错误数据上做推理。  
例如：

- 工资单 gross pay 识别错；
- W-2 Box 1 金额提取错；
- 银行流水里的非工资存款漏掉；
- 雇主名称缩写被误判为不一致。

后续判断就可能全部偏离。

**反常识之处：**  
很多 AI demo 强调“自动完成流程”，但真实生产系统更需要的是：  
**知道什么时候不该自动完成。**

**可迁移价值：**  
可以形成一个通用门控机制：

- 高置信度字段 → 进入自动推理；
- 中等置信度字段 → 自动推理但标记；
- 低置信度字段 → 人工复核；
- 关键字段低置信度 → 阻断流程。

**我应该记住什么：**  
> 自动化不是消灭人工，而是把人工放在低置信、高风险、高异常的位置。

---

###### 洞见 4：LLM 的价值不是替代规则，而是处理“合理但需要解释”的灰区

###### **核心观点：**  
> Claude 没有简单地把 W-2 和工资单收入差异判断为错误，而是识别出“可能是年中加薪”，同时要求补充证明。

**为什么重要：**  
这展示了 LLM 相比传统规则引擎的优势。

传统规则可能是：

- 差异超过阈值 → 失败；
- 雇主名称不同 → 失败；
- 银行有额外存款 → 失败。

但贷款审核中的真实判断往往不是二元的，而是：

- 差异是否能被时间因素解释？
- 今年工资高于去年是否符合加薪逻辑？
- 银行存款中哪些是工资，哪些不是？
- 异常是否意味着欺诈，还是只需要补充材料？

Claude 的判断是：

> 收入总体一致，但 W-2 与当前工资差异需要加薪证明，额外 Zelle/Venmo 存款需要来源说明。结论：REVIEW。

这比简单 PASS/FAIL 更接近真实业务流程。

**可迁移价值：**  
在很多复杂业务中，真正有价值的不是自动给“通过/拒绝”，而是生成：

- 为什么通过；
- 为什么不能直接通过；
- 缺什么材料；
- 应该由谁处理；
- 下一步行动是什么。

**我应该记住什么：**  
> LLM 最适合处理“不是错，但需要解释”的业务灰区。

---

##### 3. 底层逻辑

###### **逻辑一：文档自动化的价值来自减少“核对成本”，不是减少“阅读成本”**

- 表层现象：  
  房贷处理员 40-60% 时间花在手动处理文件上，平均贷款档案超过 500 页。

- 深层原因：  
  工作量不是单纯阅读，而是反复核对：同一个收入、雇主、身份、存款来源是否在不同文件中一致。

- 推导结论：  
  真正值得自动化的不是“读 PDF”，而是建立一套跨文档一致性检查系统。

---

###### **逻辑二：生产级 AI 系统必须把“可解释性”设计进流程，而不是事后补救**

- 表层现象：  
  系统输出 HTML 报告，包含置信度、引用来源、验证表格、决策建议。

- 深层原因：  
  贷款审核是高风险、强合规场景。结论必须可追溯，否则无法被处理员、核保人员或审计人员接受。

- 推导结论：  
  AI 输出不能只是答案，还必须包含证据、来源、置信度和下一步建议。

---

###### **逻辑三：LLM 的最佳位置是“结构化数据之后，业务决策之前”**

- 表层现象：  
  文章没有让 Claude 直接处理原始 PDF，而是让 Extract 先输出 JSON，再交给 Claude 判断。

- 深层原因：  
  LLM 擅长关系推理、异常解释和自然语言判断，但不应该承担所有基础解析工作。

- 推导结论：  
  高可靠 AI 工作流应采用分层架构：  
  **解析层 → 事实层 → 推理层 → 审计层。**
