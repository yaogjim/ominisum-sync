**知识要点**

- 块扩散草稿模型可一次并行生成 16 个 token，再由目标模型单次前向验证实现无损推测解码

#### dflash-mlx

DFlash speculative decoding for Apple Silicon  
苹果硅上的 DFlash 推测性解码

Paper: [DFlash: Block Diffusion for Flash Speculative Decoding](https://arxiv.org/abs/2602.06036) (Chen et al., 2026)  
论文： [DFlash：块扩散用于 Flash 推测性解码](https://arxiv.org/abs/2602.06036) （Chen et al., 2026）

Block-diffusion draft generates 16 tokens in one pass. Target verifies in one pass. Output is lossless — every emitted token is verified against the target model before it is committed.  
Block-diffusion 草稿一次生成 16 个 token。目标在一次过程中验证。输出是无损的——每个发出的 token 在提交前都会与目标模型进行验证。

qwen-3.5-4B.mp4

- A small draft model (\~1B params) generates 16 tokens in parallel with block diffusion.  
  一个小型草稿模型（约 10 亿参数）通过块扩散并行生成 16 个 token。
- The target model verifies those 16 tokens in a single forward pass.  
  目标模型在单次前向传播中验证这 16 个 token。
- Greedy acceptance keeps the correct prefix and rejects the rest.  
  贪婪接受保留正确的前缀并拒绝其余部分。
- Lossless: every emitted token is the target model's greedy argmax at verification time. Output can still differ from pure AR because of MLX dispatch divergence, but no unverified token is ever emitted.  
  无损：每个生成的 token 在验证时都是目标模型的贪婪 argmax。由于 MLX 调度差异，输出仍可能与纯自回归（AR）不同，但绝不会生成未经验证的 token。
- Uses stock MLX plus a small number of targeted kernels where rollback and long-context verify need tighter numerical control.  
  使用标准 MLX，外加少量针对性内核，这些内核在回滚和长上下文验证时需要更严格的数值控制。

#### Technical details

- **Tape-replay rollback**: instead of snapshotting and restoring the full GatedDeltaNet state, dflash-mlx records an innovation tape during verify and replays only the accepted steps through a custom Metal kernel. Keeps rollback cost low and preserves acceptance over long generations.  
  **磁带重放回滚** ：dflash-mlx 不采用快照和恢复完整 GatedDeltaNet 状态的方式，而是在验证期间记录一条创新磁带，仅通过自定义 Metal 内核重放已接受的步骤。这保持了回滚成本低，并且在多代中保持接受度。
- **JIT SDPA 2-pass**: long-context verify (`N >= 1024`) uses a custom Metal attention kernel that stays numerically aligned with stock MLX attention.  
  **JIT SDPA 2-pass** ：长上下文验证（ `N ≥ 1024` ）使用了一个自定义的 Metal 注意力核函数，该核函数在数值上与标准 MLX 注意力保持一致。
- **Verify-specialized int4 qmm** (`verify_qmm`): custom Metal simdgroup-MMA kernel for the M=16 quantized matmul that dominates the target verify step. Two shape-adaptive variants (`mma2big`, `mma2big_pipe` with K-split + double-buffered staging). Auto-enabled on MoE targets and dense models with ≥40 layers where the M=16 specialization amortizes over enough layers to beat stock `mx.quantized_matmul` end-to-end. Opt-in override via `DFLASH_VERIFY_LINEAR={0,1}`.  
  **验证专用的 int4 qmm** (`verify_qmm`): 用于 M=16 量化矩阵乘法的自定义 Metal simdgroup-MMA 内核，该内核主导目标验证步骤。两种形状自适应变体（ `mma2big` 、 `mma2big_pipe` ，带有 K 分裂 + 双缓冲暂存）。在 MoE 目标和层数 ≥40 的密集模型上自动启用，其中 M=16 专用化在足够多层上分摊以击败标准 `mx.quantized_matmul` 端到端性能。通过 `DFLASH_VERIFY_LINEAR={0,1}` 可选覆盖。
- **Numerical coherence**: bf16-sensitive paths, including recurrent state replay and small projections, are stabilized across speculative cycles so accepted tokens stay consistent.  
  **数值一致性** ：bf16 敏感路径（包括循环状态重放和小型投影）在推测周期中得到稳定化，确保被接受的 token 保持一致。

Hardware: Apple M5 Max, 64GB unified memory. MLX 0.31.1 from the stock pip install.  
硬件：Apple M5 Max，64GB 统一内存。MLX 0.31.1，通过默认的 pip 安装。

Protocol: stock `mlx_lm.stream_generate` on a pristine target model vs stock MLX plus the local DFlash runtime, measured sequentially. `3` repeats, median reported, `60s` cooldown between measured runs.  
协议：未经过修改的目标模型上的原生 `mlx_lm.stream_generate` 与原生 MLX 加上本地 DFlash 运行时的对比，依次测量。重复 3 次，报告中位数，测量运行之间的冷却时间为 60 秒。

Generation: prompt `"The function $f$ satisfies the functional equation \[ f(x) + f(y) = f(x + y) - xy - 1 \] for all real numbers $x$ and $y$. If $f(1) = 1$, then find all integers $n$ such that $f(n) = n$. Enter all such integers, separated by commas. Please reason step by step, and put your final answer within \boxed{}."` with chat templates enabled by default and post-prefill tok/s as the primary metric.  
函数 $f$ 满足函数方程 \\\[ f(x) + f(y) = f(x + y) - xy - 1 \\\] 对所有实数 $x$ 和 $y$ 成立。若 $f(1) = 1$，求所有整数 $n$ 使得 $f(n) = n$。请将所有满足条件的整数用逗号分隔输入，并将最终答案放在 \\boxed{} 中。

## 通俗精炼（1）

#### DFlash-MLX 项目总结

##### 一句话概括
`dflash-mlx` 是一个面向 Apple Silicon 的推测解码方案，用更小的草稿模型先并行生成，再由目标模型一次性验证，在保证“输出不丢精度”的前提下，大幅提升大模型生成速度。

##### 项目核心价值
这个项目的重点，不是单纯“跑得更快”，而是实现了 **更快 + 尽量不牺牲结果可靠性**。  
它采用 DFlash 的 block diffusion 思路：草稿模型一次生成 16 个 token，目标模型再一次性验证这 16 个 token，只保留正确前缀，错误部分丢弃重算。

##### 技术亮点
###### 1. 无损推测解码
每个最终输出的 token，都会先经过目标模型验证后再提交，因此不会输出“未经确认”的内容。  
这意味着它本质上比普通 speculative decoding 更稳，更适合对结果一致性要求高的场景。

###### 2. 针对 Apple Silicon 深度优化
项目基于 MLX，同时补充了少量定制 Metal kernel，重点优化了：
- 长上下文验证
- 回滚过程
- int4 量化矩阵乘法

本质上，这是在苹果芯片上把“推测解码”做到了工程可用，而不是论文演示级别。

###### 3. 回滚机制设计很巧
它没有粗暴地保存和恢复完整模型状态，而是采用类似“磁带重放”的 rollback 方案：  
记录验证过程中的变化，只重放被接受的步骤，从而降低回滚成本，并提高长文本生成时的稳定性。

##### 性能表现
从基准测试看，这个方案在多种 Qwen 模型上都有明显提速：
- `Qwen3.5-4B`：最高约 `3.66x`
- `Qwen3.5-9B`：最高约 `4.37x`
- `Qwen3.5-27B-4bit`：最高约 `2.37x`
- `Qwen3.6-35B-A3B-4bit`：最高约 `2.20x`

整体规律是：
- **中小模型提速更明显**
- **上下文越长，收益会下降**
- **接受率大多在 86%~91% 之间**，说明草稿模型质量总体不错

##### 适用场景
这个项目特别适合：
- 在 Mac 上本地部署和推理大模型
- 做 OpenAI 兼容服务
- 接入 Open WebUI、Continue、aider 等工具链
- 对速度敏感、但又不希望明显牺牲输出质量的场景

换句话说，它更像是一个 **面向本地 AI 应用落地的推理加速层**。

##### 产品视角看它的意义
从产品和商业角度看，`dflash-mlx` 解决的是一个很现实的问题：  
**本地大模型体验的瓶颈，不是“能不能跑”，而是“能不能跑得足够快、足够稳”。**

它的价值主要体现在三点：
- **降低本地推理等待时间**，直接改善用户体验
- **提升 Apple Silicon 设备的模型实用性**，放大 Mac 作为 AI 终端的价值
- **为本地 Agent、IDE 助手、私有化部署提供更强基础设施**

##### 局限与边界
它并不是“通用万能加速器”：
- 目前主要为 `Qwen3.5 / Qwen3.6` 系列优化
- 需要匹配的 DFlash draft model，不是任意模型都能直接用
- 长上下文下速度增益会下降
- 某些输出仍可能和纯 AR 略有差异，但不会输出未验证 token

##### 结论
`dflash-mlx` 的本质，是把论文级的推测解码能力，做成了 Apple Silicon 上可落地的高性能推理方案。  
如果你关注 **Mac 本地跑大模型、推理加速、OpenAI 兼容服务化**，这是一个很有现实价值的项目。它不是简单的“再造一个推理框架”，而是在 **速度、精度、工程可用性** 三者之间找到了较好的平衡。

#### DFlash-MLX 内容总结

这个项目把论文中的 **DFlash 推测性解码** 落到 Apple Silicon 的 MLX 生态里，目标是在**保证输出“无损验证”**的前提下，大幅提升大模型生成速度。  
核心思路是：**小草稿模型一次并行生成 16 个 token，目标模型再一次性验证，只有验证通过的 token 才会真正输出。**

##### 1. 项目是什么：在苹果芯片上做“无损”的推测性解码

- `dflash-mlx` 是一个面向 **Apple Silicon** 的 DFlash 推测性解码实现，基于 **MLX**。
- 它对应的论文是 **《DFlash: Block Diffusion for Flash Speculative Decoding》(Chen et al., 2026)**。
- 方案中，**草稿模型约 10 亿参数**，可通过块扩散在一次前向中**并行生成 16 个 token**。
- 然后由目标模型在**一次前向**中完成对这 16 个 token 的验证。
- 系统采用**贪婪接受（greedy acceptance）**：保留正确前缀，拒绝后续不匹配部分。

**通俗理解：**  
这有点像“小助手先一次写出 16 个字，大模型老师再一次性检查”。检查通过的部分直接采用，不对的部分丢掉重来，因此速度更快，但不会把“没审核过”的内容发出去。

##### 2. “无损”具体是什么意思

- 项目强调其输出是 **lossless（无损）** 的。
- 含义是：**每一个最终输出的 token，在提交前都已经被目标模型验证过**。
- README 特别说明：每个发出的 token，在验证时都是目标模型的**greedy argmax**。
- 不过，结果**仍可能与纯自回归（AR）生成略有不同**，原因是 **MLX 调度差异（dispatch divergence）**。
- 但即便如此，也能保证：**绝不会输出未经验证的 token**。

**例子：**  
如果草稿模型一次猜出 16 个 token，其中前 10 个和目标模型一致，第 11 个开始不同，那么系统只会接受前 10 个，后面 6 个不会直接输出。

##### 3. 技术实现重点：如何把验证和回滚做快、做稳

###### 3.1 Tape-replay rollback：避免“整状态快照回滚”

- 传统做法可能要**保存并恢复完整的 GatedDeltaNet 状态**，代价较高。
- `dflash-mlx` 改成在验证时记录一条 **innovation tape（创新磁带）**。
- 回滚时不恢复整个状态，而是只通过自定义 **Metal kernel**，**重放已接受的步骤**。
- 好处是：
  - **降低回滚成本**
  - 在长生成过程中更容易保持较高接受率

**通俗理解：**  
不是每次都“整盘存档再读档”，而是只记“关键变化记录”，回滚时按记录快速重演。

###### 3.2 JIT SDPA 2-pass：长上下文验证更稳定

- 当长上下文达到 **N >= 1024** 时，项目会使用自定义 **Metal attention kernel**。
- 目的是让长上下文验证时的数值表现，尽量与原生 MLX attention **保持一致**。
- 这有助于减少长上下文下因为数值漂移带来的验证偏差。

###### 3.3 verify-specialized int4 qmm：针对验证阶段做矩阵乘法优化

- 项目为验证阶段中关键的 **M=16 量化矩阵乘法**，实现了自定义 **Metal simdgroup-MMA kernel**。
- 提供两种自适应变体：
  - `mma2big`
  - `mma2big_pipe`（带 `K-split + double-buffered staging`）
- 它会在以下场景自动启用：
  - **MoE 目标模型**
  - **层数 >= 40 的稠密模型**
- 如果这些条件不满足，就退回到标准 `mx.quantized_matmul`。
- 也可以通过环境变量手动控制：`DFLASH_VERIFY_LINEAR={0,1}`。

###### 3.4 数值一致性优化

- 项目对 **bf16 敏感路径**做了稳定化处理。
- 重点包括：
  - 循环状态重放
  - 小型投影层
- 目的是让推测生成多个周期后，**被接受的 token 依然稳定一致**。

##### 4. 性能结果：速度明显提升，但长上下文下增益会下降

测试环境与方法如下：

- 硬件：**Apple M5 Max，64GB 统一内存**
- 框架：**MLX 0.31.1**
- 对比方式：
  - 基线：原生 `mlx_lm.stream_generate`
  - 对照：原生 MLX + 本地 DFlash runtime
- 每组测试 **重复 3 次**，取**中位数**
- 每次正式测量之间冷却 **60 秒**
- 主要指标是 **post-prefill tok/s**

###### 4.1 Qwen3.5-4B

- `1024 tokens`：**53.80 → 182.87 tok/s，3.40x**，接受率 **86.43%**
- `2048 tokens`：**53.90 → 188.70 tok/s，3.49x**，接受率 **87.70%**
- `4096 tokens`：**53.49 → 195.84 tok/s，3.66x**，接受率 **88.35%**
- `8192 tokens`：**53.28 → 160.51 tok/s，3.02x**，接受率 **87.30%**

**结论：**  
4B 模型上提升非常明显，最高达到 **3.66 倍**。

###### 4.2 Qwen3.5-9B

- `1024 tokens`：**30.95 → 135.34 tok/s，4.37x**，接受率 **89.55%**
- `2048 tokens`：**30.70 → 113.00 tok/s，3.65x**，接受率 **89.16%**
- `4096 tokens`：**30.56 → 94.59 tok/s，3.06x**，接受率 **88.31%**
- `8192 tokens`：**29.43 → 66.94 tok/s，2.22x**，接受率 **86.67%**

**结论：**  
这是表中提升最亮眼的一组，短上下文下最高达到 **4.37 倍**。

###### 4.3 Qwen3.5-27B-4bit

- `1024 tokens`：**33.55 → 79.02 tok/s，2.37x**，接受率 **90.04%**
- `2048 tokens`：**33.10 → 70.21 tok/s，2.12x**，接受率 **89.60%**
- `4096 tokens`：**31.47 → 55.68 tok/s，1.77x**，接受率 **88.38%**
- `8192 tokens`：**33.88 → 45.29 tok/s，1.34x**，接受率 **85.97%**

**结论：**  
模型变大后仍有收益，但加速倍数较 4B/9B 更低。

###### 4.4 Qwen3.5-35B-A3B-4bit

- `1024 tokens`：**143.03 → 248.85 tok/s，1.76x**，接受率 **89.26%**
- `2048 tokens`：**141.43 → 255.01 tok/s，1.81x**，接受率 **89.75%**
- `4096 tokens`：**141.49 → 216.47 tok/s，1.53x**，接受率 **88.50%**
- `8192 tokens`：**138.59 → 170.39 tok/s，1.22x**，接受率 **86.41%**

###### 4.5 Qwen3.6-35B-A3B-4bit

- `1024 tokens`：**138.26 → 300.33 tok/s，2.20x**，接受率 **91.02%**
- `2048 tokens`：**139.03 → 252.93 tok/s，1.82x**，接受率 **89.60%**
- `4096 tokens`：**134.50 → 208.40 tok/s，1.56x**，接受率 **88.43%**
- `8192 tokens`：**133.20 → 177.45 tok/s，1.33x**，接受率 **87.01%**

**结论：**  
Qwen3.6-35B-A3B-4bit 在 `1024 tokens` 时达到 **300.33 tok/s**，是表中很突出的速度数据。

###### 4.6 总体趋势

- **短上下文时收益更大**，例如 4B、9B 在 1024~4096 token 时可达到 **3x~4x+**。
- **上下文越长，加速倍数越容易下降**，例如 8192 token 时不少模型降到 **1.2x~3x** 区间。
- 接受率整体较稳定，大多在 **85%~91%** 之间。
- README 路线图也说明，后续重点之一就是提升 **4096+ token** 场景下的持续接受率。

##### 5. 使用方式：既能命令行生成，也能作为兼容 OpenAI 的服务

###### 5.1 安装

- 可直接安装：
  - `pip install dflash-mlx`
  - 或 `pipx install dflash-mlx`

###### 5.2 命令行生成

- 自动解析草稿模型：
  ```bash
  dflash --model Qwen/Qwen3.5-9B --prompt "$PROMPT"
  ```
- 手动指定草稿模型：
  ```bash
  dflash --model Qwen/Qwen3.5-9B --draft z-lab/Qwen3.5-9B-DFlash --prompt "$PROMPT"
  ```

###### 5.3 启动服务

- 提供 `dflash-serve`，封装 `mlx_lm.server`
- 兼容 **OpenAI 风格接口语义**
- 支持：
  - tools
  - reasoning
  - streaming

例如：

```bash
dflash-serve --model Qwen/Qwen3.5-9B --port 8000
```

如果模型支持“思考”但你不想显示，可传：

```bash
--chat-template-args '{"enable_thinking": false}'
```

###### 5.4 生态兼容性

README 明确提到，可配合以下客户端使用：

- Open WebUI
- Continue
- OpenCode
- aider
- 其他 OpenAI-compatible 客户端

##### 6. 支持的模型与适用范围

- 原则上，**只要 HuggingFace 上有对应的 DFlash draft 模型，就应该可以工作**。
- 当前尤其针对以下模型优化：
  - **Qwen3.5**
  - **Qwen3.6**
- 原因是这两类模型属于 **GatedDeltaNet + attention 混合架构**，可以更好利用磁带重放回滚的精度优势。
- **Qwen3 纯 attention** 模型也能跑，但**拿不到 tape-replay rollback 带来的精度收益**。

README 给出的典型目标模型与草稿模型配对包括：

- `Qwen/Qwen3.5-4B` → `z-lab/Qwen3.5-4B-DFlash`
- `Qwen/Qwen3.5-9B` → `z-lab/Qwen3.5-9B-DFlash`
- `mlx-community/Qwen3.5-27B-4bit` → `z-lab/Qwen3.5-27B-DFlash`
- `mlx-community/Qwen3.5-35B-A3B-4bit` → `z-lab/Qwen3.5-35B-A3B-DFlash`
- `mlx-community/Qwen3.6-35B-A3B-4bit` → `z-lab/Qwen3.6-35B-A3B-DFlash`

另外：

- 如果没有匹配的 DFlash draft，系统会**直接拒绝运行**
- 若想覆盖默认注册表，可显式传入 `--draft`

##### 7. 项目功能特点

README 总结的主要特性包括：

- **自动草稿模型解析**：通常不需要手动传 `--draft`
- **流式输出**：CLI 和服务端都支持逐 token 输出
- **聊天模板默认开启**
- **循环回滚缓存**：通过 `RecurrentRollbackCache` 保持推测验证和回滚过程中的状态一致
- **验证专用 int4 qmm 内核**：在合适模型上自动启用，不合适时自动回退

##### 8. 后续规划

项目路线图重点提到两件事：

- **提升 4096+ token 场景下的持续接受率**
  - 包括草稿 KV cache 窗口扩展
  - 长上下文验证优化
- **草稿模型蒸馏与压缩**
  - 目标是让草稿模型前向更快，从而进一步提高整体生成速度

##### 9. 一句话结论

`dflash-mlx` 的价值在于：它不是单纯追求“更快生成”，而是在 **Apple Silicon + MLX** 上实现了一个**经过目标模型逐步验证、可保持无损输出**的推测性解码系统。  
从实测看，它在 Qwen3.5/3.6 系列上已经能带来 **约 1.2x 到 4.37x** 的加速，尤其在中短上下文场景下效果最明显。
