## 结构化（1）

### 2026-09-17 03:07:58

#### Claude Code 团队的工作方式：从 “写代码” 转向 “交付目标”

Claude Code 团队正把 AI 编程从逐步下指令、检查每次操作，升级为直接交付目标，让智能体自主获取上下文、执行任务并验证结果。与此同时，他们必须不断调整甚至删除旧功能，以适应几个月就发生明显变化的模型能力。

##### 1. 从分配小任务，转向交付完整目标

早期使用 Claude Code，开发者常让它 “实现一个类” 或 “写一个函数”，并持续反馈、确认权限。现在，团队更多通过**Claude Tag**—— 一个运行在 Slack 中的智能体 —— 处理更复杂、更长期的工作。

Claude Tag 能读取 Slack 里的产品背景、团队讨论和历史决策，因此不只理解代码，还能结合 “产品为什么这样设计” 来判断。团队成员表示：

- 约**70%—80%**的工作已在 Claude Tag 中完成；
- 剩余工作才会在终端界面（TUI）或桌面应用中细调；
- 关注点从 “模型每一步调用了什么工具”，转向 “最终是否达成目标”。

Claude Tag 已被用于头脑风暴、监控、验证和代码审查等多个环节。

##### 2. 模型快速进步，辅助功能也必须随时淘汰

传统软件的底层技术往往几年才明显变化，而团队认为，AI 模型的能力可能每两个月就发生一次重要变化。这带来两项同时存在的要求：

1. 为当下模型提供真正有用的功能；
2. 提前探索更强模型出现后，产品应该如何工作。

例如，Sonnet 3.5 时代的模型难以完成长期任务：给它五件事，可能做完三件就停下。因此团队加入了 “待办清单”，帮助模型持续执行。但一年后，随着模型拥有更好的记忆和状态管理能力，这项功能已不再必要。

团队由此形成一个原则：**不要依恋已经开发的功能。** Claude Code 的许多 “脚手架” 只是为了弥补当前模型的缺陷；模型能力提升后，应及时删除它们，再针对更大、更复杂的任务提供新工具。

##### 3. 先构建基础能力，再让它们组合成新交互

团队会先开发权限、提问、可视化等基础模块，再让这些模块相互组合。

“AskUserQuestion” 工具就是一个例子。它最初用于让 Claude 在制定计划后主动询问用户，但工具设计和调用方式曾很难调好。模型进步后，Claude 已能熟练提问；进一步地，团队成员现在甚至更常让它生成一个 HTML “产物”，其中直接包含问题、图表和界面原型，供用户查看和反馈。

这说明产品交互并非固定不变：同一个需求可能依次经历 “专用工具 — 成熟调用 — 更丰富的可视化产物” 等形式。

##### 4. 从本地会话，发展到云端持续运行

智能体最初运行在个人电脑上，一旦合上电脑或离开办公室，任务就会中断。团队随后经历了以下演变：

1. 在远程开发机上运行，避免依赖本地电脑；
2. 通过 SSH 进入远程环境，但操作仍不方便；
3. 使用网页版 Claude Code 和托管容器，让任务持续在后台执行。

虽然给云端容器配置开发环境访问权限较麻烦，但一位团队成员称，这种方式让自己的生产力提高了约**10 倍**。

云端运行进一步催生了 “循环” 和 “例行任务”：用户不必每次开启一个会话，而可以设定更高层的长期目标。例如，让 Claude 每天整理用户反馈、按重要性分类，并自动修复它有较高把握解决的问题。AI 因而从一次性响应提示，变成持续执行工作的后台智能体。

##### 5. AI 处理细节，人类审查整体设计

随着 AI 生成的代码增多，如果人类仍逐行检查，代码审查会成为新的瓶颈。团队认为，Claude 更适合自动发现和修正细小问题，让人类把精力放在更高层的判断上。

传统审查中，评审者有时会提出几个小问题，以证明自己认真读过代码。现在，这类细节可以交给 Claude；人类更应关注：

- API 为什么采用这种结构；
- 服务边界为什么划在这里；
- 代码是否符合团队长期架构和产品意图；
- AI 是否遗漏了未写进代码库的背景知识。

团队还会让多个推理分支并行寻找潜在缺陷，再汇总结果。这种通过增加推理阶段的计算量来提高质量的方法，被称为**“测试时计算”**。代码审查中的这种 “并行展开再汇总” 模式，也成为其后续工作流设计的重要来源。

##### 核心逻辑

整套工作方式的演进可以概括为：

**模型能力提升 → 开发者减少逐步控制 → 任务从本地单次会话迁移到云端持续执行 → AI 承担实现和细节检查 → 人类转向目标设定、产品背景与架构判断。**

团队的关键经验不是建立一套永久不变的流程，而是持续根据模型能力重做工具、工作流和人机分工。

## 深度解读（1）

### 2026-09-17 03:09:36

#### Claude Code 的真正变化：从 “帮我写代码” 到 “替我持续完成目标”

Claude Code 团队成员称，自己已有**70%—80% 的工作在 Slack 原生代理 Claude Tag 中完成**，终端和桌面端反而只用于少量精修。这不是简单的入口迁移：过去人盯着每次工具调用、不断确认权限；现在，人给出目标，代理自行寻找产品背景、执行任务并接受验证。

这段访谈最值得关注的，是它展示了智能体产品如何同时改变软件形态、产品策略和人的职责。

##### 智能体的核心单位正在从 “会话” 变成 “持续运行的工作流”

单次对话天然要求人在线：提供上下文、纠偏、确认，然后结束。Claude Code 团队经历的演化是从本地终端，到远程开发机，再到云端容器和定时 routines。环境一旦能够持续运行，代理就可以每天读取反馈、判断优先级，并尝试修复高置信度问题。

因此，真正拉开差距的未必是更好的聊天界面，而是能否形成完整闭环：**长期获得上下文，安全调用工具，执行后验证，失败时升级给人。** Slack 的价值也不只是方便，而是其中沉淀了讨论、决策和产品语境，让代理知道 “为什么这样做”，而不只知道代码怎么改。

这可以迁移到更多知识工作。客服分析、运营巡检、研究监测的产品机会，都不应只问 “模型能否完成一次任务”，而应验证：它能否在持续变化的环境里，稳定决定何时行动、何时询问、何时停止。

##### AI 产品必须区分 “长期基础设施” 和 “模型缺陷补丁”

早期模型无法完成长链路任务，团队便加入待办清单，防止它做五件事却只完成三件。模型进步后，这项能力又变得多余。AskUserQuestion 也经历了类似变化：先被精心设计成专门工具，后来模型可以直接生成带图表、原型和问题的交互式 artifact。

这给 AI 产品一个反常规要求：**不要把现阶段的模型缺陷误认为永久用户需求。**待办清单、提示模板和复杂编排可能只是临时脚手架；权限、上下文接入、可视化、执行环境与验证机制则更可能长期存在。团队甚至需要主动删除曾经有效的功能，把复杂度预算让给更大范围的新任务。对路线图而言，功能保留率不再天然代表产品成熟度，能否随着模型能力重划边界反而更重要。

##### 代码更多以后，稀缺资源变成判断力

生成量上升并没有让审查消失，只是改变了审查重点。模型可以处理格式、小错误和大量候选缺陷搜索，人则应集中判断 API 为什么这样设计、服务边界是否合理，以及某项修改是否符合长期产品意图。换言之，人的价值从逐行检查转向**选择审查焦点、补充隐含约束并承担最终责任**。

不过，这些结论来自前沿团队的自述，“效率提升 10 倍” 也只是个人体验，不能直接外推到普通组织。其成立依赖代码库可访问、测试充分、权限可控和团队知识已经数字化。真正值得验证的不是员工是否开始大量使用智能体，而是：**在提高产出的同时，返工率、缺陷逃逸率和关键决策质量是否同步改善。**

## 口播总结（1）

### 2026-09-17 03:14:14

Claude Code 团队的工作方式，正在发生一个关键变化：他们不再盯着人工智能执行每一个工具调用，而是把完整目标交给它。人的注意力，则从逐行操作，转向目标设定、背景判断和最终验证。

团队成员说，现在大约百分之七十到百分之八十的工作，都通过 Claude Tag 完成。Claude Tag 是一个运行在 Slack 里的智能代理。只有剩下的一部分工作，才需要回到终端或桌面应用里，亲自调整细节。

过去，交给 Claude Code 的任务通常很小，比如实现一个类，或者编写一个函数。现在，团队会给它更复杂、更长期的目标。Slack 在这里很重要，因为大量产品讨论、团队决策和历史背景，本来就保存在聊天记录中。Claude Tag 可以主动查找这些上下文，理解团队为什么做出某项选择，再据此完成任务。

这意味着，人和人工智能的协作单位变了。过去，人们关心提示词怎么写，模型调用了什么工具，每一步判断是否正确。现在，团队更常采用一种拉远视角的方式：我想实现什么结果？需要满足哪些条件？然后把这个目标交给模型。

不过，这种工作方式建立在一个特殊前提上：底层模型进步得非常快。传统软件的基础技术，往往能稳定几年。人工智能模型的能力边界，却可能每两个月就发生一次明显变化。产品团队一方面要服务今天的用户，另一方面又必须提前判断，下一代模型会让哪些功能变得多余，又会带来哪些新的可能。

待办事项功能就是一个典型例子。早期模型很难完成跨度较长的任务。你给它五件事，它可能做完三件就停下。于是团队加入待办清单，帮助模型记住剩余步骤。这个设计在当时效果很好，正好弥补了模型的短板。

但一年之后，更强的模型已经能够依靠更复杂的记忆状态维持任务连贯性。原来的待办清单，也就不再那么必要。

这给产品设计带来一个反常识的原则：不要过度依恋自己开发的功能。Claude Code 外围的很多机制，本质上是在补偿当时模型的不足。模型变强以后，团队就应该删除已经失去价值的机制，而不是因为投入过时间，就继续保留。

当然，模型能力提升，并不意味着外围工具全部消失。真正发生的变化是，旧工具退出，新工具开始服务更大、更复杂的任务。问题不再是，怎样帮助模型记住五个步骤，而是怎样让模型在更长的任务中保持连贯，正确使用背景信息，并持续验证结果。

“向用户提问” 这个功能，也体现了同样的演变。团队最初希望 Claude 在制定计划后主动提问，以澄清需求。后来，他们把提问设计成一种可以随时调用的工具。光是让模型在正确时机使用这个工具，就花了很长时间。

但模型很快又进步了。现在，团队成员有时不再使用专门的提问工具，而是让 Claude 生成一个可交互的网页式成果，其中可以包含问题、图表和界面草图。用户直接在这个成果中反馈。原本勉强能完成的单一操作，很快演化成了更丰富的交互方式。

这说明，真正耐用的设计不一定是某个固定功能，而是一些可以组合的基础能力，比如权限控制、提问、可视化和成果展示。模型能力变化时，这些基础能力可以重新组合，形成新的工作流程。

另一个重要变化，是 Claude 从本地电脑转移到了云端。最初，智能代理运行在工程师的笔记本上。工程师下班合上电脑，任务也就停止了。后来，团队使用远程开发环境，让代理继续运行。但每次都要远程登录，也比较麻烦。于是，他们进一步把开发环境放进云端容器，让 Claude Code 可以在网页上持续工作。

一位团队成员估计，这种改变让自己的生产力提升到了原来的十倍。更关键的是，云端运行打破了 “一次对话就是一次任务” 的边界。

有了持续运行的环境，工程师可以设置固定流程。比如，每天自动查看用户反馈，把问题按重要程度分类，再处理那些模型有较高把握可以修复的问题。这不再是人发出一次提示，模型完成一次回答，而是人定义一个更高层的循环，让模型定期观察、判断和行动。

代码审查也因此发生了变化。生成的代码越来越多，如果工程师只是逐行寻找格式问题或小瑕疵，审查工作很容易变成新的瓶颈。

传统代码审查里，审查者有时会挑出三处很小的问题。这些意见未必最重要，却能表明自己认真读过代码。现在，这类细节可以由 Claude 自动发现和修正。人类审查者则把精力放到模型不一定充分理解的问题上。

例如，为什么某个应用程序接口要采用这样的结构？为什么两个服务的边界画在这里？这些选择可能来自长期的产品考虑、系统约束或团队经验。人工智能可以先收集相关背景，把值得关注的信息交给人类。但最终，人类需要从更高层判断，整个设计是否合理。

为了寻找潜在缺陷，团队还会让多个分析分支同时检查同一个问题，再把结果汇总。这种方法叫作测试时计算。简单说，就是在得到最终答案之前，投入更多推理时间和计算资源，从多个方向搜索风险。代码审查中的这种并行探索，也推动了更动态的自动化工作流。

最值得记住的是，人工智能编程的变化不只是 “代码写得更快”。真正的转变，是工作层级正在上移：从下达具体任务，变成设定目标；从盯住每一步，变成设计验证和反馈循环；从逐行挑错，变成判断架构、边界和产品意图。

而在模型快速进步的环境里，好的工具也不应该一成不变。今天必要的功能，可能只是暂时的脚手架。模型能力改变以后，团队要敢于拆掉旧脚手架，再为更大的任务建立新的工作方式。

这些背景很重要。以前，开发者可能让模型“实现一个类”或者“写一个函数”。现在，他们交给模型的问题更复杂，也更接近一个完整目标。模型要做出合理选择，就不能只知道代码长什么样，还需要知道团队想解决什么问题。

不过，想把这种工具做好，有一个特殊难题：底层模型进步得太快，今天很有价值的功能，过一阵子可能就不再需要。

团队成员的感受是，传统软件依赖的技术，往往几年才发生一次重要变化。人工智能模型却可能每两个月就显著改变一次。开发者既要解决用户今天的问题，又不能把产品牢牢绑在模型今天的局限上。

待办清单就是一个具体例子。早期模型不擅长持续完成较长的任务。交给它五件事，它可能做完三件就停了。团队于是加入待办清单，帮助模型记住还有哪些工作没完成。在当时，这个办法非常有效。

所以，团队强调，不能太依恋自己做出来的功能。有些功能，本质上是给当前模型补短板。短板消失了，补丁也应该允许被删掉。与此同时，任务变得更大、更难，又会需要新的支持工具。

不过，代码生成得更多，并不意味着人的判断可以省掉。接下来的问题是：代码审查应该把注意力放在哪里？

团队认为，模型可以帮助人类审查者，把时间用在更重要的地方。传统审查里，有时会出现这样的情况：审查者逐行阅读，挑出几个小问题，也借此表明自己确实认真看过代码。

现在，这类细小问题可以更多地交给模型发现和处理。人的价值，则更集中在整体设计上。

例如，一个程序接口为什么要这样设计？两个服务之间的职责边界，为什么划在这里？这些选择可能有历史原因，也可能来自产品约束。模型写代码时，未必已经充分理解了这些背景。

因此，模型不仅可以找问题，还可以把相关背景整理出来，交给人判断。人类审查者不必一直陷在逐行挑错里，而可以关注代码有没有违背更大的设计意图。

团队还提到，为了寻找潜在缺陷，他们会让多个检查任务并行展开，再把结果汇总。这种做法，相当于在审查阶段投入更多计算和推理，也成为他们探索工作流的重要起点。

这段分享最值得记住的，不是某个工具按钮，而是开发者角色的变化：把目标和背景交代清楚，让模型承担更多执行，再把人的注意力留给关键判断。同时，工具也要保持可变；为旧模型补短板的功能，不应成为新模型前进的负担。
