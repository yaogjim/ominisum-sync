**Yanhua**

### 把 Claude Code 的记忆，搬进了我的 Obsidian

我用 Obsidian 管了三年知识库，整个第二大脑就是一堆 .md 加一个 git 仓库，能搜、能改、能看每条是什么时候写的。

这周我做了件一直想做的事：让 Claude Code 的记忆，也变成我能在 Obsidian 里打开的 .md。

#### 每开一个新窗口，它都是个陌生人

用 AI 写代码这半年，最磨人的不是它不够聪明，是它不记事。

每开一个新 session，我都得从头来：这是哪个项目，技术栈是什么，上次我们定了什么，哪条路我已经说过别走。它每次都很能干，但每次都把我当成第一次见的人。

我的笔记记得我，我的 Agent 不记得。

#### EverOS 把 Agent 的记忆，存成了本地的 .md

最近接触到 EverOS 1.0.0，

[@evermind](https://x.com/@evermind) 团队开源的一个 Agent 记忆框架。它最戳我的一点是：记忆不进某个黑盒向量库，而是落成你本地的 Markdown 文件。

一行命令安装：

```text
pip install everos
```

填两个 key（一个管抽取的 LLM，一个管检索的 embedding），然后启动：

```text
everos server start
```

服务就在 127.0.0.1 上跑起来，数据放在本机的 \~/.everos 目录。

#### 官方的集成是云端的，所以我自己接了一条到本地

这里有个坑得说清楚，EverOS 现成的 Claude Code 集成是走云端的，对话会发去它们的服务器。

那不是我要的，我要的是本地、我自己硬盘上的 .md。

所以我干脆用 Claude Code 的 hook 自己接了一条到本地服务，逻辑很轻：

我提交 prompt 时，一个 hook 去本地召回相关记忆塞进上下文；它答完，另一个 hook 把这一轮写回本地。一百来行，指向 127.0.0.1:8000，没有一个字节存到我机器之外。

挂上之后，终端每轮会闪一句“已把本轮写入本地记忆”。

![Image](https://pbs.twimg.com/media/HLYUfRKaEAA38oq?format=jpg&name=large)

#### 打开 \~/.everos，记忆就是一棵我能读的 .md 树

第一件让我上头的事，是我把 \~/.everos 直接在 Obsidian 里打开了。

![Image](https://pbs.twimg.com/media/HLYUj-xboAAAD1g?format=jpg&name=large)

它把我和 Claude Code 的对话抽成了一篇结构化的 .md：顶上一段 YAML frontmatter，owner\_id 是我，下面是 Subject、Summary、Content，这就是它的记忆本体。

我能 grep，能 git diff，能像翻自己笔记一样翻阅它。

#### 真正让我坐住的，是换个窗口它还记得

存得好看只是第一步，我想知道的是，跨 session 它到底记不记得。

我开了个全新窗口，在一个跟项目无关的空目录里，只问了一句“上次我让你之后用什么语言回我”。

![Image](https://pbs.twimg.com/media/HLYUpWxbkAAOkTD?format=jpg&name=large)

它没翻任何文件，直接答“中文”，还补了一句“上次（6月20日）你明确让我用中文回复，我之后就一直用中文了”。这条信息在任何代码里都查不到，只可能来自记忆。

更狠的是下一个窗口。

我只说“帮我想想 reddtrends 下一步加个什么功能”，没给任何背景。它用中文回我，还主动加了一句“不碰已废弃的 trends-pipeline”。

那条链路是我上一个 session 跟他沟通的，这次我一个字没提。

![Image](https://pbs.twimg.com/media/HLYUw-pbcAABkA_?format=jpg&name=large)

到这它就不只是“记住了一个事实”，是记忆在指导它下一步怎么干。

它连我上次挖出来的细节都记得...

我再追了一个更具体的：上次你分析 reddtrends，发现 package.json 的测试脚本有什么问题。

![Image](https://pbs.twimg.com/media/HLYU37Sb0AAph3W?format=jpg&name=large)

它没去读代码，直接报出 5 个 test 脚本全是死引用，挨个点名，说它们指向的 scripts/ 目录在 HEAD 里已经不存在，还记得是哪次 commit 删的。

这里有我自己的功劳，也有我自己的坑。一开始我那个召回 hook 写得太浅，只把每条记忆的短摘要塞回去，结果它召回总是很空，只知道我们讨论过测试脚本，却说不出结论。

我把 hook 改成注入完整正文之后，这些细节才出来。还是需要自己搭、自己调，这种东西不折腾一版是不会跑那么顺的。

#### 一个反而让我更信它的发现

不是每次都这么顺。我中途问过它一个代码里查得到的硬事实：reddtrends 的定时任务到底用 Vercel Cron 还是 GitHub Actions。它召回了线索，但还是跑去把代码重读了一遍才回答。

![Image](https://pbs.twimg.com/media/HLYVCufaIAAeu7e?format=jpg&name=large)

一开始我以为是记忆没用。后来想想就明白了，这恰恰是对的：一个够强的 Agent，对能在源码里核实的硬事实就该去核实，记忆只是它的快速先验，不是它认的最终真相。

这也正好对上 EverOS 自己的设计：Markdown 是真相源，索引和记忆是从它派生出来的。

所以这套东西真正有意思的，不是替 Agent 记住代码里查得到的事实，是替我记住代码里查不到的东西：我的偏好、我们的决定、我定的约束。

#### 它存了什么，我又没去验什么

边界说清楚。

我亲手验过的：记忆是本地可读的 .md，我在 Obsidian 里打开、读，它跨 session 跨项目地记得我的偏好和决定。这几条是实打实的。

我没细抠的：官方说删掉索引能从 .md 整棵重建、能直接手改 .md 让记忆生效，还有 Agent 侧从重复任务里自进化出 skill。这些设计我信，但这一轮没逐条压测，就不替它打包票。

还有一条别被“本地”二字骗了：数据和索引确实都在本机，但抽取记忆要调 LLM、检索要算 embedding，这两步会联网。本地指的是你的记忆资产在你手里，不是全程离线。

#### 太长不看

以前每开一个新窗口，都是初次见面。现在它接着上次的话往下说。

对一个把整个第二大脑都放进 Markdown 的人来说，这件事的意义不只是省事。它意味着我的 Agent 记忆，是我硬盘上一堆能打开的 .md，不是某个我注销账号就蒸发的黑盒。

如果你也在做需要长期记忆的 Agent 或 LLM 应用，这个 repo 值得你点一下 Star，存下来再说。

[https://github.com/EverMind-AI/EverOS](https://github.com/EverMind-AI/EverOS)

##### 二、深入浅出解读

这篇文章讲的不是「AI 更聪明了」，而是：

> AI 开始有了你能掌控的长期记忆。

以前用 Claude Code 像请一个很强的临时工：

- 每次都很能干；
- 但每次都要重新交代背景；
- 它不知道你之前说过什么；
- 也不知道哪些路你已经否定过。

而作者做的事，相当于给这个临时工配了一本工作笔记。

更关键的是，这本笔记不是平台私有的，而是：

- 存在自己电脑上；
- 是普通 Markdown 文件；
- 能用 Obsidian 打开；
- 能搜索、修改、版本管理；
- 不会因为某个账号注销就消失。

这其实把 Agent 记忆从「平台能力」变成了「个人资产」。

###### 为什么这件事重要？

因为真正影响协作效率的，往往不是单个问题的答案，而是连续上下文：

- 我喜欢什么风格；
- 这个项目之前怎么定的；
- 哪些方案已经试过；
- 哪些文件已经废弃；
- 哪些坑不要再踩；
- 哪些原则必须遵守。

这些东西通常不在代码里，却决定了 AI 是否真的“懂你”。

###### 1. 记忆可见

不是藏在向量库里，而是 Markdown。

这意味着用户可以知道：

> AI 到底记住了什么。

###### 2. 记忆可控

用户可以用 Obsidian、grep、git 等工具管理记忆。

这比纯黑盒记忆更可信。

###### 3. 跨 session 连续性

AI 不再每次都从零开始，而能接着上次继续。

这对长期项目尤其重要。

###### 4. 人的偏好被沉淀

代码可以查，偏好和决策查不到。

##### 四、辩证思考

###### 值得肯定的地方

这套方案抓住了 Agent 产品的一个关键方向：

> 未来的 AI 助手，不只是回答问题，而是持续理解一个人和一个项目。

而且作者选择 Markdown 作为记忆载体，非常符合「长期知识资产」的逻辑：

- 开放；
- 简单；
- 可迁移；
- 可审计；
- 不绑定平台。

这比把记忆锁进某个 SaaS 黑盒更健康。

---

###### 需要警惕的地方

但「记忆」不等于「真相」。

AI 记住的内容可能：

- 过期；
- 片面；
- 抽取错误；
- 被错误召回；
- 和当前代码状态冲突。

所以理想机制应该是：

> 记忆负责提示方向，源码和事实负责最终确认。

作者提到 Agent 会重新读代码验证硬事实，这一点非常重要。

真正可靠的 Agent，不应该盲信记忆。

---

###### 还有一个隐私误区

“本地记忆”不等于“完全离线”。

虽然 Markdown 和索引在本机，但如果记忆抽取和 embedding 调用了云端模型，对话内容仍可能出本机。

所以用户需要分清：

| 概念 | 含义 |
|---|---|
| 本地存储 | 记忆资产在自己硬盘 |
| 本地运行 | 服务在本机启动 |
| 完全离线 | 不调用任何外部模型或接口 |

这三者不是一回事。

> 让 AI 的长期记忆成为用户可读、可改、可迁移的个人知识资产，而不是平台黑盒里的临时缓存。

Claude Code 没有重新读代码，而是直接回答：

- `package.json` 里有 5 个 test 脚本是死引用；
- 它们指向的 `scripts/` 目录在当前 HEAD 中已经不存在；
- 还记得是哪次 commit 删除了相关目录。

不过作者也提到，这个效果不是一开始就有的。

最初他的召回 hook 写得太浅，只注入每条记忆的短摘要，结果 Claude Code 只知道“讨论过测试脚本”，但说不出结论。

后来他把 hook 改成注入完整正文，细节才被召回出来。

这说明：

- EverOS 有用；
- 但接入方式也很关键；
- 需要自己搭建、调试，才能达到比较顺的效果。

---

##### 7. 记忆不是最终真相，硬事实仍应查源码

作者还发现一个让他更信任这套系统的现象。

他问了一个代码里可以查到的硬事实：

> reddtrends 的定时任务到底用 Vercel Cron 还是 GitHub Actions？

Claude Code 虽然召回了相关线索，但仍然重新读取代码后才回答。

作者一开始以为这是记忆没发挥作用，后来意识到这反而是正确行为：

- 对于源码中能验证的事实，Agent 应该去核实；
- 记忆只是快速先验，不应替代事实来源；
- 记忆适合保存代码里查不到的东西。

作者认为，这套系统真正有价值的地方，不是替 Agent 记住代码本身，而是记住：

- 用户偏好；
- 项目决策；
- 历史上下文；
- 已废弃方案；
- 用户设定的约束。

---

##### 8. 作者验证过什么，没验证什么

作者明确区分了自己已经验证和暂未验证的部分。

###### 已验证

作者亲自确认：

- EverOS 的记忆是本地可读的 Markdown；
- 可以在 Obsidian 中打开和阅读；
- Claude Code 能跨 session、跨项目记住用户偏好；
- 它能记住项目决策和历史约束。

###### 未深入验证

作者没有逐条压测官方宣称的一些能力，例如：

- 删除索引后，是否能从 `.md` 文件完整重建；
- 手动修改 `.md` 后，记忆是否能立即生效；
- Agent 是否能从重复任务中自进化出 skill。

作者表示这些设计他相信，但这一轮没有替它们背书。

---

##### 9. “本地”不等于“完全离线”

作者提醒，不要被“本地”两个字误导。

EverOS 的数据和索引确实都在本机，但两个环节仍可能联网：

- 抽取记忆需要调用 LLM；
- 检索需要计算 embedding。

所以这里的“本地”主要指：

> 你的记忆资产保存在你自己手里，而不是存在某个账号注销后就可能消失的黑盒服务里。

它不代表整个流程完全离线。

对作者这样把第二大脑放在 Markdown 里的人来说，这件事的意义不只是省事，而是：

- Agent 的记忆变成了本地文件；
- 可以用 Obsidian 打开；
- 可以被搜索、追踪、备份；
- 不依赖某个不可见的黑盒平台。
