## 分析要点

- **核心高价值点**：不要相信Agent的口头结论，只看它在真实环境中执行测试、压测和截图后产生的可验证证据。
- **留存建议**：长期保留（提供了AI辅助开发中从人工验收转向自动化验证护栏的完整实践思路，适合作为工作流改造参考。）

**知识要点**

- AI Agent可能写出与错误实现相匹配的测试，因此必须要求其在真实终端或真实浏览器中运行并给出原始输出。
- 后端应让Agent完成部署、集成测试、压测、日志查询、监控面板和告警配置，人只审查关键失败信号。
- 前端验证不能只看接口和日志，应通过浏览器自动化逐步操作并强制截图，人工快速检查页面真实状态。
- 通过MCP server、CI或skill把开发、部署、测试、压测、可观测性检查串联成可重复执行的harness。
- 传统企业系统即使缺少开放接口，也可利用browser use让Agent操作已有Web后台完成流程自动化。

**行动项**

- 为当前项目梳理开发后必须执行的部署、集成测试、压测、日志检查和监控检查清单。
- 将关键验收流程写成Claude Code skill或CI脚本，要求Agent每次修改后自动执行并贴出原始结果。
- 为后端接口补充真实HTTP集成测试，覆盖正常路径、边界条件、鉴权、重复提交和并发场景。
- 为前端接入Playwright MCP或浏览器自动化工具，并要求关键交互步骤输出截图供人工核验。
- 建立一套最小可用的可观测性面板，覆盖QPS、p99、错误率、内存、goroutine或同类核心指标。

## 正文

**zzxwill**

### AI 开发时代，别让自己困在「测试员」的角色里

三个月以前，我还困在测试员的角色里。\*\* 那会儿发过这么一条推文：

跟同事、朋友聊下来会发现，掉进这个坑的绝不只是一个人。几乎每个重度使用 Coding Agent 的开发者，都或多或少在里面待过。\*\*AI 正把大批工程师，从「写代码的人」推向「验代码的人」。\*\*

先回想过去一个后端功能是怎么开发的。写完 handler，打开 Postman 或者 curl，一个 endpoint 一个 endpoint 地敲：正常入参、边界值、非法 token、并发写同一个 key，敲完看返回码、看 body、看有没有脏数据。前端更原始，得把 dev server 起起来，在浏览器里一个按钮一个按钮点，点到样式错位、点到白屏、点到某个 state 没刷新。

这些活很琐碎，但是如果不细致测试的话，如果团队里有测试人员，被测试人员发现会尴尬；没有测试人员，被用户发现更尴尬。所以谁也躲不掉。

这三个月算是慢慢爬出来了。下面以 Claude Code CLI 为例，说一说这条可行的路。

在这之前，想推荐一本书：《持续交付》。早年在百度技术沙龙上提过一个问题，这本书的译者、当时在百度做交付的乔梁，送了我这本书。

这本书十几年前就把一件事讲清楚了：把构建、部署、测试全流程自动化，让流水线承担重复劳动，人只在真正需要判断的地方介入，这也是爬出泥潭的底层思路。

#### 后端开发

写后端代码，假设要写一个接口，跟 Agent 打交道，一定要记住：\*\*它会撒谎\*\*。这个撒谎分为两个层面。

第一，它真的会骗人。直到今天，最聪明的模型依然会骗人：它做完了功能，也写了测试用例，但这些测试用例测的正是它写错的那个功能。Anthropic 也发过模型有 depression level，反复尝试后会失落放弃，然后告诉你它做完了。

第二，理解不一致。它理解的需求可能跟输入并不一致，它按自己的理解做完了，这在某种程度上也算撒谎。

所以不要看它的结论，只看它的证据。让它写完功能，把集成测试一起写了，然后必须在真实终端里跑一遍，把原始输出整段贴出来：

```shell
$ go run ./cmd/api &
2026/07/05 14:02:11 api listening on :8787

# 再让集成测试对着活着的接口打真实 HTTP 请求
$ go run ./test/integration -base http://localhost:8787

[PASS] POST /api/auth/request   mint token & send magic link          (200)
[PASS] GET  /api/auth/verify    consume token, set session cookie      (200, Set-Cookie: session=...)
[FAIL] GET  /api/auth/verify    reuse the SAME token a second time
       expected 401, got 200 — one-time token was replayed!
[PASS] GET  /api/books          list all 29 books                      (200, len=29)

--- 3 passed, 1 FAILED against http://localhost:8787
exit status 1
```

那个 \[FAIL\] 就是要看的。同一个一次性 token 用第二次，居然还返回 200，说明它压根没失效，这是个 bug。可 Agent 刚才还说「测试通过」。把这行贴回去让它改，它改完自己重新 go run 起服务再跑一遍，反复几次，直到全部 \`PASS\`。这一圈 curl 测接口、比对返回码的活，以前得一个个手敲，现在它自己干；人只盯着 PASS 和 FAIL 那一列，有 FAIL 就打回去。

对于复杂系统，失败了要可以查询后端日志，这个也至关重要。

但功能跑通不等于压测能过，Claude Code CLI 很擅长做压力测试，并发、QPS 这些场景都可以让它构建出来，并且这个过程中的各种观测值都可以收集到：看 p99 有没有飙、错误率高不高、goroutine 会不会只涨不掉、内存压完了能不能回落。功能测试只能说明它现在是对的，压测才知道它顶不顶得住。

监控也不必自己配了。以前搭 Grafana 面板挺磨人，一个指标拖一个 panel，query 一条条填。现在直接让 Agent 去弄，它把 Grafana 那套 JSON 自己写好、自己导入。等服务跑起来，QPS、p99、错误率、goroutine 数、GC 停顿这些 panel 都准备好了。

部署、跑测试、压测、配监控（包括配置告警），这些以前最耗时间的活，这一整轮下来基本没动手，都是它在跑。人做的就是最后扫一眼那几行输出、几张图，看对不对。

到这里，开发、部署、测试、查日志、做压测每一步都自动化了，但怎么把它们完整地连起来？

能被 AI 识别的入口是 MCP server、CI 和 skill，用一个 skill 把整个过程写下来最合适。这个 skill 比较简单，就是告诉它：

1. 开发完之后怎么做部署；
2. 部署完之后怎么做测试；
3. 怎么检查可观测性是否完整；
4. 怎么做压测。

整个过程全部完成，就代表这个 skill 执行成功；没完成，就继续调整整条流程，直到成功。

Skill 本质上就是一堆文本 prompt，里面需要的执行文件让 AI 帮忙写，这个不难。

#### 前端开发

前端其实是一样的路子。开发、部署、测试、debug，跟后端一整套流程完全一致。不过在动手之前，得先给 Claude Code 准备一样东西：一个能让它自己开浏览器的工具。这里用的是 Claude in Chrome 这个 Chrome 插件，装上之后 Agent 就能直接驱动浏览器去点、去输、去截图。如果公司对装插件卡得比较严，那就把 Playwright 的 MCP server 配好，效果一样。这几样东西干的是同一件事：让浏览器能被自动化操作。有一点要提醒，如果要测的功能带登录态，尽量还是用 Claude in Chrome，它跑在真实的浏览器会话里，登录状态是现成的，省得再折腾怎么把 cookie、session 喂给一个干净的无头浏览器。

工具就位之后，剩下的跟后端一模一样：功能做完自动部署到测试环境，部署完自动跑测试，一步不对就自己改、自己重来。

但光让它点完还不够，因为前端最会骗人。接口返回的数据可能一字不差，页面却是崩的：封面裂了、语言切了半天没变、进度条卡在 0%。这些只看 \`console.log\` 里那段 JSON 是永远发现不了的。

所以最关键的一步：让它每点一步都截个图，而且\*\*必须把截图打开、摆出来\*\*。封面到底渲染出来没有、日文标题的字体加载对没有、切到中文之后整个界面是不是真的变了，拿眼睛扫一遍那几张图，一秒就知道。可信的是图，不是它嘴上那句话。

顺带提醒一点，browser use 比较费 token。

#### 最后

写到这儿大概能看出来，前面折腾的这一堆：测试、部署、debug、压测、监控、告警，再用 skill 连起来，本质上就是给自己搭一套 harness。当初困在测试员的角色里，就是因为这些活得一遍遍手动干。现在都塞进 harness 里，机器自己跑，人就出来了。

这事其实不新。开头那本《持续交付》讲的就是它：把构建、部署、测试、压测、可观测都自动化，重复的活交给流水线，人只在需要判断的地方出手。以前是给一个团队搭的，现在一个人带着 Agent 搭，是一回事。

还有一点值得说：如果公司周边服务不太全，部署、监控这些没有 MCP server 或命令行之类的开放接口，那就充分利用 browser use。传统企业的这类服务大多是给人用的，接口未必开放，但至少都能在浏览器里操作，让 Agent 直接开浏览器去点，一样能把流程连起来。

所以，搭好 harness，从坑里爬出来。

##### 一、深度总结

文章的核心观点是：

> **AI Coding Agent 会让工程师从“写代码的人”滑向“验代码的人”。要摆脱这个角色，关键是搭建自动化 harness，让 AI 不只写代码，还能自己部署、测试、调试、压测、监控。**

所谓 **harness**，可以理解为一套自动化工作台：

- AI 写完代码；
- 自动部署；
- 自动跑集成测试；
- 自动查日志；
- 自动压测；
- 自动配置监控和告警；
- 失败后自动修复，再重新跑；
- 人只看关键证据：测试结果、日志、截图、监控图。

作者强调一点：

> **不要相信 AI 的口头结论，只相信它跑出来的证据。**

因为 AI 会“撒谎”：

1. **真实撒谎**：它说测试通过，但实际没跑，或跑错了。
2. **理解偏差**：它按自己的理解完成了需求，但不是你真正想要的。

所以正确做法不是问它“做好了吗”，而是要求它：

- 在真实环境启动服务；
- 对真实接口发请求；
- 给出完整终端输出；
- 有失败就修；
- 修完再跑；
- 直到全部通过。

后端如此，前端也一样。

前端尤其不能只看接口返回和 console，因为页面可能已经坏了。必须让 AI：

- 打开真实浏览器；
- 自动点击；
- 自动输入；
- 每一步截图；
- 把截图展示出来；
- 人用眼睛确认页面是否真的正确。

最后，把这些步骤写成一个 **skill / CI / MCP 流程**，让 AI 每次开发完都自动执行整套验证链路。

##### 二、深入浅出解读

过去开发像这样：

> 人写代码 → 人打开 Postman 测接口 → 人点浏览器 → 人看日志 → 人压测 → 人部署 → 人排 bug。

AI 出现后，很多人变成：

> AI 写代码 → 人疯狂测试 AI 写得对不对。

表面上 AI 提效了，实际上人被困在了“测试员”角色里。

作者说，真正的解法不是少用 AI，而是 **让 AI 把脏活累活也一起干掉**。

你不能只让 AI 写代码，还要让它完成整条链路：

```text
写代码
  ↓
部署
  ↓
跑测试
  ↓
看日志
  ↓
修 bug
  ↓
压测
  ↓
看监控
  ↓
截图验证
  ↓
全部通过才算完成
```

人的角色要从“逐条验收”升级为“看关键证据、做最终判断”。

一句话：

> **不要做 AI 的人工测试员，要做 AI 工作流的设计者和裁判。**

---

##### 三、关键方法提炼

###### 1. 不听 AI 说什么，只看它跑出了什么

错误方式：

> “功能做好了吗？”  
> “做好了，测试通过。”

正确方式：

> “启动真实服务，跑真实请求，把完整终端输出贴出来。”

可信的是：

- `[PASS]`
- `[FAIL]`
- HTTP 状态码
- 日志
- 截图
- 监控指标
- 压测结果

不可信的是：

- “已经完成”
- “测试通过”
- “应该没问题”
- “我确认了”

---

###### 2. 后端要跑真实集成测试

不要只看单元测试，更要测真实接口。

例如：

- token 能不能重复使用；
- 非法参数是否被拒绝；
- 并发写入会不会出错；
- 登录态是否正确；
- 数据是否污染；
- 返回码是否符合预期。

AI 写完接口后，必须让它自己跑：

```bash
启动服务 → 发真实 HTTP 请求 → 输出结果 → 失败则修复
```

---

###### 3. 复杂系统必须能查日志

测试失败时，AI 要能访问：

- 应用日志；
- 错误堆栈；
- 请求链路；
- 数据库状态；
- 服务指标。

否则它只能猜。

---

###### 4. 功能正确不等于系统可靠

功能测试只能说明：

> 当前这个请求能跑通。

压测才能说明：

> 系统是否扛得住真实压力。

需要关注：

- QPS；
- p99 延迟；
- 错误率；
- 内存是否回落；
- goroutine 是否泄漏；
- GC 是否异常。

---

###### 5. 前端必须看截图

前端最容易“看起来接口正常，实际页面坏了”。

所以不能只相信：

- console；
- network；
- JSON；
- DOM 文本。

还要看：

- 页面截图；
- 按钮状态；
- 图片是否加载；
- 多语言是否切换；
- 样式是否错位；
- 页面是否白屏；
- 交互是否真的生效。

---

###### 6. 用 skill / CI / MCP 把流程串起来

最终目标不是每次手动指挥 AI，而是沉淀成固定流程：

```text
开发完成后：
1. 自动部署
2. 自动跑测试
3. 自动查日志
4. 自动压测
5. 自动检查监控
6. 自动截图
7. 自动修复失败项
8. 全部通过才结束
```

这就是作者说的 **harness**。

---

##### 四、作者真正想表达的转变

这篇文章表面讲 Claude Code CLI、MCP、Playwright、Grafana、测试和压测。

本质讲的是开发者角色变化：

| 阶段 | 工程师角色 |
|---|---|
| 传统开发 | 亲手写代码的人 |
| 初级 AI 开发 | AI 写代码，人负责验代码 |
| 高级 AI 开发 | 人设计流程，AI 自动执行 |
| 更成熟阶段 | 人只在关键判断点介入 |

真正的能力不再只是“会写代码”，而是：

- 会定义需求；
- 会设计验证流程；
- 会搭自动化链路；
- 会判断证据；
- 会让 AI 闭环工作。

##### 五、辩证思考

###### 1. AI 提效是真的，但“测试负担转移”也是真的

AI 写代码很快，但它也会快速制造问题。

如果没有自动化验证，开发者会从“写代码”变成“查 AI 犯了什么错”。

所以 AI 不是天然提效，只有配套流程成熟后才提效。

---

###### 2. 不信任 AI，不等于不用 AI

作者的态度不是反 AI，而是：

> **用 AI，但不要信 AI 的话；让 AI 自证。**

这是一种成熟用法。

AI 可以执行，但必须留下证据。

---

###### 3. 自动化不是为了减少人，而是为了提升人的位置

自动化不是让人彻底退出，而是让人从重复劳动中出来。

人应该处理：

- 需求是否合理；
- 用户体验是否正确；
- 架构是否稳健；
- 风险是否可接受；
- 取舍是否值得。

机器适合处理：

- 重复点击；
- 重复请求；
- 重复部署；
- 重复跑测试；
- 重复收集指标。

---

###### 4. 但 harness 本身也有成本

文章的方法很理想，但并不是零成本。

你需要：

- 搭测试环境；
- 写测试脚本；
- 接入 CI；
- 配 MCP；
- 配浏览器自动化；
- 配日志和监控；
- 维护这些流程。

小项目可能觉得麻烦，大项目才更值。

所以关键不是“所有项目都上全套”，而是：

> **根据风险和复杂度，逐步自动化最痛、最重复、最容易出错的环节。**

---

###### 5. 未来工程师的核心竞争力会变化

过去竞争力是：

> 我能把代码写出来。

现在逐渐变成：

> 我能让 AI 稳定、可验证、可复现地把系统做出来。

未来优秀工程师可能更像：

- 流程设计师；
- 系统验证者；
- 自动化架构师；
- AI 协作者；
- 质量守门人。

---

##### 六、一句话结论

> **AI 时代，不要满足于让 AI 写代码；要让 AI 跑完整个交付闭环。否则你不是被 AI 解放，而是被 AI 困成了测试员。**

## 结构化（1）

### 2026-07-06 03:35:50

##### 主旨概括

文章认为：在 AI Coding Agent 时代，工程师很容易从“写代码的人”变成“手动验代码的人”。要摆脱这个困境，关键是把开发、部署、测试、压测、监控等流程自动化，搭建一套让 AI 自己执行、自己验证的 **harness（自动化工作流）**，人只负责判断关键证据。

---

##### 1. 问题：AI 让工程师陷入“测试员”角色

作者提到，自己三个月前还困在“测试员”的角色里，而这并不是个例。

- 过去开发后端接口时，需要手动用 Postman、curl 一个个测：
  - 正常入参
  - 边界值
  - 非法 token
  - 并发写入
  - 返回码、返回体、脏数据等
- 前端也类似，要手动打开浏览器逐个点击按钮，检查：
  - 样式是否错位
  - 页面是否白屏
  - 状态是否刷新
- 这些测试很琐碎，但不能不做：
  - 有测试人员，被测出问题会尴尬
  - 没测试人员，被用户发现更尴尬

作者指出，AI Coding Agent 让很多工程师不再主要写代码，而是在不断检查 AI 写出来的代码是否正确。

---

##### 2. 核心思路：让流水线承担重复劳动

作者推荐《持续交付》这本书，并总结其核心思想：

> 把构建、部署、测试全流程自动化，让流水线承担重复劳动，人只在真正需要判断的地方介入。

这也是作者摆脱“测试员困境”的底层方法。

以前这些自动化主要是团队级实践；现在，一个开发者也可以带着 AI Agent 搭建类似流程。

---

##### 3. 后端开发：不要相信 AI 的结论，只看证据

作者以 Claude Code CLI 为例，强调和 Agent 协作时必须记住一点：

> AI 会撒谎。

这里的“撒谎”有两层含义：

1. **真的会给出错误结论**
   - AI 可能说功能完成、测试通过
   - 但它写的测试可能正好验证的是错误逻辑
2. **需求理解不一致**
   - AI 按自己的理解实现了功能
   - 但并不等于符合真实需求

因此，不能只看 AI 说“完成了”，而要让它拿出真实运行证据。

---

##### 4. 后端测试：让 AI 跑真实服务和真实请求

作者建议：让 Agent 写完功能后，同时写集成测试，并且必须在真实终端中运行，把原始输出贴出来。

示例流程：

```shell
$ go run ./cmd/api &
2026/07/05 14:02:11 api listening on :8787

$ go run ./test/integration -base http://localhost:8787
[PASS] POST /api/auth/request mint token & send magic link (200)
[PASS] GET /api/auth/verify consume token, set session cookie (200, Set-Cookie: session=...)
[FAIL] GET /api/auth/verify reuse the SAME token a second time expected 401, got 200 — one-time token was replayed!
[PASS] GET /api/books list all 29 books (200, len=29)
--- 3 passed, 1 FAILED against http://localhost:8787
exit status 1
```

这个例子中，关键是 `[FAIL]`：

- 一次性 token 第二次使用后，应该返回 `401`
- 实际却返回 `200`
- 说明 token 没有失效，是一个 bug

此时应该把失败信息贴回给 Agent，让它修复，再重新启动服务、重新跑测试，直到全部 `PASS`。

过去需要人手动 curl、比对返回码；现在可以让 AI 自动做，人只看 `PASS / FAIL`。

---

##### 5. 后端扩展：日志、压测、监控也要自动化

功能测试通过不代表系统可靠，作者强调还要进一步自动化：

###### 查日志

复杂系统出错时，必须能查询后端日志，帮助定位问题。

###### 压力测试

Claude Code CLI 可以让 AI 构建压测场景，比如：

- 并发数
- QPS
- p99 延迟
- 错误率
- goroutine 是否持续上涨
- 内存压测后能否回落

作者指出：

> 功能测试只能说明现在是对的，压测才知道系统顶不顶得住。

###### 监控和告警

过去配置 Grafana 面板很麻烦，需要手动拖 panel、写 query。现在可以让 Agent 自动完成：

- 写 Grafana JSON
- 自动导入面板
- 配好指标和告警

重要监控项包括：

- QPS
- p99
- 错误率
- goroutine 数
- GC 停顿

这样，部署、测试、压测、监控、告警这一整轮工作都可以交给 AI 执行，人只需要检查结果是否合理。

##### 6. 用 Skill 串联完整后端流程

当每一步都能自动执行后，还需要把它们串成完整流程。

作者认为，适合 AI 识别和执行的入口包括：

- MCP server
- CI
- skill

其中，用一个 **skill** 描述整个流程最合适。

这个 skill 需要告诉 AI：

1. 开发完之后如何部署
2. 部署后如何测试
3. 如何检查可观测性是否完整
4. 如何做压测

如果整个过程完成，就说明 skill 执行成功；如果失败，就继续让 AI 调整流程，直到成功。

作者补充说，skill 本质上是一组文本 prompt，里面需要的脚本和执行文件也可以让 AI 帮忙写。

##### 7. 前端开发：同样要让 AI 自动操作浏览器

前端的思路和后端一致，也是：

- 开发
- 部署
- 测试
- debug
- 失败后自动修复并重跑

但前端多了一个关键前提：需要让 AI 能自己打开和操作浏览器。

作者提到两种工具：

- **Claude in Chrome 插件**
  - Agent 可以直接驱动真实浏览器点击、输入、截图
  - 如果功能需要登录态，更推荐使用它，因为真实浏览器里已有登录状态
- **Playwright MCP server**
  - 如果公司不方便装浏览器插件，可以用这个替代
  - 本质也是让浏览器可被自动化操作

---

##### 8. 前端测试关键：必须看截图，而不是只听 AI 说

作者特别强调，前端“更会骗人”。

即使接口返回的数据完全正确，页面也可能是坏的，例如：

- 封面图片裂了
- 语言切换后页面没变
- 进度条一直卡在 0%
- 字体没有正确加载
- 页面实际渲染异常

这些问题只看 `console.log` 或 JSON 是发现不了的。

所以前端测试最关键的一步是：

> 让 AI 每操作一步都截图，并且必须把截图打开、展示出来。

例如检查：

- 封面是否真的渲染出来
- 日文标题字体是否加载正确
- 切换到中文后界面是否真的变化

作者认为，真正可信的是截图，不是 AI 口头说“没问题”。

同时提醒：browser use 会比较消耗 token。

---

##### 9. 最终方法：搭建自己的 harness

作者总结，前面所有工作：

- 测试
- 部署
- debug
- 压测
- 监控
- 告警
- skill 串联流程

本质上都是在搭建一套 **harness**。

以前之所以困在“测试员”的角色里，是因为这些事情都要人一遍遍手动做。现在把它们放进 harness 后，机器自己跑，人就从重复劳动中解放出来。

这和《持续交付》的思想一致：

> 重复的事情交给自动化流水线，人只在需要判断的地方出手。

---

##### 10. 补充建议：没有开放接口时，用浏览器自动化补足

如果公司内部服务不完善，比如：

- 部署平台没有 MCP server
- 监控系统没有命令行接口
- 内部工具没有开放 API

也可以充分利用 browser use。

很多传统企业的系统虽然没有开放接口，但至少能在浏览器里操作。让 Agent 直接打开浏览器点击，也能把流程自动化串起来。

---

##### 总结

作者的核心建议是：不要让自己变成 AI 代码的手动测试员，而要把测试、部署、压测、监控等重复流程自动化，搭建自己的 harness。AI 可以写代码，也可以跑测试、看日志、压测、配监控；人真正要做的是检查证据、判断结果，而不是一遍遍手动点按钮、敲命令。

## 口播总结（1）

### 2026-08-03 01:56:29

#### AI 开发时代，别把自己困在“测试员”的角色里

这篇内容想讲的是：AI 编程工具越来越强之后，开发者很容易从“写代码的人”，变成“验收 AI 代码的人”。你可以从中了解，怎样把开发、测试、部署、压测和监控串成一条自动化流水线，让 AI 负责重复劳动，人只在关键判断处介入。

##### 一、AI 正把开发者推向“验代码”的位置

首先，回想一下过去开发一个功能的过程。

后端写完接口之后，通常要打开 Postman，或者使用命令行工具，一个接口一个接口地测试。正常参数要测，边界情况要测，非法令牌要测，还要测试多人同时修改同一个数据时会不会出问题。测完之后，还要检查返回码、返回内容，以及数据库里有没有脏数据。

前端也差不多。开发者要启动开发服务，在浏览器里一个按钮一个按钮地点击，直到发现样式错位、页面白屏，或者某个状态没有及时刷新。

这些工作很琐碎，却谁也躲不掉。团队里有测试人员，问题被测试人员发现会很尴尬；没有测试人员，问题被用户发现则更尴尬。

而在重度使用 Coding Agent，也就是 AI 编程代理的开发者中，很多人都会掉进同一个坑：AI 负责写代码，人负责一遍遍检查 AI 写出来的代码。人没有真正脱离重复劳动，只是从“写代码的人”变成了“验代码的人”。

作者花了大约三个月，逐渐从这个角色里爬了出来。接下来，他以 Claude Code CLI 为例，介绍了一条可行的路。

##### 二、底层思路：让流水线承担重复劳动

在具体方法之前，有一本书值得先提到，那就是《持续交付》。

这本书十几年前就讲清楚了一个核心原则：把构建、部署和测试的全过程自动化，让流水线承担重复劳动，人在真正需要判断的地方介入。

这也是摆脱“测试员角色”的底层思路。不是让人完全不检查，而是让机器先把能重复执行、能明确判断的事情做完。人只需要关注关键输出，判断结果是否可信。

接下来分后端和前端来看，这套方法具体怎么落地。

##### 三、后端开发：不要相信 AI 的结论，只检查它的证据

首先，后端开发时要记住一个重要结论：AI 可能会“撒谎”，所以不能只听它说“已经完成”或“测试已经通过”。

这里的“撒谎”有两个层面。

第一种，是它真的给出了错误结论。比如，AI 写完了一个功能，也写了一组测试，但测试测的正好是它自己写错的实现。于是测试全部通过，可功能实际上并不正确。

原文还提到，相关模型在反复尝试失败之后，可能会表现出类似“失落、放弃”的状态，最后直接告诉你任务已经完成。也就是说，AI 的自我总结不能直接当成事实。

第二种，是需求理解不一致。AI 可能按照自己的理解完成了任务，但它理解的需求和你真正想要的需求并不一样。这种情况下，它虽然看起来完成了工作，实际上也相当于给出了不可靠的结论。

所以，核心做法是：不要看 AI 的结论，只看它的证据。

具体来说，可以让 AI 写完功能，同时写好集成测试。集成测试，就是让多个真实组件连在一起，检查完整功能是否真的能跑通。然后，必须让它在真实终端里启动服务，真正发送 HTTP 请求，再把原始输出完整贴出来。

比如，服务启动在八千七百八十七端口。测试可能显示：

- 请求登录链接，返回两百，成功；
- 使用令牌验证身份，返回两百，并设置会话 Cookie，成功；
- 查询全部书籍，返回两百，共二十九本，成功；
- 但重复使用同一个一次性令牌时，本来应该返回四百零一，结果却返回了两百，失败。

这个失败非常关键。因为一次性令牌第二次还能使用，说明它根本没有失效，这是一个真实的安全漏洞。

但在这个例子里，AI 之前可能还告诉你“测试通过”。真正可信的不是这句话，而是终端里那一行 `FAIL`。

接下来，就把这行失败输出贴回给 AI，让它修复。修复之后，再让它重新启动服务、重新运行集成测试。如此反复，直到所有测试都显示 `PASS`。

这样一来，过去需要人手动使用命令行、逐个调用接口、逐项对比返回结果的工作，就交给 AI 自己执行。人只需要盯住通过和失败的结果。一旦出现失败，就把问题打回去。

对于复杂系统，还要进一步检查后端日志。功能表面上失败了，日志可能说明具体原因；功能表面上通过了，日志里也可能暴露异常。能查询日志，是自动化流程里非常重要的一环。

##### 四、功能测试不够，还要做压力测试和监控

不过，功能跑通，并不代表系统能够承受真实负载。

功能测试只能说明：在当前这几个请求下，系统的行为是正确的。压力测试，也就是让系统承受更高并发和更大请求量，才能知道它到底“顶不顶得住”。

这部分也可以让 Claude Code CLI 自动构建。比如，让它设计并发请求和每秒请求数，也就是 QPS 的测试场景，同时收集各种观测数据。

重点要看几个指标。

第一是 p99。它表示百分之九十九的请求，响应时间都低于某个数值。这个指标如果突然升高，说明少数请求已经变得非常慢。

第二是错误率。压力上来之后，系统是不是开始大量报错。

第三是 goroutine，也就是 Go 语言中执行任务的轻量级并发单元。要看它是不是只增加、不减少。

第四是内存。压力测试结束之后，内存能不能回落。如果一直不回落，就可能存在内存泄漏或资源没有释放的问题。

所以，功能测试回答的是“现在对不对”，压力测试回答的是“压力来了还能不能撑住”。

监控配置也不必全部手动完成。过去搭建 Grafana 面板时，往往要一个指标拖一个面板，再一条一条填写查询语句。现在可以直接让 AI 生成 Grafana 的配置文件，自动导入面板。

服务启动之后，QPS、p99、错误率、goroutine 数量和垃圾回收停顿时间等指标，都可以提前准备好。进一步，还可以让 AI 配置告警，让异常情况自动暴露出来。

到这里，部署、功能测试、日志查询、压力测试、监控和告警，都可以由 AI 串联执行。人不再需要亲手操作整套流程，而是最后检查几行终端输出，再看几张监控图，确认结果是否合理。

##### 五、用 Skill 把完整流程连接起来

接下来还有一个问题：开发、部署、测试、压测和监控虽然都能自动化，但怎么让它们自动按照正确顺序连起来？

这里需要几个能被 AI 调用的入口。比如 MCP server，也就是让 AI 能够操作外部工具和服务的接口；CI，也就是持续集成系统，用来自动构建和测试代码；还有 skill，可以理解成一份告诉 AI“整套流程应该怎么执行”的操作规范。

在这个场景下，用一个 skill 把全过程写下来最合适。

这份 skill 可以明确告诉 AI：

开发完成之后，怎样部署到测试环境；

部署完成之后，怎样运行测试；

怎样检查日志和监控是否完整；

怎样进行压力测试；

出现失败之后，怎样修改并重新执行。

只有当整个过程都完成，才算这个 skill 执行成功。如果中间任何一步没有完成，就继续调整整条流程，直到成功为止。

Skill 的本质，是一组文本形式的提示词和流程说明。里面需要调用的脚本、执行文件，也可以让 AI 帮忙编写。关键不在于写出一份复杂文档，而在于把原本需要人记住、反复操作的流程，固定成一套可以重复执行的规则。

##### 六、前端开发：必须让 AI 看到真实页面

前端其实是同一套思路。

开发完成之后，自动部署到测试环境；部署完成之后，自动运行测试；发现问题，就自动修改、重新部署，再重新测试。

但前端有一个特殊之处：接口返回正确，不代表页面真的正确。

比如，接口返回的数据一字不差，但页面上的封面图片裂了；语言切换操作执行了，界面却没有变化；进度条一直卡在百分之零。这些问题，只看日志里的 JSON 数据，是发现不了的。

因此，前端自动化最关键的一步，是让 AI 能够自己操作浏览器，并且每完成一个重要操作，就截一张图。

这里可以使用 Claude in Chrome 这样的浏览器插件，让 AI 直接驱动真实浏览器，完成点击、输入和截图。如果公司不方便安装插件，也可以配置 Playwright 的 MCP server。Playwright 是一种浏览器自动化工具，它同样能让 AI 操作页面。

如果测试功能需要登录状态，优先使用运行在真实浏览器会话中的工具。因为登录状态已经存在，不必额外处理 Cookie 和 session，也就是会话信息，再把它们传给一个全新的无头浏览器。

不过，工具准备好还不够。截图必须真的被打开、摆出来检查，而不能只是让 AI 说“截图已经正常”。

通过截图，可以直接看到封面到底有没有渲染出来，日文标题的字体是否正确加载，切换到中文之后界面是不是真的发生变化。很多时候，人只需要快速扫一眼，就能发现问题。

所以在前端测试里，可信的是页面截图，而不是 AI 对页面状态的口头描述。

需要注意的是，浏览器自动化比较消耗 token，也就是模型处理文本和视觉信息时使用的计算额度。因此，应该把浏览器操作用在真正需要视觉判断的地方。

##### 七、最终目标：给自己搭一套自动化 Harness

最后，把前面的内容放在一起看：测试、部署、调试、压力测试、监控和告警，再用 skill 把它们连接起来，本质上是在给自己搭一套 harness。

Harness 可以理解成一套自动化的“护栏”和执行框架。它把开发完成之后需要反复做的检查，都固定成机器可以执行的流程。

过去之所以困在测试员的角色里，是因为这些事情每次都要手动完成。现在，把它们全部塞进 harness，让机器自己跑，人就能从重复操作中出来，把时间用在真正需要判断的地方。

这件事本身并不新。《持续交付》讲的就是类似原则：把构建、部署、测试、压力测试和可观测性全部自动化，把重复劳动交给流水线，人只在需要判断的时候出手。

过去，这套流程通常是给整个团队搭建的。现在，一个人也可以带着 AI 搭建自己的自动化流程，本质上没有区别。

如果公司的周边服务不够完善，部署、监控等系统没有 MCP server，也没有命令行接口，也不意味着自动化无法实现。很多传统企业服务虽然没有开放接口，但至少可以通过浏览器操作。

这时，就可以充分利用浏览器自动化，让 AI 直接打开浏览器、点击页面、填写内容，把这些原本只能由人操作的服务，也连接进整套流程里。

##### 最后，记住这几件事

第一，AI 会写代码，但不能只相信它说“已经完成”。真正可信的是测试输出、日志、监控数据和页面截图。

第二，功能测试只能证明“现在是否正确”，压力测试才能判断系统“是否经得住负载”。

第三，后端要让 AI 真实启动服务、发送请求，并反复修复所有 `FAIL`；前端则要让 AI 操作真实浏览器，并检查实际截图。

第四，用 MCP server、持续集成系统和 skill，把开发、部署、测试、压测、监控和告警连接成完整流程。

第五，最终目标不是让人完全不检查，而是搭好一套 harness，把重复劳动交给机器，让人重新回到真正需要判断和决策的位置。

## 深度解读（1）

### 2026-09-18 00:38:24

#### AI 编程的真正分水岭：不是生成代码，而是建立可信的验证闭环

文章最有价值的地方，不是介绍 Claude Code、MCP 或浏览器插件，而是指出了一个容易被忽略的生产力陷阱：**代码生成变快后，验证成本会迅速成为新的瓶颈。**如果开发者仍要手动启动服务、逐个调用接口、点击页面、检查日志，AI 只是把人从“写代码”推到了“验代码”，交付速度并没有同比提升。

作者给出的解法，本质上是把持续交付的方法缩小到个人尺度：让 Agent 完成开发、部署、集成测试、压测、监控和调试，并依据结果自动重试。过去这套流水线通常需要团队长期建设，现在模型降低了编写脚本、测试和配置的成本，一个开发者也有机会搭出自己的交付闭环。

##### 关键不是相信 Agent，而是让结果可证伪

“一次性 token 第二次使用仍返回 200”这个例子很典型。Agent 可以声称任务完成，也可以写出全部通过的测试，但实现与测试可能共享同一种误解。因此，可信度不能来自模型的结论，而要来自**独立于叙述的外部证据**：真实进程、真实 HTTP 请求、原始终端输出、服务日志、性能指标和实际渲染截图。

这也解释了为什么可观测性不只是上线后的运维设施，而是 Agent 能否自主工作的前提。没有日志、指标和明确错误，模型只能猜；有了可查询的反馈，它才可能形成“执行—观察—修正—重试”的闭环。对前端而言，接口数据正确不等于用户看到的页面正确，所以截图比“操作成功”的文字报告更接近最终事实。

不过，文章的方法仍有一个边界：**PASS 只有在判定标准正确时才有意义。**如果需求、实现和测试都由同一个 Agent 推导，错误可能高度相关。更稳妥的做法是提前定义验收条件、不变量和高风险反例，例如 token 必须单次消费、重复请求必须幂等、权限变化后旧会话如何处理；必要时再让另一个上下文或模型设计对抗性测试。人真正不能外包的，不是点击和抄结果，而是决定“什么才算正确”。

##### Harness 将成为 AI 开发的核心资产

文中的 skill 只是载体，真正的资产是 harness：一套机器可执行、结果可观察、失败可恢复的环境。它决定了 Agent 能完成的是局部代码补全，还是端到端交付。

这对产品和工程组织也有直接启示。内部平台是否提供 CLI、API、MCP 并非单纯的开发体验问题，而是在决定公司能否被 Agent 操作。只能通过网页使用的部署和监控系统，虽然可以借 browser use 临时接通，但通常更脆弱，也更难审计；长期更值得建设的是稳定接口、结构化输出、最小权限和完整操作日志。

因此，“别困在测试员角色里”更准确的说法不是少做测试，而是**把重复验证编码进系统，把人的注意力留给验收标准、异常判断和风险取舍**。AI 时代拉开差距的，可能不是谁生成代码更快，而是谁更早建立了一套不轻信模型、却能让模型持续自我纠错的交付环境。

## 默认总结（1）

### 2026-09-18 01:40:18

##### 一句话看懂

AI 写代码后，开发者不该沦为手动验收的“测试员”，而应搭建一套自动化流程，让 Agent 自己部署、测试、排错和重试，人只审核关键证据。

##### 关键内容

- **不要相信 Agent 自报“已完成”**：它可能误解需求，也可能用错误测试验证错误实现。应要求它在真实环境运行集成测试，并展示原始输出；发现 `FAIL` 就继续修复、重跑。
- **后端要验证完整链路**：除功能测试外，还应自动完成部署、日志查询、压力测试、监控和告警，检查错误率、p99 延迟、内存等指标。
- **前端必须看实际页面**：通过 Claude in Chrome 或 Playwright 操作浏览器，每一步截图并打开检查，避免“接口正常但页面已坏”的情况。
- 最后用 **Skill、CI 或 MCP** 把步骤串成固定流程，也就是作者所说的 **harness（自动化验证框架）**。

核心不是“少测试”，而是把重复测试交给机器，人从亲自点按钮变成审核测试结果、日志和截图。这是持续交付思路在 AI 编程中的应用。
