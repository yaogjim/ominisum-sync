## 正文

**Leeway**

用了一天 @AlchainHust  
的 Huashu-Design skill, 一句话感受: 终于不用像 Claude Design 那样被限流了。

Claude Design 官方是独立产品, 单独计费:  
\- Pro 每月复杂 task 有限次  
\- 交互走 GUI layer, 一次操作跑完整 render cycle  
\- token 消耗不透明, 经常到一半被截

Huashu 是装进 Claude Code 的 skill:  
\- 调用就是普通 Claude 对话, 走自己 Pro/Max 配额  
\- 没有额外 UI layer rate limit  
\- token 用量在 context 里看得见

迭代周期是 builder 最实际的 pain point。

给 codebase 做 brand extraction → 生成 landing → preview → 改 design token → 再 generate. 真实项目这个循环 10 次起步。

GUI-first 工具每次 cycle 撞一次 rate limit. 同一天第 3 次 iteration 被 throttle, 反馈链中断。

skill 跑: 我今早 1 小时做了 brand spec 提取 + 3 方向 landing proposal + 41KB HTML preview 输出. token 算在当天 Claude 对话里, 没撞任何独立 limit。

还有 3 个次要但重要优势:

① Version control — skill 本身是文件, 可以 fork / diff / revert. Claude Design 改一个样式只能在 GUI 里改.

② 自定义 — Huashu skill.md 里写了禁区清单和 design 原则. 项目要加约束直接改 skill.md. Claude Design 的禁区 override 不了.

③ Agent 流水线 — skill 可被其他 agent 调用 (extract → generate → deploy). Claude Design 是 UI 产品, pipeline 被 UI 切断.

AlchainHust 说 "必须通过 GUI 操作的已经是上一个时代的产品"——我今天第一次从用户侧体会到这不是口号. rate limit + iteration 中断 + 无法自定义 + 无法 pipeline, 是四个 UI-first 工具的结构性问题。

反过来: Huashu 要 work 的前提是你 codebase 里已有严谨的 design tokens. skill 不 hallucinate 新 design system, 从你已有 tokens 提取并扩展. tokens 层空白的项目 Huashu 也救不了。

Agent-first 才能真的作为 builder 工具用。

## 解读（1）

#### 总结

这段内容的核心意思是：

- 作者用了一天`Huashu-Design skill`，最大感受是：**不像 Claude Design 那样容易被限流，迭代更顺畅**。
- 他认为，`Claude Design`是一种**GUI-first（界面优先）**工具，而`Huashu`是**Agent-first（智能体优先）**工具。
- 对做产品的人来说，最重要的不是 “能不能生成一张好看的设计图”，而是：**能不能持续快速迭代，并接入真实开发流程**。
- 作者也强调，`Huashu`并不是万能的，它依赖项目本身已经有比较规范的`design tokens`；如果基础设计系统很乱，它也帮不了太多。

#### 解读

##### 1. 作者真正批评的，不是 “设计效果”，而是 “工作方式”

表面上看，他在比较两个设计工具；实际上，他在讲一个更深的问题：

- `Claude Design`更像一个单独的设计产品  
- `Huashu`更像一个嵌入开发流程的能力模块

作者不满的点，不是 “Claude Design 设计得不好看”，而是它有几个结构性问题：

- **限流**：做几轮就被卡住
- **流程中断**：一旦被 throttle，设计 — 预览 — 修改的链路断掉
- **不够透明**：token 消耗和限制感知不清晰
- **不能融入流水线**：难以和提取、生成、部署等 agent 流程串起来

所以他想表达的是：  
**真正适合 builder 的工具，不只是会生成，还要能连续迭代、可控、可接入流程。**

##### 2. 为什么 “迭代周期” 是重点

作者提到一个很真实的工作流：

`brand extraction -> 生成 landing -> preview -> 改 token -> 再生成`

这不是一次性动作，而是一个要反复跑很多轮的循环。  
真实项目里，设计常常不是 “做一次就结束”，而是要不断调整。

因此，工具的关键不只是单次能力，而是：

- 能不能多轮反复跑
- 每一轮成本高不高
- 中途会不会被打断

作者的体验是：`Huashu`因为直接走 Claude Code 的对话和配额，所以更像一个可持续工作的 “生产工具”；而`Claude Design`因为额外有 UI 层和独立限制，更像一个 “演示型工具” 或 “单次体验型工具”。

##### 3. 作者为什么强调 version control、自定义、pipeline

这三点其实都指向一个词：**可工程化**。

###### Version control
skill 是文件，可以：

- fork
- diff
- revert

这意味着它可以像代码一样管理。  
而 GUI 里的修改，往往很难追踪、比较和回退。

###### 自定义
如果项目有自己的品牌规范、禁区、设计原则，可以直接写进`skill.md`。  
这意味着工具能**服从项目规则**，而不是只能服从官方默认逻辑。

###### Agent pipeline
skill 可以被其他 agent 串起来调用。  
这意味着设计不再是孤立的一步，而是能进入完整自动化链路。

说白了，作者认为：  
**未来更有价值的设计工具，不是一个 “会画图的窗口”，而是一个 “能被系统调用的设计能力”。**

##### 4. 作者也给出了边界条件

这一点很重要，说明他的观点并不是无脑吹。

他明确承认：

- `Huashu`的前提，是项目本身已经有较成熟的设计 token
- 如果底层设计系统是空白的、混乱的，它也无法凭空补齐

也就是说，`Huashu`更适合：

- 已经有产品基础
- 有代码仓库
- 有设计规范
- 想提高迭代效率的团队

而不是那种 “从零开始，啥都没有，还希望工具全自动救场” 的项目。

#### 我的意见

我基本认同作者的判断，而且我觉得他抓到了重点：

- **设计 AI 的竞争，不只是比生成效果，更是比能否进入真实开发流程**
- 对开发者和 builder 来说，**不中断的迭代能力**，往往比单次惊艳效果更重要
- `Agent-first`确实比`UI-first`更接近未来的生产方式

不过也要补充两点：

1. **GUI 工具不会马上过时**  
   对非技术用户、快速展示、灵感探索来说，GUI 仍然有价值。

2. **Agent-first 的门槛更高**  
   它要求团队有更好的工程基础，比如 token 规范、代码结构、流程意识。不是所有团队都马上吃得下。

一句话说：

> 这段内容最有价值的地方，不是在夸某个工具更强，而是在提醒我们：真正好用的 AI 设计工具，必须服务 “连续迭代” 和 “工程化协作”，而不只是做出一张好看的图。
