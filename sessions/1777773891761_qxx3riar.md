## 分析要点

- **核心高价值点**：将 Claude Code 从“工具”重新理解为“有限注意力、有限时间、有行为偏好的同事”，由此推导出上下文管理、任务隔离和异步协作策略。
- **留存建议**：长期保留（文章不仅罗列 Claude Code 技巧，还抽象出上下文管理、任务拆分、模型选择和异步监控等可复用方法，对 AI 编程工作流有较高参考价值。）

**知识要点**

- 超过一定上下文长度后应使用 /compact 重新聚焦关键信息，减少 lost in the middle 影响。
- sub agents 的核心价值不只是并行，而是隔离探索过程，避免污染主上下文。
- 任务跑偏时应 fail fast，及时退出重开，而不是在污染上下文中继续修正。
- 简单任务使用较小模型可能减少过度设计，复杂任务再交给更强模型或 ultrathink。
- /loop 更适合持续监控类任务，而不是让模型长时间连续写代码。

**行动项**

- 在 Claude Code 项目中启用 /init，并维护清晰的项目说明与约束文档。
- 当上下文超过约 60% 或模型开始遗忘需求时，立即使用 /compact。
- 为代码搜索、调研、测试影响面分析等探索型任务尝试使用 sub agents。
- 建立任务复杂度分级规则：简单任务交给 Haiku，复杂任务交给 Sonnet/Opus。
- 将 CI 检查、PR 队列、慢查询等周期性状态检查改造成 /loop 监控任务。

#### 一、把 Claude 当 junior 同事，不是态度问题，是 prompt 工程

很多人看到这条会以为是「对它说话礼貌一点」。其实跟礼貌没关系，这是计算路径的选择。

LLM 接收命令式 prompt 时，触发的是「按指令执行」的浅层模式，直接 pattern match，输出快但思考浅。接收描述式 prompt 时，触发的是「理解后再行动」的深层模式，会展开 chain of thought，输出慢但准确度高一截。

同一个 bug，「修一下这里」和「这里看起来怪怪的，你查查为啥」出来的代码质量能差一倍。前者它就直接改你指出的那行，后者它会先去理解上下文，可能发现真正的问题在另一个地方。

更深一层，描述要具体且不带预设答案。「这里有 race condition」会让它只查 race condition，「这里偶尔会出错你查查」会让它展开完整排查。你 prompt 里预设的答案越少，激发的推理就越多。

#### 二、60% 用 /compact，是对抗 lost in the middle，不是省 token

这个 60% 经常被解读成「省 token 的阈值」。其实不是。

Stanford 2023 年有篇论文揭示了 lost in the middle 现象，LLM 在长 context 里的注意力是 U 型曲线，开头记得最牢，结尾记得最牢，中间最容易被忽略。

60% 这条线不是省钱的红线，是注意力开始衰减的经验线。超过这个点之后，你前面提过的关键需求会开始被「视而不见」，模型会犯一些「明明你说过了」的错。

/compact 真正的价值是它会保留关键决策和未完成事项，把中间的散乱讨论压掉。这不是粗暴截断，是在做注意力的重新聚焦。

判断什么时候该 compact，不要光看 token 数，要看模型是不是开始忘事。一旦它问出「你想做什么」之类的问题，立刻 compact，迟一步它就会带着错误前提继续往下做。

#### 三、跑偏了 exit 重开，是 token 经济学，不是耐心问题

很多人遇到 Claude 走偏，第一反应是「我再 prompt 它一下让它修正」。这个反应是错的。

被污染的 context 里，你写的修正 prompt 自己占 context，它的道歉占 context，它修正后的输出还会被错误推理影响。人类有 confirmation bias，LLM 也有，被前面的错误锚定之后很难真正跳出来。

总成本比重开高 2 到 3 倍，最终输出还可能更差。

应该建立的反射是 fail fast，看到走偏立刻 ESC，重新组织思路再 prompt，比让它自己掰回来快得多。重开不是失败，是更聪明的资源分配。

这个反射很多人建立不起来，因为觉得「重开是浪费」。其实越往后修，浪费越大。

#### 四、sub agents 真正的价值是上下文隔离，不是并行

并行只是表象，隔离才是核心。

sub agents 把 context 从一维资源变成了树形资源。父 agent 是指挥者，看大局，不需要知道每个细节怎么实现。sub agent 是执行者，可以激进探索，包括各种失败和绕路。父 agent 只看 sub agent 的最终结论，那些失败的探索不会污染主线。

什么任务最适合开 sub agent，是「需要大量探索但只需要少量结论」的任务。比如「在 codebase 里找所有用了某个 deprecated API 的地方」，让 sub agent 把代码翻完，回来交一份清单就行。父 agent 不需要知道它翻过哪些文件，更不需要被它翻过的代码污染主上下文。

理解了这一点，你会发现很多任务都可以这样拆。「调研一下 X 库怎么用」「查一下这个 bug 在哪几个文件出现过」「列出所有需要改的测试」，全都是典型的 sub agent 任务。

#### 五、简单活给 Haiku 不只是省钱，是避免「过度设计」

这背后是大模型的过度对齐问题。

大模型训练时见过太多复杂场景，对简单任务也会本能地加边缘情况处理，加错误处理，加注释和文档，用更复杂的设计模式。

写一个简单的 helper 函数，Sonnet 可能给你 30 行，Haiku 给你 10 行。后者在大多数场景反而更对。

我自己的判断标准是任务的「认知步骤数」：

1 到 2 步的活丢 Haiku 5 步以上留给 Sonnet 或 Opus 10 步以上才开 ultrathink

不要无脑用最强模型，最强模型对简单任务有「设计过度」的副作用，输出的代码后期还要花时间删冗余。

#### 六、/loop 挂 3 天的真正用法是 monitoring，不是写代码

很多人看到 /loop 第一反应是「让 Claude 连续写 3 天代码」，其实不是。

/loop 真正的用法是把 Claude 从同步工具变成异步同事。它在那挂着，定期检查状态，有事叫你。

好的 /loop 任务有几个特征：

输入是状态，不是动作 输出是「有事/没事」的判断 处理时间不连续，可以等

比如每 10 分钟看一下 CI 是不是过了，没过分析失败原因，每小时扫一下数据库慢查询，每天看一遍 PR review 队列。这些以前是「我得记得去看」的事，现在变成「Claude 看到再叫我」。

这是 Claude 从写代码工具升级成值班同事的关键。

#### 把这些串起来看

如果只看 32 个技巧，你最多能复述操作。但如果把上面这 6 个点连起来看，你会发现 Nate Herk 真正的心法，是一个心智模型：

把 Claude Code 当成一个「有限注意力，有限时间，有性格」的同事来管理，不要当成「无限算力的工具」来用。

所有技巧背后都是这个心智模型在起作用：

注意力有限，所以要做 context 管理，对应的是 /compact，/clear，sub agent 隔离 时间有限，所以要异步化，对应的是 /loop，agent team，多 session 并行 有性格，所以要 prompt 沟通，对应的是 plan mode，让它反问，junior 同事心态

心智模型一旦换过来，剩下的技巧都是延伸，自己也能想出来。

我自己用 Claude Code 写代码差不多大半年了，最大的认知升级不是某个具体技巧，而是从「我用一个工具」变成「我管一个同事」。这两种心态出来的代码质量，效率，token 消耗，差着一个数量级。

注意，此文章是我同 AI 共同创作

#### Claude Code 的 32 个使用技巧：核心总结

##### 一句话总结

这篇文章的核心不是罗列 Claude Code 技巧，而是提出一个更重要的心智模型：**不要把 Claude Code 当成无限算力工具，而要把它当成一个“有限注意力、有限时间、有性格的 junior 同事”来管理。**

---

##### 1. 32 个技巧分三层

###### 入门技巧

重点是让 Claude 更好理解项目和任务：

- 用 `/init` 生成项目说明文件 `cloud.md`
- 用 `plan mode` 先规划再执行
- 用 `/context` 查看 token 占用
- 超过一定上下文后用 `/compact` 压缩
- 把 Claude 当 junior 同事，多提问题，少下命令
- 在 todo 中加入 self check，让它自检

###### 进阶技巧

重点是提升效率和复用能力：

- 用 sub agents 并行处理任务
- 用 custom skills 复用 prompt 文件
- 简单任务交给 Haiku，节省成本和 token
- 跑偏时直接退出，重新 prompt
- 用截图辅助视觉 debug

###### 高阶技巧

重点是多任务、异步化和复杂协作：

- 用 `/loop` 自动执行周期性任务
- 用 Git worktrees 多 session 并行开发
- 用 VPS 托管，保持长期运行
- 用 ultrathink 处理高难度问题
- 用 agent team 让多个 agent 分工协作

---

##### 2. 把 Claude 当 junior 同事，本质是 Prompt 工程

这不是“说话客气”的问题，而是影响模型思考方式。

如果你直接命令它“修这里”，它可能只会机械修改你指出的地方。  
如果你描述问题“这里看起来怪怪的，你查查原因”，它会更倾向于理解上下文，主动排查真正原因。

更好的方式是：**描述现象，不预设答案。**

例如：

- 不好：这里有 race condition，修一下
- 更好：这里偶尔会出错，你查查原因

预设越少，模型越容易展开推理。

---

##### 3. `/compact` 的重点不是省 token，而是管理注意力

文章强调，60% 上下文阈值不是单纯为了省钱，而是为了对抗 **lost in the middle** 问题。

LLM 在长上下文中，对开头和结尾记得更清楚，中间内容最容易被忽略。  
当 context 太长时，Claude 会开始忘记之前的重要需求。

`/compact` 的价值是：

- 保留关键决策
- 保留未完成事项
- 压缩掉无关过程
- 重新聚焦模型注意力

判断是否该 compact，不只看 token 数，而要看 Claude 是否开始“忘事”。

---

##### 4. 跑偏了要及时重开，不要硬纠正

当 Claude 明显走偏时，继续补 prompt 让它修正，往往成本更高。

原因是错误推理已经污染了上下文：

- 你的纠正会继续占 context
- 它的道歉和修正也会占 context
- 前面的错误会形成锚定效应

更好的策略是：**fail fast，及时 ESC，重新组织 prompt。**

重开不是浪费，而是更聪明的资源分配。

---

##### 5. Sub agents 的核心价值是上下文隔离

很多人以为 sub agents 的重点是并行，其实更重要的是 **隔离上下文污染**。

父 agent 负责大局和决策，sub agent 负责探索和执行。  
sub agent 可以翻代码、试错、走弯路，但最后只把结论交给主线。

适合 sub agent 的任务是：

- 需要大量探索
- 但最终只需要少量结论

例如：

- 找出所有 deprecated API 使用位置
- 调研某个库的用法
- 定位 bug 可能出现在哪些文件
- 列出需要修改的测试

---

##### 6. 简单任务交给 Haiku，是为了避免过度设计

强模型不一定适合所有任务。

Sonnet / Opus 在简单任务上，可能会因为“想太多”而写出过度复杂的代码，比如增加不必要的边界处理、抽象、注释和设计模式。

文章给出的判断标准是：

- 1–2 步任务：交给 Haiku
- 5 步以上：交给 Sonnet 或 Opus
- 10 步以上：再考虑 ultrathink

核心原则是：**不要无脑使用最强模型。简单任务用轻量模型，往往更直接、更干净。**

---

##### 7. `/loop` 的真正价值是异步监控

`/loop` 不是让 Claude 连续写 3 天代码，而是让它变成一个“值班同事”。

它适合处理周期性检查任务：

- 每 10 分钟检查 CI 是否通过
- CI 失败时分析原因
- 每小时检查数据库慢查询
- 每天查看 PR review 队列

这类任务的特点是：

- 输入是状态
- 输出是“有事 / 没事”
- 不需要连续处理
- 适合等待和提醒

它让 Claude 从同步工具，升级为异步协作者。

---

##### 8. 最重要的心智模型

所有技巧背后都可以归纳为一句话：

> 把 Claude Code 当成一个有限注意力、有限时间、有性格的同事来管理。

对应关系是：

- 注意力有限：需要 `/compact`、`/clear`、sub agent 隔离
- 时间有限：需要 `/loop`、agent team、多 session 并行
- 有性格：需要 plan mode、反问机制、junior 同事式 prompt

---

##### 结论

这篇文章真正有价值的地方，不是 32 个操作技巧本身，而是背后的使用范式转变：

从 **“我在使用一个工具”**，升级为 **“我在管理一个 AI 同事”**。

一旦采用这个心智模型，Claude Code 的代码质量、执行效率和 token 成本都会明显改善。

##### 1. 一句话判断

> 最值得保留的是：**使用 Claude Code 的关键不是掌握命令清单，而是把它当成一个“注意力有限、上下文会被污染、能力有边界的同事”来管理。**

**价值评级：A**

**精炼理由：**  
文章真正有价值的地方，不在 32 个技巧本身，而在把 `/compact`、sub agents、exit 重开、模型选择、/loop 等操作统一到一个管理智能体的心智模型里：**AI 不是无限算力工具，而是需要分配注意力、隔离上下文、控制任务粒度的协作者。**

---

##### 2. 最重要的洞见

###### 洞见 1：把 AI 当“junior 同事”，本质是让它进入推理模式，而不是执行模式

###### **核心观点：**  
> 好的 prompt 不是更礼貌，而是少下命令、多描述现象，让模型先理解问题，再决定行动。

**为什么重要：**  
很多人用 AI 写代码时，会直接说“修这里”“改这个”。这会把模型锁进一个很窄的执行路径：它倾向于修改你指出的局部，而不是重新判断真正的问题在哪里。

更好的方式是描述现象：  
- 差：`这里有 race condition，修一下`
- 好：`这里偶尔会出错，你查查可能原因`

前者把答案预设进去了，后者给模型留下诊断空间。

**反常识之处：**  
通常人们以为 prompt 越明确越好，但在排查、设计、debug 这类任务里，**过早给出判断反而会降低模型的推理质量**。

**可迁移价值：**  
这不只适用于 Claude Code，也适用于管理人：  
- 对执行型任务，可以直接下命令；
- 对诊断型任务，应描述症状，不要提前规定结论；
- 对探索型任务，要给目标和边界，而不是给路线。

**我应该记住什么：**  
> 当你不确定答案时，不要把自己的猜测写进 prompt。让 AI 先看世界，而不是先看你的判断。

---

###### 洞见 2：`/compact` 的核心不是省 token，而是重建注意力结构

###### **核心观点：**  
> 长上下文的问题不是“太贵”，而是模型会开始忘掉中间的重要信息；compact 是为了重新聚焦注意力。

**为什么重要：**  
文章借用了 `lost in the middle` 现象：长上下文中，模型对开头和结尾更敏感，中间信息容易被忽略。

所以，当上下文超过一定比例后，问题不只是成本上升，而是判断质量下降。模型可能开始犯一种很危险的错：  
> 明明你说过，它却像没见过一样。

这不是它“不听话”，而是注意力结构出了问题。

**反常识之处：**  
很多人把压缩上下文理解成“省钱技巧”。但文章指出：  
> compact 更像是一次项目复盘，把关键决策、未完成事项、当前方向重新放回显眼位置。

**可迁移价值：**  
这对任何复杂项目都成立：  
- 会议多了，要做阶段性总结；
- 项目长了，要重写 brief；
- 讨论散了，要重新定义问题；
- 团队协作久了，要对齐当前事实和决策。

**我应该记住什么：**  
> 信息多不等于上下文好。好的上下文是经过整理、排序、聚焦的上下文。

---

###### 洞见 3：跑偏后立刻重开，不是放弃，而是更低成本的资源配置

###### **核心观点：**  
> 被污染的上下文很难修复；与其不断纠偏，不如快速中止、重写 prompt、重新开始。

**为什么重要：**  
当 Claude 已经沿着错误方向推理了一大段，继续让它“修正”往往会产生三重浪费：

1. 你的纠正占用上下文；
2. 它的解释和道歉占用上下文；
3. 旧错误仍会影响后续判断。

这类似人类决策中的锚定效应：一旦前面建立了错误框架，后面即使补充新信息，也很难彻底摆脱原来的路径。

**反常识之处：**  
很多人觉得“都聊这么久了，重开很浪费”。但文章反过来说：  
> 真正浪费的是在错误上下文里继续修补。

**可迁移价值：**  
这可以迁移到很多场景：  
- 产品方向错了，不要用更多功能补救；
- 会议跑偏了，不要继续讨论细节，先重定义问题；
- 代码架构错了，不要只打补丁，必要时重构；
- 关系沟通进入互相防御状态时，继续解释往往不如暂停重来。

**我应该记住什么：**  
> 发现方向错时，最快的前进方式可能是清空，而不是修正。

---

###### 洞见 4：sub agents 的真正价值是“上下文隔离”，不是并行执行

###### **核心观点：**  
> sub agents 最重要的作用，是让探索过程不污染主上下文；父 agent 只接收结论，不承受过程噪音。

**为什么重要：**  
很多任务需要大量搜索、试错、阅读文件，但最终只需要一个小结论。  
例如：

- 找出项目里所有废弃 API 的使用位置；
- 调研某个库的用法；
- 排查 bug 可能涉及哪些模块；
- 列出需要修改的测试文件。

这些任务如果全部塞进主对话，会让主上下文充满低价值过程信息。sub agent 的价值在于：  
> 它可以替主线承受混乱，最后只把干净结论交回来。

**反常识之处：**  
人们容易把多 agent 理解成“更快”。但文章认为，并行只是表层，**隔离才是本质**。

**可迁移价值：**  
这是一个通用组织原则：  
- 高层不应被执行细节淹没；
- 研究过程和决策上下文要分离；
- 探索性任务要有沙盒；
- 汇报应提供结论、证据和建议，而不是把所有过程倒给决策者。

**我应该记住什么：**  
> 主线负责判断，支线负责探索。不要让探索噪音污染决策上下文。

---

###### 洞见 5：最强模型不总是最优解，简单任务用弱模型反而更好

###### **核心观点：**  
> 对简单任务，大模型可能因为过度对齐和复杂场景训练，输出过度设计的方案；弱模型反而更直接、更省维护成本。

**为什么重要：**  
文章提出一个很实用的判断标准：看任务的“认知步骤数”。

- 1-2 步：Haiku  
- 5 步以上：Sonnet / Opus  
- 10 步以上：ultrathink  

这背后的关键不是省钱，而是避免复杂模型把简单问题复杂化。

**反常识之处：**  
常见认知是：模型越强越好。  
但文章指出：  
> 能力过剩会带来设计过度，后期还要花时间删冗余。

**可迁移价值：**  
这在组织和产品里也成立：

- 不要用重流程处理轻问题；
- 不要让高级专家做所有小事；
- 不要为一次性需求设计长期架构；
- 不要给简单产品堆复杂功能。

**我应该记住什么：**  
> 工具能力要匹配任务复杂度。过强，也是一种错配。

---

##### 3. 底层逻辑

###### **逻辑一：AI 的核心资源不是算力，而是注意力**

- **表层现象：**  
  Claude Code 有 `/compact`、`/context`、sub agents、clear 等上下文管理工具。

- **深层原因：**  
  LLM 在长上下文中并不是均匀理解所有信息，而是存在注意力衰减、遗忘、锚定和上下文污染。

- **推导结论：**  
  使用 AI 的关键能力不是“多塞信息”，而是管理注意力：压缩、隔离、重开、聚焦，都是为了让模型始终看见最重要的信息。

---

###### **逻辑二：错误上下文会自我强化，及时切断比持续纠偏更有效**

- **表层现象：**  
  Claude 跑偏后，继续 prompt 它修正往往越改越乱。

- **深层原因：**  
  前面的错误推理会成为后续生成的隐性锚点；纠正信息也会继续占用上下文，使模型在混杂信息里工作。

- **推导结论：**  
  对 AI 协作要建立 `fail fast` 机制：发现方向错，立即中止、重构问题、重新开始，而不是沉没成本式地继续修补。

---

###### **逻辑三：任务管理比指令技巧更重要**

- **表层现象：**  
  文章讨论了 junior 同事心态、sub agents、/loop、多模型选择、agent team。

- **深层原因：**  
  AI 不再只是单次问答工具，而是可以承担探索、执行、监控、反馈等不同角色的协作单元。

- **推导结论：**  
  高阶使用者的优势不是记住更多命令，而是会分配任务：什么该主 agent 做，什么该 sub agent 做，什么该异步监控，什么该弱模型处理，什么该重开。

---

##### 4. 反常识清单

| 反常识观点 | 常见认知 | 文章的不同判断 | 启发 |
|---|---|---|---|
| 对 AI 不要总是下明确命令，有时要描述现象 | prompt 越明确越好 | 过早预设答案会限制模型推理空间 | debug、诊断、探索类任务，要少给结论，多给症状 |

> Claude Code 的高级用法，不是把它当更强的 IDE 插件，而是把它当一个会遗忘、会跑偏、会过度设计、但也能探索和监控的初级同事；高手的工作不是命令它，而是管理它的注意力、上下文和任务边界。

## 结构化（1）

### 2026-05-03 02:09:37

#### Claude Code 的 32 个使用技巧：核心总结

文章借 Nate Herk 的视频，总结了 Claude Code 从入门到高阶的 32 个使用技巧，并进一步拆解其中 6 个最关键但常被忽略的底层逻辑。作者认为，使用 Claude Code 的核心不是掌握命令，而是把它当作一个“注意力有限、时间有限、有性格的 junior 同事”来管理。

---

##### 一、32 个技巧速览：从入门到高阶

原视频在 **16 分钟内讲了 32 个技巧**，按难度分为三类：

###### 1. 入门技巧

- 使用 `/init` 一键生成项目说明书 `cloud.md`
- 开启 **plan mode**，先规划再执行
- 用 `/context` 查看 token 占用
- 当 context 超过 **60%** 时，用 `/compact` 压缩上下文
- 把 Claude 当作 **junior 同事**，多提问题，少直接下命令
- 把 **self check** 加入 todo，让 Claude 自己检查自己的输出

###### 2. 进阶技巧

- 使用 **sub agents** 并行处理任务，避免上下文互相干扰
- 用 **custom skills** 复用 prompt 文件
- 简单任务交给 **Haiku**，节省 token
- 如果 Claude 跑偏，直接 **exit 重开 prompt**
- 用截图反馈问题，做视觉调试

###### 3. 高阶技巧

- 使用 `/loop` 自动执行周期任务，最长可跑 **3 天**
- 用 **Git worktrees** 开多个 session 并行开发
- 把 Claude Code 放到 VPS 上，避免本地断线，也方便手机远程操作
- 对难题使用 **ultrathink**，分配更多 token
- 使用 **agent team**，让多个 agent 分工协作

---

##### 二、把 Claude 当 junior 同事：本质是 prompt 工程

作者强调，“把 Claude 当 junior 同事”不是指语气礼貌，而是指要用更好的沟通方式激发它的推理能力。

###### 关键点

- 命令式 prompt 容易让模型进入“照做”模式，输出快但思考浅。
- 描述式 prompt 更容易让模型先理解上下文，再行动，准确率更高。
- prompt 中不要过早预设答案，否则会限制模型排查范围。

###### 例子

同样是修 bug：

- “修一下这里”  
  Claude 可能只改你指出的那一行。
- “这里看起来怪怪的，你查查为啥”  
  Claude 会更可能先理解上下文，甚至发现真正问题在别处。

再比如：

- “这里有 race condition”  
  会让它只围绕 race condition 排查。
- “这里偶尔会出错，你查查”  
  会让它展开更完整的分析。

---

##### 三、60% 用 `/compact`：不是省 token，而是防止注意力衰减

很多人以为 context 到 60% 后 compact 是为了省 token，作者认为真正原因是对抗 **lost in the middle** 问题。

###### 关键点

- Stanford 2023 年论文指出，LLM 在长上下文中的注意力呈 **U 型曲线**：
  - 开头记得牢
  - 结尾记得牢
  - 中间最容易被忽略
- context 超过约 **60%** 后，模型开始更容易忘记前面提过的重要需求。
- `/compact` 的价值不是简单截断，而是保留关键决策和未完成事项，压缩掉中间杂乱讨论。

###### 判断标准

不要只看 token 数，还要看 Claude 是否开始“忘事”。

如果它开始问：

> “你想做什么？”

这通常说明上下文已经失焦，应该立刻 compact。

---

##### 四、Claude 跑偏就 exit 重开：这是 token 经济学

当 Claude 走偏时，很多人会继续提示它纠正，但作者认为这通常成本更高。

###### 关键点

- 错误推理会污染 context。
- 后续修正 prompt、Claude 的道歉、重新输出，都会继续占用 context。
- 模型容易被前面的错误锚定，类似人类的 confirmation bias。
- 在污染上下文中修正，成本可能比重开高 **2 到 3 倍**，结果还可能更差。

###### 正确做法

建立 **fail fast** 习惯：

- 一旦发现方向错了，立刻 ESC 或 exit
- 重新整理思路
- 用更清晰的 prompt 重开

作者认为，重开不是浪费，而是更聪明的资源分配。

---

##### 五、sub agents 的核心价值：上下文隔离，而不只是并行

sub agents 表面上是为了并行执行任务，但作者认为真正价值是 **隔离上下文**。

###### 关键点

- 父 agent 负责统筹全局。
- sub agent 负责具体探索，可以尝试、失败、绕路。
- 父 agent 只接收最终结论，不被探索过程污染主上下文。
- 这相当于把 context 从“一维资源”变成“树形资源”。

###### 适合 sub agent 的任务

最适合的是：

> 需要大量探索，但最终只需要少量结论的任务。

例如：

- 在 codebase 中找出所有使用 deprecated API 的地方
- 调研某个库的用法
- 查某个 bug 出现在哪些文件
- 列出所有需要修改的测试

父 agent 不需要知道 sub agent 翻过哪些文件，只需要最后的清单。

---

##### 六、简单任务交给 Haiku：不只是省钱，也是避免过度设计

作者指出，不要所有任务都用最强模型。强模型处理简单任务时，可能会“过度设计”。

###### 关键点

- 大模型见过太多复杂场景，容易给简单问题加上不必要的边界处理、错误处理、注释和设计模式。
- 简单 helper 函数：
  - Sonnet 可能写出 **30 行**
  - Haiku 可能只写 **10 行**
- 很多情况下，Haiku 的简单输出反而更合适。

###### 作者的判断标准

按任务的“认知步骤数”选择模型：

- **1 到 2 步**：交给 Haiku
- **5 步以上**：用 Sonnet 或 Opus
- **10 步以上**：再开启 ultrathink

核心原则是：不要无脑用最强模型，否则后期还要花时间删掉冗余代码。

---

##### 七、`/loop` 挂 3 天：真正用途是 monitoring，而不是连续写代码

很多人看到 `/loop` 最长能跑 3 天，会以为它适合让 Claude 连续写代码。作者认为，这不是最佳用法。

###### 关键点

`/loop` 的真正价值是把 Claude 从同步工具变成异步同事，让它定期检查状态，有事再叫你。

好的 `/loop` 任务通常具备三个特征：

- 输入是状态，不是动作
- 输出是“有事 / 没事”的判断
- 处理时间不连续，可以等待

###### 例子

适合 `/loop` 的任务包括：

- 每 **10 分钟** 检查 CI 是否通过，失败后分析原因
- 每小时扫描数据库慢查询
- 每天查看 PR review 队列

这些原本需要人记得去看的事，可以变成 Claude 自动监控并提醒。

---

##### 八、最终心法：不是用工具，而是管理同事

作者认为，Nate Herk 视频真正有价值的地方，不只是列出 32 个技巧，而是传达了一个统一的心智模型：

> 把 Claude Code 当成一个“有限注意力、有限时间、有性格”的同事，而不是无限算力工具。

###### 对应关系

- **注意力有限**  
  所以要管理 context：`/compact`、`/clear`、sub agent 隔离

- **时间有限**  
  所以要异步化：`/loop`、agent team、多 session 并行

- **有性格**  
  所以要讲究沟通方式：plan mode、让它反问、把它当 junior 同事

作者最后总结，自己使用 Claude Code 半年后，最大的认知升级不是某个技巧，而是从“我在用一个工具”转变为“我在管理一个同事”。这种心态变化，会显著影响代码质量、效率和 token 消耗。
