Ask a chat model which Pokemon names end in aw and it fails, even though it knows every Pokemon by heart. Ask Claude Code and it writes a script, fetches the list, and filters for the answer in seconds. Thariq Shihipar, who works on Claude Code at Anthropic, calls that gap capability overhang: models get smarter in spiky ways, and the tools you give them decide which spikes you can reach.

Thariq covers what it takes to work with Fable, Anthropic's newest model. Claude Code cut 80 percent of its system prompt, since heavy instructions now constrain a model more imaginative than the examples it's given. The ask user question tool went from barely working under Opus 4 to generating embedded HTML questionnaires under Fable. He built a full keynote deck in four hours with it, and argues teams should stop picking two of good, fast, and cheap and start demanding all three.

#### 《Field Guide to Fable》精炼总结

Thariq Shihipar 介绍了 Anthropic 新模型 **Fable** 的使用思路：模型能力正在以“不均匀、跳跃式”的方式提升，关键不只是模型本身有多聪明，而是如何用工具、提示词和工作流释放它的能力。  
他认为，使用 Fable 需要重新理解模型、重新设计协作方式，并对效率和质量提出更高要求。

---

##### 1. Fable 登场：像打开开放世界地图

- Thariq 将 Fable 比作 RPG 游戏中“教程结束、开放世界开启”的时刻：
  - 能做的事情突然变多；
  - 机会更多，但也更容易让人困惑；
  - 因此需要一份“使用指南”。

- 他将本次分享分成四部分：
  1. **Unhobbling Claude**：解除对 Claude 的限制；
  2. **Finding your unknowns**：发现自己没意识到的问题；
  3. **Dealing with the grief**：面对编程方式变化带来的失落感；
  4. **Being unreasonable**：不要再过度接受传统取舍。

---

##### 2. 解除 Claude 的限制：模型能力取决于你给它的工具

- Thariq 强调，模型不是被“设计”出来的，而更像是被“培养”出来的：
  - 通过数据、反馈和算力成长；
  - 但它的具体行为需要人类在使用中不断理解。

- 他提出一个核心概念：**capability overhang（能力悬垂）**  
  即模型可能已经具备某些潜在能力，但只有给它合适工具时，这些能力才会显现。

###### 例子：宝可梦名字以 “aw” 结尾

- 如果问普通聊天模型：“哪些宝可梦名字以 aw 结尾？”
  - 它可能答不出来；
  - 即使它“知道”约 1000 个宝可梦名字。

- 但如果问 Claude Code：
  - 它会抓取宝可梦列表；
  - 写脚本筛选以 “aw” 结尾的名字；
  - 很快得到答案：**Croconaw 和 Drednaw**。

- 这个例子说明：
  - 模型不一定能直接靠记忆回答；
  - 但如果给它代码执行、检索等工具，它就能完成任务。

---

##### 3. 模型能力是“尖刺式”进步：提示词和工具要跟着变

- 过去人们以为解决编程问题的方式是：
  - 给模型越来越大的上下文窗口；
  - 例如把整个代码库塞进去。

- 但 Claude Code 的核心启发是：
  - 与其给模型所有上下文，不如给它“手脚”；
  - 例如 bash、搜索、文件操作等工具；
  - 让它自己去构建和探索上下文。

- Claude 的能力也在持续变化：
  - Claude Code 过去需要用户明确提示才工作；
  - Claude Tag 展示了模型可以主动“醒来”并做事；
  - 这被认为是新一代 Agent 的重要方向。

###### 系统提示词减少 80%

- Anthropic 最近将 Claude Code 的系统提示词减少了 **80%**。
- 原因是：
  - 旧模型需要大量规则、示例和限制；
  - 新模型更有创造力，过多示例反而会束缚它；
  - 对 Fable 这类模型，更适合提供背景和上下文，而不是大量“不要做什么”的约束。

###### “向用户提问”能力大幅提升

- Claude Code 有一个“向用户提问”的工具，可在规划时弹出多选问题。
- 能力演进：
  - **Opus 4**：几乎很难稳定调用这个工具；
  - **Opus 4.5**：可以连续向用户提出约 **40 个规格问题**；
  - **Opus 4.8 和 Fable**：可以生成带嵌入式问题的完整 HTML 报告。

- 这说明模型不只是“更聪明”，而是在某些能力点上突然跃迁。

---

##### 4. 发现自己的未知：让 Fable 帮你补齐地图

- Thariq 用“地图不是领土”来解释人和模型协作：
  - 人脑中的计划、提示词、规格说明是“地图”；
  - 真实代码库、环境约束、实际问题是“领土”；
  - 当真实情况超出计划时，就出现了“未知”。

- Fable 能探索很大范围，因此更容易遇到你没说明的问题。  
  所以使用 Fable 的关键，是提前发现这些未知。

###### 四类信息

- **Known knowns（已知的已知）**：你明确知道并写进提示词的内容。
- **Known unknowns（已知的未知）**：你知道自己还没弄清楚的问题。
- **Unknown knowns（未知的已知）**：你心里知道，但没写出来，往往是“看到才知道”的偏好。
- **Unknown unknowns（未知的未知）**：你完全没意识到的问题。

---

##### 5. 使用 Fable 找未知的具体方法

###### 1）Blind spot pass：盲点扫描

- 可以让 Fable 帮你检查某个领域或代码库中可能被忽略的问题。
- 示例提示：
  > “我正在这个代码库里接入一个新的认证服务，但我不熟悉它。请帮我做一次盲点扫描，找出相关的未知风险，并帮我改进提示词。”

- Fable 可以：
  - 阅读认证模块；
  - 找出常见陷阱；
  - 搜索 Git diff、Slack 或其他上下文；
  - 帮用户补齐背景知识。

###### 2）Brainstorm & prototype：头脑风暴和原型

- 对于设计类问题，很多偏好难以提前说清楚。
- 可以让 Fable 生成多个差异很大的方案，再根据结果反馈。
- 示例：
  > “我没有视觉品味，请做一个 HTML 页面，给我 4 种风格完全不同的仪表盘设计。”

- 这样可以帮助用户把“看到才知道”的偏好表达出来。

###### 3）Interviews：让 Claude 采访你

- 当你有初步目标但规格还不完整时，可以让 Fable 主动提问。
- 特别有效的方式是告诉它问题优先级：
  > “请优先问那些会改变架构决策的问题。”

- 这样能避免后期返工。

###### 4）References：给它参考地图

- 最好的“地图”之一，是另一个已经存在的参考。
- 例如：
  - 给它一段相似功能的代码；
  - 给它一个不同语言或系统中的实现；
  - 给它一个 HTML mockup 作为 React 组件的参考。

- Fable 很擅长从参考中理解意图，再迁移到新任务中。

###### 5）Implementation notes：记录实现偏差

- 当 Fable 在执行过程中遇到未知情况时，可以要求它记录下来：
  - 它在哪里偏离了原计划；
  - 为什么做出这个选择；
  - 遇到了什么约束。

- 这样用户可以追踪决策过程，而不是只看到最终结果。

###### 6）Quiz me：让 Fable 反向测验你

- 任务完成后，可以让 Fable 提问，确认你是否真正理解改动。
- 这有助于：
  - 写 PR；
  - 向团队解释实现；
  - 保持人在循环中，而不是完全放手给模型。

---

##### 6. 编程体验的情绪变化：效率提升，也伴随失落

- Thariq 回忆，在 LLM 之前写代码非常艰难：
  - 他曾运营一家约 **30 人** 的 YC 创业公司；
  - 团队经常被迫在性能、功能原型、开发周期之间取舍；
  - 一个功能可能需要 **1 到 2 个月**。

- 但现在回到旧代码库，他发现：
  - 过去要几周的工作，现在可能几小时完成；
  - 这让人既兴奋，也有失落感。

- 他坦言自己曾热爱手写代码：
  - 喜欢在脑中构建和旋转整个代码库；
  - 但也记得无数深夜调试、长期失败和项目夭折。

- 他的结论是：
  - 已经无法回到过去；
  - 只能继续向前；
  - 关键是保持人在循环中，学会和 Fable 协作。

---

##### 7. 不要太“合理”：重新挑战好、快、便宜的取舍

- Thariq 认为，AI 正在改变传统取舍逻辑。
- 过去常说：
  - 好；
  - 快；
  - 便宜；
  - 三者只能选两个。

- 但在 Fable 时代，他主张：
  - 应该尝试三个都要；
  - 不要预设取舍；
  - 先逼近极限，让现实告诉你哪里真的不可能。

###### 案例：4 小时做完整演讲稿和幻灯片

- 他提到自己用 Fable 在前一晚花约 **4 小时** 做完了这次演讲的幻灯片。
- 他认为这说明：
  - 高质量工作可以更快完成；
  - AI 不只是提高生产力，也应该帮助人节省时间。

---

##### 8. 最后的提醒：构建更容易，但创造价值仍然难

- Thariq 强调，AI 让“做东西”变简单了，但“做有价值的东西”仍然困难。
- AI 工程师不能只关注：
  - 工具链；
  - Prompt 技巧；
  - 构建过程。

- 真正重要的是：
  - 多尝试；
  - 找到能创造价值的方向；
  - 证明 AI 不只是潮流，而是真的能改变工作方式。

---

##### 总结

Fable 代表了一类更强、更有创造力的新模型，使用它的关键不是给更多限制，而是给它合适工具、上下文和反馈机制。  
Thariq 的核心建议是：主动发现未知、保持人在循环中、重新挑战传统取舍，并用更高标准证明 AI 能带来真正价值。

### 2026-07-28 06:23:06

#### 当模型的“地图”突然打开：Thariq Shihipar 的 Fable 实地指南

Anthropic 的 Claude Code 团队成员 Thariq Shihipar 从一次看似简单的宝可梦问答讲起，说明更强的模型并不会均匀地获得能力，而是会在工具、提示方式和交互形式改变后，突然展现出过去无法触及的能力。围绕 Fable，他依次讨论了如何解除模型的束缚、找出任务中的未知项、面对编程方式改变带来的得失，以及为什么人们应该开始要求工作同时做到好、快、便宜。

##### 从一张会场自拍，到突然展开的开放世界

演讲开始时，Thariq 先请现场观众配合做一件 Claude Code 团队的传统活动：每次演讲前，他们都会和听众拍一张自拍。拍完照片后，他告诉大家，Fable 即将回归，并会在当天晚些时候逐步推出；中午 12 点 30 分，他还会与 Kat Woo、Simon Wilson 参加一场炉边谈话，届时可能公布进一步消息。

他对 Fable 的描述并不是简单的“性能更强”。在他看来，这是一款会让人记住的 Anthropic 模型，就像 Sonnet 3.5 New、Opus 4 和 Opus 4.5 一样。他用角色扮演游戏来形容第一次使用它的感受：玩家过去似乎一直停留在教程阶段，直到某个时刻，地图忽然打开，开放世界真正出现。眼前有大量可以探索和完成的事情，但正因为可能性骤然增多，使用者也会感到困惑，甚至有些不知所措。

因此，这场演讲不是一份功能清单，而是一份面向新一类模型的“实地指南”。Thariq 把它分成四条相互连接的线索：解除 Claude 的束缚，找出自己的未知项，面对生产方式改变带来的失落，最后变得“不那么合理”。

##### 模型知道所有宝可梦，却答不出谁以“aw”结尾

Thariq 首先解释，Anthropic 经常说模型是“生长出来的”，而不是按照功能表逐项设计出来的。研究人员不会起床后决定，今天要专门把模型在 SWE-bench 上的成绩做到 99%。他们提供数据、反馈和算力，谨慎地培养模型，但模型最终会呈现出某种有机性。很多能力要等到实际使用时，团队才逐渐发现和理解。

这也意味着，限制模型的不只是它自身的能力，还有人类放在它外面的框架、工具和提示词。一个产品采用什么运行环境、给模型开放哪些工具、在系统提示中写入什么要求，都取决于开发者当时对 Claude 的理解。所谓“解除 Claude 的束缚”，就是更准确地理解它，进而把那些已经存在、却还没有被正确调用的能力释放出来。

为了说明这种现象，Thariq 提到一条曾经广泛传播的帖子：如果问普通聊天模型，哪些宝可梦的英文名字以“aw”结尾，它往往答不出来。这个问题看起来并不难。在大约一千个宝可梦中，符合条件的有两个：Croconaw 和 Drednaw。模型明明知道这些宝可梦的名字，却无法稳定完成这种筛选。

但如果把同一个问题交给 Claude Code，结果就不同了。Claude Code 会获取完整的宝可梦名单，编写一段脚本，再筛选出以“aw”结尾的名称，于是很快得到那两个答案。模型并不是突然多记住了两个名字，而是因为获得了代码执行能力，能够把原本难以直接完成的问题转化成获取数据、运行脚本和过滤结果的流程。

Thariq 把这种尚未被充分利用的能力差距称为“capability overhang”。模型变强并不是平滑、均匀的，而是呈现出尖峰状：它可能无法靠记忆和直接推理完成某项任务，但只要给它合适的工具，那一处能力尖峰就能被触及。Fable 带来的挑战，正是重新判断这些尖峰现在出现在哪里——哪些事情已经成为可能，只是人们还没有找到正确的使用方式。

Claude Code 本身就是这种变化的结果。早期使用聊天模型处理代码时，人们必须把上下文直接交给模型，例如复制粘贴代码库。按照一种朴素的设想，解决编程问题的方法似乎只是不断扩大上下文窗口，直到有一天可以把整个代码库塞进一个一亿 token 的窗口。

真正产生突破的方向却不是单纯扩大窗口，而是给模型“手臂”：为它提供 Bash 等工具，让它能够进入环境，搜索文件、执行命令，并为自己建立所需的上下文。这一认识最终促成了 Claude Code。模型不再只能被动接收人类整理好的材料，而是可以主动探索工作环境。

后来推出的 Claude Tag 又体现了另一种能力变化。Claude Code 通常需要人在前面发出提示，模型才开始工作；Claude Tag 所利用的，则是 Claude 在多人协作环境中主动工作、自己唤醒自己执行任务的能力。Thariq 认为，这种主动性正在打开新一轮智能体应用。

随着模型变化，系统提示的最佳写法也在改变。Claude Code 最近删除了系统提示中约 80% 的内容。早在 Sonnet 3.5 New 前后，更有效的配置通常是较短的系统提示、少量工具和大量示例。后来模型的指令遵循能力增强，开发者开始给它更大的系统提示、更多示例和更多工具。

但到了新的模型阶段，团队发现系统提示又需要缩短。过去用来帮助模型的示例，现在反而可能限制模型，因为模型的想象力已经超过了示例所展示的范围。团队因此更倾向于提供上下文，而不是堆叠约束，也尽量避免反复写“不要做某事”。这种禁止性指令对上一代模型可能非常必要，对新模型却未必仍是最合适的做法。

“向用户提问”工具的变化更直观。Thariq 刚加入 Claude Code 时曾参与开发这一功能：当 Claude 制订计划或需要补充信息时，可以向用户展示一个多项选择对话框。在 Opus 4 时，模型几乎无法可靠调用这个工具，他不得不仔细调整工具设计，才能让它正常工作。

到了 Opus 4.5，他尝试让模型围绕一份规格说明提出 40 个问题，Claude 已经能够像采访者一样连续追问。再到 Opus 4.8 和 Fable，它不仅能提问，还可以生成一份完整的 HTML 报告，把问题直接嵌入报告中。模型从用户那里获取信息的方式，因而从一次简单调用变成了一种新的交互界面。

输出形式也经历了类似演进。起初，Markdown 只是模型呈现稍丰富信息的一种格式；出现计划模式后，Markdown 开始帮助用户理解 Claude 接下来准备做什么；如今，Claude 已经能够生成内容深入的 HTML 报告。Thariq 因此强调，理解模型更像是在研究生物学，而不是物理学：其中存在经验和规律，也能够培养直觉，但人们还没有掌握全部规则。他建议使用者以这种方式对待 Fable，并推荐 Anthropic 的论文《The Biology of a Large Language Model》，作为进一步理解模型行为的材料。

##### Fable 走得越远，人越需要找到地图上没有标出的东西

解除模型的束缚只是第一步。使用 Fable 时，Thariq 发现，人也需要解除自己的束缚，因为计划与现实之间始终存在差距。

他借用了“地图不是领土”这一说法。在一个编程任务中，使用者脑中的计划、提示词和规格说明只是地图；真正的领土则是实际代码库、现实环境，以及 Claude 在执行过程中必须处理的各种约束。只要 Claude 在真实环境中遇到一件地图上没有标明的事情，就出现了一个“未知项”：它必须做出决定，而人事先没有说明该怎么做。

Fable 是最早让 Thariq 强烈意识到这个问题的模型之一。因为它能够自主穿越的范围很大，执行越深入，遇到未指定决策点的机会就越多。模型的瓶颈于是可能不再是代码能力，而是使用者能否让地图尽量贴近领土，提前发现那些会影响执行的未知项。

他用一个矩阵来区分任务中的不同信息。首先是“已知的已知”，也就是人明确知道并通常会写进提示词的目标。其次是“已知的未知”，人知道某些问题尚未弄清，只是还没有解决。第三类是“未知的已知”：一些要求对使用者而言过于理所当然，所以不会特意写下来，但看到结果时又能立刻判断是否符合预期。最后是“未知的未知”，也就是人完全没有考虑过，却可能在知道后改变提示方式甚至改变整个方案的信息。

好在，Fable 不仅会撞上这些未知项，也可以反过来帮助人寻找它们。Thariq 常做的第一件事叫“盲点检查”。例如，他可能要在一个代码库中接入自己完全不了解的新身份验证提供商。正式实现前，他会让 Claude 检查相关认证模块，帮助找出与当前任务有关的“未知的未知”，并据此改进后续提示。

在这个过程中，Claude 可能发现认证模块里存在一个经常让人走入死路的复杂角落。Thariq 也可能告诉它其他上下文存在于哪里，让它搜索 Git diff 或 Slack，找出过去出现过的问题、约束和容易踩中的坑。这种方法并不限于代码。他在进行视频剪辑、学习调色时，也曾用同样的方式让模型帮助自己了解陌生领域。模型在很多主题上知道得比他多，关键是如何把这些知识从模型中提取出来。

面对“未知的已知”，他会使用头脑风暴和原型。设计任务尤其如此：有些偏好很难事先用语言准确描述，人只能在看到方案后说出喜欢或不喜欢。比如要制作一个仪表盘时，他会直接告诉模型自己“没有视觉品味”，然后让它在一个 HTML 页面中做出四种差异很大的设计方案。人先对具体方案产生反应，再和模型一起逐步弄清那些原先无法表达的要求。

当方向大致确定后，仍然可能有大量尚未明确的决策。此时，他会要求 Claude 采访自己。为了让问题更有价值，他会补充个人背景、工作内容和项目所处阶段，并明确要求模型优先提出那些可能改变系统架构的问题。这样，提问就不再是泛泛的信息收集，而是在实现开始前寻找真正会改变方案的缺口。

参考物也是建立地图的重要方式。Thariq 认为，给 Claude 地图的最好办法之一，就是直接给它另一张地图。与其亲自写完一整份规格说明，不如交给模型一段能代表目标的现有代码，让它先阅读、理解，再以此开始工作。这段参考代码甚至可以来自不同的系统或编程语言。如果要制作 React 组件，一份 HTML 模型稿也可以成为参考地图。Fable 擅长从这类具体材料中提取结构和意图。

即使准备充分，执行期间仍会出现新的未知项。Thariq 建议，在 Fable 运行时要求它记录这些地方，也就是留下“实现说明”。这样，使用者之后能够看到实际实现在哪些位置偏离了原计划，也能通过模型补充的上下文理解偏离为什么发生。

最后，他还会让 Fable 就已经完成的工作反过来测验自己。这不是为了考察模型，而是为了确认自己仍然理解实现过程，能够在创建拉取请求或合并代码时解释所做的工作。对 Thariq 来说，使用 Fable 的关键不是让模型独自跑得越远越好，而是人必须持续留在回路中，知道它遇到了什么、做出了什么决定，并确认最终得到的确实是自己想要的结果。

##### 从几周缩短到几小时，效率提升也带来了失落

第一次使用 Fable 这一类模型时，Thariq 同时感到巨大的收获和明显的失落。回想大语言模型出现前的编程生活，他觉得那已经像一个遥远而陌生的国家。

他过去经营过一家约有 30 人的 YC 创业公司。由于写代码太困难，团队一直被迫在不同目标之间做取舍。他们可以选择让应用运行得更快，也可以选择为新功能做原型；一个方向可能需要一个月，另一个方向可能需要两个月，因此团队必须放弃其中一些事情。做决定的基础，并不总是哪个目标更重要，而是工程实现本身太慢、太难。

几周前，他重新打开了那套代码库，开始考虑一些过去想做却难以推进的工作。曾经需要数周才能完成的事情，现在几小时就能做到。面对这种差距，他说，人很难不笑，也很难不哭。

这种失落并不是因为他讨厌编程。相反，他非常喜欢亲手写代码，也喜欢在脑海中看见整个代码库、像旋转一个物体那样理解它的结构。但他同样记得那些为了调试而熬到深夜的时刻，记得在某些问题上连续工作数周却没有进展，也记得大量项目最终失败。他用“在失败中游泳”形容那种经历：自己做过的大部分项目都失败了，大多数创业公司也会破产。编程带来过强烈的满足感，但它始终是一件极其困难的事。

因此，即使怀念过去的高峰体验，他也无法再回到原来的工作方式。他的结论是，“唯一的出路是穿过去”。人们仍然需要学习新的编码方式，也仍然需要学习如何使用 Fable；但如果持续尝试、让人留在回路中，并努力解除模型的束缚，就可能穿过这段变化，最终获得远多于过去的成果。

## 口播总结（1）

### 2026-08-03 00:58:14

#### Fable 实战指南：如何释放更强模型的能力

Anthropic 的 Claude Code 团队成员 Thariq Shihipar 认为，Fable 代表了一类能力更强、但也更需要重新学习使用方法的模型。接下来，你会了解四件事：怎样释放模型的潜力，怎样发现任务中的未知问题，怎样面对编程方式的变化，以及为什么我们可以对效率和质量提出更高要求。

##### 首先，别用旧方法限制新模型

核心结论是：模型能力提升后，过去有效的提示方式和工具配置，反而可能成为限制。

Anthropic 常说，大模型更像是“生长”出来的，而不是按照一张精确蓝图设计出来的。研究者通过数据、反馈和算力培养模型，再在使用过程中逐渐理解它。因此，真正限制模型的，往往不只是模型本身，还有外部给它的工具、提示词和工作环境。

这里有一个典型例子。如果直接问聊天模型，哪些宝可梦的英文名字以字母“a、w”结尾，它可能答不出来。不是因为它不认识这些名字，而是因为它不擅长在记忆中逐个筛选。

但 Claude Code 会换一种做法。它可以获取完整名单，写一段程序，再筛选出答案：Croconaw 和 Drednaw。

这种现象被称为“能力余量”。简单说，就是模型已经具备某些潜在能力，但只有配上合适的工具，才能真正发挥出来。模型的进步也不是每个方面同时、均匀提升，而是会在某些能力上突然跃升。

Claude Code 本身就是这种思路的产物。早期有人以为，解决复杂编程任务的关键，是把整个代码库都塞进越来越大的上下文窗口。后来发现，更有效的方法是给模型“手和脚”，比如终端命令工具，以及搜索和操作环境的能力。这样，模型可以自己寻找信息，建立完成任务所需的上下文。

更重要的是，模型变强以后，使用说明也必须跟着变化。Claude Code 最近删掉了大约百分之八十的系统提示词。所谓系统提示词，就是在用户提问之前，预先告诉模型该遵守什么规则、怎样工作的那套内部说明。

过去，模型需要大量明确指令和示例。现在，过多示例可能会限制它，因为新模型有时比示例本身更有想象力。因此，团队开始减少“不要这样做”式的约束，转而提供任务背景和必要信息。

模型提问的方式也发生了类似变化。早期的 Opus 4 甚至很难稳定调用“向用户提问”工具。到了 Opus 4.5，它已经可以围绕一份需求文档，连续采访用户几十个问题。到了后续模型和 Fable，它甚至能制作一份完整的 HTML 交互报告，把问题直接嵌入其中。

所以，面对 Fable，第一步不是套用旧经验，而是重新试验：它现在能做什么？给它什么工具，才能把潜在能力真正释放出来？

##### 接下来，主动找出任务里的未知问题

第二个核心结论是：Fable 的能力越强，人就越需要把自己的意图和现实条件说清楚。

Thariq 用“地图和领土”来解释这件事。你脑中的计划、提示词和需求文档，是地图。真实的代码库、业务环境和现实限制，才是领土。

只要现实里出现了地图没有标明的情况，模型就会遇到一个“未知问题”。这意味着，它必须在你没有明确说明的地方自行判断。Fable 能探索的范围更大，所以也更容易遇到大量这样的决策点。此时，瓶颈可能不再是模型能力，而是人能不能提前发现这些未知问题。

这些信息大致可以分成四类。

第一类，是你明确知道的事情，比如想实现什么功能。第二类，是你知道自己还没想清楚的问题。第三类，是你心里知道、却没有写下来的标准，比如设计是否顺眼，往往要看到以后才知道。第四类，则是你完全没有考虑过的风险和条件。

好消息是，Fable 本身也可以帮助你寻找这些未知。

首先，可以让它做一次“盲点检查”。比如，你准备在陌生代码库里接入新的身份认证服务，就可以先让模型检查相关模块、代码改动记录和团队讨论，找出容易踩坑的地方。这个方法也能用于学习新领域。Thariq 就曾用它来了解视频剪辑中的调色知识。

接下来，可以让模型提供多种原型，帮助你发现那些难以用语言描述的偏好。比如，请它为同一个仪表盘制作四种差异明显的设计。你不必一开始就准确说出自己想要什么，只要看到不同方案，就更容易判断哪些方向合适。

然后，可以反过来让模型采访你。当你已经有一个大概方向，却担心遗漏重要条件时，可以要求它优先询问那些可能改变整体架构的问题。这样，提问就不只是补充细节，而是在真正影响方案之前暴露关键分歧。

另外，参考样例往往比长篇说明更有效。你可以给模型一段其他语言或其他系统里的代码，让它先理解其中的结构，再迁移到当前任务。制作网页组件时，也可以把一个 HTML 原型当作“地图”，让模型据此实现。

在执行过程中，还可以要求 Fable 记录“实施说明”。每当现实情况迫使它偏离原计划，就把原因记下来。任务完成后，再让它反过来测试你，确认你是否真正理解了改动。这样，在提交代码或与团队沟通时，人仍然处在决策回路之中，而不是把工作完全交给模型后失去掌控。

##### 更重要的是，承认编程方式变化带来的复杂感受

第三个核心结论是：AI 带来的不只是效率提升，也会让程序员产生真实的失落感。

Thariq 回忆，在大模型出现之前，他经营过一家大约三十人的创业公司。因为写代码太难，团队总要在不同目标之间取舍。让应用运行得更快，或者试验一个新功能，可能分别需要一个月甚至两个月，很多想法只能放弃。

后来，他重新回到当年的代码库。过去需要几周完成的工作，现在可能几小时就能完成。这种变化让人兴奋，也让人难过。

一方面，手写代码曾经带来很强的创造感。优秀的程序员会在脑中形成整个代码库的结构，并反复推演。另一方面，真实的编程工作也包含无数深夜调试、长期失败和最终夭折的项目。大多数创业公司会失败，很多软件项目也无法达到预期。

因此，他的态度不是怀念旧方式，也不是否认失落，而是继续向前。他所说的“唯一的出路，就是穿过去”，意思是要继续学习人与模型协作的新方法，同时保持自己对过程的理解和控制。只有这样，效率提升才不会以失去判断力为代价。

##### 最后，对质量、速度和成本提出更高要求

第四个核心结论是：模型正在改变过去那些看似理所当然的取舍。

传统项目管理常说，质量好、速度快、成本低，只能三选二。Thariq 认为，在 Fable 这样的模型帮助下，可以开始尝试“三个都要”。

这并不是说所有取舍已经消失，而是不要过早替现实做决定。过去，人们习惯先列出优先级，主动放弃一部分目标。现在，可以先要求模型同时满足更高标准，让实际执行结果证明哪些限制真的存在。

他用自己的演讲文稿举例。整套主题演讲幻灯片，是他和 Fable 在大约四个小时内完成的。他对质量感到满意，同时也显著缩短了制作时间。这个案例说明，更高生产力并不一定意味着投入更多工作时间，也可能意味着更快完成重要工作，把时间留给自己真正关心的人。

不过，还有一个必须保持清醒的地方：把东西做出来变容易了，不代表创造价值也变容易了。

AI 工程师很容易把注意力集中在工具、流程和配置上，但最终目标不是生成更多代码，而是解决真正有价值的问题。找到价值仍然需要很多尝试，也可能经历多次失败。AI 降低的是建造成本，却不会自动告诉人什么值得建造。

##### 最值得记住的四个结论

最后，回顾四点。

第一，Fable 的潜力不只取决于模型本身，也取决于工具、提示词和工作环境。旧方法可能会限制新模型。

第二，任务越复杂，越要区分脑中的“地图”和现实中的“领土”。要主动用盲点检查、原型、采访、参考样例和实施记录，找出未知问题。

第三，AI 编程既带来巨大效率提升，也可能带来失落感。关键不是退回过去，而是在继续前进时保持理解和参与。

第四，可以更大胆地同时追求质量、速度和低成本，但不要混淆“容易做出来”和“真正有价值”。最终要证明的，不是 AI 能生成多少内容，而是它能否帮助人们更快完成更好的工作，并节省真正宝贵的时间。

#### AI Agent 的瓶颈正在从“会不会做”转向“如何定义与控制”

能力更强的 Agent 能走得更远，也会遇到更多需求中没有写明的岔路。此时，瓶颈不再只是提示词是否清楚，而是人有没有意识到哪些决定尚未做出。

演讲提出的一组方法，本质上是在建立需求发现与控制循环：先让模型做“盲点扫描”，找出代码库和业务约束中的坑；用差异足够大的原型，暴露那些“看到才知道喜不喜欢”的隐性偏好；让模型优先追问会改变架构的事项；用现有代码、原型和案例代替冗长描述；执行中记录偏离原计划的决策，最后再让模型反向检查人的理解。

对产品工作而言，这比“写出完美 PRD”更重要。未来高质量规格的核心，可能不是穷尽所有细节，而是明确三件事：**目标是什么，哪些边界不能越，遇到未定义情况时谁拥有决策权。**

##### “好、快、便宜”可以重问，但价值不会自动产生

作者主张不再接受传统取舍，这种态度有合理部分：当实现成本骤降，许多过去因资源不足而被放弃的方案，确实值得重新估价。但“取舍消失”说得过头了。AI 降低的是制作和试错成本，并没有自动解决需求是否真实、结果是否可信、组织能否采用等问题。

更准确的变化是：**稀缺性从生产能力迁移到了问题选择、判断与验证。** 四小时做完一套演示文稿，只能证明交付更快；只有它帮助受众理解、决策或行动，才形成价值。

因此，真正值得“不讲道理”的不是盲目要求更多产出，而是把曾被成本压制的目标重新拿出来验证；同时，把省下的时间投入用户研究、结果评估和高风险决策。Agent 越强，团队越不该沉迷于“它能做什么”，而应更严格地回答：“什么事情值得让它做？”
