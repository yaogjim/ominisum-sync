## 分析要点

- **核心高价值点**：Pi 将工具、钩子、模型、会话和界面统一暴露为可热重载的扩展接口，使同一代理内核可从本地 CLI 迁移为受控的多租户应用。
- **留存建议**：精读并存档，作为构建可扩展代理与托管产品的实现参考（包含具体扩展接口、代码示例和多租户代理架构，具有较强的复用与实践价值。）

**知识要点**

- Pi 扩展可通过 pi.registerTool、pi.on\(event\) 和 ctx 对象分别注册能力、拦截生命周期事件并访问实时会话。
- before\_agent\_start 可预注入 Git 等环境上下文，tool\_result 类钩子可在模型接收结果前压缩工具输出。
- 托管式多租户部署应使用内存会话，将数据库作为事实来源，并为每位用户隔离工作目录、工具权限和执行沙箱。

**行动项**

- 实现一个 before\_agent\_start 扩展注入 Git 摘要，并验证代理无需调用工具即可识别当前分支。
- 实现输入权限门，根据策略文件在请求进入主代理前完成允许或拒绝判断。
- 用 createAgentSession、SessionManager.inMemory 和受限 ResourceLoader 搭建最小托管代理原型。

#### 扩展系统

几乎可以自定义任何内容：工具、钩子、模型提供商、会话管理、命令，以及终端界面本身。由于 Pi 了解自身的扩展 API，因此你通常不需要编写代码。告诉 Pi“把天气信息放入我的提示输入中”，它会读取扩展文档、生成小部件并重新加载。

![Image](https://pbs.twimg.com/media/HMnsa3ybwAAM7ek?format=png&name=large)

扩展是一个连接到测试框架的 TypeScript 文件。Claude Code 也有钩子，所以区别在于暴露范围。Pi 几乎通过三个对象暴露了所有的接口点：

- pi.\* 注册了新能力：registerTool、registerCommand、registerShortcut、registerProvider（您自己的 LLM）、sendUserMessage、setActiveTools。
- pi.on(event) 响应整个生命周期：输入、session\_start、before\_agent\_start、tool\_call、tool\_result、context、before\_provider\_request、session\_before\_compact。
- ctx.\* 进入实时会话：ctx.ui、ctx.sessionManager、ctx.cwd、ctx.model。

同时， /reload 为你提供热重载功能，这样代理在你使用它时可以重写自身的框架。

示例 - TUI 自定义: 我可以重新换肤我的 pi TUI - 在会话开始时调用一次 ctx.ui.setHeader(...)。或者在提示输入上方添加天气信息

#### 如何构建扩展

构建树莓派扩展实际上非常简单，以下是一些示例：

1. 注入上下文。无需任何工具调用，使代理具备 Git 感知能力。

```text
pi.on("before_agent_start", (event, ctx) => {
  return { systemPrompt: event.systemPrompt + "\n\n" + gitSummary() };
});
```

问“我现在在哪个分支？不使用任何工具”，它就已经知道了。

2\. 添加一个工具。让代理读取你的剪贴板：

```text
pi.registerTool({
  name: "read_clipboard",
  description: "Read what's currently in the clipboard",
  execute: async () => ({ content: [{ type: "text", text: await clipboard.read() }] }),
});
```

借助这个 Pi，可以使用一个新工具'read\_clipboard'

3\. 权限门

我在我的团队共享代理上运行这个，因为不是每个人都应该看到所有内容。在提示到达代理之前，一个轻量的 Haiku 调用会根据 PERMISSION.md 策略对其进行分类，决定允许或拒绝它：

```text
import { complete } from "@earendil-works/pi-ai";

pi.on("input", async (event, ctx) => {
  const policy = await readPolicy(ctx.cwd);
  if (!policy) return { action: "continue" };
  const { decision, reason } = await classify(ctx, policy, event.text); // Haiku
  if (decision === "denied") {
    ctx.ui.notify(`Blocked by PERMISSION.md: ${reason}`, "error");
    return { action: "handled" };   // skip the agent entirely
  }
  return { action: "continue" };
});
```

我设置了这样的策略："只有 Jason 能查看收入数据"，并以其他人的身份询问"6 月收入是多少？"。Pi 在请求到达代理之前拦截了该请求，并在用户界面中显示了原因。

#### 使用 Pi SDK 构建真实的 AI 应用

大多数人没意识到，Pi 不只是一个 CLI。它由五个包组成：pi-ai（调用任何模型，支持 Claude 和 Codex 订阅 OAuth 认证）、pi-agent（核心循环）、pi-coding-agent（与 Claude Code SDK 等效，包含工具、会话、压缩、扩展）、TUI 以及一个编排器。整个代理简化为一个函数调用。

![Image](https://pbs.twimg.com/media/HMnyo3yaEAAJWtM?format=jpg&name=large)

这里是大约 15 行的代理，无 UI：

```text
import { createAgentSession, SessionManager } from "@earendil-works/pi-coding-agent";

const { session } = await createAgentSession({
  sessionManager: SessionManager.inMemory(),
});

session.subscribe((event) => {
  if (event.type === "message_update" && event.assistantMessageEvent.type === "text_delta") {
    process.stdout.write(event.assistantMessageEvent.delta);   // stream to your UI
  }
});

await session.prompt("Look at the files here and tell me what this project is.");
```

运行 npx tsx 并监视其输出流，使用您现有的 Pi 身份验证（您的 Claude 订阅，文件中无需 API 密钥）。将同一个会话封装到 WebSocket 中，您就拥有了一个托管的聊天代理，每个浏览器标签页对应一个会话。

对于一款产品，你使用资源加载器和你自己的工具为每个会话定义范围：

```text
const resourceLoader = new DefaultResourceLoader({
  cwd,                                  // where the agent WORKS (a per-user sandbox)
  agentDir: getAgentDir(),              // config/auth root, stays on the host
  noExtensions: true, noSkills: true,   // deny ambient pickup, allow only what you pass
  extensionFactories: [guardrail],      // policy as code (e.g. block dangerous bash)
});
await resourceLoader.reload();

const { session } = await createAgentSession({
  sessionManager: SessionManager.inMemory(),
  customTools: [getMrr],                // your product's own capabilities
  resourceLoader,
});
```

我用这个确切的形状来构建 Posia，一个能够启动和运营业务的自主代理。选择 Web 托管而非本地部署需要你进行一个调整：Pi 的默认设置假设使用本地文件系统，其中会话以 JSONL 格式存在，工具在主机上运行。

对于多租户后端，运行 SessionManager.inMemory()，将您自己的数据库视为事实来源，通过镜像 session.subscribe，并通过每个用户的沙箱进行 re-back bash、读取和写入操作。

#### Pi agent 101：如何扩展和构建自己的框架

Pi 是驱动 OpenClaw 的核心代理框架，特点是**高度可扩展**：工具、模型、会话、命令、界面等几乎都能改。它不仅是 CLI，也可以作为 SDK 嵌入到真实 AI 产品中，用来构建网页端、多租户、自定义工具的代理应用。

---

##### 1. Pi 的扩展系统：几乎所有东西都能自定义

Pi 的扩展通常是一个 **TypeScript 文件**，用来接入框架能力。由于 Pi 理解自己的扩展 API，很多时候你甚至不用手写代码，只要告诉它想改什么，例如：

> “把天气信息放到我的提示输入框上方。”

Pi 会自动读取扩展文档、生成小部件并重新加载。

###### 核心能力由三个对象暴露

###### `pi.*`：注册新能力

用于添加工具、命令、快捷键、模型提供商等，例如：

- `registerTool`：注册工具
- `registerCommand`：注册命令
- `registerShortcut`：注册快捷键
- `registerProvider`：接入自己的 LLM
- `sendUserMessage`：发送用户消息
- `setActiveTools`：设置可用工具

###### `pi.on(event)`：监听代理生命周期

可以在代理运行的各个阶段插入逻辑，例如：

- 用户输入时：`input`
- 会话开始：`session_start`
- 代理启动前：`before_agent_start`
- 工具调用前后：`tool_call`、`tool_result`
- 上下文处理：`context`
- 请求模型前：`before_provider_request`
- 会话压缩前：`session_before_compact`

###### `ctx.*`：访问当前会话状态

可以操作当前界面、会话、工作目录和模型，例如：

- `ctx.ui`
- `ctx.sessionManager`
- `ctx.cwd`
- `ctx.model`

此外，Pi 支持 `/reload` 热重载，意味着扩展可以边用边改，代理甚至能“重写自己的外壳”。

```ts
pi.registerTool({
```

##### 6. Pi SDK：不只是 CLI，也能构建真实 AI 应用

很多人以为 Pi 只是命令行工具，但它实际上由多个包组成：

1. `pi-ai`：调用任意模型，支持 Claude 和 Codex 订阅 OAuth 认证
2. `pi-agent`：核心代理循环
3. `pi-coding-agent`：类似 Claude Code SDK，包含工具、会话、压缩、扩展
4. TUI：终端界面
5. 编排器：负责整体调度

也就是说，整个代理可以简化成一个函数调用，并嵌入到自己的应用里。

##### 7. 用约 15 行代码创建一个无 UI 代理

文章展示了一个简单代理：

```ts
import { createAgentSession, SessionManager } from "@earendil-works/pi-coding-agent";

const { session } = await createAgentSession({
  sessionManager: SessionManager.inMemory(),
});

session.subscribe((event) => {
  if (
    event.type === "message_update" &&
    event.assistantMessageEvent.type === "text_delta"
  ) {
    process.stdout.write(event.assistantMessageEvent.delta);
  }
});

await session.prompt("Look at the files here and tell me what this project is.");
```

特点：

- 无需 UI
- 可以流式输出到自己的界面
- 可使用现有 Pi 身份认证
- 支持 Claude 订阅
- 文件中不需要写 API Key

如果把这个会话封装到 WebSocket 中，就可以做成网页聊天代理，每个浏览器标签页对应一个独立会话。

---

##### 8. 面向产品的部署方式：限制资源和工具范围

构建产品时，可以用 `resourceLoader` 控制每个会话能访问什么资源。

示例能力包括：

- `cwd`：代理工作的目录，通常是每个用户的沙箱
- `agentDir`：配置和认证目录，保留在宿主机
- `noExtensions: true`：禁止自动加载外部扩展
- `noSkills: true`：禁止自动加载技能
- `extensionFactories: [guardrail]`：只允许传入受控扩展，例如安全策略
- `customTools: [getMrr]`：只提供产品自定义工具

这样可以避免代理随意访问宿主环境，适合线上产品。

---

##### 9. 多租户后端：需要调整 Pi 的默认假设

Pi 默认更适合本地运行：

- 会话以 JSONL 文件形式存储
- 工具直接在本机运行

如果要做多租户 Web 后端，需要改成：

- 使用 `SessionManager.inMemory()`
- 把自己的数据库作为真实数据源
- 通过 `session.subscribe` 同步会话事件
- 每个用户使用独立沙箱来执行 bash、读写文件

这样才能支持多人、多会话、安全隔离的在线代理服务。

##### 目标

构建一个类似轻量版 Posia 的内部 AI Agent，帮助 SaaS 团队完成运营任务，例如：

- 查询 MRR、收入、用户增长等业务指标
- 阅读当前代码仓库和 Git 状态
- 修改运营脚本、生成分析报告
- 在 Web 端为不同团队成员提供独立会话
- 根据权限策略阻止敏感问题，例如普通成员不能查看收入数据

这个实例基于 Pi 的三个核心能力：

1. **Extension 扩展系统**
2. **Pi SDK / `pi-coding-agent`**
3. **生命周期 Hook 与自定义 Tool**

---

#### 三、核心实现

##### 1. 定义权限策略

`PERMISSION.md`

```md
# 权限策略

- Jason 可以查看收入、MRR、ARR、客户付款信息。
- Growth 团队可以查看用户增长、注册量、留存率。
- 工程团队可以查看代码仓库、日志和构建信息。
- 其他用户不能查看收入、客户付款、成本、利润相关数据。
```

##### 2. 权限门扩展：在请求进入 Agent 前拦截

这是最重要的扩展之一。

```ts
//src/agent/extensions/permissionGate.ts

import fs from "node:fs/promises";
import path from "node:path";
import { complete } from "@earendil-works/pi-ai";

async function readPolicy (cwd: string) {
  const policyPath = path.join (cwd, "PERMISSION.md");

  try {
    return await fs.readFile (policyPath, "utf-8");
  } catch {
    return null;
  }
}

async function classifyPermission ({
  userName,
  userRole,
  policy,
  input,
}: {
  userName: string;
  userRole: string;
  policy: string;
  input: string;
}) {
  const prompt = `
你是一个权限分类器。

用户：
- name: ${userName}
- role: ${userRole}

权限策略：
${policy}

用户请求：
${input}

请判断该请求是否允许。

只返回 JSON：
{
  "decision": "allowed" | "denied",
  "reason": "简短原因"
}
`;

  const result = await complete ({
    model: "claude-3-5-haiku-latest",
    messages: [{ role: "user", content: prompt }],
  });

  return JSON.parse (result.text);
}

export function permissionGateExtension (user: {
  id: string;
  name: string;
  role: string;
}) {
  return (pi: any) => {
    pi.on ("input", async (event: any, ctx: any) => {
      const policy = await readPolicy (ctx.cwd);

      if (!policy) {
        return { action: "continue" };
      }

      const { decision, reason } = await classifyPermission ({
        userName: user.name,
        userRole: user.role,
        policy,
        input: event.text,
      });

      if (decision === "denied") {
        ctx.ui?.notify?.(`Blocked by PERMISSION.md: ${reason}`, "error");

        return {
          action: "handled",
        };
      }

      return {
        action: "continue",
      };
    });
  };
}
```

###### 最佳实践

- **权限检查要放在`pi.on ("input")`中**，因为这是用户请求进入 Agent 前的最早拦截点。
- **敏感问题应该在 Agent 看到之前就被拦截**，而不是让模型自己决定是否回答。
- **默认应 fail closed**：权限不明确时拒绝，而不是放行。
- **策略文件应该可审计**，例如`PERMISSION.md`进入 Git 管理。

##### 3. 注入 Git 上下文：减少无意义工具调用

让 Agent 不用调用`bash`就知道当前分支、最近提交等信息。

```ts
//src/agent/extensions/gitContext.ts

import { execSync } from "node:child_process";

function safeExec (command: string, cwd: string) {
  try {
    return execSync (command, {
      cwd,
      encoding: "utf-8",
      timeout: 2000,
      stdio: ["ignore", "pipe", "ignore"],
    }).trim ();
  } catch {
    return "";
  }
}

function gitSummary (cwd: string) {
  const branch = safeExec ("git branch --show-current", cwd);
  const status = safeExec ("git status --short", cwd);
  const lastCommit = safeExec ("git log -1 --oneline", cwd);

  return `
当前 Git 上下文：

- Branch: ${branch || "unknown"}
- Last commit: ${lastCommit || "unknown"}
- Working tree:
${status || "clean"}
`;
}

export function gitContextExtension () {
  return (pi: any) => {
    pi.on ("before_agent_start", async (event: any, ctx: any) => {
      return {
        systemPrompt:
          event.systemPrompt +
          "\n\n" +
          gitSummary (ctx.cwd),
      };
    });
  };
}
```

###### 最佳实践

- **适合稳定、轻量、经常需要的信息**，例如 Git 分支、项目名称、当前环境。
- 不要注入大段内容，例如完整日志、完整 README、完整 package-lock。
- 上下文注入应保持短小，避免污染 system prompt。
- 如果信息可能过期，可以在每轮任务开始前重新生成。

##### 4. 自定义业务工具：查询 MRR

不要让 Agent 直接访问数据库，而是给它一个受控工具。

```ts
//src/agent/tools/getMrr.ts

export function getMrrTool (db: any) {
  return {
    name: "get_mrr",
    description: "Get Monthly Recurring Revenue for a given month. Requires revenue permission.",
    parameters: {
      type: "object",
      properties: {
        month: {
          type: "string",
          description: "Month in YYYY-MM format, for example 2025-06",
        },
      },
      required: ["month"],
    },

    execute: async ({ month }: { month: string }) => {
      const mrr = await db.metrics.findMrrByMonth (month);

      return {
        content: [
          {
            type: "text",
            text: JSON.stringify ({
              month,
              mrr,
              currency: "USD",
            }),
          },
        ],
      };
    },
  };
}
```

###### 最佳实践

- **业务能力用自定义 Tool 暴露，不要让 Agent 直接连数据库。**
- Tool 输入参数要明确，例如`month: YYYY-MM`。
- Tool 返回结构化 JSON，方便 Agent 稳定解析。
- Tool 内部再次做权限校验，不能只依赖输入 Hook。
- 对敏感工具增加审计日志。

##### 5. 清理 Bash 输出：降低 Token 消耗

参考`pi-hypa`的思路，对`bash`工具结果进行压缩。

```ts
//src/agent/extensions/bashOutputCleaner.ts

function cleanGitLogOutput (output: string) {
  return output
    .split ("\n")
    .filter ((line) => {
      if (line.startsWith ("diff --git")) return false;
      if (line.startsWith ("index")) return false;
      if (line.startsWith ("+++")) return false;
      if (line.startsWith ("---")) return false;
      if (line.startsWith ("@@")) return false;
      return true;
    })
    .slice (0, 300)
    .join ("\n");
}

export function bashOutputCleanerExtension () {
  return (pi: any) => {
    pi.on ("tool_result", async (event: any) => {
      if (event.toolName !== "bash") {
        return;
      }

      const command = event.toolInput?.command || "";
      const text = event.result?.content?.[0]?.text || "";

      if (command.startsWith ("git log")) {
        return {
          result: {
            ...event.result,
            content: [
              {
                type: "text",
                text: cleanGitLogOutput (text),
              },
            ],
          },
        };
      }
    });
  };
}
```

###### 最佳实践

- 优先清理高噪声命令，例如：
  - `git log --stat`
  - `npm test`的重复失败日志
  - 大量构建输出
  - `grep -r`的长结果
- 不要盲目删除关键信息，例如错误堆栈第一行、失败文件名、退出码。
- 对输出设置最大行数或最大字符数。
- 清理逻辑要透明，可在调试模式下保留原始输出。

#### 四、创建 Agent Session

```ts
//src/agent/createSession.ts

import {
  createAgentSession,
  SessionManager,
  DefaultResourceLoader,
} from "@earendil-works/pi-coding-agent";

import { getMrrTool } from "./tools/getMrr";
import { permissionGateExtension } from "./extensions/permissionGate";
import { gitContextExtension } from "./extensions/gitContext";
import { bashOutputCleanerExtension } from "./extensions/bashOutputCleaner";

export async function createSaasAgentSession ({
  user,
  cwd,
  db,
}: {
  user: {
    id: string;
    name: string;
    role: string;
  };
  cwd: string;
  db: any;
}) {
  const resourceLoader = new DefaultResourceLoader ({
    cwd,

    // Agent 配置与认证目录，留在宿主机
    agentDir: process.env.PI_AGENT_DIR!,

    // Web 多租户场景下，不允许自动加载本地扩展和技能
    noExtensions: true,
    noSkills: true,

    // 显式传入允许的扩展
    extensionFactories: [
      permissionGateExtension (user),
      gitContextExtension (),
      bashOutputCleanerExtension (),
    ],
  });

  await resourceLoader.reload ();

  const { session } = await createAgentSession ({
    sessionManager: SessionManager.inMemory (),

    resourceLoader,

    customTools: [
      getMrrTool (db),
    ],
  });

  return session;
}
```

#### 五、WebSocket 中使用 Session

```ts
//src/server.ts

import WebSocket from "ws";
import { createSaasAgentSession } from "./agent/createSession";

const wss = new WebSocket.Server ({ port: 3001 });

wss.on ("connection", async (socket, request) => {
  const user = await authenticate (request);

  const cwd = `/srv/saas-agent/sandbox/user-${user.id}`;
  const db = await getDb ();

  const session = await createSaasAgentSession ({
    user,
    cwd,
    db,
  });

  session.subscribe ((event: any) => {
    if (
      event.type === "message_update" &&
      event.assistantMessageEvent.type === "text_delta"
    ) {
      socket.send (
        JSON.stringify ({
          type: "delta",
          text: event.assistantMessageEvent.delta,
        }),
      );
    }

    // 建议将事件镜像到自己的数据库
    saveSessionEventToDb (user.id, event);
  });

  socket.on ("message", async (raw) => {
    const message = JSON.parse (raw.toString ());

    if (message.type === "prompt") {
      await session.prompt (message.text);
    }
  });
});
```

#### 六、基于该实例的最佳实践清单

##### 1. 扩展边界要清晰

Pi 默认只有：

- `bash`
- `read`
- `write`
- `edit`

不要一开始就塞入大量工具。应该根据产品需求逐步添加。

推荐顺序：

1. 权限门
2. 上下文注入
3. 自定义业务工具
4. 输出压缩
5. UI / TUI 增强
6. 子代理或复杂工作流

---

##### 2. 多租户 Web 场景不要使用默认本地会话假设

Pi 默认更偏向本地 CLI：

- 会话存在本地 JSONL
- 工具运行在本机文件系统
- 扩展可以从本地环境自动加载

Web 产品中应改为：

```ts
SessionManager.inMemory ()
```

然后：

- 你自己的数据库作为事实来源
- 通过`session.subscribe ()`镜像事件
- 每个用户一个独立 sandbox
- 禁止自动加载未知扩展

---

##### 3. `cwd`和`agentDir`必须分离

```ts
cwd: "/srv/sandbox/user-123"
agentDir: "/srv/pi-agent"
```

含义：

| 字段 | 用途 |
|---|---|
| `cwd` | Agent 实际工作的目录，每个用户独立 |
| `agentDir` | Pi 配置、认证、模型提供商信息 |
| `noExtensions` | 禁止环境中自动拾取扩展 |
| `noSkills` | 禁止自动拾取技能 |

最佳实践：

- 用户只能访问自己的`cwd`
- 认证和密钥不能放进 sandbox
- sandbox 可以随时销毁和重建
- bash、read、write、edit 都应限制在 sandbox 内

---

##### 4. 权限控制要分层

不要只做一层权限控制。

推荐三层：

```text
输入层：pi.on ("input")
  |
  | 判断用户是否可以提出该问题
  v
工具层：customTool.execute ()
  |
  | 判断用户是否可以调用该业务能力
  v
数据层：数据库查询权限
```

例如：

- 输入层阻止 “告诉我 6 月收入”
- 工具层阻止未授权用户调用`get_mrr`
- 数据层确保 SQL 查询只返回该用户可见的数据

---

##### 5. 危险操作必须加确认

对于以下操作，不能让 Agent 静默执行：

- 删除文件
- 修改生产配置
- 执行数据库写操作
- 调用外部付款、邮件、CRM API
- 执行`rm -rf`
- 运行 deploy 命令

可以在`tool_call`或自定义工具中加入确认：

```ts
pi.on ("tool_call", async (event, ctx) => {
  if (
    event.toolName === "bash" &&
    /rm -rf|deploy|drop table|kubectl delete/.test (event.toolInput.command)
  ) {
    const approved = await ctx.ui.confirm (
      `危险命令：${event.toolInput.command}\n 是否继续？`,
    );

    if (!approved) {
      return {
        action: "deny",
        reason: "User rejected dangerous command",
      };
    }
  }
});
```

---

##### 6. 控制 Bash 输出，避免 Token 爆炸

Agent 最容易浪费 Token 的地方通常不是对话，而是工具结果。

高风险命令：

```bash
git log --stat -200
npm test
pnpm build
grep -r something .
cat large-file.log
```

最佳实践：

- 对工具输出设置最大长度
- 对常见命令做语义清理
- 保留错误摘要，而不是完整日志
- 超长输出保存到文件，只把摘要给模型
- 对`bash`工具结果统一经过清洗层

---

##### 7. 上下文注入要短，不要把系统提示变成垃圾桶

适合注入：

- 当前 Git 分支
- 当前任务 ID
- 当前用户角色
- 当前项目名称
- 当前环境，例如 staging /production
- 简短业务规则

不适合注入：

- 完整数据库 schema
- 完整日志
- 大型文档
- 所有历史会话
- 整个代码仓库摘要

原则：

> 静态、短小、每轮都需要的信息，适合注入。  
> 大型、动态、偶尔才需要的信息，应该通过 Tool 获取。

---

##### 8. 自定义 Tool 应该产品化，而不是简单封装 API

不推荐：

```ts
call_database (sql)
call_http (url)
run_anything (command)
```

推荐：

```ts
get_mrr (month)
get_user_growth (startDate, endDate)
create_customer_report (customerId)
summarize_failed_payments (month)
```

原因：

- 输入更安全
- 权限更容易控制
- 输出更稳定
- Agent 更容易正确使用
- 更适合审计

---

##### 9. 开发期使用`/reload`，生产期禁用任意热加载

Pi 的`/reload`非常适合开发扩展：

```text
修改 extension.ts
/reload
立即生效
```

但生产环境应避免：

- 用户上传任意扩展
- 自动加载未知本地扩展
- 运行未经审查的技能
- 在生产中让 Agent 改写自己的框架代码

生产推荐：

```ts
noExtensions: true,
noSkills: true,
extensionFactories: [
  permissionGateExtension (user),
  gitContextExtension (),
  bashOutputCleanerExtension (),
]
```

---

##### 10. 所有会话事件都要可观测

使用：

```ts
session.subscribe ((event) => {
  saveSessionEventToDb (user.id, event);
});
```

建议记录：

- 用户输入
- Agent 输出
- 工具调用
- 工具结果摘要
- 权限拒绝原因
- 错误信息
- Token 使用量
- 会话耗时

这样可以支持：

- 审计
- Debug
- 成本分析
- 用户行为分析
- 权限问题排查

---

#### 七、最终推荐方案

对于这个「SaaS 运营代理」实例，推荐组合是：

```text
Pi SDK
  +
SessionManager.inMemory ()
  +
DefaultResourceLoader
  +
noExtensions: true
  +
noSkills: true
  +
每用户独立 sandbox
  +
权限门 extension
  +
Git 上下文 extension
  +
Bash 输出清理 extension
  +
业务专用 custom tools
  +
session.subscribe () 持久化事件
```

一句话总结：

> 用 Pi 构建真实产品时，不要把它当成 “更强的 CLI”，而要把它当成一个可嵌入的 Agent Runtime。  
> CLI 能力保持最小，产品能力通过受控扩展和工具显式注入。

## 追问（2）

### 提问 · 2026-07-14 09:42:38

pi agent 可以应用在哪些场景中 ？

### 回答 · 2026-07-14 09:42:38

Pi Agent 的应用场景可以分成两大类：

1. **作为本地 / 团队编码代理使用**
2. **作为 Agent Runtime / SDK 嵌入到真实产品中**

它不只是一个类似 Claude Code 的 CLI，而是一个可扩展的 Agent 框架。

---

#### 1. 编程助手 / 代码仓库代理

这是最直接的场景。

Pi 默认就有：

- `bash`
- `read`
- `write`
- `edit`

所以它可以做：

- 阅读项目结构
- 解释代码库
- 修复 Bug
- 写测试
- 重构代码
- 执行构建和测试
- 修改文档
- 生成脚本
- 检查 Git 状态

例如你可以问：

> 看一下这个项目，告诉我它是做什么的，并指出主要入口文件。

或者：

> 修复这个测试失败，不要改业务逻辑。

适合个人开发者、创业团队、内部工程团队使用。

---

#### 2. 团队共享开发代理

Pi 的扩展和 Hook 很适合做团队共享 Agent。

例如在团队里接入：

- 权限控制
- Git 上下文注入
- 代码规范检查
- PR 摘要生成
- 自动测试
- 自动生成变更说明
- 敏感命令拦截

比如团队成员问：

> 帮我部署到生产环境。

Pi 可以通过`tool_call` Hook 检查命令，如果发现是危险操作，比如`deploy`、`rm -rf`、`kubectl delete`，就要求人工确认。

也可以通过`input` Hook 做权限门：

> 普通成员不能查询收入数据。  
> 只有 Jason 可以查看财务指标。

这种场景下 Pi 不只是写代码工具，而是团队内部的 “受控代理入口”。

---

#### 3. DevOps / 自动化运维助手

Pi 可以调用 Bash、读写文件、执行命令，非常适合做 DevOps 辅助。

可用于：

- 查看服务器日志
- 分析 CI/CD 失败原因
- 修复构建脚本
- 生成 Dockerfile
- 生成 GitHub Actions 配置
- 检查部署配置
- 分析 Kubernetes YAML
- 整理错误日志摘要
- 执行安全受控的运维命令

比如：

> 帮我分析为什么这个 GitHub Actions 构建失败，并给出修复 PR。

或者：

> 检查这个 Dockerfile 有没有明显的问题。

不过这类场景一定要加安全限制，比如：

- 禁止任意生产命令
- 禁止删除操作
- 高危命令二次确认
- 工具输出清洗
- 每个用户隔离 sandbox

---

#### 4. 内部数据分析 / BI 助手

通过自定义工具，Pi 可以接入公司数据系统。

例如注册这些工具：

```text

  ↓

  ↓
调用 get_mrr ("2025-06")
  ↓
调用 get_churn_rate (...)
  ↓
调用 get_top_customers (...)
  ↓
```

##### 这个场景的关键最佳实践

###### 1. 不要给 Agent 原始 SQL 权限

不推荐：

```ts
query_database (sql)
```

推荐：

```ts
get_mrr (month)
get_user_growth (startDate, endDate)
get_churn_rate (startDate, endDate)
```

这样更安全、更稳定，也更容易做权限控制。

###### 2. 权限要在输入前拦截

例如用户问：

> 6 月收入是多少？

如果他没有权限，应该在进入 Agent 前就拦截，而不是让大模型自己决定要不要回答。

可以使用：

```ts
pi.on ("input", async (event, ctx) => {
```

###### 3. 工具层也要再校验一次权限

原因是：  
**不能只相信 Agent 的调用行为。**

1. 工具边界清晰

3. 权限规则明确
4. 不需要复杂文件系统操作
5. 很容易做成 Web 产品
6. 用户能快速感知价值

> 如果你有 SaaS 数据、运营数据、财务数据，Pi 很适合做一个受控的数据分析 Agent。

###### 1. Git 上下文注入

让 Agent 自动知道当前分支、最近提交、工作区状态。

```ts
pi.on ("before_agent_start", (event, ctx) => {
```

###### 2. 危险命令拦截

拦截类似：

```bash

git push --force
kubectl delete
drop database
npm publish
```

可以在`tool_call`阶段处理：

```ts
pi.on ("tool_call", async (event, ctx) => {
  if (
    event.toolName === "bash" &&
    /rm -rf|push --force|npm publish|drop database/.test (event.toolInput.command)
  ) {
    return {
      action: "deny",
      reason: "Dangerous command blocked"
    };
  }
});
```

CI 日志通常非常长，需要压缩。

例如：

```text
npm test 输出 30,000 行

```

这可以大幅减少 token 成本。

如果你想最快落地，先做**SaaS 数据分析 Agent**。

##### 一、Pi 的核心特点：默认极简，但几乎什么都能扩展

首先，Pi 最重要的特点，是“开箱即用很简单，扩展起来很自由”。

Pi 最初是驱动 OpenClaw 的核心项目之一，原文称它可能是增长最快的代理项目之一。不过，Pi 本身并没有一开始就塞进大量复杂功能。默认情况下，它只有四个工具：执行命令的 bash、读取文件的 read、写入文件的 write，以及修改文件的 edit。

它没有内置子代理，也没有团队协作机制，没有 MCP。这里的 MCP，可以理解为一种让模型连接外部工具和数据源的标准协议。

Pi 把其他能力都交给了一个核心机制：扩展。你可以通过扩展添加工具、命令、快捷键、模型提供商、会话管理方式，甚至直接修改终端界面。

这种设计的意思是，Pi 本身只提供一个很小的基础框架。你需要什么，就自己加什么。比如，你可以告诉 Pi：“把天气信息放到提示输入框上方。”Pi 会读取扩展接口的文档，生成对应的小组件，然后重新加载它。

##### 二、扩展系统：代理可以修改自己的工作方式

接下来，重点看 Pi 的扩展系统到底能控制什么。

Pi 的扩展，本质上是一个连接到代理框架的 TypeScript 文件。TypeScript 是一种常用于开发 JavaScript 应用的编程语言。和一些只提供少量钩子的工具相比，Pi 暴露出来的接口范围更大。

这里可以把接口理解成代理留给开发者的“插槽”，主要有三类。

第一类是 `pi` 对象。它负责注册新的能力。比如注册工具、命令和快捷键，也可以注册新的模型服务商。你还可以让代理主动发送用户消息，或者切换当前允许使用的工具。

第二类是事件机制，也就是 `pi.on`。它可以监听代理整个生命周期中的各种事件。比如用户输入、会话开始、代理开始工作、工具被调用、工具返回结果、上下文变化、请求发送给模型之前，以及上下文压缩之前。

第三类是 `ctx`，也就是当前实时会话的上下文。通过它，扩展可以访问用户界面、会话管理器、当前工作目录和正在使用的模型。

更重要的是，Pi 支持 `/reload` 热重载。热重载的意思是，扩展被修改之后，不需要完全退出代理，就能重新加载。这样一来，代理在运行过程中，甚至可以帮助你重写和更新自己的框架。

##### 三、扩展不只是加工具，也能改变整个使用体验

这些接口带来的第一个变化，是 Pi 的终端界面，也就是 TUI，可以被完全定制。TUI 是 Terminal User Interface，意思是运行在终端里的图形化界面。

例如，你可以在会话开始时重新设置顶部标题，给 Pi 换一套主题。你也可以把天气信息放在提示输入框上方，让界面更像一个真正的个人工作台。

扩展甚至可以把完整的小游戏嵌入代理。原文提到，有人发布了一个名为 pi-doom 的扩展，让用户可以在编码会话里直接运行 DOOM。也就是说，代理还在工作时，终端里可以同时运行一个完整的游戏界面。

这说明 Pi 的扩展能力并不局限于“给模型增加一个函数”。它还可以修改界面、改变交互方式，甚至把其他类型的程序嵌入代理。

##### 四、一个实用案例：减少工具输出，节省大量上下文

更重要的是，扩展还可以在后台自动优化代理的工作过程。

原文提到一个叫 pi-hypa 的扩展。它的作用，是直接清理 bash 命令产生的大量无用输出，从而减少代理需要处理的工具令牌。

举个例子，当 Pi 执行 `git log --stat -200` 时，命令可能返回很多差异内容、主题信息和注释。pi-hypa 会在结果交给代理之前，先把这些噪声过滤掉，只留下真正重要的提交信息。

原文称，这类处理通常可以减少百分之八十到百分之九十八的无用输出，工具令牌消耗也可以降低大约百分之八十到百分之九十六。

关键在于，这个过程对代理是透明的。代理并没有主动请求压缩，也从来没有看到那三万四千个令牌的原始噪声。它拿到的直接就是清理后的结果。

除了这个案例，社区还已经出现了不少扩展。例如，连接 MCP 的适配器、子代理、Chrome 浏览器控制、计划模式、电脑操作、向用户提问、动态工作流、待办事项和目标管理等。

所以，Pi 的生态正在把很多其他代理工具里的功能，逐步搬到自己的扩展体系中。

##### 五、构建扩展其实很简单：从注入信息开始

下面进入实际构建方式。

第一种扩展，是向上下文里注入信息。它不需要增加任何工具调用，就能让代理提前知道某些环境信息。

例如，在代理开始工作前，扩展可以自动读取当前 Git 仓库的摘要，并把它附加到系统提示中。这样，当你问“我现在在哪个分支？”时，代理可以直接回答，而不需要再调用工具查询。

这个例子说明，扩展不仅可以让代理“做更多事”，也可以让代理在开始工作前，自动获得更准确的背景信息。

第二种扩展，是添加新工具。

比如，你可以注册一个名为 `read_clipboard` 的工具，让代理读取当前系统剪贴板。之后，代理就具备了一个原本没有的能力：直接了解你刚刚复制的内容。

添加工具时，通常只需要定义工具名称、功能说明，以及实际执行的函数。Pi 会负责把这个工具接入代理的正常调用流程。

##### 六、权限门：在请求到达代理前先进行拦截

第三种扩展，是权限控制。

原文提到，作者把这种机制用在团队共享代理上。原因很直接：团队里的不同成员，不应该看到所有内容。

具体做法是，在用户请求真正交给代理之前，先调用一个轻量模型进行分类。这个模型会读取项目里的 `PERMISSION.md` 文件，也就是用来描述访问规则的权限策略文件，然后判断当前请求应该允许还是拒绝。

例如，权限规则可以写成：“只有 Jason 能查看收入数据。”

如果其他人询问“六月收入是多少”，请求会在到达主代理之前被拦截。用户界面会显示请求被拒绝的原因，主代理则根本不会处理这条请求。

这里的关键结论是，权限控制不一定要依赖代理自己判断。你可以在代理外面加一层独立的策略检查，把敏感请求挡在最前面。这样做可以让共享代理更适合团队和企业环境。

##### 七、Pi 不只是命令行工具，也可以作为应用开发 SDK

前面讲的是扩展。接下来，视角要从“使用 Pi”切换到“用 Pi 构建产品”。

很多人可能不知道，Pi 不只是一个命令行界面。它实际上由五个部分组成：负责调用各种模型的 `pi-ai`，负责运行代理循环的 `pi-agent`，提供工具、会话、上下文压缩和扩展能力的 `pi-coding-agent`，终端界面 TUI，以及负责组织多个代理或任务的编排器。

其中，`pi-ai` 支持调用不同的模型，也支持 Claude 和 Codex 的订阅式 OAuth 登录。OAuth 可以理解为一种授权登录方式。使用这种方式时，你可以复用现有的模型订阅身份，而不一定要把 API 密钥直接写进应用文件里。

`pi-coding-agent` 则可以看作是类似 Claude Code SDK 的一套能力集合。它包含工具调用、会话管理、上下文压缩和扩展系统。

因此，一个完整的代理，不需要从零开始搭建。开发者可以直接调用 Pi 的接口，创建会话，让代理读取当前目录里的文件，并把回答以流式文本输出出来。

原文给出的示例只有大约十五行代码，而且没有用户界面。它做的事情很简单：创建一个内存中的会话，监听代理输出的文本变化，然后发出一句“查看当前文件，并告诉我这个项目是什么”。

这说明，Pi 的核心代理能力可以被压缩成一次函数调用，而不必绑定在原来的终端界面上。

##### 八、从命令行代理到网页应用，只需要换一层外壳

接下来，把这个无界面的代理放进 `npx tsx` 之类的运行环境中，就可以观察它的输出流。由于它可以使用现有的 Pi 身份认证，文件里不需要直接保存 API 密钥。

如果再把同一个会话封装进 WebSocket，也就是一种支持实时双向通信的网络连接，就能得到一个托管在服务器上的聊天代理。

每个浏览器标签页，都可以对应一个独立会话。用户在网页中发送消息，服务器端的 Pi 会继续处理请求，并把模型生成的内容实时传回浏览器。

不过，真正做成产品时，还需要解决“每个用户能看到什么、能操作什么”的问题。

Pi 提供了资源加载器，可以为每个会话单独定义运行范围。比如，给每个用户分配独立的工作目录，也就是沙箱；把配置和身份认证信息放在主机侧；关闭自动发现的扩展和技能，只允许加载产品明确传入的能力；还可以加入自己的安全规则，比如禁止危险的 bash 命令。

同时，你还可以给每个产品会话加入专属工具。例如，为业务代理提供获取 MRR 的工具。MRR 通常指月度经常性收入，也就是每个月可以稳定获得的订阅收入。

原文提到，作者正是采用了这种结构来构建 Polsia，一个能够启动和运营业务的自主代理。

##### 九、从本地运行迁移到多租户服务，需要改变会话和文件系统

最后，要特别注意本地部署和网页托管之间的差异。

Pi 的默认设计更偏向本地文件系统。会话通常以 JSONL 文件保存，JSONL 是一种按行存储 JSON 数据的格式。工具也默认直接在当前主机上运行。

但在多租户后端里，也就是很多用户共同使用同一套服务器时，不能简单地让所有会话共享本地文件和工具权限。

一种做法是使用内存中的会话管理器，把你自己的数据库作为真正的数据来源。代理产生的会话事件，可以通过订阅机制同步到数据库。每个用户的 bash、文件读取和文件写入操作，则必须在各自独立的沙箱中执行。

这样，用户之间的数据和操作范围才能隔离开来。换句话说，Pi 负责提供代理循环和工具框架，而产品开发者需要自己负责数据库、用户隔离、权限控制和安全边界。

原文最后提到，作者已经用 Pi 的这些包制作了一个 Polsia 的复刻版本，并计划分享构建过程，同时把一些 Pi 扩展放进自己的 GitHub 技能仓库。

#### 最后回顾

最后，用五点回顾这段内容。

第一，Pi 的核心策略是保持默认极简，只提供 bash、read、write 和 edit 四个基础工具。

第二，Pi 的扩展系统开放范围很大。通过 `pi.*`、事件监听和 `ctx.*`，你可以添加工具、修改界面、接入模型、控制会话，甚至改变代理的生命周期。

第三，扩展不仅能增加能力，还能优化效率。像 pi-hypa 这样的扩展，可以过滤工具输出，让无用上下文减少百分之八十以上。

第四，权限门可以在请求进入主代理之前，依据 `PERMISSION.md` 等规则先进行判断，适合团队共享和敏感数据场景。

第五，Pi 不只是一个命令行工具，也是一套 SDK。通过会话管理器、资源加载器、自定义工具和 WebSocket，它可以被改造成网页聊天代理，甚至进一步构建成支持多用户的真实 AI 产品。

### 2026-09-18 00:34:11

#### Pi 的真正价值：把 AI Agent 做成一个可拦截、可嵌入的运行时

这篇内容最值得关注的，不是 Pi 又实现了多少代理功能，而是它选择了相反的架构：核心只提供 bash、read、write、edit 四个工具，把其余能力交给扩展系统。**它试图把 Agent 从一个功能齐全的应用，变成一个拥有稳定核心和大量生命周期接口的运行时。**

##### 扩展点比预装功能更有长期价值

Pi 暴露的不只是“增加一个工具”，还包括输入进入模型前、工具调用前后、上下文组装、模型请求、会话压缩等环节。开发者因此可以改变 Agent 如何获得信息、如何执行动作，以及什么请求根本不应进入模型。

这与普通插件系统有重要区别。插件通常是在产品允许的范围内添加功能；Pi 的扩展则更像 Web 中间件，可以拦截并重写整个执行链。文章里的三个例子恰好对应三类关键控制：

- 在 `before_agent_start` 注入 Git 信息，减少模型主动查询环境的次数；
- 拦截 bash 输出，先删除无关内容，再放入上下文；
- 在 `input` 阶段执行权限判断，拒绝不该到达主 Agent 的请求。

这表明，Agent 的竞争力未必主要来自更多工具，而可能来自**信息进入模型之前和动作离开模型之后的治理能力**。

其中最有实际价值的是 `pi-hypa`：它宣称能把部分工具输出减少 80%—96%。这并非单纯节省 token。大量日志、diff 和注释会占据注意力，使真正相关的信息被稀释。先按任务语义清理工具结果，相当于在模型与现实世界之间增加一个“信息编译层”。这一方法可以迁移到数据库查询、监控日志、浏览器页面和企业知识检索，但前提是过滤规则不能删掉决定结论的异常细节。

##### 15 行代码证明的是可嵌入，不是可生产

Pi 被拆成模型调用、Agent 循环、编码代理、终端界面和编排器等包，因此同一个会话可以从 CLI 中取出，接入 WebSocket、网页 UI 或产品自有工具。这降低了构建垂直 Agent 的起点：团队不必重新实现模型适配、流式输出、会话和压缩机制，只需定义工作目录、工具和策略。

但文章从“15 行可运行”跳到“托管 AI 产品”，中间省略了最困难的部分。多租户环境还需要隔离文件系统和进程、持久化状态、控制工具权限、处理并发与失败恢复，并建立审计和成本预算。`SessionManager.inMemory()` 只是把状态责任交还给应用，并没有解决它。允许 Agent 热重载甚至重写自身扩展，也会扩大供应链攻击和越权风险。

权限示例同样应谨慎看待：用轻量模型按照 `PERMISSION.md` 分类，适合做体验层的预检，却不能替代确定性的身份认证和数据授权。真正敏感的数据应在工具或数据接口层按用户身份强制过滤，而不是依赖另一个模型判断“谁能看”。

##### 更值得验证的是“Agent 中间件层”

Pi 暗示了一个可能长期成立的产品方向：未来企业未必只需要更好的 Agent，而会需要一套围绕 Agent 生命周期的中间件——上下文裁剪、权限、审计、成本控制、沙箱和可观测性。Pi 的开放接口让这些能力可以快速实验。

因此，评估这类框架时不应只看演示中能否增加天气组件或运行 DOOM，而应看三个问题：**关键执行环节是否都能被拦截，扩展之间能否安全组合，以及从本地单用户迁移到多租户后，控制边界是否仍然清晰。**这才决定它是一个有趣的可编程 CLI，还是能承载真实产品的 Agent 运行时。
