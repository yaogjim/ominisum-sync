## 分析要点

- **核心高价值点**：subagent 不是简单的小智能体，而是 parent session 下拥有独立 work context 的托管子运行时。
- **留存建议**：短期参考后可删除
- **不足**：内容偏概念性，缺少完整案例、实现细节和证据支撑，不适合作为长期核心资料。

**知识要点**

- subagent 的启动可理解为一次 spawn\_agent 类型的工具调用，parent 会获得 child handle。
- 会话是运行时容器，上下文是模型调用可见信息，subagent 是 parent session 下的新 child session。
- child 可以共享 tools、skills、AGENTS.md、MCP、cwd、沙箱和权限等资源，但不共享完整 transcript。
- 常见 subagent 模式包括 fresh child、forked child 和 partial fork，区别在于继承多少上下文。
- 多代理协作会增加 runtime state，必须追踪谁在工作、知道什么、改了什么以及结果如何成为 evidence。

**行动项**

- 在设计多代理 coding workflow 时，明确每个 subagent 的 role、context slice 和可用 tools。
- 优先尝试 partial fork 模式，避免完整继承 parent history 带来的噪声。
- 为 subagent 输出建立 evidence 机制，记录修改、验证结果和完成状态。

#### Session, Context, Subagent

这三个词容易混在一起。

- session 是 runtime container：thread、transcript、tools、permissions、resources、status、artifacts。
- context 是某次 model call 能看到的 projection：instructions、skills、AGENTS.md、recent turns、summaries、tool results、file state。
- subagent 是 parent session 下面新开的 child session。它可以继承 resources，也会拿到一段被选择过的 context slice。

#### Fresh Agent, Forked Agent or Partial Fork?

![Image](https://pbs.twimg.com/media/HLXd2j3XAAAEb5H?format=jpg&name=large)

parent 选择投射多少 context 给 sub agent，由 subagent的类型决定， 常见的 subagent 有三种 pattern：

- fresh child 它需要收到 goal、relevant files、已尝试过什么、exact output，以及回答深度。
- forked child 已经继承了 surrounding context，prompt 应该直接给下一步 directive。
- partial fork 是最实用的中间方案。它给 child 足够的 local memory 去工作，同时避免 parent history 变成 inherited noise。

## 解读（1）

### 2026-06-25 00:57:46

#### 一个子代理打开一个新的上下文：深度总结与解读

##### 一、深度总结

这篇文章的核心观点是：

> **Subagent 不是简单的“小智能体”，而是一次工具调用触发的、由 Harness 托管的新运行时上下文。**

###### 1. Subagent 的启动，本质是一次 tool call

用户提出任务，例如：

> “使用验证器子代理来审计 webhook 重试。”

在 Harness 中，这可能被转化为一次工具调用，比如：

```text
/delegate → spawn_agent
```

工具调用完成后，父代理会得到一个 **child handle**，也就是子代理的句柄。

所以从外部看：

> **启动 subagent = 调用一个工具。**

---

###### 2. Tool call 之后，内部发生的是运行时扩展

文章强调：

> **工具调用在外部，运行时在内部。**

也就是说，表面上只是一次工具调用，但 Harness 内部会为子代理打开一个新的 **work context**。

这意味着：

- 子代理有自己的会话状态；
- 子代理看到的信息不一定等于父代理看到的信息；
- 父代理需要决定给子代理投射多少上下文。

---

###### 3. 会话、上下文、子代理三者不同

文章区分了三个容易混淆的概念：

| 概念 | 含义 |
|---|---|
| 会话 session | 运行时容器，包含线程、记录、工具、权限、资源、状态、工件 |
| 上下文 context | 某次模型调用中可见的信息，如指令、文件、摘要、工具结果 |
| 子代理 subagent | 父会话下面新开的子会话 |

简言之：

> **session 是容器，context 是模型当前能看到的内容，subagent 是新开的子容器。**

---

###### 4. Subagent 共享资源，但不共享全部对话

子代理可以继承父代理的许多资源，例如：

- tools
- skills
- AGENTS.md
- MCP 服务器
- 当前工作目录
- 沙箱
- 权限

但这不代表它自动继承父代理的全部历史记录。

关键在于：

> **共享资源 ≠ 共享 transcript。**

子代理看到什么，取决于父代理投射给它的 **context slice**。

---

###### 5. 子代理常见三种模式

文章提出三种 subagent 模式：

| 类型 | 特点 | 适用场景 |
|---|---|---|
| fresh child | 几乎全新，只给必要目标和背景 | 独立审计、验证、专项调查 |
| forked child | 继承较多上下文 | 接着父代理当前思路继续做 |
| partial fork | 部分继承，避免噪音 | 最实用，适合多数复杂任务 |

其中最重要的是：

> **partial fork 往往最实用，因为它在“足够信息”和“避免噪音”之间取得平衡。**

---

###### 6. 多子代理不是越多越好

子代理可以用于：

- 并行调查；
- 专业分工；
- 后台长任务；
- 大型重构；
- 测试验证；
- 代码评审。

但文章最后提醒：

> **更多 agent 不保证更好，更多 agent 会制造更多 runtime state。**

Harness 必须知道：

- 谁在工作；
- 它知道什么；
- 它改了什么；
- 什么时候完成；
- 结果如何成为证据。

否则，子代理不是扩展能力，而是制造混乱。

---

##### 二、深入浅出解读

可以把父代理想象成一个项目经理，子代理像临时拉进来的小组成员。

但这个“小组成员”不是凭空知道所有事情。

父代理需要告诉它：

- 你要做什么；
- 相关文件在哪里；
- 之前尝试过什么；
- 哪些结果是可靠的；
- 输出要多详细。

如果信息给少了，子代理会瞎猜。

如果信息给多了，子代理会被历史噪音淹没。

所以关键不是“有没有子代理”，而是：

> **给子代理一个刚刚好的上下文。**

---

###### 一个简单例子

任务：修复 webhook 重试问题。

可以拆成三个子代理：

1. **数据库子代理**  
   查迁移记录、重试表结构、状态字段。

2. **后端子代理**  
   查 webhook 重试逻辑、队列、错误处理。

3. **验证子代理**  
   跑测试、检查边界情况、确认修复是否有效。

父代理负责汇总它们的结果，并决定最终方案。

这就像多人协作开发：

> 子代理负责局部探索，父代理负责全局整合。

---

##### 三、关键洞见

###### 1. Subagent 的本质不是“更聪明”，而是“更可组织”

子代理并不神奇。

它真正有价值的地方在于：

- 隔离上下文；
- 并行处理；
- 专业分工；
- 减少主上下文污染；
- 让复杂任务可管理。

---

###### 2. 上下文管理比代理数量更重要

很多人容易以为：

> agent 越多，能力越强。

但实际更重要的是：

> **谁该知道什么，谁该做什么，谁该产出什么证据。**

没有清晰上下文管理，多代理只会变成多线程混乱。

---

###### 3. Harness 的核心价值在“运行时治理”

Harness 不只是调用模型或工具。

它真正承担的是运行时治理：

- 管理会话；
- 分配权限；
- 投射上下文；
- 跟踪状态；
- 收集证据；
- 合并结果。

因此，subagent 能否有效，不只取决于模型能力，更取决于 Harness 是否能管理复杂状态。

---

##### 四、辩证思考

###### 1. 子代理扩展能力，也扩展复杂性

子代理可以把一个大任务拆成多个小任务，提高效率。

但每多一个子代理，就多一份：

- 状态；
- 上下文；
- 结果；
- 权限；
- 失败路径；
- 合并成本。

所以它不是免费的能力增强，而是一次系统复杂度升级。

---

###### 2. 并行不等于高效

并行子代理适合信息可分离的任务。

例如：

- 一个查数据库；
- 一个查前端；
- 一个跑测试。

但如果任务强依赖统一判断，过早并行可能导致：

- 重复工作；
- 结论冲突；
- 上下文不一致；
- 最终整合困难。

所以并行之前，要先判断任务能不能拆。

---

###### 3. “少给上下文”与“多给上下文”都危险

给少了，子代理没有背景，容易误判。

给多了，子代理继承大量历史噪音，反而抓不住重点。

最优解通常是：

> **精选上下文，而不是完整复制上下文。**

这也是 partial fork 最实用的原因。

---

###### 4. 未来的关键不是更多 agent，而是更好的编排

真正成熟的多代理系统，不是不断增加 agent 数量，而是能回答：

- 为什么需要这个子代理？
- 它的角色是什么？
- 它需要哪些上下文？
- 它能用哪些工具？
- 它的结果如何验证？
- 它的输出如何合并？

换句话说：

> 多代理系统的上限，不在“代理数量”，而在“编排质量”。

---

##### 五、一句话总结

> **Subagent 是通过工具调用打开的新运行时上下文；它的价值在于隔离、分工与并行，但成败取决于上下文投射、角色定义和运行时治理。**

- 也就是说，subagent 不只是“被调用了一下”，而是进入了一个新的运行环境。

##### 3. Session、Context、Subagent 的区别

这三个概念容易混淆，文章做了区分：

###### Session
- 是 **运行时容器**。
- 包含：
  - thread
  - transcript
  - tools
  - permissions
  - resources
  - status
  - artifacts

###### Context
- 是某次 model call 能看到的 **信息投影**。
- 包括：
  - instructions
  - skills
  - AGENTS.md
  - recent turns
  - summaries
  - tool results
  - file state

###### Subagent
- 是 parent session 下新开的 **child session**。
- 它可以继承资源，但拿到的是一段经过筛选的 **context slice**（上下文切片）。

---

##### 4. Subagent 更像“受管理的子运行时”

- 文章指出，subagent 这个词容易让人误解成“小一点的智能体”。
- 但在 Harness 里，它更像一个 **managed child runtime**（受管理的子运行时）。
- 它可以共享父代理可用的资源，例如：
  - tools
  - skills
  - AGENTS.md
  - MCP servers
  - cwd
  - sandbox
  - permissions
- 但重点是：**共享资源，不等于共享对话记录。**
- 子代理拥有自己的 work context，父代理决定给它多少上下文。

---

##### 5. 子代理上下文如何投射：三种常见模式

父代理会根据任务类型，决定给子代理投射多少上下文。常见有三种模式：

###### 1）Fresh child（全新子代理）
适合从头开始做任务。
通常需要明确给它：
- 目标（goal）
- 相关文件（relevant files）
- 已经尝试过什么（what has been tried）
- 需要输出的精确结果（exact output）
- 回答深度要求

###### 2）Forked child（继承型子代理）
适合上下文已经很完整的情况。
- 子代理直接继承周边上下文。
- 提示词可以直接给下一步指令。

###### 3）Partial fork（部分继承）
- 这是文章认为**最实用的折中方案**。
- 它给子代理足够的本地记忆来工作，
- 同时避免把父代理历史中无关的信息也带进去，造成噪音。

---

##### 6. 适合用 Subagent 的场景

文章举了几类典型用途：

###### 并行工作
- 一个子代理查 database migration
- 一个子代理看 frontend state
- 一个子代理跑 verification

###### 角色分工
- Explorer
- Planner
- Verifier
- Worker
- Reviewer

###### 后台任务
- 多个 subagent 协作完成大型重构
- 长时间测试任务
- 持续验证类工作流

---

##### 7. 多个 Subagent 的工作流管理很重要

- 文章强调：**多个 subagent 的组织方式本身就是挑战。**
- 最好把下面几件事定义清楚：
  - 每个子代理的 role 是什么
  - 给它什么 context
  - 让它使用什么 tool
- 只有这些边界清晰，协作才不会混乱。

---

##### 8. 更多 Agent 不一定更好

- 文章最后提醒：**更多 agents 不保证更好的结果。**
- 因为 agent 越多，运行时状态也会越多，系统更复杂。
- Harness 必须清楚知道：
  - 谁在工作
  - 它知道什么
  - 它改了什么
  - 什么时候完成
  - 结果如何转化为 evidence（证据）

---

##### 9. 总结

- Subagent 的核心不是“复制一个新智能体”，而是 **为某个任务打开一个新的工作上下文**。
- 它能继承资源，但不共享完整历史。
- Harness 的价值在于：**让新世界更有序，而不是更混乱。**

- 会话是运行时容器，上下文是模型调用可见信息，subagent 是 parent session 下的新 child session。
- child 可以共享 tools、skills、AGENTS.md、MCP、cwd、沙箱和权限等资源，但不共享完整 transcript。
- 常见 subagent 模式包括 fresh child、forked child 和 partial fork，区别在于继承多少上下文。
- 多代理协作会增加 runtime state，必须追踪谁在工作、知道什么、改了什么以及结果如何成为 evidence。

###### 行动项
- 在设计多代理 coding workflow 时，明确每个 subagent 的 role、context slice 和可用 tools。
- 优先尝试 partial fork 模式，避免完整继承 parent history 带来的噪声。
- 为 subagent 输出建立 evidence 机制，记录修改、验证结果和完成状态。
