## 分析要点

- **核心高价值点**：将方法论正文与能力注册解耦，使内容加载时机、作用范围、流程状态和约束强度可以分别设计与优化。
- **留存建议**：建议精读并存档，作为设计多阶段Agent工作流和能力加载机制的参考（提出了可迁移的Agent能力架构谱系、设计权衡轴和场景选择标准，对工作流编排与上下文控制有长期参考价值。）

**知识要点**

- SKILL.md主要解决方法论分发，并不天然解决按需加载、流程推进和跨会话状态恢复。
- Agent流程约束可分布在提示词、schema枚举和运行时状态机三层，可靠性增强通常伴随灵活性下降与实现成本上升。
- 独立单步能力适合普通skill，多阶段跨会话流程适合持久化编排器，强合规流程则需要确定性状态机。

**行动项**

- 按发现粒度、正文装载时机、状态归属、推进约束和执行主体五个维度审查现有Agent架构。
- 在复杂多阶段工程任务中试验按需加载procedure与会话状态恢复，验证重启后的流程连续性。
- 对具有硬性合规要求的流程，将关键阶段条件从提示词下沉为运行时校验或状态机约束。

### 如何运行

> 复杂工程请求 → 判断是否需要结构化工作流 → 选择 route 和当前 procedure → matt\_pocock\_workflow 加载该 procedure → 将 route / procedure / phase 写入 Pi session → 该步骤完成后切换至下一 procedure

调用 matt\_pocock\_workflow 后，扩展会校验 route 和 procedure，读取 procedures/&lt;procedure&gt;.md，并将当前 { route, procedure, phase } 写入 Pi 的 custom session entry。会话重启时，扩展从同一 branch 的最后一个有效状态恢复当前步骤，因此不会依赖模型从长对话中猜测进度。

当前 procedure 的完整正文只会在启动、切换或恢复这个步骤时按需注入。后续 agent turn 只增加简短的阶段 guidance，例如当前应遵循哪个步骤、下一步明确时应自动推进、以及只有什么情况才应询问用户。它不会在每轮重新注入所有流程正文。

如果任务不属于复杂、多步骤的工程流程，就不应启动该工具；正常处理请求即可。不确定时宁可不进入工作流，也不应猜测一个 route 并加载无关 procedure。

#### Q：为何不直接公开一堆 skills？更新是不是更麻烦？

A：主要收益是控制上下文、避免全局命名冲突，并获得可恢复的流程状态。

上游的纯 skills 方案会把多份 SKILL.md 作为可独立发现的能力。tdd、research、implement 和 code-review 之类的通用名称容易与用户已安装的其他 skill collection 冲突；它们也不天然记录“当前任务走到了哪一步”。

本包将 procedure 保留为包内普通 Markdown 资源，不含 SKILL.md，因此不会被 Pi 递归发现为全局 skills。编排器只在命中工作流后加载当前 procedure，并持久化流程状态。这样保留上游方法论的内容，同时让多阶段工程工作具有明确的进度、自动切换与重启恢复能力。

更新确实不是简单复制上游文件，但工作集中在一个明确的同步边界：选择需要的上游内容，将 SKILL.md\`转为 procedures/\*.md，删除宿主专属 frontmatter 和调用语法，并保留 Pi 的会话、UI、工具启停和工程约束。具体同步规则见 UPSTREAM.md。这是一层有意维护的适配，而不是对上游仓库的镜像。

#### Q：只暴露一个 tool，但 schema 仍列出 procedure，真的节省上下文吗？

A：不能把“只注册一个 tool”误说成 schema 成本为零。

当前主 tool 的 route 固定为五个值；procedure 参数会列出该 route 下允许的流程步骤和已知别名。这样模型切换阶段时可受约束地选择有效步骤，扩展也能验证请求，而不是接受一个凭空编造的名称。

因此，schema 仍然有少量 route / procedure 枚举成本。不过它避免了每个独立skill 各自的发现、描述和完整正文同时进入上下文。更重要的是，体积最大的 procedure 正文按需一次加载；正常后续轮次只保留状态和精简 guidance。

一个更激进的未来设计可以让路由层只返回 procedure 名，再由运行时查表加载正文，并在不确定时返回空结果而不猜测流程。但这会失去 schema 对阶段切换的即时约束，需要单独权衡可靠性与 token 成本。本包当前选择的是受限枚举加按需正文加载。

### 与 mattpocock/skills 纯技能方案的区别

概括来说，上游仓库是一组可单独使用的方法论；pi-matt-pocock 则是一个把这些方法论组织为连续、受状态约束、可恢复工程流程的运行时。

### 延伸讨论：skills 之外的架构设计空间

SKILL.md 本质上是一种 提示词分发格式：它解决“如何把一段方法论文本放到模型面前”，但不解决“何时放、放多少、放到哪一步、放完之后去哪”。因此，“要不要用 skills”其实是一组更细的设计权衡的简写。拆开看，可以识别出几个独立的权衡轴：

沿这些轴可以得到一个架构谱系，而不止“扁平 skills”与“本包”两个端点：

1. 扁平 skill 库（上游方案）。 每个方法论一个 SKILL.md，独立发现、独立装载。优势是零编排成本、即装即用、能力彼此正交；代价是命名全局共享、各 skill 的发现信息和正文同时进场、多阶段进度没有着落。适合彼此独立、无先后顺序的能力。
2. 编排器 + 包内资源（本包方案）。 方法论降级为运行时的普通数据文件，由单一编排 tool 负责装载当前步骤，状态写入 session。上下文成本与命名冲突被压缩，流程获得可恢复性；代价是需要维护一个适配层（见 UPSTREAM.md），且 route / procedure 枚举仍占用少量 schema 体积。
3. 路由查表 + 完全惰性正文。 比本包更激进：tool schema 不枚举任何 procedure，模型只声明意图，运行时查表返回正文，查不到就返回空结果而不猜测。schema 成本趋近于零，但模型切换阶段时不再受枚举约束，非法转移只能靠运行时在事后拒绝，可靠性验证整体后移。本包目前不选它，理由见上文第二个 Q&amp;A。
4. 确定性状态机。把 route → procedure 的转移图编码进运行时：模型只能“请求”转移，运行时校验 done condition、拒绝非法转移，甚至用 verify 命令 gate 阶段完成。可靠性最高，但流程必须能被完整枚举；面对不符合预设图的真实任务时，要么强行套图，要么整体绕过。这是把“流程合规”从提示层下沉到机制层的方向，TODO.md 中“通过 tool 级写阻塞强制 BDD/TDD”就属于这一轴上的推进。
5. 按阶段拆分执行主体。每个阶段开新会话，或派生独立子 agent，阶段间只交接结构化产物（spec、brief、ticket），而不是累积对话历史。上下文最干净，天然支持并行调研与评审；代价是交接协议本身成为新的复杂度来源，且依赖运行时对会话与 subagent 的显式支持（同样列在 TODO.md 的推迟项中）。

几个跨架构的观察：

- 方法论正文应与能力注册解耦。 skills 模型把“一段 Markdown”同时当作内容和注册项，这直接导致了命名冲突与常驻上下文。一旦把正文降级为数据（方案 2 起），装载时机、作用范围和缓存策略都成为可独立优化的参数。
- Tool 的可用性本身可以是状态的函数。本包的 matt\_pocock\_ask 只在工作流激活期间启用，这是纯 skills 无法表达的手段：能力集合随流程状态变化，而不是安装时一次性固定。
- 约束放在哪一层，决定可靠性与 token 成本的交换比。 提示层（guidance）最便宜也最不可靠；schema 枚举（本包）居中；运行时状态机最强但最不灵活。没有全局最优，只有与任务风险匹配的选择。
- “不进入流程”必须是一等行为。 谱系上越靠运行时的方案，越需要在不确定时返回空结果或保持沉默，而不是猜测一个 route。编排器的误判成本高于 skill 的误判成本，因为错误的流程状态会被持久化并影响后续每一轮。

如何选择：

- 独立、单步、无状态的能力（例如一种特定的格式化或检查）——普通 skill 足够，引入编排层是过度设计。
- 多阶段、有依赖顺序、跨越会话的工程流程——需要编排器与持久化状态，这是本包的适用区。
- 对过程合规性有硬性要求（例如“未见红灯不得写实现”）——提示层约束不够，需要向方案 4 的机制层约束演进。

概括来说，skills 回答的是“方法论如何分发”，而工程实践真正需要的是“方法论如何在正确的时间、以正确的粒度、带着正确的状态进入上下文”。后者是一个运行时问题，这正是本包这类编排器存在的理由，也是上述谱系继续演进的方向。

## 结构化（1）

### 2026-09-03 09:20:03

#### pi-matt-pocock：用可恢复的工作流编排替代扁平 Skills

`pi-matt-pocock`将`mattpocock/skills`中适合工程协作的方法论，改造成 Pi 内部的**持久化工作流编排器**。它的核心不是简单分发提示词，而是让多阶段工程任务能按需加载流程、记录进度、自动切换，并在会话重启后继续执行。

##### 1. 安装与定位

- npm 包：`pi-matt-pocock`
- 开源仓库：`FradSer/pi-packages`
- 它不是上游`mattpocock/skills`的完整镜像，而是一层面向 Pi 运行时的适配：
  - 选择适合工程协作的上游内容；
  - 将`SKILL.md`转为包内`procedures/*.md`；
  - 移除宿主专属的 frontmatter 和调用语法；
  - 加入 Pi 的会话状态、UI、工具启停及工程约束。

##### 2. 最小化工具暴露

该包遵循 Pi 的 “最小工具暴露” 原则，主要提供三个入口：

| 入口 | 作用 |
|---|---|
| `/matt-pocock` | 打开路线菜单、查看状态、手动切换或结束工作流 |
| `matt_pocock_workflow` | 启动工程工作流或切换当前流程步骤 |
| `matt_pocock_ask` | 仅在工作流激活期间启用，用于让用户进行结构化选择 |

其中，`matt_pocock_ask`体现了渐进式披露：只有流程真正需要用户决策时，该能力才会出现，而不是始终占用上下文。

##### 3. 当前支持的 5 条工作路线

| Route | 适用场景 |
|---|---|
| **从创意到上线** | 从需求澄清、规格设计、任务拆分，到实现与评审的完整功能开发 |
| **疑难缺陷** | 诊断和修复困难、间歇性或回归类问题 |
| **分类处理** | 将原始请求或 issue 整理成可执行的 brief |
| **路径引导** | 为大型、模糊的计划建立决策和实施路径 |
| **架构** | 调查并改善代码库架构 |

例如，一个需要经历 “澄清需求 → 写规格 → 拆任务 → 实现 → 评审” 的功能，应选择 “从创意到上线”；简单的单步修改则无需启动工作流。

##### 4. 工作流如何运行

整体流程如下：

```text
复杂工程请求
→ 判断是否需要结构化工作流
→ 选择 route 与当前 procedure
→ 调用 matt_pocock_workflow
→ 加载对应 procedure
→ 将 route /procedure/phase 写入 Pi session
→ 当前步骤完成后切换到下一 procedure
```

调用`matt_pocock_workflow`后，扩展会：

1. 校验`route`和`procedure`是否有效；
2. 读取`procedures/&lt;procedure>.md`；
3. 将当前`{ route, procedure, phase }`写入 Pi 的自定义会话记录；
4. 后续通过同一个工具显式切换步骤并保存新状态。

###### 可恢复状态

会话重启后，扩展会从**同一 branch 最后一个有效状态**恢复当前步骤，无需模型重新阅读长对话并猜测进度。

###### 按需加载正文

- procedure 的完整正文只在**启动、切换或恢复步骤时**注入；
- 后续轮次只保留简短 guidance，例如：
  - 当前应执行哪个步骤；
  - 下一步明确时应自动推进；
  - 只有哪些情况才需要询问用户。

因此，它不会每一轮都重复注入完整流程文本。

###### 不应滥用流程

如果任务不是复杂、多步骤的工程工作，就应直接正常处理。无法确定 route 时，**宁可不启动工作流，也不要猜测路线**，因为错误状态一旦持久化，会持续影响后续执行。

##### 5. 为什么不直接暴露大量 Skills

上游方案将多个`SKILL.md`注册为可独立发现的能力，例如`tdd`、`research`、`implement`、`code-review`。这种方式简单，但存在三个问题：

1. **全局命名冲突**  
   通用 skill 名称容易与用户安装的其他 skill 集合重名。

2. **上下文负担较大**  
   每个 skill 都有自己的发现信息、描述和正文，多个能力可能同时进入上下文。

3. **缺少流程状态**  
   Skills 能提供方法论，却不会天然记录 “任务现在走到了哪一步”。

`pi-matt-pocock`的处理方式是：

- procedure 仅作为包内普通 Markdown 文件，不使用`SKILL.md`；
- Pi 不会将它们递归发现为全局 skills；
- 只有命中具体 route 后，才加载当前 procedure；
- 流程状态由运行时持久化，而不是依赖模型记忆。

这既保留了上游方法论，又增加了明确进度、自动切换和重启恢复能力。

##### 6. 更新成本与适配边界

该包的更新确实不能直接复制上游文件，但同步工作集中在一个明确边界内：

- 选择需要的上游内容；
- 将`SKILL.md`转为`procedures/*.md`；
- 删除上游宿主专属配置与调用语法；
- 保留 Pi 的会话、UI、工具状态和工程约束。

具体规则记录在`UPSTREAM.md`。作者将其定义为一层**有意维护的运行时适配**，而不是对上游仓库的机械镜像。

##### 7. 只暴露一个主工具，是否真的节省上下文

“只注册一个主 tool” 不代表 schema 成本为零。

当前设计中：

- `route`固定为**5 个值**；
- `procedure`参数会枚举该 route 下允许的步骤和已知别名；
- 模型只能在受约束的候选项中切换阶段；
- 扩展可以拒绝凭空编造的 procedure。

因此，schema 仍有少量枚举成本，但避免了：

- 为每个独立 skill 注册发现信息与描述；
- 多份完整正文同时进入上下文；
- 每轮重复加载体积较大的 procedure。

当前选择的是：**受限枚举 + 正文按需加载**，在可靠性和 token 成本之间取中间方案。

更激进的做法是让 schema 不列出 procedure，只由模型表达意图，再由运行时查表。但这样会失去 schema 对流程切换的即时约束，非法转移只能在运行时事后拒绝。

##### 8. 与上游纯 Skills 方案的区别

| 维度 | `mattpocock/skills` | `pi-matt-pocock` |
|---|---|---|
| 分发形式 | 多份独立`SKILL.md` | 一个 Pi extension，加包内 procedure Markdown |
| 发现方式 | 每个 skill 独立发现 | 仅暴露命令、主 workflow tool 和条件启用的问答 tool |
| 命名冲突 | `tdd`、`research`等名称可能与其他集合冲突 | procedure 不注册为全局 skill |
| 正文加载 | 各 skill 独立装载 | 命中 route 后按需加载当前 procedure |
| 状态管理 | 主要由模型和对话自行维持 | route、procedure、phase 持久化到 Pi session |
| 重启恢复 | 需要重新理解历史对话 | 恢复最后一个有效工作流状态 |
| 流程推进 | 模型根据 skill 内容自行判断 | 通过`matt_pocock_workflow`显式切换并保存 |
| 更新方式 | 直接跟随上游 skill 文件 | 选择性同步并适配 Pi 运行时 |

简而言之：

- 上游是一组可以独立使用的工程方法论；
- `pi-matt-pocock`是把这些方法论组织成**连续、受状态约束、可恢复的工程流程**。

##### 9. Skills 之外的架构权衡

文章认为，`SKILL.md`本质上只是**提示词分发格式**，解决的是 “如何把方法论文本交给模型”，却没有解决：

- 什么时候加载；
- 加载多少；
- 当前执行到哪一步；
- 完成后进入哪里；
- 是否允许跳过或非法切换。

因此，Agent 能力设计至少包含以下独立权衡轴：

| 权衡轴 | 两端选择 |
|---|---|
| 发现粒度 | 每项能力独立发现 ↔ 单一编排入口 |
| 正文加载时机 | 始终在场 ↔ 命中后按需加载 |
| 状态归属 | 由模型对话维持 ↔ 由运行时持久化 |
| 推进约束 | 模型自由决定 ↔ schema 枚举 ↔ 运行时状态机 |
| 执行主体 | 单会话顺序执行 ↔ 按阶段委派子 Agent |

##### 10. 五种可能的 Agent 架构

###### 10.1 扁平 Skill 库

每个方法论对应一个`SKILL.md`，独立发现和装载。

- **优点**：零编排成本、安装即用、能力彼此独立。
- **缺点**：全局命名冲突、上下文占用较高、多阶段进度无处保存。
- **适用**：彼此独立、没有先后顺序的单步能力。

###### 10.2 编排器 + 包内资源

即`pi-matt-pocock`当前方案：

- 方法论作为普通数据文件；
- 单一工具加载当前步骤；
- 状态写入 session；
- 正文按需注入。

优点是减少上下文和命名冲突，并支持恢复；代价是需要维护适配层，且 route/procedure 枚举仍占少量 schema。

###### 10.3 路由查表 + 完全惰性正文

tool schema 不枚举 procedure，模型只提交意图，由运行时查表：

- 查到则返回正文；
- 查不到则返回空结果，不猜测流程。

这种方式 schema 成本接近零，但失去了阶段切换时的枚举约束，非法操作只能由运行时事后拒绝，可靠性验证被整体后移。

###### 10.4 确定性状态机

将`route → procedure`的完整转移图编码进运行时：

- 模型只能请求转移；
- 运行时检查完成条件；
- 非法转移会被拒绝；
- 甚至可通过`verify`命令阻止未完成阶段继续推进。

可靠性最高，但灵活性较低。若真实任务不符合预设流程，只能强行套用或完全绕过。例如 “**未见测试红灯不得编写实现**” 这类 BDD/TDD 硬约束，就需要从提示约束下沉到工具或状态机层。

###### 10.5 按阶段拆分执行主体

每个阶段开启新会话或交给独立子 Agent，仅通过结构化产物交接，例如：

- spec；
- brief；
- ticket；
- review 结果。

这种方式上下文最干净，也适合并行调研和评审；但交接协议会成为新的复杂度来源，并要求运行时明确支持会话与 subagent。

##### 11. 跨架构的关键结论

###### 方法论正文应与能力注册解耦

把 Markdown 同时作为 “内容” 和 “全局注册项”，会导致命名冲突与上下文常驻。若将正文降级为普通数据，就能分别优化加载时机、作用范围和缓存策略。

###### Tool 可用性可以随状态变化

`matt_pocock_ask`只在工作流激活期间启用，说明 Agent 的能力集合不必在安装时永久固定，而可以成为流程状态的函数。

###### 约束层级决定可靠性与成本

- **提示层 guidance**：成本最低，但最不可靠；
- **schema 枚举**：成本和约束能力居中；
- **运行时状态机**：可靠性最高，但灵活性最低。

不存在适用于所有任务的最优方案，应根据任务风险选择。

###### “不进入流程” 必须是一等行为

越依赖持久化状态和运行时编排，就越不能随意猜测 route。普通 skill 选错的影响可能只持续一轮，而工作流选错后，错误状态会被保存并影响后续每一步。

##### 12. 如何选择能力架构

- **独立、单步、无状态能力**  
  如特定格式化或代码检查，使用普通 skill 即可，加入编排器属于过度设计。

- **多阶段、有依赖顺序、跨会话的工程任务**  
  应使用编排器和持久化状态，这正是`pi-matt-pocock`的适用场景。

- **对过程合规有硬性要求**  
  如 “测试没有先失败就不能写实现”，仅靠提示词不够，应进一步采用工具级阻塞或确定性状态机。

##### 总结

Skills 主要回答 “**方法论如何分发**”，而复杂工程 Agent 更需要解决 “**方法论何时、以何种粒度、带着什么状态进入上下文**”。`pi-matt-pocock`的价值，就是把静态方法论升级为一个按需加载、状态持久化、可约束推进且可重启恢复的运行时工作流。

## 深度解读（1）

### 2026-09-18 00:06:49

#### Agent 能力设计的分水岭：不是装多少 Skills，而是谁管理流程状态

pi-matt-pocock 最值得关注的，并不是把一组工程 skills 移植到了 Pi，而是明确区分了两件常被混在一起的事：**方法论如何分发，以及方法论如何运行。**

SKILL.md 很适合封装独立、单步能力，但当任务变成“澄清需求—写规格—拆任务—实现—评审”时，问题不再只是把哪段提示词交给模型。系统还要知道当前走到哪一步、何时加载下一段内容、重启后如何恢复，以及哪些工具此刻才应该出现。这些都属于运行时，而不是提示词本身。

##### 把方法论从“能力注册”中拆出来

传统 skill 方案让一份 Markdown 同时承担内容与注册项：每个 skill 都需要被发现、命名和描述。规模扩大后，会出现三个成本：通用名称冲突，能力描述占用上下文，以及多个阶段的正文和状态缺少统一管理。

这个包的处理很克制：对模型只暴露一个主要编排工具，将具体 procedure 作为包内资源，命中某条路线后再按需加载。这样，TDD、research、code-review 不再是全局能力名，而只是某个流程中的步骤。

这不等于“一个 tool 就没有上下文成本”。文章也承认，route 和 procedure 枚举仍会进入 schema。真正的收益是：**把大块正文的加载时机、作用范围和生命周期变成可控制变量**，而不是单纯少注册几个工具。这种解耦也意味着未来可以独立优化检索、缓存、版本和权限。

##### 持久化状态比更长的提示词更重要

更关键的变化是，route、procedure 和 phase 被写入 session，重启后可以恢复。模型不必从漫长对话中猜测“我们做到哪里了”。

这代表一种重要的 Agent 设计转向：**不要让模型负责记住流程，而要让模型在运行时维护的状态中做有限决策。** 提示词可以提醒下一步，schema 可以限制合法选项，状态机则可以拒绝非法转移。三者的可靠性依次提高，灵活性则依次下降。

因此，并非所有工作都该状态机化。格式化、检查等单步能力，用普通 skill 更轻；跨会话、多阶段且有依赖顺序的任务，才值得引入编排器；如果流程有强合规要求，例如“测试未失败前不得写实现”，仅靠提示就不够，需要运行时验证和阻断。

##### “不进入流程”也是核心能力

文章中最容易被忽略、却很成熟的一点是：不确定时宁可不启动工作流。普通 skill 误调用一次，影响可能只限于当前回答；编排器如果选错路线，会把错误状态持久化，并持续影响后续步骤。**流程化程度越高，误路由的代价越大。**

因此，真正可用的 Agent 编排产品不能只有“自动进入”，还需要明确的退出、回滚、人工切换和状态可见性。这个包已有手动查看和结束工作流的入口，但若要证明方案优于纯 skills，还需测量错误路由率、跨会话恢复成功率、任务完成质量、token 节省和上游同步成本。当前内容更像一个设计合理的 PoC，而非已经得到实证的最优架构。

它指向的长期机会，是把 Agent 能力层做成一个小型控制平面：方法论只是资源，运行时决定何时装载、允许哪些工具、保存什么状态，以及由当前会话还是子 Agent 执行。未来 Agent 的竞争力，未必来自拥有更多 skills，而更可能来自**能否在正确时机，以正确粒度和约束，调用已有能力**。

## 口播总结（1）

### 2026-09-20 00:32:48

pi-matt-pocock 想解决的，不只是“怎样把一套工程方法交给智能体”，而是更实际的问题：应该在什么时候加载哪一段方法，任务进行到了哪一步，以及会话中断后怎样继续。

它是一个面向 Pi 智能体运行环境的扩展包。它把 mattpocock 的 skills，也就是技能库中适合工程协作的内容，改造成了一个可持久化的工作流编排器。两者使用的可能是相近的方法论，但运行方式明显不同。上游 skills 更像一组可以单独取用的说明书。pi-matt-pocock 则把这些说明书串成连续流程，并为流程保存进度。

它支持五类工程路线。

“从创意到上线”，适合从需求澄清开始，依次完成规格、任务拆分、实现和评审。

“疑难缺陷”，用于诊断和修复困难、间歇性出现，或者反复回归的问题。

“分类处理”，把原始请求或问题单整理成可以执行的任务简报。

“路径引导”，为大型、模糊的计划建立决策路径和实施路线。

“架构”，用于调查代码库的结构，并推动架构改进。

这里需要区分三个层次。路线代表整个任务属于哪种场景。流程步骤，也就是 procedure，代表当前要执行的具体方法。阶段则记录这个步骤内部进行到了哪里。

面对复杂工程请求时，智能体先判断是否真的需要结构化工作流。如果需要，再选择路线和当前流程步骤，然后调用统一的工作流工具。扩展会校验选择是否合法，读取对应的流程文档，并把当前路线、步骤和阶段写入 Pi 的会话状态。

这样做最直接的价值，是进度不再依赖模型自己记忆长对话。即使会话重启，扩展也能从同一分支中最后一个有效状态恢复，继续当前步骤。模型不必重新阅读全部历史，再猜测任务做到哪里。

流程正文的加载方式也经过控制。某个步骤的完整说明，只在启动、切换或者恢复该步骤时注入。之后的对话轮次，只保留简短指引，例如现在应遵循哪个步骤，何时自动进入下一步，以及什么情况下才需要询问用户。系统不会每一轮都重新塞入整套流程文本。

这个扩展平时只暴露一个主要编排工具，以及一个管理命令。另有一个用于向用户提出结构化选择的问题工具，但它只在工作流已经激活时才启用。也就是说，工具是否可用，本身就是流程状态的一部分。

不过，并不是所有请求都应该进入工作流。简单、单步或者不需要跨阶段协作的任务，直接处理就好。无法确定是否匹配时，宁可不启动，也不要随便猜一个路线。因为一旦选错，错误状态会被持久化，并持续影响后面的对话。编排器误判的代价，通常比普通技能误判更高。

为什么不直接把测试驱动开发、调研、实现和代码评审等内容，全部注册成独立 skills 呢？

第一个原因是命名冲突。这些通用名称可能与用户安装的其他技能集合重名。pi-matt-pocock 没有把每个流程文档注册成全局技能，而是把它们作为包内普通资源保存。这样既保留了方法论，又避免占用全局能力名称。

第二个原因是上下文控制。独立技能通常需要分别提供发现信息、描述和正文。技能一多，上下文成本也会增加。编排器只在确认进入某条路线后，按需加载当前步骤，不需要让所有方法同时在场。

第三个原因是状态管理。纯技能可以告诉模型“应该怎样做”，却不天然记录“现在做到哪一步”。编排器则明确保存路线、步骤和阶段，并通过同一个工具完成切换。因此，多阶段任务获得了清晰进度、自动推进和重启恢复能力。

当然，“只暴露一个工具”并不等于没有成本。这个主工具的参数定义里，仍然列出了五条路线，以及每条路线允许使用的流程步骤和已知别名。模型切换阶段时，只能从有效选项中选择，扩展也可以立即验证请求。代价是，这些枚举仍会占用少量上下文。

当前设计选择了一个折中方案：用参数枚举约束选择，同时让体积最大的流程正文按需加载。更激进的办法，是连流程步骤都不写进工具定义，只让模型表达意图，再由运行时查表。这样能进一步降低上下文成本，但模型不再受到即时约束。非法步骤只能等到运行时再拒绝，可靠性会下降。

从更大的角度看，这不只是“用不用 skills”的争论。所谓 SKILL 点 Markdown，本质上是一种提示词分发格式。它解决的是，怎样把一段方法论文本放到模型面前。但它并没有完整解决：什么时候放，放多少，任务到了哪一步，以及下一步应该去哪里。

围绕这些问题，可以形成一条架构谱系。

最简单的是扁平技能库。每项能力独立发现、独立使用。它安装方便，彼此正交，也没有编排成本，适合单步、无状态的能力，例如特定格式化或代码检查。但它不擅长维护有先后依赖的长期流程。

再往前一步，就是 pi-matt-pocock 采用的方式：单一编排入口，加包内流程资源，再把状态写入会话。这样能减少命名冲突和不必要的正文加载，也能恢复进度。代价是必须维护一层适配，把上游技能内容转换成适合 Pi 运行时的流程文档。

更严格的方向，是确定性状态机。运行时明确规定哪些步骤可以转移到哪些步骤。模型只能提出切换请求，系统负责检查完成条件并拒绝非法转移。这种方式可靠性更高，适合对过程合规有硬性要求的任务。比如，测试还没有出现预期失败时，就不允许开始写实现。不过，真实任务未必总能完整套入预设流程，所以严格状态机也会牺牲灵活性。

还有一种方向，是按阶段拆分执行主体。每个阶段使用新会话或独立子智能体，阶段之间只传递规格、任务简报或问题单等结构化产物。这样上下文最干净，也方便并行调研和评审。但交接协议会成为新的复杂度来源，而且需要运行时提供明确的多会话或子智能体支持。

最值得记住的是，方法论正文不一定要和能力注册绑定在一起。把正文当作运行时数据之后，何时加载、加载多少、作用于哪些阶段，都可以分别优化。

普通 skills 适合独立、单步、无状态的能力。多阶段、有依赖顺序，而且需要跨会话继续的工程任务，更需要编排器和持久化状态。如果流程合规本身非常重要，就还要把约束从提示词下沉到运行时机制。

换句话说，skills 回答的是“方法论怎样分发”。而复杂工程真正需要回答的是：怎样让正确的方法，在正确的时间，以合适的粒度，带着准确的状态进入上下文。pi-matt-pocock 的价值，就在于把这个提示词问题，进一步变成了一个可管理的运行时问题。

给人工智能助手装上一组技能，不等于它就能稳妥地完成一个多阶段工程任务。真正的问题是：助手现在走到哪一步，该加载哪段方法，以及会话重启以后，能不能准确接着做。

理解这种设计，可以先想一个场景：你让助手实现一个复杂功能。助手需要澄清需求，写规格，拆任务，再进行实现和评审。如果这些方法只是几份独立的技能文档，助手可以分别调用，但“现在做到哪里了”，通常还要靠模型从对话里理解。

对话一长，或者会话重新启动，进度就需要重新判断。

这个扩展包换了一种做法。它把方法文档留在包内部，不把每份文档都注册成全局技能。模型通过一个主要的编排工具，启动或者切换工作流。每次切换，扩展都会把当前路线、具体步骤和阶段，写进 Pi 的会话记录。

比如，一个任务选择了从创意到上线的路线，当前处于需求澄清阶段。完成这一步后，模型再通过同一个工具，切换到下一步，并保存新状态。会话重启时，扩展会从同一会话分支里，恢复最后一个有效状态，而不是让模型从长对话里猜进度。

这里最值得记住的变化是：流程进度不再只存在于对话里，而是有一份由运行时保存的明确记录。

这个包目前支持五类路线。完整功能开发是一类，疑难缺陷的诊断修复是一类。还有把原始请求整理成可执行任务、为大型模糊计划建立实施路径，以及调查和改善代码库架构。

这些路线的共同点，是任务复杂、步骤之间有依赖。普通的单步请求，不需要进入工作流。

接下来再看，它为什么不直接公开一大堆技能。

作者给出的主要理由有三个：控制上下文，避免名称冲突，以及获得可恢复的流程状态。

名称冲突比较容易理解。测试驱动开发、调研、实现、代码评审，都是很通用的技能名称。如果用户已经安装了其他技能集合，就可能遇到同名能力。这个包把方法文档作为内部资源保存，不注册成全局技能，也就避开了这类冲突。

上下文控制则更细一点。这里的上下文，就是模型处理当前请求时能够看到的信息。

这个包只在启动、切换或者恢复某个步骤时，按需注入当前步骤的完整方法。后续轮次不会反复塞入所有流程正文，只增加简短的阶段指引。例如，现在应遵循哪一步，下一步明确时应自动推进，以及什么情况下才需要询问用户。

连工具是否可用，也会随状态变化。它有一个让用户作出结构化选择的问答工具，但这个工具只在工作流激活期间启用。也就是说，能力不是安装之后一直全部摆在模型面前，而是可以按当前任务开放。

不过，这里有一个重要限定：只暴露一个主要工具，不代表上下文成本为零。

工具仍然需要一份参数说明，告诉模型可以选择哪些路线、哪些步骤。这份说明叫工具模式，也就是 schema。当前方案会列出有效选项，让模型在切换步骤时有明确约束，扩展也能检查请求是否合法。

所以，它节省的是多个独立能力的发现信息，以及方法正文不必要的加载，并不是消除了所有工具描述成本。

而且，这种适配有维护代价。更新上游方法时，不能直接复制文件。维护者需要选择内容，改成内部流程文档，再保留 Pi 所需的会话、界面和工具启停逻辑。这是一层有意维护的适配，不是上游仓库的简单镜像。

理解了这些取舍，再看文章提出的更大问题：技能文件和工作流运行时，到底各自负责什么？

作者的判断是，技能文件主要解决方法论如何分发。它把一段方法送到模型面前，但并不天然解决什么时候送、送多少、当前在哪一步，以及下一步去哪里。

这些事情属于运行时设计。

沿着这个方向，还能继续加强控制。例如，不在工具参数里列出步骤，而是让模型只表达意图，由运行时查表加载方法。这样可以进一步减少参数说明的体积，但模型切换步骤时，也失去了枚举选项带来的即时约束。无效请求要留给运行时拒绝。

另一种方向，是把步骤之间允许的转移写成确定性的状态机。模型只能申请进入下一阶段，运行时检查完成条件，通过了才放行。

比如，要求测试先出现失败结果，才能开始写实现。这种硬性过程要求，仅靠提示词提醒还不够，需要机制层面的检查。

但约束越强，灵活性也越低。真实任务如果不符合预设流程，就可能被强行套进流程，或者只能绕过它。文章讨论的这些更强设计，是进一步的架构方向，不能当成当前扩展包已经具备的能力。

因此，选择方案时，不是越复杂越好。独立、单步、没有状态的能力，普通技能就足够。多阶段、有先后依赖、需要跨会话继续的工程任务，才更适合编排器和持久化状态。对过程合规有硬性要求的任务，则需要进一步考虑运行时约束。

最后还有一条容易被忽略的原则：不进入流程，也必须是正常选项。这个包明确要求，任务不适合复杂工程流程时，就正常处理；不确定时，宁可不启动，也不要猜一条路线。因为一旦错误状态被保存，它就会影响后续每一轮。

最值得记住的是：方法文档、能力注册和流程状态，可以分开设计。技能解决的是“有哪些方法可用”，编排器进一步解决“此刻该用哪一种，以及接下来怎么走”。是否需要这层编排，取决于任务的复杂度、恢复需求和过程风险，而不是工具数量越少，或者流程约束越强，就一定越好。
