### Self improving skills for agents

“not just agents with skills, but agents with skills that can improve over time”

Seems that “

[SKILL.md](http://skill.md/)” is here to stay, however, we haven’t really solved the most fundamental problem around them:

Skills are usually static, while the environment around them is not!

A skill that worked a few weeks ago can quietly start failing when the codebase changes, when the model behaves differently, or when the kinds of tasks users ask for shift over time. In most systems, those failures are invisible until someone notices the output is worse, or starts failing completely.

The missing piece here for making the skills folder actually useful is to start treating them as living system components, not fixed prompt files.

And this is exactly the idea behind

[cognee-skills](https://pypi.org/project/cognee/0.5.4.dev2/)

Not just how to store skills better or route them better, but how to make them improve when they fail or underperform!

![Image](https://pbs.twimg.com/media/HDO0Z6lXIAESPi0?format=png&name=large)

Until today, the skills were about:

1. writing a prompt
2. saving it in a folder
3. calling it whenever needed

This works surprisingly well, but unfortunately only for demos… After a certain point, we start hitting the same wall:

- One skill gets selected too often
- Another looks good but fails in practice
- One individual instruction keeps failing
- A tool call breaks because environment has changed

And the worst part of all is that no one knows if the issue is routing, instructions, or the tool call itself, which leads to manual maintenance and inspection. What we achieved with this implementation is to have the whole loop closed leading us to skills that can self-improve over time.

But let’s also give a brief overview of what is happening under the hood.

#### 1\. Skill ingestion

Right now your skill folder looks something like this:

my\_skills/ summarize/

[SKILL.md](http://skill.md/) bug-triage/

[SKILL.md](http://skill.md/)

code-review/

[SKILL.md](http://skill.md/)

Last week, we showed that with cognee we can give everything a clearer structure, not just because it looks nicer, but because it also makes searching much more effective. We can also enrich the different fields with semantic meaning, task patterns, summaries, and relationships, which helps the system understand and route information smarter. All of these are stored using cognee’s “Custom DataPoint”.

Here is a small visualization of how your skills could look like:

[![视频](https://pbs.twimg.com/amplify_video_thumb/2032174021022756864/img/e4O33hDUcsHjtLIO.jpg)](https://x.com/tricalt/status/2032179887277060476)[![视频](https://pbs.twimg.com/amplify_video_thumb/2032174021022756864/img/e4O33hDUcsHjtLIO.jpg)](https://x.com/tricalt/status/2032179887277060476)

Link to the dynamic graph view:

[https://cognee-graph-skills.vercel.app/](https://cognee-graph-skills.vercel.app/)

#### 2\. Observe

A skill cannot improve if the system has no memory of what happened when it ran. For that reason, after the execution of each skill, we store data in order to know:

- What task was attempted
- Which skill was selected
- Whether it succeeded
- What error occurred
- User feedback, if any

With observation, failure becomes something the system can reason about. You cannot improve a skill if you do not know what happened when it ran. Keeping in mind that we operate on a structure graph this can be added by an additional node which will have all the observations collected. That is all manageable by cognee’s “Custom DataPoint”, where one could specify all the fields that they want to populate.

#### 3\. Inspect

Once enough failed runs accumulate (or even after a single important failure) one can inspect the connected history around that skill: past runs, feedback, tool failures, and related task patterns. Because all of this is stored as a graph, the system can trace the recurring factors behind bad outcomes and use that evidence to propose a better version of the skill.

runs → repeated weak outcomes → inspection

#### 4\. Amend skill → .amendify()

Once the system has enough evidence that a skill is underperforming, it can propose an amendment to the instructions. That proposal can be reviewed by a human, or applied automatically. The goal is simple:

- Reduce the friction of maintaining skills as systems grow.

Instead of manually searching through your codebase for broken prompts, the system can look at the execution history of a skill, including past runs, failures, feedback, and tool errors, and suggest a targeted change.

The amendment might:

- tighten the trigger
- add a missing condition
- reorder steps
- change the output format

This is the moment where skills stop behaving like static prompt files and start behaving more like evolving components. Instead of opening a SKILL.md file and guessing what to change, the system can propose a patch grounded in evidence from how the skill actually behaved.

#### 5\. Evaluate &amp; Update skill

A self-improving system though, should never be trusted simply because it can modify itself. Any amendment must be evaluated. Did the new version actually improve outcomes? Did it reduce failures? Did it introduce errors elsewhere?

For that reason, the loop cannot be just:

- observe → inspect → amend

Instead, it must follow a more disciplined cycle:

- observe → inspect → amend → evaluate

If an amendment does not produce a measurable improvement, the system should be able to roll it back. Because every change is tracked with its rationale and results, the original instructions are never lost, and self-improvement becomes a structured, auditable process rather than uncontrolled modification. When the evaluation confirms improvement, the amendment becomes the next version of the skill.

![Image](https://pbs.twimg.com/media/HDO5uNpWUAAAGGk?format=jpg&name=large)

#### Conclusion

Skills cannot stay static while the systems around them constantly change. As models, codebases, and tasks evolve, fixed prompt files inevitably degrade. We introduced a straightforward way to do so, automatically, while not giving up any of the control and oversight over the skills themselves.

## 结构化（2）

### 2026-03-14 01:27:26

**主旨概括：**  
这篇文章讲的是：**让 Agent 的 “技能（SKILL.md）” 不再是静态提示词文件，而是能根据执行效果持续观察、修正、评估、升级的 “可自我改进组件”**。核心问题是：环境在变，但技能常常不变，所以久而久之就会失效。

---

##### 1. 为什么传统技能机制不够用
- 现在很多 Agent 技能，本质上就是：  
  **写一个 prompt → 存到文件夹里 → 需要时调用**
- 这种方式做演示时很好用，但在真实系统里会遇到很多问题：
  - 某个技能被**过度选中**
  - 某个技能看起来不错，**实际效果却差**
  - 某条指令经常**执行失败**
  - 工具调用因为环境变化而**失效**
- 更麻烦的是：  
  **很难判断问题到底出在路由、提示词指令，还是工具调用本身**，所以最后只能靠人工排查和维护。

**通俗例子：**  
比如一个 “代码审查” 技能，几周前还能正常工作；但代码库结构变了、模型行为变了，或者用户提问方式变了，这个技能就可能悄悄变差，直到有人发现输出越来越不靠谱。

---

##### 2. 核心思路：把技能当成 “活的系统组件”
- 作者提出的方向是：  
  **不只是更好地存储和调用技能，而是让技能在失败或表现差时，能够自己改进。**
- 这正是**cognee-skills**的目标：
  - 技能不是固定文件
  - 技能应该有 “记忆”
  - 技能应该能根据历史表现被修正和升级

---

##### 3. 第一步：Skill Ingestion（技能导入与结构化）
- 传统技能目录通常长这样：
  - `my_skills/summarize/SKILL.md`
  - `my_skills/bug-triage/SKILL.md`
  - `my_skills/code-review/SKILL.md`
- 作者认为，技能不应只是放在文件夹里，而要被**结构化表示**：
  - 增加更清晰的字段结构
  - 补充语义信息
  - 提取任务模式、摘要、技能之间的关系
- 这些信息会通过 cognee 的**Custom DataPoint**存储。

**好处：**
- 搜索更高效
- 系统更容易理解每个技能适合什么任务
- 技能路由会更智能

---

##### 4. 第二步：Observe（观察运行结果）
- 技能想要自我改进，前提是系统必须记住它执行时发生了什么。
- 所以每次技能执行后，要记录这些信息：
  - 尝试处理的**任务是什么**
  - 选择了**哪个技能**
  - 是否**成功**
  - 出现了什么**错误**
  - 是否有**用户反馈**
- 这些观察数据也会作为图结构中的节点保存下来。

**关键点：**
- 没有观察，就没有改进
- 失败不再是 “没人注意到的坏结果”，而是系统可以分析的证据

**例子：**  
如果 “bug-triage” 技能连续几次都在某类报错上失败，系统就能积累证据，而不是等人工事后发现。

---

##### 5. 第三步：Inspect（检查失败原因）
- 当失败记录积累到一定程度，或者哪怕只发生了一次重要失败，系统就可以回头检查这个技能的历史：
  - 过去的运行结果
  - 用户反馈
  - 工具失败记录
  - 相关任务模式
- 因为这些信息是以**图结构**存储的，系统可以找到反复出现的问题因素。

作者给出的逻辑是：  
**运行记录 → 重复的差结果 → 触发检查**

**作用：**
- 找到 “技能为什么效果差” 的真正原因
- 给后续修改提供依据，而不是靠猜

---

##### 6. 第四步：Amend（修订技能）
- 当系统收集到足够证据，判断某个技能表现不佳时，就可以提出修改建议，甚至自动应用。
- 文中把这个过程称为：**`.amendify ()`**
- 修订可能包括：
  - **收紧触发条件**
  - **增加缺失的条件判断**
  - **调整步骤顺序**
  - **修改输出格式**
- 修改方式可以是：
  - 人工审核后再应用
  - 自动应用

**核心价值：**
- 不需要人工满代码库翻 prompt 找问题
- 系统能根据执行历史，针对性地提出补丁

**通俗例子：**  
如果某个 “总结” 技能总是漏掉结论，系统可能会建议在提示词里增加 “最后必须输出结论” 这一条，而不是笼统地重写整个技能。

---

##### 7. 第五步：Evaluate & Update（评估并更新）
- 作者强调：  
  **会自我修改的系统，不能因为能改自己就被默认信任。**
- 所以修订后必须评估：
  - 新版本是否真的提升了效果？
  - 是否减少了失败？
  - 是否引入了新的错误？
- 完整闭环不应该只是：
  - **observe → inspect → amend**
- 而应该是更严格的：
  - **observe → inspect → amend → evaluate**
- 如果修订没有带来可衡量的改善，就应该**回滚**。
- 因为每一次修改都有记录，包括修改原因和结果，所以整个过程是：
  - 可追踪的
  - 可审计的
  - 可回退的

**关键点：**
- 真正的 “自我改进” 不是乱改，而是**有证据、有验证、有版本控制地改**

---

##### 8. 结论
- 技能不能一直保持静态，因为：
  - **模型会变**
  - **代码库会变**
  - **用户任务会变**
- 静态 prompt 文件最终一定会退化。
- 这篇文章提出的方法，就是用一个完整闭环让技能自动演化：
  - **结构化导入**
  - **记录执行观察**
  - **分析失败原因**
  - **提出修订**
  - **评估效果并决定是否更新**
- 这样既能实现自动改进，又不失去对技能系统的控制和监督。

这篇文章的核心意思是：仅仅给智能体配“技能文件”还不够，关键是让技能能根据实际运行效果持续改进。作者提出了一套闭环机制，让原本静态的 `SKILL.md` 变成可观察、可修正、可验证的“活系统组件”。

- **问题背景：为什么静态技能不够用**
  - 现在很多 agent 的技能，本质上只是把提示词写进 `SKILL.md`，放进文件夹里，需要时调用。
  - 这种方式做演示很有效，但一到真实环境就容易失效，因为外部条件一直在变：
    - 代码库会变化
    - 模型行为会变化
    - 用户任务类型会变化
  - 结果是：一个几周前还能正常工作的技能，可能会悄悄失效，直到输出质量明显下降，甚至完全报错，人才会发现。

- **传统技能系统的几个典型问题**
  - 技能可能被错误地频繁调用，比如“某个 skill 被选中过多”。
  - 有些技能表面上设计得不错，但实际执行经常失败。
  - 失败点可能来自单条指令、路由选择，或者工具调用环境变化。
  - 最麻烦的是：系统通常分不清问题到底出在“路由、指令还是工具调用”，所以最后只能靠人工排查和维护。

- **作者提出的核心思路：让技能进入“自我改进闭环”**
  - 文章介绍的 `cognee-skills`，重点不是“怎么更好地存技能”或“怎么更好地路由技能”，而是：
    - 当技能失败或表现不佳时，系统能自动发现问题
    - 根据证据提出修改方案
    - 再验证修改是否真的有效
  - 目标是把技能从“固定提示文件”变成“可持续优化的系统组件”。

- **1. 技能摄取（Skill ingestion）：先把技能结构化管理起来**
  - 原始技能目录可能长这样：
    - `my_skills/summarize/SKILL.md`
    - `my_skills/bug-triage/SKILL.md`
    - `my_skills/code-review/SKILL.md`
  - 作者认为，技能不应只是文件堆放，而应被结构化存储，并补充语义信息，例如：
    - 技能摘要
    - 任务模式
    - 技能之间的关系
  - 这样做的好处是：
    - 搜索更高效
    - 路由更智能
    - 系统更理解每个技能适合处理什么任务
  - 这些信息通过 cognee 的 `Custom DataPoint` 存储。

- **2. 观察（Observe）：记录每次技能运行发生了什么**
  - 如果系统没有“记忆”，技能就不可能改进。
  - 因此，每次技能执行后，都要记录关键数据，例如：
    - 尝试处理了什么任务
    - 选中了哪个技能
    - 是否成功
    - 出了什么错误
    - 有没有用户反馈
  - 文章强调：只有把失败记录下来，失败才能变成可分析、可推理的对象。
  - 这些观察结果会作为图结构中的额外节点保存，依然由 `Custom DataPoint` 管理。

  - 当某个技能积累了足够多失败记录，甚至一次重要失败后，就可以检查它相关的历史信息：
    - 过去运行记录
    - 用户反馈
    - 工具报错
    - 相关任务模式
  - 因为数据是以图结构存储的，系统可以追踪“哪些因素反复导致差结果”。
  - 作者用一个简洁逻辑表示这个过程：
    - `runs → repeated weak outcomes → inspection`
  - 通俗理解：不是凭感觉改提示词，而是根据真实失败证据来定位问题。

- **4. 修改技能（Amend skill / `.amendify()`）：基于证据提出修补方案**
  - 当系统判断某个技能表现不佳时，就可以提出对技能说明的修改建议。
  - 这个修改可以：
    - 由人工审核后再应用
    - 或自动应用
  - 修改内容可能包括：
    - 收紧触发条件
    - 增加遗漏的判断条件
    - 调整步骤顺序
    - 改变输出格式
  - 举个例子：
    - 如果某个总结技能总是在特定任务上漏掉关键数据，系统可能会建议在指令里明确加上“必须保留数字、案例和结论”。
  - 这一阶段的意义是：不再靠人工打开 `SKILL.md` 猜哪里有问题，而是让系统根据执行历史提出有依据的补丁。

- **5. 评估与更新（Evaluate & Update）：改完后必须验证**
  - 作者特别强调：系统不能因为“会自我修改”就被直接信任。
  - 每次修改后都必须评估：
    - 效果有没有变好
    - 失败有没有减少
    - 是否引入了新的问题
  - 所以完整闭环不是：
    - `observe → inspect → amend`
  - 而必须是更严格的：
    - `observe → inspect → amend → evaluate`
  - 如果修改没有带来可衡量的改进，就应该回滚。
  - 因为每次修改都会记录“修改理由”和“修改结果”，所以原始技能不会丢失，整个过程也是可审计的。
  - 只有评估通过后，修改版才会成为技能的新版本。

- **结论：技能必须从“静态文件”升级为“可进化组件”**
  - 作者的最终观点很明确：模型、代码库、任务都在不断变化，技能如果保持静态，性能一定会逐渐退化。
  - `cognee-skills` 提供的是一种相对直接的实现路径：让技能能自动观察、发现问题、提出修改、验证效果，同时保留人工控制和审查能力。

## 综合-思辨（1）

### 2026-03-14 03:21:45

下面是对这篇**“Self improving skills for agents”**的去 hype 分析。

---

#### 1. 核心主张总结

这篇文章的核心卖点很明确：**不要把 agent 的`SKILL.md`当成静态提示词文件，而要把它当成可以持续观测、诊断、修订、评估的 “活组件”**。作者想解决的问题也是真问题：随着代码库变化、工具接口变化、模型行为漂移、用户任务类型变化，原本有效的 skill 会逐渐失效，而大多数系统并没有机制去系统性发现 “到底是路由错了、提示词坏了、还是工具调用失效了”。

文章提出的机制是一个闭环：

> **ingest skill → observe execution → inspect failures/history → amend skill → evaluate & update**

底层上，它用**cognee 的 graph / Custom DataPoint**来存储 skill 结构、运行记录、失败原因、反馈、任务模式及它们之间的关系。然后在积累到足够失败证据后，系统生成一个 skill amendment（修补建议），再由人工或自动应用，并通过后续评估决定是否保留或回滚。

但要注意，文章真正推广的，除了 “self-improving skills” 这个概念本身，还有一个更具体的东西：**用 cognee 的图结构和数据模型来承载这套循环**。这里 “让技能自我进化” 是概念层卖点，而 “graph + Custom DataPoint + amendify” 是产品 / 框架层卖点。前者有现实问题基础，后者则明显带有框架包装色彩。

---

#### 2. 概念层面的价值

下面是这篇文章里**确实值得肯定**的部分。

##### 价值点 1：它抓住了 skill 系统最真实的维护痛点
“skills 是静态的，但环境是变化的” 这句并不新鲜，但它确实点中了现在很多 agent 系统的软肋。很多团队把 prompt /tool instruction /workflow 模板塞进文件夹后，就默认它们会一直有效，直到线上表现明显变差才人工排查。  
**这不是伪问题，而是实际存在的运维问题。**

##### 价值点 2：把 prompt/skill 维护问题转成 “可观测性 + 版本控制” 问题，这个方向是合理的
文章最有启发的一点不是 “LLM 会自动改 prompt”，而是它暗示了一种更工程化的思路：

- skill 运行要留痕
- 失败要有结构化记录
- 修改要有证据链
- 更新要可回滚

这其实是在把 prompt engineering 从 “手工调咒语” 往 “可观测系统维护” 推进。  
**这个方向是有建设性的，而且确实比单纯写 prompt 更成熟。**

##### 价值点 3：它试图区分 “路由问题 / 指令问题 / 工具问题”
这点很关键。很多 agent 故障其实不在 prompt 本身，而在：

- 选错 skill
- 选对了 skill，但步骤不对
- 步骤没问题，但 tool API 变了
- tool 没问题，但输出格式不兼容

文章至少在概念上意识到：**“失败” 不能只归咎于提示词质量**。这比很多只会喊 “优化 prompt” 的文章更接近实际系统。

##### 价值点 4：并非完全新范式，更像是现有实践的系统化包装
必须客观说，这套思路**并没有填补一个全新的理论空白**。社区里早就在做：

- trace /logging
- prompt versioning
- offline eval
- failure replay
- human-in-the-loop prompt refinement

作者的贡献更像是：**把这些零散实践包装成一个 “skills 自改进闭环” 叙事，并试图用图存储统一承载**。这不是坏事，但也不应被理解成 “革命性突破”。

---

#### 3. 落地与实现层面的批判

这是这篇文章最需要冷静看的地方。概念顺，但实现细节明显不够。

##### 1）核心 “自我改进” 算法几乎是黑箱
文章反复说系统可以：

- trace recurring factors
- propose a better version of the skill
- suggest a targeted change

但**完全没有给出关键机制**：

- 如何判断是 routing 问题还是 skill instruction 问题？
- 如何从历史 observation 中抽取 “根因”？
- amendment 是 rule-based、LLM-based，还是 retrieval-based？
- amendment proposal 的 prompt/template 是什么？
- 修改粒度是整段重写，还是局部 patch？
- 如何避免它把偶发错误误判为系统性问题？

也就是说，最关键的地方被一句 “系统可以 propose amendment” 带过去了。  
**听起来很高级，但真正难的恰恰就在这里。**

---

##### 2）“图结构存储” 可能是在用重型技术包装一个可先用简单方案验证的问题
文章大量强调：

- graph
- relationships
- semantic enrichment
- Custom DataPoint

但从描述看，目前存的核心信息本质上就是：

- skill 元数据
- 执行日志
- 成败标签
- 错误信息
- 用户反馈
- 修改版本

这些数据**完全可以先用更简单的方式实现**：

- JSONL / SQLite / Postgres
- 文件级 skill registry
- execution log 表
- version diff + rollback 记录

换句话说，文章没有证明 “图数据库 / 图结构” 在这个问题上带来了不可替代的收益。  
如果只是 “因为 graph 看起来更聪明，更适合展示关系”，那它更像一种**架构审美**，还不是严格意义上的必要技术。

---

##### 3）缺乏真实、可复现的量化数据，这是最大风险点
这是全文最明显的硬伤。文章没有给出任何关键指标，例如：

- amendment 前后的任务成功率变化
- tool call failure 的下降比例
- 路由错误率是否下降
- 人工维护时间是否减少
- 自动 amendment 的采纳率
- 回滚率有多高
- 在多少个 skill、多少次运行、多久时间窗口上验证过

它讲的是一个非常强调 “闭环评估” 的系统，但文章自己**没有提供这个闭环是否有效的证据**。  
这就形成了一个略微尴尬的局面：

> 文章说 “修改必须评估，否则不能信任”，但它自己也没有拿出对该框架的评估。

所以基于当前信息，这更像一个**合理的系统设计提案**，而不是被实证证明有效的成熟方案。

---

##### 4）最难的环节 “评估” 被一笔带过
作者提到：

- amendment 必须 evaluate
- 不行就 rollback

这当然正确，但问题在于：**评估才是整个系统里最难、最昂贵、最容易失真的部分**。

具体难点包括：

- skill 成功的定义是什么？
- 是用户主观满意度、任务完成率，还是 tool 输出正确率？
- 多步骤 agent 的局部 skill 改动，如何隔离变量做归因？
- 如果任务分布变了，前后表现还能直接对比吗？
- 评估集怎么构造？线上 shadow eval 还是离线 replay？
- amendment 如果提升了 A 类任务，却损伤了 B 类任务，怎么决策？

这些都没展开。于是 “evaluate & rollback” 目前更像是一个**应该做的工程原则**，而不是作者已经解决的技术能力。

---

##### 5）没有讨论 “自动修改 prompt/skill” 带来的新失稳风险
一个能修改自己的 skill 系统，会引入新的风险：

- 局部最优：为最近失败样本过拟合
- 提示词膨胀：skill 越改越长、越脆弱
- 隐性退化：某类少见任务表现变差却未被及时发现
- 错误归因：把模型波动当成 skill 缺陷
- 数据污染：用户反馈本身噪声很大
- 回路漂移：系统不断基于自己生成的解释来修自己

这些都是 self-improving 系统的核心风险。文章虽然口头上提到 “不能盲信”，但没有具体防护机制。  
**如果没有强评估与变更治理，这类系统很容易从 “自我改进” 滑向 “自我扰动”。**

---

##### 6）整体更像方向性产品宣传，而不是扎实技术分享
文章的语言风格偏产品叙事：

- “living system components”
- “whole loop closed”
- “skills that can self-improve over time”

这些说法都很吸引人，但技术分享应有的部分相对缺失：

- 没有 architecture diagram 的细节层级
- 没有 amendment 生成逻辑
- 没有评估协议
- 没有 baseline 对比
- 没有 failure case 分析
- 没有成本讨论

所以这篇内容更适合被看作：  
**“一个值得探索的产品方向预告”**，而不是 “已经证明有效的工程解法”。

#### 4. 现实替代方案对比

下面这个表，帮助你看清：它到底是在解决一个新问题，还是用更复杂的基础设施包装一个已有实践。

| 维度 | 对方方案描述 | 更简洁现实的常见做法 | 复杂度 / 依赖差异 |
|------|--------------|----------------------|-----------------|
| Skill 存储 | 用 cognee 的 graph + Custom DataPoint 存技能结构、语义字段、关系 | 直接用`SKILL.md` + YAML frontmatter / JSON 配置管理元数据 | 图结构更重，前期不一定比文件 + 结构化字段带来更高收益 |
| 运行观测 | 每次 skill 执行后写入 graph observation 节点，记录任务、成功与否、错误、反馈 | 用日志系统、JSONL、SQLite/Postgres 记录 execution trace | 传统日志 / 表格足够支撑早期分析，图不是必需 |
| 故障诊断 | 基于图中的关联历史做 inspect，寻找 recurring factors | 先做简单的失败聚类：按 skill、错误码、tool 名称、任务类型统计 | 后者实现更轻，且更容易快速验证哪些问题最常见 |
| Skill 修改 | `.amendify ()`自动提出 amendment，可能人工审核或自动应用 | 人工 review 历史失败样本后手动改 prompt；或用 LLM 生成 patch 草案但人工确认 | 自动修改更 “酷”，但风险和治理成本显著更高 |
| 评估更新 | observe → inspect → amend → evaluate，失败可 rollback | 建一个固定 eval 集 + 少量线上 A/B/shadow test，再决定是否替换 | 主流做法虽朴素，但更容易归因和建立可信度 |
| 版本治理 | 每次 amendment 带 rationale 和结果追踪 | Git diff + changelog + eval report 即可实现 | Git + eval 报告已经能满足多数团队的审计需求 |
| 路由优化 | 借助技能结构、关系、语义 enrichment 让系统更智能地选 skill | 先用 embedding 检索 + rule-based routing + few-shot 分类器 | 后者通常更透明，也更便于 debug |
| 系统依赖 | 依赖 cognee 数据模型、图存储思路、框架能力 | Markdown + Python 脚本 + 数据库 + 评估脚本 | 对大多数团队来说，后者更低成本、可控、可迁移 |
| 可解释性 | 理论上图关系更丰富，可追溯上下文 | SQL 查询、日志回放、diff 对比也能提供足够解释 | 图可视化更漂亮，但不等于更容易做出正确判断 |

**核心结论：**  
这套方案并不是没有价值，而是它引入的复杂性目前**还没有被证明确实换来了成比例的效果提升**。

##### 一句话评价

##### 对真实用户心态的推测
虽然你没有提供这篇文章的具体点赞 / 收藏 / 评论数据，但按这类内容在技术社区的典型反馈模式看，真实用户通常会分成两类：

1. **概念认同派**  
   会觉得 “对，prompt/skill 确实需要持续维护，终于有人系统化讲这件事了”。

2. **工程怀疑派**  
   会追问 “效果呢？数据呢？为什么一定要 graph？amend 到底怎么做？eval 怎么做？”

如果这篇内容出现 “点赞不少、深度讨论不多、评论里多是 ‘interesting /cool’”，那通常说明它更像是**方向获得认同**，而不是实现获得信任。  
换句话说，大家愿意为叙事点头，但还没有足够证据愿意在生产环境下注。

##### 立即可执行的实用建议

###### 建议 1：先别上图，先用最小闭环验证
先用下面最简单的闭环跑起来：

- `SKILL.md` + YAML 元数据
- 每次执行记录到 SQLite / JSONL
- 失败样本按 skill 聚类
- 人工总结最常见失败原因
- 用 LLM 生成 1 个 patch 草案
- 在固定 eval 集上跑前后对比

如果这个闭环都不能稳定带来收益，引入 graph 只会把问题包装得更复杂。

###### 建议 2：先手动迭代 3 轮，再谈自动 amend
自动 amendment 最容易让人兴奋，也最容易失控。比较稳妥的做法是：

- 前 3 轮只做 “系统提出建议，人类批准修改”
- 每轮都保留修改原因、前后 diff、eval 结果
- 统计 amendment 的真实采纳率与收益率

如果 3 轮之后你发现：
- amendment 建议大多靠谱
- 改动能稳定提升
- 回滚率可接受

再考虑局部自动化，不然很容易进入 “自动制造新问题” 的循环。
