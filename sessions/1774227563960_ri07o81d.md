## 结构化（1）

### 2026-03-23 03:17:30

#### 主旨概括

这篇内容的核心是在强调：**给代码生成 Agent 明确加入“少做、做准、不过度设计”的系统提示，能显著提升输出质量**。作者认为，这类约束不仅适用于 Claude Code，也适用于 Codex 等任何写代码的智能体。

#### 1. 作者的核心观点：系统提示很有价值

- 作者表示，Claude Code 的这段 system prompt 很实用，已经被加入到 Codex 中使用。
- 他认为，这不是只适用于某一个工具的技巧，而是对**所有代码生成 Agent**都有参考意义。
- 其背后的思想可以概括为：**减少智能体“自作主张”的空间，让它更贴近真实需求。**

#### 2. 提取出的提示原则：避免过度设计，保持简单直接

- 第一条原则是：**避免过度设计**，只做用户直接要求的修改，或者那些“明显必要”的改动。
- 不要顺手加入新功能、额外重构，或做超出任务范围的“优化”。
- 对于 bug 修复，重点是**修好 bug 本身**，而不是顺便清理整片周边代码。
- 对于简单功能，不需要额外加入可配置性。

**例子：**
如果用户只是要求“修复一个接口返回为空时的报错”，那就修这个判空逻辑即可，不需要顺手把整个接口层重构一遍，也不需要加一套配置开关。

#### 3. 关于代码写法的要求：只在必要处增加说明和校验

- 不要无意义地补充文档字符串、注释或类型注解，尤其是**对未修改的代码**不要乱加说明。
- 注释只应出现在**逻辑不够自解释**的地方。
- 不要为几乎不可能发生的情况增加错误处理、回退机制或额外验证。
- 应该信任内部代码和框架本身提供的保证，**验证主要放在系统边界**，例如：
  - 用户输入
  - 外部 API 返回
- 这意味着，不要在系统内部层层防御，造成代码膨胀。

**例子：**
调用内部已经保证非空的函数参数时，不需要每一层都再写一遍 `if x is None`；但如果数据来自用户表单或第三方接口，就应该做校验。

#### 4. 关于工程实现的要求：不要为了“将来可能”而提前复杂化

- 不要为了直接改代码就能解决的问题，额外引入功能标志（feature flag）或向后兼容层。
- 不要为一次性操作专门抽辅助函数、工具函数或额外抽象。
- 不要为“假设未来会有需求”而提前设计。
- 合适的复杂度标准是：**满足当前任务的最低复杂度即可**。
- 原文明确提出：**三个相似的代码行，往往比过早抽象更好。**

**例子：**
如果某个页面只需要改 3 处类似文案，直接改 3 行通常就够了；没必要为了“以后也许会复用”先抽一个通用文案引擎。

#### 5. 对遗留代码和兼容写法的态度：能删就删，不留“假兼容”

- 要避免那些“看起来兼容、实际上只是拖累”的 hack。
- 文中举到的反面做法包括：
  - 重命名未使用变量
  - 重新导出类型
  - 加上 `// 已移除` 之类的保留性注释
- 如果已经确定某部分代码**没有被使用**，就可以直接删除，而不是保留一层形式上的兼容。

这体现的思想是：**代码库应该尽量保持干净，而不是堆积历史包袱。**

#### 6. 引用推文与讨论区反馈：大家认可“少做但做准”的价值

- 引用推文指出：Claude Code 的 system prompt 里本来就有这些要求。
- 热门回复共 **5 条**，讨论主要集中在这套提示的实际作用上。

其中几条有代表性的观点包括：

- 有人认为，如果是这样使用，不如自己搭一个环境，再自己写 system prompt，效果可能更好。
- 有人用四句话概括这种思想：**“依需而行，删繁就简，勿谋虚设，去冗求真。”**
- 也有人质疑这类 prompt 对 AI 未必足够，因为“缺乏可执行规范”，更像是给人看的“安慰剂”。
- 也有支持者认为，这段 prompt 的价值就在于把**“少做但做准”**变成默认约束；对代码 Agent 来说，稳定输出不一定来自“更会写”，而是来自**更少擅自发挥**。
- 还有回复进一步拔高到产品层面，认为：**系统提示是智能体的灵魂**，如果开发者能把这种“灵魂”打包成可复用资产，就是一种真正的能力释放。

#### 总结

- 这篇内容本质上是在提倡一种非常务实的代码生成原则：**只解决当前问题，不过度扩展，不过早抽象，不制造额外复杂度。**
- 它的重要意义在于，为代码 Agent 设定了清晰边界，让其输出更稳定、更克制，也更符合真实开发场景。
