## 分析要点

- **核心高价值点**：记忆不是可随意外挂的插件，而是代理框架管理上下文与状态的核心能力，因此“谁控制框架，谁就控制记忆”。
- **留存建议**：短期参考后归档，适合作为智能体架构选型时的观点材料（对理解代理框架、记忆耦合与平台锁定风险有一定启发，便于后续做架构比较时回看）
- **不足**：论证以观点陈述为主，证据和可验证案例较少，且夹带产品推广，需结合其他资料交叉判断

**知识要点**

- 代理框架本质上是围绕模型、工具和上下文交互的执行层，不会因模型变强而消失
- 短期记忆与长期记忆都深受框架如何加载、压缩、存储和暴露上下文的机制影响
- 封闭框架和托管 API 会把状态与记忆锁在平台内部，显著提高迁移成本
- 开放记忆存储和模型无关架构有助于降低供应商锁定风险

**行动项**

- 评估当前使用的智能体框架是否支持导出、迁移和自主管理长期记忆
- 在架构选型时把“记忆所有权”和“跨模型可迁移性”列为核心检查项

## 正文

**Harrison Chase**

### 你的框架，你的记忆

代理框架正成为构建代理的主要方式，且不会消失。这些框架与代理记忆紧密关联。如果你使用封闭框架——尤其是在专有 API 之后——你就是在选择将代理记忆的控制权让渡给第三方。记忆对创造良好且粘性强的代理体验至关重要。这会造成极大的锁定效应。记忆——因此框架——应该是开放的，这样你才能拥有自己的记忆。

#### 代理框架是构建代理的方式，而且它们不会消失

过去三年中，构建智能体系统的“最佳”方式发生了巨大变化。ChatGPT 推出时，你能做的只有简单的 RAG 链（

[LangChain](https://github.com/langchain-ai/langchain)）随后模型有所改进，能够创建更复杂的流程（

[LangGraph](https://github.com/langchain-ai/langgraph)

）随后模型有了很大改进，催生了一种新型的脚手架——

[智能体框架](https://blog.langchain.com/the-anatomy-of-an-agent-harness/)

。

代理框架的例子包括 Claude Code、深度代理、Pi（支持 OpenClaw）、OpenCode、Codex、Letta Code 等。

![Image](https://pbs.twimg.com/media/HFnuRGXXgAAo6ci?format=png&name=large)

💡 代理安全带不会消失。

有时有人认为，模型会吸收越来越多的脚手架。但事实并非如此。发生的情况（并且还会继续发生）是，2023 年所需的大量脚手架已不再需要。但这已被其他类型的脚手架所取代。根据定义，代理是一个与工具和其他数据源进行交互的 LLM。围绕 LLM 总会有一个系统来促进这种交互。需要证据吗？当 Claude Code 的源代码被泄露时，有

[512k 行代码](https://www.reddit.com/r/technology/comments/1scyuod/anthropic_leaked_512k_lines_of_claude_codebut/)。这个代码就是框架。即使是世界上最优秀模型的开发者也在大量投入框架的开发。

当网络搜索这类功能被整合到 OpenAI 和 Anthropic 的 API 中时——它们并非“模型的一部分”。相反，它们是位于这些 API 后端的轻量级框架的一部分，该框架通过仅有的工具调用方式来协调模型与那些网络搜索 API 的工作。

有时有人认为内存是一个独立的服务，与任何特定的框架相分离。但在当前情况下，这种观点并不正确。

harness 的一项重大职责是与上下文交互。正如 Sarah 所说：

> 要求将内存接入代理框架，就如同要求将驾驶行为接入汽车。管理上下文，进而管理内存，是代理框架的核心能力和职责。

记忆只是上下文的一种形式。短期记忆（对话中的消息、大型工具调用结果）由框架处理。长期记忆（跨会话记忆）需要由框架进行更新和读取。Sarah 列出了许多框架与记忆相关联的其他方式：

> How is the
>
> [AGENTS.md](http://agents.md/) or
>
> [CLAUDE.md](http://claude.md/)
>
> file loaded into context? 技能元数据如何展示给代理？（在系统提示中？在系统消息中？） 代理可以修改自己的系统指令吗？ 压缩后什么保留下来，什么被丢失？ 交互是否被存储并可被查询？ 内存元数据如何呈现给代理？ 当前工作目录如何表示？暴露了多少文件系统信息？

目前，记忆作为一个概念仍处于起步阶段，还非常早期。很明显，长期记忆通常并不包含在 MVP（最小可行产品）中。首先需要让 agent 能够正常运行，然后再考虑个性化的问题。这意味着我们整个行业目前仍在摸索记忆的相关概念。也就是说，目前对于记忆还没有广为人知或通用的抽象概念。如果记忆能够被更广泛地认知，并且随着我们发现最佳实践，独立的记忆系统可能会变得可行，但目前还不是时候。正如 Sarah 所说：“归根结底，harness 如何总体上管理上下文和状态是 agent 记忆的基础。”

#### 如果你不拥有你的 harness，你就不拥有你的内存

这个束带与内存紧密相关。

![Image](https://pbs.twimg.com/media/HFnyQkOaMAA5Yju?format=jpg&name=large)

💡 如果你使用封闭的框架，特别是如果它在一个 API 后面，你就不拥有你的内存。

这以几种方式体现出来。

轻微缺点：如果您使用有状态的 API（例如 OpenAI 的 Responses API 或 Anthropic 的服务器端压缩），您就是在其服务器上存储状态。如果您想要切换模型并恢复之前的对话，这将不再可行。

![Image](https://pbs.twimg.com/media/HFnyS21XMAAuaBj?format=jpg&name=large)

Bad: 如果你使用一个封闭的框架（例如 Claude Agent SDK，它在内部使用 Claude Code，而 Claude Code 是非开源的），这个框架会以一种你未知的方式与内存交互。它可能会在客户端生成一些工件，但这些工件的形态如何，以及该框架应如何使用这些工件，这一点是未知的，因此无法在不同框架之间移植。

![Image](https://pbs.twimg.com/media/HFnyWT3XwAA0P8e?format=jpg&name=large)

💡 但更糟糕的是另一件事——当整个框架（包括长期记忆）都被封装在一个 API 之后时。

在这种情况下，你对内存（包括长期内存）没有任何所有权或可见性。你不知道内存的使用方式（这意味着你不知道如何使用内存）。但更糟糕的是，你甚至不拥有内存！可能有些部分通过 API 暴露，有些部分则没有——你对此无法控制。

![Image](https://pbs.twimg.com/media/HFnyZ5vXgAAMD_u?format=jpg&name=large)

当人们说“模型将吸收越来越多的框架”时——这就是他们真正的意思。他们的意思是，这些内存相关的部分将隐藏在模型提供商提供的 API 之后。

💡 这非常令人担忧 - 这意味着内存将被锁定在单一平台、单一模型中。

模型提供商有极强的动力去做这件事。而且他们已经开始这么做了。Anthropic 推出了

[Claude 托管代理](https://platform.claude.com/docs/en/managed-agents/overview)。这实际上将所有内容都置于 API 之后，锁定在他们的平台上。

即使整个工具链并非完全通过 API 提供，模型提供商仍有动力将越来越多的部分迁移到 API 背后（即通过 API 提供），并且已经在这么做了。例如：尽管 Codex 是开源的，但它会生成一个加密的压缩摘要（该摘要在 OpenAI 生态系统之外无法使用）。

他们为什么要这么做？因为内存很重要，而且这会产生仅靠模型本身无法获得的锁定效应。

#### 内存很重要，并且它会产生锁定

虽然记忆的概念由来已久，但所有人都清楚它的重要性。它让智能体在用户交互过程中不断优化，也让你能够构建数据飞轮。它还能让你的智能体针对每个用户实现个性化，并构建一种贴合用户需求和使用模式的智能体体验。

💡 没有记忆，你的代理很容易被任何拥有相同工具访问权限的人复制。

借助记忆能力，你可以构建一个专有数据集——一个包含用户交互和偏好的数据集。这个专有数据集使你能够提供差异化且日益智能的体验。

到目前为止，切换模型提供商相对容易。它们的 API 相似，即便不完全相同。当然，你需要稍微修改一下提示词，但这并不难。

但是这一切都是因为它们是无状态的。

一旦有任何关联的状态，切换就会困难得多。因为这种状态很重要。而且如果切换，你就会失去对它的访问权限。

让我讲个故事。我内部有一个电子邮件助手。它是基于一个模板构建的，该模板位于

[Fleet](https://www.langchain.com/langsmith/fleet)，我们用于构建企业级 OpenClaws 的无代码平台。这个平台内置了记忆功能，所以在过去几个月里，当我与我的电子邮件助手交互时，它积累了记忆。几周前，我的代理意外被删除了。我很生气！我尝试用相同的模板创建一个代理，但体验糟糕得多。我不得不重新教它我所有的偏好、我的语气，所有东西。

我邮件代理的加号功能被删除了——这让我意识到记忆可以多么强大且难以磨灭。

#### 打开内存，打开线束

内存需要被打开，归任何正在开发智能体体验的人所有。它允许你构建一个你实际控制的专有数据集。

内存（以及因此的 harnesses）应该与模型提供商分离。你应该希望有选择权，以尝试最适合你使用场景的任何模型。模型提供商有动机通过内存来制造锁定效应。

这就是我们开发

[Deep Agents](https://docs.langchain.com/oss/python/deepagents/overview)。Deep Agents：

- 是开源的
- 是否与模型无关
- 使用开放标准，例如
  [agents.md](http://agents.md/) 和
  [技能](https://agentskills.io/home)
- 有用于 Mongo、Postgres、Redis 以及其他用于存储记忆的插件
- 可部署：(1) 通过
  [LangSmith Deployment](https://docs.langchain.com/langsmith/deployment) (可自托管，可部署到任何云平台，可自带数据库作为内存存储); (2) 在任何标准的 Web 托管框架之后

为了拥有你的记忆，你需要使用一个 Open Harness

试用

[Deep Agents](https://docs.langchain.com/oss/python/deepagents/overview) 今天。

## 通俗精炼（1）

### 2026-04-13 07:08:26

#### 你的框架，决定你是否真正拥有 “记忆”

##### 核心观点

文章的核心结论很明确：

**代理框架不会消失，而 “记忆” 正是框架里最关键、最容易形成锁定的一部分。**  
如果你使用封闭框架，尤其是封装在模型厂商 API 背后的框架，本质上就是把代理的记忆控制权交给第三方。

---

##### 为什么代理框架不会消失

很多人以为，随着大模型变强，框架会越来越不重要。文章认为这并不成立。

###### 本质原因

代理不是 “单纯的模型”，而是：

- 一个 LLM
- 外加工具调用能力
- 外加上下文和状态管理
- 外加与外部数据源交互的机制

也就是说，**只要代理要调用工具、管理任务、连接外部世界，就一定需要框架。**  
过去淘汰的只是旧脚手架，新的脚手架还会不断出现。

---

##### 为什么 “记忆” 不是插件，而是框架能力

文章强调，记忆并不是一个可以随便插拔的独立模块，而是代理框架的核心职责。

###### 记忆依赖框架处理的内容

框架决定了很多关键问题：

- 哪些信息进入上下文
- 短期记忆如何保留和压缩
- 长期记忆如何读写
- 系统提示、技能说明、文件系统信息如何暴露给代理
- 历史交互是否可存储、可检索、可查询

所以，**记忆的本质是 “上下文与状态管理”**，而这正是框架最核心的能力之一。

---

##### 最大风险：记忆被模型厂商 “锁住”

这是文章最重要的警示。

###### 如果用封闭框架，会发生什么

- 你的状态和对话可能存储在厂商服务器上
- 你不知道记忆是怎么生成、压缩、读取的
- 你难以迁移到别的模型或框架
- 你可能根本不拥有完整记忆数据

换句话说：

**如果你不拥有框架，你就不真正拥有记忆。**  
而一旦记忆留在某个平台，切换模型的成本会急剧上升，形成强锁定。

---

##### 为什么记忆这么重要

记忆的重要性，不只是 “体验更顺滑”，而是直接关系到产品壁垒。

###### 记忆带来的价值

- 让代理越来越懂用户
- 支持长期个性化体验
- 沉淀用户偏好与交互数据
- 形成专有数据资产和数据飞轮
- 让产品变得更 “粘”，更难被替代

没有记忆时，别人拿到同样模型和工具，就能快速复制你的产品；  
有了记忆后，**真正难复制的是你积累下来的用户数据和行为偏好。**

---

##### 作者主张：记忆必须开放、可控、可迁移

文章最终倡导的是：

###### 应该坚持的方向

- 使用开放框架，而不是封闭 API 黑盒
- 让记忆独立于模型厂商
- 保持模型可替换性
- 把长期记忆存放在自己可控的数据库和系统中

核心逻辑是：  
**模型可以替换，但记忆应该属于你自己。**

---

##### 对产品经理的启示

从产品视角看，这篇文章其实在讲一件事：

###### 真正的竞争，不只在模型能力，而在 “用户状态的所有权”

未来代理产品的壁垒，可能不只是模型效果，而是：

- 你是否掌握用户长期数据
- 你是否拥有跨会话记忆
- 你是否能持续沉淀个性化资产
- 你是否避免被底层模型平台反向卡住

因此，选框架不只是技术选型，更是**产品控制权和商业主动权**的选择。

---

##### 一句话总结

**谁控制代理框架，谁就控制记忆；谁控制记忆，谁就控制未来代理产品的用户关系与商业壁垒。**

## 结构化（1）

### 2026-04-13 09:58:20

#### 主旨概括

这篇文章的核心观点是：**代理框架不会消失，而且它与 “记忆” 深度绑定**。如果你把代理建立在封闭框架或专有 API 之上，本质上就是把最关键的 “记忆控制权” 交给第三方，这会带来强锁定效应。

#### 1. 代理框架仍会长期存在

- 过去 3 年，构建智能体系统的方式不断变化：从早期的简单**RAG 链（LangChain）**，到更复杂的流程编排**LangGraph**，再到如今的**代理框架**。
- 文中列举的代理框架包括：**Claude Code、深度代理（Deep Agents）、Pi（支持 OpenClaw）、OpenCode、Codex、Letta Code**等。
- 作者强调：**“代理安全带（harness）不会消失。”**
- 原因很简单：代理的定义决定了它不仅仅是模型本身，而是一个会和**工具、外部数据源**交互的 LLM，因此外围一定需要一个系统来协调这些交互。
- 一个重要例子是：**Claude Code 源码泄露时有 512k 行代码**，这说明即使是顶级模型团队，也仍在大量投入框架建设。
- 另一个例子是：像**网络搜索**这样的能力即便被集成进 OpenAI 或 Anthropic 的 API，也**不是模型本身的一部分**，而是 API 背后框架在协调模型与搜索工具。

#### 2. 记忆不是独立插件，而是框架能力的一部分

- 作者认同 Sarah Wooders 的观点：**“记忆不是插件，而是框架。”**
- 有些人以为记忆可以作为一个独立服务，随意接到任何代理上，但作者认为：**在当前阶段，这种理解并不成立**。
- 因为框架最核心的职责之一，就是管理**上下文（context）**；而记忆本质上就是上下文的一种形式。
- 文中用了一个形象比喻：  
  **“要求把记忆接入代理框架，就像要求把驾驶行为接入汽车。”**  
  也就是说，管理上下文和状态，本来就是代理框架的核心能力。
- 文章区分了两类记忆：
  - **短期记忆**：如对话消息、工具调用结果，由框架直接处理；
  - **长期记忆**：跨会话的记忆，需要框架负责读写和更新。
- Sarah 提到，框架和记忆绑定体现在很多细节上，例如：
  - `AGENTS.md`或`CLAUDE.md`如何载入上下文；
  - 技能元数据如何展示给代理；
  - 代理是否可以修改自己的系统指令；
  - 压缩上下文时保留什么、丢弃什么；
  - 交互是否被存储、能否被查询；
  - 记忆元数据如何呈现；
  - 当前工作目录和文件系统信息暴露多少。
- 作者进一步指出：**记忆仍处于非常早期阶段**，行业还没有形成广泛接受的通用抽象，因此目前还很难把记忆真正做成一个 “可插拔” 的独立层。

#### 3. 不拥有框架，就不拥有记忆

- 作者的关键判断是：**如果你不拥有你的 harness（框架），你就不拥有你的 memory（记忆）**。
- 这种问题主要体现在三层：

##### 3.1 轻度问题：状态被存到别人的服务器

- 如果你使用有状态 API，比如：
  - **OpenAI 的 Responses API**
  - **Anthropic 的服务器端压缩**
- 那么状态就是存在对方服务器上的。
- 结果是：如果你未来想**切换模型**，并保留之前的对话和上下文，可能就做不到。

##### 3.2 更严重的问题：封闭框架如何处理记忆，你根本不知道

- 例如文中提到：**Claude Agent SDK**内部使用**Claude Code**，而 Claude Code 是**非开源**的。
- 这样一来，框架可能会在客户端生成一些与记忆相关的工件，但：
  - 这些工件是什么格式，你不知道；
  - 框架如何使用它们，你也不知道；
  - 因此它们也**无法跨框架迁移**。

##### 3.3 最严重的问题：长期记忆完全被封装在 API 背后

- 这是作者最担心的情况。
- 一旦整个框架连同长期记忆都被放到 API 后面：
  - 你不知道记忆如何被使用；
  - 你无法决定哪些记忆可见、哪些不可见；
  - 甚至**你连记忆本身都不真正拥有**。
- 作者认为，当人们说 “模型会吸收越来越多的框架” 时，真正的意思其实就是：  
  **这些与记忆有关的能力，会越来越多地被藏到模型厂商的 API 后面。**
- 这样会导致一个直接后果：  
  **记忆被锁定在单一平台、单一模型里。**

#### 4. 为什么模型厂商强烈想掌握记忆

- 作者认为，模型厂商有非常强的动力把记忆做成平台锁定工具，而且**他们已经开始这么做**。
- 例子包括：
  - **Anthropic 推出 Claude 托管代理**，把更多能力封装在自己的平台上；
  - **Codex 虽然开源，但会生成加密压缩摘要**，这个摘要在**OpenAI 生态之外无法使用**。
- 作者指出：这么做的真正原因不是技术必然，而是商业逻辑 ——  
  **记忆能带来比模型能力本身更强的锁定效应。**

#### 5. 记忆为什么如此重要

- 文章认为，记忆的重要性几乎是行业共识。
- 它的价值主要体现在几个方面：

##### 5.1 让代理持续变 “更懂你”

- 记忆能让代理在与用户长期交互中不断优化表现。
- 比如它能逐步学会用户的：
  - 偏好；
  - 语气；
  - 使用习惯；
  - 工作方式。

##### 5.2 帮你建立专有数据飞轮

- 作者强调：有了记忆，企业就可以积累一个**专有数据集**，里面包含用户交互历史和偏好。
- 这个数据集会反过来提升代理质量，形成**数据飞轮**。
- 这也是产品差异化的来源。

##### 5.3 没有记忆的代理很容易被复制

- 文中一句话很关键：  
  **“没有记忆，你的代理很容易被任何拥有相同工具访问权限的人复制。”**
- 也就是说，如果两个代理用的是同样的模型、同样的工具，但其中一个没有长期记忆，那它几乎没有护城河。

##### 5.4 状态一旦产生，迁移成本就会陡增

- 作者指出，过去切换模型提供商之所以相对容易，是因为它们的 API **基本无状态**。
- 即便提示词要稍作调整，迁移也不难。
- 但一旦代理带有大量状态和记忆，切换就会变得困难得多，因为你可能会**丢失那些已积累的关键上下文**。

#### 6. 一个真实案例：邮件助手被删后，体验显著变差

- 作者分享了自己的亲身经历：
  - 他有一个内部的**邮件助手**；
  - 这个助手基于 Fleet 平台上的模板构建；
  - Fleet 内置了记忆功能，因此几个月下来，这个助手积累了不少关于作者的偏好和风格信息。
- 后来这个代理**意外被删除**了。
- 作者尝试用同一个模板重建一个新的代理，但结果是：
  - 新代理的体验明显更差；
  - 他不得不重新教它自己的偏好、语气和工作习惯。
- 这个例子说明：  
  **记忆一旦形成，价值非常高；一旦丢失，恢复成本也非常高。**
- 这也让作者更加确信：记忆不是可有可无的附属品，而是决定代理 “好不好用、离不开” 的核心能力。

#### 7. 解决方案：开放记忆，开放框架

- 作者的结论很明确：  
  **记忆应该开放，并归开发代理体验的人自己所有。**
- 进一步说：
  - **记忆应该与模型提供商分离**；
  - **harness（框架）也应该开放**；
  - 开发者应该保有自由切换不同模型的权利，而不是被某一家平台绑定。
- 作者认为，模型厂商天然有动力通过记忆制造锁定，因此开发者更应该主动选择开放方案。

#### 8. 作者给出的实践方向：Deep Agents

- 这也是作者开发**Deep Agents**的原因。
- 文中介绍，Deep Agents 具备以下特点：
  - **开源**
  - **与模型无关**
  - 使用开放标准，例如**`agents.md`**和技能（skills）
  - 支持多种记忆存储插件，如**Mongo、Postgres、Redis**
  - 支持部署方式包括：
    - 通过**LangSmith Deployment**部署，可自托管、可部署到任意云平台、可自带数据库作为记忆存储；
    - 部署在任何标准的 Web 托管框架之后
- 作者最终强调：  
  **如果你想真正拥有自己的记忆，就需要使用开放的 harness。**

#### 总结

- 这篇文章的核心不是单纯讨论 “框架是否重要”，而是在强调：**框架决定了记忆如何形成、如何存储、如何迁移，以及最终归谁所有。**
- 作者最担心的是，随着越来越多代理能力被封装进模型厂商 API，**最有价值的长期记忆也会随之被平台锁定**。
- 因此，文章主张开发者应优先选择**开放、可控、模型无关**的代理框架，这样才能真正掌握自己的用户数据、产品体验和长期竞争力。

## 产品-最佳实践（1）

### 2026-04-13 09:59:23

#### 你的框架，你的记忆：一个具体实例与最佳实践

这篇内容的核心观点可以概括为一句话：

> **谁控制代理框架（harness），谁就控制代理记忆；谁控制代理记忆，谁就控制用户体验、迁移能力与长期壁垒。**

下面我用一个具体实例，把这个观点落到实际场景里，并进一步给出一套可执行的最佳实践。

---

##### 一个具体实例：企业邮件助理

假设你要为一家 B2B 公司做一个 “AI 邮件助理”，它需要帮助销售、客服和管理层处理日常邮件。这个助理需要完成以下任务：

- 理解用户写邮件的习惯和语气
- 记住不同客户的背景与偏好
- 在多轮会话中延续上下文
- 调用工具读取 CRM、日历、知识库和历史邮件
- 在多次会话之间保留长期记忆

###### 两种做法

###### 方案 A：使用封闭式代理框架 / 托管式 API
你直接接入某个模型提供商的托管代理 API。它声称支持：

- 会话状态
- 自动摘要压缩
- 长期记忆
- 工具调用
- 托管式执行

短期内你开发很快，体验也不错。但几个月后你发现：

- 你不知道它到底记住了什么、丢弃了什么
- 你无法导出完整记忆结构
- 你很难切换到别的模型提供商
- 同一个用户换平台后，历史偏好和上下文无法继承
- 一旦 API 策略、价格或能力变化，你会被动承受

###### 方案 B：使用开放式 harness，自主管理记忆
你使用一个开放框架搭建邮件助理，并自己定义：

- 短期记忆如何进入上下文
- 长期记忆如何存储、召回、更新
- 工具调用结果如何压缩
- 用户偏好如何建模
- 不同模型之间如何共享记忆层

这样做前期复杂一些，但你真正拥有了：

- 用户画像
- 历史行为数据
- 可迁移的记忆结构
- 可解释的上下文管理机制
- 切换模型和部署方式的自由

---

##### 为什么这个例子能说明问题

邮件助理是 “记忆价值” 最强的代理之一，因为它的体验高度依赖长期累积，而不是一次性的模型回答。

如果这个代理记不住这些内容，体验会明显变差：

- 用户偏好的称呼方式
- 用户常用的邮件语气
- 不同对象的沟通风格
- 哪些信息应该简洁，哪些需要正式展开
- 某类邮件过去如何回复过
- 某个客户或合作伙伴有哪些长期背景

这意味着：

> **邮件助理的真正竞争力，不是 “能写邮件”，而是 “能按你的方式、基于你的历史、在你的业务场景里持续变得更懂你”。**

而这部分能力，本质上就是记忆能力。

---

##### 在这个实例上的最佳实践

##### 1. 把 “记忆层” 当作核心架构，而不是附加插件

很多团队会先把代理跑起来，再想着 “以后再接 memory”。但在邮件助理这种场景里，这种顺序往往会导致后期重构成本极高。

最佳实践是从一开始就定义清楚三层记忆：

###### 短期记忆
用于当前任务上下文，例如：

- 当前邮件线程
- 最近几轮对话
- 最近一次工具调用结果
- 当前待处理草稿

###### 工作记忆
用于当前阶段任务推进，例如：

- 本封邮件的目标
- 用户当前指令
- 当前客户背景摘要
- 本次回复需要遵守的约束

###### 长期记忆
用于跨会话积累，例如：

- 用户的语气偏好
- 用户对不同角色的沟通习惯
- 常见审批或决策模式
- 客户历史偏好与重要关系信息

关键点不是 “有没有 memory API”，而是：

> **你的框架是否允许你定义、观察、修改和迁移这些记忆。**

---

##### 2. 让记忆结构显式化，而不是藏在黑箱中

在邮件助理里，最糟糕的做法是把所有 “记忆” 都交给模型提供商的隐式会话状态。

更好的做法是把长期记忆拆成明确的数据对象，例如：

```json
{
  "user_id": "u_123",
  "memory_type": "writing_preference",
  "content": {
    "tone": "professional_warm",
    "prefers_bullets": true,
    "avoids_overpromising": true
  },
  "source": "observed_from_edits",
  "confidence": 0.87,
  "updated_at": "2025-02-10T10:20:00Z"
}
```

这样做的好处是：

- 可审核
- 可迁移
- 可纠正
- 可分层检索
- 可做权限控制

也就是说，记忆不再只是 “模型好像知道了什么”，而是变成 “系统明确保存了什么”。

---

##### 3. 将 “用户偏好” 与 “任务上下文” 分开存储

这是非常重要但常被忽略的一点。

在邮件助理中，以下两类信息不能混在一起：

###### 用户偏好
相对稳定，例如：

- 喜欢简洁风格
- 面向客户时更正式
- 不喜欢感叹号
- 偏好英文邮件以美式表达为主

###### 任务上下文
短期有效，例如：

- 这封邮件是关于合同续签
- 当前客户对价格敏感
- 今天需要在下午 3 点前发出
- 此次回复要避免提及内部审批问题

如果把它们混在同一个 “总结” 里，就会出现两个问题：

- 长期记忆被短期噪音污染
- 检索时召回了大量无关信息

最佳实践是：

> **长期记忆存稳定偏好，短期上下文存当前任务状态，中间通过显式策略连接。**

---

##### 4. 对记忆写入设置 “门槛”，不要把所有交互都写进长期记忆

不是所有信息都值得永久记住。

以邮件助理为例，下面这类内容适合写入长期记忆：

- 用户连续多次手动把邮件语气改得更正式
- 用户反复强调 “报价邮件不要太激进”
- 用户在多个会话中都偏好以三点式结构回复
- 某个客户明确要求用特定称呼或流程沟通

而下面这些通常不应直接写入长期记忆：

- 一次性的临时情绪
- 某个当天才有效的任务要求
- 不稳定、低置信度的推断
- 工具调用中的冗余原始输出

可以采用一个简单规则：

> **只有 “高频出现 + 可泛化 + 对未来有价值” 的信息，才值得进入长期记忆。**

这能显著减少记忆污染。

---

##### 5. 为记忆设计 “可更正” 和 “可遗忘” 机制

记忆如果只能累积、不能修正，最终会成为负担。

在邮件助理里，用户可能会说：

- 以后给客户写邮件别那么正式
- 我现在负责新的区域，优先使用新的签名
- 不要再默认我喜欢短邮件
- 某个客户已经换联系人了

所以最佳实践不是只做 “memory write”，而是同时支持：

- 更新记忆
- 软删除记忆
- 设置记忆有效期
- 标注记忆来源和置信度
- 保留变更历史

这意味着记忆系统更像一个 “可维护知识层”，而不是一个只会堆积的日志桶。

---

##### 6. 让记忆独立于模型提供商存在

这是原文最关键的战略建议。

邮件助理如果跑在单一模型提供商的封闭 API 后面，会发生什么？

- 你的用户偏好、语气模式、客户习惯都被绑定在该平台
- 切换模型时，体验重置
- 平台涨价、限流、改策略，你很被动
- 你难以做跨模型 A/B 测试

最佳实践是：

- 记忆存储在你自己的数据库中，如 Postgres、MongoDB、Redis 等
- 记忆检索与写入逻辑由你控制
- 模型只是 “推理引擎”，不是 “记忆拥有者”
- 任何模型接入时，读取的是同一套记忆层

一句话：

> **模型可以替换，记忆不能丢。**

---

##### 7. 让上下文构造过程可观察、可调试

代理框架真正决定记忆效果的地方，不只是 “存了什么”，而是 “调用模型前，把什么放进上下文”。

在邮件助理中，一次生成回复前，系统可能会拼接：

- 系统指令
- 用户当前请求
- 当前邮件线程摘要
- 用户长期写作偏好
- 客户关系记忆
- 最近一次 CRM 查询结果
- 与当前任务有关的组织规则

最佳实践是保留一份 “上下文装配日志”，至少包括：

- 本轮注入了哪些记忆
- 每条记忆来自哪里
- 为什么被召回
- 哪些信息被压缩或丢弃
- 最终上下文长度是多少

这样你才能真正排查：

- 为什么回复突然变得不对劲
- 为什么某段偏好没有生效
- 为什么某些无关信息总被召回

如果这些过程都隐藏在封闭系统里，你实际上无法优化体验。

---

##### 8. 用开放标准描述代理行为和技能边界

原文提到像`agents.md`、技能等开放标准，这个方向非常重要。

在邮件助理里，可以把下面内容做成明确的、可迁移的规范：

- 代理角色定义
- 可调用工具及其权限
- 用户偏好字段
- 长期记忆 schema
- 记忆更新规则
- 压缩与摘要策略

这样做的价值在于：

- 方便迁移到新模型
- 方便团队协作
- 方便测试和审计
- 避免行为逻辑被某个 SDK 私有格式锁死

---

##### 9. 记忆系统要服务 “体验闭环”，而不是只服务 “存储”

很多团队会把 memory 理解成 “多存一点用户数据”，但真正重要的是闭环：

1. 观察用户行为  
2. 提炼稳定偏好  
3. 存成可检索记忆  
4. 在未来任务中正确召回  
5. 让用户感知到 “它更懂我了”  
6. 用户继续使用并产生更多高价值数据  

在邮件助理这个例子里，闭环成功的标志不是数据库记录变多，而是：

- 用户修改草稿的次数减少
- 首次生成的可用率提高
- 用户对邮件风格的满意度提升
- 同一用户跨会话的一致性增强

所以最佳实践是把记忆效果绑定到体验指标，而不是绑定到 “memory 命中次数”。

---

##### 10. 从 Day 1 就考虑 “迁移演练”

如果你真的认同 “你的框架，你的记忆”，就不能只在理念上开放，还要在工程上可迁移。

对于邮件助理，建议定期做这样的演练：

- 将同一份记忆层切换到另一个模型
- 验证历史偏好是否还能生效
- 验证上下文拼接逻辑是否可复用
- 验证工具调用协议是否仍兼容
- 验证导出和回灌是否完整

这是一种非常现实的最佳实践，因为很多锁定不是在签约时发生的，而是在你积累了 6 个月关键用户记忆之后才真正发生。

---

##### 一个推荐的落地架构

对于这个 “企业邮件助理” 实例，一个相对稳妥的开放式方案可以是：

###### 框架层
- 使用开放 agent harness
- 代理编排逻辑由自己控制
- 工具调用流程透明可观察

###### 记忆层
- `Postgres`存结构化长期记忆
- `Redis`存短期状态和会话缓存
- 向量库只作为召回辅助手段，而不是唯一记忆形态

###### 模型层
- 可插拔接入多个模型提供商
- 模型只负责推理，不托管核心记忆

###### 观测层
- 记录上下文装配日志
- 记录记忆写入原因
- 记录召回效果与用户修订反馈

###### 治理层
- 支持用户纠正记忆
- 支持记忆删除与过期
- 支持多租户权限隔离
- 支持敏感数据审计

---

##### 最终结论

这篇文章最有价值的提醒，不是 “封闭框架不好”，而是：

> **在代理时代，记忆不是附属能力，而是产品核心；而记忆一旦被框架绑定，框架就不再只是开发工具，而是业务控制权。**

用邮件助理这个例子来看，真正决定长期价值的不是 “能不能自动写邮件”，而是：

- 能不能持续记住用户
- 能不能跨模型继承这种记住
- 能不能由你自己控制这种记住

所以，基于本文内容，可以提炼出一个最重要的最佳实践原则：

> **把记忆当成你自己的产品资产来设计，而不是当成模型平台顺便提供的一项功能。**

---

##### 可直接采用的实践清单

- 优先选择开放、可自托管、可审计的 agent harness
- 将长期记忆存放在自有数据库，而不是完全依赖托管 API 状态
- 区分短期记忆、工作记忆、长期记忆
- 为长期记忆定义明确 schema、来源、置信度与更新时间
- 只把高价值、可泛化、跨会话有用的信息写入长期记忆
- 让记忆支持更新、撤销、过期与审计
- 记录每轮上下文拼接与记忆召回过程
- 保持模型层可替换，避免记忆与单一模型绑定
- 用开放标准描述代理规则、技能和记忆接口
- 定期做跨模型迁移演练，验证 “记忆 ownership” 是否真实成立
