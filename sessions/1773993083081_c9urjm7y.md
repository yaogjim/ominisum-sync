## 分析要点

- **核心高价值点**：最有价值的观点是把提示词缓存视为系统级约束来设计代理架构，而不是把它当成单点优化技巧。
- **留存建议**：长期保留（内容来自一线产品实践，包含提示词缓存、工具设计、技能体系等可直接复用的智能体工程经验，适合作为构建代码代理的参考资料。）

**知识要点**

- 提示词缓存本质是前缀匹配，静态内容必须尽量前置，动态内容后置。
- 会话中切换模型、增删工具、修改系统提示都会显著破坏缓存命中率。
- 计划模式、工具搜索、上下文压缩都应设计成缓存安全的状态转换机制。
- 工具设计应从模型真实能力出发，通过观察输出和实验不断迭代。
- 技能不是单一 Markdown，而是可包含脚本、配置、资源与数据存储的工作目录。
- 渐进式披露和子代理是扩展能力而不污染主上下文的有效方式。

**行动项**

- 审查现有智能体请求结构，按静态系统提示、项目上下文、会话上下文、动态消息重新排序以提高缓存命中率。
- 避免在对话中途切换模型或增删工具，改用子代理和工具化状态转换。
- 为技能体系建立分类清单，优先补齐验证、数据分析、代码评审和操作手册类技能。
- 给技能增加 gotchas、配置文件、脚本与稳定数据目录，减少模型重复犯错。
- 把缓存命中率和技能触发率纳入监控，像监控可用性一样持续追踪。

### 构建 Claude Code 的经验：提示词缓存就是一切

工程领域中常有人说“缓存主宰我周围的一切”，同样的规则也适用于代理。

长期运行的智能代理产品（如 Claude Code）的实现得益于提示词缓存，这使得我们能够重用之前往返中的计算，并显著降低延迟和成本。

什么是提示词缓存，它是如何工作的，以及技术上如何实现？

[阅读更多@RLanceMartin 关于提示词缓存以及我们新的自动缓存功能发布的文章](https://x.com/RLanceMartin/status/2024573404888911886)

在 Claude Code，我们围绕提示词缓存构建整个系统。高提示词缓存命中率可降低成本，并帮助我们为订阅计划设置更宽松的速率限制，因此我们会监控提示词缓存命中率，若其过低则宣布 SEV。

这些是（往往不直观的）我们在大规模优化提示词缓存过程中获得的经验教训。

#### 设置用于缓存的提示

![Image](https://pbs.twimg.com/media/HBipHa1boAAXD_A?format=jpg&name=large)

提示缓存通过前缀匹配实现——API 会缓存从请求开始到每个 cache\_control 断点为止的所有内容。这意味着你放置内容的顺序极为重要，你希望尽可能多的请求共享一个前缀。

完成此操作的最佳方式是先处理静态内容，最后处理动态内容。对于 Claude Code，这表现为：

1. 静态系统提示词 &amp; 工具（全局缓存）
2. Claude.MD（在项目中缓存）
3. 会话上下文 （在会话中缓存）
4. 对话消息

这样我们最大化了共享缓存命中的会话数量。

但这可能会出人意料地脆弱！我们之前破坏这种顺序的原因包括：在静态系统提示中放入详细的时间戳、非确定性地打乱工具顺序定义、更新工具的参数（例如 AgentTool 可以调用的代理）等。

#### 使用消息接收更新

有时，你输入提示中的信息可能会过时，例如当你有时间或者用户修改了文件时。更新提示可能会很诱人，但这会导致缓存未命中，并且可能最终对用户来说成本很高。

考虑一下下次是否可以通过消息传递这些信息。在 Claude Code 中，我们会在下一次用户消息或工具结果中添加 &lt;system-reminder&gt; 标签，包含模型的更新信息（例如现在是星期三），这有助于保留缓存。

#### 不要在会话中途更改模型

提示缓存是模型独有的，这可能会使提示缓存的计算相当难以理解。

如果你已经与 Opus 进行了 10 万个 token 的对话，并且想要提出一个比较容易回答的问题，实际上切换到 Haiku 会比让 Opus 回答更昂贵，因为我们需要为 Haiku 重建提示词缓存。

如果需要切换模型，最好的方法是使用子代理，其中 Opus 会准备一条“交接”消息给另一个需要执行该任务的模型。我们经常在使用 Haiku 的 Claude Code 中的探索代理中这样做。

#### 切勿在会话期间添加或移除工具

在对话过程中更改工具集是人们破坏提示词缓存的最常见方式之一。这似乎很直观——你应该只给模型你认为它现在需要的工具。但由于工具是缓存前缀的一部分，添加或移除工具会使整个对话的缓存失效。

规划模式 — 围绕缓存设计

计划模式是围绕缓存限制设计功能的一个很好的例子。直观的方法应该是：当用户进入计划模式时，替换掉工具集，只保留只读工具。但这会破坏缓存。

相反，我们始终保留所有工具在请求中，并将 EnterPlanMode 和 ExitPlanMode 本身用作工具。当用户开启计划模式时，代理会收到一条系统消息，说明它处于计划模式以及指令内容——探索代码库，不要编辑文件，计划完成后调用 ExitPlanMode。工具定义永远不会改变。

这有一个额外的好处：因为 EnterPlanMode 是模型可以自我调用的工具，当它检测到难题时，能够自主进入规划模式，不会造成任何缓存中断。

工具搜索 — 推迟而非移除

同样的原则适用于我们的工具搜索功能。Claude Code 可以加载数十个 MCP 工具，在每个请求中包含所有这些工具的成本会很高。但在对话过程中移除它们会破坏缓存。

我们的解决方案：defer\_loading。而不是移除工具，我们发送轻量级存根——仅包含工具名称，并附带 defer\_loading: true——，模型可以通过 ToolSearch 工具在需要时"发现"这些存根。完整的工具架构仅在模型选择它们时才会被加载。

幸运的是，您可以使用

[tool search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool) 工具通过我们的 API 来简化这一过程。

#### 分支上下文 — 压缩

![Image](https://pbs.twimg.com/media/HBitEdRbUAMVSnM?format=jpg&name=large)

压缩是当你耗尽上下文窗口时发生的情况。我们总结到目前为止的对话，并基于该总结继续一个新的会话。

令人惊讶的是，压缩在提示缓存方面存在许多边缘情况，这些情况可能不直观。

特别是，当我们进行压缩时，需要将整个对话发送给模型以生成摘要。如果这是一个带有不同系统提示且没有工具的单独 API 调用（即简单实现的情况），主对话中的缓存前缀会完全不匹配。你需要为所有这些输入 token 支付全额费用，这会大幅增加用户的成本。

解决方案 — 缓存安全分叉

当我们执行压缩时，我们使用的是完全相同的系统提示、用户上下文、系统上下文以及工具定义，与父对话完全相同。我们在开头添加父对话的消息，然后在末尾追加压缩提示作为新的用户消息。

从 API 的角度来看，这个请求看起来与父请求的上一次请求几乎相同——相同的前缀、相同的工具、相同的历史，因此重用了缓存的前缀。唯一的新标记是压缩提示本身。

不过这确实意味着我们需要预留一个“compaction buffer”，以便我们在上下文窗口中有足够的空间来包含紧凑消息和摘要输出 token。

压缩很棘手，但幸运的是，你不需要自己学习这些知识——基于我们从 Claude Code 获得的经验，我们构建了

[压缩](https://platform.claude.com/docs/en/build-with-claude/compaction#prompt-caching)直接集成到 API 中，以便你能在自己的应用中应用这些模式。

#### 经验教训

1. 提示缓存是一种前缀匹配。前缀中的任何位置发生的更改都会使之后的所有内容失效。围绕这个约束设计整个系统。正确处理顺序，大部分缓存工作都会自动有效。
2. 使用消息而非修改系统提示。你可能会想要编辑系统提示来完成诸如进入计划模式、更改日期等操作，但实际上，在对话过程中将这些内容插入消息中会更好。
3. 不要在对话过程中更换工具或模型。 使用工具来建模状态转换（如计划模式），而不是更换工具集。延迟工具加载而非移除工具。
4. 监控你的缓存命中率，就像监控运行时间一样。 我们会对缓存中断发出警报，并将它们视为事件。几个百分点的缓存未命中率可能会显著影响成本和延迟。
5. 分叉操作需要共享父进程的前缀。 如果需要运行辅助计算（压缩、汇总、技能执行），请使用相同的缓存安全参数，以便在父进程的前缀上命中缓存。

Claude Code 从一开始就以提示词缓存为核心构建，如果你正在构建代理，你也应该这样做。

### 构建 Claude 代码的经验：像智能体一样观察

构建 agent 框架最困难的部分之一是构造其动作空间。

Claude acts through Tool Calling, but there are a number of ways tools can be constructed in the Claude API with primitives like bash, skills and recently code execution (read more about programmatic tool calling on the Claude API in

[@RLanceMartin's new article](https://x.com/RLanceMartin/status/2027450018513490419)).

考虑到所有这些选项，你如何设计你的代理的工具？你只需要一个工具，比如代码执行或 Bash 吗？如果你有 50 个工具，每个工具对应代理可能遇到的一个用例，那会怎样？

为了设身处地想象自己是这个模型，我喜欢想象自己被给予一道数学难题。为了解决它，你会需要什么工具？这取决于你自己的技能！

最基础的选择是使用纸张，但你会受到手动计算的限制。计算器会更好，但你需要知道如何操作更高级的功能。最快且最强大的选择是使用计算机，但你必须知道如何用它来编写和执行代码。

这是一个设计智能体的有用框架。你希望给它一些根据自身能力定制的工具。但你如何知道这些能力是什么呢？你需要关注、查看它的输出并进行实验。你学会像智能体一样思考。

以下是我们在开发 Claude Code 时关注 Claude 所学到的一些经验教训。

### 改进信息提取与 AskUserQuestion 工具

![Image](https://pbs.twimg.com/media/HCLxg2JbsAA3Ag_?format=jpg&name=large)

开发 AskUserQuestion 工具时，我们的目标是提升 Claude 提问的能力（通常称为引导式提问）。

虽然 Claude 可以直接用纯文本提问，但我们发现回答这些问题似乎花费了过多不必要的时间。我们该如何降低这种沟通摩擦，提高用户与 Claude 之间的沟通带宽？

#### 尝试 #1 - 编辑 ExitPlanTool

我们首先尝试的是在 ExitPlanTool 中添加一个参数，以便与计划一同包含一组问题数组。这是最容易实现的，但这让 Claude 感到困惑，因为我们同时请求了一个计划和一组关于该计划的问题。如果用户的回答与计划中所述的内容冲突怎么办？Claude 是否需要调用 ExitPlanTool 两次？我们需要另一种方法。

(you can read more about why we made an ExitPlanTool in

[our post on prompt caching](https://x.com/trq212/status/2024574133011673516))

#### 尝试 #2 - 更改输出格式

接下来我们尝试修改 Claude 的输出指令，以提供一种略有修改的 Markdown 格式，使其能够用来提问。例如，我们可以要求它输出一个项目符号形式的问题列表，其中备选答案用方括号括起。然后我们可以解析并格式化该问题，作为用户界面呈现给用户。

尽管这是我们能做的最通用的改动，Claude 甚至似乎能够胜任输出这个内容，但这无法保证。Claude 会添加额外的句子、省略选项，或者完全使用不同的格式。

#### 尝试 #3 - AskUserQuestion 工具

![Image](https://pbs.twimg.com/media/HCL0gcObkAA4tKt?format=jpg&name=large)

最后，我们决定创建一个 Claude 随时可以调用的工具，但特别在规划模式下会被提示这样做。当工具被触发时，我们会显示一个模态框来显示问题，并阻止代理的循环直到用户回答。

这个工具让我们能够提示 Claude 生成结构化输出，并且帮助我们确保 Claude 为用户提供了多种选择。它还为用户提供了实现该功能的方法，例如在 Agent SDK 中调用它，或者在技能中引用它。

最重要的是，Claude 似乎喜欢调用这个工具，我们发现它的输出结果效果很好。即使是设计最精良的工具，如果 Claude 不理解如何调用它，也无法正常工作。

这是 Claude Code 中提示方式的最终形式吗？我们不确定。如你在下一个示例中所见，适用于一个模型的方法可能并不适用于另一个模型。

### 更新功能 - 任务 &amp; 待办事项

![Image](https://pbs.twimg.com/media/HCLxrfXbEAUXwRV?format=jpg&name=large)

当我们首次推出 Claude Code 时，我们意识到该模型需要一个待办事项列表来保持其按计划推进。待办事项可以在开始时记录，并在模型执行工作时标记为已完成。为实现这一点，我们为 Claude 配备了 TodoWrite 工具，该工具可以编写或更新待办事项并向用户展示。

但即便如此，我们经常看到 Claude 忘记它该做什么。为了适应，我们每 5 轮插入一次系统提醒，这些提醒会提醒 Claude 它的目标。

随着模型的改进，它们不仅不再需要被提醒待办事项列表，反而会觉得它有局限性。收到待办事项列表的提醒让 Claude 觉得它必须严格遵循这个列表，而不是修改它。我们还看到 Opus 4.5 在使用子代理方面也有了很大进步，但子代理如何在共享的待办事项列表上进行协调呢？

Seeing this, we replaced TodoWrite with the Task Tool (

[read more on Tasks here](https://x.com/trq212/status/2014480496013803643)). Whereas Todos were about keeping the model on track, Tasks were more about helping agents communicate with each other. Tasks could include dependencies, share updates across subagents and the model could alter and delete them.

随着模型能力的提升，你们的模型曾经需要的工具现在可能会限制它们。重要的是要不断重新审视关于需要哪些工具的先前假设。这也是为什么坚持使用一小部分具有相当相似能力特征的模型来支持是有用的。

### 设计搜索界面

对于 Claude 来说，特别重要的一组工具是可以用来构建其自身上下文的搜索工具。

当 Claude 首次推出时，我们使用 RAG 向量数据库为 Claude 查找上下文。虽然 RAG 功能强大且速度快，但它需要索引和设置，并且在多种不同环境中可能会很脆弱。更重要的是，Claude 被给予了这个上下文，而不是自己查找上下文。

但是如果 Claude 能在网上搜索，为什么不能搜索你的代码库呢？通过给 Claude 一个 Grep 工具，我们可以让它搜索文件并自行构建上下文。

这是我们观察到的一种模式：随着 Claude 变得更聪明，如果它得到合适的工具，它在构建上下文方面会变得越来越擅长。

当我们引入代理技能时，我们将渐进式披露的理念正式化，这使代理能够通过探索逐步发现相关上下文。

Claude 可以读取技能文件，而这些文件又可以引用模型递归读取的其他文件。事实上，技能的一个常见用途是为 Claude 添加更多搜索能力，比如给它提供如何使用 API 或查询数据库的指令。

在过去的一年中，Claude 从不太能够构建自己的上下文，转变为能够在几层文件中进行嵌套搜索，以找到所需的精确上下文。

渐进式展示现在是我们常用的一种无需添加工具即可添加新功能的技术。

### 渐进式披露 - Claude 代码指南代理

Claude Code 目前拥有大约 20 个工具，并且我们不断地问自己是否需要所有这些工具。添加新工具的门槛很高，因为这会给模型多一个需要考虑的选项。

例如，我们注意到 Claude 对如何使用 Claude Code 了解不足。如果你问它如何添加一个 MCP 或者斜杠命令是什么，它将无法回复。

我们本可以将所有这些信息都放在系统提示中，但考虑到用户很少询问这些内容，这会增加上下文衰减并干扰 Claude Code 的主要工作：编写代码。

相反，我们尝试了一种渐进式展示的方式。我们给 Claude 提供了一个文档链接，它可以加载该链接以搜索更多信息。这种方法有效，但我们发现，Claude 为了找到正确答案，会加载大量结果到上下文中，而实际上你只需要答案本身。

因此，我们构建了 Claude Code Guide 子代理，当你询问关于它自己的问题时，Claude 会被提示调用这个子代理。这个子代理有关于如何有效搜索文档以及返回什么内容的详细指令。

虽然这并非完美，但当你询问 Claude 如何进行自我设置时，它仍然可能会困惑，不过它已经比以前好多了！我们能够在不添加新工具的情况下，向 Claude 的操作空间中添加内容。

#### 一门艺术，而非一门科学

如果你期望得到一套关于如何构建你的工具的严格规则，很遗憾，本指南并非如此。为你的模型设计工具既是一门科学，也是一门艺术。这在很大程度上取决于你使用的模型、智能体的目标以及它所处的环境。

### 构建 Claude 代码的经验：我们如何运用技能

技能已成为 Claude Code 中最常用的扩展点之一。它们灵活、易于制作且易于分发。

但这种灵活性也使得难以确定什么最有效。值得培养什么样的技能？打造一个好技能的秘诀是什么？什么时候与他人分享这些技能？

我们在 Anthropic 公司广泛使用 Claude Code 中的技能，其中数百个技能正处于活跃使用状态。这些是我们学到的关于如何利用技能加速开发的经验教训。

#### 什么是技能？

If you’re new to skills, I’d recommend

[reading our docs](https://code.claude.com/docs/en/skills) or watching our newest course on

[new Skilljar on Agent Skills](https://anthropic.skilljar.com/introduction-to-agent-skills)

, this post will assume you already have some familiarity with skills.

我们常听到关于技能的一个常见误解是，它们“只是 Markdown 文件”，但技能最有趣的部分在于，它们不仅仅是文本文件。它们是文件夹，可以包含脚本、资源、数据等，代理可以发现、探索和操作这些内容。

In Claude Code, skills also have a

[wide variety of configuration options](https://code.claude.com/docs/en/skills#frontmatter-reference) including registering dynamic hooks.

我们发现，Claude Code 中一些最有趣的技能会创造性地使用这些配置选项和文件夹结构。

### 技能类型

在整理完我们所有的技能后，我们注意到它们聚集到了几个常见的类别中。最优秀的技能能清晰地归入某一类；而那些较难归类的技能则横跨多个类别。这不是一份权威清单，但它是一种很好的思考方式，能帮助你判断你的组织是否缺少某些技能。

![Image](https://pbs.twimg.com/media/HDlvMmubEAIzF-N?format=jpg&name=large)

#### 库和 API 参考

解释如何正确使用库、CLI 或 SDK 的技能。这些可以是针对内部库或 Claude Code 有时难以处理的通用库。这些技能通常包括一个参考代码片段文件夹，以及一份 Claude 在编写脚本时应避免的注意事项列表。

示例：

- billing-lib — 你内部的账单库：边缘情况、潜在陷阱等等。
- internal-platform-cli — 内部 CLI 包装器的每个子命令及其使用场景示例
- 前端设计——让 Claude 在你的设计系统中表现更好

#### 2\. 产品验证

描述如何测试或验证代码是否正常工作的技能。这些技能通常与 playwright、tmux 等外部工具配合使用，以进行验证。

验证技能对于确保 Claude 的输出正确非常有用。让工程师花一周时间来使你的验证技能变得出色是值得的。

考虑诸如让 Claude 录制其输出的视频以便你能确切看到它测试了什么，或者在每个步骤中对状态执行程序化断言等技术。这些通常通过在技能中包含各种脚本来实现。

示例：

- signup-flow-driver — 在无头浏览器中执行注册→邮箱验证→新用户引导流程，带有用于在每个步骤中断言状态的钩子
- checkout-verifier — 使用 Stripe 测试卡驱动结账界面，验证发票实际处于正确状态
- tmux-cli-driver — 用于需要 TTY 的交互式命令行界面测试

#### 3\. 数据获取与分析

与你的数据和监控栈相关的技能。这些技能可能包括用于带凭证获取数据的库、特定的仪表盘 ID 等，以及关于常见工作流或获取数据方法的说明。

示例：

- 漏斗查询 — 我需要参与哪些事件才能看到注册→激活→付费的流程，加上实际包含规范用户 ID 的表
- 队列对比 — 比较两个队列的留存率或转化率，标记具有统计显著性的差异，关联到细分定义
- Grafana — 数据源 UID、集群名称、问题 → 仪表盘查找表

#### 4\. 业务流程与团队自动化

能够将重复工作流程自动转化为单个命令的技能。这些技能通常是相当简单的指令，但可能对其他技能或 MCPs 有更复杂的依赖关系。对于这些技能，将之前的结果保存到日志文件中可以帮助模型保持一致性，并反思工作流程的先前执行情况。

示例：

- standup-post — 聚合你的工单跟踪器、GitHub 活动和之前的 Slack → 格式化的站会，仅增量
- create-&lt;ticket-system&gt;-ticket — 强制验证模式（有效的枚举值、必填字段）以及创建后工作流（通知审核人、在 Slack 中关联）
- 每周总结 — 合并 PR + 关闭工单 + 部署 → 格式化总结帖子

#### 5\. 代码脚手架与模板

生成特定功能框架样板的技能。你可以将这些技能与可组合的脚本结合使用。当你的脚手架有仅靠代码无法完全覆盖的自然语言需求时，这些技能尤其有用。

示例：

- new-&lt;框架&gt;-工作流 — 利用你的注释搭建新的服务/工作流/处理程序
- new-migration — 你的迁移文件模板加上常见陷阱
- create-app — 新的内部应用，其身份验证、日志记录和部署配置已预先配置

#### 6\. 代码质量与评审

组织内部确保代码质量并帮助进行代码审查的技能。这些技能可能包括确定性脚本或工具，以实现最大的健壮性。您可能希望将这些技能作为钩子的一部分或在 GitHub Action 中自动运行。

- 对抗性审查——生成一个全新视角子代理进行批评，实施修复，迭代直到发现的问题降级为吹毛求疵的细节
- 代码风格 — 强制执行代码风格，尤其是 Claude 默认情况下做得不好的风格。
- 测试实践 — 关于如何编写测试及测试什么的说明。

#### 7\. CI/CD &amp; 部署

帮助你在代码库内部获取、推送和部署代码的技能。这些技能可能会引用其他技能来收集数据。

示例：

- babysit-pr — 监控 PR → 重试不稳定的 CI → 解决合并冲突 → 启用自动合并
- 部署-&lt;服务&gt; → 构建 → 冒烟测试 → 逐步流量发布并进行错误率比较 → 回归时自动回滚
- cherry-pick-prod — 隔离的工作树 → cherry-pick → 冲突解决 → 带模板的拉取请求

#### 8\. 操作手册

能够处理一个症状（例如 Slack 讨论线程、告警或错误签名），进行多工具调查并生成结构化报告的技能。

示例：

- &lt;service&gt;-debugging — 映射症状 → 工具 → 查询模式 用于您的高流量服务
- oncall-runner — 获取告警 → 检查常见问题 → 格式化发现结果
- 日志关联器——给定请求 ID，从所有可能涉及该请求的系统中拉取匹配的日志

#### 9\. 基础设施运维

执行日常维护和操作流程的技能——其中一些涉及破坏性操作，这些操作得益于防护措施。这些技能让工程师更容易在关键操作中遵循最佳实践。

示例：

- &lt;资源&gt;-orphans — 查找孤儿 Pod/卷 → 发送到 Slack → 浸泡期 → 用户确认 → 级联清理
- 依赖管理 — 您的组织的依赖审批流程
- 成本调查 — '为什么我们的存储/流出费用突然激增' 针对特定的存储桶和查询模式

### 技能提升小贴士

![Image](https://pbs.twimg.com/media/HDoKg58bEAAL1bw?format=jpg&name=large)

一旦你决定了要掌握的技能，该如何撰写它？这些是我们发现的一些最佳实践、技巧和窍门。

We also recently released

[Skill Creator](https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills) to make it easier to create skills in Claude Code.

#### 不要说显而易见的话

Claude Code 对你的代码库非常了解，Claude 也对编程非常了解，包括许多默认观点。如果你要展示一项主要关于知识的技能，尽量聚焦于能让 Claude 跳出常规思维方式的信息。

The

[frontend design skill](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md) is a great example — it was built by one of the engineers at Anthropic by iterating with customers on improving Claude’s design taste, avoiding classic patterns like the Inter font and purple gradients.

#### 构建一个注意事项部分

![Image](https://pbs.twimg.com/media/HDlwEG1bEAUdmcV?format=jpg&name=large)

任何技能中最重要的内容是易错点部分。这些部分应该基于 Claude 在使用你的技能时遇到的常见失败点来构建。理想情况下，你应该随着时间更新你的技能以涵盖这些易错点。

#### 使用文件系统和渐进式展示

![Image](https://pbs.twimg.com/media/HDlwhSjbEAIJSc9?format=jpg&name=large)

就像我们之前说的，技能是一个文件夹，而不仅仅是一个 Markdown 文件。你应该将整个文件系统视为一种上下文工程和渐进式披露的形式。告诉 Claude 你技能中的文件有哪些，它会在适当的时候读取这些文件。

渐进式披露最简单的形式是指向其他 Markdown 文件供 Claude 使用。例如，你可以将详细的函数签名和使用示例拆分为 references/api.md。

另一个例子：如果你的最终输出是一个 markdown 文件，你可能会在 assets/中包含一个用于它的模板文件，供复制和使用。

你可以创建包含参考资料、脚本、示例等的文件夹，这些文件夹能帮助 Claude 更高效地工作。

#### 避免强行推动 Claude

Claude 通常会尽量遵循你的指令，但由于技能具有很强的可重复使用性，你需要注意在指令中不要过于具体。给 Claude 提供它需要的信息，同时要给予它适应具体情况的灵活性。例如：

![Image](https://pbs.twimg.com/media/HDlw1mYbEAY-Bul?format=jpg&name=large)

某些技能可能需要根据用户提供的上下文进行设置。例如，如果你正在开发一个将你的每日站会内容发布到 Slack 的技能，你可能希望 Claude 询问应该发布到哪个 Slack 频道。

#### 描述字段用于模型

当 Claude Code 启动会话时，它会构建一个包含每个可用技能及其描述的列表。Claude 会扫描这个列表以判断“是否有适用于该请求的技能”。这意味着描述字段不是摘要——而是描述何时触发此 PR。

#### 内存与数据存储

![Image](https://pbs.twimg.com/media/HDoImh1bEAU-mMI?format=jpg&name=large)

一些技能可以通过在其中存储数据来包含一种记忆形式。你可以将数据存储在任何东西中，从像仅追加文本日志文件或 JSON 文件这样简单的存储方式，到像 SQLite 数据库这样复杂的存储方式。

例如，一个 standup-post 技能可能会维护一个 standups.log 文件，记录它所写的每一篇帖子，这意味着下次运行时，Claude 会读取自己的历史记录，并能判断自昨天以来有哪些内容发生了变化。

Data stored in the skill directory may be deleted when you upgrade the skill, so you should store this in a stable folder, as of today we provide \`${CLAUDE\_PLUGIN\_DATA}\` as a stable folder per plugin to store data in.

你能给 Claude 的最强大工具之一就是代码。给 Claude 提供脚本和库，能让 Claude 在每个回合专注于组合工作，决定下一步做什么，而不是重复编写模板代码。

例如，在你的数据科学技能中，你可能拥有一个用于从事件源获取数据的函数库。为了让 Claude 进行复杂分析，你可以给它一组辅助函数，像这样：

![Image](https://pbs.twimg.com/media/HDlxbtkbkAAOse7?format=jpg&name=large)

然后 Claude 可以实时生成脚本来组合此功能，以对诸如“周二发生了什么？”这样的提示进行更高级的分析

![Image](https://pbs.twimg.com/media/HDlxfEIb0AA2E7l?format=jpg&name=large)

#### 按需钩子

技能可以包含仅在调用该技能时激活，并持续到会话结束的钩子。对于那些不想一直运行但有时又非常有用的更具倾向性的钩子，可以使用这种方式。

例如：

- /careful — blocks rm -rf, DROP TABLE, force-push, kubectl delete via PreToolUse matcher on Bash. You only want this when you know you're touching prod — having it always on would drive you insane
- /freeze — blocks any Edit/Write that's not in a specific directory. Useful
- 调试时："我想要添加日志，但我总是不小心地‘修复’无关的"

### 分配技能

技能的最大好处之一是你可以与团队中的其他成员分享它们。

有两种方式你可能会与他人分享技能：

- 检查你的技能到你的仓库中（位于 ./.claude/skills 下）
- make a plugin and have a Claude Code Plugin marketplace where users can upload and install plugins (read more on the
  [documentation](https://code.claude.com/docs/en/plugin-marketplaces) here)

对于仅使用相对较少代码仓库的小型团队而言，将技能检入代码仓库的方式效果良好。但每一项被检入的技能都会为模型的上下文增加一些内容。随着团队规模的扩大，内部插件市场允许你分发技能，并让团队自主决定安装哪些技能。

#### 管理市场

你如何决定哪些技能进入技能市场？人们如何提交这些技能？

我们没有一个集中的团队来做决策；相反，我们尝试自然地发现最有用的技能。如果你有一项希望人们尝试的技能，你可以将其上传到 GitHub 的沙箱文件夹，然后在 Slack 或其他论坛中引导人们查看它。

一旦某个技能获得发展势头（这由技能所有者决定），他们就可以提交 PR 以将其发布到市场。

A note of warning, it can be quite easy to create bad or redundant skills, so making sure you have some method of curation before release is important.

#### Composing Skills

You may want to have skills that depend on each other. For example, you may have a file upload skill that uploads a file, and a CSV generation skill that makes a CSV and uploads it. This sort of dependency management is not natively built into marketplaces or skills yet, but you can just reference other skills by name, and the model will invoke them if they are installed.

#### Measuring Skills

To understand how a skill is doing, we use a PreToolUse hook that lets us log skill usage within the company (

[example code here](https://gist.github.com/ThariqS/24defad423d701746e23dc19aace4de5)). This means we can find skills that are popular or are undertriggering compared to our expectations.

### Conclusion

Skills are incredibly powerful, flexible tools for agents, but it’s still early and we’re all figuring out how to use them best.

Think of this more as a grab bag of useful tips that we’ve seen work than a definitive guide. The best way to understand skills is to get started, experiment, and see what works for you. Most of ours began as a few lines and a single gotcha, and got better because people kept adding to them as Claude hit new edge cases.

I hope this was helpful, let me know if you have any questions.

#### 综合总结

这三篇内容其实讲的是同一件事：**要把一个好用、低成本、可扩展的代码智能体做出来，关键不只是模型强不强，而是整套“智能体操作系统”怎么设计。**

它们分别对应三个层面：

1. **底层效率层：提示词缓存**
   - 如果把智能体看成一个长期运行的程序，提示词缓存就是它的“性能地基”。
   - 缓存命中率高，意味着更低成本、更低延迟、更稳定的体验。
   - 因此系统设计要围绕“前缀稳定”展开：静态内容放前面，动态内容放后面；不要频繁换模型、换工具、改系统提示。

2. **中间能力层：工具设计**
   - 智能体的能力，不只来自模型本身，也来自它可以调用什么工具、这些工具怎样组织。
   - 工具不是越多越好，也不是越少越好，而是要**匹配模型当前真实能力**。
   - 最好的方式不是拍脑袋定义工具，而是持续观察模型行为，发现它卡在哪里、误解什么、偏好怎么调用，再迭代工具形态。

3. **上层扩展层：技能（Skills）**
   - 技能是把经验、流程、脚本、模板、验证逻辑封装成可复用能力的方式。
   - 它让智能体不只是“会写代码”，而是逐渐学会你团队的库、流程、规范、排障套路和部署方法。
   - 好的技能不是堆知识，而是提供高价值上下文、避坑说明、参考资源、脚本和渐进式披露能力。

把三者串起来看，核心逻辑是：

> **缓存保证智能体“跑得起、跑得便宜”；工具决定智能体“做得到什么”；技能决定智能体“能否持续贴近真实工作流”。**

---

#### 深入浅出解读

##### 一、这三篇内容的共同主线是什么？

如果只看表面，这三篇分别在讲缓存、工具、技能，像三个分散话题。  
但从产品工程视角看，它们共同回答的是三个问题：

- **怎么让智能体长期对话而不贵？** —— 靠缓存
- **怎么让智能体知道该怎么行动？** —— 靠工具设计
- **怎么让智能体越来越懂你的团队和业务？** —— 靠技能沉淀

换句话说，模型本身只是“大脑”，但真正让它成为生产工具的，是外面的这三层工程化结构。

---

##### 二、为什么“提示词缓存就是一切”？

###### 1. 本质上是在争夺“重复计算不要重复付费”
提示词缓存的工作方式是**前缀匹配**：  
只要一段请求前半部分和以前一样，系统就可以复用这段计算结果，不必重新计算。

这意味着，在长会话、复杂代理、多轮工具调用的场景里，缓存不是“优化项”，而是“成本结构本身”。

如果缓存命中率很高：
- 响应更快
- token 成本更低
- 产品能放宽速率限制
- 用户感觉系统更“稳”

如果缓存命中率下降几个百分点：
- 整体成本会明显上升
- 延迟变高
- 某些高级功能会变得不划算

所以文中说他们会把缓存命中率低视为事故，这一点很关键。  
这说明在 agent 产品里，缓存不是底层细节，而是核心运营指标。

###### 2. 为什么很多人会“无意中把缓存打坏”？
因为缓存很脆弱。  
只要前缀中某处变了，后面就都失效了。

最容易踩坑的地方包括：
- 在静态系统提示里塞时间戳
- 工具顺序不稳定
- 中途增删工具
- 会话途中切模型
- 为了传递新信息而修改系统提示

这些做法看起来都很“合理”，但在缓存视角下，它们会重建整段前缀，代价非常高。

###### 3. 这背后最重要的设计原则是什么？
就是一句话：

> **稳定的东西尽量前置，变化的东西尽量后置。**

因此推荐顺序是：
- 系统提示 / 工具定义
- 项目级上下文
- 会话级上下文
- 最新对话消息

这样不同请求之间能最大化共享前缀。

###### 4. 一个很反直觉的点：不要总想着“修改提示”，而要“发消息”
比如：
- 时间变了
- 用户改了文件
- 进入计划模式
- 系统状态变化了

直觉上你会想更新系统提示。  
但那会导致缓存失效。

更好的方法是：  
**把变化作为新消息注入进去**，例如通过系统提醒消息、工具结果消息、状态通知消息来传递。

这相当于把“全局配置变化”变成“局部事件通知”。

从工程思维看，这非常像：
- 不重写配置文件
- 而是发一条增量事件

这样既保留了缓存，也更符合多轮会话的演进逻辑。

---

##### 三、为什么“像智能体一样观察”这么重要？

###### 1. 因为工具设计不是静态规则，而是行为科学
第二篇最有价值的地方在于它强调：

> **不要只从人类工程师视角设计工具，要从模型实际会怎么用的视角设计。**

很多时候我们设计工具，会默认：
- 这个功能逻辑清晰，模型应该会用
- 这个参数很合理，模型应该能填
- 这个输出格式定义好了，模型应该能遵守

但现实是：
- 模型可能理解错调用时机
- 可能不会稳定输出指定格式
- 可能更偏好某种更简单的调用路径
- 可能随着版本升级，工具适配方式也要改

所以好的工具设计，不是“我觉得对”，而是“模型实际表现证明它好用”。

###### 2. AskUserQuestion 的例子特别典型
他们一开始尝试把“提问”塞进已有工具或输出格式里，结果都不理想：

- 塞进 `ExitPlanTool`：职责混乱，计划和提问耦合
- 改输出格式：不稳定，模型会跑偏
- 最终做成单独工具 `AskUserQuestion`：结构清晰、调用稳定、用户体验也好

这个案例说明一个核心原则：

> **如果某个行为对交互质量非常关键，就不要只靠提示词约束，最好把它产品化成显式工具。**

也就是说：
- 纯文本提示适合“软约束”
- 工具调用适合“强结构行为”

###### 3. 工具会过时，甚至会变成束缚
文中提到他们早期用 `TodoWrite` 帮模型维持任务清单，后来发现更强的模型反而被它束缚了。

这很重要。因为很多人做 agent 时容易假设：
- 过去有用的工具，未来也一定有用
- 模型能力增强后，只要保留更多工具就更好

但实际情况可能相反：
- 弱模型需要强约束
- 强模型需要高自由度和协作能力

于是他们从 Todo 转向 Task，重点从“约束单个模型按计划走”，转成“支持多个子代理协作、共享状态、管理依赖”。

这说明：

> **工具设计应该跟着模型能力演化，而不是一劳永逸。**

###### 4. 搜索工具的变化，也揭示了一个更深层趋势
早期很多系统喜欢用 RAG，直接把检索到的上下文塞给模型。  
但文中指出，随着模型更强，一个更好的方向是：

> **让模型自己去找上下文，而不是总是被动接收上下文。**

比如给它：
- `grep`
- 文档链接
- 技能中的参考文件
- 子代理搜索职责

这背后是一种能力升级：
- 不是“我替你准备答案”
- 而是“我给你探索世界的手段”

这更像给一个工程师配工具箱，而不是替他把所有资料摊在桌上。

---

##### 四、技能（Skills）为什么是智能体真正的“组织记忆”？

###### 1. 技能不是 Markdown，而是能力包
第三篇反复强调一个误区：  
技能不只是说明文档。

它可以包含：
- 脚本
- 模板
- 参考代码
- 配置文件
- 数据文件
- hooks
- 本地存储

这意味着技能的本质不是“知识说明”，而是：

> **一个可被代理按需发现、读取、执行、更新的工作能力单元。**

它更像：
- 一个小型插件
- 一个团队流程封装包
- 一个带文档和工具的微型运行环境

###### 2. 为什么技能特别适合团队场景？
因为团队里最值钱的往往不是公开知识，而是这些隐性经验：
- 某个内部库有哪些坑
- 某个验证流程怎样才算完整
- 某个排障步骤先看哪个 dashboard
- 某个工单模板哪些字段最容易填错
- 某个部署流程怎样逐步放量、如何自动回滚

这些内容通常：
- 不值得塞进系统提示
- 过于细碎，模型默认不知道
- 但一旦出错，代价很高

技能正好把这类知识变成可复用资产。

###### 3. 技能分类其实就是企业智能体的能力地图
文中列出的 9 类技能非常有代表性，基本覆盖了一个工程组织的主要需求：

- 库/API 参考
- 产品验证
- 数据分析
- 业务流程自动化
- 脚手架模板
- 代码质量与审查
- CI/CD 与部署
- 操作手册
- 基础设施运维

这说明一个成熟 agent 体系，不应该只盯着“代码生成”。  
真正产生业务价值的，是把代码之外的工程流程也纳入能力边界。

###### 4. 好技能的核心，不是“教常识”，而是“补盲区”
文中有一句特别重要：**不要说显而易见的话。**

也就是说，技能最该提供的不是：
- 什么是 React
- 什么是测试
- 什么是部署

而是：
- 你们内部是怎么做的
- 哪些地方 Claude 容易犯错
- 哪些边界条件最重要
- 哪些模板和脚本能直接复用

所以一个好技能通常包含三类东西：
- **高价值背景**：模型本来不知道的组织知识
- **易错点清单**：过去真实踩过的坑
- **可执行资源**：脚本、模板、配置、示例

###### 5. 技能最好做成“渐进式披露”
这和第二篇的搜索设计是同一逻辑。

不要一上来把所有东西塞进主提示。  
而是告诉模型：
- 有哪些文件
- 什么情况下看哪个
- 如果需要，可以继续深入

这种方式的好处是：
- 降低上下文拥挤
- 保持主任务聚焦
- 真需要时再加载细节
- 更适合复杂组织知识的扩展

本质上，这是一种“按需上下文工程”。

---

##### 五、把三篇放在一起，能提炼出哪些方法论？

##### 1. 围绕“稳定前缀”设计系统
不是先做功能，再想缓存；  
而是从一开始就假设缓存是产品架构的一部分。

适合缓存的内容要稳定：
- 系统提示
- 工具定义
- 项目规则
- 常驻上下文

易变内容要后置：
- 临时提醒
- 用户变更
- 运行状态
- 新结果

---

##### 2. 用“消息”表达状态，用“工具”表达动作
这是三篇内容串起来后很清晰的一条线：

- **状态变化**：尽量通过消息传递
- **动作执行**：尽量通过工具显式化
- **复杂经验**：尽量通过技能封装

这样分层之后，系统会更稳、更容易扩展，也更利于缓存。

---

##### 3. 不要把工具当功能列表，而要当行为接口
工具设计不是“产品经理列需求”。  
而是要问：

- 模型会不会理解什么时候该调它？
- 会不会稳定地产生正确参数？
- 调完之后用户体验是否顺畅？
- 它是否和现有工具职责冲突？
- 它有没有破坏缓存或增加认知负担？

一个工具是否存在，不该只看“有没有用”，更要看“模型是否真的会用好”。

---

##### 4. 让模型自己找上下文，而不是永远喂上下文
随着模型变强，越来越值得做的是：
- 给它搜索能力
- 给它文档入口
- 给它子代理
- 给它技能文件系统
- 给它脚本和参考资源

这比把所有知识塞进主提示更灵活，也更可扩展。

---

##### 5. 把技能当作组织知识的“可执行化”
最强的技能不是“写得漂亮”，而是“真的能减少错误、节省时间”。

一个技能成熟的标志不是长度，而是它是否做到：
- 新人能用
- 老人愿意复用
- 模型少踩坑
- 流程更稳定
- 结果更可验证

---

##### 六、如果把这些经验翻译成通俗比喻，可以怎么理解？

可以把一个代码智能体想成一家正在成长的软件团队里的新人工程师：

- **提示词缓存**，像是它的“工作记忆和重复劳动优化机制”  
  如果每次开会都要从头介绍公司背景、项目规则、工具列表，那效率会极低。

- **工具设计**，像是你给这个新人配什么办公设备和工作流程  
  不是工具越多越好，而是要给他真正会用、用得顺的那几样。

- **技能**，像是团队内部沉淀下来的 SOP、最佳实践和作战手册  
  包括怎么发版、怎么排障、怎么查数据、怎么写周报、怎么评审代码。

真正成熟的团队，不是招来一个聪明人就完事，  
而是会建立：
- 稳定的信息结构
- 清晰的工具接口
- 可复用的组织经验

Claude Code 这三篇内容，本质上就是在讲：  
**如何把一个强模型，变成一个真正能融入工程系统的“数字同事”。**

---

#### 最值得记住的结论

- **缓存不是优化细节，而是 agent 产品的基础设施。**
- **工具不是越多越好，而是要贴合模型当前真实能力。**
- **技能不是文档堆砌，而是组织经验的可执行封装。**
- **状态尽量通过消息传递，动作尽量通过工具完成。**
- **随着模型变强，应更多让它自己搜索、自己构建上下文。**
- **成熟的智能体系统，核心不只是模型，而是围绕模型构建的工程体系。**

---

#### 一个更凝练的总判断

如果把这三篇压缩成一句话，那就是：

> **做智能体，不要只训练“回答能力”，更要设计“记忆结构、行动接口和组织化经验”。**

这也是 Claude Code 这类产品最值得借鉴的地方：  
它不是把模型直接扔给用户，而是把模型放进了一套经过精细设计的工程框架里。

3. **面向产品/工程负责人的落地建议清单**

## 产品-最佳实践（1）

### 2026-03-20 09:49:02

#### 代码智能体操作系统三层设计：以“修复支付结账故障” 为例的最佳实践

下面我用一个具体实例，把你提供的三组经验——**提示词缓存、工具设计、技能体系**——收束成一个可落地的“代码智能体操作系统三层设计”。

---

##### 一、先给出一个具体实例

假设你要做一个企业内部代码智能体，处理下面这个任务：

> “线上支付页面在部分用户提交信用卡后卡住，请定位原因，给出修复方案，必要时修改代码、补测试，并验证结账流程恢复正常。”

这个任务不是单纯写代码，而是一个完整的工程闭环，通常会涉及：

- 读取代码库
- 搜索日志与监控
- 进入规划模式
- 询问用户一些关键缺失信息
- 修改前后端代码
- 运行测试
- 用浏览器自动化验证
- 输出修复报告

这正适合用“三层设计”来实现。

---

##### 二、三层设计

##### 1. 第 1 层：上下文与缓存层

这一层的目标不是“让模型更聪明”，而是让它**持续、稳定、低成本地聪明**。

###### 在这个实例里，推荐的上下文顺序

按缓存友好顺序组织请求前缀：

1. **静态系统提示词**
   - 角色：你是支付系统代码智能体
   - 全局原则：优先定位根因、先验证后修改、变更需补测试

2. **固定工具定义**
   - `ReadFile`
   - `Grep`
   - `Bash`
   - `EditFile`
   - `RunTests`
   - `BrowserVerify`
   - `AskUserQuestion`
   - `EnterPlanMode`
   - `ExitPlanMode`
   - `ToolSearch`

3. **项目级稳定上下文**
   - `CLAUDE.md` / 仓库约定
   - 支付模块目录说明
   - 测试命令约定
   - 发布/回滚规范

4. **会话级上下文**
   - 当前任务：支付卡住故障排查
   - 当前分支、目标环境、最近失败时间段

5. **动态对话消息**
   - 用户补充的信息
   - 工具调用结果
   - 验证结果
   - 新发现的异常

###### 这一层的最佳实践

- **静态内容永远放前面，动态内容永远放后面**
  - 系统提示、工具定义、项目规则尽可能不变
  - 故障时间、用户补充、日志结果都通过消息追加

- **不要在会话中途改工具集**
  - 不要因为进入“规划模式”就移除 `EditFile`
  - 正确做法：始终保留完整工具集，用 `EnterPlanMode` 表示状态切换

- **不要中途切模型**
  - 比如主会话一直用高能力模型，就不要临时切到轻量模型处理小问题
  - 如果要切，使用子代理，并让主代理生成交接消息

- **用消息更新“易变信息”，不要改系统提示**
  - 例如“当前时间”“刚刚用户批准了可以改代码”“已确认只修复支付模块”
  - 应以系统提醒消息或工具结果注入，而不是重写系统提示

- **把缓存命中率当生产指标**
  - 对这类高频工程代理，缓存命中率下降几个点，成本和延迟都会明显恶化
  - 应监控：
    - prompt cache hit rate
    - 平均单轮 token 成本
    - 首 token 延迟
    - 工具定义变更频率

---

##### 2. 第 2 层：动作与工具层

这一层解决的是：**模型到底能做什么，以及怎样做得稳定。**

在“修复支付结账故障”这个任务里，不应该一股脑塞 50 个工具，也不应该只给一个万能 `Bash`。正确方式是设计一组**高频、边界清晰、模型容易理解**的动作。

###### 建议的工具集

###### 核心工具
- `Grep`
  - 搜索报错、接口名、支付状态流转、前端 loading 逻辑
- `ReadFile`
  - 读取关键代码与配置
- `EditFile`
  - 修改代码
- `RunTests`
  - 跑单测、集成测试
- `BrowserVerify`
  - 自动化走完整个 checkout 流程
- `AskUserQuestion`
  - 向用户确认环境、复现路径、是否允许改 schema 等
- `EnterPlanMode` / `ExitPlanMode`
  - 规划与执行切换
- `Task`
  - 管理子任务，如“定位前端卡住点”“核验后端状态机”“补支付超时测试”
- `ToolSearch`
  - 在工具很多时按需发现更深的专用工具

###### 延迟加载工具
例如以下专用工具不必一开始全部展开完整 schema：
- `GrafanaQuery`
- `LogCorrelator`
- `StripeSandboxRunner`
- `IncidentReporter`

先给轻量存根，必要时再加载完整能力。

###### 这一层的最佳实践

- **工具要表达“动作意图”，而不只是技术接口**
  - `AskUserQuestion` 明显优于“让模型自己输出特定 Markdown 格式的问题”
  - `BrowserVerify` 明显优于“让模型自己拼一长串浏览器命令”

- **用工具表示状态切换，不要靠改提示词硬控**
  - 进入规划模式：调用 `EnterPlanMode`
  - 退出规划模式：调用 `ExitPlanMode`
  - 这样更稳定，也不破坏缓存

- **优先设计模型“愿意用”的工具**
  - 工具再强，如果模型不理解何时调用，等于没用
  - 一个好工具应满足：
    - 触发条件清晰
    - 输入少且结构稳定
    - 返回结果容易被后续步骤消费

- **不要过早把“待办”设计成刚性清单**
  - 对复杂故障，更适合 `Task` 这种可更新、可依赖、可被子代理协作的任务结构
  - 而不是每 5 轮硬提醒一次固定 Todo

- **让模型自己构建上下文，而不是总喂现成上下文**
  - 给它搜索能力：代码搜索、日志搜索、文档搜索
  - 对支付故障场景，通常比预先塞一大堆 RAG 片段更有效

---

##### 3. 第 3 层：技能与工作流层

这一层负责把“可用动作”变成“可复用解决方案”。

在这个实例里，最适合沉淀成技能的，不是“如何写 if 语句”，而是组织特有、容易踩坑、可重复复用的工程流程。

###### 推荐为这个实例设计的技能

###### 技能 1：`checkout-debugging`
用于支付结账异常排查。

包含内容：
- 常见故障路径
  - 前端 loading 未清理
  - payment intent 状态不同步
  - webhook 未到账
  - 风控回调超时
- 关键日志检索脚本
- 常见 dashboard / panel ID
- 故障排查顺序
- 易错点列表

###### 技能 2：`checkout-verifier`
用于自动验证修复是否有效。

包含内容：
- 测试卡号
- 浏览器自动化脚本
- “提交支付 -> 等待回调 -> 验证订单状态”的断言逻辑
- 截图/录屏输出能力

###### 技能 3：`payment-style-and-tests`
用于约束改动质量。

包含内容：
- 支付模块代码风格
- 必须覆盖的测试类型
- 禁止直接跳过异步重试逻辑
- 常见 mock 陷阱

##### 三、把三层串起来：一次理想的执行流程

下面是这个智能体在该实例中的推荐运行方式。

###### 第一步：进入规划模式
模型调用 `EnterPlanMode`，只做分析，不改代码。

输出计划可能是：

1. 搜索前端 checkout loading 相关状态
2. 搜索后端 payment intent 状态流转
3. 检查最近 webhook 失败日志
4. 若缺复现信息，调用 `AskUserQuestion`
5. 形成根因假设后退出规划模式

###### 第二步：按需补充信息
如果用户没说明具体支付渠道，模型调用 `AskUserQuestion`：

- 复现环境是生产还是 staging？
- 是否仅发生在信用卡支付？
- 是否允许我运行支付沙箱验证？

这里的关键点是：**用工具收集结构化信息，不要让模型自由发挥提问格式。**

###### 第三步：构建上下文
模型调用：
- `Grep` 搜索 `checkout loading`
- `ReadFile` 阅读前端支付提交逻辑
- `ToolSearch` 发现日志查询工具
- `GrafanaQuery` 或 `LogCorrelator` 查 webhook 超时

###### 第四步：退出规划并执行
模型调用 `ExitPlanMode`，开始修改代码与补测试。

###### 第五步：验证
依次执行：
- `RunTests`
- `BrowserVerify`
- `checkout-verifier` 技能中的端到端脚本

###### 第六步：产出报告
报告应包括：
- 根因
- 修改点
- 风险点
- 验证结果
- 是否建议灰度发布

##### 四、基于该实例的最佳实践清单

##### A. 上下文工程最佳实践

- **把系统提示、工具定义、项目规则视为“稳定前缀”**
- **所有运行时变化都通过消息追加，不要改前缀**
- **规划模式、调试模式、审查模式都应用工具表达，而不是换一套工具或重写系统提示**
- **辅助任务如压缩、总结、分叉分析，必须复用与主会话相同的前缀**
- **上下文压缩时，使用“缓存安全分叉”**
  - 即保留相同系统提示、相同工具、相同项目上下文
  - 只在末尾追加“请总结当前对话”的新消息

##### B. 工具设计最佳实践

- **优先做高价值、强约束、低歧义的工具**
- **不要让一个工具同时承担多个不兼容目标**
  - 例如“既输出计划，又生成给用户的问题列表”通常会让模型困惑
- **工具命名要体现任务语义**
  - `AskUserQuestion`、`BrowserVerify`、`EnterPlanMode` 都比泛化工具更容易触发
- **工具返回应尽量结构化**
  - 如状态、错误码、摘要、下一步建议
- **对重工具采用延迟加载**
  - 工具很多时，不要全量注入完整 schema

##### C. 技能设计最佳实践

- **技能重点写“坑”，不要写常识**
  - 比如支付回调的幂等性、测试卡的特殊行为、订单状态延迟传播
- **每个技能都应有“注意事项 / gotchas”部分**
- **技能要善用文件夹结构**
  - `references/`
  - `scripts/`
  - `examples/`
  - `templates/`
- **把高频脚本直接放进技能里**
  - 让模型少写模板代码，多做组合决策
- **技能描述不是摘要，而是触发条件**
  - 要写清楚“什么时候应该调用这个技能”

##### D. 验证与运营最佳实践

- **验证技能要优先投入**
  - 很多代理真正缺的不是“会写”，而是“会证伪”
- **记录技能使用率、触发率、成功率**
- **把缓存命中率、平均延迟、修复成功率一起看**
- **对高风险技能加按需钩子**
  - 如生产环境禁止 `rm -rf`
  - 限制只允许修改 `payments/` 目录
- **持续淘汰过时工具**
  - 模型能力提升后，某些旧工具会从“帮助”变成“束缚”

#### 代码智能体操作系统三层设计分析报告

##### 一句话判断

这组内容的核心结论非常清晰：  
**下一代代码智能体产品，不是“更强的聊天框”，而是一个围绕缓存、工具、技能和任务编排构建的“Agent OS（智能体操作系统）”。其竞争力不在单次回答质量，而在长期运行效率、稳定性、可扩展性与组织沉淀能力。**

##### 一、核心洞察提炼

从三篇内容里，可以提炼出 3 个一以贯之的底层逻辑：

1. **Prompt Cache 是运行时经济学的核心**
   - 长时运行代理的成本、延迟、吞吐，本质上取决于缓存命中率。
   - 一旦系统提示、工具定义、模型切换、上下文分叉处理不当，整个系统的单位成本会显著恶化。
   - 所以，代理产品不能只设计“能力”，必须先设计“缓存友好的执行路径”。

2. **工具设计不是功能堆砌，而是动作空间设计**
   - 工具不是越多越好，而是要让模型“愿意用、会用、用得准”。
   - 好的工具要顺应模型认知方式，降低调用摩擦，提升结构化输出与行为确定性。
   - 工具设计要随着模型能力变化不断重构，避免旧工具反而束缚新模型。

3. **Skills 让 Agent 从一次性能力变成组织级生产系统**
   - Skill 不只是提示词模板，而是“可调用的工作流单元 + 文件系统上下文 + 运行脚本 + 配置 + 持久记忆”。
   - 它承载了知识、流程、约束、验证与复用，是 Agent 平台化、团队化、组织化的关键接口。
   - 技能市场/插件市场意味着 Agent 从单体产品迈向生态系统。

---

##### 二、产品本质：这不是 IDE 插件，而是代码智能体操作系统

如果用产品定义来概括，这类系统的本质可以表述为：

> **面向软件生产活动的 Agent OS**：  
> 以模型为认知核心，以工具为动作接口，以技能为能力封装，以缓存和上下文管理为运行时底座，以任务和子代理为协作机制，最终承接从“理解需求—搜索上下文—生成方案—实施修改—验证结果—部署运维”的完整闭环。

它与传统 Copilot/Chat 助手的区别在于：

| 维度 | 传统代码助手 | 代码智能体操作系统 |
|---|---|---|
| 交互模式 | 问答/补全 | 持续任务执行 |
| 上下文 | 临时拼接 | 可持续管理、压缩、分支 |
| 工具使用 | 少量固定工具 | 多工具编排、子代理协同 |
| 组织知识 | 靠 prompt | 靠 skills / 插件 / 文件系统 |
| 成本结构 | 单次调用成本 | 长会话缓存优化后的规模成本 |
| 产品目标 | 提升编码效率 | 承担部分软件生产职责 |

##### 三、建议的“三层设计”模型

结合文中经验，最适合抽象成以下三层架构：

##### 1. 运行时内核层（Runtime Kernel）

这是 Agent OS 的底盘，决定成本、稳定性和规模化能力。

###### 核心职责
- Prompt 缓存管理
- 会话状态管理
- 上下文压缩与分叉
- 模型路由与子代理切换
- 工具前缀稳定性控制
- Token / Latency / Cache Hit 监控

###### 关键原则
- **静态前缀前置，动态信息后置**
  - 系统提示 / 工具定义 / 项目级规则 / 会话上下文 / 对话消息，按缓存友好顺序组织。
- **用消息更新状态，不改系统提示**
  - 如日期变化、计划模式切换、文件更新提醒，尽量通过 message 注入。
- **会话中不要随意切模型、切工具集**
  - 状态变化通过工具调用建模，而不是重写上下文。
- **所有分叉任务必须“缓存安全”**
  - 压缩、总结、辅助分析都要复用父上下文前缀。

###### 这一层的价值
- 降低单任务成本
- 支持长时代理
- 保持高响应速度
- 为商业订阅模型提供毛利空间

###### 风险
- 很多团队只做“能力层”，忽视运行时设计，最终成本失控
- 缓存命中率下降会直接拖垮产品体验和订阅模型

---

##### 2. 能力编排层（Capability Orchestration）

这是 Agent 如何“行动”的层，决定任务完成率与行为质量。

###### 核心组成
- Tool Calling
- Task / Todo / Plan Mode
- AskUserQuestion
- Search / Grep / ToolSearch
- Subagent / Handoff
- Verification / Review / Fix Loop

###### 本质
这一层不是“给模型接 API”，而是为模型设计合适的**动作空间（Action Space）**。

###### 关键设计方法
- **工具应服务于模型行为闭环**
  - 搜索上下文
  - 获取缺失信息
  - 产出计划
  - 修改代码
  - 验证结果
  - 汇报状态
- **优先提供模型真正理解并高频受益的工具**
  - 一个模型“不会用”的工具，设计再完美也没有价值。
- **状态切换用工具表达**
  - 比如 EnterPlanMode / ExitPlanMode，而不是变更工具集。
- **上下文获取尽量让模型主动搜索**
  - 从“系统喂给它”转向“它自己找”，更可扩展。
- **验证能力必须产品化**
  - 自动化测试、Playwright、tmux、日志校验、断言链路，都是生产级可信度关键。

###### 这一层的价值
- 显著提升任务闭环率
- 提高复杂任务稳定性
- 降低用户来回纠错成本
- 让 Agent 从“会写”变成“会做完”

###### 风险
- 工具过多，模型选择成本上升
- 工具语义不清晰，导致误调用或不调用
- 缺少验证链路，结果看似完成但不可用

---

##### 3. 组织知识与生态层（Knowledge & Skill Ecosystem）

这是 Agent OS 真正形成壁垒的一层，也是 PMF 最强的部分。

###### 核心组成
- Skills / Plugins / Marketplace
- 内部 API 参考
- 业务流程模板
- 验证脚本
- 运维 Runbook
- 数据查询能力
- 团队最佳实践
- Skill usage telemetry

###### Skill 的真正角色
Skill 不是“prompt 包装”，而是：
- 领域知识封装
- 工作流自动化单元
- 组织经验的沉淀载体
- Agent 可发现、可学习、可复用的能力模块

###### 优秀 Skill 的典型类型
- 库/API 参考
- 产品验证
- 数据分析
- 团队自动化
- 脚手架生成
- 代码质量审查
- CI/CD 部署
- 运维排障
- 基础设施治理

###### 关键价值
- 把“个人提示词”升级为“团队资产”
- 把“模型能力”升级为“组织能力”
- 形成跨项目复用和复利积累
- 建立插件市场与生态网络效应

###### 风险
- Skill 数量膨胀，质量失控
- 触发描述不准确，导致 under-trigger / over-trigger
- 没有 usage logging，无法持续优化
- 技能分发机制不成熟，难以规模化协同

##### 推荐产品形态

###### 3. 面向企业

##### 五、PMF 分析

##### 1. 目标用户是谁

###### 第一阶段最强 PMF 人群
- 高频写代码的工程师
- Tech Lead / Staff Engineer
- DevOps / SRE / Oncall 工程师
- 需要频繁跨系统排障的研发团队
- 内部平台/效率工具团队

###### 第二阶段扩展用户
- 数据分析师
- QA / 测试工程师
- 产品运营自动化场景
- 企业内部流程自动化团队

---

##### 2. 用户的核心痛点

- 上下文大、系统复杂，AI 很容易“看不全”
- AI 会写代码，但不会稳定完成任务闭环
- 团队知识散落在文档、脚本、Slack、口口相传中
- 每次都要重复解释组织内部规范和流程
- 复杂操作（部署、回滚、排障）风险高、门槛高
- 现有 AI 成本高、速度慢、结果不可验证

---

##### 3. 这个产品解决的“非连续性价值”

真正的 PMF 不在“快 20%”，而在以下三个跃迁：

###### 从“建议工具”到“执行工具”
用户不再只要答案，而是要完成任务。

###### 从“个人提效”到“组织能力沉淀”
好的 Skill、Runbook、验证脚本会不断复用，形成复利。

###### 从“单次推理”到“长期运行”
缓存、压缩、任务协作让 Agent 能长期工作而非一次性问答。

---

##### 4. PMF 强弱判断

###### 强 PMF 信号
- 用户把它当成默认入口，而不是备用工具
- 团队开始沉淀自己的 skills / plugins
- 出现高频复用的验证和运维类技能
- 用户开始关心缓存命中率、成功率、任务完成率
- 子代理、任务编排被自然使用而非被教育使用

###### 弱 PMF 信号
- 用户只在写样板代码时偶尔用一下
- 工具和技能很多，但调用率低
- 每次都要用户重新描述上下文
- 没有可复用资产，只有一次性 prompt
- 成本和延迟高到无法成为主工作流入口

##### 六、技术实现路线建议

##### 第一阶段：先做“Agent Runtime”而不是“万能平台”

##### 七、商业模式分析

##### 最合理的商业模式组合

###### 1. 订阅制
适合个人开发者与小团队。

适合大规模团队和企业。
- Token / Tool usage / Runtime minute / Task completed
- 高缓存命中率将直接改善单位经济模型

###### 3. 技能市场分成
中长期最有潜力。
- 官方技能
- 社区技能
- 企业认证技能
- 垂类场景技能包

###### 4. 企业私有部署 / VPC
适合大客户采购。
- 安全、审计、内网工具接入能力强时会非常有吸引力

---

##### 八、竞争分析

##### 主要竞争维度不是“模型谁更强”，而是这四个：

###### 1. Runtime 优化能力
谁能更稳定地做长时任务，并把成本打下来。

###### 2. 工具与任务闭环设计
谁能让模型真正完成任务，而不是输出看起来聪明的文本。

###### 3. Skills / 插件生态
谁能让组织知识沉淀成复用资产。

###### 4. 企业接入与治理能力
谁能进入真实生产环境。

###### 潜在竞争对手
- IDE Copilot 类工具
- 通用 Agent 框架
- 内部工程效率平台
- DevOps 自动化平台
- 企业工作流编排工具

###### 差异化机会
- 以“缓存友好 runtime”作为底层优势
- 以“Skill 作为组织知识操作系统”形成长期壁垒
- 以“验证与运维闭环”切入高价值场景，而不是泛写代码

---

##### 九、关键风险与挑战

##### 产品风险
- 用户会把它当聊天工具，而不是任务代理
- 首次体验惊艳，但长期可靠性不足
- 技能质量参差不齐，导致信任崩塌

##### 技术风险
- 缓存策略设计失误，成本失控
- 工具定义频繁变化，导致前缀抖动
- 压缩和分叉实现不当，隐藏成本暴涨
- 多模型切换缺乏缓存意识

##### 组织风险
- 缺少技能治理机制，市场迅速劣化
- 没有 telemetry，不知道哪些能力真正有效
- 平台团队和业务团队协作断裂，技能无法持续维护

---

##### 十、结论：一个高可行性的战略判断

这套思路非常有潜力，不只是 Claude Code 的经验总结，更像是一个清晰的行业方向：

> **代码智能体的终局形态，不是“更会写代码”，而是成为软件生产系统中的 Agent OS。**

其三层核心分别是：

1. **运行时内核层**：缓存、上下文、分叉、压缩、模型与工具稳定性  
2. **能力编排层**：工具、任务、计划模式、提问、搜索、验证、子代理协作  
3. **组织知识生态层**：skills、插件、流程模板、运行脚本、团队沉淀、技能市场

如果要判断这条路线是否值得做，答案是：  
**非常值得，而且应该优先做底层运行时和验证闭环，而不是先做一个看起来功能很多的平台。**

因为真正的护城河不在 UI，也不在 prompt，而在这三件事：

- **更低的长期运行成本**
- **更高的复杂任务完成率**
- **更强的组织知识复用能力**

---

##### 十一、给产品落地的精炼建议

###### 如果你要做这个方向，建议按以下优先级推进：

1. **先把 Runtime 打透**
   - 重点盯缓存命中率、会话结构、压缩分叉和工具前缀稳定性

2. **围绕“任务闭环”设计能力，而不是围绕“工具数量”设计**
   - 搜索、提问、计划、执行、验证、汇报，形成最小闭环

3. **尽快把 Skills 做成组织资产**
   - 从验证、运维、API 参考、团队流程四类开始最容易出效果

4. **把指标体系建立起来**
   - Cache hit rate、task success rate、tool invocation quality、skill trigger rate、verification pass rate

5. **商业化优先切团队与企业场景**
   - 因为组织知识沉淀、权限治理、流程复用，才是真正高价值和高粘性的付费点

## 深度解读（1）

### 2026-09-17 23:55:56

#### Claude Code 暗含的三层智能体操作系统：上下文、工具与组织技能

Claude Code 把提示词缓存命中率过低视为线上事故，这个细节很有分量。它说明：对长时间运行的智能体而言，缓存不是成本优化的附属项，而是会反过来规定产品架构。

##### 第一层：保持上下文稳定，而不是不断重写状态

提示词缓存依赖前缀匹配，前面任何变化都会使后续缓存失效。因此 Claude Code 将内容依次排列为：全局系统提示与工具、项目配置、会话上下文、对话消息。时间变化、模式切换等动态信息不去修改系统提示，而是追加为新消息。

这解释了几个反直觉设计：规划模式不替换成只读工具集，而是让模型调用 EnterPlanMode；几十个 MCP 工具不直接移除，只先暴露轻量存根；压缩上下文时也复制父会话的提示、工具和历史前缀。甚至在十万 token 的 Opus 会话中，临时切换到更便宜的 Haiku，可能因重建缓存而更加昂贵。

**这里真正值得迁移的原则是：稳定部分尽量不可变，状态变化采用追加和分叉。**它近似事件日志，而不是随时改写的配置表。其收益不只是省钱，也包括行为更可复现、问题更容易定位。不过，这套设计依赖具体模型 API、缓存计价和上下文机制，不能机械复制。

##### 第二层：工具不是功能清单，而是模型的动作界面

文章中最典型的迭代是 AskUserQuestion：把问题塞进退出规划工具，会混淆“计划”和“待确认事项”；要求模型输出特定 Markdown，又无法保证格式；最终做成结构化工具，既约束输出，又暂停执行等待用户回应。

这说明智能体工具有一个常被忽视的用户——模型。人类觉得清晰的抽象，模型未必能稳定选择和调用。工具数量、命名、参数结构与反馈方式，都需要通过实际轨迹验证，而不能仅按软件模块划分。

更重要的是，这个界面会随模型能力变化。早期 TodoWrite 和周期性提醒帮助模型坚持计划；模型增强后，固定待办反而限制调整与多智能体协作，于是被支持依赖、共享更新的 Task 替代。**模型升级不只是性能提升，也可能让旧脚手架从助力变成阻力。**因此，智能体产品需要持续做工具选择率、误调用、任务成功率和跨模型回归测试。

##### 第三层：技能正在成为“可执行的组织知识”

技能不只是 Markdown，而是包含说明、脚本、模板、数据、钩子和持久状态的文件夹。它把散落在文档、资深员工经验和临时脚本里的知识，变成模型可发现、可组合、可执行的工作单元。

其中最有价值的并非“让模型多生成代码”，而是让它可靠地验证结果：跑完整注册流程、核对支付状态、比较发布前后错误率、调查告警并生成结构化报告。生成能力日益通用后，真正稀缺的是组织特有的边界条件、数据入口、验证标准与安全护栏。

这也形成了明确的平台机会，但不能把技能数量当作价值。需要验证的是：它是否比现有文档、脚本和操作手册更能降低执行偏差与协作成本。相应的治理能力包括触发准确率、成功率、权限与风险控制、版本兼容、重复技能清理，以及基于真实使用而非集中拍脑袋的市场策展。

三篇文章合起来描绘的不是几个提示技巧，而是一套智能体操作系统：**底层管理可复用的上下文，中层设计模型能够理解的动作空间，上层沉淀可验证的组织能力。**未来智能体产品的差距，很可能不只来自所选模型，而来自这三层是否能共同演化。
