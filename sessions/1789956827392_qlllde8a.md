#### Resurrected random guitar pedal project

This is a resurrected version of my old guitar pedal project: a digital guitar pedal built around an RP2354A and a TI audio codec, with all the effects done in software on a core of its own.

It went through a phase with a little OLED screen and a couple of rotary encoders on it, and that's gone now. Editing seventeen effects through a 128x128 screen and two knobs was never going to be pleasant, and I'm not exactly known for my mad UI designing skillz, so the pedal itself is down to one knob and one stomp switch and the deep editing happens somewhere that already has a screen: there's a web app that talks to it over USB MIDI from a browser.

So what's in here:

- `Hardware` has the kicad files.
- `Effects` has the seventeen effects, one file each. They are up here rather than inside the firmware because three different things are built from them: the firmware, the test bench, and the web app's controls.
- `Audio` has the DSP the effects are built out of - biquads, envelope followers, LFOs - and the audio loop itself. The bench compiles the same files, so what gets measured is the pedal's own arithmetic.
- `Firmware` is the rest of what runs on the pedal: USB, MIDI, scenes, the board pin maps.
- `WebMIDI` is the web app that edits it.
- `scripts` is what the build runs - the effect generator, the math tables, and the checks that refuse a firmware image doing something the audio core shouldn't.
- `Validation` is the test suite. Some of it runs on your machine and some of it wants a pedal plugged in.
- `Documentation` remains a very optimistic name for a directory.

#### Firmware

I've only ever built the firmware on Linux, but it *should* be perfectly possible to build on MacOS or Windows too if you just figure out the platform requirements. The project depends on the `pico-sdk` and `tinyusb` libraries, and has submodules for both, so they get built automatically, but the build tools your platform has to provide.

Regardless of platform, you'll need the basics:

- git
- make
- python3
- cmake

and a 32-bit arm cross-build environment. On Linux, that would be something like

- arm-none-eabi-binutils-cs
- arm-none-eabi-gcc-cs
- arm-none-eabi-newlib

There's more than one board this can be built for, and the build won't guess. You say which one this tree is about once, in `board.local`, and it stays said - it's a file rather than a cmake cache variable specifically so that blowing away `build/` doesn't silently change your mind for you. So:

```
	git clone https://github.com/torvalds/GuitarPedal.git
	cd GuitarPedal
	echo unified > board.local
	make prep
	make
```

`unified` is the current one-board pedal. The other is `split`, which is the older modular pair of boards. If you forget this step the configure will stop and tell you, which is the intended behaviour - a wrong board should be an error you fix once, not a working build for hardware you don't have.

That gets you `build/pedal-unified.uf2` (and `.elf`, and `.bin`). Every artifact is named for the board it's for, so there is deliberately no `pedal.uf2` to grab by mistake. You can build the other board without changing what the tree is about - `make split` - or both with `make all-boards`.

To get the `.uf2` onto the pedal you need it in BOOTSEL mode, and there are two ways. If it's running and plugged in, send it MIDI CC 20 with value 126 and it will reboot into BOOTSEL on its own:

```
	amidi -l                          # find which card the pedal is
	amidi -p hw:5,0 -S "B0 14 7E"     # ...and that 5 is mine, not yours
```

Otherwise, hold the knob in while you plug it in. The rotary encoder's switch doubles as BOOTSEL on this board - through a Schottky, so that QSPI traffic can't fake pulling it low - and that's the route that still works on a pedal too broken to enumerate. The older boards had a proper BOOTSEL button, but it was on the little MCU daughtercard, which is fine on a bench and useless the moment the thing is screwed into a box.

Either way a USB mass storage device shows up and you copy the file to it.

If you have installed picotool with USB support (the pico-sdk build only builds a cut-down version without it), you can skip all that and just do `make flash`, which builds and flashes the board in `board.local`. `make flash-split` does the other one.

##### Testing

`Validation` has the test suite, and it's split by what it needs.

`make check` runs the part that needs no hardware at all: the MIDI packetiser, whether the web app still loads and still draws the right conclusions, and a sweep that asks every biquad in the pedal where it actually landed. `make check-biquad` is that last one on its own, and `make check-effects` puts signals through the effects themselves.

That last one works because of `Validation/bench`, which builds the pedal's actual audio core - the same `single_sample()`, the same effect headers, the same compiler flags - as a program on your machine that takes float samples on stdin and hands them back on stdout. It is not a model of the signal path. It's the signal path, with the two register blocks the audio core touches replaced by ordinary memory.

`make check-analysis` is the other host-only one, and it is what keeps the per-effect pages under `Documentation/effects` honest: every curve on those pages is a measurement, and this re-measures and says when one has stopped being true. It is separate from `check` because it re-runs every sweep on every page, which is slow.

Then there are the ones that want hardware: `make check-hw` with a signal generator, `make check-analog` with a patch cable from the pedal's output back to its own input, `make check-bench` to ask whether a real board agrees with the host build, and `make check-loop` if you have two pedals to patch into each other.

#### Hardware

The kicad design files (and some supporting infrastructure, like the 3D printed insert and the enclosure drill rules) are in the `Hardware` subdirectory.

These days it's just the one board. `Hardware/usb-stomp` has the RP2354A and the TI TAC5242 codec sitting directly on it, and that's the whole pedal: no cable, no daughtercards, no connectors in between.

What's on it:

- a 1/4" input jack and a 1/4" output jack
- a third 1/4" jack for an expression pedal or a remote stomp switch
- MIDI in and out, on 3.5mm "Type A" TRS jacks (out through a 5V buffer, in through an optocoupler, like MIDI has always wanted)
- USB-C, and the usual 9V guitar pedal power jack
- one rotary encoder with a switch under it, and one stomp switch
- three addressable WS2812B LEDs

The MIDI jacks and the expression jack are the genuinely new things. The older boards had nowhere to put them - the expression jack in particular wants two ADC pins, and those are exactly the pins the old MCU board was spending on hardware MIDI, so it could not have existed there at all.

Fair warning on that expression jack, though: the hardware is done and the firmware can read it, but only when the host asks it to over SysEx. Right now it's a probe for figuring out what people actually plug in there - expression pedals don't even agree on which contact is the wiper

- and nothing is wired up to *do* anything with the result yet.

##### How it used to be

It used to be modular, and those board files are all still here. There were two little daughtercards for the "core" hardware - the RP2354 microcontroller (`Hardware/rp2354`) and the TI TAC5112 codec (`Hardware/codec`) - plus a board for the audio and 9V DC power jacks (`Hardware/audio-jacks`), and a main board (`Hardware/pedal-board`) for the pedal IO: i2c connector for the screen, USB-C programming port, rotary encoders, pin header for stomp switches. The two halves were joined by a 12P 0.5mm FFC cable carrying power and data lines (i2c for control, i2s for audio).

That was mostly so I could try out different form factors. It let me lay the two halves out independently, and it was flexible enough to cram a 125B enclosure full of jacks, rotaries and the screen all in one top area. There was also a worry about noise isolation, which in the end never had to be tested.

I used the nice HiRose BM28 series connectors on the modular boards. They are absolutely tiny, which makes for a great board footprint but admittedly also makes for a slightly more complicated board due to the tiny 0.35mm pitch. I'm not a fan of the traditional pin headers simply because they make it so hard to do compact form factors.

Those boards are finished and they still work - the firmware builds for them, and they're still useful for testing. But what this section used to say was that if you know what you want, you should just put the codec directly on the audio jack board and the rp2354 on the IO board. Which, yes. That's the board above.

#### Basic UI

There's no screen. The pedal has one knob, one footswitch and three LEDs, and everything else happens in a browser.

##### On the pedal

Out of the box the footswitch is bypass - tap for in-circuit or not, hold it for the tuner - and the knob is the master volume, with either kind of press on it putting the volume back where it started. That last one sounds trivial and isn't: it's the way back when you can't see anything.

But none of that is compiled in. There are five gestures - turn the knob, tap it, hold it, tap the switch, hold the switch - and what each one means is a table the pedal looks up and the app writes. You can point the knob at any parameter of any effect, or make a single press take one effect's mix up while it takes another's down. A pedal with no screen can't tell you what its knob is for, so that has to be settable from something that can.

The three LEDs, left to right: something is wrong (red for clipping, amber for dropped samples), in circuit or bypassed, and the chain is busy - where "busy" means whatever the effect thinks it means, so the gate lights it while it's gating and the compressor while it's compressing.

##### In the browser

`WebMIDI` is a static web page that talks to the pedal over USB MIDI. There's nothing to install and it runs off a phone.

It doesn't know what the effects are. It asks. The pedal describes every effect it has - every pot, the ranges, the units, the hover text - and the app builds itself out of that, so it can't drift out of step with the firmware, and adding an effect to the pedal makes it show up in the app without touching the app.

What you actually do there is *route*. There are seventeen effects and none of them are in your signal path until you say so: routing picks which ones run, and in what order, and the order is yours, because a boost in front of a delay is a different pedal from a delay in front of a boost. Whatever you don't route costs nothing.

Pots are mostly just numbers, except where they aren't - the tone stacks, the parametric EQ and the cab sim draw their actual frequency response, so you can see the curve instead of inferring it from three knob positions.

![The WebMIDI app with a tone control and a tape echo routed](https://raw.githubusercontent.com/torvalds/GuitarPedal/2c837e3dcace62e0f2a46d90205da163dfa933bd/Images/WebMIDI-screenshot.png)

A tone stack with a 10dB mid bump at 810Hz and a tape echo behind it, and the fifteen effects that aren't routed sitting at the bottom waiting to be. The faint grey line is the phase response.

Eight scenes fit in the pedal's own flash. A scene is a routing plus everything set inside it, and a MIDI program change recalls one, which is half of what those MIDI jacks are for: a cheap footswitch can step between scenes with no computer in sight.

#### Audio effects

Seventeen of them, plus three that are always there and can't be unrouted: the **Signal Chain** at the front, which is the input trim, the noise gate and the master volume ([measured](https://boardrepo.com/torvalds/Documentation/effects/signal-chain.md)), and behind them the **Settings**, which is USB audio routing, MIDI channel, LED brightness and what the tuner is tuning to, and the **Expression Jack**, which is what is plugged into it and where that thing's travel ends.

They're listed in the order they run in by default. This is an overview and not documentation - the app is the reference, because it gets the ranges, the units and the hover text from the pedal itself rather than from anything I typed here.

- **Tone** - bass, mid and treble, with the corner frequencies adjustable and the mid's Q as well. There are two of them, so one can go in front of a distortion and one behind it.
- **Preamp** - a two-stage 12AX7 model, class-A biased with the asymmetry left in, and a JFET stage after it.
- **Compressor** - level, ratio, attack, release, and a boost, so it can also just be a clean boost when that's what you want. The threshold reaches low enough to work on a quiet pickup with nothing in front of it. [Measured](https://boardrepo.com/torvalds/Documentation/effects/compressor.md).
- **Boost**, with distortion. I like this one. Others may not. Set the boost stupidly high and the level low, and instead of clipping at the level the signal *folds* back down, which gives you harmonics that a soft or hard clipper doesn't.
- **Klonlike** - the obvious model: 18V charge pump for headroom, germanium diodes, and the clean/dirty blend that tracks the gain knob. Originally by Bryan Leavelle. [Measured](https://boardrepo.com/torvalds/Documentation/effects/klon.md).
- **Rat Sketch** - a ProCo RAT, from the Aion FX Helios clone. One op-amp with up to 67dB and several decibels an octave of treble emphasis inside the feedback, then diodes to ground, then the one backwards Filter knob. Three clipping modes, because the pedal has three. The op-amp saturates inside its own loop and the diodes are solved rather than approximated, which is where its second harmonic comes from. [Measured](https://boardrepo.com/torvalds/Documentation/effects/rat.md).
- **Phaser**, **Flanger** and **Vibrato** - the modulation three. All simple, all a delay line and an LFO wearing different hats.
- **Tape Echo** - the Echo King from Cleveland Music Co, a model of the Maestro Echoplex tape delays, converted from the Hothouse examples. All credit to Ricky Sheaves, and blame me for the conversion.
- **Reverb** - comb filters into allpasses, the traditional way. [Measured](https://boardrepo.com/torvalds/Documentation/effects/reverb.md).
- **Pitch** - not the clever FFT kind. It walks a delay line faster or slower than real time in two phases, crossfaded with a sine so the wrap doesn't click. So it shifts *and* delays, and it feeds back into itself, which makes it a short echo that shifts again on every repeat. Most natural an octave up, but it does fractions.
- **Tremolo** - amplitude modulation, several shapes.
- **Parametric EQ** - five bands, two shelves and three peaks, every one of them tunable across the whole range.
- **Frenchie Amp** - a small amp: triode, tone stack, power amp.
- **Test Tone** - sine, triangle, saw or noise at a known level and frequency. It replaces the input rather than adding to it, which is what lets the pedal measure itself.
- **Cabinet** - a speaker cone as a moving mass rather than as a filter, integrated at the sample rate. Pick one of five cabinets and it knows the rest of itself; the knobs are how hard the amp drives it, how much the amp lets its resonance bloom, and where the mic is pointed.

##### 核心总结

这是一个重新开发的开源数字吉他效果器：以 RP2354A 微控制器和 TI 音频编解码器为核心，用独立内核运行软件音效，集成 17 种可自由排序的效果。项目放弃小屏幕与双旋钮，把硬件界面简化为一个旋钮、一个脚踏开关和三颗 LED，复杂编辑则通过浏览器经 USB MIDI 完成。其突出特点是**效果定义同时服务于固件、测试程序和网页控件**，并用主机仿真、实机回环和外部信号源等多层测试降低 “文档、界面与实际声音不一致” 的风险。不过，表达踏板接口的软件功能尚未完成，跨平台构建、网页兼容性及实际音质表现也没有在本文中得到充分验证。

##### 通俗解读

###### 1. “简单硬件＋浏览器编辑” 是在重新分配交互任务

作者认为，用 128×128 小屏和两个旋钮编辑 17 种效果并不实用，因此让效果器本体只负责演奏时最常用的操作，如旁路、调音和音量；效果顺序、参数和按键映射则交给手机或电脑浏览器。

这并非单纯削减功能，而是把不同任务放到更合适的设备上：

- 演出时需要快速、可靠地踩踏和调节，实体控件更合适；
- 深度编辑涉及大量参数和频响曲线，大屏幕更直观；
- 八组场景可以保存在效果器中，并通过 MIDI 切换，因此设置完成后不必一直连接电脑。

代价也很明确：**单个旋钮当前控制什么，设备本身无法清楚显示**。作者用可自定义手势、LED 状态和 “一键恢复默认音量” 来缓解，但复杂配置仍依赖外部界面。

###### 2. 让设备 “告诉网页自己有什么”，可以减少版本错配

网页并未把 17 种效果及其参数写死，而是向效果器查询：有哪些效果、每个参数的范围和单位是什么、该显示什么提示，再动态生成控制界面。

这很重要，因为传统做法容易出现固件已新增参数、网页却还没更新的情况。这里把效果定义作为共同来源，用于：

- 生成设备固件；
- 生成网页控件；
- 构建测试台和分析文档。

因此，新增效果时通常不需要另外手工修改网页，**减少了同一信息在多处重复维护造成的不一致**。这是一种比 “功能多” 更有长期价值的软件工程设计。

###### 3. 测试尽量直接复用真实音频代码，而不是另写一个理想模型

项目可以把设备中的实际音频处理核心编译成电脑程序，让测试信号通过相同的处理函数、效果定义和编译选项。这样测到的不是另写的数学模型，而更接近固件真正执行的算法。

此外，测试被分成多个层次：

- 无硬件测试：检查 MIDI、网页、滤波器和效果算法；
- 文档分析：重新测量频响曲线，检查文档是否过时；
- 实机测试：检查模拟输入输出、主机版本与真实板卡是否一致；
- 双机回环：进一步验证设备间的完整信号链。

这种设计能较好发现算法错误和版本漂移。但电脑测试仍不能替代实机，因为编解码器、模拟电路、时序负载和丢采样只会在硬件环境中暴露。

##### 辩证思考

原文最有说服力的不是某种效果 “听起来更好”，而是其**工程一致性思路**：单一效果定义同时驱动固件、网页与测试；板型必须显式指定，固件文件名也带板型；文档曲线由程序重新测量。这些措施都针对真实且常见的错误 —— 刷错固件、界面落后于设备、测试模型与生产代码不一致 —— 因果关系清楚，也有具体实现支撑。

但文中对可靠性和效果表现的证明仍有限。README 反复标注部分效果 “已测量”，并列出了多种测试命令，却没有在所给内容中展示噪声、延迟、失真、动态范围、CPU 余量或实机测试结果。因此，能够确认的是**项目具备较系统的验证框架**，不能仅凭本文确认其音质、实时稳定性或模型还原度已经达到何种水平。尤其是主机端运行 “同一套算法”，只能证明数字运算较一致；它无法覆盖模拟前端、ADC/DAC、供电噪声以及满负载时是否丢采样。项目确实提供硬件测试来补足这一点，但文章没有给出测试结果。

其 “极简本体、复杂操作放网页” 的方向也依赖使用场景。对提前编辑好八组场景、演出时只需切换的人，这种设计很合理；对需要现场临时调整多个参数、又不愿连接手机或担心 WebMIDI 兼容性的人，无屏幕可能反而降低可控性。“网页可在手机运行、无需安装” 是原文主张，但具体浏览器和系统支持情况未说明，不能理解为所有手机都能无条件使用。

最后，这仍是一个带有实验性质的个人项目，而非完全成熟的产品方案：作者明确说明表达踏板接口目前只能读取数据，尚未真正控制效果；固件主要在 Linux 上构建，其他平台只是理论上可行；文档目录也自称不完善。**因此更准确的结论是：它展示了一套设计严谨、扩展性较强的数字效果器架构，但项目完整度、跨平台易用性和实际音频指标仍需代码、测量数据与长期实机使用进一步证明。**

## 结构化（1）

#### 一款由网页控制的开源数字吉他效果器

这是一个重新启动的数字吉他效果器项目：以 RP2354A 微控制器和 TI 音频编解码器为核心，音效全部由独立核心通过软件实时处理。项目放弃小屏幕和多旋钮，踏板本体只保留一个旋钮、一个脚踏开关和三个 LED，复杂编辑交给通过 USB MIDI 连接的网页应用。

##### 设计思路：简化踏板，把复杂操作搬到浏览器

旧版本曾配有 128×128 OLED 屏幕和两个旋钮，但用它们编辑 17 种效果并不方便，因此新版取消屏幕。

踏板默认操作如下：

- 脚踏开关短按：启用或旁路效果链
- 脚踏开关长按：打开调音器
- 旋钮旋转：调节主音量
- 按下旋钮：将音量恢复到初始值，方便在没有屏幕时 “找回基准”

这些功能并非写死。旋转、短按或长按旋钮，以及短按或长按脚踏开关，共五种操作，都可以在网页中重新分配，例如控制任意效果参数，或同时提高一种效果的混合比例、降低另一种效果的比例。

三个 LED 分别表示：

1. 异常状态：红色代表削波，琥珀色代表丢失采样；
2. 效果链启用或旁路；
3. 当前效果是否 “忙碌”，如噪声门正在压低声音、压缩器正在工作。

##### 网页应用：自动读取踏板能力，避免软件与固件脱节

WebMIDI 是一个无需安装的静态网页，手机也能使用，通过 USB MIDI 与踏板通信。

网页本身并不预先写死有哪些效果，而是向踏板查询。踏板会描述每种效果的参数、范围、单位和提示文字，网页再据此自动生成控制界面。因此：

- 新增效果时，通常不需要同步修改网页；
- 网页参数不会轻易与固件版本不一致；
- 用户可以自由决定哪些效果进入信号链，以及它们的先后顺序；
- 未加入信号链的效果不占用处理资源。

效果顺序会直接改变声音。例如，提升器放在延迟之前，与延迟放在提升器之前，会产生不同结果。音色栈、参数均衡器和箱体模拟还会直接绘制实际频率响应及相位响应，而不是只显示几个旋钮数值。

踏板闪存可保存**8 个场景**。每个场景包含完整的效果顺序和参数，可通过 MIDI Program Change（程序切换）调用，因此不用电脑也能借助廉价 MIDI 脚控器切换音色。

##### 软件结构：效果代码同时服务于固件、测试和网页

项目主要目录各有明确职责：

- **Hardware**：KiCad 电路板文件、外壳钻孔规则和 3D 打印内衬等；
- **Effects**：17 种效果，每种一个文件；
- **Audio**：双二阶滤波器、包络跟随器、低频振荡器（LFO）等 DSP 基础模块，以及音频处理循环；
- **Firmware**：USB、MIDI、场景管理和开发板引脚配置；
- **WebMIDI**：浏览器编辑应用；
- **scripts**：效果生成、数学查表和固件安全检查脚本；
- **Validation**：无需硬件和需要实物踏板的测试；
- **Documentation**：效果说明和测量结果。

效果代码不直接塞在固件目录中，是因为同一套代码要生成三类内容：踏板固件、测试平台和网页控制信息。这样可以减少重复实现和版本偏差。

##### 构建与刷写：必须明确选择硬件版本

作者只在 Linux 上实际构建过，但理论上 macOS 和 Windows 也可以，只要准备好：

- Git、Make、Python 3、CMake；
- 32 位 ARM 交叉编译环境；
- pico-sdk 和 TinyUSB，项目已通过子模块包含这两项。

项目支持两套硬件：

- `unified`：当前的一体化单板版本；
- `split`：较早的模块化双板版本。

用户必须把目标硬件写入`board.local`。构建系统不会自行猜测，以免生成能够正常编译、却不适用于手中硬件的固件。产物名称也会包含开发板类型，如`pedal-unified.uf2`，刻意不提供容易拿错的通用`pedal.uf2`。

刷写固件有三种方式：

- 通过 MIDI CC 20、数值 126，让运行中的踏板自动重启到 BOOTSEL 模式；
- 插入 USB 时按住旋钮，使其进入 BOOTSEL；
- 安装支持 USB 的`picotool`后，直接执行`make flash`。

进入 BOOTSEL 后，设备会显示为 USB 大容量存储器，将`.uf2`文件复制进去即可。

##### 测试原则：尽量测 “真实代码”，而不是另做近似模型

项目的核心测试思想是：桌面测试平台直接编译踏板使用的音频核心、效果文件和编译选项，只把硬件寄存器替换成普通内存。它不是对信号链的模拟，而是把同一套实际运算搬到电脑上运行。

主要测试包括：

- `make check`：无需硬件，检查 MIDI 数据封装、网页是否正常加载，以及双二阶滤波器的实际响应；
- `make check-effects`：向真实效果代码输入信号并检查输出；
- `make check-analysis`：重新测量文档中每种效果的曲线，发现文档结果是否已过时；
- `make check-hw`：配合信号发生器测试实物；
- `make check-analog`：把踏板输出接回输入，测试模拟通路；
- `make check-bench`：比较真实硬件与电脑端构建的计算结果；
- `make check-loop`：使用两台踏板互相连接测试。

这种设计使文档中的曲线来自实际测量，而不是手工绘制或理论推算。

##### 硬件演进：从模块化多板改为一体化单板

当前`usb-stomp`版本把**RP2354A**和**TI TAC5242**编解码器直接放在同一块板上，不再使用排线、子板或中间连接器。

主要接口包括：

- 6.35 mm 输入和输出接口；
- 一个表达踏板或远程脚踏开关接口；
- 3.5 mm Type A TRS MIDI 输入、输出；
- USB-C 和常见的 9V 效果器电源口；
- 一个带按键的旋转编码器和一个脚踏开关；
- 三颗 WS2812B 可寻址 LED。

表达踏板接口的硬件已经完成，固件也能读取数据，但目前只能由主机通过 SysEx 查询，还未真正绑定到效果控制。原因是不同表达踏板对触点定义并不统一，项目仍在收集实际设备信息。

旧版本采用模块化结构，由微控制器板、TI TAC5112 编解码器板、音频与电源接口板、主控制板组成，并通过 12 针、0.5 mm 间距的 FFC 排线传输电源、I²C 控制数据和 I²S 音频。模块化原本便于尝试不同外形并研究噪声隔离，但在需求明确后，一体化设计更简单。旧板仍能使用，固件也继续支持，主要用于测试。

##### 音频系统：17 种可排序效果，加上 3 个固定模块

系统提供**17 种可自由排列的效果**，另有三个始终存在、不能移除的模块：

- **Signal Chain**：输入增益、噪声门和主音量；
- **Settings**：USB 音频路由、MIDI 通道、LED 亮度和调音基准；
- **Expression Jack**：表达踏板类型及行程范围设置。

17 种效果包括：

- 两个**Tone**音色模块：可调低、中、高频，中频中心频率和 Q 值也可设置；
- **Preamp**：两级 12AX7 电子管模型，之后接 JFET 级；
- **Compressor**：可调压缩比、启动和释放时间，也可作为纯净提升器；
- **Boost**：带特殊折返失真的提升效果；
- **Klonlike**：模拟 Klon 类电路，包括 18V 电荷泵、锗二极管和随增益变化的干湿混合；
- **Rat Sketch**：基于 ProCo RAT/Aion FX Helios，包含三种削波模式；
- **Phaser、Flanger、Vibrato**：均以延迟线和 LFO 为基础；
- **Tape Echo**：基于 Maestro Echoplex 磁带延迟模型；
- **Reverb**：采用梳状滤波器和全通滤波器的传统结构；
- **Pitch**：通过改变延迟线读取速度移调，而非使用 FFT；反馈后每次重复都会继续移调；
- **Tremolo**：多种波形的音量调制；
- **Parametric EQ**：五段参数均衡，包括两段搁架和三段峰值滤波；
- **Frenchie Amp**：包含三极管、音色栈和功率放大级的小型音箱模型；
- **Test Tone**：输出已知频率和电平的正弦、三角、锯齿或噪声，用于踏板自测；
- **Cabinet**：按采样率模拟扬声器振膜的运动，可选择五种箱体，并调节驱动强度、共振和麦克风位置。

整体上，该项目通过 “极简实体控制＋浏览器深度编辑＋同源代码测试” 来平衡现场操作、功能复杂度和软件可靠性。

## 深度解读-口播（1）

### 2026-09-30 12:17:47

这份数字吉他效果器项目，最值得看的不只是它有十七种效果，而是一个设计选择：把演奏时需要的操作留在踏板上，把复杂编辑交给浏览器。与此同时，作者尽量让控制界面和测试，都以踏板真正运行的代码为依据。

这个项目是作者重新拾起的旧作。它用微控制器和音频编解码芯片处理声音，所有效果都由软件实现，并占用一个独立的处理器核心。

早期版本有一块小屏幕，还有两个旋钮。但作者发现，用一块一百二十八乘一百二十八像素的屏幕，加上两个旋钮，去编辑十七种效果，实在谈不上舒服。于是，新版干脆去掉了屏幕，只留下一个旋钮、一个脚踏开关和三颗指示灯。需要仔细调整时，再用浏览器，通过 USB 上的 MIDI 通信连接踏板。MIDI 在这里承担的是控制指令传输，而不是声音传输。

这不是简单地把操作都搬到电脑上。踏板仍然保留了演奏时最直接的控制。默认情况下，踩一下脚踏开关，就切换效果是否介入；长按进入调音器。旋钮控制总音量，按一下或长按旋钮，都能让音量回到初始值。

作者特别强调了这个“回到初始值”的动作。没有屏幕时，你不一定知道自己把音量转到了哪里，但至少需要一个不用看也能找回原点的办法。

不过，这些操作并没有被固定死。转动旋钮、短按旋钮、长按旋钮，以及脚踏开关的短按和长按，一共五种动作，都可以在网页里重新分配。旋钮可以控制某个效果的参数；一次按键，也可以同时提高一个效果的混合比例、降低另一个效果的混合比例。

也就是说，踏板负责让你顺手操作，浏览器负责告诉踏板，这些动作究竟代表什么。

接下来，理解这台效果器的关键，不是记住十七个效果的名字，而是理解“信号链”。

信号链就是吉他声音依次经过哪些处理，以及这些处理的先后顺序。这里的十七种效果，不会因为存在就自动参与处理。你必须把某个效果放进信号链，它才会运行。没有接入的效果，不占用效果处理的计算开销。

顺序也由你决定。提升音量的效果放在延迟前面，和放在延迟后面，并不是同一种结果。项目甚至准备了两套音色调节效果，让你可以把一套放在失真之前，另一套放在失真之后。

效果本身也有一些值得保留的细节。比如，作者喜欢的一种提升和失真效果，在增益开得很高、输出电平设得很低时，不只是把波形顶部削平，而是让超过一定程度的信号向下折返。这会产生不同于普通软削波或硬削波的谐波。

另一个例子是变调效果。它不是使用快速傅里叶变换来处理频谱，而是以不同速度读取延迟中的声音，再把两路声音平滑交接，避免读到末尾重新开始时产生咔嗒声。这样既会变调，也会带来延迟。加入反馈后，每一次回声还会再次变调。

这些设置可以保存成“场景”。一个场景包含信号链的排列，以及链内各项参数。踏板自身能保存八个场景，通过 MIDI 的程序切换指令调用。所以，编辑时需要浏览器，并不意味着演奏时也必须带着电脑。一个外部脚踏控制器，就可以用来切换场景。

但把复杂界面搬到浏览器，会带来另一个问题：网页和固件会不会各说各话？

这个项目的办法，是让网页先询问踏板，而不是自己预先写死所有效果的信息。踏板会报告有哪些效果、有哪些参数，以及参数范围、单位和说明文字。网页再根据这些信息生成控制界面。

因此，作者在踏板里增加效果时，不必再去网页里手工补上一套对应的控件。对于音色调节、参数均衡器和箱体模拟，网页还会显示频率响应曲线，帮助使用者理解设置如何改变声音，而不只是盯着几个旋钮的位置猜测。

这套思路在测试上走得更远：尽量测量真正运行的实现，而不是一个看起来相似的模型。

项目有一个能在电脑上运行的音频测试台。它使用踏板实际的音频处理代码、相同的效果定义和相同的编译选项，只把代码接触到的两个硬件寄存器区，替换成普通内存。测试台接收音频采样，再输出处理后的采样。

作者强调，这不是对信号路径的另一次模仿，而是把同一条信号路径搬到电脑上运行。这样测到的，才是踏板代码实际采用的运算。

文档里的效果曲线也来自测量。项目有专门的检查，会重新跑这些测量，发现曲线是否已经不再符合当前实现。另外，还有需要连接真实硬件的测试，用来检查模拟音频通路，以及实物踏板是否与电脑上的测试结果一致。

最后看硬件，这个项目也经历了一次从探索到收敛的变化。

旧版采用模块化结构。微控制器、音频芯片和接口分在不同电路板上，再通过排线连接。这样方便尝试不同的外形和布局。如今，作者把主要器件集中到一块板上，不再需要中间的子板、排线和连接器。旧板仍然能用，也仍然可以编译对应的固件。

新版还增加了 MIDI 输入输出，以及一个可以连接表情踏板或远程脚踏开关的接口。不过，这里要分清“硬件已经做好”和“功能已经完整可用”。表情踏板接口目前能在外部请求下读取数据，但还没有把读数接到实际的效果控制上。作者仍在借它了解不同表情踏板的接线方式，不能把它当成已经完成的实时控制功能。

最值得记住的，是这台踏板把演奏和编辑分开了：现场操作保持简单，复杂设置留给更合适的屏幕。更深一层，它让界面向设备询问真实能力，让测试运行真实代码，再用实物检查结果。这个项目的价值，不只是效果数量，而是这些环节怎样尽量保持一致。
