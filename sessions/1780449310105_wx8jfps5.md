Crabbox banner

**Warm a box, sync the diff, run the suite.**

Crabbox is a remote software testing and execution control plane for maintainers and AI agents. Lease fast managed cloud capacity, point at an existing SSH host, or use an agent sandbox provider — then sync your dirty checkout, run commands remotely, stream output, collect evidence, and release. Local edit-save-run loop, cloud-grade compute, agent-ready observability.

```
crabbox run -- pnpm test
```

Behind that one command: a Go CLI on your laptop, a Cloudflare Worker broker that owns provider credentials and lease state, and a managed or delegated runner.

```
your laptop                Cloudflare Worker            cloud provider
-------------              ------------------           --------------
crabbox CLI    -- HTTPS --> Fleet Durable Object  -->   Hetzner / AWS / Azure / GCP
   |                         lease + cost state              |
   |                                                         |
   +------------ SSH + rsync to leased runner <--------------+
```

- **CLI** — Go binary. Loads config, mints a per-lease SSH key, asks the broker for a lease, waits for SSH, seeds remote Git, rsyncs the dirty checkout (with a fingerprint skip when nothing changed), runs the command, streams output, releases.
- **Broker** — Cloudflare Worker plus a single Fleet Durable Object. Owns provider credentials, serializes lease state, enforces active-lease and monthly spend caps, and expires stale leases by alarm. Auth is GitHub browser login or a shared bearer token.
- **Runner** — a throwaway machine reachable over SSH on the primary port (default `2222`) plus configured fallback ports, prepared with Crabbox's sync/run prerequisites. Linux uses Ubuntu with cloud-init and `/work/crabbox`; native Windows uses OpenSSH, Git for Windows, and `C:\crabbox`. No broker credentials live on the box. Project runtimes (Go, Node, Docker, services, secrets) come from your repo's GitHub Actions hydration, devcontainer, Nix, mise/asdf, or setup scripts — not from Crabbox.

The data plane — SSH, rsync, command execution — always runs directly from the CLI to the runner. The broker only manages leases, cost, and observability.

Only `aws`, `azure`, `gcp`, and `hetzner` can be brokered through the Worker, and even those run direct from the CLI when no broker URL is configured. Every other provider always runs direct. A direct-provider mode (`--provider hetzner|aws|azure|gcp|proxmox` with local credentials) exists for debugging the broker itself or using private infrastructure.

For the full mental model, see How Crabbox Works. For the doc-to-code map, see Source Map.

#### Install

```
brew install openclaw/tap/crabbox
crabbox --version
```

No Homebrew? Grab a [GoReleaser archive](https://github.com/openclaw/crabbox/releases) for macOS, Linux, or Windows.

Laptop prerequisites: `git`, `ssh`, `ssh-keygen`, `rsync`, `curl`.

#### Quick start

Broker access is deployment-specific. Use a coordinator URL from your team, use direct-provider mode for a personal cloud account, or self-host the Worker broker with your own provider credentials and spend caps. See Getting started and Infrastructure for the setup paths.

Every lease has a stable `cbx_...` ID and a friendly crustacean slug (`blue-lobster`, `swift-hermit`, …). Either works wherever an `--id` is accepted. Use `--slug <name>` on fresh leases when a specific reusable slug helps, and `--label <text>` on `run` when the history entry needs a human-readable name.

#### Highlights

- **One-shot or warm workspaces.**`crabbox run` for fire-and-forget;`crabbox warmup` + `--id` for raw reusable leases, or `crabbox prewarm` when the box should be hydrated before the first test command. See warmup, prewarm, and run.
- **Named repo jobs.**`crabbox job run <name>` lets repos define warmup, optional Actions hydration, run command, and cleanup policy in `.crabbox.yaml`. See Jobs.
- **Local-first workspace sync.** No clean-checkout requirement. Tracked and nonignored files only, fingerprint skip on no-op runs, sanity checks against suspicious mass deletions, optional shallow base-ref hydration for changed-test workflows. See Sync.
- **Run observability.** Every coordinator-backed run gets an early `run_...`handle. Use `crabbox attach <run-id>` while it is active,`crabbox events <run-id>` for durable lifecycle/output events, and `crabbox logs <run-id>` for retained output after completion. See History and logs and Observability.
- **GitHub Actions hydration.**`crabbox actions hydrate` runs supported setup steps from the repo's workflow locally over SSH, so leased boxes get the same runtimes and tooling without GitHub write access. Use `--github-runner` only when setup needs full Actions semantics such as repository secrets, OIDC, service containers, or unsupported `uses:` steps. See Actions hydration.
- **Failure capsules.**`crabbox capsule from-actions <run-url>` captures a failing CI run into a portable, replayable bundle; `capsule replay` reruns it. See Capsules.
- **Checkpoints.** Save VM-or-workspace state and `restore` / `fork` from it, via workspace archives or provider-native snapshots/images. See Checkpoints.
- **Pond peer groups.** Leases that share a `--pond <name>` label form an emergent peer group with discovery (`pond peers`), an SSH-mesh of `ssh -L` forwards to members' `--expose` ports (`pond connect`), and bulk `pond release`. See Pond.
- **Brokered cloud with cost guardrails.** Maintainers and agents share infra without sharing provider tokens. Hetzner, AWS, Azure, and Google Cloud are the managed providers; per-lease and monthly spend caps reject over-budget leases. Providers fall back across compatible instance families when capacity or quota rejects a request. `crabbox usage` summarizes spend by user, org, provider, and type. See Coordinator,Capacity fallback, and Cost and usage.
- **Interactive desktop, browser, and code leases.**`--browser` provisions Chrome/Chromium for headless automation, `--desktop` provisions a visible UI with tunnel-only VNC takeover, and `--code` provisions code-server on managed Linux. `crabbox desktop click/paste/type/key` provide first-class input helpers; `desktop proof` captures metadata, screenshot, diagnostics, MP4, and a contact-sheet PNG in one publishable bundle. See Interactive desktop and VNC.
- **Authenticated web portal.** Browser login opens owner-scoped and shared lease/run views with run logs/events, WebVNC, code-server, and telemetry charts. `crabbox webvnc` / `crabbox code` bridge a lease into the portal;`crabbox share` grants a lease to a user or the owning org. See Portal.
- **Agent workspace evidence.** History, logs, events, telemetry, JUnit summaries, screenshots, recordings, artifacts, and PR publishing make autonomous work reviewable instead of only ephemeral terminal output. See Artifacts and Telemetry.
- **Stable timing records.**`--timing-json` on `run`, `warmup`, `prewarm`, and `actions hydrate` gives scripts one machine-readable sync/command/total timing schema across providers.
- **Hardened coordinator auth.** GitHub browser login, owner-scoped leases, admin-only routes, optional GitHub team allowlists, Cloudflare Access JWT verification, and service-token support keep normal use and operator automation separate. See Auth and admin and Security.

#### Configuration

Config resolves in order: flags → env → repo `.crabbox.yaml` → user `~/.config/crabbox/config.yaml` → defaults.

```
broker:
  url: https://broker.example.com
  provider: aws
  token: ...
class: beast
capacity:
  market: spot
  strategy: most-available
  fallback: on-demand-after-120s
  hints: true
aws:
  region: eu-west-1
  rootGB: 400
lease:
  idleTimeout: 30m
  ttl: 90m
ssh:
  key: ~/.ssh/id_ed25519
  user: crabbox
  port: "2222"
  # Ordered fallback ports tried after ssh.port; use [] to disable fallback.
  fallbackPorts:
    - "22"
```

Forwarded environment is intentionally narrow: `NODE_OPTIONS` and `CI`. Do not pass secrets as command-line arguments. For live-secret smoke tests, use `crabbox run --env-from-profile <file> --allow-env NAME` so Crabbox forwards only selected names and prints redacted presence/length metadata. For stale warm boxes, `--full-resync` (alias `--fresh-sync`) resets the remote workdir before syncing. For larger commands, use `--script <file>` or `--script-stdin` so the remote runner executes an uploaded file instead of a giant quoted shell string.

For binary or terminal-hostile output, use `crabbox run --capture-stdout <path>` or `--capture-stderr <path>`. Add `--preflight` for a remote capability snapshot, `--keep-on-failure` to SSH into the exact failed one-shot lease, or `--download remote=local` to copy a successful-run artifact back. Failed SSH-backed and Blacksmith delegated runs save local `.crabbox/captures/*.tar.gz` bundles by default. Captured files are not redacted by Crabbox.

Optional Tailscale reachability for managed Linux leases:

```
tailscale:
  enabled: true
  network: auto
  tags:
    - tag:crabbox
  hostnameTemplate: crabbox-{slug}
  authKeyEnv: CRABBOX_TAILSCALE_AUTH_KEY
  exitNode: mac-studio.example.ts.net
  exitNodeAllowLanAccess: true
```

Tailscale is a network plane, not a provider. `--tailscale` joins new managed Linux leases to the tailnet; `--network auto|tailscale|public` chooses how SSH and VNC tunnel commands resolve the host. Brokered mode uses Worker OAuth secrets to mint one-off keys; direct-provider mode reads the auth key from the configured env var. See Tailscale.

#### openclaw/crabbox 深度总结与解读

##### 一句话总结

**Crabbox 是一个“把本地代码同步到远程高性能环境并运行测试/命令”的工具，面向软件维护者和 AI Agent，核心价值是：本地开发体验 + 云端算力 + 可观测执行证据。**

---

##### 1. 深度总结

###### 核心问题

本地机器跑测试可能慢、环境不一致、算力不足；CI 又偏重、反馈慢、不方便交互。  
Crabbox 试图填补中间地带：

> 像本地一样 `crabbox run -- pnpm test`，但实际在远程云机器、沙箱或已有 SSH 主机上执行。

---

###### 核心架构

Crabbox 分三层：

| 组件 | 作用 |
|---|---|
| **CLI** | 本地 Go 命令行工具，负责配置、申请机器、同步代码、执行命令、拉取结果 |
| **Broker / Coordinator** | Cloudflare Worker + Durable Object，管理云厂商凭证、租赁状态、成本上限、鉴权 |
| **Runner** | 真正执行命令的远程机器、容器、沙箱或已有 SSH 主机 |

关键点：

- **控制面**：Broker 管机器租赁、成本、权限。
- **数据面**：CLI 直接通过 SSH / rsync 连 Runner。
- **云厂商凭证不下发到 Runner**，安全性更好。
- 支持 brokered 云资源，也支持 direct provider 本地直连。

---

###### 主要能力

###### 1. 远程运行命令

```bash
crabbox run -- pnpm test
```

自动完成：

1. 租机器；
2. 等 SSH 可用；
3. 同步本地 dirty checkout；
4. 执行命令；
5. 实时输出日志；
6. 收集证据；
7. 释放资源。

---

###### 2. Warm workspace

支持：

- 一次性运行；
- 预热机器；
- 保留可复用 lease；
- 失败后保留现场调试。

适合反复跑测试、调试复杂环境。

---

###### 3. 本地优先的代码同步

不是重新 clone 干净仓库，而是同步本地当前工作区：

- 只同步 tracked 和非 ignored 文件；
- 无变化时跳过同步；
- 防止异常大规模删除；
- 支持 full resync。

这使它更接近“本地编辑-远程运行”。

---

###### 4. 多 Provider 支持

支持大量执行环境：

- AWS / Azure / GCP / Hetzner；
- Proxmox；
- Static SSH；
- Docker / Apple Container；
- RunPod GPU；
- E2B、Modal、Railway、Daytona、Namespace 等沙箱；
- Blacksmith Testbox；
- Cloudflare Containers 等。

本质上 Crabbox 把各种“可 SSH 或可执行命令的远程环境”抽象成统一 testbox。

---

###### 5. 可观测性与证据

Crabbox 不只是跑命令，还强调“可复盘”：

- run id；
- logs；
- events；
- telemetry；
- JUnit summary；
- screenshots；
- recordings；
- artifacts；
- failure capsule；
- portal 查看；
- PR 发布证据。

这非常适合 AI Agent，因为 Agent 的行为需要被人类审计。

---

###### 6. GitHub Actions Hydration

Crabbox 可以复用 GitHub Actions 中的 setup 步骤，把远程机器配置成接近 CI 环境。

好处：

- 不需要手动维护另一套环境配置；
- 测试环境更接近 CI；
- 但复杂 Actions 语义仍可能需要真正 GitHub Runner。

---

###### 7. 成本与权限控制

Broker 管理：

- 活跃 lease；
- 月度预算；
- 单次租赁限制；
- provider fallback；
- 用户/组织用量统计；
- GitHub 登录；
- bearer token；
- team allowlist；
- Cloudflare Access JWT。

这说明 Crabbox 面向团队和自动化 Agent，而不仅是个人工具。

---

##### 2. 深入浅出解读

###### 可以把 Crabbox 理解成什么？

它像一个：

> “远程测试盒子调度器”。

你本地写代码，但不一定在本地跑。  
你只要说：

```bash
crabbox run -- go test ./...
```

它就帮你找一台强机器，把代码搬过去，跑完测试，把日志和结果带回来。

---

###### 它和 CI 有什么区别？

| 对比项 | CI | Crabbox |
|---|---|---|
| 触发方式 | push / PR 后触发 | 本地即时触发 |
| 环境 | 固定流水线 | 可租赁、可复用、可交互 |
| 反馈 | 较慢 | 更像本地命令 |
| 交互性 | 弱 | 可 SSH、VNC、code-server |
| 适用场景 | 正式验证 | 开发中快速验证、Agent 执行、调试 |

Crabbox 不是替代 CI，而是让你在 CI 前更快、更强、更可观测地验证。

---

###### 它和普通 SSH 跑命令有什么区别？

普通 SSH 是你自己准备机器、同步代码、跑命令、清理现场。

Crabbox 把这些变成标准流程：

- 自动租机器；
- 自动同步；
- 自动记录；
- 自动释放；
- 自动控成本；
- 自动收集证据；
- 支持多云和多沙箱。

所以它不是简单 SSH，而是“SSH + 云资源调度 + 测试工作流 + 可观测性”。

---

###### 它为什么适合 AI Agent？

AI Agent 需要：

1. 快速试错；
2. 跑大量测试；
3. 不暴露云凭证；
4. 出错后能复盘；
5. 结果能让人类审查。

Crabbox 正好提供：

- 隔离执行环境；
- 可租赁算力；
- logs/events/artifacts；
- failure capsule；
- portal；
- 成本上限；
- 权限隔离。

它给 Agent 一个“可控的远程工作台”。

---

##### 3. 核心价值

###### 对开发者

- 本地机器不够强时，用云端跑；
- 不想等 CI 时，本地触发远程测试；
- 失败后保留现场；
- 可以跑 Linux、Windows、macOS、GPU、容器等环境。

###### 对维护者

- 给贡献者或 Agent 提供统一测试环境；
- 不泄露 provider credentials；
- 有预算限制；
- 有日志和证据；
- 便于审计自动化行为。

###### 对团队

- 标准化远程测试；
- 降低环境漂移；
- 提高反馈速度；
- 支持交互式调试和可视化验证。

---

##### 4. 辩证思考

###### 优点

###### 1. 把“本地体验”和“云端能力”结合得很好

开发者仍然像在本地运行命令，但实际可以使用强大的远程资源。

###### 2. 架构安全边界清晰

Broker 管凭证，Runner 只执行任务。  
云厂商密钥不落到临时机器上，这是重要设计。

###### 3. 对 AI Agent 很友好

不仅能执行，还能留下证据。  
这比“Agent 在黑盒里跑完告诉你结果”更可信。

###### 4. Provider 覆盖广

它不是绑定某一家云，而是把多种远程执行环境统一起来。

###### 5. 成本意识强

有 active lease、monthly spend caps、usage summary。  
这对自动化执行尤其关键。

---

###### 风险与局限

###### 1. 系统复杂度较高

CLI、Worker、Durable Object、云厂商、SSH、rsync、provider 配置都要协同。  
对新用户来说，门槛不低。

###### 2. 依赖 SSH / rsync 模型

这很通用，但也意味着：

- Windows 支持会更复杂；
- 网络问题会影响体验；
- 大仓库同步仍可能有成本。

###### 3. 环境一致性仍需项目自己负责

Crabbox 不替你安装所有语言运行时。  
它依赖：

- GitHub Actions hydration；
- devcontainer；
- Nix；
- mise/asdf；
- setup scripts。

也就是说，它负责“盒子”，但盒子里具体装什么，仍是项目责任。

###### 4. Broker 是关键基础设施

如果团队依赖 brokered 模式，那么 Worker、认证、配额、云 provider 配置都成为运维对象。

###### 5. Agent 自动化可能带来成本和安全压力

虽然有成本控制，但 Agent 大规模运行测试、保留 lease、访问环境变量，仍需要严格策略。

---

##### 5. 我的判断

Crabbox 的定位很清晰：

> 它不是单纯 CI，不是单纯云主机租赁，也不是单纯 SSH 工具，而是面向人类开发者和 AI Agent 的远程执行控制平面。

它最适合：

- 大型项目；
- 测试耗时高的项目；
- 多平台验证；
- 维护者管理多个 Agent；
- 需要保留执行证据的团队；
- 希望在 CI 前快速验证的开发流程。

但如果只是小项目、测试很快、本地环境足够，Crabbox 可能显得过重。

---

##### 6. 精炼结论

**Crabbox 的本质：**

> 用统一 CLI 调度远程测试盒子，把本地改动同步过去运行，并把日志、成本、权限、证据都管起来。

**最大价值：**

> 让开发者和 AI Agent 拥有可控、可审计、可复用的云端执行环境。

**最大挑战：**

> 能力强，但系统复杂；适合有远程测试、算力、审计和 Agent 自动化需求的团队。

## 结构化（1）

### 2026-06-03 02:16:13

##### 主旨概括

Crabbox 是一个面向软件维护者和 AI Agent 的远程测试与执行平台：在本地写代码，然后把“未提交的改动”同步到远程机器上运行测试、收集日志和证据。它的核心体验是一条命令完成远程租机器、同步代码、运行命令、输出结果和释放资源，例如：`crabbox run -- pnpm test`。

---

##### 1. Crabbox 解决什么问题

Crabbox 的目标是把本地开发循环和云端算力结合起来：

- 本地继续编辑、保存代码；
- 远程使用更强的云机器或已有 SSH 主机执行测试；
- 自动同步当前工作区的改动，不要求代码必须提交；
- 实时输出运行日志；
- 保存运行证据，如日志、事件、截图、JUnit 摘要、录屏、制品等；
- 支持维护者和 AI Agent 共同使用。

典型用法：

```bash
crabbox run -- pnpm test
```

这条命令背后会完成远程机器租用、SSH 连接、代码同步、命令执行、日志流式输出和资源释放。

---

##### 2. 核心架构：CLI、Broker、Runner

Crabbox 主要由三部分组成：

###### CLI：本地命令行工具

CLI 是一个 Go 编写的本地二进制程序，负责：

- 读取配置；
- 为每次租用生成 SSH key；
- 向 Broker 请求远程机器；
- 等待 SSH 可用；
- 初始化远程 Git 工作区；
- 用 `rsync` 同步本地改动；
- 运行远程命令；
- 实时输出结果；
- 最后释放机器。

它还会做“指纹跳过”：如果本地文件没有变化，就避免重复同步。

###### Broker：Cloudflare Worker 调度层

Broker 由 Cloudflare Worker 和一个 Fleet Durable Object 组成，负责：

- 保存云厂商凭证；
- 管理租用状态；
- 控制活跃租用数量；
- 控制月度花费上限；
- 自动清理过期租用；
- 提供 GitHub 浏览器登录或共享 Bearer Token 认证。

重要的是：Broker 只负责租用、费用和观测，不直接传输代码和执行命令。

###### Runner：远程执行机器

Runner 是真正运行测试的远程机器，特点包括：

- 通过 SSH 访问，默认端口是 `2222`；
- 支持备用 SSH 端口；
- Linux 默认使用 Ubuntu 和 `/work/crabbox`；
- Windows 使用 OpenSSH、Git for Windows 和 `C:\crabbox`；
- 不保存 Broker 凭证；
- 项目所需环境由仓库自己的 GitHub Actions、devcontainer、Nix、mise/asdf 或 setup 脚本准备。

---

##### 3. 数据面与控制面分离

Crabbox 的一个关键设计是：代码同步和命令执行不经过 Broker。

- 数据面：CLI 直接通过 SSH、rsync 与 Runner 通信；
- 控制面：Broker 只管理机器租用、费用和运行状态。

这意味着：

- 代码不会通过 Cloudflare Worker 中转；
- Broker 不需要接触项目源码；
- 云资源凭证集中由 Broker 管理，使用者无需共享云厂商 Token。

---

##### 4. 支持的运行模式和云厂商

Crabbox 支持两类模式：

###### Broker 托管模式

目前可通过 Worker Broker 管理的云厂商包括：

- AWS；
- Azure；
- Google Cloud；
- Hetzner。

这些 provider 也可以在没有 Broker URL 时由 CLI 直接运行。

###### Direct 直连模式

其他 provider 一般由 CLI 直接连接或调用本地凭证，例如：

- Proxmox；
- Static SSH；
- Local Docker 容器；
- Apple Container；
- exe.dev；
- Namespace Devbox；
- Semaphore；
- RunPod；
- Daytona；
- Cloudflare Containers；
- E2B；
- Modal；
- Railway；
- Blacksmith Testbox；
- W&B Sandboxes 等。

目标平台支持 Linux、macOS、Windows，具体取决于 provider。

##### 5. 安装与快速开始

推荐通过 Homebrew 安装：

```bash
brew install openclaw/tap/crabbox
crabbox --version
```

如果不用 Homebrew，也可以下载 GoReleaser 提供的 macOS、Linux 或 Windows 压缩包。

本地依赖包括：

- `git`
- `ssh`
- `ssh-keygen`
- `rsync`
- `curl`

快速开始时，需要选择一种接入方式：

- 使用团队提供的 Broker URL；
- 使用个人云账号直连；
- 自托管 Cloudflare Worker Broker，并配置自己的云厂商凭证和费用上限。

##### 6. 租用标识：ID、slug 和 label

每个 lease 都有两个标识：

- 稳定 ID，例如 `cbx_...`；
- 易读 slug，例如 `blue-lobster`、`swift-hermit`。

二者都可以用于 `--id` 参数。

还可以使用：

- `--slug &lt;name>`：为新 lease 指定易读名称；
- `--label &lt;text>`：为一次 run 添加人类可读的历史记录名称。

---

##### 7. 主要功能亮点

###### 一次性运行与预热工作区

Crabbox 支持不同使用方式：

- `crabbox run`：一次性执行命令，适合快速测试；
- `crabbox warmup`：创建可复用远程机器；
- `crabbox prewarm`：先准备好远程环境，再执行测试。

例如可以先预热依赖环境，再多次复用同一台机器运行测试。

###### 仓库级 Job

可以在 `.crabbox.yaml` 中定义仓库任务：

```bash
crabbox job run <name>
```

任务可以包含：

- warmup；
- GitHub Actions hydration；
- run 命令；
- cleanup 策略。

###### 本地优先的代码同步

Crabbox 不要求干净工作区，只同步：

- Git 跟踪文件；
- 非 ignored 文件。

同时提供：

- 无变化时跳过同步；
- 防止异常大规模删除的安全检查；
- 可选浅层 base-ref hydration，用于变更测试场景。

---

##### 8. 可观测性：日志、事件和历史

对于通过 coordinator 支持的运行，Crabbox 会提前生成 `run_...` 运行句柄。

常用命令包括：

```bash
crabbox attach <run-id>
crabbox events <run-id>
crabbox logs <run-id>
```

作用分别是：

- `attach`：连接仍在运行的任务；
- `events`：查看持久化生命周期和输出事件；
- `logs`：查看完成后的保留日志。

这使得 AI Agent 或维护者不只依赖临时终端输出，而是可以事后审计运行过程。

---

##### 9. GitHub Actions Hydration

Crabbox 可以把仓库 GitHub Actions 中支持的 setup 步骤，在远程机器上通过 SSH 执行：

```bash
crabbox actions hydrate
```

这样远程 lease 可以获得与 CI 类似的运行环境，比如语言运行时和工具链。

但如果 setup 需要完整 GitHub Actions 语义，例如：

- 仓库 secrets；
- OIDC；
- service containers；
- 不支持的 `uses:` steps；

则需要使用 `--github-runner`。

---

##### 10. 失败复现、检查点和 Pond

###### Failure Capsules

Crabbox 可以把失败的 CI run 打包成可复现的 bundle：

```bash
crabbox capsule from-actions <run-url>
crabbox capsule replay
```

用途是把 CI 失败现场保存下来，之后重新运行。

###### Checkpoints

支持保存和恢复状态：

- 工作区归档；
- provider 原生快照；
- 镜像；
- fork/restore。

这适合保留昂贵环境或复杂测试现场。

###### Pond peer groups

多个带有同一 `--pond &lt;name>` 标签的 lease 会组成 peer group。

支持：

- `pond peers`：发现成员；
- `pond connect`：建立 SSH mesh；
- 批量释放 pond 内 lease。

##### 11. 费用控制与云资源管理

Broker 模式下，Crabbox 强调费用护栏：

- 云厂商凭证由 Broker 管理；
- 维护者和 Agent 不需要共享 provider token；
- 支持单次 lease 限制；
- 支持月度费用上限；
- 超预算请求会被拒绝；
- 云厂商容量或配额不足时，会在兼容实例规格之间 fallback；
- `crabbox usage` 可以按用户、组织、provider 和类型汇总花费。

托管 provider 包括：

- Hetzner；
- AWS；
- Azure；
- Google Cloud。

##### 14. 机器规格与实例类型

Crabbox 提供 class-based 机器规格，默认是 `beast`。

常见 class 包括：

- `standard`
- `fast`
- `large`
- `beast`

不同 provider 会映射到不同实例类型。

例如：

- Hetzner `beast` 可能从 `ccx63` 开始 fallback 到 `ccx53`、`ccx43`、`cpx62`、`cx53`；
- AWS Linux `beast` 可能使用 48xlarge 系列，并 fallback 到 32x、24x、16x；
- Azure `beast` 可使用 `Standard_D192ds_v6`、`Standard_D128ds_v6` 等规格；
- Cloudflare 默认使用 `standard-4`。

也可以通过以下方式固定规格：

```bash
--type
CRABBOX_SERVER_TYPE
```

Linux ARM 容量可通过以下参数选择：

```bash
--arch arm64
```

##### 15. 配置方式

配置优先级从高到低是：

1. 命令行 flags；
2. 环境变量；
3. 仓库 `.crabbox.yaml`；
4. 用户配置 `~/.config/crabbox/config.yaml`；
5. 默认值。

示例配置：

```yaml
broker:
  url: https://broker.example.com
provider: aws
class: beast

capacity:
  market: spot
  strategy: most-available
  fallback: on-demand-after-120s

aws:
  region: eu-west-1
  rootGB: 400

lease:
  idleTimeout: 30m
  ttl: 90m

ssh:
  key: ~/.ssh/id_ed25519
  user: crabbox
  port: "2222"
  fallbackPorts:
    - "22"
```

默认转发的环境变量非常有限，只包括：

- `NODE_OPTIONS`
- `CI`

不建议通过命令行传递 secrets。需要传 secrets 时，可用：

```bash
crabbox run --env-from-profile <file> --allow-env NAME
```

Crabbox 会只转发指定变量，并打印脱敏后的存在性和长度信息。

---

##### 16. Tailscale 支持

Crabbox 可为托管 Linux lease 加入 Tailscale 网络。

示例配置：

```yaml
tailscale:
  enabled: true
  network: auto
  tags:
    - tag:crabbox
  hostnameTemplate: crabbox-{slug}
  authKeyEnv: CRABBOX_TAILSCALE_AUTH_KEY
```

注意：

- Tailscale 是网络层，不是 provider；
- `--tailscale` 用于让新 Linux lease 加入 tailnet；
- `--network auto|tailscale|public` 控制 SSH 和 VNC 如何解析主机；
- Broker 模式下使用 Worker OAuth secrets 生成一次性 key；
- Direct 模式下从环境变量读取 auth key。

#### Crabbox 精炼解读：面向 AI / 产品开发 / 商业系统构建

> 项目一句话：**Crabbox 是一个“远程测试与执行控制平面”——把本地未提交代码同步到远端高性能/多环境机器，运行命令，收集证据，再释放资源。**

它解决的不是单纯 CI 问题，而是：  
**本地开发、云端算力、AI Agent 执行、可观测性、成本控制、环境复现之间的断裂。**

---

##### 1. 启发

###### 1.1 “本地编辑 + 云端执行”会成为 AI 开发基础设施的新范式

传统开发链路通常是：

```text
本地写代码 → 本地跑测试 / 推到 CI → 等待结果
```

Crabbox 代表的是另一种范式：

```text
本地写代码 → 同步 dirty checkout → 云端/沙箱跑命令 → 实时流式输出 → 收集证据
```

关键变化：

- 不要求代码已经 commit；
- 不强依赖完整 CI；
- 可以直接使用大规格云机器；
- 可以被人类开发者使用，也可以被 AI Agent 使用；
- 执行结果不仅是终端输出，而是 logs、events、JUnit、截图、录屏、artifact、telemetry 等结构化证据。

这对 AI 编程很重要，因为 Agent 需要的不只是“运行命令”，而是：

- 可租用的执行环境；
- 可复现的上下文；
- 可观察的过程；
- 可审计的结果；
- 可控的成本与权限边界。

---

###### 1.2 AI Agent 的核心瓶颈不是模型，而是执行控制平面

很多 AI coding 产品的问题不是不会写代码，而是：

- 没有可靠环境；
- 跑不动大测试；
- 无法复现用户机器状态；
- 没有安全的密钥隔离；
- 执行结果缺少证据；
- 失败后无法保留现场；
- 多个 Agent 并发执行时资源混乱。

Crabbox 的价值在于把这些问题抽象成一个“执行控制平面”：

```text
Lease → Sync → Run → Observe → Capture → Release
```

这可以看作 AI Agent 系统里的基础设施层。

---

###### 1.3 它不是 CI 替代品，而是 CI、Dev、Agent 之间的中间层

Crabbox 不只是“更快的 CI”。它更像：

- 本地开发者的远程 testbox；
- AI Agent 的执行沙箱；
- CI 失败的复现舱；
- 云资源租赁与成本控制层；
- 多 Provider 统一执行接口。

CI 通常是：

```text
push-driven
clean checkout
centralized pipeline
```

Crabbox 更偏：

```text
command-driven
dirty checkout aware
developer / agent initiated
interactive and observable
```

这使它可以填补一个很大的空白：  
**代码还没有进入正式 CI 前，如何高质量地验证、调试、复现和收集证据。**

##### 2. 高价值信息深挖

###### 2.1 架构设计：控制面和数据面分离

Crabbox 的架构很值得借鉴：

```text
Laptop CLI  -- HTTPS -->  Cloudflare Worker Broker  --> Cloud Provider
     |                                                   |
     |---------------- SSH / rsync / command ------------|
```

它把系统拆成两层：

###### 控制面

由 Cloudflare Worker + Durable Object 承担：

- 管理 provider credentials；
- 分配 lease；
- 记录成本；
- 限制并发；
- 设置月度预算；
- 过期清理；
- 记录运行历史和事件。

###### 数据面

由 CLI 直接连接远端 Runner：

- SSH；
- rsync；
- command execution；
- log streaming；
- artifact download。

这个设计的价值：

- Broker 不需要代理所有数据流，降低成本和复杂度；
- Provider 密钥不下发到 Runner；
- CLI 到 Runner 直连，性能更好；
- 控制面可以做权限、预算、审计；
- 数据面保持简单、标准、可调试。

可迁移到其他系统的模式：

> **敏感权限放控制面，重 IO 走直连数据面。**

---

###### 2.2 “Lease”是一个非常重要的产品抽象

Crabbox 不是直接暴露“云服务器”，而是暴露 lease：

```text
lease = 临时可执行环境 + 身份 + 生命周期 + 成本 + 可观测性
```

每个 lease 有：

- 稳定 ID；
- 可读 slug；
- TTL；
- idle timeout；
- provider；
- machine class；
- run history；
- cost state。

这比“创建一台云主机”更适合 AI/开发者产品。

因为用户真正需要的不是服务器，而是：

- 我能不能拿到一个环境？
- 能不能跑这段命令？
- 跑完有没有证据？
- 失败时能不能保留？
- 花了多少钱？
- 谁创建的？
- 能不能复用或释放？

这就是从 IaaS 资源抽象到 Developer Experience 抽象。

---

###### 2.3 Dirty checkout sync 是开发体验关键

Crabbox 强调：

- 不需要 clean checkout；
- 同步 tracked 和 nonignored files；
- 没有变化时 fingerprint skip；
- 防止可疑的大规模删除；
- 支持 full resync；
- 支持 shallow base-ref hydration。

这背后的产品洞察是：

> 开发者真正需要测试的是“当前工作区状态”，不是 Git 远端上的某个 commit。

这对 AI Agent 也同样重要，因为 Agent 通常会在工作区产生大量中间改动。  
如果每次都要 commit / push / 触发 CI，反馈回路会很慢。

---

###### 2.4 Actions Hydration：复用 CI 环境，而不是重写环境配置

一个非常高价值的设计是 `crabbox actions hydrate`。

它的作用是：  
把 GitHub Actions 中的 setup steps 在远端机器上执行，让 testbox 获得和 CI 类似的运行时环境。

这个设计很聪明，因为项目环境往往已经写在：

- GitHub Actions；
- devcontainer；
- Nix；
- mise/asdf；
- setup scripts。

Crabbox 不试图重新定义一套环境配置体系，而是复用已有资产。

启发：

> 新基础设施产品要尽量寄生在已有工作流上，而不是要求用户迁移到全新范式。

---

###### 2.5 Failure Capsules：把失败变成可携带资产

`capsule from-actions &lt;run-url>` 可以把失败的 CI run 捕获成一个可重放 bundle。

这背后的思想很重要：

```text
失败不是一段日志，而是一个可复现对象。
```

对 AI 产品尤其重要。  
因为 Agent 修 bug 时最需要的是：

- 失败上下文；
- 依赖环境；
- 输入状态；
- 命令；
- 证据；
- 可重放能力。

如果失败可以被封装为 capsule，那么 Agent 就能围绕“失败对象”循环工作，而不是只看日志猜测。

---

###### 2.6 证据化执行：从“我跑过了”到“这是证据包”

Crabbox 提供：

- logs；
- events；
- telemetry；
- JUnit summaries；
- screenshots；
- recordings；
- artifacts；
- desktop proof；
- PR publishing；
- run history。

这说明它不是只服务命令执行，而是服务“可信执行结果”。

未来 AI Agent 交付的关键不是：

> Agent 说它完成了。

而是：

> Agent 交付可验证的证据。

这会成为 AI 工程系统的核心能力。

---

###### 2.7 成本和权限是 Agent 基础设施的第一等公民

Crabbox Broker 支持：

- provider credentials centralized；
- active lease caps；
- monthly spend caps；
- per-lease cost state；
- usage summary；
- owner-scoped leases；
- GitHub login；
- service token；
- admin-only routes；
- GitHub team allowlist；
- Cloudflare Access JWT。

这说明一个成熟的 AI 执行平台必须同时回答：

- 谁可以创建资源？
- 可以创建多大机器？
- 最多花多少钱？
- 资源多久自动释放？
- 谁能查看日志？
- 哪些 secret 不应该泄露？
- Agent 和人类如何区分权限？

很多 AI coding sandbox 项目失败，不是因为技术跑不起来，而是因为这几个治理问题没有解决。

- [ ] 执行的命令；

- [ ] 关键日志；
- [ ] 测试结果；

- [ ] 截图；

- [ ] 是否有人工可审计入口。

这会让 AI Agent 从“聊天助手”变成“可审计执行者”。

---

###### 3.3 多 Provider 抽象清单

Crabbox 支持 AWS、Azure、GCP、Hetzner、Proxmox、SSH、Docker、E2B、Modal、RunPod、Namespace、Blacksmith 等大量 provider。

迁移经验：

- [ ] 统一成 provider interface；
- [ ] provider 能力要做 capability model；
- [ ] 不同 provider 支持不同 target：Linux / macOS / Windows；
- [ ] 不要假设所有 provider 都支持 snapshot；
- [ ] 不要假设所有 provider 都支持 desktop；
- [ ] 不要假设所有 provider 都支持 cost estimate；
- [ ] provider credentials 尽量不进入执行环境；

- [ ] 支持 class 抽象：standard / fast / large / beast；
- [ ] 允许用户用 provider-native type override；
- [ ] 网络平面，例如 Tailscale，不要和 provider 抽象混淆。

AI 执行系统必须内置成本控制：

- [ ] 每个 lease 有 TTL；
- [ ] 每个 lease 有 idle timeout；
- [ ] 每月预算上限；
- [ ] 每用户预算；
- [ ] 每组织预算；
- [ ] 每 provider 用量统计；
- [ ] 每 machine class 估算；
- [ ] 超预算拒绝创建；
- [ ] stale lease 自动清理；
- [ ] spot/on-demand fallback 策略；
- [ ] 记录谁创建了什么资源；
- [ ] 支持 usage summary；
- [ ] 支持管理员审计。

---

###### 3.5 安全清单

Crabbox 的安全设计值得借鉴：

- [ ] Provider token 不进入 runner；
- [ ] secret 不通过命令行传递；
- [ ] env forwarding 默认窄化；
- [ ] 只允许显式 allow 的 env；
- [ ] secret presence/length 可以显示，但内容红acted；
- [ ] 本地 capture 不自动 redaction，要提醒用户；

- [ ] org/team allowlist；
- [ ] service token 和 human auth 分离；

- [ ] 资源过期自动释放；
- [ ] 对共享 lease 有明确授权。

###### 3.6 开发者体验清单

Crabbox 的 DX 做得比较完整：

- [ ] 一个命令即可运行：`crabbox run -- pnpm test`
- [ ] 支持本地配置、仓库配置、环境变量、flags 多级覆盖；

##### 4. 反方与张力

###### 4.1 它可能会增加系统复杂度

Crabbox 引入了很多组件：

- CLI；
- Worker Broker；
- Durable Object；
- Runner；
- Provider credentials；
- SSH；
- rsync；
- cloud-init；
- Tailscale；
- portal；
- artifact/log/event storage；
- 多 provider 适配。

对于小团队来说，这可能过重。  
如果只是简单跑测试，GitHub Actions 或本地 Docker 可能足够。

张力：

```text
更强控制力 / 更好体验 / 更适合 Agent
vs
更高基础设施复杂度 / 运维成本 / 学习成本
```

---

###### 4.2 “复用 GitHub Actions hydration”不等于完全等价 CI

Actions hydration 是好设计，但仍然存在限制：

- 某些 Actions 语义不完全支持；
- repository secrets 可能不可用；
- OIDC 场景可能需要真实 GitHub Runner；
- service containers 可能不完全一致；
- CI 上的网络和权限上下文不一定能复现。

所以它适合“接近 CI 的远端测试”，但不能完全替代 CI。

---

###### 4.3 Dirty checkout sync 很方便，但也可能带来状态污染

同步本地工作区很符合开发直觉，但风险是：

- 本地临时文件可能影响测试；
- `.gitignore` 规则不严谨会导致遗漏；
- 非 tracked 文件处理需要谨慎；
- warm box 长期复用可能产生陈旧状态；
- 远端环境和本地认知不一致。

Crabbox 提供 full-resync、fingerprint、mass deletion sanity check 等机制，但这仍然是一个设计张力：

```text
快速增量开发体验
vs
干净、可复现、确定性的测试环境
```

---

###### 4.4 Broker 是治理中心，也可能成为信任中心

Broker 集中管理：

- provider credentials；
- lease state；
- cost caps；
- auth；
- observability。

这很好，但也意味着 Broker 成为关键基础设施。  
如果 Broker 出问题，整个团队的 remote execution 会受影响。

需要考虑：

- 高可用；
- 审计；
- disaster recovery；
- secret rotation；
- Durable Object 状态可靠性；
- Worker 平台限制；
- 企业合规要求。

---

###### 4.5 多 Provider 支持会带来维护负担

支持很多 provider 的优势是灵活，但挑战是：

- API 差异；
- 配额差异；
- 网络差异；
- 镜像差异；
- 启动速度差异；
- snapshot 能力差异；
- Windows/macOS/Linux 行为差异；
- provider 价格和可用性变化。

对于商业产品来说，多 provider 是卖点，但也是长期维护成本。

---

###### 4.6 AI Agent 使用时的安全边界更复杂

如果 Agent 可以创建远端机器、运行命令、访问 artifact、转发 env，那么风险显著增加。

需要额外考虑：

- Agent 是否能访问生产 secret？
- Agent 是否能发起网络扫描？
- Agent 是否能创建高成本资源？
- Agent 是否能读取其他用户 lease？
- Agent 是否能把证据外传？
- Agent 是否能绕过 broker 直连 provider？
- Agent 失败后保留现场是否会泄露敏感数据？

这类系统必须默认保守，而不是默认开放。

##### 5. 情境化落地

###### 5.1 如果你在做 AI Coding Agent

可以把 Crabbox 类似能力作为 Agent Runtime 的底座。

推荐抽象：

```text
Agent Task
  → create lease
  → sync workspace
  → run test/build/lint
  → collect evidence
  → diagnose failure
  → patch code
  → rerun
  → publish summary + artifacts
  → release lease
```

MVP 功能优先级：

1. 支持 SSH / Docker 本地 provider；
2. 支持 dirty checkout sync；
3. 支持 run ID 和 logs；
4. 支持 artifact capture；
5. 支持 keep-on-failure；
6. 支持 cost/TTL；
7. 支持 GitHub Actions hydration；
8. 支持 cloud provider；
9. 支持 web portal；
10. 支持 failure capsule。

关键产品指标：

- 首次运行耗时；
- sync 耗时；
- 测试成功率；
- 失败复现率；
- 每次任务成本；
- Agent 修复后 rerun 次数；
- artifact 完整率；
- 人类审查通过率。

---

###### 5.2 如果你在做企业内部开发平台

Crabbox 的定位可以是：

> 内部 Remote Dev/Test Execution Platform。

适用场景：

- 大型 monorepo 本地跑不动；
- 测试需要 Linux 大机器；
- macOS/iOS 构建资源稀缺；
- Windows 测试环境难维护；
- CI 排队太慢；
- 开发者想在提交前验证；
- AI Agent 需要安全执行环境。

落地建议：

```text
第一阶段：只接已有 SSH / Proxmox / Docker
第二阶段：接云 provider，并加预算控制
第三阶段：接 GitHub Actions hydration
第四阶段：接 portal、logs、events、artifact
第五阶段：开放给 Agent
```

不要一开始就做全 provider 矩阵。

---

###### 5.3 如果你在做 B2B SaaS

Crabbox 给出的商业启发是：  
“测试执行环境”本身可以产品化，但真正壁垒不只是算力，而是：

- 权限；
- 成本；
- 可观测；
- 证据；
- provider abstraction；
- failure replay；
- repo workflow integration；
- agent readiness。

潜在商业定位：

1. **AI Agent Execution Cloud**
   - 为各类 coding agent 提供安全执行环境。

2. **Remote Testbox for Developers**
   - 面向大型工程团队，提供高性能远端测试机器。

3. **CI Failure Replay Platform**
   - 把失败 CI 转换成可重放 capsule。

4. **Enterprise Sandbox Control Plane**
   - 企业统一管理开发/测试/Agent 沙箱。

5. **Interactive QA Cloud**
   - 提供浏览器、桌面、录屏、截图、WebVNC 的交互式测试环境。

###### 5.4 如果你在做开源工具

可学习的项目设计方式：


##### 6. 最值得提炼的底层模式

###### 模式一：Lease-based Execution

不要直接卖机器，而是提供“有生命周期的执行权”。

```text
resource → lease → run → evidence
```

---

###### 模式二：Control Plane / Data Plane Split

控制面管权限、预算、状态；数据面走直接连接。

```text
Control: auth, cost, lease state
Data: SSH, rsync, execution, streaming
```

---

###### 模式三：Evidence-first Agent Runtime

Agent 的输出不应该只是文本，而是可验证证据包。

```text
claim → logs → tests → artifacts → screenshots → telemetry → replay
```

---

###### 模式四：Workflow Hydration

不要重造用户已有环境定义，优先复用：

- GitHub Actions；
- devcontainer；
- Nix；
- mise/asdf；
- setup scripts。

---

###### 模式五：Warm Workspace

在一次性沙箱和长期开发机之间，提供中间形态：

```text
one-shot run
warmup lease
prewarm hydrated box
checkpoint / fork / restore
```

这对于 AI Agent 的多轮修复非常重要。

---

##### 7. 结论

Crabbox 的核心价值不只是“远程跑测试”，而是建立了一套适合人类开发者和 AI Agent 共用的执行基础设施：

```text
同步当前工作区
租用合适算力
安全运行命令
实时观察过程
收集可审计证据
控制权限和成本
失败可复现
环境可复用
```

如果你关注 AI 产品开发和商业系统构建，最值得带走的是：

> **未来 AI Agent 的竞争力，很大一部分会来自执行系统，而不是模型本身。**

Crabbox 展示的方向是：  
把执行环境、成本治理、安全边界、失败复现和证据交付产品化。  
这类“Agent Runtime Infrastructure”很可能成为下一阶段 AI 开发工具链的重要基础层。
