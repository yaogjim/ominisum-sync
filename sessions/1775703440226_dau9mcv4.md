为什么需要 Claude 托管代理

Claude

[messages API](https://platform.claude.com/docs/en/build-with-claude/working-with-messages) 是模型的直接入口：它接收消息并返回内容块。基于 messages API 构建的代理使用一个框架将 Claude 的工具调用路由到处理器并管理上下文。这带来了一些挑战：

- Harnesses 需要跟上 Claude 的步伐 – 我最近写了一篇博客
  [这里](https://claude.com/blog/harnessing-claudes-intelligence)专注于使用 Claude API 原语构建代理，以处理工具编排和上下文管理。但代理 Harnesses 编码关于 Claude 不能做。这些假设随着 Claude 变得更强大而变得过时，并且会
  [限制](https://rlancemartin.github.io/2025/07/30/bitter_lesson/)
  Claude 的性能。Harnesses 需要不断更新以跟上 Claude 的步伐。
- Claude 运行时间更长 – Claude 的
  [任务周期呈指数级增长](https://metr.org/time-horizons/), 已经在 METR 基准测试中超过了 10 人时的工作量。这给代理的基础设施带来了压力：它需要安全可靠，能够抵御长期任务中发生的基础设施故障，并支持扩展（例如，扩展到多个代理团队）。

应对这些挑战非常重要，因为我们预计未来的 Claude 将在数天、数周或数月内应对人类面临的最大挑战。The

[Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 是第一步，提供了一个出色的通用代理框架。Claude Managed Agents 是这一发展进程中的下一步：一个具备框架和托管基础设施的系统，旨在支持 Claude 在我们预期的工作时间范围内实现安全、可靠的执行。

关键概念

在入职过程中，需要理解三个核心概念：

- 代理 — 一种版本化的配置，包含代理的身份信息：模型、系统提示、工具、技能、MCP 服务器等。你只需创建一次，然后通过 ID 引用它。
- 环境 — 描述如何配置代理工具运行的沙箱的模板（例如，运行时类型、网络策略和包配置）。
- 会话 — 一种使用预创建的代理配置和环境的有状态运行。它从环境模板中提供一个全新的沙箱，挂载任何每次运行的资源（文件、GitHub 代码仓库），并在安全的保管库中存储认证信息（MCP 凭证）。

将代理视为一种配置，环境视为一个模板（该模板描述了你希望代理访问以执行代码的沙箱），而会话则是任何代理执行。一个代理可以有多个会话。

使用

查看

[docs](https://platform.claude.com/docs/en/managed-agents/quickstart) 此处:

- [SDKs](https://platform.claude.com/docs/en/api/client-sdks) – 这些是面向代码的：在你的应用中导入它们以在运行时驱动会话。六种语言支持托管代理：Python、TypeScript、Java、Go、Ruby、PHP。
- CLI – 面向终端的：每个 API 资源（agents、environments、sessions、vaults、skills、files）都被暴露为子命令。
- 常见模式 – 使用 CLI 进行设置，使用 SDK 进行运行时操作。代理模板是持久化的：您创建一个模板，存储它（例如，以 YAML 格式存储，其中包含模型、系统提示、工具、MCP 服务器、技能，存储在 git 中），并让 CLI 在部署流程中应用它。

## 通俗精炼（1）

### 2026-04-09 02:57:20

#### 启动 Claude 托管代理：一篇看懂

##### 一句话总结
Claude 托管代理，本质上是一个 “官方托管的智能体运行平台”—— 你负责定义代理的能力模板，系统负责提供运行框架和基础设施，让代理能更稳定地处理长任务、复杂任务和自动化任务。

##### 为什么它重要
传统基于 Messages API 自建代理，最大问题有两个：

###### 1. 自建框架很容易过时
开发者通常会在代理框架里预设 “模型能做什么、不能做什么”。但 Claude 能力进化很快，这些假设很快会失效，反而限制模型发挥。

###### 2. 长任务对基础设施要求更高
随着 Claude 可以处理越来越长周期的任务，代理系统必须更可靠、安全，还要能承受长时间运行中的故障、扩展和多代理协作。

一句话说：难点已经不只是 “怎么调模型”，而是 “怎么把模型稳定跑起来”。

##### Claude 托管代理解决什么
Claude Managed Agents 提供的是一套 “预构建 + 可配置 + 托管” 的代理系统：

###### 你负责定义
包括模型、系统提示词、工具、技能、代码库、MCP 服务等。

###### 系统负责托管
包括运行框架、沙箱环境、会话管理、安全存储、长期任务执行和基础设施可靠性。

这意味着，团队可以把精力更多放在 “业务流程设计” 和 “任务编排” 上，而不是反复造代理框架。

##### 三个核心概念
理解这个产品，抓住三个词就够了：

###### 代理（Agent）
一个可复用、可版本化的配置模板，定义代理是谁、有什么能力。

###### 环境（Environment）
代理运行所需的沙箱模板，比如运行时、网络权限、依赖包配置。

###### 会话（Session）
一次具体的任务执行。每次运行都会基于代理和环境创建新的沙箱，并挂载文件、代码库、凭证等资源。

可以简单理解为：

- Agent = 能力模板
- Environment = 运行模板
- Session = 一次执行实例

##### 常见使用场景
文章提到的典型场景，基本覆盖了企业智能体落地的主流方向：

###### 1. 事件触发自动执行
比如系统发现 bug，代理自动修复并发起 PR，全程无需人工介入。

###### 2. 定时任务
比如每天自动生成 X、GitHub 或团队工作简报。

###### 3. 人触发、代理交付
比如在 Slack 或 Teams 中交办任务，让代理产出演示文稿、表格、应用等结果。

###### 4. 长周期复杂任务
尤其适合研究、内容处理、工程探索这类需要持续运行的任务。

##### 如何开始使用
上手方式比较直接：

###### CLI 快速接入
官方提供开源技能`claude-api`，更新 Claude Code 后运行对应命令即可完成 onboarding。

###### SDK 与 CLI 配合
- CLI 适合创建和管理代理、环境、会话等资源
- SDK 适合在业务系统中驱动运行时调用

官方已支持多种语言，包括 Python、TypeScript、Java、Go、Ruby、PHP。

##### 它的设计思路
这套系统的核心设计，不是去固化一种代理框架，而是把三个部分拆开：

###### 大脑
Claude 及其推理框架

###### 手
沙箱和工具执行系统

###### 过程记录
会话事件日志

这样做的好处是：
- 各模块耦合低
- 某一部分故障不会拖垮全部
- 更容易替换、升级和扩展
- 更适合未来多代理和长期任务场景

本质上，这是把 “智能体能力问题” 升级为 “基础设施产品问题” 来解决。

##### 最后的判断
这篇文章释放出的核心信号是：

###### Claude 托管代理，不只是一个 SDK 升级
它更像是把 “智能体” 从开发框架，提升为 Claude API 里的基础能力单元。

###### 对产品和企业的意义
它降低了企业构建智能体系统的门槛，也让智能体从 “demo 级能力” 更接近 “生产级执行系统”。

###### 对未来的价值
如果未来 AI 真要承担跨天、跨周、跨月的复杂任务，那么托管代理这类能力，很可能会成为智能体产品化的关键基础设施。

##### 结论
如果用产品语言概括，Claude 托管代理做的事就是：

**把 “搭智能体” 从工程拼装题，变成配置化、托管化、可规模化的产品能力。**

它的真正价值不在 “能不能做一个代理”，而在于：  
**能不能让代理长期、稳定、安全地真正干活。**

#### 启动 Claude 托管代理：对产品经理最有价值的部分

这篇文章真正传递的，不是一个 “新工具发布”，而是一个更关键的信号：

以前大家比谁模型更强；现在开始比谁能把一个任务稳稳做完，持续做、自动做、规模化做。

---

##### 一句话抓重点

**Claude Managed Agents = 把 “会思考的模型” 包装成 “能长期稳定干活的数字员工”。**

它解决的核心不是聊天，而是三件事：

- 让代理少依赖你手写的大量编排逻辑
- 让代理能跑更久、更稳、更安全
- 让代理从一次次调用，升级成可复用、可运维、可审计的任务系统

对产品经理来说，这意味着：

**AI 功能设计，要从 “回答得好” 升级到 “任务闭环做得好”。**

##### 这篇文章最值得你记住的 4 个判断

###### 1. Agent 的瓶颈，越来越不在模型，而在 “运行层”

文章反复强调一个现实：

- `messages API`只是入口
- 真正麻烦的是工具调用、上下文管理、权限、长任务可靠性、失败恢复、扩展到多代理协作

这很像产品发展中的典型阶段：

- 0 到 1，拼能力演示
- 1 到 10，拼系统稳定性
- 10 到 100，拼组织化交付

**启发：**
如果你还把 AI 产品理解成 “接个大模型 + 写个 prompt”，那产品认知已经落后一代了。未来真正拉开差距的，是 “任务基础设施”。

你在规划 AI 产品路线图时，需要单独设计这层：

- 任务状态管理
- 权限与审计
- 人机交接点
- 长任务容错
- 多工具编排
- 结果验收机制

---

###### 2. “模板化代理” 会成为企业 AI 产品的主流交付方式

文中把核心概念拆成：

- `Agent`：身份配置
- `Environment`：运行沙箱模板
- `Session`：一次真实执行

这个拆法非常重要。它本质上是在把 AI 能力产品化、工程化、资产化。

对 PM 的意义很直接：

###### 你以后设计的，不该只是一个 “AI 助手”
你更该设计成：

- 一套可版本化的代理模板
- 一组针对场景的环境权限配置
- 一条条可观测、可回放、可追责的任务会话

这会带来两个产品机会：

###### 机会 A：把 AI 从功能变成 “岗位”
比如：

- 增长情报代理
- 客诉归因代理
- PRD 审校代理
- 竞品监控代理
- Bug 修复代理

用户买的不是 “一个 AI 按钮”，而是 “一个持续工作的角色”。

###### 机会 B：把 AI 从一次性体验变成 “持续运营系统”
比如：

- 每天定时跑简报
- 监控某个事件自动出动作
- 长周期追踪一个主题并持续更新结论

这类产品更容易形成留存，因为它进入了用户的工作流。

---

###### 3. 真正有商业价值的 Agent，优先长在 “三类任务” 上

文章给了几类用例，我建议你用产品视角重新归类：

###### A. 事件触发型
例子：发现 bug，自动写补丁并提 PR。

适合特点：

- 输入结构化
- 触发条件明确
- 验收标准清楚
- 价值能快速量化

这是最适合先落地的企业场景。

**你可以优先找：**
- 告警处理
- 数据异常排查
- 工单分类与分发
- 销售线索清洗
- 合规检查

这类场景的优势是：ROI 容易算，组织阻力低。

---

###### B. 定时执行型
例子：每日简报、GitHub 动态汇总、社媒监控。

适合特点：

- 高频重复
- 信息分散
- 人工整理成本高
- 结果格式相对稳定

这是最容易让用户感知 “AI 真在替我省时间” 的场景。

**适合做成产品里的标配能力：**
- 晨报 / 周报
- 市场监测
- 客户舆情摘要
- 销售机会雷达
- 行业政策追踪

这类能力很容易成为使用习惯入口。

---

###### C. 发射后不管型
例子：Slack 发一句任务，最后收回表格、PPT、应用原型。

这是最接近用户心中 “智能代理” 的形态，也是最容易做出惊艳感的形态。

但产品上要非常小心，重点不在酷，而在交付控制：

- 任务边界清不清楚
- 中途是否可插入反馈
- 输出结果能否验收
- 失败后如何补救
- 成本是否可控

**建议：**
这类场景不要一开始就追求全自动。先做成：

- 自动执行 + 中间检查点
- 自动生成 + 人工确认后提交
- 自动草稿 + 人工最终发布

这样更容易落地。

---

##### 这篇文章背后的一个大趋势：AI 产品正在 “服务化”

Managed Agents 的本质，其实和云计算很像。

以前你自己搭服务器；
现在云厂商帮你托管。

以前你自己写 agent harness；
现在平台开始托管 agent 的运行层。

这意味着 AI 产品会出现一次明显分层：

###### 底层：模型
负责推理、生成、理解。

###### 中层：代理运行基础设施
负责权限、工具调用、长任务执行、状态管理、日志、可靠性。

###### 上层：场景产品
负责工作流、验收标准、角色定义、业务集成、组织落地。

**对产品经理最大的提醒：**
你不需要每一层都自己做。  
未来更大的价值，常常不在 “造轮子”，而在：

- 选对底层能力
- 设计清楚任务边界
- 连接真实业务流程
- 定义结果质量标准

---

##### 你在做 AI 产品时，最该调整的 5 个设计习惯

###### 1. 从 “对话流” 切到 “任务流”
很多 AI 产品还停留在聊天框思维：

- 用户输入
- AI 回答
- 结束

Managed Agents 提醒你，真正高价值的是任务流：

- 任务触发
- 资源挂载
- 权限授予
- 执行中状态
- 失败重试
- 结果交付
- 审计回放

**实操建议：**
你下一版 PRD 里，至少补上这 6 个字段：

- 触发方式
- 任务输入
- 可用工具 / 数据源
- 中间状态
- 完成标准
- 失败处理策略

---

###### 2. 把 “权限设计” 提前到产品定义阶段
文中把环境和沙箱讲得很重，这很对。  
因为 agent 一旦真开始干活，权限就是产品边界。

你要尽早定义：

- 能访问哪些系统
- 能读哪些文件
- 能否联网
- 能否写入外部系统
- 哪些动作必须人工确认

**一句实话：**
很多 Agent 产品死掉，不是因为不聪明，是因为不敢放权；不敢放权，是因为权限设计从一开始就没做好。

---

###### 3. 把 “长任务” 当成独立产品问题
长任务不是 “把超时时间调大” 这么简单。

它会引出整套新问题：

- 用户会不会忘记自己发过这个任务
- 执行到一半失败怎么办
- 中间结果要不要可见
- 多天任务的上下文如何保持
- 成本怎么封顶

**适合加的产品能力：**
- 进度播报
- 阶段性 checkpoint
- 异常通知
- 人工接管
- 任务回放
- 结果版本对比

这类能力平时看起来不性感，真上线时就是生死线。

---

###### 4. 把 “代理模板” 当成产品 SKU 来管理
文中说 agent 是版本化配置，这一点对商业化很关键。

以后你的产品很可能不是一个统一助手，而是一组模板：

- 面向销售的代理模板
- 面向运营的代理模板
- 面向研发的代理模板
- 面向管理层的代理模板

每个模板差异在于：

- system prompt
- 工具权限
- 数据源
- 输出格式
- 风险控制级别

**这很适合做成：**
- 行业方案包
- 角色包
- 企业定制模板
- 高级版功能层级

这直接对应定价和交付方式。

---

###### 5. 评价 AI 产品时，别只看成功率，要看 “闭环率”
传统 AI demo 容易看 “回答好不好”；  
真正的 agent 产品更该看：

- 任务发起率
- 完成率
- 自动完成率
- 人工介入率
- 重试率
- 验收通过率
- 单任务成本
- 单任务节省时间

**尤其重要的是：**
用户到底有没有因为它少开一次会、少写一份报告、少盯一个后台、少切五个系统。

这才是产品价值。

---

##### 如果你是产品负责人，可以立刻做的 3 个动作

###### 1. 先挑 “高频、规则明确、可验收” 的任务做托管代理试点
优先级建议：

1. 每日 / 每周简报
2. bug triage 或研发辅助流程
3. 市场 / 舆情 / 竞品监测
4. 销售线索整理
5. 客服工单预处理

这类任务更容易在 2~4 周内做出结果。

---

###### 2. 用 “Agent / Environment / Session” 重画你的产品架构
把你现有 AI 功能拆一遍：

- 哪些属于角色定义
- 哪些属于运行环境
- 哪些属于具体任务执行
- 哪些是持久配置
- 哪些是一次性资源

你会很快发现很多耦合点，也会更容易识别未来可复用模块。

---

###### 3. 给每个 Agent 设计一张 “任务责任卡”
建议固定包含：

- 它负责什么
- 它不负责什么
- 它能调用什么工具
- 它需要哪些权限
- 它的输出长什么样
- 什么情况下必须找人

这张卡非常适合拿来对齐产品、研发、设计、法务、运营。

---

##### 最后一句判断

这篇文章的参考价值，在于它让你看清一件事：

**Agent 产品的下一阶段，不是更像聊天机器人，而是更像一个可管理、可审计、可持续交付的工作系统。**

如果你是资深产品经理，现在值得关注的重点已经很明确：

- 少纠结单次回答是否惊艳
- 多设计任务如何闭环
- 少沉迷 prompt 技巧
- 多建设运行机制
- 少把 AI 当功能点
- 多把 AI 当生产单元

这样做，产品会更容易从 “能演示” 走到 “真落地”。
