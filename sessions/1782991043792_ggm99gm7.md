**知识要点**

## 解读（1）

### 2026-07-02 11:16:11

#### 如何构建云软件工厂：规范驱动开发

##### 一、深度总结

这篇文章讲的是：**当 AI 编码代理无法一次性解决复杂需求时，应该先让它写“规范”，再让它写代码。**

作者正在构建一个“云软件工厂”，目标是把软件开发生命周期自动化。上一篇文章中，流程是：

```text
Issue → 分诊 → 实施 → PR
```

这个流程适合简单 bug、小功能。但遇到复杂、模糊、涉及产品判断的问题时，直接让 AI 写代码容易失败。

因此作者新增了一个流程：

```text
Issue → 分诊 → 写规范 → 人类审查规范 → 实施 → PR
```

核心变化是增加了一个 **Spec Agent，规范代理**。

---

##### 二、关键机制

###### 1. 分诊代理判断问题类型

分诊代理会根据 issue 情况打标签：

| 问题类型 | 标签 | 后续动作 |
|---|---|---|
| 简单、清晰 | `ready-to-implement` | 直接实现 |
| 复杂但符合路线图 | `ready-to-spec` | 先写规范 |
| 信息不足 | `needs-info` | 请求补充 |
| 不符合当前方向 | 待处理 | 暂不实现 |

判断依据主要有两个：

1. 是否符合项目的 `roadmap.md` 和 `vision.md`
2. 是否足够复杂或模糊，需要先定义清楚

---

###### 2. 什么问题需要写规范？

作者区分了两类情况：

###### 模糊性

指一个需求有多种产品或技术实现方式，需要人类判断哪种更合适。

例如：

> “给图片编辑器增加智能增强功能。”

这可能是：

- 自动调亮度
- 自动去噪
- 自动裁剪
- AI 风格化
- 一键美化

如果不先定义，AI 很可能做偏。

###### 复杂性

指实现超过几百行代码，涉及较多架构、状态管理、组件协作。

这种问题即使不模糊，也需要提前设计。

---

###### 3. Spec Agent 生成两份规范

当 issue 被标记为 `ready-to-spec` 后，GitHub Action 会启动 Spec Agent，生成两个文件：

```text
specs/issue-xxx/PRODUCT.md
specs/issue-xxx/TECH.md
```

###### `PRODUCT.md`

定义产品行为。

它回答：

- 用户能做什么？
- 交互流程是什么？
- 边界情况如何处理？
- 成功标准是什么？

###### `TECH.md`

定义技术实现。

它回答：

- 改哪些模块？
- 数据结构怎么设计？
- 代码如何组织？
- 有哪些测试？
- 如何避免破坏旧功能？

---

###### 4. 人类需要参与审查规范

作者强调：AI 生成的规范只是初稿。

更好的做法是：

```text
AI 生成规范 → 人类本地审查 → 与 AI 反复追问和修改 → 确认后再实施
```

也就是说，人类不再直接盯着代码细节，而是先把控方向和约束。

确认规范后，再把 issue 标记为可实施，Implementation Agent 会根据规范写代码。

---

##### 三、深入浅出解读

这套方法的本质是：

> 不要让 AI 直接“猜着写代码”，而是先让 AI “写清楚要做什么、怎么做”。

可以类比成盖房子：

- 简单修门锁：工人可以直接去修
- 新建一层楼：必须先画图纸
- 图纸不清楚：施工一定返工

这里的：

| 软件工厂概念 | 类比 |
|---|---|
| Issue | 业主需求 |
| Triage Agent | 项目经理 |
| Spec Agent | 产品经理 + 架构师 |
| PRODUCT.md | 产品说明书 |
| TECH.md | 施工图纸 |
| Implementation Agent | 工程队 |
| PR | 完工交付 |

作者要解决的不是“AI 会不会写代码”，而是：

> 如何让 AI 在复杂任务中少走偏、少返工、可控地交付。

---

##### 四、真正有价值的点

###### 1. 把 AI 编码从“聊天模式”变成“流程模式”

很多人用 AI 写代码是：

```text
我提需求 → AI 写代码 → 我发现不对 → 继续改
```

这很容易失控。

作者的方案是：

```text
需求 → 分类 → 规范 → 审查 → 实施 → 验证
```

这更像真实软件工程。

---

###### 2. 把隐性判断显性化

复杂需求失败，往往不是因为代码写不出来，而是因为这些问题没说清：

- 到底要服务哪个用户场景？
- 哪些情况算成功？
- 哪些边界不做？
- 技术债能否接受？
- 是否符合路线图？

`PRODUCT.md` 和 `TECH.md` 的价值，就是把这些隐性判断写下来。

---

###### 3. 人类角色从“写代码”转为“审规范”

这很关键。

未来开发者不一定亲自写每行代码，而是更像：

- 审需求
- 审方案
- 审边界
- 审测试
- 审结果

AI 负责执行，人类负责判断。

---

##### 五、热门回复的关键提醒

###### 回复 1：不能只让模型判断“是否符合规范”

有人指出：

> 让另一个模型读规范和 diff，然后说“符合”，这只是第二意见，不是真正验证。

更可靠的方式是：

> 规范里要写清楚哪些测试能证明它被实现了，然后验证这些测试是否通过。

也就是说，好的规范不应只是描述，还应包含可验证标准：

```text
功能应该如何表现？
用什么测试证明它正确？
哪些测试必须通过？
```

否则“符合规范”会变成模型之间互相背书。

---

###### 回复 2：复杂需求的难点本身就是写不出清晰规范

另一条回复更尖锐：

> 规范驱动开发有效，直到规范本身成为瓶颈。

复杂功能之所以复杂，往往正是因为：

- 产品方向不确定
- 用户场景没验证
- 技术取舍困难
- 边界情况很多
- 利益相关者意见不一致

这时写一份好规范本身可能就是一个两周项目。

所以 Spec Agent 不能神化，它只是辅助，不是魔法。

---

##### 六、我的辩证思考

###### 1. 规范驱动开发很适合 AI，但不能替代产品判断

AI 很擅长整理、拆解、生成方案。

但它不天然知道：

- 什么对业务最重要
- 用户真正需要什么
- 哪些取舍符合公司战略
- 哪些复杂度值得承担

所以，AI 可以写规范草稿，但最终拍板仍然需要人。

---

###### 2. 规范越清楚，AI 越强；规范越模糊，AI 越危险

AI 编码不是怕任务大，而是怕目标不清。

如果规范清楚：

```text
输入是什么
输出是什么
边界是什么
测试是什么
```

AI 可以非常高效。

但如果只是说：

```text
做一个更好的编辑体验
```

AI 很容易看似完成，实际偏题。

---

###### 3. 最关键的不是“生成规范”，而是“让规范可验证”

一份好规范应该包括：

- 用户行为
- 技术方案
- 非目标
- 边界情况
- 验收标准
- 测试清单

否则规范只是文档，不是工程约束。

真正强的流程应该是：

```text
规范 → 测试 → 实现 → 自动验证
```

而不是：

```text
规范 → 实现 → AI 判断是否符合
```

---

###### 4. 这套流程适合中大型项目，不一定适合所有场景

对于小 bug、小需求，直接实现更高效。

但对于以下情况，规范驱动很有价值：

- 多模块改动
- 新功能设计
- 架构调整
- 用户体验变化
- 高风险代码
- AI 容易误解的需求

所以最佳策略不是所有问题都写规范，而是：

> 简单问题快速做，复杂问题先设计。

---

##### 七、一句话结论

**云软件工厂的核心不是让 AI 直接替你写代码，而是建立一套“分类、规范、审查、实现、验证”的自动化协作流程，让 AI 在明确约束下稳定交付。**

##### 主旨概括

本文介绍了“云软件工厂”系列的第二步：在自动化开发流程中加入 **规范驱动开发（Spec-driven Development）**。核心目标是让 AI 工厂不仅能处理简单问题，也能通过生成产品规范和技术规范来处理复杂、模糊的问题。

---

##### 1. 从简单流程到更完整的软件工厂

上一篇文章中，作者构建了一个基础流程：

> **分类（Triage） → 实施（Implementation）**

这个流程适合处理：

- 简单缺陷修复
- 小功能开发
- 范围明确、可以一次性完成的问题

处理方式是：分类代理先判断问题质量，必要时提出澄清问题；如果问题足够明确，就交给实施代理生成草稿 PR。

但这个流程不适合：

- 产品方向不清的问题
- 技术实现路径很多的问题
- 代码改动较大的复杂任务

因此，作者在这篇文章中引入了新的 **Spec 代理**。

---

##### 2. 新增 Spec 代理：处理复杂或模糊问题

作者为问题分类增加了新的判断路径：

- **问题简单**：打上“可立即实施”标签，交给实施代理处理
- **问题复杂但符合路线图**：打上 `ready-to-spec` 标签，触发 Spec Agent
- **问题信息不足或有歧义**：打上 `needs-info` 标签
- **其他情况**：标记为“待实现”

其中，`ready-to-spec` 是本文重点优化的步骤。

Spec 代理的作用是：在真正写代码前，先生成清晰的规范，让后续实现更稳定、可控。

---

##### 3. 如何判断问题是否需要 Spec

作者给示例图像编辑器项目新增了两个文件：

- `roadmap.md`：描述产品接下来计划构建什么
- `vision.md`：描述产品长期愿景和发展方向

分类代理会根据这两个文件判断问题是否符合项目方向。

需要进入 Spec 流程的问题通常具备两个特征：

###### 1）存在歧义

也就是同一个需求可能有多种产品或技术实现方式，并且这些方式差异明显，需要人来判断哪种更合适。

例如：  
如果用户提出“希望图片编辑器支持更好的导出功能”，这可能意味着：

- 支持更多格式
- 提高导出速度
- 增加压缩选项
- 支持批量导出

这类问题就需要先写清楚产品规范。

###### 2）具备复杂性

作者给出的简单判断标准是：

> 如果实现可能超过几百行代码，就属于复杂任务。

这类任务不适合直接交给实施代理一次性完成，而应该先生成规范。

---

##### 4. Spec 动作会生成两个核心文档

当问题被打上 `ready-to-spec` 标签后，会触发一个新的 GitHub Action，并调用 Spec 代理。

这个动作会生成两个规范文件：

###### `PRODUCT.md`

用于定义产品行为，回答“用户最终会看到什么、功能应该如何表现”。

它主要面向产品需求，例如：

- 功能目标是什么
- 用户如何使用
- 边界情况如何处理
- 期望的交互行为是什么

###### `TECH.md`

用于定义技术架构和代码结构，回答“工程上应该如何实现”。

它主要面向技术实现，例如：

- 应改动哪些模块
- 数据结构如何设计
- 代码组织方式是什么
- 需要注意哪些技术约束

这两个文件会被放在与 GitHub issue 编号关联的 `specs` 目录下。

---

##### 5. 人类仍需要参与规范审查与迭代

作者强调，Spec 代理生成的是初始版本，通常还需要人工进一步审查和调整。

推荐做法是：

1. 将规范拉取到本地工作区
2. 与代理进行交互式修改
3. 确保规范与人的预期一致

作者提到可以使用类似 Matt Pocock 的 `/grill-me Skill` 工具来帮助审查规范。

当规范确认无误后，可以：

- 让代理把原始 issue 标记为“可实施”
- 或者直接在 GitHub 中手动标记

随后，实施代理就会根据这些规范开始开发。

---

##### 6. 实施代理也需要更新：按规范写代码

为了让 Spec 流程真正生效，作者更新了实施代理的技能。

新的实施代理在开发时会：

- 查找对应 issue 的规范文件
- 阅读 `PRODUCT.md` 和 `TECH.md`
- 按照规范进行实现
- 避免自由发挥或偏离需求

这样一来，整个流程就变成：

> 接收问题 → 自动分类 → 简单问题直接实现 → 复杂问题先写规范 → 人类审查规范 → 实施代理按规范开发

完成这些改造后，云软件工厂已经具备了更完整的能力：

##### 分诊决定需求进入哪条路径

分诊代理结合项目的 `roadmap.md` 和 `vision.md` 判断需求是否符合产品方向，并按情况打标签：

- 范围明确、可一次完成：标记为可实施，直接启动实施代理。
- 符合路线图且复杂或模糊：标记为 `ready-to-spec`，启动规范代理。
- 信息不足：标记为 `needs-info`，要求补充信息。
- 不符合当前计划：暂缓实现。

文中将“模糊”定义为存在差异显著的多种产品或技术方案，需要人做取舍；“复杂”通常指实现规模超过几百行代码。

##### 两份规范分别约束产品行为与技术实现

Spec 代理通过 GitHub Actions 触发，并生成与 Issue 编号关联的两份文件：

- `PRODUCT.md`：明确功能行为和产品预期。
- `TECH.md`：定义技术架构、代码结构与实现方式。

实施代理也被更新为主动查找并遵循这些规范，从而避免面对复杂需求时直接猜测设计意图。

##### 自动生成规范，但关键判断仍需人工校准

作者强调，代理生成的只是初稿。团队最好将规范拉到本地，通过交互式问答工具持续完善，确认预期一致后，再把 Issue 标记为可实施并启动编码。

该流程复用了已有基础设施，包括包含代码与工具链的 Docker 镜像、云端执行环境和 GitHub Actions。其意义在于把复杂开发任务拆成“分诊—定规范—人工确认—实施”的可控链路；下一步还需增加审核与验证代理，保障最终实现质量。
