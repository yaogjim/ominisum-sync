## 口播总结（1）

### 2026-09-18 03:54:57

这里讨论的重点，不是 “人工智能智能体不要参与端到端测试”，而是要重新分工：智能体负责写测试脚本，真正执行测试的工作，交给专业测试工具。

端到端测试，也就是 E2E 测试，模拟用户从头到尾完成一套操作。比如登录账号、选择商品、提交订单，再检查页面结果是否正确。

一种低效做法，是让智能体直接操作浏览器。智能体先看截图，理解页面，再点击一次；页面变化后，它又要重新查看、重新判断，然后继续操作。整个过程需要反复传递页面信息，也需要智能体不断推理。

问题就出在这里。这种测试很慢，消耗大量 token，也就是模型处理信息时所用的计算额度。而且，页面稍有变化，智能体的判断和操作就可能不稳定。更重要的是，测试完成之后，往往没有留下一套可以长期复用的成果。

更合适的办法，是让智能体编写 Node.js 加 Playwright 的自动化测试脚本。Node.js 是运行 JavaScript 程序的环境。Playwright 则是专门用来控制浏览器和执行自动化测试的工具。

脚本写好后，真正的测试不再依赖智能体一轮轮观察和点击，而是由 Playwright 按照固定步骤自动运行。比如打开登录页面，填写账号密码，点击提交，再检查是否成功进入用户主页。

这种分工的优势很直接。脚本只需要写一次，之后可以反复运行。执行通常很快，也几乎不再消耗模型的 token。测试结果更稳定，还能在软件更新之后持续做回归测试。所谓回归测试，就是每次修改代码后，重新确认原有功能没有被破坏。

因此，智能体在这里更像编写测试方案的工程师，而不是亲自坐在浏览器前，不断看图和点按钮的操作员。后者每次都要重新理解现场，前者则把测试过程固化成了可重复执行的程序。

实际落地时，可以先在项目里安装和配置 Playwright，再按照业务场景组织测试文件。例如，把登录相关测试放在认证测试文件中，把购买和支付流程放在结账测试文件中。项目启动后，直接运行 Playwright 的测试命令，就可以快速完成整套检查。

当然，智能体仍然可以帮助分析失败原因，也可以根据需求补充或修改脚本。但常规执行不应该持续依赖智能体操作浏览器。否则，每跑一次测试，都要重复支付时间和 token 成本。

最值得记住的是，问题不在于要不要让智能体参与 E2E 测试，而在于智能体参与哪一部分。让智能体写出可重复运行的脚本，再让 Playwright 负责机械执行，才能把一次性的智能操作，变成稳定、快速、可回归的工程资产。

## 通俗精炼（1）

### 2026-09-18 10:32:59

#### E2E 测试应由 Playwright 执行，Agent 只负责生成脚本

文章的核心主张是：不要让 AI Agent 通过浏览器工具或 MCP 亲自逐步操作页面完成端到端（E2E）测试，而应让它编写可重复执行的 Node.js + Playwright 测试脚本，再由 Playwright 自动运行。

##### Agent 直接操作浏览器成本高且不稳定

Agent 测试通常需要反复“查看截图—理解页面—点击操作—再次观察”，不仅执行速度慢、持续消耗 token，还容易受页面状态和视觉判断影响。更重要的是，这种一次性的操作过程难以沉淀为后续可复用的测试资产。

##### 脚本化测试更适合持续回归

Playwright 脚本写好后，可通过 `npx playwright test` 快速、稳定地重复执行，几乎不再消耗 Agent token，也便于持续回归。项目可直接使用 `npm init playwright@latest` 或 `pnpm create playwright` 初始化，并按登录、结账等业务流程拆分测试文件。

##### Agent 的价值在“写测试”，而非“充当测试执行器”

这并不是否定 Agent 参与 E2E，而是重新划分职责：Agent负责理解需求、生成和维护自动化脚本；确定性的测试框架负责执行。其意义在于把 AI 的一次性推理转化为可复用、可追踪的工程资产，同时提高测试效率、稳定性和成本可控性。
