Agent 定义：系统提示词、技能包、扩展、工具定义等。这些本质是不可变的，修改则是新的版本，需要Reload。

## 解读（1）

### 2026-06-02 08:06:20

##### 一、总结

作者认为：**Agent 不是一个单一程序，而是由三部分组成：**

1. **Agent 定义**
   - 系统提示词
   - 技能包
   - 扩展
   - 工具定义  
   这些相对固定，改了就相当于新版本，需要重新加载。

2. **Agent 持久化**
   - Memory
   - Workspace
   - 文件、状态等  
   每次运行时需要加载。  
   会话历史不建议直接挂载，建议放到 SQL 里，通过 session tools 访问。

3. **Agent 运行时**
   - 环境变量
   - 沙盒
   - 模型接入
   - 工具代理
   - 运行配置等

因为 Agent 技术变化太快，作者没有做复杂平台，而是做了一个 CLI：

```bash
cove --agent agent.yml --runtime runtime.yml
```

用两个 YAML 文件分别描述 Agent 本身和运行环境。

---

##### 二、通俗解读

可以把 Agent 理解成一个“AI 员工”。

###### 1. Agent 定义 = 员工的人设和能力说明书

比如：

- 他是谁
- 要怎么说话
- 会什么技能
- 能用哪些工具

这部分类似“岗位说明书”。  
一旦改了，就等于换了一个新版本的员工。

---

###### 2. Agent 持久化 = 员工的记忆和工作资料

比如：

- 以前做过什么
- 用户偏好是什么
- 工作目录里有哪些文件
- 历史任务记录

这些东西不能每次重启就丢，所以要单独保存。

作者还提到：  
**聊天记录最好放数据库，而不是直接挂载到运行环境里。**

这样更清晰，也更容易查询和管理。

---

###### 3. Agent 运行时 = 员工的办公室和设备

比如：

- 在什么环境里运行
- 用哪个模型
- 能不能联网
- 有没有沙盒隔离
- 工具怎么调用

这不是 Agent 的“灵魂”，而是它工作的“场地和设备”。

---

##### 三、核心观点

作者其实在讲一个重要架构思想：

> Agent 要做“定义、存储、运行环境”的分离。

也就是：

```text
Agent 定义 ≠ Agent 记忆 ≠ Agent 运行环境
```

这样做好处是：

- 更容易升级
- 更容易迁移
- 更容易复用
- 更容易多 Agent、多 Session 并发运行
- 不容易被快速变化的技术栈绑死

---

##### 四、我的意见

我认同这个思路。

现在 Agent 领域变化太快，过早做“大平台”风险很高。  
用 CLI + YAML 的方式更轻量，也更灵活。

尤其是这几点很关键：

1. **Agent 定义版本化**
   - 改提示词、工具、技能，就应该视为新版本。

2. **Memory 和 Workspace 独立管理**
   - 不要和运行环境混在一起。

3. **运行时用沙盒隔离**
   - 安全性和可控性更好。

4. **会话历史进数据库**
   - 比直接挂载文件更适合长期管理。

简单说：

> 这套设计不是在“做一个聊天机器人”，而是在给 Agent 搭一个可维护、可扩展的底座。

但如果只是个人小项目，没必要一开始就搞太复杂。  
可以先从两个文件开始：

```text
agent.yml    定义 Agent 是谁、会什么
runtime.yml  定义 Agent 在哪里、怎么跑
```

这已经是一个很好的起点。

## 结构化（1）

##### 主旨概括

文章讨论了 **Agent（智能体）的架构拆分方式**：可以将 Agent 分为“定义、持久化、运行时”三部分，以便更好地管理版本、数据和运行环境。作者实践中选择用 CLI + YAML 配置来启动和管理多个 Agent 与 Session。

---

##### 1. Agent 的三个核心组成

作者认为，Agent 本质上可以拆成三类内容：

###### 1）Agent 定义：相对不可变的部分

包括：

- 系统提示词
- 技能包
- 扩展能力
- 工具定义

这些内容决定了 Agent “是什么、会什么、能调用什么”。  
作者强调：这些内容本质上是不可变的，如果修改，就应该视为一个新版本，需要重新加载（Reload）。

**例子：**  
如果一个 Agent 原本只会写代码，后来新增了“数据分析技能包”，这就相当于 Agent 定义发生变化，应当作为新版本处理。

---

##### 2. Agent 持久化：保存记忆和工作空间

Agent 的持久化部分包括：

- Memory：记忆
- Workspace：工作区
- 其他运行过程中需要长期保存的数据

这些数据每次运行时都需要加载，可能存放在：

- 对象存储
- PVC（持久化卷）
- 其他外部存储系统

作者还特别提到：  
**会话历史不推荐直接挂载到 Agent 运行环境里，而是建议放到 SQL 数据库中，并通过 session tools 提供访问能力。**

这样做的好处是更清晰地管理会话数据，也更方便查询、复用和维护。

---

##### 3. Agent 运行时：实际执行环境

Agent 运行时指的是 Agent 真正执行任务时所依赖的环境和配置，包括：

- 环境变量
- 沙盒环境
- 模型接入配置
- 工具代理
- 其他运行配置

这部分决定了 Agent “在哪里运行、怎么运行、能访问哪些资源”。

---

##### 4. 作者的实践方案：CLI + 两个 YAML 文件

由于 Agent 架构变化很快，作者团队最终选择做了一个 CLI 工具来启动 Agent。

启动方式类似：

```bash
cove --agent agent.yml --runtime runtime.yml
```

其中：

- `agent.yml`：描述 Agent 定义
- `runtime.yml`：描述运行时配置
- 持久化相关的 endpoint 也被放到了 `runtime.yml` 中

这种方式把 Agent 的定义和运行环境分开管理，更容易维护和切换。

---

##### 5. 支持多 Agent、多 Session

这个 CLI 支持：

- 同时启动多个 Agent
- 每个 Agent 同时运行多个 Session

并且由于使用了 Sandbox（沙盒），Agent 的核心逻辑在实现上只是 CLI 中的一个协程或线程。

也就是说，Agent 本身并不一定需要是一个复杂的独立服务，而可以被 CLI 统一调度和管理。

---

##### 6. 引用推文背景：Agent 的存算分离

引用推文提到的是 **Agent 的存算分离架构设计**。

一个“有灵魂、有记忆”的 Agent，在一次任务生命周期中大致会经历：

1. 用户输入 query，包括文本和文件
2. Agent 读取提示词文件，例如 `soul.md`、`identify.md`、`user.md`
3. Agent 读取可用工具和技能，例如 `tools`、`skills`
4. Agent 开始执行任务

这与作者的观点一致：  
Agent 不只是模型调用，而是由提示词、技能、工具、记忆、工作区和运行环境共同组成的系统。

##### 一、启发

这条内容的核心启发是：**Agent 不应该被理解成一个单一程序，而应被拆成三类资产：定义、状态、运行环境。**

这类似软件工程里的经典分层：

|---|---|
| Agent 定义 | 应用代码 / 镜像 / 配置版本 |
| Agent 持久化 | 数据库 / 文件系统 / 用户状态 |
| Agent 运行时 | 容器 / VM / 执行环境 / 基础设施配置 |

这背后的关键判断是：

> 真正可规模化的 Agent 系统，不是把 Prompt、Memory、Tools、Runtime 混在一起，而是把它们拆开、版本化、可替换、可加载。

这也是从“玩具 Agent”走向“工程化 Agent”的重要分水岭。

##### 二、高价值信息深挖

###### 1. Agent 定义应当是不可变的

原文中说：

> Agent 定义：系统提示词、技能包、扩展、工具定义等。这些本质是不可变的，修改则是新的版本，需要 Reload。

这是一个非常重要的工程判断。

很多人在做 Agent 时，会把 prompt、tools、skills 直接动态改来改去，导致：

- 行为不可复现
- Debug 困难
- 线上问题无法回滚
- 多版本并存困难
- 无法做 A/B Test
- 无法稳定评估 Agent 能力

如果把 Agent 定义视为不可变资产，那么每次修改都意味着：

```text
Agent v1 → Agent v2
```

而不是在同一个 Agent 上“热改”。

这会带来几个好处：

- 可版本管理
- 可回滚
- 可审计
- 可复现
- 可评估
- 可部署到不同 runtime

这其实是在把 Agent 从“交互脚本”提升为“软件制品”。

---

###### 2. Memory 和 Workspace 应归入 Agent 持久化层

原文提到：

> Agent 持久化：包括 Memory、Workspace 等。每次运行时需要加载。

这意味着，Agent 的“记忆”和“工作区”不应该和运行时强绑定。

一个 Agent 可能今天跑在本地 Sandbox，明天跑在云端容器，后天跑在 Kubernetes 里，但它的 Memory 和 Workspace 应该可以继续被加载。

所以合理结构是：

```text
Agent Definition
      ↓
Runtime 加载
      ↓
Persistence：Memory / Workspace / Files / Artifacts
```

这类似：

```text
程序代码 ≠ 用户数据
```

Agent 定义是代码，Memory / Workspace 是数据。

如果不拆开，会导致：

- Agent 一重启记忆丢失
- 不同环境迁移困难
- 多 Session 难以隔离
- 文件、上下文、任务状态混乱
- 无法做长期任务

---

###### 3. 会话历史不建议直接挂载，而是放进 SQL

原文说：

> 会话历史推荐不挂载而是放到 SQL 里提供 session tools。

这是一个很细但很关键的实践点。

很多 Agent 系统会把会话历史直接塞进上下文，或者作为文件挂载进 Workspace。但原文建议放到 SQL，并通过 `session tools` 读取。

这背后的逻辑是：

###### 会话历史不是普通文件，而是结构化数据

它包含：

- 用户消息
- Agent 回复
- 工具调用记录
- 时间戳
- Session ID
- 用户 ID
- Token 使用情况
- 中间状态
- 任务链路
- 错误日志

这些天然适合 SQL，而不是文件。

###### 通过 tool 访问会话历史，而不是默认全部加载

这样可以避免：

- 上下文过长
- 无意义历史污染当前任务
- 隐私和权限控制困难
- Session 之间边界混乱
- 成本不可控

更好的方式是让 Agent 在需要时调用工具：

```text
search_session_history(query)
get_previous_task(session_id)
summarize_conversation(session_id)
```

也就是说：

> 历史不是全部进入上下文，而是成为可查询的外部资源。

这对于长期 Agent 非常重要。

###### 4. Runtime 应该独立于 Agent 定义

原文提到：

> Agent 运行时：实际 Agent 的运行环境和配置，包括环境变量、沙盒、模型接入、工具代理等。

这说明 Runtime 包含的是执行条件，而不是 Agent 的“人格”或“能力定义”。

比如：

```yaml
model: claude-4-sonnet
env:
  API_KEY: xxx
sandbox:
  type: docker
tools_proxy:
  endpoint: xxx
storage:
  memory_endpoint: xxx
```

Runtime 可以控制：

- 用什么模型
- 是否启用 Sandbox
- 能访问哪些环境变量
- 文件系统路径
- 外部工具代理地址
- 对象存储地址
- 网络权限
- 资源限制
- 并发数量
- 安全策略

这使得同一个 Agent 定义可以跑在多个运行环境中。

例如：

```text
Dev Runtime
Staging Runtime
Production Runtime
Local Runtime
Cloud Runtime
Enterprise Runtime
```

这就是 Agent 系统的“环境分离”。

###### 5. 两个 YAML 启动 Agent 是很好的工程抽象

原文给出的方式：

```bash
cove --agent agent.yml --runtime runtime.yml
```

这很有启发性。

它相当于把 Agent 系统拆成两个配置文件：

```text
agent.yml   → 定义 Agent 是谁、会什么、有哪些工具
runtime.yml → 定义 Agent 在哪里跑、怎么跑、接入什么资源
```

可以理解为：

```text
agent.yml = What
runtime.yml = How / Where
```

例如：

```yaml
# agent.yml
name: research-agent
version: 1.0.0
system_prompt: ./prompts/system.md
skills:
  - web_research
  - report_writing
tools:
  - search
  - browser
  - file_reader
```

```yaml
# runtime.yml
model:
  provider: openai
  name: gpt-4.1
sandbox:
  type: docker
storage:
  workspace: s3://agent-workspaces/research-agent/
  memory: postgres://memory-db
env:
  SEARCH_API_KEY: ${SEARCH_API_KEY}
```

这种抽象的价值在于：

- 清晰
- 可复制
- 可部署
- 可版本化
- 可自动化
- 适合 CI/CD
- 适合多 Agent 管理

```text
runtime.yml
memory.yml
tools.yml
skills.yml
policy.yml
```

但早期不要过度设计，两个 YAML 已经足够好。

推荐结构：

```text
/agents
  /research-agent
    agent.yml
    prompts/
      system.md
      identity.md
      style.md
    skills/
      research.md
      synthesis.md
    tools/
      search.yml
      browser.yml

/runtimes
  local.yml
  staging.yml
  production.yml
```

###### 3. Session 管理清单

建议不要简单把 Session 历史塞进上下文。

更好的做法：

- Session 历史入 SQL
- 每条消息有 session_id
- 每次 tool call 有 trace_id
- 支持按时间、关键词、任务查询
- 提供 session tools 给 Agent 调用
- 对长对话做摘要
- 原始记录和摘要分开存储

可设计工具：

```text
get_session_messages(session_id)
search_session_history(query)
summarize_session(session_id)
get_last_task_status(session_id)
get_user_preferences(user_id)
```

###### 4. 多 Agent / 多 Session 运行清单

如果一个 CLI 或服务要支持多个 Agent、多个 Session，需要考虑：

- Agent Definition 是否可多版本共存
- 每个 Session 是否有独立 Workspace
- Memory 是否按 user / agent / session 隔离
- Runtime 是否可复用
- 工具调用是否可追踪
- 失败任务是否可恢复
- Sandbox 是否按任务销毁
- Session 是否能被迁移到其他 Runtime

基本结构可以是：

```text
Agent A
  - Session 1
  - Session 2

Agent B
  - Session 1
  - Session 2

Shared Runtime / Isolated Runtime
Shared Tool Proxy
Shared SQL Session Store
Shared Object Storage
```

##### 四、反方与张力

###### 1. 不可变 Agent 定义 vs 快速迭代

把 Agent 定义做成不可变版本，有利于稳定性，但会降低迭代灵活性。

早期产品可能需要频繁改 Prompt、调 Tool、改输出格式。如果每次都新版本、Reload，会增加操作成本。

张力在于：

```text
研发速度 vs 工程稳定性
```

建议：

- 早期可以允许热更新
- 进入生产环境后强制版本化
- 对外部用户开放的 Agent 必须可回滚
- 内部实验 Agent 可降低约束

---

###### 2. SQL 管理会话历史 vs 文件化简单实现

把会话历史放 SQL 里更规范，但也更复杂。

对于个人项目或 Demo，直接用 JSON 文件、SQLite、Markdown 日志可能已经够用。

张力在于：

```text
系统复杂度 vs 可维护性
```

建议：

- Demo：JSON / SQLite 即可
- 小团队：Postgres + 简单 Session Tool
- 生产系统：SQL + 向量检索 + Trace + 权限系统

---

###### 3. Runtime 抽象 vs 过早平台化

把 Runtime 抽象出来很优雅，但也容易走向“还没几个 Agent，就先造平台”。

张力在于：

```text
平台化架构 vs 业务交付速度
```

建议：

不要一开始就做复杂 Agent 平台。

可以先用：

```bash
agent.yml + runtime.yml + CLI
```

逐步演化，而不是一开始就上 Kubernetes、控制面、调度系统、权限中心。

---

###### 4. Sandbox 安全 vs 工具能力受限

Sandbox 可以增强安全性，但也会限制 Agent 能力。

例如：

- 文件访问受限
- 网络访问受限
- 执行脚本受限
- 安装依赖麻烦
- 调试更复杂

张力在于：

```text
安全隔离 vs 执行自由度
```

建议：

- 面向生产用户必须 Sandbox
- 内部可信任务可以放宽
- 高风险工具必须走代理和审计
- 默认最小权限，按需授权

---

###### 5. 多 Agent 并发 vs 状态一致性

一个 CLI 同时启动多个 Agent，每个 Agent 多个 Session，很灵活，但状态隔离会变得关键。

容易出现：

- Workspace 混用
- Memory 污染
- Tool 权限混乱
- Session 历史错挂
- 并发写冲突

张力在于：

```text
并发效率 vs 状态隔离
```

建议：

每个任务至少明确：

```text
agent_id
agent_version
session_id
user_id
workspace_id
runtime_id
trace_id
```

否则后期排查问题会非常痛苦。

##### 五、情境化落地

###### 场景 1：个人开发者做本地 Agent CLI

可以采用最小实现：

```bash
my-agent --agent agent.yml --runtime local.yml
```

目录：

```text
/my-agent
  agent.yml
  runtime.local.yml
  prompts/
    system.md
  workspace/
  memory.sqlite
```

技术选型：

- SQLite 存 Session
- 本地文件夹做 Workspace
- `.env` 管理环境变量
- Docker 可选
- YAML 管理 Agent 定义

重点不是做平台，而是先形成清晰分层。

---

###### 场景 2：创业团队做 AI 产品中的 Agent

建议结构：

```text
Agent Definition Registry
Session DB
Workspace Object Storage
Runtime Executor
Tool Proxy
```

可以这样设计：

```text
前端用户输入
    ↓
API Server 创建 session
    ↓
加载 agent.yml
    ↓
加载 runtime.yml
    ↓
启动 Agent Runner
    ↓
Agent 调用 Tool Proxy
    ↓
Session / Memory / Workspace 持久化
```

重点关注：

- 每个 Agent 定义有版本号
- 每个用户 Session 独立
- 所有工具调用可追踪
- Workspace 存对象存储
- 会话历史入 Postgres
- Agent Runner 无状态化

这样未来可以水平扩展。

---

###### 场景 3：企业内部搭建多 Agent 自动化系统

企业场景更关注：

- 权限
- 审计
- 安全
- 数据隔离
- 合规
- 可观测性

建议：

```text
Agent Definition：Git 管理
Runtime：K8s / Docker Sandbox
Session：Postgres
Workspace：S3 / MinIO
Memory：Postgres + Vector DB
Tool：统一 Tool Gateway
Secrets：Vault / KMS
Logs：OpenTelemetry
```

关键原则：

- Agent 定义走代码审查
- Runtime 配置分环境
- 工具调用必须审计
- Memory 要按租户隔离
- 高风险工具需要审批流
- 所有执行有 trace_id

---

###### 场景 4：AI 产品经理如何用这套框架思考产品

如果你是产品负责人，可以用这三层判断功能归属：

###### 这个东西属于 Agent 定义吗？

如果是：

- Prompt
- Persona
- Skill
- Tool 列表
- 输出风格
- 任务边界

那它应该版本化。

###### 这个东西属于持久化吗？

如果是：

- 用户偏好
- 任务进度
- 文件
- 记忆
- 会话历史
- 上次执行结果

那它应该存储、查询、迁移。

###### 这个东西属于 Runtime 吗？

如果是：

- 模型选择
- API Key
- 沙盒
- 网络权限
- 资源限制
- 工具代理
- 环境变量

那它应该由部署环境控制。

这能避免产品需求和技术实现混乱。

---

##### 六、最终提炼

这条内容最有价值的地方在于，它提供了一个非常实用的 Agent 工程化框架：

```text
Agent Definition：定义 Agent 是谁
Agent Persistence：保存 Agent 记住了什么、做过什么
Agent Runtime：决定 Agent 在哪里、如何运行
```

对应到一句话：

> Agent 的灵魂要版本化，记忆要持久化，身体要运行时化。

如果你要做真正可维护、可扩展、可商业化的 Agent 产品，这个三分法非常值得作为底层架构原则。
