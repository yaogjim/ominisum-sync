#### README.md

#### What's inside?

This example demonstrates how to use the LFM2.5-Audio-1.5B model with llama.cpp to transcribe audio files locally in real-time.

When you combine the efficiency of llama.cpp with the power of a small audio model like [LFM2.5-Audio-1.5B](https://huggingface.co/LiquidAI/LFM2.5-Audio-1.5B), you can build real-time applications that can run on

- smartphones
- self-driving cars
- smart home devices
- you name it

without internet connection or any other cloud service dependencies.

Intelligent audio assistants on the edge are possible, and this repository is just one example of how to build one.

#### Quick start

1. Clone the repository
   ```
   git clone https://github.com/Liquid4All/cookbook.git
   cd cookbook/examples/audio-transcription-cli
   ```
2. Install uv on your system, if you don't have it already.
   Click to see installation instructions for uv
   **macOS/Linux:**
   ```
   curl -LsSf https://astral.sh/uv/install.sh | sh
   ```
   **Windows:**
   ```
   powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
   ```

1. Download a few audio samples
   ```
   uv run download_audio_samples.py
   ```
2. Run the transcription CLI, and see the transcription of the audio sample in the console.
   ```
   uv run transcribe --audio './audio-samples/barackobamafederalplaza.mp3' --play-audio
   ```
   By passing the `--play-audio` flag, you will hear the audio in the background during transcription.
   The model is downloaded automatically on first run. Use `--quantization` to trade accuracy for size and speed:
   ```
   uv run transcribe --audio './audio-samples/barackobamafederalplaza.mp3' --quantization Q4_0
   ```
   Quantization Total size on disk
   `Q4_0` \~1.1 GB
   `Q8_0` (default) \~1.8 GB
   `F16` \~3.3 GB

This example is a 100% local audio-to-text transcription CLI, that runs on your machine thanks to llama.cpp. Neither inputs audios nor outputs text are sent to any server. Everything runs on your machine.

The Python code downloads the necessary llama.cpp builds for your platform automatically, so you don't need to worry about it. Audio support in llama.cpp is still quite experimental, and not fully integrated on the main branch of the llama.cpp project. Because of this, the Liquid AI team has released specialized llama.cpp builds that support the LFM2.5-Audio-1.5B model, that you will need to run this CLI.

[llama.cpp](https://github.com/ggerganov/llama.cpp) is a super fast and lightweight open-source inference engine for Language Models. It is written in C++ and can be used to run LLMs on your local machine. For example, our Python CLI used llama.cpp under the hood to deliver fast transcriptions, instead of using either `PyTorch` or the higher-level `transformers` library.

In the [examples.sh](https://github.com/Liquid4All/cookbook/blob/main/examples/audio-transcription-cli/examples.sh) script you will find 3 examples on how to run inference with LFM2.5-Audio-1.5B for 3 common use cases:

- Audio to text transcription. This is essentially what our Python CLI does under the hood:
  ```
  # Audio to Speech Recognition (ASR)   
  ./llama-liquid-audio-cli \
      -m $CKPT/LFM2.5-Audio-1.5B-Q8_0.gguf \
      -mm $CKPT/mmproj-LFM2.5-Audio-1.5B-Q8_0.gguf \
      -mv $CKPT/vocoder-LFM2.5-Audio-1.5B-Q8_0.gguf \
      --tts-speaker-file $CKPT/tokenizer-LFM2.5-Audio-1.5B-Q8_0.gguf \
      -sys "Perform ASR." \
      --audio $INPUT_WAV
  ```
- Text to speech.
  ```
  # Text To Speech (TTS)
  ./llama-liquid-audio-cli \
      -m $CKPT/LFM2.5-Audio-1.5B-Q8_0.gguf \
      -mm $CKPT/mmproj-LFM2.5-Audio-1.5B-Q8_0.gguf \
      -mv $CKPT/vocoder-LFM2.5-Audio-1.5B-Q8_0.gguf \
      --tts-speaker-file $CKPT/tokenizer-LFM2.5-Audio-1.5B-Q8_0.gguf \
      -sys "Perform TTS. Use the US male voice." \
      -p "My name is Pau Labarta Bajo and I love AI" \
      --output $OUTPUT_WAV
  ```
- Text to speech with a different voice. The supported voices are `US male`,`UK male`, `US female` and `UK female`.
  ```
  ./llama-liquid-audio-cli \
      -m $CKPT/LFM2.5-Audio-1.5B-Q8_0.gguf \
      -mm $CKPT/mmproj-LFM2.5-Audio-1.5B-Q8_0.gguf \
      -mv $CKPT/vocoder-LFM2.5-Audio-1.5B-Q8_0.gguf \
      --tts-speaker-file $CKPT/tokenizer-LFM2.5-Audio-1.5B-Q8_0.gguf \
      -sys "Perform TTS. Use the UK female voice." \
      -p "What is your name man?" \
      --output $OUTPUT_WAV
  ```

#### Further improvements

The decoded text is not perfect, due to overlapping chunk and partial sentences that are grammatically incorrect.

To improve the transcription, we can use a text cleaning model to clean the text, in a local 2-step workflow for real-time Audio to Speech recognition.

For example, we can use

- LFM2.5-Audio-1.5B for audio to text extraction
- LFM2.5-350M for text cleaning

[LFM2.5-350M](https://huggingface.co/LiquidAI/LFM2.5-350M) is a small text-to-text model that can be used for tasks like text cleaning. To achieve optimal performance for your particular use case, you need to optimize your system and user prompts.

#### 本地实时语音正在变得可用，但“能运行”离“可交付”还有三道门槛

这个示例真正值得关注的，不是又多了一个转写 CLI，而是它展示了一条更现实的端侧语音路径：用 **1.5B 级音频模型、量化和轻量推理引擎**，在不依赖云服务的情况下完成语音转文字，并复用同一套工具链实现文字转语音。

LFM2.5-Audio-1.5B 经 llama.cpp 运行后，Q4、Q8 和 F16 版本占用约 1.1GB、1.8GB 和 3.3GB。这意味着语音能力已经有机会进入普通电脑，理论上也能进一步进入手机、汽车和智能家居设备。其价值不只是省掉 API 费用，而是让一些过去受网络与隐私限制的场景开始成立。

##### 本地化改变的是产品边界，而不只是部署位置

音频输入和转写文本完全不离开设备，直接改善了三类问题：敏感数据上传风险、弱网或断网不可用，以及云端调用带来的持续成本和延迟波动。因此，更值得优先验证的并非通用会议转写，而是那些**“不上云”本身就是购买理由**的需求，例如医疗访谈、企业内部会议、车载指令、工业现场记录，以及长期监听型的家庭设备。

但 README 把“可运行在智能手机、自动驾驶汽车等设备”作为前景描述，并没有提供对应硬件上的延迟、内存、功耗和准确率数据。所谓“实时”也缺少实时率、首字延迟等指标。**这份代码证明了技术可行性，却还没有证明具体设备和场景中的产品可行性。**

真正进入选型时，至少要把它与云端 ASR、端侧 Whisper 等现有替代方案比较：在目标口音、噪声环境、连续工作时长和设备功耗下，本地模型带来的隐私收益，是否足以覆盖准确率或工程成熟度上的代价。

##### 量化不是单纯的性能开关，而是产品策略

项目允许从约 3.3GB 的 F16 降到约 1.1GB 的 Q4。表面上这是准确率、体积和速度之间的技术取舍，实际对应的是不同产品边界：更小的模型可以覆盖更多低端设备，降低下载和存储门槛；更高精度的版本则适合专业记录等容错率低的场景。

因此，不必追求一个统一配置。更合理的做法可能是按任务风险分层：设备命令识别可接受较激进的量化，因为词汇集合有限且能够二次确认；法律、医疗或正式会议记录则需要更高精度，并保留人工校对机制。模型规格最终应由错误成本决定，而不是只看运行速度。

##### 两阶段管线比追求单模型完美更有迁移价值

作者明确承认，目前输出会因重叠分块和不完整句子出现语法问题，并建议再用一个 350M 文本模型做清洗。这暴露了实时转写的关键矛盾：为了低延迟，系统必须分块处理音频；但分块又会破坏句子边界和上下文连续性。

“音频提取—文本清洗”的两阶段方案因此比单一模型指标更值得保留。前一阶段专注及时捕捉内容，后一阶段负责去重、补标点和修复断句，两者可以独立量化、替换与优化。不过，清洗模型也可能把听错的内容润色成更可信的错误，尤其是数字、专有名词和否定表达。产品上应保存原始转写，并区分“识别结果”与“整理结果”，避免流畅度掩盖事实偏差。

这套示例释放的是一个清晰信号：**端侧语音能力的门槛正在下降，但竞争力不会来自“模型能在本地跑”，而来自对延迟、功耗、错误成本和后处理链路的整体控制。**下一步最有价值的不是继续扩展功能清单，而是在一个隐私或离线需求足够强的场景中，测出它相对现有方案的真实优势。

## 口播总结（1）

### 2026-09-20 00:33:52

这个项目展示了一件很实用的事：只用本地设备，就能实时把音频转成文字，不需要联网，也不需要把录音上传到云端。它采用十五亿参数的 LFM 二点五音频模型，并通过轻量级推理引擎 llama 点 C P P 运行。

本地运行的价值，不只是省去云服务费用。更重要的是，输入音频和识别结果都不会发送到服务器。对于会议录音、私人对话，或者车载、智能家居等重视隐私和网络稳定性的场景，这一点尤其重要。由于模型规模较小，这套方案未来也适合部署在智能手机、汽车和边缘设备上。

实际使用并不复杂。先下载项目代码，进入音频转写命令行工具所在的目录，再安装名为 U V 的 Python 工具。项目提供了脚本，可以下载几段音频样本。随后运行转写命令，并指定一个音频文件，就能在终端中看到识别文字。如果加入播放音频的选项，程序还会在转写过程中同步播放原始录音。

第一次运行时，模型会自动下载。项目中的 Python 代码也会根据操作系统，自动获取所需的 llama 点 C P P 构建版本。因此，用户不必自行编译底层推理引擎，也不需要安装 PyTorch 或较高层的 Transformers 框架。

模型支持不同的量化版本。量化可以理解为，用较低的数据精度保存和运行模型，从而减少体积、提高速度，但可能牺牲一部分准确率。

默认使用的是 Q 八版本，占用磁盘大约一点八 GB。更轻的 Q 四版本大约一点一 GB，更适合存储空间有限或计算能力较弱的设备。精度更高的 F 十六版本大约三点三 GB。选择时要考虑实际需求：如果更在意速度和体积，可以用 Q 四；如果希望保留更多精度，并且设备资源充足，可以选择 Q 八或 F 十六。

这套模型不只支持音频转文字。底层命令行工具还展示了另外两类能力。一类是文本转语音，也就是把输入文字合成为音频文件。另一类是在文本转语音时指定声音。当前示例支持美国男性、英国男性、美国女性和英国女性四种声音。

不过，这套方案目前仍有明显限制。llama 点 C P P 的音频支持还处在较早的实验阶段，也没有完全并入该项目的主分支。因此，Liquid AI 团队提供了专门构建的版本，用来支持 LFM 二点五音频模型。换句话说，这个示例已经可以运行，但底层技术还不算完全成熟。

转写结果也并非总是完美。实时识别通常要把长音频切成多个片段。为了避免漏掉片段交界处的内容，相邻片段可能会有重叠。这会造成重复文字、残缺句子，或者语法不完整的问题。

项目提出了一种两步处理方法。第一步，使用十五亿参数的音频模型提取文字。第二步，再用三亿五千万参数的 LFM 二点五文本模型清理结果，修正重复内容和不完整句子。这样既能维持本地实时处理，又能改善最终文本的可读性。

不过，文本清理的实际效果很依赖提示词。不同录音场景，例如会议、采访或车内对话，需要针对任务调整系统提示和用户提示，不能指望一套提示适用于所有情况。

这份示例最值得记住的有三点。第一，小型音频模型配合轻量级推理引擎，已经能够在本地完成实时转写。第二，量化让用户可以在模型体积、运行速度和识别精度之间做取舍。第三，当前转写仍可能出现重叠和残句，而增加一个本地文本清理步骤，是提升结果质量的实用办法。

### 2026-09-30 11:58:45

语音转文字，不一定要把录音上传到云端。这个开源示例展示了一条本地运行的路线：把一个小型音频模型和轻量推理引擎结合起来，让音频文件在自己的设备上转成文字，不依赖云端服务。

这里最值得关注的，不只是“能转写”，而是它把模型、运行工具和使用流程接到了一起。同时，项目也明确提醒：这套方案还有实验性限制，转写结果并不完美。

先看它是怎么工作的。

项目使用的模型叫 LFM 二点五 Audio，参数规模为十五亿。负责运行模型的，是 llama 点 cpp。你可以把模型理解为识别声音的核心，把推理引擎理解为让这个核心在设备上运转的软件。这只是帮助理解的比喻。

llama 点 cpp 是一个用 C 加加编写的开源推理引擎，特点是轻量、运行速度快。这个示例虽然用 Python 提供命令行入口，但底层真正执行模型推理的，是 llama 点 cpp，而不是 PyTorch 或者更高层的 Transformers 库。

这种组合的意义，在于探索端侧音频应用。所谓端侧，就是尽量在用户自己的设备上完成处理，而不是把任务交给远端服务器。项目作者认为，这类方案可以用于手机、智能家居设备，甚至自动驾驶汽车中的实时应用。

不过，要区分愿景和这个示例实际展示的能力。这个仓库直接提供的是一个本地音频文件转写工具，并不等于已经证明它能在所有这些设备上达到同样的实时效果。

对使用者来说，本地处理有一个很明确的特点：输入的音频和输出的文字，都不会发送到服务器。转写过程在自己的机器上完成。

但“本地运行”不等于“从第一步开始就完全不需要联网”。首次使用时，程序会自动下载模型，也会下载适合当前平台的推理引擎版本。把这些必要组件准备好之后，转写本身不依赖云端服务。

实际使用流程并不复杂。先获取项目代码，再安装一个叫 uv 的 Python 工具。随后可以下载项目提供的示例音频，启动命令行转写，并在终端里看到识别出的文字。工具还提供一个播放音频的选项，让你在转写的同时听到原始录音，方便对照结果。

这里有一个很重要的技术前提。按照项目说明，llama 点 cpp 的音频支持仍然比较实验性，还没有完整整合到主分支。因此，这个工具依赖的是 Liquid AI 团队发布的专用构建版本，而不是随便找一个普通版本就能运行。项目中的 Python 代码会自动下载所需版本，替使用者处理这一部分准备工作。

理解了运行方式，再看一个实际选择：模型该用多大的版本？

项目提供了不同的量化选项。量化可以简单理解为，用更低的数值精度存储模型，以换取更小的体积和更快的运行速度。代价是，识别精度可能受到影响。

默认的八位量化版本，总磁盘占用大约是一点八吉字节。更小的四位量化版本，大约是一点一吉字节。十六位浮点版本则大约是三点三吉字节。

这几个数字指的是磁盘上的总大小，不是运行时的内存需求。它们说明的是：使用者可以根据设备条件，在体积、速度和准确性之间做取舍。至于哪一个版本最合适，材料没有给出统一答案，也没有提供不同设备上的速度或准确率对比。

这个模型的用途也不止转写。

项目附带的底层调用示例，还展示了文字转语音，也就是把输入的文字合成为音频。说明中列出的声音选择，包括美式英语和英式英语的男声、女声。

所以，这份材料展示的不只是一个“听写工具”，还展示了同一个音频模型可以支持语音识别和语音合成。不过，仓库中的 Python 命令行工具，主要实现的仍然是音频转文字。

真正影响转写体验的问题，出在输出质量上。

项目明确承认，识别出来的文字并不完美。原因包括音频片段之间存在重叠，以及部分句子不完整，导致输出出现语法不通顺的情况。

针对这个问题，作者提出了一种本地两步流程：第一步，让十五亿参数的音频模型提取文字；第二步，再用一个小型文本模型清理文字。示例建议使用同系列、参数规模为三点五亿的文本模型来承担清理任务。

这相当于把“听出说了什么”和“把文字整理顺畅”分开处理。音频模型负责识别，文本模型负责后处理，两步都可以放在本地完成。

但这是一项改进建议，不是已经验证过的效果保证。作者还强调，要适应具体用途，需要优化系统提示词和用户提示词，也就是更清楚地规定模型的任务，以及如何处理输入。

最值得记住的是，本地语音转写已经有了可以动手尝试的开源路径，但离稳定、通用的产品体验仍有距离。判断这类方案时，要同时看三件事：转写是否真正留在本地，设备能否承担所选模型，以及输出文字是否还需要进一步清理。
