构建并维护一个持久的、不断积累的知识库，这些知识库以相互关联的 Markdown 文件形式存在。基于 [Andrej Karpathy 的 LLM Wiki 模式](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 。

与传统的 RAG（每次查询都从头重新发现知识）不同，维基知识库一次性整合知识并保持其时效性。交叉引用已经存在。矛盾信息已经被标记。综合内容反映了所有已整合的内容。

**分工：** 人类管理信息源并指导分析。代理进行总结、交叉引用、归档并保持一致性。

Use this skill when the user:

- 要求创建、构建或启动维基或知识库
- 请求将一个来源导入、添加或处理到他们的维基中
- 提出一个问题，并且在已配置的路径上存在一个现有的维基
- 要求对他们的 wiki 进行校验、审计或健康检查
- 在研究背景下引用其维基、知识库或“笔记”

#### Wiki Location

通过 `skills.config.wiki.path` 在 `~/.hermes/config.yaml` 中配置（在 `hermes config migrate` 或 `hermes setup` 过程中提示）：

```
skills:
  config:
    wiki:
      path: ~/wiki
```

回退到 `~/wiki` 默认值。解析后的路径在该技能加载时被注入 — 检查上方的 `[Skill config: ...]` 区块以获取有效配置值。

这个维基只是一个 Markdown 文件的目录 — 在 Obsidian、VS Code 或任何编辑器中打开它即可。不需要数据库，也不需要特殊工具。

```
wiki/
├── SCHEMA.md           # Conventions, structure rules, domain config
├── index.md            # Sectioned content catalog with one-line summaries
├── log.md              # Chronological action log (append-only, rotated yearly)
├── raw/                # Layer 1: Immutable source material
│   ├── articles/       # Web articles, clippings
│   ├── papers/         # PDFs, arxiv papers
│   ├── transcripts/    # Meeting notes, interviews
│   └── assets/         # Images, diagrams referenced by sources
├── entities/           # Layer 2: Entity pages (people, orgs, products, models)
├── concepts/           # Layer 2: Concept/topic pages
├── comparisons/        # Layer 2: Side-by-side analyses
└── queries/            # Layer 2: Filed query results worth keeping
```

**第 1 层 — 原始来源：** 不可变的。代理只读取这些内容，从不修改它们。 **第 2 层 —— 知识库：** 代理拥有的 Markdown 文件。创建、更新以及 由智能体交叉引用 **第 3 层——架构：** `SCHEMA.md` 定义结构、规范和标签分类法。

#### 恢复现有 Wiki（关键——每次会话都要执行此操作）

当用户已有 Wiki 时， **始终在采取任何行动之前明确自身定位** ：

① **阅读 `SCHEMA.md`** — 了解领域、约定和标签分类体系。 ② **阅读 `index.md`** — 了解存在哪些页面及其摘要。 ③ **浏览最近 `log.md`** — 阅读最近 20-30 条记录以了解近期活动。

```
WIKI="${wiki_path:-$HOME/wiki}"
# Orientation reads at session start
read_file "$WIKI/SCHEMA.md"
read_file "$WIKI/index.md"
read_file "$WIKI/log.md" offset=<last 30 lines>
```

只有在定向之后，你才应该导入、查询或进行代码检查。这可以防止:

- 为已存在的实体创建重复页面
- 缺少对现有内容的交叉引用
- 与模式的惯例相矛盾
- Repeating work already logged

对于大型维基（100+ 页），在创建任何新内容之前，还应对当前主题执行快速的 `search_files` 操作。

当用户请求创建或启动一个维基时：

1. 确定 wiki 路径（来自配置、环境变量或询问用户；默认 `~/wiki` ）
2. 创建上述的目录结构
3. 询问用户该 Wiki 涵盖的领域是什么——要具体
4. 编写 `SCHEMA.md` 针对该领域定制（见下方模板）
5. 编写初始的 `index.md` ，并带有分节标题
6. 编写初始的 `log.md` 并包含创建条目
7. 确认维基已准备就绪，并建议首批导入的来源

##### SCHEMA.md Template

适应用户的领域。模式约束代理行为并确保一致性：

````
# Wiki Schema

## Domain
[What this wiki covers — e.g., "AI/ML research", "personal health", "startup intelligence"]

## Conventions
- File names: lowercase, hyphens, no spaces (e.g., `transformer-architecture.md`)
- Every wiki page starts with YAML frontmatter (see below)
- Use `[[wikilinks]]` to link between pages (minimum 2 outbound links per page)
- When updating a page, always bump the `updated` date
- Every new page must be added to `index.md` under the correct section
- Every action must be appended to `log.md`

## Frontmatter
  ```yaml
  ---
  title: Page Title
  created: YYYY-MM-DD
  updated: YYYY-MM-DD
  type: entity | concept | comparison | query | summary
  tags: [from taxonomy below]
  sources: [raw/articles/source-name.md]
  ---
````

#### Tag Taxonomy

\[定义10-20个顶级标签用于该领域。在此处添加新标签，在使用它们之前。\]

Example for AI/ML:

- 模型：模型、架构、基准测试、训练
- 人物/组织：个人，公司，实验室，开源
- 技术：优化、微调、推理、对齐、数据
- Meta: 比较，时间线，争议，预测

规则：每个标签必须出现在这个分类体系中。如果需要新标签，先在这里添加，然后使用它。这可以防止标签泛滥。

#### Page Thresholds

- **创建一个页面** 当实体/概念出现在 2+个来源中 或 在一个来源中处于核心地位
- **添加到现有页面** 当来源提到已经涵盖的内容时
- **不要创建页面** 用于传递提及、次要细节或领域之外的内容
- **拆分页面** 当页面超过约 200 行时 — 拆分为带有交叉链接的子主题
- **归档页面** 当页面内容被完全取代时 — 移动到 `_archive/` ，从索引中移除

#### Entity Pages

每个重要实体对应一个页面。包括：

- Overview / what it is
- Key facts and dates
- 与其他实体的关系（\[\[wikilinks\]\]）
- Source references

#### Concept Pages

每个概念或主题单独成页。包括：

- Definition / explanation
- Current state of knowledge
- Open questions or debates
- 相关概念 (\[\[wikilinks\]\])

#### Comparison Pages

并排分析。包括：

- 比较的是什么，为什么
- 比较维度（建议使用表格形式）
- Verdict or synthesis
- Sources

#### Update Policy

当新信息与现有内容冲突时：

1. 检查日期——较新的来源通常会取代较旧的来源
2. 如果确实存在矛盾，需记录双方立场并标注日期和来源
3. 在前置内容中标记矛盾： `contradictions: [page-name]`
4. 在 lint 报告中标记供用户审核

### index.md Template

The index is sectioned by type. Each entry is one line: wikilink + summary.

```markdown
# Wiki Index

> Content catalog. Every wiki page listed under its type with a one-line summary.
> Read this first to find relevant pages for any query.
> Last updated: YYYY-MM-DD | Total pages: N

## Entities
<!-- Alphabetical within section -->

## Concepts

## Comparisons

## Queries
````

**缩放规则：** 当任何章节超过 50 个条目时，按首字母或子域将其拆分为子章节。当总条目数超过 200 时，创建一个 `_meta/topic-map.md` ，该文件按主题对页面进行分组以实现更快的导航。

##### log.md Template

```
# Wiki Log

> Chronological record of all wiki actions. Append-only.
> Format: `## [YYYY-MM-DD] action | subject`
> Actions: ingest, update, query, lint, create, archive, delete
> When this file exceeds 500 entries, rotate: rename to log-YYYY.md, start fresh.

## [YYYY-MM-DD] create | Wiki initialized
- Domain: [domain]
- Structure created with SCHEMA.md, index.md, log.md
```

#### Core Operations

##### 1\. Ingest

当用户提供一个来源（URL、文件、粘贴内容）时，将其整合到维基中：

① **捕获原始源：**

- URL → 使用 `web_extract` 获取 Markdown，保存到 `raw/articles/`
- PDF → 使用 `web_extract` （处理 PDF），保存到 `raw/papers/`
- 粘贴的文本 → 保存到合适的 `raw/` 子目录
- 描述性地命名文件： `raw/articles/karpathy-llm-wiki-2026.md`

② **讨论要点** 与用户——有趣的地方是什么，以及对该领域重要的内容是什么。（在自动化/定时任务场景中跳过此步骤——直接继续。）

③ **检查已存在的内容** — 搜索 index.md 并使用 `search_files` 查找已提及的实体/概念对应的现有页面。这就是不断发展的维基与一堆重复内容之间的区别。

④ **编写或更新维基页面：**

- \*\*新实体/概念：\*\* 仅当新实体/概念满足 SCHEMA.md 中的页面阈值（2 个以上来源提及或某一来源的核心内容）时，才创建页面
- **现有页面：** 添加新信息，更新事实，更新 `updated` 日期。当新信息与现有内容冲突时，遵循更新政策。
- **交叉引用：** 每一个新页面或已更新的页面必须通过\[\[wikilinks\]\]链接到至少 2 个其他页面。检查现有页面是否有反向链接。
- **标签：** 仅使用 SCHEMA.md 中分类体系里的标签

⑤ **更新导航：**

- 添加新页面到 `index.md` 的正确章节下，按字母顺序
- 更新索引头部中的"总页数"计数和"最后更新"日期
- Append to `log.md`: `## [YYYY-MM-DD] ingest | Source Title`
- 列出日志条目中创建或更新的每个文件

⑥ **报告变更内容** — 列出所有创建或更新的文件给用户。

单一来源可以触发5-15个维基页面的更新。这是正常且期望的——这就是复合效应。

##### 2\. Query

当用户询问关于 wiki 领域的问题时：

① **阅读 `index.md`** 以识别相关页面。② **对于拥有 100+ 页的维基** ，还需在所有 `.md` 文件中 `search_files` 关键术语 —— 仅靠索引可能会遗漏相关内容。③ **阅读相关页面** 使用 `read_file` 。④ **综合答案** 从整理的知识中生成。引用你参考的维基页面：“基于 \[\[page-a\]\] 和 \[\[page-b\]\]...” ⑤ **归档有价值的答案** —— 如果答案是实质性比较、深入分析或新颖的综合，请在 `queries/` 或 `comparisons/` 中创建一个页面。不要归档琐碎的查询 —— 仅归档重新推导时会很麻烦的答案。⑥ **更新 log.md** ，包含查询内容及是否已归档。

##### 3\. Lint

当用户要求对 Wiki 进行代码检查、健康检查或审计时：

① **孤立页面：** 查找没有来自其他页面的入站 `[[维基链接]]` 的页面。

```
# Use execute_code for this — programmatic scan across all wiki pages
import os, re
from collections import defaultdict
wiki = "<WIKI_PATH>"
# Scan all .md files in entities/, concepts/, comparisons/, queries/
# Extract all [[wikilinks]] — build inbound link map
# Pages with zero inbound links are orphans
```

② **失效的维基链接：** 查找指向不存在的页面的 `[[links]]`

③ **索引完整性：** 每个维基页面都应该出现在 `index.md` 中。将文件系统与索引条目进行比较。

④ **前置内容验证：** 每个维基页面必须包含所有必填字段（标题、创建时间、更新时间、类型、标签、来源）。标签必须属于分类体系。

⑤ **陈旧内容** ：页面的 `updated` 日期比提及相同实体的最新来源的日期早超过 90 天。

⑥ **矛盾** ：同一主题的页面存在相互矛盾的说法。寻找共享标签/实体但陈述不同事实的页面。

⑦ **页面大小：** 标记超过 200 行的页面——需要拆分的候选页面。

⑧ **标签审核：** 列出所有正在使用的标签，标记任何不在 SCHEMA.md 分类体系中的标签。

⑨ **日志轮转：** 如果 log.md 超过 500 条记录，轮转它。

⑩ **报告发现** ，包含具体文件路径和建议的操作，按严重程度分组（断链＞孤立页面＞过时内容＞样式问题）

⑪ **追加到 log.md：** `## [YYYY-MM-DD] lint | N issues found`

##### Searching

```
# Find pages by content
search_files "transformer" path="$WIKI" file_glob="*.md"

# Find pages by filename
search_files "*.md" target="files" path="$WIKI"

# Find pages by tag
search_files "tags:.*alignment" path="$WIKI" file_glob="*.md"

# Recent activity
read_file "$WIKI/log.md" offset=<last 20 lines>
```

##### Bulk Ingest

当同时导入多个来源时，批量处理更新：

1. Read all sources first
2. 识别所有来源中的所有实体和概念
3. 检查所有这些的现有页面（一次搜索遍历，不是 N 次）
4. 一次性创建/更新页面（避免重复更新）
5. 在最后更新一次 index.md
6. 编写一条涵盖该批次的日志记录

##### Archiving

当内容被完全取代或领域范围发生变化时：

1. 如果不存在，则创建 `_archive/` 目录
2. 将页面移动到 `_archive/` 并保持其原始路径（例如： `_archive/entities/old-page.md` ）
3. Remove from `index.md`
4. 更新任何链接到它的页面 — 将 wikilink 替换为纯文本并加上 "(archived)"
5. Log the archive action

##### Obsidian Integration

wiki 目录开箱即用，可作为 Obsidian vault 使用：

- `[[wikilinks]]` render as clickable links
- 图形视图可视化知识网络
- YAML 前置元数据支持 Dataview 查询
- 文件夹 `raw/assets/` 存储通过 `![[image.png]] 引用的图像`

For best results:

- 将 Obsidian 的附件文件夹设置为 `raw/assets/`
- 在 Obsidian 设置中启用“Wikilinks”（通常默认开启）
- 安装 Dataview 插件用于 `TABLE tags FROM "entities" WHERE contains(tags, "company") 之类的查询`

如果同时使用 Obsidian 技能与本技能，请将 `OBSIDIAN_VAULT_PATH` 设置为与 wiki 路径相同的目录。

##### Obsidian 无头版（服务器和无头机器）

在没有显示器的机器上，使用 `obsidian-headless` 替代桌面应用。它通过 Obsidian Sync 同步知识库（vaults），无需图形界面（GUI）——非常适合在服务器上运行的代理程序，这些代理程序向知识库（wiki）写入内容，而 Obsidian 桌面应用则在另一台设备上读取知识库内容。

**Setup:**

**通过 systemd 进行持续的后台同步：**

```
# ~/.config/systemd/user/obsidian-wiki-sync.service
[Unit]
Description=Obsidian LLM Wiki Sync
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=/path/to/ob sync --continuous
WorkingDirectory=/home/user/wiki
Restart=on-failure
RestartSec=10

[Install]
WantedBy=default.target
```

这允许代理在服务器上写入 `~/wiki` ，而当你在笔记本电脑/手机上的 Obsidian 中浏览同一个知识库时，更改会在几秒钟内显示出来。

#### Pitfalls

- **切勿修改 `raw/ 中的文件 — 源文件不可变。更正应提交到维基页面。`**
- **始终先明确方向** — 在新会话中进行任何操作前，请先阅读 SCHEMA + 索引 + 最近日志。跳过这一步会导致重复项和遗漏的交叉引用。
- 始终更新 index.md 和 log.md — 跳过这一步会使维基（wiki）退化。这些是导航的支柱。
- **不要为临时提及创建页面** — 请遵循 SCHEMA.md 中的页面阈值。一个名称在脚注中出现一次并不足以证明需要创建实体页面。
- **不要创建没有交叉引用的页面** — 孤立的页面是不可见的。每个页面必须至少链接到另外 2 个页面。
- **前置内容是必需的** — 它支持搜索、筛选和陈旧性检测。
- **标签必须来自分类体系** — 自由形式标签会逐渐变成噪声。首先将新标签添加到 SCHEMA.md 中，然后使用它们。
- **保持页面易读** — 维基页面应能在 30 秒内读完。将超过 200 行的页面拆分。将详细分析移至专门的深度分析页面。
- **大规模更新前先询问** — 如果一次导入会影响 10 个以上现有页面，请先与用户确认范围。
- **日志轮转** — 当 log.md 的条目数超过 500 时，将其重命名为 `log-YYYY.md` 并重新开始。代理应在 lint 过程中检查日志大小。
- **明确处理矛盾** ——不要悄无声息地覆盖。记录两个带日期的声明，在 frontmatter 中标记，并标记供用户审核。

### 2026-04-09 02:11:52

#### LLM Wiki：把知识库从 “临时检索” 升级为 “持续积累”

##### 一、核心观点

这篇文章介绍了一种 “LLM Wiki” 工作方式：不是像传统 RAG 那样每次提问都重新检索、重新拼接信息，而是把知识持续沉淀成一个长期维护的 Markdown 知识库。

它的本质是：**一次整合，多次复用，持续更新**。  
知识不再是 “查完即散”，而是逐步形成一个可追踪、可交叉引用、可校验的一套体系。

---

##### 二、它解决了什么问题

传统 RAG 的问题是：  
- 每次查询都像 “重新找资料”
- 容易重复发现相同信息
- 难以处理历史上下文与知识冲突
- 很难形成长期可维护的认知资产

LLM Wiki 的优势是：  
- 把知识沉淀为长期存在的页面
- 已有内容之间可以交叉链接
- 矛盾信息会被显式标记
- 查询时基于 “整理后的知识” 回答，而不是每次从零开始拼接

简单说，**RAG 更像临时搜索，LLM Wiki 更像长期经营知识资产**。

---

##### 三、整体结构怎么设计

文章把 Wiki 分成 3 层：

###### 1. 原始来源层
存放文章、论文、访谈、图片等原始资料，特点是：**只读、不可修改**。

###### 2. 知识页面层
把原始资料提炼成结构化页面，比如：  
- 实体页：人物、公司、产品、模型  
- 概念页：方法、主题、问题  
- 对比页：不同对象的比较  
- 查询页：值得保留的结论和分析

这是代理真正维护的核心知识层。

###### 3. 规则架构层
用`SCHEMA.md`统一规范，比如：  
- 命名规则
- 标签体系
- 页面结构
- 更新原则
- 页面拆分和归档标准

本质上，`SCHEMA.md`是这套知识库的 “宪法”。

---

##### 四、代理与人的分工

这套模式强调明确分工：

###### 人负责什么
- 决定知识库主题和边界
- 提供信息源
- 指导分析方向
- 审核关键冲突和大规模更新

###### 代理负责什么
- 总结资料
- 更新页面
- 建立交叉引用
- 维护索引和日志
- 检查一致性和健康度

也就是说，**人负责方向，代理负责整理和维护**。

---

##### 五、实际运行的关键流程

##### 1. 启动或恢复 Wiki

如果是新建 Wiki，需要先建立目录、索引、日志和 Schema。  
如果已经有 Wiki，每次会话开始都必须先做 “定位”：

- 读`SCHEMA.md`：理解规则
- 读`index.md`：了解已有页面
- 读最近的`log.md`：了解近期发生了什么

这一步很关键，因为它能避免：  
- 重复建页
- 漏掉已有关联
- 违反既有规范
- 重复做已经做过的工作

---

##### 2. 导入新资料

当用户给出文章、PDF 或文本时，流程不是 “直接总结”，而是：

- 先保存原始资料到`raw/`
- 判断资料中有哪些重要实体和概念
- 检查 Wiki 里是否已经存在相关页面
- 创建新页或更新旧页
- 为页面补上交叉链接
- 更新`index.md`和`log.md`

重点不在 “做一页摘要”，而在于**把新资料嵌入原有知识网络**。

---

##### 3. 回答问题

当用户提问时，代理应先查索引和相关页面，再基于整理好的 Wiki 内容回答。  
如果某次回答很有价值，比如形成了深度比较、综合判断或难得的结论，就应该把它沉淀为新的查询页或对比页，避免以后重复推导。

也就是说，**问答本身也能反过来扩充知识库**。

---

##### 4. 做健康检查（Lint）

文章非常强调 “知识库维护”，而不只是 “存内容”。  
健康检查主要看这些问题：

- 是否有孤立页面
- 是否存在失效链接
- 页面是否都被索引收录
- frontmatter 是否完整
- 标签是否符合分类体系
- 页面是否过时
- 是否有互相矛盾的信息
- 页面是否过长需要拆分
- 日志是否需要轮转

这说明 LLM Wiki 不只是 “记笔记”，而是**把知识库当成一个长期运行的系统来维护**。

---

##### 六、这套方法最重要的设计原则

###### 1. 原始资料不可改
`raw/`里的内容必须保持原样，修正和理解都应该写到知识页面里。

###### 2. 每个页面必须被连接
新页面至少要链接到 2 个其他页面，否则就会成为 “看不见的孤岛”。

###### 3. 不要为零散提及建页
只有当一个概念 / 实体足够重要，或者在多个来源中反复出现，才值得单独建页。

###### 4. 矛盾不能悄悄覆盖
如果新旧信息冲突，不能直接替换，而要保留双方说法、标记日期和来源，交给用户判断。

###### 5. 索引和日志必须持续更新
`index.md`是导航中枢，`log.md`是操作记录。缺了这两个，Wiki 很快会失控。

---

##### 七、为什么它对产品、研究和商业分析有价值

对产品经理、研究者、投资分析、行业观察者来说，这套方式很有意义，因为它能把碎片化的信息输入变成长期复用的认知资产。

它特别适合这些场景：  
- 长期跟踪某个行业或赛道
- 研究公司、产品、人物、技术演化
- 做竞争分析和主题比较
- 把零散信息沉淀为结构化洞察
- 让团队知识逐步积累，而不是反复从头搜索

一句话概括：**它把 “信息处理” 升级成了 “知识经营”**。

---

##### 八、文章的最终启示

这篇文章真正想表达的不是 “怎么记 Markdown 笔记”，而是：

**如何让 AI 参与构建一个持续生长、可审计、可复用、可协作的知识系统。**

它比传统笔记更结构化，比传统 RAG 更稳定，也比一次性总结更有复利。  
核心价值不在 “快速回答一个问题”，而在于**随着时间推移，让知识越来越完整、越来越可靠、越来越有网络效应**。

## 结构化（1）

### 2026-04-09 02:12:40

#### 文章主旨

这篇文档介绍了一套 “LLM Wiki” 工作方法：用一个持续积累、可交叉引用的 Markdown 知识库，替代每次都从头检索的传统 RAG。核心思想是：**把知识一次次沉淀下来、保持结构化更新，并通过规范、索引和日志保证长期可维护性**。

#### 1. 这套方案解决什么问题

- 它的目标是构建一个**持久、互联、可演化**的知识库，文件本质上就是一组 Markdown。
- 与传统 RAG 不同，LLM Wiki 不强调 “每次查询都重新发现知识”，而是强调：
  - 已有知识会被长期保存；
  - 页面之间已有交叉引用；
  - 矛盾信息会被明确标记；
  - 新回答基于已经整理过的内容综合生成。
- 人和代理的分工很明确：
  - **人类**负责管理信息源、指导研究方向；
  - **代理**负责总结、归档、交叉引用和一致性维护。

**通俗理解：**
传统 RAG 像 “每次提问都重新去图书馆找资料”；LLM Wiki 更像 “先把图书馆整理成自己的知识手册，以后越来越好用”。

#### 2. 什么时候使用这个技能

文档建议在以下场景使用：

- 用户想创建、搭建或启动一个 wiki / 知识库；
- 用户要把某个来源导入到现有知识库；
- 用户基于已有 wiki 提问；
- 用户要做 wiki 的校验、审计、健康检查；
- 用户在研究场景中提到自己的 wiki、知识库或 “笔记”。

**重点：**
只要已经存在配置好的 wiki 路径，后续查询、导入、校验都应该围绕这个知识库展开，而不是绕开它单独回答。

#### 3. Wiki 的基础结构与三层设计

##### 3.1 Wiki 路径

- 路径通过`~/.hermes/config.yaml`配置：
  ```yaml
  skills:
    config:
      wiki:
        path: ~/wiki
  ```
- 如果没有配置，就回退到默认路径`~/wiki`。

##### 3.2 目录结构

文档给出的标准结构如下：

- `SCHEMA.md`：规范、结构规则、标签体系；
- `index.md`：内容总目录，带一行摘要；
- `log.md`：操作日志，按时间追加；
- `raw/`：原始资料层，不可修改；
- `entities/`：实体页，如人物、组织、产品、模型；
- `concepts/`：概念页；
- `comparisons/`：对比分析页；
- `queries/`：值得保存的查询结果。

##### 3.3 三层架构

- **第 1 层：原始来源**
  - 放在`raw/`下；
  - 只读、不可变；
  - 例如网页文章、PDF、访谈记录、图片。
- **第 2 层：知识库页面**
  - 代理创建和维护；
  - 可以更新、补充、交叉引用。
- **第 3 层：架构规范**
  - 由`SCHEMA.md`定义；
  - 约束页面格式、标签体系、更新规则。

**核心价值：**
把 “原始资料” 和 “整理后的知识” 分开，避免把事实、来源和总结混在一起。

#### 4. 使用已有 Wiki 时，必须先做 “定向恢复”

这是全文最强调的流程之一：**每次新会话开始时，都必须先理解现有 wiki，再做任何导入、查询或检查。**

##### 必做 3 步

1. 读`SCHEMA.md`：了解领域、命名规范、标签体系；
2. 读`index.md`：了解有哪些页面和摘要；
3. 看`log.md`最近 20–30 条：了解近期做了什么。

##### 这样做能避免的问题

- 重复创建已经存在的页面；
- 漏掉已有内容的交叉引用；
- 违反现有 schema 约定；
- 重复做已经记录过的工作。

##### 对大型 Wiki 的补充要求

- 如果 wiki 超过**100 页**，在创建新内容前，还要先做一次快速搜索。

**通俗例子：**
如果用户要导入一篇关于 Transformer 的文章，而知识库里已经有`transformer-architecture.md`和`attention.md`，不先定向恢复，就很容易又新建一个重复页面。

#### 5. 如何从零创建一个 Wiki

当用户要求 “创建 / 启动一个 wiki” 时，流程是：

- 确定 wiki 路径；
- 创建标准目录结构；
- 询问 wiki 的具体领域；
- 为该领域编写定制的`SCHEMA.md`；
- 写初始版`index.md`；
- 写初始版`log.md`，记录创建行为；
- 告诉用户 wiki 已可用，并建议首批导入来源。

**关键点：**
文档强调领域一定要具体，比如不是笼统的 “AI”，而是更明确的 “AI/ML research”“personal health”“startup intelligence” 等。

#### 6. `SCHEMA.md`：整个系统的规则中心

`SCHEMA.md`是这套方法的核心，作用是让代理行为保持一致。

##### 6.1 基本规范

- 文件名必须小写、连字符、不能有空格；
- 每个页面都必须有 YAML frontmatter；
- 页面之间必须用`[[wikilinks]]`连接；
- 每页至少有**2 个对外链接**；
- 每次更新页面都要修改`updated`日期；
- 每个新页面都必须加入`index.md`；
- 每个操作都必须写入`log.md`。

##### 6.2 Frontmatter 必填项

每个页面必须包含：

- `title`
- `created`
- `updated`
- `type`
- `tags`
- `sources`

##### 6.3 标签体系

- 文档建议每个领域定义**10–20 个顶级标签**；
- 所有页面标签必须来自这个分类体系；
- 如果需要新标签，必须先加到`SCHEMA.md`，再在页面里使用。

**意义：**
这样可以防止标签无限膨胀，最后失控。

##### 6.4 页面创建阈值

只有满足以下条件才创建独立页面：

- 一个实体 / 概念出现在**2 个以上来源**中；
- 或者它是某个单一来源的核心主题。

如果只是顺带提到、次要细节、领域外信息，就不该建页。

##### 6.5 页面拆分与归档

- 页面超过约**200 行**：应拆成子主题；
- 页面内容被完全替代：移到`_archive/`。

#### 7. 各类页面应该写什么

##### 实体页`entities/`

每个重要实体一个页面，包含：

- 它是什么；
- 关键事实和时间；
- 与其他实体的关系；
- 来源引用。

##### 概念页`concepts/`

每个概念独立成页，包含：

- 定义 / 解释；
- 当前认知状态；
- 开放问题或争议；
- 相关概念链接。

##### 对比页`comparisons/`

用于并排分析，包含：

- 比较对象和原因；
- 比较维度（推荐表格）；
- 综合结论；
- 来源。

**例子：**
如果比较两个模型，不应该只写优缺点，而要明确比较维度，例如参数规模、训练成本、推理速度、基准测试结果。

#### 8. `index.md`和`log.md`：导航与可追溯性的支柱

##### 8.1 `index.md`

- 按类型分节列出所有页面；
- 每个条目只保留一行：`wikilink + 一句话摘要`；
- 头部要写：
  - 最后更新时间；
  - 总页数。

###### 扩展规则

- 某一章节超过**50 条**：按首字母或子领域再拆分；
- 总条目超过**200 条**：增加`_meta/topic-map.md`做主题导航。

##### 8.2 `log.md`

- 记录所有操作；
- 采用 append-only 方式，只追加不覆盖；
- 日志动作包括：`ingest`、`update`、`query`、`lint`、`create`、`archive`、`delete`。

###### 轮转规则

- 当`log.md`超过**500 条记录**时：
  - 重命名为`log-YYYY.md`；
  - 新建新的`log.md`。

**意义：**
`index.md`解决 “去哪里找”，`log.md`解决 “什么时候发生了什么”。

#### 9. 核心操作一：导入（Ingest）

当用户给出 URL、PDF 或粘贴文本时，要把它整合进 wiki。

##### 导入流程

###### 1）保存原始来源

- URL → 抽取为 Markdown，存入`raw/articles/`
- PDF → 存入`raw/papers/`
- 粘贴文本 → 存入合适的`raw/`子目录

文件名要具有描述性，例如：
- `raw/articles/karpathy-llm-wiki-2026.md`

###### 2）和用户讨论重点

- 在普通交互场景下，先问用户：这篇资料哪里最重要、最值得关注。
- 在自动化 / 定时任务中可跳过。

###### 3）检查已有内容

- 搜索`index.md`
- 搜索现有页面中是否已有相关实体 / 概念

###### 4）创建或更新页面

- 新实体 / 概念：只有达到建页阈值时才建页；
- 旧页面：补充信息、更新事实、改`updated`日期；
- 若出现冲突：按 “更新策略” 处理；
- 每个新 / 改页面都要链接到至少**2 个其他页面**；
- 只允许使用 schema 中已有标签。

###### 5）更新导航和日志

- 把新页面按字母顺序加入`index.md`；
- 更新 “总页数” 和 “最后更新时间”；
- 把此次导入记录追加到`log.md`。

###### 6）向用户汇报变更

- 列出所有新建 / 更新的文件。

##### 特别提醒

- 文档明确说：**单一来源触发 5–15 个页面更新是正常的。**
- 这体现的是知识库的 “复利效应”。

**例子：**
一篇关于 OpenAI 新模型的文章，可能同时影响：
- 某个模型实体页；
- 推理概念页；
- 对齐概念页；
- 公司实体页；
- 与竞品的 comparison 页。

#### 10. 核心操作二：查询（Query）

当用户提问时，不应直接凭空回答，而应基于 wiki 内容综合。

##### 查询流程

1. 读`index.md`找相关页面；
2. 如果 wiki 超过**100 页**，还要全文搜索关键词；
3. 读取相关页面；
4. 基于这些页面综合回答；
5. 如果答案很有价值，归档到`queries/`或`comparisons/`；
6. 把这次查询写入`log.md`。

##### 什么样的回答值得归档

- 实质性的比较；
- 深度分析；
- 新颖综合；
- 重新推导成本高的答案。

##### 什么不该归档

- 琐碎、一次性的简单问答。

**通俗理解：**
不是每个回答都要入库，只有 “以后很可能还会用到” 的内容才值得沉淀。

#### 11. 核心操作三：检查（Lint / Audit）

当用户要做健康检查或审计时，需要系统性检查 wiki 的结构问题。

##### 需要检查的 10 类问题

1. **孤立页面**：没有任何入站`[[wikilinks]]`；
2. **失效链接**：链接指向不存在页面；
3. **索引完整性**：实际存在的页面是否都列在`index.md`；
4. **Frontmatter 完整性**：字段是否齐全，标签是否合法；
5. **内容过时**：`updated`比最新相关来源晚了**90 天以上**；
6. **矛盾信息**：多个页面对同一事实给出冲突说法；
7. **页面过大**：超过**200 行**；
8. **标签审计**：是否出现 schema 外标签；
9. **日志轮转**：`log.md`是否超过**500 条**；
10. **输出报告**：按严重程度排序，优先级为：
   - 断链 ＞ 孤立页面 ＞ 过时内容 ＞ 样式问题

##### 输出要求

- 要给出**具体文件路径**
- 要附上**建议动作**
- 还要在`log.md`中记录本次 lint 结果。

**重点：**
lint 不只是检查格式，更是在做知识库健康管理。

#### 12. 批量导入与归档规则

##### 批量导入（Bulk Ingest）

当一次导入多个来源时，文档建议：

- 先读完所有来源；
- 一次性识别全部实体和概念；
- 一次性检查已有页面；
- 一次性批量更新页面；
- 最后统一更新`index.md`和`log.md`。

**好处：**
避免多次重复更新同一页面，提高一致性。

##### 归档（Archiving）

当内容完全被替代或领域范围改变时：

- 创建`_archive/`（如果还没有）；
- 把页面移动到`_archive/`下，保留原路径结构；
- 从`index.md`移除；
- 更新其他页面里指向它的链接，改成纯文本并标注`(archived)`；
- 在日志中记录归档动作。

#### 13. Obsidian 集成与无头同步

##### 13.1 为什么适合 Obsidian

这个 wiki 本身就是 Markdown 文件夹，所以天然适配 Obsidian：

- `[[wikilinks]]`可点击；
- 图谱视图可看知识网络；
- YAML metadata 可被 Dataview 查询；
- `raw/assets/`可存放图片等附件。

##### 13.2 推荐设置

- Obsidian 附件目录设为`raw/assets/`
- 启用 Wikilinks
- 安装 Dataview 插件

文档还给出一个 Dataview 查询例子：
- `TABLE tags FROM"entities"WHERE contains (tags,"company")`

对于没有图形界面的机器，文档推荐使用**obsidian-headless**，并通过 Obsidian Sync 同步 vault。

- 代理在服务器写入`~/wiki`；
- 用户可以在笔记本或手机的 Obsidian 中几秒内看到更新。

**实际价值：**
很适合 “服务器上的代理持续写知识库，人在其他设备上查看” 的工作流。

#### 14. 常见陷阱与操作边界

文档最后总结了很多容易犯错的点：

- **绝不能修改`raw/`**
  - 原始来源必须保持不可变；
  - 更正只能写到知识页面中。
- **必须先做定向恢复**
  - 跳过会导致重复页和漏链。
- **必须更新`index.md`和`log.md`**
  - 否则 wiki 会逐渐失去导航和可追踪性。
- **不要为偶然提及建页**
  - 只有达到阈值才值得建页。
- **不要创建孤立页面**
  - 每页至少链接到**2 个其他页面**。
- **Frontmatter 是必须的**
  - 否则无法搜索、筛选、判断是否过时。
- **标签必须来自 taxonomy**
  - 自由标签会迅速变成噪音。
- **页面要控制可读性**
  - 理想状态是**30 秒内能读完**；
  - 超过**200 行**应拆分。
- **大规模更新前先确认**
  - 如果一次导入会影响**10 个以上现有页面**，应先和用户确认范围。
- **矛盾不能悄悄覆盖**
  - 必须保留双方说法、日期和来源，并标记供人工审核。

#### 总结

这篇文档本质上是在定义一套 “可长期维护的 AI 知识库操作系统”：用`SCHEMA.md`管规则，用`index.md`管导航，用`log.md`管追踪，用`raw/`和知识页分层管理事实与总结。它最重要的价值不只是 “能记笔记”，而是让知识在不断导入、查询、校验中**持续积累、减少重复劳动，并形成越来越强的结构化复利**。

## 产品-技术开发实现（1）

### 2026-04-09 02:15:11

这是一个很成熟的 “AI 持续知识操作系统” 设计，不是普通笔记库，也不是传统 RAG。它的核心价值在于：把 “每次临时检索” 升级为 “长期积累、持续校正、结构化演进” 的知识资产。

**核心判断**
- 产品上，它解决的是 “研究知识无法沉淀、重复加工、前后不一致” 这三个高频痛点。
- 技术上，它采用`raw source -> curated wiki -> schema governance`的三层架构，本质是 “可审计的知识编译系统”。
- 与 RAG 相比，优势不是召回率，而是 “可持续更新、一致性、交叉引用、可追溯”。
- 适合研究团队、投研、竞争情报、政策分析、实验记录，不适合强事务型业务数据。

**产品设计解读**
- `raw/`不可变：这是证据层，保证溯源、复盘、审计。产品上相当于 “事实仓库”。
- `entities/concepts/comparisons/queries`：这是认知层，把碎片材料转成可复用知识对象。
- `SCHEMA.md`：这是治理层，定义分类法、命名规则、页面阈值、更新政策，避免知识库失控。
- `index.md + log.md`：一个负责导航，一个负责时间线，分别解决 “找得到” 和 “说得清怎么来的”。

最佳实践例子：
```text
错误做法：把所有文章摘要堆在一个 docs/ 目录里，靠搜索找。
正确做法：
- 原文进入 raw/articles/
- “OpenAI” 进 entities/openai.md
- “测试时计算 scaling” 进 concepts/test-time-compute.md
- “OpenAI vs Anthropic” 进 comparisons/openai-vs-anthropic.md
- 某次关于 agent memory 的综合问答沉淀到 queries/agent-memory-landscape.md
```

**为什么这比传统 RAG 更高级**
- RAG 每次 query 都重新切片、召回、拼接，容易结果漂移。
- 这个方案先把知识 “编译” 为结构化 Markdown，再查询 “已整理知识”。
- 结果是：
  - 同一概念不会反复总结
  - 矛盾信息可以显式标记
  - 链接网络会越来越强
  - 查询成本随时间下降，而不是一直重复算力消耗

适用场景例子：
- AI 研究团队：维护模型、论文、人物、路线图
- 战略团队：维护公司、产品、融资、组织关系
- 医疗 / 法务研究：维护概念、案例、争议、时效性变化

**设计上的亮点**
- “先定向再操作” 非常关键：先读`SCHEMA.md`、`index.md`、`log.md`，相当于让 agent 先做 context bootstrapping。
- “页面阈值” 设计很好：只有 2+ 来源提及或单一来源核心主题才建页，能抑制知识膨胀。
- “至少 2 个 outbound links” 很聪明：强制形成知识网络，降低孤岛率。
- “矛盾不覆盖，而是显式记录” 是高质量知识库的标志，尤其适合快速变化领域。

**工程实现上最值得借鉴的部分**
- Markdown + 文件夹，而不是数据库优先：低门槛、可迁移、对人类友好、兼容 Obsidian/VS Code/Git。
- Frontmatter 规范化：让 agent 可以稳定读写元数据，支持 lint、筛选、审计。
- `log.md` append-only：天然适合追踪 agent 行为，也方便做回放和责任边界划分。
- lint 机制不是可选项，而是知识库长期可用性的保障。

推荐的数据模型：
```yaml
---
title: Test-Time Compute
created: 2025-02-01
updated: 2025-02-10
type: concept
tags: [inference, scaling, evaluation]
sources:
  - raw/articles/openai-o1-analysis-2025.md
  - raw/papers/test-time-scaling-2025.md
contradictions: [reasoning-costs.md]
---
```

**从产品到技术的最佳实践**
- 人负责 “定义边界和判断价值”，agent 负责 “提炼、交叉引用、维护一致性”。
- 不要让 agent 自由发明 taxonomy，标签体系必须先在`SCHEMA.md`中治理。
- 导入多个来源时做 batch ingest，不要一个来源更新一次 index，避免重复写和结构震荡。
- 对 “查询结果是否归档” 设门槛，只有难复现、强综合、高价值内容才进入`queries/`。

一个很实用的团队流程：
```text
1. 研究员每天丢 5 篇文章 / 2 份报告 / 会议纪要到 raw/
2. agent 每天定时 ingest，更新相关 entities/concepts/comparisons
3. 每周跑一次 lint，修复断链、孤儿页、过时页
4. 每月人工 review taxonomy 和高冲突页面
```

**如果你要把它做成产品，建议这样落地**
- 第一层：文件系统 + Markdown，先跑通单机知识流
- 第二层：加 ingestion pipeline
  - URL 抓取
  - PDF 解析
  - OCR /transcript
  - 元数据抽取
- 第三层：加知识治理
  - link checker
  - schema validator
  - stale detector
  - contradiction detector
- 第四层：加交互层
  - 问答入口
  - entity/concept 自动建议
  - “建议归档该回答” 按钮
  - 变更 diff 可视化

一个可落地的后端模块划分：
```text
ingestion-service
- fetch_url ()
- parse_pdf ()
- normalize_markdown ()
- save_raw_source ()

wiki-compiler
- extract_entities ()
- extract_concepts ()
- resolve_existing_pages ()
- update_or_create_pages ()
- update_index ()
- append_log ()

wiki-linter
- check_broken_links ()
- check_orphans ()
- validate_frontmatter ()
- detect_staleness ()
- detect_tag_drift ()
- detect_contradictions ()
```

**几个关键风险**
- 最大风险不是模型能力，而是知识治理失控：标签泛滥、页面重复、链接失效、索引不更新。
- 如果没有`SCHEMA.md`，最后会退化成 “AI 自动生成的一堆碎片文档”。
- 如果修改`raw/`，就破坏证据链，后续无法审计。
- 如果不做 lint，6 个月后知识库可用性会急剧下降。

**最值得产品化的增强点**
- 自动提议 “该内容应更新哪些现有页面”，而不是只会新建页面。
- 基于来源时间和可信度做冲突优先级排序。
- 在查询时显示 “答案来自哪些 wiki 页面 + 哪些 raw source”。
- 自动生成 topic map，而不只是 index。
- 对大规模更新加审批流，防止 agent 一次改坏 20 个页面。

**一个更高级的 AI 最佳实践**
- 不要把 LLM 放在 “最终答案生成器” 位置，而要放在 “知识编译器” 和 “知识维护器” 位置。
- 真正高价值的模式是：
  - LLM 负责吸收新资料
  - 结构化知识库负责长期记忆
  - lint / 规则负责一致性
  - 人类负责最终判断和边界校正

一句话总结：
- 这套设计的本质不是 “让 AI 更会搜”，而是 “让 AI 帮你持续建设一个可追溯、可维护、可复用的研究大脑”。

#### 基于 LLM Wiki 的最佳实践示例

下面我用一个具体实例来说明：如果你要把`hermes-agent/skills/research/llm-wiki/SKILL.md`里的方法真正落地，怎样做才算是 “最佳实践”。

---

##### 实例场景

假设你要建立一个面向**AI 模型研究追踪**的知识库，路径为：

```bash
~/wiki
```

你的目标不是做一个 “临时检索库”，而是做一个会持续积累、可交叉引用、可审计、可在 Obsidian 中浏览的 Markdown Wiki。

这个 Wiki 主要记录：

- 大模型与多模态模型
- 模型公司与研究机构
- 关键技术概念
- 模型之间的比较
- 重要研究结论与长期可复用问答

---

##### 一、最佳实践总原则

基于原文，一个高质量的 LLM Wiki 实践，核心不是 “多存资料”，而是做到下面 5 点：

1. **原始资料与知识页面严格分层**
   - `raw/`只存原始来源，不修改。
   - `entities/`、`concepts/`、`comparisons/`、`queries/`才是被整理后的知识层。

2. **每次操作前先 “定位” 现有 Wiki**
   - 先读`SCHEMA.md`
   - 再读`index.md`
   - 再读最近的`log.md`
   - 如果 Wiki 很大，再全文搜索相关主题  
   这是避免重复建页、漏掉交叉引用、破坏既有规范的关键步骤。

3. **把 Wiki 当作 “长期维护的知识产品”，不是一次性摘要**
   - 每次导入资料时，不只是总结新来源，而是要更新已有页面、补链接、修矛盾、更新导航。

4. **所有知识都要可追溯**
   - 每个页面必须有 frontmatter
   - 每条结论应能追到`sources`
   - 冲突信息不能静默覆盖，必须显式记录

5. **导航和审计与内容本身同等重要**
   - `index.md`决定 “找不找得到”
   - `log.md`决定 “看不看得懂演化过程”
   - `lint`决定 “系统会不会慢慢烂掉”

---

##### 二、具体实例：导入一篇关于 GPT-4.1 的文章

假设你拿到一个新来源：

- 来源标题：`OpenAI GPT-4.1 Technical Notes`
- 来源类型：网页文章
- 预期影响主题：
  - GPT-4.1
  - OpenAI
  - 长上下文
  - 推理能力
  - 模型比较

---

##### 三、最佳实践做法

###### 1. 先完成会话级定位

在任何导入之前，先读这 3 个文件：

```markdown
SCHEMA.md
index.md
log.md
```

###### 为什么这是最佳实践

因为如果你不先定位，很容易出现：

- 已经有`gpt-4.md`，你又新建了`gpt-4-1.md`
- 已经有`openai.md`，你却没把新模型挂回去
- 已经有 “长上下文” 概念页，但你又重复建了一页
- 用户上周刚做过同一来源的导入，你却又做一遍

###### 这个实例里应该怎么做

你先看`index.md`，发现已有页面：

- `[[openai]]`
- `[[gpt-4]]`
- `[[context-window]]`
- `[[model-comparison-openai-series]]`

这时就知道：**不应从零开始写 4 个新页面**，而应优先考虑 “更新已有页面 + 只在必要时新建页面”。

---

###### 2. 原始来源先落到`raw/`，且永不修改

把网页文章保存为：

```markdown
raw/articles/openai-gpt-4-1-technical-notes-2026.md
```

###### 为什么这是最佳实践

这保证了：

- 原始证据不会被后续整理污染
- 知识页中的观点都能回溯来源
- 日后出现争议时，可以重新审阅原始材料

###### 不好的做法

- 直接在知识页里贴全文
- 把原始资料和总结混写在同一个文件里
- 后续 “修正原始资料”

这些都会破坏可追溯性。

---

###### 3. 先判断 “更新旧页” 还是 “创建新页”

根据原文规则，只有在以下情况才创建新页面：

- 该实体 / 概念在 2 个以上来源中出现
- 或者它在当前来源中是核心内容

###### 这个实例的判断

- `OpenAI`：明显已有，应更新`entities/openai.md`
- `长上下文`：已有概念页，应更新`concepts/context-window.md`
- `GPT-4.1`：若这是当前来源核心主题，则应新建  
  `entities/gpt-4-1.md`
- `OpenAI 系列模型比较`：如果新文章改变了比较结论，可更新  
  `comparisons/model-comparison-openai-series.md`

###### 最佳实践建议

不要因为文章里提到十几个术语，就全部建页。  
**临时提及不建页，核心对象才建页。**

---

###### 4. 新页面必须从第一天就可融入知识网络

比如你创建：

```markdown
entities/gpt-4-1.md
```

应至少包含：

```yaml
---
title: GPT-4.1
created: 2026-03-10
updated: 2026-03-10
type: entity
tags: [models, architecture, inference]
sources: [raw/articles/openai-gpt-4-1-technical-notes-2026.md]
---
```

正文中应主动链接到至少两个现有页面，例如：

```markdown
# GPT-4.1

GPT-4.1 是 [[openai]] 发布的新一代模型，重点强化了长上下文处理与推理表现，可与 [[gpt-4]] 和 [[context-window]] 一并理解。

## Overview

...

## Related
- [[openai]]
- [[gpt-4]]
- [[context-window]]
- [[model-comparison-openai-series]]
```

###### 为什么这是最佳实践

因为 “孤立页面” 等于不存在。  
只创建文件、不做交叉引用，Wiki 很快就会退化成资料堆。

---

###### 5. `index.md`必须同步更新，而不是事后补

创建了`gpt-4-1.md`后，应立即把它加入：

```markdown
## Entities
- [[gpt-4-1]] - OpenAI 新一代模型，强调长上下文与推理能力。
```

同时更新头部：

```markdown
> Last updated: 2026-03-10 | Total pages: 37
```

###### 为什么这是最佳实践

`index.md`是全局导航中心。  
如果页面存在但没进索引，后续查询和维护都容易漏掉。

###### 实务建议

不要等 “这批都做完再说”，而是把 “更新索引” 视为导入流程中的必做步骤。

---

###### 6. `log.md`要记录 “发生了什么”，而不是只写 “已处理”

例如：

```markdown
## [2026-03-10] ingest | OpenAI GPT-4.1 Technical Notes
- Added raw source: raw/articles/openai-gpt-4-1-technical-notes-2026.md
- Created: entities/gpt-4-1.md
- Updated: entities/openai.md
- Updated: concepts/context-window.md
- Updated: comparisons/model-comparison-openai-series.md
```

###### 为什么这是最佳实践

好的日志能回答：

- 这条来源什么时候进来的？
- 它影响了哪些页面？
- 是创建了什么，还是只更新了什么？
- 以后如果发现问题，要回滚思路时从哪里查？

---

###### 7. 冲突信息要 “并存标记”，不要静默覆盖

假设旧页面写的是：

- `GPT-4`在某项基准上优于前代

新来源却说：

- `GPT-4.1`在该任务上的表现重新定义了最优结果

###### 最佳实践做法

不是直接把旧说法删掉，而是：

- 对比来源日期
- 标注 “新来源更晚”
- 如果结论冲突明显，则在页面 frontmatter 标记：

```yaml
contradictions: [gpt-4]
```

正文里明确写：

```markdown
Earlier sources described [[gpt-4]] as leading on this benchmark, but the 2026-03-10 source for [[gpt-4-1]] claims improved performance under updated evaluation settings.
```

###### 为什么这是最佳实践

知识库的价值，不在于 “看起来统一”，而在于 “真实呈现知识演化”。

---

###### 8. 查询结果只归档 “高价值答案”

如果用户问：

> GPT-4.1 和 GPT-4 在长上下文上的差异是什么？

你应该先读取相关页面，综合回答。  
但不是每个问答都保存。

###### 应该归档的情况

如果回答是：

- 多页综合后的深度分析
- 难以再次快速重建的比较
- 对长期研究有复用价值

那么可创建：

```markdown
queries/gpt-4-1-vs-gpt-4-context-window.md
```

或者：

```markdown
comparisons/gpt-4-1-vs-gpt-4.md
```

###### 不应归档的情况

- 简单事实问答
- 一句话即可回答的问题
- 低复用价值的即时查询

###### 为什么这是最佳实践

否则`queries/`会迅速变成垃圾堆。

---

###### 9. 定期 lint，比 “内容越写越多” 更重要

在这个实例中，随着页面增长，你应定期检查：

- 是否有孤立页面
- 是否有失效 wikilink
- 是否所有页面都进了`index.md`
- 是否 frontmatter 缺字段
- 是否用了 taxonomy 外的标签
- 是否有 200 行以上应拆分页面
- 是否有过时结论未更新
- 是否存在冲突未标记

###### 这个实例中，可能出现的问题

比如你新建了`gpt-4-1.md`，但：

- 忘了把旧页面加回链
- `index.md`没更新
- 标签写成了`openai-model`，但 taxonomy 里没有
- 页面写到 260 行还没拆分

这些都应该在 lint 中暴露。

###### 为什么这是最佳实践

Wiki 不是 “写完就完”，而是 “必须防止结构性腐烂”。

---

###### 10. 大规模更新前，先和用户确认范围

原文里有一个非常实用的原则：

> 如果一次导入会影响 10 个以上现有页面，先与用户确认范围。

###### 这个实例中为什么重要

一篇关于 OpenAI 新模型的深度文章，可能会连带更新：

- `openai.md`
- `gpt-4.md`
- `gpt-4-1.md`
- `context-window.md`
- `inference.md`
- `benchmarking.md`
- `alignment.md`
- 多个 comparison 页

如果你不先确认，用户可能本来只想 “先收进去”，而你却做了大规模重构。

###### 最佳实践

先说清楚：

- 预计影响哪些页面
- 会不会新建页面
- 会不会改比较结论
- 是否只做轻量导入，还是做深度整合

##### 四、一个推荐的目录与文件样例

##### 五、在该实例之上的 “最佳实践清单”

下面这部分最适合直接拿去执行。

###### 内容管理

- **先定位再操作**：任何新会话先读`SCHEMA.md`、`index.md`、最近的`log.md`
- **原始资料不可变**：`raw/`只新增，不修改
- **先更新旧页，再考虑新建页**：避免重复与碎片化
- **每页至少两个外链**：保证知识网络连通
- **高价值结论才归档为`queries/`或`comparisons/`**

###### 结构治理

- **每页强制 frontmatter**：标题、创建时间、更新时间、类型、标签、来源缺一不可
- **标签只允许来自 taxonomy**：新标签先加到`SCHEMA.md`
- **超过 200 行就拆分**：避免单页膨胀失控
- **章节过大就分层索引**：50+ 条目分子节，200+ 页面建`_meta/topic-map.md`

###### 一致性维护

- **冲突信息显式记录**：不要静默覆盖旧观点
- **索引与日志必须同步更新**：否则 Wiki 会迅速失去可维护性
- **定期 lint**：重点查断链、孤儿页、缺 frontmatter、标签污染、过时内容
- **大规模变更先确认范围**：尤其是会影响 10+ 页面时

###### 工具协同

- **Obsidian 作为阅读层很合适**：适合图谱浏览与手工巡检
- **服务器上用 obsidian-headless 持续同步**：适合代理写入、人在别处阅读
- **Dataview 适合作为 “轻查询层”**：但不能替代`index.md`和`log.md`

---

##### 六、一个简化的标准操作流程

如果以后你要真的执行一次导入，可以按这个流程：

```markdown
1. 读取 SCHEMA.md/index.md/ 最近 log.md
2. 保存原始来源到 raw/
3. 搜索现有相关页面
4. 判断哪些更新、哪些新建
5. 补充 wikilinks 和 sources
6. 更新 index.md
7. 追加 log.md
8. 运行 lint 检查孤儿页、断链、标签和 frontmatter
9. 向用户汇报创建 / 更新了哪些文件
```

##### 七、结论

这个技能最值得借鉴的地方，不是 “把资料存成 Markdown”，而是它把知识管理变成了一个可持续的工程流程：

- `raw/`保证证据层稳定
- `SCHEMA.md`保证行为一致
- `index.md`保证知识可导航
- `log.md`保证演化可追踪
- `lint`保证系统长期不腐烂

如果用一句话概括这个实例上的最佳实践，就是：

> **把 Wiki 当作一个持续演进的知识操作系统，而不是一次性的笔记集合。**
