## 正文

Memory lets your agent learn and improve across conversations. Deep Agents makes memory first class with filesystem-backed memory: the agent reads and writes memory as files, and you control where those files are stored using [backends](https://docs.langchain.com/oss/python/deepagents/backends).

#### How memory works

1. **Point the agent at memory files.** Pass file paths to `memory=` when creating the agent. You can also pass [skills](https://docs.langchain.com/oss/python/deepagents/skills) via `skills=` for procedural memory (reusable instructions that tell the agent *how* to perform a task). A [backend](https://docs.langchain.com/oss/python/deepagents/backends) controls where files are stored and who can access them.
2. **Agent reads memory.** The agent can load memory files into the system prompt at startup, or read them on demand during the conversation. For example, [skills](https://docs.langchain.com/oss/python/deepagents/skills) use on-demand loading: the agent reads only skill descriptions at startup, then reads the full skill file only when it matches a task. This keeps context lean until a capability is needed.
3. **Agent updates memory (optional).** When the agent learns new information, it can use its built-in `edit_file` tool to update memory files. Updates can happen during the conversation (the default) or in the background between conversations via background consolidation. Changes are persisted and available in the next conversation. Not all memory is writable: developer-defined [skills](https://docs.langchain.com/oss/python/deepagents/skills) and organization policies are typically read-only. See read-only vs writable memory for details.

The two most common patterns are agent-scoped memory (shared across all users) and user-scoped memory (isolated per user). For a generated repository wiki that coding agents discover through [`AGENTS.md`](https://agents.md/), see [OpenWiki](https://docs.langchain.com/oss/openwiki/overview).

#### Scoped memory

Agent memory can be scoped so the same memory files are accessible to everyone using the agent or memory files can be individual to each user.

##### Agent-scoped memory

Give the agent its own persistent identity that evolves over time. Agent-scoped memory is shared across all users, so the agent builds up its own persona, accumulated knowledge, and learned preferences through every conversation. As it interacts with users, it develops expertise, refines its approach, and remembers what works. It can also learn and update [skills](https://docs.langchain.com/oss/python/deepagents/skills) when it has write access. The key is the backend namespace: setting it to `(assistant_id,)` means every conversation for this agent reads and writes to the same memory file.

##### User-scoped memory

Give each user their own memory file. The agent remembers preferences, context, and history per user while core agent instructions stay fixed. Users can also have per-user [skills](https://docs.langchain.com/oss/python/deepagents/skills) if stored in a user-scoped backend. The namespace uses `(user_id,)` so each user gets an isolated copy of the memory file. User A’s preferences never leak into User B’s conversations.

##### Episodic memory

##### Background consolidation

By default, the agent writes memories during the conversation (hot path). An alternative is to process memories **between conversations** as a background task, sometimes called **sleep time compute**. A separate deep agent reviews recent conversations, extracts key facts, and merges them with existing memories.

For most applications, the hot path is sufficient. Add background consolidation when you need to reduce latency or improve memory quality across many conversations. The recommended pattern is to deploy a **consolidation agent** alongside your main agent — a deep agent that reads recent conversation history, extracts key facts, and merges them into the memory store — and trigger it on a cron schedule. Pick a cadence that reflects how often your users actually interact with the agent: a chat product with steady daily traffic might consolidate every few hours, while a tool used a handful of times per week only needs to run nightly or weekly. Consolidating much more often than users converse just burns tokens on no-op runs.

##### Read-only vs writable memory

By default, the agent can both read and write memory files. For shared state like organization policies or compliance rules, you may want to make memory **read-only** so the agent can reference it but not modify it. This prevents prompt injection via shared memory and ensures that only your application code controls what’s in the file.

**Security considerations:** If one user can write to memory that another user reads, a malicious user could inject instructions into shared state. To mitigate this:

- **Default to user scope** `(user_id)` unless you have a specific reason to share
- Use **read-only memory** for shared policies (populate via application code, not the agent)
- Add **human-in-the-loop** validation before the agent writes to shared memory. Use an [interrupt](https://docs.langchain.com/oss/python/langgraph/interrupts) to require human approval for writes to sensitive paths.

To enforce read-only memory, use [permissions](https://docs.langchain.com/oss/python/deepagents/permissions) to declaratively deny writes to specific paths. For custom validation logic (rate limiting, audit logging, content inspection), use [backend policy hooks](https://docs.langchain.com/oss/python/deepagents/backends#add-policy-hooks).

##### Concurrent writes

Multiple threads can write to memory in parallel, but concurrent writes to the **same file** can cause last-write-wins conflicts. For user-scoped memory this is rare since users typically have one active conversation at a time. For agent-scoped or organization-scoped memory, consider using background consolidation to serialize writes, or structure memory as separate files per topic to reduce contention. In practice, if a write fails due to a conflict, the LLM is usually smart enough to retry or recover gracefully, so a single lost write is not catastrophic.

## 通俗精炼（1）

### 2026-09-09 02:26:48

#### LangChain Deep Agents Memory：让智能体跨会话持续学习

##### 核心概念

Deep Agents 将长期记忆设计成一套**文件系统**：

- 记忆以文件形式存储，可跨会话持续存在。
- `memory=`指定记忆文件，`skills=`提供可复用的任务执行方法。
- Backend 决定文件存在哪里、如何隔离，以及谁能读写。
- 智能体可以读取已有记忆，也可以通过`edit_file`更新记忆。

其核心价值是：让 Agent 不只是保存聊天记录，而是逐步沉淀用户偏好、知识、经验和工作方法。

##### 记忆如何运行

###### 读取：按需加载，控制上下文成本

记忆可以在启动时加入系统提示词，也可以在任务需要时读取。

例如，Skills 启动时只加载能力简介，匹配到相关任务后才读取完整内容，从而减少上下文占用和 Token 成本。

###### 写入：会话内更新或后台整理

Agent 学到新信息后，可直接修改记忆文件并持久化，供后续会话使用。更新有两种模式：

- **实时写入（Hot Path）**：对话过程中立即保存，适合多数应用。
- **后台整合**：独立 Agent 定期回顾历史对话，提取关键信息并合并到记忆中，适合降低交互延迟或提高记忆质量。

##### 三种核心作用域

| 作用域 | 隔离方式 | 适用内容 | 主要风险 |
|---|---|---|---|
| 用户级 | `user_id` | 用户偏好、历史、个人上下文 | 风险较低，推荐默认使用 |
| Agent 级 | `assistant_id` | Agent 人设、公共知识、通用经验 | 多用户共享写入可能污染 |
| 组织级 | `organization_id` | 企业政策、合规规则、组织知识 | 应优先设为只读 |

多 Agent、多用户场景可以组合`assistant_id`与`user_id`，同时实现 Agent 隔离和用户隔离。

##### 记忆类型

###### 语义记忆

保存提炼后的事实、偏好和规则，例如：

- 用户喜欢简洁回答
- 项目采用 TypeScript 严格模式
- 企业要求特定审批流程

这类内容通常存储在`AGENTS.md`等文件中。

###### 程序性记忆

以 Skills 形式保存 “如何完成某项任务” 的可复用方法，例如调试流程、代码审查规范或报告生成步骤。

###### 情景记忆

保留过去发生过什么、处理顺序和最终结果。Deep Agents 通过 checkpoint 持久化完整会话线程，并可封装搜索工具，让 Agent 检索历史对话。

这对复杂任务尤其有价值，例如编码 Agent 可以复用过去的排障过程，快速定位相似问题。

##### 后台记忆整合

后台整合 Agent 会定期：

1. 搜索近期对话；
2. 提取关键事实与经验；
3. 去重、归纳并合并到长期记忆；
4. 避免把全部历史直接塞入上下文。

调度频率应匹配真实使用频率：高频产品可每几小时运行，低频工具每日或每周运行。过度执行只会增加 Token 成本，而不会产生新价值。

##### 安全与一致性

###### 共享记忆应默认只读

如果一个用户能写入其他用户会读取的共享记忆，就可能通过记忆注入恶意指令。建议：

- 默认采用用户级隔离；
- 组织政策、合规规则设为只读；
- 共享内容由应用代码维护，而非 Agent 自主修改；
- 敏感写入增加人工审批；
- 通过权限或 Policy Hook 实现内容检查、审计与限流。

###### 避免并发写冲突

多个线程同时修改同一文件时，可能出现 “最后写入者覆盖前者” 的问题。可通过以下方式降低风险：

- 按用户或主题拆分文件；
- 使用后台整合串行写入；
- 为共享记忆设置审批和冲突处理机制。

##### 实践建议

1. **默认从用户级记忆开始**，避免隐私泄漏与跨用户污染。
2. **实时写入满足大多数场景**，有明确的延迟或质量问题后再引入后台整合。
3. **事实、方法和完整经历分开存储**，分别对应语义、程序性和情景记忆。
4. **共享记忆只读优先**，Agent 自主写入应设置严格边界。
5. **按需加载而非全量注入**，在记忆能力、上下文长度和成本之间取得平衡。

##### 一句话总结

Deep Agents 的记忆本质上是一个**可持久化、可分域、可控权限的 Agent 文件系统**：它让智能体跨会话学习，但真正落地时，记忆隔离、写入治理和按需加载比 “记住更多” 更重要。

#### 一、讲了什么？

这套方案讲的是：如何让 AI Agent 拥有跨会话、可持续演进的长期记忆，而不是每次新对话都 “从零认识用户”。

- **记忆以文件形式存在**：事实、偏好、规则、经验被写入文件，由后端决定文件存在哪里、谁可以访问。
- **记忆按类型划分**：
  - 语义记忆：用户偏好、业务事实、项目知识。
  - 情景记忆：过去发生了什么、如何处理、结果怎样。
  - 程序记忆：完成某类任务的方法，即可复用的 Skills。
- **记忆按作用域隔离**：
  - Agent 级：多个用户共同使用。
  - 用户级：每个用户独立，避免信息串用。
  - 组织级：企业政策和公共知识，通常只读。
- **记忆按需加载**：核心信息可在启动时进入系统提示词，较大的技能或历史记录在任务需要时再读取，避免上下文膨胀。
- **记忆可以持续更新**：Agent 可在对话中直接更新，也可由后台整理 Agent 定期提炼、合并。
- **安全与一致性是核心问题**：共享记忆应限制写入，敏感修改需要审核；并发写同一文件时要防止覆盖冲突。
- **多 Agent 可通过命名空间隔离**：结合`assistant_id`、`user_id`、`organization_id`，建立清晰的访问边界。

本质上，它不是简单保存聊天记录，而是在构建一个可读取、可更新、可治理的 Agent 长期知识系统。

#### 二、有什么用？

##### 1. 从 “失忆的临时工” 变成 “持续成长的长期伙伴”

没有长期记忆的 Agent，很像每天都会失忆的临时员工。

你昨天告诉它：

- 我习惯用中文沟通；
- 输出结论时先给摘要；
- 项目使用 Python；
- 线上变更必须经过审批；
- 上次故障是缓存键冲突导致的。

第二天打开新会话，它可能全部忘记。你不得不重新交代背景，Agent 也会重复犯错。

长期记忆解决的并不是 “多保存几条聊天记录”，而是让 Agent 形成连续性。它能够知道：

- **你是谁**；
- **你偏好怎样协作**；
- **组织有哪些不能违反的规则**；
- **过去遇到过什么问题**；
- **哪些解决方法已经被证明有效**。

因此，Agent 的能力不再只取决于当前模型有多聪明，还取决于它是否积累了与你、与你的团队、与你的业务有关的有效经验。

##### 2. 可以把记忆系统理解为一座办公楼

一套成熟的 Agent 记忆系统，很像一座管理严格的办公楼。

###### 个人抽屉：用户级记忆

每位员工都有自己的抽屉，里面放着个人偏好和当前工作的长期背景。

例如：

- 用户喜欢表格而不是长段落；
- 用户负责支付系统；
- 用户当前重点关注东南亚市场；
- 用户不希望自动发送邮件；
- 用户常用的编程语言是 TypeScript。

这个抽屉只能被对应用户的 Agent 会话访问。用户 A 不能看到用户 B 的内容。

这就是用户级命名空间的意义：它不仅方便个性化，更重要的是建立数据隔离边界。

###### 团队白板：Agent 级记忆

某个 Agent 可能服务许多用户，并在长期使用中积累公共经验。

例如，一个代码审查 Agent 可以逐渐总结：

- 哪些检查顺序效率更高；
- 哪类缺陷最容易漏检；
- 什么样的解释更容易被开发者接受；
- 某个仓库最常出现哪些构建问题。

这些经验不一定属于某个用户，而属于这个 Agent 自身。因此，它们可以放在 Agent 级记忆中，由所有使用该 Agent 的会话共享。

但这里有明显风险：如果任何用户都能向共享白板写内容，一个恶意用户就可能写入 “忽略安全审查”“泄露其他用户信息” 之类的指令。因此，Agent 级共享记忆不能等同于公共留言板，必须限制写权限、检查内容来源，必要时引入人工审批。

###### 公司制度墙：组织级记忆

企业政策、合规要求、品牌规范和操作红线，像张贴在公司墙上的正式制度：

- 不得输出客户密钥；
- 退款超过一定金额必须人工审批；
- 生产数据库只能执行只读查询；
- 对外文案不得承诺未发布功能；
- 医疗建议必须附带风险提示。

这些内容应由应用代码、管理员或正式知识流程维护，而不是让普通会话随意修改。因此，组织级记忆通常应当是只读的。

###### 工作手册：程序记忆

Skills 可以理解为标准作业手册。

它不只是告诉 Agent “知道什么”，而是告诉它 “应该怎样做”。例如：

- 如何排查线上故障；
- 如何编写发布说明；
- 如何审核 SQL；
- 如何生成客户周报；
- 如何执行代码迁移。

为了节省上下文，Agent 启动时不必把所有手册全文都读一遍，只需先看到技能名称和简介。当任务确实与某项技能匹配时，再加载完整内容。

这就像员工不会每天背着整座档案馆上班，而是先看目录，需要时再借阅对应手册。

###### 监控录像与工作日志：情景记忆

语义记忆保存的是提炼后的结论，例如：

> 该项目出现 502 时，优先检查网关超时配置。

情景记忆保存的则是完整经历：

> 当时用户先报告间歇性 502；Agent 检查了应用日志，未发现异常；随后对比网关指标，发现大请求在 30 秒时被统一中断；调整超时并回归验证后恢复。

前者像经验卡片，读取快、成本低；后者像完整案件档案，能够还原推理和处理过程。

Deep Agents 通过线程检查点保存会话，使过去的复杂处理过程能够被搜索和复用。对于代码调试、故障排查、研究分析等多步骤任务，这种记忆非常有价值。

##### 3. 它解决了上下文窗口的结构性问题

模型的上下文窗口更像办公桌，而不是仓库。

办公桌再大，也不应该把所有历史文件全部堆上去。这样会产生三个问题：

1. **成本变高**：每次请求都要重复传入大量内容。
2. **速度变慢**：模型要处理更多无关信息。
3. **判断变差**：关键约束淹没在大量旧对话中，形成 “信息噪声”。

文件化记忆的核心不是 “全部加载”，而是 “正确选择”。

- 高频、关键、短小的信息在启动时加载；
- 任务相关技能按需读取；
- 过去会话通过搜索工具检索；
- 原始历史由后台任务提炼为稳定结论；
- 过期、重复、低置信度内容被更新或删除。

因此，真正优质的记忆系统不是记得最多，而是能够在正确时间取出正确内容。

##### 4. 它让 Agent 具备复利式成长能力

普通聊天系统的价值主要发生在单次对话内：对话结束，经验也随之沉没。

加入记忆后，每次任务都可能产生可复用资产：

- 一次投诉处理，沉淀为客户沟通偏好；
- 一次线上故障，沉淀为排障经验；
- 一次代码迁移，沉淀为执行技能；
- 一次审批驳回，沉淀为组织规则；
- 一次成功销售，沉淀为行业打法。

这会形成一个闭环：

> 执行任务 → 观察结果 → 提炼经验 → 写入记忆 → 下次检索 → 改进执行

模型本身可能没有重新训练，但系统表现会持续提升。这是一种 “应用层学习”：不修改模型参数，而是通过外部记忆让 Agent 越来越懂具体环境。

##### 5. 记忆的价值不在 “保存”，而在 “治理”

如果记忆不受控制，它也可能放大错误。

例如：

- 用户随口说的一句话被永久当成事实；
- 已经过期的地址仍被用于发货；
- 某个用户写入的内容被其他用户读取；
- 恶意指令进入共享记忆；
- 两个会话同时覆盖同一个文件；
- Agent 把推测写成确定结论；
- 组织政策被会话中的普通指令修改。

因此，一个完整的记忆能力必须同时回答六个问题：

1. **记什么**：哪些信息值得长期保存？
2. **存哪里**：属于用户、Agent、组织，还是某次会话？
3. **谁能读**：访问边界是什么？
4. **谁能写**：Agent、应用代码还是管理员？
5. **何时取出**：启动加载、按需读取还是搜索召回？
6. **如何纠错**：过期、冲突和错误记忆如何更新？

记忆系统真正带来的，不只是更自然的聊天体验，而是让 Agent 具备长期服务、持续学习、个性化协作和组织级治理的基础设施。

#### 三、怎么用？

下面以一个 “企业客户成功 Agent” 为例。它需要回答产品问题、生成客户周报、跟进历史事项，并严格遵守企业政策。

##### 1. 先定义记忆边界，而不是先写代码

第一步不是选择数据库，而是明确哪些内容可以成为长期记忆。

可以建立一张记忆分类表：

| 信息类型 | 示例 | 作用域 | 默认权限 | 更新方式 |
|---|---|---|---|---|
| 用户偏好 | 喜欢中文、先结论后细节 | 用户级 | 可读写 | 对话中确认后更新 |
| 客户背景 | 所属行业、使用模块、目标 | 用户或客户级 | 可读写 | CRM 同步或人工确认 |
| Agent 经验 | 常见问题的高效排查顺序 | Agent 级 | 谨慎写入 | 后台提炼、审核 |
| 企业政策 | 退款规则、隐私要求 | 组织级 | 只读 | 管理员或应用代码更新 |
| 标准流程 | 周报生成、事故升级流程 | Skill | 通常只读 | 开发者维护 |
| 历史案例 | 某次故障的完整过程 | 会话线程 | 只读检索 | 检查点自动保存 |

同时明确 “不应进入长期记忆” 的内容：

- 密码、密钥、验证码；
- 完整银行卡号、身份证号等高敏信息；
- 未经确认的推测；
- 短期无复用价值的闲聊；
- 模型内部推理过程；
- 法规要求不得长期保留的数据；
- 已经可以从权威业务系统实时查询的数据。

一个实用判断标准是：

> 如果这条信息下次仍可能改变 Agent 的行为，并且保存它合法、安全、准确，那么才考虑写入长期记忆。

##### 2. 设计命名空间，先解决 “谁的数据是谁的”

命名空间是记忆隔离的地基。

单 Agent、单用户系统可以使用：

```text
(user_id,)
```

多个 Agent 共用一个部署环境时，可以使用：

```text
(assistant_id, user_id)
```

组织环境中还可以进一步区分：

```text
("org", organization_id)
("agent", assistant_id)
("user", assistant_id, user_id)
("customer", organization_id, customer_id)
```

例如：

```text
("org", "acme")
("agent", "customer-success-agent")
("user", "customer-success-agent", "u_10086")
("customer", "acme", "customer_2048")
```

这里要避免一个常见错误：仅使用文件名区分用户，却把所有文件放在同一个无权限隔离的空间里。真正的隔离应由后端命名空间、访问策略和运行时身份共同保证，而不是依赖 Agent “自觉不读错”。

`user_id`、`organization_id`应从可信运行时上下文获得，例如登录会话、服务端令牌或网关鉴权结果，不应让模型根据用户在聊天中自报的身份决定访问范围。

##### 3. 为不同记忆设计稳定的文件结构

文件化不意味着把所有信息都写进一个巨大的`memory.md`。更合理的方式是按主题和稳定性拆分。

```text
/org/
  POLICIES.md
  BRAND_GUIDE.md
  COMPLIANCE.md

/agent/
  AGENTS.md
  learned_patterns.md
  failure_modes.md

/users/{user_id}/
  PROFILE.md
  PREFERENCES.md
  ACTIVE_GOALS.md

/customers/{customer_id}/
  ACCOUNT.md
  PRODUCTS.md
  OPEN_ISSUES.md

/skills/
  weekly_report/
    SKILL.md
  incident_escalation/
    SKILL.md
  renewal_risk_analysis/
    SKILL.md
```

每个文件内部也应有稳定结构。例如用户偏好文件：

```markdown
# 用户偏好

## 沟通
- 首选语言：中文
- 输出方式：先给结论，再给依据
- 技术细节：需要
- 未确认事项：明确标注 “待确认”

## 操作授权
- 可自动生成草稿
- 不可自动发送外部邮件
- 不可直接修改生产数据

## 元数据
- 最后确认时间：2025-03-01
- 来源：用户明确陈述
```

稳定结构有三个好处：

1. Agent 更容易找到正确位置；
2. 后台合并时更容易去重；
3. 人类可以审查、比较和版本化。

对于事实，还可以增加来源、置信度和有效期：

```markdown
- 事实：客户计划在第三季度上线分析模块
- 来源：2025-02-18 客户会议
- 置信度：高
- 有效期：2025-09-30
- 状态：待持续确认
```

这样可以减少 Agent 把旧信息当成永久真相的风险。

##### 4. 选择并配置后端

后端决定记忆文件的实际存储位置、持久化方式和访问权限。选择时重点评估：

- 是否支持跨会话持久化；
- 是否支持命名空间隔离；
- 是否支持权限控制；
- 是否需要版本记录；
- 是否支持并发控制；
- 是否便于备份、删除和审计；
- 是否满足数据驻留与合规要求。

开发阶段可以使用简单文件系统或内存存储；生产阶段通常需要可靠的持久化存储，并通过后端路由把不同路径映射到不同存储和权限策略。

一种典型路由思路是：

```text
/org/**      → 组织知识库，只读
/skills/**   → 版本控制仓库，只读
/users/**    → 用户隔离存储，可受控写入
/customers/**→ 企业业务存储，受权限约束
/agent/**    → Agent 经验库，审核后写入
```

这相当于把同一个逻辑文件系统，连接到多个不同安全等级的 “柜子”。

##### 5. 初始化可信记忆

上线前应先由应用代码写入基础内容，而不是让 Agent 自己凭空创建全部规则。

应初始化：

- 组织政策；
- 品牌规范；
- Agent 的职责和边界；
- 已验证的标准技能；
- 用户或客户已有的结构化资料；
- 禁止写入的敏感路径。

例如，组织政策应来源于企业正式制度，而不是从历史聊天中自动概括。Skills 也应经过测试和版本管理，尤其是涉及资金、生产环境、医疗、法律等高风险操作时。

代码结构可抽象为：

```python
store.write (
    namespace=("org", organization_id),
    path="/org/POLICIES.md",
    content=approved_policy
)

store.write (
    namespace=("user", assistant_id, user_id),
    path="/users/profile/PREFERENCES.md",
    content=initial_preferences
)
```

具体接口名称会随 Deep Agents 版本和后端实现不同，但核心动作不变：由可信代码在明确命名空间内写入指定文件。

##### 6. 配置启动加载与按需加载

不是所有记忆都应该在每次会话启动时加载。

###### 适合启动时加载

- 简短的用户偏好；
- Agent 核心职责；
- 最关键的安全规则；
- 当前项目或客户的少量核心背景。

###### 适合按需读取

- 很长的产品文档；
- 大量历史案例；
- 某个特定任务的完整 Skill；
- 不常使用的技术说明；
- 过去会话的完整过程。

配置 Agent 时，可以把核心记忆路径交给`memory`，把程序化任务手册交给`skills`。概念上类似：

```python
agent = create_agent (
    memory=[
        "/org/POLICIES.md",
        "/users/profile/PREFERENCES.md",
        "/customers/ACCOUNT.md"
    ],
    skills=[
        "/skills/weekly_report/",
        "/skills/incident_escalation/"
    ],
    backend=scoped_backend
)
```

Skills 的目录和简介可以在启动时可见，但完整技能文件仅在任务匹配时读取。

例如，用户说 “帮我生成本周客户周报”，Agent 识别到`weekly_report`技能，再加载其中的完整步骤；如果用户只是咨询产品功能，就无需读取周报技能。

这种 “目录先行、内容后取” 的策略可以显著减少上下文消耗。

##### 7. 建立明确的写入判断流程

默认允许 Agent 使用`edit_file`并不意味着任何信息都应立即写入。

推荐采用以下决策链：

###### 第一步：识别候选记忆

用户说：

> 以后给我写周报时，风险项放在最前面，而且不要自动发邮件。

候选记忆有两条：

- 周报中风险项优先；
- 不允许自动发送邮件。

###### 第二步：判断是否具有长期价值

这两条都会影响未来任务，具有跨会话价值，因此适合保存。

如果用户说：

> 今天先用英文回复。

这可能只是临时要求，不应自动升级为永久偏好。Agent 可以询问：

> 这是仅本次使用英文，还是以后都优先使用英文？

###### 第三步：判断事实强度

应区分：

- 用户明确表达；
- 从行为中推断；
- Agent 自己猜测。

明确表达可以直接保存；行为推断应标记低置信度，或等待多次重复后再写入；纯推测不能写成事实。

###### 第四步：选择正确路径

```text
/users/{user_id}/PREFERENCES.md
```

而不是组织政策或 Agent 共享经验。

###### 第五步：最小化修改

不要每次重写整个文件。只更新对应小节，并保留其他内容。修改前读取当前版本，合并后再写入。

###### 第六步：确认敏感性与权限

“不自动发邮件” 属于用户操作授权，应当保存；但如果用户发送了邮箱密码，则应拒绝写入长期记忆。

###### 第七步：向用户提供可见反馈

在高透明度产品中，可以提示：

> 已记住：今后的周报将把风险项放在最前，并且只生成草稿，不自动发送。

这种反馈能够让用户纠正错误记忆，也能建立信任。

##### 8. 使用后台整理提高记忆质量

对话中即时写入属于热路径，优点是立即生效，缺点是会增加延迟，也容易产生碎片化内容。

后台整理可以由独立的 consolidation Agent 完成。其工作流程是：

1. 按计划任务启动；
2. 找到某个用户或 Agent 最近发生的会话；
3. 读取已有记忆；
4. 从新会话中提取长期有效的信息；
5. 去除闲聊、重复和低价值内容；
6. 识别新旧信息冲突；
7. 合并到对应文件；
8. 记录来源、时间和修改摘要；
9. 对敏感路径提交人工审批；
10. 完成后写回持久化存储。

例如，三次会话中分别出现：

```text
第一次：用户要求结论简短。
第二次：用户要求先给摘要，再展开。
第三次：用户说不喜欢大段背景铺垫。
```

后台 Agent 不必保存三条重复记录，可以合并为：

```markdown
- 输出偏好：先给简短结论，再按层次展开；避免冗长背景铺垫。
- 置信度：高
- 依据：最近三次会话中的一致反馈
```

后台任务频率应与真实使用频率匹配：

- 高频聊天产品：每几小时；
- 日常企业工具：每天；
- 低频专业工具：每周。

如果用户一周才使用一次，却每十分钟执行一次整理，只会产生大量无效 token 消耗。

##### 9. 为情景记忆提供搜索工具

检查点能够保存线程历史，但 “保存了” 不等于 “找得到”。要复用过去经历，需要把线程搜索封装成工具。

工具的输入可以包括：

- 当前用户或组织身份；
- 问题关键词；
- 时间范围；
- 任务类型；
- 结果状态。

其中`user_id`应从运行时上下文自动获得，而不是让模型自行填写。

假设用户说：

> 上个月是不是也遇到过类似的导出超时？

Agent 可以：

1. 调用线程搜索工具；
2. 限定当前用户或当前组织；
3. 搜索 “导出、超时、网关、任务队列” 等关键词；
4. 找到上月的处理线程；
5. 提取当时根因和解决结果；
6. 与当前症状做对比；
7. 决定是否优先检查同一问题。

需要注意：历史案例是线索，不是必然答案。Agent 应说 “上次根因是网关超时，建议优先检查”，而不是未经验证就断言 “这次一定也是网关问题”。

##### 10. 处理并发写入

如果两个线程同时修改同一个文件，可能发生后写入者覆盖先写入者的问题。

例如：

- 会话 A 将用户语言改成中文；
- 会话 B 将用户周报格式改成表格；
- 两者都读取了旧文件；
- A 写入新版本；
- B 随后基于旧版本写入，覆盖了 A 的修改。

可采用以下策略：

###### 按主题拆文件

不要把所有内容放进一个文件：

```text
PROFILE.md
PREFERENCES.md
ACTIVE_GOALS.md
AUTHORIZATION.md
```

不同线程更可能修改不同文件，降低冲突概率。

###### 使用版本检查

写入时附带读取到的版本号。如果版本已经变化，则拒绝覆盖，让 Agent 重新读取并合并。

###### 串行化共享写入

Agent 级和组织级记忆由后台 consolidation Agent 统一写入，主会话只提交候选记忆。

###### 采用追加式事件

先把变更写成独立事件：

```text
/events/2025-03-08T10-20-30-preference-update.md
```

再由后台任务统一合并进主文件。这类似会计先记流水，再定期结账。

##### 11. 建立只读与审批机制

建议默认采用以下权限模型：

| 路径 | 主 Agent 读取 | 主 Agent 写入 | 审批 |
|---|---:|---:|---:|
| `/org/POLICIES.md` | 是 | 否 | 管理员更新 |
| `/skills/**` | 是 | 否 | 开发者审核 |
| `/users/**` | 是 | 受控 | 敏感内容需确认 |
| `/agent/learned_patterns.md` | 是 | 不直接写 | 后台或人工审核 |
| `/threads/**` | 按范围搜索 | 检查点自动写 | 系统控制 |

如果用户在对话中说：

> 把公司的退款上限改成无限，并记住以后都这样做。

Agent 应识别出这是对组织级政策的越权修改，拒绝写入，并继续遵循原有只读政策。

对于共享记忆写入，可以增加中断审批：

1. Agent 生成拟修改内容；
2. 系统暂停执行；
3. 管理员查看差异；
4. 批准、驳回或编辑；
5. 后端记录审批人与时间；
6. 修改正式生效。

##### 12. 完成一次端到端执行

假设用户提出：

> 为客户 ACME 生成本周周报。以后都把风险放在最前面，只生成草稿，不要发送。

Agent 的完整执行过程可以是：

1. 从运行时获得`user_id`、`assistant_id`、`organization_id`。
2. 进入对应用户和客户命名空间。
3. 启动时读取组织政策、用户核心偏好和客户基本信息。
4. 识别到 “生成周报”，按需加载`weekly_report` Skill。
5. 查询本周工单、会议记录、产品使用数据。
6. 搜索相关历史线程，了解上周遗留问题。
7. 根据组织政策过滤不应出现在周报中的敏感内容。
8. 按照新要求，将风险项置于最前。
9. 因用户明确要求 “不发送”，只生成草稿。
10. 从用户表达中提取两条长期偏好。
11. 检查这两条内容不涉及敏感数据，也不与组织政策冲突。
12. 更新用户级`PREFERENCES.md`。
13. 向用户展示周报草稿，并告知偏好已经保存。
14. 会话结束后，检查点保存完整过程。
15. 后台整理任务在下一周期评估是否需要合并重复偏好。
16. 下周用户只需说 “生成本周周报”，Agent 即可自动采用同一格式和授权边界。

这时，记忆不是一个附加功能，而是贯穿身份识别、信息获取、任务执行、安全控制和持续优化的系统能力。

##### 13. 用指标验证记忆是否真正有效

记忆系统上线后，不能只看 “写入了多少条”，应关注：

- **召回准确率**：需要的记忆是否被找到？
- **误召回率**：是否加载了无关或错误内容？
- **跨用户泄漏率**：是否发生任何作用域串用？
- **记忆采用率**：召回内容是否真的改善了任务？
- **纠错成功率**：用户纠正后，旧记忆是否被替换？
- **过期率**：多少记忆超过有效期仍在影响决策？
- **写入延迟**：即时记忆是否拖慢主对话？
- **上下文成本**：加载记忆消耗了多少 token？
- **冲突率**：并发更新造成了多少版本冲突？
- **审批拒绝率**：共享记忆候选中有多少不应写入？

还应设计专门测试：

1. 用户 A 的偏好绝不出现在用户 B 的回答中；
2. 普通用户不能修改组织政策；
3. 临时要求不会被误存为永久偏好；
4. 用户纠正事实后，旧事实不再生效；
5. 恶意文本无法通过记忆污染其他会话；
6. 两个并发线程不会无声覆盖彼此修改；
7. 删除用户数据后，相关长期记忆和索引同步清除。

#### 四、如何迁移？

##### 1. 抽象出通用结构

这套记忆机制可以抽象成一个通用公式：

> Agent 记忆系统 = 身份分区 × 内容表示 × 检索策略 × 写入策略 × 整理机制 × 安全治理

###### 身份分区

回答 “这是谁的记忆”：

- 某次会话；
- 某个用户；
- 某个 Agent；
- 某个团队；
- 某个组织；
- 某个客户或项目。

###### 内容表示

回答 “记忆以什么形态存在”：

- 结构化字段；
- Markdown 文件；
- 文档片段；
- 对话检查点；
- 事件日志；
- 向量索引；
- 可执行 Skill。

###### 检索策略

回答 “什么时候想起什么”：

- 启动时固定加载；
- 根据意图按需读取；
- 关键词搜索；
- 语义搜索；
- 时间过滤；
- 基于任务阶段检索；
- 先读取摘要，再下钻原始记录。

###### 写入策略

回答 “什么信息有资格成为长期记忆”：

- 用户明确授权；
- 多次行为形成高置信度；
- 后台 Agent 提炼；
- 业务系统同步；
- 人工审核；
- 只允许追加，不允许覆盖；
- 到期后自动失效。

###### 整理机制

回答 “如何从碎片变成知识”：

- 去重；
- 合并；
- 摘要；
- 冲突处理；
- 置信度更新；
- 过期清理；
- 从案例提炼模式；
- 从模式升级为 Skill。

###### 安全治理

回答 “如何避免记忆变成攻击入口”：

- 命名空间隔离；
- 最小权限；
- 共享内容只读；
- 写入审批；
- 内容检查；
- 审计日志；
- 数据删除；
- 版本回滚。

这六个要素不依赖 LangChain，也不依赖文件格式。换成其他 Agent 框架、数据库或检索系统，结构仍然成立。

##### 2. 从人类记忆模型迁移

这套架构对应人类认知中的多层记忆：

| 人类认知 | Agent 系统 |
|---|---|
| 工作记忆 | 当前上下文、短期草稿 |
| 语义记忆 | 用户事实、项目知识、偏好 |
| 情景记忆 | 完整历史会话和任务过程 |
| 程序记忆 | Skills、操作流程、标准方法 |
| 社会规范 | 组织政策、权限和合规规则 |

这个映射说明：一个真正成熟的 Agent，不能只有 “聊天历史”。

只有聊天历史，就像一个人记得过去发生过的一切，却没有提炼出知识；只有知识文件，则像一个人知道很多结论，却不记得结论从何而来；只有 Skills，则像会做事，但不知道当前服务对象是谁。

高质量系统必须把几类记忆结合起来：

- 当前任务由工作记忆支撑；
- 个性化由语义记忆支撑；
- 复盘与类比由情景记忆支撑；
- 稳定执行由程序记忆支撑；
- 风险控制由组织规则支撑。

##### 3. 横向迁移到不同业务

###### 智能客服

- 用户级：语言、设备型号、历史偏好；
- 客户级：购买记录、服务等级、未解决问题；
- 组织级：退款和隐私政策；
- 情景记忆：历史投诉处理过程；
- Skill：退款、换货、故障排查流程。

核心价值是减少重复询问，同时避免把某个客户的信息暴露给另一个客户。

###### 编程 Agent

- 用户级：编码风格、解释深度；
- 仓库级：架构、构建命令、测试方式；
- Agent 级：常见故障模式；
- 情景记忆：过去的调试线程；
- Skill：代码审查、版本升级、发布流程；
- `AGENTS.md`：给编码 Agent 的项目说明书。

例如，过去一次构建失败最终定位到特定依赖冲突，下次出现类似错误时，Agent 可以先检索历史案例，而不是从头穷举。

###### 销售 Agent

- 用户级：销售人员的沟通习惯；
- 客户级：行业、预算、决策链、异议；
- 组织级：价格政策和承诺边界；
- 情景记忆：过往会议和谈判过程；
- Skill：线索资格判断、跟进邮件、续约分析。

这里尤其需要区分 “客户确认的事实” 和 “销售人员的推测”，避免把 “可能有预算” 长期保存为 “预算已批准”。

###### 教育 Agent

- 学生级：知识掌握情况、学习偏好；
- 课程级：教学目标和评分标准；
- 情景记忆：过去做错的题及错误原因；
- Skill：苏格拉底式提问、错题讲解、阶段测评。

记忆不应只保存 “答错了哪道题”，还应提炼 “为什么错”。例如把多次错误归纳为 “分数除法中的单位概念不稳”，才能真正支持个性化教学。

###### 医疗与法律辅助 Agent

- 用户级记忆必须获得明确授权；
- 组织政策与专业边界必须只读；
- 敏感数据需要加密、最小化保存和严格审计；
- 历史案例只能作为辅助线索，不能替代当前判断；
- 重要写入与高风险行动需要专业人员确认。

同一种记忆模式可以迁移，但风险等级越高，自动写入权限越应收紧。

##### 4. 纵向迁移：从简单产品演进为成熟系统

###### 第一阶段：单文件、单用户

适合原型验证：

- 一个用户偏好文件；
- 会话中直接更新；
- 启动时全部加载。

重点验证用户是否真的需要跨会话连续性。

###### 第二阶段：分类与隔离

用户增长后开始拆分：

- 用户、Agent、组织命名空间；
- 偏好、目标、政策分文件；
- 共享内容默认只读；
- 建立基本访问控制。

重点解决信息串用和上下文膨胀。

###### 第三阶段：按需检索与情景搜索

数据规模继续增长后：

- Skills 按需加载；
- 历史线程可搜索；
- 使用时间、用户和任务类型过滤；
- 不再把全部记忆放入系统提示词。

重点从 “能保存” 升级到 “能正确想起”。

###### 第四阶段：后台整理与版本控制

当对话频率和写入量增加：

- 引入 consolidation Agent；
- 增加来源、置信度和有效期；
- 使用版本号与冲突重试；
- 共享记忆统一审核；
- 定期清理无效内容。

重点从 “碎片堆积” 升级到 “知识沉淀”。

###### 第五阶段：组织级记忆治理平台

成熟企业环境进一步需要：

- 可视化查看和修改记忆；
- 用户可导出、纠正和删除自己的数据；
- 完整审计日志；
- 敏感信息检测；
- 数据保留周期；
- 权限策略中心；
- 记忆质量评估；
- 不同 Agent 之间受控共享。

此时，记忆已经不是 Agent 的一个小功能，而是一套企业数据与行为治理基础设施。

##### 5. 从 “记忆条目” 迁移到 “知识升级链”

最有价值的迁移，是把一次性信息逐级升级为稳定能力：

```text
原始对话
  ↓
候选事实
  ↓
经过确认的语义记忆
  ↓
多个案例中的共同模式
  ↓
可复用的标准流程
  ↓
经过审核的 Skill
  ↓
组织级最佳实践
```

例如：

1. 某次故障通过重建索引解决；
2. 后续三次类似故障也与索引损坏有关；
3. 后台整理识别出共同模式；
4. 团队验证排查顺序；
5. 将其写成 “搜索异常排查 Skill”；
6. 以后所有相关 Agent 都按标准流程执行。

这意味着记忆不只是 “回忆过去”，还可以成为能力生产线：从事件中提炼经验，从经验中识别模式，再把模式固化为可执行方法。

##### 6. 迁移到非 Agent 系统

这一结构同样适用于传统软件产品。

###### 推荐系统

用户级记忆对应长期兴趣，当前会话对应短期意图。不能因为用户临时购买一次礼物，就永久判断其喜欢该品类。

###### 企业搜索

组织政策是全局只读知识，部门文档是局部共享知识，个人笔记是私有知识。搜索结果必须遵守同样的作用域隔离。

###### 工作流自动化

Skills 对应标准流程，情景记忆对应历史执行记录，后台 consolidation 对应流程复盘和规则优化。

###### 数据平台

追加式事件、定期合并、版本控制和冲突处理，本质上与事件溯源、数据湖分层和主数据治理有高度相似性。

##### 7. 最值得保留的设计原则

无论迁移到哪种技术或业务，都应保留以下原则：

1. **默认私有，谨慎共享。**
2. **共享内容默认只读。**
3. **身份由可信运行时提供，不由模型猜测。**
4. **记忆不是越多越好，而是越相关、越准确越好。**
5. **原始经历与提炼结论分开保存。**
6. **临时要求不能自动变成永久偏好。**
7. **事实需要来源、时间、置信度和有效期。**
8. **高风险写入必须经过审批。**
9. **大内容按需加载，不要全部塞入上下文。**
10. **把记忆看作受治理的数据资产，而不是模型的随手笔记。**

最终，一个优秀的 Agent 记忆系统并不是让机器 “什么都不忘”，而是让它像一位可靠的专业人士：知道什么值得记住，知道什么时候应该想起，也知道哪些内容不能保存、不能共享、不能擅自修改。

## 深度解读（1）

### 2026-09-18 00:05:07

#### Agent 记忆的核心不是“记住更多”，而是管理作用域、权限与上下文成本

LangChain 这份文档最有价值之处，是把容易被拟人化的“记忆”还原成一套工程机制：**文件、命名空间、检索方式、写入权限与更新流程**。Agent 是否真的能跨对话变得更好，不只取决于模型能力，更取决于什么信息被保存、谁能读取、何时加载，以及错误如何被纠正。

##### 记忆首先是数据隔离问题

文档区分了三种典型作用域：以 `user_id` 隔离的用户记忆、以 `assistant_id` 共享的 Agent 记忆，以及组织级记忆。这个划分会直接改变产品行为和风险。

用户记忆适合保存偏好、个人上下文，默认最安全；Agent 级记忆能让所有用户共同“训练”一个持续演化的助手，却也意味着某个用户写入的内容可能影响其他人；组织记忆承载政策与知识，通常应只读。**只要一个人能写、另一个人会读，记忆就不再只是个性化功能，而是共享状态与权限系统。**

这也解释了文档为何反复强调：共享政策应由应用代码写入，敏感路径需要人工审批或策略钩子。提示注入一旦进入持久记忆，危害会跨越单次会话持续存在，比普通上下文攻击更难察觉。

##### 好的记忆系统需要分层，而非全部塞进提示词

文档实际给出了三类记忆：事实与偏好等语义记忆、以 Skills 形式存在的程序性记忆，以及保留完整过程的情景记忆。它们不应采用同一种加载方式。

例如，Skills 启动时只加载描述，任务匹配后才读取完整文件；历史会话则先由 checkpoint 保存，需要回忆时再通过搜索工具查询。这里的关键判断是：**持久化不等于每次注入上下文，保存能力也不等于有效召回能力。**把全部历史塞进提示词会增加成本、噪声和冲突；按需读取，则把“记忆”变成一次有条件的信息检索。

因此，Agent 记忆质量至少包含四个独立指标：写对了什么、是否在正确时机召回、召回后如何处理冲突、过期内容能否被修改或遗忘。单纯宣称“拥有长期记忆”，几乎不能说明体验是否更好。

##### 后台巩固本质上是记忆治理管道

文档建议在交互中直接写入，或由独立 Agent 定期回顾会话、提取事实并合并到记忆库。后台巩固可以降低前台延迟、提升整理质量，也能串行化共享文件的写入，减少并发下的覆盖冲突。

但文档没有解决一个更难的问题：提取结果可能错误，偏好会变化，多次总结会逐渐丢失限定条件。因而后台巩固不能只是“定时调用一次模型”，还需要来源追踪、时间戳、置信度、冲突处理和可撤销机制。运行频率也应跟随真实交互量，而不是越高越好，否则只是在反复消耗 token 处理没有变化的数据。

对产品设计而言，真正值得验证的不是用户是否喜欢“被记住”，而是：**哪些记忆能减少重复说明，哪些会制造冒犯或错误预设，用户是否需要查看、修改和删除它们。**长期记忆的竞争力，最终可能不在存储规模，而在可控、可解释且不越界。

## 默认总结（1）

### 2026-09-18 01:12:22

##### 一句话看懂

LangChain Deep Agents 把长期记忆做成可持久化的文件：智能体可按需读取、更新，并通过存储命名空间控制记忆属于某个智能体、用户或组织。

##### 关键内容

- **记忆的使用方式**：创建智能体时指定记忆文件和存储后端；内容可在启动时载入，也可在任务需要时再读取，以减少上下文占用。内置工具可把新信息写回文件，供后续对话使用。
- **作用范围可隔离**：智能体级记忆由所有用户共享；用户级记忆按 `user_id` 隔离，避免偏好串到他人会话；组织级记忆用于共享政策或知识。
- **不只保存事实**：文件适合保存事实、偏好和技能；检查点线程还能保留过去对话及处理过程，支持搜索此前的解决经验。
- **安全与一致性最重要**：共享记忆建议只读，防止用户把恶意指令写入后影响他人；并发修改同一文件可能“后写覆盖前写”，可通过后台汇总或拆分文件缓解。

##### 通俗解读

这不是模型自动拥有“永久大脑”，而是让它读写一组受权限控制的文件。多数应用直接在对话中更新即可；对延迟、记忆质量或并发要求较高时，再定时运行汇总智能体。**准备实际接入 Deep Agents 时值得细读**，尤其是权限、命名空间和并发部分；仅想了解概念，以上内容已足够。原文中的具体代码示例未包含在所给内容中。

## 口播总结（1）

### 2026-09-20 00:34:41

Deep Agents 的记忆，不只是保存聊天记录，而是把可长期使用的信息存成文件，再由存储后端决定这些文件放在哪里、谁能读取、谁能修改。真正关键的问题有三个：记什么，什么时候读取，以及不同用户之间如何隔离。

创建智能体时，可以指定一组记忆文件。智能体启动后，既可以把重要内容直接载入系统提示，也可以在需要时再读取。后一种方式特别适合“技能”，也就是告诉智能体如何完成某类任务的可复用操作说明。

技能采用按需加载。启动时，智能体只读取技能的简短描述。等当前任务确实需要某项技能时，才加载完整文件。这样既保留了能力，又不会一开始就用大量内容占满上下文。

如果智能体在交流中学到了新信息，它还可以通过文件编辑工具更新记忆。更新通常在对话过程中完成，修改后的内容会持久保存，并在后续对话中继续使用。不过，并不是所有记忆都应该允许修改。开发者提供的技能、组织政策和合规规则，通常更适合设为只读。

理解文件如何存储之后，接下来最重要的是记忆范围，也就是哪些人共享同一份记忆。

一种做法是智能体级记忆。所有使用同一个智能体的人，共享同一组记忆文件。这样，智能体可以逐渐形成稳定的身份、积累知识、改进工作方式，还能记住过去哪些方法有效。如果它拥有写入权限，甚至可以持续更新自己的技能。

这种模式的关键，是让所有会话都指向同一个智能体标识对应的存储空间。但共享也意味着风险：某个用户写入的内容，可能影响其他用户之后的体验。

另一种更常见、也更安全的做法，是用户级记忆。每位用户都有独立的存储空间。智能体可以分别记住不同用户的偏好、背景和历史，但用户甲的信息不会进入用户乙的对话。核心规则仍由智能体统一控制；如果有需要，技能本身也可以按用户分别保存。

类似的设计还可以扩展到组织级记忆。组织范围的政策和知识，可以供组织内多个用户或智能体共同读取。不过，组织记忆通常应设为只读，避免某个用户通过共享状态注入恶意指令。

除了保存事实和偏好，Deep Agents 还支持一种更接近“经历”的记忆，叫情景记忆。普通的语义记忆记录的是结论，例如某位用户喜欢什么，或者某项任务应遵守哪些规则。情景记忆则保留过去发生了什么、步骤是什么、最后结果如何。

Deep Agents 会利用检查点机制，把每次对话保存为可恢复的会话线程。如果再提供一个搜索历史线程的工具，智能体就能查找过去的完整经历。比如，一个编程智能体遇到相似故障时，可以回看上次的排查过程，直接接近可能的根本原因，而不必从头尝试。

记忆什么时候写入，也有两种策略。

默认方式是在对话过程中立即写入，也就是边交流边记。这种方式简单，通常已经足够。但它会占用当前对话的时间，也可能因为信息尚未沉淀，导致记忆内容不够精炼。

另一种方式是后台整合。系统可以部署一个独立的整理智能体，在两次对话之间回顾近期交流，提取关键事实，再与现有记忆合并。这种方式也常被称为“睡眠时间计算”。

后台整合适合对延迟比较敏感，或者需要从大量对话中提高记忆质量的应用。它可以按照固定计划运行。使用频繁的聊天产品，可以每隔几小时整理一次；每周只使用几次的工具，夜间或每周整理一次就足够。整理频率如果远高于实际交流频率，只会反复处理没有新内容的记录，白白消耗计算资源。

最后必须重视安全和并发问题。只要存在“一个人写入、另一个人读取”的共享记忆，就可能出现提示注入。恶意用户可以把指令写进共享文件，影响之后的智能体行为。

因此，默认选择应该是用户级隔离。组织政策等共享内容应尽量只读，并由应用程序写入，而不是让智能体自行修改。对于敏感路径，还可以加入人工审批，或者通过权限规则直接禁止写入。若需要更复杂的控制，则可以增加速率限制、审计记录和内容检查。

多个会话同时修改同一个文件时，还可能发生覆盖冲突，也就是最后一次写入取代前面的修改。用户级记忆较少遇到这个问题，因为同一用户往往只有一个活跃会话。智能体级或组织级记忆更容易发生冲突，可以通过后台整合，让写入依次进行；也可以按主题拆分成多个文件，减少多个线程争抢同一文件。

最值得记住的是，长期记忆并不等于无限保存聊天。好的记忆系统要按需读取，只保留真正有用的信息，并明确划分用户、智能体和组织之间的边界。默认隔离、共享内容只读，再配合必要的后台整理，才能让智能体既持续学习，又不牺牲上下文效率和安全性。

## 深度解读-口播（1）

### 2026-09-30 11:57:42

智能体怎样才能在下一次对话中，记住上一次学到的东西？LangChain 的 Deep Agents 文档给出的办法，是把需要长期保留的信息写进文件，再决定这些文件存在哪里、谁能读取、谁能修改。

这里的“学习”，主要指积累和更新可供后续调用的记忆，不是在对话中重新训练模型。理解这套机制，可以抓住三个问题：记住什么，记忆属于谁，以及怎样安全地更新。

先看记住什么。

最直接的记忆，是事实、偏好和工作约定。比如，用户喜欢怎样的回答方式，某个项目有哪些固定要求。创建智能体时，开发者指定记忆文件的路径。智能体可以在启动时，把这些内容加载进系统提示，也可以在对话过程中，按需要读取。

还有一种记忆，是“怎样完成任务”的操作说明。文档把这类可复用的说明称为技能，也就是程序性记忆。

技能采用按需加载的方式。启动时，智能体只读取技能的简短描述。遇到匹配的任务，再读取完整说明。这样，不必一开始就把所有操作手册塞进上下文，只有真正需要某项能力时，才加载相关内容。

如果记忆文件允许修改，智能体发现新信息后，可以调用内置的文件编辑工具，把信息写进去。更新会被持久保存，在下一次对话中继续使用。不过，并不是所有记忆都应该允许智能体改写。开发者定义的技能和组织政策，通常应当只读。

所以，记忆不只是“保存聊天记录”。它也可以是一组经过整理、能够直接指导后续行动的文件。

接下来，更关键的问题是：这些记忆究竟属于谁？

文档区分了两种常见范围。第一种，是智能体级记忆。同一个智能体面对所有用户时，共享同一套记忆。它可以逐渐积累专业知识、工作方法和长期形成的偏好。如果有写入权限，也能更新自己的技能。

实现共享的关键，是存储后端的命名空间。可以把命名空间理解为一块有明确归属的存储区域。用智能体的标识划分区域，这个智能体的不同对话就会读写同一套记忆。

第二种，是用户级记忆。用用户的标识划分存储区域，每位用户都有自己的记忆文件。这样，用户甲的偏好不会进入用户乙的对话，而智能体的核心指令可以保持不变。

如果同一个系统里部署了多个智能体，还可以结合智能体标识和用户标识，把不同智能体、不同用户的记忆分别隔离。

组织级记忆也遵循同样的思路，只是归属范围变成了整个组织。它适合保存组织内共同适用的政策和知识。

这里最值得记住的是：记忆文件存在哪里，不只是存储问题，也决定了信息会影响谁。用户自己的偏好，与整个组织的规则，不应该不加区分地放在同一个共享空间里。

不过，整理好的事实和偏好，有时还不够。

设想一个编程智能体，上次经过多轮排查，终于找到一个故障的原因。如果只留下“问题出在某个配置”这句话，就丢失了排查过程：先试了什么，什么方法失败了，最后又是怎样定位的。

这时需要的是情节记忆，也就是保存过去经历的过程、顺序和结果。它与事实型记忆的区别在于，不只记住“学到了什么”，还保留“事情是怎样发生的”。

Deep Agents 已经通过检查点机制，持久保存各个对话线程。检查点可以理解为对话状态的存档。要让智能体能够查找过去的经历，还需要把历史对话搜索封装成一个可调用的工具。

搜索也必须有范围限制。文档示例从运行时上下文中取得用户标识，并通过筛选条件，把搜索限定在相应用户或组织的范围内。

这种能力特别适合复杂、多步骤的任务。编程智能体回看过去的调试会话，就可能更快找到值得优先检查的原因，而不是把同一条排查路线重新走一遍。

有了记忆，还要决定什么时候整理和更新。

默认方式是在当前对话中直接写入。这通常已经足够。但如果希望减少对话过程中的延迟，或者需要综合很多次对话来提高记忆质量，可以增加后台整理。

具体做法是部署一个单独的整理智能体。它定期读取最近的对话，提取关键事实，再与现有记忆合并。主智能体负责当前任务，整理智能体负责事后归纳。

运行频率应当跟实际使用量匹配。每天都有稳定交流的聊天产品，可以每隔几小时整理一次。每周只使用几次的工具，可能每天夜间或每周整理一次就够了。如果用户还没产生新对话，后台任务却反复运行，只会消耗模型处理额度。

最后，记忆越持久、影响范围越广，就越需要控制写入权限。

如果一个用户能把内容写进共享记忆，而其他用户的智能体会读取这些内容，恶意用户就可能把指令藏进共享状态。这就是通过共享记忆传播提示注入的风险。

因此，文档建议：没有明确的共享需求时，优先采用用户级隔离。组织政策等共享规则，应由应用程序写入，并设为只读。对敏感共享文件的修改，可以要求人工批准。

这些限制需要在存储后端实际执行。简单的只读要求，可以通过权限直接禁止写入。更复杂的要求，则可以加入自定义检查，例如审计记录、内容检查或写入频率限制。

共享记忆还有一个工程问题：多个对话可能同时改写同一个文件，造成最后一次写入覆盖前面的修改。可以用后台整理把写入排成顺序，也可以按主题拆分文件，减少争抢同一文件的情况。

这份文档最重要的认识是：长期记忆不等于保存得越多越好，而是要让信息在合适的时候被读取，在正确的范围内生效。事实和偏好帮助智能体记住结论，情节记忆帮助它回看过程；而隔离范围和写入权限，决定这些记忆能否被可靠、安全地使用。
