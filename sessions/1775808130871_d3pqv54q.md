## 分析要点

- **核心高价值点**：最有价值的点是把文件系统视为智能体长期执行、协作、记忆与上下文卸载的基础原语，从而统一解释多种Agent能力来源。
- **留存建议**：中期保留，作为理解智能体系统设计边界的概念参考（文章对Agent Harness的组成、作用和未来演化给出了较完整的框架化总结，适合后续做系统设计时回看）

**知识要点**

- Agent能力的关键不仅在模型，还在Harness提供的状态、工具、约束和执行环境
- 文件系统是持久记忆、上下文管理、协作和长任务执行的核心基础设施
- bash加代码执行让智能体具备通用问题求解能力，减少为每个任务预制工具的需求
- 上下文腐烂需要依靠压缩、工具输出卸载和技能渐进披露等机制治理
- 长期自主执行依赖规划、自我验证、Git追踪和跨上下文窗口的状态延续

**行动项**

- 用文章中的Harness拆解法审视你当前Agent系统：状态、工具、沙箱、验证、上下文管理是否齐全
- 优先评估文件系统与Git是否被当作智能体持久工作账本来设计
- 检查是否存在上下文膨胀问题，并引入压缩、日志卸载或技能按需加载机制
- 把测试、日志、浏览器或代码检查器纳入自我验证回路，而不是只依赖模型输出

## 正文

*By Vivek Trivedy*

**简而言之：** 智能体 = 模型 + 框架。框架工程是指我们如何围绕模型构建系统，将其转化为工作引擎。模型包含智能，而框架则使这种智能得以发挥作用。我们定义了框架的概念，并推导出当今和未来智能体所需的核心组件。

Agent = Model + Harness

**如果你不是模特，那你就是安全带。**

框架是指除模型本身之外的所有代码、配置和执行逻辑。原始模型并非代理。但当框架赋予它状态、工具执行、反馈循环和可强制执行的约束等功能时，它就变成了代理。

具体来说，安全带包括以下部件：

- System Prompts
- 工具、技能、MCP+及其描述
- 捆绑式基础设施（文件系统、沙箱、浏览器）
- 编排逻辑（子代理生成、交接、模型路由）
- 用于确定性执行的钩子/中间件（压缩、延续、代码检查）

划分智能体系统中模型与底层架构的边界有很多种方法，但都比较繁琐。在我看来，这是最清晰的定义，因为它迫使我们 **围绕模型智能来思考系统设计。**

本文的其余部分将介绍核心线束组件，并从模型的核心原语反向推导出每个组件存在的 *原因* 。

#### 为什么我们需要安全带……从模特的角度来看

**有些事情我们希望智能体完成，但模型本身却无法做到。这时就需要用到接口组件了。** 模型（通常）接收文本、图像、音频、视频等数据，并输出文本。仅此而已。它们本身无法做到以下几点：

- 在交互过程中保持持久状态
- Execute code
- Access realtime knowledge
- 配置环境并安装软件包以完成工作

这些都是 **框架层面的功能** 。LLM 的结构需要某种机制来封装它们，使其能够执行有用的工作。例如，为了实现类似“聊天”的产品用户体验，我们将模型封装在一个 while 循环中，以跟踪之前的消息并添加新的用户消息。所有阅读本文的人都已经使用过这种框架。其核心思想是，我们希望将期望的代理行为转换为框架中的实际功能。

#### 从期望的代理行为出发，反向推导以利用工程技术

工具工程帮助人们注入有用的先验信息来指导智能体的行为。随着模型能力的不断提升，工具已被用于精准地扩展和修正模型，使其能够完成以前无法完成的任务。

我们不会逐一介绍所有框架功能。我们的目标是从帮助模型完成有用工作的出发点出发，提炼出一组功能。我们将遵循以下模式：

**我们想要的行为（或想要修复的行为）→ 利用设计来帮助模型实现这一目标。**

![](https://storage.ghost.io/c/97/88/97889716-a759-46f4-b63f-4f5c46a13333/content/images/2026/03/image-1.png)

#### 用于持久存储和上下文管理的文件系统

**我们希望代理程序拥有持久存储，以便与真实数据交互，卸载与上下文不符的信息，并在会话之间持久保存工作。**

模型只能直接操作其上下文窗口内的知识。在文件系统出现之前，用户必须将内容直接复制/粘贴到模型中，这种用户体验非常笨拙，而且不适用于自主代理。世界已经在使用文件系统来完成工作，因此模型自然而然地基于数十亿个如何使用文件系统的标记进行训练。自然而然的解决方案是：

**工具附带文件系统抽象和用于 fs-ops 的工具。**

文件系统可以说是最基础的工具原语，因为它解锁了许多功能：

- 代理程序会获得一个工作空间，用于读取数据、代码和文档。
- 工作可以逐步添加和卸载，而不是将所有信息都保存在上下文中。代理可以存储中间输出，并维护一个持续到会话结束的状态。
- **文件系统是一个天然的协作平台。** 多个智能体和用户可以通过共享文件进行协调。诸如智能体团队之类的架构正是基于此。

Git 为文件系统添加了版本控制功能，以便代理可以跟踪工作进度、回滚错误和进行分支实验。我们将在下文中更详细地探讨文件系统，因为它实际上是我们所需其他功能的一个关键基础组件。

#### Bash + 代码作为通用工具

**我们希望智能体能够自主解决问题，而无需人类预先设计每个工具。**

目前主流的代理执行模式是 [ReAct 循环](https://docs.langchain.com/oss/python/langchain/agents?ref=blog.langchain.com) ，其中模型进行推理，通过工具调用执行操作，观察结果，然后在 while 循环中重复此过程。但是，代理只能执行其逻辑所支持的工具。与其强迫用户为每个可能的操作构建工具，不如为代理提供一个像 bash 这样的通用工具，这才是更好的解决方案。

**该模型附带一个 bash 工具，因此模型可以通过编写和执行代码自主解决问题。**

Bash + 代码执行是 **让模型拥有计算机能力** 并自主完成其余工作的重要一步。模型可以通过代码动态设计自己的工具，而不是局限于一组预先配置好的固定工具。

虽然其他工具仍然会附带一些辅助工具，但代码执行已成为自主问题解决的默认通用策略。

#### 用于执行和验证工作的沙箱和工具

**代理需要一个具有正确默认设置的环境，以便他们能够安全地采取行动、观察结果并取得进展。**

我们赋予了模型存储和执行代码的能力，但所有这些都需要在一个地方进行。在本地运行代理生成的代码存在风险，而且单个本地环境无法扩展到大型代理工作负载。

**沙箱为代理程序提供安全的运行环境。** 代理程序无需在本地执行代码，而是可以连接到沙箱来运行代码、检查文件、安装依赖项并完成任务。这实现了安全、隔离的代码执行。为了进一步提高安全性，代理程序可以设置命令允许列表并强制执行网络隔离。沙箱还有助于扩展规模，因为可以按需创建环境，将其分发到多个任务中，并在工作完成后将其销毁。

**良好的环境需要配备完善的默认工具。Harness** 负责配置工具，以便代理能够执行有效的工作。这包括预安装语言运行时和软件包、用于 Git 和测试的命令行界面 (CLI)、以及用于 Web 交互和验证的 [浏览器](https://github.com/vercel-labs/agent-browser?ref=blog.langchain.com) 。

浏览器、日志、屏幕截图和测试运行器等工具为客服人员提供了观察和分析自身工作的方法。这有助于他们创建 **自我验证循环，从而** **编写应用程序代码、** 运行测试、检查日志并修复错误。

该模型本身并不配置执行环境。代理程序的运行位置、可用工具、可访问资源以及如何验证其工作状态，这些都是框架级别的设计决策。

**特工应该记住他们所看到的情况，并获取他们在接受培训时不存在的信息。**

模型除了自身权重和当前上下文信息之外，没有其他额外知识。由于无法编辑模型权重，因此“添加知识”的唯一方法就是通过 **上下文注入。**

对于内存而言，文件系统同样是核心原语。Harness 支持诸如 [AGENTS.md](http://agents.md/?ref=blog.langchain.com) 之类的内存文件标准，这些文件会在代理启动时注入到上下文中。当代理添加和编辑此文件时，Harness 会将更新后的文件加载到上下文中。这是一种的形式，代理可以持久地存储来自一个会话的知识，并将这些知识注入到未来的会话中。

知识截止意味着模型无法直接访问新数据，例如未经用户直接提供而更新的库版本。为了获取最新知识，网络搜索和 [Context7](https://context7.com/?ref=blog.langchain.com) 等 MCP 工具可以帮助智能体访问超出知识截止范围的信息，例如训练停止时尚不存在的新库版本或当前数据。

网络搜索和查询最新上下文的工具是集成到框架中的有用基础组件。

#### Battling Context Rot

**代理的性能不应在工作过程中下降。**

[上下文衰减](https://research.trychroma.com/context-rot?ref=blog.langchain.com) \*\*\*\*描述了随着上下文窗口逐渐被填满，模型推理和完成任务的能力会如何下降。上下文是一种宝贵且稀缺的资源，因此需要采取策略来管理它。

**如今，线束主要是一种用于良好上下文工程的交付机制。**

**压缩机制** 解决了上下文窗口即将填满时的处理问题。如果没有压缩机制，当对话超出上下文窗口时会发生什么？一种可能是 API 报错，但这显然不是理想的情况。系统必须针对这种情况采取某种策略。因此，压缩机制能够智能地卸载并汇总现有上下文窗口的内容，从而使代理能够继续工作。

**工具调用卸载** 有助于减少大型工具输出的影响，这些输出可能会在上下文窗口中造成大量噪声干扰，却无法提供有用的信息。该机制会将工具输出的头部和尾部标记保留在超过阈值标记数之后，并将完整的输出卸载到文件系统中，以便模型在需要时可以访问。

**技能** 旨在解决代理启动时加载过多工具或 MCP 服务器到上下文中的问题，这会导致代理在开始工作前性能下降。技能是一种框架级别的原语，它通过 **渐进式披露来解决这个问题。** 模型本身并未选择在启动时将技能的前端信息加载到上下文中，但框架可以支持这种做法，以防止模型出现上下文腐烂。

#### 长期自主执行

**我们希望智能体能够在较长的时间范围内自主、正确地完成复杂的工作。**

自主软件创建是编码智能体的终极目标。但如今的模型存在着早停、难以分解复杂问题以及跨多个上下文窗口工作时缺乏连贯性等问题。一个优秀的工具必须能够克服所有这些挑战。

早期的一些基础功能开始变得复杂起来。长期任务需要持久化的状态管理、规划、观察和验证，才能在多个上下文窗口中持续运行。

**文件系统和 Git 用于跨会话跟踪工作。** 代理在执行长期任务时会生成数百万个令牌，因此文件系统会持久地记录工作，以便跟踪进度。添加 Git 可以让新代理快速了解项目的最新工作和历史记录。对于多个协同工作的代理，文件系统还可以作为共享的工作账本，供代理协作。

**Ralph 循环用于持续工作。Ralph** [循环](https://ghuntley.com/loop/?ref=blog.langchain.com) 是一种工具模式，它通过钩子拦截模型的退出尝试，并在一个干净的上下文窗口中重新注入原始提示，强制代理继续执行以完成目标。文件系统使得这一切成为可能，因为每次迭代都从全新的上下文开始，但会读取前一次迭代的状态。

**规划和自我验证是确保项目顺利进行的关键。** 规划是指模型将目标分解为一系列步骤。框架通过良好的提示和注入关于如何在文件系统中使用计划文件的提醒来支持这一过程。完成每个步骤后，代理可以通过 **自我验证来检查其工作的正确性。** 框架中的钩子可以运行预定义的测试套件，并在失败时返回模型并显示错误消息；或者，也可以提示模型独立地进行代码自评估。验证将解决方案建立在测试之上，并为自我改进提供反馈信号。

#### The Future of Harnesses

#### 模型训练与线束设计的耦合

如今的智能体产品，例如 Claude Code 和 Codex，都采用模型和框架进行后训练。这有助于模型在框架设计者认为它们天生擅长的操作上取得进步，例如文件系统操作、bash 脚本执行、规划或使用子智能体并行化工作。

这就形成了一个反馈循环。有用的基本元素被发现，添加到框架中，然后在训练下一代模型时使用。随着这个循环的重复，模型在它们所训练的框架内变得越来越强大。

但这种协同演化对泛化能力产生了一些有趣的副作用。例如，改变工具逻辑会导致模型性能下降。Codex [-5.3 提示指南中](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide/?ref=blog.langchain.com#apply_patch) 关于 apply\_patch 工具逻辑的文档就是一个很好的例子，该逻辑用于编辑文件。一个真正智能的模型应该能够轻松地在不同的补丁方法之间切换，但使用循环中的工具进行训练会导致过拟合。

**但这并不意味着最适合你任务的测试环境就是模型进行后训练时使用的测试环境。Terminal** [Bench 2.0 排行榜](https://www.tbench.ai/leaderboard/terminal-bench/2.0?ref=blog.langchain.com) 就是一个很好的例子。在 Claude Code 中，Opus 4.6 的得分远低于在其他测试环境中的 Opus 4.6。 [在之前的博客中](https://x.com/Vtrivedy10/status/2023805578561060992?s=20&ref=blog.langchain.com) ，我们展示了如何仅通过更换测试环境就将我们的编码代理在 Terminal Bench 2.0 上的排名从前 30 名提升到前 5 名。针对你的任务优化测试环境，可以显著提升模型的性能。

![](https://storage.ghost.io/c/97/88/97889716-a759-46f4-b63f-4f5c46a13333/content/images/2026/03/image-2.png)

#### 线束工程的发展方向

随着模型能力的提升，目前依赖外部资源的部分功能将被模型本身吸收。例如，模型将更擅长规划、自我验证和长期一致性，从而减少对上下文信息注入的需求。

这表明随着时间的推移，线束的重要性可能会降低。但正如快速响应的工程设计在今天仍然至关重要一样，线束工程设计很可能也会继续对构建优秀的智能体发挥作用。

诚然，如今的资源管理技术可以弥补模型的不足，但它们也围绕模型智能构建系统，从而提升模型的效能。无论模型本身的智能如何，一个配置良好的环境、合适的工具、持久化的状态以及验证循环都能显著提高模型的效率。

在 LangChain，我们利用 Harness 工程来改进我们的 Harness 构建库 [deepagents，](https://docs.langchain.com/oss/python/deepagents/overview?ref=blog.langchain.com) 这是一个非常活跃的研究领域。以下是我们目前正在探索的一些开放且有趣的问题：

- 协调数百个代理并行处理共享代码库
- 代理程序通过分析自身轨迹来识别和修复线束级故障模式
- 它利用动态方式，根据具体任务实时组合合适的工具和上下文，而不是预先配置。

这篇博客旨在定义什么是模型框架，以及我们希望模型完成的工作如何塑造模型框架。

**模型包含智能，而载体系统则是使这种智能发挥作用的系统。**

为了更好地利用建筑、更好的系统和更好的代理人。

## 结构化（1）

#### 主旨概括

这篇文章的核心观点是：**智能体不只是模型本身，而是 “模型 + Harness（框架 / 承载系统）” 共同作用的结果**。  
模型负责 “智能”，而 Harness 负责把这种智能变成真正可执行、可持续、可验证的工作能力。

#### 按原文逻辑梳理

##### 1. 什么是 Harness：为什么 “模型” 本身不等于智能体

- 作者提出一个很清晰的公式：**Agent = Model + Harness**。
- 所谓 Harness，指的是**除模型本身之外的所有代码、配置和执行逻辑**。
- 原始模型本质上只是一个 “接收输入、输出文本” 的系统；只有给它配上状态、工具、反馈循环和约束机制，它才真正变成智能体。

###### Harness 主要包含的内容
- System Prompts（系统提示）
- 工具、技能、MCP 及其说明
- 文件系统、沙箱、浏览器等基础设施
- 编排逻辑，如子代理生成、交接、模型路由
- 用于确定性执行的钩子 / 中间件，如压缩、续跑、代码检查

**关键点：**  
作者强调，用 “模型智能 + 外围系统” 来理解智能体，比单纯讨论模型能力更清楚，因为这能帮助我们从 “如何让模型真正干活” 的角度设计系统。

---

##### 2. 为什么需要 Harness：从模型能力的边界倒推

- 模型通常只能处理文本、图像、音频、视频等输入，并输出文本。
- 但现实中我们希望智能体做到的很多事，**模型本身并不会**，例如：
  - 在多轮交互中保持持久状态
  - 执行代码
  - 获取实时知识
  - 配置环境、安装依赖并完成任务

**结论：**
这些都属于**框架层面的功能**，必须由 Harness 来补足。

###### 一个直观例子
- 聊天产品的 “连续对话体验”，本质上就是在模型外面包了一层`while`循环：
  - 记录历史消息
  - 加入新的用户输入
  - 反复调用模型
- 这其实就是最基础的 Harness。

**关键点：**  
作者的出发点不是 “框架里有什么功能”，而是反过来问：  
**“我们想让智能体表现出什么行为？” 然后再设计相应的工程能力去支持它。**

---

##### 3. 文件系统：智能体最基础的能力底座

作者首先强调：**文件系统是最基础、最关键的工具原语之一**。

###### 为什么需要文件系统
我们希望智能体能够：
- 和真实数据、代码、文档交互
- 把不适合塞进上下文窗口的信息 “卸载” 出去
- 在会话之间保留工作成果和状态

###### 文件系统带来的能力
- 给智能体一个工作空间，用来读取和写入数据
- 支持逐步存储中间结果，而不是把所有内容都塞在上下文里
- 让多个智能体和用户通过共享文件协作
- 结合 Git 后，可以记录历史、回滚错误、分支实验

###### 重要案例
- 作者指出：**世界本来就是用文件系统来完成工作的**，而模型训练中也见过大量与文件系统相关的使用方式，因此让智能体基于文件系统工作是很自然的设计。

**关键点：**  
文件系统不仅是存储工具，更是：
- 状态管理工具
- 协作平台
- 长任务持续执行的基础设施

---

##### 4. Bash + 代码执行：给智能体 “通用行动能力”

- 当前主流智能体执行模式是**ReAct 循环**：
  - 模型先推理
  - 再调用工具执行动作
  - 观察结果
  - 然后继续下一轮
- 问题在于：如果工具都是预先定义死的，智能体能力就会被限制住。

###### 作者的解决方案
- 与其为每个动作都专门做一个工具，不如给智能体一个更通用的工具：**bash + 代码执行能力**。
- 这样模型就能：
  - 自己写代码
  - 自己运行代码
  - 动态构造新工具解决问题

###### 意义
这相当于让模型拥有了 “使用计算机” 的能力，而不是只会调用几个固定按钮。

**关键点：**  
代码执行已经成为今天自主智能体最重要的通用策略之一，因为它大幅减少了对人工预设工具的依赖。

---

##### 5. 沙箱与默认环境：让智能体能安全、稳定地执行任务

有了代码执行能力之后，新的问题出现了：**代码在哪运行？怎么保证安全？**

###### 沙箱的作用
- 为智能体提供隔离、安全的运行环境
- 让它可以：
  - 运行代码
  - 检查文件
  - 安装依赖
  - 完成任务
- 同时可配置：
  - 命令白名单
  - 网络隔离

###### 沙箱的另一层价值：扩展性
- 可以按需创建环境
- 将环境分发给多个任务
- 工作完成后销毁

###### 好环境不只是 “能跑”，还要 “工具齐全”
Harness 还要预装或配置好：
- 语言运行时
- 常见依赖包
- Git、测试 CLI
- 浏览器

###### 浏览器和验证工具的重要性
浏览器、日志、截图、测试运行器能帮助智能体形成**自我验证闭环**：
- 写代码
- 运行测试
- 看日志
- 修复 bug

**关键点：**  
“运行位置、可用工具、能访问什么、如何验证工作结果”—— 这些都不是模型天然具备的，而是 Harness 的设计成果。

---

##### 6. 记忆与最新知识：让智能体既 “记得住” 又 “跟得上”

###### 6.1 记忆：通过文件系统实现长期记忆
- 模型除了权重和当前上下文，没有真正的长期记忆。
- 因此，新增知识的唯一现实方式是：**上下文注入**。

###### 具体做法
- Harness 可以支持像`AGENTS.md`这样的记忆文件：
  - 代理启动时把文件内容注入上下文
  - 代理可以修改这个文件
  - 下一次会话再重新读入

这相当于一种 “可持续更新的外部记忆”。

###### 6.2 最新知识：通过网络搜索和 MCP 获取
- 模型存在知识截止问题，无法天然知道训练之后的新信息。
- 比如：
  - 新发布的库版本
  - 当前实时数据
- 因此需要：
  - 网络搜索
  - Context7 等 MCP 工具

**关键点：**  
Harness 让智能体既能 “记住过去”，又能 “获取新信息”，从而突破模型本身的知识边界。

---

##### 7. 对抗上下文衰减：防止任务做着做着变笨

作者提出一个关键问题：**上下文窗口越来越满时，模型表现会下降，这就是 “上下文衰减（Context Rot）”**。

###### 为什么这是大问题
- 上下文是有限资源
- 内容堆积越多，噪声越大
- 推理质量和任务完成能力都会下降

###### Harness 的几个解决办法

###### 7.1 压缩机制
- 当上下文快满时，对已有内容进行总结和卸载
- 避免直接因为超长而报错中断

###### 7.2 工具调用卸载
- 大型工具输出常常很长，但有用信息不多
- 系统可以只保留开头和结尾，把完整输出放到文件系统里
- 需要时再读取

###### 7.3 技能（Skills）
- 如果一开始把所有工具、MCP 都塞进上下文，会拖慢智能体
- 技能机制采用**渐进式披露**：
  - 先只加载少量必要信息
  - 需要时再逐步补充

**关键点：**  
今天很多 Harness，本质上就是在做 “上下文工程”，目的是让模型在长流程工作中不掉性能。

---

##### 8. 长期自主执行：让智能体持续完成复杂工作

作者认为，**自主软件开发**是编码智能体的终极目标，但现阶段模型有几个明显短板：
- 容易早停
- 不擅长拆解复杂问题
- 跨多个上下文窗口缺乏连贯性

因此，需要 Harness 补上这些能力。

###### 8.1 文件系统 + Git：支撑长任务
- 长任务会产生**数百万 token**的轨迹
- 文件系统用来保存过程状态
- Git 用来帮助新代理快速理解当前进度与历史

###### 8.2 Ralph 循环：强制代理继续工作
- 当模型试图退出时，钩子会拦截
- 再把原始提示重新注入一个新的上下文窗口
- 让代理在 “干净上下文” 中继续执行

这能缓解上下文过长和中途停止的问题。

###### 8.3 规划与自我验证
- 规划：把大目标拆成小步骤
- 自我验证：每完成一步就检查是否正确

###### 具体验证方式
- 钩子自动运行预定义测试套件
- 测试失败时，把错误返回给模型继续修复
- 或让模型做代码自评审

**关键点：**  
长期自主执行不是单靠 “更聪明的模型” 就够了，还需要：
- 持久状态
- 规划机制
- 验证反馈
- 跨窗口的连续执行能力

---

##### 9. Harness 的未来：模型与框架会共同进化

###### 9.1 模型训练正在和 Harness 深度耦合
- 现在很多智能体产品（如**Claude Code**、**Codex**）都会针对特定 Harness 进行后训练。
- 这样模型会更擅长：
  - 文件系统操作
  - bash 执行
  - 规划
  - 子代理并行协作

###### 9.2 这种协同也会带来副作用
- 模型可能会对某种工具逻辑 “过拟合”
- 举例：
  - 作者提到`apply_patch`这类文件编辑工具逻辑
  - 理想上，真正强的模型应能灵活适配不同补丁方式
  - 但如果训练时长期绑定某种特定工具流程，就可能导致泛化变差

###### 9.3 测试环境不同，表现也会差很多
- 作者引用**Terminal Bench 2.0**作为例子：
  - 同样是**Opus 4.6**
  - 在 Claude Code 中的分数，明显低于它在其他测试环境中的表现
- 他们之前的博客还提到：
  - **仅仅更换测试环境**
  - 就让自己的编码代理在 Terminal Bench 2.0 上从**前 30 名提升到前 5 名**

**关键点：**  
这说明：**最适合某个任务的 Harness，不一定就是模型训练时使用的那个 Harness**。  
针对任务优化环境设计，可能带来非常明显的性能提升。

---

##### 10. 作者对未来方向的判断

###### 未来可能发生的变化
随着模型变强，部分今天依赖外部 Harness 的能力，可能会被模型逐渐内化，例如：
- 更强的规划能力
- 更好的自我验证
- 更稳定的长期一致性

###### 但 Harness 不会消失
作者认为，即使模型更强，Harness 仍然会长期重要。原因是：
- 好的环境配置能提升效率
- 合适工具能扩大可执行范围
- 持久状态能提升连续性
- 验证闭环能提高结果质量

###### 当前还在探索的开放问题
LangChain 团队正在研究例如：
- **如何协调数百个代理并行处理同一代码库**
- **如何让代理通过分析自身轨迹，识别并修复 Harness 层面的失败模式**
- **如何按任务动态组合工具和上下文，而不是提前静态配置**

---

#### 总结提炼

- 这篇文章最重要的结论是：**智能体的真实能力，很大程度上取决于 Harness，而不只是模型本身。**
- Harness 的核心任务，是把模型的 “会想” 变成 “能做、能记、能验证、能持续推进”。
- 文章重点讨论了几个关键组件：
  - 文件系统：管理状态、持久存储、协作
  - Bash / 代码执行：提供通用行动能力
  - 沙箱与环境：保证安全、可扩展、可验证
  - 记忆与搜索：补足长期记忆和实时知识
  - 上下文管理：防止上下文衰减
  - 规划与验证循环：支持长期自主执行
- 作者最后强调：**模型负责智能，Harness 负责把智能转化为稳定有效的生产力。**
