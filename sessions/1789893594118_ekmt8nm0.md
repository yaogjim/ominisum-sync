## 分析要点

- **核心高价值点**：当输出是预先定义的有限选项时，可读取单Token标签的logits并在候选集合内归一化，避免生成和解析答案文本；但所得概率不等于正确率，必须在实际任务数据上验证。
- **留存建议**：精读技术实现与评估部分，选择性存档；宣传数据仅作为待验证线索（包含决策与生成解耦、本地候选评分、概率校准及对比式数据整理等可复用知识，并提供部署步骤、代码和明确的适用边界。）

**知识要点**

- 按输出需求分工：生成模型负责开放式文本，决策模型负责有限选项选择，代码负责执行、权限约束与完成核验；候选动作应随系统状态更新。
- 固定选项评分与结构化生成不同：前者直接读取候选标签分数，后者仍逐Token解码；评分需要验证标签分词，并为非穷尽选项加入无匹配或升级审核出口。
- 对比式数据整理通过只改变关键事实来翻转标签，并用证据移除检查排除答案泄漏；相关配对与同源样本应留在同一数据划分中。

**行动项**

- 选择一个已有的重复路由或分类节点，建立固定选项评分原型，与现有生成路径比较正确性、延迟和每个完成任务的总成本。
- 使用工作流中的标注样本评估概率与错误率，调整自动执行和审核阈值，并测试无匹配、模糊输入及错误路由情况。
- 为接入后的Agent增加动态候选更新、操作与支出上限、进度保存、重复处理防护及独立完成检查，将发布等动作保留在审批之后。

#### 01\. 找到你的代理中 Jev 可以接管的那个部分

Jev 是 TypeSafe AI 的 System One 模型 ：你提供信息和预定义问题，它返回带有概率的类型化答案。它无法撰写你的简报、生成代码，或用散文解释其推理过程。

[TypeSafe 的发布文章](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

从一个这样的任务开始：

> 研究三款新的 AI 代理工具，并起草明天的简报。保存草稿供我审阅。

这个任务包含若干决策：我们是否有足够的来源？下一个执行者是谁？草稿是否已准备好供审阅？

这些就是 Jev 的候选事项。获取来源、撰写段落和保存文件仍然属于你的工具和生成模型。一条精确的规则，例如执行十次操作后停止，则应属于代码。

对于 GrokBot 风格的首席参谋，保存的交接内容可以供给现有的工作器使用。连接该工作器要在下面的独立设置之后进行；你无需代理团队即可完成首次运行。

#### 04\. 将请求转化为已保存的交接

chief.py

chief.py在 jev-starter 内、.venv 外创建

。使用纯文本编辑器，并保存为确切的文件名，而不是

.txt。

```text
import json
import os
from getpass import getpass
from pathlib import Path
from uuid import uuid4
from typesafe_sdk import Choice, TypeSafeAPIError, TypeSafeClient

if not os.environ.get("TYPESAFE_API_KEY"):
    os.environ["TYPESAFE_API_KEY"] = getpass("TypeSafe API key: ").strip()

goal = input("Goal: ").strip()
if not goal:
    raise SystemExit("Enter a goal.")
notes = input("Completed work: ").strip() or "Nothing yet."
state = {"goal": goal, "completed_work": notes}

try:
    with TypeSafeClient(model="jev-1.13.0") as client:
        result = client.system_one(
            state=state,
            questions={
                "next_worker": Choice(
                    instructions="Choose the next step for a research briefing.",
                    criteria={
                        "research": "Collect evidence still needed for the goal.",
                        "write": "Draft the briefing from sufficient evidence.",
                        "review": "Goal unclear, outside scope, or work complete.",
                    },
                )
            },
        )
except TypeSafeAPIError as error:
    raise SystemExit(f"API error {error.status}; see Step 8.")

answer = result.choices["next_worker"]
destination = "review"
if answer.choice in {"research", "write"} and answer.confidence >= 0.85:
    destination = answer.choice

folder = Path(__file__).resolve().parent / "queue" / destination
folder.mkdir(parents=True, exist_ok=True)
job = folder / f"{uuid4().hex}.json"
payload = dict(state, choice=answer.choice, confidence=answer.confidence,
               destination=destination, status="queued")
job.write_text(json.dumps(payload, indent=2, ensure_ascii=False), encoding="utf-8")
print("Saved handoff:", job)
```

在 macOS/Linux 上运行：

```text
.venv/bin/python chief.py
```

在 Windows 上运行：

```text
.\.venv\Scripts\python.exe chief.py
```

在提示时粘贴你的 API 密钥——终端会将其隐藏。 对于目标 ，请输入为明天的简报比较三个 AI 代理工具 。对于已完成的工作，请输入尚未收集任何来源。

你的结果： 一个已保存的交接 ：包含完整文件路径的消息。打开该 JSON 文件：其中包含你的请求、进度、Jev 的选择、置信度和目标位置。 每次运行都会在 queue/research、queue/write 或 queue/review 下创建一个新文件。这些是本地任务队列；已保存的任务会等待工作进程来消费它

API 调用和错误处理遵循

[SDK 使用指南](https://docs.typesafe.ai/sdk/python/usage)。我将初始审核阈值设为 0.85 - 请使用你工作流中的标注示例进行调整。置信度并非准确率百分比。

#### 05\. 提出有导向性的问题

三种答案类型对应不同的用途：

Jev gives you three question types, each built for a different kind of decision:

- Choice 从列表中选择一个选项。用于类似这样的问题：“接下来应该由谁工作？”它会返回所选选项、其概率分布以及置信度。
- Score 根据你定义的量表评估某事物。用于类似这样的问题：“这个来源的相关性有多高？”它会返回该量表上的一个值，以及概率和置信度。
- Noul 回答一个是或否的问题。用于类似这样的问题：“这个请求需要发布吗？”它会返回从 0 到 1 的“是”的概率。

定义一个相关性评分，包含三种描述：不相关、部分相关、直接回答问题。其数值结果范围为 0 到 2，包括小数。Noul 接近 0.5 表示对是/否不确定。

[评分](https://docs.typesafe.ai/primitives/score) ·

[Noul](https://docs.typesafe.ai/primitives/noul)

![Image](https://pbs.twimg.com/media/HSgs9sCXYAEaXNH?format=jpg&name=large)

一个有用的细节：Jev 看不到你的问题 ID。 将字段命名为 safe\_to\_publish 不会贡献任何指令。将实际需求放在问题中，并清晰地描述每个选项。

[选项文档](https://docs.typesafe.ai/primitives/choice)

同时提供证据。“研究员完成了”告诉 Jev 的信息比来源、发现和剩余缺口要少。将这些字段与原始请求分开保存。

[状态文档](https://docs.typesafe.ai/concepts/state)

![Image](https://pbs.twimg.com/media/HSgtBJgWgAEGBgE?format=jpg&name=large)

#### 07\. Stop paying for questions to wait on each other

Your dispatcher may need a worker, an urgency score, and an approval check. If all three can inspect the same state, send them together.

TypeSafe 支持并行问题和推测分支：询问可能的后续操作，然后仅使用与所选分支相关的答案。 问题之间无法读取彼此的答案。如果某个决策需要最新的搜索结果，请先执行搜索。

[并行评估模式](https://docs.typesafe.ai/patterns/fan-out)

浏览器示例暴露了另一个瓶颈。其优化后的运行时将浏览器协议调用的中位数从 1,092 次降至 101 次 ，同时任务时间中位数在三组匹配对比中下降了 25%。两个版本使用了相同的模型。

这些更改包括在一次读取中收集页面状态，并避免为不相关的动画进行新的预测。在花钱使用更快的模型之前，先检查重复的工具调用。

#### 08\. Give overnight work somewhere to stop

For a morning briefing, I'd allow source collection and draft creation, then stop at review. Publishing should require a separate permission check.

The application also needs an action limit, a spending limit, and saved progress. After an interruption, it should inspect the last completed action before repeating anything. A confident answer cannot prove that a file was saved or a message was sent.

Browser Use 在 Jev 选择 DONE 后独立检查结果。将这种分离机制借鉴到你自己的完成检查中。

[Agent loop](https://github.com/browser-use/jev-ultrafast/blob/main/jev_ultrafast/agent.py)

If the starter fails, use the error to choose the fix:

- Python 命令缺失： 完成 Python 安装并重新打开终端。
- 模块缺失： 使用相同的 .venv 解释器重复 SDK 安装。
- 401： 替换 API 密钥并重新运行。
- 422： 对照粘贴的代码检查命名的请求字段。
- 429 / 529： 允许退避；如果速率限制或过载持续存在，稍后重试。

SDK 提供重试；如果 API 错误仍然存在，脚本会停止。

#### Bespoke Nimble

**数据、模型、配方，用于开放的 Jev**

模型 · 能力 · 快速开始 · 方法论 · 文档与开发 · 引用

Introducing Bespoke Nimble. Serving reads the prompt once and then scores one answer token per question. Data curation changes one fact so that the correct answer flips. Training fine-tunes Qwen3.5-9B

Nimble 接收一些文本和一个模式，并对文本做出类型化决策。模式是要回答的问题列表。每个问题要么是从你提供的列表中选择一个选项，要么是一个真或假的问题。对于每个问题，Nimble 返回它选择的答案以及每个允许答案的概率。

Nimble 一步完成每个决策，不会先写出任何推理过程，因此速度很快（极快！）。Nimble 受到 TypeSafe 的 Jev 的 System One 方法的启发。在这个代码仓库中，我们分享了训练此类模型的配方。

请注意，我们并未从 Jev 中蒸馏。该代码仓库的目的是展示如何整理数据、如何训练以及如何部署这样一个模型，并鼓励更多研究！

你可以在搭载 Apple Silicon 的 Mac 上，或在配备 NVIDIA GPU 的机器上运行 Bespoke-Nimble-9B。

#### Capabilities

我们在一天内构建了 Nimble，因此可能会有些粗糙之处。Nimble 能做到的事情来自两个来源：第一个是基础模型 Qwen3.5-9B，第二个是我们为几个特定领域整理的数据。

Task You define You get back

Route a request 目标位置以及每个目标的适用时机 所选目的地及每个目的地的概率

Check a condition 一个是或否的问题及证据 真或假，以及各自的概率

Apply a policy 规则及允许的结果 基于你提供的文本做出的类型化决策

Rate an outcome 有序层级，每个层级都有明确的标准 所选层级以及每个层级的概率

你提供一个上下文，即要判断的文本，以及一个 schema。该 schema 必须是扁平的，这意味着它没有嵌套字段。每个字段都是一个 enum 或一个 boolean。enum 字段有一组固定的字符串选项，而 boolean 字段为 true 或 false。

每个允许的答案都有一个长度为单个 token 的代码。评分器会读取模型针对这些代码的 logits。Logits 是模型为每个 token 给出的原始分数。评分器通过 softmax 函数将 logits 转换为概率。我们的 Python 代码随后根据这些概率构建输出，因此无需解析生成的 JSON。如果某个字段是有序评分量表，你的应用程序可以使用这些概率来计算期望等级。

在 Mac 上， `ParallelScorer` 会处理一次共享上下文，然后并行对所有字段进行评分。CUDA 评分器会针对每个字段单独评分，每次都使用完整提示词。两种评分器都会返回类型化输出。它们还会返回候选答案的 logits 和概率。每个字段都是单独评分的，因此一个字段无法看到另一个字段的答案。

##### 当前发布版本无法构建的内容

- Nimble 仅接受文本。你无法用它来评判其他类型的输入，例如图像。即使基础模型包含视觉部分，也是如此。
- Nimble 仅从你提供的答案中进行选择。它无法自行编写文本，例如解释。它也无法返回嵌套 JSON 或从上下文中摘取的一段文本。一个枚举字段可以有 1 到 26 个字符串选项，而一个布尔字段有两个。
- 这些概率并不保证某个答案是正确的。Nimble 会对它们进行缩放，使其在你提供的所有答案中加起来等于 1。概率为 0.9 并不意味着该答案有 90% 的概率是正确的。如果有可能你的所有答案都不合适，请添加一个表示“无匹配”的答案。在依赖任何概率阈值之前，请在你自己的数据上进行测试。
- 每个提示最多可以有 2,048 个 token。此限制包括 schema 以及提示中指定要评分字段的部分。Nimble 会拒绝更长的提示。字段之间不能相互依赖，因此你的代码必须检查不同字段的答案是否一致。

我们在精心整理的 2,676 个示例上训练了 Bespoke-Nimble-9B。因此，它的性能将取决于这些数据及其来源领域。所以不要期望有很强的泛化能力。但我们确实看到，Nimble 在新领域中总体上优于其基础模型 Qwen3.5-9B。

#### Methodology

##### Serving

In a nutshell:

- 一次性处理上下文和模式（预填充 KV 缓存）
- 我们获取了关注标记的分数。

我们在 Bespoke-MiniCheck 中采用了这种方法（无需进行 KV 缓存预填充），因为它总是返回单个 json 元组： `{"is_claim_supported_by_context": p}` 。

这里的挑战在于，我们无法获取教师模型（或人类）给出的概率。但正如你在上面看到的，我们只需要以某种方式获取 logits，并确保 logits 尽可能经过校准以估计概率。

我们通过创建负例来推动模型经过校准，成为更好的决策者，这迫使模型成为更好的判别器。

因此，我们用一种新方法制作了训练数据，我们称之为对比式数据整理。在这种方法中，我们编写两个几乎相同的示例。它们在一个相关事实上有所不同，而这个差异会改变正确答案。其他一切保持不变，包括问题和策略。从这些配对中，模型学习哪些证据应该改变其决策。

Watch the contrastive data curation video: changing the signer from Mira to Noah flips the answer from true to false.

在这个例子中，规则是只有当退款的唯一授权由可以为该账户批准退款的人签署时，退款才被授权。这个例子有两个证据句子，你需要两者才能回答。

Evidence First example Changed example

Who can approve refunds 只有 Mira 可以为账户 42 授权退款。 Unchanged

Authorization record

Is the refund authorized? `true` `false`

我们的策展流水线将这一思路用于 Choice、Noul 和 Score 任务。它包含四个步骤：

1. 检查决策规则。我们从训练源的 schema 和策略出发。我们写下规则所依赖的基本事实。然后我们检查这些规则是否可能得出不同的答案。
2. 构建配对。我们写出两个证据句子，你需要同时具备这两句才能找到答案。然后我们在其中一个句子中最多改动八个词。我们通过这一改动来改变一个事实，我们称之为焦点事实，因此标签也随之改变。其余上下文和其他事实保持不变。
3. 检查两个示例。我们使用独立的模型调用来检查每个示例中的事实。我们还使用这些调用来检查示例是否与策略一致，以及文本是否暗示了答案。然后我们依次移除每个证据句子。在移除任一证据句子的情况下，即使所有其他文本都存在，焦点事实也必须变为未知。这样，我们就知道没有其他文本会泄露答案。
4. 生成标签。我们使用代码将已检查的规则应用于已检查的事实。只有当所有必需的检查都通过且两个标签不同时，我们才保留一对。我们保存所有模型请求和响应，以及检查结果。你可以用它们离线重放整个过程。

移除证据句子的示例仅用于检查。我们不会将它们连同标签加入训练数据，因为缺少证据并不意味着答案是错误的，也不意味着分数很低。源家族是我们从一个训练源构建的一组示例。我们将一对中的两个示例，以及来自同一源家族的所有示例，保留在同一个划分中。该划分要么是训练集，要么是评估集。

### 构建你自己的 Jev（100% 本地）

将开源 LLM 转变为快速本地决策引擎所需的一切，无需重新训练。内容涵盖下一 token 评分、带概率分布的固定选项、SGLang，以及在同一模型上与标准文本生成进行的实操基准测试。

---

许多 LLM 调用并不需要新生成的文本。应用程序已经知道可能的答案，只需要模型从中选择一个。

假设一张支持工单写道：“同一订阅我被扣了两次费。”

应用程序需要将其发送给三个团队之一：账单、技术支持或账户访问。

普通的 LLM 调用会要求模型写出一个答案。它可能返回一个句子、一个标签或一个 JSON 对象。应用程序等待该文本，解析它，并提取所选的团队。

![Image](https://pbs.twimg.com/media/HSm1UsNa8AA5lvl?format=jpg&name=large)

如果每个有效答案都已知，那就不必要了。

事实上，更好且更高效的方法是将同一个请求视为一个决策（Jev 就是这样做的）。应用程序将工单/查询和三个允许的答案提供给 Jev。然后模型一次性为每个答案返回一个分数（我们稍后会讨论具体如何做到这一点）：

```plaintext
billing             0.91
technical support   0.06
account access      0.03
```

此处以最高概率选择计费，应用程序代码实际上可以看到它获胜的强度。

这是 Jev 所具备的行为，我们将在本地复现。

我们将提供输入查询和允许的答案。在一次评分请求中，模型将返回一个决策和概率分布，而不会生成句子或 JSON 对象。

虽然 Jev 是闭源的，但这种推理模式已经在几个开源语言模型中可用。

更具体地说，我们将使用 SGLang（通过 /v1/score）来实现它，用 Qwen 和 DeepSeek 模型进行测试，并将其与结构化输出和普通文本生成进行对比。

![Image](https://pbs.twimg.com/media/HSnYuraaYAAQ63g?format=jpg&name=large)

先说明预期：本文复现的是推理路径，而非完整的 Jev 系统。Jev 还包含训练和校准工作，而评分端点并不提供这些内容。

---

### 固定答案评分不同于结构化输出

人们很容易将 Jev 的机制与结构化输出混淆，因为这两种方法都限制了应用程序接收到的内容，但它们在推理服务器内部所做的工作并不相同。

对于上面讨论的同一个支持工单，结构化输出可能会从模型得到以下输出：

```json
{"team": "billing"}
```

指定的模式阻止了无效对象，因此它不会自行选择团队。

然而，这还可以进一步改进，因为在底层，模型仍然逐个令牌地生成左花括号、字段名、值和右花括号。一旦生成完成，应用程序就会读取 team 字段。这个视频展示了这一过程：

[![视频](https://pbs.twimg.com/amplify_video_thumb/2101414186102493184/img/DC6tk4qvFBFFimx7.jpg)](https://x.com/_avichawla/status/2101563610644496464)[![视频](https://pbs.twimg.com/amplify_video_thumb/2101414186102493184/img/DC6tk4qvFBFFimx7.jpg)](https://x.com/_avichawla/status/2101563610644496464)

通过评分（Jev 就是这样做的），应用程序可以将这三个团队作为有效结果的完整列表提供。服务器可以读取每个结果的一个模型分数，并返回本文前面展示的分布。它不会生成 JSON 对象。

![Image](https://pbs.twimg.com/media/HSm3BpDbgAAUOlt?format=jpg&name=large)

然后我们可以返回所有三个值，而不是仅返回计费结果，这样应用程序代码就能以不同方式处理这两个结果：

```plaintext
Result 1                          Result 2
billing       0.91                billing       0.46
technical     0.06                technical     0.44
account       0.03                account       0.10
```

例如，在上述情况下，两者都会选择计费。

但第一个有明确的偏好，而第二个几乎是平局。应用程序可以自动路由第一张票，并在需要时将第二张发送审核。

此外，模型只会提供这些分数，而应用程序代码将为其下游使用设定规则。

例如，可能要求最高答案超过0.80，并且领先第二答案至少0.20。这些阈值存在于代码中，可以在其中进行测试和更改。

![Image](https://pbs.twimg.com/media/HSm2_dMbMAA6rpo?format=jpg&name=large)

0.91的值意味着计费在这三个选择上获得了91%的概率质量。这并不证明模型在91%的情况下是正确的。我们需要有标签的示例来衡量这一点。这就是我稍后将讨论的校准问题。

但与此同时，请记住，结构化输出会生成一个有效的对象。固定答案评分会返回应用程序已经知道的答案分布。

### LLM 如何生成第一个输出 token

在我们讨论如何将因果 LLM 转变为 Jev 风格的模型之前，最好先了解 LLM 中的常规生成步骤。

![Image](https://pbs.twimg.com/media/HSm6yGwaoAAnfso?format=jpg&name=large)

- 分词器首先将提示转换为 token ID。
- 模型处理该序列，并为下一个位置生成一个向量。
- 该向量为模型词汇表中的每个 token 都包含一个数值。例如，Qwen 的词汇表包含数万个 token，因此该向量包含数万个数值。

这些原始数字是 logits。logit 越大，表示模型越倾向于将该 token 作为下一个延续。这些值还不是概率。

在正常生成过程中，服务器会对这个向量应用模型的解码规则（温度等），选择一个 token，并将其追加到提示词中。

然后，模型会为下一个位置生成一个新的词汇表大小的向量。生成/解码会重复这个过程，直到遇到停止 token 或达到输出限制。

![Image](https://pbs.twimg.com/media/HSozL26bsAA33xt?format=jpg&name=large)

但当我们想要做出有界决策时，我们只关心第一个向量。

回想一下上面讨论的支持路由器示例。该应用程序接受三个答案：

```plaintext
billing
technical support
account access
```

在提示中，我们可以为每个答案分配一个简短的标签：

```plaintext
A = billing
B = technical support
C = account access
```

提示以请求一个标签结束。

```plaintext
Route the support ticket into exactly one category.

Ticket:
I was charged twice for the same subscription.

Allowed labels:
A = billing
B = technical support
C = account access

Return only the label.

Label:
```

“标签：”是提示中的最后文本。

因此，下一个位置就是模型通常会生成 A、B 或 C 的地方。

处理完这个提示后，模型将为该位置生成其通常的词汇量大小的向量。该向量将包含标记 A 的 logit、B 和 C 的 logits，以及词汇表中每个其他标记的 logits。

然后，评分路径可以执行四种操作：

![Image](https://pbs.twimg.com/media/HSm6tPPbwAAGsVc?format=jpg&name=large)

1. 找到 A、B 和 C 的标记 ID。
2. 读取词汇向量中这些位置上的三个 logit。
3. 忽略所有其他 logit。
4. 对选定的三个值应用 softmax。

如果选定的 logit 分别为 8.2、5.5 和 4.8，受限 softmax 会产生大约 0.91、0.06 和 0.03。我们可以将这些位置映射回账单、技术支持和账户访问。

归一化仅限于所声明的选项。我们并不是在问 A 在整个词表上是否具有 91% 的概率。

相反，我们是在问，在应用程序排除了所有其他响应之后，模型如何在 A、B 和 C 之间分配其偏好。

![Image](https://pbs.twimg.com/media/HSm7QlHaoAAK04I?format=jpg&name=large)

这是 SGLang 已经在 /v1/score 中实现的一项操作。

它将提示词输入模型，读取所请求的 token 位置，并返回它们的分数。这使我们无需修改 Qwen 实现并自行提取最终张量。

顺便说一句，答案使用 A、B 和 C，而不是直接对“billing”、“technical support”和“account access”这些词进行评分，原因在于一个可见的词不一定是一个 token。

例如：

- “billing”对于某个分词器来说可能是一个 token，而对于另一个分词器来说可能是多个 token。
- “technical support”肯定会跨越多个位置。

比较这些短语需要进行序列评分。模型必须对第一个 token 评分，将其追加，再对下一个 token 评分，并将这些值组合起来以得到完整短语的分数。长度也会成为比较的一部分。

但单 token 标签可以避免这个问题。每个选项都由同一输出位置上的一个词汇表条目表示，而语义含义仍然出现在提示中：

```plaintext
A = billing questions and payment problems
B = product errors and technical failures
C = login, password, and account access problems
```

模型在处理提示时会读取这些描述。标签只是我们之后检查其 logit 的那个 token。

我们仍然必须验证每个标签都是一个 token。

例如，tokenizer 通常会将前导空格编码为 token 的一部分。因此，字符串 "A" 和 " A" 可能具有不同的 token ID。

![Image](https://pbs.twimg.com/media/HSm8N0ca4AAwWPH?format=jpg&name=large)

聊天模板也可能在答案位置之前立即放置空白或控制 token。

为避免这种情况，请使用模型的聊天模板渲染完整提示。确定在答案位置期望的确切续写内容。将该续写内容发送到 /tokenize。如果它产生的不是单个 token，则拒绝该标签。

此标签映射保留在评分客户端内部。应用程序发送诸如 billing 和 technical\_support 之类的语义选项。它从不发送 token ID，也从不接收 A、B 或 C。这就是公共 API 保持独立于模型标签的含义。

最后，当列出的选项并非穷尽所有可能时，答案列表还需要一个逃生通道。

例如，如果安全事件到达一个仅提供账单、技术支持和账户访问的路由器，受限 softmax 仍会将所有概率质量分配给这三个错误选项。

为避免这种情况，当所有列出的选项都可能不正确时，添加 OTHER 或 ESCALATE。

### 使用 SGLang 实现本地评分端点

本地示例只需要一个推理服务器。SGLang 将 Qwen 加载到 GPU 内存中，并暴露其原生 HTTP 端点。我们的 Python 脚本直接向该服务器发送请求。

完整流程如下：

1. 使用 Qwen 模型启动 SGLang。
2. 将决策编写为带有字母标签的提示词。
3. 让 SGLang 对这些标签进行分词。
4. 向 /v1/score 发送一个请求。
5. 将返回的概率映射回各个选项。

![Image](https://pbs.twimg.com/media/HSm_Ko5a0AAiu2Q?format=jpg&name=large)

#### 步骤 1：使用 SGLang 启动 Qwen

创建一个 Python 环境并安装这里使用的两个包：

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install "sglang[all]==0.5.10.post1" "requests==2.34.2"
```

然后启动模型服务器：

```bash
python -m sglang.launch_server \
  --model-path Qwen/Qwen2.5-0.5B-Instruct \
  --host 127.0.0.1 \
  --port 30000
```

首次启动会从 Hugging Face 下载模型。后续启动会复用本地缓存。加载完成后，Qwen 会保留在内存中，SGLang 会监听端口 30000。

这个 SGLang 进程就是推理服务。在执行下面的客户端时，请保持它运行。

#### 步骤 2：定义选项并构建提示

使用以下代码创建 decide(.)py：

```python
import json
import requests

BASE_URL = "http://127.0.0.1:30000"
MODEL = "Qwen/Qwen2.5-0.5B-Instruct"

choices = {
    "A": "billing and payments",
    "B": "technical support",
    "C": "account access",
}

ticket = "I was charged twice for the same subscription."
choice_lines = "\n".join(
    f"{label} = {meaning}" for label, meaning in choices.items()
)

prompt = f"""Ticket:
{ticket}

Question:
Which category matches the ticket?

Allowed labels:
{choice_lines}

Return only the label.
Label:
"""

print(prompt)
```

该字典记录了每个答案的两种表示形式。

- A 是我们评分的 token。
- 而“billing”是返回给应用程序的含义。
- 在分词、评分和结果映射过程中，它们的顺序必须保持不变。

这是此处生成的确切提示：

```plaintext
Ticket:
I was charged twice for the same subscription.

Question:
Which category matches the ticket?

Allowed labels:
A = billing and payments
B = technical support
C = account access

Return only the label.
Label:
```

提示在“Label:”处结束。

我们希望得到模型对下一个可能出现的 token 的评分。我们并不要求 SGLang 生成那个 token。

#### 第 3 步：解析标签 token ID

将以下代码添加到提示下方：

```python
label_token_ids = []

for label in choices:
    response = requests.post(
        f"{BASE_URL}/tokenize",
        json={
            "model": MODEL,
            "prompt": label,
            "add_special_tokens": False,
        },
        timeout=30,
    )
    response.raise_for_status()
    token_ids = response.json()["tokens"]

    if len(token_ids) != 1:
        raise ValueError(
            f"{label!r} is not a single token: {token_ids}"
        )

    print(f"{label!r} -> {token_ids}")
    label_token_ids.append(token_ids[0])
```

SGLang 的 /tokenize 端点返回由 Qwen 的分词器生成的整数 ID。我们拒绝任何被拆分为多个 token 的标签。评分请求需要为每个答案提供一个词汇表位置。

对于 Qwen/Qwen2.5-0.5B-Instruct，这会打印：

```plaintext
'A' -> [32]
'B' -> [33]
'C' -> [34]
```

每个列表包含一个整数。因此我们知道每个标签占用一个 token。后续的评分请求将读取词汇表中的位置 32、33 和 34。

这一检查也防止我们假设不同模型之间的分词是相同的。一个在 Qwen 中有效的标签，在另一个分词器下可能会被拆分。

#### 步骤 4：向 SGLang 请求这三个概率

接下来添加评分请求：

```python
response = requests.post(
    f"{BASE_URL}/v1/score",
    json={
        "model": MODEL,
        "query": prompt,
        "items": [""],
        "label_token_ids": label_token_ids,
        "apply_softmax": True,
    },
    timeout=120,
)
response.raise_for_status()
score_response = response.json()

print(json.dumps(score_response, indent=2))
scores = score_response["scores"][0]
```

- 查询包含完整的提示词。
- 空的“items”表示我们对其后的位置立即进行评分。
- “label\_token\_ids”告诉 SGLang 从 Qwen 的词汇表大小的输出中读取哪三个条目。
- “apply\_softmax”会将这些条目归一化为概率。

响应只有一个分数列表，因为 items 只包含一个条目。我们针对同一个 Qwen checkpoint 运行了这个完全相同的提示，并得到：

```json
{
  "scores": [
    [
      0.67776233,
      0.310878605,
      0.011359035
    ]
  ]
}
```

这三个位置分别对应 A、B 和 C。在 softmax 之前，选中的 logits 分别为 25.277620、24.498226 和 21.188837。不同硬件和精度设置下可能会出现细微的数值差异。

官方端点参考说明，每个返回的列表都遵循 label\_token\_ids 的顺序。因此，我们的第一个分数属于 A，第二个属于 B，第三个属于 C。

#### 步骤 5：将模型标签转换回决策

使用映射代码完成脚本：

```python
probabilities = {
    choices[label]: float(score)
    for label, score in zip(choices, scores, strict=True)
}

decision = max(probabilities, key=probabilities.get)

print(
    json.dumps(
        {
            "decision": decision,
            "probabilities": probabilities,
        },
        indent=2,
    )
)
```

现在在第二个终端中运行脚本：

```json
// Output after running python decide.py

{
  "decision": "billing and payments",
  "probabilities": {
    "billing and payments": 0.6777623295783997,
    "technical support": 0.31087860465049744,
    "account access": 0.011359035037457943
  }
}
```

SGLang 在 /v1/score 背后执行该计算。一个 SGLang 进程对标签进行分词，运行一次 Qwen，并返回所选概率。

在这种情况下，计费胜出，但概率仅为0.678。如果策略要求达到0.70，则会将此工单发送进行审核，而不是自动执行路由。该阈值应来自对标注示例的评估。

远程 SGLang 路径在一个屏障后启动两个工作进程：

```python
starting_line = threading.Barrier(2)

def worker(lane, runner):
    starting_line.wait()
    for case in cases:
        updates.put(runner(case))

workers = [
    threading.Thread(target=worker, args=("jev", run_jev)),
    threading.Thread(target=worker, args=("llm", run_llm)),
]

for worker_thread in workers:
    worker_thread.start()
```

屏障同时释放两个工作进程。每个通道按顺序处理自己的案例。Jev 风格的工作进程在上一请求完成后立即发送下一个评分请求。标准工作进程对生成请求也采取同样的方式。

### 如何选择正确的方法

评分并不能替代生成，因此 Jev 的方法仅适用于应用程序在推理之前定义了输出空间的情况。

一个兼容的工作负载理想情况下应具有一组有限且有意义的标签。每个标签应映射到一个不同的下游操作。

并且调用方只需一个标签及其概率分布，而不需要新的文本。

结构化输出有所不同，因为它定义了响应的语法，而解码器仍然逐个 token 生成字段名和值。

当这些值无法事先枚举时，应使用结构化生成，因为只有当候选值已知时，评分才会移除解码过程。

此图比较了常规 LLM 解码、结构化输出解码和 Jev 风格评分：

[![视频](https://pbs.twimg.com/amplify_video_thumb/2101447733752283136/img/pX6M6TRDh6PBDGJs.jpg)](https://x.com/_avichawla/status/2101563610644496464)[![视频](https://pbs.twimg.com/amplify_video_thumb/2101447733752283136/img/pX6M6TRDh6PBDGJs.jpg)](https://x.com/_avichawla/status/2101563610644496464)

一种好的做法是根据所需的输出来选择推理路径：

- 在推理前输出内容未知时生成。
- 当输出集已知且选择足够时进行评分。在这种情况下，第一个下一词元向量已经包含排名。返回该排名可以避免调用者不需要的自回归循环。

再次重申，本文项目复现了 Jev 风格的推理机制，但并未复现 Jev 的权重、RLCD 过程或评估栈。

#### Jev 与“类型化决策模型”：综合总结与深入解读

##### 一、综合总结

这五份内容共同描述了一种正在形成的新型 AI 工程范式：

> **不要让大语言模型为每一个小判断都生成文字。**  
> 当候选答案已经确定时，可以让专门的决策模型直接对候选项打分，再由普通代码执行结果。

Jev 是这一范式中较具代表性的闭源服务。它不是通用聊天机器人，也不是为了写文章、生成代码或输出长篇推理，而是读取当前状态，在开发者预先定义的候选项中完成：

- 分类
- 路由
- 是非判断
- 评分
- 排序
- 审批或升级
- 下一步动作选择

它返回的核心不是解释文本，而是：

1. 被选中的答案；
2. 所有候选答案的相对概率；
3. 可供应用程序制定阈值策略的置信信号。

围绕这一思路，资料中出现了三类实现：

| 路线 | 代表 | 特点 |
|---|---|---|
| 专用托管决策模型 | TypeSafe Jev | 闭源 API，专门训练和校准，使用简单，公开案例表现较强 |
| 本地训练的专用模型 | Bespoke Nimble | 基于 Qwen3.5-9B 微调，开放训练数据、训练方法和本地部署代码 |
| 通用模型直接读取 logits | SemIf、SGLang 教程 | 不重新训练，直接读取开放模型对候选 token 的分数，部署灵活但效果和校准依赖基础模型 |

这些项目虽然实现方式不同，但核心接口基本一致：

```text
当前状态 + 问题 + 候选答案
            ↓
       决策模型评分
            ↓
选中答案 + 候选项概率分布
            ↓
代码根据阈值决定执行、等待、重试或转人工
```

它们共同提出了一种更合理的智能体分工：

- **生成模型负责研究、规划、写作和解释；**
- **决策模型负责分类、路由、评分和审批；**
- **普通代码负责执行、限额、持久化和结果验证。**

真正重要的并不是“7 秒找到航班”或“几美分分类上千篇论文”，而是认识到：

> 智能体内部大量昂贵的 LLM 调用，本质上并不需要生成，只需要在有限选项之间做判断。

---

#### 二、五份内容分别贡献了什么

##### 1. Jev 工程路线图：重点是工作流架构

第一份内容提供的是一套相对完整的 Jev 接入方法。

其核心建议包括：

1. 找出智能体中重复出现的小判断；
2. 将判断改写成固定候选项；
3. 在 Playground 中验证决策；
4. 通过 API 接入；
5. 把决策保存成可审计的交接文件；
6. 根据当前系统状态动态重建候选菜单；
7. 对互不依赖的问题并行评分；
8. 设置预算、动作次数和人工审核边界；
9. 单独验证动作是否真正完成；
10. 按“每个完成任务的总成本”评估收益。

其中最重要的工程思想不是 API 调用本身，而是：

> **决策、执行和完成验证必须分离。**

例如，Jev 判断“应该写作”，并不代表写作文件已经成功保存；判断“任务完成”，也不代表消息已经真正发送。最终状态仍应由代码或独立检查器确认。

---

##### 2. Nimble：展示如何训练一个开放的 Jev 类模型

Nimble 的价值不只是“有一个本地 9B 模型”，而是公开了这类决策模型的构建方法。

它接收：

- 一段文本上下文；
- 一个扁平 schema；
- 若干枚举或布尔字段。

然后直接返回：

- 每个字段的类型化答案；
- 所有候选答案的 logits；
- 经过 softmax 后的候选概率。

Nimble 不生成解释，也不需要解析 JSON 文本，而是直接围绕候选 token 训练。

它的主要创新是**对比式数据整理**：

- 构造两个几乎相同的案例；
- 只改变少量关键事实；
- 确保这个变化足以改变正确标签；
- 检查其他文本没有泄露答案；
- 用代码根据已验证的事实生成标签。

这种训练方式迫使模型学习：

> 到底哪一条证据应该改变决策，而不是依赖表面关键词或数据集偏差。

在资料所列的狭窄合成留出集上：

- 基础 Qwen3.5-9B：66.36%
- 未微调的 Qwen 27B：84.88%
- Bespoke-Nimble-9B：90.12%
- Jev 1.13.0：93.21%

这说明专门训练确实可能让较小模型超过更大的通用模型。但该结果只来自 324 个合成样本、162 个对比样本对和少数来源家族，不能直接外推为通用能力排名。

---

##### 3. SGLang 教程：解释最基础的评分机制

第三份内容解释了如何不训练新模型，直接将通用因果 LLM 变成一个本地候选评分器。

基本过程如下：

```text
A = 账单问题
B = 技术支持
C = 账户访问

问题：这张工单应该路由到哪里？
只返回标签。
标签：
```

模型处理完提示词后，会为“下一个 token”生成整个词表的 logits。评分器只读取：

- A 的 logit
- B 的 logit
- C 的 logit

然后只在这三个值之间做 softmax：

\[
P_i = \frac{e^{z_i}}{\sum_{j \in \{A,B,C\}} e^{z_j}}
\]

最终可能得到：

```text
A / 账单问题：0.68
B / 技术支持：0.31
C / 账户访问：0.01
```

整个过程没有生成句子，也没有逐 token 生成 JSON。

这说明 Jev 风格推理的一个基础版本，并不神秘：

> 它可以从模型已经计算出的下一 token 分布中，直接读取有限候选项的相对偏好。

但这只复现了**推理路径**，并没有复现 Jev 的专门训练、数据构造、概率校准和评估系统。

---

##### 4. SemIf：验证“冻结模型直接评分”的实用性

SemIf 采用冻结的开放模型，不重新训练，直接读取候选项 logits，并支持：

- CUDA；
- Apple Silicon MLX；
- 浏览器 WebGPU；
- 状态前缀复用；
- 多个问题共享一次状态预填充；
- 并行评估多个后缀问题。

其结果展示了两点。

###### 第一，直接读 logits 确实比生成 JSON 快

在相同的 Qwen3.5-4B、相同状态和 21 个二元问题上：

| 输出路径 | 时间 | 输出 token |
|---|---:|---:|
| 直接读取类型化 logits | 1.023 秒 | 0 |
| 生成紧凑 JSON 数组 | 5.332 秒 | 111 |

直接评分约快 5.21 倍。

###### 第二，推理优化可能改变结果

在共享前缀、并行后缀等优化下，吞吐量可以明显提高，但 BF16 执行方式的变化也让少量 argmax 结果发生改变。

这提醒我们：

> 缓存复用、量化、精度和并行实现，不只是性能配置，也可能影响决策一致性。

SemIf 的结果还表明，开放 4B 模型可以接近 Jev 在某些公开子集上的结果，但其“TypeSafe 子集一致性”是对已发布结果的一致率，不等于独立真实世界准确率。

##### 5. 视频案例：展示面向产品的组合方式

第五份内容用三个应用演示 Jev 的定位：

###### 语音控制浏览器

流程大致是：

1. 语音转文字；
2. 浏览器提取当前页面上的可操作元素；
3. Jev 判断用户意图、目标元素和动作类型；
4. 普通代码执行点击、滚动、返回等操作；
5. 高风险操作继续检查或等待确认。

这里的关键是每次页面变化后，都重新获取当前可用控件。否则模型可能在“昨天的菜单”中选择已经不存在的按钮。

###### AI 记忆检索

Jev 不直接回答记忆问题，而是用于判断：

- 哪些文件或片段相关；
- 某个记忆是否存在；
- 应该读取哪些内容；
- 新记忆应保存到哪里；
- 是否需要调用生成模型进行最终回答。

因此，它更像检索前的语义过滤器，而不是知识库回答器。

###### YouTube 选题评分

生成模型先产生标题和缩略图创意，Jev 再负责：

- 对候选创意打分；
- 排序；
- 判断是否符合某些模式；
- 选择最终候选。

这体现了典型组合：

```text
LLM 负责发散生成
        ↓
Jev 负责候选评估
        ↓
代码负责排序、阈值和展示
```

不过，内容表现预测本身极难，仅靠语义决策模型无法证明真实因果关系，因此这种评分更适合作为辅助筛选，而不是可靠的流量预测器。

#### 三、深入浅出理解：它本质上是什么

##### 1. 它像“可以理解自然语言的 if 语句”

传统代码可以处理精确条件：

```python
if amount > 10000:
    require_review = True
```

但很难直接处理语义条件：

```text
这封邮件是否表现出客户即将流失？
这份证据是否直接支持结论？
这个任务是否需要更强的推理模型？
用户是在下命令，还是只是在与旁人交谈？
```

通用 LLM 可以回答这些问题，但通常会写出一段文字：

```text
根据客户表达的不满和取消意图，我认为流失风险较高……
```

应用程序最终还是要把这段话解析回：

```python
high_churn_risk = True
```

类型化决策模型直接跳过中间文本：

```json
{
  "high_churn_risk": true,
  "probabilities": {
    "true": 0.92,
    "false": 0.08
  }
}
```

因此可以把它理解成：

> **传统 if 语句处理精确条件，Jev 类模型处理语义条件。**

---

##### 2. 为什么它可能更快、更便宜

普通生成模型的工作方式是：

```text
读取上下文
→ 预测第一个 token
→ 把 token 加回上下文
→ 再预测下一个 token
→ 重复几十次甚至几百次
```

而候选评分的方式是：

```text
读取上下文
→ 计算候选标签的分数
→ 结束
```

假设生成一个 JSON 需要 30 个 token，那么模型要连续运行多个解码步骤。候选评分通常只需要一次前向计算，之后从结果向量中读取几个位置。

因此，理论上它可以节省：

- 输出 token；
- 自回归解码时间；
- JSON 解析和修复；
- 格式不合法导致的重试；
- 不必要的解释文本；
- 部分重复模型调用。

但要注意，速度提升幅度取决于：

- 输入上下文长度；
- 模型大小；
- 硬件；
- 服务排队；
- 候选数量；
- 是否共享前缀缓存；
- 与什么生成基线比较。

“20～200 倍更快”或“40～400 倍更便宜”更像特定场景下的宣传性数字，不能视为所有工作负载的普遍结论。

---

##### 3. 它和结构化输出不是同一件事

这是几份材料中最容易混淆的一点。

###### 结构化输出

要求模型生成：

```json
{
  "team": "billing"
}
```

它保证语法符合 schema，但底层通常仍要逐 token 生成：

1. `{`
2. `"team"`
3. `:`
4. `"billing"`
5. `}`

它解决的是：

> 输出格式是否有效？

###### 固定候选评分

模型不生成 JSON，而是直接比较：

```text
billing
technical_support
account_access
```

返回：

```json
{
  "billing": 0.91,
  "technical_support": 0.06,
  "account_access": 0.03
}
```

它解决的是：

> 在已知候选项中，模型更偏向哪一个？

###### 如何选择

| 需求 | 推荐方式 |
|---|---|
| 答案无法提前枚举 | 普通生成 |
| 要生成文本、代码或解释 | 普通生成 |
| 内容未知，但必须符合固定 JSON 结构 | 结构化输出 |
| 候选答案已知，只需选择或评分 | 固定候选评分 |
| 高风险决策 | 评分 + 规则 + 人工审核，不应只看 argmax |

---

#### 四、概率最容易被误解

假设三个候选项的结果是：

```text
账单：0.91
技术：0.06
账户：0.03
```

这只能表示：

> 在被强制限定为这三个选项时，模型将 91% 的相对概率质量分给了“账单”。

它不表示：

> 这个答案在真实世界中有 91% 的概率正确。

原因是 softmax 会把候选项概率强制归一化为 1。即使三个选项都错了，它仍会选一个。

例如，真实输入是安全事件，但候选项只有：

- 账单
- 技术支持
- 账户访问

模型依然必须把 100% 概率分配给这三个错误选项。

因此，必须加入退出选项：

- `OTHER`
- `NO_MATCH`
- `UNKNOWN`
- `ESCALATE`
- `REVIEW`

同时，不应只使用“最高概率超过 0.8”这一条规则，还可以加入领先幅度：

```python
auto_execute = (
    top_probability >= 0.80
    and top_probability - second_probability >= 0.20
)
```

这可以区分：

```text
情况一：0.91 / 0.06 / 0.03
情况二：0.46 / 0.44 / 0.10
```

虽然两者 argmax 都相同，但第二种情况明显更接近平局，应进入人工审核。

最终阈值必须通过业务自身的标注数据确定，而不能直接照搬 0.7、0.8 或 0.85。

---

#### 五、真正可靠的智能体架构

综合所有内容，一个较合理的架构如下：

```text
用户请求或环境状态
        ↓
状态整理器
- 分离原始请求、已完成工作和证据
- 读取当前可用工具与 worker
- 构建当前候选菜单
        ↓
类型化决策层
- Choice：选择下一步
- Boolean/Noul：判断条件
- Score：按等级评分
        ↓
确定性策略代码
- 概率阈值
- 第一名与第二名的差值
- 高风险动作限制
- 调用次数和预算限制
        ↓
执行层
- 浏览器
- 研究代理
- 写作代理
- 邮件或数据库工具
        ↓
独立完成验证
- 文件是否真的存在
- 消息是否真的发送
- 浏览器是否真的到达目标
- 数据库是否真的更新
        ↓
保存状态与审计记录
        ↓
进入下一轮或人工审核
```

##### 为什么候选菜单必须动态刷新

浏览器每点击一次，页面可用操作都会变化；任务系统中的 worker 也可能忙碌、失效或新增。

因此，候选项应该来自当前状态：

```text
当前可用 worker：
- Researcher
- Writer
- Reviewer
```

而不能写死成：

```text
所有理论上存在的 worker：
- Researcher
- Writer
- Reviewer
- Publisher
- Translator
```

否则模型可能选择一个当前不存在、不可用或不应执行的动作。

候选项本身也是安全边界：

> 不允许模型选择的动作，就不要放进候选菜单。

#### 六、适合与不适合的使用场景

##### 适合

###### 1. 智能体任务路由

```text
研究 / 写作 / 审核 / 等待 / 升级
```

###### 2. 浏览器操作选择

```text
点击 / 输入 / 滚动 / 返回 / 完成 / 请求人工确认
```

###### 3. 邮件分拣

```text
回复 / 调研 / 等待 / 忽略 / 人工审核
```

###### 4. 模型路由

```text
便宜模型 / 强推理模型 / 代码模型 / 人工处理
```

###### 5. 内容和证据筛选

```text
无关 / 部分相关 / 直接相关
```

###### 6. RAG 或记忆系统过滤

```text
是否需要读取这个片段？
哪个文件最可能包含答案？
现有记忆是否足以回答？
```

###### 7. 工具调用压缩

对历史工具调用逐项评分，只保留与当前任务有关的内容。

###### 8. 风险闸门

```text
允许执行 / 要求确认 / 禁止执行
```

但高风险动作不能仅依赖模型概率，还要配合硬规则。

---

##### 不适合

###### 1. 写文章、邮件或代码

候选评分不会创造新文本。

###### 2. 开放式问题

例如：

```text
请设计一个新的商业策略。
```

答案空间无法提前枚举，应使用生成模型。

###### 3. 候选项极多且变化无规律

候选过多会增加提示长度和混淆程度。必要时应先检索缩小范围，再评分。

###### 4. 强依赖复杂多步推理的任务

如果判断需要数学证明、长链条分析或外部工具验证，单步评分可能不可靠。

###### 5. 直接执行不可逆动作

支付、删除、发布、转账、修改权限等，应有硬规则和人工审批。

---

#### 七、Jev、Nimble、SemIf 与通用评分方案的差异

| 维度 | Jev | Nimble | SemIf | SGLang 通用评分 |
|---|---|---|---|---|
| 形态 | 托管闭源服务 | 开源本地 9B 模型与训练配方 | 开源推理与评估系统 | 通用本地实现教程 |
| 是否专门训练 | 是，但细节未完全公开 | 是，LoRA 微调 | 否，使用冻结开放模型 | 否 |
| 是否本地运行 | 否，以 API 为主 | 是 | 是 | 是 |
| 输出 | Choice、Score、Noul 等类型化结果 | 扁平 enum/boolean | 类型化候选概率 | 候选 token 概率 |
| 解释文本 | 不生成 | 不生成 | 不生成 | 不生成 |
| 概率校准 | 声称包含相关训练与系统能力 | 通过对比数据改善，但仍需业务验证 | 依赖基础模型与业务校准 | 依赖基础模型与业务校准 |
| 隐私控制 | 数据发送到外部服务 | 本地可控 | 本地可控 | 本地可控 |
| 部署门槛 | 较低 | 较高，需要较大内存或 GPU | 中等 | 中等 |
| 最适合 | 快速产品集成 | 研究、私有部署与再训练 | 验证开放模型直接评分 | 理解原理和搭建轻量原型 |

##### 简单选择建议

- 想最快接入并验证业务价值：优先尝试 Jev。
- 数据不能离开本地：考虑 Nimble、SemIf 或 SGLang。
- 希望研究训练方法和自定义模型：优先看 Nimble。
- 只想验证“直接读 logits 是否有用”：SemIf 或 SGLang 更直接。
- 对质量要求高：必须用自己的标注集同时评估多个方案。

#### 八、如何正确解读资料中的基准数字

这些材料中的数字有参考价值，但不能简单横向拼成统一排行榜。

##### 1. Nimble 的 90.12% 与 Jev 的 93.21%

这是在同一批 324 个合成留出样本上的参考标签一致率，因此具有一定可比性。

但局限包括：

- 样本量较小；
- 数据来源范围狭窄；
- 参考标签是合成的；
- 只覆盖六个来源家族；
- 与真实业务分布可能差异很大。

它支持的结论是：

> 专门微调的 9B 决策模型，在该测试集上明显优于未微调 9B，并接近 Jev。

它不支持：

> Nimble 在所有业务上都有 90% 准确率。

---

##### 2. SemIf 的 0.845 与 Jev 的 0.883

这里主要是对 TypeSafe 公开结果子集的一致性比较，而且只覆盖能够对齐的 102 行。

这不能直接等同于真实标签准确率，也不能据此断言两者只差 3.8 个百分点。

---

##### 3. 7 秒找航班、0.0039 美元

该案例说明浏览器智能体可以通过决策模型减少动作选择成本和解码延迟。

但资料同时指出：

- 计时从初始页面观察后开始；
- 不包括运行后的全新验证；
- 结果是“找到航班”，不是“预订机票”；
- 浏览器基础设施成本不一定包含在模型费用中；
- 特定页面和任务不代表普遍性能。

因此应把它看成架构演示，而不是标准服务等级承诺。

---

##### 4. 分类 1,018 篇论文只花 0.08 美元

这里的 0.08 美元只对应 Jev 分类环节。前置摘要本身花费约 3.99 美元。

这正好说明评估系统成本时，不能只看最便宜的那个模型调用，而要看完整流水线：

\[
总成本 =
数据准备 + 检索 + 摘要 + 决策 + 执行 + 重试 + 人工审核
\]

真正合理的指标是：

> **每个正确完成任务的总成本。**

如果廉价路由器把任务送错方向，后续昂贵模型产生的大量无效工作，可能远高于路由器节省的费用。

#### 九、从零落地的推荐路线

##### 第一步：选择一个高频、低风险、候选项有限的判断

例如：

```text
工单路由：账单 / 技术 / 账户 / 其他 / 人工审核
```

不要一开始就做自动付款、自动发布或复杂多智能体自治。

---

##### 第二步：建立标注集

至少收集真实历史案例，并由人给出预期答案。

每条样本建议包含：

```json
{
  "state": "客户表示同一订阅被扣款两次",
  "expected": "billing"
}
```

同时记录：

- 是否允许自动执行；
- 错误路由的代价；
- 是否存在多个合理答案；
- 哪些案例必须升级人工。

---

##### 第三步：定义清楚的候选项

不好的定义：

```text
A：研究
B：写作
C：审核
```

更好的定义：

```text
research：
当前证据不足以完成目标，需要继续收集来源。

write：
已有足够证据，可以开始起草，但不得发布。

review：
目标不明确、任务越界、出现冲突，或工作已经完成。
```

模型通常看不到字段名中隐含的意义，因此指令和候选项描述必须完整。

---

##### 第四步：加入退出选项

至少加入一种：

```text
other / no_match / uncertain / review
```

否则模型会在错误候选项中被迫选择。

---

##### 第五步：比较三种基线

在相同数据上比较：

1. 普通 LLM 生成；
2. 结构化输出；
3. 候选评分。

评估指标至少包括：

- 准确率；
- 高风险类别召回率；
- 自动处理覆盖率；
- 误执行率；
- p50、p95 延迟；
- 单任务成本；
- 无效格式比例；
- 进入人工审核的比例。

---

##### 第六步：确定业务阈值

不要把概率直接当准确率，应使用验证集寻找阈值。

例如：

```python
if top_prob >= 0.85 and margin >= 0.25:
    auto_route()
else:
    send_to_review()
```

对高风险类别还可以设置更严格策略：

```python
if decision == "publish":
    always_require_human_approval()
```

---

##### 第七步：将判断和动作彻底分开

评分器只返回：

```json
{
  "choice": "research",
  "probabilities": {
    "research": 0.91,
    "write": 0.06,
    "review": 0.03
  }
}
```

普通代码负责：

- 写入任务队列；
- 防止重复消费；
- 调用具体 worker；
- 记录成本；
- 保存执行状态；
- 检查结果；
- 决定是否继续循环。

---

##### 第八步：加入生产级保护

至少需要：

- 最大动作次数；
- 最大调用次数；
- 最大支出；
- 超时；
- 重试与指数退避；
- 幂等键；
- 状态持久化；
- 人工审核入口；
- 审计日志；
- 独立完成检查；
- 发布、付款、删除等不可逆动作的审批。

---

##### 第九步：优化真正的瓶颈

优先检查：

- 是否重复读取相同页面或状态；
- 是否重复调用同一个工具；
- 多个问题能否共享一次上下文；
- 互不依赖的问题能否并行；
- 能否复用 KV cache；
- 是否把大量无关历史传入模型；
- 候选菜单是否过大或已过时。

很多情况下，减少重复工具调用比换更快的模型收益更大。

---

#### 十、需要保持警惕的几个误区

##### 误区一：模型不生成文字，所以它“不需要理解”

错误。它仍然需要理解状态、问题和候选项之间的语义关系。只是输出方式从生成文本变成了比较候选项。

##### 误区二：概率高就代表正确率高

错误。候选概率是条件化后的相对偏好，必须通过业务标注数据校准。

##### 误区三：加上固定候选项就一定比普通 LLM 准

不一定。速度通常更有优势，但准确率取决于：

- 基础模型；
- 专门训练；
- 提示设计；
- 候选定义；
- 数据领域；
- 上下文长度；
- 校准方法。

##### 误区四：结构化输出等于 Jev 风格评分

不等于。结构化输出依然是在生成，只是语法受到约束。

##### 误区五：一个决策模型可以替代整个智能体

不能。它不会研究、写作、操作工具或验证结果。它只是智能体中的决策层。

##### 误区六：开源方案已经完整复现 Jev

没有。SemIf 和 SGLang 主要复现推理接口；Nimble进一步公开了训练方法，但仍不等同于 Jev 的模型、数据、校准和服务系统。

##### 误区七：并行字段可以相互依赖

通常不能。Nimble、Jev 类并行问题往往分别读取同一状态，但一个字段看不到另一个字段的答案。依赖关系应由应用代码分阶段处理。

---

#### 十一、最终结论

这些内容共同指向的并不是“又一个更快的聊天机器人”，而是一层新的 AI 基础设施：

> **让模型把非结构化信息转换成有限、可执行、带概率的类型化决策。**

其最合理的角色不是替代 LLM，而是重构智能体内部的职责：

```text
LLM：产生新内容、研究、规划、解释
决策模型：选择、分类、评分、路由、审批
代码：执行、限额、持久化、校验
人工：处理高风险、模糊和异常情况
```

Jev 展示了专用托管模型的产品形态；Nimble展示了如何通过对比数据和专门训练构建本地决策模型；SemIf 和 SGLang 则证明，即使不重新训练，也可以从开放模型的 logits 中构建一个基础版本。

对实际开发者而言，最值得采纳的原则是：

1. 不要把所有问题都交给生成模型；
2. 输出空间已知时，优先考虑评分而不是生成；
3. 概率必须经过自身数据验证；
4. 候选项应根据当前状态动态构建；
5. 决策、执行和验证必须彼此分离；
6. 以完整任务的正确率、成本和延迟衡量价值；
7. 从一个重复、低风险、候选项明确的决策开始。

一句话概括：

> **让大模型负责“创造答案”，让决策模型负责“从已知答案中选择”，让代码负责“可靠地把选择变成现实”。**

## 深度解读-口播（1）

### 2026-09-30 12:17:27

很多人工智能代理的成本，并不是花在真正的研究和写作上，而是花在反复判断“下一步做什么”。Jev 提出的思路，是把这些小判断单独交给一个快速决策模型，而不是每次都让大语言模型生成一段答案。

比如，你让一个代理研究三款人工智能工具，再起草明天的简报。收集资料、分析内容、写出段落，确实需要生成能力。但“资料够不够”“接下来交给研究员还是写作者”“草稿是否该进入审核”，往往只需要在几个已知选项中做选择。

Jev 是 TypeSafe AI 开发的决策模型。你提供当前状态、要判断的问题，以及预先定义的答案。它返回选择结果和概率信息，不负责写简报、生成代码，也不会用长篇文字解释推理过程。

这里所谓的“类型化”，就是输出形式事先确定。可以是选一个选项，可以是按量表评分，也可以是回答是或否。软件收到结果后，就能按明确规则继续运行。

所以，这种设计不是让一个模型包办所有事情，而是重新分工：生成模型负责创造内容，决策模型负责选择方向，普通代码负责执行，以及严格遵守操作次数、支出和权限限制。

理解这种分工，再看它为什么可能更快。

假设一张客服工单写着：“同一个订阅，我被扣了两次费用。”系统已经知道，工单只能去账单、技术支持或者账户访问这几个队列。

普通语言模型可能先生成一句话：“这属于账单问题。”即使要求它输出规范的数据对象，底层通常仍然要逐个生成文本片段，程序再从中提取分类。

固定选项评分则走另一条路。材料中的本地实现，会给三个选项分别分配一个单独的标签。模型读完工单后，系统直接读取下一输出位置上，这几个标签的原始分数，再转换成候选选项之间的概率分布。不必把答案写成句子，也不必生成完整的数据对象。

可以把它想成：我们只需要模型在菜单上指一下，不需要它再写一段点餐说明。

不过，菜单必须提前存在。如果要写一封邮件、创造一个标题，或者提取事先无法枚举的内容，仍然需要生成模型。省掉的是不必要的输出过程，不是理解输入所需的全部计算。

浏览器代理的案例，最能说明这种设计怎么落地。

Browser Use 将 Jev 用于选择下一步操作，以及操作对应的页面元素。每次点击之后，网页上的按钮、链接和输入框都可能改变。因此，系统会重新整理当前可用的操作，再让 Jev 选择。需要填写文本时，则交给一个小型语言模型。

这条经验很重要：决策模型不能一直拿着昨天的菜单做今天的选择。任务状态变化之后，可用选项也要更新。路由任务时，应提供当前真正可用的工作者；挑选资料时，应提供当前实际存在的来源。

开发者报告，这个浏览器演示用大约七秒找到了航班结果，报告费用是零点零零三九美元。但这两个数字都有边界。费用没有包含浏览器成本；计时从首次页面观察之后开始，也没有包含运行后的独立核实。它找到的是航班结果，不是完成机票预订。

论文分类的案例，也体现了分工的价值。开发者先用另一个模型生成论文摘要，再让 Jev 从二十四个主题中分类。一千零一十八篇论文的分类费用，报告为零点零八美元；前面的摘要生成，则花了三点九九美元。

这说明，便宜的是其中一个决策环节，不能把它当成整个工作流的总成本。真正应该衡量的，是完成一个正确任务，总共花了多少钱、用了多久。

同样的思路，也开始出现本地开源实现。

Nimble 是其中一个项目。它受 Jev 启发，但并不是从 Jev 蒸馏出来的模型。它基于一个九十亿参数的开放模型，使用两千六百七十六个整理过的示例进行训练，可以在兼容的苹果芯片电脑或英伟达显卡上本地运行。

它的训练方法，有一个值得保留的细节，叫“对比式数据整理”。

例如，规则规定，只有某位指定人员能批准一个账户的退款。团队制作两个几乎相同的案例，只改变授权记录中的一个关键事实，让正确答案从“已授权”变成“未授权”。其他背景和规则保持不变。

这种训练要教给模型的，不是记住常见措辞，而是识别：究竟哪条证据发生变化，才应该让决策翻转。

在项目公布的三百二十四个留出样本上，Nimble 与参考标签的一致率约为百分之九十，Jev 约为百分之九十三。不过，这些标签是合成的，样本来自少量来源，而且成对案例非常接近。因此，这只能说明模型在这组狭窄测试中的表现，不能直接推出它在所有实际业务中都有同样的准确率。

另一些本地教程甚至不重新训练模型，只用现有开放模型读取固定选项的分数。但这些教程也明确区分：复现评分路径，不等于复现 Jev 的训练、校准和完整系统。

最后，有一个比速度更重要的问题：如何让这些决策可靠地进入工作流。

模型给账单选项零点九一的概率，不代表它在同类任务中有百分之九十一的正确率。这个数字首先表达的是，在你提供的候选答案之间，模型有多偏向账单。自动执行的阈值，需要用自己业务里的标注案例测试。

而且，如果三个选项全都不合适，模型仍可能从中选出一个。只要存在这种可能，就应加入“没有匹配项”或者“转人工审核”的出口。

多个判断如果都能读取同一份状态，可以一起评估。但如果后一个判断依赖最新搜索结果，就必须先搜索。并行问题不会自动知道彼此的答案。

完成检查也不能交给模型一句“做完了”就结束。保存草稿，要检查文件是否存在；发送消息，要检查实际发送结果。发布、购买、删除等高影响操作，还应有独立的权限检查。

最值得记住的，是这套分工：需要创造内容时生成，答案已经确定时评分，执行和硬性约束交给代码。先替换一个反复出现的小决策，再同时测量速度、准确性和完整任务成本。Jev 的价值，不只是某次演示有多快，而是提醒我们：很多昂贵的模型调用，从一开始就不需要生成文字。
