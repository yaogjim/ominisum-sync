### We built RLM for coding. And it F\*cking rocks. Swarm native agents are here to stay.

Today we are releasing slate.

Slate is the \*first\* frontier agent in the wild to directly use a code environment for swarm orchestration.

Slate can programmatically orchestrate and solve tasks, running a \*massive\* amount of what we call threads (subagents).

At

[@0xrandomlabs](https://x.com/@0xrandomlabs), our goal is to identify general mechanisms that can be used for general agents.

The version of Slate we are releasing today is a strong step towards it. (Our technical report is on our blog at randomlabs\[.\]ai/blog/slate )

With slate, you can have Sonnet, Opus, GPT 5.4 etc. orchestrate Codex 5.3, GLM 5, sonnet, haiku, etc.

Slate automatically selects the right model for the job. Meaning you’re spending as little as you need for completeness while getting the advantages of each model. GLM for example is one of our favorites, and is incredible for agentic search.

Have you ever felt like you wanted to talk with claude but code with codex? Yeah, us too. Slate just does it. No overhead. No weird integration stuff. No wacky skills.

Slate is swarm native. The only agent of its kind that functions like this. It’s not a system that uses message passing between subagents. It’s more of a hive mind and can synchronize many many parallel threads.

It might \*sound\* expensive, but due to some novel context engineering, it's actually not that expensive. Architecturally it also maximizes caching.

#### Now, what did we mean by “RLM for coding”?

RLM was built by

[@a1zhang](https://x.com/@a1zhang) and

[@lateinteraction](https://x.com/@lateinteraction)

(Huge shoutout! These guys have been in the game forever)

Well basically, RLM functions on two principles. The first is that the reference semantics of a REPL allow the agent to decompose the work into operations that store values \*in\* the references. The second is that the agent is able to orchestrate operations at a higher level through the python repl it has access to. In other words, it knows the operations it needs to perform and can actually think about the execution graph that it is executing INSTEAD of performing the operations.

![Image](https://pbs.twimg.com/media/HDJtjxLbwAAkLfZ?format=jpg&name=large)

Overall the semantics around task decomposition are sound.

Use a REPL to decompose the task into a known set of operations allowing the model to think strategically about the task and not be overwhelmed by context. The models right now have a hard time tracking more complex variables across execution steps, but they will eventually get there.

A very very old precursor to this was the CodeAct paper by

[@gneubig](https://x.com/@gneubig) and team, alongside the voyager paper by

[@DrJimFan](https://x.com/@DrJimFan)

and team

We hilariously came to the same conclusions independent of the RLM team, but nonetheless all three of these teams touched on the core ideas implicitly .

We define two new terms for understanding agents as well:

- Knowledge overhang, the knowledge of how to do tasks that the model doesn’t actually use while performing tasks
- Expressivity, the interplay between how expressive an interface is and the model’s bias to use that expressiveness

We explore both of these in our technical report that you can find on our blog at randomlabs\[.\]ai/blog/slate

Despite having slate internally, I (the author) mistakenly thought RLM wasn’t actually similar and intentionally didn’t take inspiration. And yet we came to the same conclusions which suggests that the primitives are actually important.

The core difference is that Slate is 1) stable over long horizon implementation tasks, and 2) can handle a mutated/changing environment. This allows it to actually parallelize work that matters to the people we are building for:

Software engineers and engineering teams

One of the best things about how slate works is that it accesses the knowledge the model has about strategy directly and separately from accessing the model’s tactical knowledge.

![Image](https://pbs.twimg.com/media/HDJuSqxbQAAk2qr?format=jpg&name=large)

Because it orchestrates the swarm using a typescript DSL, Slate is able to actually think and “program in action space”. (Again, we call this knowledge overhang, you can read about it in our technical report)

We do this by introducing a concept called threads.

#### What is a thread?

The general idea of a thread is that rather than isolating subagent context, we genuinely want to share it with the main orchestration thread.

Notably there are a few teams that have come across something similar to the benefits of threads.

[@cognition](https://x.com/@cognition),

[@fundamental](https://x.com/@fundamental)

, and

[@ManusAI](https://x.com/@ManusAI)

all operate on the same principles of think at a high level and delegate at a lower level, compressing the lower level context to something that is understandable by the agent doing the strategizing.

We explore the tradeoffs each of these teams makes in our technical report on our blog.

Due to the nature of our threading engine, we are able to maximize caching through subthread reuse.

These subthreads represent work streams that can be added to and composed to form more complex working behaviors.

Because we delegate simple tactical actions to threads, one at a time, it gives us an almost perfect boundary over which we can compress the context. This in turn has led us to an \*actually\* tractable way to create episodic memory.

Slate has episodic memory that actually makes sense. The system retains only the tool calls that contribute to its success. We also maintain the same rolling compression system from slate V0 that let it run single sessions for as long as 2 days as reported by our customers.

One funny coincidence is that Slate’s thread architecture maps directly to

[@karpathy](https://x.com/@karpathy)’s LLM OS where each thread has its own "ram" and the main thread can delegate to other threads directly. This work provides a clear primitive for scaling. Conceptually inspired by the BEAM vm, we originally called threads “actors”, but found that the model understands threads better.

![Image](https://pbs.twimg.com/media/HDJumFpacAA0j5Y?format=png&name=large)

Slate currently borrows heavily from

[@opencode](https://x.com/@opencode) in its application architecture, and would not have been possible in its current form if not for the

[@opencode](https://x.com/@opencode)

team (Shoutout

[@thdxr](https://x.com/@thdxr)

especially for being the goat!). Our client server architecture is directly based on the opencode architecture which will enable many \*many\* cool applications in the future.

It’s a miracle that this works at all, but we believe we’ve solved some of the core limitations of agents.

Now that the compaction and orchestration problems are solved, the next challenge to tackle is long term memory.

## 结构化（1）

### 2026-03-15 06:40:26

**主旨概括：**  
这篇文章主要介绍了 Random Labs 发布的新代理系统**Slate**：它把 “代码环境 + 多线程子代理协作” 结合起来，让 AI 更像一个能分工、能并行、能长期执行的软件工程助手。作者认为，这种 “swarm native（原生群体协作）” 架构不仅适合写代码，而且可能是通用智能代理的重要方向。

---

##### 1. Slate 是什么：一个能直接在代码环境中调度 “代理群” 的系统
**关键点：**
- Random Labs 发布了**Slate**。
- 作者称它是**首个**在真实环境中，**直接利用代码环境进行 swarm orchestration（群体编排）**的前沿代理。
- 它可以为任务自动创建并调度大量**threads（线程 / 子代理）**来协作完成工作。
- 目标不是只做一个写代码工具，而是探索**通用代理的通用机制**。

**通俗理解：**  
以前很多 AI 代理更像 “单兵作战”，Slate 更像一个 “项目经理 + 多个执行成员” 的团队系统。

---

##### 2. Slate 的实际能力：自动选模型、兼顾效果和成本
**关键点：**
- Slate 可以让不同大模型互相配合：
  - 例如让**Sonnet、Opus、GPT 5.4**去编排**Codex 5.3、GLM 5、Sonnet、Haiku**等模型。
- 它会**自动选择最适合当前任务的模型**。
- 目标是：
  - **尽量省钱**
  - 同时利用不同模型各自的长处
- 文中举例：
  - **GLM**被认为特别适合**agentic search（代理式搜索）**
- 作者用一句非常直白的话总结体验：
  - 想 “**和 Claude 聊天，但用 Codex 写代码**”？Slate 可以直接做到，而且**不需要复杂集成**。

**例子：**  
比如一个任务需要：
- 先理解需求 → 用擅长推理 / 对话的模型  
- 再改代码 → 用擅长编码的模型  
- 再全库搜索问题 → 用擅长搜索的模型  
Slate 会自动搭配，而不是让用户手动切换。

---

##### 3. 和传统多代理系统的区别：不是消息传递，而更像 “蜂群大脑”
**关键点：**
- 作者强调，Slate 是**swarm native**，不是普通的 “多个 agent 发消息” 系统。
- 它更像一个**hive mind（蜂群式共享思维）**，可以同步大量并行线程。
- 表面上看这种系统可能很贵，但作者说：
  - 通过新的**context engineering（上下文工程）**
  - 以及架构上对**缓存（caching）**的优化
  - 实际成本**没有想象中那么高**

**通俗理解：**  
很多系统是 “每个子代理各说各话”，Slate 更像一个共享任务状态的团队，协作更紧密。

---

##### 4. 什么是 “RLM for coding”：核心思想是让模型在 REPL 中做任务分解
**关键点：**
- 文中的**RLM**主要基于两个原则：
  1. **REPL 的引用语义**，让代理能把任务拆成一系列操作，并把中间结果保存到引用中。
  2. 代理可以通过**Python REPL**从更高层次编排这些操作。
- 这意味着：
  - 模型不必一步一步机械执行所有动作
  - 它可以站在更高层，思考 “**执行图（execution graph）**” 怎么安排
- 作者认为这种任务分解方式在语义上是合理的：
  - 用 REPL 把复杂任务拆成已知操作集合
  - 模型就能更专注于**策略**，而不是被过长上下文拖垮
- 文章还指出：
  - 现在的模型在跨多步执行时，**追踪复杂变量仍然困难**
  - 但未来会逐渐改善

**通俗例子：**  
不是让模型一次性 “凭脑子记住所有步骤” 去完成复杂编码任务，  
而是让它像程序员一样：
- 先定义变量
- 再执行操作
- 再复用中间结果  
这样更稳定，也更不容易丢上下文。

---

##### 5. 理论来源与新概念：他们和 RLM、CodeAct、Voyager 得出了类似结论
**关键点：**
- 作者提到几个相关先驱工作：
  - **RLM**
  - **CodeAct**
  - **Voyager**
- 尽管 Slate 团队最初没有刻意参考 RLM，但最后得到的核心结论很接近。
- 作者据此认为：这些底层原语（primitives）可能确实重要。

###### 文中定义了两个新术语：
###### 1）Knowledge overhang（知识悬置 / 知识冗余）
- 指模型**明明知道怎么做任务**
- 但在实际执行时，**没有把这些知识真正调动出来**

###### 2）Expressivity（表达能力）
- 指一个接口有多强大、多灵活
- 以及模型**是否倾向于真正使用这种表达能力**

**通俗理解：**  
模型不是 “不会”，而是经常 “没把会的东西用出来”。  
Slate 想做的是：给模型更合适的操作空间，让它把已有能力真正发挥出来。

---

##### 6. Slate 的核心优势：更适合长流程、变化环境、真实软件开发
**关键点：**
- 作者认为 Slate 和 RLM 的**核心区别**在于：
  1. **在长周期实现任务中更稳定**
  2. **能处理不断变化 / 被修改的环境**
- 这让它更适合真正的软件工程场景，尤其是：
  - 软件工程师
  - 工程团队

**通俗例子：**  
真实开发中，代码库会变、需求会改、测试结果会更新。  
Slate 不是只会解 “静态题目”，而是更接近真实项目里的持续协作。

---

##### 7. Thread（线程）机制：Slate 最关键的设计
**关键点：**
- Slate 用一个**TypeScript DSL**来编排 swarm，因此能在 “动作空间里编程”。
- 它引入了一个核心概念：**thread**
- thread 的思想是：
  - 不把子代理上下文完全隔离
  - 而是希望**主编排线程和子线程共享上下文**
- 作者提到，其他团队也有类似方向：
  - **Cognition**
  - **Fundamental**
  - **ManusAI**
- 共通原则都是：
  - 高层负责思考与策略
  - 低层负责具体执行
  - 并把低层过程压缩成高层可理解的信息

**通俗理解：**  
主线程像 “技术负责人”，子线程像 “不同执行小组”。  
但这些小组不是完全割裂的，信息能更自然地共享和汇总。

---

##### 8. 为什么 Thread 有价值：缓存、复用、上下文压缩、情节记忆
**关键点：**
- Slate 的线程引擎可以通过**复用子线程**，最大化缓存效果。
- 这些子线程像 “工作流模块”：
  - 可追加
  - 可组合
  - 能构成更复杂的行为
- 因为简单战术动作被逐个委派给线程，所以系统获得了一个很清晰的**上下文压缩边界**
- 这带来了一个重要结果：
  - 形成了真正可行的**episodic memory（情节记忆）**
- Slate 的情节记忆机制：
  - **只保留那些对成功有贡献的工具调用**
- 文章还保留了 Slate V0 的 “滚动压缩系统”：
  - 据客户反馈，**单次会话最长可运行 2 天**

**重要数据：**
- **单次 session 最长可持续 2 天**

**通俗例子：**  
就像一个人做项目，不会记住所有细枝末节，只保留 “哪些步骤最终起作用”。  
Slate 也是这样记忆，减少无用信息堆积。

---

##### 9. 与其他系统的关系：像 Karpathy 的 LLM OS，也受 opencode 启发
**关键点：**
- 作者说 Slate 的 thread 架构与**Karpathy 提出的 LLM OS**很像：
  - 每个线程都有自己的 “RAM”
  - 主线程可以直接委派任务给其他线程
- 这提供了一种清晰的**扩展原语**
- 最初他们受**BEAM VM**启发，曾把 threads 叫做**actors**
- 后来发现模型对 “threads” 这个词理解更好
- 应用架构上，Slate 目前大量借鉴了**opencode**
- 它的客户端 - 服务器架构直接基于 opencode，这也为后续更多应用打基础

---

##### 10. 当前进展与下一步：部分核心难题已解决，接下来攻克长期记忆
**关键点：**
- 作者认为，Slate 已经解决了一些代理系统的核心限制。
- 他们特别强调：
  - **压缩（compaction）**
  - **编排（orchestration）**
  这两个问题已经基本解决
- 下一步最大的挑战是：
  - **long term memory（长期记忆）**

**通俗理解：**  
现在 Slate 已经比较会 “组织工作” 和 “管理上下文”，  
但还需要进一步解决 “如何跨更长时间持续记住重要信息”。

---

##### 11. 测试案例与效果：在 Terminal Bench 2.0 某任务上表现突出
**关键点：**
- 作者分享了一个测试轶事：
  - 一个**比当前版本更不灵活**的旧架构
  - 在**Terminal Bench 2.0**的**`make-mips-interpreter`**任务上
  - 能通过**3 个测试中的 2 个**
- 作为对比：
  - **Opus 4.5**和**Opus 4.6**
  - 对这个任务的成功率是**1/5 或更低**
  - 而且只在少数测试 harness 中能解出
- 不过作者也说：
  - 他们**不迷信刷榜（benchmaxxing）**
  - 但未来几周会公布 benchmark 分数
  - 也正在招研究岗位的人来做这件事

**重要数据：**
- 旧版架构：`make-mips-interpreter`任务**2/3 测试通过**
- Opus 4.5 / 4.6：该任务**成功率 1/5 或更低**

---

##### 12. 结尾总结
**一句话总结：**  
Slate 的核心创新，不只是 “多模型协作”，而是把 AI 代理放进代码环境里，用**thread + REPL + 上下文压缩 + 共享编排**的方式，让它更像一个真正能长期协作的软件工程团队。  
作者认为，这种架构不仅在编码场景里很强，也可能代表未来通用代理的重要方向。
