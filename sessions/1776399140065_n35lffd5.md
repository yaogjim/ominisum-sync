## 摘要（1）

#### Agent 开发选型讨论整理

##### 一句话总览

这几条内容的核心共识是：**如果你用 TypeScript 做 Agent，当前最值得优先考虑的路线，基本集中在 `pi-mono`、`Claude Agent SDK`、`Vercel AI SDK` 这三类方案里；其中真正的主流决策，往往不是“谁最好”，而是“你更看重性能闭环、平台绑定，还是定制自由度与工程掌控力”。**

---

##### 综合总结

##### 1. 当前主流判断：真正被反复提到的核心方案就两大类

从几条内容综合看，讨论里最被认可的主线其实很明确：

- **`Claude Agent SDK`**
  - 更偏向“大厂 / 成熟 startup / 快速做出生产价值”的路线
  - 优势在于：**Claude 模型在 Agent 任务上的表现普遍被认为更强**
  - 还有一个现实红利：**开发阶段可共享 Claude Max 订阅**
  - 缺点是：**绑定 Claude 生态较深，自由度较低**

- **`pi-mono`**
  - 更适合 **TypeScript 技术栈、个人开发者、小团队、强调高度自定义** 的场景
  - 优势在于：**功能强、调用方便、可塑性高、不容易被单一模型供应商锁死**
  - 缺点不是能力不够，而是：**你需要自己更懂工程设计，自己搭体系**

不少人提到，**最后真正常用的不是“全都试一遍”，而是在这两条强路线里先选一条跑通**。

---

##### 2. `Vercel AI SDK` 是“可用、稳定、工程友好”的次优解或中间层

综合评价里，`Vercel AI SDK` 的定位比较统一：

- 可用性已经很不错
- 稳定性、可靠性较好
- 适合作为 **OpenAI 系模型或多模型接入层**
- 一些项目已经从自维护 LLM SDK 切到它

但也有提醒：

- **不要太依赖第三方扩展 provider**
- 很多第三方 provider 质量参差不齐
- 更稳妥的方式是：**基于官方内置 provider 自己扩展**

所以它更像是：

- **不是最“Agent 原生”的绝对第一选择**
- 但却是很强的**工程中间层 / 模型接入层 / UI 事件流配套层**

---

##### 3. 应用形态上，建议先做 CLI，再考虑桌面端

关于 Runtime / 应用层，几个观点高度一致：

- **刚开始做 Agent，不建议一上来就做复杂 UI**
- 最佳起步方式通常是：**先从 CLI 开始**
- 原因是：
  - 可以专注 Agent 本身
  - 更快验证 Prompt、Context、Tools、Memory、Subagent 等核心机制
  - 降低前期工程噪音

桌面端方面：

- **Electron** 仍被认为是首选
  - 稳定
  - 成熟
  - AI 对其训练语料多，很多问题容易搜到方案
- 但问题也明显：
  - 包体积大
- 因此有人推荐：
  - **Tauri** 作为更轻量替代
  - 100MB+ 的 Electron 应用可压到不到 2MB

结论就是：

- **验证阶段：CLI 优先**
- **产品化桌面端：Electron 稳，Tauri 轻**
- **如果 UI 不是核心卖点，就别太早把精力花在界面上**

---

##### 4. 真正需要学习的，不只是 SDK，而是 Agent 工程方法

有一条回复非常关键，它把讨论从“选框架”拉回到了“做系统”：

真正会反复遇到的问题，不是某个 SDK 独有，而是所有 Agent 工程都会遇到的共性问题，比如：

- Prompt / Context 管理
- Agent / Subagent 协作
- Tool 调用设计与输出处理
- Skill 机制设计
- Hook、Session 管理
- 记忆层设计

这意味着：

- **框架只是起点**
- **Agent 的核心竞争力在工程抽象与工作流设计**
- 单看 SDK API 并不能真正学会 Agent 开发

所以很多人建议去研究成熟开源项目和已泄漏/公开的实现思路，重点不是“照抄”，而是理解其内部结构。

---

##### 5. 开源参考项目很重要，尤其适合建立“整体感”

讨论里推荐了几类可观摩的项目：

- `craft-agents-oss`
  - 技术组合：TypeScript + pi-mono + Electron + React + Claude Agent SDK
  - 适合作为完整参考样本
- `CodePilot`
  - 被推荐为完整开源方案参考
- Cloudflare 的 `Agentic Inbox`
  - 适合学习“完整业务型 Agent 应用”如何构建
- `Codex` / `Opencode`
  - 适合研究编程 Agent 的工程范式

这些项目的价值，不只是看它“用了什么库”，而是看：

- Agent 生命周期怎么设计
- Tool 怎么组织
- 上下文如何裁剪
- Memory 怎么挂接
- UI 事件流怎么与模型交互同步

---

##### 6. 上层 UI / Runtime 也逐渐有配套方案

除了底层 SDK，内容里也提到一些上层搭建建议：

- 可以用 **assistant-ui + tools ui**
- 它能提供：
  - 从模型事件到 UI 的完整事件流
  - 现成组件
  - 也可以只拿 Runtime，自己做 UI

此外还有工程建议：

- 数据库可用 `better sqlite`
- 记忆层可做成**可插拔设计**
  - 外部组件也可以
  - 简单情况下甚至 Markdown 也可以

这说明当前社区已经不只是在聊“怎么调模型”，而是在逐步形成：

- 底层 SDK
- Runtime
- UI 组件
- 存储层
- Memory 层

这样一整套 Agent 应用工程分层思路。

##### 深入浅出解读

##### 1. 为什么大家会在 `Claude Agent SDK` 和 `pi-mono` 之间反复摇摆？

因为它们代表了两种完全不同的开发哲学。

###### `Claude Agent SDK` 的逻辑

它更像是：

> “我先要最强性能、最快出效果，先把产品做出来再说。”

如果你的目标是：

- 赶紧把一个 Agent 跑起来
- 希望复杂任务表现尽量强
- 团队更重结果导向
- 愿意接受一定的平台绑定

那 `Claude Agent SDK` 很自然会有吸引力。

它的本质优势不是“接口更优雅”，而是：

- **底层模型强**
- **现成能力成熟**
- **订阅红利真实存在**

所以很多公司不是因为它最开放而选择它，而是因为它**最省时间、最容易先打出价值**。

---

###### `pi-mono` 的逻辑

它更像是：

> “我不想被某个模型绑死，我要长期可控、可改、可扩展。”

如果你的目标是：

- 用 TypeScript 做深度定制
- 要兼容不同模型和资源
- 想自己控制 Agent 结构
- 做的是内部工具、实验性产品、长期演化系统

那 `pi-mono` 就更合适。

它的核心吸引力在于：

- **Agent 工程感更强**
- **可以按照自己的资源和场景去改**
- **更适合建立自己的 Agent 基础设施**

所以它受欢迎，不只是因为“好用”，而是因为它给了开发者**系统掌控权**。

---

##### 2. 为什么说“先跑通一条路径”比“研究所有框架”更重要？

因为 Agent 开发的难点，很多时候根本不在“选哪个 SDK”。

真正的难点是这些问题：

- 上下文什么时候拼进去，什么时候裁掉？
- 一个任务什么时候拆成多个子 Agent？
- Tool 输出太长、太脏时怎么处理？
- 记忆什么时候写入，什么时候召回？
- Session 如何恢复？
- 模型失控、跑偏、重复调用时怎么兜底？

这些问题不管你用：

- `Claude Agent SDK`
- `pi-mono`
- `AI SDK`
- 甚至 LangChain / LangGraph

都逃不掉。

所以“先把一条完整链路跑通”很重要，因为只有真的做完一次，你才会知道：

- 框架替你解决了什么
- 哪些坑必须自己填
- 哪些抽象值得保留
- 哪些设计只是看起来高级

换句话说：

> **先形成 Agent 的工程直觉，再谈框架比较，判断才会更靠谱。**

---

##### 3. 为什么很多人建议从 CLI 起步？

因为 CLI 是 Agent 最本质的试验场。

一个 Agent 系统的核心，不是窗口好不好看，而是它能不能稳定完成任务。  
在最早阶段，你真正要验证的是：

- 任务规划是否靠谱
- Prompt 是否稳定
- Tool 是否可控
- 多轮上下文是否积累正确
- 出错后能否恢复
- Memory 是否真的有帮助

CLI 的好处是：

- **快**
- **简单**
- **调试成本低**
- **不会被 UI 分散注意力**

而 UI 往往会过早引入很多无关复杂度：

- 状态同步
- 流式渲染
- 会话展示
- 用户交互设计
- 组件事件流
- 桌面打包问题

所以“先 CLI，后 UI”本质上是一种**工程优先级管理**。

---

##### 4. Electron 和 Tauri 的争议，本质上在争什么？

不是在争“谁更先进”，而是在争：

- **稳定成熟**
- 还是
- **轻量小巧**

###### Electron
优点：

- 成熟稳定
- 生态大
- AI 训练语料多，问题容易解决
- 对桌面 Agent 非常友好

缺点：

- 包体积大
- 资源占用高

###### Tauri
优点：

- 非常轻
- 打包体积小很多

缺点：

- 生态和成熟度通常不如 Electron
- 某些复杂桌面能力或工程经验没有 Electron 丰富

所以如果你是：

- 想快速做出桌面产品
- 不想踩太多桌面工程坑

那 Electron 仍是很务实的选择。

如果你已经明确：

- 包体积是关键指标
- 你愿意承担更多工程细节

那 Tauri 值得考虑。

---

##### 5. `Vercel AI SDK` 为什么经常被说“还不错”，却不总是第一推荐？

因为它强在“工程接入层”，但未必强在“Agent 框架心智”。

可以把它理解成：

- 很好的模型调用和应用接入基础设施
- 很适合做流式输出、Provider 抽象、前后端联动
- 在应用工程里很好用

但对于很多 Agent 开发者来说，他们更关心的是：

- 多 Agent 编排
- Tool 协调
- 长上下文管理
- 状态机制
- Agent 生命周期

这些维度上，大家感知更强的往往是 `Claude Agent SDK` 或 `pi-mono`。

所以 `AI SDK` 不是差，而是它常常扮演：

- **稳健底座**
- 或 **中间层能力**
- 而不是所有人心中的“Agent 主框架”

---

##### 6. 新手如果现在开始，应该怎么选？

如果把这些讨论翻译成更实用的建议，大概是这样：

###### 情况 A：想最快做出能用的 Agent
优先考虑：

- `Claude Agent SDK`

适合你如果：

- 追求效果优先
- 能接受 Claude 绑定
- 想先把产品价值做出来

---

###### 情况 B：你是 TypeScript 开发者，想长期做自己的 Agent 系统
优先考虑：

- `pi-mono`

适合你如果：

- 想自己掌控架构
- 不想被单一模型绑住
- 会长期演进自己的工具链

---

###### 情况 C：你更关心多模型接入和应用层工程稳定性
优先考虑：

- `Vercel AI SDK`

适合你如果：

- 想做稳健的模型接入层
- 需要较好的稳定性和可靠性
- 会配合自己的 Agent 逻辑使用

---

##### 实操建议版结论

如果把这几条内容压缩成一套最实用的行动建议，可以这样理解：

1. **先不要在十几个框架里反复横跳**
   - 主流上先看 `pi-mono` 和 `Claude Agent SDK`

2. **如果你是 TS 栈，且偏自定义，优先试 `pi-mono`**
   - 更适合建立自己的 Agent 体系

3. **如果你要最快验证强模型 Agent，优先试 `Claude Agent SDK`**
   - 特别适合先做出成果

4. **把 `Vercel AI SDK` 当成可靠的工程层工具，而不一定是唯一主框架**
   - 尤其适合模型接入与应用工程配套

5. **第一版先做 CLI**
   - 优先验证 Agent 核心机制，而不是 UI

6. **学习重点放在 Agent 工程问题，不只是 SDK API**
   - Prompt / Context / Tool / Memory / Subagent / Session 才是真核心

7. **多看完整开源项目**
   - 比单看文档更能建立整体感
