**BadUncle**

群友在讨论harness engineering， 来一个通俗解释：

Linear — 任务调度 + 人机界面  
发号施令的入口。issue 是任务单元，assign 是启动信号，comment是实时沟通通道。agent 的所有工作进展都流式回到 issue timeline，手机上就能看。它既是调度器，也是可观测性面板。

Linear MCP — agent 的嘴和耳朵  
让 CC 能读写 Linear。读 issue 内容、查关联上下文是"耳朵"；发  
activity、问用户问题（ask\_user\_via\_linear）是"嘴"。没有它，agent是个聋哑人。

Cloudflare Tunnel — 桥梁  
把云端的 Linear webhook 连到你家里的电脑。没有它，Linear的信号到不了本地的 CC。

EdgeWorker — 大脑/调度中枢  
接收 webhook，分析 issue 类型，选择 system prompt 和 subroutinepipeline，管理仓库路由。它决定 agent 该怎么干活，是 Constrain 和Inform 的核心实现。

tmux — 手  
往 CC 的终端里"打字"。通过 paste-buffer 注入prompt，模拟人类键盘输入。它是 harness 操控 agent 的物理接口。

JSONL log — 眼睛  
读 CC 写的 session 日志（\~/.claude/projects/.../session.jsonl），解析思考、工具调用、结果。它是 harness 观察 agent行为的窗口，也是流式反馈到 Linear 的数据源。

Claude Code — 马  
真正干活的 agent。写代码、读文件、跑命令、调 MCP 工具。在 tmux里以完整交互模式运行，保留所有原生能力（hooks、skills、MCP servers）。

Git worktree — 隔间  
每个 issue 一个独立的工作目录和分支。agent 之间互不干扰，也不会污染main。是 Constrain 层的物理隔离机制。

Subroutine pipeline — 流程线  
coding → verifications → git-gh → summary，每步限定工具白名单。是Constrain + Verify 的编排层，确保 agent按步骤走完整个流程而不是自由发挥。

## 解读（1）

### 2026-03-12 06:37:26

#### 总结

这段内容是在用**非常通俗的方式**解释一套 “让 AI 代理自动接活、干活、回报进度” 的系统，也就是所谓的**harness engineering**。

它把整套系统拆成几个角色：

- **Linear**：任务中心，也是人和 AI 沟通的界面
- **Linear MCP**：让 AI 能读写 Linear，相当于 “嘴和耳朵”
- **Cloudflare Tunnel**：把云端消息送到本地机器的桥
- **EdgeWorker**：负责判断任务、分配流程的大脑
- **tmux**：代替人往终端里输入命令的 “手”
- **JSONL log**：观察 AI 在做什么的 “眼睛”
- **Claude Code**：真正写代码干活的 “马”
- **Git worktree**：给每个任务单独隔离空间的 “隔间”
- **Subroutine pipeline**：规定 AI 按步骤工作的 “流水线”

**一句话概括：**  
这是一套把 AI 程序员接入任务系统、自动执行开发流程、并实时回传进度的 “自动化工作台”。

---

#### 通俗解读

可以把它想成一个 “**远程指挥 AI 程序员干活**” 的系统。

##### 1. Linear：老板下任务的地方
你在 Linear 里建一个 issue，就像给员工发了一张工单。

- **issue** = 要做的任务
- **assign** = 正式开工
- **comment** = 中途交流

而且 AI 的执行进度会持续回写到 issue 里，所以你在手机上也能看它做到哪一步了。

---

##### 2. Linear MCP：AI 和外界沟通的接口
AI 本身不会天然知道 Linear 上写了什么，也不会自己去回消息。  
所以要靠**Linear MCP**：

- 能读 issue、读上下文 → 相当于 “耳朵”
- 能发状态、能提问 → 相当于 “嘴巴”

没有它，AI 就像一个**听不见也说不出的打工人**。

---

##### 3. Cloudflare Tunnel：把外部消息送进你电脑
因为实际跑 AI 的环境可能在你自己的电脑上，但 Linear 的 webhook 在云上。

这时候**Cloudflare Tunnel**就像一条安全通道，负责把外面的通知送到你本地。

没有它，任务消息就进不来。

---

##### 4. EdgeWorker：总调度
这是整套系统最像 “大脑” 的部分。

它负责：

- 收到任务通知
- 判断这是什么类型的 issue
- 选对应的 system prompt
- 选执行流程
- 找对仓库

也就是说，它决定：

> 这个任务该让 AI 怎么做、按什么规则做、去哪做。

---

##### 5. tmux：帮你 “动手”
AI 真正运行在终端里，但终端需要有人输入。  
**tmux**就是那个 “帮你敲键盘的人”。

它可以把 prompt 注入到 Claude Code 的终端会话里，像人类操作一样启动和控制 AI。

所以它相当于**机械手**。

---

##### 6. JSONL log：实时监控窗口
AI 在工作时，会产生日志。  
这些日志记录了：

- 它想了什么
- 调了哪些工具
- 输出了什么结果

系统读取这些日志，再把关键信息同步回 Linear。

所以 JSONL log 就像**监控摄像头 + 战报来源**。

---

##### 7. Claude Code：真正干活的员工
前面那些都只是调度、控制、观察的设施。  
真正读代码、改代码、跑命令、调用工具的是**Claude Code**。

所以叫它 “马”，意思就是：  
**真正拉车干活的是它。**

---

##### 8. Git worktree：任务隔离
每个 issue 都有独立目录和分支，互不干扰。

这很重要，因为多个任务同时跑时：

- 不会互相覆盖代码
- 不会污染主分支
- 出错也容易回滚

你可以把它理解成：  
**每个任务一个独立工位。**

---

##### 9. Subroutine pipeline：防止 AI 自由发挥
AI 如果完全放飞，容易乱来。  
所以系统设计了一条固定流程，比如：

`coding → verifications → git-gh → summary`

并且每一步只开放有限工具。

这样做的目的就是：

- 先写代码
- 再验证
- 再处理 git / PR
- 最后总结

像工厂流水线一样，**减少跑偏**。

---

#### 我的意见

##### 这套设计的优点
我觉得它的思路很清晰，核心价值有三点：

1. **把 AI 接入真实工作流**
   - 不是单独聊天，而是直接进入任务系统、代码仓库、终端环境

2. **可观测性强**
   - 人能随时看到 AI 干到哪了，而不是黑盒执行

3. **约束做得比较完整**
   - 用 worktree、pipeline、工具白名单限制 AI，降低失控风险

---

##### 它适合什么场景
比较适合：

- 个人开发者的自动化助手
- 小团队的 AI coding workflow
- 需要 “远程发任务 + 实时看进度” 的开发场景

尤其适合那种：  
**人在外面，用手机提个 issue，让家里 / 办公室机器上的 AI 自动开始干活。**

---

##### 可能的挑战
不过它也有一些现实难点：

- **搭建复杂**
  - 组件不少，维护成本不低
- **稳定性依赖链长**
  - 任一环节坏了都可能断
- **调度逻辑要写得好**
  - 不然 AI 可能拿错仓库、跑错流程
- **安全性要重视**
  - 涉及本地机器、终端注入、仓库操作，权限控制很关键

---

##### 一句我的看法
如果用最通俗的话说：

> 这不是单纯 “让 AI 写代码”，而是在搭一个 “AI 程序员流水线工厂”。

它最有价值的地方，不是某个单点工具，而是把**任务分发、执行控制、过程观测、结果回传**串起来了。

## 产品-最佳实践（1）

### 2026-03-12 06:39:45

下面给你一个**具体实例**，并提炼成这套 harness engineering 的**最佳实践（精炼版）**。

---

##### 具体实例：用 Linear 驱动一个 “修复登录 bug” 的自动开发流程

###### 场景
用户在手机上打开 Linear，新建一个 issue：

**标题**：修复登录接口在 token 过期时返回 500  
**内容**：
- 复现路径：登录后放置 2 小时，再调用`/api/profile`
- 预期结果：返回 401
- 实际结果：返回 500
- 仓库：`backend-api`

然后把这个 issue assign 给机器人。

---

##### 这套系统如何运转

###### 1. Linear 作为入口
- issue 是任务单元
- assign 是启动信号
- comment 是人机沟通通道
- timeline 是可观测面板

**最佳实践**：
- issue 模板标准化：`问题描述 / 复现步骤 / 预期结果 / 仓库 / 验收标准`
- assign 才触发执行，避免 agent 被噪音信息唤醒
- 所有进展回写 issue timeline，确保手机可追踪

---

###### 2. EdgeWorker 作为调度中枢
它收到 webhook 后判断：
- 这是**bugfix**
- 对应仓库是`backend-api`
- 应该走流程：`coding → verification → summary`

**最佳实践**：
- 不让 agent “自由发挥选流程”，而是由中枢按任务类型路由
- bug /feature/refactor 使用不同 prompt 和 pipeline
- 在入口层做约束，比事后补救更便宜

---

###### 3. Git worktree 作为隔离环境
系统自动创建：
- 分支：`fix/linear-184-token-expired-401`
- worktree：独立目录

这样 agent 改代码不会污染主工作区，也不会和别的 issue 冲突。

**最佳实践**：
- 一 issue 一 worktree 一 branch
- 不在 main 或共享目录直接操作
- 所有临时文件、测试改动都限制在隔离区

---

###### 4. tmux + Claude Code 开始执行
EdgeWorker 在 tmux 会话里启动 Claude Code，把 prompt 注入进去，比如：

- 阅读 issue
- 定位登录鉴权逻辑
- 找出 500 的原因
- 修改成 token 过期时返回 401
- 补测试
- 运行验证

Claude Code 真正负责：
- 读代码
- 改代码
- 跑测试
- 调工具

**最佳实践**：
- agent 保持 “原生交互模式” 运行，不要阉割能力
- harness 只负责 “约束 + 编排 + 观察”，不替代 agent 本身
- 用 tmux 作为稳定物理接口，降低集成复杂度

---

###### 5. JSONL log 做实时观察
Claude Code 执行时产生 session.jsonl，harness 持续读取并解析：

例如 timeline 上同步显示：
- 正在读取`auth/middleware.ts`
- 发现异常：token 过期被统一包装成内部错误
- 正在修改错误映射逻辑
- 正在运行测试：`auth.spec.ts`
- 测试通过，准备生成总结

**最佳实践**：
- 流式回传 “阶段性进展”，不要只回最终结果
- 展示 “正在做什么”，而不是暴露冗长原始思维
- 反馈结构化：`阶段 / 动作 / 结果 / 阻塞`

---

###### 6. 遇到不确定点时，通过 Linear 问用户
如果 agent 发现一个分歧：
- token 过期到底返回`401`还是`403`？

它通过 Linear MCP 在 issue 下提问：
> 我发现当前系统对鉴权失败存在 401/403 两种历史实现。  
> 这个问题的验收标准是否以 401 为准？

用户在手机上回复：
> 统一改成 401。

agent 接着干。

**最佳实践**：
- 不确定的产品决策，及时 ask_user，不要擅自猜
- 让 Linear 成为唯一的人机对话面板，避免沟通分散到 IM / 终端
- 问题要具体、可决策，减少来回轮次

---

###### 7. Subroutine pipeline 保证流程完整
不是 “改完就算”，而是强制经过：

1. **coding**：只允许读写代码、搜索、编辑  
2. **verification**：只允许跑测试、lint、类型检查  
3. **git-gh**：准备提交信息、PR 材料  
4. **summary**：输出变更摘要、风险、验证结果

**最佳实践**：
- 分阶段限权，降低误操作
- verification 独立出来，避免 “写完直接宣布完成”
- summary 固定格式，便于 issue 回看和审计

---

##### 这个实例上的最佳实践总结

###### 一句话版
**让 Linear 管任务，EdgeWorker 定策略，worktree 做隔离，tmux 驱动 agent，JSONL 做观测，pipeline 保证闭环。**

###### 精炼原则
1. **入口标准化**：issue 模板统一，assign 才触发  
2. **调度中心化**：任务分类、仓库路由、prompt 选择都在 EdgeWorker  
3. **执行隔离化**：每个 issue 独立 branch/worktree  
4. **交互单一化**：所有人机沟通都回到 Linear  
5. **观测流式化**：进展持续回传，不做黑盒执行  
6. **流程强约束**：coding、verification、summary 必须分阶段  
7. **决策显式化**：遇到产品歧义立刻 ask_user  
8. **能力原生化**：Claude Code 保持原生能力，harness 不重复造轮子

---

##### 最终你可以把它理解成
这个实例里最好的落地方式不是 “做一个会写代码的机器人”，而是：

**做一个可调度、可观察、可追问、可隔离、可验收的自动化软件工人系统。**

### 提问 · 2026-03-12 06:48:35

在开源社区，是否有成熟的高质量的EdgeWorker（中间理解和调度者） ？

### 回答 · 2026-03-12 06:48:35

有，但先说结论：

**“完全对标你这个图里 EdgeWorker 职责、又成熟高质量、还能直接拿来就用” 的开源项目，不算多。**  
开源社区里更多的是：

1. **工作流 / 编排框架**  
2. **Agent runtime / 多 agent 调度框架**  
3. **Webhook / 事件驱动自动化平台**  
4. **CI/CD 风格任务编排器**  

也就是说，**有很多 “可拼装零件”**，但**少有一个现成成品**，能完整承担你这里说的：

- 收 Linear webhook
- 理解 issue 类型
- 选择 prompt
- 选择 subroutine pipeline
- 做 repo 路由
- 管理 worktree
- 驱动本地 CC/tmux
- 回写 timeline

这种 “AI coding harness 中控大脑”。

---

#### 一、如果你问 “有没有成熟开源替代品”
##### 答案是：**有部分替代，没有完整等价物**

更准确地说：

- **有成熟的 “调度框架”**
- **有成熟的 “agent 编排框架”**
- **有成熟的 “自动化工作流引擎”**
- **但缺一个特别成熟的、专门面向 Linear + Claude Code + 本地 worktree + tmux 的开源中控**

所以现实中常见做法是：

> **拿一个通用编排框架做底座，再自己补一层 EdgeWorker 业务逻辑。**

---

#### 二、开源社区里最接近的几类项目

---

##### 1）Temporal
这是最成熟的一类候选。

###### 它擅长什么
- 长时任务编排
- 有状态工作流
- 可重试
- 任务超时
- 人工介入
- 异步事件等待
- 高可靠执行

###### 对应到你的 EdgeWorker 职责
它很适合承载：

- 收到 webhook 后启动 workflow
- 按 issue 类型分支
- 等待用户回复
- 编排`coding → verification → summary`
- 失败重试
- 记录任务状态

###### 为什么它强
因为你的场景本质上不是 “单次函数调用”，而是一个**长生命周期任务**：

- 先接单
- 再开工
- 中途可能卡住
- 可能 ask_user
- 可能等评论
- 可能重试测试
- 最后总结收尾

这非常像 Temporal 的典型问题域。

###### 但它不直接提供什么
它**不会天然帮你**：
- 理解 Linear issue
- 自动选择 prompt
- 管理 tmux
- 理解 Claude Code JSONL
- 管理 git worktree

这些要你自己实现。

###### 结论
如果你要做一个真正工程化、可长期运行的 EdgeWorker，  
**Temporal 是非常强的底座候选。**

---

##### 2）LangGraph
这是 AI agent 编排领域里很热门的一类。

###### 它擅长什么
- 把 agent 流程建成图
- 有状态节点执行
- 条件分支
- 多 agent 协作
- human-in-the-loop

###### 对应你的场景
很适合表达：

```text
收到 issue
  → 分类
  → 选仓库
  → 生成任务上下文
  → 启动 coding agent
  → 跑 verification
  → 若失败则回 coding
  → 若有歧义则 ask_user
  → 用户回复后继续
  → 生成 summary
```

###### 优点
- 很适合 “理解和决策” 的 agent 逻辑
- 比纯 workflow engine 更贴近 LLM 编排
- 状态图表达比较直观

###### 缺点
- 更偏 agent orchestration，不是传统稳健型任务平台
- 在 “生产级可靠性、可观测性、重试恢复” 上，通常还得自己补很多工程能力
- 跟 tmux/worktree/Linear 的落地集成仍要自己写

###### 结论
如果你把 EdgeWorker 的核心看成 “**AI 决策图**”，  
**LangGraph 很合适。**  
如果你把它看成 “高可靠任务中控”，单用它可能还不够。

---

##### 3）Trigger.dev/n8n / Activepieces / Windmill
这类是事件驱动自动化平台。

---

###### Trigger.dev
更偏开发者友好的后台任务编排。

适合：
- webhook 触发
- 长任务
- 重试
- 任务日志
- 调 API

对你的场景：
- 可以做 webhook 接入和生命周期管理
- 可以做 issue 到任务的路由
- 可以调本地 / 远程服务

但：
- AI agent 语义不是核心
- 本地 tmux /worktree/session log 这种细活还得自己接

---

###### n8n
低代码自动化很强。

适合：
- API 编排
- webhook 接入
- 条件判断
- 消息回写

但：
- 更适合系统集成，不太适合复杂 coding harness 中控
- 对本地终端控制、长会话 agent、不规则状态机支持不够优雅

它更像：
> 自动化胶水层  
不是你这个意义上的 “工程大脑”。

---

###### Windmill
开发者自动化平台，支持脚本任务、工作流、UI。

优点：
- 比 n8n 更工程化
- 适合内部工具和自动化平台
- 写脚本比较自由

缺点：
- 仍然不是专门的 agent harness 调度器

---

###### 结论
这类工具更适合做：
- webhook 接入层
- 任务触发层
- 运维 / 辅助自动化层

不太像完整 EdgeWorker。

---

##### 4）OpenHands / SWE-agent / AutoCodeRover 这类开源 coding agent 项目
它们和你的问题相关，但定位不一样。

###### 它们擅长什么
- 给一个 issue / 任务
- 自己读仓库
- 改代码
- 跑测试
- 尝试修复

###### 为什么 “像”
因为它们也有：
- 问题理解
- 决策
- 执行步骤
- 验证循环

###### 为什么 “不完全是”
因为它们通常把：
- 理解
- 执行
- 验证

都包在 agent 自己体内了。

而你这里的 EdgeWorker 是更外层的：
- 接 webhook
- 路由仓库
- 选 prompt
- 管理环境隔离
- 驱动 Claude Code
- 回写 Linear

也就是说：

> 它们更像 “马本身” 或者 “半自带骑手的马”，  
> 而不是你图里的 “中控调度大脑”。

###### 结论
可借鉴它们的：
- 任务拆解
- 验证循环
- patch/test/fix 流程

但不能直接替代 EdgeWorker。

#### 三、如果非要选 “最像 EdgeWorker 的成熟底座”
我会这样排：

##### 工程可靠性优先
**Temporal**

适合你要：
- 多任务并发
- 长周期任务
- 失败恢复
- 人工等待
- 状态持久化
- 生产级执行

---

##### AI 编排表达力优先
**LangGraph**

适合你要：
- agent 状态图
- 复杂决策分支
- human-in-the-loop
- 多 agent 协作

---

##### 快速搭建内部自动化优先
**Trigger.dev/ Windmill**

适合你想：
- 先搭个能跑的系统
- 用 webhook + job + API 快速验证
- 不先上太重的平台

---

#### 四、现实里高质量团队通常怎么做

通常不是 “找一个开源 EdgeWorker 成品”，而是下面这三层：

##### 方案 A：最工程化
- **Temporal**：任务编排底座
- **自研 EdgeWorker 逻辑**：issue 理解、prompt 选择、repo 路由
- **自研执行器**：tmux /worktree/ JSONL parser
- **Linear MCP**：沟通层

这是最像成熟后端系统的做法。

---

##### 方案 B：最 AI-native
- **LangGraph**：agent 决策流
- **自研 webhook/router**
- **自研 execution harness**
- **自研 observability 回写**

适合强 agent 化路线。

---

##### 方案 C：最小可用
- 一个 web service
- 一个 webhook handler
- 一个简单任务队列
- 一个状态数据库
- 若干执行脚本

很多团队早期其实就是这么干的。  
因为你的 EdgeWorker 核心逻辑，未必需要很重的平台才能做出来。

---

#### 五、为什么 “没有特别统一的成熟开源成品”
因为这个问题本身跨了好几层：

1. **产品工作流层**：Linear /issue/ 评论 /assign
2. **LLM 控制层**：prompt、上下文、工具权限
3. **本地执行层**：tmux、shell、Claude Code
4. **工程隔离层**：git worktree、branch、repo routing
5. **可观测层**：JSONL、timeline、activity
6. **人机协作层**：ask_user、等待回复、恢复执行

这不像传统 CI，也不像普通 chatbot，更不像单纯 agent framework。

所以大家往往是：
- 用现成框架做一部分
- 剩下最关键的中控逻辑自己写

---

#### 六、如果你现在要选型，我给一个很务实的建议

##### 如果你要 “长期生产可用”
选：
- **Temporal 作为底座**
- 你自己写 EdgeWorker

##### 如果你要 “快速验证 agent 调度逻辑”
选：
- **LangGraph 或一个简单状态机**
- 外面包一层 webhook service

##### 如果你要 “先做内部 demo / MVP”
直接：
- **Node/Python Webhook 服务 + Redis/Postgres + 自研状态机**
- 往往比硬上大框架更快

---

#### 七、一个非常实际的判断标准
你挑 EdgeWorker 底座时，重点看它能不能支持下面 8 件事：

1. **Webhook 驱动**
2. **长时任务**
3. **等待人工回复再恢复**
4. **失败重试**
5. **任务状态持久化**
6. **多仓库路由**
7. **外部执行器调用（tmux/CLI）**
8. **可观测和审计**

如果一个框架不能优雅支持这 8 条，  
那它最多只是部分组件，不是成熟中控底座。

---

#### 八、最终结论
**开源社区有成熟的 “底座”，但没有特别成熟、直接对标你这里 EdgeWorker 的标准成品。**

最接近的高质量选择是：

- **Temporal**：最适合作为生产级调度底座
- **LangGraph**：最适合作为 agent 决策编排层
- **Trigger.dev/ Windmill /n8n**：适合作为自动化胶水层
- **OpenHands / SWE-agent 类项目**：适合借鉴 coding agent 内部流程，但不直接等价于中控

**所以最佳实践通常不是 “找一个现成 EdgeWorker”，而是 “选一个可靠底座 + 自研你自己的中控层”。**

如果你愿意，我下一条可以直接给你一份：

**“做 Linear + Claude Code harness 时，EdgeWorker 技术选型对比表（Temporal / LangGraph / Trigger.dev/ 自研）”**

这样你会更容易判断该选哪条路线。
