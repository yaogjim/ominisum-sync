> **一句话点评**：这是一篇偏宣传但信息量较高的企业级 RAG 架构分析，值得关注其“轻结构、查询时建链”的设计思路。
>
> **摘要**：文章介绍 SAG 通过事件-实体轻量索引、SQL 连接和查询时动态扩展来替代重型 GraphRAG 全局建图，强调其在多跳问答、增量更新、私有化部署和大规模检索上的工程优势，并列出适用边界。

## 分析要点

- **核心高价值点**：SAG 的核心价值在于把结构化能力从离线全局建图转移到在线检索执行阶段，用 SQL 按需生成多跳证据链，降低维护和增量成本。
- **留存建议**：长期保留（文章系统比较了 SAG、GraphRAG、HippoRAG 2 的架构取舍，并提供了企业级 RAG 在成本、增量、私有化和规模化方面的选型参考。）

**知识要点**

- GraphRAG 在企业场景中的主要问题包括全局建图成本高、增量维护困难、私有化部署压力大，以及离线图结构与在线召回逻辑脱节。
- SAG 将每个 chunk 抽取为 event 和 entities，通过 SQL 表连接在查询时动态构造局部多跳链路，而非预先维护完整知识图谱。
- SAG 使用 SQL 负责确定性过滤和连接，向量检索负责语义扩展，LLM 只在压缩后的候选集上做精排，从而降低 token 成本。
- 文章引用的实验显示 SAG 在 MuSiQue 多跳问答上 Recall@5 从 HippoRAG 2 的 65.13% 提升到 80.04%，但证据主要来自项目方材料，仍需独立复现。
- SAG 更适合跨文档、多实体、长链条问答场景，不适合简单 FAQ、单跳检索或抽取模型质量不足的环境。

**行动项**

- 阅读 SAG 论文和 GitHub 仓库，确认 event/entity 抽取格式、SQL schema 和检索流程。
- 用自己的企业文档或公开多跳数据集小规模复现 Benchmark，重点验证 Recall、延迟、写入成本和增量更新表现。
- 对比现有向量 RAG、GraphRAG、HippoRAG 2 与 SAG 在同一数据集上的检索质量和维护成本。
- 评估本地 LLM 对事件和实体抽取的稳定性，避免抽取质量成为检索链路瓶颈。
- 若业务存在跨文档多跳问答需求，可将 PostgreSQL + pgvector + 全文检索作为 SAG PoC 的基础设施方案。

**烟花老师**

### 刚开源就 SOTA，这个项目有点东西：SAG 凭什么跑赢 GraphRAG，省钱，还扛得住海量企业数据？

假设你是某家科技公司的技术负责人。

去年你用 GraphRAG 搭了一套内部知识库，拿两万份合同做 PoC，问答效果惊艳，老板当场拍板立项、批预算、上生产。

然后文档涨到五百万份。

问题开始不对劲了：

建一次知识图谱要跑整整一个周末，研发费和 token 费比这次查询产生的业务价值还高；

合规部改了一份合同，知识库三天后才更新完；

安全团队坚持数据不能出域，可你依赖的云端大模型又非得把文档传出去。

你心里冒出三个问题：

1 GraphRAG 跑分明明是 SOTA，为什么一进企业真实场景就集体拉胯？

2 多跳问答这种「张经理 → 他去年签的客户 → 那客户今年的续约」式连环追问，到底卡在哪一层？

3 有没有一种方案，既能在跑分上赢，又能扛住五亿文档、当天增量、私有化部署这三件事？

这篇论文给出了一种新的思考和路径：

![Image](https://pbs.twimg.com/media/HLBQDhca8AAzdVI?format=jpg&name=large)

[https://arxiv.org/abs/2606.15971](https://arxiv.org/abs/2606.15971)

SAG给了一个反直觉的答案：

SQL 检索增强生成，SQL 已经成熟应用于几乎所有的存储系统几十年了，

把这种成熟的结构化标准直接用于检索和Agent系统！

就是这一点！

很聪明的做法。

让我想到了最近 ClaudeCode 基于已有文件系统的 Agentic Search 方案，有异曲同工之妙。

猛一看上去不太性感，但是又有效又实用。

而且该项目已开源：

[https://github.com/Zleap-AI/SAG](https://github.com/Zleap-AI/SAG)

SAG 将每个数据块转换为一个语义完整的事件和一组索引实体，然后使用 SQL 连接查询将共享实体的事件动态链接到局部超边，并在查询时构建动态实例化的局部索引结构。

这种设计避免了全局图重建和持续维护的需要。

它在最难的 MuSiQue 多跳问答上把 Recall从 65.13% 拉到 80.04%，还扛住了约 5 亿条数据的线上秒级检索。

![Image](https://pbs.twimg.com/media/HLBQK5za4AAtFTe?format=jpg&name=large)

本文会拆解 SAG 到底做对了什么——以及它为什么可能让 GraphRAG 这类「重图」路线在企业里显得又慢又贵。

![Image](https://pbs.twimg.com/media/HLBQSKTakAAGRyu?format=jpg&name=large)

#### 多跳问答，向量召回早就到顶了

企业里最难答的问题，几乎都是多跳的。

「我们上海办公室负责合规的张经理，去年签的那个客户，今年的续约情况怎么样？」——要答出来，得先找到张经理，再找到他去年签的客户，再找到那个客户今年的续约记录。

三跳，三份分散在不同文档里的证据。

普通向量检索在这类问题上很早就到顶了。

它只会找语义相近的片段，拼凑不出「张经理 → 客户 → 续约」这条证据链。

更要命的是，Agent 做多步检索时，单步误差会沿推理链累积放大——第一步漏了一个关键实体，后面三步全在错误地基上盖楼。

对 Agent 来说，检索系统真正该提供的能力，是在多跳查询里稳定把证据组织成一条链。

向量检索给不了这个能力。于是行业分出几条路线，核心区别就一个：

什么时候建结构、建多大。

Naive RAG：切块、向量化、top-k。快、便宜、能扛量，但精度卡在语义浅层匹配。 GraphRAG：入库时就把全局知识图谱建好，先全文抽实体、抽关系，再做社区聚类。 HippoRAG 2：模仿人类海马体做认知图谱，是目前公认的多跳强基线。 SAG：几乎不预先建图，入库时只抽一个轻量的局部结构，检索时再就地「长」出一条链。

前三者方向都对，份量却都很重。SAG 押的是相反的注。

![Image](https://pbs.twimg.com/media/HLBQZvobwAAib1H?format=jpg&name=large)

GraphRAG 真正的病根：结构建了，查询时却没用上

![Image](https://pbs.twimg.com/media/HLBQf1jbAAAw4Ee?format=jpg&name=large)

GraphRAG（图增强检索增强生成）是一种将知识图谱（Knowledge Graphs）与大语言模型（LLM）相结合的先进检索技术。传统的 RAG 依赖于将文本切片并利用向量相似度进行检索，这在处理跨文档的“全局问题”或复杂的“多跳推理”时极易抓瞎。

![Image](https://pbs.twimg.com/media/HLBQlWxasAA4A2z?format=jpg&name=large)

而 GraphRAG 通过构建结构化的实体与关系网络，让 AI 具备了像人类一样“顺藤摸瓜”连点成线的能力。

GraphRAG 的卖点是用图表达实体关系，但实际查询时，系统要么在图节点上做相似度检索，要么在社区摘要上做匹配——它并没有真正去「走」那张图的多跳结构。

离线建好的精细结构，和在线实际执行的召回逻辑，是脱节的。

你付了建图的钱，买到的却只是「查询时能走多跳」的错觉。

这个「结构-检索脱钩」，才是企业里 GraphRAG 最让人沮丧的地方：

它建得起的精致，用的时候用不上。

![Image](https://pbs.twimg.com/media/HLBQrhgbYAA66xX?format=jpg&name=large)

再把账拆细，这三笔企业都跑不掉：

第一笔：入库成本

GraphRAG 要对每份文档做实体抽取、关系抽取，再跨文档做社区聚类和摘要。

而且传统知识图谱用「主体-关系-客体」这种三元组来表达关系，可现实事件几乎都是多元的：

一笔交易涉及买方、卖方、产品、金额、时间好几个主体，硬拆成两两的三元组，语义被切碎，冗余还成倍增加。

五亿份文档，光建图就是一笔可观的钱，还要扛住三元组拆分的误差累积。

第二笔：增量成本

企业文档每天都在变。GraphRAG 的全局图谱一旦某份文档变了，社区结构就可能跟着变，理论上得重新聚类。实践中没人真重跑，于是图谱和现实越漂越远，知识库变成「永远停留在上周三」的快照。有句话说得很准：当数据持续演化时，维护一张全局图的开销，甚至可能超过初始构建。

第三笔：私有化成本

这个最要命。金融、医疗、政务、法务的数据不能出域，可 GraphRAG 那几轮重型抽取，要么依赖很强的云端大模型，要么得在内网私有部署一个足够强的模型来扛。无论哪种，都是钱和合规的双重压力。

三条加起来，就是企业里那句最常见的吐槽：

「GraphRAG 我们试过，效果好是好，就是用不起、改不动、上不了线。」

HippoRAG 2

HippoRAG 2通过知识图谱、Passage Node 和 Personalized PageRank 将传统向量检索升级为“关联记忆检索”，在多跳推理（Multi-hop Retrieval）、跨文档关联和复杂上下文理解场景下明显强于传统 RAG。

HippoRAG 2 本质上是在向量检索之外增加了一层“长期记忆网络”，解决的是关联推理问题，代价是引入了图构建、实体对齐和记忆维护等额外复杂度。

HippoRAG 2 在检索效率和推理能力之间找到了一个不错的平衡点，用较低的索引成本获得了接近图推理系统的效果。但对于企业场景来说，认知图谱仍然需要持续构建和维护，面对长期增量数据时，系统复杂度并没有完全消失。

![Image](https://pbs.twimg.com/media/HLBQ4-JbUAAY3BY?format=jpg&name=large)

#### SAG 的判断：把结构搬进检索本身

既然病根是「结构建了却用不上」，解法就清楚了——把结构化能力搬进检索执行本身，别在离线阶段把结构建死。

![Image](https://pbs.twimg.com/media/HLBQ_kgakAEJ8v7?format=jpg&name=large)

在离线阶段，每个数据块被转换为一个事件和一组实体，并写入 SQL、向量和全文索引。

在在线阶段，系统执行初始召回，然后进行查询时扩展，最后在压缩后的候选集中完成选择。

SAG 的核心结构很简单。对每个文档切片，它只抽两样东西：

一个事项（event）保留这个切片的完整语义，一组实体（entities）负责索引和桥接。

chunk -&gt; event # 一个完整事项，保留语义 chunk -&gt; entities # 多个实体，负责索引 event &lt;-&gt; entities # 事项和实体之间多对多连接

理解它的关键在于：

事项和实体是对同一个切片的两类并列结果。

事项承载语义，实体只做索引和桥接，

两者通过数据库的关联查询连起来。

一个事项关联着好几个实体（人物、时间、地点、组织、产品……），这本来就是一张天然的关系网。

这就是 SAG 和 GraphRAG 最根本的区别。

GraphRAG 是「预先把整张图画好贴在墙上，谁动一下都得重画」；

SAG 是「查询的时候，根据这个问题，从命中的实体出发，沿着事项-实体的连接，临时算出一条链路」。

用企业能听懂的话说：

GraphRAG 像一家公司花半年画了一张巨型组织架构图贴在墙上，谁调岗都得重新画；

SAG 像一个查询系统，你问的时候它现查现算，「张经理 → 他去年签的客户 → 那客户今年的续约」这条线是按需长出来的，不动那面墙。

![Image](https://pbs.twimg.com/media/HLBRMcHa0AAFqtf?format=jpg&name=large)

更妙的是，SAG 的多跳扩展就是数据库的关系扩展，靠 SQL 的关联查询，沿着共享实体在不同事项之间跳过去，默认只跑一跳。

它不需要图数据库那套重家伙，一个会做表连接的数据库就够。

![Image](https://pbs.twimg.com/media/HLBRTFUbYAA_Vph?format=jpg&name=large)

#### 三个角色各司其职：SQL、向量、LLM 谁干什么

SAG 还有个务实的设计：

把检索流水线拆成三个角色，各干各的活，谁都不越界。

SQL 负责确定性的过滤和连接——实体与事项的关联、多跳扩展，全靠数据库的关系查询，精确、可解释、便宜。

向量检索负责语义扩展——别名、近义词，比如「张经理」和「老张」、「续约」和「续签」，靠向量相似度桥接。LLM 只在最后压缩过的候选集上做一次精排——前面两路把候选从几十万压到一百个之后，它才出场。

这正好对应企业的成本账。

过去很多 RAG 动不动就把 LLM 塞进检索主路径，每一步都问模型、每一步都花 token。

SAG 反过来：能交给 SQL 的绝不交给模型，把贵的调用往后压，用在刀刃上。

还有个取舍值得说：

SAG 在实体处理上故意「够用即可」——只做简单字符串归一和查重，不追求完美的实体对齐。

这听起来像偷懒，其实很清醒：

真正承载语义的是事项，实体只是个「能桥接就行」的路标。

与其花大力气做完美实体对齐（GraphRAG 在这上面烧了不少钱），不如把预算省下来。

#### 硬证据：跑分到底高在哪

在三个标准多跳问答数据集上，用相同配置（bge-large-en-v1.5 + qwen3.6-flash）和公认强基线 HippoRAG 2 对比：

![Image](https://pbs.twimg.com/media/HLBRb7aakAA7QDZ?format=png&name=large)

MuSiQue 是公认最难的多跳数据集，SAG 把 Recall@5 从 65.13% 拉到 80.04%，绝对提升接近 15 个百分点。

三集平均 Recall@2 提升了 11.16 个点，相对提升约 16.4%。

这里有个细节值得企业的人多看一眼：

提升最猛的是 Recall@2，也就是「只检索两条就命中关键证据」的能力。

这直接意味着 Agent 能用更少的上下文、更早地把证据喂给模型——

在企业里这就是省钱，更少 token、更低延迟、长任务里更少被无关上下文干扰。

![Image](https://pbs.twimg.com/media/HLBRiMzbMAEgHsV?format=jpg&name=large)

还有一个对照实验很说明问题。

把 embedding 换成更强的 NV-Embed-v2，MuSiQue 的 Recall@5 进一步到 81.71%，

HippoRAG 2 换上同模型是 74.55%。

换更强的模型当然能涨，但 SAG 的领先依然在。

这说明它的收益主要来自结构设计——对要私有化部署、模型选择受限的企业来说，这点很关键。

SAG 的强项是真正需要长链条、跨文档串联的多跳——而这恰好是企业里最难、最值钱的那类问题。

![Image](https://pbs.twimg.com/media/HLBRnzTb0AA2YRw?format=jpg&name=large)

#### 能不能在企业里真跑起来：看代码和规模

体验地址：

[https://wiki.zleap.com/search](https://wiki.zleap.com/search)

![Image](https://pbs.twimg.com/media/HLBRuicbEAAZe16?format=jpg&name=large)

跑分是研究的事，企业只认一件事：

这套东西能不能在自己机房里、自己数据上、自己模型上跑起来。

SAG 给了两个仓库。

一个是配套的 Benchmark 复现代码（

github.com/Zleap-AI/SAG-Benchmark），带版本管理、带实验记录，是把评测脚本原样开源：

> \# 上传数据集：把评测数据转成语料库，写入数据库和 ES uv 运行 Python scripts/run\_upload.py --数据集 musique # 执行复现 benchmark：多路径召回 + 多跳扩展 uv 运行 python scripts/run\_search\_benchmark.py --dataset-name musique \\ --策略 多 \\ --top-k 10 \\ --k-values "1,2,5,10" \\ --最大并发数 10

复现脚本支持 MLflow 记录实验、支持固定数据源版本，输出 Recall、Precision、F1 完整评估。

可复现、可对账、可追溯，这是企业技术评审愿意看到的。

另一个是开箱即用的本地工作台（

github.com/Zleap-AI/SAG）

技术栈是 TypeScript 全栈，数据层用 PostgreSQL + pgvector + 全文检索 + SQL 多跳，

模型侧兼容 OpenAI-compatible 接口——企业可以用自己私有部署的模型，数据完全不离开内网。

对企业落地，有几个设计尤其对路：

写入以 chunk 为并发单元。

这是「增量」成为原生能力的关键。每个切片独立抽取、独立入库，互不阻塞，等批处理、全局重算都不需要——当天改的合同，当天就能查到。

检索过程全程可视化。

每次提问，右侧面板实时展示走了哪条检索链路、多跳扩展到哪层、每步耗时多少。RAG 出问题时最头疼的是「不知道它为什么这么答」，能看到中间过程就能定位。

MCP 接入，做成 Agent 的数据底座。

工作台可作为 MCP Server 暴露给外部 Agent，企业内部的客服、风控、法务 Agent 共享同一套数据底座，文档抽一遍、多个 Agent 复用，各自存各自的。

是它已经在线上跑着一个约 5 亿条数据规模的 Wikipedia 检索 Demo（

wiki.zleap.com/search），在线检索延迟保持在秒级以内。

PoC 拿两万份文档跑出效果不难，难的是五亿条数据在线上还能秒级响应。

这个规模证明 SAG 的「轻结构」在工程上真扛得住量。

把这几件事拼起来——可复现的 benchmark 脚本、能私有部署的工作台、

5 亿级在线验证、Agent 可复用的数据底座——它就是一份企业技术选型能拿去立项的材料，而远超一个论文里的 idea。

![Image](https://pbs.twimg.com/media/HLBR9o7boAAYOtf?format=jpg&name=large)

#### 它的边界在哪，什么场景别用

第一，它依赖抽取质量。

SAG 的事项和实体是 LLM 抽出来的，模型太弱，抽取一塌糊涂，后面的检索全废。企业在私有化时如果想省钱用很小的本地模型，得先评估它的抽取质量能不能过关。地基不行，结构再巧也没用。

第二，简单场景它未必最优。

前面说过，2WikiMultiHopQA 上它的 Recall@5/10 反而略低。业务绝大多数是单跳、证据集中（比如纯 FAQ、单文档检索）时，普通向量检索甚至 BM25 就够，没必要上多跳结构。SAG 专为跨文档串联的长链条问题设计。

第三，长文档的切片仍是地基。

事项是按切片抽的，切片切得不好，事项就会残缺。这点和所有 RAG 一样，没有银弹。

第四，它需要 PostgreSQL + pgvector 这套基础设施。

比纯向量库（Milvus、Qdrant）重一点，但比 GraphRAG 要的图数据库加全套抽取管线轻得多。对已经用 PG 的企业，几乎零迁移成本。

诚实地说，SAG 要取代的，是那个「企业需要多跳、需要增量、需要私有化、需要扛规模，同时又想摆脱重图建图成本」的特定位置。

而这个位置，恰好是企业落地里最痛、最值钱的那块。

![Image](https://pbs.twimg.com/media/HLBSETWaIAAdtrA?format=jpg&name=large)

#### 回到那个判断

文章开头说，企业 RAG 死在建不动、改不动、上不了规模。深一层看，真正的病根是：

你花了大成本建的结构，查询时根本没被用上。

SAG 给的解法就一句话：把结构化能力搬进检索执行本身，查询时按需长出一条链。

离线只建一层轻量索引，在线用 SQL 把多跳关系现查现算。结构重新变成查询时真正被执行的东西，而不再是挂在墙上的装饰品。

这个判断的可贵之处在于它敢做减法。

整个 RAG 圈这几年的默认动作是「加东西」——加更重的图谱、加更多的社区、加更强的模型。

SAG 反过来问：

真正必要的结构是什么？

能不能用最轻的那一版，把同样的事干成？

答案是能，而且跑分更好。

对企业技术选型的人来说，这里有个更实际的启示。

过去选 RAG 方案，主要看跑分和精度。

但真实的企业项目里，决定方案能不能活到第二年的，是建图成本、增量时效、私有化能力、规模上限这些东西。

跑分决定 PoC 漂不漂亮，工程指标决定系统活不活得下去。

我甚至觉得这件事还能往前看一步。

事项-实体的索引结构这么轻、又能持续增量写入，它天然适合做长期运行 Agent 的记忆底座——

带版本、带时间感知，能记住 Agent 三个月前查过什么、状态怎么演化的。

这或许是 RAG 之外，这套结构更远的想象空间。

但那都是后话。

眼下能确定的是：

RAG 下一轮的进步，大概率来自这种「把该重的地方重、该懒的地方懒」的拓扑取舍。

它代表的是一个方向，值得每个在企业里做 RAG 的人认真看一眼。

## 解读（1）

### 2026-06-18 11:42:22

#### SAG 深度总结与解读

##### 一句话总结

**SAG 的核心价值：不再提前构建沉重的全局知识图谱，而是在查询时用 SQL 动态“长出”多跳证据链，从而在多跳问答、增量更新、私有化部署和大规模数据上，比传统 GraphRAG 更轻、更快、更便宜。**

---

##### 1. 深度总结

###### 1.1 企业 GraphRAG 的真实痛点

GraphRAG 在 PoC 阶段效果很好，但一旦进入企业级生产环境，问题会迅速暴露：

| 问题 | 表现 |
|---|---|
| 建图太贵 | 大规模文档需要实体抽取、关系抽取、社区聚类，成本极高 |
| 更新太慢 | 文档一变，全局图谱可能需要重新维护 |
| 私有化困难 | 强依赖大模型抽取，敏感数据不能轻易出域 |
| 查询脱节 | 离线建了复杂图，但在线检索时未必真正使用图结构 |
| 多跳不稳 | 一步召回错，后续推理全错 |

文章认为，GraphRAG 的根本问题不是“没有结构”，而是：

> **结构建得很重，但查询时没有真正用起来。**

---

###### 1.2 SAG 的核心思路

SAG，即 **SQL-Augmented Generation**，走了一条反直觉路线：

> 不预先构建庞大全局图，而是把结构化检索能力放进 SQL 查询过程里。

它对每个文本切片只抽取两类信息：

```text
chunk -> event      # 一个语义完整的事项
chunk -> entities   # 一组实体，用于索引和连接
```

然后通过数据库关系表建立连接：

```text
event <-> entities
```

查询时，SAG 先找到相关事项和实体，再通过 SQL join 沿着共享实体扩展出多跳证据链。

也就是说：

> **GraphRAG 是提前画好整张图；SAG 是查询时按需生成局部图。**

---

###### 1.3 SAG 的三层分工

SAG 的工程设计很务实：

| 模块 | 作用 |
|---|---|
| SQL | 做确定性过滤、连接、多跳扩展 |
| 向量检索 | 处理语义相似、别名、近义表达 |
| LLM | 只在压缩后的候选集上做精排和生成 |

这背后的原则是：

> 能用 SQL 做的，不交给 LLM；能便宜解决的，不用昂贵模型调用。

因此 SAG 把 LLM 从检索主路径中“后移”，降低 token 成本和延迟。

---

###### 1.4 为什么它适合多跳问答？

企业中的复杂问题往往不是单点检索，而是链式检索：

```text
张经理 -> 去年签约客户 -> 今年续约情况
```

普通向量检索只能找“语义相似片段”，但无法稳定组织证据链。

SAG 通过：

```text
事项 A 关联实体 X
实体 X 连接事项 B
事项 B 关联实体 Y
实体 Y 连接事项 C
```

让检索过程具备“顺藤摸瓜”的能力。

这不是靠 LLM 猜，而是靠数据库关系查询确定性地扩展。

---

###### 1.5 实验和工程结果

文章中提到的关键结果：

| 指标 | SAG 表现 |
|---|---|
| MuSiQue Recall@5 | 从 65.13% 提升到 80.04% |
| 三个数据集平均 Recall@2 | 提升 11.16 个点 |
| 更强 embedding 下 | 仍领先 HippoRAG 2 |
| 在线规模 | 支撑约 5 亿条数据秒级检索 |
| 部署方式 | PostgreSQL + pgvector + 全文检索，可私有化 |

尤其重要的是 Recall@2 的提升。

因为这意味着：

> 模型只需更少上下文，就能更早看到关键证据。  
> 对企业来说，就是更低 token、更低延迟、更少幻觉。

---

##### 2. 深入浅出解读

###### 2.1 用一个比喻理解 GraphRAG 和 SAG

###### GraphRAG 像什么？

像公司提前画了一张巨大的关系网：

```text
所有人、所有客户、所有合同、所有项目，全都提前连好
```

问题是：

- 数据一变，图要改；
- 图太大，维护困难；
- 真查询时，不一定真的沿图走；
- 建图成本巨大。

###### SAG 像什么？

像一个熟练的档案管理员：

```text
你问张经理相关问题
它先找到张经理
再查他关联过哪些合同
再查合同关联哪些客户
再查客户今年续约记录
```

它不是提前画完整地图，而是：

> 你问到哪里，它查到哪里。

---

###### 2.2 SAG 为什么“不性感但有效”？

因为它没有使用很炫的技术：

- 没有复杂图数据库；
- 没有全局知识图谱；
- 没有重型实体对齐；
- 没有每一步都调用大模型。

它用的是成熟基础设施：

```text
SQL + 向量检索 + 全文检索 + 少量 LLM
```

但这恰恰符合企业需求：

> 企业不需要最炫的架构，企业需要跑得动、改得动、查得准、花得少。

---

###### 2.3 SAG 真正做对了什么？

###### 第一，结构不是离线装饰，而是在线执行逻辑

GraphRAG 的结构常常停留在“建好了”，但查询时没真正发挥作用。

SAG 则让结构直接进入检索路径。

---

###### 第二，只建必要结构

SAG 不追求完整知识图谱，只抽：

```text
事项 + 实体
```

这是一种克制：

> 不构建世界的全部关系，只保留足够连接证据的索引结构。

---

###### 第三，把贵的模型调用放到最后

前面用 SQL 和向量压缩候选集，最后才让 LLM 精排和回答。

这符合企业成本逻辑。

---

###### 第四，天然适合增量更新

每个 chunk 独立处理：

```text
新文档来了 -> 抽 event/entities -> 写入数据库
```

不需要重建全局图。

这对企业非常关键，因为企业数据永远在变。

---

##### 3. SAG 的适用场景

###### 适合用 SAG 的场景

| 场景 | 原因 |
|---|---|
| 合同、法务、风控 | 多主体、多时间、多文档关联 |
| 企业知识库 | 数据量大、更新频繁 |
| 金融、医疗、政务 | 需要私有化部署 |
| Agent 记忆底座 | 需要长期、可追溯、可增量 |
| 多跳问答 | 需要跨文档组织证据链 |

---

###### 不一定适合 SAG 的场景

| 场景 | 原因 |
|---|---|
| 简单 FAQ | BM25/向量检索已足够 |
| 单文档问答 | 不需要多跳结构 |
| 抽取模型太弱 | event/entities 质量决定上限 |
| 文档切片很差 | 事项会被切碎，影响召回 |
| 极轻量系统 | PostgreSQL + pgvector 仍比纯向量库稍重 |

---

##### 4. 我的辩证思考

###### 4.1 SAG 不是“消灭 GraphRAG”，而是纠正过度建图

SAG 的价值不在于证明 GraphRAG 错了，而是指出：

> 不是所有结构都值得提前构建。  
> 不是所有关系都需要全局维护。

GraphRAG 更像“知识工程”路线，适合关系稳定、结构强、治理要求高的场景。

SAG 更像“检索工程”路线，适合数据持续变化、查询多样、规模巨大的企业场景。

二者不是绝对替代，而是不同取舍。

---

###### 4.2 SAG 的核心胜利是工程胜利

很多 RAG 论文追求模型能力和复杂结构，但企业真正关心的是：

```text
能不能部署？
能不能更新？
能不能解释？
能不能控成本？
能不能扛规模？
```

SAG 的聪明之处在于，它没有把问题都交给 LLM，而是重新分配任务：

- 数据库做确定性计算；
- 向量做语义泛化；
- LLM 做最后判断。

这是一种更成熟的 AI 工程观。

---

###### 4.3 但 SAG 仍然不是银弹

SAG 的地基仍然有两个：

```text
切片质量
抽取质量
```

如果 chunk 切坏了，event 就不完整。

如果实体抽取错了，SQL join 就会连错。

所以 SAG 降低了图维护成本，但没有消除信息抽取本身的难度。

它解决的是：

> 如何更轻地组织结构。

不是彻底解决：

> 如何完美理解文档。

---

###### 4.4 未来方向：RAG 会从“重模型”走向“重拓扑”

SAG 给出的启示是：

> 下一代 RAG 的关键，可能不是再换一个更大的模型，而是重新设计信息组织方式。

过去的路线是：

```text
更大模型 + 更复杂图谱 + 更多上下文
```

SAG 的路线是：

```text
轻结构 + 动态连接 + 精准召回 + 延迟调用模型
```

这更接近企业真实需求。

---

##### 5. 最终判断

SAG 的本质是一种“轻图化 RAG”：

```text
不用全局图谱
不用重型图数据库
不用频繁重建
而是用 SQL 在查询时动态构造局部证据链
```

它真正打中的不是学术炫技点，而是企业 RAG 最痛的四个问题：

1. **建不动**
2. **改不动**
3. **用不起**
4. **上不了规模**

如果企业面对的是大规模、强增量、私有化、多跳问答场景，SAG 很值得认真评估。

但如果只是简单 FAQ 或单文档问答，它可能反而过度设计。

---

##### 核心结论

> **GraphRAG 的问题是重结构、轻执行；SAG 的优势是轻结构、重检索。**

> **真正有生命力的企业 RAG，不是 PoC 跑分最高的方案，而是能长期低成本运行、持续更新、稳定解释的方案。**

## 结构化（1）

### 2026-06-18 11:50:26

##### 主旨概括

文章认为，企业级 RAG 的核心痛点不只是“检索不准”，而是 **GraphRAG 这类重图方案建图贵、更新慢、私有化难，且查询时未真正利用图结构**。新开源项目 **SAG（SQL-Augmented Generation）** 通过“轻量离线索引 + 查询时 SQL 动态多跳扩展”，在多跳问答效果、成本和大规模落地上都表现更优。

---

##### 1. 企业使用 GraphRAG 后遇到的真实问题

文章开头用一个企业知识库场景说明问题：

- 初期用 **GraphRAG** 在 **2 万份合同** 上做 PoC，问答效果很好。
- 但当文档增长到 **500 万份** 后，问题集中爆发：
  - 建一次知识图谱要跑一个周末；
  - 研发成本和 token 成本过高；
  - 合规部改一份合同，知识库可能三天后才更新；
  - 数据不能出域，但重型抽取又依赖云端大模型。

这引出三个关键问题：

1. GraphRAG 跑分好，为什么进企业真实场景就变慢、变贵？
2. 多跳问答到底卡在哪里？
3. 有没有既能跑分强，又能支持海量数据、当天增量、私有化部署的方案？

文章认为，SAG 给出了一个新答案：  
**用成熟的 SQL 关系查询能力来做检索增强，而不是提前构建庞大的全局知识图谱。**

---

##### 2. 多跳问答是企业 RAG 的真正难点

企业中最有价值的问题，往往不是单跳检索，而是多跳推理。

例如：

> “上海办公室负责合规的张经理，去年签的那个客户，今年续约情况怎么样？”

这个问题需要串起多份文档中的证据链：

```text
张经理 → 去年签的客户 → 该客户今年续约记录
```

普通向量检索的问题在于：

- 只能找语义相似的片段；
- 很难主动组织出跨文档证据链；
- Agent 多步检索时，前一步漏掉关键实体，后续推理都会偏离。

因此，多跳问答真正需要的是：

> 检索系统能稳定地把分散证据组织成一条链。

文章将几类方案做了对比：

| 方案 | 特点 | 问题 |
|---|---|---|
| Naive RAG | 切块、向量化、Top-K | 快、便宜，但只适合浅层语义匹配 |
| GraphRAG | 预先构建全局知识图谱 | 建图重、更新慢、成本高 |
| HippoRAG 2 | 构建类人“认知图谱” | 多跳强，但仍有图构建和维护成本 |
| SAG | 入库轻量抽取，查询时动态连链 | 更适合企业增量和大规模场景 |

---

##### 3. GraphRAG 的根本问题：结构建了，但查询时没真正用上

文章认为，GraphRAG 最大的矛盾是：

> 离线阶段花大成本建了复杂图结构，但在线查询时并没有真正沿图做多跳推理。

GraphRAG 通常会：

- 抽实体；
- 抽关系；
- 构建全局知识图谱；
- 做社区聚类和摘要。

但实际查询时，很多系统仍然是：

- 在图节点上做相似度检索；
- 或在社区摘要上做匹配。

也就是说，系统看似有图，但查询时并没有真正“走图”。

文章将这个问题称为：

> **结构-检索脱钩。**

企业因此承担三类成本：

###### 3.1 入库成本高

GraphRAG 要对每份文档做实体抽取、关系抽取和跨文档聚类。

而现实业务中的事件往往是多元关系，例如一笔交易可能涉及：

- 买方；
- 卖方；
- 产品；
- 金额；
- 时间。

如果强行拆成“主体-关系-客体”三元组，不仅语义被切碎，还会产生大量冗余和误差。

###### 3.2 增量更新成本高

企业文档每天都在变化。

一份合同更新后，GraphRAG 的全局图谱和社区结构可能都要调整。理论上需要重新聚类，但实际中很难频繁重跑。

结果就是：

> 图谱逐渐落后于真实数据，知识库变成“上周三的快照”。

###### 3.3 私有化部署成本高

金融、医疗、政务、法务等行业的数据不能出域。

GraphRAG 的重型抽取往往需要强模型支持，要么依赖云端大模型，要么在内网部署昂贵模型。

这带来双重压力：

- 成本压力；
- 合规压力。

文章总结企业对 GraphRAG 的典型评价是：

> “效果好是好，就是用不起、改不动、上不了线。”

---

##### 4. HippoRAG 2：强但仍然不够轻

文章也提到 HippoRAG 2 是目前多跳检索的强基线。

它通过：

- 知识图谱；
- Passage Node；
- Personalized PageRank；

把传统向量检索升级为一种“关联记忆检索”。

优势是：

- 多跳推理更强；
- 跨文档关联更好；
- 上下文理解能力优于普通 RAG。

但问题是：

- 仍然需要图构建；
- 需要实体对齐；
- 需要维护长期记忆网络。

所以对企业长期增量场景来说，系统复杂度并没有完全消失。

---

##### 5. SAG 的核心思路：把结构能力搬进检索过程

SAG 的判断很直接：

> 不要在离线阶段把全局图建死，而是在查询时动态生成需要的局部结构。

SAG 对每个文档切片只抽两类信息：

```text
chunk → event      # 一个语义完整的事项
chunk → entities   # 一组用于索引和桥接的实体
event ↔ entities   # 事项和实体之间多对多连接
```

其中：

- **event（事项）**：保留切片的完整语义；
- **entities（实体）**：负责索引和连接；
- 二者通过数据库关系查询连接起来。

这意味着：

- SAG 不预先构建庞大全局图；
- 查询时根据命中的实体和事项，临时扩展出局部证据链；
- 多跳扩展本质上是 SQL 表连接。

文章用一个比喻说明：

- GraphRAG 像提前画一张巨大的组织架构图，人员一变就要重画；
- SAG 像查询系统，用户问到谁，就现场查出相关关系链。

例如前面的企业问题：

```text
张经理 → 去年签的客户 → 今年续约记录
```

SAG 会在查询时通过共享实体和事项连接，动态“长出”这条链，而不是依赖提前维护好的全局图。

---

##### 6. SAG 中 SQL、向量和 LLM 的分工

SAG 的一个重要设计是：  
**SQL、向量检索、LLM 各司其职，不让 LLM 承担所有工作。**

###### 6.1 SQL：负责确定性连接

SQL 用来做：

- 实体与事项的关联；
- 多跳扩展；
- 条件过滤。

优点是：

- 精确；
- 可解释；
- 成本低；
- 工程成熟。

###### 6.2 向量检索：负责语义扩展

向量检索用来处理：

- 别名；
- 近义词；
- 语义相近表达。

例如：

```text
张经理 ≈ 老张
续约 ≈ 续签
```

###### 6.3 LLM：只在最后精排

LLM 不参与每一步检索，而是在候选集被 SQL 和向量检索压缩后，再做最终精排。

这带来的好处是：

- 减少 token 消耗；
- 降低延迟；
- 避免 LLM 调用进入检索主路径；
- 更适合企业大规模部署。

文章认为，SAG 的策略是：

> 能交给 SQL 的，就不要交给大模型；把贵的模型调用放到最后。

---

##### 7. SAG 的跑分表现：多跳检索明显领先

文章引用论文实验数据，SAG 在标准多跳问答数据集上超过强基线 HippoRAG 2。

在相同配置下：

|---|---:|---:|

提升接近 **15 个百分点**。

##### 9. SAG 的局限：并不是所有场景都适合

文章也指出，SAG 不是万能方案。

###### 9.1 依赖抽取质量

SAG 的 event 和 entities 由 LLM 抽取。

如果企业私有化时使用太弱的小模型，抽取质量差，后续检索也会受影响。

###### 9.2 简单场景未必需要 SAG

如果业务主要是：

- 单跳问题；
- FAQ；
- 单文档检索；
- 证据集中；

普通向量检索甚至 BM25 就足够。

SAG 更适合：

> 跨文档、长链条、多跳推理问题。

###### 9.3 长文档切片仍然重要

SAG 的事项是基于切片抽取的。

如果切片切得不好，event 语义会残缺。  
这一点和所有 RAG 一样，没有银弹。

###### 9.4 需要 PostgreSQL + pgvector 基础设施

SAG 比纯向量库稍重，但比 GraphRAG 所需的图数据库和复杂建图管线轻得多。

对于已经使用 PostgreSQL 的企业，迁移成本较低。

```text
离线只建轻量索引；
```

它的价值在于敢于做减法：

- 不追求庞大全局图谱；
- 不把 LLM 塞进每个检索步骤；
- 不做过度复杂的实体对齐；
- 只保留企业多跳检索真正需要的结构。

- 建图成本；
- 增量更新速度；
- 私有化部署能力；
- 规模上限；
- token 成本；
- 可解释性和可维护性。

最后，作者判断 SAG 代表了 RAG 的一个重要方向：

> 把该重的地方做重，把该轻的地方做轻，用更实用的结构设计支撑企业级多跳检索和 Agent 记忆底座。

- 表层现象：

- 推导结论：  
  对持续演化的数据，应该优先选择可局部更新、可按需实例化的结构，而不是重型全局建模。

###### **逻辑三：多跳问答的本质不是语义相似，而是证据链组织**

- 表层现象：  
  普通向量检索在多跳问题上容易到顶。

- 深层原因：  
  向量检索擅长找相似片段，但不擅长稳定串联“实体 → 事件 → 实体 → 事件”的链路。

- 推导结论：  
  企业级多跳检索需要结构化桥接能力；但这种结构不一定要是完整知识图谱，可以是轻量事件-实体索引。

## 深度解读（1）

### 2026-09-18 00:45:42

#### SAG 的价值不只是“用 SQL 替代图”，而是让结构随查询生成

SAG 最值得关注的，不是“刚开源就 SOTA”，也不是 PostgreSQL 扛住了多少数据，而是一种更务实的架构判断：**企业知识库需要的往往不是一张长期正确的全局知识图谱，而是回答当前问题所需的一小段、可执行的证据结构。**

##### 从维护全局真相，转向按需组织证据

SAG 入库时只从每个文本块中抽取两类信息：保留完整语义的“事件”，以及用于连接的实体。查询发生后，再通过共享实体和 SQL Join，把分散事件临时连接成局部超图。例如，“张经理—去年签约—某客户—今年续约”不是预先固化的关系链，而是查询时从相关事件中展开出来。

这不只是“数据库比图数据库便宜”。真正的变化是：**把计算成本从全量数据的持续维护，转移到与当前问题相关的局部范围。** 当数据不断新增、合同频繁修改时，单个切片可以独立更新，不必重新聚类或重建全局图。它因此更适合高增量、强私有化、跨文档问答的企业场景。

这种思路也可以迁移到 Agent 记忆：与其维护一套越来越复杂的“完整世界模型”，不如保存可增量写入的事件及索引，在任务发生时重建相关上下文。不过，长期状态、因果关系和时间冲突能否仅靠事件—实体连接处理，仍有待验证。

##### 它真正减少的是“不必要的智能”

SAG 的另一个可取之处，是明确划分不同组件的职责：SQL 做确定性过滤和连接，向量负责别名与语义近邻，LLM 只对压缩后的候选集精排。它不是简单地少用模型，而是避免让概率模型承担数据库早已擅长的工作。

论文报告称，在 MuSiQue 上，Recall@5 从 HippoRAG 2 的 65.13% 提升至 80.04%；Recall@2 的提升尤其值得关注，因为更少的候选意味着更短上下文和更低干扰。但这里要保持分寸：**检索召回率不等于最终问答正确率，更不直接等于生产成本下降。** 后者还取决于抽取成本、候选长度、查询延迟、缓存命中和生成模型表现。

##### “跑赢 GraphRAG”是一个过宽的结论

文章对 GraphRAG 的批评抓住了真实问题，却有所泛化。不同 GraphRAG 实现并非都“不走图”，而且社区摘要式 GraphRAG 更擅长“整个语料在谈什么”这类全局归纳问题；SAG 更像是在解决实体明确、证据可连接的多跳检索。两者并不完全处于同一任务边界。

同样，“约 5 亿条数据秒级检索”只能证明潜在扩展性，尚不能替代生产证据。选型前至少要验证：这里的“条”究竟是文档、切片还是事件；并发与 P95 延迟如何；增量写入是否影响在线查询；实体重名、别名和时间冲突会造成多大误连；本地小模型的事件抽取质量是否足够。

因此，更可靠的判断不是 SAG 已经取代 GraphRAG，而是：**它提供了一种值得优先验证的中间路线——比纯向量检索更会组织证据，又比全局知识图谱更容易增量维护。** 对企业团队，第一步也不是迁移基础设施，而是统计真实问题中单跳、跨文档多跳和全局归纳各占多少，再用端到端答案正确率、证据可追溯性、更新时效和总成本做同场评测。SAG 是否成立，最终取决于企业问题的“查询拓扑”，而不只是公开榜单。
