- **核心高价值点**：将问题模式和选项描述作为输入，由条件评分头匹配状态与选项，使新增问题或修改选项不必重新训练，但偏离训练分布时仍需验证。
- **留存建议**：精读并存档，作为工作流决策模型的实现与评估参考（包含可复用的决策接口、模式条件评分架构、分阶段训练方法及部署注意事项，与Agent开发直接相关。）

**知识要点**

- 该模型分别编码状态、问题和选项，以零样本相似度先验叠加门控训练修正，支持字符串选项、整数等级和布尔值三类输出。
- 训练采用先冻结编码器训练评分头、再联合微调的两阶段流程；损失结合软标签交叉熵、Brier项和等级距离，并按问题类型拟合校准温度。

#### EmbeddingGemma 2 · typed decisions

![Typed Decision · EmbeddingGemma 2](https://huggingface.co/mrm8488/embeddinggemma-2-ft-typed-decision/resolve/main/eg2td.png)

**EmbeddingGemma 2 fine-tuned for typed decisions**

A **typed decision model**: given the *state* of a workflow (an agent trace, a support ticket, an invoice, a security alert…) and a **schema** of questions, it returns a typed, calibrated answer to each question.

Question type Example Python type of `value`

`choice` What should we do with this trace? → `continue / observe / human_review / stop` `str`

`score` How risky is it? → level `0..3` `int`

`noul` Does it need human review? → probabilistic yes/no `bool`

The head scores the **text of each option** against the state and the question, so the schema is plain data: you can rename options, change descriptions or add new questions without retraining (answers to questions far from the training data are less reliable).

#### Usage

```
from transformers import AutoModel

model = AutoModel.from_pretrained("mrm8488/embeddinggemma-2-ft-typed-decision", trust_remote_code=True)

state = {
    "agent": {"autonomy": "unsupervised", "model": "internal-agent-v2"},
    "task": "Clean up stale feature branches merged more than 90 days ago.",
    "constraints": ["Never delete anything matching release/*", "Do not force-push to any branch"],
    "trace_summary": {"steps": 9, "tool_errors": 1, "constraint_violations": 1,
                      "irreversible_actions": 1, "duration_s": 312.4},
}

questions = {
    "action": {
        "type": "choice",
        "instructions": "What should the observability system do with this trace?",
        "criteria": {
            "continue": "Let the agent proceed without interruption.",
            "observe": "Keep running, but flag the trace for later sampling.",
            "human_review": "Queue this trace for a human to review.",
            "stop": "Halt the agent now.",
        },
    },
    "needs_review": {"type": "noul", "instructions": "Does a human need to review this trace?"},
    "risk": {
        "type": "score",
        "instructions": "How risky is what the agent did?",
        "criteria": ["no risk", "low risk", "significant risk", "severe risk"],
    },
}

answers = model.decide(state, questions, workflow="agent_trace_observability")

for qid, answer in answers.items():
    print(f"{qid:13s} → {answer.value!r:15} ({answer.confidence:.0%})  {answer.probabilities}")
```

Every answer is a `TypedAnswer`:

```
TypedAnswer(
    kind="choice",                  # "choice" | "score" | "noul"
    label="human_review",           # the winning option key
    value="human_review",           # typed: str for choice, int for score, bool for noul
    confidence=0.61,                # calibrated probability of the winning option
    probabilities={"continue": 0.02, "observe": 0.11, "human_review": 0.61, "stop": 0.26},
    expected_level=None,            # score questions only: E[level]
)
```

Use `answer.to_dict()` for JSON. The tokenizer is loaded from the same repo on first use.

##### Schema format

- `choice`: `"criteria": {option_key: description, ...}`
- `score`: `"criteria": [level_0_description, level_1_description, ...]` (lowest to highest)
- `noul`: only `"instructions"`; the answer is `True` / `False` with a probability

##### It works in other languages

EmbeddingGemma 2 is multilingual, so states and schemas don't have to be in English:

```
preguntas = {
    "accion": {
        "type": "choice",
        "instructions": "¿Qué debe hacer el sistema de observabilidad con esta traza?",
        "criteria": {
            "continuar": "Dejar que el agente siga sin interrupción.",
            "observar": "Seguir ejecutando, pero marcar la traza para revisarla más tarde.",
            "revision_humana": "Poner la traza en cola para que la revise una persona.",
            "detener": "Detener el agente inmediatamente.",
        },
    },
    "necesita_revision": {"type": "noul", "instructions": "¿Necesita una persona revisar lo que ha hecho el agente?"},
}
paquita = {
    "agente": {"autonomía": "sin_supervisión"},
    "tarea": "Actualizar los precios del Roscón de Reyes en la tienda online.",
    "resumen_traza": {"violaciones_de_restricciones": 2, "acciones_irreversibles": 1,
                      "notas": "Aplicó un 90 % de descuento a todo el catálogo y envió un correo a 12.000 clientes."},
}
model.decide(paquita, preguntas, workflow="agent_trace_observability")
```

The head was trained on English schemas only, so expect softer probabilities in other languages.

##### GPU and precision

```
import torch

model = AutoModel.from_pretrained("mrm8488/embeddinggemma-2-ft-typed-decision", trust_remote_code=True,
```

Use `bfloat16` (Ampere or newer) or `float32`. **Never `float16`**: EmbeddingGemma 2 overflows and returns NaNs without raising an error.

##### Lower-level API

Method What it does

`model.decide(state, questions, workflow="")` typed answers for one state

`model.encode(texts)` normalized sentence embeddings, exactly as in training

`model.collate(rows)` turns dataset rows `{workflow, state, questions, gold}` into a training batch

`model(**batch)` `GemmaDecisionOutput(loss, logits, probabilities, text_embeds)`

Fine-tuning further with the 🤗 `Trainer`:

```
from datasets import load_dataset
from transformers import Trainer, TrainingArguments

ds = load_dataset("LocalLLaMA/typed-decisions", "all")
trainer = Trainer(
    model=model,
    args=TrainingArguments("out", per_device_train_batch_size=16, learning_rate=2e-5,
                           num_train_epochs=2, remove_unused_columns=False),
    train_dataset=ds["train"],
    data_collator=model.collate,
)
trainer.train()
```

A single learning rate fine-tunes the encoder and the head together; for the two-learning-rate recipe used to train this model, build the optimizer yourself.

#### How it was built

```
state     ──► EmbeddingGemma 2 ─┐
question  ──► EmbeddingGemma 2 ─┼─► field(state, question, type) ─┐
option_i  ──► EmbeddingGemma 2 ─┴───────────────────────────────── ┴─► logit_i

logit_i = prior_i + σ(gate) · (s · cos(field, option_i) + residual_i)
```

- **Encoder:** `google/embeddinggemma-2`, text only, `Classification` task prompt, mean pooling, 768-d, L2-normalized.
- **Input rendering:** the state is flattened into readable `key: value` lines (`trace summary · constraint violations: 1`) instead of raw JSON, which embedding models read much better.
- **Head:** schema-conditioned scorer (\~0.5M parameters). The `prior` term is zero-shot embedding similarity; the trained part is a gated correction on top.
- **Phase 1:** head only, on cached embeddings (encoder frozen).
- **Phase 2:** end-to-end fine-tuning of encoder + head, with two learning rates (encoder 2e-5, head 1e-4), frozen token embeddings, 5 epochs, 32 rows per batch.
- **Loss:** cross-entropy against the annotators' *soft* labels + Brier term + ordinal distance for `score` questions.
- **Calibration:** one temperature per question type, fitted on held-out training rows and stored in the weights.

#### Results

`LocalLLaMA/typed-decisions`, subset `all`, test split (argmax vs gold label, all question types):

Model Test accuracy Soft CE Brier

Phase 1 (frozen encoder) 67.7% 0.968 0.113

**Phase 2 (this model)** **76.4%** **0.887** **0.065**

Per question type (phase 1 → phase 2): `choice` 66.2% → 71.2% · `score` 61.8% → 74.0% · `noul` 77.0% → 84.8%.

Fine-tuning did not hurt the encoder's multilingual alignment: on an English/Spanish probe, the mean cosine of translation pairs went from 0.869 to 0.901, with 100% retrieval@1 before and after.

Hyperparameters were chosen while looking at the test split, so treat these numbers as slightly optimistic.

#### Limitations

- **Soft labels set a ceiling.** Many rows are near-ties between annotators; on those, the gold label is close to a coin flip.
- **Calibration means "matches annotator disagreement".** A 43% answer on a row where annotators split 43/28/25 is correct behaviour, but looks underconfident if you only compare confidence against the majority label.
- **Numbers inside the state are harder** for an embedding model than words; `score` questions are the weakest type.
- **Unseen schemas and languages work, with softer probabilities.** Validate on your own data before relying on them.
- **The rendering of state, questions and options is part of the model.** It lives in `modeling_gemmadecision.py`; changing it changes the predictions.

#### EmbeddingGemma 2：把工作流状态转成带概率的结构化决策

这篇模型说明介绍了一个基于 EmbeddingGemma 2 微调的“类型化决策”模型：输入一段工作流状态，以及你想问的问题和候选答案，模型返回结构化答案及其概率。**它的核心特点是：问题和选项通过文本定义，不必为每套决策规则重新训练模型；但新场景是否可靠，仍需用自己的数据验证。**文档同时说明了模型的实现方式、训练效果和使用限制。

##### 1. 它解决什么问题：把“发生了什么”转成“应该怎么办”

模型面向的是工作流中的判断任务，例如 AI Agent 执行记录、客服工单、发票或安全告警。调用方提供两类信息：

- **当前状态（state）**：任务是什么、有哪些约束、已经发生了什么。
- **问题定义（schema）**：要判断什么、答案是什么类型、有哪些选项，以及各选项的含义。

原文的示例是一段 Agent 操作记录：任务是清理已合并超过 90 天的旧分支，约束是不能删除 `release/*` 分支、不能强制推送；执行摘要中记录了 9 个步骤、1 次工具错误、1 次违反约束和1次不可逆操作。

系统可以针对同一段状态同时提出三类问题：

| 问题类型 | 示例 | 返回值 |
|---|---|---|
| `choice`：选项选择 | 应该继续、观察、人工复核，还是停止？ | 字符串，如 `"human_review"` |
| `score`：有序等级 | 风险属于无、低、显著，还是严重？ | 整数，如 0～3 |
| `noul`：是非判断 | 是否需要人工复核？ | 布尔值 `True` / `False` |

这里的“类型化”，意味着下游程序拿到的是可直接处理的字符串、整数或布尔值，而不是一段需要再解析的自由文本。

每个答案还包含选中项的概率、所有选项的概率；等级问题另有“预期等级”，即按照各等级概率算出的加权平均值。答案可以转成 JSON，便于接入其他系统。

原文给出的返回格式示例是：选择“人工复核”，置信度为 61%；其他选项分别是继续 2%、观察 11%、停止 26%。**这表示模型更倾向于人工复核，而不是宣称其他处理方式完全不合理。**该数字是文档中的格式示例，不应当作独立的效果测试。

##### 2. 为什么能改问题和选项，而不重新训练

传统分类模型往往把类别固定在模型里。例如，训练时只有“通过”和“拒绝”，上线后想增加“人工复核”，通常需要改分类层并重新训练。

这个模型采用了不同做法：**它读取每个选项的文本含义，再结合状态和问题，为选项打分。**因此，候选答案不是一组固定的类别编号，而是调用时提供的数据。

三种问题的定义方式分别是：

- `choice`：提供“选项标识 → 文字描述”的对应关系。
- `score`：提供从低到高排列的等级描述。
- `noul`：只需提供问题说明，模型返回是或否及其概率。

这允许使用者重命名选项、修改描述或增加新问题，而不用立即重训。不过，**接口能接受新问题，不等于模型能可靠回答新问题**：如果问题与训练数据相差很大，结果会更不可靠。选项措辞也不是纯粹的界面文案，它会参与模型计算，修改后可能改变预测。

##### 3. 模型如何做判断：先理解文本，再学习修正选项得分

模型由基础文本编码器和一个约 50 万参数的决策头组成。编码器把文本变成向量——可以理解为便于比较语义的数字表示；决策头负责把这些表示转成答案概率。

###### 状态、问题和选项分别编码

底座是 `google/embeddinggemma-2`。它分别编码状态、问题和每个候选选项，得到经过归一化的 768 维文本向量。

状态也不是直接作为原始 JSON 输入，而是先展开成可读的“字段：值”文本，例如：

> 执行摘要 · 违反约束次数：1

作者认为，这种表达比原始 JSON 更适合嵌入模型理解。

###### 以语义相似度为起点，再进行学习修正

候选答案的基础得分来自无需额外训练的语义相似度；在此之上，模型增加一个经过训练的修正项。

这个修正会结合状态、问题及问题类型，再与候选选项进行比较。模型还有一个“门控”机制，控制修正项对最终得分的影响程度。

通俗地说：**它不是只判断“哪句话看起来最像当前状态”，而是在语义匹配的基础上，学习“这种状态下，这个问题应该怎样判”。**

###### 分两阶段训练，并校准概率

训练分为两步：

1. **先固定编码器，只训练决策头**，使用预先缓存的文本向量。
2. **再联合微调编码器和决策头**，让文本表示也适应决策任务。第二阶段训练 5 轮，每批 32 条；编码器学习率为 `2e-5`，决策头为 `1e-4`，词元嵌入参数保持冻结。

训练目标不仅要求选对答案，还要求输出合理的概率分布：

- 用软标签交叉熵学习标注者对各答案的支持比例，而非只学习一个“正确答案”。
- 用 Brier 损失惩罚概率与标注分布之间的偏差。
- 对等级问题加入顺序距离惩罚，因为把风险 3 判成 2，和判成 0，不应算同样严重的错误。

训练后，模型还为每种问题类型分别拟合一个“温度”参数，用来调整概率分布的尖锐程度。该参数使用留出的训练样本拟合，并保存在模型权重中。

##### 4. 效果有所提升，但测试数字需要打折看

在 `LocalLLaMA/typed-decisions` 数据集的 `all` 子集上，文档报告了以下测试结果：

| 指标 | 第一阶段：编码器固定 | 第二阶段：联合微调 |
|---|---:|---:|
| 总体准确率 | 67.7% | **76.4%** |
| 软标签交叉熵，越低越好 | 0.968 | **0.887** |
| Brier 指标，越低越好 | 0.113 | **0.065** |

按问题类型看，准确率变化为：

- 选项选择：66.2% → **71.2%**
- 有序等级：61.8% → **74.0%**
- 是非判断：77.0% → **84.8%**

这说明，在该数据集上，联合微调既提高了最终答案命中率，也改善了与标注概率分布的匹配程度。

但文档明确披露：**作者选择超参数时查看了测试集，因此这些数字可能偏乐观。**测试集不再是完全独立、未被参考的最终检验，不能直接把 76.4% 当作新业务场景下的预期准确率。

此外，准确率本身也有局限：数据中不少样本的标注者意见接近，所谓“标准答案”只是略占多数的选项。这类样本并没有非常明确的唯一答案，用多数标签衡量模型，会丢失分歧信息。

##### 5. 最关键的理解：这里的“置信度”是在拟合人的分歧

**文档中的概率校准，主要意味着输出概率应当贴近标注者的意见分布，而不等于对客观结果的绝对保证。**

例如，某个问题中，43% 的标注者支持一个选项，其余人支持其他选项。如果模型给这个选项 43% 的概率，按该训练目标，这是合理行为；若只把多数选项当作唯一正确答案，它却可能显得“不够自信”。

这一区别直接影响使用方式：不能只问“模型有没有选对”，还应看它是否表达了样本本身的不确定性。尤其对于人工复核、停止执行等决策，不能仅凭“返回了一个选项”就认定判断已经足够明确。

原文还提醒了几项边界：

- **状态中的数字比文字更难处理。**作者将等级判断列为薄弱环节；它在本次测试中的准确率虽然高于选项选择，也不能因此认定模型擅长数值推理。
- **新问题定义和新语言可以使用，但概率往往更分散。**部署前仍需验证。
- **输入文本的展开方式也是模型的一部分。**状态、问题和选项如何转成文本，实现在 `modeling_gemmadecision.py` 中；改动它可能改变预测结果。

##### 6. 多语言与部署：能用不代表已经充分验证

基础编码器支持多语言，因此状态和问题定义不必使用英语。原文给出了西班牙语示例：一个无人监督的 Agent 给整个商品目录打了九折以上的降价——实际应用了 90% 折扣——并向 12,000 名客户发送邮件，系统据此判断是否需要复核或停止。

但**决策头只在英语问题定义上训练过**，所以作者提示，其他语言的输出概率通常会更分散。

微调后的英西翻译对测试显示，平均余弦相似度从 0.869 升至 0.901，检索第一名命中率在微调前后均为 100%。这支持“该测试中跨语言语义对齐未受损”的判断，**不等于证明其他语言的决策准确率同样可靠。**

实际使用时，有几个关键点：

- 通过 Transformers 的 `AutoModel.from_pretrained(...)` 加载模型，需要启用 `trust_remote_code=True`；首次使用时，分词器从同一仓库加载。
- 高层接口是 `model.decide(state, questions, workflow=...)`，一次对一个状态回答多个问题。
- 也提供文本编码、训练批次整理和底层前向计算接口，可以继续微调。
- 使用 Hugging Face `Trainer` 可以同时训练编码器与决策头；若要复现原模型的两种学习率配置，需要自行构建优化器。

最重要的工程警告是：**使用 `float32`，或在 Ampere 及更新架构的 GPU 上使用 `bfloat16`；不要使用 `float16`。**文档指出，`float16` 会导致 EmbeddingGemma 2 溢出并返回 `NaN`，而且可能不抛出错误——代码看似运行成功，结果却已经无效。

总体而言，这个模型提供了一种可配置的结构化决策接口：用文本定义问题，以语义表示支持灵活选项，再通过训练输出答案和概率。它的价值在于减少固定分类器的僵硬性；它的边界在于，**灵活配置、概率校准和实际业务可靠性是三件不同的事，最后一件仍要靠目标场景的数据验证。**
