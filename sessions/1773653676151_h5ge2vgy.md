#### Symphony

Symphony turns project work into isolated, autonomous implementation runs, allowing teams to manage work instead of supervising coding agents.

Symphony demo video preview

*In this demo video, Symphony monitors a Linear board for work and spawns agents to handle the tasks. The agents complete the tasks and provide proof of work: CI status, PR review feedback, complexity analysis, and walkthrough videos. When accepted, the agents land the PR safely. Engineers do not need to supervise Codex; they can manage the work at a higher level.*

## 结构化（1）

### 2026-03-16 09:33:44

这篇文章主要介绍了 `openai/symphony` 是什么、能做什么，以及如何开始使用它。核心意思是：Symphony 把“盯着代码代理干活”升级成“直接管理任务流”，让团队用更高层级的方式推进项目。

- 第一部分：Symphony 的定位  
  - Symphony 的目标是把项目工作拆成彼此隔离、可自主执行的实现任务。  
  - 团队不需要一直监督编码代理，而是把重点放在“管理要完成的工作”上。  
  - 用通俗的话说，它像一个“任务调度中枢”：发现任务、分配给代理、跟踪结果、最后安全落地。  

- 第二部分：它是怎么工作的  
  - 文中提到一个演示场景：Symphony 会监控 `Linear` 看板，一旦发现任务，就自动拉起代理去处理。  
  - 代理完成任务后，不只是交代码，还会提供“工作证明”，包括：  
    - CI 状态  
    - PR Review 反馈  
    - 复杂度分析  
    - 讲解视频（walkthrough videos）  
  - 当这些结果被接受后，代理可以把 PR 安全合入。  
  - 这说明 Symphony 不只是“写代码”，而是覆盖了从接单、实现、验证到合并的一整套流程。  

- 第三部分：它带来的价值  
  - 文章强调：工程师不需要持续盯着 `Codex` 这类编码代理。  
  - 人的角色从“监督每一步编码细节”转成“在更高层面管理任务和结果”。  
  - 举例来说，以前可能要手动分配任务、催进度、看 CI、审 PR；现在 Symphony 试图把这些环节自动串起来。  

- 第四部分：使用前提与适用场景  
  - 文中指出，Symphony 最适合已经采用 `harness engineering` 的代码库。  
  - 它被描述为下一阶段：从“管理编码代理”进化到“管理待完成的工作”。  
  - 也就是说，如果团队已经有较规范的自动化、验证流程和代理协作基础，Symphony 的价值会更明显。  

- 第五部分：如何开始运行

## 产品-技术开发（1）

### 2026-03-16 09:50:06

这不是一个“更强的 coding agent”，而是把 AI 开发从“人盯代理执行”升级为“系统按工作单元自动编排”。`Symphony` 的核心价值，在于把任务管理、执行隔离、验收证明、合并落地串成一条可运营的交付流水线。

**产品解读**
- 从“监督 AI”转向“管理工作”：产品对象不再是单个 agent，而是 `work item -> run -> proof -> acceptance -> merge` 的闭环。
- 面向团队协作而非个人提效：它监听 `Linear` 这类任务系统，说明入口是团队已有流程，而不是让工程师手动发 prompt。
- 强调“可验收的自动化”：不是只产出代码，而是同时产出 `CI 状态`、`PR review`、`complexity analysis`、`walkthrough video`，本质是给组织一个“可审计的 AI 交付包”。
- 把 AI 开发纳入工程治理：安全合并、隔离运行、任务级自主执行，说明它瞄准的是研发管理和交付效率，不只是代码生成。

**技术架构解读**
- `isolated run` 是系统核心：每个任务独立环境、独立上下文、独立执行轨迹，避免多任务串扰、上下文污染和权限扩散。
- 事件驱动编排：典型链路应是 `任务系统 webhook -> 调度器 -> worker/agent run -> CI/Review/Artifact 汇总 -> 回写任务系统/PR`。
- 多代理不是重点，编排层才是重点：真正壁垒不在“调用哪个模型”，而在任务拆分、上下文注入、状态机、失败恢复、证据归档。
- “proof of work” 是比代码更重要的产物：系统必须能回答“为什么这段改动可信、是否通过验证、风险在哪”。

**设计实现的关键最佳实践**
- **任务状态机先行**：定义清晰状态，如 `queued / preparing / implementing / validating / awaiting-review / accepted / merged / failed`，不要靠日志推断流程。
- **执行环境强隔离**：每个 run 使用独立分支、临时工作区、最小权限凭证；理想形态是容器或远程沙箱，而不是共享本地 runner。
- **上下文分层注入**：给 agent 的上下文分成三层：任务描述、仓库规则、局部代码上下文。避免把整个仓库和所有历史对话都塞进去。
- **验收标准结构化**：任务卡必须带 `目标 / 非目标 / 验收条件 / 风险约束`，否则 agent 很容易“写了很多，但没解决问题”。
- **先验证后提交**：实现链路应固定为 `code -> test -> static analysis -> PR comment -> human/auto gate -> merge`，不要让 agent 直接落主分支。
- **失败可恢复**：运行失败后要保留中间产物、日志、diff、模型推理摘要，支持重试和人工接管，而不是整条链路重跑。

**一个推荐的落地架构例子**
- 入口层：监听 `Linear/Jira/GitHub Issues`，只消费带明确标签的任务，如 `ai-ready`。
- 编排层：调度器读取任务模板，生成 run plan，分配到对应 worker。
- 执行层：worker 拉代码、创建分支、调用 coding agent 实现。
- 验证层：自动跑 `unit test / lint / type check / integration smoke test`。
- 证据层：生成 `PR 描述`、测试结果、风险说明、变更摘要、必要时录制 walkthrough。
- 治理层：根据规则自动合并，或进入人工审批。

一个简化流程可以是：

```text
Linear任务进入“In Progress”
-> Symphony创建隔离run
-> agent读取任务+仓库规范+相关代码
-> 生成改动并提交分支
-> CI执行测试和静态检查
-> 自动生成PR与变更说明
-> Review bot给出风险与复杂度分析
-> 满足门禁后自动merge
-> 回写Linear状态与结果
```

**产品经理视角的最佳实践**
- 不要一开始就做“全自动”，先从低风险任务切入：测试补全、文档更新、小型 CRUD、内部工具。
- 任务模板化比模型升级更重要：高质量任务卡能显著提升成功率。
- 先定义“不允许 agent 做什么”：例如数据库 schema 破坏性变更、支付逻辑、权限系统核心路径。
- 用 SLA 管理 AI 执行：如“30 分钟内产出 PR，失败自动转人工”，而不是无限重试。

**工程实现视角的最佳实践**
- 仓库必须有“机器可读规范”：如 `CONTRIBUTING.md`、测试命令、代码风格、模块边界说明。
- 提前建设 harness engineering：标准启动命令、可重复测试、确定性脚本、无交互式依赖，这是 Symphony 能跑起来的前提。
- 观测性必不可少：每个 run 记录 `输入任务、使用上下文、执行步骤、token/耗时、测试结果、失败原因`。
- 合并门禁要硬编码：例如必须 `CI 通过 + 无高危 review finding + owner approval` 才能 merge。

**一个高质量任务卡示例**
```text
标题：为订单页增加“导出 CSV”功能

目标：
- 用户可在订单列表页导出当前筛选结果为 CSV

非目标：
- 不做异步导出
- 不支持超大数据量分片下载

验收条件：
- 保持现有筛选条件生效
- CSV 包含订单号、用户、金额、状态、创建时间
- 前后端测试通过
- 不影响现有分页性能

约束：
- 复用现有权限校验
- 不新增第三方导出库
```

这种任务比“给订单页加导出功能”更适合 Symphony，因为 agent 能直接围绕验收条件执行。

**你可以如何判断 Symphony 是否值得引入**
- 适合：任务流标准化、PR/CI 流程成熟、代码库测试基础较好、有大量中低复杂度工程任务。
- 不适合：需求高度模糊、测试体系薄弱、部署流程混乱、代码库缺少明确边界和规范。

**本质判断**
- `Symphony` 代表的不是“AI 写代码工具”，而是“AI 原生研发操作系统”的早期形态。
- 它最值得关注的地方，不是 Elixir 实现本身，而是它提出了一个新单位：不是管理 agent，而是管理 work。

## 产品-最佳实践（1）

### 2026-03-16 09:52:33

可以。基于你给的 `openai/symphony` 内容，我用一个“团队在真实仓库里落地 Symphony”的具体实例，来说明它之上的最佳实践。

**具体实例**

假设你们团队有一个 SaaS 产品仓库，使用 GitHub + Linear 管理需求，仓库里已经有基础 CI。  
你们希望用 Symphony 实现这样的工作流：

- Linear 上新建任务：`API-142 为用户资料接口增加头像上传能力`
- Symphony 监听到该任务后，自动启动一个隔离的实现 run
- Agent 在隔离环境中完成：
  - 修改后端上传接口
  - 增加权限校验
  - 补充单元测试和集成测试
  - 运行 CI
  - 提交 PR
  - 附上 proof of work：测试结果、复杂度分析、review 反馈、变更说明
- 人类工程师只做最终验收，而不是全程盯着 agent 写代码

这个实例非常适合 Symphony，因为它不是“让 agent 随便改代码”，而是“把一项边界明确的工作，交给一个可审计、可隔离、可验收的执行单元”。

**在这个实例上的最佳实践**

- 先把任务切小，再交给 Symphony  
  不要直接把“重构用户系统”交给 agent，应该像这个例子一样拆成“给用户资料接口增加头像上传”。最佳实践是让每个任务都有明确输入、明确完成标准、明确影响范围，这样 agent 更容易在一次 run 中稳定完成。

- 为任务写清楚验收标准  
  例如这个任务不要只写“支持头像上传”，而要写成：
  - 支持 `jpg/png`
  - 单文件大小不超过 2MB
  - 只有登录用户可上传
  - 上传成功后返回新头像 URL
  - 补充接口测试  
  Symphony 的价值在于“管理工作”，而不是“猜需求”。验收标准越清楚，run 的成功率越高。

- 强制隔离执行环境  
  这个例子里，每个实现 run 都应该在独立分支、独立工作目录，必要时独立容器中完成。  
  最佳实践不是让 agent 直接在主开发环境里改，而是保证：
  - 不污染开发者本地状态
  - 不互相覆盖改动
  - 出问题时容易回溯
  - 可以并行处理多个任务  
  这正是 Symphony 强调的“isolated, autonomous implementation runs”的核心。

- 把 proof of work 变成硬性输出  
  在这个头像上传任务里，PR 不能只提交代码，还应附带：
  - CI 通过截图或状态
  - 受影响模块列表
  - 测试覆盖说明
  - 风险点说明
  - 如果有 UI，还可附 walkthrough video  
  最佳实践是把这些作为标准产物，而不是可选项。这样团队验收的是“结果 + 证据”，不是“感觉 agent 应该做对了”。

- 让 CI 成为 agent 的第一验收人  
  对这个任务，至少应自动检查：
  - lint
  - unit test
  - integration test
  - 安全扫描或依赖检查
  - API contract 校验  
  最佳实践是让 Symphony 生成的 PR 必须先过自动化门禁，再进入人工 review。否则团队只是在把监督工作从“盯着写”变成“盯着 debug”。

- 限制 agent 的权限边界  
  在这个例子里，agent 应该只拥有完成该任务所需的最小权限，比如：
  - 只访问当前仓库
  - 只可推送到临时分支
  - 不允许直接合并到主分支
  - 不允许访问无关生产系统  
  这是落地 Symphony 时非常关键的最佳实践：自治不等于无限权限。

- 给仓库补齐“harness engineering”基础设施  
  原文里提到 Symphony 最适合已经采用 harness engineering 的代码库。落实到这个头像上传任务，意味着仓库最好已经具备：
  - 一键启动开发环境
  - 一键运行测试
  - 明确的代码规范
  - 可复现的 fixture / seed 数据
  - 稳定的 CI  
  如果这些基础没有打好，agent 不是在实现功能，而是在和环境搏斗。Symphony 的效率会大打折扣。

- 规定 PR 模板，让 agent 输出结构化结果  
  对这个任务，建议 PR 描述固定包含：
  - 任务来源：Linear 链接
  - 实现内容
  - 未实现内容
  - 测试结果
  - 风险与回滚方式
  - 需要 reviewer 特别关注的点  
  最佳实践是让所有 run 的输出格式统一，这样团队可以快速批量审查，而不是每次重新理解 agent 的表达方式。

- 优先选择“可验证任务”，不要一开始就交给高模糊需求  
  “增加头像上传”适合 Symphony，因为结果容易验证。  
  但像“提升用户体验”“优化系统架构”这种抽象任务，不适合直接作为首批自动化工作项。最佳实践是先从：
  - CRUD 接口
  - 测试补齐
  - 明确 bug 修复
  - 文档同步
  - 小型重构  
  这些任务开始，逐步建立团队信任。

- 把人工角色从“监督编码”改成“验收业务结果”  
  在这个例子里，工程师不需要一路盯着 agent 写头像上传逻辑，而应该重点检查：
  - 业务规则是否被正确实现
  - 风险说明是否充分
  - 边界条件是否覆盖
  - 是否符合团队架构约束  
  这也是 Symphony 的核心价值：人类从“过程监督者”转为“结果负责人”。

**这个实例下的一套推荐流程**

你们可以把最佳实践落成一个标准流程：

- 产品或工程负责人在 Linear 创建明确任务
- 任务包含验收标准、影响范围、依赖说明
- Symphony 监听到任务后创建隔离 run
- Agent 在隔离环境中实现、测试、生成 PR
- 系统自动附加 proof of work
- CI 先做第一轮验收
- Reviewer 只审业务正确性、架构一致性、风险控制
- 验收通过后再安全合并

**一句话总结**
