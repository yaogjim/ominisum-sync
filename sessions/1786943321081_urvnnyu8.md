## 分析要点

- **核心高价值点**：把图中的连线直接作为上下文选择协议，使模型将读取的来源、顺序和被排除内容在生成前可见、可编辑且可追溯。
- **留存建议**：保留其可视化上下文协议的产品思路，具体工具效果需另行验证（将节点连线直接定义为模型上下文的设计具有复用价值，可用于研究型对话、Agent工作流和AI产品交互设计。）
- **不足**：文章主要是产品介绍，缺少技术架构、评测数据、竞品比较和真实使用案例，难以验证实际效果。

**知识要点**

- LLM对话历史不等于实际发送上下文，界面应显式展示每次生成所使用的内容。
- 通过节点和边组织上下文，可以保留无关分支而不让其继续影响后续回答。
- 在问题不变时仅调整上下文并重新生成，可用于观察和复现上下文对答案的影响。

**行动项**

- 在研究或Agent原型中增加生成前的上下文来源、顺序和token预览。
- 用显式边关系控制上下文纳入与排除，并记录每次生成对应的上下文版本。
- 选择一个长对话任务试用该工具，对比线性聊天与图式上下文管理的结果差异。

## 结构化（1）

### 2026-08-17 05:17:46

#### ThoughtDAG：让大模型上下文可见、可编辑

ThoughtDAG 将大模型的上下文呈现为一张可编辑的关系图：**节点承载问题、证据与对话，连线决定哪些内容会被发送给模型**。用户可以在生成回答前检查、调整和复现上下文，避免传统线性聊天中无关内容干扰答案。

##### 1. 传统聊天的困境：记录可见，上下文不可见

- 聊天记录越长，用户越难判断下一次提问时，系统究竟会把哪些内容交给模型。
- 同一段对话可能同时包含研究讨论、临时问题和闲聊，但系统的上下文筛选机制通常隐藏在后台。
- 因此，**问题即使完全相同，也可能因为混入不同上下文而得到不同答案**。

**原文案例：**

在研究讨论中插入“今晚吃什么”的话题后，这段闲聊仍被带入研究总结，导致回答中出现“晚饭可以吃火锅”等无关内容。

##### 2. 核心理念：连线即上下文

ThoughtDAG 用图来直接定义模型的上下文，而不只是整理聊天内容：

- **节点**：保存问题、回答、原文摘录、图片或证据。
- **连线**：决定某个节点是否进入后续生成的上下文。
- **上游关系**：系统沿着连入节点的边查找并排列相关内容，再组成发送给模型的消息。

因此，图不是回答生成后的辅助示意，而是生成前真正生效的**“上下文协议”**。用户能够明确知道：

- 模型将看到什么；
- 为什么会看到这些内容；
- 哪些内容已经被排除；
- 上下文将按什么顺序发送。

##### 3. 从原文展开：保留证据及出处

用户可以直接在原文中选中文字或图像：

- 对选中内容立即追问；
- 将其摘取为独立节点；
- 保留原始出处，方便追溯证据；
- 自主决定该节点是否通过连线进入上下文。

例如，选中“**这个效应只在实验条件下出现**”后，可以继续询问其含义。摘录虽然已保存在画布上，但只有建立相应连线后，才会真正进入模型上下文。

##### 4. 生成前检查：看清来源、顺序和 Token

在生成回答之前，ThoughtDAG 会展示模型本次将读取的内容，包括：

- 上下文来源；
- 内容排列顺序；
- 相关分支；
- Token 使用量。

这样，上下文不再由系统暗中选择。用户可以在提交前发现无关信息，避免它影响最终结果。

##### 5. 编辑与复现：剪掉一条线，再生成一次

用户只需删除某条连线，就能让整条无关分支退出上下文，同时仍将其保留在画布上。

**原文案例：**

- 初始上下文包含“研究问题”“证据 A”和“晚饭话题”。
- 删除晚饭话题对应的橙色连线后，上下文减少了 **47 tokens**。
- 再次发送完全相同的“请用要点总结”，回答不再出现晚饭建议，而是聚焦研究内容：
  1. 记录数据库版本；
  2. 双人独立筛选；
  3. 冲突由第三人仲裁。

这一过程说明：**问题没有改变，只有上下文连线发生变化，答案便随之更新**，而且整个过程可以检查和复现。

##### 6. 主要使用方式

ThoughtDAG 支持以下几种思考与组织方式：

- **展开分支**：沿不同方向继续思考，不必改写原来的路径。
- **排除旁枝**：保留岔路内容，但不让它进入下一次对话。
- **合并思路**：把指定证据和推理路径汇总成新的回答。
- **生成前预览**：确认模型即将看到的完整上下文。
- **追溯来源**：保留摘录出处，明确答案基于哪些材料。

其核心价值可概括为三个特点：**可见、可编辑、可追溯**。

##### 7. 桌面版本与下载信息

ThoughtDAG 提供带本地引擎的桌面应用，无需安装 Node，也不需要使用终端。

- 当前版本：**v0.3.18**

##### 总结

ThoughtDAG 解决的不是“如何把聊天画成图”，而是“如何让用户真正控制大模型的上下文”。它通过节点保存信息、用连线决定上下文，使复杂对话中的证据筛选、分支排除和答案复现都变得直观透明。

## 通俗精炼（1）

### 2026-09-18 10:40:25

#### ThoughtDAG：把大模型上下文变成可编辑、可追溯的图

ThoughtDAG 是一款将对话上下文可视化为有向图的工具。它试图解决长对话中的核心问题：用户通常看得到聊天记录，却不知道下一次请求究竟会把哪些内容发送给模型。其核心理念是“连线即上下文”——图不只是整理信息的画布，而是直接控制模型输入的协议。

##### 用图明确模型会看到什么

用户可以从原文中选取文字或图片，创建保留出处的独立节点，再通过连线决定它们是否进入后续上下文。生成回答前，系统会展示内容来源、排列顺序和 token 用量；随后沿连入节点的边查找上游信息，组合成发送给模型的消息。

因此，用户可以：

- 展开不同思考分支，而不覆盖原有路径；
- 保留旁支内容，但剪断连线使其退出上下文；
- 合并证据与推理路径，生成新的回答；
- 在生成前检查并调整模型实际接收的信息。

##### 上下文变化可以复现和验证

页面用“研究讨论中混入晚饭话题”说明问题：即使提问完全相同，无关上下文也可能改变答案。删除对应连线后，该分支不再发送给模型，示例中上下文减少了 47 tokens，再次生成的总结也不再出现晚饭建议。

这使回答差异能被追溯到具体的上下文变更，而不是交给隐藏的系统逻辑。其产品价值尤其适合研究、证据整理和复杂决策等需要控制信息来源的场景。不过页面主要展示的是产品理念与交互案例，并未提供效果评测。

ThoughtDAG 提供内置本地引擎的独立桌面应用，无需 Node 或终端。当前页面列出 v0.3.18，支持 Windows x64、Linux x64；macOS 版已完成 Apple 签名与公证，历史版本可在 GitHub Releases 获取。
