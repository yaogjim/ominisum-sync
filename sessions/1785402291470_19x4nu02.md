Key Points

• Buzz treats agents as members of your team, so one shared chat becomes the context layer for humans and agents together.

• The harness under any agent swaps freely, and every chat, project, and decision comes along for the ride.

• Globally installed agent skills stay available inside Buzz, so an existing Claude Code setup carries straight over.

• Agents branch, work in parallel worktrees, push to Git hosting on your own relay, and ship live apps end to end.

• Shared compute lets a small team run one local model on one machine and use it from many computers.

• Buzz sits in early preview today, which makes it a strong fit for solopreneurs and small teams iterating fast.

Numbered Section Summaries

1\. Openness as the Real Selling Point

Vinny opens with the line people keep repeating, that Buzz reads as a Slack killer, then redirects to what actually sold him: openness. Buzz ships as an open source app on an open protocol, and that single choice drives nearly every feature we cover.

2\. Agents as First-Class Teammates

Slack invites agents in through integrations; Buzz treats them as members of the team from the start. Vinny shows the default agent roster, then the layer underneath where you edit agents, add new ones, and give each one instructions that work like a system prompt.

3\. Swappable Harnesses and Portable Context

Each agent sits on a swappable harness, so Claude Code, Codex, Goose, or open code slot in underneath on demand. Vinny frames this as the cure for model fatigue: swap the engine, keep every chat and every project you have built with that agent.

4\. Huddles and Live Collaboration With Agents

Buzz includes audio huddles where agents join the call carrying full chat context. The live attempt stays quiet while we record, so we describe how it works and I share why live, spoken interaction unlocks my own creative process better than typed back-and-forth.

5\. Git, Worktrees, and Projects Built In

Agents create feature branches and work in parallel worktrees, keeping your local files intact while several versions get built at once. Buzz also runs its own Git hosting on your relay, which is the server holding your chats and data, so the ambition here reaches past Slack and toward GitHub

6\. From Chat to Shipped App

Vinny asks Buzz for a simple CRM using the Wasp full stack framework deployed to Railway, and gets links, screenshots, and a live app back before he even checks the work. He then shows a tweet leaderboard he built, wired to a public API that posts daily stats into a channel where his agent Fizz analyzes the top performers.

#### 《Jack Dorsey 的 Buzz：是什么、为什么重要、怎么用》精炼总结

Buzz 是 Block 推出的一款**开源、以 AI 代理为核心的团队聊天应用**，常被称为“代理时代的 Slack”。它真正的价值不只是聊天，而是把人、代理、项目和历史对话放进同一个上下文中，让代理能够持续协作、编写代码并交付产品。

##### 1. Buzz 的核心卖点：开放，而不只是“替代 Slack”

- Buzz 是建立在开放协议 **Nostr** 上的开源应用。
- Slack 通常通过“集成插件”接入 AI，而 Buzz 从一开始就把代理视为**正式团队成员**。
- 用户可以添加、编辑代理，并通过类似“系统提示词”的指令，为代理设定角色和职责。
- Buzz 的开放性意味着团队更容易接入外部工具、控制自己的数据，也能降低对单一平台的依赖。

##### 2. 可随时更换代理框架，同时保留全部上下文

- 每个代理底层使用的“运行框架”可以自由切换，例如：
  - Claude Code
  - Codex
  - Goose
  - OpenCode
- 更换框架或模型后，原有的**聊天记录、项目背景、决策过程和工作上下文仍会保留**，不必从头解释。
- 这能缓解频繁切换模型带来的“模型疲劳”：用户可以换更强或更便宜的模型，但不丢失已有工作。
- 已经全局安装的 Claude Code 技能和工具也可继续在 Buzz 中使用，无须重新配置。

##### 3. 代理可以加入语音讨论，并理解完整聊天背景

- Buzz 支持类似 Slack Huddle 的语音会议，代理可以加入通话，并带着整个频道的上下文参与讨论。
- 语音互动尤其适合头脑风暴，因为它比反复打字更接近真实团队协作。
- 不过，节目中的现场尝试没有成功，嘉宾本人也尚未充分测试这一功能，说明它目前仍不够成熟。

##### 4. 内置 Git、分支与并行开发能力

- 代理可以自动创建 Git 功能分支，并在多个 **worktree（独立工作副本）** 中并行开发。
- 例如，团队讨论完落地页后，可以直接让代理同时制作 **3 个不同版本**，互不干扰本地文件。
- Buzz 既能连接 GitHub，也能在自己的 **Relay（中继服务器）** 上托管远程代码仓库。
- Relay 同时承载聊天、数据和代码，因此 Buzz 的目标可能不只是挑战 Slack，也可能覆盖一部分 GitHub 的能力。
- 即使用户不熟悉 Git，代理也能代为处理分支、提交、推送和部署等技术流程。

##### 5. 从聊天直接生成并上线应用

###### CRM 案例

嘉宾只提出了一个简短要求：

> 使用 Wasp 全栈框架创建一个简单 CRM，并部署到 Railway。

代理随后自动完成了：

- 编写应用；
- 将代码推送到远程仓库；
- 部署到互联网；
- 返回访问链接和截图。

最终得到的是一个可运行的 CRM 仪表盘。团队成员还可以继续在同一频道里讨论缺失功能，再让代理根据讨论结果直接修改产品。

###### 对企业的意义

Buzz 可以把聊天中的业务背景直接转换成软件或数字资产。例如：

- 导入客户资料和会议纪要；
- 根据不同客户自动生成个性化提案；
- 将提案制作成网页或内部应用；
- 根据团队反馈继续迭代。

核心变化是：**“讨论—决策—开发—部署”可以在同一个上下文中连续完成。**

##### 6. 推文排行榜案例：把业务数据送回团队频道

嘉宾还制作了一个 Twitter/X 数据仪表盘，用来统计团队发帖表现，包括：

- 发帖数量；
- 曝光量；
- 表现最好的推文；
- 不同内容之间的共同规律。

具体流程是：

1. 用 Buzz 构建全栈数据应用；
2. 为应用创建公开 API；
3. 设置每日工作流，自动读取数据；
4. 将结果发回 Buzz 频道；
5. 让代理 Fizz 分析高表现内容并提出新选题。

分析结果显示：

- 表现最好的两条推文合计获得了**超过 100 万次曝光**；
- 表现较差的一组内容合计约 **8.8 万次曝光**；
- 代理总结出的规律是：**新奇内容带来触达，摩擦或争议带来互动。**

过去这类分析需要手动导出数据、复制到 ChatGPT，再把结果搬回团队工具；Buzz 则让数据、分析和协作始终处于同一个上下文中。

##### 7. 与代理沟通的最佳方式：自然、直接、简短

- 不需要复杂的“提示词工程”，像和普通同事聊天一样即可。
- 代理拥有频道和项目上下文，因此通常能理解简短指令，甚至可以容忍错别字。
- 更有效的做法是：
  - 明确说出目标；
  - 直接指定要分析或交付的内容；
  - 让代理基于已有上下文行动，而不是每次重新介绍背景。

##### 8. 共享算力与本地模型

- Buzz 可以推荐并下载本地大语言模型，还能把一台设备上的模型共享给团队成员使用。
- 例如，一群资金有限的学生创业者，可以共同购买一台性能较强的 Mac Studio、Mac mini 或笔记本，在上面运行模型，再从多台电脑访问。
- 这样能减少昂贵云端订阅的需求，也能利用不断进步的开源模型。
- 它让小团队在模型选择、使用成本和数据控制上拥有更大自主权。

##### 9. 数据所有权、模型选择与平台锁定

文章认为，团队聊天工具已经成为企业的重要“上下文仓库”，其中包含：

- 创意和决策；
- 产品讨论；
- 客户信息；
- 项目历史；
- 团队知识。

传统封闭平台的问题在于，数据很难完整迁移，团队容易被平台锁定。模型服务也有类似风险：

- 今天的高级套餐可能是每月 **200 美元**，未来可能涨到 **2,000 美元**；
- 模型能力、政策限制或可用性可能突然变化；
- 某些模型甚至可能在发布数日后被撤回。

因此，如果企业要把业务建立在 AI 上，就应尽量保留：

- 更换模型的自由；
- 迁移上下文的能力；
- 对数据和算力的控制权。

##### 10. Nostr 与比特币支付的潜在可能

- Buzz 建立在 Nostr 上，而 Nostr 与低成本、快速的 **比特币闪电网络**联系紧密。
- 未来可能出现的场景包括：
  - 代理自动支付模型算力费用；
  - 用户为他人完成的任务付费；
  - 社区成员提供设计、代码或创意后，直接获得小额打赏。
- 例如，某位设计师在 Buzz 社区中提交了优秀 Logo，需求方可以立即用比特币支付报酬。
- 但这只是嘉宾对未来的推测，**当前 Buzz 尚未正式集成该功能**。

##### 11. 代理设置建议：先简单使用，再逐步分工

嘉宾的实用建议包括：

- 无须一开始就创建大量复杂代理。
- 可以把不同代理固定到不同模型：
  - 强模型处理复杂任务；
  - 较轻量模型处理日常工作，避免快速消耗 Token。
- 可创建一个“首席代理官”，专门判断任务应交给谁，例如：
  - 文案代理；
  - 头脑风暴代理；
  - 代码审查代理；
  - 开发代理。
- 全局安装的技能可直接复用，不需要在 Buzz 中重新建设整套工具链。

##### 12. 当前局限：仍处于非常早期的预览阶段

Buzz 目前可能处于 Beta、Alpha 或早期预览阶段，主要问题包括：

- 定时与循环工作流不够稳定；
- 部分功能无法可靠执行；
- 速度通常比直接使用 Claude Code 或 Codex 慢；
- 原因之一是请求需要经过 Relay 服务器往返；
- 暂时不适合复杂、大规模、要求高度稳定的软件工程。

因此，它现在更适合：

- 独立创业者；
- 小型创业团队；
- 快速验证创意的人；
- 开发小型软件和自动化工作流的团队。

##### 13. 小团队为什么值得尝试

- Buzz 支持公开与私密频道：
  - 公共频道可用于用户社区；
  - 私密频道用于内部协作。
- 当用户在公共频道报告 Bug 或提出功能需求时，团队可以直接 @代理，让它基于当前对话立即修复或制作原型。
- 对小型软件公司而言，这能缩短从“用户反馈”到“产品修改”的距离。

##### 结论：还不是成熟的 Slack 替代品，但代表未来工作方式

Buzz 目前尚不足以全面取代 Slack，也不适合复杂企业级开发，但它展现了一种重要方向：未来团队中的 AI 代理可能多于人类成员，而聊天工具将成为人、代理、业务数据和软件项目共享的上下文中心。

文章最终建议创业者和小团队亲自试用。即使最后不采用 Buzz，也能通过体验它理解代理协作、上下文共享和开放模型的价值，并进一步优化现有的 Slack 或 AI 工作流。

#### 文章精炼总结

Buzz 是 Block 推出的一款**开源、基于开放协议、以 AI 智能体为核心的团队聊天工具**。它表面上像“带智能体的 Slack”，但真正的价值在于：聊天上下文、模型、智能体执行框架和数据都能灵活迁移，帮助个人与小团队从讨论直接走向开发、部署和运营。

##### 1. Buzz 的核心卖点不是“取代 Slack”，而是开放

- Buzz 是一款**开源应用**，并构建在开放协议 **Nostr** 之上。
- 与 Slack 通过插件接入 AI 不同，Buzz 从设计之初就把智能体视为团队成员，而不是附加功能。
- 开放架构意味着用户可以自由更换模型、执行工具和部署方式，并降低对单一平台的依赖。
- 因此，Buzz 不只是聊天软件，更像是一个把**沟通、上下文、智能体和软件开发**连接起来的工作平台。

##### 2. 智能体是“正式团队成员”

- Buzz 内置多个默认智能体，用户也可以自行创建、编辑和分工。
- 每个智能体都能配置专属指令，作用类似于系统提示词，例如设置为：
  - 文案写手；
  - 头脑风暴助手；
  - 代码审查员；
  - 负责分配任务的“首席智能体官”。
- 人类成员和智能体共享同一聊天空间，因此智能体可以直接理解团队之前讨论过的需求、决策和项目背景。

##### 3. 可自由更换智能体的执行底座，同时保留上下文

- 每个智能体下面的执行框架（Harness）都可以更换，例如：
  - Claude Code；
  - Codex；
  - Goose；
  - Open Code。
- 更换底层工具后，原来的聊天记录、项目背景和决策不会丢失，能够随智能体一起迁移。
- 这解决了 AI 用户频繁切换模型时需要反复补充背景的问题，也缓解了“模型疲劳”。
- 用户过去全局安装的智能体技能，也能继续在 Buzz 中使用，无须从头配置。

##### 4. 支持与智能体进行语音协作

- Buzz 提供音频 Huddle，用户可以让智能体加入语音会议。
- 智能体进入会议时会携带完整聊天上下文，理论上可以参与实时讨论，而不只是等待文字指令。
- 这种实时交流更适合需要边说边构思、快速激发创意的人。
- 不过，该功能在节目现场没有成功响应，受访者也尚未深入使用，说明它目前仍处于较早期阶段。

##### 5. 将 Git、分支开发和并行任务内置到聊天中

- 智能体可以自动：
  - 创建项目；
  - 建立功能分支；
  - 在多个 Worktree 中并行开发；
  - 推送代码；
  - 部署应用。
- 例如，团队讨论完落地页后，可以要求智能体同时生成 **3 个不同版本**，分别在独立工作区中开发，不影响本地原文件。
- Buzz 可以连接 GitHub，也能把代码托管在自己的 Relay 上。
- Relay 是存储和同步聊天、数据及代码的服务器，因此 Buzz 的长期目标可能不仅是挑战 Slack，还希望覆盖部分 GitHub 的能力。

##### 6. 案例一：从一句需求直接生成并上线 CRM

受访者向 Buzz 提出需求：

> 使用 Wasp 全栈框架创建一个简单 CRM，并部署到 Railway。

智能体随后自动完成了：

- 编写应用；
- 将代码推送到远程仓库；
- 部署到互联网；
- 返回访问链接；
- 提供应用截图和预览。

最终得到的是一个可以实际使用、并能分享给团队成员的 CRM 仪表盘。后续团队只需继续在聊天中讨论缺失功能，再让智能体根据讨论结果修改产品。

这意味着，具备少量技术知识的用户可以从“讨论需求”快速进入“获得线上软件”的阶段，而不必手动处理每个开发步骤。

##### 7. 案例二：用公开 API 构建推文运营闭环

受访者还使用 Buzz 构建了一个 Twitter/X 推文排行榜应用，用于统计：

- 团队发帖数量；
- 推文表现；
- 热门内容；
- 浏览量和互动数据。

具体流程是：

1. 应用通过公开 API 获取推文数据；
2. Buzz 的定时工作流每天读取数据；
3. 数据自动发布到指定频道；
4. 智能体 Fizz 分析高表现推文的共同特征；
5. 团队基于分析继续讨论新的营销方向。

实际分析中：

- 表现最好的两条推文均获得了**超过 100 万次曝光**；
- 表现较差的一组内容合计约 **8.8 万次曝光**；
- 智能体总结出：“新鲜感带来传播，摩擦和争议带来互动。”

过去需要人工导出、复制数据，再粘贴到 ChatGPT 中分析；在 Buzz 里，数据采集、分析和团队讨论都处于同一上下文中，形成持续闭环。

##### 8. 使用智能体时，不需要复杂的提示词

- 受访者认为，当前模型已经能够较好地判断用户意图，不必过度设计提示词。
- 最有效的方式是像与同事交流一样，直接、简短地提出问题。
- 即使有错别字或口语化表达，只要已有上下文，智能体通常也能理解。
- Buzz 还会展示智能体调用了哪些工具、读取了哪些频道及执行了什么步骤，方便用户了解后台过程。

##### 9. 共享算力与本地模型

Buzz 支持下载并运行本地大模型，还可以把一台机器的算力分享给团队成员。

例如：

- 几名大学生或创业者共同购买一台性能较好的 Mac Studio、Mac mini 或笔记本；
- 在这台设备上运行本地模型；
- 其他成员通过各自电脑使用同一个模型。

这样可以减少昂贵订阅的依赖，让小团队共享 AI 能力。随着开源和本地模型逐渐接近 Anthropic、OpenAI 等公司的前沿模型，这种模式可能更有价值。

##### 10. 数据所有权、模型选择与避免平台锁定

- Slack 等封闭平台掌握着团队的大量聊天和决策数据，迁移到其他平台往往困难。
- 但在 AI 工作中，历史上下文是提升模型表现的关键资产。
- Buzz 把上下文作为基础层，让用户可以更换模型、智能体工具和算力来源，同时保留历史信息。
- 这种自由度也有商业意义：今天每月约 **200 美元**的高级 AI 套餐，未来可能涨到 **2,000 美元**；如果企业只能依赖一家模型供应商，风险会很高。
- 对企业而言，能控制自己的数据、工具和模型，是长期可持续经营的重要条件。

##### 11. Nostr 与比特币支付的潜在可能

- Buzz 基于 Nostr，而 Nostr 与比特币闪电网络联系紧密。
- 目前 Buzz 尚未正式集成相关支付功能，但未来可能用于：
  - 智能体购买算力；
  - 用户为他人的工作付费；
  - 社区成员之间打赏；
  - 智能体自动结算任务费用。
- 例如，用户在设计社区中征集 Logo，某位设计师给出优秀方案后，用户可以直接通过闪电网络支付小额报酬。
- 这部分仍属于推测和未来方向，并非现阶段已完善的功能。

##### 12. 设置智能体的实用建议

- 初期不必创建太多复杂角色，先使用默认智能体开始尝试。
- 可以根据任务难度绑定不同模型：
  - 简单任务使用成本较低、速度较快的模型；
  - 复杂推理或开发任务使用能力更强的模型。
- 如果智能体数量增加，可以创建一个负责分派任务的管理型智能体，由它判断应该把工作交给文案、开发、审查或研究智能体。
- 已在 Claude Code 等工具中全局安装的技能，可以继续被 Buzz 调用。

##### 13. 当前局限：仍是早期预览软件

Buzz 目前可能处于 Alpha、Beta 或 Early Preview 阶段，成熟度有限：

- 定时任务和工作流有时无法稳定运行；
- 响应速度可能慢于直接使用 Claude Code 或 Codex；
- 由于需要通过 Relay 与服务器通信，会增加一定延迟；
- 不适合复杂、大规模的软件工程项目；
- 一些新功能仍处于实验状态，需要手动开启。

因此，它目前更适合：

- 独立创业者；
- 快速迭代的小团队；
- 希望用 AI 构建轻量软件的人；
- 大约 **1～10 人**、年营收 **0～1,000 万美元**阶段的创业公司。

##### 14. 小团队为什么值得尝试

- Buzz 支持公开频道和私有频道：
  - 公开频道可以邀请社区用户反馈；
  - 私有频道用于团队内部讨论。
- 用户在公开频道提出 Bug 或新功能后，团队可以直接 @ 智能体，让它开始修复或制作原型。
- 用户反馈、团队讨论、代码开发和部署都在同一上下文中完成，能显著缩短从问题发现到产品迭代的距离。

##### 15. 最终评价：不是成熟的 Slack 替代品，但代表未来方向

- Buzz 目前还不足以全面取代 Slack，也不一定适合所有企业。
- 但它展示了一种未来工作形态：团队中的智能体数量可能多于人类成员，而聊天工具会成为管理上下文、分配任务和交付成果的核心界面。
- 即使最终不长期使用 Buzz，尝试它也能帮助用户理解：
  - 如何把智能体融入团队；
  - 如何组织共享上下文；
  - 如何自动化开发和营销流程；
  - 如何减少对封闭平台的依赖。
- 它同时是开源应用和开放协议产品，社区可以直接参与改进，这可能成为其长期竞争优势。

> **结论：**Buzz 最值得关注的不是“像不像 Slack”，而是它把聊天、智能体、上下文、代码和算力放进了一个开放系统。对于独立创业者和小团队，它已经值得尝试；对于大型或复杂工程团队，则更适合作为探索未来工作方式的实验工具。

#### Buzz：以共享上下文为核心的“代理原生 Slack”

Block 推出的 Buzz 是一款基于开放协议 Nostr 的开源协作应用。它不只是给聊天工具添加 AI 插件，而是把代理视为团队成员，让人、代理、代码和业务数据共享同一套上下文。其真正卖点并非“取代 Slack”，而是模型可替换、数据可掌控、工作流可扩展。

##### 更换模型，不必重建上下文

每个代理都可切换底层执行工具（如 Claude Code、Codex、Goose），历史聊天、项目决策和全局安装的技能仍可继续使用。这试图解决频繁换模型带来的迁移成本和平台锁定。Buzz 还支持与代理进行语音讨论，但视频中的现场演示未成功，实际体验仍待验证。

##### 从团队讨论直接推进到交付

代理可创建 Git 分支、在并行工作树中开发，并部署完整应用。演示中，Buzz 使用 Wasp 框架生成 CRM，部署至 Railway，并返回链接和截图；另一个案例通过公开 API 每日把推文数据写回频道，再由代理分析高表现内容。其价值在于把“讨论—开发—上线—数据反馈”放入连续上下文，减少手工搬运信息。

##### 开放性有潜力，但产品仍很早期

Buzz 可让团队共享一台机器上的本地模型，降低成本并增强数据控制；Nostr 与比特币闪电网络的结合也可能支持代理购买算力或任务支付，但目前只是受访者推测。现阶段工作流不够稳定、响应比直接使用编码代理慢，不适合复杂工程。作者认为，它更适合独立创业者和小团队试用，用来理解“代理多于人类同事”的未来工作方式，而非立即全面替代 Slack。
