#### Intro to Jev + Opus 5.5

At its core, this system runs Opus 5.5 for deep reasoning tasks and routes any smaller tasks through Jev for cheap, fast decisions.

You get the best of both worlds: deep reasoning from Opus and efficiency from Jev.

Jev Handles the Judgments

Jev is a pure decision-making model.

You give it two things:

1. The state: whatever it's looking at (an email, a tweet, a task, a document)
2. The questions: what you want it to judge/score

With this info, Jev can return probabilities and confidence scores (you'll see how this comes in handy in a second).

Jev answers three types of questions:

- Choice: pick one option from a list
- Score: rate something on a scale of \[1-10\]
- True/false: is \[x\] statement true?

![Image](https://pbs.twimg.com/media/HT-Kn24aIAAwJX9?format=jpg&name=large)

Opus 5.5 Handles the Thinking

Opus 5.5 is the best "thinking" model in the world right now.

I like to use it for:

- Writing and editing
- Research
- High-level strategy
- Coding, building tools, scripts, and automations

The only downside is that Opus 5.5 is quite expensive when run daily and on its own.

By adding Jev on top, Opus only sees what actually needs it.

For example: Let's say you're running an Email triage workflow. Instead of having Opus scan thousands of messages from your inbox, Jev can score them by priority and show Opus only the 5 emails worth replying to.

![Image](https://pbs.twimg.com/media/HT-LbeVasAAv0e5?format=jpg&name=large)

Why the Combination Works

The system is essentially:

Jev judges → Opus thinks → Code executes on the backend

1. Jev sorts, scores, filters, and ranks all the data/context coming in
2. Opus 5.5 does the high-leverage work
3. Code carries out the actions: archive, label, schedule, send

By using this system, your outputs are:

- Faster: hundreds of decisions in seconds (Jev)
- Cheaper: Opus only consumes tokens on what matters
- More reliable: Jev returns structured answers

#### How to Build Perfect Workflows

If you want to be successful with routing tasks through both models, there are a few general principles you need to apply to get the best possible outputs:

1\. Map the Workflow Before You Automate It

Before Opus writes a line of code, break the task into steps and label each one:

```text
EXAMPLE: CLEARING YOUR INBOX

Pull unread emails .............. Action (code)
Is this urgent? ................. Judgment (Jev)
Does it need a reply? ........... Judgment (Jev)
Archive the junk ................ Action (code)
Summarise what matters .......... Thinking (Opus)
Draft replies ................... Thinking (Opus)
Send after approval ............. Action (code)
```

2\. Write Atomic Questions

Every Jev question should be very specific and check only one thing. Remember, Jev is not a text-output model; it can only give yes/no answers and a confidence score before routing to Opus.

```text
BAD:  Is this email important?

GOOD: Choice: Urgent, needs reply, FYI, or ignore?
      True/false: Sent by a real person?
      True/false: Asks me to take an action?
      Score: Sender importance (low, medium, high)
```

3\. Give Jev the Right Context

Context is king in this system.

4\. Route by Confidence

```text
High confidence → code acts automatically
Medium confidence → Opus takes a closer look
Low confidence → flagged for you
```

Step 5: Keep Everything in One File

Have Opus put every Jev question and threshold in a single config file, and log every decision with its confidence score. When something goes wrong, you can easily change the workflow.

Step 6: Test Small, Then Schedule

Test your questions in the Playground on a few real examples. Once successful, THEN scale to a full automation inside Claude Code.

A few sample workflows so you can get some ideas of what the system is capable of:

Workflow 1: Inbox Triage + Management

What Jev judges (per email):

- Choice: Ranks emails as urgent, needs reply, or ignore
- True/false: Sorts if an email is from a real person (not automated)?
- True/false: Does this ask \[me\] to do something? (like reply)
- Score: How important is the sender? (low / medium / high)

What Opus 5.5 does:

Reads only the urgent and needs-reply emails, summarises each in one line, and drafts replies in your voice from a Claude Skill for you to approve.

```text
INBOX TRIAGE PROMPT

Using the TypeSafe skill, build an inbox triage workflow for my Gmail.

1. Pull unread emails from the last 24 hours.
2. For each email, ask Jev:
   - Choice: urgent, needs reply, FYI, or ignore
   - True/false: sent by a real person (not automated)
   - True/false: asks me to take an action
   - Score: sender importance (low, medium, high)
3. If Jev is highly confident an email is "ignore", archive it. 
   Label FYI emails. Flag anything with low confidence for my review.
4. For urgent and needs-reply emails, you (Opus 5.5) write a 
   one-line summary and draft a reply in my tone. Do not send 
   anything without my approval.
5. Give me a short digest: what was archived, what needs me, and 
   the drafts.

Put all Jev questions and confidence thresholds in one config file 
so I can review them.
```

Workflow 2: Research Filter

A workflow to get deeper, better-curated research:

(works for any topic)

```text

Using the TypeSafe skill, build a research filter.

My focus areas: [e.g. AI agents, crypto x AI, trading automation]

1. Take the list of links or documents I give you (or pull them
```

#### Opus 5.5 + Jev：用“判断、思考、执行”分工搭建 AI 工作流

文章介绍了一套多模型协作方案：让 Jev 负责大量、简单的分类与评分，让 Opus 5.5 负责研究、写作和复杂推理，再由代码执行归档、打标签等操作。**核心不是让一个模型包办所有事情，而是先筛选，再把昂贵的推理能力用在真正需要的地方。**作者认为这样可以提高速度、降低成本、增强可靠性，但文中没有提供性能测试或成本对比，标题中的“产出提升 10 倍”应视为宣传性表述，而非经过验证的结论。

##### 一、这套系统如何分工，为什么可能更高效？

文章把工作流拆成三个角色：

| 角色 | 负责什么 | 邮件处理中的例子 |
|---|---|---|
| **Jev：做判断** | 分类、评分、筛选、排序 | 判断是否紧急、是否需要回复、发件人是否重要 |
| **Opus 5.5：做深度工作** | 理解、总结、写作、研究、策略和编程 | 阅读重要邮件、总结要点、起草回复 |
| **代码：执行动作** | 调用应用接口，完成具体操作 | 拉取邮件、归档、打标签、发送已批准的回复 |

###### Jev 接收“待判断的内容”和“具体问题”

按照文章介绍，使用 Jev 时需要提供两部分信息：

- **状态或内容**：例如一封邮件、一篇文档、一条推文。
- **判断问题**：希望它对内容判断什么。

它主要支持三类问题：

1. **选择题**：从给定选项中选择，例如“紧急、需要回复、仅供知悉、忽略”。
2. **评分题**：按指定尺度评价，例如内容清晰度或相关性。
3. **真假题**：判断某个说法是否成立，例如“这封邮件要求我采取行动吗？”

输出是结构化结果，并附带概率或置信度。这里的“结构化”意味着程序可以直接读取选项和分数，不必从一段自由文本中猜测模型的意思。

原文后面曾把 Jev 简化为“只能回答是／否”，这与前面的三类能力不一致。更合理的理解是：**Jev 主要用于返回明确的判断结果，而不是撰写长篇内容。**

###### Opus 只处理筛选后值得深入处理的内容

作者将 Opus 用于写作编辑、研究、高层策略，以及代码、工具和自动化开发。作者认为它擅长复杂思考，但每天让它处理所有输入，成本较高。

例如，邮箱里有上千封邮件。如果全部交给 Opus 阅读和分析，会消耗大量输入、输出 token——也就是模型处理文本时计费的基本单位。先让 Jev 筛选，再只把少数值得回复的邮件交给 Opus，可以减少昂贵模型的调用量。

因此，这套方案的收益来自三个环节：

- **速度**：大量简单判断由作者所称更快的 Jev 完成。
- **成本**：Opus 不再深入处理大量低价值内容。
- **流程稳定性**：固定格式的判断结果更容易接入代码，减少解析错误。

**但结构化输出不等于判断正确，置信度高也不等于一定可靠。**这些是方案能否真正落地时必须区分的两件事。

##### 三、工作流能否有效，关键在问题与路由设计

###### 先拆步骤，再自动化

以清理邮箱为例，文章建议先明确每一步由谁负责：

| 步骤 | 负责人 |
|---|---|
| 拉取未读邮件 | 代码 |
| 判断是否紧急、是否需要回复 | Jev |
| 归档无关邮件 | 代码 |
| 总结重要内容、起草回复 | Opus |
| 经批准后发送 | 代码 |

这样拆分可以避免两个问题：用昂贵模型处理简单分类，以及让分类模型承担它不擅长的开放式思考。

###### 每个问题尽量只判断一件事

“这封邮件重要吗？”过于宽泛，因为“重要”可能意味着紧急、来自关键客户、涉及大额资金，或者只是需要本人回复。

文章建议把它拆成具体问题：

- 是否要求我采取行动？
- 是否由真人发送，而不是自动通知？
- 发件人的重要程度如何？
- 应归入哪种处理类别？

这就是“原子问题”：**一个问题尽量只检查一个明确维度，方便测试，也方便定位错误。**

原文对评分格式有些混用：前面提到 1—10 分，示例又使用“低、中、高”。实际实现时，需要统一问题类型、取值和输出格式，避免配置与程序理解不一致。

###### 给模型足够的判断依据

仅给邮件正文，Jev 未必知道谁是关键客户，也不知道哪些事情必须今天处理。

例如，要判断“发件人是否重要”，通常还需要重要联系人名单或相关规则；要判断研究内容是否“新”，通常需要知道已有信息或此前读过什么。这些是对原文“提供正确上下文”的具体解释。

**问题写得再清楚，如果缺少判断所需的背景，模型仍可能给出看似明确但依据不足的答案。**

###### 按置信度决定下一步

文章提出的路由规则是：

- **高置信度**：由代码自动执行。
- **中等置信度**：交给 Opus 进一步检查。
- **低置信度**：标记给用户处理。

作者还建议增加一个“**不确定**”选项，让模型不必强行选择。

需要注意的是，文中没有给出具体阈值，也没有证明置信度与正确率之间的关系。实际使用时，应通过真实样例验证；自动化权限还应考虑操作风险。文章的邮件示例就明确规定：**回复可以自动起草，但未经用户批准不能发送。**

###### 配置集中保存，决定留下记录

把所有 Jev 问题和置信度阈值集中放在一个配置文件中，并记录每次判断及其置信度。

这样一旦发现误归档、错排序等问题，就能回查是问题设计、上下文还是阈值出了问题，而不是在多处代码中寻找原因。先用少量真实样例测试，确认有效后，再扩大规模并设置定时运行。

##### 四、三个示例：邮件、研究和内容改进

###### 1. 邮件分流：批量筛选，重点回复

处理最近 24 小时的未读邮件，让 Jev 判断：

- 属于紧急、需要回复、仅供知悉还是忽略；
- 是否由真人发送；
- 是否要求用户采取行动；
- 发件人的重要程度。

随后按结果分流：

- 高置信度的“忽略”邮件自动归档；
- “仅供知悉”的邮件打标签；
- 低置信度邮件交给用户检查；
- 紧急或需要回复的邮件交给 Opus，生成一句话摘要和符合用户语气的回复草稿。

最后给用户一份简报，说明归档了什么、哪些事项需要处理，以及有哪些待批准的草稿。

**这里要减少的是用户和 Opus 阅读低价值邮件的时间，而不是取消用户对外发送信息时的控制权。**

###### 2. 研究筛选：先排序，再深读

输入一组链接或文档，也可以从保存资料的 Notion 页面读取。Jev 分别判断：

- 与关注领域的相关性；
- 是否包含真正的新信息；
- 是否有具体、可执行的启示；
- 属于新闻、教程、观点还是研究。

把这些结果合成排序，原文要求**相关性的权重是其他因素的两倍**。Opus 只完整阅读前五项，输出一页简报：关键内容、新信息，以及可以采取的行动。

同时展示完整排名，让用户看到哪些资料被筛掉。这样能提高筛选过程的可检查性，但不能保证被排除的资料一定没有价值。

###### 3. 内容评分：定位问题，再针对性修改

用户输入标题、开头或草稿，Jev 检查：

- 主旨是否清晰；
- 表达是否具体；
- 是否引发好奇；
- 是否过于通用，像任何人都能写出的内容。

系统先排序，并展示每份内容在哪些标准上未达标。随后 Opus 重写排名后半部分的内容，**只修正未达标的地方**，再交给 Jev 评分，展示修改前后的差异。

这形成了一个闭环：

**Jev 发现问题 → Opus 修改 → Jev 再检查。**

它适合把内容标准拆成具体维度，而不是只给一个“好／不好”的总评。不过，评分提高仍只是这些标准下的改善，不等于真实读者一定更喜欢。
