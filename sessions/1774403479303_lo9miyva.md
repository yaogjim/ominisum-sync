## 正文

Deep Agents can create subagents to delegate work. You can specify custom subagents in the `subagents` parameter. Subagents are useful for [context quarantine](https://www.dbreunig.com/2025/06/26/how-to-fix-your-context.html#context-quarantine) (keeping the main agent’s context clean) and for providing specialized instructions.This page covers **synchronous** subagents, where the supervisor blocks until the subagent finishes. For long-running tasks, parallel workstreams, or cases where you need mid-flight steering and cancellation, see Async subagents.

#### Why use subagents?

Subagents solve the **context bloat problem**. When agents use tools with large outputs (web search, file reads, database queries), the context window fills up quickly with intermediate results. Subagents isolate this detailed work—the main agent receives only the final result, not the dozens of tool calls that produced it.**When to use subagents:**

- ✅ Multi-step tasks that would clutter the main agent’s context
- ✅ Specialized domains that need custom instructions or tools
- ✅ Tasks requiring different model capabilities
- ✅ When you want to keep the main agent focused on high-level coordination

**When NOT to use subagents:**

- ❌ Simple, single-step tasks
- ❌ When you need to maintain intermediate context
- ❌ When the overhead outweighs benefits

#### Configuration

`subagents` should be a list of dictionaries or `CompiledSubAgent` objects. There are two types:

##### SubAgent (Dictionary-based)

For most use cases, define subagents as dictionaries with the following fields:

Field Type Description

`name` `str` Required. Unique identifier for the subagent. The main agent uses this name when calling the `task()` tool. The subagent name becomes metadata for `AIMessage` s and for streaming, which helps to differentiate between agents.

`description` `str` Required. Description of what this subagent does. Be specific and action-oriented. The main agent uses this to decide when to delegate.

`system_prompt` `str` Required. Instructions for the subagent. Custom subagents must define their own. Include tool usage guidance and output format requirements.  
Does not inherit from main agent.

`tools` `list[Callable]` Required. Tools the subagent can use. Custom subagents specify their own. Keep this minimal and include only what’s needed.  
Does not inherit from main agent.

`model` `str` \| `BaseChatModel` Optional. Overrides the main agent’s model. Omit to use the main agent’s model.  
Inherits from main agent by default. You can pass either a model identifier string like `'openai:gpt-5'` (using the `'provider:model'` format) or a LangChain chat model object (`init_chat_model("gpt-5")` or `ChatOpenAI(model="gpt-5")`).

`middleware` `list[Middleware]` Optional. Additional middleware for custom behavior, logging, or rate limiting.  
Does not inherit from main agent.

`interrupt_on` `dict[str, bool]` Optional. Configure human-in-the-loop for specific tools. Subagent value overrides main agent. Requires checkpointer.  
Inherits from main agent by default. Subagent value overrides the default.

`skills` `list[str]` Optional. Skills source paths. When specified, the subagent will load skills from these directories (e.g., `["/skills/research/", "/skills/web-search/"]`). This allows subagents to have different skill sets than the main agent.  
Does not inherit from main agent. Only the general-purpose subagent inherits the main agent’s skills. When a subagent has skills, it runs its own independent `SkillsMiddleware` instance. Skill state is fully isolated—a subagent’s loaded skills are not visible to the parent, and vice versa.

**CLI users:** You can also define subagents as `AGENTS.md` files on disk instead of in code. The `name`, `description`, and `model` fields map to YAML frontmatter, and the markdown body becomes the `system_prompt`. See Custom subagents for the file format.

#### Structured output

All subagents support structured output which you can use to validate the subagent’s output.You can set a desired structured output schema by passing it as the `response_format` argument to the call to `create_agent()`. When the model generates the structured data, it’s captured and validated. The structured object itself is not returned to the parent agent. When using structured output with subagents, include the structured data in the `ToolMessage`.For more information, see response format.

#### The general-purpose subagent

In addition to any user-defined subagents, Deep Agents have access to a `general-purpose` subagent at all times. This subagent:

- Has the same system prompt as the main agent
- Has access to all the same tools
- Uses the same model (unless overridden)
- Inherits skills from the main agent (when skills are configured)

##### Override the general-purpose subagent

Include a subagent with `name="general-purpose"` in your `subagents` list to replace the default. Use this to configure a different model, tools, or system prompt for the general-purpose subagent:When you provide a subagent with the general-purpose name, the default general-purpose subagent is not added. Your spec fully replaces it.

##### When to use it

The general-purpose subagent is ideal for context isolation without specialized behavior. The main agent can delegate a complex multi-step task to this subagent and get a concise result back without bloat from intermediate tool calls.

#### Example

Instead of the main agent making 10 web searches and filling its context with results, it delegates to the general-purpose subagent: `task(name="general-purpose", task="Research quantum computing trends")`. The subagent performs all the searches internally and returns only a summary.

##### Skills inheritance

When configuring skills with `create_deep_agent`:

- **General-purpose subagent**: Automatically inherits skills from the main agent
- **Custom subagents**: Do NOT inherit skills by default—use the `skills` parameter to give them their own skills

Only subagents configured with skills get a `SkillsMiddleware` instance—custom subagents without a `skills` parameter do not. When present, skill state is fully isolated in both directions: the parent’s skills are not visible to the child, and the child’s skills are not propagated back to the parent.

#### LangChain 子代理（Subagents）要点总结

##### 一、核心概念

Subagent 是主代理（Main Agent）调用的 “分工助手”。  
它的作用不是替代主代理，而是帮主代理处理某一类独立任务，处理完后只返回结果，不把中间过程全部塞回主上下文。

一句话理解：**主代理负责统筹，子代理负责隔离执行。**

---

##### 二、为什么要用子代理

###### 1. 解决上下文膨胀
当代理频繁调用搜索、读文件、查库等工具时，会产生大量中间信息，迅速占满上下文窗口。  
子代理可以把这些细节 “关在自己内部”，主代理只拿最终结论。

###### 2. 提升任务分工效率
子代理适合承担特定领域任务，比如研究、写代码、数据分析等，让主代理专注于高层协调。

###### 3. 支持能力差异化配置
不同子代理可以配不同的：
- 提示词
- 工具集
- 模型
- 技能（skills）
- 中间件

本质上，**子代理是 “隔离上下文 + 专业分工 + 能力定制” 的组合机制。**

---

##### 三、适用场景与不适用场景

###### 适合使用
- 多步骤、信息量大的任务
- 需要专业化指令或专用工具的任务
- 不同任务需要不同模型能力
- 希望主代理保持简洁、聚焦协调

###### 不适合使用
- 简单的一步任务
- 必须保留中间过程上下文的任务
- 子代理带来的额外开销大于收益时

---

##### 四、子代理怎么配置

##### 1. 两种形式
子代理主要有两类：

- **SubAgent（字典配置）**：适合大多数场景
- **CompiledSubAgent（预构建 LangGraph）**：适合复杂工作流

###### 2. 关键配置项
常见字段包括：

- `name`：子代理唯一名称，主代理靠它调用
- `description`：描述子代理做什么，越具体越好
- `system_prompt`：子代理自己的系统提示词，不继承主代理
- `tools`：子代理可用工具，不继承主代理
- `model`：可单独指定模型
- `middleware`：可加日志、限流等能力
- `interrupt_on`：支持特定工具的人类介入
- `skills`：可单独加载技能目录

重点是：**大部分关键能力默认不继承，需按需单独配置。**

---

##### 五、通用子代理（general-purpose）是什么

除了你自己定义的子代理，系统默认还会提供一个 “通用子代理”。

它的特点是：
- 与主代理使用相同系统提示词
- 共享主代理工具
- 默认共享主代理模型
- 会继承主代理 skills

它特别适合一种场景：  
**任务并不需要专业分工，但需要把复杂执行过程从主上下文里隔离出去。**

例如：主代理不用亲自做 10 次搜索，而是把研究任务丢给通用子代理，最后拿回一段总结即可。

如果你自己定义了`name="general-purpose"`，就会覆盖默认版本。

---

##### 六、技能（Skills）继承规则

这里有一个容易混淆的点：

###### 继承规则
- **通用子代理**：默认继承主代理 skills
- **自定义子代理**：默认不继承 skills，必须显式配置

###### 隔离规则
即使配置了 skills，技能状态也是隔离的：
- 父代理看不到子代理加载的技能
- 子代理也看不到父代理内部技能状态

也就是说，**skills 能赋能，但不会共享内部状态。**

---

##### 七、上下文传递机制

###### 1. 默认会传递父上下文
主代理运行时传入的 context，会自动传到所有子代理。

###### 2. 如果要做子代理专属配置
可以用 “命名空间 key” 方式，例如给不同子代理传各自专属参数。

###### 3. 如何识别是谁调用了工具
系统会在元数据里带上`lc_agent_name`，用于区分是主代理还是哪个子代理发起的调用。

这对于：
- 调试 tracing
- 工具行为分支
- 多代理共享工具

都很有用。

---

##### 八、最佳实践

###### 1. 描述要清晰具体
主代理是否会调用某个子代理，很大程度取决于`description`。  
描述越具体，分工越准确。

###### 2. 系统提示词要写细
要明确：
- 工具怎么用
- 输出格式是什么
- 返回结果要多简洁

###### 3. 工具集尽量最小化
只给子代理完成任务所需的工具，能提升：
- 专注度
- 安全性
- 可控性

###### 4. 按任务选模型
不同任务可用不同模型，不必全靠一个模型硬扛。

###### 5. 返回结果要简洁
子代理最好返回 “总结” 而不是 “原始数据”，否则上下文隔离效果会被削弱。

---

##### 九、常见问题

###### 1. 子代理没有被调用
原因通常是主代理觉得自己能做。  
解决方式：
- 把子代理描述写得更明确
- 在主代理提示词中强调 “该类任务要委派”

###### 2. 上下文还是很膨胀
原因通常是子代理返回内容太长。  
解决方式：
- 明确要求返回摘要
- 大数据放文件系统，不直接塞回消息

###### 3. 调错了子代理
原因通常是多个子代理描述过于相似。  
解决方式：
- 在 description 中明确边界和职责差异

---

##### 十、一句话结论

Subagents 的本质价值，不是 “多开几个代理”，而是：

**把复杂执行过程隔离出去，让主代理保持轻量、清晰、可控。**

如果你从产品视角看，它更像是 Agent 系统里的 “组织分工机制”——  
主代理做决策编排，子代理做专业执行，最终提升系统的可扩展性与稳定性。

#### 总结

`Subagents` 是 LangChain Deep Agents 里的“子代理”机制：主代理把某些任务分派给子代理去完成，自己只接收最终结果，不接收中间大量工具调用细节。  
它的核心价值有两点：

- **隔离上下文**：避免主代理被搜索结果、文件读取、数据库查询等大量中间信息“塞满”。
- **专业化分工**：不同子代理可以有不同的提示词、工具、模型和技能。

适合复杂、多步骤、专业性强的任务；不适合简单一步就能完成的任务。

---

#### 通俗解读

##### 1. 子代理到底是什么？

你可以把它理解成“主代理的外包助手”。

- **主代理**：负责统筹、规划、做最后整合
- **子代理**：负责某一块具体工作，比如研究、写代码、分析数据

例如：

- 主代理接到任务：“研究量子计算趋势并输出结论”
- 它不自己做 10 次搜索
- 而是把这件事交给 `research-agent`
- `research-agent` 内部完成搜索、筛选、整理
- 最后只回给主代理一份简洁总结

这样主代理的上下文就不会被大量中间内容撑爆。

---

##### 2. 为什么要用子代理？

文档强调的核心问题是：**上下文膨胀（context bloat）**。

代理一旦频繁调用工具，尤其是：

- 网页搜索
- 文件读取
- 数据库查询

就会产生很多中间结果。如果这些都塞进主代理上下文里，很快就会：

- 占满上下文窗口
- 影响后续推理质量
- 增加成本
- 让主代理“注意力分散”

子代理就是把这些脏活累活关在一个“小房间”里做完，再把结论交出来。

一句话理解：

> 子代理像“隔离舱”，帮主代理只保留有价值的结果。

---

##### 3. 什么时候该用，什么时候不该用？

###### 适合用

- 多步骤任务，过程很长
- 某个领域需要专门提示词或专用工具
- 某些任务更适合换一个模型来做
- 希望主代理专注在协调与决策上

###### 不适合用

- 任务本身很简单，一步就能完成
- 你必须保留完整中间过程
- 使用子代理的额外开销比收益还大

也就是说：

> 复杂任务用子代理，简单任务别硬拆。

---

##### 4. 子代理能配置什么？

文档里最常见的是用字典定义 `SubAgent`。几个关键字段最重要：

- `name`：子代理名字，主代理靠它来调用
- `description`：描述这个子代理擅长干什么，主代理靠它判断该不该调用它
- `system_prompt`：子代理自己的行为说明
- `tools`：它能用哪些工具
- `model`：可选，允许给它单独换模型
- `skills`：可选，给它独立技能集

关键点在于：

- **自定义子代理不会自动继承主代理的提示词和工具**
- 它通常需要你**明确配置自己的 system prompt 和 tools**
- 这样做是为了更强的隔离和专注

---

##### 5. 通用子代理（general-purpose）是什么？

Deep Agents 默认自带一个“通用子代理”。

它的特点是：

- 和主代理使用相同 system prompt
- 使用相同工具
- 默认使用相同模型
- 会继承主代理技能

它适合的场景不是“专业分工”，而是：

> 只是想把复杂过程隔离出去，不想让主代理上下文变脏。

比如主代理把“研究某个主题”交给 `general-purpose`，子代理做完后只回一段总结。

如果你自己定义了一个名字叫 `general-purpose` 的子代理，就会**覆盖默认那个**。

---

##### 6. 技能（skills）和上下文是怎么继承的？

这部分比较容易混。

###### 技能继承规则

- **通用子代理**：默认继承主代理技能
- **自定义子代理**：默认**不继承**
- 如果想给自定义子代理技能，要单独写 `skills`

而且技能状态是**隔离的**：

- 主代理看不到子代理加载的技能
- 子代理也拿不到主代理的技能状态

###### 上下文传递规则

运行父代理时传入的 `context`，会自动传给所有子代理。

如果你想给某个子代理单独配置参数，文档建议用**带前缀的命名空间 key**，比如把 key 写成某个子代理专属名字开头。

这相当于：

- 全局上下文可以共享
- 个别子代理的配置可以“分命名空间”管理

---

##### 7. 怎么知道是谁调用了工具？

文档提到一个很实用的元数据：`lc_agent_name`

它会标识当前是哪个代理在运行或调用工具。用途包括：

- 区分 tracing 里是哪一个代理执行的
- 同一个工具被多个代理共享时，判断是谁在调用
- 做针对某个子代理的特殊逻辑分支

这对调试和观测很有帮助。

---

##### 8. 最佳实践有哪些？

文档给出的建议很实用，核心可以浓缩成 4 条：

###### 说明要写清楚

`description` 要具体，不要模糊。  
因为主代理就是靠这个判断该把任务交给谁。

###### 提示词要写细

`system_prompt` 里要明确：

- 如何使用工具
- 输出格式是什么
- 最终返回结果要多简洁

###### 工具要少而准

不要把一堆无关工具全塞给子代理。  
工具越少：

- 越聚焦
- 越安全
- 越不容易乱调用

###### 返回结果要简洁

子代理应该返回“总结”而不是“原始材料堆”。

否则虽然用了子代理，主代理上下文还是会膨胀。

---

#### 我的意见

我认为这套设计非常实用，尤其适合中大型 Agent 系统。

##### 优点

- **非常符合工程实践**：把复杂任务拆分、隔离、职责单一，和软件架构思路一致
- **能明显缓解上下文污染**：这是多工具 Agent 系统里最常见的问题之一
- **方便做专业分工**：研究、分析、写作、代码等任务可以各自优化

##### 需要注意的点

- **不要滥用**：如果任务简单，增加子代理只会让系统更复杂
- **描述不清会选错代理**：主代理能不能正确分派，很依赖 `description`
- **如果子代理返回不够简洁，隔离效果会打折**
- **继承规则要搞清楚**：尤其是 tools、system prompt、skills，不要想当然

##### 我的建议

如果你在做 Deep Agents，我建议这样用：

1. **先只设一个通用子代理**，解决上下文膨胀问题  
2. **再按场景拆专业子代理**，比如 research / code / analysis  
3. **每个子代理只给必要工具**  
4. **强制要求返回摘要而非原始内容**  
5. **用 `lc_agent_name` 做 tracing 和调试**

一句话结论：

> 子代理最有价值的地方，不只是“分工”，更是“让主代理保持清醒”。
