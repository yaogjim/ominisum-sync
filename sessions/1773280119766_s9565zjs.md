## 分析要点

- **核心高价值点**：最有价值的是把Qwen 3.5缓存失效拆解为“模型架构限制 + 服务端缓存实现 + 模板/工具渲染差异”三层问题，而不是简单归咎于单一框架Bug。
- **留存建议**：短期参考后可归档（内容聚焦于特定模型和推理框架的缓存问题，适合在本地部署或性能排障时作为案例备查。）

**知识要点**

- Qwen 3.5在MLX下的缓存失效与Mamba/SSM类不可裁剪缓存有关，导致多轮对话难以高效复用前缀。
- reasoning模型会在缓存键中引入不会被后续请求重放的推理token，造成前缀早期分叉和低效命中。
- 工具调用的JSON字段顺序和Jinja模板渲染差异会破坏提示词稳定性，从而让Prompt Cache失效。
- 社区临时修复包括调整checkpoint位置、排序tool/args键、定制chat\_template，但仍非彻底官方解法。

**行动项**

- 如果你在Apple Silicon本地跑Qwen 3.5，可优先检查是否存在工具参数顺序变化、thinking标签漂移和模板不一致问题。
- 对比测试GLM等替代模型在相同工作流中的缓存命中与响应延迟，评估是否临时切换模型更划算。
- 在自建推理服务中尽量固定system prompt、tool schema和序列化顺序，减少前缀不稳定带来的重复prefill。
- 关注mlx-lm相关Issue和后续PR，待官方对混合缓存/分层缓存机制完善后再决定是否长期采用Qwen 3.5本地部署。

So the lru prompt cache leaves the cache in memory when trimming. That was meant as an optimization since you can fork conversations for free.

**SlimG** commented on 3/8/2026

I have the same issue with mlx-lm 0.31.0 and Qwen3.5-35B-A3B-4bit, using OpenCode 1.2.13 as client.  
I am not a proficient programmer, but I've done my due diligence with troubleshooting this issue, and I find it difficult to wait, so I had Claude (Opus 4.6) analyze the problem to make me a temporary fix that seem to work for me during testing. I'm sharing it here for any other impatient soul who can't wait to get their hands on Qwen3.5 😉

Claude's analysis of why the checkpoint mechanism in PR [#911](https://github.com/ml-explore/mlx-lm/pull/911) doesn't help Qwen3.5:

> The checkpoint cache is stored with a key that includes the last user message content. When the client sends request [#2](https://github.com/ml-explore/mlx-lm/issues/2), it modifies earlier messages (e.g. removing tags), so the checkpoint key diverges from the new prompt. The server finds a "longer match" but can\_trim\_prompt\_cache() returns False because ArraysCache.is\_trimmable() inherits False from \_BaseCache. Result: fetch\_nearest\_cache returns None, tokens — full cache miss.

Claude's workaround:

> For hybrid models, move the checkpoint from just before to just before the last user message. This way the checkpoint key becomes \[System + Tools\] — a stable prefix that matches across requests without needing to trim ArraysCache.

My test results (identical setup, two-message conversation):

Before patch After patch

Qwen3.5 request [#2](https://github.com/ml-explore/mlx-lm/issues/2) 11962/11967 tokens processed (full miss) 57/379 tokens processed (cache hit)

GLM-5 request [#2](https://github.com/ml-explore/mlx-lm/issues/2) 320/321 (unaffected) 320/321 (unaffected)

MiniMax-M2.1 request [#2](https://github.com/ml-explore/mlx-lm/issues/2) 348/351 (unaffected) 348/351 (unaffected)

Patch (replace `_compute_prompt_checkpoint` in `server.py`):

```
def _compute_prompt_checkpoint(self, tokenizer, request, prompt):
    if request.request_type != "chat":
        return False, -1
    if request.messages[-1]["role"] != "user":
        return False, -1
    try:
        test_cache = make_prompt_cache(self.model_provider.model)
        is_hybrid = not can_trim_prompt_cache(test_cache)
    except Exception:
        is_hybrid = False
    if is_hybrid:
        im_start_id = None
        try:
            im_start_id = tokenizer._tokenizer.convert_tokens_to_ids(
                "<|im_start|>"
            )
        except Exception:
            pass
        if im_start_id is not None:
            im_start_count = 0
            for i in range(len(prompt) - 1, 0, -1):
                if prompt[i] == im_start_id:
                    im_start_count += 1
                    if im_start_count == 2:
                        checkpoint_offset = len(prompt) - i
                        return True, -checkpoint_offset
    prompt_checkpoint = -1
    if tokenizer.has_thinking:
        for i in range(1, min(11, len(prompt)) - 1, 1):
            if prompt[-i] == tokenizer.think_start_id:
                prompt_checkpoint = -i - 1
                break
    return True, prompt_checkpoint
```

Known limitations:

- single checkpoint per request,
- hardcoded &lt;\|im\_start\|&gt; (ChatML only),
- \_serve\_single codepath not covered.

Looking forward to the proper solution. This is a vibe-coded workaround that may very well introduce it's own issues. Ye have been warned 😉

#### 一句话总结

这两段内容都在讨论一个核心问题：**Qwen 3.5 在 MLX / LM Studio / OpenClaw 这类本地推理环境里，提示词缓存（Prompt Cache / Prefill）经常失效，导致每轮对话都要重新“全量读题”，所以特别慢。**

#### 一、内容总结

##### 内容 1 在讲什么

KeenZ 对自己上一条推文做了更正和补充：

- 之前他以为问题主要是 **mlx_vlm** 引起的；
- 后来查资料发现，**LM Studio 的 MLX 引擎其实是统一架构**：
  - 所有 MLX 模型都走 `mlx-lm` 的文本核心；
  - 视觉能力只是额外挂载，纯文本时不会加载视觉部分。
- 所以，**Qwen 3.5 反复预填充**，并不是单一组件的锅，而是**多个因素叠加**：
  1. `mlx_lm` 的 KV Cache / Prompt Cache 机制存在局限；
  2. **Qwen 官方 Jinja 模板**会造成请求前缀不稳定；
  3. **Qwen 3.5 模型自身架构特性**也不利于缓存复用。

他的结论是：

- 这是个**复合型底层问题**；
- 社区目前**还没有完美的一键修复方案**；
- 在 Mac 本地跑 OpenClaw 时，**GLM 4.7 Flash 当前更稳更快**。

---

##### 内容 2 在讲什么

GitHub Issue #903 更技术化地解释了这个问题：

###### 1. 现象
- 跑 Qwen 3.5 时，缓存几乎不生效；
- 响应里的 `cached tokens` 常常是 `0`；
- 每轮都要重新处理整段 prompt。

###### 2. 原因
主要有三类：

###### A. 模型缓存机制限制
Qwen 3.5 带有 **Mamba / SSM 类缓存**，这类缓存**不好裁剪（trim）**。  
意思是：  
- 如果只是继续同一段对话，缓存可能还能复用一些；
- 但如果你是“相同 system prompt + 新问题”，往往还是得重算前面很多内容。

###### B. reasoning / thinking token 干扰缓存
对“会思考”的模型来说：

- 上一轮缓存里可能包含：
  `系统提示 + 用户问题 + reasoning + 助手回答`
- 但下一轮请求通常不会把 `reasoning` 部分重新发回去；

于是新旧请求前缀不再一致，导致：
- 缓存命中变差；
- 即使命中，也只能命中前面一小段；
- 后面还是要重新 prefill 很多 token。

###### C. Qwen 3.5 的 chat template / tools 渲染不稳定
模板里工具定义、参数顺序、JSON key 顺序等，**前后轮次可能变化**：

- 同样的工具，渲染出来的 JSON 字段顺序可能不同；
- tool args 顺序也可能不同；

虽然语义没变，但对缓存系统来说，**字符串不一样就是不同 prompt**，于是缓存失效。

---

#### 二、深入浅出解读

##### 1. 什么叫“预填充反复发生”？

可以把大模型对话理解成：

- **Prefill（预填充）**：先把你整段历史聊天记录从头读一遍，建立上下文；
- **Decode（生成）**：再开始一个字一个字往外答。

正常情况下，多轮对话应该尽量复用之前“已经读过”的部分。  
但 Qwen 3.5 这里的问题是：

> **它像一个记性不太好的学生，每次你追问一句，它都要把前面整本笔记再翻一遍。**

所以就会出现：

- 首 token 很慢；
- 工具调用后更慢；
- 上下文越长越慢；
- Agent 场景尤其难受。

---

##### 2. 为什么 GLM 4.7 Flash 体感更好？

不是说 Qwen 3.5 一定不行，而是**当前 MLX 生态下，GLM 的缓存路径更顺**：

- 模板更稳定；
- 缓存复用更容易；
- 不容易触发“每次从头再算”。

所以在本地 Agent 场景里，用户体感就会变成：

- **Qwen：生成速度快，但开场前要等很久**
- **GLM：虽然未必每项最强，但整体响应更丝滑**

---

##### 3. 为什么这是“复合问题”？

因为它不是“改一个参数就好”的那种 bug，而是三层同时出问题：

###### 第一层：模型层
Qwen 3.5 的某些层缓存天然不容易裁剪，导致复用困难。

###### 第二层：服务端实现层
`mlx-lm` 当前的 prompt cache / LRU cache 策略，对这种模型不是最友好，还可能带来额外内存占用。

###### 第三层：模板层
Qwen 的 chat template、tools、参数序列化顺序不稳定，破坏了“同前缀”这个缓存前提。

**三层叠加，结果就是：缓存理论上存在，实际经常打不中。**

---

#### 三、这件事对普通用户意味着什么

##### 如果你是普通本地用户
你看到的表象会是：

- 模型“首字慢”
- 每轮都重新加载 prompt
- tool call 越多越卡
- 长上下文下等待时间指数级变差

这通常**不是你电脑坏了，也不一定是配置错了**，而是当前链路对 Qwen 3.5 的支持还不够成熟。

---

##### 如果你是 Agent / Coding 场景用户
这个问题会更严重，因为 Agent 天然会：

- 多轮对话；
- 高频工具调用；
- 长 system prompt；
- 大量上下文拼接。

这正好把 Qwen 3.5 当前缓存弱点全部放大。

---

##### 如果你是开发者
现在比较明确的优化方向有：

- **按层处理缓存，而不是按整个模型统一处理**
- 对 reasoning model，**缓存保存到“思考输出前”**
- 修正 Qwen chat template 的稳定性：
  - `tojson(sort_keys=True)`
  - 参数排序
  - 工具定义排序
- 为不可裁剪缓存设计更合适的 checkpoint / snapshot 方案

也就是说，**问题并非无解，但需要工程层面持续修。**

---

#### 四、我的意见

##### 结论
**短期看，不建议把 Qwen 3.5 + MLX 作为 Mac 本地 Agent 的首选方案。**

###### 更务实的建议：
- 如果你追求**稳定、响应快、少折腾**：
  - 优先试 **GLM 4.7 Flash**
- 如果你就是想用 **Qwen 3.5**：
  - 接受它目前在 MLX 下缓存不稳定的现实；
  - 尽量减少 tool schema 变化；
  - 保持模板输出稳定；
  - 关注 `mlx-lm` 后续修复进展。

##### 我对 KeenZ 这次结论的看法
我觉得他的修正是**靠谱的**：

- 没把锅简单甩给某一个模块；
- 承认是多因素叠加；
- 也给出了更现实的替代方案（先用 GLM）。

这比“换个模型就好了”或“纯属配置问题”的说法更接近事实。

---

#### 五、最终结论

##### 核心判断
**Qwen 3.5 在 MLX 生态里的慢，不是单点 bug，而是“模型结构 + 缓存机制 + 模板渲染”共同导致的缓存失效问题。**

##### 目前最实用的建议
- **要稳定：先用 GLM 4.7 Flash**
- **要折腾 Qwen 3.5：关注缓存修复、模板排序、checkpoint 优化**
- **不要把“每次全量 prefill”误以为只是自己配置有问题**

## 追问（1）

### 提问 · 2026-03-12 02:07:25

详述：“ Qwen 3.5 的 chat template / tools 渲染不稳定
模板里工具定义、参数顺序、JSON key 顺序等，前后轮次可能变化”

### 回答 · 2026-03-12 02:09:09

这里的意思是：**哪怕“语义上是同一个请求”**，Qwen 3.5 的聊天模板在把 messages / tools 渲染成最终 prompt 字符串时，**文本字节级结果可能前后不完全一样**。而 prompt cache 看的是“前缀字符串是否完全一致”，不是看“你是不是大意相同”。只要有一点点差异，缓存命中就会明显变差。

我分几层讲。

---

#### 1. 先说“模板渲染不稳定”到底是什么

大模型真正吃进去的不是你程序里的 Python dict，也不是“这个 tool 逻辑上没变”，而是最终拼出来的一大段文本，比如：

- system prompt
- 历史消息
- tool 定义
- tool 调用格式说明
- schema JSON
- assistant / user / tool 的特殊标记

这些内容通常由 **chat template** 负责渲染。

所谓“不稳定”，就是：

同样一组 messages / tools，理论上应该渲染出完全相同的前缀文本；  
但实际上，可能因为一些实现细节，渲染结果在不同轮次出现微小变化，例如：

- 工具列表顺序变了
- JSON 对象的 key 顺序变了
- required 字段顺序变了
- properties 里参数顺序变了
- tool call 参数序列化顺序变了
- 某些空格、换行、逗号位置变了
- 是否包含某个可选字段前后不一致

**对人看起来差不多，对缓存系统来说就是不同 prompt。**

---

#### 2. 为什么这会直接伤害缓存

Prompt cache / KV cache 的常见复用逻辑是：

> 新请求的前 N 个 token，必须和上一次请求的前 N 个 token 完全相同，才能直接复用这部分计算结果。

注意是：

- 不是“语义接近”
- 不是“JSON 等价”
- 不是“字段顺序无所谓”

而是：

- **token 序列尽可能逐个一致**

所以如果工具定义区里有一个字段顺序变化，例如：

```json
{"type":"object","properties":{"city":{"type":"string"},"unit":{"type":"string"}}}
```

下一轮变成：

```json
{"properties":{"unit":{"type":"string"},"city":{"type":"string"}},"type":"object"}
```

虽然语义一样，但 tokenizer 看到的是**不同的字符串序列**，于是：

- 这段开始往后的 token 都可能不一样
- cache match 会在这里中断
- 后续需要重新 prefill

如果 tool schema 很长，那就是一大段前缀白白失去复用。

---

#### 3. “工具定义不稳定”具体指什么

##### 3.1 tools 列表顺序变化

假设你有两个工具：

- `search_web`
- `read_file`

某一轮模板渲染成：

```json
[
  {"name":"search_web", ...},
  {"name":"read_file", ...}
]
```

下一轮由于代码里 tools 来源于：

- dict 遍历
- set 去重
- 某个 registry 动态注册
- 插件加载顺序

结果变成：

```json
[
  {"name":"read_file", ...},
  {"name":"search_web", ...}
]
```

语义上没问题，但文本前缀完全不同。

如果这段工具定义被拼在 prompt 前部，那么**缓存从 tools 开始就断了**。

---

##### 3.2 单个 tool 内部字段顺序变化

例如某轮是：

```json
{
  "name": "weather",
  "description": "Get weather",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {"type":"string"},
      "date": {"type":"string"}
    },
    "required": ["city"]
  }
}
```

另一轮可能变成：

```json
{
  "description": "Get weather",
  "parameters": {
    "required": ["city"],
    "properties": {
      "date": {"type":"string"},
      "city": {"type":"string"}
    },
    "type": "object"
  },
  "name": "weather"
}
```

这通常来自：

- Python / JS 对对象遍历顺序依赖不一致
- 中间做过 merge / deepcopy / schema 转换
- Pydantic / dataclass / OpenAPI schema 导出时顺序不固定
- 不同库版本对 schema 生成顺序处理不同

虽然在 JSON 语义上都合法，但对于 token cache 来说，这两段不是一个前缀。

---

##### 3.3 `properties` 内参数顺序变化

这是最常见、也最容易被忽视的点。

比如函数参数本来是：

- `query`
- `top_k`
- `lang`

有时渲染为：

```json
"properties": {
  "query": {...},
  "top_k": {...},
  "lang": {...}
}
```

有时变成：

```json
"properties": {
  "lang": {...},
  "query": {...},
  "top_k": {...}
}
```

来源可能是：

- 参数 schema 来自普通 dict，构建时顺序不固定
- 某个步骤做了哈希映射、过滤、重新拼接
- 多模块收集参数后再合并

因为 tool schema 往往很长，这种变化对缓存破坏非常大。

---

##### 3.4 `required` 数组顺序变化

很多人会觉得：

```json
"required": ["city", "unit"]
```

和

```json
"required": ["unit", "city"]
```

没区别。

在 JSON Schema 语义上通常确实没区别。  
但在 prompt cache 看来，数组顺序就是文本顺序，顺序不同就不同。

同理：

- `enum` 数组顺序
- `oneOf` / `anyOf` 列表顺序
- examples 顺序

都可能引发同样问题。

---

##### 3.5 tool call 参数渲染顺序变化

不只是“工具定义”，**实际调用参数**也会影响后续轮次前缀一致性。

例如 assistant 发起工具调用：

某次是：

```json
{"city":"Beijing","unit":"celsius"}
```

下次是：

```json
{"unit":"celsius","city":"Beijing"}
```

模型和后端可能都能正确理解，但文本不同。

如果下一轮请求会把这段历史 tool call 一起带上，那么这段历史消息本身就变了，缓存也就更难命中。

---

##### 3.6 空值、默认值、可选字段是否输出不一致

例如一轮工具 schema 中包含：

```json
{"description":"","nullable":false}
```

下一轮被简化成：

```json
{}
```

或者：

- 有时输出 `default`
- 有时不输出
- 有时输出 `additionalProperties: false`
- 有时省略

这些都会让 prompt 文本漂移。

---

##### 3.7 空格、缩进、换行风格变化

即便 JSON 数据本身没变，序列化方式变了也一样伤缓存。

比如：

###### 紧凑格式
```json
{"name":"weather","parameters":{"type":"object","properties":{"city":{"type":"string"}}}}
```

###### pretty 格式
```json
{
  "name": "weather",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {
        "type": "string"
      }
    }
  }
}
```

或者同是紧凑格式，但：

- 冒号后是否有空格
- 逗号后是否有空格
- 结尾换行是否保留

都可能改变 token 序列。

---

#### 4. 为什么 Qwen 3.5 这里更容易暴露这个问题

这通常和它的 **chat template 对 tools 的嵌入方式**有关。

很多支持 tool calling 的模型模板，会把工具定义直接以较大段文本插到 prompt 前部，类似：

- “You have access to the following tools…”
- 然后跟一个 JSON / schema 区块
- 再跟格式说明
- 再开始历史消息

如果这整段在每一轮都会重新渲染，而且渲染结果不是严格 canonical 的，那么每一轮就可能产生轻微不同的 prompt 前缀。

而缓存最依赖的恰恰就是：

> **系统提示 + 工具定义 + 早期历史消息** 这部分必须稳定。

一旦工具区不稳定，相当于最该缓存的大头恰好最不稳定。

---

#### 5. 一个非常具体的例子

假设你每轮都传同一个工具：

```python
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "Get weather by city",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string"},
                "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
            },
            "required": ["city"]
        }
    }
}]
```

你以为每轮都一样。  
但实际链路可能是：

1. 先从 Python dict 变成内部 schema
2. 再加上一些默认字段
3. 再通过模板 `tojson`
4. 某轮经过一次 normalize
5. 某轮又经过 tool registry merge

结果第一轮 prompt 中是：

```json
{"type":"function","function":{"name":"get_weather","description":"Get weather by city","parameters":{"type":"object","properties":{"city":{"type":"string"},"unit":{"type":"string","enum":["celsius","fahrenheit"]}},"required":["city"]}}}
```

第二轮变成：

```json
{"function":{"description":"Get weather by city","name":"get_weather","parameters":{"properties":{"unit":{"enum":["celsius","fahrenheit"],"type":"string"},"city":{"type":"string"}},"required":["city"],"type":"object"}},"type":"function"}
```

对人类：
- 还是同一个工具

对缓存：
- 完全不是同一个前缀

结果就是第二轮依然要重新 prefill 大量 tokens。

---

#### 6. “参数顺序变化”为什么会经常发生

因为很多工程代码默认并没有把“字节级稳定输出”当成目标。

系统设计时往往只保证：

- API 能用
- JSON 合法
- 模型看得懂
- 函数能被调起来

但**不会默认保证每次序列化出来都是 canonical JSON**。

常见诱因有：

- 用 dict / object 存 schema，然后多次 merge
- 遍历 map/hashmap 时无固定排序
- 动态注册工具，注册先后不稳定
- 中途插入 tracing / metadata 字段
- 某些字段只有在特定轮次出现
- 同一 schema 由不同模块生成
- 不同语言/版本运行时对象顺序行为不同

对普通应用这都不是大问题，  
但对 prompt cache 来说，这正是致命细节。

---

#### 7. 为什么“前后轮次可能变化”

你可能会问：如果工具本身没改，为啥前后轮会变化？

因为每轮请求通常不是简单复用上次同一字符串，而是**重新构造一次请求对象，再重新渲染 prompt**。在这条链路上，很多步骤都可能带来漂移：

- 本轮激活的工具集合略有不同
- 工具 registry 返回顺序不同
- schema 生成器版本或分支路径不同
- 只在本轮加入某些 hints / examples
- 某个 tool 上一轮被调用过，本轮带入了额外 metadata
- 历史消息中 tool call args 的序列化顺序不同
- reasoning 内容是否保留不同
- 模板条件分支命中不同

因此即使“你主观上觉得工具没变”，最终 prompt 也未必一模一样。

---

#### 8. 这对缓存命中的破坏路径

你可以这样理解：

##### 理想情况
前缀完全相同：

`system + tools + 历史消息A + 历史消息B`

下一轮只新增：

`+ 新用户问题`

那么前面一大段都能复用。

##### 实际情况
如果 tools 区有一点点变化：

`system + tools' + 历史消息A + 历史消息B`

那么缓存匹配可能从 tools 那里就断了。  
后面的历史消息即使“内容看起来一样”，由于 token 流已经分叉，也往往无法直接复用成原来那么高的比例。

这就是为什么用户看到的是：

- `cached tokens = 0`
- 或只有极少数 token 命中
- 首 token 时间很长

---

#### 9. 怎么判断自己是不是遇到了这个问题

可以看几个信号：

##### 9.1 同样 system prompt、同样 tools，每轮 cached tokens 仍接近 0
这很像前缀不稳定。

##### 9.2 关闭 tools 后，速度明显改善
说明工具定义区很可能在破坏缓存。

##### 9.3 把 tool schema 手工固定排序后，命中率上升
这是最直接证据。

##### 9.4 日志里看到同一 tool 的 JSON 文本每轮不一样
哪怕只是字段顺序不同，也足以说明问题。

---

#### 10. 如何解决“渲染不稳定”

核心思路就一句话：

> **把 tools / schema / tool args 的文本表示做成 canonical、deterministic、byte-stable。**

也就是：  
同样输入，永远输出完全相同的字符串。

---

##### 10.1 固定 tools 列表顺序

按稳定键排序，比如：

- 先按 `function.name`
- 再按 `type`

不要依赖注册顺序、dict 顺序、插件加载顺序。

例如逻辑上：

```python
tools = sorted(tools, key=lambda t: t["function"]["name"])
```

---

##### 10.2 JSON 序列化时强制 key 排序

例如 Python：

```python
json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
```

这样至少能稳定：

- 对象 key 顺序
- 空格风格
- 输出紧凑格式

Jinja 里如果有 `tojson`，最好确认是否支持类似：

- `sort_keys=True`
- 固定 separators

否则不同轮次可能仍有差异。

---

##### 10.3 递归规范化 schema

不只是顶层排序，最好对以下部分都做规范化：

- `properties` 按 key 排序
- `required` 按字母序排序
- `enum` 若语义允许则固定顺序
- `oneOf` / `anyOf` / `allOf` 递归排序
- 删除无意义默认字段
- 统一是否输出 `additionalProperties`
- 统一空字符串 / null / 缺省策略

---

##### 10.4 固定 tool call args 的序列化

assistant 产生工具调用后，写入历史时不要直接用“原始 dict 随机顺序”，而要：

- 排序 key
- 统一紧凑 JSON
- 保证每次回放历史时文本一致

---

##### 10.5 避免每轮动态改写工具 schema

例如不要本轮加一句 hint，下轮删一句 example。  
只要工具没变，就尽量保证 schema 文本完全不变。

---

##### 10.6 模板层面做 canonical rendering

也就是让 chat template 不只是“能渲染”，而是“稳定渲染”：

- 固定换行
- 固定空格
- 固定字段出现顺序
- 固定工具段落位置
- 固定消息包装格式

---

#### 11. 最关键的认识

“模板里工具定义、参数顺序、JSON key 顺序等，前后轮次可能变化”这句话，本质上不是在说：

> Qwen 不懂工具

而是在说：

> **Qwen 3.5 这条本地推理链路中，工具相关 prompt 的字符串表示不够稳定，导致 prompt cache 很难把它认成“同一个前缀”。**

所以问题重点不在“语义对不对”，而在：

- 是否 deterministic
- 是否 canonical
- 是否字节级稳定

对缓存系统来说，**稳定文本比语义等价更重要**。
