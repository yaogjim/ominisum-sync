## 分析要点

- **核心高价值点**：最有价值的是其将同一套 agent 体系适配到多个主流 AI 编码工具，并提供转换与安装脚本，降低了迁移和落地成本。
- **留存建议**：作为代理模板与工具集成参考短中期保留（包含较完整的代理分类、安装方式与多工具适配说明，适合作为后续搭建代理系统时检索参考）
- **不足**：内容偏仓库清单与宣传页，方法论提炼不足，证据质量一般，重复枚举较多

**知识要点**

- 多角色 AI agent 可以按职能拆分为工程、设计、营销、产品、测试等分工体系
- 同一套 agent 描述可通过转换脚本适配 Claude Code、Copilot、Cursor、Aider、Qwen Code 等不同工具
- 高质量 agent 模板通常包含身份设定、任务边界、工作流、交付物和成功指标

**行动项**

- 挑选与你当前工作最相关的 3-5 个 agent，先在单一工具链中试装验证效果
- 参考其 agent 模板结构，抽象出适合自己团队的角色定义与交付规范

#### 🚀 这是什么？

诞生于一个 Reddit 帖子和数月的迭代后， **The Agency** 是一个不断发展的精心打造的 AI 代理人格集合。每个代理都是：

- **🎯 专业的** ：在其领域内拥有深厚的专业知识（而非通用的提示词模板）
- **🧠 个性驱动** ：独特的声音、沟通风格和方法
- **📋 交付成果导向** : 真实代码、流程和可衡量的成果
- **✅ 生产就绪** ：经过实战检验的工作流程和成功指标

**可以把它看作是** ：组建你的梦想团队，只不过他们是从不睡觉、从不抱怨、且总能交付的 AI 专家。

```
# Copy agents to your Claude Code directory
cp -r agency-agents/* ~/.claude/agents/

# Now activate any agent in your Claude Code sessions:
# "Hey Claude, activate Frontend Developer mode and help me build a React component"
```

Each agent file contains:

- Identity &amp; personality traits
- Core mission &amp; workflows
- 技术交付物与代码示例
- 成功指标与沟通风格

浏览下方的代理，复制/调整你需要的那些！

```
# Step 1 -- generate integration files for all supported tools
./scripts/convert.sh

# Step 2 -- install interactively (auto-detects what you have installed)
./scripts/install.sh

# Or target a specific tool directly
./scripts/install.sh --tool cursor
./scripts/install.sh --tool copilot
./scripts/install.sh --tool aider
./scripts/install.sh --tool windsurf
./scripts/install.sh --tool kimi
```

**更快运行（并行）** — 在多核机器上，使用 `--parallel` 以便每个工具并行处理。跨工具的输出顺序是非确定性的。适用于交互式和非交互式安装：例如 `./scripts/install.sh --interactive --parallel` （选择工具，然后并行安装）或 `./scripts/install.sh --no-interactive --parallel` 。作业数默认为 `nproc` （Linux）、 `sysctl -n hw.ncpu` （macOS）或 4；使用 `--jobs N` 覆盖。

```
./scripts/convert.sh --parallel                    # convert all tools in parallel
./scripts/convert.sh --parallel --jobs 8           # cap parallel jobs
./scripts/install.sh --no-interactive --parallel   # install all detected tools in parallel
./scripts/install.sh --interactive --parallel      # pick tools, then install in parallel
./scripts/install.sh --no-interactive --parallel --jobs 4
```

这是一个名为 `agency-agents` 的 GitHub 项目，核心目标是把“AI 智能体”做成一整套可直接使用的专业团队：每个 agent 都有明确分工、个性、流程和可交付成果。它不仅提供了大量现成角色，还支持安装到多种 AI 编码工具中，方便用户像“组建公司团队”一样调用不同专家协作。

它抓住的不是模型能力本身，而是用户在使用 Claude Code、Copilot、Cursor、Aider 等工具时的一个高频痛点：

- 模型很强，但“不稳定、不成体系、不像一个真实团队”
- 用户知道要做什么，但不知道“该怎么组织 AI”
- 单一通用助手难以覆盖复杂项目中的多角色协作需求
- 市面上很多 agent 方案是封闭黑盒，而这个项目提供了“透明、可 fork、可定制、跨工具复用”的能力

所以它的价值不在“重新发明模型”，而在于：
- 把“专家经验 + 交付流程 + 风格人格”封装成可调用资产
- 降低用户设计 prompt / workflow 的门槛
- 用“团队化心智”提升 AI 的可用性和可信度
- 借多工具兼容，获得更强分发和社区传播能力

一句话定义：
`agency-agents` 是一个面向 AI 原生工作流的“专家角色库 + 跨平台 agent 分发层”。

**1. 产品是什么**
从产品形态看，它不是 SaaS，不是 Agent Runtime，也不是 Workflow 编排平台。  
它更像：

- Agent 模板库
- 专家人格与流程资产库
- 跨 AI coding tool 的兼容层
- AI 协作方式的“中间抽象层”

核心资产是：
- 角色定义
- 工作流程
- 输出格式
- 质量标准
- 成功指标

也就是说，真正的“产品”不只是 `.md` 文件，而是：

因此它满足的不是“模型推理需求”，而是“任务执行组织需求”。

**3. 它最像谁**

- Prompt Library：但更结构化、更强调交付结果
- AI Skills Marketplace：但目前是开源、静态、可 fork 的
- 咨询公司方法论模板：把岗位 SOP 产品化

如果继续停留在“静态 agent 库”，PMF 会强于传播、弱于商业化。

**六、核心问题与风险**

**1. 最大风险：看起来很强，实际使用成本可能很高**
agent 很多会产生典型“菜单过载”问题：

- 我到底该选哪个 agent？
- 多 agent 如何协作？
- 角色是否重叠？
- 什么任务适合单 agent，什么适合 team？
- 输出冲突怎么办？

如果用户第一次打开 repo 就被 140+ agents 淹没，转化效率会下降。  
所以当前产品存在“内容资产强，导航体验弱”的问题。

**2. 静态 prompt 的上限明显**
尽管 agent 文档设计得很好，但它本质上仍是“静态指令资产”。  
缺少这些更高阶能力：

- 记忆管理
- 状态同步
- 任务分发
- 角色编排
- 自动验收
- 结果合并
- feedback loop

这意味着它离真正“AI agency”还有较大距离。  
现在更准确是“AI agency 的角色说明书”，不是“agency runtime”。

**3. 护城河偏弱**
如果只看 repo 内容，其护城河主要来自：

- 作者方法论
- 社区积累
- agent 覆盖广度
- 多工具兼容

但这些都容易被复制。  
真正难复制的护城河应该来自：

- 用户任务数据
- 最佳实践反馈闭环
- agent 效果评测体系
- 企业级组织层能力
- 行业特定 workflow 模板

**4. 质量一致性风险**
147 个 agents 意味着内容维护难度极高。  
随着数量增长，会出现：

- 风格不一致
- 深度不一致
- 实战价值参差不齐
- 部分 agent 高度重合
- 更新滞后

如果没有强标准化评审机制，规模会反过来稀释品牌价值。

**5. 成果归因不清**
用户可能觉得“是 Claude/ChatGPT 强，不是这个 agent 强”。  
如果产品无法证明 agent 的独特增益，商业化就会困难。

所以未来必须建立：
- 使用前后效果对比
- 任务完成率提升
- 时间节省
- 输出质量评分
- 团队协作效率改善

**七、技术实现分析**

**1. 当前技术架构本质**
当前架构偏“内容编译 + 多平台安装分发”：

- 源格式：agent markdown / structured files

- 分发层：`install.sh`
- 宿主适配：不同工具目标格式、目标目录、命名规则

这是一个典型的“内容源 -> 多终端产物”的构建系统。

它的技术聪明点在于：
- 没有自己造 runtime
- 借用现有 agentic 工具生态
- 通过脚本降低集成成本
- 用转换器适配不同工具的 agent/rules/conventions 格式

这是一种非常轻的产品策略，适合早期快速扩张。

**2. 技术上做对了什么**
- 用 shell 实现跨环境最小依赖安装
- 通过 tool-specific conversion 降低接入成本
- 把 agent 设计成内容资产而不是代码耦合逻辑
- 支持 project-scoped 与 user-scoped 两种安装方式
- 兼容多平台，提升 adoption

**3. 技术上接下来的瓶颈**
如果继续发展，当前实现会遇到几个瓶颈：

- 内容版本管理复杂
- agent schema 缺少强约束
- 各工具格式差异会越来越难维护
- 缺少自动化测试来验证转换正确性
- 缺少 agent 质量回归验证
- 没有 usage telemetry，难以做产品迭代

**4. 如果我是产品/技术负责人，下一步技术升级路径**
建议从“agent 文件仓库”升级到“agent platform”：

第一层：Schema 标准化
- 定义统一 Agent DSL / JSON Schema
- 明确 identity / workflow / deliverables / metrics / examples 字段
- 所有平台产物从 schema 编译生成

第二层：评测与 QA
- 建立 agent lint
- 建立 agent completeness score
- 建立 benchmark tasks
- 测试不同模型/平台下的表现差异

第三层：运行时编排
- 支持 agent team preset
- 支持 supervisor / router / critic / validator 模式
- 支持串行与并行协作流程模板

第四层：知识与记忆
- 支持 project context injection
- 支持 role memory / task memory
- 支持 org-level customization

第五层：可视化产品
- agent selector
- workflow builder
- task-to-team recommender
- success metrics dashboard

**实例：用 The Agency 在 2 周内做一个 AI SaaS 产品落地页 + 注册转化闭环**

假设你要做一个新产品：`MeetingMind`，它能自动总结会议、提炼行动项，并同步到 Notion/Jira。你的目标不是“写几个页面”，而是：

- `Tracking & Measurement Specialist`：设计埋点、转化事件
- `Evidence Collector`：截图验证关键页面状态

**最佳实践，不是“多 agent 一起上”，而是“每个 agent 只负责一个明确产物”**

这个仓库最值得借鉴的点，就是每个 agent 都有：
- 明确身份
- 固定流程
- 具体 deliverable
- 成功指标

所以在这个实例里，最佳实践是把任务拆成“可交付物”而不是“泛泛协作”。

例如：

1. `Product Manager` 只产出一页 PRD
2. `UX Researcher` 只产出首屏信息架构和用户异议清单
3. `UI Designer` 只产出视觉方向、颜色/字体/token、组件规范
4. `Frontend Developer` 只负责把这些内容实现成页面
5. `Tracking & Measurement Specialist` 只定义事件表
6. `Evidence Collector` 只做截图和验收证据
7. `Reality Checker` 只决定“能不能上线”

这样做的好处是：不会出现多个 agent 同时“指导前端”导致输出冲突。

**一个实际执行流程**

你可以这样运行这个项目思路：

第一阶段，先做目标对齐，而不是直接写代码。

让 `Product Manager` 输出：

- 目标用户：独立顾问、小团队 founder、产品经理
- 页面目标：让访客提交邮箱申请 beta
- 核心价值：5 分钟内把会议记录变成可执行任务
- 页面结构：Hero / Social proof / Problem / How it works / Pricing hint / CTA
- 成功指标：首周访问转化率 > 4%

这一步的最佳实践是：
- 每个页面只能有一个主 CTA
- 每个区块只回答一个问题
- 成功指标必须先定义，否则后续 agent 很容易只做“好看页面”

第二阶段，让 `UX Researcher` 把“用户为什么会犹豫”说清楚。

例如，他应输出：

- 用户担心 AI 总结不准确
- 用户担心接入 Notion/Jira 很麻烦
- 用户担心会议隐私
- 用户不知道和现有工具相比有什么优势

在这个基础上，最佳实践是：
- 页面内容不要按“公司想说什么”排，而要按“用户先想知道什么”排
- Hero 不要堆功能，要先讲结果
- FAQ 必须覆盖高阻力问题，而不是凑数

比如：
- 错误写法：`AI-powered workflow orchestration for teams`
- 更好写法：`把 1 小时会议，5 分钟变成可执行任务`

第三阶段，让 `UI Designer` 定义“实现约束”，不是只给审美建议。

最佳实践是让设计 agent 明确输出：

- 设计 token：主色、辅助色、字号、间距、圆角、阴影
- 页面节奏：首屏强对比，中段可信度，尾部重复 CTA
- 组件清单：按钮、输入框、卡片、评价模块、FAQ 折叠区
- 响应式规则：移动端首屏 CTA 必须在首屏内可见

这是很关键的一点。这个仓库强调 deliverable，不是空泛人格，所以设计 agent 最好给“可编码规范”，而不是“做得现代一点”。

第四阶段，`Frontend Developer` 才开始动手。

这里的最佳实践不是“让前端自己想需求”，而是只根据前三者输出实现。

前端交付建议包括：

- React/Next.js 单页落地页
- 表单提交逻辑
- 基础 loading / success / error 状态
- 性能优化：图片懒加载、字体优化、减少首屏 JS
- 可访问性：按钮语义、label、键盘导航、颜色对比度

更进一步，最佳实践是要求前端在实现时同时输出：

- 组件树
- 状态流说明
- 埋点触发点
- 已知 trade-off

例如：

- CTA 按钮点击 -> `signup_cta_clicked`
- 表单提交成功 -> `signup_submitted`
- FAQ 展开 -> `faq_opened`
- 页面滚动到 pricing -> `pricing_viewed`

这样，后续 `Tracking & Measurement Specialist` 就不需要重新猜代码该怎么埋。

**在这个实例上，最重要的最佳实践：先定义事件，再上线页面**

很多团队会先做页面，再补埋点。这是低效的。

基于这个仓库的分工思想，更好的方式是：
- 在页面开发开始前，就让 `Tracking & Measurement Specialist` 产出事件字典

例如：

```text
event: landing_view
trigger: 页面首次加载
purpose: 统计访问量

event: hero_cta_click
trigger: 首屏 CTA 点击
purpose: 衡量首屏文案吸引力

event: signup_submit
trigger: 邮箱提交成功
purpose: 主转化指标

event: faq_privacy_open
trigger: 用户展开隐私相关 FAQ
purpose: 判断隐私是否是主要阻碍
```

这一步的最佳实践有三条：

- 事件名统一、稳定、可读
- 每个事件都要有“业务用途”
- 只埋关键行为，不要过度埋点

**为什么 `Evidence Collector` 和 `Reality Checker` 很关键**

这是这个仓库里非常有意思也非常实用的设计：它不只关注“产出”，还关注“验收”。

在这个实例里，`Evidence Collector` 最佳实践是要求它提交一份“视觉验证证据”：

- 桌面端首屏截图
- 移动端首屏截图
- 表单 error 状态截图
- 表单 success 状态截图
- FAQ 展开状态截图
- Lighthouse 关键指标截图

而 `Reality Checker` 不应该只说“看起来可以上线”，而应该按上线标准审核：

- CTA 是否唯一明确
- 表单是否真的可提交
- 埋点是否触发
- 首屏是否清楚说明产品价值
- 移动端是否首屏可用
- 是否有明显性能问题
- 是否存在假按钮、死链接、占位文案

这就是最佳实践里的“质量闸门思维”：  
不是代码写完就结束，而是必须经过证据和标准验证。

**如果只用一个 agent，会出现什么问题**

这是理解该仓库价值的反面例子。

如果你只用 `Frontend Developer`，常见结果是：

- 页面能做出来，但文案不聚焦
- CTA 太多
- 没有埋点
- 没有证据化验收
- 没有“是否可上线”的明确标准
- 设计风格与用户目标脱节

所以，这个仓库真正的最佳实践不是“agent 越多越好”，而是：

- 小团队组合
- 角色边界清晰
- 每个 agent 对应一个交付物
- 用统一目标和成功指标串起来

**基于这个实例，可直接复用的一套最佳实践**

你可以把它理解成一个多代理协作模板：

- 明确一个北极星目标：例如“注册转化率 > 4%”
- 每个 agent 只负责一个文档或一种输出
- 所有 agent 都围绕同一个用户场景，不各说各话
- 先做 PRD、信息架构、事件字典，再做实现
- 设计输出必须可编码，不能只是概念描述
- 开发输出必须包含状态、埋点、性能和可访问性
- 验收必须有截图证据和上线清单
- 最后由 `Reality Checker` 做 go/no-go 决策

**一句话总结这个仓库的最佳使用方式**

最好的用法不是“召唤一个超级 agent 替你做完一切”，而是“把复杂项目拆成多位专家的明确交付链条”，让每个 agent 都像一个真实团队成员一样，对一个具体结果负责。

## 总结（1）

#### 基于`agency-agents`的最佳实践示例

下面我用一个具体实例，说明如何基于`msitarzewski/agency-agents`这类 “多智能体协作库”，设计一套更可落地、可复用、可控风险的最佳实践。

---

##### 一句话理解这个项目

`agency-agents`的核心价值，不是 “有很多角色提示词”，而是把 AI 协作从单个万能助手，升级为：

- 有明确分工的专家团队
- 每个专家有固定职责、流程、交付物和成功指标
- 可以围绕同一个业务目标并行协作
- 可安装到多种 AI 编码 / 代理工具中复用

所以，它最适合的不是 “随便问点问题”，而是：

- 产品发现
- 企业功能开发
- 营销活动启动
- 跨职能复杂项目推进
- 需要质量门禁和结构化交付的任务

---

#### 具体实例：从 0 到 1 打造一个面向中国市场的 AI 学习产品 MVP

假设你要做一个产品：

> “一个帮助中国大学生准备英语面试的 AI Web App，包含题库练习、语音反馈、学习路径推荐和微信生态分享能力。”

目标是在 4 周内完成 MVP，验证是否值得继续投入。

---

##### 参与的 Agent 团队

基于你提供的内容，这个实例中最合适的团队组合是：

- `产品经理`：定义目标用户、MVP 范围、验收标准
- `趋势研究员`：分析市场机会、竞品和用户需求
- `前端开发人员`：开发 Web 端界面
- `后端架构师`：设计 API、数据模型、鉴权和可扩展方案
- `AI Engineer`：实现语音反馈与学习推荐能力
- `微信小程序开发者`或`飞书集成开发者`：负责生态接入思路
- `UI Designer`：输出高保真界面和组件规范
- `增长黑客`：设计首批获客和激活实验
- `证据收集者`：基于截图 / 录屏做视觉验证
- `现实验证者`：做上线前质量门禁

如果资源有限，第一版可以缩减为 6 个核心角色：

- 产品经理
- 趋势研究员
- 前端开发人员
- 后端架构师
- AI Engineer
- 现实验证者

---

#### 这个实例之上的最佳实践

##### 1. 先定义 “任务地图”，再调用 Agent

很多团队使用多 Agent 时，最大的问题是：

- 一上来就 “大家一起干”
- 结果重复劳动
- 输出风格不一致
- 责任边界模糊
- 最后没有统一结果

最佳实践是先定义一页任务地图。

###### 推荐模板

```markdown
## 项目目标
在 4 周内上线 AI 英语面试练习 MVP，并完成 100 位种子用户测试。

## 用户对象
中国大学生 / 应届毕业生 / 有英语面试需求人群

## 核心问题
- 不知道如何准备英文面试
- 缺少即时反馈
- 练习过程枯燥且难坚持

## MVP 范围
- 题库练习
- AI 语音反馈
- 每日学习计划
- 微信分享卡片

## 非目标
- 不做完整社区
- 不做企业版后台
- 不做复杂付费体系

## 成功指标
- 7 日留存 > 20%
- 题目完成率 > 60%
- 首次语音练习转化率 > 40%
```

###### 为什么这是最佳实践

因为这会让所有 Agent 在同一个边界内工作：

- `产品经理`不会无限扩需求
- `前端开发人员`不会先做花哨但无关的功能
- `增长黑客`不会设计和产品现状脱节的投放方案
- `现实验证者`可以依据明确标准验收

---

##### 2. 用 “阶段制协作”，不要让所有 Agent 同时输出

虽然项目强调并行协作，但实践里最稳妥的方法不是 “全并行”，而是 “分阶段并行”。

###### 推荐阶段

###### 阶段 1：发现与定义
由以下 Agent 输出：

- `趋势研究员`
- `产品经理`
- `UX 研究员`（如有）

交付物：

- 市场机会分析
- 用户画像
- 竞品拆解
- MVP 定义
- 风险清单

###### 阶段 2：方案设计
由以下 Agent 输出：

- `后端架构师`
- `前端开发人员`
- `UI Designer`
- `AI Engineer`

交付物：

- 系统架构图
- API 草案
- 数据模型
- 页面流转图
- AI 能力调用方案

###### 阶段 3：构建与验证
由以下 Agent 输出：

- `前端开发人员`
- `后端架构师`
- `AI Engineer`
- `证据收集者`
- `现实验证者`

交付物：

- 可运行 MVP
- 测试截图 / 录屏
- 缺陷清单
- 上线建议

###### 阶段 4：增长试验
由以下 Agent 输出：

- `增长黑客`
- `内容创作者`
- `分析记者`

交付物：

- 种子用户招募方案
- 首轮激活漏斗
- 数据看板定义
- 实验假设表

###### 为什么这是最佳实践

因为多 Agent 的真正效率，来自：

- 并行处理 “同阶段不同专业” 问题
- 串行推进 “阶段之间存在依赖” 的问题

否则容易出现：

- 设计稿没定，前端先写死
- API 没定，AI 能力先绑定错误接口
- 产品价值没验证，就已经做完一整套复杂系统

---

##### 3. 每个 Agent 只对一种交付物负责

这是最重要的一条。

不要让 Agent 只输出 “建议”，而要输出 “可接力的成果物”。

###### 错误方式

- 让`后端架构师`提一些口头建议
- 让`前端开发人员`自己猜接口
- 让`增长黑客`只写一堆口号

###### 正确方式

给每个 Agent 固定交付模板。

###### 示例

###### `趋势研究员`
输出：

```markdown
- 目标市场规模简述
- Top 5 竞品
- 用户痛点排序
- 差异化机会
- 风险假设
```

###### `产品经理`
输出：

```markdown
- MVP PRD
- 用户故事
- 优先级矩阵
- 验收标准
```

###### `后端架构师`
输出：

```markdown
- API 列表
- 数据表设计
- 鉴权方案
- 日志与监控建议
- 扩展风险
```

###### `前端开发人员`
输出：

```markdown
- 页面结构
- 组件列表
- 状态流转说明
- 性能关注点
```

###### `现实验证者`
输出：

```markdown
- 是否满足上线标准
- 证据列表
- 阻塞问题
- 可接受风险
- 发布建议
```

###### 为什么这是最佳实践

因为多 Agent 系统最怕的不是 “能力不够”，而是 “输出不可拼接”。

只有当每个 Agent 的结果是标准化的，下一个 Agent 才能接得住。

---

##### 4. 设一个 “总协调人”，避免多 Agent 互相打架

在这个实例里，最适合作为协调人的角色是：

- `产品经理`
- 或`代理编排器`

###### 协调人的职责

- 统一项目目标
- 分配 Agent 输入上下文
- 控制 Agent 间依赖关系
- 合并冲突意见
- 输出最终版本

###### 例如，实际冲突会长这样

- `增长黑客`希望增加裂变分享功能
- `前端开发人员`认为会拖慢 MVP 进度
- `后端架构师`认为分享链路要改鉴权模型
- `现实验证者`认为新功能增加上线风险

这时不应该让所有 Agent 无限讨论，而应由协调人做决策：

```markdown
决策：
本轮 MVP 不做站内裂变，仅保留微信分享海报能力。

原因：
- 满足增长验证最低需要
- 不影响核心学习链路
- 降低登录与邀请关系复杂度
- 符合 4 周上线目标
```

###### 为什么这是最佳实践

多 Agent 不是 “民主讨论”，而是 “专业协作 + 中央决策”。

否则项目会变成：

- 建议越来越多
- 冲突越来越大
- 决策越来越慢

---

##### 5. 给 Agent 的上下文要 “足够小，但足够完整”

这类项目的另一个常见问题是：

- 要么上下文太少，Agent 理解偏差
- 要么把整个仓库、全部聊天记录、所有 PRD 都塞进去，导致噪音过大

最佳实践是按角色给上下文。

###### 示例：给`前端开发人员`的上下文

```markdown
你负责 AI 英语面试 Web App MVP 的前端实现。

项目目标：
4 周内上线 MVP，用于验证大学生用户是否愿意持续练习。

本轮范围：
- 登录页
- 题库练习页
- 语音反馈页
- 学习计划页
- 微信分享结果页

设计约束：
- 移动优先
- 首屏加载快
- 适合中文用户
- 简洁、明确、可连续练习

依赖输入：
- UI Designer 的页面草图
- Backend Architect 的 API 定义
- Product Manager 的验收标准

你的输出：
- 页面结构说明
- 组件设计
- 状态管理建议
- 实现代码
- 风险说明
```

###### 为什么这是最佳实践

因为 Agent 最擅长的是：

- 在清晰约束下做深度产出

而不是：

- 在混乱背景里自己猜任务边界

---

##### 6. 把 “成功指标” 前置，而不是最后补

你给的项目内容里有一个很强的特点：

> 每个 Agent 都强调成功指标和可衡量成果。

这是很对的，真正的最佳实践是把这个做得更彻底。

###### 在本实例里，建议建立三层指标

###### 业务指标
- 注册转化率
- 首次练习完成率
- 7 日留存
- 分享率

###### 产品行为指标
- 每次会话平均练习题数
- 语音功能使用率
- 学习计划完成率
- 用户中断点分布

###### 工程质量指标
- 首屏加载时间
- API 错误率
- AI 响应时间
- 崩溃率 / 严重 Bug 数

###### 为什么这是最佳实践

因为：

- `增长黑客`看的是转化
- `产品经理`看的是留存与价值验证
- `前端开发人员`看的是性能
- `现实验证者`看的是可发布性

如果一开始没有统一指标，最后每个 Agent 都会说自己 “完成了”，但项目仍然失败。

---

##### 7. 让测试 Agent 介入得更早，而不是上线前才找它们

你提供的项目里有：

- `证据收集者`
- `现实验证者`
- `性能基准测试工具`
- `API Tester`
- `无障碍审计员`

很多团队会在最后才找这些角色，这其实不是最佳实践。

###### 正确做法

在阶段 2 设计完成后，就让测试类 Agent 提前介入。

###### 例如

###### `API Tester`
在 API 方案阶段就输出：

- 哪些接口容易缺字段
- 哪些错误码需要标准化
- 哪些边界场景必须测试

###### `无障碍审计员`
在 UI 稿阶段就输出：

- 按钮对比度是否足够
- 表单标签是否清晰
- 语音反馈是否有文本替代

###### `证据收集者`
在开发中期就要求：

- 核心页面截图基线
- 响应式布局证据
- 关键流程录屏

###### 为什么这是最佳实践

因为这能避免：

- 功能做好了才发现流程不通
- 样式全部写完才发现可访问性不合规
- 上线前才发现移动端页面崩坏

---

##### 8. 把 “提示词工程” 升级成 “工作流工程”

这个项目最有价值的地方，不是 agent persona 本身，而是：

- 身份
- 规则
- 流程
- 成功指标
- 交付物模板

所以最佳实践不是 “写更花哨的提示词”，而是 “设计更稳定的工作流”。

###### 一个推荐工作流

```markdown
1. Product Manager 定义目标与范围
2. Trend Researcher 输出市场与竞品洞察
3. UI Designer 与 Backend Architect 并行给出方案
4. Frontend Developer / AI Engineer 按方案实现
5. API Tester / Evidence Collector 做中期验证
6. Reality Checker 做发布前门禁
7. Growth Hacker 设计首轮增长实验
8. Analyst Reporter 搭建复盘指标
```

###### 为什么这是最佳实践

因为 Agent 的可复用性，来自流程可复制，而不是角色名称本身。

**节点 1：项目定义阶段 —— 先用 Product Manager，不要先用开发 Agent**

这是最容易做错的一步。

很多人拿到 agent 之后，会先问：

- 帮我做个 MVP
- 帮我写个首页
- 帮我想技术方案

这会导致方向混乱。

正确操作是：先激活`Product Manager`。

你在这一节点的详细操作：

1. 给`Product Manager`明确项目背景
2. 要求它只输出 PRD，不做技术实现
3. 把输出沉淀到`docs/product-requirements.md`

你可以这样发指令：

```text
请切换到 Product Manager 模式。

基于 docs/project-brief.md 的内容，为 “AI 英语面试练习 MVP” 生成一份面向中国大学生市场的 MVP PRD。

要求：
1. 输出目标用户、问题定义、核心场景、MVP 范围、非目标
2. 给出用户故事和验收标准
3. 所有内容必须围绕 4 周上线、快速验证
4. 不要扩展成大而全平台
5. 输出结构适合直接保存到 docs/product-requirements.md
```

这一步的最佳实践操作细节：

- 只让它管 “做什么” 和 “为什么做”
- 不要让它直接定义数据库和前端组件
- 如果输出太宽泛，继续追问 “请收缩范围到首版 4 个功能”
- 如果它提了很多 “未来能力”，你要让它移到 “后续版本”

这一节点的产物必须包括：

- 用户画像
- 核心价值主张
- MVP 功能边界
- 非目标
- 成功指标
- 验收标准

如果没有这些，后面的 agent 会一直跑偏。

**节点 2：市场与中国本地化验证 —— 使用 Trend Researcher / China Market Localization 类 Agent**

因为你的产品是面向中国市场，这一步不能省。

这一节点的目标是回答：

- 中国学生是否真的有这个需求
- 他们在哪些场景使用
- 有哪些本地竞品或替代品
- 微信生态、内容传播、用户习惯会如何影响产品设计

你要激活研究类 agent，必要时再加中国市场相关 agent。

推荐操作方式：

先给它 PRD，再让它做验证，而不是让它从零发散。

示例指令：

```text
请切换到 Trend Researcher 模式。

基于 docs/project-brief.md 和 docs/product-requirements.md，
请分析这个 AI 英语面试练习 MVP 在中国大学生市场的机会与风险。

请输出：
1. 目标用户的真实需求场景
2. 可能的替代方案和竞品类型
3. 中国市场特有的渠道与行为习惯
4. 用户最可能在意的 5 个问题
5. 对 MVP 功能范围的修正建议

请把结果整理成适合保存到 docs/market-research.md 的结构化文档。
```

如果仓库里有偏中国市场、微信、Xiaohongshu、Zhihu、Baidu 相关 agent，可以追加问：

```text
从中国用户获取和分享习惯角度，补充：
- 微信分享是否必要
- 小红书 / 知乎内容触达是否适合首轮增长
- 用户对 AI 口语打分的信任门槛是什么
```

这一步的详细操作重点：

- 不是让 agent 写 “行业报告”
- 而是逼它回答 “这个 MVP 应不应该这样做”
- 最终要形成对 PRD 的修订

你应当把研究结果反哺给`Product Manager`，让它更新 PRD：

```text
请回到 Product Manager 视角。
基于 docs/market-research.md 的发现，修订 docs/product-requirements.md。
保留 MVP 核心目标，但把不适合中国首发市场的部分删掉或降级。
```

这就是 agent 间的第一次交接。

**节点 3：定义用户体验与信息结构 —— 使用 UX/UI 相关 Agent**

这一节点不要急着做高保真图，先做信息架构。

你要先让`UI Designer`或`UX Architect`帮你定义：

- 用户进入产品后的最短路径
- 页面层级
- 关键页面上的信息优先级
- 中文用户更容易理解的交互方式

推荐先让它输出低保真结构，而不是视觉稿。

你可以这么操作：

```text
请切换到 UI Designer 模式。

基于 docs/product-requirements.md 和 docs/market-research.md，
为这个面向中国大学生的 AI 英语面试练习 MVP 设计信息架构与核心页面结构。

请输出：
1. 用户主流程
2. 页面列表
3. 每个页面的主要目标
4. 每个页面的内容优先级
5. 移动端优先的布局建议

暂时不要输出视觉风格图，请先输出可用于产品和前端对齐的结构文档。
结果保存为 docs/ui-spec.md
```

然后第二轮，再让它做视觉与组件规则：

```text
继续作为 UI Designer。

在 docs/ui-spec.md 基础上，补充：
1. 视觉方向
2. 字体、颜色、间距、按钮、卡片等设计 token
3. 适合中国学生用户的界面语气
4. 题目练习页、语音反馈页、学习计划页的组件建议

要求：
- 风格简洁、可信、轻学习感
- 不要过度 “AI 科幻”
- 移动端优先
```

这里的最佳实践是：

- 第一轮做结构
- 第二轮做视觉
- 不要一轮里同时让它搞清流程、文案、颜色、组件、动效全部内容

你最终要拿到的是一个能被前端直接消费的文档，而不是 “审美建议”。

**节点 4：后端方案设计 —— 使用 Backend Architect**

这一步你要做的是把产品需求变成可实现的服务边界。

你要给`Backend Architect`的输入：

- `docs/product-requirements.md`
- `docs/ui-spec.md`
- 如果有 AI 需求描述，也一起给

你的操作示例：

```text
请切换到 Backend Architect 模式。

基于 docs/product-requirements.md 和 docs/ui-spec.md，
为 AI 英语面试练习 MVP 输出一份首版后端技术方案。

请包含：
1. 核心服务模块
2. API 列表
3. 数据模型
4. 用户、练习记录、语音反馈、学习计划的数据关系
5. 鉴权方案
6. 日志与错误处理建议
7. 首版可以接受的技术妥协

要求：
- 适合 4 周内上线 MVP
- 优先简单、稳定、易扩展
- 不要设计过度复杂的微服务
- 输出保存为 docs/backend-spec.md
```

你这里要特别盯住两个点：

- 是否过度设计
- 是否和 MVP 节奏匹配

如果它开始提：

- 拆 6 个微服务
- 上 Kafka
- 全量事件总线
- 复杂多租户体系

你就要立即收回来：

```text
请把方案收缩为单体优先 / 模块化单体，目标是 4 周 MVP，不做企业级过度设计。
```

这就是你在使用 agent 时必须掌握的控制动作：不是接受第一轮输出，而是持续 “收边界”。

**节点 5：AI 能力设计 —— 使用 AI Engineer**

这一节点的目标不是 “上 AI”，而是明确：

- AI 到底在哪个环节产生价值
- 调用什么模型
- 输入输出格式是什么
- 如何降低不稳定性
- 如何把 AI 能力嵌入产品流程

你要把产品需求和后端方案一起喂给`AI Engineer`。

操作示例：

```text
请切换到 AI Engineer 模式。

基于 docs/product-requirements.md 和 docs/backend-spec.md，
设计本项目首版 AI 能力方案。

重点功能：
1. 英语口语练习后的反馈
2. 面试回答质量点评
3. 学习计划推荐

请输出：
- 每个 AI 功能的输入 / 输出结构
- Prompt 或推理链建议
- 模型调用建议
- 成本控制方案
- 错误兜底策略
- 哪些内容必须结构化返回，便于前端渲染

结果保存为 docs/ai-spec.md
```

这里要特别注意，很多 AI 类 agent 会输出很抽象的话。你必须追问到结构化：

```text
请把 “语音反馈” 部分改写为明确 JSON 返回结构，包括：
- pronunciation_score
- grammar_feedback
- confidence_feedback
- suggested_answer
- next_action
```

这一步是非常关键的，因为如果 AI 输出结构不清，前端和后端很难稳定接入。

最佳实践是：

- 每个 AI 功能都要求 “结构化输出”
- 每个 AI 功能都要求 “失败兜底”
- 每个 AI 功能都要求 “成本估算”
- 每个 AI 功能都要求 “误判风险说明”

**节点 6：定义中国生态接入点 —— 使用 WeChat Mini Program Developer / China 相关 Agent**

虽然你的 MVP 可能是 Web 应用，但如果面向中国市场，微信生态通常会影响传播和留存。

这里不是一定要立刻做小程序，而是让相关 agent 评估：

- 首版是否需要微信登录
- 是否要支持分享卡片
- 是否需要公众号 / 小程序作为后续入口
- 是否存在合规或体验问题

你可以这么操作：

```text
请切换到 WeChat Mini Program Developer 模式。

当前产品首版是 Web MVP，但面向中国大学生市场。
请评估微信生态在首版中的最小接入方案。

请输出：
1. 首版是否建议微信登录
2. 是否建议支持微信分享卡片
3. 后续迁移到小程序的成本与收益
4. 对前端与后端架构的影响
5. MVP 阶段最值得保留的微信能力

结果补充到 docs/market-research.md 或单独保存到 docs/wechat-strategy.md
```

这一步的作用，不是马上开发，而是避免你后面发现：

- 产品适合微信传播，但架构完全没留入口
- 分享链路非常重要，但前端页面没有适配
- 文案和页面设计不适合微信内打开

**节点 7：前端实施规划 —— 使用 Frontend Developer**

现在你才真正进入开发侧。

你不要一上来就让前端 agent 写全量代码，先让它给出实施方案。输入文档应包括：

- `docs/product-requirements.md`
- `docs/ui-spec.md`
- `docs/backend-spec.md`
- `docs/ai-spec.md`

示例操作：

```text
请切换到 Frontend Developer 模式。

基于以下文档：
- docs/product-requirements.md
- docs/ui-spec.md
- docs/backend-spec.md
- docs/ai-spec.md

请先不要直接输出完整代码。
先输出：
1. 页面路由结构
2. 组件拆分方案
3. 状态管理方案
4. API 对接方式
5. AI 结果渲染方式
6. 移动端适配重点
7. 性能和可访问性注意事项

要求：
- 适合快速 MVP 开发
- 结构清晰，便于后续逐页实现
```

等它给出实施方案后，再逐页生成代码。

这是非常重要的最佳实践：

- 先生成 “实现蓝图”
- 再逐页面、逐模块生成代码
- 不要让它一口气生成全项目，否则容易失控

后续逐页开发时，你可以像这样操作：

```text
请实现登录页与首页，基于 docs/ui-spec.md 的页面结构和视觉规范。
要求：
- 使用项目当前技术栈
- 代码可直接放入现有目录
- 包含 loading /error/empty 状态
- 保持移动端优先
```

然后继续：

```text
请实现题库练习页。
要求：
- 展示题目
- 支持录音入口占位或上传入口
- 展示答题进度
- 预留 AI 反馈区域
- 埋点位置先用注释标出
```

你会发现，这样比 “帮我把整个项目写完” 稳定很多。

---

**节点 8：埋点与转化设计 —— 使用 Tracking & Measurement Specialist**

这是很多人忽略但非常值钱的一步。

你做 MVP 的目标不是 “产品上线”，而是 “验证是否有效”。所以必须在开发中期就引入埋点 agent。

你的输入：

- PRD
- 页面结构
- 前端实施方案

操作示例：

```text
请切换到 Tracking & Measurement Specialist 模式。

基于：
- docs/product-requirements.md
- docs/ui-spec.md
- 前端页面结构方案

请输出 MVP 的埋点方案，包含：
1. 关键业务事件
2. 每个事件的触发时机
3. 事件参数
4. 事件命名规范
5. 哪些指标用于判断 MVP 成功

请保存为 docs/analytics-plan.md
```

你应该拿到类似内容：

- `landing_view`
- `signup_started`
- `signup_completed`
- `practice_started`
- `practice_completed`
- `ai_feedback_viewed`
- `study_plan_generated`
- `wechat_share_clicked`

然后再把这个埋点文档交给前端 agent：

```text
请基于 docs/analytics-plan.md，
把关键埋点加入当前前端实现方案中。
如果暂时不接真实分析平台，请封装统一的 track 方法，并在关键交互点调用。
```

这就是 agent 间的高质量交接：不是重复解释，而是把文档作为标准。

---

**节点 9：代码审查与风险收缩 —— 使用 Code Reviewer**

当你完成一部分前后端代码后，不要等最后才 review。

你应该让`Code Reviewer`周期性介入。仓库里本身就有`Code Reviewer`这类角色，这正好适合做中途质量控制。

你的操作方式：

- 给它看实际代码文件
- 给它看 PRD 和关键技术规范
- 明确要求它以 “找问题” 为主，而不是表扬

示例指令：

```text
请切换到 Code Reviewer 模式。

请基于以下背景审查当前实现：
- docs/product-requirements.md
- docs/backend-spec.md
- docs/ai-spec.md

重点关注：
1. 是否存在与 MVP 目标不一致的过度实现
2. 是否有明显的状态管理风险
3. 是否存在接口契约不清问题
4. 是否有移动端体验缺陷
5. 是否存在 AI 返回结果不可控导致的渲染问题

请按严重程度列出问题和建议，不要泛泛总结。
```

最佳实践是：

- 每实现 1-2 个核心模块就 review 一次
- 不要只在最后一次性 review 整个项目
- review 输出要回流到具体文档或 issue 列表中

---

**节点 10：证据化验证 —— 使用 Evidence Collector**

这个 agent 的价值不在 “看代码”，而在 “看结果”。

当主要页面和流程跑通后，让`Evidence Collector`介入，要求它从 “可见证据” 的角度列检查项。

你可以这样用：

```text
请切换到 Evidence Collector 模式。

当前 MVP 已完成核心页面开发。
请为以下流程制定证据化验收清单：
1. 注册或登录流程
2. 题库练习流程
3. 语音反馈展示流程
4. 学习计划生成流程
5. 微信分享卡片流程

请输出：
- 每个流程需要的截图证据
- 每个流程需要的录屏证据
- 桌面端与移动端都要验证的页面
- 哪些状态必须被覆盖：loading /success/error /empty
```

然后你按它的清单去补证据，或让它根据现有截图判断是否缺漏。

这一步的实际价值是：

- 防止 “代码写了但流程没打通”
- 防止 “只有 happy path，没有失败状态”
- 防止 “PC 看着正常，手机崩掉”

---

**节点 11：上线门禁 —— 使用 Reality Checker**

这是你整个流程里最后的裁决 agent。

很多人会把这个角色当成 “再看一遍”，但正确用法是：让它做 go /no-go 决策。

它的输入应包括：

- PRD
- 埋点方案
- 截图或证据
- 当前已知缺陷
- 关键页面和流程说明

你可以这样操作：

```text
请切换到 Reality Checker 模式。

请作为发布前的最终质量闸门，审核这个 AI 英语面试练习 MVP 是否适合上线给首批中国学生用户测试。

输入包括：
- docs/product-requirements.md
- docs/ui-spec.md
- docs/backend-spec.md
- docs/ai-spec.md
- docs/analytics-plan.md
- 当前缺陷列表
- 当前证据截图与录屏说明

请输出：
1. 是否建议上线：go /no-go
2. P0 阻塞问题
3. P1 重要但可带着上线的问题
4. 当前最大产品风险
5. 当前最大工程风险
6. 当前最大数据验证风险
7. 上线后第一周必须观察的指标
```

这是一个非常实用的做法，因为它会逼你站在 “真实发布” 的角度检查，而不是 “差不多就行”。

---

**节点 12：冷启动与增长实验 —— 使用 Growth Hacker / 内容类 Agent**

产品上线后，并不是结束。

你要立刻进入验证环节。这时激活增长相关 agent，不是让它空谈传播，而是让它基于你这个 MVP 的真实形态设计首轮实验。

示例：

```text
请切换到 Growth Hacker 模式。

当前产品是一个面向中国大学生的 AI 英语面试练习 Web MVP，
具备题库练习、AI 反馈、学习计划、微信分享卡片。

目标：
在低预算下获得首批 100 位种子用户，并验证激活与留存。

请输出：
1. 最适合的 3 个获客渠道
2. 每个渠道的内容形式建议
3. 用户从看到内容到开始练习的最短转化路径
4. 首轮 A/B 实验建议
5. 哪些数据能证明这个产品值得继续做
```

如果仓库里有：

- `Xiaohongshu Specialist`
- `Zhihu Strategist`
- `WeChat Official Account Manager`
- `SEO Specialist`
- `Content Creator`

你可以针对不同渠道单独启用。

比如：

```text
请切换到 Xiaohongshu Specialist 模式。
为这个产品设计 10 条适合小红书发布的选题，目标是吸引有英语求职压力的大学生。
```

或者：

```text
请切换到 Zhihu Strategist 模式。
设计适合知乎问答场景的冷启动内容策略，目标是导流到 MVP 试用页。
```

这一步的最佳实践是：

- 增长 agent 不要在产品还没成型时就提前主导
- 但产品一旦具备试用能力，就要立即接入
- 所有增长建议都必须绑定可测指标

---

**节点 13：复盘与下一轮规划 —— 再次回到 Product Manager**

完成首轮测试后，不要让 agent 继续无序演化。你需要回到`Product Manager`，做复盘收敛。

你要把以下信息给它：

- 埋点结果
- 用户反馈
- 证据清单
- 缺陷清单
- 增长实验结果

操作示例：

```text
请切换到 Product Manager 模式。

基于以下输入：
- 上线后一周数据
- 用户反馈
- docs/analytics-plan.md
- 缺陷清单
- 增长实验结果

请输出：
1. 本轮 MVP 验证结论
2. 哪些假设成立，哪些不成立
3. 下一版本必须做的 3 件事
4. 应该暂停或删除的功能
5. 下一轮版本规划建议

要求：
- 以数据与证据为依据
- 保持范围克制
- 仍以中国大学生市场验证为核心
```

到这里，你就完成了一次完整的多 - agent 闭环。

---

**如何在实际对话里切换和衔接 Agent**

你真正使用`agency-agents`时，不是每次从零描述一遍，而是用 “固定切换模式 + 文档引用”。

建议你的每次调用都遵守这个格式：

1. 指定角色
2. 指定输入文档
3. 指定输出文档
4. 指定边界
5. 指定格式

推荐模板：

```text
请切换到 [Agent 名称] 模式。

项目背景：
参考 docs/project-brief.md

输入文档：
- docs/xxx.md
- docs/yyy.md

你的任务：
[只写一个具体任务]

输出要求：
1. 输出成结构化 Markdown
2. 适合保存到 docs/zzz.md
3. 明确列出风险、假设与建议
4. 不要超出 MVP 范围
```

这样做有几个好处：

- agent 输出更稳定
- 各节点可追溯
- 后续容易复用
- 新 agent 接手时也看得懂

**一个最小可执行的真实调用顺序**

如果你今天就要开始，我建议你按这个顺序用：

1. `Product Manager`
2. `Trend Researcher`
3. `Product Manager`二次收敛
4. `UI Designer`
5. `Backend Architect`
6. `AI Engineer`
7. `Frontend Developer`
8. `Tracking & Measurement Specialist`
9. `Code Reviewer`
10. `Evidence Collector`
11. `Reality Checker`
12. `Growth Hacker`
13. `Product Manager`复盘

这是最稳的一条链。

---

**使用 agency-agents 时最容易犯的 6 个错误**

- 一开始同时启用太多 agent，导致建议互相冲突
- 不建共享文档，所有上下文都靠聊天历史
- 让 agent 输出 “想法”，而不是输出 “文档和交付物”
- 不控制范围，导致每个角色都在扩需求
- 只在最后才让 reviewer 和 reality checker 介入
- 没有指定成功指标，最后不知道 MVP 是否有效

---

**你可以直接照抄的一套主控话术**

如果你想把自己当成 “总协调人”，下面这段话术非常实用：

```text
这是一个 4 周内上线的中国市场 AI 学习产品 MVP。
所有建议必须服务于 “快速验证用户价值”。
请避免过度设计、避免扩展为完整平台。
如果有多个方案，请优先推荐：
- 开发更快
- 风险更低
- 更容易验证
- 更适合中国大学生用户
的那个方案。
输出必须是下一位 agent 能直接接手的文档或结构化结果。
```

这段话建议你在每个 agent 调用时都带上。
