## 分析要点

- **核心高价值点**：最值得保留的是将规格批准设为编辑前置门禁、将ERC/DRC设为完成门禁，从工具权限层约束代理，而不是仅依赖提示词要求其自律。
- **留存建议**：建议精读并存档，重点保留其受约束代理工作流与硬件验证机制（提供了可复用的规格门禁、文件编辑、变更传播、工具验证和失败回滚流程，对Agent开发及产品交付具有长期参考价值。）

**知识要点**

- 高风险Agent可通过限制工具暴露面来保证流程不可绕过，例如仅向MCP宿主提供完整的结果级工具，而不开放原始文件编辑能力。
- 硬件变更流程可组织为提出规格、编辑真实工件、传播引用、执行ERC/DRC、记录理由和提交快照的闭环。
- 确定性检查与生成式操作应分离：检查、漂移检测和BOM导出无需调用LLM，可安全用于CI和交付门禁。

**行动项**

- 在测试分支安装Copperhead，并先运行doctor、init和check验证环境及现有KiCad项目。
- 选择一个低风险PCB改动，用dry-run或演示项目验证规格门禁、ERC/DRC和失败回滚流程。
- 参考其MCP接口设计，将自有Agent的底层编辑工具收口为不可绕过的完整流水线工具。

[![copperhead](https://raw.githubusercontent.com/copperheadhq/copperhead/main/docs/branding/lockup-transparent.png)](https://copperhead.sh)

电路板的 Cursor。一个 AI 代理，能够根据提示设计、记录并验证真实 PCB，直接作用于现有的 KiCad 代码仓库。

[![copperhead agent shell demo](https://raw.githubusercontent.com/copperheadhq/copperhead/main/assets/copperhead.gif)](https://raw.githubusercontent.com/copperheadhq/copperhead/main/assets/copperhead.gif)

> 状态：早期阶段。第一阶段已实现，CLI 可运行。技术规范是唯一权威来源；在 1.0 版本之前，界面可能会有变动。

完整文档位于 docs.copperhead.sh。

面向硬件的 AI 产品开发代理：从产品简报直达可制造文件、固件和构建计划。

- **`copperhead create`** ：从自然语言简报开始的完整流程：规格、架构、元器件选型、原理图、初稿布局，然后是 Gerber 文件、固件框架和开发计划。
- **`copperhead do "<change>"`** ：以编码代理操作代码库的方式，对现有的 KiCad 代码仓库进行操作。

它读取并编辑真实的 `.kicad_sch` / `.kicad_pcb` 文件（s 表达式文本），将 Markdown 设计文档作为记忆进行维护，将每次更改传播到所有引用它的工件中，并通过运行 `kicad-cli` ERC/DRC 直到检查通过来验证自身工作。

#### Install

如果您更倾向于手动安装：

```
npm install -g copperhead   # or: npx copperhead check
```

想要一键安装？ `install.sh` 会检查以下前置条件，安装 copperhead（通过 npm 全局安装，或在代码库内运行时从源码构建），并使用 `copperhead doctor` 验证结果：

```
./install.sh                # interactive: asks before installing anything
./install.sh --yes          # assume yes to the install prompts
./install.sh --check-only   # report what is missing, install nothing
```

该脚本设计上较为保守：它从不运行 `sudo` ，也从不修改 shell 配置；每当无法安全地自行操作时，它会打印出需要您手动运行的精确命令。重复运行是安全的：在已就绪的机器上，它不会安装任何内容，并以退出码 0 结束。

##### Requirements

- Node.js ≥ 20
- KiCad ≥ 8，且 `kicad-cli` 已加入 PATH（在 Windows 和 macOS 上，copperhead 也会自动搜索标准安装目录；可通过 `COPPERHEAD_KICAD_CLI` 覆盖）
- 一个模型后端：本地安装的、经 ChatGPT 认证的 Codex CLI，已登录的 Cursor Agent CLI（ `agent login` ），已登录的 Claude Code（参见已保存的登录），或环境中的 `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` 。 `check` 从不调用 LLM。

#### Quick start

在现有的 KiCad 代码仓库中：

```
export ANTHROPIC_API_KEY=...   # or OPENAI_API_KEY; optional: with no key, `copperhead` offers a model picker
copperhead init                # scaffold docs/ from the schematic; idempotent
copperhead                     # interactive agent shell (Claude Code–style REPL)
copperhead demo --tour          # what the agent does (no LLM)
copperhead demo --model cursor # full USB-C breakout create pipeline
# or one-shot:
copperhead do "add reverse-polarity protection on VIN"
copperhead check               # ERC + DRC + doc drift; no LLM, CI-safe
```

想从零开始？编写一份产品简报并运行 `copperhead create --brief brief.md` 。examples/ 目录中提供了按难度分类的现成简报，以及一份关于哪个简报被设计为注定失败的说明。

当 Codex CLI 已经认证时，无需模型 API 密钥：

Plain `codex` 遵循你的 Codex 模型配置。如需显式指定模型，请使用 `codex:<model-id>` 。如果可执行文件不在 `PATH` 中，请设置 `COPPERHEAD_CODEX_PATH=/absolute/path/to/codex` 。可选 SDK 也会安装一个兼容的启动器；如需全局安装，可使用 `COPPERHEAD_CODEX_PATH="$(npm root -g)/@openai/codex/bin/codex.js"` 作为后备方案。

Codex 的只读沙箱阻止原生写入，但不会限制原生读取。Copperhead 指示 Codex 不要使用其自身的文件系统工具，但 CLI 在技术上仍可读取诸如 `.env` 之类的文件。Codex 还会将会话日志保存在 `~/.codex/sessions/` 下；这些文件位于 Copperhead 的转录编辑边界之外，应根据你的本地数据保留策略进行保护。

这是一个循环，看起来很像结对编程，只不过代码库是一块电路板。

1. 从文档开始。每个决策都记录在设计文档中，因此代理会先阅读这些文档，从而了解整个设计，而不仅仅是眼前的部分。
2. 讨论变更。描述你想要什么（“添加外部钥匙插孔”、“降低休眠电流”）。代理会提出部件和电路方案；你提出异议，直到逻辑站得住脚为止。
3. 编辑真实文件。代理直接将更改写入 KiCad 原理图及设计文档，并在所有地方使用相同的部件名称和网络名称，确保内容不会偏离。
4. 传播。更改一个值，比如充电电流或引脚，它会自动传递到所有引用它的文档和原理图中。这个枯燥且容易出错的步骤，恰恰是代理最擅长的。
5. 检查工作。代理运行 ERC/DRC，读回错误并修复它们。在工具确认无误之前，没有任何事情算是“完成”。
6. 写下原因。每个实际决策旁边都附上一行理由，这样下一次修改就不会悄悄将其撤销。

两个不变量使这一点值得信赖：

1. 没有规格说明就不开始。代理在有效的变更提案存在之前无法触碰 KiCad 文件；在此之前，编辑工具在结构上不可用。每次编辑都可追溯到有文档记录的意图。
2. 在工具达成一致之前，没有任何事情算是“完成”。每次文件变更后，代理在报告成功之前都会运行一次 ERC/DRC 检查。

规格把关进入，验证把关输出：设计不能偏离其需求，因为偏离就是构建失败。

#### CLI

```
copperhead init [--path hardware/]   # scaffold docs/ from an existing schematic; idempotent
copperhead do "<change request>"     # the core loop: propose, edit, verify, propagate, commit
copperhead skill list                # registered skills (no LLM)
copperhead skill run generate-report # read-only design report (needs a model)
copperhead check                     # ERC + DRC + doc-drift + spec validation; no LLM calls (alias: verify)
copperhead doctor                    # env preflight: node, kicad-cli, git, openspec, provider credential; no LLM/network
copperhead sync [--dry-run]          # verify the whole design state, resolve drift
copperhead create --brief brief.md   # brief → full output package
copperhead export bom --supplier jlcpcb   # supplier-ready ordering file from docs/BOM.md
copperhead mcp                       # EXPERIMENTAL: serve the gated pipeline to MCP hosts over stdio
```

全局标志： `--repo <path>` （默认值：当前工作目录）和 `--json` 用于机器可读输出。 `--model` 在 `do` 、 `sync` 、 `create` 、 `skill run` 和 `doctor` 上可用； `--interactive` 仅在 `do` 和 `create` 上可用； `do` 还接受 `--dry-run` 、 `--max-turns` 和 `--allow-dirty` 。

`copperhead create` 仍然使用其自身硬编码的阶段；这些阶段尚不是技能。

`--model` 接受 `gpt-5` （OpenAI）、 `claude` / `claude-<id>` （Anthropic API）、 `claude-code` / `claude-code:<id>` （Claude Code，已保存登录）、 `cursor` / `cursor:<id>` （Cursor Agent CLI，已保存登录）以及 `codex` / `codex:<id>` （Codex CLI，已保存登录）。路由按前缀进行； `claude-code` 在 `claude` 前缀之前匹配。 `compat:<id>` 通过 `COPPERHEAD_BASE_URL` 和 `COPPERHEAD_API_KEY_ENV` 定位任何兼容 OpenAI 的端点（Groq、OpenRouter、Gemini 或本地 Ollama）——每种配置的示例见 `.env.example` 和配置参考。

`--model cursor` 使用你在 `agent login` 中保存的登录信息驱动 Cursor Agent CLI，因此你可以在没有 `OPENAI_API_KEY` 或 `ANTHROPIC_API_KEY` 的情况下运行 copperhead。Cursor 在计划模式中纯粹用作推理后端：代理循环、安全门控以及每次文件编辑都保留在 copperhead 内部。

```
agent status
copperhead do "add reverse-polarity protection on VIN" --model cursor
```

如果 `agent` 不在 `PATH` 中，请将 `COPPERHEAD_CURSOR_PATH` 设置为 CLI 二进制文件（某些安装中也可作为 `cursor-agent` 使用）。Cursor 的 JSON 模式不报告令牌使用情况，因此运行摘要会显示 `--model cursor` 的 0 个令牌。

`--model claude-code` 通过 Claude Agent SDK 驱动 Claude Code，并复用你已保存的登录信息（来自 `claude setup-token` 的 `CLAUDE_CODE_OAUTH_TOKEN` ），因此 Claude 订阅可以在没有 `ANTHROPIC_API_KEY` 的情况下运行 copperhead。Claude Code 纯粹用作推理后端：代理循环、其安全门控以及每次文件编辑都保留在 copperhead 内部，与其他提供商完全一致。

```
claude setup-token                          # while logged into Claude Code
export CLAUDE_CODE_OAUTH_TOKEN=...           # the token setup-token printed
copperhead do "add reverse-polarity protection on VIN" --model claude-code
```

Claude Agent SDK 作为可选依赖随附，因此常规安装即可将其引入。copperhead 仅在你选择 `claude-code` 时加载它，若缺失（例如在 `npm install --omit=optional` 之后），则会打印一条可操作的错误信息，提示你通过 `npm i @anthropic-ai/claude-agent-sdk` 添加它。

copperhead 从不读取、复制或记录凭据；CLI 负责认证。依赖缺失或未认证的安装会以可操作的消息失败，且不会触碰任何内容。

`copperhead export bom` 将经过漂移检查的 `docs/BOM.md` 转换为供应商无需手动编辑即可接受的文件。它是确定性的、无 LLM、无网络的，在 `check` 所在的任何地方都安全，并且它读取 `BOM.md` （绝不读取原理图），因此继承了漂移保证；当 `BOM.md` 与原理图不一致时，它拒绝导出。

```
copperhead export bom --supplier jlcpcb                 # JLCPCB assembly CSV → outputs/jlcpcb-bom.csv
copperhead export bom --supplier digikey --boards 25    # DigiKey cart CSV, quantities for 25 boards
copperhead export bom --supplier mouser --spares 15     # Mouser cart CSV, 15% spare parts
```

- `--supplier <jlcpcb|digikey|mouser>` （必需）。JLCPCB 获取装配服务格式（Comment、Designator、Footprint、LCSC Part #，每行分组的设计 ators）；DigiKey 和 Mouser 获取购物车上传列表（MPN、制造商、数量、客户参考）。
- `--boards <n>` （默认 1）和 `--spares <percent>` （默认 10）设置订单数量： `ceil(perBoardCount × boards × (1 + spares/100))` ，对于被动元件线路（封装 `R_` / `C_` / `L_` ）则提升至 `perBoardCount × boards + 2` ；用镊子弄丢几个 0402 元件是常态，仅按百分比备料会在低数量被动元件上备料不足。
- 没有 MPN 的行，以及仍标记为 `UNVERIFIED` 的行，将从供应商文件中排除，并在 stderr 上的警告页脚中列出。 `--include-unverified` 将已标记但具有 MPN 的行重新纳入（它从不包含无 MPN 的行）。 `create` 阶段 6 还会自动生成 `outputs/jlcpcb-bom.csv` 。

`docs/BOM.md` 可在基础 `Refdes | Value | Footprint | MPN | Rationale` 之外携带可选的 `Manufacturer` 和 `LCSC` 列；导出器按表头匹配列，因此当您希望在供应商文件中填充这些列时，请添加它们； `init` 仅搭建基础列。仅追加列是安全的：保持 `Refdes | Value | Footprint` 在最前且顺序不变，因为漂移检查（ `check` / `sync` ，导出器以此作为门控）按位置读取这三列，因此重新排序会导致其比较错误的单元格，并以虚假的漂移消息拒绝导出。

没有黑箱：决策记录在仅追加的 `docs/DECISIONS.md` 中，每次运行都会在其记录旁边写入一份人类可读的摘要，每次运行的 `docs/CHANGELOG.md` 会叙述设计历史。

编码代理已经通过通用文件工具指向 KiCad 仓库，这意味着宿主代理可以在没有规格门禁、没有核实、没有回滚的情况下重写 `.kicad_sch` 。 `copperhead mcp` 弥补了这一缺陷：它将门控流水线以五个不透明的、结果级别的工具—— `copperhead_check` 、 `copperhead_do` 、 `copperhead_sync` 、 `copperhead_init` 、 `copperhead_doctor` ——提供给任何 MCP 宿主，不再提供更细粒度的工具。没有文件编辑工具，没有原始 KiCad 工具，也没有可绕过的部分循环工具，因此宿主代理无法通过任何调用序列跳过规格门禁或核实。

> 该接口是实验性的且不稳定。它声明了一个 `0.` 协议主版本：工具名称、输入和结果形状可能在任何发布中发生变化，在稳定化标准满足之前没有注册表列表。Claude Code 和通用 stdio 宿主的配置、配套技能、Codex 缺口以及这些标准都在 `integrations/` 中。

`copperhead_check` 、 `copperhead_init` 和 `copperhead_doctor` 不需要凭据； `copperhead_do` 和 `copperhead_sync` 与 `resolve: true` 配合时会以类型化错误拒绝，并指出缺失的环境变量名称。服务器自身不打开任何网络传输——仅 stdio，LLM 调用恰好发生在 CLI 已经执行它们的位置。

- 不是自动布线器。布线仍由人工完成或委派处理；copperhead 生成通过 DRC 检查的初稿，布局工具在此基础上进行优化。
- 不是新的编辑器。没有封闭生态；你安装的 KiCad 仍是编辑器。
- 不是责任工程师。由人工签字确认；代理绝不会声称设计已具备制造条件，只会说“ERC/DRC 检查通过”。

#### Simple demo

从本仓库的检出副本中，使用 USB-C 电源分线板的简要说明运行最小的 create-pipeline 演示：

```
npm run demo:simple
```

该脚本在 `demo-runs/usb-c-breakout/` 处创建或恢复一个 git 仓库，并运行：

```
copperhead create --brief examples/simple/usb-c-breakout.md
```

在 `--` 之后传递正常的创建标志，例如 `npm run demo:simple -- --model claude` 。如果某个阶段失败，重新运行相同的命令；演示仓库会保留一个基线提交并忽略运行记录，因此重试会从最后提交的设计状态开始。

更多简报（包括中等和困难级别）位于 examples/目录中。

#### Maturity

- **扎实。** `check` init `verify` 和 `/` 是确定性的、无 LLM 的，并且由离线测试套件针对真实 KiCad 夹具覆盖：脚手架、ERC/DRC、s 表达式读取器、漂移检测和制造导出在 CI 中全部通过。

#### Copperhead 的真正价值，不是“AI 画板”，而是给硬件代理装上护栏

Copperhead 把自己称为“电路板的 Cursor”，但这个类比容易让人误判。它最值得关注的并不是用一句提示生成 PCB，而是尝试把硬件设计改造成一种**有规格约束、可自动检查、可回滚、可追溯的仓库工作流**。

它直接读写 KiCad 的原理图和 PCB 文本文件，维护设计说明、BOM、决策记录与变更日志，并在修改后调用 `kicad-cli` 执行 ERC/DRC。真正有价值的是这条受控链路：先形成变更提案，再开放编辑能力；修改后传播相关信息，运行确定性检查；失败则回滚，成功也只报告“检查通过”，不宣称“可以制造”。

##### 关键创新是控制代理权限，而不是改进提示词

通用编码代理已经能修改 KiCad 文件，问题是它也能绕过规格、验证和记录，直接重写原理图。Copperhead 的应对方式，是把模型降为推理后端，把流程控制留在自己的程序里。

它设置了两个硬约束：**没有有效规格就不能编辑，没有工具验证就不能完成**。通过 MCP 暴露能力时，也只提供 `check`、`do`、`sync` 等结果级工具，而不开放原始文件编辑或半截流水线。这比要求模型“务必先检查”可靠得多，因为限制来自能力边界，不依赖模型是否遵守文字指令。

这是一种可迁移的代理产品设计：在高风险任务中，模型负责提出方案和处理例外，确定性程序负责权限、状态转换、验证与回滚。财务配置、基础设施变更、合规文档和工业设计，都可能采用类似结构。**可信代理的核心未必是模型更聪明，而是系统让错误难以越过关键关口。**

不过，README 对 MCP 的安全表述仍有隐含前提：宿主不能同时拥有另一套通用文件工具。Copperhead 可以保证自己的接口不可绕过，却无法阻止拥有仓库写权限的外部代理另走一条路。最终的控制还需要结合工具白名单、文件权限和 CI 分支保护。

##### ERC/DRC 解决的是一致性，不是工程正确性

项目对边界的说明相当诚实：它不是自动布线器，也不是责任工程师；布局只是通过 DRC 的初稿，仍需人工优化。ERC/DRC 能发现未连接、规则冲突和间距违规，却无法证明电路在真实环境中可靠，更不能覆盖热设计、EMI、器件供货、容差、可测试性和制造工艺。

因此，“Hardware as fast as software”目前更准确的含义是：**让硬件变更的协调成本更接近软件，而不是让物理验证本身变快。** 修改充电电流后，同步原理图、BOM、设计文档和采购文件，正是繁琐、规则明确又容易遗漏的工作，适合自动化；至于充电方案是否合理，仍需要工程判断和实测。

这种定位反而比“从简报直达可制造文件”更可信。短期产品机会可能不在全自动生成新板，而在既有 KiCad 项目的变更传播、文档防漂移、审计记录和采购导出——用户已有人工流程和真实痛点，结果也更容易验收。

##### 这是一个值得验证的架构原型，还不是成熟生产力

仓库明确承认：`check`、`init`、漂移检测和制造导出已有离线测试；但依赖实时模型的 `do`、`sync --resolve` 与 `create` 尚未观察到端到端验收通过。这意味着当前最可靠的是确定性基础设施，最吸引人的自动设计能力仍是待检验主张。

接下来真正决定价值的，不是演示能否生成一块简单 USB-C 分线板，而是它能否在复杂旧项目中稳定往返编辑 KiCad 文件，能否发现规格遗漏而非自信补全，以及人工复核时间是否显著低于手工修改。**Copperhead 已经提出了一个比“让 AI 自由操作工具”更成熟的答案；现在缺的是证据，证明这些护栏包围的不只是安全的失败，而是持续可用的工程产出。**

## 口播总结（1）

### 2026-09-20 00:35:12

Copperhead 想解决一个硬件开发中的核心难题：能不能像使用编程代理修改代码一样，让人工智能直接修改真实的电路板项目，同时又不牺牲可追溯性和验证流程？它把自己定位成“电路板领域的 Cursor”。不过项目仍处于早期阶段，命令行工具已经可以运行，但在一点零版本之前，界面和流程仍可能变化。

Copperhead 面向的是 KiCad 项目。KiCad 是一套开源电子设计软件。它的原理图和电路板文件本质上是结构化文本，因此代理可以直接读取和编辑，而不是只能生成一段供人复制的建议。

使用 Copperhead 有两种主要方式。如果已经有 KiCad 仓库，可以让它执行一项具体修改，比如“在输入电源上增加反接保护”或者“降低休眠电流”。如果从零开始，则可以给它一份自然语言产品简报。它会尝试完成规格整理、系统架构、元器件选择、原理图、初步布局，以及 Gerber 制造文件、固件框架和开发计划。

真正重要的，不是人工智能会不会画原理图，而是 Copperhead 给整个过程设置了两道硬约束。

第一道约束是，没有规格说明，就不能开始编辑。代理必须先形成有效的变更提案，记录准备修改什么，以及为什么修改。在这之前，编辑 KiCad 文件的工具在结构上不可用。也就是说，每次实际编辑，都必须对应一项已经记录的设计意图。

第二道约束是，工具没有达成一致，就不能宣布完成。每次修改之后，Copperhead 都会运行 ERC 和 DRC。ERC 是电气规则检查，用来发现未连接引脚、电源冲突等原理图问题。DRC 是设计规则检查，用来发现间距、尺寸或连接关系等电路板问题。代理会读取检查结果，继续修复，直到检查通过。它最多只能说“ERC 和 DRC 已通过”，不能声称产品已经适合制造，更不能代替责任工程师签字。

这两道门可以概括成一句话：规格负责把关入口，验证负责把关出口。

中间的工作方式，则很像结对编程。代理先阅读设计文档，理解整个产品，而不只是当前文件。人与代理讨论方案，包括器件和电路选择。方案确定后，代理修改真实的 KiCad 文件，并同步维护物料清单、设计决策和变更记录。

这种同步能力很关键。硬件开发中，一个充电电流、一个引脚编号或一个网络名称，往往同时出现在原理图和多份文档里。人工修改时，很容易只改一处。Copperhead 会把变更传播到所有引用位置，并检查文档与设计文件是否出现漂移。每个重要决定旁边还会保留理由，防止未来的修改无意中推翻原来的设计约束。

常用操作也围绕这条流程展开。初始化命令会根据已有原理图建立文档结构，而且可以重复运行。执行变更的命令会完成提案、编辑、验证、传播和提交。检查命令则只运行 ERC、DRC、规格验证和文档漂移检查，不调用大语言模型，因此适合放进持续集成流程。

Copperhead 还提供物料清单导出。它可以把经过漂移检查的物料清单，转换成嘉立创、DigiKey 或 Mouser 可接受的订购文件。这个过程是确定性的，不使用人工智能，也不访问网络。如果物料清单与原理图不一致，它会拒绝导出。没有制造商料号，或者仍标记为“未经验证”的器件，也会默认排除并发出警告。

为了降低人工智能误操作的风险，每次变更都运行在 Git 快照中。如果验证失败，Copperhead 会回滚。因此按照项目的说法，最坏的结果应该是一次没有实际修改的提交，而不是被破坏的原理图。不过维护者仍然建议始终在独立分支上工作。

Copperhead 可以连接多种模型后端，包括 OpenAI、Anthropic、Claude Code、Cursor Agent 和 Codex，也能接入兼容 OpenAI 接口的其他服务。但模型只负责推理。代理循环、安全门控和文件编辑仍由 Copperhead 控制。

它还提供一个实验性的 MCP 接口，让其他人工智能宿主调用完整流程。这里的设计重点是，不暴露原始文件编辑工具，只提供检查、执行变更、同步、初始化和环境诊断等结果级工具。这样，宿主代理就不能通过组合底层调用，绕过规格门禁或最终验证。不过这套接口目前仍不稳定，工具名称和数据格式都可能变化。

这个项目的边界也必须说清楚。Copperhead 不是自动布线器。它可以生成通过设计规则检查的初稿，但最终布线仍需要人工完成或另行委派。它也不是新的电路板编辑器，真正的编辑环境依旧是 KiCad。最重要的是，它不是责任工程师。规则检查通过，只能说明机器检查没有发现对应错误，不等于设计已经完整、安全或可制造。

当前成熟度存在明显分层。初始化、检查、漂移检测、文件读取和制造导出等确定性功能，已经由离线测试覆盖。相比之下，真正依赖模型的代理循环，包括自动修改、自动同步和从简报创建完整项目，虽然已经实现了结构化控制，但项目方明确表示，尚未观察到完整的端到端验收通过，因此实际使用中应当预期会遇到粗糙之处。

如果要试用，基础条件是二十或以上版本的 Node.js，以及八或以上版本的 KiCad，并确保 KiCad 命令行工具可用。项目采用 Apache 二点零许可证，生成内容仍然是用户仓库中的普通 KiCad、Markdown 和 JSON 文件，没有专有格式锁定。

最值得记住的是，Copperhead 的价值并不只是“让人工智能画电路板”。它真正尝试建立的，是一条有规格、有记录、可传播、可回滚，并由工程工具验证的硬件代理流程。但它目前仍是早期工具。可以把它当作受约束的硬件开发助手，不能把它当作已经成熟的自动化硬件工程师。

项目把自己称为“电路板的 Cursor”。你可以把它理解为一个面向硬件的开发代理：像编码助手修改软件项目一样，它直接操作真实的电路板设计文件，而不是只给你一段建议，或者生成一张电路示意图。

它使用的设计工具是 KiCad，这是一款开源电子设计软件。Copperhead 不打算取代 KiCad，也不要求你进入一个封闭的新编辑器。原理图和电路板文件，仍然留在你自己的项目仓库里。

它有两种主要用法。一种是在已有设计上提出修改，比如“给电源输入增加反接保护”。另一种是从自然语言产品简报出发，逐步形成规格、系统架构、元器件选型、原理图和初稿布局，再输出电路板制造文件、固件框架和开发计划。

不过，理解这个项目，最重要的不是输出清单，而是它怎样限制人工智能的操作。

Copperhead 的工作方式，很像结对编程，只不过双方讨论的是一块电路板。

代理先阅读设计文档，理解现有方案和约束。你提出需求后，它会给出元器件和电路方案。你可以继续质疑、讨论，直到修改理由站得住脚。随后，代理才编辑真实文件，把变更同步到相关文档，并运行检查。

这里有两道关键关卡。

第一道在修改之前。没有有效的变更提案，代理就不能动 KiCad 文件。项目说明，这不是一句提醒，而是工具层面的限制：提案没有通过，编辑工具就不可用。这样，每次修改都有一份可以追溯的意图记录。

第二道在修改之后。代理必须运行电气规则检查和设计规则检查。前者主要检查电路连接是否符合电气规则，后者检查电路板设计是否满足设定的规则。代理读回错误，再尝试修复，不能仅凭自己的判断宣布完成。

简单说，就是用规格把住入口，用检查把住出口。人工智能提出方案，但是否通过，要由外部工具来核实。

这种流程还有一个很实际的价值：处理硬件项目里那些枯燥、却容易出错的同步工作。

假设你修改了充电电流。需要变化的可能不只是一个元件值，还包括设计说明、物料清单，以及其他引用这个参数的地方。如果只改原理图，文档很快就会过时；如果只改文档，制造和采购又可能沿用旧信息。

Copperhead 把设计文档当作持续维护的记忆，并尝试把变更传播到所有相关工件。部件名称、网络名称和参数，要在不同文件里保持一致。每个实际决策旁边还要留下简短理由，避免下一次修改时，把原本有意做出的选择悄悄撤销。

它也会记录设计决策和变更历史。因此，这个项目不只是追求“改得快”，也在追求“以后还能说清楚，为什么这样改”。

物料清单导出，是这种一致性要求的一个具体例子。

物料清单，就是采购和装配需要的零件列表。Copperhead 可以把文档中的物料清单，转换成供应商接受的订购文件。这一步不调用语言模型，也不需要联网，而是按固定规则处理。

但导出之前，工具会检查物料清单是否与原理图一致。如果两者已经发生偏离，就拒绝导出。缺少制造商零件编号的项目，或者仍被标记为未经验证的项目，默认也不会进入供应商文件，而是给出警告。

备料规则还考虑了一个很小、却很真实的问题：小封装的电阻、电容，可能用镊子夹着夹着就弄丢了。所以对于少量被动元件，工具不只按百分比增加备料，还会设置至少多备两个的规则。

这些细节说明，项目关注的不只是让模型“想出电路”，还包括把设计信息可靠地传递到后续工作。

不过，可靠流程和成熟能力，是两回事。这也是原文最值得保留的提醒。

按照项目自己的说明，初始化、规则检查、文档一致性检查，以及制造导出等不依赖语言模型的部分，已经有离线测试覆盖，并在持续集成中通过。

但真正需要模型参与的代理流程，包括自动修改、解决不一致，以及从简报创建完整设计，虽然已经实现，也有结构上的约束，却尚未观察到端到端验收测试通过。项目明确提醒，使用时应预期会遇到粗糙之处。

它还设置了回滚机制。每次变更都在版本控制快照的保护下进行，验证失败就回滚。即便如此，项目仍建议在独立分支上工作，而不是直接拿重要设计冒险。

另一个边界同样关键：Copperhead 不是自动布线器。布线仍需要人工完成，或者交给其他工具。它也不是承担设计责任的工程师。通过电气规则和设计规则检查，不等于整块板已经适合制造，更不等于产品性能、安全性和可靠性都得到验证。最终仍要由人审核并签字确认。

这个项目最值得记住的，不是“人工智能已经能自动造电路板”，而是它尝试把硬件修改变成一条有记录、有约束、可检查、可回滚的流程。对目前的 Copperhead，合理的期待是：重视它减少文档漂移和重复劳动的思路，同时清楚区分，哪些能力已经经过测试，哪些仍等待真实的端到端验证。
