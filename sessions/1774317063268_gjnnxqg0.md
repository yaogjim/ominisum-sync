## 分析要点

- **核心高价值点**：最有价值的点是明确区分了智能体以终端用户身份执行与以固定凭证执行两种授权模型，这直接影响权限边界、渠道支持和安全策略设计。
- **留存建议**：短期参考后可归档（对理解智能体权限模型有概念澄清价值，适合作为产品设计参考案例留存。）

**知识要点**

- 智能体授权可分为 on-behalf-of 与 fixed credentials 两类
- 共享型智能体若使用固定凭证，需要配合 human-in-the-loop 降低高风险操作
- 跨渠道共享助手需要建立外部渠道用户 ID 与内部身份系统的映射

**行动项**

- 在设计企业智能体时先明确采用用户代理授权还是固定服务账号授权
- 为固定凭证型智能体补充高风险操作的人审或审批机制

**Harrison Chase**

### Two different types of agent authorization

We launched

[LangSmith Fleet](https://blog.langchain.com/introducing-langsmith-fleet/) last week as a way to build, use, and manage agents. A key part of this launch was the introduction of two different types of agent authorization.

Agent authorization refers to what the agent is authorized to do. When an agent calls a Slack tool - who does it authenticate as before pulling the data?

#### On-behalf-of

The standard way that most people thought of agents until recently is that they operate “on-behalf-of” a user.

Let’s imagine an onboarding agent with access to Notion and Rippling. When Alice interacts with it, it should be able to look up information about Alice in Rippling and see all pages in Notion that Alice has access to. Alice should not be able to use this onboarding agent to look up any private information about Bob in Rippling, or see any private Notion pages Bob might have. When Bob uses the onboarding agent, he should be able to access all his information in Rippling and all his private pages in Notion, but not Alice’s.

In order to implement this, you need a few things. You need a way to know who is using the agent - is it Alice or is it Bob? You then need to map those user IDs to some auth credentials that are passed into tools at runtime.

#### Then came OpenClaw

On-behalf-of was the primary way that people thought of agents until OpenClaw came around. With OpenClaw, Alice would create an agent. Maybe she would be the only one to use that agent (in which case this auth distinction would not matter much). But maybe she would expose to others, through different channels (like text or email or Twitter).

When others interacted with that agent, it didn’t use the credentials of the end user - it used the authorization that Alice had given it.

Sometimes this could be Alice’s own credentials, but that might not be that desirable. If the agent had Alice’s credentials, it could look up anything in Notion that Alice had access to. That might include private documents that he may not want others to be able to ask the agent about.

This lead to people creating dedicated accounts in Notion, Rippling, etc specifically for that agent, so they could control what that agent had access to. Everyone interacting with that agent would then effectively be using the same set of credentials.

#### LangSmith Fleet

When launching LangSmith Fleet, we saw that people wanted both types of agents. Sometimes they wanted to create an agent and let others use it with their own credentials, other times they would want that agent to have its own fixed set of credentials. We added two different types of agents, which mapped to these two types of authorization:

- Assistants: act “on-behalf-of” their end user
- Claws: have their own fixed credentials

We also added the concept of channels (Slack, Gmail, Outlook, and Teams to start) and sharing of agents. Assistants and Claws support different channels. In order for Assistants to be shared, we have to have a mapping of an end user in that channel (e.g. their Slack user ID) to their LangSmith ID. So right now Assistants are only available in a subset of channels where we support that mapping.

Channels and these different authorization types also highlight the need for human in the loop. If you are creating an agent with a fixed set of credentials, and exposing it via a channel. You are opening it up to be used in a variety of ways. If that agent can take actions that may potentially be dangerous or sensitive, you might want to use some “human-in-the-loop” guardrails to ensure that those actions are gated.

#### Examples

To make this concrete, let’s take a look at a few of the real agents we’ve created and their authorization types.

Onboarding Agent: Assistant. Has access to Slack and Notion, and is exposed in Slack. Uses the end user’s Slack and Notion credentials.

Email Agent: Claw. This agent responds to incoming emails. Regardless of who is emailing, this agent will look at my calendar to determine meeting availability and attempt to respond on my behalf. Sending emails and calendar invites is gated behind a human-in-the-loop guardrail.

Product agent: Claw. This agent monitors competitors and help with product questions and roadmap. It has it’s own Notion account and is exposed via a custom Slack bot.

#### Future work

We’re excited to rollout these two different agent types in LangSmith Fleet. We think this is just the start, however, of agent authorization. Read

[this blog from WorkOS](https://workos.com/blog/agents-need-authorization-not-just-authentication) on some potential future directions.

We’re also excited to follow up this work with more granular memory permissions. Depending on which agent type (Assistants or Claws) you may want memory to be handled differently. For example, you probably don’t want an assistant remembering sensitive things about Alice that it can use in a chat with Bob. Right now, we manage this with access permissions. When you share an agent, you choose whether other users can edit it, including its memory. In the future, we will introduce user specific memory.

[Try out LangSmith Fleet today](https://smith.langchain.com/agents?skipOnboarding=true).

## 结构化（1）

### 2026-03-24 06:18:04

#### 文章主旨

这篇文章主要讲的是：在构建和管理 AI Agent 时，“Agent 以谁的身份去访问数据和执行操作”是一个核心问题。作者围绕 LangSmith Fleet 的发布，解释了两种不同的 Agent 授权模式，以及它们各自适用的场景、限制和后续发展方向。

##### 1. 什么是 Agent 授权

- 所谓 **Agent 授权（agent authorization）**，指的是：Agent 在调用工具时，究竟是以谁的身份完成认证和访问数据。
- 例如，当 Agent 调用 Slack、Notion、Rippling 等工具时，需要明确：
  - 它是以当前使用者的身份访问；
  - 还是以 Agent 自己的一套固定身份访问。
- 这会直接决定 Agent 能看哪些数据、能执行哪些操作。

##### 2. 第一类：代表用户执行（On-behalf-of）

- 这是过去大家最常想到的 Agent 模式，即 Agent **“代表当前用户”工作**。
- 文中举了一个 **入职助手（onboarding agent）** 的例子：
  - 当 Alice 使用这个 Agent 时，它应该只能查看 Alice 在 Rippling 中的信息，以及 Alice 在 Notion 中有权限访问的页面。
  - Alice 不应该借助这个 Agent 去查看 Bob 的私密信息或 Bob 的私有页面。
  - 同样，当 Bob 使用时，他只能访问自己的信息，不能访问 Alice 的内容。
- 要实现这种模式，至少需要两项能力：
  - 知道当前是谁在使用 Agent（比如是 Alice 还是 Bob）；
  - 能把这个用户身份映射到相应的认证凭据，并在运行时传给工具。
- 这种模式的核心优点是：**权限天然跟随用户本人，边界清晰，安全性更符合企业常规权限管理逻辑。**

##### 3. 第二类：使用固定凭据执行

- 作者提到，在 OpenClaw 出现后，大家开始更多考虑另一种模式：**Agent 不用最终用户的凭据，而是用创建者授予它的一套固定权限**。
- 举例来说：
  - Alice 创建了一个 Agent；
  - 这个 Agent 可能不仅 Alice 自己用，还可能通过短信、邮件、Twitter 等渠道开放给其他人使用；
  - 这时，其他人与 Agent 交互时，用的不是他们自己的权限，而是 Agent 被授予的那套权限。
- 这种方式带来一个风险：
  - 如果 Agent 直接使用 Alice 本人的凭据，
  - 那么它可能能访问 Alice 在 Notion 里所有有权限的内容，
  - 包括一些 Alice 并不希望别人通过 Agent 间接访问到的私密文档。
- 因此，实践中很多人会专门为 Agent 创建 **独立账号**：
  - 比如在 Notion、Rippling 等系统中单独给 Agent 配一个账户；
  - 这样可以精确控制这个 Agent 能访问什么；
  - 所有和该 Agent 交互的人，实际上都共享同一套 Agent 凭据。
- 这种模式的核心特点是：**更适合对外开放、跨渠道服务，但权限设计必须更谨慎。**

##### 4. LangSmith Fleet 如何落地这两种模式

- 在发布 **LangSmith Fleet** 时，作者团队发现，用户其实同时需要这两类 Agent：
  - 有时希望 Agent 代表每个终端用户工作；
  - 有时希望 Agent 拥有自己固定的一套权限。
- 因此，LangSmith Fleet 提供了两种 Agent 类型：
  - **Assistants**：代表最终用户执行（on-behalf-of）
  - **Claws**：拥有自己固定的凭据
- 这相当于把“授权模式”直接做成了产品里的两种 Agent 形态，方便用户按场景选择。

##### 5. 渠道共享与身份映射的限制

- LangSmith Fleet 还引入了 **渠道（channels）** 和 **Agent 分享（sharing）** 的概念。
- 文中提到，首批支持的渠道包括：
  - **Slack**
  - **Gmail**
  - **Outlook**
  - **Teams**
- 但 Assistants 和 Claws 支持的渠道并不完全一样。
- 原因在于：如果要共享一个 **Assistant**，系统必须知道“渠道中的终端用户是谁”，并把他映射到 LangSmith 里的身份。
  - 例如，需要能把某人的 **Slack user ID** 映射到其 **LangSmith ID**。
- 正因为这个映射要求比较高，所以目前 **Assistants 只支持部分已完成身份映射的渠道**。
- 这说明：**代表用户执行的模式虽然更安全自然，但实现复杂度更高，尤其是在跨渠道共享时。**

##### 6. 为什么需要 Human-in-the-loop（人类参与审核）

- 作者特别强调，这两种授权模式和多渠道接入，也凸显了 **human-in-the-loop** 的必要性。
- 尤其当一个 Agent：
  - 拥有固定凭据；
  - 又通过某个渠道对外开放；
  - 并且还能执行敏感或高风险动作时；
- 就很有必要增加“人工把关”的护栏，避免 Agent 被滥用或误操作。
- 通俗理解就是：
  - 查询信息类动作可以尽量自动化；
  - 但发邮件、发邀请、修改关键数据这类动作，最好先让人确认一下。

##### 7. 真实案例：三种 Agent 的授权设计

作者给了 3 个具体例子，帮助理解这两种授权模式。

###### 7.1 入职 Agent

- 类型：**Assistant**
- 接入工具：**Slack、Notion**
- 暴露渠道：**Slack**
- 权限方式：使用 **最终用户自己的 Slack 和 Notion 凭据**
- 含义：
  - 每个员工看到的都是自己本来就有权限看的信息；
  - 更适合企业内部按人分权的场景。

###### 7.2 邮件 Agent

- 类型：**Claw**
- 功能：
  - 响应收到的邮件；
  - 无论是谁发邮件过来，它都会查看“我的日历”来判断会议是否有空；
  - 并尝试“代表我”进行回复。
- 权限方式：使用 **固定的一套凭据**
- 安全措施：
  - **发送邮件和发会议邀请** 这类动作，被放在 **human-in-the-loop guardrail** 之后，需要人工确认。
- 这个例子很典型地说明了：
  - 固定凭据适合对外统一服务；
  - 但涉及敏感操作时，必须加人工审核。

###### 7.3 产品 Agent

- 类型：**Claw**
- 功能：
  - 监控竞争对手；
  - 回答产品问题；
  - 协助处理路线图（roadmap）相关内容。
- 权限方式：
  - 拥有 **自己的 Notion 账号**
- 暴露渠道：
  - 通过一个 **自定义 Slack bot**
- 这个案例说明：
  - 对于面向多人使用、知识范围固定的 Agent，
  - 让它拥有一个专门账号通常比直接使用某个人的账号更合理、更可控。

##### 8. 未来方向：更细粒度的记忆权限

- 作者认为，这两类 Agent 只是 Agent 授权的开始，未来还会有更多演进方向。
- 其中一个重点是：**更细粒度的记忆（memory）权限控制**。
- 因为不同类型的 Agent，对“记忆”应该有不同处理方式。
- 文中给了一个很直观的例子：
  - 你大概率不希望一个 Assistant 记住 Alice 的敏感信息，
  - 然后在和 Bob 聊天时把这些信息用出来。
- 目前的做法是通过 **访问权限（access permissions）** 管理：
  - 在分享 Agent 时，可以设置别人是否能编辑它；
  - 包括是否能编辑它的 memory。
- 未来计划是：引入 **用户级别的专属记忆（user specific memory）**。
- 这意味着以后 Agent 可能会更细致地区分：
  - 哪些记忆属于 Alice；
  - 哪些内容绝不能泄露给 Bob。

##### 9. 文章结论

- 文章核心结论是：**Agent 的能力不仅取决于模型本身，更取决于它“以谁的身份行动”**。
- LangSmith Fleet 用两种清晰的产品形态来解决这个问题：
  - **Assistants** 适合代表每个用户执行；
  - **Claws** 适合使用固定凭据提供统一服务。
- 同时，作者也指出了两个重要配套方向：
  - 对高风险操作引入 **human-in-the-loop**
  - 对跨用户信息隔离引入更细粒度的 **memory 权限控制**
- 换句话说，未来 Agent 系统要真正落地，除了“会做事”，还必须做到 **权限清楚、边界可控、安全可审计**。

#### 内容总结

这篇内容主要讲了：**Agent（智能体）有两种不同的授权方式**。

1. **On-behalf-of（代表用户）**
   - Agent 用的是“当前使用者自己的权限”。
   - 比如 Alice 用 Agent，只能看到 Alice 能看的 Notion 和 Rippling 数据；Bob 用时，只能看到 Bob 自己的数据。
   - 核心是：**谁在用，Agent 就按谁的身份访问系统**。

2. **Fixed credentials（固定凭证）**
   - Agent 用的是“它自己固定的一套权限”，而不是终端用户的权限。
   - 不管是谁来用，这个 Agent 都是以同一个身份去访问工具。
   - 为了安全，通常会专门给 Agent 配一个独立账号，限制它能访问的数据范围。

LangSmith Fleet 把这两类 Agent 分别产品化为：
- **Assistants**：代表最终用户执行
- **Claws**：使用自己固定的凭证执行

同时，作者也强调了两个关键点：
- **渠道映射能力**：如果 Agent 要代表用户执行，系统必须知道“渠道里的这个人是谁”
- **Human-in-the-loop（人工审核）**：如果 Agent 拥有固定权限，且还能发邮件、发消息、改日历等，就最好加人工确认

#### 深入解读

##### 1. 这其实是在回答一个很关键的问题

不是“Agent 能不能调用工具”，而是：

> **Agent 调工具时，到底是以谁的身份在行动？**

这决定了它能看什么、能做什么，也决定了安全边界在哪里。

---

##### 2. “代表用户”更像是企业内部助手

这种模式下，Agent 像是一个“智能员工助手”：

- 你问它，它就用你的身份去查数据
- 你没权限看的内容，它也看不到
- 每个人看到的结果天然不同

好处是：
- 权限边界清晰
- 更符合企业原有权限体系
- 数据泄露风险更低

难点是：
- 必须识别当前用户是谁
- 还要把 Slack、Teams 等渠道身份映射到系统身份
- 接入实现更复杂

适合场景：
- 内部知识库问答
- 员工 onboarding
- 个人日程/文档助手
- CRM/HR/财务等按人隔离的数据访问

---

##### 3. “固定凭证”更像是一个机器人账号

这种模式下，Agent 更像一个“拥有自己工号的数字员工”：

- 谁来和它交互不重要
- 它始终用同一个账号访问系统
- 所有人实际共享的是同一套能力

好处是：
- 部署简单
- 很适合对外开放或跨渠道使用
- 适合做公共能力型 Agent

风险也更明显：
- 如果权限给大了，任何与它对话的人都可能间接获得不该有的信息
- 如果它还能执行动作（发邮件、发邀请、改数据），风险更高

所以作者提到一个很重要的实践：
> **不要直接给 Agent 创始人或管理员本人的权限，最好单独创建专用账号。**

这相当于给机器人单独开一个“受限工位”。

适合场景：
- 自动回邮件
- 产品/竞品监控 Agent
- 面向多人共享的公共问答机器人
- 对外服务型 Agent

---

##### 4. 为什么“人工审核”很重要

当 Agent 只是“读数据”，问题还相对可控；
但一旦它可以“做动作”，比如：

- 发邮件
- 发 Slack 消息
- 创建日历邀请
- 修改数据库

那就不能只靠模型自己判断。

所以文中强调：
- **固定凭证 + 对外开放渠道**
- **高风险动作**
- **必须有人类做最后确认**

这本质上是给 Agent 上“刹车系统”。

---

##### 5. 作者提到的“记忆权限”也很关键

未来 Agent 不只是“能访问什么”，还包括“能记住什么”。

举例：
- 如果一个 Assistant 记住了 Alice 的敏感信息
- 之后又在和 Bob 的对话里调用了这些记忆
- 就会造成严重的数据串线

所以未来更细粒度的权限，不只是工具权限，还包括：
- 用户级记忆隔离
- 会话级记忆隔离
- 共享 Agent 的记忆边界控制

这说明 Agent 安全正在从“工具授权”扩展到“记忆授权”。

---

#### 我的意见

我认为这篇内容很有价值，原因有三点：

1. **它点出了 Agent 产品设计里最核心却最容易被忽视的问题：身份边界**
   - 很多人只关注“接了多少工具”，却没先想清楚“Agent 是替谁做事”。

2. **把两种授权模式拆开是对的**
   - 现实业务里，这两种模式都需要，不能用一种方案硬套所有场景。

3. **真正落地时，安全重点不在模型，而在权限设计**
   - 账号隔离
   - 渠道身份映射
   - 高风险动作审批
   - 记忆隔离  
   这些比“提示词写得好不好”更重要。

如果让我给一个实用建议，那就是：

> **默认优先选“代表用户”模式；只有在明确需要共享能力、跨渠道开放或做公共机器人时，再用“固定凭证”模式，并且一定配专用账号 + 人工审核。**

一句话概括：

> **Agent 的本质不只是“会不会做事”，而是“它在替谁做事、以谁的名义做事”。**
