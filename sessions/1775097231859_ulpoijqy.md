#### Summary

- **Implements the `cch` request signing mechanism** described in [this reverse-engineering article](https://a10k.co/b/reverse-engineering-claude-code-cch.html). The `cch` field in the `x-anthropic-billing-header` is an xxHash64-based integrity hash over the serialized request body that gates features like fast mode.
- **Adds `xxhash-wasm` dependency** for WebAssembly-based xxHash64 computation — fast, portable, no native bindings required.
- **New `src/utils/cch.ts` module** computes the hash: `xxHash64(body_with_placeholder, seed) & 0xFFFFF`, formatted as 5-char zero-padded hex.
- **Modified `buildFetch` in `client.ts`** to intercept `/v1/messages` requests containing the `cch=00000` placeholder, compute the hash, and replace the placeholder before sending.
- **Removed the `NATIVE_CLIENT_ATTESTATION` feature gate** from `system.ts` so the `cch=00000` placeholder is always included in the attribution header. The hash is now computed in JS-land instead of relying on Bun's native HTTP stack.

##### Algorithm (from the article)

1. Build the complete request body with `cch=00000` as placeholder
2. Compute `xxHash64(body_bytes, seed) & 0xFFFFF` (seed: `0x6E52736AC806831E`)
3. Format as zero-padded 5-character lowercase hex
4. Replace `cch=00000` with the computed value in the body

##### Activation conditions (matching the original Bun native implementation)

- URL path contains `/v1/messages`
- `anthropic-version` header is present
- Request body contains the `cch=00000` placeholder

#### 主旨概括

这篇内容主要介绍了一个 PR：为客户端补上`cch`请求签名机制，用`xxHash64`对请求体做完整性哈希，从而匹配 Anthropic 原本的请求校验方式，并解锁如`fast mode`这类能力。  
核心改动是：统一在请求发送前，把请求体里预留的`cch=00000`占位符替换成真实哈希值，而不是再依赖 Bun 的原生 HTTP 实现。

##### 1. 这个 PR 做了什么

- 实现了`cch`请求签名机制，目标是复刻逆向分析文章中描述的行为。
- `cch`是放在`x-anthropic-billing-header`相关内容中的一个完整性校验字段，用来校验序列化后的请求体。
- 新增依赖`xxhash-wasm`，通过 WebAssembly 计算`xxHash64`，优点是：
  - 速度快
  - 跨平台
  - 不需要原生绑定
- 新增模块`src/utils/cch.ts`，专门负责：
  - 计算`cch`
  - 检查是否存在占位符
  - 替换占位符
- 修改`src/services/api/client.ts`中的`buildFetch`：
  - 拦截发往`/v1/messages`的请求
  - 如果请求体里有`cch=00000`，就先计算真实值，再替换后发送

  - 让系统始终附带`cch=00000`占位符

##### 2. `cch`的算法逻辑

原文给出的算法步骤非常明确，流程如下：

1. 先构造完整请求体，并在其中保留`cch=00000`占位符  
2. 对整个请求体字节序列计算`xxHash64`
3. 使用固定种子：`0x6E52736AC806831E`
4. 计算结果再做掩码：`& 0xFFFFF`
5. 最终格式化为**5 位、补零、小写十六进制字符串**
6. 用这个值替换掉原来的`cch=00000`

###### 例子

- 如果哈希最终结果低 20 位是`0x1a3f`
- 那么格式化后就会变成`01a3f`
- 请求体中的`cch=00000`会被替换成`cch=01a3f`

这说明它不是一个完整长哈希，而是取了结果的一部分作为短校验值。

##### 3. 什么时候会触发签名

PR 中说明，这个行为与原本 Bun 的原生实现保持一致，只有满足以下条件才会计算`cch`：

- URL 路径包含`/v1/messages`
- 请求头中存在`anthropic-version`
- 请求体中包含`cch=00000`占位符

也就是说，不是所有请求都会签名，而是只针对 Anthropic 消息接口的特定请求生效。

##### 5. 请求发送流程是怎么跑的

原文用时序图描述了完整过程，可以概括成：

- 客户端发起请求
- `FetchWrapper`检查：
  - 是否是`/v1/messages`
  - 是否有`cch=00000`
- 如果满足条件：
  - 调用`CCHUtil`
  - `CCHUtil`初始化或复用`xxHash64`实例
  - 用 UTF-8 编码后的 body 和固定 seed 计算哈希
  - 截取结果并格式化成 5 位 hex
  - 把 body 中的占位符替换掉
- 最后把更新后的请求体发给 API Server

一句话理解：**请求先 “签名”，再真正发出去。**

##### 7. Code Review 提出的两个重要问题

###### 问题一：不要静默吞掉 CCH 签名错误

CodeRabbit 指出，在`src/services/api/client.ts`中，当前`try/catch`同时包住了日志解析和 CCH 签名逻辑，导致：

- 如果`computeCch`失败
- 请求会继续发出
- 但错误被静默忽略，难以及时发现回归问题

建议改法：

- 把 “URL 解析 / 日志记录” 和 “CCH 签名” 拆成两个独立的`try/catch`
- 如果签名失败：
  - 记录日志
  - 保持原 body 不变
  - 继续发送请求

这样可以保证请求不中断，同时也能看到失败信号。

###### 问题二：占位符匹配范围太大，可能误伤用户内容

CodeRabbit 还指出，`src/utils/cch.ts`里的辅助函数目前是全局查找`cch=00000`，这会带来风险：

- 如果用户消息正文里刚好出现`cch=00000`
- 代码可能误替换用户文本
- 反而真正的 attribution header 没被正确签名

建议改法：

- 只在`attribution-header`这段内容里查找和替换`cch`
- 用正则把匹配范围限定在 header 片段中
- 如果 header 不存在，就：
  - `replaceCchPlaceholder`返回原始 body
  - `hasCchPlaceholder`返回 false

这是一个很关键的健壮性问题，因为它关系到 “替换的是不是该替换的地方”。
