> **摘要**：文章比较多种编程 Agent 的上下文压缩实现，解释摘要请求改变工具、系统提示词或历史后为何可能失去缓存复用，并给出热缓存复用、冷缓存回退、窗口预留、摘要安全及成本验收建议。

## 分析要点

- **核心高价值点**：将压缩请求视为上一轮正常请求的分叉，保持原有请求前缀并在末尾追加总结指令，同时根据缓存有效性和预计成本决定是否回退到独立摘要请求。
- **留存建议**：精读并保留为上下文压缩设计检查清单，实施前核对所用服务商与版本的缓存规则。（包含多种工具的压缩实现对比、明确的缓存复用条件、失败兜底和验收指标，可直接支持 Agent 成本优化与安全测试。）

**知识要点**

- 前缀缓存的复用依赖请求前缀一致性；改变工具、系统提示词或历史结构可能导致后续缓存失效，具体边界需核对服务商规则。
- 复用缓存并非始终更便宜：模型与配置一致性、缓存有效期、窗口容量及缓存写入成本共同决定压缩路径的选择。
- 压缩摘要可能保留网页或命令输出中的不可信指令，应明确标注为历史摘要而非新任务，并测试工具调用是否会被误派发。

**行动项**

- 实现缓存复用压缩路径：复制上一轮请求并仅在末尾追加总结指令，测试请求体前缀一致性；工具调用或空响应须在执行前丢弃，再回退到独立摘要请求。
- 分别测试热缓存和过期缓存，记录摘要、失败重试及压缩后首轮请求的缓存读写、普通输入和输出成本，比较两条压缩路径。
- 为摘要输出预留窗口空间，并建立摘要注入与工具误调用回归测试，验证引用内容不会变成新任务、摘要路径不会实际执行工具。

## 正文

**KC**

agent 压缩上下文的那一下，经常是整段对话里最贵的一次请求。这时候上下文已经快满了，摘要请求要是没命中 prompt cache，就等于把十几万 token 按原价重新读一遍。

我在给自己的 SSH 客户端 Hatoba 做 AI 助手，第一版就踩了这个坑。压缩时换了一个不带工具的系统提示词，tools 也去掉了，历史里的工具调用还被压成了文本，从第一个 token 开始就和缓存对不上。所以我翻了一圈 Claude Code、Codex、Qwen Code、OpenCode、Cline、Roo Code、pi、Gemini CLI 和 Aider 的源码、文档和 issue，看看大家是怎么处理的。

先说原理。prompt cache 是前缀匹配，Anthropic 的顺序是 tools、system、messages，前面任何一个字节变了，后面全部失效。给摘要单独写一个系统提示词，或者把工具删掉，等于主动放弃整段缓存。Anthropic 文档还写明了，改 tool\_choice 也会让 messages 部分的缓存失效，所以想用 tool\_choice 禁止模型调工具同样不行。

看下来大家分成两派。

一派把压缩请求当成主请求的分叉，也就是把上一次正常请求原样复制一份，工具、系统提示词、完整历史、thinking 设置都不动，只在最后多加一条总结指令。

Claude Code 官方文档写的就是这种做法。指令附在最后一条 user 消息里，工具也留在请求里，只在文字上要求模型只输出文本、不要调工具。缓存还热的时候，/compact 基本只花输出的钱。

Qwen Code 为这件事专门写了设计文档。主路径用同样的系统提示词、工具和完整历史，末尾加一句不要调用工具。模型如果还是调了工具或者回了空，就丢掉结果，退回不复用缓存的独立请求再试一次。PR 里一个测试样例的缓存命中率从 0% 到了 96.7%。

Codex 在 OpenAI、Azure、Bedrock 上走服务端压缩，请求带同样的工具、instructions 和 cache key，末尾加一个 compaction\_trigger，服务端返回一段加密的摘要。

旧版 Cline 更直接，把总结指令贴在下一次正常请求后面，让模型用 summarize\_task 工具交回摘要。

另一派单独发一个摘要请求，用一段专门的短系统提示词，不带工具，历史要么压成一段文本，要么改写过。OpenCode v1、现在的 Cline SDK、Roo Code、pi、Gemini CLI、Aider 都是这样。Gemini CLI 还会再调一次模型，检查摘要有没有漏东西。Codex 给其他服务商用的本地压缩也把 tools 去掉了。

比较有意思的是几个半路翻车的例子。

OpenCode V2 修过一次，PR 里明确说之前的压缩请求换了系统提示词和工具集，用不上热缓存，于是改成了共享。但它只把要被总结的那部分旧历史发出去。有用户在 issue 里统计了 132 次压缩，缓存读取的中位数只有 4% 到 7%，按 Anthropic 计价花了 70.51 美元，如果都按缓存读取算只要 8.17 美元。原因维护者还没确认，报告人怀疑就是只发了半段历史，缓存断点和主循环对不上。

Claude Code 自己也翻过车。有人在 issue 里抓包发现，开了 advisor 工具之后，压缩请求和主循环的工具数量差了一个（66 和 67），system 也有一块不一样，每次压缩都把整段对话重新写一遍缓存，后来才修掉。

Anthropic 自己 SDK 里之前的客户端压缩，摘要请求连 system 和 tools 都不带，现在已经删掉，换成了服务端压缩。

pi 则是故意不用缓存。它给摘要请求关掉了缓存写入，代码注释的意思是一次性的摘要没必要写缓存。它也试过复用缓存的做法，第二天就回滚了，原因没写。现在有个 PR 把它做成可选，而且要先满足几个条件：模型和 thinking 设置一致，距离上次请求没超过缓存有效期的 90%，窗口放得下，估算下来比单独请求便宜。缓存已经过期的话，分叉请求读不到任何东西，还要多付一笔写缓存的钱，pi 加这些判断就是为了避开这种情况。

想少踩坑的话，下面这几条可以直接照着做。

压缩请求就是上一次正常请求加一条指令。tools、system、完整历史、模型、thinking 配置逐字节不动，指令放在最后。  
不要靠去掉工具或者改 tool\_choice 来禁止调工具。用文字要求，再加兜底，模型调了工具或者回了空就丢掉结果，换独立请求重试。  
发完整历史，别只发要被总结的那一段。  
别为了省钱换小模型来压缩，缓存是按模型分的。Roo Code 干脆删了自定义压缩模型，理由是只有对话本来的模型才总结得准。  
压缩请求是一次性的，就算要写缓存也用 5 分钟 TTL，Claude Code 就是这么分的，主循环用 1 小时，压缩用 5 分钟。缓存已经冷了的话，可以像 pi 那样直接走不写缓存的独立请求。  
阈值要给摘要输出留空间，用窗口减去一个预留量，别写死一个百分比。OpenCode V2 是窗口减 max(10%, 16k)，pi 是窗口减 16384，Qwen 是 85% 且不超过窗口减 33k。  
压缩之后的历史反正是冷的，系统提示词一定要冻结，至少 tools 和 system 还能命中。摘要用 user 消息注入，外面包一层说明，这是之前对话的摘要，不是新指令。摘要里很可能带着网页和命令输出的原文，不包这一层，它们就成了用户说的话。  
清理旧的工具输出也是在改历史，从改动的位置开始缓存全部失效。要清就攒着一次清一批，Qwen 一次清到阈值的一半，免得每一轮都破坏前缀。  
用数据验收。看压缩请求的 cache\_read\_input\_tokens，有条件就像 Codex 那样写个测试，直接比对压缩请求和上一次正常请求的 body。

## 通俗精炼（1）

### 2026-10-09 11:10:52

#### Agent 压缩上下文为什么会很贵：关键不在摘要长度，而在能否复用缓存

文章讨论的是 AI Agent 在长对话中“压缩上下文”的成本陷阱：为了继续工作，Agent 需要把旧对话总结成摘要，但生成摘要时仍要读取大量历史。**如果压缩请求破坏了原有的提示词缓存，就可能把十几万 token 按普通输入价格重新读取，使这次“省空间”的操作成为整段对话里最贵的一次请求。** 作者比较了多个编程 Agent 的实现，主张：缓存仍有效时，尽量沿用正常请求的配置和完整历史，只在末尾追加总结指令；缓存已过期时，则需要重新判断哪条路径更便宜。

##### 1. 压缩只是缩短后续上下文，不会自动降低这次请求的成本

模型的上下文窗口有容量上限。对话接近上限时，Agent 通常会让模型阅读旧历史、生成摘要，再用摘要替换部分历史，以便继续对话。

问题在于：**摘要虽然短，生成摘要所需的输入却可能非常长。** 模型必须先读完要总结的内容，而此时往往恰好是整段对话最长的时候。

提示词缓存（prompt cache）可以降低重复读取相同内容的成本。它不是“记住相似意思”，而是复用请求中已经处理过的、保持一致的前缀。按作者引用的 Anthropic 机制，请求内容的顺序是：

`tools（工具定义） → system（系统提示词） → messages（对话历史）`

前面某处发生变化，该位置之后的内容就无法继续匹配原来的缓存。因此：

- 换一套“专门用于总结”的系统提示词，会破坏后续历史的缓存匹配。
- 删除工具定义，可能让请求从最前面就与原请求不同。
- 把历史中的结构化工具调用改写成普通文本，也会改变对应位置之后的前缀。
- Anthropic 文档还明确说明，修改 `tool_choice`——控制模型是否、以及如何调用工具的设置——会使 `messages` 部分的缓存失效。

作者在给 SSH 客户端 Hatoba 开发 AI 助手时就踩了这个坑：压缩时换了系统提示词、去掉工具，又把工具调用历史转成文本，结果无法复用原有缓存。

**“摘要请求更简洁”不等于“摘要请求更便宜”：删掉一些内容，可能反而让剩下的大量内容按更高价格重新读取。**

##### 2. 两种压缩路线：复用正常请求，或另建摘要请求

###### 路线一：保留原请求，只在末尾追加总结指令

这条路线把压缩请求当成正常请求的一个分支：工具、系统提示词、完整历史以及相关配置保持不变，只在最后加上“请总结、不要调用工具”的要求。

这样，大部分输入仍与之前一致，可以利用尚未过期的缓存；新增总结指令和摘要输出则另行计费。

| 实现 | 文中介绍的做法 |
|---|---|
| **Claude Code** | 官方文档要求把总结指令附在最后一条用户消息中，保留工具，只通过文字要求模型输出文本、不调用工具。缓存仍有效时，`/compact` 的成本主要来自输出。 |
| **Qwen Code** | 主路径复用系统提示词、工具和完整历史。如果模型仍调用工具或返回空结果，就丢弃结果，改用不复用缓存的独立请求重试。一个 PR 测试样例中，缓存命中率从 **0% 提升到 96.7%**。 |
| **Codex** | 在 OpenAI、Azure、Bedrock 上走服务端压缩：保留相同的工具、instructions 和 cache key，末尾追加 `compaction_trigger`，由服务端返回加密摘要。 |
| **旧版 Cline** | 把总结指令附在下一次正常请求后，让模型通过 `summarize_task` 工具提交摘要。 |

其中，Qwen 的数字来自**一个测试样例**，不能直接视为所有对话都能达到的效果。

###### 路线二：单独发送一个专门的摘要请求

这条路线使用短的专用系统提示词，不带工具，并可能把历史拼成文本或改写后再发送。它的特点是摘要任务与正常任务分离，但通常无法复用正常请求的完整缓存前缀。

作者将 **OpenCode v1、当前的 Cline SDK、Roo Code、pi、Gemini CLI 和 Aider** 归入这一类。Gemini CLI 还会再调用一次模型，检查摘要是否遗漏内容；Codex 面向其他服务商的本地压缩，也会去掉工具。

**两条路线并不是“复用缓存永远正确、独立请求永远错误”。** 如果原缓存已经过期，或者复用原请求需要额外写入大量缓存，独立请求反而可能更便宜。

##### 3. 实际案例说明：看起来共享了配置，也不一定真正命中缓存

###### OpenCode V2：改成共享请求，但命中率仍然很低

OpenCode V2 曾修正压缩时更换系统提示词和工具集的问题，改为共享这些配置。不过，它只发送需要总结的那部分旧历史，而不是完整历史。

一名用户在 issue 中统计了 **132 次压缩**：

- 缓存读取的中位数只有 **4%～7%**。
- 按 Anthropic 计价，共花费 **70.51 美元**。
- 报告者估算，如果相关输入都能按缓存读取计费，只需 **8.17 美元**。

报告者怀疑，截取部分历史导致压缩请求与主循环的缓存断点无法对齐。**维护者尚未确认原因，因此不能把这个推测当成已证实的结论。**

###### Claude Code：一个工具、一个系统提示词差异，也足以破坏复用

有人抓包发现，启用 advisor 工具后，Claude Code 的正常请求和压缩请求存在差异：工具数量分别为 66 和 67，系统提示词也有一块不同。

结果是每次压缩都重新写入整段对话的缓存，后来才修复。这个案例说明，不能只看设计上“共用一套配置”，还要检查实际发出的请求是否一致。

###### Anthropic SDK 与 pi：实现路线也会调整

Anthropic SDK 之前的客户端压缩请求不带系统提示词和工具，后来删除了这套实现，改用服务端压缩。

pi 则主动关闭独立摘要请求的缓存写入，理由是一次性的摘要请求没有必要再建立缓存。它曾尝试复用正常请求缓存，但第二天就回滚，文中没有给出原因。

目前 pi 有一个将缓存复用做成可选项的 PR，并设置了前提：

- 模型与 thinking 设置一致；thinking 是模型推理相关配置。
- 距离上次请求不超过缓存有效期的 90%。
- 上下文窗口仍能容纳这次请求。
- 估算成本低于独立摘要请求。

背后的逻辑是：**缓存过期后，复用路径可能既读不到旧缓存，又多付一笔新缓存写入费。**

##### 4. 作者给出的实现建议：先保住缓存，再处理失败和容量

###### 保持前缀一致，不靠删除工具来限制模型

缓存有效时，压缩请求应尽量沿用上一次正常请求的工具、系统提示词、完整历史、模型及 thinking 配置，把总结指令放在末尾。

不要通过删掉工具或修改 `tool_choice` 来禁止工具调用。作者建议用文字要求模型只输出摘要，并加上失败兜底：如果返回工具调用或空结果，就丢弃结果，切换到独立摘要请求重试。

**这一兜底必须发生在工具执行之前。** 热门回复进一步建议：注入一个模拟工具调用响应，挂上假执行器，验证摘要路径会先丢弃结果、转入备用路径，且工具执行次数始终为零。

###### 不要只截取“需要总结的那一段”

作者建议发送完整历史，而不是只发送一个历史片段。原因不是每条历史都必须写进摘要，而是截取或重排历史可能破坏请求与缓存的对应关系。

同样，不要只因为小模型单价低，就默认换小模型压缩更便宜。缓存按模型区分，换模型会失去原模型的缓存收益。

文章还提到，Roo Code 删除了自定义压缩模型，理由是原对话模型更能准确总结自己的对话。这是该项目的取舍，**不能据此断言其他模型一定无法做好摘要。**

###### 一次性压缩请求不宜盲目写长期缓存

TTL 是缓存的有效时间。作者建议，压缩请求即使要写缓存，也使用较短的 **5 分钟 TTL**；文中介绍的 Claude Code 将主循环缓存设为 1 小时，压缩请求设为 5 分钟。

如果原缓存已经失效，可以像 pi 一样，考虑走不写缓存的独立摘要请求，避免为一次性输入支付额外写入成本。

###### 提前留出摘要空间，不能等窗口彻底满了再压缩

压缩请求除了旧历史，还需要容纳新增总结指令，并为摘要输出预留空间。触发阈值因此不应只机械地设成窗口容量的某个百分比，还应考虑绝对预留量。

文中列出的做法是：

| 实现 | 压缩触发阈值 |
|---|---|
| OpenCode V2 | 窗口容量减去 `max(10% 的窗口容量, 16k token)` |
| pi | 窗口容量减去 `16,384 token` |
| Qwen Code | 采用 85% 阈值，同时不超过“窗口容量减去 33k token” |

这些数值不是通用标准；共同原则是：**压缩本身也要占空间，必须在窗口耗尽之前启动。**

##### 5. 压缩之后：既要减少缓存损失，也要避免把外部内容变成指令

###### 新摘要会改变历史，但稳定的前缀仍可复用

压缩后，旧历史被摘要替换，变动之后的内容自然需要重新建立缓存。作者因此强调，应冻结系统提示词和工具定义，至少让这些未变化的前缀仍有机会命中缓存。

清理旧工具输出也是同样的道理：修改历史中的某个位置，会使该位置之后的缓存失效。与其每轮删一点，不如集中清理一批。文中举例，Qwen 会一次清理到阈值的一半，减少反复破坏前缀的次数。

###### 摘要是历史资料，不是用户的新命令

作者建议将摘要放进用户消息时，在外层明确标注：**这是之前对话的摘要，不是新指令。**

因为摘要可能保留网页、终端命令输出等外部内容。如果把这些内容直接写成“用户说的话”，模型可能把其中的命令误认为当前任务，而不是待参考的历史资料。这涉及提示注入风险：外部文本越过了应有的边界，被当成了指令。

热门回复建议补一个反例测试：在网页原文中夹入命令，检查压缩后模型是否会将其误认成用户的新任务。这是在检验包装是否有效，而不是假设加一句说明就能彻底消除风险。

##### 6. 验收要看真实请求和完整成本，不能只看设计意图

作者建议直接检查压缩请求中的 `cache_read_input_tokens`，即实际通过缓存读取的输入 token 数量；有条件时，还应像 Codex 那样编写测试，比对压缩请求与上一轮正常请求的请求体，找出意外变化。

热门回复补充了一个重要的成本口径：把**摘要请求、失败后的重试，以及压缩后的第一轮正常请求**放在一起计算，分别记录缓存读取、缓存写入、普通输入和输出费用。否则，摘要请求看似便宜，后续重新建立缓存的开销却可能被漏掉。

还应将缓存仍有效的会话与缓存已过期的会话分开比较，才能判断两条压缩路径分别适用于什么条件。

**全文的关键判断是：上下文压缩不能只被看成“生成一段摘要”，而应被看成“在保留任务信息的同时，尽量少破坏已有缓存的一次请求变更”。** 摘要质量、真实缓存命中、失败处理和压缩后的重建成本，都需要一起验收。
