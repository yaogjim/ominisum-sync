## 分析要点

- **核心高价值点**：将每个数据源封装为 query/update 两类自然语言接口，并让子代理承担具体 API 规则，可显著降低主代理上下文负担。
- **留存建议**：短期参考后可归档保留（提出了在主代理与工具之间增加上下文提供者层的架构思路，对多工具 Agent 设计有参考价值。）

**知识要点**

- 多工具 Agent 的常见问题包括上下文污染、工具命名和作用域冲突、工具使用规则挤占主代理提示词。
- ContextProvider 将一个数据源的复杂工具集封装为少量高层接口，底层由受限子代理负责调用真实工具。
- 技能机制适合放在具体数据源的子代理中，而不是直接加载到主代理上下文里。
- 读写分离的 ContextProvider 可以带来更好的权限隔离，例如只读查询与受控写入分别由不同子代理执行。

**行动项**

- 在多工具 Agent 项目中尝试按数据源封装 query\_&lt;source&gt; 和 update\_&lt;source&gt; 接口。
- 评估当前 Agent 的工具数量、提示词长度和工具误调用率，判断是否需要引入中间层。
- 对高风险数据源优先设计读写分离和权限隔离的子代理。
- 关注该方案在缓存、OAuth、多轮会话认证和何时暴露底层工具方面的后续实践。

**Ashpreet Bedi**

### 上下文提供者：代理与工具之间缺失的层

如果你构建了一个拥有相当数量工具的代理，你就会遇到三个壁垒：

1. 来自太多工具的上下文污染
2. 因作用域重叠导致的性能下降
3. 主代理忘记了自己的职责，因为其上下文全是工具指令

如果你不同意，尝试让一个代理同时访问 Slack、Google Drive 和 Notion。请告诉我搜索是否有效。

我一直在测试一个能解决这些问题的新协议，初步结果已经足够好，可以广泛分享。

### 三堵墙

1. 上下文污染。 每个工具都会占用宝贵的上下文。 模式、描述、示例用法，所有这些都进入系统提示中。Slack 工具集包含 8 到 12 个工具，Gmail 是 6 到 10 个，日历工具也是 6 个。云端硬盘、GitHub、您的 CRM、网页工具。在添加任何自定义工具之前，您已经有 50 个工具了。超过 20 个工具时，模型开始虚构不存在的工具，或者错误调用形状错误的工具。
2. 模糊的范围无法组合。 两个工具都接受 workspace 参数：一个是 Slack 的，一个是 Google 的。在一个 MCP 中的搜索会与另一个 MCP 中的搜索发生冲突。send\_message 可以是 Slack、电子邮件或您的 CRM。 这个代理一半时间会选错，没有命名规范能解决这个问题，因为同一个词在不同来源中合理地表示不同的含义。一旦你从无法控制的来源（MCP 服务器、第三方 SDK、其他团队）构建工具时，就会产生重叠，模型就没有可靠的消歧方法。
3. 工具使用逻辑与主代理共存。 这是最深的壁垒，也是引发最多问题的壁垒。为了让代理能够良好地使用 Slack，系统提示必须解释 Slack 的操作方式：在直接发送消息（DM）给用户之前，先查询用户 ID；发布消息前，先将频道名称解析为 ID。这需要数百个 token 的 Slack 特定指导内容。现在对 Gmail 和日历（Calendar）也做同样的说明。 系统提示变成了每个 API 特性的集合。每一次交互都承载着所有规则，即使用户只是询问 Slack 相关内容。主要代理陷入了对用户问题以及它可能调用的每个 API 的工作机制的推理中。添加一个数据源意味着编辑提示词并希望没有其他部分出现退化。

### 缺失的层

今天规范的代理形状是： 代理 &lt;- 工具

或者，使用 MCP：Agent &lt;- MCP服务器 &lt;- 工具

或者，带有技能： Agent &lt;- 技能说明 &lt;- 工具

在所有情况下，代理会看到每个来源的原始工具界面。每个 Slack 工具、每个 Drive 工具、每个 CRM 工具。代理的提示词必须包含如何使用它们中的每一个。

我一直在测试的形状在中间放置了一层薄层：

代理 &lt;-&gt; 上下文提供者

每个 ContextProvider 封装一个数据源（例如 Slack、文件系统、Drive）

对于调用代理，它恰好提供两个工具：

- 查询\_&lt;源&gt;(问题) 用于自然语言读取
- 更新\_&lt;source&gt;(指令) 用于自然语言写作

就是这样。主代理看不到 Slack 的十二种工具，它只看到 query\_slack 和 update\_slack。它看不到 Drive 的特性，只看到 query\_drive。再添加十个来源，代理的工具界面将保持线性，最大为 2N。

每个工具背后都有一个子代理，其作用域限定于该特定源。该子代理负责管理源的工具、源的特性、先查后写模式以及分页的怪异情况。它在自身上下文中运行，返回答案，主代理则获得一个干净的结果。

```python
from agno.agent import Agent
from agno.context.slack import SlackContextProvider
from agno.context.gdrive import GDriveContextProvider
from agno.context.database import DatabaseContextProvider

slack = SlackContextProvider(id="slack", token=...)
drive = GDriveContextProvider(id="drive", service_account_file=...)
crm = DatabaseContextProvider(id="crm", sql_engine=engine)

agent = Agent(
    model=...,
    tools=[*slack.get_tools(), *drive.get_tools(), *crm.get_tools()],
)
```

代理看到四个工具：查询 Slack、查询 Drive、查询 CRM、更新 CRM。

#### 技能怎么样？

技能是对 wall 3 的一次重大尝试。技能将特定任务的指令（例如“如何使用 Slack”）封装到一个模块中，模型会在相关时加载该模块，而不是一直将其包含在系统提示中。

技能将任务知识从始终在线的提示中移出，并转化为更具条件性的内容。但在调用技能后，Slack 工具仍会作用于该代理。加载 2 个技能后，搜索仍会发生冲突。实际上，存在更高的可能性是，冲突的技能会在你毫无察觉的情况下破坏你的代理。

ContextProvider + 技能配合使用效果更佳。

Slack ContextProvider 的子代理本身可以加载 Slack 技能，而这正是技能发挥最佳作用的地方——即在实际与 Slack 交互执行的场景中，而非在仅仅想要得到答案的主代理中。

大致的划分是：技能压缩如何执行任务。ContextProvider 隐藏存在任务，直到主代理决定委派一个任务为止。

### 意外发现和开放性问题

一些有趣的观察。

- 子代理比预期便宜。我原以为额外的跳数会占主导地位，但事实并非如此。主代理的上下文要小得多，因此其调用更快且效果更好，而子代理仅在涉及源的回合中触发。在 Scout 的工作负载下，当源数量较少时，总令牌数大致持平，随着源数量增加而提高。在我测量的每个源数量下，墙上时钟延迟都有所下降。
- 主代理的提示明显变小了。我本以为需要一些编排逻辑，但事实并非如此。在统一的界面下，路由规则简化为“选择正确的查询\_&lt;source&gt;”。 gpt-5.4 开箱即用，不需要任何关于如何使用数据源的指导。这就是那种魔力，你需要亲眼看到才能真正理解我为什么对这种模式如此兴奋。
- 组合就是这么好用。两个提供者可以在同一轮次中互相读取（query\_slack 用于讨论，query\_drive 用于文档），主代理撰写综合内容。多个来源一起工作效果更好。
- 添加一个源是一行，移除一个也是一行。 交换后端（对于 Web 提供商，从 Exa 到 Parallel）在提供商内部进行，代理不会察觉，并且源就能正常工作，因为我不需要更新代理的使用提示。

我还在处理一些事情。

- 主代理的提示词能有多简短？ 我一直在通过评估进行爬山法优化，看看能把它推到什么程度。有没有可能完全不给出任何指令的情况？
- 会话内跨调用的缓存。 同一个查询\_&lt;source&gt;("who's on the X channel")不应该在两回合后重新执行工作。
- 逐用户认证，可在跳转中维持。 部分解决（Scout 将用户 ID、会话 ID、元数据和依赖项传递给子代理）。对于 OAuth 类型的源还有待完成。
- 何时转而暴露底层工具。 有些数据源适合让代理直接驱动工具调用，通常当数据源足够小，使得模式成本较低且代理的推理是限制因素时。该协议为此提供了一种模式。我还在确定这条界限在哪里。

## 通俗精炼（1）

### 2026-04-27 23:41:42

#### 文章总结：ContextProvider——代理与工具之间缺失的中间层

##### 核心观点

当 AI Agent 接入大量工具时，直接把所有工具暴露给主代理，会带来严重的上下文污染、工具冲突和性能下降。作者提出一种新架构：在 Agent 和工具之间加入 **ContextProvider（上下文提供者）**，让主代理只面对简化后的自然语言查询/更新接口。

---

##### 现有 Agent 架构的三大问题

###### 1. 上下文污染严重

每个工具都需要在提示词中写入 schema、描述、使用示例等信息。  
当 Slack、Gmail、Calendar、Drive、GitHub、CRM 等工具叠加后，工具数量很容易超过 50 个。

结果是：

- 模型开始“幻觉”不存在的工具
- 调错工具
- 参数结构错误
- 主代理上下文被工具说明占满

---

###### 2. 工具作用域重叠，难以区分

不同系统里经常有类似命名的工具或参数，例如：

- `search` 可能来自 Slack、Drive、Notion
- `send_message` 可能是发 Slack、邮件或 CRM 消息
- `workspace` 在不同服务中含义不同

模型很难稳定判断应该调用哪个工具，尤其当工具来自第三方 MCP、SDK 或其他团队时，命名规范也无法彻底解决。

---

###### 3. 主代理被迫理解所有工具细节

为了正确使用 Slack，提示词里要写：

- 发消息前先查用户 ID
- 发频道消息前先解析频道 ID
- 如何分页
- 如何处理 API 特殊规则

Gmail、Calendar、Drive 也都有类似规则。

最终主代理不只要理解用户意图，还要理解每个 API 的调用逻辑，导致系统提示越来越臃肿，维护成本极高。

---

##### 作者提出的方案：ContextProvider

###### 新架构

传统方式是：

```text
Agent <- Tools
```

或：

```text
Agent <- MCP Server <- Tools
```

作者建议改为：

```text
Agent <-> ContextProvider
```

每个 ContextProvider 封装一个数据源，例如 Slack、Google Drive、数据库、文件系统等。

---

##### ContextProvider 如何工作

每个数据源只向主代理暴露两个自然语言工具：

```text
query_<source>(问题)
update_<source>(指令)
```

例如：

- `query_slack`
- `update_slack`
- `query_drive`
- `query_crm`
- `update_crm`

主代理不再看到 Slack 的十几个底层工具，也不需要理解 Slack 的调用细节。

真正的复杂逻辑由 ContextProvider 背后的子代理处理，包括：

- 工具选择
- API 调用规则
- 分页
- ID 查询
- 读写权限控制
- 错误处理

主代理只拿到干净的结果。

---

##### 方案价值

###### 1. 降低主代理复杂度

主代理只需要判断：

> 我应该问哪个数据源？是查询还是更新？

而不需要理解每个工具的具体调用方式。

---

###### 2. 工具数量更可控

如果有 N 个数据源，最多只暴露 `2N` 个工具。  
相比直接暴露几十上百个底层工具，复杂度大幅降低。

---

###### 3. 数据源可独立维护

新增一个数据源只需加一行配置，移除也很简单。  
更换底层供应商，例如 Web 搜索从 Exa 换成 Parallel，主代理无需感知。

---

###### 4. 安全性更好

读写可以拆成不同子代理和权限：

- 只读代理负责查询
- 写入代理负责修改
- GitHub 示例中，代理可以读主分支，但只能在工作分支写入并生成 PR，不能直接推送主分支

这让权限边界更清晰。

---

##### 与 Skill 的关系

Skill 可以把某类任务的说明从主提示词中拆出来，确实缓解了部分问题。

但 Skill 仍然会让主代理直接面对底层工具。  
当多个 Skill 同时加载时，工具冲突依旧存在。

作者认为更好的方式是：

> ContextProvider + Skill

也就是让子代理加载对应数据源的 Skill，而不是让主代理加载所有 Skill。

这样 Skill 只在真正操作某个数据源时生效，主代理保持简洁。

---

##### 示例场景

###### 1. 数据库读写隔离

通过不同子代理分别处理数据库读取和写入，确保权限安全。

###### 2. GitHub 读写分离

代理可以读取主分支代码，但写入发生在独立 worktree 中，最终生成 PR，避免直接修改主分支。

###### 3. Slack + Web 联合分析

代理从 Slack 频道提取话题，再进行网络搜索，最后生成内部讨论与外部资料对应的简报。

###### 4. MCP 包装

一个包含 50 个工具的 MCP Server，可以被包装成单个：

```text
query_<id>
```

主代理不再直接接触所有底层工具文档。

---

##### 仍待解决的问题

作者也提到一些开放问题：

- 主代理提示词能否进一步缩短，甚至不写工具使用说明？
- 同一会话内的查询结果如何缓存，避免重复执行？
- 多用户 OAuth 授权如何在主代理和子代理之间稳定传递？
- 什么情况下应该直接暴露底层工具，而不是封装进 ContextProvider？

---

##### 一句话总结

**ContextProvider 的本质，是把“如何使用工具”的复杂性从主代理中剥离，交给专门面向单一数据源的子代理处理，让主代理只负责意图理解和跨源编排。**

这是一种更适合大规模工具接入、多数据源协作和企业级 Agent 架构的中间层设计。

  - Gmail：约 **6–10 个工具**
  - Calendar：约 **6 个工具**
  - 再加 Drive、GitHub、CRM、网页工具等，轻松超过 **50 个工具**
- 当工具超过 **20 个** 时，模型容易：
  - 虚构不存在的工具
  - 调用错误工具
  - 使用错误参数格式

###### 2）工具作用域重叠导致性能下降

- 不同系统里的工具可能使用相同概念，但含义不同。
- 例如：
  - Slack 和 Google 都可能有 `workspace`
  - `send_message` 可能指 Slack 消息、邮件或 CRM 消息
  - 多个 MCP 服务里都可能有 `search`
- 即使命名规范也无法完全解决，因为这些词在各自系统中都是合理的。
- 当工具来自第三方 MCP、SDK 或其他团队时，重叠更难避免，模型也缺乏可靠的消歧能力。

###### 3）工具使用逻辑挤占主代理能力

- 主代理不仅要理解用户问题，还要记住每个 API 的使用规则。
- 例如使用 Slack 时，系统提示词需要说明：
  - 给用户发私信前，要先查询用户 ID
  - 发频道消息前，要先把频道名解析成频道 ID
- 类似规则也要为 Gmail、Calendar 等重复编写。
- 结果是：系统提示变成各种 API 操作手册的合集，主代理的职责被稀释，新增数据源还可能导致已有能力退化。

---

##### 2. 当前常见架构的局限

文章认为，今天常见的代理架构大致是：

```text
Agent <- Tools
```

或使用 MCP：

```text
Agent <- MCP Server <- Tools
```

或使用技能：

```text
Agent <- Skill Instructions <- Tools
```

这些方式都有一个共同问题：  
**主代理仍然直接看到每个数据源的原始工具接口。**

也就是说，Slack 的每个工具、Drive 的每个工具、CRM 的每个工具都暴露给主代理，导致主代理必须理解并选择所有工具。

---

##### 3. 作者提出的新层：ContextProvider

作者测试的新架构是在代理和工具之间加入一层：

```text
Agent <-> ContextProvider
```

每个 `ContextProvider` 封装一个数据源，例如：

- Slack
- 文件系统
- Google Drive
- 数据库
- CRM

对主代理来说，每个数据源只暴露两个自然语言工具：

```text
query_<source>(问题)      用于读取信息
update_<source>(指令)    用于写入或修改信息
```

例如：

- `query_slack`
- `update_slack`
- `query_drive`
- `query_crm`
- `update_crm`

这样，主代理不再看到 Slack 的十几个底层工具，只看到统一的查询和更新接口。

---

##### 4. ContextProvider 的工作方式

每个 ContextProvider 背后都有一个 **子代理**。

子代理负责处理具体数据源的复杂性，包括：

- 调用底层工具
- 理解该数据源的 API 特性
- 处理“先查 ID 再写入”的流程
- 处理分页、权限、参数格式等细节

主代理只需要提出自然语言请求，子代理完成具体执行后返回干净结果。

示例代码中，作者接入了 Slack、Google Drive 和 CRM：

```python
slack = SlackContextProvider(id="slack", token=...)
drive = GDriveContextProvider(id="drive", service_account_file=...)
crm = DatabaseContextProvider(id="crm", sql_engine=engine)

agent = Agent(
    model=...,
    tools=[
        *slack.get_tools(),
        *drive.get_tools(),
        *crm.get_tools(),
    ],
)
```

主代理最终只看到少量工具，例如：

- 查询 Slack
- 查询 Drive
- 查询 CRM
- 更新 CRM

工具数量随数据源线性增长，最多约为 `2N`，而不是每个数据源暴露大量底层工具。

---

##### 5. 与 Skill（技能）机制的关系

作者认为，Skill 是对第三个问题的一种重要尝试。

Skill 的作用是：

- 把“如何使用 Slack”这类任务知识封装成模块
- 只在相关时加载，而不是一直放在系统提示词中

但 Skill 仍有局限：

- 一旦加载技能，底层 Slack 工具仍暴露给主代理
- 如果同时加载多个技能，搜索、发送消息等工具仍可能冲突
- 冲突甚至可能在开发者无感的情况下破坏代理表现

作者认为更好的方式是：

```text
ContextProvider + Skill
```

也就是让 **ContextProvider 的子代理** 加载对应技能。  
例如 Slack 子代理加载 Slack Skill，而不是让主代理直接处理 Slack 操作细节。

##### 7. 作者的观察与开放问题

###### 已观察到的优势

- 添加一个数据源只需一行代码
- 移除一个数据源也只需一行代码
- 替换后端时，主代理无需感知  
  例如 Web provider 从 Exa 换成 Parallel，只需在 provider 内部调整
- 因为主代理不用改提示词，所以更不容易引发退化

###### 仍在探索的问题

作者还在研究几个方向：

1. **主代理提示词能否更短**
   - 正在通过评估做优化
   - 甚至探索是否可以完全不给主代理额外指令

2. **会话内缓存**
   - 例如两轮对话前刚问过：
     ```text
     query_source("who's on the X channel")
     ```
   - 后续不应重复执行相同查询

3. **逐用户认证与跨跳转维持**
   - Scout 已经能传递用户 ID、会话 ID、元数据和依赖项给子代理
   - 但 OAuth 类型的数据源仍需完善

4. **何时暴露底层工具**
   - 有些小型数据源可能适合直接让主代理调用底层工具
   - 尤其当工具 schema 成本较低、主要瓶颈在代理推理时
   - 作者还在寻找这条边界

---

##### 总结

作者提出的 ContextProvider 本质上是一个“工具抽象层”：主代理不再直接面对大量复杂工具，而是通过统一的自然语言查询/更新接口与各数据源交互。这样可以减少上下文污染、缓解工具冲突，并把具体 API 操作逻辑交给专门的子代理处理，从而让主代理更专注于理解用户意图和整体任务编排。
