## 分析要点

- **核心高价值点**：最有价值的点是明确了“缓存还热且任务未切换时，继续当前会话通常比开新会话更省 Token”的反直觉原则。
- **留存建议**：建议长期保留，适合作为 Claude Code 使用与成本控制的实操参考（内容高度实用，包含可直接复用的会话管理原则、配置项和决策规则）

**知识要点**

- 提示缓存只对完全一致的输入前缀生效，且存在时效窗口
- 是否开新会话应基于任务是否切换、缓存是否过期、上下文是否充满噪音来判断
- 1M 上下文虽然同价，但缓存失效后的重建成本极高，日常编码应谨慎使用
- 控制输入比控制输出更重要，长日志和大文件应通过路径引用而非直接粘贴
- 精简 CLAUDE.md、减少技能与 MCP 工具加载，可以显著降低隐性 Token 消耗

**行动项**

- 在实际使用 Claude Code 时建立会话规则：任务不变且 1 小时内持续交互时优先继续当前会话
- 在 \`\~/.claude/settings.json\` 中按需设置 \`CLAUDE\_CODE\_DISABLE\_1M\_CONTEXT\` 或 \`CLAUDE\_CODE\_AUTO\_COMPACT\_WINDOW\`
- 审查并精简项目中的 \`CLAUDE.md\`、技能和 MCP 服务，减少每轮请求的固定上下文
- 为代码库配置 \`permissions.deny\`，排除 \`node\_modules\`、构建产物和敏感文件以降低搜索浪费
- 将简单日常任务优先分配给 Sonnet，将复杂架构和高推理任务留给 Opus

## 正文

**宝玉**

### Claude Code 省 Token 指南：慎用 1M 上下文，不开新会话或者总是开新会话都不对

最近社区里怨声载道：配额烧得太快了。Max 用户一周的额度，有人两天就用完。有人在 AWS Bedrock 上算了一笔账，一个会话的真实成本超过 134 美元，而 Pro Max 5x 订阅一个月才 100 美元。Anthropic 的订阅本身就是亏本在卖。

很多人的第一反应是频繁 /clear，或者每做完一步就开新会话。觉得这样“轻装上阵”能省钱。但如果你理解了 Claude Code 背后的缓存机制，会发现这个操作经常适得其反：你刚刚触发了一次全价上下文重建，花的钱比继续聊下去还多。

#### 模型每次都在“从头读”

要理解配额为什么烧得快，得先搞清楚大语言模型处理输入的方式——它跟人类的“接着读”完全不同。

想象你在写一篇关于气候变化的论文，每次去图书馆都要做同一件事：找到那本 500 页的《全球气候报告》，翻到需要的章节，把关键数据抄下来。第一次花 40 分钟，第二次问了个不同的问题，还是同一本书，又花 40 分钟。第三次、第四次，同样的 40 分钟。

大语言模型干的就是这件事。它没有“记忆”，不会因为刚读过就跳过。每次收到你的消息，它都要从头“读”一遍完整的输入内容，读的时间和内容长度成正比。

在 Claude Code 里，输入内容通常包括三部分：

- 固定部分：系统指令、工具定义、CLAUDE.md 里的项目规则
- 对话历史：之前所有的对话轮次
- 新消息：你刚刚输入的那句话

前两部分在同一个会话里几乎不变，但模型每次都要重新“读”一遍。聊了 20 轮之后，每条新消息可能要带上 10 万个 Token 的“旧行李”，既慢又贵。

![Image](https://pbs.twimg.com/media/HFu1gVBXsAAIX7y?format=jpg&name=large)

#### 提示缓存：把“笔记”存起来

每次都从头翻那本 500 页的书，任谁都受不了。解决办法很直接：把笔记提前做好，下次只翻笔记本。

提示缓存干的就是这件事。

模型读完一段输入后，会生成一组中间计算结果，相当于“阅读笔记”。后续生成回答时，模型靠的就是这组笔记，不会再回去看原文。提示缓存的机制是：第一次算完笔记后存下来，下次再遇到相同的输入前缀，直接用存好的笔记，跳过重复计算。

读取缓存的成本只有重新计算的十分之一。

粗略算一下：一个 20 轮的会话，10 万 Token 的上下文，缓存一直命中的话，输入成本比每次都全价处理低 6 倍以上。

但缓存有两个前提条件。

第一，缓存只对“前缀”有效。 必须从头开始、一字不差地匹配。

打个比方：你在作文纸上写了一篇文章，前 3 页一字不差，第 4 页改了一个字。只有前 3 页能用缓存，第 4 页开始就得重新计算。如果你在第 1 页就改了一个字？整个缓存全部失效，从头算。

所以 Claude Code 的输入结构很重要：系统指令、工具定义这些不变的内容放在最前面，对话历史在中间，新消息放在最后。每次只有末尾那一小段需要重新计算，前面一大段都能命中缓存。

在同一个活跃会话里，前缀天然一致，每一轮只是在尾部追加新内容，缓存命中率很高。但如果你开了一个新会话，前缀从零开始，之前积累的缓存全部用不上。

![Image](https://pbs.twimg.com/media/HFu1i6lWgAAfyuJ?format=jpg&name=large)

第二，缓存有存活时间。 根据 Claude Code 团队的说明，主智能体的缓存窗口是 1 小时，子智能体是 5 分钟。API 用户默认只有 5 分钟（可以付费开启 1 小时，但更贵）。每次缓存命中都会刷新计时器，只要你保持交互频率，缓存可以一直活着。

Claude Code 团队的原话：

> “Claude Code 是缓存利用率最高的框架。”

但缓存未命中的代价，随上下文长度增大而急剧增加。一个 200K 的缓存未命中和一个 1M 的缓存未命中，完全是两个量级的开销。

#### 三个反直觉的省钱策略

理解了缓存之后，有些“常识”要翻过来。

#### 缓存还热的时候，继续聊比开新会话便宜

Claude Code 每次新会话启动，都要重新加载系统提示、工具定义、CLAUDE.md、项目配置。这些“基础设施”大约 5 万 Token。频繁 /clear 等于反复为这些不变的内容付全价写入费。

而在活跃会话里，这些内容一直在缓存中，每次只付十分之一的价格。

Anthropic 员工 Lydia Hallie 说的“闲置约一小时的大型会话，建议重新开始”，关键词是“闲置”。活跃工作中的会话，缓存一直是热的，继续聊才最省。

#### 复杂任务一次做对，比来回改三轮更省

关掉扩展思考确实能在单次请求里省 Token。但一个复杂的重构任务，开着扩展思考一次搞定，和关掉之后来回改三轮，后者更贵的概率很大。因为每多一轮对话，整个上下文都要重新发送一次，三轮累积的 Token 远超一次深度思考的额外开销。

简单任务反过来。把 /effort 调低或者在 /config 里关掉思考模式，效果立竿见影。思考 Token 按输出价计费，默认预算对简单任务来说浪费明显。

#### 长内容给路径，别往对话里贴

比起控制输出长度，更有效的是控制输入质量。不要把 10000 行日志复制粘贴到对话里让 Claude 自己找错误，直接把日志文件路径发给它。Claude Code 会自己用 grep 之类的工具去检索需要的信息，只把相关内容拉进上下文。最便宜的 Token，永远是根本没进上下文的 Token。

![Image](https://pbs.twimg.com/media/HFu1rYoWoAAi58h?format=jpg&name=large)

#### 继续聊还是开新会话：一张决策表

这可能是 Claude Code 省 Token 最关键的一个判断。很多人的默认习惯是“做完就清”，实际上最省的默认习惯应该反过来：能继续就继续，开新会话是有条件触发的操作。

满足以下任一条件，继续当前会话：

- 任务没变。还在调同一个 bug、写同一个模块、围绕同一组文件工作。
- 距离上一条消息不超过 1 小时。缓存还活着，前面积累的上下文几乎不花钱。
- 上下文里的内容对当前工作仍然有用。之前读过的文件、讨论过的方案，模型还在用。

如果在思考问题暂时没有输入，可以发一条简短消息保持缓存活跃。有用户甚至写了心跳扩展来自动保活缓存，刷新一次缓存的成本只有完整缓存未命中的十分之一。

满足以下任一条件，开新会话：

- 任务换了。刚写完认证模块要做支付功能，两件事的上下文完全不同。老会话里堆的代码文件、调试记录对新任务毫无用处，每条请求都在为这些无关内容付费。
- 闲置超过 1 小时。缓存大概率已经过期，继续聊等于触发全量重建，还不如从干净状态开始。
- 上下文被不相关内容塞满。试了十几种方案、读了大量无关文件，这些内容还在占位。即使缓存命中，模型也要在噪音里找信号，输出质量下降，而且压缩后可能丢掉关键信息。

一句话总结：缓存还热、任务没换，继续聊。缓存过期、任务切换、上下文里噪音太多，果断重开。

社区里有人反馈，一个会话只做一件事的工作方式，几乎不会触发配额问题。

![Image](https://pbs.twimg.com/media/HFu1t_saEAAEMmd?format=jpg&name=large)

#### 1M 上下文窗口：慎用

从 2026 年 3 月起，Max、Team、Enterprise 计划默认使用 Opus 4.6 的 1M 上下文窗口。Anthropic 取消了长上下文的 2 倍价格溢价，1M 窗口和 200K 同价。

但 1M 上下文正在成为很多人配额见底的头号原因。

问题出在缓存失效的代价上。你用 1M 上下文积累了一个很长的会话，中间离开电脑超过 1 小时，回来继续聊，这时候 1M Token 的缓存全部过期，一条消息就要触发全量重建。团队确认了这个问题，正在考虑将默认上下文从 1M 降到 400K。

而且大多数日常会话在 80-120K 上下文时就会触发压缩，根本用不到 200K，更别说 1M。社区里的经验数据也指向同一个结论：上下文超过 200K 后模型表现明显下降，350K 以上基本靠运气。

适合 1M 的场景确实存在：一次性加载大型代码库做全局重构、长时间多轮对话不想被压缩打断。但日常写代码改 bug 用不上。

我的建议：保留 1M 窗口但设一个保守的自动压缩阈值，兼顾灵活性和效率。

如果你想禁用 1M 上下文，在 \~/.claude/settings.json 中添加：

> \[json\] { "env": { "CLAUDE\_CODE\_DISABLE\_1M\_CONTEXT": "1" } }  
> \[json\] { "env": { "CLAUDE\_CODE\_DISABLE\_1M\_CONTEXT": "1" } }

如果你想设置自动压缩上下文的阈值：

> \[json\] { "env": { "CLAUDE\_CODE\_AUTO\_COMPACT\_WINDOW": "200000" } }  
> \[JSON\] { "env": { "CLAUDE\_CODE\_AUTO\_COMPACT\_WINDOW": "200000" } }

上下文接近 20 万 Token 时自动压缩摘要化，既保留上下文连续性，又防止成本失控。

#### 六条操作规则

#### 一、用 Sonnet 做日常工作

Opus 的输入成本大约是 Sonnet 的 1.7 倍，但更关键的是 Opus 消耗 Token 的速度大约是 Sonnet 的两倍。很多团队花大量时间研究怎么让 Opus 少说点，不如先问一句：这件事真的需要 Opus 吗？大多数编码任务 Sonnet 就够了，Opus 留给复杂架构决策和多步推理。在 Claude Code 里输入 /model 切换。

#### 二、别在会话中间换模型

提示缓存按模型隔离。你在 Opus 上积累了 10 万 Token 的缓存，切到 Sonnet 问个简单问题，Sonnet 要从零建立自己的缓存。这时候让 Opus 直接回答，反而比切到“更便宜”的 Sonnet 花得少。需要用轻量模型的场景，用子智能体而非切换主模型。

#### 三、精简 CLAUDE.md，控制技能数量

CLAUDE.md 的内容会注入到每一次请求里。官方建议控制在 200 行以内，只保留真正长期有效的规则。代码审查流程、数据库迁移步骤这类只在特定时刻需要的长说明，挪到技能里去；技能默认只在调用时加载，不会提前占上下文。

但技能也不是越多越好。加载太多技能和智能体是配额消耗的一个隐形杀手，团队正在改进界面让这些消耗更可见。技能放在项目目录（.claude/skills/）而非全局目录，只装当前项目真正需要的。没在用的 MCP 服务也记得关掉。

一个小技巧：在 CLAUDE.md 里用 HTML 注释写维护者备注，Claude 注入上下文前会把注释剥掉，不花 Token。

#### 四、命令行优先，MCP 其次

GitHub 的 gh 命令行工具比 GitHub MCP 服务器消耗的 Token 少得多。MCP 工具会把完整的结构定义注入上下文，请求和响应两端都在花 Token。能用命令行解决的事，别装 MCP。

#### 五、先花一点 Token 做计划

复杂任务先进入计划模式，让 Claude 先探索代码、提出方案，再进入实施，总成本往往更低。真正昂贵的是方向错了以后重扫代码、重写实现、重跑测试。

提问也是一样：“帮我优化这个代码库”这种模糊提示会触发广泛扫描；「给 auth.ts 里的 login 增加输入校验」这种具体指令，文件读取和试错都会显著减少。

#### 六、用 permissions.deny 限制模型的阅读范围

没有索引的代码库会迫使模型通过文件搜索来寻找上下文，效率极低。在 .claude/settings.json 中用 permissions.deny 严格限制模型可读取的范围，比如排除 node\_modules、构建产物、大型数据文件：

> \[json\] { "permissions": { "deny": \[ "Read(./.env)", "Read(./.env.\*)", "Read(./secrets/\*\*)", "Read(./node\_modules/\*\*)", "Read(./build)" \] } }  
> \[json\] { "权限": { "否认": \[ 读取(./.env) 读取(./.env.\*) 读取(./secrets/\*\*) 读取(./node\_modules/\*\*) 读取(./构建) \] } }

匹配这些模式的文件会被排除在文件发现和搜索结果之外，读取操作也会被直接拒绝。模型有时候会陷入长达 5 分钟以上的代码库搜索循环，即便你指明了文件路径，它仍可能在背景中反复读取不相关文件。permissions.deny 能从源头减少这种浪费。

#### 把部分工作委派出去

两个委派思路可以减少主会话的 Token 消耗。

子智能体：Claude Code 的子智能体有独立上下文，完成后只返回简短摘要给主会话。子智能体的缓存窗口只有 5 分钟（主智能体是 1 小时），每次调用的缓存利用率更低。但它的价值在于隔离上下文：代码审查、跑测试、查文档这些工作的详细输出不会留在主会话里，后续每条消息都不用为这些内容付费。

智能体团队和子智能体不同。智能体团队里每个成员都是独立 Claude 实例，各自维护自己的上下文窗口。计划模式下智能体团队的 Token 消耗是标准会话的数倍（社区估算约 7 倍），闲置的成员也在继续消耗。并发加速有成本，多智能体不等于更便宜。

Codex 插件：如果你同时有 OpenAI 订阅，社区里有人用 openai/codex-plugin-cc 把部分任务分出去。这是第三方社区方案，有用户反馈 Codex 完成同等任务大概只用 Claude Code 三分之一的 Token，但具体效果因任务而异。适合委派的：结构化的 bug 修复、代码审查、写测试。留给 Claude Code 的：架构设计、跨文件重构、需要理解整个代码库的复杂工作。

安装方式：

> \[bash\] claude mcp add codex -- npx -y
>
> [@openai/codex-plugin-cc](https://x.com/@openai/codex-plugin-cc)

#### 一些被澄清的误解

社区里流传不少关于配额消耗的说法，Claude Code 团队在讨论中做了官方澄清。

流传最广的一条是“上下文超过 256K 之后消耗会更快”。官方回应很直接：这不是真的。 实际原因很可能是用户重启了闲置已久的会话，触发了大规模缓存未命中，被误归因于上下文长度。

还有人抱怨模型每次读文件都在检查是否为恶意软件，浪费 Token。这个安全检测提示从 Sonnet 3.7 就有了，每次新模型都做过评估，没有引发退化。Opus 4.6 已经移除了这个提示。至于“自适应思考导致配额消耗异常”，团队也已排除。团队表示没有盲目相信内部指标，仍在持续调查：

> “我们在认真对待这件事，仍在持续调查。我们没有盲目相信内部指标。”

![Image](https://pbs.twimg.com/media/HFu157HbYAA2ot2?format=jpg&name=large)

省 Token 的核心思路就一句话：让缓存尽可能多地被命中，让上下文尽可能少地装无关内容。

开新会话是手段，理解了提示缓存之后你会发现，“在活跃会话里继续工作”才是默认策略，“开新会话”是特定条件触发的优化操作。

社区里很多人在比较 Claude Code、Codex、Cursor 的配额谁更慷慨。但配额收紧可能是个行业趋势，有人说我们正处在“补贴算力时代的末期”，类似当年 Uber 3 美元打车的阶段。与其赌哪家补贴更久，不如搞清楚成本结构，把钱花在刀刃上。

你们平时一个会话大概多长？有没有因为不敢继续聊而频繁 /clear 的习惯？

## 通俗精炼（1）

### 2026-04-13 07:08:36

#### Claude Code 省 Token 指南：核心总结

##### 一、核心结论

Claude Code 省 Token 的关键，不是 “频繁开新会话”，而是**尽量让缓存持续命中**。  
因此，**不开新会话不对，总是开新会话也不对**：要看任务是否延续、缓存是否还有效、上下文是否已经被噪音污染。

##### 二、为什么配额烧得快

###### 1. 模型不会 “接着读”
大模型每次收到新消息，都会把当前输入重新读一遍，而不是像人一样延续记忆。  
在 Claude Code 里，这些输入包括：

- 系统指令和工具定义
- `CLAUDE.md`规则
- 整段历史对话
- 你刚输入的新消息

对话越长，每次请求要 “重读” 的旧内容越多，成本自然越来越高。

###### 2. 真正省钱的是提示缓存
Claude Code 会把前面读过的内容做成 “缓存”，下次如果前缀完全一致，就可以直接复用。  
**缓存命中时，成本只有重算的约十分之一。**

但缓存有两个前提：

- **前缀必须完全一致**：中途改动前面的内容，后面的缓存就失效
- **缓存有时效**：主会话约 1 小时，子智能体约 5 分钟

所以，**活跃会话通常比新开会话更省钱**。

##### 三、最重要的判断：继续聊，还是开新会话

###### 适合继续当前会话
满足任一条件，就继续：

- 还在做同一件事
- 距离上一条消息不到 1 小时
- 之前读过的文件和讨论内容仍然有用

一句话：**任务没变、缓存还热，就继续聊。**

###### 适合开新会话
满足任一条件，就重开：

- 任务已经切换
- 会话闲置超过 1 小时
- 上下文塞满了无关内容，噪音明显变多

一句话：**任务换了、缓存过期、上下文变脏，就果断重开。**

##### 四、三个最反直觉但最有用的策略

###### 1. 频繁`/clear`往往更贵
新会话会重新加载系统提示、工具定义、项目规则等固定内容。  
这些基础内容本来在旧会话里可以走缓存，频繁清空反而等于反复付全价。

###### 2. 复杂任务不一定要省 “思考 Token”
对复杂重构、架构调整这类任务，**一次深度思考做对**，通常比 “关掉思考然后改三轮” 更省。  
因为每多一轮对话，整段上下文都要再传一遍。

###### 3. 少贴大段内容，多给路径
不要把大日志、大文件直接贴进对话。  
更好的做法是给文件路径，让 Claude 自己检索关键内容。  
**最省的 Token，是压根没进上下文的 Token。**

##### 五、1M 上下文为什么要慎用

###### 1. 问题不在单价，而在失效代价
虽然 1M 上下文和 200K 价格一样，但一旦缓存过期，**1M 的重建成本极高**。  
如果你离开 1 小时再回来继续聊，可能一条消息就触发一次超大规模重算。

###### 2. 大多数日常任务根本用不上
日常写代码、修 bug，通常 80K–120K 就已经足够。  
超过 200K 后，社区普遍反馈效果变差；到 350K 以上，质量更不稳定。

###### 3. 更合理的做法
建议：

- 保留 1M 能力，但不要默认依赖它
- 设置更保守的自动压缩阈值，比如`200000`

核心原则：**长上下文不是免费午餐，越长越怕缓存失效。**

##### 六、六条最实用的操作建议

###### 1. 日常优先用 Sonnet
大多数编码任务 Sonnet 已经够用，Opus 留给复杂推理和架构决策。  
先选对模型，比事后抠 Token 更重要。

###### 2. 不要在会话中途切模型
缓存按模型隔离。  
你从 Opus 切到 Sonnet，相当于让 Sonnet 从零重新建缓存，未必更省。

###### 3. 精简`CLAUDE.md`
`CLAUDE.md`会注入每次请求。  
只保留长期有效规则，控制在 200 行内；临时流程放到 skills 里按需加载。

###### 4. 命令行优先，少用 MCP
能用`gh`、`grep`、命令行工具完成的，就别优先走 MCP。  
因为 MCP 会把更多结构信息注入上下文，Token 开销更高。

###### 5. 先花一点 Token 做计划
复杂任务先让模型探路、定方案，通常比直接开干再返工更省。  
**错方向的返工，才是最贵的 Token 浪费。**

###### 6. 限制可读范围
用`permissions.deny`排除`node_modules`、构建产物、大型数据文件、敏感文件。  
这样可以减少模型无意义地扫库和误读。

##### 七、子智能体和任务委派的价值

###### 1. 子智能体的价值是 “隔离上下文”
代码审查、跑测试、查文档这类工作，可以交给子智能体。  
它们完成后只回传摘要，避免把大量中间过程堆进主会话。

###### 2. 多智能体不等于更省
智能体团队虽然并发更强，但每个成员都在独立消耗 Token。  
计划模式下，整体开销可能是普通会话的数倍。

###### 3. 委派适合标准化任务
适合外包出去的工作：

- 结构化 bug 修复
- 代码审查
- 测试编写

适合留在主会话的工作：

- 架构设计
- 跨文件重构
- 需要全局理解代码库的复杂任务

##### 八、最终记住这一句话

###### 省 Token 的本质
**让缓存尽量命中，让上下文尽量干净。**

因此，最优策略不是 “总开新会话”，而是：

- **缓存还热、任务没变：继续聊**
- **缓存过期、任务切换、噪音过多：开新会话**

这才是 Claude Code 更省配额的正确使用方式。

## 结构化（1）

### 2026-04-13 09:59:45

#### 主旨概括

这篇文章的核心观点是：**Claude Code 费 Token 的根本原因，不只是上下文长，而是 “缓存是否命中”**。很多人以为频繁`/clear`或不断开新会话能省配额，但在缓存还有效时，这么做往往反而更贵。

#### 一、为什么配额会烧得这么快

- 社区普遍反馈 Claude Code 配额消耗过快：**Max 用户有人 2 天就用完一周额度**。
- 有人在**AWS Bedrock**上估算，**一个会话真实成本超过 134 美元**，而**Pro Max 5x 月订阅才 100 美元**，说明官方订阅本身可能是在补贴成本。
- 很多人第一反应是频繁`/clear`或每步都开新会话，但作者指出：**如果不了解缓存机制，这种做法可能适得其反**。

#### 二、模型为什么会 “越聊越贵”

- 大语言模型不像人类会 “接着读”，它**每次收到新消息，都要从头读取整段输入**。
- Claude Code 的输入通常包括三部分：
  - **固定部分**：系统指令、工具定义、`CLAUDE.md`规则
  - **对话历史**：此前所有轮次
  - **新消息**：当前输入
- 问题在于，前两部分在同一会话中通常变化不大，但模型仍然要重新处理。
- 结果是：**聊到 20 轮后，一条新消息可能附带 10 万 Token 的历史内容**，自然又慢又贵。

**例子：**
- 文章用 “每次去图书馆都要重新翻同一本 500 页报告” 的比喻说明：即使问题不同，但只要输入没缓存，每次都得重读整本书。

#### 三、提示缓存到底在解决什么问题

- 提示缓存可以理解为：**第一次读完后，把 “阅读笔记” 存下来**。
- 下次如果输入前缀相同，就不必重新算，可以直接复用缓存。
- 关键收益：**读取缓存的成本只有重新计算的 1/10**。
- 粗略估算：
  - 一个**20 轮会话**
  - 上下文约**10 万 Token**
  - 如果缓存持续命中，**输入成本可比每次全价处理低 6 倍以上**

#### 四、缓存生效有两个关键前提

##### 1. 只能命中 “完全一致的前缀”

- 缓存不是模糊匹配，而是要求：**从开头开始，一字不差**。
- 如果前 3 页完全一样，第 4 页改了一个字，那么只能复用前 3 页缓存；如果第 1 页就变了，**整段缓存失效**。
- Claude Code 的输入结构之所以有效，就是因为：
  - 前面放固定内容
  - 中间放历史对话
  - 最后追加新消息
- 这样每轮只变末尾一小段，前面大部分都能继续命中缓存。

##### 2. 缓存有存活时间

- **主智能体缓存窗口：1 小时**
- **子智能体缓存窗口：5 分钟**
- **API 用户默认：5 分钟**，也可付费开到 1 小时
- 每次命中缓存都会**刷新计时器**，所以只要持续互动，缓存就能一直保持 “热” 的状态。

#### 五、三个最反直觉但很重要的省钱策略

##### 1. 缓存还热时，继续聊比开新会话更省

- 每个新会话都要重新加载：
  - 系统提示
  - 工具定义
  - `CLAUDE.md`
  - 项目配置
- 这些 “基础设施” 大约就有**5 万 Token**
- 所以频繁`/clear`，本质上是在反复支付这部分的全价成本。
- 如果会话仍活跃，这些内容都在缓存里，**只需付约 1/10 成本**。

**关键判断：**
- “闲置约 1 小时的大型会话建议重开” 这句话的重点是：**闲置**，不是 “会话大就一定要重开”。

##### 2. 复杂任务一次做对，往往比反复返工更省

- 关闭扩展思考，单次请求确实能省 Token。
- 但如果是复杂重构任务：
  - 开着思考，一次做对
  - 和关掉思考后反复修改 3 轮
- 后者通常更贵，因为**每多一轮，对话上下文都要再发一遍**。
- 相反，简单任务就适合降低`/effort`，或在`/config`里关闭思考模式，能立刻省成本。

##### 3. 长内容不要直接贴进对话

- 不要把**1 万行日志**直接粘贴给 Claude 让它自己找问题。
- 更省的方法是：**给文件路径**，让 Claude Code 用工具去搜索需要的信息。
- 这样只有相关片段会进入上下文。

**一句话：**
- **最便宜的 Token，是根本没进入上下文的 Token。**

#### 六、到底什么时候继续聊，什么时候开新会话

##### 适合继续当前会话的情况

- **任务没变**：还在修同一个 bug、写同一个模块
- **距离上一条消息不超过 1 小时**：缓存大概率还活着
- **旧上下文还有用**：之前读过的文件、讨论的方案仍然相关

**补充技巧：**
- 如果你在思考、暂时不操作，可以发一句简短消息维持活跃。
- 有用户甚至做了 “心跳扩展” 自动保活缓存，因为**刷新缓存的成本只有完整缓存未命中的 1/10**。

##### 适合开新会话的情况

- **任务切换了**：比如刚写完认证模块，现在开始做支付模块
- **闲置超过 1 小时**：缓存大概率过期
- **上下文噪音太多**：尝试了很多无关方案、读了大量不相关文件，影响质量也浪费成本

**作者给出的判断口诀：**
- **缓存还热、任务没换，继续聊。**
- **缓存过期、任务切换、噪音太多，果断重开。**

#### 七、为什么要慎用 1M 上下文窗口

- 从**2026 年 3 月起**，Max、Team、Enterprise 默认使用**Opus 4.6 的 1M 上下文窗口**。
- Anthropic 取消了长上下文**2 倍价格溢价**，因此**1M 和 200K 同价**。
- 但真正的问题不是单价，而是：**缓存失效后的重建代价太高**。

##### 1M 的主要风险

- 如果你积累了一个接近**1M Token**的长会话
- 中间离开电脑超过**1 小时**
- 回来继续聊时，缓存过期
- 结果就是：**一条消息触发整段 1M Token 的全量重建**

##### 社区经验与官方倾向

- 团队已经确认这个问题，并考虑将默认上下文从**1M 降到 400K**
- 大多数日常会话其实在**80K–120K**时就会被压缩
- 很多场景甚至用不到**200K**
- 社区经验还显示：
  - **超过 200K**后，模型表现明显下降
  - **超过 350K**后，效果 “基本靠运气”

##### 什么时候才适合 1M

- 一次性加载大型代码库做全局重构
- 长时间多轮对话，不希望频繁被压缩打断

##### 作者建议

- **保留 1M 能力，但设置保守的自动压缩阈值**
- 例如在`~/.claude/settings.json`中设置：
  - 禁用 1M：`CLAUDE_CODE_DISABLE_1M_CONTEXT=1`
  - 自动压缩阈值：`CLAUDE_CODE_AUTO_COMPACT_WINDOW=200000`
- 这样在接近**20 万 Token**时自动压缩，兼顾连续性与成本控制。

#### 八、六条实用操作规则

##### 1. 日常优先用 Sonnet，不要默认 Opus

- **Opus 输入成本约是 Sonnet 的 1.7 倍**
- 更关键的是：**Opus 消耗 Token 的速度约是 Sonnet 的 2 倍**
- 大部分编码任务 Sonnet 就够用，Opus 更适合复杂架构和多步推理。

##### 2. 不要在会话中途切模型

- 提示缓存是**按模型隔离**的。
- 例如你在 Opus 上积累了**10 万 Token 缓存**，切到 Sonnet 后，Sonnet 要从零开始建缓存。
- 所以很多时候，**继续让 Opus 回答，反而比切到更便宜的 Sonnet 更省**。

##### 3. 精简`CLAUDE.md`，减少技能数量

- `CLAUDE.md`会注入到**每一次请求**
- 官方建议控制在**200 行以内**
- 长流程说明适合拆到技能里，因为技能默认只在调用时加载
- 但技能也不是越多越好，过多技能和智能体本身就是隐形消耗源
- 小技巧：在`CLAUDE.md`里用**HTML 注释**写维护说明，注入前会被剥掉，**不花 Token**

##### 4. 命令行优先，MCP 其次

- 例如`gh`命令行工具比 GitHub MCP 更省 Token
- 原因是 MCP 会把大量结构定义注入上下文，请求和响应都更重
- 能用命令行解决的，尽量不要装 MCP

##### 5. 先花一点 Token 做计划，反而能省总成本

- 复杂任务先让 Claude 探索代码、提出计划，再实施，整体更省
- 真正昂贵的不是规划，而是：
  - 方向错了
  - 重新扫代码
  - 重写实现
  - 重跑测试
- 提问越具体，越省 Token  
  例如：
  - 模糊：`帮我优化这个代码库`
  - 具体：`给 auth.ts 里的 login 增加输入校验`

##### 6. 用`permissions.deny`限制阅读范围

- 在`.claude/settings.json`中排除：
  - `node_modules`
  - 构建产物
  - 大型数据文件
  - `.env`、`secrets`
- 这样这些文件既不会出现在搜索结果里，也不能被读取。
- 文章提到，模型有时会陷入**超过 5 分钟**的代码库搜索循环，即使你已经明确给了路径。限制读取范围能从源头减少浪费。

#### 九、把部分工作委派出去，减少主会话负担

##### 子智能体

- 子智能体有**独立上下文**
- 完成后只把简短摘要返回主会话
- 虽然它的缓存窗口只有**5 分钟**，缓存利用率不如主智能体
- 但它的价值在于：**把大量细节隔离在外部，不污染主会话**

**适合委派给子智能体的工作：**
- 代码审查
- 跑测试
- 查文档

##### 智能体团队

- 和子智能体不同，智能体团队中的每个成员都是独立 Claude 实例
- 每个成员都有自己的上下文窗口
- 在计划模式下，社区估算其 Token 消耗约为**标准会话的 7 倍**
- 并发更快，但**绝不意味着更便宜**

##### Codex 插件

- 社区里有人用`openai/codex-plugin-cc`分担部分任务
- 有用户反馈：**同等任务，Codex 约只消耗 Claude Code 的 1/3 Token**
- 但这是第三方方案，效果依任务而异

**适合分派的任务：**
- 结构化 bug 修复
- 代码审查
- 写测试

**适合留给 Claude Code 的任务：**
- 架构设计
- 跨文件重构
- 需要理解整个代码库的复杂工作

#### 十、几个常见误解，官方已经澄清

##### 误解 1：上下文超过 256K 后消耗会变快

- 官方明确表示：**这不是真的**
- 更可能的真实原因是：用户重启了闲置太久的会话，触发了大规模缓存未命中。

##### 误解 2：安全检测提示会显著浪费 Token

- 这类提示从**Sonnet 3.7**就存在
- 官方表示已评估过，没有导致明显退化
- **Opus 4.6**已经移除了这个提示

##### 误解 3：自适应思考导致异常耗额

- 团队表示：**这个原因也已被排除**
- 同时他们也强调，问题还在持续调查，并没有盲信内部指标。

#### 结论

- 文章最后把核心逻辑浓缩成一句话：**尽量让缓存命中，尽量别把无关内容塞进上下文。**
- 真正省 Token 的默认习惯不是 “做完就清空”，而是：
  - **任务没变、缓存还热，就继续聊**
  - **任务换了、缓存过期、噪音太多，再开新会话**
