## 分析要点

- **核心高价值点**：将LLM支出与调用链路、用户、模型、失败模式和预算限额关联起来，使成本控制从月度账单管理转为实时工程治理。
- **留存建议**：短期参考后可保留为AI成本治理案例（提供了企业内部管理编码代理LLM支出的网关化思路，包括预算分层、实时追踪、限额告警与调用归因，具备一定参考价值。）

**知识要点**

- 编码代理可能在单个任务中发起大量模型调用，导致个人每周产生高额不可见成本。
- LLM预算可按组织、工作区、用户、API key 以及月、周、日、小时窗口分层设置。
- 集中式LLM网关可以为工程管理层提供实时支出可见性和统一熔断点。
- 成本数据与trace、模型调用和评估系统结合后，可用于定位高成本代理行为并优化实现。
- 硬性限额需要配套提前告警和预算提升审批流程，否则容易阻碍正常研发。

**行动项**

- 盘点团队中所有编码代理和LLM客户端的调用入口，评估是否能统一接入网关或代理层。
- 按组织、团队、用户和API key设计分层预算，并设置日级和小时级异常使用阈值。
- 将LLM成本数据与调用trace、用户身份、模型名称和任务类型关联，便于追踪异常支出来源。
- 为高成本或接近限额场景设计提前告警和可审计的额度提升流程。

### 我们如何让编码代理的花费可预测

LangSmith LLM Gateway is currently in private beta.

[Sign up here](https://www.langchain.com/blog/introducing-llm-gateway) to request access.

在过去几年中，AI 的使用在预算方面很容易被忽视。在 LangChain，模型使用主要局限于少数几个团队，使用情况可预测，而且月度账单也在可控制范围内。

然而，在过去的一年里，由于同时发生了几件事，这一点不再成立：

- AI 的使用从几个团队扩展到了整个公司
- 最好的机型变得更贵了
- 代理变得足够强大，能够轻松发起数十次模型调用来完成单个任务。

因此，AI 支出变得更难理解且更难实时控制。

在工程领域中，这种情况表现得最为突出。一名大量使用编码代理的开发人员，在无人察觉的情况下每周就能产生数千美元的支出。我们的领导层需要一种能够实时查看支出情况、按团队和用户设置限制、防止意外失控使用，同时不影响正常工作效率的解决方案。

#### 实现 LLM 网关

考虑到成本跟踪，我们直接将 LangSmith LLM Gateway 集成到了我们每天使用的产品中。直接目标很简单：通过编写代理程序防止意外的失控支出，让工程副总裁和财务负责人都能安心。

在 LangSmith LLM Gateway 中，预算可以在几个维度上设置：

- 全组织范围的
- 工作区
- 用户
- API 密钥

我们有默认预算，每位员工都能在月度、周度、日度和小时度的范围内达成，并且能够为参与需要更高资源使用量项目的人员设置异常。

我们在公司内能够进行集中部署的各个场景中应用了 Gateway：通过 Claude Code、Codex 或 LangChain Deep Agents 部署编码代理。公司内每次符合条件的编码代理调用都经过 LLM Gateway，让我们的工程负责人能够精确到分钟地全面了解全公司的支出情况。我们还确保了其易于实施，通过我们的 MDM 进行集中编排，这样每个用户就无需自行处理设置。

“Gateway 的优势在于，集中控制带来了更高的确定性，这样我就不会打开仪表盘时看到一张意外的数千美元账单。我可以通过集中的关闭/控制点查看限制和支出情况。”——Alex Lunev，LangChain 工程副总裁

#### 连接成本控制到 LangSmith 技术栈的其余部分

当成本数据与 AI 系统的其余部分连接时，网关最为有用。

因为 LangSmith LLM Gateway 是 LangSmith 的一部分，支出控制与我们已用于管理 AI 应用的系统相连。Gateway 的运行可被追踪、归因于用户或密钥，并与生产数据一起进行分析。

这意味着成本数据不仅限于月度账单。我们可以将支出与特定的代理、模型调用、追踪和故障模式关联起来。我们还可以使用现有的 LangSmith 控件来处理 OAuth、模型管理和用户管理，而无需围绕独立代理重新构建这些工作流。

这也让网关数据更具可操作性。当编码代理的消耗超出预期时，我们可以检查追踪数据，了解发生了什么，并利用评估和可观测性数据来改进底层代理的行为。

#### 我们的内部推出教会了我们什么，以及它如何塑造了产品

我们自己运行 Gateway 首先揭示了账单和路由在纸面呈现方式与实际运行表现之间的差距。三个经验教训确定了我们下一步的投资方向：

1. Model pricing is more complex than a static table. A lookup table goes stale quickly, so accurate cost accounting has to absorb caching, token-tier nuances and frequent provider prices changes. This pushed us to treat model pricing as a system than a constant: we’re auditing our calculation logic and building in a more rigorous update path in order to maintain trustworthy costs.
2. Not every client routes cleanly through Gateway, and support varies by app and by how it is managed. In our rollout, Cursor only exposed base-url swap as a per-user setting covering only Chat, and not something that we could push through our MDM across the platform. Claude Desktop could only be passed through the gateway as a managed config, but turning it on shifted the app into a local agent in place of standard Chat (and the capability is early in development). Rather than wait on provider support, this shaped our approach to measure the delta of what gateway captures versus what the rest of our enterprise provider settings capture (i.e. monthly Claude plans) in order to have spend accounted for even when traffic can’t flow through Gateway directly.
3. Hard limits need a workflow around them. A cap with no runway just blocks work. Engineers told us that they want early warning well before they hit a limit and a fast, auditable way to raise it. That feedback turned limits from static guardrails into a workflow: we’re adding tiered alerting ahead of a threshold and exploring a paper-trailed budget-increase request flow so spend controls protect the business without getting in the way.

内部试用将抽象的边缘情况转化为具体的产品优先级，包括价格准确性、优雅处理无法通过网关路由的客户端，以及管理支出限额。

#### 结果

自从在内部推出 LangSmith LLM Gateway 以来，我们的 LLM 成本一直控制在预算范围内。

更大的变化是，支出不再是我们只能在月底才弄明白的事情。工程领导者可以实时查看使用情况，设置适当的限额，并让团队能够灵活使用编码代理，而不会产生意外账单。

## 解读（1）

### 2026-06-16 08:36:49

#### 我们如何让编码代理的花费可预测

##### 一、深度总结

这篇文章讲的是：**当 AI 编码代理从少数人试用变成全公司常态后，LLM 成本开始失控，必须从“事后看账单”转向“实时管控”。**

LangChain 的变化主要来自三点：

1. **AI 使用范围扩大**  
   从少数团队使用，变成几乎全公司都在用。

2. **高性能模型越来越贵**  
   最强模型单次调用成本更高。

3. **代理会自动多轮调用模型**  
   一个编码任务可能触发几十次 LLM 调用，开发者未必意识到成本正在快速累积。

结果是：  
> 一个重度使用编码代理的工程师，可能在一周内产生数千美元费用，而管理层事前并不知道。

为解决这个问题，LangChain 内部部署了 **LangSmith LLM Gateway**，把公司内的编码代理调用统一经过网关，包括 Claude Code、Codex、LangChain Deep Agents 等。

它主要提供：

- 按组织设置预算
- 按 Workspace 设置预算
- 按用户设置预算
- 按 API Key 设置预算
- 支持月、周、日、小时级别的预算窗口
- 支持特殊项目申请更高额度
- 实时查看支出
- 超限前预警或限制
- 可追踪每次调用、代理、用户、模型与失败原因

核心价值是：

> 不再等月底才知道花了多少钱，而是实时知道钱花在哪里、谁花的、为什么花、是否值得。

---

##### 二、深入浅出解读

可以把 LLM Gateway 理解成：

> **公司所有 AI 调用前面的“智能水表 + 电闸 + 账本”。**

过去用 AI 像用水电：

- 谁开了水龙头，不清楚
- 水流多大，不清楚
- 哪个部门用最多，不清楚
- 月底账单来了才发现爆表

现在加了一个网关：

- 每个人用了多少，实时看得到
- 每个团队花了多少，能统计
- 每个模型调用花了多少钱，能追踪
- 超过额度前能提醒
- 必要时能限流或关停
- 如果某个代理特别费钱，可以回看调用链，优化它

这对编码代理尤其重要。

因为编码代理不是简单问答。  
它可能会：

1. 读代码
2. 搜索文件
3. 分析上下文
4. 修改代码
5. 跑测试
6. 报错后继续修
7. 再次调用模型

用户只看到“帮我实现功能”，背后可能已经发生几十次模型调用。

所以真正的问题不是：

> AI 能不能写代码？

而是：

> AI 写代码时，公司能不能控制成本、理解成本、优化成本？

---

##### 三、产品实践带来的关键经验

###### 1. 模型定价不是静态表格

LLM 价格会受到很多因素影响：

- 模型不同
- 输入输出 token 不同
- 缓存命中不同
- provider 调价
- token tier 不同

所以成本计算不能靠一张固定价格表。  
必须把模型定价当成一个持续维护的系统。

---

###### 2. 不是所有客户端都能顺利接入网关

一些工具不一定支持企业统一配置。

例如：

- Cursor 的 base URL 配置只覆盖部分功能
- Claude Desktop 的网关接入能力还比较早期
- 有些流量无法完全经过 Gateway

所以企业不能假设“所有 AI 调用都能被网关捕获”。

更现实的做法是：

> 网关捕获一部分，企业级 provider 账单补齐另一部分，两边对账。

---

###### 3. 硬性限额不能粗暴

如果只是简单设置上限，到了额度就停，会影响工程师工作。

更好的方式是：

- 提前预警
- 分级提醒
- 快速申请提额
- 留下审批记录
- 对特殊项目放宽限制

也就是说，预算控制不是“堵住使用”，而是“让使用可控”。

---

##### 四、热门回复补充理解

###### 1. 代理输出太大，往往说明任务没拆好

Mitchell Hashimoto 提到：

> 如果代理一次生成超过 1000 到 1500 行 diff，通常说明任务太大，需要拆解。

这和成本控制相关。  
任务越大，代理越容易：

- 多轮思考
- 反复修改
- 产生大量上下文
- 消耗更多 token
- 结果也更难 review

所以控制成本不仅靠网关，也靠更好的开发习惯：

> 小任务、小 diff、小步提交。

---

###### 2. 小模型可用于低价值环节

Florian Brand 提到：

> 用 4B 小模型探索代码库，可降低 10% 到 50% token 成本，同时不影响大模型最终表现。

这指出另一个方向：

> 不是所有步骤都需要最贵模型。

例如：

- 搜索代码：小模型够用
- 分类文件：小模型够用
- 初步理解：小模型够用
- 核心设计与复杂推理：再用大模型

未来编码代理很可能是多模型协作，而不是一路调用最贵模型。

---

##### 五、辩证思考

###### 1. 成本可控，是 AI 工程化的前提

AI 试用阶段，大家关注效果。  
AI 规模化阶段，必须关注成本。

如果一项技术无法预测成本，它就很难进入企业核心流程。

所以 LLM Gateway 的意义不只是省钱，而是让 AI 使用变得：

- 可观测
- 可归因
- 可审计
- 可治理
- 可扩展

这相当于把 AI 从“个人工具”推进到“企业基础设施”。

---

###### 2. 但过度控制也可能压制创新

如果预算限制太死，工程师可能：

- 不敢尝试新工具
- 不愿探索复杂任务
- 绕过官方系统
- 用个人账号或影子 IT

因此，好的成本控制不是“一刀切”，而是：

> 默认有限制，合理可突破，全程可追踪。

控制的目标不是少用 AI，而是避免无意识浪费。

---

###### 3. 真正的问题不是“贵”，而是“不知道为什么贵”

贵不一定错。  
如果一次高成本代理任务节省了工程师一天时间，那可能很划算。

问题在于：

- 不知道谁花了
- 不知道花在哪里
- 不知道有没有产出
- 不知道能不能优化

所以企业要看的不是单纯账单，而是：

> AI 成本 / 工程产出 / 时间节省 / 质量提升之间的关系。

未来更重要的指标可能不是“花了多少钱”，而是：

> 每 1 美元 AI 成本创造了多少工程价值。

---

###### 4. 编码代理需要“技术治理 + 使用方法”双轮驱动

网关能解决可见性和限制问题，但不能单独解决全部浪费。

还需要：

- 更好的任务拆分
- 更小的代码变更
- 更合理的模型路由
- 更强的 agent 评估
- 更清晰的权限和审批
- 更成熟的工程规范

也就是说：

> 成本治理不是财务问题，而是 AI 工程能力的一部分。

---

##### 六、一句话结论

**当编码代理开始规模化使用，企业最需要的不是简单“省钱”，而是建立一套实时、可追踪、可调节的 AI 成本治理系统，让开发者放心用，让管理者看得见，让预算不失控。**

## 结构化（1）

### 2026-06-16 08:54:32

#### 我们如何让编码代理的花费可预测

LangChain 发现，随着 AI 使用从少数团队扩展到全公司，尤其是编码代理普及后，LLM 成本开始变得难以预测。为了解决“一个开发者一周可能无意产生数千美元费用”的问题，他们内部引入了 **LangSmith LLM Gateway**，用于实时监控、预算控制和成本归因。

---

##### 1. 背景：AI 成本从“可忽略”变成“难控制”

过去几年，LangChain 的 AI 使用范围较小，主要集中在少数团队，因此：

- 使用量相对稳定；
- 月度账单可预测；
- 成本管理压力不大。

但过去一年情况发生变化：

- AI 使用扩展到整个公司；
- 更强的模型价格更高；
- 编码代理能力增强，一个任务可能触发几十次模型调用。

因此，AI 支出变得更难理解，也更难实时控制。

---

##### 2. 问题最突出地出现在工程团队

在工程场景中，编码代理的使用尤其容易导致成本失控。

一个大量使用编码代理的开发者，可能在没人察觉的情况下：

- 每周产生数千美元支出；
- 触发大量模型调用；
- 到月底账单出来时才发现异常。

公司管理层需要一种机制，能够：

- 实时查看支出；
- 按团队、用户设置预算限制；
- 防止意外超额使用；
- 同时不影响工程师正常工作效率。

---

##### 3. 解决方案：引入 LangSmith LLM Gateway

LangChain 将 **LangSmith LLM Gateway** 集成到日常使用的 AI 工具中，目标是防止编码代理带来的意外失控支出。

Gateway 支持从多个维度设置预算：

- 整个组织；
- 工作区；
- 用户；
- API 密钥。

他们为员工设置了默认预算，覆盖：

- 月度；
- 周度；
- 日度；
- 小时级别。

同时，对于参与高资源消耗项目的员工，也可以单独设置例外额度。

---

##### 4. 部署方式：集中管理所有编码代理调用

LangChain 将 Gateway 应用于公司内部多个编码代理场景，例如：

- Claude Code；
- Codex；
- LangChain Deep Agents。

每次符合条件的编码代理调用都会经过 LLM Gateway，使工程负责人可以：

- 精确到分钟查看全公司支出；
- 了解具体用户和团队的使用情况；
- 及时发现异常消耗。

为了降低使用门槛，他们还通过 MDM 进行集中配置，避免每位员工都要手动设置。

LangChain 工程副总裁 Alex Lunev 表示，Gateway 的价值在于提供集中控制点，避免打开仪表盘时突然看到几千美元的意外账单。

---

##### 5. 成本控制与 LangSmith 技术栈打通

文章强调，LLM Gateway 不只是一个账单工具，只有当成本数据和 AI 系统运行数据连接起来时，价值才最大。

由于 Gateway 是 LangSmith 的一部分，因此支出数据可以与以下信息关联：

- 具体代理；
- 模型调用；
- 用户或 API 密钥；
- 追踪数据；
- 生产环境数据；
- 故障模式。

这意味着团队不只是月底看账单，而是可以分析：

- 哪个代理最耗钱；
- 哪类模型调用异常；
- 哪些失败任务造成了额外成本；
- 如何通过评估和可观测性改进代理行为。

---

##### 6. 内部试用带来的三个产品经验

LangChain 在内部使用 Gateway 后，发现了账单和路由在真实环境中的复杂性，并总结出三个关键经验。

###### 6.1 模型定价比静态价格表复杂

模型价格不是一张固定表就能解决的，因为它会受到很多因素影响：

- 缓存机制；
- token 分层计费；
- 供应商频繁调整价格。

因此，LangChain 认为模型定价应该被当作一个持续更新的系统，而不是一个固定常量。

他们正在：

- 审计成本计算逻辑；
- 建立更严谨的价格更新流程；
- 确保成本统计可信。

---

###### 6.2 并非所有客户端都能顺利通过 Gateway

不同应用对网关路由的支持程度不同。

例如：

- Cursor 只允许用户级别设置 base-url，而且只覆盖 Chat，无法通过 MDM 在全平台统一推送；
- Claude Desktop 可以通过受管配置走 Gateway，但启用后会切换到本地代理模式，而不是标准 Chat，并且能力还处于早期阶段。

因此，LangChain 没有单纯等待供应商支持，而是开始衡量：

- Gateway 能捕获多少流量；
- 企业供应商设置中还有多少支出未经过 Gateway；
- 例如月度 Claude 套餐费用如何纳入整体成本统计。

---

###### 6.3 硬性限额需要配套流程

单纯设置预算上限并不够。

如果没有提前提醒和申请机制，硬性限制可能会直接阻塞工程师工作。

工程师反馈希望拥有：

- 接近限额前的提前预警；
- 快速、可审计的额度提升流程。

因此，LangChain 正在将预算限制从静态规则变成完整工作流，包括：

- 分级预警；
- 达到阈值前提醒；
- 带记录的预算提升申请流程。

目标是既保护公司成本，又不妨碍正常开发。

---

##### 7. 结果：成本保持在预算内，并实现实时可见

自内部推出 LangSmith LLM Gateway 后，LangChain 的 LLM 成本一直保持在预算范围内。

更重要的是，AI 支出不再是月底才知道的事情。工程负责人现在可以：

- 实时查看使用情况；
- 设置合理限额；
- 支持团队灵活使用编码代理；
- 避免意外账单。

##### 8. 热门回复中的补充观点

文章下方也有一些值得注意的讨论。

###### Mitchell Hashimoto

他提到自己的经验法则：

- 如果代理生成的代码差异超过 **1001 到 1500 行**，通常说明任务太大；
- 应该把问题拆分成更小的任务。

这说明成本控制不仅是预算问题，也和任务拆分、代理使用方式有关。

###### Florian Brand

他提到微软的一个方向：

- 使用 **4B 小模型**探索代码库；
- 可将 token 成本降低 **10% 到 50%**；
- 同时保持大模型的整体性能。

这说明未来降低编码代理成本，也可以通过“小模型 + 大模型”的组合来实现。
