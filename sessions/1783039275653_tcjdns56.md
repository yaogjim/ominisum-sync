I built these skills as a way to fix common failure modes I see with Claude Code, Codex, and other coding agents.

> "No-one knows exactly what they want"
>
> David Thomas &amp; Andrew Hunt, [The Pragmatic Programmer](https://www.amazon.co.uk/Pragmatic-Programmer-Anniversary-Journey-Mastery/dp/B0833F1T3V)

**The Problem**. The most common failure mode in software development is misalignment. You think the dev knows what you want. Then you see what they've built - and you realize it didn't understand you at all.

This is just the same in the AI age. There is a communication gap between you and the agent. The fix for this is a **grilling session** - getting the agent to ask you detailed questions about what you're building.

**The Fix** is to use:

- `/grill-me` - for non-code uses
- `/grill-with-docs` - same as `/grill-me`, but adds more goodies (see below)

These are my most popular skills. They help you align with the agent before you get started, and think deeply about the change you're making. Use them *every* time you want to make a change.

> With a ubiquitous language, conversations among developers and expressions of the code are all derived from the same domain model.
>
> Eric Evans, [Domain-Driven-Design](https://www.amazon.co.uk/Domain-Driven-Design-Tackling-Complexity-Software/dp/0321125215)

**The Problem**: At the start of a project, devs and the people they're building the software for (the domain experts) are usually speaking different languages.

I felt the same tension with my agents. Agents are usually dropped into a project and asked to figure out the jargon as they go. So they use 20 words where 1 will do.

**The Fix** for this is a shared language. It's a document that helps agents decode the jargon used in the project.

Example

Here's an example [`CONTEXT.md`](https://github.com/mattpocock/course-video-manager/blob/076a5a7a182db0fe1e62971dd7a68bcadf010f1c/CONTEXT.md), from my `course-video-manager` repo. Which one is easier to read?

- **BEFORE**: "There's a problem when a lesson inside a section of a course is made 'real' (i.e. given a spot in the file system)"
- **AFTER**: "There's a problem with the materialization cascade"

This concision pays off session after session.

This is built into `/grill-with-docs`. It's a grilling session, but that helps you build a shared language with the AI, and document hard-to-explain decisions in ADR's.

It's hard to explain how powerful this is. It might be the single coolest technique in this repo. Try it, and see.

> "Always take small, deliberate steps. The rate of feedback is your speed limit. Never take on a task that’s too big."
>
> David Thomas &amp; Andrew Hunt, [The Pragmatic Programmer](https://www.amazon.co.uk/Pragmatic-Programmer-Anniversary-Journey-Mastery/dp/B0833F1T3V)

**The Problem**: Let's say that you and the agent are aligned on what to build. What happens when the agent *still* produces crap?

It's time to look at your feedback loops. Without feedback on how the code it produces actually runs, the agent will be flying blind.

**The Fix**: You need the usual tranche of feedback loops: static types, browser access, and automated tests.

For automated tests, a red-green-refactor loop is critical. This is where the agent writes a failing test first, then fixes the test. This helps give the agent a consistent level of feedback that results in far better code.

I've built a **`/tdd` skill** you can slot into any project. It encourages red-green-refactor and gives the agent plenty of guidance on what makes good and bad tests.

For debugging, I've also built a **`/diagnosing-bugs`** skill that wraps best debugging practices into a simple loop.

> "Invest in the design of the system *every day*."
>
> Kent Beck, [Extreme Programming Explained](https://www.amazon.co.uk/Extreme-Programming-Explained-Embrace-Change/dp/0321278658)

> "The best modules are deep. They allow a lot of functionality to be accessed through a simple interface."
>
> John Ousterhout, [A Philosophy Of Software Design](https://www.amazon.co.uk/Philosophy-Software-Design-2nd/dp/173210221X)

**The Problem**: Most apps built with agents are complex and hard to change. Because agents can radically speed up coding, they also accelerate software entropy. Codebases get more complex at an unprecedented rate.

**The Fix** for this is a radical new approach to AI-powered development: caring about the design of the code.

This is built in to every layer of these skills:

- `/to-prd` quizzes you about which modules you're touching before creating a PRD

And crucially, `/improve-codebase-architecture` helps you rescue a codebase that has become a ball of mud. I recommend running it on your codebase once every few days.

#### Reference

These split on one axis — who can invoke them. **User-invoked** skills are reachable only when you type them (e.g. `/grill-me`); their job is to orchestrate. **Model-invoked** skills can be invoked by you *or* reached for automatically by the agent when the task fits; they hold the reusable discipline. A user-invoked skill may invoke model-invoked skills, but never another user-invoked one.

##### Engineering

Skills I use daily for code work.

**User-invoked**

- **ask-matt** — Ask which skill or flow fits your situation. A router over the user-invoked skills in this repo.
- **grill-with-docs** — Grilling session that also builds your project's domain model, sharpening terminology and updating `CONTEXT.md` and ADRs inline.
- **triage** — Move issues through a state machine of triage roles.
- **improve-codebase-architecture** — Scan a codebase for deepening opportunities, present them as a visual HTML report, then grill through whichever one you pick.
- **setup-matt-pocock-skills** — Configure this repo for the engineering skills (issue tracker, triage labels, domain doc layout). Run once per repo before using the other engineering skills.
- **to-issues** — Break any plan, spec, or PRD into independently-grabbable issues using vertical slices.
- **to-prd** — Turn the current conversation into a PRD and publish it to the issue tracker. No interview — just synthesizes what you've already discussed.

**Model-invoked**

- **prototype** — Build a throwaway prototype to answer a design question — a runnable terminal app for state/logic questions, or several radically different UI variations toggleable from one route.
- **diagnosing-bugs** — Disciplined diagnosis loop for hard bugs and performance regressions: reproduce → minimise → hypothesise → instrument → fix → regression-test.
- **research** — Investigate a question against high-trust primary sources and capture the findings as a cited Markdown file in the repo, run as a background agent.
- **tdd** — Test-driven development with a red-green-refactor loop. Builds features or fixes bugs one vertical slice at a time.
- **domain-modeling** — Actively build and sharpen a project's domain model — challenge terms against the glossary, stress-test with edge-case scenarios, and update `CONTEXT.md` and ADRs inline.
- **codebase-design** — Shared discipline and vocabulary for designing deep modules: a lot of behaviour behind a small interface, placed at a clean seam, testable through that interface.
- **code-review** — Two-axis review of the diff since a fixed point: **Standards** (does it follow the repo's coding standards, plus a Fowler smell baseline?) and **Spec** (does it faithfully implement the originating issue/PRD?), run as parallel sub-agents so neither pollutes the other.

##### Productivity

General workflow tools, not code-specific.

**User-invoked**

- **grill-me** — Get relentlessly interviewed about a plan or design until every branch of the decision tree is resolved.
- **handoff** — Compact the current conversation into a handoff document so another agent can continue the work.
- **teach** — Teach the user a new skill or concept over multiple sessions, using the current directory as a stateful teaching workspace.
- **writing-great-skills** — Reference for writing and editing skills well: the vocabulary and principles that make a skill predictable.

**Model-invoked**

- **grilling** — Interview the user relentlessly about a plan or design until every branch of the decision tree is resolved. The reusable loop behind `grill-me` and `grill-with-docs`.

claude-handoff: say handoff summary, not document

name claude-handoff

description Hand the current conversation off to a fresh background agent that picks up the work immediately.

argument-hint What will the next session be used for?

disable-model-invocation true

Write a handoff summary of the current conversation so a fresh agent can continue the work. Instead of saving it, launch a background agent seeded with the summary as its prompt: `claude --bg --name "<descriptive name>" "<handoff summary>"`. It starts in the current working directory and returns immediately; the user manages it with `claude agents`.

Always pass `-n` / `--name` with a descriptive name (e.g. `--name "Fix login bug"`) — it sets the display name shown in the job list, session picker, and terminal title.

Include a "suggested skills" section in the summary, which suggests skills that the agent should invoke.

Do not duplicate content already captured in other artifacts (PRDs, plans, ADRs, issues, commits, diffs). Reference them by path or URL instead.

Redact any sensitive information, such as API keys, passwords, or personally identifiable information — the summary becomes the agent's prompt.

If the user passed arguments, treat them as a description of what the next session will focus on and tailor the summary accordingly.

##### 核心信息汇总

###### 1. `/wayfinder` 是 Matt 新提出的核心技能

Matt Pocock 在多条推文中提到，他正在使用新技能 `/wayfinder` 来规划一整门课程，并且在过去四天里进行了接近 100 次独立的：

- grilling / 深度追问
- prototyping / 原型验证
- research / 研究调研

这些会话的结果都会回流到一个中心地图中。

这张地图有两个关键特征：

> 随着他对问题理解加深，地图会“增长”；  
> 随着问题被回答、决策被确定，地图又会“收缩”。

也就是说，`/wayfinder` 不是简单生成一份计划，而是在帮助用户持续管理“不确定性”。

---

###### 2. `/wayfinder` 是 `/grill-me` 的下一代形态

Matt 明确说：

> `/wayfinder` 是 `/grill-me` 的下一次进化。

`/grill-me` 的核心能力是让 AI 不急着执行，而是先反复追问用户，把需求、计划、设计中的模糊点问清楚。

而 `/wayfinder` 面向的是更大的问题：

- `/grill-me` 适合澄清一个计划或设计；
- `/wayfinder` 适合规划“巨大的工作块”；
- 它会识别：
  - 当前有哪些决策还没定；
  - 哪些地方仍处于“战争迷雾”中；
  - 哪些问题应该通过追问解决；
  - 哪些问题应该通过研究解决；
  - 哪些问题应该通过原型验证解决。

可以理解为：

##### 一、Matt 这套东西到底在解决什么问题？

它解决的不是“怎么让 AI 写代码”，而是更深一层的问题：

> 怎么让 AI 像一个靠谱工程团队成员一样参与真实项目？

真实软件开发中，最大的问题往往不是代码不会写，而是：

- 要做什么没说清；
- 为什么这么做没想透；
- 业务语言不统一；
- 任务太大，边界模糊；
- 决策没有记录；
- 做到一半发现方向错了；
- 代码写出来了，但架构变差了；

Matt 的 skills 就是在给 AI 加一套“工程护栏”。

##### 二、为什么 `/grill-me` 很重要？

`/grill-me` 的思想很简单：

> 在动手之前，先让 AI 追问你。

很多人用 AI 写代码时，会直接说：

```text
帮我做一个用户权限系统。
```

然后 AI 就开始写。

但问题是，“用户权限系统”里面有太多隐含问题：

- 有哪些角色？
- 权限是基于角色还是资源？
- 是否支持团队？
- 是否有组织层级？
- 是否需要审计日志？
- 管理员权限是否可配置？
- 默认权限是什么？
- 和现有数据库怎么兼容？
- 前端要不要隐藏无权限按钮？
- 后端是否要强校验？

如果不先问清楚，AI 很可能写出一个看似能跑、实际不符合需求的东西。

所以 `/grill-me` 的价值是：

> 把隐含需求显性化，把模糊想法变成清晰决策。

---

##### 三、那 `/wayfinder` 比 `/grill-me` 多了什么？

`/grill-me` 像一个访谈专家，擅长追问。

但当任务非常大时，光追问还不够。

比如 Matt 说他在规划一整门课程。这样的问题不是问十几个问题就能解决的，它可能涉及：

- 课程目标；
- 受众水平；
- 内容边界；
- 教学顺序；
- 示例项目；
- 练习设计；
- 视频结构；
- 代码仓库组织；
- 先修知识；
- 市场定位；
- 和已有课程的差异；
- 哪些章节需要原型；
- 哪些概念需要研究；
- 哪些部分还没决策。

这类任务有大量未知，不能一次性规划完。

所以 `/wayfinder` 的重点是：

> 管理探索过程，而不是一次性给答案。

它会帮你判断：

| 问题类型 | 应该怎么处理 |
|---|---|
| 用户心里已有答案，只是没说清 | grilling，继续追问 |
| 需要外部事实支持 | research，做研究 |
| 不知道方案是否可行 | prototype，做原型 |
| 已经足够清楚 | 写入地图或进入 spec |
| 已经解决 | 从开放问题中移除 |

这就是“地图会增长，也会收缩”的含义。

##### 四、“中心地图”为什么关键？

`/wayfinder` 最重要的概念是中心地图。

它类似一个动态项目认知图，记录：

- 当前目标；
- 已经明确的事实；
- 未解决的问题；
- 决策边界；
- 风险；
- 需要研究的点；
- 需要原型验证的点；
- 已完成的探索；
- 下一步行动。

这和普通 AI 对话最大的区别是：

普通对话很容易线性流逝：

```text
问了很多，聊了很多，但最后散落在聊天记录里。
```

而 `/wayfinder` 会把这些探索结果收敛到一个共享地图里。

这使得长期复杂任务可以持续推进，而不是每次都从头解释。

##### 七、未来工作流意味着什么？


可以理解成 AI 工程的五阶段流水线。

###### 1. `/wayfinder`：探索问题

用于大规模、不确定、高复杂度的任务。

产出可能是：

- 决策地图；

- 可验证；
- 范围清楚；

###### 4. `/implement`：执行实现

Agent 根据 ticket 编码。

理想情况下会结合：

- `tdd`；
- `prototype`；
- `diagnosing-bugs`；
- `domain-modeling`；
- `codebase-design`。

###### 5. `/code-review`：审查结果

审查不是只看代码风格，而是从两个方向检查：

| 审查维度 | 关注点 |
|---|---|
| Standards | 是否符合仓库标准、是否有代码异味 |
| Spec | 是否忠实实现了原始规格 |

这可以减少“代码能跑但做错了”的问题。

#### 人工智能工程复杂任务导航：核心总结

Matt Pocock 提出了一套面向真实软件工程的 AI 协作方法：用新技能 **`/wayfinder`** 管理超大任务中的未知问题，再通过访谈、研究、原型、测试和代码评审逐步推进。核心不是让 AI 一次性“包办开发”，而是建立可控、可验证、能持续积累上下文的工程流程。

##### 1. `/wayfinder`：为大型任务绘制动态地图

`/wayfinder` 是 `/grill-me` 的进一步演化，主要用于规划远超单次对话承载能力的复杂工作。

- 它会识别当前的**决策边界**与“战争迷雾”，找出尚未解决的问题。
- 根据问题类型，建议采取不同方式：
  - **Grilling（追问访谈）**：澄清目标、需求和取舍。
  - **Prototyping（原型验证）**：用可运行的实验回答设计问题。
  - **Research（研究）**：查阅高可信的一手资料并形成带引用的结论。
- 所有会话都会回写到一个**中央地图**：
  - 随着对问题了解加深，地图会扩展；
  - 随着问题获得答案，待解决范围又会收缩。
- 该地图可放在用户选择的任务系统中，如 **GitHub、Linear 或本地文件**。

Matt 用它连续 **4 天**规划一门完整课程，开展了接近 **100 次**独立的访谈、原型和研究会话。他认为它将成为比 `/grill-with-docs` 更上层、更有组织、也更不容易出错的编排器；但原文发布时仍处于 **in-progress** 阶段。

Matt 的技能库定位为“真实工程师使用的技能”，反对只凭感觉让 AI 大规模生成代码。

- 一些完整流程框架会试图接管开发过程，一旦中间出现错误，用户很难定位和修复。
- 他的方案强调技能应当：
  - **小而专注**；
  - **容易修改**；
  - **可以组合**；
  - **不绑定特定模型**。
- AI 提高编码速度的同时，也会更快地制造复杂度和技术债，因此传统软件工程原则反而更加重要。

##### 3. 解决需求错位：先让 AI 充分追问

软件开发中最常见的问题是**双方以为已经达成一致，实际理解却不同**。在人与 AI 合作时，这种沟通鸿沟同样存在。

对应技能包括：

- **`/grill-me`**：让 AI 对计划或设计持续提问，直到关键决策分支都得到处理。
- **`/grill-with-docs`**：除追问外，还会建立领域模型、维护项目术语，并把重要决策写入 ADR。
- **`grilling`**：可被其他技能自动调用的底层访谈能力。

重点是：在 AI 开始编码前，先通过高强度提问澄清“要做什么、为什么做、有哪些边界和取舍”。

##### 4. 建立共享领域语言，减少长期沟通成本

项目初期，开发者、业务专家和 AI 往往使用不同词汇。AI 如果没有统一术语，可能需要用很多句子解释一个本可准确命名的概念。

解决方法是维护共享的领域文档，例如：

- `CONTEXT.md`：记录领域模型和术语；
- ADR：记录难以解释的重要架构决策。

原文给出的对比是：

- 修改前：  
  “当课程某章节中的一节课被变成‘真实内容’，即在文件系统中获得位置时，会出现问题。”

- `/tdd`：按垂直切片实现功能或修复缺陷，并规范测试质量。
- `/diagnosing-bugs`：按照“复现 → 最小化 → 提出假设 → 添加观测 → 修复 → 回归测试”的顺序诊断复杂问题和性能退化。

##### 6. AI 提高速度，也会加速代码熵增

AI 能快速生成大量代码，但也可能以前所未有的速度增加系统复杂度，使代码库逐渐变成难以维护的“大泥球”。

解决方向是持续关注软件设计：

- `/to-prd` 会在生成需求文档前确认涉及哪些模块；
- `/improve-codebase-architecture` 会扫描代码库，寻找可以形成“深模块”的位置，并生成可视化 HTML 报告；
- 作者建议每隔几天运行一次架构改进流程；
- `/codebase-design` 强调把大量行为封装在简单接口之后，并把模块放在清晰、可测试的边界上；
- `/code-review` 从两个维度并行审查：
  - **标准维度**：是否符合仓库规范及常见代码质量原则；
  - **规格维度**：是否忠实实现了原始需求或工单。

##### 7. 技能分为“用户调用”和“模型调用”

技能库按照“谁可以触发”分为两类：

###### 用户调用型

只能由用户主动输入，主要负责组织工作流，例如：

- `/grill-me`：深入澄清计划；
- `/grill-with-docs`：澄清需求并维护领域文档；
- `/to-prd`：把已有讨论整理成需求文档；
- `/to-issues`：将计划拆成可独立领取的垂直工单；
- `/triage`：推动工单经过不同分诊状态；
- `/handoff`：为下一个代理整理交接信息；
- `/teach`：通过多个会话持续教学。

###### 模型调用型

既可由用户触发，也可由代理在适合时自动使用，例如：

- `prototype`：制作可丢弃原型来验证设计问题；
- `research`：基于高可信一手资料开展研究，并生成带引用的 Markdown 文件；
- `tdd`：执行测试驱动开发；
- `diagnosing-bugs`：进行系统化调试；
- `domain-modeling`：完善领域模型和术语表；
- `codebase-design`：设计接口简单、功能丰富的深模块；
- `code-review`：并行检查规范符合度与需求实现度。

规则是：**用户调用型技能可以编排模型调用型技能，但不会再调用另一个用户调用型技能。**

##### 8. 使用后台代理完成会话交接

Matt 还提出通过 Claude Code 的后台代理切换任务：

```bash
claude --bg --name "Session Name" "Prompt goes here"
```

该命令会在当前工作目录中启动一个命名后台代理并立即返回，适合让新代理直接接手后续工作。

`claude-handoff` 技能会：

- 总结当前会话；
- 根据下一阶段目标调整交接内容；
- 推荐新代理应使用的技能；
- 引用已有 PRD、ADR、工单、提交或差异文件，而不重复复制；
- 删除 API 密钥、密码及个人身份信息；
- 使用描述性名称启动后台代理。

这使复杂任务可以跨会话、跨代理延续，同时减少上下文丢失和重复沟通。

##### 9. 最终工作流：从探索到实现与审查

Matt 正在调整技能命名：

- `/to-prd` 将改为 `/to-spec`；
- `/to-issues` 将改为 `/to-tickets`。

计划中的完整流程是：

```text
/wayfinder
→ /to-spec
→ /to-tickets
→ /implement
→ /code-review
```

各阶段分别负责：

1. `/wayfinder`：探索问题，消除不确定性；
2. `/to-spec`：把已确认的认识整理成规格；
3. `/to-tickets`：拆分成可独立执行的工单；
4. `/implement`：按工单实现；
5. `/code-review`：检查工程规范与规格一致性。

##### 总结

这套方法并不追求让 AI 一次性完成整个项目，而是把复杂工程拆成可探索、可验证、可追踪的小步骤。其关键价值在于：用 `/wayfinder` 管理不确定性，以共享语言保证理解一致，通过测试和调试形成反馈闭环，再借助持续架构治理控制 AI 高速编码带来的复杂度。

#### Wayfinder：用“动态决策地图”组织 AI 完成超大复杂任务

##### 地图随认知扩张，也随问题解决而收缩

Wayfinder 会识别当前的“决策前沿”和信息盲区，再根据问题类型建议下一步行动：

- 需求或取舍不清：通过追问澄清；
- 缺少外部事实：启动资料研究；
- 设计可行性未知：制作一次性原型验证。

新发现会让地图扩展，已解决的问题则从地图中收敛。Pocock 用它连续四天规划一门课程，组织了近 100 次独立的讨论、原型和研究会话；中心地图可放在 GitHub、Linear 或本地文件等任务系统中。

它被定位为 `/grill-me` 的下一代形态，并可能取代 `/grill-with-docs` 的上层编排角色。规划中的工作流是：

`/wayfinder → /to-spec → /to-tickets → /implement → /code-review`

##### 核心价值是可控编排，而非更强的“一键生成”
