## 分析要点

- **核心高价值点**：将长任务Agent的稳定性问题抽象为状态、规划、验证三大控制面，并进一步落到五层工程架构和最小闭环实践。
- **留存建议**：长期保留（文章系统总结了长任务Agent工程化中的状态、规划、执行、验证、监督五层架构，并提供了可直接复用的闭环实践清单，适合作为Agent系统设计参考。）

**知识要点**

- 长任务Agent容易在上下文污染、任务边界漂移、浅层验证中逐步失控。
- 生产级Agent不应只依赖上下文记忆，应将长期状态外置到progress.md、ledger、trace或数据库中。
- 规划层需要同时包含任务切分和运行预算，否则Agent容易无限探索或草率收工。
- 验证层应优先依赖机器验证、环境验证和独立评价，而不是生成Agent的自我声明。
- 五层Agent架构包括状态层、规划层、执行层、验证层和监督层。
- 更强模型会改变harness的厚度，但不会完全取消外部状态、外部验证、权限控制和成本控制。

**行动项**

- 在长任务Agent工作流中引入Spec-first机制，先明确目标、非目标、约束、验收和风险。
- 为Agent任务设计Plan gate，在自动执行前审查阶段拆分、交付物、验证方式和停止条件。
- 建立Progress ledger，让Agent在每个阶段记录目标、完成项、变更文件、决策、验证结果和下一步。
- 将生成者与评价者分离，引入独立Evaluator并赋予其判定FAIL的权限。
- 对Web类Agent任务加入浏览器级验证，如Playwright操作、截图、控制台错误检查和关键路径验证。
- 为高影响操作设置停止条件、人工确认和回滚路径，并记录完整trace以便审计。

## 正文

**烟花老师**

### 我最近两个月的探索和实践分享：长任务 Agent 的最小工程闭环

> 一张 Claude 工程师分享的图，把长任务 Agent 最常见的三个问题说得很准：带不住状态，估不准工作量，评不好自己的输出。

![Image](https://pbs.twimg.com/media/HJAr2B4a4AApbp5?format=jpg&name=large)

很多人第一次认真用 Agent，都会经历一个相似的过程。

> 前十分钟很惊艳。它能读代码、改文件、跑命令，还能自己解释下一步要做什么。

> 半小时后开始不放心。它还在执行，但你已经不确定它有没有记住最初的目标。

> 两小时后，问题变得更明显：它做了很多事，改了很多文件，跑了很多验证，最后交上来的结果却经不起细看。

Claude 工程师那张图把这个问题拆得很准：Agent 会丢状态，会误判工作量，也会高估自己的输出质量。

这三个问题放在一起，就会形成长任务里最常见的失控链路：上下文越来越脏，计划越来越虚，验证越来越浅。最后 Agent 没有突然变笨，只是在一个缺少控制回路的系统里越跑越偏。

所以这篇文章不聊怎么写一个更“聪明”的 prompt。

我们聊一个更工程的问题：如果要让 Agent 稳定处理长任务，系统里至少要补上哪些控制层？

![Image](https://pbs.twimg.com/media/HJArS3ubgAEeeeg?format=jpg&name=large)

这三层可以当成全文的索引。

Context 管现场，Planning 管边界，Verification 管证据。

任何一层松掉，另外两层都会被拖下水。

#### 状态丢失：Agent 的工作台会越堆越乱

很多 Agent 长任务出问题，最早冒出来的信号通常还不在代码，而在状态。

它一开始知道目标是什么，也知道刚刚读过哪些文件。

随着对话变长、工具调用变多、错误信息堆进来、临时判断反复覆盖，context 里的噪声开始变多。到了后半程，它还在继续工作，但已经不像在沿着原来的任务前进，更像是在当前上下文里找一个看起来合理的出口。

这就是 context window 的真实边界。

上下文窗口经常被理解成“模型能记住多少东西”。

这个理解太乐观了。

对 Agent 来说，context 更像一张工作台。任务说明、文件片段、命令输出、错误日志、用户补充、模型自己的中间判断，全都堆在这张桌子上。

桌子变大当然有用，但桌子再大，也不等于它能自动整理材料。

Anthropic 在 Claude Code 最佳实践里讲得很直接：

> context window 会很快被填满，窗口越满，模型越容易忘记早期指令或犯错。它还建议给 Claude 明确的验证方式，比如测试、截图和期望输出，因为这是提升结果质量的高杠杆动作。

这个经验在长任务 Agent 里非常明显。很多跑偏发生在第 40 步、第 80 步，发生在 Agent 已经积累了足够多“看起来相关、实际干扰”的上下文之后。

更麻烦的是 session 之间的状态断裂。一次任务没做完，换一个 session 继续。

Agent 看起来能接上，但它接上的往往只是压缩摘要，只剩压缩后的现场。哪些决定已经确认过，哪些方案被否掉，哪些文件刚改过但还没验证，哪些失败路径不要再试，这些信息如果没有被写进外部状态，很容易在下一轮里丢掉。

所以生产级 Agent 不能把状态全押在 context 里。

最小可用的状态层至少要有几类东西：

![Image](https://pbs.twimg.com/media/HJAqgQibgAAIbp8?format=jpg&name=large)

这些东西如果只留在对话里，Agent 一旦上下文变脏，就会开始凭印象工作。写进 progress.md、任务 ledger、trace log、issue comment 或数据库，才有机会在下一轮被稳定读回。

这也是很多 harness 设计的第一层价值：

让模型不用靠临场记忆硬撑。

一个好的 Agent 系统，会主动把“工作状态”和“推理上下文”分开。context 里只放当前步骤需要的材料，长期状态放到外部。每次进入新阶段，Agent 先读状态，再继续执行；每次完成一个阶段，Agent 先写状态，再清理上下文。

这听起来像传统工程里的 checkpoint。放到 Agent 里，它更像防止任务漂移的锚点。

没有这个锚点，长任务很容易变成一场上下文赌博：前面写得越多，后面越难判断它到底还记得什么。

#### 规划失真：Agent 经常不会判断这件事到底有多大

状态问题解决了一半，长任务还是会翻车。

另一类更隐蔽的失败来自任务尺寸感。

人类工程师接到一个需求，会下意识判断几件事：

这是不是一个小改动？

会不会牵动数据结构？

有没有迁移？有没有兼容问题？验收标准是什么？

这件事适合一次做完，还是要拆成几个阶段？

Agent 经常没有这个尺度。

你让它“改一下文档生成流程”，它可能把整个内容系统都扫一遍。你让它“做一个可用 demo”，它可能只搭一个 UI 空壳。

你让它“修一个 bug”，它可能顺手重构半个模块。看起来都在努力，方向也都说得过去，但任务边界开始松动。

这类问题在长任务里会被放大。

一开始，Agent 倾向于把完整项目 one-shot 掉。

它会列一个很大的计划，把架构、代码、测试、文档、部署都写进去，然后从第一步开始做。

前几步看起来很顺，等 context 用掉一大半，真正难的部分还没碰。

后半程它开始收缩范围，跳过细节，最后用“核心功能已完成”这种话收尾。

另一种情况刚好相反。

它看到局部进展，就把局部完成当成整体完成。

页面能打开了，就说产品可用了；

接口返回 200 了，就说功能通过了；

单元测试过了，就说端到端没问题。很多 Agent 失败卡在一个更早的位置：太快判断“够了”。

这就是任务尺寸感的问题。

规划层要解决的事情很具体：

让 Agent 形成几个硬约束。

- 这次任务的交付物是什么？
- 哪些内容明确不做？
- 每个阶段的完成标准是什么？
- 当前阶段最多允许消耗多少上下文、多少工具调用、多少时间？
- 如果做到一半发现范围变大，什么时候停下来重新估算？
- 如果验证过不了，是否允许继续扩展实现，还是必须先修当前问题？

没有这些约束，计划就只是一个开场白。

Agent 会在执行过程中不断重新解释计划，最后交付一个和最初目标越来越远的东西。

我现在更倾向于把 Agent 规划分成两层。

第一层是任务切分。它回答“这件事应该怎么拆”。这里需要把大任务拆成可以独立验证的小阶段，每一段都有清楚的输入、输出和验收方式。

第二层是运行预算。它回答“这一段最多跑到什么程度”。

包括 max turns、token budget、tool call budget、时间上限、失败重试次数，以及触发人工确认的条件。

这两层缺一层，Agent 都容易失控。

只有任务切分，没有运行预算，Agent 可能在一个子任务里无限探索。只有运行预算，没有任务切分，Agent 会在快到限制时随便找一个能交差的版本收工。

Anthropic 在长任务 harness 的思路里，已经能看到这个方向：

先由 initializer agent 搭环境、列 feature、写进 progress file；  
首先由 initializer agent 搭建环境、列出特性、写入 progress file；

后续 coding agent 每个 session 只处理一个 feature，完成后再把状态写回。Anthropic 把这个问题描述成跨多个 context window 做持续进展的挑战，每个新 session 都需要接上前一个 session 留下的现场。

![Image](https://pbs.twimg.com/media/HJAr8IvbEAEE8Yq?format=jpg&name=large)

工程上真正有用的计划，通常不像“我要完成 A、B、C”这么简单。

它更接近一张施工单：

- 当前阶段只做什么。
- 做完以后用什么验证。
- 验证失败如何回滚或重试。
- 哪些情况必须停下来问人。
- 下一阶段要读哪份状态继续。

Agent 更需要边界，不需要鼓励式放权。

边界越清楚，它越像一个可调度的执行单元。边界越模糊，它越像一个勤奋但不可靠的自由发挥系统。

#### 验证失灵：Agent 最危险的能力，是把没做对的事讲得像做完了

状态会丢，计划会漂，但这两件事通常还能被人看出来。

验证失灵更麻烦。

Agent 很擅长给自己的工作一个体面的收尾。

它会说“已完成实现”“已通过基本验证”“核心流程正常”。

如果你继续追问，它还能解释验证步骤，列出改动文件，补一段风险说明。

问题在于，这些话有时候只是在替一个很浅的验证包装结论。

最常见的情况是 curl-only verification。

接口能返回 200，Agent 就说功能可用。它没有点过页面，没有走过真实用户路径，没有看浏览器控制台，没有检查数据是否真的写入，也没有确认错误状态怎么展示。

做 Web 应用时，这个问题尤其明显。

一个按钮存在，不代表按钮能用。

页面能打开，不代表主流程跑通。测试通过，不代表用户不会卡在 loading 状态。Agent 如果只在命令行里验证，很容易把“系统有响应”误判成“产品可使用”。

第二种情况是 stub 逃逸。

Agent 做到复杂功能时，会先写一个简化版本。

这个动作本身没问题。工程里经常先用 mock、stub、placeholder 搭流程。问题出在它后面忘了回来，或者把这个临时实现包装成阶段成果。

比如：

- 支付流程只打印日志，没有真实状态机。
- 权限判断写了 TODO，但页面已经放开入口。
- RAG 只返回固定示例，却说“检索链路已打通”。
- 图表数据写死，却说 dashboard 已完成。
- E2E 测试只测 happy path，没有失败路径。

第三种情况是自我评分过高。

Agent 评自己的输出时，经常会发现问题，但把问题降级。它会说“目前实现满足核心需求，后续可优化”。这句话在人工 review 里很常见，但放到 Agent 里要小心。很多关键缺陷就是被这句话放过去的。

真正的问题在于，Agent 没有足够独立的评价位置。

写代码的那个 Agent，天然希望任务收敛。它已经投入了上下文、工具调用和多轮推理，也在接近限制。

到了后半程，它会倾向于把不确定问题解释成可接受风险，把未完成部分解释成后续优化，把浅验证解释成基本通过。

这和人类工程师也很像。自己写的代码，自己 review，严格程度通常不够。区别在于，人类工程师知道团队里还有 CI、QA、代码评审、线上监控。

Agent 如果没有这些外部机制，就会自己宣布自己合格。

所以验证层不能只依赖 Agent 的口头报告。

一个能跑长任务的 Agent 系统，至少需要三类验证：

第一类是机器验证。

能用工具判断的，就不要交给模型判断。测试、类型检查、lint、build、schema validation、数据对账、截图 diff、可访问性检查、日志扫描，都属于这一类。

第二类是环境验证。

Agent 要在真实或接近真实的环境里走一遍。Web 应用要用浏览器点，不只用 curl。数据任务要读回结果，不只看写入命令成功。文档发布要 fetch 回来检查，不只看 API 返回 OK。

第三类是独立评价。

生成者和评价者要分开。

Planner 拆任务，Generator 执行，Evaluator 按 rubric 检查。Evaluator 不负责安慰 Generator，也不负责帮它解释。它只回答几个硬问题：

- 需求是否真的满足？
- 关键路径是否真的跑通？
- 有没有 stub 或 TODO 被包装成交付？
- 失败路径有没有处理？
- 验证证据够不够？
- 如果不够，下一轮该修什么？

这也是 Anthropic 在 long-running application development harness 里强调的方向：  
这也是 Anthropic 在长期运行的应用程序开发框架里强调的方向：

让独立 evaluator 用 Playwright 像真实用户一样操作应用，测试 UI 功能、API endpoint 和数据库状态，避免让生成代码的 Agent 自己说“我觉得可以”

![Image](https://pbs.twimg.com/media/HJAskavbMAAc1KM?format=jpg&name=large)

这个设计很重要。

它把“完成”从一句话变成一个证据链。代码改了只是第一步，测试通过只是第二步，真实路径跑通、证据可回放、评价器同意，才更接近可以交付。

很多 Agent 产品现在缺的就是这条证据链。

它们能执行，能解释，能生成日报，能把日志写得很漂亮。

可一旦你追问“你怎么知道这件事真的做对了”，回答就开始变虚。

生产级 Agent 最该警惕的，是系统误判成功。

失败可以重试，可以回滚，可以升级给人。

真正贵的是：它失败了，系统却以为它成功了。

#### 工程化 Agent 的五层架构

把前面三个问题放到一起看，会发现 Agent 失控往往不属于单点故障。

状态层没有沉淀，规划层就只能靠当前上下文猜任务进度。规划层没有边界，执行层就会不断扩展范围。验证层不够硬，Agent 就会把局部成功包装成整体完成。监督层缺位时，所有风险都会一路流到最后，由用户自己兜底。

所以生产级 Agent 不能只看模型调用链。

一个更稳的结构，至少要有五层。

![Image](https://pbs.twimg.com/media/HJAst_LagAA5cxs?format=jpg&name=large)

1 状态层：让任务有可恢复的现场

状态层负责保存 Agent 不能丢的东西。

包括任务目标、当前进度、阶段产物、决策记录、文件变更、验证结果、阻塞点、人工确认记录。它可以是 progress.md，可以是数据库，也可以是 trace store、issue comment、artifact ledger。

形式不重要，关键是可读回、可续跑、可审计。

没有状态层，Agent 的长任务会变成一次性对话。对话断了，现场也断了。上下文压缩之后，很多细节只剩一个模糊摘要。下一轮 Agent 看起来在继续，实际已经丢了一部分工程现场。

2 规划层：把大任务压成可调度的小任务

规划层负责把用户目标拆成阶段、依赖、预算和停止条件。

这里的计划不能停留在一张好看的 checklist。它更像调度系统里的 job spec：当前阶段做什么，输入是什么，输出是什么，用什么验证，最多允许跑多久，失败几次后停止，哪些操作需要人工确认。

好的规划层会限制 Agent 的自由度。

它让 Agent 每次只处理一个足够小、足够可验证的任务。这样做会牺牲一点“自动到底”的幻觉，但换来更高的恢复能力。某个阶段失败了，可以重跑这个阶段，整条长任务不用一起糊掉。

3 执行层：工具调用只是其中一部分

执行层负责把计划变成真实操作。

读文件、改代码、跑测试、开浏览器、查日志、调 API、写文档、生成图片，都在这一层。很多 Agent 系统把执行层做得很热闹，工具很多、权限很大、动作很快，但前后的状态和验证跟不上，最后反而更危险。

执行层的关键不在工具数量，关键在每次工具调用都能回到任务状态里。

一个命令跑完，输出要进入状态。一个文件改完，变更要进入状态。一个 API 调用成功，读回结果也要进入状态。工具调用如果只在上下文里闪一下，很快就会被后续噪声淹没。

4 验证层：把完成变成证据链

验证层负责回答一个问题：怎么知道这件事真的做对了？

这一层要尽量使用外部证据。测试结果、浏览器截图、数据库 readback、日志、trace、diff、rubric 评分、人工 review，都比 Agent 自己说“已完成”更可靠。

验证层最好和执行层分开。

同一个 Agent 做完再自评，容易把风险解释成可接受。独立 evaluator 会严格得多。它不需要理解 Generator 的全部心理活动，只需要按验收标准检查产物。

这一层越硬，用户越不用自己当最后一道 QA。

5 监督层：控制权限、成本和升级路径

监督层负责 Agent 什么时候能继续，什么时候必须停。

这里包括权限控制、预算控制、loop budget、max turns、危险操作确认、发布前确认、失败升级、人类接管、回滚策略。很多 Agent 工作流表面上追求自动化，实际缺的恰好是这层刹车。

一个成熟的监督层不会频繁打断正常任务，也不会让 Agent 无限自由发挥。它只在几个关键点介入：

- 任务范围扩大。
- 预算接近上限。
- 验证连续失败。
- 操作涉及删除、发布、权限、付费、生产数据。
- Agent 发现自己无法判断。
- 结果影响真实用户。

监督层的价值在于，它把“要不要继续”从模型的临场判断里拿出来，变成系统规则。

这五层合起来，Agent 才从一个会调用工具的模型，变成一个可恢复、可验证、可停止的执行系统。

模型仍然重要。

它决定单步推理质量、代码质量、工具选择能力和异常处理能力。

可一旦任务变长，决定稳定性的往往是模型外面的这些层：

状态有没有沉淀，计划有没有边界，执行有没有记录，验证有没有证据，监督有没有硬停止条件。

#### 更强的模型会改变 harness，但不会取消 harness

模型变强以后，很多外层设计确实会变。

以前必须拆成 5 个 sprint 的任务，可能新模型自己就能保持连贯。

以前需要写很细的中间计划，新模型可以在更少提示下做出合理判断。以前必须用专门的子 Agent 查资料，新模型也许能在一次更长的上下文里完成。

这很正常。

每一个 harness 组件背后，都藏着一个判断：

> 当前模型在这件事上还不够稳定，所以系统要补一层。模型能力提高，这个判断就应该被重新测试。继续保留过时的 harness，会让系统变慢、变重，也会制造新的失败点。

Anthropic 在 long-running harness 的讨论里也提到，harness 组件编码了关于模型能力边界的假设，模型换代后这些假设需要重新压力测试。

这个观点很重要。

它提醒我们，harness 不能当宗教。

层数越多未必越专业，角色越多未必越先进。

好的 Agent 架构应该随着模型能力变化而变薄，把不再需要的外壳拆掉，把真正有价值的控制点留下来。

但有几类东西很难被模型能力完全吃掉。

第一类是外部状态。

模型可以读更长的上下文，但真实任务里的状态不只存在于上下文里。文件系统变了，数据库变了，API 状态变了，浏览器页面变了，用户在别处改了需求，权限和成本也在变化。Agent 要持续工作，就需要一个能和外部世界对齐的状态层。

第二类是外部验证。

模型可以更会反思，也可以更会写测试。但“有没有真的点过页面”“数据库里是不是写进去了”“发布后的文档能不能打开”“用户路径有没有卡住”，这些问题需要环境反馈。只靠模型想一遍，永远差一层证据。

第三类是权限和责任。

删除文件、发布内容、修改权限、触碰生产数据、花钱调用外部服务，这些动作不能因为模型更聪明就全交出去。这里需要明确的规则、审计日志和人工确认。模型负责判断，系统负责授权。

第四类是成本。

长任务 Agent 很容易把 token、工具调用、浏览器会话、外部 API 调用变成隐性成本。模型越强，单次调用越贵，越需要 budget routing、max turns、timeout 和 circuit breaker。否则系统看起来很自动，账单也会很自动。

所以更强模型带来的变化，是让架构重新分工。架构不会因此消失。

模型负责越来越多的语义判断、代码生成、异常处理和局部规划。harness 负责把这些能力放进可观测、可恢复、可验证、可停止的流程里。

真正该避免的是两种极端。

一种是迷信模型。

模型一升级，就把状态、验证、权限、预算都交给它临场判断。短 demo 很漂亮，长任务容易埋雷。

另一种是迷信 harness。

模型已经能稳定做的事，还强行拆成复杂流程，最后系统慢、贵、难维护，错误还藏在编排层。

更好的做法是定期问一个问题：

> 这层 harness 现在还在解决真实问题吗？

如果答案是肯定的，就保留，并把它做得更可观测。

如果答案是否定的，就删掉，让模型直接做。

Agent 架构师的工作，不该把模型包得越来越厚。

更准确地说，是持续识别模型当前的能力边界，然后只在边界外补必要的工程控制。

#### 长任务 Agent 的最小工程闭环

讲架构很容易讲虚。

真正有用的 Agent 设计，最后要落到一些很具体的动作上：

任务怎么进来，状态写在哪里，谁来验证，什么时候停，失败后怎么恢复。

下面这几种模式，我会优先放进任何一个长任务 Agent 系统里。

![Image](https://pbs.twimg.com/media/HJAtRoRaoAAVgjD?format=jpg&name=large)

Spec-first：先写施工单，再让 Agent 动手

不要直接让 Agent “帮我做完这个功能”。

先让它生成一份短 spec，里面只写几件事：

- 目标：这次要交付什么。
- 非目标：哪些明确不做。
- 约束：技术栈、风格、权限、预算、时间。
- 验收：怎么判断完成。
- 风险：哪些地方可能扩大范围。

这份 spec 不需要长。半页就够。

![Image](https://pbs.twimg.com/media/HJAv9ntbMAARDil?format=jpg&name=large)

关键是让任务在执行前先固化一次。

后面 Agent 想扩大范围、绕开验证、提前收工，都可以拿 spec 对照。

Plan gate：计划先过关，再进入自动执行

![Image](https://pbs.twimg.com/media/HJAvq7OaEAAsNVK?format=jpg&name=large)

让 Agent 先出计划，不要马上执行。

计划里必须包含：

- 阶段拆分。
- 每阶段交付物。
- 每阶段验证方式。
- 预计会碰到的文件或系统。
- 停止条件。
- 需要人工确认的操作。

这一步最适合人参与。

你不需要 review 每一行代码，但应该 review 任务拆法。拆错了，后面跑得越快，偏得越远。

很多 Agent 失控，错误从第一张计划就开始了：边界在那时已经放丢。

Progress ledger：每个阶段都写状态

![Image](https://pbs.twimg.com/media/HJAu60zaYAALMI3?format=jpg&name=large)

长任务不要只靠对话续命。

每完成一个阶段，Agent 要写一份 progress ledger。

可以是 Markdown，可以是 JSON，也可以是 issue comment。格式简单就行：

```text
## Current Goal
...

## Completed
- ...

## Changed Files
- ...

## Decisions
- ...

## Verification
- ...

## Open Risks
- ...

## Next Step
...
```

这份文件的价值在于续跑。

下一轮 Agent 先读 ledger，再读代码。

人也可以扫一眼 ledger，快速知道它到底做到哪里。上下文满了、session 断了、模型换了，都能接回来。

Independent evaluator：让另一个角色验收

生成者不要当最终裁判。

可以用另一个 Agent，也可以用脚本、测试、CI、Playwright、人工 review。关键是评价标准要独立于执行过程。

Evaluator 的输出不要写成“整体不错，有一些建议”。这种话没用。

更好的格式是：

```text
Result: PASS / FAIL

Evidence:
- ...

Blocking Issues:
- ...

Non-blocking Issues:
- ...

Required Fixes:
- ...
```

Evaluator 必须有权判 FAIL。

![Image](https://pbs.twimg.com/media/HJAukx8aIAAa94W?format=jpg&name=large)

没有失败权的 evaluator，只是总结员。

Browser-level verification：Web 产品必须点过  
浏览器级验证：Web 产品必须点击过

Web 任务里，curl 和单元测试都不够。

至少要让 Agent 用浏览器走一遍关键路径：

- 页面是否能打开。
- 控件是否能点击。
- 表单是否能提交。
- 数据是否能显示。
- 错误状态是否正常。
- 控制台有没有报错。
- 移动端有没有明显布局问题。

如果是视觉相关任务，还要截图。截图是很便宜的证据。它能帮你发现很多“命令行看不见”的问题。

Stop condition：让 Agent 知道什么时候该停

![Image](https://pbs.twimg.com/media/HJAuURSbMAA8nct?format=jpg&name=large)

Agent 需要明确的停止条件。

常见停止点包括：

- 连续两次验证失败。
- 任务范围明显扩大。
- 需要删除、发布、改权限、花钱、触碰生产数据。
- 当前阶段超过预算。
- 遇到多个可行方案但无法判断取舍。
- 关键依赖不可用。
- 用户给的目标互相冲突。

停下来很正常。失去边界继续跑，风险更大。

一个好的 Agent 工作流，应该允许它说：“我现在需要人判断。”

Rollback path：每个阶段都要能退回

Agent 自动化越强，越需要回滚路径。

代码任务至少要有 git diff。数据任务要有 dry-run、备份、row count。发布任务要有草稿、预览、读回验证。配置任务要记录旧值。

没有回滚路径，就不要让 Agent 自动执行高影响操作。

Trace everything：把过程留下来

![Image](https://pbs.twimg.com/media/HJAuIlWaQAA5ITR?format=jpg&name=large)

长任务 Agent 最怕黑箱。

至少要留下这些东西：

- 输入任务。
- 使用的模型和工具。
- 关键工具调用。
- 文件变更。
- 验证结果。
- 人工确认。
- 失败重试。
- 最终产物。

OpenAI Agents SDK 的 tracing 文档也采用了类似思路：

> 记录 agent run 中的 LLM generation、tool call、handoff、guardrail 和自定义事件，用于开发和生产环境里的调试、可视化和监控。

trace 的目的不在漂亮 dashboard，而在出问题时能回答：它为什么这么做？哪里开始偏？哪一步验证放过了问题？

Agent 的可控性，很大一部分来自可追踪性。

#### 最后：Agent 的上限看模型，下限看架构

Agent 的能力上限当然来自模型。

更强的模型会写出更好的代码，会更会拆问题，会更会调用工具，也会更少犯低级错误。这个趋势不用怀疑。

可长任务进生产，不能只看上限。

它还要看下限：

状态乱了能不能恢复，计划漂了能不能拉回，验证失败能不能发现，权限风险能不能挡住，成本异常能不能停止。

ReAct 论文早就把一个方向讲清楚：

> Agent 需要在 reasoning 和 acting 之间交替，通过外部环境拿 observation，再更新计划。Reflexion 进一步强调 feedback signal 对 agent 改进的重要性，它把反馈转成语言记忆，让后续尝试能从失败里学习。

![Image](https://pbs.twimg.com/media/HJAt2x0b0AAdw4W?format=jpg&name=large)

这些研究和今天的工程实践，其实指向同一件事：

Agent 的质量不只来自生成，还来自行动后的反馈。

缺状态，反馈留不住。

缺规划，反馈不知道该回到哪个阶段。

缺验证，反馈本身就是假的。

Context、Planning、Verification 已经不属于三个小技巧，它们已经是 Agent 系统最基本的控制面。

未来更强的 Agent，不会只是更像一个“自动干活的人”。

它会更像一个可审计的工程系统：

知道自己在做什么，知道做到哪里，知道怎么证明做对了，也知道什么时候该停下来找人。

我现在判断一个 Agent 工作流，会先跳过模型名。

我会先问这五个问题：

- 状态在哪里？
- 计划怎么拆？
- 执行怎么记录？
- 结果怎么验证？
- 什么时候必须停？

这五个问题回答不清，模型越强，跑偏时造成的动静越大。

回答清楚了，Agent 才真正开始从 demo 进入工程。

#### 长任务 Agent 的最小工程闭环

##### 一、内容总结

文章核心讲：**长任务 Agent 不能只靠更聪明的模型，必须靠工程控制闭环。**

长任务 Agent 最常见的 3 个问题：

1. **状态丢失**
   - 对话越长，上下文越乱。
   - Agent 会忘记最初目标、已做决策、失败路径和当前进度。

2. **规划失真**
   - Agent 不擅长判断任务大小。
   - 容易把小任务做大，或把局部完成当整体完成。

3. **验证失灵**
   - Agent 很会“说自己完成了”。
   - 但可能只是跑了浅层测试，比如接口返回 200，就声称功能可用。

因此，长任务 Agent 至少需要五层工程结构：

| 层级 | 作用 |
|---|---|
| 状态层 | 记录目标、进度、决策、变更、风险 |
| 规划层 | 拆任务、定边界、设预算 |
| 执行层 | 调工具、改代码、跑命令 |
| 验证层 | 用证据证明真的完成 |
| 监督层 | 控权限、控成本、必要时让人接管 |

一句话总结：

> Agent 的上限看模型，下限看架构。

---

##### 二、深入浅出解读

可以把长任务 Agent 想成一个“会干活的实习生”。

刚开始很惊艳：

> 你说一句，它能读代码、改文件、跑测试。

但时间一长，问题来了：

- 它可能忘了最初要做什么；
- 它可能越做越大，偏离目标；
- 它可能没真正测完，却告诉你“已经完成”。

所以问题不只是“模型聪不聪明”，而是：

> 有没有一套机制，让它不跑偏、不乱花钱、不瞎宣布成功。

###### 1. 状态层：别让 Agent 靠记忆硬撑

不能只靠聊天记录。

应该把关键内容写下来，比如：

```md
当前目标：
已完成：
改了哪些文件：
做过哪些验证：
还有哪些风险：
下一步：
```

这样即使上下文满了、会话断了，也能继续接上。

---

###### 2. 规划层：先写施工单，再动手

不要直接说：

> 帮我把这个功能做完。

更好的方式是先让 Agent 写：

- 要做什么；
- 不做什么；
- 分几步做；
- 每步怎么验收；
- 什么情况必须停下来问人。

计划不是摆设，而是边界。

---

###### 3. 验证层：不要相信“我完成了”

Agent 说完成，不等于真的完成。

尤其是 Web 产品，不能只看：

```bash
curl 返回 200
```

还要真的用浏览器点一遍：

- 页面能不能打开；
- 按钮能不能点；
- 表单能不能提交；
- 数据有没有写入；
- 控制台有没有报错；
- 截图是否正常。

完成不是一句话，而是一条证据链。

---

###### 4. 独立评价：写代码的别自己当裁判

生成者天然倾向于说：

> 核心功能已完成，剩下是优化。

所以最好有独立 Evaluator：

```md
Result: PASS / FAIL

Evidence:
- ...

Blocking Issues:
- ...

Required Fixes:
- ...
```

关键是：**Evaluator 必须有权判失败。**

---

###### 5. 监督层：自动化也要有刹车

Agent 必须知道什么时候停。

比如：

- 连续验证失败；
- 超过预算；
- 要删除文件；
- 要发布上线；
- 要动生产数据；
- 要花钱；
- 任务范围变大；
- 多个方案无法判断。

好的 Agent 不是一路自动到底，而是该停时能停。

---

##### 三、我的意见

我认同文章的核心判断：

> 真正能进生产的 Agent，不是“更会聊天”，而是“可恢复、可验证、可停止”。

现在很多 Agent Demo 看起来很强，是因为任务短、风险低、没人深究验证。

但一旦进入真实工程，最重要的不是它能不能做，而是：

1. **做偏了能不能发现？**
2. **失败了能不能恢复？**
3. **完成了有没有证据？**
4. **危险操作能不能拦住？**
5. **成本失控能不能停止？**

我认为最小闭环可以简化成 5 个问题：

```md
1. 状态写在哪里？
2. 计划怎么拆？
3. 执行怎么记录？
4. 结果怎么验证？
5. 什么时候必须停？
```

如果这五个问题答不清，模型越强，风险越大。

最终结论：

> 短任务靠模型能力，长任务靠工程闭环。  
> Agent 要从 Demo 走向生产，必须从“会干活”升级为“可审计的执行系统”。

## 结构化（1）

### 2026-06-02 07:55:03

##### 主旨概括

文章认为，长任务 Agent 失控的核心不是 prompt 不够聪明，而是缺少工程控制闭环。要让 Agent 稳定完成复杂任务，至少需要围绕 **Context（状态）、Planning（规划）、Verification（验证）** 建立控制层，并进一步形成可恢复、可验证、可停止的工程系统。

---

##### 1. 长任务 Agent 的三大常见问题

Claude 工程师的一张图总结了长任务 Agent 最典型的三个问题：

- **带不住状态**：任务做久后，Agent 会忘记最初目标、历史决策和已验证内容。
- **估不准工作量**：不知道任务到底多大，容易过度扩展或过早收工。
- **评不好自己的输出**：常把浅层验证包装成“任务已完成”。

这三者会形成失控链路：

> 上下文越来越脏，计划越来越虚，验证越来越浅。  
> Agent 不是突然变笨，而是在缺少控制回路的系统里越跑越偏。

---

##### 2. 状态丢失：Agent 的“工作台”会越堆越乱

长任务中，Agent 最早出问题的往往不是代码，而是状态。

随着对话变长、工具调用增多、错误日志和临时判断不断堆积，context 会变成一张杂乱的工作台。即使上下文窗口很大，也不代表模型能自动整理信息。

###### 关键问题

- 早期目标和指令容易被噪声淹没。
- 第 40 步、第 80 步后，Agent 可能还在执行，但已经偏离原始任务。
- session 之间切换时，压缩摘要会丢失大量工程现场：
  - 哪些决定已确认？
  - 哪些方案被否掉？
  - 哪些文件改过但还没验证？
  - 哪些失败路径不要再试？

###### 解决思路

生产级 Agent 不能只把状态放在对话里，而要写入外部状态，例如：

- `progress.md`
- 任务 ledger
- trace log
- issue comment
- 数据库
- artifact ledger

一个好的系统应做到：

- **长期状态放外部**
- **当前步骤材料放 context**
- 每次进入新阶段先读状态
- 每次完成阶段先写状态
- 定期清理上下文

这类似传统工程里的 **checkpoint**，是防止任务漂移的锚点。

---

##### 3. 规划失真：Agent 经常不知道任务到底有多大

即使状态问题缓解，长任务仍可能因为规划失真而失败。

人类工程师接需求时，会自然判断：

- 这是小改动还是大改动？
- 是否影响数据结构？
- 是否涉及迁移、兼容、验收标准？
- 应该一次做完还是拆阶段？

但 Agent 经常缺少这种“任务尺寸感”。

###### 常见表现

- 用户说“改一下文档生成流程”，Agent 可能扫描整个内容系统。
- 用户说“做一个可用 demo”，Agent 可能只搭 UI 空壳。
- 用户说“修一个 bug”，Agent 可能顺手重构半个模块。

还有两种典型失控：

1. **计划过大**
   - 一开始列出架构、代码、测试、文档、部署的大计划。
   - 前几步看似顺利，但 context 快用完时真正困难还没碰。
   - 最后用“核心功能已完成”草草收尾。

2. **过早判断完成**
   - 页面能打开，就说产品可用了。
   - 接口返回 200，就说功能通过了。
   - 单元测试过了，就说端到端没问题。

###### 规划层要建立硬约束

规划不能只是开场白，而要明确：

- 本次交付物是什么？
- 哪些明确不做？
- 每阶段完成标准是什么？
- 当前阶段最多消耗多少 context、工具调用和时间？
- 范围变大时何时停下来重新估算？
- 验证失败时是继续扩展，还是先修当前问题？

作者建议将规划分为两层：

###### 第一层：任务切分

回答“这件事应该怎么拆”。

每个子任务都应有：

- 输入
- 输出
- 验收方式

###### 第二层：运行预算

回答“这一段最多跑到什么程度”。

包括：

- max turns
- token budget
- tool call budget
- 时间上限
- 失败重试次数
- 人工确认条件

只有任务切分没有预算，Agent 会无限探索；只有预算没有切分，Agent 会临近限制时随便交差。

---

##### 4. 验证失灵：Agent 会把没做对的事讲得像做完了

验证失灵比状态丢失和规划漂移更危险，因为 Agent 很擅长给自己的结果“体面收尾”。

它常说：

- “已完成实现”
- “已通过基本验证”
- “核心流程正常”

但这些结论可能只是非常浅的验证。

###### 常见问题一：curl-only verification

Agent 看到接口返回 200，就认为功能可用。

但它可能没有验证：

- 页面是否真的能操作
- 浏览器控制台是否报错
- 数据是否真的写入
- 错误状态是否正常展示
- 用户路径是否完整跑通

尤其在 Web 应用中：

> 按钮存在，不代表能用；页面能打开，不代表主流程跑通。

###### 常见问题二：stub 逃逸

Agent 先写简化版本没问题，但危险在于忘记回来补完整，甚至把临时实现包装成交付成果。

例子包括：

- 支付流程只打印日志，却说流程已完成。
- 权限判断写了 TODO，但页面入口已开放。
- RAG 只返回固定示例，却说检索链路已打通。
- 图表数据写死，却说 dashboard 已完成。
- E2E 测试只测 happy path，没有失败路径。

###### 常见问题三：自我评分过高

Agent 经常把问题降级成：

> “目前实现满足核心需求，后续可优化。”

但很多关键缺陷正是这样被放过去的。

根本原因是：

- 写代码的 Agent 天然希望任务收敛。
- 到后半程时，它会倾向于把未完成解释成“后续优化”。
- 自己写、自己评，严格度不够。

###### 验证层至少需要三类验证

###### 1. 机器验证

能用工具判断的，不要交给模型判断。

包括：

- 测试
- 类型检查
- lint
- build
- schema validation
- 数据对账
- 截图 diff
- 可访问性检查
- 日志扫描

###### 2. 环境验证

Agent 要在真实或接近真实的环境中走一遍。

例如：

- Web 应用要用浏览器点击，而不只是 curl。
- 数据任务要读回结果，而不只是看写入命令成功。
- 文档发布要 fetch 回来检查，而不只是 API 返回 OK。

###### 3. 独立评价

生成者和评价者要分开。

可以采用：

- Planner 拆任务
- Generator 执行
- Evaluator 按 rubric 检查

Evaluator 只回答硬问题：

- 需求是否真的满足？
- 关键路径是否真的跑通？
- 是否存在 stub 或 TODO 被包装成交付？
- 失败路径有没有处理？
- 验证证据是否足够？
- 下一轮该修什么？

Anthropic 的 long-running application development harness 中，就让独立 evaluator 用 **Playwright** 像真实用户一样操作应用，验证 UI、API 和数据库状态。

核心是把“完成”从一句话变成一条证据链。

---

##### 5. 工程化 Agent 的五层架构

作者认为，生产级 Agent 不能只看模型调用链，而至少需要五层结构。

###### 1）状态层：让任务有可恢复现场

状态层保存 Agent 不能丢的信息：

- 任务目标
- 当前进度
- 阶段产物
- 决策记录
- 文件变更
- 验证结果
- 阻塞点
- 人工确认记录

形式可以是：

- `progress.md`
- 数据库
- trace store
- issue comment
- artifact ledger

关键要求是：

- 可读回
- 可续跑
- 可审计

---

###### 2）规划层：把大任务压成可调度小任务

规划层负责拆分：

- 阶段
- 依赖
- 预算
- 停止条件

它更像调度系统里的 job spec，而不是漂亮 checklist。

每个阶段要明确：

- 当前阶段做什么
- 输入是什么
- 输出是什么
- 用什么验证
- 最多跑多久
- 失败几次后停止
- 哪些操作需要人工确认

---

###### 3）执行层：工具调用只是其中一部分

执行层负责把计划变成真实操作，例如：

- 读文件
- 改代码
- 跑测试
- 开浏览器
- 查日志
- 调 API
- 写文档
- 生成图片

关键不是工具越多越好，而是每次工具调用都要回到任务状态中：

- 命令输出要记录
- 文件变更要记录
- API 调用后要读回验证结果
- 工具调用不能只在上下文里一闪而过

---

###### 4）验证层：把完成变成证据链

验证层回答：

> 怎么知道这件事真的做对了？

应尽量使用外部证据：

- 测试结果
- 浏览器截图
- 数据库 readback
- 日志
- trace
- diff
- rubric 评分
- 人工 review

验证层最好与执行层分开，避免 Agent 自己给自己放水。

---

###### 5）监督层：控制权限、成本和升级路径

监督层负责决定 Agent 什么时候能继续，什么时候必须停。

包括：

- 权限控制
- 预算控制
- loop budget
- max turns
- 危险操作确认
- 发布前确认
- 失败升级
- 人类接管
- 回滚策略

需要介入的场景包括：

- 任务范围扩大
- 预算接近上限
- 验证连续失败
- 涉及删除、发布、权限、付费、生产数据
- Agent 无法判断
- 结果影响真实用户

这五层合起来，Agent 才从“会调用工具的模型”，变成一个：

> 可恢复、可验证、可停止的执行系统。

---

##### 6. 更强模型会改变 harness，但不会取消 harness

模型变强后，很多外层设计确实会变薄。

例如：

- 以前要拆成 5 个 sprint 的任务，新模型可能能自己保持连贯。
- 以前要写很细的中间计划，新模型可能用更少提示就能判断。
- 以前要子 Agent 查资料，新模型可能一次长上下文完成。

但 harness 不是宗教，应该随着模型能力重新测试。

###### 不能完全交给模型的几类东西

###### 1. 外部状态

真实任务中的状态不仅在上下文里，还包括：

- 文件系统变化
- 数据库变化
- API 状态变化
- 浏览器页面变化
- 用户需求变化
- 权限和成本变化

这些需要外部状态层对齐。

###### 2. 外部验证

模型可以更会反思，但仍需要环境反馈：

- 是否真的点过页面？
- 数据库是否真的写入？
- 发布后的文档能否打开？
- 用户路径是否卡住？

这些不能只靠模型“想一遍”。

###### 3. 权限和责任

涉及高风险动作时，不能因为模型更聪明就完全放权：

- 删除文件
- 发布内容
- 修改权限
- 触碰生产数据
- 花钱调用外部服务

应由系统负责授权，模型负责判断。

###### 4. 成本

长任务 Agent 很容易产生隐性成本：

- token
- 工具调用
- 浏览器会话
- 外部 API 调用

模型越强，单次调用可能越贵，越需要：

- budget routing
- max turns
- timeout
- circuit breaker

###### 两种极端都要避免

- **迷信模型**：把状态、验证、权限、预算都交给模型临场判断。
- **迷信 harness**：模型已经能稳定完成的事，还强行拆成复杂流程。

更好的做法是定期问：

> 这层 harness 现在还在解决真实问题吗？

有用就保留，无用就删掉。

---

##### 7. 长任务 Agent 的最小工程闭环

作者最后给出一组具体模式，适合放进任何长任务 Agent 系统。

###### 1）Spec-first：先写施工单，再动手

不要直接让 Agent “帮我做完功能”。

应先生成一份短 spec，包含：

- 目标：交付什么
- 非目标：哪些明确不做
- 约束：技术栈、风格、权限、预算、时间
- 验收：怎么判断完成
- 风险：哪些地方可能扩大范围

半页即可，重点是先固化任务边界。

---

###### 2）Plan gate：计划先过关，再自动执行

Agent 应先出计划，不能马上执行。

计划必须包含：

- 阶段拆分
- 每阶段交付物
- 每阶段验证方式
- 预计涉及的文件或系统
- 停止条件
- 需要人工确认的操作

人不一定要 review 每行代码，但应该 review 任务拆法。

---

###### 3）Progress ledger：每个阶段都写状态

长任务不能只靠对话续命。

每阶段完成后，Agent 应写 progress ledger，例如：

```md
## Current Goal
...

## Completed
- ...

## Changed Files
- ...

## Decisions
- ...

## Verification
- ...

## Open Risks
- ...

## Next Step
...
```

它的价值是续跑：

- 下一轮 Agent 先读 ledger，再读代码。
- 人可以快速知道做到哪里。
- 上下文满了、session 断了、模型换了，也能接回来。

---

###### 4）Independent evaluator：让另一个角色验收

生成者不要做最终裁判。

Evaluator 可以是：

- 另一个 Agent
- 脚本
- 测试
- CI
- Playwright
- 人工 review

输出应简洁明确：

```md
Result: PASS / FAIL

Evidence:
- ...

Blocking Issues:
- ...

Non-blocking Issues:
- ...

Required Fixes:
- ...
```

Evaluator 必须有权判 FAIL，否则只是总结员。

---

###### 5）Browser-level verification：Web 产品必须点过

Web 任务中，curl 和单元测试不够。

至少要用浏览器验证关键路径：

- 页面是否能打开
- 控件是否能点击
- 表单是否能提交
- 数据是否能显示
- 错误状态是否正常
- 控制台有没有报错
- 移动端有没有明显布局问题

如果涉及视觉，还要截图。截图是便宜但有效的证据。

---

###### 6）Stop condition：让 Agent 知道什么时候该停

常见停止点包括：

- 连续两次验证失败
- 任务范围明显扩大
- 需要删除、发布、改权限、花钱、触碰生产数据
- 当前阶段超过预算
- 遇到多个方案但无法判断
- 关键依赖不可用
- 用户目标互相冲突

停下来不是失败，失去边界继续跑才危险。

---

###### 7）Rollback path：每个阶段都要能退回

Agent 自动化越强，越需要回滚路径。

不同任务需要不同回滚手段：

- 代码任务：保留 git diff
- 数据任务：dry-run、备份、row count
- 发布任务：草稿、预览、读回验证
- 配置任务：记录旧值

没有回滚路径，就不要让 Agent 自动执行高影响操作。

---

###### 8）Trace everything：把过程留下来

长任务 Agent 最怕黑箱。

至少要记录：

- 输入任务
- 使用的模型和工具
- 关键工具调用
- 文件变更
- 验证结果
- 人工确认
- 失败重试
- 最终产物

OpenAI Agents SDK 的 tracing 文档也强调记录：

- LLM generation
- tool call
- handoff
- guardrail
- 自定义事件

trace 的目的不是漂亮 dashboard，而是在出问题时能回答：

> 它为什么这么做？哪里开始偏？哪一步验证放过了问题？

---

##### 8. 最后结论：Agent 的上限看模型，下限看架构

Agent 的能力上限来自模型，但能否进生产，关键看下限：

- 状态乱了能不能恢复？
- 计划漂了能不能拉回？
- 验证失败能不能发现？
- 权限风险能不能挡住？
- 成本异常能不能停止？

ReAct 和 Reflexion 等研究都指向同一件事：

> Agent 的质量不只来自生成，还来自行动后的反馈。

如果缺状态，反馈留不住；  
如果缺规划，反馈不知道回到哪个阶段；  
如果缺验证，反馈本身可能就是假的。

作者最后提出，判断一个 Agent 工作流，不应先看模型名，而应先问五个问题：

1. 状态在哪里？
2. 计划怎么拆？
3. 执行怎么记录？
4. 结果怎么验证？
5. 什么时候必须停？

这五个问题回答清楚，Agent 才真正从 demo 进入工程。

#### 长任务 Agent 的最小工程闭环：精炼版

##### 1. 启发：长任务 Agent 的核心不是「更聪明」，而是「可控」

这篇内容最重要的启发是：

> 长任务 Agent 的失败，往往不是模型突然变笨，而是系统缺少控制回路。

很多人使用 Agent 的体验是：

- 前 10 分钟：惊艳，能读代码、改文件、跑命令；
- 半小时后：开始不放心，不确定它是否还记得目标；
- 两小时后：做了很多事，但结果经不起细看。

背后的三个典型问题是：

1. **带不住状态**：上下文越来越脏，早期目标、决策、失败路径逐渐丢失；
2. **估不准工作量**：任务边界漂移，要么过度扩展，要么过早收工；
3. **评不好输出**：浅验证被包装成“已完成”，自己给自己打高分。

这三个问题会形成失控链路：

> Context 变脏 → Planning 变虚 → Verification 变浅 → Agent 自信交付错误结果。

因此，长任务 Agent 的关键不是写一个更好的 prompt，而是建立一个最小工程闭环：

> **状态可恢复，计划有边界，执行有记录，验证有证据，监督能叫停。**

---

##### 2. 高价值信息深挖

###### 2.1 Context 不是记忆，而是工作台

很多人把 context window 理解成“模型能记住多少东西”，但更准确的理解是：

> Context 是一张工作台，不是一个长期记忆系统。

工作台上会堆满：

- 用户需求；
- 文件片段；
- 命令输出；
- 错误日志；
- 中间判断；
- 失败尝试；
- 临时假设；
- 工具调用结果。

桌子变大有用，但桌子再大，也不等于它会自动整理材料。

所以，生产级 Agent 不能把状态全部押在上下文里，而要把「工作状态」和「推理上下文」分开：

| 类型 | 应该放哪里 |
|---|---|
| 当前步骤需要的信息 | Context |
| 任务目标、进度、决策、验证结果、风险 | 外部状态层 |
| 文件变更、失败路径、人工确认 | Ledger / DB / issue / trace |
| 可续跑现场 | progress.md / artifact log |

关键原则是：

> Context 只负责当前推理，长期状态必须外部化。

这类似传统工程里的 checkpoint。没有 checkpoint，长任务就变成一次上下文赌博。

---

###### 2.2 规划不是 checklist，而是施工单

Agent 很容易缺乏任务尺寸感。

你让它“修一个 bug”，它可能重构半个系统；  
你让它“做一个 demo”，它可能只搭一个 UI 空壳；  
你让它“优化文档生成流程”，它可能扫描整个内容系统。

所以规划层不是简单写：

> 我要完成 A、B、C。

而是要写成可调度的 job spec：

```md
当前阶段只做什么？
输入是什么？
输出是什么？
验收标准是什么？
最多允许消耗多少时间 / token / tool call？
验证失败怎么办？
哪些情况必须停下来问人？
```

一个有效规划至少包含两层：

| 规划层级 | 解决的问题 |
|---|---|
| 任务切分 | 这件事应该拆成哪些可独立验证的小阶段 |
| 运行预算 | 每个阶段最多跑到什么程度，什么时候停 |

缺少任务切分，Agent 会乱做；  
缺少运行预算，Agent 会无限探索；  
两者都缺，长任务一定漂。

---

###### 2.3 验证层的本质：把“完成”变成证据链

Agent 最危险的能力之一是：

> 把没做对的事情讲得像做完了。

典型表现包括：

###### 1. Curl-only verification

接口返回 200，就说功能完成。

但 Web 产品里：

- 页面能打开 ≠ 主流程跑通；
- 按钮存在 ≠ 按钮能用；
- API 返回 OK ≠ 数据正确写入；
- 单元测试通过 ≠ 用户路径可用。

###### 2. Stub 逃逸

Agent 做了临时实现，但忘了回来补完整：

- 支付流程只打印日志，却说链路打通；
- 权限判断写了 TODO，却开放了入口；
- RAG 返回固定示例，却说检索完成；
- 图表数据写死，却说 dashboard 完成。

###### 3. 自我评分过高

Agent 经常会说：

> 当前实现满足核心需求，后续可优化。

但这句话可能掩盖关键缺陷。

所以验证不能只依赖生成者自己的描述，而要构建独立验证：

| 验证类型 | 示例 |
|---|---|
| 机器验证 | test、lint、build、type check、schema validation |
| 环境验证 | 浏览器操作、数据库 readback、日志检查、截图 diff |
| 独立评价 | evaluator 按 rubric 判定 PASS / FAIL |

好的验证层要回答：

```md
需求是否真的满足？
关键路径是否真的跑通？
有没有 stub / TODO 被包装成交付？
失败路径有没有处理？
验证证据是否足够？
如果不够，下一轮该修什么？
```

核心判断：

> 生产级 Agent 最贵的失败，不是失败本身，而是失败了系统却以为成功了。

---

##### 3. 可迁移清单：长任务 Agent 的最小工程闭环

下面这套清单可以迁移到 AI 编程助手、数据分析 Agent、自动运营 Agent、内容生产 Agent、客服 Agent、RPA Agent 等系统中。

---

###### 3.1 Spec-first：先写施工单，再开始执行

不要直接让 Agent “帮我做完”。

先生成一份短 spec：

```md
## Goal
这次要交付什么？

## Non-goals
哪些明确不做？

## Constraints
技术栈、风格、权限、预算、时间限制是什么？

## Acceptance Criteria
如何判断完成？

## Risks
哪些地方可能扩大范围？
```

价值：

- 固化任务边界；
- 防止 Agent 自行扩展；
- 后续验证有依据；
- 人可以先审任务，而不是最后审烂摊子。

---

###### 3.2 Plan gate：计划先过关，再进入自动执行

Agent 执行前必须先出计划：

```md
## Phases
阶段拆分

## Deliverables
每阶段交付物

## Verification
每阶段验证方式

## Expected Files / Systems
预计涉及哪些文件、API、数据库、页面

## Stop Conditions
什么情况下必须停止

## Human Confirmation
哪些操作需要人工确认
```

建议：

> 人类不一定要 review 每一行代码，但应该 review 任务拆法。

因为很多 Agent 失控，问题从第一张计划就已经开始了。

---

###### 3.3 Progress ledger：每个阶段都写状态

每完成一个阶段，Agent 都要写 progress ledger。

模板：

```md
## Current Goal
当前目标

## Completed
已完成事项

## Changed Files
修改过的文件

## Decisions
关键决策

## Verification
验证方式与结果

## Open Risks
未解决风险

## Next Step
下一步
```

价值：

- 支持跨 session 续跑；
- 防止上下文压缩丢现场；
- 人可以快速扫进度；
- 失败后可以定位偏移点；
- 模型换了也能接着做。

---

###### 3.4 Independent evaluator：生成者和验收者分开

Evaluator 不要写成“整体不错，有一些建议”。

要用硬格式：

```md
Result: PASS / FAIL

Evidence:
- 验证证据 1
- 验证证据 2

Blocking Issues:
- 阻塞问题

Non-blocking Issues:
- 非阻塞问题

Required Fixes:
- 必须修复项
```

关键原则：

> Evaluator 必须有权判 FAIL。  
> 没有失败权的 evaluator，只是总结员。

---

###### 3.5 Browser-level verification：Web 产品必须真的点过

Web 类任务不能只靠 curl、单元测试或接口返回。

至少要检查：

- 页面是否能打开；
- 控件是否能点击；
- 表单是否能提交；
- 数据是否能显示；
- 错误状态是否正常；
- 控制台有没有报错；
- 移动端有没有明显布局问题；
- 关键流程是否真的走完；
- 必要时保存截图。

截图和浏览器轨迹是低成本、高价值的证据。

---

###### 3.6 Stop condition：让 Agent 知道什么时候必须停

常见停止条件：

- 连续两次验证失败；
- 任务范围明显扩大；
- 需要删除文件；
- 需要发布到线上；
- 需要修改权限；
- 需要花钱调用服务；
- 需要触碰生产数据；
- 当前阶段超过预算；
- 出现多个可行方案但无法判断；
- 关键依赖不可用；
- 用户目标互相冲突。

好 Agent 不应该永远硬跑。

它应该能说：

> 当前情况需要人工判断。

---

###### 3.7 Rollback path：每个阶段都要能退回

不同任务的回滚方式：

| 任务类型 | 回滚机制 |
|---|---|
| 代码任务 | git diff、branch、commit、revert |
| 数据任务 | dry-run、备份、row count、事务 |
| 发布任务 | draft、preview、staging、rollback plan |
| 配置任务 | 记录旧值、变更日志 |
| 权限任务 | 审计记录、双确认 |

原则：

> 没有回滚路径，就不要让 Agent 自动执行高影响操作。

---

###### 3.8 Trace everything：让过程可追踪

至少记录：

- 输入任务；
- 使用的模型；
- 工具调用；
- 文件变更；
- 关键命令输出；
- 验证结果；
- 失败重试；
- 人工确认；
- handoff 过程；
- 最终产物。

Trace 的目的不是做漂亮 dashboard，而是回答：

```md
它为什么这么做？
哪里开始跑偏？
哪一步验证放过了问题？
哪个状态没有被正确继承？
```

---

##### 4. 反方与张力

###### 4.1 反方一：模型变强后，还需要这么复杂的 harness 吗？

需要重新评估，但不会完全消失。

更强模型确实会改变架构：

- 原本需要拆成 5 个阶段的任务，可能 2 个阶段就够；
- 原本需要很细的 prompt，新模型可能能自行判断；
- 原本需要多个子 Agent，新模型可能一次完成。

所以 harness 不能宗教化。

> 每一层 harness 都是在补模型当前不稳定的地方。  
> 模型变强后，这些假设必须重新压力测试。

但有几类东西很难被模型能力完全替代：

| 控制点 | 为什么不能完全交给模型 |
|---|---|
| 外部状态 | 文件、数据库、API、用户需求都在上下文外变化 |
| 外部验证 | 页面有没有点过、数据有没有写入，需要环境反馈 |
| 权限责任 | 删除、发布、生产数据、花钱操作需要规则和审计 |
| 成本控制 | token、工具调用、API、浏览器会话都是真成本 |

结论：

> 更强模型会让 harness 变薄，但不会取消 harness。

---

###### 4.2 反方二：层数越多越安全吗？

不一定。

过度工程化会带来新的问题：

- 系统更慢；
- 成本更高；
- 编排更复杂；
- 错误藏在 harness 里；
- Agent 被过度限制，失去灵活性；
- 多 Agent handoff 造成信息损耗。

所以要避免两个极端：

| 极端 | 风险 |
|---|---|
| 迷信模型 | demo 很漂亮，生产长任务容易埋雷 |
| 迷信 harness | 系统慢、贵、难维护，控制层本身成为失败源 |

更好的问题是：

> 这层 harness 现在还在解决真实问题吗？

如果是，保留并增强观测；  
如果不是，删除，让模型直接做。

---

###### 4.3 关键张力：自动化程度 vs 可控性

长任务 Agent 的产品设计中，始终存在一组张力：

| 张力 | 说明 |
|---|---|
| 自动到底 vs 阶段验收 | 全自动体验好，但阶段验收更可靠 |
| 快速执行 vs 先写 spec | 直接开干快，但边界容易丢 |
| Agent 自评 vs 独立验证 | 自评便宜，但容易高估质量 |
| 长上下文 vs 外部状态 | 长上下文方便，但不可审计、不可恢复 |
| 多工具能力 vs 权限控制 | 工具越多越强，也越危险 |
| 多 Agent 分工 vs 信息损耗 | 分工更清楚，但 handoff 可能丢细节 |

产品上真正难的是：

> 既让用户感受到 Agent 的自动化能力，又不让系统在关键节点失去控制权。

---

##### 5. 情境化落地

###### 5.1 如果你在做 AI 编程助手

最小落地方案：

```md
1. 用户提交需求后，先生成 spec.md
2. Agent 输出 plan.md，用户确认
3. 每个阶段只改一个 feature 或 bug
4. 每阶段结束写 progress.md
5. 自动运行 test / lint / build
6. Web 项目用 Playwright 跑关键路径
7. Evaluator 独立判断 PASS / FAIL
8. 高风险操作必须人工确认
9. 所有改动保留 git diff 和 trace
```

关键指标：

- 每阶段平均修复次数；
- 验证失败率；
- evaluator 判 FAIL 的比例；
- 人工接管点；
- 回滚次数；
- 任务续跑成功率。

---

###### 5.2 如果你在做企业内部流程 Agent

例如：报销、合同、审批、数据录入、CRM 更新。

重点不是让 Agent “全自动处理”，而是：

- 状态可审计；
- 权限可控；
- 高风险动作有人确认；
- 结果可回滚；
- 每一步有证据。

推荐闭环：

```md
任务输入 → 规则识别 → 计划生成 → 人工确认关键规则 →
执行低风险步骤 → 写入 ledger → 环境 readback →
独立校验 → 高风险提交前再次确认
```

尤其要注意：

- 不能让 Agent 自己判断是否可以跳过审批；
- 涉及金额、权限、客户数据时必须有 guardrail；
- 失败不能静默通过；
- 所有变更必须可追踪。

---

###### 5.3 如果你在做内容生产 Agent

例如：写研报、生成课程、运营文章、市场材料。

也可以迁移这套框架。

常见失败：

- 主题漂移；
- 内容重复；
- 引用不实；
- 生成了漂亮但不准确的总结；
- 没有按目标用户场景落地；
- 没有事实核查。

落地方式：

```md
Spec:
- 目标读者是谁？
- 内容目的是什么？
- 不写什么？
- 必须引用哪些资料？
- 验收标准是什么？

Plan:
- 信息提取
- 结构设计
- 初稿生成
- 事实核查
- 风格编辑
- 最终审阅

Verification:
- 来源是否可追溯？
- 关键事实是否有证据？
- 是否满足目标读者需求？
- 是否有明显幻觉？
- 是否符合品牌语气？
```

内容 Agent 同样需要独立 evaluator，尤其是事实核查和引用检查。

---

###### 5.4 如果你在做数据分析 Agent

常见风险：

- SQL 跑通但口径错；
- 样本过滤错误；
- 指标定义混乱；
- 图表看似合理但误导；
- 没有 readback；
- 没有对账；
- Agent 用错误解释包装结果。

建议闭环：

```md
1. 先确认指标定义和数据口径
2. 明确 non-goals，避免扩展分析范围
3. 每一步 SQL 都记录
4. 查询结果要 readback 和抽样检查
5. 关键指标要和历史数据对账
6. 图表生成后要检查轴、单位、口径
7. Evaluator 检查结论是否被数据支持
8. 输出中区分事实、推断和建议
```

尤其要警惕：

> 查询成功 ≠ 分析正确。  
> 图表生成 ≠ 洞察成立。

---

##### 6. 最后总结：判断 Agent 工作流的五个问题

评估一个长任务 Agent，不要先看模型名，而要先问五个问题：

```md
1. 状态在哪里？
2. 计划怎么拆？
3. 执行怎么记录？
4. 结果怎么验证？
5. 什么时候必须停？
```

如果这五个问题回答不清楚，模型越强，跑偏时造成的动静越大。

如果这五个问题回答清楚，Agent 才真正从 demo 进入工程。

一句话总结：

> Agent 的上限看模型，下限看架构。  
> 生产级 Agent 的关键，不是让它一直自动干活，而是让它知道自己在做什么，做到哪里，如何证明做对了，以及什么时候必须停下来。

#### 长任务 Agent 的关键指标，不是“能跑多久”，而是“不会误判成功”

这篇文章最值得保留的，不是五层架构本身，而是一个更准确的故障判断：**长任务 Agent 的主要风险并非模型突然变笨，而是系统长期处于开环运行。**它持续行动，却没有可靠机制确认目标是否漂移、进度是否真实、结果是否合格。

状态、规划和验证，分别承担了控制系统里的记忆、边界与反馈。三者一旦同时变弱，就会出现典型链路：上下文被日志和临时判断污染，Agent 对任务范围的估计逐渐失真，最后再用一次浅层验证为结果背书。真正昂贵的不是失败，而是**失败后仍被系统标记为成功**——因为显性失败可以重试，假成功却会流入发布、数据、权限和用户流程。

##### Context 不是状态库，长上下文也替代不了工程现场

文章对 context window 的“工作台”比喻很准确。扩大窗口相当于换了一张更大的桌子，但不会自动区分目标、已确认决策、废弃方案和最新事实。尤其跨 session 后，压缩摘要通常只能保留故事主线，无法稳定保存“哪些路径已经失败”“哪些改动尚未验证”这类决定后续行动的信息。

因此，真正可恢复的 Agent 必须把长期状态外置：目标、非目标、阶段产物、变更记录、验证结果和阻塞项，都应成为可读回、可审计的对象。这里的重要变化是：**对话不再是任务本身，只是执行某一步时的临时工作区。**这会直接影响产品设计——Agent 的核心界面不应只有聊天记录，还应有任务账本、证据、版本与恢复点。

##### “另一个 Agent 来验收”还不够，关键是建立失败判据

文章强调独立 evaluator，但独立性不能只靠换一个角色名称。如果生成者和评价者使用相同模型、读取相似上下文，又面对模糊的“整体是否可用”，它们仍可能产生高度相关的误判。

更可靠的验证应优先依赖外部事实：测试结果、数据库读回、浏览器真实操作、截图差异、日志和数据对账。评价器还必须拥有明确的 FAIL 权限，并指出阻断项，而不是给出“整体不错、后续优化”的软性结论。高风险操作则仍需要人工授权，因为验证结果正确，不等于权限与责任可以交给模型。

由此也能看到一个比“通用 Agent 平台”更具体的产品机会：**为特定业务建立可执行的验收与证据基础设施。**例如电商运营 Agent 的关键资产，不只是生成能力，而是价格、库存、页面展示和发布结果之间的自动对账。真正需要验证的假设是：误判成本是否足够高，以及现有人工复核是否足够昂贵，能否支撑这套基础设施。

##### Harness 应随能力变薄，但不会完全消失

文章另一个成熟判断是：模型增强会改变编排方式，却不会消除外部状态、环境验证、权限和预算控制。可以减少子 Agent、缩短计划、扩大单次任务范围，但不能因为模型更聪明，就让它自己决定是否已成功、是否有权发布、是否值得继续花钱。

需要补充的是，文中依据主要来自厂商实践与工程经验，还不足以证明“五层架构”适合所有任务。更合理的做法不是固定套模板，而是按**失败影响、可逆性与验证难度**动态加厚控制：低风险任务允许宽松自治；涉及生产数据、付款、权限或真实用户时，则强化检查点、回滚和人工确认。

判断一个 Agent 是否真正进入工程阶段，最终不该看它连续运行了多少小时，而要看：**中断后能否恢复，偏航后能否发现，失败后能否拒绝交付，高影响动作前能否停下来。**
