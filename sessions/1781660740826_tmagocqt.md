## 分析要点

- **核心高价值点**：将上下文管理定义为“从完整历史到模型下一步所需视图的投影”，并明确区分完整日志、模型可见上下文和结构化应用状态。
- **留存建议**：短期参考后可归档，适合作为设计Coding Agent上下文管理机制的概念性备忘（提出了将上下文视为投影的框架，并区分durable log、model-visible context与app state，对Agent架构设计有参考价值）

**知识要点**

- 成熟的Coding Agent应区分durable log、model-visible context和app state，避免依赖完整transcript维持状态。
- 上下文投影应在模型调用前完成，根据当前任务、证据、上下文压力和运行时状态选择模型可见内容。
- 大规模tool output不应随机截断，而应保留完整结果在prompt外，同时向模型提供稳定preview和必要metadata。
- auto-compact需要阈值、阻断机制、递归防护以及压缩后状态恢复，不能只是简单触发总结。

**行动项**

- 在Agent设计中增加上下文投影层，将完整日志、模型上下文和应用状态分离。
- 为大日志、测试输出、grep结果等工具返回实现preview机制，并保留完整内容以便追溯。
- 设计context pressure监控、warning threshold和hard blocking threshold，在模型调用前触发压缩。
- 将已完成的旧片段显式折叠为summary，并保留compact boundary以支持resume和debug。

### 上下文是一种投影

Harness 系列文章之 6，关于 context management。

在 coding agent的世界里，昨日的重现，就是将昨日重要的事情映射到今天。

> 记录记录发生的事情。上下文决定现在什么重要。

![Image](https://pbs.twimg.com/media/HK8EiTPXYAALoN2?format=jpg&name=large)

每个 coding agent 最后都会遇到同一个问题： session 会越来会长。

Model 读过文件，跑过命令，搜过日志，改过代码，收到过 validation output，也回答过旧问题。

这些 context 如何管理？

#### 朴素的追加循环

![Image](https://pbs.twimg.com/media/HK8FLOfWkAAY71s?format=jpg&name=large)

最直觉的做法很简单，append transcript。但其实这是 context flooding。

一开始，model 似乎更聪明，因为它能看到更多。

很快就会遇到问题：

- 旧 tool output 会和当前 evidence 竞争
- 巨大的 shell log 会淹没下一条 instruction
- retry message，partial read，旧 plan，stale summary 全部挤在一个不断变大的 blob 里

#### 多匝循环

![Image](https://pbs.twimg.com/media/HK8oPOSXAAAM0hK?format=jpg&name=large)

比 Naive Append Loop 更成熟一点的是 5 phase loop，这部分放在文章的末尾。

#### 核心拆分

成熟的 Harness 会把三件事分开：

![Image](https://pbs.twimg.com/media/HK8F23DXYAAkQf9?format=jpg&name=large)

- Durable log 应该完整和简洁，它服务 resume，audit，evals 和 debugging。
- Model-visible context 应该被选择，是 model 为下一步行动需要看到的视图。
- app state 应该结构化。它不能依赖旧 transcript text 是否还在 prompt 里。

在此，我们定义出了projection：

> 投影是指将完整历史转化为模型下一步所需的精简的、相关的视图。

这对应了这篇文章的标题：

> 上下文是一种投影

#### 投影发生在模型调用之前

Context management 应该发生在 model call 之前。

Harness 投影流水线

![Image](https://pbs.twimg.com/media/HK8Gr4-WEAAOdcp?format=jpg&name=large)

- 先从完整 session log 开始，这是 source of truth
- 再看 context pressure：下一轮回答，tool use，evidence 还需要多少 context 空间
- 保留最近几轮 verbatim，因为这里通常放着当前任务
- 大的 output 变成 preview，完整内容留在 prompt 外
- 已完成的旧片段做显式 summary
- 注入当前 app state：已更改文件，验证，目标，任务 和 新证据

#### 四个投影移动

![Image](https://pbs.twimg.com/media/HK8IpbGXYAArHPa?format=jpg&name=large)

每个动作解决 context management 中面临的不同问题

#### 大结果预览

有些 tool result 太大，不适合在每个 turn 原样放进 context。

例如：

- 测试日志，grep 输出
- 生成的文件，网页获取
- 依赖树

弱 Harness 会随机截断，更强的 Harness 则会把完整结果放到别处，然后在 model-visible context 里放一个稳定 preview。

![Image](https://pbs.twimg.com/media/HK8JQaJWgAAuo8L?format=jpg&name=large)

Model 得到足够继续工作的 evidence。

Harness 保留足够的 metadata，用来 resume，inspect，或者重新加载完整结果。

#### 空转间隙微型紧凑型

有些 context 因为时间过去而变得不那么重要。

比如用户吃完午饭回来，或者 session 空闲了一夜。

最新 goal 仍然重要，最近几次 edit 仍然重要。

很久以前的重复 read 和 command output，未必重要。

microcompact 是一个小动作：

![Image](https://pbs.twimg.com/media/HK8J9NeW4AAy-fQ?format=jpg&name=large)

#### Old-Span 折叠

有时一整段 messages 已经完成使命，Harness 可以把这段折叠成 summary。但 summary 应该显式存在：

![Image](https://pbs.twimg.com/media/HK8KIo0WMAAbUML?format=jpg&name=large)

Model 知道 collapse 发生过，用户可以检查保留下来的内容。

resume 可以围绕 compact boundary 重建 conversation，而不会把 summary 当成一条随机的新 user message。

#### 接近极限自动压缩

当 context pressure 很高时，Harness 应该在 model call 失败前 compact。

好的实现不能只写一句 "if too long, summarize"。

![Image](https://pbs.twimg.com/media/HK8frS0XAAExtOC?format=jpg&name=large)

它需要：

- warning thresholds：提示用户 context 还剩余多少百分比
- hard blocking thresholds：超过限制前需要block model call，要求 compact 后再继续
- 递归防护：防止压缩又触发新的压缩
- 恢复的附件或状态块：压缩后重新加入附件、文件状态、验证、目标和任务。

auto-compact 要保护下一轮，同时保留继续工作所需的 evidence。

#### 多匝循环

![Image](https://pbs.twimg.com/media/HK8haVmWcAAIoZR?format=png&name=large)

context 的管理，在 Multi-turn Loop 中尤其重要。

一个 Multi-turn Loop 大概如下，分为 5 个 phase：

![Image](https://pbs.twimg.com/media/HK8hq38WcAATs8k?format=jpg&name=large)

在循环中，下一轮从已提交的运行时状态开始。

第二阶段上下文投影负责生成模型可见视图。

Phase 5 负责提交变化，让下一轮从真实的 runtime state 开始。

从 model call 开始，coding agent 的世界状态发生了变化，划分成了昨天和今天。

Model 不需要整个过去，它需要正确的过去、当前 state，以及足够支持下一步的 evidence。

> Harness Context management 就是管理和决定模型调用看到的选定视图。

## 解读（1）

### 2026-06-17 02:12:11

#### 《上下文是一种投影》精炼解读

##### 一、深度总结

这篇文章讨论的是 **Coding Agent 的上下文管理**。

核心观点：

> **上下文不是完整历史，而是从完整历史中投影出来的“下一步所需视图”。**

Coding Agent 在长时间工作后，会积累大量信息：

- 读过的文件
- 执行过的命令
- 旧日志
- 修改记录
- 验证结果
- 旧计划与旧回答

如果简单地把所有内容不断追加到 prompt 里，就会造成 **context flooding**：

- 旧信息干扰新证据
- 大日志淹没当前指令
- 过时计划误导模型
- 上下文越来越臃肿，模型反而变笨

因此，成熟的 Agent Harness 需要区分三件事：

| 类型 | 作用 |
|---|---|
| Durable log | 完整记录，用于恢复、审计、调试、评估 |
| Model-visible context | 给模型看的精简视图 |
| App state | 结构化状态，如目标、任务、文件变更、验证结果 |

所谓 **projection（投影）**，就是：

> 从完整历史中，选择、压缩、重组出模型下一步真正需要的信息。

这件事必须发生在 **model call 之前**。

---

##### 二、深入浅出解读

可以把 Coding Agent 想象成一个程序员助手。

它昨天干了很多事：

- 看了几十个文件
- 跑了很多测试
- 改了几处代码
- 遇到一些报错
- 形成了一些旧判断

到了今天，它不需要把昨天所有终端输出都重新看一遍。

它真正需要的是：

1. 当前目标是什么  
2. 哪些文件改过  
3. 最近失败在哪里  
4. 哪些验证结果可靠  
5. 下一步该做什么  

所以，**上下文管理不是“记得越多越好”，而是“该出现的出现，不该出现的退场”。**

文章提出几种关键做法：

###### 1. 大结果做预览

大日志、大文件、大量 grep 输出，不应该原样塞进 prompt。

更好的方式是：

- 完整内容保存在外部
- prompt 中只放摘要、关键片段、元数据

模型看到足够证据即可，不必被垃圾信息淹没。

---

###### 2. 旧内容折叠成摘要

已经完成使命的旧对话，可以压缩成明确 summary。

但要显式标记：

> 这里发生过折叠，这是摘要，不是新的用户消息。

这样便于恢复，也避免模型误解。

---

###### 3. 接近上下文极限时自动压缩

不能等 prompt 爆了才处理。

好的系统应该有：

- 预警阈值
- 强制 compact 阈值
- 防递归 compact 机制
- compact 后重新注入当前状态

目标是：

> 保护下一轮模型调用，同时保留继续工作的必要证据。

---

###### 4. 多轮循环中的上下文投影

一个成熟 Agent 的每一轮，不是简单“输入—输出”。

而是：

1. 从真实 runtime state 开始  
2. 做 context projection  
3. 调用模型  
4. 执行动作  
5. 提交状态变化  

下一轮不是从旧 transcript 开始，而是从 **已提交的真实状态** 开始。

---

##### 三、最核心的一句话

> **Agent 不需要完整过去，它需要正确的过去、当前状态，以及足够支持下一步的证据。**

---

##### 四、辩证思考

###### 1. 上下文越多，不一定越智能

很多人误以为模型窗口越大，Agent 越强。

但事实是：

> 信息过载会降低判断质量。

长上下文如果缺乏结构，反而会让旧信息污染当前任务。

---

###### 2. 摘要有价值，但也有风险

压缩上下文可以提升效率，但摘要可能丢失细节。

所以关键不是“要不要摘要”，而是：

- 什么内容该摘要
- 什么内容必须保留原文
- 摘要是否可追溯
- 是否能重新加载完整证据

好的 compact 不是删除，而是 **可恢复的压缩**。

---

###### 3. Agent 的核心能力不只是模型，而是 Harness

文章隐含了一个重要判断：

> Coding Agent 的能力，很大程度取决于模型之外的系统设计。

模型负责推理，但 Harness 决定模型看到什么。

谁控制上下文，谁就在控制模型的注意力。

---

###### 4. “上下文是一种投影”也是一种产品哲学

这不只适用于 Coding Agent。

人类工作也是如此：

- 会议纪要是投影
- 项目看板是投影
- 简历是人生经历的投影
- Debug 报告是完整排查过程的投影

真正重要的不是保存一切，而是：

> 在正确时刻，把正确信息呈现给正确对象。

---

##### 五、结论

这篇文章的本质是在说：

> 长程 Agent 的关键，不是无限记忆，而是高质量选择。

优秀的上下文管理系统应该做到：

- 完整历史可追溯
- 当前状态结构化
- 模型视图被精心选择
- 大信息可预览、可恢复
- 旧内容可压缩、可检查
- 每一轮从真实状态出发

最终目标只有一个：

> 让模型在每一步都看到“足够少但足够对”的信息。

## 结构化（1）

### 2026-06-18 11:52:25

##### 主旨概括

文章认为：**上下文管理不是把所有历史都塞给模型，而是把完整历史“投影”为模型下一步真正需要的视图**。成熟的 coding agent Harness 应区分完整日志、模型可见上下文和结构化应用状态，避免 session 越来越长导致信息淹没。

---

##### 1. 问题：Coding Agent 的上下文会越来越长

在 coding agent 的运行过程中，模型会不断积累信息：

- 读过文件
- 跑过命令
- 搜过日志
- 改过代码
- 收到验证输出
- 回答过旧问题

随着 session 变长，所有这些内容如果都继续放进上下文，会让模型难以判断**当前真正重要的内容**。

核心问题是：**过去发生了很多事，但下一步并不需要全部过去，只需要相关的过去。**

---

##### 2. 朴素做法：不断追加 transcript 会造成“上下文洪水”

最直觉的做法是：把所有对话、工具输出和历史记录不断追加到 prompt 中。

这种方式叫做 **Naive Append Loop**，看似简单，但会导致 **context flooding**：

- 旧的 tool output 会和当前证据竞争注意力
- 巨大的 shell log 会淹没新的 instruction
- retry message、partial read、旧 plan、过期 summary 混在一起
- prompt 变成越来越大的 blob，模型反而更难判断重点

一开始模型似乎“更聪明”，因为看到更多；但很快会因为信息过载而变差。

---

##### 3. 成熟 Harness 的核心：拆分三类信息

成熟的 Harness 不会把所有内容混在一起，而是区分三件事：

###### 1）Durable log：完整持久日志

用于：

- resume：恢复会话
- audit：审计
- evals：评估
- debugging：调试

它应该**完整且简洁**，作为事实来源。

###### 2）Model-visible context：模型可见上下文

这是模型下一步行动真正需要看到的内容。

它不是完整历史，而是经过选择后的视图。

###### 3）App state：结构化应用状态

例如：

- 当前目标
- 已修改文件
- 验证结果
- 任务状态
- 新证据

它不能依赖旧 transcript 是否仍然留在 prompt 中，而应以结构化方式保存。

---

##### 4. 核心概念：上下文是一种“投影”

文章给出的定义是：

> **投影，就是把完整历史转化为模型下一步所需的精简、相关视图。**

也就是说，Harness 并不是简单地“记住一切”，而是在每次模型调用前决定：

- 哪些历史需要保留原文
- 哪些内容可以总结
- 哪些大输出只需要预览
- 哪些状态必须结构化注入
- 哪些旧内容可以折叠

因此，**context management 应该发生在 model call 之前**。

---

##### 5. Harness 的上下文投影流水线

一个成熟的 Harness 通常会按如下流程生成模型可见上下文：

1. **从完整 session log 开始**  
   它是 source of truth，保存完整历史。

2. **评估 context pressure**  
   判断下一轮回答、工具使用、证据展示还需要多少上下文空间。

3. **保留最近几轮原文**  
   因为最近几轮通常包含当前任务和最新意图。

4. **大输出变成 preview**  
   完整内容留在 prompt 外，模型只看到稳定摘要或预览。

5. **已完成旧片段生成显式 summary**  
   让模型知道这些内容被折叠过，而不是完全消失。

6. **注入当前 app state**  
   包括已更改文件、验证结果、目标、任务、新证据等。

这些步骤共同解决上下文过长、信息过载和状态丢失的问题。

---

##### 6. 大结果处理：不要随机截断，而要稳定预览

有些工具结果太大，不适合每轮原样放入上下文，例如：

- 测试日志
- grep 输出
- 生成的文件
- 网页抓取内容
- 依赖树

弱 Harness 的做法是随机截断；更强的 Harness 会：

- 把完整结果保存到 prompt 外
- 在模型可见上下文中放一个稳定 preview
- 保留 metadata，方便之后恢复、检查或重新加载完整结果

这样模型既能获得足够证据继续工作，又不会被巨大日志淹没。

---

##### 7. 空闲后的 microcompact：折叠不再重要的旧内容

有些上下文会随着时间流逝而降低重要性。

例如：

- 用户吃完午饭回来
- session 空闲了一夜

这时仍然重要的是：

- 最新目标
- 最近几次 edit
- 当前验证状态

而很久以前的重复 read、旧 command output 可能就没必要继续保留原文。

因此 Harness 可以做 **microcompact**：轻量折叠旧内容，减少上下文压力。

---

##### 8. Old-Span 折叠：旧片段可以总结，但必须显式

当一整段消息已经完成使命时，Harness 可以把它折叠成 summary。

但这个 summary 应该是显式存在的，因为：

- 模型知道发生过 collapse
- 用户可以检查被保留下来的内容
- resume 时可以围绕 compact boundary 重建对话
- 不会把 summary 误认为一条新的随机 user message

重点是：**压缩不是删除历史，而是建立清晰边界的摘要。**

---

##### 9. 接近上下文极限时：需要自动压缩机制

当 context pressure 很高时，Harness 应该在模型调用失败前进行 compact。

好的实现不能只是简单写一句：

> if too long, summarize

而需要包含：

- **warning thresholds**：提示用户上下文还剩多少百分比
- **hard blocking thresholds**：超过限制前阻止 model call，要求先 compact
- **递归防护**：避免压缩本身又触发新的压缩
- **恢复附件或状态块**：压缩后重新加入附件、文件状态、验证、目标和任务

auto-compact 的目标是：**保护下一轮调用，同时保留继续工作所需的证据。**

---

##### 10. 多匝循环：上下文投影是关键阶段

文章提到，比 Naive Append Loop 更成熟的是 **5 phase loop**。

在多匝循环中：

- 下一轮从已提交的 runtime state 开始
- 第二阶段负责做上下文投影，生成模型可见视图
- Phase 5 负责提交变化，让下一轮基于真实 runtime state 继续

这说明，context management 不是附属功能，而是 multi-turn coding agent 的核心机制之一。

---

##### 总结

文章的核心观点是：**模型不需要完整过去，而需要“正确的过去”、当前状态，以及足够支持下一步行动的证据。**

Harness 的上下文管理，本质上就是在每次模型调用前，把完整历史投影成一个精简、相关、可靠的模型可见视图。
