> **摘要**：该仓库是针对RTX 3090系列优化的llama.cpp分支，通过MTP推测解码、64K草稿词表、TurboQuant KV缓存及定制SM86内核，提高Qwen模型的单卡长上下文推理速度，并给出可运行配置。

## 分析要点

- **核心高价值点**：将MTP-3推测解码、精确p/q验证、64K草稿词表和量化KV缓存组合起来，在单张RTX 3090上兼顾超长上下文容量与生成速度。
- **留存建议**：保留并结合目标硬件复现实测，重点查阅专项优化文档（提供了面向Ampere显卡的明确推理优化组合、启动参数与性能目标，对单卡长上下文部署具有直接参考价值。）

**知识要点**

- 缩小MTP草稿词表可降低推测解码开销，并与精确p/q验证结合以保持采样分布正确性。
- KV缓存采用q8\_0 K与turbo3 V并配合融合注意力内核，可在显存容量和长上下文解码速度之间取得平衡。
- 不同V缓存格式对应不同上下文上限和内核支持条件，选择时需要同时考虑显存、速度与编译选项。

**行动项**

- 在RTX 3090或3090 Ti上按QWEN\_AMPERE.md构建SM86版本，并使用文中完整参数启动服务。
- 使用相同模型、上下文长度和采样设置，对比该分支、原版llama.cpp及可用的vLLM配置。
- 分别测试turbo3、q8\_0和q5\_1缓存方案，记录显存占用、最大上下文和每秒生成速度。

> **llamAmpere** (v0.3): this fork runs Qwen3.8-27B at up to 245K context on one RTX 3090 / 3090 Ti with the model's own MTP head: 99 tok/s on clean agentic and coding fixtures at temperature 1 (1.46x stock llama.cpp, 1.28x v0.2), 93 tok/s at 100K KV depth, and 1.10x tuned vLLM single-stream at 32K. Start with QWEN\_AMPERE.md and the write-up in docs/llamampere-v0.3/ARTICLE.md (v0.2: docs/llamampere-v0.2/ARTICLE.md). Successor of [llama-cpp-qwen-ampere](https://github.com/JakeATX/llama-cpp-qwen-ampere) (v0.1). It also loads **Agnes 3.0 Flash**, including its MTP head, which upstream llama.cpp does not; see docs/agnes-3.0-flash.md. The rest of this README is upstream llama.cpp's.

**Fastest configuration (v0.3, one RTX 3090 / 3090 Ti).** Build from `main` as in QWEN\_AMPERE.md, with the GGUF from [jakeatx/Qwen3.8-27B-ATX-IQ4\_XS-M-GGUF](https://huggingface.co/jakeatx/Qwen3.8-27B-ATX-IQ4_XS-M-GGUF), then:

```
GGML_Q8_TURBO3_MMA_FUSED=1 ./build-sm86/bin/llama-server -m Qwen3.8-27B-ATX-4-XS.gguf \
  -c 245760 -b 4096 -ub 1024 -t 8 -tb 8 -ngl 99 -fa on -ctk q8_0 -ctv turbo3 \
  --parallel 1 --jinja --fit off \
  --cache-prompt --cache-ram 8192 --ctx-checkpoints 24 --checkpoint-min-step 10240 \
  --spec-type draft-mtp --spec-draft-n-max 3 --spec-draft-p-min 0 \
  --spec-draft-type-k q8_0 --spec-draft-type-v q8_0 \
  --spec-draft-vocab-map docs/mtp-vocab/atx_65536.txt
```

The speed comes from MTP-3 speculative decoding with exact p/q verification (on by default), `--spec-draft-p-min 0`, the 65,536-token draft vocabulary map, a q8\_0 K / turbo3 V cache on the fused attention kernel, and a q8\_0/q8\_0 drafter cache. Lower `-c` if you need VRAM for something else; the decode flags stay the same. To avoid turbo3, `-ctv q8_0` (\~165K context) and `-ctv q5_1` (\~190K, needs a `-DGGML_CUDA_FA_ALL_QUANTS=ON` build, no fused kernel yet) are listed with their trade-offs under KV cache options.

#### Description

The main goal of `llama.cpp` is to enable LLM (and VLM) inference with minimal setup and state-of-the-art performance on a wide range of hardware - locally and in the cloud.

- Plain C/C++ implementation without any dependencies
- Apple silicon is a first-class citizen - optimized via ARM NEON, Accelerate and Metal frameworks
- AVX, AVX2, AVX512 and AMX support for x86 architectures
- RVV, ZVFH, ZFH, ZICBOP and ZIHINTPAUSE support for RISC-V architectures
- 1.5-bit, 2-bit, 3-bit, 4-bit, 5-bit, 6-bit, and 8-bit integer quantization for faster inference and reduced memory use
- Custom CUDA kernels for running LLMs on NVIDIA GPUs (support for AMD GPUs via HIP and Moore Threads GPUs via MUSA)
- Vulkan and SYCL backend support
- CPU+GPU hybrid inference to partially accelerate models larger than the total VRAM capacity

The `llama.cpp` project is build on top of the [ggml](https://github.com/ggml-org/ggml) library.

#### 3090 跑 27B 长上下文：真正的突破是把瓶颈逐层拆开

这个项目最值得关注的，不是“消费级显卡也能跑大模型”这一结论，而是一个更具体的工程信号：**一张 24GB 的 RTX 3090，在高度定制的软件栈下，可以让 27B 模型承载最高 245K 上下文，并在 100K KV 深度时维持约 93 tok/s。**作者报告，在特定任务上速度达到 99 tok/s，较原版 llama.cpp 提升 1.46 倍，32K 场景下还略快于调优后的 vLLM 单流推理。

这不是某个单点优化的成果，而是同时处理了推理中的三个约束：算力、显存和内存带宽。

##### 长上下文的关键成本，正在从模型权重转向 KV Cache

27B 模型经过约 4 bit 量化后，权重已经有机会装进 24GB 显存；真正随上下文持续增长的是 KV Cache。项目采用 q8_0 K 与更激进的 turbo3 V 缓存压缩，才把上下文上限推到 245K。若改用更常规的 q8_0 或 q5_1，容量会下降到约 165K 或 190K。

这揭示了一个容易被忽略的变化：**长上下文推理不再只是“模型能否加载”，而是每生成一个 token，要读写多少历史状态。**上下文越长，缓存占用和访存压力越可能成为主导因素。因此，未来本地推理的差异化未必只来自权重量化，KV Cache 的表示方式、注意力内核和缓存管理同样会决定可用性。

但“能放进 245K”不等于“模型能有效利用 245K”。仓库证明的是工程容量和生成速度，没有提供超长上下文下的信息召回、推理质量或量化损失数据。

##### 推测解码的价值，在于用验证机制换取低成本试错

项目使用模型自身的 MTP 头一次预测最多三个未来 token，再由主模型进行精确的 p/q 验证。它还把草稿阶段的候选词表缩减到 65,536 个 token，以降低草稿计算量。

这里有一个可迁移的设计原则：**先让便宜模块提出候选，再让昂贵模块批量验证；只要验证规则严格，提速不必以改变采样分布为代价。**这比单纯使用“小模型猜、大模型验”更紧耦合，因为 MTP 头本来就是目标模型的一部分。

不过，短名单和多 token 预测带来的收益依赖任务分布：代码、工具调用等可预测性较强的文本，接受率可能更高；开放式创作或多语言长尾词汇则未必如此。准确性可以由拒绝机制保护，但性能收益不能直接外推。

##### 它指向的是专用本地推理，而非通用替代云服务

这套方案把特定模型、Ampere SM86、量化格式、融合注意力内核和启动参数绑定得很紧。它更像“赛车调校”，不是开箱即用的平台能力。仓库体量也仍较小，数据主要来自作者基准，缺少功耗、首 token 延迟、多并发和跨任务复现。

因此，近期机会更可能出现在**单用户、长会话、高频持续生成**的本地代理场景，例如代码代理、私有知识库分析或敏感数据处理，而不是高并发在线服务。值得验证的核心并非用户是否喜欢“本地 AI”，而是：与云 API、新显卡或多卡方案相比，既有 3090 的固定成本优势，能否覆盖额外的部署和维护复杂度。

更长期的判断是，旧硬件的寿命 increasingly 取决于软件能否针对模型结构、缓存格式和芯片特性协同优化。硬件代际不再单独决定推理能力，**优化栈是否愿意为庞大的存量设备做深度适配，也会改变算力供给。**

## 口播总结（1）

### 2026-09-20 00:37:20

这个项目要解决的问题很具体：如何让一张英伟达 RTX 三零九零或三零九零 Ti，在运行二百七十亿参数的大模型时，既容纳超长上下文，又保持较高的生成速度。

项目名叫 llamAmpere。它是 llama.cpp 的一个分支，专门针对英伟达 Ampere 架构优化，重点适配三零九零系列显卡。根据项目作者公布的测试，运行 Qwen 三点八、二百七十亿参数模型时，单张显卡最多可以支持约二十四万五千个词元的上下文。在温度参数设为一的智能体和编程测试中，生成速度最高达到每秒九十九个词元。即使键值缓存，也就是 KV 缓存的深度达到十万个词元，速度仍有每秒九十三个词元。

需要注意，这些数字来自项目自己的特定配置和测试样例。它们依赖指定的量化模型、编译选项、缓存格式和解码参数，并不代表任意模型、任意任务都能达到同样速度。

这套优化的第一个关键，是多词元预测，也叫 MTP 推测解码。

普通自回归模型通常一次生成一个词元。每生成一个词元，都要运行一轮主模型计算。推测解码的思路，是先让一个成本更低的预测模块，一次提出几个候选词元，再由主模型统一检查。如果候选正确，就可以在一次验证中前进多个词元。

llamAmpere 使用 Qwen 模型自带的 MTP 预测头，每轮最多草拟三个词元。它还使用严格的概率验证，也就是项目所说的精确 p、q 验证。简单理解，主模型并不是无条件接受草稿，而是按照目标模型与草稿模型各自的概率分布进行校验。这样既能利用推测解码提速，又尽量保证最终采样结果符合主模型原本的分布。

不过，推测解码还有一个成本：预测模块如果每次都要在完整词表上计算，开销可能抵消一部分收益。这个项目为草稿阶段准备了一个包含六万五千五百三十六个词元的候选表。草稿模块只在这份缩小后的词表里工作，从而减少计算量。完整主模型仍负责最终验证，所以这不是简单地把正式模型的词表永久裁掉。

第二个关键，是压缩并加速 KV 缓存。

KV 缓存保存模型处理过的上下文信息。上下文越长，缓存占用的显存越大，注意力计算也越重。对于只有二十四吉字节显存的三零九零来说，想装下二十多万个词元，KV 缓存往往比模型权重本身更容易成为瓶颈。

llamAmpere 对键缓存和数值缓存采用不同格式。键缓存使用八位量化，数值缓存使用项目定制的 TurboQuant，也就是 Turbo 三格式。这里的量化，可以理解为用精度更低、占用更小的数据表示缓存。项目还把这种缓存格式与注意力内核融合，减少数据转换和额外读写。

正是这种缓存压缩，让单张三零九零有机会把上下文容量推到约二十四万五千个词元。但这是容量上限，不等于每次都应该使用这么长的上下文。上下文设置越大，显存越紧张，也可能影响其他程序。如果需要给系统或别的任务保留显存，可以降低上下文上限，而解码优化本身仍然可以保留。

项目也提供了不使用 Turbo 三的替代方案。数值缓存改用八位量化时，大约可支持十六万五千个词元；改用五位量化格式时，大约可支持十九万个词元。不过，五位方案需要额外的编译选项，而且暂时没有对应的融合内核。也就是说，不同缓存格式是在上下文容量、速度、兼容性和实现复杂度之间做取舍。

第三个关键，是针对硬件和模型定制计算内核。

三零九零使用的是 Ampere 架构中的 SM 八六计算单元。通用框架通常要兼顾很多显卡和模型，不可能对每一种组合都做到最激进的优化。llamAmpere 则专门加入了 SM 八六和 Qwen 模型相关的 CUDA 内核，并配合融合注意力、量化缓存和推测解码工作。

作者公布的比较结果显示，在特定的智能体与编程测试中，每秒九十九个词元的成绩，大约是原版 llama.cpp 的一点四六倍，也是该项目零点二版本的一点二八倍。在三万二千词元上下文下，它还比经过调优的 vLLM 单路推理快约百分之十。这里强调的是单请求、单数据流性能，不应直接推导为多用户并发服务中的整体吞吐优势。

除了 Qwen，这个分支还能加载 Agnes 三点零 Flash，包括该模型的 MTP 预测头。材料称，当时上游 llama.cpp 还不支持这一能力。不过，项目的主要性能路径仍然围绕 Qwen 三点八、二百七十亿参数模型和三零九零系列显卡展开。

实际使用并不是下载后直接运行就能获得全部收益。用户需要从项目主分支按指定方式编译，使用作者提供的特定量化 GGUF 模型，并启用融合内核、量化 KV 缓存、MTP 推测解码、六万五千五百三十六词元草稿表，以及提示缓存和上下文检查点等选项。改变模型版本、量化格式、驱动、上下文长度或采样方式，都可能改变最终速度。

最值得记住的是，llamAmpere 的提升并非来自单一技巧。它把推测解码、草稿词表缩减、KV 缓存量化，以及面向 SM 八六的定制内核组合在一起，专门优化单张三零九零上的长上下文推理。

它展示的核心思路是：消费级显卡运行大模型时，不仅要压缩模型权重，还要同时控制草稿计算成本、KV 缓存体积和显存读写开销。项目给出的性能很有吸引力，但这些成绩高度依赖指定硬件、模型和参数，评估时必须连同测试条件一起看。

## 深度解读-口播（1）

### 2026-09-30 11:54:56

一张英伟达 RTX 三零九零显卡，能不能让二百七十亿参数的大模型，在长上下文下仍然快速生成？llamAmpere 这个项目给出的答案是：针对特定模型和硬件，把缓存、生成流程和底层计算一起优化，可以显著提高性能。但这些成绩有明确的配置前提，不能直接推广到所有模型和显卡。

llamAmpere 是 llama 点 cpp 的一个分支。原版框架强调在多种硬件上运行大模型，这个分支则重点优化英伟达的安培架构，尤其是 RTX 三零九零和三零九零 Ti。

项目零点三版本公布的主力配置，是通义千问三点八、二百七十亿参数模型，搭配指定的量化模型文件。在一张上述显卡上，这套配置支持约二十四万五千个词元的上下文。词元是模型处理文本的基本单位，不等于汉字，也不等于完整的词。

速度方面，项目报告：在较干净的智能体任务和编程测试中，采样温度设为一时，生成速度可以达到每秒九十九个词元，是原版 llama 点 cpp 的一点四六倍。采样温度会影响输出的随机程度，因此这个设置也是比较性能时需要保留的条件。

更值得关注的是长上下文表现。项目报告，在缓存已经积累到十万个词元的深度时，仍能达到每秒九十三个词元。这里说的是已有上下文很长时的生成速度，不是处理十万个输入词元的速度。

这些都是项目自身公布的测试结果。理解它们的价值，要看加速究竟来自哪里。

第一处关键，是压缩模型的上下文缓存。

大模型逐步生成文本时，会保存已经处理过的内容所对应的一些中间计算结果，避免每次都从头计算。这类缓存叫 KV 缓存，可以理解为模型读取前文时留下的工作记录。上下文越长，工作记录通常也越大，显存压力就越明显。

llamAmpere 的最快配置，对缓存里的两部分采取了不同处理。称为 K 的部分使用八位量化格式；称为 V 的部分使用名为 Turbo3 的压缩格式。同时，项目配套了融合注意力计算内核，把相关计算整合起来执行。

所以，这项优化不只是“把缓存压小”。缓存怎么存，显卡又怎么读取和计算，是一起设计的。

项目也提供不用 Turbo3 的选择。如果 V 缓存改用八位量化，文档估算可支持约十六万五千个词元的上下文。如果改用另一种五位量化格式，估算可支持约十九万个词元。不过，五位方案需要额外的编译选项，而且暂时没有对应的融合内核。

这说明，缓存格式不只是影响能装下多长的文本，也会影响可用的加速路径。选择替代格式后，不能默认仍然获得最快配置的成绩。

第二处关键，是改变逐个生成词元的工作方式。

项目使用了 MTP，也就是多词元预测，并把它用于推测解码。可以把这个过程理解为：先提出几个可能的后续词元，再由正式模型验证。猜得合适，就有机会减少逐步生成的开销；猜得不合适，也不能直接把草稿当作最终答案。

这里有两个重要细节。

一个是，项目使用模型自身的多词元预测头来生成草稿，最快配置最多起草三个词元。另一个是，草稿阶段使用一个包含六万五千五百三十六个词元的候选词表。这个较小的候选范围，是加速草稿生成的一部分。

但候选词表缩小，不代表最终输出可以跳过验证。项目默认启用了精确验证机制，对照正式模型和草稿模型的概率，决定是否接受草稿。也就是说，这套方案不仅关心“猜得快”，还关心“怎么正确地接受或拒绝猜测”。

草稿模型本身也有缓存。最快配置为草稿的 K 和 V 缓存都使用八位量化。主模型缓存、草稿缓存和验证设置，共同组成了整套加速方案，而不是打开一个开关就能完成。

再往底层看，llamAmpere 还加入了面向这类显卡和千问模型的定制计算内核。因此，公布的性能应当理解为一整套针对性优化的结果，不能全部归功于某一种缓存压缩技术，或者单独归功于推测解码。

这也决定了怎样看待它和其他推理引擎的比较。项目报告，在三万二千个词元的上下文、单路请求条件下，速度达到经过调优的 vLLM 的一点一倍。这个结论说的是特定场景下的单路性能，并不是高并发服务能力的全面比较。

如果准备实际使用，最重要的是复现配套条件：针对目标显卡编译，使用项目指定的量化模型，并配齐缓存格式、推测解码参数和草稿词表。假如还要给其他程序留显存，可以降低上下文上限；项目说明，生成阶段的主要参数可以保持不变。

最值得记住的是，长上下文推理的性能，往往不是一个因素决定的。llamAmpere 的亮点，是把缓存压缩、推测解码和专用计算内核协同起来。它展示了特定消费级显卡的潜力，但每秒九十九个词元和约二十四万五千个词元上下文，都应当连同模型、配置和测试条件一起理解。
