## 分析要点

- **核心高价值点**：将模型输出视为生产材料，而不是可信成果；通过 manifest、provenance、确定性编译、QA 和局部修复形成可控提交链路。
- **留存建议**：长期保留（文章系统拆解了 hatch-pet skill 的目录结构、资产协议、任务 manifest、子代理边界、溯源、QA 与修复流程，对理解可控 Agent 生产系统有较高参考价值。）

**知识要点**

- 成熟 Skill 不应只是 prompt 包，而应封装领域协议、执行边界、工具链、验收标准和修复策略。
- imagegen-jobs.json 作为外部 manifest，可记录任务依赖、输入输出、生成方式、hash、来源和完成状态，避免长任务状态只存在于上下文中。
- 子代理适合并行生成候选，但 manifest、record、finalize、package 等真值提交权应由父代理集中控制。
- QA 应区分结构正确性和语义正确性，脚本验证尺寸、透明、hash 等，视觉一致性仍需人工或模型检查。
- repair workflow 的核心是最小失败范围修复，而不是整体重试，能降低成本和漂移风险。

**行动项**

- 参考 hatch-pet 的结构，为自己的 Agent Skill 设计 SKILL.md、references、scripts 和 manifest。
- 在复杂 Agent 工作流中引入外部任务清单，记录依赖、状态、来源、hash 和可恢复信息。
- 将多代理架构拆分为 control plane 与 worker plane，限制子代理写权限。
- 为生成式任务建立结构 QA 与语义 QA 两层验收机制。
- 将失败处理从简单 retry 改造成基于最小失败范围的 repair 流程。

#### 序言

Skills 概念火了后（ [深度解析 Skills](https://mp.weixin.qq.com/s?__biz=MzIzNjE2NTI3NQ==&mid=2247491129&idx=1&sn=451107b90247a2f8ae5aaacca3804328&scene=21#wechat_redirect) ），市面上冒出一堆看似很酷、实则很水的东西：什么“蒸馏同事”、“复刻名人”、“一键生成 PPT”、“把某某大佬装进 XXX”…，名字一个比一个唬人，截图一个比一个炸裂，实际一看，大多还是几段角色扮演 prompt，再配一点花里胡哨的 workflow 包装。它们虽然能用，但却 **把 Skill 这个概念重新拉回了提示词玩具时代：用人格模仿制造幻觉，用营销标题制造稀缺感，用浅层自动化伪装成工程能力。**

很多人以为自己已经会 Skills 了，因为会写一个 `SKILL.md` ，会塞几段 instructions，会让模型“像某某一样思考”，甚至会搞几个看起来很炫的 demo。但这其实还在门外打转。真正的 Skill 不是“让模型换个语气说话”，也不是“把一个 prompt 存成文件”，更不是给 Agent 套一层玄学人设。有价值的 Skill，应该把一个领域里隐性的经验、边界、工具链、失败处理、验收标准和执行流程，压缩成 Agent 可以稳定调用的 **可执行协议** 。

过去我也一度以为，复杂任务编排必须依赖 n8n \[1\] 、 Zapier \[2\] 这类强 workflow 工具：节点清晰、链路明确、触发器稳定，看起来更像“工程”。但深入研究 Skills 后，会发现另一种解法正在成型： **不是把流程全部画死在节点图里，而是把能力、约束、脚本、参考资料、验收规则和修复策略封装成可组合的执行单元** 。传统 workflow 擅长确定性链路，一旦任务需要理解上下文、动态决策、局部修复、多代理协作，就很容易变成一张越来越难维护的巨型流程图。Skills 的优势恰恰在这里：它可以保持模块化，又能让 Agent 根据当前任务状态选择工具、展开步骤、调用脚本、分发子任务、回收结果，并在失败后按协议修复，而不是每次都靠人工重新接线。

所以 Codex 的 hatch-pet skill \[3\] 值得专门拆。它表面上只是一个“生成 Codex 电子宠物”的小功能，甚至还有点可爱、有点玩具感，但它的源码恰恰展示了什么叫真正的 Skill 工程：它不是让模型随便画一只宠物，而是把图像生成、资产协议、动画状态、子代理并行、provenance、QA、局部修复、最终打包全部串成了一条可验证的生产流水线。也正因为如此，它比那些靠标题博眼球的“人格蒸馏 Skill” 更能说明问题： **Skill 的本质不是角色扮演，也不只是轻量 workflow，而是把不可控的模型能力关进可控的工程边界里。**

#### Hatch Pet

![图片](https://mmbiz.qpic.cn/mmbiz_png/oghJwiaPb1CulRMCUjAxxbgVEo77rR5ugI4SfZkrenM7c1A2fH3Vp1olmtJVng2xhOcNhmdzRht4B6TrDIfDxza5IUol13DKtdIibR0fwAh4g/640?wx_fmt=png&from=appmsg&watermark=1&tp=webp&wxfrom=5&wx_lazy=1#imgIndex=0)

`hatch-pet` 表面上是 Codex 的一个“生成宠物”技能，但源码里真正有价值的不是“可爱”，而是它展示了 Codex Skills 的一种高级范式： **用 Skill 把模型生成、子代理并行、确定性脚本、QA、修复、打包、应用加载串成一个可复用工作流** 。它不是 prompt 包，也不是简单的 image generation wrapper，而是一个面向 Codex app 的 **animated pet asset pipeline** 。

先拆清楚两个概念： **Codex Pets** 是 Codex app 的宠物功能；官方文档说它是可选动画伙伴，可以在 `Settings → Appearance → Pets` 里选择内置宠物或刷新本地自定义宠物，也可以用 `/pet` 或命令面板唤醒/收起。这个 overlay 还会显示当前 active thread、Codex 是否运行中、等待输入或等待 review，本质上是一个轻量状态可视化层。 `hatch-pet` 则是生成自定义宠物资产的 Skill，官方文档给出的安装方式是 `$skill-installer hatch-pet` ，然后 Force Reload Skills，再用 `$hatch-pet create ...` 触发生成。

#### 简介

Codex Skills 机制本身定义得很明确：一个 Skill 是包含 `SKILL.md` 、可选 `scripts/` 、 `references/` 、 `assets/` 、 `agents/openai.yaml` 的目录；Codex 一开始只把 skill 的 name、description、路径放入上下文，只有当它决定使用这个 skill 时才读取完整 `SKILL.md` ，这叫渐进式披露（progressive disclosure），用来避免技能库把上下文撑爆。

OpenAI Skills \[4\] 主要分为内置和手动安装：

- `.system` 技能会随新版 Codex 自动安装。
- `.curated` 和 `.experimental` 技能则通过 `$skill-installer` 安装。

`hatch-pet` 归属于 `.curated` ，其目录结构是一个标准但偏高级的 Skill：

```
skills/.curated/hatch-pet/
├── LICENSE.txt                      # Apache-2.0 许可证
├── SKILL.md                         # Skill 主入口：定义触发条件、生成委托、执行边界、QA、修复与打包流程
├── agents/
│   └── openai.yaml                  # OpenAI/Codex interface 元数据：展示名、短描述、默认 prompt
├── references/
│   ├── animation-rows.md            # 动画行协议：定义 8x9 atlas 中每行状态、帧数与时长
│   ├── codex-pet-contract.md        # Codex Pet 资产契约：atlas 尺寸、网格、透明背景、pet.json 结构
│   └── qa-rubric.md                 # QA 验收标准：几何、角色一致性、sprite 风格、动画完整性、修复策略
└── scripts/
    ├── prepare_pet_run.py           # 初始化 pet run：生成目录、pet_request、prompts、layout guides、imagegen-jobs manifest
    ├── pet_job_status.py            # 读取 imagegen-jobs.json，输出 ready / blocked / complete job 状态和依赖信息
    ├── record_imagegen_result.py    # 摄取 $imagegen 输出：校验来源、复制到 decoded、记录 hash/provenance、写 canonical base
    ├── derive_running_left_from_running_right.py  # 条件满足时，将 running-right 精确水平镜像为 running-left，并记录 mirror_decision
    ├── extract_strip_frames.py      # 从 row strip 抽帧：移除 chroma key，优先按连通组件抽取，必要时按 slot 切分
    ├── inspect_frames.py            # 检查 frame QA：尺寸、透明像素、边缘残留、chroma-adjacent 像素、抽取方式等
    ├── compose_atlas.py             # 从 frames 或已有 atlas 组装/规范化最终 8x9 spritesheet
    ├── validate_atlas.py            # 验证 atlas：尺寸、格式、alpha、used cell、unused cell、近乎全不透明背景等
    ├── make_contact_sheet.py        # 生成带标签的 contact sheet，方便检查每一行动画和未使用 cell
    ├── render_animation_videos.py   # 用 ffmpeg 从 atlas 渲染各状态动画预览视频
    ├── render_animation_videos.sh   # render_animation_videos.py 的 Bash 包装入口
    ├── package_custom_pet.py        # 将验证后的 spritesheet 打包为本地 Codex pet：写 pet.json 和 spritesheet.webp
    ├── queue_pet_repairs.py         # 根据 qa/review.json 重新打开失败 row job，归档旧输出，并追加 repair prompt note
    ├── generate_pet_images.py       # 二级 fallback：当 $imagegen 不可用时，通过 OpenAI Images API 生成 base/row strips
    └── finalize_pet_run.py          # 总收口脚本：校验 job 完成与 provenance，抽帧、检查、拼 atlas、验证、出 QA、渲染视频、打包
```

这意味着 `hatch-pet` 的本质不是“宠物生成器”，而是一个 **Codex-compatible animated pet packaging workflow** 。它最终要产出的不是一张好看的图，而是：

```
${CODEX_HOME:-$HOME/.codex}/pets/<pet-name>/
├── pet.json
└── spritesheet.webp
```

其中 `pet.json` 描述 id、displayName、description、spritesheetPath， `spritesheet.webp` 是 Codex app 能按固定背景位置读取的精灵图。 `references/codex-pet-contract.md` 明确规定 atlas 格式为 PNG/WebP，尺寸 `1536x1872` ，网格 `8 columns x 9 rows` ，每格 `192x208` ，背景透明，未使用格必须完全透明；app 的 webview 动画通过固定行列数和 CSS background position 读取。

#### 使用方式

操作很简单：先在 Codex app 中执行 `$skill-installer hatch-pet` 安装这个 Skill；安装完成后，按 `Cmd + K` （macOS）或 `Ctrl + K` （Windows/Linux）打开命令菜单，搜索并执行 `Force Reload Skills` ，让 Codex 重新扫描本地 Skills。刷新完成后，就可以在输入框中调用：

```
$hatch-pet create a new pet inspired by my recent projects
```

这不是普通 shell 命令意义上的 `$hatch-pet` ，而是 Codex skill invocation。Codex Skills 支持显式调用和隐式调用：CLI/IDE 中可以用 `/skills` 或输入 `$` mention skill；如果任务和 skill description 匹配，Codex 也可以隐式选择技能。

如果你不给名字， `SKILL.md` 要求它从 concept、reference filename 或 personality 推断一个短名字；不给描述，则从 concept/reference 推断；不给 reference，则先通过文本生成 base pet，再把 base 作为后续所有动画行的 canonical reference。

社区并没有只把 Codex Pets 当成卖萌装饰，很多人第一时间看到了它的状态提示价值：可以把 active thread、运行中、等待输入、等待 review 这些枯燥状态，翻译成一个更自然、更低打扰的可视化反馈。这也和官方文档对 overlay 的描述对得上——宠物不是 UI 彩蛋，而是 Agent 状态的一层情绪化外壳。

#### 资产协议

为什么是 8x9 atlas，而不是随便一堆 GIF？

`references/animation-rows.md` 是这个 Skill 的资产契约核心。它规定 Codex app 读取一个固定 atlas：8 列 9 行、每格 `192x208` 。9 行分别是：

```
0 idle           6 frames
1 running-right  8 frames
2 running-left   8 frames
3 waving         4 frames
4 jumping        5 frames
5 failed         8 frames
6 waiting        6 frames
7 running        6 frames
8 review         6 frames
```

未使用的 cell 必须完全透明。每行还带有语义： `idle` 是呼吸/眨眼， `running-right` 是向右跑， `failed` 是失败/沮丧反应， `review` 是专注检查状态。

这点很关键。它说明 `hatch-pet` 不是在生成“角色形象”，而是在生成一个 **状态机可消费的动画表** 。Codex app 需要把 agent state 映射成宠物动作，所以每一行动画都要有稳定语义。比如：

```
agent idle      -> idle row
agent running   -> running / running-right / running-left row
agent waiting   -> waiting row
agent failed    -> failed row
agent reviewing -> review row
```

这就是为什么源码里反复强调：不能接受“看起来不错但状态不清”的图。一个漂亮的宠物插画不等于可用的 pet asset。对于 app 来说，可用性来自固定尺寸、固定行列、透明背景、动作语义、循环完整度和身份一致性。

#### SKILL.md 核心设计

把不可控图像生成关进工程边界

`SKILL.md` 最值得看的部分是 Generation Delegation。它规定所有正常视觉生成都要委托给 `$imagegen` ，不能直接调用 Image API；本 skill 自己的脚本只做确定性工作：准备 prompts/manifests、摄取 imagegen 输出、抽帧、验证、拼 atlas、生成 QA media、打包。

这句话背后有个很强的架构边界：

- **非确定性部分** ：$imagegen 负责
- **确定性部分** ：hatch-pet scripts 负责

也就是说，模型可以生成视觉内容，但不能自己“假装完成生产”。 `SKILL.md` 明确禁止用本地 Python/Pillow、SVG、canvas、HTML/CSS 或脚本去画、拼、变形、伪造宠物视觉；普通流程最多 10 个视觉生成任务：1 个 base pet + 9 个 row strip。唯一特例是 `running-left` ，可以在 `running-right` 已生成、已视觉检查、并确认适合镜像后由脚本水平镜像得到。

这就是为何说它不是 prompt 包的原因。它内置了 **反作弊/反幻觉边界** ：

- 不能手改 imagegen-jobs.json 标记完成
- 不能复制 run/tmp/decoded 中的本地文件冒充生成结果
- 不能写 helper script 填充 row outputs
- 必须用 record\_imagegen\_result.py 记录真实 $imagegen 输出
- row job 必须带 grounding images
- base job 才允许 prompt-only

从 agent 工程角度看，这是一种非常成熟的 skill 写法：它不相信模型“说完成了”，只相信文件、hash、manifest、QA 结果和可检查产物。

#### Prompt 策略

不是“更好看”，而是“更像 Codex digital pet”

`hatch-pet` 的美术风格也写得非常具体。默认风格是 Codex app 内置 digital pets：小型 pixel-art-adjacent mascot，compact chibi proportions，chunky silhouette，1–2px 深色描边，stepped/pixel edges，有限色板，flat cel shading，简单表情，小四肢。它明确禁止 polished illustration、painterly rendering、anime key art、3D render、glossy app icon、realistic fur、soft gradients、高细节抗锯齿等。

这段不是审美偏好，而是工程约束。因为最终 cell 只有 `192x208` ，高细节会在小尺寸下糊成噪声；柔光、阴影、半透明效果会破坏 chroma key / alpha extraction；复杂饰品会导致行间身份漂移。

它还对透明背景和 effects 做了极细规则：允许的效果必须和宠物轮廓接触或重叠，必须在同一 frame slot 内，必须 opaque、hard-edged、pixel-style，且不能用 chroma-key 邻近色；禁止 wave marks、motion arcs、speed lines、afterimages、blur、detached stars、floating punctuation、shadows、glows、speech bubbles、UI panels、checkerboard transparency 等。

这说明 `hatch-pet` 的 prompt 不是“增强生成质量”，而是在压缩生成空间：减少图像模型最爱犯的花活，把输出限制到 sprite production contract 里。

#### 编排起点

`prepare_pet_run.py` 的职责是创建一次 pet run 的工作目录、prompt 文件和 `imagegen-jobs.json` 。它内置 atlas 参数：8 列 9 行、cell `192x208` ，并定义全部动画行： `idle` 、 `running-right` 、 `running-left` 、 `waving` 、 `jumping` 、 `failed` 、 `waiting` 、 `running` 、 `review` 。

它会做几件关键事：

1. 推断 pet name / pet id / description / pet notes
2. 复制 reference images 到 run/references
3. 自动选择 chroma key
4. 生成 layout guide images
5. 写 pet\_request.json
6. 写 prompts/base-pet.md
7. 写 prompts/rows/.md
8. 写 imagegen-jobs.json

最有意思的是 chroma key 选择。脚本不是固定用绿色，而是从候选色中选择和参考图像像素距离较远的颜色，候选包括 magenta、cyan、yellow、blue、orange、green。也就是说，它提前规避“宠物本体颜色被背景抠掉”的问题。 `SKILL.md` 也明确要求使用 `pet_request.json` 中存储的 chroma key，不要强行固定 green screen。

另一个关键点是 layout guide。每个 row job 都会带一个对应状态的 layout guide，用作 frame count、spacing、centering、安全边距的视觉参考；但 prompt 又要求不能把 guide 的框线、标记、颜色复制到最终图像里。以失败态为例，大概长这样：

#### 用 manifest 约束生成

`prepare_pet_run.py` 生成的 job manifest（ `imagegen-jobs.json` ）是这个 Skill 的控制中心。它先创建一个 `base` job，然后为每个 state 创建 row-strip job。base job 可以在没有 reference 时 prompt-only；但 row-strip job 都要求 grounded generation，必须附带 canonical base、decoded/base、layout guide，以及原始 reference。

`running-left` 是特殊 job：它依赖 `base` 和 `running-right` ，并带有 mirror policy。只有当 `running-right` 视觉上足够对称，镜像不会破坏身份、道具方向、左右手、标记、文字、光照和方向语义时，才允许由 `derive_running_left_from_running_right.py` 镜像生成；否则必须作为普通 row 重新通过 `$imagegen` 生成。

这里非常工程化。它不是让模型在脑子里“记住流程”，而是把流程固化成 manifest：

```
{
  "id": "running-left",
  "kind": "row-strip",
  "depends_on": ["base","running-right"],
  "generation_skill": "$imagegen",
  "requires_grounded_generation": true,
  "allow_prompt_only_generation": false,
  "mirror_policy": {
    "may_derive_from": "running-right",
    "derivation": "horizontal-mirror",
    "requires_explicit_approval": true
  }
}
```

这就是 Harness 思维（ [深度解析：Harness Engineering](https://mp.weixin.qq.com/s?__biz=MzIzNjE2NTI3NQ==&mid=2247491737&idx=1&sn=7540894e1d73a1cf20da8e34ba421634&scene=21#wechat_redirect) ）：模型只负责选择下一步和执行局部任务，状态、依赖、边界、验收由外部结构保存。

📌 imagegen-jobs.json

这份 JSON 本质上是一次 `hatch-pet` 生成任务的 **Job Manifest** ，也就是运行清单。顶层字段负责描述本次 run 的基本信息： `schema_version` 表示结构版本， `created_at` 表示创建时间， `run_dir` 指向工作目录， `primary_generation_skill` 记录主要生成能力，例如 `$imagegen` 。真正的核心是 `jobs` 数组：每个 job 都是一个可独立追踪的任务单元，例如 `base` 、 `idle` 、 `running-right` 、 `jumping` 、 `review` 。这些 job 通过 `prompt_file` 、 `input_images` 、 `output_path` 、 `depends_on` 、 `parallelizable_after` 等字段，描述自己使用什么 prompt、依赖哪些参考图、产物写到哪里、必须等待哪些任务完成，以及何时可以并行执行。

以下是结构化后 JSON，方便展示此 manifest 设计：

```
{
  "schema_version": 1,
  "created_at": "ISO-8601 timestamp",
  "run_dir": "absolute-or-relative-run-directory",
  "primary_generation_skill": "skill-or-tool-name",

  "jobs": [
    {
      "id": "job-id",
      "kind": "job-type",
      "status": "pending | complete",

      "prompt_file": "path/to/prompt.md",
      "input_images": [
        {
          "path": "path/to/input.png",
          "role": "why this input is used"
        }
      ],

      "output_path": "path/to/output.png",
      "depends_on": ["dependency-job-id"],
      "parallelizable_after": ["dependency-job-id"],

      "generation_skill": "skill-or-tool-name",
      "requires_grounded_generation": true,
      "allow_prompt_only_generation": false,

      "identity_reference_paths": [
        "path/to/canonical-reference.png"
      ],

      "mirror_policy": {
        "may_derive_from": "source-job-id",
        "derivation": "horizontal-mirror",
        "requires_explicit_approval": true,
        "fallback_generation_skill": "skill-or-tool-name"
      },

      "recording_owner": "parent",
      "source_path": "path/to/generated-source.png",
      "source_provenance": "source-provider-or-method",
      "source_sha256": "sha256-of-source",
      "output_sha256": "sha256-of-recorded-output",
      "completed_at": "ISO-8601 timestamp",

      "metadata": {
        "width":0,
        "height":0,
        "mode":"RGB | RGBA",
        "format":"PNG | WEBP"
      }
    }
  ],

  "canonical_identity_reference": {
    "path": "path/to/canonical-reference.png",
    "source_job": "job-id",
    "sha256": "sha256-of-reference",
    "metadata": {
      "width": 0,
      "height": 0,
      "mode": "RGB | RGBA",
      "format": "PNG | WEBP"
    }
  }
}
```

这套结构的重点不只是“记录结果”，而是把生成过程变成一张可编排、可验证、可修复的任务图。 `generation_skill` 、 `requires_grounded_generation` 、 `allow_prompt_only_generation` 、 `identity_reference_paths` 用来约束生成方式，避免后续动画行只靠 prompt 发散； `source_path` 、 `source_provenance` 、 `source_sha256` 、 `output_sha256` 、 `completed_at` 和 `metadata` 用来记录来源与校验信息，保证产物可追溯； `mirror_policy` 则表达特殊派生规则，比如 `running-left` 是否可以从 `running-right` 镜像得到。需要注意的是，manifest 中持久化的 job `status` 主要是 `pending` 和 `complete` ； `blocked` 是 `pet_job_status.py` 根据依赖缺失派生出来的视图概念， `failed` 则通常体现在 QA/review 结果或 repair 流程里，而不是常规 manifest status。最后的 `canonical_identity_reference` 是全局身份锚点，通常来自 `base` job，用来保证所有动画行仍然是同一只宠物。

#### 子代理设计

并行生成，但父代理独占写权限

`hatch-pet` 要求在 base job 记录完成、 `references/canonical-base.png` 存在后，row-strip visual generation 必须使用 subagents，除非用户明确说不要。父代理负责准备 run、生成并记录 base、查看 job status、先派发 `idle` 和 `running-right` ，再决定 `running-left` 是否镜像，之后派发剩余 row jobs。

这和 Codex Subagents 的官方能力对得上：Codex 可以生成 specialized agents 并行执行任务，然后收集结果；这种模式适合复杂且高度并行的任务，但会消耗更多 tokens。官方文档也说，Codex 负责 spawn、routing、waiting、closing agent threads，并且 subagents 继承当前 sandbox policy。

`hatch-pet` 的关键不是“用了子代理”，而是它定义了非常严格的写边界：

```
Subagent 可以：
- 读取 row prompt
- 调用 $imagegen
- 检查候选图
- 返回 selected_source 和 qa_note

Subagent 不可以：
- 修改 imagegen-jobs.json
- 拷贝文件进 decoded/
- 执行 record_imagegen_result.py
- 镜像 running-left
- finalize
- repair
- package
```

父代理独占 manifest 和 package 写入。这避免了并行写冲突、来源混乱和 provenance 污染。对于 agent 系统来说，这是非常值得借鉴的模式： **并行任务可以分发，状态提交必须集中** 。

#### 资产溯源

从“生成了图”到“可追溯资产”

图像生成完成后，不能直接把图片丢进最终目录。必须运行：

```
python "$SKILL_DIR/scripts/record_imagegen_result.py" \
  --run-dir /absolute/path/to/run \
  --job-id <job-id> \
  --source /absolute/path/to/generated-output.png
```

这个脚本会检查 job 依赖是否完成、要求的 grounding images 是否存在，然后把 source copy 到 job 的 `output_path` ，记录 `source_path` 、 `source_provenance` 、 `source_sha256` 、 `output_sha256` 、metadata、completed\_at。base job 还会额外复制出 `references/canonical-base.png` ，并写入 `pet_request.json` 和 manifest。

这一步非常重要。它把“模型给了我一张图”转换为“这张图是哪个 job 的产物、从哪里来、hash 是什么、是否满足依赖”的可审计记录。

`finalize_pet_run.py` 后续还会验证这些 hash。如果 job 缺少 `source_sha256` ，它会报错并提示必须用 `record_imagegen_result.py` ，而不是手改 `imagegen-jobs.json` 。如果 decoded output 和 source hash 不一致，也会报错，提示不要本地改写 decoded visual outputs。

这就是 anti-hallucination 的硬约束：模型不能靠“我已经处理好了”过关，必须留下可验证的 provenance。

#### 打包链路

从 row strips 到最终宠物包

当所有 imagegen jobs 都 complete 后，最终执行：

```
python "$SKILL_DIR/scripts/finalize_pet_run.py" \
  --run-dir /absolute/path/to/run
```

`finalize_pet_run.py` 的流程大致是：

1. 读取 pet\_request.json
2. 检查 imagegen-jobs.json 中所有 job 都已 complete
3. 验证每个 job 的 source provenance 和 hash
4. extract\_strip\_frames.py 抽帧
5. inspect\_frames.py 检查每帧
6. compose\_atlas.py 拼 spritesheet.png / spritesheet.webp
7. validate\_atlas.py 验证最终 atlas
8. make\_contact\_sheet.py 生成 QA contact sheet
9. render\_animation\_videos.py 生成 preview videos
10. package\_custom\_pet.py 打包到 ${CODEX\_HOME:-$HOME/.codex}/pets/ ，或通过 --package-dir 指定目录
11. 写 qa/run-summary.json

源码里可以看到，finalize 会先 `require_complete_jobs` ，不完整就提示用 `pet_job_status.py` 继续完成；然后执行 `extract_strip_frames.py` 、 `inspect_frames.py` ，如果 review 失败，会输出 `repair_hint` ：运行 `queue_pet_repairs.py` ，重新生成 reopened row jobs，再 finalize。通过后才 compose atlas、validate、生成 contact sheet、videos，并 package。

这是一条完整的生产链，而不是单轮生成。它天然支持失败、修复、重跑、验收。

#### QA 策略

确定性 QA 只检查“结构”，不检查“好不好看”

`validate_atlas.py` 检查的是最终 spritesheet 的工程正确性：尺寸必须是 `1536x1872` ，格式必须是 PNG 或 WebP，除非显式 allow，否则必须有 alpha channel；它逐个 cell 统计 alpha 非零像素，used cell 太稀疏会报错，unused cell 非透明会报错，used cell 近似全 opaque 会被视为背景没抠干净。

但 `SKILL.md` 反复强调：deterministic validation necessary but not sufficient。即使 `qa/review.json` 和 `final/validation.json` 没错误，也必须人工/视觉检查 contact sheet，确认没有 identity drift：不能换物种、换体型、换脸、换标记、换调色板、换道具设计、换轮廓。

这点非常专业。自动 QA 可以证明尺寸、透明、帧数、空格、alpha；但它不能证明“这还是同一只宠物”。所以 `hatch-pet` 把验收拆成两层：

- **结构正确性** ：脚本检查
- **视觉一致性** ：模型/人类视觉检查

这和真实生产系统很像：schema validation 只能证明数据形状正确，不能证明语义正确。

#### Repair Workflow

不是重来，而是最小失败范围修复

如果 finalization 因 row QA 失败而停止， `SKILL.md` 要求运行：

```
python "$SKILL_DIR/scripts/queue_pet_repairs.py" \
  --run-dir /absolute/path/to/run
```

然后只重新生成 reopened row job。它明确要求 regenerate the smallest failing scope：失败的是某一行，就修这一行，不要重做整张 sheet。对于 identity repairs，要用 canonical base、original references、contact sheet、exact row failure note 作为 grounding context。

`qa-rubric.md` 也强调 repair policy：原则上先定位最小失败范围，只有 identity 或 layout 广泛损坏时才 full atlas regeneration；而当前自动化生产路径里， `queue_pet_repairs.py` 会按失败 row 重新打开整行动画 job，并在 repair note 中要求重生成整行，而不是只修某一帧。

这又是一个高级点：它不是“生成失败就重新 prompt 一遍”，而是把失败局部化。对图像生成这种高成本、不稳定任务来说，局部修复比整体重跑更可控。

#### Secondary fallback

有 API fallback，但不是默认路径

`scripts/generate_pet_images.py` 是 secondary fallback。 `SKILL.md` 写得很清楚：只有当已安装的 `$imagegen` system skill 不可用或当前环境不能调用时，才使用这个 fallback；普通宠物创建应该委托给 `$imagegen` ，因为 `$imagegen` 拥有 built-in-first image generation policy 和 CLI fallback 行为。fallback 需要 `OPENAI_API_KEY` ，并可用 `--model gpt-image-2 --states all` 执行。

这体现了另一个边界： `hatch-pet` 不想自己接管所有图像生成策略。它只定义宠物生产协议；视觉生成策略交给系统级 `$imagegen` 。这是一种 skill composition：

```
hatch-pet  = domain workflow
$imagegen  = visual generation capability
scripts    = deterministic asset compiler
```

这比把所有东西塞进一个巨型脚本更干净。

#### Skills 高级范式

`hatch-pet` 最值得学习的不是“怎么做宠物”，而是它展示了一个成熟 Skill 应该如何写。

- **description 是路由入口** 。Codex 初始上下文里只有 skill name、description、path，所以 description 必须精准说明何时触发。 `hatch-pet` 的 description 一开始就写：create、repair、validate、preview、package Codex-compatible animated pet spritesheets，并列出 8x9 atlas、transparent unused cells、row-by-row animation prompts、QA contact sheets、preview videos、pet.json packaging。这个 description 不是营销文案，是 router spec。
- **SKILL.md 是操作系统级 workflow contract** 。它规定谁能生成、谁能写 manifest、什么时候用 subagents、什么时候必须停止、哪些行为禁止、什么算验收。它不是“建议模型这样做”，而是在给 agent 建立行为边界。
- **scripts 是确定性编译器** 。视觉内容来自模型，但资产结构不能靠模型猜。抽帧、拼 atlas、透明验证、hash、package 都由脚本完成。这种组合非常适合 Agent：模型处理语义，脚本处理确定性。
- **references 是协议文档** 。 `animation-rows.md` 规定动画状态， `codex-pet-contract.md` 规定 app 消费格式， `qa-rubric.md` 规定验收标准。它们不是给用户看的说明书，而是给 agent 和脚本共享的生产契约。
- **subagents 并行但不共享写权限** 。这点尤其值得用于自己的 AgentOS 架构：并行子代理可以做探索、生成、候选筛选，但统一状态、审计、manifest、package 必须由父控制面写入。

#### 局限性

`hatch-pet` 的源码也暴露出几个天然限制。

它依赖 `$imagegen` 的视觉稳定性。Skill 通过 base canonical reference、layout guide、row prompt、QA 修复降低漂移，但无法从根上保证所有动画行完全一致。所以它才要求 contact sheet 视觉检查，并把 identity drift 视为 blocker。

它生成的是固定格式资产，不是任意动画系统。8x9、192x208、固定 row state 是 Codex app 的消费协议。你可以把这个思路移植到别的 app，但不能假设 `spritesheet.webp` 直接适配任意 UI。

它的 QA 仍然有语义空洞。 `validate_atlas.py` 能检查 alpha、尺寸、空 cell、近似 opaque，但不能判断 “review 状态是否真的像 review”、“failed 是否太夸张”、“running-left 镜像是否破坏角色设定”。这部分仍然依赖视觉检查和模型判断。

它的子代理要求会增加成本。官方 Subagents 文档也说明，子代理各自执行模型和工具工作，会比单代理消耗更多 tokens。 `hatch-pet` 选择子代理，是因为 9 行动画天然并行；但如果只是小修一行，顺序执行可能更便宜。

#### Agent 工程启发

如果只把 `hatch-pet` 看成“一个会画宠物的 Skill”，就会低估它真正展示的东西。它更像一个缩小版 Agent 生产系统：把用户一句模糊的创意请求，转换成一条有输入规范、任务图、来源证明、确定性编译、QA、修复和最终打包的资产流水线。

真正的 Skill 不是“提示词模板”，而是把一个领域的隐性经验、失败边界和产物协议，编译成 Agent 可以执行、可以恢复、可以验收的生产流程。

这也是 `hatch-pet` 和普通 prompt wrapper 的根本差别。普通 prompt wrapper 往往只是告诉模型“你要怎么想、怎么写、怎么生成”； `hatch-pet` 则先定义产物是什么，再定义生成过程如何受控。它不满足于“画一只好看的宠物”，而是要求最后产出一个 Codex app 能加载的 animated pet package。美术只是其中一个环节，真正的目标是一个符合协议的 artifact。

从这个角度看， `hatch-pet` 的核心链路可以抽象成：

```
intent
-> request
-> job manifest
-> generated candidates
-> recorded provenance
-> compiled artifact
-> QA result
-> targeted repair
-> packaged asset
```

这条链路给 Agent 工程的几层启发：

- **不要把模型输出直接当成果，而要把它当生产材料** 。模型可以生成 base pet，可以生成 row strip，可以判断某个候选是否更好；但这些输出都只是材料。只有经过 `record_imagegen_result.py` 记录来源、经过脚本抽帧和拼 atlas、经过 `validate_atlas.py` 和 contact sheet 检查、再经过 `package_custom_pet.py` 打包之后，它才变成最终资产。换句话说，模型是 creative worker，不是 trusted committer。
- **关键状态不能藏在上下文里，必须外部化成 manifest** 。长任务里的对话上下文会压缩、会遗忘、会被新的推理覆盖； `imagegen-jobs.json` 不会。它把 job 的依赖、输入、输出、来源、派生规则、记录者和完成状态写成可检查结构，让任务可以恢复、可以 diff、可以被另一个脚本重新验证。对 AgentOS 来说，这比“让模型记住自己做到哪一步”可靠得多。凡是需要跨步骤、跨代理、跨失败恢复的任务，都应该有类似的外部状态机，而不是只依赖 prompt 里的计划。
- **多代理的关键不是并行，而是提交权隔离** 。 `hatch-pet` 让 subagents 生成动画行，是因为 row strips 天然可以并行；但它更重要的设计是写边界。子代理可以读 prompt、调用 `$imagegen` 、挑选 source、写 QA note，却不能改 manifest、不能 copy 到 decoded、不能 record、不能 mirror、不能 finalize、不能 package。父代理才是 control plane，子代理只是 worker plane。这个模式值得抽象成一条规则：并行任务可以分发，truth commit 必须集中。
- **QA 要承认结构正确和语义正确不是一回事** 。脚本能检查尺寸、alpha、空 cell、帧数、hash、透明背景，但不能证明“这还是同一只宠物”，也不能证明 review 状态真的像 review。 `hatch-pet` 没有假装脚本能解决一切，而是把自动 QA 和视觉检查拆开。这个分层非常重要。很多 Agent 系统只做 schema validation，然后误以为任务完成；但真实生产里，schema correct 只是底线，semantic correct 才是用户真正关心的结果。
- **repair 比 retry 更像工程** 。失败后重新生成一整套资产当然简单，但成本高、漂移大，也容易把原本好的部分重新破坏。 `hatch-pet` 的方式是定位失败 row，归档旧输出，追加 repair note，重开对应 job，再重新 finalize。它承认模型生成有波动，但用流程把波动限制在最小失败范围内。这个思想可以迁移到代码、UI、文档、测试、知识库等任务：成熟 Agent 不应该只会 retry，而应该知道失败在哪里、修复边界在哪里、如何保留已经通过验收的部分。

所以，对 AgentOS / control plane 方向来说， `hatch-pet` 的启发不是“给 Agent 加一个宠物功能”，而是展示了一种更普适的构造方法：

```
让模型生成候选
让 manifest 保存状态
让脚本编译产物
让 QA 切分结构与语义
让 repair 局部收敛
让 control plane 统一提交
```

这比单纯给 Agent 更多 prompt 更重要。prompt 可以提升一次回答的质量，但协议、manifest、provenance、编译器和 QA 才能提升一个系统的稳定性。 `hatch-pet` 做的是动画宠物，但它真正示范的是如何把不可控的模型能力，接进一个可控的产物系统。

这也解释了为什么它和 vibe coding 并不矛盾。很多人把 vibe coding 理解成少约束、快生成、跟着感觉走；但 `hatch-pet` 展示的是更成熟的版本：创意层开放，协议层收紧，提交层验证，失败层可修。只有底层边界足够硬，上层创意才敢流动。否则所谓 vibe 只是一次灵感截图；有了产物协议和验收链路，它才会变成一个真的能被应用加载、复用和长期维护的 artifact。

#### Codex /goal 命令

Codex v0.128.0 是一次重要更新，核心变化是引入了更强的目标驱动执行机制。新增的 `/goal <objective>` 命令允许用户为 Codex 设置明确目标；当 agent 完成一轮执行后，如果用户没有继续输入，Codex 会自动注入提示，引导模型选择下一个具体动作继续推进。这个机制会将 goal 的需求映射到可验证证据上，例如文件变更、测试结果、PR 状态等；模型只能通过更新 goal 来标记任务完成。因此，它更像是一个内置的 Ralph loop++：不再停留于单轮响应，而是围绕目标持续执行、检查证据并推进任务，直到目标完成或 token 预算耗尽。goal 命令需要在配置中开启，默认不会显示，config.toml \[features\] 中新增 goals = true。

在源码中也有一些证据 codex-rs/goals \[5\] ，感兴趣的朋友自行了解。此命令一出，终于不用再给 codex 连续发送“继续”了...

## 通俗精炼（1）

### 2026-05-04 00:48:47

#### 深度解析：Codex Pet Skill 总结

##### 核心观点

文章借 Codex 的 `hatch-pet skill` 说明：真正有价值的 Skill 不是提示词包装、角色扮演或浅层 workflow，而是把领域经验、工具链、约束、验收标准、失败修复和交付流程封装成 Agent 可稳定执行的“工程协议”。

`hatch-pet` 表面是生成 Codex 电子宠物，实质是一个完整的动画资产生产流水线：从图像生成、任务编排、子代理并行、来源追踪、QA、局部修复到最终打包，全部被工程化约束。

---

##### 1. Skill 的本质：不是 Prompt，而是可执行协议

作者批评市面上很多所谓 Skills 只是：

- 几段角色扮演 prompt
- 名人/同事人格模仿
- 一键生成类 workflow 包装
- 看似炫酷但缺少工程边界的 demo

真正的 Skill 应该解决的是：如何把模型不可控的生成能力，放进一个可控、可验证、可恢复的生产系统中。

`hatch-pet` 的价值不在于“会画宠物”，而在于它定义了一个 Codex app 可消费的动画宠物资产协议。

---

##### 2. hatch-pet 是什么

`hatch-pet` 是 Codex 官方 curated Skill，用于生成自定义 Codex Pets。

它最终产出的是一个 Codex app 能加载的宠物包：

```text
~/.codex/pets/<pet-name>/
├── pet.json
└── spritesheet.webp
```

其中：

- `pet.json` 描述宠物 ID、名称、描述、spritesheet 路径
- `spritesheet.webp` 是固定规格的动画精灵图

所以它不是单纯生成图片，而是生成一个符合 Codex app 协议的 animated pet asset。

---

##### 3. 资产协议：固定 8x9 动画图集

Codex Pet 使用固定 atlas 格式：

- 尺寸：1536 x 1872
- 网格：8 列 x 9 行
- 单格：192 x 208
- 背景：透明
- 未使用 cell：必须完全透明

9 行分别对应不同状态：

| 行 | 状态 |
|---|---|
| 0 | idle |
| 1 | running-right |
| 2 | running-left |
| 3 | waving |
| 4 | jumping |
| 5 | failed |
| 6 | waiting |
| 7 | running |
| 8 | review |

这说明它生成的不是“好看的角色图”，而是一个可被状态机消费的动画表。

---

##### 4. 核心架构：非确定性交给模型，确定性交给脚本

`hatch-pet` 明确划分边界：

- 非确定性部分：由 `$imagegen` 负责视觉生成
- 确定性部分：由 scripts 负责抽帧、校验、拼图、打包、记录来源

它禁止模型用 Python、SVG、HTML/CSS 等方式伪造视觉结果，也禁止手改 manifest 标记完成。

这体现了一个关键原则：

> 模型可以生成材料，但不能直接成为可信提交者。

最终资产必须经过脚本处理、hash 校验、QA 验证和打包。

---

##### 5. Job Manifest：把状态外部化

`imagegen-jobs.json` 是整个生成流程的控制中心。

它记录：

- 每个 job 的 ID 和类型
- prompt 文件
- 输入图片
- 输出路径
- 依赖关系
- 是否允许并行
- 是否必须 grounded generation
- source provenance
- hash
- 完成状态

这让任务从“模型记在上下文里”变成“外部可恢复、可检查、可验证的任务图”。

对 Agent 工程来说，这是非常重要的设计：

> 长任务的状态不应该藏在对话上下文中，而应该沉淀为 manifest。

---

##### 6. 子代理设计：并行生成，但父代理统一提交

`hatch-pet` 会在 base pet 生成后，使用 subagents 并行生成各行动画。

但它严格限制子代理权限：

子代理可以：

- 读取 row prompt
- 调用 `$imagegen`
- 检查候选图
- 返回 source 和 QA note

子代理不可以：

- 修改 `imagegen-jobs.json`
- 拷贝文件到 decoded
- 执行 record
- 镜像 running-left
- finalize
- package

父代理统一负责写 manifest、记录 provenance、最终打包。

核心原则是：

> 并行任务可以分发，但 truth commit 必须集中。

---

##### 7. Provenance：从“生成了图”到“可审计资产”

每张图生成后，必须通过 `record_imagegen_result.py` 记录。

它会：

- 检查 job 依赖是否完成
- 检查 grounding images 是否存在
- 复制 source 到指定目录
- 记录 source path
- 记录 hash
- 写入 metadata
- 更新完成时间

如果缺少 hash 或 provenance，finalize 阶段会报错。

这是一种反幻觉机制：系统不相信“模型说完成了”，只相信文件、hash、manifest 和可验证产物。

---

##### 8. QA：结构正确与语义正确分层

`validate_atlas.py` 负责确定性校验：

- 尺寸是否正确
- 格式是否正确
- 是否有 alpha channel
- unused cell 是否透明
- used cell 是否过空
- 是否存在背景未抠干净问题

但作者强调：结构正确不等于语义正确。

自动 QA 无法判断：

- 是否还是同一只宠物
- review 是否真的像 review
- failed 是否表达失败
- running-left 镜像是否破坏角色设定

所以 `hatch-pet` 把 QA 分成两层：

- 结构 QA：脚本检查
- 语义 QA：模型/人工视觉检查

---

##### 9. Repair Workflow：最小范围修复，而不是全量重来

如果某一行动画失败，系统不会重做全部资产，而是通过 `queue_pet_repairs.py` 只重新打开失败 row job。

修复时会使用：

- canonical base
- 原始 references
- contact sheet
- 失败原因说明
- repair prompt note

这体现了成熟 Agent 系统的思路：

> 不要只会 retry，而要知道哪里失败、修哪里、保留已经通过验收的部分。

局部修复比整体重跑更稳定、更低成本，也更不容易引入新的漂移。

---

##### 10. hatch-pet 展示的高级 Skill 范式

作者总结出成熟 Skill 的几个特征：

###### description 是路由入口

Codex 初始只读取 skill name、description、path，所以 description 必须精准说明触发场景，而不是营销文案。

###### SKILL.md 是 workflow contract

它定义：

- 谁可以生成
- 谁可以写文件
- 什么时候用 subagents
- 哪些行为禁止
- 如何验收
- 如何修复

###### scripts 是确定性编译器

模型负责语义和生成，脚本负责结构化、验证和产物编译。

###### references 是协议文档

包括动画行协议、资产契约、QA 标准，是 Agent 和脚本共享的生产规则。

###### subagents 是 worker，父代理是 control plane

子代理可以并行执行，但最终状态提交必须由父代理统一控制。

---

##### 11. 对 Agent 工程的启发

`hatch-pet` 的通用链路可以抽象为：

```text
intent
-> request
-> job manifest
-> generated candidates
-> recorded provenance
-> compiled artifact
-> QA result
-> targeted repair
-> packaged asset
```

这对 AgentOS / control plane 设计有几条重要启发：

1. 模型输出只是生产材料，不是最终成果  
2. 关键状态必须外部化为 manifest  
3. 多代理并行时，提交权必须集中  
4. QA 要区分结构正确和语义正确  
5. repair 比 retry 更工程化  
6. 协议、provenance、编译器和 QA 比单纯 prompt 更重要  

---

##### 12. 局限性

`hatch-pet` 也有明显限制：

- 依赖 `$imagegen` 的视觉稳定性
- 无法彻底避免 identity drift
- 固定 8x9 atlas，只适配 Codex Pet 协议
- 自动 QA 无法覆盖语义判断
- 子代理并行会增加 token 成本

但这些限制并不影响它作为 Skill 工程范式的参考价值。

---

##### 13. Codex /goal 命令补充

文章最后提到 Codex v0.128.0 引入 `/goal &lt;objective>` 命令。

它可以让 Codex 围绕一个目标持续执行，在每轮任务后自动推进下一步，而不是等待用户反复输入“继续”。

该机制会把目标映射到可验证证据，例如：

- 文件变更
- 测试结果
- PR 状态

这意味着 Codex 正在从单轮响应式 Agent，走向更持续的目标驱动执行系统。

---

##### 总结

`hatch-pet` 真正值得学习的不是宠物功能，而是它展示了一种成熟 Agent Skill 的工程方法：

> 创意层开放，协议层收紧，提交层验证，失败层可修。

它把不可控的模型生成能力，接入了一个可控、可验证、可恢复、可交付的产物系统。

这才是 Skill 从“提示词玩具”走向“Agent 工程模块”的关键。

```text
用户意图
→ 请求规格
→ 任务 manifest
→ 模型生成候选
→ 记录 provenance
→ 确定性编译
→ 自动 QA
→ 语义检查
→ 局部修复
→ 最终打包
```

适用于：

- 代码生成
- UI 生成
- 文档生成
- 数据分析

> 模型输出只是原材料，只有经过协议化、验证化、可追溯化之后，才是生产资产。

---

###### 洞见 2：Agent 工程的关键不是“更复杂的 workflow”，而是“外部化状态 + 可验证任务图”

###### **核心观点：**  
> 长任务不能依赖模型记忆和对话上下文，关键状态必须外部化为 manifest，让任务可恢复、可检查、可修复、可交接。

hatch-pet 的 `imagegen-jobs.json` 不是简单记录表，而是一次生成任务的控制中心。它记录：

- 每个 job 的 id
- 输入图
- prompt 文件
- 输出路径
- 依赖关系
- 是否允许 prompt-only
- 是否需要 grounded generation
- 是否可以并行
- 是否可由其他 job 镜像派生
- source hash
- provenance
- completed_at
- metadata

这意味着系统不是靠模型说“我完成了”，而是靠 manifest 判断：

- 哪些 job ready
- 哪些 blocked
- 哪些 complete
- 哪些依赖缺失
- 哪些产物来源不可信
- 哪些需要 repair

**为什么重要：**  
Agent 长任务最大的问题不是不会做，而是：

- 容易忘
- 容易跳步
- 容易自我确认
- 容易在失败后重来
- 多代理协作时状态污染

manifest 把“任务进度”和“事实状态”从模型上下文中剥离出来，变成外部可检查对象。

**反常识之处：**  
很多人以为提升 Agent 能力靠更长上下文、更强模型、更复杂 prompt。  
文章真正强调的是：**上下文不是数据库，模型记忆不是状态机。**

**可迁移价值：**  
凡是满足以下条件的任务，都应该引入 manifest：

- 多步骤
- 多工具
- 多代理
- 有失败恢复
- 有中间产物
- 有最终验收
- 需要审计和复现

比如代码任务可以有：

```text
task-manifest.json
- files_to_change
- tests_to_run
- generated_files
- review_status
- failed_cases
- repair_scope
- provenance
```

数据分析可以有：

```text
analysis-manifest.json
- raw_data_sources
- cleaning_steps
- transformations
- charts
- assumptions
- validation_checks
- final_outputs
```

**我应该记住什么：**  
> 让模型推理，让 manifest 记忆。  
> 让模型行动，让外部状态机判断它行动到了哪里。

---

###### 洞见 3：多 Agent 协作的核心不是并行，而是“提交权隔离”

###### **核心观点：**  
> 子代理可以并行生成、探索、筛选候选，但 truth commit 必须由父代理集中控制。

hatch-pet 允许 subagents 并行生成动画行，但严格限制它们的权限。

子代理可以：

- 读取 row prompt
- 调用 `$imagegen`
- 检查候选图
- 返回 selected source
- 写 QA note

子代理不可以：

- 修改 `imagegen-jobs.json`
- 拷贝文件进 decoded
- 执行 `record_imagegen_result.py`
- 镜像 running-left
- finalize
- repair
- package

父代理独占：

- manifest 写入
- provenance 记录
- 最终打包
- 修复调度
- 状态提交

**为什么重要：**  
多 Agent 系统最大风险不是“并行不够”，而是：

- 谁有权改状态？
- 谁有权宣布完成？
- 谁有权写最终产物？
- 多个 Agent 的结果如何避免互相覆盖？
- provenance 谁负责？

hatch-pet 的设计相当清楚：  
**worker 可以产出候选，control plane 才能提交事实。**

**反常识之处：**  
大家谈多 Agent 常常兴奋于“多个智能体一起干活”。  
但真正工程化的问题是：**并行越多，越需要集中提交。**

**可迁移价值：**  
这是一个非常通用的组织/系统原则：

```text
探索权可以分散
提交权必须集中
```

适用于：

- 多人协作开发
- 多 Agent 编码
- 内容生产流水线
- 数据标注与审核
- 企业审批流程
- 自动化部署系统

类比软件工程：

- 分支可以多人开发
- merge 权限必须受控
- CI 通过不等于自动上线
- release 需要统一负责人

**我应该记住什么：**  
> 多 Agent 不是“大家都能写”，而是“大家都能做候选，只有控制面能提交真相”。

---

###### 洞见 4：QA 不能只验证结构正确，还必须承认语义正确无法完全自动化

###### **核心观点：**  
> 自动化 QA 可以验证尺寸、格式、透明度、hash、空 cell，但不能证明“这还是同一只宠物”或“这个状态语义正确”。

hatch-pet 把 QA 分为两层：

###### 结构正确性

由脚本验证：

- atlas 尺寸是否为 1536x1872
- 是否有 alpha channel
- used cell 是否太稀疏
- unused cell 是否完全透明
- 是否背景未抠干净
- hash 是否匹配
- 文件格式是否正确

###### 语义正确性

需要视觉检查：

- 是否 identity drift
- 是否换物种
- 是否换脸
- 是否换体型
- 是否换色板
- 是否动作语义不清
- review 状态是否真的像 review
- failed 状态是否合理
- running-left 镜像是否破坏设定

**为什么重要：**  
很多 AI 系统会犯一个错误：  
只要 JSON schema 正确、测试通过、格式没错，就认为任务完成。

但真实生产里经常是：

```text
结构正确 ≠ 语义正确
格式合格 ≠ 用户可用
测试通过 ≠ 产品成立
```

**反常识之处：**  
自动化越强，越容易误以为所有验收都能自动化。  
文章反而强调：**成熟系统要知道自动化验证的边界。**

**可迁移价值：**  
这对 AI 编程尤其重要：

- 单元测试通过，不代表架构合理
- 类型检查通过，不代表业务逻辑正确
- 页面能渲染，不代表用户体验合格
- 数据 pipeline 跑通，不代表结论可信
- 文档格式正确，不代表表达有效

更成熟的验收应该分层：

```text
Schema validation
→ Static checks
→ Runtime tests
→ Artifact inspection
→ Semantic review
→ User acceptance
```

**我应该记住什么：**  
> 自动 QA 证明底线，人类/模型视觉检查判断意义。  
> 不要用结构正确冒充语义正确。

---

###### 洞见 5：成熟的 Agent 不应该只会 retry，而应该会 repair

###### **核心观点：**  
> 失败后不要整体重来，而要定位最小失败范围，保留已通过部分，只修复失败局部。

hatch-pet 的 repair workflow 很有价值：

- 如果某一行动画失败
- 不重新生成整张 spritesheet
- 而是运行 `queue_pet_repairs.py`
- 归档旧输出
- 重开失败 row job
- 追加 repair note
- 使用 canonical base、原始 references、contact sheet 和失败原因作为 grounding context
- 重新 finalize

这是一种从“随机重试”到“工程修复”的转变。

**为什么重要：**  
AI 生成具有波动性。整体重跑会带来三个问题：

1. 成本高  
2. 已经正确的部分可能被破坏  
3. 输出风格和身份可能漂移更严重  

局部修复则把不确定性锁在最小范围内。

**反常识之处：**  
很多 AI 工作流的失败策略是“再生成一次”。  
文章展示的策略是：**不要 retry，要 repair；不要重来，要收敛。**

**可迁移价值：**  
用于代码生成：

```text
不要让 Agent 重写整个模块
只修 failing test 对应函数
```

用于 UI 生成：

```text
不要重做整个页面
只修 layout overflow 的组件
```

用于文档生成：

```text
不要重写全文
只修逻辑断裂的章节
```

用于数据分析：

```text
不要重跑全流程
只修清洗错误或异常字段
```

**我应该记住什么：**  
> Retry 是抽奖，repair 是工程。  
> 高级 Agent 的标志，是知道失败在哪里，以及修到哪里为止。

---

##### 3. 底层逻辑

###### **逻辑一：非确定性能力必须被确定性边界包裹**

- **表层现象：**  
  hatch-pet 用 `$imagegen` 生成宠物图像，但大量脚本负责抽帧、验证、拼接、打包、记录 hash。

- **深层原因：**  
  图像模型擅长生成视觉内容，但不擅长稳定遵守尺寸、透明度、帧位、资产协议、状态语义和文件溯源。  
  所以系统必须把生成能力限制在“候选材料”层，把最终资产生产交给确定性流程。

- **推导结论：**  
  AI 应用的可靠性不来自“完全相信模型”，而来自：

  ```text
  模型负责开放生成
  脚本负责确定性编译
  manifest 负责状态记忆
  QA 负责验收
  repair 负责收敛
  ```

---

###### **逻辑二：产物协议决定生成策略，而不是 prompt 美学决定最终质量**

- **表层现象：**  
  hatch-pet 严格规定 pixel-art-adjacent 风格，禁止 painterly、3D、glossy、soft gradients、复杂光影和漂浮特效。

- **深层原因：**  
  这些不是审美偏好，而是由最终消费场景决定的工程约束：

  - cell 只有 192x208
  - 高细节会糊成噪声
  - 柔光半透明会影响抠图
  - 复杂装饰会导致身份漂移
  - 浮动特效会破坏 frame slot
  - 状态动画需要清晰可读

- **推导结论：**  
  好的生成提示不是追求“更好看”，而是压缩生成空间，使输出更符合产物协议。  
  在生产系统里，prompt 的目标不是释放模型，而是约束模型。

---

###### **逻辑三：长任务可靠性的核心是“状态外部化”和“提交权集中化”**

- **表层现象：**  
  hatch-pet 用 `imagegen-jobs.json` 记录任务图，并且只允许父代理写 manifest 和 package。

- **深层原因：**  
  对话上下文会遗忘、压缩、漂移；多个子代理并行时会产生状态冲突和 provenance 混乱。  
  因此，系统需要一个外部 truth source，并由 control plane 统一提交。

- **推导结论：**  
  多 Agent 系统的基本架构应是：

  ```text
  worker plane：生成、探索、评估候选
  control plane：记录、验证、提交、打包
  ```

  并行提升效率，集中提交保障可信度。

---

##### 4. 反常识清单

| 反常识观点 | 常见认知 | 文章的不同判断 | 启发 |
|---|---|---|---|
| Skill 不是 prompt 包，而是可执行协议 | 会写 `SKILL.md`、会写 instructions 就是 Skill | 真正的 Skill 要包含产物契约、工具链、失败处理、QA、修复和打包流程 | 不要包装 prompt，要沉淀领域生产协议 |
| 模型输出不是成果，只是材料 | AI 生成了一张图/一段代码，就算完成 | 只有经过 provenance、hash、验证、编译、打包后才是可信产物 | 把模型当 creative worker，不要当 trusted committer |
| 更强 Agent 不等于更复杂 workflow | 复杂任务应该画成 n8n/Zapier 式固定流程图 | 当任务需要上下文理解、动态决策、局部修复时，固定流程图会变脆；Skill 更适合封装可组合执行单元 | 确定链路用 workflow，不确定任务用协议化 Skill |
| 多 Agent 的重点不是并行，而是提交权隔离 | 多个 Agent 一起干活就能提升效率 | 子代理可以生成候选，但不能写 manifest、不能 finalize、不能 package | 分散探索，集中提交 |
| QA 通过不代表语义正确 | 自动检查没报错就是完成 | 脚本只能验证结构，不能保证身份一致、动作语义和审美可用性 | 验收要区分结构正确与语义正确 |
| 失败后不应默认 retry，而应局部 repair | 生成失败就重新生成一遍 | 定位最小失败范围，只重开失败 row job，保留已通过部分 | 成熟 Agent 要会收敛，而不是反复抽奖 |
| Prompt 的目标不是让模型更自由，而是压缩生成空间 | 好 prompt 应该激发模型创造力 | 生产型 prompt 要限制风格、尺寸、背景、特效、动作语义，减少模型花活 | 创意层开放，协议层收紧 |
| 宠物 UI 不是彩蛋，而是 Agent 状态可视化层 | Codex Pets 只是卖萌装饰 | 它把 running、waiting、failed、review 等状态转成低打扰的情绪化反馈 | 好的状态反馈不一定是仪表盘，也可以是环境化、情绪化界面 |
| 外部 manifest 比长上下文更可靠 | 给模型更多上下文，它就能记住进度 | 上下文会遗忘和压缩，manifest 才是可恢复、可 diff、可验证的任务状态 | 长任务必须外部化状态 |
| 产物协议先于生成过程 | 先让 AI 生成好东西，再看怎么用 | 先定义 app 如何消费资产，再倒推生成、QA 和打包流程 | 真正的 AI 产品应从 artifact contract 开始设计 |

## 结构化（1）

### 2026-05-04 08:13:55

#### 《深度解析：Codex Pet Skill》精炼总结

本文通过拆解 OpenAI Codex 的 `hatch-pet` Skill，说明真正有价值的 Skill 不是角色扮演 prompt，也不是简单 workflow 包装，而是把领域经验、工具链、约束、QA、修复和交付流程封装成 Agent 可稳定执行的工程协议。  
`hatch-pet` 表面是“生成电子宠物”，本质上展示了一套完整的 Agent 资产生产流水线：生成、并行、溯源、验证、修复、打包全部可控。

---

##### 1. 序言：Skill 不应退化成“提示词玩具”

作者批评当前很多所谓 Skill 只是“人格模仿”“一键生成 PPT”“复刻名人”等包装，本质仍是几段 prompt 加简单 workflow。

关键观点：

- 真正的 Skill 不是让模型“换个语气说话”。
- 也不是把 prompt 存成 `SKILL.md`。
- 更不是给 Agent 套一个“玄学人设”。
- 有价值的 Skill 应该把一个领域里的：
  - 隐性经验
  - 执行流程
  - 工具链
  - 边界条件
  - 失败处理
  - 验收标准  
  压缩成 Agent 可以稳定调用的“可执行协议”。

作者认为，传统 n8n、Zapier 这类 workflow 工具适合确定性链路，但面对需要上下文理解、动态决策、局部修复、多代理协作的任务时，容易变成难维护的巨大流程图。Skills 的优势在于：既模块化，又能让 Agent 根据任务状态动态选择工具、调用脚本、分发子任务并处理失败。

---

##### 2. `hatch-pet` 的本质：不是宠物生成器，而是资产生产流水线

`hatch-pet` 表面功能是生成 Codex 电子宠物，但源码展示的是一个高级 Skill 范式。

它不是简单的 image generation wrapper，而是一个面向 Codex app 的：

> animated pet asset pipeline  
> 动画宠物资产生产流水线

它串联了：

- 图像生成
- 子代理并行
- 确定性脚本
- provenance 溯源
- QA 验收
- 局部修复
- 最终打包
- Codex app 加载

最终产物不是“一张好看的图”，而是 Codex app 可加载的本地宠物包：

```text
${CODEX_HOME:-$HOME/.codex}/pets/<pet-name>/
├── pet.json
└── spritesheet.webp
```

其中：

- `pet.json` 描述宠物 ID、名称、描述、精灵图路径。
- `spritesheet.webp` 是 Codex app 按固定行列读取的动画精灵图。

---

##### 3. Codex Pets 与 `hatch-pet` 的关系

文章区分了两个概念：

###### Codex Pets

Codex app 内置的宠物功能，可以在：

```text
Settings → Appearance → Pets
```

中选择内置宠物或刷新本地自定义宠物，也可以用 `/pet` 或命令面板唤醒、收起。

它不只是装饰，还能显示 Agent 状态，例如：

- 当前 active thread
- Codex 是否运行中
- 是否等待输入
- 是否等待 review

本质上是一个轻量状态可视化层。

###### `hatch-pet`

这是生成自定义宠物资产的 Skill。

安装方式：

```bash
$skill-installer hatch-pet
```

安装后需要执行：

```text
Force Reload Skills
```

然后可以调用：

```text
$hatch-pet create a new pet inspired by my recent projects
```

这里的 `$hatch-pet` 不是普通 shell 命令，而是 Codex Skill invocation。

---

##### 4. Codex Skills 机制：渐进式披露，避免上下文爆炸

Codex Skill 是一个目录，通常包含：

```text
SKILL.md
scripts/
references/
assets/
agents/openai.yaml
```

Codex 一开始只把 Skill 的：

- name
- description
- path

放进上下文。只有当它决定使用这个 Skill 时，才读取完整 `SKILL.md`。

这叫：

> progressive disclosure  
> 渐进式披露

作用是避免技能库过大导致上下文被撑爆。

OpenAI Skills 分为：

- `.system`：随新版 Codex 自动安装
- `.curated`：通过 `$skill-installer` 安装
- `.experimental`：也通过 `$skill-installer` 安装

`hatch-pet` 属于 `.curated`。

---

##### 5. `hatch-pet` 的目录结构：标准但高级的 Skill

`hatch-pet` 的目录大致如下：

```text
skills/.curated/hatch-pet/
├── LICENSE.txt
├── SKILL.md
├── agents/
│   └── openai.yaml
├── references/
│   ├── animation-rows.md
│   ├── codex-pet-contract.md
│   └── qa-rubric.md
└── scripts/
    ├── prepare_pet_run.py
    ├── pet_job_status.py
    ├── record_imagegen_result.py
    ├── derive_running_left_from_running_right.py
    ├── extract_strip_frames.py
    ├── inspect_frames.py
    ├── compose_atlas.py
    ├── validate_atlas.py
    ├── make_contact_sheet.py
    ├── render_animation_videos.py
    ├── package_custom_pet.py
    ├── queue_pet_repairs.py
    ├── generate_pet_images.py
    └── finalize_pet_run.py
```

这些文件分工明确：

- `SKILL.md`：定义触发条件、边界、流程、QA、修复和打包。
- `references/`：定义动画行协议、资产契约和 QA 标准。
- `scripts/`：负责确定性工作，例如抽帧、拼图、验证、打包。
- `agents/openai.yaml`：提供 Codex/OpenAI interface 元数据。

这说明它不是 prompt 包，而是完整的可执行工程系统。

---

##### 6. 资产协议：为什么必须是 8x9 atlas？

`hatch-pet` 最核心的资产契约是固定精灵图格式：

- 尺寸：`1536x1872`
- 网格：`8 columns x 9 rows`
- 单格：`192x208`
- 背景：透明
- 未使用 cell：必须完全透明
- 格式：PNG 或 WebP

9 行动画状态如下：

| 行号 | 状态 | 帧数 | 含义 |
|---|---|---:|---|
| 0 | idle | 6 | 待机、呼吸、眨眼 |
| 1 | running-right | 8 | 向右跑 |
| 2 | running-left | 8 | 向左跑 |
| 3 | waving | 4 | 挥手 |
| 4 | jumping | 5 | 跳跃 |
| 5 | failed | 8 | 失败、沮丧 |
| 6 | waiting | 6 | 等待输入 |
| 7 | running | 6 | 运行中 |
| 8 | review | 6 | 检查、review 状态 |

这说明 `hatch-pet` 生成的不是单纯角色插画，而是：

> 一个能被 Codex app 状态机消费的动画表。

例如：

```text
agent idle      -> idle row
agent running   -> running / running-right / running-left row
agent waiting   -> waiting row
agent failed    -> failed row
agent reviewing -> review row
```

所以“好看”不等于“可用”。可用性来自固定尺寸、透明背景、动作语义、循环完整度和身份一致性。

---

##### 7. `SKILL.md` 的核心设计：把不可控生成关进工程边界

`SKILL.md` 明确规定：

- 正常视觉生成必须委托给 `$imagegen`。
- `hatch-pet` 自己的脚本只做确定性工作。
- 不能用 Python/Pillow、SVG、canvas、HTML/CSS 或脚本伪造宠物视觉。
- 普通流程最多 10 个视觉生成任务：
  - 1 个 base pet
  - 9 个 row strip

唯一例外：

- `running-left` 可以在 `running-right` 已生成且适合镜像时，由脚本水平镜像得到。

这形成了清晰边界：

| 类型 | 负责方 |
|---|---|
| 非确定性视觉生成 | `$imagegen` |
| 确定性资产处理 | `hatch-pet scripts` |

文章特别强调，这是一种反幻觉、反作弊机制：

- 不能手改 `imagegen-jobs.json` 标记完成。
- 不能复制本地文件冒充生成结果。
- 不能写 helper script 填充 row outputs。
- 必须用 `record_imagegen_result.py` 记录真实 `$imagegen` 输出。
- row job 必须带 grounding images。
- base job 才允许 prompt-only。

也就是说，系统不相信模型“说完成了”，只相信：

- 文件
- hash
- manifest
- QA 结果
- 可检查产物

---

##### 8. Prompt 策略：不是追求更漂亮，而是限制生成空间

`hatch-pet` 的默认美术风格非常具体：

- 小型 digital pet
- pixel-art-adjacent mascot
- compact chibi proportions
- chunky silhouette
- 1–2px 深色描边
- stepped/pixel edges
- 有限色板
- flat cel shading
- 简单表情、小四肢

明确禁止：

- polished illustration
- painterly rendering
- anime key art
- 3D render
- glossy app icon
- realistic fur
- soft gradients
- 高细节抗锯齿

这些不是单纯审美偏好，而是工程约束。因为最终每格只有 `192x208`，高细节会糊成噪声，柔光和半透明会破坏抠图，复杂饰品会造成不同动画行之间身份漂移。

它还限制特效：

允许：

- 与宠物轮廓接触或重叠
- 在同一 frame slot 内
- opaque
- hard-edged
- pixel-style

禁止：

- motion arcs
- speed lines
- afterimages
- blur
- detached stars
- floating punctuation
- shadows
- glows
- speech bubbles
- UI panels
- checkerboard transparency

本质是减少图像模型“自作聪明”的空间，让输出尽量符合 sprite production contract。

---

##### 9. 编排起点：`prepare_pet_run.py`

`prepare_pet_run.py` 会创建一次 pet run 的工作目录、prompt 文件和 job manifest。

它会：

- 推断 pet name / pet id / description
- 复制 reference images
- 自动选择 chroma key
- 生成 layout guide images
- 写入 `pet_request.json`
- 写入 `prompts/base-pet.md`
- 写入各状态 row prompt
- 写入 `imagegen-jobs.json`

其中一个细节很关键：chroma key 不是固定绿色，而是从候选色中选择与参考图像像素距离较远的颜色。

候选色包括：

- magenta
- cyan
- yellow
- blue
- orange
- green

这样可以避免宠物本体颜色被错误抠掉。

另一个重要设计是 layout guide。每个 row job 都会带一个 layout guide，用来约束：

- 帧数
- 间距
- 居中
- 安全边距

这解决了图像模型生成 sprite strip 时常见的问题，比如：

- 6 帧画成 5 帧半
- 间距混乱
- 角色跨格
- 边缘裁切

layout guide 是给模型看的“施工图”，不是最终资产的一部分。

---

##### 10. `imagegen-jobs.json`：把生成流程变成可追踪任务图

`imagegen-jobs.json` 是一次生成任务的 Job Manifest，也就是运行清单。

它记录：

- 本次 run 的基本信息
- 每个 job 的状态
- 每个 job 的 prompt
- 输入图
- 输出路径
- 依赖关系
- 是否允许并行
- 是否要求 grounded generation
- 生成来源
- hash
- metadata
- canonical identity reference

每个动画状态都是一个独立 job，例如：

- `base`
- `idle`
- `running-right`
- `jumping`
- `review`

`running-left` 有特殊规则：

- 依赖 `base` 和 `running-right`
- 只有在镜像不会破坏身份、文字、方向、道具、光照等语义时，才允许由 `running-right` 镜像得到
- 否则必须重新通过 `$imagegen` 生成

文章称这体现了 Harness 思维：

> 模型只负责选择下一步和执行局部任务，状态、依赖、边界和验收由外部结构保存。

这比让模型“记住流程”可靠得多。

---

##### 11. 子代理设计：并行生成，但父代理独占写权限

`hatch-pet` 要求在 base job 完成并生成 `references/canonical-base.png` 后，row-strip 的视觉生成通常要使用 subagents。

父代理负责：

- 准备 run
- 生成并记录 base
- 查看 job status
- 派发 `idle` 和 `running-right`
- 判断 `running-left` 是否可镜像
- 派发其他 row jobs
- 记录结果
- finalize
- repair
- package

子代理可以：

- 读取 row prompt
- 调用 `$imagegen`
- 检查候选图
- 返回 `selected_source`
- 返回 `qa_note`

子代理不可以：

- 修改 `imagegen-jobs.json`
- 拷贝文件进 `decoded/`
- 执行 `record_imagegen_result.py`
- 镜像 `running-left`
- finalize
- repair
- package

核心原则是：

> 并行任务可以分发，状态提交必须集中。

这避免了并行写冲突、来源混乱和 provenance 污染。

---

##### 12. 资产溯源：从“生成了图”到“可审计资产”

生成图片后，不能直接放进最终目录，而必须执行：

```bash
python "$SKILL_DIR/scripts/record_imagegen_result.py" \
  --run-dir /absolute/path/to/run \
  --job-id <job-id> \
  --source /absolute/path/to/generated-output.png
```

该脚本会：

- 检查 job 依赖是否完成
- 检查 grounding images 是否存在
- 把 source copy 到 job 的 output path
- 记录 `source_path`
- 记录 `source_provenance`
- 记录 `source_sha256`
- 记录 `output_sha256`
- 记录 metadata
- 记录 completed_at

如果是 base job，还会生成：

```text
references/canonical-base.png
```

并更新 `pet_request.json` 和 manifest。

后续 `finalize_pet_run.py` 会验证这些 hash。如果缺少 `source_sha256`，或 decoded output 与 source hash 不一致，就会报错。

这体现了强 anti-hallucination 设计：模型不能只靠“我已经完成了”过关，必须留下可验证证据。

---

##### 13. 打包链路：从 row strips 到最终宠物包

所有 imagegen jobs 完成后，执行：

```bash
python "$SKILL_DIR/scripts/finalize_pet_run.py" \
  --run-dir /absolute/path/to/run
```

`finalize_pet_run.py` 大致流程：

1. 读取 `pet_request.json`
2. 检查所有 jobs 是否 complete
3. 验证 provenance 和 hash
4. 用 `extract_strip_frames.py` 抽帧
5. 用 `inspect_frames.py` 检查每帧
6. 用 `compose_atlas.py` 拼 spritesheet
7. 用 `validate_atlas.py` 验证 atlas
8. 用 `make_contact_sheet.py` 生成 QA contact sheet
9. 用 `render_animation_videos.py` 生成动画预览
10. 用 `package_custom_pet.py` 打包到 Codex pets 目录
11. 写入 `qa/run-summary.json`

如果中途发现 QA 失败，会提示运行：

```bash
python "$SKILL_DIR/scripts/queue_pet_repairs.py" \
  --run-dir /absolute/path/to/run
```

这说明它不是单轮生成，而是一条支持失败、修复、重跑、验收的生产链。

---

##### 14. QA 策略：脚本检查结构，人或模型检查语义

`validate_atlas.py` 主要检查工程正确性：

- 尺寸必须是 `1536x1872`
- 格式必须是 PNG 或 WebP
- 必须有 alpha channel
- used cell 不能太稀疏
- unused cell 必须完全透明
- used cell 不能近似全不透明，否则可能是背景没抠干净

但作者强调：

> deterministic validation necessary but not sufficient  
> 确定性验证必要，但不充分。

脚本能检查：

- 尺寸
- 透明度
- 帧数
- 空 cell
- alpha
- hash

但不能判断：

- 这是否还是同一只宠物
- review 状态是否真的像 review
- failed 是否过度夸张
- running-left 镜像是否破坏角色设定

所以验收分两层：

| 层级 | 方式 |
|---|---|
| 结构正确性 | 脚本检查 |
| 视觉/语义一致性 | 人类或模型视觉检查 |

这和真实生产系统类似：schema 正确只是底线，语义正确才是用户关心的结果。

---

##### 15. Repair Workflow：不是整体重来，而是最小范围修复

如果 finalization 因某一行动画 QA 失败而停止，`hatch-pet` 不会要求重做全部资产，而是运行：

```bash
python "$SKILL_DIR/scripts/queue_pet_repairs.py" \
  --run-dir /absolute/path/to/run
```

然后只重新生成失败的 row job。

修复原则是：

> regenerate the smallest failing scope  
> 只重生成最小失败范围。

例如：

- 如果只有 `failed` 行不合格，就只修 `failed` 行。
- 如果 identity 或 layout 大范围损坏，才考虑 full atlas regeneration。

这比简单 retry 更工程化，因为它能：

- 降低成本
- 减少已有合格部分被破坏
- 控制图像生成的不稳定性
- 保持修复边界清晰

---

##### 16. Secondary fallback：有 API 备用路径，但不是默认路径

`scripts/generate_pet_images.py` 是二级 fallback。

只有当 `$imagegen` system skill 不可用，或当前环境无法调用时，才使用它。

可通过：

```bash
--model gpt-image-2 --states all
```

执行，并需要 `OPENAI_API_KEY`。

这说明 `hatch-pet` 并不想自己接管所有图像生成策略。它只定义宠物生产协议：

```text
hatch-pet = domain workflow
$imagegen = visual generation capability
scripts = deterministic asset compiler
```

这是一种更干净的 Skill composition。

---

##### 17. `hatch-pet` 展示的高级 Skill 范式

作者总结，一个成熟 Skill 应该具备以下结构：

###### 1. description 是路由入口

Codex 初始上下文只看到 name、description、path，所以 description 必须准确说明什么时候触发。

`hatch-pet` 的 description 明确列出：

- create
- repair
- validate
- preview
- package
- 8x9 atlas
- transparent unused cells
- QA contact sheets
- preview videos
- pet.json packaging

它不是营销文案，而是 router spec。

###### 2. `SKILL.md` 是 workflow contract

它规定：

- 谁能生成
- 谁能写 manifest
- 什么时候用 subagents
- 什么时候必须停止
- 哪些行为禁止
- 什么算验收通过

###### 3. scripts 是确定性编译器

模型负责视觉和语义，脚本负责：

- 抽帧
- 拼 atlas
- 验证透明度
- 验证尺寸
- 记录 hash
- 打包

###### 4. references 是协议文档

例如：

- `animation-rows.md`：动画状态协议
- `codex-pet-contract.md`：app 消费格式
- `qa-rubric.md`：验收标准

###### 5. subagents 并行但不共享写权限

子代理可生成、探索、筛选候选，但统一状态、审计、manifest 和 package 必须由父代理控制。

---

##### 18. 局限性：仍依赖生成模型稳定性和人工语义判断

`hatch-pet` 也有明显限制：

###### 1. 依赖 `$imagegen` 的视觉稳定性

即使有 canonical base、layout guide、row prompt 和 QA 修复，也不能完全保证所有动画行身份一致。

所以 contact sheet 视觉检查仍然必要。

###### 2. 只适配 Codex app 固定协议

它生成的是：

- 8x9
- 192x208 cell
- 固定 row state
- `spritesheet.webp`

不能假设直接适配任意 UI 或动画系统。

###### 3. 自动 QA 有语义空洞

脚本能检查结构，但不能完全判断动作语义是否自然。

###### 4. 子代理会增加成本

9 行动画适合并行，所以用 subagents 合理。但如果只是小修一行，顺序执行可能更省 token。

---

##### 19. Agent 工程启发：模型是创意工人，不是可信提交者

文章认为，`hatch-pet` 最大价值不是“做宠物”，而是展示了一个缩小版 Agent 生产系统。

它把一句模糊请求：

```text
create a new pet inspired by my recent projects
```

转换成：

```text
intent
-> request
-> job manifest
-> generated candidates
-> recorded provenance
-> compiled artifact
-> QA result
-> targeted repair
-> packaged asset
```

带来的工程启发包括：

###### 1. 不要把模型输出直接当成果

模型输出只是生产材料。只有经过：

- provenance 记录
- 抽帧
- 拼 atlas
- 验证
- contact sheet 检查
- package

才是最终资产。

###### 2. 关键状态必须外部化成 manifest

对话上下文会遗忘、压缩、偏移，而 `imagegen-jobs.json` 不会。

长任务需要外部状态机，而不是让模型“记住自己做到哪一步”。

###### 3. 多代理关键不是并行，而是提交权隔离

子代理是 worker plane，父代理是 control plane。

规则是：

> 并行任务可以分发，truth commit 必须集中。

###### 4. QA 要区分结构正确和语义正确

很多 Agent 系统只做 schema validation 就以为完成，但真实生产中，semantic correct 才是最终标准。

###### 5. repair 比 retry 更像工程

成熟 Agent 不应只会“重试”，而应知道：

- 失败在哪里
- 修复边界在哪里
- 哪些部分已经通过验收
- 如何局部收敛

---

##### 20. 与 vibe coding 的关系：创意开放，协议收紧

作者认为 `hatch-pet` 和 vibe coding 并不矛盾。

更成熟的 vibe coding 应该是：

- 创意层开放
- 协议层收紧
- 提交层验证
- 失败层可修

如果没有产物协议和验收链路，vibe 只是一次灵感截图；有了 manifest、provenance、编译器和 QA，它才会变成能被应用加载、复用和维护的 artifact。

---

##### 21. Codex `/goal` 命令：目标驱动执行机制

文章最后提到 Codex v0.128.0 的重要更新：新增 `/goal &lt;objective>` 命令。

它允许用户给 Codex 设置明确目标。Agent 完成一轮执行后，如果用户没有继续输入，Codex 会自动注入提示，引导模型继续选择下一步动作。

它会把 goal 映射到可验证证据上，例如：

- 文件变更
- 测试结果
- PR 状态

模型只能通过更新 goal 来标记任务完成。

作者将它类比为一个内置的：

> Ralph loop++

它让 Codex 不再停留于单轮响应，而是围绕目标持续执行、检查证据并推进任务，直到目标完成或 token 预算耗尽。

该功能默认不显示，需要在 `config.toml` 中开启：

```toml
[features]
goals = true
```

---

##### 总结

`hatch-pet` 的核心价值不在于“生成可爱的 Codex 宠物”，而在于它示范了真正成熟的 Skill 工程：用协议、manifest、provenance、脚本、QA 和局部修复，把不可控的模型生成能力接入一个可控的产物系统。

它给 Agent 工程的最大启发是：  
**prompt 能提升一次回答的质量，但协议、状态机、溯源、编译器和验收流程，才能提升整个系统的稳定性。**

##### 二、深入浅出解读

##### 1. 真正的 Skill 不是“高级提示词”

很多所谓 Skill，其实只是：

> 把一段 prompt 存成文件，再让模型扮演某个人或执行某个套路。

比如：

- “复刻某某大佬”
- “蒸馏同事”
- “一键生成 PPT”
- “让模型像某某一样思考”

这些东西看起来很酷，但本质上还是角色扮演和 prompt 包装。

作者认为，真正有价值的 Skill 应该是：

> 把一个领域里的经验、规则、工具、流程、失败处理和验收标准，封装成 Agent 能稳定执行的协议。

换句话说，Skill 不应该只是告诉模型“你要怎么想”，而应该告诉系统：

- 输入是什么？
- 产物是什么？
- 流程怎么走？
- 哪些步骤可以自动化？
- 哪些步骤必须验证？
- 失败后怎么修？
- 最终如何交付？

`hatch-pet` 就是这样的例子。

---

##### 2. `hatch-pet` 不是画图工具，而是资产生产线

如果只是“画一只电子宠物”，那一个图像生成 prompt 就够了。

但 Codex app 需要的不是一张漂亮插画，而是一套可运行的动画资产：

- 每一行动画对应一个 Agent 状态。
- 每一帧都要在正确位置。
- 背景必须透明。
- 未使用格子必须空白。
- 宠物形象必须一致。
- 最终文件必须能被 Codex app 正确读取。

所以 `hatch-pet` 做的不是“画画”，而是：

```text
用户想法
-> 生成需求
-> 创建任务清单
-> 生成 base 角色
-> 生成各行动画
-> 记录来源和 hash
-> 抽帧
-> 拼 spritesheet
-> 自动校验
-> 生成预览
-> 局部修复
-> 打包成 Codex pet
```

这更像一条小型生产流水线。

---

##### 3. 模型负责创意，脚本负责确定性

文章里一个很重要的观点是：

> 模型不应该直接被信任为最终提交者。

模型可以做：

- 生成宠物形象
- 生成动画 strip
- 判断候选图是否合适
- 给出视觉反馈

但最终产物必须经过确定性流程：

- 文件是否存在？
- 尺寸是否正确？
- hash 是否一致？
- 透明背景是否合格？
- cell 是否越界？
- 未使用区域是否透明？
- 是否生成了 pet.json？
- 是否成功打包？

这些事情不能靠模型“说我完成了”，而要靠脚本验证。

这就是 `hatch-pet` 的核心工程思想：

> 模型输出只是材料，经过验证和编译后，才是资产。

---

##### 4. manifest 是 Agent 的“外部记忆”

`imagegen-jobs.json` 非常关键。

它记录了：

- 当前有哪些 job
- 每个 job 的状态
- job 之间的依赖
- 每个 job 用了哪些输入图
- 输出文件在哪里
- 是否允许 prompt-only
- 是否必须 grounded generation
- source hash 是什么
- output hash 是什么
- 哪个 job 可以镜像生成

这相当于把 Agent 的工作状态写到了外部文件中。

为什么重要？

因为对话上下文不可靠：

- 会被压缩
- 会遗忘
- 会混入错误推理
- 多代理协作时更容易乱

而 manifest 是明确、可检查、可恢复的。

这对 Agent 工程非常重要：

> 长任务不能只靠模型记忆，必须有外部状态机。

---

##### 5. 子代理真正重要的是“权限隔离”

`hatch-pet` 会使用 subagents 并行动画生成。

但它不是简单地“多开几个模型更快”。

更重要的是权限设计：

###### 子代理可以做：

- 读取 row prompt
- 调用 `$imagegen`
- 检查候选图
- 返回结果和 QA note

###### 子代理不能做：

- 修改 `imagegen-jobs.json`
- 复制文件到 decoded
- 执行 record
- 镜像 running-left
- finalize
- package

这些关键操作只能由父代理完成。

这背后的工程原则是：

> Worker 可以干活，但 truth commit 必须集中。

也就是说，子代理可以生产候选结果，但不能直接修改系统真相。

这能避免并发写冲突、来源混乱和状态污染。

---

##### 6. QA 分成结构正确和语义正确

自动脚本能检查很多东西：

- 图片尺寸
- 格子数量
- alpha 通道
- 背景透明
- 未使用 cell 是否为空
- used cell 是否过于稀疏
- 是否整张图几乎不透明

但它不能完全判断：

- 这还是不是同一只宠物？
- failed 状态是否真的像失败？
- review 状态是否真的像检查？
- running-left 镜像后是否破坏角色设定？
- 动作是否自然？

所以作者强调：

> deterministic validation necessary but not sufficient。

也就是：

> 自动校验是必要的，但不够。

这很像真实软件工程：

- 类型检查通过，不代表业务逻辑正确。
- 单测通过，不代表用户体验好。
- schema 正确，不代表语义正确。

---

##### 7. Repair 比 Retry 更工程化

很多 Agent 失败后只会重试：

> 重新生成一遍。

但 `hatch-pet` 的做法是：

> 找到失败的最小范围，只修失败部分。

比如某一行动画坏了，就只重新生成这一行，而不是重做整张 spritesheet。

这样有几个好处：

- 成本更低
- 不破坏已通过的部分
- 减少身份漂移
- 更容易收敛
- 更接近真实工程维护方式

这也是文章非常重要的启发：

> 成熟 Agent 不应该只会 retry，而应该会 repair。

##### 三、我的意见

我认为这篇文章真正有价值的地方，不是介绍了一个“宠物生成器”，而是借 `hatch-pet` 说明了下一代 Skill / Agent 工程的方向。

一句话概括：

> 好的 Skill，不是把 prompt 包装得更花，而是把模型能力放进一个可控的生产系统里。

`hatch-pet` 的设计很值得借鉴，尤其是这几点：

##### 1. Skill 应该产出 artifact，而不是只产出回答

很多 AI 应用还停留在“回答用户问题”的阶段。

但真正有生产力的 Agent，应该能产出可复用成果，比如：

- 代码包
- 测试报告
- UI 组件
- 文档站点
- 数据分析结果
- 设计资产
- 配置文件
- 可部署应用

`hatch-pet` 很清楚地定义了最终 artifact：

```text
pet.json + spritesheet.webp
```

这比“生成一张好看的图”更工程化。

---

##### 2. Agent 系统一定要有外部状态

对于复杂任务，只靠模型上下文是不够的。

应该有类似：

- manifest
- task graph
- provenance log
- validation report
- repair queue
- artifact registry

这样的外部结构。

否则 Agent 很容易出现：

- 忘记做到哪一步
- 重复执行
- 错把失败当成功
- 无法恢复
- 多代理互相覆盖结果

`hatch-pet` 的 `imagegen-jobs.json` 就是一个很好的范例。

---

##### 3. 模型不应该拥有最终提交权

模型很强，但它也会幻觉。

所以合理的架构应该是：

```text
模型生成候选
脚本验证结构
系统记录来源
QA 检查质量
控制面统一提交
```

而不是：

```text
模型说完成了
系统就相信完成了
```

这点对代码生成、设计生成、数据处理都适用。

---

##### 4. Workflow 和 Skill 会走向融合

传统 workflow 工具，如 n8n、Zapier，适合确定性流程。

但面对需要理解上下文、动态决策、失败修复、多代理协作的任务，固定节点图会越来越复杂。

Skill 的优势在于：

- 可以模块化封装能力
- 可以让 Agent 根据状态动态选择步骤
- 可以调用脚本和工具
- 可以并行分发子任务
- 可以根据 QA 结果局部修复

未来更强的 Agent 系统，可能不是单纯的 workflow，也不是单纯的 prompt，而是二者融合：

> workflow 提供边界，Agent 提供判断，script 提供确定性，QA 提供验收。

---

##### 5. `/goal` 是 Codex 走向持续执行的重要一步

文末提到的 `/goal` 也很关键。

它让 Codex 不再只是“一问一答”，而是能围绕目标持续推进。

这意味着 Codex 正在从：

```text
聊天助手
```

走向：

```text
目标驱动执行系统
```

如果再结合 Skill、manifest、QA、repair，未来 Agent 就可以更像一个真正的工程助手，而不是只会生成片段结果的工具。

---

##### 四、结论

`hatch-pet` 的表层是电子宠物，内核是 Agent 工程。

它证明了一个成熟 Skill 应该包含：

- 清晰的触发描述
- 明确的产物协议
- 外部任务 manifest
- 可追溯的生成记录
- 确定性脚本编译
- 自动 QA
- 人工/视觉语义检查
- 局部 repair
- 最终 package

它最重要的启发是：

> 不要试图让模型本身变得完全可靠，而是要用协议、状态、脚本、验证和修复机制，把不可靠的模型能力接入可靠的工程系统。

所以，`hatch-pet` 虽然做的是宠物，但它真正展示的是：

> 如何把 AI 生成从“灵感截图”变成“可加载、可验证、可维护的产品资产”。
