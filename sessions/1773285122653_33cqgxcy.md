#### birdclaw

`birdclaw` is a local-first X workspace: archive import, cached live reads, focused triage, and reply flows in one local web app + CLI.

Status: WIP. Real and usable. Not done. Expect schema churn, transport gaps, and rough edges while the core settles.

- keeps your X data in local SQLite
- stores media and avatar cache under `~/.birdclaw`
- imports archives when you have them
- still works when you do not
- gives you a clean local UI for home, mentions, DMs, inbox, and blocks
- exposes scriptable JSON for agents and automation

- one shared SQLite DB for multiple accounts
- FTS5 search over tweets and DMs
- archive autodiscovery on macOS
- archive import for tweets, likes, profiles, and full DMs
- profile hydration from live X metadata
- local avatar cache
- local media cache root under `~/.birdclaw`

##### Web UI

- `Home` timeline
- `Mentions` queue
- `DMs` workspace with two-column layout
- `Inbox` for mixed mention + DM triage
- `Blocks` for local blocklist maintenance
- constrained timeline lane instead of full-width dashboard UI
- tweet expansion with URLs, inline images, quoted tweets, replies, and profile hover cards
- sender bio and influence context in the DM detail header
- system / light / dark theme switcher with animated transition

- replied / unreplied filters for timelines
- DM filters by participant, followers, and derived influence score
- AI-ranked inbox for mentions + DMs
- OpenAI scoring hook for low-signal filtering
- cached live mentions export in `xurl` -compatible JSON
- live profile-reply inspection for borderline AI/slop triage

##### Actions

- post tweets
- reply to tweets
- reply to DMs
- add / remove local blocks
- add / remove local mutes
- sync remote blocks through `xurl` when available

##### Safety

- local-first by default
- tests disable live writes
- CI disables live writes
- app has no auth layer because it is a local-only tool

- broader resumable live sync beyond the targeted paths already wired
- fuller media fetch pipeline
- richer multi-account UX
- more complete transport coverage
- more archive edge-case handling

If you need polished product-grade sync parity today, this is not there yet.

#### Screens

- `Home`: read and reply without fighting the main X timeline
- `Mentions`: work the reply queue with clean filters
- `DMs`: triage by sender context, follower count, and influence
- `Inbox`: let heuristics / OpenAI float likely-important items
- `Blocks`: maintain a local-first account-scoped blocklist

## 产品-技术开发（1）

### 2026-03-12 03:20:28

下面我从**产品定位、核心设计、技术实现、最佳实践**四个角度，精炼解读`birdclaw`。

---

##### 1. 产品定位：它不是 “另一个 X 客户端”，而是 “本地优先的 AI/Agent 工作台”

###### 核心判断
`birdclaw`的产品价值不在 “刷时间线”，而在于：

- **把 X/Twitter 数据沉淀为本地可控资产**
- **把人与 AI/Agent 的协作建立在稳定、可脚本化的数据层上**
- **把 “信息消费” 改造成 “信息处理 + 回复决策 + 自动化”**

###### 产品设计上最值得注意的点
1. **local-first**
   - 数据归自己，SQLite 做 canonical truth
   - 没网 / 接口失效 / 平台限流时，仍可工作
   - 这是 AI 场景的关键：Agent 需要稳定上下文，不适合直接绑死实时 API

2. **Archive + Live 双源融合**
   - 有归档时补全历史，没有归档也能用 live read
   - 本质是 “冷启动 + 增量同步” 的产品设计
   - 非常适合做个人知识资产化

3. **UI 不是社交产品 UI，而是 triage UI**
   - Home / Mentions / DMs / Inbox / Blocks
   - 重点不是沉浸浏览，而是**筛选、判断、行动**
   - 很像 “客服工作台 + 个人舆情控制台 + AI inbox”

4. **CLI + Web 双界面**
   - Web 负责高频人工处理
   - CLI 负责自动化、脚本、Agent 接入
   - 这是典型的 “人机共用同一语义层” 的优秀产品结构

---

##### 2. 产品架构解读：为什么这个设计适合 AI Agent

##### 2.1 单一事实源：SQLite canonical store
这是全项目最重要的产品 / 技术决策。

###### 优势
- UI、CLI、Agent 都基于同一份标准化数据
- 避免 “接口返回一种格式、前端一套状态、脚本再转一次” 的数据割裂
- 本地 FTS5 搜索能直接支持：
  - tweet search
  - dm search
  - inbox ranking 前置召回
  - agent prompt context retrieval

###### 最佳实践
建议采用类似三层模型：

- **Raw Layer**
  - 原始 archive /xurl/live API payload
- **Normalized Layer**
  - 统一 tweet、dm、profile、block、mute 模型
- **Derived Layer**
  - influence score
  - unreplied state
  - ai priority score
  - thread summary
  - sender context

这样可以保证：
- 原始数据可追溯
- 规范模型易消费
- 派生特征可持续演进

---

##### 2.2 local-first + cache-first，是现实可用而不是理想主义
`birdclaw`明确说 live transport 不完整，但产品仍可用，原因在于：

- archive import 提供历史基座
- live read 只是 “增量增强”
- cached live reads 减少 API 依赖与成本
- JSON export 给 agent 稳定输入

这类设计对 AI 产品极其重要，因为 AI 最怕：

- 上下文不稳定
- 数据不完整
- 请求成本不可控
- 平台接口随时变

###### 最佳实践例子：Agent 数据出口
比如你要做 “自动回复建议 Agent”，不要让 Agent 直接打 X API，而是：

1. 先由`birdclaw`拉取 mentions /dms
2. 归一化存到 SQLite
3. Agent 只消费：
   - `text`
   - `plainText`
   - `author metadata`
   - `thread context`
   - `replied/unreplied`
   - `influence score`
4. Agent 输出：
   - 是否建议回复
   - 回复语气
   - 草稿文本
5. 最终由人工确认，或通过 compose/reply 命令发送

这样比 “Agent 直接接 API + 直接发帖” 安全得多。

---

##### 3. 产品设计亮点：它抓住了真实高频痛点

##### 3.1 Mentions / DMs / Inbox 的拆分很聪明
很多产品把消息统一做成一个收件箱，但`birdclaw`做了更细的工作流划分：

- **Mentions**：偏公开互动，适合内容运营和回复队列
- **DMs**：偏高上下文，适合关系维护和商务机会
- **Inbox**：混合 triage，由 heuristics / AI 提前排序

这其实是三种不同任务：

| 场景 | 用户目标 | 最重要特征 |
|---|---|---|
| Mentions | 快速判断要不要公开回复 | 语义、是否已回复、上下文 |
| DMs | 判断是否值得深入沟通 | 发送者背景、影响力、历史上下文 |
| Inbox | 从噪音中找重要信号 | 排序、过滤、AI 打分 |

###### 最佳实践
如果你做类似产品，Inbox 不应只是 “所有消息列表”，而应是：
- 召回层：mentions + dms
- 特征层：followers /influence/prior interactions /semantic intent
- 排序层：规则 + LLM score
- 行动层：reply /mute/block /archive/mark done

---

##### 3.2 “影响力分数” 是很实用的弱监督特征
项目里有：
- `followers`
- `derived influence score`
- `min-influence-score`
- `sort influence`

这说明产品设计不是单纯靠 LLM，而是用**结构化特征先做粗筛**。

###### 这是 AI 产品的最佳实践
不要一上来就 “让大模型决定一切”，而要：

- 先用规则召回
- 再用结构化特征过滤
- 最后让 LLM 做边界判断

###### 例子：DM triage 的三层策略
**第一层：硬过滤**
- 已屏蔽 / 已静音去掉
- 重复模板内容去掉
- 历史已处理去掉

**第二层：规则排序**
- followers > 1000 加权
- 有 mutual / 历史互动加权
- 最近 7 天活跃加权

**第三层：LLM 精排**
Prompt 判断：
- 是否是商务合作
- 是否需要人工优先回复
- 是否疑似 AI 套壳寒暄
- 是否和你当前关注主题相关

这比单纯 “OpenAI 评分 hook” 更稳。

---

##### 4. 技术设计解读：这是一个很典型的 “本地数据平台 + 多端壳”

##### 4.1 架构本质
可以理解为：

- **存储层**：SQLite + media/avatar cache
- **采集层**：archive importer + xurl/live transport
- **领域层**：normalized core model
- **体验层**：web UI + CLI
- **智能层**：AI inbox scoring /agent export

这是很标准、也很正确的分层。

###### 好处
- Transport 可替换
- UI 可重做
- Agent 能复用核心数据
- 测试可以以 core model 为中心

---

##### 4.2 SQLite + FTS5 是正确选型
对个人工作台型产品，这比上来就 PostgreSQL / Elastic 更合理。

###### 为什么适合
- 本地单用户
- 易安装
- 易备份
- FTS5 足够覆盖 tweet/dm 搜索
- 和 Electron/Tauri/Node CLI/Next Web 都容易集成

###### 最佳实践 schema 建议
核心表建议至少有：

- `accounts`
- `profiles`
- `tweets`
- `tweet_threads`
- `mentions`
- `dms`
- `conversations`
- `blocks`
- `mutes`
- `media_assets`
- `sync_cursors`
- `raw_payloads`
- `ai_scores`

索引重点：
- `tweets (created_at desc, account_id)`
- `mentions (replied, created_at desc)`
- `dms (conversation_id, created_at desc)`
- `profiles (handle)`
- `blocks (account_id, profile_id)`
- FTS virtual tables for `tweets.text`, `dms.text`

---

##### 4.3 “archive import + hydrate profiles” 体现了增量建模思路
这是个很实战的设计。

###### 两阶段导入模型
**第一阶段：archive import**
- 导入 tweets /likes/profiles /dms
- 建立基础关系图

**第二阶段：profile hydration**
- 用 live metadata 补齐头像、简介、followers、认证状态等

###### 优点
- 初次导入快
- 没有 live auth 也能工作
- 后续补全不会污染原始数据层

###### 最佳实践
给 profile 设计字段来源优先级：
- archive snapshot
- live fetch
- user override /local note

并记录：
- `source`
- `last_synced_at`
- `staleness`
- `confidence`

这样 AI 和 UI 都知道哪些信息是旧的。

---

##### 5. AI 设计解读：它的思路对，但还可以更体系化

##### 5.1 现在的 AI 位置是 “排序助手”，不是 “决策核心”
这是对的。

项目目前 AI 能力主要是：
- inbox scoring
- low-signal filtering
- “是否像 AI/slop” 的辅助判断

这说明 AI 被放在：
- 高噪音过滤
- 边界判断
- 优先级建议

而不是：
- 直接自动发言
- 直接替代事实层
- 直接替代规则系统

###### 这是最佳实践
LLM 适合做：
- 语义理解
- 弱结构化判断
- 摘要与建议

不适合做：
- 事实源
- 权限控制
- 状态机真值
- 可审计写操作

---

##### 5.2 更好的 AI Inbox 实现范式
建议把 inbox score 设计成**可解释特征 + LLM 补充**，例如：

###### Rule features
- sender followers
- mutual follows
- prior reply rate
- contains question
- contains URL
- account age
- repeated template likelihood
- reply urgency keyword
- relationship strength

###### LLM features
- intent classification
- commercial relevance
- emotional tone
- spam likelihood
- reply-worthiness
- summary

###### 最终输出
```json
{
  "priority": 0.86,
  "reason_codes": ["high_influence", "direct_question", "prior_interaction"],
  "llm_summary": "Potential partnership inquiry with concrete ask.",
  "suggested_action": "reply",
  "reply_draft": "Thanks — happy to chat. What timeline are you targeting?"
}
```

这比只有一个 score 更适合产品落地，因为：
- 用户信任更高
- 可调试
- 可做 A/B 优化
- 方便 agent 接入

---

##### 6. 安全与工程实践：非常对路

##### 6.1 “local-only，无 auth layer” 是合理取舍
因为这是本地工具，不是云服务。

###### 好处
- 大幅降低复杂度
- 避免伪安全
- 开发速度快

###### 但最佳实践补充
仍建议增加：
- 本地数据库加密可选项
- 敏感 cookie/token 独立密钥存储
- “只读模式” 启动参数
- 危险写操作二次确认
- AI 自动发消息默认关闭

---

##### 6.2 CI 禁用 live writes，很关键
这说明作者意识到：
- 测试环境不能碰真实社交写操作
- transport 层必须可 mock / 可断路

###### 最佳实践
把写操作分成三层：
- `dry-run`
- `staged`
- `commit`

例如：
- `compose reply --dry-run`
- `compose reply --preview`
- `compose reply --send`

Agent 只能默认拿到`dry-run`权限，这是最稳的。

---

##### 7. 对开发者最有价值的可复用模式

##### 模式 1：本地优先的 Agent 数据底座
适用于：
- 邮件助手
- Slack triage
- Reddit monitor
- Discord mod tool
- CRM 个人工作台

关键原则：
- 本地 DB 是真相
- 外部 API 只是同步源
- Agent 只读标准化 JSON

---

##### 模式 2：UI 和 CLI 共用同一个领域核心
适用于任何 “人工操作 + 自动化脚本” 混合场景。

最佳实践：
- core domain package
- transport adapters
- UI/CLI 只调用 use cases
- 不要在前端组件里写数据拼装逻辑

---

##### 模式 3：AI 只做排序与建议，不直接做状态变更
适用于高风险交互型产品。

最佳实践：
- AI 输出 suggestion，不输出 commit
- 所有写操作可审计
- score 可解释
- 允许用户快速纠正
