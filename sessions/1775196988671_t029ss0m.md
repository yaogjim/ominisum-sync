- **核心高价值点**：最有价值的是提出“评估会塑造智能体行为”，因此应围绕生产中真实关心的行为构建少而准的定向评估，而不是盲目堆积测试数量。
- **留存建议**：长期保留（内容提供了面向生产环境的智能体评估框架、指标设计和实验组织方式，适合作为后续搭建评测体系的参考模板。）

**知识要点**

- 评估应围绕目标行为设计，并通过docstring与标签实现自文档化和分组运行
- 模型选择应先看正确性，再在达标模型中比较延迟、成本与效率
- 可借助“理想轨迹”衡量智能体是否存在多余步骤、冗余工具调用和未并行化问题
- 内部试用反馈、外部基准和手工编写测试可共同构成评估数据来源
- 评估可通过pytest与GitHub Actions集成进CI，支持低成本定向实验

**行动项**

- 为自己的智能体系统梳理3到5类关键生产行为，并据此设计定向评估用例
- 给现有评估补充分类标签、docstring和失败模式追踪，建立可复盘的评测台账
- 在评估指标中加入效率维度，如步骤数、工具调用数、耗时和成本
- 将评估接入CI，只对相关标签子集运行实验以控制成本

**Viv**

### 我们如何构建深度智能体的评估

TLDR: 最佳的代理评估直接衡量我们关心的代理行为。以下是我们如何获取数据、创建指标，并随着时间的推移开展范围明确、针对性强的实验，以提高代理的准确性和可靠性。

#### 评估塑造代理行为

我们一直在精心构建评估以衡量和改进

[Deep Agents](https://github.com/langchain-ai/deepagents). Deep Agents 是一个开源的、与模型无关的代理工具包，可为像

[Fleet](https://www.langchain.com/langsmith/fleet)

以及

[Open SWE](https://github.com/langchain-ai/open-swe)

. 评估定义并塑造代理行为，因此精心设计它们非常重要。

每次评估都是一个会改变你的代理系统行为的向量。例如，如果一个关于高效文件读取的评估失败，你可能会调整系统提示或 read\_file 工具描述来引导行为，直到评估通过。你保留的每次评估都会随着时间的推移对整个系统施加压力。

在添加评估时要深思熟虑，这一点至关重要。盲目地添加数百（或数千）个测试可能会很诱人。但这会导致一种错觉，即通过在评估套件中取得高分来“提升你的智能体”，而该评估套件可能无法准确反映你在生产环境中关注的行为。

更多的评估 ≠ 更好的智能体。相反，构建有针对性的评估以反映生产环境中期望的行为。

在构建 Deep Agents 时，我们梳理生产环境中关键的行为，例如从文件系统中的多个文件中检索内容，或准确地按顺序组合 5 个以上的工具调用。与整体使用基准测试任务不同，我们采用以下方法进行评估整理：

1. 决定我们希望代理遵循哪些行为。然后研究并精心挑选针对性的评估，以可验证的方式衡量这些行为。
2. 对于每个 eval，添加一个 docstring 来解释它如何衡量 agent 能力。这确保每个 eval 是自文档化的。我们还为每个 eval 标记如 tool\_use 之类的类别，以支持分组运行。
3. 检查输出跟踪以了解故障模式并更新评估覆盖率

因为我们将每次评估运行追溯到一个共享的

[LangSmith](https://docs.langchain.com/langsmith/observability) 项目，团队中的任何人都可以参与进来分析问题、进行修复，并重新评估特定评估的价值。这为添加和维护良好的评估创建了共同责任。在许多评估中运行多个模型可能会成本高昂，因此有针对性的评估可以节省成本，同时改进你的代理。

在本博客中我们涵盖：

- 我们如何整理数据
- 我们如何定义指标
- 我们如何运行评估

#### 我们如何整理数据

我们有几种获取 evals 的方式：

1. 利用我们代理内部试用的反馈
2. 从外部基准测试中拉取选定的评估数据（如
   [终端基准测试 2.0](https://www.tbench.ai/) 或
   [BFCL](https://gorilla.cs.berkeley.edu/leaderboard.html)
   ）并经常为特定代理调整这些评估数据
3. 编写我们自己的（手工的）评测和单元测试，针对我们认为重要的行为

![Image](https://pbs.twimg.com/media/HET8gsLWkAAun5Q?format=jpg&name=large)

我们每天都在内部试用我们的代理。每个错误都成为编写评估和更新我们代理定义及上下文工程实践的机会。

> 注意：我们将 SDK 单元测试和集成测试（系统提示透传、中断配置、子代理路由）与模型能力评估区分开来。任何模型都能通过这些测试，因此将它们纳入评分不会增加任何信号。你绝对应该编写单元测试和集成测试，但本博客仅关注模型能力评估。

#### 内部试用代理和读取痕迹是评估的重要来源

这使得发现错误成为可能。

[跟踪记录](https://docs.langchain.com/langsmith/observability-concepts#traces)给我们提供数据以了解代理行为。由于跟踪记录通常很大，我们使用内置代理，如

[Polly](https://docs.langchain.com/langsmith/polly)

或

[Insights](https://docs.langchain.com/langsmith/insights)

以大规模分析它们。你也可以对其他代理（如 Claude Code 或

[Deep Agents CLI](https://docs.langchain.com/oss/python/deepagents/cli/overview)

）以及一种获取跟踪记录的方法，如

[LangSmith CLI](https://docs.langchain.com/langsmith/langsmith-cli)

。我们的目标是理解每种失败模式，提出修复方案，重新运行代理，并跟踪进度和随时间的回归情况。

例如，现在很大一部分修复 bug 的拉取请求（PR）是通过

[Open SWE](https://blog.langchain.com/open-swe-an-open-source-framework-for-internal-coding-agents/)，我们的开源背景编码代理。使用它的团队会接触许多不同的代码库，这些代码库具有不同的上下文、规范和目标。这自然会导致错误。Open SWE 的每一次交互都会被追踪，因此这些交互可以很容易地成为评估，以确保错误不再发生。

其他评估是从现有的基准测试中提取并调整，如

[BFCL](https://gorilla.cs.berkeley.edu/leaderboard.html) 用于函数调用。对于编码任务，我们与

[Harbor](https://github.com/laude-institute/terminal-bench)

以运行选定的任务来自数据集（如

[Terminal Bench 2.0](https://www.tbench.ai/leaderboard/terminal-bench/2.0)

在沙箱环境中执行的任务。许多评估是从头编写的，作为专注的测试以观察孤立行为，例如测试 read\_file 工具。

#### 我们根据它们测试的内容对评估进行分组

建立一个评估的分类体系来获得对智能体表现的中间视角是很有帮助的（不是单一的数字，也不是单个的运行结果）。

> 提示： 创建该分类法时，应关注它们测试的内容，而非它们的来源。例如，来自
>
> [FRAMES](https://huggingface.co/datasets/google/frames-benchmark) 和
>
> [BFCL](https://gorilla.cs.berkeley.edu/leaderboard.html)
>
> 可以标记为“外部基准测试”，但这无法分别展示它们如何衡量检索和工具使用。

以下是我们定义的一些类别以及它们测试的内容：

![Image](https://pbs.twimg.com/media/HET-ppfW8AAwuK_?format=jpg&name=large)

如今，所有评估均是智能体在某个任务上的端到端运行。我们刻意鼓励评估结构的多样性。有些任务从输入提示开始一步完成，而另一些任务则需要经过10+轮交互，由另一个模型模拟用户。

#### 我们如何定义指标

在为我们的代理选择模型时，我们首先考虑正确性。如果一个模型不能可靠地完成我们关注的任务，其他一切都无关紧要。我们在评估中运行多个模型，并随着时间的推移不断优化评估框架，以解决我们发现的问题。

测量正确性取决于测试的内容。大多数内部评估使用自定义断言，例如“代理是否并行调用了工具？”。像 BFCL 这样的外部基准测试使用与数据集中真实答案的精确匹配。对于像代理是否在内存中持久化了正确内容这类语义层面的正确性评估，我们使用以 LLM 作为评判者的方法。

一旦几个模型达到了那个标准，我们就转向效率。 两个解决相同任务的模型在实际中可能表现得非常不同。 一个模型可能会进行额外的交互轮次，进行不必要的工具调用，或者由于模型大小而在完成任务时更慢。在生产环境中，这些差异会表现为更高的延迟、更高的成本以及更差的整体用户体验。

总体而言，我们为每次评估器运行所测量的指标是：

![Image](https://pbs.twimg.com/media/HET_GObbYAECk4q?format=jpg&name=large)

解决率衡量智能体解决任务的速度，通过预期步骤数进行归一化。与延迟比类似，它捕捉解决任务的端到端时间，包括模型往返、服务提供商延迟、错误转向和工具执行时间。对于能够定义理想轨迹的简单任务，解决率比延迟比更容易处理，因为它只需要测量给定智能体的任务持续时间。

这为我们提供了一种选择带有针对性评估集的模型的简单方法：

1. 首先检查准确性：哪些模型在你真正关心的任务上足够准确？
2. 然后，比较效率：在足够好的模型中，哪一个在正确性、延迟和成本之间提供最佳的权衡？

#### 评估相关的有用指标示例

为了让模型比较具有可操作性，我们研究模型如何成功和失败。这需要一个具体的参考点，来定义“良好执行”在准确性之外的样子。我们使用的一个基本概念是理想轨迹。 这是一系列步骤，能够产生正确的结果，且不包含“不必要”的操作。

对于简单且范围明确的任务，变量定义得足够严格，使得最优路径通常很明显。对于更开放的任务，我们使用到目前为止表现最佳的模型近似生成一条轨迹，然后随着模型和工具的改进重新审视基准。通过这种方式，观察智能体的行为有助于我们优化关于理想轨迹的先验知识。

考虑一个简单的请求：

> 我住的地方当前的时间和天气是什么？

一个智能体的理想轨迹可能如下所示：

- 它进行最少的必要工具调用（例如：确定用户 → 确定位置 → 获取时间和天气）
- 它在可能的情况下并行化独立的工具调用
- 它生成最终答案，不经过不必要的中间步骤

理想轨迹： 4 步骤，4 工具调用，约 8 秒

![Image](https://pbs.twimg.com/media/HEUAv4bbYAAtFOs?format=jpg&name=large)

现在将其与一条在技术上仍然正确但效率较低的轨迹进行比较。

低效轨迹: 6步，5次工具调用，约14秒。

![Image](https://pbs.twimg.com/media/HEUAy-UbwAAQTf3?format=jpg&name=large)

正确但低效的轨迹: 6 个代理步骤，5 次工具调用，包含一次不必要的工具调用，且未并行化工具调用。

上面的例子具有说明性：REPL 可以更快地解决这个任务，但调用工具的版本让这个想法更容易解释。

两次运行都是正确的，但第二次运行会增加延迟和成本，并增加了更多的失败机会。

这种框架使我们能够在评估中同时评估正确性和效率。我们维护并更新指标，以将运行结果提炼为可衡量的数值，从而用于比较实验。从上面的例子中，低效但正确的运行得分会是：

#### 我们如何进行评估

我们使用 pytest 和 GitHub Actions 在 CI 中运行评估，以便代码变更能在干净、可重现的环境中执行。每次评估都会创建一个使用指定模型的 Deep Agent 实例，向其输入任务，并计算正确性和效率指标。

我们也可以通过标签来运行评估的一个子集，以节省成本并衡量针对性实验。例如，如果要构建一个需要大量本地文件处理和合成的智能体，我们可能会专注于带标签为 file\_operations 和 tool\_use 的子集。

```bash
export LANGSMITH_API_KEY="lsv2_..."

uv run pytest tests/evals --eval-category file_operations --eval-category tool_use --model baseten:nvidia/zai-org/GLM-5
```

我们的评估架构和实现已在

[Deep Agents 代码仓库](https://github.com/langchain-ai/deepagents/tree/main/libs/evals)。

## 通俗精炼（1）

### 2026-04-03 06:15:48

#### 我们如何构建深度智能体评估

##### 核心观点

评估不只是“考试”，而是在直接塑造智能体行为。  
好的评估，不是数量多，而是能准确衡量你在真实生产环境中最关心的行为。

**一句话总结：**  
要用“有针对性、可验证、贴近真实场景”的评估，持续提升智能体的准确性、效率和可靠性。

##### 为什么评估很重要

每增加一个评估，都会反过来影响智能体的优化方向。  
如果评估设计得不好，就可能出现一种假象：模型在测试集上分数很高，但在真实场景里表现一般。

因此，作者强调：

- 评估越多，不一定越好
- 关键是评估要对准真实业务目标
- 每个评估都应清楚说明自己在测什么能力

##### 他们怎么设计评估

作者的方法不是先堆测试，而是先定义“希望智能体具备哪些行为”，再围绕这些行为设计评估。

比如重点关注：

- 能否从多个文件中准确检索内容
- 能否按顺序完成 5 个以上工具调用
- 能否高效使用工具，而不是绕路完成任务

同时，每个评估都会：

- 写清楚用途说明（docstring）
- 打标签分类，如 `tool_use`
- 方便团队协作分析问题、复跑和维护

##### 评估数据从哪里来

他们主要从 3 类来源构建评估：

###### 1. 内部真实使用反馈
团队每天实际试用智能体，把真实 bug 和失败案例沉淀成评估。

###### 2. 外部基准测试
从一些现有 benchmark 中挑选合适任务，再根据自己的代理场景做调整，比如：

- BFCL
- Terminal Bench 2.0

###### 3. 自己手写评测
针对关键能力写更聚焦的测试，比如单独测试 `read_file` 这样的工具行为。

**重点：**  
他们会把 SDK 的单元测试 / 集成测试，与“模型能力评估”分开。因为前者测系统正确性，后者才真正反映模型智能水平。

##### 他们怎么定义指标

作者把评估分成两个核心维度：

###### 1. 正确性优先
先看模型能不能把任务真正做对。  
如果做不对，其他指标都没有意义。

不同任务会用不同方式判断正确性：

- 自定义断言
- 与标准答案精确匹配
- 用 LLM 作为裁判做语义判断

###### 2. 再看效率
当多个模型都“做得对”后，再比较谁更高效。  
效率差异会直接影响：

- 延迟
- 成本
- 用户体验

##### 什么是“理想轨迹”

为了衡量效率，他们提出了一个很重要的概念：**理想轨迹**。

意思是：  
完成任务的那条“正确且没有多余动作”的最优路径。

例如问“我这里现在几点、天气如何”，理想智能体应该：

- 用最少的必要工具调用
- 能并行就并行
- 不走多余步骤
- 尽快输出答案

这就能区分两种情况：

- **正确且高效**
- **正确但低效**

虽然两者结果都对，但低效路径会带来更高成本、更长延迟，也更容易出错。

##### 他们如何运行评估

评估通过 `pytest + GitHub Actions` 在 CI 中运行，保证环境干净、可复现。  
每次运行时，会指定模型、输入任务，再计算正确性和效率指标。

他们还支持按标签运行评估子集，这样可以：

- 节省成本
- 聚焦某一类能力
- 快速验证针对性优化是否有效

##### 这篇文章的启发

这篇文章最有价值的地方在于，它提醒我们：

**评估不是“刷分工具”，而是智能体产品设计的一部分。**

真正有效的方法是：

- 从真实使用中找失败模式
- 围绕关键行为做小而准的评估
- 同时衡量“做对”和“做得好”
- 持续维护、更新、删减评估，而不是只会堆数量

##### 一句话结论

**优秀的智能体评估，核心不是覆盖更多题，而是精准衡量你最在意的真实行为，并用这些评估持续驱动模型变得更准、更稳、更高效。**

## 结构化（1）

### 2026-04-03 06:18:20

#### 文章主旨

这篇文章的核心观点是：**好的智能体评估，不是越多越好，而是要精准衡量你真正关心的行为**。作者围绕 Deep Agents 的实践，说明了他们如何整理评估数据、设计指标，并通过持续实验提升智能体的**准确性、效率和可靠性**。

#### 1. 为什么评估会直接塑造智能体行为

- 评估不只是“测成绩”，它会反过来影响智能体系统的设计与优化方向。  
- 例如，如果一个关于**高效读取文件**的评估失败，团队可能会去调整系统提示词，或者修改 `read_file` 工具描述，直到该行为被引导正确。  
- 因此，**每一个保留下来的评估，都会持续对系统施加优化压力**。  
- 作者特别强调：**“更多评估 ≠ 更好的智能体”**。  
- 如果盲目加入几百甚至几千个测试，可能只是让智能体在评估集上得高分，却**不能真实反映生产环境中的关键能力**。

#### 2. 他们如何确定“该评估什么”

- 团队不是先堆题库，而是先明确：**希望智能体具备哪些关键行为**。  
- 例如，Deep Agents 在生产环境中重点关注的行为包括：  
  - 从文件系统中的**多个文件检索内容**  
  - **准确且按顺序组合 5 个以上的工具调用**  
- 基于这些真实需求，他们再去设计或挑选能**可验证地衡量这些行为**的评估。  
- 每个评估都会补充一个 `docstring`，说明它在测什么能力；同时还会打上像 `tool_use` 这样的标签，方便按类别分组运行。  
- 团队还会持续检查输出追踪（trace），分析失败模式，再决定是否补充新的评估覆盖范围。

#### 3. 他们如何整理评估数据来源

作者提到，他们主要通过 3 种方式获取评估数据：

- **来自内部试用反馈**：团队每天都在真实场景中试用代理，出现的每一个 bug，都可能转化成新的评估。  
- **来自外部基准测试**：会选取像 **Terminal Bench 2.0**、**BFCL** 这样的基准数据，再根据具体代理任务做适配。  
- **自己手工编写评测和单元测试**：专门针对某些关键行为进行定制化测试。  

这里有一个重要区分：

- 作者明确把 **SDK 单元测试 / 集成测试** 和 **模型能力评估** 分开。  
- 前者测试的是系统功能是否正常，比如：  
  - 系统提示是否透传  
  - 中断配置是否生效  
  - 子代理路由是否正确  
- 因为“任何模型”都可能通过这些测试，所以它们**不适合纳入模型能力评分**；但依然应该写。

#### 4. 为什么“读 trace”是高价值评估来源

- 团队认为，**内部试用 + trace 分析** 是最重要的评估来源之一。  
- 因为真实 trace 能直接暴露智能体在实际运行中的失败模式。  
- 由于 trace 往往很大，他们会借助内置代理（如 **Polly** 或 **Insights**）来规模化分析。  
- 他们的目标是：  
  - 理解每一种失败模式  
  - 提出修复方案  
  - 重新运行代理  
  - 跟踪修复进展和后续是否回归  

具体案例：

- 许多修复 bug 的 PR 是通过 **Open SWE** 完成的。  
- Open SWE 是他们的开源后台编码代理，会面对**不同代码库、不同上下文、不同规范和目标**，所以自然会暴露大量真实错误。  
- 由于每次交互都会被追踪，这些交互就能方便地转化成评估，确保**同类错误不再重复发生**。

#### 5. 他们如何给评估分类

- 团队不会只看一个总分，也不会只看单次运行结果，而是会建立一个**评估分类体系**，获得更细粒度的中间视角。  
- 一个关键建议是：**分类应按“测什么”来分，而不是按“来自哪里”来分**。  
- 例如，FRAMES 和 BFCL 虽然都可归为“外部基准”，但这种分法无法体现一个在测**检索能力**、另一个在测**工具使用能力**。  
- 现在他们的评估都采用**端到端任务运行**的形式。  
- 评估结构也刻意保持多样：  
  - 有些是一次输入提示就完成  
  - 有些则需要**10 轮以上对话**，并由另一个模型模拟用户互动  

这样做的好处是，评估更接近真实使用场景。

#### 6. 他们如何定义指标：先看正确性，再看效率

##### 6.1 正确性是第一优先级

- 在选择模型时，团队首先关注的是**正确性**。  
- 原因很简单：如果模型**不能稳定完成关键任务**，那后面的速度、成本都没有意义。  
- 不同任务的正确性衡量方式不同：  
  - 对内部评估，常用**自定义断言**，例如：代理是否并行调用工具  
  - 对外部基准（如 **BFCL**），常用与标准答案的**精确匹配**  
  - 对语义层面的判断，例如是否把正确内容写入记忆，则用 **LLM as a judge（让大模型做裁判）**  

##### 6.2 当多个模型都“够准”后，再比较效率

- 如果几个模型都能正确完成任务，团队就会转向比较**效率**。  
- 因为两个都能做对任务的模型，现实表现可能差很多：  
  - 一个可能多走很多轮对话  
  - 一个可能多调用不必要的工具  
  - 一个可能因为模型体量更大而更慢  
- 这些差异最终会体现为：  
  - 更高延迟  
  - 更高成本  
  - 更差用户体验  

#### 7. 他们特别关注“理想轨迹”

- 为了让模型比较更有操作性，他们提出了一个核心概念：**理想轨迹（ideal trajectory）**。  
- 它指的是：**一条能正确完成任务、且没有多余操作的步骤路径**。  
- 对简单且范围清晰的任务，最优路径通常比较明确。  
- 对更开放的问题，他们会先用当前表现最好的模型近似生成一条轨迹，之后再随着模型和工具进步不断更新。  

这意味着：  
- 评估不只看“答对没答对”，还看**是不是用合适的方式答对**。  

#### 8. 具体例子：时间和天气查询任务

作者给了一个很直观的例子：

> “我住的地方当前的时间和天气是什么？”

一个理想轨迹可能是：

- 用**最少必要的工具调用**完成任务  
  - 例如：确定用户 -> 确定位置 -> 获取时间和天气  
- 能并行的调用尽量**并行化**  
- 直接生成最终答案，不增加不必要中间步骤  

文中给出的理想情况数据是：

- **4 个步骤**
- **4 次工具调用**
- **约 8 秒完成**

而一个“结果正确但过程低效”的轨迹可能是：

- **6 个步骤**
- **5 次工具调用**
- **约 14 秒完成**
- 存在一次**不必要的工具调用**
- 且**没有并行化工具调用**

这个例子说明：

- 两次运行都“答对了”，但第二种方案会带来更高的延迟和成本。  
- 更重要的是，步骤越多、工具调用越多，**失败概率也会更高**。  

所以他们的评估会同时考察：

- **正确性**
- **效率**
- **成本与延迟之间的权衡**

#### 9. 他们如何实际运行评估

- 团队使用 **pytest + GitHub Actions** 在 CI 中运行评估。  
- 这样每次代码变更都能在**干净、可复现的环境**里执行测试。  
- 每次评估运行时，都会：  
  - 创建一个指定模型的 Deep Agent 实例  
  - 输入任务  
  - 计算正确性和效率指标  

他们也支持按标签只运行某一部分评估，以便：

- 节省成本  
- 验证特定方向的实验效果  

比如，如果某个智能体重点处理本地文件和工具调用，就可以只跑 `file_operations` 和 `tool_use` 相关评估。文中给出的示例命令是：

```bash
export LANGSMITH_API_KEY="lsv2_..." uv run pytest tests/evals --eval-category file_operations --eval-category tool_use --model baseten:nvidia/zai-org/GLM-5
```

这说明他们的评估体系不仅关注理论设计，也非常强调**工程上的可执行性**。

#### 10. 接下来他们要做什么

文章最后提到，团队接下来会继续扩展评估体系，重点方向包括：

- 比较**开源模型**与**闭源前沿模型**在各评估类别上的表现  
- 探索如何把**评估本身变成一种自动改进智能体的机制**，用于真实任务  
- 公开分享他们如何随着时间**维护、删减和扩展**每个代理的评估集  

#### 总结

- 这篇文章最重要的启发是：**评估的价值不在数量，而在是否对准真实生产行为**。  
- 一个好的评估体系，应该能从真实错误中提炼任务、按能力分类、同时衡量正确性与效率，并持续迭代。  
- 对智能体开发来说，真正有效的方法不是“刷 benchmark 分数”，而是围绕**关键行为、真实 trace、理想轨迹和成本效率**来设计评估。
