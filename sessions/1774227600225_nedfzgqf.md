### 一个 Swarm &amp; Hermes，随你一同成长

### 这里始于36小时前。

我已经进行增长实验9年了。增长黑客、分发、转化优化。这个循环总是一样的：假设、测试、衡量、保留或淘汰、重复。

问题从来不是想法本身，而是速度。一个团队每周可能开展 2-5 个实验。大部分时间都花在协调上，而非执行。研究团队不与分析团队沟通。撰写者不知道上周哪些做法有效。背景信息存在于人们的脑海中，却在 Slack 的对话线程中消逝。

我尝试用 AI 代理解决这个问题。尝试了 OpenClaw。尝试了具备工具使用能力的独立代理。尝试了全套的“AI 员工”行动方案。

它一直因为同一个原因失败。

一个没有团队的代理就只是一个没有上下文的提示。

没有人会雇佣一个没有研究团队、没有分析能力、没有策略、没有反馈机制的作家。你不会雇佣个人。你要组建团队。

所以我就是这么做的。

### 我构建的

一个群体框架，其中多个代理作为团队运作。每个代理都有自己的角色、工具、MCP 访问、专门的 LLM 模型和上下文窗口。它们共享知识、交接工作，并从彼此的成果中学习。

Hermes 作为操作者处于顶层。它可以控制集群、覆盖操作、分配任务，并从下方的代理那里学习。Hermes 与集群共同变得更智能。

### 为什么选择 Hermes 而不是 OpenClaw?

说实话。从纸面上看，这两个看起来很相似。两者都是持久代理。两者都有 SOUL.md。两者都具备技能、cron、内存、跨平台消息传递、MCP。两者都是自托管的。

我们都尝试过 OpenCLaw，对吧？有些人喜欢它，有些人讨厌它。

但是这就是我转换的原因。

python vs node.

OpenClaw 是 Node.js。Hermes 是 Python。在构建机器学习/人工智能（ML/AI）基础设施时——多模型路由、实验循环、知识存储、异步编排——Python 是原生栈。我需要的每个库（httpx、asyncio、apscheduler，必要时还有 numpy）都可以通过 pip 安装。在 Node.js 运行时之上构建我的引擎，意味着每一步都要与生态系统抗争。仅这一点就占了决策的 60%。

执行沙箱化

OpenClaw 在绑定到本地主机的 Node 进程上运行。Hermes 提供五种执行后端：本地、Docker、SSH、Singularity、Modal。通过只读根文件系统、已禁用的权限和命名空间隔离进行容器加固。当你在 VPS 上运行 30 多个具备工具访问权限的代理（这些代理能够写入文件、调用 API 和执行代码）时，这一差距至关重要。Hermes 将沙箱化视为核心基础设施，而非事后考虑。

子代理隔离

Hermes 生成具有独立对话、终端和 Python RPC 脚本的独立子代理。零上下文成本——父代理在子代理运行时不会丢失上下文。OpenClaw 具有多代理路由功能，但它是基于会话的隔离，而非执行隔离。当我的增长负责人需要将研究任务委派给三位作者并行处理时，Hermes 可以原生处理，且不会污染任何上下文窗口。

内存架构

openclaw 的内存是基于文件的 Markdown（对话日志 + 精心整理的长期内容）。单智能体使用时运行良好。但它默认在重启时会清除工作内存——存在一个已知问题，即用户会因静默压缩而丢失数天的智能体上下文。 Hermes 拥有持久化内存 + 自动生成的技能，这些在重启后仍然保留。结合我的 QMD 知识库（BM25 + 向量 + LLM 重新排序），整体内存架构为：Hermes 记得如何操作，QMD 记得团队学到了什么。两层架构，均为持久化。

SOUL.md : 相同的概念，不同的执行方式。

两者都有 SOUL.md。但 Hermes 每一条消息都会重新加载它。我在凌晨 2 点更新了集群成员名单，Hermes 会在下一次交互时获取到它。无需重启，无需重新编译，无需缓存失效。而 Openclaw 对于某些配置更改需要进程重启。当你在迭代一个由 11 个代理组成的集群时，热重载不是可有可无的功能，而是你保持理智的方式。

研究和强化学习流程

hermes 具备批量轨迹生成、并行工作器、检查点以及 Atropos 强化学习训练集成功能。支持 ShareGPT 导出用于微调。这是 NousResearch DNA。他们构建训练基础设施。如果您希望您的操作器最终能在您自己的任务数据上进行微调，hermes 拥有相应的流程，而 openclaw 没有该流程。

真诚的权衡

openclaw 拥有更好的用户体验。其生态系统更大，目前已针对个人助手使用场景进行了优化。

但我不只是在构建一个个人助手。我正在构建一个引擎，该引擎能够通过实验循环和共享知识库，协调 5 种模型上无限数量的专业代理。为此，Hermes 的 Python 栈、执行隔离和研究流程是关键。

Hermes 是操作员。蜂群是团队。你和 Hermes 交流。Hermes 协调下方的一切。

### Karpathy 模式 (QMD + program.md)

这是最重要的部分。

![Image](https://pbs.twimg.com/media/HDc_gTrbYAAYFvr?format=jpg&name=large)

我采用了卡尔帕西的自动研究循环——他用于自动化机器学习研究的模式——并将其应用于增长。

每个代理有三个文件：

program.md -- 不可变的目标 + 单一北极星指标

\`strategy.md\` -- 可根据结果演变的"可编辑事物"

\`results.tsv\` -- 仅追加的实验日志

循环：代理读取当前策略。提出一个实验。执行。测量结果。指标是否改善？是，保留策略变更。否，恢复。记录失败。尝试其他方法。

```python
python
# experiment.py

VERDICT_THRESHOLD = 0.20  # 20% improvement = meaningful

def evaluate_experiment(self, experiment, results):
    if len(results) < experiment.sample_size_needed:
        return "running"
    avg_metric = sum(r.metric_value for r in results) / len(results)
    improvement = (avg_metric - experiment.baseline) / experiment.baseline
    if improvement > self.VERDICT_THRESHOLD:
        return "keep"
    elif improvement < -self.VERDICT_THRESHOLD:
        return "discard"
    else:
        return "inconclusive"
```

这是 QMD 发挥优势的地方。每个成果——研究扫描、内容草稿、性能数据、实验结论、策略决策——都会被保存到共享知识库中。QMD 使用混合搜索（BM25 + 向量 + LLM 重排序）对其进行索引。在本地运行。

当任何代理运行时，它不只是看到自己的历史，还会看到团队中其他每个代理所生成的内容：

群体不会因为模型的改进而变得更智能。它变得更智能是因为策略在逐步优化。第一天将是它有史以来最糟糕的一天。

为什么这对增长尤为重要：经过9年的手动实验，我知道瓶颈从来不是“我们没有想法”，而是“我们从已尝试的事物中学习得不够快。”这种架构使每个实验的结果能永久地被所有代理访问。

### 多模型路由

不是每个任务都需要 Claude。路由到能够处理每种任务类型的最便宜模型，是成本从数百降至个位数的关键。

当将小型模型分配到合适的任务时，它们产生的输出是大型模型的 2-3 倍。Mistral Nemo 以 0.02 美元/百万的价格负责路由和结构化处理。Qwen 以 0.26 美元/百万的价格负责创意写作。Claude 仅在需要级联决策时才会被调用。

在11个代理上完成一个完整周期的成本为$0.009。但实际上，我认为一旦针对质量进行优化，数值会略有上升，但仍然很便宜。

### 它如何融入实际工作流程

这不是玩具。它融入了团队实际的运作方式。

该群体与 ClickUp（或 Notion，或您使用的任何项目管理工具）集成。交付成果会落在那里。如果没有分配任务，代理们就会自主开展工作——进行研究、实验、优化，以达成您为他们设定的北极星指标。如果有紧急事项，您可以通过 Hermes（Telegram、Slack、命令行界面）进行分配，它会将任务委派给群体中合适的代理。

随着时间的推移，你在团队中构建社交图谱。Hermes + The Swarm 能更好地理解这些代理，弄清楚什么是有效的，并共同变得更智能。

### 对代理坦诚

让我说一些 AI 代理领域里没人想要说的话。

如果你一直在基于 AI 代理进行开发……你知道它们真实的样子。不是内容搬运工所描述的那样，也不是“完全自主”的幻想，而是现实。

智能体目前还不能端到端完成100%的复杂工作。目前还做不到。我认为，如果期望一个架构良好的智能体群体能承担50-75%的繁重工作，这是合理的。随着时间的推移，当模型和工具不断改进时，我们或许能逐步接近100%的目标。但目前，假装能做到100%是不诚实的。

95%的人使用人工智能。或许5%的人能从中看到实际的、累积的成果。

我试图回答的问题是：我们如何调整那个数字？我们如何从5%实现实际效果提升到10%、15%、20%？

我的看法是：关键不在于更好的模型。而在于更好的架构、协作、共享上下文、实验循环，以及能够学习且不放弃的团队。

每个人都在致力于让单个智能体更智能。我认为关键在于让智能体之间协同工作并相互学习。

## 结构化（1）

### 2026-03-23 03:17:30

#### 文章主旨

这篇文章的核心观点是：**AI 代理真正的价值，不在于单个代理有多聪明，而在于多个代理能否像团队一样协作、共享知识并持续通过实验变强。**  
作者基于自己 9 年增长实验经验，搭建了一个以 Hermes 为核心、Swarm 为执行团队的多代理系统，用来解决增长工作中“想法不缺、执行太慢、经验难沉淀”的问题。

#### 1. 问题背景：增长工作的瓶颈不是创意，而是速度与协同

- 作者做了 **9 年增长实验**，涉及增长黑客、分发、转化优化等。
- 增长工作的常见循环始终是：**提出假设 → 测试 → 衡量 → 保留或淘汰 → 重复**。
- 真正的问题不在“没有想法”，而在于：
  - 团队执行速度太慢；
  - 每周通常只能完成 **2-5 个实验**；
  - 大量时间浪费在协调，而不是执行；
  - 研究、分析、写作团队之间信息不互通；
  - 关键背景知识散落在人的脑海或 Slack 对话中，难以沉淀和复用。

**通俗理解**：  
就像一个公司明明有很多增长点子，但每次推进都要拉会、对齐、交接，最后效率非常低，且很多经验做完就丢了。

#### 2. 作者的判断：单个 AI 代理不行，必须像“团队”那样工作

- 作者尝试过多种 AI 代理方案，包括：
  - OpenClaw；
  - 带工具能力的独立代理；
  - “AI 员工”式整套方案。
- 这些方案反复失败，原因都类似：
  - **单个代理没有完整上下文；**
  - 它没有研究、分析、策略、反馈机制等配套角色；
  - 本质上只是一个“没有团队支持的提示词”。

- 作者因此得出结论：  
  **你不会雇一个只有写作能力、却没有研究员、分析师、策略负责人支持的人；同样，AI 代理也不能只靠单兵作战。**

#### 3. 解决方案：构建一个“群体框架”，让多个代理像团队协作

- 作者搭建了一个多代理系统：
  - 多个代理各自承担不同角色；
  - 每个代理有自己的：
    - 角色定义；
    - 工具；
    - MCP 访问权限；
    - 专属模型；
    - 上下文窗口。
- 它们之间可以：
  - 共享知识；
  - 交接工作；
  - 从彼此成果中学习。

- 整体架构中：
  - **Hermes** 是顶层操作员（operator）；
  - Hermes 负责控制集群、任务分发、人工覆盖、从下层代理中学习；
  - 下层代理组成 **Swarm（群体）**，完成研究、写作、分析、设计等具体工作。

- 作者提出了一个很关键的设计理念：  
  **“一个文件夹 = 一个团队”**

例如团队目录结构包含：
- `program.md`：团队使命、约束、语气规则；
- `brand-kit.md`：品牌规范；
- `agents/`：不同角色代理配置；
- `results/`：每个代理的策略演变记录和实验日志。

**通俗理解**：  
这相当于把一个团队“产品化”了。只要创建文件夹、写配置，就能启动一个 AI 团队。

#### 4. 为什么作者从 OpenClaw 转向 Hermes

作者重点解释了为什么最终选择 **Hermes** 而不是 **OpenClaw**。虽然两者表面上都支持持久代理、SOUL.md、技能、内存、MCP、自托管，但 Hermes 更适合作者要做的“多代理实验引擎”。

##### 4.1 Python 栈更适合 AI/ML 基础设施

- OpenClaw 基于 **Node.js**
- Hermes 基于 **Python**
- 作者认为，做多模型路由、实验循环、知识存储、异步编排时，Python 是更自然的技术栈。
- 关键库如：
  - `httpx`
  - `asyncio`
  - `apscheduler`
  - `numpy`
  都可直接通过 `pip` 使用。
- 作者直言：**这一点就占了他决策的 60%。**

##### 4.2 Hermes 更重视执行沙箱与安全隔离

- OpenClaw 运行在本地 Node 进程中。
- Hermes 提供 **5 种执行后端**：
  - 本地
  - Docker
  - SSH
  - Singularity
  - Modal
- Hermes 支持：
  - 只读根文件系统；
  - 禁用权限；
  - 命名空间隔离；
  - 容器加固。

- 这在作者场景中尤其重要，因为他要在 VPS 上运行 **30 多个可调用工具、能写文件、能调 API、能执行代码的代理**。

##### 4.3 子代理隔离更强

- Hermes 支持生成**独立子代理**，每个子代理有：
  - 独立对话；
  - 独立终端；
  - 独立 Python RPC 脚本。
- 好处是：父代理不会因为子代理工作而丢失上下文。
- 作者举例：
  - 当增长负责人要把研究任务并行分给 **3 位作者** 时；
  - Hermes 可以原生支持并行执行；
  - 且不会污染上下文窗口。

##### 4.4 持久内存能力更强

- OpenClaw 的内存主要是基于 Markdown 文件；
- 单代理场景还可以，但存在已知问题：
  - **重启后工作内存可能丢失；**
  - 用户可能因为静默压缩而丢掉几天上下文。

- Hermes 的优势：
  - 持久化内存；
  - 自动生成技能；
  - 重启后仍能保留。
- 再结合作者自己的 **QMD 知识库**：
  - Hermes 记住“怎么做”；
  - QMD 记住“团队学到了什么”。

##### 4.5 SOUL.md 热加载能力更实用

- 两者都有 `SOUL.md`；
- 但 Hermes 会在**每条消息重新加载**。
- 比如作者凌晨 2 点更新集群成员，Hermes 下一次交互立刻生效；
- 不需要重启、不需要重新编译、不需要清缓存。

##### 4.6 更适合研究与强化学习流程

- Hermes 支持：
  - 批量轨迹生成；
  - 并行 worker；
  - checkpoint；
  - 与 Atropos 的强化学习训练集成；
  - ShareGPT 导出用于微调。
- 作者认为，如果未来想让操作员基于真实任务数据进行微调，Hermes 已具备这条路径，而 OpenClaw 没有。

##### 4.7 诚实的权衡

作者并没有一味吹 Hermes，而是明确说：
- **OpenClaw 的用户体验更好**；
- 生态更大；
- 对个人助手场景更友好。

但作者要的不是个人助手，而是一个能：
- 协调**无限数量专业代理**；
- 覆盖 **5 种模型**；
- 跑实验循环；
- 使用共享知识库；
- 持续演化的引擎。

所以 Hermes 更适合他的目标。

#### 5. 这个系统如何运作：两阶段日常工作流

作者介绍了当前系统的实际运行方式：**两阶段每日循环**。

##### 阶段 1：自动规划

每天早上自动运行：
- 研究分析师先扫描信息；
- 增长负责人选定方向并分配任务；
- 然后系统暂停，等待人工审批。

##### 阶段 2：审批后并行执行

- 用户可以在喝咖啡时，通过 **Telegram** 审批。
- 审批通过后：
  - 写作代理并行工作；
  - 视觉内容生成；
  - 全部结果保存到知识库中。

- 作者指出：
  - 当前人类仍是流程中的“瓶颈”；
  - 只有等足够信任系统后，才会切换到 `auto_approve=True` 全自动模式。

**通俗例子**：  
这有点像一个总编系统。早上 AI 先选题、做提纲、分配任务，老板看一眼“同意/不同意”，然后写手、设计、视频等角色同时开工。

#### 6. 最核心的机制：Karpathy 式自动研究循环 + QMD 知识库

作者认为这部分最重要，并借鉴了 Karpathy 的自动研究模式，把它应用到增长工作上。

##### 6.1 每个代理有 3 个关键文件

- `program.md`：不可变目标 + 唯一北极星指标
- `strategy.md`：可根据结果迭代的策略
- `results.tsv`：只追加的实验日志

##### 6.2 工作循环

代理按以下流程运转：
- 读取当前策略；
- 提出一个实验；
- 执行；
- 衡量结果；
- 如果指标改善，则保留策略；
- 如果没有改善，则回滚；
- 记录失败并尝试别的方法。

##### 6.3 关键阈值示例

作者给了一个实验判断逻辑示例：

- 当结果样本量不足时，状态是 `running`
- 如果平均指标相对基线提升 **超过 20%**，则 `keep`
- 如果下降 **超过 20%**，则 `discard`
- 介于中间则 `inconclusive`

这说明系统不是“拍脑袋决策”，而是用明确规则判断实验成败。

##### 6.4 QMD 负责知识沉淀和检索

- 所有成果都会进入共享知识库，包括：
  - 研究扫描；
  - 内容草稿；
  - 性能数据；
  - 实验结论；
  - 策略决策。
- QMD 使用混合搜索：
  - **BM25**
  - **向量检索**
  - **LLM 重排序**
- 并且在本地运行。

- 这样一来，任何代理工作时，不只看到自己历史，还能看到其他代理做过的事。

**作者的关键观点**：  
群体不是因为模型升级而变聪明，而是因为**策略在不断优化**。  
所以：**“第一天将是它最差的一天。”**

#### 7. 为什么这对增长工作特别重要

- 作者基于 9 年经验强调：
  - 增长工作的最大瓶颈不是“没有新点子”；
  - 而是“从已尝试过的事情里学得不够快”。

- 这个系统的价值就在于：
  - 每一个实验结果都能被永久记录；
  - 所有代理都能访问这些经验；
  - 新实验不是从零开始，而是在过往经验之上继续优化。

**通俗理解**：  
传统团队做实验像“做完就忘”；  
这个系统则像“整个团队共享一套越来越厚的作战手册”。

#### 8. 多模型路由：把成本压得极低

作者特别强调：**不是每个任务都值得用最贵的模型。**

##### 模型分工示例

- **Mistral Nemo**
  - 用于路由和结构化处理
  - 成本：**$0.02 / 百万 tokens**
- **Qwen**
  - 用于创意写作
  - 成本：**$0.26 / 百万 tokens**
- **Claude**
  - 只在需要级联决策时调用

##### 成本效果

- 在 11 个代理上跑完整一轮的成本大约是：**$0.009**
- 作者也坦言：
  - 后续为了提升质量，成本可能会略有上升；
  - 但整体仍然“非常便宜”。

- 另一个关键数据是：
  - 小模型如果用在合适任务上，产出可以达到大模型的 **2-3 倍**。

#### 9. 它如何接入真实团队工作流

  - 更清楚哪个代理擅长什么；

  - 从而持续提升整体表现。
