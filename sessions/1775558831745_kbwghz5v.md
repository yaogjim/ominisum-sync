**Harrison Chase**

### AI 智能体的持续学习

大多数关于人工智能持续学习的讨论都聚焦于一件事：更新模型权重。但对于 AI 代理而言，学习可以发生在三个不同的层次：模型、框架和上下文。理解这些差异会改变你构建随时间改进的系统的思路。

智能体系统的三个主要层是：

- 模型：模型权重本身。
- Harness: 框架：围绕模型的框架，为代理的所有实例提供动力。这指的是驱动代理的代码，以及始终作为框架一部分的任何指令或工具。
- 上下文：存在于 harness 之外的额外上下文（指令、技能），并且可用于配置 harness。

![Image](https://pbs.twimg.com/media/HFExmQ5asAAkKq9?format=jpg&name=large)

示例 #1: 将其映射为类似 Claude Code 的编码代理：

- 模型：claude-sonnet，等
- 利用：Claude 代码
- 用户上下文：
  [CLAUDE.md](http://claude.md/)，/技能，mcp.json

示例 #2: 将这个映射到 OpenClaw：

- 型号：许多
- 框架：Pi + 一些其他脚手架
- 代理上下文：
  [SOUL.md](http://soul.md/)，来自 clawhub 的技能

当我们谈论持续学习时，大多数人会立刻想到模型。但实际上——一个 AI 系统可以在这三个层面都进行学习。

#### 模型层的持续学习

当大多数人谈论持续学习时，他们最常指的是：更新模型权重。

更新这一点的技术包括

[SFT](https://cameronrwolfe.substack.com/p/understanding-and-using-supervised)，RL（例如

[GRPO](https://cameronrwolfe.substack.com/p/grpo)

）等

这里的一个核心挑战是灾难性遗忘 — 当模型在新数据或新任务上更新时，它往往会在之前已知的内容上表现退化。这是一个开放的研究问题。

当人们为特定的代理系统训练模型时（例如，你可以将 OpenAI 的 Codex 模型视为是为其 Codex 代理训练的），他们大多是为整个代理系统进行训练。

[LORA](https://unsloth.ai/docs/get-started/fine-tuning-llms-guide/lora-hyperparameters-guide) 例如，你可以按用户粒度进行（如每个用户一个 LORA），但在实践中，这主要是在代理级别进行的。

#### 框架层的持续学习

如前所述，框架指的是驱动代理的代码，以及任何始终属于该框架的指令或工具。

随着 harnesses 变得越来越流行，已经有几篇论文讨论了如何优化 harnesses。

最近的一个是

[\*\*Meta-Harness: 端到端优化的模型框架](https://yoonholee.com/meta-harness/).\*\*

核心思想是代理在循环中运行。首先，你在一系列任务上运行它，然后对这些任务进行评估。然后，你将所有这些日志存储到文件系统中。接着，你运行一个编码代理来查看这些跟踪数据，并对框架代码提出修改建议。

![Image](https://pbs.twimg.com/media/HFEx20FbcAAmSmj?format=jpg&name=large)

与模型的持续学习类似，这通常在智能体层面进行。理论上，你也可以在更细粒度的层面上进行（例如，针对每个用户学习不同的代码框架）。

#### 上下文层的持续学习

“Context” 存在于 harness 之外，可用于配置 harness。Context 由指令、技能甚至工具等内容组成。这也常被称为记忆。

同样类型的上下文也存在于框架中（例如，框架可能包含基础系统提示、技能）。区别在于它是框架的一部分还是配置的一部分。

学习上下文可以在几个不同的级别上进行。

学习上下文可以在代理级别实现——代理拥有持久的“记忆”，并随时间更新自身配置。一个很好的例子是 OpenClaw，它拥有自己的

[SOUL.md](https://docs.openclaw.ai/concepts/soul) 会随时间更新。

学习上下文通常在租户级别（用户、组织、团队等）进行设置。在这种情况下，每个租户会获得随时间更新的专属上下文。示例包括

[Hex’s Context Studio](https://hex.tech/product/context-studio/)，

[Decagon’s Duet](https://decagon.ai/blog/introducing-duet)

，

[Sierra’s Explorer](https://sierra.ai/blog/explorer)

。

你也可以混合搭配！所以你可以拥有一个同时具备智能体级别上下文更新、用户级别上下文更新以及组织级别上下文更新的智能体。

这些更新可以通过两种方式完成：

- 在离线任务中事后进行。类似于 harness 更新——在一系列近期轨迹数据上运行以提取洞察并更新上下文。这就是 OpenClaw 所谓的
  [“dreaming”](https://docs.openclaw.ai/concepts/memory-dreaming).
- 在代理运行的热路径中。代理可以决定（或者用户可以提示它）在执行核心任务时更新其记忆。

![Image](https://pbs.twimg.com/media/HFEx7TUbIAAhZtI?format=jpg&name=large)

这里需要考虑的另一个方面是记忆更新的明确性。是用户在提示智能体进行记忆，还是智能体根据框架本身的核心指令进行记忆？

## 结构化（1）

### 2026-04-07 11:03:07

#### 文章主旨

这篇文章的核心观点是：**AI 智能体的持续学习，不只是在“更新模型参数”这一层发生**，还可以发生在 **harness（代理运行框架）** 和 **context（上下文/记忆）** 两层。  
理解这三层的区别，会直接影响你如何设计一个能“越用越聪明”的 AI 系统。

##### 1. 持续学习要分三层来看

作者先提出，智能体系统主要由三层组成：

- **Model（模型层）**：模型本身的权重，比如 `claude-sonnet` 这类底层模型。
- **Harness（框架层）**：驱动智能体运行的代码、固定指令和工具，也就是“代理外壳”。
- **Context（上下文层）**：放在 harness 外部、用于配置智能体的内容，比如额外指令、技能、记忆等。

作者强调：**大多数人一提持续学习，就只想到模型训练，但实际上这三层都可以学习。**

###### 文中案例

- 以类似 **Claude Code** 的编码代理为例：
  - Model：`claude-sonnet`
  - Harness：`Claude Code`
  - User context：`CLAUDE.md`、`/skills`、`mcp.json`

- 以 **OpenClaw** 为例：
  - Model：多个模型
  - Harness：`Pi` 加上一些配套框架
  - Agent context：`SOUL.md`、来自 `clawhub` 的技能

这些例子说明：**一个智能体最终能力的提升，不一定来自“换模型”，也可能来自外层框架和上下文的优化。**

##### 2. 模型层的持续学习：最常见，但也最难

这一层是大家最熟悉的持续学习方式，即直接更新模型权重。

###### 关键点

- 常见方法包括：
  - **SFT（监督微调）**
  - **RL（强化学习）**，例如 **GRPO**
- 主要难点是 **灾难性遗忘（catastrophic forgetting）**：
  - 模型学了新任务后，原来会的东西可能反而退化。
  - 作者认为这仍是一个**开放研究问题**。

###### 作者的判断

- 在实际应用里，如果有人为某个智能体系统专门训练模型，通常是**针对整个 agent 系统级别**来做。
- 理论上也可以做得更细，比如：
  - **每个用户一个 LoRA**
- 但现实中，这种细粒度做法还不常见，通常还是在**agent 级别**完成。

###### 通俗理解

可以把模型层学习理解为：  
**直接改“大脑”**。  
好处是能力可能整体增强，坏处是训练成本高，而且容易“学新忘旧”。

##### 3. Harness 层的持续学习：优化智能体“做事方式”

作者接着说，harness 指的是驱动智能体运行的那套代码、固定指令和工具。随着 agent 越来越流行，已经有研究开始专门优化这部分。

###### 关键点

- 作者提到一个较新的工作：**Meta-Harness: End-to-End Optimization of Model Harnesses**
- 核心流程是：
  1. 让 agent 在一批任务上运行
  2. 对结果做评估
  3. 把执行日志保存到文件系统
  4. 再让一个编码 agent 去分析这些轨迹（traces）
  5. 最后给出对 harness 代码的修改建议

###### 作者的判断

- 这类 harness 优化，和模型训练类似，通常也是在**agent 级别**进行。
- 理论上也可以更细，比如：
  - **每个用户一套不同的 harness 代码**
- 但实践中仍然较少这样做。

###### 通俗理解

如果说模型层是在改“大脑”，  
那 harness 层更像是在改 **“工作流程”和“操作系统”**。

比如同一个模型，换一个更合理的工具调用流程、更好的系统提示词、更顺手的代码框架，智能体表现就可能明显提高，**而且不需要重新训练模型**。

##### 4. Context 层的持续学习：让智能体逐步形成“记忆”

作者认为，context 是在 harness 外部、用来配置智能体的内容，包括：

- 指令
- 技能
- 工具
- 记忆（memory）

这一层实际上就是很多人说的“长期记忆”能力。

###### 关键点

- context 既可以在 **agent 级别**更新，也可以在更常见的 **tenant 级别**更新。
- 这里的 tenant 可以是：
  - 用户
  - 组织
  - 团队

###### 文中案例

- **Agent 级别记忆**：
  - **OpenClaw** 会持续更新自己的 `SOUL.md`
- **租户级别记忆**：
  - **Hex 的 Context Studio**
  - **Decagon 的 Duet**
  - **Sierra 的 Explorer**

###### 可以混合使用

作者特别指出，这些层级可以叠加：

- agent 级记忆更新
- user 级记忆更新
- org 级记忆更新

也就是说，一个系统可以同时拥有：

- 智能体自己的长期记忆
- 用户个人偏好记忆
- 企业级共享知识记忆

###### 更新方式有两种

###### 1）离线更新

- 在任务完成后，通过后台任务分析最近的 traces
- 提取经验，再写回 context
- OpenClaw 把这种方式叫做 **“dreaming”**

###### 2）在线更新

- 在 agent 执行任务的过程中，直接更新记忆
- 可以是：
  - agent 自己决定记住什么
  - 用户主动要求它记住某件事

###### 另一个重要维度：记忆更新是否显式

作者还提醒，要考虑记忆更新到底是：

- **用户明确要求**“记住这件事”
- 还是 agent 根据系统规则**自动记忆**

###### 通俗理解

这一层不是改模型，也不是改代码框架，而是在改智能体的 **“经验库”**。  
比如：

- 用户每次都喜欢用中文回复
- 某团队有固定代码规范
- 某公司有自己的业务知识和术语

这些内容都更适合放在 context 层持续积累，而不是重新训练模型。

##### 5. 三种持续学习方式的共同基础：Traces

在比较三层方法时，作者指出：**traces（执行轨迹）是核心基础设施**。

###### 关键点

- trace 指的是智能体一次完整执行过程的全路径记录。
- 无论你想优化哪一层，都离不开 trace 数据。
- 作者提到他们的平台 **LangSmith** 可以帮助收集这些 traces。

###### traces 的不同用途

- **用于模型层**
  - 收集 traces 后，可以找像 **Prime Intellect** 这样的合作方训练自己的模型
- **用于 harness 层**
  - 可以通过 **LangSmith CLI** 和 **LangSmith Skills**
  - 让编码 agent 读取这些 traces，再去改进 harness
  - 作者说，他们就是用这种方式提升了 **Deep Agents**
  - 并且在 **terminal bench** 上取得改进
- **用于 context 层**
  - 前提是 harness 本身要支持记忆学习
  - 作者提到 **Deep Agents** 已经以**生产可用（production ready）**方式支持：
    - 用户级记忆
    - 后台学习
    - 等更多能力

##### 6. 文章结论

作者想传达的重点是：

- **持续学习不是单一技术问题，而是系统设计问题**
- 智能体可以在三层持续进化：
  - 模型层：改权重
  - harness 层：改框架和流程
  - context 层：改记忆和配置
- 其中，**context 和 harness 的优化，很多时候比重新训练模型更现实、更容易落地**
- 而三者共同依赖的底层资产，就是 **traces**

##### 一个最简例子帮助理解

假设你有一个“代码助手”智能体，它可以这样持续学习：

- **模型层学习**：用更多编程数据微调模型，让它整体代码能力更强
- **harness 层学习**：优化工具调用流程，比如先读报错、再查文件、最后改代码，减少乱改
- **context 层学习**：记住某个用户喜欢 `TypeScript`、某团队要求写测试、某公司用特定架构

这样一来，智能体变强就不再只有“训练更大模型”这一条路，而是有了**三条并行可演进的路径**。

## 趣读意义（1）

### 2026-04-08 08:37:33

#### 一句话先说透

这篇文章真正想纠正一个常见误区：**AI 智能体的 “持续学习” 不只是在训模型，更像是在同时升级 “大脑、操作系统、和随身笔记本”。**

#### 通俗总结

- **模型层**：改权重，像给大脑做手术，能力上限最高，但成本高，还容易 “学会新的，忘了旧的”。
- **框架层（Harness）**：改智能体的代码、工具、固定指令，像升级操作系统，常常比改模型更快见效。
- **上下文层（Context）**：改记忆、技能、租户配置，像给它补一本越来越懂你的工作手册，最灵活，也最贴近业务。
- **核心燃料都是轨迹（Trace）**：智能体做过什么、怎么做的、哪里翻车了，这些过程日志才是真正的学习原料。
- **所以持续学习的本质**：不是 “再训练一次模型”，而是**把轨迹变成系统性改进**，在不同层做不同粒度的优化。

#### 这事为什么重要

你可以把三层理解成三个改进杠杆：

| 层 | 像什么 | 优点 | 问题 |
|---|---|---|---|
| 模型 | 大脑 | 天花板高 | 贵、慢、易遗忘 |
| 框架 | 操作系统 | 稳定提升流程能力 | 依赖工程能力 |
| 上下文 | 笔记本 / 记忆卡 | 灵活、个性化、适合业务 | 容易碎、要治理 |

文章最有价值的一点是：**别一上来就想着训模型。**  
很多产品问题，先改框架和上下文，ROI 可能高得多。

#### 对你这个产品经理的参考意义

##### 1. 做 AI 产品，先别把 “学习” 理解成 “训练”

很多团队一提持续学习，脑子里只有微调、RL、SFT。  
但现实里，**大多数能快速落地的改进，都发生在框架层和上下文层。**

对你来说，这意味着：

- 产品 roadmap 不该只押在模型团队
- 可以把 “学习能力” 拆成多个产品模块设计
- 很多业务价值，其实来自**记忆机制、工具编排、反馈闭环**，不是模型参数本身

一句话：**别把持续学习做成科研项目，要先做成产品系统。**

##### 2. 企业场景里，上下文层往往才是主战场

评论区那句很关键：**权限控制**。  
企业里很多知识不是 “模型学了就行”，因为不同人能看的东西不一样。

所以：

- 公共能力，适合放框架
- 个体偏好、团队知识、组织规则，适合放上下文
- 涉及权限隔离的信息，**几乎天然属于上下文层，不适合进模型层**

这对 B 端产品尤其重要：  
**你卖的不是更聪明的模型，而是更会 “分人、分组织、分权限” 地使用知识。**

##### 3. 真正的产品壁垒，正在从模型转向 “轨迹 + 评估 + 记忆治理”

文章反复强调 trace，本质上是在说：

> 谁能持续收集高质量轨迹，谁就能持续优化系统。

这对产品的启发非常直接：

- 没有轨迹，就没有学习闭环
- 没有评估，就不知道改进是真提升还是幻觉
- 没有记忆治理，智能体就会越学越乱

所以一个成熟 AI 产品的核心资产，可能不是模型本身，而是：

- 用户任务轨迹
- 任务成功 / 失败评估体系
- 多层记忆与配置系统
- 能把经验沉淀回系统的机制

说白了，**未来拼的不是谁会调用大模型，而是谁能把 “使用过程” 变成复利。**

#### 你可以直接拿去用的判断框架

当团队说 “我们要让智能体持续学习” 时，你可以直接追问三句：

- **是学模型，还是学框架，还是学上下文？**
- **学习依据是什么轨迹？怎么评估学得对不对？**
- **这次学习是全局生效，还是按用户 / 团队 / 组织分层生效？**

这三问，基本能快速分辨一个方案是 “真闭环”，还是 “PPT 式智能”。

#### 最后一句

这篇文章的价值，不在于提出了多新鲜的技术，而在于它把一个很容易被说玄的命题讲清楚了：

**AI 智能体的持续学习，不是一次训练动作，而是一套分层进化系统。**

如果你做产品，这个视角非常值钱 —— 因为它会让你少走很多 “先训再说” 的弯路，转而去设计真正能跑起来、还能越跑越聪明的产品机制。
