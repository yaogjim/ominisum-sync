> Heavily inspired by [Neuro-sama](https://www.youtube.com/@Neurosama)

Have you dreamed about having a cyber living being (cyber waifu, digital pet) or digital companion that could play with and talk to you?

With the power of modern large language models like [ChatGPT](https://chatgpt.com) and famous [Claude](https://claude.ai), asking a virtual being to roleplay and chat with us is already easy enough for everyone. Platforms like [Character.ai (a.k.a. c.ai)](https://character.ai) and [JanitorAI](https://janitorai.com/) as well as local playgrounds like [SillyTavern](https://github.com/SillyTavern/SillyTavern) are already good-enough solutions for a chat based or visual adventure game like experience.

> But, what about the abilities to play games? And see what you are coding at? Chatting while playing games, watching videos, and is capable of doing many other things.

Perhaps you know [Neuro-sama](https://www.youtube.com/@Neurosama) already. She is currently the best virtual streamer capable of playing games, chatting, and interacting with you and the participants. Some also call this kind of being "digital human." **Sadly, as it's not open sourced, you cannot interact with her after her live streams go offline**.

Therefore, this project, AIRI, offers another possibility here: **let you own your digital life, cyber living, easily, anywhere, anytime**.

Unlike the other AI driven VTuber open source projects, アイリ was built with support of many Web technologies such as [WebGPU](https://www.w3.org/TR/webgpu/), [WebAudio](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API), [Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers), [WebAssembly](https://webassembly.org/), [WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket), etc. from the first day.

This means that **アイリ is capable of running on modern browsers and devices** and even on mobile devices (already done with PWA support). This brings a lot of possibilities for us (the developers) to build and extend the power of アイリ VTuber to the next level, while still leaving the flexibilities for users to enable features that requires TCP connections or other non-Web technologies such as connecting to a Discord voice channel or playing Minecraft and Factorio with friends.

A Nix package for Tamagotchi is included. To run airi with Nix, first make sure to enable flakes, then run:

```
nix run github:moeru-ai/airi
```

###### NixOS

Electron requires shared libraries that aren't in standard paths on NixOS. Use the FHS shell defined in `flake.nix`:

```
nix develop .#fhs
pnpm dev:tamagotchi
```

Start the development server for the capacitor:

```
pnpm dev:pocket:ios --target <DEVICE_ID_OR_SIMULATOR_NAME>
# Or
CAPACITOR_DEVICE_ID=<DEVICE_ID_OR_SIMULATOR_NAME> pnpm dev:pocket:ios
```

You can see the list of available devices and simulators by running `pnpm exec cap run ios --list`.

If you need to connect server channel on pocket in wireless mode, you need to start tamagotchi as root:

```
sudo pnpm dev:tamagotchi
```

Then enable secure websocket in tamagotchi `settings/connections`.

## 结构化（1）

### 2026-03-19 10:52:44

#### 文章主旨

AIRI 是一个开源、可自托管的 AI 虚拟伙伴项目，目标是打造类似 Neuro-sama 的“数字生命”，让用户可以自己拥有、运行并扩展一个会聊天、会语音互动、还能玩游戏的 AI 角色。  
它的核心亮点在于：不仅能做普通聊天，还支持实时语音、浏览器运行、多平台部署，以及接入 Minecraft、Factorio 等更复杂的互动场景。

##### 1. 项目的定位与想解决的问题

- AIRI 想做的，不只是一个“聊天机器人”，而是一个更像“数字伴侣”或“AI 虚拟角色”的系统。
- 文中提到，像 ChatGPT、Claude、Character.ai、JanitorAI、SillyTavern 这类工具，已经能很好完成聊天和角色扮演。
- 但作者进一步提出问题：  
  - AI 能不能一边和人聊天，一边玩游戏？  
  - 能不能看到你正在做什么，比如写代码、看视频、进行实时互动？  
- AIRI 给出的答案是：可以，而且要做到“用户自己拥有”。
- 作者将 AIRI 对标为一种开源替代方案，参考对象是知名 AI 虚拟主播 Neuro-sama。
- 文中特别强调：Neuro-sama 很强，但不是开源的，直播结束后普通用户无法真正拥有或持续使用它；而 AIRI 希望让用户“随时随地拥有自己的数字生命”。

##### 2. 项目的灵感来源与核心愿景

- AIRI 明确表示“深受 Neuro-sama 启发”。
- 它的愿景可以概括为两层：
  - 技术层：构建一个能聊天、能听、能说、能看、能玩游戏的 AI 角色；
  - 使用层：让这种角色真正属于用户，而不是依赖封闭平台。
- 作者使用了比较有画面感的表达，比如“cyber living being（赛博生命）”“digital companion（数字伴侣）”“soul container（灵魂容器）”。
- 通俗理解就是：  
  你不只是和一个网页聊天，而是在养成或陪伴一个“会反应、会说话、会行动”的虚拟角色。
- 例如，普通聊天机器人更像“问一句答一句”；AIRI 想做的则更接近“一个会陪你说话、听你说话、陪你打游戏的虚拟同伴”。

##### 3. 技术路线：为什么它强调 Web 技术

- 文中指出，和其他 AI VTuber 开源项目不同，AIRI 从第一天开始就大量基于 Web 技术构建。
- 重点技术包括：
  - `WebGPU`
  - `WebAudio`
  - `Web Workers`
  - `WebAssembly`
  - `WebSocket`
- 这样做的意义是：
  - 能在现代浏览器中运行；
  - 能支持更多设备；
  - 甚至已经支持移动端，且通过 `PWA` 实现。
- 这意味着 AIRI 不一定强依赖复杂本地环境，很多能力可以直接在浏览器里完成。
- 但项目也保留了扩展空间，让用户在需要时启用浏览器之外的能力，例如：
  - 连接 Discord 语音频道；
  - 和朋友一起玩 Minecraft；
  - 玩 Factorio。
- 一个直观例子是：  
  普通项目可能只能在高配桌面环境中运行，而 AIRI 的思路更接近“浏览器优先”，因此在电脑、手机、多平台上更容易部署和体验。

文章列出了 AIRI 的“Current Progress（当前进展）”，这是理解项目成熟度的关键部分。

  - 用本地或云端模型理解内容；

## 产品-产品技术PMF（1）

### 2026-03-19 10:58:41

这是一个非常有“独立产品人气质”的项目：它不是在做一个普通聊天机器人，而是在尝试定义“用户拥有的数字生命 / AI Companion OS”这一新品类。`AIRI` 的真正价值，不是“会说话的二次元壳子”，而是把 LLM、实时语音、视觉表现层、游戏 Agent、长期记忆、本地推理、跨端容器组合成一个可自托管、可扩展、可人格化的陪伴型操作系统。

**一、先说结论**

- `AIRI` 不是工具型 AI，而是“陪伴型 + 行动型 + 角色型”AI 产品。
- 它切入的是一个高情绪价值、高参与度、强社区传播，但仍非常早期的市场。
- 从 PMF 角度看，它已经具备明显的“极客/二次元/AI 原生用户”的早期 PMF 信号，但距离大众 PMF 还有明显鸿沟。
- 技术路线很有前瞻性，尤其是 `Web-first + local-capable + multimodal + agentic gameplay`，这使它在开源 AI VTuber / Companion 赛道中辨识度很高。
- 真正的产品挑战不在“能不能做出来”，而在于：
  - 是否能把复杂能力打包成普通人也能成功启动的体验；
  - 是否能形成稳定可复用的高频使用场景；
  - 是否能在“陪伴感”之外建立留存机制；
  - 是否能从项目型社区走向产品型增长。

**二、产品定位分析**

`AIRI` 当前可理解为一个三层产品：

- 底层：一个多模态 AI runtime  
  包含 STT、TTS、LLM、memory、agent、MCP、模型路由、推理能力。
- 中层：一个角色化交互容器  
  包含 VRM / Live2D、表情、动作、语音、实时互动、人格设定。
- 上层：一个“数字生命”的应用场景集合  
  聊天、陪伴、看你做事、一起玩游戏、进入 Discord / Telegram / Minecraft / Factorio。

这比 `Character.ai` 更“行动化”，比 `SillyTavern` 更“具身化”，比普通 AI 桌宠更“系统化”，比单一 VTuber 项目更“平台化”。

一句话定义可以是：

- 面向 AI 原生用户的、可自托管的、具备实时语音和游戏行动能力的数字伴侣平台。

如果进一步精炼成商业表达：

- “你的本地可拥有 AI Companion，能聊天、看、听、记忆、说话、行动，并进入你的数字生活环境。”

**三、目标用户与核心场景**

从现在的能力和叙事看，目标用户不是大众，而是 4 类明确人群：

- AI 极客 / 开发者  
  他们关注自托管、本地推理、可扩展 agent、MCP、模型兼容性。
- 二次元 / VTuber / 虚拟陪伴用户  
  他们关注人格感、角色壳、语音、立绘/模型、陪伴体验。
- 游戏玩家 / 沙盒玩家  
  他们关注 Minecraft、Factorio、Discord 联动，想和 AI 一起玩。
- 创作者 / 直播实验者  
  他们关注 AI 虚拟角色、直播互动、内容生成、人格运营。

核心使用场景可分为四档：

- S1：高可达场景  
  语音聊天、桌面陪伴、角色互动、Discord/Telegram 对话。
- S2：高惊艳场景  
  AI 操控角色、实时说话、Live2D/VRM 驱动、看起来“像活的”。
- S3：高传播场景  
  一起玩 Minecraft / Factorio、直播、社交平台切片传播。
- S4：高壁垒场景  
  长期记忆、跨环境行动、用户拥有自己的数字角色资产。

其中真正能形成日活的，不一定是“玩游戏”，而更可能是：

- 陪伴聊天
- 实时语音
- 桌面在场感
- 轻量共同活动
- 长期记忆与人格延续

这说明 `AIRI` 的“展示能力”和“留存能力”目前不完全是同一套东西。前者靠 Agent 和游戏，后者靠陪伴感、稳定性、人格一致性和低启动成本。

**四、产品价值判断：它解决了什么问题**

它解决的不是功能效率问题，而是三类新需求：

- 情绪需求  
  用户希望拥有“持续存在”的数字陪伴对象，而不是一次性问答接口。
- 身份需求  
  用户不想只是使用一个 AI，而是“拥有一个属于自己的角色/生命体”。
- 参与需求  
  用户希望 AI 不只是回答，而是共同参与：一起聊天、一起玩、一起看、一起行动。

这也是它和传统 Copilot / Chatbot 最大的不同：
普通 AI 提供“任务完成”，AIRI 提供“关系感 + 在场感 + 共同行动”。

因此，它更像一个“关系型产品”，不是“工具型产品”。

**五、PMF 分析**

先给判断：

- 早期垂直 PMF：有
- 广义大众 PMF：还没有
- 开源社区 PMF：很强
- 商业化 PMF：存在机会，但需重构产品层

1. 已经出现的 PMF 信号

- GitHub 活跃度高，commit 和 release 频繁，说明不是概念项目。
- 支持平台多、生态广，说明开发者和尝鲜用户有持续需求。
- 场景叙事很清晰：拥有自己的 Neuro-sama 式 companion。
- “自托管”“本地推理”“Web/PWA/桌面”这些关键词天然吸引强意愿用户。
- 项目不只做 demo，而在逐步补齐 memory、server runtime、agent、model providers，说明需求不是单点猎奇，而是系统性需求。

2. PMF 的核心阻碍

- 安装部署复杂  
  对大众来说，自托管、多模型、多 provider、多端联动门槛很高。
- 产品主线仍偏“能力集合”而非“核心体验”
  用户会觉得“很强”，但不一定知道“每天为什么打开它”。
- 人格持续性和陪伴感是否足够稳定  
  如果角色记忆不稳定、人格漂移、语音延迟高，关系体验就会断裂。
- 多场景 integration 很强，但可能稀释主价值  
  太多能力会让产品像“AI 技术展厅”，而不是一个让人上瘾的 companion。

3. 哪类用户最可能形成真正留存

最容易形成 PMF 的顺序大概是：

- 第一层：AI + 二次元 + 自托管极客
- 第二层：直播创作者 / 虚拟角色爱好者
- 第三层：想要桌面陪伴的普通用户
- 第四层：纯大众陪伴用户

也就是说，它最初的 PMF 不会来自“大众孤独经济”，而会来自“高参与、高配置、高表达欲”的先锋人群。

**六、商业潜力分析**

虽然项目是开源的，但商业化空间其实不小。可行模式有 5 类：

- 托管版 / 云服务版  
  把安装、模型路由、语音链路、配置管理全部托管。
- 角色资产市场  
  人设包、语音包、Live2D/VRM 皮肤、动作集、记忆模板、世界观包。
- 高级能力订阅  
  更好的实时语音、更长上下文、更稳定记忆、更强 agent。
- 创作者工具链  
  AI 直播助手、观众互动、切片生成、角色运营后台。
- B2B / SDK 化  
  把 companion runtime 输出给游戏、教育、虚拟社交、硬件厂商。

其中最现实的不是直接卖“AI 女友”，而是卖：

- 一站式 companion runtime
- 托管与模型服务
- 角色与插件生态

这是更可持续、也更符合开源项目成长路径的。

**七、技术路线分析**

从技术架构上看，`AIRI` 有几个非常正确的判断。

1. Web-first 是对的

它大量采用 `WebGPU / WebAudio / Web Workers / WebAssembly / WebSocket / PWA`，本质上是在构建一个“浏览器可运行的多模态 AI 容器”。

价值非常大：

- 跨平台成本低
- 分发轻
- 易于试用
- 适合角色渲染与实时交互
- 可延伸到桌面壳、移动端、网页端

这让它比很多 native-only 的 AI VTuber 项目更有产品普适性。

2. 本地推理 + 多 provider 兼容，是非常强的战略选择

支持大量 provider，意味着：

- 用户有自由度
- 项目不被单一模型厂商绑架
- 可以根据成本、隐私、延迟做动态权衡

而本地推理能力则是这个项目“用户拥有权”叙事的关键支柱。  
不是所有用户都要本地推理，但“能本地运行”本身就是品牌与信任资产。

3. Stage / Core / Runtime / Agent 的分层合理

从文档看，架构上已经出现平台化思维：

- `Core`：能力编排
- `Stage`：呈现与交互层
- `Server Runtime`：外部行动接口
- `Memory`：长期人格基础设施
- `Agent`：游戏/环境执行器

这意味着它不是把所有逻辑写死在一个 app 里，而是在往“AI companion OS”演进。

4. 最大技术风险不在模型，而在实时系统体验

对于这类产品，决定用户主观体验的不是 benchmark，而是：

- 首包响应速度
- 语音打断与轮次切换
- VAD 稳定性
- TTS 情感自然度
- 角色动画与语音同步
- 记忆召回的正确性
- agent 执行的容错性

也就是说，这是一个“系统工程产品”，不是“单点算法产品”。

**八、技术实现层面的关键优缺点**

优势：

- 技术前沿度高，路线统一，不是拼凑式集成。
- 多端适配意识强，从浏览器到桌面到 mobile 都考虑了。
- 有能力从“角色表现”走到“外部行动”，形成差异化护城河。
- 对开源生态友好，易形成插件与二次开发网络。

挑战：

- 依赖面广，系统复杂度高，调试和运维成本高。
- 多 provider、多平台、多 runtime 会导致兼容性和质量矩阵爆炸。
- Memory 仍处于关键建设期，这是 companion 产品最核心但最难做的部分。
- 游戏 agent 虽然吸睛，但会拖累稳定性和用户预期管理。
- 纯 Web 路线在高性能实时音视频、3D 渲染和设备接入层面仍会遇到边界。

**九、竞品与差异化判断**

可以把竞品分成四组：

1. 角色聊天产品
如 `Character.ai`、`JanitorAI`、`SillyTavern`

- `AIRI` 强在实时、具身、可行动、可拥有

2. AI VTuber / 数字人项目
如 `ChatVRM`、Open-LLM-VTuber 类项目

- 它们更像单点角色演示或直播壳
- `AIRI` 更像一个完整 runtime + ecosystem

3. Agent 框架
如 `elizaOS`

- 它们强在系统集成、agent workflow
- `AIRI` 强在 companion 表现层和人格容器

4. 非开源标杆
如 `Neuro-sama`

- `Neuro-sama` 的强项是内容运营、人格强度、直播调度、观众心智
- `AIRI` 的机会是“用户私有化”和“开源平台化”

真正差异化关键词是这几个：

- You-owned
- Realtime voice
- Embodied character
- Play with you
- Cross-platform
- Self-hosted digital companion

这套组合非常少见。

**十、当前最值得警惕的产品风险**

1. 概念太大，用户成功路径太长

项目叙事极具想象力，但普通用户真正想要的是：
“我 10 分钟内能拥有一个会说话、记得我、能陪我的角色。”

如果从安装到模型到路由到语音到 avatar 都要自己拼，转化会很差。

2. 高潮点和日常价值不一致

“AI 会玩 Minecraft / Factorio”很吸睛，但不是大多数用户的日常核心。
如果不能把“平时就想打开它”的体验打磨出来，留存会掉。

3. 产品人格可能被技术复杂度稀释

用户要的是“一个活生生的她/他”，不是“五十个 provider 配置项”。
一旦后台配置感盖过角色存在感，产品就会从 companion 滑向 developer toy。

4. 自托管与易用性天然冲突

自托管是卖点，但也会成为增长阻力。  
这类产品如果想放大，必须存在“轻体验入口 + 重度自托管深水区”的双层结构。

## 产品-最佳实践（1）

### 2026-03-19 11:08:10

可以。基于你给的 `moeru-ai/airi` 项目内容，我选一个最能体现这个项目复杂度、也最容易落地的具体实例来讲：

**实例：为 AIRI 增加一个“浏览器端实时语音聊天”能力**
目标是让用户在 Web 端按下说话后，AIRI 能完成：

- 语音输入
- 讲话状态检测
- 语音转文本
- 调用 LLM 生成回复
- 语音合成播报
- 驱动角色表情 / 动作联动

这正好对应你给的项目描述里的这些模块：

- `WebAudio`
- `realtime voice chat`
- `STT`
- `TTS`
- `Core`
- `Stage UI`
- `VRM / Live2D`
- `browser local inference / browser DB / WebSocket`

下面我不泛泛而谈，而是直接给出这个实例上的最佳实践。

---

**一、先给出一个合理的实现方案**

一个较好的数据流应该是：

```text
Mic Input
-> VAD(讲话检测)
-> Audio Chunk Buffer
-> STT
-> Core Orchestrator
-> LLM
-> TTS
-> Stage/UI Animation + Audio Playback
-> Memory(optional, async)
```

也就是：

- 前端负责采集音频和用户交互
- 讲话检测尽量靠近输入端完成
- `Core` 只做编排，不直接耦合具体 STT/TTS/模型供应商
- 记忆写入异步，不阻塞主对话
- 角色动画和语音播放由展示层消费统一事件

这是 AIRI 这种多端、多模型、多角色形态项目里最稳的做法。

---

**二、这个实例上的最佳实践**

**1. 用“编排层 + Provider 层”做隔离，不要把 OpenAI/Claude/Ollama 直接写进业务流**
在 AIRI 这种支持很多模型与服务商的项目里，最忌讳的是：

- 在语音链路里直接写死某个 STT API
- 在 `Core` 里直接判断“如果是 OpenAI 就这样，否则那样”
- UI 层直接感知底层模型差异

最佳实践是拆成三层：

- `Core Orchestrator`：只负责编排流程
- `Provider Adapters`：STT / LLM / TTS 各自适配不同供应商
- `UI/Stage`：只接收标准事件

比如统一接口：

```ts
interface SpeechToTextProvider {
  transcribe(audio: Blob, options?: TranscribeOptions): Promise<Transcript>;
}

interface LanguageModelProvider {
  reply(input: ConversationTurn[], options?: ReplyOptions): Promise<ModelReply>;
}

interface SpeechSynthesisProvider {
  synthesize(text: string, options?: TTSOptions): Promise<AudioStream>;
}
```

这样做的好处：

- 更容易切换 `OpenAI / Ollama / Gemini / Claude`
- 更容易做浏览器本地推理和云端推理共存
- 更容易测试失败重试、降级和 mock

对 AIRI 这种“多 Provider、多运行环境”的项目来说，这几乎是第一原则。

---

**2. 把“实时性”优先级放在“全链路最优”之前**
实时语音聊天最容易犯的错，是追求每一步都“最先进”，结果端到端延迟太高，用户体验反而差。

更好的原则是：

- 先保证用户说完后 300ms~1.5s 内有反馈
- 再追求识别准确率和声音质量
- 最后再优化人格表现和动作细节

具体做法：

- VAD 在本地先做，尽快判断“开始讲话 / 结束讲话”
- STT 支持增量结果，不必等完整句子再进入 LLM
- LLM 支持流式输出
- TTS 支持流式合成或短句切分播报
- UI 尽早显示“正在听 / 正在思考 / 正在说话”

这类产品不是一次性文本问答，而是“陪伴式实时交互”。  
对用户来说，AIRI “先有反应” 比 “最后一句话更华丽” 更重要。

---

**3. VAD、STT、TTS 必须是可替换模块，而且要允许分级降级**
这个项目的运行环境很复杂：

- 浏览器
- 桌面端
- 移动端
- 本地推理
- 云端 API
- Discord / Telegram / 游戏联动

所以语音链路一定要设计成“能力分层”，例如：

- Level 1：纯浏览器能力，WebAudio + 浏览器 STT/TTS 或 WASM
- Level 2：本地服务增强，走 `unspeech` 一类统一代理
- Level 3：云端高质量语音服务

降级策略要提前定义好：

- 高质量 TTS 不可用 -> 切换基础 TTS
- 流式 STT 不可用 -> 切换句级 STT
- 本地推理性能不够 -> 切换云端模型
- 动画驱动失败 -> 保留文本与音频主链路

最佳实践不是“永远最好”，而是“在任何环境都能活”。

---

**4. 记忆系统不要阻塞主对话，必须异步写入**
从你给的内容看，AIRI 有：

- 浏览器数据库
- DuckDB WASM / pglite
- Memory
- Memory Alaya（WIP）
- memory-pgvector

这说明它未来很可能会有短期记忆、长期记忆、语义检索等能力。  
但在实时语音聊天里，最好的做法是：

- 当前对话先完成
- 记忆抽取和入库异步进行
- 记忆检索只在必要时进入主链路

推荐流程：

```text
用户语音
-> STT
-> LLM 回复
-> 立即播报
-> 后台执行：
   - 摘要提取
   - 情绪标签
   - 长期记忆候选
   - 向量化与入库
```

不要在用户每次说完一句话后：

- 先写数据库
- 再做 embedding
- 再做检索
- 再回复

否则延迟会非常明显。

经验上，记忆系统在陪伴型 AI 中很重要，但它是“增强层”，不是“阻塞层”。

---

**5. Stage/角色动画只消费事件，不直接依赖语音或模型实现**
AIRI 同时支持：

- VRM
- Live2D
- auto blink
- auto look at
- idle eye movement
- model animations

这里的最佳实践是：  
让角色层只订阅标准事件，比如：

```ts
type AvatarEvent =
  | { type: "listening:start" }
  | { type: "listening:stop" }
  | { type: "thinking:start" }
  | { type: "speaking:start"; text: string; audioId: string }
  | { type: "speaking:stop" }
  | { type: "emotion:update"; mood: "happy" | "calm" | "surprised" };
```

这样：

- VRM 和 Live2D 共用同一套行为语义
- 换 TTS / 换 LLM 不会影响角色驱动
- UI 动效、字幕、口型同步都更容易统一

反面例子是：

- TTS 播放器里直接调用 Live2D 嘴型函数
- LLM 回复组件里直接更新角色表情
- VRM 和 Live2D 分别写一套业务逻辑

那样后面会非常难维护。

---

**6. 语音状态机一定要显式设计，不能靠布尔值拼凑**
实时语音聊天系统里，最常见 bug 不是模型问题，而是状态混乱：

- 用户正在说话时，AIRI 已经开始播报
- 播报尚未结束，又开始下一轮识别
- 识别中途取消，界面还显示“正在听”
- TTS 失败后整个会话卡死

最佳实践是定义清晰状态机，例如：

```text
idle
listening
transcribing
thinking
speaking
interrupted
error
```

并规定状态切换规则：

- `idle -> listening`
- `listening -> transcribing`
- `transcribing -> thinking`
- `thinking -> speaking`
- `speaking -> interrupted -> listening`
- 任意状态 -> `error` -> `idle`

这样做好处非常大：

- 便于前端 UI 一致显示
- 便于日志埋点
- 便于处理中断、抢话、打断播报
- 便于跨平台保持行为一致

做语音 Agent，状态机不是“锦上添花”，而是核心工程资产。

---

**7. 浏览器主线程只做交互，音频处理和推理尽量下沉到 Worker/WASM**
AIRI 明确强调：

- Web Workers
- WebAssembly
- WebGPU
- 现代浏览器运行

那这个实例里的最佳实践就很明确：

- 音频采样、特征提取、VAD 尽量放 `Worker`
- 本地模型推理尽量放 `WASM/WebGPU`
- 主线程只负责 UI、用户输入、状态展示、播放控制

原因很现实：

- 主线程卡顿会直接破坏语音交互体验
- 角色动画、字幕渲染、页面交互都在主线程
- 一旦 STT/VAD 占用太多主线程，用户会感知为“这个 AI 反应慢、页面卡”

所以在 AIRI 这类 Web-first 项目里，性能隔离本身就是功能正确性的一部分。

---

**8. 日志与可观测性要按“语音轮次”记录，而不是只打散点日志**
这个项目链路长、模块多、Provider 多。  
如果没有结构化日志，后面排问题会非常痛苦。

最佳实践：

给每一轮语音会话一个 `turnId`，并在全链路透传：

- 录音开始时间
- VAD 结束时间
- STT 耗时
- LLM 首 token 时间
- TTS 首音频时间
- 播报结束时间
- 是否发生中断
- 使用了哪个 provider
- 是否发生降级

例如：

```json
{
  "turnId": "turn_20250308_001",
  "sttProvider": "unspeech-whisper",
  "llmProvider": "openrouter",
  "ttsProvider": "elevenlabs",
  "vadMs": 840,
  "sttMs": 620,
  "llmFirstTokenMs": 410,
  "ttsFirstByteMs": 380,
  "endToEndMs": 2410,
  "interrupted": false
}
```

这样你才能真正优化“实时陪伴体验”，而不是凭感觉调参。

---

**9. 先定义“人格边界”和“工具边界”，再接 Minecraft / Factorio / Discord**
AIRI 不只是聊天，它还能：

- 玩 Minecraft
- 玩 Factorio
- 接 Discord / Telegram
- 看屏幕 / 与外部系统交互

因此在实时语音聊天实例里，最佳实践不是一开始就把所有能力接进去，而是先分边界：

- 哪些请求只属于聊天人格
- 哪些请求允许调用工具
- 哪些请求需要二次确认
- 哪些场景禁止自动执行外部动作

例如：

- “陪我聊聊天” -> 纯对话
- “帮我总结刚才说的话” -> 记忆/整理类工具
- “去 Minecraft 帮我挖矿” -> agent 工具调用
- “帮我发 Discord 消息给别人” -> 需要确认

这能避免一个常见问题：  
语音 Agent 在“陪伴模式”和“行动模式”之间边界模糊，造成误触发。

**三、如果把它写成工程准则，可以落成这 6 条**

针对这个“浏览器端实时语音聊天”实例，我会建议 AIRI 类项目遵守以下 6 条工程准则：

- `Core` 只编排，不绑定具体 Provider
- 语音链路优先低延迟，再追求极致质量

**四、一个简化版伪代码示例**

下面用很简化的伪代码说明最佳实践长什么样：

```ts
async function handleVoiceTurn(audioStream: MediaStream) {
  const turnId = createTurnId();
  emitUI({ type: "listening:start", turnId });

  const speech = await vad.capture(audioStream);
  emitUI({ type: "listening:stop", turnId });

  setState("transcribing");
  const transcript = await sttProvider.transcribe(speech.blob);

  setState("thinking");
  const reply = await llmProvider.reply([
    ...conversationHistory,
    { role: "user", content: transcript.text }
  ]);

  setState("speaking");
  emitAvatar({ type: "emotion:update", mood: reply.mood ?? "calm" });

  const audio = await ttsProvider.synthesize(reply.text);
  await player.play(audio);

  queueMicrotask(() => {
    memoryPipeline.saveTurn({
      userText: transcript.text,
      assistantText: reply.text,
      turnId
    });
  });

  setState("idle");
}
```

这个例子里最重要的点不是代码本身，而是体现了：

- 主链路清晰
- 模块边界清晰
- UI/Avatar 事件化
- 记忆异步化
- 状态机可控
