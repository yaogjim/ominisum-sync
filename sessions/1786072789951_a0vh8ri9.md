## 分析要点

- **核心高价值点**：将代码提交、版本演进、社区讨论与时代背景联合分析，能同时理解项目的技术变化及其形成原因。
- **留存建议**：保留其研究思路，实际使用时需补充提示词、来源核验和输出验证流程（提出了可复用的开源项目研究视角，与AI辅助编程、学习方法和知识整理高度相关。）

**知识要点**

- 研究开源项目不必局限于静态代码，还可结合提交记录、Release、Issue和社区讨论还原演进过程。
- 按时间线组织多来源材料，有助于把零散技术决策转化为可阅读的项目发展叙事。
- 该方法依赖项目历史记录的完整性与提交质量，记录混乱时效果会明显受限。

**行动项**

- 选择一个历史记录较完整的开源项目，收集提交记录、Release、Issue及社区资料。
- 让AI按时间线整理项目从零到一的关键版本、技术决策和外部背景。
- 抽查编年史中的关键节点是否与原始提交和讨论记录一致。

## 产品-最佳实践（1）

### 2026-08-07 03:19:49

#### 实例：让 AI 编写《Vue.js 从首次公开到 1.0 的项目编年史》

下面以**Vue.js 从早期公开开发到 1.0 发布**为具体实例，演示如何让 AI 综合 Git 提交、Release、Issue、论坛讨论及时代背景，生成一部既有可读性、又经得起核查的开源项目编年史。

> **核心原则：**先建立可追溯的事实库，再让 AI 负责串联和叙事。  
> 不要直接把仓库交给 AI，然后要求它 “一次性写成小说”。

---

##### 一、先明确研究问题

不要使用过于宽泛的任务：

> 阅读 Vue.js 的全部历史，然后写一篇编年史。

应将范围限定为：

```text
项目：Vue.js
研究阶段：首次公开开发至 v1.0 发布
核心问题：
1. 项目最初想解决什么问题？
2. 最早可用版本是如何形成的？
3. 哪些用户反馈改变了 API 或架构？
4. 哪些提交属于真正的转折点？
5. v1.0 为什么在那个时间点发布？
6. 同时期前端生态对项目产生了什么影响？
```

最终交付物可以规定为：

```text
- 一份结构化事件表
- 一条按月划分的时间线
- 5～8 个关键转折点
- 一篇带引用的叙事型编年史
- 一份存疑事实和证据缺口清单
```

---

##### 二、建立可复现的研究目录

```text
vue-chronicle/
├── sources/
│   ├── commits.jsonl
│   ├── tags.json
│   ├── releases.json
│   ├── issues.jsonl
│   ├── pull_requests.jsonl
│   ├── discussions.jsonl
│   └── external-links.csv
├── evidence/
│   ├── events.csv
│   ├── people.csv
│   ├── claims.csv
│   └── contradictions.md
├── drafts/
│   ├── 01-origin.md
│   ├── 02-first-users.md
│   ├── 03-api-evolution.md
│   └── 04-road-to-v1.md
├── scripts/
│   ├── collect_git.py
│   ├── collect_github.py
│   └── build_timeline.py
└── README.md
```

###### 最佳实践

- 保存原始数据，不只保存 AI 摘要。
- 所有提交使用完整 SHA。
- 所有网页记录抓取日期。
- Issue、PR 和 Release 保存永久链接。
- 生成稿与证据库分开，避免叙事污染事实。
- 记录脚本、模型和提示词版本，保证结果可复现。

---

##### 三、采集第一手资料

###### 1. 克隆完整仓库

```bash
git clone --mirror https://github.com/vuejs/vue.git
cd vue.git
```

不要使用浅克隆：

```bash
# 不推荐
git clone --depth=1 https://github.com/vuejs/vue.git
```

浅克隆会丢失早期提交、分支和标签关系，不适合历史研究。

---

###### 2. 导出提交记录

```bash
git log \
  --all \
  --reverse \
  --date=iso-strict \
  --format='% H% x09% aI% x09% an% x09% ae% x09% P% x09% s' \
  > commits.tsv
```

建议同时导出每次提交的变更规模：

```bash
git log \
  --all \
  --reverse \
  --date=iso-strict \
  --numstat \
  --format='COMMIT% x09% H% x09% aI% x09% an% x09% s' \
  > commits-with-stats.txt
```

列出标签及其指向：

```bash
git for-each-ref refs/tags \
  --sort=creatordate \
  --format='%(refname:short)%09%(creatordate:iso-strict)%09%(objectname)%09%(subject)' \
  > tags.tsv
```

---

###### 3. 采集 GitHub 数据

使用 GitHub CLI：

```bash
gh api --paginate \
  repos/vuejs/vue/releases \
  > sources/releases.json

gh api --paginate \
  'repos/vuejs/vue/issues?state=all&per_page=100' \
  > sources/issues-and-prs.json
```

如果需要区分 Issue 和 Pull Request：

```bash
jq '[.[] | select (has ("pull_request") | not)]' \
  sources/issues-and-prs.json \
  > sources/issues.json

jq '[.[] | select (has ("pull_request"))]' \
  sources/issues-and-prs.json \
  > sources/pull_requests.json
```

###### 注意

GitHub API 返回的`issues`集合通常也包含 PR，不能直接把所有记录都当成 Issue。

---

###### 4. 收集外部背景资料

可以补充以下信息：

| 来源 | 用途 |
|---|---|
| 项目官方网站及历史文档 | 了解项目自我定位 |
| 作者博客、演讲和采访 | 了解设计动机 |
| Hacker News、Reddit、论坛 | 了解早期社区反应 |
| npm 历史版本 | 交叉验证发布时间 |
| 同时期框架的 Release | 建立技术背景 |
| 新闻、浏览器版本及标准进展 | 解释外部环境变化 |
| Internet Archive | 查找已经删除或改写的网页 |

建议建立外部来源表：

```csv
id,date,type,title,url,archived_url,retrieved_at,reliability
EXT-001,2014-02-01,blog,Early Vue announcement,https://...,https://web.archive.org/...,2026-01-01,A
EXT-002,2015-10-01,forum,Community discussion,https://...,https://web.archive.org/...,2026-01-01,C
```

---

##### 四、建立证据等级

不同来源的可信度不同，不能让 AI 将一条论坛评论和正式 Release 等量齐观。

| 等级 | 来源 | 适合证明什么 |
|---|---|---|
| A | Commit、Tag、Release、合并后的 PR | 代码何时发生了什么变化 |
| A-/B+ | 官方文档、路线图、作者同期文章 | 项目公开表达的目标 |
| B | 作者后来的采访和演讲 | 作者对历史的回忆 |
| C | Issue、论坛和社区讨论 | 用户需求、争议和社区反应 |
| D | 新闻转述、个人博客、社交媒体 | 外部传播和时代氛围 |
| E | AI 推断 | 只能作为待验证假设 |

###### 关键规则

> **Commit 可以证明 “代码发生了变化”，但通常不能独立证明 “作者为什么这样改”。**

例如：

- Commit 证明某个 API 被删除；
- Issue 可能说明用户遇到了什么问题；
- PR 讨论可能说明维护者如何权衡；
- 作者博客才能进一步支持其设计动机。

只有多种证据互相印证时，才能写出较强的因果结论。

##### 五、先让 AI 生成 “事件卡”，不要直接写文章

每一个重要历史事件都应转换为结构化事件卡。

###### 事件卡模板

```yaml
event_id: VUE-0017
date_start: YYYY-MM-DD
date_end: YYYY-MM-DD
title: 某项 API 的首次引入
event_type: feature
actors:
  - 项目维护者
summary: >
  该阶段引入了某项能力，并在后续提交中多次调整。
claims:
  - text: 该能力首次出现在某次提交中
    evidence:
      - type: commit
        url: https://github.com/vuejs/vue/commit/FULL_SHA
    confidence: high

  - text: 这项能力主要用于回应社区对某类开发体验的需求
    evidence:
      - type: issue
        url: https://github.com/vuejs/vue/issues/NUMBER
      - type: pull_request
        url: https://github.com/vuejs/vue/pull/NUMBER
    confidence: medium

uncertainties:
  - 无法仅凭现有资料确认该设计是否直接受到其他框架影响

narrative_value: turning-point
```

###### 推荐提示词

```text
你是一名软件史研究助理。

请根据我提供的 Commit、Issue、PR 和 Release 资料，提取 “事件卡”，不要直接写叙事文章。

要求：
1. 只记录有来源支持的事实；
2. 将 “代码变化”“公开理由”“你的推断” 分开；
3. 每项结论必须附来源；
4. 使用 high、medium、low 标记置信度；
5. 如果多个来源相互矛盾，保留矛盾，不要自行解决；
6. 不得根据今天的项目定位倒推早期目标；
7. 日期使用 ISO 8601 格式；
8. 输出 YAML。
```

##### 六、从大量 Commit 中找出转折点

不能只根据 Commit Message 中是否出现`important`、`rewrite`等关键词判断重要性。建议综合以下信号评分：

```text
事件重要性 =
  代码变更规模
  + 核心目录权重
  + 后续提交引用次数
  + Issue/PR 关联数量
  + Release Note 提及
  + API 兼容性影响
  + 社区讨论热度
```

###### 可操作的筛选规则

优先检查以下提交：

- 新建核心模块；
- 删除或替换核心实现；
- 修改公共 API；
- 修改构建方式或包结构；
- 大规模重命名；
- 引入测试体系；
- 修复导致版本延期的缺陷；
- Release 前后的集中提交；
- 被多个 Issue 或 PR 引用的提交；
- 后续被 revert 的提交。

###### 不要忽视 “小提交”

一行代码也可能改变公共 API 或修复关键错误，因此变更行数只能作为筛选信号，不能作为最终历史价值判断。

---

##### 七、建立 “事实 — 解释 — 叙事” 三层结构

###### 第一层：事实

```text
某日，提交 A 引入了某项 API。
若干天后，提交 B 修改了其参数形式。
Release C 首次将其写入公开发布说明。
```

###### 第二层：解释

```text
关联 Issue 显示，早期使用者在某种场景下遇到了重复代码问题。
PR 讨论表明，维护者在易用性和实现复杂度之间进行了权衡。
```

###### 第三层：叙事

```text
这个后来被视作理所当然的接口，最初并不是完整设计出来的。
它是在用户不断暴露边界条件、维护者反复收缩设计范围的过程中，
逐渐形成稳定形态的。
```

###### 最佳实践

叙事可以生动，但必须能反向追溯到前两层。  
如果删掉修辞后找不到支撑句子的证据，该句就不应作为事实出现。

##### 八、具体示范：如何写一个章节

以下是一个**写作结构示范**。其中事件名称和编号需要根据实际采集的 Vue.js 资料替换，不能直接当作已核验史实。

---

###### 第三章：一个 API 是怎样稳定下来的

###### 1. 开场：从一个不完整的实现开始

在早期版本中，某项后来成为 Vue.js 使用体验重要组成部分的能力，并不是以完整形态出现的。第一次相关提交只提供了最基本的实现，随后几周内，参数形式、错误处理和边界行为都经历了多次修改。

> 证据：提交`COMMIT_SHA_1`、`COMMIT_SHA_2`  
> 置信度：高

###### 2. 用户真正遇到了什么问题

Issue `#NUMBER`中，早期用户给出了一个实际场景：在某种组件或数据更新方式下，原有接口会产生重复逻辑。讨论没有立刻得出答案，维护者最初建议使用现有机制组合解决。

> 证据：Issue `#NUMBER`  
> 置信度：高

这里需要避免写成：

> “Vue.js 因为这个 Issue 才发明了该 API。”

除非维护者明确说明因果关系，否则更稳妥的表达是：

> “该 Issue 记录了社区对这一问题的早期需求，并与随后发生的 API 调整在时间上相邻。”

###### 3. 第一次尝试为什么没有保留

随后合并的 PR `#NUMBER`扩展了原有实现，但不久后又被另一项提交部分撤销。代码差异表明，第一次方案增加了额外分支；PR 讨论则显示维护者担心它使核心行为难以预测。

> 证据：PR `#NUMBER`、提交`COMMIT_SHA_3`  
> 置信度：中到高

这里可以进行有限度解释：

> 这次回撤说明，项目当时追求的不只是 “功能可用”，还开始重视 API 是否能够形成一致的心智模型。

如果讨论中没有出现类似表述，则应标记：

```text
这是根据代码变化作出的解释，置信度为中等，不是维护者的直接陈述。
```

###### 4. Release 使实验变成了承诺

当这项能力进入正式 Release Note 后，它的性质发生了变化。此前它只是仓库中可以继续调整的实验；进入版本说明之后，它开始成为项目向用户公开承诺的一部分。

> 证据：Release `vX.Y.Z`  
> 置信度：高

###### 5. 小结

这个 API 不是由单个 “天才时刻” 创造出来的，而是经过以下循环逐渐稳定的：

```text
初步实现
  → 用户暴露边界问题
  → 扩大能力范围
  → 复杂度上升
  → 回撤部分设计
  → 写入正式版本
```

这种模式比单次提交更能说明项目如何形成自己的设计风格。

##### 九、让 AI 写作时使用 “双轨引用”

正文可以保持可读性，但每个关键结论都要附引用。

###### 正文格式

```markdown
Vue.js 在这一阶段开始收缩某项 API 的职责范围 [^1]。
随后出现的 Issue 表明，早期用户仍然对其边界行为存在疑问 [^2]。
维护者最终选择保留较小的核心，并将更复杂的能力放到其他层处理 [^3]。
```

###### 脚注格式

```markdown
[^1]: Commit `完整 SHA`，日期，永久链接。
[^2]: Issue `# 编号`，相关评论的永久链接，访问日期。
[^3]: PR `# 编号`和 Release `vX.Y.Z`。
```

###### 最佳实践

- 引用到具体 Commit，而不是仓库首页；
- 引用到具体评论，而不是整个 Issue；
- 尽量使用完整 SHA；
- 网页资料同时保存原始链接和存档链接；
- 引用应支持紧邻它的结论，而不是仅仅 “主题相关”。

---

##### 十、处理因果关系时采用分级措辞

| 证据强度 | 推荐措辞 |
|---|---|
| 维护者明确说明 | “维护者表示，这项修改是为了……” |
| Issue 与提交直接关联 | “该修改直接回应了 Issue 中提出的……” |
| 时间接近、主题一致 | “这项修改可能与同期讨论有关……” |
| 只有代码变化 | “代码显示项目开始……” |
| 仅为 AI 推断 | “一种可能的解释是…… 但现有资料不足以确认。” |

###### 避免

```text
由于 React 当时流行，所以 Vue.js 决定修改该 API。
```

###### 改为

```text
该修改发生在相关技术路线受到广泛讨论的时期。
不过，目前尚未找到维护者明确表示两者存在直接因果关系的材料。
```

---

##### 十一、处理提交历史不规范的问题

原文回复中提到一个现实问题：有些项目的 Commit Message 并不清晰。

这时不要放弃，而要使用多源拼接。

###### 当 Commit Message 很差时，依次检查

1. `git show`中的实际代码差异；
2. 同一时间附近的提交；
3. Merge Commit；
4. 分支和 Tag；
5. Issue、PR、邮件列表；
6. Release Note 和 Changelog；
7. 测试文件变化；
8. 文档和示例变化；
9. 作者博客及论坛回复；
10. 后续提交中的 revert、fix 和引用。

例如，一个提交消息可能只有：

```text
fix
```

但其真实意义可以从以下信息恢复：

```text
- 修改了公共 API；
- 新增了回归测试；
- 与 Issue #123 时间相邻；
- Release Note 将其列为 breaking change；
- 后续提交引用了该 SHA。
```

因此，**提交信息不规范会增加工作量，但不等于无法研究。**

---

##### 十二、专门检查常见错误

###### 1. 幸存者偏差

今天仍保留的代码不一定是早期最重要的尝试。被删除、回滚和放弃的方案同样重要。

###### 2. 用今天的概念解释过去

不要直接把当前 Vue.js 的定位套到早期版本上。早期 README、文档和作者同期表述通常比今天的官网介绍更有历史价值。

###### 3. 把相关性写成因果性

两个事件时间接近，不等于前者导致后者。

###### 4. 只看主分支

功能可能先在实验分支开发，后来 squash 或重写后才进入主分支。

###### 5. 忽略时间戳差异

需要区分：

- Author Date；
- Committer Date；
- PR 创建时间；
- PR 合并时间；
- Tag 创建时间；
- Release 发布时间；
- npm 实际发布时间。

###### 6. 过度相信作者回忆

多年后的采访很有价值，但人的回忆会重构。最好与同期提交、文章和讨论交叉验证。

###### 7. 让 “小说感” 覆盖不确定性

叙事流畅不代表事实正确。AI 尤其容易自动补全缺失的动机、冲突和转折。

##### 十三、推荐的 AI 工作流

```mermaid
flowchart TD
    A [克隆完整仓库] --> B [导出 Commit/Tag/ 分支]
    C [抓取 Issue/PR/Release] --> D [统一时间与数据格式]
    E [收集博客 / 论坛 / 新闻] --> D
    B --> D
    D --> F [生成结构化事件卡]
    F --> G [聚类为历史阶段]
    G --> H [识别关键转折点]
    H --> I [人工核验引用和因果关系]
    I --> J [生成章节草稿]
    J --> K [反向事实审计]
    K --> L [发布带脚注的编年史]
```

###### 分工原则

| 工作 | AI | 人 |
|---|---:|---:|
| 摘要大量提交 | 主力 | 抽查 |
| 聚类相似事件 | 主力 | 调整 |
| 识别候选转折点 | 建议 | 决策 |
| 判断代码真实语义 | 辅助 | 负责 |
| 判断历史因果 | 辅助 | 负责 |
| 查找矛盾 | 主力 | 核验 |
| 写叙事初稿 | 主力 | 编辑 |
| 最终事实签字 | 不负责 | 负责 |

##### 十四、用于生成终稿的提示词

```text
你是一名严谨的软件史作者。

请根据事件卡和证据表，撰写《Vue.js 从首次公开到 v1.0》的一个章节。

写作要求：
1. 使用时间顺序，但不要写成提交日志流水账；
2. 围绕 “问题 — 尝试 — 反馈 — 调整 — 结果” 组织情节；
3. 可以采用有节奏感的叙事语言，但不得虚构对话、心理活动或冲突；
4. 每个关键事实必须附脚注；
5. 明确区分：
   - 代码能够直接证明的事实；
   - 维护者公开表达的动机；
   - 根据多项材料得出的解释；
6. 没有足够证据时，使用 “可能”“现有材料显示”“尚不能确认” 等措辞；
7. 不得将时间相邻自动写成因果关系；
8. 不得使用项目后来的成功反向解释早期决策；
9. 章节末尾列出：
   - 关键转折点；
   - 仍待确认的问题；
   - 使用的第一手资料；
10. 输出 Markdown。
```

##### 十五、发布前审计清单

###### 事实审计

- [ ] 每个日期都能找到原始来源；
- [ ] 每个 Commit 链接都使用正确 SHA；
- [ ] Issue 和 PR 没有混淆；

- [ ] 删除或回滚的方案也被纳入检查。

###### 因果审计

- [ ] “因为”“导致”“为了” 都有直接证据；
- [ ] 时间相邻但无直接证据时使用保守措辞；
- [ ] AI 推断被明确标记；
- [ ] 相互矛盾的来源没有被擅自合并；
- [ ] 没有用项目今天的定位倒推早期动机。

###### 写作审计

- [ ] 正文不是 Commit 列表；
- [ ] 每章有一个明确的问题；
- [ ] 技术变化与用户需求、社区反馈相互关联；
- [ ] 小说化只体现在结构和语言，不体现在虚构事实；
- [ ] 读者可以沿脚注重建主要结论。

##### 十六、这个方法的最佳实践总结

1. **限定范围**：先研究一个版本阶段，不要一开始处理整个项目历史。
2. **完整采集**：Commit、Tag、Release、Issue、PR 和外部材料缺一不可。
3. **结构化优先**：先生成事件卡，再生成故事。
4. **来源分级**：代码、官方记录、作者回忆和社区评论不能等量齐观。
5. **事实与解释分离**：代码证明 “发生了什么”，其他资料帮助解释 “为什么”。
6. **因果关系保守表达**：宁可留下疑问，也不要自动补全动机。
7. **保留失败路线**：被回滚的设计往往比最终方案更能体现决策过程。
8. **使用永久引用**：完整 SHA、具体评论链接和网页存档是编年史的基础设施。
9. **人工负责最终判断**：AI 擅长读取、归纳和写作，但不能承担历史真实性责任。
10. **把可追溯性置于可读性之前**：最好的项目编年史既像故事，也能像研究报告一样被复核。

最终产物不应只是 “AI 总结了一个仓库”，而应当是一部能够回答以下问题的软件史：

> 这个项目在什么环境下出现，最初解决了什么问题，经历了哪些失败和选择，又如何一步步变成后来人们熟悉的样子。

##### 效果取决于项目资料质量

这种方法并非适用于所有项目。如果提交信息随意、历史记录缺失，或关键讨论发生在不可访问的渠道，AI 很难准确还原因果关系。生成的“小说式”叙事也可能放大推断，因此更适合作为探索入口，而不是未经核验的事实记录。
