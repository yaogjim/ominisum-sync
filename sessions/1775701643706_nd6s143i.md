## 分析要点

- **核心高价值点**：最有价值的点是提出并解释了“大脑、手、记忆”解耦架构，这为长期运行、多工具、安全隔离的智能体系统提供了可复用的设计框架。
- **留存建议**：长期保留（对 AI 智能体基础设施产品化趋势、企业落地方式和架构拆分思路有较强参考价值。）

**知识要点**

- Managed Agents 将 agent harness、沙盒、状态恢复、凭证管理等基础设施托管化，显著降低企业部署门槛。
- Claude Code 面向个人本地使用，而 Managed Agents 面向企业云端长期运行和产品嵌入。
- “大脑-手-记忆”解耦可提升智能体系统的弹性、安全性和组件独立演进能力。
- 模型厂商自带 harness 的优势在于能随模型迭代持续优化，减少企业自建框架的维护负担。
- 平台绑定、上下文管理和成本可预测性仍是托管智能体方案的重要限制。

**行动项**

- 如果你在做企业级 AI 应用，评估是否应优先采用托管 Agent 基础设施而非自建全栈调度系统。
- 将“大脑-手-记忆”解耦框架纳入自己的 Agent 系统架构设计清单。
- 为现有或计划中的 AI Agent 项目补做平台绑定、上下文策略和成本预算评估。
- 关注 Anthropic 与 OpenAI 等平台在托管 Agent 赛道的后续竞争和能力开放节奏。

#### 它是什么？和 Claude Code 有什么区别？

如果你用过 Claude Code，你知道 AI 智能体怎么工作：你给它一个任务，它自己规划步骤、调用工具、写代码、改文件，一步步把事做完。

Claude Code 跑在你自己的电脑上，是给开发者个人用的命令行工具。 你关了电脑，它就停了。

Managed Agents 跑在 Anthropic 的云上，是给企业用的 API 服务。 它可以 24 小时不间断运行，断线了也不丢进度，你的产品可以直接内嵌智能体能力。Notion 就是这么干的：用户在 Notion 里把任务分配给 Claude 智能体，智能体在后台干完活把结果交回来，用户全程不需要离开 Notion。

![Image](https://pbs.twimg.com/media/HFayu1wXAAAlyLW?format=jpg&name=large)

几种典型用法：

- 事件触发型：系统发现 bug，自动派智能体修复并提 PR，中间不需要人介入。
- 定时型：每天早上自动生成 GitHub 活动摘要或团队工作简报。
- 即发即忘型：在 Slack 里给智能体派个活，它做完把表格、PPT、App 交回来。
- 长时间任务型：跑几个小时的深度研究或代码重构。

#### 和企业自己搭的云端智能体有什么区别？

能自己搭，但很贵很慢。

一个能上线的智能体，需要的东西远比“调一下 API”多得多：沙盒环境（sandbox，一个隔离的安全空间，AI 在里面跑代码、改文件，不管怎么折腾都不会影响外面的真实系统，相当于给 AI 一台专用虚拟电脑）、凭证管理、状态恢复、权限控制、全链路追踪……

很多企业客户之前需要一整个工程师团队专门搞这些。现在开箱即用，工程师可以去做产品真正核心的部分。

最早他们把所有东西塞进一个容器：AI 的推理循环、代码执行环境、会话记录，全在一起。好处是简单，坏处是鸡蛋全在一个篮子里，容器一挂，整个会话就丢了，而且没法单独替换某个部分。

后来他们做了一个关键拆分：

![Image](https://pbs.twimg.com/media/HFay5N_XIAALx1w?format=jpg&name=large)

- “大脑” 是 Claude 和它的调度框架，负责思考和决策。
- “手” 是沙盒和各种工具，负责执行具体操作。
- “记忆” 是独立的会话日志，记录发生的一切。

三者互不依赖，任何一个挂了都不影响其他两个。

这个拆分带来几个实际好处：

#### 快

不是每个任务都需要启动完整的沙盒环境，现在只有 AI 真的需要跑代码时才按需启动。首次响应延迟中位数降了约 60%，极端情况降了超过 90%。

#### 安全

AI 生成的代码跑在沙盒里，而访问外部系统的凭证存在沙盒外面的安全保险箱里，两边物理隔离。比如访问 Git 仓库，系统初始化时就把代码克隆好了，AI 正常用 git push/pull，但 Token 本身对 AI 不可见。对于 Slack、Jira 这类服务，通过 MCP 协议接入，请求经过代理层，代理层去保险箱取凭证调服务，AI 全程不经手凭证。

![Image](https://pbs.twimg.com/media/HFay7_wXoAAMhaM?format=jpg&name=large)

#### 灵活

大脑不关心手是什么。工程博客里有句话很有意思：调度框架不知道沙盒到底是一个容器、一部手机、还是一个宝可梦模拟器。 只要符合“名字和输入进去，字符串出来”的接口就行。

这也意味着多个大脑可以共享手，一个大脑可以把手交给另一个大脑，为多智能体协作打下了基础。

#### 局限性

Managed Agents 并不是万能的。几个需要注意的点：

部分功能还在研究预览阶段。 多智能体协作、高级记忆工具、自我评估迭代（让智能体自己判断任务完成质量并反复改进）这些能力目前还没有全面开放，需要申请才能使用。

平台绑定。 选择 Managed Agents 意味着你的智能体基础设施绑在了 Anthropic 生态里。如果未来想换模型或换平台，迁移成本不可忽视。

上下文管理仍然是难题。 虽然会话日志独立存储，但长时间任务中哪些信息该保留、哪些该丢弃，仍然涉及不可逆的决策。这是一个持续挑战，他们目前的做法是把上下文存储和上下文管理分开：存储保证不丢，管理策略随模型进化调整。

成本可预测性。 0.08 美元/会话小时听起来不多，但智能体跑几个小时的复杂任务，Token 消耗加上运行时费用，成本可能不低。企业需要做好预算评估。

Managed Agents 说明大多数企业离“全面用 AI 智能体干活”还有很长的路要走。基础设施的门槛降低了，但怎么定义好的任务、怎么设计好的工作流、怎么建立信任让 AI 接触核心业务数据，这些问题 Managed Agents 帮不了你。

#### AI 智能体基建的“AWS 时刻”

看起来 Managed Agents 走的是 AWS 当年的老路：先有了计算能力，然后把运行环境也包了。十年前企业纠结“上不上云”，现在纠结“Agent 基础设施自建还是托管”。历史经验告诉我们，大多数企业最终会选择托管，因为基础设施从来不是核心竞争力。 OpenAI 也推出了自己的 Agent 平台 Frontier，这个赛道的竞争刚刚开始。

从技术角度看，“大脑和手分离”这个架构思路值得关注。它让系统的每个部分都可以独立演进：模型升级了，换大脑；需要新工具，加一双手；存储方案改了，替换记忆层。工程博客里的类比说得好：操作系统的 read() 命令不关心底下是 1970 年代的磁盘还是现代 SSD，抽象层稳定了，底下的实现随便换。

从使用角度看，如果你是企业开发者，想在自己的产品里嵌入 AI 智能体能力，Managed Agents 可能会省掉你几个月的基础设施工作。六种语言（Python、TypeScript、Java、Go、Ruby、PHP）有 SDK 支持。如果你已经在用 Claude Code，更新到最新版，输入 /claude-api managed-agents-onboarding 就能开始。如果你是普通 AI 爱好者，短期内最直观的感受可能是：你用的那些 SaaS 产品里，会有越来越多的 AI 智能体在后台帮你干活，而这些智能体很可能就跑在 Managed Agents 上。

定价参考：Token 费用按 Anthropic API 标准价格，运行时 0.08 美元/会话小时（空闲不计费），网页搜索 10 美元/千次。

## 结构化（1）

### 2026-04-09 02:27:23

#### 主旨概括

Anthropic 推出的`Claude Managed Agents`，本质上是在卖 “一整套可直接上线的 AI 智能体托管基础设施”，让企业不必自己搭云端运行、沙盒、安全、状态恢复等复杂系统。  
这可能改变 AI 智能体基建市场格局：原本需要工程团队做几个月的事，现在几天到几周就能上线，也会挤压一部分做智能体基础设施的创业团队空间。

##### 1. 这是什么：把 AI 智能体 “托管上云”

- `Claude Managed Agents`是 Anthropic 提供的企业级托管服务：用户只要描述想要什么样的智能体，Anthropic 负责在云端运行、维护基础设施，并按使用量收费。
- 它和`Claude Code`的核心区别是：
  - `Claude Code`：跑在本地电脑上，偏个人开发者工具，电脑关机就停止。
  - `Managed Agents`：跑在 Anthropic 云上，面向企业 API，可 24 小时持续运行，断线也能恢复。
- 这意味着企业可以把智能体能力直接嵌入自己的产品，而不是只给开发者一个命令行工具。

**典型场景包括：**
- 事件触发型：发现 bug 后，自动修复并提交 PR。
- 定时型：每天自动生成 GitHub 活动摘要或团队简报。
- 即发即忘型：在 Slack 里丢个任务，智能体完成后返回表格、PPT、App。
- 长时间任务型：执行数小时的深度研究或代码重构。

##### 2. 为什么重要：省下的不只是人力，而是整套基建负担

- 企业当然可以自己搭智能体系统，但真正上线需要的不只是 “调 API”，还包括：
  - 沙盒环境
  - 凭证管理
  - 状态恢复
  - 权限控制
  - 全链路追踪
- 文章强调，很多企业此前要专门配一个工程团队做这些，现在变成 “开箱即用”。

**更深层的价值在于：**
- 自建的 agent harness（调度 / 运行框架）很容易随着模型升级而过时。
- 因为模型厂商最清楚模型的局限和优化方式，所以他们做的托管框架往往比第三方更适配模型本身。

**文中给出的关键例子：**
- Anthropic 工程博客提到，`Claude Sonnet 4.5`在接近上下文窗口极限时会 “焦虑”，容易草草结束任务，因此他们曾加入 “上下文重置” 补丁。
- 但`Claude Opus 4.5`发布后，这个问题消失了，旧补丁反而成了累赘。
- 这说明如果企业自己维护一套调度框架，每次模型升级都可能要重新适配；而托管服务可以由 Anthropic 持续代为优化。

##### 3. 谁已经在用：实际案例说明落地速度很快

###### Notion
- 用户可以直接在 Notion 工作区里把编码、做 PPT、整理表格等任务交给 Claude。
- 支持**几十个任务并行运行**，团队还能围绕同一个结果协作。
- 用户不需要离开 Notion，就能把复杂、开放式任务委托给智能体。

###### Sentry
- 做出了 “从发现 bug 到提交修复代码” 的全自动流程。
- AI 调试工具`Seer`找到问题根因后，Claude 会直接写补丁并开 PR。
- 工程总监表示：**几周就上线了**，并且省掉了自建基础设施的持续运营成本。

###### Rakuten
- 在工程、产品、销售、市场、财务等多个部门部署专项智能体。
- **每个智能体一周内上线**。
- 通过 Slack 和 Teams 接收任务，交付的是表格、PPT、App 等实际成果。

###### General Legal
- 以前需要提前预判各种用户问题，并为每类问题开发检索工具。
- 现在智能体可以根据用户问题，**临时生成工具**去查数据。
- CTO 表示：**开发时间缩短了 10 倍**。

###### 其他接入案例
- `Atlassian`：把智能体接进 Jira，开发者可直接分配任务。
- `Asana`：推出 AI Teammates，让 AI 在项目管理里承担协作角色。

##### 4. 技术原理：把 “大脑” 和 “手” 拆开

Anthropic 的核心架构思路是：**“大脑” 和 “手” 分离**。

###### 早期问题
- 最初他们把推理循环、代码执行环境、会话记录都塞在一个容器里。
- 好处是简单；坏处是：
  - 容器一挂，整个会话丢失
  - 各模块难以单独替换或升级

###### 后来的三层拆分
- **大脑**：Claude 模型 + 调度框架，负责思考、规划、决策。
- **手**：沙盒和工具，负责执行具体操作。
- **记忆**：独立会话日志，记录全过程。

###### 这样拆分的好处

**1）更快**
- 不是每次都要启动完整沙盒，只有真正需要执行代码时才按需启动。
- 结果是：
  - **首次响应延迟中位数下降约 60%**
  - **极端情况下下降超过 90%**

**2）更安全**
- AI 生成的代码在沙盒里运行。
- 访问外部系统的凭证保存在沙盒外的 “保险箱” 中，与 AI 物理隔离。
- 例如：
  - Git 仓库会提前克隆好，AI 能正常`push/pull`，但看不到 Token。
  - Slack、Jira 等通过 MCP 协议接入，请求先经过代理层，由代理去保险箱取凭证，AI 不直接接触密钥。

**3）更灵活**
- “大脑” 不需要知道 “手” 具体是什么，只需要符合输入输出接口。
- 这意味着：
  - 可以替换不同类型的执行环境
  - 多个智能体可共享同一套工具
  - 一个智能体还能把工具交给另一个智能体，便于多智能体协作

##### 5. 局限和风险：它不是万能解法

###### 部分能力还没全面开放
- 多智能体协作
- 高级记忆工具
- 自我评估迭代  
这些目前仍在研究预览阶段，需要申请才能使用。

###### 平台绑定风险
- 一旦采用`Managed Agents`，企业的智能体基础设施会较深绑定在 Anthropic 生态中。
- 未来如果想切换模型或平台，迁移成本可能不低。

###### 上下文管理仍很难
- 虽然会话日志可以独立保存，不容易丢失数据，但长任务里 “哪些信息该保留、哪些该丢弃” 依然是难题。
- Anthropic 的做法是把：
  - **上下文存储**：保证信息不丢
  - **上下文管理**：根据模型能力持续调整策略  
  分开处理。

###### 成本需要评估
- 定价包括：
  - Token 费用：按 Anthropic API 标准价格
  - 运行时费用：**0.08 美元 / 会话小时**（空闲不计费）
  - 网页搜索：**10 美元 / 千次**
- 单价看起来不高，但如果智能体持续跑数小时复杂任务，总成本仍可能不低，企业需要做预算测算。

##### 6. 文章的核心判断：这是 AI 智能体基建的 “AWS 时刻”

- 作者认为，`Managed Agents`很像当年 AWS 把计算能力和运行环境一起托管出去的路径。
- 十年前企业纠结的是 “上不上云”；现在开始纠结的是 “Agent 基础设施要不要自建”。
- 文章判断：**多数企业最终可能还是会选择托管**，因为基础设施通常不是核心竞争力。

**为什么这件事值得关注：**
- 对企业开发者来说，它可能直接省掉几个月的基建工作。
- 对普通用户来说，未来很多 SaaS 产品里的 AI 功能，背后可能都运行在类似`Managed Agents`的平台上。
- 对行业来说，这也意味着：
  - 智能体基础设施平台化会加速
  - 大厂集中化趋势可能增强
  - 做底层 agent infra 的团队会面临更大压力

这篇文章的重点不是 “Anthropic 又发了个新功能”，而是：**Anthropic 正在把 AI 智能体从 “模型能力” 升级成 “可直接托管的企业基础设施服务”**。一旦这种模式跑通，未来企业做 AI 智能体，很可能会像今天用云服务一样，越来越少自建、越来越多依赖大厂平台。

Managed Agents 降低了 “怎么跑” 的门槛，但没解决 “跑什么、怎么验收、出了错谁负责”。

很多软件会从 “驾驶舱” 变成 “任务前台”。

###### 判断一：你该做 “Agent 基建”，还是 “Agent 应用层”
如果你是创业或做新业务，这篇文章给出的方向很明确：

**尽量别从通用基建切入，优先做垂直任务层。**

原因很简单：
- 大厂天然更懂模型边界
- 大厂有更强的 infra、价格、生态和默认入口
- 通用层越往下，越容易被平台收编

更优的切法是：
- 选一个高频、高价值、可验收的任务
- 把 Agent 深深嵌进业务场景
- 让用户获得 “交付结果”，不是 “模型能力”

例如：
- 自动修复 PR 的工程助手
- 生成可直接发客户的销售方案
- 带审计链路的法务检索与起草
- 项目管理里的 AI 协作者

用户买的是 “结果 + 可靠性”，不是 “你也接了模型 API”。

很多团队还在卷聊天框、提示词、人格、回答效果。  
这已经不够支撑企业级 Agent 产品。

更值得花时间的模块是：
- 任务发起：一句话交办，还是结构化表单
- 任务状态：进行中、阻塞、需确认、已完成
- 任务记忆：哪些上下文长期保留
- 任务协作：多人是否可接力查看和批注
- 任务验收：什么条件算真正完成
- 任务治理：权限、审计、成本、回滚

一句话：  
聊天只是入口，任务系统才是骨架。

Anthropic 打动企业客户的点，核心不是 “更聪明”，而是 “更容易接入生产环境”。

所以企业买单的真实逻辑通常是：
- 上线够快
- 风险够低
- 成本能算
- 能接已有系统
- 维护负担小

这意味着你在做产品规划时，要重点看这几个指标：
- 从 POC 到上线需要几周
- 接入一个业务系统需要几天
- 一个任务链路里人工介入点有几个
- 平均每次任务成本多少
- 出错后是否可定位、可复盘、可补救

这类指标，比 “模型回答更像人” 更接近预算决策。

### 提问 · 2026-04-09 02:31:25

以“带审计链路的法务检索与起草”为场景，给出一个深度的最佳实践，并 进行解读

### 回答 · 2026-04-09 02:31:25

可以。  
如果把 “带审计链路的法务检索与起草” 作为一个企业级 Agent 场景来看，最优做法不是做一个 “会回答法律问题的聊天机器人”，而是做一个：

**可检索、可起草、可追溯、可复核、可问责的法务任务系统。**

这和前文说的`Managed Agents`非常契合，因为法务场景天然就是长任务、高风险、强权限、强审计，不适合只靠一次对话完成。

下面我给你一套相对 “最佳实践级” 的方案，并顺带解释为什么要这么设计。

---

**场景定义**

先把场景收窄，不然法务太大，系统会失焦。

这里我们定义一个典型企业法务任务：

- 员工、销售、采购、HR 或业务负责人提出一个法律相关请求
- 系统自动检索公司内部制度、历史合同、法条、监管要求、过往案例模板
- Agent 生成结构化结论与合同 / 函件 / 回复草稿
- 全过程保留证据链、引用来源、版本记录、审批轨迹
- 最终由法务人员审核并决定是否发出或落库

典型任务包括：

- 合同条款比对与修订建议
- NDA、采购协议、服务协议初稿生成
- 回答 “这个业务动作是否合规”
- 针对某个客户条款给出风险摘要和谈判建议
- 劳动人事通知、催款函、内部合规意见初稿

这个场景最核心的要求不是 “智能”，而是四个字：

**可被审计。**

因为法务不是内容创作问题，而是责任问题。

---

**最佳实践总原则**

先给结论，法务 Agent 最佳实践要遵守 6 条原则：

- 检索优先，生成次之
- 结论必须绑定证据
- 起草必须模板化和分层授权
- 全链路事件可回放
- 高风险动作默认人工签发
- 模型只负责建议，不直接成为责任主体

你可以把这理解成一句话：

**让 AI 像 “初级法务助理” 一样工作，而不是像 “自动签字的总法律顾问” 一样工作。**

---

##### 一套可落地的最佳实践架构

我分成 7 层讲。

---

###### 1. 入口层：不要做纯聊天框，要做 “任务单入口”

很多团队做法务 AI，第一步就错了：  
直接给用户一个对话框，用户输入一句 “帮我看下这份合同有没有风险”。

这看似自然，实际上非常不利于审计和交付。

更好的做法是：

**把法务请求设计成结构化任务单。**

一个标准任务单至少包含：

- 任务类型：合同审查 / 条款起草 / 合规问答 / 风险评估 / 法务函件
- 业务背景：交易对象、业务目的、金额、地区、时间要求
- 请求人身份：部门、岗位、权限级别
- 紧急程度：普通 / 紧急 / 高风险
- 输出形式：风险摘要 / 红线修订 / 正式草稿 / 内部意见
- 附件：合同文本、邮件、业务说明、招投标材料
- 适用法域：如中国大陆、香港、新加坡、欧盟等
- 审批要求：是否必须法务经理 / 合规负责人复核

为什么这一步重要？

因为聊天框只记录 “说了什么”，任务单记录的是 “这个活到底是什么”。  
法务责任永远绑定任务上下文，不绑定一句 prompt。

**解读：**  
这就是从 “AI 对话” 转向 “任务系统” 的典型体现。  
在法务里，没有任务结构，就没有责任边界；没有责任边界，就没有企业级可用性。

---

###### 2. 检索层：采用 “三域检索”，而不是一个大知识库

法务 Agent 最容易出问题的地方，是把所有材料揉成一个库，检索完让模型自由发挥。

最佳实践是做三域分层检索：

###### 域一：权威规范域
包括：

- 现行法律法规
- 行业监管规则
- 司法解释
- 行政规范性文件
- 公司内部制度与合规政策

这一层回答的是：

**“从规则上，什么能做，什么不能做？”**

###### 域二：企业记忆域
包括：

- 历史合同模板
- 已审合同版本
- 法务意见归档
- 过往谈判记录
- 董事会 / 管理层决策口径
- 标准条款库与替代条款库

这一层回答的是：

**“公司过去通常怎么处理？”**

###### 域三：任务上下文域
包括：

- 当前合同原文
- 当前附件
- 当前业务说明
- 对方提出的修订条款
- 当前审批备注与补充事实

这一层回答的是：

**“这次具体发生了什么？”**

然后检索时，不是一次性召回，而是按任务类型做不同权重：

- 合规问答：规范域权重最高
- 合同起草：企业记忆域 + 当前上下文权重最高
- 风险审查：三域并行召回
- 谈判建议：企业记忆域优先，再补规范域

**解读：**  
这一步本质上是在解决 “AI 回答像不像公司自己的法务团队”。  
只喂法条，输出会像法律考试答案；  
只喂历史模板，输出会像机械复读；  
只有三域结合，才会同时满足合法性、公司惯例和当前交易实际。

---

###### 3. 推理层：强制 “证据先行”，不要允许裸结论

法务场景绝不能允许模型直接输出：

- “这个条款风险较高”
- “建议不要签”
- “公司可能承担连带责任”

而不说明依据是什么。

所以推理层要采用一种固定工作流：

###### 第一步：问题分类
先识别当前请求属于哪类问题：

- 合同风险识别
- 条款起草
- 合规判断
- 程序性建议
- 监管差异分析

###### 第二步：列证据
Agent 必须先输出它依赖的证据清单：

- 引用了哪些法条
- 引用了哪些公司制度
- 引用了哪些历史模板
- 哪些事实来自当前任务附件
- 哪些信息缺失，导致结论不稳定

###### 第三步：形成分析链
要求输出结构化分析：

- 事实前提
- 适用规则
- 风险判断
- 可替代方案
- 结论置信度
- 是否建议人工复核

###### 第四步：再进入起草
只有在证据和分析链完成后，才允许生成合同条款、回复邮件或意见草稿。

这意味着系统内部应把 “分析” 和 “写作” 拆成两个 Agent 或两个阶段：

- 一个负责 legal reasoning
- 一个负责 legal drafting

这正好对应你前文提到的 “大脑和手分离” 思路。  
在法务里，还可以进一步变成：

- 规则大脑
- 起草大脑
- 检索之手
- 文档编辑之手
- 审计记忆层

**解读：**  
为什么一定要这样？  
因为法务真正需要的不是 “答案”，而是 “答案从哪来”。  
没有证据链的结论，法务人员不会真正信任，也无法对外承担责任。

---

###### 4. 起草层：模板化生成，不要从零自由写作

在法务场景里，最危险的不是检索不准，而是模型过度自由创作。

最佳实践是：

**所有正式法律文本都从模板出发，不从空白页出发。**

推荐采用三层模板机制：

###### A. 文档级模板
例如：

- 标准 NDA
- 标准采购协议
- 标准服务合同
- 劳动通知函
- 法务意见书模板

###### B. 条款级模板
例如：

- 保密条款
- 违约责任
- 责任限制
- 知识产权归属
- 数据合规与跨境条款
- 争议解决条款

###### C. 风格级模板
例如：

- 强保护公司利益版本
- 平衡谈判版本
- 客户友好版本
- 海外法域适配版本

Agent 的职责是：

- 从模板库中选取合适基底
- 根据当前检索和分析结果填充变量
- 在允许替换的条款范围内生成红线建议
- 对所有新增或修改文字打上来源说明

这里建议强制每一段关键输出都带元数据：

- 来源条款
- 修改原因
- 依据材料
- 修改人：AI / 人工
- 版本号
- 风险等级

**解读：**  
你可以把这理解成 “生成受限化”。  
很多人以为这会削弱 AI 的能力，其实恰恰相反：  
在高风险场景里，最好的 AI 不是最会自由发挥的 AI，而是最会在边界内稳定交付的 AI。

---

###### 5. 审计层：把 “每一步发生了什么” 做成事件流

这是这个场景里最关键的一层。

真正的 “带审计链路”，不是简单保存聊天记录，而是要记录成一条完整事件流。

建议每次任务都自动记录以下事件：

- 谁在什么时间发起任务
- 上传了哪些附件
- 使用了哪个任务模板
- 检索了哪些知识源
- 哪些文档被模型实际引用
- 模型版本是什么
- 使用了哪些工具
- 生成了哪些中间结论
- 哪些结论被人工修改
- 哪一版文本最终被采纳
- 谁审批通过
- 谁驳回过，驳回理由是什么
- 最终文件是否发出、发给谁、何时发出

更进一步，审计层最好满足三种能力：

###### 1. 可回放
能还原某个法律意见是如何形成的。

###### 2. 可比对
能看出 AI 草稿和人工终稿差异在哪里。

###### 3. 可归责
能明确哪些内容是系统建议，哪些是法务确认，哪些是业务补充。

这一步在系统实现上，通常要用事件日志 + 文档版本库 + 引用索引三套东西一起做，而不是只靠数据库字段。

**解读：**  
这正是`Managed Agents`里 “记忆独立” 的价值在法务场景中的落点。  
法务系统最怕两件事：
- 结论出来了，但不知道怎么来的
- 文件发出去了，但说不清谁改的

审计链路就是把 “智能过程” 变成 “可治理过程”。

---

###### 6. 权限层：凭证、知识、动作全部分级，不给大一统权限

法务场景最忌讳一个 Agent 拿着所有系统权限乱跑。

最佳实践是三重权限控制：

###### 一类：知识访问权限
不是每个人都能让 Agent 检索所有法务材料。

比如：

- 普通员工只能访问公开制度和与本人相关模板
- 采购经理可访问采购协议库
- HRBP 可访问劳动合规模板
- 法务专员可访问历史意见库
- 总法或合规负责人可访问敏感案件档案

###### 二类：任务操作权限
不是每个人都能触发同等级任务。

比如：

- 普通员工可发起咨询
- 业务负责人可发起合同起草
- 法务可发起正式审查
- 高风险领域必须二次审批才可生成对外文本

###### 三类：外部动作权限
尤其要控制：

- 是否允许向外发邮件
- 是否允许推送到合同系统
- 是否允许回写审批系统
- 是否允许调用外部法规数据库
- 是否允许自动发送给客户

最佳实践是：

**AI 可以草拟、建议、提交待审，但默认不能直接对外生效。**

凭证也必须在模型外保存，由代理层代为调用。  
这和前文文章提到的 “AI 不直接接触 Token” 在这里完全适用。

**解读：**  
法务系统不能只讲 “数据安全”，还要讲 “法律效果安全”。  
很多文本一旦发出，就不是内容问题，而是法律行为问题。  
所以权限控制本质上不是 IT 权限，而是法律权力映射。

---

###### 7. 人机协同层：把人工复核设计成产品能力，而不是补丁

很多团队觉得 “反正最后让法务看一下” 就行。  
这其实不是最佳实践，因为它没有设计复核流程，只是把责任甩回人工。

正确做法是把复核做成明确产品环节：

一个成熟的法务 Agent 复核界面应该至少支持：

- 风险点摘要卡片
- 每个结论的引用来源
- 原文与修订文对照
- AI 修改理由
- 一键替换候选条款
- 高风险语句高亮
- 缺失事实提醒
- 置信度提示
- 审批意见记录
- 退回重做指令

更进一步，可以加入两类 “复核 Agent”：

###### 规则复核 Agent
专门检查：

- 是否引用过期法规
- 是否和内部制度冲突
- 是否遗漏强制条款
- 是否法域适配错误

###### 风险复核 Agent
专门检查：

- 是否存在过度承诺
- 是否责任边界不清
- 是否付款、赔偿、知识产权条款失衡
- 是否与公司历史谈判底线冲突

这样法务人员看到的，不是一团生成内容，而是一份已经被初步整理过的 “可审批工作台”。

**解读：**  
企业级 AI 的最佳体验，不是 “完全自动化”，而是 “让专业人士在最关键的位置出手”。  
法务尤其如此。  
好的系统不是取消律师，而是让律师少花时间找材料、抄模板、比版本，多花时间做判断。

##### 一条完整的最佳实践流程

下面给你一条比较完整的端到端流程。

###### 阶段 1：发起任务
销售提交 “客户要求修改标准服务协议中的责任限制条款，请给出风险意见和回复版本”。

系统要求补齐：
- 客户名称
- 合同金额
- 所属法域
- 截止时间
- 对方修改版附件
- 当前业务重要性

###### 阶段 2：自动分流
系统识别为：
- 合同审查
- 高风险条款
- 涉及责任限制
- 需要法务复核

###### 阶段 3：检索
Agent 自动查询：
- 公司标准服务协议模板
- 历史相似客户谈判条款
- 责任限制条款底线规则
- 适用法域下相关法律规则
- 过去法务对同类条款的处理意见

###### 阶段 4：生成分析卡
输出：
- 客户修订点摘要
- 与公司标准文本差异
- 风险等级：高 / 中 / 低
- 主要风险原因
- 可接受替代方案
- 缺失信息列表
- 引用证据

###### 阶段 5：生成起草结果
生成三套内容：
- 给业务同事看的简明解释版
- 给客户回传的红线修订版
- 给法务内部归档的正式意见版

###### 阶段 6：人工复核
法务查看：
- AI 引用是否正确
- 风险判断是否偏保守或偏激进
- 替代条款是否符合当下谈判策略

可直接：
- 采纳
- 局部修改
- 退回补检索
- 升级给资深法务 / 外部律师

###### 阶段 7：归档与审计
系统自动保存：
- 所有检索源
- 所有中间版本
- 最终审批意见
- 最终发出版本
- 对应任务标签

之后这些又反哺企业记忆域。

这就形成一个闭环：
**任务处理 -> 审计沉淀 -> 模板优化 -> 下次更准。**

##### 这套最佳实践的核心价值，怎么理解

可以从 5 个层面解读。

---

###### 1. 它解决的不是 “法律知识获取”，而是 “法律工作交付”
普通法律问答系统只能告诉你一些信息；  
法务 Agent 要解决的是：

- 我该怎么判断
- 我该怎么写
- 我该怎么留痕
- 我该怎么让组织放心使用

所以真正的产品单位不是一次问答，而是一次 “法务任务交付”。

---

###### 2. 它把 “可信” 拆成了可实现的组件
法务 AI 的 “可信” 不是一个抽象词，而是由这些能力组成：

- 有来源
- 有边界
- 有版本
- 有权限
- 有审批
- 有回放

你会发现，可信其实不是模型参数调出来的，更多是系统工程做出来的。

---

###### 3. 它天然适合托管式 Agent 基础设施
这个场景非常匹配`Managed Agents`这类能力，因为它需要：

- 长时间运行
- 多步骤任务编排
- 断点恢复
- 安全沙盒
- 凭证隔离
- 记忆独立存储
- 工具按需调用

换句话说，法务不是一个 “单轮对话 API” 场景，而是一个 “长期任务 orchestration” 场景。  
所以越往企业级走，越像托管 Agent，而不像普通聊天机器人。

---

###### 4. 它重新定义了法务团队和 AI 的分工
最佳实践下，AI 适合负责：

- 找材料
- 做初筛
- 做对比
- 套模板
- 出初稿
- 标注证据
- 形成可审工作底稿

而人更适合负责：

- 风险取舍
- 谈判策略
- 例外批准
- 责任承担
- 对外签发

这才是合理的人机边界。  
如果边界划错，要么系统价值很低，要么风险高到企业不敢用。

---

###### 5. 它的护城河不在模型，而在组织化沉淀
这个场景里最值钱的资产不是 “接了哪个大模型”，而是：

- 公司自己的条款库
- 历史审查意见
- 风险偏好
- 审批规则
- 法域适配经验
- 任务闭环数据
- 审计日志体系

这也是为什么这个方向很适合产品化：  
因为随着使用增长，系统会越来越懂 “这家公司怎么做法务”，而不只是 “法律上怎么说”。

---

##### 最容易踩的 8 个坑

如果你真要做这个场景，这 8 个坑很常见：

- 只做聊天，不做任务单
- 只做知识库，不做证据绑定
- 只出结论，不列依据
- 从零生成合同，不走模板
- 把聊天记录当审计记录
- 没有版本差异和审批链
- 让 Agent 直接调用外部发送动作
- 把所有法务场景混在一个工作流里

这些坑本质上都指向同一个问题：

**把法务当内容生成，而不是当风险控制。**

---

##### 如果我是产品负责人，我会这样定义 MVP

先别一上来做 “全能法务 Agent”。  
最佳 MVP 应该只选一个窄而高价值的切口。

我会建议先做：

**“标准合同审查 + 红线修订 + 审计归档”**

原因是：
- 数据最容易拿到
- 流程最标准化
- 审计需求最明确
- ROI 最容易衡量
- 最容易形成模板库和版本库

MVP 功能只做这些：

- 上传合同
- 自动条款拆分
- 检索公司标准模板和历史案例
- 输出风险摘要
- 生成红线修订建议
- 引用依据展示
- 法务复核与审批
- 自动归档版本和日志

等这个跑顺了，再扩展到：
- 合规问答
- 多法域比较
- 外部函件
- 劳动法务
- 争议前置处理

---

##### 最后给一个产品级结论

“带审计链路的法务检索与起草” 这个场景的最佳实践，不是让 AI 代替法务做决定，而是把法务工作的前半段和中间层标准化、证据化、系统化。

最优解不是：
- 一个更聪明的聊天机器人

而是：
- 一个有任务入口
- 有分层检索
- 有证据绑定
- 有模板起草
- 有权限控制
- 有审批复核
- 有全链路审计
的法务 Agent 工作台。

一句话概括：

**在法务场景里，AI 的价值不在 “会不会写”，而在 “写出来的东西能不能被组织放心地用”。**

- 能接入企业现有文档系统、合同系统、审批系统、IM 和知识库

##### 二、系统架构分层解读

---

###### 1. 用户与业务系统层

```text
[员工 / 销售 / 采购 / HR / 法务]
        │
        ├─ Web Portal
        ├─ OA / 审批系统
        ├─ 合同管理系统
        ├─ CRM
        └─ IM（Slack/Teams/ 企微）
```

**职责**
- 作为任务入口和结果消费端
- 提供业务上下文、附件和审批动作
- 承载人工复核、意见确认、任务协同

**设计要点**
- 不建议只提供聊天框
- 优先提供 “法务任务单”
- 结果回写到原业务系统，而不是让用户反复切系统

**产品含义**
- 用户看到的是一个 “法务工作台”
- 不是一个孤立的 AI 页面

---

###### 2. 任务接入与编排层

```text
[Task Intake]
   ├─ 表单校验
   ├─ 任务类型识别
   ├─ 风险等级评估
   ├─ 选择工作流模板
   ├─ 指定审批要求
   └─ 分派给对应 Agent 流程
```

**核心模块**
- `Task Intake Service`
- `Workflow Engine`
- `Agent Orchestrator`
- `Policy Router`

**输入**
- 任务单
- 附件
- 发起人身份
- 所属部门
- 任务类型
- 法域信息

**输出**
- 标准化任务对象
- 风险等级
- 执行工作流 ID
- 审批要求
- 可调用工具范围

**关键规则**
- 合规问答、合同审查、起草、函件生成走不同工作流
- 高风险任务强制增加人工复核节点
- 缺失关键信息时，不进入起草，先补信息

**为什么重要**
- 这是从 “Prompt 驱动” 切换到 “任务驱动” 的核心层
- 决定系统是否具备企业治理能力

---

###### 3. 检索与知识服务层

```text
                 ┌──────────────────────────┐
                 │      Query Planner       │
                 └─────────────┬────────────┘
                               │
         ┌─────────────────────┼─────────────────────┐
         ▼                     ▼                     ▼
┌──────────────────┐ ┌──────────────────┐ ┌──────────────────┐
│   规范域检索      │ │   企业记忆域检索   │ │   任务上下文域检索 │
│ 法律 / 法规 / 监管     │ │ 模板 / 历史意见 / 条款  │ │ 当前合同 / 附件 / 邮件 │
└──────────────────┘ └──────────────────┘ └──────────────────┘
         │                     │                     │
         └─────────────────────┼─────────────────────┘
                               ▼
                     ┌──────────────────┐
                     │ Re-ranker/Citation│
                     └──────────────────┘
```

**三域定义**
- 规范域：法律法规、监管规则、公司制度
- 企业记忆域：历史合同、模板、法务意见、底线条款
- 任务上下文域：当前合同、当前业务背景、对方修订稿

**关键能力**
- 分任务类型配置召回权重
- 支持关键词、向量、结构化筛选混合检索
- 每条检索结果都要带出处元数据
- 生成 “引用包” 供后续推理和起草使用

**输出对象**
- `Evidence Bundle`
  - evidence_id
  - source_type
  - source_path
  - excerpt
  - jurisdiction
  - version
  - confidence

**为什么重要**
- 法务 Agent 的可信度，不来自 “模型自信”，来自 “证据引用完整”

###### 4. Agent 推理层

```text
┌──────────────────────────────┐
│       Legal Reasoner         │
│  - 问题分类                   │
│  - 法律适用分析               │
│  - 风险识别                   │
│  - 缺失事实识别               │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│       Risk Analyzer          │
│  - 风险等级                   │
│  - 风险类型标签               │
│  - 可接受替代方案             │
│  - 是否升级人工               │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│       Fact / Citation Check  │
│  - 结论是否有证据             │
│  - 是否引用过期规则           │
│  - 是否和内部制度冲突         │
└──────────────────────────────┘
```

**推理层原则**
- 先分析，后写作
- 先证据，后结论
- 先识别缺失事实，再决定是否可起草

**标准输出**
- 事实前提
- 引用依据
- 风险判断
- 替代建议
- 缺失信息
- 置信度
- 审批建议

**推荐做法**
- 拆成多个子 Agent，而不是一个大 Agent 一次性写完
- 例如：
  - 检索规划 Agent
  - 法律分析 Agent
  - 风险复核 Agent
  - 起草 Agent

**为什么重要**
- 法务工作天然不是一步出答案，而是证据链 + 判断链

###### 5. 文档与起草服务层

```text
┌──────────────────────────────────────┐
│         Draft Composer               │
│  基于模板生成文档骨架                 │
└─────────────────┬────────────────────┘
                  ▼
┌──────────────────────────────────────┐
│         Clause Rewriter              │
│  生成条款替代方案 / 谈判版本 / 风险提示 │
└─────────────────┬────────────────────┘
                  ▼
┌──────────────────────────────────────┐
│         Redline Generator            │
│  原文 - 建议稿差异对比 / 标注修改理由     │
└──────────────────────────────────────┘
```

**起草层原则**
- 模板优先，不从零开始
- 条款级拼装，不做无限制自由生成
- 所有关键修改都要有依据和理由
- 正式文书默认人工签发，不自动外发

**输出形式**
- 风险摘要卡
- 内部法务意见稿
- 红线修订版合同
- 对业务同事的简明说明版
- 对外回复草稿

**为什么重要**
- 企业法务最看重稳定、可控、可追责，不是文采

###### 6. 工具与执行层

```text
[Tool Hub]
  ├─ OCR / 文档解析
  ├─ PDF / Word / 扫描件处理
  ├─ 条款切分与结构化
  ├─ 对比引擎
  ├─ 合同系统连接器
  ├─ 审批系统连接器
  ├─ 邮件系统连接器
  ├─ DMS / 知识库连接器
  └─ 外部法规库连接器
```

**设计原则**
- 工具调用与模型解耦
- 凭证不暴露给模型
- 所有外部访问通过代理层

**执行安全**
- 只允许白名单工具
- 按任务级和角色级控制工具权限
- 高风险外部动作必须人工确认

**为什么重要**
- 法务场景里，真正危险的是 “发出去了”，不是 “写出来了”

- 输出加水印和来源说明
- 高风险文本禁止自动外发
- 保留期与日志策略符合内控要求

##### 五、单任务工作流详解

这里用 “客户修改责任限制条款，要求法务给意见并生成回复版本” 为例。

---

###### 阶段 1：发起任务

```text
用户 -> 提交法务任务单
  - 任务类型：合同审查
  - 合同类型：服务协议
  - 对方修订条款：责任限制
  - 金额：XXX
  - 法域：中国大陆
  - 截止时间：T+1
  - 附件：合同原稿、客户修订稿、业务说明
```

**系统动作**
- 校验必填项
- 识别上传文档类型
- 抽取基础元数据
- 创建 task_id

**审计记录**
- `task_created`
- `attachment_uploaded`
- `requester_identity_bound`

---

###### 阶段 2：标准化与分流

```text
[Task Normalizer]
  输入：原始任务单 + 附件
  输出：标准任务对象
```

标准任务对象示意：

```json
{
  "task_id": "LEGAL-2025-00128",
  "task_type": "contract_review",
  "sub_type": "liability_clause_negotiation",
  "jurisdiction": "CN",
  "risk_hint": "high",
  "requester_role": "sales_manager",
  "attachments": ["contract_v1.docx", "counterparty_redline.docx"],
  "required_outputs": ["risk_summary", "redline_draft", "business_explanation"]
}
```

**系统判断**
- 这是高风险条款审查
- 需要法务复核
- 禁止自动外发

**审计记录**
- `task_classified`
- `risk_pre_scored`
- `workflow_selected`

---

###### 阶段 3：风险分级与权限校验

```text
[Policy Engine]
  ├─ 判断用户是否有权限发起该类任务
  ├─ 判断该任务是否可调用历史谈判库
  ├─ 判断是否必须法务经理审批
  └─ 限定可用工具范围
```

**典型规则**
- 销售可发起，但不能直接签发法律文本
- 可访问服务协议历史条款库，不可访问争议案件档案
- 必须进入人工复核
- 不允许自动发送给客户

**审计记录**
- `policy_checked`
- `tool_scope_granted`
- `approval_gate_set`

---

###### 阶段 4：检索规划

```text
[Query Planner]
  目标：把任务拆成若干检索问题
```

示意：

```text
Q1: 公司标准服务协议中的责任限制标准条款是什么？
Q2: 历史上类似金额 / 类似客户类型的谈判接受边界是什么？
Q3: 当前法域下责任限制条款有哪些强制性限制？
Q4: 当前客户修订相较公司标准文本偏离在哪里？
Q5: 是否存在公司内部制度对该风险有特殊要求？
```

**产出**
- 检索计划
- 知识域权重
- 必要证据清单

**审计记录**
- `query_plan_generated`

---

###### 阶段 5：多域证据检索

```text
                   ┌──────────────┐
                   │ Query Planner│
                   └──────┬───────┘
                          ▼
     ┌────────────────────┼────────────────────┐
     ▼                    ▼                    ▼
[规范域检索]         [企业记忆域检索]      [任务上下文检索]
 法律法规             历史条款 / 底线         当前合同 / 客户修订稿
 内部制度             历史意见               业务说明 / 附件
```

**输出**
- `Evidence Bundle`
- 每条 evidence 都附带：
  - 来源
  - 段落
  - 时间
  - 法域
  - 版本
  - 适用说明

示意：

```text
Evidence #E01
  来源：公司标准服务协议模板 v3.2
  条款：责任限制 12.4
  状态：现行
  说明：公司标准上限为已支付费用总额

Evidence #E02
  来源：历史客户谈判案例 #C238
  条款：责任限制替代方案
  说明：战略客户曾接受 12 个月费用上限

Evidence #E03
  来源：某法域法规解释
  说明：故意或重大过失不得完全免责
```

**审计记录**
- `knowledge_retrieved`
- `evidence_bundle_created`

---

###### 阶段 6：法律分析与风险判断

```text
[Legal Reasoner]
  输入：任务对象 + Evidence Bundle
  输出：分析卡 Analysis Card
```

分析卡结构：

```text
1. 事实前提
2. 当前客户修改内容摘要
3. 与公司标准文本差异
4. 适用规则
5. 风险点列表
6. 风险等级
7. 可接受替代方案
8. 需要补充的事实
9. 是否建议升级审批
```

示意输出：

```text
分析结论：
- 客户要求删除责任上限，风险高
- 与公司标准条款偏离较大
- 若接受，可能导致无限责任暴露
- 在现有规则下，不建议直接接受
- 可替代方案：
  A. 以 12 个月已支付费用为上限
  B. 对间接损失免责，但保留故意 / 重大过失例外
- 缺失信息：
  该客户是否属于战略客户；
  交易是否包含数据处理义务；
  是否有额外保险安排
```

**审计记录**
- `analysis_generated`
- `risk_scored`
- `missing_facts_detected`

---

###### 阶段 7：证据校验与缺失信息识别

```text
[Risk Reviewer Agent]
  ├─ 检查每个高风险结论是否绑定证据
```

#### 检察院场景最佳实践：检察官对公安提交的刑事案件卷宗进行智能审查

> 目标不是 “让 AI 替代检察官办案”，而是构建一套**可追溯、可复核、可治理、可升级**的卷宗审查智能体系统，帮助检察官更快完成事实梳理、证据校验、程序审查、法律适用分析和文书辅助起草。

---

##### 一、场景定义

###### 1. 典型业务场景

公安机关移送审查起诉后，检察官需要对卷宗进行系统审查，核心任务通常包括：

- 审查案件事实是否清楚
- 审查证据是否确实、充分，证据链是否完整
- 审查侦查程序是否合法
- 审查定性与法律适用是否准确
- 审查强制措施、扣押冻结、鉴定、搜查等程序材料是否完备
- 识别退回补充侦查点
- 形成审查报告、阅卷笔录、讯问提纲、退补提纲、起诉意见辅助材料

###### 2. 为什么这是 Agent 的强场景

这个场景天然符合托管式 Agent 的优势：

- **任务长**：一次卷宗审查常常持续数小时到数天
- **材料多**：案卷、笔录、鉴定、电子数据、清单、法律文书数量巨大
- **流程复杂**：既要实体审查，也要程序审查
- **证据密集**：每个判断都必须能指向原始材料
- **高审计要求**：所有 AI 输出都必须可追溯、可解释、可复核
- **强协同**：检察官、书记员、检察官助理、部门负责人可能都要参与

所以这里最合适的不是 “一个聊天机器人”，而是一个**卷宗审查工作流 Agent 系统**。

---

#### 二、最佳实践的总原则

##### 1. 先给结论

这类系统的最佳实践不是 “把卷宗扔给模型，让它总结”，而是：

1. **把案件审查拆成标准化任务流**
2. **把 “大脑” 和 “手” 分开**
3. **把 “结论” 和 “证据出处” 绑定**
4. **把 “AI 草稿” 和 “检察官判断” 明确分层**
5. **把 “过程留痕” 和 “权限控制” 做成基础设施，而不是补丁**

---

##### 2. 核心设计原则

###### 原则 A：AI 只能辅助，不直接替代检察裁量

AI 可以做：

- 卷宗结构化
- 时间线抽取
- 证据目录生成
- 事实冲突识别
- 程序瑕疵提示
- 法条候选匹配
- 文书草稿起草

AI 不应直接做最终决定：

- 是否批准逮捕
- 是否提起公诉
- 是否认定主从犯
- 是否认定证据排除
- 是否适用认罪认罚从宽
- 是否作出退回补充侦查决定

###### 原则 B：所有结论必须 “带引文”

任何 AI 输出都必须回答两个问题：

- **你为什么这么判断？**
- **这个判断对应卷宗哪一页、哪份材料、哪条法律？**

没有证据锚点的判断，在检察业务里几乎没有可用价值。

###### 原则 C：工作流优先于 Prompt

成熟系统不应该只是一个 Prompt，而应当是：

- 任务入口
- 审查模板
- 多阶段 Agent
- 人工复核门
- 审计链路
- 知识沉淀

###### 原则 D：长任务要可中断、可恢复、可回放

卷宗审查不是 30 秒问答，而是长流程工作：

- 今天审一半，明天继续
- 中间补材料后继续
- 领导复核时能看到 AI 做过什么
- 发生争议时能回放分析依据

##### 2. 这套架构为什么适合检察审查

###### 大脑和手分离

借鉴你给的文章里 Anthropic Managed Agents 的思路，最值得借用的是：

- **大脑**：负责理解案件、推理、规划
- **手**：负责 OCR、页码定位、证据抽取、清单比对、法条检索
- **记忆**：负责保留案件状态、审查过程、引用关系、版本记录

在检察场景里，这种解耦特别重要：

- OCR 组件可以升级，不影响法律分析组件
- 法律模型可以升级，不破坏卷宗索引
- 审查模板可以调整，不需要重建整套系统
- 任何步骤中断后都能恢复

#### 四、最佳实践：一个 “标准案件审查流” 应该怎么设计

下面给出一个深度版最佳实践，假设场景是：

> **公安机关移送一起涉嫌盗窃 / 诈骗 / 帮助信息网络犯罪活动罪的案件，检察官需要在法定期限内完成卷宗审查，决定是否退补、是否起诉、是否需要补充讯问与补证。**

---

##### 阶段 0：案件接入与数字化准备

###### 输入

- 案件基本信息
- 移送起诉意见书
- 案卷目录
- 讯问笔录、询问笔录
- 证人证言
- 鉴定意见
- 勘验检查笔录
- 搜查扣押材料
- 电子数据提取说明
- 扣押清单、发还清单
- 视听资料清单
- 适用法律意见
- 认罪认罚具结相关材料

###### 系统动作

1. 导入卷宗
2. 做 OCR 和版式恢复
3. 识别文书类别
4. 生成页级索引和材料级索引
5. 抽取关键元数据：
   - 人名
   - 时间
   - 地点
   - 物品 / 金额
   - 银行卡 / 账号 / 设备号
   - 侦查措施
   - 法律文书名称
6. 建立文书之间的关联图

###### 最佳实践要求

- 每一页都要有唯一`page_id`
- 每一份材料都要有唯一`doc_id`
- 所有 AI 引用都必须能落到`doc_id + page_id`
- OCR 不仅做文本化，还要保留原版式定位坐标

###### 解读

这是整个系统可用性的基础。

如果系统只能 “看懂内容”，却不能 “准确指出出处”，那它最多是摘要工具，不是办案辅助系统。

---

##### 阶段 1：案件标准化建模

###### 目标

把 “卷宗堆” 变成 “可计算案件对象”。

###### 推荐案件对象结构

```json
{
  "case_id": "CASE-2025-001",
  "case_type": "fraud",
  "suspects": [],
  "charges_candidate": [],
  "facts_timeline": [],
  "evidence_catalog": [],
  "procedure_actions": [],
  "coercive_measures": [],
  "financial_flows": [],
  "electronic_evidence": [],
  "issues_detected": [],
  "draft_outputs": []
}
```

###### 推荐拆分子任务

- 人物关系图谱
- 时间线构建
- 证据目录清洗
- 程序行为链重建
- 罪名候选映射
- 争议焦点发现

###### 解读

不要让模型直接面对 “原始混乱卷宗”。

最佳实践是先把卷宗转为结构化案件对象，这样后续每个 Agent 都基于同一数据底座工作。

---

##### 阶段 2：卷宗完整性与形式审查

###### Agent：`Dossier Integrity Agent`

###### 核心任务

检查卷宗是否 “材料齐、顺序清、可审查”。

###### 关注点

- 案卷目录与实际材料是否一致
- 页码是否连续
- 是否存在缺页、重页、扫描模糊
- 关键法律文书是否缺失
- 鉴定意见是否附送检材料说明
- 电子数据是否有提取、固定、移送链条说明
- 扣押、冻结、发还材料是否齐备
- 认罪认罚材料是否完备

###### 输出样式

```markdown
## 卷宗完整性初审结果

### 发现问题
1. 《扣押决定书》目录记载存在，但正文未检出，疑似缺失
2. 第 243-247 页扫描模糊，关键金额无法辨认
3. 电子数据提取说明存在，但未发现原始存储介质校验值记录
4. 鉴定意见已附，但未见送检提取笔录的明确对应页码

### 风险等级
中高

### 建议动作
- 补齐扣押决定书
- 重新扫描相关页
- 核验电子数据固定链条
- 建议将鉴定意见与送检材料做显式关联
```

###### 解读

这一步看起来 “低级”，但非常重要。

很多办案风险不在实体判断，而在卷宗基础条件不足。最佳实践是让 Agent 先做 “卷宗质量闸门”，不合格材料先拦下来，而不是直接进入深度法律分析。

---

##### 阶段 3：案件事实时间线重建

###### Agent：`Timeline Agent`

###### 目标

自动生成案件时间轴，帮助检察官快速判断事实是否闭合。

###### 处理内容

从以下材料抽取时间事件：

- 报案
- 接警
- 立案
- 传唤
- 抓获
- 扣押
- 搜查
- 讯问
- 转账
- 登录
- 通联
- 鉴定
- 退赃退赔
- 认罪认罚签署
- 移送起诉

###### 输出形式

```markdown
## 案件时间线

- 2025-02-03 19:21：被害人向公安报案（`doc_12`, `p3`）
- 2025-02-04 09:15：公安机关立案（`doc_04`, `p1`）
- 2025-02-07 16:40：嫌疑人张某被抓获（`doc_18`, `p2`）
- 2025-02-07 18:20：对张某进行第一次讯问（`doc_21`, `p1-p8`）
- 2025-02-08 10:00：扣押手机 2 部、银行卡 3 张（`doc_29`, `p2-p4`）
- 2025-02-10：提取微信聊天记录与转账记录（`doc_34`, `p1-p6`）
- 2025-02-15：出具电子数据检验意见（`doc_42`, `p1-p5`）
- 2025-03-01：公安机关移送审查起诉（`doc_01`, `p1`）

## 时间线冲突提示

1. 第一次讯问时间早于抓获时间 35 分钟，需核验记录准确性
2. 扣押清单时间与搜查笔录时间不一致
3. 电子数据提取时间晚于首次查封设备时间 3 日，需核验封存链条
```

###### 解读

这一步极有价值，因为检察官审卷时最耗费精力的一件事，就是在大量材料里拼出 “事实 - 证据 - 程序” 时间轴。

Agent 擅长做这种密集信息重建，但最终冲突是否构成实质问题，仍由检察官判断。

---

##### 阶段 4：证据链审查

###### Agent：`Evidence Chain Agent`

###### 核心目标

判断 “关键事实有没有足够证据支持”。

###### 审查维度

###### 1. 事实要件拆分

例如诈骗案可拆成：

- 行为人身份
- 虚构事实 / 隐瞒真相行为
- 被害人陷入错误认识
- 基于错误认识处分财产
- 财产损失
- 嫌疑人与涉案账户 / 设备 / 聊天记录的关联
- 主观故意

###### 2. 为每个要件建立证据矩阵

```markdown
| 事实要件 | 支持证据 | 证据位置 | 可靠性提示 | 缺口 |
|---|---|---|---|---|
| 嫌疑人控制涉案微信号 | 聊天记录、登录设备、手机号绑定 | doc_34 p2, doc_37 p4 | 需核验提取方式 | 有待补强 |
| 被害人转账 | 银行流水、转账截图、陈述 | doc_11 p3, doc_26 p1 | 一致性较高 | 无 |
| 主观明知 | 讯问供述、同案人证言、分赃记录 | doc_21 p5, doc_45 p2 | 供述有反复 | 存在争议 |
```

###### 3. 自动识别问题

- 仅有口供、缺乏客观证据
- 证据之间矛盾
- 证据来源链不完整
- 证明力弱、关联性不足
- 非法取证风险
- 电子数据证明链不闭合

###### 推荐输出

```markdown
## 证据充分性结论

### 已基本闭合的事实
- 被害人发生财产处分
- 涉案金额达到入罪标准
- 嫌疑人实际接触涉案账户 / 设备的事实有较强支持

### 尚不充分的事实
- 嫌疑人主观明知程度证据仍偏弱
- 同案犯供述与电子数据之间尚未完全印证
- 资金流向到终端受益账户的闭环尚未完全形成

### 建议补证方向
1. 调取涉案手机号实名及登录 IP 关联证明
2. 强化设备使用人与聊天账号之间的绑定
3. 补充资金流向最终控制人的客观证据
```

###### 解读

这是整个系统最关键的部分。

最佳实践不是让模型说 “证据充分” 或 “不充分”，而是让它输出：

- 哪些事实已被支持
- 哪些事实仍有缺口
- 缺口对应什么材料
- 建议补哪些证据

也就是把 “大判断” 拆成 “小证据链”。

---

##### 阶段 5：程序合法性审查

###### Agent：`Procedure Review Agent`

###### 核心任务

对侦查程序进行形式与实质风险检查。

###### 审查对象

- 立案手续
- 传唤 / 拘留 / 逮捕手续
- 搜查手续
- 扣押冻结手续
- 讯问同步录音录像
- 辩护权告知
- 见证人在场要求
- 鉴定委托与告知
- 电子数据提取、封存、校验
- 认罪认罚程序
- 未成年人、聋哑人、精神障碍人员的特别程序

###### 输出示例

```markdown
## 程序合法性审查提示

### 发现事项
1. 第一次讯问未见完整权利义务告知页，需核验是否漏装卷
2. 搜查笔录存在，但搜查证扫描不清，建议补正
3. 电子数据提取说明未明确哈希校验值，固定链条偏弱
4. 认罪认罚具结书已附，但值班律师见证记录不完整
5. 扣押清单与扣押见证材料页码关联不清

### 风险判断
- 不一定直接导致证据排除
- 但可能影响证据能力与程序稳健性
- 建议在起诉前补齐或说明
```

###### 解读

很多所谓 “法律 AI” 只会做实体法条匹配，但真正高价值的是同时做程序法审查。

检察审查不是单纯判断 “像不像犯罪”，而是还要判断 “侦查是否合法、证据能不能站住”。

---

##### 阶段 6：法律适用与争点识别

###### Agent：`Legal Analysis Agent`

###### 核心任务

输出 “可供检察官思考” 的法律分析框架，而不是最终替代判断。

###### 输出应包含

- 罪名候选
- 入罪构成要件匹配情况
- 争议焦点
- 轻重情节
- 是否可能改变定性
- 是否适用从犯、未遂、既遂、共犯等
- 是否适用认罪认罚从宽
- 相关司法解释与指导案例候选

###### 输出范式

```markdown
## 法律适用分析卡

### 候选定性
- 诈骗罪
- 帮助信息网络犯罪活动罪（备选分析）
- 掩饰、隐瞒犯罪所得罪（需排除性分析）

### 当前更倾向的定性
诈骗罪

### 理由
1. 被害人基于虚假信息处分财产的链条较完整
2. 涉案聊天记录与资金流具有较强对应关系
3. 嫌疑人与诈骗行为的参与程度高于单纯帮助支付结算

### 主要争点
1. 嫌疑人系直接实行者还是仅提供帮助
2. 主观明知程度是否达到诈骗共犯标准
3. 对部分金额是否应全额计入犯罪数额

### 建议检察官重点核实
- 嫌疑人与上游组织者的联络证据
- 对诈骗话术和分工的知情程度
- 对分赃和收益的客观证据
```

###### 解读

这一步不能做成 “AI 最终结论”。

最佳实践是让 Agent 像一个高质量助理一样，给出：

- 候选路径
- 支持与反对理由
- 争议点
- 待核验点

这样既有实用价值，也保留检察官的裁量空间。

---

##### 阶段 7：退回补充侦查点生成

###### Agent：`Supplementary Investigation Agent`

###### 目标

在证据缺口或程序问题存在时，自动形成可操作的退补提纲。

###### 高质量退补提纲长什么样

不是泛泛地说 “进一步查清事实”，而是：

- 缺什么事实
- 为什么现在证据不足
- 应补什么材料
- 哪个疑点最关键
- 预期证明目的是什么

###### 输出示例

```markdown
## 退回补充侦查建议提纲

### 一、关于嫌疑人主观明知问题
当前仅有供述反映其知悉 “账号有问题”，但缺乏与上游诈骗行为直接关联的客观证据。
建议补充：
1. 调取涉案账号的历史登录设备、IP、地理位置记录
2. 调取嫌疑人与同案人之间的通联和聊天记录
3. 核查嫌疑人对异常资金往来的解释及相应客观印证

### 二、关于电子数据固定链条问题
现有电子数据提取说明未能完整反映封存、提取、校验过程。
建议补充：
1. 提供提取设备信息及操作人员记录
2. 补充哈希校验值及封存照片
3. 明确原始介质与导出材料之间的对应关系

### 三、关于涉案金额认定问题
部分转账记录未与具体被害人陈述形成一一对应。
建议补充：
1. 建立被害人、转账记录、涉案账户三方对应表
2. 对争议金额部分逐笔核对资金流转路径
```

###### 解读

这是 Agent 在司法场景里特别有价值的地方：

它不只是总结材料，而是能把 “办案经验” 转成结构化补证建议。

##### 阶段 8：文书辅助起草

###### Agent：`Drafting Agent`

###### 适合生成的文书类型

- 阅卷摘要
- 审查报告草稿
- 讯问提纲
- 退补提纲
- 证据瑕疵说明
- 争议焦点摘要
- 法条适用卡片

###### 不建议自动直接出终稿的文书

- 正式起诉书终版
- 不起诉决定书终版
- 抗诉文书终版
- 证据排除最终法律意见

###### 最佳实践要求

每个文书段落都要能回指来源：

```markdown
### 事实摘要（引用：`doc_21 p2`, `doc_34 p3`, `doc_26 p1`）

### 证据分析（引用：`doc_42 p1-p3`, `doc_45 p2`）

### 程序审查（引用：`doc_18 p2`, `doc_29 p3`）

### 需要补查问题（来源：AI 综合分析 + 人工确认）
```

###### 解读

文书生成不是为了替检察官 “写结论”，而是把高重复、格式化、证据密集的写作工作提效。

最重要的是：**所有草稿都必须保留 “AI assisted” 标记和版本链路。**

#### 五、最佳实践中的 Agent 角色设计

---

##### 1. 推荐使用多 Agent，而不是单 Agent

```text
Orchestrator Agent
├─ Intake Agent
├─ Dossier Integrity Agent
├─ Timeline Agent
├─ Evidence Chain Agent
├─ Procedure Review Agent
├─ Legal Analysis Agent
├─ Supplementary Investigation Agent
├─ Drafting Agent
└─ Audit Agent
```

---

##### 2. 为什么多 Agent 更优

###### 单 Agent 的问题

- 上下文过长，容易丢重点
- 容易把实体判断、程序审查、文书起草混在一起
- 输出不可控，难审计
- 升级某一环节困难

###### 多 Agent 的好处

- 每个 Agent 任务边界清晰
- 每一步都可以做质量校验
- 便于人工插入复核节点
- 模型升级和规则升级更灵活
- 更符合检察业务分工

---

#### 六、最佳实践中的人机协同设计

---

##### 1. AI 负责什么，检察官负责什么

###### AI 负责

- 找材料
- 建时间线
- 找矛盾
- 列缺口
- 出草稿
- 做引用
- 做对照

###### 检察官负责

- 判断证据证明力
- 判断是否排除合理怀疑
- 判断程序瑕疵性质
- 判断定性与量刑建议
- 判断是否退补、起诉、不诉
- 对外签发正式法律文书

---

##### 2. 必须设置的人工门

###### 门 1：案件进入深度分析前

确认：

- 材料是否齐
- OCR 是否可用
- 权限是否正确

###### 门 2：证据不足时

确认：

- 是否确需退补
- 补证重点是否合理

###### 门 3：文书导出前

确认：

- 草稿内容是否准确
- 是否有不当推断
- 是否存在引用错误
- 是否适合进入正式流程

###### 门 4：正式法律决定前

必须由检察官本人作出实质性判断。

---

#### 七、审计链路最佳实践

这是司法场景最核心的建设项之一。

##### 1. 必须记录的内容

- 谁导入了案件
- 哪个模型参与了分析
- 模型分析基于哪些材料
- 每条结论引用了哪些页码
- 哪个检察官接受 / 拒绝了哪些 AI 建议
- 哪份草稿后来被人工如何修改
- 最终结论与 AI 草稿差异在哪里

##### 2. 审计事件流示例

```text
case_created
dossier_uploaded
ocr_completed
document_classified
timeline_generated
evidence_matrix_built
procedure_issue_flagged
legal_analysis_generated
supplementary_outline_generated
human_review_started
manual_edit_applied
draft_exported
case_archived
```

##### 3. 解读

如果没有这条审计链，系统一旦出错，就很难回答：

- 错在模型，还是错在数据？
- 错在 OCR，还是错在法律分析？
- AI 说过，还是人工后来改过？

司法场景里，不能只要 “结果”，必须要 “过程”。

---

#### 八、数据与知识管理最佳实践

---

##### 1. 案件知识不能和通用知识混在一起

至少要分三层：

###### 层 1：案件上下文层

- 当前案件卷宗
- 当前批注
- 当前补充材料

###### 层 2：规范依据层

- 刑法
- 刑诉法
- 司法解释
- 指导案例
- 规范性文件
- 办案指引

###### 层 3：组织知识层

- 本院审查模板
- 常见退补模板
- 证据审查清单
- 重点罪名审查规则
- 历史高质量匿名案例范式

---

##### 2. 最佳实践：把 “存储” 和 “管理” 分开

这点很值得借鉴文章里说的上下文管理思路：

- **存储层**负责不丢
- **管理层**负责判断当前应给模型哪些内容

在检察场景里尤其必要：

- 卷宗全文可以存
- 但每一步分析不一定都要把全文塞给模型
- 应按子任务动态裁剪上下文
- 长任务靠 “案件记忆对象” 续接，不靠无限上下文堆叠

---

#### 九、安全与合规最佳实践

---

##### 1. 部署原则

###### 强烈建议

- 内网部署或专网部署
- 模型白名单
- 案件分级隔离
- 全链路加密
- 输出水印
- 操作实名制
- 禁止外网工具直接调用案件数据

###### 不建议

- 直接将涉案卷宗发到公网大模型
- 使用无留痕的通用聊天模式处理案件
- 把案卷作为训练数据默认沉淀
- 允许 AI 直接向外部系统自动发送正式文书

---

##### 2. 权限策略

按角色控制：

- 检察官
- 检察官助理
- 书记员
- 技术人员
- 部门负责人
- 管理员

按案件控制：

- 仅承办人可见
- 部门可见
- 院级可见
- 敏感案件单独隔离

按动作控制：

- 可查看
- 可检索
- 可生成草稿
- 可导出
- 可审批
- 可归档

---

#### 十、质量控制最佳实践

---

##### 1. 不要只看 “模型答得像不像”

要看四类指标：

###### A. 证据绑定质量

- 引文命中率
- 页码定位准确率
- 引文与结论一致率

###### B. 审查发现质量

- 证据缺口识别召回率
- 程序瑕疵识别召回率
- 时间线冲突识别率

###### C. 文书辅助质量

- 草稿可采纳率
- 人工修改率
- 关键错误率

###### D. 治理与稳定性

- 可回放率
- 中断恢复成功率
- 越权调用次数
- 敏感输出拦截率

---

##### 2. 最佳实践：双层校验

###### 第一层：Agent 自检

- 每个结论是否有引文
- 是否使用过期法条
- 是否存在明显冲突

###### 第二层：Review Agent 复核

- 证据链是否闭合
- 是否有关键反向证据未纳入
- 是否越权给出最终裁判性结论

---

#### 十一、一个可落地的最佳实践工作流

下面给出一版适合产品、技术、业务三方都能对齐的标准流。

```text
1. 导入案件卷宗
2. OCR + 文书分类 + 页级索引
3. 建立案件结构化对象
4. 完整性审查
5. 时间线重建
6. 证据矩阵构建
7. 程序合法性审查
8. 法律适用分析
9. 识别退补点 / 争点 / 讯问重点
10. 生成辅助文书草稿
11. 检察官人工复核与修改
12. 输出审查结果并归档
13. 审计留痕与规则沉淀
```

#### 十二、这套最佳实践的真正价值

##### 1. 对检察官的价值

- 缩短阅卷和摘录时间
- 快速形成案件全貌
- 提高证据缺口识别效率
- 减少低级遗漏
- 把精力集中到真正的法律判断上

##### 2. 对办案质量的价值

- 审查更标准化
- 引用更清晰
- 过程更可复核
- 风险更早暴露
- 退补更有针对性

##### 3. 对组织治理的价值

- 审查经验可沉淀
- 模板与规则可复用
- 新人培养效率更高
- 院内统一审查口径更容易形成

---

#### 十三、最容易踩的坑

##### 坑 1：把它做成一个聊天机器人

后果：

- 输出随机
- 过程不可控
- 无法留痕
- 难以纳入办案流程

##### 坑 2：只做摘要，不做证据绑定

后果：

- 不能复核
- 不能引用
- 检察官不敢用

##### 坑 3：只看实体，不看程序

后果：

- 发现不了真正高风险问题
- 只能做 “像法律助理”，做不到 “像办案辅助系统”

##### 坑 4：没有人工门禁

后果：

- 组织无法放心使用
- 容易造成越权输出和责任不清

##### 坑 5：把长任务强行塞进一次大模型上下文

后果：

- 成本高
- 稳定性差
- 易漏信息
- 难恢复

#### 十四、如果借鉴 Managed Agents，这个场景最值得学什么

结合你给的文章背景，这个场景最值得借鉴的不是 “云上托管” 本身，而是三件事：

##### 1. 用托管式长任务运行替代本地一次性会话

检察卷宗审查天然是长任务：

- 可以后台跑
- 可以暂停后恢复
- 可以多人接力
- 可以保留状态

##### 2. 用 “大脑 — 手 — 记忆” 解耦替代单体式 Agent

- 大脑：法律分析与调度
- 手：OCR、检索、页码定位、法条比对
- 记忆：案件状态、审查轨迹、引文关系、版本链

这会让系统更稳定，也更适合司法业务治理。

##### 3. 用 “工作流系统” 替代 “Prompt 工程”

真正的竞争力不在于 Prompt 写得多花，而在于：

- 任务拆得准
- 引文链做得严
- 人工门放得对
- 审计线留得全
- 规则库沉淀得深

> 在 “检察官审查公安移送刑事卷宗” 这个场景里，最佳实践不是造一个会回答法律问题的大模型，而是建设一个以卷宗证据为中心、以工作流为骨架、以人工复核为闸门、以审计链路为底座的办案辅助 Agent 系统。

- 帮你更快看清案件

- 帮你把复杂审查过程产品化、标准化、可回放化

#### 三、分层解读

##### 1. 用户与业务入口层

这一层解决的是 “谁在用、从哪里进、在什么业务节点使用”。

典型角色包括：

- **检察官**：查看分析结果、作出实质判断、修改草稿
- **检察官助理**：导入材料、发起审查、整理结果
- **书记员**：做卷宗整理、记录和导出
- **部门负责人**：做复核、查看办案质量
- **案管系统 / 办案系统**：作为案件来源与结果回写端

这一层的重点不是智能，而是**把 Agent 嵌入原有办案流程**，避免成为独立孤岛工具。

---

##### 2. 案件接入与任务编排层

这是整个系统的 “流程控制中心”。

核心职责：

- 创建案件实例
- 接收卷宗文件与元数据
- 判断案件类型
- 选择对应审查模板
- 按案件状态推进工作流
- 在关键节点强制人工复核

这一层相当于 “司法版任务编排器”，保证系统不是自由对话，而是**按办案逻辑运转**。

---

##### 3. Agent 编排与推理决策层

这一层是系统的 “大脑”。

建议采用一个`Orchestrator Agent`统一调度多个专业 Agent，而不是一个大模型从头做到尾。

原因很简单：

- 审查任务太长
- 子任务边界清晰
- 需要中断恢复
- 需要可审计
- 需要人工插入干预

---

##### 4. 卷宗理解与检索能力层

这一层是系统 “看懂卷宗” 的基础能力。

关键不是单纯 OCR，而是形成：

- 页级可定位文本
- 文书类型识别
- 结构化字段抽取
- 可回溯的证据锚点

如果这层做不好，后面的法律分析再强也没有落地价值，因为结论无法回指卷宗。

---

##### 5. 工具执行与规则引擎层

这一层是系统的 “手”。

用于执行那些稳定、可控、可复用的任务，比如：

- 页码连续性检查
- 材料目录比对
- 时间轴自动拼接
- 证据要件表生成
- 程序节点核查
- 电子数据取证链条核验

原则上，**能规则化的尽量规则化，能工具化的不要全交给模型猜**。

---

##### 6. 文书与结果生成层

这一层负责输出办案成果，但要坚持一个原则：

> 只能生成 “辅助成果”，不能直接生成 “最终裁量结果”。

适合生成：

- 阅卷摘要
- 审查提示
- 退补提纲
- 讯问提纲
- 争议焦点摘要
- 证据缺口列表

不适合未经人工确认直接生成正式法律决定。

---

##### 7. 数据与记忆层

这一层是系统的 “记忆”。

必须存储：

- 原始卷宗
- OCR 文本
- 文书分类结果
- 页级索引
- 引文关系
- Agent 中间结果
- 人工修改记录
- 草稿版本
- 审查过程状态

这里最重要的思想是：

> **把 “存储” 与 “上下文管理” 分开。**

卷宗可以全量保存，但每个 Agent 只拿当前子任务需要的那部分上下文，否则成本高、稳定性差、错误率高。

---

##### 8. 审计、安全与治理层

司法场景里，这一层不是附属品，而是底座。

至少应具备：

- 操作实名制
- 案件权限隔离
- 模型使用范围限制
- 输出内容可审计
- 引文可回放
- 版本可追踪
- 导出可控制
- 错误可复盘

没有这一层，系统就不具备正式办案辅助的可用性。

#### 十一、系统中的 “记忆” 设计图

这个场景很适合借鉴 “大脑 — 手 — 记忆” 分离思路。

```text
                    ┌──────────────────────┐
                    │      大脑层            │
                    │ Agent 推理与调度        │
                    └──────────────────────┘
                              │
                              │ 调用
                              ▼
                    ┌──────────────────────┐
                    │      手层              │
                    │ OCR / 检索 / 规则 / 校验工具 │
                    └──────────────────────┘
                              │
                              │ 读写
                              ▼
                    ┌──────────────────────┐
                    │      记忆层            │
                    │ 案件状态               │
                    │ 文书索引               │
                    │ 引文关系               │
                    │ 草稿版本               │
                    │ 人工批注               │
                    │ 审计日志               │
                    └──────────────────────┘
```

###### 解读

在检察场景里，“记忆层” 尤其重要，因为一个案件审查不是一次问答，而是一个持续过程：

- 今天看完卷宗完整性
- 明天补充审查证据链
- 后天领导复核
- 一周后补充材料再次分析

如果没有独立记忆层，系统就无法稳定续办。

#### 十二、推荐的模块边界

为了避免后期系统越来越乱，建议从一开始就明确边界：

##### 1. 模型负责

- 文本理解
- 事实抽取
- 争议归纳
- 证据关联推断
- 草稿表达

##### 2. 工具负责

- OCR
- 页码定位
- 目录比对
- 法条检索
- 规则校验
- 权限检查
- 文书模板渲染

##### 3. 人工负责

- 裁量判断
- 事实最终认定
- 证据证明力评价
- 程序瑕疵性质判断
- 起诉 / 不诉 / 退补决定
