## 正文

**Philipp Schmid**

### How Autoresearch will change Small Language Models adoption

What if you could optimize a model overnight without any ML experience? What if an AI agent runs hundreds of training experiments autonomously, keeping only the improvements? That is the idea behind

[autoresearch](https://github.com/karpathy/autoresearch). You give an AI agent a training script and a metric. It edits the code, runs a short experiment, checks if the metric improved, keeps or discards, and repeats.

[Karpathy](https://x.com/karpathy/status/2031135152349524125)

used it to squeeze 11% more speed out of his GPT-2 training.

[Tobi Lütke](https://x.com/tobi/status/2030771823151853938)

, Shopify's CEO, trained a 0.8B model overnight that outscored his previous 1.6B.

#### How Autoresearch Works

An LLM agent that can edit training code, runs a short experiment, checks if the metric improved, and repeats, without human involvement.

![Image](https://pbs.twimg.com/media/HDDSuvTXkAAXkdY?format=jpg&name=large)

Design constraints that make it work:

- Fixed 5-min time budget. Results stay comparable regardless of what the agent changes.
- Single file scope. Agent edits
  train.py only. Data prep and evaluation are locked down.
- Git as memory. Each experiment is a commit. The agent reads branch history to plan what to try next.
- Binary keep/discard. No human judgment needed.

Roughly 12 experiments/hour. Around 100 overnight.

#### Two Early Experiments

Both examples below are small-scale and early. The setups are minimal, the models are small, and neither is a controlled study. But they show where this is headed.

Karpathy: 700 experiments on nanochat

Karpathy pointed autoresearch at

[nanochat](https://github.com/karpathy/nanochat), his already well-tuned GPT-2 training codebase. Over two days the agent ran \~700 experiments and found \~20 real improvements. Stacked together, time-to-GPT-2 dropped from 2.02 to 1.80 hours (11% faster). The agent caught things Karpathy had missed:

- Parameterless QKNorm had no scaler multiplier, making attention too diffuse
- Value Embeddings had no regularization applied
- Banded attention window was too conservative
- AdamW betas, weight decay schedule, and initialization were all suboptimal

All improvements transferred from depth-12 to depth-24 models.

Tobi Lütke query expansion overnight

Tobi adapted the pattern for a query-expansion model for the

[QMD Open source project](https://github.com/tobi/qmd):

1. Told an AI agent to read the autoresearch repo and build a version for QMD. Get training data from tobi/qmd github.
2. Went to sleep
3. Woke up to a 0.8B model scoring 19% higher than the previous 1.6B model after 37 experiments in 8 hours

A smaller model outperformed one twice its size. He then pointed the same loop at a reranker and beat that baseline too.

#### How to apply this

The loop hinges on your eval. If the metric is gamed or leaky, the model looks better on paper and fails in production. Your eval set must be held out completely — the agent never touches it, never trains on it, never sees it during optimization. You need a training script the agent can modify, training data (manually labeled or synthetic), and a metric that reflects what the model will actually do in production.

When experiments run 100x faster than a human can manage, your eval becomes the bottleneck. Static benchmarks get saturated. Build your eval pipeline so it can evolve, refresh from real production data, harder edge cases.

The pattern fits search ranking, product categorization, clinical NER, fraud scoring, contract extraction, intent classification, and similar tasks. Small models work well — training runs finish in minutes and improvements transfer when you scale up. Open models like Gemma are a good starting point: small enough for a single GPU, performant for production tasks, commercially licensed.

How this differs from GEPA and prompt optimizers

[GEPA](https://arxiv.org/abs/2501.09361) (Genetic-Pareto prompt evolution, ICLR 2026) optimizes prompts using genetic evolution and reflection. It works on frozen models and APIs where you cannot change weights.

Autoresearch optimizes weights — it modifies training code, architectures, and hyperparameters to produce a better model.

- GEPA / prompt optimization: No training. Works on frozen models and APIs.
- Autoresearch / weight optimization: Changes the model itself. Requires training infra and data.

For teams building domain SLMs, both layers compound.

## 结构化（1）

### 2026-03-12 12:01:41

**主旨概括：**  
Autoresearch 的核心价值是：让 AI 代理自动改训练代码、跑实验、保留有效改动，从而大幅降低小语言模型（SLM）的优化门槛。文章认为，这种方式会加速 SLM 在垂直场景中的落地，因为它能用更少人力、更小模型做出更好的效果。

---

##### 1. 什么是 Autoresearch：让 AI 自动做 “训练实验员”
- Autoresearch 的思路很简单：  
  给 AI 一个训练脚本和一个评估指标，它会**自己改代码、跑短实验、看指标有没有变好、决定保留还是丢弃**，然后不断重复。
- 整个过程**不需要人工反复盯实验**，即使没有 ML 经验，也可能在一夜之间把模型优化一轮。
- 文中给出两个直观例子：  
  - **Karpathy**用它把 GPT-2 训练速度提升了**11%**。  
  - **Shopify CEO Tobi Lütke**用它一夜训出一个**0.8B**模型，表现还超过了之前的**1.6B**模型。

---

##### 2. 它是怎么工作的：靠严格约束保证实验有效
文章强调，Autoresearch 能跑起来，关键不只是 “AI 会改代码”，而是有一套约束机制：

- **固定 5 分钟实验预算**  
  每次实验时间都一样，方便公平比较不同改动的效果。
- **只改一个文件（train.py）**  
  数据处理和评估流程锁死，避免代理乱改整个项目，保证可控。
- **用 Git 当记忆系统**  
  每次实验都是一次 commit，AI 可以通过分支历史判断下一步尝试什么。
- **二元决策：保留 / 丢弃**  
  不需要人工主观判断，只看指标是否提升。
- **实验速度很快**  
  大约**每小时 12 次实验**，一晚上能做**约 100 次**。

通俗理解：  
它像一个不会累的 “自动调参研究员”，不停试小改动，只留下真正有用的部分。

---

##### 3. 两个早期案例：虽然规模小，但方向很清晰

###### 3.1 Karpathy：在 nanochat 上做了约 700 次实验
- Karpathy 把 autoresearch 用在自己已经优化过的 GPT-2 训练代码库**nanochat**上。
- **两天内跑了约 700 次实验**，其中找到**约 20 个真正有效的改进**。
- 这些改进叠加后，**达到 GPT-2 水平所需训练时间从 2.02 小时降到 1.80 小时**，也就是**快了 11%**。

AI 找到了一些人容易忽略的问题，比如：
- **Parameterless QKNorm**没有 scaler multiplier，导致 attention 太分散；
- **Value Embeddings**没有加正则；
- **Banded attention window**设得过于保守；
- **AdamW betas、weight decay schedule、初始化**都不是最优。

更重要的是：
- 这些改进**不仅在 12 层模型有效，也能迁移到 24 层模型**。  
  说明它找出的不是偶然技巧，而是有一定泛化价值的优化。

---

###### 3.2 Tobi Lütke：一夜之间让更小模型超过更大模型
- Tobi 把同样的方法用在**QMD 开源项目**的 query-expansion 模型上。
- 他的操作流程很简单：
  1. 让 AI 代理阅读 autoresearch 仓库；
  2. 基于 QMD 搭一个可用版本；
  3. 从`tobi/qmd` GitHub 获取训练数据；
  4. 然后去睡觉。

结果是：
- **8 小时内跑了 37 次实验**；
- 最终得到一个**0.8B 模型**；
- 该模型的得分比之前的**1.6B 模型高 19%**。

这说明：
- **更小的模型也可能通过更好的训练方式，打败更大的模型**。
- 后来他把同样的自动循环用在 reranker 上，也**超过了原有 baseline**。

---

##### 4. 真正的关键不在 “跑得快”，而在 “评估是否靠谱”
文章特别提醒：Autoresearch 的成败，**核心取决于评估体系（eval）**。

- 如果指标本身有漏洞、能被 “刷分”，模型可能只是**纸面变好**，上线却失败。
- 因此评估集必须：
  - **完全留出（held out）**；
  - 代理**不能接触**；
  - **不能参与训练**；
  - 优化过程中也**不能看到**。

要应用这套方法，至少需要三样东西：
- 一个可修改的训练脚本；
- 训练数据（人工标注或合成数据都可以）；
- 一个真正反映生产效果的指标。

文章的判断是：
- 当实验速度变成**人工的 100 倍**时，瓶颈就不再是 “跑实验”，而是 “有没有足够好的评估”。
- 所以评估系统不能是死的，要能：
  - 持续更新；
  - 从真实线上数据刷新；
  - 补充更难的边界案例。

---

##### 5. 适合哪些任务：尤其适合垂直场景的小模型
这种模式适合很多明确任务目标的场景，例如：
- 搜索排序
- 商品分类
- 临床命名实体识别（clinical NER）
- 欺诈评分
- 合同信息抽取
- 意图分类

为什么适合小模型（SLM）？
- **训练一次只要几分钟**，试错成本低；
- 找到的改进在放大模型时往往还能迁移；
- 小模型更容易在生产环境落地。

文中还提到：
- 像**Gemma**这样的开源模型是不错的起点：  
  - 小到可以在**单张 GPU**上训练；  
  - 对生产任务来说性能足够；  
  - 而且有**商业许可**。

---

##### 6. 它和 GEPA / Prompt 优化有什么不同
文章最后区分了两类优化路线：

###### GEPA / Prompt 优化
- 代表：**GEPA（Genetic-Pareto prompt evolution, ICLR 2026）**
- 做法：用遗传进化和反思来优化 prompt。
- 特点：
  - **不训练模型**
  - 适合**冻结模型**或 API 场景
  - 不能改模型权重

###### Autoresearch / 权重优化
- 做法：直接改训练代码、模型结构、超参数，最终**优化模型本身**。
- 特点：
  - **会训练模型**
  - 需要训练基础设施和数据
  - 能改变权重，得到真正更好的模型

一句话理解：
- **Prompt 优化**：不动模型，只优化 “怎么问”。  
- **Autoresearch**：直接优化 “模型怎么学”。

文章认为：
- 对于要做垂直领域 SLM 的团队，这两层优化**可以叠加使用**，效果会更强。

---

##### 总结
Autoresearch 让 AI 代理自动完成大量训练实验，把模型优化从 “专家手工调参” 变成 “自动化搜索改进”。从文中的两个案例看，它已经能在真实任务中带来明显收益：**Karpathy 的 GPT-2 训练提速 11%，Tobi 的 0.8B 模型反超 1.6B 模型 19%**。  
它最有潜力推动的是**小语言模型在垂直业务中的普及**，但前提是：**评估体系必须足够可靠，否则自动优化只会放大错误方向。**

## 产品-最佳实践（1）

### 2026-03-12 12:02:29

下面用一个**“电商商品分类小模型”**的具体实例，说明 Autoresearch 的最佳实践。

##### 具体实例
目标：训练一个**0.8B 的商品分类 SLM**，用于把商品标题 / 描述自动归类到标准类目。  
约束：

- 训练脚本固定为`train.py`
- 每次实验**5 分钟**
- 优化指标：**线上分布贴近的验证集 F1**
- Agent 只能改：
  - 学习率、batch size、weight decay
  - loss 设计
  - pooling 方式
  - 分类头结构
  - 正则化参数
- Agent 不能碰：
  - 测试集
  - 数据清洗逻辑
  - 评估脚本

运行一晚后，Agent 自动尝试 80~100 次实验，例如：

- 把 mean pooling 改成 attention pooling
- 调整 AdamW betas
- 给长尾类目加 class weight
- 加 label smoothing
- 调整 warmup ratio
- 改 dropout 和初始化方式

最终保留有效改动，模型从**F1=84.2 提升到 87.1**，并且推理成本仍低于原先的大模型方案。

---

##### 在这个实例上的最佳实践（精炼）

###### 1. **先锁死评估，再开放优化**
Autoresearch 成败不在 “试得多”，而在 “评得准”。  
最佳实践：

- 保留**完全隔离的 held-out test set**
- Agent 只看训练集 + 小验证集
- 验证指标必须接近真实业务目标，而不是方便计算的代理指标

> 否则 Agent 只会 “刷分”，不会真正提升线上效果。

###### 2. **把搜索空间限制在高价值、低风险改动**
不要让 Agent 随意改整个工程。  
最佳实践：

- 只允许改`train.py`
- 先开放超参、正则、loss、head、pooling
- 后续再开放更高风险结构改动

> 这样更稳、更容易复现，也更适合夜间自动跑。

###### 3. **固定每轮实验预算，保证可比性**
文章里的关键设计就是**固定 5 分钟预算**。  
最佳实践：

- 每次实验相同训练时长 / 相同步数
- 相同数据切片
- 相同评估流程

> 不然有些实验只是 “跑得更久”，不是 “方法更好”。

###### 4. **用 Git 记录每次实验，形成可回溯记忆**
最佳实践：

- 每次实验一个 commit
- commit message 写清：改了什么、指标如何
- 只保留优于 baseline 的版本

> 这样 Agent 和人类都能快速理解哪些改动真正有效。

###### 5. **采用二元决策：保留 / 丢弃**
不要让流程依赖人工主观判断。  
最佳实践：

- 指标提升就保留
- 无提升就回滚
- 设定最小提升阈值，避免噪声误判

> 核心是把优化循环做成 “自动化生产线”。

###### 6. **优先选小模型任务，先验证再放大**
Autoresearch 最适合**训练快、反馈快**的任务。  
最佳实践：

- 先用 0.5B~1B 小模型验证
- 找到稳定收益后，再迁移到更大模型

> 很多改进会从小模型迁移到大模型，成本却低很多。

###### 7. **持续刷新评估集，防止 benchmark 被刷穿**
当 Agent 一晚跑上百次，静态验证集很快会失效。  
最佳实践：

- 定期从真实线上错误案例补充新样本
- 加入长尾类目、脏文本、歧义标题
- 维护 “困难集”

> Autoresearch 的瓶颈最终不是训练，而是 eval 质量。

---

##### 一句话总结
**Autoresearch 最佳落地方式，不是让 Agent “随便改模型”，而是让它在一个严格受控、评估可信、反馈极快的闭环里高频试错。**  
对商品分类、检索排序、NER、意图识别这类任务，尤其适合先从**小模型 + 固定预算 + 强评估**开始。
