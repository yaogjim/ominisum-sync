An on-device search engine for everything you need to remember. Index your markdown notes, meeting transcripts, documentation, and knowledge bases. Search with keywords or natural language. Ideal for your agentic flows.

QMD combines BM25 full-text search, vector semantic search, and LLM re-ranking—all running locally via node-llama-cpp with GGUF models.

QMD Architecture

You can read more about QMD's progress in the CHANGELOG.

#### Quick Start

```
# Install globally (Node or Bun)
npm install -g @tobilu/qmd
# or
bun install -g @tobilu/qmd

# Or run directly
npx @tobilu/qmd ...
bunx @tobilu/qmd ...

# Create collections for your notes, docs, and meeting transcripts
qmd collection add ~/notes --name notes
qmd collection add ~/Documents/meetings --name meetings
qmd collection add ~/work/docs --name docs

# Add context to help with search results, each piece of context will be returned when matching sub documents are returned. This works as a tree. This is the key feature of QMD as it allows LLMs to make much better contextual choices when selecting documents. Don't sleep on it!
qmd context add qmd://notes "Personal notes and ideas"
qmd context add qmd://meetings "Meeting transcripts and notes"
qmd context add qmd://docs "Work documentation"

# Generate embeddings for semantic search
qmd embed

# Search across everything
qmd search "project timeline"           # Fast keyword search
qmd vsearch "how to deploy"             # Semantic search
qmd query "quarterly planning process"  # Hybrid + reranking (best quality)

# Get a specific document
qmd get "meetings/2024-01-15.md"

# Get a document by docid (shown in search results)
qmd get "#abc123"

# Get multiple documents by glob pattern
qmd multi-get "journals/2025-05*.md"

# Search within a specific collection
qmd search "API" -c notes

# Export all matches for an agent
qmd search "API" --all --files --min-score 0.3
```

QMD's `--json` and `--files` output formats are designed for agentic workflows:

```
# Get structured results for an LLM
qmd search "authentication" --json -n 10

# List all relevant files above a threshold
qmd query "error handling" --all --files --min-score 0.4

# Retrieve full document content
qmd get "docs/api-reference.md" --full
```

##### MCP Server

Although the tool works perfectly fine when you just tell your agent to use it on the command line, it also exposes an MCP (Model Context Protocol) server for tighter integration.

**Tools exposed:**

- `query` — Search with typed sub-queries (`lex` / `vec` / `hyde`), combined via RRF + reranking
- `get` — Retrieve a document by path or docid (with fuzzy matching suggestions)
- `multi_get` — Batch retrieve by glob pattern, comma-separated list, or docids
- `status` — Index health and collection info

```

###### HTTP Transport

By default, QMD's MCP server uses stdio (launched as a subprocess by each client). For a shared, long-lived server that avoids repeated model loading, use the HTTP transport:

```
# Foreground (Ctrl-C to stop)
qmd mcp --http                    # localhost:8181
qmd mcp --http --port 8080        # custom port
qmd mcp --http --host 0.0.0.0     # bind all interfaces (e.g. container probes)

# Background daemon
qmd mcp --http --daemon           # start, writes PID to ~/.cache/qmd/mcp.pid
qmd mcp stop                      # stop via PID file
qmd status                        # shows "MCP: running (PID ...)" when active
```

The server binds to `localhost` by default. Pass `--host` (or set the `QMD_HOST` environment variable) to override — `--host 0.0.0.0` is useful when the server runs in a container and a liveness probe connects from a non-loopback address.

The HTTP server exposes two endpoints:

- `POST /mcp` — MCP Streamable HTTP (JSON responses, stateless)
- `GET /health` — liveness check with uptime

LLM models stay loaded in VRAM across requests. Embedding/reranking contexts are disposed after 5 min idle and transparently recreated on the next request (\~1s penalty, models remain loaded).

Point any MCP client at `http://localhost:8181/mcp` to connect.

Tool Parameter Type Notes

`query` `searches` array Typed sub-queries (`lex` / `vec` / `hyde`), 1–10. **Required.** First gets 2x weight.

`query` `collections` string\[\] Filter by collection names (OR). **Array only** — singular `collection` is silently ignored.

`query` `intent` string Disambiguation context (does not search on its own)

`query` `limit` number Max results (default 10)

`query` `minScore` number Minimum relevance 0–1 (default 0)

`query` `candidateLimit` number Max candidates to rerank (default 40)

`query` `rerank` boolean Run LLM reranking (default **true**); set false for RRF-only

`get` `file` string Path, docid (`#abc123`), or `path:from:count` (e.g. `#abc123:120:40`)

`get` `fromLine` number Start line (1-indexed); overrides the `:from` suffix

`get` `maxLines` number Limit returned lines

`get` `lineNumbers` boolean Prefix lines with numbers (default **true**)

`multi_get` `pattern` string Glob pattern or comma-separated list

`multi_get` `maxBytes` number Skip files larger than N (default 10240)

`multi_get` `maxLines` number Limit lines per file

`multi_get` `lineNumbers` boolean Prefix lines with numbers (default **true**)

Unknown parameters are silently ignored (not rejected) — double-check names if results seem unscoped. The HTTP `/query` and `/search` endpoints return `qmd://collection/path` URIs in the `file` field, matching the CLI and MCP output.

###### Search

The unified `search()` method handles both simple queries and pre-expanded structured queries:

```
// Simple query — auto-expanded via LLM, then BM25 + vector + reranking

// With options
const results2 = await store.search({
  query: "rate limiting",
  intent: "API throttling and abuse prevention",
  collection: "docs",
  limit: 5,
  minScore: 0.3,

// Pre-expanded queries — skip auto-expansion, control each sub-query
const results3 = await store.search({

// Skip reranking for faster results
const fast = await store.search({ query: "auth", rerank: false })

##### Search Backends

Backend Raw Score Conversion Range

**FTS (BM25)** SQLite FTS5 BM25 `Math.abs(score)` 0 to \~25+

**Vector** Cosine distance `1 / (1 + distance)` 0.0 to 1.0

**Reranker** LLM 0-10 rating `score / 10` 0.0 to 1.0

##### Fusion Strategy

The `query` command uses **Reciprocal Rank Fusion (RRF)** with position-aware blending:

1. **Query Expansion**: Original query (×2 for weighting) + 1 LLM variation
2. **Parallel Retrieval**: Each query searches both FTS and vector indexes
3. **RRF Fusion**: Combine all result lists using `score = Σ(1/(k+rank+1))` where k=60
4. **Top-Rank Bonus**: Documents ranking #1 in any list get +0.05, #2-3 get +0.02
5. **Top-K Selection**: Take top 30 candidates for reranking
6. **Re-ranking**: LLM scores each document (yes/no with logprobs confidence)
7. **Position-Aware Blending**:
   - RRF rank 1-3: 75% retrieval, 25% reranker (preserves exact matches)
   - RRF rank 4-10: 60% retrieval, 40% reranker
   - RRF rank 11+: 40% retrieval, 60% reranker (trust reranker more)

**Why this approach**: Pure RRF can dilute exact matches when expanded queries don't match. The top-rank bonus preserves documents that score #1 for the original query. Position-aware blending prevents the reranker from destroying high-confidence retrieval results.

##### Score Interpretation

Score Meaning

0.8 - 1.0 Highly relevant

0.5 - 0.8 Moderately relevant

0.2 - 0.5 Somewhat relevant

0.0 - 0.2 Low relevance

QMD uses three local GGUF models (auto-downloaded on first use):

Model Purpose Size

`embeddinggemma-300M-Q8_0` Vector embeddings (default) \~300MB

`qwen3-reranker-0.6b-q8_0` Re-ranking \~640MB

`qmd-query-expansion-1.7B-q4_k_m` Query expansion (fine-tuned) \~1.1GB

Models are downloaded from HuggingFace and cached in `~/.cache/qmd/models/`.

Override the default embedding model via the `QMD_EMBED_MODEL` environment variable. This is useful for multilingual corpora (e.g. Chinese, Japanese, Korean) where `embeddinggemma-300M` has limited coverage.

```
# Use Qwen3-Embedding-0.6B for better multilingual (CJK) support
export QMD_EMBED_MODEL="hf:Qwen/Qwen3-Embedding-0.6B-GGUF/Qwen3-Embedding-0.6B-Q8_0.gguf"

# After changing the model, re-embed all collections:
qmd embed -f
```

Supported model families:

- **embeddinggemma** (default) — English-optimized, small footprint
- **Qwen3-Embedding** — Multilingual (119 languages including CJK), MTEB top-ranked

> **Note:** When switching embedding models, you must re-index with `qmd embed -f` since vectors are not cross-compatible between models. The prompt format is automatically adjusted for each model family.

```
# Embed all indexed documents (900 tokens/chunk, 15% overlap)
qmd embed

# Force re-embed everything
qmd embed -f

# Enable AST-aware chunking for code files (TS, JS, Python, Go, Rust)
qmd embed --chunk-strategy auto

# Also works with query for consistent chunk selection
qmd query "auth flow" --chunk-strategy auto

# Memory control for large corpora / constrained systems
qmd embed --max-docs-per-batch 50   # cap docs per embedding batch
qmd embed --max-batch-mb 64         # cap batch size in MB
```

**AST-aware chunking** (`--chunk-strategy auto`) uses tree-sitter to chunk code files at function, class, and import boundaries instead of arbitrary text positions. This produces higher-quality chunks and better search results for codebases. Markdown and other file types always use regex-based chunking regardless of strategy.

The default is `regex` (existing behavior). Use `--chunk-strategy auto` to opt in. Run `qmd status` to verify which grammars are available.

> **Note:** Tree-sitter grammars are optional dependencies. If they are not installed, `--chunk-strategy auto` falls back to regex-only chunking automatically. Tested on both Node.js and Bun.

##### Configuring index.yml

The `collection` and `context` commands above all read and write a single YAML config file — you can also edit it directly. Everything QMD knows about your collections (paths, masks, exclusions, per-collection update hooks, contexts, and optional model overrides) lives here. A fully-commented starter template ships as `example-index.yml` in this repo.

**Location:**`~/.config/qmd/index.yml` by default. The directory honors `XDG_CONFIG_HOME` (→ `$XDG_CONFIG_HOME/qmd/index.yml`) and `QMD_CONFIG_DIR`. A named index uses `{name}.yml` — `qmd --index work …` reads/writes `work.yml`. A **project-local** index created with `qmd init` lives at `.qmd/index.yml` (`.qmd/index.yaml` is also accepted) alongside a project-local `index.sqlite`, so config and index stay inside the project instead of `~/.config` / `~/.cache`.

```
# ~/.config/qmd/index.yml

# Context applied to every collection (system-message style). Optional.
global_context: "Knowledge base for my projects"

# Terminal hyperlink template for search results. Optional.
# Overridden by the QMD_EDITOR_URI env var. See "Editor Links" below.
editor_uri: "vscode://file{path}:{line}:{col}"

# Override the default GGUF models per role. Optional — omit to use the
# built-in defaults. `qmd init` writes this block pre-filled with the
# resolved defaults. See "Model Configuration" for the default URIs.
models:
  embed: "hf:ggml-org/embeddinggemma-300M-GGUF/embeddinggemma-300M-Q8_0.gguf"
  rerank: "hf:ggml-org/Qwen3-Reranker-0.6B-Q8_0-GGUF/qwen3-reranker-0.6b-q8_0.gguf"
  generate: "hf:tobil/qmd-query-expansion-1.7B-gguf/qmd-query-expansion-1.7B-q4_k_m.gguf"

# One entry per collection. The key is the collection name.
collections:
  notes:
    path: /Users/me/notes        # absolute path to index (required)
    pattern: "**/*.md"           # glob mask (default: **/*.md)
    ignore:                      # glob patterns to exclude from indexing
      - "Archive/**"
      - "**/drafts/**"
    update: "git pull --rebase"  # bash command run before each `qmd update`
    includeByDefault: true       # include in unscoped queries (default: true)
    context:                     # path prefix → description; longest match wins
      "/": "Personal notes and ideas"
      "/work": "Work-related notes"
```

Key Scope Purpose

`global_context` top-level Context prepended for every collection. Set via `qmd context add /`.

`editor_uri` (alias `editor_uri_template`) top-level Hyperlink template for clickable result paths; `QMD_EDITOR_URI` overrides.

`models.embed` / `.rerank` / `.generate` top-level HuggingFace GGUF URIs (`hf:<user>/<repo>/<file>`) overriding the built-in defaults per role.

`collections.<name>.path` per-collection Absolute directory to index.

`collections.<name>.pattern` per-collection Glob mask. Set via `qmd collection add --mask`. Default `**/*.md`.

`collections.<name>.ignore` per-collection Glob patterns excluded from indexing — useful to stop nested collections double-indexing. **YAML-only — no CLI command sets this.** Additive with QMD's built-in exclusions (`node_modules`, `.git`, `.cache`, `vendor`, `dist`, `build`), which you cannot un-ignore.

`collections.<name>.update` per-collection Bash command run before `qmd update` re-indexes this collection. Set via `qmd collection update-cmd`.

`collections.<name>.includeByDefault` per-collection Whether unscoped queries search it. Toggle with `qmd collection include` / `exclude`. Default `true`.

`collections.<name>.context` per-collection Path-prefix → description map; the most specific (longest) matching prefix wins. Set via `qmd context add`.

> **Note:** Editing `index.yml` changes which directories and models QMD *uses*, but does not re-index on its own. Run `qmd update` after changing `path`,`pattern`, or `ignore`, and `qmd embed` after changing `models.embed`.

A collection's `update` field is QMD's built-in refresh hook: when you run `qmd update`, each collection's `update` command runs **first**, then the collection is re-indexed. This keeps a collection in sync with an upstream source (a git remote, a sync script) without wrapping `qmd` yourself.

```
collections:
  wiki:
    path: ~/reference/wiki
    update: "git pull --ff-only"
```

```
$ qmd update
[1/3] wiki (**/*.md)
    Running update command: git pull --ff-only
    Already up to date.
Collection: ~/reference/wiki (**/*.md)
Indexed: 0 new, 2 updated, 340 unchanged, 0 removed
```

The command runs via `bash -c` in the collection's own directory (its `path`), not your current working directory. If it exits non-zero, `qmd update` prints the failure and **aborts the entire run** — collections after the failing one are not re-indexed. Set or clear it from the CLI instead of editing YAML by hand:

```
qmd collection update-cmd wiki 'git pull --ff-only'   # set
qmd collection update-cmd wiki                         # clear
```

##### Collection Filtering

The `-c` / `--collection` flag filters results by collection **name** (as shown by `qmd collection list`). Collections are a global registry — you can search any collection from any directory:

```
qmd search "auth" -c notes           # single collection
qmd search "auth" -c notes -c docs   # multiple collections (OR)
```

With no `-c` flag, all default-included collections are searched. Collections marked excluded (`qmd collection exclude <name>`) are skipped unless named explicitly with `-c`.

> **Note:** With multiple `-c` flags, results come from a global top-K pool and are then filtered. If one collection dominates the rankings, matches from smaller collections may not appear at the default limit — raise `-n` or use `--all`.

Each query runs against four backends, reporting precision@k, recall, MRR, and F1:

Backend What it tests LLM required

`bm25` Keyword search only (FTS5) No

`vector` Semantic similarity only Embedding model

`hybrid` BM25 + vector fusion (no reranking) Embedding model

`full` Full pipeline with LLM reranking All three models

##### Embedding Flow

Documents are chunked into \~900-token pieces with 15% overlap using smart boundary detection:

```
Document ──► Smart Chunk (~900 tokens) ──► Format each chunk ──► node-llama-cpp ──► Store Vectors
                │                           "title | text"        embedBatch()
                │
                └─► Chunks stored with:
                    - hash: document hash
                    - seq: chunk sequence (0, 1, 2...)
                    - pos: character position in original
```

##### Smart Chunking

Instead of cutting at hard token boundaries, QMD uses a scoring algorithm to find natural markdown break points. This keeps semantic units (sections, paragraphs, code blocks) together.

**Break Point Scores:**

Pattern Score Description

`# Heading` 100 H1 - major section

`## Heading` 90 H2 - subsection

`### Heading` 80 H3

`#### Heading` 70 H4

`##### Heading` 60 H5

`###### Heading` 50 H6

```` ``` ```` 80 Code block boundary

`---` / `***` 60 Horizontal rule

Blank line 20 Paragraph boundary

`- item` / `1. item` 5 List item

Line break 1 Minimal break

**Algorithm:**

1. Scan document for all break points with scores
2. When approaching the 900-token target, search a 200-token window before the cutoff
3. Score each break point: `finalScore = baseScore × (1 - (distance/window)² × 0.7)`
4. Cut at the highest-scoring break point

The squared distance decay means a heading 200 tokens back (score \~30) still beats a simple line break at the target (score 1), but a closer heading wins over a distant one.

**Code Fence Protection:** Break points inside code blocks are ignored—code stays together. If a code block exceeds the chunk size, it's kept whole when possible.

**AST-Aware Chunking (Code Files):**

For supported code files, QMD also parses the source with [tree-sitter](https://tree-sitter.github.io/) and adds AST-derived break points that are merged with the regex scores above:

AST Node Score Languages

Class / interface / struct / impl / trait 100 All

Function / method 90 All

Type alias / enum 80 All

Import / use declaration 60 All

Supported for `.ts`, `.tsx`, `.js`, `.jsx`, `.py`, `.go`, and `.rs` files. Enable with `--chunk-strategy auto`. Markdown and other file types always use regex chunking.

#### QMD：面向个人知识库与 AI Agent 的本地搜索引擎

##### 一句话概括

QMD 是一个运行在本地的轻量级搜索工具，可索引 Markdown 笔记、会议记录、项目文档和知识库，并通过**关键词检索、语义搜索和 LLM 重排序**，帮助用户或 AI Agent 找到更准确的上下文。

##### 核心价值

QMD 解决的是 “资料都在本地，但很难快速找准” 的问题：

- **本地运行**：文档、索引和模型默认不依赖云端，兼顾隐私与可控性。
- **统一搜索**：跨笔记、会议、文档等多个目录检索。
- **自然语言查询**：不必记住原文关键词，也能按语义找到内容。
- **Agent 友好**：支持结构化结果、文件批量获取与 MCP，可直接作为 AI Agent 的长期记忆检索层。

##### 搜索能力

QMD 提供三种主要搜索方式：

| 模式 | 原理 | 适用场景 |
|---|---|---|
| `search` | BM25 关键词检索 | 查术语、文件名、API 等精确内容 |
| `vsearch` | 向量语义检索 | 查询表达与原文措辞不一致 |
| `query` | 混合检索 + LLM 重排序 | 追求综合准确率，适合 Agent |

完整流程是：**查询扩展 → BM25 与向量并行召回 → RRF 融合 → 本地 LLM 重排序**。系统会保护高置信度的精确匹配，同时让 LLM 更多优化排名靠后的模糊结果。

##### 差异化设计：上下文树

QMD 允许为知识库、目录或子目录添加说明，例如：

- `notes`：个人想法与灵感
- `meetings`：会议纪要
- `docs/api`：API 参考文档

这些上下文会随搜索结果返回，帮助 AI 理解 “文档属于什么业务、目录和用途”，而不只是看到一段孤立文本。这是它提升 Agent 选文准确率的重要设计。

##### 使用与集成

QMD 提供三种产品形态：

1. **CLI**：适合个人检索、脚本和自动化流程。
2. **MCP Server**：可接入 Claude Desktop、Claude Code 等 MCP 客户端，提供查询、单文档获取、批量获取和索引状态能力。
3. **Node.js/ Bun SDK**：可嵌入应用，自主管理知识集合、上下文、索引、Embedding 和搜索流程。

MCP 还支持常驻 HTTP 服务，使模型持续驻留显存，避免每个客户端重复加载。

```bash

QMD 本质上不是一个笔记应用，而是一个**本地知识检索基础设施**。它适合：

- 个人第二大脑与本地知识库
- 企业内部文档搜索
- 编程 Agent 的代码与文档检索

qmd context add qmd://docs "工作文档"

##### 4. MCP 服务与 AI 工具集成

- `get`：按路径或 docid 获取单个文档，找不到时提供模糊匹配建议。
- `multi_get`：通过通配符、文件列表或 docid 批量获取。
- `status`：查看索引健康状态和集合信息。

  "mcpServers": {
    "qmd": {

}

```bash
claude plugin marketplace add tobi/qmd

##### 5. HTTP MCP 服务

默认情况下，MCP 使用`stdio`，每个客户端会单独启动一个子进程。若希望多个客户端共享模型、避免反复加载，可启动长期运行的 HTTP 服务：

```bash
qmd mcp --http                  # 默认 localhost:8181
qmd mcp --http --port 8080      # 自定义端口
qmd mcp --http --host 0.0.0.0   # 允许非本机地址访问
qmd mcp --http --daemon         # 后台运行
qmd mcp stop                    # 停止后台服务
```

HTTP 服务提供两个端点：

- `POST /mcp`：无状态的 MCP Streamable HTTP 接口。
- `GET /health`：存活检查，并返回运行时间。

性能与资源管理方面：

- LLM 模型会持续保留在显存中。
- 嵌入和重排序上下文闲置**5 分钟**后释放。
- 下次请求会自动重建上下文，约增加**1 秒**延迟，但模型本身无需重新加载。

###### 重要参数限制

- `query.searches`：必须是数组，支持**1～10 个**子查询；第一个查询权重为**2 倍**。
- `query.limit`：默认返回**10**条。
- `query.candidateLimit`：默认最多重排**40**个候选。
- `query.rerank`：默认开启。
- `multi_get.maxBytes`：MCP 参数表中的默认值为**10,240 字节**。
- 未知参数会被**静默忽略**，不会报错。
- `collections`必须使用数组；误写成单数`collection`可能被忽略，导致搜索范围不符合预期。
- HTTP `/query`和`/search`返回的路径格式为：

```text
qmd://collection/path
```

##### 8. 混合搜索架构

QMD 的核心流程可概括为：

```text
用户查询
→ 查询扩展
→ BM25 与向量检索并行执行
→ RRF 融合
→ 选择候选文档
→ 本地 LLM 重排序
→ 按位置混合分数
→ 最终结果
```

###### 查询扩展与并行检索

- 原始查询会被保留，并给予**2 倍权重**。
- LLM 会生成额外查询变体；文中架构示意与文字说明在变体数量上略有不同，但核心都是让同一意图以多种表达参与搜索。
- 查询类型包括：
  - `lex`：BM25 关键词。
  - `vec`：语义向量查询。
  - `hyde`：生成假设性文档片段，再进行向量检索。
- 每个查询会同时进入：
  - SQLite FTS5 的 BM25 全文检索。
  - 向量语义检索。

###### RRF 结果融合

QMD 使用倒数排名融合（RRF）：

```text
score = Σ(1 / (k + rank + 1))
```

其中`k = 60`。

额外规则：

- 某个结果若在任一列表中排名第**1**，加**0.05**。
- 排名第**2～3**，加**0.02**。
- 融合后保留前**30**个候选进入重排序。

这些额外奖励用于防止查询扩展稀释原始关键词的精确匹配。

###### LLM 重排序与位置感知混合

QMD 使用本地`qwen3-reranker`判断文档是否相关，并结合概率置信度评分。最终分数会根据初始排名采用不同权重：

| RRF 初始排名 | 检索分数权重 | LLM 重排权重 |
|---|---:|---:|
| 第 1～3 名 | 75% | 25% |
| 第 4～10 名 | 60% | 40% |
| 第 11 名以后 | 40% | 60% |

这样做的目的：

- 前几名通常是精确匹配，应优先保留传统检索结果。
- 排名较后的文档更需要 LLM 判断语义相关性。
- 避免重排模型破坏原本非常可靠的关键词匹配。

---

##### 9. 各类分数与结果解释

###### 后端分数转换

| 检索方式 | 原始分数 | 转换方式 | 大致范围 |
|---|---|---|---|
| BM25 / SQLite FTS5 | BM25 分数 | `Math.abs (score)` | 0～约 25+ |
| 向量检索 | 余弦距离 | `1 / (1 + distance)` | 0～1 |
| LLM 重排 | 0～10 评分 | `score / 10` | 0～1 |

###### 最终相关度含义

| 最终分数 | 含义 |
|---|---|
| 0.8～1.0 | 高度相关 |
| 0.5～0.8 | 中度相关 |
| 0.2～0.5 | 有一定相关性 |
| 0～0.2 | 相关性较低 |

##### 1. 为什么这个实例适合 QMD

传统关键词搜索容易漏掉表达不同但含义相近的文档，例如：

- 运维手册写的是`JWKS key rotation`
- 事故复盘写的是 “签名公钥缓存没有及时刷新”
- 会议纪要写的是 “认证服务更换了新的`kid`”
- 用户搜索的是 “密钥轮换导致的偶发 401”

QMD 可以组合使用：

| 能力 | 适合解决的问题 |
|---|---|
| BM25 全文搜索 | 精确查找`401`、`JWKS`、`kid`、事故编号 |
| 向量语义搜索 | 查找 “含义相同但用词不同” 的内容 |
| RRF 融合 | 合并关键词与向量搜索结果 |
| LLM 重排 | 将最符合排障意图的文档排到前面 |
| Context 上下文 | 告诉模型某个目录是什么、是否权威、适用于什么场景 |
| MCP | 让 Claude Code 等 Agent 直接检索知识库 |

所有索引和检索模型均可在本地运行。

##### 3. 先把 Markdown 写成 “可检索” 的形式

QMD 能提高搜索质量，但不能完全弥补文档本身结构混乱的问题。

以下是示例运维手册。

```markdown
# 支付 API 在密钥轮换后出现 401

## 适用范围

- 服务：payment-api
- 环境：production、staging
- 认证方式：JWT + JWKS
- 常见错误：HTTP 401、unknown kid、signature verification failed

## 现象

认证服务轮换签名密钥后，部分 payment-api 实例间歇性返回 401。
重新部署实例后错误暂时消失。

## 快速判断

1. 从失败请求的 JWT Header 中读取`kid`。
2. 查询认证服务当前的 JWKS。
3. 检查当前 JWKS 中是否存在该`kid`。
4. 检查 payment-api 日志中是否出现：
   - `unknown kid`
   - `JWKS cache stale`
   - `signature verification failed`

## 根因

旧版本 payment-api 的 JWKS 缓存 TTL 为 15 分钟。
当认证服务开始使用新密钥后，未刷新缓存的实例无法识别新的`kid`。

## 处置步骤

1. 主动刷新 JWKS 缓存。
2. 如果刷新失败，滚动重启 payment-api。
3. 检查认证服务是否同时保留旧公钥。
4. 确认 401 错误率恢复到基线。

## 长期修复

- 收到未知`kid`时立即刷新一次 JWKS。
- 密钥轮换期间同时保留新旧公钥。
- 为`unknown kid`增加独立指标和告警。

## 相关资料

- 事故：INC-2025-0218
- 文档：认证服务 JWT 校验流程
- 会议：2025-02-10 认证系统迁移评审
```

###### 文档编写最佳实践

1. **标题同时包含业务对象和故障现象**
   - 推荐：`支付 API 在密钥轮换后出现 401`
   - 不推荐：`认证问题记录`

2. **保留准确的技术关键词**
   - `JWT`
   - `JWKS`
   - `kid`
   - `HTTP 401`
   - `signature verification failed`

3. **同时补充自然语言描述**
   - 例如同时写 “签名密钥轮换” 和 “key rotation”。

4. **使用稳定标识**
   - 事故编号：`INC-2025-0218`
   - 服务名称：`payment-api`
   - 错误码：`PAY-AUTH-401`

5. **使用固定章节**
   - 现象
   - 快速判断
   - 根因
   - 临时处置
   - 长期修复
   - 相关资料

这样可以同时提高关键词检索、语义搜索和最终重排的质量。

##### 6. 为 Collection 和目录添加 Context

Context 是 QMD 很重要的能力。它不仅描述 Collection，还可以按目录形成树状上下文，并随搜索结果一起返回。

```bash
qmd context add qmd://docs \
  "当前有效的产品与架构文档；适合确认系统设计和认证流程。"

qmd context add qmd://docs/auth \
  "认证服务文档，覆盖 JWT 校验、JWKS、公钥缓存和密钥轮换。"

qmd context add qmd://ops \
  "生产运维手册；当问题需要立即处置时，应优先参考这里的步骤。"

qmd context add qmd://ops/payments \
  "支付服务生产排障手册；包含告警判断、止损步骤、恢复验证和升级路径。"

qmd context add qmd://meetings \
  "会议纪要和历史讨论；主要用于理解决策背景，不应替代当前运维手册。"

qmd context add qmd://incidents \
  "已发生事故的复盘记录；用于匹配相似症状、历史根因和修复措施。"
```

###### Context 最佳实践

Context 应回答以下问题：

- 这里保存的是什么资料？
- 它适用于什么任务？
- 它是否权威？
- 它与其他资料发生冲突时，谁优先？
- 它包含哪些关键主题？

推荐：

```text
生产运维手册；需要立即处置线上故障时优先使用。
```

不推荐：

```text
这里是一些文档。
```

对于本实例，建议明确资料优先级：

```text
ops > docs > incidents > meetings
```

不过，优先级不是简单的绝对排序。例如：

- 查询 “怎么立即恢复服务” 时优先`ops`
- 查询 “历史上是否发生过” 时优先`incidents`
- 查询 “为什么采用这种架构” 时可能优先`docs`和`meetings`

###### 8.1 精确关键词搜索

如果已知错误码或术语：

```bash

或者搜索事故编号：

```bash

适合：

- 事故编号
- API 名称
- 类名和函数名
- 日志原文
- 固定技术术语

---

###### 8.2 语义搜索

如果不知道文档里的准确用词：

```bash
qmd vsearch "支付服务因为认证公钥没有及时刷新而间歇性鉴权失败"
```

即使文档中使用的是：

```text
JWKS cache stale
unknown kid
key rotation
```

向量搜索仍可能找到它。

适合：

- 用户用自然语言描述问题
- 文档与搜索词表达不同
- 需要寻找相似事故
- 不知道准确关键词

---

###### 8.3 混合搜索并进行重排

生产使用时优先使用：

```bash
qmd query "支付接口上线后偶发 401，如何判断是否由 JWT 签名密钥轮换或 JWKS 缓存未刷新引起？"
```

如果要限定范围，可以先搜索最相关的 Collection：

```bash
qmd query \
  "支付接口偶发 401，检查 JWT kid、JWKS 缓存和密钥轮换，并给出恢复步骤" \
  -c ops
```

`query`会组合关键词搜索、向量搜索、RRF 融合与 LLM 重排，通常具有最佳结果质量，但延迟也会高于普通`search`。

##### 9. 推荐的搜索策略

| 查询类型 | 推荐命令 | 原因 |
|---|---|---|
| 查事故编号 | `qmd search` | 精确、快速 |
| 查日志原文 | `qmd search` | BM25 更擅长精确术语 |
| 用自然语言描述故障 | `qmd vsearch` | 不依赖完全相同的措辞 |
| 需要最终高质量答案 | `qmd query` | 混合检索并重排 |
| 高频交互式补全 | `qmd search`或关闭重排 | 更低延迟 |
| Agent 最终检索 | `qmd query` | 结果质量更重要 |

简化为一句话：

> 已知关键词用`search`，只知道含义用`vsearch`，需要最佳质量用`query`。

##### 10. 先搜索，再按需读取正文

不要让 Agent 一开始就读取所有文件。推荐两阶段检索：

1. 搜索并筛选候选文档。
2. 只读取最相关文档的必要行。

先获得结构化结果：

```bash
qmd query \
  "支付 API 401，JWT kid 不存在，JWKS 缓存未刷新" \
  --json \
  -n 5
```

结果中会包含文档路径或类似下面的 URI：

```text
qmd://ops/payments/401-after-key-rotation.md
```

随后读取最相关文档：

```bash
qmd get "ops/payments/401-after-key-rotation.md" --full
```

也可以使用搜索结果中的文档 ID：

```bash
qmd get "#abc123"
```

若只需要部分行，应优先限制范围：

```bash
qmd get "#abc123:20:60"
```

含义是从指定位置读取有限行数，避免将整份长文档全部送入模型。

###### 检索正文最佳实践

- 首轮只取前 5～10 个搜索结果。
- 先看标题、摘要、Context 和分数。
- 只读取最相关的 2～3 份文档。
- 长文档优先按行读取。
- 让最终回答保留文档 URI 和行号，方便人工核验。
- 不要因为某个文档被召回，就假定其中所有内容都相关。

##### 11. Agent 使用的结构化查询

通过 MCP 调用`query`时，可以将精确查询和语义查询组合起来。

本实例可使用：

```json
{
  "searches": [
    {
      "type": "lex",
      "query": "\"unknown kid\"JWKS 401 payment-api"
    },
    {
      "type": "vec",
      "query": "支付服务因为 JWT 签名密钥轮换和公钥缓存未刷新而出现间歇性鉴权失败"
    }
  ],
  "collections": [
    "ops",
    "incidents",
    "docs"
  ],
  "intent": "排查生产环境支付 API 的间歇性 401；优先返回可执行处置步骤，其次返回相似事故和认证原理",
  "limit": 5,
  "minScore": 0.35,
  "candidateLimit": 30,
  "rerank": true
}
```

###### 为什么这样设计

1. **把最强的精确查询放在第一个**
   - QMD 对第一个子查询给予更高权重。
   - `"unknown kid"`是很有辨识度的日志原文。

2. **同时提供语义查询**
   - 用来匹配 “公钥缓存陈旧”“密钥轮换窗口” 等不同表达。

3. **明确填写`intent`**
   - `intent`用于帮助消歧和重排。
   - 它本身不会单独执行搜索。

4. **限定 Collections**
   - 先搜索`ops`、`incidents`和`docs`。
   - 不把噪声较多的会议纪要放入首轮结果。

5. **保留重排**
   - 故障排查需要结果质量，适合设置`"rerank": true`。

###### MCP 参数注意事项

`collections`必须是数组：

```json
{
  "collections": ["ops", "incidents"]
}
```

不要写成：

```json
{
  "collection": "ops"
}
```

QMD 的未知参数可能被静默忽略。如果参数名写错，查询可能没有真正限定范围，因此需要特别检查：

- `searches`
- `collections`
- `intent`
- `limit`
- `minScore`
- `candidateLimit`
- `rerank`

##### 13. 多个 Agent 共用长驻 MCP 服务

如果每个客户端都以 stdio 方式启动 QMD，可能重复加载模型。多个 Agent 或频繁请求时，可以启动 HTTP 服务：

```bash

```

默认地址：

```text
http://localhost:8181/mcp
```

健康检查：

```bash

```

查看状态：

```bash
qmd status
```

停止服务：

```bash
qmd mcp stop
```

###### HTTP 部署最佳实践

默认只监听本机：

```bash
qmd mcp --http
```

仅当服务运行在容器中，并且健康探针必须通过非回环地址访问时，才考虑：

```bash
qmd mcp --http --host 0.0.0.0
```

不要在没有认证、网络隔离或防火墙的情况下，将 QMD 直接暴露到公网。

长驻 HTTP 服务的主要优点是：

- 模型可以跨请求保留在内存或显存中。
- 避免每个 Agent 重复加载模型。
- 降低连续查询的启动延迟。
- 多个 MCP 客户端可以共用同一索引。

##### 14. 搜索分数不要机械使用

QMD 给出的分数可以大致理解为：

| 分数 | 含义 |
|---:|---|
| `0.8～1.0` | 高度相关 |
| `0.5～0.8` | 中度相关 |
| `0.2～0.5` | 有一定相关性 |
| `0.0～0.2` | 相关性较低 |

本实例可以从以下阈值开始：

```bash
qmd query \
  "支付 API 401 与 JWKS 密钥轮换" \
  --all \
  --files \
  --min-score 0.35
```

但分数只能作为排序和过滤依据，不能当作事实置信度。

例如：

- `0.9`表示 “文档与查询高度相关”
- 不表示 “文档内容有 90% 的概率正确”
- 不表示 “文档一定是当前版本”
- 不表示 “文档中的处置步骤一定适用于生产环境”

建议使用一组固定问题进行校准：

| 测试问题 | 预期首位结果 |
|---|---|
| `unknown kid JWKS 401` | 401 运维手册 |
| `INC-2025-0218` | 对应事故复盘 |
| `为什么密钥轮换会造成间歇性鉴权失败` | 运维手册或认证设计文档 |
| `认证迁移为什么保留旧公钥` | 架构文档或会议纪要 |
| `如何立即恢复 payment-api` | 运维手册 |

如果预期文档经常排不到前三，应优先检查：

1. 文档标题是否清晰。
2. 文档是否包含准确术语。
3. Context 是否说明用途和权威性。
4. 嵌入是否已更新。
5. Collection 是否被错误过滤。
6. 查询是否过短或过于宽泛。

##### 15. SDK 自动化示例

如果要把 QMD 嵌入内部 Node.js 工具，可以显式创建独立索引。

安装：

```bash
npm install @tobilu/qmd
```

示例：

```typescript
import { createStore } from "@tobilu/qmd";

const store = await createStore ({
  dbPath: "./data/engineering-knowledge.sqlite",
  config: {
    collections: {
      docs: {
        path: "/Users/example/knowledge/product-docs",
        pattern: "**/*.md"
      },
      ops: {
        path: "/Users/example/knowledge/runbooks",
        pattern: "**/*.md"
      },
      meetings: {
        path: "/Users/example/knowledge/meetings",
        pattern: "**/*.md"
      },
      incidents: {
        path: "/Users/example/knowledge/incidents",
        pattern: "**/*.md"
      }
    }
  }
});

try {
  await store.setGlobalContext (
    "内部工程知识库。故障处置优先参考 ops，历史根因参考 incidents，系统原理参考 docs。"
  );

  await store.addContext (
    "ops",
    "/payments",
    "支付服务生产运维手册，包含可执行排障和恢复步骤。"
  );

  const updateResult = await store.update ({
    onProgress: ({ collection, file, current, total }) => {
      console.log (`[${collection}] ${current}/${total} ${file}`);
    }
  });

  console.log ("Index update:", updateResult);

  await store.embed ({
    force: false,
    chunkStrategy: "auto",
    onProgress: ({ collection, current, total }) => {
      console.log (`[${collection}] embedding ${current}/${total}`);
    }
  });

  const results = await store.search ({
    queries: [
      {
        type: "lex",
        query: "\"unknown kid\"JWKS 401 payment-api"
      },
      {
        type: "vec",
        query: "支付服务因签名密钥轮换和公钥缓存陈旧而间歇性鉴权失败"
      }
    ],
    collections: ["ops", "incidents", "docs"],
    intent: "生产故障排查；优先可执行处置步骤",
    limit: 5,
    minScore: 0.35,
    explain: true
  });

  for (const result of results) {
    console.log ({
      title: result.title,
      score: result.score,
      path: result.displayPath,
      context: result.context,
      snippet: result.snippet
    });
  }
} finally {
  await store.close ();
}
```

###### SDK 最佳实践

- 始终显式设置`dbPath`。
- 将索引数据库放在应用自己的数据目录中。
- 使用`try/finally`确保执行`store.close ()`。
- 正常更新时使用`force: false`。
- 为更新和嵌入增加进度日志。
- 应用退出时关闭模型和数据库连接。
- 不要让多个应用实例无协调地同时重建同一个索引。

##### 16. 安全与隐私注意事项

“本地搜索” 不等于所有后续数据流都必然留在本地。

例如：

1. QMD 在本地建立索引并召回文档。
2. Claude Code 通过 MCP 获取召回内容。
3. Claude Code 可能将这些内容发送给远程模型。

因此需要分别考虑：

- 索引是否本地保存
- MCP 是否只监听本机
- 使用的 Agent 是否连接远程模型
- 被召回内容是否含有密钥、令牌或个人信息
- 日志和事故复盘是否允许被模型处理

不要索引：

```text
.env
private-key.pem
credentials.md
production-secrets.md
```

建议在知识库源目录中预先排除：

- API Key
- Access Token
- 私钥
- 数据库密码
- 客户隐私数据
- 未脱敏的生产日志
- 不应跨团队访问的文档

##### 结论

在这个 “支付接口偶发 401” 实例中，QMD 的最佳用法不是简单地把所有 Markdown 文件放进一个目录后直接搜索，而是：

1. **按文档性质拆分 Collection**
2. **通过树状 Context 描述用途与权威性**
3. **把 Markdown 写成结构化、可检索的知识**
4. **同时使用精确关键词和语义查询**
5. **使用`query`完成融合与重排**
6. **让 Agent 先检索、再按行读取、最后带来源回答**
7. **持续更新嵌入，并建立安全边界**

这样才能把 QMD 从一个本地搜索命令，真正升级为可靠的工程知识检索基础设施。

## 口播总结（2）

### 2026-08-03 00:31:14

#### QMD：在本地搜索你的笔记、文档和知识库

QMD 是一款完全在本地运行的轻量级命令行搜索引擎。它能统一检索 Markdown 笔记、会议记录、工作文档和知识库，并通过关键词搜索、语义搜索和大模型重排，提高查找结果的准确性。

听完这份介绍，你可以了解 QMD 的核心能力、基本用法、与 AI 助手的集成方式，以及它背后的混合搜索架构。

##### 首先，QMD 解决什么问题

核心结论是，QMD 想把分散在本地文件中的知识，变成一个可被人和 AI 助手共同使用的搜索库。

简单来说，你可以把个人笔记、会议转录、项目文档和内部知识库分别加入 QMD。之后，无论你记得的是准确关键词，还是只记得大概意思，都可以在同一个地方搜索。

QMD 的特点是全程在本地运行。它通过 `node-llama-cpp` 加载本地模型，不需要把文档发送到外部服务。这种方式尤其适合隐私资料，也适合需要自动查找资料的 AI 智能体工作流。

在搜索技术上，QMD 同时使用三种能力。第一种是 BM25 全文搜索，也就是按照关键词出现的位置和重要程度进行匹配。第二种是向量语义搜索，它不只看字面是否相同，还会判断两段文字表达的意思是否接近。第三种是大语言模型重排，也就是让本地模型再次检查候选结果，把更相关的文档排到前面。

##### 接下来，建立自己的本地知识库

核心结论是，使用 QMD 的基本流程并不复杂：安装工具，添加文档集合，补充上下文，生成向量索引，然后开始搜索。

QMD 可以通过 Node.js 的 npm，或者 Bun 的包管理工具进行全局安装。系统也支持通过 npx 或 bunx 直接运行，不一定要永久安装。

安装后，首先要建立“集合”。集合可以理解为一组需要统一管理的文件。例如，你可以把个人笔记目录命名为 notes，把会议记录目录命名为 meetings，再把工作文档目录命名为 docs。

更重要的是，QMD 支持为集合或集合中的路径添加“上下文”。这里的上下文，是一段描述文件用途和背景的文字。例如，可以说明 notes 是“个人笔记和想法”，meetings 是“会议转录和记录”，docs 是“工作文档”。

这些上下文可以形成树状结构。当某个子文档被搜索到时，相关的上层说明也会一起返回。这样，AI 助手不只看到零散片段，还能理解这份文档属于什么项目、有什么用途。项目作者特别强调，这是 QMD 帮助大模型正确选择文档的关键能力。

完成集合配置后，需要运行嵌入操作。所谓“嵌入”，就是把文档内容转换成可以比较语义相似度的数字向量。生成这些向量之后，QMD 才能进行语义搜索。

##### 三种搜索方式各有用途

核心结论是，QMD 提供关键词搜索、语义搜索和混合搜索三种主要模式，可以在速度和准确性之间做选择。

首先，`qmd search` 是快速关键词搜索。它适合查找明确的名称、接口、错误代码或固定短语。例如，搜索“project timeline”，可以快速找到包含项目时间线相关词语的文件。

接下来，`qmd vsearch` 是向量语义搜索。即使文档没有出现完全相同的词，只要表达的含义接近，也有机会被找到。例如，搜索“如何部署”，可能找到一份标题为“上线流程”的文档。

质量最高的方式是 `qmd query`。它会把全文搜索和语义搜索结合起来，再让本地大模型重新排序。它适合“季度规划流程”这类含义较复杂、需要综合判断的问题。不过，因为多了一轮模型处理，速度通常会比纯关键词搜索慢。

搜索也可以限制在某个集合中。例如，只在 notes 中查找 API 相关内容。用户还可以设置最低相关度，只返回超过指定分数的结果。

找到结果以后，`qmd get` 可以按照文件路径或文档编号读取具体文档。文档编号类似井号加一段短字符。`multi-get` 则可以按照通配符或多个编号批量读取文件，例如一次取得某个月份的全部日记。

如果搜索结果要交给 AI 助手处理，还可以使用 JSON 格式获得结构化数据，或者只输出符合条件的文件列表。需要完整内容时，也可以明确要求返回整份文档。

##### 更重要的是，QMD 可以直接接入 AI 助手

核心结论是，QMD 不只是给人使用的命令行工具，还提供 MCP 服务，让 AI 客户端能够直接搜索和读取本地知识。

MCP 的全称是“模型上下文协议”。可以把它理解为一套标准接口，让 Claude 等 AI 客户端知道 QMD 提供了哪些工具，以及应该怎样调用。

QMD 的 MCP 服务暴露四类主要工具。

第一类是 `query`，负责搜索。它支持不同类型的子查询。`lex` 代表关键词检索，`vec` 代表向量语义检索，`HyDE` 则是通过假设性文档辅助语义搜索。多组结果会经过融合和重排。

第二类是 `get`，用于按照路径或文档编号读取单份文档。如果路径不准确，它还能提供相近文件的建议。

第三类是 `multi_get`，用于按照通配符、多个路径或多个文档编号批量读取。

第四类是 `status`，用于检查索引健康状况和集合信息。

Claude Desktop 可以通过配置文件启动 QMD 的 MCP 服务。Claude Code 则可以安装官方插件，也可以手动配置 MCP。

这里有两个容易忽略的参数细节。第一，搜索集合必须使用数组形式传入；如果误用单个集合字段，系统可能会静默忽略。第二，未知参数也不会直接报错，而是会被忽略。因此，如果搜索结果没有按预期缩小范围，需要先检查参数名称和格式。

##### HTTP 模式适合长期共享服务

核心结论是，默认的 MCP 服务适合单个客户端临时使用，而 HTTP 模式更适合多个请求或长期运行。

默认情况下，QMD 使用标准输入输出，也就是 stdio 模式。每个客户端会把它作为子进程启动。这样配置简单，但重复启动时，可能反复加载模型。

如果希望模型长期驻留，可以启动 HTTP 服务。默认地址是本机的 8181 端口，也可以指定其他端口。服务既能在前台运行，也能作为后台守护进程运行，并通过状态命令检查进程是否仍然存在。

HTTP 服务提供两个端点。一个用于接收 MCP 请求，另一个用于健康检查，并返回服务已运行的时间。默认情况下，服务只绑定本机地址。需要在容器中接受非回环地址的健康探测时，可以把主机地址设置为所有网络接口。

HTTP 模式的实际好处是，大语言模型可以持续保留在显存中，不必每次请求都重新加载。用于嵌入和重排的运行上下文，如果空闲超过五分钟会被释放。下次请求时会自动重建，额外延迟大约一秒，但模型本身仍然保持加载状态。

##### 开发者也能把 QMD 当作程序库使用

核心结论是，除了命令行和 MCP，QMD 还提供 Node.js 与 Bun 软件开发工具包，可以直接嵌入应用。

开发者安装软件包后，可以调用 `createStore` 创建一个搜索存储。这里的 store，可以理解为统一管理数据库、集合、索引、搜索和本地模型的对象。

创建存储有三种方式。第一种是在代码中直接写集合配置。第二种是读取 YAML 配置文件。第三种是只提供已有数据库的路径，重新打开之前配置过的存储。

统一的 `search` 方法可以直接接收自然语言问题。系统会自动扩展查询，再完成关键词检索、向量检索和模型重排。开发者也可以自己提供结构化子查询，精确控制关键词表达式和语义问题。若更看重速度，还可以关闭重排。

软件开发工具包同时提供文档读取、批量读取、集合增删和改名、上下文管理、文件重新索引以及向量生成等能力。索引过程中还可以接收进度回调，了解当前处理到哪个集合和文件。

QMD 也支持为代码集合指定文件模式和忽略规则。例如，只收录 TypeScript 文件，并排除依赖目录和测试文件。生成嵌入时，还可以选择普通规则切分，或者针对代码使用抽象语法树进行自动切分。

需要注意的是，软件开发工具包要求明确提供数据库路径，不会自行假定默认位置。这样做可以避免它在嵌入其他应用时产生意外文件或副作用。使用结束后，还应主动关闭 store，以释放数据库连接和本地模型资源。

##### QMD 的混合搜索是怎样工作的

核心结论是，QMD 不会只相信某一种搜索方法，而是让关键词检索、语义检索和大模型判断互相补充。

首先，系统会处理用户的原始问题，并生成替代查询表达。原始查询会获得两倍权重，因为它最能代表用户真正输入的内容。

接下来，每个查询都会同时进入两套检索系统。一套是基于 SQLite FTS5 的 BM25 全文搜索，擅长找到准确词语和固定表达。另一套是向量搜索，擅长发现语义相近、但用词不同的内容。

然后，QMD 使用 RRF，也就是“倒数排名融合”，来合并多份结果。它更关注一份文档在不同结果列表中的排名，而不是直接比较不同搜索系统产生的原始分数。融合公式中的常数是 60，用来降低不同排名之间的剧烈波动。

为了保护特别准确的匹配，任何列表中排名第一的文档会获得零点零五的额外奖励，排名第二或第三的文档会获得零点零二的奖励。这样可以避免查询扩展后的结果淹没原始问题中的精确匹配。

融合完成后，系统保留排名最靠前的 30 个候选结果，交给本地的大模型重排器。重排器会判断文档是否真正相关，并结合模型输出概率形成置信度。

最后，QMD 不会让重排模型完全推翻前面的检索结果，而是根据原始排名动态混合两种分数。

排名第一到第三的结果，检索分数占百分之七十五，模型重排占百分之二十五。这样能尽量保住高置信度的精确匹配。

排名第四到第十的结果，检索分数占百分之六十，重排占百分之四十。

排名第十一及以后的结果，则让模型发挥更大作用。检索分数占百分之四十，重排占百分之六十。

这种设计是为了解决两个问题。只做排名融合，可能会让精确匹配被多个扩展查询稀释；只依赖大模型重排，又可能破坏原本非常可靠的搜索结果。按排名分配权重，是在两者之间取得平衡。

##### 如何理解相关度分数

核心结论是，QMD 会把不同搜索后端的结果转换为可比较的分数，最终相关度位于零到一之间。

BM25 的原始得分可能从零延伸到二十五以上。向量搜索使用余弦距离，再把距离转换成零到一之间的相似度。大模型重排器内部使用零到十分的评价，再除以十，转换为统一范围。

在最终结果中，零点八到一点零代表高度相关。零点五到零点八代表中等相关。零点二到零点五表示有一定关系。低于零点二，通常说明相关性较弱。

这些区间可以帮助用户设置最低分数。例如，交给 AI 自动处理时，可以适当提高门槛，减少无关文件；如果是在探索资料，则可以降低门槛，保留更多可能有用的结果。

##### 最后，运行环境与使用前提

核心结论是，QMD 的搜索和模型推理都在本机完成，因此需要较新的运行环境和本地模型支持。

系统要求 Node.js 版本不低于 22，或者 Bun 版本不低于 1.0。macOS 用户需要安装支持扩展功能的 Homebrew SQLite。

QMD 使用三个本地 GGUF 模型。GGUF 是一种适合在个人电脑上运行大模型的文件格式，通常用于量化模型，可以降低内存和显存需求。原始材料没有进一步列出这三个模型的具体名称，但它们分别支撑查询处理、向量生成和结果重排等本地能力。

##### 最值得记住的五点

最后回顾一下。

第一，QMD 是一个完全在本地运行的文档搜索引擎，适合统一管理笔记、会议记录、文档和知识库。

第二，它同时使用 BM25 关键词搜索、向量语义搜索和大模型重排。关键词搜索速度快，语义搜索能理解意思，混合查询的整体质量最高。

第三，上下文是 QMD 的关键设计。为集合和路径添加背景说明，可以帮助 AI 更准确地理解和选择文档。

第五，它的排序策略会保护精确匹配，同时让大模型重点改善排名较后的候选结果，从而在检索稳定性和语义判断之间取得平衡。

QMD 是一个完全在本地运行的个人文档搜索引擎。它要解决的问题很直接：当笔记、会议记录和工作文档越来越多时，怎样既能按关键词精确查找，又能用自然语言找到意思相关的内容，还能把最有用的结果排在前面。

QMD 的核心思路，是把三种搜索方法串成一条流水线。

第一种是 BM25 全文搜索。可以把它理解为更成熟的关键词匹配。它擅长寻找准确出现的术语、文件名、产品名和错误信息。比如搜索“项目时间线”，包含这些字词的文档通常会得到较高排名。

第二种是向量语义搜索。它不只看字面是否一致，还比较意思是否接近。比如你搜索“怎样部署系统”，即使文档写的是“生产环境发布流程”，也可能被找到。

第三种是大语言模型重排序。前两种方法先找出候选文档，再由本地模型判断哪些结果真正符合问题，并重新调整顺序。关键词搜索负责精确，语义搜索负责召回，大模型负责最后筛选。QMD 把这三部分都放在本机运行，使用 node-llama-cpp 和 GGUF 格式的本地模型，不需要把私人文档交给外部搜索服务。

实际使用时，先把不同目录注册成“集合”。例如，可以把个人笔记、会议记录和工作文档分别设成三个集合。然后运行索引和嵌入生成。完成后，就可以跨集合搜索，也可以把范围限制在某一个集合。

QMD 提供三种主要搜索方式。search 是快速关键词搜索；vsearch 是语义搜索；query 则同时使用关键词、向量和模型重排序，速度相对慢一些，但质量最好。找到结果后，可以按文件路径读取文档，也可以使用搜索结果中的文档编号。它还支持按通配模式批量取得文件，例如一次读取某个月份的全部日志。

QMD 有一个很值得注意的设计，叫作“上下文”。这里的上下文，是附加在集合或目录上的描述信息。比如，可以告诉系统，notes 集合存放“个人笔记和想法”，meetings 集合存放“会议记录”，docs 集合存放“工作文档”。还可以给某个子目录增加更具体的说明，例如标注某个目录是“REST 接口参考资料”。

这些描述会随着匹配结果一起返回。对普通搜索来说，它们可以帮助判断相关性。对人工智能代理来说，价值更大。因为代理看到的不只是一个文件名和一段文本，还知道这份材料属于什么领域、处在什么目录语境中。这样，代理在多个相似结果之间做选择时，更不容易选错。

理解了基本功能，再看 QMD 如何提高混合搜索的可靠性。

用户输入一个问题后，QMD 会让本地模型扩展查询，生成意思相近的替代表达。原始问题和扩展问题都会分别进入全文索引与向量索引。原始问题的权重更高，是扩展查询的两倍。这样做是为了避免模型改写之后偏离用户真正想找的内容。

多个搜索结果随后通过一种叫“倒数排名融合”的方法合并。简单说，一份文档如果在不同结果列表中都排得靠前，综合排名就会上升。任何列表中的第一名还会获得额外加分，第二名和第三名也有较小加分。系统保留排名最高的三十个候选结果，再交给本地大模型判断相关性。

不过，QMD 不会让重排序模型完全推翻前面的检索结果。对于原始检索排在前三名的文档，最终得分更依赖关键词和向量检索，检索部分占百分之七十五。排在第四到第十名时，检索部分占百分之六十。到了更后面的结果，系统才更信任大模型，让重排序占百分之六十。

这种分段混合有一个明确目的：精确匹配通常已经很可靠，不应该轻易被模型降到后面；而排名较低的候选结果更模糊，更适合让模型根据语义重新判断。换句话说，QMD 既利用大模型，又尽量避免大模型破坏明确的关键词命中。

除了命令行，QMD 还提供 MCP 服务。MCP，也就是模型上下文协议，是让人工智能客户端调用外部工具的一种标准接口。接入之后，Claude Desktop、Claude Code 或其他兼容客户端，可以直接调用 QMD 搜索、读取单个文档、批量读取文档，并检查索引状态。

MCP 服务默认作为客户端的子进程运行。如果不想让每个客户端重复启动和加载模型，也可以开启长期运行的 HTTP 服务。这样，本地模型会在显存中保持加载状态。嵌入和重排序的运行上下文闲置五分钟后会释放，但模型本身不会卸载。下一次请求重建上下文，大约会增加一秒延迟。这种模式更适合多个客户端共享同一套搜索服务。

开发者还可以把 QMD 当作 Node.js 或 Bun 的程序库使用。应用可以自行创建索引数据库、配置集合、更新文件、生成向量、执行混合搜索，并按路径或文档编号读取内容。数据库路径必须明确指定，不会自动采用默认位置。这个限制可以减少嵌入其他应用时产生意外文件或副作用。

使用上有两个细节需要留意。通过 MCP 查询时，集合过滤参数必须使用数组形式；如果误传成单个集合名称，参数可能被静默忽略。未知参数也不会报错，而是直接忽略。所以当搜索结果没有按预期限制范围时，应该先检查参数名称和数据形式。

运行环境方面，QMD 要求 Node.js 二十二或更高版本，或者 Bun 一点零以上版本。在 macOS 上，还需要通过 Homebrew 安装支持扩展的 SQLite。

最值得记住的是，QMD 不是单纯给文件加一个搜索框。它把精确关键词、语义理解和本地模型判断组合起来，同时用目录上下文帮助人工智能理解文档身份。它的重点也不只是搜索质量，而是在不把资料上传到外部服务的前提下，让个人知识库能够被人和人工智能代理共同使用。

#### QMD 的启示：Agent 知识库的难点不是“存进去”，而是可靠地找回来

QMD 表面上是一个本地 Markdown 搜索工具，真正值得关注的却是它对 Agent 检索问题的拆解：**关键词、语义相似和 LLM 判断各有盲区，可靠结果来自分阶段组合，而不是把所有文档塞进向量库。**

##### 混合检索的价值，在于让不同方法互相纠错

QMD 先用原始问题和扩展问题，分别执行 BM25 全文检索与向量检索，再通过 RRF 合并排名，最后交给本地 LLM 重排。这个流程并不新奇，设计上的分寸更有价值。

纯向量检索擅长寻找“意思相近”的内容，却可能漏掉 API 名称、错误码、人名等精确匹配；查询扩展能提高召回率，也会引入偏题结果；LLM 重排理解力更强，但可能推翻原本非常确定的命中。QMD 因而给原始查询双倍权重，为各检索列表的头部结果加分，并按初始排名动态调整重排权重：前三名更多相信检索，靠后结果更多相信 LLM。

这体现了一条可迁移的原则：**检索系统不应让能力更强但不稳定的模型，无条件覆盖便宜且确定的信号。** 在企业搜索、客服知识库和代码检索中，模型更适合处理模糊区域，而不是重新裁决所有结果。遗憾的是，页面主要给出了方案，没有展示基准数据，因此这些权重目前更像值得验证的工程假设，而非已被证明的最优解。

##### “上下文”可能比增加模型能力更重要

QMD 特别强调给集合和目录添加层级化描述，例如说明某目录是会议记录还是 API 文档。这些元数据会随命中文档返回，帮助 Agent 判断结果属于什么范围、该如何使用。

这解决了常被低估的问题：一段文字即使语义相关，也未必在当前任务中有效。同一句“发布流程”，可能来自个人笔记、过期会议或正式规范。仅靠文本切片，很容易丢失文档来源、用途和权威性。QMD 的 context 本质上是在检索结果旁补回“组织语境”。

对于产品设计，这比盲目扩大上下文窗口更有启发：**高质量 RAG 不只需要切分和 embedding，还需要把权限、时效、文档类型、责任人和权威等级变成可检索、可返回的信号。** QMD 目前只提供人工维护的路径描述，但已经指出了正确方向。

##### 本地优先正在成为 Agent 基础设施的一种现实形态

它同时提供 CLI、MCP、HTTP 常驻服务和 Node/Bun SDK，并让模型常驻显存，说明目标不是做一个搜索界面，而是成为 Agent 可调用的本地记忆层。它适合隐私敏感、文件频繁变化、云端上传成本高的个人或小团队场景，也降低了把检索嵌入自动化流程的门槛。

但“全本地”并不自动意味着成熟：本地模型质量、首次索引与重排延迟、硬件要求、Markdown 覆盖范围都可能限制采用；未知 MCP 参数会被静默忽略，更可能造成“看似按范围查询，实际没有生效”的隐蔽错误。

因此，QMD 最值得保留的不是又一个本地搜索产品，而是一套清晰判断：**Agent 记忆的产品壁垒，可能不在模型或向量库本身，而在语境建模、检索融合、可观测性，以及对失败方式的精细控制。**
