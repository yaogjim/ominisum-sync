**知识要点**

- 在Ampere上，注意力后端能否直接读取FP8 KV会同时影响上下文容量和解码吞吐；后端路由不是单纯的配置选择。

#### The shape

Two weight classes — the **speed** series (int4) and the **fidelity** series (fp8) — each now in three drafter depths:

base (built-in MTP) **`super`** (DFlash2 + fp8 KV / FlashInfer) **`ultra`** (DFlash2 + fp8 KV / FlashAttn)

**speed** (int4) `fast` **`superfast`** **`ultrafast`**

**fidelity** (fp8) `max` **`supermax`** **`ultramax`**

- **`super*`** swaps the built-in MTP head for an **external DFlash2 block-drafter** while keeping the base tier's fp8 KV. You keep the full context envelope; you gain code throughput; and because the drafter is external, it structurally sidesteps the built-in-MTP acceptance-collapse class entirely.
- **`ultra*`** runs that same drafter on **FlashAttention**, the fastest decode path on Ampere. It used to require bf16 KV, which cost context. Since [feat(qwen38): use prebuilt FlashAttention FP8 KV in ultramax #1274](https://github.com/noonghunna/club-3090/pull/1274) it runs **fp8 KV on FlashAttention**, so on two cards it keeps the full envelope AND the fast path. On 4+ cards `ultra*` stays on bf16 KV, which already reaches 262K there (see below). fit 262K on two cards).

One drafter serves all six DFlash2 slugs. It's keyed to the base architecture, not the weight quant, so the *same* [`syvai/Qwen3.8-27B-DFlash2-W4A16`](https://huggingface.co/syvai/Qwen3.8-27B-DFlash2-W4A16) drives both the int4 and the fp8 targets.

#### Where the speed comes from — and why ultra no longer trades context

> **This section described a hardware wall that has since been removed.** It is kept  
> because the mechanism still explains the tier names, and because the wall was real  
> until 2026-09-14. What changed is at the end of the section.

One finding drives the whole hierarchy, and it's a hardware wall worth stating plainly.

**On Ampere (sm\_86), stock FlashAttention and fp8 KV cache *were* mutually exclusive** — a real kernel limit, not a config we forgot to flip. (Past tense as of 2026-09-14: a community plugin now bridges it. The original reasoning follows, because it still explains the tier names.) vLLM's `FLASH_ATTN` backend defers a quantized KV dtype to a capability check that requires FlashAttention **3** (Hopper) or **4** (Blackwell). Our 3090s run FA **2**, which has no fp8-KV read path, so the moment you set fp8 KV, vLLM routes attention to **FlashInfer** instead.

That splits the DFlash2 drafter (whose block attention wants FlashAttention) two ways:

- **`super*` keeps fp8 KV** → runs on FlashInfer → **keeps the full 262K envelope**, at a decode cost (\~40% vs the FlashAttn path).
- **`ultra*` keeps FlashAttention** → *used to* require **bf16 KV** → **fastest decode**, but bf16 KV is 2× the size, so context dropped.

##### ⭐ What changed on 2026-09-14

[@AntonProkopyev](https://github.com/AntonProkopyev) built an FA2 extension that registers fp8 KV support **through the  
FLASH\_ATTN API** on sm\_86, shipped as a digest-pinned prebuilt kernel image  
([#1274](https://github.com/noonghunna/club-3090/pull/1274)). Nothing compiles on  
your rig. Both dual `ultra` slugs now run **fp8 KV on FlashAttention**, so the  
either/or is gone on two cards:

ceiling narrative code

`dual-superfast` — FlashInfer 262K 82 141

**`dual-ultrafast` — FlashAttn** **262K** **123** **220**

`dual-supermax` — FlashInfer 147K 70 144

**`dual-ultramax` — FlashAttn** **262K** **94** **170**

Measured on 2× RTX 3090, `bench.sh` 3 warm + 5 measured. The `ultrafast` / `superfast`  
pair was run at a **matched** ceiling so the attention backend is the only variable;  
the fidelity pair ran at its shipped defaults, where the ceiling gap is itself part  
of the result.

**On two cards, `ultra` now beats `super` on both axes** — same or more context, and  
30–56% more decode. The FlashInfer path costs more than the \~40% this post  
originally estimated. What that means for the `super` tier on duals is a separate  
question and not settled here.

Two caveats worth stating: the `super` arms are single boots (a 50% gap cannot be  
the \~1% boot-to-boot spread we measure, but don't quote the decimals), and  
`supermax` 's code arm produced erratic token counts, so its 144 is the softest  
number in the table.

So the original hierarchy wasn't arbitrary — it was the two sides of one Ampere constraint. `super` = "all the context, collapse-immune, faster than MTP." `ultra` = "maximum decode, shorter context."

##### Why the fidelity duals cap lower

`supermax` (147K) still caps below its int4 cousin. **`ultramax` no longer does** — it reached 64K only because bf16 KV was forced on it, and at fp8 it now runs the full 262K. The FP8 weights are \~29 GiB, and the external DFlash2 drafter costs \~2.6 GiB of KV pool that the built-in MTP head doesn't. On two 24 GB cards that leaves little room — bf16 KV especially. **The `multi4` / `multi8` variants recover the full 262K** once the weights split across more cards.

#### For 4+ GPU rigs — where the fidelity tiers stop compromising

Every tier above also ships in **4-card (`multi4`, TP=4)** and **8-card (`multi8`, TP=8)** form — the same speed×fidelity × base/super/ultra matrix, **twelve DFlash2 slugs** in all. We can't bench them (the reference rig has exactly two 3090s), so they're **community-validated by design** — but if you have four or more cards, this is the topology the **fidelity series was waiting for**.

**On two cards the FP8 tiers are VRAM-starved; more cards remove the compromise.** The official FP8 weights (\~29 GiB) leave so little room on 2× 3090 that `supermax` caps at 144K and `ultramax` at 64K — you trade context to keep FP8 precision. Split those weights across **four or eight cards and the tradeoff disappears**: FP8-precision weights **and** the full 262K context **and** the DFlash2 drafter, all at once. The dual fidelity tiers are the constrained version; **multi4/multi8 is where full-quality FP8 finally gets the full window.** (The int4 *speed* tiers already fit 262K on two cards — for them, more cards buy concurrency headroom, not context.)

**There's already a strong 4-card datapoint.**[@A1RM4X](https://github.com/A1RM4X) ran the full gate on 4× RTX 3090 ([#1064](https://github.com/noonghunna/club-3090/issues/1064)): verify-full 9/9, stress to **240,635 tok (91% of 256K)** at 0 MiB growth, soak PASS, **code decode 190 tok/s**, both 8-pack arms (**120/150** no-think · **128/150** think). ⚠️ That run was the INT4 speed tier on the **incoai** bf16 drafter (PR [#1060](https://github.com/noonghunna/club-3090/pull/1060)), not the shipped **syv-ai** W4A16 — a strong cross-reference for the multi4-DFlash2 *shape*, not the exact shipped slug. The full-context-FP8 claim above follows from the VRAM math (weights split → room for 262K fp8 KV), not a first-party bench — a `bench.sh` on `vllm/qwen38-27b-multi4-supermax` from any 4-card rig is what turns it from projection into a shipped row. (MTP base tier: [#1025](https://github.com/noonghunna/club-3090/issues/1025) 96/119, [#1004](https://github.com/noonghunna/club-3090/issues/1004) 103/135 — same 240K ceiling.)

**⚠️ Budget KV headroom for DFlash2.** A1RM4X's other finding: the drafter's codebooks (\~0.5 GiB/GPU) + 5-layer backbone cost VRAM the KV pool wants — pushing to 512K needed `--gpu-memory-utilization 0.80` (0.90 OOM'd the first prefill). More cards give you the room; don't assume the MTP tier's gmu carries over.

Boot one, run `report.sh --full`, and file it via the numbers-from-your-rig template — that's what turns 🧪 into a shipped row.

##### Why the 4- and 8-card ultra slugs stay on bf16 KV

They already reach 262K on bf16, because the aggregate VRAM carries it. fp8 KV  
would buy them **no** context and cost the same decode it costs everywhere else,  
so converting them would be a regression in exchange for nothing. They are  
deliberately left alone.

If you run **many concurrent sequences** on 4 or 8 cards there is a reason to flip  
it — fp8 roughly doubles the KV pool at the same ceiling, which is headroom above  
the shipped `max_num_seqs: 2`:

```
KV_CACHE_DTYPE=fp8_e4m3 bash scripts/switch.sh vllm/qwen38-27b-multi4-ultrafast --force
```

⚠️ Untested at TP=4/8 on our side — the reference rig has two cards, and the FA2  
plugin itself is validated at TP=2 only. Treat it as unproven and please report back.

#### Things worth knowing before you launch

**⛔ No quality numbers yet.** verify-full passes 9/9 on every dual slug, but the **8-pack, NIAH fill depth, and soak have not been run** on any of these. Throughput without a quality number is half a picture — the c3 catalog leaves the 8pk column deliberately blank rather than imply the other half.

**⚠️ Setup needs the drafter.** The six DFlash2 slugs need the external drafter on disk. Fetch it with `WITH_DFLASH_DRAFT=1` when you run `setup.sh` (it's \~1.2 GB, shared by every DFlash2 tier).

**⚠️ Spec-decode is exposed to [vllm#50021](https://github.com/vllm-project/vllm/pull/50021)** — the same open GDN spec-decode index bug as the MTP tiers, still present in v0.27.1. Our collapse soak ran crash-free to 21k tokens, but treat that as "not observed," not "immune." Mitigate with `SPEC_N=0`.

**⚠️ These decode numbers are a CUDA-13 ceiling, not a peak.** Our image runs CUDA 13.0, where FlashInfer's radix top-k for the DFlash2 candidate selector can't JIT-compile and falls back to a slower sort — [@oceanplexian](https://github.com/oceanplexian) found this in [#1056](https://github.com/noonghunna/club-3090/pull/1056). The selector's "sort-free" fast path also isn't in stock v0.27.1. So treat these figures as a floor for the config: a CUDA-12 build, or a vLLM carrying the sort-free selector path, should decode faster.

##### Quality — both reasoning legs, each its OWN boot

Instruct is the shipped default (leg A = bare launch). Going *back* to instruct after a thinking run needs a reboot too, or the "instruct" leg is silently a second thinking leg.

```
# leg A — instruct (default; no env)
bash scripts/switch.sh --force vllm/qwen38-27b-dual-ultrafast
bash scripts/quality-test.sh --full --no-thinking --sampling-from-server \
  --max-tokens 4096 --thinking-max-tokens 16384 --timeout-per-case 600

# leg B — thinking  ⚠️ all FOUR sampler vars, or you run reasoning with INSTRUCT sampling
ENABLE_THINKING=true TEMP=1.0 TOP_P=0.95 PRESENCE_PENALTY=0.0 \
  bash scripts/switch.sh --force vllm/qwen38-27b-dual-ultrafast
REASONING_EFFORT=low BENCHLOCAL_MODEL_TURN_TIMEOUT=900 \
bash scripts/quality-test.sh --full --enable-thinking --sampling-from-server \
  --max-tokens 4096 --thinking-max-tokens 16384 --timeout-per-case 600
```

Any DFlash2 slug substitutes: `vllm/qwen38-27b-{dual,multi4,multi8}-{superfast,ultrafast,supermax,ultramax}`.

##### Quality on the single-card llama.cpp slug — llamacpp/qwen38-27b-single-iq4xs

One 3090, TP=1, GGUF IQ4\_XS, built-in MTP head, **262K context on q4\_0 KV**. Useful if you  
have a single card, or want a second opinion on the same weights through a different engine.  
**Its defaults are the mirror image of the vLLM slugs above — read this before copying the  
recipe.**

⚠️ **Thinking is the DEFAULT here, not instruct.** The gate flipped 2026-09-01 on a community  
request backed by [#1027](https://github.com/noonghunna/club-3090/issues/1027), where instruct  
scored 120/150 pass@1 — worst of the four modes tested. So a bare launch gives you *leg B*,  
not leg A.

Run it **as shipped** — full 262K, q4\_0 KV, no overrides. That is what the slug is, and it is  
what the numbers should describe:

```
# leg A — INSTRUCT.  One knob: INSTRUCT=1 flips --reasoning off AND the card's INSTRUCT
# sampler row together, so you do NOT set the four sampler vars by hand here.
FORCE=1 INSTRUCT=1 bash scripts/launch.sh --variant llamacpp/qwen38-27b-single-iq4xs
URL=http://localhost:8090 bash scripts/quality-test.sh --full --no-thinking \
  --sampling-from-server --max-tokens 4096 --thinking-max-tokens 16384 --timeout-per-case 600

# leg B — THINKING (the shipped default; no sampler env needed — the compose already
# ships the card's THINKING row: temp 1.0 / top_p 0.95 / top_k 20 / min_p 0.0)
FORCE=1 bash scripts/launch.sh --variant llamacpp/qwen38-27b-single-iq4xs
URL=http://localhost:8090 REASONING_EFFORT=low BENCHLOCAL_MODEL_TURN_TIMEOUT=900 \
bash scripts/quality-test.sh --full --enable-thinking --sampling-from-server \
  --max-tokens 4096 --thinking-max-tokens 16384 --timeout-per-case 600
```

- **Gated slug — and the form differs per script.**`launch.sh` takes it as an env var (`FORCE=1`), `switch.sh` as a flag (`--force`). ⚠️ `launch.sh … --force` fails with `Unknown flag: --force` — this post said otherwise until 2026-09-11. The slug is hidden from `switch.sh --list`  
  (reveal with `--list --all`).
- Port is **8090**, not 8020. `quality-test.sh` auto-detects the endpoint via preflight, but  
  passing `URL=` explicitly avoids it finding something else you have running.
- `CUDA_VISIBLE_DEVICES` defaults to `0`, so GPU 1 stays free — you can leave a dual-card  
  vLLM slug down and still run this without touching the other card.
- `--sampling-from-server` on both legs: the point is to score what the compose actually  
  ships, not a sampler you typed.

###### 🔬 Bonus arm nobody has run yet: does q8 KV buy anything here?

This compose ships **q4\_0** KV to reach 262K on one card. Our standing rule is that sub-q8 KV  
is a speed exhibit rather than serving-grade — but on *this* model that is a rule, not a  
measurement. Nobody has the quality delta.

Re-run either leg with the q8 override and post both. It costs context (262K → 131K), which  
is exactly the trade worth quantifying:

```
KV_TYPE=q8_0 CTX_SIZE=131072 \
  FORCE=1 bash scripts/launch.sh --variant llamacpp/qwen38-27b-single-iq4xs
# then the same quality-test.sh line as the leg above
```

A q4\_0-vs-q8\_0 pair on identical weights, sampler and packs would settle whether the KV floor  
costs accuracy on Qwen3.8-27B or just headroom — **please label which KV the numbers came  
from**, since the two are not comparable with each other or with the q8-and-above results  
further up.

One configuration-safety note that may be worth making explicit in the tier docs:

For the current Qwen3.8 DFlash2 exports, `SPEC_N` is coupled to the checkpoint's `dflash_config.block_size`; it is not a free tuning knob. The DFlash2 implementation constructs the grouped-convolution block size as `1 + num_speculative_tokens`, and `_grouped_conv` uses that value as its causal reset boundary. The published exports declare `block_size = 8`, so `SPEC_N=7` is the matching depth.

A mismatch can load successfully because `block_size` does not shape any checkpoint parameter. It instead changes the causal boundary silently and may reduce draft acceptance rather than failing at boot. In particular, `SPEC_N=15` should only be paired with an export that declares `block_size=16`.

Suggestion: treat `SPEC_N` as checkpoint-coupled metadata and validate `1 + SPEC_N == dflash_config.block_size` at launch, preferably failing loud on mismatch.

#### Follow-up: ultrafast's 231 tok/s is a short-context number — the tiers swap places by \~32K

The tables above are the canonical bench, which uses a \~25-token prompt. That's the right  
protocol for comparing decode speed, and the numbers are real — but it means the hierarchy they  
show (`ultra` &gt; `super`) is measured at one end of the context range, and several of you are  
running these tiers at 30K+.

We measured the same two shipped slugs across context with **long one-shot prompts**, spec-on as  
shipped, 400 generated tokens counted from the API's own `usage`. The ranking inverts:

prompt ctx `dual-ultrafast` (bf16 / FlashAttn) `dual-superfast` (fp8 / FlashInfer)

\~4K **124** tok/s 86 ultrafast

\~8K **79** 72 ultrafast

\~16K **92** 79 ultrafast

\~32K 55 **68** **superfast**

\~90K 17 **≈72** **superfast, by \~4×**

\~200K — (past its envelope) **66** superfast only

*Spec-on decode is noisy: per-arm spread across boots is 18–37% and accept-length swings  
1.84–3.41, so treat these as locating a crossover, not as precise figures. The 90K superfast  
cell is a 3-boot median; the rest are single boots.*

**Practical routing, today, on the shipped slugs:**

- **Short prompts (chat, code completion, agentic turns under \~16K)** — `ultrafast` is the right  
  pick and the 231 tok/s headline holds.
- **Long prompts (RAG over big documents, whole-repo context, long transcripts) at 32K+** —  
  **use `superfast`.** It is faster *and* keeps the full 262K envelope. At 90K `ultrafast` is  
  roughly 4× slower.
- The crossover sits between 16K and 32K. If your workload straddles it, `superfast` is the safer  
  default — it degrades gently with context where `ultrafast` falls off a cliff.

##### Why — and it isn't the KV dtype

It's the **attention kernel at speculative-decode shape**. Each verify step submits  
`num_speculative_tokens + 1` query tokens at once. FlashAttention-2's paged path forbids splitting  
that work across the KV length, so it launches roughly `batch × heads` thread blocks and walks the  
whole context serially in each — on our rig, 12 blocks on an 82-SM card. FlashInfer splits it and  
keeps every SM busy.

Measured at kernel level, on identical KV bytes, `q=8` versus `q=1`:

KV length FA2 FlashInfer

32K **×21.4** ×1.02

200K **×28.5** ×1.02

So `ultrafast` 's bf16-KV/FlashAttention path — the thing that makes it fastest on short prompts —  
is also what makes it fall behind at depth. Same trade-off as the context envelope, just less  
visible.

##### There is a fix, and it is upstream-pending — not shipped

Two open PRs against vLLM's FlashAttention fork lift the restriction:  
[vllm-project/flash-attention#176](https://github.com/vllm-project/flash-attention/pull/176) and  
[#190](https://github.com/vllm-project/flash-attention/pull/190). We arrived at the same fix  
independently, found theirs first was more general, and closed ours — our tests and end-to-end  
numbers are posted on both.

With that patch applied in a **probe container** (⚠️ *not a shipped configuration, do not try to  
replicate this in your compose*), `ultrafast` at 32K goes from **55 → 111 tok/s (n=3 medians)** and  
retakes the lead over `superfast` at that depth. At 90K FlashInfer still wins, for a separate  
reason the patch doesn't address.

**Nothing in this section changes what you get today.** The routing advice above is for the slugs  
as they ship. If one of those PRs merges and reaches a vLLM release we pin, the crossover moves and  
we'll update this note in one line.

##### ⚠️ What this means for the ultra\* tiers going forward

Two things follow from the above that are worth flagging before you build around these slugs.

**The advertised context on the `ultra*` tiers is a capability ceiling, not a usable-throughput  
ceiling.**`dual-ultrafast` declares 204,800, and the 4- and 8-card `ultra*` slugs declare 262,144.  
The engine will boot and serve those lengths — but as the table above shows, decode past \~32K is  
not something you want a workload sitting on. **We are likely to cap or re-scope those advertised  
numbers so the declared ceiling matches the usable range.** If you have a compose pinned to a large  
`MAX_MODEL_LEN` on an `ultra*` slug today, that is the change most likely to affect you, and  
`super*` is the tier that holds long context properly.

**We are not retiring the `ultra*` tiers.** They are the fastest thing we ship at short context and  
that is not an Ampere quirk — a community bench on 2× RTX 5090  
([#1086](https://github.com/noonghunna/club-3090/issues/1086) /  
[#1085](https://github.com/noonghunna/club-3090/issues/1085)) puts `dual-ultramax` at **183 tok/s**  
against `dual-supermax` at **152** on the same `bench.sh` instrument — the same \~20% short-context  
lead, on different silicon. If you are under \~16K, `ultra*` remains the right pick.

Two honest limits on the above: the crossover is measured for the **int4** pair (`ultrafast` /  
`superfast`) on 2× 3090. For the **fp8** pair (`ultramax` / `supermax`) we have no long-context  
comparison at all — only that short-context 5090 data — so read the `max` tiers as unproven at  
depth rather than as sharing `ultrafast` 's cliff. And if  
[#176](https://github.com/vllm-project/flash-attention/pull/176) /  
[#190](https://github.com/vllm-project/flash-attention/pull/190) merge and reach a pinned release,  
the 32K row roughly doubles and this section gets rewritten rather than acted on.

If you are running an `ultra*` slug above 32K today, we would like to hear about it — that is the  
case this change would affect, and it is the one we have the least visibility into.

#### 核心判断

**这篇文章最值得关注的，不是 “2×3090 跑到 220 tok/s”，而是：旧 GPU 的实际能力越来越取决于推理软件栈与任务形态，而不只是显存、算力和模型大小。**

作者报告称，仅替换投机解码器和 attention/KV kernel，同一套 2×RTX 3090、同一 27B 模型的代码生成速度就从 100 提升到 220 tok/s；随后一个社区 kernel 又消除了 “速度与上下文二选一” 的限制。这说明在本地推理中，**软件路径可能带来接近一次硬件换代的收益**。

但这还不是一个可以直接用于采购或生产部署的结论：数据主要是作者自测，质量评估缺失，4/8 卡结论多为显存推算，而且 220 tok/s 是经过挑选的代码场景，不是通用速度。

> 可信度提醒：页面标注的发布时间和更新日期是 2026-09-12/14，且依赖文中所称的 vLLM v0.27.1、Qwen3.8 与社区插件。使用前应核对这些版本和提交是否真实可获取。下文把数字视为 “作者报告”，而非独立确认的事实。

---

##### 1. 投机解码的收益是 “任务分布红利”，不能抽象成统一的 2.2 倍

###### 洞见是什么

**DFlash2 并没有把模型普遍加速 2.2 倍；它主要在 “容易预测后续 token 的输出” 上获得高收益。**  
因此，判断它对你是否有价值，首要变量不是 GPU，而是你的输出类型。

###### 为什么成立

文章自己的数字已经显示出明显差异：

| 配置 | 叙事文本 | 代码 |
|---|---:|---:|
| INT4 基础 MTP | 73 tok/s | 100 tok/s |
| INT4 DFlash2 + FlashAttention | 123 tok/s | 220 tok/s |
| 提升 | **约 68%** | **120%** |

FP8 系列也类似：

- 叙事文本：69 → 94，约**36%**
- 代码：87 → 170，约**95%**

机制并不神秘：投机解码器先预测一段 token，再让目标模型批量验证。代码中缩进、语法结构、常见 API 和模板有较强规律，草稿更容易被接受；开放式散文的下一段表达不确定性更高，接受率就低。

所以，标题里的 220 tok/s 是一个真实可能存在、但高度依赖 workload 的上界。它不应被解释为所有请求的服务能力。

###### 对你有什么用

如果你的主要用途是：

- 编程代理、代码补全、批量代码生成；
- 结构化 JSON、SQL、模板化报告；
- 长输出、机器消费结果；

那么这种优化可能非常有价值。

如果主要是：

- 短问答；
- 开放式写作；
- 人类逐字阅读的聊天；
- 首 token 延迟比生成速度更重要的交互；

220 tok/s 的商业或体验价值会小很多。人未必能消费这么快，而草稿模型的额外开销还可能影响首 token 时间。

**低成本验证方式：**从自己的真实日志抽取 50～100 个请求，按代码、结构化文本、开放文本分类，分别测量：

- p50/p95 首 token 延迟；
- decode tok/s；
- 草稿 token 接受率；
- 单任务完成时间，而不只是每秒 token；
- 有无投机解码时的任务成功率。

如果只跑作者的 “code-shaped prompt”，测到的是硬件演示，不是你的收益。

---

##### 2. “262K 上下文” 目前主要是容量结论，不是能力结论

###### 洞见是什么

**能把 262K token 放进 KV cache，和模型能有效使用 262K 信息，是两件完全不同的事。**

这篇文章比较充分地讨论了前者，却几乎没有证明后者。

###### 为什么成立

作者提供或声称验证的主要是：

- 显存能否容纳；
- 是否 OOM；
- decode 速度；
- 短期 soak 是否崩溃；
- `verify-full 9/9`。

但文章也明确承认以下测试尚未完成：

- NIAH 等长上下文信息检索；
- 完整质量评估；
- 更深入的稳定性测试；
- 多任务并发；
- 8-pack 行为测试。

此外，长上下文部署至少还有三个未展示的重要成本：

1. **Prefill 时间**  
   262K 输入的预填充可能远比后续 decode 更耗时。只展示 decode tok/s，会掩盖实际端到端等待时间。

2. **上下文有效性**  
   模型可能在 262K 窗口中遗漏信息、受位置偏差影响，或者只在靠近首尾的位置表现较好。

3. **并发容量**  
   单请求能塞进 262K，不等于服务器可以同时承载多个长请求。KV cache 仍然是并发的主要约束。

文章里的社区 kernel 确实可能解决了一个工程瓶颈：让 Ampere 上的 FlashAttention 路径读取 FP8 KV。但它解决的是 “存储与计算路径”，不是模型的长上下文理解能力。

###### 对你有什么用

如果你在做长文档问答、代码库理解或长轨迹 Agent，不应把 “支持 262K” 直接写进采购决策。你真正要问的是：

> 在我的文档长度和检索任务上，它能否比 “检索后只送 32K/64K” 获得更高的任务成功率，并足以抵消 prefill 和显存成本？

一个简单测试是：

- 在 32K、64K、128K、262K 四档放置同一组关键信息；
- 改变关键信息所在位置；
- 同时记录正确率、TTFT、峰值显存和端到端耗时；
- 加入 RAG + 短上下文作为对照。

很多场景下，更好的检索和上下文压缩可能比强行塞入 262K 更划算。

---

##### 3. 正确的结论不是 “ultra 永远最好”，而是静态档位命名很容易迅速过时

###### 洞见是什么

**文章中最有代表性的变化，是它建立的 tier hierarchy 在两天内就被底层 kernel 更新部分推翻了。**

原先：

- `super`：FP8 KV、长上下文，但较慢；
- `ultra`：FlashAttention、更快，但 BF16 KV 导致上下文缩水。

社区插件让 Ampere 的 FlashAttention 支持 FP8 KV 后，双卡`ultra`同时获得了更快速度和完整上下文。也就是说，在作者报告的双卡指标上，`ultra`基本支配了`super`。

###### 为什么成立

这说明原来的产品层级不是来自稳定的用户需求差异，而是来自一个暂时的软件能力缺口。缺口一旦被填补，层级就失去了主要存在理由。

类似问题还会继续发生：

- CUDA 12/13 的 kernel 路径不同；
- FlashInfer 是否能编译 radix top-k；
- vLLM 是否合入 sort-free selector；
- TP=2 与 TP=4/8 的插件兼容性不同；
- driver、GPU 架构、量化格式会改变最优组合。

所以 “fast/superfast/ultrafast” 这类固定 slug 可以方便启动，却不适合作为长期性能认知。真正稳定的表达应该是能力矩阵：

- 权重量化；
- KV dtype；
- attention backend；
- drafter 类型与深度；
- 上下文上限；
- 并发数；
- GPU 架构；
- 已验证的软件版本。

###### 对你有什么用

如果你维护本地推理平台，长期价值不在于手工追逐越来越多的配置名，而在于建立一个**自动能力检测和回归测试流程**：

1. 检测 GPU 架构、显存与可用 kernel；
2. 自动生成可行配置；
3. 用真实 workload 测 TTFT、decode、质量和稳定性；
4. 在升级 CUDA、vLLM 或 kernel 后自动重跑；
5. 选择 Pareto 最优配置，而不是相信档位名称。

文章中的`c3` cockpit 已经解决了 “发现与启动配置” 的一部分，但从其描述看，尚不能替代 workload 驱动的自动选择。

---

##### 4. “fidelity” 目前只是精度格式标签，不是已证明的质量优势

###### 洞见是什么

**FP8 被命名为 fidelity 系列，但文章没有质量数据证明它在目标任务上优于 INT4。**

因此不能从命名直接得出 “FP8 更值得部署”。

###### 为什么成立

可以确认的差异是：

- INT4 权重更省显存，双卡更容易保留完整上下文；
- FP8 权重约 29 GiB，占用更多显存；
- 在报告数据中，INT4 的速度普遍更高；
- 完整的行为质量评估尚未运行。

从通常规律看，FP8 比 INT4 保留更多数值精度是合理预期，但质量损失是否会转化为实际任务差异，取决于：

- 量化方法；
- 代码、推理、工具调用等具体任务；
- 长上下文长度；
- 采样参数；
- 对格式和精确答案的容错。

还要区分两件事：

- **更换 INT4/FP8 目标模型**可能影响质量；
- **加入投机 drafter**在验证算法正确时，理论上主要改变速度，不应随意改变目标分布。

但文章同时提到尚未修复的 spec-decode index bug，因此实现正确性不能只靠理论保证。

###### 对你有什么用

如果你只有 2×3090，不能因为`max/ultramax`被称为 fidelity 就默认选择 FP8。更合理的决策规则是：

- 若 INT4 在你的任务上与 FP8 成功率无显著差异，INT4 的速度和显存优势更实用；
- 只有当 FP8 在代码正确率、推理通过率、工具调用或格式遵循上产生可测量收益时，才值得承受其资源成本。

尤其不要用主观观感比较。应使用可判分任务，例如单元测试通过率、JSON schema 通过率、答案一致率和 Agent 成功率。

---

##### 哪些结论暂时不应相信得太多

1. **4/8 卡会完整兑现所有收益**  
   文章明确说没有第一方 4/8 卡测试；完整上下文主要来自显存数学推算。能装下通常可以推算，但吞吐、通信开销和稳定性不能由显存直接推出。

2. **这些数字是稳定的生产性能**  
   部分数据只有单次 boot，`supermax`的 token 计数还出现异常。它们足以显示 “大概率存在明显性能差距”，不足以支持精确到个位数的比较。

3. **220 tok/s 就代表系统吞吐**  
   文中主要是单路 decode 速度，不等于并发请求吞吐，也没有覆盖排队、prefill、网络和调度成本。

4. **自定义预编译 kernel 没有额外代价**  
   它可能延长 3090 的使用寿命，但也引入兼容性、升级、供应链和崩溃风险。生产环境需要固定镜像、校验 digest，并设置不启用投机解码的回退路径。

---

#### 如果只尝试一件事

**不要先升级硬件，也不要直接采用最快的 slug；先用你的真实请求对`dual-fast`与`dual-ultrafast`做一次受控 A/B。**

至少同时测：

- 端到端任务成功率；
- p50/p95 TTFT；
- decode tok/s；
- 输出长度和草稿接受率；
- 长上下文正确率；
- 峰值显存、OOM 与长时间稳定性；
- 开启和关闭投机解码的输出一致性。

如果`ultrafast`在你的任务上保持质量和稳定性，同时显著缩短完整任务时间，那么这篇文章真正揭示的机会就成立了：**用软件优化把现有 3090 的有效寿命再延长一代，而不是为一个选择性 benchmark 立即购买新 GPU。**

## 口播总结（1）

### 2026-09-20 00:39:49

这份测试最重要的结论是：同样使用两张英伟达 RTX 三零九零，运行千问三点八、二百七十亿参数的稠密模型，引入 D Flash 二外部草稿模型后，代码生成速度最高可达每秒二百二十个 token，同时保留约二十六万两千个 token 的完整上下文。不过，这只是吞吐量成绩，目前还没有足够的质量评测，不能直接理解成“速度翻倍而质量完全不变”。

整个配置体系可以从两个维度理解。

第一个维度是模型权重。速度系列使用 INT 四量化，重点是节省显存和提高速度。保真系列使用官方 FP 八权重，精度更高，但占用的显存也更多。

第二个维度是推测解码的深度。基础档使用模型内置的 MTP，也就是多 token 预测头。超级档和极速档，则改用外部的 D Flash 二块级草稿模型。草稿模型会先猜出一批候选 token，再让主模型集中验证。如果候选命中率足够高，主模型就能一次确认多个 token，从而提高生成速度。

超级档使用 FP 八格式的 KV 缓存，并通过 Flash Infer 执行注意力计算。KV 缓存可以简单理解为模型在处理长对话时保存的“上下文工作记忆”。FP 八占用较小，因此有利于保留长上下文。

极速档同样使用 D Flash 二，但把注意力后端换成更快的 Flash Attention。对三零九零所用的安培架构来说，这条路径的解码速度明显更高。

这里曾经有一个重要限制。过去，安培显卡上的 Flash Attention 二不能直接读取 FP 八格式的 KV 缓存。用户只能二选一：要么使用 Flash Infer，保留完整上下文；要么使用 Flash Attention 和体积更大的 B F 十六缓存，以牺牲上下文换取最高速度。

二零二六年九月十四日，这个限制被社区贡献解决了。新的扩展让安培显卡上的 Flash Attention 二可以读取 FP 八缓存，而且使用的是预编译内核，用户不需要在本机编译。于是，在两张三零九零上，极速档不再需要用上下文换速度。它现在可以同时获得完整的约二十六万两千 token 上下文和最快的解码路径。

具体成绩来自两张 RTX 三零九零。测试进行了三次预热，再进行五次正式测量。

在 INT 四速度系列中，基础 fast 档处理叙事文本时，每秒约七十三个 token；处理代码型提示时，每秒约一百个 token。

换成 D Flash 二和 Flash Infer 的 superfast 档后，叙事速度约为每秒七十八个 token，提升不大；但代码速度达到每秒一百四十一个 token，比基础档高约百分之四十一。

再换成 Flash Attention 的 ultrafast 档，叙事速度达到每秒一百二十三个 token，代码速度达到每秒二百二十个 token。相对于基础 fast 档，代码吞吐量提高了百分之一百二十，也就是达到原来的二点二倍。

这个对比说明，D Flash 二的收益与输入内容有关。代码型提示更适合草稿模型提前预测，所以加速特别明显。叙事文本也有提升，但不能把代码场景中的二百二十 token 每秒，当成所有任务都能达到的通用速度。

在 FP 八保真系列中，基础 max 档的叙事和代码速度，分别约为每秒六十九和八十七个 token。使用 Flash Infer 的 supermax 档，代码速度大约在每秒一百三十到一百四十多个 token，但这个数字波动较大，作者明确表示，它是表格中可信度相对最低的一项。

使用 Flash Attention 的 ultramax 档，则达到叙事每秒九十四个 token、代码每秒一百七十个 token，并且在更新后也能保留完整的约二十六万两千 token 上下文。

不过，保真系列在两张卡上仍然更受显存约束。官方 FP 八权重大约占二十九吉字节，外部 D Flash 二还会进一步挤占约二点六吉字节的 KV 缓存空间。两张三零九零每张只有二十四吉字节显存，所以 supermax 档的上下文上限仍只有大约十四万多个 token。相比之下，INT 四速度系列在两张卡上就已经能容纳完整上下文。

四张或八张卡理论上可以解决保真系列的显存压力。权重分摊到更多显卡后，FP 八权重、完整上下文和 D Flash 二草稿模型有望同时容纳。INT 四系列本来就能在两张卡上实现完整上下文，因此增加显卡对它的主要价值，是支持更多并发请求，而不是继续扩大上下文。

但这里必须区分实测与推算。作者的参考机器只有两张三零九零，所以四卡和八卡配置大多没有第一方跑分。已有一次四张三零九零的相关测试，在约二十四万个 token 的压力下没有出现显存增长，代码解码速度达到每秒一百九十个 token。不过，那次测试使用的草稿模型与正式发布版本并不完全相同，只能证明整体方案可行，不能当作正式配置的精确成绩。四卡和八卡的完整 FP 八上下文，目前主要仍是根据显存容量推算出来的。

这些配置还有几个现实限制。

第一，所有 D Flash 二档位目前都标为实验性配置，需要强制启动。外部草稿模型约一点二吉字节，需要单独下载，但可以由所有相关档位共享。

第二，目前没有完整的质量数字。两卡配置通过了九项基础验证，但更全面的八组行为测试、长上下文信息检索测试和持续稳定性测试还不完整。吞吐量只是半张成绩单，不能据此判断推测解码是否影响回答质量。

第三，现有版本仍暴露在一个推测解码索引错误之下。测试中连续生成到两万一千个 token 没有观察到崩溃，但“没有观察到”不等于已经免疫。

第四，这些速度可能还不是硬件极限。当前镜像使用 CUDA 十三，其中一个候选筛选内核无法走最快路径，只能退回较慢的排序实现。因此，使用 CUDA 十二，或者加入无排序快速路径的新版本，理论上还可能更快。

最值得记住的是三点。D Flash 二确实能让两张消费级三零九零上的二百七十亿参数模型获得显著加速，尤其适合代码生成。新的 FP 八缓存扩展又消除了极速档过去必须牺牲上下文的限制。但目前最亮眼的是速度数据，而不是完整的质量结论；在正式部署前，仍要根据自己的任务验证输出质量、长上下文稳定性和显存余量。

## 深度解读-口播（1）

### 2026-09-30 11:53:32

两张 RTX 三零九零显卡，运行同一个二百七十亿参数的模型，代码生成速度能从每秒一百个词元，提高到二百二十个。关键不是换更大的显卡，而是换一种让模型生成答案的方式。不过，这个提升有明确的测试条件，不能直接理解为所有任务都快了一倍，也不能据此判断回答质量更好。

这篇材料讨论的是通义千问三点八的部署档位。理解这些档位，先抓住两个问题：模型权重用什么精度保存，以及生成时用什么加速方法。

权重精度分成两类。速度系列使用四比特整数量化，权重更省显存。保真系列使用官方八比特浮点权重，保留更高的数值精度。但“保真”是档位名称，不是已经得到质量测试证明的结论。

每个系列又分成基础、super 和 ultra 三档。基础档使用模型内置的多词元预测模块，也就是尝试一次预测多个后续词元。super 和 ultra 则换成一个外部的 DFlash 二草稿模型。

词元可以粗略理解为模型处理文字的小单位，不一定对应一个汉字。所谓草稿模型，就是先让一个较小的模型提出一段候选内容，再由主模型验证。候选内容被接受得越多，主模型就越有机会减少逐个生成的开销。这叫推测式解码。

所以，这次加速的核心，是改变生成流程，而不是增加主模型的参数。外部草稿模型还从结构上绕开了内置预测模块特有的一类接受率崩塌问题。但这不等于所有推测式解码故障都被消除了。

super 和 ultra 的区别，主要在于底层计算路径。这里需要认识一个概念：键值缓存。它保存模型已经处理过的上下文信息，是长对话占用显存的重要来源。

最初，三零九零所属的安培架构存在一个限制：更快的 FlashAttention 计算路径，不能同时使用八比特浮点键值缓存。

这就形成了一道选择题。super 保留省显存的八比特缓存，使用另一条叫 FlashInfer 的计算路径。ultra 使用更快的 FlashAttention，但当时必须配合更占显存的十六比特缓存。结果就是，ultra 生成更快，却要牺牲上下文长度。

不过，这篇材料在二零二六年九月十四日更新了一个关键变化。社区贡献的扩展，让三零九零上的 FlashAttention 也能读取八比特缓存。于是，双卡 ultra 不再需要在速度和上下文之间二选一。

这点尤其值得记住：如果看到旧结论说，双卡 ultra 必须缩短上下文，那已经不是这篇材料更新后的结果。

具体快了多少？先看四比特的速度系列。

在两张三零九零上，基础 fast 档的代码生成速度约为每秒一百个词元。换成 superfast，约为一百四十一个。换成 ultrafast，达到二百二十个，也就是基础档的两点二倍。

但换成叙事性文字，结果就不同了。基础档约为每秒七十三个词元，ultrafast 约为一百二十三个。提升仍然明显，却不是代码测试中的两点二倍。

因此，二百二十这个数字必须和“代码型提示”一起记。它不是各种输入都能达到的统一速度。

更新后的双卡 ultrafast，同时支持约二十六万两千个词元的完整上下文窗口。不过，支持这么长的窗口，不代表在填满这个窗口时，也一定能保持短提示测试中的生成速度。

八比特浮点权重的保真系列，也有类似变化。基础 max 档的代码生成约为每秒八十七个词元，ultramax 约为一百七十个，接近翻倍。更新后的双卡 ultramax，同样支持完整的约二十六万两千词元窗口。

相比之下，双卡 supermax 的上下文上限仍只有约十四万到十五万个词元。原因是八比特权重本身约占二十九吉比字节，再加上外部草稿模型的额外开销，两张各有二十四吉比字节显存的卡，空间比较紧张。

作者的更新测试显示，在双卡配置下，ultra 现在不仅生成更快，上下文也不比 super 短。但这还不能推出 super 已经没有存在价值，作者没有在这里给出这个结论。另外，更新中的 super 对照只做了单次启动测试，supermax 的代码词元计数还有波动，不宜过度解读精确数字。

如果增加到四张或八张卡，显存压力就会减轻。权重分摊到更多显卡后，理论上可以同时容纳八比特权重、外部草稿模型和完整上下文。

但这里要分清实测和推算。作者自己的机器只有两张三零九零，没有给四卡、八卡各档位提供完整的一手测试。

社区确实有一个四卡案例：四张三零九零运行四比特速度档，完成了约二十四万个词元的压力测试，代码生成约为每秒一百九十个词元。不过，这次用的草稿模型，与文章正式提供的版本不同。它能支持“这种四卡部署方案可行”，却不能代替所有正式配置的测试，更不能证明八比特保真档已经全面验证。

四卡和八卡的 ultra，默认也仍然使用十六比特缓存。因为这些机器的总显存，已经足以支持完整窗口，作者没有把双卡的新缓存方案直接套过去。

最后，比跑分更重要的是验证边界。

这些档位仍属于实验配置。双卡各档位都通过了九项基础验证，但完整的行为质量评测还没有结果。长上下文检索和长期稳定性测试也没有全部补齐。所以，目前能说的是“在这些条件下生成更快”，不能说“回答质量已经证明不变”。

推测式解码还有一个已知的软件索引问题尚未解决。相关测试连续运行到两万一千个词元，没有观察到崩溃，但“没有观察到”不等于“已经免疫”。

最值得留下的认识是：外部草稿模型可以在不更换显卡、不扩大主模型的情况下，显著提高生成吞吐。社区补丁又让双卡 ultra 摆脱了原先速度与上下文之间的取舍。但选择部署档位时，仍要把生成速度、上下文容量和回答质量分开看，不能拿一个漂亮的速度数字，替代另外两项验证。
