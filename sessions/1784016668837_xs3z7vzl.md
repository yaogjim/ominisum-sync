## 分析要点

- **核心高价值点**：将长期运行的智能体循环拆成契约、状态日志、触发器、执行验证和演化机制，并为每一层明确安全边界与职责。
- **留存建议**：建议精读并存档，可作为设计长期运行智能体循环的框架参考（提供了可复用的循环契约、状态日志、触发器、执行验证及周期性优化框架，并配有工程和客户运营案例。）

**知识要点**

- 循环契约应明确目标、完成条件、自治边界、人工升级条件和标准操作流程。
- 状态用于保存当前假设、待办和后续事项，追加式日志用于记录每次运行，避免智能体重复探索和浪费令牌。
- 高风险任务宜拆分为编排者、隔离执行者和验证者，并要求验证者生成便于人工审查的测试证据。

**行动项**

- 为一个现有Agent任务建立README，写入目标、边界、SOP、精简状态和追加式运行日志。
- 根据反馈速度与紧急程度选择连续、定时、事件或组合触发器，并用脚本预检是否存在真实任务。
- 为生产代码或客户消息增加独立验证环节，并每运行5至10次复盘和优化循环配置。

## 结构化（1）

### 2026-07-14 08:11:08

#### 《How to design loops that actually works》精炼总结

这篇内容分享了作者团队在公司**Superdesign**连续运行 AI Loop 约 1 个月后的经验：真正有用的 Loop 不是简单让 AI 重复执行任务，而是要设计好目标、边界、触发机制、验证机制和自我改进机制。核心思想是从 “人给 Agent 下指令” 转向 “设计一个能自主发现任务、执行、验证并持续优化的系统”。

---

##### 1. 开场：AI Loop 已在真实业务中运行

作者举了几个真实例子说明 Loop 已经在公司日常运行，而不是演示 Demo：

- 晚上**12 点**，代码库仍不断收到 PR。
- 原因不是团队熬夜，而是有 Agent 每**30 分钟**自动唤醒：
  - 扫描代码库的问题和改进点；
  - 检查服务器日志；
  - 自动提交 PR；
  - 由验证 Agent 完整测试，并附上证据供人审查；
  - 对低风险修复，甚至可以自动合并。
- 其他业务 Loop：
  - CRM 生命周期 Agent 自动扫描用户并分群，决定跟进策略；
  - 客服工单可自动处理，不受用户语言限制。

---

##### 2. Loop Engineer：从 “提示词” 到 “系统设计”

作者提出 “Loop Engineer” 的概念：

- 过去：人不断给 Agent 输入 prompt，让它做单个任务。
- 现在：设计一个系统，让 Agent 能：
  1. 自己判断要做什么；
  2. 执行任务；
  3. 验证结果；
  4. 根据经验持续改进。

作者强调：  
**写一个简单 Loop 很容易，只占 5%；真正困难的是设计好安全边界和护栏，让人可以放心离开。**

---

##### 3. 一个可用 Loop 的基本结构

作者团队内部的每个 Loop 通常由三部分组成：

###### 3.1 Loop Contract：Loop 的 “宪法”

Loop Contract 通常写在一个 Markdown 文件中，定义这个 Loop 的基本规则。

关键内容包括：

- **目标 Goal**
  - 什么算成功？
  - 是否有明确终点？
- **边界 Boundaries**
  - Agent 可以自己做什么？
  - 哪些情况必须升级给人类处理？
- **SOP 标准流程**
  - Agent 每次运行都应遵循的工作步骤和原则。

---

###### 3.2 State & Logs：让 Agent 记住过去

同一个 Markdown 文件里还会记录 Loop 的状态和日志。

###### State：当前状态

用于保存重要的长期信息，例如：

- 当前假设；
- 待处理 backlog；
- 已提交但还需要跟进的内容。

作者建议：  
**State 要尽量小，只保留真正重要的信息。**

###### Logs：追加式运行记录

Logs 是每次运行后的记录，主要作用是：

- 避免 Agent 每天重复发现同样的问题；
- 避免浪费 token 在已经尝试过的事情上；
- 帮助 Loop 随时间积累经验。

---

##### 4. 案例一：React Doctor 代码健康检查 Loop

作者举了一个工程类 Loop 的例子：**React Doctor Checks**。

这个 Loop 的工作方式是：

- 每天运行开源 CLI 工具**React Doctor**；
- 扫描代码库中的关键问题；
- 选择最严重的问题之一自动修复；
- 提交 PR，并经过验证流程。

它的 Loop Contract 中包含：

- 作用范围和目标；
- Agent 如何启动子 Agent；
- 子 Agent 如何在隔离的 worktree 中修复问题；
- 哪些变更可以自动合并；
- 哪些变更需要人类 Review；
- 标准执行流程 SOP；
- 当前状态和历史日志。

团队还做了内部 Dashboard，用来追踪：

- 打开的 PR；
- 已合并的 PR；
- React Doctor 健康分数随时间的变化。

---

##### 5. 案例二：CRM 生命周期 Loop

Loop 不只适用于工程任务，也可以用于业务增长和用户运营。

作者团队有一个 CRM 生命周期 Loop，每天扫描活跃用户，并自动分群，例如：

- 小型影响者：适合做 affiliate 或分发合作；
- 明显受挫用户：根据大语言模型日志判断其使用中遇到困难；
- 高活跃但未升级用户：适合转化跟进。

根据优先级和风险，Agent 可以：

- 自动发送低风险消息；
- 或先草拟消息，等待作者批准。

这个 Loop 也有类似结构：

- 目标；
- SOP；
- 边界；
- Agent 做用户研究时要注意的陷阱；
- 哪些消息可自动发送；
- 哪些必须人工审批；
- 当前假设和时间线。

---

##### 6. Loop 文件组织方式

作者团队的 Loop 通常按文件夹组织：

- 每个 Loop 有一个独立文件夹；
- 文件夹内有一个`README.md`；
- README 中记录 Loop Contract、State 和 Logs；
- 其他相关产物也可以放在同一文件夹中，并在 README 中引用。

这样可以让 Loop 的规则、状态和历史都集中管理。

---

##### 7. Trigger：选择合适的触发方式很关键

作者认为，Trigger 是 Loop 成本和效率的关键。不同任务适合不同触发方式。

###### 7.1 连续循环 Trigger

类似 Codex 或 Claude Code 的`go`命令。

运行逻辑类似：

> 只要目标未完成，就持续执行下一步，直到成功、达到最大轮数或 token 预算耗尽。

适合场景：

- Bug 修复；
- 明确规格的软件实现；
- 能快速获得反馈的任务。

---

###### 7.2 定时 Trigger

类似 Cron Job。

特点：

- 每隔一段时间唤醒 Agent；
- 例如每天、每小时或每 30 分钟运行一次。

适合场景：

- 每日扫描；
- 周期性检查；
- 定期生成报告。

---

###### 7.3 事件触发 Trigger

当某个事件发生时才唤醒 Agent。

例子：

- 收到新邮件；
- 服务器发生故障；
- Webhook 收到失败事件。

作者提到，Codex 和 Claude Code 目前不原生支持这类触发，因此可以：

- 本地运行一个 daemon 服务；
- 暴露一个 URL；
- 让 Webhook 通知它；
- 再由它唤醒 Agent。

例如：  
Render 上出现失败事件时，通过 Webhook 通知本地 daemon，再触发 Agent 处理事故。

---

###### 7.4 组合式 / Workflow Trigger

这是作者认为最实用的一类 Trigger。

它不是一到时间就直接唤醒 Agent，而是：

1. 定时运行一个脚本；
2. 脚本先检查数据源；
3. 如果确实有新任务，再唤醒 Agent；
4. 如果没有任务，就跳过。

案例：客服工单分拣 Loop

- 每**30 分钟**从 Intercom 拉取最近更新；
- 如果有真实更新，就唤醒 Agent 处理；
- 如果没有，就不运行。

优点：

- 更省成本；
- 更省 token；
- 可以把多个任务批量交给 Agent 处理；
- 避免无意义唤醒。

---

##### 8. Agent 执行层：发现任务、执行任务、验证任务

Agent 被触发后，通常经历三个阶段：

1. **收集信号**
   - 找出有什么任务需要做；
   - 判断优先级。
2. **执行任务**
   - 修复代码、回复用户、生成内容等。
3. **验证结果**
   - 确认任务真的完成；
   - 提供证据供人类审查。

对于简单任务，一个 Agent 可以完成全部流程。  
对于复杂或高风险任务，作者建议拆成多个角色：

- **Orchestrator Agent**
  - 负责研究、规划、分配任务；
- **Executor Agents**
  - 在隔离 worktree 中并行执行任务；
- **Verifier Agent**
  - 测试结果；
  - 把验证证据附到 PR 中；
  - 方便人类快速 Review。

---

##### 9. Verifier：高风险 Loop 的前提条件

作者强调：  
如果 Loop 要处理高风险任务，例如生产代码变更或真实客户消息，验证机制是前提。

好的验证系统应做到：

- 让 Agent 能低成本验证自己的工作；
- 自动生成证据；
- 方便人类快速判断结果是否可信。

作者提到的验证方式包括：

- 用 Playwright 进行测试；
- 录制视频或截图作为证据；
- 使用远程沙盒环境并行运行测试，避免本地开发服务器数量受限。

作者也提供了一个开源的 verifier setup skill，方便在真实代码库中搭建验证系统。

---

##### 10. Evolve Loop：让 Loop 自我改进

作者发现，一个 Loop 刚开始通常不会完美，因此需要一个 “进化 Loop”。

做法是：

- 每运行**5 到 10 次**后，启动一个专门的 evolve session；
- 给 Agent 提供：
  - 当前 Loop 配置；
  - 历史 state；
  - 历史 logs；
  - 原始对话记录；
- 让 Agent 分析如何改进。

可改进的内容包括：

- Loop Contract；
- 过时的状态信息；
- 重复 SOP 是否可以变成脚本；
- Trigger 是否可以更省成本；
- 哪些步骤可以自动化。

案例：  
客服支持 Loop 最初可能只是定时运行，后来在 evolve run 中，Agent 改进为 “先用程序检查是否有新工单，再决定是否唤醒 Agent”，从而降低成本。

##### 11. 案例三：文档维护 Loop

作者还提到一个适合入门的 Loop：**Documentation Maintainer Loop**。

它每天运行一次：

- 对比 README、setup guide、examples、runbooks 等文档；
- 判断哪些文档已经过时；

这个 Loop 解决的问题是：

作者的核心经验是：  
**真正可用的 AI Loop，不是让 Agent 无限重复执行，而是要有清晰目标、边界、状态记忆、合适触发器、验证机制和自我进化能力。**

#### 3. Loop Contract 最佳实践

Keep project documentation accurate and up to date with recently merged product, API, deployment, and developer-experience changes.

## Success Criteria

A run is successful if:

1. It identifies whether recent merged changes require documentation updates.
2. It updates only relevant documentation files.
3. It provides evidence showing why the update is needed.
4. It passes documentation verification.
5. It records state and logs for future runs.

The loop may read:

- Git history
- Merged PRs
- Source code diffs
- Existing documentation
- Package scripts
- API route definitions
- Environment variable usage

The loop may edit:

- `README.md`
- `docs/**/*.md`
- `examples/**/*.md`
- `docs/runbooks/**/*.md`

The loop must not edit:

- Production source code
- Database migrations
- Payment logic
- Authentication logic
- Pricing copy
- Legal or compliance documents

## Autonomy Boundaries

The agent may automatically open a PR when:

- The change is documentation-only.
- The update is directly supported by merged code changes.
- The diff is small and localized.
- Verification passes.

The agent may auto-merge only when:

- The change fixes typos, broken internal links, stale commands, or outdated file paths.
- The change does not alter product promises, pricing, security claims, or API semantics.

The agent must request human review when:

- It changes public API behavior descriptions.
- It updates security, auth, billing, or compliance documentation.
- It is unsure whether the code behavior or documentation is correct.
- It needs to delete or rewrite large documentation sections.
- Verification fails or is inconclusive.

## SOP

Every run must follow this workflow:

1. Acquire loop lock.
2. Run `scripts/check-work.ts`.
3. If no relevant merged changes are found, skip and append a log entry.
4. Collect merged PRs and diffs from the past 24 hours.
5. Classify changes into:
   - API changes
   - CLI/setup changes
   - environment variable changes
   - deployment changes
   - user-facing behavior changes
   - internal-only changes
6. Compare classified changes against existing docs.
7. Decide whether docs are stale.
8. Make the smallest possible documentation update.
9. Run verification:
   - Markdown lint
   - Link check
   - Code block sanity check
   - Docs site build if applicable
10. Create PR with:
   - Summary
   - Source PRs inspected
   - Files changed
   - Verification evidence
   - Risk level
11. Update State.
12. Append Log.

## Verification Requirements

Minimum required checks:

```bash

pnpm docs:check-links
pnpm docs:build
```

If examples are changed, also run:

```bash

```

The PR description must include command outputs or artifact links.

- Setup docs often become stale after changes to `.env.example`, `package.json`, or deployment scripts.
- Runbooks often become stale after infrastructure or logging changes.

- `packages/api/**`
- `apps/web/app/api/**`
- `.env.example`
- `package.json`
- `pnpm-lock.yaml`
- `docker-compose.yml`
- `docs/**`
- `examples/**`

###### Open PRs

- None

###### Follow-ups

- Add automated validation for shell commands in docs.
- Consider splitting API docs update into a separate loop if volume increases.

##### Logs

- Only internal refactors found.
- No user-facing API, setup, deployment, or example changes detected.

Evidence:

- `artifacts/2026-07-14/change-summary.json`
```

# 4. Trigger 最佳实践

不要简单地每天直接唤醒 Agent。  
更好的做法是使用**Combo Trigger**：

> 定时触发一个轻量脚本，先判断有没有真实工作。  
> 有工作才唤醒 Agent，没有工作就跳过。

## 推荐触发策略

```text
每天 09:00 运行 check-work.ts
        ↓
检查过去 24 小时 merged PR
        ↓
是否包含文档相关变更？
        ↓
是：唤醒 Agent
否：记录 skipped log，不唤醒 Agent
```

这样可以显著降低 token 成本，避免 Agent 每天重复分析无意义 diff。

##### 示例：`check-work.ts`

```ts
import { execSync } from "node:child_process";

const watchedPatterns = [
  "packages/api/",
  "apps/web/app/api/",
  ".env.example",
  "package.json",
  "docker-compose.yml",
  "examples/",
];

function getChangedFilesSinceYesterday (): string [] {
  const output = execSync (
    `git log --since="24 hours ago"--merges --name-only --pretty=format:`,
    { encoding: "utf-8" }
  );

  return [...new Set (output.split ("\n").map (x => x.trim ()).filter (Boolean))];
}

const changedFiles = getChangedFilesSinceYesterday ();

const relevantFiles = changedFiles.filter (file =>
  watchedPatterns.some (pattern => file.startsWith (pattern) || file === pattern)
);

if (relevantFiles.length === 0) {
  console.log ("NO_WORK");
  process.exit (0);
}

console.log ("WORK_FOUND");
console.log (JSON.stringify ({ relevantFiles }, null, 2));
process.exit (1);
```

最佳实践：

| 做法 | 原因 |
|---|---|
| 先用脚本判断是否有工作 | 降低成本 |
| 只检查过去 24 小时 | 控制上下文大小 |
| 用 watched paths 限定范围 | 避免 Agent 过度探索 |
| 无工作时只写 log | 避免无意义运行 |
| 有工作时再唤醒 Agent | 提高 Loop 的投入产出比 |

#### 11. 这个实例的完整最佳实践总结

##### 设计原则

1. **先写 Loop Contract，再写 Agent Prompt**
   - Contract 定义目标、边界、SOP。
   - Prompt 只是唤醒 Agent 的入口。

2. **State 和 Logs 分开**
   - State 是当前认知。
   - Logs 是每次运行的不可变历史。

3. **用 Combo Trigger 降低成本**
   - cron 只触发脚本。
   - 脚本判断有无真实工作。
   - 有工作才唤醒 Agent。

4. **低风险自动化，高风险人工审查**
   - typo、路径、链接可以自动合并。
   - API、安全、计费、法律文档必须人工审批。

5. **Verifier 必须产出证据**
   - 命令输出。
   - 检查结果。
   - artifact 链接。
   - PR 描述中的风险说明。

6. **每 5 到 10 次运行进化一次 Loop**
   - 优化 trigger。
   - 把重复 SOP 脚本化。
   - 更新 watched paths。
   - 收紧或放宽边界。

7. **不要让 Agent 重新发现同样的问题**
   - 失败原因写入 Logs。
   - 当前假设写入 State。
   - 下次运行从已有认知继续。

## 口播总结（1）

### 2026-08-03 01:39:23

#### 如何设计真正能工作的智能体循环

这份材料的核心，是介绍怎样把人工智能智能体，从“被人一次次下指令的工具”，设计成能够自己找任务、执行、检查，并持续改进的循环系统。接下来你会听到，这类循环系统的基本结构、触发方式、质量保障方法，以及它们在工程和客户运营中的实际案例。

##### 一、真正的循环，不是一次演示，而是持续工作的系统

首先，真正有效的智能体循环，应该能够在没有人持续盯着的情况下，稳定地产出结果。

通俗地说，循环就是让智能体按照固定节奏醒来。它先检查系统里有什么工作，再挑选任务，完成任务，验证结果，最后把经验记录下来，供下一轮使用。它不是简单地让智能体“再试一次”，而是让整个系统越来越清楚该做什么、怎么做，以及什么情况下必须请人介入。

材料中提到，作者所在团队的循环系统已经连续运行了几个月。比如，代码库里的智能体每隔三十分钟醒来一次，自动扫描代码中的改进机会和错误，检查服务器日志，然后提交代码变更请求，也就是通常所说的 PR。另一个验证智能体会完整测试这个 PR，并附上测试证据，供人审核。对于低风险修改，系统甚至可以直接合并。

与此同时，客户关系管理循环，也就是 CRM 循环，会每天扫描用户群体，找出适合联系和培养的用户。支持工单则可以自动处理，而且不受用户使用哪种语言的影响。作者特别强调，这些都不是演示视频里的假流程，而是真正在公司业务中运行的系统。

不过，写出一个能运行的循环，只是最简单的部分。真正困难的，是设计足够可靠的安全边界，让人可以暂时离开，而系统仍然能够安全工作，并且随着时间推移不断改进。

##### 二、循环的第一层，是一份清楚的“循环契约”

接下来，设计循环的基础，是先写清楚一份“循环契约”。它可以理解成这个循环的宪法，规定系统的目标、权限和工作方法。

在实际做法中，团队通常用一个 Markdown 文件来保存这份契约，同时保存循环当前的状态和运行记录。这样，这个文件就不只是说明文档，也是循环的长期记忆。

一份好的循环契约，至少要回答三个问题。

首先是目标。也就是，什么结果才算成功，系统有没有明确的终点。比如，是要修复一个具体错误，还是要持续提升代码健康分数。

第二是边界。要明确哪些事情智能体可以自己完成，哪些事情必须升级给人处理。比如，低风险的格式修复可以自动合并，但涉及核心业务逻辑的修改，就必须人工审核。

第三是 SOP。SOP 是“标准操作流程”的缩写，意思是每次执行任务时，都应该遵循的一套固定步骤和原则。它可以规定智能体如何调查问题、如何创建分支、如何测试，以及什么时候提交结果。

这三个部分的作用，是把“让智能体自己处理”变成“让智能体在明确规则内处理”。没有目标，智能体不知道什么叫完成；没有边界，智能体可能做出超出权限的决定；没有流程，同一类任务每次都可能采用不同做法。

##### 三、状态和日志要分开，避免循环每天重复犯错

有了契约之后，循环还需要记住自己过去做过什么。这里要区分两个概念：状态和日志。

状态可以理解为一张精简的当前快照。它记录智能体现在的判断和假设、还没有处理的任务、已经提交但需要跟进的变更，以及当前最重要的问题。状态应该尽量小，而且只保留对下一轮真正有用的信息。

日志则不同。日志是每一轮运行之后追加的完整记录。它不应该被反复改写，而是按照时间顺序，记录每次发生了什么、尝试了什么、结果怎样。

这样区分非常重要。因为如果没有日志，智能体每天醒来时，可能会重新调查同一个问题，重复尝试已经失败的方法，浪费模型调用资源，也浪费人的审核时间。状态负责告诉它“现在是什么情况”，日志负责告诉它“过去发生过什么”。

对于规模较小的循环，这些内容通常可以放在同一个 Markdown 文件里。随着循环运行，这份文件会不断更新，成为循环的长期记忆。

##### 四、两个实际案例：代码修复循环和客户运营循环

下面看第一个工程案例。这个循环叫作 React Doctor 检查循环。

React Doctor 是一个可以在代码库中运行的命令行工具。它会自动识别一些关键问题，列出问题清单，并给出一个健康分数。团队设置的循环是每天运行一次扫描，然后自动挑选最严重的问题进行修复。

这个循环的契约文件会写清楚几个关键规则。比如，修复工作必须交给子智能体，在隔离的工作区中进行，不能直接影响主代码；修复完成后必须经过验证；哪些改动可以自动合并，哪些改动必须交给人审查，也要提前写清楚。

文件里还会保存标准操作流程、当前已经打开或合并的任务、需要继续跟进的事项，以及每次运行后的追加日志。每天智能体醒来时，就会把这份文档作为上下文，开始下一轮工作。

为了观察效果，团队还做了一个内部仪表盘，跟踪哪些 PR 被打开、哪些被合并，以及代码健康分数是否随着时间提高。这里的数据意义不只是“自动修了多少问题”，更重要的是能看出这个循环是否真的让代码库变得更健康。

第二个案例，是 CRM 生命周期循环。

CRM，也就是客户关系管理，指的是围绕用户进行分组、联系、培养和转化。这个循环每天查看活跃用户，再根据用户行为把他们分成不同群体。

比如，有些用户是规模较小但有影响力的人，适合联系他们做联盟合作或推广；有些用户根据大语言模型，也就是 LLM，分析过的对话日志来看，明显遇到了问题，需要及时安抚；还有一些用户使用得很投入，但还没有升级付费，适合进行针对性沟通。

不同用户群体对应不同的自动化权限。低风险、规则明确的消息，可以由智能体直接发送；风险更高，或者更需要判断语气的消息，则只由智能体起草，最后等待人来批准。

这个循环同样拥有目标、标准流程、边界、当前状态和时间线。尤其是边界部分，要明确哪些信息可以使用，哪些沟通内容必须人工确认，以及研究用户时需要避免哪些潜在问题。

由此可以看到，循环契约并不只适用于写代码。只要一个任务能够被拆成“观察、判断、执行、检查和记录”，它就可能适合用循环系统来管理。

##### 五、触发方式不同，循环的成本和效果也不同

接下来，是循环设计中的另一个关键部分：触发器。

触发器就是负责唤醒智能体的机制。不同任务，应该选择不同的触发方式。材料中主要介绍了四种。

###### 第一种，是连续循环

连续循环类似一个持续运行的程序。只要目标还没有完成，智能体就继续查看契约、执行下一步，直到任务完成，或者达到预设的最大轮次和模型资源上限。

这种方式适合有即时反馈的任务。比如修复一个错误，或者按照明确规格开发一段复杂软件。每一步做完后，系统马上就能测试结果，因此适合持续推进。

但它不适合所有场景。如果任务本身没有明确终点，或者反馈很慢，连续循环可能会一直消耗资源。

###### 第二种，是定时任务

定时任务，也就是常说的 cron 任务，会按照固定时间间隔唤醒智能体。例如每小时一次、每天一次，或者每隔三十分钟一次。

它适合定期扫描代码、检查用户变化、更新文档等任务。材料提到，云端运行的自动化和当前会话中的定时循环，在形式上有所不同，但本质上都是按照时间把智能体叫醒。

连续循环和定时循环通常可以直接通过 Codex 或 Claude Code 这类工具提供的功能实现，因此适用范围已经很广。

###### 第三种，是事件触发

事件触发不是看时间，而是等事情发生。

比如，收到新邮件时，立刻唤醒智能体处理；服务器发生故障时，立即让智能体参与排查和修复。这种方式特别适合需要及时响应的任务。

但目前一些常用的编码智能体工具，并不能直接支持所有事件触发场景。一个常见做法，是运行一个本地后台服务，也就是 daemon。这个服务会暴露一个网址，外部系统通过 webhook，也就是“事件通知接口”，把消息发送过来。后台服务收到通知后，再唤醒智能体。

这种方式能够把邮件系统、服务器监控系统等外部事件，连接到智能体循环中。

###### 第四种，是组合式工作流

材料认为，最实用的一种方式，往往是“定时检查加程序判断”的组合工作流。

它仍然按照固定间隔运行，但不一定每次都直接唤醒智能体。更高效的做法是，先运行一个小脚本，从数据源中检查有没有真正的新任务。只有发现新工作时，才启动智能体；如果没有变化，就跳过这一轮。

例如，在支持收件箱循环中，团队每三十分钟从 Intercom 获取最近的更新。如果确实有新的工单或消息，就让智能体集中处理；如果没有新的变化，就不启动智能体。

这样做的意义很直接：可以把多项新工作批量交给智能体，同时避免没有工作时反复调用模型。因此，它能够明显降低成本和模型资源消耗。

材料提到，前两种触发方式通常可以直接使用现成工具，而事件触发和组合工作流，则需要自己编写脚本，并运行后台服务。作者团队还把内部的循环管理工具开源了，让团队可以在本地集中管理循环契约、状态、日志和触发器。

所以，触发器并不是一个技术细节，而是会直接影响循环的响应速度、稳定性和运行成本。

##### 六、复杂任务要拆成执行者和验证者

触发器唤醒智能体之后，智能体还需要按照合理的角色分工来工作。

一个完整的任务流程通常有三个阶段。第一，收集信号，找到并确定优先级最高的工作。第二，执行任务。第三，检查结果，确认任务真的完成。

对于简单任务，一个智能体可以同时完成这三步。但对于复杂、重要、风险较高的工作，最好拆成不同角色。

常见结构是：先由一个“协调智能体”负责接收任务、调查背景、制定计划；然后由多个“执行智能体”分别处理具体工作。每个执行智能体都在隔离的工作区中运行，因此多个任务可以并行推进，也不容易互相干扰。

执行完成后，还要交给“验证智能体”。验证智能体不能只看执行者说“完成了”，而要真正运行测试，检查结果，并把证据附在 PR 中。这样，人类审核者就可以更快判断这项工作是否可靠。

这套验证机制，是高风险循环的前提。尤其当任务涉及生产环境代码，或者要直接向真实客户发送消息时，系统必须能给出容易审查的证据。

为了让验证更高效，作者提到可以使用浏览器自动化工具，例如 Playwright，去测试页面并录制图片或视频证据；也可以使用远程沙盒环境，让多个智能体同时运行测试，而不受本地开发服务器数量的限制。

材料还提到了一个用于配置验证环境的开源技能包。它的作用，是帮助智能体在实际代码库中搭建合适的测试和验证系统。

最终，所有执行结果、验证结果和新的发现，都要写回循环契约文档。这样下一轮启动时，系统就不是从零开始，而是带着上一轮的经验继续工作。

##### 七、循环还要能够改进自己

更重要的是，一个刚开始运行的循环，通常不会一开始就设计得很完美。因此，还需要增加一层“进化循环”。

进化循环的意思是，定期让另一个专门的智能体，回顾这个循环过去的表现，并提出改进。

例如，它可以检查触发方式是否浪费成本，某些重复性的操作是否应该改写成脚本，标准流程是否过时，当前状态是否混乱，或者边界规则是否需要调整。

具体做法是，每运行五到十轮，就启动一次专门的进化会话。这个会话会读取当前的循环配置、过去的状态和日志，以及之前的原始对话记录。然后，它判断最值得改进的地方，并修改循环契约、状态内容，或者触发脚本。

支持工单循环就是一个例子。它在一次进化过程中发现，自己不应该每隔一段时间就直接唤醒智能体，而应该先用程序检查是否真的有新消息。于是，它增加了程序化触发器，只在有必要时才启动智能体。

这说明，循环的目标不只是自动完成任务，还要持续优化“如何发现任务”和“如何完成任务”。进化循环解决的，正是系统长期运行之后的效率和质量问题。

##### 八、最后一个例子：自动维护文档

最后，材料开始介绍一个文档维护循环。

很多团队都会把文档、云端知识库、代码说明文件，作为智能体理解项目背景的依据。但这些内容很容易过时。代码已经更新了，安装方式变了，示例和操作手册却可能还停留在旧版本。

因此，可以设置一个简单的每日循环，让智能体检查过去二十四小时内发布了哪些改动，再把这些改动与 README、安装指南、示例和运行手册进行对照。

这个循环的核心结论是：文档也应该像代码一样，被持续检查和维护，而不是只在项目开始时写一次。材料在这里的讲解尚未继续展开，但已经明确了它的基本思路：让智能体定期比较“系统实际发生的变化”和“文档记录的内容”，及时发现不一致。

##### 结尾：四个最值得记住的结论

最后，回顾这份材料中最重要的几点。

第一，智能体循环的核心，不是让模型不断重复执行，而是让它能够自己找工作、完成工作、验证结果，并把经验留给下一轮。

第二，循环必须有一份清楚的契约。契约要写明目标、边界和标准操作流程；同时还要区分当前状态与历史日志，避免系统每天重复调查同样的问题。

第三，触发方式要根据任务选择。连续循环适合有即时反馈的明确任务；定时任务适合周期性检查；事件触发适合紧急响应；定时检查加程序判断的组合工作流，则更节省成本。

第四，凡是涉及生产代码或真实客户的高风险任务，都需要验证者和可审查的证据。只有这样，人类才能放心把一部分决策和执行权交给智能体。

第五，循环不是一次性工程。运行五到十轮后，就应该回顾日志，改进契约、流程和触发器，让系统在长期运行中变得更准确、更省资源，也更可靠。

## 深度解读（1）

### 2026-09-18 00:32:23

#### 真正可用的 Agent Loop，不是“更自主”，而是可审计的持续运营系统

这段分享最有价值的地方，不是展示 Agent 半夜自动提交 PR，而是给出了一套经过一个月实践的工程化框架：**目标与权限契约、持续状态、合适的触发器、独立验证，以及定期改进机制。**它把“让模型反复执行任务”推进成了“让一项工作可以长期无人值守”。

这套方法并不神秘，甚至很像 CI、定时任务和工作流引擎。真正的新意在于：它开始回答 Agent 产品最难的问题——**怎样让一个具有不确定性的执行者，进入可控、可追踪的生产流程。**

##### 把概率型 Agent 放进确定性的外壳

作者把每个 Loop 的目标、操作边界和 SOP 写入一个 Markdown 文件，同时维护两类记忆：精简的当前状态，以及只追加、不改写的运行日志。

两者不能混为一谈。状态是 Agent 下一轮需要直接使用的“工作记忆”，例如当前假设、待办和需要回访的变更；日志则用于追责、复盘和发现重复失败。如果每次都把全部历史塞进上下文，成本会不断上升，噪声也会淹没有效信息；如果完全没有历史，Agent 又会反复调查同一问题。

更重要的是，作者没有让 LLM 负责所有环节。以客服任务为例，先用普通脚本查询最近半小时是否有新消息，确有任务时才唤醒 Agent。**确定性程序负责筛选和调度，LLM只处理需要理解、判断与生成的部分。**这比单纯提高模型能力更能降低成本和意外，也是可以迁移到大量 Agent 场景的设计原则。

##### 触发方式应由反馈周期决定

文章区分了四类触发器：持续循环、定时运行、事件触发，以及“定时检查、有任务才调用 Agent”的组合方式。

这不是实现细节，而是任务性质的分类。代码修复有测试结果作为即时反馈，适合连续循环直到通过；文档维护和用户分群变化较慢，适合每日执行；线上事故需要事件触发；客服整理则更适合先聚合一批新消息再处理。

很多 Agent 产品的问题，未必是模型做不好，而是**在错误的时间、以错误的粒度唤醒了模型**。过度频繁会浪费 token 并制造无意义动作，过度批处理又会损失时效性。设计 Loop 时，首先应问的不是“多久跑一次”，而是任务到达频率、响应期限、可验证性和单次启动成本分别是什么。

##### 自主权的上限，由验证能力决定

作者反复强调 verifier：执行 Agent 完成工作后，通过测试、截图、视频或其他证据证明结果，再由人审批；只有低风险修改可以自动合并。这是整套方案最关键的判断：**自动化程度不应由 Agent 看起来多聪明决定，而应由错误是否可检测、可恢复，以及证据是否便于人工复核决定。**

因此，生产代码比开放式市场判断更适合闭环自动化：前者有测试、静态检查和回滚机制，后者通常缺少快速、客观的反馈。CRM Agent 自动联系真实用户尤其需要谨慎，因为语言是否“合理”不等于品牌风险、隐私使用和用户感受都合格。

所谓 evolve loop——每运行若干次后，让 Agent 根据日志改写契约、状态或触发脚本——也只有在外部指标可靠时才算“自我改进”。否则，它可能只是根据自己的叙述优化自己的流程，甚至逐渐绕开原有约束。更稳妥的做法是允许它提出变更，但对权限边界、验证规则和关键指标保留人工审批。

##### 机会不只是再做一个 Agent 平台

作者开源的管理工具指向一个潜在产品层：集中管理 Loop 的契约、状态、触发器和运行记录。但这类产品的竞争对象不仅是其他 Agent 框架，还包括 cron、CI/CD、工作流平台和内部脚本。真正可能形成价值的，不是“可以循环调用模型”，而是**权限控制、运行可观测性、证据归档、成本核算、失败恢复和跨 Loop 治理**。

文章尚未提供失败率、人工审核时间、成本变化等量化数据，因此“能稳定运行”和“会持续变好”仍主要是作者的经验判断。值得保留的结论更克制：Agent Loop 的成熟标志不是运行次数更多，而是每一次行动都有明确授权、可靠反馈和可追溯证据。只有这三件事成立，“无人值守”才不是把操作成本换成事故成本。

## 默认总结（1）

### 2026-09-18 01:45:33

##### 一句话看懂

真正可长期运行的 AI 自动化循环，不是让智能体反复执行提示词，而是建立一套包含明确规则、状态记忆、合适触发器和结果验证的系统。

##### 关键内容

- **先写“循环契约”**：明确目标、权限边界和标准流程，例如哪些低风险修改可自动合并，哪些必须交给人工审批。
- **保留状态与日志**：状态记录当前假设、待办和后续事项；日志按次追加执行结果，避免智能体反复调查同一问题。作者通常将这些内容放在一个持续更新的 Markdown 文件中。
- **按任务选择触发方式**：可连续运行、定时运行、事件触发，或先由脚本检查是否有新任务再唤醒智能体。作者认为最后一种更节省成本和 Token。
- **高风险工作必须验证**：复杂任务可拆成“统筹—执行—验证”角色；验证者负责测试并附上截图、录像等证据。每运行 5—10 次，还可让专门智能体根据历史日志优化规则和触发脚本。

##### 通俗解读

核心不是让 AI “更自主”，而是让它在可检查、可追踪的范围内自主工作。就像给员工的不只是任务，还包括权限、交接记录、验收标准和复盘机制。文中的效果来自作者团队近一个月的内部实践，并非普遍适用的定论。
