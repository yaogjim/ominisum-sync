## 分析要点

- **核心高价值点**：在大规模AI辅助重构前，先让AI梳理耦合点并产出详细spec和阶段文档，再逐阶段实施。
- **留存建议**：短期参考后可归档（包含AI辅助前端重构、需求拆解、UI描述和Storybook走查等实践经验，可作为类似项目的流程参考。）

**知识要点**

- 不同AI模型适合承担不同任务，例如Codex更适合架构梳理和计划文档，Claude Opus更适合前端实现和交互理解。
- 非设计师做UI时，可以先从用户路径和功能优先级出发，用竞品和成熟软件作为参考。
- 向AI描述UI交互时，使用准确的组件名称比自然语言长描述更高效、更稳定。
- Storybook适合枚举组件的正常态、空态、加载态、错误态、禁用态，降低AI修改导致样式回退的风险。

**行动项**

- 在AI重构前先生成一份代码耦合点清单和分阶段重构spec。
- 为新增或重构的核心UI组件补充Storybook，并覆盖主要状态。
- 整理常见UI组件名称和交互模式，作为后续与AI沟通的提示词词库。

#### 不是设计师怎么设计 UI

不是设计师的话就先不用考虑美不美的事情，为你的功能服务，让人能看得过去，整体规规矩矩的是第一要务。自己不会设计，但总归是用过很多软件，很多被设计师设计过的软件。不懂设计语言设计系统，不知道该怎么交互的时候就去看别的软件。但不能光看，要主动分析为什么会这样设计。前提你看的是好软件。 对于 Lody 这次重新设计难度还好，因为功能都是已有的功能，自己又是自己软件的用户。那么在对这样的有限集去做考虑的时候就可以简单地带入用户视角，一进来希望看到什么，哪些是最热的路径，哪些功能希望是最快被触达的，哪些可以增加层级做更明确且符合直觉的区分。这一步是最需要花费时间多多考虑的。 大概考虑好之后脑子里就有了几个蓝图，大概的结构。我就拿 iPad 去把所有的主要的界面和组件画了出来。

#### 怎么向 AI 描述想要的交互

接下来我们就开始真的让 AI 编写前端代码了，我们有了“真实”的渲染图和一些交互的想法，但是该如何有效地让 AI 理解你的想法。 如果你没有做过设计或者前端，那你就需要去

[shadcn ui](https://ui.shadcn.com/docs/components) 或者其他的组件库的官网，把所有的组件都看一遍，拿着你的渲染图上不知道怎么描述的组件挨个去比对，去组件的网站上挨个去点一点看效果是不是你想要的，然后记住这个组件的名称。 和 AI 描述的时候就不用说

> 我想要一个问题和答案的列表，默认只展示问题，点击之后可以在下面显示答案，点击别的问题时候已经展开的需要自动收起。不同的问题之间有个分割线分开。 问题和答案分别是 Question A，Answer A；......

> 使用 Accordion 组件，Trigger 和 Content 分别是 Question A，Answer A；......”  
> 使用手风琴组件，触发部分和内容部分分别是 Question A 和 Answer A；......”

非专业的朋友学习 vibe coding 就可以在日常工作的时候浏览网站的时候看到这种专业名词就记下来，不但节省 tokens 而且 AI 理解得更加清楚。

让 Opus 复原渲染图时就可以从上到下描述一遍当前图上的所有的组件，它是什么它的功能是什么你希望的交互效果是什么。

第一遍 AI 应该只能复现个大概，很多地方会有偏差，先看一下大概的架构和主题风格是不是你想要的，然后有出入的地方就需要一点一点继续磨，就全看个人对细节的把控了。

![Image](https://pbs.twimg.com/media/HJOtxWJaAAAFT8u?format=jpg&name=large)

磨\~磨\~磨\~

在磨 UI UX 的时候，当前阶段使用 web 技术栈的好处就体现出来了，这时候就可以使用 codex 的预览模式，cursor 的 design 模式或者是 Lody 的预览模式。在 Lody 上甚至可以直接在手机上给对应的组件直接评论发送给 Agent。 web 可以 HMR 热更新，改完就能看到效果，节省很多时间。

#### 善用 Storybook 便于走查

组件编码完成不代表生命周期的结束，AI随时可能把已经设计好的样式或者交互给搞坏。最后推荐一下

[Storybook](https://storybook.js.org/)，它是用于独立展示和测试构建 UI 组件的，不依赖真实的接口，非常适合同屏展示组件的所有可能的状态，正常态、空态、加载态、错误态、禁用态等等。我们在 AGENTS.md 中就添加了一条，新增的组件就要创建枚举所有状态的 Storybook，之后就不需要特别地每次都端到端地测试组件样式。都在 Storybook 中看就行，而且很多不会注意的空状态，异常状态也都不会被忽略。

#### 怎么用 Codex + Claude Code 重构前端 UI

##### 一、总结

作者分享了用 **Codex + Claude Code/Opus** 重构 Lody 移动端 UI 的经验。

核心流程：

1. **先理解模型能力**
   - Codex/GPT 更适合：架构梳理、找耦合、写计划、拆任务。
   - Claude Opus 更适合：写前端、理解交互、实现 UI。

2. **把大量时间花在文档和 Spec 上**
   - 先让 AI 扫描代码，找出移动端和桌面端耦合点。
   - 再让 AI 写重构计划。
   - 把大任务拆成多个阶段，逐步执行。

3. **先设计，再编码**
   - 不懂设计也没关系，先从用户路径和功能优先级出发。
   - 参考优秀 App 的交互。
   - 用 iPad 画草图，再让 Codex 生成接近真实效果图。

4. **用专业组件名描述需求**
   - 不要含糊描述“点开收起列表”。
   - 直接说：使用 `Accordion`、`Trigger`、`Content`。
   - 这样 AI 更容易理解，也更省 token。

5. **反复打磨 UI**
   - AI 第一版通常只能做到大概。
   - 后续需要持续调整布局、样式、交互细节。

6. **用 Storybook 管理组件状态**
   - 展示正常态、空态、加载态、错误态等。
   - 防止 AI 后续改代码时破坏已有 UI。

---

##### 二、深入浅出解读

这篇文章本质上讲的是：

> 不要把 AI 当成“直接写代码的工具”，而要把它当成“协作团队”。

###### 1. Codex 像架构师

它适合先帮你看项目：

- 哪些代码耦合严重？
- 哪些组件该拆？
- 哪些逻辑该复用？
- 重构分几步比较稳？

也就是说，Codex 更适合做 **规划和拆解**。

---

###### 2. Claude Opus 像前端工程师

等架构和文档清楚后，再让 Claude 写 UI。

因为前端 UI 不是只写代码，还要理解：

- 按钮放哪里？
- 哪个区域更重要？
- 点击后怎么反馈？
- 移动端手势怎么设计？

Claude 在这类交互理解上更强。

---

###### 3. 文档比代码更重要

作者反复强调：**先写计划，再写代码**。

因为大重构最怕的是：

- AI 理解错需求；
- 改着改着范围失控；
- 旧功能被破坏；
- 桌面端和移动端互相影响。

所以要先让 AI 产出文档，再人工 review。

这其实是在给 AI “上轨道”。

---

###### 4. 不会设计，也可以做出可用 UI

作者的思路很实用：

- 不追求一开始就很美；
- 先保证功能清楚、路径顺畅；
- 多看成熟产品怎么做；
- 画草图表达结构；
- 再让 AI 帮忙生成视觉稿。

重点不是“设计天赋”，而是：

> 你要知道用户最想先做什么。

---

###### 5. 和 AI 沟通要用“行业词”

比如你想要一个可展开列表。

差的说法：

> 我要一个点开问题显示答案的列表。

好的说法：

> 使用 Accordion 组件，Trigger 是问题，Content 是答案。

这就像和装修师傅沟通：

- 你说“弄个好看的墙”，很模糊；
- 你说“做奶油风、哑光乳胶漆、无主灯”，就清楚很多。

---

##### 三、我的意见

这篇文章最有价值的点是：

> AI 编程不是少思考，而是把人的思考前置。

很多人用 AI 写代码失败，不是模型不行，而是：

- 没有明确需求；
- 没有拆任务；
- 没有设计稿；
- 没有验收标准；
- 一上来就让 AI 改一大片代码。

更好的方式是：

```text
先让 AI 理解项目
再让 AI 写计划
人工确认方向
分阶段实现
每阶段 review
最后用 Storybook 保底
```

如果是中大型前端重构，我建议采用这个组合：

| 阶段 | 推荐做法 |
|---|---|
| 梳理代码 | Codex |
| 写重构方案 | Codex |
| 拆任务 | Codex |
| 画草图 | 人 |
| 生成视觉参考 | Codex |
| 写 UI 代码 | Claude Opus |
| 组件验收 | Storybook |
| 最终打磨 | 人 + AI |

一句话总结：

> Codex 负责想清楚怎么拆，Claude 负责把 UI 写出来，人负责判断好不好用。

## 结构化（1）

### 2026-06-01 10:11:10

##### 主旨概括

作者分享了如何借助 **Codex 和 Claude Code/Opus**，通过 “vibe coding” 的方式，对 Lody 的移动端前端 UI 和架构进行较大规模重构。核心经验是：**先用 AI 梳理架构和写规划文档，再结合手稿、渲染图和组件库语言，让 AI 高效落地 UI 与交互。**

---

##### 1. 重构背景：移动端只是“适配”，不是“设计”

Lody 因为技术栈和人力原因，网页端、桌面端、移动端都用 Web 统一构建。

早期主要先做网页端，后来逐步加桌面端和移动端，但移动端实现比较粗糙：

- 代码中大量使用 `isMobile()` 判断移动端逻辑；
- 移动端整体布局基本是把桌面端变窄；
- 额外加了一个 sidebar；
- 虽然“能用”，但交互、字体、按钮等都不适合移动端。

随着远程控制和多端同步能力趋于稳定，作者决定提高移动端优化优先级。

这次重构目标有两个：

1. **架构层面**：把多端通用部分组件化，新增移动端独立入口，让移动端布局与旧布局解耦；
2. **体验层面**：重新设计移动端 UI 和交互。

---

##### 2. 先理解不同 AI 模型的特点

作者强调，在做大任务前，要先了解不同模型各自擅长什么。

以 Codex 和 Claude Code/Opus 为例：

| 模型 | 擅长 | 不擅长 |
|---|---|---|
| GPT / Codex | 架构梳理、生成图像、找 bug 真实原因、复杂后端或业务逻辑 | 写前端、写简洁文档 |
| Claude Opus | 写前端、理解交互、中小任务、写文档总结 | 复杂且需要持续深入的任务、不能遗漏细节的任务 |

作者认为这些差异不是“80 分和 90 分”的区别，而是“能不能用”的区别。

因此，做大任务前要先试探模型边界，尤其每次模型更新后都需要重新测试。不同模型组合使用，也就是异构 multi-agent，能明显提升生产力。

---

##### 3. 把大量时间花在文档和 Spec 上

作者没有一上来就让 AI 写代码，而是先让 Codex 梳理当前代码库中移动端耦合的位置。

结果大约找出了 **40 个存在耦合的文件**。

之后作者基于 Codex 生成的重构文档，继续调整：

- 文件如何拆分；
- 命名方式；
- 移动端路由方式；
- 移动端组件划分；
- 共享组件和移动端专用组件的边界。

最终形成了一篇接近 **1000 行的计划文档**。

随后作者让 Codex 把大任务拆成多个阶段：

1. 再次搜索确认耦合位置，明确共享/分端维护边界；
2. 拆出纯移动端使用、无耦合的组件；
3. 重构 chat、session、settings、archive 等核心功能的移动端布局；
4. 评估新的移动端组件、手势和 UI 设计方案；
5. 测试可访问性、设备矩阵，并进行渐进发布。

作者会在每个阶段完成后，再继续和 Codex 讨论下一阶段方案，并通过 diff review 进行评论和调整。

---

##### 4. 非设计师如何设计 UI

作者承认自己不是设计师，因此不追求一开始就做出特别漂亮的设计，而是先满足三个目标：

- 服务功能；
- 看起来规整；
- 用户能顺畅使用。

不会设计时，可以参考优秀软件的设计，但不能只看表面，要主动分析：

- 为什么入口放这里；
- 为什么这个路径更短；
- 哪些功能被优先展示；
- 哪些功能被隐藏到更深层级。

对于 Lody 来说，功能都是已有的，作者自己也是用户，所以可以从用户视角思考：

- 用户一进来最想看到什么；
- 哪些是最高频路径；
- 哪些功能应该最快触达；
- 哪些功能可以增加层级区分。

在想清楚大致结构后，作者用 iPad 把主要界面和组件画成手稿。

---

##### 5. 用手稿让 Codex 生成渲染图

手稿能表达内容和布局，但缺少样式和风格。

于是作者把手稿发给 Codex，并描述自己想要的大致风格，让 Codex 模拟真机渲染图。

这个过程需要不断：

- 调整 prompt；
- 多次生成；
- 对比手稿和生成图；
- 直到获得接近预期的视觉效果。

当有了大致真实的渲染图后，Codex 那边的架构重构也差不多完成了。作者 review diff 后，再开启新的对话，请 Claude Opus 负责前端实现。

作者特别提到：**Opus 很擅长写前端。**

---

##### 6. 如何向 AI 描述想要的交互

作者认为，如果不是设计师或前端开发，要让 AI 理解交互，最好学会使用组件库里的专业术语。

例如，可以去看：

- shadcn/ui；
- 其他组件库官网。

把常见组件都浏览一遍，看到类似自己想要的交互，就记住组件名称。

比如不要啰嗦地描述：

> 我想要一个问题和答案列表，默认只展示问题，点击后显示答案，点击别的问题时之前展开的自动收起，不同问题之间有分割线……

可以直接说：

> 使用 Accordion 组件，Trigger 和 Content 分别是 Question A、Answer A……

这样做有两个好处：

- 节省 tokens；
- AI 更容易准确理解需求。

让 Opus 复原渲染图时，作者会从上到下描述每个组件：

- 它是什么；
- 有什么功能；
- 希望有什么交互效果。

第一版通常只能复现大概效果，后面需要不断根据细节继续调整。

---

##### 7. 反复打磨 UI/UX，并利用 Web 技术栈优势

作者强调，AI 生成的第一版 UI 往往会有偏差，需要持续打磨。

打磨时，Web 技术栈的优势很明显：

- 可以使用 Codex 预览模式；
- 可以使用 Cursor design 模式；
- 可以使用 Lody 自己的预览模式；
- 支持 HMR 热更新，改完马上看到效果。

在 Lody 中，作者甚至可以直接在手机上对具体组件评论，并发送给 Agent，让 AI 根据反馈继续修改。

这大大节省了 UI 调整时间。

---

##### 8. 用 Storybook 管理组件状态，防止后续被 AI 改坏

作者提醒：组件写完并不代表结束，因为 AI 后续修改时，可能会破坏已经设计好的样式或交互。

因此他推荐使用 **Storybook**。

Storybook 可以独立展示和测试 UI 组件，不依赖真实接口，适合展示组件的各种状态，比如：

- 正常态；
- 空态；
- 加载态；
- 错误态；
- 禁用态。

作者在 `AGENTS.md` 中添加了一条规则：

> 新增组件必须创建枚举所有状态的 Storybook。

这样之后就不必每次都通过端到端测试检查组件样式，直接在 Storybook 中统一查看即可，也能避免遗漏空状态、异常状态等细节。

---

##### 总结

作者的核心方法可以概括为：

1. **先让 Codex 做架构梳理和重构计划**；
2. **用详细文档拆解大任务，减少 AI 误解**；
3. **自己从用户视角设计移动端结构和路径**；
4. **用手稿 + Codex 生成渲染图**；
5. **用 Claude Opus 编写和打磨前端 UI**；
6. **通过组件库术语精准描述交互**；
7. **用预览和 Storybook 持续检查组件质量**。

这篇文章的重点不是展示一个完美设计，而是说明：即使不是专业设计师或前端，也可以通过合理分工、清晰文档和持续反馈，借助 AI 完成较大规模的前端 UI 与架构重构。
