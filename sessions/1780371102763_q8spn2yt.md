## 解读（1）

### 2026-06-02 03:29:59

##### 1. 总结

宝玉的观点是：

> **不要指望一个 AI 模型样样最强。**

不同模型各有优势，正确用法是：

- **多用几个模型**
- **了解各自长处**
- **按任务组合使用**
- **针对模型特性调提示词**

他认为：

- **Opus 4.8**
  - 写作一般
  - UI 设计、UI 实现不错
  - 系统设计、任务规划能力强
- **GPT-5.5**
  - 可与 Opus 对比使用
  - 在某些实现任务上未必优于 Opus
- **Claude Design**
  - 适合先做设计，再交给不同模型实现

---

##### 2. 解读

这段话的核心不是“哪个模型最好”，而是：

> **AI 不是选老婆，而是组团队。**

一个模型可能：

- 写文章强
- 写代码一般
- 做 UI 很强
- 做计划很稳
- 处理复杂任务更靠谱

所以用 AI 时，不要迷信单一模型。

更好的流程是：

```text
先让一个模型做方案/设计
再让另一个模型实现
最后用第三个模型检查和优化
```

比如：

```text
Claude Design：做界面设计
Opus 4.8：实现 UI / 做系统规划
GPT-5.5：补充代码 / 改写 / 检查
```

另外，同一个模型在不同工具里表现也会不同。

例如：

- Claude Code
- Cursor
- ChatGPT
- API Agent

它们的上下文、工具能力、提示词方式不同，结果也会不一样。

---

##### 3. 我的意见

我同意这个观点。

现在用 AI，最重要的不是问：

> “哪个模型最强？”

而是问：

> “这个任务适合哪个模型？”

建议普通用户这样用：

| 任务 | 用法 |
|---|---|
| 写作 | 多模型对比，选表达最自然的 |
| 编程 | 一个写，一个审，一个改 |
| UI 设计 | 先设计，再实现 |
| 复杂任务 | 先让 AI 做计划，再执行 |
| 重要内容 | 不要只信一个模型 |

一句话：

> **别追求万能模型，要学会搭配模型。**

会搭配的人，AI 效果会明显更好。

#### 文章主旨概括

宝玉认为：不要期待某一个 AI 模型在所有任务上都最强，正确做法是了解不同模型的长处，组合使用。以 Opus 4.8 为例，它在写作上不一定突出，但在 UI 设计、UI 实现、系统设计和任务规划方面表现较好。

##### 1. 对“Opus 4.8 被骂”的回应

原文引用了一条批评 Anthropic 和 Opus 4.8 的推文，认为其产品水平不高，甚至预测 Anthropic 三年内会消失或被收购。

宝玉对此并不认同，他的核心观点是：

- 不能用“一个模型是否全能”来判断它是否有价值。
- 每个模型都有自己的优势和短板。
- 用 AI 时应该“多模型组合”，根据任务选择合适的模型。

通俗来说，就是不要指望一个 AI 什么都第一，而是要像挑工具一样：写作、设计、编程、规划，分别找最合适的模型。

##### 2. Opus 4.8 的优势与短板

宝玉提到，Opus 4.8 在不同任务上的表现差异明显：

- **写作方面不太行**：尤其不应默认它在写作任务上一定强。
- **UI 设计和 UI 实现较强**：他认为 Opus 4.8 在这方面比 GPT-5.5 好很多。
- **系统设计和计划能力强**：复杂任务通常需要先做 Plan 和系统设计，Opus 4.8 在这类任务上质量较高。

例如，如果要做一个复杂项目，不能直接让模型开始写代码，而是应先让它做任务拆解、系统架构和执行计划，这正是 Opus 4.8 比较适合的场景。

##### 3. 推荐的使用方式：多模型组合

宝玉建议，不要只依赖单一模型，而是可以这样组合使用：

1. 先用 **Claude Design** 做 UI 设计；
2. 再把 Claude Design 的设计结果分别交给 **GPT-5.5** 和 **Opus 4.8** 实现；
3. 对比两个模型的实现效果，选择更好的结果。

这种方式的重点是：  
不是问“哪个模型最好”，而是看“哪个模型最适合当前任务”。

##### 4. Agent 和提示词也会影响效果

宝玉还强调，模型效果不仅取决于模型本身，也和使用环境、Agent、提示词有关。

关键点包括：

- 每个模型都有自己的特性；
- 需要针对不同模型重新设计提示词；
- 提示词要反复调优，不能一套提示词套所有模型；
- 如果在 **Claude Code** 和 **Cursor** 里使用 Opus 4.8，除写作外，其他任务效果基本没问题。

也就是说，如果觉得某个模型“不好用”，可能不只是模型问题，也可能是工具环境、提示词或使用方法不匹配。

#### 多模型使用观：不要找“最强模型”，要搭“模型组合系统”

##### 1. 启发

###### 核心观点

不要期待一个 AI 模型在所有任务上都最强。更有效的方式是：

> 把不同模型当成不同能力模块，识别它们各自的强项，然后组合使用。

这其实不是“选模型”，而是“搭系统”。

类似产品开发里的分工：

- 有的人擅长产品规划；
- 有的人擅长视觉设计；
- 有的人擅长工程实现；
- 有的人擅长文案表达；
- 有的人擅长代码 review。

AI 模型也是如此。

###### 对 AI/产品开发者的启发

过去很多人问的是：

> 哪个模型最好？

但更成熟的问题应该是：

> 在我的工作流里，哪个模型适合承担哪一段任务？

比如：

| 任务阶段 | 更应该关注的能力 |
|---|---|
| 需求分析 | 理解复杂上下文、拆解问题 |
| 产品规划 | 结构化思考、方案设计 |
| UI 设计 | 审美、布局、组件组织 |
| 前端实现 | 代码生成、设计还原 |
| 后端实现 | 架构能力、稳定性 |
| 文案写作 | 表达、风格、语言控制 |
| 代码审查 | 严谨性、错误发现 |
| Agent 执行 | 工具调用、规划、容错 |

所以，AI 使用的关键不是“忠诚于一个模型”，而是建立一套“多模型协作机制”。

##### 2. 高价值信息深挖

###### 2.1 模型能力不是线性排序，而是能力矩阵

很多人会把模型简单分为：

> A 比 B 强，B 比 C 弱。

但实际情况更像这样：

| 能力维度 | 模型 A | 模型 B | 模型 C |
|---|---:|---:|---:|
| 写作 | 强 | 中 | 弱 |
| UI 设计 | 中 | 强 | 强 |
| 代码实现 | 强 | 中 | 强 |
| 系统设计 | 中 | 强 | 中 |
| 长上下文理解 | 强 | 中 | 强 |
| 工具调用 | 中 | 强 | 中 |
| 稳定性 | 强 | 中 | 中 |
| 创造性 | 中 | 强 | 强 |

所以，一个模型“写作不行”，不代表它“整体不行”。

这条内容里有一个重要判断：

> 某个模型在写作上可能不如另一个模型，但在 UI 设计、UI 实现、系统设计、复杂任务规划上可能更强。

这意味着产品团队不能只用单一测试标准来评价 AI 模型。

比如你拿“写小说”去测试一个模型，然后得出“这个模型没用”的结论，这可能是错误的。

真正应该做的是：

- 用设计任务测设计能力；
- 用代码任务测代码能力；
- 用系统设计任务测规划能力；
- 用文案任务测表达能力；
- 用 Agent 任务测执行稳定性。

###### 2.2 多模型工作流比单模型调用更接近真实生产

文章中提到一个很实用的流程：

> 先用 Claude Design 做设计，然后分别交给不同模型实现，比较差异。

这本质上是一个“并行产出 + 交叉评估”的工作流。

例如：

```text
需求输入
  ↓
模型 A：做产品理解和页面结构
  ↓
模型 B：做 UI 设计稿
  ↓
模型 C：实现前端代码
  ↓
模型 D：审查代码和交互问题
  ↓
人工选择和整合
```

这比单纯让一个模型“一口气从需求做到代码”更稳。

因为复杂任务中，一个模型容易在某个阶段掉链子：

- 需求理解没问题，但设计一般；
- 设计不错，但代码实现糟糕；
- 代码能跑，但结构不可维护；
- 结构不错，但用户体验不自然。

多模型组合可以降低单点失败。

###### 2.3 Prompt 不是通用的，要根据模型特性重新设计

文章中特别提到：

> 每个模型都有自己的特性，需要重新设计提示词反复调优。

这是很多人忽略的一点。

同一个 prompt，在不同模型上的效果可能完全不同。

原因包括：

- 模型对指令权重的理解不同；
- 模型对格式要求的敏感度不同；
- 模型的默认风格不同；
- 模型对工具调用的习惯不同；
- 模型对上下文优先级处理不同。

所以，不能简单认为：

> 这个 prompt 在 A 模型上好用，在 B 模型上不好用，所以 B 模型差。

更准确的说法是：

> 这个 prompt 是为 A 模型优化过的，不一定适合 B 模型。

对于产品团队来说，这意味着每个模型都需要独立的 prompt 策略。

##### 3. 可迁移清单

下面是一套可以直接迁移到 AI 产品开发、个人工作流、团队系统搭建中的清单。

###### 3.1 建立自己的“模型能力地图”

不要凭感觉评价模型，建议建立表格：

| 模型 | 擅长任务 | 不擅长任务 | 推荐使用场景 | 注意事项 |
|---|---|---|---|---|
| 模型 A | 写作、总结 | UI 设计 | 内容生产 | 需要加强结构约束 |
| 模型 B | 设计、规划 | 长文表达 | 产品原型、系统设计 | 输出可能偏抽象 |
| 模型 C | 代码实现 | 创意表达 | 前端/后端开发 | 需要人工 review |
| 模型 D | 推理、审查 | 速度较慢 | 代码审计、方案评估 | 成本较高 |

每次使用后更新一次，不断形成自己的“模型情报库”。

###### 3.2 复杂任务先拆阶段，再分配模型

不要这样做：

```text
请帮我从 0 到 1 做一个完整产品。
```

更好的方式是拆成：

```text
1. 需求澄清
2. 用户画像
3. 功能优先级
4. 信息架构
5. UI 草图
6. 视觉设计
7. 前端实现
8. 后端设计
9. 数据结构
10. 测试用例
11. 上线检查
```

然后给不同模型分配任务。

###### 3.3 对同一任务做“双模型对照”

尤其适合高价值任务：

- 产品方案；
- 技术架构；
- UI 设计；
- 重要文案；
- 商业策略；
- 投资分析；
- 代码重构。

流程：

```text
同一个任务 → 给模型 A 和模型 B
       ↓
比较差异
       ↓
找出各自优点
       ↓
让模型 C 综合
       ↓
人工最终决策
```

这能显著提升输出质量。

###### 3.4 为不同模型准备不同提示词模板

例如，对于偏规划型模型：

```text
请先不要直接执行。
先完成：
1. 任务理解
2. 隐含约束
3. 风险点
4. 执行计划
5. 需要我确认的问题
确认后再进入实现。
```

对于偏实现型模型：

```text
请直接基于以下设计和约束实现。
要求：
1. 保持组件结构清晰
2. 不要引入不必要依赖
3. 输出完整代码
4. 标注关键实现逻辑
5. 最后列出可优化点
```

对于偏审查型模型：

```text
请不要重写方案，先审查以下内容。
重点检查：
1. 逻辑漏洞
2. 技术风险
3. 用户体验问题
4. 性能隐患
5. 可维护性问题
6. 可能遗漏的边界情况
```

###### 3.5 让 AI 先 Plan，再执行

复杂任务不要直接让模型开干。

推荐流程：

```text
任务 → Plan → Review → Execute → Test → Refine
```

尤其是：

- 代码开发；
- 系统设计；
- 产品功能设计；
- 数据分析；
- Agent 自动化任务。

好的模型不只是能“回答”，更重要的是能“规划”。

##### 4. 反方与张力

###### 4.1 反方观点：多模型组合会增加复杂度

多模型工作流虽然强，但也有成本：

- 学习成本高；
- prompt 管理复杂；
- 上下文迁移麻烦；
- 不同模型输出风格不一致；
- 成本可能增加；
- 团队协作更难标准化。

所以对于简单任务，单模型可能更高效。

例如：

- 简单摘要；
- 日常翻译；
- 普通邮件；
- 简单代码片段；
- 快速头脑风暴。

不一定每个任务都要多模型组合。

###### 4.2 张力：模型评测 vs 实际工作流

很多人评价模型喜欢看榜单或单点测试。

但实际生产中，模型价值取决于：

- 是否适合你的工作流；
- 是否能和工具链配合；
- 是否能稳定执行；
- 是否容易通过 prompt 调教；
- 是否能与其他模型互补；
- 是否能降低你的整体交付成本。

一个模型在公开评测中不突出，但在你的具体场景里可能非常好用。

反过来，一个模型在榜单上很强，但可能不适合你的实际业务。

###### 4.3 张力：模型能力强不等于产品体验好

文章也隐含了一个重要问题：

> 模型本身的能力，与使用它的产品环境强相关。

同一个模型，在不同工具里表现可能不同。

比如：

- 在 Claude Code 里表现好；
- 在 Cursor 里表现不同；
- 在独立 API 里又是另一种体验；
- 在 Agent 框架下受工具调用和上下文管理影响更大。

所以产品体验不只是模型能力，还包括：

- 上下文管理；
- 工具调用；
- 文件系统访问；
- 记忆机制；
- prompt 封装；
- UI 交互；
- 调试体验；
- 失败恢复机制。

对于 AI 产品开发者来说，这一点尤其重要：

> 模型只是底层能力，真正的护城河可能在工作流设计。

---

##### 5. 情境化落地

###### 场景一：个人开发者做一个小产品

推荐工作流：

```text
1. 用模型 A 做需求澄清和功能规划
2. 用模型 B 做 UI 设计和页面结构
3. 用模型 C 做前端实现
4. 用模型 D 做代码审查
5. 再让模型 A 总结产品文档和上线清单
```

实际操作：

- 不要一开始就写代码；
- 先让 AI 输出产品 Plan；
- 再让另一个模型挑战这个 Plan；
- 最后让实现型模型执行。

###### 场景二：团队做 AI 产品原型

可以建立一个“模型分工制度”：

| 角色 | AI 负责内容 |
|---|---|
| 产品助理 | 需求分析、用户故事、功能列表 |
| 设计助理 | 页面结构、组件设计、交互建议 |
| 工程助理 | 代码实现、接口设计 |
| 测试助理 | 测试用例、边界情况 |
| 策略助理 | 商业模式、定价、竞品分析 |

每个“AI 角色”背后可以是不同模型。

这样团队不是“用一个 AI”，而是“拥有一个虚拟协作团队”。

###### 场景三：构建商业系统

如果你关注商业系统构建，可以把多模型机制用于：

- 销售脚本生成；
- 客户画像分析；
- 增长实验设计；
- CRM 自动化；
- 内容生产；
- 产品迭代；
- 用户反馈分析；
- 定价策略；
- 数据报表解读。

示例流程：

```text
用户反馈数据
  ↓
模型 A：归类痛点
  ↓
模型 B：提炼产品机会
  ↓
模型 C：生成迭代方案
  ↓
模型 D：评估商业影响
  ↓
人工决策优先级
```

这比单模型直接“帮我分析用户反馈”更可靠。

###### 场景四：Agent 产品开发

Agent 场景尤其需要多模型思路。

可以这样设计：

| Agent 阶段 | 推荐模型能力 |
|---|---|
| 任务理解 | 长上下文、语义理解 |
| 计划生成 | 系统设计、分步骤规划 |
| 工具调用 | 稳定性、执行力 |
| 异常处理 | 推理、纠错 |
| 最终总结 | 表达、结构化输出 |

Agent 不一定从头到尾使用同一个模型。

更高级的架构是：

```text
Planner Model → Executor Model → Critic Model → Summarizer Model
```

也就是：

- 一个模型负责计划；
- 一个模型负责执行；
- 一个模型负责检查；
- 一个模型负责总结。

---

##### 6. 精炼结论

这条内容真正有价值的地方不是“某个模型好不好”，而是提出了一个更成熟的 AI 使用范式：

> 不要寻找万能模型，而要建立多模型组合工作流。

对于 AI/产品开发和商业系统构建者，关键动作是：

1. 建立模型能力地图；
2. 按任务阶段拆解工作流；
3. 用不同模型处理不同环节；
4. 为每个模型单独调 prompt；
5. 用并行输出和交叉审查提升质量；
6. 把模型能力嵌入产品系统，而不是停留在聊天层面。

一句话总结：

> 真正会用 AI 的人，不是选中了一个最强模型，而是知道什么时候该让哪个模型上场。
