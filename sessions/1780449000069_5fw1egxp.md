## 分析要点

- **核心高价值点**：将“完成标准”显式化为可验证 rubric，并由独立评分子代理驱动多轮修正，可显著降低人工检查和重跑成本。
- **留存建议**：短期参考后可归档，适合作为构建智能体自评迭代机制的实现思路参考（包含较清晰的智能体评分循环设计和可复用的中间件接入示例，对AI应用开发有参考价值）

**知识要点**

- RubricMiddleware 在主代理完成前调用评分子代理，对照 rubric 判断是否满足各项标准
- 评分器可使用测试、代码检查等工具获取证据，而不是仅依赖语言模型主观判断
- 反馈按标准返回并注入上下文，使主代理能够针对具体失败项进行修正
- 该机制适合成功标准明确、可验证的任务，如代码生成、测试通过、报告结构完整性检查

**行动项**

- 在代码生成类智能体中尝试定义明确 rubric，如测试通过、函数签名正确、边界情况覆盖
- 为评分子代理配置可调用工具，例如测试套件、lint、格式检查或输出验证器
- 设置最大迭代次数，避免评分-修复循环失控
- 将 rubric 设计为可复用模板，用于不同任务类型的自动化验收

#### TL;DR

- Agents often produce outputs that head in the right direction but don't fully land on the first attempt.
- RubricMiddleware is how you tell the agent what "done" looks like — and make it keep going until it gets there.
- Most effective for tasks with clear, verifiable success criteria like passing tests, avoiding forbidden patterns, covering required sections.

Agents are taking on more complex tasks than ever. More often than not, they fall short of the finish line. We've added RubricMiddleware to Deep Agents to fix that — you define a rubric, and the agent self-evaluates and iterates until it satisfies every criterion, or hits a configured cap.

If you're familiar with /goal in Claude Code or Codex, this is a similar pattern. This implementation is a bit more flexible because evaluation is handled by a dedicated grader sub-agent that can call tools, reason over the full transcript, and return per-criterion feedback.

### The problem

Some agent tasks have a clear definition of "done." A code refactor is finished when the test suite passes. A report is complete when every required section is covered.

But agents don't always get there on the first try. As context grows larger, ambiguous instructions, tool misuse, and non-deterministic errors all compound — output quality deteriorates, and developers are left to diagnose and re-run tasks manually.

### How it works

Before the agent run finishes, a separate grader sub-agent reviews it against the rubric. If everything passes, the run concludes. If anything falls short, the grader's per-criterion feedback is injected back into the conversation and the agent runs again. The loop terminates when the rubric is satisfied, or when a configured iteration limit is hit.

![Image](https://pbs.twimg.com/media/HJ09cXHWQAI3G3Q?format=jpg&name=large)

The loop terminates on \`satisfied\`, \`max\_iterations\_reached\`, \`failed\`, or \`grader\_error\`.

#### Wiring it up

Here's the minimal setup, broken into steps. The key idea: define a RubricMiddleware once, attach it to a deep agent, then pass a rubric string at invoke time. (If rubric is absent, the middleware does nothing.)

#### 1\) Define RubricMiddleware

This middleware adds a grader loop on top of the base agent. The grader is configured with:

- model: the LLM used for grading (often smaller/cheaper than your main agent model)
- system\_prompt: instructions that define the grader’s role and what “good” looks like
- tools: optional tools the grader can call to gather evidence (e.g., run tests, lint, validate outputs)
- max\_iterations: the maximum number of fix → re-grade loops before the run stops

```python
from deepagents import RubricMiddleware

rubric_middleware = RubricMiddleware(
    model="anthropic:claude-haiku-4-5",
    system_prompt="You are a code reviewer grading generated code against a rubric.",
    tools=[run_test_suite],
    max_iterations=5,
)
```

#### 2\) Pass it to a deep agent

你的深度代理也应该有自己的“操作说明”。代理的系统提示告诉它如何完成工作，而评分标准告诉评分者如何评判工作。

In the snippet below:

- model: the LLM used to generate the solution
- system\_prompt: coding conventions + constraints for the agent
- middleware: attaches rubric\_middleware so the agent can be iteratively corrected

```python
from deepagents import create_deep_agent

agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    system_prompt=(
        "You are a careful Python engineer. Write correct, readable code. "
        "Follow the user’s instructions exactly."
    ),
    middleware=[rubric_middleware],
)
```

#### 3\) Invoke with a human message + rubric

At invocation time you provide:

- messages: the human request (and optionally prior turns)
- rubric: a newline-delimited checklist that the grader must mark satisfied

```python
from langchain.messages import HumanMessage

result = agent.invoke(
    {
        "messages": [
            HumanMessage(
                content=(
                    "Write a Python function `find_duplicates(lst)` that returns a list of "
                    "all elements that appear more than once in the input list, in the order "
                    "they first appear."
                )
            )
        ],
        "rubric": (
            "- All tests pass in run_test_suite\n"
            "- The function is named `find_duplicates` and accepts a single list argument\n"
        ),
    },
    config={"configurable": {"thread_id": "code-generation-session"}},
)
print(result["messages"][-1].text)
```

Rather than asking the grader to reason abstractly about correctness, we give it a \`run\_test\_suite\` tool to verify behavior directly. The grader can call tools to gather hard evidence before producing a verdict — and falls back to reasoning from the transcript when no tools are provided.

#### Seeing it in practice

In the code generation example above, the agent's first attempt looked correct but failed one test. The grader returned:

> "One test fails: test\_unhashable. The function crashes with TypeError when encountering unhashable types like lists within the input list."

The agent revised its implementation and passed all tests on the second iteration. The feedback isn't a generic "try again" — each criterion gets its own verdict, so the agent knows exactly what to fix.

#### Why it matters

Agent outputs are probabilistic: the same prompt can succeed on one run and fall short on the next. RubricMiddleware shifts the burden of catching that variance away from the developer and onto the system.

Instead of manually inspecting outputs and re-running failed tasks, you define what "done" looks like once and the loop handles the rest. Each retry is informed — the grader identifies exactly what's wrong and produces targeted, per-criterion feedback.

The result: more reliable agents on tasks where correctness matters.

RubricMiddleware is in beta and the API may change. For a full walkthrough including configuration, observability, and rubric persistence, see

[the documentation](https://docs.langchain.com/oss/python/deepagents/rubric).

#### 评分量规 RubricMiddleware：让智能体“自查—修正—再提交”

##### 一、深度总结

这篇内容介绍了 **RubricMiddleware**：一种让 AI 智能体根据明确标准，自动评估并修正自身输出的机制。

核心问题是：

> 智能体常常“方向对，但不完全对”。  
> 它可能第一次生成的结果看似合理，却漏掉要求、测试失败、格式不符或违反约束。

RubricMiddleware 的解决思路是：

1. 用户提前定义“完成标准”，也就是 rubric / 评分量规；
2. 智能体完成任务后，不直接结束；
3. 一个独立的“评分子智能体”检查输出是否满足标准；
4. 如果不满足，就把具体反馈注入回对话；
5. 主智能体根据反馈继续修改；
6. 循环直到：
   - 全部标准满足；
   - 达到最大迭代次数；
   - 执行失败；
   - 评分器出错。

它特别适合那些 **成功标准清晰、可验证** 的任务，例如：

- 代码是否通过测试；
- 是否避免某些禁止模式；
- 报告是否覆盖所有必要章节；
- 输出格式是否符合规范；
- 是否满足安全、合规、风格要求。

---

##### 二、深入浅出解读

可以把它理解成：

> 给 AI 配了一个“质检员”。

普通智能体像是一个员工：  
它接到任务后直接交付结果。

RubricMiddleware 加入后，流程变成：

```text
员工完成任务
   ↓
质检员按清单检查
   ↓
合格：交付
不合格：指出哪里错
   ↓
员工返工
   ↓
再次质检
```

这里的“质检清单”就是 rubric。

例如让 AI 写一个函数：

```python
find_duplicates(lst)
```

rubric 可以写成：

```text
- 所有测试必须通过
- 函数名必须是 find_duplicates
- 只能接受一个列表参数
- 返回重复元素，顺序按首次出现排列
```

如果第一次代码遇到不可哈希元素时报错，评分器会指出：

> `test_unhashable` 失败，输入中有列表等不可哈希类型时会触发 TypeError。

于是主智能体不会盲目重写，而是针对问题修复。

这比简单说“再试一次”强得多，因为反馈是具体、可执行的。

---

##### 三、关键价值

###### 1. 把“人工返工”变成“系统闭环”

过去开发者需要：

```text
看输出 → 找问题 → 提示 AI 修改 → 再检查
```

现在可以变成：

```text
定义标准 → 系统自动检查和迭代
```

人的负担从“逐次盯结果”转为“设计好验收标准”。

---

###### 2. 提升智能体稳定性

AI 输出有概率性。  
同一个提示词，这次成功，下次可能失败。

RubricMiddleware 通过自评和重试，减少这种不稳定性。

它不是保证 AI 永远正确，而是提高“最终交付正确”的概率。

---

###### 3. 让“完成”变得可操作

很多 AI 任务失败，不是因为模型太弱，而是因为“完成”定义太模糊。

RubricMiddleware 的本质是：

> 把模糊要求转化为可检查的完成标准。

这对复杂任务尤其重要。

---

##### 四、适用场景

特别适合：

- 代码生成与重构；
- 测试驱动开发；
- 文档生成；
- 数据清洗；
- 合规检查；
- 格式化输出；
- 多步骤研究报告；
- 有明确 checklist 的任务。

不太适合：

- 纯创意写作；
- 审美判断；
- 开放式战略讨论；
- 标准模糊、无法验证的任务。

##### 五、我的辩证思考

###### 1. 它提升可靠性，但不等于真正“自我理解”

RubricMiddleware 看起来像 AI 会自我反省，但本质上是：

> 用另一个模型按标准做外部审查。

这是一种工程上的闭环，而不是模型本身真正具备稳定自省能力。

所以它有效，但不能神化。

---

###### 2. 标准越清晰，效果越好

这个机制的上限很大程度取决于 rubric 的质量。

如果标准写得模糊：

```text
- 结果要好
- 内容要完整
- 代码要优雅
```

评分器也很难判断。

如果标准写得具体：

```text
- 必须通过 run_test_suite
- 不得使用全局变量
- 输出必须包含摘要、风险、建议三部分
```

效果会明显更好。

**结论：智能体时代，写好验收标准会成为一种核心能力。**

---

###### 3. 它会增加成本和延迟

每次评分、返工、再评分都会消耗：

- 模型调用成本；
- 工具执行时间；
- 上下文长度；
- 系统复杂度。

所以它不适合所有任务。

对于低价值、低风险任务，直接生成即可。  
对于高价值、高风险任务，rubric 闭环很有必要。

---

###### 4. 评分器本身也可能出错

评分子智能体不是绝对裁判。它可能：

- 误判；
- 漏检；
- 过度挑剔；
- 被上下文误导；
- 工具调用失败。

因此最可靠的方式是：

> 能用工具验证的，就不要只靠模型判断。

例如代码任务应优先跑测试，而不是让模型“感觉代码对不对”。

---

##### 六、一句话总结

**RubricMiddleware 的本质，是把 AI 从“一次性交付”改造成“按验收标准自动返工的闭环系统”。**

它最重要的启发是：

> 未来使用智能体，关键不只是写提示词，而是写清楚“什么叫完成”。

##### 解决方案：RubricMiddleware

###### 定义

**RubricMiddleware**是 Deep Agents 中的一个中间件，用于给智能体增加 “评分 — 反馈 — 修正” 循环。

它允许开发者定义一组评分标准，也就是**rubric / 评分量规**，然后由独立评分子智能体判断主智能体的输出是否满足这些标准。

---

##### 工作流程

###### 基本流程

```text
主智能体执行任务
        ↓
评分子智能体按 rubric 检查
        ↓
全部通过？
   是 → 结束运行
   否 → 将逐项反馈注入对话
        ↓
主智能体根据反馈修正
        ↓
再次评分
```

###### 终止条件

循环可能在以下情况下结束：

| 终止状态 | 含义 |
|---|---|
| `满足` | 所有评分标准均已满足 |
| `达到最大迭代次数` | 修正次数达到配置上限 |
| `失败` | 主任务运行失败 |
| `评分器错误` | 评分子智能体或评分过程出错 |

---

##### 核心组成

###### 1. 主智能体

负责完成用户任务，例如：

- 写代码；
- 修改代码；
- 生成报告；
- 处理数据；
- 完成多步骤任务。

###### 2. 评分子智能体

负责根据 rubric 检查主智能体的输出。

它可以：

- 查看完整对话历史；
- 逐项判断标准是否满足；
- 调用工具收集证据；
- 返回针对每条标准的反馈。

###### 3. Rubric / 评分量规

用户定义的完成标准，例如：

```text
- 所有测试必须通过
- 函数名必须正确
- 输出必须包含摘要、风险和建议
- 不得使用某些禁止模式
```

###### 4. 工具

评分器可选调用的验证工具，例如：

- 测试套件；
- lint 工具；
- 格式校验；
- schema 验证；
- 静态分析；
- 内容检查工具。

---

##### 代码接入方式

###### 第一步：定义 RubricMiddleware

```python
from deepagents import RubricMiddleware

rubric_middleware = RubricMiddleware (
    model="anthropic:claude-haiku-4-5",
    system_prompt="You are a code reviewer grading generated code against a rubric.",
    tools=[run_test_suite],
    max_iterations=5,
)
```

###### 参数说明

| 参数 | 作用 |
|---|---|
| `model` | 用于评分的 LLM，通常可选择更小、更便宜的模型 |
| `system_prompt` | 定义评分者角色和判断方式 |
| `tools` | 评分器可调用的工具，如运行测试套件 |
| `max_iterations` | 最大修正 — 重新评分轮数 |

---

###### 第二步：创建 Deep Agent 并挂载中间件

```python
from deepagents import create_deep_agent

agent = create_deep_agent (
    model="anthropic:claude-sonnet-4-6",
    system_prompt=(
        "You are a careful Python engineer. Write correct, readable code."
        "Follow the user’s instructions exactly."
    ),
    middleware=[rubric_middleware],
)
```

###### 配置含义

| 配置项 | 作用 |
|---|---|
| 主模型 | 负责生成解决方案 |
| 系统提示词 | 约束智能体行为和代码风格 |
| middleware | 挂载 RubricMiddleware，让智能体具备自评迭代能力 |

---

###### 第三步：调用时传入任务和 rubric

```python
from langchain.messages import HumanMessage

result = agent.invoke (
    {
        "messages": [
            HumanMessage (
                content=(
                    "Write a Python function`find_duplicates (lst)`that returns a list of"

                    "they first appear."
                )
            )
        ],
        "rubric": (
            "- All tests pass in run_test_suite\n"
            "- The function is named`find_duplicates`and accepts a single list argument\n"
        ),
    },
    config={"configurable": {"thread_id": "code-generation-session"}},
)

print (result ["messages"][-1].text)
```

##### 示例任务

###### 用户需求

写一个 Python 函数：

```python
find_duplicates (lst)
```

要求：

- 输入一个列表；
- 返回所有重复出现的元素；
- 按元素第一次出现的顺序返回。

###### 评分标准

```text
- 所有测试必须通过 run_test_suite
- 函数名必须是 find_duplicates
- 函数只接受一个列表参数
```

###### 实际迭代过程

| 阶段 | 结果 |
|---|---|
| 第一次生成 | 代码看似正确，但有测试失败 |
| 评分器检查 | 发现`test_unhashable`失败 |
| 反馈内容 | 输入包含不可哈希类型，如列表时，会触发 TypeError |
| 主智能体修正 | 调整实现以支持不可哈希元素 |
| 第二次评分 | 所有测试通过 |

##### 适用场景

RubricMiddleware 最适合**成功标准明确、可验证**的任务。

###### 适合

| 场景 | 示例 |
|---|---|
| 代码生成 | 函数实现必须通过测试 |
| 代码重构 | 重构后测试套件全部通过 |
| 文档生成 | 必须包含指定章节 |
| 报告写作 | 必须覆盖所有必要部分 |
| 格式化输出 | 必须符合 JSON schema |
| 安全检查 | 不得包含禁止模式 |
| 合规任务 | 必须满足 checklist |

###### 不太适合

| 场景 | 原因 |
|---|---|
| 纯创意写作 | 成功标准较主观 |
| 审美判断 | 难以明确验证 |
| 开放式战略讨论 | 标准模糊且依赖价值判断 |
| 高度主观评价 | 评分器可能不稳定 |

---

##### 核心价值

###### 1. 明确 “完成” 的定义

RubricMiddleware 让开发者把隐含的验收标准显式写出来。

从：

```text
请把这个任务做好
```

变成：

```text
满足以下标准才算完成
```

---

###### 2. 降低人工返工成本

开发者不再需要每次手动：

```text
检查输出 → 找问题 → 提示修改 → 再检查
```

而是由系统自动完成：

```text
生成 → 评分 → 反馈 → 修正 → 再评分
```

---

###### 3. 提高智能体可靠性

由于 LLM 输出具有概率性，同一任务可能有时成功、有时失败。

RubricMiddleware 通过自动检查和迭代，提高最终交付结果的稳定性。

---

###### 4. 提供具体反馈

相比简单的 “再试一次”，评分器会指出：

- 哪条标准未满足；
- 为什么未满足；
- 需要修复什么。

---

##### 关键设计原则

###### 1. Rubric 要具体

低质量标准：

```text
- 结果要好
- 内容要完整
- 代码要优雅
```

高质量标准：

```text
- 所有测试必须通过
- 输出必须是合法 JSON
- 报告必须包含摘要、方法、结果和风险四个部分
- 不得使用全局变量
```

---

###### 2. 能用工具验证，就不要只靠模型判断

对于代码任务，应优先使用：

- 测试套件；
- lint；
- 类型检查；
- 静态分析。

对于结构化输出，应优先使用：

- JSON schema；
- 正则检查；
- 字段完整性验证。

---

###### 3. 控制迭代次数

需要设置`max_iterations`，避免：

- 无限修复循环；
- 成本失控；
- 延迟过高；
- 评分器和主智能体反复拉扯。

---

###### 4. 主模型和评分模型可以分工

常见配置：

| 角色 | 模型 |
|---|---|
| 主智能体 | 更强模型，负责复杂生成 |
| 评分器 | 更便宜模型，负责检查和反馈 |

这种设计可以在质量与成本之间取得平衡。

---

##### 局限性

###### 1. 评分器也可能出错

评分子智能体本身也是 LLM，可能：

- 误判；
- 漏判；
- 过度挑剔；
- 被上下文误导；
- 工具调用失败。

---

###### 2. Rubric 质量决定上限

如果标准模糊，评分循环也难以稳定工作。

因此开发者需要投入精力设计高质量 rubric。

---

###### 3. 增加成本和延迟

每轮评分和修正都会消耗：

- 模型调用；
- token；
- 工具执行时间；
- 系统运行时间。

---

###### 4. 不保证绝对正确

RubricMiddleware 提高的是可靠性和通过率，但不能保证智能体永远正确。

尤其是在标准不完整、测试覆盖不足或评分器误判时，仍可能输出有问题的结果。

---

##### 与传统提示词的区别

| 方式 | 特点 |
|---|---|
| 普通提示词 | 一次性生成，依赖模型首次输出质量 |
| “请检查自己” | 仍由同一上下文内模型自查，容易漏检 |
| RubricMiddleware | 独立评分子智能体按标准检查，可调用工具并驱动迭代修正 |

---

##### 对开发者的启发

###### 从 “写提示词” 转向 “写验收标准”

未来构建智能体时，关键不只是告诉模型做什么，还要告诉它：

```text
什么样的结果才算完成？
如何判断是否完成？
哪些失败必须被修复？
```

###### 可沉淀的工程资产

Rubric 可以变成可复用模板，例如：

- 代码生成 rubric；
- 重构任务 rubric；
- 报告生成 rubric；
- 数据分析 rubric；
- 合规审查 rubric；
- 客服回复质量 rubric。

---

##### 最终结论

**RubricMiddleware 是一种智能体可靠性工程模式。**

它通过 “评分量规 + 独立评分子智能体 + 工具验证 + 自动迭代修正”，把 AI 从一次性回答系统升级为更接近可交付工作流的智能体系统。

它最适合用于标准明确、结果可验证、正确性重要的任务。

## 结构化（1）

### 2026-06-03 02:16:13

##### 主旨概括

文章介绍了 **RubricMiddleware（评分量规中间件）**：它让智能体在完成任务前，先按预设标准自我检查，并根据反馈反复修改，直到满足要求或达到迭代上限。它特别适合有明确验收标准的任务，例如代码测试通过、报告覆盖指定章节、避免禁用模式等。

---

##### 1. 背景：智能体经常“差一点完成”

- 现在智能体承担的任务越来越复杂，但很多时候第一次输出只是“方向对”，并没有真正达到完成标准。
- 常见问题包括：
  - 指令理解模糊；
  - 上下文变长后质量下降；
  - 工具使用错误；
  - 非确定性错误导致同一任务结果不稳定。
- 结果是开发者需要手动检查、诊断问题，并重新运行任务，效率较低。

---

##### 2. 核心思路：用评分量规定义“完成是什么样”

- **RubricMiddleware 的作用**是告诉智能体：什么结果才算真正完成。
- 用户可以定义一组评分标准（rubric），智能体在结束前会被检查是否满足这些标准。
- 如果没有全部满足，系统会把具体反馈返回给智能体，让它继续修改。
- 这个模式类似 Claude Code 或 Codex 中的 `/goal`，但这里更灵活：
  - 由专门的 **grader sub-agent（评分子智能体）**负责评估；
  - 它可以调用工具；
  - 可以查看完整对话记录；
  - 可以针对每条标准给出具体反馈。

---

##### 3. 工作机制：评分—反馈—修改循环

RubricMiddleware 的流程如下：

1. 主智能体完成一次任务输出；
2. 在任务结束前，评分子智能体根据 rubric 检查结果；
3. 如果全部通过，任务结束；
4. 如果有不满足的标准，评分反馈会被加入对话；
5. 主智能体根据反馈继续修改；
6. 重复上述过程，直到满足标准或达到上限。

循环可能以以下状态结束：

- `satisfied`：所有标准满足；
- `max_iterations_reached`：达到最大迭代次数；
- `failed`：任务失败；
- `grader_error`：评分器出错。

---

##### 4. 如何配置 RubricMiddleware

文章给出了一个最小配置流程，核心是：**先定义 RubricMiddleware，再挂载到 deep agent，最后在调用时传入 rubric。**

###### 第一步：定义 RubricMiddleware

配置项包括：

- `model`：用于评分的模型，通常可以比主模型更小、更便宜；
- `system_prompt`：告诉评分器它的角色和判断标准；
- `tools`：可选工具，例如运行测试、lint、验证输出；
- `max_iterations`：最多允许修改和重新评分的次数。

示例中使用：

```python
RubricMiddleware(
    model="anthropic:claude-haiku-4-5",
    system_prompt="You are a code reviewer grading generated code against a rubric.",
    tools=[run_test_suite],
    max_iterations=5,
)
```

这里设置了最多 **5 次迭代**，并让评分器可以调用 `run_test_suite` 来验证代码。

---

##### 5. 将 RubricMiddleware 接入智能体

接着创建一个 deep agent：

- 主模型负责生成解决方案；
- `system_prompt` 指定编码规范和约束；
- `middleware` 中加入前面定义好的 `rubric_middleware`。

示例中主模型使用：

```python
model="anthropic:claude-sonnet-4-6"
```

评分模型则是更轻量的：

```python
model="anthropic:claude-haiku-4-5"
```

这体现了一个常见设计：**主模型负责高质量生成，较便宜的模型负责检查和反馈。**

---

##### 6. 调用时传入任务和评分标准

在调用智能体时，需要提供：

- `messages`：用户任务；
- `rubric`：评分标准清单。

文章中的例子是要求智能体写一个 Python 函数：

```python
find_duplicates(lst)
```

功能要求：

- 返回输入列表中所有重复出现的元素；
- 按它们第一次出现的顺序返回。

对应 rubric 包括：

```text
- All tests pass in run_test_suite
- The function is named `find_duplicates` and accepts a single list argument
```

也就是说，评分器不仅检查函数名和参数，还会通过测试工具验证功能是否正确。

---

##### 7. 实际案例：第一次失败，第二次修正通过

文章中的代码生成案例显示：

- 智能体第一次生成的代码看起来正确；
- 但运行测试时，有一个测试失败；
- 评分器给出具体反馈：

> “一个测试失败：test_unhashable。当输入列表中包含不可哈希类型（如列表）时，函数会因 TypeError 崩溃。”

随后：

- 智能体根据反馈修改实现；
- 第二轮通过了所有测试。

这个例子说明，RubricMiddleware 的反馈不是简单地说“再试一次”，而是会指出具体哪条标准没满足、哪里出了问题，从而让智能体有针对性地修复。

---

##### 8. 价值：把人工检查变成系统自动循环

RubricMiddleware 的意义在于提升智能体结果的可靠性：

- 智能体输出具有概率性，同一个提示词可能一次成功、一次失败；
- 过去开发者需要手动发现问题并重跑；
- 现在只要提前定义“完成标准”，系统就能自动检查和迭代。

它适合用于对正确性要求较高的任务，例如：

- 代码生成与重构；
- 测试必须通过的任务；
- 报告或文档必须覆盖指定内容；
- 输出必须符合格式或约束的场景。

- RubricMiddleware 目前处于 **beta 阶段**；
- API 未来可能变化；
- 官方文档提供了更完整的配置、可观测性和 rubric 持久化说明。

RubricMiddleware 本质上是在智能体外加了一层“自动验收机制”：用户定义验收标准，评分子智能体负责检查，主智能体根据反馈不断修正。它让智能体不只是“生成答案”，而是更接近“交付符合标准的结果”。
