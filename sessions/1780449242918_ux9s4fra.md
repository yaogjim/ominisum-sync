这篇文章先讲清楚一件事：

我到底干成了什么，以及这件事对一个内容创作者有什么用

#### 一、这套系统有什么用

大多数人做内容，有一个很隐蔽的浪费

你已经写过很多东西，但下一次做新选题时，还是要重新想问题、重新找观点、重新翻案例、重新搭结构

旧内容明明在那里，但它很难再次被调用

问题出在旧内容的形态上：它们大概率还只是「文件」，还没有进入「系统」状态

一篇文章发完之后，它会留在某个文件夹里。一个推文写完之后，它会留在某个平台导出记录里。一个短视频文稿写完之后，它会变成本地某个 .md、.txt 或 .docx 文件

它们都还在

但下一次你要写一个新主题时，这些文件很难直接回答：

这个选题相关的问题有哪些？

有哪些稳定观点？

有哪些案例能证明？

有哪些方案能落地？

哪些内容之前已经写过，哪些内容是新长出来的？

所以这套系统要做的第一件事，就是把旧内容拆成可以再次调用的对象

我把文稿里的内容拆成 5 类：

问题、概念、观点、案例、方案

在工程里，它们分别对应 QST、CON、OPI、CAS、SOL

这 5 类东西看起来很朴素，但它们刚好对应一篇内容最重要的骨架

你要写一篇文章，通常要先知道读者被什么问题困住，再解释关键概念，再给出判断，再用案例证明，最后给出行动方案

所以，当旧内容被拆成这些单元之后，它开始变成以后可以继续调用、重组、扩展的生产资料

这就是这套系统最直接的用处

你是在一个已经沉淀过问题、观点、案例和方案的内容资产池里，重新装配一篇新内容

![Image](https://pbs.twimg.com/media/HJy2z5obYAEMsqu?format=jpg&name=large)

#### 二、我具体做了什么

我先给这个工程定规则，再抽取内容

这种项目最容易失败的地方，通常是边界一开始就乱了

如果不知道哪些素材该进来，哪些素材不该进来，哪些是原始素材，哪些是处理结果，哪些是当前版本，哪些是历史痕迹，后面抽得越多，只会越乱

所以第一步，我建立了一个新的副本工程

原始素材不直接改动，只复制到新工程里

这件事很重要

因为任何内容结构化工程，都必须保留回溯路径。你后面看到一个观点、一个案例、一个方案，必须能知道它来自哪篇原文

然后我给工程建立了几层结构

第一层是规则层

这里定义内容单元怎么命名，字段怎么写，关系怎么连，新增文稿怎么进入系统，重复内容怎么处理，来源怎么登记

第二层是状态层

这里记录哪些来源已经处理，哪些还没处理，哪些被跳过，哪些需要复核

第三层是内容单元库

这里存放从原文里抽出来的问题、概念、观点、案例和方案

第四层是主题地图

主题地图是一组相关节点的组织方式。比如一个主题下面会有几个问题、几个观点、几个案例、几个方案，它们共同构成一个可以继续展开的内容面

第五层是选题装配稿

装配稿更像是一个可发布内容的骨架：这个选题给谁看，核心问题是什么，调用哪些观点，引用哪些案例，用什么结构展开

最后，我又补了关系索引、去重候选、处理状态总览和 Obsidian 直链

这一步的意义是让系统真的能被浏览、被检查、被继续使用

因为只把内容拆出来还不够

节点之间必须有关系

一个问题可以被某个观点回应，一个概念可以解释某个问题，一个案例可以证明某个观点，一个方案可以解决某个问题

这些关系被写进文件之后，Obsidian 里就能看到节点之间的连接

这也是为什么最终工程里出现了 1720 条显式关系

它最终形成的是一张可以继续扩展的内容关系网

![Image](https://pbs.twimg.com/media/HJy27s-bAAABd5s?format=jpg&name=large)

#### 三、为什么要这样设计

很多人第一次用 Agent，会把它当成一个更强的聊天框

比如让它写一篇文案，改一个标题，总结一个文件，生成几个选题

这些事情当然有用

但它们都是单次任务

你给它一段内容，它回答你一次，这一轮就结束了

这次的对象是一个本地工程

工程和聊天最大的区别在于：工程有规则，有状态，有目录，有版本，有来源，有后续动作

我必须真的进入文件系统，创建目录，写规则文件，复制素材，生成索引，抽取内容单元，补关系，跑去重，更新状态

这也是为什么这件事耗掉了 2 天和约 2 亿 token

真正费 token 的地方，是让 Agent 持续处理一个复杂工程，并且不断检查自己前面做过什么

如果你也想用 Agent 做类似的事，有一个判断标准很简单

如果你要的是一段文案，正常聊天就够了

如果你要的是一个以后还能继续运转的本地系统，你要把它放进工程里用

你要给它工程边界、目录位置、处理规则、验收标准，以及持续推进的目标

skill 的意义就在这里

它把一套已经跑通过的工程方法，固定成 Agent 可以重复执行的流程

#### 四、这套系统会怎么帮你写内容

假设你今天想写一个选题：

年轻人怎么赚钱

普通做法是重新想一遍

你会开始问自己：现在年轻人最大的问题是什么？他们有哪些误区？我之前讲过哪些案例？有没有可执行方案？这篇文章应该从哪里开头？

如果你的内容资产没有结构化，这些问题都要靠你重新翻

但在这个系统里，做法会变

系统可以先找到和「年轻人赚钱」相关的问题节点，再找到解释这些问题的概念节点，再找到已经存在的观点、案例和方案

然后它可以把这些东西排列成一个选题装配稿

你会看到这个选题面对谁，核心冲突是什么，文章可以调用哪些旧内容，哪些地方还缺新观点，哪些案例可以拿来证明

写作仍然需要判断

但排列组合、关系检索、素材调取、结构搭建，这些事情对 Agent 来说非常适合

人最应该做的是判断：这个观点对不对，这个案例够不够硬，这个结构有没有击中读者

Agent 最适合做的是把可调用的内容端出来，让你从重复翻旧稿里解放出来

这就是内容工程和普通素材库的区别

素材库只是把东西存起来

内容工程会让旧内容继续参与新内容生产

#### 深度总结

这篇文章讲的是：**用 Agent 把个人长期积累的内容，改造成可持续复用的“内容资产工程系统”。**

作者用 2 天、约 2 亿 token，把 dontbesilent 本地的大量内容资料结构化处理：

- 原始内容规模：143 个目录、2330 个文件、约 1293 万中文字符
- 生成结果：
  - 1419 个内容单元
  - 223 张主题地图
  - 224 份选题装配稿
  - 1720 条显式关系

核心思想是：

> 旧内容如果只是文件，就是库存；  
> 旧内容如果被拆解、分类、连接、装配，就是生产资料。

系统把内容拆成 5 类基本单元：

| 类型 | 含义 |
|---|---|
| QST | 问题 |
| CON | 概念 |
| OPI | 观点 |
| CAS | 案例 |
| SOL | 方案 |

再通过关系连接起来：

- 问题被观点回应
- 概念解释问题
- 案例证明观点
- 方案解决问题

最终形成一个可以被 Agent 检索、调用、重组、继续生长的内容网络。

#### 深入浅出解读

##### 1. 它解决的不是“写作问题”，而是“复用问题”

很多内容创作者最大的问题不是没写过东西，而是：

> 写过的东西躺在文件夹里，下次写新内容时还是从零开始。

以前的旧文章、推文、课程稿、视频稿，只是零散文件。

它们不能直接回答：

- 我以前写过哪些问题？
- 哪些观点可以复用？
- 哪些案例能证明这个观点？
- 哪些方案可以直接拿来改写？
- 哪些内容重复了？
- 哪些内容还缺口？

所以，这套系统的本质是：

> 把“内容文件夹”升级成“内容操作系统”。

---

##### 2. 它不是简单整理资料，而是建立内容工程

普通整理资料，可能只是：

```text
文章/
推文/
课程稿/
素材/
案例/
```

看起来整齐，但不一定好用。

这套系统更像工程：

```text
规则层
状态层
原始素材区
内容单元库
主题地图
选题装配稿
关系索引
去重候选
处理总览
```

区别在于：

| 普通素材库 | 内容工程 |
|---|---|
| 存东西 | 调用东西 |
| 靠人翻找 | 让 Agent 检索 |
| 文件孤立 | 节点互联 |
| 发完就沉没 | 可继续参与生产 |
| 静态归档 | 动态生长 |

---

##### 3. 为什么要拆成“问题、概念、观点、案例、方案”？

因为一篇好内容通常就是这 5 个东西的组合：

```text
读者有什么问题？
需要解释什么概念？
作者有什么判断？
有什么案例证明？
最后怎么行动？
```

所以，把旧内容拆成这 5 类，相当于把过去写过的文章拆成“积木”。

以后写新文章时，不是从白纸开始，而是从积木池里重新组装。

比如你要写《年轻人怎么赚钱》：

系统可以自动帮你找出：

- 年轻人赚钱相关的问题
- 过去写过的认知误区
- 可复用的观点
- 可引用的案例

这篇文章反复强调一个点：

> 先定规则，再抽取内容。

因为内容工程最容易失败的地方不是 AI 不够聪明，而是边界混乱：

- 哪些文件纳入？
- 哪些文件排除？
- 原始素材放哪里？
- 处理结果放哪里？
- 哪些是当前版本？
- 哪些是历史痕迹？
- 内容单元如何命名？
- 来源如何登记？
- 重复内容如何处理？
- 什么状态才算完成？

如果没有这些规则，Agent 处理得越多，系统越混乱。

所以这套方法的底层思想是：

> 不要先追求规模化处理，要先建立可持续运行的工程秩序。

---

##### 4. 显式关系是内容系统的关键杠杆

这套系统生成了 1720 条显式关系。

关系类型包括：

- 回应
- 解释
- 证明
- 冲突

例如：

```text
某个观点 → 回应 → 某个问题
某个概念 → 解释 → 某个问题
某个案例 → 证明 → 某个观点
某个方案 → 解决 → 某个问题
```

这一步非常重要。

因为孤立的内容单元只是碎片。

有关系之后，内容才变成网络。

而一旦形成网络，Agent 就可以围绕某个主题自动调取相关节点，生成新的内容结构。

这就是从“资料整理”进入“知识图谱 / 内容图谱”的关键一步。

##### 三、可迁移清单

以下方法不仅适用于内容创作者，也适用于产品开发、知识管理、咨询交付、课程开发、研究团队和商业系统构建。

---

##### 1. 内容资产工程化清单

###### A. 输入层：明确素材范围

你需要先定义：

- 哪些内容进入系统？
- 哪些内容暂时排除？
- 哪些是自己原创？
- 哪些是外部资料？
- 哪些是已发布内容？
- 哪些是草稿？
- 哪些内容可信度更高？
- 哪些内容需要复核？

示例：

```text
纳入：
- 已发布公众号文章
- 已发布推文
- 课程逐字稿
- 成熟选题草稿
- 产品复盘文档

排除：
- 临时聊天记录
- 不完整草稿
- 无来源外部摘录
- 重复导出文件
```

---

###### B. 工程层：建立固定目录

可以迁移为以下结构：

```text
00-规则层/
01-原始素材区/
02-处理状态/
03-内容单元库/
04-主题地图/
05-选题装配稿/
06-关系索引/
07-去重候选/
08-总览报表/
```

关键原则：

> 不直接修改原始素材，所有处理都在副本工程里完成。

---

###### C. 内容层：统一拆解对象

建议采用 5 类内容单元：

```text
QST：问题
CON：概念
OPI：观点
CAS：案例
SOL：方案
```

对产品开发者，也可以映射为：

| 内容系统 | 产品系统 |
|---|---|
| 问题 QST | 用户痛点 / 需求 |
| 概念 CON | 产品机制 / 核心定义 |
| 观点 OPI | 产品判断 / 策略假设 |
| 案例 CAS | 用户案例 / 竞品案例 |
| 方案 SOL | 功能方案 / 运营动作 |

---

###### D. 关系层：建立可推理连接

最小可用关系可以是：

```text
回应：观点回应问题
解释：概念解释问题
证明：案例证明观点
冲突：观点之间存在张力
解决：方案解决问题
```

内容生产时，系统就可以自动形成链路：

```text
用户问题 → 核心概念 → 关键判断 → 证明案例 → 可执行方案
```

---

###### E. 输出层：生成可复用产物

至少生成 3 类结果：

1. **内容单元库**
   - 所有问题、概念、观点、案例、方案

2. **主题地图**
   - 某一主题下的相关节点集合

3. **选题装配稿**
   - 面向发布的文章 / 视频 / 课程结构草稿

---

##### 2. Agent 工程化执行清单

如果你要让 Agent 处理本地系统，不要只说：

```text
帮我整理资料。
```

而要这样说：

```text
我的输入目录是：
我的输出目录是：
本次纳入范围是：
本次排除范围是：
优先处理顺序是：
原始素材不得修改：
先建立工程骨架：
先处理样本，不要假装全量完成：
每一步都要更新状态：
所有结果必须可回溯到原文：
最后输出可核验统计：
```

这类指令的价值在于，它把 AI 从“建议者”变成“执行者”。

##### 四、反方与张力

##### 1. 不是所有人都需要内容工程

如果你只有几十篇文章，或者内容生产频率很低，搭这种系统可能过度工程化。

适合人群：

- 长期写作者
- 知识型创作者
- 课程开发者
- 自媒体团队
- 咨询顾问
- 产品研究团队
- 有大量历史文档的组织

不适合人群：

- 刚开始写作的人
- 内容量很少的人
- 没有固定主题的人
- 只追求短期爆款的人

判断标准：

> 如果翻旧内容的成本已经明显影响新内容生产，就值得做内容工程。

---

##### 2. 结构化会带来效率，也可能损失语境

把文章拆成问题、概念、观点、案例、方案，会提高复用效率。

但也有风险：

- 原文的语气被削弱
- 观点的上下文丢失
- 案例被误用
- 复杂表达被过度简化
- 内容变成机械拼装

所以人仍然需要做最终判断：

> Agent 负责调取和装配，人负责判断和表达。

---

##### 3. 显式关系很有价值，但维护成本不低

关系网络越大，越容易出现：

- 错误关系
- 重复节点
- 过时观点
- 弱相关连接
- 关系膨胀
- 维护困难

因此，系统不能只追求“节点数量”和“关系数量”。

更重要的是：

- 关系是否准确？
- 来源是否可靠？
- 节点是否可复用？
- 装配稿是否真的能提高产出质量？

---

##### 4. 2 亿 token 本身也是一种成本提醒

这个项目展示了能力，但也提醒我们：

> 工程级 Agent 使用不是免费的，规模化处理会带来真实成本。

未来做 AI 产品时，需要考虑：

- token 成本
- 执行时间
- 错误修复成本
- 人工复核成本
- 本地文件安全
- 长期维护成本

所以商业化时，不能只卖“AI 自动整理”，而要卖：

> 降低长期生产成本、提高资产复用率、形成持续生产系统。

目标不是一次性整理完，而是验证：

##### 七、对 AI/产品开发和商业系统构建的关键启示

###### 1. AI 产品的护城河不是模型，而是工作流

这套系统的价值不在于用了哪个模型，而在于：

- 规则设计
- 工程结构
- 状态管理
- 内容分类
- 关系抽取
- 可回溯机制
- 持续更新流程

未来 AI 产品真正的壁垒可能是：

> 谁能把复杂工作流产品化，谁就能把 AI 变成长期生产力。

---

###### 2. 本地资产会成为新的 AI 入口

很多人关注公开互联网数据，但对个人和组织来说，更高价值的数据往往在本地：

- 历史文档
- 项目资料
- 写作稿件
- 客户记录
- 会议纪要
- 课程内容
- 复盘材料

未来高价值 AI 应用，会围绕这些“私有资产”展开。

---

###### 3. 从 Copilot 到 Operator，再到 System Builder

AI 使用可以分三层：

| 层级 | AI 角色 | 典型任务 |
|---|---|---|
| Copilot | 辅助者 | 写文案、总结、改标题 |
| Operator | 执行者 | 批量处理、调用工具、操作文件 |
| System Builder | 系统构建者 | 建目录、定规则、建状态、持续运行 |

这篇文章展示的是第三层。

---

##### 八、一句话总结

这套内容资产工程系统的本质是：

> 把过去写过的内容，从“文件库存”升级成“可被 Agent 调用、重组和持续生产的内容操作系统”。

对内容创作者，它意味着更高复用率。

对产品开发者，它意味着 AI 工作流产品化的样板。

对商业系统构建者，它意味着：

> 真正有价值的不是一次性生成，而是把经验、内容和知识沉淀成能持续运转的系统。
