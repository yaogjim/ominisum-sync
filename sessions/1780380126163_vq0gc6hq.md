## 分析要点

- **核心高价值点**：界面中心区域应分配给当前任务的主要执行者：人主导则工作区居中，Agent主导则对话/任务区居中。
- **留存建议**：短期参考后可归档（提供了一个简洁可复用的Agent产品界面布局判断框架，适合作为AI产品设计参考。）

**知识要点**

- Agent产品设计需先判断是“人主导、Agent辅助”还是“Agent主导、人监督”。
- 主流Agent产品如Codex App、Claude Desktop、Cursor Agent多采用Agent对话区居中的设计。
- PPT、写作等高决策密度任务可能更适合人主导；代码生成等可委托任务更适合Agent主导。

**行动项**

- 设计AI产品界面前，先明确核心工作流中谁是主要执行者。
- 根据主导方调整视觉面积和界面中心位置。
- 在评审Agent产品原型时，用“谁是核心谁在中间”作为快速检查标准。

## 正文

**宝玉**

Agent 产品的设计，要看定位是以 Agent 为主还是以人为主 Agent 为辅。

如果 Agent 只是辅助，那么工作区在中间，Agent 干活区就在右侧。毕竟主要的场景都是人操作工具区，偶尔让 AI 在右侧辅助。

如果以Agent为主，那Agent干活区在中间，其他在右边。因为大部分时候你都在指挥 Agent，所以并不需要直接去操作工作区。

你看主流的 Agent：Codex App、Claude Desktop、Cursor Agent，都是 Agent 对话区在中间，其他都在右边

典型场景就是写 PPT：  
如果主要都是你自己在写 Slides，那么打开 Google Slides，自己编辑，右侧随时和 Agent 对话，辅助帮你做一些事情

如果是让 Agent 帮你写 Slides，打开 Codex，告诉你的想法，让它生成，生成好了你在右边看看，不满意告诉 Agent 去帮你调整。

## 解读（1）

### 2026-06-02 06:01:50

##### 一、总结

这篇内容的核心观点：

> **Agent 产品怎么设计界面，关键看“谁是主角”。**

- 如果是 **人主导，Agent 辅助**：  
  工作区放中间，Agent 放右侧。  
  例：人在 Google Slides 里写 PPT，AI 在旁边帮忙。

- 如果是 **Agent 主导，人指挥**：  
  Agent 对话区放中间，工作结果/工具区放右侧。  
  例：人在 Codex 里告诉 AI 做 PPT，AI 生成，人只负责检查和修改意见。

一句话：

> **谁负责主要工作，谁就占据视觉中心。**

---

##### 二、解读

这其实不是单纯的 UI 布局问题，而是产品定位问题。

###### 1. 人主导：AI 是助手

这种模式下，人还在亲自操作软件。

比如：

- 自己写文档
- 自己改 PPT
- 自己处理表格
- 自己写代码

AI 只是偶尔帮忙：

- 提建议
- 改文字
- 查资料
- 生成一小段内容

所以界面应该是：

```text
中间：人的工作区
右侧：AI 辅助区
```

因为用户主要看的是自己的编辑区域。

---

###### 2. Agent 主导：AI 是执行者

这种模式下，人不再直接操作很多细节，而是给 Agent 下指令。

比如：

- “帮我做一份商业计划书”
- “帮我改这个项目的代码”
- “帮我生成一套 PPT”
- “帮我分析这批数据”

这时用户主要是在和 Agent 沟通：

```text
中间：Agent 对话/任务区
右侧：结果预览/工具区
```

因为核心动作变成了：

> 人提出目标 → Agent 执行 → 人检查 → Agent 修改

---

##### 三、我的意见

我认同这个判断。

Agent 产品的核心不是“把 AI 放在哪里”，而是先想清楚：

> **用户到底是在亲自干活，还是在指挥 AI 干活？**

如果判断错了，产品就会别扭：

- 明明用户要自己操作，却把 AI 放太大，会干扰工作。
- 明明用户想让 AI 干活，却还让用户盯着传统工具区，会降低效率。

更通俗地说：

> **AI 是副驾驶，就坐旁边；AI 是司机，就坐中间。**

未来很多 ToB AI 产品，可能会出现两种形态：

1. **助手型 AI**：嵌入现有软件，辅助人工作。
2. **Agent 型 AI**：人只提需求，AI 调用工具完成任务。

真正好的设计，不是固定左中右布局，而是让界面匹配工作模式。  
核心原则很简单：

> **谁干活，谁居中；谁辅助，谁靠边。**

## 结构化（1）

### 2026-06-02 07:06:48

##### 主旨概括

文章讨论 **AI Agent 产品界面该如何设计**：核心判断标准是产品定位——到底是“Agent 主导工作”，还是“人主导工作、Agent 辅助”。  
一句话总结：**谁是工作核心，谁就应该占据界面中心位置。**

---

##### 1. Agent 只是辅助：工作区应在中间，Agent 放右侧

如果产品定位是 **人主要操作工具，AI 只是辅助**，那么界面设计应该让人的工作区占据中心位置。

- 中间区域：用户实际工作的地方，比如文档、PPT、表格、设计稿等。
- 右侧区域：Agent 对话或辅助区。
- 原因是：大多数时间是人在操作工具，AI 只是偶尔帮忙。

**例子：自己写 PPT**

如果你主要是自己写 Slides：

- 打开 Google Slides；
- 自己在中间编辑 PPT；
- 右侧和 Agent 对话，让它辅助做一些事，比如：
  - 帮你润色标题；
  - 生成某页文案；
  - 优化结构；
  - 提供配图建议。

这种场景下，AI 是“副驾驶”，不是主驾驶。

---

##### 2. Agent 主导工作：Agent 对话区应在中间

如果产品定位是 **Agent 主要干活，人主要发指令和检查结果**，那么 Agent 的工作区或对话区应该放在中间。

- 中间区域：Agent 对话与执行区。
- 右侧区域：结果预览、文件、工作区等辅助内容。
- 原因是：用户大部分时间不是直接操作工具，而是在指挥 Agent。

文章提到，很多主流 Agent 产品都是这种布局：

- **Codex App**
- **Claude Desktop**
- **Cursor Agent**

它们通常都是：

> Agent 对话区在中间，其他辅助内容放右侧。

---

##### 3. 同样是写 PPT，界面设计取决于谁在主导

文章用写 PPT 举了一个典型例子，说明不同产品定位下界面应该不同。

###### 场景一：人主导写 PPT

如果是你自己主要负责写：

- 中间应该是 Google Slides 这样的编辑区；
- Agent 放在右侧，随时辅助。

这种模式适合：

- 人需要深度参与；
- 内容判断主要由人完成；
- Agent 只是提高效率。

###### 场景二：Agent 主导写 PPT

如果是让 Agent 帮你写：

- 你打开 Codex 或类似 Agent 产品；
- 在中间告诉 Agent 你的想法；
- Agent 自动生成 Slides；
- 生成后，你在右侧查看结果；
- 不满意再继续指挥 Agent 修改。

这种模式下，用户主要是在“下达任务”和“验收结果”。

---

##### 4. 对 ToB AI 软件设计的延伸讨论

引用推文认为，很多 ToB AI 软件的最终形态应该是：

> 把企业业务抽象成工具调用，让 AI 能真正替企业干活。

也就是说，企业软件不只是加一个聊天框，而是要让 AI 能调用业务工具、执行真实流程。

文中提到的思路包括：

- 使用类似 **Mastra 框架** 的工具；
- 帮助小公司把业务流程抽象为 AI 可调用的工具；
- 让 AI 从“聊天助手”变成“实际办事的 Agent”。

这与宝玉的观点相呼应：如果 AI 真的是主要执行者，那么产品界面就应该围绕 Agent 来设计。

---

##### 5. 热门回复中的补充观点

###### 视觉面积决定谁是核心

有回复认为，可以简单看界面中谁的视觉面积更大：

1. 如果是 Agent 干活，对话框或 Agent 区域面积应该更大；
2. 如果是人自己干活，人操作的工作区面积应该更大。

这进一步强化了文章观点：**界面面积和位置应该反映产品的核心工作流。**

---

###### “谁是核心谁在中间”

另一条回复总结得很直接：

> 谁是核心，谁就在中间。

这也是全文最简洁的设计原则。

---

###### 不同任务对 Agent 主导程度不同

还有回复指出，不同任务适合不同的主导方式。

例如：

- 写代码时，像 **Cursor、Zed、Codex** 这类产品中，Agent 可以主导更多工作；
- 因为很多代码实现细节可以交给 AI 执行；
- 但写 PPT、写文章这类任务，往往需要人进行更多判断、审美和深度决策。

所以，不能所有 AI 产品都套一个界面模板，而要看具体任务中：

- 人需要参与多少；
- Agent 能独立完成多少；
- 最终决策权在谁手里。

---

##### 核心结论

AI Agent 产品设计的关键不是“聊天框放哪里”，而是先判断工作流：

- **人主导、AI 辅助**：工作区在中间，Agent 在右侧；
- **Agent 主导、人指挥和验收**：Agent 区在中间，结果或工具区在右侧。

最终原则可以概括为：

> 产品界面应该服务于真实工作流，谁承担主要工作，谁就应该占据界面的核心位置。
