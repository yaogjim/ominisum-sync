## 分析要点

- **核心高价值点**：最有价值的点是把工程师角色从写代码转为设计环境、约束和反馈回路，并将知识、规则与计划全部版本化沉淀到仓库中。
- **留存建议**：长期保留（内容提供了智能体优先研发的系统性框架、架构约束和知识管理实践，适合作为AI工程团队设计工作流与代码仓库治理的长期参考。）

**知识要点**

- 仓库即记录系统：对智能体不可见的知识等同于不存在，关键规范和计划必须进入版本化代码仓库。
- AGENTS.md应作为目录而非百科，通过渐进式披露控制上下文负载。
- 通过自定义linter、结构测试和CI机械化执行架构边界与品味不变量，比依赖文档和人工记忆更可靠。
- 优化目标从人类可读转向智能体可推理，优先使用API稳定、训练覆盖充分的“无聊技术”。
- 高吞吐智能体开发中，等待成本高于纠错成本，因此需要缩短PR生命周期并减少不必要的阻塞门。
- 智能体会放大仓库中的好坏模式，因此必须建立持续的“垃圾回收”和技术债清理机制。

**行动项**

- 为当前项目建立精简版\`AGENTS.md\`与结构化\`docs/\`目录，把关键架构、规范和执行计划沉淀到仓库中。
- 梳理现有系统的架构不变量，并用linter、结构测试或CI规则进行机械化约束。
- 评估当前工具链中哪些依赖对智能体不透明，优先替换为更稳定、可推理的实现或自研关键子集。
- 为智能体补齐可观测性、UI操作和本地验证能力，形成可闭环的自动修复反馈回路。
- 建立定期扫描代码异味、文档腐烂和模式漂移的后台任务，持续执行轻量化重构。

## 正文

### 工程技术：在智能体优先的世界中利用 Codex \| OpenAI

https://openai.com/zh-Hans-CN/index/harness-engineering/

在过去五个月里，我们的团队一直在进行一项实验：构建并交付一款软件产品的内部 beta 版， **其中没有一行代码是人工编写的** 。

该产品有内部日常活跃用户和外部 Alpha 测试者。它经历了交付、部署、故障和修复的整个过程。与众不同的是，每一行代码 — 从应用逻辑、测试、CI 配置、文档、可观察性到内部工具 — 全都是由 Codex 编写的。据估计，我们只用了手工编写代码所需的大约 1/10 的时间就完成了这项工作。

**人类掌舵。智能体执行。**

我们有意选择这一限制，以便构建必要的内容，从而将工程速度提升数个数量级。我们用了几周的时间来交付最终达到一百万行代码的项目。为此，我们需要了解，当软件工程团队的主要工作不再是编写代码，而是设计环境、明确意图和构建反馈回路，从而使 Codex 智能体能够可靠地工作时，会发生哪些变化。

这个帖子要说的是，在我们与智能体团队一起从零开始打造一款全新产品的过程中，所能学到的经验教训 — 哪些地方出了问题，哪些问题相互叠加，以及如何最大化利用我们唯一真正稀缺的资源：人类的时间和注意力。

#### 我们从一个空的 Git 代码仓库开始

首次提交到一个空的代码仓库是在 2025 年 8 月下旬。

初始架构 — 包括代码仓库结构、CI 配置、格式化规则、包管理器设置和应用框架 — 是在一小套现有模板的指导下，由 Codex CLI 使用 GPT‑5 生成的。就连指导智能体如何在代码仓库中工作的初始 AGENTS.md 文件本身也是由 Codex 编写的。

该系统没有预存任何人工编写的代码。从一开始，代码仓库就由智能体塑造。

五个月后，该代码仓库已经拥有约一百万行代码，从应用逻辑、基础设施、工具、文档到内部开发者工具应有尽有。在那段时间内，大约有 1,500 个 Pull Request 被打开与合并，而推动 Codex 的仅仅是一个由三名工程师组成的小团队。这相当于平均每位工程师每天处理 3.5 个 PRs 的吞吐量，而且令人惊讶的是，随着团队规模扩大到现在的七名工程师，吞吐量甚至还 *增加* 了。重要的是，这并非为了输出而输出：该产品已在数百名内测用户那里投入使用，其中包括每天都在使用的内测高级用户。

在整个开发过程中，人类从未直接直接贡献过任何代码。这成为团队的核心理念： **不手动编写代码** 。

#### 重新定义工程师的角色

由于缺乏人工编码的实践， **工程师工作的重点转向了系统、架构和杠杆作用** 。

早期进展比我们所预期的要慢，而这并不是因为 Codex 不具备相应的能力，而是因为环境的规范不够明确。该智能体缺乏实现高级目标所需的工具、抽象层和内部结构，因而无法取得进展。我们工程团队的主要任务成了协助智能体完成有用的工作。

在实践中，这意味着采用深度优先的工作方式：将更大的目标拆解为更小的构建模块（设计、代码、评审、测试等），提示智能体去构建这些模块，并使用它们去解锁更复杂的任务。当事情进行不顺利时，解决方案基本上再也不会是“再努力一点”。因为取得进展的唯一方式是让 Codex 来完成工作，而人类工程师则总是介入这项任务并追问：“究竟还需要什么样的能力，我们又该如何让这个能力对智能体来说既清晰可读又可强制执行？”

人类几乎完全通过提示与系统交互：工程师描述任务，运行智能体，并允许其打开一个 Pull Request。为了推动 PR 的完成，我们会指示 Codex 在本地审核其自身的更改，在本地和云端请求额外的特定智能体审查，对任何人工或智能体给出的反馈做出响应，并循环往复，直到所有智能体审核人员都满意为止（这实际上是一个 [Ralph Wiggum 循环 ⁠](https://ghuntley.com/loop/) ）。Codex 直接使用我们的标准开发工具（gh、本地脚本和嵌入代码仓库的技能）来收集情境，而无需人工将内容复制粘贴到 CLI 中。

人类可以审核 Pull Request（合并请求），但并非必须这样做。随着时间的推移，我们已将几乎所有的审核工作调整为用智能体对智能体的方式来处理。

#### 提高应用程序的可读性

随着代码吞吐量的增加，我们的瓶颈变成了人工 QA 能力。由于人类的时间和注意力是固定的限制因素，我们一直在努力通过令应用程序的 UI、日志和应用指标等内容对 Codex 直接可读，从而为智能体增加更多功能。

例如，我们令应用程序可以根据 git worktree 启动，因此 Codex 可以为每次更改启动并驱动一个实例。我们还将 Chrome DevTools 协议接入智能体运行时，并创建了用于处理 DOM 快照、屏幕截图和导航的技能。这使 Codex 能够复现错误、验证修复，并直接推理 UI 的行为。

我们经常看到单次 Codex 运行在单个任务上持续工作超过六个小时（通常是在人类睡眠时间）。

#### 我们将代码仓库设为记录系统

情境管理是使智能体在大型和复杂任务中有效发挥作用的最大挑战之一。我们学到的最早经验教训之一很简单： **要给 Codex 的是一张地图，而不是一本 1,000 页的说明书。**

我们尝试了“一个大型的 [`AGENTS.md` ⁠](https://agents.md/) ”方法。可想而知，这是一次失败的尝试：

- **情境是一种稀缺资源。** 一个巨大的指令文件会挤掉任务、代码和相关文档 — 因此智能体要么会错过关键约束条件，要么开始针对错误的约束条件进行优化。
- **过多的指导反而变得** ***无效*** **。** 当一切都 "重要"时，一切都不重要了。智能体最终会在本地进行模式匹配，而不是有意识地进行导航。
- **它会立即腐烂。** 一本庞杂的手册会变成陈旧规则的坟场。智能体无法判断哪些信息仍然有效，一旦人类停止维护它，此文件就会悄然成为一个颇具吸引力的麻烦源头。
- **这很难核实。** 单个 blob 不适合进行机械检查（覆盖率、新鲜度、所有权、交叉链接），因此漂移是不可避免的。

因此，我们不再将 `AGENTS.md` 视为百科全书，而是将其视为 **内容目录** 。

代码仓库的知识库位于一个结构化了的 `docs/` 目录中，此目录被当作记录系统来使用。一份简短的 `AGENTS.md` （大约 100 行）被注入到情境中，主要用作地图，并指向其他地方更深层次的真实信息来源。

代码仓库内知识存储布局。

设计文档已被编目和索引，其中包括验证状态和一套核心理念，定义了智能体优先的操作原则。 [架构文档 ⁠](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html) 提供域和包分层的顶层地图。一份高质量的文档会对每个产品领域和架构层进行评分，并随着时间的推移追踪差距。

计划被视为一流的工件。临时轻量计划用于小幅变更，而复杂工作则记录在 [执行计划 ⁠](https://cookbook.openai.com/articles/codex_exec_plans) 中，并附带进度和决策日志，这些日志会被提交到代码仓库。活跃计划、已完成计划和已知的技术债务都已进行版本控制并集中存放，使智能体能够在不依赖外部情境的情况下运行。

这实现了 **渐进式披露** ：智能体从一个小而稳定的切入点开始，并被指导下一步该去哪里查看，而不是一开始就被淹没。

我们严格执行这一点。专职的 linter 和 CI 作业会验证知识库的更新状况、是否已交叉链接且结构正确。一个定期运行的“doc-gardening”智能体会扫描那些不再反映真实代码行为的过时或废弃文档，并发起修复用的 Pull Request。

#### 目标是智能体的可读性

随着代码库的发展，Codex 的设计决策框架也需要随之演变。

由于该代码仓库完全由智能体生成，因此我们首先针对 *Codex* 的 *可读性* 进行了优化。就像团队会努力提升代码对新入职工程师的可导航性一样，我们的人类工程师的目标也是让智能体能够 **直接从代码仓库** 推理出完整的业务领域。

从智能体的角度来看，它在运行时无法在情境中访问的任何内容都是不存在的。存储在 Google Docs、聊天记录或人们头脑中的知识都无法被系统访问。代码仓库本地的、已版本化的工件（例如，代码、Markdown、模式、可执行计划）就是它所能看到的全部。

我们了解到，随着时间的推移，我们需要将越来越多的情境推送到仓库中。那次让团队在架构模式上达成一致的 Slack 讨论？如果智能体无法发现它，那么它就会像迟了三个月入职的新员工一样，对其一无所知。

为 Codex 提供更多情境意味着要组织和展示正确的信息，好令智能体能够基于这些信息进行推理，而不是用临时指令使其不堪重负。就像你会在产品原则、工程规范和团队文化（包括表情符号偏好）方面为新队友提供引导一样，将这些信息提供给智能体会带来更一致的输出。

这一框架明确了许多取舍。我们倾向于选择那些可以完全内化于在仓库中进行推理的依赖项和抽象。对智能体来说，通常被称为“枯燥”的技术，由于其可组合性、API 稳定性和在训练集里的表现，往往更容易建立模型。在某些情况下，让智能体重新实现部分功能子集比绕过公共库中不透明的上游行为更便宜。例如，我们没有引入通用的 `p-limit` 风格包，而是投入使用了我们自己的带并发的 map 辅助函数：它与我们的 OpenTelemetry 仪表紧密集成，具备 100% 的测试覆盖率，并且其行为完全符合我们的运行时预期。

将系统的更多部分转化为智能体可以检查、验证并直接修改的形式，可以直接提高杠杆效应 — 这不仅适用于 Codex，也适用于其他智能体（例如 Aardvark) 也在参与代码库的开发。

#### 规范架构与品味

仅靠文档本身，是没法保持完全由智能体生成的代码库的连贯性的。 **通过强制执行不变量，而非对实施过程进行微观管理，我们令智能体能够快速交付，而且不会削弱基础。** 例如，我们要求 Codex [在边界处解析数据形状 ⁠](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/) ，但不规定具体实现方式（模型似乎偏好 Zod，但我们没有指定特定库）。

智能体在具有 [严格边界和可预测结构 ⁠](https://bits.logic.inc/p/ai-is-forcing-us-to-write-good-code) 的环境中最为高效，因此我们围绕一个严格的架构模型构建了该应用。每个业务域都划分为一组固定的层，依赖方向经过严格验证，并且仅允许有限的一组边。这些约束是通过自定义的 linter（当然是由 Codex 生成的！）和结构测试机械地强制执行的。

下图展示了规则：在每个业务领域内（例如应用设置），代码只能“向前”依赖于一组固定的层（Types → Config → Repo → Service → Runtime → UI）。横切关注点（认证、连接器、遥测、功能标志）通过一个单一的显式接口进入：Providers。其他任何内容都不被允许，并将通过自动化方式强制执行。

题为“具有明确交叉界限的分层领域架构”的图表。在业务逻辑域内存在以下模块：Types → Config → Repo，以及 Providers → Service → Runtime → UI，底部是 App Wiring + UI。一个 Utils 模块位于界限之外，并向 Providers 提供输入。

这种架构通常要等到你拥有数百名工程师时才会推迟。对于编码智能体来说，这是一个早期的先决条件：有了约束，速度才不会下降，架构才不会漂移。

在实践中，我们通过自定义的代码检查器和结构测试来强制执行这些规则，并辅以一小组“品味不变式”。例如，我们通过自定义 lint 静态地强制执行结构化日志记录、模式和类型的命名约定、文件大小限制，以及特定平台的可靠性要求。由于这些 lint 是自定义的，我们编写错误信息时会在智能体情境中注入修复指令。

在以人为本的工作流程中，这些规则可能会让人感到迂腐或束缚。有了智能体，它们就成了倍增器：一旦编码，它们就能立即应用于所有地方。

同时，我们还明确指出了哪些地方需要限制，哪些地方不需要限制。这类似于领导一个大型工程平台组织：在中央层面强制执行边界，在本地层面允许自主权。你非常重视界限、正确性和可重复性。在这些边界内，你允许团队或智能体在解决方案的表达方式上拥有很大的自由。

生成的代码不总是符合人类的风格偏好，这也没关系。只要输出是正确的、可维护的，并且对未来的智能体运行而言清晰易读，就可以算作达标。

人类的品味会不断反馈到系统中。审查评论、重构的 Pull Request 和面向用户的 Bug 会被记录为文档更新，或直接编码到工具中。当文档不够完善时，我们会将规则转化为代码

#### 吞吐量改变了合并的理念

随着 Codex 的吞吐量增加，许多传统的工程规范变得不再有效。

该代码仓库在运行过程中尽量减少阻塞合并门。Pull Request 的生命周期很短。测试偶发失败通常通过后续重跑来解决，而不是无限期地阻碍进展。在一个智能体吞吐量远超人类注意力的系统中，纠错成本低，而等待成本高。

在低吞吐量环境中，这样做是不负责任的。而在这里，这通常是正确的选择。

#### “智能体生成”实际上意味着什么

当我们说代码库是由 Codex 智能体生成的，我们指的是整个代码库。

智能体的产出包括：

- 产品代码与测试
- CI 配置和发布工具
- 内部开发者工具
- 文档和设计历史
- 评估框架
- 审阅评论和回复
- 管理代码仓库本身的脚本
- 生产仪表板定义文件

人类始终参与其中，但工作的抽象层次与过去不同。我们优先处理工作，将用户反馈转化为验收标准，并对结果进行验证。当智能体遇到困难时，我们将其视为一个信号：识别缺失的内容 — 工具、指导与约束、文档 — 并将其反馈到代码仓库中，始终由 Codex 自己编写修复。

智能体可以直接使用我们的标准开发工具。他们会拉取审查反馈、在行内回复、推送更新，并且经常压缩并合并他们自己的 Pull Request（合并请求）。

#### 不断提高的自主水平

随着越来越多的开发环节被直接编码到系统中 — 包括测试、验证、审查、反馈处理和恢复 — 该代码仓库最近跨过了一个重要门槛，使 Codex 能够端到端地驱动一个新功能。

给定一个提示，智能体现在可以：

- 验证代码库的当前状态
- 重现已报告的漏洞
- 录制一个演示故障的视频
- 实施修复措施
- 通过运行应用程序来验证修复
- 录制第二个视频，演示解决方案
- 打开 Pull Request
- 回应智能体和人类反馈
- 检测并修复构建故障
- 仅在需要判断时才交由人工处理
- 合并更改

此行为在很大程度上取决于此代码仓库的具体结构和工具，不应在没有类似投入的情况下假定它可以泛化 — 至少目前还不行。

#### 熵与垃圾收集

**完全自主的智能体也引入了新的问题。** Codex 会复现代码仓库中已存在的模式 — 甚至包括那些不均衡或不够理想的模式。随着时间的推移，这不可避免地导致漂移。

最初，人类是手动处理这个问题的。我们的团队过去每周五（占一周的20%）都要花时间清理“AI 残渣”。不出所料，那并不具备可扩展性。

相反，我们开始将我们称为“黄金原则”的内容直接编码到代码仓库中，并建立了一个循环清理流程。这些原则是带有主观意见的机械规则，旨在保持代码库的可读性和一致性，以便将来运行智能体。例如：(1) 我们更倾向于使用共享的实用程序包，而不是手工编写的辅助工具，以便将不变式集中管理；(2) 我们不会使用“YOLO 式”探测数据 — 我们会验证边界，或依赖类型化的 SDK，这样智能体就不会意外地基于猜测的结构进行构建。我们会定期运行一组后台 Codex 任务，扫描偏差、更新质量等级，并发起有针对性的重构 Pull Request。其中大多数都可以在一分钟内完成审查并自动合并。

其功能类似于垃圾回收。技术债务就像一笔高息贷款：不断地以小额贷款的方式偿还债务，总比让债务不断累积，再痛苦地一次解决要好得多。人类的品味一旦被捕捉，就会持续应用于每一行代码。这也使我们能够每天发现并解决不良模式，而不是让它们在代码库中传播数天或数周。

#### 我们仍在学习的内容

到目前为止，这一策略在 OpenAI 的内部发布和采纳过程中表现良好。为真实用户打造真实产品，帮助我们将投资锚定在现实中，并引导我们实现长期的可维护性。

我们尚不清楚的是，在一个完全由智能体生成的系统中，架构连贯性会如何随着时间的推移而演变。我们仍在学习人类的判断力在哪些方面能发挥最大作用，以及如何对这种判断力进行编码，使其发挥更大作用。我们也不知道，随着时间的推移，模型的功能不断增强，这一系统将如何演变。

显而易见的是：构建软件仍然需要纪律，但纪律更多地体现在支撑结构上，而不是代码上。保持代码库一致性的工具、抽象和反馈回路变得越发重要。

**我们当前最棘手的挑战集中在设计环境、反馈回路和控制系统方面** ，帮助智能体实现我们的目标：大规模构建和维护复杂、可靠的软件。

随着像 Codex 这样的智能体在软件生命周期中占据越来越大的比重，这些问题将变得更加重要。我们希望通过分享一些早期的经验教训，帮助你理清投入精力的方向，以便 你可以直接开始构建 。

#### 概念 2：机械化执行

#### 核心思想

> 通过强制执行不变量，而非对实施过程进行微观管理

- 横切关注点必须通过 Providers 进入

Error: File exceeds 500 lines.

#### 概念 5：吞吐量改变合并理念

#### 原文要点

当 Codex 的吞吐量远超人类注意力时，传统的工程规范变得不再有效。

核心转变： **纠错成本低，等待成本高。**

#### 具体变化

##### PR 生命周期缩短

- 1,500 个 PR / 5 个月 / 3 人 = 人均每天 3.5 个 PR
- PR 不再是需要精雕细琢的大作，而是快速流动的小变更
- 扩展到 7 人后吞吐量仍在增长（说明瓶颈不在人数）

##### 合并门控最小化

- 尽量减少阻塞合并的门
- 测试偶发失败 → 后续重跑解决，不无限期阻塞
- 在低吞吐量环境中这是不负责任的；在高吞吐量环境中这通常是正确的

##### 智能体审查智能体

- 人类可以审核 PR，但 **不是必须的**
- 随着时间推移，几乎所有审核都调整为智能体对智能体
- Ralph Wiggum 循环：Codex 本地审核 → 请求额外智能体审查 → 对反馈做出响应 → 循环直到所有审核通过

#### 来自其他文章的补充

实战结论：

- ❌ 每次改动跑全量测试
- ✅ 优化迭代速度，快速发现和修复问题
- ✅ 便宜模型（Sonnet/Haiku）做子任务，贵模型（Opus）做编排

长时间自主执行需要：

1. 文件系统 + git 追踪持久化工作
2. **Ralph Loop** 拦截退出，在新上下文窗口中重注入原始提示词
3. 规划 + 自我验证分解目标为步骤

当编码从手写转向引导生成时，开发者偏好作为选型标准的重要性下降。组织可能基于 harness 的质量和"AI 友好度"来选择技术栈 → 技术栈趋向收敛。

#### 关键洞察

这个概念的本质是一个 **经济学问题** ：

```
传统模式：人力贵 + 吞吐量低 → 每个 PR 都要精心审查 → 阻塞门多
Harness 模式：智能体便宜 + 吞吐量高 → 快速迭代修复 → 阻塞门少
```

前提条件：必须有足够的 **背压机制** （测试、lint、结构检查）来保证基本质量，否则就不是"快速迭代"而是"快速腐烂"。

#### 概念 3：熵管理与垃圾回收

#### 问题

智能体会复现仓库中已存在的模式—— **包括坏模式** 。

随着时间推移，不可避免地产生漂移（drift）：

- 重复的辅助函数散落各处
- 不一致的错误处理风格
- 基于猜测的数据结构（YOLO 式探测）
- 过时的文档与实际代码不符

#### 失败方案：人工清理

> 团队每周五花 20% 时间清理"AI 残渣"。不出所料，不具备可扩展性。

##### "黄金规则"（Golden Rules）

带主观意见的机械规则，编码进仓库：

1. **共享实用程序包 &gt; 手写辅助工具** — 不变式集中管理
2. **不做 YOLO 探测** — 在边界验证数据，或使用类型化 SDK
3. **偏好自有实现的关键子集** — 与自有遥测集成、100% 测试覆盖、行为完全可预测

##### 垃圾回收流程

```
定期后台 Codex 任务
  → 扫描偏差
  → 更新质量评分
  → 发起重构 PR
  → 大多数 1 分钟内审查 + 自动合并
```

#### 类比

技术债 = 高息贷款

- ✅ 每天小额偿还（持续垃圾回收）
- ❌ 累积到痛苦时一次性清偿（重写/大重构）

#### 关键洞察

> 人类的品味一旦被捕捉（编码为规则），就会持续应用于每一行代码。

品味的传播路径：

```
人类审查评论 → 文档更新 → lint 规则 → 自动应用于所有代码
```

#### 从 Harness Engineering 到产品实践：对资深产品经理的启发

##### 一句话结论

这组内容的核心，不是“AI 会不会替代工程师写代码”，而是：**当智能体成为主要执行者后，产品与研发的竞争力，正在从“人写得多快”，转向“组织能否把目标、约束、反馈、知识和质量机制设计成一套可被 AI 执行的系统”。**

对产品经理而言，这意味着你的价值重心也在迁移：  
**从“定义需求的人”，升级为“设计产品—工程—智能体协同操作系统的人”。**

---

##### 一、这组内容共同揭示了什么

###### 1. 软件生产的基本单位，正在从“功能开发”变成“系统编排”
OpenAI 的实践不是单纯提效，而是在重构软件生产函数：

- 人类不再直接参与大量编码，而是负责：
  - 设计环境
  - 明确意图
  - 构建反馈回路
  - 设定边界与不变量
  - 验证结果
- 智能体负责：
  - 生成实现
  - 自测
  - 自审
  - 修复
  - 提交与迭代

这意味着，未来的产品研发不再只是“需求 -> 开发 -> 测试 -> 上线”的流水线，而更像：

**目标定义 -> 约束编码 -> 环境供给 -> 智能体执行 -> 自动反馈 -> 持续纠偏**

对于产品经理，这背后是一次很大的方法论切换：  
你不只是写 PRD，而是在**设计一个能持续产出正确结果的生产系统**。

---

###### 2. “知识是否进入仓库”，决定了它是否能转化为生产力
这些内容反复强调一句话：

> 不在仓库里的东西，对智能体来说不存在。

这不仅是工程原则，对产品管理也是强提醒。很多组织里的高价值信息，仍然散落在：

- Slack / 飞书群讨论
- 会议纪要
- 产品经理脑中的隐性判断
- 销售/客服口头反馈
- 各种未结构化文档

对人来说，这些信息“好像存在”；  
但对 AI 和跨团队协同来说，它们其实并不存在。

这背后的产品启发是：

- **产品知识必须从“口口相传”变成“结构化资产”**
- 否则 AI 无法利用，团队也无法复用
- 产品团队的输出不能只停留在“写一份文档”，而要升级为：
  - 可索引
  - 可引用
  - 可校验
  - 可版本化
  - 可执行

换句话说，未来 PM 的工作成果不应只是 PPT/PRD，而应是**产品知识库与决策系统**。

---

###### 3. AI 时代真正稀缺的，不是代码，而是“高质量判断”
OpenAI 文中最重要的一句之一是：

> 唯一真正稀缺的资源：人类的时间和注意力。

在高吞吐智能体环境里，代码不再是主要瓶颈，真正的瓶颈变成：

- 哪些问题值得做
- 什么叫“做对”
- 哪些约束必须守住
- 哪些异常需要人工介入
- 何时应该放宽门槛，何时必须卡死
- 如何把“品味”与“判断”转成规则

这对产品经理非常关键。因为这本来就是 PM 最接近的领域。  
AI 提升的不是“要不要 PM”，而是**倒逼 PM 更聚焦高阶判断，而不是低效协调与文档搬运**。

所以未来优秀 PM 的区分点，越来越不是：

- 会不会写长文档
- 会不会开会推动
- 会不会盯排期

而是：

- 会不会定义清晰目标与验收标准
- 会不会把模糊问题压缩成 AI 可执行问题
- 会不会设计反馈闭环
- 会不会把组织经验沉淀成机制
- 会不会在速度与质量之间设计合适的经济结构

---

##### 二、对产品实践最重要的 8 个启发

##### 1. PRD 要从“说明书”升级为“执行协议”

传统 PRD 的假设是：  
“人类读完后，凭经验理解并落地。”

但智能体优先的环境下，好的需求文档更像：

- 目标定义
- 边界条件
- 验收标准
- 决策依据
- 失败信号
- 回退策略
- 关联上下文入口

也就是说，未来 PRD 更像一种 **Protocol / Contract**，而不是“详尽叙述文”。

###### 对产品实践的具体启发
你写需求时，应更多增加以下内容：

- 这个功能要优化的核心目标是什么
- 哪些指标是成功标准
- 哪些是绝不能破坏的不变量
- 用户旅程里哪些节点最关键
- 哪些异常是可接受的，哪些必须阻断
- 如果 AI 需要更多背景，它应去哪份文档找

###### 一个简单对比
传统 PRD 更像：
> 做一个会员中心，展示权益、购买入口、订单记录……

AI 友好的 PRD 更像：
> 目标：将会员页到支付成功转化率提升 15%。  
> 关键约束：支付路径不可增加超过 1 步；首屏加载 < 1.2s；退款入口必须在 2 次点击内可达。  
> 关键旅程：访客进入会员页 -> 查看权益 -> 选择套餐 -> 支付 -> 成功页。  
> 验收标准：四条关键旅程无阻塞；移动端首屏 CLS < 0.1；埋点完整。  
> 参考：`docs/pricing-principles.md`、`docs/member-user-journey.md`

这不是“写得更长”，而是**写得更可执行**。

---

##### 2. PM 的核心能力，变成“把模糊意图压缩成可验证任务”

这些内容反复体现一个原则：

> 出问题时，答案不是“再努力一点”，而是“缺什么上下文/工具/约束”。

这本质上也是产品工作中大量低效的根源。很多需求推进慢，不是团队不努力，而是：

- 问题定义不清
- 目标粒度过粗
- 依赖关系不透明
- 验收标准不明确
- 反馈机制滞后
- 决策没有沉淀为规则

###### 这对 PM 的启发
未来优秀 PM 应更像“任务编译器”：

把模糊业务目标，逐层编译成：

1. 业务目标
2. 用户问题
3. 产品策略
4. 关键路径
5. 约束条件
6. 验收标准
7. 监控指标
8. 异常处理规则

你越能把上层模糊意图编译成下层清晰结构，AI 与团队执行效率就越高。

---

##### 3. 产品管理的“源代码”，应该进入版本化知识库

OpenAI 的实践里，仓库不仅存代码，也存：

- design docs
- exec plans
- product specs
- quality score
- reliability / security
- 决策日志

这意味着：**产品文档不再是附属物，而是生产系统的一部分。**

###### 对产品团队的启发
你可以把产品知识库分为几类：

- `product-specs/`：功能规格
- `user-journeys/`：关键用户旅程
- `decision-logs/`：为什么这么做
- `core-principles/`：产品原则
- `metrics/`：核心指标定义
- `experiments/`：实验结论与复盘
- `known-tradeoffs/`：已知权衡
- `tech-debt-from-product/`：由产品复杂性引入的债务

###### 为什么这很重要
因为对 AI 来说，真正可用的不是“你知道什么”，而是“系统能读到什么”。  
对组织来说，真正可复用的不是“曾经讨论过什么”，而是“今天还能被检索、校验、引用什么”。

这会改变 PM 的产出物定义：  
**你不是在交付一份需求，而是在给组织留下可持续复用的决策资产。**

---

##### 4. 好产品组织的关键，不是“给 AI 更多自由”，而是“给 AI 更好的边界”

一个很反直觉但非常重要的洞察是：

> 限制解空间，反而让 AI 更可靠。

在产品领域，我们常容易误以为“给团队更多自由”“让 AI 自主发挥”就会更创新。  
但这组内容说明，在复杂系统里，真正带来高质量产出的，是：

- 清晰边界
- 稳定接口
- 固定结构
- 可验证规则
- 少而强的约束

###### 对产品实践的启发
产品规范体系要从“倡导型”转向“约束型”。

例如：

- 设计系统不是建议，而是默认强制
- 埋点规范不是上线前补，而是需求的一部分
- 文案规范不是运营偏好，而是结构规则
- 权限模型、状态机、异常分支要提前定义
- 关键体验红线要被自动检查

这会带来一个变化：  
产品经理不只是“提出想法”，而要参与定义“不变量”。

###### 适合 PM 去定义的不变量示例
- 核心转化链路不允许新增无必要步骤
- 关键页面的首屏时间不超过某阈值
- 退款/注销等负向操作不能被隐藏
- 重要状态必须可解释，不允许黑盒反馈
- 用户操作失败时必须给出下一步建议

你定义得越机械化、越可检查，执行越稳定。

---

##### 5. 用户体验的设计，要转向“可观测、可验证、可回放”

OpenAI 特别强调，让智能体可以直接“读懂”应用：

- 能启动独立实例
- 能看 UI
- 能截屏
- 能读 DOM
- 能查日志
- 能查指标
- 能定位性能问题

这对产品实践有极强启发。  
过去 PM 往往通过“人工体验 + 用户反馈 + 数据报表”理解问题；未来更先进的产品团队会要求系统天然具备：

- 关键旅程可回放
- 关键状态可观察
- 关键异常可归因
- 关键体验可自动验证

###### 这意味着 PM 需要更重视“产品可观测性”
不仅看结果指标，还要建设：

- 关键旅程埋点图谱
- 漏斗中的异常节点
- 体验级 SLA/SLO
- 用户反馈与日志、行为数据的映射
- 核心操作的视频/回放证据链

最终目标不是“看报表”，而是让系统能自动回答：

- 哪条用户旅程坏了
- 坏在哪一步
- 对哪些用户影响最大
- 最近哪次改动导致的
- 修复后是否恢复

未来最强的 PM，通常也是最会定义“反馈回路”的 PM。

---

##### 6. 吞吐量上升后，产品迭代节奏和决策机制都要重构

内容 6 的核心很值得产品侧重视：

> 纠错成本低，等待成本高。

当 AI 能以极高频率产出小改动时，传统“大需求评审—大版本上线—长周期验证”的节奏会越来越笨重。

###### 对产品实践的启发
很多产品流程会从“大批量、低频、强审批”转向：

- 更小粒度的变更
- 更短周期的验证
- 更自动化的评估
- 更动态的合并策略
- 更依赖后验反馈，而不是前置讨论

这意味着 PM 的工作方式也要变化：

###### 从“前置穷尽讨论”转向“定义护栏后快速试错”
你不需要在一开始把所有问题都想清楚，而要把以下内容想清楚：

- 哪些能快速上线验证
- 哪些必须卡死
- 哪些风险可以通过回滚/灰度控制
- 哪些指标能快速证明方向对错
- 哪些异常会触发人工介入

这本质上是把产品管理从“规划学”变成“控制论”。

---

##### 7. 产品复杂性将不再被自然压制，反而更容易失控

AI 提高开发效率后，一个危险变化是：  
**做东西变便宜了，导致做太多东西也变容易了。**

也就是说，过去限制功能膨胀的一个重要因素是“研发成本高”；  
现在这个约束被显著削弱，产品团队更容易滑向：

- 功能泛滥
- 状态膨胀
- 规则叠加
- 体验分叉
- 设计系统破碎
- 文档快速失真

OpenAI 提出的“熵管理”和“垃圾回收”尤其值得 PM 重视。  
未来产品管理的一项重要职责，不是推动更多功能，而是**持续清理复杂性**。

###### 对产品的现实启发
你需要引入“产品垃圾回收机制”：

- 定期清理低使用功能
- 合并重复路径
- 统一相近概念与命名
- 清点失效规则/策略
- 删除无人维护的配置项
- 纠正文档与实际行为不一致的问题

###### 一个关键判断
未来很多产品失败，不是输在“做不出来”，而是输在“太容易做出来，结果越做越乱”。

因此，PM 的一个高级能力会变成：  
**控制增长带来的熵。**

---

##### 8. 产品经理要学会把“品味”翻译成“规则”

内容 7 中很重要的一点是：

> 人类的品味一旦被捕捉，就会持续应用于每一行代码。

这对产品同样成立。  
很多资深 PM 的价值，来自隐性的体验判断，例如：

- 什么叫“可信”
- 什么叫“不过度打扰”
- 什么叫“简洁但不空”
- 什么叫“高效但不粗暴”
- 什么叫“商业化但不损害长期关系”

问题是，过去这些常停留在个人经验里，难以规模化。  
AI 时代最大的机会之一，就是把这些“高阶品味”逐步转译为：

- 产品原则
- 文案规则
- 交互约束
- 风险等级
- 优先级模型
- 审核清单
- 自动检查项

###### 这会极大提升你的组织杠杆
因为你不再依赖自己一遍遍 review、解释、救火，  
而是把自己的判断沉淀成可以持续复制的系统能力。

从这个角度看，资深 PM 的真正壁垒，可能不是“懂业务”，而是：

**能否把自己的业务理解与产品品味，编码成组织可复用的规则。**

---

##### 三、对产品经理角色的重构：从 PM 到“产品控制系统设计者”

综合这些内容，可以看到 PM 角色正在出现三层升级。

###### 第一层：从需求管理者，变成意图设计者
过去你写“做什么”；  
未来你要更清楚地定义：

- 为什么做
- 成功长什么样
- 哪些边界不可破
- 哪些异常允许存在
- 怎样让 AI/团队知道自己做对了

---

###### 第二层：从跨团队协调者，变成知识系统建设者
过去你大量时间花在同步和沟通上；  
未来高杠杆 PM 更重要的工作是建设：

- 产品知识库
- 决策日志
- 指标字典
- 规则体系
- 实验资产
- 反馈机制

你做的不是一次协同，而是让未来协同成本越来越低。

---

###### 第三层：从项目推进者，变成反馈回路与治理机制设计者
未来的 PM 将更多关注：

- 哪些环节自动化
- 哪些信号足够判断成败
- 哪些问题可以交给 AI 闭环
- 哪些问题必须升级人工判断
- 怎样持续降低系统熵

这已经不是传统 PM，而更像产品领域的“系统治理者”。

---

##### 四、对产品实践最可落地的行动框架

如果把这些内容转成你的产品工作方法，我建议用下面这个五层框架。

##### 1. 把“需求管理”升级为“意图管理”
每个重要需求都要补足 5 类信息：

- 目标：想改变什么业务结果
- 用户问题：为谁解决什么问题
- 约束：不可突破的边界
- 验收：什么叫完成
- 反馈：上线后看哪些信号

这会大幅提高 AI、研发、设计对需求的可执行性理解。

---

##### 2. 把“产品文档”升级为“产品知识库”
建议沉淀以下资产：

- `core-principles.md`：产品原则
- `user-journeys/`：关键旅程
- `decision-logs/`：重要决策记录
- `specs/`：功能规格
- `metrics.md`：指标定义
- `tradeoffs.md`：关键权衡
- `known-issues.md`：已知问题
- `experiment-history/`：实验与复盘

重点不是文件名，而是形成一个原则：  
**产品知识必须被版本化、结构化、可引用。**

---

##### 3. 把“经验判断”升级为“护栏机制”
把常见争议提前变成规则：

- 哪类需求必须 A/B Test
- 哪类页面必须满足性能阈值
- 哪类弹窗必须限制触达频次
- 哪类风险词必须人工审核
- 哪类链路不能因商业化而加步骤
- 哪类功能若 90 天低使用必须触发清理评估

当规则足够清晰，团队速度才会更快，而不是更慢。

---

##### 4. 把“上线”升级为“可观测实验”
每个重要功能上线时，不只问“能不能发”，还要问：

- 是否有核心旅程埋点
- 是否有关键异常监控
- 是否有体验阈值
- 是否有回滚条件
- 是否能在 24/48/72 小时内判断成败

这样产品迭代才不会变成黑箱试错。

---

##### 5. 把“复盘”升级为“垃圾回收”
建议建立固定节奏的产品垃圾回收：

- 每周扫一轮低价值复杂性
- 每月评估功能冗余
- 每季度重构概念体系与导航结构
- 同步修正文档与真实行为
- 把典型错误沉淀为新规则

核心原则是：  
**不是等系统乱了再治理，而是持续小额偿还复杂性债务。**

##### 五、对未来产品组织的更大推演

##### 1. 产品组织会从“人驱动协作”转向“系统驱动协作”
未来很多组织效率差距，不再主要来自人才密度，而来自：

- 是否有高质量知识仓库
- 是否有清晰规则体系
- 是否有可执行验收标准
- 是否有自动反馈闭环
- 是否有持续垃圾回收机制

换句话说，组织能力会越来越“产品化”。

---

##### 2. PM 的产出会越来越像“组织接口”
未来优秀 PM 提供的不只是方向，而是：

- 一套让设计可执行的说明
- 一套让研发可实现的约束
- 一套让 AI 可调用的上下文
- 一套让运营可理解的策略
- 一套让管理层可追踪的指标

PM 不再只是“桥梁”，而是“接口定义者”。

---

##### 3. 技术、产品、运营之间的边界会变浅
因为当知识和规则被结构化后，很多原本属于某个岗位的工作，都会被系统吸收一部分。

比如：

- 产品验收的一部分被自动化
- 设计规范检查被工具化
- 文案一致性被规则化
- QA 的一部分被智能体接管
- 研发评审的一部分转为机器审查

这意味着 PM 需要更懂：

- 数据
- 系统结构
- 反馈回路
- AI 工作方式
- 规则设计

不会要求 PM 去写代码，但会要求 PM 能设计“AI 能工作的上下文”。

---

##### 4. 产品竞争力会越来越来自“组织复利”
最强的团队，不一定是单次创意最惊艳的团队，而是：

- 知识能沉淀
- 经验能复用
- 错误能转规则
- 规则能自动执行
- 复杂性能被持续回收

这是一种非常强的复利型组织能力。  
而 PM 在其中，正好位于“意图—规则—反馈—迭代”的核心位置。

## 结构化（1）

### 2026-04-07 10:57:19

#### 智能体时代的产品系统设计：精炼总结

这篇文章的核心观点是：在“智能体优先”的软件工程中，工程师的主要职责不再是亲自写代码，而是**设计环境、明确意图、搭建反馈回路**，让 AI 智能体稳定地产出高质量软件。  
OpenAI 的实践表明，只要系统设计得当，少量工程师就能借助 Codex 在极短时间内构建出大规模、可上线的真实产品。

##### 1. 背景：从“人写代码”转向“人类掌舵，智能体执行”

- OpenAI 团队进行了一个持续 **5 个月** 的实验：从空 Git 仓库开始，构建一个真实可用的软件产品。
- 整个项目最终达到约 **100 万行代码**，且**没有一行代码由人工直接编写**。
- 代码范围不仅包括产品逻辑，还覆盖：
  - 测试
  - CI 配置
  - 文档
  - 可观测性
  - 内部开发工具
  - 生产仪表板定义等
- 由 **3 名工程师** 驱动，期间共处理约 **1,500 个 Pull Request**，相当于**人均每天约 3.5 个 PR**。
- 后续团队扩展到 **7 人** 后，吞吐量还在继续增长。
- 整体开发时间大约只是手工编写代码所需时间的 **1/10**。
- 产品并非实验玩具，而是已经被**数百名内测用户**使用，其中有每天都在使用的高频用户。

**一句话理解**：他们不是在证明“AI 会写代码”，而是在验证“一个由智能体主导的软件工程系统是否能真的交付产品”。  

---

##### 2. 工程师角色重定义：重点变成系统设计，而不是编码

- 由于团队坚持“**不手动写代码**”，工程师的工作重心发生转移：
  - 设计系统和架构
  - 拆解任务
  - 写提示词
  - 审核结果
  - 补足工具、约束和文档
- 早期进展慢，不是因为 Codex 能力不够，而是因为**环境和规范不够清晰**。
- 当智能体做不好任务时，正确做法不是“再试一次”，而是追问：
  - 缺了什么工具？
  - 缺了什么上下文？
  - 缺了什么约束？
- 团队采用“**深度优先**”方式推进工作：
  - 先拆分大目标
  - 让智能体先构建小模块
  - 再逐步组合成更复杂能力

**例子**：如果智能体做不好复杂功能，不是直接让它“把功能做完”，而是先让它分别生成设计、测试、验证机制、审查逻辑，再拼成完整流程。  

---

##### 3. 提升智能体能力：让应用本身对 Codex“可读、可操作、可验证”

文章强调，真正的瓶颈不是写代码，而是**人工 QA 和人工注意力**。因此他们不断增强智能体自己检查系统的能力。

###### 3.1 让智能体能直接操作应用

- 应用支持按 **git worktree** 启动。
- 这样 Codex 每次改动都可以拉起一个独立实例，自行验证改动效果。
- 团队把 **Chrome DevTools 协议**接入智能体运行时，并提供处理以下内容的技能：
  - DOM 快照
  - 截图
  - 页面导航
- 这使 Codex 可以自己：
  - 复现 bug
  - 观察 UI 行为
  - 修复问题
  - 重启应用并循环验证

**例子**：Codex 可以先记录修复前界面状态，再修复代码，最后重新打开页面确认 UI 是否恢复正常。  

###### 3.2 让智能体能看懂日志、指标和追踪

- 团队给 Codex 接入了本地临时可观测性栈。
- 智能体可以直接查询：
  - 日志：`LogQL`
  - 指标：`PromQL`
  - 追踪：`TraceQL`
- 每个工作树都有独立、临时的可观测性环境，任务结束后自动删除。

这让更高级的提示成为可能，比如：

- “确保服务启动时间在 **800ms** 以内”
- “四条关键用户路径中，任何一个跨度都不能超过 **2 秒**”

###### 3.3 智能体可以长时间自主工作

- 单次 Codex 运行经常能持续工作 **6 小时以上**。
- 很多任务是在**人类睡觉时**自动完成的。

**核心意义**：一旦 UI、日志、性能指标都对智能体开放，AI 就不只是“写代码工具”，而是变成了“能自查自修的工程执行者”。  

---

##### 4. 仓库即记录系统：不在仓库里的知识，对智能体来说就不存在

这是全文最重要的原则之一。

- 对智能体来说，运行时上下文以外的知识就是“不存在”：
  - Slack 讨论：对人类可见，对智能体不可见
  - Google Docs：对人类可见，对智能体不可见
  - 团队成员脑中的经验：对智能体不可见
  - 仓库中的 Markdown、代码、计划、规则：对智能体可见
- 因此，团队把代码仓库当作**唯一记录系统（source of truth）**。

###### 4.1 AGENTS.md 不是百科，而是目录

他们曾尝试写一个很大的 `AGENTS.md`，结果失败，原因有三点：

- **挤占上下文**：大文件会占掉有限上下文窗口，反而让任务和代码本身进不来
- **难维护**：内容很快过时
- **难验证**：无法机械检查更新状态、覆盖率和所有权

后来改成：

- `AGENTS.md` 只保留约 **100 行**，作为“目录页”
- 详细知识放进结构化的 `docs/` 目录

例如仓库中会有：

- `ARCHITECTURE.md`
- `docs/design-docs/`
- `docs/exec-plans/`
- `docs/product-specs/`
- `docs/references/`
- `QUALITY_SCORE.md`
- `RELIABILITY.md`
- `SECURITY.md`

###### 4.2 渐进式披露，而不是一次塞满

- 智能体先从小入口进入
- 再根据索引逐步查看更深层文档
- 这样比一开始塞给它“1000 页说明书”更有效

###### 4.3 文档也要被持续维护

- 团队用专门的 **linter 和 CI** 检查文档：
  - 是否更新
  - 是否交叉链接
  - 是否结构正确
- 还会运行一个“**doc-gardening**”智能体，定期扫描过时文档并自动发起修复 PR。

**一句话理解**：要让 AI 真能接手工程工作，知识必须被写进仓库，并且可被持续校验。  

---

##### 5. 优化目标改变：不是只追求人类可读，而是追求“智能体可推理”

文章提出了一个关键转变：代码库要优先对智能体友好。

- 团队不再只关注“新人类工程师是否容易上手”
- 更关注“智能体能否直接从仓库推理出业务和架构”

###### 5.1 偏好“无聊技术”

- 团队更倾向于选择 API 稳定、训练数据覆盖更好的技术栈
- 因为这类技术对智能体更容易建模，行为也更可预测

###### 5.2 有时自研比接第三方库更划算

文中给了一个很典型的例子：

- 他们没有引入通用的 `p-limit` 风格库
- 而是自己实现了一个支持并发的 `map` 辅助函数

原因是它：

- 能与自家的 OpenTelemetry 仪表深度集成
- 有 **100% 测试覆盖**
- 行为完全符合自身运行时预期
- 比依赖一个“上游行为不透明”的库更容易让智能体理解和维护

**启发**：智能体时代，技术选型不再只看“开发者喜不喜欢”，还要看“AI 能不能稳定理解和操作”。  

---

##### 6. 用机械约束维持架构：不要微观指挥，而要强制执行不变量

仅靠文档无法保证一个纯智能体生成的代码库长期保持一致性，因此他们把很多规则做成了**机械化约束**。

###### 6.1 架构采用严格分层

每个业务域都必须遵循固定层次：

`Types → Config → Repo → Service → Runtime → UI`

横切关注点（如认证、连接器、遥测、功能标志）只能通过 `Providers` 进入。

约束规则包括：

- 依赖方向只能“向前”
- 不允许跨层乱连
- 违反规则会被自定义 linter 和结构测试拦截

###### 6.2 约束重点是“边界”，不是“实现细节”

- 例如，要求在边界处解析数据结构
- 但不强制必须用哪一个具体库（虽然模型自己常选 Zod）

这体现的是：

- 中央层面严格规定边界和正确性
- 局部实现方式保留自由

###### 6.3 自定义 lint 不只报错，还告诉智能体怎么修

他们的 lint 错误信息里会直接给出修复路径。

**例子**：  
不是只说“文件超过 500 行”，而是进一步提示：

- 按 `ARCHITECTURE.md` 拆模块
- 类型放到 `types/`
- 服务逻辑放到 `service/`

这样错误提示就不是“人看报错”，而是“AI 可执行的修复说明”。

**核心意义**：对人类来说显得刻板的规则，对智能体来说反而是效率倍增器。  

---

##### 7. 高吞吐量改变了工程管理方式：等待比纠错更贵

当 AI 的产出速度远快于人类注意力时，传统工程流程会失效。

###### 7.1 PR 生命周期变短

- 他们把 PR 处理成短周期、小步快跑
- 不是把每个 PR 打磨成“大作品”

###### 7.2 阻塞性门禁减少

- 仓库尽量减少会卡住合并的门槛
- 测试偶发失败时，通常选择后续重跑，而不是无限等待

文章指出：

- 在低吞吐量团队里，这样做可能不负责任
- 但在高吞吐量、低纠错成本的智能体系统里，这反而更合理

###### 7.3 审查也越来越智能体化

- 人类可以审 PR，但不是必须
- 后期大多数审查变成“**智能体审查智能体**”
- Codex 会：
  - 本地自审
  - 请求其他智能体评审
  - 根据反馈继续修改
  - 循环到所有审查者满意为止

**本质变化**：过去的默认思路是“尽量防错再合并”；现在更像“快速合并、快速纠偏”。  

---

##### 8. 智能体不仅写代码，还能完成端到端开发流程

文章特别说明，“智能体生成”不是只指代码，而是**整个工程活动**都由智能体完成。

包含内容有：

- 产品代码和测试
- CI 与发布工具
- 内部开发工具
- 文档与设计历史
- 评估框架
- 审查评论与回复
- 管理仓库本身的脚本
- 生产仪表板定义

目前，Codex 已能在合适的仓库结构和工具支持下，端到端完成新功能开发：

- 检查当前代码库状态
- 复现 bug
- 录制故障演示视频
- 实施修复
- 启动应用验证
- 录制修复后视频
- 发起 PR
- 响应人类或智能体反馈
- 修复构建失败
- 只在需要判断时升级给人类
- 最终合并变更

不过作者也强调：这很依赖当前仓库的结构和配套工具，**不能简单假设所有团队都能直接复制**。  

---

##### 9. 熵与垃圾回收：AI 会复制好模式，也会复制坏模式

完全自主的智能体会持续放大现有模式，所以“坏味道”也会被复制。

###### 9.1 最初靠人工清理，成本太高

- 团队曾经每周五拿出 **20% 的时间**清理“AI 残渣”
- 例如：
  - 重复辅助函数
  - 不一致的错误处理
  - 猜测式数据结构
  - 过时文档
- 这种方式显然不可扩展

###### 9.2 后来把“人类品味”编码成黄金规则

他们把偏好的工程原则变成机械规则，例如：

- **共享工具包优先于手写零散 helper**
- **禁止 YOLO 式数据探测**
  - 要么在边界验证数据
  - 要么依赖类型化 SDK
- 对关键子集功能，宁可自研可控实现，也不要依赖不透明上游行为

###### 9.3 像垃圾回收一样持续扫债

- 后台定期运行 Codex 任务
- 扫描偏差
- 更新质量评分
- 自动发起有针对性的重构 PR
- 大多数 PR 可以在 **1 分钟内**完成审查并自动合并

文章用一个很形象的比喻：

- **技术债像高息贷款**
- 最好每天小额偿还
- 不要拖到最后集中爆炸

**重要结论**：一旦把人类的判断和品味编码进系统，它就能持续、自动地作用于每一行代码。  

---

##### 10. 仍未解决的问题：真正难的是环境与控制系统设计

文章最后并没有把这套方法说成“已完全成熟”，而是明确指出还有很多未知。

目前仍在探索的问题包括：

- 完全由智能体生成的系统，长期架构连贯性能否稳定保持？
- 哪些判断最适合由人类保留？
- 如何把这些判断进一步编码进系统？
- 随着模型能力持续增强，整套工程体系会如何演化？

但作者认为有一点已经很明确：

- 软件工程依然需要纪律
- 只是纪律不再主要体现为“人如何写代码”
- 而是体现为：
  - 环境如何设计
  - 反馈回路如何搭建
  - 约束和控制系统如何建立

---

##### 11. 文章结论：智能体时代，真正的工程杠杆在“支撑结构”

可以把全文浓缩成三句话：

- **智能体不会自动带来高效工程，真正决定成败的是环境设计。**
- **代码库必须成为知识、计划、规则和反馈的统一载体。**
- **未来工程师最重要的能力，不只是写代码，而是把判断力转化成智能体可执行的系统。**

**一个最直观的例子**：  
过去遇到 bug，工程师会自己看日志、点页面、改代码、跑测试；  
而在这套系统里，工程师更像是在搭建一个“自动修 bug 的流水线”，让 Codex 能自己完成这些环节，只在人类判断真正不可替代时才接管。
