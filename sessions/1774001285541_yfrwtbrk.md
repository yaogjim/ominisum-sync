- **核心高价值点**：最有价值的是将技能视为“可包含脚本、数据、配置和钩子的文件夹系统”，通过渐进式披露与可组合脚本提升代理执行质量。
- **留存建议**：长期保留（内容提供了较系统的技能分类、设计原则与团队分发经验，适合作为构建 AI 编码工作流的参考框架。）

**知识要点**

- 高质量技能应重点沉淀易错点、避免显而易见的信息，并保留适应具体场景的灵活性
- 技能目录可作为上下文工程载体，利用参考文件、模板、脚本和稳定存储实现渐进式披露与记忆

**Thariq**

### 构建 Claude 代码的经验：我们如何运用技能

技能已成为 Claude Code 中最常用的扩展点之一。它们灵活、易于制作且易于分发。

但这种灵活性也使得难以确定什么最有效。值得培养什么样的技能？打造一个好技能的秘诀是什么？什么时候与他人分享这些技能？

我们在 Anthropic 公司广泛使用 Claude Code 中的技能，其中数百个技能正处于活跃使用状态。这些是我们学到的关于如何利用技能加速开发的经验教训。

#### 什么是技能？

如果你是技能新手，我建议

[阅读我们的文档](https://code.claude.com/docs/en/skills)或者观看我们最新的关于

[新的 Skilljar 关于座席技能](https://anthropic.skilljar.com/introduction-to-agent-skills)

，这篇文章将假设你已经对技能有一定的了解。

我们常听到关于技能的一个常见误解是，它们“只是 Markdown 文件”，但技能最有趣的部分在于，它们不仅仅是文本文件。它们是文件夹，可以包含脚本、资源、数据等，代理可以发现、探索和操作这些内容。

在 Claude Code 中，技能也拥有

[多种多样的配置选项](https://code.claude.com/docs/en/skills#frontmatter-reference)包括注册动态钩子。

我们发现，Claude Code 中一些最有趣的技能会创造性地使用这些配置选项和文件夹结构。

### 技能类型

在整理完我们所有的技能后，我们注意到它们聚集到了几个常见的类别中。最优秀的技能能清晰地归入某一类；而那些较难归类的技能则横跨多个类别。这不是一份权威清单，但它是一种很好的思考方式，能帮助你判断你的组织是否缺少某些技能。

![Image](https://pbs.twimg.com/media/HDlvMmubEAIzF-N?format=jpg&name=large)

#### 库和 API 参考

解释如何正确使用库、CLI 或 SDK 的技能。这些可以是针对内部库或 Claude Code 有时难以处理的通用库。这些技能通常包括一个参考代码片段文件夹，以及一份 Claude 在编写脚本时应避免的注意事项列表。

示例：

- billing-lib — 你内部的账单库：边缘情况、潜在陷阱等等。
- internal-platform-cli — 内部 CLI 包装器的每个子命令及其使用场景示例
- 前端设计——让 Claude 在你的设计系统中表现更好

#### 2\. 产品验证

描述如何测试或验证代码是否正常工作的技能。这些技能通常与 playwright、tmux 等外部工具配合使用，以进行验证。

验证技能对于确保 Claude 的输出正确非常有用。让工程师花一周时间来使你的验证技能变得出色是值得的。

考虑诸如让 Claude 录制其输出的视频以便你能确切看到它测试了什么，或者在每个步骤中对状态执行程序化断言等技术。这些通常通过在技能中包含各种脚本来实现。

示例：

- signup-flow-driver — 在无头浏览器中执行注册→邮箱验证→新用户引导流程，带有用于在每个步骤中断言状态的钩子
- checkout-verifier — 使用 Stripe 测试卡驱动结账界面，验证发票实际处于正确状态
- tmux-cli-driver — 用于需要 TTY 的交互式命令行界面测试

#### 3\. 数据获取与分析

与你的数据和监控栈相关的技能。这些技能可能包括用于带凭证获取数据的库、特定的仪表盘 ID 等，以及关于常见工作流或获取数据方法的说明。

示例：

- 漏斗查询 — 我需要参与哪些事件才能看到注册→激活→付费的流程，加上实际包含规范用户 ID 的表
- 队列对比 — 比较两个队列的留存率或转化率，标记具有统计显著性的差异，关联到细分定义
- Grafana — 数据源 UID、集群名称、问题 → 仪表盘查找表

#### 4\. 业务流程与团队自动化

能够将重复工作流程自动转化为单个命令的技能。这些技能通常是相当简单的指令，但可能对其他技能或 MCPs 有更复杂的依赖关系。对于这些技能，将之前的结果保存到日志文件中可以帮助模型保持一致性，并反思工作流程的先前执行情况。

示例：

- standup-post — 聚合你的工单跟踪器、GitHub 活动和之前的 Slack → 格式化的站会，仅增量
- create-&lt;ticket-system&gt;-ticket — 强制验证模式（有效的枚举值、必填字段）以及创建后工作流（通知审核人、在 Slack 中关联）
- 每周总结 — 合并 PR + 关闭工单 + 部署 → 格式化总结帖子

#### 5\. 代码脚手架与模板

生成特定功能框架样板的技能。你可以将这些技能与可组合的脚本结合使用。当你的脚手架有仅靠代码无法完全覆盖的自然语言需求时，这些技能尤其有用。

示例：

- new-&lt;框架&gt;-工作流 — 利用你的注释搭建新的服务/工作流/处理程序
- new-migration — 你的迁移文件模板加上常见陷阱
- create-app — 新的内部应用，其身份验证、日志记录和部署配置已预先配置

#### 6\. 代码质量与评审

组织内部确保代码质量并帮助进行代码审查的技能。这些技能可能包括确定性脚本或工具，以实现最大的健壮性。您可能希望将这些技能作为钩子的一部分或在 GitHub Action 中自动运行。

- 对抗性审查——生成一个全新视角子代理进行批评，实施修复，迭代直到发现的问题降级为吹毛求疵的细节
- 代码风格 — 强制执行代码风格，尤其是 Claude 默认情况下做得不好的风格。
- 测试实践 — 关于如何编写测试及测试什么的说明。

#### 7\. CI/CD &amp; 部署

帮助你在代码库内部获取、推送和部署代码的技能。这些技能可能会引用其他技能来收集数据。

示例：

- babysit-pr — 监控 PR → 重试不稳定的 CI → 解决合并冲突 → 启用自动合并
- 部署-&lt;服务&gt; → 构建 → 冒烟测试 → 逐步流量发布并进行错误率比较 → 回归时自动回滚
- cherry-pick-prod — 隔离的工作树 → cherry-pick → 冲突解决 → 带模板的拉取请求

#### 8\. 操作手册

能够处理一个症状（例如 Slack 讨论线程、告警或错误签名），进行多工具调查并生成结构化报告的技能。

示例：

- &lt;service&gt;-debugging — 映射症状 → 工具 → 查询模式 用于您的高流量服务
- oncall-runner — 获取告警 → 检查常见问题 → 格式化发现结果
- 日志关联器——给定请求 ID，从所有可能涉及该请求的系统中拉取匹配的日志

#### 9\. 基础设施运维

执行日常维护和操作流程的技能——其中一些涉及破坏性操作，这些操作得益于防护措施。这些技能让工程师更容易在关键操作中遵循最佳实践。

示例：

- &lt;资源&gt;-orphans — 查找孤儿 Pod/卷 → 发送到 Slack → 浸泡期 → 用户确认 → 级联清理
- 依赖管理 — 您的组织的依赖审批流程
- 成本调查 — '为什么我们的存储/流出费用突然激增' 针对特定的存储桶和查询模式

#### 不要说显而易见的话

Claude Code 对你的代码库非常了解，Claude 也对编程非常了解，包括许多默认观点。如果你要展示一项主要关于知识的技能，尽量聚焦于能让 Claude 跳出常规思维方式的信息。

The

[前端设计技能](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md)是一个很好的例子 — 它是由 Anthropic 的一名工程师通过与客户迭代来改进 Claude 的设计品味，避免了像 Inter 字体和紫色渐变这样的经典模式而开发的。

#### 构建一个注意事项部分

![Image](https://pbs.twimg.com/media/HDlwEG1bEAUdmcV?format=jpg&name=large)

任何技能中最重要的内容是易错点部分。这些部分应该基于 Claude 在使用你的技能时遇到的常见失败点来构建。理想情况下，你应该随着时间更新你的技能以涵盖这些易错点。

#### 使用文件系统和渐进式展示

![Image](https://pbs.twimg.com/media/HDlwhSjbEAIJSc9?format=jpg&name=large)

就像我们之前说的，技能是一个文件夹，而不仅仅是一个 Markdown 文件。你应该将整个文件系统视为一种上下文工程和渐进式披露的形式。告诉 Claude 你技能中的文件有哪些，它会在适当的时候读取这些文件。

渐进式披露最简单的形式是指向其他 Markdown 文件供 Claude 使用。例如，你可以将详细的函数签名和使用示例拆分为 references/api.md。

另一个例子：如果你的最终输出是一个 markdown 文件，你可能会在 assets/中包含一个用于它的模板文件，供复制和使用。

你可以创建包含参考资料、脚本、示例等的文件夹，这些文件夹能帮助 Claude 更高效地工作。

#### 描述字段用于模型

当 Claude Code 启动会话时，它会构建一个包含每个可用技能及其描述的列表。Claude 会扫描这个列表以判断“是否有适用于该请求的技能”。这意味着描述字段不是摘要——而是描述何时触发此 PR。

#### 内存与数据存储

![Image](https://pbs.twimg.com/media/HDoImh1bEAU-mMI?format=jpg&name=large)

一些技能可以通过在其中存储数据来包含一种记忆形式。你可以将数据存储在任何东西中，从像仅追加文本日志文件或 JSON 文件这样简单的存储方式，到像 SQLite 数据库这样复杂的存储方式。

例如，一个 standup-post 技能可能会维护一个 standups.log 文件，记录它所写的每一篇帖子，这意味着下次运行时，Claude 会读取自己的历史记录，并能判断自昨天以来有哪些内容发生了变化。

存储在技能目录中的数据在升级技能时可能会被删除，因此你应该将其存储在稳定的文件夹中，截至今日我们提供 \`${CLAUDE\_PLUGIN\_DATA}\` 作为每个插件的稳定文件夹以存储数据。

例如，在你的数据科学技能中，你可能拥有一个用于从事件源获取数据的函数库。为了让 Claude 进行复杂分析，你可以给它一组辅助函数，像这样：

#### 按需钩子

技能可以包含仅在调用该技能时激活，并持续到会话结束的钩子。对于那些不想一直运行但有时又非常有用的更具倾向性的钩子，可以使用这种方式。

例如：

- / 小心 — 通过 Bash 上的 PreToolUse 匹配器阻止 rm -rf、DROP TABLE、force-push、kubectl delete 命令。只有当你确定在操作生产环境时才应该启用此功能——一直启用会让你抓狂
- / 冻结 — 阻止任何不在特定目录中的编辑/写入操作。很有用
- 调试时："我想要添加日志，但我总是不小心地‘修复’无关的"

### 分配技能

技能的最大好处之一是你可以与团队中的其他成员分享它们。

有两种方式你可能会与他人分享技能：

- 检查你的技能到你的仓库中（位于 ./.claude/skills 下）
- 创建一个插件并拥有一个 Claude Code Plugin 市场，用户可以在其中上传和安装插件（在文档中了解更多信息：
  [文档](https://code.claude.com/docs/en/plugin-marketplaces)此处）

对于仅使用相对较少代码仓库的小型团队而言，将技能检入代码仓库的方式效果良好。但每一项被检入的技能都会为模型的上下文增加一些内容。随着团队规模的扩大，内部插件市场允许你分发技能，并让团队自主决定安装哪些技能。

#### 管理市场

你如何决定哪些技能进入技能市场？人们如何提交这些技能？

我们没有一个集中的团队来做决策；相反，我们尝试自然地发现最有用的技能。如果你有一项希望人们尝试的技能，你可以将其上传到 GitHub 的沙箱文件夹，然后在 Slack 或其他论坛中引导人们查看它。

一旦某个技能获得发展势头（这由技能所有者决定），他们就可以提交 PR 以将其发布到市场。

需要注意的是，创建不良或冗余的技能可能相当容易，因此在发布前确保有某种管理方法是很重要的。

#### 创作技能

你可能需要拥有相互依赖的技能。例如，你可能有一个上传文件的文件上传技能，以及一个生成 CSV 文件并上传它的 CSV 生成技能。这种依赖管理尚未原生集成到市场或技能中，但你可以直接通过名称引用其他技能，并且如果其他技能已安装，模型将调用它们。

#### 测量技能

要了解某个技能的表现情况，我们使用 PreToolUse hook，它能让我们在公司内部记录技能使用情况（

[示例代码](https://gist.github.com/ThariqS/24defad423d701746e23dc19aace4de5)）这意味着我们可以找出那些使用频繁的或与预期相比触发不足的技能。

### 结论

技能是智能体极其强大且灵活的工具，但目前仍处于早期阶段，我们都在摸索如何最好地使用它们。

与其说这是一份权威指南，不如把它看作是我们见过的实用技巧的大杂烩。理解技能的最佳方式是开始行动、尝试，并看看什么适合你。我们的大多数技巧最初都只是几行代码和一个需要注意的地方，并且随着 Claude 遇到新的边缘情况，人们不断补充完善，它们才变得更好。

我希望这很有帮助，如果你有任何问题，请告诉我。

#### 文章主旨

这篇文章分享了 Anthropic 团队在使用 Claude Code「技能（Skills）」过程中的实战经验：技能之所以强大，不只是因为它能写提示词，而是因为它可以把脚本、配置、数据、钩子和工作流整合成可复用的能力模块。  
文章核心想说明两件事：第一，哪些类型的技能最值得做；第二，怎样把技能做得真正好用、可扩展、可分享。

##### 1. 什么是技能：它不只是一个 Markdown 文件

- 很多人误以为技能“只是一个 Markdown 文件”，但作者强调，技能本质上是一个**文件夹**。
- 这个文件夹里不仅能放说明文档，还能放：
  - 脚本
  - 资源文件
  - 数据
  - 配置项
  - 动态钩子（hooks）
- 也就是说，技能不是单纯“告诉 Claude 怎么做”，而是能真正提供**可执行能力和辅助材料**，让 Claude 自己去发现、读取和调用。

**通俗理解：**  
如果只写一段说明，Claude 只能“照着理解”；但如果你把 API 示例、校验脚本、模板文件、日志记录都放进去，它就像拿到了一整套工具箱，而不是一张便条。

---

##### 2. 技能主要分成 9 类：帮助团队系统化补齐能力

作者整理了团队内**数百个正在活跃使用的技能**，发现它们大致会聚集到 9 类。这个分类不是官方标准，但很适合帮助团队检查自己“缺了哪些能力”。

###### 2.1 库和 API 参考

- 用来解释内部库、CLI、SDK 应该如何正确使用。
- 常见内容包括：
  - 参考代码片段
  - 常见陷阱
  - 不推荐写法
- 适合解决 Claude 对某些库“理解不稳定”或“容易误用”的问题。

**案例：**
- `billing-lib`：内部计费库的边界情况和坑点
- `internal-platform-cli`：内部 CLI 每个子命令的使用方式
- 前端设计技能：帮助 Claude 更好遵守设计系统

###### 2.2 产品验证

- 用于测试或验证代码是否真的工作正常。
- 通常会结合外部工具，如：
  - `playwright`
  - `tmux`
- 作者特别强调：**非常值得让工程师花一周时间把验证技能打磨好。**

**关键做法：**
- 录制测试过程视频，方便人类确认 Claude 实际测了什么
- 每个步骤加入程序化断言，验证状态是否正确

**案例：**
- `signup-flow-driver`：自动跑注册 → 邮箱验证 → 新手引导流程
- `checkout-verifier`：用 Stripe 测试卡验证结账和发票状态
- `tmux-cli-driver`：测试依赖 TTY 的交互式 CLI

###### 2.3 数据获取与分析

- 面向数据仓库、监控平台、分析系统的技能。
- 主要作用是让 Claude 更高效地：
  - 拉数据
  - 查监控
  - 跑分析
  - 找仪表盘

**案例：**
- 漏斗查询：分析“注册 → 激活 → 付费”的事件链路
- 队列对比：比较两个队列的留存或转化率，并标记统计显著差异
- `Grafana`：维护数据源 UID、集群名、问题到仪表盘的映射表

###### 2.4 业务流程与团队自动化

- 把重复性工作变成“一条命令”。
- 这类技能说明通常不复杂，但背后可能依赖其他技能或 MCP。
- 作者提到一个很实用的点：**把之前结果写入日志文件，有助于模型保持一致性。**

**案例：**
- `standup-post`：聚合工单、GitHub 活动和历史 Slack 内容，自动生成站会更新
- `create-&lt;ticket-system>-ticket`：校验字段后创建工单，并通知审核人
- 每周总结：把 PR、关闭工单和部署信息合并成总结帖

###### 2.5 代码脚手架与模板

- 用于快速生成某类功能的基础代码。
- 特别适合那些“不能只靠模板代码，还需要一些自然语言约束”的场景。

**案例：**
- `new-&lt;framework>-workflow`：生成新服务、工作流或处理器
- `new-migration`：带迁移模板和常见坑提醒
- `create-app`：创建预配置好认证、日志和部署的内部应用

###### 2.6 代码质量与评审

- 用于提高代码质量，辅助审查。
- 可以接入钩子或 GitHub Action 自动运行，增强稳定性。

**案例：**
- 对抗性审查：生成“挑刺”子代理来批评代码，修复后反复迭代，直到只剩吹毛求疵的问题
- 代码风格：强制执行 Claude 默认不擅长遵守的团队风格
- 测试实践：告诉 Claude 应该测什么、怎么写测试

###### 2.7 CI/CD 与部署

- 面向提代码、合并、部署、回滚等流程。
- 有些技能会调用其他技能来先收集信息，再执行部署动作。

**案例：**
- `babysit-pr`：监控 PR、重试不稳定 CI、处理冲突、打开自动合并
- `deploy-&lt;service>`：构建 → 冒烟测试 → 灰度发布 → 错误率比较 → 回归自动回滚
- `cherry-pick-prod`：隔离工作树、挑提交、解决冲突并生成 PR

###### 2.8 操作手册（Runbooks）

- 面向故障排查、告警处理、多系统联查。
- 可以把一个“现象”转成结构化调查流程。

**案例：**
- `&lt;service>-debugging`：针对高流量服务，维护“症状 → 工具 → 查询模式”的映射
- `oncall-runner`：接告警后检查常见原因并整理结果
- 日志关联器：根据 request ID 从多个系统拉相关日志

###### 2.9 基础设施运维

- 用于日常运维和维护流程，常涉及有风险的操作。
- 这类技能特别适合加入防护措施，避免误操作。

**案例：**
- `&lt;resource>-orphans`：查孤儿 Pod/卷 → 发 Slack → 观察期 → 用户确认 → 清理
- 依赖管理：组织内部依赖审批流程
- 成本调查：分析存储或流量费用为什么突然上涨

##### 3. 怎样把技能写好：作者总结的实用技巧

这一部分是全文最有价值的地方，重点在于“技能要如何设计，才能真的让 Claude 表现更好”。

###### 3.1 不要写显而易见的话

- Claude 本来就懂很多编程知识，也对代码库有较强理解。
- 所以技能最有价值的部分，不是重复常识，而是补充 Claude **默认不知道、但你团队非常在意的信息**。

**案例：**
- 前端设计技能不是泛泛谈“页面要美观”，而是专门训练 Claude 避开一些常见但俗套的选择，比如：
  - `Inter` 字体
  - 紫色渐变

**启示：**
技能应该提供“纠偏信息”，而不是重复教科书。

###### 3.2 一定要写“易错点”部分

- 作者明确说：**任何技能里最重要的内容，就是易错点（pitfalls）部分。**
- 这些内容应该来自 Claude 在实际使用中反复犯的错误。
- 最理想的做法是随着使用不断更新，让技能越来越“抗坑”。

**通俗理解：**  
一个好技能，不是写得最全，而是最懂“Claude 会在哪摔跤”。

###### 3.3 用文件系统做“渐进式展示”

- 技能是文件夹，所以不要把所有内容都塞进一个主文档。
- 更好的方式是：
  - 主文档只放关键指引
  - 详细内容拆到其他文件里按需读取

**例子：**
- 把函数签名和调用示例拆到 `references/api.md`
- 把输出模板放到 `assets/` 中供 Claude 复制使用

这样做的好处是：
- 降低主提示冗长度
- 保持上下文简洁
- 让 Claude 只在需要时再读详细资料

###### 3.4 不要把 Claude “绑死”

- 技能需要可复用，所以不要把指令写得过于死板。
- 应提供必要信息，但保留足够灵活性，让 Claude 能根据实际情况调整。

**本质上：**
技能不是流程脚本的“硬编码版本”，而是“带边界的指导系统”。

###### 3.5 重视设置与配置

- 某些技能需要基于用户上下文完成初始化。
- 例如一个自动发站会到 Slack 的技能，应该知道发到哪个频道。
- 推荐把这类信息存放在技能目录中的 `config.json`。
- 如果没配置，Claude 可以主动询问用户。
- 如果想让 Claude 以结构化方式提问，可以使用 `AskUserQuestion` 工具。

###### 3.6 描述字段不是摘要，而是触发条件

- Claude Code 在启动时，会读取每个技能的名称和描述，判断“这个请求要不要触发某技能”。
- 所以描述字段不应该只是介绍内容，而应该说明：**什么时候该用这个技能。**

**这点非常重要：**
如果描述写得像简介，技能可能触发不足；如果描述写清使用场景，Claude 更容易在合适时机调用它。

###### 3.7 给技能加入“记忆”

- 技能可以通过存数据形成某种“长期记忆”。
- 存储形式可以很简单，也可以复杂：
  - 追加日志文件
  - JSON 文件
  - SQLite 数据库

**案例：**
- `standup-post` 技能维护一个 `standups.log`
- 下次运行时，Claude 会读取之前自己写过的站会内容，从而知道“自昨天以来有哪些变化”

**注意：**
- 如果数据放在技能目录内，升级技能时可能丢失
- 官方提供 `${CLAUDE_PLUGIN_DATA}` 作为每个插件的稳定数据目录

###### 3.8 把脚本和代码也纳入技能

- 作者强调：你能给 Claude 的最强工具之一就是**代码本身**。
- 如果把常用脚本和函数库放进技能里，Claude 每次就不必从零写样板代码，而能专注于：
  - 调用已有能力
  - 组合工具
  - 决定下一步行动

**案例：**
- 在数据科学技能中预置事件源获取函数
- Claude 再临时生成脚本，把这些函数组合起来分析“周二到底发生了什么”

###### 3.9 用“按需钩子”增强安全和约束

- 技能可以带只在调用后启用、并持续到会话结束的钩子。
- 适合那些“不该一直开着，但某些时候非常有用”的规则。

**案例：**
- `/careful`：在 `PreToolUse` 阶段阻止危险命令，如：
  - `rm -rf`
  - `DROP TABLE`
  - `force-push`
  - `kubectl delete`
- `/freeze`：阻止对指定目录外的写操作，适合调试时避免“顺手改了无关代码”

##### 4. 技能如何分发：小团队适合仓库内管理，大团队适合市场机制

###### 4.1 两种分发方式

作者提到两种常见共享方法：

- 直接把技能检入仓库：`./.claude/skills`
- 打包成插件，通过 Claude Code Plugin 市场上传和安装

###### 4.2 适用场景不同

- **小团队、代码仓少**：直接放仓库里通常够用
- **团队变大时**：插件市场更合适，因为不是所有人都需要全部技能

原因在于：
- 每个检入仓库的技能，都会给模型上下文增加一点负担
- 技能太多会让系统变重，也容易重叠

###### 4.3 市场需要治理

- 作者说他们没有一个中心化团队统一审批
- 更常见的做法是让技能先自然扩散：
  - 先上传到 GitHub 沙箱目录
  - 再在 Slack 等地方邀请大家试用
- 一旦某个技能真正被大家用起来，拥有者再提交 PR 发布到市场

**核心观点：**
- 好技能需要“被验证后再推广”
- 因为低质量或重复技能其实很容易做出来

---

##### 5. 技能还能互相调用，也应该被衡量效果

###### 5.1 技能之间可以互相依赖

- 现实中，一个技能往往会依赖另一个技能。
- 例如：
  - 一个技能负责上传文件
  - 另一个技能负责生成 CSV 后再调用上传技能
- 目前这种依赖关系还**没有原生集成到市场或技能系统里**
- 但可以直接通过名称引用其他技能，只要对方已安装，模型就能调用

###### 5.2 要衡量技能是否真的好用

- 作者团队通过 `PreToolUse hook` 来记录技能使用情况。
- 这样可以知道：
  - 哪些技能用得很多
  - 哪些技能应该被触发却没有触发
- 这说明技能不是“写完就结束”，而是要像产品一样持续观察和优化。

---

##### 6. 结论：技能仍处早期，但已经是非常强大的智能体扩展方式

- 作者认为，技能是智能体系统中**极其强大且灵活的工具**，但整体还处于早期探索阶段。
- 这篇文章不是权威手册，更像是一份高价值的实战经验汇总。
- 最重要的建议不是“先读懂全部理论”，而是：
  - 先动手做
  - 从小技能开始
  - 随着 Claude 暴露新边界情况不断补充

**作者的经验总结很接地气：**
- 大多数好技能一开始都只是“几行代码 + 一个注意事项”
- 之后才在真实使用中不断演化成熟

###### 7.2 技能也需要定期清理，避免膨胀

- 一条热门回复提到一个很实用的做法：
  - 给每个技能加“最后使用日期”
  - 每两周检查一次长期未使用技能
- 这样可以保持技能列表精简，减少：
  - 冗余
  - 重叠
  - 上下文负担

##### 总结一句话

这篇文章最重要的启发是：**技能的价值不在于“写一段提示词”，而在于把团队知识、脚本、验证、配置、记忆和安全约束，沉淀成 Claude 可反复调用的能力单元。**  
真正好用的技能，往往不是最复杂的，而是最了解实际工作流、最能减少错误、并且能随着使用不断迭代的那种。
