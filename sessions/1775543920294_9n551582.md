## 分析要点

- **核心高价值点**：最有价值的点是把“文档访问接口”统一抽象为代理天然熟悉的文件系统操作，从而绕过复杂工具schema和碎片化RAG上下文的问题。
- **留存建议**：短期保留，适合作为Agent文档访问方案的案例参考（提出了将文档站点映射为文件系统的清晰产品思路，对Agent工具设计有启发）

**知识要点**

- RAG对跨页面语义和精确函数签名场景可能不足，文件系统式浏览能补足完整上下文
- 代理对Unix文件操作已有强先验，使用grep、cat、tree等命令比新增专用工具更自然
- 文档网站可被规范化为目录树，并通过缓存、按需加载和共享命名空间提升访问效率
- 客户端内存Shell替代容器沙箱可显著降低静态只读文档访问的启动成本

**行动项**

- 评估你当前Agent工作流中，文档查询是否可由文件系统式接口替代部分RAG检索
- 用一两个高频API文档站点做PoC，对比grep/cat流程与现有MCP或RAG方案的准确率和延迟
- 重点验证其在跨页依赖、参数签名准确性和大规模文档站上的实际效果
- 如计划采用，先补充对隐私遥测、缓存时效和失败回退机制的审查

**Arlan**

### 将整个网络转变为文件系统。

代码幻觉不是模型问题，而是数据问题。

每天，API 都会引入破坏性变更、弃用端点并重命名参数。模型无法跟上，因为它们的训练数据落后了数月，有时甚至落后数年。因此，你的代理编写的代码看起来完美、编译无误，但在运行时失败，因为该库在六个月前就已经更新了。

标准解决方案是 RAG：将文档分块、嵌入，然后检索与查询匹配的 Top-K 片段。这能帮你完成 80%的工作，直到答案分布在三页内容中，或者代理需要精确的函数签名（而这些签名在分块过程中未被保留）。检索只能得到片段，但代理需要完整的信息。

我们想要一些不同的东西。如果一个代理能够直接查阅文档？不是检索片段，而是真正地浏览它们。就像你用 grep 搜索代码库或者用 cat 查看 README 文件一样。

文件系统的概念

Unix 五十年前就解决了这个问题。设备、进程、套接字。一切皆文件。一个统一的接口。\`open\`、\`read\`、\`write\`、\`close\`。你不需要为每个资源学习新的 API。你只需学习文件，而这种知识适用于所有地方。

代理在 Unix 系统上进行了预训练。数十亿个文件系统交互的 token 被嵌入到权重中。\`tree\`、\`grep\`、\`find\`。这些不是代理需要学习使用的工具，而是代理已经掌握的工具。每个代码模型都见过数百万个类似\`cat README.md\`、\`grep -r "auth" .\`和\`find . -name "\*.md"\`的示例。

![Image](https://pbs.twimg.com/media/HFLDuzZbMAA2_2c?format=jpg&name=large)

图 1：统一抽象原则的演变：从 Unix 的文件系统（70 年代）历经 DevOps 代码制品（10 年代）到代理型 AI 的基于文件的上下文和内存（20 年代）

与 MCP 相比，每个工具都需要 JSON 模式、自然语言描述以及谨慎的参数构建。每个工具都会消耗上下文窗口空间，并引入被误用的风险面。而文件系统则不需要这些。

所以我们问：如果网络上的每个文档网站都能成为一个你可以用\`cd\`进入的目录会怎样？

它是如何工作的


这就是整个界面。没有 API 密钥，无需安装，无需配置。一条命令就能给你一个 bash shell，在这个 shell 中，任何文档都会被挂载为文件系统。用 tree 浏览，用 grep 搜索，用 cat 查看单个页面。将其通过管道传递给你的代理。

在幕后，发生了三件事。

1\. 目录

当你首次访问一个 URL 时，后端会抓取该网站。它会识别 \`llms.txt\`，检测 OpenAPI 规范，处理重定向。每个页面都会变成一个文件。URL \`

[https://docs.stripe.com/api/charges/create](https://docs.stripe.com/api/charges/create)\` 变为 \`/api/charges/create.md\`。

棘手的部分是路径规范化。文档站点的 URL 结构极其不一致：有些将所有内容放在 \`/docs/\` 下，有些放在 \`/api/reference/\` 下，有些则直接使用根目录。我们会在所有已索引的 URL 中自动检测通用路径前缀并将其剥离，这样在你访问到实际内容之前，文件系统不会呈现三层深的结构。

```python
def detect_common_path_prefix(urls, base_url):
    # Split all paths into segments, find shared prefix
    path_segments = [p.split('/') for p in paths]
    common_prefix = []
    for i in range(min(len(segs) for segs in path_segments)):
        segments_at_i = [segs[i] for segs in path_segments]
        if len(set(segments_at_i)) == 1:
            common_prefix.append(segments_at_i[0])
        else:
            break
    return '/' + '/'.join(common_prefix)
```

结果：\`

[https://better-auth.com/docs/installation](https://better-auth.com/docs/installation)\` 变为 \`/installation.md\`，而非 \`/docs/installation.md\`。文件系统反映的是你对文档的理解方式，而非 URL 的实际结构。

2\. 服务

后端将文件系统操作作为 API 端点公开：

```shell
GET  /shell-docs/load?url=...              # status + full dump
GET  /shell-docs/{namespace}/read?path=... # single file
POST /shell-docs/{namespace}/grep          # regex search
GET  /shell-docs/{namespace}/ls?path=...   # directory listing
GET  /shell-docs/{namespace}/tree          # full tree
GET  /shell-docs/{namespace}/find?pattern= # glob matching
```

所有内容均采用 gzip 压缩。\`/load\` 端点在一个请求中返回状态和所有文件。启动一个 Shell 会话只需一次往返请求。响应会被缓存（\`Cache-Control: public, max-age=300\`），并且 CLI 会在 \`\~/.cache/nia-docs/\` 维护一个磁盘缓存，该缓存通过命名空间和 \`indexed\_at\` 时间戳进行索引。再次访问相同文档？瞬间完成。

命名空间是共享的。当有人索引 \`

docs.stripe.com\`，它会被存储在 \`shelldocs-{canonical\_id}\` 下并对所有人可用。整个系统从设计上就是未经过身份验证的。这些是公开文档。

3\. Shell

Shell 本身在客户端运行。没有容器，没有沙箱，没有虚拟机。我们使用

[just-bash](https://github.com/nicolo-ribaudo/just-bash)，一个用 TypeScript 重新实现的 bash，支持 grep、cat、ls、find、cd、tree、管道和别名。整个文件系统是一个内存中的 JavaScript 对象。

```typescript
const bash = new Bash({
  files: initialFiles,    // { "/stripe.com/docs/api/charges.md": "..." }
  cwd: `/${domain}/docs`,
  env: buildCommonEnv(domain),
  executionLimits: EXECUTION_LIMITS,
});
```

所有文件都预先加载并挂载到虚拟文件系统中。命令在进程内执行。在超过 500 个文档页面中执行 \`grep -r "webhook" .\` 命令在毫秒级内完成，因为这只是在内存中进行字符串匹配。对于大型站点（1000+页面），我们预先加载文件树，并在执行 \`cat\` 命令时按需延迟获取内容，且内容会为会话缓存。

为什么不做一个真正的沙箱？

- 启动时间：约100毫秒（已缓存），约2秒（已建立索引），约30-120秒（新站点的冷启动索引）
- 每会话计算：服务器端计算为零。文件来自 Postgres，命令在客户端运行
- 无编排或暖池

最明显的替代方案是给代理一个实际的文件系统。启动一个容器，将文档克隆到其中，然后让代理开始工作。有些团队会这样做。这是正确的做法，而且有效。但对于本质上是针对静态文本的只读工作负载而言，这种方法速度慢且成本高。

文档 shell 不需要进程隔离、可写存储或内核。它需要在已知的一组文件上进行字符串匹配。在微型虚拟机中运行这个就好比租一个仓库来存放一个书架。

我们采取了另一种方式：shell 完全在客户端作为一个进程内的 TypeScript bash 解释器运行。后端是一个简单的文件服务器。无需启动容器，也无需管理会话。

代理已经知道这个

代理的设置只需一行：

```bash
npx nia-docs setup https://docs.example.com | claude

codex "$(npx nia-docs setup https://docs.example.com)"

npx nia-docs agents https://docs.example.com >> AGENTS.md

opencode --prompt "$(npx nia-docs setup https://docs.example.com)"

gemini "$(npx nia-docs setup https://docs.example.com)"

copilot -i "$(npx nia-docs setup https://docs.example.com)"
```

这会向代理的指令文件追加几行：

```markdown
## Stripe Docs

Before working on a Stripe feature, check the docs via `npx nia-docs https://docs.stripe.com`.

    # Search for a topic
    npx nia-docs https://docs.stripe.com -c "grep -rl 'webhook' ."

    # Read a specific page
    npx nia-docs https://docs.stripe.com -c "cat getting-started.md"
```

代理获取了它。当需要检查某物如何工作时，它执行命令，获取实际的当前文档，并根据该文档编写代码，而非依据训练数据中的内容。

\-c 标志执行单个命令并退出。代理永远不会进入交互式会话。它运行 grep，获取结果，读取相关文件，继续执行。标准的工具使用循环。文件系统只是一个接口。

从 docs 开始

我们从文档入手，因为在这里幻觉造成的伤害最大，而且数据问题也最容易解决。文档网站是公开的、结构化的，而且相对较小（大多数都不到 1000 页）。它们更新得足够频繁，以至于训练数据总是过时的；但更新速度又足够慢，使得 5 天的缓存 TTL 能够保持内容的时效性。

但这个想法不止于文档。API 参考是一个目录。变更日志是一个文件。OpenAPI 规范本身就是你可以用 cat 命令查看的 JSON。我们会自动检测并索引 OpenAPI 规范，与文档一同进行索引。它们会出现在文件系统的 /api-spec/ 路径下。

整个网络应该能以代码库相同的方式进行导航。我们正在构建基础设施以实现这一点，目前从对智能体最重要的部分开始。

我们正在测量的

代理在 shell 会话中执行的每一条命令都会被记录（可通过设置 NIA\_DOCS\_TELEMETRY=off 选择退出）：命令名称、是否成功、执行时长、哪些文件匹配了 grep。记录的不是内容，仅记录模式。我们希望了解代理实际如何浏览文档，以便改进文件系统。

早期数据显示，代理趋向于采用一致的工作流程：使用 tree 进行定位，使用 grep -rl 查找相关文件，使用 cat 读取文件。这与人类开发者的操作完全一致。文件系统抽象并非代理需要学习的内容，而是在有选择时他们默认采用的方式。

网络很大。但每一个文档站点、每一个 API 参考、每一个更新日志，都变成了你可以 cd 进入的目录。

## 通俗精炼（1）

### 2026-04-07 06:38:40

#### 将网络文档变成 “可浏览的文件系统”

##### 核心观点

这篇文章的核心在于：**AI 代码幻觉的根源，很多时候不是模型不够聪明，而是它拿到的资料过时了。**  
文档、API、参数经常变化，模型按旧知识写出的代码看起来没问题，但一运行就报错。

##### 传统方案的问题

常见做法是用 RAG，从文档里切片检索相关内容。  
它能解决一部分问题，但也有明显短板：

- 只能拿到 “片段”，拿不到完整上下文
- 关键信息可能被切碎，比如函数签名、参数结构
- 当答案分散在多个页面时，效果会明显下降

**一句话：代理真正需要的不是零散摘录，而是像人一样直接翻文档。**

##### 作者提出的新思路

作者的方案很直接：**不要把文档当检索库，而要把它变成文件系统。**  
也就是说，让代理像在本地代码仓库里一样使用：

- `cd`进入文档目录
- `tree`看结构
- `grep`搜关键词
- `cat`读页面

这样，代理不需要学习一堆复杂工具接口，而是直接用它最熟悉的 “文件操作方式” 查资料。

##### 为什么这个思路成立

文章认为，这种方式强在两个地方：

###### 1. 文件系统是统一接口

Unix 的经典思想就是 “一切皆文件”。  
如果文档网站也能变成目录和文件，代理就能用统一方式访问各种信息，而不必为每个网站、每类工具重新适配。

###### 2. 代理天然会用这套方法

模型在训练中见过大量`grep`、`find`、`cat README.md`这样的操作。  
所以相比 MCP 这类需要定义 JSON 模式、参数说明的工具，**文件系统接口更符合模型已有能力，也更省上下文。**

##### 它是怎么实现的

作者做了一个工具`nia-docs`，输入一个文档网址，就能把整个文档站挂载成 “可浏览文件系统”。

整体分三步：

###### 1. 文档抓取与目录化

系统先抓取网站内容，把每个页面转成一个文件，并自动整理路径结构。  
比如复杂的网址会被简化成更符合人类理解的目录形式。

###### 2. 后端提供文件接口

后端把这些文档暴露成一组类似文件系统的能力，例如：

- 读取文件
- 查看目录
- 搜索关键词
- 查找文件树

并且做了缓存和共享索引，提升速度。

###### 3. 客户端用 “轻量 Shell” 运行

真正的 shell 运行在客户端，不开容器、不启沙箱。  
本质上是一个内存里的虚拟文件系统，速度快、成本低，非常适合 “只读查文档” 这种场景。

##### 这解决了什么问题

它解决的不是 “让 AI 更聪明”，而是：**让 AI 在写代码前，先看到最新、完整、可导航的文档。**  

这样代理可以先搜索文档、再读取具体页面、最后生成代码，减少因为知识过时导致的错误。

##### 文章的边界与价值

作者也承认，这个方案首先适合的是**公开、结构化、更新频繁但规模适中的文档网站**。  
比如：

- 产品文档
- API Reference
- Changelog
- OpenAPI 规范

它暂时解决的是 “公开技术资料实时获取” 问题，**并不等于解决了所有知识接入问题**，比如个人文档、企业私有知识等场景仍然更复杂。

##### 一句话总结

**这篇文章的本质，是把 “AI 查文档” 从检索问题，改写成文件系统问题。**  
相比让代理调用一堆复杂工具，不如把整个文档网站变成它熟悉的目录和文件，让它像工程师一样自己去找、去读、去理解。

## 结构化（1）

### 2026-04-07 11:03:58

#### 主旨概括

这篇文章的核心观点是：**AI 代码幻觉的根源，很多时候不是模型能力不足，而是文档数据过时**。作者提出一种比传统 RAG 更直接的方案：**把在线文档站点“挂载”为可浏览的文件系统**，让代理像查本地代码库一样，用 `tree`、`grep`、`cat` 去读最新文档。

#### 1. 问题背景：代码幻觉本质上是“数据滞后”

- API、SDK 和文档每天都可能发生变化，比如**破坏性更新、接口弃用、参数重命名**。
- 但模型训练数据通常会**滞后数月甚至数年**，导致代理写出的代码“看起来正确、能编译”，却在运行时失败。
- 典型场景是：**某个库 6 个月前已经更新，但模型仍按旧版本写代码**。

**关键结论：**
- 许多“代码幻觉”并不是模型不会写代码，而是**模型拿到的是过期知识**。

#### 2. 为什么传统 RAG 不够用

- 标准做法是 RAG：把文档切块、做嵌入、检索 Top-K 片段。
- 这种方式能解决**约 80% 的问题**，但在以下场景容易失效：
  - 答案分散在**多页文档**中；
  - 代理需要**精确函数签名**；
  - 文档切块后，**上下文结构和完整性被破坏**。
- 作者认为：**检索拿到的是碎片，但代理真正需要的是完整文档结构和原始内容**。

**一个直观例子：**
- 如果你要确认某个 API 的参数签名，仅靠一个片段可能不够，因为参数说明、示例、错误码可能分散在几页里。

#### 3. 核心思路：把文档网站变成“文件系统”

- 作者借用了 Unix 的经典思想：**“一切皆文件”**。
- 设备、进程、套接字都可以统一用 `open`、`read`、`write`、`close` 访问。
- 同样地，作者希望让代理面对文档时，不是调用各种专门工具，而是像操作文件一样去浏览。

**为什么这个思路适合代理：**
- 代理在训练中已经见过大量文件系统操作：
  - `cat README.md`
  - `grep -r "auth" .`
  - `find . -name "*.md"`
- 也就是说，`tree`、`grep`、`find` 不是代理新学的工具，而是**它本来就熟悉的工作方式**。

**作者的判断：**
- 相比 MCP 那种每个工具都要定义 JSON 模式、自然语言说明和参数结构的方式，**文件系统接口更统一、更轻量，也更不容易被误用**。
- 文中引用 Jerry Liu 的观点：**一个有文件系统工具和代码解释器的代理，可能和有 100+ 个 MCP 工具的代理一样通用，甚至更通用。**

#### 4. 产品形态：让任何文档站都能 `cd` 进去

作者给出的产品是 `nia-docs`，用法非常简单：

```bash
npx nia-docs https://docs.trynia.ai
```

或者给代理配置：

```bash
npx nia-docs setup https://docs.trynia.ai | claude
```

**特点：**
- **无 API Key**
- **无需安装**
- **无需额外配置**
- 一条命令就能打开一个 bash shell，把文档网站挂载成文件系统

在这个环境里，代理或开发者可以：
- 用 `tree` 浏览目录结构
- 用 `grep` 搜索主题
- 用 `cat` 查看具体页面
- 再把结果通过管道交给 Claude、Cursor、Copilot、Codex、Gemini CLI、OpenCode 等工具

#### 5. 它是如何工作的：三层结构

##### 5.1 目录层：把网页转成文件

- 后端首次访问某个 URL 时，会抓取整个文档站点。
- 系统会自动处理：
  - `llms.txt`
  - OpenAPI 规范
  - 重定向
- 每个网页会转换成一个文件，例如：
  - `https://docs.stripe.com/api/charges/create`
  - 变成 `/api/charges/create.md`

**关键优化：路径规范化**
- 不同文档站 URL 结构非常不统一：
  - 有些内容都在 `/docs/`
  - 有些在 `/api/reference/`
  - 有些直接挂在根目录
- 系统会自动检测公共路径前缀并剥离，让文件结构更符合人的认知。

**例子：**
- `https://better-auth.com/docs/installation`
- 会变成 `/installation.md`
- 而不是 `/docs/installation.md`

**意义：**
- 文件系统反映的是**用户理解文档的方式**，而不是网站原始 URL 的历史包袱。

##### 5.2 服务层：把文件系统操作暴露成 API

后端提供了一组文件系统风格的接口：

- `load`：加载状态和完整文档
- `read`：读取单个文件
- `grep`：正则搜索
- `ls`：列目录
- `tree`：输出完整树
- `find`：按 glob 查找

**性能设计：**
- 所有内容都用 **gzip 压缩**
- `/load` 可在**一次请求**中返回状态和全部文件
- 响应缓存为 `Cache-Control: public, max-age=300`
- CLI 还会在 `~/.cache/nia-docs/` 做磁盘缓存
- 如果文档已经被索引过，再访问时通常是**瞬时完成**

**共享命名空间：**
- 比如有人已经索引过 `docs.stripe.com`，别人也可直接复用
- 系统从设计上就是**匿名共享**，因为目标对象本来就是公开文档

##### 5.3 Shell 层：命令在客户端内存里执行

- Shell 本身运行在客户端，不用容器、沙箱或虚拟机。
- 作者使用的是 `just-bash`：一个用 TypeScript 实现的 bash。
- 支持的命令包括：
  - `grep`
  - `cat`
  - `ls`
  - `find`
  - `cd`
  - `tree`
  - 管道、别名等

**关键实现：**
- 整个文件系统本质上是一个**内存中的 JavaScript 对象**
- 文件预加载后挂载到虚拟文件系统
- 命令在当前进程内执行，所以速度很快

**性能数据：**
- 在 **500+ 页面**的文档站中执行 `grep -r "webhook" .`，可在**毫秒级**完成
- 对于 **1000+ 页面**的大站点：
  - 先预加载文件树
  - `cat` 时再按需拉取内容
  - 会话内继续缓存

#### 6. 为什么不用“真正的沙箱或容器”

作者认为，对文档这种**只读、静态文本**场景来说，容器太重了。

**给出的理由：**
- 启动速度：
  - **已缓存**约 `100ms`
  - **已建立索引**约 `2 秒`
  - **新站点冷启动索引**约 `30-120 秒`
- 每个会话的服务器端计算几乎为 **0**
- 后端只是文件服务器，不需要容器调度、暖池或会话管理

**作者的比喻：**
- 对于文档检索这种工作负载，用微型虚拟机就像**“租一个仓库来放一个书架”**——明显过度设计。

#### 7. 为什么代理容易接受这种方式

- 给代理的接入方式非常轻，只需要一行 setup 命令。
- 代理拿到的指令非常直白，例如：
  - 先用 `grep -rl 'webhook' .` 找相关文件
  - 再用 `cat getting-started.md` 查看具体页面
- 代理不会一直停留在交互式 shell 中，而是用 `-c` 参数执行单个命令、读取结果、继续推理。

**关键点：**
- 这不是在教代理一个全新工具体系；
- 而是在利用代理原本就熟悉的**“文件系统式工作流”**。

#### 8. 为什么从文档开始，以及下一步能扩展到什么

作者选择先从文档入手，原因是：

- 文档是**公开的**
- 文档结构相对**规整**
- 规模通常不大，**大多数不到 1000 页**
- 更新频率高，训练数据很容易过时
- 但又没有高到必须秒级同步，因此**5 天缓存 TTL**通常足够保持时效性

**作者认为这套思路不止适用于文档：**
- API Reference 可以是一个目录
- Changelog 可以是一个文件
- OpenAPI 规范本身可以是一个可 `cat` 的 JSON 文件

**当前已支持：**
- 自动检测并索引 OpenAPI 规范
- 并把它们放到 `/api-spec/` 路径下

#### 9. 他们正在观察什么：代理真实的浏览行为

- 系统会记录代理在 shell 中执行的命令行为（可通过 `NIA_DOCS_TELEMETRY=off` 关闭）。
- 记录内容包括：
  - 命令名称
  - 是否成功
  - 执行耗时
  - 哪些文件匹配了 `grep`
- **不会记录文档内容本身**，只记录行为模式。

**早期发现：**
- 代理往往会采用一种很稳定的流程：
  1. `tree` 先定位结构
  2. `grep -rl` 找相关文件
  3. `cat` 读取目标内容

**作者的结论：**
- 这与人类开发者查文档的方式几乎一样
- 说明“文件系统抽象”不是代理勉强适应的形式，而是**它们天然偏好的交互方式**

#### 10. 文章结论

- 作者主张：**整个网络，至少是文档、API 参考、更新日志这些结构化内容，应该像代码库一样可导航。**
- 这样做的价值不只是“更方便”，更重要的是：
  - 让代理拿到**最新信息**
  - 减少因训练数据过时造成的**运行时错误**
  - 用代理本来就会的方式，提高工具使用效率

#### 11. 文中保留的重要案例与数据

- RAG 可解决**约 80%** 的问题，但在跨页信息、精确签名等场景仍不足。

  - HTTP 缓存 `max-age=300`
