#### 主旨概括

这篇内容主要介绍了 Frad 在 Claude Code 中实践很久的一套工作流插件 `meeseeks-vetted`，核心目标是：**强制 AI 在任务完成前做好验证，避免“看起来做完了，其实没完全确认”的情况**。  
作者认为，如果把 Claude Code 看作一个“操作系统”，那么 Hook/插件机制就是编排这个系统行为的关键工具，而这个插件正是把这种思路落地的一种方式。

##### 1. 插件是什么，以及怎么安装

作者正式介绍了一个名为 `meeseeks-vetted` 的插件，并给出了安装方式：

```bash
claude plugin marketplace add FradSer/dotclaude
claude plugin install meeseeks-vetted@frad-dotclaude
```

关键点：
- 插件来自 `FradSer/dotclaude`
- 名称是 `meeseeks-vetted`
- 作者说明，这套方法是自己在 Claude Code 里实验了很久后，参考相关提示词进一步修改出来的

通俗理解：
- 它不是单纯“优化提示词”，而是把“任务必须验证完成”这件事，做成了一个可执行的流程规则
- 这样 AI 不只是“回答你”，而是要按预设标准完成并自检

##### 2. 这个插件的核心工作原理

作者把插件逻辑拆成了 3 个步骤。

###### 2.1 在任务开始时，先注入约束

当用户输入 prompt 时，系统会自动注入一段提示词，用来约束：
- 如何判断任务是否完成
- 什么样的结果才算达标

并且要求：
- 任务完成后，回复必须以 `Fully Vetted.` 结尾

这里作者提到，这种做法类似 `ralph-loop`。

通俗理解：
- 相当于一开始就告诉 AI：“不是做一点就算完，必须满足明确标准，而且要打上完成标记。”
- `Fully Vetted.` 就像一个“验收章”

###### 2.2 每轮结束时，检查有没有完成标记

每一轮执行结束后，系统会检查输出里是否包含：

```text
Fully Vetted.
```

如果没有：
- 系统就会报错
- 并把原始 prompt 和已修改的文件返回
- 要求 AI 补充验证后再重试

关键点：
- 这里不是“没写标记就算了”，而是直接拦截
- 还会保留上下文信息，方便下一轮继续完善

通俗例子：
- 比如你让 AI 修改一段代码，它改完了但没有确认测试、校验或检查结果
- 这时插件不会放过，而是要求它继续验证，直到真正符合“完成标准”

###### 2.3 如果任务没完成，新 prompt 会自动合并上下文

作者还提到一个很重要的机制：

如果旧任务还没完成，但用户又输入了新的 prompt，系统不会简单地“开启新话题”，而是会合并：
- 旧 prompt
- AI 已有输出
- 用户新 prompt

然后把合并后的内容，作为统一上下文进入下一轮执行。

关键点：
- 防止任务中途断裂
- 避免 AI 忘掉之前做了什么、还差什么
- 让多轮协作更连贯

通俗理解：
- 就像一个持续推进的工单系统，而不是每次对话都重新开一个窗口

##### 3. 作者对 Claude Code 工作方式的理解

简化来说：
- 提示词决定 AI “怎么想”
- Hook/插件决定 AI “必须怎么做”

## 解读（1）

#### 内容总结

这条内容主要是在介绍一个给 Claude Code 用的插件：`meeseeks-vetted`。  
作者 Frad 表示，自己参考并改造了一套提示词和 Hook 机制，做成了一个可复用的方案，让 AI 在执行任务时更“自觉”地检查是否真的完成。

它的核心机制有 3 点：

1. **任务开始前注入约束**
   - 用户一输入 prompt，系统就自动加上一层提示词。
   - 这层提示词会规定：如何判断任务完成、完成标准是什么。
   - 任务真正完成后，回复必须以 `Fully Vetted.` 结尾。

2. **每轮结束自动验收**
   - 每一轮结束时，系统检查输出里有没有 `Fully Vetted.`。
   - 如果没有，就认为任务没验收通过，会报错，并把原始 prompt 和改动文件带回去，要求 AI 补充验证后重试。

3. **未完成任务可自动续接**
   - 如果任务还没完成，用户又输入了新 prompt，
   - 系统会把旧 prompt、AI 上一轮输出、新 prompt 合并成统一上下文，
   - 然后再进入下一轮执行，避免上下文断裂。

作者的观点是：  
如果把 Claude Code 看成一个“操作系统”，那么 **Hook 就像这个系统最关键的编排工具**。这和 `ralph-loop` 的思路很接近。

#### 深入解读

##### 这套方法到底解决了什么问题？

它主要解决的是：**AI 很容易“看起来做完了”，但其实没完全做完。**

比如常见情况有：

- 代码改了，但没验证能不能跑
- 只回答了思路，没有真正执行完
- 改了一半，用户又补充要求，导致上下文混乱
- 模型为了尽快结束，倾向于“宣布完成”

这个插件本质上是在做一件事：

> 给 AI 增加一道“交作业门槛”。

只有当它满足预设标准，并明确输出 `Fully Vetted.`，这一轮才算真正结束。  
否则，就继续补验证、补检查、补执行。

---

##### 为什么 `Fully Vetted.` 这个标记很关键？

因为它相当于一个**机器可识别的完成信号**。

平时 AI 会说：

- “应该可以了”
- “理论上没问题”
- “已经完成修改”

这些话对人来说像完成了，但对系统来说很模糊。  
而 `Fully Vetted.` 这种固定标记，方便 Hook 去判断：

- 有没有完成
- 要不要拦截
- 要不要强制重试

所以这不是一句普通结束语，而是一个 **验收协议**。

---

##### Hook 在这里为什么重要？

Hook 可以理解成：  
**在 AI 工作流程里的关键节点，自动插入规则和动作。**

比如：

- 用户刚发任务时，先注入约束
- AI 回答结束时，自动检查结果
- 没通过时，自动回退并重试
- 用户追加需求时，自动拼接上下文

这意味着你不只是“写了一个好 prompt”，而是在 **搭一个可重复执行的流程**。  
这比单纯靠提示词更稳定，因为提示词只是在“劝模型”，而 Hook 是在“管流程”。

---

##### 它为什么像 `ralph-loop`？

因为两者思路都很像：

- 不轻易接受“表面完成”
- 用明确规则判断是否结束
- 不通过就继续循环
- 把“验证”变成流程的一部分，而不是可选项

简单说，都是在把 AI 从“回答机器”，往“任务执行器”方向推。

---

##### 这套方案的价值在哪里？

它的价值不在于“更聪明”，而在于“更稳”。

适合的场景包括：

- 写代码
- 改文件
- 多轮迭代任务
- 需要明确完成标准的工作流

它特别适合那些对结果质量要求较高、不想反复人工盯验收的人。

---

#### 我的意见

我认为这个思路是**很实用的，而且比单纯优化 prompt 更进一步**。

优点很明显：

- **降低假完成**：减少 AI 只做表面工作的情况
- **强化验收意识**：让“验证”变成必须步骤
- **适合工程化复用**：不是一次性技巧，而是可长期使用的流程设计
- **多轮任务更稳**：上下文合并机制能减少任务跑偏

但也有几点要注意：

1. **别把标记当成真实质量**
   - AI 写了 `Fully Vetted.`，不等于真的完全验证过。
   - 关键还是看 Hook 背后有没有绑定实际检查动作。

2. **规则过严可能增加成本**
   - 如果每轮都强制很重的验证，可能会拖慢速度，增加 token 和执行时间。

3. **上下文自动合并要防止污染**
   - 旧 prompt、旧输出、新需求全拼起来，虽然连续性更好，
   - 但也可能把错误信息一起带进去，导致越滚越复杂。

我的整体判断是：

> 这不是“神奇提示词”，而是一种更像工程系统的 AI 工作流设计。

如果你经常用 Claude Code、Codex、Cursor 这类工具做持续性任务，这种机制非常值得借鉴。  
真正有价值的地方，不是那句 `Fully Vetted.`，而是它背后的理念：

**不要只要求 AI“回答”，而要设计它“交付并验收”。**
