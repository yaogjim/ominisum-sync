#### Cloudflare Computer

Cloudflare Computer is a virtual filesystem that lives inside a Durable Object. The Durable Object holds the authoritative state in SQLite and exposes one pluggable execution surface through `workspace.runtime`. Three backends ship today:

- **Container** projects the SQLite state into a sandbox container as a real FUSE mount. A sandbox-side daemon (`computerd`) mounts the state as a filesystem and syncs changes back over a capnweb RPC channel. Full Linux userland, real binaries, real network.
- **Isolate shell** runs [just-bash](https://github.com/vercel-labs/just-bash) in a Dynamic Worker. It reaches the authoritative Workspace over Workers RPC, so there is no second store or sync round trip.
- **Isolate JavaScript** runs an ECMAScript module in a fresh Dynamic Worker with structured input/results, durable relative imports, configured libraries, Workspace-backed `node:fs/promises`, and trusted `ws:git` and `ws:artifacts` modules.

A Workspace may register multiple backends under stable IDs.`workspace.runtime.exec(source, { backend })` is the single execution entry point; the selected backend defines whether `source` is a shell command or an ECMAScript module. Backends connect lazily on first use.

Workspace can also be constructed without a backend at all, giving callers the filesystem on its own.

#### Using it

If you want to build on Cloudflare Computer, install `@cloudflare/computer` and follow that package's README — it has the installation steps, the entrypoint map, and worked examples of the `fs` and `runtime` surfaces.

To work on this repository itself, see `CONTRIBUTING.md` for setup, build, and test instructions.

#### Examples

The `examples/` directory holds runnable consumers of the public surface. Each is a Worker workspace with its own README.

- `examples/container` — runs `computerd` inside a container, mounts a workspace, and talks to a Durable Object over capnweb. A `write` / `read` / `exec` HTTP surface.
- `examples/worker-shell` — same HTTP surface as the container example, but the shell runs [just-bash](https://github.com/vercel-labs/just-bash) in a Dynamic Worker loaded through `env.LOADER`. No container.
- `examples/worker-javascript` — mirrors `worker-shell`, but `exec` evaluates an ECMAScript module in a Dynamic Worker instead of running a shell command.
- `examples/think` — a [`@cloudflare/think`](https://www.npmjs.com/package/@cloudflare/think) chat agent that uses the workspace as its working directory, reachable from a terminal.
- `examples/think-compare-runtimes` — a web UI that runs the same agent task against the container and worker runtimes side by side.
- `examples/tutorial` — a step-by-step build: one endpoint, one agent that writes a markdown recipe card on the host and runs `pandoc` on it in the container to produce a PDF.
- `examples/artifacts` — generates a Worker project in a workspace and publishes it to Cloudflare Artifacts as a clone-ready repo.
- `examples/assets` — turns a prompt into an image with Workers AI, writes it to the workspace, and returns a shareable link through `@cloudflare/computer/assets`.

#### Repository layout

The repo is a small monorepo. Each package has its own README with package-specific status and usage notes.

- `packages/dofs` (`@cloudflare/dofs`) — Durable Object SQLite-backed virtual filesystem, sync protocol building blocks, and a `@platformatic/vfs` provider for Node.
- `packages/rpc` (`@cloudflare/computer-rpc`) — capnweb wire types and server/client helpers shared between the Durable Object and `computerd`.
- `packages/computerd` (`@cloudflare/computerd`) — the `computerd` daemon: a FUSE mount plus HTTP/WebSocket RPC server that runs inside the sandbox container.
- `packages/computer` (`@cloudflare/computer`) — the top-level Computer package consumed by Durable Objects. Work in progress.
- `packages/computer-computerd-linux-x64` (`@cloudflare/computer-computerd-linux-x64`) — the prebuilt `computerd` binary for linux-x64, distributed for use in container images.

#### Performance

computerd's FUSE mount beats real disk on metadata-heavy work and trails it on large sequential I/O. See `docs/19_performance.md` for the full `fs-bench` numbers, a `cloudflare/sandbox-sdk` `npm install` comparison, and how to reproduce them.

#### Documentation

- `docs/` — design specification. Forward-looking; treat as intent.
- `docs/19_performance.md` — filesystem benchmarks.

#### Contributing

See `CONTRIBUTING.md` for setup, formatting, testing, commit message, and pull request conventions.

If you're working in this repo as an agent, start with `AGENTS.md` and the skills under`.agents/skills/`.

#### Cloudflare Computer：给 AI Agent 一台 “云端电脑”

##### 一句话总结

Cloudflare Computer 为 AI Agent 提供一个**可持久化的虚拟文件系统与可插拔执行环境**，让 Agent 能像使用真实电脑一样读写文件、运行 Shell 或 JavaScript，并在不同运行时之间切换。

##### 核心架构

系统以**Durable Object**作为 Workspace：

- 文件状态持久化在 Durable Object 的**SQLite**中，作为唯一权威数据源。
- 通过统一接口`workspace.runtime.exec (source, { backend })`执行任务。
- 执行后端按需连接，可为同一 Workspace 注册多个后端。
- 也可以不配置执行后端，只把它当作独立的持久化文件系统使用。

##### 三种执行后端

| 后端 | 执行方式 | 主要特点 |
|---|---|---|
| **Container** | 在容器内执行 Shell 和原生程序 | 通过 FUSE 挂载文件系统，具备完整 Linux 环境、真实二进制与网络能力 |
| **Isolate Shell** | 在 Dynamic Worker 中运行`just-bash` | 无需容器，直接通过 Workers RPC 访问 Workspace，没有额外数据副本 |
| **Isolate JavaScript** | 在全新 Dynamic Worker 中执行 ES Module | 支持结构化输入输出、持久化相对导入、`node:fs/promises`、Git 与 Artifacts 模块 |

三者共享同一套 Workspace 数据，但在**能力、启动成本和隔离方式**上有所不同。

##### 典型应用场景

项目已提供多个可运行示例：

- AI Agent 将 Workspace 作为长期工作目录。
- 对比同一 Agent 任务在容器与 Worker 运行时中的效果。
- Agent 生成 Markdown，再调用`pandoc`转换为 PDF。
- 自动生成 Worker 项目并发布为可克隆仓库。
- 调用 Workers AI 生成图片、写入 Workspace 并返回分享链接。
- 通过 HTTP 提供文件读写与代码执行能力。

##### 技术与产品价值

Cloudflare Computer 的关键价值，是把 Agent 所需的两类能力统一起来：

1. **持久化状态**：任务文件不会随着单次执行结束而消失。
2. **可切换执行环境**：轻量任务用 Worker，依赖完整 Linux 的任务用容器。
3. **统一开发接口**：上层 Agent 无需直接适配不同运行时。
4. **边缘平台集成**：可直接结合 Workers AI、Artifacts、Durable Objects 等 Cloudflare 服务。

它本质上是一层面向 Agent 的 “**云端电脑抽象**”，而不仅是一个代码沙箱。

##### 性能与成熟度

- FUSE 文件系统在**元数据密集型操作**中可能快于真实磁盘。
- 在**大文件顺序读写**中则落后于真实磁盘。
- 顶层`@cloudflare/computer`包仍标记为**Work in Progress**。
- `docs/`中部分内容属于前瞻性设计，应视为目标而非全部已稳定实现。

##### 项目定位

该项目适合构建需要长期文件状态、工具调用和代码执行能力的 Agent，例如编程助手、研究代理、内容生产流水线和自动化开发平台。当前更像是 Cloudflare 面向 Agent 基础设施的一套早期能力框架，而非完全成熟的通用桌面环境。

### 2026-08-07 08:45:50

#### Cloudflare Computer：给智能体一台可编程的“电脑”

Cloudflare Computer 是一套面向智能体和 Cloudflare Workers 的虚拟计算环境。它把持久化文件系统和多种执行后端统一起来，让智能体既能长期保存文件，也能运行 Linux 命令、Shell 脚本或 JavaScript 模块。

听完这份介绍，你可以了解它的核心架构、三种运行后端、典型使用场景，以及项目目前的性能特点和开发状态。

##### 首先，理解它的核心：一个持久化的虚拟工作区

Cloudflare Computer 的基础，是一个位于 Durable Object，也就是“持久化对象”内部的虚拟文件系统。

Durable Object 是 Cloudflare 提供的一种有状态计算单元。简单来说，普通云函数执行结束后，内存状态通常会消失；而 Durable Object 可以长期保存状态。Cloudflare Computer 就利用这一能力，为智能体提供一个不会随着单次任务结束而丢失的工作区。

工作区的权威数据保存在 SQLite 中。SQLite 是一种轻量级数据库，这里承担的是文件系统底层存储的角色。所谓“权威数据”，意思是它是文件状态的最终来源。无论外部使用哪种运行环境，最终都以这里保存的内容为准。

在此基础上，Cloudflare Computer 通过统一的运行接口，把文件系统和不同执行环境连接起来。这样，调用者面对的是同一个 Workspace，也就是工作区，而不用分别管理多套文件数据。

##### 接下来，是三种可以替换的执行后端

Cloudflare Computer 目前提供三种后端。它们共享同一个持久化工作区，但执行任务的方式不同。

第一种是容器后端。

它会把 SQLite 中保存的状态映射到沙箱容器里，看起来就像一个真实的文件系统。这里使用了 FUSE。FUSE 可以理解为一种让用户态程序实现文件系统的机制。

容器里会运行一个名为 computerd 的后台程序。它负责挂载文件系统，并通过 capnweb RPC 通道把文件变更同步回 Durable Object。RPC，也就是远程过程调用，可以理解为两个独立程序之间互相调用功能和传递数据的方式。

这种后端提供完整的 Linux 用户环境，可以运行真实的二进制程序，也可以访问真实网络。适合需要系统工具、复杂依赖，或者必须执行原生程序的任务。

第二种是隔离式 Shell 后端。

它不启动容器，而是在 Dynamic Worker，也就是按需创建的动态 Worker 中运行 just-bash。just-bash 是一个可执行 Bash 风格命令的环境。

这个后端会通过 Workers RPC 直接访问权威工作区。因此，它不需要维护第二份文件存储，也不需要先把文件同步到另一套系统再执行。它更轻量，适合主要使用 Shell 命令、但不需要完整 Linux 容器的任务。

第三种是隔离式 JavaScript 后端。

它会在一个全新的 Dynamic Worker 中运行 ECMAScript 模块，也就是现代 JavaScript 模块。任务可以接收结构化输入，并返回结构化结果。

这个环境支持持久化的相对路径导入、预先配置的程序库，以及由 Workspace 支持的文件系统接口。它还提供受信任的 Git 和制品模块，用于处理代码仓库与构建产物。

换句话说，如果任务本身适合用 JavaScript 完成，就可以直接在轻量的 Worker 环境中执行，不必启动 Shell 或完整容器。

##### 更重要的是，三种后端使用同一个执行入口

一个 Workspace 可以注册多个后端，并为它们分配稳定的标识。执行任务时，统一调用 `workspace.runtime.exec`，再指定要使用哪个后端。

被选中的后端会决定传入内容的含义。选择容器或 Shell 后端时，内容通常是一条 Shell 命令；选择 JavaScript 后端时，内容则是一个 ECMAScript 模块。

这些后端采用延迟连接方式，也就是第一次真正使用时才建立连接。这样可以避免提前启动暂时用不到的运行环境。

此外，Workspace 也可以完全不配置执行后端。此时，调用者仍然能够把它当作一个独立的持久化虚拟文件系统使用。

##### 如何使用这套系统

如果要在自己的项目中使用 Cloudflare Computer，可以安装顶层软件包 `@cloudflare/computer`。它提供安装说明、入口映射，以及文件系统和运行接口的完整示例。

如果要参与这个代码仓库本身的开发，则需要按照项目的贡献文档完成环境设置、构建和测试。

这个项目目前是一个小型 monorepo。monorepo 指的是把多个相关软件包放在同一个代码仓库中统一维护。每个软件包都有自己的说明文档，用来介绍具体状态和使用方式。

##### 典型案例展示了哪些能力

项目提供了多组可以直接运行的示例，每一组都是一个独立的 Worker 工作区。

首先是容器示例。它在容器中运行 computerd，挂载 Workspace，并通过 capnweb 与 Durable Object 通信。示例提供写文件、读文件和执行命令等 HTTP 接口。

接下来是 Worker Shell 示例。它提供与容器示例相同的 HTTP 功能，但 Shell 运行在 Dynamic Worker 中，不需要容器。这能直观展示两种后端虽然底层不同，却可以暴露相似的使用方式。

JavaScript 示例则进一步把执行环境换成 ECMAScript 模块。它不运行 Shell 命令，而是在 Dynamic Worker 中直接计算 JavaScript 代码。

项目还提供了智能体案例。一个名为 think 的聊天智能体，会把 Workspace 当作自己的工作目录，并且可以从终端访问。另一个对比案例，会让同一个智能体任务分别在容器和 Worker 环境中运行，方便并排观察两种运行方式的差异。

教程案例展示了一条更完整的工作流：智能体先在宿主工作区中生成一份 Markdown 格式的食谱卡片，再进入容器运行 Pandoc，把它转换成 PDF。这个案例说明，持久化文件系统和真实命令行工具可以组合成连续任务。

另外还有两个生成类案例。一个会在工作区中生成 Worker 项目，并发布到 Cloudflare Artifacts，形成可以克隆的代码仓库。另一个会根据提示词调用 Workers AI 生成图片，把图片写入工作区，再返回一个可以分享的链接。

##### 仓库中的主要组成部分

这个仓库由几个职责不同的软件包构成。

`@cloudflare/dofs` 提供由 Durable Object 和 SQLite 支持的虚拟文件系统，同时包含同步协议的基础组件，以及面向 Node.js 的虚拟文件系统适配器。

`@cloudflare/computer-rpc` 定义 Durable Object 与 computerd 之间共享的通信类型，并提供服务器端和客户端工具。

`@cloudflare/computerd` 是运行在沙箱容器中的后台程序。它同时负责 FUSE 文件系统挂载，以及 HTTP 和 WebSocket 形式的 RPC 服务。

顶层的 `@cloudflare/computer` 是 Durable Object 使用的主要软件包，也是外部项目最直接接触的入口。不过原文明确说明，这一部分仍在开发中。

此外，项目还提供预编译的 Linux x64 版本 computerd，方便在容器镜像中直接使用。

##### 性能表现并不是简单地快或慢

在文件系统性能方面，computerd 的 FUSE 挂载有一个比较鲜明的特点：面对大量文件元数据操作时，它的表现可以超过真实磁盘；但在大文件连续读写，也就是顺序输入输出方面，它会落后于真实磁盘。

元数据操作主要包括查询文件是否存在、读取目录、查看文件属性等。这类操作频繁的开发任务，可能更能发挥它的优势。相反，如果任务需要持续传输大块文件，真实磁盘仍然更有优势。

项目文档提供了完整的文件系统基准测试、与 Cloudflare Sandbox SDK 安装 npm 软件包的对比，以及复现实验的方法。

##### 最后，理解项目当前的定位

仓库中的设计文档具有前瞻性，更适合被看作项目计划和设计意图，而不是所有功能都已经完全实现的承诺。

参与贡献时，需要遵循项目对环境设置、代码格式、测试、提交信息和拉取请求的约定。如果是由智能体直接参与仓库开发，项目还专门提供了智能体说明和技能文件。

整个项目采用 MIT 许可证，允许在许可证规定下自由使用、修改和分发。

##### 最值得记住的几点

最后回顾五个核心结论。

第一，Cloudflare Computer 的核心不是单纯的远程容器，而是一个由 Durable Object 和 SQLite 支持的持久化虚拟工作区。

第二，它目前提供三种执行后端：完整 Linux 容器、轻量 Shell，以及直接运行 JavaScript 模块的 Dynamic Worker。

第三，所有后端都可以围绕同一个 Workspace 工作，并通过统一的执行入口调用；也可以只使用文件系统，完全不配置执行环境。

第四，它适合智能体处理需要长期保存文件、执行工具、生成代码或产物的多步骤任务。

第五，它在元数据密集型文件操作上表现突出，但大文件连续读写仍弱于真实磁盘，而且顶层软件包目前仍处于开发阶段。

## 深度解读（1）

### 2026-09-18 00:12:04

#### Cloudflare Computer：把智能体的“电脑”拆成持久工作区与临时算力

Cloudflare Computer 最值得关注的，并不是又提供了一台云端虚拟机，而是**重新划定了智能体计算环境的边界**：文件系统长期存在，执行环境则可以按需创建和替换。

它把权威文件状态保存在 Durable Object 的 SQLite 中，再接入三种执行后端：拥有完整 Linux、真实二进制和网络能力的容器；运行 `just-bash` 的轻量 Worker；以及执行 JavaScript 模块的 Worker。调用者统一通过 `workspace.runtime.exec` 执行任务，但可以选择不同后端。

##### 智能体真正需要持久的，未必是整台机器

传统沙箱常把进程、文件与容器生命周期绑在一起。容器销毁后，要么丢失现场，要么依靠额外的卷、对象存储和同步逻辑恢复。对智能体而言，这很别扭：一次任务可能持续数小时，中间经历多轮推理、工具调用、失败重试和环境重建，但真正需要延续的通常只是代码、文档、依赖描述和中间产物。

Cloudflare 的方案把工作区变成稳定锚点：容器可以临时挂载它，Worker 可以直接访问它，执行环境退出后文件仍然存在。这使智能体能够恢复任务、切换运行时，甚至让不同执行器接力完成同一工作。相比专用“记忆库”，文件系统还有一个现实优势：Git、编译器、Pandoc 和大量现有工具已经理解它，无需重新发明工具协议。

##### 同一个工作区，不等于后端完全可互换

统一的 `exec` 入口提供了一个很有价值的控制点：普通文件处理可交给启动快、成本低的隔离运行时；需要系统依赖、原生程序或完整网络能力时，再升级到容器。由此可以形成按**能力、成本和风险**动态路由任务的智能体基础设施，而不必让所有步骤默认占用完整 Linux 沙箱。

但这种统一不能被误解为无差别替换。不同后端接收的代码形态都不同——有的是 shell 命令，有的是 ECMAScript 模块；Worker 也不具备完整 Linux 用户空间。智能体或调度器仍需理解任务对二进制、网络、依赖和权限的要求。更准确的比喻是：**同一张持久书桌，可以换不同能力的执行者，而不是三台完全相同的电脑。**

##### 现在更像值得验证的架构，而非成熟结论

仓库明确标注顶层包仍在开发中，设计文档也只是前瞻意图。其性能结论同样需要限定：FUSE 文件系统只是在元数据密集型操作上快于真实磁盘，大块顺序读写反而更慢，不能泛化为“虚拟文件系统性能更高”。

真正决定这套架构能否成为平台能力的，是并发写入、崩溃恢复、同步延迟、权限与密钥隔离，以及跨后端执行的一致性。对智能体平台团队而言，最值得测试的也不是演示是否能运行，而是：**把状态与算力解耦后，能否在不降低任务成功率的前提下，显著减少环境恢复复杂度和容器成本。**如果成立，“给智能体一台电脑”最终卖的不会是一台机器，而是一个可持续、可迁移、可治理的工作现场。

##### 一句话看懂

Cloudflare Computer 是一个面向 AI Agent 的持久化虚拟工作区：文件存于 Durable Object 的 SQLite 中，并可统一调用容器、轻量 Shell 或 JavaScript 三种执行环境。

##### 关键内容

- **一份文件状态，多种执行后端**：Workspace 是唯一可信的数据源，通过 `workspace.runtime.exec()` 选择后端执行命令或代码；也可只使用文件系统，不配置执行环境。
- **三种后端各有侧重**：容器提供完整 Linux、真实二进制和网络；Isolate Shell 用 `just-bash` 轻量执行；Isolate JavaScript 在新的 Dynamic Worker 中运行 ES 模块，并支持持久化导入及文件、Git、产物模块。
- **项目提供完整示例**：涵盖读写与执行接口、聊天 Agent、不同运行时对比、生成 PDF、发布代码仓库和 AI 图片等。实际使用应安装 `@cloudflare/computer`，仓库内的顶层包仍标为开发中。
- **性能并非全面胜过磁盘**：项目基准显示，FUSE 文件系统在大量元数据操作中更快，但大文件连续读写较慢；设计文档也偏前瞻，应视为目标而非全部已实现能力。

##### 通俗解读

这里的“Computer”不是一台可远程操作的桌面电脑，而是给 Agent 使用的“持久文件夹＋可切换执行器”。Agent 写下的文件长期保留，需要完整 Linux 工具时进容器，只跑脚本时则可用更轻量的 Worker。
