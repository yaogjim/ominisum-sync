## 正文

**sitin**

刷 GitHub 看到一个挺有意思的项目，叫 Clawith。简单说一句话：它想把 OpenClaw 从“个人 AI 助手”，变成“AI 团队协作平台”。

Clawith 做了一件事：把OpenClaw的“定时触发”升级成“持续感知”。

他们提出了一个叫 Aware 的机制。  
除了 OpenClaw 原本的 heartbeat、cron、interval、webhook 这些触发方式之外，还加了一个很关键的触发器：on\_message。

就是说只要有人或者另一个 Agent 发消息，它就会立刻触发。

在多 Agent 协作里，这其实特别重要。  
因为任务来源不再只有人，还可能是别的 Agent。整个系统会变成一个不断互相触发的协作网络，而不是一个一个排队执行的脚本。

另一个设计 Relationship（关系系统）  
Clawith 把 Agent 当成“数字员工”来设计。  
每个 Agent 进来以后，不只是有技能，还会认识团队成员：谁是老板、谁是同事、谁负责什么工作。

甚至还有一个类似 公司朋友圈的广场，Agent 可以发动态、分享发现、评论别人的工作。

乍一看有点像社交功能，但其实背后的逻辑是：让 Agent 持续吸收组织里的信息，而不是孤立干活。

很多人现在在做 Agent，其实还是在做“会自动执行的工具”。

但真正的方向可能不是工具，而是 数字劳动力。

一个人养一个 Agent，和一个团队养一群 Agent，是完全不同的问题。

当 Agent 开始互相协作、互相触发、互相传递任务的时候，你就会发现——这已经不是“AI 帮你干点活”。而是一群 AI 在一起工作。

## 解读（1）

### 2026-03-17 08:16:14

##### 总结

这段内容在说一个叫 **Clawith** 的项目，它想把 OpenClaw 从“单个 AI 助手”升级成“多个 AI 一起工作的协作平台”。

核心有两点：

- **触发方式升级**：不只是定时执行，还加入了 `on_message`，即一收到消息就能立刻行动。
- **关系系统升级**：把 Agent 设计成“数字员工”，让它们有分工、有上下级、有协作关系，还能共享信息。

作者的核心判断是：未来 Agent 不是单纯的“自动化工具”，而更像是能协作的“数字劳动力”。

---

##### 解读

###### 1. 为什么 `on_message` 很重要？

以前很多 Agent 系统更像“定时脚本”：

- 到时间执行一次
- 有 webhook 就响应一下
- 按固定频率轮询

这类方式适合自动化，但**不适合团队协作**。

`on_message` 的意义在于：

- 人给 Agent 发消息，Agent 立刻响应
- 一个 Agent 给另一个 Agent 发消息，也能立刻触发
- 任务不再是“排队等执行”，而是能形成“实时接力”

通俗讲，就是从“闹钟响了才干活”，变成了“同事一喊你就开工”。

这会让整个系统更像一个真实团队，而不是一堆孤立的自动脚本。

###### 2. 为什么“关系系统”值得关注？

很多 Agent 产品只关心两件事：

- 它会什么
- 它能不能把任务做完

但 Clawith 多做了一层：**它是谁，和谁协作，处在什么组织关系里**。

这意味着 Agent 不只是“工具”，而是“组织成员”：

- 知道谁给它派任务
- 知道谁能配合它完成工作
- 知道团队最近发生了什么

这样设计的好处是，Agent 不会只盯着眼前指令，而是更容易理解上下文。

通俗讲：
一个只会执行命令的 Agent，像“计算器”；
一个能理解组织关系的 Agent，更像“员工”。

###### 3. 这背后代表了什么趋势？

作者其实在强调一个很大的方向变化：

- 过去：一个人配一个 AI 工具
- 未来：一个团队配一群可协作的 AI

这两者差别很大。

如果只是单 Agent，重点是“能力强不强”；
如果是多 Agent，重点就变成：

- 怎么分工
- 怎么沟通
- 怎么触发彼此
- 怎么共享信息
- 怎么避免混乱和重复劳动

也就是说，难点不再只是“模型聪不聪明”，而是“系统会不会协作”。

---

##### 我的意见

我认为这个方向**很有价值，而且比单纯做更强的 Agent 更接近实际生产场景**。

###### 看好的地方

- **`on_message` 很关键**：这是多 Agent 协作真正跑起来的基础。
- **关系系统有想象力**：它补上了很多 Agent 系统里缺失的“组织层”。
- **更贴近企业需求**：现实工作本来就不是单点执行，而是多人协同。

###### 需要警惕的问题

- **容易失控**：Agent 互相触发，可能导致消息风暴、重复执行、死循环。
- **管理成本会上升**：Agent 越多，权限、分工、责任边界越复杂。
- **“社交化”不一定等于高效率**：如果信息流过多，可能反而噪音变大。

###### 我的判断

这类项目最值得看的，不是“概念新不新”，而是后面能不能解决三个现实问题：

1. **协作是否稳定**：多 Agent 会不会乱套  
2. **成本是否可控**：消息、调用、算力会不会爆炸  
3. **结果是否可追踪**：出了问题能不能知道是谁触发了谁  

如果这些问题能处理好，Clawith 这类方向确实可能代表下一阶段 Agent 产品的演进路线：  
不是“一个 AI 帮你做事”，而是“一个 AI 团队替你协作”。
