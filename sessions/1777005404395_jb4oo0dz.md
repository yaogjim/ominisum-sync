### GitHub 联合创始人：Git 这个工具从来没被设计过

Scott Chacon 说了一句大实话：Git 当年根本没想过要做面向用户的产品。

它是给 Linux 内核团队写的管道命令，本质就是一堆 Perl 脚本凑合用 — 核心团队自己写 Perl，懒得写的人就直接用这些脚本。

后来这套东西被社区采纳，又从 Perl 改写成 C，但命令几乎没变。

20 年过去了，没有人真正从“产品设计”的角度驱动过它的演进。

GitHub 团队和 Git 核心团队的关系

Scott 回忆，当年 GitHub 刚起来时，Git 核心团队觉得他们“不太聪明”，因为 GitHub 团队不会写 C。

后来这种“勉强的尊重”（grudging respect）是慢慢建立的——因为太多项目迁移到了 GitHub。

但他也提到 Linus 的真实态度：GitHub 只是“不错的托管商”，但“我讨厌 PR，讨厌你们那套东西”。

本质上，就是把 GitHub 当免费托管用。这也代表了核心团队的态度：你是谁不重要，工具能用就行。

Git 是一个没有设计者的工具

他形容 Git 是一个“Frankenstein”。

什么都往里加，功能很强，但没有设计感。

作为一个开源项目，“只要看起来还行的想法就会被加进去”，但没有人定义产品方向，也没有人真正 say no。

这和 GitHub 完全不同：GitHub 是有 product vision、有 taste 的；但 Git 本身，从来没有。

Git 原始设计哲学的致命缺陷

Git 的设计基于 Unix philosophy：每个命令只做一件事，输出可以 pipe 给下一个命令。

但这从一开始就是一个折中：

- 既想让机器好用
- 又想让人类可读

结果是，两边都没做好。

他说得很直白：“你跑 git branch，它就只是列个分支，没有任何 UI。”

Git 解决的是底层 hard problems：

- delta 压缩
- wire 传输协议
- tree 的高效读写

但用户体验，从来不是目标。

为什么 AI agent 和 Git 合不来

一个非常精准的观察：

- agent 每执行一个命令，就要查一次 status
- interactive rebase 对 agent 来说几乎是噩梦

agent 需要不断解析 Git 的文本输出，再自己做决策。

但 Git 从来没为这种使用方式设计过。

更有意思的是：agent 现在还在用 sed、grep 这些 20 年前的 Unix 工具。

甚至很多年轻人，是被 agent 教会这些工具的。

Git 的向后兼容性是个诅咒

Git 几乎永远保持向后兼容。

之前存在的任何东西，他们都不会取出。

Scott 说他 2009 年写的 Pro Git 第一版，到现在命令几乎都还能用。

这意味着什么？

你几乎不可能做一个“Git 3.0 UI 重写”。

这不只是技术问题，而是文化问题：没人愿意 break anything，也没人有权力做这个决定。

他的解决方案：GitButler

他的答案不是推翻 Git，而是“加一层”。

核心思路：

- 保留现有的数据存储和传输协议
- 在用户界面层注入 product taste

GitButler 可以和普通 Git 自由切换，是一个 drop-in replacement，而不是一个全新物种。

目标不是让用户重新学习，而是让 Git 变得“终于像个产品”。

核心创新：Virtual Branches（虚拟并行分支）

这是最关键的技术点。

现在的常见 workaround 是 Git WorkTree：给项目做多份副本，每个人在不同副本里开发，再手动合并。

问题是：本质还是隔离副本 + 合并，流程复杂。

GitButler 的方式完全不同：

- 所有人（人类或 agent）在同一个代码库上工作
- 用 virtual branches 隔离每个人的改动
- 不复制文件，不产生传统 merge conflict

用户“感觉”在自己的分支上，但底层没有真正分叉。

改动在一个 loop 结束或尝试提交时自动合并。

这不是隔离，而是真正的并行协作。

代码审查已经过时了

他说得非常直接：“你真的会把 PR 从头读到尾吗？”

现实是：

- 大多数人只是扫一眼
- 没明显问题就 approve

PR 模式还带来了“commit slop”：

- 哎呀
- 再次修复
- 实际修复

commit message 逐渐失去意义。

而早期 mailing list 模式更好：patch 本身就是 artifact，逼着你写清楚。

在 agent 时代：

- 自动拉取 patch
- 编译
- 跑测试
- 输出摘要

review 变成“验证结果”，而不是盯 UI。

下一个超能力：写作和沟通

全场最重要的一句话：“未来最强的工程师，是那些能沟通、能写作、能描述的人。”

当 AI 把“how”变得极其便宜，约束变成：

- 为什么
- 什么

能清晰定义产品、写好 spec 的人，才能真正驾驭 agent。

他说很多开发者习惯把逻辑“放在脑子里”，觉得不用解释。

但在 agent 时代，这会成为致命弱点。

多 agent 协作的正确方式

一个很反直觉的建议：不要同时跑 20 个 agent。

那是管理灾难：

- 不知道谁在做什么
- review 成本爆炸

更好的方式是：

让 agent 在“空闲时间”通信，比如：“我在改这个文件，你别动。”

本质上是在解决一个老问题：inter-team communication。

而这正是 agent 最擅长的。

Metadata 会变得比代码更重要

他们在实验把这些信息直接挂到版本控制上：

- 聊天记录
- 工具调用日志
- 设计规格

让版本控制记录“为什么”，而不是只记录“做了什么”。

但问题也很现实：

- 每个 prompt 都存
- 每次调用都存

数据量会爆炸。

他还做过一个 CRDT 实验：记录每一次 file buffer save，可以回到 17 分钟前任意状态。

技术很酷，但 UI 完全不可用，信息过载，最终被砍。

结论很直接：能做出来 ≠ 人类能用。

现在他们在用 Git 内部一些冷门的高级 primitive，来解决 metadata 的存储和检索问题（原本是为 Windows / Office 级别代码库设计的）。

终极问题：最好的工程师 + 停止时间

他最后提出一个很哲学的问题：

如果 agent 的终点是 — 一个可以“停止时间”、无限工作、再恢复的顶级工程师。

那问题就变成：

- 你要用它做什么？
- 你怎么管理这段“冻结时间”？
- 你怎么判断结果已经足够好？

他用语言学习做类比：

即时翻译（babblefish）已经出现了，但它不等于真正会一门语言。

你不能靠翻译去建立深层关系、创业、理解文化。

同样的：

agent 会越来越强，但 “你到底想要什么” 这个问题，永远是人的责任。

## 通俗精炼（1）

### 2026-04-24 04:32:54

#### Git 的本质：强大工具，不是好产品

##### 一句话结论
Scott Chacon 的核心观点是：**Git 很强，但它从来不是为“普通用户体验”设计的产品**。它原本只是 Linux 内核团队内部使用的一组工具，后来虽然被广泛采用，但 20 年来几乎没有真正从产品设计角度重做过。

##### Git 为什么一直“难用”
Git 解决的是底层技术难题，比如存储、压缩、传输和版本管理效率；但**易用性、界面友好、交互设计**从一开始就不是目标。它延续了 Unix 工具思路：命令拆得很细、能串联使用，但结果是**对人不够友好，对机器也不够理想**。

##### 根本问题：没有人真正负责“产品设计”
Scott 认为，Git 像一个不断拼接功能的“科学怪人”——功能越来越多，却缺少统一体验。开源社区擅长持续加能力，但**没人真正定义整体方向，也很少有人敢删掉旧东西**。因此 Git 很强大，却始终不像一个完整、清晰的产品。

##### 为什么 Git 和 AI Agent 天生别扭
AI agent 使用 Git 时很痛苦，因为 Git 的交互方式主要是给人看的文本输出，不是给 agent 直接消费的结构化接口。像 `status`、`rebase` 这类操作，agent 需要反复解析文本、推断状态、再做决策，效率低且容易出错。**Git 并不是为 AI 协作时代设计的。**

##### Git 的历史包袱：兼容性太强
Git 最大的优点之一是向后兼容，但这也成了它进化的障碍。旧命令、旧习惯几乎都保留下来，导致你很难彻底重做一套更现代的交互方式。**这不只是技术问题，更是社区文化问题。**

##### GitButler 的思路：不推翻 Git，而是在上层重做体验
Scott 给出的方案不是替代 Git，而是在 Git 之上加一层更好的产品体验。GitButler 保留 Git 底层的数据和协议，但重新设计交互方式，让用户不用重新学习整个版本控制体系，就能获得更直观、更像“产品”的使用体验。

##### 最重要的创新：Virtual Branches
GitButler 提出的“虚拟分支”想解决多人或多 agent 并行开发的痛点。传统做法往往依赖多个副本或 worktree，管理复杂；而虚拟分支希望让多个改动在**同一个代码库中并行存在**，减少复制、切换和冲突处理成本。核心价值是：**让协作更自然，而不是让人适应复杂流程。**

##### 他对代码审查的判断：PR 模式正在过时
Scott 认为，很多 PR 审查并没有真正“认真阅读”，更多只是快速浏览后批准。随着 AI 参与开发，未来审查重点可能从“逐行看代码”转向“验证结果是否可靠”，例如自动跑测试、生成摘要、检查风险。**review 会更像结果校验，而不是界面化审批。**

##### AI 时代最稀缺的能力，不是写代码
他最重要的判断是：当“怎么做”越来越容易交给 AI，真正重要的是**你想做什么、为什么做、如何清楚表达需求和约束**。也就是说，未来最强的工程师或产品人，未必是最会手写代码的人，而是最会定义问题、写 spec、做沟通的人。

##### 未来版本控制记录的不只是代码
Scott 还提到，未来版本控制系统里更重要的，可能不是代码本身，而是围绕代码产生的元数据：聊天记录、设计说明、工具调用日志、决策原因等。因为真正有价值的，不只是“做了什么”，而是**为什么这么做**。

##### 最终启示
这篇内容本质上讲的是一件事：**技术工具可以非常强大，但如果没有产品视角，就很难真正适应新的使用时代。**  
在 AI 时代，人类最核心的责任不会消失——依然是定义目标、做判断、管结果。代码越来越便宜，**清晰表达与高质量决策会越来越贵。**

## 结构化（1）

### 2026-04-24 04:43:40

#### 文章主旨

这篇内容的核心观点是：`Git` 从诞生开始就不是一个面向普通用户设计的“产品”，而更像是为 Linux 内核团队临时拼出来的底层工具。进入 AI agent 时代后，Git 在交互方式、协作模式和可用性上的缺陷被进一步放大，也催生了像 `GitButler` 这样试图“在 Git 之上加一层产品体验”的新方案。

##### 1. Git 一开始就不是给普通用户设计的

- Scott Chacon 直言：`Git` 当年并不是一个认真做出来的用户产品，而是给 Linux 内核团队使用的一组“管道命令”。
- 早期本质上是“一堆 Perl 脚本凑合用”，后来虽然社区采纳并逐步改写成 C，但命令风格几乎没变。
- 过去约 `20 年`，Git 的演进几乎没有被“产品设计”驱动过，而更多是技术和兼容性驱动。

**例子：**
- 核心团队自己会写 Perl，就直接用脚本；不想写的人也只能继续用这些脚本，这说明它最初就是“内部工具思路”，不是“用户体验思路”。

##### 2. GitHub 与 Git 核心团队长期是两种思路

- Scott 回忆，GitHub 刚崛起时，Git 核心团队并不太看得起他们，觉得 GitHub 团队“不会写 C”。
- 后来随着越来越多项目迁移到 GitHub，核心团队才逐渐产生一种“勉强的尊重”（`grudging respect`）。
- Linus 对 GitHub 的态度很直接：认可它是个“不错的托管商”，但并不喜欢 `PR` 这套工作方式。

**关键点：**
- Git 核心团队更看重“工具能不能用”，不太关心“你是谁”或“交互体验好不好”。
- GitHub 则明显更偏向产品思维，有产品愿景、审美和使用体验设计。

##### 3. Git 功能强大，但像“缝合怪”

- Scott 用 `Frankenstein` 来形容 Git：功能不断叠加，什么都能塞进去，但整体没有统一设计感。
- 在开源模式下，只要一个想法“看起来还行”，就可能被加进去；但很少有人真正定义整体产品方向。
- 问题不在于 Git 不强，而在于“没人负责说不”，也没人统一决定它应该成为什么样的产品。

**通俗理解：**
- Git 像一个超强工具箱，里面工具很多，但摆放混乱、说明书难懂、上手门槛高。

##### 4. Git 原始设计哲学解决了底层难题，却牺牲了用户体验

- Git 深受 Unix philosophy 影响：每个命令只做一件事，输出再 pipe 给下一个命令。
- 但 Scott 认为，这种设计从一开始就是折中失败：
  - 想让机器容易处理；
  - 也想让人类能看懂；
  - 结果两边都没做到最好。
- Git 真正擅长的是底层“硬问题”，比如：
  - `delta` 压缩
  - 传输协议（wire protocol）
  - tree 的高效读写
- 但用户体验从来不在设计目标里。

**例子：**
- `git branch` 运行后只是列出分支，没有任何更友好的界面提示，这就是典型的“工具输出”，不是“产品界面”。

##### 5. 为什么 AI agent 与 Git 天生不合拍

- AI agent 在执行开发任务时，经常需要反复调用 `git status` 来确认当前状态。
- `interactive rebase` 这类交互式流程，对 agent 来说几乎像噩梦。
- agent 必须不断解析 Git 输出的文本，再自己决定下一步怎么做，而 Git 并不是为这种机器协作方式设计的。

**关键观察：**
- 今天的 agent 不仅在用 Git，还在用 `sed`、`grep` 这些 `20 年前` 的 Unix 工具。
- 甚至很多年轻人，反而是通过 agent 才重新接触并学会这些老工具。

##### 6. Git 的向后兼容既是优势，也是诅咒

- Git 几乎极端重视向后兼容，过去存在的东西很少会被真正移除。
- Scott 提到，他 `2009 年` 写的《Pro Git》第一版里的很多命令，到今天几乎都还能直接用。
- 这带来的问题是：你几乎不可能做一个“`Git 3.0` 式的彻底 UI 重写”。

**本质原因：**
- 这不只是技术问题，更是文化问题：
  - 没人愿意 break anything；
  - 也没人真正有权拍板做这种大改。

##### 7. GitButler 的思路：不推翻 Git，而是在上面加一层

- Scott 给出的解决方案不是重造版本控制，而是做一个“包裹 Git 的产品层”——`GitButler`。
- 它保留 Git 现有的数据存储和传输协议，只在用户界面和交互层加入更强的产品设计。
- 它可以和普通 Git 自由切换，是 `drop-in replacement`，不是完全不同的新系统。

**核心目标：**
- 不要求用户重学版本控制；
- 而是让 Git 第一次更像一个真正可用的产品。

##### 8. 最关键创新：Virtual Branches（虚拟并行分支）

- 传统的并行开发常见做法是 `Git WorkTree`：为同一个项目开多个副本，在不同副本里开发，再手动合并。
- Scott 认为这本质还是“隔离副本 + 合并”，流程复杂，成本高。
- `GitButler` 的 `Virtual Branches` 想法是：
  - 所有人或所有 agent 在同一个代码库工作；
  - 用虚拟分支隔离各自改动；
  - 不复制文件；
  - 不走传统意义上的分叉与合并流程；
  - 在一个 loop 结束或尝试提交时自动合并。

**通俗例子：**
- 传统做法像每个人拿一份文档副本，改完再人工对比合并；
- 虚拟分支更像多人在同一份底稿上工作，但系统自动帮你隔离和协调改动。

##### 9. 代码审查（PR 模式）正在过时

- Scott 对现有 PR 审查模式很不客气：现实中，大多数人并不会真的把 PR 从头到尾认真读完。
- 典型情况是：
  - 大致扫一眼；
  - 没明显问题就 approve。
- 这种模式还制造了大量 `commit slop`：
  - “哎呀”
  - “再次修复”
  - “实际修复”
- 结果是 commit message 越来越没信息量。

**对比观点：**
- 早期 mailing list 模式更强调 patch 本身是正式产物，逼着人把变更说明写清楚。
- 在 agent 时代，review 更可能变成：
  - 自动拉 patch
  - 自动编译
  - 自动跑测试
  - 自动生成摘要
- 审查重点从“盯 UI 看代码”转向“验证结果是否可靠”。

##### 10. 未来工程师最重要的能力，不再只是写代码

- Scott 认为，未来最强的工程师，是那些“能沟通、能写作、能描述问题”的人。
- 因为当 AI 把“怎么做（how）”变得越来越便宜，真正稀缺的是：
  - 为什么做（why）
  - 做什么（what）
- 谁能把需求讲清楚、把 spec 写清楚，谁就更能驾驭 agent。

**现实提醒：**
- 很多开发者习惯把逻辑放在脑子里，不愿意写清楚。
- 但在 agent 时代，这种“只可意会”的工作方式会成为明显短板。

##### 11. 多 agent 协作，重点不是越多越好，而是沟通机制

- Scott 提出一个反直觉建议：不要同时跑 `20 个 agent`。
- 原因很简单：
  - 你会不知道谁在做什么；
  - review 和协调成本会快速爆炸。
- 更好的方式是让 agent 在“空闲时间”彼此通信，比如：
  - “我在改这个文件，你别动。”

**本质上：**
- 这不是新问题，而是老问题——`inter-team communication`。
- 只是现在，这种沟通任务可能正好是 agent 擅长的。

##### 12. 未来版本控制中，Metadata 可能比代码更重要

- 他们正在尝试把更多“上下文信息”直接挂到版本控制里，比如：
  - 聊天记录
  - 工具调用日志
  - 设计规格
- 目标是让版本控制不仅记录“做了什么”，还记录“为什么这样做”。

**但问题也很现实：**
- 如果每个 prompt 都存、每次调用都存，数据量会急剧膨胀。
- Scott 还提到一个 `CRDT` 实验：记录每一次 file buffer save，甚至能回到 `17 分钟前` 的任意状态。
- 技术上很酷，但最终因为 UI 不可用、信息过载而被砍掉。

**结论：**
- 能实现，不等于人类真的能用。
- 他们现在在尝试利用 Git 内部一些冷门但高级的 primitive，去处理 metadata 的存储与检索问题。

##### 13. 最终问题不是 agent 能做多少，而是人想要什么

- Scott 最后抛出一个很有哲学意味的问题：
  - 如果 agent 可以像“停止时间”一样无限工作，
  - 那你到底想让它替你完成什么？
  - 你如何管理这段“冻结时间”？
  - 又如何判断结果已经足够好？
- 他用语言学习举例：
  - 即时翻译像 `babblefish` 一样已经出现；
  - 但它不等于真正掌握一门语言。
- 同样地，agent 会越来越强，但“目标定义”和“价值判断”仍然必须由人负责。

#### 总结

这篇文章不是单纯在批评 Git，而是在指出一个更深层的问题：`Git` 极其强大，却从来不是按“产品”思路演进的；而 AI agent 的出现，把这种历史包袱暴露得更明显。Scott 的答案不是推翻 Git，而是在兼容现有生态的前提下，用更好的产品设计、协作模型和 metadata 系统，让版本控制真正适应人和 agent 共存的未来。
