## 分析要点

- **核心高价值点**：把AI使用重点从“写好一次提示词”转向“设计可验证、可停止、可迭代的自动反馈循环”。
- **留存建议**：短期参考后可归档，适合作为AI Agent工作流设计的概念性材料（包含可复用的循环工程框架、构建块和应用场景，虽证据不足但有方法论参考价值）

**知识要点**

- 循环工程的核心流程包括发现、计划、执行、验证、迭代，目标是减少人类在每一步中的手动介入
- 闭环比开环更适合作为起点，因为目标、步骤、评估标准和停止条件更明确，成本和失控风险更低
- 高质量Agent循环需要自动化触发、隔离工作树、项目技能文件、外部工具连接器、独立审核子代理和持久记忆
- 长期运行的AI循环会快速消耗大量token，因此长上下文、低成本模型和良好的上下文管理是落地关键

**行动项**

- 为一个常见工作任务设计闭环流程，明确触发条件、成功标准、验证方式和停止条件
- 整理项目级技能文件，包括愿景、架构、规则、构建步骤、测试步骤和禁止事项
- 在编码或研究任务中尝试引入独立检查代理，避免生成者自审导致质量偏差
- 评估现有AI工作流的token成本、上下文复用方式和是否具备持久记忆

### Loop Engineering：每个建设者在 2026 年都需要的 AI 技能

大多数人仍然在手动提示代理。

他们输入一个任务。

等待一个答案。

自己审查它。

修复错误本身。

然后再次提示

这意味着人类仍然是循环的一环。

下一步是不同的。

你不只是提示代理。

你设计一个循环，该循环会提示代理、检查结果、决定下一步行动，并持续运行直到工作通过。

那就是循环工程。

> 你不应该再提示编码代理了。你应该设计循环来提示你的代理。

然后，Anthropic 公司 Claude Code 的负责人鲍里斯·切尔尼以不同的方式说了同样的事情：

> 我不再提示 Claude 了。我有正在运行的循环，这些循环会提示 Claude 并弄清楚该做什么。我的工作是编写循环。

---

#### 为什么大多数人从未构建真正的循环

循环听起来很棒，直到你看到代币账单。

一个普通的代理循环会快速消耗大量上下文：

- 一个中等规模的编码循环可以使用 50K-200K tokens
- 由一个编排器和若干专业代理组成的集群循环可以使用 500K-2M tokens
- 一个每日定时循环每周可达到数百万个 token

每次重试都会消耗令牌。

每一次自我修正都会消耗令牌。

每一个验证步骤都消耗令牌。

每个子代理都需要消耗代币。

那是一个没人充分讨论的隐藏问题。

Loop 工程并不难，因为其概念很复杂。

这很难，因为大多数人无法负担让代理长时间自由运行。

> 你说得轻巧，你拥有无限的 OpenAI 访问权限。

那个反应是合理的。

这就是为什么更便宜的长上下文模型至关重要。

如果你想要循环每天运行，你需要：

- 廉价输入令牌
- 廉价的输出令牌
- 大上下文窗口
- 工具调用
- JSON 输出
- 高并发
- 足够的上下文以记住循环中之前发生的事情

没有那个，循环就会变成昂贵的实验。

这样一来，循环成为实用的工作流程。

---

#### 旧方式 vs 新方式

在过去两年中，大多数人使用过这样的代理：

你提示

代理回答。

你审核。

你找到这个错误。

你再次提示。

那可行，但它无法扩展。

旧方法：

- 你给出一个提示
- 代理给出一个输出
- 你检查输出
- 你修复薄弱环节
- 您手动重复

新的方式：

- 你定义目标
- 循环发现所需内容
- 循环安排工作
- 代理执行
- 检查器验证结果
- 循环修复故障
- 当目标达成时，系统停止

提示给代理一个指令。

循环工程为代理分配任务。

---

#### Loop 工程到底是什么

循环工程是为 AI 代理设计可重复反馈循环的实践。

目标很简单：

从尝试到已验证结果，无需人类手动操控每一步。

基本周期包含五个阶段：

1. 发现
2. 计划
3. 执行
4. 验证
5. 迭代

如果输出通过，就发货。

如果它失败，将其送回循环中。

这就是整个核心思想。

没有一个完美的提示。

一个持续改进输出直到达到标准的系统。

---

#### 单代理 vs 集群

循环有两种基本尺寸。

### 单代理循环

一个代理运行整个周期。

它识别所需内容，规划工作，执行任务，检查结果，并在出现问题时进行改进。

这就像一个人重写自己的草稿。

适用于：

- 专注任务
- 小范围
- 简单目标
- 内容草稿
- 漏洞修复
- 研究总结

一个大脑。

一个循环

自我提升

---

### 车队循环

一个舰队循环更大。

你给予一个 orchestrator agent 主要目标。

它把工作分解成小块。

然后它将那些部分发送给专业代理。

每个专家也可以使用更小的子代理来处理特定任务。

示例

```plaintext
Example: "Build a productivity app"

Orchestrator owns the mission
    ↓              ↓              ↓
Research      Engineering        QA
Specialist    Specialist         Specialist
    ↓              ↓              ↓
Web           Code Writer        Test Writer
Researcher    + Debugger         + Bug Tracker
```

这不是一个代理独自工作。

这更接近于一个小团队端到端地负责一个项目。

---

#### 开环 vs 闭环

这是最重要的实际区别。

并非所有循环都相等。

#### 开放循环

开环是探索性的。

你给代理一个宽泛的目标，并且让它寻找路径。

这很强大，因为代理能够发现你未指定的事物。

但是它也很昂贵且杂乱。

开环可以：

- 尝试太多路径
- 销毁过多代币
- 快速创建低质量输出
- 偏离真正的目标
- 变得难以控制

开环很令人兴奋。

但是对大多数人来说，它们不是最好的起点。

---

#### 闭环

闭合回路是有界的。

人首先设计路径。

循环仍然自主运行，但在明确的规则之内。

闭环具有：

- 明确的目标
- 已定义的步骤
- 每一步之后的评估
- 停止条件
- 交接点（如果卡住）

这就是今天真正能带来回报的版本。

它更便宜。

它更可靠。

它产生更干净的输出。

从闭环开始。

稍后当你的检查足够强时再打开它们。

#### 良好循环的6个构建块

从概念上讲，每个循环都有五个阶段。

但实际上，你需要六个构建块来使循环正常工作。

#### 自动化

这是心跳。

自动化会自动启动循环，无需你手动记住运行它。

示例：

- 每天早上跑步
- 在 PR 打开时运行
- 当文件更改时运行
- 当新工单出现时运行
- 运行直到所有测试通过

如果仍然需要手动启动所有内容，那么这个循环实际上并没有完成足够的工作。

#### 2\. 工作树

当多个代理编辑代码时，工作树很重要。

没有分离，代理会碰撞。

两个代理可以编辑同一个文件。

一个可以覆盖另一个。

工作树为每个代理提供了各自独立的干净工作区和分支。

这使得多个代理能够并行工作，而不会把代码仓库弄得一团糟。

#### 3\. 技能

技能是可复用的项目知识。

与其每次都解释你的项目，你只需一次写下重要的背景信息。

良好的技能文件包括：

- 愿景
- 架构
- 规则
- 构建步骤
- 测试步骤
- 代理绝对不能做的事项

没有技能，每个循环都从冷启动开始。

凭借技能，每一个循环都始于积累的上下文。

#### 4\. 插件和连接器

一个只能处理文件的循环是有限的。

连接器让循环接触你的实际工具。

示例：

- GitHub
- Slack
- 线性的
- 吉拉
- 谷歌邮箱
- Google Drive
- 数据库
- 预发布 API

这就是“这里有一个建议的修复”和“我打开了 PR，关联了工单，查看了 CI，并发布了更新”之间的区别。

#### 5\. 分代理

制作者和检查者不应该总是同一个人。

编写代码的人在审查代码时通常会过于宽容。

撰写该文章的作者将会忽略其自身的薄弱部分。

使用单独的代理用于：

- 探索
- 实现
- 审核
- 测试
- 事实核查
- 最终总结

当评审者不是创作该作品的同一主体时，质量得到提升。

#### 6\. 内存

内存是使循环在多次运行中持续的东西。

模型会忘记。

这个仓库不

笔记不

项目日志不

内存可以存在于：

- Markdown 文件
- 项目日志
- 线性票
- GitHub 问题
- Obsidian 知识库
- 数据库
- Claude 项目

一个长期运行的循环需要知道哪些尝试过了，哪些通过了，哪些失败了，以及还有哪些需要发生。

没有记忆，它每次都从零开始。

#### 真实循环示例

以下是使这个想法具体化的循环。

#### 编码循环

循环：

```plaintext
Read VISION.md + ARCHITECTURE.md
↓
Plan next change
↓
Edit code
↓
Run tests
↓
If tests fail → read error → fix → test again
↓
If tests pass → summarize changes
↓
Stop
```

没有人需要推动每一步。

代理编写、测试、修复并验证。

#### 研究循环

循环：

```plaintext
Define research question
↓
Search for sources
↓
Summarize findings
↓
Verify claims against sources
↓
Compare conflicting information
↓
Synthesize final answer
↓
Stop when confidence threshold met
```

这比请求一个快速的总结好得多。

#### 内容循环

循环：

```plaintext
Topic + audience + goal defined
↓
Draft created
↓
Critique agent reviews draft
↓
Rewrite based on critique
↓
Score against success criteria
↓
If score passes → publish
↓
If score fails → rewrite again
```

这个循环将一个想法转化为内容体系。

#### 销售外展循环

循环：

```plaintext
ICP (Ideal Customer Profile) defined
↓
Find leads matching profile
↓
Enrich with company data
↓
Qualify against criteria
↓
Personalize message
↓
Quality review
↓
Send or escalate to human
```

相同的骨架:

目标

操作。

检查

修复

重复直到完成。

#### 提示工程师 vs 循环工程师

这是2026年出现的技能缺口

#### 提示工程师

提示工程师专注于更好的提示。

他们改进了措辞。

他们得到更好的单一输出。

但是人仍然会在运行之后审查一切。

人仍然是反馈循环。

#### 循环工程师

回路工程师设计反馈系统。

他们决定：

- 什么启动了循环
- 代理需要什么上下文
- 它可以使用哪些工具
- 什么算作成功
- 谁检查工作
- 当循环应该停止时
- 结果应该保存在哪里

提示工程师说：

给我写一个函数。

一位回路工程师说：

编写它，测试它，修复它，直到它通过，然后总结这个变更。

相同的工具

不同的思维模式。

最高杠杆的 AI 构建者不仅仅是在编写更好的英文提示词。

他们正在设计能够正确发现、规划、执行、验证并停止的系统。

#### 简版

循环工程是从手动提示到自动化反馈循环的转变。

转变：

- 旧方式：一次向代理提示一个任务
- 新方法：设计运行完整周期的循环

你实际构建的6件事：

- 自动化：启动循环的心跳
- 工作树：无文件冲突的并行代理
- 技能：项目知识每次运行复用
- 插件和连接器：获取实际工具
- 子代理：制单人与审核人分离
- 内存：循环在运行之间保持记忆

这两种尺寸：

- 单一智能体循环：一个智能体改进自己的工作
- 集群循环：编排器加专家加子代理

这两种类型：

- 开环：强大的，探索性的，昂贵的
- 闭环：有界的，可靠的，可负担的

5个阶段:

1. 发现
2. 计划
3. 执行
4. 验证
5. 迭代

实际成本问题：

- 循环快速销毁代币
- 廉价的长上下文模型使循环变得实用
- 没有价格亲民的代币，大多数人永远无法超越实验阶段

思维模式的转变：

- 提示工程师向 AI 请求输出
- Loop 工程师设计可产生已验证成果的系统

That is the real unlock.

Stop trying to write one perfect prompt.

Start building the loop that makes imperfect outputs better.

A reliable loop beats a perfect prompt.

#### 《Loop Engineering》深度总结与解读

##### 一句话总结

**未来真正重要的 AI 能力，不是写出“完美提示词”，而是设计一个能自动执行、检查、修正、停止的反馈循环。**

---

##### 1. 深度总结

###### 核心观点

过去，人类使用 AI 的方式是：

> 人提出任务 → AI 输出 → 人检查 → 人修改 → 再提示

这本质上是：**人仍然卡在循环里。**

而 Loop Engineering 的目标是：

> 人设计规则和系统，让 AI 自己完成“执行—检查—修正—再执行”，直到结果达标。

也就是说，人不再反复提示 AI，而是设计一个能持续运转的工作流。

---

##### 2. Loop Engineering 是什么？

**Loop Engineering = 为 AI Agent 设计可重复的反馈循环。**

一个基本循环包括：

```text
发现 → 计划 → 执行 → 验证 → 迭代
```

如果结果合格，就结束；  
如果不合格，就回到循环继续修正。

重点不是“一次生成完美结果”，而是：

> 让系统不断把不完美结果变好，直到通过标准。

---

##### 3. 旧方式 vs 新方式

###### 旧方式：提示工程

```text
你写提示词
AI 给答案
你检查
你修改
你再问
```

问题是：  
**无法规模化，因为人始终是瓶颈。**

---

###### 新方式：循环工程

```text
你定义目标
AI 拆解任务
AI 执行任务
检查器验证结果
失败则自动修复
达标后停止
```

优势是：  
**人从“操作员”变成“系统设计者”。**

---

##### 4. 两类循环

###### 1）单 Agent 循环

一个 Agent 完成全部流程：

```text
理解任务 → 制定计划 → 执行 → 自查 → 修正
```

适合：

- 写文章
- 修 bug
- 做总结
- 小型研究
- 简单代码任务

特点：轻量、便宜、容易上手。

---

###### 2）集群 Agent 循环

一个总控 Agent 负责拆解任务，多个专业 Agent 分工执行。

例如：

```text
总控 Agent
├── 研究 Agent
├── 工程 Agent
├── 测试 Agent
└── 审核 Agent
```

适合：

- 构建产品
- 大型代码项目
- 复杂研究
- 多步骤业务流程

特点：能力强，但成本高、复杂度高。

---

##### 5. 开环 vs 闭环

###### 开环

开环更自由：

```text
给 AI 一个大目标，让它自己探索路径
```

优点：

- 可能发现意外机会
- 创造性更强

缺点：

- 容易跑偏
- 消耗大量 token
- 结果难控制
- 成本高

---

###### 闭环

闭环更可控：

```text
明确目标、步骤、检查标准和停止条件
```

优点：

- 更便宜
- 更稳定
- 更适合实际落地
- 更容易评估效果

结论：

> 普通人和团队应先做闭环，再逐步开放。

---

##### 6. 好循环的 6 个构建块

###### 1）自动化

循环应能自动启动。

例如：

- 每天定时运行
- PR 打开时运行
- 文件变化时运行
- 工单创建时运行

如果每次都要人手动启动，就还不是真正的循环。

---

###### 2）工作树

多个 Agent 同时改代码时，需要独立工作区，避免互相覆盖。

作用是：

> 让多个 AI 可以并行工作，而不把项目搞乱。

---

###### 3）技能

技能是可复用的项目知识。

包括：

- 项目愿景
- 架构说明
- 编码规则
- 构建步骤
- 测试方法
- 禁止事项

有了技能，AI 不用每次从零理解项目。

---

###### 4）插件和连接器

循环不能只停留在文本里，而要连接真实工具。

例如：

- GitHub
- Slack
- Jira
- Gmail
- 数据库
- CI/CD
- Google Drive

这决定了 AI 是“给建议”，还是“真正完成工作”。

###### 5）子代理

创作者和审核者最好分开。

因为：

> 写代码的 AI 不一定能严格审查自己的代码；写文章的 AI 也容易忽略自己的问题。

所以需要不同 Agent 分工：

- 实现
- 测试
- 审核
- 查证
- 总结

###### 6）内存

循环需要长期记忆。

记住：

- 做过什么
- 哪些失败了
- 哪些通过了
- 下一步是什么

内存可以放在：

- Markdown
- GitHub Issue
- 项目日志
- 数据库
- Obsidian
- Linear / Jira

没有内存，AI 每次都像第一次上班。

##### 7. 最大现实问题：成本

Loop Engineering 的瓶颈不是概念，而是成本。

一个循环会消耗大量 token：

- 每次重试要 token
- 每次验证要 token
- 每个子代理要 token
- 长上下文也要 token

所以，要让循环真正普及，需要：

- 便宜的输入 token
- 便宜的输出 token
- 长上下文窗口
- 稳定工具调用
- JSON 输出能力
- 高并发能力

否则，循环只是昂贵实验。

## 结构化（1）

### 2026-07-03 11:36:14

#### 《Loop Engineering：每个建设者在 2026 年都需要的 AI 技能》精炼总结

文章的核心观点是：AI 使用方式正在从“人工反复提示代理”转向“设计自动反馈循环”。未来更重要的能力不是写出完美提示词，而是构建能自动执行、检查、修复并最终交付结果的系统。

---

##### 1. 从“手动提示”到“循环工程”

过去大多数人使用 AI 代理的方式是：

1. 人输入任务  
2. 代理给出答案  
3. 人审查结果  
4. 人发现错误并修复  
5. 再次提示代理  

这种方式的问题是：**人仍然是整个反馈循环的核心环节**，效率无法规模化。

新的方式是：  
不是直接提示代理，而是设计一个循环，让系统自动完成：

- 给代理分配任务
- 检查代理输出
- 判断下一步动作
- 失败后自动修复
- 直到结果达标才停止

这就是文章所说的 **Loop Engineering，循环工程**。

Anthropic Claude Code 负责人 Boris Cherny 也表达了类似观点：  
> 他不再直接提示 Claude，而是编写能自动提示 Claude、判断下一步该做什么的循环。

---

##### 2. 为什么大多数人还没有真正构建循环？

循环听起来简单，但真正落地的最大障碍是：**成本太高，尤其是 token 成本**。

一个普通代理循环会快速消耗大量上下文和 token：

- 中等规模编码循环：约 **50K - 200K tokens**
- 编排器 + 多个专业代理的集群循环：约 **500K - 2M tokens**
- 每日定时运行的循环：每周可能消耗 **数百万 tokens**

每一次重试、自我修正、验证、调用子代理，都会继续消耗 token。

因此，循环工程难点不在于概念复杂，而在于：  
**大多数人负担不起让代理长时间自主运行。**

要让循环成为实用工作流，需要模型具备：

- 便宜的输入 token
- 便宜的输出 token
- 大上下文窗口
- 工具调用能力
- JSON 输出能力
- 高并发
- 足够长的上下文记忆能力

没有这些条件，循环就只是昂贵的实验。

---

##### 3. 旧方式 vs 新方式

###### 旧方式：提示驱动

旧方法是：

- 人给出提示
- 代理输出结果
- 人检查
- 人修复问题
- 人手动重复

这种方式可用，但不能扩展。

###### 新方式：循环驱动

新方法是：

- 人定义目标
- 循环发现需要做什么
- 循环安排任务
- 代理执行
- 检查器验证结果
- 循环修复失败部分
- 达成目标后系统停止

一句话区别：

> 提示是给代理一个指令；循环工程是给代理设计一套完成任务的系统。

---

##### 4. Loop Engineering 到底是什么？

循环工程是：  
**为 AI 代理设计可重复运行的反馈循环，让任务从尝试走向已验证结果，而不需要人类手动操控每一步。**

一个基础循环通常包含五个阶段：

1. **发现**：弄清楚需要做什么  
2. **计划**：制定执行方案  
3. **执行**：完成具体任务  
4. **验证**：检查结果是否达标  
5. **迭代**：失败则返回修复，成功则停止  

核心思想不是写一个完美提示词，而是构建一个系统，让不完美的输出不断改进，直到符合标准。

---

##### 5. 两种循环规模：单代理循环与集群循环

###### 5.1 单代理循环

单代理循环是指：一个代理完成整个流程。

它会自己：

- 识别需求
- 制定计划
- 执行任务
- 检查结果
- 修复问题

这类似一个人不断修改自己的草稿。

适合场景包括：

- 小范围任务
- 内容草稿
- 漏洞修复
- 研究总结
- 简单目标

特点是：  
**一个大脑，一个循环，自我改进。**

---

###### 5.2 集群循环

集群循环更像一个小团队。

通常结构是：

- 一个 orchestrator agent，负责任务总目标
- 多个专业代理，负责不同模块
- 每个专业代理还可以调用更小的子代理

例如目标是：**构建一个生产力 App**

可能拆分为：

- Research Specialist：负责调研
- Engineering Specialist：负责工程实现
- QA Specialist：负责质量测试
- Web Researcher、Code Writer、Test Writer、Bug Tracker 等子代理

这不是一个代理独自完成任务，而是多个代理协作，像一个端到端项目团队。

---

##### 6. 两种循环类型：开环与闭环

###### 6.1 开环：探索性强，但成本高

开环是指给代理一个宽泛目标，让它自己探索路径。

优点是：

- 能发现人没有明确指定的问题
- 更有创造性
- 适合探索未知任务

缺点是：

- 容易尝试太多路径
- 消耗大量 token
- 输出质量不稳定
- 容易偏离目标
- 难以控制

文章认为：开环虽然令人兴奋，但不适合大多数人作为起点。

---

###### 6.2 闭环：更可靠、更便宜、更适合落地

闭环是指人先设计好边界和路径，代理在规则内自主运行。

闭环通常具备：

- 明确目标
- 已定义步骤
- 每一步后的评估机制
- 停止条件
- 卡住时的人工交接点

它的优势是：

- 成本更低
- 可靠性更高
- 输出更干净
- 更适合当前实际生产环境

作者建议：  
**先从闭环开始，等检查机制足够强后，再逐步开放为开环。**

---

##### 7. 一个好循环需要的 6 个构建块

虽然循环概念上有五个阶段，但真正落地需要六个关键构建块。

---

###### 7.1 自动化：循环的心跳

自动化决定循环何时启动。

例如：

- 每天早上自动运行
- PR 打开时自动运行
- 文件变更时自动运行
- 新工单出现时自动运行
- 测试未通过时持续运行直到通过

如果每次都需要人工手动启动，那么这个循环还不够完整。

---

###### 7.2 工作树：避免多个代理互相冲突

当多个代理同时编辑代码时，容易出现冲突：

- 两个代理修改同一个文件
- 一个代理覆盖另一个代理的改动
- 仓库状态变混乱

工作树可以为每个代理提供独立工作区和分支，让它们并行工作而不互相破坏。

---

###### 7.3 技能：可复用的项目知识

“技能”是沉淀下来的项目上下文。

与其每次都向代理解释项目，不如一次性写好关键知识文件，例如：

- 项目愿景
- 系统架构
- 编码规则
- 构建步骤
- 测试步骤
- 代理绝对不能做的事

没有技能文件，每次循环都是冷启动；有了技能文件，每次循环都能基于已有知识继续工作。

---

###### 7.4 插件和连接器：连接真实工具

如果循环只能处理本地文件，能力会非常有限。

连接器可以让代理接入实际工作工具，例如：

- GitHub
- Slack
- Linear
- Jira
- Gmail
- Google Drive
- 数据库
- 预发布 API

这让代理从“给出建议”升级为“真正执行工作”。

例如不只是说：  
> 这里有一个建议修复方案。

而是可以做到：  
> 我已经打开 PR，关联工单，检查 CI，并发布了进度更新。

---

###### 7.5 子代理：创作者和检查者分离

文章强调：  
**做事的人和检查的人不应该总是同一个。**

原因是：

- 写代码的代理可能对自己的代码过于宽容
- 写文章的代理可能忽略自己表达中的薄弱点

因此可以设置不同子代理负责：

- 探索
- 实现
- 审核
- 测试
- 事实核查
- 最终总结

当评审者不是创作者时，质量通常会更高。

---

###### 7.6 内存：让循环不会每次从零开始

模型本身会遗忘，但项目文件、日志和数据库不会。

循环需要记录：

- 已尝试过什么
- 哪些方案失败了
- 哪些结果通过了
- 下一步还需要做什么

内存可以存在于：

- Markdown 文件
- 项目日志
- Linear 工单
- GitHub Issue
- Obsidian 知识库
- 数据库
- Claude 项目

没有内存，循环每次都像第一次运行；有了内存，循环才能长期积累经验。

---

##### 8. 几个真实循环案例

###### 8.1 编码循环

一个编码循环可以是：

1. 读取 `VISION.md` 和 `ARCHITECTURE.md`
2. 规划下一个改动
3. 编辑代码
4. 运行测试
5. 如果测试失败，读取错误并修复
6. 再次测试
7. 如果测试通过，总结变更
8. 停止

这个过程中，人不需要推动每一步。  
代理会自动完成编写、测试、修复和验证。

---

###### 8.2 研究循环

一个研究循环可以是：

1. 定义研究问题
2. 搜索资料来源
3. 总结发现
4. 根据来源验证结论
5. 比较冲突信息
6. 综合最终答案
7. 达到可信度阈值后停止

这比简单要求 AI “快速总结一下”更可靠，因为它包含验证和冲突处理。

---

###### 8.3 内容创作循环

一个内容循环可以是：

1. 定义主题、受众和目标
2. 生成初稿
3. 评论代理审查初稿
4. 根据批评意见重写
5. 根据成功标准打分
6. 达标则发布
7. 不达标则继续重写

这个循环可以把一个想法转化为稳定的内容生产系统。

---

###### 8.4 销售外展循环

一个销售外展循环可以是：

1. 定义理想客户画像 ICP
2. 找到符合画像的潜在客户
3. 补充公司数据
4. 按标准筛选客户
5. 个性化生成消息
6. 进行质量审查
7. 发送或升级给人工处理

这些案例的共同骨架都是：

> 目标 → 行动 → 检查 → 修复 → 重复，直到完成。

---

##### 9. 提示工程师 vs 循环工程师

文章认为，2026 年的 AI 技能缺口在于：  
从“提示工程师”转向“循环工程师”。

###### 提示工程师关注什么？

提示工程师主要关注：

- 如何写更好的提示词
- 如何优化措辞
- 如何获得更好的单次输出

但问题是：  
人仍然需要在每次输出后审查和反馈。

---

###### 循环工程师关注什么？

循环工程师设计的是整个反馈系统。

他们需要决定：

- 什么会启动循环
- 代理需要哪些上下文
- 代理可以使用哪些工具
- 什么算成功
- 谁来检查结果
- 什么时候停止
- 结果保存在哪里

两者的区别可以用一句话概括：

- 提示工程师说：  
  > 给我写一个函数。

- 循环工程师说：  
  > 写出这个函数，运行测试，修复错误，直到测试通过，然后总结变更。

工具可能相同，但思维方式完全不同。

---

##### 10. 最重要的结论

Loop Engineering 的本质，是从“手动提示 AI”转向“设计自动化反馈循环”。

关键转变是：

- 旧方式：一次提示代理完成一个任务
- 新方式：设计一个能发现、计划、执行、验证、迭代并停止的系统

真正要构建的是六件事：

1. **自动化**：让循环自动启动  
2. **工作树**：支持多个代理并行工作  
3. **技能**：复用项目知识  
4. **插件和连接器**：接入真实工具  
5. **子代理**：分离执行者和检查者  
6. **内存**：让系统长期积累经验  

最终观点是：

> 不要再追求一个完美提示词。  
> 应该构建一个能让不完美输出不断变好的循环。  
> 一个可靠的循环，胜过一个完美的提示。

- **开环**允许代理自由探索，可能发现意外路径，但成本高、易偏离目标。
- **闭环**预先规定步骤、评估标准、停止条件和人工交接点，更便宜、可靠，适合现阶段落地。

一个可用循环需要六类基础设施：自动触发机制、隔离并行修改的工作树、沉淀项目知识的技能文件、连接 GitHub 等业务工具的插件、创作与审核分离的子代理，以及记录历次尝试和结果的持久化内存。

##### 成本与验证能力决定能否规模化

循环会因重试、验证和多代理协作快速消耗 token。作者估计，中型编码循环可能使用 5万—20万 token，复杂代理集群可达 50万—200万。因此，低价长上下文模型、工具调用、结构化输出和高并发能力，是循环从实验走向日常工作的关键。

核心转变是：提示工程追求一次更好的回答，循环工程追求一个能稳定产出“已验证结果”的系统。可靠的反馈循环，往往比完美提示词更有价值。
