## 结构化（1）

### 2026-07-21 03:35:37

##### 主旨概括

文章通过拆解 Matt Pocock 的 Skills 与工作流，总结出一套 **AI Coding 文档上下文的拆分原则**：不同类型的信息应分别存放，避免上下文混乱，并让 AI 能按“领域建模—方案设计—任务执行—测试审查”的流程稳定开发。

##### 一、项目知识与 AI 上下文应分开管理

1. **项目知识库**
   - 包括架构讨论、项目背景、调研材料等。
   - 建议放在项目代码之外，避免大量背景信息进入 AI 上下文，影响其对当前任务的判断。

2. **`Agents.md`：规则与导航**
   - 主要记录 AI Agent 必须遵守的规则、开发流程和项目规范。
   - 同时提供重要的项目导航，帮助 AI 快速找到相关文件和模块。

3. **`Context.md`：统一术语**
   - 维护术语表（Glossary）和统一语言（Ubiquitous Language）。
   - 明确业务、技术术语的含义，减少人和 AI 对同一概念的理解偏差。

##### 二、架构、设计与决策分别记录

4. **ADR：架构决策记录**
   - ADR 即 Architecture Decision Records。
   - 每项关键架构决策单独使用一个 Markdown 文件记录，防止后续开发破坏既定架构。
   - 例如：明确规定“**A 模块永远不能反向依赖 B 模块**”。

5. **`Architecture.md`：架构文档**
   - 描述系统整体结构、模块关系、依赖方向和架构边界。
   - 与 ADR 的区别是：Architecture 说明当前整体架构，ADR 解释某项架构决策及其约束。

6. **`Design.md`：设计文档**
   - 记录具体功能或系统的设计方案。
   - 重点说明“准备如何实现”，作为架构与实际开发之间的衔接。

##### 三、把方案逐步拆成可执行任务

7. **`Spec`：阶段性实现方案**
   - 使用文件夹管理不同阶段或功能的规格说明。
   - 记录实现方案、范围和边界，明确“做什么”以及“不做什么”。

8. **`Tickets`：按完整能力纵向切分**
   - 每个 Ticket 都应是一个可独立执行、演示和验收的任务。
   - 不应按前端、后端、测试等职能横向拆分，而应围绕一个完整用户功能进行**垂直切片**。
   - 一个 Ticket 可同时覆盖：
     - UI
     - API
     - Runtime
     - Storage
     - Test
     - 验收
   - 如果一个 Ticket 的内容超过 AI 的一个 **Context Window（上下文窗口）**，则应继续拆小。

9. **`Scratch`：本地临时问题管理**
   - 可作为本地 Issues，记录临时问题、想法和待办事项。
   - 如果项目已经使用 GitHub Issues，则优先使用 GitHub Issues，避免重复维护。

##### 四、推荐的 AI Coding 工作流

Matt Pocock 的工作流可概括为：

```text
Grill → Domain Modeling → Spec → Tickets → Implement → TDD → Code Review
```

对应含义如下：

1. **Grill**：通过持续追问澄清需求，找出模糊点和隐含假设。
2. **Domain Modeling**：建立领域模型，统一业务概念及其关系。
3. **Spec**：形成明确的实现规格、范围与边界。
4. **Tickets**：把方案拆成可独立验收的垂直任务。
5. **Implement**：按 Ticket 实现功能。
6. **TDD**：通过测试驱动开发保证行为符合预期。
7. **Code Review**：审查代码质量、架构约束和实现完整性。

##### 五、评论区的补充与争议

- **关于知识库是否应放在项目外**
  - 有评论质疑：如果知识库能随主分支同步更新，就不一定会产生信息不一致；项目背景也有助于 Agent 进行设计。
  - 争议的核心不是 AI 能否读取知识库，而是：**是否应让大量背景材料默认进入每次任务的上下文**。更稳妥的方式是按需检索，而不是全量加载。

- **关于 Skills 与企业知识沉淀**
  - 有观点认为，模型公司的 FDE（前线部署工程师）会先帮助企业落地 Agent、沉淀 Skills，再将这些经验转化为模型能力。
  - 这可能提升企业效率；但如果业务没有同步增长，也可能进一步减少人力需求。

##### 核心结论

这套方法的关键不是“多写文档”，而是让不同文档各司其职：**知识库保存背景，`Agents.md` 管规则，`Context.md` 统一术语，ADR 约束架构，Spec 定义方案，Tickets 驱动执行**。最终目标是让 AI 每次只获得完成当前任务所需的最小、准确且结构化的上下文。

## 通俗精炼（1）

### 2026-09-18 10:57:12

#### AI Coding 文档应分层管理，让 Agent 获得准确、可执行的上下文

文章拆解 Matt Pocock 的 Skills 工作流后提出：不要把所有资料都塞给 AI，而应按用途拆分文档，让规则、术语、架构约束与执行任务各归其位。核心目标是减少无关信息干扰，并把需求转化为 Agent 能独立完成和验收的任务。

##### 不同文档承担不同上下文职责

- **项目知识库**：架构讨论、调研和背景材料等放在项目外，避免污染编码上下文；但评论者也质疑，只要能同步更新，背景知识本身可能有助于设计。
- **Agents.md**：记录协作规则、开发流程和关键项目导航。
- **Context.md**：维护术语表和统一语言，明确领域概念的含义。
- **ADR**：一项架构决策对应一个文件，固化不可轻易破坏的约束，例如“A 模块不能反向依赖 B 模块”。
- **Architecture.md / Design.md**：分别描述整体架构和具体设计。
- **Spec**：保存阶段性实现方案及实现边界。
- **Scratch**：记录本地事项；已有 GitHub Issues 时优先使用后者。

##### Ticket 要按完整能力切分，而非按职能分工

每个 Ticket 都应是可执行的“垂直切片”，围绕一项完整用户能力，覆盖 UI、API、运行时、存储、测试和验收，而不是分别拆成前端、后端任务。它必须能够独立演示和验收；若内容超过一个上下文窗口，还需继续拆分。

##### 工作流从澄清需求走到测试驱动交付

推荐流程是：**Grill（充分追问）→ 领域建模 → Spec → Tickets → 实现 → TDD → Code Review**。其意义在于把长期知识、稳定约束和短期任务分离，使 AI 每次只读取当前决策所需的信息，降低上下文过载与架构逐步劣化的风险。
