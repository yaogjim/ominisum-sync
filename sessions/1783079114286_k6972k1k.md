这条内容的核心不是“哪个模型最强”，而是作者在搭建一套**本地多 Agent 协作体系**。

##### 关键做法

- **Hermes 作为调度中枢**
  - 统一管理不同 Agent。
  - 根据任务类型调用不同模型或工具。

- **GPT 5.5 负责复杂开发**
  - 适合处理复杂逻辑、代码架构、开发任务。

- **DeepSeek V4 Pro 负责文档类任务**
  - 比如会议纪要、说明文档、上下文压缩。

- **DeepSeek 给 GPT 5.5 做上下文压缩**
  - GPT 5.5 单独使用时容易上下文爆掉。
  - 通过压缩历史信息，让 GPT 5.5 保持高效工作。

- **接入 Claude Code**
  - 让 Hermes 可以直接调用 Claude Code。
  - 进一步测试：让 DeepSeek Agent 调 Claude Code 改代码，再和 GPT 5.5 直接改代码对比。

##### 作者最大的变化

过去关心：

> 哪个模型最强？

现在关心：

> 任务怎么拆？  
> 上下文怎么控？  
> 哪个 Agent 调哪个工具最划算？

这说明作者的 AI 使用方式，已经从“单模型崇拜”进入了“多模型协作系统设计”。

#### 深入浅出解读

可以把这套系统理解成一个“小型 AI 公司”。

##### Hermes：项目经理

Hermes 不一定亲自干活，但它负责：

- 判断任务类型；
- 分配给合适的“员工”；
- 协调不同模型之间的配合。

##### GPT 5.5：高级工程师

适合做复杂开发，比如：

- 代码设计；
- 复杂 bug 分析；
- 架构判断；
- 多步骤推理。

但问题是：

> 它很强，但上下文容易撑爆。

也就是聊着聊着，前面的信息太多，模型记不住或处理不动了。

##### DeepSeek：文档秘书 + 信息压缩员

DeepSeek 被用来做两件事：

1. **写文档**
   - 会议纪要；
   - 说明文档；
   - 项目背景整理。

2. **压缩上下文**
   - 把冗长对话、历史材料、项目背景压缩成更短、更清晰的信息；
   - 再交给 GPT 5.5 继续处理。

这相当于给高级工程师配了一个秘书：

> 工程师不需要读完所有原始材料，只需要看秘书整理好的重点。

##### Claude Code：外包程序员

Claude Code 被接入后，就像多了一个专门写代码的外包团队。

作者正在测试：

- GPT 5.5 自己改代码；
- DeepSeek 指挥 Claude Code 改代码；
- 两种方式谁更好、更便宜、更稳定。

#### 本质洞察

这条内容真正有价值的地方在于：

##### AI 使用的重点正在变化

从：

> 单点模型能力

转向：

> 系统协作能力

也就是说，未来用 AI 的高手，不一定是会问“哪个模型最强”的人，而是会设计流程的人。

核心能力包括：

- 会拆任务；
- 会设计上下文；
- 会选择模型；
- 会控制成本；
- 会让不同 Agent 协同；
- 会评估结果质量。

---

#### 辩证思考

##### 好的一面

###### 1. 多模型分工更接近真实工作流

现实公司里，也不会让一个人干所有事。

有人写代码，有人写文档，有人开会，有人做项目管理。

AI Agent 体系也是类似逻辑：

> 让合适的模型做合适的事。

这样效率更高，也更经济。

###### 2. 上下文压缩非常关键

很多 AI 系统失败，不是模型不聪明，而是信息太乱、太长、太散。

上下文压缩相当于“信息治理”。

谁能把复杂信息整理得更清楚，谁就能让模型发挥得更好。

###### 3. 成本意识开始变重要

不是所有任务都需要最贵、最强的模型。

会议纪要、普通文档、信息整理，可以交给便宜模型。

复杂开发、关键判断，再交给强模型。

这是一种更成熟的 AI 使用方式。

---

##### 需要警惕的一面

###### 1. 系统复杂度会上升

模型越多、Agent 越多、工具越多，调度就越复杂。

可能出现：

- 结果不一致；
- 信息丢失；
- 调用链过长；
- 调试困难；
- 出错后难以追责。

最后可能变成：

> 为了提高效率，先搭了一个很复杂的系统，结果维护系统本身又消耗大量精力。

###### 2. 上下文压缩可能损失关键信息

压缩不是无损的。

如果 DeepSeek 在压缩时漏掉关键细节，GPT 5.5 后续判断就可能出错。

所以压缩要有机制，比如：

- 保留原文引用；
- 标注不确定信息；
- 区分事实、判断、待确认事项；
- 关键任务前回查原始材料。

###### 3. Agent 协作不等于自动可靠

多个 AI 协作，听起来很强，但它们都可能犯错。

一个 Agent 的错误，可能被下一个 Agent 放大。

所以仍然需要：

- 人类验收；
- 自动测试；
- 版本控制；
- 日志记录；
- 明确的任务边界。

---

#### 一句话结论

这条内容的重点不是“GPT、DeepSeek、Claude 谁更强”，而是：

> 真正高效的 AI 工作流，正在从“选模型”升级为“设计一套会分工、会压缩上下文、会控制成本的数字员工系统”。

## 通俗精炼（1）

### 2026-09-18 11:02:43

#### 本地 Agent 的重点正从“最强模型”转向“任务编排”

作者搭建了一套由 Hermes 统一调度的本地多 Agent 系统：不同模型承担其擅长的任务，并通过上下文压缩和工具调用协同工作。实践后的核心感受是，模型能力固然重要，但真正影响效率和成本的，已变成任务如何拆分、上下文如何管理，以及不同“数字员工”和外部工具如何组合。

##### 多模型按能力分工

- GPT 5.5 负责复杂开发任务。
- DeepSeek V4 Pro 处理会议纪要、说明文档等文本工作。
- Claude Code 作为代码工具接入 Hermes，可被其他 Agent 直接调用。

作者还在对比两种开发方式：让 DeepSeek Agent 调用 Claude Code 修改代码，或由 GPT 5.5 直接完成，以观察不同组合的实际效果。

##### 上下文压缩缓解长任务瓶颈

单独使用 GPT 5.5 时，上下文很容易超限，导致工作流不顺。作者因此让 DeepSeek 专门为 GPT 5.5 压缩上下文，明显改善了连续处理复杂任务的体验。这说明 Agent 系统的瓶颈不只是模型推理能力，还包括信息筛选、传递和保留。

##### 会议纪要依赖项目背景，而非只做转写摘要

会议流程是先用飞书妙记录音并生成全文，再交给 Agent。生成纪要前，Agent 会先读取整个项目的背景文档，然后结合会议原文输出结果。相比直接总结录音文本，这种做法能让纪要更贴近项目语境。

整体上，这套系统仍处于测试阶段，但已体现出一个趋势：AI 应用的竞争焦点正从单模型排名，转向多模型协作的质量、稳定性与成本效率。
