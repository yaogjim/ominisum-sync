## 正文

**海拉鲁编程客**

最近实践了一些 harness engineering ，我在 AGENTS/CLAUDE.md 加了一个原则章节用于指挥 coding agent

个人觉得蛮好用的， 推荐给大家试试。

\## 原则

1\. 代码仓库是唯一的记录系统：不在 repo 里的知识对智能体不存在。讨论、脑中决策、外部文档——如果影响开发，必须落地为 repo 内的 versioned artifact  
2\. 本文件是地图，不是百科全书：保持 \~100 行，指向 docs/ 深层。每层只暴露本层信息 + 下一步导航  
3\. 把品味编码为规则：优先用 linter、结构测试、CI 检查来强制约束，而非自然语言指令。可机械验证 &gt; 散文指南  
4\. 计划是一等工件：执行计划带进度日志，versioned 并集中存放于 docs/exec-plans/  
5\. 持续垃圾回收：技术债以小额持续偿还，不攒到大规模清理。差距追踪见 docs/exec-plans/tech-debt-tracker.md  
6\. 卡住时修环境，不是更用力：智能体遇到困难时，问"缺什么上下文、工具或约束"，然后补进 repo

在我的实际编码中，这段提示词在大部分情况下的表现都比我不加这段提示词好上不少。包括 opus 4.6，gpt 5.4 以及 @MiniMax\_AI  
，感觉整体干活多了点灵性。

需要补充说明的是，我对超大篇幅的 AGENTS.md 的有效性存疑。所以我尽量追求只加几行就能有不少提升的方案。当然，因为 AGENTS.md 成为了地图，所以，还需要增加一节「深入阅读」做个配合。

## 解读（1）

### 2026-04-13 06:31:40

#### 总结

这篇内容的核心观点是：**想让 coding agent 更稳定、更 “懂项目”，关键不是写很长的提示词，而是把真正影响开发的信息沉淀到仓库里**。作者在`AGENTS/CLAUDE.md`里补了一组简短原则，实践后感觉明显比 “随便给点提示” 更有效。

他提出的 6 条原则，本质上是在强调几件事：

- **repo 是智能体唯一可信的知识来源**
- `AGENTS.md`应该是**导航地图**，不是大而全说明书
- **规则尽量工具化、可验证**
- **计划和进度要落盘、可追踪**
- **技术债要持续小步清理**
- 遇到问题时，优先**补环境、补上下文、补约束**，而不是硬逼模型继续猜

作者也特别强调：**不太相信超长 AGENTS.md 的效果**，更倾向于 “少量高价值原则 + 深入阅读入口” 的方式。

#### 解读

这套方法为什么有效？可以通俗理解为：

##### 1. 别让 AI 靠 “猜”，要让它靠 “看”

如果一个决策只存在于聊天记录、脑子里、会议里，AI 就等于不知道。  
所以作者说 “**代码仓库是唯一记录系统**”，本质是在减少信息丢失和理解偏差。

这很像带新人：

- 如果规则没写下来，新人就只能反复问
- 如果规则写在 repo 里，任何人和任何 agent 都能按同一套标准做事

##### 2. AGENTS.md 不是手册，而是路标

作者反对把`AGENTS.md`写成超长百科全书，这一点很关键。  
因为对 agent 来说，信息太多反而会：

- 抓不到重点
- 增加阅读成本
- 容易忽略真正关键的约束

所以更好的做法是：

- 首页只放原则和导航
- 具体细节放到`docs/`各自对应的位置

也就是：**入口轻，细节深，层次清楚**。

##### 3. “品味” 不要只靠嘴说，要变成机器能检查的规则

“代码要优雅”“风格要统一” 这种话，人懂，AI 未必稳定执行。  
但如果换成：

- linter
- 结构测试
- CI 校验
- 目录约束

那 agent 就不是 “理解你的审美”，而是 “遵守明确规则”。

这背后的思想很实用：  
**能自动检查的，就不要只写成自然语言要求。**

##### 4. 计划要成为正式产物

作者提出 “**计划是一等工件**”，意思是：  
不是临时想一下再做，而是把执行计划、进度、问题记录都存进 repo。

这样做的价值有两个：

- 对人：方便回看决策过程
- 对 agent：方便续做、接力、不跑偏

尤其在多轮协作里，计划文件相当于 “施工日志”。

##### 5. 卡住时先修路，不要硬冲

这一条很像工程思维的精华：  
如果 agent 做不动，不一定是它笨，而可能是：

- 缺文档
- 缺测试
- 缺约束
- 缺样例
- 缺工具

所以正确动作不是反复催它 “再试一次”，而是问：  
**到底缺了什么，才能把这件事做好？**

这比单纯调 prompt 更接近真正的 harness engineering。

#### 我的意见

我觉得这套方法**很值得借鉴，而且方向是对的**。

优点很明显：

- **成本低**：不需要写一大堆复杂提示词
- **可复用**：换模型也基本通用
- **更工程化**：把 “会不会做” 变成 “有没有规则和材料可依赖”

我尤其认同两点：

- **短 AGENTS.md + 深入阅读链接**，比超长说明书更现实
- **把规则写进工具链**，比反复提醒模型更可靠

但也有一个边界要注意：  
如果仓库里的文档本身已经混乱、过期、互相矛盾，那么 “repo 是唯一事实来源” 也会变成负担。  
所以这套方法要发挥效果，前提是：**仓库内容本身要持续维护，不能只新增、不清理。**

一句话说：  
**这不是在 “教 AI 更聪明”，而是在 “把项目整理得更适合 AI 和人一起协作”**。这类方法，通常比堆提示词更长期有效。

## 产品-最佳实践（1）

### 2026-04-13 06:35:19

#### 基于该思路的一个具体实例：为「电商结算服务」设计最小可用 Harness

下面我用一个具体场景，把你提供的 6 条原则落到实处，并给出一套更偏 “可执行” 的最佳实践。

---

##### 场景设定

假设你有一个仓库，项目叫`checkout-service`，负责电商下单、优惠券、支付状态同步。

团队开始引入 coding agent，希望它能参与这些任务：

- 新增一个优惠券叠加规则
- 修复支付回调幂等问题
- 重构结算金额计算模块
- 补测试、补文档、补 CI 规则

此时，问题通常不是模型 “不会写代码”，而是：

- 不知道项目真实约束在哪里
- 不知道哪些文档才是最新的
- 不知道改动应遵循什么工程标准
- 卡住后只会反复试，而不是补齐环境和上下文

所以，Harness 的目标不是 “写一篇很长的 AGENTS.md”，而是把 agent 的行为约束成一套仓库内、可验证、可导航、可持续演进的系统。

---

##### 一个推荐的仓库结构

```text

├─ CLAUDE.md

│  │  ├─ checkout-flow.md

│  ├─ standards/

│  │  ├─ api-contracts.md
│  │  └─ code-style.md
│  ├─ exec-plans/

│  │  └─ tech-debt-tracker.md

│     └─ common-failures.md
├─ src/
├─ tests/
├─ .github/workflows/
│  └─ ci.yml
├─ package.json
└─ README.md
```

##### 最小版`AGENTS.md`示例

重点：它是地图，不是百科全书。

```md
# AGENTS Guide

## Mission
You are working in a production checkout service. Prefer safe, incremental, test-backed changes.

## Principles
1. The repository is the only source of truth.
2. This file is a map, not an encyclopedia.
3. Encode preferences as checks, not prose.
4. Plans are first-class artifacts.
5. Continuously pay down technical debt.
6. When stuck, improve context/tools/constraints first.

## Start Here
- Product flow: `docs/architecture/checkout-flow.md`
- Payment invariants: `docs/architecture/payment-idempotency.md`
- Testing rules: `docs/standards/testing.md`
- API constraints: `docs/standards/api-contracts.md`
- Local setup: `docs/runbooks/local-dev.md`

## Required Workflow
- For non-trivial work, create or update a plan in `docs/exec-plans/`
- Make the smallest safe change
- Add or update tests
- If blocked, document the missing context in repo artifacts
- Update docs if behavior or constraints changed

## Definition of Done
- Tests pass
- Lint/typecheck pass
- Behavior constraints documented
- Plan file updated with progress and decisions
```

这个长度就比较合适：短、硬、可导航。

---

##### 具体任务示例：新增 “优惠券可叠加” 规则

###### 需求

原来系统规定：一个订单只能使用一张优惠券。  
现在新增规则：

- 运费券可以和满减券叠加
- 两张满减券不能叠加
- 同一类券不可叠加
- 结算结果必须可审计

这是一个很适合验证 Harness 是否有效的任务，因为它同时涉及：

- 业务规则
- 金额计算
- 测试覆盖
- 文档更新
- agent 是否会乱猜

---

##### 在这个实例上的最佳实践

##### 1. 把 “口头规则” 落地成 repo 内工件

###### 不推荐

只在 prompt 里告诉 agent：

> “运费券和满减券可以叠加，但别搞错顺序。”

这类信息极易丢失，也不可审计。

###### 最佳实践

把规则写进仓库，例如：

`docs/standards/api-contracts.md`

```md
## Coupon Combination Rules
- At most one shipping coupon may apply.
- At most one discount coupon may apply.
- A shipping coupon and a discount coupon may be combined.
- Two coupons of the same category must be rejected.
- The response must include an itemized discount breakdown.
```

同时，把关键不变量写成测试：

```ts
it ("allows shipping coupon + discount coupon", () => {})
it ("rejects two discount coupons", () => {})
it ("rejects two shipping coupons", () => {})
it ("returns itemized discount breakdown", () => {})
```

###### 为什么这是最佳实践

因为 agent 最可靠的输入，不是聊天记录，而是：

- 仓库里的规范文档
- 失败的测试
- CI 的红线

也就是你提到的：**可机械验证 > 散文指南**。

---

##### 2. 让`AGENTS.md`只负责导航，不负责解释全部背景

###### 不推荐

把优惠券所有历史、边界条件、数据库细节都塞进`AGENTS.md`。

结果通常是：

- 文件越来越长
- agent 读不完
- 人也不愿维护
- 过期信息越来越多

###### 最佳实践

`AGENTS.md`只写：

```md
- Coupon rules: `docs/standards/api-contracts.md`
- Amount calculation: `docs/architecture/checkout-flow.md`
- Current execution plans: `docs/exec-plans/`
```

详细内容分层放在`docs/`里。

###### 为什么这是最佳实践

这相当于给 agent 建了 “认路系统”：

- 顶层文件只提供方向
- 深层文档承载细节
- 每一层只暴露 “当前层必要信息 + 下一步导航”

这样更符合 agent 的检索式工作方式。

---

##### 3. 把 “品味” 翻译成 lint、测试和 CI 规则

你文中最有价值的一点之一，就是：**别把品味只写成自然语言**。

###### 在这个实例中，可以这样做

###### 3.1 用结构化测试固化结算规则

```ts
describe ("coupon stacking", () => {
  it ("applies shipping coupon before final payable amount is returned", () => {})
  it ("produces deterministic discount breakdown", () => {})
  it ("rejects invalid same-category stacking", () => {})
})
```

###### 3.2 用 schema 或 contract test 限制 API 输出

比如要求返回：

```json
{
  "subtotal": 10000,
  "discounts": [
    { "type": "shipping_coupon", "amount": 800 },
    { "type": "discount_coupon", "amount": 1500 }
  ],
  "total": 7700
}
```

这样 agent 不能只 “算对结果”，还得 “按契约输出”。

###### 3.3 在 CI 中强制执行

```yaml
- run: npm run lint
- run: npm run test
- run: npm run typecheck
- run: npm run test:contracts
```

###### 为什么这是最佳实践

因为 “代码要清晰”“结构要好” 这种要求太模糊，agent 往往会自作解释。  
而测试、类型、契约、CI 会把模糊偏好变成确定约束。

---

##### 4. 非平凡任务必须先建执行计划

这是很多团队容易忽略但非常有效的一点。

###### 在这个实例里，建议先创建：

`docs/exec-plans/2025-02-14-coupon-stacking.md`

```md
# Coupon Stacking Support

## Goal
Allow one shipping coupon and one discount coupon to be combined safely.

## Constraints
- No same-category stacking
- Must preserve idempotent checkout result
- Must return discount breakdown

## Steps
1. Document combination rules in API contracts
2. Add failing tests for allowed and rejected combinations
3. Refactor pricing engine to support typed coupon slots
4. Add response breakdown fields
5. Update local docs and examples

## Progress Log
- [x] Added contract rules
- [x] Added failing tests
- [ ] Refactor pricing engine
- [ ] Update API examples

## Decisions
- Use category-based validation instead of pairwise rule table for v1
```

###### 为什么这是最佳实践

因为 plan 文件会显著提升 agent 的稳定性：

- 减少它一次性大改
- 让它知道当前阶段目标
- 让决策可回溯
- 方便中断后恢复上下文

尤其是多轮协作时，这比 “聊天记录回放” 可靠得多。

---

##### 5. 技术债不要等 “统一治理”，而要借任务顺手偿还

这个原则在 agent 参与开发时特别重要。

###### 在这个实例中，常见技术债可能是：

- 金额计算逻辑散落在多个文件
- 优惠券类型用字符串硬编码
- 返回结构没有统一 schema
- 历史测试只测 happy path

###### 最佳实践

在本次任务中顺手做 “小额偿还”：

- 把`coupon.type ==="shipping"`这类魔法字符串收敛成枚举
- 把金额计算抽成纯函数，方便测试
- 增加一组表驱动测试
- 在`docs/exec-plans/tech-debt-tracker.md`记录尚未处理的更大问题

例如：

```md
## Pricing Engine Debt
- [ ] Split tax and coupon calculation into separate modules
- [ ] Introduce Money value object to avoid raw integer misuse
- [ ] Add snapshot fixture tests for complex order scenarios
```

###### 为什么这是最佳实践

因为 agent 很容易在一次任务中：

- 要么只完成表面需求
- 要么过度重构

“小额持续偿还” 是最稳的平衡点。

---

##### 6. Agent 卡住时，优先补环境，而不是反复换说法

这是非常实战的一条。

###### 这个实例里，agent 可能卡住在：

- 不知道金额计算顺序
- 不知道支付幂等约束是否影响优惠券叠加
- 本地跑不起来测试
- 不知道哪个接口才是线上真实入口

###### 不推荐

继续追加 prompt：

> “你再仔细想想”
> “你应该能理解的”
> “按常识处理”

这类做法对 agent 基本没帮助。

###### 最佳实践

把缺失的上下文补进仓库：

- 新增`docs/architecture/checkout-flow.md`
- 新增`docs/runbooks/common-failures.md`
- 在`README.md`写清最小启动步骤
- 给测试夹具增加典型订单样例
- 在计划文件里记录 blocker

例如：

```md
## Blockers
- Missing documentation for discount application order
- No fixture covering shipping + discount coupon combination
```

然后补齐这些内容，而不是继续 “更用力 prompting”。

###### 为什么这是最佳实践

因为 agent 的失败，很多时候不是推理不够，而是输入环境不完整。

---

##### 一套更完整的落地模板

如果要把你的这套方法真正推广到团队里，我建议在原有 6 条原则上，再补 4 条操作层面的最佳实践。

###### 1. 为每类任务定义 “入口文档”

例如：

- 功能开发：先看`docs/architecture/`和`docs/standards/`
- Bug 修复：先看`docs/runbooks/common-failures.md`
- 重构：先看`docs/exec-plans/tech-debt-tracker.md`

这样 agent 不需要每次都从零搜索。

###### 2. 为 agent 提供 “最小成功路径”

比如在`docs/runbooks/local-dev.md`里明确写：

```md
## Minimum Dev Loop
1. `npm install`
2. `npm test -- pricing`
3. `npm run lint`
```

比起写一整套长篇环境说明，最小成功路径更关键。

###### 3. 用示例驱动，而不是抽象说教

在文档里直接放一个真实请求 / 响应例子、一个失败测试例子、一个合法叠加例子，效果通常比十段原则说明更强。

###### 4. 要求 agent 更新文档，而不是只改代码

如果本次优惠券规则变了，DoD 不应只是 “测试通过”，还应包括：

- 规则文档更新
- 示例响应更新
- plan 文件打勾
- 如有新增边界，tech debt tracker 记录后续项

---

##### 一份可直接借鉴的 “最佳实践清单”

你这套 Harness 思路，如果要压缩成团队可执行版本，我会建议这样表述：

```md
## Harness Best Practices

1. Put every development-relevant decision inside the repo.
2. Keep AGENTS.md short and navigational.
3. Turn preferences into tests, lint rules, schemas, and CI checks.
4. Require a versioned execution plan for non-trivial tasks.
5. Pay down technical debt in small increments during normal work.
6. When blocked, add missing context/tools/constraints to the repo.
7. Prefer concrete examples over abstract instructions.
8. Define a clear Definition of Done for agents.
9. Make important invariants discoverable within 1-2 hops from AGENTS.md.
10. Optimize for recoverability: another agent should resume work from repo artifacts alone.
```

---

##### 这套方法为什么有效

用一句话概括：

**它不是在 “教模型更聪明”，而是在 “把协作环境变得更适合模型稳定发挥”。**

也就是说，你的方案之所以有效，不一定是 prompt 本身神奇，而是它引导团队做了这些真正有价值的事：

- 把隐性知识显性化
- 把经验约束程序化
- 把任务过程产物化
- 把失败原因环境化

这才是 Harness engineering 最核心的价值。

如果你已经有了 “原则” 章节，下一步最值得加的，不是继续加更多原则，而是补两个配套机制：

###### 深入阅读
让 agent 在 1~2 跳内找到：
- 架构说明
- 测试规范
- runbook
- 当前执行计划

###### 完成定义
明确要求每次非平凡改动至少满足：
- 有计划
- 有测试
- 有文档更新
- 有 CI 校验
- 有 blocker 记录

这样你的`AGENTS.md`就不只是 “价值观声明”，而会真正变成 agent 的工作操作系统。

## 趣读产品（1）

### 2026-04-13 06:37:16

#### 对你真正有用的点：把 “提示词技巧” 升级成 “组织操作系统”

这段内容最有价值的地方，在于它透露了一个很现实的趋势：

> 真正拉开 AI coding agent 效果差距的，已经不只是模型能力，更多是你怎么给它搭舞台。

模型像一个很聪明的新员工。  
`AGENTS.md/ CLAUDE.md/docs/ / CI /plan`这套东西，才是工位、流程、门禁卡、SOP 和绩效考核。

谁把这些搭得清楚，谁就能把 “偶尔惊艳” 变成 “稳定产出”。

---

##### 这篇内容的核心洞察

###### 1. repo 正在变成 AI 团队的 “脑外硬盘”
作者那句 “代码仓库是唯一的记录系统”，含金量很高。

对 agent 来说，没写进 repo 的信息，几乎等于没发生过。  
会议纪要在飞书、决策在脑子里、规范在口头里，最后都会变成 agent 的 “隐形墙”。

对你做 AI 产品也一样：

- 如果关键知识没有沉淀进系统，AI 永远只能靠猜
- 猜得再像，也很难稳定复现
- 产品一旦进入多人协作、长周期迭代，隐性知识会迅速变成效率黑洞

一句话：  
**AI 时代，文档不是为了人看得舒服，首先是为了机器执行得准确。**

---

###### 2. 好 harness 的目标不是 “写更多说明”，是 “减少误解空间”
作者怀疑超长`AGENTS.md`的有效性，这个判断很成熟。

因为 agent 不怕信息少，怕信息乱。  
一份 800 行的总说明，往往像把新员工扔进一个堆满 PDF 的档案室。

“地图，不是百科全书” 这个原则很适合创业团队：

- 顶层文件只讲方向、约束、入口
- 细节按主题下沉到`docs/`
- 每一层只回答当前最需要知道的事

这其实是在控制认知负荷。  
对人有效，对 agent 更有效。

你可以把它理解成：  
**给 AI 的上下文，应该像产品导航，不该像维基百科。**

---

###### 3. “把品味编码为规则” 是最值得抄的一条
这条最像创业中的 “降本增效真经”。

因为自然语言里的 “写优雅一点”“保持一致性”“代码简洁” 都很虚。  
agent 会点头，会输出，会偏掉。

一旦变成：

- linter
- type check
- contract test
- snapshot
- CI gate
- directory conventions
- PR template

事情就清楚了。  
规则一旦可验证，agent 的发挥空间会收敛，交付质量会明显稳定。

这对 AI 产品创业者的启发非常直接：

###### 能不能把 “人的判断” 翻译成 “机器可检查的约束”，决定了你的组织杠杆有多大。

很多团队卡在这里：  
创始人有品味，团队知道一点，AI 完全不知道。  
结果创始人成了系统里唯一的 “编译器”。

这不可扩展。

---

###### 4. 计划是一等工件，本质是在训练 agent 形成 “工作记忆”
“执行计划带进度日志，versioned 并集中存放” 这一条，表面看像项目管理，实际上是在解决 agent 的短板：**上下文易丢失、行动缺乏连续性**。

你可以把`docs/exec-plans/`理解成 agent 的外置工作记忆区。

它的作用有三个：

- 让任务从 “单轮对话” 升级成 “可持续执行”
- 让下一次接手的 agent 快速进入状态
- 让人能看懂 agent 之前想了什么、做了什么、卡在哪里

这很像给 AI 配了一块白板。  
没有白板，聪明人也会转身就忘。

---

###### 5. “卡住时修环境” 是很强的产品思维
这条非常像优秀产品团队做增长时的思路：

当用户总犯同一个错，先别骂用户，先改界面。  
当 agent 总卡在同一个坑，先别重复催它，先补上下文、工具、约束。

这是一种很工程化的思考方式：

- 出错不可怕
- 重复出错却没有把问题产品化，才可怕

对你做 AI 产品尤其重要。  
因为今天你在给 coding agent 设计 harness，明天你就在给业务 agent 设计环境。

本质是一回事：  
**别把失败归因给模型智商，先看系统有没有把路铺平。**

---

##### 对你的参考意义：这背后其实是一个产品机会

这篇内容看上去在聊 coding agent，实际上已经碰到了一个更大的方向：

##### 未来很多 AI 产品的竞争力，会来自 “环境设计能力”，不是聊天框体验。

用户买的不是一个更会说话的模型。  
用户买的是：

- 这个 agent 进场后，多久能开始干活
- 它会不会反复犯同样的错
- 它能不能继承团队经验
- 它能不能在多人协作里稳定输出
- 它出了问题，能不能追责和修复

所以你如果做 AI 产品、AI workflow、AI agent 平台，这篇文章给你的信号很清楚：

###### 下一阶段的产品壁垒，正在从 “模型接入能力” 转向 “可执行上下文基础设施”。

也就是：

- 记忆如何落盘
- 规则如何显式化
- 计划如何持续化
- 反馈如何回写系统
- 经验如何版本化

这些东西一旦做成产品能力，价值会比 “再包一层 prompt” 高很多。

##### 你可以直接拿去用的 3 个动作

###### 1. 给你的项目加一份 “100 行以内的顶层地图”
建议结构：

```md
# AGENTS.md

## 项目目标
这个仓库解决什么问题，当前阶段重点是什么

## 工作原则
3-6 条硬规则：允许什么，禁止什么，优先什么

## 代码与文档入口
核心目录说明 + 深入阅读链接

## 执行要求
计划放哪、日志放哪、交付前检查什么

## 深入阅读
docs/architecture.md
docs/product-decisions.md
docs/exec-plans/
```

关键点：

- 控制在短篇幅
- 只保留高价值约束
- 每条都能影响执行行为

---

###### 2. 把创始人品味改造成 “检查项”
如果你发现自己常说这些话：

- 这里写得不一致
- 结构不对
- 命名太飘
- 测试覆盖关键路径了吗
- 这个方案不符合我们产品哲学

那就说明这些判断该落地了。

你可以优先做这几类：

- 命名规范
- 文件组织规则
- 测试最低要求
- PR 模板
- 发布前 checklist
- CI fail 条件

目标很简单：  
**让 agent 尽量少猜，让系统尽量多裁判。**

---

###### 3. 建一个`exec-plans`目录，观察 agent 是否开始 “像人一样连续工作”
目录示例：

```text
docs/
  exec-plans/
    2025-02-onboarding-redesign.md
    2025-02-billing-bugfix.md
    tech-debt-tracker.md
```

每份 plan 只要有这几个块就够了：

- 背景
- 目标
- 假设
- 步骤
- 当前进度
- 卡点
- 结论 / 后续

你会很快发现：  
很多原本需要你反复盯的任务，突然变得可追踪、可接力、可复盘。

##### 一个很值得你注意的信号

评论区里有人说：“深入阅读 claude 会不读，在你指出他没读的时候再和你道歉。”

这句吐槽其实非常真实。  
它提醒了一个重要事实：

###### harness 不是写给 “理想中的智能体” 的，是写给 “现实里会漏看、会偷懒、会误读” 的智能体的。

所以设计时别假设 agent 会自觉、完整、认真阅读所有材料。  
更好的做法是：

- 关键规则前置
- 长文拆层
- 用链接导航
- 用工具强约束
- 用计划文件承接上下文
- 用 CI 做最后守门

这才是对现实负责的设计。

---

##### 最后一句判断

这篇文章表面上是在分享一个小技巧，实际上传达的是一个更大的方法论：

###### 你不是在 “优化提示词”，你是在给 AI 员工搭建工作制度。

一旦你用这个视角看问题，很多动作会变得非常清晰：

- 哪些知识必须写进 repo
- 哪些判断必须做成规则
- 哪些任务必须留下计划和进度
- 哪些重复错误说明环境该升级了

这套东西，短期提升 agent 产出质量，长期会沉淀成你的组织资产。
