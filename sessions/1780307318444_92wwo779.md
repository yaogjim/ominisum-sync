#### pi-codex-goal

Codex-style goal tracking for pi.

This package adds a `/goal` command plus three model-callable tools:

- `get_goal`
- `create_goal`
- `update_goal`

Goal state is stored in pi session custom entries, so it follows session history, resume, fork, tree navigation, reload, and compaction behavior without an external database.

`/goal` is an interactive editor command. Do not use `pi -p '/goal ...'` as a slash-command smoke path; print mode sends an initial model prompt and is not a reliable way to exercise this extension command. For headless automation, prompt the model to call the `create_goal`, `get_goal`, and `update_goal` tools instead of relying on slash-command parsing.

#### User Commands

```
/create-goal Build the requested feature and verify it end to end
/goal
/goal Build the requested feature and verify it end to end
/goal pause
/goal resume
/goal clear
```

`/create-goal <task>` is the recommended way to start a goal. It expands the task into a strict objective and asks the model to call the `create_goal` tool.

`/goal` with no arguments reports the current objective, status, token budget, token usage, and elapsed active time. A plain `/goal <objective>` starts a new goal or replaces the current one after confirmation.

This intentionally matches Codex TUI behavior: token budgets are set through the model tool rather than parsed from `/goal --tokens`. This package keeps its objective size limit at 8000 Unicode characters.

#### Model Tools

`create_goal` starts a goal with an objective and optional positive token budget. It fails if a non-complete goal already exists. After a goal is complete, `create_goal` replaces it with a new active goal.

`get_goal` returns the current goal state and usage.

`update_goal` only accepts `status: "complete"`, matching Codex's model-side contract. Calling it on an already-complete goal is idempotent and does not append duplicate session entries. The extension reports final token and elapsed-time usage before marking the goal complete.

Completed goals are terminal for automatic transitions: pause, resume, and hidden continuations do not reopen them. To recover from premature completion, use `/goal <objective>` to replace the goal or `/goal clear` before starting again.

In bridged MCP environments such as `pi-cursor-sdk`, pi may expose these tools under namespaced MCP names like `pi__get_goal`, `pi__create_goal`, and `pi__update_goal`. Prompt guidance tells models to call whichever goal-tool name is actually exposed in the current run, not display or transcript labels.

#### Behavior

While a goal is active, the extension:

- tracks elapsed active time between turns and tool completions
- adds completed assistant turn input plus output token usage when the active model reports it
- coalesces runtime goal custom-entry writes so unchanged status and usage are not appended on every tool completion; live footer usage stays current, and meaningful usage is flushed at turn boundaries, shutdown, compaction, budget crossings, and bounded intervals during long tool-heavy runs
- pauses when an active assistant turn is aborted, such as when you press Esc
- recovers from provider assistant errors without immediate hidden continuation loops: context-window overflow triggers automatic compaction and then resumes the active goal, transient errors use bounded backoff retries, and repeated unrecoverable failures pause with a clear `/goal resume` path
- prompts on session resume before reactivating a paused goal, and resumes explicitly with `/goal resume` (only from paused)
- rejects `/goal pause` unless the goal is active and `/goal resume` unless the goal is paused
- treats completed goals as terminal for automatic transitions while allowing `/goal <objective>` to replace them without extra friction
- marks the goal `budgetLimited` when a positive token budget is reached
- sends hidden steering messages when budget is reached or when the agent is idle but the goal is still active
- compacts repeated hidden goal continuations before provider context so only the latest active continuation stays runnable, older ones become short bookkeeping markers, and auto-queued continuations use a compact prompt after `/goal` start or resume
- shows Codex-style status labels with compact token or elapsed-time usage in the pi footer when UI is available

Token counts are formatted with commas and compact abbreviations, for example `123M (123,456,789) tokens`. Token totals use pi's completed assistant turn input plus output usage. Cache read and cache write channels are excluded because they are provider cache accounting fields, not extra sent and received text tokens. Pi does not currently expose a separate extension usage total for automatic compaction summary calls.

##### 一、总结

**pi-codex-goal** 是一个给 **pi** 增加“目标追踪”能力的插件，功能类似 Codex 的 Goals。

它主要提供：

- 一个命令：`/goal`
- 三个模型可调用工具：
  - `create_goal`：创建目标
  - `get_goal`：查看目标
  - `update_goal`：标记目标完成

```bash
/create-goal <任务描述>
```

而不是手写 `/goal`，因为模型会自动把普通任务扩展成更完整的执行目标、验收标准和约束。

这个项目解决的问题是：

> 让 AI 在长任务中不忘记自己要干什么，并且能持续推进直到完成。

5. **只有验证后才能标记完成**

##### 8. 模型工具行为

###### `create_goal`

- 用 objective 创建一个目标。
- 可选设置正数 token budget。
- 如果已有未完成目标，则创建失败。
- 如果当前目标已完成，则可以用新目标替换。

###### `get_goal`

- 返回当前目标状态和使用情况。

###### `update_goal`

- 只接受：

```json
{
  "status": "complete"
}
```

- 如果目标已经完成，再次调用是幂等的，不会重复追加 session entries。
- 在标记完成前，扩展会报告最终 token 和耗时用量。

###### 已完成目标的规则

- 完成后的目标是终态。
- pause、resume、hidden continuation 不会重新打开已完成目标。
- 如果误标完成，可以：

  - 用 `/goal &lt;objective>` 替换目标
  - 或先 `/goal clear`，再重新创建

##### 10. 运行时行为

当目标处于 active 状态时，该扩展会自动处理多种情况。

###### 时间与 token 跟踪

- 跟踪 assistant turn 和 tool completion 之间的活跃耗时。
- 统计已完成 assistant turn 的输入 token 和输出 token。
- 只在状态或用量有意义变化时写入 session，避免每次工具完成都重复追加。
- 会在以下时机刷新用量：

  - turn 边界
  - shutdown
  - compaction
  - token budget 达到阈值
  - 长时间大量工具调用期间的有界间隔

###### 暂停与恢复

- 如果用户中断 active assistant turn，例如按下 Esc，目标会暂停。
- session resume 时，会提示用户是否重新激活 paused goal。
- 只有显式执行 `/goal resume` 才会从 paused 恢复。

###### 错误处理

- 遇到 provider assistant 错误时，不会立刻陷入 hidden continuation 循环。
- 如果是 context-window overflow，会自动 compaction，然后恢复 active goal。
- 如果是短暂错误，会进行有限 backoff 重试。
- 如果多次不可恢复失败，会暂停目标，并提示可用 `/goal resume` 继续。

###### 预算限制

- 当正数 token budget 被达到时，目标会标记为 `budgetLimited`。
- 达到预算或 agent 空闲但目标仍 active 时，会发送隐藏 steering messages。

###### 隐藏 continuation 压缩

- 重复的隐藏 goal continuation 会被压缩。
- provider context 中只保留最新可运行的 active continuation。
- 较旧 continuation 会变成简短 bookkeeping markers。
- 自动排队的 continuation 会使用紧凑提示词。

###### UI 显示

- 在有 UI 的情况下，pi footer 会显示类似 Codex 的状态标签。
- 会显示紧凑 token 或耗时用量。

---

##### 11. Token 统计规则

- token 数量会使用逗号和紧凑缩写格式，例如：

```text
123M (123,456,789) tokens
```

- token 总量使用 pi 报告的已完成 assistant turn 输入和输出用量。
- 不计入 cache read 和 cache write，因为它们是 provider 缓存记账字段，不代表额外发送或接收的文本 token。
- pi 当前不暴露自动 compaction summary calls 的独立扩展用量总计。

##### 1. 一句话判断

> 最值得保留的是：**把“目标”设计成会随会话历史流动的状态对象，而不是一次性提示词，从而让 AI Agent 获得可恢复、可验证、可续跑的任务执行能力。**

价值评级：**A**

精炼理由：这不是一个普通插件说明，而是暴露了 Agent 产品设计中的关键原则：**目标管理不是 UI 功能，而是状态机、验证契约和恢复机制。**

---

##### 2. 最重要的洞见

###### 洞见 1：目标不应只是 Prompt，而应是“可持久化的执行状态”

###### **核心观点：**  
> goal state 被存储在 pi session custom entries 中，因此它会跟随 session history、resume、fork、tree navigation、reload、compaction，而不需要外部数据库。

**为什么重要：**  
多数人把目标理解成“用户说过的一句话”。但对 Agent 来说，目标必须成为系统状态的一部分，否则一旦中断、压缩上下文、分叉会话或恢复历史，任务连续性就会断裂。

**反常识之处：**  
常见做法是引入外部数据库保存任务状态；这里反而选择嵌入会话历史。  
原因是：Agent 的真实工作轨迹本来就在会话树里，目标状态如果脱离会话，反而会制造一致性问题。

**可迁移价值：**  
设计 AI 产品时，不要只问“数据存哪里”，而要问：  
> 这个状态应该跟随什么生命周期？

如果状态本质上属于一次会话，就应绑定会话；如果属于用户长期资产，才应外置。

**我应该记住什么：**  
> Agent 的目标状态，最好和执行轨迹同生同灭。

---

###### 洞见 2：人类不一定擅长写目标，Agent 反而更适合生成“完成契约”

###### **核心观点：**  
> 作者建议使用 `/create-goal` 模板，而不是手写 goal，因为 Agents can write better goal completion contracts than humans do。

**为什么重要：**  
高质量目标不是一句“帮我做 X”，而应包含：

- outcome：要达成什么结果  
- verification：如何验证  
- constraints：约束条件  
- iteration：失败后如何迭代  
- audit：如何审计  
- blocked-stop：何时停止并说明阻塞  

这其实是在把模糊任务转成“可执行合同”。

**反常识之处：**  
通常认为人类更清楚自己想要什么，所以目标应由人类写。  
但在工程执行层面，人类往往只会描述愿望，Agent 更擅长补齐执行标准。

**可迁移价值：**  
在任何复杂协作中，都可以让系统先把需求扩展成“完成契约”，再开始执行。  
适用于：

- 产品需求  
- 外包任务  
- 自动化测试  
- AI 编程  
- 项目管理  
- 个人计划  

**我应该记住什么：**  
> 好目标不是愿望，而是带验证条件的合同。

---

###### 洞见 3：Agent 的可靠性来自“状态机约束”，不是来自模型自觉

###### **核心观点：**  
> create_goal、get_goal、update_goal 被设计成受限工具；update_goal 只接受 `complete`，完成后的 goal 是 terminal，pause/resume/hidden continuation 都不能重新打开。

**为什么重要：**  
作者没有把可靠性交给模型“自觉遵守”，而是通过工具协议限制模型行为：

- 未完成目标存在时，不能创建新目标  
- 完成状态是终态  
- 重复 complete 是幂等的  
- pause/resume 只能在合法状态间转换  
- 过早完成后必须显式 replace 或 clear  

这让 Agent 更像一个可控流程系统，而不是自由发挥的聊天模型。

**反常识之处：**  
很多 AI 产品试图通过更强提示词提高可靠性。  
这里的判断是：  
> 真正的可靠性来自状态约束，而不是语言约束。

**可迁移价值：**  
凡是涉及 AI 自动执行的系统，都应优先设计：

- 状态枚举  
- 合法转移  
- 幂等操作  
- 终态保护  
- 恢复路径  
- 错误边界  

**我应该记住什么：**  
> 不要劝模型守规矩，要让它没法乱来。

---

###### 洞见 4：长任务 Agent 的核心难点不是启动，而是“中断后的正确继续”

###### **核心观点：**  
> 插件处理了 abort、provider error、context overflow、automatic compaction、hidden continuation、budget limit、resume prompt 等连续性问题。

**为什么重要：**  
AI Agent 执行长任务时，真正困难的不是开始任务，而是各种异常后的延续：

- 用户按 Esc 中断  
- 模型服务报错  
- 上下文窗口溢出  
- 会话被压缩  
- 工具调用时间过长  
- token 预算耗尽  
- 旧 continuation 堆积  

作者把这些都纳入 goal 生命周期，而不是当成边缘情况。

**反常识之处：**  
常见 Agent demo 展示的是“一口气完成任务”。  
真实系统要优化的是：  
> 没有一口气完成时，如何不失控、不重复、不遗忘、不误续。

**可迁移价值：**  
任何自动化系统都要把“失败后继续”设计成一等公民。  
尤其适用于：

- AI 编程助手  
- RPA  
- 数据管道  
- 长流程审批  
- 自动测试  
- 多步骤运营任务  

**我应该记住什么：**  
> Agent 产品的成熟度，取决于异常恢复，而不是首次成功率。

##### 3. 底层逻辑

###### **逻辑一：目标连续性 = 状态绑定执行轨迹**

- 表层现象：插件把 goal 存在 session custom entries，而不是外部数据库。
- 深层原因：Agent 的上下文、分叉、恢复、压缩都发生在会话系统内；目标若不随会话流动，就会和执行历史脱节。
- 推导结论：需要随历史演化的状态，应嵌入历史系统，而不是独立存储。

---

###### **逻辑二：目标可靠性 = 明确契约 + 状态机约束**

- 表层现象：`create_goal`、`get_goal`、`update_goal` 被严格限制，完成状态不可自动重开。
- 深层原因：模型天然倾向于语言性承诺，但执行系统需要可验证、可恢复、可审计的状态。
- 推导结论：AI 系统不能只靠提示词约束行为，必须用工具协议和状态转移限制行为空间。

---

###### **逻辑三：长任务能力 = 压缩、续跑、错误恢复的组合**

- 表层现象：插件支持 hidden continuation、compaction、budget crossing、bounded backoff、resume prompt。
- 深层原因：长任务一定会遇到上下文、预算、错误和中断问题。
- 推导结论：Agent 的核心基础设施不是“更聪明的模型”，而是“不会断线的执行框架”。
