#### Open Agents

Open Agents 是一个在 Vercel 上构建和运行后台编码代理的开源参考应用。它包含 Web 用户界面、代理运行时、沙箱编排，以及从提示到代码变更所需的 GitHub 集成，无需使用你的笔记本电脑。

这个代码库旨在被分叉和调整，而不是被视为黑箱。

#### What it is

Open Agents 是一个三层系统：

```
Web -> Agent workflow -> Sandbox VM
```

- 该 Web 应用处理认证、会话、聊天和流式用户界面。
- 代理以持久化工作流的形式在 Vercel 上运行。
- 沙箱是执行环境：文件系统、Shell、Git、开发服务器和预览端口。

###### 关键架构决策：代理不是沙箱

The agent does not run inside the VM. It runs outside the sandbox and interacts with it through tools like file reads, edits, search, and shell commands.  
代理不会在虚拟机内运行。它在沙箱外部运行，并通过文件读取、编辑、搜索和 shell 命令等工具与沙箱进行交互。

这种分离是该项目的主要点：

- 代理执行不与单一请求生命周期绑定
- 沙箱生命周期可以独立地休眠和恢复
- 模型/提供商选择和沙箱实现可以独立演进
- 虚拟机仍然是一个简单的执行环境，而不是成为控制平面

#### Current capabilities

- 基于聊天的编码代理，具备文件、搜索、Shell、任务、技能和网页工具
- 由工作流 SDK 支持的持久多步骤执行
- 隔离的 Vercel 沙箱，带有基于快照的恢复
- 沙箱内的仓库克隆和分支工作
- 可选的自动提交、推送以及在成功运行后创建拉取请求
- 会话共享通过只读链接
- 可选的语音输入，通过 ElevenLabs 转录

#### Runtime notes

一些对理解当前实现很重要的细节：

- 聊天请求启动一个工作流运行，而不是内联执行代理。
- 每次代理轮次可以继续跨越多个持久化的工作流步骤。
- 对于现有工作流，活跃的运行实例可通过重新连接到流来恢复。
- Sandboxes use a base snapshot, expose ports `3000`, `5173`, `4321`, and `8000`, and hibernate after inactivity.  
  沙箱使用基础快照，暴露端口 `3000` 、 `5173` 、 `4321` 和 `8000` ，并在闲置后休眠。
- 自动提交和自动 PR 得到支持，但它们是偏好驱动的功能，不是始终开启的行为。

#### 今天实际需要的是什么

这些要求基于当前的 `apps/web` 代码路径，而非旧的设置脚本。

###### Minimum runtime

这些是应用程序启动并加载服务器状态的硬性要求：

```
POSTGRES_URL=
JWE_SECRET=
```

###### 需要登录才能实际使用托管应用

一个有用的部署还需要令牌加密加上 Vercel OAuth 登录：

```
ENCRYPTION_KEY=
NEXT_PUBLIC_VERCEL_APP_CLIENT_ID=
VERCEL_APP_CLIENT_SECRET=
```

没有这些，网站可以部署，但 Vercel 登录将无法使用。

###### 是 GitHub 仓库访问、推送和拉取请求所必需的

如果你希望用户连接 GitHub、在仓库/组织上安装应用、克隆私有仓库、推送分支或打开拉取请求，请添加这些 GitHub 应用的值：

```
NEXT_PUBLIC_GITHUB_CLIENT_ID=
GITHUB_CLIENT_SECRET=
GITHUB_APP_ID=
GITHUB_APP_PRIVATE_KEY=
NEXT_PUBLIC_GITHUB_APP_SLUG=
GITHUB_WEBHOOK_SECRET=
```

###### Optional

```
REDIS_URL=
KV_URL=
VERCEL_PROJECT_PRODUCTION_URL=
NEXT_PUBLIC_VERCEL_PROJECT_PRODUCTION_URL=
VERCEL_SANDBOX_BASE_SNAPSHOT_ID=
ELEVENLABS_API_KEY=
```

- `REDIS_URL` / `KV_URL` ：可恢复流、停止信号以及基于 Redis 的缓存。
- `VERCEL_PROJECT_PRODUCTION_URL` / `NEXT_PUBLIC_VERCEL_PROJECT_PRODUCTION_URL`: canonical production URL for metadata and some callback behavior.  
  `VERCEL_PROJECT_PRODUCTION_URL` / `NEXT_PUBLIC_VERCEL_PROJECT_PRODUCTION_URL` ：用于元数据和某些回调行为的规范生产环境 URL。
- `VERCEL_SANDBOX_BASE_SNAPSHOT_ID`: 覆盖默认沙箱快照。
- `ELEVENLABS_API_KEY` ：语音转录。

#### 在 Vercel 上部署你自己的副本

推荐路径：在 Vercel 的仓库根目录部署此仓库，然后叠加身份验证和 GitHub 集成。

1. Fork this repo.
2. 创建一个 PostgreSQL 数据库并复制它的连接字符串。
3. Generate these secrets:
   ```bash
   openssl rand -base64 32 | tr '+/' '-_' | tr -d '=\n'   # JWE_SECRET
   openssl rand -hex 32                                    # ENCRYPTION_KEY
   ```
4. Import the repo into Vercel.
5. 在 Vercel 项目设置中至少添加这些环境变量：
   ```bash
   POSTGRES_URL=
   JWE_SECRET=
   ENCRYPTION_KEY=
   ```
6. 部署一次以获取稳定的生产 URL。
7. 创建一个 Vercel OAuth 应用，回调 URL 为：
   ```bash
   https://YOUR_DOMAIN/api/auth/vercel/callback
   ```
8. 添加这些环境变量并重新部署:
   ```bash
   NEXT_PUBLIC_VERCEL_APP_CLIENT_ID=
   VERCEL_APP_CLIENT_SECRET=
   ```
9. If you want the full GitHub-enabled coding-agent flow, create a GitHub App using:  
   如果你想要完整的支持 GitHub 的编码代理流程，请创建一个 GitHub 应用，使用：
   - 首页网址: `https://YOUR_DOMAIN`
   - Callback URL: `https://YOUR_DOMAIN/api/github/app/callback`  
     回调 URL: `https://YOUR_DOMAIN/api/github/app/callback`
   - Setup URL: `https://YOUR_DOMAIN/api/github/app/callback`  
     设置 URL: `https://YOUR_DOMAIN/api/github/app/callback`
   In the GitHub App settings:
   - 启用 "在安装期间请求用户授权(OAuth)"
   - use the GitHub App's Client ID and Client Secret for `NEXT_PUBLIC_GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET`  
     使用 GitHub App 的客户端 ID 和客户端密钥分别作为 `NEXT_PUBLIC_GITHUB_CLIENT_ID` 和 `GITHUB_CLIENT_SECRET`
   - make the app public if you want org installs to work cleanly  
     如果希望组织安装正常工作，请将应用设为公开
10. 添加 GitHub App 的环境变量并重新部署
11. Optionally add Redis/KV and the canonical production URL vars.  
    可选添加 Redis/KV 和规范的生产环境 URL 变量。

#### Local setup

1. Install dependencies:
   ```bash
   bun install
   ```
2. Create your local env file:
   ```bash
   cp apps/web/.env.example apps/web/.env
   ```
3. Fill in the required values in `apps/web/.env`.  
   在 `apps/web/.env` 中填写所需的值。
4. Start the app:
   ```bash
   bun run web
   ```

If you already have a linked Vercel project, you can still pull env vars locally with `vc env pull`, but setup is now intentionally manual so you can see exactly which values matter.  
如果您已有一个已关联的 Vercel 项目，您仍然可以通过 `vc env pull` 命令拉取环境变量到本地，但配置现在是有意手动进行的，以便您确切了解哪些值是重要的。

#### OAuth and integration setup

###### Vercel OAuth

Create a Vercel OAuth app and use this callback:  
创建一个 Vercel OAuth 应用并使用此回调:

```
https://YOUR_DOMAIN/api/auth/vercel/callback
```

For local development, use:

```
http://localhost:3000/api/auth/vercel/callback
```

Then set:

```
NEXT_PUBLIC_VERCEL_APP_CLIENT_ID=...
VERCEL_APP_CLIENT_SECRET=...
```

###### GitHub App

You do not need a separate GitHub OAuth app. Open Agents uses the GitHub App's user authorization flow.  
您不需要单独的 GitHub OAuth 应用。Open Agents 使用 GitHub 应用的用户授权流程。

Create a GitHub App for installation-based repo access and configure:  
创建一个用于基于安装的仓库访问的 GitHub App 并进行配置：

- Homepage URL: `https://YOUR_DOMAIN`  
  首页网址: `https://YOUR_DOMAIN`
- Callback URL: `https://YOUR_DOMAIN/api/github/app/callback`  
  回调 URL: `https://YOUR_DOMAIN/api/github/app/callback`
- Setup URL: `https://YOUR_DOMAIN/api/github/app/callback`  
  设置 URL: `https://YOUR_DOMAIN/api/github/app/callback`
- enable "Request user authorization (OAuth) during installation"  
  启用"在安装过程中请求用户授权（OAuth）"
- make the app public if you want org installs to work cleanly  
  如果希望组织安装能正常工作，请将应用设为公开

For local development, use `http://localhost:3000/api/github/app/callback` for the callback/setup URL and `http://localhost:3000` as the homepage URL.  
对于本地开发，请使用 `http://localhost:3000/api/github/app/callback` 作为回调/设置 URL，使用 `http://localhost:3000` 作为首页 URL。

Then set:

```
NEXT_PUBLIC_GITHUB_CLIENT_ID=...   # GitHub App Client ID
GITHUB_CLIENT_SECRET=...           # GitHub App Client Secret
GITHUB_APP_ID=...
GITHUB_APP_PRIVATE_KEY=...
NEXT_PUBLIC_GITHUB_APP_SLUG=...
GITHUB_WEBHOOK_SECRET=...
```

`GITHUB_APP_PRIVATE_KEY` can be stored as the PEM contents with escaped newlines or as a base64-encoded PEM.  
`GITHUB_APP_PRIVATE_KEY` 可以存储为带有转义换行符的 PEM 内容，或者存储为 base64 编码的 PEM。

#### Open Agents：一句话看懂

##### 核心概述
Open Agents 是一个开源参考应用，帮助团队在 Vercel 上搭建 “后台运行的编码代理”。  
它不依赖本地电脑执行，而是把网页交互、代理工作流、代码执行环境拆开，形成一套可部署、可扩展的代理开发平台。

##### 它到底是什么
这个系统本质上分三层：

###### Web 层：用户入口
负责登录认证、会话管理、聊天交互和流式 UI 展示。  
用户看到的是一个聊天式编码助手。

###### Agent 工作流层：大脑
代理运行在 Vercel 的持久化工作流里，不是一次请求执行完就结束。  
它可以跨多步持续工作，支持复杂任务编排。

###### Sandbox VM 层：执行环境
真正执行文件操作、Shell 命令、Git 操作、开发服务器预览的地方。  
它像一个独立、安全的远程开发机。

##### 最关键的设计思想
###### 代理不在沙箱里运行
这是 Open Agents 最重要的架构特点。  
代理本身运行在沙箱外，通过 “读文件、改文件、搜索、执行命令” 等工具与沙箱交互。

###### 这样设计的价值
- 代理执行不受单次请求生命周期限制  
- 沙箱可以独立休眠和恢复，更省资源  
- 模型能力和沙箱实现可以分开演进  
- 沙箱保持简单，不承担控制平面职责

一句话：**大脑和手脚分离，系统更灵活、更稳定。**

##### 当前具备哪些能力
###### 编码代理能力
支持聊天式代码协作，能调用文件、搜索、Shell、任务、技能和网页工具。

###### 工程协作能力
支持仓库克隆、分支开发、自动提交、自动推送，以及成功后自动创建 PR。

###### 运行与恢复能力
支持持久化多步骤执行、沙箱快照恢复、会话分享，以及可选语音输入。

##### 部署时真正需要关注什么
###### 最低必需项
应用要正常启动，至少需要：
- `POSTGRES_URL`
- `JWE_SECRET`

###### 可用但不完整
如果缺少 Vercel OAuth 相关配置，网站能部署，但登录能力不完整。

###### 想接入 GitHub 必须补齐
如果要访问私有仓库、推送分支、创建 PR，就必须配置 GitHub App 相关变量。

###### 可选增强项
Redis/KV、生产 URL、沙箱快照 ID、ElevenLabs 语音转录等，都属于增强能力，不是启动硬门槛。

##### 推荐部署路径
###### 在线部署
官方推荐做法是：Fork 仓库 → 配 PostgreSQL → 生成密钥 → 导入 Vercel → 配 OAuth 和 GitHub App → 重新部署。  
这条路径最适合想快速拥有自定义编码代理的团队。

###### 本地启动
本地只需：
- 安装依赖：`bun install`
- 复制环境变量模板
- 填写必要配置
- 运行：`bun run web`

整体上，本地配置被设计成 “手动可见”，目的是让开发者明确知道每个变量的作用。

##### 适合谁
###### 适合的场景
- 想搭建自己的 AI 编码代理平台
- 希望代理在云端后台持续运行
- 需要 GitHub、PR、沙箱执行、预览环境一体化
- 想基于开源代码二次改造，而不是用黑箱产品

##### 一句话结论
Open Agents 不是一个简单的聊天机器人，而是一套 “云端编码代理基础设施模板”。  
它的核心价值在于：**把 AI 代理、执行环境和工程协作能力系统化拆分，让团队可以真正构建自己的 Agent 产品。**
