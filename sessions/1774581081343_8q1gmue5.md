## 分析要点

- **核心高价值点**：最有价值的是提出“评估直接塑造代理行为”，强调应围绕生产中真正关心的行为设计针对性 eval，而不是盲目堆测试数量。
- **留存建议**：长期保留（内容包含智能体评估设计、指标体系与中间件扩展框架，适合后续搭建或优化代理系统时反复参考。）

**知识要点**

- 评估应按被测行为分类，并为每个 eval 写明其能力映射与标签，便于分组运行和长期维护。
- 模型选择应先看正确性，再在达标模型中比较效率、延迟和成本，并借助“理想轨迹”衡量行为质量。
- Agent Middleware 通过 before\_model、wrap\_model\_call、wrap\_tool\_call 等钩子，将业务逻辑、合规与运行时控制从核心代理循环中解耦。

**行动项**

- 为当前智能体系统梳理 5-10 个关键生产行为，并补齐对应的针对性 eval，而非继续泛化堆 benchmark。
- 建立评估标签体系与 docstring 规范，在 CI 中支持按行为类别和模型进行子集评测。
- 审视现有代理框架是否需要引入 middleware 层来承载 PII 处理、重试、总结、动态工具选择等横切逻辑。

### 我们如何构建深度智能体的评估

TLDR: 最佳的代理评估直接衡量我们关心的代理行为。以下是我们如何获取数据、创建指标，并随着时间的推移开展范围明确、针对性强的实验，以提高代理的准确性和可靠性。

#### 评估塑造代理行为

我们一直在精心构建评估以衡量和改进

[Deep Agents](https://github.com/langchain-ai/deepagents). Deep Agents 是一个开源的、与模型无关的代理工具包，可为像

[Fleet](https://www.langchain.com/langsmith/fleet)

以及

[Open SWE](https://github.com/langchain-ai/open-swe)

. 评估定义并塑造代理行为，因此精心设计它们非常重要。

每次评估都是一个会改变你的代理系统行为的向量。例如，如果一个关于高效文件读取的评估失败，你可能会调整系统提示或 read\_file 工具描述来引导行为，直到评估通过。你保留的每次评估都会随着时间的推移对整个系统施加压力。

在添加评估时要深思熟虑，这一点至关重要。盲目地添加数百（或数千）个测试可能会很诱人。但这会导致一种错觉，即通过在评估套件中取得高分来“提升你的智能体”，而该评估套件可能无法准确反映你在生产环境中关注的行为。

更多的评估 ≠ 更好的智能体。相反，构建有针对性的评估以反映生产环境中期望的行为。

在构建 Deep Agents 时，我们梳理生产环境中关键的行为，例如从文件系统中的多个文件中检索内容，或准确地按顺序组合 5 个以上的工具调用。与整体使用基准测试任务不同，我们采用以下方法进行评估整理：

1. 决定我们希望代理遵循哪些行为。然后研究并精心挑选针对性的评估，以可验证的方式衡量这些行为。
2. 对于每个 eval，添加一个 docstring 来解释它如何衡量 agent 能力。这确保每个 eval 是自文档化的。我们还为每个 eval 标记如 tool\_use 之类的类别，以支持分组运行。
3. 检查输出跟踪以了解故障模式并更新评估覆盖率

因为我们将每次评估运行追溯到一个共享的

[LangSmith](https://docs.langchain.com/langsmith/observability) 项目，团队中的任何人都可以参与进来分析问题、进行修复，并重新评估特定评估的价值。这为添加和维护良好的评估创建了共同责任。在许多评估中运行多个模型可能会成本高昂，因此有针对性的评估可以节省成本，同时改进你的代理。

在本博客中我们涵盖：

- 我们如何整理数据
- 我们如何定义指标
- 我们如何运行评估

#### 我们如何整理数据

我们有几种获取 evals 的方式：

1. 利用我们代理内部试用的反馈
2. 从外部基准测试中拉取选定的评估数据（如
   [终端基准测试 2.0](https://www.tbench.ai/) 或
   [BFCL](https://gorilla.cs.berkeley.edu/leaderboard.html)
   ）并经常为特定代理调整这些评估数据
3. 编写我们自己的（手工的）评测和单元测试，针对我们认为重要的行为

![Image](https://pbs.twimg.com/media/HET8gsLWkAAun5Q?format=jpg&name=large)

我们每天都在内部试用我们的代理。每个错误都成为编写评估和更新我们代理定义及上下文工程实践的机会。

> 注意：我们将 SDK 单元测试和集成测试（系统提示透传、中断配置、子代理路由）与模型能力评估区分开来。任何模型都能通过这些测试，因此将它们纳入评分不会增加任何信号。你绝对应该编写单元测试和集成测试，但本博客仅关注模型能力评估。

#### 内部试用代理和读取痕迹是评估的重要来源

这使得发现错误成为可能。

[跟踪记录](https://docs.langchain.com/langsmith/observability-concepts#traces)给我们提供数据以了解代理行为。由于跟踪记录通常很大，我们使用内置代理，如

[Polly](https://docs.langchain.com/langsmith/polly)

或

[Insights](https://docs.langchain.com/langsmith/insights)

以大规模分析它们。你也可以对其他代理（如 Claude Code 或

[Deep Agents CLI](https://docs.langchain.com/oss/python/deepagents/cli/overview)

）以及一种获取跟踪记录的方法，如

[LangSmith CLI](https://docs.langchain.com/langsmith/langsmith-cli)

。我们的目标是理解每种失败模式，提出修复方案，重新运行代理，并跟踪进度和随时间的回归情况。

例如，现在很大一部分修复 bug 的拉取请求（PR）是通过

[Open SWE](https://blog.langchain.com/open-swe-an-open-source-framework-for-internal-coding-agents/)，我们的开源背景编码代理。使用它的团队会接触许多不同的代码库，这些代码库具有不同的上下文、规范和目标。这自然会导致错误。Open SWE 的每一次交互都会被追踪，因此这些交互可以很容易地成为评估，以确保错误不再发生。

其他评估是从现有的基准测试中提取并调整，如

[BFCL](https://gorilla.cs.berkeley.edu/leaderboard.html) 用于函数调用。对于编码任务，我们与

[Harbor](https://github.com/laude-institute/terminal-bench)

以运行选定的任务来自数据集（如

[Terminal Bench 2.0](https://www.tbench.ai/leaderboard/terminal-bench/2.0)

在沙箱环境中执行的任务。许多评估是从头编写的，作为专注的测试以观察孤立行为，例如测试 read\_file 工具。

#### 我们根据它们测试的内容对评估进行分组

建立一个评估的分类体系来获得对智能体表现的中间视角是很有帮助的（不是单一的数字，也不是单个的运行结果）。

> 提示： 创建该分类法时，应关注它们测试的内容，而非它们的来源。例如，来自
>
> [FRAMES](https://huggingface.co/datasets/google/frames-benchmark) 和
>
> [BFCL](https://gorilla.cs.berkeley.edu/leaderboard.html)
>
> 可以标记为“外部基准测试”，但这无法分别展示它们如何衡量检索和工具使用。

以下是我们定义的一些类别以及它们测试的内容：

![Image](https://pbs.twimg.com/media/HET-ppfW8AAwuK_?format=jpg&name=large)

如今，所有评估均是智能体在某个任务上的端到端运行。我们刻意鼓励评估结构的多样性。有些任务从输入提示开始一步完成，而另一些任务则需要经过10+轮交互，由另一个模型模拟用户。

#### 我们如何定义指标

在为我们的代理选择模型时，我们首先考虑正确性。如果一个模型不能可靠地完成我们关注的任务，其他一切都无关紧要。我们在评估中运行多个模型，并随着时间的推移不断优化评估框架，以解决我们发现的问题。

测量正确性取决于测试的内容。大多数内部评估使用自定义断言，例如“代理是否并行调用了工具？”。像 BFCL 这样的外部基准测试使用与数据集中真实答案的精确匹配。对于像代理是否在内存中持久化了正确内容这类语义层面的正确性评估，我们使用以 LLM 作为评判者的方法。

一旦几个模型达到了那个标准，我们就转向效率。 两个解决相同任务的模型在实际中可能表现得非常不同。 一个模型可能会进行额外的交互轮次，进行不必要的工具调用，或者由于模型大小而在完成任务时更慢。在生产环境中，这些差异会表现为更高的延迟、更高的成本以及更差的整体用户体验。

总体而言，我们为每次评估器运行所测量的指标是：

![Image](https://pbs.twimg.com/media/HET_GObbYAECk4q?format=jpg&name=large)

解决率衡量智能体解决任务的速度，通过预期步骤数进行归一化。与延迟比类似，它捕捉解决任务的端到端时间，包括模型往返、服务提供商延迟、错误转向和工具执行时间。对于能够定义理想轨迹的简单任务，解决率比延迟比更容易处理，因为它只需要测量给定智能体的任务持续时间。

这为我们提供了一种选择带有针对性评估集的模型的简单方法：

1. 首先检查准确性：哪些模型在你真正关心的任务上足够准确？
2. 然后，比较效率：在足够好的模型中，哪一个在正确性、延迟和成本之间提供最佳的权衡？

#### 评估相关的有用指标示例

为了让模型比较具有可操作性，我们研究模型如何成功和失败。这需要一个具体的参考点，来定义“良好执行”在准确性之外的样子。我们使用的一个基本概念是理想轨迹。 这是一系列步骤，能够产生正确的结果，且不包含“不必要”的操作。

对于简单且范围明确的任务，变量定义得足够严格，使得最优路径通常很明显。对于更开放的任务，我们使用到目前为止表现最佳的模型近似生成一条轨迹，然后随着模型和工具的改进重新审视基准。通过这种方式，观察智能体的行为有助于我们优化关于理想轨迹的先验知识。

考虑一个简单的请求：

> 我住的地方当前的时间和天气是什么？

一个智能体的理想轨迹可能如下所示：

- 它进行最少的必要工具调用（例如：确定用户 → 确定位置 → 获取时间和天气）
- 它在可能的情况下并行化独立的工具调用
- 它生成最终答案，不经过不必要的中间步骤

理想轨迹： 4 步骤，4 工具调用，约 8 秒

现在将其与一条在技术上仍然正确但效率较低的轨迹进行比较。

低效轨迹: 6步，5次工具调用，约14秒。

![Image](https://pbs.twimg.com/media/HEUAy-UbwAAQTf3?format=jpg&name=large)

上面的例子具有说明性：REPL 可以更快地解决这个任务，但调用工具的版本让这个想法更容易解释。

两次运行都是正确的，但第二次运行会增加延迟和成本，并增加了更多的失败机会。

#### 我们如何进行评估

我们使用 pytest 和 GitHub Actions 在 CI 中运行评估，以便代码变更能在干净、可重现的环境中执行。每次评估都会创建一个使用指定模型的 Deep Agent 实例，向其输入任务，并计算正确性和效率指标。

我们也可以通过标签来运行评估的一个子集，以节省成本并衡量针对性实验。例如，如果要构建一个需要大量本地文件处理和合成的智能体，我们可能会专注于带标签为 file\_operations 和 tool\_use 的子集。

```bash
export LANGSMITH_API_KEY="lsv2_..."

uv run pytest tests/evals --eval-category file_operations --eval-category tool_use --model baseten:nvidia/zai-org/GLM-5
```

[Deep Agents 代码仓库](https://github.com/langchain-ai/deepagents/tree/main/libs/evals)。

### 中间件如何让你自定义你的代理框架

代理框架是用于构建代理的工具，它们将 LLM 连接到其环境并让它执行操作。

当你构建代理时，很可能需要构建一个特定于应用的代理框架。“代理中间件”能让你在 LangChain 和 Deep Agent 的坚实基础上进行构建，同时为你的使用场景进行定制。

#### 什么是代理框架

智能体是围绕模型构建的系统。该模型需要连接到环境、数据、记忆和工具。智能体框架是帮助你实现这一连接的系统。

每个代理框架的核心都相同，而且非常简单：一个 LLM 在循环中运行并调用工具。尽管简单，这个核心循环却蕴含着力量。

![Image](https://pbs.twimg.com/media/HEV_aJ2WUAABVOQ?format=png&name=large)

LangChain 包含 \`create\_agent\`——一个仅具有此核心循环的抽象。

#### 为什么你会想要定制你的代理框架

不同的代理使用场景有不同的需求。它们可能需要不同的代理框架。

agent harness 的某些部分（比如指令或工具）相当容易自定义。例如，LangChain 中的 create\_agent 允许你传入系统提示和工具。

其他部分更复杂。如果你希望在模型执行前始终运行某个步骤该怎么办？如果你始终希望检查工具输出中的某些内容该怎么办？

涉及改变代理核心循环的事情修改起来更棘手。如果操作正确，它能够实现非常强大的自定义，同时仍然允许你在核心框架上进行构建。

AgentMiddleware 是我们针对这一问题的解决方案——我们如何让人们定制 LangChain 代理。

#### 什么是代理中间件？

注：“中间件”是软件工程其他实践中常用的通用术语，但下文我们所指的是另一个不同的系统，我们称之为 agent middleware。

中间件提供了一组钩子，让你可以在每个步骤之前和之后运行自定义逻辑，以便你可以控制循环中每个阶段的操作：

![Image](https://pbs.twimg.com/media/HEWQUxEbYAAuNLm?format=png&name=large)

- before\_agent: 在调用时运行一次。适用于加载内存、连接资源或验证初始输入。
- before\_model: 在每次模型调用前触发。使用它来修剪历史记录或在个人身份信息(PII)到达 LLM 之前捕获它们。
- wrap\_model\_call: 端到端封装模型调用。缓存、重试以及动态模型请求（如更改可用工具）都在此处实现。
- wrap\_tool\_call: 封装工具执行，方式类似。注入上下文、拦截结果或控制哪些工具实际运行。
- after\_model: 在模型响应之后但在工具执行之前运行。是最自然的人在回路环节。
- after\_agent: 在完成后运行一次。保存结果, 发送通知, 清理。

中间件是可组合的，因此你可以尽情地混合搭配。

LangChain 提供了一套针对最常见模式（如总结、重试和个人身份信息脱敏）的预构建中间件。开发者还可以继承 AgentMiddleware 类，针对业务的任何定制化需求编写自己的中间件。

#### 中间件示例

定制需求往往集中在相同主题上。以下是最常见的用例：

"业务逻辑与合规。有些事情无法仅通过提示词实现，比如个人身份信息(PII)脱敏和内容审核。这些是必须每次都触发的确定性策略。你无法通过提示词达成 HIPAA 合规。"

- 深度解析：个人身份信息检测 LangChain 的内置 PIIMiddleware 实现了 before\_model 和 after\_model 钩子。它能够对模型输入、输出以及工具输出中的个人身份信息(PII)进行屏蔽/编辑/哈希处理。在最关键的个人身份信息检测场景中，它还可以引发 PIIDetectionError。

动态代理控制。 中间件可以在运行时重塑代理：根据当前状态注入工具，在任务中途切换模型，随着上下文演变更新系统提示。这是对代理在每个步骤中行为的主动控制。

- 深度分析：动态工具选择 LangChain’s
  [LLM 工具选择器中间件](https://docs.langchain.com/oss/python/langchain/middleware/built-in#llm-tool-selector)在 wrap\_model\_call 钩子中运行一个快速的 LLM，以识别注册表中哪些工具与给定请求相关。然后将这些工具绑定到模型请求，以减少主模型调用中不必要工具导致的上下文膨胀。

上下文管理。 模型的效果取决于你输入给它的内容。例如，当你接近 token 限制时可能需要进行总结，并修剪嘈杂的工具输入/输出。上下文工程是一个运行时问题，而不是一次性提示问题。

- 深度解析：总结与上下文卸载 LangChain 的内置
  [SummarizationMiddleware](https://docs.langchain.com/oss/python/langchain/middleware/built-in#summarization) 实现了 before\_model 钩子。为避免上下文溢出，如果消息历史记录超过某个 token 阈值，其内容会在传递给模型之前被总结。该中间件的扩展实现了 wrap\_tool\_call 钩子，以将详细的工具调用输入和输出扩展到文件系统。

生产就绪。 中间件允许您构建模型/工具重试逻辑、模型回退以及带有中断的人在回路。这类功能在演示中不会体现，但对生产代理至关重要。

- 深度解析：模型重试 LangChain 的内置实现了 wrap\_model\_call 钩子，以便使用重试处理程序包装模型的 API 调用。该处理程序支持重试配置，例如重试次数、退避因子和初始延迟（用于排查速率限制问题）。

工具集。 注入需要围绕代理循环进行自定义设置和拆卸的工具，例如连接到外部工具服务器、初始化 Shell 或启动沙箱。

- 深度解析: Shell 工具中间件 LangChain 的
  [ShellToolMiddleware](https://docs.langchain.com/oss/python/langchain/middleware/built-in#shell-tool) implements the before\_agent and after\_agent hooks in order to initialize and teardown shell resources around the core agent loop. It also adds the shell tool to the model’s list of tools.

#### 综合洞察：从「Agent 评估」到「Agent 中间件」，对产品实践的启发

这两篇内容表面上分别在讲 **如何评估 Agent** 和 **如何定制 Agent 框架**，但放在一起看，实际上指向了一个更深的产品命题：

> **未来的 AI 产品竞争，不只是模型能力竞争，而是“行为设计能力”竞争。**
> 谁能更精准地定义系统应该如何行动、如何被约束、如何被验证，谁就更可能做出稳定、可规模化、可商业化的 AI 产品。

如果把它翻译成产品语言，这两篇内容共同回答了三个问题：

1. **你到底希望 AI 产品表现出什么“可预期行为”？**
2. **你用什么机制让它稳定地产生这些行为？**
3. **你如何持续验证这些行为在真实场景中没有退化？**

这对产品经理的意义非常大，因为它意味着：  
在 Agent 时代，产品经理不再只是定义“功能”和“流程”，而是要定义一套 **行为系统（Behavior System）**。

---

#### 一、核心结论

##### 1. Agent 产品的本质，不是“会不会做”，而是“是否稳定地按你希望的方式做”

内容 1 的核心观点非常重要：  
**评估不是验收工具，而是塑造 Agent 行为的机制。**

每加一个 eval，本质上都在给系统施加一个优化方向。  
这和传统产品里的 KPI 很像——你衡量什么，团队就会优化什么；AI 系统也一样。

因此，产品上的关键启发是：

- 不能只问“这个 Agent 能不能完成任务”
- 更要问“它是不是以我们期望的方式完成任务”
- 以及“这种完成方式是否适合真实用户场景、成本结构和风险约束”

这意味着，Agent 产品定义的对象，不再只是结果，还包括：

- 完成路径
- 工具使用方式
- 上下文管理方式
- 错误恢复方式
- 成本/延迟边界
- 合规与安全处理方式

也就是说，**产品定义从结果导向，升级为结果 + 过程导向。**

---

##### 2. Agent 产品的护城河，不在“Prompt 写得好”，而在“框架化地管理行为”

内容 2 的核心观点是：  
**仅靠 prompt 无法支撑生产级 Agent。**

很多关键需求无法通过 prompt 保证，例如：

- PII 脱敏
- 审核与合规
- 工具调用限制
- 模型重试与回退
- 动态上下文管理
- 人在回路
- 运行时策略切换

这些需求必须通过更底层、更确定性的机制实现。  
中间件的价值就在于：**把这些运行时控制点抽象出来，形成可组合、可复用、可治理的控制层。**

对产品经理来说，这个启发是：

> 真正成熟的 AI 产品设计，不是“设计一个 Agent”，而是“设计一个 Agent 操作系统”。

这个系统至少包含三层：

- **能力层**：模型、工具、知识、记忆
- **控制层**：中间件、策略、路由、护栏、上下文治理
- **验证层**：评估、指标、回归、trace 分析、线上反馈闭环

谁能把这三层闭环打通，谁才可能做出真正稳定的 AI 产品。

---

#### 二、两篇内容合并后，透露出的产品方法论升级

---

##### 1. 从“功能需求”转向“目标行为定义”

传统产品 PRD 更像是在描述：

- 页面怎么跳
- 功能怎么点
- 流程怎么走

但 Agent 产品的 PRD，如果还停留在这个层面，会很快失效。  
因为 Agent 不是确定性流程机，而是带有概率性的行动系统。

所以未来更有效的产品定义方式，应该从功能描述转向行为定义。

###### 传统写法
- 用户点击按钮后，系统生成报告
- 用户输入需求后，系统返回推荐结果

###### Agent 时代更好的写法
- 系统在生成报告前，必须先检索最近 7 天数据，再调用分析工具，再生成结构化结论
- 对不确定信息必须显式表达置信不足，不能编造
- 涉及敏感信息时必须先脱敏再送入模型
- 当上下文过长时应优先总结历史而非截断关键任务信息
- 当工具结果异常时应重试一次并在失败后请求用户澄清

这其实是在写 **行为规格（behavior spec）**，而不只是功能说明。

对产品经理来说，这是一种非常关键的能力迁移：
你未来要定义的，不只是用户流程，而是 **系统在复杂不确定条件下的行为原则**。

---

##### 2. 从“上线一个功能”转向“运营一套行为资产”

内容 1 反复强调一个点：  
**不要盲目堆 eval。更多评估不等于更好的 Agent。**

这句话背后，对产品实践的启发很深：

###### Eval 是产品资产，不是测试清单
每一个 eval，都应该映射到一个真实高价值行为，比如：

- 多文件检索是否准确
- 长任务中的工具顺序是否合理
- 是否会进行不必要调用
- 是否会丢失长期记忆
- 是否能在多轮中维持任务目标

所以产品经理未来管理的，不只是需求池和迭代列表，还要有一套 **行为资产池**：

- 核心行为清单
- 高风险失败模式清单
- 关键任务轨迹样本
- 线上典型错误 trace
- 对应 eval 与指标

这相当于把“用户反馈”升级为“行为训练数据与验证资产”。

###### 一个重要推演
未来优秀 AI PM，很可能会像今天优秀增长 PM 管漏斗一样，去管：

- 哪些行为最影响用户感知
- 哪些失败模式最影响留存/转化
- 哪些 Eval 最能预测真实线上效果
- 哪些行为值得被持续固化为系统能力

这本质上是把产品管理，从需求管理推进到了 **行为管理**。

---

##### 3. 从“版本发布”转向“持续校准”

传统软件发布后，行为相对稳定。  
但 Agent 产品会因以下因素持续漂移：

- 模型版本变化
- Prompt 变化
- 工具变化
- 记忆机制变化
- 中间件策略变化
- 用户任务分布变化

所以 Agent 产品不是做完上线，而是要持续校准。

内容 1 给出的实践非常有代表性：

- 内部 dogfooding
- 线上 trace 分析
- 从 bug/失败案例反推 eval
- 用标签化评估做局部优化
- 持续维护和减少评估集，而不是无限膨胀

对产品实践的启发是：

> AI 产品管理会越来越像“控制系统管理”，而不是“功能项目管理”。

你要管理的是偏差、漂移和反馈闭环。

---

#### 三、对产品经理最直接的 8 个启发

---

##### 1. 产品目标要拆成“用户价值”与“系统行为”两层

过去很多 PM 会直接写：
- 提升回答准确率
- 提高任务完成率

但对于 Agent 来说，这还不够。  
你需要继续追问：

- 它通过什么行为达成？
- 哪些行为是不可接受的，即使结果偶尔是对的？
- 哪些行为虽然正确，但成本、延迟、风险不可接受？

所以建议每个 AI 产品目标都拆成两层：

###### 用户价值层
- 更快解决问题
- 更少人工操作
- 更高结果质量

###### 系统行为层
- 更少无效工具调用
- 更强上下文保持
- 更稳定的多步任务执行
- 更少幻觉式补全
- 更合理的失败恢复

这会让你的产品设计从“感性目标”变成“可落地行为设计”。

---

##### 2. 正确性不是唯一指标，效率同样是产品体验的一部分

内容 1 提到一个非常重要的判断顺序：

1. 先看正确性
2. 再看效率
3. 再看成本与延迟权衡

这对产品经理特别重要，因为很多 AI 产品容易掉进一个误区：

- 只要答对就行
- 只要能完成任务就行

但真实用户不会只感知“对不对”，还会感知：

- 慢不慢
- 啰不啰嗦
- 是否绕路
- 是否频繁出错后自我修复
- 是否调用太多工具导致等待感强

所以未来产品指标要从单一准确率，升级成组合指标，例如：

- 任务完成率
- 首次完成率
- 平均工具调用数
- 平均完成轮次
- 平均端到端时长
- 失败恢复率
- 单任务成本
- 用户主观满意度

也就是说，**正确但低效，依然是坏产品体验。**

---

##### 3. 要把“理想轨迹”当作产品设计对象

内容 1 提出的 ideal trajectory 很值得产品经理借鉴。

传统产品设计关注：
- 用户路径

Agent 产品还要关注：
- 系统路径

例如用户说一句“帮我看下我这里现在几点、什么天气”，系统内部理想路径可能是：

1. 获取用户位置
2. 并行调用时间与天气
3. 汇总输出
4. 不做多余调用

这实际上是一个 **系统最优行动路径设计**。

产品经理可以把它用在很多场景中：

- 销售助手如何生成客户洞察
- 编码 Agent 如何修复 bug
- 运营 Agent 如何分析报表
- 研究 Agent 如何做资料整合

如果你不定义理想轨迹，团队最后很可能只能看结果，而忽略路径中的低效、风险和脆弱性。

一个成熟的 AI 产品团队，应该同时维护：

- 用户旅程图
- 系统理想轨迹图
- 常见失败轨迹图

---

##### 4. 线上 bug 不只是要修，还要被“产品化”为 eval

这是内容 1 最具操作价值的一点。

很多团队面对 AI 错误时的反应是：
- 改 prompt
- 加规则
- 再试试

这非常低效，因为错误没有沉淀成组织资产。

更好的方法是：
- 从真实失败案例中抽取任务
- 抽象为标准化 eval
- 归类到某个行为维度
- 用于后续回归验证

这带来的产品价值非常大：

- bug 不再是一次性成本，而是系统学习样本
- 团队对“什么问题重要”会形成共识
- 可以追踪某类体验是否持续改善
- 产品路线图会越来越基于真实行为短板，而不是拍脑袋

对 PM 来说，这意味着：
**你要推动建立“线上失败 → 行为抽象 → 评估沉淀 → 策略修复”的闭环。**

---

##### 5. 未来产品经理要能定义“哪些事必须 deterministic，哪些可以交给模型”

中间件部分揭示了一个核心判断：

并不是所有问题都该交给 LLM 决策。  
有些事属于模型的强项，有些事必须用确定性逻辑兜底。

###### 适合交给模型的
- 语义理解
- 任务分解
- 内容生成
- 开放性推理
- 工具选择建议

###### 更适合 deterministic 控制的
- 合规处理
- PII 脱敏
- 审批流
- 访问权限控制
- 重试规则
- 中断与升级机制
- 风险阈值判断
- 可用工具白名单/黑名单

这会成为未来 AI 产品设计的核心能力之一：

> **不是“让模型做更多”，而是“明确模型该做什么，不该做什么”。**

这其实是一种新的产品边界设计能力。

---

##### 6. 中间件思想，本质上是“把复杂产品规则从 prompt 中抽出来”

很多团队一开始会把所有要求都塞进 prompt：

- 不能输出敏感信息
- 不要太长
- 要先查知识库
- 不确定要说不知道
- 要遵守业务流程
- 遇到 A 情况做 B，遇到 C 情况做 D

但随着复杂度增加，prompt 会越来越像一团不可维护的泥球。

中间件的价值就在于把这些逻辑结构化拆分：

- before_agent：初始化资源、校验输入
- before_model：整理上下文、做脱敏
- wrap_model_call：重试、缓存、动态模型切换
- wrap_tool_call：工具拦截、注入上下文
- after_model：人工审核、风险校验
- after_agent：存档、通知、清理

从产品角度看，这是一种非常重要的架构思想：

> 把“产品规则”从“模型描述”中解耦出来，变成独立、可复用、可治理的系统模块。

这会显著提升：

- 可维护性
- 可解释性
- 团队协作效率
- 复用性
- 合规性
- 组织级能力沉淀

---

##### 7. AI 产品的竞争，会从“单点能力”走向“体系化工程能力”

这两篇内容共同传递出一个信号：

未来做 Agent，真正拉开差距的不是某个 prompt 技巧，也不是接了多少工具，而是整套工程体系是否成熟，包括：

- 行为定义
- 失败模式识别
- 运行时控制
- 线上 trace
- 评估体系
- 回归机制
- 成本治理
- 组织协作方式

这对产品经理是一个角色升级信号。

未来优秀 AI PM 不只是“懂用户、懂需求、懂商业”，还需要理解：

- Agent 的关键行为结构
- 模型与规则的边界
- 哪些能力要通过架构实现
- 哪些能力要通过 eval 固化
- 哪些体验问题本质上是运行时控制问题

换句话说，AI PM 会比过去更像：
**产品策略师 + 行为设计师 + AI 系统运营者。**

---

##### 8. 组织协作方式也会变：产品、工程、研究会围绕“行为单元”协作

内容 1 提到一个很关键的细节：  
每个 eval 都有 docstring、标签、共享 trace，团队成员都能共同分析问题、修复和重评估。

这说明在 Agent 团队里，更好的协作对象不是“页面模块”，而是“行为单元”。

例如：

- 文件检索行为
- 工具串联行为
- 长任务上下文保持行为
- 敏感信息处理行为
- 子代理路由行为

这会带来更好的跨职能协作：

- PM 定义行为目标和优先级
- 工程实现中间件/工具/流程控制
- 算法或提示工程优化模型行为
- QA 与数据同学沉淀 eval 与 failure cases
- 运营反馈线上真实任务分布和投诉点

这是一种更适合 AI 产品的协作基本盘。

---

#### 四、对你的产品实践，最值得重点吸收的框架

如果你是资深产品经理，我会建议你把这两篇内容沉淀为一个可直接落地的框架：

##### 一个 AI Agent 产品的四层实践框架

---

##### 第一层：定义关键任务
先不要急着定义功能，而是定义用户真正要完成的任务。

比如：

- 帮销售在 3 分钟内完成客户会前准备
- 帮开发者快速定位 bug 并产出修复建议
- 帮运营从日报中识别异常并提出动作建议
- 帮研究人员从多来源资料中提炼结论

重点不是“有什么功能”，而是“任务是否被完整解决”。

---

##### 第二层：定义目标行为
围绕每个关键任务，定义系统应该表现出的行为。

包括：

- 如何检索
- 如何调用工具
- 如何处理长上下文
- 如何表达不确定性
- 如何做失败恢复
- 如何管理成本与时延
- 如何处理权限与合规

这一步是未来 AI PRD 的核心。

---

##### 第三层：建立控制机制
用中间件思想，把关键策略模块化。

例如：

- 输入校验
- PII/合规处理
- 动态工具注入
- 模型切换
- 重试与回退
- 人工审核节点
- 结果后处理
- 会话总结与长期记忆管理

这里本质上是在搭产品的“行为控制层”。

---

##### 第四层：建立验证闭环
把真实失败案例转成 eval，并按行为维度管理指标。

建议至少有三类：

- 正确性指标：是否完成任务
- 效率指标：用了多少步、多少工具、多久完成
- 风险指标：是否越权、泄露、幻觉、误用工具

最终让产品迭代从“感觉优化”变成“行为校准”。

---

#### 五、一些更深一层的推演

---

##### 1. AI 产品经理的核心产出物会发生变化

未来一个成熟 AI PM 的关键产出，可能不再只是：

- PRD
- 原型图
- 流程图
- 需求池

而会增加：

- 行为规范文档
- 理想轨迹定义
- 失败模式地图
- 评估用例清单
- 中间件策略清单
- 风险边界说明
- 人机协同升级规则

这意味着产品工作会更“系统设计化”。

---

##### 2. 用户体验设计会从界面设计扩展到“系统人格与行动风格设计”

Agent 产品里，体验已经不只是 UI 交互。

用户实际感知的是：

- 它是否懂边界
- 它是否会主动澄清
- 它是否绕路
- 它是否过度自信
- 它是否能在复杂任务中保持稳定
- 它是否像一个可靠助手，而不是一个随机生成器

这些都不是 UI 问题，而是行为设计问题。

所以未来的 UX，会更像：
**界面体验 + 决策体验 + 行为体验。**

---

##### 3. 真正的产品差异化，将越来越来自“任务完成系统”而不是“聊天入口”

很多 AI 产品今天看起来都差不多，因为大家都停留在聊天入口层。

但这两篇内容告诉我们，差异化会发生在更深层：

- 是否有清晰的行为控制层
- 是否有高质量任务评估集
- 是否能从线上失败快速学习
- 是否能在不同任务中动态配置工具/模型/上下文
- 是否能做到稳定、便宜、快、可解释

因此，产品战略上应该尽量避免把自己定义成一个“通用聊天工具”，而要定义成一个：

> **在特定高价值任务上可验证地稳定完成工作的系统。**

---

#### 六、给你在产品实践中的具体建议

##### 1. 重写你的 AI 产品 PRD 模板
建议新增几个固定模块：

- 目标任务定义
- 关键行为要求
- 不可接受行为
- 理想轨迹
- 失败恢复机制
- 风险与合规约束
- 评估与验收指标

---

##### 2. 为每个核心场景建立“行为标签体系”
类似内容 1 里的做法，把场景按行为维度分组，而不是按来源分组。

例如：

- `retrieval`
- `tool_use`
- `memory`
- `planning`
- `handoff`
- `safety`
- `latency`
- `cost_control`

这样你就能真正知道系统哪种能力在退化，而不是只看到一个总分。

---

##### 3. 建立“线上失败案例池”
把以下信息结构化记录：

- 用户任务
- 实际输出
- trace/调用路径
- 失败类型
- 影响程度
- 是否可复现
- 是否已沉淀为 eval
- 修复方案归属（prompt / tool / middleware / model / policy）

这会极大提升你团队的 AI 迭代效率。

---

##### 4. 推动工程团队把关键规则中间件化
凡是以下类型的需求，都应优先考虑中间件或规则层，而不是 prompt：

- 权限
- 合规
- 安全
- 日志
- 监控
- 限流
- 模型切换
- 工具注入
- 人工升级
- 重试回退

---

##### 5. 不要只追求“更聪明”，要追求“更稳、更快、更可控”
很多团队会被大模型能力进展带偏，持续追逐“更强模型”。

但真正影响商业化落地的，常常是：

- 成功率是否稳定
- 延迟是否可接受
- 成本是否可控
- 风险是否可治理
- 失败时是否可恢复
- 能否被组织放心接入业务流程

从产品优先级上看，这些往往比“再提升一点开放问答能力”更重要。

---

#### 七、一句话总结

这两篇内容共同给出的最重要启发是：

> **AI 产品的核心，不再是设计一个会回答问题的系统，而是设计一个可被约束、可被校准、可被持续进化的行为系统。**

对产品经理而言，这意味着能力重心要从：

- 功能定义
- 交互流程
- 版本迭代

升级到：

- 行为定义
- 运行时控制
- 评估闭环
- 风险治理
- 任务完成系统设计

如果说过去的产品经理是在设计“用户与软件的交互”，  
那么 Agent 时代的产品经理，正在开始设计“用户目标如何被一个半自主系统可靠完成”。

---

#### 最后给你的一个实践落点

如果你要把这两篇内容快速转成团队动作，我建议只做三件事：

1. **先选 3 个最关键用户任务**，为每个任务写出理想轨迹和不可接受行为  
2. **从最近 20 个真实失败案例里抽取 eval**，按行为标签归类  
3. **梳理哪些规则必须从 prompt 升级为中间件/确定性控制**

只要这三步做起来，你的 AI 产品实践就已经从“做 demo”进入“做系统”阶段了。
