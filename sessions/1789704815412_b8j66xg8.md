## 分析要点

- **核心高价值点**：将文件选择、任务分组、规则匹配和评论定位交给确定性模块，把动态判断与上下文检索交给Agent，可同时改善覆盖稳定性、定位精度和Token成本。
- **留存建议**：重点保留，适合作为AI代码审查产品设计、Agent架构和工程落地的参考（提供了可复用的确定性工程与LLM Agent混合架构，并包含安装、配置、审查模式、集成方式和基准设计。）

**知识要点**

- 纯自然语言驱动的代码审查Agent容易出现文件覆盖不全、评论位置漂移和提示词敏感等问题。
- 按相关文件分组并为每组运行隔离上下文的子Agent，可用分治与并发方式处理大型变更集。
- 代码审查系统应同时衡量精确率、召回率、F1、执行时间和Token消耗，而不能只看缺陷发现数量。

**行动项**

- 在测试仓库安装并配置OCR，分别运行工作区审查、分支差异审查和全文件扫描。
- 选取真实Pull Request，对比OCR与通用编程Agent的误报率、漏报率、定位准确度、耗时和Token成本。
- 为项目关键目录配置路径过滤和定向规则，并评估其在CI流程中的稳定性。

Open Code Review is an AI-powered code review CLI tool. It originated as Alibaba Group's internal official AI code review assistant — over the past two years, it has served tens of thousands of developers and identified millions of code defects. After thorough validation at massive scale, we incubated it into an open source project for the community. Simply configure a model endpoint to get started.

It reads Git diffs, sends changed files to a configurable LLM via an agent with tool-use capabilities, and generates structured review comments with line-level precision. The agent can read full file contents, search the codebase, inspect other changed files for context, and produce deep reviews — not just surface-level diff feedback. Beyond diff review, `ocr scan` reviews entire files for auditing unfamiliar codebases or directories that have no meaningful diff.

Visit the [official website](https://open-codereview.ai) for more details.

Highlights

#### Benchmark

> Compared to general-purpose agents (Claude Code), Open Code Review achieves significantly higher **Precision** and **F1** with the same underlying model, while consuming only **\~1/9 of the tokens** and completing reviews faster. Note that its Recall is lower than general-purpose agents — a deliberate trade-off favoring precision over noise.

A real-world code review benchmark built from **50** popular open-source repositories, **200** real Pull Requests, and **10** programming languages — cross-validated by 80+ senior engineers (**1,505** annotated ground-truth issues).

[Explore the AACR-Bench dataset on Hugging Face](https://huggingface.co/datasets/Alibaba-Aone/aacr-bench).

Metric What it measures Why it matters

**F1** Harmonic mean of precision and recall Best single number for overall review quality

**Precision** Proportion of reported issues that are real defects Higher = fewer false alarms to triage

**Recall** Proportion of real defects that are found Higher = fewer issues slip through review

**Avg Time** Wall-clock time per review Matters for CI pipeline latency

**Avg Token** Total tokens consumed per review Directly impacts API cost

Benchmark

If you've used general-purpose agents like Claude Code with Skills for code review, you've likely encountered these pain points:

- **Incomplete coverage** — On larger changesets, agents tend to "cut corners," selectively reviewing only some files and missing others.
- **Position drift** — Reported issues frequently don't match the actual code location, with line numbers or file references drifting off target.
- **Unstable quality** — Natural-language-driven Skills are hard to debug, and review quality fluctuates significantly with minor prompt variations.

The root cause: a purely language-driven architecture lacks hard constraints on the review process.

Open Code Review's core philosophy is to combine deterministic engineering with an agent, each handling what it does best.

**Deterministic Engineering — Hard Constraints**

For review steps that *must not go wrong*, engineering logic — not the language model — guarantees correctness:

- **Precise file selection** — Determines exactly which files need review and which should be filtered, ensuring no important change is missed.
- **Smart file bundling** — Groups related files into a single review unit (e.g., `message_en.properties` and `message_zh.properties` are bundled together). Each bundle runs as a sub-agent with isolated context — a divide-and-conquer strategy that stays stable on very large changesets and naturally supports concurrent review.
- **Fine-grained rule matching** — Matches review rules to each file's characteristics, keeping the model's attention sharply focused and eliminating information noise at the source. Compared to purely language-driven rule guidance, template-engine-based rule matching is more stable and predictable.
- **External positioning and reflection modules** — Independent comment-positioning and comment-reflection modules systematically improve both the location accuracy and content accuracy of AI feedback.

**Agent — Dynamic Decision-Making**

The agent's strengths are concentrated where they matter most — dynamic decisions and dynamic context retrieval:

- **Scenario-tuned prompts** — Prompt templates deeply optimized for code review, improving effectiveness while reducing token consumption.
- **Scenario-tuned toolset** — Distilled from deep analysis of tool-call traces in large-scale production data — including call frequency distributions, per-tool repetition rates, and the impact of new tools on the overall call chain — resulting in a purpose-built toolset that is more stable and predictable for code review than a generic agent toolkit.

##### CLI

###### Install

```
npm install -g @alibaba-group/open-code-review
```

After installation, the `ocr` command is available globally.

For other installation methods (install script, GitHub Release binary, from source), see [Installation](https://open-codereview.ai/docs/installation).

###### Quick Start

**1. Configure LLM**

You must configure an LLM before reviewing code, unless you use [Delegation Mode](https://open-codereview.ai/docs/delegate).

```
ocr config provider          # Select a built-in provider or add a custom one
ocr config model             # Pick a model for the active provider
```

Provider setup

The interactive UI guides you through provider selection, API key entry, and model configuration, then automatically tests connectivity.

For CLI setup, environment variables, custom providers, and other advanced configuration, see [Configuration](https://open-codereview.ai/docs/configuration).

**2. Review**

```
cd your-project

# Workspace mode — review all staged, unstaged, and untracked changes
ocr review

# Branch range — reviews feature-branch's changes since it diverged from main (merge-base mode)
ocr review --from main --to feature-branch

# Single commit
ocr review --commit abc123

# Resume an interrupted range or commit review
ocr session list
ocr review --from main --to feature-branch --resume <session-id>

# Full-file scan — review whole files instead of a diff (no git history needed)
ocr scan                          # scan the entire repository
ocr scan --path internal/agent    # scan a directory or specific files
ocr scan --resume <session-id>   # resume an interrupted full-file scan

# Save results to a file (recommended for AI host agents)
ocr review --format json --output result.json

# Delegation mode — let your AI coding agent perform the review itself
# OCR handles file selection and rule resolution; no LLM configuration needed
ocr delegate preview
ocr delegate rule src/main.go src/handler.go
```

## 口播总结（1）

### 2026-09-18 04:22:15

Open Code Review 想解决的，不是“让大模型看一眼代码”这么简单，而是怎样让人工智能代码审查更稳定、更准确，也更适合放进真实的研发流程。它的核心判断是：不能把整个审查过程都交给语言模型。更可靠的方式，是用确定性的工程流程约束关键步骤，再让大模型负责需要理解和判断的部分。

这个项目最初是阿里巴巴内部的人工智能代码审查助手。项目方称，它在过去两年服务了数万名开发者，发现了数百万个代码缺陷，经过大规模使用后才转为开源。

Open Code Review 会先读取 Git 的代码差异，也就是本次改动了什么。然后，它把相关文件交给具备工具调用能力的大模型代理。这个代理不只看几行差异，还能读取完整文件、搜索整个代码仓库，并查看其他相关改动。因此，它有机会理解跨文件关系，而不是只做表面的语法检查。生成的审查意见可以精确对应到文件和代码行。

如果没有有意义的 Git 差异，例如刚接手一个陌生项目，用户还可以运行全文件扫描。这个模式会审查完整文件、指定目录，甚至整个代码仓库，不依赖历史提交。

为什么不直接使用 Claude Code 一类通用代理来审查代码？项目给出的答案是，纯粹由自然语言驱动的流程缺少硬约束，容易出现三类问题。

第一类是覆盖不完整。改动一多，通用代理可能选择性地检查部分文件，遗漏其他文件。

第二类是位置漂移。模型指出的问题可能基本正确，但文件名或代码行对不上，导致开发者很难采用这条意见。

第三类是质量不稳定。只要提示词发生细微变化，审查结果就可能明显波动。这种流程也不容易调试和复现。

Open Code Review 因此采用了混合架构，把任务分给两个部分。

第一部分是确定性的工程流程。凡是不能依赖模型临场发挥的步骤，都由程序规则保证。

例如，系统会明确计算哪些文件需要审查，哪些文件应当过滤，避免模型自己决定看什么。系统还会把相关文件组合成一个审查单元。英文和中文的消息配置文件，就可能被放在同一组里比较。每一组由独立的子代理处理。这样既能分而治之，也能并发审查，在大型改动中保持相对稳定。

系统还会根据文件类型和项目路径，匹配适用的审查规则。这样，大模型不必同时面对一大堆无关要求，而是只关注当前文件真正需要检查的问题。内置规则覆盖多种语言和常见缺陷，包括空指针、线程安全、跨站脚本攻击和 SQL 注入等问题。

此外，评论定位和评论复核也由独立模块处理。前者尽量确保意见准确落在对应代码行上，后者重新检查评论内容，减少不准确或低价值的反馈。

第二部分才是大模型代理。它主要负责动态判断和补充上下文。例如，模型可以决定是否需要读取完整文件，是否要搜索某个函数的调用位置，或者是否要检查其他改动文件。项目还为代码审查专门优化了提示词和工具集合。这些工具不是简单照搬通用代理，而是依据大规模生产环境中的工具调用记录进行筛选，包括不同工具的使用频率、重复调用情况，以及新增工具对整个调用链的影响。

一句话概括，这套设计不是让大模型随意探索，而是先由工程流程规定审查边界，再让模型在边界内做复杂判断。

项目公布的基准测试也体现了这种取舍。测试数据来自五十个流行的开源仓库，包含二百个真实的合并请求，覆盖十种编程语言。八十多名资深工程师参与交叉验证，共标注了一千五百零五个真实问题。

按照项目公布的结果，在使用相同底层模型时，Open Code Review 的准确率和 F 一分数明显高于通用代理，平均消耗的令牌数量大约只有后者的九分之一，完成审查也更快。

这里需要理解三个指标。准确率表示，工具报告的问题中，有多少确实是真缺陷。准确率越高，开发者需要处理的误报越少。召回率表示，所有真实缺陷中，有多少被工具发现。召回率越高，漏掉的问题越少。F 一分数则综合考虑准确率和召回率。

Open Code Review 的召回率低于通用代理。这不是项目方隐瞒的缺点，而是明确选择的权衡：它更重视少报错、少制造噪声，即使代价是可能漏掉更多问题。这个取向适合不希望被大量可疑警告淹没的团队，但如果目标是尽可能找出所有潜在问题，就要清楚它的限制。

在使用上，Open Code Review 是一个命令行工具，命令简称 OCR。它要求 Git 版本不低于二点四一。安装后，需要配置一个大模型服务和具体模型，也可以接入自定义服务。完成配置后，OCR 可以审查当前工作区的未提交改动、两个分支之间的差异，或者某一个提交。中断的任务可以从已有会话继续执行，结果也能保存为结构化的 JSON 文件。

它还提供委托模式。在这种模式下，OCR 只负责选择文件和匹配规则，真正的审查由已有的人工智能编程代理完成，因此不必再为 OCR 单独配置大模型密钥。项目也提供了面向 Claude Code、Codex、Cursor、Kimi Code 和 OpenCode 等工具的集成，并能接入 GitHub Actions、GitLab 持续集成和 Gerrit 等研发流程。

最值得记住的是，Open Code Review 的价值不只是换了一个更好的提示词，而是把代码审查拆成了两类任务。文件选择、规则匹配和评论定位，交给可预测的工程系统；上下文理解和缺陷判断，交给大模型。它追求的也不是发现尽可能多的问题，而是在速度、成本和误报之间，优先提供更精准、更容易采用的审查意见。

## 深度解读（1）

### 2026-09-18 04:24:32

#### AI 代码审查的关键，不是让模型更聪明，而是限制它犯错的方式

Open Code Review 最值得关注的，并非“阿里开源了一款 AI 代码审查工具”，而是它把一个已在生产环境反复出现的问题说清楚了：**通用 Agent 的灵活性，恰恰会破坏代码审查所需要的完整、准确与稳定。**

纯语言驱动的 Agent 容易漏看大变更中的部分文件，评论位置可能漂移，质量还会随着提示词的细微变化而波动。Open Code Review 的解决办法不是继续优化一段万能 Prompt，而是把任务拆成两类：文件选择、关联文件分组、规则匹配、评论定位等不容出错的步骤，交给确定性程序；只有理解上下文、搜索代码和判断缺陷，才交给模型。

##### 混合架构的价值，是缩小模型的自由度

这种设计本质上是在为 Agent 建立“轨道”。例如，多语言资源文件会被自动放进同一审查单元；不同文件只加载适用规则；大变更被拆成隔离上下文的子任务并行执行。模型不必自行决定“看哪些文件、带哪些规则、结果贴在哪里”，因而能把有限上下文集中在真正需要推理的地方。

项目声称，在使用相同底层模型时，其精确率和 F1 高于 Claude Code 一类通用 Agent，Token 消耗约为后者的九分之一，但召回率更低。这是一个合理而重要的取舍：**代码审查不是缺陷越多越好，而是每条反馈都在消耗开发者的注意力。**误报过多后，团队会像忽略噪声告警一样忽略 AI 评论。对提交前审查而言，高精确率可能比追求理论上的全覆盖更有产品价值；对安全审计或关键系统，则不能接受同样的召回损失。

##### 真正可迁移的是“确定性外壳”

这套思路不只适用于代码审查。凡是要求覆盖完整、引用准确、过程可追踪的 AI 产品——合同审阅、财务核查、客服质检、医疗文档检查——都不应让模型同时负责流程编排与专业判断。更可靠的设计是：程序保证输入集合、规则适用范围、结果定位和状态管理，模型只处理难以形式化的判断。

这也提示了一个产品机会：Agent 应用的壁垒未必在模型或 Prompt，而可能在**任务分解、专用工具、评测集和反馈闭环**。Open Code Review 甚至支持“委托模式”，由它负责选文件和解析规则，再让外部编码 Agent 执行推理，说明工作流控制层可以与模型解耦。

当然，现有性能结论主要来自项目方自建的 AACR-Bench：50 个开源仓库、200 个 PR、1,505 个标注问题，虽经 80 多位工程师交叉验证，仍需独立复现；阿里内部“数万开发者、数百万缺陷”的使用规模，也不能直接证明开源版本在不同技术栈中同样有效。但它提出的判断值得保留：**当 Agent 进入严肃生产流程，进步不只来自更强模型，更来自明确规定哪些事情根本不该由模型决定。**

## 深度解读-口播（1）

### 2026-09-30 11:51:53

人工智能做代码审查，难点不只是看懂代码，还在于能不能稳定地审完该看的文件，把问题定位到正确的代码行，并且少报一些并不存在的缺陷。阿里开源的 Open Code Review，核心思路就是：用确定性的工程流程约束审查过程，再让大语言模型负责理解代码和动态判断。

按照项目介绍，这款工具源自阿里集团内部的官方人工智能代码审查助手。过去两年，它服务过数万名开发者，识别出数百万个代码缺陷，之后被孵化成开源项目。这些规模数据来自项目方的介绍，可以作为背景，但理解它的价值，更重要的是看它怎样工作，以及它选择了什么取舍。

先看一个常见场景。你提交了一批代码改动，让通用人工智能编程助手帮忙审查。它可能发现一些有价值的问题，但也可能只看了部分文件，或者指出的问题是对的，标注的文件和行号却不对。提示词稍微调整一下，审查结果还可能出现明显波动。

项目方认为，这些现象背后有一个共同原因：如果整个审查流程都靠自然语言来驱动，就缺少硬约束。模型既要决定看哪些文件，又要寻找上下文、选择规则、判断缺陷，还要给出准确位置。所有任务混在一起，过程就容易失去稳定性。

Open Code Review 的做法，是把流程控制和智能判断拆开。

需要稳定执行的部分，交给程序逻辑。例如，确定哪些改动文件需要审查，哪些文件应该过滤。这里保证的是文件选择和流程覆盖，并不等于保证发现所有缺陷。

接着，工具会把有关联的文件放进同一个审查单元。比如，一个项目同时修改了英文和中文的消息资源文件，把两份文件一起看，比各自孤立地看，更容易理解这次改动。不同审查单元由独立的子代理处理，各自拥有隔离的上下文，也可以并发执行。这样，大批量改动就不必全部挤进同一段模型上下文。

规则的选择也不完全交给模型临场决定。工具会根据文件特征，匹配适用的审查规则，减少无关信息。它内置了多语言规则，涉及空指针异常、线程安全，以及跨站脚本和数据库查询注入等问题。后两类都是安全风险：前者涉及网页执行不可信脚本，后者涉及不可信输入改变数据库查询的含义。

生成意见后，还有独立的评论定位和复核模块，用来改善问题位置和评论内容的准确性。

这套分工的关键是：不是让模型独自管理全部流程，而是先用工程逻辑搭好轨道，再让模型在轨道内发挥判断能力。

不过，流程被约束，并不意味着模型只能机械地检查几行改动。

Open Code Review 会读取版本管理系统中的代码差异，再由具备工具调用能力的智能代理展开审查。代理可以读取完整文件，搜索代码库，也可以查看其他改动文件，补齐判断所需的上下文。

例如，一处修改是否有问题，可能取决于别处怎样调用它。只看改动的几行，信息可能不够；能够主动查找相关代码，才有机会做更深入的判断。

项目还针对代码审查优化了提示词和工具集。按照项目方的说明，工具集的设计参考了大规模生产环境里的调用记录，包括哪些工具常用、哪些调用反复发生，以及新增工具怎样影响整个调用链。目标不是工具越多越好，而是让审查过程更稳定、更可预测。

那么，这样的设计效果如何？

项目公布了一套真实代码审查基准，取自五十个热门开源仓库中的两百次真实代码合并请求，覆盖十种编程语言，并由八十多位资深工程师交叉验证。

按照项目报告，在使用相同底层模型时，Open Code Review 相比 Claude Code 这样的通用代理，准确率和综合评分更高，审查更快，模型消耗的令牌数量大约只有对方的九分之一。令牌可以理解为模型处理文本时使用的计量单位，它会直接影响模型接口的使用成本。

不过，这个结果有一个必须一起记住的前提：它的召回率更低。

准确率，关注的是“报出来的问题，有多少是真的”。召回率，关注的是“实际存在的问题，有多少被找到了”。一个工具可以少报错，但同时漏掉更多真实问题，这两个指标并不矛盾。

项目明确表示，这是有意做出的取舍：更重视报告的可信度，减少开发者需要排查的误报，而不是尽可能多地报出可疑问题。项目所说的综合评分，就是同时考虑准确率和召回率的指标。因此，“综合表现更好”，不能听成“发现的缺陷更多”，也不能听成“不会漏报”。

实际使用上，这款工具主要有两类审查范围。日常开发时，可以检查工作区里的改动、某个分支相对主分支的变化，或者单次提交。面对不熟悉的代码库，也可以扫描完整文件或目录，不必依赖有意义的改动记录。

模型的使用方式也有两种。默认模式下，由 Open Code Review 调用你配置的大语言模型，它支持与 OpenAI 和 Anthropic 兼容的接口。另一种是委托模式：工具负责文件选择和规则解析，具体审查交给你正在使用的人工智能编程助手，使用那个助手自己的模型，因此不需要再为 Open Code Review 单独配置模型接口密钥。

最值得记住的是，这个项目的重点不只是让模型读代码，而是用工程约束把代码审查变成更稳定的流程。它强调准确定位、较少误报和较低消耗，但接受了召回率较低的代价。理解这层取舍，才能正确看待它的基准成绩，也才能判断它是否符合你的审查需求。
