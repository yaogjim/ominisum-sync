## 分析要点

- **核心高价值点**：父代理只做计划、分派、审查和升级，不写代码，以避免长项目中的上下文坍塌。
- **留存建议**：长期保留（包含可复用的大型AI代理工程编排模式、风险分阶段方法和成本数据，适合作为后续项目设计参考。）

**知识要点**

- 大型AI代理项目应先并行审计，并将范围、波次和未知项固化到单一清单中。
- 按风险而非便利性安排执行顺序，把不可逆的生产数据和数据库模式变更放在充分验证之后。
- 并行子代理必须拥有明确且不重叠的文件边界，以降低冲突和协调成本。
- 每个阶段之间应设置回归测试、备份检查、Git标签等安全门。
- 不可逆决策由人类批准，代理负责提出建议和执行已批准任务。

**行动项**

- 在自己的AI代理项目中尝试建立父编排器加子执行器的职责分离模式。
- 为大型迁移任务先创建审计清单，并规定未知项必须升级而非猜测。
- 将任务按风险分波，并在每波之间设置自动化回归测试和备份检查。
- 为并行代理任务明确指定不重叠的文件范围和完成标准。
- 把项目中的范围裁定、异常处理和文档更新沉淀为可复用模板。

**Ryan Carson**

### 如何使用 Fable 编排一个拥有 40 个子代理的大型项目

Last week at

[@HelloUntangle](https://x.com/@HelloUntangle) we completed the largest and riskiest engineering program in our history.

- 834个文件
- 生产数据变异
- 数据库模式更新
- 31 个 PR
- 周五开始 -&gt; 周一完成
- 零生产环境事件

所有操作都在一个 Fable 父编排器会话中。

One parent

[@DevinAI](https://x.com/@DevinAI) session planned the work, spawned forty child sessions to execute it, enforced regression gates and backup checks between phases, and surfaced only the decisions that genuinely required an owner: scope rulings and go/no-go on irreversible steps.

What made this work is a set of program-management patterns that would improve any large migration.

这就是我们如何做到的...

#### 架构：一个编排器，多个工作节点

- One parent session owned the program end to end. Its only job was to plan, spawn child sessions, review their output, sequence the phases, and escalate to me when a decision needed a human. It wrote zero code.
- \~40 child sessions did every piece of actual work: eleven parallel audit sessions in Phase 0, execution sessions for each wave, and dedicated gate-runner sessions whose only job was to run regression suites.

The split matters because the failure mode of long-running projects — AI or human — is context collapse: the thing doing the work gradually loses the plot of the overall program.

保持父组件为纯编排器可使其上下文保持干净；它负责持有计划、范围决策以及每一波的状态。每个子组件会获得一个全新且专注的上下文，且仅负责一项任务。

#### 使其成功的七种模式

首先进行审计，然后将审计发现固定在一个单一的清单中

阶段 0 是十一并行审计会话，每个覆盖代码库的一个部分：应用路由、API 路由和定时任务、数据库模式、共享库和工作流、脚本和文档。他们的发现被整合成一个文件并提交到代码库。

该清单为每个代码单元分配一个判定和一个波数。两条规则使其功能强大：

- No worker re-litigates scope. Every execution prompt said, in effect: the manifest is the source of truth. Without this, each of forty sessions would derive its own opinion about what is in scope — and they would disagree.
- UNKNOWN means stop and ask. Anything the audits were silent on was explicitly marked unknown, with an instruction: do not guess; get a ruling. Owner rulings were recorded directly into the manifest, so later sessions inherited them.

2\. 按风险而非便利性安排工作

这些波被按照从最安全到最不可逆的顺序排序。

Production data changes (Wave 5) come before schema changes (Wave 6), and both come only after every code path that touched the affected tables was verifiably updated. By the time the migrations ran, nothing could still be depending on the old state.

3\. 文件不相交的边界使并行性安全

在一个波中，子会话并行运行——一个波中有四个会话同时处理树的不同部分。规则是：每个提示都包含明确的文件边界，且这些边界不重叠。没有合并冲突，没有两个代理编辑同一个文件，子会话之间完全不需要协调。

This is classic task decomposition — the same thing you'd do splitting work across engineers — but agents need it stated explicitly, in the prompt, every time.

4\. 波之间的安全门

没有波浪开始，直到前一个波浪通过了一个门。这些门本身就是子会话：

- A browser-driven, end-to-end regression suite covering the platform's core customer workflow ran after Wave 2 and again after Waves 3–4, on a fresh isolated database branch.
- 在进行任何生产数据变更之前：一个专门的会话审计了我们的数据库备份清单（数量、日期范围、保留期），并且我们创建了一个新的时间点快照。
- 生产步骤本身先进行了试运行，生成了行数用于所有者审批，并在执行后重新验证了行数。
- git 标签标记每一行已更改内容的恢复点。

当某个门发生故障时，它会生成一个范围限定的修复会话。例如，回归测试套件捕获了一个面向客户的流程，该流程因一个过于急切的变更而被破坏；一个修复会话在几小时内将其恢复。这就是系统的作用——该门将原本可能由客户报告的缺陷转化为当日修复。

5\. 人类批准；代理提议

我从未在这个项目中编写过代码、执行过迁移或运行过生产脚本。但每个不可逆转的步骤都需要我明确批准：每次合并到主分支、生产数据变更、模式迁移，以及对未知范围事项的每次裁定。

破坏性操作的模式：代理方提出一份清单，人类批准该清单，然后代理方严格执行该清单。生产会话在接触任何内容之前，先生成了它将要接触的精确行列表。我批准了一份具体的清单，而非模糊的意图。

6\. 意外情况升级协议

当现实与指示不符时，孩子们被告知该怎么做：停止，向家长报告，不要即兴发挥。真实案例：

- 被审计标记为安全的模块，结果发现在其他地方存在活跃的依赖项 → 子模块标记了该问题，该单元被降级到后续波次，并记录了相关的纠缠情况。
- 第二轮审计推翻了五个完整领域的第一轮判决 → 这些推翻被作为明确的覆盖写入清单，而不是由遇到这些情况的任何会话临时解决。

上级将这些意外情况纳入了计划。一线员工从未做出范围决策。

7\. 保持营地更干净：教系统识别变化

Wave 7 may be the most underrated phase. After the change shipped, sessions rewrote our AGENTS.md, repo skills, and agent knowledge base to describe the new architecture — so every future agent session starts from the truth, not from stale instructions. If your engineering is agent-driven, your documentation is load-bearing infrastructure. 第 7 波可能是最被低估的阶段。变更发布后，会话重写了我们的 AGENTS.md、仓库技能和代理知识库，以描述新架构——因此每个未来的代理会话都从事实出发，而非过时的指令。如果你的工程是代理驱动的，那么你的文档就是承重基础设施。

#### 它的成本是多少

每个程序中的会话都被标记了，因此分类账是完整的：一个父会话和三十九个子会话，所有会话都在 Devin 的 Ultra Agent 上，时间从周五下午到周一上午。这些是来自我们使用情况仪表板的实际计量成本。

分析中，三件事很突出。

1. 整个十二环节审核阶段产生的清单成本低于90美元——这是我们买过的最便宜的保险。
2. 最昂贵的项目正好出现在需要深入思考的地方：纠缠手术（299美元）和回归门（245美元），这两个项目确保了一切都合规。
3. 风险最高的步骤——生产数据变更——花费了15美元，因为在它运行时，所有风险都已经被消除了。

注：整个项目本可以更实惠，如果 Devin 允许我为子代理选择不同的模型。大部分编码工作使用 gpt 5.5 或 opus 4.8 本可以成功完成。指导 Fable 选择合适的模型以匹配子代理任务会很简单。

尽管如此：1000美元对于我们完成的工作来说简直便宜得难以置信——而且完成和验证的速度之快——哇。

#### 核心要点

标题并不是 AI 编写了大量代码——现在，执行明确指定变更的智能体已是基本要求。

标题是，项目管理本身被下放了：分解、排序、并行化、门控和升级都在编排器内进行，而人工角色被简化为仅处理需要负责人的决策。

如果你打算尝试这个，窃取模式，而非工具：

1. 先审计；将发现结果固定在一份清单中，任何工人不得重新提起诉讼。

3. 为并行工作器明确提供不相交的文件边界。

5. 在进行破坏性变更之前，要求提供建议清单；批准清单，而非想法。
6. 在意外发生之前定义升级路径。
7. 作为项目的一部分更新你的文档和代理知识，而不是在项目之后。

##### 一句话总结

这不是 “AI 自动写了很多代码” 的故事，而是一次**用父代理做项目经理、子代理做执行者、测试和备份做安全门、人类做最终责任人**的大型工程编排实践。

##### 深度总结

###### 核心成果

- 834 个文件变更  
- 涉及生产数据变更、数据库 Schema 更新  
- 31 个 PR  
- 周五开始，周一完成  
- 约 40 个 AI 会话  
- 0 个生产事故  
- 总成本：约**$1,155**

###### 核心架构

| 角色 | 职责 |
|---|---|
| 父代理 | 只做计划、分派、审查、排序、升级，不写代码 |
| 子代理 | 只做单一任务，专注执行 |
| 人类 | 审批不可逆操作，裁定未知范围 |
| 测试 / 备份 | 作为阶段之间的安全门 |

关键点：  
**父代理保持上下文清洁，子代理保持任务聚焦。**

这样避免了大型项目常见问题：  
> 做着做着，执行者忘了全局目标，开始跑偏。

---

##### 七个关键模式

###### 1. 先审计，再固化清单

先让多个代理并行审计代码库，然后把结论合成一个统一清单。

清单决定：

- 哪些文件要改
- 哪些不改
- 哪些未知
- 属于哪一波次

规则：

- 子代理不能重新争论范围
- 遇到 UNKNOWN 必须停止并上报

**本质：先统一地图，再让队伍行动。**

---

###### 2. 按风险排序，不按方便排序

执行顺序不是 “哪个容易先做”，而是：

> 从最安全，到最不可逆。

大致顺序：

1. 审计与恢复点
2. 低风险代码变更
3. 复杂依赖拆解
4. 大量代码修改
5. 生产数据变更
6. 数据库 Schema 迁移
7. 依赖清理与文档更新

关键是：  
**生产数据和数据库结构这种不可逆操作，必须放在所有代码路径验证之后。**

---

###### 3. 并行必须靠 “不重叠边界”

同一波次中，多个子代理可以并行工作，但前提是：

- 每个代理只改指定文件
- 文件范围互不重叠
- 不允许互相抢同一个文件

这样避免：

- 合并冲突
- 互相覆盖
- 上下文混乱

**并行不是放任，而是切干净边界。**

---

###### 4. 每一波之间设置安全门

每波完成后，都要过关：

- 端到端回归测试
- 独立数据库分支验证
- 生产备份审计
- 快照创建
- Git 标签恢复点

如果测试失败，就生成专门的修复会话。

**安全门的价值：把客户会发现的问题，提前变成内部当天修复的问题。**

---

###### 5. 代理提议，人类批准

作者不写代码，也不跑迁移，但所有关键动作都需要人工批准：

- 合并主分支
- 生产数据变更
- Schema 迁移
- 未知范围裁定

**AI 可以执行，但责任不能外包。**

---

###### 6. 意外必须升级，不能即兴发挥

子代理遇到现实与指令不符时：

> 停止、报告、等待裁定。

比如：

- 原本以为无依赖，实际有依赖
- 第二轮审计推翻第一轮结论

这些都不让子代理临场决定，而是写回清单，统一继承。

**局部执行者不能擅自改变全局范围。**

---

###### 7. 项目结束前更新文档和代理知识

不是项目做完再补文档，而是把：

- 依赖说明
- agents.md
- 知识库
- 操作规则

作为项目本身的一部分更新。

**让系统下次更聪明，而不是只让这次侥幸成功。**

##### 深入浅出解读

可以把这个过程理解成盖一栋楼：

| 工程现场 | AI 编排 |
|---|---|
| 总包 | 父代理 |
| 分包队伍 | 子代理 |
| 施工图纸 | 审计清单 |

真正厉害的不是 “找了 40 个 AI 同时干活”，而是：

> 每个 AI 都只知道自己该干什么、不该干什么、遇到问题该找谁。

这才是大型 AI 工程的关键。

5. 每波之后必须有测试门  
6. 生产操作前必须有备份与快照  
7. AI 只提案，人类批不可逆动作  
8. 未知情况必须升级  
9. 文档和知识库同步更新

##### 辩证思考

###### 积极意义

这篇文章真正展示的是：

> AI 编程正在从 “单点助手” 进入 “组织化劳动力” 阶段。

过去我们问 AI：

- 帮我写函数
- 帮我修 bug
- 帮我解释代码

现在开始变成：

- 帮我审计系统
- 帮我拆解项目
- 帮我并行执行
- 帮我跑门禁
- 帮我维护迁移秩序

这意味着工程能力的瓶颈，正在从 “会不会写代码” 转向：

> 会不会设计流程、边界、验证和责任机制。

---

###### 潜在风险

但这不是 “AI 可以放心接管工程” 的证明。

它成功的前提很强：

- 有完善测试
- 有备份机制
- 有清晰代码边界
- 有可分解任务
- 有人类持续审批
- 有足够强的工程纪律

如果清单错了，40 个代理会把错误放大。  
如果测试弱了，安全门只是摆设。  
如果边界切不清，并行只会制造混乱。  
如果人类不懂系统，审批就会流于形式。

---

###### 我的判断

这套方法的本质不是 “自动化”，而是：

> 用 AI 扩展执行力，用流程约束风险，用人类保留最终判断。

未来高级工程师的价值，可能不只是亲自写最多代码，而是能设计出：

- 好清单
- 好边界
- 好波次
- 好测试
- 好升级机制
- 好回滚路径

一句话：

> AI 让执行变便宜，但让架构、验证和责任更重要。

  - 制定计划与划分阶段
  - 启动子会话
  - 审查子会话结果
  - 安排执行顺序
  - 维护项目范围和各波次状态
  - 将必须由负责人决定的问题升级给人类
- **子会话负责实际工作**，包括审计、代码修改、迁移和运行回归测试。

这种拆分是为了避免大型长期项目中的“**上下文崩塌**”：执行者工作越久，越容易忘记整体目标。父代理始终保留干净的全局上下文，而每个子代理只处理一项明确任务。

> 文章前文称约 40 个子会话；最终账单记录为 **1 个父会话 + 39 个子会话，共 40 个会话**。

---

##### 二、使项目成功的七种模式

###### 1. 先审计，再将结论固定到唯一清单

项目的第 0 阶段启动了 **11 个并行审计会话**，分别检查：

- 应用路由
- API 路由与定时任务
- 数据库模式
- 共享库和工作流
- 脚本与文档

所有发现被整合进一个清单文件，并提交到代码库。清单为每个代码单元标注：

- 是否属于修改范围
- 应在哪一波执行
- 是否存在未知风险

清单遵守两条核心规则：

1. **子代理不得重新讨论范围**  
   清单是唯一事实来源，否则约 40 个会话可能各自判断范围并产生冲突。

2. **UNKNOWN 表示停止并询问**  
   审计未覆盖的事项不能猜测，必须由负责人裁定；裁定结果再写回清单，供后续代理继承。

---

###### 2. 按风险安排波次，而不是按便利性安排

项目按照“**从安全、可逆到高风险、不可逆**”的顺序推进：

| 波次 | 工作内容 | 风险 |
|---|---|---|
| 0 | 审计、生成清单、创建 Git 恢复标签 | 无 |
| 1 | 修改已确认没有活跃依赖的部分 | 接近零 |
| 2 | 处理共享基础设施中的复杂依赖 | 中等 |
| 3–4 | 完成大部分代码变更 | 中等 |
| 5 | 修改生产数据，包含模拟盘点与快照 | 高 |
| 6 | 数据库模式迁移 | 高 |
| 7 | 清理依赖、重写 `agents.md`、审计代理知识库 | 低 |

关键顺序是：

1. 先更新所有会访问相关数据表的代码路径；
2. 再修改生产数据；
3. 最后执行数据库模式迁移。

这样，等到迁移真正运行时，系统中已经没有代码依赖旧状态。

---

###### 3. 用互不重叠的文件边界实现安全并行

同一波次可以让多个子代理并行工作，例如四个会话同时处理代码树的不同区域，但必须满足：

- 每个提示词都明确列出允许修改的文件；
- 不同子代理的文件范围互不重叠；
- 两个代理不能同时修改同一文件。

因此项目几乎不需要子代理之间相互协调，也不会产生合并冲突。

这本质上与工程团队拆分任务相同，只是面对 AI 代理时，必须在每次任务提示中明确写出边界。

---

###### 4. 在每个波次之间设置安全门禁

前一波未通过门禁，下一波就不能开始。门禁本身也由专门的子代理执行。

主要措施包括：

- 在第 2 波以及第 3–4 波之后，运行浏览器驱动的端到端回归测试；
- 测试覆盖平台最核心的客户工作流；
- 每次测试都使用全新、隔离的数据库分支；
- 修改生产数据前，专门审计数据库备份：
  - 备份数量
  - 日期范围
  - 保留期限
- 在高风险操作前创建新的时间点快照；
- 使用 Git 标签为每一批代码变更建立恢复点。

如果门禁失败，父编排器会启动一个范围明确的修复会话。

**实际案例：**回归测试发现，一项过于激进的修改破坏了面向客户的流程。系统随即创建修复会话，并在数小时内恢复功能，把原本可能由客户报告的问题变成了当天即可解决的缺陷。

---

###### 5. 代理提出方案，人类批准不可逆操作

项目负责人没有亲自：

- 编写代码
- 执行迁移
- 运行生产脚本

但以下操作都必须获得人类明确批准：

- 每次合并到主分支
- 生产数据修改
- 数据库模式迁移
- 对未知范围事项的裁定

核心原则是：**代理负责准备和提议，人类负责批准不可逆步骤。**  
审批对象应是具体的变更清单，而不是模糊的想法。

---

###### 6. 提前定义异常升级协议

所有子代理都收到明确指令：

> 如果现实情况与任务说明不一致，立即停止、向父代理报告，不要自行发挥。

文章给出两个真实案例：

- 一个原本被审计为“安全”的模块，后来发现仍被其他地方使用。子代理没有直接处理，而是上报问题；父代理将其移到更晚的波次，并把依赖关系记录进清单。
- 第二轮审计推翻了第一轮对 **5 个完整领域**的判断。新结论被作为明确覆盖项写回清单，而不是由后续遇到问题的代理临时决定。

因此，**一线子代理不做范围决策，父编排器负责吸收异常并调整计划。**

---

###### 7. 把文档和代理知识维护纳入项目

项目最后不仅清理代码和依赖，还同步完成：

- 依赖裁剪
- 重写 `agents.md`
- 审计并更新代理知识库

目的不是只完成一次迁移，而是让文档和代理认知与新系统状态保持一致，避免后续代理继续依据过时信息工作。

---

##### 四、核心经验

这次项目的重点不是“AI 一次写了多少代码”，而是如何像管理大型工程团队一样管理代理：

- **先审计，再执行；所有结论统一写入唯一清单。**
- **按风险划分波次，把不可逆操作放到最后。**
- **通过互不重叠的文件边界实现安全并行。**
- **每个波次都必须经过真实回归测试和备份检查。**
- **代理提出具体方案，人类批准关键和不可逆操作。**
- **提前规定异常升级路径，禁止子代理自行猜测。**
- **把文档、依赖和代理知识库更新视为项目的一部分。**

最终，真正可复用的不是某个特定工具，而是这套“**纯编排父代理、专职子代理、统一清单、风险分波、阶段门禁和人工决策**”的项目管理方法。

## 口播总结（1）

### 2026-08-03 01:22:33

#### 这次大型项目做了什么

这篇材料讲的是，如何用 Fable 编排一个包含大约四十个智能体会话的大型工程项目。你将听到三件事：它是怎样分工的，怎样控制并行开发和高风险变更，以及这套方法实际花了多少钱、为什么能够做到零生产事故。

上周，HelloUntangle 完成了公司历史上规模最大、风险最高的一次工程项目。

项目涉及八百三十四个文件，包含生产数据变更、数据库模式更新，以及三十一个合并请求。从周五开始，到周一完成。整个过程没有发生生产环境事故，而且所有操作都在一个 Fable 父编排器会话中完成。

这个父会话负责规划工作，并启动了大约四十个子会话来执行任务。它还负责在不同阶段之间设置回归测试和备份检查，只把真正需要人类决定的问题交给项目负责人，比如范围怎么定，以及不可逆操作要不要继续。

接下来，看看这套系统是怎样组织起来的。

#### 一、一个父编排器，多个专注的工作节点

核心结论是：父会话只负责管理项目，不直接写代码；真正的执行工作交给多个子会话。

通俗地说，父会话像项目总指挥。它负责制定计划、启动子任务、检查结果、安排先后顺序，并在需要人类判断时发出升级请求。它不承担具体编码工作，因此始终保留对全局计划和项目状态的清晰认识。

大约四十个子会话则负责实际工作。比如，第一阶段有十一轮并行审计，后面每一波变更都有专门的执行会话，还有一些会话只负责运行回归测试。

这样拆分，主要是为了避免一个常见问题，叫作“上下文坍缩”。意思是，一个长期执行任务的智能体，做着做着会越来越专注于眼前的小问题，最后忘记整个项目的目标、范围和当前进度。

父会话保持纯粹的编排职责，就能持续掌握计划、范围决策和每一波工作的状态。每个子会话则获得一个全新的、干净的上下文，只处理一项明确任务。这样，整体视角和局部执行就不会互相干扰。

有了这个架构之后，项目主要依靠七种管理模式来控制风险。

#### 二、首先审计，再把结论固定进一份清单

第一个关键做法是：先审计，后执行；而且所有审计结果都要汇总到一份唯一的清单里。

项目的第一阶段，也就是阶段零，安排了十一轮并行审计。每轮审计负责代码库的一部分，包括应用路由、接口路由和定时任务、数据库模式、共享库和工作流，以及脚本和文档。

审计结果最后被整合成一个文件，并提交到代码库。这个文件就是项目清单。它为每个代码单元标记三件事：应该怎么处理、属于哪一波，以及当前的范围判断。

这份清单之所以重要，有两个原因。

第一，任何执行会话都不能重新讨论范围。所有执行提示都会明确说明：清单就是唯一依据。

如果没有这条规则，四十个会话可能会各自判断哪些内容属于项目范围，最后得出互相矛盾的结论。

第二，审计没有覆盖到的内容，要明确标记为“未知”。遇到未知，智能体必须停止并询问，不能自行猜测。

项目负责人作出的裁定，会直接写回清单。这样，后续会话就能继承同一个结论，而不是每次重新判断。

换句话说，清单把一次性的项目决策，变成了所有工作节点都能读取的共同事实。

#### 三、接下来，按照风险而不是便利性安排工作

第二个关键做法是：工作顺序按照风险排序，而不是按照“哪个任务更方便”来排序。

整个项目被拆成多个波次，从最安全的工作开始，逐渐推进到最不可逆的操作。

第一波主要是审计、建立清单，并创建 Git 恢复点，风险几乎为零。

第二波处理已经验证、而且没有活跃依赖的变更，风险接近于零。

第三波和第四波处理大部分代码变更，风险处于中等水平。

第五波才进行生产数据变更。第六波进行数据库模式迁移，这两步都属于高风险操作。

最后的第七波，处理依赖清理、代理说明文档，也就是 `agents.md` 的重写，以及代理知识库审计。虽然这些工作放在最后，但它们本身的风险相对较低。

这里有一个很重要的顺序：生产数据变更在数据库模式迁移之前，但两者都要等到相关代码路径全部更新并验证之后才能进行。

这样做的含义是，等数据库迁移真正开始时，就不会再有旧代码依赖旧的数据状态。

项目不是一上来就修改数据库，也不是先做最方便的任务，而是先把所有依赖旧状态的代码处理完，再进行不可逆的数据库操作。

#### 四、并行工作必须使用互不重叠的文件边界

第三个关键做法是：并行任务之间必须有清晰、互不重叠的文件范围。

在同一个波次里，多个子会话可以同时工作。比如，一个波次中可以有四个会话并行处理代码树的不同部分。

但每个提示词里都必须明确写出它能修改哪些文件，而且这些文件边界不能重叠。

这样就不会出现两个智能体同时修改同一个文件，也不会产生合并冲突。子会话之间也不需要频繁协调。

这其实和人类工程团队拆分任务的方式一样。区别在于，面对智能体时，文件边界不能只存在于管理者脑中，而要在每一次任务提示里明确写出来。

并行本身并不自动安全。只有当每个工作节点的范围足够清楚，而且彼此没有重叠时，并行才真正可控。

#### 五、更重要的是，每个波次之间都要设置安全门

第四个关键做法是：一个波次没有通过检查，就不能开始下一个波次。

这些安全门本身，也由专门的子会话负责执行。

项目在第二波完成后，以及第三、第四波完成后，都运行了由浏览器驱动的端到端回归测试。所谓“端到端回归测试”，就是模拟真实用户操作，检查平台最核心的客户流程是否仍然完整。测试使用的是一个全新的、隔离的数据库分支。

在进行任何生产数据变更之前，还有一个专门会话审计数据库备份清单。它检查备份数量、日期范围和保留期限，同时创建了一个新的时间点快照。

此外，每一波变更都会用 Git 标签标记恢复点。这样，如果后续发现问题，就有明确的回退位置。

这套安全门真正发挥了作用。一次回归测试发现，一个面向客户的流程被一个过于激进的变更破坏了。系统没有让问题继续向后传播，而是自动生成了一个范围明确的修复会话。几个小时内，流程就被恢复了。

也就是说，原本可能要等客户发现并报告的问题，被测试门提前捕获，并在当天完成修复。

#### 六、人类负责批准，代理负责提出方案

第五个关键做法是：让智能体提出方案，让人类批准不可逆的行动。

项目负责人在整个过程中没有写代码，没有执行数据库迁移，也没有运行生产脚本。

但所有不可逆的步骤，都需要他明确批准。这些步骤包括合并到主分支、修改生产数据、执行数据库模式迁移，以及对未知范围问题作出裁定。

这里的人机分工非常清楚。

智能体可以负责分析、编码、测试、整理建议，并说明风险。人类则保留最终的控制权，尤其是面对无法轻易撤销的操作时。

项目负责人批准的不是一个模糊的“想法”，而是一份已经准备好的执行清单。这样，审批对象更加具体，也更容易检查。

#### 七、遇到意外时，必须停止并升级

第六个关键做法是：提前规定意外情况的处理方式。

当现实情况和原始指示不一致时，子会话被明确告知三步规则：停止，向父会话报告，不要自行发挥。

项目中就出现过这样的例子。

审计最初判断某个模块可以安全处理，但执行过程中发现，它在其他地方还有活跃依赖。子会话没有擅自继续，而是标记问题，把这个代码单元降级到后面的波次，并记录相关依赖关系。

还有一次，第二轮审计推翻了第一轮对五个完整领域的判断。项目没有让某个执行会话临时决定怎么处理，而是把这些新结论作为明确的覆盖规则写回清单。

这样，意外情况会被纳入上层计划，而不是由一线执行会话临时作出范围决策。

这套规则的核心，是让子会话拥有“发现问题”的能力，但不让它们拥有“擅自改变项目范围”的权限。

#### 八、最后，把文档和代理知识一起更新

第七个关键做法是：项目结束时，不只留下代码，也要更新项目知识。

这次最后一个波次包含依赖清理、代理说明文档重写，以及代理知识库审计。

这意味着，系统不仅要完成眼前的迁移，还要把这次项目中发现的变化、依赖关系和操作规则，整理回文档和知识库。

这样，下一次智能体参与项目时，能够识别已经发生过的变化，而不是继续依据过时信息工作。

这就是“保持营地更干净”的含义：项目完成后，代码、文档和代理知识都应该比开始时更清楚。

#### 九、这套方法实际花了多少钱

接下来看看成本。

所有会话都被标记和记录下来，因此项目有一份完整账目：一个父会话和三十九个子会话，总共四十个会话。它们都运行在 Devin 的 Ultra Agent 上，时间跨度从周五下午到周一上午。

整个项目的总成本是 1155.38 美元。

其中，负责多日规划的父编排器花了 115.26 美元。

阶段零的两轮审计和清单合成，一共十二个会话，花费 85.56 美元。这个阶段的成本低于九十美元，但它承担了后续风险识别和范围统一的工作，因此项目方把它看作非常便宜的保险。

第一波花费 37.55 美元。

第二波，也就是处理复杂依赖关系的“纠缠手术”，花费最高之一，是 299.34 美元。第三、第四波的回归检查和修复花费 244.69 美元。

这两个部分最贵，原因也很直接：它们需要更深入地分析依赖关系，并用真实测试确认系统没有被破坏。

第三、第四波本身的代码变更花费 130.84 美元。

第五波的生产数据变更，以及备份审计，一共花费 15.20 美元。

第六波的数据库模式迁移花费 118.83 美元。

第七波的依赖清理、文档和知识库工作，再加上最终检查，花费 96.64 美元。

另外，还有一次基础设施修复，花费 11.47 美元。

这里最值得注意的是：风险最高的生产数据变更，反而只花了 15 美元。

这并不是因为生产变更天然简单，而是因为在它开始之前，代码依赖已经处理完，备份已经审计，时间点快照也已经创建，前面的安全门都已经通过。换句话说，大部分风险是在更早的阶段被消除了。

项目负责人还提到，如果 Devin 允许父会话为不同的子代理选择不同模型，整体成本本来可以更低。大部分编码任务，使用成本更低的模型也可能完成。让 Fable 根据子任务类型选择合适模型，也会相对容易。

#### 十、最值得记住的几个结论

最后，回顾这次项目最重要的五点。

第一，重点不是“让人工智能一次写出大量代码”，而是把大型项目拆成明确、可验证、可回退的任务。执行明确变更的智能体，已经只是基础能力，真正困难的是项目编排。

第二，先审计，再把结果固定在一份唯一清单中。所有执行会话都以清单为准，遇到未知就停止询问，不能各自重新判断范围。

第三，按照风险安排波次。安全的工作先做，不可逆的生产数据和数据库变更最后做。

第四，并行工作必须有不相交的文件边界；每个波次之间都要经过真实回归测试、备份审计和恢复点检查。

第五，代理负责提出和执行方案，人类保留对范围和不可逆操作的最终批准权。面对意外时，智能体要停止并升级，而不是自行发挥。

这套方法的价值，不只在于用了多少个智能体，更在于它把一个复杂项目变成了有计划、有边界、有检查点，也有人类最终把关的执行流程。

## 深度解读（1）

### 2026-09-18 00:36:30

#### 40 个代理并不意味着更大自治，而是更严格的工程控制

这次迁移最值得关注的，不是 AI 在一个周末修改了 834 个文件、提交 31 个 PR，而是团队把一个高风险工程项目改造成了**可审计、可暂停、可回滚的状态机**。父代理不写代码，只维护计划、状态和决策；约 40 个子代理各自完成边界明确的任务。生产数据与数据库模式变更被放到最后，最终没有出现生产事故。

这不是“一个更聪明的代理完成大项目”，而是**通过限制每个代理的自由度，获得整体可控性**。

##### 真正的核心资产是清单，而不是提示词

十一轮并行审计的结果被固化为一份清单：每个代码单元都有范围判断、执行波次和风险状态。执行代理不能重新讨论范围；审计未覆盖的事项必须标记为 `UNKNOWN`，停止并请求裁决。人类做出的决定再写回清单，供后续代理继承。

这解决了多代理系统中一个常被低估的问题：不同代理即使能力相近，也会对范围、依赖和优先级形成不同理解。仅靠共享一段长提示，项目越久，分歧越大。清单则把“项目记忆”从会话上下文转化为版本化的外部事实。

这套机制同样适用于人类团队。它的价值不是让所有人掌握更多背景，而是明确：**哪些事实已经确定，哪些决定不得重复争论，哪些未知必须升级。**

##### 并行能力来自任务独立，而不是代理数量

每个并行代理都获得不重叠的文件边界，因此无需彼此协调，也没有合并冲突。波次之间设置真实关卡：端到端回归测试、隔离数据库、备份审计、时间点快照和 Git 恢复标签。某个关卡发现客户流程被破坏后，系统没有继续推进，而是生成范围有限的修复任务。

因此，40 个代理只是表象。真正允许并行的，是提前完成了依赖识别和边界设计。若代码高度耦合、测试不能代表真实流程，增加代理反而会放大冲突和错误。**代理编排首先是系统可分解性问题，其次才是模型能力问题。**

成本分布也印证了这一点：总费用约 1155 美元，前期审计不到 90 美元；最贵的是纠缠依赖处理和回归验证。生产数据变更本身只花了 15 美元，因为风险已经在执行前被逐步消除。衡量 AI 工程效率时，不能只看“生成代码多少钱”，更应该看发现依赖、验证正确性和控制不可逆操作的成本。

##### 工具机会在“程序控制面”，但案例仍需谨慎外推

现有代理产品多以会话为中心，而这类项目真正需要的是程序级控制面：机器可读的范围清单、任务边界检查、阶段门禁、人工审批、回滚证据、决策沿袭，以及按任务选择不同成本模型。它更像 CI/CD、工作流引擎和项目治理系统的结合，而不只是一个聊天界面。

不过，这仍是团队自述的单次成功案例：没有提供人工方案的时间与成本基线，“零事故”也不能证明没有延迟暴露的问题。其成功还依赖成熟的回归测试、备份能力和足够清晰的代码边界。真正值得复用的判断因此不是“40 个代理可以替代一个团队”，而是：**当工作能被外部状态描述、按风险排序并由证据逐阶段放行时，代理规模化才可能安全；否则，多代理只是更快地产生不可控变化。**
