## 正文

**Leo｜一个人 + AI**

今天排查了一个诡异的问题：最近 Opus 4.8 用起来总觉得"不对劲"，回复质量飘忽，偶尔提到一些我没问过的东西。

查了半天，发现问题出在我自己身上——我写的 17 个 Hook 脚本一直在往模型的对话上下文里灌垃圾。

Claude Code 的 Hook 有两条输出通道。一条是模型能看到的，一条是只有你终端能看到的。大部分人写 Hook 的时候不会注意到这个区别，默认的输出方式恰好走的是"模型能看到"那条。

结果就是：你每调用一次工具，Hook 就往模型的上下文里塞一条它根本不需要看的提醒。我的情况是单个对话被注入了 280 次，其中有一个计数器 bug 让模型以为"本 session 已经 21810 次工具调用了"。

模型不是变笨了，是在一堆你自己注入的噪音里挣扎。

修法就一行，把 Hook 里的 \`echo "xxx"\` 改成 \`echo "xxx" &gt;&amp;2\`，从"模型能看到"切到"只有终端看到"。

如果你写了自定义 Hook 又觉得模型表现变差了，先查这个。

## 解读（1）

### 2026-06-25 04:04:46

##### 一、深度总结

这篇内容的核心结论很直接：

> **模型“变差”未必是模型本身的问题，可能是你的工具链在悄悄污染上下文。**

作者排查 Opus 4.8 表现异常后发现，问题根源不是模型退化，而是自己写的 **17 个 Hook 脚本**在反复把无关信息写进了模型可见的上下文里。  
结果是：

- 每次工具调用都会额外注入噪音；
- 单个对话被注入了 **280 次**；
- 其中还有一个计数器 bug，让模型误以为本 session 已经有 **21810 次工具调用**。

真正的修复很简单：

```bash
echo "xxx" >&2
```

把输出从 **模型可见** 切到 **终端可见**，问题就解决了。

---

##### 二、深入浅出解读

你可以把模型想成一个正在认真做题的人。

但现在发生的事情是：

- 你每点一次“计算器”，
- 旁边就有人不停往他耳朵里塞废话，
- 还反复提醒他“你已经做了两万多道题了”。

那他当然会：

- 回答飘忽；
- 记忆混乱；
- 偶尔扯出你根本没问的东西。

所以这件事的本质不是“AI 失灵”，而是：

> **上下文被污染了。**

而 `stdout` / `stderr` 的区别，就像：

- `stdout`：模型能看到的广播；
- `stderr`：只给你自己看的日志。

很多人写 Hook 时默认用了前者，等于把“调试信息”误当成“输入内容”喂给了模型。

---

##### 三、辩证思考

###### 1. 这不是模型无能，而是系统设计的边界问题
AI 的表现，很大程度取决于你给它什么输入。  
**输入噪音越大，输出越不稳定。**

###### 2. 但也不能全怪用户
这说明工具链的默认行为不够安全。  
如果一个简单的 Hook 就能把上下文污染到这种程度，说明：

- 可观测性不够清晰；
- 默认输出通道容易误用；
- 开发者很容易在“以为只是日志”时，实际上喂了模型。

###### 3. 真正重要的能力，不只是会用 AI，而是会“管住 AI 的环境”
高阶使用 AI，拼的不只是提示词，而是：

- 上下文管理；
- 工具输出隔离；
- 垃圾信息清理；
- 定期检查链路污染。

---

##### 四、一句话结论

> **当 AI 变笨时，先别急着怪模型，先查是不是你自己把噪音喂给了它。**

## 结构化（1）

### 2026-06-25 05:57:58

##### 主旨概括

作者排查了一个看似“模型变笨”的问题，最后发现根因不是 Opus 4.8 本身，而是自己写的 Hook 脚本把大量无关信息不断注入到了模型可见的对话上下文里。核心教训是：写自定义 Hook 时，要分清“模型能看到”和“终端才能看到”的输出通道。

##### 1. 问题现象：模型回复开始“不对劲”

- 作者最近发现，Opus 4.8 的回答质量忽高忽低，甚至会**主动提到一些自己没有问过的内容**。
- 这种表现让人误以为是模型能力下降了，但实际原因另有隐情。

##### 2. 根因：17 个 Hook 脚本把垃圾信息灌进了上下文

- 作者排查后发现，问题出在自己写的 **17 个 Hook 脚本**。
- Claude Code 的 Hook 有 **两条输出通道**：
  - 一条是**模型能看到**的；
  - 另一条是**只有终端能看到**的。
- 很多人写 Hook 时没注意这个区别，默认输出会进入**模型可见上下文**。
- 结果是：**每调用一次工具，Hook 就往上下文里塞一条模型根本不需要看的提示**。

##### 3. 具体影响：单个对话被注入 280 次，还出现计数器 bug

- 作者的案例里，**单个对话被注入了 280 次**。
- 其中还有一个**计数器 bug**，让模型误以为：
  - **“本 session 已经有 21810 次工具调用了”**
- 这会严重干扰模型判断，造成回答飘忽、上下文污染。

##### 4. 结论：不是模型变差，而是上下文被噪音污染

- 作者的判断是：**模型不是变笨了，而是在大量自己注入的噪音里挣扎**。
- 也就是说，问题本质是**上下文污染**，不是模型能力退化。

##### 5. 解决办法：把输出从模型可见改成终端可见

- 修复方法很简单，只要把 Hook 里的：

```bash
echo "xxx"
```

- 改成：

```bash
echo "xxx" >&2
```

- 这样就从“模型能看到”的输出，切换到了**只有终端能看到**的通道。

##### 6. 实用建议

- 如果你写了**自定义 Hook**，又觉得模型表现突然变差了，建议优先检查：
  - 是否有输出被写进了模型上下文；
  - 是否存在类似的计数器或重复注入 bug。
- 作者还在回复里提到，除了 Hook 之外，**RTK hook** 等相关机制也可能需要检查。
