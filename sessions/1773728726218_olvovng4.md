### You Should Be Using Subagents in Codex!

Codex supports subagents: specialized child agents that you explicitly spawn for parallel work. Each subagent runs with its own instructions, model settings, and tool context, and Codex merges the results back into one response.

[![视频](https://pbs.twimg.com/amplify_video_thumb/2033620015535296513/img/nu0PHQlqlmbTujqS.jpg)](https://x.com/reach_vb/status/2033636057690800452)[![视频](https://pbs.twimg.com/amplify_video_thumb/2033620015535296513/img/nu0PHQlqlmbTujqS.jpg)](https://x.com/reach_vb/status/2033636057690800452)

This is most useful when the task has clean separable parts like PR review, codebase exploration, or debugging workflows where one agent should investigate while another validates or implements.

Note: Subagents are opt-in. Codex only spawns them when you ask, and each child does its own model and tool work, so this usually costs more tokens than a single-agent run.

#### Custom agents

Codex ships with built-in agents like default, worker, and explorer, but the real power is in custom agents.

Custom agents live as standalone TOML files in \~/.codex/agents/ or .codex/agents/. Each one must define:

- name
- description
- developer\_instructions

Everything else can be inherited or overridden per agent, including model, model\_reasoning\_effort, sandbox\_mode, mcp\_servers, and skills.config.

```plaintext
name = "reviewer"
description = "PR reviewer focused on correctness, security, and missing tests."
developer_instructions = """
Review code like an owner.
Prioritize correctness, regressions, security, and missing test coverage.
"""
```

The best agents are narrow. A mapper should map. A reviewer should review. A docs agent should verify APIs. Once one agent has too many responsibilities, you lose most of the benefit.

#### Runtime model

Subagents inherit the parent session’s sandbox and approval state. They are parallel workers inside the same runtime policy, not independent sessions with looser permissions.

Global limits live under \[agents\]:

```plaintext
[agents]
max_threads = 6
max_depth = 1
```

max\_threads controls concurrency. max\_depth controls delegation depth.

#### A good way to use subagents

A strong pattern is to split a task into focused roles, for example:

- pr\_explorer to trace affected code paths
- reviewer to find correctness and security risks
- docs\_researcher to verify framework or API behavior

That keeps context smaller, roles clearer, and outputs easier to trust.

```plaintext
Review this branch against main. Have pr_explorer map the affected code paths, reviewer find real risks, and docs_researcher verify the APIs the patch relies on. 
Wait for all agents and summarize the findings.
```

#### Tips

- Use subagents only when the work is actually parallelizable.
- Keep agents narrow and opinionated.
- Use read-only sandboxes for exploration and review.
- Use faster models for search and mapping, stronger models for judgment.
- Keep depth low unless nested delegation is necessary.

Subagents are best thought of as role isolation with orchestration. The value is not just parallelism. It is cleaner boundaries, less context drift, and better decomposition on complex tasks.

To read more, check out our detailed docs here:

developers.openai.com/codex/subagents

## 结构化（1）

### 2026-03-17 06:55:20

这篇文章的主旨是：在 Codex 中，`subagents`（子代理）适合处理“可以拆开并行”的复杂任务，核心价值不只是提速，更是让不同角色分工更清晰、结论更可靠。作者尤其强调：真正好用的关键，不在于多开几个 agent，而在于把每个 agent 的职责设计得足够单一、明确。

- 第一部分：什么是 subagents
  - Codex 支持手动创建 `subagents`，它们是专门处理某一类任务的子代理。
  - 每个子代理都有自己独立的：
    - 指令（instructions）
    - 模型设置（model settings）
    - 工具上下文（tool context）
  - 最后由 Codex 把多个子代理的结果合并成一个回复。
  - 它最适合用于“能明显拆分”的工作，比如：
    - PR 审查
    - 代码库探索
    - Debug 流程中一边排查、一边验证或实现

- 第二部分：使用前要注意的成本
  - `subagents` 不是默认自动启用，只有你明确要求时 Codex 才会创建。
  - 每个子代理都会单独调用模型和工具，因此通常会比单代理运行消耗更多 token。
  - 也就是说，只有在任务确实能并行拆分时，使用它才更划算。

- 第三部分：自定义 agent 才是重点
  - Codex 自带一些内置 agent，例如：
    - `default`
    - `worker`
    - `explorer`
  - 但作者认为，真正的威力来自“自定义 agent”。
  - 自定义 agent 以独立 TOML 文件存在于：
    - `~/.codex/agents/`
    - `.codex/agents/`
  - 每个 agent 至少要定义 3 个字段：
    - `name`
    - `description`
    - `developer_instructions`
  - 其他配置可以继承或单独覆盖，比如：
    - `model`
    - `model_reasoning_effort`
    - `sandbox_mode`
    - `mcp_servers`
    - `skills.config`
  - 文中示例把 `reviewer` 定义为一个专注于“正确性、安全性、缺失测试”的 PR 审查 agent，这说明 agent 最好围绕单一目标设计。

- 第四部分：为什么 agent 要“窄而专”
  - 作者明确提出：最好的 agent 应该职责很窄。
  - 例如：
    - mapper 只负责“梳理结构/映射代码”
    - reviewer 只负责“评审风险”
    - docs agent 只负责“核对 API 或文档”
  - 如果一个 agent 责任太多，就会失去 subagents 的大部分优势。
  - 通俗理解：不要让一个人同时做“找问题、查文档、改代码、写总结”，分工越清楚，输出越可信。

- 第五部分：运行机制和限制
  - 子代理会继承父会话的沙箱和审批状态，不是权限更高的独立会话。
  - 也就是说，它们只是同一运行策略下的并行工作者。
  - 全局限制在 `[agents]` 配置下，例如：
    - `max_threads = 6`：最多并发 6 个线程
    - `max_depth = 1`：最多一层委派深度
  - 其中：
    - `max_threads` 控制并发数量
    - `max_depth` 控制代理再继续委派的层级

- 第六部分：推荐的使用方式
  - 作者给出一个很实用的角色拆分方案：
    - `pr_explorer`：追踪受影响的代码路径
    - `reviewer`：寻找正确性和安全风险
    - `docs_researcher`：验证补丁依赖的框架/API 行为
  - 这样做的好处是：
    - 上下文更小
    - 角色更清楚
    - 结果更容易信任
  - 文中示例任务是：让多个 agent 一起审查某个分支相对 `main` 的改动，分别做代码路径分析、风险审查、API 校验，最后再统一汇总。

- 第七部分：实用建议
  - 只在任务“真的适合并行”时使用 subagents。
  - agent 要保持“职责单一、立场明确”。
  - 做探索和审查时，优先用只读沙箱，更安全。
  - 搜索、代码映射这类任务可用更快的模型；判断、评审这类任务可用更强的模型。
  - `max_depth` 尽量保持低，除非确实需要多层委派。

- 结尾：文章结论
  - 作者认为，subagents 的本质不是单纯并行，而是“角色隔离 + 协同调度”。
  - 它带来的核心收益包括：
    - 边界更清晰
    - 上下文漂移更少
    - 复杂任务更容易拆解
  - 如果你在 Codex 里做 PR review、排查问题或分析大型代码库，subagents 会是非常值得用的能力。
