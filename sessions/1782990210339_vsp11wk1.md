## 分析要点

- **核心高价值点**：将子代理调用从单次模型决策转为解释器代码中的循环、分支和并行批处理，可显著提升复杂任务编排的确定性和可控性。
- **留存建议**：长期保留（包含LangChain动态子代理的核心机制、适用场景和多种可复用编排模式，对构建复杂Agent工作流有参考价值。）

**知识要点**

- Dynamic subagents依赖解释器运行时，通过task\(\)全局函数在代码中调度子代理。
- 使用“workflow”作为提示词可触发模型倾向于通过解释器组织任务，而不是逐个普通工具调用。
- 适合处理大量独立单元、多视角分析、递归分析和需要结果综合的任务。
- 常见模式包括分类后处理、并行扇出汇总、对抗验证、生成过滤、锦标赛评审和循环发现。
- 传入responseSchema后，task\(\)返回值可直接作为类型化JavaScript对象使用。
- task\(\)在eval内部调度，不走普通工具调用路径，因此父Agent的逐次审批机制不会自动应用到每个子任务。

**行动项**

- 在实验项目中安装langchain-quickjs并尝试CodeInterpreterMiddleware。
- 为一个批量代码审查或工单分流任务设计2-3个专用subagent并测试workflow触发效果。
- 将文中的六种动态子代理模式整理为可复用Agent编排模板。
- 在涉及高风险操作时，为eval工具本身增加审批或安全网关。

## 正文

Dynamic subagents let an agent dispatch subagents from interpreter code. Instead of asking the model to choose one subagent call at a time, the agent can use JavaScript loops, branches, and parallel batches to route work across configured subagents and synthesize the results.Use this pattern when work spans many independent units, needs multiple perspectives, or benefits from recursive analysis. For general interpreter setup, see Interpreters.

Dynamic subagents use the interpreter runtime, which is in **beta**. APIs and lifecycle behavior may change between releases.

Interpreters require `langchain-quickjs>=0.1.0` and Python `>=3.11`.

#### Quickstart

Dynamic subagents require two things: subagents to dispatch work to, and a code interpreter, a secure, lightweight runtime where the model writes and executes orchestration code. Deep Agents includes an optional code interpreter based on QuickJS. Install the QuickJS middleware package, then pass interpreter middleware through the `middleware` argument on `create_deep_agent`.Deep Agents ships with a general-purpose subagent built in, so basic fan-out works without extra configuration. For specialized work, configure custom subagents with their own names, descriptions, and system prompts; the names and descriptions are how the agent knows which role to reach for. See Subagents for configuration.To trigger dynamic subagents, prompt the agent with the word “workflow”:

**The word “workflow” is a useful trigger.** The interpreter system prompt treats “workflow” as a signal to organize work through the interpreter, dispatching subagents with `task()` from code rather than grinding through items one model-chosen tool call at a time. Phrasing a request as a “workflow” is a deliberate lever you can pull to opt into dynamic orchestration. For a single, direct delegation, phrase the request plainly instead.

##### Use with a coding agent

The fastest way to try dynamic subagents is with `dcode`, the LangChain terminal coding agent built on a Deep Agent. It ships with the code interpreter enabled, so dynamic subagents works out of the box with nothing to wire up.Install `dcode`:Run it:

```
dcode
```

To trigger dynamic subagents, ask for a “workflow”. Instead of grinding through the work itself or managing fan-out through its native `task` tool, the agent writes an orchestration script that calls the built-in `task()` global and runs it in the code interpreter. For example: “Run a workflow to review every file in src/ for SQL injection.” As subagents spawn, `dcode` shows them live in the dynamic subagents panel, grouped into phases by dispatch.

![The dcode dynamic subagents panel showing spawned subagents grouped into phases by dispatch](https://mintcdn.com/langchain-5e9cc07a/mcM5dSw40KzBUENf/oss/images/deepagents/dcode-dynamic-subagents-panel.png?fit=max&auto=format&n=mcM5dSw40KzBUENf&q=85&s=bc20632b54e21fecfc5ff4f8d169a2c7)

The dcode dynamic subagents panel showing spawned subagents grouped into phases by dispatch

`dcode` is the fastest way to try this, but you can also use dynamic subagents in the coding agent of your choice over ACP (for example, Zed).

#### How it works

When an agent has subagents and interpreter middleware, the interpreter exposes a built-in `task()` global that dispatches subagents from code. A task spanning many independent units (reviewing every file in a directory, triaging a batch of tickets) becomes a loop that fans the work out, so it runs deterministically instead of one model-chosen tool call at a time.Subagent orchestration also supports recursive language model (RLM) workflows, the approach described in the [Recursive Language Models paper](https://arxiv.org/abs/2512.24601): keep the working set in interpreter variables, select slices, call subagents with `task()`, and synthesize the results.`task()` takes the following inputs:

- `description`: The prompt for the subagent
- `subagentType`: Which configured subagent to run
- `responseSchema` (optional): Structured output

A `task()` runs a full agentic loop and resolves to the subagent’s result:When you pass `responseSchema`, the resolved value is already a typed JavaScript object; only call `JSON.parse` if a subagent intentionally returned a JSON string.

#### Patterns

The agent picks a strategy from the shape of the task; these emerge from how it writes interpreter code, not from configuration, and the subagents you make available determine what it can do. Every pattern shares one model: hold work in JS variables, dispatch subagents with `task()`, and combine results in code. The diagrams below show the common shapes, each with a runnable example.

##### Classify and act

Items are classified first, then each item is handled by a specialized subagent based on its classification. This lets you process mixed inputs where different items need different expertise. **Use cases:** Triaging support tickets, error logs, user feedback, or any batch of items that need different handling depending on their type.

**What you configure**

```
agent = create_deep_agent(

    model="openai:gpt-5.5",

    subagents=[

        {

            "name": "bug-fixer",

            "description": "Investigates bug reports and provides reproduction steps",

            "system_prompt": "You are a bug triage specialist. Investigate each bug report and provide clear reproduction steps.",

        },

        {

            "name": "feature-analyst",

            "description": "Evaluates feature requests for feasibility and effort",

            "system_prompt": "You are a product analyst. Evaluate each feature request for technical feasibility, estimated effort, and potential impact.",

        },

        {

            "name": "support-agent",

            "description": "Answers user questions based on documentation",

            "system_prompt": "You are a support specialist. Answer user questions clearly based on the available documentation.",

        },

    ],

    middleware=[CodeInterpreterMiddleware()],

)

result = await agent.ainvoke({

    "messages": [{"role": "user", "content": "Go through these 30 support tickets. Categorize each one, then for bugs give me reproduction steps, and for feature requests give me a feasibility assessment."}]

})
```

##### Fan-out and synthesize

The agent dispatches the same kind of work across many items in parallel, then combines the results. **Use cases:** Code review across a directory, analyzing a batch of documents, processing log files, running the same check across many services.

##### Adversarial verification

A two-pass pattern. The first pass produces findings. The second pass sends each finding to independent verifiers, and only findings that survive agreement are kept. This reduces false positives when confidence matters more than speed. **Use cases:** Security audits where false positives are costly, compliance checks, any review where you need high confidence in findings.

**What you configure** **What the agent writes**

##### Generate and filter

Multiple subagents generate independent solutions to the same problem. The agent compares, scores, and filters the results in code, keeping only the best. **Use cases:** Architecture proposals, refactoring strategies, content variations, any task where exploring multiple options before committing produces a better outcome.

**What you configure** **What the agent writes**

##### Tournament

Variations are compared head-to-head by a judge subagent, with winners advancing through elimination rounds. **Use cases:** Optimization under subjective criteria, style selection, choosing between competing implementations.

Example: tournament

**What you configure**

```
agent = create_deep_agent(

    model="openai:gpt-5.5",

    subagents=[

        {

            "name": "writer",

            "description": "Rewrites a function with a focus on readability and clarity",

            "system_prompt": "You are an expert programmer focused on clean code. Rewrite the given function to maximize readability. Explain your choices.",

        },

        {

            "name": "judge",

            "description": "Compares two code implementations and picks the more readable one",

            "system_prompt": "You are a code quality judge. Compare two implementations and pick the more readable one. Justify your choice with specific criteria.",

        },

    ],

    middleware=[CodeInterpreterMiddleware()],

)

result = await agent.ainvoke({

    "messages": [{"role": "user", "content": "Rewrite the processOrder function in src/checkout.ts five different ways and find the most readable version."}]

})
```

**What the agent writes**

```
// Generate variants, then judge pairwise until a single winner remains.

let bracket = await Promise.all(

  [1, 2, 3, 4, 5].map((n) =>

    task({ description: `Rewrite processOrder for readability (variant ${n}).`, subagentType: "writer" }),

  ),

);

while (bracket.length > 1) {

  const winners = [];

  for (let i = 0; i < bracket.length; i += 2) {

    if (bracket[i + 1] === undefined) { winners.push(bracket[i]); break; }

    const { winner } = await task({

      description: `Pick the more readable:\n\nA:\n${bracket[i]}\n\nB:\n${bracket[i + 1]}`,

      subagentType: "judge",

      responseSchema: pickSchema, // -> { winner: "A" | "B" }

    });

    winners.push(winner === "A" ? bracket[i] : bracket[i + 1]);

  }

  bracket = winners;

}

bracket[0]; // the winning rewrite
```

##### Loop until done

The agent runs a discovery loop, deduplicating against what it has already found, until no new results appear. Useful when the scope of the work is not known upfront. **Use cases:** Exhaustive search, dead code detection, dependency audits, any sweep where you want completeness rather than a fixed number of results.

**What you configure** **What the agent writes**

`task()` dispatches from inside an already-running `eval` call. It does not go through the normal tool calling path, so `interrupt_on` approval workflows on the parent agent are not enforced per dispatch. Gate the `eval` tool itself if you need approval before subagent orchestration runs.

#### Disable dynamic subagents

Subagent dispatch is on by default whenever the agent has subagents. Disable it if you want subagents to be available only through the normal `task` tool path.

#### Dynamic Subagents 深度总结

##### 1. 核心是什么？

**Dynamic subagents**是 LangChain Deep Agents 的一种动态编排机制。

它允许主 Agent 在**代码解释器**中写 JavaScript 逻辑，通过`task ()`动态调用多个子 Agent，而不是让模型一次只选择一个工具调用。

一句话：

> 让 Agent 像写程序一样，批量、并行、递归地调度多个子 Agent 完成复杂任务。

---

##### 2. 解决了什么问题？

传统 Agent 调用子 Agent 通常是：

```text
模型判断 → 调一个子 Agent → 等结果 → 再判断 → 再调下一个
```

问题是：

- 慢
- 不稳定
- 难并行
- 难处理大量独立任务
- 难做多轮验证和结果合成

Dynamic subagents 改成：

```text
主 Agent 写一段 JS 编排代码
→ 循环 / 分支 / 并行调用多个子 Agent
→ 收集结果
→ 统一汇总
```

更像一个**自动化工作流引擎**。

---

##### 3. 关键机制

需要两样东西：

1. **Subagents**
   - 可配置不同角色
   - 例如：bug 分析员、产品分析员、安全审计员、代码评审员

2. **Code Interpreter**
   - 一个安全轻量的代码运行环境
   - Deep Agents 使用 QuickJS
   - 要求：
     - Python >= 3.11
     - `langchain-quickjs >= 0.1.0`

核心函数是：

```js
task ({
  description: "交给子 Agent 的任务",
  subagentType: "子 Agent 名称",
  responseSchema: 可选结构化输出
})
```

`task ()`会运行一个完整的子 Agent 循环，并返回结果。

---

##### 4. 如何触发？

文档强调一个触发词：

> **workflow**

如果你对 Agent 说：

```text
Run a workflow to review every file in src/for SQL injection.
```

Agent 更可能进入动态编排模式，写代码批量调度子 Agent。

如果只是普通请求，则可能走普通单次工具调用。

---

##### 5. 典型模式

###### 5.1 分类后处理

先分类，再交给不同专家处理。

```text
工单 → 分类
bug → bug-fixer
feature → feature-analyst
question → support-agent
```

适合：

- 客服工单
- 用户反馈
- 错误日志
- 混合任务批处理

---

###### 5.2 扇出并汇总

同一种任务分发给多个子任务并行执行。

```text
多个文件 → 多个 Worker 并行检查 → 汇总结果
```

适合：

- 代码审查
- 文档批量分析
- 日志扫描
- 多服务检查

---

###### 5.3 对抗式验证

第一批 Agent 找问题，第二批 Agent 验证问题。

```text
发现问题 → 多个验证 Agent 复核 → 保留高置信结果
```

适合：

- 安全审计
- 合规检查
- 低容忍误报的场景

---

###### 5.4 生成并筛选

多个 Agent 生成不同方案，再筛选最好结果。

```text
多个方案 → 打分 / 排序 / 过滤 → 最佳方案
```

适合：

- 架构设计
- 重构方案
- 文案生成
- 策略选择

---

###### 5.5 锦标赛模式

多个方案两两比较，胜者晋级。

```text
方案 A vs 方案 B → Judge 选胜者 → 最终冠军
```

适合：

- 主观质量评估
- 风格选择
- 代码可读性比较

---

###### 5.6 循环直到完成

不断发现新结果，去重，直到没有新发现。

```text
搜索 → 发现新项 → 去重 → 继续搜索 → 无新增 → 结束
```

适合：

- 死代码检测
- 依赖审计
- 全量搜索
- 范围未知的问题排查

---

##### 6. 通俗理解

可以把 Dynamic subagents 想成：

> 主 Agent 是项目经理，子 Agent 是专业员工，代码解释器是任务调度表。

以前项目经理只能：

```text
一个一个叫人干活
```

现在项目经理可以写一张执行计划：

```text
这 100 个文件分给 10 个人并行查；
查完后再让 3 个审计员复核；
最后把所有结果汇总成报告。
```

所以它的本质不是 “更聪明的单个 Agent”，而是：

> 让 Agent 具备程序化组织能力。

---

##### 7. 重要注意点

###### 7.1 仍处于 Beta

文档明确说：

> interpreter runtime 仍是 beta，API 和生命周期可能变化。

所以生产环境要谨慎。

---

###### 7.2 审批机制可能绕过

`task ()`是在解释器`eval`内部调度的，不走普通工具调用路径。

因此：

> 父 Agent 上的`interrupt_on`审批不会逐个作用到子 Agent 调度。

如果需要审批，应拦截整个`eval`工具，而不是每个子任务。

---

###### 7.3 可关闭动态子 Agent

如果希望子 Agent 只能通过普通 task 工具调用，而不是解释器动态调度，可以关闭该能力。

---

#### 辩证思考

##### 优点

###### 1. 更适合复杂任务

大量文件、工单、日志、方案评估，本质上都是批处理问题。  
Dynamic subagents 把 Agent 从 “聊天式处理” 升级成 “工作流式处理”。

---

###### 2. 更可控

用代码表达循环、分支、并行、筛选，比模型自由发挥更稳定。

```text
模型负责判断
代码负责流程
子 Agent 负责专业执行
```

这是更合理的分工。

---

###### 3. 更容易扩展

只要增加不同角色的子 Agent，就能扩展能力边界。

例如：

- 安全专家
- 测试专家
- 产品专家
- 法务专家
- 文档专家

主 Agent 负责调度即可。

---

##### 风险

###### 1. 复杂度上升

动态编排虽然强大，但也引入：

- 调试难度
- 成本控制问题
- 子 Agent 结果一致性问题
- 工作流失控风险

---

###### 2. 成本可能暴涨

一个`workflow`可能瞬间调度几十甚至上百个子 Agent。

如果没有限制：

```text
并行越多 ≠ 越好
```

可能导致 token、时间、API 成本快速上升。

---

###### 3. 安全和权限要更谨慎

因为它在解释器里动态执行调度逻辑，审批机制又可能不逐个生效，所以必须设计好边界：

- 哪些任务能自动跑
- 哪些任务必须人工批准
- 子 Agent 能访问什么资源
- 是否限制并发和递归深度

---

#### 最精炼结论

**Dynamic subagents = Agent 的程序化多专家调度系统。**

它适合：

- 大批量任务
- 多角色协作
- 多方案比较
- 高置信验证
- 递归式探索

但要注意：

- 仍是 Beta
- 成本可能放大
- 审批要拦截解释器层
- 不适合简单单次任务

最终价值在于：

> 把 Agent 从 “单人问答助手” 推进到 “可编排的智能工作流系统”。

#### 《Dynamic subagents》内容总结

动态子代理让智能体通过解释器代码，批量、并行或递归地调度多个子代理，而不是每次只由模型手动选择一个子代理调用。它适合处理大量独立任务、多角度分析，以及需要反复探索和汇总的复杂工作流。

##### 1. 核心概念

- 动态子代理的核心是：  
  **智能体编写 JavaScript 编排代码，并在代码中调用 `task()` 分发任务。**
- 与传统方式相比，它可以使用：
  - 循环
  - 条件分支
  - 并行批处理
  - 递归分析
  - 结果汇总与筛选
- 典型场景包括：
  - 审查目录中的所有代码文件
  - 批量处理工单或日志
  - 为同一问题生成多个方案
  - 对结果进行复核、比较和排名

> 动态子代理依赖解释器运行时，目前仍处于 **Beta** 阶段，API 和生命周期行为可能在不同版本之间发生变化。

##### 2. 使用前提与安装

动态子代理需要两个条件：

1. **可供调度的子代理**
2. **代码解释器**
   - Deep Agents 提供了基于 QuickJS 的可选解释器。
   - 需要安装 `langchain-quickjs>=0.1.0`。
   - Python 版本要求为 `>=3.11`。
   - 创建智能体时，通过 `middleware` 参数传入解释器中间件：

```python
middleware=[CodeInterpreterMiddleware()]
```

###### 子代理配置

Deep Agents 内置了一个通用子代理，因此基础的任务分发无需额外配置。

如果需要专业化处理，可以配置自定义子代理，包括：

- `name`：子代理名称
- `description`：能力描述，帮助主智能体选择角色
- `system_prompt`：该子代理的系统提示词和工作规范

例如可以分别配置：

- `bug-fixer`：分析漏洞或缺陷并提供复现步骤
- `feature-analyst`：评估功能需求的可行性和工作量
- `support-agent`：根据文档回答用户问题

##### 3. 如何触发动态子代理

在用户请求中加入 **“workflow”** 一词，可以提示智能体使用动态工作流：

> “Run a workflow to review every file in `src/` for SQL injection.”

解释器的系统提示会把 “workflow” 视为一种信号，促使智能体：

1. 通过解释器编写编排代码；
2. 在循环或批处理中调用 `task()`；
3. 并行调度多个子代理；
4. 汇总最终结果。

如果只是一次简单的任务委派，则可以直接使用普通措辞，不必使用 “workflow”。

##### 4. 使用 dcode 快速体验

最快的体验方式是使用 **dcode**：

- dcode 是基于 Deep Agent 构建的 LangChain 终端编码代理；
- 默认启用了代码解释器；
- 无需额外配置即可使用动态子代理。

基本流程：

```bash
dcode
```

然后可以提出类似请求：

> “Run a workflow to review every file in `src/` for SQL injection.”

dcode 会通过内置的 `task()` 全局函数生成编排脚本，并在解释器中执行。子代理运行时，会在动态子代理面板中实时显示，并按照不同的调度阶段分组。

除 dcode 外，也可以通过 ACP 在其他编码代理中使用，例如 **Zed**。

##### 5. 工作原理

当智能体同时具备子代理和解释器中间件时，解释器会提供内置的：

```javascript
task()
```

主智能体可以把一个大型任务转化为代码循环。例如：

- 遍历目录中的每个文件；
- 为每个文件启动一个审查子代理；
- 并行收集结果；
- 最后统一分析和汇总。

这样可以让任务分发更加确定，而不是依赖模型逐次选择工具调用。

###### `task()` 的主要参数

```javascript
task({
  description: "交给子代理的具体任务描述",
  subagentType: "要运行的子代理类型",
  responseSchema: "可选的结构化输出格式"
})
```

其中：

- `description`：子代理要完成的任务；
- `subagentType`：要调用的已配置子代理；
- `responseSchema`：可选，用于约束返回结构。

`task()` 会运行一个完整的子代理智能体循环，并返回子代理结果。

如果指定了 `responseSchema`，返回值已经是类型化的 JavaScript 对象，通常不需要再次使用 `JSON.parse()`。只有当子代理主动返回 JSON 字符串时，才需要解析。

###### 支持递归语言模型工作流

动态子代理也支持递归语言模型（RLM）模式：

1. 把工作集保存在解释器变量中；
2. 根据需要选择其中的部分数据；
3. 使用 `task()` 调用子代理；
4. 在代码中综合所有结果。

这种方式适合处理规模较大、需要逐步筛选和递归分析的数据。

##### 6. 常见工作流模式

###### 6.1 先分类，再执行

先由分类器判断每个项目的类型，再交给对应的专业子代理处理。

```text
工单
 ├─ Bug       → Bug 修复子代理
 ├─ 功能请求  → 功能分析子代理
 └─ 用户问题  → 客服子代理
```

**适用场景：**

- 支持工单分流
- 错误日志分类
- 用户反馈处理
- 不同类型任务混合出现的批处理

**原文案例：**

> 处理 30 个支持工单：先分类；对于 Bug，提供复现步骤；对于功能请求，评估可行性。

---

###### 6.2 扇出并汇总

将相同类型的任务分配给多个子代理并行处理，最后统一收集和综合结果。

```text
多个项目
   ↓
多个并行工作子代理
   ↓
收集结果
   ↓
综合分析
```

**适用场景：**

- 审查一个目录中的所有代码
- 分析一批文档
- 处理大量日志文件
- 对多个服务执行同一项检查

这种方式可以把原本串行的重复工作改造成并行处理。

---

###### 6.3 对抗式验证

采用两轮处理：

1. 第一轮由子代理生成发现结果；
2. 第二轮让多个独立验证者分别复核这些发现；
3. 只有通过多数验证或达成一致的结果才保留。

```text
初步发现
   ↓
多个独立验证者
   ↓
多数投票
   ↓
确认结果
```

**适用场景：**

- 安全审计
- 合规检查
- 对误报非常敏感的代码审查

该模式牺牲部分速度，以换取更高的准确性和置信度。

---

###### 6.4 生成、筛选与排名

让多个子代理针对同一问题生成不同方案，然后由主智能体在代码中比较、评分和筛选，最终保留最佳结果。

```text
多个候选方案
   ↓
比较与评分
   ↓
筛选排名
   ↓
最佳方案
```

**适用场景：**

- 架构方案设计
- 重构策略选择
- 内容版本生成
- 需要先探索多个方向再做决定的任务

---

###### 6.5 锦标赛式比较

候选方案两两比较，由评审子代理选出胜者，胜者进入下一轮，直到最终只剩一个结果。

```text
候选方案
   ↓
两两比较
   ↓
胜者晋级
   ↓
多轮淘汰
   ↓
最终胜者
```

**适用场景：**

- 根据主观标准进行优化
- 代码风格选择
- 多种实现方案比较
- 从多个创作版本中选出最佳版本

###### 原文案例

任务是将 `src/checkout.ts` 中的 `processOrder` 函数重写 **5 个版本**，然后找出可读性最高的版本：

1. 使用 `writer` 子代理生成 5 个重写方案；
2. 使用 `judge` 子代理两两比较；
3. 每轮保留更易读的方案；
4. 直到得到最终版本。

示意代码逻辑如下：

```javascript
let bracket = await Promise.all(
  [1, 2, 3, 4, 5].map((n) =>
    task({
      description: `Rewrite processOrder for readability (variant ${n}).`,
      subagentType: "writer"
    })
  )
);

while (bracket.length > 1) {
  const winners = [];

  for (let i = 0; i < bracket.length; i += 2) {
    if (bracket[i + 1] === undefined) {
      winners.push(bracket[i]);
      break;
    }

    const { winner } = await task({
      description: `Pick the more readable:\n\nA:\n${bracket[i]}\n\nB:\n${bracket[i + 1]}`,
      subagentType: "judge",
      responseSchema: pickSchema
    });

    winners.push(winner === "A" ? bracket[i] : bracket[i + 1]);
  }

  bracket = winners;
}

bracket[0];
```

---

###### 6.6 循环执行，直到没有新结果

智能体持续进行发现，并将新结果与已经发现的内容去重，直到不再产生新的结果。

```text
执行搜索
   ↓
发现新结果？
 ├─ 是：继续搜索
 └─ 否：结束
```

**适用场景：**

- 穷尽式搜索
- 死代码检测
- 依赖审计
- 不确定任务规模、但希望尽可能完整地扫描的工作

##### 7. 重要限制与控制方式

###### 审批机制不会逐次生效

`task()` 是在已经运行的解释器调用内部发起的，不会经过普通工具调用路径。因此：

- 父智能体的 `interrupt_on` 审批流程；
- 不会自动对每次子代理调度逐一生效。

如果需要在编排启动前获得批准，应当对整个解释器执行或 `eval` 工具进行审批控制。

###### 可以关闭动态子代理

默认情况下，只要智能体配置了子代理，动态调度功能就会启用。

如果希望子代理只能通过普通的 `task` 工具调用，而不能由解释器动态编排，可以将动态子代理功能关闭。

## 口播总结（1）

#### Dynamic subagents：让智能体用代码动态调度子代理

这篇文档介绍了 LangChain 中的“动态子代理”模式。听完后，你会了解它是什么、怎样启用、为什么要用“workflow”触发，以及它如何处理批量任务、并行分析、结果验证和多方案比较。

##### 一、动态子代理解决什么问题

核心结论是：动态子代理允许一个智能体通过解释器里的代码，主动调度多个子代理协同工作。

简单来说，传统方式是让模型一次选择一个子代理，再调用一次工具。动态子代理则不同。智能体可以写出 JavaScript 代码，使用循环、条件分支和并行批处理，把任务分发给不同的子代理，最后再统一汇总结果。

这种方式特别适合三类工作。

第一类，是任务包含很多互相独立的单元。比如检查一个目录里的所有文件，或者批量处理许多工单。

第二类，是同一个问题需要多个角度分析。比如让多个子代理分别提出方案，再比较哪一个最好。

第三类，是需要递归分析的任务。也就是说，智能体先拆分问题，继续分派子任务，再把子任务结果合并起来。

不过需要注意，动态子代理依赖的解释器目前仍处于测试阶段。它的 API，也就是编程接口，以及生命周期行为，都可能随着版本更新而变化。

##### 二、启用动态子代理需要什么

接下来，启用动态子代理需要两个基本条件。

第一个条件，是要有可以被调度的子代理。Deep Agents 内置了一个通用子代理，因此即使不额外配置，也能完成基础的任务分发。

如果需要更专业的处理，可以配置自定义子代理。每个子代理可以有自己的名称、描述和系统提示词。名称和描述相当于它的“角色标签”，帮助主智能体判断什么时候应该调用它。

第二个条件，是要有代码解释器。解释器可以理解为一个安全、轻量的运行环境。智能体会在里面编写并执行协调任务的代码。

Deep Agents 提供了一个基于 QuickJS 的可选代码解释器。QuickJS 是一种轻量级的 JavaScript 运行时。使用前，需要安装 QuickJS 中间件，并在创建智能体时，通过中间件参数传入解释器。

这里有两个版本要求：需要安装 `langchain-quickjs`，版本至少是零点一；同时，Python 版本需要至少是三点十一。

##### 三、为什么要用“workflow”这个词

更重要的是，动态子代理通常由提示词中的英文单词“workflow”触发。

“Workflow”可以翻译成“工作流”。在解释器的系统提示中，这个词被当作一种信号。它告诉智能体：这次任务应该组织成一个工作流，并通过解释器里的 `task()` 函数，从代码中批量调度子代理。

这样做的好处是，智能体不会自己逐项处理，也不会一次只选择一个工具调用。它可以按照预先写出的循环或并行逻辑，稳定地处理一批任务。

例如，可以这样提出请求：“运行一个工作流，检查 src 目录中的每个文件，寻找 SQL 注入问题。”SQL 注入，是一种通过恶意输入影响数据库操作的安全漏洞。

相反，如果只是想直接委派一个单独任务，就应该用普通、直接的表达方式，不必刻意加入“workflow”。

##### 四、最快的体验方式：使用 dcode

如果想快速尝试，文档推荐使用 dcode。

dcode 是 LangChain 提供的终端编程智能体，底层基于 Deep Agent。它已经默认启用了代码解释器，所以不需要额外配置，动态子代理就可以直接运行。

使用时，只要启动 dcode，然后提出一个包含“workflow”的请求即可。智能体会编写一段协调代码，调用内置的 `task()` 函数，并在代码解释器中执行。

比如，它可以把“检查 src 目录里的所有文件是否存在 SQL 注入”拆成多个子任务，再分别交给子代理处理。

当子代理被创建后，dcode 会在动态子代理面板中实时显示它们。不同的调度批次会被归到不同阶段，方便观察任务是怎样逐步展开的。

dcode 是最快的尝试方式，但不是唯一方式。也可以在其他支持 ACP 的编程智能体中使用动态子代理，例如 Zed。ACP 可以理解为一种让编程工具与智能体协作的协议。

##### 五、动态子代理具体怎样工作

当一个智能体同时具备子代理和解释器中间件时，解释器会提供一个内置的 `task()` 函数。

主智能体可以在代码中调用这个函数，把任务描述和指定的子代理类型传进去。这样，一个包含很多独立单元的任务，就可以被写成循环或并行分发流程。

例如，“检查目录中的每个文件”，可以变成一个循环。循环为每个文件创建一个任务，再同时或依次交给子代理处理。相比让模型自己一个接一个地选择工具，这种方式更确定，也更容易控制。

动态子代理还支持一种叫作 RLM 的递归语言模型工作流。RLM 的意思是“递归语言模型”。这种方法会把工作集，也就是当前正在处理的数据，保存在解释器变量中；接着选取其中的一部分，调用 `task()` 分派给子代理，最后再把结果综合起来。

`task()` 主要接受三个输入。

第一，是 `description`，也就是给子代理的任务说明。

第二，是 `subagentType`，也就是要运行的已配置子代理类型。

第三，是可选的 `responseSchema`。它用于规定结构化输出格式，比如要求子代理返回一个包含固定字段的对象。

一次 `task()` 调用会运行完整的子代理智能体流程，并最终返回子代理的结果。如果提供了 `responseSchema`，返回值已经是带类型的 JavaScript 对象。只有当子代理故意返回 JSON 字符串时，才需要再调用 `JSON.parse` 进行解析。

##### 六、第一种模式：先分类，再处理

第一种常见模式，是“分类并执行”。

核心做法是，先让一个分类子代理判断每个项目属于哪一类，再根据分类结果，把项目交给不同的专业子代理。

这适合混合型输入。比如，一批支持工单里，可能同时包含漏洞报告、功能请求和普通用户问题。不同类型的内容，需要不同的处理方式。

文档中的例子是：处理三十张支持工单。先对每张工单分类；如果是漏洞，就给出复现步骤；如果是功能请求，就评估技术可行性和工作量；如果是用户问题，就依据文档给出回答。

这里可以配置三个角色。

一个是漏洞处理代理，负责调查问题并提供清晰的复现步骤。

一个是功能分析代理，负责评估功能请求的技术可行性、预计工作量和潜在影响。

还有一个是支持代理，负责根据现有文档回答用户问题。

这种模式的价值在于：不是让同一个子代理处理所有内容，而是让每类任务都交给最适合的角色。

##### 七、第二种模式：并行分发，再综合结果

第二种模式，是“分发并综合”。

核心结论是：当许多项目需要进行相同类型的分析时，可以把它们并行交给多个工作子代理，最后统一收集和总结。

例如，可以让多个子代理分别审查一个代码目录中的文件，分析一批文档，处理多份日志，或者对多个服务执行同一种检查。

这种方式把任务拆成许多相互独立的部分。每个子代理只关注自己负责的项目，主智能体再把所有结果收集起来，形成最终结论。

它的优势是结构清晰，而且适合批量任务。相比逐个处理，批量分发也更符合动态子代理的设计目标。

##### 八、第三种模式：对抗式验证

第三种模式，是“对抗式验证”，也可以理解成两轮检查。

第一轮，多个子代理先独立地产生发现结果。比如分别找出安全漏洞、合规问题或代码风险。

第二轮，再把每一个发现分别交给独立的验证子代理进行复核。只有得到足够一致支持的发现，才会被保留下来。

这种方法主要用来减少误报。所谓误报，就是系统把实际上不存在的问题，错误地判断成了问题。

文档特别强调，这种模式适合安全审计、合规检查，以及任何“准确性比速度更重要”的场景。

它的代价是需要更多的子代理调用，但换来的，是更高的结果可信度。

##### 九、第四种模式：生成多个方案，再筛选排名

第四种模式，是“生成并过滤”。

核心做法是，让多个子代理针对同一个问题，分别提出独立方案。主智能体再用代码比较、评分和筛选，只保留最好的结果。

例如，可以让多个子代理分别提出软件架构方案、代码重构策略，或者不同版本的内容。之后，再根据预先设定的标准进行比较。

这种模式适合那些“先探索多个可能性，再做决定”的任务。因为如果一开始就只生成一个方案，可能会过早限制选择范围。

通过独立生成多个结果，再进行过滤和排名，智能体可以在更多候选方案中挑选最终答案。

##### 十、第五种模式：锦标赛式比较

第五种模式，是“锦标赛”。

它和普通的方案筛选类似，但比较过程更像淘汰赛。多个候选方案先两两比较，由评审子代理选出胜者。胜者继续进入下一轮，直到最后只剩下一个结果。

文档给出的例子，是把 `processOrder` 函数，也就是订单处理函数，重写成五个不同版本，然后找出最易读的版本。

具体过程是：先由写作型子代理生成五种重写方案。接着，评审型子代理两两比较这些方案，判断哪个更易读。每轮淘汰一部分方案，最终留下一个获胜版本。

这种模式适合主观标准较强的任务，比如比较代码风格、选择内容表达方式，或者在多个实现之间选择最符合要求的一个。

它特别适用于“可读性”“表达风格”或“整体质量”这类不容易用单一硬指标判断的场景。

##### 十一、第六种模式：循环搜索直到没有新结果

第六种模式，是“持续循环，直到完成”。

核心做法是，智能体不断进行发现，并把新结果与已经找到的内容进行去重。只要还能找到新的结果，就继续循环；当不再出现新结果时，任务结束。

这种方式适合一开始无法确定范围的任务。

例如，可以用来进行尽可能完整的搜索、查找无效代码、审计依赖关系，或者扫描一个系统中的所有潜在问题。

与“固定处理十个项目”不同，这种方法的结束条件不是一个预先设定的数量，而是“没有新的发现”。

因此，它更适合追求完整性的任务。但同时，实际运行成本和耗时，也会随着发现数量增加而增加。

##### 十二、使用时需要注意权限和关闭方式

最后，还有一个重要的运行机制需要注意。

`task()` 是在已经运行的解释器执行调用，也就是 `eval` 调用内部进行分发。它不会经过通常的工具调用路径。

因此，父智能体上的 `interrupt_on` 审批流程，不会针对每一次子代理分发单独执行。换句话说，如果系统要求在执行某些操作前获得人工批准，不能默认认为每个动态子代理都会自动触发审批。

如果需要在子代理编排开始前进行审批，就应该把审批设置在整个 `eval` 工具上，而不是依赖每一次 `task()` 调用分别审批。

另外，只要智能体配置了子代理，动态分发默认就是开启的。

如果希望子代理只能通过普通的 `task` 工具路径调用，而不能由解释器动态编排，可以主动关闭动态子代理功能。

##### 结尾：最值得记住的五点

最后，回顾五个最重要的结论。

第一，动态子代理的核心，是让智能体通过解释器代码调用 `task()`，从而批量、并行或递归地调度多个子代理。

第二，启用它需要子代理和代码解释器，并且当前解释器仍处于测试阶段；环境需要 `langchain-quickjs` 至少零点一，以及 Python 至少三点十一。

第三，在提示词中使用“workflow”，是主动要求智能体采用动态工作流的关键触发方式；单个任务的直接委派，则不必使用这个词。

第四，动态子代理支持多种组织方式，包括先分类再处理、并行分发后综合、对抗式验证、多方案筛选、锦标赛比较，以及循环搜索直到没有新结果。

第五，动态分发不会自动逐次经过父智能体的审批流程。如果需要控制权限，应当对整个解释器执行调用进行审批；如果不需要动态编排，也可以将它关闭。

## 深度解读（1）

### 2026-09-18 00:41:55

#### 动态子代理的真正变化：让模型写“执行计划”，而不只是连续调用工具

LangChain 这项能力最值得关注的，不是“一个 Agent 可以召唤更多 Agent”，而是**把任务编排从模型逐步做决定，转成模型先写一段可执行代码**。

过去，模型通常完成一步、观察结果，再决定下一次工具调用。面对 30 张工单或一个代码目录，这种方式不仅慢，还容易漏项、重复，执行路径也难以复现。动态子代理则让主代理在 QuickJS 沙箱中生成循环、分支和并发批次：工作项保存在变量中，通过 `task()` 分派给不同子代理，最后再用代码聚合结果。所谓“确定性”主要指任务遍历、路由和汇总流程更明确，**并不意味着子代理的判断本身不再随机**。

##### 代码正在成为 Agent 的控制平面

这其实是一种值得迁移的架构分工：让语言模型负责理解问题、生成计划，让解释器负责可靠地执行计划。

文章列出的分类后处理、并行分析、对抗验证、生成后筛选、锦标赛和持续发现，并非几个零散技巧，而是不同的计算结构。例如，审查整个代码库适合并行展开；安全检查则可先发现问题，再交给独立代理复核，只有通过多数验证的结果才保留；范围未知的依赖审计，可以循环搜索并去重，直到不再出现新发现。

这里的收益不只是提速。**显式的数据流让完整性、成本和质量控制都有了可操作的落点**：可以看到处理了多少项、每轮产生什么结果、何时停止，也可以为高风险任务增加复核，而不是笼统地要求模型“更仔细”。

##### 多代理的价值来自流程设计，不来自角色数量

文档也间接修正了一个常见误解：配置更多“专家角色”不会自然提高质量。真正决定效果的是任务能否合理拆分，以及结果是否有清晰的合并规则。

“生成五个方案”只是增加采样；如果评价标准含糊，锦标赛可能只是把偏见反复放大。“多数投票”也只在验证者相对独立时有效；若它们共享同一模型、提示和错误信息，表面共识未必代表更可靠。因此，落地时更应验证三个变量：工作单元是否足够独立、评价标准能否结构化、额外调用成本是否换来了可测量的质量提升。

##### 当前最明显的缺口是治理，而非编排能力

文档提示，解释器内部的 `task()` 不经过常规工具调用路径，父代理的逐次审批不会自动生效，只能在整个解释器执行前设闸。这对代码修改、外部通信或敏感数据处理尤其重要：一旦批准，内部可能批量派发大量任务。再加上运行时仍处于 beta，生命周期和 API 可能变化，现阶段更适合边界清楚、可回滚、以读取和分析为主的工作。

另一个值得注意的细节是，需要用“workflow”这个词来触发动态编排。它是方便的显式模式开关，也说明系统尚不能稳定地自行判断何时值得承担编排开销。对产品设计而言，下一步更关键的能力不是继续增加代理，而是提供**执行计划预览、预算上限、权限继承、过程观测与失败恢复**。当这些控制成为标准组件，多代理才会从演示性的“并行思考”，变成可托付的批量生产系统。

## 默认总结（1）

### 2026-09-18 01:41:04

##### 一句话看懂

LangChain 的“动态子代理”让主代理在 JavaScript 解释器中通过循环、分支和并行任务批量调度多个子代理，比逐次调用更适合大规模、可拆分或需要多角度验证的工作。

##### 关键内容

- 启用时需配置子代理和 `CodeInterpreterMiddleware`，环境要求 Python ≥ 3.11、`langchain-quickjs` ≥ 0.1.0；该能力仍处于 Beta，接口可能变化。
- 在提示中使用 **“workflow”**，会引导代理编写编排代码，通过 `task()` 调用子代理；普通表述更适合单次委派。
- 常见模式包括：分类后交给不同专家、并行处理后汇总、二次验证降低误报、多方案生成与筛选、淘汰赛评选，以及循环搜索直到没有新发现。
- `task()` 在解释器内部直接派发，不经过常规工具调用流程，因此父代理的逐次审批机制不会自动生效；如需人工批准，应限制或审批解释器的 `eval` 工具。

##### 通俗解读

它相当于让主代理先写一段“项目调度脚本”，再把几十项工作同时分给不同助手，最后自动整理结果。优势是批处理更稳定、高效；代价是配置与安全控制更复杂。

**是否值得细读：**如果你正用 Deep Agents 处理批量代码审查、工单分类或高置信度审核，值得细读示例；若只需偶尔调用一个子代理，了解概念即可。
