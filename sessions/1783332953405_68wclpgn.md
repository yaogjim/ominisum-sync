## 分析要点

- **核心高价值点**：将任务拆成“目标、指标、边界”，并让模型基于假设持续实验和记录失败路径，是最值得复用的方法。
- **留存建议**：提取其中可复用的提示词模板和工作流框架后短期保留，模型窗口期相关信息后续可清理（包含可直接试用的目标设定、实验循环、状态文件、记忆更新和反向面试等AI工作流模板）

**知识要点**

- 高质量Agent任务应明确目标、评价指标和不可触碰边界
- 长周期自动化任务需要状态文件记录历史、下一步和停止条件
- 提示词迭代可以通过Shadow Prompt方式在真实流量上做A/B测试
- 个人工作模式、重复指令和纠错经验可转化为Skills、系统指令和记忆库

**行动项**

- 尝试运行六问提示词，让模型总结个人高频工作流并生成可复用模板
- 为一个重复任务设计包含排期、状态文件、检查标准和停止条件的loop
- 将常用提示词按目标、交付格式、红线和介入条件重新结构化
- 对新旧提示词做小规模A/B测试，记录分歧案例和胜负比例

### 分享 8 个 Fable5 下线前必跑的超实用 Prompt

> 榨榨榨榨榨干算力

满打满算，Fable5 还剩不到 48 小时就从订阅计划里下线了，

整个周末我都在把额度刷刷刷满，剩下最后 20% 的时候在 X 上看到一个开发者发的一条长贴，他说他把 Fable 5 的行为模式，再结合 Claude 团队自己开源的 Fable5 提示语技巧，提炼成了一份协议，贴给 Opus 4.8 用。

![Image](https://pbs.twimg.com/media/HMgxPMmaEAAZLJ6?format=jpg&name=large)

顺着这条线往下挖，我用了两天时间把中英文圈十几篇最有料的实战帖全翻了一遍，全变成 prompt，让你现在立刻马上就跑起来的。

我把筛完的东西按稀有度排了个序。先给结论。

Fable 5 最值得做的事情就两类，

第一类，让它自己跑实验。你睡觉，它干活，醒来看报告。

第二类，让它研究你自己，然后把你的工作方式变成一套可复用的系统。

其他所有用法都是这两类的子集。

先说第一类，因为它效果更夸张。

Superpowers 的作者 Jesse Vincent 用 Fable5 做出了 6.0 版本，这个项目里的头脑风暴 brainstorming Skill 属于是入门 Agent 必装的一个 Skill 了，

![Image](https://pbs.twimg.com/media/HMgxKT6bcAAyLIm?format=jpg&name=large)

他做的就是睡觉前给 Fable 写了一个/goal 提示语，翻译成中文就是，

> \## goal目标提示语 /goal 任务完成后，再专门跑一轮成本优化研究，让Opus负责统筹，持续记录“我为什么这么试、预期会怎样、实际结果如何”。至少做 25 次不同实验，每次实验开始前先写清楚假设，失败路线也要完整记录。如果中途发现数据量错了、口径不一致，或者评估方法有问题，要当场修正并继续。

等他第二天起床的时候，25 个实验跑完了。

花了 165 刀就把构建速度提高 50%，token 开销降了 60%。

赚麻了。

这个 goal 提示语跟我之前看到的不同之处就在它补充实验的过程，每个实验都有清楚记录的假设。每个被否定的想法被完整记录下来。Fable5 在跑实验的过程中就发现了自己的三个测量 bug，自己中途修正了。

它在没有任何人类介入的情况下给自己纠错。

而且还很诚实地告诉你哪些优化路径是完全没用，甚至产生负面效果的。

有人觉得「给 Fable5 的思考过程加个字数上限，能省点 token」，Jesse 测了，结果适得其反。Fable5 为了在限制里把话说清楚，反而车轱辘话来回说，原本 92 轮能搞定的事变成了 138 轮，输出翻倍，更贵了。

还有人想「先用便宜的 Sonnet 模型写计划，再让贵的 Fable5 执行」能省钱。Jesse 也测了，Sonnet 写出来的计划虽然看着没问题，但根本不是 Fable 的思路，整个任务结构都乱了。

还有就是「给测试计划设个字数预算」这种看起来很合理的操作，直接把模型的测试内容削减了 62%。其实就像让一个研究员用一页纸写实验方案，在保证每个实验质量不变的情况下，他只能把一半实验删掉。

这些彻底失败的实验结果比成功的还值钱。

因为之后在新的项目上，我不用再花钱重新踩一遍坑。

测试这个 goal 提示语的时候，我想起 Karpathy 大神说过一句话。

「Here's an objective, here's a metric, here's your boundaries of what you can and cannot do. And go.｜ 这是你要达成的目标，这是怎么判断你做完了，这是你的边界。剩下的交给你了。」

目标，指标，边界。三个词。

这其实就是 /goal 提示语的最佳结构。

给模型说清楚要什么结果，怎么判断做完了，什么东西不能碰。

写完这三样，放手让它去发挥。

好，来到第二类，让 Fable5 研究我们，

我觉得这可能是整个窗口期里最被低估的用法，简单来说就是让 Fable5 研究我们的工作模式，优化之后打包成一套系统，交给一个 Opus4.8 或者别的模型去执行。

输出工作模式跟直接总结出一个报告还不太一样，这是一套可以直接用的东西。

你以后切回 Opus 4.8 的时候，它已经知道你是谁，了解你的工作模式了。

> \## 工作模式提示语 遍历我Claude所有的历史聊天记录，重复提示，文档，项目，Skills和工作流程。然后回答： 1、我最常使用Claude做什么？ 2、哪些任务我总是重复地做？ 3、哪些指令我总是手动重写？ 4、哪些工作流程应该变成可重用的Skills？ 5、过去做了哪些事的方法和思路是错的，以你的视角应该要避免？ 6、Opus应该知道什么，这样它就能给我90%的Fable 5体验？ 把所有这些转化为Claude Skills、使用指南、工作流程模板，以及给Opus的系统指令。

![Image](https://pbs.twimg.com/media/HMgxGD4bIAA6WWx?format=jpg&name=large)

那如果之前被封了很多次账号，也没有从被封账号的历史对话记录成功恢复自己的对话，又想要得到一个表现还不错的工作流程的话，那我们就要回到开头的开发者 hiromi maeo 的事了。

他从 Anthropic 的 Fable 5 文档里，反向提炼出了一份能让 Fable5 表现更好的行为规范，

> \## 行动规范提示语 结论先行｜每次汇报第一句话就说「发生了什么」或「发现了什么」，不要让我翻三页才看到结果。 立即行动｜信息够了就动手。不要重新推导已经确定的事实，不要重新讨论已经关闭的决定，不要列一堆你不会采用的方案。 实证汇报｜报告前用工具结果交叉验证。没验证的说没验证，测试失败的把输出原样贴出来。编造进度是最恶劣的失败。 最小范围｜不做要求以外的功能、重构或抽象化。做最小能用的东西。不要写防御不可能发生的场景的代码。 说到做到｜永远不要说「这就去做」然后停下来。执行完再终止。

这样一份行为规范有什么用呢？

Fable 5 虽然聪明，但它不会一个人干完所有活。遇到大任务的时候，它会自己拆分成多个独立任务，派出几个小弟去完成，也就是 subagent，那这些 agent 里面内置的模型可能是便宜一点的 Opus，也可能是再低一档的 Sonnet。

问题是，这些小弟没有 Fable 5 那么聪明。

不明确告诉它们该怎么干活，它们就会按自己的习惯来，可能会磨蹭，可能会重复做已经确定的事，甚至会说好的我这就去做然后就停在这摸鱼。

我们需要一份行为规范，贴在每一个小弟的提示语末尾，这样 subagent 输出的结果会变得更加易读，换成 API 的时候就可以完全让 Fable5 出计划，其他模型去执行。

说到 subagent，这几天还有一个非常极端的任务分配逻辑火了，

既然两天不到就要用 API 了，那就提前适应，让 Fable5 自己判断什么任务下放给便宜模型，什么留给自己。这样 token 消耗就降下来了。

> \## subagent分配提示语 对于任何编码任务，自行判断选择低算力模型并在 subagent 中运行。小任务交给便宜模型，重任务保留全力运行。

我上周开源的搭子 Skill 也是同样的逻辑，

让 Fable5 在出计划的步骤来分配哪个阶段用哪个 Agent，claude code 可以把 codex 也拉进来干活，codex 也可以让 Fable5 在出计划的时候参与进来。

![Image](https://pbs.twimg.com/media/HMgxB0VakAA6o82?format=jpg&name=large)

但是还有人更加极端，直接所有执行都走 codex subagent，让 Fable5 只负责出计划和头脑风暴。

API 计费之后，这种多 Agent 分配的打法大概率会变成主流。

同样的思路，有个叫 Machina 的开发者把让 AI 自己判断什么时候做什么这件事，固化成了 25 个可以直接抄的 loop 工作流（在 claude code 上就是固定的时间间隔运行某个任务），也就是说把 fable5 加入到自动化工作流里了。

每个 loop 有五个要素。

一个排期表，什么时候醒来。每轮只改一件事。同一个检查标准，让本周的分数和上周可比。一个状态文件，记录做了什么、下一步是什么。一个停止条件，硬性限制轮次的上限加上对完成和流程被堵住的定义。

他还给每个定时任务标了颜色。

绿色完全自动跑。

黄色要我们审批才能发出去。

红色涉及生产环境或者外发消息，就不能在无人的时候自动跑。

我把这个 25 个定时任务都看完了，状态文件就是让每次运行比上一次更聪明的关键。模型每轮开始前先读自己上一轮的历史，这样它永远都不会重做已完成的工作。

这 25 个 loop 里，我觉得最值得抄的是 Shadow prompt loop，一句话总结就是测新提示语的效果的时候走流量的 A/B Test。让新旧两个 prompt 同时跑在真实流量上，用数据决定好坏。

> \## loop提示语 /loop daily, on real traffic 读取 shadow-prompt-STATE.md，里面记录了： - baseline prompt（当前线上版本） - candidate prompt（待验证的新版本） - 已积累的 disagreement cases（两个 prompt 输出不一致的真实请求） 本轮任务： 1. 从今天真实流量中抽取 N 条代表性请求（边缘 case、高频场景各占一半） 2. 同时用baseline和candidate各跑一遍，记录输出 3. 只记录有分歧的case（输出明显不同），相同的跳过 4. 每个分歧case标注：哪个更好、为什么、是否 candidate 一致性更优 约束： - 不直接替换线上prompt，只积累对比数据 - 积累50个有效分歧case后，生成一份「是否切换」的推荐报告 - 报告必须包含：candidate胜/平/负的比例，典型分歧场景，切换风险评估 State file（状态文件）: shadow-prompt-STATE.md（记录：已测多少条、disagreement堆、当前结论） Stop（停止条件）: 50 个分歧 case 或 14 天 Color: 🟢 Green（只读流量 + 写 state file，不改线上配置）

我现在其他 loop 都统一成了这个模版。

最后说两个 Anthropic 官方放出来的提示语模板。我自己验证过，直接能用，也已经设成 hook 了。

第一个是自动检查点。

Fable5 确实可以长时间运行，我基本都把权限拉满的，但还是需要它在关键时刻停下来问我，

> \## 自治运行 + 自动暂停提示语 只在工作真正需要我介入时暂停，破坏性或不可逆的操作，真正的范围变更，或者只有我才能提供的信息。其他情况继续推进，完成后汇报。

第二个是记忆系统。

这个我已经设成 hook 了，只要说「记一下」就自动触发。

主要是因为被封的次数太多了，每次封完回来都是一片空白。

有了这个 hook，它至少能从错题本里知道上一世犯过什么错，保留一手前世记忆。

> \## 记忆更新提示语 每条经验单独存成一条记录，开头用一句话概括。 只记录两类东西： 1. 被我纠正过、下次不能再犯的点 2. 已经验证有效、以后可以复用的方法 每条记录要写清楚它为什么重要。 不要记录仓库、文档或聊天记录里已经有的信息。 如果已有相似记录，就更新旧记录，不要重复新建。 如果后来发现某条记忆是错的，就删掉或标记废弃。

最后补一个动手前让 Fable5 反向面试你的提示语，

在写需求文档的时候，等它问到 95% 有把握了，再进入正式执行。

> \## 反向面试提示语 问我问题，直到你有95%的把握可以把这件任务完成

问清楚之后，就给 Fable5 开个计划模型（plan）按照 Anthropic 推荐的/goal 结构化写法模板做一个初版本，

> \## goal目标提示语 背景：我在为 \[谁\] 做 \[什么项目\]，他们需要 \[这个东西能帮他们解决什么问题\]。 具体要求：\[用一句话说清楚你要什么\] 交付格式：\[你希望最终结果是什么样的，怎么给你\] 红线：\[过程中绝对不能做什么事\]

#### 深度总结

##### 一句话概括

这篇文章的核心不是“收藏 8 个 Prompt”，而是：**趁强模型还便宜，把它用来沉淀可复用的工作系统，而不是只拿来做一次性任务。**

---

##### 核心观点

Fable5 最值得做两件事：

1. **让它自己跑实验**
   - 给目标、指标、边界；
   - 让模型自动尝试、记录、复盘、纠错；
   - 重点不是成功实验，而是把失败路线也沉淀下来。

2. **让它研究你自己**
   - 分析你的历史对话、重复任务、常用指令；
   - 把你的工作方式转成 Skills、模板、系统指令；
   - 让之后更便宜或更弱的模型也能复用你的工作流。

---

#### 8 个 Prompt 的本质

| Prompt | 本质用途 |
|---|---|
| `/goal` 目标实验 | 让模型像研究员一样自动做实验 |
| 工作模式分析 | 把“你怎么工作”提炼成系统 |
| 行动规范 | 约束 subagent 别废话、别瞎做 |
| subagent 分配 | 贵模型做规划，便宜模型做执行 |
| loop 工作流 | 让 AI 定期自动迭代任务 |
| 自动暂停 | 只在真正需要人类时打断 |
| 记忆更新 | 建立长期错题本和复用经验库 |
| 反向面试 | 先问清需求，再开始执行 |

---

#### 深入浅出解读

##### 1. 不要把强模型当“聊天机器人”

普通用法：

> 我问一句，它答一句。

高级用法：

> 我给它目标、评价标准和限制，它自己去实验、执行、记录、复盘。

也就是从 **问答模式** 变成 **项目经理 + 研究员模式**。

---

##### 2. 好 Prompt 的核心是三件事

> **目标、指标、边界。**

例如：

- 目标：把构建速度提升 50%
- 指标：运行时间、token 成本、错误率
- 边界：不能改生产配置，不能删数据

模型最怕的不是任务难，而是任务模糊。

---

##### 3. 失败实验比成功实验更值钱

文章里强调：

> 哪些方法没用，甚至有害，也要记录。

因为失败记录可以避免以后重复烧钱。

这其实就是把 AI 使用过程变成一套“实验资产”。

---

##### 4. 最重要的资产不是模型，而是你的工作系统

模型会换，订阅会变，价格会涨。

但这些东西可以留下：

- 你的工作流
- 你的常用 Prompt
- 你的错误记录
- 你的项目模板
- 你的自动化规则
- 你的个人 Claude / AI 使用手册

真正应该沉淀的是这些。

---

#### 文章背后的方法论

可以压缩成一个公式：

> **强模型负责探索和设计，弱模型负责执行和复用。**

再进一步：

> **一次性输出不重要，可复制流程才重要。**

所以文章真正提倡的是：

- 把 Prompt 变成 Skill；
- 把经验变成 Memory；
- 把任务变成 Loop；
- 把个人习惯变成系统指令；
- 把模型能力变成自动化流程。

---

#### 辩证思考

##### 值得肯定

###### 1. 从“使用 AI”升级为“训练自己的 AI 工作系统”

这比单纯追新模型更有长期价值。

###### 2. 强调实证，而不是感觉

A/B Test、真实流量、状态文件、失败记录，这些都让 AI 使用更工程化。

###### 3. 把人从重复劳动中解放出来

重复三次以上的任务，就应该考虑自动化。

这是 AI 时代非常重要的工作习惯。

---

##### 需要警惕

###### 1. 自动化不等于可靠

模型会误判、遗漏、过度自信。

尤其是涉及：

- 生产环境
- 用户数据
- 外发信息
- 金融、法律、医疗等高风险场景

必须有人类审批。

---

###### 2. “烧额度”不一定等于高 ROI

文章主张“不要怕烧 API 额度”，但前提是：

> 你烧出来的是可复用资产。

如果只是反复让模型闲聊、重写、空转，那就是浪费。

---

###### 3. 工作模式沉淀也有隐私风险

让模型遍历历史聊天、文档、项目，确实能生成好系统。

但也可能暴露：

- 商业机密
- 客户信息
- 个人隐私
- 内部流程

因此必须做好权限和数据边界。

---

#### 我的结论

这篇文章最有价值的不是那几个 Prompt，而是一个转变：

> **不要只让 AI 帮你完成任务，要让 AI 帮你升级完成任务的方式。**

最值得立刻做的一个动作：

```text
让模型分析你的历史工作记录，
找出重复任务、常用指令、低效流程，
然后生成一套可复用的 Skills、模板和系统指令。
```

因为模型会过期，额度会消失。

但你的工作系统一旦沉淀下来，会持续复利。

## 结构化（1）

### 2026-07-22 09:34:34

#### 《分享 8 个 Fable5 下线前必跑的超实用 Prompt》精炼总结

文章认为，Fable5 下线订阅计划前，最值得做的只有两类事：**让它自主实验、持续优化；让它研究你的工作方式，并沉淀成可复用的 Skills、流程和记忆系统**。模型会更换、窗口会关闭，但这些工作资产可以长期保留，并交给 Opus 4.8 等其他模型继续使用。

##### 一、核心思路：把 Fable5 当成研究员和系统设计师

作者用两天时间整理了中英文圈十几篇实战帖，将高价值用法归纳为两类：

1. **自主实验**：给出目标、指标和边界，让模型在无人干预下反复测试、纠错并提交报告。
2. **研究用户**：分析历史聊天、重复任务和工作习惯，将个人经验转化为 Skills、模板、系统指令和“错题本”。

其他用法，如多 Agent 协作、定时循环、记忆更新，本质上都服务于这两类目标。

---

##### 二、Prompt 1：用 `/goal` 让模型自主完成实验

###### 核心写法

一个高质量 `/goal` 应明确三件事：

- **目标**：最终要得到什么结果；
- **指标**：如何判断任务完成、效果是否提升；
- **边界**：哪些事情不能做、哪些范围不能超出。

同时要求模型：

- 至少进行多轮不同实验；
- 每次实验前写出假设和预期；
- 记录实际结果及失败路线；
- 发现数据、口径或评估方法有误时，立即修正并继续。

###### 实战案例

Superpowers 作者 Jesse Vincent 让 Fable5 独立完成 **25 次实验**。第二天得到的结果是：

- 花费约 **165 美元**；
- 构建速度提升 **50%**；
- Token 开销降低 **60%**；
- 模型还自行发现并修复了 **3 个测量 Bug**。

###### 失败实验同样重要

实验还推翻了几个看似省钱的方案：

- 给思考过程设置字数上限后，任务轮次从 **92 轮增加到 138 轮**，输出翻倍，反而更贵；
- 先让 Sonnet 写计划、再交给 Fable5 执行，会因模型思路不一致而打乱任务结构；
- 给测试计划限制字数，会让测试内容减少 **62%**，相当于被迫删除大量实验。

关键价值不仅是找到有效方案，也在于**完整记录无效路线，避免以后重复花钱踩坑**。

---

##### 三、Prompt 2：让 Fable5 研究你的工作模式

这类 Prompt 不是让模型生成一份普通总结，而是要求它把你的工作习惯转化为可直接复用的系统。

###### 建议分析的六个问题

1. 我最常使用 Claude 做什么？
2. 哪些任务总在重复？
3. 哪些指令经常需要手动重写？
4. 哪些流程应该封装成 Skills？
5. 过去有哪些方法或思路是错误的，今后应避免？
6. Opus 需要知道什么，才能提供约 **90% 的 Fable5 使用体验**？

最终应输出：

- Claude Skills；
- 使用指南；
- 工作流程模板；
- 可复用的系统指令；
- 个人常见错误和避坑清单。

这样即使更换模型或账号丢失，也能快速恢复熟悉的工作方式。

---

##### 四、Prompt 3：为所有 Subagent 统一行动规范

Fable5 遇到大任务时会拆分工作，并交给多个 Subagent 执行。但低成本模型可能出现拖延、重复劳动、汇报不实或只说“马上做”却不真正执行的问题。

因此，应在每个 Subagent 的提示语末尾加入统一行为规范：

- **结论先行**：第一句话说明发生了什么、发现了什么；
- **立即行动**：信息充分后直接执行，不重复讨论已经确定的事项；
- **实证汇报**：用工具结果交叉验证，未验证的明确说明，失败输出如实保留；
- **最小范围**：只做任务要求的内容，不额外重构、抽象或增加功能；
- **说到做到**：不要停留在“这就去做”，执行完成后再结束。

这能让 Fable5 负责规划，其他模型负责执行，同时保证结果更加可靠、易读。

---

##### 五、Prompt 4：让模型自主分配不同算力的 Agent

为了适应按 Token 计费，可以让 Fable5 自己判断任务难度：

> 小任务交给便宜模型或 Subagent，复杂任务保留给高算力模型。

更进一步的做法是：

- Fable5 只负责规划、头脑风暴和关键决策；
- Codex、Sonnet 或其他低成本模型负责具体执行；
- 在计划阶段就明确每一步由哪个 Agent 完成。

有人甚至把所有执行工作都交给 Codex Subagent，只让 Fable5 负责计划。作者认为，进入 API 计费后，这种**多 Agent 分工模式很可能成为主流**。

---

##### 六、Prompt 5：用 Loop 建立可持续自动化流程

开发者 Machina 将自动化任务固化为 **25 个 Loop 工作流**。每个 Loop 包含五个要素：

1. **排期表**：何时自动唤醒运行；
2. **单一改动**：每轮只修改一件事；
3. **统一指标**：确保本周和上周的数据可比较；
4. **状态文件**：记录已完成内容和下一步；
5. **停止条件**：限制最大轮数，并定义完成或阻塞状态。

其中，状态文件最重要：模型每轮开始前先读取上一轮记录，从而避免重复做已经完成的工作。

###### 风险颜色分类

- 🟢 **绿色**：可以全自动运行；
- 🟡 **黄色**：执行或发布前需要人工审批；
- 🔴 **红色**：涉及生产环境或外发消息，不能无人值守运行。

###### 最值得复用的 Shadow Prompt Loop

该 Loop 用真实流量对新旧 Prompt 进行 A/B 测试：

- 从真实请求中抽取样本，边缘案例和高频场景各占一半；
- baseline 与 candidate 同时运行；
- 只记录输出明显不同的案例；
- 判断哪一个更好、原因是什么；
- 不直接替换线上 Prompt，只积累证据；
- 达到 **50 个有效分歧案例**或运行 **14 天**后停止；
- 最终报告需包含 candidate 的胜、平、负比例，典型场景和切换风险。

---

##### 七、Prompt 6：自治运行，但在关键节点自动暂停

Fable5 可以长时间自主运行，但不能完全取消人工控制。官方推荐的原则是：

> 只有在真正需要用户介入时才暂停，其他情况持续推进，完成后统一汇报。

需要暂停的主要情况包括：

- 破坏性或不可逆操作；
- 任务范围发生实质变化；
- 缺少只有用户才能提供的信息。

这样既能减少不必要的确认，又能在高风险节点保留人工决策权。

---

##### 八、Prompt 7：建立长期记忆和个人“错题本”

作者将记忆更新设置成 Hook，只要说“记一下”就自动触发，用于应对账号被封或历史对话丢失后的工作断层。

记忆系统只记录两类内容：

1. 用户纠正过、以后不能再犯的错误；
2. 已经验证有效、未来可以复用的方法。

每条记忆应做到：

- 单独保存，并用一句话概括；
- 说明为什么重要；
- 不重复记录仓库、文档或聊天中已有的信息；
- 发现相似记录时更新旧内容，而不是新建重复项；
- 后来发现记忆错误时，删除或标记废弃。

其作用是让模型拥有跨项目、跨账号的“前世记忆”，持续减少重复犯错。

---

##### 九、Prompt 8：正式执行前，让模型反向面试你

在需求不够明确时，不要直接让模型开始工作，而是要求它：

> 持续提问，直到对完成任务有 **95% 的把握**。

信息确认后，再进入 Plan 模式，并按 `/goal` 结构生成初版计划：

- **背景**：为谁做什么项目，要解决什么问题；
- **具体要求**：用一句话说明最终需求；
- **交付格式**：结果应以什么形式提供；
- **红线**：过程中绝对不能做什么。

这能显著减少模型因理解偏差造成的返工。

---

##### 十、最终建议：把重复工作沉淀为长期资产

Claude Code 团队的习惯是：**任何工作重复三次以上，就想办法让 AI 自动化**。

Fable5 从订阅制转为按 Token 计费后，Prompt 的设计会直接影响账单，但作者认为不必一味追求便宜模型：高能力模型虽然单价高，却可能通过更少的返工、更好的计划和更准确的执行，成为总体成本更低的方案。

在窗口关闭前，最值得做的最小动作，是重新运行“六问工作模式 Prompt”，让 Fable5 把你沉淀为一套可复用的 Skill。模型会变、服务会下线，但以下资产可以长期保留：

- 工作模式；
- Prompt 和 Skills；
- 自动化流程；
- 状态文件；
- 错题本；
- 与模型协作的长期记忆。

作者认为，这可能是整个窗口期里 **ROI 最高的 20 分钟**。
