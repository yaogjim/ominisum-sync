## 分析要点

- **核心高价值点**：将动态端口与访问地址解耦，并为 Git worktree 自动生成分支子域名，可显著降低多项目、多代理并行开发时的端口冲突和地址管理成本。
- **留存建议**：建议精读并存档，作为多应用本地开发环境配置参考（提供了完整的安装、配置、路由、HTTPS、工作树及远程分享方案，命令和边界条件明确，具有较强复用价值。）

**知识要点**

- Portless 为应用分配随机内部端口，再通过稳定的命名域名和本地反向代理提供访问入口。
- Git worktree 可自动使用分支名作为子域名前缀，使不同工作树拥有互不冲突的固定 URL。
- 自定义真实域名形式的 TLD 可让本地环境更接近生产环境，并适配严格限制回调域名的 OAuth 提供商。

**行动项**

- 全局安装 Portless，并选择一个现有项目用 portless run 启动，验证命名 URL、HTTPS 和热更新。
- 在 Monorepo 中创建 portless.json，为前端、API 等工作区配置稳定名称并测试统一启动。
- 使用 portless doctor 检查代理、DNS 和本地 CA 信任状态，再根据需要启用 LAN、Tailscale 或 ngrok 分享。

#### portless

用稳定的、命名的.localhost URL 替代端口号，用于本地开发。面向人类和代理。

```
- "dev": "next dev"                  # http://localhost:3000
+ "dev": "portless run next dev"     # https://myapp.localhost
```

#### Install

**Global (recommended):**

```
npm install -g portless
```

**或者作为项目的开发依赖：**

```
npm install -D portless
```

> portless 尚未发布 1.0 版本。按项目安装时，不同的贡献者可能运行不同的版本。状态目录格式可能在不同发布之间发生变化，这可能需要重新运行 `portless trust` 。

```
portless myapp next dev
# -> https://myapp.localhost
```

默认启用带 HTTP/2 的 HTTPS。首次运行时，portless 会生成一个本地 CA、信任它，并绑定端口 443（在 macOS/Linux 上会自动通过 sudo 提权）。使用 `--no-tls` 来启用纯 HTTP。

当你运行应用时，代理会自动启动。一个随机端口（4000-4999）通过 `PORT` 环境变量分配。大多数框架（Next.js、Express、Nuxt 等）会自动遵循这一点。对于忽略 `PORT` 的框架（Vite、VitePlus、Astro、React Router、Angular、Expo、React Native），portless 会自动注入正确的 `--port` 标志，并在需要时注入匹配的 `--host` 标志。注入会穿透命令以框架或已知运行器（ `"dev": "vite"` 、 `"dev": "bunx vite"` ）开头的包脚本。只有框架的服务器命令会获得这些标志（ `dev` 、 `serve` 、 `preview` 、 `start` 、裸 `vite` 或 `vite [root]` ）；不提供服务的命令，例如 `vite build` 、 `vite optimize` 、 `vp test` 或 `astro check` ，会拒绝这些标志并保持原样。Expo 连接模式（ `--localhost` 、 `--lan` 、 `--tunnel` ）会被保留，同时仍会注入分配的端口。portless 无法分类的脚本也会保持原样：在其标志语法未被跟踪的 CLI 上，标志位于子命令之前（ `vp --mode dev build` ）。当向脚本追加标志无法生效时，portless 也会保持该脚本原样：复合命令（ `&&` 、 `|` 、 `;` ）、末尾的 `#` 注释、它自己的 `--` 选项终止符、环境变量前缀（ `NODE_ENV=production vite` ）、委托给另一个脚本（ `"dev": "npm run dev:vite"` ），或脚本名称之前的运行器标志（ `bun run --bun dev` ）。这些会保留自己的端口，因此请在脚本中自行设置。

自动启动时，portless 会复用最近一次代理运行的配置（端口、TLS、TLD），因此重启或重新启动不会静默恢复为默认值。显式环境变量（ `PORTLESS_PORT` 、 `PORTLESS_HTTPS` 等）始终优先。

Portless 将每个用户的状态存储在 `~/.portless` 中。当代理在 sudo 下运行时，它会从调用用户的主目录解析此路径，以便代理和非特权应用进程共享相同的路由注册。

在非交互式环境中（无 TTY，或 `CI=1` ），portless 会以描述性错误退出而不是提示，因此像 turborepo 和 CI 脚本这样的任务运行器会尽早失败并给出清晰的消息。

#### Configuration

裸 `portless` 开箱即用。它通过代理运行来自 `package.json` 的 `"dev"` 脚本，从包名、git 根目录或目录推断应用名称：

```
portless        # -> runs "dev" script, https://<project>.localhost
```

使用可选的 `portless.json` 来覆盖默认值：

```
{ "name": "myapp" }
```

```
portless        # -> runs "dev" script, https://myapp.localhost
```

该脚本默认为 `"dev"` 。如果未在配置中设置，名称将从 `package.json` 推断。

##### Monorepo

仓库根目录下的一个 `portless.json` 覆盖所有工作区包。Portless 从 `pnpm-workspace.yaml` 或 `package.json` 中的 `"workspaces"` 字段（npm、yarn、bun）发现包：

```
{
  "apps": {
    "apps/web": { "name": "myapp" },
    "apps/api": { "name": "api.myapp" }
  }
}
```

```
portless        # from repo root: starts all workspace packages with a "dev" script
cd apps/web && portless   # start just one package
```

`apps` 映射是可选的，仅在需要名称覆盖时需要。未列出的包仍会自动发现，名称从其 `package.json` 推断。

没有 `apps` 映射时，主机名遵循 `<package>.<project>.localhost` 约定。项目名称来自工作区包中最常见的 npm scope（例如 `@myorg/web` 和 `@myorg/api` 产生 `myorg` ），回退到工作区根目录名称。如果包的短名称与项目名称匹配，它将获得裸 `<project>.localhost` 而无需重复。

##### Config fields

Field Type Default Description

`name` string inferred 基础应用名称。worktree 前缀仍然适用。

`script` string `"dev"` Name of a `package.json` script to run.

`appPort` number auto 子进程的固定端口。

`proxy` boolean auto 是否通过代理进行路由。自动检测。

`apps` object 工作区包的覆盖项，以相对路径为键。

`turbo` boolean `true` 设置 `false` 以使用直接生成，而不是 turborepo。

除了单独的 `portless.json` 之外，你还可以向你的 `package.json` 添加一个 `"portless"` 键。字符串值是设置名称的简写：

```
{
  "name": "@myorg/web",
  "portless": "myapp"
}
```

对象支持所有按应用字段（ `name` 、 `script` 、 `appPort` 、 `proxy` ）：

```
{
  "name": "@myorg/web",
  "portless": { "name": "myapp", "script": "dev:app" }
}
```

`package.json` `"portless"` 键优先于 `portless.json` 应用条目，但会被 CLI 标志覆盖。

##### --script flag

为单次调用覆盖默认脚本：

```
portless --script start       # run "start" instead of "dev"
portless --script test        # run "test" instead of "dev"
```

##### Turborepo

要将 portless 与 turborepo 一起使用，请将 `portless` 作为 `dev` 脚本，并将实际命令放在单独的脚本中：

```
{
  "scripts": {
    "dev": "portless",
    "dev:app": "next dev"
  },
  "portless": { "name": "myapp", "script": "dev:app" }
}
```

Turbo 会运行每个包的 `dev` 脚本，该脚本会调用 portless。Portless 读取配置，检测包管理器，并通过代理运行 `pnpm run dev:app` （或 yarn/bun/npm）。无需更改 `turbo.json` 。

根目录下的 `pnpm dev` 会像往常一样通过 turbo 工作。没有 portless 的人可以直接运行 `pnpm run dev:app` 。

你仍然可以在 `package.json` 脚本中使用 portless：

```
{
  "scripts": {
    "dev": "portless run next dev"
  }
}
```

使用 `portless.json` 后，你可以简化为：

```
{
  "scripts": {
    "dev": "next dev"
  }
}
```

然后运行 `portless` 或 `portless run` 以通过代理。

当你按下 Ctrl+C 时，portless 会转发该中断信号，并等待命令的进程树退出。再次按下 Ctrl+C 可转发另一次中断信号。任何剩余的后代进程将在短暂的宽限期后被终止。

#### Subdomains

使用子域名组织服务：

```
portless api.myapp pnpm start
# -> https://api.myapp.localhost

portless docs.myapp next dev
# -> https://docs.myapp.localhost
```

默认情况下，只有显式注册的子域名才会被路由（严格模式）。启动代理时使用 `--wildcard` 可允许已注册路由的任意子域名回退到该应用（例如 `tenant1.myapp.localhost` 会路由到 `myapp` 应用，无需额外注册）。

#### Git Worktrees

`portless run` 会自动检测 git worktree。在链接的 worktree 中，分支名称会作为子域名前置，因此每个 worktree 都会获得自己的 URL，无需任何配置更改：

```
# Main worktree (no prefix)
portless run next dev   # -> https://myapp.localhost

# Linked worktree on branch "fix-ui"
portless run next dev   # -> https://fix-ui.myapp.localhost
```

使用 `--name` 覆盖推断出的基础名称，同时保留 worktree 前缀：

```
portless run --name myapp next dev   # -> https://fix-ui.myapp.localhost
```

将 `portless run` 放入 `package.json` 一次，即可在任何地方使用。主检出使用普通名称，每个 worktree 获得唯一的子域名。无冲突，无需 `--force` 。

#### Custom TLD

默认情况下，portless 使用 `.localhost` ，在大多数浏览器中会自动解析为 `127.0.0.1` 。如果你更喜欢其他 TLD（例如 `.test` ），请使用 `--tld` ：

```
portless proxy start --tld test
portless myapp next dev
# -> https://myapp.test
```

代理会自动同步 `/etc/hosts` 以用于路由主机名（包括 `.test` ），因此这些域名会在你的机器上解析。

重复 `--tld` 以从单个代理为同一应用名称在多个 TLD 下提供服务：

```
portless proxy start --tld localhost --tld test
portless myapp next dev
# -> https://myapp.localhost
# -> https://myapp.test
```

当配置了多个 TLD 时， `PORTLESS_URL` 使用第一个 TLD。 `PORTLESS_TLD` 也接受逗号分隔的列表，例如 `PORTLESS_TLD=localhost,test` 。

推荐： `.test` （IANA 保留，无冲突风险）。避免使用 `.local` （与 mDNS/Bonjour 冲突）和 `.dev` （Google 所有，通过 HSTS 强制使用 HTTPS）。

##### Multi-segment TLDs

`--tld` 值接受小写 DNS 名称（一个或多个以点分隔的标签，无尾随点），因此您拥有的域名可以用作“TLD”。这使本地 URL 具有与生产环境相同的结构，从而保持 OAuth 重定向 URI、跨子域 Cookie 和基于主机的路由在两种环境中以相同方式工作：

```
portless proxy start --tld dev.example.com
portless myapp next dev
# -> https://myapp.dev.example.com
```

每个标签必须遵循 DNS 规则：小写字母、数字和内部连字符，每个标签最多 63 个字符，总计最多 253 个字符。完整主机名（ `app.TLD` ）也受 253 字符 DNS 限制的约束。

代理会自动为已注册的主机名同步 `/etc/hosts` ，因此 `myapp.dev.example.com` 在您的机器上解析为 `127.0.0.1` 。这是仅限回环的设置：在 LAN 模式之外，代理仅绑定到 `127.0.0.1` 和 `::1` （见下文），因此自定义 TLD 只能从运行代理的机器访问。要从其他设备访问代理，需要 LAN 模式（ `--lan` ），但 LAN 模式在 `.local` TLD 下提供应用服务，并忽略自定义 `--tld` ，因此目前两者无法结合使用。

严格的 OAuth 提供商（Google、Apple）会拒绝 `.localhost` 和 `.test` 重定向 URI，但接受真实域名，因此 `https://myapp.dev.example.com/api/auth/callback/google` 可作为重定向 URI 使用。

在非 LAN 模式下，代理及其 HTTP 重定向监听器仅绑定到 IPv4 和 IPv6 回环地址，即 `127.0.0.1` 和 `::1` 。它们不接受通过 LAN、VPN 或其他网络接口的连接。

默认启用带 HTTP/2 的 HTTPS。浏览器将 HTTP/1.1 限制为每个主机 6 个连接，这会对提供大量未打包文件的开发服务器（Vite、Nuxt 等）造成瓶颈。HTTP/2 通过单个连接多路复用所有请求。

WebSocket 在两种协议版本上均可工作，因此开发服务器 HMR（Next.js、Vite 等）可通过代理正常工作：HTTP/1.1 的 `Upgrade` 请求按原样转发，而通过 HTTP/2 连接打开的 WebSocket 使用扩展 CONNECT（RFC 8441）。

首次运行时，portless 会生成一个本地 CA 并将其添加到你的系统信任存储中。没有浏览器警告。无需手动设置。

```
# Use your own certs (e.g., from mkcert)
portless proxy start --cert ./cert.pem --key ./key.pem

# Disable HTTPS (plain HTTP on port 80)
portless proxy start --no-tls

# If you skipped the trust prompt on first run, trust the CA later
portless trust
```

在 Linux 上， `portless trust` 支持 Debian/Ubuntu、Arch、Fedora/RHEL/CentOS 和 openSUSE（通过 `update-ca-certificates` 或 `update-ca-trust` ）。在 Windows 上，它使用 `certutil` 将 CA 添加到系统信任存储中。在 WSL 上，它会同时更新 Linux 信任存储和 Windows 当前用户根存储，以便 Windows 浏览器信任 portless HTTPS 证书。

将代理安装为操作系统启动服务，这样重启后无需从终端启动代理即可使用简洁的 HTTPS URL：

```
portless service install
portless service install --lan
portless service install --wildcard
PORTLESS_STATE_DIR=~/.portless-lan PORTLESS_LAN=1 portless service install
portless service status
portless service uninstall
```

除非提供了安装选项或 `PORTLESS_*` 环境变量，否则服务使用 portless 默认值：HTTPS 使用端口 443，并使用 `.localhost` 名称。 `service install` 接受你会与 `proxy start` 一起使用的代理选项，包括 `--port` 、 `--no-tls` 、 `--lan` 、 `--ip` 、 `--tld` 、 `--wildcard` 、 `--cert` 和 `--key` 。使用 `--state-dir <path>` 或 `PORTLESS_STATE_DIR=<path>` 来选择服务状态和日志的写入位置。

所选的服务配置会写入 launchd、systemd 或任务计划程序，并在重启后复用。 `portless service status` 会报告已安装的端口、HTTPS 模式、TLD、LAN 模式、通配符模式和状态目录。macOS 和 Linux 会安装一个 root 拥有的服务，以便端口 443 可以在启动时绑定。Windows 会安装一个以 SYSTEM 身份运行的任务计划程序启动任务。安装和移除可能需要管理员权限。 `portless clean` 会自动移除该服务。

#### LAN mode

```
portless proxy start --lan
portless proxy start --lan --https
portless proxy start --lan --ip 192.168.1.42
```

`--lan` 会显式地将代理绑定到 IPv4 和 IPv6 未指定地址，即 `0.0.0.0` 和 `::` ，并切换到 mDNS 发现。这会使服务以 `<name>.local` 的形式可供同一网络上的设备访问。Portless 会自动检测你的 LAN IP，并自动跟随 Wi-Fi/IP 变化，但你可以使用 `--ip <address>` 或通过导出 `PORTLESS_LAN_IP` 来固定另一个地址。在你的 Shell 中设置 `PORTLESS_LAN=1` （0/1 布尔值），以便在代理启动时默认启用 LAN 模式。

Portless 通过 `proxy.lan` 记住 LAN 模式，因此如果你停止 LAN 代理并再次启动它，它会保持 LAN 模式。所有代理设置（端口、TLS、TLD、LAN）都会被持久化，并在自动启动时复用，除非被显式标志或环境变量覆盖。使用 `PORTLESS_LAN=0` 进行一次启动即可切换回 `.localhost` 模式。如果代理已在运行且具有不同的显式 LAN/TLS/TLD 设置，portless 会发出警告并要求你先停止它。

LAN 模式依赖于 portless 已经启动的系统 mDNS 工具：macOS 自带 `dns-sd` ，而 Linux 使用来自 `avahi-utils` 的 `avahi-publish-address` （通过 `sudo apt install avahi-utils` 或你的发行版中的等效方式安装）。如果该命令缺失或你的网络不可达， `portless proxy start --lan` 会打印相关错误并退出。

##### Framework notes

- Next.js：将你的 `.local` 主机名添加到 `allowedDevOrigins` ：
  ```
  // next.config.js
  module.exports = {
    allowedDevOrigins: ["myapp.local", "*.myapp.local"],
  };
  ```
- Expo / React Native：portless 始终注入 `--port` 。React Native 还会获得 `--host 127.0.0.1` 。Expo 在 LAN 模式之外会获得 `--host localhost` ，但在 LAN 模式下，portless 会让 Metro 保持其默认 LAN 主机行为，而不是强制使用 `--host` 或 `HOST` 。

#### Tailscale sharing

通过你的 Tailscale 网络与队友共享你的开发服务器：

```
portless myapp --tailscale next dev
# -> https://myapp.localhost           (local)
# -> https://devbox.yourteam.ts.net    (tailnet)
```

每个 `--tailscale` 应用都根挂载在其自己的 Tailscale HTTPS 端口上，因此不需要任何框架 `basePath` 配置。第一个应用获得端口 443，后续应用获得 8443、8444 等。

```
portless myapp --tailscale next dev     # -> https://devbox.ts.net
portless api --tailscale pnpm start     # -> https://devbox.ts.net:8443
```

使用 `--funnel` 通过 Tailscale Funnel 将你的开发服务器暴露到公共互联网：

```
portless myapp --funnel next dev
# -> https://devbox.yourteam.ts.net    (public)
```

在 `--tailscale` 或 `--funnel` 能够注册 HTTPS URL 之前，必须启用 Tailscale HTTPS 证书。在 `--funnel` 能够注册公共 URL 之前，还必须为 tailnet 和节点启用 Funnel。如果缺少任一设置，portless 会在启动子进程之前退出。

在你的 shell 配置文件中设置 `PORTLESS_TAILSCALE=1` ，或设置 `.env` 以默认共享每个应用。 `portless list` 会同时显示本地 URL 和 tailnet URL。当应用退出时，Tailscale serve 注册会自动清理。

需要安装并连接 Tailscale CLI（ `tailscale up` ），并启用 Tailscale HTTPS 证书。

#### ngrok sharing

使用 ngrok 将你的开发服务器暴露到公共互联网：

```
portless myapp --ngrok next dev
# -> https://myapp.localhost           (local)
# -> https://abc123.ngrok.app          (public)
```

在你的 shell 配置文件中设置 `PORTLESS_NGROK=1` ，或设置 `.env` 以在 portless 运行应用时默认启用 ngrok。 `portless list` 会同时显示本地 URL 和 ngrok URL。当应用退出时，ngrok 隧道会自动清理。

需要安装并认证 ngrok CLI。如果 ngrok 报告认证错误，请运行 `ngrok config add-authtoken <token>` 并重试。

#### Troubleshooting

运行 `portless doctor` 可在不改变状态的情况下检查本地健康状况。它会检查 Node.js、状态目录、代理存活状态、路由条目、HTTPS CA 信任、主机名解析以及局域网模式先决条件，然后打印建议的修复方案。

如果你的前端开发服务器（例如 Vite、webpack）将 API 请求代理到另一个 portless 应用，请确保代理重写 `Host` 请求头。否则，portless 会将请求路由回前端，导致无限循环。

**Vite** (`vite.config.ts`):

```
server: {
  proxy: {
    "/api": {
      target: "https://api.myapp.localhost",
      changeOrigin: true,
      ws: true,
    },
  },
}
```

**webpack-dev-server** (`webpack.config.js`):

```
devServer: {
  proxy: [{
    context: ["/api"],
    target: "https://api.myapp.localhost",
    changeOrigin: true,
  }],
}
```

Portless 会自动在子进程中设置 `NODE_EXTRA_CA_CERTS` ，以便 Node.js 信任 portless CA。如果你在 portless 之外运行单独的 Node.js 进程，请手动将其指向该 CA： `NODE_EXTRA_CA_CERTS=~/.portless/ca.pem` 。或者，使用 `--no-tls` 以使用纯 HTTP。

Portless 会检测到这种错误配置，并返回 `508 Loop Detected` 以及指向此修复方案的消息。

#### Portless：用稳定域名替代本地开发端口

##### 一句话概括

**Portless 是一个本地开发反向代理工具，将`localhost:3000`这类动态端口替换为`https://myapp.localhost`这样的稳定、可读 URL，让开发者和 AI Agent 更容易访问、识别和管理本地服务。**

##### 核心工作方式

启动应用时，Portless 会：

1. 为应用分配一个随机内部端口；
2. 通过`PORT`环境变量或命令参数传给开发服务器；
3. 根据应用名称注册本地域名；
4. 由统一代理通过 443 端口将请求转发到对应应用。

```bash
portless myapp next dev
# https://myapp.localhost
```

默认启用 HTTPS 与 HTTP/2，首次使用会生成并信任本地 CA。

##### 主要能力

###### 1. 稳定、语义化的本地地址

开发者不再需要记忆或协调端口号，可以使用：

```text
https://myapp.localhost
https://api.myapp.localhost
https://docs.myapp.localhost
```

这对多人协作、自动化测试和 AI Agent 尤其有价值，因为服务地址不再随启动顺序变化。

###### 2. 主流框架自动适配

Portless 支持 Next.js、Express、Nuxt、Vite、Astro、Angular、Expo 等框架。

- 优先注入`PORT`环境变量；
- 对不读取`PORT`的框架，自动追加`--port`、`--host`；
- 构建、测试等非服务命令不会被错误修改；
- 复杂脚本无法安全识别时保持原样，需自行配置端口。

###### 3. Monorepo 与 Turborepo 支持

在 Monorepo 根目录运行`portless`，可自动发现并启动所有包含`dev`脚本的工作区应用，并为它们生成独立域名。

```text
web.myproject.localhost
api.myproject.localhost
```

可通过`portless.json`或`package.json`覆盖应用名称、启动脚本和固定端口。

###### 4. Git Worktree 自动隔离

Portless 会把 worktree 的分支名加入子域名：

```text
主工作区：    https://myapp.localhost
fix-ui 分支： https://fix-ui.myapp.localhost
```

因此多个分支可以同时运行，无需手动换端口，也不会发生路由冲突。

###### 5. 自定义域名与生产环境模拟

除了默认的`.localhost`，还支持：

```text
myapp.test
myapp.dev.example.com
```

使用真实域名结构，可让本地环境更接近生产环境，适合验证：

- OAuth 回调地址；
- 跨子域 Cookie；
- Host-based 路由；
- 多租户子域名。

其中，Google、Apple 等严格 OAuth 服务通常不接受`.localhost`或`.test`，但可接受自有真实域名。

###### 6. 局域网与外部分享

Portless 提供多种分享方式：

- **LAN 模式**：通过`myapp.local`供同一局域网设备访问；
- **Tailscale**：在私有 Tailnet 内分享；
- **Tailscale Funnel**：公开分享；
- **ngrok**：生成公网访问地址。

适合移动端调试、远程协作、Webhook 和客户演示。

###### 7. 完整的本地代理管理

提供路由与环境管理命令：

```bash
portless list          # 查看路由
portless doctor        # 检查代理、DNS、证书
portless alias api 8080 # 为现有服务或 Docker 注册域名
portless prune         # 清理崩溃后遗留的进程
portless clean         # 清理状态、证书和 hosts 配置
```

还可安装为系统启动服务，使 HTTPS 代理在开机后自动运行。

##### 配置优先级

Portless 支持三类配置方式：

1. CLI 参数；
2. `package.json`中的`portless`字段；
3. `portless.json`。

其中，**CLI 优先级最高，`package.json`高于`portless.json`**。代理端口、TLS、TLD、LAN 等配置会被持久化，后续自动启动时继续复用。

##### 使用限制与注意事项

###### 稳定性

项目尚未发布 1.0，不同版本的状态目录格式可能变化。团队按项目安装时，成员版本不一致可能需要重新执行：

```bash
portless trust
```

###### 权限与安全

默认 HTTPS 需要：

- 创建并信任本地 CA；
- 在 macOS/Linux 上通过提权绑定 443 端口；
- 修改系统信任存储及必要的`/etc/hosts`记录。

团队引入前应评估本地证书和管理员权限策略。

###### 模式限制

- 自定义 TLD 与 LAN 模式目前不能同时使用；
- LAN 模式依赖系统 mDNS 工具；
- 复杂 npm 脚本可能无法自动注入端口；
- `.local`容易与 mDNS 冲突，`.dev`被 HSTS 强制要求 HTTPS，官方更推荐`.test`。

##### 产品价值

Portless 的本质不是 “隐藏端口”，而是为本地服务增加一层**稳定的服务发现与命名系统**。它解决了三个典型问题：

- **认知成本**：开发者无需记忆端口；
- **协作成本**：团队、脚本和文档可以使用统一地址；
- **自动化成本**：AI Agent、测试工具和浏览器自动化能够可靠定位服务。

对于多应用 Monorepo、多分支并行开发、OAuth 联调和 AI 编程场景，Portless 的价值最明显。

### 提问 · 2026-09-10 04:39:08

在 本地局域网，如何使用自定义域名，这个自定义域名如何让局域网内几台机的 小伙伴们访问到？我觉得使用 localhost  不合适，因为大家可以在自己的机器上使用localhost。

### 回答 · 2026-09-10 04:39:08

你的判断是对的：**`localhost`永远指向访问者自己的机器**，所以不能作为局域网共享地址。

不过需要区分：

- `myapp.localhost`：浏览器解析到每个人自己的`127.0.0.1`，不能共享；
- `myapp.local`：通过 mDNS 解析到运行 Portless 的那台开发机，可以在局域网共享；
- `myapp.test`、`myapp.dev.example.com`：需要局域网 DNS 或 hosts 配置，并且通常还要额外的反向代理。

##### 方案一：直接使用 Portless LAN 模式

这是最简单、最符合 Portless 设计的方案。

###### 在运行项目的开发机上

先确认开发机局域网 IP，例如：

```text
192.168.1.42
```

建议在路由器中为这台机器设置 DHCP 地址保留，避免 IP 变化。

启动 LAN 代理：

```bash
portless proxy start --lan --ip 192.168.1.42
```

然后运行应用：

```bash
portless myapp next dev
```

局域网内其他人访问：

```text
http://myapp.local
```

这里的`.local`不是`localhost`。它通过 mDNS 解析到你的开发机，而不是访问者自己的机器。

如果 IP 不固定，也可以让 Portless 自动检测：

```bash
portless proxy start --lan
```

Portless 会尝试跟随 Wi-Fi/IP 变化。

###### 使用 HTTPS

```bash
portless proxy start --lan --https --ip 192.168.1.42
```

其他人访问：

```text
https://myapp.local
```

但要注意：Portless 生成的是本地 CA，默认只会被运行 Portless 的机器信任。其他人的电脑不会自动信任它。若想消除证书警告，需要把**同一个 Portless 根 CA 的公开证书**安全地安装到每台客户端的系统信任存储中，不能只让每个人各自生成一套 CA，也不要分发 CA 私钥。

如果只是可信局域网中的临时联调，HTTP 配置最简单；如果涉及 Secure Context、Service Worker、某些 OAuth 或安全 Cookie，则需要 HTTPS。

###### Linux 额外依赖

Portless LAN 模式在 Linux 上依赖 Avahi：

```bash
sudo apt install avahi-utils
```

其他发行版安装对应的`avahi-publish-address`工具。macOS 自带`dns-sd`。

###### 如果别人打不开

依次检查：

1. 双方是否在同一局域网或可互通的 VLAN；
2. Wi-Fi 是否开启了 “客户端隔离 / AP Isolation”；
3. 开发机防火墙是否允许入站 80 或 443；
4. Linux 是否安装并启动了 Avahi；
5. 公司网络是否禁止 mDNS / 组播；
6. Next.js 等框架是否需要配置允许来源，例如：

```js
//next.config.js
module.exports = {
  allowedDevOrigins: ["myapp.local", "*.myapp.local"],
};
```

如果 mDNS 被网络禁用，可以在每台客户端的 hosts 文件中添加：

```text
192.168.1.42 myapp.local
```

这样仍然可以使用 Portless 的`myapp.local`路由。

##### Portless LAN 模式的限制

当前 Portless **不能把 LAN 模式和自定义 TLD 结合使用**：

```bash
portless proxy start --lan --tld test
```

在 LAN 模式下，自定义`--tld`会被忽略，应用仍通过：

```text
myapp.local
```

提供服务。

同样，仅运行：

```bash
portless proxy start --tld test
```

也不能解决局域网访问问题。非 LAN 模式下，Portless 只监听：

```text
127.0.0.1
::1
```

即使把`myapp.test`的 DNS 指向开发机局域网 IP，其他机器也连接不上。

因此：

- 只要求 “局域网内有一个稳定名称”：使用`myapp.local`；
- 必须使用`myapp.test`或`myapp.dev.example.com`：需要局域网 DNS 加额外反向代理。

##### 方案二：使用真正的自定义域名

假设你希望同事访问：

```text
http://myapp.test
```

推荐架构：

```text
同事电脑
   │
   │ DNS：myapp.test → 192.168.1.42
   ▼
开发机上的 Caddy/Nginx
   │
   ▼
127.0.0.1:3000
```

###### 1. 为开发机固定局域网 IP

例如：

```text
192.168.1.42
```

最好在路由器上配置 DHCP Reservation。

###### 2. 配置名称解析

任选一种：

###### 在路由器或内网 DNS 中增加记录

```text
myapp.test  A  192.168.1.42
```

可以使用：

- 路由器的本地 DNS 功能；
- Pi-hole；
- AdGuard Home；
- dnsmasq；
- 公司内部 DNS。

这是多人团队最推荐的方式，只配置一次，所有客户端都能使用。

###### 或修改每台电脑的 hosts

```text
192.168.1.42 myapp.test
192.168.1.42 api.myapp.test
```

适合只有两三个人的临时场景，但 IP 或域名变化时需要逐台修改。

###### 3. 在开发机运行反向代理

例如使用 Caddy：

```caddyfile
http://myapp.test {
    reverse_proxy 127.0.0.1:3000
}

http://api.myapp.test {
    reverse_proxy 127.0.0.1:4000
}
```

然后让应用固定运行在对应端口：

```bash
PORT=3000 npm run dev
```

Caddy 会处理普通 HTTP、WebSocket 和大多数 HMR 场景。

如果仍想让 Portless 帮你启动应用，可以设置固定的`appPort`，让 Caddy 直接代理到该端口：

```json
{
  "name": "myapp",
  "appPort": 3000
}
```

但此时对外的自定义域名和 LAN 监听主要由 Caddy/Nginx 负责，而不是 Portless。

##### 自定义域名的 HTTPS

###### 使用`.test`

公共 CA 不会为`myapp.test`签发证书。你需要：

- 使用 Caddy、mkcert 或 Portless 类似的内部 CA；
- 将同一个根 CA 安装到所有参与者的系统信任存储。

例如 Caddy 可以使用内部 CA：

```caddyfile
myapp.test {
    tls internal
    reverse_proxy 127.0.0.1:3000
}
```

每台客户端都需要信任 Caddy 的根 CA。

###### 使用自己拥有的真实域名

例如：

```text
myapp.dev.example.com
```

可以在内网 DNS 中将其解析为：

```text
192.168.1.42
```

这叫 Split DNS 或 Split-horizon DNS。证书可以通过 DNS-01 验证申请，或者使用已有的通配符证书：

```text
*.dev.example.com
```

这种方案最接近生产环境，也适合 OAuth、跨子域 Cookie 和基于 Host 的路由，但配置成本更高。

##### 推荐选择

| 需求 | 推荐方案 |
|---|---|
| 几个同事临时访问 | `portless proxy start --lan`，使用`myapp.local` |
| mDNS 被公司网络禁用 | hosts 或内网 DNS 将`myapp.local`指向开发机 |
| 必须使用`myapp.test` | 内网 DNS/hosts + Caddy/Nginx |
| 必须使用真实业务域名 | Split DNS + Caddy/Nginx + DNS-01 / 通配符证书 |
| 需要跨网络访问 | Tailscale、Tailscale Funnel 或 ngrok |

对于你的场景，建议先使用：

```bash
portless proxy start --lan --ip 192.168.1.42
portless myapp next dev
```

让小伙伴们访问：

```text
http://myapp.local
```

它已经解决了`localhost`指向各自电脑的问题。如果你们明确要求`myapp.test`之类的域名，再增加内网 DNS 和 Caddy。LAN 模式会把服务暴露给可达的局域网设备，因此不要在不可信公共 Wi-Fi 上启用，并建议通过防火墙限制可访问网段。

### 2026-09-18 00:03:40

#### Portless 不只是隐藏端口，而是在本地开发中补上一层“服务身份”

Portless 的表面功能很简单：把 `localhost:3000` 换成 `https://myapp.localhost`。真正值得关注的并非 URL 更好记，而是它将**服务身份与临时进程端口解耦**：应用每次可以运行在随机端口，浏览器、脚本和其他服务始终通过稳定名称访问，由本地代理维护映射。

这解决的是一个随开发并行度上升而放大的问题。单项目时，记住 3000、3001 尚可接受；到了 monorepo、多服务、Git worktree 和多个编码代理并行工作，端口已经不再是可靠标识。Portless 能从包名和工作区推断域名，并为 `fix-ui` 之类的 worktree 自动生成 `fix-ui.myapp.localhost`。这意味着开发者或代理可以复制稳定链接、配置回调地址、运行端到端测试，而不必先询问“这次到底占了哪个端口”。

##### AI 编程需要的不只是执行能力，还需要稳定的环境语义

“面向人类和代理”并非一句空泛定位。代理擅长启动进程，却容易在端口冲突、进程残留、目录切换和多实例并存时失去上下文。命名 URL 相当于给本地服务建立一个轻量注册中心：名称表达“它是谁”，端口只是“它此刻在哪里”。

这一思路可以迁移到更广泛的 AI 开发基础设施。未来瓶颈未必是模型不会写代码，而是代理之间缺少稳定、可发现、可清理的共享环境。Portless 对 Ctrl+C 后代进程清理、崩溃进程回收、路由列表和诊断命令的处理，说明真正有价值的代理工具不能只封装启动命令，还要管理资源生命周期。

##### 本地环境正在从“能跑”走向“接近真实部署语义”

默认 HTTPS、HTTP/2、子域名、跨子域 Cookie、OAuth 回调和基于 Host 的路由，让 Portless 超出了地址美化工具的范围。尤其是允许使用 `myapp.dev.example.com` 这样的真实域名结构，可以让严格 OAuth 提供商接受回调，也能减少本地与生产环境在证书、域名和 Cookie 行为上的偏差。对多租户、身份认证和微前端项目，这类一致性比省去几个数字更有价值。

但这种便利来自接管更多系统能力：它要安装本地 CA、绑定 443、修改 hosts、处理不同框架的参数语法，还要兼容 mDNS、Tailscale 和 ngrok。README 大量篇幅都在描述例外与故障恢复，恰好揭示了边界：**稳定命名不是一个简单别名功能，而是一项小型本地控制面的工作。**项目尚未到 1.0，也没有提供采用率或效率提升数据，因此还不能据此断言它会成为标准。

更值得验证的判断是：当团队普遍采用多 worktree 和多代理并行开发后，稳定服务命名是否会从个人体验优化，变成测试、协作与自动化的基础协议。Portless 提供了一个相当完整的答案，也暴露了实现这种答案所需承担的复杂性。

## 口播总结（1）

### 2026-09-20 00:36:38

Portless 要解决的，是本地开发中一个看似很小、却经常打断工作的问题：端口号不稳定，也不容易记。它让你不再访问 localhost 冒号三千，而是用类似 myapp 点 localhost 这样的固定名称打开应用。这个地址对开发者更直观，对自动化代理也更可靠。

它的基本原理很简单。启动应用时，Portless 会从四千到四千九百九十九之间分配一个空闲端口，再把应用名称注册到本地反向代理。浏览器访问 myapp 点 localhost，请求会先到代理，再被转发给真正的应用端口。端口仍然存在，但被隐藏在稳定的网址后面。

例如，原本用 next dev 启动项目，可以改为 portless run next dev。之后访问的就是 https 冒号双斜杠 myapp 点 localhost。应用名称可以明确指定，也可以根据 package 点 json 中的包名、Git 仓库根目录名称或当前目录自动推断。直接运行 portless 时，它还会默认执行项目的 dev 脚本。

大多数框架会读取 PORT 环境变量，所以 Next.js、Express 和 Nuxt 等框架通常不需要额外适配。对于 Vite、Astro、Angular、Expo 和 React Native 等可能忽略这个变量的工具，Portless 会识别真正用于启动服务器的命令，并自动补上端口参数，必要时还会补上主机参数。

这里的识别比较谨慎。像 Vite build、Astro check 这类不启动服务器的命令，不会被错误地添加端口参数。复合命令、带环境变量前缀的命令，或者继续委托给另一个脚本的命令，如果无法安全修改，也会保持原样。这种情况下，需要开发者在脚本中自行配置端口。

Portless 默认使用 HTTPS，并支持 HTTP 二。第一次运行时，它会生成一个本地证书颁发机构，也就是本地 CA，并把它加入系统的信任存储。这样浏览器不会弹出证书警告。它默认使用四百四十三端口，因此在 macOS 和 Linux 上，首次绑定端口时可能需要通过 sudo 提权。如果不需要 HTTPS，也可以使用 no tls 选项，改成普通 HTTP。

默认采用 HTTP 二并不只是为了让本地网址看起来像生产环境。传统 HTTP 一点一通常限制每个主机同时使用的连接数。Vite 或 Nuxt 这类开发服务器可能需要加载大量没有打包的文件，容易受到这个限制。HTTP 二可以在一个连接中并行传输多个请求。开发服务器常用的热更新 WebSocket，也能正常经过代理。

Portless 的一个重要价值，是同时运行多个项目时不再需要手工争抢端口。前端可以叫 myapp 点 localhost，接口服务可以叫 api 点 myapp 点 localhost，文档站可以叫 docs 点 myapp 点 localhost。默认情况下，只有明确注册过的名称才能访问。如果启动代理时开启 wildcard，也就是通配符模式，未单独注册的子域名就可以回退到对应的父应用。这适合需要模拟多租户子域名的项目。

这种命名方式对 Git worktree 尤其有用。Git worktree 可以让同一个仓库的不同分支同时存在于多个工作目录。Portless 会自动识别链接的 worktree，并把分支名放到应用名称前面。主工作区仍然使用 myapp 点 localhost，而 fix-ui 分支可以自动获得 fix-ui 点 myapp 点 localhost。这样多个分支可以同时运行，不会发生端口冲突，也不需要反复使用 force 强行接管路由。

在多包仓库里，Portless 可以从 pnpm workspace 配置，或者 package 点 json 的 workspaces 字段发现各个包。从仓库根目录运行时，它会启动所有包含 dev 脚本的工作区包。默认网址通常采用“包名点项目名点 localhost”的形式，也可以通过 portless 点 json 为前端、接口等包分别指定名称。它也能配合 Turborepo 使用，不需要修改 turbo 点 json。

除了默认的点 localhost，Portless 还支持自定义顶级域名。比如使用点 test，代理会自动更新本机的 hosts 配置，让 myapp 点 test 指向本机。官方更推荐点 test，因为这是专门保留用于测试的域名，不容易产生冲突。点 local 应尽量避免，因为它会和 mDNS 或 Bonjour 冲突。点 dev 也要谨慎，因为浏览器会强制它使用 HTTPS。

更进一步，还可以把自己拥有的真实域名用于本地开发，比如 myapp 点 dev 点 example 点 com。这样，本地环境与生产环境可以保持相似的网址结构，对跨子域 Cookie、基于主机名的路由和 OAuth 登录尤其有帮助。Google、Apple 等严格的 OAuth 提供商可能拒绝点 localhost 和点 test 的回调地址，却可以接受真实域名下的 HTTPS 回调地址。

不过，自定义域名默认仍然只在本机可用。普通模式下，代理只监听一二七点零点零点一和 IPv6 回环地址，不接受局域网、虚拟专用网络或其他网络接口的连接。这是一个重要的安全边界。

如果确实需要在手机或同一网络中的其他设备上测试，可以启用 LAN 模式。此时代理会监听局域网接口，并通过 mDNS 提供类似 myapp 点 local 的地址。Portless 能自动检测局域网 IP，并在无线网络或地址变化时跟随更新。但 LAN 模式使用点 local，并会忽略自定义顶级域名，因此目前不能与自定义域名模式结合。Next.js 在这种模式下，还需要把相应的点 local 主机名加入 allowedDevOrigins 配置。

如果需要把开发服务器分享给远程队友，Portless 还能接入 Tailscale。它会同时保留本地地址，并在 Tailscale 私有网络中注册一个 HTTPS 地址。也可以通过 Tailscale Funnel 或 ngrok 暴露到公共互联网。应用退出时，相应的共享注册和隧道会自动清理。不过这些功能依赖外部工具已经安装、登录并完成证书或权限配置。

日常使用中，Portless 会记住最近一次代理的端口、HTTPS、顶级域名和 LAN 设置，自动重启时不会悄悄恢复默认值。它还可以安装成操作系统启动服务，让代理在电脑重启后自动运行。出现问题时，可以用 portless list 查看活动路由，用 portless doctor 检查代理、域名解析和证书信任，用 portless prune 清理崩溃后遗留的开发进程。

最值得记住的是，Portless 并没有消灭端口，而是用稳定、可读的名字管理端口。它的核心收益不仅是少记几个数字，更是让多项目、多分支、多包仓库和自动化工具拥有一致的本地入口。需要注意的是，它尚未发布一点零版本。项目内安装时，不同贡献者可能使用不同版本，状态目录格式也可能变化，因此全局安装通常更稳妥，升级后偶尔可能需要重新执行证书信任操作。

## 深度解读-口播（1）

### 2026-09-30 11:56:04

Portless 想解决的，是本地开发里一个很常见的麻烦：应用明明有名字，访问时却要记住一串端口号。它把这些容易变化的端口，藏到一个本地代理后面，让人和 AI 代理都能通过稳定、带名字的地址访问应用。

比如，一个项目原来要通过 localhost 加三千端口访问。使用 Portless 后，访问地址可以变成“myapp 点 localhost”，并且默认使用 HTTPS。你记住的是项目名称，而不是它这次启动占用了哪个端口。

这里要先澄清一点：Portless 不是让应用不再使用端口，而是把端口管理和对外访问分开。

应用启动时，Portless 会从四千到四千九百九十九之间，分配一个空闲端口。浏览器访问带名字的地址，请求先到本地代理，再由代理转发给对应的应用。应用实际运行在哪个端口，可以变化；你访问它的名字，不必跟着变化。

多数开发框架会读取一个叫 PORT 的环境变量，也就是用来指定监听端口的配置。Portless 通过这个变量告诉应用应该使用哪个端口。对于 Vite、Astro 等不按这种方式读取端口的框架，Portless 会识别服务器启动命令，自动补上端口参数，必要时也会补上监听地址。

所以，稳定地址不是靠所有项目约定好端口，而是靠代理维护“名字对应哪个应用”这层关系。

理解这一点，再看 Portless 最有价值的使用场景：同时运行多个服务，或者同时开发多个分支。

一个项目可能有网页、接口和文档服务。Portless 可以分别给它们命名，例如“myapp 点 localhost”、“api 点 myapp 点 localhost”，以及“docs 点 myapp 点 localhost”。这些名字直接表达服务之间的关系，比一组端口号更容易辨认。

在单仓库、多软件包的项目里，Portless 可以自动发现工作区中的包。从仓库根目录启动时，它会运行带有开发脚本的工作区包。不需要为了获得不同地址，逐个手动分配端口。需要调整名字时，再用配置文件覆盖。

另一个很具体的场景，是 Git 工作树。工作树允许你在不同目录里，同时检出同一仓库的不同分支。

假设主工作树的地址是“myapp 点 localhost”。另一个工作树正在开发名为“fix-ui”的分支，Portless 就会把分支名放到前面，形成“fix-ui 点 myapp 点 localhost”。

这样，同一个项目的两个版本可以同时运行，各有自己的访问地址，不需要为了并行开发反复修改配置。这也是它强调“面向人类和代理”的原因之一：地址可以表达项目和分支，而不只是一个临时数字。

不过，Portless 做的并不只是给地址起名字。它还默认启用 HTTPS，并支持 HTTP 第二版，也就是 HTTP/2。

这对某些开发服务器有实际意义。按照项目文档的解释，浏览器使用 HTTP 第一版时，每个主机的连接数通常限制为六个。像 Vite 这类可能提供大量未打包文件的开发服务器，就可能遇到连接瓶颈。HTTP/2 可以在一个连接里同时传输多个请求，减轻这个限制。

开发时常用的热更新也能通过代理工作。它依赖的 WebSocket，也就是浏览器与服务器之间持续保持的双向连接，Portless 同样支持。

为了让浏览器信任本地 HTTPS，首次运行时，Portless 会生成本地证书颁发机构，并将它加入系统信任存储。这不是单纯换一个网址：它涉及系统证书信任；在 macOS 和 Linux 上，绑定默认的四百四十三端口，也会通过提权来完成。

如果本地登录流程对域名有更严格的要求，Portless 还允许使用你拥有的真实域名作为地址后缀。

这个功能主要解决第三方登录回调的问题。项目文档指出，Google、Apple 等严格的登录服务，会拒绝以 localhost 或 test 结尾的回调地址，但接受真实域名。Portless 可以把相应的开发主机名写入本机的 hosts 文件，让它仍然指向本机，同时使用真实域名结构。

这里的关键是：名字看起来像真实域名，不代表开发服务器已经公开到互联网。

默认情况下，Portless 只监听本机的回环地址。局域网、虚拟专用网络，以及其他网络接口上的连接，都不能直接访问这个代理。

如果要用手机测试，就需要明确启用局域网模式。这个模式会让代理监听网络接口，并通过局域网里的名称发现机制，提供以 local 结尾的地址。它与默认的本机模式不同，也会改变服务的可访问范围。

而且，目前局域网模式会忽略自定义域名后缀。也就是说，“用真实域名模拟生产环境”和“让同一网络里的手机访问”，这两种设置暂时不能直接结合。

最后，还有两个使用前提值得记住。

一个是自动适配有边界。Portless 能识别许多常见框架和启动方式，但遇到复合命令、脚本前面的环境变量，或者一个脚本再调用另一个脚本时，可能不会自动追加端口参数。这些情况下，需要在脚本里自行设置端口，不能把自动适配理解成适用于所有命令。

另一个是版本状态。Portless 尚未发布一点零版本。项目文档提醒，不同版本之间，状态目录格式可能变化，升级后也可能需要重新执行证书信任操作。

记住 Portless 的核心，不是“消灭端口”，而是用稳定的名字管理变化的端口。它尤其适合多服务、多工作区和多分支并行开发；但证书信任、框架适配，以及是否开放网络访问，仍然需要明确配置和理解。

###### 摘要
文章系统介绍 Portless：以稳定的命名式本地域名取代端口号，通过 HTTPS 反向代理适配多种框架、Monorepo 与 Git worktree，并支持自定义 TLD、局域网及远程分享。

###### 知识要点
- Portless 为应用分配随机内部端口，再通过稳定的命名域名和本地反向代理提供访问入口。
- Git worktree 可自动使用分支名作为子域名前缀，使不同工作树拥有互不冲突的固定 URL。
- 自定义真实域名形式的 TLD 可让本地环境更接近生产环境，并适配严格限制回调域名的 OAuth 提供商。

###### 行动项
- 全局安装 Portless，并选择一个现有项目用 portless run 启动，验证命名 URL、HTTPS 和热更新。
- 在 Monorepo 中创建 portless.json，为前端、API 等工作区配置稳定名称并测试统一启动。
- 使用 portless doctor 检查代理、DNS 和本地 CA 信任状态，再根据需要启用 LAN、Tailscale 或 ngrok 分享。
