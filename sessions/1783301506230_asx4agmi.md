## 分析要点

- **核心高价值点**：用“Markdown + YAML frontmatter + Git目录结构”作为最低复杂度的知识交换格式，在可读性、可维护性和Agent可解析性之间取得了较好平衡。
- **留存建议**：长期保留（该文档定义了一套简洁、可落地的开放知识表示格式，对构建人类与AI Agent共同可读的知识库、数据目录和元数据体系具有长期参考价值。）

**知识要点**

- OKF 将知识包定义为由 Markdown 文件组成的目录树，每个普通 Markdown 文件代表一个概念。
- 每个概念文件必须包含 YAML frontmatter，且至少需要非空的 type 字段。
- title、description、resource、tags、timestamp 是推荐但非强制字段。
- index.md 用于目录级内容导航，log.md 用于记录目录范围内的更新时间线。
- 概念之间通过标准 Markdown 链接建立关系，消费者通常可将其解析为有向无类型边。
- OKF 强调宽松消费模型，消费者不应因未知字段、缺失可选字段、断链或缺少 index.md 而拒绝整个知识包。
- 该格式不替代 Avro、Protobuf、OpenAPI 等领域 schema，而是引用和补充它们周围的上下文知识。
- Git 仓库是推荐的分发方式，可天然支持历史、归因、diff 和协作。

**行动项**

- 尝试用 OKF 结构整理一个现有项目知识库或数据目录。
- 为关键数据表、API、指标或Playbook建立独立 Markdown 概念文件。
- 统一为知识文档添加 type、title、description、resource、tags、timestamp 等 frontmatter。
- 为知识库根目录和重要子目录生成 index.md，提升人和Agent的浏览效率。
- 在文档中使用 Markdown 内链显式表达依赖、引用、关联和上下游关系。
- 为关键事实和外部依据增加 Citations 区块，提升知识可信度。

**Version 0.1 — Draft**

OKF is an open, human- and agent-friendly format for representing *knowledge* — the metadata, context, and curated insight that surrounds data and systems. It is designed to be authored by people, generated by agents, exchanged across organizations, and consumed by both.

The format is intentionally minimal: a directory of markdown files with YAML frontmatter. There is no schema registry, no central authority, and no required tooling. If you can `cat` a file, you can read OKF; if you can `git clone` a repo, you can ship it.

---

#### 1\. Motivation

The space of knowledge representation for AI agents is evolving quickly, and many incompatible conventions are emerging. OKF takes the position that knowledge is best represented in commonly accessible, established formats that are:

- **Readable** by humans without tooling.
- **Parseable** by agents without bespoke SDKs.
- **Diffable** in version control.
- **Portable** across tools, organizations, and time.

The format is minimally opinionated. It standardizes only the small set of structural conventions needed to make a knowledge corpus *self-describing* — anything beyond that is left to the producer.

##### Goals

1. Define a universal format that **enrichment agents** can write into.
2. Inform how **consumption agents** should read and traverse it.
3. Facilitate **exchange** of knowledge across systems and organizations.
4. Standardize the small number of **required** fields that must be present for content to be meaningfully consumed.

##### Non-goals

- Defining a fixed taxonomy of concept types.
- Prescribing storage, serving, or query infrastructure.
- Replacing domain-specific schemas (Avro, Protobuf, OpenAPI, etc.) — OKF *references* them; it does not subsume them.

---

#### 2\. Terminology

- **Knowledge Bundle** — A self-contained, hierarchical collection of knowledge documents. The unit of distribution.
- **Concept** — A single unit of knowledge within a bundle. Represented as one markdown document. May describe a tangible asset (a table, an API), an abstract idea (a metric, a business process), or anything in between.
- **Concept ID** — The path of the concept's file within the bundle, with the `.md` suffix removed. For example, `tables/users.md` has concept ID `tables/users`.
- **Frontmatter** — YAML metadata block delimited by `---` at the top of a markdown file.
- **Body** — Everything in the file after the frontmatter.
- **Link** — A standard markdown link from one concept to another, used to express relationships beyond the implicit parent/child hierarchy.
- **Citation** — A link from a concept to an external source that supports a claim in the body.

---

A bundle is a directory tree of markdown files. The directory structure is independent of the domain — producers organize concepts however makes sense for the knowledge being captured.

```
path/to/bundle/
├── index.md                      # Optional. Directory listing for progressive disclosure.
├── log.md                        # Optional. Chronological history of updates.
├── <concept>.md                  # A concept at the bundle root.
└── <subdirectory>/               # Subdirectories organize concepts into groups.
    ├── index.md
    ├── <concept>.md
    └── <subdirectory>/
        └── …
```

A bundle MAY be distributed as:

- A git repository (recommended — provides history, attribution, diffs).
- A tarball or zip archive of the directory.
- A subdirectory within a larger repository.

The following filenames have defined meaning at any level of the hierarchy and MUST NOT be used for concept documents:

Filename Purpose

`index.md` Directory listing. See §6.

`log.md` Update history. See §7.

All other `.md` files are concept documents.

Tags themselves remain a first-class concept — see the `tags` frontmatter field in §4.1. OKF does not specify a separate file format for aggregating documents by tag; producers that want a tag-browsing view can synthesize one at consumption time by scanning frontmatter.

---

Every concept is a UTF-8 markdown file. It has two parts:

1. A **YAML frontmatter block**, delimited by `---` on its own line at the start of the file and a closing `---` on its own line.
2. A **markdown body**, containing free-form content.

##### 4.1 Frontmatter

```
---
type: <Type name>                  # REQUIRED
title: <Optional display name>
description: <Optional one-line summary>
resource: <Optional canonical URI for the underlying asset>
tags: [<tag>, <tag>, …]            # Optional
timestamp: <ISO 8601 datetime>     # Optional last-modified time
# … other producer-defined key/value pairs
---
```

**Required:**

- `type` — A short string identifying the kind of concept. Consumers use this for routing, filtering, and presentation. Example values:`BigQuery Table`, `BigQuery Dataset`, `API Endpoint`, `Metric`,`Playbook`, `Reference`.
  Type values are **not** registered centrally. Producers SHOULD pick values that are descriptive and self-explanatory; consumers MUST tolerate unknown types gracefully (typically by treating them as generic concepts).

**Recommended (in priority order):**

- `title` — Human-readable display name. If omitted, consumers MAY derive a title from the filename.
- `description` — A single sentence summarizing the concept. Used by `index.md` generators, search snippets, and previews.
- `resource` — A URI that uniquely identifies the underlying asset the concept describes. Absent for concepts that describe abstract ideas rather than physical resources.
- `tags` — A YAML list of short strings for cross-cutting categorization.
- `timestamp` — ISO 8601 datetime of last meaningful change.

**Extensions:** Producers MAY include any additional keys. Consumers SHOULD preserve unknown keys when round-tripping and SHOULD NOT reject documents with unrecognized fields.

##### 4.2 Body

The body is standard markdown. Producers SHOULD favor structural markdown — headings, lists, tables, fenced code blocks — over freeform prose, since structure aids both human reading and agent retrieval.

There are no required body sections. The following section headings have **conventional** meaning and SHOULD be used when applicable:

Heading Purpose

`# Schema` Structured description of an asset's columns/fields.

`# Examples` Concrete usage examples, often as fenced code blocks.

`# Citations` External sources backing claims in the body. See §8.

```
---
type: BigQuery Table
title: Customer Orders
description: One row per completed customer order across all channels.
resource: https://console.cloud.google.com/bigquery?p=acme&d=sales&t=orders
tags: [sales, orders, revenue]
timestamp: 2026-05-28T14:30:00Z
---

# Schema

| Column        | Type      | Description                              |
|---------------|-----------|------------------------------------------|
| `order_id`    | STRING    | Globally unique order identifier.        |
| `customer_id` | STRING    | Foreign key into [customers](/tables/customers.md). |
| `total_usd`   | NUMERIC   | Order total in US dollars.               |
| `placed_at`   | TIMESTAMP | When the customer submitted the order.   |

# Joins

Joined with [customers](/tables/customers.md) on `customer_id`.

# Citations

[1] [BigQuery table schema](https://console.cloud.google.com/bigquery?p=acme&d=sales&t=orders)
```

```
---
type: Playbook
title: Incident response — data freshness alert
description: Steps to triage a freshness alert on the orders pipeline.
tags: [oncall, incident]
timestamp: 2026-04-12T09:00:00Z
---

# Trigger

A freshness alert fires when `orders` lags more than 30 minutes behind
its expected SLA. See the [orders table](/tables/orders.md).

# Steps

1. Check the [ingestion job dashboard](https://example.com/dash).
2. …
```

---

#### 5\. Cross-linking

Concepts MAY link to other concepts using standard markdown links. Two forms are supported:

Begin with `/`, interpreted relative to the bundle root.

```
See the [customers table](/tables/customers.md) for the join key.
```

This is the **recommended** form because it is stable when documents are moved within their subdirectory.

Standard markdown relative paths.

```
See the [neighboring concept](./other.md).
```

A link from concept A to concept B asserts a *relationship*. The specific kind of relationship (parent/child, references, joins-with, depends-on, etc.) is conveyed by the surrounding prose, not by the link itself. Consumers that build a graph view typically treat all links as directed edges of an untyped relationship.

Consumers MUST tolerate broken links — a link whose target does not exist in the bundle is not malformed; it may simply represent not-yet-written knowledge.

---

An `index.md` file MAY appear in any directory, including the bundle root. It enumerates the directory's contents to support **progressive disclosure** — letting a human or agent see what is available before opening individual documents.

Index files contain no frontmatter. The body uses one or more sections, each grouping concepts under a heading:

```
# Section / Group Heading

* [Title 1](relative-url-1) - short description of item 1
* [Title 2](relative-url-2) - short description of item 2

# Another Section

* [Subdirectory](subdir/) - short description of the subdirectory
```

Entries SHOULD include the description from the linked concept's frontmatter. Producers MAY generate `index.md` automatically; consumers MAY synthesize one on the fly when none is present.

---

A `log.md` file MAY appear at any level of the hierarchy to record the history of changes to that scope. The format is a flat list of date-grouped entries, newest first:

```
# Directory Update Log

## 2026-05-22
* **Update**: Added new BigQuery table reference for [Customer Metrics](/tables/customer-metrics.md).
* **Creation**: Established the [Dataplex Playbook](/playbooks/dataplex.md).

## 2026-05-15
* **Initialization**: Created foundational directory structure.
* **Update**: Added progressive-disclosure guidelines to the root [index](/index.md).
```

Date headings MUST use ISO 8601 `YYYY-MM-DD` form. Log entries are prose; the leading bold word (`**Update**`, `**Creation**`,`**Deprecation**`, etc.) is a convention, not a requirement.

---

#### 8\. Citations

When a concept's body makes claims sourced from external material, those sources SHOULD be listed under a `# Citations` heading at the bottom of the document, numbered:

```
# Citations

[1] [BigQuery public dataset announcement](https://cloud.google.com/blog/products/data-analytics/...)
[2] [Internal data quality runbook](https://wiki.acme.internal/data/quality)
```

Citation links MAY be absolute URLs, bundle-relative paths, or paths into a `references/` subdirectory that mirrors external material as first-class OKF concepts.

---

#### 9\. Conformance

A bundle is **conformant** with OKF v0.1 if:

1. Every non-reserved `.md` file in the tree contains a parseable YAML frontmatter block.
2. Every frontmatter block contains a non-empty `type` field.
3. Every reserved filename (`index.md`, `log.md`) follows the structure described in §6 and §7 respectively when present.

Consumers SHOULD treat all other constraints as soft guidance. In particular, consumers MUST NOT reject a bundle because of:

- Missing optional frontmatter fields.
- Unknown `type` values.
- Unknown additional frontmatter keys.
- Broken cross-links.
- Missing `index.md` files.

This permissive consumption model is intentional: OKF is meant to remain useful as bundles grow, get refactored, and are partially generated by agents.

---

OKF is intentionally close to several established patterns:

- **LLM "wiki" repositories** that use markdown + frontmatter as agent-readable knowledge bases.
- **Personal knowledge tools** like Obsidian and Notion, which use hierarchical markdown with cross-links.
- **"Metadata as code"** approaches that store catalog metadata alongside source code rather than in a separate registry.

OKF differs primarily in being **specified** — pinning down the small set of rules needed for interoperability without dictating tooling.

---

#### 11\. Versioning

This document specifies OKF version **0.1**. Future revisions will be versioned in the form `<major>.<minor>`:

- A **minor** version bump introduces backward-compatible additions (new optional fields, new conventional section headings).
- A **major** version bump may make breaking changes (renaming required fields, changing reserved filenames).

Bundles MAY declare the OKF version they target by including `okf_version: "0.1"` in a bundle-root `index.md` frontmatter block (the only place frontmatter is permitted in an `index.md`). Consumers that do not understand the declared version SHOULD attempt best-effort consumption rather than refusing the bundle.

#### OKF 规范深度总结与解读

##### 一句话总结

**OKF（Open Knowledge Format）是一种用“Markdown 文件 + YAML 元数据”组织知识的开放格式，目标是让人类和 AI Agent 都能轻松读、写、交换、维护知识。**

---

##### 1. 深度总结

###### 1.1 OKF 要解决什么问题？

AI Agent 时代，各种系统都在生成和消费“知识”：

- 数据表说明
- API 文档
- 指标定义
- 业务流程
- 运维手册
- 引用资料
- 系统上下文

但问题是：

> 不同组织、不同工具、不同 Agent 使用的知识格式不统一，导致知识难以迁移、复用、协作和长期维护。

OKF 的核心主张是：

> 知识不应该被锁在复杂平台或私有格式里，而应该用最普通、最稳定、最容易理解的格式表达。

所以它选择：

```text
目录结构 + Markdown 文件 + YAML Frontmatter
```

---

##### 2. OKF 的核心设计

###### 2.1 Knowledge Bundle：知识包

一个 OKF 知识库就是一个目录树：

```text
bundle/
├── index.md
├── log.md
├── tables/
│   ├── index.md
│   └── orders.md
└── playbooks/
    └── incident.md
```

它可以通过：

- Git 仓库分发
- zip/tar 包分发
- 放在更大项目的子目录中

其中推荐 Git，因为可以天然支持：

- 历史记录
- diff
- 协作
- 归因

---

###### 2.2 Concept：知识单元

每个普通 `.md` 文件就是一个 Concept。

它可以描述：

- 一张数据表
- 一个 API
- 一个指标
- 一个业务概念
- 一个操作手册
- 一个系统组件

例如：

```text
tables/orders.md
```

它的 Concept ID 就是：

```text
tables/orders
```

---

###### 2.3 每个 Concept 的结构

一个 OKF 文档由两部分组成：

```markdown
---
type: BigQuery Table
title: Orders
description: One row per completed customer order.
tags: [sales, orders]
---

# Schema

...
```

包括：

1. **YAML Frontmatter**：结构化元数据  
2. **Markdown Body**：正文内容

---

##### 3. Frontmatter 规范

###### 必填字段

```yaml
type: <Type name>
```

`type` 表示这个知识单元的类型，例如：

- BigQuery Table
- API Endpoint
- Metric
- Playbook
- Reference

OKF 不维护统一类型注册表。

也就是说：

> 生产者可以自由定义类型，消费者必须容忍未知类型。

---

###### 推荐字段

```yaml
title: 显示名称
description: 一句话描述
resource: 底层资源 URI
tags: [标签1, 标签2]
timestamp: 最后更新时间
```

这些字段不是强制的，但非常有用：

| 字段 | 作用 |
|---|---|
| `title` | 给人看的标题 |
| `description` | 简短摘要，可用于搜索和索引 |
| `resource` | 对应真实资产，如数据表、API 地址 |
| `tags` | 跨目录分类 |
| `timestamp` | 记录最后有意义变更时间 |

---

##### 4. Body 正文规范

正文是标准 Markdown。

OKF 建议多使用结构化内容：

- 标题
- 列表
- 表格
- 代码块
- 链接

而不是大段自由文本。

常见章节包括：

```markdown
# Schema
# Examples
# Citations
```

但这些不是强制要求。

---

##### 5. 链接机制

OKF 使用普通 Markdown 链接表达知识之间的关系。

推荐使用从根目录开始的链接：

```markdown
[customers table](/tables/customers.md)
```

也支持相对路径：

```markdown
[neighbor](./other.md)
```

一个链接意味着：

> A 知识单元与 B 知识单元存在关系。

但 OKF 不强制定义关系类型。

关系类型需要从上下文中理解，例如：

- 引用
- 依赖
- join
- 属于
- 相关

消费者通常可以把链接看作图中的一条有向边。

重要的是：

> 断链不算错误。

因为知识库可能还在建设中。

---

##### 6. index.md：目录索引

`index.md` 是保留文件名，用来列出当前目录内容。

它用于渐进式浏览：

```markdown
# Tables

* [Orders](orders.md) - One row per completed customer order.
* [Customers](customers.md) - Customer profile table.
```

它可以手写，也可以自动生成。

---

##### 7. log.md：更新日志

`log.md` 也是保留文件名，用来记录目录范围内的变更历史。

格式大致是：

```markdown
# Directory Update Log

## 2026-05-22

* **Update**: Added new table reference.
* **Creation**: Created playbook.
```

日期必须是：

```text
YYYY-MM-DD
```

---

##### 8. Citations：引用来源

如果正文中的内容来自外部资料，建议在底部写：

```markdown
# Citations

[1] [BigQuery docs](https://...)
[2] [Internal runbook](https://...)
```

引用可以指向：

- 外部 URL
- Bundle 内部路径
- `references/` 目录中的本地化资料

这让知识更可信，也方便追溯。

---

##### 9. 合规要求

一个 OKF v0.1 Bundle 合规，只需要满足：

1. 每个普通 `.md` 文件都有可解析的 YAML Frontmatter
2. 每个 Frontmatter 都有非空 `type`
3. `index.md` 和 `log.md` 如果存在，要遵守对应结构

除此之外都尽量宽容。

消费者不能因为下面问题拒绝整个 Bundle：

- 缺少可选字段
- 遇到未知 `type`
- 有未知元数据字段
- 有断链
- 没有 `index.md`

这体现了 OKF 的设计哲学：

> 宽进严出，保持开放，优先可用。

---

#### 10. 深入浅出解读

##### OKF 本质上是什么？

可以把 OKF 理解成：

> 给 AI Agent 和人类共同使用的“知识 Git 仓库格式”。

它不是数据库，不是知识图谱系统，也不是文档平台。

它更像是一个约定：

```text
我们都用 Markdown 写知识；
用 YAML 写元数据；
用目录组织层次；
用链接表达关系；
用 Git 管版本。
```

---

##### 为什么它很适合 AI Agent？

因为 Agent 需要的知识通常有几个特点：

1. **要能读懂上下文**
2. **要能定位相关概念**
3. **要能跟踪来源**
4. **要能增量更新**
5. **要能跨系统迁移**

OKF 正好提供这些能力：

| Agent 需求 | OKF 对应设计 |
|---|---|
| 找知识 | 目录、index、tags |
| 理解类型 | `type` 字段 |
| 理解摘要 | `description` |
| 找真实资源 | `resource` |
| 追踪关系 | Markdown 链接 |
| 验证来源 | Citations |
| 维护变更 | Git + log.md |

---

##### OKF 为什么刻意简单？

因为越复杂的标准，越难推广。

OKF 只规定最少的东西：

- 文件必须是 Markdown
- 元数据必须是 YAML
- 必须有 `type`
- 保留 `index.md` 和 `log.md`

其他都不强制。

这种设计的好处是：

> 任何团队几乎不需要新工具，就能开始用。

---

##### OKF 和传统知识库有什么不同？

| 对比项 | 传统知识库 | OKF |
|---|---|---|
| 存储 | 平台数据库 | 文件目录 |
| 格式 | 私有或半私有 | Markdown + YAML |
| 协作 | 平台内协作 | Git 协作 |
| 可迁移性 | 较弱 | 很强 |
| Agent 可读性 | 不稳定 | 较好 |
| 扩展性 | 依赖平台 | 依赖约定 |

---

#### 11. 辩证思考

##### 11.1 OKF 的优势

###### 1. 极低门槛

任何人会写 Markdown 就能参与。

任何 Agent 能读文本和 YAML 就能消费。

这让 OKF 很容易被组织采用。

---

###### 2. 极强可移植性

它不绑定：

- 云厂商
- 数据库
- 知识图谱系统
- SDK
- Schema Registry

只要文件还在，知识就还在。

---

###### 3. 非常适合 GitOps 和 Metadata as Code

OKF 把知识当代码管理：

- 可 review
- 可 diff
- 可回滚
- 可审计
- 可自动生成

这对企业知识治理很重要。

---

###### 4. 对 AI 友好

它既有人类可读的正文，又有机器可解析的元数据。

这比纯文档更结构化，比复杂 ontology 更轻量。

---

##### 11.2 OKF 的局限

###### 1. 语义关系较弱

链接只表示“有关联”，但不说明关系类型。

例如：

```markdown
[orders](/tables/orders.md)
```

它可能表示：

- 依赖
- 引用
- join
- 属于
- 示例

这对复杂知识图谱来说不够精确。

---

###### 2. 类型体系不统一

`type` 没有中心注册表。

好处是灵活，坏处是容易混乱。

不同团队可能写出：

```yaml
type: BigQuery Table
```

也可能写：

```yaml
type: BQTable
```

还可能写：

```yaml
type: table
```

这会增加消费端适配成本。

---

###### 3. 缺少强校验

OKF 故意宽松，但企业级场景可能需要：

- 权限控制
- 数据质量校验
- Schema 校验
- 生命周期管理
- 审批流程

这些都不属于 OKF 本身，需要外部工具补足。

---

###### 4. 大规模检索需要额外基础设施

小型知识库直接用文件没问题。

但如果有几十万文档，就需要：

- 索引系统
- 向量数据库
- 图数据库
- 搜索引擎
- 增量同步机制

OKF 只是“源格式”，不是完整知识平台。

---

##### 11.3 我的判断

OKF 的价值不在于“技术复杂”，而在于“共识简单”。

它最适合扮演：

> AI 时代的开放知识交换格式。

它不是要替代：

- 数据目录
- API 管理平台
- 知识图谱
- 数据治理系统

而是作为它们之间的中间层和可交换层。

更准确地说：

```text
OKF = 知识资产的 Markdown 化、Git 化、Agent 化
```

---

#### 12. 最精炼结论

OKF 是一个极简开放标准：

- 用目录组织知识
- 用 Markdown 表达内容
- 用 YAML 表达元数据
- 用链接表达关系
- 用 Git 管理演化
- 用引用保证可信
- 用宽松规则保证兼容

它的核心哲学是：

> 不追求一次性建成完美知识图谱，而是让知识先以最低成本流动起来。

适合：

- AI Agent 知识库
- 数据资产目录
- 企业内部知识治理
- 文档与元数据协作
- 跨组织知识交换

但若用于大规模、强语义、强治理场景，还需要额外工具和规范补充。

## 结构化（1）

### 2026-07-06 03:35:50

##### 主旨概括

OKF（Open Knowledge Format）是一种开放、轻量、便于人类和 AI Agent 共同读写的知识表示格式。它用“Markdown 文件 + YAML frontmatter”的方式组织知识，不依赖中心化注册、专用工具或复杂基础设施，目标是让知识能跨工具、组织和时间流动。

---

##### 1. OKF 的定位与设计思想

OKF 用来表示围绕数据和系统的知识，包括元数据、上下文、说明、经验和引用资料等。

核心特点：

- **人类可读**：普通 Markdown 文件即可阅读。
- **Agent 可解析**：YAML frontmatter 提供结构化元数据。
- **适合版本管理**：可以用 Git 做 diff、历史追踪和协作。
- **便于分发**：一个目录、一个 Git 仓库、zip/tar 包都可以。
- **最小规范**：只规定必要结构，不强制分类体系或工具链。

简单理解：OKF 像一个“面向人和 AI 的知识仓库标准”，但它不试图替代数据库 schema、OpenAPI、Protobuf 等专业格式，而是引用和补充它们。

---

##### 2. 设计动机：解决知识格式碎片化问题

文章指出，AI Agent 相关的知识表示方式正在快速发展，但出现了很多不兼容的约定。OKF 希望用成熟、通用的格式来降低交换成本。

OKF 追求的格式应满足：

- 不用特殊工具也能读。
- Agent 不需要专用 SDK 也能解析。
- 能在 Git 中比较差异。
- 能长期、跨组织、跨工具使用。

###### OKF 的目标

- 定义一个 Agent 可以写入的通用知识格式。
- 指导消费端 Agent 如何读取和遍历知识。
- 促进不同系统、组织之间交换知识。
- 标准化少量必要字段，让内容能被有效消费。

###### OKF 不做什么

- 不定义固定的概念类型分类。
- 不规定存储、服务、查询基础设施。
- 不替代 Avro、Protobuf、OpenAPI 等领域专用 schema。

---

##### 3. 核心术语

OKF 中几个重要概念如下：

| 术语 | 含义 |
|---|---|
| Knowledge Bundle | 一个自包含、层级化的知识文档集合，是分发单位 |
| Concept | 单个知识单元，用一个 Markdown 文件表示 |
| Concept ID | 文件路径去掉 `.md` 后的结果，例如 `tables/users.md` 的 ID 是 `tables/users` |
| Frontmatter | Markdown 文件顶部由 `---` 包围的 YAML 元数据 |
| Body | frontmatter 之后的正文内容 |
| Link | Markdown 链接，用来表示概念之间的关系 |
| Citation | 指向外部来源的链接，用来支撑正文中的说法 |

---

##### 4. Bundle 目录结构

一个 OKF Bundle 本质上是一个 Markdown 文件目录树。

示例结构：

```text
path/to/bundle/
├── index.md
├── log.md
├── <concept>.md
└── <subdirectory>/
    ├── index.md
    ├── <concept>.md
    └── ...
```

###### 分发方式

OKF Bundle 可以通过以下方式分发：

- **Git 仓库**：推荐方式，支持历史、归因、diff。
- tarball 或 zip 压缩包。
- 更大仓库中的一个子目录。

###### 保留文件名

以下文件名在任意层级都有特殊含义，不能作为普通概念文档：

| 文件名 | 用途 |
|---|---|
| `index.md` | 目录索引 |
| `log.md` | 更新历史 |

其他 `.md` 文件都视为 Concept 文档。

---

##### 5. Concept 文档格式

每个 Concept 都是一个 UTF-8 Markdown 文件，包含两部分：

1. YAML frontmatter。
2. Markdown 正文。

###### 5.1 Frontmatter 元数据

典型格式如下：

```yaml
---
type: <Type name> # 必填
title: <Optional display name>
description: <Optional one-line summary>
resource: <Optional canonical URI>
tags: [<tag>, <tag>]
timestamp: <ISO 8601 datetime>
---
```

###### 必填字段

- `type`：概念类型，必须存在且非空。
  - 例子：`BigQuery Table`、`BigQuery Dataset`、`API Endpoint`、`Metric`、`Playbook`、`Reference`。
  - 类型不需要中心注册。
  - 消费者必须能容忍未知类型。

###### 推荐字段

- `title`：人类可读标题。
- `description`：一句话摘要。
- `resource`：底层资源的唯一 URI。
- `tags`：标签列表。
- `timestamp`：最后一次有意义变更时间，ISO 8601 格式。

###### 扩展字段

生产者可以添加任意额外字段；消费者应保留未知字段，不应因为未知字段拒绝文档。

---

##### 6. Markdown 正文约定

正文是标准 Markdown，没有强制章节，但推荐使用结构化内容，例如标题、列表、表格、代码块等。

常见章节包括：

| 标题 | 用途 |
|---|---|
| `# Schema` | 描述字段、列、结构 |
| `# Examples` | 给出使用示例 |
| `# Citations` | 列出外部引用来源 |

###### 示例：BigQuery 表文档

```markdown
---
type: BigQuery Table
title: Customer Orders
description: One row per completed customer order across all channels.
resource: https://console.cloud.google.com/bigquery?p=acme&d=sales&t=orders
tags: [sales, orders, revenue]
timestamp: 2026-05-28T14:30:00Z
---

# Schema

| Column | Type | Description |
|---|---|---|
| `order_id` | STRING | Globally unique order identifier. |
| `customer_id` | STRING | Foreign key into [customers](/tables/customers.md). |
| `total_usd` | NUMERIC | Order total in US dollars. |
| `placed_at` | TIMESTAMP | When the customer submitted the order. |

# Joins

Joined with [customers](/tables/customers.md) on `customer_id`.

# Citations

[1] [BigQuery table schema](https://console.cloud.google.com/bigquery?p=acme&d=sales&t=orders)
```

这个例子展示了如何描述一张 BigQuery 表，包括字段、关联表和引用来源。

---

##### 7. 概念之间的交叉链接

OKF 使用标准 Markdown 链接表达概念之间的关系。

支持两种链接形式：

###### 形式一：从 Bundle 根目录开始

```markdown
See the [customers table](/tables/customers.md)
```

这是推荐方式，因为移动文件时更稳定。

###### 形式二：相对路径

```markdown
See the [neighboring concept](./other.md)
```

链接本身只表示“存在关系”，具体关系类型需要从上下文判断，例如：

- 引用
- 依赖
- join 关系
- 父子关系
- 相关文档

消费者通常可以把所有链接看作“有向边”，但不强制区分关系类型。

重要原则：**消费者必须容忍坏链接**。目标文件不存在并不代表 Bundle 非法，可能只是知识还没补全。

---

##### 8. `index.md`：目录索引

`index.md` 可以出现在任意目录，用来列出该目录下的内容，帮助人或 Agent 先看概览，再深入阅读。

它通常不包含 frontmatter，正文以分组标题和链接列表组成。

示例：

```markdown
# Section / Group Heading

* [Title 1](relative-url-1) - short description of item 1
* [Title 2](relative-url-2) - short description of item 2

# Another Section

* [Subdirectory](subdir/) - short description of the subdirectory
```

要点：

- 条目最好包含被链接概念的 `description`。
- 生产者可以自动生成 `index.md`。
- 如果没有 `index.md`，消费者也可以临时扫描生成。

---

##### 9. `log.md`：更新历史

`log.md` 可以出现在任意目录，用来记录该范围内的变更历史。

格式是按日期分组的扁平列表，最新日期在前。

示例：

```markdown
# Directory Update Log

## 2026-05-22

* **Update**: Added new BigQuery table reference for [Customer Metrics](/tables/customer-metrics.md).
* **Creation**: Established the [Dataplex Playbook](/playbooks/dataplex.md).

## 2026-05-15

* **Initialization**: Created foundational directory structure.
* **Update**: Added progressive-disclosure guidelines to the root [index](/index.md).
```

关键规则：

- 日期标题必须使用 `YYYY-MM-DD` 格式。
- `**Update**`、`**Creation**`、`**Deprecation**` 等只是惯例，不是强制要求。

---

##### 10. Citations：引用来源

如果正文中的说法来自外部资料，应在文档底部使用 `# Citations` 列出来源。

示例：

```markdown
# Citations

[1] [BigQuery public dataset announcement](https://cloud.google.com/blog/products/data-analytics/...)
[2] [Internal data quality runbook](https://wiki.acme.internal/data/quality)
```

引用链接可以是：

- 绝对 URL。
- Bundle 内部相对路径。
- 指向 `references/` 子目录中的 OKF 概念。

---

##### 11. 合规性要求

一个 Bundle 符合 OKF v0.1，需要满足：

1. 每个非保留 `.md` 文件都有可解析的 YAML frontmatter。
2. 每个 frontmatter 都包含非空 `type` 字段。
3. `index.md` 和 `log.md` 如果存在，应遵守对应结构。

###### 消费者不应拒绝以下情况

OKF 明确要求消费端宽容处理：

- 缺少可选字段。
- 出现未知 `type`。
- 有未知 frontmatter 字段。
- 存在坏链接。
- 缺少 `index.md`。

这种宽松模型是有意设计的，方便 Bundle 在增长、重构、部分自动生成时仍然可用。

---

##### 12. 与现有模式的关系

OKF 接近以下已有实践：

- 面向 LLM 的 Markdown + frontmatter 知识库。
- Obsidian、Notion 等个人知识管理工具的层级 Markdown 和交叉链接。
- “Metadata as code” 模式，即把目录元数据与源码一起管理，而不是放在独立注册中心。

OKF 的差异在于：它把少量必要规则明确写成规范，提升互操作性，但不绑定具体工具。

---

##### 13. 版本管理

本文定义的是 **OKF 版本 0.1**。

版本规则：

- 小版本升级：增加向后兼容内容，例如新的可选字段、常规章节标题。
- 大版本升级：可能引入破坏性变化，例如重命名必填字段或更改保留文件名。

Bundle 可以在根目录 `index.md` 中声明：

```yaml
okf_version: "0.1"
```

这是唯一允许 `index.md` 出现 frontmatter 的情况。即使消费者不理解声明版本，也应尽力读取，而不是直接拒绝。

---

##### 14. 完整示例结构

示例 Bundle：

```text
my_bundle/
├── index.md
├── datasets/
│   ├── index.md
│   └── sales.md
└── tables/
    ├── index.md
    ├── orders.md
    └── customers.md
```

其中 `tables/orders.md` 可以这样写：

```markdown
---
type: BigQuery Table
title: Orders
description: One row per completed customer order.
resource: https://console.cloud.google.com/bigquery?p=acme&d=sales&t=orders
tags: [sales, orders]
timestamp: 2026-05-28T00:00:00Z
---

# Schema

| Column | Type | Description |
|---|---|---|
| `order_id` | STRING | Unique order identifier. |
| `customer_id` | STRING | FK to [customers](/tables/customers.md). |
| `total_usd` | NUMERIC | Order total in USD. |

Part of the [sales dataset](/datasets/sales.md).
```

这个例子说明：一张订单表可以通过 frontmatter 描述元数据，通过 Markdown 表格描述 schema，并通过链接关联客户表和销售数据集。

## 口播总结（1）

### 2026-08-03 01:56:24

#### 开场：OKF 是什么

这份材料介绍的是 **OKF，也就是开放知识格式**，一种用 Markdown 文件和 YAML 元数据来组织知识的开放标准。听完之后，你会了解它为什么被设计出来、一个知识包应该怎样组织、文件里要写什么，以及人工和智能代理应该怎样读取它。

#### 一、OKF 要解决什么问题

首先，OKF 的核心结论是：知识最好放在普通、开放、容易长期使用的格式里，而不是依赖某个专用工具或中心化平台。

通俗地说，OKF 把知识保存成一组 Markdown 文件。人可以直接阅读，智能代理也可以直接解析。文件可以放进版本控制系统，查看修改差异；也可以在不同工具、组织和时间之间迁移。

它的设计非常克制。OKF 不建立中央注册中心，也不要求统一的软件工具，更不规定必须使用某种数据库或查询系统。只要能够查看文本文件，就能读取 OKF；只要能够克隆代码仓库，就能分发一套知识。

OKF 的目标主要有四个：

第一，让知识增强代理能够写入统一格式的知识。  
第二，告诉消费知识的代理，应该怎样读取和遍历这些内容。  
第三，方便不同系统和组织之间交换知识。  
第四，只统一那些保证知识能够被理解和使用的少量必要字段。

更重要的是，OKF 也明确了它不做什么。它不规定固定的概念分类，不要求某种存储、服务或查询基础设施，也不取代 Avro、Protobuf、OpenAPI 这类领域专用的模式规范。它可以引用这些规范，但不会把它们全部纳入自己内部。

#### 二、OKF 中的几个基本概念

接下来，要理解 OKF，先要掌握几个术语。

第一个是“知识包”。知识包就是一套自包含、分层组织的知识文档，也是知识分发的基本单位。它通常表现为一个目录树，里面放着许多 Markdown 文件。

第二个是“概念”。概念是知识包中的一个知识单元，对应一个 Markdown 文档。它可以描述具体资产，比如一张数据表或一个 API；也可以描述抽象内容，比如一个指标、一套业务流程，甚至其他任何需要记录的知识。

第三个是“概念 ID”。它就是概念文件的路径，只是去掉最后的“.md”后缀。比如，文件路径是“tables/users.md”，它的概念 ID 就是“tables/users”。

第四个是“前置元数据”，也叫 frontmatter。它位于 Markdown 文件最顶部，用两行单独的三个短横线包围，里面使用 YAML 格式记录元数据。

第五个是“正文”。正文就是前置元数据之后的全部 Markdown 内容。

最后是“链接”和“引用”。链接是从一个概念指向另一个概念的标准 Markdown 链接，用来表达概念之间的关系。引用则是指向外部资料的链接，用来支持正文中的某个说法。

#### 三、知识包怎样组织

OKF 的核心结构，是一个由 Markdown 文件组成的目录树。

首先，知识包的目录结构不受具体领域限制。生产者可以按照自己的知识体系来安排目录。根目录可以放概念文件，也可以放子目录；子目录还可以继续包含概念文件和更深层的子目录。

知识包可以有三种常见的分发方式：

第一种，是 Git 仓库，这是官方更推荐的方式，因为它能提供修改历史、贡献者信息和版本差异。  
第二种，是目录的压缩包，比如 tar 包或 zip 包。  
第三种，是某个更大代码仓库中的一个子目录。

这里有两个保留文件名需要特别注意。

“index.md”表示目录索引，不能当作普通概念文档使用。  
“log.md”表示更新日志，同样不能当作概念文档使用。  
除了这两个保留文件名之外，其他以“.md”结尾的文件，默认都可以是概念文档。

标签在 OKF 中仍然是一种正式的概念。OKF 不规定专门的“按标签聚合文件”格式。如果生产者需要标签浏览页面，可以在读取时扫描各个文件的前置元数据，再自动生成。

#### 四、每个概念文件包含什么

接下来是文件本身。每个概念都是 UTF-8 编码的 Markdown 文件，并且由两部分组成：顶部的 YAML 前置元数据，以及后面的 Markdown 正文。

##### 1. 前置元数据

这里最重要的结论是：每个概念文件必须有一个非空的“type”字段，也就是概念类型。

这个字段是一个简短字符串，用来说明这个概念属于什么类型。消费方可以据此进行分类、筛选、路由和展示。常见例子包括“大查询表”“大查询数据集”“API 端点”“指标”“操作手册”和“参考资料”。

OKF 不设立一个中央类型注册表。生产者只要选择清楚、容易理解的类型名称即可。如果消费方遇到未知类型，也不能因此报错，而应该把它当作普通概念处理。

除了“type”之外，还有几项推荐字段。

“title”是适合人阅读的名称。如果没有提供，消费方可以根据文件名推导。  
“description”是一句话摘要，可用于生成目录索引、搜索结果和预览。  
“resource”是底层资产的规范 URI，也就是能够唯一标识具体资源的地址。抽象概念没有对应的实体资源时，可以不填写。  
“tags”是一组简短标签，用于跨目录分类。  
“timestamp”是 ISO 8601 格式的时间，用来表示最近一次有意义的修改。

例如，一个描述客户订单表的概念文件，可以把类型写成“BigQuery Table”，标题写成“Customer Orders”，摘要说明“每一行代表一个已完成的客户订单”，再补充数据表地址、销售和订单等标签，以及最后修改时间。

OKF 还允许生产者添加其他键值字段。消费方在重新写回文件时，应该保留自己不认识的字段，也不应该因为出现未知字段就拒绝整个文档。

##### 2. Markdown 正文

正文没有强制要求的章节。生产者可以根据需要自由组织。

不过，OKF 建议优先使用有结构的 Markdown，比如标题、列表、表格和代码块，而不是一大段无结构的文字。结构越清楚，人越容易阅读，智能代理也越容易检索。

有三个标题有约定俗成的含义：

“Schema”通常用于描述数据资产的列或字段。  
“Examples”通常用于放具体使用示例，常见形式是代码块。  
“Citations”用于列出正文中引用的外部资料。

举个例子，客户订单表可以在 Schema 部分说明：订单编号是字符串，用来唯一标识订单；客户编号是字符串，用来关联客户表；订单金额是数值，表示美元金额；下单时间是时间戳，表示客户提交订单的时间。正文还可以说明，这张订单表通过客户编号与客户表连接，并在末尾列出支持这些信息的资料来源。

另一个例子是“数据新鲜度告警响应手册”。它可以把类型写成“Playbook”，摘要说明这是处理订单数据延迟告警的步骤，然后在正文中说明：当订单数据比预期服务等级协议，也就是 SLA，落后超过三十分钟时触发告警；接着列出检查摄取任务看板等处理步骤。

这里的三十分钟不是 OKF 的固定规则，而只是业务知识正文中的一个案例。

#### 五、概念之间怎样建立关系

更重要的是，OKF 允许不同概念之间互相链接。

链接可以使用两种形式。第一种是以斜杠开头的路径，它相对于知识包根目录计算。比如，订单表可以链接到“tables/customers.md”。这种写法更稳定，因为即使当前文件在子目录中移动，链接仍然以知识包根目录为基准。

第二种是普通的 Markdown 相对路径，比如链接到同一目录下的“other.md”。

一个链接代表两个概念之间存在关系。但具体是什么关系，要由链接周围的文字说明。它可以表示父子关系、引用关系、表连接关系，也可以表示依赖关系。链接本身不携带统一的关系类型。

如果消费方要建立知识图谱，通常可以把所有链接看成有方向、但没有预设类型的边。

OKF 还要求消费方能够容忍断开的链接。也就是说，链接指向的文件暂时不存在，并不代表文档格式错误。它可能只是表示那部分知识还没有写入。

#### 六、索引文件和更新日志

接下来是两个可选的辅助文件：index.md 和 log.md。

##### 1. index.md 目录索引

index.md 可以出现在知识包根目录，也可以出现在任意子目录。它的作用是列出当前目录有哪些内容，帮助人或智能代理先了解“这里有什么”，再决定是否打开具体文件。这种方式叫渐进式披露。

索引通常按照分组标题组织内容。每项包含一个链接、一个名称，以及来自概念元数据的简短描述。索引也可以列出子目录，并说明子目录的用途。

index.md 通常不使用前置元数据。唯一的例外是知识包根目录的 index.md，可以用前置元数据声明 OKF 版本。

生产者可以自动生成 index.md。即使文件不存在，消费方也可以扫描目录和前置元数据，临时合成索引。

##### 2. log.md 更新日志

log.md 用来记录某个目录范围内的修改历史。它采用按日期分组的平面列表，并且最新日期放在最前面。

日期必须使用 ISO 8601 的“年、月、日”格式，比如“2026-05-22”。日志内容可以写成“更新”“创建”或“弃用”等说明。开头加粗的动作词是一种惯例，但不是强制要求。

例如，日志可以记录：某天新增了客户指标表的引用；另一天建立了数据平台操作手册；更早的时候完成了基础目录结构，并加入了渐进式披露指南。

#### 七、外部引用怎样写

如果正文中的某个判断来自外部材料，OKF 建议在文档底部增加“Citations”，也就是引用章节。

引用通常按编号列出，并给出资料名称和地址。地址可以是外部网页，也可以是知识包内部的相对路径，还可以指向一个 references 目录。这样一来，外部资料本身也可以被保存成 OKF 概念，成为知识包中的一等内容。

这样做的意义是，让正文中的关键说法能够追溯来源，而不是只留下没有根据的结论。

#### 八、什么样的知识包算符合 OKF

按照 OKF 0.1 版本，一个符合规范的知识包至少要满足三点。

第一，目录树中除保留文件之外的每一个 Markdown 文件，都必须包含可以解析的 YAML 前置元数据。  
第二，每个前置元数据块都必须有非空的 type 字段。  
第三，如果出现 index.md 或 log.md，它们必须遵循各自规定的结构。

除此以外，大多数规则都只是宽松指导，而不是必须执行的硬性条件。

消费方不能因为以下情况就拒绝整个知识包：

缺少可选字段；  
遇到未知的类型名称；  
遇到额外的、自己不认识的元数据字段；  
发现链接暂时断开；  
或者发现没有 index.md 文件。

这种宽松的读取方式是有意设计的。因为知识包可能不断扩大、重构，也可能有一部分内容是由智能代理自动生成的。如果要求所有内容一开始就完全整齐，格式就很难长期使用。

#### 九、OKF 与其他知识组织方式的关系

OKF 并不是凭空出现的。它与几种已有做法比较接近。

第一类，是使用 Markdown 和前置元数据的智能代理知识库。  
第二类，是 Obsidian、Notion 这类个人知识工具所使用的层级化 Markdown 和交叉链接。  
第三类，是“元数据即代码”的做法，也就是把目录元数据和源代码放在一起，而不是存进单独的注册中心。

OKF 与这些做法最主要的区别在于：它把最少的一组互操作规则明确写了下来。它不强迫大家使用同一种工具，但规定了不同工具之间能够共同理解的基本结构。

#### 十、版本管理和一个完整例子

最后，OKF 0.1 是当前这份材料定义的版本。未来版本采用“主版本号加次版本号”的形式。

次版本升级表示向后兼容的增加，比如加入新的可选字段或新的约定章节。主版本升级则可能带来不兼容变化，比如修改必填字段名称，或者改变保留文件名。

知识包可以在根目录的 index.md 前置元数据中写入 `okf_version: "0.1"`，声明自己针对哪个版本。不了解这个版本的消费方，也应该尽量读取，而不是直接拒绝。

一个完整的知识包可以包含根目录的 index.md、数据集目录和数据表目录。数据集目录里可以有一个销售数据集概念；数据表目录里可以有订单表和客户表。订单表文件的类型可以是 BigQuery Table，标题是 Orders，摘要说明每一行代表一个客户订单，并列出订单编号、客户编号和美元金额。订单表还可以通过链接指向客户表，并说明它属于销售数据集。

这个例子体现了 OKF 的全部核心思路：目录负责组织层级，前置元数据负责描述概念，正文负责记录具体知识，链接负责表达关系，而索引和日志负责帮助浏览与追踪变化。

#### 结尾：最值得记住的五点

最后，回顾五个最值得记住的结论。

第一，OKF 是一种开放知识格式。它用普通 Markdown 加 YAML 元数据表示知识，既方便人读，也方便智能代理处理。

第二，OKF 的设计非常简洁。它不要求中央注册中心、专用 SDK 或固定基础设施，只统一少量必要结构。

第三，一个知识包就是一棵 Markdown 目录树。每个普通 Markdown 文件代表一个概念，必须有非空的 type 字段；index.md 和 log.md 则分别承担索引和日志功能。

第四，OKF 鼓励用标准 Markdown 链接连接概念，并且要求消费方容忍未知字段、未知类型、断开链接和缺少索引。

第五，OKF 0.1 追求的是互操作性，而不是把所有知识都规定成同一种形状。它允许不同组织自由组织内容，同时保留一套足够小、足够清楚的共同规则。

## 深度解读（1）

### 2026-09-18 00:37:56

#### OKF 的价值不在“知识格式”，而在为人和 Agent 找到最低协作成本

OKF v0.1 并没有发明新的知识表示技术：一个目录、若干 Markdown 文件、YAML 元数据、普通链接，再加上可选的索引与更新日志。它真正提出的是一个值得检验的判断：**Agent 时代的知识互操作，可能不需要先建立统一知识图谱，而应先形成一个任何人都能读、任何模型都能解析、任何仓库都能保存的最低公约数。**

##### 少规定，反而可能更容易成为协议

OKF 只强制概念文档具有可解析的 frontmatter 和非空 `type`；标题、描述、资源地址、标签、时间戳均可选，类型也不需要中央注册。消费者必须容忍未知字段、未知类型、断链和缺失索引。

这种宽松不是遗漏，而是核心设计。知识库往往处于持续生成、迁移和局部失效之中，尤其当多个 Agent 同时写入时，要求全量完整、类型统一、引用无误，反而会让交换协议变成治理工程。OKF 选择让不完整内容仍可消费，以降低跨工具和跨组织流动的门槛。

代价同样明确：`Metric`、`Playbook` 等类型会逐渐产生语义漂移，链接只表示“有关联”，具体关系依赖上下文文本。它适合做**可携带的知识包**，却不能直接替代强类型数据目录、权限系统或知识图谱。

##### `index.md` 实际上是一种上下文预算机制

规范中最容易被低估的是“渐进披露”：Agent 先读取目录索引和一句话描述，再决定打开哪些概念，而不是把整个知识库塞进上下文。这不仅方便浏览，更接近一种面向模型的接口设计——目录负责发现，frontmatter 负责路由和筛选，正文提供细节，链接支持继续遍历。

这一模式可迁移到代码库文档、客服知识、数据资产和操作手册。它的效果取决于索引质量、描述准确性，以及 Agent 是否真的遵循分层读取；仅仅把现有文档转换成 Markdown，并不会自然提升检索和推理效果。

##### 它解决的是包装，不是可信度

OKF 对引用、时间戳和日志有所约定，但引用只是建议项，时间戳由生产者声明，也没有处理作者身份、审批状态、访问控制、冲突合并和内容过期。因此，一个完全合规的知识包仍可能陈旧、矛盾或缺乏依据。

这也界定了更现实的产品机会：未必是再做一个知识编辑器，而是围绕开放文件格式提供治理层，例如自动生成索引、检查链接与引用、标记过期内容、同步权限、评估 Agent 检索效果，并在往返转换时保留未知字段。真正需要验证的不是“Markdown 是否流行”，而是团队是否确实遭遇知识被锁在 Wiki、数据目录和专有 Agent 平台之间，且可移植格式能显著降低迁移与协作成本。

**OKF 目前更像一个有方向感的草案，而不是已经成立的标准。**它最重要的启发是：在快速变化的 Agent 生态里，先标准化“如何打包、发现和传递知识”，可能比过早统一“知识究竟应该如何建模”更务实。
