## 正文

An agent harness is a combination of several different capabilities that make building long-running agents easier:

- Planning capabilities
- Virtual filesystem
- Task delegation (subagents)
- Context and token management
- Code execution
- Human-in-the-loop

Alongside these capabilities, Deep Agents use Skills and Memory for additional context and instructions.

#### Planning capabilities

The harness provides a `write_todos` tool that agents can use to maintain a structured task list.**Features:**

- Track multiple tasks with statuses (`'pending'`, `'in_progress'`, `'completed'`)
- Persisted in agent state
- Helps agent organize complex multi-step work
- Useful for long-running tasks and planning

#### Virtual filesystem access

The harness provides a configurable virtual filesystem which can be backed by different pluggable backends. The backends support the following file system operations:The virtual filesystem is used by several other harness capabilities such as skills, memory, code execution, and context management. You can also use the file system when building custom tools and middleware for Deep Agents.For more information, see backends.

#### Task delegation (subagents)

The harness allows the main agent to create ephemeral “subagents” for isolated multi-step tasks.**Why it’s useful:**

- **Context isolation** - Subagent’s work doesn’t clutter main agent’s context
- **Parallel execution** - Multiple subagents can run concurrently
- **Specialization** - Subagents can have different tools/configurations
- **Token efficiency** - Large subtask context is compressed into a single result

**How it works:**

- Main agent has a `task` tool
- When invoked, it creates a fresh agent instance with its own context
- Subagent executes autonomously until completion
- Returns a single final report to the main agent
- Subagents are stateless (can’t send multiple messages back)

**Default subagent:**

- “general-purpose” subagent automatically available
- Has filesystem tools by default
- Can be customized with additional tools/middleware

**Custom subagents:**

- Define specialized subagents with specific tools
- Example: code-reviewer, web-researcher, test-runner
- Configure via `subagents` parameter

#### Context management

The harness manages context so deep agents can handle long-running tasks within token limits while retaining the information they need.**How it works:**

- **Input context** — System prompt, memory, skills, and tool prompts shape what the agent knows at startup
- **Compression** — Built-in offloading and summarization keep context within window limits as tasks progress
- **Isolation** — Subagents quarantine heavy work and return only results (see Task delegation)
- **Long-term memory** — Persistent storage across threads via the virtual filesystem

**Why it’s useful:**

- Enables multi-step tasks that exceed a single context window
- Keeps the most relevant information in scope without manual trimming
- Reduces token usage through automatic summarization and offloading

For configuration details, see Context engineering.

#### Code execution

When you use a sandbox backend, the harness exposes an `execute` tool that lets the agent run shell commands in an isolated environment. This enables the agent to install dependencies, run scripts, and execute code as part of its task.**How it works:**

- Sandbox backends implement the `SandboxBackendProtocol` — when detected, the harness adds the `execute` tool to the agent’s available tools
- Without a sandbox backend, the agent only has filesystem tools (`read_file`, `write_file`, etc.) and cannot run commands
- The `execute` tool returns combined stdout/stderr, exit code, and truncates large outputs (saving to a file for the agent to read incrementally)

**Why it’s useful:**

- **Security** — Code runs in isolation, protecting your host system from the agent’s operations
- **Clean environments** — Use specific dependencies or OS configurations without local setup
- **Reproducibility** — Consistent execution environments across teams

For setup, providers, and file transfer APIs, see Sandboxes.

#### Human-in-the-loop

The harness can pause agent execution at specified tool calls to allow human approval or modification. This feature is opt-in via the `interrupt_on` parameter.**Configuration:**

- Pass `interrupt_on` to `create_deep_agent` with a mapping of tool names to interrupt configurations
- Example: `interrupt_on={"edit_file": True}` pauses before every edit
- You can provide approval messages or modify tool inputs when prompted

**Why it’s useful:**

- Safety gates for destructive operations
- User verification before expensive API calls
- Interactive debugging and guidance

#### Skills

The harness supports skills that provide specialized workflows and domain knowledge to your deep agent.**How it works:**

- Skills follow the [Agent Skills standard](https://agentskills.io/)
- Each skill is a directory containing a `SKILL.md` file with instructions and metadata
- Skills can include additional scripts, reference docs, templates, and other resources
- Skills use progressive disclosure—they are only loaded when the agent determines they’re useful for the current task
- Agent reads frontmatter from each `SKILL.md` file at startup, then reviews full skill content when needed

**Why it’s useful:**

- Reduces token usage by only loading relevant skills when needed
- Bundles capabilities together into larger actions with additional context
- Provides specialized expertise without cluttering the system prompt
- Enables modular, reusable agent capabilities

For more information, see Skills.

#### Memory

The harness supports persistent memory files that provide extra context to your deep agent across conversations. These files often contain general coding style, preferences, conventions, and guidelines that help the agent understand how to work with your codebase and follow your preferences.**How it works:**

- Uses [`AGENTS.md` files](https://agents.md/) to provide persistent context
- Memory files are always loaded (unlike skills, which use progressive disclosure)
- Pass one or more file paths to the `memory` parameter when creating your agent
- Files are stored in the agent’s backend (StateBackend, StoreBackend, or FilesystemBackend)
- The agent can update memory based on your interactions, feedback, and identified patterns

**Why it’s useful:**

- Provides persistent context that doesn’t need to be re-specified each conversation
- Useful for storing user preferences, project guidelines, or domain knowledge
- Always available to the agent, ensuring consistent behavior

For configuration details and examples, see Memory.

## 通俗精炼（1）

### 2026-03-25 01:51:24

#### Harness 能力总结：让长任务 Agent 更好用的 “工具箱”

##### 一、它是什么

Harness 可以理解为一套给 Agent 配备的 “基础设施”，目的是让 Agent 更稳定地处理**复杂、多步骤、长周期任务**。

它不仅让 Agent 能 “思考”，还让它能**规划、执行、记忆、协作、受控运行**。  
核心能力包括：**任务规划、虚拟文件系统、子代理协作、上下文管理、代码执行、人工介入、技能、记忆**。

---

##### 二、核心价值

###### 1. 让 Agent 能做更复杂的事
普通 Agent 容易受上下文长度、任务复杂度限制；Harness 通过规划、压缩上下文、拆分任务，让 Agent 可以完成更长链路的工作。

###### 2. 让执行更可控、更安全
通过沙箱执行和人工审批机制，Agent 可以运行代码，但不会失控，适合真实生产环境。

###### 3. 让 Agent 越用越 “懂你”
借助 Skills 和 Memory，Agent 不只是一次性回答问题，而是逐步形成稳定的工作方式和偏好理解。

---

##### 三、八项关键能力

###### 1. 任务规划：让 Agent 会拆解任务
Harness 提供`write_todos`工具，帮助 Agent 维护任务清单，并标记状态，如待处理、进行中、已完成。

**作用：**
- 适合复杂、多步骤任务
- 让长流程执行更有条理
- 支持任务状态持续保存

###### 2. 虚拟文件系统：给 Agent 一个 “工作空间”
Harness 提供可配置的虚拟文件系统，Agent 可以在里面读写文件。

**作用：**
- 是技能、记忆、代码执行等能力的基础
- 方便扩展自定义工具和中间件
- 让 Agent 有稳定的操作环境

###### 3. 子代理协作：把复杂任务分包处理
主 Agent 可以临时创建多个子 Agent，分别处理独立子任务，最后只返回结果。

**优势：**
- 隔离上下文，避免主 Agent 被细节拖累
- 支持并行执行，提高效率
- 不同子代理可承担不同角色，如代码审查、测试、研究等
- 更省 token，因为中间过程被压缩成最终结果

###### 4. 上下文管理：解决长任务 “记不住” 的问题
Harness 会自动管理上下文，把重要信息保留，把冗余内容压缩或转存。

**作用：**
- 支持超出单轮上下文窗口的任务
- 自动摘要、压缩，降低 token 消耗
- 保持关键内容持续在上下文中

###### 5. 代码执行：让 Agent 真正动手
如果接入沙箱环境，Agent 可以通过`execute`工具运行命令、装依赖、执行脚本。

**价值：**
- 在隔离环境中运行，更安全
- 环境可复现，适合团队协作
- 不依赖本地手工配置，执行更标准化

###### 6. 人工介入：关键动作可审批
Harness 支持在特定工具调用前暂停，让人类审批、修改或指导。

**适用场景：**
- 文件编辑前确认
- 高成本 API 调用前审核
- 高风险操作前加一道保险

###### 7. Skills：把专业能力模块化
Skills 是可复用的能力包，本质上是一套带说明文档、脚本、模板和资源的专业工作流。

**特点：**
- 只有在需要时才加载，节省 token
- 能把复杂能力打包复用
- 让 Agent 具备更专业的领域能力

###### 8. Memory：让 Agent 有长期记忆
Memory 通过`AGENTS.md`等文件，为 Agent 提供跨会话持续生效的偏好和规则。

**作用：**
- 记住用户习惯、代码规范、项目约定
- 每次对话无需重复交代背景
- 保证 Agent 长期行为一致

---

##### 四、整体理解

###### 1. Harness 不只是 “能力集合”，而是 Agent 的运行框架
它解决的不是 “回答问题”，而是 “如何让 Agent 在真实任务里持续、稳定、可控地工作”。

###### 2. 核心逻辑是四个字：能做、会做、稳做
- **能做**：有文件系统、执行环境、子代理
- **会做**：有规划、技能、上下文压缩
- **稳做**：有人类审批、沙箱隔离、长期记忆

---

##### 五、一句话总结

Harness 的本质，是把 Agent 从 “会聊天的模型” 升级成一个**可规划、可执行、可协作、可记忆、可管控的任务系统**。

#### 内容总结

这篇文档介绍了 LangChain Deep Agents 的 `harness`（运行支架）是什么，以及它为“长时间运行、可执行复杂任务的智能体”提供了哪些核心能力。

它主要包括 6 类能力：

- **规划能力**：用 `write_todos` 维护任务清单，跟踪任务状态。
- **虚拟文件系统**：给智能体一个可配置的文件读写环境，很多能力都依赖它。
- **任务委派（子智能体）**：主智能体可以把子任务交给临时子智能体处理，减少上下文污染。
- **上下文管理**：通过压缩、隔离、长期记忆等方式，解决 token 不够用的问题。
- **代码执行**：如果接入沙箱环境，智能体可以运行 shell 命令、脚本、安装依赖。
- **人工介入**：可以在某些工具调用前暂停，让人审核、修改或批准。

此外，文档还提到两个“增强组件”：

- **Skills**：按需加载的专业技能包。
- **Memory**：跨对话持久保留的记忆文件，如偏好、规范、项目约定等。

#### 深入浅出地解读

##### 1. Harness 本质上是什么？

可以把 `harness` 理解成：**给智能体配的一整套工作平台**。

如果没有 harness，智能体通常只是“会对话、会推理”；  
有了 harness，它才更像一个真正能干活的助手，能：

- 自己列计划
- 读写文件
- 拆分任务
- 跑代码
- 记住长期信息
- 在关键动作前等你确认

也就是说，`harness` 不是单一功能，而是把智能体从“聊天机器人”提升为“可执行任务的代理系统”。

---

##### 2. 为什么“规划能力”重要？

文档里提到 `write_todos`，本质就是让智能体有一个**任务看板**。

这很重要，因为复杂任务往往不是一步完成的，比如：

1. 先分析需求
2. 再修改文件
3. 然后运行测试
4. 最后整理结果

如果智能体不能跟踪这些步骤，就容易：

- 做到一半忘了前面干了什么
- 跳步骤
- 重复劳动
- 无法清晰汇报进度

所以，规划能力让智能体更像一个“会管理自己工作流的人”。

---

##### 3. 虚拟文件系统解决了什么问题？

它相当于给智能体一个**安全、统一、可插拔的工作目录**。

智能体很多操作都离不开文件，比如：

- 读取项目代码
- 写入修改后的文件
- 存储中间结果
- 保存记忆和技能文件

文档强调它是很多能力的基础，因为：

- **Skills** 需要从文件读取说明和资源
- **Memory** 需要持久保存
- **代码执行** 往往也要依赖文件输入输出
- **上下文管理** 可能要把信息卸载到文件里

简单说：**没有文件系统，很多“能干活”的能力就落不了地。**

---

##### 4. 子智能体为什么是亮点？

这是这篇文档里很关键的一点。

主智能体可以创建一个“临时子智能体”去处理某个子任务，比如：

- 代码审查
- 查资料
- 跑测试
- 分析日志

这样做的好处很明显：

###### 上下文更干净
如果所有细节都堆在主智能体上下文里，很快就会爆 token。  
子智能体把脏活累活处理完，只把最终结果带回来，主智能体就轻松很多。

###### 可以并行
多个子任务可以同时做，效率更高。

###### 可以专业分工
不同子智能体可以配置不同工具，像不同岗位的人协作。

###### 更省 token
子任务过程不用全部保留在主上下文里，只保留结论。

通俗地说：  
**主智能体像项目经理，子智能体像外包小组或专项员工。**

---

##### 5. 上下文管理在解决什么核心痛点？

大模型最大的问题之一就是：**上下文窗口有限**。

任务一长，就会出现：

- 早期信息丢失
- 对话越来越贵
- 重点和噪声混在一起
- 模型记不住真正重要的内容

文档给出的解法是几种组合拳：

- **输入上下文设计**：系统提示、记忆、技能共同决定起始认知
- **压缩与卸载**：把不重要或过长的信息总结、迁移
- **子智能体隔离**：把重任务放到独立上下文
- **长期记忆**：跨会话保存稳定信息

这本质上是在做“信息分层管理”：

- 当前必须知道的，放在眼前
- 暂时不用但以后可能要的，压缩保存
- 长期稳定不变的，放进记忆

这让智能体更适合处理真正复杂、持续时间长的任务。

---

##### 6. 代码执行为什么必须配沙箱？

文档明确说：只有使用支持沙箱的 backend，才会给智能体 `execute` 工具。

原因很现实：  
如果智能体可以直接在宿主机上执行命令，风险很高，比如：

- 改坏环境
- 安装错误依赖
- 执行危险命令
- 泄漏敏感数据

所以沙箱的价值在于：

- **安全隔离**
- **环境干净**
- **结果可复现**

这意味着 harness 不是只追求“能力强”，也在兼顾“安全可控”。

---

##### 7. 人工介入为什么很实用？

文档里的 `interrupt_on` 可以在某些工具调用前暂停，比如：

- 编辑文件前
- 发起昂贵请求前
- 执行危险操作前

这很像给智能体加“人工审批流”。

它的意义在于：

- 防止误操作
- 给用户保留控制权
- 便于调试和纠偏

所以 human-in-the-loop 不是让智能体变慢，而是让它在关键节点更可靠。

---

##### 8. Skills 和 Memory 有什么区别？

这两个很容易混淆，但其实定位不同：

###### Skills
是“按需调用的专业能力包”。

特点：

- 平时不全部展开
- 需要时再加载详细内容
- 适合封装某类任务的方法和资源

像是智能体的“工具书”或“岗位手册”。

###### Memory
是“始终存在的长期记忆”。

特点：

- 每次都会加载
- 记录偏好、规范、经验
- 帮助智能体长期保持一致行为

像是智能体的“长期工作习惯”和“用户档案”。

一句话区分：

- **Skills：做事的方法库**
- **Memory：长期不忘的背景信息**

---

#### 我的意见

我认为这套设计思路是比较成熟的，尤其适合真正要落地的 Agent 系统。

优点很明显：

- **完整**：不只是模型调用，而是覆盖计划、执行、记忆、安全、协作。
- **实用**：很多设计都在解决真实痛点，比如 token 限制、任务拆分、人工审核。
- **可扩展**：文件系统、子智能体、技能包、记忆机制都便于定制。

但也有几点要注意：

- **系统会更复杂**：能力越多，配置和调试成本越高。
- **对子智能体和上下文设计要求高**：设计不好，反而会增加混乱。
- **Memory 需要治理**：如果长期写入不加约束，记忆可能变脏、变冗余。
- **人工介入策略要拿捏好**：拦太多会影响效率，拦太少又有风险。

我的总体判断是：

> `harness` 的价值不在于“给智能体加几个工具”，而在于为智能体建立了一套能长期工作的操作系统。

如果你是想做一个真正可执行、可持续、可控的 Agent，这篇文档讲的不是“锦上添花”，而是“基础设施”。
