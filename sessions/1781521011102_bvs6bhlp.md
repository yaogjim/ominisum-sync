## 正文

**马东锡 NLP**

### 工具是契约，而非功能

Harness 系列文章之 3，工具即契约。

如果 Coding Agent 拥有一个世界，那么每次 tool call，就是用 generated text 请求改变其世界的状态。

Tool call 很容易显得过于简单，model 输出 JSON，Harness parse 它，某个本地 function 被执行，result 被放回下一轮 prompt。

这是 tiny agent 版本。

但 coding agent 的 tool call，并非简单的 function。

工具调用来自生成的文本，它正在请求访问工作区、Shell、网络、转录内容或者另一个 Agent。

这个差异会改变整个 Coding Agent 的状态和所处的环境。

> 模型可以提问。框架做决定。

#### 建议书与合同

想象 model 输出：

它看起来很 structured，它依然只是一份 proposal。

Model 产出了看似合法的 JSON，并不自动获得 write access。

Harness 仍然需要回答：

- 这个 tool 是否存在？
- args 是否匹配 schema？
- path 是否在 workspace 内？
- 这是创建、覆盖，还是补丁？
- model 最近是否读过现有文件？
- 文件状态基线是否是最新的？
- 这个 action 是否需要 approval？
- approval 前应该给 human 看什么？
- 多少 result output 可以安全进入 context？
- 执行之后需要更新哪些 transcript 和 state？

这一串问题，就是 tool contract。

#### 朴素设计

朴素设计会把工具当作一个函数映射表：

这段代码很短，所以看起来干净， 但它同时把很多责任压进了一行。

解析、模式验证、路径安全、权限策略、沙箱选择、执行、输出裁剪、转录记录、状态更新，全都被塞进 tool(...)

Demo 可以这样写。但能够修改真实 repo 的 coding agent，需要更强的边界。问题不在 function 本身，问题在于 tool boundary 有不同的 trust rules。

函数调用 vs 工具调用

> 在普通程序中，函数调用是实现细节。

> coding agent 里，tool call 是 generated text 请求改变真实世界的位置。

#### 工具合同包含的内容

有用的 tool contract 不能只有 name 和 handler。它应该描述：

有些字段面向 model。有些字段只属于 harness。

Model 需要足够的信息来正确发起请求，Harness 需要足够的 metadata 来正确裁决。

#### 生命周期

一个最小可用 lifecycle：

每一步拦截不同类型的问题。

- 解析处理格式错误的输出
- 模式验证处理缺失字段和错误类型
- 路径验证 处理 工作区逃逸
- 策略处理风险操作、审批、沙箱、拒绝
- 执行 运行真实处理程序
- bounding 避免一次 command 或 file read 淹没下一轮 prompt
- recording 让下一轮可以恢复和审计

所以，“just call the function” 这个 mental model 不够用，function 只是 lifecycle 中的很小片段。

#### 批准前验证

validation 应该发生在 approval 之前。

- 如果 patch\_file 指向 workspace 外，先 reject
- 如果 old\_text 缺失或有歧义，先 reject
- 如果 tool call 立刻重复上一轮失败请求，先 reject 或 retry
- 如果 write 目标是现有文件，但缺少 fresh baseline，先 reject
- 批准是产品表面

用户不应该被要求判断一个本来就无效的请求。，需要 approval 时，summary 应该保持 bounded。

文件编辑的审批提示应该展示受影响的路径和变更形态，避免倾倒无界原始内容。

Harness 可以之后展示 diff，count，preview。Approval boundary 要小而清楚。

#### 有边界的结果是安全的一部分

Tool output 会变成 context，Context 会影响 Agent 行为。

- 如果 search 返回 10,000 条结果，model 并没有更清楚
- 如果 run\_shell 打出巨大 log，下一轮可能丢掉真正的 user request
- 如果 read\_file 每一轮重复同一个未变化文件，有用 context 会被 duplicate text 挤走

所以工具契约需要结果限制：

这不只是 token cost，它关系到 model working set 是否准确。

Harness 应该决定哪些结果证据进入记录，哪些成为持久状态，哪些保留为外部工件引用。

评估一个 coding-agent tool 时，不要先问：

> model 能不能 call 它？

更应该问：

- 论证模式精确吗？
- 这个 tool 能 read 或 mutate 什么？
- 哪些路径、命令、资源被允许？
- 运行前需要哪种 fresh state？
- 允许、请求、沙箱、拒绝由什么策略决定？
- 什么 result evidence 会回到 model？
- success 或 failure 之后，哪些 durable state 会变化？
- 之后如何把这个 call 和 result 配对？

Model 可以请求，Harness 负责裁决。

Tool Call 只在 Harness 裁决批准后执行。

这个过程，就是契约。

简而言之，工具即契约。

## 通俗精炼（1）

### 2026-06-15 10:54:39

#### 工具是契约，而非功能

##### 核心观点

在 Coding Agent 中，**工具调用不是简单的函数调用，而是模型用生成文本请求改变真实世界状态**。  
因此，工具不应被理解为“功能入口”，而应被设计成一套明确的 **契约机制**。

模型可以提出请求，但是否执行、如何执行、执行后如何记录，必须由 Harness 裁决。

---

##### 为什么工具不是函数

普通程序里的函数调用，是代码内部的实现细节。  
但 Coding Agent 的 tool call 可能会访问或修改：

- 工作区文件
- Shell 环境
- 网络资源
- 其他 Agent
- 转录内容与上下文状态

这意味着一次工具调用可能真实改变项目、环境和后续推理上下文。  
所以，`model 输出 JSON → 执行函数` 这种朴素模式，只适合 Demo，不适合真实 Coding Agent。

---

##### 工具调用本质上是“建议书”

模型输出的结构化 JSON，看起来像合法请求，但它只是一个 proposal。  
Harness 需要继续判断：

- 工具是否存在
- 参数是否符合 schema
- 路径是否安全
- 是否会创建、覆盖或修改文件
- 模型是否读过最新文件
- 是否需要人工审批
- 执行结果能否安全进入上下文
- 执行后如何更新状态和记录

这些判断共同构成了 **tool contract，工具契约**。

---

##### 工具契约应包含什么

一个成熟的工具契约，不能只有 `name + handler`，还应包含：

- 参数 schema
- 权限边界
- 路径限制
- 可读写资源范围
- 沙箱策略
- 审批规则
- 输出裁剪规则
- 状态更新规则
- 审计与记录机制

其中一部分信息给模型看，帮助它正确请求；另一部分只属于 Harness，用来做安全裁决。

---

##### 工具调用的完整生命周期

一个可靠的工具调用，大致应经过以下流程：

1. **解析**：处理格式错误  
2. **模式验证**：检查字段缺失、类型错误  
3. **路径验证**：防止越权访问工作区外路径  
4. **策略判断**：决定允许、拒绝、审批或沙箱执行  
5. **执行**：调用真实处理程序  
6. **结果限制**：避免超大输出污染上下文  
7. **记录状态**：支持恢复、审计和下一轮推理

函数执行只是其中很小的一步。

---

##### 审批前必须先验证

无效请求不应交给用户审批。  
例如：

- 修改 workspace 外文件，应直接拒绝
- patch 缺少明确 old_text，应拒绝
- 重复上一次失败请求，应拒绝或重试
- 修改现有文件但没有最新基线，应拒绝

审批是产品界面，不是安全兜底。  
用户看到的审批信息应小而清晰，例如受影响路径、变更类型、diff 预览，而不是大量原始内容。

---

##### 输出边界也是安全机制

工具输出会进入上下文，进而影响模型后续行为。  
如果输出不受限制，会带来问题：

- 搜索结果过多，模型反而更混乱
- Shell 日志过大，挤掉真正重要的用户需求
- 重复读取相同文件，浪费上下文窗口

因此，工具契约必须规定：

- 输出数量限制
- 内容截断策略
- 哪些结果进入上下文
- 哪些结果作为持久状态保存
- 哪些结果作为外部引用保留

这不仅是 token 成本问题，更关乎模型工作记忆的准确性。

---

##### 评估工具时应问什么

不要只问：模型能不能调用这个工具？  
更应该问：

- 参数模式是否精确
- 它能读写什么资源
- 哪些路径、命令、网络资源被允许
- 执行前需要什么最新状态
- 什么情况下允许、拒绝、审批或沙箱执行
- 哪些结果证据会返回给模型
- 成功或失败后会改变哪些持久状态
- 如何把调用与结果准确配对并审计

---

##### 一句话总结

**工具调用是模型提出的请求，Harness 才是裁决者。**

在真实 Coding Agent 中，工具不是函数表，而是一套围绕权限、安全、状态、审批、输出和审计建立的契约系统。  
所以，**工具即契约，而非功能。**

---

##### 3. 朴素设计的问题：把工具当函数表

简单实现通常会把工具设计成函数映射表：

> 模型请求某个工具 → 调用对应函数 → 返回结果

这种写法在 Demo 中看起来很干净，但问题是它把太多责任压进了一步里，包括：

- 解析输出
- 参数验证
- 路径安全
- 权限策略
- 沙箱选择
- 实际执行
- 输出裁剪
- 转录记录
- 状态更新

对于能修改真实代码仓库的 Coding Agent，这种边界太弱。  
核心问题不是函数本身，而是 **工具边界有不同的信任规则**。

---

##### 4. 函数调用与工具调用的本质区别

在普通程序中，函数调用只是实现细节。

但在 Coding Agent 中，工具调用是：

> 模型通过生成文本，请求改变真实世界状态。

因此，工具不能只包含 `name` 和 `handler`，还需要描述更多契约信息。

其中：

- 一部分字段是给模型看的，帮助模型正确发起请求；
- 一部分字段只属于 Harness，用来做权限、策略和安全裁决。

---

##### 5. 工具调用应有完整生命周期

一个最小可用的工具调用生命周期包括：

1. **解析**：处理格式错误的模型输出  
2. **Schema 验证**：检查缺失字段、错误类型  
3. **路径验证**：防止访问 workspace 外部路径  
4. **策略判断**：处理风险操作、审批、沙箱、拒绝  
5. **执行**：运行真正的工具处理程序  
6. **结果限制**：避免命令输出或文件内容淹没上下文  
7. **记录状态**：方便下一轮恢复、审计和追踪

所以，“just call the function” 的理解是不够的。  
函数执行只是整个生命周期中的一小部分。

---

##### 6. 验证应该发生在用户批准之前

文章强调：**validation 应该先于 approval。**

也就是说，不应该让用户审批一个本来就无效的请求。

例如：

- `patch_file` 指向 workspace 外：直接拒绝
- `old_text` 缺失或有歧义：直接拒绝
- 工具调用重复上一轮失败请求：拒绝或重试
- 修改现有文件但没有最新文件基线：拒绝

用户批准应该只面对已经通过基础验证、确实需要人工决策的请求。

---

##### 7. Approval 是产品表面，要小而清楚

当工具调用需要用户批准时，展示内容应该是有边界的，而不是把大量原始内容直接倾倒给用户。

例如文件编辑审批中，应展示：

- 受影响路径
- 变更类型
- diff 摘要
- 变更数量
- 预览内容

这样用户能快速理解风险和影响。  
审批边界应该 **小、清楚、可判断**。

---

##### 8. 有边界的结果输出也是安全的一部分

工具输出会进入上下文，而上下文会影响 Agent 后续行为。

如果不限制结果，会带来问题：

- search 返回 10,000 条结果，模型反而更难判断重点；
- run_shell 输出巨大日志，可能挤掉真正重要的用户请求；
- read_file 每轮重复读取同一文件，会让上下文被重复文本污染。

因此，工具契约需要限制结果输出，例如：

- 最大输出长度
- 摘要策略
- 截断规则
- 哪些证据进入上下文
- 哪些内容作为持久状态保存
- 哪些内容只作为外部工件引用

这不只是节省 token，而是保证模型的 working set 准确。

---

##### 9. 评估工具时，应关注契约而非能否调用

评估一个 Coding Agent 工具，不应只问：

> 模型能不能调用它？

更应该问：

- 参数 schema 是否精确？
- 这个工具能读取或修改什么？
- 哪些路径、命令、资源被允许？
- 执行前是否需要最新状态？
- 哪些操作需要批准、沙箱或拒绝？
- 哪些结果证据会回到模型？
- 成功或失败后，哪些持久状态会改变？
- 如何把本次调用和结果准确配对？

---

##### 10. 核心结论：模型请求，Harness 裁决

模型可以提出工具调用请求，但不能自动获得执行权。

真正的流程是：

> Model 发起请求 → Harness 验证与裁决 → 必要时用户审批 → 执行工具 → 限制结果 → 记录状态

工具调用只有在 Harness 裁决通过后才会执行。

**简而言之：工具不是功能入口，而是一份契约。**

文章主张 Coding Agent 的工具调用不是简单函数调用，而是模型通过生成文本请求改变环境状态的契约。Harness 需要负责 schema、路径、权限、审批、沙箱、输出边界和状态记录等裁决。

###### 知识要点
- Tool call 本质是 generated text 对真实环境状态变更的请求，需要 Harness 裁决后才能执行
- 工具契约应覆盖 schema 验证、路径安全、权限策略、审批、沙箱、输出裁剪、转录记录和状态更新
- validation 应发生在 approval 之前，避免让用户审批本就无效或危险的请求
- Tool output 会进入上下文，因此结果 bounding 是安全性和工作集准确性的一部分

###### 行动项
- 设计 Agent 工具时，为每个 tool 增加 schema、权限、路径范围、审批策略和输出限制说明

- 对文件写入类工具强制检查 fresh baseline、workspace 边界和 diff/preview 审批信息
- 限制 shell、search、read_file 等工具返回内容规模，避免污染模型上下文
