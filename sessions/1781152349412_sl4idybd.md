## 分析要点

- **核心高价值点**：将 Claude Design 输出的 HTML、CSS、React 和 data 文件纳入 Git 版本管理，用文本 diff 跟踪设计变更。
- **留存建议**：短期参考后可归档（包含较具体的 Claude Design 使用技巧和 AI 设计工作流，可作为实践参考）

**知识要点**

- 使用成熟 Design System 可以减少 AI 生成界面的随机感和不一致性
- PRD 与线框图原型结合，有助于同时兼顾 AI 可读性和交互直观性
- Claude Design 的输出结果适合进入代码仓库做版本管理
- 设计同步流程应尽量保持 Claude Design 到代码的单向流动

**行动项**

- 在 Claude Design 项目中设置默认 Design System，如 Adobe Spectrum
- 先用 PRD 和线框图确定布局与交互，再生成高保真原型
- 将 Claude Design 导出的文件纳入 Git 管理并跟踪变更
- 为项目维护 CLAUDE.md，记录反复需要遵守的设计与生成规则

**宝玉**

用好 Claude Design 的一些经验：

1\. 加上 Design System 可以有效避免设计 AI 味

比如我偏好用 Adobe Spectrum 2 Design System [https://github.com/adobe/react-spectrum…](https://github.com/adobe/react-spectrum)

设置为默认设计系统，后续就会默认使用这个设计系统，你就可以把重点放在界面布局和交互上。

2\. 不要指望一次性做个完美的版本

一开始少做一点功能，把架子搭好，然后通过左侧的聊天框，一点点调整，一点点添加功能

3\. 多用 Markup 功能去局部修改

Markup 功能可以框选特定的位置，然后评论，缺点是不能添加附件、截图

Edit 功能是给你手动调整的，选中元素左侧可以修改树形，比如调整一下字体大小

4\. 注意上下文管理  
左侧的对话框不是无限聊天的，也要做上下文管理，当新的任务就创建新的会话

5\. 用 Tweaks 去尝试不同风格、导航  
Tweaks 是一个设置面板，你可以通过它来调整应用属性，比如theme、布局、加载状态等等

另外如果你界面多，也可以通过 Tweak 添加导航，快速进入相应的界面而不必一步步点击

好的设计同步流程应该是单向的：Claude Design -&gt; Code

## 解读（1）

### 2026-06-11 04:32:29

#### 深度总结

这篇内容的核心不是 “Claude Design 怎么点按钮”，而是：**把 AI 设计工具当成一个可迭代、可管理、可版本化的设计生产系统**。

##### 核心经验

1. **先定设计系统**
   - 使用 Adobe Spectrum 2 等成熟 Design System。
   - 作用：减少 “AI 味”，让界面更统一、更专业。
   - 重点从 “好不好看” 转向 “布局、交互、信息结构”。

2. **不要一次做完**
   - AI 设计不适合一口气生成完美产品。
   - 正确方式是：先搭骨架，再逐步增改功能。

3. **局部修改优先**
   - 用 Markup 框选局部提意见。
   - 用 Edit 手动微调元素。
   - 避免每次都让 AI 重做整页。

4. **管理上下文**
   - 聊天上下文不是无限的。
   - 新任务、新阶段，最好新建会话，避免指令混乱。

5. **用 Tweaks 探索方案**
   - 可快速调整主题、布局、加载状态、导航等。
   - 适合比较不同风格和交互路径。

6. **接受随机性，多试几次**
   - LLM 有 “抽卡” 属性。
   - 同一需求，多生成几版，往往会有明显差异。

7. **先线框，后高保真**
   - 没想清楚布局和交互时，先做线框图。
   - 线框满意后，再进入高精度原型。

8. **PRD + 线框图结合**
   - PRD 适合 AI 理解、版本管理。
   - 线框图适合人类直观看布局和交互。
   - 推荐流程：
     1. 先手写粗 PRD；
     2. 生成线框原型；
     3. 调整满意后，让 AI 反向生成详细 PRD。

9. **设计也要版本管理**
   - Claude Design 输出 HTML / CSS / React /data.js。
   - 都是文本格式，适合放进 Git。
   - Git diff 能清楚记录设计变化，也方便 AI 理解变更。

10. **把 Claude Design 当唯一设计源**
    - 设计变更应先改设计稿，再改代码。
    - 推荐单向流程：  
      **Claude Design → Code**

11. **使用 CLAUDE.md**
    - 把长期规则、偏好、约束写进去。
    - 减少重复提示，提高一致性。

#### 深入浅出解读

这套方法可以概括成一句话：

> **不要把 Claude Design 当 “神笔马良”，而要当 “设计协作者 + 原型工程师”。**

很多人用不好 AI 设计工具，原因是期待错了：

- 以为输入一句话，就能得到完美设计；
- 以为 AI 会自动理解产品逻辑；
- 以为设计稿和代码可以分开随便改；
- 以为一次生成就应该能上线。

宝玉的经验正好相反：

##### 1. 先给 AI 规矩

Design System 就像 “装修风格手册”。

没有它，AI 会自由发挥，结果容易花哨、混乱、有模板感。  
有了它，AI 就会在统一颜色、组件、间距、字体规范下工作。

这不是限制 AI，而是**让 AI 在正确范围内发挥**。

##### 2. 先做粗，再做细

线框图解决的是：

- 页面有哪些区域；
- 信息怎么摆；
- 用户怎么操作；
- 路径是否顺畅。

高保真解决的是：

- 颜色；
- 字体；
- 质感；
- 细节；
- 状态。

如果一开始就追求高保真，很容易在细节里打转，反而没想清楚产品结构。

##### 3. 文档和原型要互相校验

PRD 是 “说清楚”，线框是 “看清楚”。

只写 PRD，容易抽象；  
只做原型，容易缺逻辑。

最好是：

> 人写粗需求 → AI 做线框 → 人调整交互 → AI 生成详细 PRD → 再进入高保真和开发。

这其实是一个轻量版产品设计闭环。

##### 4. 设计结果要像代码一样管理

Claude Design 的优势在于输出是代码化的设计资产。

这意味着：

- 可版本管理；
- 可 diff；
- 可回滚；
- 可让 AI 阅读；
- 可和开发流程衔接。

这点比传统 Figma 更适合 AI 协作。

---

#### 辩证思考

##### AI 设计工具的价值

它最大的价值不是替代设计师，而是降低 “从想法到可交互原型” 的成本。

过去可能要：

> 产品经理写需求 → 设计师画图 → 前端做 Demo

现在可以变成：

> 一个人写想法 → AI 生成线框 → 反复调整 → 输出可开发原型

效率会明显提高。

##### 但它也有边界

AI 擅长：

- 快速生成；
- 多方案探索；
- 套用设计系统；
- 结构化输出；
- 把原型转成文档。

AI 不擅长：

- 判断真实用户需求；
- 把握品牌气质；
- 做原创视觉语言；
- 处理复杂业务取舍；
- 对最终体验负责。

所以，AI 能加速设计流程，但不能替代人的判断。

##### 最关键的能力变化

以后重要的不是 “会不会画界面”，而是：

- 能不能写清楚需求；
- 能不能判断设计好坏；
- 能不能拆分任务；
- 能不能管理版本；
- 能不能建立统一设计源；
- 能不能让 AI 持续稳定地产出。

也就是说，设计能力会从 “手工制作” 转向 “系统编排”。

---

#### 一句话结论

**用好 Claude Design 的关键，不是让 AI 一次生成完美设计，而是用设计系统、PRD、线框图、版本管理和持续迭代，把 AI 纳入一套可控的设计生产流程。**

## 结构化（2）

### 2026-06-11 04:33:09

##### 主旨概括

宝玉分享了使用**Claude Design**做界面设计和原型的经验：不要把它当成 “一次生成完美设计” 的工具，而应结合设计系统、PRD、线框图、版本管理等方法，逐步迭代出可用设计。核心思路是：**先搭框架、再细化交互，最后用版本管理保证设计与代码同步。**

---

##### 1. 使用 Design System，减少 “AI 味”

- 给 Claude Design 配置默认的**Design System**，可以让生成的界面更统一、更专业，避免常见的 “AI 生成感”。
- 作者偏好使用**Adobe Spectrum 2 Design System**。
- 设置为默认设计系统后，后续设计会自动沿用这套规范，用户就可以把重点放在：
  - 页面布局
  - 交互流程
  - 功能组织

> 相关链接：  
> [Adobe React Spectrum](https://github.com/adobe/react-spectrum)

---

##### 2. 不要期待一次生成完美版本

- 使用 Claude Design 时，不要一开始就要求它完成所有功能。
- 更好的方式是：
  1. 先做少量核心功能；
  2. 搭好整体页面架子；
  3. 再通过左侧聊天框逐步调整；
  4. 一点点补充功能和细节。

- 这种方式更适合 AI 协作，因为设计本身需要反复试错和迭代。

---

##### 3. 多用 Markup 和 Edit 做局部修改

- **Markup 功能**适合局部修改：
  - 可以框选界面中的某个区域；
  - 然后直接评论修改意见；
  - 适合指出 “这里不对”“这里要改成什么样”。

- Markup 的缺点：
  - 不能添加附件；
  - 不能上传截图。

- **Edit 功能**适合手动微调：
  - 选中元素后，可以在左侧修改树形结构；
  - 比如调整字体大小、组件层级等。

---

##### 4. 注意上下文管理

- 左侧聊天框不是无限上下文，不能一直在一个会话里无限聊。
- 当任务发生变化，或者进入新的设计阶段时，建议新建会话。
- 这样可以避免上下文过长导致 AI 理解混乱。

---

##### 5. 用 Tweaks 尝试风格、布局和导航

- **Tweaks**是一个设置面板，可以用来快速调整应用属性，例如：
  - theme 主题；
  - 页面布局；
  - 加载状态；
  - 其他界面状态。

- 如果界面很多，也可以通过 Tweaks 添加导航。
- 好处是可以快速进入指定页面，不用每次都一步步点击过去。

---

##### 6. 好设计也需要 “抽卡”

- LLM 有随机性，设计结果也有随机性。
- 就像 AI 出图一样，不一定第一次就满意。
- 如果效果不好，可以多生成几次、多试几个方向。

> 简单理解：  
> Claude Design 不是每次都稳定产出最佳结果，必要时要多 “抽” 几版再挑。

---

##### 7. 先做线框草图，再做高精度原型

- 如果还没想清楚布局和交互，不要急着做精细设计。
- 推荐先选择**线框草图**，反复确认：
  - 页面结构；
  - 信息层级；
  - 用户操作路径；
  - 交互方式。

- 线框图满意后，再新建一个高精度交互原型项目继续细化。

###### 从线框草图过渡到高精度原型的方法

1. **直接把之前项目链接发给 Claude Design**
   - 让它基于已有草图继续实现。

2. **让 Claude Design 根据已有设计写详细 PRD**
   - Claude Design 写需求文档的能力较强；
   - 生成后可以人工补充和修改；
   - 修改文档通常比直接在 Claude Design 里调界面更方便；
   - 最后再把 PRD 作为附件发给 Claude Design 进行二次创作。

---

##### 8. PRD 和线框图最好搭配使用

作者认为，**PRD 和线框图各有优势，最好结合起来。**

###### PRD 的优势

- 是文本形式，对 AI 很友好；
- 方便版本管理；
- 适合作为讨论和开发参考。

###### PRD 的不足

- 不够直观；
- 很难直接看到界面最终长什么样。

###### 线框图原型的优势

- 能看到布局和交互；
- 可以直接点击体验；
- 调整交互流程更方便。

###### 推荐流程

1. **先手写 PRD**
   - 不需要格式特别规范；
   - 想到哪里写到哪里；
   - 也可以配合 Chat、Cowork 等工具整理。

2. **基于手写 PRD 生成线框图原型**
   - 然后反复调整；
   - 直到布局和交互满意。

3. **生成最终 PRD**
   - 把确认好的线框图原型和原始 PRD 一起交给 AI；
   - 让 AI 写成详细 PRD；
   - 方便后续版本管理、团队讨论和开发实现。

---

##### 9. 设计结果要做版本管理

- Claude Design 交付的是文本化代码结果，包括：
  - HTML；
  - CSS；
  - React；
  - `data.js`。

- 这些文件对 AI 和开发都很友好：
  - CSS 可以看清颜色系统、尺寸规范；
  - React 可以看清组件结构；
  - `data.js`可以看清数据结构。

- 作者认为这比 Figma 对 AI 更友好，尤其是`data.jsx/data.js`，因为一般设计工具不会提供这种结构化数据，但开发很需要。

###### 作者的做法

- 每次从 Claude Design 下载 zip；
- 本地解压后放入项目；
- 替换旧版本；
- 用 Git 管理设计变更；
- 通过`git diff`可以清楚看到设计稿改了什么。

---

##### 10. 把 Claude Design 当作唯一设计源

- 开发时临时调整界面很常见，但作者建议：
  - 一定要先改 Claude Design 里的设计稿；
  - 再改代码。

- 如果临时先改了代码，也要及时同步回设计稿。
- 否则时间久了，设计稿和代码会越来越不一致。

###### 推荐同步流程

```text
Claude Design -> Code
```

也就是说，设计应该单向流向代码，而不是两边随意改。

---

##### 11. 使用 CLAUDE.md 保存长期规则

- Claude Design 支持`CLAUDE.md`文件。
- 可以通过左侧聊天窗口初始化这个文件。
- 适合把一些需要反复提醒 Claude 的规则写进去，例如：
  - 设计规范；
  - 命名习惯；
  - 组件使用要求；
  - 不希望出现的设计风格。

- 这和在 Claude Code 里使用`CLAUDE.md`类似，可以减少重复说明。

---

##### 总结

使用 Claude Design 的关键不是 “一句话生成完美设计”，而是建立一套稳定工作流：**设计系统定风格，PRD 定需求，线框图定布局，Markup/Edit 做局部调整，Tweaks 试风格，Git 管版本，CLAUDE.md 固化规则。**  
把 Claude Design 当成设计源头，并让设计持续同步到代码，才能更好地发挥它在产品设计和开发协作中的价值。

##### 主旨概括

这篇内容总结了宝玉使用 **Claude Design** 的一系列经验：核心是把它当作可迭代的设计工具，而不是一次性生成完美设计的工具。通过设计系统、线框图、PRD、版本管理等方法，可以减少“AI 味”，提高设计质量和开发衔接效率。

---

##### 1. 使用 Design System，减少“AI 味”

- Claude Design 生成的界面如果没有约束，容易显得模板化、缺少专业感。
- 建议提前指定一个成熟的设计系统，让 AI 按统一规范生成界面。
- 作者偏好使用 **Adobe Spectrum 2 Design System**，并将其设置为默认设计系统。
- 这样后续设计会自动遵循该系统，用户就可以把注意力放在：
  - 页面布局
  - 交互流程
  - 功能结构

> 例子：使用 Adobe React Spectrum 作为默认设计系统后，按钮、颜色、间距、组件风格会更统一。

链接：&lt;https://github.com/adobe/react-spectrum>

---

##### 2. 不要期待一次生成完美版本

- 使用 Claude Design 时，不要一开始就要求它做出完整、复杂、完美的产品。
- 更推荐的方式是：
  1. 先做少量核心功能；
  2. 搭好整体架子；
  3. 再通过左侧聊天框逐步调整；
  4. 一点点增加功能。

- 这种迭代式方法更容易控制结果，也更符合设计实际流程。

---

##### 3. 多用 Markup 和 Edit 做局部修改

- **Markup 功能**适合对页面局部进行反馈和修改。
  - 可以框选某个位置；
  - 然后添加评论，让 Claude Design 修改。
- 但 Markup 也有局限：
  - 不能添加附件；
  - 不能上传截图。

- **Edit 功能**更偏向手动调整。
  - 选中元素后，可以在左侧修改树形结构；
  - 例如调整字体大小、组件层级等。

> 简单理解：Markup 适合“告诉 AI 这里怎么改”，Edit 适合“自己动手微调”。

---

##### 4. 注意上下文管理

- 左侧聊天框并不是无限上下文。
- 如果一直在同一个会话里反复聊，可能会导致上下文混乱或记忆失效。
- 作者建议：
  - 同一类任务可以放在同一个会话；
  - 新任务最好创建新会话；
  - 不要把太多无关需求堆在一个聊天上下文里。

---

##### 5. 使用 Tweaks 尝试不同风格和导航

- **Tweaks** 是 Claude Design 中的一个设置面板。
- 可以用它快速调整应用属性，例如：
  - theme 主题；
  - 页面布局；
  - 加载状态；
  - 视觉风格。

- 如果界面较多，也可以通过 Tweaks 添加导航。
- 这样可以快速跳转到对应页面，不必一步步点击进入。

> 适合用于快速比较不同设计方案，比如深色/浅色主题、不同布局结构等。

---

##### 6. 好设计也需要“抽卡”

- LLM 具有随机性，Claude Design 的设计结果也一样。
- 同一个需求，多生成几次，可能会得到质量差异很大的结果。
- 作者把这个过程类比为“抽卡”或“AI 出图”：
  - 不要只看第一次结果；
  - 多尝试几轮；
  - 从多个版本里选更好的方向继续迭代。

---

##### 7. 先做线框草图，再做高精度交互

- 如果还没想清楚布局和交互，不建议直接做高精度设计。
- 更好的方式是先做 **线框草图**：
  - 确定页面结构；
  - 梳理核心交互；
  - 反复调整信息层级和布局。

- 等线框图满意后，再新建一个高精度交互原型项目继续细化。

可用的衔接方式包括：

1. **直接把之前项目链接发给 Claude Design**
   - 让它基于原来的线框草图继续实现。

2. **让 Claude Design 基于已有设计生成详细 PRD**
   - Claude Design 写 PRD 的能力较强；
   - 生成后，人可以再补充和修改；
   - 修改文档比直接在设计界面里反复调整更方便；
   - 最后再把 PRD 作为附件发给 Claude Design 进行二次创作。

---

##### 8. PRD 和线框图最好搭配使用

作者认为，**PRD 和线框图原型各有优势，最好结合使用**。

###### PRD 的优点

- 文本形式，AI 更容易理解；
- 方便管理版本；
- 适合用于讨论、评审和开发参考。

###### PRD 的缺点

- 不够直观；
- 很难直接看到页面最终长什么样。

###### 线框图原型的优点

- 能直观看到布局和交互；
- 可以直接体验页面流程；
- 调整交互和结构更方便。

###### 作者推荐流程

1. **先手写 PRD**
   - 不必追求格式；
   - 想到什么写什么；
   - 也可以配合 Chat、Cowork 等工具一起整理。

2. **基于手写 PRD 生成线框图原型**
   - 然后反复调整；
   - 直到布局和交互满意。

3. **生成最终 PRD**
   - 基于确认后的线框图，加上原始 PRD；
   - 让 AI 写一份更详细、结构化的 PRD；
   - 用于版本管理、团队讨论和开发参考。

---

##### 9. 设计结果要做版本管理

- Claude Design 交付的结果通常是：
  - HTML
  - CSS
  - React
  - data.js / data.jsx

- 这些文件对 AI 和开发都很友好：
  - CSS 可以清楚看到颜色系统、尺寸规范；
  - React 可以看到组件结构；
  - data.js / data.jsx 可以看到数据结构。

- 相比 Figma，这种文本格式更适合 AI 读取和理解。
- 作者特别提到，`data.jsx` 是一般设计 App 不会提供的，但对开发很重要。

###### 作者的做法

- 每次从 Claude Design 下载 zip；
- 本地解压；
- 放到项目中替换旧版本；
- 用 Git 做版本管理；
- 通过 `git diff` 清楚查看设计稿改了什么。

---

##### 10. 把 Claude Design 当作唯一设计源

- 开发过程中临时调整设计很常见，但作者强调：
  - 应该先改设计稿；
  - 再改代码。

- 如果先在代码里改，也要及时同步回 Claude Design。
- 否则时间一长，设计稿和代码就会逐渐脱节。

###### 推荐流程

```text
Claude Design -> Code
```

也就是说，设计同步应该尽量保持单向流动：从 Claude Design 到代码，而不是两边各改各的。

---

##### 11. 使用 CLAUDE.md 固化规则

- Claude Design 支持 `CLAUDE.md` 文件。
- 可以通过左侧聊天窗口初始化 `CLAUDE.md`。
- 适合把一些需要反复提醒 Claude 的规则写进去。

例如：

- 默认使用某个设计系统；
- 保持某种视觉风格；
- 页面间距规则；
- 组件命名规范；
- 不要使用某类设计元素。

这和在 Claude Code 中使用 `CLAUDE.md` 的方式类似，可以帮助保持长期项目的一致性。

---

##### 总结

宝玉的核心经验是：**Claude Design 更适合“持续迭代 + 结构化管理”，而不是一次性生成最终稿**。实际使用时，应结合 Design System、线框图、PRD、Tweaks、Markup、Git 和 CLAUDE.md，把 AI 设计流程变成一个可控、可复用、可追踪的工作流。

#### 实例：用 Claude Design 设计一个「AI 写作任务管理后台」

假设我们要做一个 Web 产品后台，名字叫**WriteFlow**，用于管理 AI 写作任务。

核心功能包括：

- 查看写作任务列表
- 创建新的写作任务
- 查看任务详情和生成进度
- 管理不同文章状态：草稿中、生成中、待审核、已发布
- 支持深色 / 浅色主题
- 后续交付给前端开发实现

下面是基于这个实例，使用 Claude Design 的一套最佳实践。

---

##### 一、先确定设计系统，避免 “AI 味”

在开始设计前，不要直接让 Claude Design 自由发挥 UI 风格，而是先指定一个成熟的 Design System。

例如本项目使用：

> Adobe Spectrum 2 Design System

这样做的好处是：

- 组件风格统一
- 间距、颜色、按钮、表单更规范
- 避免出现常见的 “AI 生成 UI 味”
- 后续开发时更容易拆成真实组件

###### 推荐操作

在 Claude Design 中创建或设置默认 Design System：

```text
请使用 Adobe Spectrum 2 Design System 作为默认设计系统。

设计风格要求：
- 使用 Spectrum 风格的按钮、输入框、表格、卡片和导航
- 保持专业、克制、清晰的信息层级
- 不要使用过度渐变、玻璃拟态、夸张阴影
- 优先保证后台管理系统的可读性和操作效率
```

---

##### 二、不要一开始就做完整高保真版本

不要上来就说：

```text
帮我设计一个完整的 AI 写作后台系统，包含所有功能。
```

这样很容易导致：

- 页面太复杂
- 交互不稳定
- 信息架构混乱
- 修改成本变高

更好的方式是先做一个最小版本。

---

##### 三、第一轮只做线框图，先确认布局和交互

###### 第一版目标

先只做 3 个核心页面：

1. 任务列表页
2. 创建任务页
3. 任务详情页

先用线框图，不要急着做高保真。

###### 示例 Prompt

```text
请为一个名为 WriteFlow 的 AI 写作任务管理后台设计线框图原型。

目标用户：
- 内容运营人员
- 编辑
- 市场团队成员

核心页面：
1. 任务列表页
   - 显示任务标题、类型、状态、创建时间、负责人、操作按钮
   - 支持按状态筛选
   - 支持搜索任务标题
   - 有 “新建任务” 按钮

2. 新建任务页
   - 输入文章标题
   - 选择文章类型：博客、社媒文案、产品介绍、邮件
   - 输入关键词
   - 选择语气风格
   - 提交生成任务

3. 任务详情页
   - 展示任务基本信息
   - 展示生成进度
   - 展示生成结果预览
   - 支持重新生成、复制内容、提交审核

要求：
- 先做线框图，不要做高保真视觉设计
- 重点确认信息架构、布局和交互流程
- 使用清晰的左侧导航
- 页面之间可以点击跳转
```

---

##### 四、通过聊天框一点点迭代，而不是一次性改完

第一版出来后，不要要求它重做全部页面，而是局部迭代。

例如发现任务列表页信息太拥挤，可以这样改：

```text
请只调整任务列表页。

当前问题：
- 表格信息有点多
- 状态不够醒目
- 任务标题和文章类型的层级不明显

调整要求：
- 将状态改成彩色 Badge
- 任务标题加粗
- 文章类型作为标题下方的辅助信息
- 保留搜索、筛选和新建任务按钮
- 不要改动其他页面
```

这样做的优势是：

- 变更可控
- 不容易破坏已有结构
- 更接近真实产品设计流程

---

##### 五、善用 Markup 做局部修改

当某个页面大体满意，但局部有问题时，不要在聊天框笼统描述。

例如你觉得 “新建任务页” 的表单布局太松散，可以使用 Markup 框选对应区域，然后评论：

```text
这个表单区域请改成两列布局。

左侧放：
- 文章标题
- 文章类型
- 关键词

右侧放：
- 语气风格
- 目标字数
- 参考资料

底部保留一个主按钮：开始生成。
```

Markup 适合处理：

- 某个卡片布局
- 某个按钮位置
- 某个表格区域
- 某个导航区
- 某段文案或状态展示

不适合处理：

- 全局架构重构
- 多页面统一调整
- 需要附图解释的复杂改动

##### 六、用 Tweaks 快速测试不同状态和风格

后台产品通常不只一种状态，例如：

- 浅色主题
- 深色主题
- 空数据状态
- 加载中状态
- 错误状态
- 不同用户角色
- 不同页面入口

可以通过 Tweaks 添加这些变量。

###### 推荐 Tweaks 配置

```text
请添加以下 Tweaks：

1. theme
   - light
   - dark

2. taskStatusView
   - all
   - generating
   - review
   - published
   - empty

3. userRole
   - admin
   - editor
   - viewer

4. currentPage
   - taskList
   - createTask
   - taskDetail
   - settings
```

这样你可以快速查看：

- 深色模式下表格是否可读
- 空任务状态是否合理
- Viewer 用户是否应该隐藏创建按钮
- 不同页面是否能快速切换

##### 七、线框图满意后，再生成高保真版本

不要在线框图阶段就纠结颜色、阴影、圆角。

等到布局和交互确认后，再进入高保真设计。

###### 示例 Prompt

```text
基于当前已经确认的线框图，请生成高保真交互原型。

要求：
- 使用 Adobe Spectrum 2 Design System
- 保持企业级 SaaS 后台风格
- 信息层级清晰，避免花哨视觉
- 使用浅色主题为默认主题
- 保留深色主题 Tweak
- 表格、筛选器、状态 Badge、表单控件都应符合 Spectrum 风格
- 不要新增核心功能，只提升视觉完成度
```

##### 八、让 Claude Design 反向生成 PRD

高保真原型出来后，不要只拿设计图去开发。

更好的方式是让 Claude Design 根据当前设计生成一份详细 PRD。

###### 示例 Prompt

```text
请基于当前 WriteFlow 的设计原型，生成一份详细 PRD。

PRD 需要包含：
1. 产品背景
2. 目标用户
3. 核心使用场景
4. 信息架构
5. 页面清单
6. 每个页面的功能说明
7. 表单字段定义
8. 表格字段定义
9. 状态流转规则
10. 权限规则
11. 空状态、加载状态、错误状态
12. 交互说明
13. 前端数据结构建议
14. 后续可扩展功能

请使用 Markdown 格式输出。
```

这样得到的 PRD 可以用于：

- 和团队讨论
- 交给开发评估
- 作为需求文档版本管理
- 作为下一轮 Claude Design 输入材料

---

##### 九、PRD 和线框图要配合使用

推荐流程是：

```text
手写粗略 PRD
    ↓
生成线框图原型
    ↓
调整布局和交互
    ↓
生成高保真原型
    ↓
反向生成详细 PRD
    ↓
人工修订 PRD
    ↓
进入开发
```

不要只依赖文字 PRD，也不要只依赖原型。

二者的优劣如下：

| 类型 | 优点 | 缺点 |
|---|---|---|
| PRD | AI 友好，便于版本管理，适合描述规则 | 不直观 |
| 线框图 | 直观看到布局和交互 | 不适合管理复杂规则 |
| 高保真原型 | 接近最终体验 | 太早做容易浪费时间 |

最佳实践是：

> PRD 管规则，原型管体验。

##### 十、做好上下文管理，不要无限聊天

Claude Design 左侧对话不是无限上下文。

如果一直在同一个会话里反复说：

- 改任务列表
- 改创建页
- 改权限
- 改主题
- 改数据结构
- 改移动端
- 改 PRD

很容易导致上下文混乱。

###### 推荐做法

按阶段创建不同会话：

| 会话 | 用途 |
|---|---|
| 会话 1 | 线框图探索 |
| 会话 2 | 高保真视觉设计 |
| 会话 3 | PRD 生成 |
| 会话 4 | 细节修复 |
| 会话 5 | 开发交付整理 |

每个新会话开始时，给它明确上下文：

```text
这是 WriteFlow 项目的高保真设计阶段。

已有结论：
- 使用 Adobe Spectrum 2 Design System
- 页面包括任务列表、新建任务、任务详情
- 默认浅色主题
- 支持深色主题
- 左侧导航结构已确认
- 当前不要新增功能，只优化视觉细节
```

这样可以减少反复提示，也能提升输出稳定性。

Claude Design 交付的是：

- HTML
- CSS
- React
- data.js/data.jsx

这些都是文本文件，非常适合放进 Git。

```text
│       └── writeflow-prd-v2.md
├── src/
│   ├── components/

```

每次从 Claude Design 下载 zip 后：

```bash
git checkout -b design/writeflow-v2

git add .

```

这样你可以清楚看到：

哪些地方发生了变化：

- CSS 颜色变化
- React 组件结构变化
- 表格字段变化
- data.js 数据结构变化
- 页面状态变化

这对 AI 和开发都很友好。

##### 十三、把 Claude Design 当作唯一设计源

开发过程中，一定会出现临时调整，例如：

- 前端觉得按钮太大
- 真实数据比设计稿更长
- 某个状态缺失
- 表格字段需要新增
- 权限逻辑需要调整

不要只在代码里改。

正确流程应该是：

```text
先更新 Claude Design
    ↓
再导出设计结果
    ↓
提交 Git
    ↓
再同步到代码
```

也就是：

```text
Claude Design → Code
```

不要变成：

```text
Claude Design ↔ Code
```

否则时间一长会出现：

- 设计稿和代码不一致
- PRD 和实际实现不一致
- 团队不知道哪个版本才是准的
- 后续 AI 也无法准确理解当前产品状态

---

##### 十四、需要 “抽卡”，但要有方法地抽

LLM 有随机性，设计也有随机性。

同一个 Prompt，多生成几次结果可能不一样。

但不要盲目抽卡，而是有标准地比较。

###### 比较标准

| 维度 | 判断问题 |
|---|---|
| 信息架构 | 用户能否快速找到核心功能？ |
| 操作效率 | 新建任务是否足够顺畅？ |
| 可读性 | 表格是否清楚？状态是否醒目？ |
| 一致性 | 是否符合 Spectrum 设计系统？ |
| 可开发性 | 组件结构是否容易实现？ |
| 扩展性 | 后续增加团队、模板、审核流是否方便？ |

可以生成 3 个版本：

```text
请基于当前 PRD，为 WriteFlow 生成 3 个不同的信息架构方案。

方案 A：偏传统后台，左侧导航 + 表格为主
方案 B：偏工作台，首页突出任务概览和快捷操作
方案 C：偏内容生产流水线，突出状态流转和看板

每个方案都需要可点击的线框图。
```

然后选择一个最适合的方向继续深入。

##### 十五、推荐完整工作流总结

```text
1. 写一个粗略 PRD
   ↓
2. 指定 Design System，例如 Adobe Spectrum 2
   ↓
3. 生成低保真线框图
   ↓
4. 用聊天框逐步调整整体结构
   ↓
5. 用 Markup 局部修改页面细节
   ↓
6. 用 Tweaks 测试主题、状态、角色和页面跳转
   ↓
7. 布局和交互满意后，再生成高保真原型
   ↓
8. 让 Claude Design 根据原型生成详细 PRD
   ↓
9. 人工修订 PRD
   ↓
10. 下载 HTML / CSS / React /data.js
   ↓
11. 提交到 Git 做版本管理
   ↓
12. 开发时保持 Claude Design → Code 的单向同步
```

##### 一句话总结

对于 WriteFlow 这种后台产品，使用 Claude Design 的最佳方式不是 “一句话生成完整设计”，而是：

> 用 Design System 控制风格，用线框图确认结构，用 Markup 和 Tweaks 精修体验，用 PRD 和 Git 管理版本，最后保持 Claude Design 到代码的单向同步。
