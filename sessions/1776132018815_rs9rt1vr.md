## 正文

**ℏεsam**

这是我创建的一个工具，它能为你的代码库（认证、数据库、API）的不同部分提供 4-10 个专家级 Claude 代码，这些代码拥有自己的记忆、任务和技能。它们可以：

&gt; 生成大量的其他 Claude 代码,  
&gt; 相互交谈  
&gt; 管理并行工作

开源，面向所有感兴趣的人。

它叫 OctoGent，是我出于对 Agent Engineering 仪表盘可能是什么样子的好奇而制作的一个原型。

OctoGent 只是一个在本地运行的轻量级代理编排仪表板，它围绕 Claude Code 构建，而非将其隐藏在抽象概念之下。

使用 OctoGent，你可以拥有：  
&gt; 专业的上下文和技能，针对代码库的多个部分。（我称它们为触手）  
&gt; 每个触须的任务列表，由您或 Claude 定义。  
&gt; 一个用于 Claude Code 的命令行界面，用于创建其他 Claude Codes，提示它们并检查它们的工作。  
&gt; 你可以控制这些孩子并查看他们的作品。  
&gt; 所有内容在图形画布中可见，因此您可以从上帝视角了解正在发生的情况。  
Claude 使用限制始终可见，这样你就不会感到意外。  
一个类似 GitHub 的 Claude 使用情况热力图  
&gt; 您与 Claude Code 的历史对话列表，您可以在其中进行搜索，或导出到其他地方使用

这非常简单明了  
在数据库触须下生成一个新的 Claude 代码  
它读取所有它写下来的记忆和上下文  
读取待办事项列表  
并且开始处理任务，

基本上，你使用 Claude Code 的方式，只是多了更多的功能。

这仍然处于早期阶段，属于实验性内容，所以如果你遇到任何问题，请提交到仓库。你也可以分叉它并随意修改。

有关于如何将 Claude Code 用作协调代理、如何使其使用其他代理、与它们通信、如何使用其钩子、向 Claude 注入提示词，以及使用它所暴露的所有功能的文档。

## 解读（1）

#### 内容总结

这条内容介绍了一个开源工具 `OctoGent`。  
它的核心思路是：把一个代码库拆成多个“专业代理”（比如认证、数据库、API），每个代理都有自己的记忆、任务和技能，并且都围绕 `Claude Code` 工作。

这个工具可以做到：

- 为代码库不同部分创建 4~10 个“专家代理”
- 这些代理可以继续生成更多代理
- 代理之间可以互相沟通、协作
- 支持并行处理任务
- 提供可视化仪表盘，能看到所有代理的状态和工作内容
- 显示 Claude 使用额度、历史对话、任务列表等信息

作者强调：`OctoGent` 不是把 Claude Code 封装得更抽象，而是让你更直接地“调度和观察”它。  
目前它还是一个早期实验性原型，但已经开源，任何人都可以使用、修改、提交问题。

---

#### 通俗解读

##### 这东西本质上是什么？

你可以把它理解成一个“AI 开发团队控制台”。

平时你用一个 AI 写代码，像是在和一个全能但单线程的助手合作。  
而 `OctoGent` 想做的是：

- 让一个 AI 专门管数据库
- 一个 AI 专门管认证
- 一个 AI 专门管 API
- 甚至再派出更多小助手去做子任务

最后，你像项目经理一样，在一个面板里看他们怎么分工、怎么交流、怎么推进任务。

---

##### 它为什么有吸引力？

因为大型代码库往往不是“一个脑子”就能高效处理的。

比如一个真实项目里：

- 数据库改动要考虑表结构和迁移
- API 改动要考虑协议和兼容性
- 认证改动要考虑权限和安全
- 前端改动又有自己的上下文

如果让一个 AI 一次性吃下所有上下文，容易：

- 上下文过载
- 忘记前面说过的细节
- 任务混在一起
- 改一处影响另一处

`OctoGent` 的思路就是：**按领域拆脑子**。  
每个代理只关注自己擅长的一块，效率和清晰度可能会更高。

---

##### 它和普通“AI 编程工具”有什么不同？

普通工具更像：

- 你提需求
- AI 回答
- 你继续追问
- 一轮一轮完成

而 `OctoGent` 更像：

- 你搭一个代理系统
- 给每个代理分工
- 让它们自己执行、协作、汇报
- 你从全局角度监督

也就是说，它卖点不是“更聪明的单个 AI”，而是“更像团队协作的 AI 工作流”。

---

##### 它最有价值的地方在哪？

我觉得有三点：

###### 1. 可视化
很多 Agent 系统最大的问题不是不能跑，而是**看不懂它在干嘛**。  
`OctoGent` 把代理、任务、记忆、对话、配额都放到画布里，降低了理解成本。

###### 2. 专业分工
不同代理保留各自上下文，减少彼此干扰。  
这对大型项目、多人协作、复杂重构都很有意义。

###### 3. 保留对 Claude Code 的直接控制
它不是完全替你“黑盒自动化”，而是给你一个更强的操控台。  
这点很重要，因为开发者通常不想失去过程可见性。

---

##### 它可能存在的问题

虽然想法很强，但也有明显挑战：

- **代理越多，协调越复杂**：分工清晰不代表结果一定一致
- **上下文隔离可能带来信息断层**：认证代理不知道账单代理的限制，未必总是好事
- **并行工作容易冲突**：多人改同一代码区域时，合并和一致性会变难
- **维护成本高**：代理的记忆、任务、提示词设计，本身就需要管理
- **实验性阶段不稳定**：早期工具常见问题是好看、好玩，但未必稳定耐用

所以它更像“前沿实验平台”，而不是已经成熟的工业标准方案。

---

#### 我的意见

我认为这类工具方向是对的，而且很有前景。

原因很简单：  
未来 AI 编程大概率不会只是“一个聊天框 + 一个模型”，而会走向：

- 多代理分工
- 长期记忆
- 可视化编排
- 人类做监督和仲裁

`OctoGent` 正是在探索这条路。

但现阶段，我会把它看成：

> 一个很值得关注和尝试的实验原型，而不是所有团队都能立刻落地的生产工具。

如果你是下面这几类人，值得试：

- 喜欢折腾 Agent workflow 的开发者
- 想研究多代理协作怎么做的人
- 管理复杂代码库、希望让 AI 按模块分工的人

如果你只是想“赶紧写点代码”，那它现在可能还偏重，学习和管理成本不低。

一句话评价：

> `OctoGent` 展示的不是“AI 会不会写代码”，而是“AI 团队怎么一起写代码”。这个方向很有想象力，但离成熟还需要时间。
