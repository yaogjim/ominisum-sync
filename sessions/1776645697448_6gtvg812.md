## 正文

💡

****TL;DR:**** 我们发布了 `deepagents` 和 `deepagentsjs` 的新次要版本，新增了异步（非阻塞）子代理、扩展的多模态文件系统支持以及更多改进。

查看 [更新日志](https://docs.langchain.com/oss/python/releases/changelog?ref=blog.langchain.com) 了解详情。

#### Async subagents

Deep Agents 现在可以将工作委派给在后台运行的远程代理。与现有的内联 [subagents](https://docs.langchain.com/oss/python/deepagents/subagents?ref=blog.langchain.com) 不同，这些内联子代理会阻塞主代理直到它们完成，而异步子代理则会立即返回一个任务 ID，并在远程服务器上独立执行。

请查看 [Deep Agents docs](https://docs.langchain.com/oss/python/deepagents/async-subagents?ref=blog.langchain.com) 以获取更多详细信息。

##### Motivation

内联子代理对于简短、专注的任务很有效，但在运行时会阻塞主管的执行循环。对于耗时几分钟而非几秒的工作——深度研究、大规模代码分析、多步骤数据管道——这就会成为瓶颈。主管必须等到子代理返回后，才能响应用户或推进其他工作。当大多数代理和子代理的生命周期较短时，这一问题并不严重，但随着可处理的任务长度增加，阻塞问题变得更加严重。

异步子代理消除了这一限制。主管可以并行启动多个子代理，继续与用户对话，并在结果可用时收集它们。与内联子代理不同，异步子代理也是有状态的：它们在交互过程中维护自己的线程，因此主管可以发送后续指令或在任务中途纠正方向。

这也为异构部署打开了大门，在这种部署中，轻量级编排器会将任务委托给运行在不同硬件上、使用不同模型或维护各自工具集的专门远程代理。

##### Usage

The `subagents` 参数已被扩大，以接受一个 `AsyncSubAgent` 规范，该规范指向一个远程代理：

```python
from deepagents import AsyncSubAgent, create_deep_agent

agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    subagents=[
        AsyncSubAgent(
            name="researcher",
            description="Performs deep research on a topic.",
            url="<https://my-agent-server.dev>",
            graph_id="research_agent",
        ),
    ],
)
```

`AsyncSubAgent` 规范可以与现有 `SubAgent` 和 `CompiledSubAgent` 规范自由混合—— `create_deep_agent` 会根据类型将每个规范路由到相应的中间件。

配置完成后，主代理获得五个用于管理后台工作的工具：

Tool Purpose

`start_async_task` 在远程代理上启动任务。立即返回一个任务 ID。

`check_async_task` 轮询任务的状态，并在完成时获取其结果。

`update_async_task` 给一个正在运行的任务发送后续指令

`cancel_async_task` Cancel a running task.

`list_async_tasks` 列出所有已跟踪的任务及其当前状态。

交互模型为 fire-and-forget：主代理发起任务后，继续工作或与用户对话，在需要时检查结果。多个异步子代理可以并发运行。

##### Server protocol

任何实现了 [代理协议](https://github.com/langchain-ai/agent-protocol?ref=blog.langchain.com) 的远程代理都是异步子代理的有效目标。这意味着你可以将 Deep Agent 指向任何符合代理协议的服务器，包括任何使用 [LangSmith 部署的](https://docs.langchain.com/langsmith/deployment?ref=blog.langchain.com) 代理、使用 [服务器存根](https://github.com/langchain-ai/agent-protocol/tree/main/server?ref=blog.langchain.com) 的自定义 FastAPI 服务，或任何其他实现。我们为 Deep Agents 添加了针对 [Python](https://github.com/langchain-ai/deepagents/tree/main/examples/async-subagent-server?ref=blog.langchain.com) 和 [JS](https://github.com/langchain-ai/deepagentsjs/tree/main/examples/async-subagent-server?ref=blog.langchain.com) 的示例服务器实现。

如果省略 `url` 字段，Deep Agents 将使用 ASGI 传输与子代理进行通信。这允许主管代理和子代理共同部署并在同一进程中进行通信。

要了解完整的使用指南——包括部署配置、跟踪、故障排除和参考实现——请参阅 [异步子代理文档](https://docs.langchain.com/oss/python/deepagents/async-subagents?ref=blog.langchain.com) 。

##### Why Agent Protocol

异步子代理需要一个标准的服务器协议，即任何远程代理都能实现的协议，无论其部署方式或位置如何。在确定使用 Agent Protocol 之前，我们研究了其他可用的选项。

[**ACP**](https://agentcommunicationprotocol.dev/introduction/welcome?ref=blog.langchain.com) (代理客户端协议) 专为编辑器与代理之间的通信而设计，在工具领域的采用率不断提高。对于我们的使用场景，ACP 存在两个问题。首先，它基于同步会话模型构建，客户端发送提示并等待响应，这无法很好地适配异步子代理。其次，它目前仅支持标准输入输出传输，这意味着远程代理必须作为本地子进程运行。HTTP 支持已在规划中，但尚未发布，因此目前 ACP 对于远程部署不可行。

[**A2A**](https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/?ref=blog.langchain.com) (代理间协议) 是一个更合适且技术上兼容的协议。它具备完整的 HTTP 支持和原生异步任务模型。它是一个强大的协议，旨在解决整个行业范围内广泛的代理互操作性挑战，涵盖推送/拉取订阅、代理发现和能力协商等方面。然而，由于异步子代理仍在发展中，我们优先考虑了允许更快迭代的协议。对 A2A 的支持可能会在未来版本中添加。

[代理协议](https://github.com/langchain-ai/agent-protocol?ref=blog.langchain.com) 是 LangChain 自主开发的用于服务 LLM 代理的开放规范，并且已经是 LangGraph 平台的底层协议。这在几个方面都很合适。

模型排列整齐。Agent 协议围绕线程构建并运行。你创建一个线程来保存对话上下文，启动一个运行来开始工作，并在需要结果时检查它。这直接对应于异步子代理的工作方式。这也意味着子代理在交互过程中是有状态的。当你发送任务中途更新时，远程代理会在上下文中继续处理，因为线程历史被保留，而不是从头开始。

结果是一个自然适配异步任务模型、适用于托管部署和自托管部署，并且保持足够灵活性以随功能一起演进的协议。

#### Expanded multi-modal support

Deep Agents 此前支持从其 [虚拟文件系统](https://docs.langchain.com/oss/python/deepagents/backends?ref=blog.langchain.com) 读取图像。此版本将多模态支持扩展到 PDF、音频、视频和其他文件类型。该代理使用相同的 `read_file` 工具；无需更改 API。文件类型从扩展名自动检测，内容以原生内容块的形式传递给模型，并附带相应的 MIME 类型。详情请参见 [Deep Agents 文档](https://docs.langchain.com/oss/python/deepagents/harness?ref=blog.langchain.com#supported-multimodal-file-extensions) 。

重要的是，支持哪些模态取决于底层模型。您可以通过 [模型配置文件](https://docs.langchain.com/oss/python/langchain/models?ref=blog.langchain.com#model-profiles) 以编程方式检查支持的模态——每个 LangChain 聊天模型都会暴露一个配置文件，该配置文件声明了它接受哪些输入类型。

## 通俗精炼（1）

### 2026-04-20 00:36:46

#### Deep Agents v0.5：这次升级，核心是让代理更像“团队协作”

##### 一句话总结

Deep Agents v0.5 主要做了三件事：  
1. 支持**异步子代理**，让主代理不再被长任务拖住；  
2. 扩展了**多模态文件支持**，可直接处理 PDF、音频、视频等；  
3. 通过更合适的协议设计，增强了**远程部署与多代理协作能力**。

##### 1. 最大变化：子代理从“串行打工”变成“并行协作”

过去，子代理执行任务时会阻塞主代理，主代理必须等它做完，才能继续和用户交互或处理其他事情。  
现在新增的**异步子代理**可以在后台独立运行，主代理只需发起任务、拿到任务 ID，就能继续处理别的工作。

这意味着 Deep Agents 更适合处理那些**耗时长、步骤多、需要并行推进**的任务，比如深度研究、复杂代码分析、多阶段数据处理。

##### 2. 为什么这很重要：解决长任务场景的效率瓶颈

文章的核心判断是：  
当代理能力增强后，任务不再只是几秒钟的小任务，而越来越多地变成几分钟级的复杂任务。此时，“阻塞式调用”会成为系统瓶颈。

异步子代理带来的价值主要有三点：

###### 持续响应用户
主代理不用一直等待子代理返回，可以边跑任务边和用户继续对话。

###### 支持并发
主代理可以同时启动多个子代理，让不同任务并行推进，提升整体效率。

###### 支持中途调整
异步子代理是**有状态的**，会保留自己的上下文线程，所以主代理可以在任务执行过程中追加指令、纠偏，而不是每次都从头开始。

##### 3. 产品层面的意义：从“单代理”走向“代理网络”

这次升级不只是一个功能补丁，更像是一次架构升级。  
它让 Deep Agents 开始具备“编排器 + 专业代理”的模式：

- 主代理负责统筹和用户交互
- 子代理负责具体专业任务
- 不同子代理可以运行在不同服务器、硬件、模型和工具链上

通俗讲，就是从一个“全能助手”，升级成一个“会调度专家团队的总指挥”。

##### 4. 协议选择背后的思路：先保证可落地，再谈行业标准

为了支持异步子代理，LangChain 需要一个适合远程调用的代理协议。  
他们比较了 ACP、A2A 和 Agent Protocol，最终选择了 **Agent Protocol**。

原因很现实：

- **ACP** 更适合同步、本地子进程场景，不适合远程异步任务
- **A2A** 很强大，也兼容异步，但设计更重，迭代成本更高
- **Agent Protocol** 与 Deep Agents 当前的线程、任务运行方式天然匹配，且便于快速演进

这反映出产品策略上的一个特点：  
**先选最适合当前场景、能快速迭代的方案，而不是一开始就追求最完整的行业标准。**

##### 5. 多模态支持也更进一步：不只是读图片了

除了代理协作机制，这次还扩展了虚拟文件系统的多模态能力。  
此前主要支持读取图片，现在进一步支持：

- PDF
- 音频
- 视频
- 其他文件类型

而且使用方式没有变，仍然通过同一个 `read_file` 工具读取。系统会自动识别文件类型，并按对应 MIME 类型传给模型。

这意味着开发者接入成本很低，但应用场景明显变宽了。

##### 6. 最值得关注的结论

Deep Agents v0.5 的真正价值，不只是“加了几个功能”，而是明确推动了代理系统从：

**单点执行工具**  
走向  
**可并发、可持续、可远程编排的多代理系统**

如果说过去的代理更像“一个聪明的助手”，那这次更新后的方向更像“一个会调度多个专家、还能边做边改的工作系统”。

##### 7. 适合谁关注

这次更新尤其值得以下人群关注：

- 在做复杂 AI Agent 产品的人
- 需要长链路、多步骤自动化流程的团队
- 希望把不同模型、工具、部署环境组合起来的开发者
- 关注多代理协作与 Agent Infra 演进的人

这篇文章释放出的信号很明确：  
LangChain 正在把 Deep Agents 从“能调用工具的代理”推进为“能组织远程专业代理协同工作的基础设施”。

短期看，这是效率提升；

### 2026-04-20 00:56:58

#### Deep Agents v0.5 核心总结

Deep Agents v0.5 这次更新的重点，是让代理能把耗时任务交给“后台异步子代理”去做，不再卡住主代理的执行。同时，它还增强了多模态文件支持，能直接处理 PDF、音频、视频等更多类型文件。

---

##### 1. 版本更新主旨

- 发布了 `deepagents` 和 `deepagentsjs` 的新次要版本。
- 主要新增三类能力：
  - 异步（非阻塞）子代理
  - 扩展的多模态文件系统支持
  - 其他若干改进
- 官方建议通过更新日志和文档查看完整细节。

---

##### 2. 为什么要引入异步子代理

###### 过去的问题：内联子代理会阻塞主代理
- 原来的内联子代理适合短、小、专注的任务。
- 但如果子任务要执行几分钟，例如：
  - 深度研究
  - 大规模代码分析
  - 多步骤数据处理流水线
- 主代理就必须一直等待，无法继续回复用户，也不能推进其他工作。

###### 新方案的价值：主代理不再“卡住”
- 异步子代理启动后会立即返回一个任务 ID。
- 任务会在远程服务器后台独立运行。
- 主代理可以同时做别的事，比如：
  - 继续和用户对话
  - 并行启动多个子代理
  - 需要时再回来查看结果

###### 一个通俗例子
- 比如主代理接到“帮我调研 3 家竞品并整理报告”的请求。
- 以前它要等研究任务做完才能继续。
- 现在它可以：
  1. 先把调研任务丢给后台子代理；
  2. 立刻告诉用户“任务已开始，我先同步已有信息”；
  3. 等后台完成后，再把结果汇总回来。

---

##### 3. 异步子代理的关键能力

###### 支持并行和持续跟进
- 多个异步子代理可以同时运行。
- 和一次性执行的内联子代理不同，异步子代理是“有状态”的：
  - 会维护自己的线程上下文
  - 主代理可以中途追加指令
  - 也可以在任务进行中纠正方向

###### 带来更灵活的部署方式
- 主代理可以作为轻量级编排器。
- 它把任务分发给不同的远程专用代理，这些代理可以：
  - 跑在不同硬件上
  - 使用不同模型
  - 拥有各自不同的工具集

这意味着系统更适合复杂、长周期、分工明确的任务场景。

---

##### 4. 如何使用异步子代理

###### 配置方式
- `subagents` 参数现在支持 `AsyncSubAgent` 规范。
- 它通过远程代理地址和 `graph_id` 指向目标代理。

文中的 Python 示例核心意思是：
- 创建主代理时，可以注册一个名为 `researcher` 的异步子代理；
- 这个子代理负责“深度研究某个主题”；
- 它运行在指定远程服务上。

###### 可以和现有子代理混用
- `AsyncSubAgent` 可以和以下类型自由混合：
  - `SubAgent`
  - `CompiledSubAgent`
- `create_deep_agent` 会根据类型自动路由到对应中间件。

这意味着老用法不用完全推翻，可以逐步接入异步能力。

---

##### 5. 主代理新增了哪些后台任务管理工具

主代理会自动获得 5 个工具来管理异步任务：

| 工具名 | 作用 |
|---|---|
| `start_async_task` | 在远程代理上启动任务，并立即返回任务 ID |
| `check_async_task` | 轮询任务状态，完成时获取结果 |
| `update_async_task` | 给正在运行的任务追加后续指令 |
| `cancel_async_task` | 取消正在运行的任务 |
| `list_async_tasks` | 查看所有已跟踪任务及当前状态 |

###### 交互模式
- 采用的是“fire-and-forget（发起后先不阻塞等待）”模式：
  - 主代理先发起任务
  - 然后继续处理其他事情
  - 需要时再检查结果

这个模式特别适合长任务和多任务并发。

##### 6. 服务端协议如何工作

###### 兼容哪些远程代理
- 任何实现了“代理协议（Agent Protocol）”的远程代理，都可以作为异步子代理目标。
- 包括：
  - 使用 LangSmith 部署的代理
  - 基于服务器存根的自定义 FastAPI 服务
  - 其他符合该协议的实现

###### Python 和 JS 都有示例
- 官方已经补充了 Python 和 JavaScript 的示例服务端实现。

###### 一个额外细节
- 如果不填写 `url`，Deep Agents 会改用 ASGI 传输与子代理通信。
- 这意味着：
  - 主代理和子代理可以一起部署
  - 可以在同一进程内通信

这对本地部署或单体服务集成很方便。

---

##### 7. 为什么选择 Agent Protocol，而不是 ACP 或 A2A

###### ACP 不适合当前需求
文章提到 ACP（代理客户端协议）有两个主要问题：

- 它基于同步会话模型：
  - 客户端发提示后等待响应
  - 不适合异步子代理这种后台任务模式
- 目前只支持标准输入输出传输：
  - 远程代理必须作为本地子进程运行
  - HTTP 支持还在规划中，尚未正式发布

所以，ACP 现在不适合远程异步部署。

###### A2A 更合适，但目前太“重”
- A2A（代理间协议）技术上是兼容的。
- 它具备：
  - 完整 HTTP 支持
  - 原生异步任务模型
- 但它目标更大，想解决更广泛的行业级代理互操作问题，比如：
  - 推送/拉取订阅
  - 代理发现
  - 能力协商

官方认为，在异步子代理仍快速演进的阶段，先采用更便于快速迭代的协议更现实。未来版本可能会支持 A2A。

###### Agent Protocol 为什么最匹配
LangChain 最终选择自家的开放规范 Agent Protocol，原因主要有三点：

- 它本来就是 LangGraph 平台的底层协议；
- 它的模型和异步子代理工作方式天然一致：
  - 线程保存上下文
  - run 启动任务
  - 轮询获取结果
- 子代理因此天然是“有状态”的：
  - 中途更新任务时，不需要从头开始
  - 因为线程历史会被保留

简单说，就是它既适合异步任务，又适合托管部署和自托管部署，还便于后续继续演进。

---

##### 8. 多模态支持有哪些扩展

###### 从“只读图片”扩展到更多文件类型
- 之前 Deep Agents 已经能从虚拟文件系统里读取图片。
- 这次进一步扩展到：
  - PDF
  - 音频
  - 视频
  - 其他文件类型

###### 使用方式没有变
- 仍然使用同一个 `read_file` 工具。
- 不需要改 API。
- 系统会根据文件扩展名自动识别类型，并把内容连同对应 MIME 类型一起传给模型。

这意味着开发者接入成本很低，但能处理的内容类型更多。

###### 但要注意模型本身是否支持
- 最终支持哪些模态，取决于底层模型能力。
- 可以通过模型配置文件以编程方式检查：
  - 每个 LangChain 聊天模型都会暴露配置文件
  - 其中会声明它接受哪些输入类型

也就是说，框架支持了，不代表所有模型都一定能处理这些文件。
