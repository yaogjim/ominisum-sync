将一个 AI 驱动的应用从简单的聊天机器人升级到功能丰富的用户界面是很困难的。手动将模型输出转换为 UI 状态是繁琐、脆弱且不可预测的。由于 LLM 状态和 UI 是独立的系统，手动桥接它们会导致问题。

如果 UI 仅仅是 AI 状态的一种功能 会怎样？如果 LLM 知道它可以使用哪些组件，并自行决定渲染什么内容呢？这就是这个想法。但将布局决策交给模型会带来真正的问题：它会遵循你的品牌标准吗？它生成的 UI 看起来会像是属于你的网站吗？它会违反无障碍指南吗？

That’s where 限制性 UI 生成 (RUG) comes in. RUG constrains the model to only the UI components you explicitly give it. Components you’ve built, tested, and QA’d. The AI decides which to use. You get dynamic, AI-driven layout without giving up ownership of what actually renders.

过去两年，我一直在开发自己的 RUG 框架。最近，这个领域出现了一些新工具。其中一个是 Vercel Labs 的 JSON 渲染（JSON Render）。

#### JSON 渲染：AI → 状态（JSON）→ UI

这是作为基础设施的 RUG。目录是你的组件契约。规范是模型的输出。注册表是你的渲染器。没有其他内容跨越边界。模型生成的状态（以 JSON 形式传递）是渲染器的唯一输入，该渲染器将该状态映射到你的组件和数据。

要快速了解它的工作原理，请查看 [playground](https://json-render.dev/playground) 。本文的第二部分将深入探讨如何从 GitHub 仓库制作一个“code roast”视频。人工智能会分析该仓库，并生成一系列简短的场景，利用真实数据幽默地批评该项目。每个仓库都会根据模型实际发现的内容，得到不同的场景序列。

#### What Makes JSON Render Tick

JSON 渲染基于三个核心原语构建：模式、目录和注册表。

一个 **schema** 定义了 UI 规范的结构和验证规则。它是一种语法，决定了如何在 JSON 中表达 UI：元素如何组织，允许哪些属性和数据绑定，交互如何定义。

一个 **目录** 定义了生成 UI 规范时可用的组件、操作和功能。如果说模式是语法，那么目录就是词汇。它确切地告诉系统（以及 AI）存在哪些 UI 元素和行为。

一个 **注册中心** 将目录连接到特定平台上的实际实现，将每个组件和操作映射到实际运行的代码。目录定义了规范中可以存在的内容。注册中心定义了渲染方式以及操作在运行时的执行方式。

#### The Contract in Code

这三个基本类型在代码中比在文字描述中更容易理解。下面展示每个在实际中的样子。

#### Define your Schema

在大多数情况下，您不需要从头编写模式。您可以使用预构建的模式。对于 React，那就是 `@json-render/react/schema` 。但是，如果您需要在整个目录中使用自定义验证规则或内置操作，您可以定义自己的：

```c
import { defineSchema } from "@json-render/core";

export const schema = defineSchema(
  (s) => ({
    spec: s.object({ ... }),
    catalog: s.object({ ... }),
  }),
  {
    builtInActions: [
      {
        name: "dismiss",
        description: "Dismiss the current UI element",
      },
    ],
  }
);
```

#### Define your Catalog

该目录定义了可用的组件及其属性类型。正如文档中所述，它是“你的用户界面的词汇表”。这是一种结构，它告诉 LLM 其输出应该是什么样子。

```c
import { defineCatalog } from '@json-render/core';
import { schema } from '@json-render/react/schema'
import { z } from 'zod';

export const catalog = defineCatalog(schema, {
  components: {
    Card: {
      props: z.object({
        title: z.string(),
        description: z.string().nullable(),
      }),
      hasChildren: true,
    },
    Metric: {
      props: z.object({
        label: z.string(),
        statePath: z.string(),
        format: z.enum(['currency', 'percent']),
      }),
    },
  },
  actions: {
    export: { params: z.object({ format: z.string() }) },
  },
});
```

#### Spec: AI generates JSON

当被提示时（在这个例子中，针对总收入），模型会返回一个这样的 JSON 对象，这个对象会告诉前端根据你注册表中的组件来渲染什么

```c
{
  "root": "dashboard",
  "elements": {
    "dashboard": {
      "type": "Card",
      "props": {
        "title": "Revenue Dashboard"
      },
      "children": ["revenue"]
    },
    "revenue": {
      "type": "Metric",
      "props": {
        "label": "Total Revenue",
        "statePath": "/metrics/revenue",
        "format": "currency"
      }
    }
  }
}
```

#### Define registry

> *这里我们使用的是 React。JSON Render 也适用于其他 UI 库。*

注册表是目录的平台特定对应物。它接收目录对象和组件映射，并使用它们在运行时进行渲染。

```c
import { defineRegistry } from '@json-render/react';
import { catalog } from './catalog';

export const { registry, handlers, executeAction } = defineRegistry(catalog, {
  components: {
    Card: ({ props, children }) => (
      <div className="card">
        <h2>{props.title}</h2>
        {props.description && <p>{props.description}</p>}
        {children}
      </div>
    ),
    Metric: ({ props, state }) => (
      <div className="metric">
        <span className="metric-label">{props.label}</span>
        <span className="metric-value">
          {formatValue(state[props.statePath], props.format)}
        </span>
      </div>
    ),
  },
  actions: {
    submit_form: async (params, setState) => {
      const res = await fetch('/api/submit', {
        method: 'POST',
        body: JSON.stringify(params),
      });
      const result = await res.json();
      setState((prev) => ({ ...prev, formResult: result }));
    },
    export_data: async (params) => {
      const blob = await generateExport(params.format);
      downloadBlob(blob, `export.${params.format}`);
    },
  },
});
```

#### JSON 渲染不是什么

JSON Render 是一个很棒的工具，可在一次操作中将模型状态映射到 UI。它不是一个代理型框架。您可以在循环中添加一个代理，但 JSON Render 不需要代理，也并非专门为该用例构建。如果您希望将代理状态渲染到 UI，可以看看 A2UI。

#### Conclusion

JSON Render 解决了 AI 驱动界面中最困难的部分——模型输出与用户界面(UI)之间的界限。与其解析文本、创建脆弱的约定，或编写定制化的渲染逻辑，你只需定义一个契约，让模型生成结构化状态，而你的 UI 知道如何渲染这种状态。

模型不会自由生成 HTML，也不会虚构组件。它在你拥有和控制的已定义元素目录内运行。这既保持界面符合品牌风格，又能让布局和顺序动态生成。

结果是构建 AI 应用时的一种不同思维模型。你不再需要考虑如何提示聊天机器人，而是开始思考生成应用状态。UI 成为该状态的确定性映射。大量混乱的胶水代码消失了。

模型生成规范。渲染器将规范转换为用户界面。中间的一切都只是一个契约。

在 第二部分 中，我们将把这付诸实践。演示项目是 Code Roast：一个从 GitHub 仓库中提取真实数据并生成类似 Wrapped 风格的吐槽视频的工具。每个仓库会根据模型实际发现的内容获得不同的场景序列。

##### 大纲式精炼总结

- **核心问题**：把 LLM 的文本输出手动解析成 UI 状态，过程繁琐、脆弱，而且难以保证一致性、品牌规范和可访问性。  
- **核心观点**：与其 “解析文本再拼 UI”，不如让 AI 直接生成**结构化 JSON 状态**，再由前端把它确定性地渲染成界面。  
- **关键方法**：文章提出**RUG（约束式 UI 生成）**思路 —— 模型只能从你预先定义、测试过的组件集合里选用组件，而不能随意生成 HTML。  
- **JSON Render 的角色**：它把流程抽象为`AI -> JSON 状态 -> UI`，通过 “契约” 让模型输出和前端渲染解耦。  
- **三大原语**：  
  - `Schema`：定义 JSON UI 规范的结构与校验规则  
  - `Catalog`：定义模型可使用的组件、属性、动作，相当于 UI 词汇表  
  - `Registry`：把目录中的组件和动作映射到真实运行时代码，实现实际渲染与行为执行  
- **工作机制**：模型生成符合 schema 和 catalog 的 JSON；前端 registry 根据该 JSON 调用真实组件和动作，渲染出页面。  
- **优势**：保留动态布局能力，同时确保 UI 仍在开发者可控范围内，减少胶水代码和脆弱约定。  
- **边界说明**：JSON Render 不是 Agent 框架，它专注于 “把模型生成的结构化状态渲染成 UI”，而不是负责复杂代理循环。  
- **文章延展**：作者下一篇将展示如何用 JSON Render 和 Remotion 做一个基于 GitHub 仓库数据生成 “吐槽视频” 的动态 AI 视频项目。  

##### 一句话评论

这篇文章最有价值的地方，是把 “AI 做 UI” 从不可靠的文本猜测，提升为一种可验证、可约束、可工程化的状态驱动架构。

##### 一句话高价值内容

**真正值得带走的结论是：AI 应用的前端不该围绕 “聊天回复” 设计，而应围绕 “模型生成的结构化应用状态” 设计。**

## 通俗精炼（1）

### 2026-03-25 01:55:16

#### 用 JSON 直接驱动 UI：别再解析 AI 文本了

##### 核心观点

这篇文章的重点是：**不要再把大模型输出的文本手动“翻译”成界面状态**，而是让模型直接输出结构化 JSON，再由前端把 JSON 渲染成 UI。

作者认为，传统做法的问题在于：
- 模型输出和 UI 是两套独立系统
- 中间靠人工解析和胶水代码连接，容易脆弱、混乱、不可控
- 一旦产品复杂，维护成本会迅速上升

---

##### JSON Render 是什么

JSON Render 提供了一种更清晰的链路：

**AI → JSON 状态 → UI**

也就是说：
- 模型不直接生成 HTML
- 模型只生成符合约定的 JSON 规范
- 前端根据这份规范，把它映射成真实组件

本质上，它是在模型和 UI 之间建立了一份明确的“合同”。

---

##### 它为什么有价值

它解决的是 AI 产品里一个很核心的问题：**如何让模型参与界面生成，但又不失控。**

好处主要有三点：

- **更稳定**：不再依赖文本解析和临时规则
- **更可控**：模型只能使用你预先定义好的组件
- **更灵活**：页面内容、布局、顺序可以由 AI 动态决定

这意味着，产品既能保留 AI 驱动的动态性，又不会牺牲品牌一致性、可用性和无障碍规范。

---

##### 关键机制：RUG 思路

文章提到一个核心理念叫 **RUG（限制性 UI 生成）**。

它的意思是：
- 不是让模型随意生成任意界面
- 而是只允许它从你提供的组件库里“挑选”和“组合”

所以控制权的分工是：
- **你**负责定义和实现组件
- **AI**负责决定在当前场景下该用哪些组件、怎么组织

这是一种很适合企业级产品的思路：既利用 AI 的生成能力，又把风险控制在边界内。

---

##### JSON Render 的三个核心概念

###### 1. Schema：定义规则

Schema 用来规定 JSON 的结构和校验规则，相当于语法。

它决定：
- UI 规范长什么样
- 允许哪些属性
- 支持哪些交互行为

###### 2. Catalog：定义“词汇表”

Catalog 定义 AI 可使用的组件、属性和动作。

可以理解为告诉模型：
- 你能用哪些组件
- 每个组件接收什么参数
- 有哪些交互动作可调用

###### 3. Registry：负责真正渲染

Registry 把前面的抽象定义，映射到具体前端实现。

它的作用是：
- 把 JSON 中的组件类型对应到真实 React 组件
- 把动作对应到真正的执行逻辑

一句话概括：

**Schema 管规则，Catalog 管可选项，Registry 管落地执行。**

---

##### 文章举的例子

作者用一个收入看板举例：
- 模型根据提示生成一份 JSON
- JSON 里写明要渲染一个 `Card` 和一个 `Metric`
- 前端读取这份 JSON，再用注册过的 React 组件把它显示出来

这样做的好处是：
- 模型只负责“描述界面状态”
- 前端只负责“按约定渲染”
- 双方边界清晰，系统更容易扩展

---

##### 作者强调：它不是什么

JSON Render **不是代理式框架（Agent Framework）**。

也就是说：
- 它主要解决“结构化状态到 UI”的问题
- 它不是专门为复杂 agent 循环设计的
- 如果你要把 agent 状态渲染到 UI，还需要其他更适合的方案

这一点很重要，因为它说明 JSON Render 更像是**基础设施层能力**，不是全能型 AI 应用框架。

---

##### 对产品经理的启发

这篇文章最值得关注的，不只是一个工具，而是一个产品设计思路的变化：

从过去的：
**“怎么提示聊天机器人输出我能用的内容”**

转向：
**“怎么定义一套结构化状态契约，让 AI 生成可直接驱动产品界面的状态”**

这意味着 AI 产品设计会更像在设计：
- 状态机
- 组件协议
- 渲染边界
- 控制与开放的平衡

本质上，**UI 不再是对话结果的附属品，而是模型状态的确定性映射。**

---

##### 一句话总结

**JSON Render 的核心价值，是把 AI 输出从“难以控制的文本”升级为“可验证、可约束、可渲染的界面状态”，从而让 AI 驱动 UI 真正具备产品化能力。**
