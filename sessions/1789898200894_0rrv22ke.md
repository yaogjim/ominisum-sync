## 分析要点

- **核心高价值点**：对比式数据整理通过仅改变一个会翻转标签的焦点事实，并执行证据移除与规则一致性检查，使模型学习真正影响决策的证据而非表面线索。
- **留存建议**：精读并长期保留，适合作为结构化决策模型、数据整理和评估流程的实现参考（提供了可运行代码、数据整理流程、训练配方、评估结果与适用边界，对Agent路由、策略判断和本地分类系统具有直接复用价值。）

**知识要点**

- 可将扁平枚举或布尔Schema中的每个候选答案映射为单token代码，直接读取Logits并经Softmax生成类型化结果，避免解析生成式JSON。
- 对比式数据整理应构造最小事实差异的样本对，并通过逐句移除证据检查答案泄漏，再由代码根据已验证事实生成标签。
- 训练集与评估集应按来源家族整体划分，避免高度相似的对比样本跨集合泄漏；概率阈值还必须在业务自有数据上校准验证。

**行动项**

- 选取一个Agent路由或策略判断任务，将输出改写为扁平枚举与布尔Schema，并加入“无匹配”候选项。
- 基于业务规则制作最小事实变化的对比样本对，执行证据移除、规则一致性和标签翻转检查。
- 在自有人工标注数据上同时测试准确率、概率校准和延迟，再决定是否使用概率阈值进入生产流程。

#### Bespoke Nimble

**数据、模型、配方，用于开放的 Jev**

模型 · 能力 · 快速开始 · 方法论 · 文档与开发 · 引用

Introducing Bespoke Nimble. Serving reads the prompt once and then scores one answer token per question. Data curation changes one fact so that the correct answer flips. Training fine-tunes Qwen3.5-9B

Nimble 接收一些文本和一个模式，并对文本做出类型化决策。模式是要回答的问题列表。每个问题要么是从你提供的列表中选择一个选项，要么是一个真或假的问题。对于每个问题，Nimble 返回它选择的答案以及每个允许答案的概率。

Nimble 一步完成每个决策，不会先写出任何推理过程，因此速度很快（极快！）。Nimble 受到 TypeSafe 的 Jev 的 System One 方法的启发。在这个代码仓库中，我们分享了训练此类模型的配方。

请注意，我们并未从 Jev 中蒸馏。该代码仓库的目的是展示如何整理数据、如何训练以及如何部署这样一个模型，并鼓励更多研究！

你可以在搭载 Apple Silicon 的 Mac 上，或在配备 NVIDIA GPU 的机器上运行 Bespoke-Nimble-9B。

#### Capabilities

我们在一天内构建了 Nimble，因此可能会有些粗糙之处。Nimble 能做到的事情来自两个来源：第一个是基础模型 Qwen3.5-9B，第二个是我们为几个特定领域整理的数据。

Task You define You get back

Route a request 目标位置以及每个目标的适用时机 所选目的地及每个目的地的概率

Check a condition 一个是或否的问题及证据 真或假，以及各自的概率

Apply a policy 规则及允许的结果 基于你提供的文本做出的类型化决策

Rate an outcome 有序层级，每个层级都有明确的标准 所选层级以及每个层级的概率

你提供一个上下文，即要判断的文本，以及一个 schema。该 schema 必须是扁平的，这意味着它没有嵌套字段。每个字段都是一个 enum 或一个 boolean。enum 字段有一组固定的字符串选项，而 boolean 字段为 true 或 false。

每个允许的答案都有一个长度为单个 token 的代码。评分器会读取模型针对这些代码的 logits。Logits 是模型为每个 token 给出的原始分数。评分器通过 softmax 函数将 logits 转换为概率。我们的 Python 代码随后根据这些概率构建输出，因此无需解析生成的 JSON。如果某个字段是有序评分量表，你的应用程序可以使用这些概率来计算期望等级。

在 Mac 上， `ParallelScorer` 会处理一次共享上下文，然后并行对所有字段进行评分。CUDA 评分器会针对每个字段单独评分，每次都使用完整提示词。两种评分器都会返回类型化输出。它们还会返回候选答案的 logits 和概率。每个字段都是单独评分的，因此一个字段无法看到另一个字段的答案。

##### 当前发布版本无法构建的内容

- Nimble 仅接受文本。你无法用它来评判其他类型的输入，例如图像。即使基础模型包含视觉部分，也是如此。
- Nimble 仅从你提供的答案中进行选择。它无法自行编写文本，例如解释。它也无法返回嵌套 JSON 或从上下文中摘取的一段文本。一个枚举字段可以有 1 到 26 个字符串选项，而一个布尔字段有两个。
- 这些概率并不保证某个答案是正确的。Nimble 会对它们进行缩放，使其在你提供的所有答案中加起来等于 1。概率为 0.9 并不意味着该答案有 90% 的概率是正确的。如果有可能你的所有答案都不合适，请添加一个表示“无匹配”的答案。在依赖任何概率阈值之前，请在你自己的数据上进行测试。
- 每个提示最多可以有 2,048 个 token。此限制包括 schema 以及提示中指定要评分字段的部分。Nimble 会拒绝更长的提示。字段之间不能相互依赖，因此你的代码必须检查不同字段的答案是否一致。

我们在精心整理的 2,676 个示例上训练了 Bespoke-Nimble-9B。因此，它的性能将取决于这些数据及其来源领域。所以不要期望有很强的泛化能力。但我们确实看到，Nimble 在新领域中总体上优于其基础模型 Qwen3.5-9B。

#### Methodology

##### Serving

In a nutshell:

- 一次性处理上下文和模式（预填充 KV 缓存）
- 我们获取了关注标记的分数。

我们在 Bespoke-MiniCheck 中采用了这种方法（无需进行 KV 缓存预填充），因为它总是返回单个 json 元组： `{"is_claim_supported_by_context": p}` 。

这里的挑战在于，我们无法获取教师模型（或人类）给出的概率。但正如你在上面看到的，我们只需要以某种方式获取 logits，并确保 logits 尽可能经过校准以估计概率。

我们通过创建负例来推动模型经过校准，成为更好的决策者，这迫使模型成为更好的判别器。

因此，我们用一种新方法制作了训练数据，我们称之为对比式数据整理。在这种方法中，我们编写两个几乎相同的示例。它们在一个相关事实上有所不同，而这个差异会改变正确答案。其他一切保持不变，包括问题和策略。从这些配对中，模型学习哪些证据应该改变其决策。

Watch the contrastive data curation video: changing the signer from Mira to Noah flips the answer from true to false.

在这个例子中，规则是只有当退款的唯一授权由可以为该账户批准退款的人签署时，退款才被授权。这个例子有两个证据句子，你需要两者才能回答。

Evidence First example Changed example

Who can approve refunds 只有 Mira 可以为账户 42 授权退款。 Unchanged

Authorization record

Is the refund authorized? `true` `false`

我们的策展流水线将这一思路用于 Choice、Noul 和 Score 任务。它包含四个步骤：

1. 检查决策规则。我们从训练源的 schema 和策略出发。我们写下规则所依赖的基本事实。然后我们检查这些规则是否可能得出不同的答案。
2. 构建配对。我们写出两个证据句子，你需要同时具备这两句才能找到答案。然后我们在其中一个句子中最多改动八个词。我们通过这一改动来改变一个事实，我们称之为焦点事实，因此标签也随之改变。其余上下文和其他事实保持不变。
3. 检查两个示例。我们使用独立的模型调用来检查每个示例中的事实。我们还使用这些调用来检查示例是否与策略一致，以及文本是否暗示了答案。然后我们依次移除每个证据句子。在移除任一证据句子的情况下，即使所有其他文本都存在，焦点事实也必须变为未知。这样，我们就知道没有其他文本会泄露答案。
4. 生成标签。我们使用代码将已检查的规则应用于已检查的事实。只有当所有必需的检查都通过且两个标签不同时，我们才保留一对。我们保存所有模型请求和响应，以及检查结果。你可以用它们离线重放整个过程。

移除证据句子的示例仅用于检查。我们不会将它们连同标签加入训练数据，因为缺少证据并不意味着答案是错误的，也不意味着分数很低。源家族是我们从一个训练源构建的一组示例。我们将一对中的两个示例，以及来自同一源家族的所有示例，保留在同一个划分中。该划分要么是训练集，要么是评估集。

##### Finetuning

训练器将 LoRA 应用于 Qwen3.5-9B，在允许的候选 logits 上优化交叉熵。它直接学习类型化决策。保存的 Jev 概率可用于未来的软目标蒸馏（如果需要），但当前训练目标使用的是并非源自 Jev 的硬参考标签。

最终配方使用以下设置：

- LoRA rank 16
- Learning rate 5e-5
- Effective batch size 8
- Random seed 17
- One epoch of training

它保留了选择过程中使用的三阶段线性学习率计划，并在选定轮次后停止。训练使用 BF16 和 2,048 个 token 的提示限制。调优在 L40S 上运行；最终拟合和评估在 H100 上运行。

## 结构化（1）

### 2026-09-20 09:55:44

#### Nimble：面向本地类型化决策的轻量模型与开放训练方案

Nimble 是 Bespoke Labs 开源的类型化决策系统：输入一段文本和一个扁平 schema，模型直接从预设选项中作答，并返回各候选答案的分数与概率。它基于 Qwen3.5-9B，通过对比式数据整理和少量 LoRA 微调，在特定决策任务上取得了接近 Jev、优于未微调大模型的结果。

##### 核心能力：快速做受约束的决策

用户提供两部分内容：

- **上下文**：需要判断的文本。
- **Schema**：一组互不依赖的问题，每个字段只能是：
  - 枚举：从 1～26 个字符串选项中选择一个；
  - 布尔值：判断 true 或 false。

适用任务包括：

- **请求路由**：把请求分到合适的目标；
- **条件判断**：判断某个条件是否成立；
- **规则执行**：根据政策或规则选择允许的结果；
- **结果评级**：按照有明确标准的有序等级打分。

例如，输入“所有客户都无法使用支付服务”，schema 要求判断优先级和是否需要审核，模型可返回：

```json
{"priority": "HIGH", "requires_review": true}
```

同时还会给出 `HIGH/LOW`、`true/false` 等候选答案各自的 logits（模型原始分数）和归一化概率。

##### 工作方式：不生成推理过程，直接读取候选分数

每个候选答案都对应一个单 token 代码。评分器读取模型对这些代码的 logits，再用 softmax 转为总和为 1 的概率，最后由 Python 代码组装类型化结果。因此：

- 不需要模型生成和解析 JSON；
- 不输出解释或思维过程；
- 每个字段单独评分，不能看到其他字段的答案；
- 适合低延迟、结果格式固定的决策场景。

在 Apple Silicon Mac 上，`ParallelScorer` 可以只处理一次共享上下文，再并行评分多个字段；CUDA 评分器则为每个字段分别使用完整提示词。

##### 关键方法：用“对比式数据”训练模型抓住决定性证据

作者认为，只有硬标签而没有教师概率时，要让模型成为更好的决策者，需要构造能明确改变答案的负例。为此提出了**对比式数据整理**：

1. 从 schema 和政策中提取决策所依赖的基本事实；
2. 构造两个几乎相同的样本；
3. 最多改动其中一个证据句的八个词，改变一个关键事实；
4. 确保这一变化会让正确标签随之改变；
5. 独立检查事实、规则一致性和是否存在答案泄露；
6. 用代码根据已验证的规则生成最终标签。

例如，退款规则要求“授权记录必须由有权批准该账户退款的人签署”。两个样本保持账户、政策和大部分证据不变，只更改签署人，使“退款是否被授权”的答案从 true 变为 false。这样模型能学到：究竟哪条证据应该改变决策，而不是依赖表面措辞。

整理过程中还会逐一删除证据句进行检查：删除任何必要证据后，关键事实都应变为未知，以证明其他文本没有泄露答案。这些删减样本只用于验证，不进入训练集，因为“缺少证据”不等于答案为假。

为防止数据泄漏，一对样本及其同一来源家族的其他样本，会整体进入训练集或评估集，不会被拆开。

##### 数据与训练：少量、高针对性的样本

训练数据覆盖商业、教育、家庭、媒体、公共服务、科学、软件、供应链、旅行和职场等领域。

数据规模为：

- `train.jsonl`：2,826 条，其中发布模型实际使用 2,676 条；
- 留出评估集：324 条；
- 任务类型：
  - 单选：856 条训练、146 条评估；
  - 布尔判断：888 条训练、114 条评估；
  - 有序评分：932 条训练、64 条评估。

训练以 Qwen3.5-9B 为基础，通过 LoRA 直接优化候选答案的交叉熵，使用的是独立生成的硬参考标签，并未从 Jev 蒸馏。主要配置为：

- LoRA rank：16；
- 学习率：`5e-5`；
- 有效批量：8；
- 随机种子：17；
- 训练 1 个 epoch；
- BF16 精度；
- 训练提示上限：2,048 token。

作者强调，Nimble 只用 2,676 个精选样本训练，因此性能高度依赖数据覆盖范围，不应期待很强的通用泛化能力。

##### 评估结果：9B 微调模型超过未微调 27B

在 324 个合成留出样本上，各模型与参考标签的一致率为：

| 模型 | 一致率 |
|---|---:|
| Gemma 3 270M IT | 28.70% |
| Qwen3.5-0.8B | 45.37% |
| Qwen3.5-4B | 61.42% |
| Qwen3.5-9B | 66.36% |
| Qwen3.8-27B | 84.88% |
| **Bespoke-Nimble-9B** | **90.12%** |
| Jev 1.13.0 | 93.21% |

Nimble-9B 比未微调的 27B 模型多匹配 17 个标签，高出 5.25 个百分点；Jev 又比 Nimble 多匹配 10 个标签，高出 3.09 个百分点。

但作者明确提醒，这不是宽泛的通用能力测试：

- 324 个样本实际上是 162 对高度相似的对比样本；
- 参考标签是合成的；
- 数据只来自六个来源家族；
- 测试范围较窄。

因此，这些结果主要证明其训练方法在特定类型化决策任务中有效，不能直接推广到所有场景。

##### 延迟表现：比生成式模型快，但受硬件和实现影响

Nimble 每次只评分一次，不重复采样，也不生成解释。在记录的测试中：

- Nimble-9B 在 H100 上的中位延迟约为 **106 毫秒**，但该结果只覆盖 120 个样本；
- 在 64GB M5 Pro Mac 上，324 个样本的中位延迟约为 **444 毫秒**；
- Jev API 在同一留出集上的中位延迟约为 **247 毫秒**；
- 经 OpenRouter 调用的通用生成模型，中位延迟约为 **2.8～2.9 秒**。

这些结果来自不同硬件、服务和部分不同数据集，不能简单横向比较。仓库也强调，只有在相同样本和相同测试方式下，模型间比较才有意义。

##### 主要限制与使用注意事项

当前版本有明确边界：

- 只接受文本，不能处理图像；
- 只能从预设答案中选择，不能生成解释、摘取原文或返回嵌套 JSON；
- schema 必须扁平，字段之间不能互相依赖；
- 不同字段是否一致，需要应用程序自行检查；
- 每个枚举字段最多有 26 个选项；
- 模型概率只是候选答案间的归一化分数，不代表真实正确率。

例如，某答案概率为 0.9，并不意味着它有 90% 的概率正确。如果所有选项都可能不合适，应显式加入“无匹配”选项；使用概率阈值前，也必须在自己的数据上校准和测试。

README 主体多处写明推理提示上限为 2,048 token，但仓库最新提交信息提到将上限提高到 8,192 token。实际使用时应以具体模型修订版本及其 `schema_config.json` 为准。

##### 部署条件与项目定位

模型可以本地运行：

- Mac：需要 Apple Silicon，并通过 MLX/Metal 推理；
- Linux：需要支持 BF16 的 NVIDIA GPU；
- 未量化的 9B 权重约占 18GB，实际运行和合并 LoRA 适配器需要更多内存与磁盘空间；
- 官方建议使用 Python 3.12，并为 MLX、PyTorch 和数据整理工具建立独立环境。

该项目的重点不只是发布一个模型，而是开放完整方法，包括本地评分、数据整理、数据验证、LoRA 训练、评估与部署流程。它受 TypeSafe Jev 的 System One 方法启发，但作者特别说明：**Nimble 没有从 Jev 蒸馏，其训练标签也并非来自 Jev。**

## 口播总结（1）

### 2026-09-21 00:13:02

Nimble 想解决一个很具体的问题：当应用只需要做判断，而不需要生成长篇文字时，能不能让本地模型直接、快速地给出结构化答案，并同时返回各个候选答案的概率？

它的答案是，可以。Nimble 接收一段文本，再接收一份判断规则，也就是模式定义。然后，它直接做出类型化决策。比如，一条客户请求应该分配到哪个部门；某个条件是否成立；一项政策是否适用；或者一个结果应该评为哪个等级。

这里的“类型化”，意味着答案必须来自预先规定的范围。每个字段只能是两类之一。第一类是枚举，也就是从固定选项中选择一个。第二类是布尔值，也就是真或假。整个模式必须是扁平的，不能包含嵌套结构。

例如，输入文本是：“支付服务中断，所有客户都无法付款。”模式中可以有两个问题。一个问题判断优先级是高还是低。另一个问题判断，客户是否无法完成购买。Nimble 可能直接返回：优先级为高，需要审核为真。除此之外，它还会返回高和低各自的分数，以及真和假各自的分数。

Nimble 的关键设计，是不让模型先写推理过程，再解析生成结果。它为每个允许的答案分配一个单一标记代码，直接读取模型对这些代码给出的原始分数。随后再通过一种叫作“软最大值”的计算，把分数转换成总和为一的概率。这样，系统不用等待模型生成完整的 JSON，也不用担心格式解析失败，所以速度更快，输出结构也更稳定。

不过，这些概率要谨慎理解。某个答案得到百分之九十，并不等于它客观上有百分之九十的正确率。这个数字只表示，在你提供的候选答案中，模型更偏向这个选项。如果所有候选项都可能不合适，就应该主动加入一个“无匹配”选项。真正要设置概率阈值，也必须先用自己的业务数据测试。

Nimble 最值得关注的部分，不只是模型本身，而是它整理训练数据的方法。开发者把这种方法称为“对比式数据整理”。

基本思路是，创建两个几乎完全相同的案例。两个案例只在一个关键事实上有细微差别，而且这个差别必须改变正确答案。问题、政策和其他背景全部保持不变。这样，模型不能靠表面词汇猜答案，而必须学会识别，究竟哪条证据会真正改变决策。

例如，规则规定，只有获得指定批准人的签署，某笔退款才算得到授权。判断时需要结合两条证据。一条说明，谁有权批准这个账户的退款。另一条说明，授权记录由谁签署。训练数据可以只改动授权记录中的签署人，让答案从真变成假，或者从假变成真。改动最多只有八个词，其他内容保持不变。

数据整理还包含严格检查。系统先确认决策规则确实可能导向不同答案，再检查两个案例中的事实是否和规则一致，也检查文本有没有无意中泄露答案。然后，它会分别删除每一条关键证据。如果删除任意一条后，答案仍然可以确定，就说明案例里可能还有其他线索泄露结论，这对数据就不会被保留。

最后，标签不是让模型自由猜出来的，而是用代码把经过检查的规则应用到经过检查的事实之上。只有当所有检查都通过，而且一对案例的标签确实不同，这对数据才会进入数据集。删除证据的版本只用于质量检查，不会被当成负例加入训练，因为“缺少证据”并不等于“结论为假”。

为了避免信息泄漏，一对高度相似的案例，以及来自同一个源家族的其他案例，都会被放进同一个数据划分。它们要么全部属于训练集，要么全部属于评估集，不会被拆开。

发布的 Bespoke Nimble 九十亿参数模型，以千问三点五九十亿参数模型为基础，通过低秩适配，也就是 LoRA，进行微调。实际用于训练的样本只有两千六百七十六个，覆盖商业、教育、媒体、公共服务、软件、供应链和旅行等领域。任务包括固定选项选择、真假判断和有序等级评分。

在三百二十四个留出样本上，未经微调的千问三点五九十亿参数模型，匹配参考标签的比例约为百分之六十六点四。更大的二百七十亿参数模型约为百分之八十四点九。Bespoke Nimble 九十亿参数模型达到百分之九十点一。作为灵感来源的 Jev 达到百分之九十三点二。

这说明，针对决策任务整理少量但高度聚焦的数据，可能比单纯扩大模型更有效。九十亿参数的 Nimble，在这项测试中超过了未经专门调优的二百七十亿参数模型。

但这个结果不能被过度解读。评估标签是合成的。三百二十四个样本实际上由一百六十二对相近案例组成，而且只来自六个源家族，测试范围比较窄。Nimble 的作者也明确提醒，不应期待它具备很强的通用泛化能力。这个项目据称在一天内完成，当前版本仍可能比较粗糙。

它的能力边界也很清楚。Nimble 只处理文本，不能判断图像。它只能从给定答案中选择，不能自行写解释，不能摘取原文片段，也不能返回嵌套结构。枚举字段最多可以有二十六个选项。每个字段单独评分，所以一个字段看不到另一个字段的答案。跨字段是否矛盾，需要应用程序自己检查。当前说明中的输入上限是每次两千零四十八个标记，而且这个上限还包括模式定义和评分提示。

在部署方面，模型可以运行在苹果芯片的 Mac 上，也可以运行在支持十六位浮点格式的英伟达显卡上。未经量化时，单是九十亿参数的权重就大约占十八吉字节，实际运行和模型合并还需要更多内存。项目同时支持苹果的 MLX 推理和基于 CUDA 的推理，并公开了数据、训练、评估和部署方法。作者特别说明，Nimble 并不是从 Jev 蒸馏得到的，而是独立使用硬标签训练。

最值得记住的是，Nimble 不是一个缩小版的聊天机器人，而是一个专门做受约束判断的本地模型。它的核心价值来自两点：一是直接读取候选答案分数，换取快速、稳定的类型化输出；二是用只改变关键事实的对比案例，教模型识别真正影响决策的证据。

同时，概率不等于正确率，小规模窄领域评估也不等于普遍可靠。真正使用时，仍然需要加入“无匹配”选项，在自己的数据上校准阈值，并由应用程序检查多个字段之间是否一致。

## 深度解读-口播（1）

### 2026-09-21 00:16:43

Nimble 想解决一个很具体的问题：很多应用并不需要大模型写长篇回答，只需要它快速做出结构化判断。比如，一条客服请求该转给哪个部门，一项条件是否成立，某个结果属于哪个等级。Nimble 把这类任务压缩成一次本地、类型明确的决策，并同时给出各个候选答案的相对概率。

使用时，你提供两样东西。第一样是待判断的文本，也就是上下文。第二样是一个扁平的模式，用来定义需要回答的问题。每个字段只能是两类之一。一类是布尔判断，也就是真或假。另一类是枚举选择，也就是从预先给定的字符串中选一个答案。每个枚举字段可以有一个到二十六个选项。

例如，输入是“支付服务中断，所有顾客都无法付款”。模式中可以有两个字段。一个判断优先级是高还是低，另一个判断是否需要人工复核。Nimble 最终可能返回“高优先级”和“需要复核”，并附上每个候选答案的分数与概率。

关键在于，Nimble 不会先生成解释，也不需要生成一段 JSON 文本再进行解析。系统会为每个允许的答案分配一个单一令牌代码，然后直接读取模型对这些代码给出的原始分数。这个原始分数叫作逻辑值，也就是 logits。系统再通过 softmax 函数，把这些分数转成总和为一的概率，最后由 Python 程序构造类型化输出。

这种做法减少了文本生成和结果解析的开销，也避免了模型生成格式错误的 JSON。如果任务采用有序等级，比如从一级到五级，应用程序还可以利用各等级的概率计算期望等级。

不过，这里的概率必须谨慎理解。某个答案得到百分之九十，并不代表它在现实中就有百分之九十的正确率。这个数字只表示，在用户提供的候选答案中，模型给它的相对分数最高。如果所有候选答案都有可能不合适，就应该主动加入“无匹配”这一选项。任何概率阈值也都应该先在自己的数据上验证。

Nimble 的另一个重要特点，是每个字段独立评分。一个字段看不到其他字段的答案。这样有利于并行处理，却也意味着不同字段之间可能出现矛盾，应用程序必须自行检查一致性。在苹果芯片的 Mac 上，评分器可以先处理一次共享上下文，再并行判断多个字段。英伟达显卡版本则会为每个字段分别使用完整提示进行评分。

真正值得关注的，不只是推理方式，还有它的数据整理方法。开发者把这种方法称为“对比式数据整理”。

传统训练样本通常只是给模型一个问题和一个正确答案。但这种方式不一定能让模型真正理解，究竟是哪条证据改变了结论。Nimble 的做法是构造两个几乎完全相同的样本。两个样本使用相同的问题、相同的规则和几乎相同的上下文，只改变一个与决策直接相关的事实，而且最多修改八个词。这个微小变化必须让正确答案随之改变。

比如，规则规定，只有具备特定权限的人签署，退款才算获得授权。两个样本中的账户、退款请求和规则都不变，只修改授权记录中的关键事实。一个样本的答案是真，另一个样本的答案是假。通过这样的配对，模型更容易学会：哪些证据只是背景，哪些证据才应该真正改变决定。

数据整理过程还包含严格检查。系统先把决策规则拆成所依赖的基本事实，再确认这些规则确实可能导向不同答案。构造配对后，独立的模型调用会检查事实、策略和标签是否一致。接着，系统会轮流删除每一句必要证据。如果删掉任何一句后，答案仍然能从其他文字中推断出来，就说明存在信息泄漏，这组样本不能保留。最后，标签由代码根据已经验证的规则和事实生成。只有所有检查都通过，而且一对样本的标签确实不同，这组数据才会进入数据集。

这里还有一个细节。删除证据后的版本只用于检查，不会作为带标签的训练样本。因为缺少证据只代表答案未知，并不等于答案一定错误。为了防止数据泄漏，同一对样本以及来自同一来源家族的相关样本，也会全部放进训练集，或者全部放进评估集，不会拆开。

发布的九十亿参数模型基于千问三点五九十亿参数版本，用两千六百七十六个样本进行了微调。训练任务包括候选选择、真假判断和有序等级评分。训练采用 LoRA，也就是低秩适配方法，只训练一小部分新增参数。整个最终训练只进行一个轮次。项目特别说明，这些训练标签不是从 Jev 模型蒸馏而来。仓库公开的是如何整理数据、训练模型和部署评分器的完整配方。

在三百二十四个留出样本上，未经专门微调的千问三点五九十亿参数模型，参考标签匹配率约为百分之六十六点四。更大的二百七十亿参数模型约为百分之八十四点九。Bespoke Nimble 九十亿参数模型达到百分之九十点一。作为灵感来源的 Jev 达到百分之九十三点二。

这说明，在任务定义明确、训练数据针对性很强时，一个较小的专用模型可能超过更大的通用模型。但这个结果不能被理解成普遍能力的胜利。评估标签是合成的，三百二十四个样本其实是由一百六十二组相近样本构成，而且只来自六个来源家族，测试范围很窄。项目也明确承认，模型只在少量精心整理的数据上训练，不应该期待它拥有很强的跨领域泛化能力。

速度方面，因为模型不生成解释，只对候选答案评分，所以本地推理可以很快。在部分留出样本上，H100 显卡的中位耗时约为每个样本一百零六毫秒。一台配备六十四吉字节内存的 M5 Pro Mac，中位耗时约为四百四十四毫秒。不过，这些计时来自不同运行环境，也不是严格受控的服务测试，只适合帮助理解大致量级，不能随意进行横向比较。

Nimble 的边界同样清楚。当前发布版本只接受文本，不能判断图像。它只能从给定答案中选择，不能写解释，不能摘取原文片段，也不能返回嵌套结构。正文所描述的提示长度上限为两千零四十八个令牌。模型权重未量化时大约需要十八吉字节空间，实际运行和模型合并还需要更多内存。

Nimble 最值得记住的，是把大模型从“自由写作器”变成了“受约束的本地决策器”。它的效率来自直接读取候选答案分数，而不是生成推理和格式化文本。它的方法价值则来自对比式数据整理：只改变一个关键事实，迫使模型学会真正影响决策的证据。与此同时，候选概率不等于真实正确率，小规模窄领域评估也不等于普遍能力，实际部署前仍然必须用自己的数据进行验证。
