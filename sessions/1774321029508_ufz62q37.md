#### 最硬的部分：DASH 视频播放

B 站的高清视频走的是 DASH 协议，服务端返回的是分离的 video stream 和 audio stream ，需要客户端自己做 mux 。

浏览器的 `<video>` 标签支持 MSE （ Media Source Extensions ），可以直接喂 DASH 数据。但 React Native 里的 `react-native-video` 底层走的是 Android ExoPlayer ，它需要一个标准的 `.mpd` 文件才能工作。

B 站接口返回的是 JSON ，不是 MPD ，所以我手写了一个转换器：

```typescript
// utils/dash.ts
export function buildDashMpdUri(dashData: DashData): string {
  const videoRep = dashData.video
    .map(v => `
      <Representation id="${v.id}" bandwidth="${v.bandwidth}"
        codecs="${v.codecs}" width="${v.width}" height="${v.height}" frameRate="${v.frameRate}">
        <BaseURL>${escapeXml(v.baseUrl)}</BaseURL>
        <SegmentBase indexRange="${v.segmentBase.indexRange}">
          <Initialization range="${v.segmentBase.initialization}"/>
        </SegmentBase>
      </Representation>`)
    .join('');

  const audioRep = dashData.audio
    .map(a => `
      <Representation id="${a.id}" bandwidth="${a.bandwidth}" codecs="${a.codecs}">
        <BaseURL>${escapeXml(a.baseUrl)}</BaseURL>
        <SegmentBase indexRange="${a.segmentBase.indexRange}">
          <Initialization range="${a.segmentBase.initialization}"/>
        </SegmentBase>
      </Representation>`)
    .join('');

  const mpd = `<?xml version="1.0" encoding="UTF-8"?>
<MPD xmlns="urn:mpeg:dash:schema:mpd:2011" ...>
  ...${videoRep}${audioRep}...
</MPD>`;

  // 转成 data URI ，直接喂给 react-native-video
  return `data:application/dash+xml;base64,${btoa(unescape(encodeURIComponent(mpd)))}`;
}
```

生成的 MPD data URI 直接传给 `<Video source={{ uri: mpdUri }} />` ，ExoPlayer 拿到合法的 MPD 就能正确解码 1080P+ / 4K HDR 内容。

#### WBI 签名：纯 TypeScript 手写 MD5

B 站在 2023 年给核心 API 加了 WBI 签名校验。每次请求需要：

1. 从 `/x/web-interface/nav` 拉取 `img_url` 和 `sub_url` ，从路径中提取密钥字符
2. 按固定顺序重排密钥，取前 32 位拼出 `mixin_key`
3. 在请求参数里加入 `wts` （当前时间戳），用 `mixin_key` 对参数做 MD5 签名，附上 `w_rid`

关键在于 MD5——React Native 环境里没有 Node.js 的 `crypto` 模块，npm 上的 MD5 库又大多依赖 Buffer ，在 Hermes 引擎上会有兼容问题。

最终选择自己实现了一个精简版 MD5 ，纯字符串操作，零外部依赖，在所有平台上跑得很稳。nav 接口结果缓存 12 小时，避免频繁请求。

#### 弹幕系统：两套机制，一套界面

##### 视频弹幕

通过 `/x/v1/dm/[list.so](http://list.so)` 拉取 XML 格式的全量弹幕，解析后得到带时间戳的弹幕列表。播放时按当前进度 drip （逐帧滴入）到飘屏层。

飘屏层（ `DanmakuOverlay` ）维护 5 条轨道，每条弹幕根据文字长度计算飞行时间，自动选择未被占用的轨道，避免重叠。颜色、字号、舰长标记全部还原。

##### 直播弹幕

完全不同的机制——WebSocket 长连接，B 站直播弹幕走的是私有二进制协议（头部 16 字节，含包长度、协议版本、操作码、序列号）。

`useLiveDanmaku` Hook 处理连接建立、心跳保活（每 30 秒发一次 `[object Object]` 心跳包）、Zlib 解压和数据包解析。支持普通弹幕、礼物事件、进场通知，舰长弹幕有独立标记和颜色。直播弹幕实时追加，保留最近 500 条。

---

#### 首页内联视频：BigVideoCard

列表里的精选视频直接内联播放，静音自动开始，可见时播放、离屏时暂停。

额外实现了水平手势快进：用 `PanResponder` 监听水平滑动，每 `dx` 像素对应一定秒数的快进/快退，滑动时显示浮层时间标签，松手跳转。进度条和缓冲条实时更新，和视频状态完全同步。

---

#### 全局迷你播放器

这是体验细节里比较难做的一个功能。要求是：从视频详情页退出后，底部出现迷你播放器，续播当前视频，不会因为页面卸载而中断。

实现方式： `videoStore` （ Zustand ）保存当前播放视频的元数据和播放状态， `MiniPlayer` 组件挂载在根布局 `_layout.tsx` 里，与路由层级完全解耦。视频详情页卸载时不销毁播放器，只是把控制权交给 MiniPlayer ，播放状态无缝衔接。

---

#### 扫码登录

完整实现了 B 站的 OAuth 扫码流程：

1. 调用 `generateQRCode()` 获取 `qrcode_key` 和二维码内容
2. 用第三方二维码渲染服务生成图片展示给用户
3. 每 2 秒轮询 `pollQRCode` ，监听 `code` 字段变化
4. 扫码确认后（ `code === 0` ），从响应头的 `set-cookie` 字段提取 `SESSDATA`
5. 写入 AsyncStorage ，后续所有请求自动携带

登录状态通过 `authStore` 持久化，App 启动时自动恢复。

---

#### 离线下载 + 局域网分享

下载功能支持多清晰度选择（ 720P / 1080P / 1080P+），后台队列下载，进度实时显示在导航栏角标。

有一个比较有意思的功能：下载完成后，可以一键启动内置 HTTP 服务器，生成局域网访问二维码。同一 Wi-Fi 下的任意设备扫码，直接在浏览器播放已下载的视频，不需要任何额外 App 。

TIGER 的观点是“技术平权来了，扔给 AI 也能做出一个像样前端”。  
这句话有一半是对的：

- **对的部分**：AI 确实极大降低了开发门槛，特别是 UI、常规业务逻辑、脚手架、基础页面这些环节。
- **不对的部分**：这个项目真正有价值的地方，不在“像不像 B 站页面”，而在于那些 **不那么容易让 AI 一步到位的复杂部分**，例如：
  - DASH 播放链路
  - MPD 拼装
  - WBI 签名
  - 直播弹幕二进制协议
  - 跨端兼容
  - 状态管理与播放器续播

所以，**“前端页面模仿”很容易，“可用的视频客户端工程化落地”没那么容易**。  
这是评论区很多争论的根源：有的人盯着“像不像前端皮肤”，有的人看到的是“底层实现很硬”。

---

###### 2. 社交媒体最擅长的，是把“技术项目”变成“情绪故事”
原始项目本来是一个开发者作品展示，结果因为标题和转述方式，被迅速改写成了一个更有传播力的故事：

- “被裁员”
- “前大厂员工”
- “开源前东家源码”
- “技术平权”
- “AI 秒做竞品”

这些词都非常抓眼球，因为它们天然带有冲突感、戏剧性、爽点。  
但越有传播力，越容易偏离事实。

这就是典型的社交媒体传播机制：

> 技术事实本身很复杂，传播时会被压缩成一句最刺激的话。

于是，很多用户点进去期待看到“官方源码泄露”，最后发现只是“第三方重写项目”，自然会觉得被误导，评论区就开始反噬。

---

###### 3. Grok 被夸，不只是因为“回答得对”，而是因为“体验像在办案”
Muratcan 的重点其实不是 B 站项目本身，而是 **Grok 专家模式的搜索体验**。  
他想表达的是：

- 不是简单搜几条结果
- 而是像一个代理（agent）一样去翻很多页面
- 快速归纳、提炼、展示证据
- 还能带图片、技术上下文、结构化信息

为什么这点会让人印象深刻？因为这个事件本身就很适合代理式搜索发挥：

- 同时有 X 帖子、GitHub 仓库、V2EX 讨论
- 同一事件在不同平台有不同叙事
- 真相需要交叉比对才能看清

也就是说，**这个案例天然不是“找一个答案”，而是“拼接全貌”**。  
代理式搜索在这种任务上比传统搜索更有优势。

---

##### 二、`JKVideo` 这个项目到底有没有技术含量？

有，而且不低。

从 GitHub 和 V2EX 描述看，它不是简单的“套壳”：

###### 项目亮点大致可以分成三层

###### 1. 表层：用户能直接感知的能力
- 首页热门/直播混排
- 视频详情页
- 实时弹幕
- 直播页
- 扫码登录
- 下载管理
- 迷你播放器
- Android / iOS / Web 跨端运行

这些功能已经超出一般 Demo 水平，更接近“能用的客户端雏形”。

###### 2. 中层：工程实现能力
- React Native + Expo 的跨端架构组织
- Zustand 做全局状态
- Axios + Cookie/WBI 签名处理请求
- 文件系统路由
- 下载队列
- 本地 HTTP 服务做局域网分享

说明作者不只是“堆界面”，而是在做一个完整应用。

###### 3. 深层：真正难的地方
- **DASH JSON 转 MPD**：这是为了喂给 ExoPlayer 正确播放高清视频。
- **纯 TypeScript 实现 MD5 / WBI 签名**：绕开 RN/Hermes 环境兼容问题。
- **直播弹幕协议解析**：涉及 WebSocket、二进制协议、解压、心跳维持。
- **播放器状态跨页面续播**：要解决组件生命周期与全局状态切换。

这些点都说明：  
**作者做的不只是“B 站长得像”，而是“B 站里难做的能力”也认真做了。**

所以，如果只用“这玩意 AI 也能写”来概括，明显低估了项目难度。

---

##### 三、为什么评论区会这么撕裂？

因为大家讨论的根本不是同一个问题。

###### 认可派在看什么？
他们看的是：
- 一个人能做出这种完成度，很强
- 项目开源，有学习价值
- 说明个人开发者借助 AI 和社区积累，确实能做出过去要团队才能做的东西

所以他们的情绪是：**佩服、兴奋、支持、Star 一下。**

###### 质疑派在看什么？
他们看的是：
- 标题是不是故意误导
- 作者是不是在蹭“裁员”和“大厂”热度
- 如果并非 B 站员工，却让人误以为是，那就是标题党
- 如果真和前东家有关，是否有法律与职业道德风险

所以他们的情绪是：**被欺骗、反感、担忧、举报。**

###### 两边其实都没完全错
- **项目本身可能确实不错**
- **传播方式也确实可能有误导性**

换句话说，这是一个典型的“**作品质量不错，但叙事方式翻车**”案例。

---

##### 四、“技术平权”到底体现在哪里？

这件事里，“技术平权”不是说任何人都能立刻做出 B 站。

更准确地说，它体现为三种变化：

###### 1. 学习资料更开放了
过去很多能力要靠公司内部积累、团队传帮带。  
现在社区逆向分析、开源项目、博客、GitHub issue、AI 辅助，让个人也能迅速摸到门路。

###### 2. 开发工具更强了
React Native、Expo、成熟播放器库、状态管理库，再加上 AI 生成和补全代码，让“搭骨架”的成本大幅下降。

###### 3. 个人开发者能做更完整的产品了
以前一个人做 Demo 容易，做“像应用”的产品难。  
现在一个人可以同时兼顾：
- 页面
- 状态
- 接口
- 播放
- 登录
- 下载
- 多端

这才是“技术平权”的真正含义：  
**不是人人都变成顶级工程师，而是普通开发者能触达更高的产出上限。**

---

##### 五、但“技术平权”不等于“事实可以随便包装”

这件事也提醒了另一个现实：

###### 传播能力越强，越要珍惜可信度
一个项目火起来很难，但掉信用很快。  
如果标题让人误以为“泄露前东家源码”，而事实只是“第三方重写”，那即便作品很好，也会被很多人直接打上：

- 标题党
- 蹭热度
- 营销式求职
- 不可信

尤其在求职语境里，这种印象可能比项目本身还致命。  
因为公司招人时，除了看技术，也会看：

- 诚实度
- 风险意识
- 法律边界
- 对外表达方式

所以这件事从职业角度看，也是一个很典型的提醒：

> 技术作品能加分，但失真的叙事可能会抵消加分，甚至变成扣分。

---

##### 六、Grok 在这个案例里为什么显得“厉害”？

因为它处理的是一种很难的任务：**多源信息拼图**。

###### 传统搜索更像：
- 给你 10 个链接
- 你自己点开看
- 自己判断哪个是真的

###### 代理式搜索更像：
- 帮你把 X、GitHub、论坛、评论串起来
- 自动比对说法冲突
- 提取项目技术点
- 告诉你哪些是事实，哪些是情绪包装

这个案例里，用户真正需要的不是“JKVideo 是什么”，而是：

- 它到底是不是 B 站源码？
- 作者到底是不是 B 站员工？
- 项目技术上值不值得关注？
- 为什么网上一边吹爆、一边群嘲？

这类问题本质上是 **调查型问题**，而不是 **百科型问题**。  
所以 Muratcan 才会觉得 Grok 的体验“和以前完全不同”。

---

#### 关键信息提炼

##### 可以基本确认的部分
- `JKVideo` 是一个 **第三方开源客户端项目**，不是官方 B 站 App 源码仓库。
- 项目技术实现较完整，尤其在播放器、弹幕、WBI 等环节有一定技术含量。
- 社交传播中出现了“开源 B 站源码”“B 站员工被裁后开源”等强叙事表达。
- 评论区大量人对这些说法的真实性提出质疑。

##### 容易被误解的部分
- “开源了 B 站 app 源码”  
  更准确应理解为：**开源了一个模仿/实现 B 站核心体验的第三方客户端项目**。
- “B 站前端开发工程师被裁员”  
  从评论质疑看，这一点 **并没有在现有材料中被可靠证实**，反而存在明显争议。

##### 真正值得关注的部分
- 个人开发者借助 AI 和开源生态，已经能做出接近正式产品形态的复杂 App。
- 代理式搜索在“跨平台还原事实全貌”这类场景里，体验优势很明显。
- 技术作品出圈后，**叙事方式** 可能比技术本身更影响公众评价。

---

#### 一句话结论

**这不是一起“官方源码泄露”新闻，而是一个技术完成度不错的第三方 B 站客户端项目，被带有误导性的传播话术推上热搜；它既展示了 AI 时代个人开发者能力上限的提升，也暴露了社交媒体时代“好项目 + 坏标题”会迅速引发信任危机。**
