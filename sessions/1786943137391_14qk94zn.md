## 分析要点

- **核心高价值点**：将Agent全部能力插件化，并让恢复、分叉、检索和回放共享同一份仅追加事件流，为可组合与可追踪的Agent系统提供了清晰架构。
- **留存建议**：精读并存档，重点跟踪插件接口、运行轨迹和自定义模式能力（与Agent开发高度相关，提供了可组合插件架构、统一事件流和多运行模式等可复用设计思路。）

**知识要点**

- Cordis内核仅负责插件加载、卸载和依赖管理，具体Agent能力由插件通过服务与事件协作提供。
- 会话采用仅追加事件流记录提示词、工具调用、子Agent调度和上下文注入，可支持恢复、分叉、检索与回放。
- 标准、PTC、极简和创造四种模式分别面向完整开发、多步工具编排、基准测试和自定义Agent预设。

**行动项**

- 检查开源仓库与开发文档，评估插件API、依赖机制和自定义preset的成熟度。
- 选取现有Agent项目，尝试将模型、工具、存储和调度拆分为可替换插件进行对照实验。

## 结构化（1）

### 2026-08-17 05:17:46

#### DeepSeek Harness 开发者预览版总结

DeepSeek Harness 是一套面向全球开发者开放测试并同步开源的 Agent 开发框架。其核心理念是 **“一切皆插件”**：模型、工具、会话、沙箱、存储、调度和 UI 等能力都能自由替换、扩展与组合。

##### 1. 核心定位：让模型成为可持续工作的 Agent

- DeepSeek 将 Agent 概括为：**Agent = Model + Harness**。
- 模型是 Agent 的“灵魂”，Harness 则负责让模型：
  - 理解运行环境；
  - 调用各种工具；
  - 管理会话与任务；
  - 在真实场景中持续工作。

##### 2. 架构设计：所有能力都由插件提供

###### Cordis 内核

- DeepSeek Harness 基于 **Cordis 插件系统**构建。
- Cordis 内核只处理：
  - 插件加载与卸载；
  - 插件之间的依赖关系。
- 内核本身不直接承载具体的 Agent 能力，因此整体架构更轻量、灵活。

###### 能力插件化

以下 Agent 能力均由插件提供：

- 模型
- 工具
- 技能（Skills）
- 会话
- 沙箱
- 存储
- 循环
- 调度
- UI

这些插件通过 Cordis 的服务与事件机制协同工作。开发者无需修改 Harness 源码，只需调整配置，就能选择、替换或扩展任意能力。

##### 3. 运行可追踪：每次执行都有完整记录

- 模型在运行中看到和使用的信息，会写入采用**仅追加设计**的会话日志，包括：
  - 系统提示词；
  - 模型推理相关记录；
  - 工具调用及结果；
  - 子 Agent 调度；
  - 每次上下文注入。
- 开发者可在 **Trajectory 视图**中按来源查看这些信息。
- 会话恢复、分叉、检索和回放共用同一份事件流，便于调试、分析与复现 Agent 的运行过程。

##### 4. 四种运行模式

###### 标准模式

面向完整编码任务，支持：

- 文件编辑与 Shell；
- 文件和网页检索；
- Skills；
- 计划与目标管理；
- 子 Agent；
- 工作流。

###### PTC 模式

- 具备标准模式的全部能力。
- 通过 **Code Mode SDK**向模型提供工具。
- 模型可以生成一段 TypeScript 程序，把多轮工具调用组合成一次多步骤操作。

###### 极简模式

- 仅保留两个工具：
  - 持久化 `bash`；
  - `str_replace_editor` 文件编辑工具。
- 适合在最小化环境中进行模型基准测试。

###### 创造模式

- 用于创建自定义 Agent preset（预设）。
- 除标准模式能力外，还支持：
  - 检查当前运行时；
  - 在内存中实验 Cordis 插件；
  - 根据需求组合插件；
  - 获得 preset 创作指导。

例如，开发者可以直接描述想构建的 Agent，再利用运行时检查和插件实验能力设计新的运行模式。

##### 5. 快速开始与源码安装

###### 快速体验

安装 Node.js 后，可通过以下命令启动 Web UI：

```bash
npx @deepseek-ai/dsh web
```

###### 从源码安装

可克隆完整项目，并按照仓库文档安装：

```bash
git clone https://github.com/deepseek-ai/deepseek-harness
```

##### 6. 当前阶段与生态方向

- DeepSeek Harness 目前仍是面向 Harness 开发者的**开发者预览版**。
- 核心插件和基础 API 仍会持续迭代，现阶段可能存在接口变化。
- 项目希望与全球开发者共同建设一个具备以下特点的 Agent 基础设施：
  - 开源；
  - 开放；
  - 可复用；
  - 可组合。
- 开发者可通过 GitHub 和官方开发者文档进一步了解项目，并参与 DSH 插件生态建设。

## 口播总结（1）

### 2026-09-17 00:25:55

DeepSeek Harness 想解决的核心问题是：怎样让人工智能代理，也就是 Agent，不只会生成答案，还能理解运行环境、调用工具，并在真实任务中持续工作。它给出的思路可以概括为一句话：模型是 Agent 的核心，而 Harness 是承载和组织各种能力的运行框架。更特别的是，这套框架把几乎一切能力都做成了插件。

DeepSeek Harness 目前是开发者预览版，已经面向全球开发者开放测试，并同步开放源代码。它最重要的设计原则，是“一切皆插件”。

模型、工具、技能、会话、沙箱、存储、任务循环、调度和用户界面，都不是写死在系统里的固定模块，而是可以组合的插件。这些插件通过 Cordis 内核提供的服务和事件机制彼此协作。

Cordis 内核本身非常克制。它只负责插件的加载、卸载和依赖关系，不直接承载 Agent 的具体能力。可以把它理解成一个插件底座。至于 Agent 能做什么，则取决于开发者安装了哪些插件，又如何组合这些插件。

这种设计带来的直接好处，是灵活性。开发者不需要修改 DeepSeek Harness 的源代码，就能在配置层选择、替换或扩展任意能力。比如，可以更换模型，调整工具组合，替换存储方式，或者加入新的调度和交互界面。这样一来，同一套底层框架可以拼装出面向不同任务的 Agent。

除了可组合，DeepSeek Harness 还强调运行过程可以追踪。

模型在运行中看到的内容，都会进入一份只允许追加、不随意覆盖的会话日志。记录范围包括系统提示词、思维链、工具调用及其结果、子 Agent 的调度，以及每一次注入上下文的过程。

开发者可以在 Trajectory，也就是运行轨迹视图中，按照信息来源查看这些内容。会话恢复、分叉、检索和回放，也都建立在同一份事件流之上。

这意味着，当 Agent 的行为不符合预期时，开发者不仅能看到最终结果，还能回头检查它接收了什么信息、调用了什么工具，以及任务在哪一步出现偏差。插件化解决的是“能力怎样组合”，运行轨迹解决的则是“行为怎样理解和复现”。

为了适应不同的开发和测试需求，DeepSeek Harness 提供了多种运行模式。

标准模式是一套功能完整的编码 Agent。它支持文件编辑、命令行操作、文件与网页检索、技能调用、计划和目标管理，还支持子 Agent 与工作流。

PTC 模式包含标准模式的全部能力，但工具的使用方式不同。它通过 Code Mode 软件开发工具包来呈现工具，让模型生成一段 TypeScript 程序，把多轮工具调用组合成一次多步骤操作。简单来说，标准模式更像逐步调用工具，PTC 模式则允许模型先写一段代码，再由这段代码组织复杂操作。

极简模式只保留两个工具：一个可以持续运行的 Bash 命令行环境，以及一个用于精确替换文本的文件编辑工具。这个模式主要用于最小化环境下的模型基准测试。它尽量减少外围能力，从而更集中地观察模型本身的表现。

创造模式则面向自定义 Agent。它拥有标准模式的完整能力，同时可以检查当前运行环境，在内存中试验 Cordis 插件，并根据试验结果创建新的 Agent 预设。开发者可以先描述想构建的内容，再逐步组合出适合特定场景的运行模式。

想快速体验，安装 Node.js 之后，可以通过 DeepSeek 提供的 npx 命令启动网页界面。需要深入开发时，也可以从 GitHub 获取完整源代码，按照项目说明安装和修改。

不过，需要注意一个前提：DeepSeek Harness 目前仍处于开发者预览阶段。核心插件和基础应用程序接口还会继续迭代，因此现阶段更适合测试、探索和参与生态建设，而不是把所有接口都视为已经稳定。

最值得记住的是两点。第一，DeepSeek Harness 把 Agent 拆成了可以自由替换和重组的插件，让开发者能在配置层快速改变系统能力。第二，它用统一的事件流记录运行过程，让恢复、分叉、检索、回放和问题排查共享同一套依据。它要提供的不是某一个固定 Agent，而是一套开放、可复用、可组合的 Agent 基础设施。

## 深度解读（1）

### 2026-09-17 00:35:28

#### DeepSeek Harness 的关键不在“插件”，而在把 Agent 运行时变成可替换、可回放的系统

DeepSeek Harness 提出的公式是 **Agent = Model + Harness**。这看似简单，实际是在修正一种常见误解：Agent 的效果并不只取决于模型能力，还取决于模型能看到什么、能调用什么、如何循环、怎样保存状态，以及失败后能否恢复。

这篇发布说明没有提供任务成功率、成本或稳定性数据，因此还不能证明 Harness 比其他 Agent 框架更有效。它真正值得关注的贡献，是公开了一套相对彻底的运行时设计：模型、工具、技能、会话、沙箱、存储、调度乃至 UI 都被实现为插件，内核只管理加载、卸载和依赖。

##### “一切皆插件”让 Agent 架构从代码分叉变成配置实验

许多 Agent 系统表面上支持扩展，但关键能力仍被写死在框架内部。更换模型容易，更换上下文管理、循环策略或沙箱实现，往往意味着修改源码，随后形成难以合并的私有分支。

Harness 试图把这些差异提升为配置层的组合问题。其价值不只是开发方便，而是让团队能更低成本地验证：同一模型在不同工具集、循环策略和存储机制下，效果究竟相差多少。极简模式只保留 Bash 与文件编辑器，标准模式加入检索、计划、子 Agent 和工作流，PTC 模式则让模型用一段 TypeScript 组合多轮工具调用——这些模式实际上是在把“工具如何暴露给模型”视为一个可控变量。

这可能让 Agent 评测更接近真实工程：不是笼统比较两个“智能体”，而是固定模型和任务，分别替换沙箱、上下文注入或调度插件，定位性能来自哪里。

不过，**插件化本身并不会自动带来生态**。真正的门槛是接口能否稳定、插件之间是否能可靠组合，以及升级后行为是否可预测。当前仍是开发者预览版，核心插件和 API 会持续变化；“无需改源码”目前更像架构承诺，还不是经过大规模插件兼容性验证的事实。

##### 仅追加事件流，可能比功能数量更重要

Harness 把系统提示词、工具调用及结果、子 Agent 调度和每次上下文注入写入仅追加的会话日志，并让恢复、分叉、检索与回放共享同一份事件流。这相当于把 Agent 从一个难以解释的聊天黑箱，转成可重建的运行过程。

对真实产品而言，这解决的是很具体的问题：当 Agent 修改错文件或执行了危险命令，团队需要知道错误来自模型判断、工具返回、上下文污染，还是调度逻辑；修复后还要能从某个节点重放，而不是重新跑完整任务。分叉能力也使人工接管、方案对比和回归测试更自然。

代价同样明显。日志可能包含系统提示词、用户数据、密钥、工具结果，甚至文章所称的“思维链”。因此可观测性越完整，数据治理责任越重：脱敏、权限、保存周期和审计边界不能只是外围功能，否则“运行有迹可循”也会变成敏感信息集中泄露的入口。

##### 值得验证的是运行时生态，而不是又一个 Agent 外壳

如果这套架构成立，潜在机会并非简单做更多工具插件，而是提供可替换且可测量的关键组件，例如企业沙箱、上下文压缩、成本调度、策略审计和轨迹评测。现有替代方案通常是各框架自带能力或企业内部定制；Harness 的待验证假设，是这些能力能否通过稳定协议跨场景复用，并形成足够强的网络效应。

因此，现阶段最值得观察的指标不是插件数量，而是：**第三方插件能否在不理解整个系统的情况下安全接入，以及一次 Agent 运行能否被可靠解释、复现和迁移。** 如果这两点成立，Harness 才可能从开源框架进一步成为 Agent 时代的运行时基础设施。

##### 一句话看懂

DeepSeek 发布并开源了 Harness 开发者预览版：它把模型、工具、记忆、沙箱、调度和 UI 等 Agent 能力全部做成可替换插件，让开发者通过配置自由组合智能体。

##### 关键内容

- **插件化架构**：Cordis 内核只管理插件加载、卸载和依赖关系，具体能力由插件提供，开发者通常无需修改 Harness 源码。
- **运行过程可追踪**：系统会以仅追加日志记录提示词、模型推理信息、工具调用、子 Agent 调度及上下文注入，并支持恢复、分叉、检索和回放。
- **提供四种模式**：标准模式功能完整；PTC 模式用 TypeScript 代码组合多步工具调用；极简模式用于基准测试；创造模式用于制作自定义 Agent 配置。
- **目前仍是预览版**：可通过 `npx @deepseek-ai/dsh web` 体验或从 GitHub 安装，但核心插件和 API 还会继续变化。

##### 通俗解读

它更像“Agent 的乐高底座”，而不是一个新模型：模型负责思考，Harness 负责接工具、保存过程并让任务持续运行。**Agent 基础设施或插件开发者值得继续看文档和源码**；普通用户浏览此页即可，因为原文主要是产品概览，没有提供 API 细节、性能测试或稳定性说明。
