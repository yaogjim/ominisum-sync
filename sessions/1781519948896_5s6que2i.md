## 通俗精炼（2）

### 2026-06-15 10:38:02

#### CJ Zafir：通过 Claude + Codex 分工，减少 50% Claude Code 消耗

##### 核心观点

CJ Zafir 分享了一套 AI 编程工作流：  
通过在 Claude Code 中安装 OpenAI Codex 插件，把“规划、执行、审核”拆给不同模型处理，从而让每周 Claude Code 使用额度减少约 50%。

##### 推荐工作流

###### 1. Claude 负责规划

使用 **Claude Fable 5 High** 做项目规划。  
适合负责理解需求、拆解任务、制定实现方案。

###### 2. Codex 负责执行

使用 **Codex 5.5 xhigh** 进行代码实现。  
重点是：通过 Codex 计划使用，不走 API。

CJ 表示，如果希望一次执行到位、减少反复调试，推荐使用 **xhigh**；如果要求没那么高，**high** 也可以。

###### 3. Claude 负责审核

使用 **Claude Fable 5 Max** 做最终审核。  
主要用于检查代码质量、逻辑漏洞和整体实现效果。

##### 热门讨论

###### 成本优化 vs 质量提升

有用户认为，这种方式本质是“Claude 负责思考，Codex 负责执行”，属于智能拆分。  
但关键问题是：它到底提升了输出质量，还是只是降低了成本？

###### 审核模型可能过度配置

也有人认为，对于 90% 的项目来说，用 Claude Fable Max 做代码审核可能有些浪费。  
更常见的组合是：

- Claude Fable 5 High / Medium：负责规划
- GPT 5.5、GLM 5.1：负责执行
- GPT-5.3-Codex：负责代码审查

###### 可替代执行模型

CJ 补充，如果执行环节想换其他模型，也可以考虑：

- DeepSeek v4 Pro
- MiMo v2.5
- Minimax 3
- GLM 5.1
- Qwen 3.6 Max

但他强调，项目中必须有一个强编排器，例如 Claude 或 Codex，来掌控整体方向。

##### 产品视角总结

这套方法的本质不是单纯“换模型”，而是把 AI 编程流程产品化：

- **规划**：用强推理模型做任务拆解
- **执行**：用高性价比代码模型生成代码
- **审核**：用强模型把关质量

核心价值是：在保证一定质量的同时，降低 Claude Code 的额度消耗，提高整体开发效率。

###### 模型不是全程都要用最贵的

软件开发任务可以拆成三类：

1. **规划：理解需求、设计方案**
2. **执行：写代码、改文件、跑流程**
3. **审核：检查质量、发现问题**

其中，规划和审核更依赖强推理与上下文理解；  
执行阶段则可以交给成本更低或额度更充足的模型完成。

###### 从“单模型全包”转向“多模型协作”

现在更高效的方式是根据任务类型进行模型分工：

- 高价值环节用最强模型
- 重复执行环节用更经济模型
- 最后再用强模型做质量控制

这类似产品和工程团队里的分工：  
**架构师定方案，工程师执行，负责人验收。**

##### 主旨概括

CJ Zafir 分享了一套在 Claude Code 中结合 OpenAI Codex 使用的工作流，称这样可以让自己每周消耗的 Claude Code 限额减少约 **50%**。核心思路是：**让 Claude 负责规划和审核，让 Codex 负责执行代码任务**，从而降低 Claude 的使用消耗。

##### 1. 具体做法：在 Claude Code 中接入 Codex

作者的操作很简单：

- 在 **Claude Code** 中安装 **OpenAI Codex 插件**
- 然后按不同阶段分配模型任务：

| 阶段 | 使用模型 | 作用 |
|---|---|---|
| 规划 | Claude Fable 5 High | 负责思考、拆解任务、制定方案 |
| 执行 | Codex 5.5 xhigh | 按计划写代码、完成实现 |
| 审核 | Claude Fable 5 Max | 检查代码质量、发现问题 |

作者强调：**不使用 API，而是使用 Codex 计划**。  
他表示这套方式“确实有效”。

##### 2. 核心逻辑：把“思考”和“执行”拆开

热门回复中有人总结得很准确：

> Claude 负责思考，Codex 负责执行。

也就是说，不再让 Claude 从头到尾包办所有事情，而是：

- Claude 做更擅长的高层规划、架构判断
- Codex 做更消耗 token 的代码实现
- Claude 最后再做质量把关

这样可以减少 Claude Code 的额度消耗，同时保持一定的开发质量。

##### 3. 关于模型配置：不一定每个项目都要用最高档

有回复指出：

- 对 **90% 的项目** 来说，用 **Fable Max** 做审核可能有点“过度配置”
- 更常见的组合可以是：
  - **Fable 5 High 或 Medium** 用于规划
  - **GPT 5.5 或 GLM 5.1** 用于执行
  - **GPT-5.3-Codex** 用于代码审查

这说明实际使用时可以根据项目复杂度调整模型，不一定都要使用最高级别。

##### 4. 作者补充：高质量项目需要强编排器

CJ Zafir 进一步解释：

如果想要高质量输出，一个强大的“编排器”很重要，例如：

- Codex
- Claude

它们负责掌控项目方向、拆解任务和协调执行，这一点在复杂项目中非常关键。

但具体执行代码时，可以选择更多模型，例如：

- Deepseek v4 专业版
- MiMo v2.5
- 极小极大 3
- GLM 5.1
- 通义千问 3.6 Max

也就是说，**规划和管理项目的模型要强，执行模型可以更灵活选择**。

##### 5. 执行档位建议：xhigh 更适合一次到位

作者还补充：

- 如果希望一次执行成功，减少反复调试，推荐使用 **xhigh**
- 如果不追求一次到位，使用 **high** 也可以

这表明 xhigh 更适合复杂或要求较高的任务，但也可能更消耗资源。

##### 6. 最简单的上手方式

作者最后给出简化建议：

> 只需要让 Claude 安装官方 Codex 插件即可。

也就是说，对普通用户而言，不必一开始就配置复杂流程，可以先在 Claude Code 中接入 Codex，再逐步尝试“Claude 规划 + Codex 执行 + Claude 审核”的模式。
