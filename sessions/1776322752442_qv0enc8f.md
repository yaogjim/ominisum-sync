- **核心高价值点**：最有价值的点是把每次模型回复后的下一步操作视为“上下文管理决策点”，并明确区分 continue、rewind、clear、compact、subagents 的适用边界。

**知识要点**

- 长上下文会带来 context rot，模型在上下文变长时性能可能下降
- rewind 比事后纠错更适合清理错误尝试带来的上下文污染
- compact 是有损压缩，clear 是手工重建上下文，两者适用场景不同
- subagents 适合处理中间输出很多但最终只需结论的任务

**行动项**

- 在使用 Claude Code 时，为新任务默认开启新 session，避免无关上下文累积
- 调试失败后优先尝试 /rewind，而不是在污染过的上下文里继续修正
- 对长任务主动提前 /compact，并附带压缩重点说明，减少坏压缩风险
- 将代码库调研、结果验证、文档生成等高噪声工作交给 subagents

## 正文

**Thariq**

### 使用 Claude Code：会话管理 &amp; 1M 上下文

Today we’re rolling out a new update to /usage to help you understand your usage with Claude Code, this was informed by a number of conversations with customers.

What came up again and again in these calls is that there is a lot of variance in how you might manage your sessions, especially with our new update to 1 million context in Claude Code.

Do you only use one session or two sessions that you keep open in a terminal? Do you start a new session with every prompt? When do you use compact, rewind or subagents? What causes a bad compact?

There’s a surprising amount of detail here that can really shape your experience with Claude Code and almost all of it comes from managing your context window.

#### A Quick Primer on Context, Compaction &amp; Context Rot

![Image](https://pbs.twimg.com/media/HF-nqWCbEAE3Oan?format=jpg&name=large)

上下文窗口是模型生成下一个响应时能同时“看到”的所有内容。它包括你的系统提示、迄今为止的对话、每一次工具调用及其输出，以及每一个已读取的文件。Claude Code 的上下文窗口为一百万 token。

不幸的是，使用上下文会带来一定的成本，这通常被称为“上下文衰减（context rot）”。上下文衰减指的是这样一种现象：随着上下文变长，模型性能会下降，因为注意力会分散到更多的词元上，而更早的、无关的内容开始对当前任务产生干扰。

Context windows are a hard cutoff, so when you’re nearing the end of the context window, you will need to summarize the task you’ve been working on into a smaller description and continue the work in a new context window, we call this compaction. You can also trigger compaction yourself.

![Image](https://pbs.twimg.com/media/HF-ntaxboAAZuCm?format=jpg&name=large)

### Every Turn Is a Branching Point

Say you've just asked Claude to do something and it's finished, you’ve now got some information in your context (tool calls, tool outputs, your instructions) and you have a surprising number of options for what to do next:

- Continue — send another message in the same session
- /rewind (esc esc) — jump back to a previous message and try again from there
- /clear — start a new session, usually with a brief you've distilled from what you just learned
- Compact — summarize the session so far and keep going on top of the summary
- Subagents — 委派下一段工作给拥有自己干净上下文的代理，并且只将其结果拉回

While the most natural is just to continue, the other four options exist to help manage your context.

![Image](https://pbs.twimg.com/media/HF-n6mMbEAEImhv?format=jpg&name=large)

#### When to Start a New Session

When do you keep a long running session vs starting a new one? Our general rule of thumb is when you start a new task, you should also start a new session.

1M context windows do mean that you can now do longer tasks more reliably, for example to have it build a full-stack app from scratch.

Sometimes you may do related tasks where some of the context is still necessary, but not all. For example, writing the documentation for a feature you just implemented. While you could start a new session, Claude would have to reread the files that you just implemented, which would be slower and more expensive.

#### Rewinding Instead of Correcting

![Image](https://pbs.twimg.com/media/HF-oDqjbEAI94h5?format=jpg&name=large)

If I had to pick one habit that signals good context management, it’s rewind.

In Claude Code, double-tapping Esc(or running /rewind) lets you jump back to any previous message and re-prompt from there. The messages after that point are dropped from the context.

Rewind is often the better approach to correction. For example, Claude reads five files, tries an approach, and it doesn't work. Your instinct may be to type "that didn't work, try X instead." but the better move is to rewind to just after the file reads, and re-prompt with what you learned. "Don't use approach A, the foo module doesn't expose that — go straight to B."

You can also use “summarize from here” to have Claude summarize its learnings and create a handoff message, kind of like a message to the previous iteration of Claude from its future self that tried something and it didn’t work.

![Image](https://pbs.twimg.com/media/HF-oKwBbEAAdb6I?format=jpg&name=large)

#### Compacting vs. Fresh Sessions

Once a session gets long, you have two ways to shed weight: /compact or /clear (and start fresh). They feel similar but behave very differently.

Compact asks the model to summarize the conversation so far, then replaces the history with that summary. It's lossy, you're trusting Claude to decide what mattered, but you didn't have to write anything yourself and Claude might be more thorough in including important learnings or files. You can also steer it by passing instructions (/compact focus on the auth refactor, drop the test debugging).

![Image](https://pbs.twimg.com/media/HF-oPtxaAAAUKMr?format=jpg&name=large)

使用 /clear 你写下重要的内容（“我们正在重构认证中间件，约束条件是 X，重要的文件是 A 和 B，我们排除了方法 Y”）并从头开始。这会更费功夫，但最终的上下文是你认为相关的内容。

#### What Causes a Bad Compact?

![Image](https://pbs.twimg.com/media/HF-oy22bEAE_Jd8?format=jpg&name=large)

If you run a lot of long running sessions, you might have noticed times in which compacting might be particularly bad. In this case we’ve often found that bad compacts can happen when the model can’t predict the direction your work is going.

For example autocompact fires after a long debugging session and summarizes the investigation and your next message is "now fix that other warning we saw in

[bar.ts](http://bar.ts/)."

But because the session was focused on debugging, the other warning might have been dropped from the summary.

This is particularly difficult, because due to context rot, the model is at its least intelligent point when compacting. With one million context, you have more time to /compact proactively with a description of what you want to do.

#### Subagents &amp; Fresh Context Windows

![Image](https://pbs.twimg.com/media/HF-o6v1bQAA7pS6?format=jpg&name=large)

Subagents are a form of context management, useful for when you know in advance that a chunk of work will produce a lot of intermediate output you won't need again.

When Claude spawns a subagent via the Agent tool, that subagent gets its own fresh context window. It can do as much work as it needs to, and then synthesize its results so only the final report comes back to the parent.

The mental test we use: will I need this tool output again, or just the conclusion?

While Claude Code will automatically call subagents, you may want to tell it to explicitly do this. For example, you may want to tell it to:

- “Spin up a subagent to verify the result of this work based on the following spec file”
- “Spin off a subagent to read through this other codebase and summarize how it implemented the auth flow, then implement it yourself in the same way”
- “Spin off a subagent to write the docs on this feature based on my git changes”

### Summary

In summary, when Claude has ended a turn and you’re about to send a new message, you have a decision point.

Overtime we expect that Claude will help you handle this itself, but for now this is one of the ways you can guide Claude's output.

![Image](https://pbs.twimg.com/media/HF-qwt9bEAEa1eq?format=jpg&name=large)

## 通俗精炼（1）

### 2026-04-16 06:58:20

#### 使用 Claude Code 的核心方法：管好会话，才能用好 1M 上下文

##### 一、这篇文章讲什么

文章核心在讲一件事：**Claude Code 好不好用，关键不只是模型强不强，而是你怎么管理上下文（context）和会话（session）**。  
1M 上下文让你能做更长、更复杂的任务，但如果不会管理，也会出现“上下文越长，效果越差”的问题。

##### 二、什么是上下文，为什么会“变笨”

上下文就是模型当前一次性能“看到”的所有内容，包括：系统提示词、聊天记录、工具调用、工具输出、读过的文件等。  
Claude Code 现在支持 **100 万 token**，这意味着它能处理更长链路的任务。

但问题是：**上下文越长，模型注意力越分散**。  
文章把这种现象称为 **context rot（上下文腐化）**——历史信息太多、太杂，会干扰当前任务，导致回答质量下降。

##### 三、每一轮对话后，你其实有 5 个选择

当 Claude 完成一轮任务后，下一步不只有“继续聊”这一种方式，而是有 5 种选择：

###### 1. Continue：继续当前会话
适合任务还没切换、当前上下文仍然有价值的时候。

###### 2. Rewind：回退到之前的节点重来
适合路线走错了，但前面获取的信息仍然有用。  
比起直接说“刚才不对，换个方法”，**回退后重新提示**通常更高效，也更干净。

###### 3. Clear：开启全新会话
适合进入一个新任务。  
原则很简单：**新任务，尽量新会话**。

###### 4. Compact：压缩当前会话
让模型把已有内容总结成更短的版本，再继续。  
优点是省事，缺点是**会丢信息**，因为模型要自己判断哪些内容重要。

###### 5. Subagents：让子代理处理
适合那些会产生大量中间过程、但你最终只关心结论的任务。  
子代理拥有**全新上下文窗口**，做完后只把结果返回，能有效减少主会话污染。

##### 四、什么时候该开新会话

文章给出的经验法则很明确：

**只要进入新任务，就该考虑开新会话。**

不过也有例外：  
如果新任务和刚刚做的事情高度相关，比如“功能刚写完，接着写文档”，保留会话可能更省时间，因为 Claude 不用重新读文件。

所以本质上不是“新开 or 不新开”，而是判断：  
**旧上下文到底是资产，还是负担。**

##### 五、为什么 Rewind 是最值得养成的习惯

作者特别强调：**会用 Rewind，通常说明你很会管理上下文。**

原因是，很多人发现模型尝试错了，会直接在原对话里纠正。  
但这样会把“错误尝试过程”也继续留在上下文里，增加噪音。

更好的方式是：  
**回退到错误发生前，然后带着新认知重新下指令。**  
这样既保留了有效信息，又不会让错误路径持续污染上下文。

##### 六、Compact 和 Clear 的本质区别

这两个动作看起来都像“清理上下文”，但逻辑完全不同：

###### Compact：让模型帮你总结
优点是快、省事，适合你不想手动整理时使用。  
缺点是它是有损压缩，可能漏掉你之后会用到的信息。

###### Clear：你自己定义新的起点
优点是上下文更可控，只保留你认为真正重要的信息。  
缺点是更费精力，需要你主动整理和重述。

一句话概括：  
**Compact 是把“筛选权”交给模型，Clear 是把“筛选权”拿回自己手里。**

##### 七、什么情况下会出现“糟糕的压缩”

文章指出，坏的 compact 往往发生在：  
**模型不知道你接下来要往哪个方向走。**

比如刚经历一大段调试，自动压缩时会重点保留调试内容；  
结果你下一句突然切到另一个 warning，模型可能已经把相关内容丢了。

更麻烦的是，压缩通常发生在上下文已经很长的时候，而这正是模型状态最差的时候。  
所以更好的做法是：

**不要等快满了再被动压缩，而是主动提前 compact，并明确告诉它要保留什么、忽略什么。**

##### 八、子代理最适合什么任务

子代理最适合那些：  
**过程很长、输出很多，但最后你只想要结论** 的工作。

比如：

- 让子代理检查某项实现是否符合规格
- 让子代理研究另一个代码库的认证流程并总结
- 让子代理根据 Git 变更自动写文档

判断标准很简单：  
**你以后还需要那些中间输出吗？如果不需要，只需要结论，就适合交给子代理。**

##### 九、这篇文章的核心结论

Claude Code 的使用体验，本质上是一个 **上下文管理问题**。  
1M 上下文不是让你无脑把所有内容都塞进去，而是让你有更大的操作空间去做更复杂的任务。

真正高效的使用方式是：

- 新任务尽量开新会话
- 走错方向时优先用 Rewind
- 长会话中谨慎使用 Compact
- 想要强控制时用 Clear
- 中间过程噪音很大时用 Subagents

一句话总结：  
**不是上下文越大越好，而是你越会管理上下文，Claude Code 才越强。**

## 结构化（1）

### 2026-04-17 05:43:24

#### 使用 Claude Code 管理会话与 1M 上下文：精炼总结

Claude Code 这次更新的核心，是帮助用户更好理解和管理使用量，尤其是在支持 **100 万 token 上下文窗口**之后，如何通过合理管理会话来提升效果。  
文章重点说明：**同样是和 Claude 协作，是否新开会话、何时压缩、何时回退、何时用子代理，都会显著影响质量、速度和成本。**

##### 1. 为什么“会话管理”变得重要

- 作者提到，和很多客户交流后发现，大家使用 Claude Code 的方式差异很大：
  - 有人长期只开 1~2 个终端会话；
  - 有人每次提问都新开会话；
  - 有人会用 `/compact`、`/rewind`、subagents（子代理）；
  - 也有人遇到过“压缩后效果变差”的情况。
- 这些体验差异，背后几乎都和**上下文窗口管理**有关。
- 随着 Claude Code 支持 **100 万 token 上下文**，虽然可以处理更长、更复杂的任务，但也更需要用户理解如何“控制上下文”。

##### 2. 什么是上下文、压缩和“上下文衰减”

- **上下文窗口**，就是模型在生成下一个回答时，能同时看到的全部内容，包括：
  - 系统提示词；
  - 当前对话历史；
  - 每次工具调用及其输出；
  - 所有已读取的文件。
- Claude Code 的上下文窗口上限是 **1,000,000 token**。
- 但上下文不是越长越好，因为会出现 **上下文衰减（context rot）**：
  - 内容越多，模型注意力会分散；
  - 越早、越无关的信息，越可能干扰当前任务；
  - 结果就是模型表现下降。
- 上下文窗口有**硬上限**，接近上限时就必须把已有工作**总结压缩**成更短描述，再继续任务，这就是 **compaction（压缩）**。
- 用户也可以主动触发压缩，而不是等系统自动处理。

##### 3. 每一轮对话结束后，其实都有 5 种选择

作者强调：当 Claude 完成一轮工作后，下一步并不只有“继续问”这一种选项，而是有多种路径：

- `Continue`：继续在同一个会话里发下一条消息；
- `/rewind`（或双击 `Esc`）：回到之前某条消息，从那里重新开始；
- `/clear`：清空并开启新会话，一般会带上你整理好的简报；
- `Compact`：把当前会话压缩成摘要，再基于摘要继续；
- `Subagents`：把一部分工作交给有独立干净上下文的子代理，只把结果带回来。

关键点是：  
- 最自然的做法通常是直接继续；
- 但后面 4 种，其实都是为了**更好管理上下文**，避免上下文过长、混乱或失真。

##### 4. 什么时候应该新开会话

- 作者给出的经验法则很明确：**只要开始一个新任务，就应该新开一个新会话。**
- 100 万上下文窗口意味着，Claude 现在更适合做**长任务**，例如：
  - 从零开始搭建一个全栈应用。
- 但“能做更长任务”不代表“所有事情都塞进同一个会话最好”。
- 有些任务是相关但不完全相同的，比如：
  - 你刚实现完一个功能；
  - 接着要写这个功能的文档。
- 这时如果开新会话，Claude 需要重新读取刚才的文件，会更慢、成本更高；
- 所以这类“部分上下文仍然有价值”的相关任务，可以考虑继续留在原会话中。

简单理解就是：
- **新任务**：优先新开会话；
- **紧密相关任务**：可以保留当前会话，避免重复读取文件。

##### 5. 出错时，很多时候“回退”比“纠正”更好

作者特别强调一个好习惯：**善用 `/rewind`**。

- 在 Claude Code 中，双击 `Esc` 或输入 `/rewind`，可以回到任意之前的消息；
- 那个节点之后的消息都会被从上下文中移除。
- 为什么它很重要？
  - 因为很多人看到 Claude 方案失败后，会直接说：
    - “这个不行，换 X 试试。”
  - 但更好的做法通常是：
    - 回退到 Claude 刚读完文件、但还没开始走错路的时候；
    - 再重新提示，把新学到的信息明确告诉它。

文章中的例子：
- Claude 读了 **5 个文件**，尝试了一个方案，但没成功；
- 直觉做法是直接说：“不行，改用 X”；
- 更好的做法是回退到“读完文件之后”，然后重新提示：
  - “不要用方案 A，`foo` 模块没有暴露那个能力，直接走方案 B。”

这样做的好处：
- 把错误尝试及其无效过程从上下文中删掉；
- 保留真正有价值的学习结果；
- 让后续推理更干净、更聚焦。

此外，还可以使用 **“summarize from here”**：
- 让 Claude 把失败尝试总结成一段交接说明；
- 相当于“未来的 Claude 给过去的 Claude 留言”，说明哪些路已经试过、为什么不行。

##### 6. `/compact` 和 `/clear` 看起来相似，但本质不同

当一个会话变得很长时，作者说可以用两种方式“减重”：

###### `/compact`：让模型帮你总结
- Claude 会总结当前会话，然后用这份总结替换之前历史；
- 优点：
  - 省事，不需要你手动整理；
  - Claude 可能会比你更全面地保留重要结论、关键文件和学习结果。
- 缺点：
  - 这是**有损压缩**；
  - 你是在相信 Claude 去判断“什么重要”。

还可以加指令引导压缩方向，比如：
- `/compact focus on the auth refactor, drop the test debugging`
- 意思是：重点保留认证重构，丢掉测试调试细节。

###### `/clear`：你自己决定什么最重要
- 你手动写下关键内容，然后从头开始一个新会话；
- 比如：
  - “我们正在重构认证中间件”
  - “约束条件是 X”
  - “重要文件是 A 和 B”
  - “方法 Y 已经被排除”
- 优点：
  - 新上下文里只保留你认为真正相关的信息；
  - 控制力更强。
- 缺点：
  - 更费时间和精力。

可以把两者理解为：
- `/compact`：**让 Claude 替你总结**
- `/clear`：**你亲自重新定义问题**

##### 7. 什么情况下会出现“糟糕的压缩”

作者指出，压缩效果差，往往不是随机发生，而是有典型原因：

- 当模型**无法预测你接下来要往哪个方向继续**时，压缩就容易丢关键信息。
- 文章给了一个具体例子：
  - 你前面花了很长时间在调试某个问题；
  - 自动压缩（autocompact）触发时，自然会把“调试过程”和当前主线总结进去；
  - 但你接下来突然说：
    - “现在去修 `bar.ts` 里我们之前看到的另一个 warning。”
  - 由于之前会话主轴是调试，`bar.ts` 那个 warning 可能根本没被保留进摘要里。
- 这会更麻烦的原因是：
  - 会话越长、越接近上下文上限时，模型其实正处在**最容易受上下文衰减影响**的时候；
  - 也就是说，它恰恰是在“最不聪明”的时候做压缩。

作者给出的建议：
- 有了 **100 万上下文** 后，用户拥有更多缓冲空间；
- 最好在自己知道下一步重点是什么时，**主动提前 `/compact`**；
- 并明确告诉 Claude：
  - 这次压缩要保留什么；
  - 可以丢掉什么。

##### 8. 子代理（Subagents）适合处理“过程很多、结果才重要”的工作

- 子代理本质上也是一种**上下文管理工具**。
- 当你预判某部分工作会产生大量中间输出，而这些过程之后并不需要反复参考时，就适合用子代理。
- 工作方式是：
  - Claude 通过 Agent 工具启动一个子代理；
  - 子代理拥有自己的**全新上下文窗口**；
  - 它可以独立完成大量工作；
  - 最后只把精炼后的结果返回给主会话。

作者提供了一个判断标准：
- 问自己一句：
  - “我之后还需要这些工具输出细节吗，还是只需要结论？”

如果只需要结论，就适合用子代理。

文章中的几个典型例子：

- “启动一个子代理，根据某个 spec 文件验证这次工作的结果。”
- “启动一个子代理，去阅读另一个代码库，总结它是如何实现认证流程的，然后再按同样方式实现。”
- “启动一个子代理，根据我的 git 改动为这个功能写文档。”

这些场景的共同点是：
- 中间过程可能很长；
- 但主会话真正需要的只是**最后总结**；
- 这样可以避免主会话被大量细节“污染”。

##### 9. 文章结论

- 每当 Claude 完成一轮回答、你准备发送下一条消息时，其实都面临一个**上下文管理决策点**。
- 这时候你可以选择继续、回退、新开、压缩，或者交给子代理。
- 作者认为，未来 Claude 会越来越多地自动帮用户处理这些决策；
- 但在当前阶段，用户主动管理这些选择，仍然是**提高 Claude Code 输出质量的重要手段**。

##### 10. 一句话理解全文

- **Claude Code 的 100 万上下文让长任务更可行，但真正决定效果的，不只是“上下文有多大”，而是你是否会在合适的时候新开、回退、压缩，或把任务拆给子代理。**
