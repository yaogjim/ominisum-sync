#### Model Configuration

This page covers the models Kimi Code provides and how to switch between them in each client.

#### Model Overview

Kimi Code currently offers two models—Kimi K3 and Kimi K2.7 Code—across four model IDs, selectable by model ID in clients or third-party tools. Model specs:

Recommended model launch

`k3-256k` is now available. Within 256k context, it delivers the same results. `k3` (1M) consumes about twice as much quota as `k3-256k`. Ideal for everyday Q&amp;A, code completion, routine feature development, and single-file or small-file edits — video input is not supported.

> 💓 Reminder
>
> **Switching from K3 (1M) to K3-256k:** When switching from `k3` (1M) to `k3-256k`, if the current session's context already exceeds 256k, some coding tools such as Kimi Code CLI and Claude Code will perform a compact on the tool side.
>
> Switching recommendations:  
> (1) Because different agent tools handle this differently, manually run compact once before switching to compress the context to within 256k. This preserves the key points of the task, keeps the session intact, and lets you benefit from more durable quota after switching.  
> (2) If the conversation history includes video files, switching directly will fail because K3-256k does not support video input. Please compact first, then switch.
>
> **Switching from K3-256k to K3 (1M):** When switching from `k3-256k` to `k3` (1M), if `k3-256k` is close to the 256k limit and you don't want compact to lose information, you can switch directly to 1M. The current version switching from 256k to 1M does not affect the cache.

Why did usage go up after the new model launched?

After switching models, the context cache built earlier no longer hits on the new model, so that context has to be re-prefilled. Usage therefore looks higher right after switching. Recommended action:

- **Start a new session when using the new model**: this gives better results and lower consumption.

Why do I still get a 401 with the correct model ID?

When the requested capability exceeds your plan's entitlements, the server returns `401`. Three common cases:

- **No K3 access**: your plan is below Moderato and can't call `k3`, `k3-256k` — upgrade to Moderato or above.
- **No 1M access**: on a Moderato plan, `k3` supports up to 256K context; up to 1M context is available on Allegretto and higher tiers. `k3-256k` has a fixed 256K context limit.
- **No HighSpeed access**: some plans don't include HighSpeed — upgrade to Allegretto or a higher tier to call `kimi-for-coding-highspeed`.

For the full error text and how to handle it, see the [Error Reference](https://www.kimi.com/code/docs/en/kimi-code/error-reference.html).

Why isn't HighSpeed noticeably faster?

Two common reasons:

- **Mistyped model ID**: the HighSpeed ID must be `kimi-for-coding-highspeed`; a wrong value silently falls back to the standard `kimi-for-coding` — no error, no speedup.
- **Tools and scripts dominate**: HighSpeed only speeds up **model output**. Tool calls (reading/writing files, running commands, etc.) and script execution are unaffected, so when they take up most of a turn the overall speedup feels small.

How to reduce the overhead of switching reasoning effort?

Switching reasoning effort invalidates the context cache you've built up, so context that would have hit the cache must be re-prefilled. To avoid triggering re-prefill too often:

- Pick an effort that fits the task and keep it consistent within a session;
- When you genuinely need a different effort, start a new session rather than switching back and forth in a long session.

#### How to Switch Models

Usage notes

- **Start a new session when switching model IDs**: switching models invalidates the context cache you've built up. We recommend starting a new session to get the best experience and avoid extra token consumption.
- **Fill in the Model ID, not the model version name**: when calling a model, use one of the Model IDs from the table above (`k3`, `k3-256k`, `kimi-for-coding`, `kimi-for-coding-highspeed`). Entering a model version name like `Kimi K3` or `K2.7 Code` will cause the call to fail.
- **K3 / K2.7 without Thinking routes to K2.6**: keep Thinking on to use K3 or K2.7 Code; disabling thinking routes the request to K2.6.

Ways to switch to the target model:

##### Official clients

- **Official Kimi Code CLI**: type `/model` to switch models—no config changes needed; if the latest model isn't listed yet, `/logout` and sign in again with `/login`.
- **Kimi Code for VS Code**: pick the target model from the dropdown menu in the input bar; if it isn't listed yet, restart VS Code or reinstall the extension.

##### Third-party tools

Set the tool's Model ID to the target model. Detailed steps:

1. Create an API Key in the [Kimi Code Console](https://www.kimi.com/code/console).
2. Fill in the Base URL and the corresponding Model ID in your tool.

Kimi Code API supports both OpenAI and Anthropic protocols. Base URLs:

Protocol Base URL

OpenAI compatible `https://api.kimi.com/coding/v1`

Anthropic compatible `https://api.kimi.com/coding/`

For detailed setup steps, see the corresponding tool guide:

Before using K3 in third-party tools

K3's setup differs slightly from K2.7 Code. Before using it, check the two points below:

- **Context window**: some tools default to a context window smaller than the max 1M—manually set the context-window field to `1048576` to use K3's full up-to-1M context.
- **Reasoning effort**: K3 supports `low` / `high` / `max`; the effort a tool sends is mapped as below:

```
# default
null / undefined       → high
any other unknown       → HTTP 400 error

# → max
ultra / max / xhigh     → max

# → high (recommended)
high / medium           → high

# → low
low / minimum / light   → low

# → thinking disabled
none                    → thinking.type disabled
```

#### Kimi Code 模型配置总结

Kimi Code 目前提供 **Kimi K3** 和 **Kimi K2.7 Code** 两类模型，共对应 4 个模型 ID。用户可以在官方客户端或第三方工具中通过填写模型 ID 来切换模型；不同模型在上下文长度、速度、推理能力、多模态输入和会员等级要求上有所区别。

##### 一、模型概览

| 模型 ID | 对应版本 | 主要特点 | 速度 | 上下文窗口 | 多模态输入 | 可用范围 |
|---|---|---|---|---|---|---|
| `k3` | Kimi K3 | 旗舰编程模型，约 **2.8T 参数**，支持最长 **1M 上下文** | 标准 | 最高 1M；1M 上下文需更高等级会员 | 图片、视频 | Moderato 及以上；Allegretto 及以上可用 1M |
| `k3-256k` | Kimi K3 256K 版 | 在 256K 上下文内效果与 K3 基本一致，消耗更低 | 标准 | 固定 256K | 仅图片 | Moderato 及以上 |
| `kimi-for-coding` | Kimi K2.7 Code | 适合代码补全、日常开发和常规任务 | 标准 | 256K | 图片、视频 | 所有会员 |
| `kimi-for-coding-highspeed` | K2.7 Code HighSpeed | 与 K2.7 Code 编程能力相同，输出约快 **5～6 倍** | 高速；约 **6 倍速度、3 倍额度消耗** | 256K | 图片、视频 | Allegretto 及以上 |

###### 模型选择建议

- **日常问答、代码补全、常规功能开发、单文件或小规模文件修改**：推荐使用 `k3-256k`。
- **需要处理超长上下文或大型代码项目**：使用 `k3`，最高支持 1M 上下文。
- **追求更快输出速度**：使用 `kimi-for-coding-highspeed`，但需要注意额度消耗约为普通版本的 3 倍。
- `k3-256k` **不支持视频输入**。

##### 二、K3 与 K3-256K 的切换注意事项

###### 从 K3（1M）切换到 K3-256K

如果当前会话上下文已经超过 256K，Kimi Code CLI、Claude Code 等工具可能会自动执行 **compact**，即压缩上下文。

官方建议：

1. 切换前手动执行一次 compact，将上下文压缩到 256K 以内。
2. 这样可以保留任务关键内容、维持当前会话，并在切换后获得更持久的额度使用效果。
3. 如果历史记录中包含视频文件，不能直接切换到 `k3-256k`，因为该模型不支持视频输入；应先 compact，再切换。

###### 从 K3-256K 切换到 K3（1M）

如果 `k3-256k` 接近 256K 上限，且担心 compact 会丢失信息，可以直接切换到 `k3`。

当前版本从 256K 切换到 1M **不会影响缓存**。

##### 三、会员等级与权限

不同会员计划会影响：

- 可使用的模型；
- 最大上下文长度；
- 是否支持 HighSpeed；
- 输出速度和额度消耗。

常见权限限制如下：

- **无法使用 K3**：会员等级低于 Moderato，无法调用 `k3` 和 `k3-256k`。
- **无法使用 1M 上下文**：Moderato 用户使用 `k3` 时最多只有 256K 上下文；Allegretto 及更高等级才支持最高 1M。
- **无法使用 HighSpeed**：部分会员计划不包含高速模型，需要升级到 Allegretto 或更高等级。
- `k3-256k` 始终固定为 256K 上下文，不会因会员等级提高而扩展到 1M。

如果请求的模型能力超出当前计划权限，服务端通常会返回 **401**。

##### 四、为什么切换模型后用量会增加？

切换模型后，之前建立的上下文缓存通常无法继续命中，需要重新预填充上下文，因此刚切换时用量看起来会明显上升。

**建议：**

- 使用新模型时直接开启一个新会话；
- 新会话通常能获得更好的效果，并减少额外消耗。

##### 五、HighSpeed 为什么不一定明显更快？

主要有两个原因：

1. **模型 ID 填写错误**  
   HighSpeed 的正确 ID 是：

   ```text
   kimi-for-coding-highspeed
   ```

   如果填写错误，系统可能会静默回退到普通的：

   ```text
   kimi-for-coding
   ```

   此时不会报错，但也不会获得加速效果。

2. **工具调用和脚本执行耗时不受影响**  
   HighSpeed 只会加快模型生成文本的速度，以下操作不会加速：

   - 读取或写入文件；
   - 执行命令；
   - 调用外部工具；
   - 执行脚本。

   如果一次任务的大部分时间都花在这些步骤上，整体速度提升就不会特别明显。

##### 六、推理强度切换的影响

切换 `reasoning_effort` 会使已经建立的上下文缓存失效，原本可以直接命中的上下文需要重新预填充，从而增加消耗和延迟。

建议：

- 根据任务难度选择合适的推理强度，并在同一会话中保持一致；
- 如果确实需要改用另一种推理强度，建议新建会话，而不是在长会话中反复切换。

K3 支持以下推理强度：

```text
low / high / max
```

默认值为：

```text
high
```

##### 七、如何切换模型

###### 1. 官方 Kimi Code CLI

在 CLI 中输入：

```text
/model
```

然后选择目标模型，无需修改配置。

如果最新模型没有出现在列表中：

1. 输入 `/logout` 退出；
2. 再输入 `/login` 重新登录。

###### 2. Kimi Code for VS Code

在输入栏的模型下拉菜单中选择目标模型。

如果模型列表中没有最新模型，可以：

- 重启 VS Code；
- 或重新安装 Kimi Code 扩展。

###### 3. 第三方工具

在第三方工具中设置目标模型的 **Model ID**，基本步骤如下：

1. 在 Kimi Code Console 创建 API Key；
2. 在工具中填写 Base URL；
3. 填写对应的 Model ID。

Kimi Code 同时支持 OpenAI 和 Anthropic 两种协议。

| 协议 | Base URL |
|---|---|
| OpenAI 兼容协议 | `https://api.kimi.com/coding/v1` |
| Anthropic 兼容协议 | `https://api.kimi.com/coding/` |

##### 八、使用模型 ID 时的注意事项

调用模型时必须填写模型 ID，而不是模型版本名称。

###### 正确写法

```text
k3
k3-256k
kimi-for-coding
kimi-for-coding-highspeed
```

###### 错误写法

```text
Kimi K3
K2.7 Code
```

填写版本名称会导致调用失败。

此外，如果使用 K3 或 K2.7 时关闭 Thinking，实际请求会被路由到 **K2.6**。因此，要使用 K3 或 K2.7 Code，应保持 Thinking 开启。

##### 九、在第三方工具中使用 K3 的额外配置

K3 与 K2.7 Code 的配置略有不同，使用前需要重点检查两项设置。

###### 1. 手动设置上下文窗口

部分第三方工具默认的上下文窗口小于 K3 支持的最大值。若希望使用 K3 的完整 1M 上下文，需要手动设置：

```text
context-window = 1048576
```

###### 2. 配置推理强度映射

第三方工具发送的参数会映射为 K3 的 `low`、`high` 或 `max`：

| 工具发送的值 | K3 实际推理强度 |
|---|---|
| `null` / `undefined` | `high`，默认值 |
| `ultra` / `max` / `xhigh` | `max` |
| `high` / `medium` | `high`，推荐 |
| `low` / `minimum` / `light` | `low` |
| `none` | 关闭 Thinking |
| 其他未知值 | 返回 HTTP 400 错误 |

总体而言，第三方工具中建议使用 `high`，并确认工具确实将上下文窗口设置为 `1048576`，这样才能充分发挥 K3 的 1M 上下文能力。

## 口播总结（1）

#### Kimi Code 模型配置概览

这份内容主要讲两件事：Kimi Code 提供哪些模型，以及怎样正确切换和配置这些模型。听完之后，你会知道不同模型适合什么任务、各自需要什么会员等级，以及如何避免切换模型带来的额外消耗和常见报错。

#### 首先，了解四个可用的模型 ID

Kimi Code 目前提供两类模型，也就是 Kimi K3 和 Kimi K2.7 Code。实际使用时，一共有四个可填写的模型 ID。

这里先解释一个概念。“上下文窗口”，指的是模型一次能够处理的对话、代码和文件内容总量。它通常用 token 计算。token 可以简单理解为模型处理文字和代码时使用的基本计量单位。

第一个模型 ID 是小写的“k3”。

它对应 Kimi K3，是目前能力最强的旗舰编程模型，拥有二点八万亿参数。它最高支持一百万 token 的上下文窗口，适合大型代码库、超长对话和复杂开发任务。它支持图片和视频输入，也可以选择低、高、最高三档推理强度，默认是高档。

不过，k3 需要 Moderato 或更高等级的会员。Moderato 用户最多使用二十五万六千 token 的上下文；只有 Allegretto 或更高等级，才能使用完整的一百万 token。

第二个模型 ID 是“k3-256k”。

它也是 Kimi K3，但上下文固定为二十五万六千 token。在这个范围内，它和百万上下文版本能提供相同的结果，但消耗明显更低。百万上下文的 k3，大约会使用 k3-256k 两倍的额度。

因此，官方更推荐把 k3-256k 用于日常问答、代码补全、常规功能开发，以及单个文件或少量文件的修改。需要注意，它只支持图片，不支持视频。

第三个模型 ID 是“kimi-for-coding”。

它对应 Kimi K2.7 Code，擅长代码补全和常规开发任务，上下文窗口是二十五万六千 token，支持图片和视频，所有会员都可以使用。

第四个模型 ID 是“kimi-for-coding-highspeed”。

它是 K2.7 Code 的高速版本，编程能力与标准版相同，但模型输出速度大约快五到六倍。代价是额度消耗约为标准版的三倍，而且需要 Allegretto 或更高等级的会员。

#### 接下来，注意 K3 两种上下文版本之间的切换

如果从百万上下文的 k3，切换到 k3-256k，首先要看当前会话是否已经超过二十五万六千 token。

如果超过了限制，Kimi Code CLI、Claude Code 等编程工具，可能会自动执行一次“compact”。这里的 compact，就是把较长的历史对话压缩成更短的摘要，保留任务的主要信息，让会话能够继续。

不过，不同代理工具处理上下文的方式并不完全一样。官方建议在切换前手动运行一次 compact，先把上下文压缩到二十五万六千 token 以内。这样更容易保留任务重点，也能减少后续额度消耗。

还有一个特殊情况。如果当前对话历史里包含视频文件，不能直接切换到 k3-256k，因为这个模型不支持视频输入。正确做法也是先执行 compact，再进行切换。

反过来，如果从 k3-256k 切换到百万上下文的 k3，就简单得多。特别是当前会话已经接近二十五万六千 token，而你又不希望 compact 导致信息丢失时，可以直接切换到 k3。按照当前版本的机制，从二十五万六千切换到一百万上下文，不会影响已有缓存。

#### 更重要的是，切换模型会影响缓存和额度消耗

这里的“上下文缓存”，可以理解为系统已经处理过、能够重复利用的会话内容。

当你更换模型 ID 后，旧模型建立的缓存无法继续命中新模型。系统必须重新处理前面的上下文，也就是重新预填充。因此，刚切换模型时，使用量看起来可能会突然增加。

官方建议是，切换模型 ID 时尽量开启一个新会话。这样通常能获得更好的效果，也能减少重复处理长上下文带来的额外消耗。

调整推理强度也会产生类似影响。K3 的推理强度包括低、高和最高三档。每次切换强度，都可能让已有缓存失效。

所以，最好根据任务难度选定一个合适的推理档位，并在同一会话中保持不变。如果确实需要换档，与其在长会话里反复调整，不如新建一个会话。

#### 然后，理解常见的 401 权限错误

即使模型 ID 填写正确，只要请求的能力超出了当前会员权益，服务器仍然会返回 401 错误。

常见情况有三种。

第一，没有 K3 使用权限。低于 Moderato 的会员不能调用 k3，也不能调用 k3-256k，需要先升级到 Moderato 或更高等级。

第二，没有一百万上下文权限。Moderato 用户虽然可以调用 k3，但上下文最高只有二十五万六千 token。完整的一百万上下文，需要 Allegretto 或更高等级。至于 k3-256k，它本身就固定在二十五万六千 token，不能扩展到一百万。

第三，没有 HighSpeed 权限。如果当前会员方案不包含高速模型，就不能调用 kimi-for-coding-highspeed。这个模型同样需要 Allegretto 或更高等级。

#### 为什么 HighSpeed 有时感觉不快

HighSpeed 只会加快模型生成内容的速度，并不会加快所有操作。

首先要检查模型 ID 是否完全正确。高速模型必须填写“kimi-for-coding-highspeed”。如果拼写错误，系统可能不会直接报错，而是悄悄退回标准版“kimi-for-coding”。这样自然看不到速度提升。

另一个常见原因，是工具和脚本占用了大部分时间。比如读取文件、写入文件、执行命令或者运行脚本，这些步骤不会因为使用 HighSpeed 而变快。

因此，如果一次任务主要时间都花在外部工具上，即使模型本身输出快了五到六倍，整个任务的体感提升也可能不明显。

#### 如何在官方客户端中切换模型

在官方 Kimi Code CLI 中，可以输入“斜杠 model”命令切换模型，不需要修改配置文件。

如果列表里暂时没有最新模型，可以先输入“斜杠 logout”退出，再使用“斜杠 login”重新登录。

在 Kimi Code 的 VS Code 扩展中，可以从输入栏的下拉菜单里选择目标模型。如果没有看到最新模型，可以重启 VS Code，或者重新安装扩展。

使用时必须填写模型 ID，而不是模型的版本名称。正确写法只能是 k3、k3-256k、kimi-for-coding，或者 kimi-for-coding-highspeed。

如果填写“Kimi K3”或者“K2.7 Code”这样的版本名称，请求会失败。

另外，要保持“Thinking”，也就是思考模式开启。K3 和 K2.7 Code 在关闭思考模式后，请求会被转到 K2.6，而不是继续使用原本选择的模型。

#### 最后，第三方工具需要额外配置

在第三方工具里使用 Kimi Code，首先需要在 Kimi Code 控制台创建 API Key，也就是用于验证调用权限的密钥。

然后，在工具中填写对应的 API 服务地址和准确的模型 ID。Kimi Code API 同时兼容 OpenAI 和 Anthropic 两种协议，具体使用哪一种，取决于第三方工具支持的接口格式。

使用 K3 时，还要特别检查两个配置。

第一个是上下文窗口。有些第三方工具的默认上下文小于 K3 支持的上限。要使用完整的一百万 token，需要手动把“context-window”字段设置为一百零四万八千五百七十六。

第二个是推理强度。K3 支持低、高、最高三档。如果工具没有填写推理强度，默认会使用高档。

工具传入“ultra”“max”或者“xhigh”，会映射到最高档；传入“high”或者“medium”，会映射到高档，也是官方推荐设置；传入“low”“minimum”或者“light”，会映射到低档；传入“none”，则会关闭思考模式。其他无法识别的值，会返回 HTTP 400 错误。

#### 重点回顾

最后，总结五个最值得记住的结论。

第一，日常开发优先考虑 k3-256k。它在二十五万六千 token 范围内与 K3 百万上下文版本效果相同，但后者大约会消耗两倍额度。

第二，只有大型代码库或超长任务真正需要百万上下文。完整的一百万 token 需要 Allegretto 或更高等级会员。

第三，切换模型会让已有上下文缓存失效，可能造成用量突然增加。最稳妥的做法，是切换模型时新建会话。

第四，从百万上下文切换到 k3-256k 前，如果会话过长或包含视频，应先执行 compact。因为 k3-256k 的上下文上限较小，而且不支持视频。

第五，配置时一定要填写准确的模型 ID，并保持思考模式开启。HighSpeed 只加快模型输出，不会加快文件操作、命令执行和脚本运行。

## 深度解读（1）

### 2026-09-18 00:15:30

#### 模型切换不是选档，而是在管理上下文、缓存与系统瓶颈

这份文档表面上只是 Kimi Code 的模型配置说明，真正值得关注的却是：**在编码 Agent 中，“使用哪个模型”已经不是一个孤立选项，而是对上下文状态、缓存成本、工具耗时和会员权限的联合决策。**模型能力差异固然重要，但实际体验往往由这些外围机制决定。

##### 长上下文不是越大越好，而是按需购买的工作空间

K3 的 1M 与 256K 版本，在上下文不超过 256K 时，官方称结果相同，但 1M 版本大约消耗两倍额度。由此看，日常问答、补全、小范围改动默认使用 `k3-256k` 更合理；只有代码库探索、长时间多轮任务或上下文即将溢出时，1M 才真正产生价值。

这修正了一个常见误解：上下文窗口不是模型能力的简单排名，更像一块昂贵的工作内存。它的价值取决于任务是否真的需要同时保留大量信息。若任务本身可以拆分，或者经过 compact 后只需保留关键决策，持续使用 1M 反而是在为闲置容量付费。

但 compact 也不是无损操作。从 1M 切到 256K 时，如果已有上下文超限，工具可能先压缩会话；摘要保住了任务主线，却可能丢掉某个边界条件、失败尝试或隐含约束。因此，一个实用策略是：**可压缩的常规任务用 256K，信息丢失代价高的长任务再扩到 1M，而不是把最大窗口设成永久默认值。**

##### 会话本身正在成为一种有成本的状态

切换模型 ID，甚至切换 reasoning effort，都会使既有上下文缓存失效，导致历史内容重新 prefill，短期额度消耗上升。文档因此建议换模型时新建会话，而不是在同一长会话里反复切换。

这意味着用户看到的“对话”并不只是聊天记录，而是一份已经投入计算成本建立起来的运行状态。保留会话可以延续语义，却不一定能延续缓存；改变配置看似轻量，背后可能相当于重新加载整个工作区。

对 Agent 产品而言，这比单纯展示模型下拉框更重要。理想界面应告诉用户：当前上下文占用多少、切换是否触发重新预填、compact 可能损失什么、预计消耗如何变化。否则用户只能看到“额度突然变快”或“切换后效果变差”，却无法判断原因。

##### 端到端效率不能用模型输出速度代替

K2.7 HighSpeed 的输出约快 5—6 倍，但消耗约为 3 倍；如果一轮任务主要耗在读写文件、运行命令和脚本上，整体速度提升可能并不明显。这里揭示了编码 Agent 的关键指标：**应优化完成任务的总时间和总成本，而不是只比较 token 输出速度。**

文档中的几个配置陷阱进一步说明了这一点：HighSpeed ID 写错会静默回退到普通模型；关闭 Thinking 会路由到 K2.6；权限不足则可能统一表现为 401。用户以为自己在评估新模型，实际上可能根本没有调用到它。

因此，模型平台真正缺少的可能不是更多档位，而是更强的运行可观测性：明确显示实际命中的模型、缓存状态、上下文压缩、工具耗时与额度分解。**当模型逐渐商品化，能否让用户准确理解“这次任务究竟由什么完成、时间和额度花在哪里”，会成为开发者工具体验的重要分水岭。**
