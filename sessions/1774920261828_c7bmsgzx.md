## 正文

**卡颂**

很多程序员的 Skill 数量已经失控了。

今天试了 superpowers，明天又被安利 compound-engineering，后天跟风又装了 gstack，Skill 数量瞬间膨胀到几十个，Skill 之间的跳转、召回逻辑变得无比不稳定。

这是很多人都会经历的，本质原因是：这些框架都是对 Harness Engineering 最佳实践的探索，自身都有亮点（比如 superpowers 的 Skill 编排，compound 的持续学习），但能力又有交集。

当前 Skill 管理工具的思路都是“屏蔽复杂度”（比如启用/停用 某个 Skill），而不是“降低复杂度”。

我当前在实践的方式是：以 superpowers 为基础框架，把其他框架的亮点（比如 compound）合并在基础框架上。当然，合并、测试 Skill 都是通过 Skill 完成的。

这样能控制 Skill 数量的膨胀速度～

## 通俗精炼（1）

### 2026-03-31 01:24:21

#### 很多程序员的 Skill 数量为何会失控

##### 现象：Skill 越装越多，系统却越来越乱

很多程序员在尝试不同 Skill 框架时，容易陷入 “今天装一个、明天换一个” 的状态。结果是 Skill 数量迅速膨胀到几十个，彼此之间的跳转、调用和召回逻辑变得越来越不稳定，最终影响整体效率。

##### 原因：工具在叠加，复杂度却没有真正减少

问题的根源不在于某个框架不好，而在于这些框架本质上都在探索 Harness Engineering 的最佳实践，各自都有亮点，但能力范围又彼此重叠。  
目前大多数 Skill 管理工具的思路是 “隐藏复杂度”，比如通过启用 / 停用 Skill 来管理；但这并没有真正 “减少复杂度”，只是把复杂问题暂时遮住了。

##### 做法：用一个基础框架统一整合能力

作者当前的实践思路是：选定`superpowers`作为基础框架，再把其他框架的优势能力逐步合并进来，比如吸收`compound`的持续学习能力。  
这样不是让多个框架并行存在，而是以一个主框架为核心，统一承接其他能力，从而控制 Skill 的数量增长。

##### 关键点：不是多，而是清晰、不重叠

评论区也给出了一些补充经验：  
核心不是 Skill 数量绝对少，而是每个 Skill 的职责要足够单一、边界清晰，避免多个 Skill 同时命中同一类任务，引发冲突。`superpowers`更适合承担路由和分发角色，而具体 Skill 则应聚焦在窄领域能力上。

##### 一句话总结

**Skill 管理的关键，不是不断增加和开关 Skill，而是用统一框架整合能力、减少重叠，让系统从 “看起来可控” 变成 “真正更简单”。**

## 追问（4）

### 提问 · 2026-03-31 01:24:39

如何 “以 superpowers 为基础框架，把其他框架的亮点（比如 compound）合并在基础框架上。”？

### 回答 · 2026-03-31 01:24:39

可以，核心思路不是 “把多个框架同时跑起来”，而是 “选`superpowers`当唯一运行时，再把其他框架拆成能力模块，逐个嫁接进去”。

**先说结论**
- `superpowers`负责：Skill 注册、路由、编排、执行入口
- `compound`这类框架提供的亮点，拆成若干 “能力层”：持续学习、记忆沉淀、反馈优化、触发策略
- 最终形态不是 “`superpowers + compound`并列”，而是 “带有 compound 能力的`superpowers`”

**怎么合并**
- **保留一个主控层**：只保留`superpowers`作为 Skill 生命周期管理器，所有 Skill 的启停、调用、权限、上下文注入，都从它走
- **抽取对方的亮点，而不是照搬框架**：比如`compound`的持续学习，不要整套接入，而是只抽象出`学习事件采集 -> 经验归纳 -> 规则 / 记忆更新`这条链路
- **把 “框架能力” 改写成 “平台能力”**：例如把`compound`的学习机制改成`superpowers`的一个基础服务，供所有 Skill 共用，而不是某个单独 Skill 私有
- **统一上下文模型**：不同框架常有各自的 prompt、memory、tool schema，合并时先定义一套统一的数据结构，比如：
  - `task_context`
  - `skill_input`
  - `execution_trace`
  - `feedback`
  - `memory_entry`
- **统一触发和路由规则**：不要让两个框架各自决定 “该不该触发某 Skill”，否则一定打架。触发权必须只在`superpowers router`手里

**一个实操拆法**

可以把系统拆成 4 层：

1. **Runtime 层**
- 只用`superpowers`
- 管理 Skill 注册表、依赖关系、执行流程、超时 / 重试、观测日志

2. **Capability 层**
- 把其他框架的优点沉淀成通用能力
- 例如：
  - `learning_service`：记录任务结果、用户修正、成功路径
  - `memory_service`：长期记忆 / 经验案例召回
  - `policy_service`：根据历史效果调整路由策略
  - `eval_service`：自动评估 Skill 输出质量

3. **Skill 层**
- 每个 Skill 只做一件事，比如：
  - 代码修改
  - 测试修复
  - 文档生成
  - 部署诊断
- Skill 不直接实现 “学习系统”，它只上报执行结果和反馈给 Capability 层

4. **Feedback 层**
- 接收用户反馈、任务成功率、回滚情况、二次修改情况
- 决定更新：
  - 哪些触发条件该收紧
  - 哪些 prompt 该优化
  - 哪些 Skill 该合并 / 下线

**拿`compound`的 “持续学习” 举例**

如果你想把它合到`superpowers`，不要理解成 “把 compound 也装进去”，而是做这几件事：

- **采集学习信号**
  - 用户是否接受输出
  - 输出后是否被二次大改
  - 哪个 Skill 命中成功率高
  - 哪类任务经常误触发
- **沉淀成结构化经验**
  - 把成功案例存成`pattern -> preferred_skill -> prompt_variant -> outcome`
  - 把失败案例存成`anti-pattern -> avoid_skill`
- **反哺路由**
  - 下次遇到类似任务时，优先选历史成功的 Skill
  - 对冲突 Skill 增加更严格的前置条件
- **反哺 Skill 内容**
  - 自动调整 Skill 的 system prompt、few-shot、工具顺序
  - 给某些 Skill 增加 “不适用场景” 说明

也就是说，`compound`的价值被你转译成：
`观察 -> 学习 -> 更新策略`
这条链挂在`superpowers`下面，而不是另起一个王国。

**最重要的一步：先做 “能力对照表”**

你可以先列一张表，把各框架的亮点映射出来：

```text
superpowers:
- Skill 编排
- 路由分发
- 生命周期管理

compound:
- 持续学习
- 反馈闭环
- 经验沉淀

gstack / 其他:
- 图式工作流
- 多步依赖控制
- 某类任务模板
```

然后再做第二张表：

```text
保留在 superpowers 核心:
- 路由
- 执行入口
- Skill 注册

改造成平台能力:
- 学习
- 记忆
- 评估
- 策略优化

下沉为普通 Skill:
- 某个特定领域的流程
- 某类工具调用模板
```

这样你就能判断：
哪些是 “框架级能力”，哪些只是 “一个 Skill 就能实现的功能”。

**合并时最容易踩的坑**
- **双路由**：两个系统都在决定调用谁，最后行为不可预测
- **双记忆**：A 有一套 memory，B 也有一套，召回结果互相污染
- **职责重叠**：两个 Skill 都能处理 “写代码 + 修测试”，必然冲突
- **反馈不闭环**：记录了很多日志，但没有真正回写到路由规则和 Skill 配置
- **整框架搬运**：把别人一整套概念全搬进来，复杂度反而更高

**一个更稳的迁移顺序**
1. 先固定`superpowers`为唯一入口
2. 梳理现有 Skill，删掉重叠职责
3. 把其他框架的亮点拆成独立能力模块
4. 先接入 “观测 / 反馈”，不要一开始就做自动学习
5. 等数据稳定后，再让路由策略做半自动优化
6. 最后才考虑自动改写 prompt 或自动合并 Skill

**一个简单判断标准**
如果某个 “亮点” 满足下面任一条件，就应该并入基础框架，而不是保留成另一个框架：
- 多个 Skill 都要用到
- 它影响路由或调度
- 它依赖统一的历史数据
- 它本质上是平台规则，而不是单任务逻辑

反过来，如果只是某个具体任务流程，比如 “部署一个 Python 服务并验证健康检查”，那它更适合作为一个普通 Skill，而不是框架能力。

**你可以把它理解成**
- `superpowers` = 操作系统内核
- `compound`的亮点 = 文件系统 / 调度器 / 学习引擎
- 各种具体 Skill = 应用程序

不是装很多操作系统，而是在一个内核里吸收别人的好机制。

### 回答 · 2026-03-31 01:34:54

可以。我理解你的问题不是 “理念对不对”，而是：

- `superpowers`本身没有天然完整的 “插件 / Skill 治理层”
- 作者说 “以`superpowers`为基础框架，吸收`compound`的持续学习能力、其他框架的亮点”
- 但没说明：第三方 Skill 怎么接、怎么注册、怎么路由、怎么治理、怎么持续演化

所以真正要回答的是一件工程设计问题：

**如何在`superpowers`之上，补出一层 Skill Runtime / Registry / Router / Learning Loop，让它既能托管原生 Skill，也能托管第三方 Skill，并且把`compound`的持续学习变成平台能力。**

我给你一个尽量具体、可落地的实现模型。

**核心原则**
- `superpowers`只做 “唯一运行时内核”
- 第三方框架不直接参与调度，只提供能力或 Skill 适配层
- `compound`的 “持续学习” 不作为另一个平行框架存在，而是作为`superpowers`下的一组平台服务
- 所有 Skill，无论来自`superpowers`、`compound`、`gstack`还是未来别的来源，最终都必须被转换成同一种平台内 Skill 对象

换句话说，最后你不是在运行多个框架，而是在运行一个 “扩展过的`superpowers`平台”。

--------------------------------------------------
**一、先定义目标系统长什么样**
--------------------------------------------------

你可以把整套系统拆成 6 个层次：

1. **Skill Registry**
- 管理所有 Skill 的元数据
- 记录它是谁提供的、版本、输入输出、依赖、触发条件、风险等级、适用场景、禁用场景

2. **Skill Runtime**
- 真正执行 Skill
- 处理超时、重试、并发、回滚、日志、状态流转

3. **Router**
- 决定 “当前任务应该用哪个 Skill”
- 负责冲突消解、优先级排序、候选召回、降级策略

4. **Workflow Orchestrator**
- 处理多 Skill 串联
- 比如：需求分析 -> 代码修改 -> 测试 -> 文档更新

5. **Learning Layer**
- 吸收`compound`的核心价值
- 根据历史执行结果、用户反馈、成功率、纠错情况更新路由策略和 Skill 配置

6. **Adapter Layer**
- 用来接第三方 Skill / 第三方框架
- 把它们包装成统一 Skill 接口

这 6 层里，`superpowers`最适合承担的是：
- Skill Runtime
- Workflow Orchestrator
- 一部分 Router

而缺失的能力，要由你自己补：
- Registry
- Adapter Layer
- Learning Layer
- 更强的治理能力

--------------------------------------------------
**二、最关键的一步：先定义统一 Skill 标准**
--------------------------------------------------

如果没有统一标准，第三方 Skill 永远接不进来，也无法治理。

你需要先定义一个平台级 Skill Manifest。可以理解成每个 Skill 都要交一份 “身份证 + 使用说明 + 运行契约”。

一个 Skill 至少要有这些字段：

```json
{
  "id": "code.refactor.react",
  "name": "React Refactor",
  "provider": "third-party",
  "source_framework": "gstack",
  "version": "1.2.0",
  "description": "Refactor React components safely",
  "input_schema": {},
  "output_schema": {},
  "capabilities": ["code-edit", "react", "refactor"],
  "tags": ["frontend", "safe-edit"],
  "triggers": {
    "intent_keywords": ["refactor", "cleanup", "component split"],
    "file_patterns": ["src/**/*.tsx"],
    "task_types": ["code_modification"]
  },
  "constraints": {
    "requires_tools": ["editor", "test-runner"],
    "forbidden_contexts": ["production-deploy"],
    "max_scope": "medium"
  },
  "routing": {
    "priority": 70,
    "confidence_threshold": 0.65,
    "exclusive_group": "react-edit"
  },
  "learning": {
    "feedback_enabled": true,
    "track_success_rate": true
  }
}
```

这份 manifest 的意义非常大：

- 让原生 Skill 和第三方 Skill 一视同仁
- Router 可以基于元数据做筛选
- Learning Layer 可以基于 Skill ID 持续统计效果
- 平台可以做版本管理、禁用、灰度、回滚

也就是说，**你不是直接管理 Skill 代码，而是先管理 Skill 描述。**

--------------------------------------------------
**三、第三方 Skill 怎么接进来：靠 Adapter，不靠直连**
--------------------------------------------------

这是整件事里最容易被说空的地方。

如果第三方 Skill 来自不同框架，它们的定义方式、调用方式、上下文格式都不一样。不能让 Router 直接理解每种框架，否则系统会越来越乱。

所以必须有一层 Adapter。

**平台内部统一接口**
```ts
interface UnifiedSkill {
  manifest: SkillManifest;
  canHandle (context: TaskContext): Promise<MatchResult>;
  execute (context: TaskContext): Promise<SkillResult>;
  evaluate?(result: SkillResult, feedback: UserFeedback): Promise<EvalResult>;
}
```

然后针对不同来源，做不同 Adapter：

- `SuperpowersSkillAdapter`
- `CompoundSkillAdapter`
- `GstackSkillAdapter`
- `CliWorkflowAdapter`
- `PromptTemplateAdapter`

每个 Adapter 的职责是：
- 读取第三方 Skill 的定义
- 转换成统一 manifest
- 把第三方调用方式包装成统一`execute`
- 把第三方的中间日志映射成平台统一 trace

比如：
- 某个`gstack` Skill 是图节点流程，你就把它包装成一个可执行 Skill
- 某个`compound` Skill 有自己的一套 memory 读写方式，你就拦截掉，改接平台 Memory API
- 某个第三方 Skill 只是一段 prompt + tool sequence，也能包装进统一接口

这一步的本质是：

**所有第三方 Skill 先 “去框架化”，再 “平台化”。**

--------------------------------------------------
**四、Superpower 作为基础框架，到底负责什么**
--------------------------------------------------

如果你要让`superpowers`成为底座，它不能只是 “一个装 Skill 的地方”，而必须承担固定角色。

建议这样分工：

**1. 注册**
- 启动时扫描 Skill manifest
- 把 Skill 加入 Registry
- 校验 schema、依赖、版本兼容性
- 决定是否启用、灰度、停用

**2. 路由**
- 接收用户任务
- 分析意图、上下文、文件范围、风险等级
- 找出候选 Skill
- 做排序、冲突消解
- 选定一个或一组 Skill

**3. 编排**
- 如果任务需要多个 Skill 协作，由`superpowers`负责串起来
- 例如先让 “代码理解 Skill” 构建上下文，再让 “修改 Skill” 执行，再让 “测试 Skill” 验证

**4. 执行控制**
- 提供统一的运行环境
- 管理 tool access、超时、并发、重试、缓存

**5. 观测**
- 记录每次 Skill 的输入摘要、命中原因、执行路径、输出质量、用户反馈

你可以理解为：

**`superpowers`不是 Skill 的集合，而是 Skill 的操作系统。**

--------------------------------------------------
**五、怎么做 Skill 管理，而不是只是启用 / 停用**
--------------------------------------------------

这正是作者那句话的重点：很多工具是在 “屏蔽复杂度”，不是 “降低复杂度”。

真正的 Skill 管理，不是一个开关面板，而是一套治理机制。至少要有这几类管理能力。

**1. 分类管理**
不要按来源分，而要按职责分：
- `analysis`
- `codegen`
- `refactor`
- `test`
- `deploy`
- `ops`
- `docs`

这样第三方 Skill 进来以后，不会因为 “它来自`gstack`” 就单独一类，而是被放入职责体系。

**2. 能力边界管理**
每个 Skill 必须声明：
- 它能做什么
- 它不能做什么
- 它和谁冲突
- 它适用于多大范围

例如：
- Skill A：只处理单文件重构
- Skill B：只处理跨模块迁移
- Skill C：只做测试补齐

这比 “都能改代码” 强得多。

**3. 冲突管理**
给 Skill 加几个治理字段：
- `exclusive_group`
- `priority`
- `scope_limit`
- `risk_level`
- `cooldown_policy`

举个例子：
- 两个 Skill 都属于`react-edit`
- 那 Router 同一轮只允许选一个
- 或者先选高置信度的一个，失败后再降级到另一个

**4. 生命周期管理**
每个 Skill 都要有状态：
- `draft`
- `testing`
- `active`
- `canary`
- `deprecated`
- `disabled`

这很重要，因为未来 Skill 会越来越多，不可能都长期`active`。

**5. 版本管理**
同一个 Skill 允许多版本存在：
- `react.refactor@1`
- `react.refactor@2`

Router 可以通过策略控制：
- 新任务 10% 流量给 v2
- 出问题自动回退 v1

这才是真正的平台治理。

--------------------------------------------------
**六、Compound 的持续学习怎么接进来**
--------------------------------------------------

这里是整件事最有价值的部分。

`compound`的亮点一般不是某个具体 Skill，而是：
- 从执行中学习
- 从反馈中修正
- 从历史中优化下一次选择

所以它不该作为 Skill 接进去，而应该作为平台的 Learning Layer。

你可以把持续学习拆成 4 个服务。

**1. Event Collector**
收集所有运行事件：
- 用户任务是什么
- Router 为什么选了这个 Skill
- Skill 输出结果如何
- 用户是否接受
- 后续是否重写 / 回滚 / 追问
- 最终是否成功完成

例子：
```json
{
  "task_id": "t_1001",
  "skill_id": "code.refactor.react",
  "routing_reason": ["tag_match", "historical_success"],
  "result": "partial_success",
  "user_feedback": "accepted_with_edits",
  "followup_actions": ["manual_fix_test"],
  "timestamp": "..."
}
```

**2. Experience Store**
把事件变成经验样本：
- 什么任务类型适合哪个 Skill
- 哪些上下文下容易误触发
- 哪些 Skill 组合成功率高
- 哪些 prompt 版本效果更好

这部分不是原始日志，而是可用于优化的结构化经验。

**3. Policy Learner**
根据经验更新路由策略，比如：
- 提高某 Skill 在某任务类别下的优先级
- 降低某 Skill 在高风险上下文下的可选性
- 给某些冲突 Skill 增加更严格的触发门槛
- 更新 workflow 推荐链路

**4. Config Writer**
把学习结果真正落回平台配置：
- 更新 manifest 中的触发权重
- 更新 Router 的排序参数
- 更新某个 Skill 的禁用条件
- 更新推荐 Skill 组合

这样，“持续学习” 才不是一句空话，而是形成闭环：

**执行 -> 采集 -> 归因 -> 更新策略 -> 下一次路由更准**

--------------------------------------------------
**七、一个可落地的 Router 设计**
--------------------------------------------------

如果没有 Router，Skill 数量一多必乱。

建议 Router 用 “四阶段” 决策，而不是一次拍脑袋。

**阶段 1：粗召回**
根据这些信息找候选 Skill：
- 任务意图
- 当前文件类型
- 仓库结构
- 用户显式指令
- 权限 / 风险级别

例如任务是 “拆一个 React 大组件并补测试”，候选可能是：
- `react.refactor`
- `component.extract`
- `unit-test.generate`

**阶段 2：规则过滤**
按硬条件排除：
- 当前仓库不是前端项目
- Skill 需要的工具不存在
- Skill 处理范围超过当前任务规模
- Skill 被禁用或处于 canary 外

**阶段 3：评分排序**
每个候选 Skill 都算一个分数：

```text
score =
0.30 * intent_match
+ 0.20 * context_match
+ 0.20 * historical_success
+ 0.15 * recent_feedback
+ 0.10 * cost_efficiency
- 0.15 * conflict_penalty
- 0.10 * risk_penalty
```

这样`compound`的持续学习就体现在：
- `historical_success`
- `recent_feedback`

**阶段 4：冲突消解**
如果多个 Skill 很接近：
- 同`exclusive_group`只保留一个
- 高风险任务优先保守 Skill
- 新 Skill 只能在低风险场景试运行
- 必要时进入多阶段编排，而不是只选单 Skill

--------------------------------------------------
**八、第三方 Skill 的接入流程，应该标准化**
--------------------------------------------------

未来还有更多 Skill 进来，所以不能靠手工 “看着接”。

建议你定义一个 Skill Onboarding Pipeline：

**第 1 步：导入**
- 读取第三方 Skill 定义
- 自动生成基础 manifest
- 指定来源框架和适配器

**第 2 步：规范化**
- 统一输入输出 schema
- 统一标签、能力名、任务类型
- 检查是否与现有 Skill 职责重叠

**第 3 步：沙箱测试**
- 用一组标准任务集评估这个 Skill
- 测成功率、稳定性、耗时、误触发率

**第 4 步：灰度发布**
- 先只在少数任务类型下可用
- 或者只作为备选 Skill，不直接主选

**第 5 步：持续观测**
- 看是否比现有 Skill 表现更好
- 如果没有明显提升，就不升为 active

这样，新增 Skill 不再是 “装进去”，而是 “走平台准入流程”。

--------------------------------------------------
**九、如何吸收 gstack /graph workflow 这类框架**
--------------------------------------------------

像`gstack`或基于图的 workflow，本质上提供的是：
- 更强的多步依赖控制
- 分支条件
- 节点复用
- 明确状态机

这类能力不要把它当作 “另一个大框架和`superpowers`平级运行”。

更合理的方式有两种：

**方式 A：把图流程当作高级 Skill**
- 一个图工作流本身包装成单个 Skill
- 比如`frontend.big-refactor.workflow`
- `superpowers`只把它当一个可执行单元

适合：
- 图流程比较独立
- 不想侵入底层 Runtime

**方式 B：把图执行器接入 Orchestrator**
- `superpowers`仍是主入口
- 当某类任务需要复杂流程时，调用 graph orchestrator 作为子编排器

适合：
- 你想让图能力成为平台级编排手段
- 而不是某个 Skill 私有能力

简单说：
- “图” 如果是任务模板，就作为 Skill
- “图” 如果是通用编排能力，就作为 Orchestrator 插件

你现在的想法本质上是：

- 不去深改`superpowers`
- 不去做一个很重的统一运行时
- 而是做一个 “管理 Skill 的 Skill”
- 这个 Skill 负责：
  - 维护一套接入规范
  - 在需要时加载 / 选择 / 包装其他 Skill

  - 把`compound`这类框架的优点转成可调用的能力

这个方向是成立的。它比 “造平台” 更轻，且更符合 AI Agent 生态的现实：很多时候你并不能真正控制底层，只能通过上下文、配置、工具调用和 Skill 约定，去 “软管理” 其他 Skill。

**先给结论**
- 可以把最终产物设计成一个上层的 “Skill Governor” 或 “Skill Manager” Skill
- 它本身不是替代`superpowers`，而是跑在`superpowers`之上，借它做基础编排
- `compound`不是整框架接入，而是把它的 “持续学习” 拆成若干规则、记忆文件、经验模板，供这个管理 Skill 使用
- 其他第三方 Skill 不要求一开始都变成统一原生格式，而是先通过一个轻量 manifest + adapter 规范被 “托管”
- 所以你最终交付的，确实可以只是 “一组 Skill”，而不是一个庞大系统

这就从 “平台工程” 变成了 “元 Skill 工程”。

**这个模型怎么理解**
你可以把它理解成三层：

- **底层**：`superpowers`
  - 已有的 Skill 运行 / 编排能力
  - 不深改，尽量当现成底座用
- **中层**：`skill-manager`这类元 Skill
  - 负责登记、选择、冲突检查、加载策略、调用规则
- **上层**：各种业务 Skill / 第三方 Skill
  - `compound`相关 Skill
  - `gstack`相关 Skill
  - 未来别的 Skill

也就是说，不是 “拿`superpowers`去统一所有框架”，而是：

**用一个更高层的 Skill，来调度和约束其他 Skill；`superpowers`只是这个管理 Skill 依赖的底层能力之一。**

这就简单很多。

**这套方案里，最重要的不是 adapter，而是 “托管协议”**
你不必一开始做很重的适配器系统。你只要先定义一个足够轻的托管协议，让任何第三方 Skill 先能被登记和被选择。

比如每个 Skill 只先补这几项信息：

```yaml
id: compound.memory.learn

source: compound
purpose: 从任务执行中提炼经验
inputs:
  - task_summary
  - execution_result
  - user_feedback

  - memory_note
when_to_use:
  - 任务完成后
  - 出现用户修正时
not_when:
  - 纯闲聊
  - 无明确任务结果

  - another-learning-skill

  entry: compound.memory.learn

- 它知道这个 Skill 是干嘛的
- 它知道什么时候该调用
- 它知道和谁冲突
- 它知道调用入口是什么

这已经能管理了，不需要先把所有底层执行都统一掉。

**所以你的最终产物，比较像这 3 类 Skill**

**1. `skill-registry`**
负责登记和查询 Skill。

它做的事：
- 扫描你维护的 Skill 清单
- 记录每个 Skill 的用途、触发条件、依赖、冲突项
- 提供 “当前有哪些 Skill 可用” 的能力

它本质上是一本 “Skill 通讯录”。

**2. `skill-router`**
负责决定该用谁。

它做的事：
- 读取当前任务
- 从 registry 里找候选 Skill
- 按规则过滤冲突
- 选出一个或多个最合适的 Skill
- 决定是直接调用，还是走多步流程

它本质上是 “路由脑”。

**3. `skill-learner`**
负责吸收`compound`的持续学习思想。

它做的事：
- 在每次任务后记录：
  - 调用了谁
  - 成没成功
  - 用户有没有改
  - 哪个环节出错
- 把这些结果写成经验
- 下次给 router 提供偏好建议

它本质上是 “经验回路”。

这 3 个其实都可以是 Skill，而不必是框架模块。

- 不需要重写`superpowers`核心
- 不需要一开始统一所有 Skill 的运行时
- 不需要一开始做很重的 adapter framework
- 不需要把所有第三方 Skill 都改造成原生实现

你只需要做到：

- 先能 “描述” Skill
- 再能 “选择” Skill
- 最后能 “记住” Skill 的效果

这已经能跑起来了。

**这里的关键变化是：从 “管理执行” 变成 “管理决策”**
你前面觉得复杂，是因为我前一个方案更像在做操作系统，要统一执行模型。

而你现在这个方案更聪明，它只管：
- 谁能用
- 什么时候用
- 用完效果怎样
- 下次优先谁

- Claude Code 的上下文机制
- `superpowers`已有编排能力
- 第三方 Skill 自己的调用逻辑

**第 1 级：声明式接入**

- 触发条件
- 冲突项

**第 2 级：包装式接入**
适合第三方 Skill 调用方式有点特殊，但还能通过 prompt /command/tool 包一层。

这就是轻 adapter。

**第 3 级：隔离式接入**
适合很复杂的第三方框架，比如它自己有流程控制、记忆、子任务树。

不要把它拆开，直接把它当成 “一个黑盒大 Skill” 接入。
也就是：
- 对平台来说，它只是一个高级 Skill
- 只有在特定场景下才选它

这样就避免了深度整合。

这个分层非常重要，因为它让你可以按成本接入，而不是所有 Skill 一刀切。

**所以可以有一个很现实的最小方案**
如果你现在就要做，不追求完美，我建议最小实现只做这些。

**第一步：做一个 Skill 清单**
先别写复杂系统，只维护一份 registry 文件。

例如：

```yaml
skills:
  - id: superpowers.router
    source: superpowers
    role: orchestration
    when_to_use: ["multi-step tasks", "broad tasks"]

  - id: compound.learn
    source: compound
    role: learning
    when_to_use: ["after task completed", "after user correction"]

  - id: gstack.workflow.frontend
    source: gstack
    role: graph_workflow
    when_to_use: ["complex frontend refactor"]
```

**第二步：做一个`skill-router` Skill**
它接收一个任务，按规则输出：
- 推荐调用哪个 Skill
- 为什么
- 是否冲突
- 是否需要串联多个 Skill

**第三步：做一个`skill-learner` Skill**
每次任务后写经验记录。

**第四步：做少量 wrapper**
只给最常用的第三方 Skill 补 wrapper，不要全量搞。

做到这里，其实你已经拥有一个 “Skill 管 Skill” 的系统了。

**这个系统长什么样**
最终可能不是一个 Skill，而是一组很薄的 Skill：

- `skill-manager`
- `skill-router`
- `skill-registry`
- `skill-learner`
- `skill-adapter-basic`

这些 Skill 自己也属于 Skill 系统的一部分。

这就形成了你说的那种递归结构：
- 用 Skill 管理 Skill
- 用 Skill 接入 Skill
- 用 Skill 学习 Skill 的使用效果

这个想法是通的，而且很符合 Agent 生态。

**它的真正价值在于：你不用统一底层，只统一 “使用协议”**
这是最关键的一句话。

因为现实里：
- 你控制不了所有 Skill 的实现
- 你也不可能要求所有第三方都遵守同一运行时
- 但你可以要求：凡是要接进你的工作流，就至少提供一份统一描述，并接受你的调用约束

这就够了。

**不过要提醒你一个边界**
这种方式虽然轻，但它有一个天然限制：

- 它擅长 “治理” 和 “协调”
- 不擅长强控制底层执行

也就是说，它更像：
- 软路由
- 软规范
- 软记忆
- 软编排

如果某个第三方 Skill 本身特别封闭、特别强势，有自己完整路由和记忆体系，那你的管理 Skill 只能把它当黑盒，不能真的彻底纳管。

但这通常已经够用了，因为你要解决的主要问题，本来也不是 “完美统一执行”，而是：
- Skill 太多
- 不知道用谁
- 经常冲突
- 经验留不下来

而你这个方案正好解决的是这四个问题。

**我给你一个更贴近你想法的定义**
你要做的东西，不是 “新的 superpowers 平台”，而是：

**一个托管型元 Skill 套件。**

它有 4 个职责：
- 托管 Skill 元信息
- 决策 Skill 选择
- 记录 Skill 经验
- 包装 Skill 接入

这比 “平台化重构” 轻得多，也更适合先落地。

**一、Skill Manifest 草案**

建议先用 YAML，方便人读、人改，也适合后续让 Skill 自己维护。

一个最小但够用的 manifest 结构如下：

```yaml
id: superpowers.react.refactor
name: React Refactor
source:
  framework: superpowers
  provider: native
version: 1.0.0
status: active

purpose: >
  对 React 组件做中小规模重构，保持行为不变，优先最小修改。

capabilities:
  - code_edit
  - react
  - refactor
  - frontend

inputs:
  task_types:
    - code_modification
    - refactor
  file_patterns:
    - "src/**/*.tsx"
    - "src/**/*.ts"
  keywords:
    - refactor
    - cleanup
    - split component
    - simplify component

outputs:
  artifacts:
    - code_patch
    - refactor_summary
  guarantees:
    - minimal_scope_change
    - preserve_behavior

constraints:
  scope:
    min: single_file
    max: medium_module
  forbidden:
    - deployment
    - infra_change
  requires:
    tools:
      - editor
  risk_level: medium

routing:
  priority: 80
  confidence_threshold: 0.7
  exclusive_group: react_edit
  fallback_to:
    - generic.codegen
  prefer_when:
    - task mentions React component structure
    - user requests safe refactor
  avoid_when:
    - task is architecture redesign
    - task spans multiple services

learning:
  enabled: true
  track:
    - acceptance
    - rework
    - followup_fix
    - completion

invoke:
  mode: skill
  entry: superpowers.react.refactor
```

这个结构里最重要的是 7 块：

- `id`：唯一标识
- `purpose`：它到底做什么
- `capabilities`：能力标签
- `inputs`：什么任务会命中它
- `constraints`：什么情况下不能用
- `routing`：路由时怎么排序、和谁冲突、失败后找谁兜底
- `invoke`：最后怎么调用它

preferences:
  - task_pattern: react component refactor
    prefer:
      - superpowers.react.refactor
    avoid:
      - generic.codegen

    avoid: []
    reason: >
      Better decomposition and clearer delegation.
    confidence: high
```

也就是说：

- `experience.yaml`是原始经验
- `policies.yaml`是学习后提炼出的路由偏好

**四、Router Prompt 草案**

这个 prompt 的目标不是直接做所有事，而是完成一件非常明确的事：

**根据当前任务 + Skill manifest + 经验策略，选出本次最适合的 Skill 或 Skill 组合。**

建议把它写成系统提示词或 Skill 提示词。

```md
你是 Skill Router，负责在当前任务中选择最合适的 Skill。

你的目标：
1. 根据用户任务、当前上下文、可用 Skill manifest、历史经验 policies，选择最合适的 Skill。
2. 优先减少冲突、减少重复调用、减少过度使用泛化 Skill。
3. 如果一个任务明显需要多个阶段，输出一个简短的多 Skill 执行顺序。
4. 不要因为某个 Skill 来源于某个框架就优先它；只根据适用性、边界、风险、经验来决策。
5. 如果没有明显合适的 Skill，返回最保守的兜底选择，并说明风险。

输入材料：
- 当前任务说明
- 当前仓库 / 文件上下文
- 可用 Skill manifests
- 当前 routing policies
- 最近经验摘要（如有）

路由规则：
1. 先识别任务类型：
   - single narrow action
   - code modification
   - refactor
   - debugging
   - documentation
   - deployment
   - broad multi-step task
2. 先过滤明显不适用的 Skill：
   - 超出 scope
   - 命中 forbidden 场景
   - 需要的工具不可用
   - status 不是 active 或 canary
3. 如果多个 Skill 属于同一 exclusive_group，只保留最适合的一个。
4. 优先选：
   - purpose 与任务最匹配的 Skill
   - constraints 最清晰的 Skill
   - policies 明确 prefer 的 Skill
   - 历史上 rework 更低的 Skill
5. 降低以下 Skill 的优先级：
   - 边界模糊的泛化 Skill
   - 在类似任务中经常需要返工的 Skill
   - 风险等级高但本次任务不需要的 Skill
6. 当任务需要多个 Skill 时：
   - 先选 orchestrator 或明确给出顺序
   - 顺序应从分析 / 规划 -> 执行 -> 验证 -> 学习
7. 除非必要，不要同时选择多个职责重叠的执行 Skill。

输出格式：
```yaml
decision:
  route_type: single | multi_step
  selected_skills:
    - id: ""
      reason: ""
      confidence: high | medium | low
  rejected_skills:
    - id: ""
      reason: ""
  execution_order:
    - ""
  risks:
    - ""
  fallback:
    - ""
```

决策要求：
- 理由必须引用 manifest 中的 purpose /constraints/routing /policies
- 理由要简洁，不要空泛
- 如果推荐多 Skill，必须说明每一步为什么需要它
- 如果没有足够信息，明确指出缺失信息，不要假装确定
```

**六、Learner Prompt 草案**

这个 prompt 的目标是：

**任务完成后，读取本次执行情况，生成结构化经验，并提炼出是否要更新路由偏好。**

```md
你是 Skill Learner，负责在任务结束后总结这次 Skill 使用的经验，并提出后续路由优化建议。

你的目标：
1. 从这次任务中提炼事实经验，而不是泛泛总结。
2. 判断这次选择的 Skill 是否合适。
3. 识别是否存在误路由、职责重叠、返工过多、风险过高等问题。
4. 产出两类结果：
   - 一条或多条 experience record
   - 是否建议更新 routing policy

输入材料：
- 原始任务
- Router 决策结果
- 实际调用的 Skill
- 执行结果
- 用户反馈
- 后续修正 / 返工情况
- 现有 experience /policies（可选）

分析规则：
1. 先判断任务结果：
   - success
   - partial_success
   - failure
2. 再判断用户接受度：
   - accepted_without_edits
   - accepted_with_minor_edits
   - accepted_with_major_edits
   - rejected
3. 识别返工信号：
   - 是否改调其他 Skill
   - 是否大量手工修复
   - 是否补做测试 / 文档 / 验证
4. 判断当前 Skill 的适配度：
   - 非常合适
   - 可用但不是最佳
   - 不适合
5. 如果发现以下情况，提出 policy update：
   - 同类任务中某 Skill 稳定表现更好
   - 某 Skill 经常误触发
   - 某组 Skill 经常冲突
   - 某个高风险 Skill 被用于低风险简单任务
6. 不要因为单次样本就做过强结论；如果证据不足，输出 low confidence 建议。

输出格式：
```yaml
experience_records:
  - task_pattern: ""
    selected_skill: ""
    outcome: success | partial_success | failure
    acceptance: accepted_without_edits | accepted_with_minor_edits | accepted_with_major_edits | rejected
    followup_actions: []
    notes: ""
    confidence: high | medium | low

policy_updates:
  - action: prefer | avoid | tighten_scope | lower_priority | raise_priority | add_fallback
    task_pattern: ""
    skill_id: ""
    reason: ""
    confidence: high | medium | low

diagnostics:
  routing_fit: good | acceptable | poor
  overlap_detected: true | false
  conflict_detected: true | false
  comments:
    - ""
```

要求：
- notes 必须是可复用经验，不能只是复述任务
- policy_updates 只有在证据足够时才输出
- 如果没有明确更新建议，policy_updates 返回空数组
```
