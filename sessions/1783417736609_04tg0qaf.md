## 分析要点

- **核心高价值点**：把 Spec 定义为 AI Agent 的执行协议，强调约束、边界和验收标准比单纯描述需求更重要。
- **留存建议**：长期保留（包含可复用的 Spec 五要素框架和可直接落地的 CLAUDE.md/AGENTS.md 起步方法，适合作为 AI 编程协作规范参考。）

**知识要点**

- 高质量 Spec 应包含目标、约束、边界、验收标准和技术上下文五个核心要素。
- Spec 不是 PRD、技术设计文档或用户故事，而是面向执行的软件行为约束与验证标准。
- 明确“不做什么”可以防止 AI Agent 基于训练数据自行扩展功能范围。
- 验收标准应尽量可测试，使 Agent 能通过测试、截图对比或 lint 结果自我验证。
- CLAUDE.md 或 AGENTS.md 可作为项目级长期记忆，承载技术栈、命令、结构和关键约束。

**行动项**

- 在项目根目录创建 CLAUDE.md 或 AGENTS.md，写入项目说明、技术栈和 1-3 条关键约束。
- 让 AI 扫描代码库并补充常用命令、项目结构、测试方式和代码风格，再人工 review。
- 为下一个新功能按目标、约束、边界、验收标准、技术上下文五要素写一页 Spec。
- 在使用 Claude Code、Cursor 或 Copilot 前先进行计划审查，确认文档层对齐后再执行代码修改。

### #5 写好一份 Spec 的实战手册

> 📌 本文是「AI 时代的编码新范式」系列的第 5 篇。全系列共 9 篇，基于 43 篇行业文献、学术论文与一线实践报告，探讨 Spec-Driven Development 如何在 AI Agent 时代从边缘实践变为工程的基础设施。每篇可独立阅读。前四篇解决了「为什么需要 spec」（第 1 篇）、「spec 的角色变了」（第 2 篇）、「spec 让任务变快」（第 3 篇）、「spec 是 Agent 的外部记忆」（第 4 篇）。本篇回答最后一个问题：spec 到底怎么写。

你已经相信 spec 重要了。

你读完了前四篇。你被注册页面那个黄色警告框说服了——口喷需求会把理解成本后移到 debug 阶段。你知道了 spec 是 Agent 的执行协议，不是给人看的说明书。你甚至理解了 Anthropic 那套三文件记忆系统。

然后你打开了一个空的 Markdown 文件。

光标在闪烁。

你开始想：写多长？用什么格式？要不要画 UML 图？要不要写用户故事？要不要像公司里的 PRD 那样搞个模板？你翻了翻网上那些 spec 示例——有的像 RFC 长达几十页，有的只有三行。你不知道该学哪个。

于是你关掉了文件，决定「下次再写」。

这个「下次」通常不会来。

#### Spec 不是什么

在告诉你怎么写之前，先说清楚它不是什么。大多数人的「不会写 spec」，其实是「把 spec 当成了别的东西」。

它不是 PRD。 产品需求文档回答的问题是「用户想要什么」——目标用户是谁，使用场景是什么，业务价值在哪里。这些问题很重要，但它们是给人看的。Agent 不需要理解「用户痛点」——它需要理解「接口长什么样，输入什么，输出什么，什么不能做」。PRD 说「用户需要一个安全的注册流程」，spec 说「密码用 bcrypt 存储，cost factor ≥ 10，错误提示不区分用户不存在和密码错误」。前者是产品判断，后者是执行约束。

Thoughtworks 在 2025 年的行业分析里给了一个更精确的技术定义：spec 应当显式定义目标软件的外部行为——输入输出映射、前置条件与后置条件、不变量、约束、接口类型、集成契约、状态机。不是「描述业务需求」，是「定义软件行为」。

它不是技术设计文档。 技术设计回答的是「架构怎么搭」——用什么数据库，怎么分微服务，消息队列选 Kafka 还是 RabbitMQ。spec 不关心这些。spec 关心的是「功能怎么实现」——这个 API 接受什么参数，返回什么状态码，异常时怎么处理。Addy Osmani 在他的 spec 方法论里说了一句到位的话：高层 spec 应该聚焦于 what 和 why，而不是 how——至少在最初阶段如此。架构决策是 how，那是 Agent 在实现阶段自己会做的事。你只需要告诉它 what 和 why。

它不是用户故事。 用户故事的经典格式是「作为一个用户，我想要上传文件，以便分享给同事」。它只有意图。但 Agent 需要的不只是意图——它需要约束（文件大小限制、类型白名单）、边界（本期不做断点续传）、验收标准（上传成功后文件出现在列表中、超时返回明确错误）。用户故事是 spec 的起点，不是 spec 本身。

Amazon 有一个产品方法论叫 Working Backwards——在开始做任何东西之前，先写一份「如果这个产品已经做完了，新闻稿会长什么样」。这不是 spec，但它给了 spec 一个正确的起点：从结果倒推。先想清楚「做完了是什么样」，再想「需要满足什么条件才能做到那个样子」。第 1 篇里那份注册功能 spec 就是这个思路——它不是从「用户需要一个注册页面」开始的，是从「一个安全的注册流程应该满足什么条件」倒推出来的。

#### Spec 的五要素

澄清了误解之后，正面回答：一份合格的 spec 包含什么。

GitHub 官方博客上一篇被广泛引用的分析——作者 Matt Nigh 读取了超过 2500 个 agents.md 文件——发现最有效的 spec 都覆盖了六个领域：命令、测试、项目结构、代码风格、Git 工作流、边界。其中「永远不要提交密钥」是出现频率最高的一条单条约束。

把这个结论跟 Addy Osmani 的方法论、Thoughtworks 的技术定义、以及第 1 篇的注册页面 spec 交叉对照之后，可以提炼出五个核心要素。一、目标。 这个功能解决什么问题，为谁解决。不需要长篇大论——一两句话说清楚就够了。AWS 的 Prescriptive Guidance 把这个原则叫做「Start with why」：先说为什么做，再说做什么。Agent 需要知道目标才能在不偏离方向的前提下自己做细节决策。如果目标模糊——「优化一下这个页面」——Agent 没有方向锚点，它的每一个选择都是随机的。

二、约束。 绝对不能做什么，必须遵守什么规则。这是 spec 最区别于用户故事的部分。约束分两类：安全约束（密码哈希、输入验证、不暴露用户数据）和工程约束（不用某个已废弃的 API、遵循现有的错误处理模式、不引入新依赖）。GitHub 那个 2500 文件研究里，「不要碰什么」比「要做什么」更值得重视——「永远不要提交密钥」是出现频率最高的单条约束。

三、边界。 输入输出的范围、依赖关系、以及——同样重要的——明确不做什么。第 1 篇的注册 spec 里有一节叫「明确不做（本期）」：不发送验证邮件，不做社交登录，不做 CAPTCHA。这三条看起来像是「没什么可写了凑数的」，但它们的作用是防止 Agent 自作主张扩展功能。Agent 有一种天然的倾向：它看到「注册」就会联想到「邮箱验证」「密码强度检测」「登录频率限制」——这些都是训练数据里注册功能的常见配套。如果你不明确说「不做」，Agent 就会做。

四、验收标准。 怎么算「做对了」。这一条是整个 spec 的锚。Claude Code 的 Best Practices 文档里说得很直接：给 Agent 一种验证自己工作的方式。测试用例是最直接的验证方式。截图对比是 UI 开发的验证方式。Linting 结果是代码风格的验证方式。每一项验收标准都是一条「Agent 可以不依赖人类判断就推进」的许可。没有验收标准的任务，Agent 每走一步都要回头看你——这恰好是把 Agent 用慢了的方式。Thoughtworks 补充了一个有用的建议：用 Given/When/Then 的格式写验收标准——这个从 BDD 里继承来的结构在 AI 时代依然有效。

五、技术上下文。 项目结构、技术栈、相关文件位置。这部分你不需要手写——让 Agent 读一遍你的代码库，它自己就能生成。Addy Osmani 的第一条原则就是「先给高层愿景，让 AI 草拟细节」：你写两句话描述项目目标，让 Agent 扫描代码库生成一份包含技术栈、目录结构、命令清单的上下文文档，你 review 一下就行。这部分 spec 的价值在于让后续每一次 Agent 会话都能快速定位「相关代码在哪、怎么跑测试、用什么框架」。

#### 同一个功能，两份 Spec

回到第 1 篇那个注册页面。口喷需求是一句话：「帮我做一个注册页面」。

Agent 听到这句话之后，它脑中的「注册页面」是训练数据里成千上万个注册页面的平均值。那个平均值有邮箱输入框、密码框、注册按钮——但没有「密码不能明文对比」「错误提示不能区分用户」「接口响应不能返回其他用户数据」。因为这些是安全约束，不是 UI 模板。

结果就是那个黄色警告框：「密码需要唯一。该密码已被用户 r\*\*\*88 使用。」

现在对照第 1 篇里那份 spec，用五要素的镜头重新看一遍。

目标——「为平台提供邮箱注册入口」，一句话。不是「做一个注册页面」，是「提供注册入口」。措辞的差别决定了 Agent 的思考方向：前者让它想 UI，后者让它想流程。

约束——「密码使用 bcrypt 存储，cost factor ≥ 10，不可逆」「错误提示不附带任何关联账户信息」「接口响应中不返回其他用户的数据」。三条安全约束，每一条都是对那个黄色警告框的预防。

边界——「不发送验证邮件」「不做社交登录」「不做 CAPTCHA」。三条明确的「不做」，每一条都在堵住 Agent 自作主张的路。

验收标准——六条可测试的断言：「新邮箱 + 合规密码 → 201，数据库密码字段为 bcrypt 哈希」「已注册邮箱 → 409」「接口响应中不出现其他用户的标识信息」。每一条都可以写成自动化测试。Agent 做完之后能自己跑一遍验证，不需要你逐行检查。

技术上下文——API 路径（POST /api/auth/register）、数据字段（email、password、created\_at）、前端路由（/register）。这些就是 Agent 需要的技术锚点。

同一份功能，口喷需求一句话 vs 五要素 spec 一页纸。Agent 在前者上产出了一个泄露用户密码的系统，在后者上一次通过安全审计。差异不在于 Agent 的能力——是同一个 Agent。差异在于你给了它什么。

Addy Osmani 在他的文章里引用了一个观察：「有经验的开发者会先写好文档，然后模型可能仅凭这份文档就能构建出匹配的实现。」spec 不是辅助材料——在足够好的 spec 面前，Agent 有可能仅凭它就构建出匹配的实现。

#### 从三句话开始

说完了五要素，你可能会觉得写 spec 是一件需要认真准备的事。它确实是。但「认真准备」不等于「从完美的文档开始」。

Addy Osmani 的方法论第一条就是：「先给一个简洁的高层 spec，然后让 AI 把它扩展成详细计划。」你不是在写一份巨著——你是在种一颗种子。

现在就可以做的事：在你的项目根目录下创建一个 CLAUDE.md 文件（如果你用的是 Copilot 或 Cursor，创建 AGENTS.md——内容一样，文件名不同）。写下三行：

```markdown
# 项目说明

这是一个 [一句话描述你的项目做什么]。
技术栈：[列出主要框架和语言]。
Agent 必须遵守：[写 1-3 条最重要的约束]。
```

三行。写完了。这就是你的第一份 spec。

它不完美。它不完整。但它做到了最重要的一件事：从零到一。Agent 下次启动时，它读到的不再是一个空目录——它读到了项目的身份、技术栈和底线。这三条信息足以让 Agent 的产出质量产生质变。

然后你让它扩展。打开 Claude Code，对它说：「读一下这个项目的代码库和 CLAUDE.md，帮我补充：常用命令、项目结构说明、测试方式、代码风格示例。」Agent 会扫描你的代码库，生成一份更完整的上下文文档。你花两分钟 review 一下，改掉它猜错的地方，补上它漏掉的约束。

这就是 Addy Osmani 说的「让 AI 草拟细节」。你提供方向，Agent 填充细节，你 review 结果。这个循环比你自己从零写一份完整 spec 快得多。

Claude Code 的 Plan Mode 把这个循环产品化了。你在 Plan Mode 里描述你想做什么，Agent 只读不改——它分析代码库、理解约束、输出一份执行计划。你审查计划，觉得方向对就通过，不对就改。通过之后才退出 Plan Mode，让 Agent 开始写代码。Plan Mode 的本质就是：先在文档层对齐，再在代码层执行。在文档层解决一次理解偏差的成本，远低于在代码层解决同一个偏差。

#### Spec 是活文档

Thoughtworks 在那篇行业分析里传达了一个意思：行业对规范该是什么还没有形成共识——方法论仍在形成中。

这句话的意思不是「等标准出来了再开始」。它的意思是：没有人能告诉你「正确的 spec 长什么样」，因为所有人都还在摸索。

这反而给了你一个优势：你不需要学一套标准流程。你不需要买工具。你不需要安装框架。你需要的只是一个 Markdown 文件和三句话。

第一天：三行 CLAUDE.md。第一周：补充项目结构和常用命令。第一个月：为每个新功能写一份五要素 spec。第二个月：你回头看初版 CLAUDE.md，发现它已经长到了两页——但你没有哪一天是「专门坐下来写文档」的。它是随着开发自然生长出来的。

这就是 spec 作为 living document 的真正含义。它不是在项目开始时写完、然后在 Confluence 里过期的文档。它是你每次跟 Agent 交互时都在更新的工作文件——你改了 spec，Agent 下次执行立刻就变。spec 和代码之间形成了一个实时反馈循环：代码变了，你更新 spec；spec 变了，Agent 重新执行。

Ubuntu 的工程团队在 2026 年初发表的一篇回顾文章里写了一句话，放在 AI 时代依然精确：「文档是开发过程的一部分，而不是事后补充。」他们不是在说 SDD——他们是在说一个更朴素的道理：文档只有跟开发同步呼吸，才有生命力。

你不需要写一份完美的 spec。你需要的是开始写。

三句话就够了。

## 结构化（1）

### 2026-07-07 09:48:56

#### 《写好一份 Spec 的实战手册》精炼总结

本文核心观点：**Spec 不是传统需求文档，而是给 AI Agent 的 “执行协议”**。写好 Spec 的关键不是追求完美模板，而是明确目标、约束、边界、验收标准和技术上下文，让 Agent 少猜、多执行、可验证。

---

##### 1. 背景：为什么很多人知道 Spec 重要，却写不出来

本文是「AI 时代的编码新范式」系列第 5 篇，全系列共**9 篇**，基于**43 篇行业文献、论文和实践报告**，讨论 Spec-Driven Development 如何成为 AI Agent 时代的工程基础设施。

前四篇已经说明：

- 为什么需要 Spec；
- Spec 的角色已从 “给人看的说明” 变成 “给 Agent 的执行协议”；
- Spec 能让任务变快；
- Spec 是 Agent 的外部记忆。

但真正落地时，很多人会卡在一个问题上：**Spec 到底怎么写？**

很多人打开 Markdown 文件后，会纠结：

- 要写多长？
- 要不要像 PRD？
- 要不要画 UML？
- 要不要写用户故事？
- 为什么有的 Spec 几十页，有的只有三行？

结果往往是：先关掉文件，“下次再写”，而这个下次通常不会来。

---

##### 2. Spec 不是什么：先避免三个常见误区

作者强调，很多人不会写 Spec，是因为把 Spec 当成了别的东西。

###### 2.1 Spec 不是 PRD

PRD 关注的是：

- 用户是谁；
- 场景是什么；
- 用户痛点是什么；
- 业务价值是什么。

但 AI Agent 更需要的是：

- 接口长什么样；
- 输入输出是什么；
- 哪些行为不能做；
- 出错时怎么处理。

举例：

- PRD 说：用户需要一个安全的注册流程。
- Spec 说：密码用`bcrypt`存储，`cost factor ≥ 10`；错误提示不能区分 “用户不存在” 和 “密码错误”。

前者是产品判断，后者才是 Agent 能执行的约束。

Thoughtworks 在 2025 年的分析中也指出：Spec 应该定义软件的**外部行为**，包括输入输出、前置条件、后置条件、不变量、接口契约、状态机等，而不是泛泛描述业务需求。

---

###### 2.2 Spec 不是技术设计文档

技术设计文档关注：

- 架构怎么搭；
- 数据库选什么；
- 是否拆微服务；
- 消息队列用 Kafka 还是 RabbitMQ。

Spec 关注的是：

- 功能应该表现成什么样；
- API 接收什么参数；
- 返回什么状态码；
- 异常怎么处理。

Addy Osmani 的观点是：高层 Spec 应先聚焦**what 和 why**，而不是一开始就规定**how**。

也就是说，你先告诉 Agent “要做什么、为什么做”，实现细节可以让 Agent 在编码阶段处理。

---

###### 2.3 Spec 不是用户故事

用户故事通常是：

> 作为一个用户，我想上传文件，以便分享给同事。

它表达的是意图，但不够具体。

Agent 还需要知道：

- 文件大小限制；
- 允许哪些文件类型；
- 本期是否做断点续传；
- 上传成功后如何验收；
- 超时要返回什么错误。

所以，用户故事最多只是 Spec 的起点，不是完整 Spec。

---

##### 3. 正确起点：从结果倒推

Amazon 有一个产品方法论叫**Working Backwards**：先想象产品已经完成，写出 “发布新闻稿” 会是什么样，再倒推需要满足什么条件。

这给 Spec 写作提供了一个好思路：

> 不要从 “我要做一个注册页面” 开始，而要从 “一个安全的注册流程应该满足什么条件” 倒推。

例如注册功能，不只是有邮箱框、密码框和按钮，还要定义：

- 密码如何存储；
- 错误提示不能泄露信息；
- 接口不能返回其他用户数据；
- 哪些功能本期不做。

---

##### 4. 一份合格 Spec 的五个核心要素

GitHub 官方博客曾分析超过**2500 个`agents.md`文件**，发现有效的 Agent 配置通常覆盖六类内容：命令、测试、项目结构、代码风格、Git 工作流、边界。

其中出现频率最高的单条约束是：

> 永远不要提交密钥。

结合 GitHub、Addy Osmani、Thoughtworks 以及文章中的注册页面案例，作者总结出 Spec 的五个核心要素。

---

###### 4.1 目标：说明为什么做

目标回答：

- 这个功能解决什么问题？
- 为谁解决？

不需要长篇大论，一两句话即可。

例如：

> 为平台提供邮箱注册入口。

这比 “做一个注册页面” 更好，因为它让 Agent 关注完整注册流程，而不仅是 UI 页面。

AWS 的建议是：**Start with why**，先说为什么做，再说做什么。

如果目标太模糊，比如 “优化一下页面”，Agent 就没有判断方向，只能随机猜。

---

###### 4.2 约束：明确必须遵守和绝对不能做的事

约束是 Spec 区别于用户故事的核心。

约束主要分两类：

###### 安全约束

例如：

- 密码必须哈希存储；
- 输入必须校验；
- 不暴露用户数据；
- 错误提示不能泄露账号是否存在。

###### 工程约束

例如：

- 不使用废弃 API；
- 遵循现有错误处理模式；
- 不随便引入新依赖；
- 不提交密钥。

作者强调：对 Agent 来说，**“不要做什么” 往往比 “要做什么” 更重要**。

---

###### 4.3 边界：明确范围，尤其是 “不做什么”

边界包括：

- 输入输出范围；
- 功能依赖；
- 本期做什么；
- 本期明确不做什么。

例如注册功能中明确写：

- 不发送验证邮件；
- 不做社交登录；
- 不做 CAPTCHA。

这些看似普通，但非常重要。

因为 Agent 会根据训练数据自动联想：看到 “注册”，就可能顺手加上邮箱验证、密码强度检测、登录频率限制等功能。

如果你不明确说 “不做”，Agent 可能会自作主张扩展功能。

---

###### 4.4 验收标准：定义怎样才算做对

验收标准是 Spec 的锚点。

它回答：

- 什么结果算成功？
- 怎么验证 Agent 做对了？
- 能不能自动测试？

Claude Code 的最佳实践强调：要给 Agent 一种验证自己工作的方式。

常见验收方式包括：

- 自动化测试；
- UI 截图对比；
- Linting 结果；
- 接口返回值检查。

Thoughtworks 建议使用 BDD 中常见的格式：

> Given / When / Then

例如：

- Given 一个未注册邮箱；
- When 用户提交合规密码；
- Then 接口返回 201，并且数据库中的密码字段是 bcrypt 哈希。

有了验收标准，Agent 就能自己推进和验证，不需要每一步都等人判断。

---

###### 4.5 技术上下文：告诉 Agent 项目在哪里、怎么跑

技术上下文包括：

- 项目结构；
- 技术栈；
- 相关文件路径；
- 常用命令；
- 测试方式；
- 代码风格。

这部分不一定要手写，可以让 Agent 扫描代码库后生成。

Addy Osmani 的方法是：

> 人提供高层愿景，AI 草拟细节，人再 review。

例如你可以让 Claude Code 扫描项目，补充：

- 目录结构；
- 技术栈；
- 构建命令；
- 测试命令；
- 代码风格示例。

这样后续每次 Agent 工作时，都能快速知道 “相关代码在哪、怎么运行、用什么框架”。

---

##### 5. 案例：同一个注册功能，两种需求写法，结果完全不同

文章用第 1 篇中的注册页面做对比。

###### 5.1 口头需求：一句话导致安全漏洞

原始口头需求是：

> 帮我做一个注册页面。

Agent 听到后，会生成训练数据中 “注册页面” 的平均样子：

- 邮箱输入框；
- 密码输入框；
- 注册按钮。

但它可能忽略安全约束。

结果出现了严重问题：

> 黄色警告框提示：“密码需要唯一。该密码已被用户 r***88 使用。”

这意味着系统不仅错误地比较了密码，还泄露了其他用户信息。

---

###### 5.2 五要素 Spec：让 Agent 做出安全实现

同样是注册功能，如果写成五要素 Spec，就完全不同。

###### 目标

> 为平台提供邮箱注册入口。

这让 Agent 关注注册流程，而不是只做页面。

###### 约束

包括：

- 密码使用`bcrypt`存储，`cost factor ≥ 10`；
- 密码不可逆；
- 错误提示不能包含关联账户信息；
- 接口响应不能返回其他用户数据。

这些约束可以直接避免前面的安全事故。

###### 边界

明确本期不做：

- 不发送验证邮件；
- 不做社交登录；
- 不做 CAPTCHA。

防止 Agent 擅自扩展功能。

###### 验收标准

例如：

- 新邮箱 + 合规密码 → 返回`201`；
- 数据库密码字段必须是 bcrypt 哈希；
- 已注册邮箱 → 返回`409`；
- 接口响应中不能出现其他用户标识信息。

这些都可以写成自动化测试。

###### 技术上下文

包括：

- API 路径：`POST /api/auth/register`；
- 数据字段：`email`、`password`、`created_at`；
- 前端路由：`/register`。

结论是：**差异不在 Agent 能力，而在你给它的信息质量。**

一句话需求会让 Agent 猜；五要素 Spec 会让 Agent 执行。

---

##### 6. 如何开始：不用完美，从三句话 Spec 开始

作者强调：写 Spec 不等于一开始就写完美文档。

Addy Osmani 的建议是：

> 先给一个简洁的高层 Spec，再让 AI 扩展成详细计划。

最简单的做法是在项目根目录创建：

- Claude Code 用：`CLAUDE.md`
- Copilot / Cursor 用：`AGENTS.md`

内容先写三行即可：

```markdown
# 项目说明

这是一个 [一句话描述你的项目做什么]。

技术栈：[列出主要框架和语言]。

Agent 必须遵守：[写 1-3 条最重要的约束]。
```

这就是第一份 Spec。

它不完整，但已经完成了最关键的事：让 Agent 知道项目身份、技术栈和底线。

---

##### 7. 让 Agent 帮你扩展 Spec

写完三行后，可以让 Agent 继续补充：

> 读一下这个项目的代码库和 CLAUDE.md，帮我补充：常用命令、项目结构说明、测试方式、代码风格示例。

Agent 会扫描代码库，生成更完整的上下文文档。

人的工作是：

- review；
- 改掉 Agent 猜错的地方；
- 补上遗漏的约束。

这比自己从零写完整 Spec 快得多。

---

##### 8. Plan Mode：先在文档层对齐，再写代码

Claude Code 的**Plan Mode**把这个流程产品化了。

流程是：

1. 你描述想做什么；
2. Agent 只读代码，不改代码；
3. Agent 分析代码库和约束；
4. Agent 输出执行计划；
5. 你审查计划；
6. 通过后，Agent 才开始写代码。

Plan Mode 的本质是：

> 先在文档层解决理解偏差，再进入代码层执行。

这样做的好处是：在文档里改方向，比在代码写错后返工便宜得多。

---

##### 9. Spec 是活文档，不是一次性文档

Thoughtworks 指出：行业对 Spec 的标准形式还没有完全形成共识。

作者认为，这不代表要等标准成熟再开始，而是说明：

> 你不需要学习一套复杂流程，只需要从一个 Markdown 文件开始。

Spec 应该像活文档一样自然生长：

- 第一天：写三行`CLAUDE.md`；
- 第一周：补充项目结构和常用命令；
- 第一个月：为每个新功能写五要素 Spec；
- 第二个月：最初的文件可能已经自然长到两页。

它不是项目开始时写完、之后在 Confluence 里过期的文档，而是每次和 Agent 协作时都会更新的工作文件。

代码变了，更新 Spec；Spec 变了，Agent 下次执行就会改变。

Ubuntu 工程团队在 2026 年的回顾中也表达了类似观点：

> 文档是开发过程的一部分，而不是事后补充。

---

##### 10. 最终结论

写 Spec 的关键不是模板，而是让 Agent 明确知道：

- 要达成什么目标；
- 必须遵守什么约束；
- 哪些事情不做；
- 怎样才算完成；
- 项目上下文在哪里。

你不需要一开始写出完美 Spec。  
**从三句话开始，就已经足够让 Agent 的输出质量发生明显变化。**

## 口播总结（1）

### 2026-08-03 01:53:49

#### 写好一份 Spec 的实战手册

这篇文章要回答一个核心问题：在 AI Agent 参与开发的时代，一份真正有用的 Spec，也就是“规范说明”，到底应该怎么写。听完你会知道，Spec 不是什么、应该包含哪些要素，以及如何从三句话开始，让 Agent 更准确、更安全地完成开发任务。

##### 一、先弄清楚：Spec 不是什么

首先，Spec 不是产品需求文档，也就是 PRD。

PRD 主要回答“用户想要什么”。它会描述目标用户、使用场景和业务价值。Spec 则要进一步回答：“软件具体应该表现成什么样。”

比如，PRD 可能会说：“用户需要一个安全的注册流程。”

而 Spec 会明确规定：密码必须使用 bcrypt，也就是一种不可逆的密码哈希算法来存储，成本因子至少是十；用户不存在和密码错误时，提示信息不能有区别；接口也不能返回其他用户的数据。

前者是在做产品判断，后者是在定义软件行为。

接下来，Spec 也不是技术设计文档。

技术设计关注的是“架构怎么搭”。比如使用什么数据库，要不要拆成微服务，消息队列选择 Kafka 还是 RabbitMQ。Spec 在最初阶段不必决定这些实现细节。它更关心的是：接口接收什么参数，返回什么结果，出错时怎么处理。

换句话说，高层 Spec 应该先聚焦于“做什么”和“为什么做”，而不是一开始就规定“怎么做”。具体的架构方案，可以留给 Agent 在实现阶段分析和决定。

更重要的是，Spec 也不是用户故事。

用户故事通常是：“作为一个用户，我想上传文件，以便分享给同事。”这句话表达了意图，但还远远不够。Agent 还需要知道文件多大、允许哪些格式、本期不做断点续传，以及上传成功和失败分别是什么结果。

所以，用户故事可以作为 Spec 的起点，但不能代替 Spec。

这里还有一个有用的起点，叫做亚马逊的“反向工作法”。它的思路是，先想象产品已经完成，最终结果应该是什么样，再倒推实现这个结果需要满足哪些条件。

因此，不要只从“用户需要一个注册页面”开始，而要先问：“一个安全的注册流程，应该具备哪些条件？”

##### 二、一份合格的 Spec，至少包含五个要素

澄清了这些误解之后，接下来进入核心：一份实用的 Spec 应该写什么。

GitHub 曾经分析过超过两千五百份 `agents.md` 文件，也就是给 AI Agent 使用的项目说明文件。研究发现，效果较好的说明通常覆盖六个领域：命令、测试、项目结构、代码风格、Git 工作流，以及边界。

其中出现频率最高的一条具体约束是：“永远不要提交密钥。”

结合这项研究，以及 Thoughtworks 和 Addy Osmani 等人的方法，可以提炼出五个核心要素。

###### 第一，目标

核心结论是：先用一两句话说明，这个功能要解决什么问题，以及为谁解决。

通俗地说，Agent 需要一个方向锚点。比如“优化一下这个页面”，目标就太模糊了。Agent 不知道什么叫优化，也不知道应该优先考虑速度、视觉效果，还是转化率。

但如果你说：“为平台提供一个邮箱注册入口”，Agent 的思考方向就会从单纯做一个页面，转向完成一整套注册流程。

所以，目标不需要长篇大论，但一定要清楚。

###### 第二，约束

核心结论是：必须明确告诉 Agent，什么一定要遵守，什么绝对不能做。

约束是 Spec 和用户故事之间最重要的区别之一。它通常分为两类。

第一类是安全约束，比如密码必须哈希存储，输入必须验证，接口不能暴露用户数据。

第二类是工程约束，比如不能使用已经废弃的 API，要遵循项目现有的错误处理方式，也不能随意引入新的依赖。

很多时候，“不要做什么”比“要做什么”更加重要。前面提到的 GitHub 研究中，“永远不要提交密钥”就是最常见的一条约束。

###### 第三，边界

核心结论是：除了规定输入、输出和依赖关系，还要明确本期不做什么。

边界的作用，是防止 Agent 自作主张地扩大功能范围。

还是以注册功能为例，可以明确写出三点：本期不发送验证邮件，不做社交登录，也不做 CAPTCHA，也就是验证码挑战。

这些内容看起来像是在列举“没做的功能”，但它们非常重要。因为 Agent 看到“注册”这个词，很容易联想到训练数据中常见的配套功能，例如邮箱验证、密码强度检测和登录频率限制。

如果你不明确说“不做”，Agent 很可能就会主动加上。

###### 第四，验收标准

核心结论是：必须告诉 Agent，怎样才算做对了。

验收标准是整份 Spec 的锚点。它给了 Agent 一种可以自行检查工作的方式。

在不同任务里，验证方式也不同。后端功能可以使用自动化测试，界面开发可以做截图对比，代码风格可以检查 Lint，也就是代码规范检查工具的结果。

每一条验收标准，都相当于给 Agent 一张“可以继续推进”的许可。没有验收标准，Agent 每完成一步都要回来询问人类，这会让整个过程变慢。

验收标准还可以使用 Given、When、Then，也就是“在什么前提下、执行什么操作、应该得到什么结果”的格式。

例如：给定一个新的邮箱和符合要求的密码；当用户提交注册请求时；那么接口返回二零一，数据库中的密码字段保存为 bcrypt 哈希。

这样的描述比“注册功能要正常工作”更加清楚，也更容易直接写成测试。

###### 第五，技术上下文

核心结论是：告诉 Agent 项目使用什么技术、代码大致在哪里，以及相关命令怎么运行。

技术上下文包括项目结构、技术栈、相关文件位置、测试命令和常用开发命令。

但这部分不一定要由人从头手写。你可以先用两句话描述项目目标，让 Agent 扫描代码库，然后由它生成技术栈、目录结构和命令清单，最后由你检查和修正。

这样做的价值是，后续每次启动 Agent，它都能快速知道相关代码在哪里、项目如何运行、测试应该怎么执行。

##### 三、同一个注册功能，为什么结果会完全不同

下面用一个典型案例，把这五个要素放在一起看。

一句口头需求可能是：“帮我做一个注册页面。”

Agent 听到这句话后，往往会根据大量训练数据，生成一个“平均意义上的注册页面”。通常会有邮箱输入框、密码输入框和注册按钮。

但它不一定会想到：密码不能明文比较，错误提示不能暴露用户是否存在，接口响应不能返回其他用户数据。

结果就可能出现文章开头那个问题：页面弹出黄色警告框，提示“密码需要唯一，这个密码已经被用户某某使用”。

这个提示泄露了用户信息。问题不在于 Agent 不够聪明，而在于需求没有明确告诉它安全边界。

现在换成一份包含五要素的 Spec。

目标是：“为平台提供邮箱注册入口。”这句话不只是要做一个页面，而是要完成一个注册入口和相关流程。

约束包括三条：密码使用 bcrypt 存储，成本因子至少为十，而且不可逆；错误提示不能包含任何关联账户信息；接口响应不能返回其他用户的数据。

边界则是：本期不发送验证邮件，不做社交登录，不做 CAPTCHA。

验收标准可以写成多个可测试的断言。比如，新邮箱加合规密码，接口返回二零一，数据库保存的是 bcrypt 哈希；已注册邮箱返回四零九；接口响应中不能出现其他用户的标识信息。

技术上下文则提供接口路径 `POST /api/auth/register`，数据字段包括 `email`、`password` 和 `created_at`，前端路由是 `/register`。

这样一来，Agent 完成代码后，可以自己运行测试进行验证，而不需要人类逐行检查。

同一个功能，口头需求只有一句话，Spec 可能只有一页纸，但结果却完全不同。前一种方式可能生成泄露用户信息的系统，后一种方式则有机会一次通过安全审计。

差异不在 Agent 的能力，而在于你给了它什么信息。

##### 四、不要等完美文档，从三句话开始

讲到这里，你可能会觉得写 Spec 很复杂，需要先准备一份完整文档。

核心结论是：认真准备不等于一开始就写得完美。最重要的是先从零到一。

可以先在项目根目录创建一个 `CLAUDE.md` 文件。如果使用 Copilot 或 Cursor，也可以创建 `AGENTS.md`，内容基本相同，只是文件名不同。

第一份文件只需要写三句话：

第一句，说明项目是什么。

第二句，列出主要技术栈，也就是使用的框架和编程语言。

第三句，写出一到三条最重要的约束，也就是 Agent 必须遵守的底线。

例如，可以这样说：

“这是一个帮助用户管理个人任务的网页应用。”

“技术栈是 React、Node.js 和 PostgreSQL。”

“Agent 必须遵循现有的错误处理方式，不能提交密钥，也不能引入未经确认的新依赖。”

三句话就够了。

它当然不完整，也不完美。但它已经完成了最重要的一步：让 Agent 下次启动时，面对的不是一个毫无背景的空目录，而是一个有项目身份、有技术栈、有底线的工作环境。

接下来，再让 Agent 帮你扩展这份文档。

你可以让它读取代码库和 `CLAUDE.md`，补充常用命令、项目结构、测试方法和代码风格示例。Agent 负责扫描和起草，你花几分钟检查它的结果，修正猜错的地方，再补上遗漏的约束。

这就是“让 AI 草拟细节”的方法：人负责方向，Agent 填充细节，人再审核结果。

整个循环通常比人从零写一份完整 Spec 更快。

##### 五、先对齐计划，再开始写代码

接下来，是一个能够进一步降低错误成本的方法：Plan Mode，也就是计划模式。

在计划模式下，你描述想做的事情，Agent 只读取代码和分析问题，不直接修改文件。它会理解代码库、识别已有约束，并输出一份执行计划。

你先审查这份计划。如果方向不对，就在文档层面修改。如果方向正确，再让 Agent 退出计划模式，开始真正写代码。

它的核心价值是：先在文档层解决理解偏差，再在代码层执行。

如果代码已经写了一大堆，才发现双方理解不一致，修复成本通常很高。但如果问题只出现在一份执行计划里，修改起来就容易得多。

因此，Plan Mode 本质上是把 Spec 的作用产品化了：先对齐，再执行。

##### 六、Spec 不是一次性文档，而是活文档

最后要理解的是，Spec 不需要等待行业形成统一标准。

Thoughtworks 的行业分析指出，目前整个行业对于 Spec 究竟应该长什么样，还没有形成共识。方法论仍然在发展，大家都还在摸索。

这并不意味着要等标准出来以后再开始。恰恰相反，这说明你不需要先学习一套复杂流程，也不需要购买专门工具或安装某个框架。

你只需要一个 Markdown 文件，以及最开始的三句话。

第一天，写三行 `CLAUDE.md`。

第一周，补充项目结构和常用命令。

第一个月，为每个新功能写一份包含五个要素的 Spec。

到了第二个月，你可能会发现最初的三行已经变成了两页。但你并没有专门抽出一天来写文档，它是在日常开发过程中自然长出来的。

这就是“活文档”的含义。

它不是项目开始时写完，然后被丢在某个文档系统里逐渐过期的材料。它是你每次和 Agent 协作时都会更新的工作文件。

代码变了，就更新 Spec。Spec 变了，Agent 下次执行时就遵循新的要求。Spec 和代码之间形成一个实时反馈循环。

Ubuntu 工程团队也强调过类似的观点：文档是开发过程的一部分，而不是事后补充。

所以，你不需要先写出完美的 Spec。你需要做的是现在就开始写。

##### 最后，记住这五点

第一，Spec 不是 PRD、技术设计或用户故事。它的核心任务，是定义软件的外部行为和执行约束。

第二，一份实用的 Spec 至少要包含五个要素：目标、约束、边界、验收标准和技术上下文。

第三，明确“不做什么”非常重要。它能防止 Agent 根据训练数据，自作主张地扩展功能。

第四，验收标准越具体，Agent 就越能自己验证工作，越少需要反复询问人类。

第五，不要等完美文档。从项目根目录里的三句话开始，让 Agent 帮你逐步扩展，并在开发过程中持续更新。

Spec 不是额外负担，而是 AI Agent 的方向、记忆和行动准则。

## 深度解读（1）

### 2026-09-18 00:37:03

#### AI 编程时代，Spec 的核心不是“写得完整”，而是把判断变成可验证的边界

这篇文章最有价值的地方，不是提出了一套新模板，而是重新划分了人与 Agent 的职责：**人负责定义目标、风险边界和完成标准，Agent 负责在这些条件内寻找实现路径。**

“帮我做一个注册页面”看似明确，实际只给出了功能类别。Agent 只能调用训练数据中“注册页面”的平均模式，却不知道当前系统最在意的是防止账户枚举、兼容既有错误处理，还是避免引入新依赖。文章提出的五要素——目标、约束、边界、验收标准、技术上下文——本质上是在补齐这些无法从任务名称推导出来的信息。

##### 验收标准不是收尾清单，而是 Agent 的自主运行条件

五要素中，真正决定 Agent 能否独立推进的是**可验证的验收标准**。

传统协作中，“效果不对”“体验不好”还可以通过人与人的追问逐步校正；Agent 面对这类模糊反馈，只能继续猜。相反，“已注册邮箱返回 409”“响应中不得出现其他用户标识”“新用户创建后密码字段应为哈希”，都可以转化为测试。Agent 因而能够形成闭环：实现、运行测试、发现偏差、继续修改。

这会改变 Spec 的衡量方式：不应看它有多少页，而应看它减少了多少需要人临场判断的环节。**每一条机器可验证的标准，都相当于把一次人工确认转化为 Agent 的继续执行权。**

对产品经理而言，这也意味着需求交付不能只停留在用户故事和页面流程。高质量需求需要继续追问：哪些结果可以观察？异常时应发生什么？哪些信息绝不能泄露？什么情况虽然“能用”，却仍算失败？这些问题过去容易在开发或测试阶段补充，如今直接决定 Agent 生成代码的质量。

##### “不做什么”比功能清单更能抑制失控

文章对负向边界的强调同样重要。Agent 并非只会漏做，也会依据常见模式主动补全：看到注册功能，顺手加入验证码、邮箱验证、社交登录或新的依赖。单项看似合理，合在一起却可能扩大工期、攻击面和维护成本。

因此，“本期不做什么”不是文档中的附属栏目，而是在对抗模型的模式补全倾向。更一般地说，**AI 协作的难点正从告诉它“可以做什么”，转向明确哪些合理选项在当前情境下不可接受。**安全、合规、兼容性和数据权限尤其如此，因为这些要求往往无法仅凭界面目标推断。

不过，文章对 Spec、PRD 和技术设计的切割略显过度。它一面说 Spec 不应规定 how，一面又要求 bcrypt 和具体 cost factor；这显然已经是实现约束。更准确的原则应是：**默认描述可观察行为，但当某项实现选择关系到安全政策、兼容性或不可逆成本时，就应明确规定。**问题不在于是否写 how，而在于人是否确实有理由收回 Agent 的决策权。

##### 不要把项目记忆与功能 Spec 混成一个不断膨胀的文件

文章建议从三行 `CLAUDE.md` 或 `AGENTS.md` 开始，这个启动方式务实，但它混合了两类不同文档：

- 项目级规则：目录结构、运行命令、代码规范、禁止事项；
- 任务级 Spec：本次目标、范围、验收条件和特殊约束。

前者应稳定、简短，供每次会话复用；后者应随功能创建和结束。如果所有信息都持续堆进一个“活文档”，最终会出现过期规则、相互冲突和上下文噪声，反而降低 Agent 的判断质量。让 Agent 自动扫描代码库生成上下文也很有效，但生成内容只是草稿，尤其需要检查命令、目录和安全规则是否准确。

文章引用的仓库统计能说明开发者常写哪些约束，却不能证明这些写法必然提升交付质量；注册案例也更像说明性案例，而非因果证据。因此，最值得保留的不是“写了 Spec 就能一次通过审计”这种强结论，而是一种更可靠的工作方式：**先在低成本的文字和测试层暴露分歧，再允许 Agent 修改高成本的代码。**

实践中可以从一个很小的检查开始：每次交给 Agent 前，写清一句目标、三条不可违反的边界、三条可自动验证的结果。Spec 的价值不来自文档仪式，而来自它是否把人的隐性判断，变成了机器能够遵守和检验的契约。

## 默认总结（1）

### 2026-09-18 01:43:05

##### 一句话看懂

一份好的 AI 编程 Spec 不是传统 PRD，而是明确目标、约束、边界、验收标准和技术上下文的“执行协议”，让 Agent 知道该做什么、不能做什么，以及怎样才算完成。

##### 关键内容

- **先分清 Spec 的定位**：PRD 讲用户需求，技术设计讲架构方案，用户故事只表达意图；Spec 重点定义软件的外部行为和执行规则，如输入输出、异常处理及安全限制。
- **核心是五要素**：目标提供方向；约束规定底线；边界明确本期不做什么；验收标准让 Agent 能通过测试自行验证；技术上下文帮助它找到代码、命令和项目规范。
- **不必一次写完**：可先在 `CLAUDE.md` 或 `AGENTS.md` 写项目简介、技术栈和关键约束，再让 Agent 扫描代码库补充细节，由人审核纠错。
- **Spec 应随项目更新**：先在计划阶段对齐理解，再写代码；需求或代码变化时同步修改，而不是写完后长期搁置。

##### 通俗解读

Agent 会用训练数据中的“常见做法”补齐空白，因此一句“做注册页面”可能引发越界开发或安全问题。Spec 的作用不是把文档写长，而是提前堵住关键误解，并给出可验证的完成条件。

**是否值得细读：值得。** 尤其适合正在使用 Claude Code、Cursor 等工具的人；但文章案例较多、观点有重复，掌握“五要素＋三行起步法”后即可快速实践。
