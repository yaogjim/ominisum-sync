## 解读（1）

### 2026-06-17 02:12:11

##### 一、深度总结

这段内容的核心是：

> **提升 coding 效率，不是靠“更拼”，而是把重复劳动系统化、自动化、Agent 化。**

作者 10 天独自更新 8 个版本，靠的不是单纯手速，而是把开发流程拆成三类：

1. **脚本化**  
   把打包、部署、发版、查日志、生成 changelog 等固定流程写成脚本。

2. **规则化**  
   把经验沉淀成明确规则，比如：
   - 改功能前先读哪些文件；
   - 发版前必须测哪些链路；
   - 报错时先看哪些日志。

3. **Agent 化 / Skill 化**  
   把重复、可描述、可调用的任务交给 Agent 执行。  
   人不再亲自做每个细节，而是把工作流程逐步转化成可复用的 Skill。

最终形成一种分工：

> **人负责方向判断和结果验收，Agent 负责重复执行。**

---

##### 二、深入浅出解读

这其实是在讲一种新的开发方式：

###### 过去的开发方式

开发者亲自做所有事：

- 自己写代码；
- 自己查日志；
- 自己打包；
- 自己部署；
- 自己整理 changelog；
- 自己检查上线流程。

结果是：  
大量时间消耗在重复动作上。

---

###### 更高效的方式

把工作流程变成“流水线”：

| 工作类型 | 处理方式 |
|---|---|
| 重复操作 | 写脚本 |
| 固定经验 | 写规则 |
| 标准流程 | 做成 Skill |
| 具体执行 | 交给 Agent |
| 方向判断 | 人来负责 |
| 最终验收 | 人来负责 |

也就是说：

> 不要每次都重新做一遍，而是每做一次，就想办法让下一次更省力。

---

##### 三、关键启发

###### 1. 效率来自复利

第一次做事是完成任务。  
第二次做事时，就应该思考：

> 这件事以后还会不会做？  
> 如果会，能不能自动化？

真正的效率提升，不是一次快，而是以后每次都更快。

---

###### 2. 经验不能只存在脑子里

很多人的经验是隐性的：

- “我知道该看哪个文件”
- “我知道哪里容易出错”
- “我知道上线前要测什么”

但这些如果不写下来，就无法复用，也无法交给 AI 或团队成员执行。

经验规则化之后，才会变成资产。

---

###### 3. Agent 不是替代人，而是放大人

Agent 适合处理：

- 重复任务；
- 明确流程；
- 可验证结果；
- 有上下文规则的工作。

人更适合处理：

- 判断方向；
- 设计架构；
- 权衡取舍；
- 发现异常；
- 验收结果。

所以关键不是“让 AI 写代码”，而是：

> 让 AI 嵌入你的工作流。

---

##### 四、辩证思考

###### 值得肯定的地方

这套方法很有价值，因为它抓住了现代软件开发的本质：

> 高效开发者不是做得更多，而是亲手做得更少。

把流程脚本化、规则化、Agent 化，可以显著减少低价值劳动，让人专注于真正重要的判断。

---

###### 但也要警惕几个问题

###### 1. 不要为了自动化而自动化

如果一个任务只做一次，写脚本可能反而浪费时间。

自动化适合高频、稳定、可复用的流程。

---

###### 2. Agent 不能盲目信任

Agent 能执行，但不一定理解业务。  
所以必须保留：

- 代码 review；
- 测试；
- 日志检查；
- 人工验收。

否则效率提升可能变成风险放大。

---

###### 3. 规则化不等于僵化

规则是为了减少重复思考，不是限制创造力。  
当业务变化时，规则和 Skill 也要持续更新。

---

##### 五、一句话结论

> 未来高效的程序员，不只是会写代码的人，而是能把自己的工作流产品化、自动化、Agent 化的人。

## 结构化（1）

### 2026-06-18 11:52:25

##### 主旨概括

作者分享了自己 **10 天独立更新软件 8 个版本** 的经验：提升 coding 效率的关键，不是单纯依赖 AI Agent，而是先把重复流程标准化、脚本化，再交给 Agent 执行。人负责方向判断和结果验收，Agent 负责重复劳动。

##### 1. 先把重复流程脚本化

作者认为，凡是可以重复执行的流程，都应该尽量写成脚本，减少手动操作。

关键点包括：

- 打包
- 部署
- 发版
- 检查日志
- 生成 changelog

通俗来说，就是把每天都会做、步骤固定的事情自动化。比如每次发版都要执行一堆命令，就不应该每次手动输入，而是做成一个一键脚本。

##### 2. 把经验沉淀成规则

除了流程自动化，作者还强调要把自己的开发经验整理成明确规则。

例如：

- 每次改功能前，先读哪些文件
- 发版前，必须测试哪些关键链路
- 遇到报错时，先查看哪个日志

这些规则可以减少临时判断和重复思考，让开发流程更稳定，也方便后续交给 Agent 执行。

##### 3. 能交给 Agent 的就不要手搓

作者建议：如果某些任务可以交给 Agent 处理，或者可以做成 skills，再让 Agent 调用脚本完成，就不要自己手动做。

也就是说，Agent 更适合执行已经明确的任务，比如：

- 调用部署脚本
- 按规则检查日志
- 根据模板生成 changelog
- 按流程跑测试

前提是流程本身已经比较清晰。

##### 4. 把个人工作流程逐步变成 Skill

作者的核心方法是：把自己平时做事的流程，一点点沉淀为 Skill。

这里的 Skill 可以理解为“可复用的能力模块”或“标准操作流程”。比如：

- 发版 Skill
- Debug Skill
- 日志检查 Skill
- 功能修改前的代码阅读 Skill

这样做的好处是，开发效率会随着流程积累不断提高。

##### 5. 人和 Agent 的分工要清楚

作者总结了人与 Agent 的合理分工：

- **人负责：判断方向、制定规则、验收结果**
- **Agent 负责：执行重复动作、调用脚本、按流程完成任务**

换句话说，不是让 Agent 代替人思考所有问题，而是让它承担重复、机械、流程化的工作。

##### 6. 热门回复观点补充

评论区也补充了几个重要看法：

- 有人认为这种方式效率很高，体现了程序员应有的工作方式。
- 有人表示认同：现在 Agent 的门槛在于，它不是一上手就像网上说得那么神奇，很多人试了几次效果不好就放弃了。
- 还有人强调顺序很重要：**先脚本化，再 Agent 化**。如果流程本身混乱，Agent 只会更快地制造混乱。

##### 总结

这篇内容的核心经验是：提升开发效率，要先把重复工作脚本化，把经验规则化，再让 Agent 执行。AI Agent 不是万能工具，只有在流程清晰、规则明确的前提下，才能真正放大个人效率。
