## 通俗精炼（1）

#### AI 时代协作开发的新问题

##### 核心观点

这段内容主要在讨论：**传统的 `git worktree` 协作方式，不适合多 Agent 同时写代码的场景**。  
原因是每个 worktree 本质上都是彼此隔离的，Agent 无法实时感知其他 Agent 在改什么，结果就是前面各自推进，最后合并时才集中爆发冲突。

##### 作者的判断

作者认为，未来更需要的不是简单的多分支并行，而是一个能表达**任务依赖关系**和**Agent 协作流程**的新基础设施。

这里面有两个关键点：

###### 1. 用 Graph DB 管理依赖关系
需要一种图数据库式的结构，把任务、计划、代码修改、Agent 分工之间的依赖关系表达清楚，才能更好地做多 Agent 编排。

###### 2. 单个 Agent 也要形成闭环
一个 Agent 不只是“写代码”，而是要跑完整循环：

`Code -> CI & Review -> Fix -> Human in the Loop`

也就是说，AI 开发流程会越来越像一个自动迭代系统，人类更多是在关键节点介入。

##### 对现有方案的看法

作者提到 Steve Yegge 做了 `beads`，但自己觉得不好用，所以在迭代自己的工具。  
这说明现有工具还没有很好解决 **多 Agent 实时协作、依赖管理、冲突预防** 这些问题，行业仍在早期探索阶段。

##### 延伸讨论

回复里还提到一种可能方向：  
**像在线文档协作那样，用 CRDT 思路处理代码协作。**

背后的判断是：如果多人实时编辑文档可行，那么理论上代码协作也可能成立。

同时作者还提出一个更深的观点：

###### 文档和代码应该是一体的
文档不是独立产物，而应该是代码的**摘要和整体说明**。  
这意味着未来开发过程里，代码、文档、计划、依赖关系，可能会逐渐融合成一个统一系统。

##### 一句话总结

**这段内容的本质是在说：AI 编程时代的瓶颈，已经不是“能不能写代码”，而是“多个 Agent 如何实时协作、共享上下文、管理依赖并避免最后打架”。**
