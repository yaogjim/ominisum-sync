#### Gpt-Agreement-Payment

ChatGPT Team 订阅协议的端到端重放工具，附带从零实现的 hCaptcha 视觉求解器，以及一组真实运行采集的反欺诈机制实证数据。

---

#### 这是什么

从抓包逆出 `Stripe Checkout → PayPal billing agreement → ChatGPT manual-approval → Codex OAuth + PKCE` 整条链路并实现成可运行客户端。给一个干净代理 + 一个支付凭证，命令跑完拿到 OAuth `refresh_token` 。

三个值得看的点：

- **hCaptcha 视觉求解器** （ `CTF-pay/hcaptcha_auto_solver.py` ，约 4000 行，独立可用）。VLM 主路径 + CLIP/OpenCV 启发式回退 + Playwright 人类动作合成，覆盖 12 种已知 hCaptcha 题型。
- **反欺诈机制实证数据** 。IP 字符串级精确指纹、批次关联延迟封禁、probe 层 vs ban 层分离。45 个号 24 小时存活率约 2% 的实测样本，含修正模型。详见 `docs/anti-fraud-research.md` 。
- **十二路自愈环 daemon** （ `pipeline.py::daemon()` ）。Webshare API 自动换 IP、CF DNS 配额清理、tmpfs 孤儿回收、gost 中继看门狗、DataDome 滑块自动拖拽等。设计目标是无人值守跑数周。

---

#### 架构

详细子系统拆解、文件分工、协议链路细节看 `docs/architecture.md` 。

---

#### 现状与门槛

实事求是讲，这不是个开箱即用的工具。要把整条链路跑通，至少需要：

- 一个真实可登录的 PayPal 账号，第一次跑要人肉过一次邮箱 OTP 2FA
- 一个出口在 EU / US 的代理（PayPal 锁地区，Stripe 锁国家）
- 一个 Cloudflare zone（用于开 catch-all 子域注册邮箱）
- 一台能跑 Camoufox + Playwright 的 Linux（约 5 GB 磁盘 + 2 GB 内存）
- （可选）一个 OpenAI 兼容的 VLM API key，hCaptcha 求解用；家宽 / 伪家宽出口通常不会触发 hCaptcha，无 VLM 时也会降级到 CLIP
- （可选）一个兼容 createTask/getTaskResult 协议的打码平台 API key，作为浏览器 passive captcha 的兜底

第一次完整跑通通常要花 1–3 小时调通配置。daemon 模式跑稳后，单次 pipeline 约 5 分钟。

代码偏研究性质，不追求可读性最大化。 `CTF-pay/card.py` 是单文件 8000 行，按协议阶段而不是按抽象层分区。

#### 已知限制

- **PayPal 仅 EU 开通** 。Stripe 账号限制，只能以 IE 等欧盟身份下单。
- **批量注册次日存活率约 2%** 。这是 ChatGPT 反欺诈机制的批次关联效应导致的，不是工具本身的问题。详见 `docs/anti-fraud-research.md` 。
- **免费账号路径目前不通** 。OpenAI 改了 free 账号二次登录流程，重定向到 `/add-phone` 没真实手机号绕不过；ChatGPT-Web client 的 access\_token 调 Codex API audience 不匹配。
- **Stripe runtime 指纹会漂** 。 `runtime.version` / `js_checksum` / `rv_timestamp` 大约几周一次需要重新对齐。
- **hCaptcha 题型覆盖不全** 。当前 12 种常见题，未覆盖时由 VLM 直出坐标兜底，不保证成功率。
- **代码风格偏粗放** 。 `card.py` 单文件 8000 行，注释混中英文，不适合作为 Python 工程范例。

##### 一句话概括

3. **反欺诈机制实证研究**
   - 记录了 ChatGPT、Stripe、PayPal 等平台在注册、支付、风控、封禁方面的观察数据。
   - 包括 IP 指纹、批量账号关联、延迟封禁等现象。
   - 项目作者提到批量注册账号的次日存活率非常低，约 2%。

项目还提供了：

- WebUI 配置向导
- daemon 自动维护模式
- 代理切换、DNS 清理、验证码处理等自动化组件
- 安装、配置、架构、调试、反欺诈研究等文档

但作者也明确说明：

- 这不是开箱即用工具
- 配置复杂，依赖真实 PayPal、代理、Cloudflare、Linux 环境等
- 代码偏研究性质，可读性一般
- 存在较高法律和平台合规风险
- 禁止用于欺诈、规避支付、批量造号、违反第三方服务条款等行为

#### 二、深入浅出解读

##### 1. 这个项目本质上是什么？

通俗地说，它不是普通的“ChatGPT 订阅助手”，而更像是一个：

> 对 ChatGPT 付费订阅、支付协议、验证码、风控系统进行逆向研究和自动化复现的实验工具。

它关注的不是用户正常在网页上点按钮订阅，而是研究浏览器背后发生了什么请求、什么参数、什么风控判断，然后尝试用程序自动复现这一整套流程。

---

##### 2. 为什么它技术上复杂？

因为它涉及多个独立系统：

| 环节 | 涉及对象 |
|---|---|
| 支付页面 | Stripe |
| 支付授权 | PayPal |
| 账号登录 | OpenAI / ChatGPT |
| 授权协议 | OAuth + PKCE |
| 验证码 | hCaptcha |
| 风控 | IP、浏览器指纹、账号行为、支付地区 |
| 自动化 | Playwright、Camoufox、代理、Cloudflare |

这些系统本身都具备反自动化、反欺诈、反滥用机制，所以项目需要处理：

- 浏览器指纹伪装
- TLS 指纹模拟
- 代理 IP 管理
- 邮箱验证码接收
- hCaptcha 自动识别
- 支付地区限制
- 账号封禁监控
- 失败后自动恢复

这也是为什么作者说它“调通一次通常要 1–3 小时”。

---

##### 3. hCaptcha 求解器为什么是重点？

验证码的目的就是区分“真人”和“机器”。

这个项目尝试用：

- 视觉语言模型识别图片内容
- CLIP 做图片语义匹配
- OpenCV 做图像处理
- Playwright 模拟鼠标点击和拖动

来自动完成验证码。

从技术研究角度看，这部分有一定计算机视觉和自动化测试价值；但从实际用途看，它也很容易被用于绕过平台防护，因此敏感性很高。

---

##### 4. 反欺诈研究部分说明了什么？

项目作者观察到：

- 平台可能会记录非常细的 IP 和代理特征
- 批量账号之间可能存在关联识别
- 有些封禁不是立即发生，而是延迟触发
- 支付、注册、登录、OAuth 等不同阶段的风控可能分层进行

简单说就是：

> 平台不是只看一个账号是否异常，而是综合判断 IP、设备、支付、行为模式、批次特征等多个因素。

所以作者提到，即使自动化流程跑通，账号存活率也很低。

---

##### 5. 它的风险在哪里？

这个项目涉及的风险比较明显：

###### 合规风险

它可能违反 OpenAI、Stripe、PayPal、hCaptcha 等平台的服务条款。

###### 法律风险

如果用于绕过支付、批量造号、欺诈交易、规避验证码，就可能触及法律问题。

###### 账号和资金风险

使用者可能面临：

- PayPal / Stripe 风控
- OpenAI 账号封禁
- 付款失败或资金损失
- 代理服务、邮箱、域名被标记
- 个人身份或支付信息风险

###### 技术风险

项目依赖第三方服务协议，一旦平台接口或风控策略变化，工具就可能失效。

- 验证码系统面临哪些自动化挑战

原因很简单：

> 技术门槛高，合规风险大，实际收益低，账号和资金风险不小。

##### 3. 验证码求解器技术上有意思，但伦理边界很重要

hCaptcha 求解器展示了 AI 视觉模型对传统验证码的冲击。

但这类技术也很容易被滥用，所以应当限定在：

- 合法授权测试
- 自有系统验证
- 学术研究
- 防御评估

不应当用于绕过真实平台的访问控制。
