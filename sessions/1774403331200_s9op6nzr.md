## 正文

Context engineering is providing the right information and tools in the right format so your deep agent can accomplish tasks reliably.Deep agents have access to several kinds of context. Some sources are provided to the agent at startup; others become available during runtime, such as user input. Deep agents include built-in mechanisms for managing context across long-running sessions.This page provides an overview of the different kinds of context your deep agent has access to and manages.

New to context engineering? See the conceptual overview for the different types of context and when to use them.

#### Types of context

#### Input context

Input context is information provided to your deep agent at startup that becomes part of its system prompt. The final prompt consists of several sources:

##### System prompt

Your custom system prompt is prepended to the built-in system prompt, which includes guidance for planning, filesystem tools, and subagents. Use it to define the agent’s role, behavior, and knowledge:The `system_prompt` parameter is static which means it does not change per invocation. For some use cases you may want a dynamic prompt: for example, to tell the model “You have admin access” vs “You have read-only access,” or to inject user preferences like “User prefers concise responses” from long-term memory. If your prompt depends on context or `runtime.store`, use `@dynamic_prompt` to build context-aware instructions. Your middleware can read `request.runtime.context` and `request.runtime.store`. See Customization for adding custom middleware and the LangChain context engineering guide for examples.You do **not** need middleware when tools alone use context or `runtime.store`; tools receive `config.context` and `runtime.store` directly. Add middleware only when tools should be packaged with an update to the system prompt.

##### Memory

Memory files ([`AGENTS.md`](https://agents.md/)) provide persistent context that is **always loaded** into the system prompt. Use memory for project conventions, user preferences, and critical guidelines that should apply to every conversation:Unlike skills, memory is always injected—there is no progressive disclosure. Keep memory minimal to avoid context overload; use skills for detailed workflows and domain-specific content. See Memory for configuration details.

##### Skills

Skills provide **on-demand** capabilities. The agent reads frontmatter from each `SKILL.md` at startup, then loads full skill content only when it determines the skill is relevant. This reduces token usage while still providing specialized workflows:Keep each skill focused on a single workflow or domain; broad or overlapping skills dilute relevance and bloat context when loaded. Within a skill, keep the main content concise and move detailed reference material to separate files that are referenced in the skill file. Put always-relevant conventions in memory. See Skills for authoring and configuration.

##### Tool prompts

Tool prompts are instructions that shape how the model uses tools. All tools expose metadata the model sees in its prompt—typically a schema and a description. Tools you pass via the `tools` parameter surface that tool metadata (schema and descriptions) to the model. Deep Agents built-in tools are packaged in middleware and typically also update the system prompt with more guidance for those tools.**Built-in tools** – Middleware that adds harness capabilities (planning, filesystem, subagents) automatically appends tool-specific instructions to the system prompt, creating tool prompts that explain how to use those tools effectively:

- Planning prompt – Instructions for `write_todos` to maintain a structured task list
- Filesystem prompt – Documentation for `ls`, `read_file`, `write_file`, `edit_file`, `glob`, `grep` (and `execute` when using a sandbox backend)
- Subagent prompt – Guidance for delegating work with the `task` tool
- Human-in-the-loop prompt – Usage for pausing at specified tool calls (when `interrupt_on` is set)
- Local context prompt – Current directory and project info (CLI only)

**Tools you provide** – Tools passed via the `tools` parameter get their descriptions (from the tool schema) sent to the model. You can also add custom middleware that adds tools and appends its own system prompt instructions.For tools you provide, make sure to provide a clear name, description, and argument descriptions. These guide the model’s reasoning about when and how to use the tool. Include *when* to use the tool in the description and describe what each argument does.See Harness for built-in capabilities and Customization for passing tools directly.

##### Complete system prompt

The deep agent’s system message—the assembled system prompt the model receives at the start of a run—consists of the following parts:

1. Custom `system_prompt` (if provided)
2. [Base agent prompt](https://github.com/langchain-ai/deepagents/blob/e18e9dcd0e6edc72c0a4a5b76ae752c4bc539752/libs/deepagents/deepagents/graph.py#L37)
3. To-do list prompt: Instructions for how to plan with to do lists
4. Memory prompt: `AGENTS.md` + memory usage guidelines (only when `memory` provided)
5. Skills prompt: Skills locations + list of skills with frontmatter information + usage (only when skills provided)
6. Virtual filesystem prompt (filesystem + execute tool docs if applicable)
7. Subagent prompt: Task tool usage
8. User-provided middleware prompts (if custom middleware is provided)
9. Human-in-the-loop prompt (when `interrupt_on` is set)

#### Runtime context

Runtime context is per-run configuration you pass when you invoke the agent. It is not automatically included in the model prompt; the model only sees it if a tool, middleware, or other logic reads it and adds it to messages or the system prompt. Use runtime context for user metadata (IDs, preferences, roles), API keys, database connections, feature flags, or other values your tools and harness need. Tools and subagents receive this context from the `config` argument:Runtime context **propagates to all subagents**. When a subagent runs, it receives the same `config` (including `context`) as the parent. See Subagents for per-subagent context (namespaced keys).

#### Context compression

Long-running tasks produce large tool outputs and long conversation history. Context compression reduces the size of information in an agent’s working memory while preserving details relevant to the task. The following techniques are the built-in mechanisms to ensure the context passed to LLMs stays within its context window limit:Deep Agents use the built-in filesystem tools to automatically offload content and to search and retrieve that offloaded content as needed. Content offloading happens when tool call inputs or results exceed a token threshold (default 20,000):

1. **Tool call inputs exceed 20,000 tokens**: File write and edit operations leave behind tool calls containing the complete file content in the agent’s conversation history. Since this content is already persisted to the filesystem, it’s often redundant. As the session context crosses 85% of the model’s available window, deep agents truncate older tool calls, replacing them with a pointer to the file on disk and reducing the size of the active context.
   ![An example of offloading showing a large input which is saved to disk and the truncated version is used for the tool call](https://mintcdn.com/langchain-5e9cc07a/0G7fpRWZQ2tFN1wL/oss/images/deepagents/offloading-inputs.png?fit=max&auto=format&n=0G7fpRWZQ2tFN1wL&q=85&s=fa18372080684d661965ea6f5ed1edd0)
   An example of offloading showing a large input which is saved to disk and the truncated version is used for the tool call
2. **Tool call results exceed 20,000 tokens**: When this occurs, the deep agent offloads the response to the configured backend and substitutes it with a file path reference and a preview of the first 10 lines. Agents can then re-read or search the content as needed.
   ![An example of offloading showing a large tool response that is replaced with a message about the location of the offloaded results and the first 10 lines of the result](https://mintcdn.com/langchain-5e9cc07a/0G7fpRWZQ2tFN1wL/oss/images/deepagents/offloading-results.png?fit=max&auto=format&n=0G7fpRWZQ2tFN1wL&q=85&s=11f3da2f37cae63b8aa4c440549f1a67)
   An example of offloading showing a large tool response that is replaced with a message about the location of the offloaded results and the first 10 lines of the result

##### Summarization

When the context size crosses the model’s context window limit (for example 85% of `max_input_tokens`), and there is no more context eligible for offloading, the deep agent summarizes the message history.This process has two components:

- **In-context summary**: An LLM generates a structured summary of the conversation including session intent, artifacts created, and next steps—which replaces the full conversation history in the agent’s working memory.
- **Filesystem preservation**: The complete, original conversation messages are written to the filesystem as a canonical record.

This dual approach ensures the agent maintains awareness of its goals and progress (via the summary) while preserving the ability to recover specific details when needed (via filesystem search).

![An example of summarization showing an agent's conversation history, where several steps get compacted](https://mintcdn.com/langchain-5e9cc07a/0G7fpRWZQ2tFN1wL/oss/images/deepagents/summarization.png?fit=max&auto=format&n=0G7fpRWZQ2tFN1wL&q=85&s=a8fea59d4365dd688e49ce118e706e76)

An example of summarization showing an agent's conversation history, where several steps get compacted

**Configuration:**

- Triggers at 85% of the model’s `max_input_tokens` from its model profile
- Keeps 10% of tokens as recent context
- Falls back to 170,000-token trigger / 6 messages kept if model profile is unavailable
- If any model call raises a standard `ContextOverflowError`, Deep Agents immediately falls back to summarization and retries with summary + recent preserved messages
- Older messages are summarized by the model

###### Summarization Tool

Deep Agents includes an optional tool for summarization, enabling agents to trigger summarization at opportune times—such as between tasks—instead of at fixed token intervals.You can enable this tool by appending it to the middleware list:Enabling this feature does not disable the default summarization action at 85% of the model’s context limit.See [API reference](https://reference.langchain.com/python/deepagents/middleware/summarization/SummarizationToolMiddleware) for details.

#### Context isolation with subagents

Subagents solve the **context bloat problem**. When the main agent uses tools with large outputs (web search, file reads, database queries), the context window fills quickly. Subagents isolate this work—the main agent receives only the final result, not the dozens of tool calls that produced it. You can also configure each subagent separately from the main agent (for example, model, tools, system prompt, and skills).**How it works:**

- Main agent has a `task` tool to delegate work
- Subagent runs with its own fresh context
- Subagent executes autonomously until completion
- Subagent returns a single final report to the main agent
- Main agent’s context stays clean

**Best practices:**

1. **Delegate complex tasks**: Use subagents for multi-step work that would clutter the main agent’s context.
2. **Keep subagent responses concise**: Instruct subagents to return summaries, not raw data:
3. **Use the filesystem for large data**: Subagents can write results to files; the main agent reads what it needs.

See Subagents for configuration and context management for runtime context propagation and per-subagent namespacing.

#### Long-term memory

When using the default filesystem, your deep agent stores its working memory files in agent state, which only persists within a single thread. Long-term memory enables your deep agent to persist information across different threads and conversations. Deep agents can use long-term memory for storing user preferences, accumulated knowledge, research progress, or any information that should persist beyond a single session.To use long-term memory, you must use a `CompositeBackend` that routes specific paths (typically `/memories/`) to a LangGraph Store, which provides durable cross-thread persistence. The `CompositeBackend` is a hybrid storage system where some files persist indefinitely while others remain scoped to a single thread.You do not need to pre-populate `/memories/` with files. You provide the backend config, store, and system prompt instructions that tell the agent *what* to save and *where*. For example, you may prompt the agent to store preferences in `/memories/preferences.txt`. The path starts empty and the agent creates files on demand using its filesystem tools (`write_file`, `edit_file`) when users share information worth remembering.To pre-seed memories, use the Store API when deploying on LangSmith. See Long-term memory for setup and use cases.

#### Best practices

1. **Start with the right input context** – Keep memory minimal for always-relevant conventions; use focused skills for task-specific capabilities.
2. **Leverage subagents for heavy work** – Delegate multi-step, output-heavy tasks to keep the main agent’s context clean.
3. **Adjust subagent outputs in configuration** – If you notice when debugging that subagents generate long output, you can add guidance to the subagent’s `system_prompt` to create summaries and synthesized findings.
4. **Use the filesystem** – Persist large outputs to files (for example subagent writes or automatic offloading) so the active context stays small; the model can pull in fragments with `read_file` and `grep` when it needs details.
5. **Document long-term memory structure** – Tell the agent what lives in `/memories/` and how to use it.
6. **Pass runtime context for tools** – Use `context` for user metadata, API keys, and other static configuration that tools need.

#### 《Context engineering in Deep Agents》通俗总结

##### 一、核心观点：让 Agent 在对的时候看到对的信息
这篇文章讲的本质很简单：

**Context Engineering（上下文工程）**，就是把**正确的信息、工具和提示**，以**合适的方式**提供给 Deep Agent，让它能更稳定、更可靠地完成任务。

对 Agent 来说，能力不只取决于模型本身，更取决于：
- 它一开始拿到了什么信息
- 运行过程中能访问什么工具和数据
- 面对超长任务时，怎么控制上下文不爆炸

一句话概括：**不是让 Agent 知道更多，而是让它在合适的时候知道最需要的东西。**

---

##### 二、上下文分三类：启动时、运行时、长期记忆
文章把 Agent 的上下文大致分成三类。

###### 1. 输入上下文：启动时就给它的内容
这是 Agent 一开始就会带上的信息，通常会进入 system prompt，包括：
- 自定义系统提示词：定义角色、行为方式、规则
- `AGENTS.md`记忆文件：放长期有效的偏好、规范、关键原则
- Skills：按需加载的技能说明，不是一直全塞进去
- Tool prompts：告诉模型有哪些工具、每个工具怎么用

核心原则是：
**长期且始终相关的信息放 Memory，任务型、专业型的信息放 Skills。**

###### 2. 运行时上下文：每次调用时传入的信息
比如：
- 用户身份、角色、偏好
- API Key
- 数据库连接
- 功能开关
- 业务配置

这类信息**不会自动进入模型提示词**，只有工具、中间件或其他逻辑主动读取后，模型才会 “看到”。

也就是说，它更像是**运行配置层**，而不是天然的 “对话内容”。

###### 3. 长期记忆：跨会话保存的信息
如果你希望 Agent 在不同线程、不同会话之间也能记住事情，就要用长期记忆。

适合存：
- 用户偏好
- 持续积累的知识
- 研究进展
- 多轮任务中的沉淀结果

本质上，这是让 Agent 不再只活在 “当前会话”，而是开始具备**跨会话连续性**。

---

##### 三、为什么需要上下文工程：Agent 最大的问题是 “上下文膨胀”
Deep Agent 在长任务里很容易遇到一个核心问题：

**上下文越堆越多，最终超出模型窗口，导致效率下降、成本上升、表现变差。**

典型来源包括：
- 很长的对话历史
- 大量工具调用记录
- 超长文件读写内容
- 搜索、数据库、网页抓取等大结果集

所以，文章重点不是单纯介绍 “有哪些上下文”，而是在讲：

**怎么让 Agent 在长流程中持续保持清醒。**

---

##### 四、系统怎么解决：压缩、外置、总结
为了解决上下文膨胀，Deep Agents 内置了几种机制。

###### 1. 内容外置（Offloading）
如果工具输入或输出太大，系统不会一直把完整内容留在上下文里，而是：
- 把内容保存到文件系统或后端
- 在上下文里只留一个路径引用和少量预览

这样做的价值是：
**重要信息没有丢，只是不再一直占着模型的脑容量。**

###### 2. 自动总结（Summarization）
当上下文接近模型上限，又没有更多内容可外置时，系统会对历史进行总结：
- 用结构化摘要保留任务目标、已完成内容、下一步动作
- 原始完整记录仍保存到文件系统中

这相当于：
**把 “长篇流水账” 压缩成 “项目纪要”。**

###### 3. 保留最近内容
系统不会把所有历史都压缩掉，而是会保留一部分最近消息，让 Agent 还能紧跟当前任务。

所以整体思路是：
**旧内容总结，重内容外置，新内容保留。**

---

##### 五、Subagents 很关键：用 “分身” 隔离复杂任务
文章非常强调 Subagents（子代理）的作用。

###### 1. 子代理解决什么问题
主 Agent 如果亲自做所有事，比如：
- 搜索网页
- 读很多文件
- 查数据库
- 跑多步分析

那主上下文会很快被塞满。

子代理的做法是：
- 主 Agent 把任务派出去
- 子代理在自己的独立上下文里完成工作
- 最后只把结论返回给主 Agent

###### 2. 这样做的好处
核心好处是：

**主 Agent 只保留结果，不背负过程。**

这非常像现实中的管理方式：
- 主 Agent 是 “项目负责人”
- Subagent 是 “专项执行者”

负责人不需要知道所有细节，只需要拿到清晰结果。

###### 3. 最佳实践
文中建议：
- 复杂、多步骤、输出很大的任务优先交给子代理
- 子代理返回摘要，不要返回原始大段数据
- 大结果写入文件，主 Agent 按需读取

这本质上是在做**上下文分层管理**。

---

##### 六、Memory、Skills、Runtime Context 的分工要清楚
这三者很容易混，但文章的意思其实很明确。

###### 1. Memory：放始终有效的规则
适合放：
- 项目规范
- 用户长期偏好
- 永远适用的重要原则

要求是：**少而精。**
因为它会一直注入 prompt，太多会造成负担。

###### 2. Skills：放按需调用的能力
适合放：
- 某类任务流程
- 某个领域知识
- 某种固定工作法

要求是：**聚焦单一场景。**
不要写得太泛，否则既影响判断，又容易让上下文变臃肿。

###### 3. Runtime Context：放运行配置
适合放：
- 身份信息
- 权限信息
- API 配置
- 外部系统依赖

它更像 “系统参数”，不一定直接给模型看，而是给工具链和执行层使用。

一句话区分：
- **Memory 是长期规则**
- **Skills 是按需能力**
- **Runtime Context 是运行配置**

---

##### 七、对产品经理的启发：本质是 “信息架构设计”
从产品视角看，这篇文章讲的不只是技术实现，更像是在讲 Agent 的信息架构。

###### 1. Agent 不是 “喂更多信息” 就会更聪明
真正重要的是：
- 哪些信息应该始终存在
- 哪些信息按需出现
- 哪些信息应该被沉淀
- 哪些信息应该被隔离

这跟做产品后台、知识库、工作流设计，本质很像。

###### 2. Agent 设计的关键是 “信息流效率”
一个好 Agent，不是上下文最多，而是：
- 信息进入有层次
- 信息调用有节制
- 信息存储有结构
- 信息压缩有机制

也就是说，**Agent 的稳定性，越来越像一个系统设计问题，而不只是 Prompt 问题。**

###### 3. 未来竞争点会从模型能力转向上下文管理能力
模型会越来越强，但真正拉开产品差距的，往往是：
- 记忆机制是否合理
- 技能体系是否清晰
- 多代理协作是否顺畅
- 长任务管理是否稳定

所以，上下文工程其实是 Agent 产品化落地的关键基础设施。

---

##### 八、最简结论
这篇文章的核心可以浓缩为三句话：

###### 1. Context Engineering 的本质
**让 Agent 在合适的时候拿到合适的信息和工具。**

###### 2. Deep Agent 的关键能力
**不是只会回答，而是会管理上下文：加载、隔离、压缩、总结、持久化。**

###### 3. 实战中的最佳思路
**少量常驻信息 + 按需技能 + 子代理隔离 + 文件系统外置 + 长期记忆沉淀。**

#### 总结

这篇文档讲的是：**如何给 Deep Agents 提供“恰到好处的上下文”**，让它在长任务、复杂任务里仍然稳定、节省 token、少出错。

核心分三块：

- **输入上下文**：启动时就给 agent 的信息，比如 `system prompt`、`AGENTS.md` 记忆、`skills`、工具说明。
- **运行时上下文**：每次调用时传入的配置，比如用户身份、权限、偏好、API Key，但**默认不会自动进入模型提示词**，只有工具或中间件主动读取后才会用到。
- **上下文压缩与隔离**：当对话太长、工具输出太大时，系统会通过**内容落盘、摘要压缩、子代理隔离**来控制上下文大小。

一句话理解：  
**Context engineering = 在合适的时候，把合适的信息，以合适的形式，给到 agent。**

---

#### 深入解读

##### 1. 输入上下文：一开始喂给 agent 的“底料”

这是 agent 启动时就会看到的内容，最终会拼进 system prompt。

###### `system prompt`
这是你给 agent 定义角色、行为和规则的地方。

- 适合放：身份、做事原则、输出风格
- 不适合放：每次都变的动态信息

文档特别强调：

- `system_prompt` 是**静态的**
- 如果内容会随着场景变化，比如：
  - “你现在有管理员权限”
  - “用户偏好简洁回答”
  
  那就应该用 **dynamic prompt** 或 middleware 动态生成

通俗说：  
**system prompt 像员工手册，dynamic prompt 像今天的临时通知。**

---

##### 2. Memory：始终注入，但一定要克制

`AGENTS.md` 里的内容会**一直加载**到 system prompt 中。

适合存：

- 项目约定
- 用户长期偏好
- 非常关键、每次都要遵守的规则

但文档反复提醒：**不要塞太多。**

原因很简单：

- Memory 是“永久带着走”的
- 一旦写太多，会造成上下文污染和 token 浪费

所以它更像：

- “团队必须遵守的总规则”

而不是：

- “某个任务的详细操作手册”

---

##### 3. Skills：按需加载，比 memory 更聪明

`skills` 的设计很关键：  
agent 启动时只读每个 `SKILL.md` 的概要信息，**真正详细内容只在相关时才加载**。

这带来两个好处：

- 节省 token
- 避免无关信息干扰当前任务

适合放：

- 某一类工作流
- 某一个专业领域知识
- 柍个明确能力模块

最佳实践是：

- 一个 skill 只做一件事
- 不要做成“大而全”
- 细节材料拆到独立文件里，让 skill 去引用

通俗说：  
**Memory 像“常驻脑海的习惯”，Skill 像“需要时才翻开的说明书”。**

---

##### 4. Tool prompts：告诉模型“工具该怎么用”

工具不只是给 agent 一个函数名，还要给它：

- 清晰的名字
- 清楚的描述
- 参数说明
- 适用场景

因为模型会根据这些文字判断：

- 什么时候该用这个工具
- 该怎么填参数
- 工具是否适合当前任务

也就是说，**工具描述本身就是提示词的一部分**。

这点很容易被忽视。很多 agent 工具效果差，不是工具不行，而是：

- 描述太模糊
- 参数含义不清
- 没说明“什么时候该用”

---

##### 5. Runtime context：运行时配置，不会自动“进脑子”

运行时上下文适合存：

- 用户 ID
- 用户角色
- 偏好设置
- API 密钥
- 数据库连接
- feature flag

但重点是：

> 这些信息默认不会自动进入模型 prompt

只有当：

- 工具读取它
- 中间件读取它
- 逻辑主动把它加进消息或 prompt

模型才“知道”。

这说明一个很重要的设计思想：

**不是所有有用信息都要直接喂给模型。**

有些信息只要让工具知道就够了，比如 API Key，根本不该进 prompt。

---

##### 6. 上下文压缩：上下文太长时，怎么不把模型撑爆

长任务会遇到一个现实问题：  
工具输出太长、对话历史太多，模型上下文窗口会被塞满。

文档给了三种主要机制。

###### 6.1 内容落盘（offloading）
如果工具输入或输出超过阈值（默认 20,000 tokens），系统会把大内容保存到文件系统，只在上下文里保留：

- 文件路径
- 简短预览

好处：

- 模型不用一直背着整段大文本
- 需要时再 `read_file` 或搜索

这很像人类工作方式：  
**长材料先归档，需要时再翻。**

---

###### 6.2 摘要压缩（summarization）
当上下文逼近模型上限，且已经没什么能继续落盘时，系统会：

- 把较早的对话历史总结成结构化摘要
- 保留最近一部分消息
- 原始历史则完整写入文件系统备查

这样做的目的，是同时保住两件事：

- agent 还知道“我在做什么、做到了哪一步”
- 真要找细节时，还能从文件里恢复

这比单纯“删历史”聪明得多。

---

###### 6.3 子代理（subagents）做上下文隔离
这是全文非常实用的一点。

如果主 agent 去做：

- 大量网页搜索
- 大文件读取
- 数据库查询
- 多步复杂推理

它的上下文会很快膨胀。

解决办法是交给 **subagent**：

- 子代理在自己的独立上下文里工作
- 做完后只返回一份简洁结论给主代理

效果就是：

- 主代理上下文保持干净
- 复杂过程被隔离
- 更不容易失控

通俗说：  
**主 agent 像项目经理，subagent 像专项执行小组。**

---

##### 7. 长期记忆：跨会话保存，不再“聊完就忘”

默认文件系统下，很多记忆只在当前线程有效。  
如果想跨会话保留信息，就需要 **long-term memory**。

适合记：

- 用户偏好
- 长期研究进展
- 积累的知识
- 持久规则

做法是把特定路径（比如 `/memories/`）接到持久化存储里。

关键点在于：

- 不需要提前把文件都建好
- agent 可以自己在合适时机写入记忆
- 但你最好提前告诉它：**什么该记、记到哪里、怎么组织**

否则它可能“会记”，但“记得乱”。

---

#### 我的意见

##### 这篇文档最值得记住的 4 点

- **不要把所有信息都塞进 prompt**
- **memory 要少而精，skills 要按需加载**
- **大内容尽量落盘，不要硬塞上下文**
- **复杂任务优先交给 subagents，主 agent 只收结论**

---

##### 我对这套设计的看法

我认为这套思路非常成熟，核心优点有三点：

###### 1. 它不是在堆 prompt，而是在做“信息分层”
很多人做 agent，习惯把规则、知识、工具说明、用户数据全塞进一个大 prompt。  
LangChain 这套方法更合理：把上下文分成不同层次，各管各的。

这会明显提升：

- 稳定性
- 可维护性
- token 利用率

---

###### 2. 它承认“大模型记不住一切”，所以强调外部化
文档里的文件系统、摘要、子代理，本质上都是在做一件事：

**不要逼模型硬记所有过程，而是把信息外部化管理。**

这是做复杂 agent 很重要的思想转变。

---

###### 3. 真正难的不是“让 agent 有上下文”，而是“让它只看到当前最需要的上下文”
这篇文章最有价值的，不是罗列上下文来源，而是强调：

- 什么该常驻
- 什么该动态注入
- 什么该按需加载
- 什么该被压缩
- 什么该交给子代理隔离

这才是 context engineering 的本质。

---

##### 实践建议

如果你要自己设计 Deep Agent，我建议这样做：

1. **先把 `system prompt` 写短**
   - 只放角色、原则、边界
2. **把长期规则放进 `AGENTS.md`**
   - 但控制在“必须一直知道”的范围
3. **把专业流程拆成独立 skills**
   - 一 skill 一能力
4. **给工具写清楚描述**
   - 尤其说明“何时使用”
5. **对大输出默认落盘**
   - 不要让主上下文背大包袱
6. **复杂任务优先 subagent 化**
   - 特别是搜索、分析、整理类工作

## 结构化（1）

### 2026-03-25 10:26:54

#### 文章主旨

这篇文章主要讲的是：要让 Deep Agents 稳定、可靠地完成复杂任务，关键不是一味给更多信息，而是**在合适的时候，以合适的形式，提供合适的上下文**。  
LangChain 为此设计了多层上下文机制，包括输入上下文、运行时上下文、上下文压缩、子代理隔离和长期记忆。

##### 1. 什么是 Context Engineering

- 核心定义：**为深度代理提供正确的信息和工具，并且用正确的格式组织起来**，从而提高任务完成的可靠性。
- Deep Agents 能接触到两类上下文：
  - **启动时就提供的上下文**，例如系统提示词、记忆、技能。
  - **运行中才出现的上下文**，例如用户输入、工具结果、运行时配置。
- 因为深度代理常常是**长时间运行**的，所以系统还内置了上下文管理能力，避免上下文越来越大、最终超出模型窗口。

##### 2. 输入上下文：启动时就注入给代理的信息

###### 2.1 System prompt（系统提示词）

- 用户自定义的 `system_prompt` 会加在内置系统提示词前面。
- 它主要用来定义：
  - 代理的角色
  - 行为方式
  - 基础知识或约束
- 但 `system_prompt` 是**静态的**，不会随着每次调用变化。

**例子：**
- 静态提示适合写死规则，例如“你是一个代码助手”。
- 如果你希望根据场景动态变化，例如：
  - “你有管理员权限”
  - “你只有只读权限”
  - “用户偏好简洁回复”
  
  那就应该使用 `@dynamic_prompt`，让提示词读取运行时上下文或长期存储内容。

###### 2.2 Memory（记忆文件）

- 记忆文件通常是 `AGENTS.md`，会**始终注入到系统提示词里**。
- 适合存放：
  - 项目规范
  - 用户偏好
  - 每次对话都必须遵守的重要规则
- 文章特别强调：**memory 要尽量精简**。

原因是：
- memory 没有“按需加载”机制；
- 它会一直被放进上下文里；
- 写太多容易造成上下文拥挤。

**适合放 memory 的内容：**
- “代码风格统一用 snake_case”
- “用户喜欢简短回答”
- “所有输出都要先给结论”

###### 2.3 Skills（技能）

- Skills 是**按需加载的能力模块**。
- 启动时，代理只会先读取每个 `SKILL.md` 的 frontmatter（前置信息）；
- 只有在判断某项技能和当前任务相关时，才会加载完整内容。

这样做的好处：
- 减少 token 消耗
- 保留专业能力
- 避免无关内容长期占据上下文

**最佳实践：**
- 每个 skill 只聚焦**单一工作流或单一领域**
- 不要做得过宽、过杂，否则会：
  - 降低匹配准确度
  - 让上下文膨胀
- 详细参考资料可以拆到独立文件中，由 skill 文件引用

**简单理解：**
- `memory` 是“永远带着的小抄”
- `skills` 是“需要时才翻开的专业手册”

###### 2.4 Tool prompts（工具提示）

- 工具本身也会影响模型行为。
- 模型能看到工具的：
  - 名称
  - 描述
  - 参数 schema
- 这些信息会帮助模型判断：
  - 什么时候该用这个工具
  - 怎么正确调用它

内置工具通常还会额外配套系统提示，例如：

- **Planning prompt**：指导如何用 `write_todos` 维护任务清单
- **Filesystem prompt**：说明 `ls`、`read_file`、`write_file`、`edit_file`、`glob`、`grep` 等工具怎么用
- **Subagent prompt**：指导何时把任务委托给子代理
- **Human-in-the-loop prompt**：说明在指定工具调用处如何暂停并等待人工介入
- **Local context prompt**：提供当前目录和项目信息（CLI 场景）

**对自定义工具的建议：**
- 工具名称要清晰
- 描述要明确“何时使用”
- 参数说明要具体说明每个字段的作用

##### 3. 完整系统提示词由哪些部分组成

Deep Agent 最终收到的 system message，通常由这些部分拼接而成：

- 自定义 `system_prompt`
- 基础代理提示词
- To-do list 规划提示
- Memory 提示（如有）
- Skills 提示（如有）
- 虚拟文件系统提示
- 子代理提示
- 用户自定义中间件提示
- Human-in-the-loop 提示（如有）

也就是说，真正送进模型的并不是单一提示词，而是一个**组合后的完整上下文包**。

##### 4. Runtime context：每次运行时传入的上下文

- Runtime context 是**每次调用时传入的配置**。
- 它**不会自动进入模型提示词**；
- 只有当工具、中间件或其他逻辑主动去读取并加入消息时，模型才会“看到”它。

适合放在 runtime context 中的内容：

- 用户 ID
- 用户角色
- 用户偏好
- API keys
- 数据库连接
- feature flags
- 其他工具运行所需的静态配置

**一个关键点：**
- runtime context 会**传递给所有子代理**。
- 子代理运行时，拿到的 `config` 和主代理一致，包括其中的 context。

所以，runtime context 更像是“系统运行参数”，不一定直接给模型看，但工具和代理执行流程可以依赖它。

##### 5. 上下文压缩：如何避免上下文爆炸

长任务会产生两个大问题：

- 工具输出很长
- 对话历史越来越长

因此 Deep Agents 内置了“上下文压缩”机制，主要有两种：**内容卸载（offloading）** 和 **总结（summarization）**。

###### 5.1 Content offloading（内容卸载）

当工具调用输入或输出太大时，系统会把大内容挪到文件系统或后端中，只在当前上下文里保留简化引用。

###### 触发阈值

- 当工具调用输入或结果**超过 20,000 tokens** 时，触发 offloading 相关处理。

###### 场景 1：工具输入超过 20,000 tokens

- 比如写文件、编辑文件时，工具调用里可能包含完整文件内容。
- 这些内容其实已经写进文件系统了，再保留在对话历史里就很冗余。
- 所以当整个会话上下文达到模型窗口的 **85%** 时，系统会截断较早的工具调用，只保留一个**文件路径指针**。

###### 场景 2：工具结果超过 20,000 tokens

- 如果某个工具返回特别长的结果，Deep Agent 会把完整结果卸载到后端。
- 然后在上下文中只保留：
  - 文件路径引用
  - 结果前 **10 行预览**

这样模型后续如果需要细节，可以再读取文件或搜索内容。

**好处：**
- 保留可追溯性
- 减少活跃上下文占用
- 需要时还能重新读取原始内容

###### 5.2 Summarization（总结压缩）

当上下文继续变大，并且已经没有更多内容可卸载时，系统会开始总结历史消息。

这个过程包含两个部分：

###### 1）上下文内总结
- 由 LLM 生成结构化摘要
- 内容包括：
  - 当前会话目标
  - 已创建的产物
  - 下一步计划
- 用这个摘要替代完整对话历史

###### 2）文件系统保留原始记录
- 完整原始消息会写入文件系统，作为正式记录保存

这是一种“双保险”设计：

- 模型继续靠摘要理解当前任务进度
- 如果需要查细节，仍可去文件系统找原始记录

###### 触发规则

- 默认在达到模型 `max_input_tokens` 的 **85%** 时触发
- 会保留最近 **10% token** 作为新鲜上下文
- 如果拿不到模型 profile，则回退到：
  - **170,000 tokens** 触发
  - 保留最近 **6 条消息**
- 如果任意模型调用抛出标准 `ContextOverflowError`，系统会**立即改用总结机制并重试**

###### 5.3 Summarization Tool（可选总结工具）

- 系统还提供了一个可选的总结工具。
- 这样代理可以在更合适的时机主动总结，比如：
  - 一个阶段任务做完之后
  - 切换到新任务之前
- 即使启用了这个工具，也**不会关闭默认的 85% 阈值总结机制**。

##### 6. 子代理如何解决上下文膨胀

文章明确指出：**Subagents 是解决上下文膨胀的重要手段。**

###### 原理

当主代理自己去做大量检索、读文件、查数据库时，会产生很多中间工具调用，迅速塞满上下文。  
子代理的做法是：

- 主代理把任务委托出去
- 子代理在自己的全新上下文中执行
- 完成后只返回一份最终报告
- 主代理只接收结果，不接收中间全部过程

###### 工作流程

- 主代理通过 `task` 工具委派工作
- 子代理在独立上下文里运行
- 子代理自主执行直到完成
- 最后返回一个简洁总结给主代理
- 主代理上下文因此保持干净

###### 适合委托给子代理的任务

- 多步骤任务
- 输出很多的任务
- 会产生大量工具调用的任务

**例如：**
- 复杂网页搜索
- 批量文件读取
- 数据库查询和汇总
- 大规模资料整理

###### 最佳实践

- 把复杂任务交给子代理
- 明确要求子代理**返回摘要而不是原始大数据**
- 大结果写入文件，由主代理按需读取必要片段

##### 7. Long-term memory：跨会话持久记忆

默认情况下，Deep Agent 的工作记忆只在**单个线程**内有效。  
如果想让代理跨线程、跨对话长期记住信息，就需要使用**长期记忆**。

###### 可以存什么

- 用户偏好
- 累积知识
- 研究进展
- 任何应该跨会话保留的信息

###### 怎么实现

- 需要使用 `CompositeBackend`
- 一般把特定路径（通常是 `/memories/`）路由到 `LangGraph Store`
- 这样部分文件可以长期保存，部分文件仍然只属于当前线程

###### 使用方式

- 不需要提前往 `/memories/` 填文件
- 你只要配置好 backend、store 和 system prompt
- 再告诉代理“什么值得记住、应该存到哪里”
- 代理就可以在合适时，用 `write_file`、`edit_file` 等工具自己创建记忆文件

**例子：**
- 你可以提示代理把用户偏好保存到 `/memories/preferences.txt`
- 一开始这个路径可以是空的
- 用户透露偏好后，代理再按需创建并写入

如果要预置记忆，则可以在部署到 LangSmith 时使用 Store API。

##### 8. 文末最佳实践总结

文章最后给出了几条很实用的原则：

- **输入上下文要选对**
  - 永远相关的内容放 memory
  - 任务专属能力放 skills
- **重任务交给子代理**
  - 特别是多步骤、输出重的工作
- **控制子代理输出长度**
  - 如果子代理输出太长，可以在它的 `system_prompt` 中要求它只给总结和综合结论
- **多利用文件系统**
  - 大结果写入文件，减少活跃上下文压力
  - 需要细节时，再用 `read_file` 或 `grep` 拉取片段
- **明确长期记忆结构**
  - 提前告诉代理 `/memories/` 里该放什么、怎么组织
- **把运行时配置放进 runtime context**
  - 尤其是用户元数据、API key、静态配置等工具依赖信息

##### 9. 一句话理解全文

可以把这套机制理解成：  
**memory 负责“始终记得”、skills 负责“按需调用”、runtime context 负责“本次运行参数”、offloading 和 summarization 负责“瘦身”、subagents 负责“分流”、long-term memory 负责“跨会话记住”。**

## 产品-最佳实践（1）

### 2026-03-25 10:32:25

#### 基于 Deep Agents 的 Context Engineering 最佳实践示例

下面我用一个具体场景，说明如何把文中提到的 `system prompt`、`memory`、`skills`、`runtime context`、`subagents`、`filesystem`、`long-term memory` 组合起来，形成一套可落地的最佳实践。

---

##### 示例场景

假设你要构建一个 **企业级研发助手**，用于帮助团队完成以下任务：

- 分析代码仓库
- 生成变更方案
- 查询内部文档
- 输出技术报告
- 记住不同用户的偏好（如语言、输出风格、权限等级）

这个 Agent 是一个典型的 **长任务、多步骤、上下文容易膨胀** 的 Deep Agent。

---

##### 一、推荐的上下文设计方案

###### 1. `system prompt`：只放“始终有效”的高层规则

`system prompt` 应该定义 Agent 的稳定角色和行为边界，而不是塞入大量流程细节。

###### 示例

```text
你是企业研发助手，负责帮助用户分析代码、查阅文档、制定技术方案并输出结论。
你的回答要求：
1. 先给结论，再给依据
2. 涉及代码修改时，优先给出最小可行改动
3. 对不确定的信息明确标注假设
4. 大型任务优先拆解并使用子代理处理
5. 对长内容优先写入文件，再按需读取片段
```

###### 最佳实践

- 只放 **角色、风格、原则、边界**
- 不要把详细 SOP 全塞进 `system prompt`
- 动态信息（如“当前用户是管理员”）不要写死，应通过 `dynamic prompt` 或 `runtime context` 注入

---

##### 二、`memory`：只保留“每次都要用”的内容

文档强调：`AGENTS.md` 中的 memory 会 **始终注入**，所以必须保持精简。

###### 适合放进 memory 的内容

```md
# AGENTS.md

- 用户偏好中文回复
- 输出优先使用 markdown
- 代码建议默认遵循团队 Python 风格
- 涉及生产环境操作时先提示风险
```

###### 不适合放进 memory 的内容

- 完整的代码审查流程
- 某个具体系统的 50 条 API 规则
- 某类任务的详细操作手册

这些内容更适合放进 `skills`。

###### 最佳实践

- memory 只保留 **长期稳定、全局生效、简短** 的信息
- 控制在“看一眼就能理解”的规模
- 一旦 memory 变大，模型每轮都要背着它，成本和噪声都会上升

---

##### 三、`skills`：把专业流程按主题拆开，按需加载

对于研发助手，可以设计多个技能文件，而不是一个大而全的知识包。

###### 推荐拆分方式

###### Skill 1：代码审查技能

```md
---
name: code_review
description: 用于代码变更审查、识别 bug 风险、回归风险和测试缺口
---

当用户要求 review、审查 PR、分析变更风险时使用本技能。

流程：
1. 先识别行为变化
2. 再检查 bug 风险
3. 再检查边界条件
4. 最后指出缺失测试
```

###### Skill 2：技术方案技能

```md
---
name: tech_design
description: 用于撰写技术方案、架构取舍、模块设计
---

当用户要求设计方案、技术选型、架构建议时使用本技能。
```

###### Skill 3：内部文档检索技能

```md
---
name: docs_lookup
description: 用于检索内部文档、汇总规范、生成摘要
---
```

###### 最佳实践

- 一个 skill 只解决 **一种任务或一个领域**
- skill 主文件保持简洁，长参考材料放到附属文件中
- 避免 skill 之间高度重叠，否则模型难以判断加载哪个

---

##### 四、`runtime context`：承载“这次运行才有”的信息

文档里有一个很关键的点：`runtime context` **不会自动进入 prompt**，但工具和中间件可以读取它。

对于企业研发助手，适合通过 `runtime context` 传递：

- `user_id`
- `role`（admin / developer / viewer）
- `team`
- `repo_url`
- `feature_flags`
- 数据库连接、API key
- 本轮任务所属项目

###### 示例

```python
context = {
    "user_id": "u_1024",
    "role": "admin",
    "team": "payments",
    "repo": "git@company/payments-service.git",
    "response_style": "concise"
}
```

###### 如何使用

- 工具读取：决定能否访问某些资源
- 动态 prompt 读取：告诉模型“当前用户是 admin，可执行高权限检查”
- 子代理自动继承：减少重复传参

###### 最佳实践

- 运行时状态放 `runtime context`，不要硬编码进 prompt
- 权限、密钥、数据库连接等尤其适合放这里
- 如果只是工具用得到，就没必要额外写进 system prompt

---

##### 五、复杂任务必须用 `subagents` 隔离上下文

这是整篇文档里最值得优先落地的实践之一。

###### 在本例中，哪些任务适合子代理？

###### 主代理负责

- 理解用户目标
- 制定总计划
- 汇总各部分结论
- 输出最终报告

###### 子代理负责

- 分析代码仓库
- 扫描大量日志
- 检索内部 Wiki
- 跑数据库查询
- 汇总测试覆盖率

###### 一个典型流程

用户提问：

> 帮我分析支付服务最近这次重构是否会影响退款链路，并输出风险报告。

主代理可以拆成：

1. 子代理 A：分析 `payments-service` 最近重构的代码改动
2. 子代理 B：检索退款链路相关文档
3. 子代理 C：检查测试覆盖和历史事故记录
4. 主代理：整合为最终风险报告

###### 最佳实践

- 多步骤、长输出、搜索型任务，优先交给子代理
- 给子代理明确要求：**只返回摘要，不返回原始大段数据**
- 如果数据量很大，子代理应先写入文件，再返回文件路径和简述

###### 推荐的子代理提示语风格

```text
你负责独立完成指定分析任务。
只返回：
1. 关键发现
2. 风险点
3. 需要主代理进一步查看的文件路径
不要返回完整原始日志、完整源码拷贝或冗长过程记录。
```

---

##### 六、善用 `filesystem`：大内容存文件，不要塞满对话上下文

在这个例子里，代码 diff、日志、文档摘录、扫描结果都可能非常长。  
文档明确建议：**把大输出持久化到文件系统，再按需读片段**。

###### 错误做法

- 子代理把 3000 行日志直接返回给主代理
- 工具把整个仓库扫描结果全部塞进会话消息
- 一次性把完整文档全文贴给模型

###### 正确做法

- 写入 `reports/refund-risk-analysis.md`
- 写入 `artifacts/recent-diff-summary.txt`
- 写入 `tmp/log_scan_result.txt`
- 主代理只读取必要片段，或用搜索工具定位关键信息

###### 最佳实践

- 大结果先落盘，再引用路径
- 主代理只读“相关片段”，避免全文回灌
- 文件命名要清晰，便于后续检索和 summarization 后恢复

---

##### 七、利用自动压缩机制，但不要完全依赖它

文档提到两类压缩：

- **offloading**：超大输入/输出转成文件引用
- **summarization**：上下文接近上限时，把旧历史压缩成摘要

这很有用，但最佳实践不是“放任上下文膨胀”，而是主动设计减负策略。

###### 在本例中的正确思路

- 先用子代理减少主上下文污染
- 再用文件系统承接大结果
- 最后让自动 offloading / summarization 兜底

###### 最佳实践

- 不要把 summarization 当作主策略，它是保险机制
- 主动控制每一步输出长度
- 在任务阶段切换点，可主动触发总结，保持上下文整洁

---

##### 八、`long-term memory`：跨会话记住真正有价值的信息

企业研发助手经常需要跨多次会话保留信息，比如：

- 用户偏好中文简洁回复
- 某团队偏好输出“风险矩阵”格式
- 某项目的关键目录结构
- 之前调查过的事故结论

这些适合写入 `/memories/` 下的长期记忆。

###### 示例

```text
/memories/preferences/user_u_1024.md
/memories/projects/payments-service.md
/memories/incidents/refund-timeout-2024-11.md
```

###### 应该保存什么

- 稳定的用户偏好
- 高复用的项目知识
- 已确认的研究结论
- 后续会反复用到的结构化信息

###### 不应该保存什么

- 临时任务中间产物
- 未验证的猜测
- 一次性日志片段
- 很快过时的上下文

###### 最佳实践

- 预先约定长期记忆目录结构
- 明确告诉 Agent 什么该写入 `/memories/`
- 只保存“未来还会有价值”的信息

---

##### 九、这套方案的完整落地结构

下面是一个推荐的组织方式：

```text
system_prompt:
  - 定义角色、输出原则、风险边界

AGENTS.md:
  - 用户语言偏好
  - 团队统一输出格式
  - 始终有效的行为准则

skills/
  - code_review/SKILL.md
  - tech_design/SKILL.md
  - docs_lookup/SKILL.md
  - incident_analysis/SKILL.md

runtime context:
  - user_id
  - role
  - team
  - repo
  - feature_flags

subagents:
  - repo_analyzer
  - docs_researcher
  - test_coverage_checker

filesystem:
  - artifacts/
  - reports/
  - tmp/

long-term memory:
  - /memories/preferences/
  - /memories/projects/
  - /memories/incidents/
```

---

##### 十、基于该实例的最佳实践清单

###### 推荐做法

- 用 `system prompt` 定义稳定规则，不塞流程细节
- 用 `memory` 保存始终生效且简短的偏好与约束
- 用 `skills` 管理按需加载的专业能力
- 用 `runtime context` 传递本轮用户、权限、项目、密钥等信息
- 用 `subagents` 承担多步骤和大输出任务，保护主代理上下文
- 用 `filesystem` 保存大体积结果，主代理只读取必要片段
- 用 `long-term memory` 保存跨会话复用的信息
- 把自动 `offloading` 和 `summarization` 当作兜底机制，而不是唯一策略

###### 避免做法

- 把所有规则、流程、文档都塞进 `system prompt`
- 把很长的知识库直接写进 `AGENTS.md`
- 让子代理返回原始全文而不是摘要
- 让主代理直接承接大量日志、全文文档、完整 diff
- 把临时结果写进长期记忆
- 不区分“本轮上下文”和“跨会话知识”

---

##### 十一、一句话总结

如果把这个例子浓缩成一句最佳实践，那就是：

> **把“永远需要的信息”放进 memory，把“按需能力”放进 skills，把“本轮配置”放进 runtime context，把“重任务”交给 subagents，把“大结果”写进 filesystem，把“长期有价值的信息”存进 long-term memory。**
