## 通俗精炼（1）

### 2026-06-15 10:38:02

#### Mimo Code / Obelisk：让 Coding Agent “记得过去”

##### 核心观点

文章讨论了 **AI 编码助手如何检索历史会话、复用关键决策信息**。  
Mimo Code 基于 OpenCode 开发，已经实现了较好的 **session history 检索**；而 Obelisk 在此基础上进一步探索更灵活、更轻量的 Agent 记忆与检索机制。

---

##### 1. 轻量级历史检索：SQLite FTS + BM25

Mimo Code 和 Obelisk 都采用了：

- **SQLite FTS**：全文检索
- **BM25**：经典文本相关性排序算法

作用是让 Coding Agent 能检索过去的 session，知道之前做过什么、为什么这么做，避免在长期任务中丢失关键上下文和决策依据。

---

##### 2. Obelisk 的增强：Agent 可主动写检索逻辑

相比普通检索，Obelisk 提供了一个 **retrieval query runtime**。

也就是说，Agent 不只是被动搜索历史记录，而是可以：

- 自己编写代码检索 session
- 根据任务动态组织查询
- 更灵活地找到相关历史信息

这让 Agent 的历史复用能力更接近“可编程检索层”。

---

##### 3. 新增 Memory：本质是“综合结果缓存”

Obelisk 新加入的 memory，并不是传统意义上的长期记忆，而更像是 **synthesis cache（综合结论缓存）**。

逻辑是：

- 检索历史成本较高
- 如果某次检索和总结形成了稳定结论
- Agent 应该把这个结论写成文档
- 下次直接复用，减少重复检索和推理成本

---

##### 4. Memory 必须人工确认，避免污染上下文

作者强调：**错误的 memory 比没有 memory 更糟糕**。

因此，每条 memory 的：

- 写入
- 归档
- 复用

都需要经过人的确认。  
因为错误或过期的结论会误导 Agent，尤其在代码重构、需求变化、长期维护项目中，memory 很容易变成噪声来源。

---

##### 5. 后续计划：Electron 控制面板

Obelisk 计划推出一个基于 Electron 的控制面板，用于：

- 查看 memory
- 追溯 memory 来源
- 管理和归档历史结论
- 理解 Agent 正在复用哪些信息

它不是必需功能，但能提升透明度，让用户知道 Agent 的判断依据来自哪里。

---

##### 6. 趋势判断：向量数据库可能太重了

作者认为，对 Coding Agent 来说：

> 向量数据库 + Embedding 模型正在显得过于沉重。

相比之下，SQLite FTS、BM25 这类轻量级检索方案，可能更适合本地编码助手场景。

---

##### 总结

这篇内容的核心是：  
**Coding Agent 不只需要更大的上下文窗口，更需要可靠、可追溯、可管理的历史检索与记忆机制。**

Obelisk 的方向是：

- 用轻量检索替代重型向量数据库
- 让 Agent 能主动检索历史
- 把稳定结论沉淀为 memory
- 通过人工确认避免错误记忆污染系统

一句话概括：  
**让 AI 编码助手真正“记得过去”，但不能盲目信任记忆。**

## 结构化（1）

### 2026-06-15 10:54:56

##### 主旨概括

文章讨论了 **Mimo Code 和 Obelisk 在 Coding Agent“历史记忆/会话检索”上的探索**：通过轻量级检索方式，让 Agent 能找回过去的决策和上下文，减少重复推理和信息丢失。作者认为，相比“向量数据库 + embedding 模型”，基于 SQLite FTS、BM25 等轻量方案更适合当前 Coding Agent。

---

##### 1. Mimo Code 的 session history 检索能力

- **Mimo Code 基于 OpenCode 开发**，实现了较好的 **session history 检索**功能。
- 它和 Obelisk 类似，采用：
  - **SQLite FTS**：全文检索能力；
  - **BM25**：经典相关性排序算法。
- 这样做的目的，是让 Agent 能“知道自己过去在做什么”，避免遗忘关键决策。

**简单理解：**  
如果 Agent 之前已经讨论过“为什么选择某个架构方案”，后续再写代码时，它可以检索到这段历史，而不是每次都重新判断。

---

##### 2. Obelisk 在检索能力上走得更远

- 作者提到，**Obelisk 不只是简单检索历史记录**，而是提供了一个 **retrieval query runtime**。
- 这意味着 Agent 可以自己写代码来检索 session，而不是只能被动接受固定检索结果。
- 这样带来的好处是：
  - 检索方式更灵活；
  - Agent 可以根据任务需要主动查找历史信息；
  - 更适合复杂项目中的长期上下文管理。

---

##### 3. 新增 memory 功能：本质是 synthesis cache

- Obelisk 现在加入了 **memory 功能**。
- 但作者强调，它不同于传统意义上的“记忆”，更像是 **synthesis cache（综合结果缓存）**。
- 原因是：
  - 检索历史 session 是有成本的；
  - 如果某次检索和总结产生了稳定结论；
  - Agent 应该把这个结论写成文档，下次可以直接复用。

**例子：**  
如果 Agent 多次检索后确认“项目中统一使用某个状态管理方案”，那就可以把这个结论写入 memory。以后遇到相关问题时，无需再次检索大量历史记录。

---

##### 4. memory 必须人工确认，错误记忆危害更大

- 作者特别强调：**memory 的准确性非常重要**。
- 每条 memory 的：
  - 写入；
  - 归档；
  - 更新；
  
  都必须经过人的确认。
- 原因是他们已经深刻体会到：

> 错误的 memory，比没有 memory 更干扰工作。

**含义：**  
如果 Agent 记住了一个错误结论，它后续可能会反复基于这个错误前提做决策，导致问题越来越严重。

---

##### 5. 后续会推出 Electron 控制面板

- 作者计划后续更新一个基于 **Electron** 的控制面板。
- 这个面板用于：
  - 查看 memory；
  - 追溯 memory 来源；
  - 归档 memory；
  - 理解 Agent 正在复用哪些历史结论。
- 作者说明，这个面板不是必须的，但能让用户更直观地看到 Agent 的记忆使用情况。

---

##### 6. 对 Coding Agent 检索层的判断

- 作者认为，对 Coding Agent 来说，**向量数据库 + embedding 模型太重了**，这正在成为一种共识。
- 他们会继续探索更轻量的检索层方案。
- 核心目标是：

> bring history back again  
> 让历史上下文重新回到 Agent 的工作流中。

##### 8. 热门回复中的补充讨论

###### memory 是否会变成噪声？

有用户提出担忧：

- 即使 memory 当下经过严格判断是正确的；
- 随着项目重构、修改、长期维护；
- 这些 memory 也可能逐渐过时；
- 过时的高度总结性 memory，可能会影响 Agent 的检索路径；
- 因此可能需要人工持续做降权、归档和管理。

###### 作者对 Agent 检索层形态的进一步看法

作者补充说：

- 单纯的 skill 机制局限较多，偏被动；
- Obelisk 作为检索层，不应该只是被动工具；
- 它也应该能主动介入 Agent loop；
- 理想情况下，harness 需要有跨 runtime 标准；
- 可以通过类似 **event bus** 的方式，让检索层更主动地参与 Agent 工作流程。

###### memory 展示形态

作者还提到：

- 查看 memory 更好的形态可能不是传统 app；
- 而是 **GenUI**；
- 但目前模型能力下，GenUI 还不太可用。

这篇文章的核心观点是：**Coding Agent 需要可靠、轻量、可追溯的历史检索和记忆机制**。Obelisk 的方向是用 SQLite FTS、BM25、retrieval query runtime 和人工确认的 memory，让 Agent 既能找回历史，又避免被错误记忆误导。
