## 分析要点

- **核心高价值点**：高质量设计Agent的关键不是生成静态UI，而是在生成界面前先构建可运行的数据结构、状态管理和交互逻辑。

**知识要点**

- Agent产品可分为模型层和Harness层，前者决定核心能力，后者包括提示词、工具链和交互流程。
- 可交互高保真原型比静态设计稿更依赖系统架构能力，需要模型提前设计数据结构和状态流转。
- 设计产物以React、CSS、JSON等代码形式输出，可降低设计Agent与开发Agent之间的沟通损耗。
- 使用设计Agent时可先给目标而非过细需求，再通过多轮反馈迭代原型。

**行动项**

- 尝试使用Claude Design或类似工具生成一个可交互原型，重点观察其数据结构和状态管理实现。
- 对比不同模型在同一产品原型提示词下的UI完整度、交互响应和状态保持能力。
- 在AI辅助设计工作流中优先描述目标和使用场景，再通过迭代修正细节。

## 正文

**宝玉**

为啥 Codex 还不推出类似 Codex Design 的产品？

Anthropic 最近推出了 Claude Design，是我除了编程之外用得最多的 Agent，也推荐过很多次。效果真的好：你用一句话描述想要的 App，它直接给你生成一个可交互的原型，点哪哪都有反应，不仔细看还以为在操作真实的 App。

有网友问：为啥 Codex 还不推出类似 Codex Design 的产品？

简单来说，GPT-5.5 的模型能力还做不好这件事。但要解释清楚为什么，得先理解一个关键区分。

【1】Agent 的两层：模型和 Harness

很多人把 Codex、Claude Design 和 GPT-5.5、Claude Opus 4.8 混在一起说，其实它们是完全不同的两层。

Claude Design 和 Codex 是"产品层"，业界叫 Harness，包括提示词、工具链、UI 交互流程这些工程层面的东西。Claude Opus 4.8 和 GPT-5.5 是"模型层"，是真正干活的大脑。

打个比方：Harness 是厨房，里面有锅碗瓢盆（工具）和菜谱（Skills），模型是厨师。同一套厨房，换个厨师，做出来的菜完全不一样。

理解了这个区分，后面的事情就好说了。

【2】Harness 不是门槛

Claude Design 的 Harness 层技术上不复杂。花点心思逆向一下，提示词、工具代码几乎都可以拿到。我已经做过了，成果在 baoyu-design（[https://github.com/JimLiu/baoyu-design…](https://github.com/JimLiu/baoyu-design)），可以借助 Skill 把 Claude Design 在其他模型上运行。工程上没秘密。

真正拉开差距的是背后的模型。

【3】高精度可交互原型，难在模型

Claude Design 这个名字容易让人误解，以为交付的是 Figma、Photoshop 那样的静态设计图。实际上它交付的比 Figma 更进一步，是融合了设计稿和原型的高精度可交互原型：你不光能看到设计，还能直接上手操作。

这对模型的要求很高。

举个例子。我要做一个类似 X/微博的客户端。让模型画一个好看的静态界面，很多模型都做得到。但要让这个界面能交互就复杂了：切换不同 Timeline，展示不同类型的推文（文本、图片、视频），点赞要变红心，删推要从列表消失，从列表点进详情再返回，状态还要保持住。

要做到这些，模型必须在动手画 UI 之前，先把整套数据结构和状态管理想清楚：tweet 长什么样、timeline 有哪几种、每个按钮当前是什么状态、状态之间怎么联动。这是系统架构设计的活，不是画 UI 的活。

Claude Design 对模型的要求，是同时具备优秀的 UI/UX 设计能力和系统架构设计能力，缺一个效果就大打折扣。这也是为什么我之前反对只产出纯 HTML 的设计稿，那只是静态的 UI 设计，没有融合 UX 交互。

有条件的话可以自己测试感受一下。比如用这个提示词：

Design a X Client for Mac, similar to Tweetbot for Mac from Tapbots

同样的提示词让 Codex 去做，也能出个东西，能看，也能简单交互。但对比一下就知道差距了：列表能滚动，sidebar 不能点；点赞按钮没反应。来回迭代好几轮，才能达到一个勉强凑合的水平。

Claude Design 做出来完全不一样。从 Timeline 切到通知页，从列表点进详情再返回，全程流畅，状态都保持住了。不仔细看真以为在操作一个完成度很高的 App，虽然数据都是模拟的。

Claude Opus 4.8 显然在设计和架构这类场景上做了大量训练和优化。

【4】产出物就是代码

去看 Claude Design 的产出物，注意里面的 data.jsx 文件。它把整个设计的数据结构定义得很清晰，基于这个结构模拟了一套完整数据，然后用 React 在这套数据上构建 UI。

设计产物本身就是代码（React、CSS、JSON），不是 Figma 或 PSD，任何开发者拿到都能直接看出按钮的圆角、主色、间距，照着自己的技术栈实现就行。后续设计变更？git diff 一看就知道改了什么。设计和开发之间的沟通损耗降到了最低。

说得不严谨，应该说设计 Agent 和开发 Agent 之间的沟通损耗很低了。现在都是人在指挥 Agent 去设计，人指挥 Agent 写代码了。

【5】怎么用好 Claude Design

很多人不知道该怎么用好 Claude Design，其实有点像 Vibe Coding：有个基本的想法，先让它做一个版本出来，然后通过 Chat 去指挥 Agent 帮你改，调整几个版本你的思路就清晰了。

整个调整的过程非常神奇，有一种"言出法随"的感觉，你想让它怎么改它总能给你实现出来。这也是为啥我现在很痴迷用 Claude Design，反馈来得太快太过瘾了。

还有一个小技巧：不要说太具体的要求，而是说你的目标是想要什么，让它自由发挥。往往能得到更好的效果，毕竟它训练过几乎所有公共的 UI 设计。

回到最初的问题。Codex 不推类似的设计产品，是因为 GPT-5.5 还扛不住这个活。画个好看的界面很多模型都行，难的是在动手之前把数据结构、状态管理、交互逻辑都想清楚，然后一次性交付一个完整的可交互原型。

目前只有 Claude 的模型做到了。至于能领先多久，就看 OpenAI 或者其他家后面模型的进化速度了。

## 通俗精炼（1）

### 2026-06-15 09:58:21

#### 为什么 Codex 还没有推出类似 Claude Design 的产品？

##### 核心结论

Codex 之所以还没推出类似 Claude Design 的产品，关键不在产品工程，而在模型能力。

Claude Design 的强大，不只是能“画界面”，而是能一次性生成高完成度、可交互、带状态管理的 App 原型。目前 GPT-5.5 在这类任务上还不够稳定，而 Claude Opus 4.8 更适合。

---

##### 1. 先区分：产品层和模型层

作者强调，很多人把 Codex、Claude Design 和 GPT-5.5、Claude Opus 混为一谈，其实它们是两层东西：

- **Codex / Claude Design**：产品层，也叫 Harness  
  包括提示词、工具链、交互流程、UI 等工程封装。
- **GPT-5.5 / Claude Opus 4.8**：模型层  
  是真正负责理解、设计、推理和生成内容的大脑。

类比来说：

> Harness 是厨房，模型是厨师。厨房相似，但厨师水平不同，结果差异很大。

---

##### 2. Claude Design 的门槛不在工程

Claude Design 的产品封装并不神秘。

作者认为，它的提示词、工具代码、工作流等 Harness 层都可以逆向和复现，技术门槛并不高。真正形成差距的是背后的模型能力。

也就是说：

> 做一个“类似 Claude Design 的壳”不难，难的是让模型真的做出高质量结果。

---

##### 3. 难点不是静态 UI，而是完整交互原型

Claude Design 不是简单生成 Figma 式静态设计稿，而是生成：

- 有视觉设计的界面
- 可点击、可跳转的交互
- 有模拟数据
- 有状态变化
- 有完整前端结构的代码原型

例如做一个类似 X / 微博的客户端，不只是把界面画出来，还要处理：

- 不同 Timeline 的切换
- 文本、图片、视频等不同推文类型
- 点赞状态变化
- 删除推文后列表更新
- 列表页和详情页之间跳转
- 返回后状态保持

这要求模型在写 UI 前，先想清楚：

- 数据结构
- 状态管理
- 交互逻辑
- 页面关系
- 组件组织

所以这不是单纯的 UI 设计，而是 **UI/UX 设计能力 + 系统架构能力** 的结合。

---

##### 4. Claude 的优势：设计和架构能力更强

同样的提示词，让 Codex 和 Claude Design 分别生成一个 Mac 版 X 客户端：

- Codex 可以生成能看的界面，也有一些简单交互
- 但经常出现 sidebar 不能点、点赞没反应、状态不完整等问题
- 需要多轮迭代才能勉强可用

而 Claude Design 生成的原型：

- 页面切换自然
- 列表和详情页跳转流畅
- 状态保持完整
- 交互体验接近真实 App

作者判断，Claude Opus 4.8 显然在设计、架构、交互原型这类任务上做了大量优化。

---

##### 5. 设计产物本质上就是代码

Claude Design 输出的不是 Figma、PSD，而是代码，例如：

- React
- CSS
- JSON / JSX 数据结构

其中 `data.jsx` 会清晰定义数据结构和模拟数据，再基于这些数据构建 UI。

这种方式的优势是：

- 开发者可以直接理解设计细节
- 圆角、颜色、间距都在代码里
- 后续修改可以通过 git diff 查看
- 设计 Agent 和开发 Agent 之间沟通成本更低

未来的协作模式可能变成：

> 人指挥设计 Agent 做原型，再指挥开发 Agent 实现产品。

---

##### 6. 如何更好使用 Claude Design

作者建议使用 Claude Design 的方式类似 Vibe Coding：

1. 先给一个大致想法
2. 让它生成第一版
3. 再通过对话持续调整
4. 在迭代中逐渐明确自己的产品思路

一个重要技巧是：

> 不要一开始给太细的要求，而是描述目标，让模型自由发挥。

因为 Claude 可能已经学习过大量公开 UI 设计案例，给它空间，反而更容易得到高质量方案。

---

##### 最终判断

Codex 目前不推出类似 Claude Design 的产品，不是因为做不出产品壳，而是因为 GPT-5.5 还难以稳定完成这类高复杂度任务。

真正难的是：

- 先设计数据结构
- 再规划状态管理
- 再组织交互逻辑
- 最后一次性交付完整可交互原型

目前作者认为，在这件事上，Claude 的模型能力明显领先。OpenAI 或其他厂商能否追上，取决于后续模型进化速度。

- 状态之间如何联动；

作者指出，这其实已经是 **系统架构设计**，而不只是 UI 设计。

1. **优秀的 UI/UX 设计能力**
2. **清晰的系统架构设计能力**

缺少任何一个，效果都会明显变差。

作者也反对只生成纯 HTML 的“设计稿”，因为那往往只是静态 UI，没有真正融合 UX 交互。

##### 5. Claude Design 的产出物本质上就是代码

Claude Design 生成的不是 Figma 文件或 PSD，而是代码，例如：

- React；
- CSS；
- JSON；
- `data.jsx` 等。

- 它会清晰定义整个设计所需的数据结构；
- 基于这些结构模拟完整数据；
- 再用 React 在这些数据上构建 UI。

这带来几个好处：

- 开发者能直接看到：
  - 按钮圆角；
  - 主色；
  - 间距；
  - 组件结构。

- 设计和开发之间的沟通成本大幅降低。

> 设计 Agent 和开发 Agent 之间的沟通损耗变低了。  
> 人在指挥 Agent 做设计，也在指挥 Agent 写代码。

---

##### 6. 如何更好地使用 Claude Design

作者认为，使用 Claude Design 有点像 **Vibe Coding**：

1. 先有一个大概想法；
2. 让它先做出一个版本；
3. 再通过聊天不断指挥它修改；
4. 多调整几轮后，自己的思路也会越来越清晰。

作者形容这种体验像“言出法随”：

> 你想让它怎么改，它往往就能实现出来。  
> 反馈速度很快，所以用起来很上瘾。

###### 使用技巧

作者建议，不要一开始就把需求写得过于具体。

更好的方式是：

- 告诉它你的目标；
- 让它自由发挥。

原因是 Claude 模型已经学习过大量公开 UI 设计，往往能给出比用户自己细抠细节更好的方案。

---

##### 7. 回到核心问题：为什么 Codex 还没有类似产品？

作者的结论是：

- 不是因为 Codex 做不出类似的产品壳；
- 而是因为 **GPT-5.5 目前还撑不起这个任务**。

真正困难的地方不是“画一个好看的页面”，而是：

- 在动手之前先设计好数据结构；
- 想清楚状态管理；
- 处理完整交互逻辑；
- 一次性交付一个接近真实 App 的可交互原型。

作者认为，目前只有 Claude 的模型在这方面做得足够好。

至于 Claude 能领先多久，则取决于：

- OpenAI 后续模型进化速度；
- 其他 AI 公司模型能力的提升速度。
