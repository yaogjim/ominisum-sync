## 正文

**Barret李靖**

最近一直在研究 Codex 和 Claude Code 的记忆设计，发现两者的设计哲学和玩法有很大差异。

Codex 的设计目标是让一个 agent 运行的够久，所以它的执行策略偏向于把记忆当做工具，持续构建工作上下文（work memory），为当前的 goal 服务。OpenClaw 也是这个工作模式。

Claude Code 更像把记忆当成认知架构。它不只记录当前目标，还会在不同时间尺度上持续沉淀用户偏好、上下文变化、执行经验和行为反馈。它更偏向于让多个 agent 各自在独立上下文中高效工作，由外部逻辑（文件记录、coordinator 管理等）确保整体进度不丢失。它不信任任何单个 agent 能跑到底，所以把进度状态放在 agent 之外。

Codex 也意识到当前记忆设计的缺陷，尝试引入更持久的记忆机制（执行 codex features enable memories 可启用），支持跨对话记住你的项目上下文。每个交互轮次结束后，Codex 会自动从对话中提取有价值的信息（架构决策、代码约定、踩坑经验等），存到 \~/.codex/memories/。

Codex 更像是一个执行者，专注于完成任务，而不是管理记忆或上下文。它的设计哲学是“做就对了”，不太关心过程中的失误或偏差，只要最终结果符合预期就行。正因如此，很多人体感 Codex 在指令遵循方面做的更好。

Claude Code 更像是一个学习者，通过不断的试错和反思来提升自己的能力。它不仅关注完成任务，还关注如何完成任务。它会持续记录和分析执行过程中的每一步，积累经验和反馈，不断优化自己的行为策略。

二者各有优劣，你更看好哪种模式？

## 通俗精炼（1）

### 2026-05-04 00:48:47

#### Codex vs Claude Code：两种「记忆设计」哲学的差异

##### 核心观点

文章对比了 **Codex** 和 **Claude Code** 在「记忆机制」上的不同设计思路：  
**Codex 更像执行者，强调把任务做完；Claude Code 更像学习者，强调持续积累和优化。**

---

##### Codex：为当前任务服务的工作记忆

Codex 的目标是让一个 Agent 能够持续运行并完成任务。  
它更倾向于把记忆当作一种 **工具**，围绕当前目标不断构建「工作上下文」。

特点是：

- 关注当前任务目标
- 记忆主要服务于执行过程
- 强调快速推进和结果交付
- 不太纠结过程中的失误，只要最终结果正确即可

因此，很多用户会感觉 **Codex 的指令遵循能力更强**，更像一个“执行力很强的工程师”。

---

##### Claude Code：作为认知架构的长期记忆

Claude Code 不只是记录当前任务，而是把记忆看成 Agent 的一部分认知能力。  
它会在不同时间尺度上沉淀：

- 用户偏好
- 项目上下文变化
- 执行经验
- 行为反馈
- 过程中的试错和反思

它更适合多个 Agent 在不同上下文中协作，由外部机制维护整体状态，避免单个 Agent 中断导致进度丢失。

---

##### 关键差异：信任单 Agent，还是外部管理状态

Codex 更像相信一个 Agent 可以持续推进任务，所以重点是让它在当前上下文里跑得更久。  

Claude Code 则不完全信任任何单个 Agent 能一路跑到底，因此把进度和状态放在 Agent 外部，通过文件、协调器等方式来保障任务连续性。

---

##### Codex 也在补足长期记忆能力

Codex 已经意识到当前记忆设计的不足，开始引入更持久的记忆机制。

启用后，它可以跨对话记住项目上下文，并在每轮交互结束后自动提取有价值信息，例如：

- 架构决策
- 代码规范
- 踩坑经验
- 项目约定

这些内容会被保存到本地记忆目录中。

---

##### 总结：两种模式各有优势

| 维度 | Codex | Claude Code |
|---|---|---|
| 角色定位 | 执行者 | 学习者 |
| 关注重点 | 完成任务 | 优化过程 |
| 记忆方式 | 当前工作上下文 | 长期认知沉淀 |
| 优势 | 指令遵循强、执行直接 | 适合长期协作和持续改进 |
| 风险 | 过程经验沉淀不足 | 复杂度更高、依赖外部管理 |

---

##### 一句话总结

**Codex 更适合“明确任务、快速完成”；Claude Code 更适合“长期项目、持续学习和多 Agent 协作”。**

## 高价值（1）

### 2026-05-04 06:59:44

#### 高价值信息提取

##### 1. 一句话判断

> 最值得保留的是：**AI 编程 Agent 的关键差异，不在模型能力本身，而在“记忆放在哪里、服务什么目标”：Codex 把记忆当执行工具，Claude Code 把记忆当认知架构。**

**价值评级：A**

**精炼理由：**  
这篇短文真正有价值的是提出了一个判断 Agent 产品形态的框架：**长期任务能力，不只取决于上下文长度或模型聪明程度，而取决于记忆系统如何设计、由谁维护、服务单 Agent 还是多 Agent 协作。**

---

##### 2. 最重要的洞见

###### 洞见 1：记忆不是一个功能，而是一种产品哲学

###### **核心观点：**  
> Codex 把记忆当作完成当前任务的工具；Claude Code 把记忆当作持续学习和组织协作的认知架构。

**为什么重要：**  
很多人讨论 AI Agent 时，会把“记忆”理解成一个附加能力：能不能记住项目背景、用户偏好、历史决策。  
但这篇文章指出，记忆其实决定了 Agent 的工作方式：

- Codex 的记忆服务于当前 goal；
- Claude Code 的记忆服务于长期行为优化；
- 前者偏执行，后者偏学习；
- 前者追求任务完成，后者追求过程沉淀。

这不是功能差异，而是系统定位差异。

**反常识之处：**  
常见认知是：  
> 记忆越多，Agent 越强。

但文章隐含的判断是：  
> 记忆如何组织，比记住多少更重要。

记忆如果只是当前任务上下文，就是执行缓存；  
记忆如果能跨时间尺度沉淀经验、偏好、反馈，就是认知基础设施。

**可迁移价值：**  
判断任何 AI 产品时，不要只问：

- 它能记住什么？
- 上下文窗口多长？
- 是否支持 memory？

更应该问：

- 记忆服务于当前任务，还是长期学习？
- 记忆由单个 Agent 自己维护，还是由外部系统维护？
- 记忆是临时工作区，还是可复用的组织资产？

**我应该记住什么：**  
> 记忆设计决定 Agent 的边界：它到底是一个“更强的执行器”，还是一个“会成长的工作系统”。

---

###### 洞见 2：真正可靠的长期 Agent，不应该信任单个 Agent 能跑到底

###### **核心观点：**  
> Claude Code 更倾向于让多个 Agent 在独立上下文中工作，并把关键进度状态放在 Agent 外部，而不是相信某个 Agent 能从头到尾稳定完成任务。

**为什么重要：**  
这是文章里最有工程含量的一点。

很多人对 Agent 的想象是：  
> 给它一个目标，它自己规划、执行、修正，直到完成。

但 Claude Code 的设计哲学更现实：  
> 不假设单个 Agent 永远稳定，而是通过外部文件、coordinator、状态管理机制确保整体进度不丢失。

这相当于把 Agent 从“全能个体”降级为“可替换工作单元”，再用外部系统保证可靠性。

**反常识之处：**  
常见方向是追求更长上下文、更强单 Agent、更连续的自主执行。  
但这里的判断是：

> 长期可靠性不一定来自一个更强的 Agent，而可能来自一个更好的外部状态系统。

这和传统软件工程很像：  
可靠系统不是因为单个进程永不失败，而是因为状态、日志、检查点、调度和恢复机制设计得好。

**可迁移价值：**  
这可以迁移到所有 Agentic 系统设计：

- 不要把状态完全放进对话上下文；
- 不要假设 Agent 会一直记得自己做过什么；
- 把关键进度、决策、约束、待办、错误记录外部化；
- Agent 可以失败、重启、替换，但系统进度不能丢。

**我应该记住什么：**  
> 构建长期 Agent 的核心，不是让 Agent 永不遗忘，而是让系统即使在 Agent 遗忘时仍能继续运行。

---

###### 洞见 3：Codex 的“少反思、多执行”反而可能带来更好的指令遵循体验

###### **核心观点：**  
> Codex 更像执行者，目标是完成任务；它不太关心过程中的偏差，只要最终结果符合预期，因此用户会感觉它指令遵循更好。

**为什么重要：**  
这解释了一个常见体感差异：有些 AI 工具并不显得“更会思考”，但用起来更顺手。  
原因可能不是模型更强，而是产品哲学更偏向：

- 减少自我发挥；
- 减少过度解释；
- 减少过程反思；
- 更集中地完成用户明确要求。

**反常识之处：**  
很多人以为 Agent 越会反思、越会总结、越会自我优化，就越好。  
但在执行型任务中，过度“学习者心态”可能反而干扰用户：

- 它可能分析太多；
- 可能引入额外步骤；
- 可能改变原始意图；
- 可能把过程优化凌驾于任务完成之上。

所以，反思能力不是无条件加分项，取决于任务类型。

**可迁移价值：**  
在产品设计中，需要区分两类场景：

| 场景 | 更适合的 Agent 类型 |
|---|---|
| 明确需求、短周期交付、强指令约束 | 执行者型 Agent |
| 长期项目、偏好沉淀、复杂协作、持续改进 | 学习者型 Agent |

**我应该记住什么：**  
> 不要把“会反思”误认为一定更好；有些任务需要的是低损耗执行，而不是高存在感思考。

---

###### 洞见 4：记忆的价值不只在“跨对话”，更在于自动提取结构化经验

###### **核心观点：**  
> Codex 也在引入持久记忆：每轮交互后自动提取架构决策、代码约定、踩坑经验等，存入本地 memory。

**为什么重要：**  
这里轻描淡写，但很关键。

普通“记忆”只是保存历史聊天记录；  
高价值记忆是从历史中抽取可复用知识，例如：

- 架构决策；
- 代码规范；
- 项目约定；
- 已踩过的坑；
- 用户偏好；
- 不应重复的错误。

这说明 AI 记忆的关键不是存储，而是**萃取**。

**反常识之处：**  
很多人以为记忆系统就是“把过去内容都存起来”。  
但真正可用的记忆系统要做的是：

> 从冗长历史中提炼未来决策需要的压缩知识。

否则记忆只会变成噪音堆积。

**可迁移价值：**  
无论是个人知识管理、团队复盘，还是 AI Agent 设计，都应该从“记录一切”转向“提取可复用经验”：

- 不要只保存会议纪要，要提取决策；
- 不要只保存事故过程，要提取防错规则；
- 不要只保存项目文档，要提取约定和边界条件；
- 不要只保存聊天记录，要提取未来会影响判断的信息。

**我应该记住什么：**  
> 好记忆不是完整记录过去，而是压缩出未来可用的判断依据。

---

##### 3. 底层逻辑

###### **逻辑一：Agent 的长期能力 = 模型能力 × 记忆结构 × 状态管理**

- **表层现象：**  
  Codex 和 Claude Code 都有记忆能力，但使用体验和工作哲学不同。

- **深层原因：**  
  Codex 的记忆主要服务当前任务执行；Claude Code 的记忆更像跨时间尺度的认知系统，并通过外部文件、coordinator 等方式管理状态。

- **推导结论：**  
  长期 Agent 的竞争不只是模型竞争，而是记忆架构和状态管理能力的竞争。

---

###### **逻辑二：单 Agent 连续性不可靠，所以关键状态必须外部化**

- **表层现象：**  
  Claude Code 倾向于多个 Agent 分别在独立上下文中工作。

- **深层原因：**  
  它不默认任何单个 Agent 能稳定跑完整个长期任务，所以把任务进度、关键状态、上下文变化放到 Agent 外部维护。

- **推导结论：**  
  可靠的 Agent 系统应该像分布式系统一样设计：允许局部失败，但保证整体状态可恢复、可追踪、可接续。

---

###### **逻辑三：执行优化与学习优化存在张力**

- **表层现象：**  
  Codex 给人的感觉是指令遵循更好；Claude Code 更关注过程记录和行为优化。

- **深层原因：**  
  Codex 的目标函数更偏“完成任务”；Claude Code 的目标函数更偏“持续学习”。  
  前者降低过程复杂度，后者增加反思和沉淀。

- **推导结论：**  
  不同任务需要不同 Agent：短期明确任务需要执行者，长期复杂项目需要学习者。

## 结构化（1）

### 2026-05-04 08:13:55

#### 文章主旨概括

作者对比了 **Codex** 和 **Claude Code** 的“记忆设计”思路：前者更像专注执行任务的工具型 agent，后者更像会持续学习和沉淀经验的认知型系统。两者代表了不同的 agent 设计哲学，各有优势和适用场景。

---

##### 1. Codex：把记忆当作“工具”，服务当前任务

- Codex 的核心目标是：**让一个 agent 能持续运行足够久，并完成当前目标**。
- 它的记忆更偏向于构建当前任务所需的 **工作上下文（work memory）**。
- 这种设计强调：围绕当前 goal，不断补充和维护有用信息。
- 作者提到 **OpenClaw** 也是类似的工作模式。

简单理解：  
Codex 更像一个执行力很强的员工，重点是“把眼前任务做好”。

---

##### 2. Claude Code：把记忆当作“认知架构”

- Claude Code 不只是记录当前目标，还会在不同时间尺度上沉淀更多信息，包括：
  - 用户偏好
  - 上下文变化
  - 执行经验
  - 行为反馈
- 它更强调长期学习和经验积累。
- Claude Code 倾向于让多个 agent 在各自独立上下文中工作，再通过外部机制保持整体进度。

例如：

- 用文件记录任务状态；
- 用 coordinator 管理多个 agent；
- 把项目进度放在 agent 外部，而不是依赖某个单一 agent 一直跑到底。

简单理解：  
Claude Code 更像一个会复盘、会学习的团队协作者。

---

##### 3. 两者对 agent 可靠性的假设不同

- Codex 更倾向于相信单个 agent 能持续完成任务，因此重点放在当前执行链路中维护上下文。
- Claude Code 则不完全信任任何单个 agent 能从头跑到尾，所以把关键状态放在 agent 之外。

这意味着：

- Codex 更强调“当前 agent 持续推进”；
- Claude Code 更强调“即使 agent 中断或切换，整体进度也不会丢”。

---

##### 4. Codex 也在补足长期记忆能力

作者提到，Codex 已经意识到当前记忆设计的不足，并开始引入更持久的记忆机制。

具体方式：

- 可以通过执行 `codex features enable memories` 启用记忆功能；
- 支持跨对话记住项目上下文；
- 每轮交互结束后，Codex 会自动从对话中提取有价值的信息；
- 这些信息会被存储到：

```bash
~/.codex/memories/
```

Codex 会提取的内容包括：

- 架构决策；
- 代码约定；
- 踩坑经验等。

这说明 Codex 正在从“短期执行记忆”向“长期项目记忆”扩展。

---

##### 5. Codex 更像“执行者”：重结果、轻过程

作者认为 Codex 的设计哲学可以概括为：**“做就对了”**。

它更关注：

- 任务是否完成；
- 最终结果是否符合预期；
- 指令是否被准确执行。

它不太关注：

- 执行过程中是否走过弯路；
- 是否出现过偏差；
- 中间过程是否值得复盘。

因此，很多用户会感觉：  
**Codex 在指令遵循方面表现更好。**

---

##### 6. Claude Code 更像“学习者”：重过程、重反馈

Claude Code 不仅关注任务完成，还关注“如何完成任务”。

它会持续记录和分析：

- 每一步执行过程；
- 试错情况；
- 用户反馈；
- 行为策略的效果。

通过这些信息，它会不断优化自己的行为方式。

简单来说：  
Claude Code 更像一个会复盘的助手，不只是完成任务，还会从任务中学习。

---

##### 7. 作者观点：两种模式各有优劣

作者没有明确站队，而是提出问题：  
**你更看好哪种模式？**

可以概括为：

| 对比项 | Codex | Claude Code |
|---|---|---|
| 角色定位 | 执行者 | 学习者 |
| 记忆定位 | 工具，服务当前任务 | 认知架构，长期沉淀 |
| 优势 | 指令遵循强、执行直接 | 长期适应强、能积累经验 |
| 风险 | 可能忽略过程偏差 | 系统设计更复杂 |
| 适合场景 | 明确目标、快速完成任务 | 长期项目、多 agent 协作、持续优化 |

---

##### 8. 热门回复补充

评论区中有用户认为：

- 从长期使用看，**Claude Code 可能更有优势**；
- 但无论使用哪种工具，重点都应该放在自己的 **业务 workspace 设计** 上；
- 也有人提出可以观察：哪种模式更接近人类完成任务和反馈改进的方式。

这说明讨论焦点不仅是工具本身，也包括如何设计更好的工作流和协作环境。
