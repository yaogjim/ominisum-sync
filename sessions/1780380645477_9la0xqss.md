- Agent沙箱不应默认拥有开放互联网访问，应通过基础设施策略限制可访问目标。

- 动态凭证回调可支持OAuth刷新、用户范围令牌和内部认证服务生成的短期凭证。

**Harrison Chase**

### Auth Proxy 如何保障 LangSmith 代理沙箱的网络访问安全

If you’ve ever worked at a large enterprise, you have probably seen the standard corporate laptop setup.

There’s endpoint protection, browser filtering, device management, network controls, certificate stores, secret scanners… a long list of tools whose job is to stop an otherwise trusted employee from accidentally leaking credentials, installing a malicious package, or visiting the wrong page.

That tooling exists because developers have broad access. They run code, install dependencies, and copy data between systems. They authenticate to internal and external services. A lot of enterprise security is built around making that powerful, open-ended environment safer.

Agents change the scale and shape of this problem. You’re not just giving one developer a laptop. You may be spawning thousands, or eventually millions, of “untrusted developers” that can write code, run commands, install packages, and make network requests on your behalf.

For human developers, the environment often needs to stay open by default. Developers need to explore, debug, install tools, and reach new services as their work changes. For agents, the default can be different. If the task is known, the network can be narrower. If the agent only needs GitHub and an LLM provider, it should not be able to talk to every random host on the internet. If it needs a credential, that credential should not have to exist inside the runtime at all.

This is where sandbox networking becomes a first-class part of the agent harness.

#### Introducing the sandbox Auth Proxy

[LangSmith Sandboxes](https://www.langchain.com/langsmith/sandboxes) give agents isolated environments for running code and interacting with filesystems without affecting your main infrastructure. But isolation is only one part of the story. Agents still need to call external APIs like model providers, GitHub, package registries, internal services, data APIs, and more.

[sandbox auth proxy](https://docs.langchain.com/langsmith/sandbox-auth-proxy)

Instead of putting API keys into the sandbox as environment variables or files, the proxy sits on the outbound network path and controls how sandboxed code interacts with external services. It can enforce policy for which destinations are allowed, what authentication is applied, and how requests are shaped before they leave the sandbox. Sandbox code makes a normal request to an external API, while credentials and access rules are handled outside the sandbox at the network layer.

![Image](https://pbs.twimg.com/media/HI0NSDYbsAAI2iO?format=jpg&name=large)

Three things become much easier with this model:

1. Credentials stay out of the runtime. The agent can use an API without being able to read the API key, which reduces the damage from prompt injection, malicious dependencies, accidental logging, and model mistakes.
2. Network access becomes explicit. If an agent should only talk to OpenAI, Anthropic, GitHub, or an internal API, that should be encoded as infrastructure policy rather than left to the agent’s judgment.
3. Teams get a cleaner separation of concerns: the agent focuses on the task, the sandbox provides isolation, the proxy handles network authorization and credential injection, and the application or auth service handles user-scoped access and token refresh.

This separation is important because agents are untrusted and you can’t review every branch they will take ahead of time. The safer pattern is to give them constrained environments where the possible actions are bounded by infrastructure, so the auth proxy keeps credentials out of the sandbox entirely.

#### How it works

At a high level, the auth proxy is a controlled intermediary for sandbox egress, which looks like this:

1. The agent or sandboxed code makes an outbound request.
2. The request passes through Auth Proxy.
3. Auth Proxy checks the configured policy for that destination.
4. The proxy can block the request, allow it, or attach headers.
5. The request continues to the destination without exposing credentials to the runtime.

A simple rule might say: when the sandbox calls

api.openai.com, inject an \`Authorization\` header whose value comes from a LangSmith workspace secret. Another rule might say: when the sandbox calls

api.github.com

on \`/repos/\*\` or \`/user\`, inject a GitHub token.

Because we control the network for the sandbox, this is completely transparent. This is not implemented by hoping every language, package manager, SDK, or subprocess respects \`HTTP\_PROXY\`. Not all runtimes behave the same way, and agents often execute arbitrary code paths you didn’t write.

![Image](https://pbs.twimg.com/media/HI0NdMdb0AAE7Pd?format=jpg&name=large)

#### Authenticate without handing credentials to your agent

The proxy supports many different policy configurations. One powerful one is the ability to inject headers into requests that match certain characteristics.

Headers can be configured with different types:

- \`workspace\_secret\`: references a secret stored in LangSmith workspace settings
- \`plaintext\`: stored and returned as-is, for non-sensitive headers
- \`opaque\`: write-only, encrypted at rest, and never returned by the API

For example, in the example of the OpenAI rule, we can inject:

```text
{
  "name": "Authorization",
  "type": "workspace_secret",
  "value": "Bearer {OPENAI_API_KEY}"
}
```

The sandbox code does not need to know the API key. It does not need an \`.env\` file. It does not need a secret mounted into its filesystem. It just calls the API, and the proxy adds the right header when the destination matches the configured rule.

这对代理系统来说是一个更好的默认设置。开发人员可能需要直接访问凭证以调试新的集成，而代理通常不需要。代理需要的是凭证的作用——即调用特定 API 的能力——而不是直接持有凭证本身。

随着代理运行次数的增加，这种区别变得更加重要。对于单个沙箱，泄露的密钥是个问题，但对于大量沙箱（或沙箱集群），直接将凭证放入运行时是一个重大风险。每个工具调用、包安装、日志条目和文件写入都是可能的凭证泄露路径。头部注入将凭证移出了该攻击范围。

#### 锁定网络

凭证只是网络问题的一半；代理还需要出站策略，因为它们可以安装依赖、获取脚本、调用 API 以及遵循来自不可信内容的指令。如果每个沙箱都有开放的互联网访问权限，那么被入侵或困惑的代理可能会到达它不应该到达的地方。

同一个注入头信息的代理边界，也可以成为团队定义哪些目标是预期的地方，例如：

- allowing the model provider API and blocking everything else
- allowing GitHub API paths the agent needs, but not arbitrary GitHub-adjacent domains
- allowing a package registry, but only the internal mirror
- blocking known malicious or untrusted package registries
- preventing accidental calls to unauthorized third-party services

This is especially important for package management. If a coding agent can run \`pip install\`, \`npm install\`, or \`curl \| bash\`, it can fetch and execute code. The security question is not just whether the sandbox can contain execution, but whether you can control where that code comes from and where it can send data.

#### Dynamic credentials for real production auth

While integrating sandboxes with LangSmith Fleet, we realized that for advanced use cases, static configuration may not be sufficient. Fleet agents may need delegated access and OAuth token refreshes while still keeping the actual credential handling outside the agent runtime.

Other examples of advanced use cases include:

- short-lived OAuth access tokens
- per-user-scoped tokens
- credentials minted by an internal auth service
- tokens that need to be refreshed based on the destination or current user context

For these cases, the auth proxy supports

[dynamic credentials with callbacks](https://docs.langchain.com/langsmith/sandbox-auth-proxy#dynamic-credentials-with-callbacks).

Instead of putting all credential material into static rules, you configure a callback under \`proxy\_config\`. When the sandbox makes a request to a matching host and the proxy does not have a cached credential, the proxy calls your callback endpoint with the target host and port. Your endpoint returns the headers to inject, and the proxy caches the result for a configured TTL.

The contract is simple: the callback returns a JSON object like:

```text
{
  "headers": {
    "Authorization": "Bearer <token>",
    "X-Org-Id": "..."
  }
}
```

The proxy injects those headers into the outbound request. If the callback fails, returns malformed JSON, or responds with a non-2xx status, the proxy fails closed and rejects the sandbox request rather than sending it without credentials. This is the pattern lets the sandbox network layer participate in auth flows without exposing refresh tokens or long-lived credentials to the sandbox.

#### What this unlocks next

Once you control the sandbox network path, the proxy can become more than a credential injector, and there are a few natural extensions.

1. DNS remapping: a team may want requests to public package registries to resolve to an internal Artifactory or package mirror instead. You may want to point LLM API requests towards an internal gateway. The agent still runs normal install commands, but the network layer points those requests at approved infrastructure.
2. Network logging: if agents are doing meaningful work over long horizons, teams will want to know which services they called, which packages they fetched, and which domains they attempted to reach. Network logs become part of the audit trail for agent behavior.
3. Request transformation: since the proxy sees outbound requests, it can eventually become a place to apply deterministic transformations, such as redacting PII, adding organization metadata, enforcing request shape, or blocking payloads that violate policy.

The broader point is that agent infrastructure needs control planes that live outside the runtime and aren’t exposed to agent instructions and decisions.

#### The new default for agent egress

Agents need credentials and network access to do useful work, but those capabilities should not require putting long-lived secrets or unrestricted internet access inside the runtime. Auth Proxy gives sandboxed agents a safer default by keeping credentials outside the environment, routing outbound traffic through a controlled layer, and applying policy consistently across languages, SDKs, package managers, and CLIs.

The result is a sandbox model that gives agents access to the systems they need, while keeping credentials and network policy under platform control.

##### 一、总结

LangSmith 的 **Sandbox Auth Proxy** 用来保护 AI 代理沙箱的网络访问安全。

核心做法：

- **凭证不放进沙箱**
  - 不把 API Key 写进 `.env`、文件或环境变量
  - 由沙箱外部的 Auth Proxy 在请求时自动注入认证头

- **网络访问可控**
  - 代理只能访问被允许的目标
  - 例如只允许访问 OpenAI、Anthropic、GitHub 或内部 API

- **策略统一执行**
  - 不依赖代码、SDK、包管理器是否遵守代理配置
  - 所有出站请求都经过统一网络控制层

- **支持动态凭证**
  - 可通过回调获取短期 OAuth Token、用户级 Token
  - 凭证仍不暴露给代理运行环境

##### 二、深入浅出解读

可以把 AI 代理想象成一个“自动写代码的实习生”。

它可能会：

- 写代码
- 安装依赖
- 调 API
- 访问 GitHub
- 请求模型服务
- 运行命令

问题是：  
**这个实习生很能干，但不一定可信。**

如果直接把 API Key 给它，就像把公司钥匙交给它：

> 一旦它被提示注入、恶意依赖、错误代码影响，密钥就可能泄露。

Auth Proxy 的思路是：

> 不给它钥匙，只让它通过门禁系统办事。

也就是说：

1. 代理发起请求  
2. 请求经过 Auth Proxy  
3. Auth Proxy 判断能不能访问  
4. 如果允许，再帮它加上认证信息  
5. 代理本身看不到密钥  

例如：

```text
代理请求 OpenAI API
        ↓
Auth Proxy 检查规则
        ↓
允许访问，并自动加 Authorization
        ↓
请求发送到 OpenAI
```

这样代理可以正常工作，但不能偷看到 API Key。

---

##### 三、它解决了什么问题？

###### 1. 防止密钥泄露

以前：

```text
API Key 放进沙箱
代理、依赖、日志、文件都有机会接触它
```

现在：

```text
API Key 留在沙箱外
代理只能使用能力，不能读取凭证
```

---

###### 2. 限制乱访问互联网

如果代理能访问任意网站，就可能：

- 下载恶意包
- 调用未知服务
- 泄露数据
- 执行不安全脚本

Auth Proxy 可以限制：

```text
只允许访问指定 API
只允许访问内部包镜像
禁止访问未知域名
禁止访问不可信服务
```

---

###### 3. 更适合大规模代理运行

一个代理泄露密钥已经很危险。  
如果是成千上万个代理同时运行，风险会被放大。

所以必须把：

- 凭证管理
- 网络策略
- 权限控制

放到沙箱外部，由平台统一控制。

---

##### 四、我的意见

这是一个非常合理的安全设计。

AI 代理和人类开发者不同：

- 人类需要开放环境来探索
- 代理更适合“最小权限”
- 任务明确时，访问范围就应该明确限制

我认为未来 AI Agent 平台的默认安全模式应该是：

```text
不给密钥
不给全网访问
只给必要能力
所有出站流量可审计
```

Auth Proxy 的价值不只是“自动加 API Key”，而是把代理运行时和安全控制面分离。

一句话概括：

> AI 代理可以干活，但不能拿钥匙；可以出门，但必须走安检。

#### Auth Proxy 如何保障 LangSmith 代理沙箱的网络访问安全

文章核心观点：随着 AI Agent 能像开发者一样运行代码、安装依赖、调用 API，传统“开放网络 + 运行时放密钥”的方式风险急剧放大。LangSmith Sandboxes 通过 **Auth Proxy（认证代理）** 将凭证管理和网络访问控制移到沙箱外部，让 Agent 在受控环境中安全访问所需服务。

---

##### 1. 为什么 Agent 需要新的网络安全模型

在大型企业中，开发者电脑通常会配备端点保护、浏览器过滤、设备管理、网络控制、证书管理、密钥扫描等工具。

这些工具存在的原因是：

- 开发者权限很广：能运行代码、安装依赖、访问内外部服务；
- 他们可能不小心泄露凭证、安装恶意包、访问危险网站；
- 企业安全体系就是为了让这种“开放但强大”的工作环境更安全。

但 Agent 改变了问题规模：

- 不再只是给一个开发者一台电脑；
- 而是可能同时运行成千上万，甚至未来数百万个“非完全可信的开发者”；
- 这些 Agent 也能写代码、执行命令、安装包、发起网络请求。

因此，Agent 的默认环境不应像人类开发者那样“开放优先”，而应根据任务进行更严格限制。

---

##### 2. Agent 的网络访问应默认收窄

人类开发者通常需要开放环境来探索、调试、安装工具、访问新服务。

但 Agent 不同：

- 如果任务已知，网络范围就可以被提前限制；
- 如果 Agent 只需要访问 GitHub 和某个 LLM 服务商，就不应允许它访问任意互联网主机；
- 如果 Agent 需要凭证，也不应该让凭证直接存在于运行时环境中。

这意味着：**沙箱网络控制应成为 Agent 运行框架中的核心能力。**

---

##### 3. LangSmith Sandboxes 与 Auth Proxy 的作用

LangSmith Sandboxes 为 Agent 提供隔离环境，使其可以运行代码、操作文件系统，而不会影响主基础设施。

但仅有隔离还不够，因为 Agent 仍然需要访问外部服务，例如：

- 模型服务商 API；
- GitHub；
- 包注册表；
- 内部服务；
- 数据 API。

Auth Proxy 的作用是：  
**不把 API Key 作为环境变量或文件放入沙箱，而是在出站网络路径上统一控制请求。**

它可以决定：

- 哪些目标地址允许访问；
- 请求是否需要认证；
- 是否注入认证头；
- 请求离开沙箱前是否需要被修改或阻止。

例如，沙箱代码正常请求 OpenAI API，但真正的 API Key 由 Auth Proxy 在网络层自动加上，Agent 本身无法读取密钥。

---

##### 4. Auth Proxy 带来的三个主要好处

###### 4.1 凭证不进入运行时

Agent 可以调用 API，但无法读取 API Key。

这样可以降低以下风险：

- Prompt Injection 窃取密钥；
- 恶意依赖读取环境变量；
- 日志意外打印密钥；
- 模型错误操作导致泄露。

###### 4.2 网络访问变得明确

如果 Agent 只应访问：

- OpenAI；
- Anthropic；
- GitHub；
- 某个内部 API；

这些规则应写成基础设施策略，而不是依赖 Agent 自己判断。

###### 4.3 职责分离更清晰

不同组件各司其职：

- Agent：专注完成任务；
- Sandbox：提供隔离环境；
- Auth Proxy：负责网络授权与凭证注入；
- 应用或认证服务：负责用户级访问控制和 Token 刷新。

这对 Agent 很重要，因为它们是不完全可信的，且无法提前审查其所有执行路径。

---

##### 5. Auth Proxy 的基本工作流程

Auth Proxy 是沙箱出站流量的受控中间层，流程如下：

1. Agent 或沙箱代码发起外部请求；
2. 请求经过 Auth Proxy；
3. Auth Proxy 检查目标地址对应的策略；
4. 代理决定阻止、放行，或附加请求头；
5. 请求继续发送到目标服务，但凭证不会暴露给沙箱运行时。

###### 示例

一条规则可以规定：

- 当沙箱请求 `api.openai.com` 时；
- 自动注入 `Authorization` 请求头；
- 请求头的值来自 LangSmith workspace secret。

另一条规则可以规定：

- 当沙箱请求 `api.github.com` 的 `/repos/*` 或 `/user` 路径时；
- 自动注入 GitHub Token。

这种机制不是依赖每种语言、SDK、包管理器或子进程是否遵守 `HTTP_PROXY`，而是在沙箱网络层统一控制，因此更可靠。

---

##### 6. 不把凭证交给 Agent，也能完成认证

Auth Proxy 支持多种策略配置，其中一个重要能力是：  
**根据请求特征自动注入 Header。**

Header 支持几种类型：

- `workspace_secret`：引用 LangSmith 工作区中的密钥；
- `plaintext`：明文保存，适合非敏感 Header；
- `opaque`：只写、静态加密保存，API 不会返回其内容。

###### OpenAI 示例

```json
{
  "name": "Authorization",
  "type": "workspace_secret",
  "value": "Bearer {OPENAI_API_KEY}"
}
```

在这种模式下：

- 沙箱代码不需要知道 API Key；
- 不需要 `.env` 文件；
- 不需要把密钥挂载到文件系统；
- 只需正常调用 API，代理会在匹配规则时自动添加 Header。

文章强调：  
Agent 需要的是“使用凭证产生的能力”，例如调用某个 API，而不是直接拥有凭证本身。

---

##### 7. 为什么大规模 Agent 场景下更重要

对于单个沙箱，密钥泄露已经是问题；  
对于大量沙箱或沙箱集群，风险会更严重。

因为每一个环节都可能成为泄露路径：

- 工具调用；
- 包安装；
- 日志记录；
- 文件写入；
- 依赖执行。

将凭证从运行时移到网络层，可以显著减少攻击面。

---

##### 8. 锁定网络访问范围

凭证只是网络安全的一部分，Agent 还需要明确的出站访问策略。

因为 Agent 可以：

- 安装依赖；
- 下载脚本；
- 调用 API；
- 执行来自不可信内容的指令。

如果每个沙箱都能访问整个互联网，被攻陷或误导的 Agent 就可能访问不该访问的地方。

可配置的网络策略包括：

- 只允许访问模型服务商 API，阻止其他目标；
- 只允许访问 Agent 所需的 GitHub API 路径，而非任意相关域名；
- 只允许访问内部包镜像，而非公网包注册表；
- 阻止已知恶意或不可信包源；
- 防止意外调用未经授权的第三方服务。

###### 包管理尤其关键

如果编码 Agent 可以执行：

```bash
pip install
npm install
curl | bash
```

它就能下载并执行外部代码。

安全问题不仅是“沙箱能否隔离执行”，还包括：

- 这些代码来自哪里；
- 这些代码能把数据发送到哪里。

---

##### 9. 支持生产级动态凭证

在将沙箱与 LangSmith Fleet 集成时，作者发现静态配置并不总是足够。

高级场景可能需要：

- 短期 OAuth Access Token；
- 按用户范围授权的 Token；
- 由内部认证服务动态签发的凭证；
- 根据目标地址或用户上下文刷新 Token。

为此，Auth Proxy 支持 **动态凭证回调 callbacks**。

###### 工作方式

1. 在 `proxy_config` 中配置回调地址；
2. 沙箱请求匹配目标主机；
3. 如果代理没有缓存凭证，就调用回调端点；
4. 回调端点根据目标 host 和 port 返回要注入的 Header；
5. 代理缓存结果，缓存时间由 TTL 配置决定。

回调返回格式示例：

```json
{
  "headers": {
    "Authorization": "Bearer <token>",
    "X-Org-Id": "..."
  }
}
```

如果回调失败、返回错误 JSON，或 HTTP 状态码不是 2xx，代理会 **fail closed**：直接拒绝沙箱请求，而不是在无凭证情况下继续发送。

这样可以让沙箱网络层参与认证流程，同时不暴露刷新 Token 或长期凭证。

---

##### 10. Auth Proxy 未来还能扩展什么能力

一旦控制了沙箱的网络路径，Auth Proxy 不只是凭证注入器，还可以扩展更多能力。

###### 10.1 DNS 重映射

例如：

- 将公网包注册表请求重定向到内部 Artifactory 或包镜像；
- 将 LLM API 请求指向内部网关。

Agent 仍然执行正常安装命令，但网络层会把请求导向被批准的基础设施。

###### 10.2 网络日志

长期运行的 Agent 需要审计能力。

团队可能需要知道：

- Agent 调用了哪些服务；
- 下载了哪些包；
- 尝试访问了哪些域名。

这些网络日志可以成为 Agent 行为审计的一部分。

###### 10.3 请求转换

由于代理能看到出站请求，因此未来可以做确定性处理，例如：

- 脱敏 PII；
- 添加组织元数据；
- 强制请求格式；
- 阻止违反策略的请求体。

---

##### 11. 新的 Agent 出站访问默认模式

文章最后总结：  
Agent 要完成有用任务，确实需要凭证和网络访问，但这不应意味着把长期密钥或无限制互联网访问权限放进运行时。

Auth Proxy 提供了一种更安全的默认方式：

- 凭证保留在沙箱外；
- 出站流量经过受控网络层；
- 策略可跨语言、SDK、包管理器和 CLI 一致执行；
- Agent 只能访问任务所需系统；
- 凭证和网络策略由平台统一管理。

最终，LangSmith Sandboxes + Auth Proxy 构建了一种更适合 Agent 的安全沙箱模型：  
**让 Agent 有能力完成任务，但不让它直接持有敏感凭证或自由访问整个互联网。**

因此，Agent 的安全默认值不能照搬人类开发环境。

###### 1.2 Agent 需要的是“能力”，不是“凭证本身”

文章最重要的思想是：

> Agent 不应该持有 API Key，它只需要具备调用某个 API 的能力。

比如 Agent 要调用 OpenAI API，没必要把 `OPENAI_API_KEY` 放进 `.env`、文件系统或环境变量里。更安全的方式是：

1. Agent 正常向 `api.openai.com` 发请求；
2. 出站请求经过 Auth Proxy；
3. Proxy 根据策略判断目标是否合法；
4. 若合法，Proxy 在网络层注入 `Authorization` Header；
5. Agent 永远看不到真实 API Key。

这等于把“凭证”从 Agent 运行时中剥离出去，只暴露受控能力。

过去很多 Agent 框架关注：

- Prompt；
- Tool use；
- Memory；
- Workflow；
- Evaluation；
- Sandbox 隔离。

但这篇内容提醒我们：

> Sandbox 只解决了“代码在哪里跑”的问题，Auth Proxy 解决的是“代码能访问哪里、以什么身份访问、访问时带什么权限”的问题。

真正成熟的 Agent 基础设施，需要在运行时之外建立控制面：

- 凭证不进入运行时；
- 网络访问显式声明；
- 目标域名、路径、Header、Token、用户身份都由平台层控制；
- Agent 无法通过 prompt injection 或恶意依赖绕过策略。

##### 2. 高价值信息深挖

##### 2.1 Auth Proxy 的本质：Agent 出站流量的安全网关

Auth Proxy 位于沙箱的出站网络路径上。

基本流程：

```text
Agent / sandboxed code
        ↓
Outbound request
        ↓
Auth Proxy
        ↓
Policy check
        ↓
Block / Allow / Inject headers
        ↓
External API
```

它不依赖每种语言或 SDK 都遵守 `HTTP_PROXY`，而是控制沙箱整体网络路径。  
这点非常关键，因为 Agent 可能执行任意语言、CLI、包管理器或子进程。

如果只靠环境变量配置代理：

- 有的运行时可能不遵守；
- 有的工具可能绕过；
- 恶意脚本可能主动规避；
- Agent 执行路径不可预测。

而网络层代理的好处是：一致、透明、语言无关。

---

##### 2.2 三个核心能力

###### 能力一：凭证不进入运行时

传统做法：

```bash
OPENAI_API_KEY=sk-xxx
GITHUB_TOKEN=ghp_xxx
```

这些凭证可能出现在：

- 环境变量；
- `.env` 文件；
- 日志；
- 堆栈报错；
- 临时文件；
- Agent 生成代码；
- 被安装的恶意依赖读取；
- Prompt injection 诱导 Agent 打印密钥。

Auth Proxy 的做法是：

```json
{
  "name": "Authorization",
  "type": "workspace_secret",
  "value": "Bearer {OPENAI_API_KEY}"
}
```

Agent 只发普通请求，Proxy 在匹配目标时注入 Header。

安全收益：

- Agent 不能读取 API Key；
- 恶意依赖无法直接扫描密钥；
- 日志泄露风险降低；
- Prompt injection 无法让模型“告诉我你的 Key”；
- 大规模沙箱集群下风险显著下降。

---

###### 能力二：网络访问显式化

Agent 默认不应拥有全互联网访问。

可以用策略表达：

- 只允许访问 OpenAI / Anthropic；
- 只允许访问 GitHub API 的特定路径；
- 只允许访问内部 API；
- 包安装只能访问内部 package mirror；
- 禁止未知域名；
- 禁止恶意或不可信包源；
- 阻止访问未授权第三方服务。

这对于 coding agent 尤其重要。

因为 coding agent 可能执行：

```bash
pip install xxx
npm install xxx
curl https://example.com/script.sh | bash
```

安全问题不只是“沙箱能不能隔离执行”，还包括：

> 它从哪里下载代码？下载后的代码能把数据发到哪里？

如果网络是开放的，即使运行环境隔离，也可能出现数据外泄、供应链攻击、恶意回连等风险。

---

###### 能力三：动态凭证与真实生产授权

静态 API Key 只适合简单场景。

复杂 Agent 系统会遇到：

- 用户级 OAuth Token；
- 短期访问令牌；
- 按用户上下文生成的凭证；
- 内部 Auth Service 动态签发 Token；
- Token 过期刷新；
- 不同目标服务使用不同身份。

Auth Proxy 支持 callback 模式。

流程：

1. Sandbox 请求某个匹配 Host；
2. Proxy 没有缓存凭证；
3. Proxy 调用配置好的 callback endpoint；
4. Callback 根据 host、port、用户上下文返回 Header；
5. Proxy 注入 Header；
6. 凭证按 TTL 缓存；
7. 如果 callback 失败，则 fail closed，拒绝请求。

返回格式类似：

```json
{
  "headers": {
    "Authorization": "Bearer <token>",
    "X-Org-Id": "..."
  }
}
```

这里的关键是：

> 刷新 Token、长效凭证、用户授权逻辑都留在 Agent 运行时之外。

Agent 只获得“被授权后的请求能力”，而不是凭证生命周期管理能力。

##### 4. 反方与张力

##### 4.1 安全与开发效率的张力

Auth Proxy 增加了安全性，但也带来配置成本。

反方观点：

> Agent 做探索性任务时，过窄的网络策略会频繁阻塞任务，降低自动化效率。

例如：

- Agent 需要查新文档；
- Agent 需要访问一个临时 API；
- Agent 需要安装某个未在白名单中的包；
- Agent 需要调试未知依赖问题。

如果策略太严格，Agent 会频繁失败。

平衡方式：

- 根据任务类型设置不同网络策略；
- 对生产任务采用严格 allowlist；
- 对探索任务使用临时扩展权限；
- 引入审批机制；
- 记录被阻断请求，辅助策略迭代。

---

##### 4.2 静态策略与动态任务的张力

Agent 的价值之一是处理开放式任务，但安全策略需要提前定义。

这会产生矛盾：

- Agent 越自主，越难提前知道它需要访问哪里；
- 网络越开放，风险越大；
- 网络越封闭，Agent 越容易卡住。

可行解法是分层权限：

```text
Level 0: 无网络
Level 1: 仅模型 API
Level 2: 模型 API + GitHub
Level 3: 加内部包源
Level 4: 加内部 API
Level 5: 人工审批后临时公网访问
```

不同任务选择不同等级，而不是给所有 Agent 同样权限。

---

##### 4.3 Proxy 自身成为关键风险点

Auth Proxy 让凭证不进入沙箱，但 Proxy 本身会变成高价值目标。

风险包括：

- Proxy 策略配置错误；
- Header 注入规则过宽；
- Callback endpoint 被滥用；
- 日志误记录敏感 Header；
- Proxy 被攻破后可批量窃取凭证；
- 缓存 Token 的 TTL 过长。

因此，Proxy 自身也需要：

- 最小权限；
- 审计日志；
- 规则测试；
- 策略版本管理；
- Secret 加密存储；
- Header 脱敏；
- 异常流量检测；
- 高隔离部署。

---

##### 4.4 只控制出站网络还不够

Auth Proxy 解决的是网络和凭证问题，但 Agent 安全还包括：

- 文件系统隔离；
- 进程隔离；
- 资源限制；
- Prompt injection 防护；
- 工具调用审计；
- 数据脱敏；
- 代码执行限制；
- 供应链安全；
- 人工审批流程；
- 输出内容检查。

所以它不是完整安全方案，而是 Agent 基础设施中的关键组件。

**一句话点评**: 一篇有实用架构价值的Agent沙箱安全设计说明，但证据和案例支撑偏弱。
**核心高价值点**: 将凭证从Agent运行时移出，在网络代理层按策略注入认证头，是降低提示注入、恶意依赖和日志泄露风险的关键设计。

###### 摘要
文章介绍LangSmith沙箱Auth Proxy如何通过出站网络代理控制Agent访问外部服务，避免凭证进入运行时，并支持访问白名单、头部注入、动态OAuth凭证、DNS重映射和网络审计等能力。

###### 知识要点
- Agent沙箱不应默认拥有开放互联网访问，应通过基础设施策略限制可访问目标。
- Auth Proxy可在出站请求路径上注入认证头，使Agent具备调用API的能力但无法读取凭证。
- 动态凭证回调可支持OAuth刷新、用户范围令牌和内部认证服务生成的短期凭证。
- 控制沙箱网络路径后，可进一步实现DNS重映射、网络日志审计和请求转换。

###### 行动项
- 评估现有Agent运行环境是否存在凭证直接注入环境变量或文件的问题。
- 为Agent沙箱设计出站访问白名单和默认拒绝策略。
- 将长期密钥迁移到代理层或密钥管理服务，通过请求匹配规则注入认证头。
- 为高风险Agent任务增加网络日志记录和包源访问限制。
