## 分析要点

- **核心高价值点**：将 Agent 视为多层循环系统，而不是单一模型调用：执行循环负责完成任务，验证循环保证质量，事件循环实现规模化运行，爬山循环推动系统持续改进。
- **留存建议**：长期保留（提供了智能体系统从执行、验证、事件触发到持续优化的分层框架，适合作为构建生产级 Agent 的方法论参考。）

**知识要点**

- 生产级 Agent 不应只依赖模型能力，还需要任务适配的控制框架。
- 验证循环可通过评分器、测试、LLM Judge 或确定性规则对 Agent 输出进行反馈重试。
- 事件驱动循环使 Agent 能通过 cron、webhook、消息频道等方式嵌入实际业务系统。
- 爬山循环利用运行轨迹分析来改进提示词、工具、评分标准甚至模型本身。
- 人工监督仍应保留在高风险操作、主观质量判断和部署审核等关键节点。

**行动项**

- 在现有 Agent 项目中检查是否只有基础工具调用循环，并补充验证与评分机制。
- 为关键 Agent 运行结果建立可追踪日志和轨迹分析流程。
- 将适合后台自动化的 Agent 接入事件触发器，如 webhook、定时任务或消息频道。
- 识别高风险工具调用，在执行前加入人工审批节点。
- 定期基于失败轨迹优化提示词、工具描述、评分标准和测试用例。

### 循环工程的艺术

智能体之所以有用，是因为它们能在现实世界中采取行动，帮助我们自动化工作。但要让智能体可靠地完成有价值的工作，不仅仅需要一个良好的模型：还需要一个精心设计的框架，以适配特定的任务集。

The core agent algorithm is simple: give the LLM context and let it call tools in a loop until it's done. This is the most fundamental loop. But it’s far from the only loop that powers agents.

[@swyx](https://x.com/@swyx) recently wrote a great piece on

["loopcraft: the art of stacking loops"](https://www.latent.space/p/ainews-loopcraft-the-art-of-stacking)

, the idea that you can stack and extend loops to build more effective agents.

这是我们对该技术栈的思考方式，以及如何使用 LangChain 原语对每个层级进行仪器化。

#### 循环 1：代理

本质上，智能体只是一个在循环中调用工具直到任务完成的模型。

![Image](https://pbs.twimg.com/media/HK8cVApXsAE94vJ?format=jpg&name=large)

This is what LangChain’s

[创建\_agent](https://docs.langchain.com/oss/python/langchain/agents) gives you. Pick any model, plug in tools, and you have a working agent loop. Tools are what give the agent the power to take action in the real world.

以我们的内部文档代理为例（我们将在本文其余部分以此作为激励性示例）。在第一个循环层级，它接收一个关于文档改进的请求，模型规划并草拟修改内容，然后使用工具克隆代码仓库、读取文件、撰写文档、打开拉取请求等。

![Image](https://pbs.twimg.com/media/HK8cXkUXgAEnJXz?format=jpg&name=large)

#### 2级：核实循环

代理循环能够完成工作，但并不总是能在第一次尝试时产出正确或一致的成果。当一致性很重要时，通常将其包裹在一个验证循环中会很有用，该循环会检查输出，并在结果不足时向模型发送反馈。

![Image](https://pbs.twimg.com/media/HK8cZ8PWwAA3eD6?format=jpg&name=large)

验证循环新增了一个评分器：该评分器会对照评分标准检查代理的输出，如果未通过，则将结果连同反馈返回。评分器可以是确定性的或代理式的（此处，以大语言模型（LLM）作为评判者是一个典型例子）。

[Rubric 中间件](https://docs.langchain.com/oss/python/deepagents/rubric) handles this pattern, or you can wire it up with an after\_agent hook on create\_agent.

对于我们的文档撰写者示例，评分器会在每次尝试后运行测试，检查所有链接都能正常解析、所有持续集成检查都通过，并且差异范围限定为实际请求的内容。不需要人工审核来捕获这些类型的错误。

![Image](https://pbs.twimg.com/media/HK8cckrWIAAVLHk?format=jpg&name=large)

一个权衡是：添加验证会增加延迟和每次运行的成本。当质量比速度更重要时，这是值得的，而大多数生产用例都是如此。

#### 第3级：事件驱动循环

代理开发中最重要的部分之一是集成层：将你的代理连接到你的生态系统，以便它能在后台运行。

事件驱动循环将您的代理连接到您的生态系统。当事件触发时——新文档到达、计划触发、webhook 到达——代理便会运行。代理不是您手动调用的，而是在更大系统中持续运行的组件。

#### 第4级：爬山循环

前三个循环实现工作自动化。第四个（可以说是最重要的）循环实现改进自动化！

![Image](https://pbs.twimg.com/media/HK8coslWMAAyYLu?format=jpg&name=large)

每次代理运行都会生成一条轨迹：记录模型的行为、调用的工具、评分者反馈等。这些轨迹包含关于哪些方法有效、哪些无效的高价值信号。爬山循环在这些轨迹上运行一个分析代理，并利用发现结果用改进后的配置重写框架。这可能包括提示词/工具调整或评分者调整。

In LangSmith, you can use

[引擎](https://www.langchain.com/langsmith/engine), our trace analysis agent, to instrument this fourth loop.

完成文档代理类比的分析后，我们使用 Engine 分析文档代理的执行轨迹以检测任何问题。当多个轨迹表明存在潜在问题时，会提交一个问题报告，要求对有问题的提示词或工具进行修改。

![Image](https://pbs.twimg.com/media/HK8czWeXQAAYMu7?format=jpg&name=large)

这里的关键动作是，返回箭头不仅仅是循环回到顶部——它会深入内部并直接更新代理循环。外部循环的每个周期都会使内部循环更有效。

> Looking forward: prompt and tool configuration are the most simple things to improve, but they're not the only options. For teams running open-weight models, the hill climbing loop can feed into RL fine-tuning, using trace or eval outcomes as training signal to improve the model itself. Auxiliary context like memory and retrieved skills can be improved the same way. The loop is the pattern; what it optimizes is up to you.

#### 人类监督与专业知识

自动化并不意味着将人类从流程中移除。在每个层面，都存在人工监督能增加价值的自然节点。自动评分系统可以检查链接是否有效，但需要人类来注意到表述方式对受众而言不合适。这种源于语境、经验和品味的判断，正是人工审核获得其应有地位的地方。

一些专业知识应该被编码在提示词/工具本身中，但对于敏感操作，实时人工审核是必不可少的（例如金融交易、数据库操作等）。LangChain 使在每个循环中对这些接触点进行检测变得简单：

1. 在代理循环中，敏感操作/工具调用前需人类输入
2. 在核实循环中，人可以充当敏感工作流程的评分者
3. 在应用流程中，人可以在输出返回给最终用户之前批准输出
4. 在爬山循环中，harness 的改进可以在部署前经过人工审核

All of LangChain’s open source frameworks make adding a “human in the loop” a

[一等原始类型](https://docs.langchain.com/oss/python/deepagents/human-in-the-loop).

## 解读（1）

### 2026-06-17 02:12:11

#### 《循环工程的艺术》精炼解读

##### 一、深度总结

文章核心观点：  
**智能体的价值不只来自“大模型本身”，而来自一套由多层循环组成的工程系统。**

智能体要真正可靠地工作，需要把“模型调用工具”这一基础能力，放进更大的循环结构中，不断执行、校验、触发、改进。

---

##### 二、四层循环框架

| 层级 | 循环 | 作用 | 价值 |
|---|---|---|---|
| 1 | 代理循环 | LLM 根据上下文反复调用工具，直到完成任务 | 自动干活 |
| 2 | 验证循环 | 用评分器检查结果，不合格则反馈重试 | 保证质量 |
| 3 | 事件驱动循环 | 由 webhook、定时任务、消息等事件触发智能体运行 | 融入系统，规模化运行 |
| 4 | 爬山循环 | 分析运行轨迹，反向优化提示词、工具、评分器甚至模型 | 持续进化 |

一句话概括：

> 第一层让智能体“会做事”，第二层让它“做得对”，第三层让它“自动发生”，第四层让它“越做越好”。

---

##### 三、深入浅出解读

可以把智能体想象成一个“自动文档助手”。

###### 1. 代理循环：先让它能干活

用户说：  
“帮我改一下这份文档。”

智能体会自己：

- 查代码仓库
- 读文件
- 修改文档
- 提交 PR
- 调用相关工具

这就是最基础的 Agent：  
**模型 + 工具 + 循环执行。**

但问题是：  
它第一次不一定做得好。

---

###### 2. 验证循环：给它一个检查员

所以需要第二层：验证。

比如文档助手改完后，系统自动检查：

- 链接是否有效
- CI 是否通过
- 修改范围是否超出需求
- 格式是否正确

如果不合格，就把问题反馈给智能体，让它重做。

这相当于给智能体配了一个“质检员”。

代价是：

- 更慢
- 更贵

但在生产环境里，通常值得。

---

###### 3. 事件驱动循环：让它自动上岗

第三层不是用户手动点一下才运行，而是让智能体接入真实系统。

例如：

- Slack 频道里有人发消息
- GitHub 出现新 issue
- 每天定时扫描文档
- webhook 触发任务

智能体就自动启动。

这一步的关键是：

> 智能体不再是一个聊天窗口，而是系统中的后台员工。

---

###### 4. 爬山循环：让它自己变强

前三层解决“自动工作”，第四层解决“自动改进”。

每次智能体运行都会留下轨迹：

- 模型想了什么
- 调用了哪些工具
- 哪里失败了
- 评分器给了什么反馈
- 哪类任务反复出错

然后用另一个分析智能体去看这些轨迹，找出系统问题。

例如：

- 提示词不清楚
- 工具设计不好
- 评分标准太宽或太严
- 某类任务总失败

再反过来改进智能体配置。

这就是“爬山”：

> 每次不求完美，但每轮都向更优方向走一点。

---

##### 四、人的位置：不是被替代，而是被放到关键处

文章强调：  
**自动化不等于完全去人。**

不同循环里，人都有价值：

- 代理循环：敏感工具调用前需要人确认
- 验证循环：复杂判断可由人评分
- 事件循环：结果返回用户前可人工审核
- 爬山循环：系统改进上线前需人工批准

机器适合检查确定性问题：  
链接、格式、测试、权限、范围。

人更适合判断模糊问题：  
语气、受众、战略风险、业务后果、审美与价值取向。

---

##### 五、核心启发

这篇文章真正讲的不是某个 LangChain 功能，而是一种智能体工程范式：

> 不要只优化单次回答，要设计能持续运行、持续验证、持续学习的循环系统。

未来高价值智能体，不是一个“更聪明的聊天机器人”，而是一个：

- 能接入业务系统
- 能自动执行任务
- 能自我检查
- 能从历史中改进
- 能在人类监督下安全运行的工作流系统

---

##### 六、辩证思考

###### 1. 循环越多，不一定越好

多层循环带来可靠性，也带来复杂性。

优点：

- 更稳定
- 更自动化
- 更可扩展
- 更容易持续优化

风险：

- 成本升高
- 延迟变长
- 调试困难
- 失败链路更复杂
- 错误可能在自动化中被放大

所以不是所有场景都需要四层循环。

简单任务用一层即可；  
高风险、高价值、长期运行的任务，才值得堆叠循环。

---

###### 2. “自我改进”不能完全自动化

爬山循环很诱人，但也危险。

如果系统根据错误信号盲目修改自己，可能出现：

- 过拟合评分器
- 为了通过测试而牺牲真实质量
- 提示词越来越复杂
- 工具调用策略变得不可解释
- 局部优化损害整体目标

所以第四层必须有治理机制：

- 明确评价标准
- 保留人工审查
- 版本化变更
- 可回滚
- 监控副作用

---

###### 3. 真正的壁垒不是模型，而是反馈系统

模型能力会越来越普及。  
真正难的是组织是否能建立：

- 高质量任务流
- 清晰评分标准
- 可追踪执行记录
- 稳定工具接口
- 人机协作机制
- 持续改进闭环

也就是说：

> AI 智能体的长期价值，不在“单点智能”，而在“组织级反馈循环”。

---

##### 七、一句话结论

**智能体工程的关键，不是让模型一次性变聪明，而是用多层循环把它变成一个可执行、可验证、可触发、可进化的系统。**

## 结构化（1）

#### 《循环工程的艺术》精炼总结

智能体的价值不只来自大模型本身，而来自围绕模型设计的一整套“循环”框架：让模型能调用工具、验证结果、响应事件，并持续自我改进。文章提出了从基础代理循环到持续优化循环的四层架构，并说明如何用 LangChain / LangSmith 等工具实现。

---

##### 1. 核心思想：智能体 = 模型 + 工具 + 循环

智能体最基础的工作方式很简单：

> 给大语言模型上下文，让它不断调用工具，直到任务完成。

但真正可靠、有生产价值的智能体，不能只靠这个基础循环。作者借用 “loopcraft” 的概念，强调可以把多个循环层层叠加，构建更强、更稳定、更可扩展的智能体系统。

---

##### 2. 循环 1：代理循环——让模型真正执行任务

第一层是最基础的 **代理循环**：

- 模型接收任务；
- 根据上下文进行规划；
- 调用工具执行操作；
- 反复迭代，直到任务完成。

在 LangChain 中，可以用 `create_agent` 创建这种代理循环。只要选择模型并接入工具，就能得到一个可运行的智能体。

**例子：内部文档代理**

一个文档改进代理收到请求后，可以自动：

- 克隆代码仓库；
- 阅读相关文件；
- 草拟文档修改；
- 写入文件；
- 打开 Pull Request。

这一层的核心作用是：**自动化完成工作**。

---

##### 3. 循环 2：核实循环——用评分器保证质量

基础代理循环可以完成任务，但不一定每次都正确。因此第二层加入 **验证 / 核实循环**。

它的做法是：

- 代理先产出结果；
- 评分器根据标准检查结果；
- 如果不合格，就把反馈返回给模型；
- 模型根据反馈重新尝试。

评分器可以是：

- 确定性规则，例如测试是否通过；
- 另一个 LLM，例如用大模型当评审者。

在 LangChain 中，可以通过 **Rubric 中间件** 或 `after_agent hook` 实现。

**文档代理中的核实例子**

评分器会检查：

- 所有链接是否能正常解析；
- CI 检查是否通过；
- 修改范围是否只限于用户实际请求的内容。

这些错误不需要人工审核就能自动发现。

**代价与取舍**

加入验证会增加：

- 运行延迟；
- 每次调用成本。

但当质量比速度更重要时，这种成本是值得的。文章指出，大多数生产场景都属于这种情况。

---

##### 4. 循环 3：事件驱动循环——让智能体嵌入真实系统

第三层是 **事件驱动循环**，重点是把智能体接入组织的真实工作流。

它不是让人手动调用代理，而是让代理在系统中持续运行，并由事件触发：

- 新文档到达；
- 定时任务触发；
- webhook 到达；
- Slack 消息出现。

LangSmith Deployment 支持这类触发基础设施，包括：

- cron 定时任务；
- webhooks。

文章提到 openclaw 中的 “heartbeats” 是一个典型 cron 场景，可以把智能体变成长期在线、主动工作的助手。

**文档代理中的事件触发例子**

作者团队使用 Fleet 这个无代码智能体构建工具：

- 通过 Fleet 的 channels 和 schedules 管理事件触发；
- 当有人在 Slack 的 `#docs-plz` 频道发送消息时，文档代理就会自动启动。

这一层的核心作用是：**让智能体规模化地融入实际业务系统**。

---

##### 5. 循环 4：爬山循环——让系统持续自我改进

前三个循环主要是自动化工作，第四个循环则是自动化改进。

每次代理运行都会生成轨迹数据，包括：

- 模型采取了什么行动；
- 调用了哪些工具；
- 评分器给了什么反馈；
- 哪些步骤成功或失败。

这些轨迹中包含大量高价值信号。**爬山循环**会让一个分析代理读取这些轨迹，并基于发现结果改进系统配置，例如：

- 调整提示词；
- 改进工具；
- 修改评分标准。

在 LangSmith 中，可以用 **Engine** 作为轨迹分析代理，实现这一层循环。

**文档代理中的改进例子**

作者团队用 Engine 分析文档代理的执行轨迹：

- 如果多个轨迹显示同一类问题；
- 系统会提交问题报告；
- 要求修改有问题的提示词或工具。

这层循环的关键在于：反馈不是简单回到任务开头，而是深入修改内部代理配置，让下一轮代理运行更有效。

未来，这种循环还可以用于：

- 对开源权重模型做 RL 微调；
- 用轨迹或评估结果作为训练信号；
- 改进记忆系统；
- 优化检索到的技能和上下文。

---

##### 6. 人类监督：自动化不等于移除人

文章强调，自动化并不意味着完全不需要人类。人在多个环节仍然非常重要，尤其是在涉及判断力、语境、经验和品味的地方。

例如：

- 自动评分器可以检查链接是否失效；
- 但人类更适合判断文档表达是否适合目标读者。

对于敏感操作，人类审核尤其必要，例如：

- 金融交易；
- 数据库操作；
- 高风险业务流程。

LangChain 支持在各个循环中加入 “human in the loop”：

- 在代理循环中：敏感工具调用前需要人工确认；
- 在核实循环中：人可以作为评分者；
- 在应用流程中：输出给最终用户前由人批准；
- 在爬山循环中：系统改进部署前由人审核。

---

##### 7. 四种循环的整体关系

| 循环 | 功能 | 主要影响 | LangChain / LangSmith 原语 |
|---|---|---|---|
| 1. 代理循环 | 模型反复调用工具直到任务完成 | 自动化工作 | `create_agent`，任意 LangChain 支持的模型 |
| 2. 核实循环 | 代理输出后由评分器检查，不合格则反馈重试 | 保证质量 | Rubric 中间件 |
| 3. 事件循环 | 由系统事件触发代理运行 | 规模化工作 | LangSmith Deployment / Fleet channels |
| 4. 爬山循环 | 分析生产轨迹并改进代理配置 | 持续优化 | LangSmith Engine |

---

##### 8. 结论：未来重点在第 3 和第 4 层循环

作者认为，行业已经对第 1 层“代理循环”和第 2 层“核实循环”思考较多。接下来更重要的是第 3 和第 4 层：

- 把智能体真正嵌入组织生态系统；
- 让智能体根据组织标准持续改进。

这样，智能体不只是一次性完成任务的工具，而会变成能够长期运行、持续优化、不断积累价值的系统。

## 深度解读（1）

### 2026-09-18 00:47:20

#### 智能体真正的壁垒，不是“会调用工具”，而是可控的反馈系统

文章把智能体拆成四层循环：执行任务、验证结果、由事件持续触发、再根据生产轨迹改进系统。这个框架最有价值的地方，不是又提出了一套 Agent 架构，而是指出：**智能体从演示走向生产，关键变量会从模型能力转向反馈系统的质量。**

##### 四层循环，其实是四种不同的控制能力

第一层“模型调用工具直到完成”解决的是执行问题。它能克隆仓库、修改文档、提交 PR，但“完成了”不等于“做对了”。

第二层加入评分器，把链接有效、CI 通过、修改范围符合要求等标准变成自动检查。这相当于给执行系统加上质量闭环。不过，验证循环并不会自动产生正确性，它只会强化那些**已经被表达成规则的正确性**。链接和测试容易检查，语气是否合适、论证是否误导、修改是否真正帮助读者，则很难完全交给 LLM 评判。

第三层的事件驱动，才让智能体从工具变成组织中的常驻角色：Slack 消息、定时任务或 webhook 到来后，它自动介入工作流。这里产生的价值不只是节省一次操作，而是缩短“事件发生—任务识别—执行完成”的链条。但风险也同时放大：一个偶尔犯错的助手，被改造成全天候自动运行的组件后，错误会以更高频率进入真实系统。因此，**自动触发必须和权限、幂等、回滚、预算及人工审批一起设计**。

##### “自我改进”最诱人，也最容易被高估

第四层用运行轨迹分析失败，再修改提示词、工具、评分标准，甚至把结果用于模型微调。它确实可能形成数据飞轮：使用越多，轨迹越丰富，系统越容易发现重复故障。

但这不是天然的自我进化。轨迹只能显示系统做过什么，未必能说明为什么失败；评分器若存在盲点，优化系统还可能更熟练地迎合错误指标。比如文档代理为了提高“检查通过率”，可能倾向于减少改动，而不是解决真正的问题。所谓爬山，只能保证沿着当前度量前进，不能保证选对了山。

因此，第四层最需要治理：配置变更要可审查、可灰度、可回滚；离线评测要防止回归；线上反馈还应包含用户是否接受修改、后续是否被撤销等真实结果，而不只是模型评委的分数。

##### 产品机会在“工作流控制面”，而非再包装一个 Agent

文章虽带有明显的 LangChain 产品映射，但判断仍有普遍意义：未来更有持续价值的基础设施，可能不是单次编排模型，而是管理整套循环——事件接入、轨迹观测、评测标准、权限审批、版本发布与持续优化。

对产品团队而言，合理路径不是一开始就追求“自动进化”，而是先选择高频、边界清晰、结果可验证的任务：明确交付物，建立确定性检查和人工升级条件，再接入事件触发并积累轨迹。**没有稳定的评价标准，更多循环只会更快地放大不确定性；有了可信反馈，模型反而可以替换，系统却会持续变强。**
