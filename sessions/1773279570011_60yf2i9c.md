- **核心高价值点**：最有价值的是明确指出 reasoning token 与不可裁剪的 SSM/Mamba 缓存共同导致多轮对话前缀复用失败，这是性能骤降的核心原因。

**知识要点**

- Qwen3.5 在 MLX-LM 中的缓存问题不只是简单未命中，还涉及 reasoning token 破坏共享前缀与 SSM 缓存不可 trim 的结构性限制。
- 工具调用场景下，chat template 的 JSON 键顺序与参数顺序不稳定，也会让缓存键漂移并持续触发全量重处理。

**行动项**

**angeloskath** commented on 2/18/2026

So the lru prompt cache leaves the cache in memory when trimming. That was meant as an optimization since you can fork conversations for free.

However it is obviously problematic when the cache is 10GB and then you copy it 10x so you spend 100GB on a cache...

I think the fix is fairly simple, the cache needs to be aware of how much cache size is currently being used and how much is available. If we are reaching the limit it should evict instead of copying etc.

I am not a proficient programmer, but I've done my due diligence with troubleshooting this issue, and I find it difficult to wait, so I had Claude (Opus 4.6) analyze the problem to make me a temporary fix that seem to work for me during testing. I'm sharing it here for any other impatient soul who can't wait to get their hands on Qwen3.5 😉

Claude's analysis of why the checkpoint mechanism in PR [#911](https://github.com/ml-explore/mlx-lm/pull/911) doesn't help Qwen3.5:

> The checkpoint cache is stored with a key that includes the last user message content. When the client sends request [#2](https://github.com/ml-explore/mlx-lm/issues/2), it modifies earlier messages (e.g. removing tags), so the checkpoint key diverges from the new prompt. The server finds a "longer match" but can\_trim\_prompt\_cache() returns False because ArraysCache.is\_trimmable() inherits False from \_BaseCache. Result: fetch\_nearest\_cache returns None, tokens — full cache miss.

Claude's workaround:

> For hybrid models, move the checkpoint from just before to just before the last user message. This way the checkpoint key becomes \[System + Tools\] — a stable prefix that matches across requests without needing to trim ArraysCache.

My test results (identical setup, two-message conversation):

Before patch After patch

Qwen3.5 request [#2](https://github.com/ml-explore/mlx-lm/issues/2) 11962/11967 tokens processed (full miss) 57/379 tokens processed (cache hit)

GLM-5 request [#2](https://github.com/ml-explore/mlx-lm/issues/2) 320/321 (unaffected) 320/321 (unaffected)

MiniMax-M2.1 request [#2](https://github.com/ml-explore/mlx-lm/issues/2) 348/351 (unaffected) 348/351 (unaffected)

Patch (replace `_compute_prompt_checkpoint` in `server.py`):

```
def _compute_prompt_checkpoint(self, tokenizer, request, prompt):
    if request.request_type != "chat":
        return False, -1
    if request.messages[-1]["role"] != "user":
        return False, -1
    try:
        test_cache = make_prompt_cache(self.model_provider.model)
        is_hybrid = not can_trim_prompt_cache(test_cache)
    except Exception:
        is_hybrid = False
    if is_hybrid:
        im_start_id = None
        try:
            im_start_id = tokenizer._tokenizer.convert_tokens_to_ids(
                "<|im_start|>"
            )
        except Exception:
            pass
        if im_start_id is not None:
            im_start_count = 0
            for i in range(len(prompt) - 1, 0, -1):
                if prompt[i] == im_start_id:
                    im_start_count += 1
                    if im_start_count == 2:
                        checkpoint_offset = len(prompt) - i
                        return True, -checkpoint_offset
    prompt_checkpoint = -1
    if tokenizer.has_thinking:
        for i in range(1, min(11, len(prompt)) - 1, 1):
            if prompt[-i] == tokenizer.think_start_id:
                prompt_checkpoint = -i - 1
                break
    return True, prompt_checkpoint
```

Known limitations:

- single checkpoint per request,
- hardcoded &lt;\|im\_start\|&gt; (ChatML only),
- \_serve\_single codepath not covered.

Looking forward to the proper solution. This is a vibe-coded workaround that may very well introduce it's own issues. Ye have been warned 😉

### 2026-03-12 01:39:29

#### 总结

这个 Issue 讨论的是：**Qwen3.5 在`mlx-lm`里提示词缓存（prompt caching）效果很差，常常每次都重跑整段上下文**，导致速度慢、显存 / 内存占用高，尤其在多轮对话、工具调用、代码代理场景中更明显。

核心原因主要有 3 类：

1. **Qwen3.5 / Hybrid / Mamba (SSM) 缓存不可随意裁剪**
   - 普通 KV cache 可以按共享前缀复用。
   - 但 Mamba/SSM 类缓存**不能方便地 trim**，所以只要新请求和旧缓存不完全对齐，就很难命中。

2. **Reasoning（思维链）token 破坏缓存前缀**
   - 上一次缓存里可能包含：`Prompt + Reasoning + Assistant`
   - 但下一次请求客户端通常不会把 reasoning token 再发回来，只会发：`Prompt + Assistant + User`
   - 结果是缓存虽然 “看起来相关”，但真正可复用的前缀很短，收益很差，甚至会产生很多没用的大缓存副本。

3. **工具调用 / 模板渲染不稳定**
   - Qwen3.5 的 chat template 里，tools 和参数 JSON 的键顺序可能变化。
   - 文本哪怕只变一点，缓存键就不同，导致缓存 miss。

此外，维护者也确认：
- **这是个真实问题**，不是用户误用。
- 修复方向包括：
  - 按层处理缓存，而不是按整个模型一刀切；
  - 对 reasoning model，只保存到 reasoning 开始前的缓存；
  - 对不可裁剪缓存，使用更合理的 checkpoint /snapshot 机制；
  - 在内存接近上限时，不再无限复制大缓存。

---

#### 通俗解读

可以把缓存理解成 “**做题草稿**”。

正常情况下：
- 你上一轮已经把前面的题目都算过了；
- 下一轮只是在原题后面加一句新问题；
- 那么你应该直接接着算，不用从头再来。

但 Qwen3.5 这里的问题是：

##### 1. 草稿本不好剪
有些模型的缓存像一叠便签，想保留前半段很容易；
但 Qwen3.5 里有一部分缓存更像一整块连续状态，**不能从中间随便剪掉**。

所以如果新请求和旧请求不是 “几乎一模一样接着来”，就没法优雅复用，只能重算很多内容。

---

##### 2. 模型脑内 “思考过程” 没有被下一轮带上
比如第一轮：

- 用户：请帮我写函数
- 模型内部：先分析需求、列步骤……（reasoning）
- 模型输出：这是函数代码

缓存里其实可能存了：
- 用户问题
- 模型 reasoning
- 模型回答

但第二轮客户端发来的内容通常不会包含 reasoning，只会发：
- 用户问题
- 模型回答
- 新用户问题

这就像你上次草稿里夹了一大段 “心里默算”，但下次题目里这段没了。  
于是缓存系统会发现：**咦，后面对不上了**，只能退回到更早的位置，甚至几乎重来。

---

##### 3. 工具列表哪怕顺序变一下，也算 “不是同一个提示词”
对于 agent /tool calling 场景，prompt 里往往会嵌入工具定义 JSON。

如果第一轮是：

```json
{"type":"object","required":["pattern"],"additionalProperties":false}
```

第二轮变成：

```json
{"additionalProperties":false,"type":"object","required":["pattern"]}
```

虽然语义完全一样，但字符串不同。  
**缓存是按 token / 文本匹配，不会理解 “你这只是换了个字段顺序”**，所以还是 miss。

---

#### 我的意见

##### 一、这不是单点 bug，而是 “多因素叠加”
我认为这件事不能简单理解成 “Qwen3.5 缓存坏了”，更准确地说是：

- **模型结构特性**（SSM /hybrid）
- **reasoning token 的处理方式**
- **chat template /tools 序列化不稳定**
- **当前 LRU prompt cache 策略过于粗糙**

这些因素叠在一起，才导致体验特别差。

---

##### 二、短期最有效的办法：先解决 “稳定前缀”
如果你现在就要用 Qwen3.5，我建议优先做这几件事：

###### 1. 保证 tools 渲染稳定
- 对 JSON key 排序
- 对 tool arguments 排序
- 保证每轮模板输出尽量一致

这是**投入小、收益大**的优化。

###### 2. checkpoint 放在 reasoning / 最后用户消息之前
- 不要把`&lt;think>`后面的内容也作为主要缓存锚点
- 尽量缓存 “稳定前缀”

这对 reasoning model 很关键。

###### 3. 接受 “最后一轮可能仍要重算”
由于 SSM 层不可裁剪，**完全像传统 Transformer 一样丝滑复用，短期可能做不到**。
现实目标应该是：
- 不要每次从开头重跑
- 只重跑最近一轮附近的内容

这已经能明显改善体验。

---

##### 三、从工程角度看，官方后续方向是对的
我比较认同维护者提到的思路：

- **按层处理缓存**
- 对不可 trim 的层做快照 / 锚点恢复
- 对 reasoning 模型只存到 reasoning 开始前
- 内存不足时避免复制巨型缓存

这是比 “头痛医头” 更稳的路线。

---

##### 四、如果你是普通用户，当前结论很简单
###### 可以这样理解：
- **不是 Qwen3.5 不能缓存**
- 而是它在`mlx-lm`当前实现下，**缓存命中条件更苛刻**
- 尤其在：
  - 多轮对话
  - agent
  - 工具调用
  - reasoning 输出
  这些场景下更容易失效

###### 实际建议：
- 如果追求稳定缓存体验，当前阶段**MiniMax / 非 hybrid 模型可能更省心**
- 如果必须用 Qwen3.5：
  - 更新到较新版本
  - 使用更 cache-friendly 的 chat template
  - 固定 tools/args 顺序
  - 减少 prompt 在每轮中的细微变化

---

#### 一句话结论

**这个问题本质上不是 “缓存完全没做”，而是 Qwen3.5 的模型结构 + reasoning + tools 模板，让现有缓存机制很难高效复用；短期靠稳定模板和更好的 checkpoint 能缓解，长期需要框架层重构缓存策略。**

### 2026-03-12 01:46:48

#### 总结

这条 GitHub Issue 主要在讨论：**`mlx-lm` 跑 Qwen3.5 时，提示缓存（prompt cache）效果很差，常常每轮都要把整个 prompt 重新处理一遍**，导致响应越来越慢、上下文越长越明显，甚至出现 OOM。

核心原因大致有三类：

1. **Qwen3.5 / 混合模型里有 Mamba/SSM 这类“不可裁剪”的缓存**
   - 普通 KV cache 往往可以按前缀复用、裁剪。
   - 但 Mamba/SSM 的状态不好裁剪，所以缓存命中场景变少。

2. **推理模型的 reasoning token（思维链）会破坏缓存前缀**
   - 上一轮缓存里可能是：`系统 + 用户 + reasoning + 助手`
   - 下一轮请求往往只会发：`系统 + 用户 + 助手 + 新用户`
   - 因为客户端通常不会把 reasoning token 回传，所以两边前缀很早就分叉了，导致缓存命中很差。

3. **工具调用 / chat template 渲染不稳定**
   - 工具 JSON 的 key 顺序、参数顺序、模板渲染方式在不同轮次可能不一致。
   - 虽然语义一样，但 token 序列变了，缓存就失效。

---

#### 解读

##### 1. 为什么别的模型缓存正常，Qwen3.5 却不行？

可以把缓存理解成“**把已经读过的前文做笔记，下次接着看**”。

正常情况下，如果两次请求前半段完全一样，模型就不需要再从头读一遍，可以直接复用“笔记”。

但 Qwen3.5 这里麻烦在于：

- 它不是纯 Transformer 的简单 KV cache；
- 里面有 **SSM / Mamba 状态**，这类缓存不像普通缓存那样“想截哪里就截哪里”。

所以即使前面有很多相同内容，也**不一定能优雅复用**。

---

##### 2. reasoning token 为什么会让缓存“看起来命中了，其实没省多少”？

举个最简单的例子：

###### 第一次请求
- 用户发：`系统提示 + 问题A`
- 模型回：`思考过程 + 回答A`

缓存里可能记住的是：

```text
系统提示 + 问题A + 思考过程 + 回答A
```

###### 第二次请求
客户端通常会发：

```text
系统提示 + 问题A + 回答A + 问题B
```

注意：**“思考过程”没带回来**。

于是模型一比对：

- 缓存：`系统 + 问题A + 思考过程 + 回答A`
- 新请求：`系统 + 问题A + 回答A + 问题B`

它会发现：
- 前面只有 `系统 + 问题A` 是稳定一致的；
- 后面很快就对不上了。

结果就是：**缓存不是完全没命中，而是命中了一个很短的前缀，仍然要重新处理大量 token**。  
所以用户体感上就像“缓存没工作”。

---

##### 3. 为什么工具调用也会破坏缓存？

因为缓存看的是 **token 是否完全一致**，不是“语义差不多”。

比如下面两段 JSON：

```json
{"a":1,"b":2}
```

和

```json
{"b":2,"a":1}
```

对人来说一样，对缓存来说**不是同一串 token**。

Issue 里有人发现，Qwen3.5 的 chat template 在工具描述、参数顺序、tool args 序列化时，经常前后轮次不一致。  
于是虽然工具没变，prompt 开头却悄悄变了，缓存直接 miss。

这也是为什么有人建议：

- `tojson(sort_keys=True)`
- 参数遍历时做 `dictsort`

本质上就是让 prompt **稳定化**，这样缓存才有机会命中。

---

##### 4. 为什么还会 OOM？

Issue 里还提到一个问题：  
**LRU prompt cache 在 trim/copy 时，旧缓存可能还留在内存里。**

本来这样设计是为了支持“会话分叉”——一个会话可以从同一个前缀继续发展。

但如果每个缓存都很大（比如 10GB），你 trim/copy 几次就可能变成：

- 1 份 10GB
- 复制成 10 份
- 直接占掉 100GB

所以不是单纯“缓存没命中”，而是**缓存策略本身也可能很吃内存**。

---

#### 目前社区里比较明确的方向

##### 已识别出的优化方向

###### 1. 对 reasoning model，只保存到“开始推理前”的缓存点
也就是不要把 `&lt;think>` 或 reasoning token 也一起存进 prompt cache。  
这样下一轮请求更容易和缓存前缀对齐。

这是讨论里比较被认可的方向。

###### 2. 对混合模型按“层”处理缓存，而不是按“整个模型”处理
有人提出：
- 可裁剪层按普通方式处理；
- 不可裁剪层只存稀疏快照/锚点；
- 这样可以减少整段重算和大内存复制。

维护者回复说：**这基本就是计划方向**。

###### 3. 让 chat template 更稳定
比如：
- 工具 JSON key 排序
- 参数顺序固定
- 避免同一工具在不同轮渲染成不同 token 序列

这是最容易立刻见效的工程优化。

#### 我的意见

##### 一句话判断

**这更像是“Qwen3.5 + mlx-lm 当前缓存机制适配不完善”的问题，不是你用法有问题。**

---

##### 我对问题优先级的看法

###### 如果你是普通使用者
短期最值得做的是：

1. **升级到较新的 `mlx-lm` 版本**
   - 因为一些 `&lt;think>` / hybrid cache 相关修复已经在推进。

2. **尽量保证 prompt 稳定**
   - system prompt 不要动态改动
   - tools 的 JSON 顺序固定
   - 参数顺序固定
   - chat template 尽量统一

3. **如果是 agent / tool-heavy 场景，优先怀疑模板和工具序列化**
   - 很多“缓存没命中”其实不是模型本身，而是前端传入内容每轮都不完全一样。

---

###### 如果你是开发者
我认为最重要的正式修复顺序应该是：

1. **reasoning cache checkpoint 前移**
   - 只缓存到 reasoning 开始前；
   - 这是收益大、逻辑也相对清晰的修复。

2. **对不可裁剪缓存做分层缓存设计**
   - 这是从根本上解决 hybrid / SSM 模型缓存复用差的问题。

3. **加入 cache 内存占用感知**
   - 避免 trim/copy 把内存炸掉。

4. **让 chat template / tools 序列化更稳定**
   - 这类问题看似“小”，但对缓存命中率影响极大。

---

##### 实际建议

如果你现在就在用 Qwen3.5 + MLX agent，我建议：

- **先不要指望“像 Minimax 那样顺滑缓存”**
- **优先修模板稳定性**
- **减少工具描述和参数的非必要变化**
- **关注相关 PR/Issue（如 #911、#923）**
- 如果是生产用途，**先做压测再决定是否继续用 Qwen3.5 作为长上下文 agent 主力模型**

---

#### 结论

这条 Issue 说明了一件事：

> **Qwen3.5 在 `mlx-lm` 里的缓存问题，不是单点 bug，而是“模型结构 + reasoning 机制 + 工具模板稳定性 + 缓存策略”叠加造成的。**

短期能缓解，长期需要框架层面做更细的缓存设计。  
如果你现在遇到“每轮都重跑整段 prompt”，**大概率不是错觉，社区里很多人都复现了。**
