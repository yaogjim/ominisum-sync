How it works

#### Eight stages, start to finish.

You write the brief. copperhead runs the stages in order, each one its own agent run. A stage has to leave its artifact on disk before the next starts. If a gate fails, the run stops there.

1. 01
   ##### spec
   `docs/SPEC.md`
   gate a budgets section, actually filled in
2. 02
   ##### architecture
   `docs/SUBSYSTEMS.md`
   gate real reasoning under every subsystem
3. 03
   ##### parts
   `docs/BOM.md`
   gate part numbers chosen against datasheets
4. 04
   ##### schematic
   `design.kicad_sch`
   gate symbols placed, docs agree, ERC clean
5. 05
   ##### layout
   `design.kicad_pcb`
   gate footprints on the board, DRC clean
6. 06
   ##### outputs
   `gerbers / drill / STEP`
   gate gerbers actually on disk
7. 07
   ##### firmware
   `firmware/ / pins.h`
   gate sources on disk, pins from the pinout
8. 08
   ##### dev plan
   `docs/DEVPLAN.md`
   gate a written bring-up and test plan

- Every hop is a gate: **no real work on disk, no commit**.
- Copper border: **verified by KiCad itself, ERC and DRC clean**.

FAQ

#### Questions, before you ask them.

What is copperhead?

An open source AI agent that designs, documents and verifies printed circuit boards. You describe a change or hand it a product brief, and it edits your real KiCad files, updates every document that references them, and runs KiCad's own checks until they pass. Longer introduction here.

What problem does it actually solve?

Drift. A hardware design spreads one decision across a schematic, a bill of materials, a power budget and several documents, and nothing breaks when they fall out of sync. The inconsistency is found at bring-up, and a respin costs 5,000 to 50,000 dollars and six to eight weeks. The full argument is here.

What do I need installed?

Node 20 or newer, [KiCad](https://www.kicad.org/) with `kicad-cli` on your path and a model API key of your own. Then `npm i -g copperhead`.

Does it work on a design that already exists?

That is the main case. Point it at a KiCad repository, run `copperhead init` and start asking for changes. It can also run the full pipeline from a written brief with `copperhead create`, but iterating on real designs is what it is best at.

What will it refuse to do?

It refuses to run on a dirty git tree, refuses to edit any design file before a validated change proposal exists and refuses changes that break a budget or constraint you have documented, citing the line it would violate. It also never invents a part number it cannot justify from a datasheet.

Will it rewrite my whole schematic?

No. Edits are surgical changes to the KiCad s-expression source, so your diffs stay small and reviewable and untouched parts of the file stay byte-identical. A tool that regenerates the file to move one net has made its own work impossible to review.

## 深度解读（1）

### 2026-09-18 00:04:47

#### Copperhead 的价值不在“AI 画板”，而在让硬件变更可验证、可追责

Copperhead 表面上是一个能生成和修改 KiCad PCB 的 AI Agent，但更值得关注的设计，是它没有把“模型生成了文件”当成任务完成。它把流程拆成规格、架构、选型、原理图、布局、生产文件、固件和测试计划八个阶段；每一步都必须留下实际产物，并通过相应检查才能继续。

其中真正承担验证工作的也不是模型，而是 KiCad 的 ERC、DRC、文件存在性检查以及预先写明的预算和约束。**模型负责提出和执行修改，确定性工具负责阻止明显错误进入下一阶段。**这比单纯提高模型的 PCB 生成能力更有迁移价值：在工程场景里，可信度往往不是来自“AI 更聪明”，而是来自它必须提交证据，并接受现有权威工具的检查。

##### 它瞄准的核心问题是设计漂移，而不是从零生成

硬件的一次变更，可能同时影响原理图、BOM、功耗预算、引脚定义、固件和说明文档。软件中很多不一致会被编译器或测试迅速暴露，硬件中的不一致却可能直到打样、焊接和 bring-up 才出现。Copperhead 所说的“drift”因此是一个真实且昂贵的问题，尽管网页中“重打样损失 5000—50000 美元、延期六到八周”的数字没有给出来源。

它把“修改已有设计”列为主要场景，也是比自动从 brief 生成整块板更合理的切口。拒绝在 dirty git tree 上运行、修改前必须先生成并验证 change proposal、只对 KiCad 源文件做局部编辑、保持无关部分字节不变，这些规则并不炫目，却直接服务于代码审查式的硬件协作：工程师看到的是一个小而明确的 diff，而不是让 AI 重写整个文件后再猜哪里发生了变化。

这说明高风险专业工具的关键产品指标，未必是“一次完成率”，而可能是**修改是否可解释、错误是否能被拦截、人工是否容易复核，以及失败后能否恢复**。

##### 商业模式卖的不是生成能力，而是组织级信任

免费 CLI 提供完整本地能力，用户自带模型 Key，产物保持为 Markdown、JSON 和 KiCad 文件；收费层则提供托管运行、团队协作、CI 检查、共享约束库、权限、审计、自托管和合规支持。这种 open-core 路径与需求较为匹配：个人工程师需要的是能力，团队和企业愿意付费的则是统一执行、责任边界和审计证据。

但目前的证据仍然有限。公开案例只有一块袖珍 ESP32-S3 电报键，足以证明流程能跑通，不足以证明它能处理高速信号、电源完整性、散热、EMC、机械配合、可制造性和供应链替代等复杂约束。ERC、DRC 干净只表示规则内没有报错，并不表示板子一定能工作；能从 datasheet 解释料号，也不等于器件合适、可采购或长期供货。

因此，Copperhead 最值得验证的不是“它能不能自动画一块板”，而是：**在真实存量项目中，它能否持续减少跨文件不一致，同时不制造大量误报、错误修改和额外审查负担。**如果这一点成立，它代表的将不是又一个生成式设计工具，而是一种更可靠的工程 Agent 范式——自主性被约束包围，每次行动都留下可检查的产物。

## 口播总结（1）

### 2026-09-20 00:35:15

Copperhead 是一个面向印刷电路板设计的开源人工智能代理。它要解决的核心问题，不只是“让人工智能画电路板”，而是防止设计文件、物料清单和技术文档彼此脱节。它会直接修改真实的 KiCad 工程，并用 KiCad 自己的检查工具验证结果。

为什么文件不同步这么危险？一项硬件设计决策，往往会同时出现在原理图、物料清单、功耗预算、引脚定义和测试文档里。工程师改了其中一处，其他地方却不会自动报错。问题常常要到硬件上电调试时才暴露。Copperhead 官网给出的估算是，一次重新打板可能损失五千到五万美元，并耽误六到八周。

Copperhead 的思路，是把设计流程拆成八个连续阶段，而且每个阶段都有一道硬性关卡。前一阶段必须在磁盘上留下真实、可检查的文件，下一阶段才能开始。任何检查失败，流程就停在现场，不会假装已经完成。

第一阶段是规格定义，要生成完整的规格文档，其中必须包含已经填写的预算和约束。第二阶段是系统架构，要解释各个子系统为什么这样划分，而不是只列出名称。第三阶段是元器件选择，要形成物料清单。具体料号必须有数据手册作为依据，不能凭空编造。

接下来进入真正的电路设计。第四阶段生成 KiCad 原理图，并运行电气规则检查，也就是 ERC。元件符号必须实际放进原理图，相关文档也必须与设计一致。第五阶段完成电路板布局，封装要真实出现在板上，并通过设计规则检查，也就是 DRC。

第六阶段输出生产文件，包括 Gerber 文件、钻孔文件和三维模型。系统不是只报告“导出成功”，而是要确认这些文件确实已经写入磁盘。第七阶段处理固件，生成源代码和引脚定义，而且引脚必须来自已经确定的硬件引脚表。第八阶段形成开发计划，写清楚上电调试和测试步骤。

这套流程的关键，可以概括成一句话：没有真实成果文件，就不能进入下一步；没有通过验证，就不能提交版本。原理图和电路板是否合规，也不是由人工智能自己宣布，而是由 KiCad 的 ERC 和 DRC 工具检查。

Copperhead 尤其强调对现有工程进行增量修改。用户可以把它指向一个已经存在的 KiCad 代码仓库，初始化之后，再用自然语言提出改动要求。它也能根据一份简短的产品说明，从头跑完整流程。不过按照项目方的说法，它最擅长的场景，仍然是在真实设计上持续迭代。

为了让修改可控，Copperhead 设置了几条拒绝规则。如果 Git 工作区里存在尚未处理的改动，它会拒绝运行。如果还没有经过验证的变更方案，它不会直接编辑设计文件。如果某项修改违反了文档中明确记录的预算或约束，它也会拒绝执行，并指出冲突发生在哪一行。

它修改原理图时，并不会为了改动一根网络，就重新生成整个文件。Copperhead 会直接编辑 KiCad 使用的结构化源文件，只做局部变更。这样一来，版本差异会比较小，工程师更容易审核；没有被触碰的部分则保持不变。对于需要代码审查和责任追踪的团队，这一点非常重要。

项目方还公开了一个名为 Open Telegraph 的验证案例。这是一台口袋大小、采用 ESP 三十二 S 三芯片的摩尔斯电码键。它从规格、元器件选择到原理图、布局、固件和测试计划，都按照这套流程完成。相关决策、检查结果和文件也全部公开，用来证明这套方法确实在真实电路板上运行过。

Copperhead 采用开放核心模式。命令行工具免费并保持开源，可以在用户自己的电脑和 Git 仓库里运行。用户需要准备二十或更高版本的 Node、带命令行工具的 KiCad，以及自己的 Claude 或 GPT 五模型接口密钥。生成结果使用普通的 Markdown、JSON 和 KiCad 文件，因此不会被锁在专有格式里。

收费部分主要解决托管、协作和审计问题。云服务按用户每月四十九美元收费，提供私有仓库运行、网页查看器、检查历史，以及 Gerber、三维模型和物料清单导出。团队版价格同样是每人每月四十九美元，在云服务基础上增加持续集成检查、共享约束库、单点登录和集中管理。企业版则按年度定制，可部署在企业自己的网络或私有云中，并提供更完整的权限控制、审计记录和技术支持。

理解 Copperhead，最值得记住的不是“人工智能可以自动画板”，而是它把硬件开发变成了一条有文件、有约束、有检查的连续流程。它试图消除的，是原理图、物料清单、预算、固件和文档之间悄悄产生的偏差。真正的价值，也不在一次生成，而在每次修改都能留下小而清楚的差异，并由现有工程工具重新验证。

## 深度解读-口播（1）

### 2026-09-30 11:57:19

设计一块电路板，难点不只是把线路画出来。更麻烦的是，电路已经改了，元器件清单、功耗预算和说明文档却还停在旧版本。Copperhead 这款人工智能工具，主要想解决的，就是硬件设计中这种不知不觉发生的不同步。

它把自己定位为电路板领域的智能编程助手。你提出修改要求，或者交给它一份产品需求，它就直接修改真实的设计文件，同步更新相关文档，再调用电路板设计软件 KiCad 自带的检查工具，验证修改结果。

这里最值得注意的，不是“人工智能会画电路板”，而是它试图让设计、文档和检查始终保持一致。

为什么这件事重要？因为硬件上的一个决定，往往同时存在于好几个地方。比如选择某个元器件，既会影响原理图，也会影响物料清单，还可能影响电源预算。只改其中一处，其他文件未必会自动报错。

按照 Copperhead 网站的说法，这类不一致，有时要等到电路板做出来、开始上电调试时才会被发现。重新做一版板子，可能花费五千到五万美元，还要再等六到八周。这是网站给出的成本范围，不是每个项目都会付出同样的代价。但它说明了产品的核心思路：尽量把问题拦在文件和检查阶段，而不是留到实物调试时。

为了做到这一点，Copperhead 把从需求到交付的过程，拆成八个阶段。每个阶段都是一次独立的人工智能代理运行，而且必须把实际成果写到磁盘上，下一阶段才能开始。任何一道检查关卡失败，流程就停在那里。

这套流程可以分成三段来理解。

第一段，是把“想做什么”变成有依据的设计。先写规格，其中必须有真正填好的预算部分。再拆分系统架构，每个子系统都要说明设计理由。接着选择元器件，具体型号必须能从数据手册中找到依据。

也就是说，不能只有一句“这里需要一个合适的芯片”，更不能编出一个看起来像真的型号。设计需要落实到可核查的选择。

第二段，是把这些决定变成电路板文件。先做原理图，要求元器件符号已经放好，相关文档与设计一致，并通过电气规则检查。然后做电路板布局，要求元器件封装已经放到板上，并通过设计规则检查。

这两种检查都由 KiCad 自己执行。电气规则检查，主要检查电气连接规则是否存在冲突；设计规则检查，则检查板上的布局和布线是否符合设定规则。Copperhead 强调的，是调用设计软件本身来验证，而不只是让人工智能口头说一句“检查通过”。

第三段，是准备制造和调试所需的交付物。制造文件必须真实生成，包括用于生产电路板的 Gerber 文件、钻孔文件和三维模型。固件阶段要留下源代码，引脚定义要来自设计中的引脚分配。最后，还要写出上电调试和测试计划。

所以，这八个阶段的共同要求很简单：不能只说工作做完了，要有真实文件，也要过对应的检查关卡。

不过，Copperhead 最擅长的场景，并不是从一张白纸开始。网站明确说，围绕已有的 KiCad 设计反复修改，才是它的主要用途。

这也解释了它为什么特别重视修改的边界。

开始工作前，代码仓库必须处于干净状态，也就是不能混着尚未提交的改动。修改设计文件前，必须先有经过验证的变更提案。如果修改会违反已经写明的预算或约束，它就拒绝执行，并指出会违反哪一条记录。

文件怎么改，同样重要。Copperhead 宣称，它对 KiCad 文件做的是局部、精确的修改，而不是为了挪动一条连接，就把整张原理图重新生成一遍。没有改动的部分，保持原样。这样，工程师审查版本差异时，就更容易看清人工智能究竟改了什么。

把这些限制放在一起看，产品的重点就更清楚了：它不只是替人操作设计软件，还试图让每一次修改都有依据、有边界，并且便于复核。

网站也给出了一个公开案例，叫 Open Telegraph。这是一款采用 ESP32-S3 微控制器的口袋大小摩尔斯电码电键。网站称，这个项目从头到尾使用了上述流程，设计决策、检查过程和文件都公开可查。这个案例的意义，在于提供了一份真实项目记录，让人可以查看流程实际留下了什么。

使用方式上，Copperhead 采用开放核心模式。免费的命令行版本在用户自己的电脑上运行，直接处理自己的 KiCad 文件和版本仓库。输出使用普通的 Markdown 文档、JSON 数据和 KiCad 文件，强调不把用户锁在专有格式里。不过，使用者需要自行提供人工智能模型的接口密钥；命令行工具免费，不等于模型调用也免费。

付费部分主要卖的是托管和协作。云端版每位用户每月四十九美元，提供托管运行、网页查看设计和检查报告等功能。团队版也是每位用户每月四十九美元，在此基础上增加自动检查、共享约束和组织管理。企业版则提供自托管或私有云部署，以及审计、支持等服务，按年定制报价。

最值得记住的是，Copperhead 要解决的核心问题，是电路板设计与文档之间的漂移。它的主要办法，是让修改直接落到真实文件里，让相关记录同步变化，再用明确的关卡检查结果。这里的价值不只是“生成得更快”，而是让一次硬件修改更有依据，也更容易被检查和审查。
