**STEP 01**

##### 手动安装

如果你熟悉命令行，也可以自己把项目克隆到电脑，然后进入目录安装依赖。

```
git clone https://github.com/nutllwhy/hyperframes-motion-library.git
cd hyperframes-motion-library
npm install
```

**STEP 02**

##### 本地启动和渲染

本地启动后可以改参数、看预览、生成视频。渲染会调用本机的 Chrome / FFmpeg，所以算力成本由自己的电脑承担。

```
npm run dev
npm run check
npm run render -- metric-pulse templates/metric-pulse/presets/default.json
```

**STEP 03**

##### 让 Agent 继续加动效

把整个文件夹交给自己的 Agent，让它先读项目规范，再按同样结构新增模板。

1. 先读 `README.md` ，理解系统怎么运行。
2. 再读 `SYSTEM.md` ，理解一个模板必须包含什么。
3. 参考已有 `templates/<id>/` 目录，新增自己的动效。
4. 更新 `catalog.json` ，让新模板出现在展示站里。
5. 运行检查，确认模板可以被复用。

**AGENT PROMPT**

##### 可以直接复制给 Agent 的任务描述

```

1. 在 templates/<template-id>/ 下创建 index.html、design.md、meta.json、presets/default.json、package.json。
2. 动效必须使用 HyperFrames 的 data-composition-variables 暴露可编辑文案、数字和颜色。
3. 默认配色沿用黑色背景 + 橙色强调，不要引入蓝绿色系。
4. 先完成最完整时刻的静态布局，再加入确定性的 GSAP 动画。
5. 更新 catalog.json，让模板出现在展示站。
6. 运行 npm run check，并尽量为新模板生成 sample 预览。
7. 不要破坏已有模板和已有预设。
```

##### Agent 有效的前提，是任务已经被规范化

页面给 Agent 的指令非常具体：先读 `README.md` 和 `SYSTEM.md`，按既有目录创建文件，暴露指定变量，先完成静态布局，再添加确定性的 GSAP 动画，最后更新目录并运行检查。这揭示了一个容易被忽略的事实：**Agent 并不是凭空获得了设计与工程能力，而是因为项目把隐性经验写成了机器可执行的约束。**

这套思路可以迁移到很多内容生产场景。设计系统不仅要提供组件，还应定义新增组件需要哪些文件、哪些参数必须可编辑、怎样验收、怎样进入资产目录。文档、示例、脚手架和检查器共同构成了 Agent 的工作环境。相比继续优化提示词，建立这样的“生产协议”通常更能提升结果的一致性。

不过，页面目前证明的是工作流可运行，而不是 Agent 能稳定产出高质量动效。`npm run check` 如果只验证文件是否齐全，就无法发现节奏生硬、文字溢出、镜头安全区失效或不同分辨率下视觉崩坏。模板越多，真正的瓶颈越可能从“生成代码”转向**视觉质量如何被自动验收**。

##### 最现实的机会是高频、结构化的视频生产

它最适合的用户，不是偶尔剪一个视频的个人，而是反复制作同类内容的团队：媒体数据栏目、增长营销、产品运营、研究报告视频化，以及需要保持品牌一致性的内容工作室。现有替代方案通常是剪辑软件模板、AE 工程或设计师手工改稿；它们成熟，但批量改数据、版本管理和 Agent 协作并不自然。

这里值得验证的并非“大家是否喜欢 AI 动效”，而是更具体的三个问题：同类视频是否足够高频，模板化能否显著缩短交付时间，以及非开发者能否承受 Node、Chrome、FFmpeg 等本地环境成本。后者也是当前方案的明显边界：本地渲染节省云端费用并保护素材，却把安装、兼容性和算力负担交给用户。

因此，这个项目最有启发的判断不是“Agent 会替代动效设计师”，而是：**当创意工作被拆成明确接口、可复用资产和自动检查后，Agent 才可能从一次性助手变成生产系统的一部分。** 下一步最值得关注的，也不是模板数量，而是它能否建立可靠的视觉验收、版本治理与批量内容接口。
