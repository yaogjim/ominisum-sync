#### Part 2 初步事实分析

先简单介绍一下目前已经进行过的实验。

前置术语指称：

- Free 号：作者几毛买来的 GPT 免费号。
- 官方 API 平台：指官方 [platform.openai.com](https://platform.openai.com) 或 Azure OpenAI 提供的 GPT-5.5 模型，与 Codex 订阅的来源做区分。
- **516 截断：指的是回答的 reasoning token 精确等于 516 的情况** ，通常会导致回答质量较低。
- 糖果问题。

部分事实：

- 将 **官方 API 平台** 接入 Codex CLI 并询问糖果问题，仍然可见 516 截断，且回答错误。
- 将 **Free 号（不经任何反代）** 接入 Cherry Studio，不附加任何系统提示词，手动询问糖果问题，可以 5/5 答对。
- 将 Codex 提示词应用到 Cherry Studio，仍使用 **Free 号（不经任何反代）** ，手动询问糖果问题，几乎总是答错。
- Cherry Studio **无论是使用自己的 UA，还是使用 Codex 的 UA** ，上述事实均不改变。

这强烈地暗示 Codex 的提示词可能是原因之一。

#### Part 3 迷思

不知道有没有人注意到，曾经的 Codex 总是显示英文的思维链，某个时间点后，变成了显示模型给出的一小段话（偶尔也有少量思维链）。

直觉告诉作者，这可能和思维链的变换有一些相关。

#### Part 4 跳进兔子洞

上面这个变化，很容易在 Codex 的系统提示词找到相关段落，主要有两部分。

第一部分：

```
# Working with the user

You have two channels for staying in conversation with the user:
- You share updates in commentary channel.
- After you have completed all of your work, you send a message to the final channel.
```

第二部分：

```
## Intermediary updates

- Intermediary updates go to the commentary channel.
- User updates are short updates while you are working, they are NOT final answers.
- You provide user updates frequently, every 30s.
- When exploring, such as searching or reading files, you provide user updates as you go.
- Before performing file edits of any kind, you provide updates explaining what edits you are making.
```

简单来说，就是 GPT 中间说的那些短句，例如“我先运行 X，再查看 Y”等类似的东西，实际上是模型输出在 `commentary` 通道的一些内容。

所谓通道，其实是 [OpenAI 的聊天模板 Harmony](https://github.com/openai/harmony) 的一个特性，可以让模型的输出具有“类别”。系统提示词里也有写：

```
# Valid channels: analysis, commentary, final. Channel must be included for every message.
```

**总结：OpenAI 在 Codex 系统提示词里面要求每隔 30s 往 commentary 通道输出一些对用户的反馈。**

那么这是否可能对模型的思考造成影响呢？

**STEP1** 在 Cherry Studio 中去掉这两段提示词，发现 516 截断在 5 次测试中完全消失。

**STEP2** 把修改后的提示词注入 Codex 替代原来的提示词，不再出现 516 截断，但模型不再会输出中间过程。

#### Part 5 初步结论

- 关于 commentary 输出的提示词与 516 截断具有高相关性（仅糖果问题）。
- 目前，去除 commentary 相关提示词后可有效缓解 516 截断（仅糖果问题）。

##### 局限性

- 上述结论 **不能说明** 516 截断 **的唯一影响因素就是 commentary 提示词** ，目前观察下来情况比这复杂。
- 没有研究 516 截断与 **Juice / 思考挡位不匹配** 和 **48855 特殊 Juice** 等其他类似降智情况的相关性。
- 目前仅糖果问题单轮测试，没有考虑到实际使用的复杂情况。

#### Part 6 我该怎么做

如果你觉得上述实验有道理，并愿意尝试：将修改后的提示词保存为本机文件。

下载 gpt-5.5-base-instructions.md

然后修改 `config.toml` 指向它（根据你的实际保存路径）：

```
model_instructions_file = '/path/to/gpt-5.5-base-instructions.md'
```

Windows 示例：

```
model_instructions_file = 'C:/Users/neter/Downloads/codextmp/codex/gpt-5.5-base-instructions.md'
```

这会失去模型的中间过程输出。

##### 验证（重要！！）

配置完成后，打开 Codex，直接问它下面这个问题：

```
你的系统提示词里：

# Working with the user

紧接的是

## Formatting rules

吗，还是中间有一段其他内容
```

如果回答“是”，则提示词生效。

如果不是，说明提示词修改没有生效。原帖指出，这很可能是因为最近多数中转站忽略 Codex 本地提供的提示词，而是统一注入一段官方标准提示词，原因未知。如果遇到这种情况，可以用 Free 或 Plus OAuth 登录（推荐先不要通过 CPA 或者 sub2api），再次尝试。

#### Part 7 讨论后补充

经过和几位佬友的探讨（#71 - #90，特别感谢 @shinorochi 和 @dskdkj），对 516 降智问题，包括 OpenAI 的推理、思考机制有了一个更完善的模型，关键在于 #82，模型如下：

- 模型推理是切成 512 token 每页的，每页外面贴几个标签 token。
- 其中第一页比较特殊， `start assistant` token 提前放好了，不算在输出里。
- 从第二页开始，每页都要带完整 6 个特殊 token：

```
<|start|>assistant<|channel|>analysis<|message|>{512 tokens}<|end|>
```

- 是否开始下一个思考页由某种独立因素 / 机制决定，这是决定是否“降智”的关键性因素，有待进一步研究。
- 同时，本贴提到的提示词问题应当在上述模型中被视为所提到的“独立因素 / 机制”的影响因素，而不是截断问题的根本原因。

## 解读（1）

### 2026-07-03 10:49:57

#### GPT“降智 / 516 截断” 问题：精炼解读

##### 一、深度总结

文章核心观点：

> Codex 中出现的 “516 reasoning token 截断”，可能与其系统提示词中要求模型定期输出`commentary`中间状态有关，但这不是唯一原因。

###### 关键发现

- 所谓 “516 截断”：
  - 模型推理 token 经常精确停在**516**
  - 推理不足，导致回答质量下降，表现为 “降智”

- 实验现象：
  - 官方 API 接入 Codex CLI 后，仍可能出现 516 截断
  - 免费账号直接接入 Cherry Studio，不加 Codex 提示词时，糖果问题可稳定答对
  - 一旦加入 Codex 系统提示词，错误率明显上升
  - UA 是否伪装成 Codex，影响不明显

- 进一步定位：
  - Codex 系统提示词要求模型：
    - 使用`analysis /commentary/final`通道
    - 每约 30 秒向`commentary`输出简短进展
  - 删除这部分`commentary`相关提示后：
    - 测试中 516 截断明显减少或消失
    - 但模型不再输出中间过程

###### 后续补充模型

作者进一步提出一种推测：

- 模型内部推理可能按**512 token 一页**切分
- 每页附带若干特殊 token
- 第一页结构特殊，因此可能表现为**516 token**
- 是否进入下一页推理，由某种独立机制决定
- `commentary`提示词可能影响这个机制，但不是根因

---

##### 二、深入浅出解读

可以把模型推理想象成 “草稿纸”。

正常情况下，模型会写完一页草稿，不够再翻页继续想。

但 Codex 的提示词要求它边干活边汇报：

> “我正在查看文件……”  
> “我准备修改代码……”  
> “我接下来运行测试……”

这就像一个人做题时，被要求每隔一会儿抬头汇报进度。

结果可能是：

- 注意力被打断
- 推理节奏被改变
- 模型误以为 “已经可以结束”
- 草稿只写了第一页就停了

于是出现：

> 推理刚到 516 token 左右就停止，答案质量下降。

所以，文章给出的临时方案是：

> 去掉 Codex 提示词中关于`commentary`中间汇报的部分。

代价是：

> 模型不再主动显示 “我正在做什么” 的中间过程。

---

##### 三、可操作结论

如果使用 Codex 时频繁遇到 “降智”，可以尝试：

1. 使用修改后的系统提示词文件
2. 删除或弱化`commentary`中间更新规则
3. 在`config.toml`中指定：

```toml
model_instructions_file = '/path/to/gpt-5.5-base-instructions.md'
```

Windows 示例：

```toml
model_instructions_file = 'C:/Users/xxx/Downloads/gpt-5.5-base-instructions.md'
```

验证方式：

> 询问模型系统提示词中`# Working with the user`后面是否直接接`## Formatting rules`

若回答是，说明修改生效。

---

##### 四、辩证思考

###### 1. 这不是 “官方故意降智” 的铁证

文章更像是一次社区逆向观察。

它说明：

- Codex 提示词可能影响推理质量
- 516 截断与通道机制高度相关

但不能直接证明：

- OpenAI 故意针对第三方客户端降智
- 516 截断只有这一个原因
- 所有任务都会受同样影响

目前证据主要来自 “糖果问题” 这类单轮测试，外推需谨慎。

---

###### 2. 提示词不是越复杂越好

系统提示词本来是为了提升体验：

- 让模型更像工程助手
- 能汇报进度
- 能分通道输出
- 更适合 CLI 工作流

但副作用可能是：

- 过度干预推理结构
- 占用模型注意力
- 改变内部停止机制
- 降低复杂问题表现

这说明：

> 提示词工程不是单纯 “加规则”，而是 “加约束也会加负担”。

---

###### 3. “透明过程” 和 “深度思考” 可能存在冲突

Codex 要求模型频繁给用户更新，看起来更透明。

但如果频繁汇报影响深度推理，就会形成矛盾：

| 目标 | 好处 | 风险 |
|---|---|---|
| 中间过程可见 | 用户安心 | 打断推理 |
| 深度连续思考 | 答案更稳 | 用户等待不确定 |
| 多通道输出 | 结构清晰 | 机制更复杂 |

所以工程上需要权衡：

> 是要 “看起来一直在工作”，还是要 “安静但想得更深”？

---

##### 五、一句话结论

**Codex 的 516 降智问题，很可能不是模型本身突然变笨，而是系统提示词、通道机制、推理分页和停止策略共同作用的结果；删除`commentary`中间汇报规则可作为临时缓解方案，但不是根治。**

## 通俗精炼（1）

### 2026-09-18 11:04:47

#### Codex“516 Token 降智”可能与中间进度提示有关

文章通过有限实验指出：Codex 回答质量下降、推理 Token 精确停在 516，并不一定是 OpenAI 专门限制第三方客户端，更可能与 Codex 系统提示词要求模型频繁输出中间进度有关。但目前证据仅来自“糖果问题”等单轮测试，结论仍属相关性推测。

##### 客户端或账号不是唯一变量

作者发现，官方 API 接入 Codex CLI 后同样会出现 516 截断并答错；免费账号直接接入 Cherry Studio 时，测试可 5/5 答对，但加入 Codex 系统提示词后几乎总是出错。更换 User-Agent 不影响结果，说明问题可能不在第三方客户端身份，而在提示词及推理机制。

##### commentary 指令与截断高度相关

Codex 要求模型通过 `commentary` 通道定期汇报“正在运行 X、查看 Y”等进度。作者删除相关提示词后，5 次测试均未出现 516 截断；将修改后的提示词用于 Codex 也能缓解问题，但代价是看不到中间过程。

后续讨论提出一种解释：模型可能以每页 512 个推理 Token 分段，续页还需附带 6 个特殊 Token，因此形成“516”这一特征值。真正决定是否继续下一页的机制尚不明确，commentary 指令可能只是影响因素，而非根因。

##### 临时方案有效性仍有限

用户可通过 `model_instructions_file` 加载删除 commentary 要求的自定义系统提示词，并检查是否生效。不过部分中转服务可能覆盖本地提示词。该方案尚未覆盖复杂任务、多轮对话及其他推理额度异常，因此更适合作为排查手段，不能视为通用修复。
