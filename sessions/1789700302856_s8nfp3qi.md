## 分析要点

- **核心高价值点**：在让Agent编码前，先用可行性分析、设计文档和高保真原型依次消除产品、技术与交互层面的不确定性。
- **留存建议**：建议存档，作为AI辅助功能开发流程的实践模板（提供了从需求判断、方案设计、原型验证到实现测试的完整流程，具有较强的复用和实践价值。）

**知识要点**

- 功能开发前应分别验证产品价值、产品定位匹配度、技术可行性与成本可控性。
- 产品与技术混合设计文档可作为Agent实施上下文、人工方向确认依据及后续维护参考。
- 高保真原型能够在编码前低成本明确界面、交互和场景划分，并通过多轮反馈快速收敛。

**行动项**

- 收到新功能需求后，先让Agent结合现有代码库输出可行性分析和候选技术方案。
- 编码前形成包含需求、架构、界面和实施里程碑的设计文档，并由人工确认方向。
- 先迭代高保真原型，再让Agent按里程碑实现，最后由人工执行多轮黑盒测试并反馈修正。

### 我的 AI 开发流程

之前有网友问我我的 AI 开发流程是什么，正好我前几天用 AI 实现了一个小功能，值得拿出来作为案例展示一下，也可以作为一个参考。

![Image](https://pbs.twimg.com/media/HQhSiBCX0AA9veu?format=jpg&name=large)

这个功能起源是有网友在 GitHub 的 Issues 给我留言（图1），问能不能给我写的字幕转录翻译 App BaoCut 加上远程转录功能。 也就是说我有两台电脑，一台是有英伟达显卡的高性能电脑 A，另一台只是日常办公的电脑 B，我想借助电脑 A 的算力，但日常一般只在电脑 B 上使用，我在电脑 B 使用 BaoCut 去转录的时候，把消耗算力转录的工作让电脑 A 完成。 我一看就觉得这是挺好的需求，但我没做过这个工作，也不知道是不是可行。 所以我的第一步不是马上去写代码，而是先做可行性分析。 一、可行性分析 没有做可行性就盲目动手我吃的亏可太多了，经常白忙活。另外就算做了可行性分析，有时候也可能做出错误判断，比如我前几天还做了一个本地文本模型帮助拆分对齐的，做可行性分析的时候觉得没问题，做完了实际体验才发现效果很糟糕，最后还是砍掉了，浪费了几天时间加很多 token，还好只是 token。 可行性分析通常有两个层面： 一个是从产品角度，这个功能是不是有价值，是不是和 App 的定位符合 一个是从技术角度，看这个功能技术上是否可行，成本是否可控 这里我从产品角度觉得这个功能对用户是有价值的，也和产品定位符合，所以我只是聚焦在技术可行性分析上。

![Image](https://pbs.twimg.com/media/HQhSuB_WAAAWB4a?format=jpg&name=large)

## 默认总结（1）

### 2026-09-18 02:58:22

##### 一句话看懂

作者用给 BaoCut 增加 “远程调用另一台电脑算力转录” 的案例，展示了一套 AI 开发流程：**先验证可行性，再写设计、做原型，最后让 AI 实现，并由人负责体验和验收。**

##### 关键内容

- **先判断值不值得做。**作者先从产品价值、定位和技术成本评估需求，让 Claude Code 结合现有项目提出多个方案，再按易用性与 Windows 兼容性选择方案 A，而不是直接写代码。
- **用文档和原型提前定方向。** AI 生成产品与技术混合设计文档；随后制作高精度交互原型，并由作者多轮调整页面布局、功能入口和状态展示。
- **方案明确后再交给 Agent 编码。** AI 按文档中的阶段逐步实现，并自行截图验证；作者再手动运行，通过黑盒测试发现问题并要求修改。
- **这不是严谨的软件工程范本。**作者明确表示自己没有审查代码，只充当 QA，并承认可行性分析也可能误判，因此结果较依赖所用 Agent 的能力。

##### 通俗解读

核心不是 “让 AI 一句话生成应用”，而是**人把关需求与体验，AI 承担分析、设计和编码**。这套方法适合想了解 AI Agent 实战协作的人，案例具体，值得细读；若想看远程转录的代码细节、测试规范或安全设计，原文信息不足，且部分过程依赖未展示的配图。

## 口播总结（1）

### 2026-09-18 02:59:03

这套人工智能开发流程的关键，不是让人工智能尽快写代码，而是先让它帮助判断方向、明确设计，再把实现和验证逐步交给智能体。真正重要的，是在成本最低的时候发现问题，而不是代码写完以后才发现需求错了。

案例来自字幕转录和翻译应用 BaoCut。有用户提出，希望增加远程转录功能。具体场景是这样的：用户有两台电脑。电脑 A 配有英伟达显卡，算力强。电脑 B 只用于日常办公。用户希望在电脑 B 上操作 BaoCut，但把真正消耗算力的转录任务交给电脑 A。

这个需求听起来合理，但作者以前没有做过类似功能，也不确定技术上能不能实现。所以第一步不是写代码，而是做可行性分析。

可行性通常分成两个层面。一个是产品层面，也就是功能对用户有没有价值，是否符合应用的定位。另一个是技术层面，也就是能不能实现，成本是否可控。

这一步不能省。作者过去曾经为 BaoCut 做过一个本地文本模型，用来帮助拆分和对齐内容。前期分析时觉得没有问题，真正做完以后，才发现实际体验很差，最后只能砍掉。结果浪费了几天时间，也消耗了不少模型调用额度。这说明，即使做了可行性分析，也可能判断失误；但如果完全不分析，盲目开工，浪费往往更多。

远程转录这个需求，在产品价值和产品定位上都没有明显问题，所以作者把重点放在技术可行性上。他把原始需求交给 Claude Code，让它结合现有项目分析，并提出不同方案。

人工智能给出的方案里，有些不需要修改 BaoCut 的代码，但要求用户自己搭建语音识别服务器。技术上虽然能用，对普通用户却不够友好。还有一个方案对 Windows 支持不好。作者最终选择的方案是：用户只要安装 BaoCut，就能在高性能电脑上直接启动转录服务。与此同时，再附带提供一个基于网络协议的转录接口，方便其他程序调用。

这里最值得注意的是，人工智能负责调查和提出选项，但方案的取舍仍然由人完成。判断标准也不只是 “能不能做”，还包括用户是否容易使用，以及是否适合现有产品。

确定可行和初步方案以后，作者依然没有立刻写代码，而是先写设计文档。

这份文档不是单纯的技术说明。它同时包含需求、整体架构、界面和交互设计，以及当前项目的实际情况。这样做有几个作用。实现过程中，人工智能有明确参照，不容易偏离目标。未来维护时，也能知道当初为什么这样设计。更重要的是，在真正投入开发之前，人可以先检查方向是否正确。

作者也承认，这次自己有些偷懒。人工智能写完设计文档后，他觉得方案没有明显问题，就直接继续推进了。更稳妥的做法，仍然是认真检查文档，而不是把人工智能生成的方案当成最终答案。

接下来是原型设计。原型的价值，是用很低的成本验证需求，同时尽早确定界面和交互。作者的项目有专门的原型页面，每次新增或修改功能，都会先更新原型，而不是直接修改正式应用。

因为前面已经有设计文档，第一个原型很快就做出来了。初版把远程转录放进设置页面。用户可以启动服务，也可以发现网络中的其他转录节点。这个原型不是简单的线框草图，而是接近最终界面的高精度原型。也就是说，原型本身基本就是界面设计。

不过，第一版只是讨论的起点。作者看到原型后，连续给出反馈。最初，启动本机服务和访问其他节点被放在同一个布局里。作者认为，这是两个不同的使用场景，于是要求改成两个独立的标签页。他还增加了状态图标，让用户一眼就能判断服务正在运行，还是已经停止。

随后，作者又发现，把远程转录放在设置页面里，不方便随时查看服务状态。于是，他要求把相关入口移到主界面。经过多轮调整，界面和操作方式才基本稳定。

这一阶段体现了一个重要分工：人工智能可以快速生成原型，人则要根据真实使用场景不断纠偏。很多交互问题，单靠文字需求很难发现，看到可以操作的原型后，问题才会暴露出来。

等设计文档和高精度原型都准备好，写代码反而成了相对简单的一步。作者把文档交给 Claude Code，并通过目标指令让它开始实施。智能体按照文档中规划的里程碑逐项开发，还会自行截图，检查实现结果是否符合设计。

但智能体声称验证通过，不代表人可以完全相信。功能完成以后，作者仍然亲自运行了多遍，把发现的问题交回给智能体修改。经过几轮 “测试、反馈、修正”，功能才达到可用状态。

这次开发中，作者没有亲自审查代码。他把自己当成质量测试人员，主要进行黑盒测试。所谓黑盒测试，就是不深入检查内部代码，而是像用户一样操作软件，看输入、输出和整体体验是否正确。这种做法建立在他对所用智能体能力的信任上，并不意味着所有项目都可以省略代码审查。

整套流程最值得记住的，是把人工智能开发的重心从 “写代码” 前移到 “做判断”。先确认产品价值和技术可行性，再用设计文档固定方案，用原型低成本暴露交互问题，最后才让智能体实现。人工智能可以承担大量执行工作，但方向选择、体验判断和最终验收，仍然需要人负责。

## 深度解读（1）

### 2026-09-18 03:33:44

#### AI 把写代码变便宜后，开发瓶颈转向了 “尽早证伪”

这篇文章最有价值的不是推荐了某个模型或 Skill，而是用一个完整案例展示了：**当 Agent 已经能稳定完成实现，人的主要工作会从 “如何编码” 转向 “如何逐步消除不确定性”。**

作者为字幕工具 BaoCut 增加远程转录：办公电脑负责操作，带英伟达显卡的电脑提供算力。整个过程依次经过可行性分析、设计文档、高保真原型、代码实现和人工验收。表面看是开发流程，实质上是一条逐层收窄解空间的链路。

##### 文档和原型不再只是沟通材料，而是 Agent 的控制界面

过去，小功能写设计文档、做高保真原型，成本可能高于直接编码。Agent 改变了这笔账：文档和原型的生产成本下降，却能同时承担三项作用 —— 迫使人明确需求、约束 Agent 的实现空间、为后续修改保留上下文。

其中最典型的不是 AI 自动生成了界面，而是作者连续做出的人工判断：把 “开启服务” 和 “访问节点” 拆成两个 Tab，用图标表达服务状态，再把入口从设置页移到主界面。**Agent 擅长生成候选方案，人仍负责识别场景差异、信息优先级和操作是否顺手。**

这也意味着，未来产品经理交付给开发系统的核心资产，可能不再只是 PRD，而是一组彼此一致、可被执行和验证的材料：需求边界、架构约束、界面状态、验收标准。谁能把模糊判断转化为这些中间产物，谁就更能稳定驾驭 Agent。

##### “先分析再实现” 还不够，关键是设计最便宜的证伪实验

文章也无意间暴露了 AI 可行性分析的边界。作者此前曾让 AI 判断本地文本模型方案可行，实际完成后体验却很差，最终砍掉。原因是 “技术上能运行” 不等于 “产品上可用”：模型可以判断依赖、接口和架构，却很难仅靠代码仓库预测准确率、延迟以及用户对结果的容忍度。

因此，更稳妥的流程不是让 AI 写一份更长的分析，而是把可行性拆成不同层次：

1. 静态分析回答 “能不能接起来、成本大致多少”；
2. 技术 Spike 回答 “关键链路是否跑得通”；
3. 真实样本测试回答 “效果是否值得使用”；
4. 原型回答 “交互是否清楚”，但不能单独证明需求成立。

**可行性分析的终点不应是一个肯定结论，而应是找到最可能推翻方案的变量，并尽早测试它。**

##### “不 Review 代码” 只适用于风险边界明确的场景

作者把自己当作 QA，只做黑盒测试，这对个人工具、小范围功能或易回滚项目可能成立；但远程服务恰好涉及端口暴露、鉴权、文件传输、并发和失败恢复，仅凭界面跑通无法覆盖这些风险。若进入多人使用、敏感数据或商业交付环境，仍需自动化测试、安全检查、日志监控和针对关键模块的代码审查。

所以，这套流程真正值得复制的并非 “以后不用看代码”，而是：**根据故障代价决定验证深度，把人的注意力放在高风险假设上。**衡量 AI 开发流程好坏，也不该只看代码生成得多快，而要看它能否让错误更早、更便宜地暴露。

## 深度解读-口播（1）

### 2026-09-30 12:10:47

用人工智能开发功能，最关键的未必是怎么让它写代码，而是先把需求、方案和交互想清楚。这位开发者给自己的字幕转录翻译应用 BaoCut 增加远程转录功能，就展示了这样一条流程：先降低不确定性，再交给人工智能实现，最后由人亲自验证。

这个需求来自一位用户。用户有两台电脑：一台配有英伟达显卡，性能强；另一台是日常使用的办公电脑。用户希望在办公电脑上操作 BaoCut，却把最消耗算力的语音转录工作，交给高性能电脑完成。

需求听起来合理，但作者没有马上写代码。因为“用户想要”，并不等于“值得做”，更不等于“做得出来”。

他把可行性分成两个层面。产品层面，要看功能有没有价值，是否符合应用的定位。技术层面，要看能否实现，以及实现成本是否可控。

在这个案例里，产品价值比较明确，所以作者主要让人工智能分析技术可行性。他把原始需求交给编程助手 Claude Code，让它结合现有项目，判断是否可行，并提出方案。

这里重要的不是得到一句“可以做”，而是比较不同方案的代价。

有些方案不需要修改应用代码，但用户得自己搭建语音识别服务器。对开发者省事，对用户却不友好。另一个方案对 Windows 用户不够友好。作者最终选择了这样一条路线：用户只要安装了 BaoCut，就能直接启动自己的转录服务，让另一台电脑来调用。

他还从其他方案里挑出一个值得保留的点：顺便提供一个通过网络请求调用转录功能的接口。

也就是说，人工智能负责提供分析和选项，人负责判断什么最适合产品和用户，而不是原封不动地接受某一整套方案。

不过，可行性分析也不是保证书。作者此前尝试过用本地文本模型帮助拆分和对齐内容。分析时觉得可行，做出来之后，实际体验却很糟糕，最后还是砍掉了。那次尝试花了几天时间，也消耗了不少模型调用量。这说明，前期分析能减少盲目投入，但不能替代真实体验。

确定初步方案后，作者仍然没有直接进入代码实现，而是先让人工智能写设计文档。

这份文档不是单纯的技术说明。它把产品需求、架构方案和界面设计放在一起，回答几个相互关联的问题：到底要做什么，现有项目有哪些基础，功能应该怎么组织，用户又该怎么操作。

文档的作用，是把讨论过的想法变成可以反复参照的依据。人工智能实施时有据可循，未来维护时也能找到背景。更重要的是，人可以在这里确认方向是否正确。

作者也承认，这一步他偷了懒，没有仔细复核文档，主要因为此前的方案看起来没什么大问题，而且他比较信任所用的模型。他仍然认为，有条件最好看一遍。

接下来，真正帮助他发现交互问题的，是原型设计。

作者的应用有一个配套的原型页面。每次新增或修改功能，他都会先更新这个页面。这里的原型不是粗略的线框图，而是接近最终界面的高精度原型，可以同时验证布局、视觉效果和操作方式。

第一版原型把远程转录放在设置页面里。用户可以开启本机服务，也可以发现其他电脑上的服务节点。乍看已经像一个完整功能，但实际看过界面之后，作者发现，这里面混着两个不同的使用场景。

一个场景是：让这台电脑提供转录服务。另一个场景是：让这台电脑连接别的电脑，借用对方的算力。

于是，他让人工智能把两种操作拆成不同的选项卡，又加上状态图标，让用户能清楚看出服务正在运行，还是已经停止。

调整到这里，他又发现一个问题：如果入口藏在设置页面里，平时就不方便查看服务状态。于是，他把这部分功能挪到了主界面。

这个过程体现了原型的价值。文档可以写清楚“需要显示状态”，但只有把界面摆出来，人才更容易发现“这个状态放在哪里才方便”。在原型上修改布局和入口，比写完代码后再返工，成本更低。

等设计文档和界面原型都准备好，作者才让编程助手正式实施。他把文档一起交过去，让助手按照规划好的阶段目标逐个完成。助手还会自行截图，检查实现结果。

在作者看来，有了清楚的需求、方案和原型，代码实现对如今的人工智能编程助手来说，已经相对容易。前面的工作，正是在减少实现阶段需要临时猜测的东西。

但助手说自己验证过，并不代表人就可以放心结束。

作者接着亲自运行功能，把发现的问题反馈给助手，再让它修改。这样反复几轮，最终功能才达到他认为基本可用的程度。

这里还要分清两种检查。作者没有审查代码，而是把自己当成质量测试人员，只做了黑盒测试。所谓黑盒测试，就是不看内部代码，主要通过操作应用、观察结果，判断功能是否符合预期。这是作者在这个案例中的实际做法，不是他同时完成了代码质量审查。

这套流程最值得记住的，是把人工智能写代码放在了后面：先判断需求和方案，再用文档与原型把方向说清楚。人工智能可以承担大量分析、设计和实现工作，但方案取舍、交互反馈和最终使用体验，仍然需要人来判断。
