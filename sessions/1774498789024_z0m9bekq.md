### Building CLIs for agents

If you've ever watched an agent try to use a CLI, you've seen it get stuck on an interactive prompt it can't answer, or parse a help page with no examples. Most CLIs were built assuming a human is at the keyboard. Here are some things I've found that make them work better for agents:

Make it non-interactive. If your CLI drops into a prompt mid-execution, an agent is stuck. It can't press arrow keys or type "y" at the right moment. Every input should be passable as a flag. Keep interactive mode as a fallback when flags are missing, not the primary path.

```bash
# this blocks an agent
$ mycli deploy
? Which environment? (use arrow keys)

# this works
$ mycli deploy --env staging
```

Don't dump all your docs upfront. An agent runs mycli, sees subcommands, picks one, runs mycli deploy --help, gets what it needs. No wasted context on commands it won't use. Let it discover things as it goes.

Make --help actually useful. Every subcommand gets a --help, and every --help includes examples. The examples do most of the work. An agent pattern-matches off mycli deploy --env staging --tag v1.2.3 faster than it reads a description.

```text
$ mycli deploy --help
Options:
  --env     Target environment (staging, production)
  --tag     Image tag (default: latest)
  --force   Skip confirmation

Examples:
  mycli deploy --env staging
  mycli deploy --env production --tag v1.2.3
  mycli deploy --env staging --force
```

Accept flags and stdin for everything. Agents think in pipelines. They want to chain commands and pipe output between tools. Don't require positional args in weird orders or fall back to interactive prompts for missing values.

```bash
cat config.json | mycli config import --stdin
mycli deploy --env staging --tag $(mycli build --output tag-only)
```

Fail fast with actionable errors. If a required flag is missing, don't hang. Error immediately and show the correct invocation. Agents are good at self-correcting when you give them something to work with.

```bash
Error: No image tag specified.
  mycli deploy --env staging --tag <image-tag>
  Available tags: mycli build list --output tags
```

Make commands idempotent. Agents retry constantly. Network timeouts, context getting lost mid-task. Running the same deploy twice should return "already deployed, no-op", not create a duplicate.

Add --dry-run for destructive actions. Agents should be able to preview what a deploy or deletion would do before committing. Let them validate the plan, then run it for real.

```bash
$ mycli deploy --env production --tag v1.2.3 --dry-run
Would deploy v1.2.3 to production
  - Stop 3 running instances
  - Pull image registry.io/app:v1.2.3
  - Start 3 new instances
No changes made.

$ mycli deploy --env production --tag v1.2.3
✓ Deployed v1.2.3 to production
```

\--yes / --force to skip confirmations. Humans get "are you sure?" and agents pass --yes to bypass it. Make the safe path the default but allow bypassing.

Predictable command structure. If an agent learns \`mycli service list\`, it should be able to guess \`mycli deploy list\` and \`mycli config list\`. Pick a pattern (resource + verb) and use it everywhere.

Return data on success. Show the deploy ID and the URL. Emojis are cute, but not really needed.

```bash
deployed v1.2.3 to staging
url: https://staging.myapp.com
deploy_id: dep_abc123
duration: 34s
```

If you're building CLIs that agents will use, these patterns save a lot of debugging time. Most of the work is just making explicit what humans figured out implicitly!

I bet there are many more things that I've forgotten, let me know!

## 通俗精炼（1）

### 2026-03-26 04:16:10

#### 面向 AI Agent 的 CLI 设计要点

##### 核心结论

大多数 CLI 默认是给“人”用的，不是给 AI Agent 用的。  
如果希望 Agent 能稳定调用 CLI，关键不是让功能更复杂，而是把原本靠人类“默认理解”的操作，变成**明确、可传参、可预测、可重试**的接口。

##### 一、最重要的设计原则

###### 1. 默认非交互
Agent 最怕执行中突然弹出交互式问题，比如选择环境、确认操作等。  
最佳做法是：**所有输入都能通过 flag 传入**，交互模式只作为兜底，而不是主路径。

###### 2. 帮助信息要“能直接照着用”
`--help` 不能只有参数说明，还要有**真实示例**。  
因为 Agent 往往不是逐字阅读文档，而是通过示例快速模仿正确命令格式。

###### 3. 支持 flag 和 stdin
Agent 天然适合用管道串联工具。  
因此 CLI 应支持：
- 通过 flag 显式传参
- 通过 stdin 接收输入
- 避免奇怪的参数顺序和隐式输入方式

##### 二、让 Agent 更容易自我修正

###### 1. 快速失败，报错可执行
缺少参数时，不要卡住等待输入；要**立即报错**，并告诉它正确命令应该怎么写。  
这样 Agent 才能根据错误信息自动修正并重试。

###### 2. 命令要幂等
Agent 会频繁重试任务。  
如果重复执行同一个命令会产生重复部署、重复创建资源，就很容易出问题。  
理想状态是：重复执行时返回“已完成，无需重复处理”。

###### 3. 高风险操作支持 dry-run
像部署、删除这类操作，最好提供 `--dry-run`。  
这样 Agent 可以先预览结果，再正式执行，降低误操作风险。

##### 三、提升可预测性与可组合性

###### 1. 提供 `--yes` / `--force`
对人类友好的确认步骤，对 Agent 往往是阻碍。  
应保留安全确认默认值，但提供跳过确认的显式参数，方便自动化执行。

###### 2. 命令结构要统一
CLI 的命名和层级要有一致性。  
如果 Agent 学会了 `service list`，就应该能推测出 `config list`、`deploy list`。  
本质上是让命令体系更“可猜”。

###### 3. 成功结果返回结构化信息
执行成功后，不要只输出“成功了”。  
更好的做法是返回关键结果，如：
- 部署 ID
- URL
- 耗时

这能让 Agent 在下一步继续使用这些信息。

##### 四、这篇内容的本质启发

###### 从“给人用”转向“给机器也能顺畅用”
作者的核心观点是：  
**优秀的 Agent CLI，不是新增很多 AI 功能，而是把 CLI 做得更显式、更标准、更自动化友好。**

换句话说，真正重要的是：
- 不要依赖人类临场判断
- 不要依赖模糊上下文
- 不要让执行结果不可预测

##### 五、补充观点

###### 评论区的两个延伸方向
热门回复里还补充了两个值得关注的问题：
- **输出推荐下一步命令**：帮助 Agent 发现后续可执行动作
- **认证设计（auth）**：这是云端 Agent 使用 CLI 时的一个大难点，未来可能需要更好的模式支持

##### 一句话总结

**面向 Agent 设计 CLI，本质就是把“人类心照不宣的使用习惯”，改造成“机器可直接理解和执行的明确接口”。**

## 结构化（1）

### 2026-03-26 07:24:49

#### 主旨概括

这篇文章的核心观点是：**大多数 CLI 是为“人在键盘前操作”设计的，但如果希望它被 AI Agent 顺畅使用，就必须改成“对机器更友好”的方式**。作者总结了一套实用原则，重点是减少交互、增强可预测性、提供可执行示例，并让错误与输出都足够清晰。

#### 按原文逻辑总结

##### 1. 先解决 Agent 最容易卡住的问题：避免交互式设计

- 传统 CLI 常在执行中弹出交互式提示，这对 Agent 很不友好，因为它无法像人一样灵活地按方向键、输入 `y` 或临场判断。
- 因此，**所有必要输入都应支持通过 flag 传入**，交互模式只应作为“缺少参数时的兜底方案”，而不是默认路径。
- 原文示例：
  - 不适合 Agent：
    ```bash
    mycli deploy
    ? Which environment? (use arrow keys)
    ```
  - 更适合 Agent：
    ```bash
    mycli deploy --env staging
    ```

##### 2. 文档不要一次性灌太多，要支持“按需发现”

- Agent 使用 CLI 时，通常是先运行主命令查看子命令，再进入具体子命令看 `--help`。
- 所以 CLI 的帮助系统应支持**分层探索**，而不是一开始就输出大量无关信息，浪费上下文。
- 关键点是：**让 Agent 可以逐步发现它当前真正需要的信息**。

##### 3. `--help` 不仅要有说明，还必须有示例

- 作者强调：**每个子命令都应该有 `--help`，而且每个帮助页都要包含示例**。
- 因为 Agent 往往不是逐字阅读长说明，而是通过模式匹配快速学习调用方式。
- 原文举例中，`mycli deploy --help` 包含：
  - 参数说明：
    - `--env`：目标环境，如 `staging`、`production`
    - `--tag`：镜像标签，默认值是 `latest`
    - `--force`：跳过确认
  - 示例命令：
    ```bash
    mycli deploy --env staging
    mycli deploy --env production --tag v1.2.3
    mycli deploy --env staging --force
    ```
- 这里的重要数据和案例是：**环境示例包括 `staging`、`production`，版本标签示例为 `v1.2.3`**。

##### 4. 所有功能都应支持 flag 和 stdin，方便流水线调用

- Agent 很擅长把多个命令串起来使用，因此 CLI 应该适配这种“管道式思维”。
- 不要强依赖奇怪顺序的位置参数，也不要在缺值时退回交互提示。
- 原文示例：
  - 从标准输入导入配置：
    ```bash
    cat config.json | mycli config import --stdin
    ```
  - 把一个命令的输出作为另一个命令的参数：
    ```bash
    mycli deploy --env staging --tag $(mycli build --output tag-only)
    ```
- 这说明好的 CLI 应该天然适合自动化编排，而不是只适合人工单步操作。

##### 5. 出错时要快速失败，并给出可执行的修正方式

- 如果缺少必填参数，CLI 不应该卡住等待，而应**立即报错**。
- 更重要的是，错误信息不能只说“错了”，还要告诉 Agent **正确的命令格式是什么**，以及接下来可以怎么补救。
- 原文示例：
  ```bash
  Error: No image tag specified.
  mycli deploy --env staging --tag <image-tag>
  Available tags: mycli build list --output tags
  ```
- 这类错误提示的价值在于：
  - 明确指出缺失项：`image tag`
  - 给出正确调用模板：`mycli deploy --env staging --tag &lt;image-tag>`
  - 提供下一步命令：`mycli build list --output tags`
- 这能让 Agent 更容易自我修正。

##### 6. 命令应具备幂等性，因为 Agent 会频繁重试

- Agent 在执行任务时，经常因为网络超时、上下文中断等原因重复发起同一个命令。
- 因此，CLI 的关键操作要尽量做到**幂等**：重复执行不会产生额外副作用。
- 原文强调：同一次部署执行两遍，理想结果应是“已经部署，无需操作（no-op）”，而不是重复创建资源。
- 这能显著减少自动化场景下的异常和脏数据。

##### 7. 危险操作要支持 `--dry-run` 预演

- 对部署、删除这类有风险的操作，CLI 应提供 `--dry-run`，让 Agent 先验证计划再正式执行。
- 原文示例：
  ```bash
  mycli deploy --env production --tag v1.2.3 --dry-run
  ```
  输出会说明将执行哪些步骤，例如：
  - 向 `production` 部署 `v1.2.3`
  - 停止 `3` 个运行中的实例
  - 拉取镜像 `registry.io/app:v1.2.3`
  - 启动 `3` 个新实例
  - 最后明确说明：`No changes made.`
- 正式执行后则返回：
  ```bash
  ✓ Deployed v1.2.3 to production
  ```
- 这里保留了重要案例与数据：**环境是 `production`，版本是 `v1.2.3`，涉及停止和启动各 `3` 个实例**。

##### 8. 保持安全默认值，同时允许用 `--yes` / `--force` 跳过确认

- 对人类用户来说，确认提示能降低误操作风险；但对 Agent 来说，这种确认常常会阻塞流程。
- 所以更合理的方式是：
  - 默认保留安全确认
  - 同时提供 `--yes` 或 `--force` 让 Agent 显式跳过
- 这实现了“**默认安全，必要时可自动化绕过**”的平衡。

##### 9. 命令结构要可预测，方便 Agent 类推

- 作者建议使用统一的命令组织模式，例如“资源 + 动作（resource + verb）”。
- 如果 Agent 学会了：
  ```bash
  mycli service list
  ```
  那它就应该能自然猜出：
  ```bash
  mycli deploy list
  mycli config list
  ```
- 可预测的命令结构能降低学习成本，也能提升 Agent 自主探索能力。

##### 10. 成功输出要返回有用数据，而不只是“看起来很可爱”

- 成功执行后，CLI 不应只输出一些装饰性内容或 emoji，而应返回**可继续使用的关键信息**。
- 原文示例输出：
  ```bash
  deployed v1.2.3 to staging
  url: https://staging.myapp.com
  deploy_id: dep_abc123
  duration: 34s
  ```
- 这里的重要数据包括：
  - 部署版本：`v1.2.3`
  - 环境：`staging`
  - 地址：`https://staging.myapp.com`
  - 部署 ID：`dep_abc123`
  - 耗时：`34s`
- 这些输出非常适合后续自动化流程继续读取和使用。

##### 11. 作者的总结与评论区补充

- 作者最后总结：如果 CLI 面向 Agent，这些设计模式能省下大量调试时间。
- 本质上，很多工作只是把“人类默认知道但没写出来的规则”变得更明确。
- 热门回复中还有两点补充很值得注意：
  - 一位评论者认为，CLI 输出中还可以加入**相关命令或推荐的下一步命令**，帮助 Agent 继续探索。
  - 另一点是：**认证（auth）是云端 Agent 使用 CLI 时的一个明显难题**。
- 作者回应说：在云环境中，认证这件事是 **MCP 很有优势的应用场景之一**。

#### 精炼结论

- 这篇文章本质上是在讲：**为 Agent 设计 CLI，就是把“隐含规则”全部显式化**。
- 最关键的改进方向包括：
  - 非交互优先
  - `--help` 可分层查看且附带示例
  - 支持 flag、stdin 和管道
  - 错误信息可执行
  - 幂等、可预演、可跳过确认
  - 命令结构统一
  - 成功输出包含机器可用的数据
- 如果做到这些，CLI 不仅更适合 Agent，也通常会让人类用户的自动化体验更好。
