## 分析要点

- **核心高价值点**：将 Agent 与 Harness 区分开：Agent 是用户感知到的行为，Harness 才是产生智能体行为的底层工程系统。
- **留存建议**：长期保留，适合作为构建生产级 AI Agent 的架构参考（系统梳理了 Agent Harness 的核心组件、设计取舍和工程实践，具备较高复用价值）

**知识要点**

- 生产级 Agent Harness 包含编排循环、工具、记忆、上下文管理、提示词构建、输出解析、状态管理、错误处理、护栏、验证循环和子智能体编排等组件
- 上下文工程的目标是用最小、最高信号密度的 Token 集合提升任务完成概率
- 验证循环是区分玩具 Demo 和生产级智能体的关键，可通过规则测试、视觉反馈或 LLM-as-judge 实现
- 工具、权限、安全执行和错误恢复应由 Harness 控制，而不是完全交给模型自由决定
- 随着模型能力提升，Harness 可能变薄，但仍需要负责状态、执行、验证和上下文管理

**行动项**

- 对现有 Agent 项目按 12 个 Harness 组件做一次架构盘点，找出缺失环节
- 为长任务 Agent 增加上下文压缩、观察掩码或即时检索机制
- 为关键工具调用增加参数校验、权限检查、沙箱执行和错误反馈
- 在生产 Agent 中设计验证循环，例如测试、代码检查、截图检查或独立评审 Agent
- 优先优化单智能体 Harness，再考虑引入多智能体编排

本文将深入探讨 Anthropic、OpenAI、Perplexity 和 LangChain 究竟在开发什么。我们将聊聊编排循环、工具、记忆、上下文管理，以及那些将“无状态”的大语言模型（LLM）转变为全能智能体（Agent）的底层机制。

你可能已经开发过聊天机器人，甚至可能用一些工具搭建了一个 ReAct 循环 （ReAct：Reason + Act，一种让模型在行动前先进行推理的模式）。跑 Demo 的时候看着挺好，但一旦投入生产环境，系统就会开始掉链子：模型会忘记三步前做了什么，工具调用悄悄报错，上下文窗口（Context Window）里塞满了毫无意义的垃圾信息。

问题其实并不在模型本身，而在模型外围的基础设施。

LangChain 证明了这一点：他们仅仅通过改变包裹大语言模型的底层架构——模型没变，参数没变——就让系统在 TerminalBench 2.0 （一个衡量 AI 智能体处理命令行任务能力的权威基准测试） 上的排名从 30 名开外飙升到了第 5 名。另一项研究则通过让大语言模型自己去优化这套架构，实现了 76.4% 的通过率，甚至超过了人类精心设计的系统。

现在，这套基础设施有了一个正式的名字：AI Agent Harness。

虽然这个术语在 2026 年初才正式确立，但其核心理念早已存在。Harness是包裹在大语言模型之外的完整软件架构：它包括编排循环、工具、记忆、上下文管理、状态持久化、错误处理和护栏（Guardrails）。Anthropic 在其 Claude Code 文档中直截了当地指出：SDK（软件开发工具包）就是“驱动 Claude Code 的 Agent Harness”。OpenAI 的 Codex 团队也使用了同样的说法，明确将“智能体”和“Harness”等同，指代那些让大语言模型真正发挥作用的非模型架构。

我非常喜欢 LangChain 的 Vivek Trivedy 给出的定义公式：“如果你不是模型本身，那你就是 Harness。”

这里有一个经常让人搞混的区别：“AI 智能体”（Agent）是用户感知到的行为体现，它是一个有目标、会用工具、能自我纠错的实体；而\*\*“Harness”\*\*则是产生这种行为的背后机器。当有人说“我开发了一个智能体”时，他真正的意思是“我开发了一套 Harness，并把它接入了模型”。

![Image](https://pbs.twimg.com/media/HH_X7DiWQAASlWi?format=jpg&name=large)

Beren Millidge 在其 2023 年的博文中做了一个精准的类比：原生大语言模型就像一个没有内存、没有硬盘、也没有输入输出设备的 CPU。此时，上下文窗口充当了内存（快但容量有限），外部数据库扮演了硬盘（大但速度慢），工具集成则是设备驱动程序。而Harness，就是那个操作系统。正如 Millidge 所写：“我们重新发明了冯·诺依曼架构（Von Neumann architecture）”，因为这是任何计算系统最自然的抽象方式。

围绕模型，工程化可以分为三个同心圆层次：

- 提示词工程 (Prompt engineering)：精心设计模型接收到的指令。
- 上下文工程 (Context engineering)：管理模型在什么时间点能看到什么内容。
- Harness 工程 (Harness engineering)：涵盖了上述两者，再加上整个应用架构：包括工具编排、状态持久化、错误恢复、验证循环、安全执行以及生命周期管理。

Harness 不仅仅是一个包裹提示词的套壳（AI Wrapper），它是让智能体能够自主行动的完整系统。

综合 Anthropic、OpenAI、LangChain 以及广大从业者的实践经验，一个生产级的 Agent Harness 由 12 个不同的组件构成。让我们逐一拆解。

![Image](https://pbs.twimg.com/media/HH_YZYdWkAA-BtD?format=jpg&name=large)

#### 1\. 编排循环（编排循环）

这是系统的“心脏”。它实现了“思考 - 行动 - 观察”（Thought-Action-Observation，简称 TAO）循环，也被称为 ReAct 循环。这个循环不停运转：整合提示词 -&gt; 调用大语言模型 -&gt; 解析输出 -&gt; 执行工具调用 -&gt; 反馈结果 -&gt; 重复，直到任务完成。

从技术实现上看，它通常只是一个 while 循环。但复杂的地方不在于循环本身，而在于循环所要处理的各种状态和逻辑。Anthropic 将他们的运行时描述为一个“笨循环”，所有的智慧都存在于模型之中，Harness 只负责管理回合的切换。

#### 2\. 工具 (Tools)

工具是智能体的“双手”。它们被定义为某种结构化模式（名称、描述、参数类型），并注入到模型的上下文中，让模型知道哪些工具可用。工具层负责注册、格式校验、参数提取、在\*\*沙箱（Sandbox）\*\*环境执行、结果捕获，并最终将结果格式化为模型可读的“观察结果”。

Claude Code 提供了六大类工具：文件操作、搜索、执行、网页访问、代码分析和子智能体创建。OpenAI 的 Agents SDK 则支持函数工具（通过

[@function\_tool](https://x.com/@function_tool) 定义）、托管工具（如网页搜索、代码解释器、文件搜索）以及 MCP （Model Context Protocol，一种开放的工具接入标准） 服务器工具。

#### 3\. 记忆 (Memory)

记忆在不同的时间尺度上运作。短期记忆是单次会话中的对话历史。长期记忆则跨越多个会话持久存在：Anthropic 使用项目文件和自动生成的 memory.md 文件；LangGraph 使用按命名空间组织的 JSON 存储；OpenAI 则支持由 SQLite 或 Redis 驱动的会话存储。

Claude Code 实现了三层记忆架构：一个轻量级索引（每条约 150 字符，始终加载）、按需调用的详细主题文件，以及仅通过搜索访问的原始对话记录。一个核心设计原则是：智能体将自己的记忆视为一种“提示”，在行动前必须根据实际状态进行验证。

#### 4\. 上下文管理 (Context Management)

这是许多智能体容易暗中翻车的地方。核心问题在于上下文腐烂：当关键信息处于窗口中间位置时，模型表现会下降 30% 以上（这就是斯坦福大学发现的“迷失在中间”现象）。即便是支持百万级 Token （Token：模型处理文本的最小单位，大致相当于单词或汉字的部分） 的窗口，随着上下文的增长，指令遵循能力也会退化。

生产环境的应对策略包括：

- 压缩 (Compaction)：在接近限制时总结对话历史（Claude Code 会保留架构决策和未修复的 Bug，同时丢弃冗余的工具输出）。
- 观察掩码 (Observation masking)：隐藏旧的工具输出，但保留工具调用的记录。
- 即时检索 (Just-in-time retrieval)：只保留轻量级标识符，动态加载数据（Claude Code 倾向于使用 grep 或 head 命令，而不是加载整个文件）。
- 子智能体委托：让每个子智能体进行深度探索，但仅返回 1000 到 2000 Token 的浓缩摘要。

Anthropic 的上下文工程指南指出，目标是：找到能最大化达成目标概率的、信号最强的最小 Token 集合。

#### 5\. 提示词构建 (Prompt Construction)

这决定了模型在每一步具体能看到什么。它是层级化的：系统提示词、工具定义、记忆文件、对话历史，以及当前的用户消息。

OpenAI 的 Codex 使用严格的优先级栈：服务器控制的系统消息（最高优先级）、工具定义、开发者指令、用户指令，最后才是对话历史。

#### 6\. 输出解析 (Output Parsing)

现代 Harness 依赖于原生工具调用，即模型返回结构化的 tool\_calls 对象，而不是需要费力解析的自由文本。Harness 会检查：是否有工具调用？如果有，执行并继续循环；如果没有，那当前的输出就是最终答案。

对于结构化输出，OpenAI 和 LangChain 都支持通过 Pydantic 模型 （Python 中用于数据校验和格式化的库） 进行模式约束。

#### 7\. 状态管理 (State Management)

LangGraph 将状态模拟为在图形节点中流动的类型化字典。系统会在关键步骤进行“存档”（Checkpointing），这样即使中断也能恢复，甚至可以进行“时间旅行”式的调试。OpenAI 则提供了四种策略：应用内存、SDK 会话、服务器端 API 或轻量级的响应 ID 链。Claude Code 采用了不同的思路：将 Git 提交作为存档点，将进度文件作为结构化的草稿纸。

#### 8\. 错误处理 (Error Handling)

为什么这很重要？一个包含 10 个步骤的过程，即使每一步的成功率高达 99%，最终全流程的成功率也只有约 90.4%。错误是会滚雪球的。

LangGraph 将错误分为四类：临时性的（带延迟的重试）、模型可恢复的（将错误作为工具消息返回，让模型自己调整）、用户可修复的（暂停等待人类干预）以及意外错误（上报调试）。

#### 9\. 护栏与安全 (Guardrails and Safety)

OpenAI 的 SDK 实现了三个层级：输入护栏（在第一个智能体运行时检查）、输出护栏（检查最终结果）以及工具护栏（每次调用工具前检查）。一旦触发“绊网”（Tripwire）机制，智能体将立即停止。

Anthropic 在架构上将“权限执行”与“模型推理”分离。模型决定想做什么，但 Harness 决定允许做什么。

#### 10\. 验证循环 (Verification Loops)

这是区分“玩具演示”和“生产级智能体”的关键。Anthropic 推荐三种方法：基于规则的反馈（测试、代码检查）、视觉反馈（通过 Playwright 截取 UI 截图）以及以大语言模型为裁判 (LLM-as-judge)（由另一个子智能体评估输出）。

Claude Code 的创造者 Boris Cherny 指出，让模型能够验证自己的工作，能让产出质量提升 2 到 3 倍。

#### 11\. 子智能体编排 (Subagent Orchestration)

Claude Code 支持三种模式：克隆 (Fork)（复制父级上下文）、队友 (Teammate)（通过文件邮箱通信的独立窗口）和 工作树 (Worktree)（独立的 Git 分支）。OpenAI 则支持将智能体作为工具（专家处理特定子任务）或移交（专家接管后续控制权）。

既然了解了组件，让我们看看它们在一次循环中是如何协同工作的。

![Image](https://pbs.twimg.com/media/HH_YfilX0AAFR4G?format=jpg&name=large)

1. 第一步（提示词组装）：Harness 构建完整的输入信息。
2. 第二步（模型推理）：组装好的内容发送给模型 API，模型生成 Token：可能是文本，也可能是工具调用请求。
3. 第三步（输出分类）：如果没有工具调用，循环结束；如果有，进入执行阶段。
4. 第四步（工具执行）：Harness 校验参数、检查权限，在沙箱中运行并捕获结果。
5. 第五步（结果打包）：将结果格式化为模型可读的消息，捕获错误以便模型自愈。
6. 第六步（上下文更新）：将结果追加到历史记录，必要时触发压缩。
7. 第七步（循环）：返回第一步，直到满足退出条件。

![Image](https://pbs.twimg.com/media/HH_YlPbWgAAyPU9?format=jpg&name=large)

- Anthropic (Claude Agent SDK)：通过一个简单的 query() 函数暴露 Harness，运行时是一个“笨循环”，智慧全在模型里。
- OpenAI (Agents SDK)：采用“代码优先”策略，工作流逻辑直接用 Python 表达，而不是复杂的图形语言。
- LangGraph：将 Harness 建模为显式的状态图，强调对流程的精细控制。
- CrewAI：实现了基于角色的多智能体协作，由“流程层”管理确定性的骨干逻辑。
- AutoGen：由微软开发，支持多种编排模式，如顺序执行、群聊、移交和动态任务管理。

“脚手架”这个比喻并非装饰，而是极其精准的。建筑脚手架是临时性的基础设施，让工人们能触及原本够不到的高度。脚手架本身不盖房子，但没有它，工人就上不去高层。

![Image](https://pbs.twimg.com/media/HH_YrOyXUAAOFUR?format=jpg&name=large)

关键洞察在于：房子盖好后，脚手架是要拆除的。 随着模型能力的提升，Harness 的复杂程度应该逐渐降低。

这就是协同进化原则：现在的模型在训练时，就已经考虑了 Harness 的存在。如果你的 Harness 设计得好，当模型升级时，你不需要增加复杂度，性能就会自动提升。

![Image](https://pbs.twimg.com/media/HH_Yw1OWAAAphY9?format=jpg&name=large)

每个 Harness 的架构师都面临这七个选择：

![Image](https://pbs.twimg.com/media/HH_Y2gpWcAAl2uX?format=jpg&name=large)

1. 单智能体 vs. 多智能体：官方建议：先充分挖掘单智能体的潜力。多智能体会带来额外的开销和信息损耗。
2. ReAct vs. 先规划后执行：ReAct 灵活但成本高；“先规划后执行”速度更快。
3. 上下文管理策略：是总结对话，还是动态加载？
4. 验证循环设计：是用硬性的代码测试，还是用另一个 LLM 来打分？
5. 权限与安全架构：是追求速度自动批准，还是追求安全步步确认？
6. 工具范围管理：工具不是越多越好。暴露当前步骤所需的最小工具集往往效果最佳。
7. Harness 的厚度：多少逻辑写死在系统里，多少逻辑留给模型发挥？

两个使用完全相同模型的智能体，性能可能天差地别，原因就在于 Harness 的设计。TerminalBench 的证据已经非常明确：仅仅改变 Harness，就能让排名变动 20 多位。

Harness 不是一个已经解决的问题，也不是一个通用的商品层。它是硬核工程能力的体现：如何将上下文视为稀缺资源进行管理？如何设计验证循环以防止错误累积？如何构建不产生幻觉的记忆系统？

随着模型越来越强，Harness 会变薄，但它永远不会消失。即便最强大的模型，也需要系统来管理窗口、执行代码、保存状态并验证工作。

下次当你的智能体表现不佳时，别光顾着抱怨模型，去检查一下你的Harness吧。

## 通俗精炼（1）

### 2026-05-12 04:28:29

#### 深度拆解：AI Agent Harness 的构造

##### 一句话总结

AI Agent 的能力不只取决于大模型本身，更取决于包裹在模型外部的工程系统——**Agent Harness**。它负责工具调用、记忆、上下文管理、状态持久化、错误恢复、安全控制和验证循环，是让“无状态 LLM”变成“可执行任务智能体”的关键基础设施。

---

##### 核心概念：什么是 Agent Harness？

**Agent 是用户看到的智能行为，Harness 是背后的运行机器。**

如果把大模型看作一个没有内存、硬盘和外设的 CPU，那么：

- 上下文窗口 = 内存
- 外部数据库 = 硬盘
- 工具调用 = 设备驱动
- Harness = 操作系统

所以，所谓“开发一个 AI Agent”，本质上是：**设计一套 Harness，并把它接到模型上。**

---

##### 为什么 Harness 很重要？

很多 AI Agent Demo 看起来能跑，但一到生产环境就容易失败：

- 模型忘记前几步做过什么
- 工具调用失败却没有处理
- 上下文窗口被无效信息塞满
- 错误一步步累积
- 输出无法验证

问题往往不在模型，而在模型外围的工程架构。

LangChain 的案例显示：**模型不变，仅优化 Harness，就能让 Agent 在基准测试中的排名大幅提升。**

---

##### Harness 的三层工程关系

围绕大模型的工程能力可以分成三层：

1. **Prompt Engineering**
   - 设计模型看到的指令。

2. **Context Engineering**
   - 管理模型在什么时候看到什么信息。

3. **Harness Engineering**
   - 不仅包括提示词和上下文，还包括工具、状态、记忆、错误处理、安全、验证和生命周期管理。

**Harness 不是简单的 AI Wrapper，而是完整的智能体运行系统。**

---

##### 生产级 Agent Harness 的 12 个核心组件

###### 1. 编排循环：Agent 的心脏

核心是经典的 ReAct / TAO 循环：

> 思考 → 行动 → 观察 → 再思考

流程大致是：

1. 组装提示词
2. 调用模型
3. 解析输出
4. 执行工具
5. 返回结果
6. 更新上下文
7. 重复直到任务完成

本质上可能只是一个 `while` 循环，但难点在于状态、错误和上下文管理。

---

###### 2. 工具：Agent 的双手

工具让模型能操作外部世界，例如：

- 读写文件
- 搜索信息
- 执行代码
- 访问网页
- 分析代码
- 调用 API

Harness 负责：

- 注册工具
- 校验参数
- 检查权限
- 沙箱执行
- 捕获结果
- 把结果转成模型可理解的观察信息

---

###### 3. 记忆：跨时间的上下文能力

记忆分为两类：

- **短期记忆**：当前会话历史
- **长期记忆**：跨会话保存的信息

优秀的记忆系统不是简单把所有历史塞给模型，而是分层管理：

- 轻量索引：始终加载
- 详细文件：按需调用
- 原始记录：搜索访问

关键原则是：**记忆只是提示，行动前仍需验证现实状态。**

---

###### 4. 上下文管理：防止信息污染

上下文窗口不是越大越好。信息过多会导致：

- 模型注意力下降
- 关键内容被埋在中间
- 指令遵循能力退化

常见策略包括：

- **压缩历史**：保留关键决策，丢弃冗余信息
- **隐藏旧工具输出**：保留调用记录即可
- **即时检索**：需要时再加载具体内容
- **子智能体摘要**：复杂探索后只返回精炼结论

目标是：**用最少 Token 提供最高信号密度的信息。**

---

###### 5. 提示词构建：决定模型看到什么

Prompt Construction 负责把不同信息按优先级拼装起来：

- 系统提示词
- 工具定义
- 开发者指令
- 记忆内容
- 对话历史
- 当前用户请求

不同来源的信息需要有清晰优先级，否则模型容易混乱。

---

###### 6. 输出解析：识别模型想做什么

现代 Agent 不再依赖解析自由文本，而是使用结构化工具调用。

Harness 要判断：

- 如果模型返回工具调用：执行工具并继续循环
- 如果没有工具调用：输出最终答案

结构化输出可以通过 Pydantic 等方式做格式约束和校验。

---

###### 7. 状态管理：让 Agent 可恢复、可追踪

生产系统必须知道 Agent 当前处于什么状态。

状态管理可以支持：

- 中断恢复
- Checkpoint 存档
- 调试回放
- 多步骤任务追踪

例如 LangGraph 用状态图管理流程，Claude Code 则结合 Git 提交和进度文件记录状态。

---

###### 8. 错误处理：避免失败滚雪球

多步骤任务中，即使每一步成功率很高，整体失败率也会迅速上升。

错误大致分为：

- 临时错误：重试
- 模型可恢复错误：把错误反馈给模型，让它修正
- 用户可修复错误：暂停等待人工介入
- 意外错误：上报调试

好的 Harness 要让错误可见、可恢复、可控制。

---

###### 9. 护栏与安全：模型想做，不代表系统允许做

安全机制通常包括：

- 输入检查
- 输出检查
- 工具调用前检查
- 权限控制
- 沙箱执行
- 触发风险后立即停止

关键原则是：

> 模型决定“想做什么”，Harness 决定“能不能做”。

---

###### 10. 验证循环：从 Demo 到生产的分水岭

验证是提升 Agent 可靠性的关键。

常见方式包括：

- 测试和代码检查
- UI 截图反馈
- 另一个 LLM 作为评审
- 规则化结果校验

让模型能够验证自己的工作，通常能显著提升输出质量。

---

###### 11. 子智能体编排：复杂任务的分工机制

多 Agent 可以处理复杂任务，但也会引入额外成本和信息损耗。

常见模式包括：

- 克隆上下文处理子任务
- 独立智能体通过文件或消息通信
- 使用不同 Git 分支并行工作
- 把专家 Agent 当作工具调用
- 将任务控制权移交给专家 Agent

官方建议通常是：**先把单 Agent 做到极致，再考虑多 Agent。**

---

###### 12. 生命周期与退出条件

Agent 不能无限循环，Harness 需要定义：

- 什么情况下继续
- 什么情况下结束
- 什么情况下请求用户确认
- 什么情况下中断
- 什么情况下回滚或重试

这是让 Agent 从“能跑”变成“可控”的关键。

---

##### 一次 Agent 循环如何工作？

典型流程如下：

1. **提示词组装**
   - Harness 构建完整输入。

2. **模型推理**
   - 模型生成文本或工具调用。

3. **输出分类**
   - 判断是最终答案还是工具请求。

4. **工具执行**
   - 校验参数、检查权限、沙箱运行。

5. **结果打包**
   - 把执行结果转成模型可读信息。

6. **上下文更新**
   - 追加历史，必要时压缩。

7. **继续循环**
   - 直到任务完成或触发退出条件。

---

##### 主流框架的不同思路

###### Anthropic Claude Agent SDK

强调简单运行时，“笨循环 + 聪明模型”。

###### OpenAI Agents SDK

代码优先，用 Python 表达工作流逻辑。

###### LangGraph

用显式状态图建模 Harness，强调流程控制。

###### CrewAI

偏角色化多智能体协作。

###### AutoGen

支持顺序、群聊、移交、动态任务等多种编排模式。

---

##### 关键架构选择

设计 Harness 时需要回答几个问题：

1. 单智能体还是多智能体？
2. ReAct 循环还是先规划后执行？
3. 上下文是总结压缩还是动态检索？
4. 验证靠规则、测试，还是 LLM 裁判？
5. 权限是自动批准还是人工确认？
6. 工具是全部暴露还是按需暴露？
7. 逻辑是写死在系统里，还是交给模型判断？

这些选择会直接决定 Agent 的可靠性、成本和能力边界。

---

##### 最重要的洞察

**两个使用同一模型的 Agent，能力可能天差地别，差距就在 Harness。**

模型能力决定上限，但 Harness 决定模型能否稳定发挥。

随着模型变强，Harness 可能会变薄，但不会消失。因为再强的模型也仍然需要系统来：

- 管理上下文
- 调用工具
- 保存状态
- 控制权限
- 处理错误
- 验证结果

---

##### 结论

AI Agent 的竞争，不只是模型能力的竞争，更是 **Harness 工程能力** 的竞争。

当一个 Agent 表现不好时，不应只怪模型，而应该检查：

- 上下文是否污染
- 工具是否设计合理
- 记忆是否可靠
- 状态是否可恢复
- 错误是否能自愈
- 验证是否充分
- 权限是否安全

真正生产级的 Agent，不是“会聊天的模型”，而是一套围绕模型构建的完整操作系统。

## 结构化（2）

##### 主旨概括

文章指出：真正让“无状态”的大语言模型变成可执行任务的 AI Agent 的，不只是模型本身，而是模型外围的一整套工程系统——**AI Agent Harness**。  
Harness 包含编排循环、工具、记忆、上下文管理、状态、错误处理、安全护栏等组件，是决定智能体生产可用性的关键。

---

##### 1. 为什么需要 AI Agent Harness

很多 Demo 级智能体看起来能跑，但一到生产环境就容易出问题：

- 模型忘记前几步做了什么；
- 工具调用失败却没有被正确处理；
- 上下文窗口被无效信息占满；
- 多步骤任务中错误不断累积。

文章强调，问题往往不在模型能力，而在**模型外部的基础设施设计**。

一个典型案例是 **LangChain**：  
在模型和参数不变的情况下，仅通过改进 Harness 架构，就让系统在 **TerminalBench 2.0** 中从 **30 名开外提升到第 5 名**。另一项研究让 LLM 自动优化 Harness，达到 **76.4% 通过率**，超过人工设计系统。

---

##### 2. 什么是 AI Agent Harness

**AI Agent Harness** 是包裹在大语言模型外部的完整软件架构，用来让模型具备持续行动能力。

它包括：

- 编排循环；
- 工具调用；
- 记忆系统；
- 上下文管理；
- 状态持久化；
- 错误恢复；
- 安全护栏；
- 验证机制。

文章引用 LangChain 的 Vivek Trivedy 的定义：

> 如果你不是模型本身，那你就是 Harness。

也就是说：

- **Agent** 是用户看到的智能行为；
- **Harness** 是产生这种行为的底层机器。

类比来看，原始 LLM 像一个没有内存、硬盘和输入输出设备的 CPU：

- 上下文窗口像内存；
- 外部数据库像硬盘；
- 工具像设备驱动；
- Harness 像操作系统。

---

##### 3. Prompt、Context 与 Harness 的区别

围绕大模型的工程可以分为三层：

1. **提示词工程 Prompt Engineering**  
   设计模型接收到的指令。

2. **上下文工程 Context Engineering**  
   管理模型在什么时间看到什么信息。

3. **Harness 工程 Harness Engineering**  
   包含提示词和上下文管理，还包括工具编排、状态保存、错误恢复、安全执行、验证循环和生命周期管理。

所以，Harness 不是简单的“AI Wrapper”，而是让智能体能够持续自主行动的完整系统。

---

##### 4. 生产级 Agent Harness 的核心组件

###### 4.1 编排循环：智能体的心脏

编排循环通常是一个“思考—行动—观察”的过程，也叫 **TAO / ReAct 循环**：

1. 组装提示词；
2. 调用大语言模型；
3. 解析模型输出；
4. 执行工具调用；
5. 把结果反馈给模型；
6. 重复，直到任务完成。

技术上可能只是一个 `while` 循环，但难点在于管理状态、错误、上下文和退出条件。

Anthropic 将其运行时称为“笨循环”：  
Harness 只负责回合管理，真正的智能尽量交给模型。

---

###### 4.2 工具：智能体的双手

工具让模型能操作外部世界，例如读写文件、搜索、执行代码、访问网页等。

工具层通常负责：

- 工具注册；
- 参数格式校验；
- 权限检查；
- 沙箱执行；
- 结果捕获；
- 将结果转成模型可读的观察信息。

例如：

- **Claude Code** 提供文件操作、搜索、执行、网页访问、代码分析、子智能体创建等工具；
- **OpenAI Agents SDK** 支持函数工具、网页搜索、代码解释器、文件搜索和 MCP 工具。

---

###### 4.3 记忆：让智能体跨步骤和跨会话工作

记忆分为两类：

- **短期记忆**：当前会话的历史对话；
- **长期记忆**：跨会话保留的信息。

不同系统有不同实现：

- Anthropic 使用项目文件和自动生成的 `memory.md`；
- LangGraph 使用按命名空间组织的 JSON 存储；
- OpenAI 支持 SQLite 或 Redis 驱动的会话存储。

Claude Code 采用三层记忆架构：

1. 轻量级索引，每条约 **150 字符**，始终加载；
2. 按需读取的详细主题文件；
3. 通过搜索访问的原始对话记录。

关键原则是：  
智能体不能盲信记忆，行动前必须根据当前真实状态验证。

---

###### 4.4 上下文管理：防止模型“看不见重点”

上下文管理是智能体最容易失效的地方。

文章提到斯坦福的“迷失在中间”现象：  
当关键信息位于上下文窗口中间时，模型表现会下降 **30% 以上**。

即使上下文窗口达到百万 Token，信息越多，模型遵循指令的能力也可能下降。

常见解决方法包括：

- **压缩 Compaction**：接近上下文限制时，总结对话历史；
- **观察掩码 Observation Masking**：隐藏旧工具输出，只保留调用记录；
- **即时检索 Just-in-time Retrieval**：只保留轻量 ID，需要时再加载数据；
- **子智能体委托**：让子智能体深入探索，但只返回 **1000 到 2000 Token** 的摘要。

Anthropic 的目标是：  
用最少、信号最强的 Token，最大化任务成功率。

---

###### 4.5 提示词构建：决定模型每一步看到什么

提示词通常按层级组织：

1. 系统提示词；
2. 工具定义；
3. 记忆文件；
4. 对话历史；
5. 当前用户消息。

OpenAI Codex 使用严格的优先级栈：

1. 服务器系统消息；
2. 工具定义；
3. 开发者指令；
4. 用户指令；
5. 对话历史。

这保证了高优先级规则不会轻易被低优先级内容覆盖。

---

###### 4.6 输出解析：判断下一步是回答还是行动

现代 Harness 更依赖原生工具调用，而不是从自由文本里硬解析。

流程通常是：

- 如果模型输出包含 `tool_calls`，Harness 执行工具并继续循环；
- 如果没有工具调用，则认为是最终答案。

OpenAI 和 LangChain 还支持用 **Pydantic** 约束结构化输出，提升结果稳定性。

---

###### 4.7 状态管理：让任务可以恢复和调试

状态管理用于记录智能体当前进度，防止中断后丢失任务状态。

例如：

- **LangGraph** 将状态建模为图节点中流动的类型化字典，并支持 Checkpoint；
- 这样可以中断恢复，甚至进行“时间旅行”式调试；
- **OpenAI** 提供应用内存、SDK 会话、服务器端 API、响应 ID 链等策略；
- **Claude Code** 则用 Git 提交作为存档点，用进度文件当结构化草稿纸。

---

###### 4.8 错误处理：防止小错误滚雪球

多步骤任务中，错误会累积。

文章举例：  
如果一个流程有 **10 个步骤**，每步成功率 **99%**，整体成功率也只有约 **90.4%**。

LangGraph 将错误分为四类：

1. **临时错误**：延迟后重试；
2. **模型可恢复错误**：把错误返回给模型，让模型调整；
3. **用户可修复错误**：暂停等待人类介入；
4. **意外错误**：上报调试。

---

###### 4.9 护栏与安全：模型想做，不代表系统允许做

安全护栏用于限制模型行为，避免越权操作。

OpenAI SDK 有三层护栏：

- 输入护栏；
- 输出护栏；
- 工具调用护栏。

一旦触发 Tripwire，智能体会立即停止。

Anthropic 的设计思路是：  
模型负责决定“想做什么”，Harness 负责决定“允许做什么”。

---

###### 4.10 验证循环：生产级智能体的关键

验证循环是区分玩具 Demo 和生产级 Agent 的重要标准。

Anthropic 推荐三类验证方式：

1. **规则反馈**：测试、代码检查；
2. **视觉反馈**：用 Playwright 截取 UI 截图；
3. **LLM-as-judge**：让另一个模型或子智能体评估结果。

Claude Code 创造者 Boris Cherny 认为：  
让模型能验证自己的工作，可以让产出质量提升 **2 到 3 倍**。

---

###### 4.11 子智能体编排：把复杂任务拆给多个智能体

Claude Code 支持三种子智能体模式：

- **Fork 克隆**：复制父级上下文；
- **Teammate 队友**：通过文件邮箱通信；
- **Worktree 工作树**：使用独立 Git 分支。

OpenAI 支持两种方式：

- 将智能体作为工具，处理特定子任务；
- 将任务移交给专家智能体接管。

不过文章也提醒：  
多智能体会带来额外开销和信息损耗，应优先挖掘单智能体能力。

---

##### 5. 一次 Harness 循环如何运行

一次典型的 Agent Harness 执行流程如下：

1. **提示词组装**  
   Harness 整合系统指令、工具、记忆、历史和用户请求。

2. **模型推理**  
   模型生成文本或工具调用请求。

3. **输出分类**  
   如果没有工具调用，输出最终答案；如果有，进入执行阶段。

4. **工具执行**  
   Harness 校验参数、检查权限，并在沙箱中运行工具。

5. **结果打包**  
   将工具结果或错误信息转成模型可读消息。

6. **上下文更新**  
   把结果加入历史，必要时压缩上下文。

7. **继续循环**  
   回到第一步，直到任务完成或触发停止条件。

---

##### 6. 各主流框架的 Harness 思路

不同厂商和框架对 Harness 的实现方式不同：

- **Anthropic Claude Agent SDK**  
  用简单的 `query()` 函数暴露 Harness，运行时是“笨循环”。

- **OpenAI Agents SDK**  
  采用代码优先策略，用 Python 表达工作流逻辑。

- **LangGraph**  
  将 Harness 建模为显式状态图，强调精细控制和可恢复性。

- **CrewAI**  
  强调基于角色的多智能体协作，由流程层管理确定性逻辑。

- **AutoGen**  
  微软开发，支持顺序执行、群聊、移交和动态任务管理等模式。

---

##### 7. Harness 的七个核心架构选择

每个 Harness 设计者都要面对以下取舍：

1. **单智能体 vs 多智能体**  
   建议先把单智能体做到足够强。

2. **ReAct vs 先规划后执行**  
   ReAct 灵活但成本高；先规划后执行更快。

3. **上下文管理策略**  
   是总结历史，还是动态加载？

4. **验证循环设计**  
   用代码测试，还是用另一个 LLM 打分？

5. **权限与安全架构**  
   是自动批准追求速度，还是步步确认追求安全？

6. **工具范围管理**  
   工具不是越多越好，最好只暴露当前步骤需要的最小工具集。

7. **Harness 厚度**  
   哪些逻辑写死在系统里，哪些交给模型自主发挥？

---

##### 8. 结论：智能体差距往往来自 Harness，而不是模型

文章最后强调：  
两个智能体即使使用完全相同的模型，表现也可能天差地别，关键就在 Harness 设计。

TerminalBench 的结果已经说明：  
只改 Harness，就能让排名变化 **20 多位**。

随着模型能力增强，Harness 可能会变薄，但不会消失。因为再强的模型，也仍然需要系统来：

- 管理上下文窗口；
- 调用和执行工具；
- 保存状态；
- 处理错误；
- 验证结果；
- 控制权限和安全。

所以，当智能体表现不好时，不要只怪模型，应该检查它背后的 **Agent Harness** 是否设计得足够好。

#### 《深度拆解：AI Agent Harness 的构造》精炼总结

本文核心观点：**AI Agent 的能力不只取决于大模型本身，更取决于包裹在模型外部的工程系统——Agent Harness**。Harness 负责工具调用、记忆、上下文管理、错误处理、安全控制等，是把“无状态 LLM”变成可执行任务的智能体的关键基础设施。

##### 1. 为什么需要 Agent Harness？

很多人做过聊天机器人或简单 ReAct Demo，但一到生产环境就容易失败：

- 模型会忘记几步前的操作；
- 工具调用可能静默失败；
- 上下文窗口被无关信息填满；
- 长任务中错误会不断累积。

文章指出：**问题往往不在模型本身，而在模型外围的基础设施**。

一个典型案例是 LangChain：  
在模型、参数不变的情况下，仅通过改变外层架构，就让系统在 **TerminalBench 2.0** 上的排名从 **30 名开外提升到第 5 名**。另一项研究让 LLM 自己优化这套架构，最终达到 **76.4% 通过率**，超过人工设计方案。

---

##### 2. 什么是 AI Agent Harness？

**Agent Harness** 是大模型外部的一整套软件架构，用来让模型具备持续行动、调用工具、记忆状态和自我纠错的能力。

它包括：

- 编排循环；
- 工具系统；
- 记忆；
- 上下文管理；
- 状态持久化；
- 错误处理；
- 安全护栏；
- 验证机制。

Anthropic 在 Claude Code 文档中称 SDK 是“驱动 Claude Code 的 Agent Harness”；OpenAI Codex 团队也将“智能体”和“Harness”联系起来，指代使 LLM 真正工作的非模型架构。

LangChain 的 Vivek Trivedy 给出一句简洁定义：

> 如果你不是模型本身，那你就是 Harness。

---

##### 3. Agent 和 Harness 的区别

文章强调，很多人会混淆 **Agent** 和 **Harness**：

- **Agent**：用户看到的智能行为，比如有目标、会用工具、能纠错；
- **Harness**：产生这些行为的底层机器和系统。

也就是说，当有人说“我开发了一个智能体”，更准确地说是：

> 我开发了一套 Harness，并把它接入了大模型。

作者引用 Beren Millidge 的类比：

- 原生 LLM 像一个没有内存、硬盘、输入输出设备的 CPU；
- 上下文窗口像内存，快但容量有限；
- 外部数据库像硬盘，大但慢；
- 工具集成像设备驱动；
- **Harness 就像操作系统**。

---

##### 4. 围绕模型的三层工程

文章将大模型应用工程分为三个同心圆：

1. **提示词工程**  
   设计模型接收到的指令。

2. **上下文工程**  
   管理模型在什么时间看到什么信息。

3. **Harness 工程**  
   包含提示词和上下文管理，并进一步负责工具编排、状态持久化、错误恢复、验证、安全执行和生命周期管理。

结论是：  
**Harness 不是简单的 AI Wrapper，而是让智能体真正自主行动的完整系统。**

---

##### 5. 生产级 Agent Harness 的 12 个核心组件

###### 5.1 编排循环：系统的心脏

编排循环实现“思考—行动—观察”流程，即 TAO / ReAct 循环：

1. 组装提示词；
2. 调用大模型；
3. 解析输出；
4. 执行工具；
5. 反馈结果；
6. 重复直到任务完成。

技术上它可能只是一个 `while` 循环，但难点在于管理状态、错误、上下文和退出条件。

Anthropic 将自己的运行时称为一个“笨循环”：  
**Harness 负责回合管理，智慧主要留给模型。**

---

###### 5.2 工具：智能体的“双手”

工具让模型能够操作外部世界，例如读写文件、搜索网页、执行代码。

工具系统需要负责：

- 工具注册；
- 参数格式校验；
- 权限检查；
- 沙箱执行；
- 捕获结果；
- 将结果转换成模型可理解的“观察”。

案例：

- Claude Code 提供六类工具：文件操作、搜索、执行、网页访问、代码分析、子智能体创建。
- OpenAI Agents SDK 支持函数工具、网页搜索、代码解释器、文件搜索和 MCP 服务器工具。

---

###### 5.3 记忆：跨时间保持信息

记忆分为：

- **短期记忆**：当前会话中的对话历史；
- **长期记忆**：跨会话保存的信息。

不同系统的实现方式包括：

- Anthropic 使用项目文件和 `memory.md`；
- LangGraph 使用按命名空间组织的 JSON 存储；
- OpenAI 支持 SQLite 或 Redis 驱动的会话存储。

Claude Code 使用三层记忆架构：

1. 轻量级索引，每条约 **150 字符**，始终加载；
2. 按需读取的详细主题文件；
3. 只能通过搜索访问的原始对话记录。

重要原则是：  
**智能体不能盲信自己的记忆，行动前必须结合当前真实状态验证。**

---

###### 5.4 上下文管理：防止“上下文腐烂”

上下文管理是智能体常见失败点。

斯坦福研究发现，当关键信息位于上下文窗口中间时，模型表现会下降 **30% 以上**，这被称为“迷失在中间”。

即使上下文窗口达到百万 Token，随着内容增长，模型的指令遵循能力仍会下降。

常见策略包括：

- **压缩**：接近限制时总结历史，保留重要架构决策和未修复 Bug；
- **观察掩码**：隐藏旧工具输出，只保留调用记录；
- **即时检索**：只保留轻量标识符，需要时再加载；
- **子智能体委托**：让子智能体深入探索，只返回 **1000–2000 Token** 摘要。

Anthropic 的目标是：

> 找到能最大化任务成功率的、信号最强的最小 Token 集合。

---

###### 5.5 提示词构建：决定模型每一步能看到什么

提示词构建是将各种信息按优先级组织给模型。

通常包括：

- 系统提示词；
- 工具定义；
- 记忆文件；
- 对话历史；
- 当前用户消息。

OpenAI Codex 使用严格优先级栈：

1. 服务器控制的系统消息；
2. 工具定义；
3. 开发者指令；
4. 用户指令；
5. 对话历史。

---

###### 5.6 输出解析：识别模型要“说话”还是“行动”

现代 Harness 通常依赖模型原生工具调用能力，而不是从自由文本中硬解析。

Harness 会判断：

- 如果模型返回工具调用，就执行工具并继续循环；
- 如果没有工具调用，就将输出视为最终答案。

OpenAI 和 LangChain 还支持通过 **Pydantic 模型**约束结构化输出格式。

---

###### 5.7 状态管理：让任务可恢复、可调试

状态管理保证智能体在长任务中不中断、不迷路。

案例：

- LangGraph 将状态表示为在图节点中流动的类型化字典；
- 系统可以在关键步骤进行 Checkpoint；
- 支持中断恢复和“时间旅行”式调试；
- OpenAI 提供应用内存、SDK 会话、服务器端 API、响应 ID 链等策略；
- Claude Code 使用 Git 提交作为存档点，用进度文件作为结构化草稿纸。

---

###### 5.8 错误处理：防止错误滚雪球

错误处理非常关键，因为多步骤任务的成功率会快速下降。

文章举例：

> 一个 10 步流程，即使每一步成功率都是 99%，整体成功率也只有约 90.4%。

LangGraph 将错误分为四类：

1. **临时错误**：延迟后重试；
2. **模型可恢复错误**：把错误作为工具消息返回，让模型自我调整；
3. **用户可修复错误**：暂停，等待人类干预；
4. **意外错误**：上报用于调试。

---

###### 5.9 护栏与安全：模型想做，不代表系统允许做

OpenAI SDK 有三层护栏：

- 输入护栏；
- 输出护栏；
- 工具护栏。

一旦触发 Tripwire，智能体立即停止。

Anthropic 的设计是将：

- **模型推理**
- **权限执行**

分离开来。

也就是说，模型可以决定“想做什么”，但 Harness 决定“能不能做”。

---

###### 5.10 验证循环：生产级智能体的关键

验证循环是区分玩具 Demo 和生产级 Agent 的核心。

Anthropic 推荐三种验证方式：

1. **规则反馈**：测试、代码检查；
2. **视觉反馈**：例如用 Playwright 截取 UI 截图；
3. **LLM-as-judge**：让另一个模型或子智能体评估结果。

Claude Code 创造者 Boris Cherny 表示：

> 让模型能够验证自己的工作，可以让输出质量提升 2 到 3 倍。

---

###### 5.11 子智能体编排：把任务拆给多个专家

Claude Code 支持三种子智能体模式：

- **Fork**：复制父级上下文；
- **Teammate**：通过文件邮箱通信的独立窗口；
- **Worktree**：独立 Git 分支。

OpenAI 则支持：

- 将智能体作为工具，处理特定子任务；
- 将任务移交给专家智能体接管后续流程。

---

##### 6. 一次完整 Harness 循环如何运行？

一次智能体执行过程大致如下：

1. **提示词组装**：Harness 构建完整输入；
2. **模型推理**：发送给模型，模型生成文本或工具调用；
3. **输出分类**：判断是否需要调用工具；
4. **工具执行**：校验参数、检查权限、沙箱运行；
5. **结果打包**：将工具结果转为模型可读消息；
6. **上下文更新**：追加历史，必要时压缩；
7. **继续循环**：直到达到退出条件。

---

##### 7. 主流框架的 Harness 思路

不同公司和框架的 Harness 设计有所不同：

- **Anthropic Claude Agent SDK**  
  通过简单的 `query()` 函数暴露 Harness，运行时是“笨循环”，能力主要依赖模型。

- **OpenAI Agents SDK**  
  采用“代码优先”策略，用 Python 表达工作流逻辑。

- **LangGraph**  
  将 Harness 建模为显式状态图，强调流程控制和可调试性。

- **CrewAI**  
  偏向角色化多智能体协作，由流程层管理确定性主干。

- **AutoGen**  
  微软开发，支持顺序执行、群聊、移交、动态任务管理等模式。

---

##### 8. Harness 会随着模型进步而变薄，但不会消失

文章用“脚手架”类比 Harness：

- 脚手架本身不盖房子；
- 但没有脚手架，工人到不了高处；
- 房子建好后，脚手架可以减少甚至拆除。

对应到 AI：

- 当前模型还需要复杂 Harness 支撑；
- 随着模型能力提升，Harness 的复杂度会降低；
- 但它不会完全消失，因为仍需要管理上下文、执行代码、保存状态、验证结果和控制权限。

---

##### 9. 设计 Harness 时的 7 个关键选择

每个 Harness 架构师都需要权衡以下问题：

1. **单智能体还是多智能体**  
   官方建议先充分挖掘单智能体能力，多智能体会增加开销和信息损耗。

2. **ReAct 还是先规划后执行**  
   ReAct 更灵活但成本更高；先规划后执行速度更快。

3. **上下文管理策略**  
   是总结历史，还是动态加载信息？

4. **验证循环设计**  
   是用代码测试，还是让另一个 LLM 打分？

5. **权限与安全架构**  
   是自动批准提高速度，还是逐步确认保证安全？

6. **工具范围管理**  
   工具不是越多越好，应暴露当前步骤所需的最小工具集。

7. **Harness 厚度**  
   哪些逻辑写死在系统里，哪些交给模型自主判断？

---

##### 10. 最终结论

两个使用相同模型的智能体，表现可能天差地别，关键就在 Harness 设计。TerminalBench 的案例已经证明：**只改变 Harness，就能让排名提升 20 多位**。

Harness 不是通用商品，也不是已经解决的问题，而是硬核工程能力的体现。真正优秀的智能体系统，需要认真处理：

- 上下文作为稀缺资源如何管理；
- 错误如何避免累积；
- 记忆如何避免幻觉；
- 工具如何安全执行；
- 输出如何被验证。

文章最后提醒：  
**当你的智能体表现不好时，不要只抱怨模型，应该先检查你的 Harness。**

##### 2. 最重要的洞见

###### 洞见 1：Agent 不是模型，而是模型外的操作系统

###### **核心观点：**  
> 大语言模型像 CPU，Harness 才像操作系统；Agent 的“智能行为”是模型与外部系统协同产生的结果。

**为什么重要：**  
很多人把 Agent 失败归因于“模型不够强”，但生产问题常来自：上下文污染、工具失败、状态丢失、权限混乱、错误累积。

**反常识之处：**  
不是“换更强模型”就能解决 Agent 问题；很多时候，**模型没变，Harness 变了，能力就变了。**

**可迁移价值：**  
任何 AI 产品都可以按这个思路拆解：

- 模型：负责推理与生成  
- Harness：负责记忆、工具、状态、验证、权限、恢复  
- 产品体验：是两者组合后的涌现结果

**我应该记住什么：**  
> 如果你不是在改模型参数，那你就是在做 Harness 工程。

---

###### 洞见 2：上下文不是越多越好，而是越“高信号”越好

###### **核心观点：**  
> 上下文窗口是稀缺资源，真正目标不是塞满信息，而是构造“最小且信号最强”的 Token 集合。

**为什么重要：**  
长上下文并不等于强智能。信息越多，噪音越多，模型越容易丢失关键指令，尤其是“迷失在中间”。

**反常识之处：**  
百万 Token 窗口也会退化；大窗口不是免死金牌，反而可能诱导懒惰的上下文管理。

**可迁移价值：**  
适用于所有信息系统：

- 给人汇报：不是材料越多越好，而是决策信号越高越好  
- 做产品：不是功能越多越好，而是当前任务所需越精准越好  
- 做组织协作：不是同步所有信息，而是按需检索关键上下文

**我应该记住什么：**  
> 上下文工程的本质，是信息压缩与注意力分配。

---

###### 洞见 3：验证循环是玩具 Demo 与生产系统的分水岭

###### **核心观点：**  
> 生产级 Agent 不能只会执行任务，还必须能验证自己的工作。

**为什么重要：**  
多步骤任务中，错误会连乘放大。即使每步 99% 成功，10 步后整体成功率也只有约 90%。

**反常识之处：**  
“让模型多想想”不如“让系统能检查”。  
可靠性不是靠更长推理堆出来的，而是靠测试、反馈、裁判、回滚、重试机制形成闭环。

**可迁移价值：**  
所有复杂工作都应设计验证闭环：

- 写代码：测试、Lint、运行结果  
- 做设计：用户反馈、截图检查  
- 做研究：交叉验证、反例搜索  
- 做管理：过程检查、结果复盘

**我应该记住什么：**  
> 没有验证循环的 Agent，只是会说话的自动化脚本。

---

###### 洞见 4：工具越多，Agent 未必越强

###### **核心观点：**  
> 暴露给模型的工具应是当前任务所需的最小集合，而不是工具箱越大越好。

**为什么重要：**  
工具越多，选择空间越大，调用错误、权限风险、上下文膨胀也越严重。

**反常识之处：**  
很多人以为 Agent 强在“能接很多工具”；文章实际暗示，强 Agent 更依赖**工具治理**：注册、校验、权限、沙箱、结果格式化。

**可迁移价值：**  
这也是组织和产品设计原则：

- 给员工权限：够用即可，不是越多越好  
- 给用户功能：当前场景最相关即可，不是堆菜单  
- 给模型工具：按阶段动态暴露，而非一次性全开放

**我应该记住什么：**  
> 工具能力的上限来自可控性，不是数量。

---

###### 洞见 5：未来模型会变强，但 Harness 不会消失，只会变薄

###### **核心观点：**  
> 随着模型能力提升，Harness 的复杂度应下降；但窗口、状态、工具、安全、验证这些外部系统需求不会消失。

**为什么重要：**  
这提供了一个长期判断：不要把 Harness 做成过度复杂、难以替换的胶水系统，而要让它能随模型进化自动受益。

**反常识之处：**  
不是模型越强，工程越不重要；而是工程从“补模型缺陷”转向“管理模型与现实世界的接口”。

**可迁移价值：**  
构建 AI 系统时，应避免把太多智能硬编码进流程；保留弹性，让更强模型自然接管更多判断。

**我应该记住什么：**  
> 好的 Harness 像脚手架：支撑当前能力，但不阻碍未来拆除。

---

##### 3. 底层逻辑

###### **逻辑一：模型能力 × 外部系统设计 = Agent 实际能力**

- 表层现象：同一个模型，在不同 Agent 框架中表现差异巨大。
- 深层原因：Agent 任务不是单次问答，而是连续状态管理、工具执行、错误恢复和目标保持。
- 推导结论：评估 Agent 不能只看模型榜单，还要看 Harness 设计。

---

###### **逻辑二：多步骤任务的核心风险不是单点错误，而是错误累积**

- 表层现象：Demo 能跑，生产环境频繁掉链子。
- 深层原因：每一步小概率失败都会在长链路中放大；上下文污染、工具报错、状态丢失会互相叠加。
- 推导结论：生产级 Agent 必须内置重试、验证、回滚、人工介入和权限控制。

---

###### **逻辑三：智能系统的关键资源不是算力，而是注意力窗口**

- 表层现象：上下文越长，模型有时越不稳定。
- 深层原因：模型注意力并非均匀可靠，关键信息会被噪音稀释。
- 推导结论：上下文管理的目标不是“尽量多给”，而是“只给当前最有用的信息”。
