**idoubi**

我年初开始做 OpenClaw 托管服务，在一套 k8s 集群部署了 500 个 Pod，每个 Pod 限制 4g 的运行内存。日常开着 18 台 4c16g 的服务器作为节点池，一个月成本将近 5k 刀。

几个月下来，托管服务的 MRR 突破了 8k 刀，除去运营成本，利润非常低。

今天终于把服务迁移到了 FastClaw，通过存算分离的架构，让 Agent 无需常驻，而是在收到请求时动态挂载 sandbox 来提供服务。服务器从 18 台降到了 3 台，运营成本降到了 1/6，下个月有机会赚到钱了。😄

跟 OpenClaw 比，FastClaw 真的是太轻量了。

1\. 代码体积约为 OpenClaw 的 1/40  
2\. 运行资源占用约为 OpenClaw 的 1/7  
3\. 单二进制分发，无环境依赖  
4\. OpenClaw 的 gateway 启动大概需要 15s，FastClaw 秒级启动

FastClaw 本身是为云原生多租户场景而设计的 Agent 运行框架，同样也适用本地运行场景。

##### 1. 总结

作者做 **OpenClaw 托管服务**：

- 原方案：  
  - k8s 集群跑 **500 个 Pod**
  - 每个 Pod 限制 **4GB 内存**
  - 需要 **18 台 4c16g 服务器**
  - 月成本接近 **5000 美元**

- 收入情况：  
  - MRR（月经常性收入）超过 **8000 美元**
  - 但扣除成本后，利润很低

- 新方案：迁移到 **FastClaw**
  - 采用 **存算分离**
  - Agent 不再常驻
  - 有请求时才动态挂载 sandbox
  - 服务器从 **18 台降到 3 台**
  - 成本降到原来的 **1/6**

- FastClaw 优势：
  - 代码体积约为 OpenClaw 的 **1/40**
  - 资源占用约为 **1/7**
  - 单二进制分发，无环境依赖
  - 启动更快，秒级启动

---

##### 2. 解读

这件事的核心是：

> **不是收入不够，而是架构太重，成本吃掉了利润。**

原来的 OpenClaw 模式类似：

> 每个用户/任务都提前准备好一个 Agent，占着服务器资源等请求。

问题是：

- 用户没请求时，资源也在烧钱
- Pod 多，内存占用高
- k8s 节点池规模大
- 运维和云成本都很重

FastClaw 的思路更像：

> 平时不运行，需要时再启动。

也就是：

- Agent 不常驻
- 计算资源按需使用
- sandbox 动态挂载
- 大幅降低闲置成本

这就是典型的 **云原生降本优化**。

---

##### 3. 我的意见

这个迁移很关键，说明 Agent 服务真正商业化时，拼的不只是模型能力，还有：

- **资源利用率**
- **启动速度**
- **部署复杂度**
- **单位请求成本**
- **多租户隔离能力**

FastClaw 的方向是对的：  
轻量、按需、低成本，更适合托管服务。

但也要注意：

- 动态启动可能带来冷启动延迟
- sandbox 隔离安全要足够强
- 高并发时调度能力很重要
- 稳定性要经过真实业务验证

一句话：

> **Agent 产品能不能赚钱，最后很大程度取决于基础设施够不够轻。**

#### OpenClaw 托管服务迁移到 FastClaw：精炼分析

##### 1. 启发

###### 核心启发：AI Agent 产品的瓶颈不只是模型，而是运行架构

这条内容表面上讲的是一次基础设施迁移：  
从 **OpenClaw + 常驻 Pod + Kubernetes**，迁移到 **FastClaw + 存算分离 + 按需挂载 sandbox**。

但更深层的启发是：

> 对 AI Agent 托管服务来说，真正决定商业可行性的，往往不是功能是否能跑，而是单位请求背后的资源占用模型。

原来的模式是：

- 500 个 Pod 常驻
- 每个 Pod 限制 4GB 内存
- 18 台 4c16g 服务器
- 月成本接近 5000 美元
- MRR 超过 8000 美元，但利润很低

迁移后：

- 服务器从 18 台降到 3 台
- 成本降到原来的 1/6
- 业务从“有收入但不赚钱”，变成“有机会真正赚钱”

这说明：

> AI 产品商业化阶段，架构优化不是工程细节，而是利润模型的一部分。

---

##### 2. 高价值信息深挖

###### 2.1 常驻型 Agent 架构的隐性成本极高

OpenClaw 的部署方式是每个 Agent 或租户长期占用资源：

```text
用户/Agent → 常驻 Pod → 常驻内存/CPU → 持续产生成本
```

这种模式的问题是：

- 即使用户不请求，资源也被占用
- Pod 数量越多，资源浪费越明显
- 多租户场景下，成本线性增长
- MRR 增长并不必然带来利润增长

尤其对于 Agent 托管服务来说，用户请求通常是间歇性的，而不是持续高频的。  
如果每个用户都绑定一个常驻运行环境，就会出现：

> 收入按使用频率增长，成本却按用户数量增长。

这是非常危险的商业结构。

---

###### 2.2 FastClaw 的关键不是“更轻”，而是“资源占用模式改变”

文中提到 FastClaw 的优势：

1. 代码体积约为 OpenClaw 的 1/40
2. 运行资源占用约为 OpenClaw 的 1/7
3. 单二进制分发，无环境依赖
4. 秒级启动

这些当然重要，但真正关键的是：

> Agent 不再需要常驻，而是在收到请求时动态挂载 sandbox。

也就是从：

```text
常驻 Agent / 常驻 Pod
```

变成：

```text
请求到来 → 动态加载运行环境 → 执行任务 → 释放资源
```

这相当于把 Agent 运行框架从“租服务器模式”变成了“serverless / 按需计算模式”。

商业意义非常大：

| 对比项 | 常驻型架构 | 按需型架构 |
|---|---|---|
| 成本增长方式 | 随用户数增长 | 随实际请求增长 |
| 空闲资源浪费 | 高 | 低 |
| 多租户支持 | 成本压力大 | 更自然 |
| 毛利率 | 容易被吞噬 | 有改善空间 |
| 扩展性 | 依赖节点池 | 更弹性 |

---

###### 2.3 MRR 不是终点，毛利结构才是关键

MRR 突破 8000 美元听起来不错，但如果月成本接近 5000 美元，还要考虑：

- 云服务器成本
- 存储成本
- 带宽成本
- 监控与日志成本
- 支付手续费
- 人力维护成本
- 客服和运营成本
- 模型 API 成本，如果有的话

实际利润可能非常薄。

这说明 AI SaaS / Agent 托管服务不能只看：

```text
MRR 是否增长
```

更要看：

```text
每个用户的边际成本是否可控
每次请求的服务成本是否下降
毛利率是否随着规模扩大而改善
```

否则会出现一种伪增长：

> 用户越多，收入越多，但基础设施亏损也越多。

##### 3. 可迁移清单

以下经验可以迁移到其他 AI 产品、Agent 平台、开发者工具或 SaaS 系统中。

###### 3.1 产品商业化前，先算清楚资源账

需要持续追踪：

- 单用户平均资源占用
- 单请求平均成本
- 空闲资源比例
- 峰值资源需求
- 平均并发量
- 毛利率
- 云成本 / MRR 比例

一个简单判断标准：

```text
如果基础设施成本占 MRR 超过 30%～40%，就需要警惕。
```

对于 AI 产品，这个比例甚至可能更高，因为还有模型调用成本。

---

###### 3.2 尽量避免“低频用户常驻资源”

如果用户请求不是持续高频，不应为每个用户绑定常驻环境。

可以考虑：

- 按需启动
- 动态 sandbox
- serverless runtime
- worker 池
- 队列调度
- 冷热分层
- 空闲自动回收
- 多租户资源复用

核心原则：

> 让成本跟随真实使用量，而不是跟随用户账户数量。

---

###### 3.3 把“启动速度”当成产品能力

FastClaw 秒级启动，这不是单纯的技术指标，而是决定架构是否可行的前提。

如果按需启动太慢，用户体验会变差；  
如果启动够快，就可以大胆做资源回收和动态分配。

因此，Agent 运行框架需要重点优化：

- 冷启动时间
- sandbox 创建速度
- 依赖加载速度
- 二进制体积
- 初始化流程
- 状态恢复速度

对于 AI Agent 产品，启动速度会直接影响：

```text
成本优化空间 + 用户体验 + 并发弹性
```

---

###### 3.4 代码体积和依赖复杂度会影响商业成本

FastClaw 的几个特点值得注意：

- 代码体积小
- 资源占用低
- 单二进制分发
- 无环境依赖

这类特性表面上是工程审美，实际上会影响：

- 部署复杂度
- 故障率
- 冷启动速度
- 维护成本
- 节点资源利用率
- 客户私有化部署难度

可迁移原则：

> 越是基础设施型产品，越应该追求轻量、可移植、低依赖、易启动。

---

###### 3.5 从“功能能跑”升级到“单位经济模型能跑”

很多 AI 产品早期只关注：

- Agent 能不能执行任务
- Tool call 是否成功
- Demo 是否流畅
- 用户是否愿意试用

但真正商业化时，需要转向：

- 单次任务成本是多少
- 单个租户成本是多少
- 并发上来后成本曲线如何
- 空闲资源浪费有多大
- 是否具备规模经济

一句话：

> Demo 阶段看能力，商业阶段看单位经济模型。

---

##### 4. 反方与张力

###### 4.1 按需启动不一定适合所有 Agent 场景

FastClaw 的按需架构很有吸引力，但不是所有场景都适用。

可能不适合：

- 高频实时交互型 Agent
- 需要长期保持上下文的 Agent
- 需要持续监听事件的 Agent
- 长时间任务执行环境
- 对冷启动极其敏感的企业场景

如果用户需要的是“始终在线”的 Agent，那么常驻资源可能仍然有必要。

张力在于：

```text
成本效率 vs 实时性
资源回收 vs 状态连续性
轻量架构 vs 长任务稳定性
```

---

###### 4.2 存算分离会引入新的复杂度

存算分离可以降低计算资源成本，但也会带来新问题：

- 状态如何保存？
- sandbox 如何快速恢复？
- 多租户隔离是否安全？
- 文件系统如何挂载？
- 执行过程如何审计？
- 任务失败后如何恢复？
- 并发请求如何避免状态冲突？

因此不能只看到服务器数量从 18 台降到 3 台，还要关注：

> 成本下降是否伴随系统复杂度、可靠性风险和安全风险上升。

---

###### 4.3 Kubernetes 不一定是错，错的是资源模型

文中从 18 台 k8s 节点降到 3 台服务器，容易让人得出一个简单结论：

> k8s 太重，别用 k8s。

但更准确的判断应该是：

> k8s 不是问题，常驻 Pod + 低利用率才是问题。

Kubernetes 适合管理复杂集群，但如果每个 Pod 都低频空转，任何编排系统都会很贵。

所以反方观点是：

- 问题不一定在 OpenClaw
- 也不一定在 Kubernetes
- 核心问题是 Agent runtime 的资源生命周期设计

---

###### 4.4 成本降低后，也可能暴露新的瓶颈

服务器成本从 5000 美元降到约 800 多美元，这是巨大进步。  
但随着业务继续增长，新的瓶颈可能出现：

- 模型调用成本
- sandbox 安全成本
- 日志和审计成本
- 存储 IO 成本
- 请求排队延迟
- 高峰期扩容速度
- 企业客户 SLA 要求

所以成本优化不是一次性动作，而是持续过程。

---

##### 5. 情境化落地

###### 5.1 如果你在做 AI Agent SaaS

优先检查这几个问题：

1. 每个用户是否长期占用独立运行环境？
2. 用户不活跃时，资源是否还在消耗？
3. 是否可以把 Agent 状态和运行时分离？
4. 是否可以按请求启动 sandbox？
5. 冷启动时间是否可以接受？
6. 是否有 worker pool 或任务队列机制？
7. 是否知道单次任务的真实成本？

建议目标：

```text
让 Agent runtime 从“常驻服务”变成“按需执行单元”。
```

---

###### 5.2 如果你在做开发者工具

开发者工具常常容易忽略基础设施成本，因为早期用户量不大。  
但一旦做托管服务，就要从第一天考虑：

- 多租户隔离
- 执行环境复用
- 单二进制部署
- 依赖最小化
- 资源限制
- 日志追踪
- 失败恢复
- 动态扩缩容

尤其是代码执行、Agent sandbox、自动化任务类产品，建议尽早设计：

```text
任务调度层 + sandbox 层 + 状态存储层
```

不要让每个租户直接绑定一个长期运行的容器。

---

###### 5.3 如果你在做 AI 产品商业化

可以用一个简单框架评估业务健康度：

| 指标 | 需要回答的问题 |
|---|---|
| MRR | 收入是否稳定增长？ |
| Gross Margin | 毛利率是否足够高？ |
| Infra Cost / MRR | 基础设施是否吞噬收入？ |
| Cost per Request | 单次请求成本是否下降？ |
| Idle Cost | 空闲资源浪费有多高？ |
| Cold Start | 按需启动是否影响体验？ |
| Utilization | 资源利用率是否持续提升？ |

尤其要警惕：

```text
MRR 增长，但毛利率不增长。
```

这通常说明架构没有规模经济。

---

###### 5.4 如果你是小团队或独立开发者

这条案例的价值很大，因为它说明：

> 小团队不一定要靠更强销售赚钱，也可以靠更好的架构把利润做出来。

对于小团队，建议优先做三件事：

1. **减少常驻资源**
   - 空闲自动释放
   - 低频任务按需启动
   - 用户环境动态挂载

2. **降低部署复杂度**
   - 单二进制
   - 少依赖
   - 少中间件
   - 快速启动

3. **持续看成本面板**
   - 云账单
   - 单用户成本
   - 单任务成本
   - 空闲资源成本
   - 毛利率趋势

小团队最怕的是：

```text
产品有收入，但基础设施和维护成本把利润吃光。
```
