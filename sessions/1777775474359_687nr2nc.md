## 分析要点

- **核心高价值点**：用Context Providers作为主Agent与各类工具之间的隔离层，减少上下文污染和工具复杂度，是最有复用价值的架构设计。
- **留存建议**：长期保留（文章提出了构建企业AI上下文层的可复用架构思路，并给出开源项目、工具接口和快速启动方式，适合作为AI Agent产品设计与企业知识管理方案参考。）

**知识要点**

- Context Providers将每个信息源封装为query\_source和update\_source，主Agent无需直接处理底层工具细节。
- “导航优于搜索”强调像代码代理遍历文件系统一样访问实时数据源，而不是依赖过期的向量索引。
- 公司大脑可分为数据层和操作系统层：前者组织企业知识，后者负责执行、监控和闭环调整。
- Scout通过CRM、知识维基、跟进表和按需SQL表，将无明确来源归属的信息结构化沉淀。
- 该方案的主要代价是每次查询需要更多LLM调用，成本和延迟高于一次性向量检索。

**行动项**

- 阅读Scout仓库和Context Providers相关文章，评估其架构是否可用于自己的Agent系统。
- 本地部署Scout，连接Slack或Google Drive进行小规模测试。
- 在现有AI Agent设计中尝试增加工具隔离层，减少主Agent上下文污染。
- 对比向量检索与实时导航式检索在企业知识问答中的准确率、时效性和成本。
- 梳理自身团队的核心信息源，设计query/update风格的上下文提供器接口。

### Meet Scout

[Scout is a open-source context agent](https://github.com/agno-agi/scout). It navigates live information sources to assemble context on demand. It connects the fragmented knowledge living in slack, google drive, linear using proven patterns like "navigation over search", "context providers", and "learning machines".

Scout also builds its own wiki and CRM as it learns about your company. So you can share that "Josh from Anthropic shared this new paper on RLMs" and it'll add a note in the CRM, parse the paper and store it in the company wiki.

You can also share that "a decision on v3 schema migration" is pending and it'll log a follow up in the CRM, ready to surface next time anyone asks what's open. Put follow-up review on a daily cron and the loop gets tighter.

让我们讨论一些设计决策，这些决策使得 Scout 比那种把所有东西都扔进向量数据库然后祈祷能找到正确数据块的做法更好。

### 上下文提供者

构建“公司大脑”时遇到的第一个问题，是一个智能体连接所有工具并跨信息源工作的能力。目前尚未解决的三个问题是：

1. 来自太多工具的上下文污染
2. 范围重叠导致的性能下降
3. 主代理停止工作，因为其上下文全是工具怪癖

我发现可行的解决方案是 agent 和工具之间的一个薄层，称为 Context Providers。每个信息源（Slack、Drive、CRM）都成为一个 context provider，并向主 agent 暴露两个工具：

- 查询\_&lt;source&gt; 用于自然语言读取
- 更新\_&lt;source&gt; 用于自然语言写作

这种方法的第一个优点是主代理看不到 Slack 的十二个工具，它只看到 query\_slack。

第二个优势，即“大赢”（BIG WIN），在于 query\_slack 工具背后是一个子代理，该子代理掌握了 Slack 的所有特殊处理方式（如在直接发送消息（DM）给用户前先查询用户信息、通过游标进行分页、优先使用 conversations.replies 处理线程）。这一点极为重要，因为现在主代理的上下文不会被如何使用 Slack 的指令或所有中间工具调用结果所污染。

不，技能无法解决这个问题。技能是特定任务的指令（例如“如何使用 Slack”），模型会按需加载这些指令。技能将任务知识从始终存在的提示中移出，转移到更具条件性的内容中。但是当模块被加载时，Slack 工具仍然会作用于主代理，中间工具调用的结果仍然保留在主上下文中。加载两个具备搜索能力的技能，你的代理会立即崩溃。

Scout 的工具界面今日：

- Web: query\_web
- Slack: query\_slack, update\_slack
- Google Drive: query\_gdrive
- CRM: query\_crm, update\_crm (writes to contacts / projects / notes / follow-ups)
- Knowledge wiki: query\_knowledge, update\_knowledge
- Voice wiki: query\_voice (read-only)
- MCP servers: query\_mcp\_&lt;server&gt; (one per registered server)
- Workspace: query\_workspace
- Cross-cutting: list\_contexts

The payoff:

1. 你实际上可以同时使用多个上下文提供者。query\_slack 找到讨论，query\_gdrive 找到文档。
2. 路由是最基本的，这意味着 Scout 的指令保持不变，并且添加更多工具不会导致回归问题。

### 搜索导航

构建“公司大脑”时的默认做法是将所有数据导入向量数据库，进行分块、嵌入处理，然后检索 top-k 结果。

这根本没用。索引总是过时的。这些块落在错误的边界上。引用指向的片段在上周二时是正确的。一半的时候，相关内容其实在那个从未被索引的 Slack 线程里——毕竟哪个神智正常的人会去索引 Slack 呢！

编码代理发现的关键是：不要搜索，要导航。他们用 \`ls\` 列出目录内容，用 \`grep\` 搜索函数名，打开文件，跟踪导入，遍历文件系统，就像人类一样。

这种模式非常适用于上下文代理。每个信息源已经具备了相当于 ls、grep 和 cat 的功能。这些功能通过上下文提供者暴露出来。

The payoff:

1. 实时状态。您三十秒前发送的 Slack 消息可供座席使用。昨天的路线图文档是最新的，因为它是实际文档。
2. 真实引用。每个引用都是一个你可以打开的路径。没有来自嵌入边界的片段。
3. Permissions stay where they live. Drive enforces who can read what, Slack enforces channel membership. Scout sees what its credentials see.

The trade off is more LLM calls per query. A vector lookup is one round trip; navigation is three or four.

### The wiki, crm, and the closed loop

Some things don't have a natural source home. "Josh from Anthropic shared an RLM paper last week" doesn't live anywhere obvious. It was probably mentioned in Slack, but you don't search Slack for "who is Josh".

That's what the CRM and the knowledge wiki are for. Scout populates these as it learns. Josh becomes a contact in the CRM. The RLM paper becomes a wiki page linked from his contact note.

The CRM ships with four tables: scout\_contacts, scout\_projects, scout\_notes, scout\_followups. Beyond those, the write sub-agent creates new scout\_\* tables on demand. "Track my coffee orders" becomes a scout\_coffee\_orders table with the right columns. Schema on demand.

> If you think LLMs are good at bash, wait till you see them write SQL.

### Scout in action

#### Quickstart

Clone the repo, add your API key and run scout locally using docker.

```text
git clone https://github.com/agno-agi/scout && cd scout

cp example.env .env             # set OPENAI_API_KEY

docker compose up -d --build
```

By default, scout comes with the web, CRM, knowledge wiki, voice wiki, and workspace context providers. Slack and Google Drive providers are wired up, you just need to set up the credentials.

#### AgentOS

Scout runs on Agno's

[AgentOS](https://docs.agno.com/). You get a UI, multi-user sessions, scheduled tasks, and a FastAPI app that deploys anywhere Docker runs. Once you have Scout running locally, connect it to the AgentOS UI at

[os.agno.com](https://os.agno.com/)

## 通俗精炼（1）

### 2026-05-03 02:27:34

#### 认识 Scout：开源公司的“大脑”

##### 一句话总结

Scout 是一个开源的“上下文代理”，试图把 Slack、Google Drive、CRM、知识库等分散信息连接起来，让 AI 能像员工一样理解公司、追踪事项、沉淀知识，并进一步演化为企业 AI 操作系统。

##### 核心观点：公司需要“活的大脑”

文章认为，未来每家公司都需要一个“公司大脑”：

- 把分散在 Slack、邮件、文档、工单、数据库里的知识连接起来；
- 让 AI 能理解公司的背景、决策、流程和客户关系；
- 不只是搜索信息，而是能持续学习、更新、执行和跟进。

但作者反对传统做法：把所有数据丢进向量数据库，再靠搜索召回。因为索引容易过期、分块不准确、权限复杂、信息源遗漏严重。

##### Scout 的关键理念：导航优于搜索

Scout 的核心设计是“导航优于搜索”。

传统 AI 知识库通常依赖：

- 数据导入；
- 分块；
- 向量化；
- top-k 检索。

Scout 更像程序员读代码：

- 先看有哪些信息源；
- 再进入 Slack、Drive、CRM 等具体系统；
- 按路径、线程、文档逐步查找；
- 获取实时、可验证、可追溯的信息。

好处是：

- 信息更实时；
- 引用更真实；
- 权限由原系统控制；
- 不依赖过期索引。

代价是：每次查询需要更多 LLM 调用，成本和延迟更高。

##### 关键架构：Context Providers

Scout 在主 Agent 和各种工具之间加了一层：Context Providers。

每个信息源，比如 Slack、Google Drive、CRM，都被封装成一个上下文提供者，只暴露简单接口：

- `query_slack`
- `update_slack`
- `query_gdrive`
- `query_crm`
- `update_crm`
- `query_knowledge`
- `update_knowledge`

这样做的价值是：

1. **减少上下文污染**  
   主 Agent 不需要理解 Slack、Drive 等复杂工具细节。

2. **降低工具复杂度**  
   Slack 的分页、线程、用户查询等特殊逻辑由子 Agent 处理。

3. **增强扩展性**  
   新增工具不会显著破坏主 Agent 的稳定性。

作者认为，这比单纯给 Agent 加“技能”更有效，因为技能仍然会把工具调用结果塞进主上下文，容易导致 Agent 混乱。

##### Scout 会自动构建公司知识库和 CRM

Scout 不只是查询工具，还会在工作中不断沉淀结构化知识。

例如：

- 有人提到“Anthropic 的 Josh 分享了一篇 RLM 论文”；
- Scout 会把 Josh 记录进 CRM；
- 把论文解析并写入知识库；
- 把两者关联起来。

再比如：

- “v3 schema 迁移决策还没定”；
- Scout 会记录为待跟进事项；
- 后续可以通过定时任务主动提醒。

Scout 自带 CRM 表：

- 联系人；
- 项目；
- 笔记；
- 跟进事项。

还支持按需生成新表，比如用户说“帮我追踪咖啡摄入量”，它就可以创建对应数据结构。

##### 从“公司大脑”到“AI 操作系统”

文章把“公司大脑”和“企业 AI 操作系统”区分为两层：

- **公司大脑**：数据与上下文层，负责理解公司知识；
- **AI 操作系统**：执行与闭环层，负责基于理解做决策、执行任务、持续反馈。

Scout 目前更接近“公司大脑”的基础设施，但它具备向 AI 操作系统演进的潜力：

- 多信息源连接；
- 自动沉淀知识；
- CRM 和知识库更新；
- 定时任务；
- Slack 交互；
- 后续可扩展 GitHub、Gmail、Calendar 等系统。

##### 产品价值

Scout 的价值不在于做一个更好的搜索框，而在于让 AI 真正成为“懂公司的人”。

它解决的是企业 AI 落地中的核心问题：

- AI 不知道公司上下文；
- 信息分散在各个系统；
- 静态知识库很快过期；
- Agent 工具太多后容易失控；
- 企业需要可持续更新的知识与执行闭环。

##### 总结

Scout 代表了一种新的企业 AI 基础设施思路：不是把公司数据静态索引起来，而是让 AI 通过上下文提供者实时导航各类信息源，并在过程中持续构建知识库、CRM 和待办闭环。

它的本质是：让 AI 从“会搜索资料的助手”，进化为“理解公司运转方式的团队成员”。

##### 2. 最重要的洞见

###### 洞见 1：企业 AI 的核心不是“搜索知识”，而是“导航现实”

###### **核心观点：**  
> 把 Slack、文档、工单、CRM 全部导入向量数据库并不能构成“公司大脑”；真正有效的方式，是让智能体像人一样在原始系统中导航：查目录、搜关键词、打开文件、追踪上下文、顺着线索走。

**为什么重要：**  
很多企业知识管理的默认路径是：收集数据 → 分块 → embedding → 向量检索 → RAG。  
但企业信息的特点是：

- 高频变化；
- 权限复杂；
- 上下文分散；
- 有大量信息只存在于对话、线程、临时决策中；
- 真实答案常常不是一个文档块，而是一条路径。

所以，静态索引天然会落后于现实。

**反常识之处：**  
主流做法是“把知识结构化、索引化、向量化”。  
作者反而认为：**不要急着整理世界，让 AI 学会在世界中行动。**

**可迁移价值：**  
这对所有复杂系统都适用：

- 企业知识库：少做大一统索引，多做实时访问层；
- 产品设计：不要复制数据，优先连接源系统；
- 数据平台：不要只追求统一湖仓，也要保留原始系统的可导航性；
- 个人知识管理：不一定要完美分类，重要的是能顺着问题找到上下文。

**我应该记住什么：**  
> 对动态系统来说，导航常常比搜索更可靠；访问真实源头，比维护副本更重要。

---

###### 洞见 2：Context Provider 是智能体工具爆炸的关键中间层

###### **核心观点：**  
> 主智能体不应该直接面对一堆 Slack、Drive、CRM 的底层工具，而应该只看到每个信息源抽象出的两个接口：`query_source` 和 `update_source`。

作者提出的架构是：

```text
主 Agent
  ↓
Context Provider
  ↓
Slack / Drive / CRM / Wiki / MCP / Workspace
```

每个 Context Provider 对主 Agent 暴露简单接口：

- `query_slack`
- `update_slack`
- `query_gdrive`
- `query_crm`
- `update_crm`

但在接口背后，由子代理处理具体系统的复杂性，例如：

- Slack 线程如何分页；
- DM 前如何查用户；
- 什么时候用 `conversations.replies`；
- Google Drive 如何查文件；
- CRM 如何写入记录。

**为什么重要：**  
智能体系统一旦接入多个工具，会出现三个问题：

1. **上下文污染**：主 Agent 的 prompt 里塞满工具说明；
2. **作用域重叠**：多个工具都能“搜索”，模型不知道该用哪个；
3. **主任务丢失**：Agent 花太多注意力处理工具细节，忘了原始目标。

Context Provider 的价值在于：  
**把工具复杂度封装到局部，把主 Agent 的认知负担降到最低。**

**反常识之处：**  
常见思路是给 Agent 更多工具、更详细说明、更强模型。  
作者的判断相反：**不是工具越多越强，而是主 Agent 看到的工具越少越稳定。**

**可迁移价值：**  
这是一个很强的组织与系统设计原则：

- 软件架构：复杂能力应该被封装成清晰接口；
- 组织管理：高层不应处理所有一线细节，而应面对抽象后的责任接口；
- 产品平台：能力越复杂，对外接口越要简单；
- AI Agent：主 Agent 负责判断，子 Agent 负责专业执行。

**我应该记住什么：**  
> Agent 的能力上限，不只取决于模型智力，也取决于工具边界设计。

---

###### 洞见 3：“技能”不能真正解决工具复杂度问题，因为它没有隔离执行痕迹

###### **核心观点：**  
> Skill 只是把某类任务说明从常驻 prompt 中移出去，但一旦加载，工具调用和中间结果仍然污染主 Agent 的上下文。

这是文章中一个被轻描淡写但很重要的技术判断。

Skill 的问题在于：

- 它能按需加载“如何使用 Slack”的说明；
- 但 Slack 的底层工具仍然直接暴露给主 Agent；
- 中间调用结果仍然进入主上下文；
- 多个具备搜索能力的 Skill 同时加载时，Agent 仍然会混乱。

所以 Skill 解决的是“提示词常驻负担”，没有解决“执行过程隔离”。

**为什么重要：**  
这区分了两类优化：

| 优化对象 | Skill | Context Provider |
|---|---|---|
| 减少常驻说明 | 可以 | 可以 |
| 隐藏底层工具复杂度 | 不充分 | 可以 |
| 隔离中间执行结果 | 不充分 | 可以 |
| 降低主 Agent 认知负担 | 有限 | 明显 |
| 支持多源并行查询 | 容易崩 | 更稳定 |

**反常识之处：**  
很多人以为“给 Agent 装 Skill”就是模块化。  
但作者指出：**真正的模块化不是按需加载说明，而是隔离复杂执行。**

**可迁移价值：**  
这对 AI 系统设计非常关键：

- Prompt 模块化 ≠ 系统模块化；
- 指令复用 ≠ 能力封装；
- 工具接入 ≠ 上下文治理；
- 真正的抽象要隐藏过程，而不只是隐藏说明。

**我应该记住什么：**  
> 如果一个模块的中间过程仍然污染主系统，它就不是真正的模块。

---

###### 洞见 4：公司大脑不是只读知识库，而应该能写入、跟进、形成闭环

###### **核心观点：**  
> Scout 不只是查询 Slack 和文档，它还会把新知识写入 CRM、Wiki、Follow-up，并通过定时任务把未完成事项重新浮现出来。

这意味着“公司大脑”不是一个静态问答系统，而是一个动态运行系统：

```text
读信息 → 理解语义 → 写入结构化记忆 → 设定跟进 → 定期触发 → 更新状态
```

例如：

- “Josh from Anthropic 分享了一篇 RLM 论文”
  - Josh 成为 CRM 联系人；
  - 论文进入 Wiki；
  - 两者建立关联。

- “v3 schema migration 决策待定”
  - 写入 follow-up；
  - 下周二自动浮现；
  - 后续讨论继续带着完整历史。

**为什么重要：**  
企业真正缺的不是“能不能查到过去”，而是：

- 未完成的事情会不会被重新带回决策场；
- 临时对话能不能变成组织记忆；
- 一次性信息能不能转化为可复用资产；
- AI 能不能观察行动后的结果并调整。

**反常识之处：**  
很多 AI 知识库产品把重点放在“问答准确率”。  
但企业 AI OS 的关键指标可能是：**它能不能让组织减少遗忘、减少断点、减少重复沟通。**

**可迁移价值：**  
这是从“查询系统”走向“运营系统”的分界线：

- 好的销售系统不是只记录客户，而是提醒下一步动作；
- 好的项目系统不是只存任务，而是暴露阻塞；
- 好的个人知识系统不是只收藏文章，而是推动行为；
- 好的 AI 助手不是回答问题，而是维护连续性。

**我应该记住什么：**  
> 记忆的价值不在保存，而在未来某个正确时刻重新出现。

---

###### 洞见 5：动态 schema 可能比预先设计完整数据模型更适合 AI 工作流

###### **核心观点：**  
> Scout 的 CRM 默认只有几张基础表，但写入子代理可以按需创建新的 `scout_*` 表；用户说“帮我追踪咖啡摄入”，系统就创建 `scout_coffee_orders` 表。

这代表一种新的系统设计思路：  
不是先由工程师定义所有可能的数据结构，而是让 AI 在使用中根据任务生成结构。

**为什么重要：**  
企业内部有大量长尾流程：

- 临时项目；
- 临时跟进；
- 非标准客户信息；
- 团队自定义追踪项；
- 个体习惯记录；
- 新业务探索指标。

传统 SaaS 往往要求用户先适配系统字段。  
而 AI-native 系统可以反过来：**系统结构适配用户语言。**

**可迁移价值：**  
这可能影响很多产品形态：

- CRM：从固定字段变为自然语言生成字段；
- 数据库：从人建表变成 Agent 建表；
- 内部工具：从低代码走向“语义驱动建模”；
- 个人管理：从模板化工具走向按需结构化。

**我应该记住什么：**  
> AI 时代的结构化，不一定发生在输入前，也可以发生在理解后。

---

##### 3. 底层逻辑

###### **逻辑一：动态信息系统中，源头真实性优先于索引效率**

- **表层现象：**  
  向量数据库检索速度快，但在企业知识场景中经常找不到最新、完整、正确的上下文。

- **深层原因：**  
  企业知识不是稳定文档集合，而是持续变化的互动网络。Slack 线程、Drive 文档、CRM 记录、工单状态都在实时变化，且有权限、版本、上下文依赖。

- **推导结论：**  
  与其维护一个永远滞后的知识副本，不如让 Agent 直接访问原始系统，并通过导航方式组合上下文。

---

###### **逻辑二：Agent 复杂度的瓶颈不是工具数量，而是主上下文的污染程度**

- **表层现象：**  
  Agent 接入越多工具，性能越不稳定，越容易误调用、漏调用、忘记任务。

- **深层原因：**  
  所有工具说明、中间结果、系统怪癖都挤入主 Agent 上下文，会侵占模型注意力，造成决策混乱。

- **推导结论：**  
  需要在 Agent 和工具之间加入 Context Provider，把复杂工具使用封装到子代理中，让主 Agent 只面对少量高层语义接口。

---

###### **逻辑三：企业 AI 的终局不是问答，而是闭环执行**

- **表层现象：**  
  很多企业 AI 产品停留在“查询知识”“总结会议”“回答问题”。

- **深层原因：**  
  企业运转依赖的不只是信息获取，还包括承诺、跟进、状态变化、责任延续和反馈调整。

- **推导结论：**  
  真正的 AI OS 需要具备读、写、记忆、调度、跟进、更新的能力；否则它只是增强版搜索框，不是操作系统。

## 结构化（1）

### 2026-05-03 08:00:33

#### 文章精炼总结：认识 Scout，这家开源公司的“大脑”

文章介绍了开源项目 **Scout**：一个“公司大脑”式的上下文智能体，目标是让 AI 能够理解并使用企业中分散在 Slack、Google Drive、CRM、代码库等工具里的实时信息。作者认为，构建公司大脑的关键不是把所有资料塞进向量数据库搜索，而是让 AI 像人一样“导航”信息源。

---

##### 1. 背景：YC 提出的两个创业方向指向同一个问题

YC Summer 2026 Requests for Startups 提到两个相关方向：

- **Company Brain（公司大脑）**  
  把分散在 Slack、邮件、工单、数据库、人脑中的知识提取出来，结构化、保持更新，并让 AI 能够使用。

- **AI Operating System for Companies（企业 AI 操作系统）**  
  让公司默认对 AI 可理解：会议、工单、客户互动都能被智能层读取和学习，并形成闭环系统，根据结果持续调整。

作者认为：

- “公司大脑”是底层数据层；
- “AI 操作系统”是运行在这个数据层之上的系统；
- 目前还没有成熟产品，但相关能力已经具备，例如模型能力、上下文提供者、Agentic SQL、MCP、持久记忆、定时执行等。

---

##### 2. Scout 是什么：开源的上下文智能体

**Scout 是一个开源 context agent（上下文智能体）**，它可以连接企业中的实时信息源，并在需要时动态组装上下文。

它支持的信息来源包括：

- Slack
- Google Drive
- Linear
- CRM
- 公司知识库
- 语音知识库
- MCP servers
- 本地 workspace

Scout 的目标不是简单搜索资料，而是：

- 理解公司内部信息分布；
- 按需从不同系统中导航和提取上下文；
- 自动构建公司 Wiki 和 CRM；
- 记录待办、跟进事项和业务知识。

###### 示例

如果你告诉 Scout：

> “Josh from Anthropic shared this new paper on RLMs.”

Scout 可以：

- 在 CRM 中记录 Josh 这个联系人；
- 解析 RLM 论文；
- 把论文内容加入公司知识 Wiki；
- 将人物、资料和上下文关联起来。

如果你说：

> “v3 schema migration 的决策还没定。”

Scout 可以：

- 在 CRM 中记录一个 follow-up；
- 下次有人问“有哪些未决事项”时自动提醒；
- 未来还可以通过定时任务每天检查这些待办。

---

##### 3. 核心设计一：Context Providers，避免工具和上下文污染

作者认为，构建公司大脑时，智能体连接多个工具会遇到三个问题：

1. **太多工具导致上下文污染**  
   主 Agent 需要记住 Slack、Drive、CRM 等各种工具的使用细节。

2. **工具范围重叠导致性能下降**  
   多个工具都能搜索或写入时，Agent 容易混乱。

3. **主 Agent 被工具细节拖垮**  
   主 Agent 的上下文被各种工具调用结果和操作规则占满，忘记真正任务。

###### Scout 的解决方案：Context Providers

Scout 在主 Agent 和工具之间加了一层薄层，叫 **Context Providers**。

每个信息源都被包装成一个上下文提供者，只向主 Agent 暴露两个简单能力：

- `query_&lt;source>`：用自然语言读取信息；
- `update_&lt;source>`：用自然语言写入信息。

例如：

- Slack：`query_slack`、`update_slack`
- Google Drive：`query_gdrive`
- CRM：`query_crm`、`update_crm`
- Knowledge Wiki：`query_knowledge`、`update_knowledge`

这样主 Agent 不需要知道 Slack 背后有十几个 API 或操作细节，只需要调用 `query_slack`。

###### 关键好处

- 主 Agent 的上下文更干净；
- Slack、Drive 等复杂操作交给子 Agent 处理；
- 新增工具时，不容易导致系统退化；
- 可以同时使用多个上下文来源，例如先用 Slack 找讨论，再用 Google Drive 找文档。

作者特别强调：**“技能（skills）”不能完全解决这个问题**。因为即使技能按需加载，工具调用结果仍会进入主 Agent 上下文，多个搜索类技能同时加载时，Agent 仍可能崩溃。

---

##### 4. 核心设计二：不要只搜索，要像人一样导航

传统“公司大脑”的常见做法是：

1. 把所有数据导入向量数据库；
2. 分块；
3. 做 embedding；
4. 检索 top-k 结果。

作者认为这套方法在企业知识场景中效果很差，原因包括：

- 索引总是过时；
- 文档切块边界经常不合理；
- 引用内容可能已经过期；
- 很多重要信息在未被索引的 Slack 线程里；
- 企业权限和实时状态难以维护。

###### Scout 的方法：Navigation over Search

作者借鉴编码 Agent 的工作方式：

- 用 `ls` 查看目录；
- 用 `grep` 搜索函数；
- 打开文件；
- 跟踪 import；
- 像人一样遍历文件系统。

Scout 把这种模式用于企业信息源：

- 在 Slack 中查找线程；
- 在 Drive 中打开实时文档；
- 在 CRM 中读取联系人和项目；
- 在 Wiki 中查找知识页面。

###### 好处

- **实时性更强**  
  30 秒前发的 Slack 消息就可以被 Scout 使用；昨天的路线图文档也是最新版本。

- **引用更真实**  
  引用指向可打开的真实路径，而不是向量数据库中切出来的片段。

- **权限仍由原系统控制**  
  Google Drive 继续控制谁能读文档，Slack 继续控制频道权限。Scout 只能看到自己凭证允许看到的内容。

###### 代价

相比一次向量检索，导航式查询需要更多 LLM 调用：

- 向量检索可能只需一次往返；
- 导航式查询通常需要三到四次调用。

但作者认为，这是换取准确性、实时性和可追溯性的必要成本。

---

##### 5. Wiki、CRM 与闭环系统：让零散知识有归属

有些知识没有天然归属地，例如：

> “Josh from Anthropic 上周分享了一篇 RLM 论文。”

这类信息可能出现在 Slack，但你不会自然去 Slack 搜“Josh 是谁”。

因此 Scout 内置了：

- **CRM**
- **Knowledge Wiki**

Scout 会随着使用自动填充这些系统：

- Josh 会成为 CRM 中的联系人；
- RLM 论文会成为 Wiki 页面；
- 论文会链接到 Josh 的联系人备注中。

###### CRM 默认包含四张表

- `scout_contacts`
- `scout_projects`
- `scout_notes`
- `scout_followups`

此外，写入子 Agent 可以按需创建新的 `scout_*` 表。

###### 示例

如果你说：

> “帮我追踪咖啡订单。”

Scout 可以自动创建：

- `scout_coffee_orders` 表；
- 并设计合适字段，例如咖啡类型、时间、备注等。

作者称这种能力为 **Schema on demand（按需建模）**，并认为 LLM 写 SQL 的能力会非常有用。
