## 结构化（1）

这篇内容的主旨是：`sandbox cloud`已正式提供 “浏览器自动化” 能力，用户可以直接在沙箱里自动操作网站。它的价值在于，把原本复杂的 E2E 测试、网页登录和会话保存，变成更容易落地的自动化流程。

- 第一部分：产品正式上线
  - `sandbox cloud`宣布上线浏览器自动化服务。
  - 所有创建出来的沙箱，都可以直接使用内置的`browser cli`和相关`skill`来操作网页。
  - 核心意思：沙箱不只是跑代码，也能像 “真人用户” 一样访问和操作网站。

- 第二部分：主要能做什么
  - 可以运行`e2e 测试`，适合做网站功能验证。
  - 可以模拟真人用户登录网站，处理需要账号态的操作。
  - 可以使用`sandbox snapshot`保存凭证和用户状态，方便后续复用。
  - 例子：如果一个测试流程需要先登录后台，再执行一系列页面操作，就可以先登录一次，再把登录态快照保存，之后直接恢复使用。

- 第三部分：延伸出的实际价值
  - 自动化网页操作能力，让 AI Agent 或自动化脚本更容易完成真实任务。
  - 不仅适合测试，也适合需要 “带用户态” 的网页任务，比如登录后抓取数据、执行后台流程等。
  - 本质上是把 “网页交互” 从手动操作，变成可编排、可复用的自动化能力。

- 第四部分：评论区补充信息与案例
  - 有评论认为作者的方法论值得学习：`先找到客户，再帮客户解决问题`，同时兼顾营销和技术分享。

    - `MutationObserver`智能滚动

- 一句话结论
  - 这篇内容重点是在说：`sandbox cloud`让 “可登录、可保存状态、可自动操作网站” 的浏览器自动化能力，变成了沙箱的标准能力，而且这类能力在 AI Agent、测试和真实业务流程中都很实用。

## 产品-最佳实践（1）

### 2026-03-16 08:48:48

可以。基于你给的内容，我建议不要只停留在 “能用 browser cli 自动点网页”，而是把它包装成一个 “可复用、可恢复、可控成本” 的自动化流程。

我用一个具体实例来讲：

**实例：自动化登录 Google Ads / X / Shopify 后台，定时抓取核心数据并执行回归检查**

假设你要做一个 SaaS 运维助手，每天自动登录商家后台，完成 3 件事：

- 登录网站并进入控制台
- 抓取昨天的关键指标
- 检查某个核心流程是否可用，比如 “创建广告”“查看订单”“导出报表”

在`sandbox cloud`这个能力上，这个场景很适合，因为它同时需要：

- 浏览器自动化
- 用户登录态持久化
- 定时复跑
- 出问题时人工接管或回放

**推荐的最佳实践，不是 “每次从零跑一遍”，而是 “首登一次，之后快照复用 + 分层自动化”**

你可以把整个流程设计成 4 层：

- 首次人工辅助登录
- 登录态快照保存
- 日常自动化任务执行
- 失败后的降级和恢复

具体做法如下。

**1. 首次登录：把最难的环节单独处理，不要混在日常任务里**

第一次运行时，很多网站会有：

- 短信验证码
- 邮箱验证码
- 2FA
- 图形验证
- 风控检查

这一步最佳实践是：

- 只做 “登录并到达稳定首页”
- 登录成功后立即创建`snapshot`
- 不要在首次登录脚本里顺手做一堆业务动作

原因很简单：

- 登录失败和业务失败是两类问题
- 分开后更容易定位
- 登录态一旦保存，后续任务可以跳过最脆弱的环节

你可以把它理解成两个任务：

- `bootstrap_login`
- `daily_report_check`

而不是一个巨长的 “万能脚本”。

**2. 用 snapshot 保存凭证和用户态，但把它当成 “会过期的资产” 管理**

你提供的内容里提到`sandbox snapshot`可以备份凭证和用户态，这非常关键。最佳实践是：

- 每个客户、每个环境、每个站点单独一个快照
- 给快照打版本标签，比如`shopify-prod-userA-2025-02`
- 设置刷新机制，不要等失效了才发现

建议这样分：

- 按租户分隔：避免 A 客户的登录态污染 B 客户
- 按用途分隔：采集账号、测试账号、管理员账号不要共用快照
- 定期校验：每天任务开始前先做一次 “登录态健康检查”

比如健康检查只验证：

- 是否还能打开控制台首页
- 是否出现登录页
- 是否出现 “session expired”

如果发现失效：

- 不直接让主任务崩掉
- 标记为`snapshot_expired`
- 进入 “重新登录队列” 或通知人工处理

这比 “任务跑到一半才发现掉登录态” 要稳很多。

**3. 自动化脚本要做 “分层执行”，不要一上来就全量浏览器操作**

你贴的回复里有一个非常有价值的点：  
轻量方式够用时，别急着用重浏览器；复杂场景再降级到浏览器兜底。

基于这个思路，最佳实践是：

- 能直接请求接口或读页面关键文本，就不要全量 DOM 深抓
- 能轻量提取，就不要长时间滚动、展开、渲染
- 只有遇到复杂交互时，再使用完整浏览器自动化

在这个实例里可以这么拆：

**轻量层**
- 打开 dashboard
- 读取几个 KPI 文本
- 判断 “导出按钮” 是否存在
- 判断页面是否有报错提示

**浏览器层**
- 点击筛选器
- 打开日期选择器
- 导出 CSV
- 创建广告 / 创建订单草稿等复杂交互

这样做的好处：

- 更省 token / 更省执行时间
- 页面结构轻微变化时，不容易全部失效
- 浏览器只用在 “必须点击” 的地方

一句话总结：  
**把浏览器当成兜底执行器，而不是默认的唯一执行器。**

**4. 每个自动化任务都要设计 “稳定锚点”，不要依赖脆弱选择器**

很多浏览器自动化最容易死在这：

- 写死`div:nth-child (7) > button`
- 依赖动态 class
- 页面刚加载完就点击
- 看到文本类似就当成功

更稳的做法是：

- 优先找语义化元素：按钮文本、表单标签、ARIA 属性
- 给每一步设置 “成功判据”
- 点击前后都做状态确认

例如 “导出报表” 这一步，不是简单地：

- 点击`Export`

而是要定义为：

- 找到 “Export” 按钮
- 确认按钮可点击
- 点击后等待菜单出现
- 选择 CSV
- 观察下载触发标记或成功 toast
- 若 10 秒内无反馈，截图并记日志

也就是说，自动化不是 “模拟点击”，而是 “验证状态迁移”。

**5. 把 “等待” 设计成业务等待，不要只用固定 sleep**

很多脚本不稳定，是因为大量使用：

- `sleep 3`
- `sleep 5`

最佳实践是等待业务信号：

- URL 变化
- 某个标题出现
- 某个 loading 消失
- 某个按钮从 disabled 变为 enabled
- 某个 toast 出现

比如登录后的等待条件，不要写成：

- 等 8 秒

而应该写成：

- 等待出现 “Dashboard”
- 或 URL 包含`/dashboard`
- 或用户头像出现

这样在网络快时更快，网络慢时也更稳。

**6. 任何涉及登录和快照的流程，都必须做最小权限控制**

既然这个方案会保存用户态和凭证，安全是第一优先级。最佳实践：

- 专门创建自动化账号，不要直接用创始人或管理员主账号
- 权限最小化，只开放必须访问的页面和动作
- 快照按环境隔离，生产和测试绝不混用
- 日志里不要打印 cookie、token、验证码、邮箱链接
- 失败截图也要注意脱敏

如果你是给客户做服务，这一点尤其重要。  
**“能跑” 不是上线标准，“可审计、可隔离、可撤销” 才是上线标准。**

**7. 给失败分类，不要把所有失败都叫 “脚本失败”**

这个实例里，至少要分成 5 类：

- `auth_failed`：登录失败
- `snapshot_expired`：快照过期
- `ui_changed`：页面结构变化
- `network_timeout`：网络超时
- `business_assertion_failed`：业务断言失败，比如 “导出按钮不存在”

为什么这很重要？

因为后续动作不同：

- `auth_failed` → 通知人工重新登录
- `ui_changed` → 提醒维护脚本
- `network_timeout` → 自动重试
- `business_assertion_failed` → 可能是产品真的挂了，应立即告警

如果不分类，你最后只会看到一堆 “失败了”，但不知道该修产品、修脚本，还是修账号。

**8. 把 snapshot 和 e2e 结合起来，做 “有状态回归测试”**

你给的内容里提到可以跑 e2e 测试，这里最实用的做法不是只做匿名用户测试，而是做：

- 已登录用户态下的关键路径测试

比如对一个电商后台，每天跑这几个检查：

- 登录后能否看到订单列表
- 搜索订单是否正常
- 导出报表是否正常
- 新建折扣码是否正常

因为这些流程往往都依赖真实登录态、权限、租户配置。  
`snapshot`的价值就在这里：  
**你不需要每次都处理登录，直接从业务态开始测试。**

这比传统 “每次从登录页开始” 的 e2e 更快，也更接近真实商家使用场景。

**一个更完整的推荐流程**

你可以把整个自动化体系设计成这样：

- 第一次：人工辅助登录，创建快照
- 每天定时：
  - 启动沙箱
  - 恢复快照
  - 做登录态健康检查
  - 执行轻量数据读取
  - 必要时执行浏览器交互
  - 输出结果、截图、关键日志
- 如果失败：
  - 自动分类
  - 可重试的先重试
  - 不可重试的进入人工队列
- 如果登录态过期：
  - 标记快照失效
  - 触发重新登录流程
  - 更新快照版本

**一句话最佳实践**

如果只用一句话概括这个实例上的最佳实践，就是：

**把 sandbox cloud 当成 “持久化用户态的自动化运行环境”，而不是 “临时点网页的脚本容器”；用 snapshot 解决登录成本，用分层执行控制成本，用失败分类保证可运营性。**

用`sandbox cloud + browser cli/skill + snapshot`，做 “需要登录态的网站自动化回归测试”。

**具体实例**

假设你有一个 SaaS 产品，核心路径是：

1. 用户登录
2. 进入控制台
3. 创建一个项目
4. 上传一份 CSV
5. 系统完成解析并展示结果
6. 用户退出登录

你的目标不是 “能跑一次”，而是 “每天稳定跑、出了问题能定位、凭证安全、成本可控”。

---

**推荐实践**

- 先把 “登录” 从 “业务流程测试” 中拆出来，单独做成一次性的认证初始化流程
- 用`snapshot`保存登录后的浏览器状态，只在失效时重新登录，避免每条 e2e 都重复走短信、验证码、OAuth
- 把自动化拆成 “轻交互步骤 + 少量关键断言”，不要一上来全量抓 DOM 或把整个页面转文本
- 优先验证用户真正关心的结果，比如 “项目创建成功”“解析状态变成 completed”，而不是页面上每个像素都一致
- 所有关键步骤都加可观测信息：截图、控制台日志、网络失败日志、最终页面 URL
- 用稳定选择器，例如`data-testid`，不要依赖文案、层级、nth-child

---

**这个实例下的最佳落地方式**

假设你要实现 “已登录用户上传 CSV 并验证解析成功”。

**1. 把流程分成 3 类任务**

- `auth setup`：专门负责登录并生成 snapshot
- `smoke test`：验证最核心主路径，3 到 5 分钟内跑完
- `full regression`：覆盖更多异常分支、权限分支、边界输入

这样做的原因是：
- 登录态失效时，只需要修`auth setup`
- 主链路失败时，定位更快
- 成本不会被大量重复登录放大

---

**2. 登录态管理的最佳实践**

在这个例子里，最容易出问题的是登录。

建议：

- 第一次人工或半自动完成登录
- 登录成功后立即创建一个 “已认证 snapshot”
- 后续测试直接从该 snapshot 启动
- 为 snapshot 设置版本和用途，例如：
  - `prod-admin-auth-v1`
  - `staging-basic-user-auth-v3`
- snapshot 不要混用环境，生产、测试、预发必须分开
- 如果账号有不同权限，按角色分别建 snapshot，不要一个超级管理员跑所有测试

一个好的习惯是：
- “认证状态” 是资产
- “业务测试” 消费这个资产
- 不要把两者耦合在同一个脚本里

---

**3. 页面交互的最佳实践**

以 “上传 CSV 并等待解析完成” 为例，不要写成：

- 打开页面
- sleep 10 秒
- 点某个按钮
- 再 sleep 30 秒
- 看页面有没有那几个字

更好的做法是：

- 等待明确元素出现
- 通过稳定选择器点击
- 上传固定测试文件
- 轮询状态标签从`processing`变成`completed`
- 超时后保留截图和错误日志

关键原则：

- 少用固定等待，优先用显式等待
- 断言 “状态变化”，不要断言 “时间差不多应该好了”
- 文件上传的测试数据要固定且可重复

例如，测试 CSV 应该：
- 行数固定
- 包含已知字段
- 预期输出明确
- 不依赖线上实时数据

---

**4. 凭证和安全的最佳实践**

文里提到用 snapshot 备份凭证和用户态，这里一定要补一层安全规范。

建议：

- snapshot 只保存测试必须的登录态，不要混入个人浏览记录或无关站点会话
- 专门使用测试账号，不要用创始人、管理员真实主账号
- 给测试账号最小权限，只能访问本次测试需要的功能
- 定期轮换账号密码、API key、会话
- snapshot 命名与过期时间明确，过期后自动废弃
- 敏感操作页（付款、删库、发邮件）要默认加保护开关

一句话：
`snapshot 是加速器，不是万能缓存，更不是长期秘钥仓库。`

---

**5. 降低 token 和执行成本的最佳实践**

你给的回复里提到一个很重要的点：重型 DOM 抓取非常耗 token。

在这个实例里，最佳实践是：

- 先走轻量操作路径：点击、输入、读取关键元素文本
- 只在失败或页面结构异常时，才退回到更重的页面分析
- 不要把整个页面 DOM 全量喂给 Agent
- 对断言结果做结构化提取，比如只取：
  - 当前 URL
  - 页面标题
  - 上传任务状态
  - 错误提示文本
- 页面失败时保留 “截图 + 关键日志 + 少量 DOM 片段”，而不是全量页面源码

这会直接带来三点收益：
- 更省 token
- 更快
- 更容易定位问题

---

**6. 让自动化真正稳定的最佳实践**

这个例子里，稳定性比 “能演示” 更重要。

建议你给每条 e2e 设计统一规范：

- 前置条件明确：账号、数据、环境、snapshot 版本
- 输入固定：上传哪个 CSV，大小多少，内容是什么
- 输出明确：成功状态、结果页字段、任务 ID
- 失败产物固定：截图、日志、最终 URL、错误堆栈
- 清理机制明确：测试创建的项目是否删除，何时删除

尤其要避免两类反模式：

- 多条测试共享同一个脏数据环境
- 上一条测试失败后，把环境搞坏，下一条继续跑

最好做到：
- 每次测试创建独立项目名，例如带时间戳或随机后缀
- 测试结束后自动清理
- 清理失败也要记录，但不要静默吞掉

---

**7. 一个更接近生产的推荐流程**

如果把这个案例变成团队可用流程，我会建议：

- 每天凌晨运行一次`auth setup`，验证 snapshot 是否仍有效
- 每次代码合并后运行`smoke test`
- 每晚跑一次`full regression`
- 如果`smoke test`失败：
  - 自动附带截图
  - 输出失败步骤
  - 标注是 “页面问题 / 接口问题 / 登录态问题 / 环境问题”
- 如果是登录态失效：
  - 自动触发重新生成 snapshot
  - 失败后再通知人工处理

这比 “失败了只报红” 更有工程价值，因为你能快速知道：
- 是脚本坏了
- 是页面改了
- 是账号过期了
- 还是后端服务挂了

---

**一份可直接套用的最佳实践模板**

以这个 “CSV 上传解析” 案例，可以整理成下面这套标准：

- 测试目标：验证登录用户可成功上传 CSV 并看到解析完成
- 测试账号：独立测试账号，最小权限

- 选择器规范：统一使用`data-testid`
- 等待策略：显式等待 + 状态轮询，禁用长时间硬编码 sleep
- 测试数据：固定 CSV 样本，可重复、可校验
- 失败留痕：截图、控制台日志、网络错误、最后页面 URL
- 清理策略：删除测试项目与测试文件
- 成本控制：优先轻量交互，失败时再升级为重型页面分析

这不是一条 “新功能上线” 的动态，它更像是在宣布一件事：浏览器，正在从 “人使用软件的入口”，变成 “AI 代理接管世界的执行层”。

- 背后的结构性力量，不是技术炫技，而是 AI Agent 商业化的真实瓶颈发生了转移。大模型本身正在商品化，真正稀缺的不是 “会思考的模型”，而是 “能进入真实网站、跨过登录、保持状态、稳定执行” 的操作闭环。谁控制了这个闭环，谁就更接近下一代 Agent 的基础设施层。

- 热门回复里最有价值的信息，不在 “厉害”“干货”，而在两个细节。第一，`不用单独启动新实例，直接操控当前 Chrome`，这意味着自动化正从 “实验室环境” 进入 “真实用户环境”；第二，`700 token vs 8000 token`，说明竞争核心已经不是 “能不能做”，而是 “谁更贴近浏览器原生语义，谁就更便宜、更稳、更可扩展”。这是一场从 “模型能力竞争” 转向 “上下文压缩效率竞争” 的迁移。
- 但代价也在这里。所谓`snapshot`备份登录态和凭证，本质是在把 “身份” 对象化、可复制化。它提升了效率，也放大了风险：一旦账号态可以被保存、迁移、复用，那么泄漏的就不再只是密码，而是整个 “行为人格”。我们过去保护的是密钥，未来要保护的是 “持续在线的自己”。
- 更深一层看，这类服务会推动互联网进入 “反自动化军备竞赛”。平台会更强地识别 bot、限制异常行为、收紧接口；自动化服务则会更像真人、更分布式、更低噪音。最后被牺牲的，可能是开放 Web 本身：网站为了防代理而变得更封闭，更敌视普通开发者，也更敌视用户自主控制自己的数据与操作。
- 所以它真正提出的，不是 “Agent 能不能帮你点按钮”，而是一个根本问题：当 “用户行为” 被平台化、脚本化、外包给云端代理时，这个系统是在扩展人的能力，还是在抽空人的自主性？如果未来每个人都依赖代理登录、浏览、购买、申请、沟通，那么谁拥有这些代理的默认规则，谁就在重新定义用户意志。

我的判断是：这条产品动态的意义，不在浏览器自动化本身，而在它标志着 AI Agent 进入了 “执行层基础设施竞争” 阶段。接下来比拼的不会只是模型智商，而是三件事：

- 谁能最低成本地接管真实网站
- 谁能最安全地托管用户态与凭证
- 谁能在平台封锁中维持稳定执行

一句话点评：这不是 “AI 会用浏览器了”，而是 “浏览器正在被改造成 AI 的劳动力接口”。真正值得追问的，不是它多强，而是当 “可复制的用户” 成为基础设施时，我们究竟在解放人，还是在把人进一步接口化。
