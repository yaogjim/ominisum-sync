## 正文

#### Automation Agent (Side Panel + Daemon)

Summarize can run as a **网站自动化代理** inside the Chrome side panel. This is **可选的** and **需通过复选框启用** in Options.

Scope:

- **关闭（默认）：** 聊天仅为问答（无工具）。
- **主题：** chat 运行一个具备工具能力的代理，用于网页自动化。

明确排除项（根据产品方向）： **无更新检查器** ， **无教程/欢迎流程** ， **无代理配置** ， **无 API 密钥对话框** 。所有模型调用均经过本地守护进程。

#### Architecture (High Level)

1. **侧边面板** 维护代理循环 + 聊天 UI。
2. **Background** 处理标签页数据、提取和工具执行。
3. **内容脚本** 处理元素选取和原生输入桥接。
4. **守护进程** 提供 `/v1/agent` (SSE 数据块流 + 最终助手消息)

##### Data Flow (Agent Loop)

- 用户在侧边栏发送消息。
- 面板压缩历史并将 `panel:agent` 发送到后台，其中：
- `messages` (pi-ai Message\[\])
- `tools` (names)
- `summary` (可选的当前摘要 markdown)
- 后台构建 `pageContent` 使用最新的提取内容（摘要 + 文字稿/文本 + 元数据）。
- 后台调用守护进程 `POST /v1/agent` (SSE)
- 守护进程流式传输 `chunk` 事件，然后是 `assistant` 事件（可能包含工具调用）。
- Panel 在本地执行工具调用，附加 `toolResult` 消息，并重复执行 `/v1/agent` 直到没有工具调用剩余。

守护进程 **never** 执行工具。它只返回下一条助手消息。

#### Settings + Permissions

##### Settings

`automationEnabled` （布尔类型）位于 `apps/Chrome 扩展/src/lib/设置.ts`

- 选项 UI 提供了开关。
- 当禁用时，工具列表为空，且守护进程使用 **仅聊天** 提示。

##### Optional Permissions

定义在 `apps/chrome-extension/wxt.config.ts` 中，并通过选项请求：

- `debugger` ——是 **native input** 和 **debugger** 工具所必需的。
- `userScripts` – 预留为主要世界脚本执行（当前 REPL 路径不需要）。

###### Chrome: 启用用户脚本（如果需要）

1. `chrome://extensions`
2. Open extension details
3. Enable **Allow User Scripts**
4. Reload the tab

#### Daemon Endpoint

##### POST /v1/agent (SSE)

**Headers**

- `Authorization: Bearer <token>`
- `内容类型: application/json`

**Body**

```shell
{
  "url": "https://...",
  "title": "Page title",
  "pageContent": "<summary + transcript + metadata>",
  "cacheContent": "<transcript/text used for cache key>",
  "messages": [/* pi-ai Message[] */],
  "model": "auto" | "openai/..." | "anthropic/..." | ...,
  "length": "short" | "xl" | "20k" | ...,
  "language": "auto" | "en" | "de" | ...,
  "tools": ["navigate", "repl", "ask_user_which_element", "skill", "debugger"],
  "automationEnabled": true
}
```

**Response (SSE, default)**

```shell
event: chunk
data: { "text": "..." }

event: assistant
data: { /* AssistantMessage */ }

event: done
data: {}

event: error
data: { "message": "..." }
```

```shell
{ "ok": true, "assistant": { /* AssistantMessage */ } }
```

##### POST /v1/agent/history

返回与 `/v1/agent` 相同缓存键的缓存聊天历史。

**Body**

```shell
{
  "url": "https://...",
  "pageContent": "<summary + transcript + metadata>",
  "cacheContent": "<transcript/text used for cache key>",
  "model": "auto" | "openai/..." | "anthropic/..." | ...,
  "length": "short" | "xl" | "20k" | ...,
  "language": "auto" | "en" | "de" | ...,
  "automationEnabled": true
}
```

**Response**

```shell
{ "ok": true, "messages": [/* Message[] */] }
```

##### Model Resolution (Daemon)

- **固定模型** （显式 `model` ）：解析为 `<provider>/<model>` 。提供程序基础 URL 覆盖来自配置/环境变量（OpenAI、Anthropic、Google、xAI、ZAI）。OpenRouter 使用与 OpenAI 兼容的补全功能。
- **自动模型** ：使用现有的自动选择逻辑（ `buildAutoModelAttempts` ），优先使用 API-key 传输方式，当 CLI 可用时则使用 CLI 作为备选方案。
- **合成模型** ：为与 OpenAI 兼容的基础 URL（local/openrouter）创建。
- `maxOutputTokens` 默认值为 2048 或 `maxOutputTokens` 覆盖。
- CLI 模型支持自动回退，也支持通过显式的 `cli/<provider>` 或 `cli/<provider>/<model>` 覆盖。
- 如果守护进程在关键设置或安装变更后仍然提示没有可用模型，请重启或重新安装它，以使保存的环境快照刷新。

#### Page Content Payload

`pageContent` 由最新提取内容构建，包括：

- **摘要** (可选): 当前摘要 Markdown (截断到设置上限)
- **文字记录/文本** ：当可用时为带时间戳的文字记录，否则为提取的文本。
- **元数据** ：URL/标题，来源（ `页面` 与 `URL` ），提取策略，Markdown 提供方，Firecrawl 使用情况，转录提供方 + 缓存状态，媒体时长，字数统计，截断标志。

查看 `buildChatPageContent()` 在 `apps/chrome-extension/src/entrypoints/background.ts` 中的使用情况。

#### Tools

##### 1\) navigate

Navigate the active tab.

Params:

```shell
{ "url": "https://...", "newTab": false }
```

Result:

```shell
{ "finalUrl": "https://...", "title": "...", "tabId": 123 }
```

Notes:

- 使用 `chrome.tabs.update` 或 `chrome.tabs.create` 。
- 等待标签页状态 `complete` (15 秒超时)

##### 2\) repl

在沙箱中执行 JavaScript，使用 `browserjs()` 在页面上下文中运行。

Params:

```shell
{ "title": "...", "code": "..." }
```

Result:

```shell
{ "output": "console/return output", "files": [{ "fileName": "...", "mimeType": "...", "contentBase64": "..." }] }
```

REPL environment:

- 运行在一个 **沙盒化的 iframe** 中（无法访问面板的 DOM）
- 当可用时，使用 `chrome.userScripts.execute` （主世界）。
- 回退到 `chrome.scripting.executeScript` （隔离世界）
- `navigate({ url })` 在 REPL 中可用（始终用于导航）。
- `sleep(ms)` helper.
- 控制台输出被捕获并返回；返回值以 `=> value` 的形式追加。
- `returnFile(name, content, mimeType)` 或 `returnFile({ fileName, content, mimeType })` 将文件附加到工具结果中。

Safety:

- REPL 代码中的导航（ `window.location` 、 `history` 等）被拒绝。请改用 `navigate()` 。

页面上下文助手（通过 `browserjs()` ）：

- 当域名模式匹配活跃的 URL 时，技能库会自动注入。
- 如果授予了 `debugger` 权限，原生辅助工具将被暴露：
- `nativeClick(selector)`
- `nativeType(selector, text)`
- `nativePress(key)`
- `原生按键按下(key)` / `原生按键释放(key)`

##### 3\) ask\_user\_which\_element

显示一个点击选择覆盖层并返回元素元数据。

Params:

```shell
{ "message": "Optional guidance" }
```

Result (example):

```shell
{
  "selector": "#submit",
  "xpath": "//button[1]",
  "text": "Send",
  "tagName": "button",
  "attributes": { "type": "submit" },
  "html": "<button ...>",
  "boundingBox": { "x": 20, "y": 120, "width": 180, "height": 40 }
}
```

Overlay UX:

- 悬停高亮光标下的元素。
- Click selects.
- ↑ / ↓ 向上或向下移动 DOM 树。
- Esc cancels.

##### 4\) skill

CRUD for 特定领域的库 (stored in `chrome.storage.local`).

Storage keys:

- `automation.skills` (名称到技能的映射)
- `automation.skillsSeeded` (一次性默认种子)

Actions:

- `list` (可选地按 URL 过滤)
- `get` （可选地包括库代码）
- `create` / `rewrite`
- `update` (string replacement)
- `delete`

默认技能源自 `apps/chrome-extension/src/automation/default-skills.json` 。

Matching:

- 类 Glob 的域模式（支持 `*` 和 `**` ）
- 匹配是基于主机名 + 路径（例如 `github.com/*/issues` ）。

Notes:

- `update` 用于就地字符串替换；使用 `rewrite` 进行重命名。
- 技能库在 `browserjs()` 中运行，并且必须避免导航。

##### 5\) debugger (optional)

通过 Chrome 调试器在 **主世界** 中运行 JavaScript。 **最后的手段** （显示 Chrome 调试横幅）

Params:

```shell
{ "action": "eval", "code": "..." }
```

Result:

```shell
{ "text": "...", "details": { ... } }
```

##### 6\) summarize

对一个 URL 运行摘要流水线（摘要或仅提取）

Params:

```shell
{
  "url": "https://...",
  "extractOnly": false,
  "format": "text",
  "markdownMode": "readability",
  "model": "openai/gpt-5-mini",
  "length": "short",
  "language": "auto",
  "prompt": "Optional override",
  "timeout": "2m",
  "maxOutputTokens": "2k",
  "noCache": false,
  "firecrawl": "auto",
  "preprocess": "auto",
  "youtube": "auto",
  "videoMode": "auto",
  "timestamps": false,
  "maxCharacters": 120000
}
```

Result (summary):

```shell
{ "output": "..." }
```

Result (extract-only):

```shell
{ "output": "...", "details": { "content": "...", "title": "...", "wordCount": 123, ... } }
```

Notes:

- 仅 URL（使用守护进程 URL 管道）
- 使用 `extractOnly: true` + `format: "markdown"` 来返回提取的 Markdown。
- 当 `format: "markdown"` 时， `markdownMode` 默认值为 `readability` 。

#### 原生输入桥接（调试器权限）

原生输入事件使用 Chrome 调试器协议：

- `browserjs()` 向内容脚本发送消息。
- 内容脚本转发到后台 (`automation:native-input`).
- 后台附加调试器并分发：
- `Input.dispatchMouseEvent` (点击)
- `Input.insertText` (type)
- `输入.dispatchKeyEvent` (按下/按键按下/按键释放)

如果权限缺失，调用失败且工具报告错误。

#### UX Notes

- 自动化功能通过选项复选框选择启用。
- 常规总结流程保持不变。
- 工具结果被视为 **数据** ，而非指令。系统提示仍然要求助手以纯文本形式重复重要的工具衍生信息。
- 工具结果目前在聊天界面中呈现以用于调试；它们未来可能会被隐藏。
- 当对话过程中活动标签页的 URL 发生变化时，面板会追加一个 **导航工具结果** ，其中包含新的 URL、标题和匹配技能。这使代理能够知晓用户驱动的导航。
- 调用 `browserjs()` 的 REPL 执行会显示一个带有 **中止** 操作的小覆盖层；中止会停止当前的代理循环（尽力而为）。

#### Where Things Live

- **守护进程** : `src/daemon/server.ts`, `src/daemon/agent.ts`
- **自动化工具** : `apps/chrome-extension/src/automation/`
- **元素选择器 + 原生输入桥接器** ： `apps/chrome-扩展/src/entrypoints/automation.content.ts`
- **后台代理** : `apps/chrome-extension/src/entrypoints/background.ts`
- **侧边栏代理循环** : `apps/chrome-extension/src/entrypoints/sidepanel/`
- **选项切换** ： `apps/chrome-extension/src/entrypoints/options/`

#### Agent / Daemon 文档精炼解读

##### 一、深度总结

Summarize 的**Automation Agent**是 Chrome 侧边栏里的可选网页自动化代理。

核心机制：

> **侧边栏负责对话与代理循环，后台负责页面数据和工具执行，守护进程负责模型调用。**

###### 1. 启用方式

默认关闭。

- 关闭：普通聊天问答，无工具能力
- 开启：聊天变成可操作网页的 Agent

产品明确不做：

- 更新检查器
- 教程 / 欢迎页
- 代理配置页
- API Key 弹窗

所有模型调用都走本地 daemon。

---

###### 2. 架构分工

| 模块 | 职责 |
|---|---|
| Side Panel | 聊天 UI、代理循环 |
| Background | 标签页数据、页面提取、工具执行 |
| Content Script | 元素选择、原生输入桥接 |
| Daemon | `/v1/agent`模型接口，返回助手消息 |

关键原则：

> **Daemon 不执行工具，只决定下一步；工具永远在本地浏览器执行。**

---

###### 3. Agent 工作流

流程如下：

1. 用户在侧边栏输入消息
2. 侧边栏整理历史，发给后台
3. 后台拼接当前网页内容
4. 后台请求 daemon `/v1/agent`
5. daemon 流式返回文本和助手消息
6. 如果助手要求调用工具，侧边栏本地执行
7. 工具结果追加进对话
8. 重复请求 daemon，直到不再需要工具

这就是一个典型的：

> **“模型决策，本地执行，循环反馈” Agent 模式。**

---

###### 4. 页面上下文

Agent 会把当前页面信息传给模型，包括：

- 页面摘要
- 文本 / 转录内容
- URL、标题
- 提取方式
- 字数、截断状态
- 视频时长、缓存信息等

这让模型不是 “盲聊”，而是基于当前网页理解任务。

---

###### 5. 支持的工具

| 工具 | 作用 |
|---|---|
| `navigate` | 打开或跳转网页 |
| `repl` | 在页面环境中执行 JS |
| `ask_user_which_element` | 让用户点击选择元素 |
| `skill` | 管理特定网站的自动化技能库 |
| `debugger` | 用 Chrome 调试协议执行 JS |
| `summarize` | 对 URL 运行摘要 / 提取流程 |

其中最关键的是：

- `repl`：网页操作核心
- `ask_user_which_element`：解决模型不确定元素的问题
- `skill`：沉淀网站自动化经验
- `debugger`：最后手段，能力强但侵入性更高

---

###### 6. 权限与安全

自动化需要用户显式开启。

可选权限包括：

- `debugger`：原生点击、输入、按键需要
- `userScripts`：用于主世界脚本执行

安全设计包括：

- 工具结果被当作数据，不是指令
- REPL 禁止直接用`window.location`等方式跳转
- 导航必须通过`navigate ()`
- debugger 工具标记为最后手段
- 用户可通过覆盖层选择元素，也可取消

##### 二、深入浅出解读

可以把它理解成一个 “会看网页、会动手、但不直接碰系统核心” 的网页助手。

###### 它像什么？

像一个坐在你浏览器旁边的助理：

1. 先读懂当前网页
2. 根据你的要求想下一步
3. 如果要点按钮、跳页面、填表，就调用工具
4. 操作完再看结果
5. 继续判断下一步

但它不是完全放任模型乱操作。

模型只负责 “想”，真正的 “做” 由浏览器本地工具完成。

---

###### 为什么要 daemon？

Daemon 是模型调用中枢。

好处：

- API Key 不暴露给前端
- 模型选择统一管理
- 可支持 OpenAI、Anthropic、Google、xAI、OpenRouter、本地模型等
- Chrome 扩展更轻量

简单说：

> Chrome 扩展管浏览器，daemon 管 AI。

---

###### 为什么工具不在 daemon 执行？

因为工具操作的是用户浏览器页面。

如果 daemon 直接执行工具，会带来：

- 权限边界混乱
- 安全风险更高
- 页面状态同步困难
- 本地浏览器控制复杂

所以设计成：

> daemon 给建议，浏览器本地执行。

这个边界很重要。

---

###### `skill`的意义

`skill`是自动化能力的积累机制。

比如某个网站结构复杂，Agent 可以保存一段专门适配该网站的脚本逻辑。

以后再访问类似页面，就能复用。

这让 Agent 不只是一次性执行任务，而是可以逐渐形成：

> 网站级经验库。

---

##### 三、辩证思考

###### 优点

1. **架构清晰**
   - 模型、界面、工具、页面脚本分层明确。

2. **安全边界较好**
   - daemon 不直接执行工具。
   - 自动化默认关闭。
   - debugger 是可选权限。

3. **扩展性强**
   - 可接多个模型。
   - 可增加工具。
   - 可沉淀 skill。

4. **适合真实网页任务**
   - 能读页面、点元素、输入文本、跳转、总结 URL。

---

###### 风险

1. **权限风险**
   - 一旦启用 debugger，能力很强，也更敏感。

2. **工具调用误判**
   - 模型可能选错元素、误填表单、误导航。

3. **提示注入风险**
   - 网页内容可能诱导模型执行错误操作。

4. **复杂度高**
   - side panel、background、content script、daemon 多方协作，调试成本不低。

5. **用户信任问题**
   - 自动化代理在浏览器里操作，用户需要知道它 “做了什么”。

---

###### 我的判断

这个设计方向是合理的：

> 它不是把 AI 做成一个 “万能黑盒”，而是做成一个有边界、有工具、有反馈循环的浏览器代理。

但真正落地的关键不在 “能不能自动化”，而在：

- 是否足够透明
- 是否可控
- 是否能防提示注入
- 是否能让用户随时中断
- 是否能清楚展示每一步操作原因

一句话总结：

> 这是一个偏工程化、偏安全边界清晰的网页 Agent 方案；潜力大，但必须把权限、可解释性和用户控制放在第一位。

## 结构化（1）

### 2026-07-22 09:35:08

#### Summarize 自动化代理与守护进程概述

Summarize 可在 Chrome 侧边栏中作为网页自动化代理运行，但该功能默认关闭，需在选项中手动启用。代理循环和工具都由扩展端执行，本地守护进程只负责调用模型、流式返回回答与工具请求，不直接操作网页。

##### 1. 功能范围

- **默认关闭**：聊天仅用于普通问答，不提供工具。
- **启用后**：聊天会变成具备网页导航、元素选择、脚本执行等能力的自动化代理。
- **明确不包含**：
  - 更新检查器
  - 教程或欢迎流程
  - 代理配置
  - API 密钥对话框
- 所有模型调用都通过**本地守护进程**完成。

##### 2. 整体架构

系统由四部分组成：

- **侧边面板**：提供聊天界面，并维护代理循环。
- **后台程序**：处理标签页数据、页面内容提取和工具执行。
- **内容脚本**：负责网页元素选择，以及原生鼠标、键盘输入的桥接。
- **本地守护进程**：提供 `/v1/agent` 接口，以 SSE 方式流式返回文本和最终助手消息。

核心原则是：**守护进程只决定下一步做什么，真正的网页工具由 Chrome 扩展在本地执行。**

##### 3. 代理运行流程

1. 用户在侧边栏发送消息。
2. 面板压缩对话历史，并向后台发送：
   - `messages`：对话消息
   - `tools`：可使用的工具名称
   - `summary`：可选的当前页面摘要
3. 后台根据最新提取结果构建 `pageContent`，包括摘要、文字稿或正文及元数据。
4. 后台调用守护进程的 `POST /v1/agent`。
5. 守护进程通过 SSE 依次返回：
   - `chunk`：流式文本片段
   - `assistant`：完整助手消息，可能带有工具调用
   - `done`：结束
   - `error`：错误信息
6. 若助手要求使用工具，侧边面板在本地执行，并把结果作为 `toolResult` 加回对话。
7. 面板继续请求 `/v1/agent`，直到没有剩余工具调用。

##### 4. 设置与权限

###### 自动化开关

设置项为 `automationEnabled`：

- `false`：工具列表为空，守护进程使用纯聊天提示。
- `true`：启用自动化代理及相关工具。

###### 可选权限

- **`debugger`**：原生点击、输入以及 debugger 工具所必需。
- **`userScripts`**：为主世界脚本执行预留；当前 REPL 路径不一定需要。

如需启用 Chrome 用户脚本，可进入：

1. `chrome://extensions`
2. 打开扩展详情
3. 启用 **Allow User Scripts**
4. 重新加载网页标签页

##### 5. 守护进程接口

###### `POST /v1/agent`

用于生成代理的下一条消息。主要请求字段包括：

- 页面信息：`url`、`title`
- 页面内容：`pageContent`
- 缓存键内容：`cacheContent`
- 对话：`messages`
- 模型：`model`
- 输出长度：`length`
- 语言：`language`
- 工具列表：`tools`
- 自动化状态：`automationEnabled`

支持的工具名称示例：

```json
[
  "navigate",
  "repl",
  "ask_user_which_element",
  "skill",
  "debugger"
]
```

默认采用 SSE 响应，也可以返回包含完整 `assistant` 消息的 JSON。

###### `POST /v1/agent/history`

用于读取与当前缓存键对应的历史对话，返回：

```json
{
  "ok": true,
  "messages": []
}
```

##### 6. 模型选择机制

守护进程支持三类模型解析方式：

- **固定模型**：显式指定为 `&lt;provider>/&lt;model>`，如 OpenAI、Anthropic、Google、xAI、ZAI。
- **自动模型**：使用现有自动选择逻辑，优先尝试 API Key 调用；CLI 可用时作为后备。
- **合成模型**：为兼容 OpenAI API 的基础地址创建，例如本地模型或 OpenRouter。

其他规则：

- OpenRouter 使用与 OpenAI 兼容的补全接口。
- 默认 `maxOutputTokens` 为 **2048**，也可单独覆盖。
- CLI 模型支持自动回退，也可显式指定：
  - `cli/&lt;provider>`
  - `cli/&lt;provider>/&lt;model>`
- 如果修改关键设置或安装环境后仍提示无可用模型，应重启或重装守护进程，以刷新已保存的环境快照。

##### 7. 页面内容载荷

`pageContent` 由最新提取结果组成，主要包括：

- **当前摘要**：可选的 Markdown，并按设置上限截断。
- **文字稿或正文**：
  - 有媒体文字稿时使用带时间戳的文字稿；
  - 否则使用网页提取文本。
- **元数据**：
  - URL、标题
  - 页面来源与 URL 来源
  - 提取策略
  - Markdown 提供方
  - 是否使用 Firecrawl
  - 转录服务及缓存状态
  - 媒体时长
  - 字数
  - 是否被截断

##### 8. 六类主要工具

###### 8.1 `navigate`：网页导航

用于更新当前标签页或新建标签页。

```json
{
  "url": "https://example.com",
  "newTab": false
}
```

执行后返回最终 URL、页面标题和标签页 ID。系统会等待页面加载完成，超时时间为 **15 秒**。

###### 8.2 `repl`：运行 JavaScript

在沙盒 iframe 中执行 JavaScript，并可通过 `browserjs()` 在页面上下文中操作。

主要能力：

- 捕获控制台输出和返回值。
- 使用 `sleep(ms)` 等待。
- 使用 `navigate({ url })` 导航。
- 使用 `returnFile(...)` 返回生成的文件。
- 返回文件时包含文件名、MIME 类型和 Base64 内容。

执行优先级：

1. `chrome.userScripts.execute`，在主世界运行；
2. 不可用时回退到 `chrome.scripting.executeScript`，在隔离世界运行。

安全限制：

- 禁止通过 `window.location`、`history` 等方式导航。
- 必须使用 `navigate()`。
- REPL 沙盒无法访问侧边面板 DOM。

如果授予了 `debugger` 权限，还可调用：

- `nativeClick(selector)`
- `nativeType(selector, text)`
- `nativePress(key)`
- 原生按键按下与释放

###### 8.3 `ask_user_which_element`：让用户选择元素

该工具会在页面上显示点击选择层：

- 鼠标悬停时高亮元素。
- 点击确认选择。
- `↑` / `↓`：在 DOM 树中向上或向下移动。
- `Esc`：取消。

返回信息包括：

- CSS 选择器
- XPath
- 元素文本和标签名
- 属性
- HTML
- 元素位置和大小

例如，可返回按钮 `#submit`，以及其宽高和页面坐标。

###### 8.4 `skill`：管理特定网站技能

技能保存在 `chrome.storage.local`，用于为特定网站注入自动化辅助代码。

支持操作：

- `list`
- `get`
- `create`
- `rewrite`
- `update`
- `delete`

匹配规则类似 Glob，支持 `*` 和 `**`，并根据“主机名 + 路径”匹配。例如：

```text
github.com/*/issues
```

注意：

- `update` 用于原地字符串替换。
- 重命名应使用 `rewrite`。
- 技能代码会在 `browserjs()` 中运行，不能自行导航。

###### 8.5 `debugger`：主世界脚本执行

通过 Chrome 调试器在页面主世界中执行 JavaScript，例如：

```json
{
  "action": "eval",
  "code": "document.title"
}
```

这是**最后手段**，因为执行时 Chrome 会显示调试提示横幅。

###### 8.6 `summarize`：摘要或提取 URL 内容

对指定 URL 运行摘要流水线，支持：

- 生成摘要
- 只提取正文
- 输出文本或 Markdown
- 指定模型、语言、长度和提示词
- 设置超时、最大输出 Token、缓存、Firecrawl、YouTube、视频模式和时间戳

重要参数示例：

- `timeout: "2m"`
- `maxOutputTokens: "2k"`
- `maxCharacters: 120000`
- `extractOnly: true`
- `format: "markdown"`

若要直接获得提取后的 Markdown，可使用：

```json
{
  "url": "https://example.com",
  "extractOnly": true,
  "format": "markdown"
}
```

当输出格式为 Markdown 时，`markdownMode` 默认采用 `readability`。

##### 9. 原生输入桥接

原生点击和键盘输入通过 Chrome 调试器协议完成：

1. `browserjs()` 向内容脚本发送请求。
2. 内容脚本转发给后台。
3. 后台附加调试器并调用：
   - `Input.dispatchMouseEvent`：点击
   - `Input.insertText`：输入文字
   - `Input.dispatchKeyEvent`：按键按下或释放

如果未授予 `debugger` 权限，调用会失败并返回工具错误。

##### 10. 用户体验与安全原则

- 自动化功能必须由用户在选项中主动启用。
- 普通摘要流程不受影响。
- 工具结果被视为**数据，而不是指令**，以降低工具输出诱导模型执行错误操作的风险。
- 系统要求助手用普通文本复述关键工具结果。
- 工具结果目前会显示在聊天界面中，便于调试，未来可能隐藏。
- 如果用户在对话中手动切换页面，面板会自动加入一条导航工具结果，其中包含新 URL、标题和匹配技能。
- REPL 调用 `browserjs()` 时会显示带“中止”按钮的小型覆盖层；中止会尽力停止当前代理循环。

##### 11. 主要代码位置

- **守护进程**：`src/daemon/server.ts`、`src/daemon/agent.ts`
- **自动化工具**：`apps/chrome-extension/src/automation/`

- **后台代理**：`apps/chrome-extension/src/entrypoints/background.ts`
- **侧边栏代理循环**：`apps/chrome-extension/src/entrypoints/sidepanel/`
- **选项开关**：`apps/chrome-extension/src/entrypoints/options/`

## 口播总结（1）

### 2026-08-03 01:21:40

#### 主旨概览

这份材料介绍了 Summarize 的可选网站自动化代理：它运行在 Chrome 侧边面板中，能够理解当前网页、调用工具并完成导航、元素选择和页面操作。你将了解它的整体架构、代理循环、模型调用方式、六类工具、安全边界，以及权限和使用体验。

#### 首先，自动化功能默认关闭

核心结论是：Summarize 原本的聊天和总结功能保持不变，网站自动化必须由用户主动开启。

在默认状态下，侧边栏只是普通问答，不会获得任何自动化工具。用户需要在选项页面勾选开关，才能让聊天变成具备工具能力的代理。这里的“代理”，可以理解为一个会反复思考、调用工具、读取结果，再继续行动的助手。

产品也明确排除了一些功能，包括更新检查、教程或欢迎流程、代理配置页面，以及 API 密钥对话框。

更重要的是，无论是否开启自动化，所有模型请求都会经过本地守护进程。所谓“守护进程”，就是一项在本机后台持续运行、负责连接模型服务的程序。

#### 接下来，理解四层架构

核心结论是：整个系统分成侧边面板、扩展后台、内容脚本和本地守护进程四层，各自负责不同工作。

首先，侧边面板负责聊天界面和代理循环。它保存对话，接收模型提出的工具调用，并决定是否继续下一轮。

其次，扩展后台负责获取标签页数据、整理网页内容，并真正执行一部分工具。

再次，内容脚本运行在网页附近，主要处理元素选择，以及原生鼠标和键盘输入的桥接。

最后，本地守护进程提供代理接口，调用所选模型并返回下一条助手消息。

这里最需要记住的边界是：守护进程永远不直接执行网页工具。它只告诉侧边面板下一步应该做什么。真正的工具调用由扩展在本地完成。

#### 代理循环如何运转

核心结论是：代理通过“模型提出动作、本地执行动作、再把结果交回模型”的循环完成任务。

用户先在侧边栏发送消息。面板会压缩历史记录，再把对话、可用工具名称，以及可选的当前摘要发送给扩展后台。

后台随后整理当前页面内容。这些内容可能包括已有摘要、视频文字稿或网页正文，以及页面标题、网址和提取方式等元数据。整理完成后，后台向本地守护进程发送请求。

守护进程通过 SSE 返回结果。SSE，也就是“服务器发送事件”，可以理解为服务器一边生成，一边把文字片段持续推送给界面。它先发送若干文本片段，再发送完整的助手消息。助手消息里可能包含工具调用。

如果模型要求调用工具，侧边面板就在本地执行，把结果追加为一条工具结果消息，然后再次请求守护进程。这个过程不断重复，直到模型不再提出新的工具调用。

如果用户自己切换了当前标签页的网址，面板还会补充一条导航结果，告诉代理新的网址、标题和匹配到的技能。这样，代理不会因为用户手动跳转而失去上下文。

#### 设置、权限和接口

核心结论是：自动化由一个布尔开关控制，而更敏感的能力还需要额外的 Chrome 权限。

当自动化被关闭时，工具列表为空，守护进程也会使用纯聊天提示。开启后，系统才会向模型开放相应工具。

调试器权限主要用于原生点击、输入和调试器工具。另一项用户脚本权限，则为在网页的主执行环境中运行脚本预留。当前的 REPL，也就是交互式 JavaScript 执行工具，并不一定依赖这项权限。如果需要启用用户脚本，用户要在 Chrome 扩展详情中允许它，并重新加载页面。

守护进程的主要入口是代理接口。请求中可以携带当前网址、标题、页面内容、聊天消息、模型、输出长度、语言、工具列表，以及自动化是否开启。默认响应是刚才提到的 SSE 流，也可以返回一次性的完整助手消息。

另一个历史接口会按照相同的缓存键，返回已经缓存的聊天记录。这样，同一页面和内容对应的对话有机会继续使用，而不必完全重新开始。

#### 模型如何选择

核心结论是：系统既支持明确指定模型，也支持自动选择和命令行回退。

如果用户明确指定模型，系统会把它解析成“服务提供商加模型名称”的形式。支持的来源包括 OpenAI、Anthropic、Google、xAI 和 ZAI，也可以覆盖这些服务的基础地址。OpenRouter 则使用与 OpenAI 兼容的调用方式。

如果选择自动模型，守护进程会按照现有逻辑逐个尝试。它优先使用 API 密钥方式；如果本机存在可用的命令行工具，也可以把命令行模型作为备选。

系统还支持为本地服务或 OpenRouter 这类兼容 OpenAI 接口的地址创建合成模型。默认最大输出量是两千零四十八个 token。Token 可以粗略理解为模型处理文本时使用的基本片段，不完全等同于汉字或单词。

如果关键设置或安装发生变化后，守护进程仍然提示没有可用模型，材料建议重启或重新安装守护进程，让它保存的环境快照得到刷新。

#### 页面内容包含什么

核心结论是：代理看到的不是单一网页正文，而是一份经过整理、可能被截断的页面内容包。

这份内容包首先可以包含当前摘要，并按照设置的上限截断。接下来是带时间戳的文字稿；如果没有文字稿，就使用提取出的网页文本。

它还会携带元数据，例如网址、标题、内容来自当前页面还是指定网址、使用了哪种提取策略、由谁生成 Markdown、是否调用 Firecrawl、转录服务和缓存状态、媒体时长、字数，以及内容是否被截断。

这些信息的意义在于，模型不仅能读到内容，还能判断内容从哪里来、是否完整，以及提取过程用了什么方式。

#### 六类自动化工具

核心结论是：代理的能力主要由六类工具组成，分别负责导航、运行脚本、选择元素、管理技能、底层调试和独立总结。

首先是导航工具。它可以在当前标签页打开网址，也可以新建标签页。执行后会等待页面加载完成，最长等待十五秒，然后返回最终网址、标题和标签页编号。

第二是 REPL 工具。它可以在沙箱中执行 JavaScript，并通过页面上下文助手操作网页。沙箱意味着代码与侧边面板的界面隔离，不能直接访问面板本身。

REPL 可以捕获控制台输出和返回值，也能生成文件并附加到工具结果中。为了安全，代码不能直接修改页面地址，也不能通过浏览器历史记录偷偷导航，必须使用专门的导航函数。

如果授予调试器权限，REPL 还能使用原生点击、原生输入和原生按键功能。执行期间，页面会显示一个带“中止”操作的小覆盖层。用户中止后，系统会尽力停止当前代理循环。

第三是元素选择工具。当代理无法确定用户指的是哪个按钮或输入框时，可以显示一个点击选择层。用户把鼠标移到元素上时，系统会高亮显示；点击即可选择。上下方向键可以沿网页的元素树移动，退出键可以取消。结果会包含选择器、文字、标签类型、属性、网页结构片段和位置尺寸。

第四是技能工具。这里的“技能”指针对特定网站或领域预先编写的脚本库，保存在 Chrome 本地存储中。代理可以列出、读取、创建、修改、重写或删除技能。技能通过类似通配符的域名和路径规则匹配，例如针对某个网站的议题页面生效。匹配后，技能会自动注入页面助手，但技能本身必须避免执行导航。

第五是调试器工具。它能通过 Chrome 调试器，在网页的主执行环境中运行 JavaScript。由于使用时会显示 Chrome 的调试提示横幅，因此被定位为最后手段，而不是常规工具。

第六是总结工具。它可以对一个网址运行完整的总结流程，也可以只提取内容。参数可以控制输出格式、提取方式、模型、长度、语言、超时、缓存、视频处理和最大字符数等。如果只想取得提取后的 Markdown，可以开启“仅提取”，并选择 Markdown 格式。

#### 原生输入和安全边界

核心结论是：原生点击和键盘输入通过 Chrome 调试器协议完成，而且权限缺失时必须明确失败。

具体流程是，页面助手先向内容脚本发送消息，内容脚本再转发给扩展后台。后台连接调试器后，分别发送鼠标点击、文本插入和按键事件。

这种方式比简单修改网页元素更接近真实用户输入，因此适合某些依赖原生事件的网站。不过，如果用户没有授予调试器权限，调用会失败，工具也会返回错误，不会静默绕过限制。

另一个重要安全原则是，工具结果只被视为数据，而不是新的指令。系统提示仍要求助手用普通文字重述由工具获得的重要信息。这有助于降低网页内容或工具输出干扰代理行为的风险。

目前，聊天界面会显示工具结果，方便调试。未来这些结果可能会被隐藏。

#### 最后，源码职责如何分布

核心结论是：代码按照守护进程、自动化工具、内容脚本、扩展后台、侧边面板和选项页面分开组织。

守护进程的服务器和代理逻辑位于项目的 daemon 目录。自动化工具集中在 Chrome 扩展的 automation 目录。元素选择和原生输入桥接由 automation 内容脚本负责。

后台代理位于扩展的 background 入口，侧边面板代理循环位于 sidepanel 入口，自动化开关则位于 options 入口。这种分工与前面介绍的四层架构基本一致，方便分别维护模型调用、网页执行和用户界面。

#### 关键结论回顾

最后，最值得记住的有五点。

第一，网站自动化是可选功能，默认关闭；不开启时，Summarize 仍然只是普通聊天和总结工具。

第二，代理采用循环执行方式。模型提出工具调用，本地扩展执行，再把结果交回模型。守护进程本身永远不操作网页。

第三，系统分为侧边面板、扩展后台、内容脚本和本地守护进程四层，职责和权限边界清晰。

第四，代理主要拥有导航、脚本执行、元素选择、技能管理、调试器和网址总结六类工具。敏感的原生输入与调试能力需要额外权限。

第五，页面和工具返回的内容都被当作数据处理，而不是可信指令。再加上禁止脚本私自导航、调试器作为最后手段等限制，共同构成了这套自动化系统的基本安全边界。

## 深度解读（1）

### 2026-09-18 00:41:00

#### 浏览器 Agent 的关键不在“会操作”，而在权限、状态与执行边界

这份文档最值得关注的，不是它提供了导航、点击、输入和执行 JavaScript 等工具，而是它对浏览器 Agent 做了一个明确分层：**模型负责决定下一步，浏览器端负责真正执行，守护进程永不直接调用工具。**

具体流程是：侧边栏维护对话与代理循环，后台整理当前页面内容并请求本地守护进程；模型返回工具调用后，扩展在本地执行，再把结果送回模型，直到不再需要工具。这个设计把“推理”和“行动”拆开了。其意义是，模型服务可以替换或回退，真正掌握标签页、DOM 和调试器权限的始终是浏览器扩展，而不是远端模型接口。

##### Agent 产品首先是一个受控运行时

文档支持 OpenAI、Anthropic、本地兼容接口、OpenRouter 和 CLI 回退，但模型选择反而不是架构核心。真正决定体验的，是一套运行时能力：上下文压缩、页面提取、工具调度、执行结果回传、导航状态同步、超时与中止，以及权限不足时的降级。

这修正了一个常见误解：浏览器 Agent 的竞争力并不主要来自更长的提示词或更强的模型，而来自**能否持续维持“模型认知的页面”与“用户实际看到的页面”之间的一致性**。这里已经做了几项针对性设计：每次请求带上最新摘要、正文或转录、元数据；用户主动跳转页面时补充导航结果；REPL 中禁止直接修改 `window.location`，要求统一通过 `navigate()`。它们都在减少模型绕过状态管理、导致轨迹失控的可能。

但这一问题尚未彻底解决。提取文本、缓存历史和实时 DOM 可能处于不同时间点，现代网页还会在 URL 不变时大幅更新界面。对高可靠任务，后续需要验证的不只是“操作成功率”，而是每一步执行前能否重新确认关键状态，例如按钮是否仍对应原对象、提交内容是否发生变化。

##### 权限渐进开放，比一次性全能更可信

自动化默认关闭；开启后才暴露工具。普通脚本优先，原生输入需要额外的 debugger 权限，调试器直接执行则被定义为会出现浏览器警示的“最后手段”。这种能力分级符合真实用户的信任形成过程：先允许读取与低风险操作，再逐步开放模拟输入和主世界执行。

文档还强调“工具结果是数据，而不是指令”，显然是在防范网页内容诱导 Agent 执行恶意操作。不过这更像一条提示词层面的原则，而非完整安全边界。页面文本本身也会进入模型上下文，REPL 还能把代码带入页面环境。若用于登录态网站、后台系统或交易场景，还需要更明确的能力策略：高风险动作确认、域名白名单、敏感字段隔离、操作审计，以及对技能代码来源的校验。

##### “技能库”可能是最有产品价值的抽象

技能按域名与路径自动匹配并注入，可以把通用 Agent 变成针对 GitHub、后台系统或垂直网站的半结构化操作器。它位于两种方案之间：比纯视觉或临时 DOM 探索更稳定，又比为每个网站硬编码完整流程更便宜。

真正值得验证的机会不是“用户是否想保存提示词”，而是：**高频网站是否存在一组可复用、可维护、能显著降低失败率的操作知识。**如果成立，技能的版本管理、权限声明、失败诊断和可信分发，会比技能编辑本身更重要。浏览器 Agent 最终可能不是一个无所不能的聊天框，而是一个以通用模型为调度器、以受控工具和领域技能为可靠性来源的自动化平台。
