#### Sandbank

> AI Agent 统一沙箱 SDK — 一次编写，多云运行。

Sandbank 提供统一的 TypeScript 接口来创建、管理和编排云端沙箱。切换 Provider 无需修改业务代码。

**[官网](https://sandbank.dev)** \| **English** \| **日本語**

#### 为什么选择 Sandbank?

AI Agent 需要隔离的执行环境，但每家云厂商的 API 都不一样 — Daytona、Fly.io、Cloudflare Workers 各有一套。Sandbank 将它们统一到一个接口后面：

```
import { createProvider } from '@sandbank.dev/core'
import { DaytonaAdapter } from '@sandbank.dev/daytona'

const provider = createProvider(new DaytonaAdapter({ apiKey: '...' }))
const sandbox = await provider.create({ image: 'node:22' })

const result = await sandbox.exec('echo "Hello from the sandbox"')
console.log(result.stdout) // Hello from the sandbox

await provider.destroy(sandbox.id)
```

把 `DaytonaAdapter` 换成 `FlyioAdapter` 或 `CloudflareAdapter` — 代码零改动。

Sandbank 内置编排层，支持多 Agent 实时协作。 **Relay** 负责沙箱间的消息传递和共享上下文。

```
import { createSession } from '@sandbank.dev/core'

const session = await createSession({
  provider,
  relay: { type: 'memory' },
})

// 在隔离沙箱中启动 Agent
const architect = await session.spawn('architect', {
  image: 'node:22',
  env: { ROLE: 'architect' },
})

const developer = await session.spawn('developer', {
  image: 'node:22',
  env: { ROLE: 'developer' },
})

// 共享上下文 — 所有 Agent 均可读写
await session.context.set('spec', { endpoints: ['/users', '/posts'] })

// 等待所有 Agent 完成
await session.waitForAll()
await session.close()
```

在沙箱内部，Agent 使用 `@sandbank.dev/agent` ：

```
import { connect } from '@sandbank.dev/agent'

const session = await connect() // 自动读取 SANDBANK_* 环境变量

session.on('message', async (msg) => {
  if (msg.type === 'task') {
    // 执行任务...
    await session.send(msg.from, 'done', result)
  }
})

await session.complete({ status: 'success', summary: '完成了 5 个 API 端点' })
```

#### 快速开始

```
# 安装
pnpm add @sandbank.dev/core @sandbank.dev/daytona  # 或 @sandbank.dev/flyio、@sandbank.dev/cloudflare

# 配置 Provider
export DAYTONA_API_KEY=your-key
```

```
import { createProvider } from '@sandbank.dev/core'
import { DaytonaAdapter } from '@sandbank.dev/daytona'

const provider = createProvider(
  new DaytonaAdapter({ apiKey: process.env.DAYTONA_API_KEY! })
)

// 创建沙箱
const sandbox = await provider.create({
  image: 'node:22',
  resources: { cpu: 2, memory: 2048 },
  autoDestroyMinutes: 30,
})

// 执行命令
const { stdout } = await sandbox.exec('node --version')

// 文件操作
await sandbox.writeFile('/app/index.js', 'console.log("hi")')
await sandbox.exec('node /app/index.js')

// 清理
await provider.destroy(sandbox.id)
```

#### 设计原则

1. **最小接口，最大互操作** — 只做真正的最大公约数 (exec + files + lifecycle)
2. **显式优于隐式** — 不自动 fallback、不缓存、不隐式重试
3. **能力检测，而非假实现** — 不支持就报错，不返回假数据
4. **幂等操作** — 销毁已销毁的沙箱不报错
5. **完全解耦** — Provider 层和 Session 层独立，自由组合

## 结构化（1）

### 2026-03-16 08:36:31

这篇文章主要介绍了 Sandbank：一个给 AI Agent 使用的 “统一云沙箱 SDK”。它的核心价值是把不同云厂商的沙箱能力封装成同一套 TypeScript 接口，让开发者 “一次编写，多云运行”。

- **1. 产品定位：解决多云沙箱接口不统一的问题**
  - AI Agent 需要隔离执行环境，但 Daytona、Fly.io、Cloudflare Workers 等平台 API 各不相同。
  - Sandbank 把这些差异统一到同一个接口后面，开发者只需更换适配器，不必改业务代码。
  - 例子：把`DaytonaAdapter`换成`FlyioAdapter`或`CloudflareAdapter`，其余创建沙箱、执行命令、销毁沙箱的代码都不用变。

- **2. 整体架构：核心层 + 适配器层 + 底层平台**
  - 上层是你的应用或 AI Agent。
  - 中间是 Sandbank 的核心模块：
    - `@sandbank.dev/core`：统一 Provider 接口
    - `@sandbank.dev/skills`：Skill 注册和注入
    - `@sandbank.dev/agent`：沙箱内 Agent 客户端
    - `@sandbank.dev/relay`：多 Agent 通信中枢
  - 下层是各类适配器：
    - `@sandbank.dev/daytona`
    - `@sandbank.dev/flyio`
    - `@sandbank.dev/cloudflare`
    - `@sandbank.dev/boxlite`
  - 最底层对应真实运行环境：Daytona、Fly.io Machines、Cloudflare Workers、以及自托管 Docker 的 BoxLite。

- **3. 支持的能力：基础功能统一，扩展功能按需检测**
  - 所有 Provider 都必须支持 5 个基础操作：
    - 创建 / 销毁沙箱
    - 列出沙箱
    - 执行命令
    - 读写文件
    - Skill 注入
  - 扩展能力是 “可选的”，需要运行时检测后再使用，例如：
    - `volumes`：持久卷
    - `port.expose`：对外暴露端口
    - `exec.stream`：实时输出 stdout/stderr
    - `snapshot`：状态快照与恢复
    - `terminal`：交互式 Web 终端
    - `sleep`：休眠与唤醒
  - 重要细节：
    - Cloudflare 的 volumes 需要额外启用`storage`配置。
    - Cloudflare 保留了**3000 端口**作为控制面板，用户可用端口范围是**1024–65535，但不包括 3000**。

- **4. 不同 Provider 的特性差异：统一接口下仍保留平台特点**
  - Daytona：完整 VM，冷启动约**10 秒**。
  - Fly.io：Firecracker 微虚拟机，冷启动约**3–5 秒**。
  - Cloudflare：V8 隔离 + 容器，冷启动约**1 秒**，速度最快。
  - BoxLite：Docker 容器，冷启动约**2–5 秒**，适合自托管。
  - 文件 I/O 方式也不同：
    - Daytona、Cloudflare：原生 SDK
    - Fly.io、BoxLite：通过`exec` + base64
  - 区域能力也不同：
    - Daytona、Fly.io：多区域
    - Cloudflare：全球边缘
    - BoxLite：自托管

- **5. 多 Agent 协作：内置编排和消息通信能力**
  - Sandbank 不只是单个沙箱管理工具，还支持多 Agent 协同工作。
  - 通过`createSession`可以同时启动多个角色不同的 Agent，比如：
    - `architect`
    - `developer`
  - Agent 之间可以共享上下文，例如把接口规范`['/users', '/posts']`放进共享 context，所有 Agent 都能读写。
  - 沙箱内部的 Agent 可通过`@sandbank.dev/agent`自动读取`SANDBANK_*`环境变量，接收任务、发送结果，并最终回报完成状态。
  - 例子中，Agent 最后汇报：**“完成了 5 个 API 端点”**。

- **6. 快速开始：创建、执行、写文件、销毁**
  - 安装后先配置 Provider，例如 Daytona 需要设置`DAYTONA_API_KEY`。
  - 创建沙箱时可指定：
    - 镜像：`node:22`
    - CPU：**2**
    - 内存：**2048 MB**
    - 自动销毁时间：**30 分钟**
  - 然后可以在沙箱内执行命令、写入文件、运行脚本，最后再销毁沙箱。
  - 这说明 Sandbank 的使用流程比较直接，适合快速接入 AI Agent 执行环境。

- **7. 开发与测试：覆盖单元测试、一致性测试和真实集成测试**
  - 项目支持多种开发命令：
    - `pnpm test`：单元测试
    - `pnpm test:conformance`：跨 Provider 一致性测试
    - `pnpm typecheck`：类型检查
  - 集成测试会调用真实 API，并通过环境变量启用：
    - Daytona：`DAYTONA_API_KEY`
    - Fly.io：`FLY_API_TOKEN`、`FLY_APP_NAME`
    - Cloudflare：`E2E_WORKER_URL`
  - 这表明项目不仅关注接口统一，还强调不同平台行为的一致性验证。

- **8. 设计原则：追求最小共性、显式行为和可组合性**
  - 只抽象 “最大公约数” 能力：`exec + files + lifecycle`，避免过度封装。
  - 强调 “显式优于隐式”：不自动 fallback、不缓存、不隐式重试。
  - 不支持的能力就直接报错，而不是伪造结果。
  - 销毁操作要求幂等：即使沙箱已经销毁，也不报错。
  - Provider 层和 Session 层完全解耦，可以自由组合。
  - 许可证为**MIT**。

### 2026-03-16 08:37:53

可以。基于你提供的 Sandbank 文档，我用一个 “AI 自动生成并验证一个 Node.js API 服务” 的实例，给出一套更贴近落地的最佳实践。

**具体实例**

假设你要做一个 “云端 AI 开发代理”：

- `architect` Agent 负责生成接口设计
- `developer` Agent 负责写代码
- `tester` Agent 负责运行测试
- 底层沙箱希望既能跑在 Daytona，也能切到 Fly.io 或 Cloudflare
- 你的目标不是 “某家云厂商跑通”，而是 “业务代码尽量不随 Provider 改动”

这个场景正好是 Sandbank 最擅长的：统一生命周期、命令执行、文件读写，再用能力检测处理差异能力。

**推荐做法**

- 先只依赖最小公约数能力：`create`、`exec`、`read/writeFile`、`destroy`；把业务主流程建立在这些接口上，保证换 Provider 时无需改核心逻辑。
- 把可选能力当增强项，不当主路径：比如端口暴露、卷、流式输出、快照，只能通过能力检测后再启用，不能直接假设存在。
- 让每个 Agent 的职责单一：`architect`只产出规范，`developer`只改代码，`tester`只验证结果；共享状态放到`session.context`，不要靠约定俗成的文件名串联一切。
- 所有沙箱都设置生命周期边界：如`autoDestroyMinutes`、CPU / 内存限制、超时控制，防止 AI 任务失控导致成本失控。
- 清理动作写进`finally`：Sandbank 设计里销毁是幂等的，这意味着你应该默认 “无论成功失败都清理”。

**一个更好的实现方式**

```ts
import {
  createProvider,
  createSession,
  withPortExpose,
} from '@sandbank.dev/core'
import { DaytonaAdapter } from '@sandbank.dev/daytona'

const provider = createProvider (
  new DaytonaAdapter ({
    apiKey: process.env.DAYTONA_API_KEY!,
  })
)

async function runTask () {
  const session = await createSession ({
    provider,
    relay: { type: 'memory' },
  })

  try {
    await session.context.set ('spec', {
      name: 'user-service',
      endpoints: ['/users', '/users/:id'],
      stack: 'node',
      testCommand: 'pnpm test',
    })

    const architect = await session.spawn ('architect', {
      image: 'node:22',
      env: { ROLE: 'architect' },
      resources: { cpu: 1, memory: 1024 },
      autoDestroyMinutes: 20,
    })

    const developer = await session.spawn ('developer', {
      image: 'node:22',
      env: { ROLE: 'developer' },
      resources: { cpu: 2, memory: 2048 },
      autoDestroyMinutes: 20,
    })

    const tester = await session.spawn ('tester', {
      image: 'node:22',
      env: { ROLE: 'tester' },
      resources: { cpu: 2, memory: 2048 },
      autoDestroyMinutes: 20,
    })

    await session.waitForAll ()

    // 只有在支持时才暴露端口
    const maybePort = withPortExpose?.(developer)
    if (maybePort) {
      const exposed = await maybePort.expose (8080)
      console.log ('preview url:', exposed.url)
    }
  } finally {
    await session.close ()
  }
}

runTask ().catch (console.error)
```

**这段实例上的最佳实践**

- `provider`初始化只出现一次；业务层只依赖`createProvider (...)`返回的统一接口，不把 Daytona/Fly.io/Cloudflare 的差异泄漏到业务代码里。
- `spawn`时明确资源配额；不要让所有 Agent 默认拿同样的 CPU / 内存，因为 “写代码” 和 “跑测试” 的资源需求明显不同。
- `session.context`只放结构化信息，如接口列表、技术栈、验收标准；不要把大体积构建产物塞进去，共享上下文应是 “协作契约”，不是文件系统替代品。
- `withPortExpose`作为增强能力使用；如果不可用，系统仍能完成 “生成 + 测试” 的主任务。
- `finally -> session.close ()`是必须的；这比 “任务结束后再记得销毁” 可靠得多。

**为什么这是 Sandbank 风格的最佳实践**

Sandbank 的设计原则里最重要的几条，在这个例子里都能落地：

- 最小接口，最大互操作：主流程只依赖`exec/files/lifecycle`
- 显式优于隐式：不偷偷 fallback，不猜测某个能力可能可用
- 能力检测，而非假实现：端口、卷、快照只在确认支持时启用
- 完全解耦：Session 协作层和 Provider 层分开，未来替换底层云不用重写 Agent 编排

**容易踩坑的地方**

- 把 Provider 特性写死在业务里：例如代码里直接写 “Cloudflare 一定支持快照” 或 “Daytona 一定有某个目录结构”，这样一换 Provider 就碎。
- 把流式输出当成通用能力：文档里`exec.stream`不是全 Provider 支持，所以日志采集要支持 “流式” 和 “非流式” 两条路径。
- 假设端口 3000 一定能暴露：文档明确提到 Cloudflare 保留了`3000`，如果你做 Web 预览，默认用`8080`或从可配置端口池里选。
- 把文件 I/O 性能视为一致：不同 Provider 的文件实现路径不同，像 Fly.io/BoxLite 的某些路径可能经由`exec (base64)`，大量小文件写入会放大延迟。
- 忘记幂等清理：AI 任务常常中途失败，清理逻辑不应依赖 “前一步一定成功”。

**在这个实例上进一步细化的工程实践**

- 配置隔离：把 API Key、Provider 类型、镜像名、资源配额都放环境变量或配置文件，不写死在代码里。
- 工作目录约定：统一让所有 Agent 在`/workspace`或`/app`下工作，减少跨镜像行为差异。
- 命令可重复：`exec`里的命令尽量写成幂等脚本，比如先检测依赖、再安装、再测试，避免半执行状态难恢复。
- 错误分层：区分 “Provider 创建失败”“Agent 执行失败”“测试未通过”，不要全部只报一个`task failed`。
- 一致性测试优先：在你自己的业务仓库里也做类似`conformance`的思想验证，至少确保核心流程在两个 Provider 上都能跑通。

**如果我要给这个实例定一套推荐架构**

- 核心编排层：只使用 Sandbank 统一接口
- 能力适配层：单独封装`volumes`、`port.expose`、`snapshot`
- Agent 协作层：统一通过`session.context`和消息通信
- Provider 配置层：根据环境选择 Daytona / Fly.io/ Cloudflare
- 清理与审计层：统一记录沙箱 ID、创建时间、销毁状态、任务结果

这样做的好处是：你切换 Provider 时，改的是 “配置和能力适配”，不是 “业务主流程”。

**一句话结论**

在这个 “AI 自动生成并验证 Node.js API” 的实例里，Sandbank 的最佳实践不是 “把所有高级能力都用上”，而是 “先用统一最小接口跑通主链路，再把能力检测后的增强功能逐层叠加”。

## 综合-启发一下（1）

### 2026-03-16 08:38:50

这份内容的核心价值，不在 “又一个沙箱 SDK”，而在它把 AI Agent 基础设施里最容易被供应商锁定、最难统一抽象的一层，做成了 “稳定业务接口 + 可变底层实现” 的分离。

- 启发
  - 真正值得产品化的，不是某个云能力本身，而是 “跨云差异的吸收层”；Sandbank 把执行环境从资源采购问题，变成接口设计问题。
  - AI Agent 时代的基础设施，关键不是功能多，而是 “最小可用公约数” 是否足够稳定；`exec + files + lifecycle`这个选择很克制，也很有商业判断。
  - 多 Agent 协作的重点，不只是让多个 agent 存在，而是让它们在隔离环境中共享上下文、交换任务、独立完成；这更接近 “组织系统” 而不是 “单点工具”。
  - “能力检测而非假实现” 是一个很强的产品哲学：不为了统一体验而伪装一致性，而是显式暴露差异，让上层系统自己做策略决策。
  - 它提示了一个普遍规律：在 AI 基础设施领域，最有机会沉淀长期价值的，不是模型调用层，而是执行、状态、权限、通信这些更贴近生产系统的层。

- 高价值信息深挖
  - 抽象边界选得很准：统一的是 Provider 接口，不强行统一所有能力。这意味着它避免了 “抽象泄漏后全部失效” 的常见中间层陷阱。
  - 能力系统是关键设计点：`withVolumes`、`withPortExpose`这类运行时能力检测，本质上是在做 “渐进增强”，而不是 “最低标准绑死所有 Provider”。
  - Provider 对比表透露出真实 trade-off：
    - Daytona/Fly.io 更像传统计算资源，适合稳定执行和更强环境控制。
    - Cloudflare 启动快、边缘近，但能力有约束，适合高响应、轻状态场景。
    - BoxLite 是重要的兜底层，意味着产品不仅服务云，也服务私有化 / 本地部署诉求。
  - Relay + Agent 组合，实际上把 “沙箱” 从单机执行容器，升级成 “可编排的 agent runtime”；这比简单的远程 exec 平台更接近未来 AI 工作流基础设施。
  - 设计原则很适合商业系统：
    - 不隐式 fallback：避免生产事故时定位困难。
    - 不隐式重试：避免成本失控和副作用放大。
    - 幂等销毁：对自动化系统特别重要。
    - Provider 层与 Session 层解耦：利于不同客户按需采购复杂度。
  - 一个容易被忽略的点是 “一致性测试”。跨 Provider SDK 里，真正难的不是写适配器，而是长期维持行为一致；`test:conformance`比很多功能本身更有护城河价值。

- 可迁移清单
  - 如果你在做 AI 产品平台，可以直接迁移这套设计思路：
  - 先定义最小稳定内核：只保留 3-5 个所有底层都能可靠实现的核心动作。
  - 把差异能力做成显式 capability，而不是塞进统一接口里假装一致。
  - 上层编排和底层执行解耦：编排层负责任务、状态、协作；执行层负责资源、文件、命令。
  - 对 “不可支持” 保持诚实：宁可报错，也不要 silent fallback。
  - 给每个适配器建立 conformance test，而不是只写单元测试。
  - 在 API 设计上默认幂等，尤其是 create/destroy/retry 相关动作。
  - 多 Agent 设计优先考虑共享上下文和通信协议，而不是先堆更多角色模板。
  - 为私有化 / 本地环境保留一层自托管适配器，这是 B2B 商业化的重要前提。
  - 文档中直接暴露能力矩阵，让客户一开始就知道边界，减少售前和接入摩擦。

- 反方与张力
  - 最大公约数策略的代价，是你可能永远无法充分吃到某个 Provider 的独特红利；统一接口会天然抑制极致优化。
  - “显式能力差异” 对工程师友好，但对普通产品团队不一定友好；他们往往希望 “接上就能跑”，不想理解能力矩阵。
  - 多 Agent + 沙箱 + relay 的系统虽然强，但复杂度会上升很快；一旦进入生产，排障、观测、成本控制会成为新门槛。
  - 不自动 fallback、不隐式重试是正确的工程哲学，但在商业产品里也会带来体验张力：用户可能会觉得系统 “不够聪明”。
  - 跨云中间层常见风险是 “看起来降低锁定，实际上提高了迁移成本”：如果业务大量依赖 Sandbank 的 session/relay/skills 语义，最终可能从云厂商锁定变成框架锁定。
  - 统一抽象还有一个现实问题：计费模型、冷启动、文件 I/O、端口暴露这些差异，最后会在 SLA 和成本结构上重新浮现，抽象并不能真正消灭它们。

- 情境化落地
  - 如果你是做 AI Coding/Dev Agent 产品
    - 可以把 Sandbank 式架构理解成 “执行层标准件”。
    - 你的产品重点不该放在怎么连某家云，而该放在任务拆解、上下文管理、协作协议、结果校验。
    - 最适合的路径是：先用最小 Provider 跑通，再逐步开放 volumes、snapshot、stream 等高级能力。
  - 如果你是做企业内部 AI 平台
    - 这类方案很适合做成统一执行底座：研发、数据、运营 agent 共用同一套隔离运行时。
    - 商业上可形成 “中心治理 + 多业务接入” 模式，特别适合权限、审计、成本归集要求高的组织。
    - 优先补上的不是更多 provider，而是审计日志、资源配额、身份映射、可观测性。
  - 如果你是做 AI 工作流 / 自动化产品
    - 可以借鉴它的 capability 设计，把外部工具接入分成 “核心动作” 和 “增强动作”。
    - 不要一开始追求全兼容，而要先把 80% 场景跑通，再通过能力声明扩展边界。
  - 如果你在看商业机会
    - Sandbank 这类项目的机会不只在 SDK 本身，而在其上层可能长出来的托管编排、企业控制台、策略治理、可观测与成本管理。
    - 也就是说，SDK 可能是获客入口，真正高毛利层往往是运行托管、团队协作和企业治理。
  - 如果你要自己做类似产品
    - 第一阶段：只做统一执行接口和 2-3 个 provider 适配。
    - 第二阶段：加入 capability system 和 conformance tests。
    - 第三阶段：做 session/relay，把单 agent 运行时升级为多 agent 协作系统。
    - 第四阶段：补企业能力，形成商业闭环。
