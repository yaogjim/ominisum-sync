## 正文

**陈成**

写了个小工具 codexthropic，一个本地 Node 代理，把 Anthropic Messages API 翻译成 OpenAI Codex Responses API。实际效果：你可以用 Claude Code 直接连 OpenAI 的 GPT-5.5 后端写代码。

做这个的动机很直接——Claude Code 是目前最好的 AI coding agent 前端，但它只说 Anthropic 协议。Codex 后端（GPT-5.5）的代码能力也很强，但只有 OpenAI 自家的 Codex CLI 能用。codexthropic 在中间做协议翻译，让两边的长处接上。

技术上要处理的东西比想象中多：

1）SSE 流式事件双向映射。Anthropic 的 message\_start / content\_block\_start / content\_block\_delta / content\_block\_stop / message\_delta / message\_stop 这套事件模型，和 Codex 的 response.created / response.output\_text.delta / response.output\_item.added / response.completed 完全是两套语言，逐事件翻译，还要维护 block index 状态机。

2）Tool Use 完整映射。Anthropic 的 tools 定义转成 Codex 的 function tools，tool\_use block 转成 function\_call item，tool\_result 转成 function\_call\_output。tool\_choice 也要映射：auto→auto，any→required，none→none，指定工具名→{type:function, name}。

3）多轮推理连续性——这个最巧妙。Codex 的 reasoning.encrypted\_content 是加密的思维链状态，需要在多轮工具调用间传递才能保持推理连贯。方案是把它塞进 Anthropic thinking block 的 signature 字段，Claude Code 会原样回传 thinking blocks，下一轮请求时再从 signature 还原成 Codex 的 reasoning input item。链式思维跨轮次不断。

4）OAuth 认证。读 \~/.codex/auth.json，JWT 过期前 60s 自动刷新，并发请求用 single-flight 合并避免重复刷新。刷新失败有 30s 冷却防止锁死风暴。收到 401 会 force-refresh 重试一次。如果 Codex CLI 在后台轮换了 refresh\_token，代理会检测磁盘文件变化自动重载，不用重启。原子写入用 tmp+fsync+rename 保证不写坏 auth 文件。

5）reasoning effort 翻译。Anthropic 的 thinking.budget\_tokens 按阈值映射：&lt;4000→low，&lt;16000→medium，&lt;32000→high，≥32000→xhigh。adaptive thinking 和 output\_config.effort:max 也走 xhigh。

模型映射：所有 Claude 模型名（opus/sonnet/haiku）统一映射到 gpt-5.5，因为 ChatGPT 账号的 Codex 后端目前只接受这个模型。gpt-\* 和 o\* 开头的模型名直接透传。

用法极简：npx codexthropic@latest 启动代理，另一个终端 ANTHROPIC\_BASE\_URL=http://127.0.0.1:8765 ANTHROPIC\_API\_KEY=any claude 即可。零运行时依赖，纯 node:http 实现，88 个离线测试覆盖各种边界情况。需要 Node 20+ 和 codex login 完成过的本地认证。

#### codexthropic：让 Claude Code 直接调用 OpenAI Codex 后端

##### 一句话总结

作者做了一个本地 Node.js 代理工具 **codexthropic**，把 **Anthropic Messages API** 翻译成 **OpenAI Codex Responses API**，让用户可以用 **Claude Code 作为前端**，连接 **OpenAI GPT-5.5 / Codex 后端** 来写代码。

##### 背景与动机

Claude Code 被认为是当前体验很好的 AI 编程 Agent 前端，但它只能使用 Anthropic 协议。

与此同时，OpenAI Codex / GPT-5.5 的代码能力也很强，但主要通过 OpenAI 自家的 Codex CLI 使用。

**codexthropic 的价值在于：把 Claude Code 的交互体验和 OpenAI Codex 的模型能力连接起来。**

##### 核心能力

###### 1. 协议翻译

工具在本地启动一个 Node 代理，将 Anthropic 的消息格式和 OpenAI Codex 的响应格式互相转换。

例如：

- Anthropic 的流式事件
- Codex 的流式事件
- 工具调用
- 多轮上下文
- 推理状态

都会被代理层自动映射。

###### 2. 支持工具调用

它能把 Anthropic 的 tool use 转换成 Codex 的 function calling。

包括：

- 工具定义转换
- 工具调用转换
- 工具结果转换
- tool choice 策略映射

这意味着 Claude Code 原本依赖的工具调用机制，在 Codex 后端上也能继续工作。

###### 3. 保持多轮推理连续性

这是比较巧妙的一点。

Codex 有加密的推理状态 `reasoning.encrypted_content`，需要在多轮调用中传递，才能保持连续推理。

codexthropic 的做法是：  
把这个状态塞进 Anthropic 的 `thinking block signature` 字段里，让 Claude Code 原样带回，下一轮再恢复给 Codex。

这样可以实现跨轮次推理不断链。

###### 4. 处理本地 Codex 认证

工具会读取本地 `~/.codex/auth.json`，复用用户已经登录过的 Codex 认证信息。

它还支持：

- JWT 自动刷新
- 并发刷新合并
- 401 后强制刷新重试
- 检测本地 token 文件变化
- 原子写入，避免认证文件损坏

##### 使用方式

使用很简单：

```bash
npx codexthropic@latest
```

然后在另一个终端运行：

```bash
ANTHROPIC_BASE_URL=http://127.0.0.1:8765 ANTHROPIC_API_KEY=any claude
```

要求：

- Node.js 20+
- 本地已完成 `codex login`
- 使用 Claude Code 客户端

##### 产品与商业意义

这个工具本质上是一个 **协议适配层**。

它说明了一个趋势：  
AI Agent 的前端体验、模型能力、工具生态正在逐渐解耦。

未来用户可能不再被某一家厂商的完整闭环绑定，而是可以自由组合：

- 最好的 Agent 前端
- 最强的模型后端
- 最适合自己的工具链
- 本地化的认证和执行环境

##### 关键价值

- 降低 Claude Code 与 OpenAI Codex 之间的使用壁垒
- 让开发者复用熟悉的 Claude Code 工作流
- 提供更灵活的模型后端选择
- 体现了 API 代理和协议转换在 AI 工具生态中的重要性

##### 总结

codexthropic 是一个面向开发者的小工具，但它背后的意义不小：  
它把不同 AI 编程生态之间的协议墙打通，让用户可以把 **Claude Code 的产品体验** 和 **OpenAI Codex 的模型能力** 组合起来使用。

##### 2. 最重要的洞见

###### 洞见 1：最好的 AI 产品，未必来自“最强模型”，而可能来自“最强前端 + 最强后端”的重组

###### **核心观点：**  
> Claude Code 被认为是优秀的 AI coding agent 前端，而 GPT-5.5/Codex 后端代码能力很强；`codexthropic` 的价值不是创造新模型，而是把两个生态的优势接起来。

**为什么重要：**  
很多人默认 AI 产品竞争是模型能力竞争，但这篇文章暴露了另一个更现实的层面：  
- 前端 agent 体验是一种能力；
- 后端模型推理/代码能力是一种能力；
- 协议适配和状态管理也是一种能力。

当这些能力被拆开后，真正的创新可能来自**重新组合**，而不是从零构建。

**反常识之处：**  
常见认知是：  
> Anthropic 的工具只能用 Anthropic 后端，OpenAI 的工具只能用 OpenAI 后端。

但这里的判断是：  
> 只要协议、事件流、工具调用、推理状态可以被映射，不同厂商的产品边界就不是铁板一块。

**可迁移价值：**  
这适用于很多领域：

- SaaS：把 A 产品的交互层接到 B 产品的数据层；
- 企业系统：用中间层打通多个封闭系统；
- AI 应用：选择“最佳组件组合”，而不是押注单一厂商；
- 个人工具链：不要只问“哪个工具最好”，而要问“哪些工具组合后最好”。

**我应该记住什么：**  
> 在生态割裂的地方，协议翻译器往往是高杠杆工具。

###### 洞见 2：真正难的不是“接口转发”，而是“语义等价”

###### **核心观点：**  
> `codexthropic` 看似只是一个本地 Node 代理，但核心难点在于把 Anthropic 和 Codex 两套完全不同的事件模型、工具调用模型、推理状态模型翻译成语义上连续的体验。

**为什么重要：**  
普通 API 代理只是转发请求；高级代理需要理解双方的抽象模型。

例如文章中提到的几个关键点：

- Anthropic 的 SSE 事件：  
  `message_start / content_block_start / content_block_delta / content_block_stop / message_delta / message_stop`

- Codex 的 SSE 事件：  
  `response.created / response.output_text.delta / response.output_item.added / response.completed`

这不是字段名替换，而是两套状态机的对齐。

**反常识之处：**  
很多人会低估“胶水层”的复杂度，以为中间代理只是：

```text
A 请求 → 改几个字段 → B 响应
```

但真实情况是：

```text
A 的交互语义 → 中间状态机 → B 的交互语义
```

其中任何一个状态、索引、工具调用、流式事件错位，都会破坏 agent 的连续体验。

**可迁移价值：**  
这对系统集成、AI infra、企业软件都有启发：

> 集成的核心不是 API 兼容，而是行为兼容。

一个优秀的适配层，需要处理：

- 协议转换；
- 状态维护；
- 错误恢复；
- 认证续期；
- 并发控制；
- 边界测试；
- 上游变化的容错。

**我应该记住什么：**  
> 低价值代理转发数据，高价值代理翻译语义。

---

###### 洞见 3：跨轮推理连续性的关键，不是“保存聊天记录”，而是“保存模型内部推理状态的可传递载体”

###### **核心观点：**  
> Codex 的 `reasoning.encrypted_content` 是加密的思维链状态，需要在多轮工具调用之间传递；作者把它塞进 Anthropic `thinking block` 的 `signature` 字段，让 Claude Code 原样回传，从而实现跨轮推理连续。

**为什么重要：**  
这是全文最有技术含金量的细节。

很多人理解多轮对话时，只想到保存上下文文本。但 agent 场景里，尤其涉及工具调用和推理链延续时，仅保存可见对话是不够的。

这里真正重要的是：

```text
用户消息 + 工具结果 + 可见上下文
≠
完整推理状态
```

Codex 需要额外的 `reasoning.encrypted_content` 来保持推理连续。  
如果这个状态在协议转换中丢失，模型可能“看似继续对话”，但实际已经失去内部推理线索。

**反常识之处：**  
常见认知是：

> 多轮对话只要把历史 message 带上就行。

文章隐含的判断是：

> 对高级 agent 来说，历史文本只是上下文的一部分；隐藏状态的传递同样关键。

**可迁移价值：**  
这可以迁移到很多系统设计中：

- AI agent：不要只持久化对话，要持久化执行状态；
- 工作流系统：不要只记录步骤结果，要记录中间决策状态；
- 分布式系统：不要只传输数据，还要传输 continuation token；
- 产品设计：看似“无状态”的体验，背后常常依赖精心维护的状态链。

**我应该记住什么：**  
> 高级 AI agent 的连续性，本质上是状态连续性，不只是文本连续性。

---

###### 洞见 4：一个小工具是否可靠，关键看它是否处理“无聊但致命”的边界问题

###### **核心观点：**  
> 文章大量篇幅写认证刷新、并发合并、401 重试、refresh token 轮换、原子写入、离线测试，这些不是亮点功能，却决定工具能不能长期稳定使用。

**为什么重要：**  
很多开源小工具失败，不是因为主路径不通，而是因为边界条件一多就崩：

- token 过期；
- 并发刷新；
- refresh token 被其他进程更新；
- auth 文件写坏；
- 401 后无限重试；
- 多个请求同时触发刷新风暴。

作者对 OAuth 的处理说明这个工具不是 demo，而是工程化工具。

尤其这几个细节很关键：

- JWT 过期前 60 秒自动刷新；
- single-flight 合并并发刷新；
- 刷新失败后 30 秒冷却，避免风暴；
- 401 后强制刷新并重试一次；
- 检测磁盘 auth 文件变化并自动重载；
- tmp + fsync + rename 原子写入；
- 88 个离线测试覆盖边界。

**可迁移价值：**  
判断一个工具是否成熟，不要只看它的核心功能是否跑通，而要看它如何处理：

```text
认证、并发、失败、重试、状态污染、文件一致性、测试覆盖
```

**我应该记住什么：**  
> 工程质量通常不体现在 happy path，而体现在异常路径。

##### 3. 底层逻辑

###### **逻辑一：生态边界不是由品牌决定的，而是由协议和状态机制决定的**

- **表层现象：**  
  Claude Code 只能接 Anthropic 协议，Codex 后端只能通过 OpenAI 工具使用。

- **深层原因：**  
  各厂商产品之间的隔离，很多时候不是能力不可互通，而是协议、认证、事件模型和状态管理不兼容。

- **推导结论：**  
  只要能翻译协议、映射工具调用、传递推理状态，就可以重组不同生态的优势能力。

---

###### **逻辑二：AI agent 的核心体验依赖连续状态，而不只是模型单次输出质量**

- **表层现象：**  
  多轮工具调用中，需要传递 Codex 的 `reasoning.encrypted_content`。

- **深层原因：**  
  Agent 在执行复杂任务时，不只是生成文本，而是在持续维护目标、计划、工具结果和隐含推理链。

- **推导结论：**  
  未来 AI infra 的关键能力之一，是对“推理状态”的封装、迁移、恢复和兼容。

---

###### **逻辑三：集成工具的护城河在边界条件，而非主路径功能**

- **表层现象：**  
  文章强调 token 刷新、single-flight、401 重试、文件原子写入、离线测试等细节。

- **深层原因：**  
  主路径转发很容易做，但真实使用环境里，失败、并发、状态漂移和上游变化才是主要风险。

- **推导结论：**  
  一个适配层能否成为长期可用的基础设施，取决于它对异常路径的工程化处理能力。

| AI 编程体验可以由不同厂商的前后端拼出来 | Claude Code 就该配 Claude，Codex 就该配 OpenAI CLI | 通过协议翻译，Claude Code 可以连接 OpenAI Codex 后端 | 不要把产品边界等同于能力边界 |

## 结构化（1）

### 2026-05-03 02:09:13

##### 主旨概括

陈成发布了一个本地 Node 代理工具 **codexthropic**，可以把 **Anthropic Messages API** 转换为 **OpenAI Codex Responses API**。它的核心价值是：让用户能用 **Claude Code 这个优秀的 AI 编程前端**，直接连接 **OpenAI GPT-5.5 / Codex 后端** 来写代码。

---

##### 1. 工具定位：连接 Claude Code 和 OpenAI Codex

- **codexthropic** 是一个本地运行的 Node 代理。
- 它负责在中间做协议翻译：
  - 前端：Claude Code，只支持 Anthropic 协议。
  - 后端：OpenAI Codex / GPT-5.5，代码能力强，但通常只能通过 OpenAI 自家的 Codex CLI 使用。
- 通过这个代理，用户可以把两者优势结合起来：

> 用 Claude Code 的交互体验 + OpenAI GPT-5.5 的代码能力。

---

##### 2. 核心技术难点：协议和事件模型完全不同

工具需要处理的不只是简单转发，而是完整协议转换。

###### SSE 流式事件映射

Anthropic 和 OpenAI Codex 的流式事件模型不同，需要逐个事件翻译。

- Anthropic 事件包括：
  - `message_start`
  - `content_block_start`
  - `content_block_delta`
  - `content_block_stop`
  - `message_delta`
  - `message_stop`

- Codex 事件包括：
  - `response.created`
  - `response.output_text.delta`
  - `response.output_item.added`
  - `response.completed`

此外，还要维护 **block index 状态机**，确保流式输出顺序和结构正确。

---

##### 3. Tool Use 映射：支持工具调用

codexthropic 完整支持工具调用映射。

主要转换包括：

- Anthropic 的 `tools` 定义 → Codex 的 `function tools`
- Anthropic 的 `tool_use block` → Codex 的 `function_call item`
- Anthropic 的 `tool_result` → Codex 的 `function_call_output`

`tool_choice` 也会对应转换：

| Anthropic | Codex |
|---|---|
| `auto` | `auto` |
| `any` | `required` |
| `none` | `none` |
| 指定工具名 | `{type:function, name}` |

---

##### 4. 多轮推理连续性：保留加密思维链状态

这是作者认为最巧妙的部分。

- Codex 有一个 `reasoning.encrypted_content` 字段，用于保存加密的推理状态。
- 这个状态需要在多轮工具调用之间持续传递，否则推理会断裂。
- codexthropic 的做法是：
  - 把 Codex 的加密推理内容塞进 Anthropic 的 `thinking block` 的 `signature` 字段。
  - Claude Code 会原样回传这些 thinking blocks。
  - 下一轮请求时，再从 `signature` 中恢复为 Codex 的 reasoning input item。

这样就能实现：

> 多轮对话和工具调用中，模型的推理状态保持连续。

---

##### 5. OAuth 认证：自动刷新和容错处理

codexthropic 会读取本地认证文件：

```bash
~/.codex/auth.json
```

认证机制包括：

- JWT 过期前 **60 秒** 自动刷新。
- 并发请求使用 **single-flight** 合并，避免重复刷新 token。
- 刷新失败后有 **30 秒冷却时间**，防止反复失败造成请求风暴。
- 收到 `401` 后会强制刷新并重试一次。
- 如果 Codex CLI 在后台轮换了 `refresh_token`，代理会检测磁盘文件变化并自动重载，无需重启。
- 写入 auth 文件时使用：
  - 临时文件 `tmp`
  - `fsync`
  - `rename`

以保证认证文件不会被写坏。

---

##### 6. reasoning effort 映射：按 token 预算转换推理强度

Anthropic 的 `thinking.budget_tokens` 会被映射到 Codex 的 reasoning effort：

| Anthropic thinking.budget_tokens | Codex reasoning effort |
|---|---|
| `< 4000` | `low` |
| `< 16000` | `medium` |
| `< 32000` | `high` |
| `≥ 32000` | `xhigh` |

另外：

- `adaptive thinking`
- `output_config.effort:max`

也会映射为 `xhigh`。

---

##### 7. 模型映射规则

由于 ChatGPT 账号的 Codex 后端目前只接受 `gpt-5.5`，所以工具做了统一映射：

- 所有 Claude 模型名都会映射到：

```text
gpt-5.5
```

包括：

- `opus`
- `sonnet`
- `haiku`

而以下模型名会直接透传：

- `gpt-*`
- `o*`

---

##### 8. 使用方式：启动简单，依赖少

使用步骤很简单：

###### 启动代理

```bash
npx codexthropic@latest
```

###### 另一个终端启动 Claude Code

```bash
ANTHROPIC_BASE_URL=http://127.0.0.1:8765 \
ANTHROPIC_API_KEY=any \
claude
```

运行要求：

- Node.js **20+**
- 已经执行过 `codex login`，完成本地认证
- 工具本身：
  - **零运行时依赖**
  - 使用纯 `node:http` 实现
  - 有 **88 个离线测试** 覆盖边界情况
