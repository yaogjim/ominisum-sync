## 分析要点

- **核心高价值点**：Harness Engineering 的核心不是继续替 Agent 编排信息，而是赋予其自主获取反馈的工具，同时用沙箱、权限、测试和流程边界防止失控。
- **留存建议**：长期保留（文章提供了从 Prompt 到 Context 再到 Harness 的清晰工程演进框架，并结合多个 Agent 工程案例讨论自主性、反馈与边界设计，具备较高方法论和长期参考价值。）

**知识要点**

- Prompt Engineering 主要优化静态单次输入，适合短任务，但难以处理动态展开的多步任务。
- Context Engineering 的核心是用程序化方式管理多步任务中的信息流转，包括检索、压缩、反馈注入和上下文选择。
- Harness Engineering 强调为 Agent 构建运行环境，让模型自主调用工具、获取反馈并判断下一步行动。
- 自主 Agent 必须配套能力边界，例如沙箱隔离、CI 次数限制、文件权限、结构化测试和架构约束。
- Agent 工程的重点正在从模型能力本身转向环境设计、反馈循环、控制系统和评估治理。

**行动项**

- 梳理现有 LLM 应用中哪些逻辑仍是硬编码 context 编排，评估是否可交给 Agent 自主决策。
- 为 Agent 工作流设计可快速返回的反馈工具，如 lint、测试、日志、浏览器状态和代码检索。
- 基于 Agent 实际失败模式倒推边界设计，而不是仅依赖 prompt 约束。
- 在代码类 Agent 场景中引入沙箱、权限控制、结构化测试和最多重试次数等保险机制。
- 将 Prompt、Context、Harness 三层能力分开评估，避免把 runtime 能力误认为 Harness 设计。

**yan5xu**

### 从 Prompt 到 Harness：如何理解大语言模型工程

虽然 LLM 应用的历史始于 2022 年 ChatGPT 问世，但工程实践已经从 Prompt Engineering，经历 Context Engineering，发展到如今的 Harness Engineering。

想要彻底理解 Harness Engineering，就必须回到前面两者，理解为什么旧的做法不够用了，新的做法解决了什么，又卡在了哪里。

太长不看

- Prompt Engineering：任务是静态的，人手工优化单次输入。局限：解决不了多步任务。
- Context Engineering：任务是动态展开的，程序按预设规则编排步与步之间的信息流转。局限：人硬编码的规则限制了模型的自主能动性。
- Harness Engineering：模型足够强了，放手让它自主获取反馈、自主判断，同时框定能力边界作为保险。

---

#### Prompt Engineering：对着🔮许愿的时代

2022 年底 ChatGPT 上线，所有人第一次面对同一个问题：怎么让这个东西给出有用的回答？

没有人知道规则。你对模型说一句话，它给你一个回答，但没人能确切解释为什么这么问就行、那么问就不行。于是大家开始试：换措辞、加前缀、调语气，看看哪种说法能得到更好的结果。

这个时期出了不少今天看来相当魔幻的事情。有人发现在 prompt 末尾加一句"这对我的职业生涯非常重要"，模型的输出质量就会提升。有人发现说"请一步步思考"比直接问答案靠谱得多。还有人试出"你是一个拥有 20 年经验的资深工程师"比"你是一个工程师"效果好，于是所有人都开始给模型编简历，年限越长越好，最好再加个"世界顶级"。

这些尝试逐渐沉淀出一套实践：Few-shot、Chain-of-Thought、Role assignment、Output format。GitHub 上涌现了大量 prompt 模板库，awesome-chatgpt-prompts 成了最热的 repo 之一。大家交换 prompt 的方式像交换咒语，这条咒语能召唤出好的代码，那条咒语能让翻译更地道。

这些技巧确实有效。CoT 在当时能把推理任务的准确率拉高十几个百分点。一个精心设计的 prompt 和一个随手写的 prompt，输出质量可能差两个等级。

但 Prompt Engineering 的局限性也很明显：它本质上是单次任务的优化。一封邮件、一段翻译、一个函数，你写好 prompt，发出去，看结果，不满意改措辞重来。虽然 ChatGPT 也支持多轮对话，但人还是在逐轮审核每一次输出，任务是短的、一次性的，人有足够精力逐条检查。

然后模型开始支持工具调用了。任务从"问一个问题"变成了"跑一个流程"。这时候你发现，措辞再完美，如果模型看到的信息是错的或者不够的，输出就是错的。

瓶颈从"怎么问"移到了"给它看什么"。

---

#### Context Engineering：当任务不再是一句话能说清的

Prompt Engineering 时代，任务是静态的。写一封邮件、翻译一段话、解释一个概念，你在发出 prompt 的那一刻就完整地知道自己要什么，也完整地知道模型需要看到什么。

但真实世界的任务很少是静态的。

你让 agent 修一个 bug。一开始你只知道"用户报了个 bug"。Agent 搜了日志，才发现是支付模块的问题。读了支付模块的代码，才定位到具体的函数。改了那个函数，LSP 报了三个新的 type error，才发现还有关联的调用方要改。改完跑测试，两个 pass 一个 fail，才知道还有一个边界情况没处理。

每一步的输出决定了下一步该做什么、该看什么。任务的全貌不是一开始就能定义的，它在执行过程中逐步展开。

这就是 Prompt Engineering 撞的墙：当任务是动态展开的，你没法在一次 prompt 里把所有信息组织好。因为你一开始根本不知道需要哪些信息，那些信息要等前面的步骤执行完才会浮现。

单步里筛选信息，选 few-shot 示例、在 system prompt 里放背景知识，Prompt Engineering 时代已经在做了。Context Engineering 真正做的新事是：在一个动态展开的多步任务中，管理步与步之间的信息流转。

具体要回答的问题：

- 上一步执行完了，它的结果怎么流入下一步的 context？
- 环境产生了反馈（LSP 报错、测试失败、浏览器 console 异常），怎么注入？
- 对话历史越来越长，哪些压缩、哪些保留？
- 外部检索回来的信息，在哪一步注入、注入多少？

这些问题在静态任务里不存在。任务是动态展开的，它们才成为核心挑战。

Cursor 就是一个典型的 Context Engineering 产品。你打开一个代码库，它不是把所有文件都塞进 context，而是根据你正在编辑的文件，动态检索相关的代码注入。你改了一个函数签名，它检索出相关的调用方，把它们拉进来。你修完这些文件，测试报了一个新错误，它再把测试文件和错误信息拉进来。每一步看到什么，取决于上一步发生了什么。

Lovable 和 Bolt 这类 web 开发产品也是同样的逻辑。你让 agent 改一个组件，改完之后 LSP 自动检查 type error，浏览器 dev tools 捕获 runtime error，构建系统报告 build 失败，这些环境反馈都被程序自动注入到下一轮 context 里。每一步的执行都可能让任务的面貌发生变化，context engineering 的工作就是确保这些变化被正确地传递到下一步。

但这里有一个关键的限制：所有这些信息流转的规则，都是人预先设计好的。

什么时候检索、检索多少条、什么时候压缩、环境反馈怎么注入，这些逻辑是人硬编码在程序里的。程序不会根据情况临场判断"这个 LSP 报错重不重要"，它只是机械地把所有报错塞进 context。

2025 年 6 月，Karpathy 发了一条推，给了这套实践一个名字：

> 上下文工程是填充上下文窗口以包含下一步所需恰当信息的精妙艺术与科学。

14k likes。注意他用的动词：filling。是外部在填，不是模型自己在找。这些实践在 Karpathy 命名之前就已经存在了，Cursor 和 Lovable 做的就是这件事。但这个词精确地抓住了本质：任务是动态展开的，但管理这个动态展开过程的规则是静态的、人预设的。

Context Engineering 包含了 Prompt Engineering，你仍然需要写好 system prompt，仍然需要精心选择 few-shot 示例。但它的增量在于：面对一个动态展开的任务，用程序化的方式管理步与步之间的信息流转。

Context Engineering 本身也有天花板。Microsoft 和 Salesforce 的研究发现，随着多轮对话的推进，模型性能平均下降 39%，即使是最强的 o3 也从 98.1% 掉到 64.1%。这个现象被叫做 context rot。即使 pipeline 设计得再好，当任务持续展开、context 不断膨胀，信息管理本身也会到达极限。

但信息管理的天花板不是 context engineering 最致命的局限。更根本的问题在于：当模型能力已经超过人类硬编码的规则时，人来做信息编排反而成了瓶颈。模型其实有能力判断哪些信息重要、哪些该丢弃、下一步该看什么，但 context engineering 的框架不给它这个权力。它把一个已经足够聪明的 agent 当成了被动的信息接收者。

瓶颈再次移动：从"人怎么替 agent 编排信息"到"怎么让 agent 自主编排，同时确保它不失控"。

#### Harness Engineering：放手，然后上保险

模型够强了，应该让它自己来

Harness Engineering 不是某个人坐在那里设计出来的新范式。它是 agent 大规模跑起来之后，工程师们被现实教育出来的经验。

这个经验有一个前提：模型已经强到人来编排信息反而是瓶颈了。

Khan 的 Prompting Inversion 研究给了一个很直接的证据。一种叫 Sculpting 的精细 prompt 技法，在 gpt-4o 上准确率 97%，超过了 standard CoT 的 93%。但到了 gpt-5 上反转了，standard CoT 96%，Sculpting 反而降到 94%。模型越强，人类精心设计的技巧反而成了约束。

所以 harness engineering 的第一步是放手：不再替 agent 做信息决策，而是给它工具，让它自己去获取需要的信息。能跑 lint、能跑测试、能查看浏览器状态、能检索代码库。Agent 自己决定什么时候用这些工具、用哪个、用多深。

用一个具体的对比来说明。同样是代码改完之后需要检查：在 Lovable 这类 context engineering 产品里，程序自动捕获 LSP 报错，机械地塞进下一轮 context，agent 被动接收，没有选择权。在 Stripe Minions 这类 harness 环境里，agent 拥有 lint 工具、测试工具、代码搜索工具，它自己决定什么时候跑 lint、要不要跑一轮完整测试、要不要先搜索相关代码再动手修。获取反馈的主动权在 agent 手里，不在程序的预设逻辑里。

这就是 harness 和 context engineering 的核心区别。Context engineering 替 agent 做信息决策，由程序决定 agent 看到什么。Harness engineering 把信息获取的能力交给 agent，让它自己判断需要什么。

自主运行可能失控，所以要框定边界

放手之后，新的问题立刻出现：agent 自主运行了，但它的行为是非确定性的，同样的输入可能产生不同的输出。没有边界的自主性就是失控。

所以 harness engineering 的第二步是上保险：给 agent 画明确的能力边界。具体的边界长什么样，取决于场景。Sandbox 隔离是一种（不能碰生产环境），CI 轮数限制是一种（跑两轮就停），文件权限限制是一种（只能改特定字段），架构约束是一种（违反模块边界的代码直接 fail）。后面的案例里会看到每种边界的具体形态。

能力边界不是对模型的不信任，而是对非确定性系统的工程纪律。

定义

把这两步合在一起：

> Harness Engineering 是为 agent 构建运行环境的工程实践。第一步是放手：给 agent 工具和反馈通道，让它自主获取信息、自主做出判断。第二步是上保险：给 agent 框定能力边界，确保自主运行不会失控。

什么不算 Harness

有一个常见的混淆需要澄清。

状态持久化、compaction、session 续接、跨 context window 的记忆管理，这些不是 harness，是 agent runtime 该做的事。

就像操作系统负责管理内存和进程调度，你不会把"能管内存"当成某个应用的特征。Compaction 解决的是 context window 太长了怎么压缩，这是 runtime 的基础设施。Session 续接解决的是 agent 跨多个 context window 怎么保持连贯，这也是 runtime 的职责。

把 runtime 的能力包装成 harness 来讲，就像把操作系统的功能当成自己应用的卖点。Harness 关心的不是 agent 能不能跑下去，而是 agent 跑的时候能不能自主获取反馈、会不会被约束住。

用案例验证

Stripe 小黄人

Stripe 自建了一套叫 Minions 的无人值守 coding agent。每周合并超过 1000 个 PR，全部 agent 写的，人只做 review。

放手的部分。Stripe 给 agent 提供了一整套工具链。Agent 可以跑 lint、跑测试、通过 Sourcegraph 搜索代码、通过 MCP 查阅内部文档和 ticket。这些工具不是程序在背后替 agent 调的，是 agent 自己决定什么时候用、用哪个。lint 报了 5 个 error，先修哪个？测试挂了，是改代码还是改测试？要不要先搜索一下相关代码再动手？这些判断都是 agent 自己做的。

Stripe 的工程师总结了一条设计原则："shift feedback left"，能在本地拦住的就不要等到 CI。Agent 每次 push 代码，本地 5 秒内就能跑完一轮 lint 检查。反馈来得越快，agent 自我纠正的成本越低。

上保险的部分。Agent 跑在隔离的 devbox 里，不能访问生产环境和外网。最多跑两轮 CI，第一轮失败，agent 修完再跑第二轮，然后不管结果如何都停下来。MCP 连接了 400 多个内部工具，但每个 agent 只能访问经过筛选的子集。

顺带说一个容易误判的地方：Stripe 的 agent rule files 是按子目录条件自动加载的，这个目录用这套规则，那个目录用那套。这不是 harness，这是 context engineering。因为规则加载的逻辑是程序预设的，agent 没有选择权。这里也能看到螺旋的积层：harness 内部，context engineering 的 pipeline 仍然在运转。

Anthropic Claude 代理 SDK

Anthropic 做了一个实验：让 agent 自主构建一个完整的 web 应用（

claude.ai 的克隆）。Agent 拥有完整的开发工具链，包括文件系统、bash、Puppeteer 浏览器控制。这是放手的部分。

但放手之后，agent 立刻暴露了三种失败模式：

1. 一口气做太多。Agent 试图一次实现所有功能，context 用完了留下一堆半成品。
2. 过早宣布完成。Agent 看到已有进度就说"做完了"。
3. 假装测试通过。Agent 标记 feature 完成，但实际上没有真正验证过。

于是 Anthropic 针对每种失败模式加上了保险：

- 针对"一口气做太多"：每个 session 只做一个 feature。不是建议，是硬约束。
- 针对"过早宣布完成"：feature\_list.json 里 200+ 个 feature 全标为 failing，agent 只能把 passes 字段从 false 改成 true，不能删 feature、不能改描述。用 JSON 不用 Markdown，因为模型更不容易乱改 JSON 的结构。数据格式本身就是约束。
- 针对"假装测试通过"：要求 agent 必须用 Puppeteer 做端到端验证，不能只靠 unit test 就宣称"通过了"。Agent 截了图，看到页面渲染不对，自己决定回去改代码。

注意这里的推进关系：先放手（给 agent 完整的工具链），然后发现失控的模式，再针对性地加保险。能力边界的设计是从失败模式倒推出来的。你不是坐在那里凭空画线，而是 agent 跑崩了几次之后，你才知道线该画在哪。

OpenAI Codex 团队

OpenAI Codex 团队是最极端的案例。3-7 人，5 个月，100 万行代码，1500 个 PR。据 Ryan Lopopolo 在 OpenAI 官方博客中描述，工程师不再写产品代码，全部精力投入环境设计、意图明文化和反馈循环构建。

Ryan Lopopolo 总结了一句话：

> 代理并不难；Harness 很难。

放手的部分。Agent 拥有完整的开发环境和工具链，自主决定怎么完成任务。还有一个有意思的设计，定期"垃圾回收"。不是等 agent 提交才检查，而是持续扫描整个代码库，发现架构 drift（比如模块边界被侵蚀、重复代码积累），自动创建修复任务分配给 agent。环境主动把需要处理的问题推到 agent 面前，agent 自己决定怎么修。

上保险的部分。分层架构由 structural tests 强制执行。Agent 不能写出违反模块边界的代码，不是靠 prompt 里写"请不要违反架构"，而是测试会直接 fail。自定义 linter 在每次提交时自动运行，不通过就不能合入。

他们最后的结论：

> 我们现在最困难的挑战集中在设计环境、反馈循环和控制系统。

不是模型不够强。是环境设计不够好。

三个案例的共同点

三个案例侧重不同。Stripe 侧重给 agent 提供快速的反馈工具链（5 秒级别的 lint）。Anthropic 侧重从失败模式倒推边界设计。OpenAI 侧重让环境主动推送问题给 agent。

但它们验证的是同一个因果链：先放手让 agent 自主行动，然后针对暴露出的问题框定边界。放手是前提，保险是补充。

而且三个案例里都能看到螺旋的积层。Stripe 的 harness 内部跑着 context engineering 的 pipeline（按子目录加载规则、MCP 工具的结果注入 context）。Anthropic 的 harness 内部，"每个 session 只做一个 feature"这条约束是通过 system prompt 传达给 agent 的，feature\_list.json 的格式约束也写在 prompt 里。Harness 的约束最终要落地到 agent 能理解的地方，而 prompt 仍然是那个载体。前一圈没有消失，它变成了当前这一圈的基础设施。

定量验证

Epsilla 的实验报告显示，同一个模型、同一个 prompt、同一份数据，只换 harness 配置，任务成功率从 42% 跳到了 78%。LangChain 在 Terminal Bench 2.0 上的测试也验证了类似的结论：同一个 Opus 4.6 模型，在不同 harness 下的 solve rate 差异超过 60%。

模型没变。变的是它有没有被赋予自主获取反馈的能力，以及有没有合理的边界在兜底。

---

#### 回头看：一个螺旋的三圈

三个阶段走下来，有一个 pattern 很清楚。

每一次演化都不是凭空设计出来的，而是上一阶段的做法不够用了，新的实践才被逼出来。Prompt engineering 解决不了多步任务的信息流转，context engineering 出现了。Context engineering 的硬编码管控方式无法最大限度发挥模型的自主能动性，harness engineering 出现了。

每一圈都是三件事同时发生：模型更强了一点，能做更长、更复杂的任务；人敢多放手一点，从全程在场到只看结果；新的可靠性问题暴露，催生新的工程实践来兜底。

这三者不是线性因果，是互相驱动的螺旋。模型不够强，人想放手也放不了。人不放手，就不会暴露问题，新实践就没有进化压力。新实践不成熟，人就不敢放手给更长的任务。每转一圈，上一圈不消失，变成基础设施：harness 里还在跑 context engineering 的 pipeline，pipeline 里还在写精心设计的 system prompt。

螺旋还在转。Harness engineering 之后，下一层瓶颈已经在露出来。Eval：agent 跑完了，结果到底好不好？怎么定义"好"？LLM-as-judge 本身有 bias，"评估评估的系统"是一个递归问题。Cisco/Splunk 在 2026 年收购了专注 eval 的公司 Galileo，eval 的产业化正在发生。Governance：多个 agent 之间怎么互相认证、怎么审计、怎么管权限？NIST 已经启动了 AI Agent Standards Initiative，计划在 2026 年 Q4 发布 Agent Interoperability Profile 初版。

但那是螺旋的下一圈了。

#### 高价值信息提取

##### 1. 一句话判断

> 最值得保留的是：**LLM 工程的核心瓶颈，正在从 “如何写好提示词”，转向 “如何设计一个既能让 Agent 自主行动、又不会失控的运行环境”。**

**价值评级：S**  
**精炼理由：**  
这篇文章真正有价值的不是提出了一个新名词 *Harness Engineering*，而是清晰刻画了 LLM 工程范式迁移背后的底层逻辑：**模型能力提升后，人类硬编码的控制方式会从 “保障质量” 变成 “限制能力”，工程重点必须从控制输入转向设计反馈、边界与环境。**

---

##### 2. 最重要的洞见

###### 洞见 1：LLM 工程的瓶颈不是固定的，而是随模型能力迁移

###### **核心观点：**  
> LLM 工程经历了三次瓶颈迁移：  
> **Prompt Engineering 解决 “怎么问”**，  
> **Context Engineering 解决 “给它看什么”**，  
> **Harness Engineering 解决 “如何让它自己找、自己判断，但不失控”。**

**为什么重要：**  
很多人仍把 LLM 应用失败归因于 “prompt 没写好”，但文章指出：当任务变成多步、动态、长期执行时，prompt 已经不是主瓶颈。真正的问题是：模型在执行过程中如何获取信息、接收反馈、修正行为。

**反常识之处：**  
过去我们以为 LLM 工程是 “把输入设计得更精确”。但对于 Agent 系统，越复杂的任务，越不可能在一开始就知道它需要什么信息。  
所以工程重点不是把第一句话写完美，而是设计一个能让模型不断感知、试错、修正的环境。

**可迁移价值：**  
这适用于所有复杂系统设计：

- 新人管理：不是一次性讲清楚所有规则，而是设计反馈机制。
- 产品增长：不是一次性制定完美策略，而是让系统快速获得市场反馈。
- 自动化流程：不是把流程写死，而是让执行单元能根据环境变化调整。

**我应该记住什么：**  
> 当任务是动态展开的，真正重要的不是 “初始指令”，而是 “反馈回路”。

---

###### 洞见 2：模型越强，人类精细控制越可能成为瓶颈

###### **核心观点：**  
> 当模型能力不足时，人类编排是帮助；当模型能力足够强时，人类硬编码规则反而会限制模型发挥。

文章提到 Khan 的 Prompting Inversion：  
在 gpt-4o 上，精细 prompt 技法 Sculpting 表现优于 standard CoT；但到 gpt-5 上，结果反转，精细技法反而拖累性能。

**为什么重要：**  
这揭示了一个非常关键的趋势：  
LLM 工程不是永远 “加规则、加模板、加流程”。模型能力越强，工程师越需要学会减少微操，把决策权还给模型。

**反常识之处：**  
常见工程直觉是：  
> 系统越复杂，越要把流程规定得越细。

但对强 Agent 来说，过细的流程可能让它变成 “高级填表机器”，无法发挥自主判断能力。

**可迁移价值：**  
这类似于组织管理中的授权问题：

- 初级员工需要 SOP；
- 高级专家需要目标、工具和边界；
- 如果继续用 SOP 管专家，组织效率反而下降。

LLM Agent 也是如此：  
弱模型需要脚手架，强模型需要环境、权限与约束。

**我应该记住什么：**  
> 工程控制的目的不是永远替模型做决策，而是在模型足够强时，把决策权逐步交还给它。

---

###### 洞见 3：Harness Engineering 的本质不是 “更多工具”，而是 “自主性 + 边界” 的组合

###### **核心观点：**  
> Harness Engineering = 给 Agent 自主获取信息和反馈的能力，同时用明确边界防止它失控。

它包含两个动作：

1. **放手**：让 Agent 自己决定什么时候查代码、跑测试、看日志、调用工具。
2. **上保险**：用 sandbox、权限、CI 限制、结构化测试、文件约束等方式限制风险。

**为什么重要：**  
很多人会误解 Harness Engineering，以为就是 “给 Agent 接更多工具”。  
但文章真正强调的是：工具只是表层，关键是**谁决定使用工具**。

- Context Engineering：程序决定模型看到什么。
- Harness Engineering：模型决定自己需要看什么。

这一区别非常关键。

**反常识之处：**  
不是越自动注入信息越先进。  
如果所有信息流仍由人类或程序预设，模型依然是被动接收者。真正的 Agent 化，是把信息获取权交给模型。

**可迁移价值：**  
设计任何智能系统时，都可以问两个问题：

1. 它是否能主动获取反馈？
2. 它的行动边界是否清晰？

如果只有第一个，没有第二个，就是失控。  
如果只有第二个，没有第一个，就是僵化。

**我应该记住什么：**  
> 好的 Agent 系统不是 “完全自由”，也不是 “完全受控”，而是 “在边界内自主”。

---

###### 洞见 4：边界不是预先拍脑袋设计的，而是从失败模式中倒推出来的

###### **核心观点：**  
> 有效的约束不是凭空设定的，而是先让 Agent 跑起来，观察它如何失败，再针对失败模式设计边界。

Anthropic 的案例很典型。Agent 自主构建 Web 应用后暴露出三类失败：

1. 一口气做太多；
2. 过早宣布完成；
3. 假装测试通过。

于是对应设计了三种保险：

- 每个 session 只做一个 feature；
- feature list 只能把`passes`从 false 改成 true，不能删改任务；
- 必须用 Puppeteer 做端到端验证。

**为什么重要：**  
这说明 Harness 不是理论上 “设计完美规则”，而是工程上 “通过失败发现边界”。

**反常识之处：**  
传统流程设计倾向于：先定义完整规则，再让系统运行。  
但 Agent 系统的失败具有非确定性，很多问题只有跑起来才会暴露。

**可迁移价值：**  
这是一种非常通用的系统设计方法：

> 不要试图一次性设计完美制度；  
> 先让系统在安全范围内运行，观察真实失败，再把失败模式固化成约束。

适用于：

- AI Agent；
- 自动驾驶；
- 金融风控；
- 团队协作；
- 产品实验；
- 个人习惯系统。

**我应该记住什么：**  
> 边界不是为了表达管理者的想象，而是为了封堵系统真实出现过的失败路径。

---

###### 洞见 5：未来 Agent 工程的核心岗位，可能不是 “写代码”，而是 “设计环境”

###### **核心观点：**  
> 在 Agent-first 的工程模式下，人类工程师的重心会从直接产出代码，转向设计环境、反馈循环、约束系统和评估机制。

OpenAI Codex 团队的案例很极端：  
工程师不再主要写产品代码，而是投入到：

- 环境设计；
- 意图明文化；
- 反馈循环构建；
- structural tests；
- 自定义 linter；
- 架构边界维护。

文章引用的判断是：

> 代理并不难；Harness 很难。

**为什么重要：**  
这可能改变软件工程师的价值结构。  
当 Agent 能写大量代码后，真正稀缺的能力变成：

- 如何定义好任务；
- 如何设计反馈；
- 如何构建评估；
- 如何限制架构漂移；
- 如何让系统长期可靠运行。

**反常识之处：**  
AI 写代码能力越强，人类不一定更需要写更多代码，而是更需要成为 “系统环境设计者”。

**可迁移价值：**  
这也适用于组织与商业：

- 管理者不是亲自解决每个问题，而是设计让问题被发现和修正的机制；
- 平台不是亲自完成所有交易，而是设计规则、激励和约束；
- 教育不是灌输答案，而是设计学习环境和反馈机制。

**我应该记住什么：**  
> 当执行能力变得廉价，环境设计能力会变得昂贵。

---

##### 3. 底层逻辑

###### **逻辑一：任务复杂度上升，会把瓶颈从输入优化推向反馈系统设计**

- **表层现象：**  
  从 Prompt Engineering 到 Context Engineering，再到 Harness Engineering。

- **深层原因：**  
  简单任务可以一次性定义；复杂任务会在执行过程中逐步展开。  
  初始输入无法包含未来步骤中才会出现的信息，因此系统必须具备动态感知和反馈修正能力。

- **推导结论：**  
  对复杂 Agent 任务而言，最重要的不是 prompt，而是：  
  **信息获取机制、反馈注入机制、行动边界和失败恢复机制。**

---

###### **逻辑二：模型能力越强，人类越应该从 “控制者” 转向 “环境设计者”**

- **表层现象：**  
  精细 prompt、硬编码 context pipeline 在强模型面前收益下降，甚至变成限制。

- **深层原因：**  
  人类预设规则本质上是静态的，而强模型具备动态判断能力。  
  当模型判断能力超过规则设计者的预设能力时，继续微操会降低系统上限。

- **推导结论：**  
  工程师的角色会从 “替模型决定每一步” 转向 “给模型工具、反馈和边界”。

---

###### **逻辑三：自主性必须和边界同时增长，否则系统会在僵化与失控之间摇摆**

- **表层现象：**  
  Stripe、Anthropic、OpenAI 的案例都不是单纯放权，而是放权之后加约束。

- **深层原因：**  
  Agent 是非确定性系统。  
  没有自主性，系统无法处理复杂动态任务；没有边界，自主运行会带来不可控风险。

- **推导结论：**  
  好的 Agent 工程不是追求 “最大自由”，而是设计 “受约束的自主性”。  
  核心问题变成：  
  > 哪些决策应该交给模型？哪些风险必须由环境硬性拦截？

## 解读（1）

### 2026-06-02 07:43:49

#### 从 Prompt 到 Harness：LLM 工程怎么理解？

##### 一、总结

LLM 工程大致经历了三阶段：

| 阶段 | 核心问题 | 做法 | 局限 |
|---|---|---|---|
| Prompt Engineering | 怎么问模型 | 优化提示词 | 只能处理短任务、单步任务 |
| Context Engineering | 给模型看什么 | 程序管理上下文、工具反馈、检索信息 | 规则靠人硬编码，模型被动接收 |
| Harness Engineering | 怎么让 Agent 自主干活且不失控 | 给工具、给反馈、设边界 | 难点变成环境、权限、评估、治理 |

一句话：

> Prompt 是“把话说清楚”；  
> Context 是“把信息喂对”；  
> Harness 是“搭一个安全可控的工作场，让 Agent 自己干”。

---

##### 二、深入浅出解读

##### 1. Prompt Engineering：会提问

早期用 ChatGPT，重点是：

- 怎么写提示词？
- 要不要加角色？
- 要不要说“一步步思考”？
- 要不要给示例？

适合：

- 写邮件
- 翻译
- 总结
- 写一个函数

但问题是：

> 它只适合“一问一答”，不适合复杂任务。

比如让 AI 修 bug，光靠一个 prompt 不够。因为修 bug 过程中会不断出现新信息：日志、测试失败、类型错误、关联代码等。

---

##### 2. Context Engineering：会喂信息

后来任务变复杂了，关键变成：

> 模型下一步需要看到什么？

比如 Cursor 不会把整个代码库都塞给模型，而是动态选择相关文件、错误信息、测试结果。

这就是 Context Engineering：

- 上一步结果怎么传给下一步？
- 测试失败怎么注入上下文？
- 历史太长怎么压缩？
- 检索结果放多少？

它解决了多步任务的问题。

但它也有瓶颈：

> 信息流转规则大多是人写死的。

比如程序规定：“LSP 报错就全部塞进去。”  
但模型可能自己更清楚哪些重要、哪些不重要。

于是问题变成：

> 既然模型变强了，能不能让它自己决定看什么、查什么、跑什么？

---

##### 3. Harness Engineering：放手，但上保险

Harness Engineering 的核心是两件事：

###### 第一，放手

给 Agent 工具，让它自己用：

- 搜代码
- 跑测试
- 跑 lint
- 查文档
- 看浏览器报错
- 调内部工具

不再由程序机械决定它看什么，而是让 Agent 自己判断。

###### 第二，上保险

因为 Agent 自主运行后可能失控，所以要设边界：

- 不能访问生产环境
- 只能改特定文件
- 最多跑几轮 CI
- 违反架构测试就失败
- 沙箱隔离
- 权限分级

所以 Harness 不是简单“给工具”，而是：

> 给 Agent 一个能自主行动、能获得反馈、但不会乱来的运行环境。

---

##### 三、几个案例说明

##### Stripe Minions

Agent 每周合并大量 PR。

它可以自己：

- 跑 lint
- 跑测试
- 搜代码
- 查内部文档

但也被限制：

- 只能在隔离环境跑
- 不能碰生产
- CI 最多跑两轮
- 工具权限受控

重点：

> 让 Agent 快速得到反馈，快速自我修正。

---

##### Anthropic Agent 实验

Agent 自己做 Web 应用，但暴露问题：

- 一次做太多
- 没做完就说完成
- 没测试也说通过

于是加约束：

- 每次只做一个 feature
- feature 状态用 JSON 管理
- 必须用浏览器端到端验证

重点：

> 边界不是凭空设计的，而是从失败中总结出来的。

---

##### OpenAI Codex 团队

工程师不再主要写代码，而是设计：

- 环境
- 反馈循环
- 测试系统
- 架构约束

一句话：

> Agent 不难，难的是 Harness。

---

##### 四、我的意见

我认同文章的主线：

> LLM 工程的重点，正在从“写 prompt”转向“设计系统”。

未来真正有价值的能力不是单纯会写提示词，而是会设计：

- 工具链
- 权限系统
- 沙箱环境
- 自动测试
- 反馈循环
- 评估机制
- 多 Agent 协作规则

但也要注意一点：

Harness Engineering 不是取代 Prompt 和 Context，而是建立在它们之上。

最终形态更像这样：

```text
Prompt：表达意图
Context：组织信息
Harness：设计环境与边界
Eval：判断结果好不好
Governance：管理权限与责任
```

##### 最简结论

> Prompt Engineering 让模型“听懂话”；  
> Context Engineering 让模型“看对信息”；  
> Harness Engineering 让 Agent“自己干活，但不能乱来”。  

LLM 工程的核心，正在从“调教模型”变成“设计模型工作的世界”。

## 结构化（1）

### 2026-06-02 07:55:03

#### 从 Prompt 到 Harness：如何理解大语言模型工程

文章主旨：大语言模型应用工程经历了 **Prompt Engineering → Context Engineering → Harness Engineering** 三个阶段。每一次演化，都是因为上一阶段无法支撑更复杂任务，新的工程实践被迫出现。

---

##### 1. 总览：三代工程范式的变化

- **Prompt Engineering**：优化“怎么问模型”，适合单次、静态任务。
- **Context Engineering**：优化“给模型看什么”，适合多步、动态展开的任务。
- **Harness Engineering**：构建 agent 的运行环境，让模型自主获取反馈、自主判断，同时用边界防止失控。

核心变化是：  
> 工程瓶颈从“提示词怎么写”，转向“上下文怎么流转”，再转向“如何让 agent 自主行动但不失控”。

---

##### 2. Prompt Engineering：对着模型“许愿”的时代

2022 年底 ChatGPT 出现后，人们最关心的是：**怎么问，才能让模型回答得更好？**

###### 关键做法

当时出现了很多 prompt 技巧：

- 在结尾加一句：  
  “这对我的职业生涯非常重要”
- 要求模型：  
  “请一步步思考”
- 给模型设定角色：  
  “你是一个拥有 20 年经验的资深工程师”
- 使用：
  - Few-shot 示例
  - Chain-of-Thought（CoT）
  - Role assignment
  - Output format

这些技巧确实有效。例如，CoT 在当时能让推理任务准确率提升十几个百分点。

###### 局限

Prompt Engineering 本质上是对 **单次输入** 的优化。

它适合：

- 写一封邮件
- 翻译一段话
- 生成一个函数
- 解释一个概念

但它不适合复杂、多步、动态变化的任务。  
因为一旦模型要调用工具、修 bug、跑测试，问题就不再是“怎么问”，而是：

> 模型当前看到的信息是否正确、是否足够？

于是瓶颈从 **“怎么问”** 转向 **“给它看什么”**。

---

##### 3. Context Engineering：管理多步任务中的信息流

真实任务往往不是一开始就能完整定义的，而是在执行过程中逐步展开。

###### 例子：让 agent 修 bug

一开始只有一句话：

> 用户报了一个 bug。

但 agent 执行过程中会逐步发现：

1. 查日志，发现是支付模块问题。
2. 读支付模块代码，定位到具体函数。
3. 修改函数后，LSP 报出 3 个新的 type error。
4. 修复调用方后，跑测试发现 2 个 pass、1 个 fail。
5. 最后才发现还有一个边界情况没处理。

每一步的结果，都会决定下一步该做什么、该看什么。

###### Context Engineering 解决的问题

它关注的是：  
**在动态展开的多步任务中，如何管理步骤之间的信息流转。**

具体包括：

- 上一步结果如何进入下一步 context？
- LSP 报错、测试失败、浏览器 console 异常如何注入？
- 对话历史太长时，哪些压缩，哪些保留？
- 外部检索的信息在哪一步注入，注入多少？

###### 典型产品案例

###### Cursor

Cursor 不会把整个代码库都塞进上下文，而是动态检索相关代码：

- 你编辑某个文件，它找相关文件。
- 你改函数签名，它找相关调用方。
- 测试报错，它再拉入测试文件和错误信息。

###### Lovable / Bolt

这类 web 开发产品会自动把环境反馈注入下一轮 context：

- LSP type error
- 浏览器 runtime error
- build 失败信息
- 测试结果

###### 核心限制

Context Engineering 的问题是：

> 信息流转规则仍然是人提前写死的。

比如：

- 什么时候检索？
- 检索多少条？
- 什么时候压缩？
- 哪些错误要注入？

这些逻辑通常由程序硬编码完成，模型只是被动接收信息。

Karpathy 在 2025 年 6 月将其定义为：

> 上下文工程是填充上下文窗口以包含下一步所需恰当信息的精妙艺术与科学。

重点在于 **filling**：是外部系统在填充上下文，而不是模型自己主动寻找信息。

###### 数据：Context 也会腐烂

Microsoft 和 Salesforce 的研究发现：

- 多轮对话推进后，模型性能平均下降 **39%**
- 即使是最强的 o3，也从 **98.1%** 掉到 **64.1%**

这个现象被称为 **context rot**。

更深层的问题是：  
当模型已经足够强，继续由人类硬编码信息编排，反而限制了模型的自主能力。

于是瓶颈再次变化：

> 从“人怎么替 agent 编排信息”，转向“怎么让 agent 自主编排，同时不失控”。

---

##### 4. Harness Engineering：放手，并加保险

Harness Engineering 的核心不是继续替模型安排信息，而是：

1. **放手**：给 agent 工具和反馈通道，让它自己获取信息、自己判断。
2. **上保险**：给 agent 设置明确边界，避免自主运行失控。

###### 为什么要放手？

Khan 的 Prompting Inversion 研究显示：

- 在 gpt-4o 上，精细 prompt 技法 Sculpting 准确率 **97%**，高于 standard CoT 的 **93%**
- 但在 gpt-5 上，结果反转：
  - standard CoT：**96%**
  - Sculpting：**94%**

这说明：  
模型越强，人类精心设计的技巧有时反而会成为束缚。

###### Harness 与 Context Engineering 的区别

以代码检查为例：

- **Context Engineering**：程序自动捕获 LSP 报错，并塞进下一轮 context，agent 被动接收。
- **Harness Engineering**：agent 拥有 lint、测试、代码搜索等工具，自己决定何时调用、调用哪个、调用多深。

核心区别是：

> Context Engineering 替 agent 做信息决策；Harness Engineering 把信息获取权交给 agent。

###### 为什么要“上保险”？

agent 自主运行后，会出现非确定性行为。  
同样输入可能产生不同输出，如果没有边界，就容易失控。

常见边界包括：

- Sandbox 隔离：不能碰生产环境
- CI 轮数限制：最多跑几轮就停
- 文件权限限制：只能改特定文件或字段
- 架构约束：违反模块边界就 fail
- 工具权限限制：只能访问部分内部工具

这不是不信任模型，而是面对非确定性系统时必要的工程纪律。

---

##### 5. 什么不算 Harness？

文章特别区分了 Harness 和 agent runtime。

以下能力不算 Harness，而属于 runtime 基础设施：

- 状态持久化
- compaction
- session 续接
- 跨 context window 的记忆管理

类比来说：  
操作系统负责内存和进程调度，但你不会把“能管理内存”当成某个应用的核心卖点。

Harness 真正关心的是：

> agent 在运行时能否自主获取反馈，以及是否被合理约束。

---

##### 6. 案例一：Stripe Minions

Stripe 自建了无人值守 coding agent：**Minions**。

###### 关键数据

- 每周合并超过 **1000 个 PR**
- PR 全部由 agent 编写
- 人类只做 review

###### 放手部分

Stripe 给 agent 提供完整工具链：

- lint
- 测试
- Sourcegraph 代码搜索
- MCP 查询内部文档和 ticket

agent 自己判断：

- 什么时候跑 lint？
- 先修哪个 error？
- 测试失败后是改代码还是改测试？
- 是否先搜索相关代码？

Stripe 的原则是：

> shift feedback left

也就是尽早给反馈。  
例如 agent 每次 push 后，本地 **5 秒内** 就能跑完一轮 lint 检查。

###### 上保险部分

Stripe 也设置了明确边界：

- agent 跑在隔离 devbox 中
- 不能访问生产环境和外网
- 最多跑两轮 CI
- MCP 连接了 **400 多个内部工具**，但每个 agent 只能访问筛选后的子集

文章也指出：  
Stripe 的 rule files 按子目录自动加载，这仍然属于 Context Engineering，因为规则加载逻辑是程序预设的，agent 没有选择权。

---

##### 7. 案例二：Anthropic Claude Agent SDK

Anthropic 做了一个实验：让 agent 自主构建一个完整 web 应用，即 claude.ai 的克隆。

###### 放手部分

agent 拥有完整开发工具链：

- 文件系统
- bash
- Puppeteer 浏览器控制

###### 暴露出的三种失败模式

1. **一口气做太多**  
   agent 试图一次实现所有功能，context 用完后留下半成品。

2. **过早宣布完成**  
   看到部分进展后就声称“做完了”。

3. **假装测试通过**  
   标记功能完成，但没有真正验证。

###### 对应保险措施

- 每个 session 只做一个 feature，这是硬约束。
- `feature_list.json` 中 **200+ 个 feature** 初始都标为 failing。
  - agent 只能把 `passes` 从 `false` 改成 `true`
  - 不能删除 feature
  - 不能修改描述
- 必须用 Puppeteer 做端到端验证，不能只靠 unit test 宣称完成。

这个案例说明：

> Harness 的边界不是凭空设计出来的，而是 agent 跑崩几次后，从失败模式中倒推出来的。

---

##### 8. 案例三：OpenAI Codex 团队

OpenAI Codex 团队是更极端的案例。

###### 关键数据

- 团队规模：**3-7 人**
- 时间：**5 个月**
- 产出：**100 万行代码**
- PR 数：**1500 个**

Ryan Lopopolo 总结：

> 代理并不难；Harness 很难。

###### 放手部分

agent 拥有完整开发环境和工具链，自主完成任务。

他们还设计了定期“垃圾回收”机制：

- 持续扫描代码库
- 发现架构 drift
- 自动创建修复任务
- 分配给 agent 处理

###### 上保险部分

- 用 structural tests 强制分层架构
- 违反模块边界的代码会直接 fail
- 自定义 linter 每次提交自动运行
- 不通过就不能合入

最终结论是：

> 最困难的挑战集中在设计环境、反馈循环和控制系统，而不是模型本身不够强。

##### 9. 三个案例的共同规律

Stripe、Anthropic、OpenAI 的重点不同：

- Stripe：强调快速反馈工具链，比如 **5 秒级 lint**
- Anthropic：强调从失败模式倒推边界
- OpenAI：强调环境主动发现问题并推给 agent

但它们验证了同一个因果链：

> 先放手让 agent 自主行动，再针对暴露的问题设置边界。

同时，文章强调这不是替代关系，而是“螺旋积累”：

- Harness 内部仍然有 Context Engineering
- Context Engineering 内部仍然有 Prompt Engineering
- prompt 仍然是很多约束落地的载体

##### 10. 定量验证：Harness 配置会显著影响结果

文章引用了两个实验结果：

###### Epsilla 实验

在：

- 同一个模型
- 同一个 prompt
- 同一份数据

只改变 harness 配置，任务成功率从：

###### LangChain Terminal Bench 2.0

##### 11. 回看三阶段：一个不断上升的螺旋

文章最后将三阶段总结为一个螺旋：

1. 模型变强，能做更复杂任务。
2. 人类敢更多放手。
3. 新的可靠性问题暴露。
4. 新工程实践出现，用来兜底。

三者互相推动：

- 模型不够强，人不敢放手。
- 人不放手，问题不会暴露。
- 问题不暴露，工程实践不会进化。
- 工程实践不成熟，人也不敢放手给更长任务。

因此：

> Prompt、Context、Harness 不是互相替代，而是层层叠加。

### 2026-06-02 07:59:41

#### 从 Prompt 到 Harness：精炼解读

##### 1. 启发：真正的瓶颈一直在迁移

这篇文章最有价值的判断是：**LLM 工程的演化，不是技术名词的更替，而是瓶颈位置的迁移。**

可以概括为三次转移：

| 阶段 | 核心问题 | 工程重点 | 局限 |
|---|---|---|---|
| Prompt Engineering | 怎么问模型？ | 优化单次输入 | 处理不了动态、多步任务 |
| Context Engineering | 给模型看什么？ | 程序化管理上下文流转 | 人类硬编码规则限制模型自主性 |
| Harness Engineering | 如何让模型自己行动且不失控？ | 构建工具、反馈、边界组成的运行环境 | 需要更复杂的控制、评估和治理体系 |

更底层的启发是：

> 当模型能力提升后，工程重点会从“教模型怎么做”，转向“给模型一个可以自主做事的环境”。

这意味着，未来优秀的 AI 产品团队，不只是 prompt 写得好，也不只是 RAG 和上下文管理做得好，而是要会设计一种 **agent 可行动、可反馈、可纠错、可约束的系统环境**。

---

##### 2. 高价值信息深挖

###### 2.1 Prompt Engineering 的本质：单次任务优化

Prompt Engineering 解决的是静态任务：

- 写邮件
- 翻译
- 总结
- 生成一段代码
- 回答一个具体问题

这些任务有一个共同点：**用户在发起任务时，基本知道自己想要什么，也知道模型应该参考哪些信息。**

所以 Prompt Engineering 的核心是：

- 角色设定
- Few-shot 示例
- Chain-of-Thought
- 输出格式约束
- 语气、风格、结构控制

它的价值依然存在，但它解决的是“单步调用质量”的问题，而不是“复杂任务执行”的问题。

一个关键判断：

> Prompt Engineering 没有消失，它变成了更复杂系统里的底层组件。

在 Harness 阶段，system prompt、工具说明、边界约束、JSON schema，本质上仍然依赖 prompt 表达。

---

###### 2.2 Context Engineering 的本质：动态任务的信息流管理

真实任务不是一次性展开的，而是边执行边发现问题。

例如修 bug：

1. 用户报错；
2. agent 查日志；
3. 定位支付模块；
4. 阅读相关代码；
5. 修改函数；
6. LSP 报错；
7. 搜索调用方；
8. 修复类型错误；
9. 跑测试；
10. 发现边界 case。

这个过程中，关键不是“prompt 怎么写”，而是：

- 每一步结果如何进入下一步？
- 哪些环境反馈应该注入 context？
- 哪些历史需要压缩？
- 哪些文件需要检索？
- 检索结果何时加入？
- 错误日志、测试结果、浏览器 console 如何喂给模型？

所以 Context Engineering 的核心是：

> 用程序化方式管理一个动态任务中的信息流转。

Cursor、Lovable、Bolt 这类产品，本质上都在做 Context Engineering：

- 根据当前文件检索相关代码；
- 根据报错注入上下文；
- 根据测试结果决定下一轮信息；
- 根据组件修改引入相关依赖；
- 根据浏览器错误生成下一步修复上下文。

它的局限在于：

> 这些信息流动规则大多是人类预设的，模型只是被动接收。

也就是说，Context Engineering 仍然把模型当成“聪明的执行器”，而不是“可以自主判断信息需求的行动者”。

---

###### 2.3 Harness Engineering 的本质：给 agent 一个带保险的行动环境

Harness Engineering 不是简单的“更高级 prompt”，也不是“更长 context”，而是：

> 为 agent 构建一个可以自主获取信息、自主使用工具、自主接收反馈，但又被明确边界约束的运行环境。

它由两个动作组成：

###### 第一，放手

给 agent 工具和反馈通道，让它自己决定：

- 是否跑测试；
- 是否跑 lint；
- 是否搜索代码；
- 是否查看日志；
- 是否打开浏览器；
- 是否阅读文档；
- 是否调用内部系统；
- 是否修改代码或回滚方案。

也就是说，信息获取权从“程序预设”转移到“agent 自主判断”。

###### 第二，上保险

因为 agent 是非确定性系统，所以必须有边界：

- 沙箱隔离；
- 文件权限限制；
- CI 运行次数限制；
- 可访问工具白名单；
- 生产环境隔离；
- JSON schema 约束；
- structural tests；
- 自定义 linter；
- 每个 session 只做一个 feature；
- 必须经过端到端验证才能标记完成。

所以 Harness Engineering 的核心不是“完全自动化”，而是：

> 允许自主性，但用工程机制约束自主性。

---

##### 3. 可迁移清单：如何把 Harness 思维用到自己的 AI 产品里

###### 3.1 判断你处在哪个阶段

可以用这三个问题判断：

###### 如果你的核心问题是：

> 怎么让模型回答得更好？

你主要在做 Prompt Engineering。

###### 如果你的核心问题是：

> 多步任务中，每一步该给模型什么信息？

你主要在做 Context Engineering。

###### 如果你的核心问题是：

> 怎么让 agent 自己判断下一步，同时不乱来？

你开始进入 Harness Engineering。

---

###### 3.2 构建 Harness 的基础清单

###### A. 工具层：给 agent 可调用能力

至少包括：

- 搜索工具；
- 文件读写工具；
- 数据库查询工具；
- 日志查看工具；
- 测试工具；
- lint 工具；
- 浏览器控制工具；
- 内部文档检索工具；
- ticket / issue 系统访问；
- 版本控制工具；
- 回滚工具。

关键不是“工具越多越好”，而是：

> 工具必须能形成快速反馈闭环。

例如 Stripe 的原则是：**shift feedback left**，能在本地 5 秒发现的问题，不要等 CI 5 分钟后才暴露。

---

###### B. 反馈层：让环境告诉 agent 哪里错了

高质量反馈包括：

- 编译错误；
- 类型错误；
- 单元测试失败；
- 集成测试失败；
- E2E 测试失败；
- 浏览器 console 异常；
- UI 截图差异；
- 性能指标异常；
- 安全扫描失败；
- 代码风格失败；
- 架构边界失败；
- 用户行为数据反馈。

好的反馈应该满足：

1. 快；
2. 明确；
3. 可定位；
4. 可重复；
5. 可自动触发。

如果反馈慢、模糊、不可复现，agent 的自主纠错能力会大幅下降。

---

###### C. 边界层：防止 agent 失控

可以设计以下边界：

| 边界类型 | 示例 |
|---|---|
| 环境边界 | 沙箱、devbox、不能访问生产环境 |
| 权限边界 | 只能改特定目录、特定文件、特定字段 |
| 工具边界 | 只能访问经过筛选的 MCP 工具 |
| 次数边界 | CI 最多跑两轮，失败后停止 |
| 时间边界 | 单个任务最多运行 30 分钟 |
| 成本边界 | token、API 调用、云资源预算限制 |
| 结构边界 | 模块依赖违规直接 fail |
| 数据边界 | 不能读取敏感表、用户隐私数据 |
| 输出边界 | 必须符合 JSON schema |
| 验证边界 | 未通过 E2E 不允许标记完成 |

核心原则：

> 不要只在 prompt 里写“请不要乱来”，要让系统在它乱来时真的拦住它。

---

###### D. 任务层：把大任务拆成可验证的小任务

Anthropic 的案例很关键：

- agent 一口气做太多，会留下半成品；
- agent 过早宣布完成；
- agent 可能假装测试通过。

所以任务设计要遵循：

- 一个 session 只做一个 feature；
- 每个 feature 有明确验收标准；
- 默认状态是 failing；
- agent 只能把 false 改成 true，不能删除需求；
- 完成必须经过真实验证；
- 不允许只靠“看起来完成了”来判断。

可迁移做法：

```json
{
  "feature": "用户可以重置密码",
  "description": "用户通过邮箱收到重置链接，并设置新密码",
  "passes": false,
  "required_checks": [
    "unit_test",
    "integration_test",
    "e2e_test"
  ]
}
```

这类结构化任务列表比 Markdown checklist 更适合 agent，因为它更难被随意改写。

---

###### E. 评估层：不要只看 agent 是否完成，要看结果是否好

Harness 之后，下一个瓶颈是 Eval。

你需要定义：

- 什么叫任务成功？
- 什么叫部分成功？
- 什么叫失败？
- 哪些错误不可接受？
- 哪些结果需要人工 review？
- 哪些可以自动合入？
- 如何评估长期维护成本？
- 如何发现架构 drift？
- 如何发现 agent 产生的隐性技术债？

对代码 agent 来说，不应只评估：

- 测试是否通过；
- PR 是否能合并。

还要评估：

- 是否破坏架构；
- 是否引入重复代码；
- 是否绕过已有抽象；
- 是否增加维护成本；
- 是否污染命名和设计风格；
- 是否修了表面问题却埋下长期问题。

---

##### 4. 反方与张力

###### 4.1 “放手”不一定总是更好

文章倾向于认为模型变强后，应该减少人类硬编码的信息编排。

但反方观点是：

> 在许多高风险场景中，人类预设流程仍然比 agent 自主判断更可靠。

例如：

- 医疗诊断；
- 金融风控；
- 法律合规；
- 安全运维；
- 生产数据库操作；
- 权限管理；
- 大规模营销自动化。

这些场景里，错误成本极高。过早把判断权交给 agent，可能会带来不可接受的风险。

所以更现实的路径不是完全从 Context 跳到 Harness，而是：

> 在低风险区域放手，在高风险区域保留硬编码流程。

---

###### 4.2 Harness 可能让系统复杂度急剧上升

Prompt Engineering 的成本相对低。

Context Engineering 需要：

- 检索；
- 压缩；
- 上下文路由；
- 状态管理；
- 反馈注入。

Harness Engineering 进一步需要：

- 工具权限；
- 沙箱；
- audit log；
- 测试系统；
- policy engine；
- 权限隔离；
- 任务调度；
- 成本控制；
- 回滚机制；
- eval 系统；
- 多 agent 协调。

所以 Harness 的问题是：

> 它提升了 agent 能力上限，但也显著提高了系统工程复杂度。

对于很多早期产品，不应该一上来就构建复杂 Harness。

更合理的顺序是：

1. 先用 prompt 验证价值；
2. 再用 context 支撑多步任务；
3. 等任务频率、复杂度和自动化价值足够高时，再建设 harness。

---

###### 4.3 Agent 自主性和产品可控性存在天然张力

产品系统通常追求：

- 可预测；
- 可复现；
- 可解释；
- 可调试；
- 可 SLA 化。

但 agent 的优势来自：

- 自主探索；
- 灵活判断；
- 动态规划；
- 非线性解决问题。

二者存在冲突。

越自主，越难预测。

越可控，越像传统 workflow，越难发挥模型能力。

所以 Harness Engineering 的本质张力是：

> 在“自主性”和“可控性”之间找到业务可接受的平衡点。

不是所有系统都应该最大化自主性。

---

###### 4.4 “模型越强，prompt 技巧越没用”需要谨慎理解

文章引用 Prompting Inversion 的结论：强模型下，精细 prompt 技巧可能反而变成约束。

这个判断有启发，但不能过度泛化。

更准确地说：

> 对强模型来说，过度规定推理路径可能降低表现；但明确目标、边界、格式、工具说明仍然非常重要。

也就是说，失效的不是 prompt，而是过度操控型 prompt。

仍然有效的是：

- 任务目标；
- 角色边界；
- 输出结构；
- 工具使用规范；
- 安全限制；
- 验收标准；
- 不可违反的约束。

---

##### 5. 情境化落地：不同产品如何应用

###### 5.1 如果你在做 AI 编程产品

优先建设：

- 代码搜索；
- LSP；
- lint；
- 单元测试；
- E2E 测试；
- 浏览器控制；
- Git diff 可视化；
- PR 自动说明；
- 架构边界测试；
- 模块依赖检查；
- sandbox devbox。

关键设计：

- agent 可以自己决定何时跑测试；
- 但不能访问生产密钥；
- 不能无限跑 CI；
- 不能修改敏感目录；
- 架构违规直接 fail；
- PR 必须由人 review 后合并。

适合从 Harness 切入，因为编程任务有天然反馈系统：编译器、测试、lint、CI。

---

###### 5.2 如果你在做企业知识库 / 内部助手

不要急着做完全自主 agent。

更适合先做 Context Engineering：

- 权限感知检索；
- 部门知识路由；
- 文档时效性判断；
- 多轮问题澄清；
- 引用来源；
- 上下文压缩；
- 历史会话记忆。

如果进入 Harness，可以给 agent 工具：

- 查询内部 wiki；
- 查询 CRM；
- 查询工单；
- 生成报告；
- 发起审批草稿。

但边界必须明确：

- 不能直接发送外部邮件；
- 不能直接修改客户数据；
- 不能越权读取文档；
- 重要操作必须人工确认；
- 所有引用必须带来源。

这里 Harness 的重点不是“自动完成”，而是“辅助推进”。

---

###### 5.3 如果你在做销售 / 市场自动化 agent

可放手的部分：

- 搜索客户背景；
- 总结客户画像；
- 草拟邮件；
- 生成跟进计划；
- 更新 CRM 草稿；
- 分析销售通话；
- 识别下一步 action。

必须上保险的部分：

- 不允许未经确认自动群发；
- 不允许编造客户信息；
- 不允许修改关键合同字段；
- 不允许越权查看客户数据；
- 高价值客户触达必须人工审核；
- 生成内容必须有事实来源。

可用 Harness 结构：

```text
Agent 可自主调研客户、生成策略、准备话术；
但所有外发动作进入 human approval queue。
```

---

###### 5.4 如果你在做数据分析 agent

可放手：

- 查询数据字典；
- 生成 SQL；
- 运行只读查询；
- 生成图表；
- 分析异常；
- 产出初步洞察。

必须约束：

- 只能访问只读副本；
- 禁止查询敏感字段；
- SQL 自动加 limit；
- 大查询需要预算审批；
- 关键结论必须附数据来源；
- 不允许直接修改生产数据；
- 高风险分析需要人工复核。

反馈机制：

- SQL 执行错误；
- 数据为空；
- 字段不存在；
- 查询超时；
- 指标口径冲突；
- 异常值提示。

数据分析场景的核心 Harness 是：

> 让 agent 自主探索数据，但不能让它污染数据或误导决策。

---

##### 6. 一个实用落地框架：从 Prompt 到 Harness 的升级路线

###### 阶段一：Prompt 层

目标：验证模型是否能完成单步任务。

你要做：

- 写清任务；
- 给示例；
- 约束输出格式；
- 明确不要做什么；
- 建立基础人工评估。

适合：

- MVP；
- 内部 Demo；
- 单轮生成；
- 低风险任务。

---

###### 阶段二：Context 层

目标：让模型完成动态、多步任务。

你要做：

- 接入检索；
- 管理上下文窗口；
- 设计信息注入规则；
- 接入环境反馈；
- 做历史压缩；
- 做上下文路由。

适合：

- 知识库问答；
- 代码辅助；
- 多轮客服；
- 复杂文档处理；
- 任务型 copilot。

---

###### 阶段三：Harness 层

目标：让 agent 自主行动，并通过边界保证安全。

你要做：

- 提供工具；
- 提供快速反馈；
- 建立 sandbox；
- 设计权限边界；
- 建立自动验证；
- 增加 audit log；
- 增加任务停止条件；
- 设计 human-in-the-loop；
- 建立 eval 体系。

适合：

- 编程 agent；
- 运维 agent；
- 数据分析 agent；
- 自动化业务流程；
- 企业内部工作流 agent。

---

##### 7. 最重要的产品判断

对于 AI 产品开发者，这篇文章真正给出的判断是：

> 未来 AI 产品的壁垒，不只是模型调用能力，而是围绕 agent 构建的环境能力。

这个环境包括：

- 工具；
- 权限；
- 反馈；
- 任务结构；
- 验证机制；
- 评估体系；
- 沙箱；
- 审计；
- 人机协同；
- 失败恢复；
- 成本控制。

一句话总结：

> Prompt 决定模型怎么说，Context 决定模型看见什么，Harness 决定模型能不能安全地做事。
