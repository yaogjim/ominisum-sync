## 分析要点

- **核心高价值点**：最有价值的点是明确了子代理的判断原则：只有当任务能拆分为彼此独立的并行块时，使用子代理才真正有收益。
- **留存建议**：短期参考后可归档保留（内容对理解Codex子代理的基本概念、适用场景和使用提示有直接参考价值，可作为工具上手速查材料。）
- **不足**：证据和案例支撑较弱，更多是功能介绍与经验性建议，缺少系统验证。

**知识要点**

- 子代理通过并行处理不同子任务来减少主线程上下文污染
- 可按任务性质为主代理和工作代理选择不同模型与推理强度
- Codex支持内置代理，也支持通过TOML文件自定义专用代理
- 并行写同一文件、强顺序依赖任务和简单改单文件场景不适合子代理
- 子代理会增加token消耗，应在并行收益明确时使用

**行动项**

- 在实际项目中设计一个并行代码审查提示词，分别检查安全、测试缺口和性能问题
- 为常见重复任务定义一个自定义代理配置并放入\`.codex/agents/\`目录测试效果

## 正文

**Emanuele Di Pietro**

### How to run subagents in Codex

Codex just dropped subagents.

Here's everything you need to know.

#### 𝗪𝗵𝗮𝘁 𝗮𝗿𝗲 𝘀𝘂𝗯𝗮𝗴𝗲𝗻𝘁𝘀?

When you use Codex today, everything runs in one single thread.

You give it a task. It explores your codebase. It writes code. It runs tests. All together.

The problem is that over time, the thread fills up with noise — exploration notes, test logs, stack traces. Codex starts losing context. Performance drops.

Subagents fix this.

Instead of one agent doing everything, Codex now spawns multiple specialized agents that run in parallel. Each one handles a specific task. When they're done, they report back to the main agent with clean summaries.

One brain coordinating a team.

#### 𝗛𝗼𝘄 𝘁𝗼 𝘂𝘀𝗲 𝘁𝗵𝗲𝗺

No complex setup. You just tell Codex what you want.

Example prompt:

"Review this branch with parallel subagents. Spawn one for security risks, one for test gaps, one for maintainability. Wait for all three, then summarize."

Codex spawns 3 agents. They work simultaneously. Each explores a different angle. The main agent combines everything into one clean output.

#### 𝗖𝗵𝗼𝗼𝘀𝗶𝗻𝗴 𝘁𝗵𝗲 𝗿𝗶𝗴𝗵𝘁 𝗺𝗼𝗱𝗲𝗹 𝗳𝗼𝗿 𝗲𝗮𝗰𝗵 𝗮𝗴𝗲𝗻𝘁

This is where it gets interesting.

You can let Codex pick the model automatically, or you can specify it yourself.

→ 𝗴𝗽𝘁-𝟱.𝟰 — For your main agent and anything requiring deep reasoning. Complex logic, ambiguous tasks, security analysis.

→ 𝗴𝗽𝘁-𝟱.𝟯-𝗰𝗼𝗱𝗲𝘅-𝘀𝗽𝗮𝗿𝗸 — Optimized for speed. Exploration, scanning, quick summaries. Use this for your worker agents.

Or actually any model you like and want!

You can also set reasoning effort per agent:

→ high — complex logic, edge case analysis → medium — balanced default → low — when speed matters more than depth

#### Practical example:

Your main agent runs gpt-5.4 with high reasoning. It spawns 3 spark agents with low reasoning to scan your codebase in parallel. They report back. Main agent synthesizes everything.

Codex also ships with 3 built-in agents out of the box:

→ default — general-purpose fallback

→ worker — execution-focused, for implementation tasks

→ explorer — read-heavy, for exploration and scanning

You can use these directly without any config. If you need something custom and deterministic, define your own agent in a TOML file:

name = "security-reviewer" description = "Scans for security vulnerabilities" developer\_instructions = "Focus only on security risks. Report findings clearly." model = "gpt-5.3-codex-spark" model\_reasoning\_effort = "high"

Drop it in .codex/agents/ in your project (or \~/.codex/agents/ for personal use). Codex picks it up automatically.

#### 𝗕𝗲𝘀𝘁 𝘂𝘀𝗲 𝗰𝗮𝘀𝗲𝘀

→ Code review — one agent per concern (security, performance, readability)

→ Bug triage — one agent per reported bug, all running at the same time

→ Large codebase exploration — split the repo, each agent scans a section

→ Test coverage — one writes tests, another checks edge cases, another validates

→ Documentation — agents scan different modules and generate docs in parallel

→ Refactoring — agents analyze different patterns across your codebase at once

The rule is simple: if the work can be split into independent chunks, subagents are the right tool.

#### 𝗪𝗵𝗲𝗻 𝗡𝗢𝗧 𝘁𝗼 𝘂𝘀𝗲 𝘁𝗵𝗲𝗺

→ Parallel writes to the same files — you'll get conflicts

→ Sequential tasks where step 2 depends on step 1 — agents can't coordinate mid-run

→ Simple single-file changes — unnecessary overhead

Also worth knowing: subagents consume more tokens since each one does its own model and tool work independently. Use them when parallelism actually makes sense.

#### 𝗤𝘂𝗶𝗰𝗸 𝘀𝘁𝗮𝗿𝘁

Open Codex and try this:

"Review my project. Spawn 3 subagents:

1. Check for security vulnerabilities
2. Identify missing test coverage
3. Suggest performance improvements Wait for all three, then give me a prioritized action list."

That's it.

Subagents are one of those features that feel obvious once you see them. The main agent focuses on decisions. The subagents handle the noise.

Cleaner context. Faster results. Better output.

What's the first task you'd split into parallel agents? 👇

## 结构化（2）

### 2026-03-17 06:41:13

这篇文章主要介绍了 Codex 新推出的“子代理（subagents）”功能：它把原本由一个代理完成的工作，拆成多个并行的小代理来做，从而减少上下文噪音、提升效率和输出质量。核心思想是：主代理负责统筹决策，子代理负责分头执行和汇报。

- 什么是子代理
  - 过去，Codex 的所有工作都在同一个线程里完成：探索代码、写代码、跑测试全混在一起。
  - 问题是线程会不断堆积“噪音”，比如探索笔记、测试日志、报错堆栈，导致上下文混乱、性能下降。
  - 子代理的改进点是：主代理把任务拆给多个“专门代理”并行处理，最后只接收它们整理好的摘要。
  - 作者用一句话概括：像是“一个大脑，协调一个团队”。

- 怎么使用
  - 不需要复杂配置，直接用自然语言告诉 Codex 你要怎么拆任务即可。
  - 文中示例：让 Codex 对一个分支做并行审查，分别启动 3 个子代理检查“安全风险、测试缺口、可维护性”，等全部完成后再统一总结。
  - 运行方式是：3 个代理同时工作，各自从不同角度分析，最后主代理把结果合并成一份清晰输出。

- 如何给不同代理选模型
  - Codex 可以自动选模型，也可以手动指定。
  - 文中推荐：
    - `gpt-5.4`：适合主代理，或者需要深度推理的任务，比如复杂逻辑、模糊问题、安全分析。
    - `gpt-5.3-codex-spark`：更偏速度，适合探索、扫描、快速总结，适合作为工作型子代理。
  - 还可以给每个代理设置推理强度：
    - `high`：复杂逻辑、边界情况分析
    - `medium`：默认平衡
    - `low`：速度优先
  - 具体例子：主代理用 `gpt-5.4 + high`，再启动 3 个 `spark + low` 的子代理并行扫描代码库，最后由主代理统一归纳。

- 内置代理和自定义代理
  - Codex 自带 3 种代理：
    - `default`：通用型
    - `worker`：偏执行、实现任务
    - `explorer`：偏读取、探索和扫描
  - 如果想要更可控、更稳定的行为，可以自己定义代理，写成 TOML 文件。
  - 文中给的示例是一个 `security-reviewer`：
    - 名称：`security-reviewer`
    - 描述：扫描安全漏洞
    - 指令：只关注安全风险，并清晰汇报结果
    - 模型：`gpt-5.3-codex-spark`
    - 推理强度：`high`
  - 配置文件放在项目目录 `.codex/agents/`，或者个人目录 `~/.codex/agents/`，Codex 会自动识别。

- 最适合的使用场景
  - 文章给了 6 类典型场景：
    - 代码审查：一个代理看安全，一个看性能，一个看可读性
    - Bug 分诊：每个 bug 分给一个代理，同时排查
    - 大型代码库探索：把仓库拆块，每个代理扫一部分
    - 测试覆盖：一个写测试，一个查边界情况，一个做验证
    - 文档生成：不同代理分别扫描不同模块并并行产出文档
    - 重构分析：不同代理同时分析不同代码模式
  - 总结原则很简单：只要任务能拆成彼此独立的部分，子代理就很适合。

- 什么时候不适合用
  - 有 3 类情况不建议使用：
    - 多个代理同时修改同一批文件：容易产生冲突
    - 强依赖顺序的任务：比如第 2 步必须等第 1 步结果出来，子代理无法在运行中途互相协调
    - 非常简单的单文件修改：拆分反而增加额外成本
  - 还要注意一个现实代价：子代理会消耗更多 token，因为每个代理都在独立调用模型和工具，只有在“并行确实有价值”时才值得使用。

- 快速上手示例
  - 文末给了一个可直接尝试的提示词：
    - 检查项目的安全漏洞
    - 找出缺失的测试覆盖
    - 提出性能优化建议
    - 等 3 个子代理都完成后，再输出一份按优先级排序的行动清单
  - 作者最后的结论是：子代理的价值在于让主代理专注“做决策”，把琐碎和噪音交给子代理处理，从而实现更干净的上下文、更快的结果和更好的输出。

这篇文章主要介绍了 Codex 新推出的 `subagents`（子代理）功能：它通过“主代理 + 多个并行子代理”的方式，把复杂任务拆开处理，从而减少上下文噪音、提升效率和输出质量。核心思想很简单：让主代理负责统筹，让子代理分别做专项工作。

- 什么是 `subagents`
  - 过去 Codex 是单线程工作：同一个代理同时做代码探索、写代码、跑测试。
  - 问题在于线程里会不断堆积探索笔记、测试日志、报错堆栈等“噪音”，导致上下文变乱、性能下降。
  - `subagents` 的改进是：把任务交给多个专门代理并行处理，完成后再把结果用干净的摘要汇报给主代理。
  - 作者用一句话概括：像是“一个大脑在协调一个团队”。

- 怎么使用
  - 不需要复杂配置，直接用自然语言告诉 Codex 你想怎么拆分任务即可。
  - 文中示例：让 Codex 并行启动 3 个子代理，分别检查安全风险、测试缺口、可维护性问题，全部完成后再统一总结。
  - 这样主代理最后拿到的是 3 份整理好的结果，而不是混杂的执行过程。

- 模型怎么选
  - Codex 可以自动选模型，也可以手动指定。
  - 文中推荐：
    - `gpt-5.4`：适合主代理，以及需要深度推理的任务，比如复杂逻辑、含糊需求、安全分析。
    - `gpt-5.3-codex-spark`：速度更快，适合子代理做扫描、探索、快速总结。
  - 推理强度也可以单独设置：
    - `high`：复杂逻辑、边界情况分析
    - `medium`：默认平衡
    - `low`：速度优先

- 内置代理与自定义代理
  - Codex 自带 3 个内置代理：
    - `default`：通用兜底
    - `worker`：偏执行，适合实现任务
    - `explorer`：偏读取，适合探索和扫描
  - 如果需要更稳定、可定制的行为，可以自己写 TOML 配置。
  - 文中给出的例子是一个 `security-reviewer` 代理：
    - 名称：`security-reviewer`
    - 职责：扫描安全漏洞

    - 推理强度：`high`

- 最适合的使用场景
  - 文章列了 6 类典型场景：
    - 代码审查：按安全、性能、可读性分别分工
    - Bug 分诊：每个 bug 交给一个代理同时处理
    - 大型代码库探索：按仓库不同部分拆开扫描
    - 测试覆盖：一个写测试、一个找边界情况、一个做验证
    - 文档生成：不同代理扫描不同模块并并行产出文档
    - 重构分析：多个代理同时分析不同代码模式
  - 判断标准很明确：如果任务能拆成彼此独立的块，就适合用 `subagents`。

- 什么时候不要用
  - 不适合并行修改同一批文件，否则容易冲突。
  - 不适合强依赖前后顺序的任务，比如第 2 步必须等第 1 步做完。
  - 不适合简单的单文件小改动，因为会有额外开销。
  - 文章还特别提醒：`subagents` 会消耗更多 token，因为每个代理都要独立调用模型和工具，所以只有在“并行确实有价值”时才值得使用。
