## 正文

**Han1**

最近做了一条开发 pipeline，想分享一下背后的想法。

我是被 loop / goal engineering、还有 auto-goal（让 agent 自己写 goal、自己 spawn 子任务）那一串东西启发的。但真正让我想通的，是一件关于我自己的事：我的 taste 是“一看就知道”型的，不是“能描述”型的。很多东西我得看到了才知道“不对，不是这个”，事先根本写不清楚。冷著问我要什么，我挤不出来；可给我一个丑原型，我立刻知道哪里不对。

所以这条 pipeline 是反过来走的：先丢一个丑到不行的原型逼出我的反应 →把每个“不对，我要…”抄成一条可检查的规则 →这些规则变成验收标准，让 agent 一项一项开发 →而且每一项都由另一个没参与建造的 agent 独立验收，它没办法自己宣布自己做完了。

对比一下不这样做：你丢一句“帮我做 X”，agent 埋头一路跑到底，最后给你一个打磨得很漂亮、却不是你要的东西——还偏偏是在最贵的时候（结尾）才发现。这条 pipeline 做的，就是把“发现不对”这一刻，挪到最前面、最便宜的时候，而且全程不准 agent 放水、自欺。

灵感来源都很值得读：Lance Martin 讲长时间跑的 agent 会偷懒、自恋、偏离目标；Addy Osmani 讲怎么把 session 里反覆出现的修正，提炼成可复用的规则。

## 解读（1）

### 2026-06-17 10:28:51

#### 深度总结

这条开发 pipeline 的核心是：

> **不要一开始逼自己 “说清楚想要什么”，而是先做一个粗糙原型，逼出真实反应，再把反应转成规则，让 agent 按规则开发，并由独立 agent 验收。**

作者的关键洞察是：

- 很多人的品味不是 “可提前描述” 的，而是 “看到后才知道对不对”。
- 传统 AI 开发方式是：  
  **一句需求 → agent 自行完成 → 最后才发现跑偏**。  
  问题是：发现错误太晚，修改成本最高。
- 这条 pipeline 反过来：  
  **先暴露错误 → 提炼规则 → 再执行开发 → 独立验收**。  
  把 “发现不对” 的时刻提前到最便宜的阶段。

流程大致是：

```text
idea
 ↓
1. idea-to-prototype
   先做丑原型，让人产生反应

 ↓
2. prototype-to-roadmap
   根据反馈切成可开发路线图

 ↓
3. roadmap-to-loop
   写成 LOOP.md：任务、完成标准、验收人

 ↓
4. loop-to-goal
   agent 自动拆目标、执行、验收、推进

 ↓
shipped
```

底层还有一个机制：

```text
taste-to-rubric
```

也就是把用户每次说的：

> “不是这个”  
> “这里不对”  
> “我想要这种感觉”

沉淀成`RUBRIC.md`，变成以后可复用的判断标准。

---

#### 深入浅出解读

这套方法本质上是在解决一个问题：

> **人说不清楚需求，但看得出好坏。**

就像装修房子。

如果你一开始对设计师说：

> “帮我做一个高级、舒服、有质感的客厅。”

设计师可能做出一个很贵、很完整、但你完全不喜欢的方案。

更好的方式是：

1. 先给你几个很粗糙的草图；
2. 你看到后说：“不要冷色调”“沙发太商务”“灯光要柔一点”；
3. 设计师把这些反馈整理成规则；
4. 后面所有设计都按这些规则推进；
5. 最后再让另一个人检查：是否真的符合规则。

这条 AI 开发 pipeline 也是如此。

它不是让 AI 一口气 “憋大招”，而是让 AI 先拿出一个 “靶子”，让你打：

> 原型不是为了漂亮，  
> 而是为了让你更快发现：  
> **我不要什么，以及我真正想要什么。**

---

#### 关键价值

##### 1. 把模糊品味变成明确规则

人的 taste 很难直接表达，但可以通过反应捕捉。

```text
反应 → 偏好 → 规则 → 验收标准
```

这让 “感觉不对” 逐渐变成 “哪里不对”。

---

##### 2. 把错误提前暴露

传统方式：

```text
需求模糊 → 开发很久 → 成品偏离 → 高成本返工
```

这套方式：

```text
快速丑原型 → 立刻反馈 → 低成本修正 → 再正式开发
```

核心是：

> 宁愿早期丑，别到最后错。

---

##### 3. 防止 agent 自嗨

作者特别强调：

> 做任务的 agent 不能自己宣布完成。

所以引入独立验收 agent：

```text
开发 agent：负责做
验收 agent：负责查
```

这解决了长期运行 agent 常见的问题：

- 偷懒；
- 自我合理化；
- 偏离目标；
- 做完了但不符合用户真实期待。

---

#### 辩证思考

##### 好的一面

这套方法很适合：

- 需求模糊的产品开发；
- 设计、前端、创意工具；
- 个人开发者 vibe coding；
- 用户自己也说不清 “我要什么” 的场景。

它真正抓住了 AI 协作的关键：

> AI 不只是执行工具，  
> 还可以是 “帮你逼出需求” 的工具。

---

##### 局限的一面

但它也不是万能。

如果项目本身是：

- 金融系统；
- 医疗系统；
- 底层架构；
- 高安全、高确定性工程；

那就不能只靠 “先做丑原型再反馈”。

因为这类项目的核心不是 taste，而是：

- 正确性；
- 稳定性；
- 合规性；
- 边界条件；
- 系统约束。

这时需要更强的前置设计，而不只是反应式迭代。

---

##### 更深一层看

这条 pipeline 的本质不是 “让 AI 更自动化”，而是：

> **重新设计人与 AI 的分工。**

人不必假装自己一开始就知道答案。

人负责：

- 判断；
- 品味；
- 取舍；
- 最终方向。

AI 负责：

- 快速生成；
- 提炼规则；
- 拆解任务；
- 执行开发；
- 辅助验收。

最理想的关系不是：

```text
人下命令，AI 执行
```

而是：

```text
AI 提供刺激，人做判断；
判断沉淀成规则，AI 再规模化执行。
```

---

#### 一句话总结

> 这套 pipeline 的聪明之处在于：  
> **不要求人先说清楚需求，而是用快速原型逼出真实品味，再把品味变成规则，让 AI 按规则开发并独立验收。**

## 结构化（1）

### 2026-06-17 10:36:23

##### 主旨概括

作者分享了一条新的开发 pipeline：先用“很丑的原型”逼出真实反馈，再把反馈转成可检查规则，最后让 agent 按规则开发并由独立 agent 验收。核心目的是把“发现做错了”的时刻提前到成本最低的阶段，避免 agent 最后交付一个精致但不符合需求的成品。

---

##### 1. 灵感来源：从 goal engineering 到 auto-goal

作者的 pipeline 受到以下思路启发：

- **loop / goal engineering**：围绕目标不断循环、修正、推进。
- **auto-goal**：让 agent 自己写 goal，并自动拆分、生成子任务。
- 这些理念促使作者思考：如何让 AI 开发过程更可靠、更接近真实需求。

但真正让作者想通的，不是技术概念，而是对自己需求表达方式的认识。

---

##### 2. 核心洞察：很多需求不是“能提前说清”，而是“看了才知道”

作者发现自己的审美和判断属于“一看就知道”型：

- 事先很难准确描述自己想要什么。
- 如果冷启动问“你要什么”，往往说不清。
- 但只要看到一个很差的原型，就能马上判断：
  - “这里不对”
  - “不是这个感觉”
  - “我想要的是另一种样子”

通俗来说：  
**不是先有清晰需求再开发，而是先看到东西，才能激发出真实需求。**

---

##### 3. Pipeline 的做法：先做丑原型，再提炼规则

这条 pipeline 采用“反过来”的开发路径：

1. **先丢出一个很丑的原型**
   - 目的不是直接做对，而是逼出人的真实反应。
   - 让用户更容易指出“不对”的地方。

2. **把每个反馈记录成规则**
   - 例如：“不对，我要……”这种反馈，会被转写成一条可检查的标准。
   - 这些规则不再只是模糊感受，而变成具体的验收条件。

3. **规则变成验收标准**
   - agent 后续不是自由发挥，而是逐项按照规则开发。

4. **独立 agent 负责验收**
   - 每一项任务完成后，不由开发它的 agent 自己宣布完成。
   - 而是交给另一个没有参与开发的 agent 独立检查。
   - 这样可以减少 agent 自我放水、自我欺骗的问题。

---

##### 4. 与普通 AI 开发方式的区别

普通做法通常是：

> 用户说一句“帮我做 X”，agent 就一路开发到最后。

问题在于：

- agent 可能跑偏。
- 最后交付的东西看起来很精致，但不是用户真正想要的。
- 最糟糕的是，问题往往在项目结尾才暴露。
- 而结尾阶段是修改成本最高的时候。

作者的 pipeline 想解决的正是这个问题：

- 把“发现不对”的时间点提前。
- 在最早、最便宜的阶段暴露问题。
- 用规则和独立验收防止 agent 自作主张。

---

##### 5. 执行机制：像“拿着清单的工头”

在热门回复中，作者补充说明了最后一步：他写了一个自动运行的 goal 引擎，类似一个“拿着清单的工头”。

具体流程是：

- 清单文件是 **LOOP.md**。
- 每条任务都写明：
  - 要做什么；
  - 怎样才算做好。
- 引擎从上到下执行：
  1. 派一个新 agent 去做一条任务；
  2. 做完后，叫另一个 agent 来验收；
  3. 验收通过后，打勾并存档；
  4. 然后进入下一条任务。

关键点是：  
**开发和验收分离，agent 不能自己说自己完成了。**
