## 分析要点

- **核心高价值点**：将本地模型落地抽象为可复用链路：资源评估、权重与引擎适配、服务化验证、工具接入，再按任务拆分为多模型协作流程。
- **留存建议**：建议精读并存档，作为本地模型部署和Agent链路搭建的实践参考（提供了从硬件评估、模型部署、接口验证到工具调用和多模型协作的完整路径，命令与配置具有复用价值。）

**知识要点**

- MoE模型虽然每次只激活部分参数，但部署时仍需加载完整权重，并为推理引擎和KV Cache预留内存。
- 单请求生成速度与多并发聚合吞吐是不同指标，Continuous Batching可提高整机吞吐，比较性能时必须统一测试口径。
- 本地Agent的基本架构是模型通过OpenAI兼容接口提出工具调用，由执行层访问文件、命令或业务接口，再将结果返回模型继续处理。

**行动项**

- 部署前核算模型权重、KV Cache和推理引擎的总内存需求，并据此选择量化版本、上下文长度和并发数。
- 使用官方适配的vLLM分支启动OpenAI兼容服务，并通过curl和基准测试验证可用性、延迟及吞吐。
- 将本地接口接入TUI或Agent框架，先以只读工具验证调用链，再逐步增加文件写入、命令执行和业务接口能力。

#### 02 模型安装部署

先介绍下安装环境：我使用的是 NVIDIA DGX Spark，配备 GB10 芯片和 121.6GB 统一内存，系统为 ARM64 架构的 Ubuntu 24.04。本次部署的是 Ling-3.0-flash-INT4，后面的吞吐测试会使用本机的 Qwen 3.8-27B 作为参照。

官方提供了基础版和 FP8、FP4、INT4 等不同精度版本，大家可以根据自己的硬件选择。

另外还有 8B 的 Ling-3.0-tiny 及 FP8、INT4 版本，普通 Mac 或单张 4090 可以优先从 Tiny 的低精度版本开始尝试。

![Image](https://pbs.twimg.com/media/HP7VWJraAAAH33j?format=jpg&name=large)

---

第一步，下载模型。 我这次使用的是官方 INT4 版本，下载入口👇🏻

- Hugging Face：
  [Ling-3.0-flash-int4](https://huggingface.co/inclusionAI/Ling-3.0-flash-int4)
- ModelScope：
  [Ling-3.0-flash-int4](https://modelscope.cn/models/inclusionAI/Ling-3.0-flash-int4)

如果访问 Hugging Face 不方便，也可以直接从 ModelScope 手动下载，这里就不赘述具体过程了。下载后共有 24 个 safetensors 分片，实测约 71.75GB。运行时还要给推理引擎和 KV Cache 留出空间。

第二步，准备环境。 Ling-3.0-flash 的 BailingMoeV3 架构比较新。我试过用 GGUF 配合 llama.cpp，结果报错 unknown model architecture: 'bailingmoe3'。所以这次直接使用👉🏻

[官方适配的 vLLM 分支](https://github.com/inclusionAI/vllm-ling-v3)：

```text
pip install uv
uv venv ~/my_ling_env
source ~/my_ling_env/bin/activate

git clone -b ling_3_0 https://github.com/inclusionAI/vllm-ling-v3.git
cd vllm-ling-v3
VLLM_USE_PRECOMPILED=1 uv pip install --editable . --torch-backend=auto
```

第三步，启动推理服务。 把模型路径换成本地下载好的 INT4 权重：

```text
vllm serve /path/to/Ling-3.0-flash-int4 \
  --served-model-name ling-int4 \
  --host 127.0.0.1 \
  --port 30000 \
  --trust-remote-code \
  --max-model-len 16384 \
  --gpu-memory-utilization 0.8 \
  --max-num-seqs 8 \
  --reasoning-parser ling3 \
  --speculative-config '{"method":"bailing_hybrid_v3_mtp","num_speculative_tokens":1}'
```

> ⚠️命令中的相关路径，请替换成你本机的真实路径。

这里把上下文上限设为 16K，并发数设为 8，同时开启 MTP 投机解码。

> 说明：MTP（Multi-Token Prediction）会让模型一次尝试预测多个 Token，预测正确的部分可以直接采用，从而减少逐个生成 Token 的计算轮次，提升输出速度。

第四步，验证服务。 启动完成后，发一个最简单的请求：

```bash
curl -s http://127.0.0.1:30000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"ling-int4",
       "messages":[{"role":"user","content":"你好，请用一句话介绍自己。"}],
       "stream":true}'
```

终端开始流式返回内容，就说明这个 124B 模型已经在本地跑起来了。

这里可能有人会疑惑：为什么 Ling 单并发只有 34.77 tok/s，到了 8 并发反而变成了 141.38 tok/s？也有技术朋友会问，这个单并发成绩和一些官方数据相比，是不是偏慢了？

这里需要先说明一下测试的具体方法，以及因为测评方式不同带来的速度不同：

1. 测试方法与真实端到端链路： 本次使用的是本地 OpenAI 兼容接口，通过 HTTP 流式请求进行压测，不是脱离服务框架的离线推理测试。Ling 的每个请求使用同一段约 150 Token 的长文本提示词，最多生成 512 Token。计时从客户端发起 HTTP 请求开始，到流式响应接收完成为止，因此会包含本地 HTTP 调用、服务调度、Tokenizer 处理、Prefill、逐 Token 解码和流式返回等环节。
2. 单路出字速率 vs 整机聚合吞吐： 单流速度（单人真实体感）：$c=1$ 时测出的是单用户的端到端出字速率（约 35.34 tok/s，真实单次对话实测在 38+ tok/s），相当于每秒打出 35 个以上的汉字，肉眼看已经是极快的飞速流式打字效果； 聚合吞吐（并发总产出）：并发增加后，vLLM 会利用 Continuous Batching 将多个请求合并打包送入 GPU 计算，充分复用 Blackwell 的统一内存带宽。在 8 并发下，整机的聚合吞吐直接飙升到了 141.38 tok/s。

至于为什么和某些官方跑分不同，关键还是测试口径。模型精度、推理引擎、上下文长度、输入输出 Token 数、并发规模，以及使用离线推理还是 HTTP 服务，都会影响最终结果。只有这些条件基本一致，数字才适合直接比较。

简单来说：因为测评方式不同带来的速度不同——如果在极高并发（如 32/64 并发）或脱离网络协议的纯计算环境下测试，总吞吐数字会看起来更高；而在我们日常单人对话、写代码的真实生产调用中，Ling 的单流 35+ tok/s 和秒开首字延迟（&lt;220ms），实际使用时已经能明显感觉到回复极度流畅、毫无卡顿。

单并发时，Ling 的平均单路速度约为 35.34 tok/s；到了 8 并发，整机聚合吞吐达到 141.38 tok/s。Qwen3.8 在 8 并发下的聚合吞吐为 32.61 tok/s。这一轮跑下来，Ling 的优势主要体现在出字速度和并发吞吐上，实际使用时也能明显感觉到回复更快。

#### 04 从 API 到 TUI，再到工具调用

前面完成了模型部署和能力测试，但对普通用户来说，curl 更适合用来验证接口是否正常，并不适合作为日常使用方式。真要和本地模型长时间对话，还是需要一个更顺手的交互界面。

所以我先做了一个简单的 TUI，也就是运行在终端里的聊天界面。它并不是什么复杂的软件，我直接让 AI 写了一个 Python 脚本，把本地接口调用、流式输出和对话记录保存封装起来，再用一条命令启动：

```text
python3 ling-3.0-chat.py
```

这样就不用每次手写 curl 了。打开终端就能直接聊天，回答会流式显示，还能看到 TPS、TTFT 和 Token 数。前面几轮能力测试，我就是在这个界面里完成的。

不过，这时候的 TUI 还只是一个文字聊天工具，并没有调用工具的能力。大模型更像一个负责思考的“大脑”，但它没有“手和脚”，没办法直接读取文件、执行命令，也不知道系统当前的真实状态。

想让它调用系统能力，就要给它加上工具调用。简单来说，就是把命令执行、文件读取和写入等操作封装成工具。模型会先判断自己需要什么信息，再发起一次 tool use；Python 脚本负责执行，并把结果交还给模型继续处理。

比如一开始，我让它查看系统的 GPU 信息，它并不能知道真实的占用情况，只能告诉我应该怎么查。加入工具调用之后，它就可以自己执行系统命令，再把查询结果整理好，直接显示在 TUI 里。

基于同样的原理，还可以继续接入 Web 搜索、企业内部接口、数据库等能力。具体接入哪些工具，可以根据自己的业务需求自由扩展。

#### 05 接入可视化界面

平时自己使用，一套 TUI 加上工具调用，其实已经完全够用了。如果还想再进一步，把模型放进一个更完整的 Agent 工作台，就可以接入 Harness 这类智能体框架。

这次我选择梁圣的 DeepSeek Harness，它不只是给模型加一个聊天页面，还提供了上下文管理、工作区、工具调用、权限控制和任务规划等能力，并且自带可以在浏览器中使用的 Web UI。它采用“一切皆插件”的架构，后续可以根据需要继续扩展功能。

需要注意的是，DeepSeek Harness 目前仍处于开发者预览阶段，更新速度很快，后续可能会出现不兼容的改动。类似的开源 Agent 框架还有很多，大家可以根据自己的需求选择，这里就不一一展开了。

接入过程并不复杂，核心就是添加一个自定义模型服务，把地址指向 vLLM 提供的本地接口。除了直接在 Web UI 中配置，也可以修改配置文件，示意如下：

```text
llm-pi-ai:
  providers:
    ling:
      displayName: "Ling-3.0-flash (124B)"
      api: openai-completions
      baseURL: http://127.0.0.1:30000/v1
      apiKeyEnv: OPENAI_API_KEY
      models:
        - id: ling-int4
          name: Ling-3.0-flash (124B MoE)
```

启动 Web UI 后，在浏览器打开默认地址：

```text
http://localhost:3080
```

这样一来，日常聊天、历史记录和模型切换，都可以直接在 DeepSeek Harness 里完成。Harness 本身已经提供了文件操作、命令执行和任务规划等能力，也可以通过插件继续扩展。具体用法和第三方插件，感兴趣的朋友可以自行搜索，这里就不赘述了。

需要注意的是，前面 Python TUI 里由我自己编写的工具不会自动迁移过来。如果还想在 Harness 中继续使用，需要按照它的插件机制重新接入。下面是我为 Ling 做的实际接入效果，大家可以直接看录屏。

#### 06 搭建 AI 工作流

做到这里，从模型部署、对话界面到工具调用，一套围绕 Ling-3.0-flash 的单模型链路就全部打通了。

不过，平时真正做项目时，通常不会只用一个模型。不同模型擅长的事情不一样，把它们组合起来，往往比让一个模型包办所有任务更合适。

Ling-3.0-flash 的优势是文本处理和生成速度，但它不支持原生多模态输入。如果任务里需要理解图片或视频，可以接入 Qwen3.8-27B 这类多模态模型；如果还要生成视频，也可以接入最近开源的 MiniMax H3。每个模型负责自己擅长的部分，再把结果交给下一个模型继续处理。

比如要搭一套视频生成工作流，可以让 Ling 先理解需求、编写脚本和拆分分镜，再让多模态模型检查参考素材和画面一致性，最后交给视频模型生成。生成完成后，还可以再做一轮视觉检查，根据结果修改提示词并重新生成：

```text
需求与素材
→ Ling 生成脚本和分镜
→ 多模态模型检查素材和画面要求
→ MiniMax H3 生成视频
→ 多模态模型检查画面和连续性
→ Ling 根据反馈调整提示词
→ 人完成最终审核
```

#### 大模型本地部署指南：从模型服务到 Agent 工作流

##### 一句话总结

文章以**Ling-3.0-flash INT4**为例，演示了一条可复用的本地 AI 落地路径：

> **下载模型 → 用 vLLM 提供 API → 接入聊天界面 → 增加工具调用 → 搭建 Agent 平台 → 编排多模型工作流。**

核心目的不是展示某套固定配置，而是让模型真正连接本地数据、系统工具与业务流程。

##### 1. 为什么选择本地部署

本地部署主要解决三类问题：

- **数据可控**：文件、对话和业务数据留在本机或内网。
- **降低边际成本**：高频、长文本调用不再按 Token 计费。
- **高度可定制**：可以自由选择模型、量化精度、推理引擎及内部工具。

但 “Token 自由” 并不等于零成本，本质是将 API 费用转化为**硬件、电力、部署和运维成本**。

##### 2. 模型与硬件选择

文章部署的是**Ling-3.0-flash**：

- MoE 模型，总参数量**124B**
- 每次推理激活约**5.1B**参数
- INT4 权重约**71.75GB**
- 虽然只激活部分参数，但完整权重仍需加载进内存

测试设备为 NVIDIA DGX Spark，配备约**121.6GB 统一内存**。普通设备可优先尝试**Ling-3.0-tiny 8B 的低精度版本**。

##### 3. 本地部署的四个步骤

###### 第一步：下载模型

从 Hugging Face 或 ModelScope 下载 Ling-3.0-flash INT4 权重，共 24 个分片。

除了模型权重，还必须为推理引擎、上下文和 KV Cache 预留内存。

###### 第二步：安装推理环境

由于 BailingMoeV3 架构较新，通用 llama.cpp 暂不支持，因此使用官方适配的**vLLM 分支**。

vLLM 的职责是加载模型、管理上下文与并发，并提供 OpenAI 兼容 API。

###### 第三步：启动模型服务

关键配置包括：

- 上下文长度：16K
- 最大并发：8
- 显存利用率：80%
- 开启 MTP 投机解码

MTP 会尝试一次预测多个 Token，以减少逐 Token 解码次数，提高生成速度。

###### 第四步：验证 API

通过`/v1/chat/completions`发起流式请求。若终端能够持续返回内容，说明模型已成功在本地运行。

##### 4. 性能与能力表现

###### 性能测试

文章给出的核心结果：

| 场景 | Ling-3.0-flash 表现 |
|---|---:|
| 单路端到端速度 | 约 35 tok/s |
| 8 并发聚合吞吐 | 141.38 tok/s |
| vLLM 基准总吞吐 | 133.10 tok/s |
| MTP 接受率 | 67.35% |

并发提升后，vLLM 通过 Continuous Batching 合并请求，因此整机总吞吐会明显增加，但这不代表单个用户的出字速度同步增长。

###### 能力测试

文章从三个方向验证模型：

1. **逻辑推理**：检查能否理解变式条件，而不是机械套公式。
2. **安全边界**：面对高风险操作，是否先识别风险并请求确认。
3. **长文本理解**：能否从长上下文中定位关键信息，并保持稳定输出。

##### 5. 从聊天模型升级为本地 Agent

###### TUI：解决交互问题

作者先用 Python 封装了终端聊天界面，实现：

- 流式输出
- 对话历史保存
- TPS、TTFT 和 Token 数展示

这一步只是改善使用体验，模型仍然只能 “说”，不能直接操作系统。

###### 工具调用：给模型加上 “手和脚”

将文件读写、命令执行等能力封装为工具后，模型可以：

1. 判断需要调用什么工具；
2. 发起 Tool Use；
3. 由 Python 执行真实操作；
4. 将结果返回给模型继续处理。

同样的方法还可以接入搜索、数据库、企业内部 API 等能力。

###### Agent 工作台：提供完整运行环境

文章进一步接入 DeepSeek Harness，使本地模型获得：

- Web UI
- 上下文和历史记录管理
- 工作区
- 文件与命令工具
- 权限控制
- 任务规划
- 插件扩展

接入的本质，是将 Harness 的模型地址指向 vLLM 提供的本地 OpenAI 兼容接口。

##### 6. 多模型工作流才是最终形态

单一模型通常无法覆盖所有任务。文章建议按能力拆分角色：

- **Ling**：需求理解、脚本生成、文本处理
- **多模态模型**：图片、视频和素材理解
- **视频模型**：生成视频
- **人类**：最终审核与决策

示例流程：

```text
需求与素材
→ Ling 生成脚本和分镜
→ 多模态模型检查素材
→ 视频模型生成内容
→ 多模态模型检查一致性
→ Ling 根据反馈调整提示词
→ 人工审核
```

真正有价值的不是 “同时运行多个模型”，而是让模型围绕同一任务**分工、交接、反馈和迭代**。

##### 7. 实际落地的约束

###### 资源约束

多个大模型同时常驻，对显存和内存要求极高。部署前需要计算：

- 模型权重占用
- KV Cache
- 推理引擎开销
- 并发与上下文长度
- 多模型同时运行的资源峰值

资源不足时，可以采用量化、按流程切换模型、多机部署或本地与云端混合调用。

###### 框架约束

不同 Agent 框架的工具和插件机制并不通用。TUI 中自行开发的工具，迁移到 Harness 后通常需要重新适配。

###### 测试口径

性能数字高度依赖模型精度、输入输出长度、并发量、推理引擎和测试链路，不能简单横向比较。

此外，文章日志中的平均 TTFT 约为**19.7 秒**，但后文又提到首字延迟低于**220ms**，两组数据可能来自不同测试场景，文中未充分解释。与 Qwen 的对比也未完全统一精度和架构条件，因此更适合作为部署体验参考，而非严格基准结论。

##### 核心启示

本地大模型的价值不只是 “免费聊天”，而是获得一套可控的 AI 基础设施：

> **模型负责推理，工具连接真实系统，Agent 管理任务，多模型工作流完成复杂业务。**

是否值得部署，最终取决于数据敏感度、调用频率、任务稳定性、硬件成本和运维能力。对企业而言，最有价值的方向通常不是追求最大模型，而是找到**效果、成本、安全与可维护性之间的最佳平衡**。

## 结构化（1）

### 2026-08-21 09:53:27

#### 文章精炼总结

文章以 **Ling-3.0-flash 124B MoE 模型**为例，完整演示了从本地部署、性能测试，到 TUI、工具调用、Agent 框架和多模型工作流的搭建过程。核心目标是让模型、数据和工具都掌握在自己手中，减少 API Token 成本与外部服务依赖，实现可复用的“本地 Agent”。

##### 01｜基础概念与模型选择

- **模型精度决定部署门槛**：同一模型通常有基础版、FP8、FP4、INT4 等版本，精度越低，体积和内存需求通常越小。
- 本次使用官方 **Ling-3.0-flash INT4**，完整权重约 **71.75GB**。
- Ling-3.0-flash 是 **124B MoE（混合专家）模型**：
  - 每次推理只激活约 **5.1B 参数**；
  - 但完整的 **124B 权重仍需加载进内存**，不能只按激活参数估算硬件需求。
- **推理引擎不是模型本身**，其作用是加载权重、管理上下文和并发，并提供 API。
- 作者选择官方适配的 **vLLM**，因为它支持该模型的 INT4 权重及 **MTP 投机解码**。

##### 02｜本地部署流程

###### 1. 硬件与系统环境

作者使用的设备为：

- **NVIDIA DGX Spark**
- **GB10 芯片**
- **121.6GB 统一内存**
- **ARM64 Ubuntu 24.04**

如果硬件较弱，可以尝试 **Ling-3.0-tiny 8B** 的 FP8 或 INT4 版本，普通 Mac 或单张 RTX 4090 更适合从这类小模型开始。

###### 2. 下载模型

可从以下平台获取官方权重：

- Hugging Face：Ling-3.0-flash-int4
- ModelScope：Ling-3.0-flash-int4

INT4 版本共有 **24 个 safetensors 分片**，约占 **71.75GB**。实际运行时还必须为推理引擎和 **KV Cache** 预留额外内存。

###### 3. 安装官方适配的 vLLM

由于 Ling 使用较新的 **BailingMoeV3** 架构，作者尝试 GGUF 与 llama.cpp 时遇到：

```text
unknown model architecture: 'bailingmoe3'
```

因此改用 Ling 官方适配的 vLLM 分支，主要流程为：

1. 使用 `uv` 创建独立 Python 环境；
2. 克隆 `vllm-ling-v3` 仓库的 `ling_3_0` 分支；
3. 安装预编译依赖及对应 Torch 后端。

###### 4. 启动推理服务

核心启动配置包括：

- OpenAI 兼容接口：`127.0.0.1:30000`
- 上下文长度：**16K**
- 最大并发：**8**
- GPU 内存利用率：**0.8**
- 开启 Ling 推理解析器
- 开启 **MTP 投机解码**

MTP 会尝试一次预测多个 Token，预测正确的部分可直接采用，从而减少逐 Token 生成的计算轮次，提高输出速度。

启动后，可通过 `/v1/chat/completions` 接口发送 `curl` 请求。若终端能正常流式返回回答，就说明 124B 模型已在本地运行。

##### 03｜性能与能力测试

###### 1. Token 吞吐表现

vLLM 自带的 `bench serve` 测试结果如下：

| 指标 | 结果 |
|---|---:|
| 成功请求 | 20 |
| 失败请求 | 0 |
| 输出吞吐 | **84.34 tok/s** |
| 总 Token 吞吐 | **133.10 tok/s** |
| MTP 接受率 | **67.35%** |
| 平均 TTFT | **19,692.98ms** |
| 平均 TPOT | **44.61ms** |
| 平均 ITL | **74.09ms** |

并发对比中：

| 模型 | 单并发/单流速度 | 8 并发整机聚合吞吐 |
|---|---:|---:|
| Ling-3.0-flash | 约 **35.34 tok/s**，实际对话可达 38+ tok/s | **141.38 tok/s** |
| Qwen 3.8-27B | 未给出 | **32.61 tok/s** |

8 并发下，Ling 的聚合吞吐约为 Qwen 的 **4.34 倍**。

###### 2. 为什么并发越高，总吞吐反而越高？

- **单流速度**反映一个用户实际看到的出字速度，Ling 约为每秒 35 个以上 Token，肉眼已经非常流畅。
- **聚合吞吐**是所有并发请求的总产出。
- vLLM 会通过 **Continuous Batching（连续批处理）**把多个请求合并计算，因此 8 并发时可以更充分利用硬件，整机吞吐明显上升。

不同测试结果不能只看数字直接比较，因为以下因素都会影响性能：

- 模型精度与量化方式
- 推理引擎
- 上下文长度
- 输入、输出 Token 数
- 并发规模
- 离线推理还是 HTTP 流式服务

文中基准日志显示高并发测试的平均 TTFT 约为 **19.69 秒**，同时作者称真实单人调用的首字延迟可低于 **220ms**；两者测试场景和负载不同，不宜直接混为同一指标。

###### 3. 实际能力测试

作者从三个方向测试模型，但没有给出统一量化分数：

1. **逻辑推理**  
   使用鸡兔同笼变式题、洗车问题和洗车机问题。其中加入 **4 只三条腿机械鸟**，用于判断模型是在理解条件，还是机械套用熟悉答案。

2. **安全边界**  
   观察模型面对高风险操作时，是否会直接执行，还是先识别风险、向用户确认，并提供更安全的方案。

3. **长文本能力**  
   将关键信息隐藏在较长上下文中，测试模型的信息检索准确度、输出速度和稳定性。

##### 04｜从 API 升级到 TUI 与工具调用

`curl` 适合验证接口，但不适合作为日常聊天工具。作者让 AI 编写了一个 Python TUI，即终端聊天界面，实现：

- 调用本地模型接口
- 流式显示回答
- 保存对话记录
- 展示 TPS、TTFT 和 Token 数
- 使用一条命令启动

```bash
python3 ling-3.0-chat.py
```

不过，纯聊天模型只有“脑”，没有操作系统的“手和脚”，无法直接知道 GPU 占用、读取文件或执行命令。

因此，作者进一步加入了 **工具调用**：

1. 将命令执行、文件读写等能力封装成工具；
2. 模型判断需要调用哪个工具；
3. Python 脚本实际执行；
4. 将结果返回给模型继续整理和回答。

例如，未接入工具时，模型只能告诉用户“如何查询 GPU”；接入后，它可以直接运行系统命令并返回真实 GPU 信息。相同方式还能扩展到 Web 搜索、数据库和企业内部接口。

##### 05｜接入可视化 Agent 工作台

如果需要更完整的 Web 体验，可以接入 Agent 框架。作者选择了 **DeepSeek Harness**，其能力包括：

- 浏览器 Web UI
- 上下文与历史记录管理
- 工作区
- 文件和命令工具
- 权限控制
- 任务规划
- 插件扩展

接入的核心是添加自定义模型服务，将 `baseURL` 指向本地 vLLM：

```text
http://127.0.0.1:30000/v1
```

启动后，在浏览器访问：

```text
http://localhost:3080
```

即可进行聊天、切换模型和管理历史记录。

需要注意：

- DeepSeek Harness 仍处于**开发者预览阶段**，更新可能带来不兼容改动。
- 原先 Python TUI 中自行编写的工具不会自动迁移，必须按照 Harness 的插件机制重新接入。

##### 06｜搭建多模型 AI 工作流

真实项目通常不应让一个模型包办全部任务，而应根据能力分工：

- **Ling-3.0-flash**：文本理解、脚本编写、提示词生成，速度较快；
- **Qwen 3.8-27B 等多模态模型**：理解图片、视频和参考素材；
- **MiniMax H3**：负责视频生成。

文章给出的视频工作流示例：

```text
需求与素材
→ Ling 生成脚本和分镜
→ 多模态模型检查素材与画面要求
→ MiniMax H3 生成视频
→ 多模态模型检查画面和连续性
→ Ling 根据反馈调整提示词
→ 人工最终审核
```

一旦流程固定，后续只需替换需求和素材即可重复使用。

###### 本地多模型部署的资源限制

多个模型同时常驻会消耗大量显存或统一内存：

- Ling-3.0-flash INT4：约 **72GB**
- Qwen 3.8-27B BF16：约 **51.77GB**
- 还需额外容纳 KV Cache、推理引擎和视频模型

因此，即使是 121.6GB 统一内存的 DGX Spark，也很难让这些模型全部同时常驻。可采用以下方案：

- 按工作流步骤切换模型；
- 使用更低精度的量化版本；
- 将不同模型分布到多台设备；
- 提前计算权重、KV Cache 和运行时内存需求。

真正的多模型工作流，不是让多个模型各自运行，而是围绕同一个任务依次协作、相互检查。

##### 07｜结论：重点是可复用的方法，而非固定配置

文章最终总结出一条通用路径：

```text
下载模型权重
→ 配置推理引擎
→ 启动本地 API
→ 接入 TUI 或 Web UI
→ 添加工具调用
→ 连接 Agent 框架
→ 编排多模型工作流
```

即使未来更换模型、量化精度或推理引擎，这套思路仍然适用。本地部署的主要价值包括：

- **数据可控**：文件、对话和业务数据可留在本机或内网，权限由自己管理。
- **适合高频使用**：无需按调用量持续支付 Token 费用，也减少对网络和第三方服务的依赖。
- **方便定制**：模型、精度、推理引擎、工具、数据库和内部接口都可自行调整。

文章的核心观点是：应根据任务、硬件和预算选择合适模型，再将模型与工具、Agent 和工作流结合起来，最终形成一套属于自己的本地 AI 系统，实现更自主的“Token 自由”。

## 口播总结（1）

### 2026-09-17 00:21:54

本地部署大模型，真正有价值的地方，不只是省下接口调用费。更重要的是，你可以把模型接入本地文件、系统命令和业务工具，最终搭成一套数据可控、能够反复使用的智能体工作流。

这次部署的模型，是蚂蚁百灵开源的 Ling 三点零 Flash。它是一个总参数量一千二百四十亿的混合专家模型，简称 MoE。所谓混合专家，是指模型虽然拥有大量参数，但每次推理只激活其中一部分。Ling 每次大约激活五十一亿参数。不过要注意，完整的一千二百四十亿参数权重，仍然需要加载进内存。不能只根据激活参数量判断硬件需求。

部署使用的是官方 INT4 量化版本。INT4 可以理解为用更低的数字精度保存模型，从而减小体积、降低运行门槛。这个版本实测约七十一点七五 GB。

硬件是一台英伟达 DGX Spark，配备 GB10 芯片和一百二十一点六 GB 统一内存，系统是 ARM64 架构的 Ubuntu。七十多 GB 的模型装进去以后，还必须给推理引擎和 KV Cache 留空间。KV Cache 是模型处理上下文时使用的缓存。因此，模型文件能够放进内存，不等于模型一定能够稳定运行。

如果硬件没有这么强，也不必从一千二百四十亿参数的版本起步。Ling 还有八十亿参数的 Tiny 版本。普通 Mac 或单张四零九零显卡，可以优先尝试 Tiny 的低精度版本。

完整部署可以概括为四步。

先从 Hugging Face 或 ModelScope 下载模型权重。这个 INT4 版本包含二十四个权重分片。

然后准备推理环境。Ling 使用的 Bailing MoE V3 架构比较新。作者尝试用 GGUF 格式配合 llama.cpp 运行时，遇到了架构无法识别的问题。因此，最终选择了官方适配的 vLLM 分支。

这里要区分模型和推理引擎。模型是权重本身，vLLM 则是负责加载权重、管理上下文、处理并发，并向外提供接口的软件。

第三步是启动 vLLM 服务。作者把上下文上限设为一万六千 Token，把最大并发数设为八，并开启了 MTP 投机解码。MTP 的意思是多 Token 预测。普通生成通常一个 Token 一个 Token 往外写，MTP 会提前尝试预测后面的多个 Token。预测正确的部分可以直接采用，从而减少计算轮次，提高输出速度。

第四步是向本地服务发送一个最简单的聊天请求。如果终端能够持续返回模型生成的文字，就说明这个一千二百四十亿参数的模型已经在本机运行起来了。由于 vLLM 提供的是兼容 OpenAI 格式的接口，后续很多聊天工具和智能体框架都可以直接接入。

模型跑起来以后，性能数字要谨慎理解。

在一轮二十个请求的服务测试中，Ling 的输出吞吐约为每秒八十四个 Token，总 Token 吞吐约为每秒一百三十三个，MTP 的预测接受率约为百分之六十七。

另一轮并发测试中，单并发的端到端生成速度约为每秒三十五个 Token。并发增加到八路以后，整台机器的聚合吞吐达到每秒一百四十一个 Token。作为参照，本机的 Qwen 三点八二十七 B，在相同八并发测试中的聚合吞吐约为每秒三十三个 Token。

为什么并发增加后，总吞吐反而更高？因为 vLLM 会使用连续批处理，把多个请求合并送入 GPU 计算。单个用户看到的是自己这一路的出字速度，整机聚合吞吐统计的则是所有请求加起来的总产出。两者不是同一个指标。

同样，不同机构的跑分也不能只看最终数字。模型精度、推理引擎、上下文长度、输入和输出的 Token 数、并发规模，以及离线推理还是通过 HTTP 提供服务，都会影响结果。只有测试条件接近，性能数字才适合直接比较。

部署完成只是第一层。下一步，是让模型从“能聊天”变成“能做事”。

直接使用命令行请求，适合检查接口，却不适合长期对话。作者先让人工智能编写了一个 Python 终端聊天界面，也就是 TUI。它把本地接口调用、流式输出和对话记录封装起来，还能显示生成速度、首字延迟和 Token 数量。

不过，此时的模型仍然只有“大脑”，没有“手和脚”。例如，你让它查看显卡占用情况，它并不知道机器当前的真实状态，只能告诉你应该输入什么命令。

解决办法是加入工具调用。具体做法，是把读取文件、写入文件和执行命令等系统能力，封装成模型可以选择的工具。模型先判断自己缺少什么信息，再发起工具调用。Python 程序负责真正执行操作，并把结果交还给模型。模型随后根据真实结果继续回答。

按照同样的思路，还可以接入网页搜索、数据库和企业内部接口。但工具越强，风险也越高，所以文件目录、命令范围和操作权限需要受到限制。

如果希望使用浏览器界面和更完整的智能体能力，还可以接入 DeepSeek Harness 一类框架。它能提供上下文管理、工作区、工具调用、权限控制和任务规划。接入的核心，是把模型地址指向 vLLM 的本地接口。不过，这类框架仍可能快速更新。原先在 Python 聊天界面中编写的工具，也不会自动迁移，需要按照新框架的插件机制重新接入。

再往前一步，就是多模型工作流。因为不同模型擅长的任务不同，没有必要让一个模型包办一切。

例如制作视频时，可以先让 Ling 理解需求、编写脚本并拆分分镜。再让多模态模型检查参考素材和画面要求。随后交给视频模型生成。生成完成后，多模态模型检查画面一致性和连续性，Ling 再根据反馈修改提示词，最后由人完成审核。

这套流程一旦固定，之后只需替换需求和素材，就能重复使用。但多模型同时常驻，对内存要求非常高。Ling 的 INT4 版本约占七十二 GB，文中的 Qwen 二十七 B模型约占五十二 GB，再加上缓存和视频模型，很难全部装进同一台设备。资源不足时，可以按步骤切换模型，改用量化版本，或者把模型分散到多台机器。

最值得记住的是，本地部署不是简单地把聊天网页搬到电脑里。真正完整的路径，是下载权重、启动推理服务、接入对话界面，再赋予模型工具和工作流。

本地模型的优势也不只是不用按次支付 Token 费用。文件、对话和业务数据可以留在本机或内网，模型和工具都能按需求调整。只要根据任务、设备和预算选对模型，即使从较小的量化版本开始，也能逐步搭出一套属于自己的本地智能体。

## 深度解读（1）

### 2026-09-17 00:38:38

#### 本地大模型真正买到的不是“Token 自由”，而是工作流控制权

这篇文章最有价值的部分，不是成功在 DGX Spark 上跑起一个 124B 模型，而是完整展示了本地 AI 系统的分层：**模型权重负责能力，vLLM 提供标准化推理服务，TUI 或 Web UI 负责交互，工具与 Agent 框架连接真实任务。**一旦这几层通过 OpenAI 兼容接口解耦，底层模型就可以替换，上层工作流不必推倒重来。

这比某个模型的短期跑分更值得保留。开源模型变化很快，但“权重—推理服务—工具—工作流”的链路相对稳定。本地部署因此不只是安装软件，而是在建立一个自己可控制的 AI 基础设施。

##### MoE 降低的是计算量，不是内存门槛

Ling-3.0-flash 总参数量为 124B，每次推理只激活约 5.1B 参数，这是它能获得较高生成速度的重要原因。但未被激活的权重仍需加载，INT4 版本也占约 71.75GB，还要为推理引擎和 KV Cache 留空间。文章使用的是拥有 121.6GB 统一内存的 DGX Spark，并非普通个人电脑环境。

这揭示了评价本地模型时容易混淆的两个变量：**激活参数决定主要计算成本，总参数和精度决定主要存储门槛。**MoE 可以让大模型“跑得快”，却不必然让它“装得下”。对个人用户，8B 量化模型更现实；对企业，124B 模型是否值得本地化，要看数据敏感度、调用规模和运维能力，而不是仅看 API Token 单价。

所谓“Token 自由”也不是免费：成本从按量付费转移成硬件折旧、电力、部署维护和模型升级。只有调用长期稳定且足够高频，或者隐私、离线与内网接入具有硬约束，本地方案才可能更优。

##### 吞吐数据说明了部署能力，却不足以证明模型能力

文章区分单用户速度与整机聚合吞吐是准确的：Continuous Batching 能让并发请求共享 GPU 计算，因此 8 并发的 141.38 tok/s 不等于单个用户获得这一速度。对交互产品，首字延迟和单路生成速度更影响体验；对批处理、客服或内部平台，聚合吞吐才决定单位成本。

但文中的数字存在需要澄清之处：基准日志显示平均首 Token 延迟约 19.7 秒，后文却称“秒开首字延迟 <220ms”，显然不是同一测试条件，不能直接并列。Ling 与 Qwen 的 4.34 倍吞吐差距也可能同时受到模型架构、量化精度、推理引擎和并发设置影响，不能推导为能力或性价比高出四倍。文章提到逻辑、安全和长文本测试，却没有给出系统结果，因此能力结论仍然偏演示性质。

##### Agent 的关键瓶颈会从模型转向权限与可迁移性

给模型接入文件、Shell、数据库后，它才从聊天工具变成可执行系统，但风险也随之变化：隐私数据留在本地，不代表系统天然安全；一个拥有宽泛命令权限的本地 Agent，同样可能误删文件、泄露凭据或执行提示注入带来的恶意操作。

更值得注意的是，作者自制 TUI 中的工具不能自动迁移到 Harness，必须重新按插件机制接入。这说明真正需要标准化的已不只是模型 API，还有**工具协议、权限边界、执行审计和工作流状态**。对于产品团队，最值得投入的未必是绑定某个热门模型，而是建立可替换模型、可复用工具、最小权限和人工确认机制。模型会快速迭代，可靠的控制层才是更持久的资产。
