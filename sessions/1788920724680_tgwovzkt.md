## 分析要点

- **核心高价值点**：连接容器归工作区所有，而具体凭证具有代理或用户所有者；运行时按调用者身份解析凭证，从而支持多用户隔离授权而无需在业务代码中传递用户ID。
- **留存建议**：作为托管代理连接、用户授权与凭证治理的实施参考长期保留（系统说明了连接所有权、认证模式、运行时解析、授权中断和前端恢复流程，具有直接开发与排障价值。）

**知识要点**

- 代理拥有的凭证适合共享服务账户，用户拥有的OAuth凭证则按运行调用者身份解析，缺少授权时会触发credential\_authorization\_required中断。
- 托管深度代理可承担OAuth回调、令牌存储、刷新和同意流程，应用前端只需处理连接链接、状态轮询与运行恢复。
- MCP连接可通过服务器元数据发现并动态注册OAuth客户端；无法自动注册时需改用目录OAuth或手动配置端点。

**行动项**

- 为每个连接明确选择代理所有或用户所有模式，并为生产代理创建最小权限的专用服务账户。
- 在自定义前端实现授权中断识别、HTTPS连接链接展示、认证状态轮询及stream.respond恢复流程。
- 为本地开发配置对应的MDA\_DEV\_&lt;SLUG&gt;环境变量，并验证连接轮换无需重新部署即可生效。

## 正文

连接将受管深度代理链接到外部服务，如 GitHub、Notion 或 Tavily。凭据存储在您的 LangSmith 工作区中。在创作的工具或 MCP 服务器定义中使用 `connections.get(...)` ，即可在运行时解析该凭据。 Connections let you:

- 将凭据保留在项目之外： `mda deploy` 在每次部署时将 `.env` 值作为部署密钥收集。连接值则保留在工作区中。
- 为每个调用者赋予独立身份：用户拥有的连接会解析发起请求者的凭据，因此代理会读取该用户的文档并以其名义执行操作。而环境变量对所有人只保存一个值。
- 省去 OAuth 集成工作：受管深度代理负责执行授权往返流程，因此项目无需回调路由、令牌存储或同意页面。这些流程由您的受管深度代理自动处理。
- 在多个代理间复用同一个 slug：连接属于工作区，因此多个部署可以解析同一个 slug。每个部署在该 slug 下持有自己的凭证：在每个项目根目录下运行一次 `mda connections create <slug>` 。轮换某个部署的值将在其下次运行时生效，无需重新部署。

在 LangSmith 中存储凭证以便在你的托管深度代理中使用，只需一条命令： 读取它只需一行代码： 本页其余部分涵盖围绕这些步骤的两个选择：谁拥有凭证，以及服务如何进行身份验证。

托管深度代理目前处于公开测试阶段，仅在美国区域的 LangSmith 云上可用。

#### Choose a credential owner

每次 `connections.get(...)` 调用都会指明其解析的凭证所有者： `connections.get(...)` 解析为字符串形式的凭证值。 连接是一个容器，它属于工作区而非所有者。其中的凭证有所有者。没有 `--owner` 标志：你使用的创建模式决定了所有者。 `connections.get(...)` 选择的是所有者，而非创建所有者。若请求的所有者没有自己的凭据，则 `agent` 的运行会失败，并针对 `user` 引发 `credential_authorization_required` 中断。同一 slug 下存储的、属于其他所有者的凭据不能满足此查找。 代理拥有的凭据属于项目的部署，因此请在至少一次成功的 `mda deploy` 之后创建它们。一次部署只读取其自身拥有的凭据。若要从第二个部署解析相同的 slug，请在该项目根目录下再次运行 `mda connections create <slug>` ：在已有 slug 上，该命令会附加一个新的代理拥有的凭据，而不会失败。

##### Identify the caller

用户拥有的连接会根据托管深度代理附加到运行上的调用者身份进行解析。该身份的来源取决于代理的调用方式： 默认身份声明验证的是 LangSmith API 密钥。该密钥认证的是调用客户端，而非个人用户，因此所有持有该密钥的调用者都会被解析为同一身份。若要为每位已登录用户提供独立凭证，请声明 Supabase 身份。 代码绝不会将用户 ID 传递给 `connections.get(...)` 。运行时负责解析调用者身份，并返回该用户的凭证。

Slack 和 Studio 为调用者完成完整的授权往返流程。对自定义渠道的一流支持正在开发中。若要在当前基于调用者身份构建自定义前端，请参阅处理授权中断并联系 LangChain 团队。

#### Choose a create mode

所有权决定了代理如何使用凭据。创建模式决定了该凭据如何到达工作区，并取决于外部服务的认证方式： For example:不要在一个命令中混合使用模式。例如， `--mcp` 不能与 `--oauth` 、自定义端点、 `--client-id` 或密钥值结合使用。

##### Name a connection

`mda connections create` 的第一个参数是一个 slug：即你对连接的命名，也是你的代码传递给 `connections.get(...)` 的名称。它不是提供者名称，提供者名称应传递给 `--oauth` ： Slug 在工作区内是唯一的。请使用小写字母、数字和单个连字符，并选择一个能标识该连接指向哪个账户的名称，例如 `organization-tavily` 或 `engineering-notion` 。

#### Create an opaque secret

为代理存储一个固定的秘密。从环境变量、文件、标准输入或提示中读取该值。此模式适用于自定义工具的 API 密钥，例如 Tavily 搜索密钥。使用 CLI 创建的不透明秘密归代理所有。 将源值放入 Shell 环境或项目 `.env` 文件中，然后从该变量创建连接。在项目根目录下运行命令。CLI 需要 LangSmith API 密钥和工作区 ID。 这将 `TAVILY_API_KEY` 中的值存储为代理拥有的秘密。运行时代码通过 `connections.get(...)` 解析它。 提供该值的其他方式：

- **`--secret-from-file PATH`** ：从仅包含该秘密的文件中读取一个值。
- stdin：通过管道或重定向传入值，例如 `printf '%s' "$ACME_API_KEY" | mda connections create acme-api` 。
- 交互式提示：在 TTY 上省略值标志。CLI 会隐藏输入，因此秘密不会显示在屏幕上或 Shell 历史记录中。

使用 CLI 创建的不透明秘密始终归代理所有。对于按调用方分配的凭据，请使用 OAuth 连接。 签发一个属于代理的密钥，而不是重复使用个人密钥。专用密钥可以进行范围限定、轮换和撤销，而不会影响共享该密钥的任何其他内容。

##### Use the OAuth catalog

每个 OAuth 提供商都需要相同的五项设置：授权 URL、令牌 URL、令牌端点认证方法、授权参数和默认范围。目录条目提供全部五项，因此 `--oauth <service>` 加上您自己的客户端 ID 和密钥即为完整配置。 List the catalog with:该命令会打印每个服务的默认作用域以及注册应用的页面。它不会调用 LangSmith，因此无需工作区 ID 或 API 密钥。将第一列中的值传递给 `--oauth` 。 没有默认作用域的服务需要 `--scope` 。 GitHub 需要一个 OAuth 客户端 ID 和客户端密钥。设置 `GITHUB_CLIENT_SECRET` ，然后创建连接。将 `********` 替换为客户端 ID： 创建时，CLI 会打印重定向 URI，用于向提供商注册。在调用方授权之前，请先在提供商的应用程序设置页面上注册该 URI。该 URI 遵循您的 LangSmith 主机，例如生产环境中的 `https://api.smith.langchain.com/v1/agent-auth/oauth/callback` 。 Optional flags:

- **`--scope SCOPE`** ：替换目录默认值。对每个作用域重复此操作。
- **`--allowed-scope SCOPE`** ：后续授权可能请求的上限。默认为 `--scope` 值，并且必须覆盖每个 `--scope` 。
- **`--authorization-param KEY=VALUE`** ：额外的授权查询参数。每个参数重复一次。
- **`--auth-method METHOD`** ：客户端向令牌端点进行身份验证的方式： `client_secret_basic` 、 `client_secret_post` 或 `none` （用于公共客户端）。默认为目录服务的方法。

##### 授权代理拥有的 OAuth 账户

默认情况下，OAuth 连接会在每次调用时从每个调用者处收集授权。传入 `--authorize` 可自行登录一次，并为部署存储该授权。此后，每个调用者都将以该账户身份操作，且不会看到授权提示： CLI 会为您登录的账户启动授权流程，并将生成的授权存储到部署中。运行时代码将其解析为代理拥有的凭据： `--authorize` 仅适用于 OAuth 连接。可将其与 `--oauth` 、自定义端点或 `--mcp` 结合使用。请从项目目录运行，因为该授权属于该项目的部署。 当每个调用者都应作为共享账户而非其自身身份操作时，请使用代理拥有的 OAuth 账户。例如，一个公司 Notion 账户向问答代理授予读取权限，即为此类场景。

授权一个由你的团队拥有的专用账户，而不是你自己的账户。你登录所用的账户将成为代理代表每位调用者执行每项操作时的身份标识。使用个人账户会让你付出三方面的代价：

- 代理将获得你在该提供商处的全部访问权限。
- 提供商的审计日志会显示你的名字，记录代理所执行的操作。
- 当你自己的访问权限发生变化时，代理将停止工作。

以这种方式授予的权限始终与授权它的账户绑定，即使是专用账户也不例外。密码重置、会话撤销或账户停用都会终止该权限，因此请将该账户视为生产基础设施。 为专用账户赋予代理所需的最小 `--scope` 值。设置 `--allowed-scope` 以限制后续任何授权可请求的范围。

##### Read the interrupt in your UI

渲染此中断的前端是一个 Web 应用程序，因此无论代理是用 Python 还是 TypeScript 编写的，这些示例都是 TypeScript。 在 `stream.interrupt` 上检测凭据门控负载，渲染连接卡片，然后在每次授权存储后使用 `stream.respond` 恢复：

```
import { useStream } from "@langchain/react";

type CredentialAuthorizationRequired = {

  type: "credential_authorization_required";

  message?: string;

  credentials: Array<{

    slug: string;

    kind: "oauth2" | "secret";

    connect_url?: string;

    auth_id?: string;

  }>;

};

function isCredentialAuthorization(

  value: unknown

): value is CredentialAuthorizationRequired {

  return (

    typeof value === "object" &&

    value !== null &&

    "type" in value &&

    value.type === "credential_authorization_required"

  );

}

export function Chat() {

  const stream = useStream({

    apiUrl: "https://your-deployment.example",

    assistantId: "agent",

  });

  const payload = stream.interrupt?.value;

  const credentialAuth = isCredentialAuthorization(payload) ? payload : null;

  return (

    <div>

      {/* messages … */}

      {credentialAuth && (

        <ConnectCard

          payload={credentialAuth}

          onComplete={async (connectedSlugs) => {

            await stream.respond(

              {

                type: "credential_authorization_completed",

                connected_slugs: connectedSlugs,

              },

              { interruptId: stream.interrupt?.id }

            );

          }}

        />

      )}

    </div>

  );

}
```

#### Agent 接入外部服务，真正的难题是“代表谁行动”

这份文档表面上是 LangChain 的连接配置指南，真正值得关注的是它对 Agent 身份模型的拆分：**连接外部系统不再只是保存一个 API Key，而是要明确每次运行代表哪个主体、使用哪份权限。**

传统环境变量只有一个部署级值。无论谁调用 Agent，它都以同一账户访问 GitHub、Notion 或搜索服务。这适合无用户差异的后台能力，却无法支持“读取我的文档”“替我提交 Issue”这类场景。Managed Deep Agents 将其拆成三层：工作区中的连接标识 `slug`、部署或用户拥有的凭据，以及运行时识别出的调用者身份。代码只请求某个连接，平台负责解析当前应该使用哪份凭据。

##### 凭据所有权决定了产品到底是谁在行动

文档区分了两种重要模式。

**代理拥有凭据**时，所有调用者共享同一身份。典型场景是企业公共 Notion 知识库、统一购买的搜索 API，或专门为 Agent 创建的服务账户。这种模式易于运维，但所有操作在外部系统看来都来自同一个账户，因此应使用专用账户、最小权限和可独立撤销的密钥，而不是开发者个人账号。

**用户拥有凭据**时，每位调用者单独完成 OAuth，Agent 以该用户身份读取和操作资源。这不仅带来个性化，也保留了外部系统原有的权限边界与审计身份。不过，一个容易忽略的前提是：系统必须真的知道调用者是谁。默认 LangSmith API Key 识别的是调用客户端，多个用户共用同一 Key 时，仍会被视为同一身份；要做到逐用户隔离，需要接入 Supabase 等用户身份声明。

因此，产品设计时不能只问“是否支持 GitHub”，而应先问：**这是一个公共能力、组织服务账户，还是用户委托？** 选错模式，功能可能正常运行，权限模型却从一开始就是错的。

##### OAuth 被重新定义为可恢复的运行状态

更有迁移价值的设计，是把缺少授权处理成 Agent 运行中的标准中断。平台在模型开始推理前检查所需连接；缺少凭据时，一次性返回授权清单，运行暂停，用户授权后再从原状态恢复。前端只展示连接链接并轮询结果，不接触访问令牌。

这比“工具调用失败后让模型解释错误”更可靠：授权是确定性的执行前置条件，不应交给模型临场判断。对任何需要审批、付款确认、人工复核的 Agent 产品，这种**门控—暂停—恢复**机制都可复用。它也意味着 Agent UI 不能只是聊天消息流，还必须能承载结构化中断和异步恢复。

##### 集成成本下降，但治理问题没有消失

OAuth 目录、MCP 自动发现与客户端注册，确实减少了回调路由、令牌存储和刷新逻辑；同一 `slug` 还能跨多个 Agent 复用接口名称，并独立轮换各部署的凭据。但这只是消除了认证工程，并未自动解决授权范围、危险操作确认、审计归因和凭据失效后的恢复策略。

目前该能力仍是仅限美国区的公开测试版，自定义渠道支持也未完全成熟。因而更适合把它视为一个清晰的架构信号，而非立即锁定的平台选择：**Agent 基础设施正在从“替应用保管秘密”，走向“在每次执行中解析委托关系”。** 对真正进入企业工作流的 Agent，后者很可能比模型能力本身更早成为产品能否上线的决定因素。

## 口播总结（1）

### 2026-09-20 00:34:08

在托管深度代理中，连接的核心作用，是把 GitHub、Notion、Tavily 等外部服务的凭据，与代理项目分开管理。凭据保存在 LangSmith 工作区里。代理运行时，只需要通过 connections.get，按连接名称读取凭据。

这样做有三个主要价值。凭据不必写进项目或环境变量。不同调用者可以使用各自的身份。OAuth 的授权跳转、令牌存储和刷新等流程，也可以交给托管平台处理。

不过，理解连接时，最重要的不是服务类型，而是凭据由谁拥有。

连接本身是工作区里的一个容器。连接中的具体凭据，则有两种所有者。一种是代理，也就是某个项目部署。另一种是调用代理的用户。

代理拥有的凭据，适合所有调用者共用一个服务账户。例如，问答代理统一读取一个公司的 Notion 账户。用户拥有的凭据，则适合让代理代表每位用户行动。例如，每位员工连接自己的 GitHub，代理只能读取和操作这个员工有权访问的内容。

运行代码不会把用户编号直接传给 connections.get。托管运行时会识别当前调用者，并自动找到属于这个人的凭据。如果该用户还没有授权，代理不会拿其他用户的凭据顶替，而是暂停运行，要求当前用户完成授权。

这里有一个容易忽略的身份问题。默认情况下，调用者身份来自 LangSmith 的接口密钥。接口密钥认证的是调用客户端，不一定是某个具体的人。因此，共用同一把接口密钥的调用者，可能会被视为同一个身份。如果希望每位已登录用户都有独立凭据，需要声明 Supabase 身份，或者使用平台支持的其他调用者身份机制。

代理拥有的凭据还与具体部署绑定。要创建这类凭据，项目至少要成功部署过一次。即使多个代理使用相同的连接名称，每个部署仍然要在自己的项目目录中创建一次凭据。轮换凭据后，新值会在下一次运行时生效，不需要重新部署。

连接名称在命令中叫作 slug，也就是代码传给 connections.get 的标识名。这个名称不是服务提供商的名字，而是你为具体连接起的名字。它在工作区内必须唯一，通常只使用小写字母、数字和单个连字符。名称最好能说明连接指向哪个账户，例如 organization-tavily，或者 engineering-notion。

创建连接主要有三种方式，选择哪一种，取决于外部服务如何认证。

第一种是不透明秘密，也就是固定的 API 密钥。它适合 Tavily 搜索密钥一类的场景。可以从环境变量、只保存密钥的文件、标准输入，或者隐藏输入提示中读取秘密，再用 MDA connections create 命令存入工作区。通过命令行创建的不透明秘密始终归代理所有，不能用来给每位调用者分别保存凭据。

安全上，最好为代理签发专用密钥，而不是复用个人密钥。专用密钥可以单独限制权限、轮换和撤销，也不会影响个人账户的其他用途。

第二种是 OAuth 连接。OAuth 是一种让用户授权应用访问外部账户的标准机制。LangSmith 提供常见服务的 OAuth 目录。目录中包含授权地址、令牌地址、认证方式、授权参数和默认权限范围。对于 GitHub 等服务，通常还需要提供自己注册的客户端编号和客户端密钥，并把命令行工具给出的回调地址登记到服务商后台。

默认情况下，OAuth 连接会要求每位调用者分别授权。如果创建连接时使用 authorize 选项，则可以由管理员先登录一次，把授权保存为代理拥有的凭据。此后，所有调用者都通过同一个账户操作，不再分别看到授权提示。

共享 OAuth 账户虽然方便，但风险也更集中。不要直接使用管理员的个人账户。否则，代理可能继承这个人的全部访问权限，外部服务的审计日志也会把代理操作记录在这个人名下。一旦个人权限变化，代理还可能停止工作。

更稳妥的做法，是建立由团队管理的专用账户，只授予代理真正需要的最小权限。还可以设置允许申请的权限上限，避免后续授权扩大范围。即使是专用账户，也要把它视为生产基础设施。密码重置、会话撤销或账户停用，都可能让代理失去访问能力。

第三种方式是 MCP OAuth 连接。MCP，也就是模型上下文协议，可以让代理连接远程工具服务器。如果远程 MCP 服务器支持 OAuth 客户端自动注册，托管深度代理会发现服务器的认证信息，并自动注册客户端，不需要手动提供客户端编号和密钥。

MCP 服务器可以先在项目中声明，再用对应的连接名称创建连接。也可以直接提供服务器地址。如果地址没有写协议，系统会按 HTTPS 处理。如果服务器不支持自动注册，命令行工具会明确报错，并提示改用普通 OAuth 配置。部署时，系统也会尝试自动补齐缺失的用户自有 MCP 连接；如果发现或注册失败，部署会提前终止。

用户授权时，托管深度代理会通过“授权中断”完成整个过程。代理在模型开始处理请求之前，会检查本次运行所需的用户凭据。如果缺少一个或多个授权，系统只触发一次凭据授权中断，把所有缺失连接放在同一个负载中。

在 Slack 和 LangSmith Studio 中，这套流程由平台直接处理。用户打开安全的 HTTPS 授权链接，完成同意后，代理从暂停位置继续运行。自定义前端则需要读取中断负载，展示每个连接的授权入口，并轮询授权状态。状态可能是等待中、已完成、失败或过期。所有连接都完成后，前端再发送恢复指令，让原来的运行继续。

访问令牌不应该进入前端界面。授权系统会代替前端保存令牌。代理恢复后，再通过 connections.get 读取。前端只负责引导授权和确认状态。

当前版本还有两个重要限制。第一，托管深度代理的连接功能仍处于公开测试阶段，目前只在美国区域的 LangSmith 云中提供。第二，不透明秘密的授权中断不会自带连接链接。自定义前端如果需要收集这类秘密，必须用隐藏输入接收，再为现有连接名称创建凭据。

本地开发时，代理拥有的不透明连接可以从特定环境变量读取。变量名以 MDA_DEV 开头，连接名称要转成大写，并把连字符改成下划线。例如，organization-tavily 对应 MDA_DEV_ORGANIZATION_TAVILY。

最值得记住的是，连接不仅是在保存密钥，更是在定义代理以谁的身份行动。共享服务账户，应使用代理拥有的凭据；代表个人访问数据，应使用用户拥有的 OAuth 凭据。无论采用哪种方式，都应使用专用账户、最小权限和清晰的连接名称，把凭据管理与项目代码彻底分开。

## 深度解读-口播（1）

### 2026-09-30 11:58:49

让一个代理连接 GitHub、Notion 或搜索服务，关键不只是把密钥填进去，还要弄清楚：代理究竟在用谁的身份，访问谁的数据，又代表谁执行操作。LangChain 的受管深度代理，把这些问题交给“连接”来管理。

连接的基本作用，是把外部服务的凭据保存在 LangSmith 工作区里。代理运行时，再通过连接名称读取所需凭据，不必把密钥直接写进项目。

这与环境变量有一个重要区别。部署时，项目环境文件里的值会被收集为部署密钥；连接中的凭据则留在工作区。连接还可以根据调用者身份，提供不同用户各自的授权，而不是让所有人共用一个环境变量。

不过，要理解连接，最重要的是分清两个层次：连接本身属于工作区，连接里面的凭据才有具体的所有者。

你可以把连接想成一个有名字的容器。这个比喻只是为了帮助理解：知道容器的名字，不代表就能拿到里面任意一份凭据。运行时还必须明确，要读取的是代理拥有的凭据，还是当前用户拥有的凭据。

代理拥有的凭据，属于项目的部署。比如，一个问答代理统一使用公司的 Notion 账户，所有调用者都通过这个账户读取资料。

用户拥有的凭据，则属于发起请求的人。比如，两个人使用同一个代理访问 GitHub，代理应当分别读取两个人自己的授权，访问各自有权查看的仓库。

这两种凭据不能互相顶替。如果代码要求当前用户的授权，系统不会因为同一个连接名称下面已有代理的凭据，就直接拿来使用。缺少用户授权时，运行会触发授权中断，等待用户完成连接。

这里还有一个容易误解的地方：多个部署可以使用同一个连接名称，但这不表示它们自动共用同一份代理凭据。

代理拥有的凭据要在至少一次成功部署之后创建。第二个项目想使用相同的连接名称，也需要在自己的项目目录中创建对应凭据。每个部署只读取属于自己的那一份。某个部署的凭据轮换后，下一次运行就会使用新值，无需重新部署。

所以，连接名称可以复用，凭据的归属却必须明确。

接下来，用户拥有的连接还有一个前提：系统必须知道，当前调用者到底是谁。

默认情况下，受管深度代理验证的是 LangSmith 的接口密钥。这个密钥证明的是调用客户端的身份，不是某个自然人的身份。如果多个人使用同一个接口密钥，他们会被解析成同一个调用者，而不是自动拥有各自独立的凭据。

文档给出的做法，是为每位已登录用户配置 Supabase 身份。这样，运行时才能按用户区分授权。

读取连接时，工具代码不需要自己传入用户编号。调用者身份由运行时解析，随后返回对应用户的凭据。换句话说，按用户隔离授权，不只是工具代码的问题，也取决于代理入口是否正确识别了用户。

弄清楚“凭据归谁”，再来看“凭据怎么进入系统”。这里主要有三种方式。

最直接的一种，是保存固定密钥，比如搜索服务的接口密钥。文档把这种值称为“不透明秘密”：系统保存这个值，工具在运行时取出并使用。

密钥可以从环境变量、文件、标准输入或者隐藏输入提示中读取。通过命令行创建的这类秘密，始终归代理所有。如果需要按调用者分别授权，就应当使用 OAuth 连接。

OAuth 是一种让用户登录外部服务，并同意授予访问权限的机制。受管深度代理会处理授权流程，因此项目不需要自己搭建回调路由、令牌存储、刷新逻辑或同意页面。

对于目录中已经支持的服务，目录会提供授权地址、令牌地址和默认权限范围等配置。你仍然需要提供自己的客户端标识和密钥，并把创建时显示的回调地址，注册到服务提供方的应用设置中。没有默认权限范围的服务，还需要明确指定范围。

OAuth 默认按调用者收集授权。但如果你在创建时先登录一个账户，并把这份授权保存给部署，那么之后所有调用者都会以这个共享账户的身份操作，不再分别看到授权提示。

这正是共享账户方便的地方，也是需要谨慎的地方。

文档建议，不要用自己的个人账户给代理做共享授权，而要使用团队拥有的专用账户。否则，代理可能获得你的全部访问权限，服务商的审计日志会把代理操作记在你的名字下，你个人权限的变化也可能让代理停止工作。

即使用了专用账户，授权仍然依附于这个账户。密码重置、会话撤销或账户停用，都可能终止授权。因此，这个账户应当被当作生产基础设施来维护，并且只授予代理真正需要的最小权限。还可以设置后续授权允许请求的权限上限。

第三种方式，是连接远程 MCP 服务器。MCP 是一种让代理连接外部工具的协议。对于支持 OAuth 客户端自动注册的服务器，受管深度代理可以发现授权配置并注册客户端，你不必手动提供客户端标识和密钥。

不过，自动配置有条件。如果服务器不支持自动注册，命令行会提示改用常规 OAuth 配置，而不是自动绕过授权。

最后，看授权缺失时，代理会怎样运行。

在模型开始第一轮处理之前，系统会检查这次运行需要的用户连接。如果用户缺少一个或多个授权，系统会统一暂停运行，发出一次授权中断。用户完成授权后，代理再用这个用户的凭据继续。

Slack 和 LangSmith Studio 已经内置了这套交互。以 Slack 为例，调用者可以直接打开授权链接，完成同意，然后恢复运行，不需要再进入 LangSmith 操作。

如果你做的是自定义前端，就需要读取授权中断，显示连接入口，并检查授权是否完成。授权失败或链接过期时，应当让用户发起新的运行，取得新链接。所需连接都完成后，再恢复原来的运行。

这里有一条明确的安全要求：不要把访问令牌展示在界面中。授权由认证服务保存，代理恢复后再通过连接读取。

这些能力目前仍处于公开测试阶段，而且只在美国区域的 LangSmith 云上可用。自定义渠道的一流支持仍在开发中，也不能假设所有凭据都有授权链接。例如，固定秘密类型的中断就没有连接链接，需要另外处理输入和保存。

最值得记住的是：连接管理的不只是密钥，还管理代理代表谁行动。用户各自的数据，应当配合各自的身份和授权；统一服务账户，则需要明确的凭据归属、专用账户和最小权限。只有这些边界清楚，连接外部服务才不只是“能调用”，而是能够持续、可控地运行。

文档介绍如何为LangSmith托管深度代理创建和使用外部服务连接，涵盖代理或用户拥有的凭证、不透明密钥、通用OAuth、MCP自动注册、授权中断、前端恢复及本地开发限制。

###### 知识要点
- 代理拥有的凭证适合共享服务账户，用户拥有的OAuth凭证则按运行调用者身份解析，缺少授权时会触发credential_authorization_required中断。
- 托管深度代理可承担OAuth回调、令牌存储、刷新和同意流程，应用前端只需处理连接链接、状态轮询与运行恢复。
- MCP连接可通过服务器元数据发现并动态注册OAuth客户端；无法自动注册时需改用目录OAuth或手动配置端点。

###### 行动项
- 为每个连接明确选择代理所有或用户所有模式，并为生产代理创建最小权限的专用服务账户。
- 在自定义前端实现授权中断识别、HTTPS连接链接展示、认证状态轮询及stream.respond恢复流程。
- 为本地开发配置对应的MDA_DEV_&lt;SLUG>环境变量，并验证连接轮换无需重新部署即可生效。
