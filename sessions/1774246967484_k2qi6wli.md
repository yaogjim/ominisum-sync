## 正文

**Hrishi**

Clausetta（Clawd + Rosetta）仍然是我见过的 hanks 做的最酷的事情之一：复杂代码之间的即时连接器。它也是开源的。

它是一个非常简单的 hank，它使\*\*任何\*\*代理框架都能访问并符合相同的接口规范——我们的接口规范（实际上是我们从未升级过的原始 Claude 接口规范）。因此，它是一个 AI 程序，能够自动适配任何代理，使其能够用与 Claude Code 相同的语言进行交互。

试试它：  
克隆 [https://github.com/SouthBridgeAI/hankweave-runtime/tree/release/alpha/learning/examples/clausetta/hank.json…](https://github.com/SouthBridgeAI/hankweave-runtime/tree/release/alpha/learning/examples/clausetta/hank.json) 或替换到下面的命令中：

bunx hankweave -i "&lt; 您选择的代理框架名称&gt;"

它会尝试构建一个从该代理到 hankweave 的连接器。如果完成，你可以使用生成的适配层来编写你自己的编码到 pi、opencode 或任何你想要的内容。

我们生活在疯狂的时代。

它的工作原理很简单。有一个密码子设置一切，还有一个密码子在最后编写文档，但核心环节是两个密码子之间的简单循环——构建和验证。

我们加载一个测试套件和一个 Markdown 规范作为测试装置。在几个循环内（即使是俳句）——你可以构建一些相当可靠的连接器。

我们现有的用于 Gemini CLI 和 Codex 的垫片是以这种方式生成的——这些是我们几乎每天都会使用的垫片。

有时候使用和制作这些垫片感觉就像粘合代码的未来。编码智能体是最难对接的对象之一，因为涉及大量的并行工作、状态和副作用。它们如何处理会话？并行工具调用？子代理？

我们与 Clausetta hank 的合作流程使得在生产环境中部署适配层成为可能，并且当底层 harness 更新时可以重新生成它们。流程如下：

我们发现问题 / 测试框架 X 获得更新 -&gt; 我们更新 hank 并重新运行它 -&gt; 我们部署 shim

真正的规范驱动开发——在那里，hank 就是规范。如果你看 Clausetta，你会发现它并不特定于任何一个代理。

#### 文章主旨

这篇内容主要在介绍一个叫 **Clausetta（Clawd + Rosetta）** 的开源项目：它可以把不同的 AI 代理框架自动适配到同一套接口规范上，让它们像 `Claude Code` 一样工作。  
作者认为这是一种很有前景的“规范驱动开发”方式，尤其适合解决编码智能体之间对接复杂、更新频繁的问题。

##### 1. Clausetta 是什么

- Clausetta 被作者称为他见过的 **最酷的项目之一**，本质上是一个“复杂代码之间的即时连接器”。
- 它是 **开源** 的，核心目标很明确：让 **任何代理框架** 都能接入并遵循同一套接口规范。
- 这里采用的接口规范，是他们自己的规范，准确说是 **“从未升级过的原始 Claude 接口规范”**。
- 换句话说，Clausetta 相当于一个 AI 程序，可以 **自动把任意代理适配成能用 Claude Code 语言交互的形式**。

##### 2. 它能解决什么问题

- 它解决的是 **不同代理框架之间接口不统一** 的问题。
- 生成适配层后，开发者就可以把自己的编码能力接到不同系统上，比如文中提到的：
  - `pi`
  - `opencode`
  - 或其他任意你想接入的框架
- 作者特别强调，编码智能体其实是 **最难对接的一类对象之一**，因为里面牵涉很多复杂因素：
  - 并行工作
  - 状态管理
  - 副作用
  - 会话处理
  - 并行工具调用
  - 子代理协作

##### 3. 怎么使用 Clausetta

- 作者给出了一个直接的体验方式：
  - 克隆示例配置：`hank.json`
  - 或者直接运行命令：
  
```bash
bunx hankweave <hank 的链接> -i "<你选择的代理框架名称>"
```

- 这条命令会尝试 **自动构建从目标代理到 hankweave 的连接器**。
- 如果生成成功，你就能使用这个适配层，把自己的代码工作流接到目标代理框架中。

文中给出的示例链接是：

- `https://github.com/SouthBridgeAI/hankweave-runtime/tree/release/alpha/learning/examples/clausetta/hank.json`

##### 4. 它的工作原理

作者说它的原理其实并不复杂，整体流程可以概括为三部分：

- 一个“密码子”负责初始化全部设置
- 一个“密码子”负责最后写文档
- 中间最核心的是两个步骤不断循环：
  - **构建**
  - **验证**

这意味着它不是一次性手工写死，而是通过反复测试和修正，逐步生成可靠的适配器。

##### 5. 它为什么能做得比较可靠

- Clausetta 会加载两类测试材料作为“测试夹具”：
  - 一个 **测试套件**
  - 一份 **Markdown 规范**
- 作者认为，只需要经过 **几个循环**，即使过程很短，也能做出 **相当可靠的连接器**。
- 这说明它的可靠性不是靠人工反复硬编码，而是靠：
  - 明确的规范
  - 测试驱动
  - 自动验证循环

可以简单理解成：  
先告诉系统“应该符合什么规范”，再用测试不断检查“是不是真的符合”，最后得到可以投入使用的适配层。

##### 6. 已经有哪些实际成果

- 作者提到，他们现有的 **Gemini CLI** 和 **Codex** 的 shim（垫片/适配层），就是 **用这种方式生成的**。
- 更重要的是，这些 shim **几乎每天都在使用**。
- 这说明 Clausetta 不是一个停留在概念层面的实验，而是已经有 **实际生产价值** 的工具。

##### 7. 为什么作者觉得这代表未来

- 作者说，有时候制作和使用这些 shim，会让人感觉像是在接近 **“粘合代码的未来”**。
- 原因在于：随着 AI 编码代理越来越多，不同系统之间互联互通会越来越重要。
- Clausetta 提供的不是某个一次性的适配脚本，而是一种 **可重复生成、可随着底层更新而继续迭代的机制**。

##### 8. 生产环境中的工作流程

作者给出了一套比较清晰的生产流程：

1. 发现问题，或测试框架 `X` 更新  
2. 更新对应的 `hank`  
3. 重新运行它  
4. 部署新的 `shim`

这套流程的关键点在于：

- 适配层不是手工一点点修补，而是可以 **重新生成**
- 当底层 harness 更新时，也能快速跟上
- 这体现了作者所说的 **“真正的规范驱动开发”**

##### 9. “hank 就是规范” 的含义

- 作者特别强调：在这个体系里，**hank 本身就是规范**。
- 也就是说，规范不只是写在文档里给人看，而是直接进入生成和验证流程。
- 如果去看 Clausetta 的设计，会发现它 **并不绑定某一个特定代理**。
- 这也是它通用性强的原因：它面向的是“适配方法”，而不是某一个单独产品。

##### 10. 作者的整体态度

- 作者对这个项目明显非常兴奋，甚至说“我们生活在疯狂的时代”。
- 热门回复里，作者还补充了一句很有意思的话：
  - **“现在写 Hanks 已经是它这辈子最难的时候了。”**
- 这句话背后的意思是：虽然现在写这类适配逻辑还不轻松，但作者相信以后只会越来越容易。

#### 总结

- Clausetta 是一个 **开源的 AI 适配器生成方案**，目标是把任何代理框架接入统一接口规范。
- 它通过 **测试套件 + Markdown 规范 + 构建/验证循环**，自动生成可靠的连接器。
- 文中提到的 **Gemini CLI** 和 **Codex** shim 已经是实际案例，而且被 **几乎每天使用**。
- 它最大的价值在于：面对代理框架更新频繁、接口复杂的问题，团队可以通过 **更新 hank 并重新生成 shim** 的方式持续维护系统，这是一种很典型的 **规范驱动开发** 思路。
