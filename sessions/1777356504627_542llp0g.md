**jolestar**

AI Coding 时代，好的编程习惯仍然重要

最近做一个 Agent benchmark，发现不能简单地用开发者视角来评估一个编程任务对 AI 的复杂度。

比如一个重构任务：把一个几千行的大文件，按功能拆成十多个小模块。

这个任务对开发者来说其实不算难，主要工作就是移动代码、整理 imports、编译验证，新手也能搞定。

所以想着用一个简单的任务来做一下 benchmark，结果却出乎意料。

Claude Code 判断这个任务比较大，尝试拆了一部分，提了个 PR 写了 Future work 打算分步来。

我自己的 Agent 是“硬上”，往完整拆分的方向推进了更多，但代价也很明显：Token 消耗是 Claude 的几十倍，后面大量时间都花在反复读文件、修编译错误、再读文件、再修错误上。

这让我意识到，人觉得简单的任务，对 Agent 不一定简单。

对人来说，这类重构很多时候就是“把这一段挪过去”。但对 Agent 来说，它要先分批读大文件，记住哪些函数和哪些测试有关，再生成一堆跨文件修改，最后通过编译错误一点点补洞。看起来像机械活，实际变成了一个高 Token、高状态管理成本的任务。

前一段时间看到有人说，AI Coding 时代，拆分模块这些编程原则没那么重要了，反正人也不看代码。现在看，我不太同意。模块边界清楚、文件粒度合适、依赖关系简单，不只是方便人读，也是在帮 Agent 降低任务复杂度。

从另一个角度看，现在 Agent 的读文件和改文件工具，对这种重构也不太顺手。

Coding Agent 改文件，主要还是文本替换。比如 Claude Code 常见的是 old\_string / new\_string 模式：先给出一段旧文本，再替换成新文本。Codex 常用的是 apply\_patch：生成一个类似 git diff 的 patch，表达把旧的内容替换成新的。它们都适合小范围修改，但如果要删除一大段旧代码，或者把一批函数挪到别的文件，模型往往还是要先把原始内容读进上下文，再生成一大段替换或 diff。

所以我后来给 Agent 一个提示，让它先用脚本、sed、perl 这类工具把大文件粗拆开，直接把旧内容删掉，写到新文件中，然后再逐个慢慢修，它的完成度确实高了许多。Agent 默认不会这样做，主要是因为系统提示词里会强烈要求 Agent 用内置工具修改文件，而不是命令行工具。

再往前想一步，Coding Agent 可能还需要更高级的编辑工具。不是只给它一个“替换文本”的接口，而是先通过 parser、LSP 或 compiler 建立代码结构，让 Agent 可以像 IDE 一样做重构：移动函数，删除 impl block，整理 imports。不知道是否有朋友做这方面的尝试。

总的来说，即便是 AI Coding 时代，好的编程习惯还是有价值的。尽量在早期通过 harness engineering，把好的编程习惯变成 Agent 的默认工作方式，比后来再重构的成本要小很多。

## 通俗精炼（1）

### 2026-04-28 06:07:29

#### AI Coding 时代，好的编程习惯仍然重要

##### 核心观点

即使进入 AI Coding 时代，清晰的模块划分、合理的文件粒度、简单的依赖关系依然非常重要。  
这些习惯不仅方便人类维护代码，也能显著降低 AI Agent 理解和修改代码的复杂度。

##### 关键发现：人觉得简单，AI 未必简单

作者在做 Agent benchmark 时发现，一个“把几千行大文件拆成十多个小模块”的重构任务：

- 对人类开发者来说不算难，主要是移动代码、整理 import、编译验证。
- 对 AI Agent 来说却很复杂，需要反复读取大文件、记住函数关系、跨文件修改、修复编译错误。
- 结果是 Token 消耗巨大，状态管理成本很高，效率并不理想。

这说明：开发者视角下的“简单机械活”，对 Agent 可能是高成本任务。

##### AI Agent 当前的局限

目前主流 Coding Agent 的文件编辑方式仍偏基础：

- Claude Code 常用 `old_string / new_string` 文本替换。
- Codex 常用 `apply_patch` 生成 diff。
- 这些方式适合小范围修改，但不适合大规模重构、代码搬迁、批量删除。

因此，Agent 往往需要先把大量代码读进上下文，再生成大段替换内容，导致效率低、错误多。

##### 有效改进：让 Agent 使用脚本辅助重构

作者发现，如果提示 Agent 先用脚本、`sed`、`perl` 等命令行工具粗拆大文件，再逐步修复问题，任务完成度会明显提升。

但很多 Agent 默认不会这么做，因为系统提示词通常更鼓励使用内置编辑工具，而不是命令行工具。

##### 未来方向：更高级的代码编辑工具

作者认为，Coding Agent 需要的不只是“文本替换”接口，而是更接近 IDE 的结构化重构能力，例如：

- 基于 parser、LSP、compiler 理解代码结构；
- 支持移动函数、删除实现块、自动整理 imports；
- 让 Agent 以代码结构为单位操作，而不是纯文本替换。

##### 产品启示

AI Coding 并不会让工程规范失效，反而会让好的代码结构更有价值。

越早通过工程规范和 harness engineering，把良好的编程习惯变成 Agent 的默认工作方式，后续维护和重构成本就越低。

##### 主旨概括

作者通过一次 Agent benchmark 发现：**人类开发者觉得简单的重构任务，对 AI Coding Agent 未必简单**。即使进入 AI Coding 时代，清晰的模块划分、合理的文件粒度、简单的依赖关系等良好编程习惯，仍然非常重要。

##### 1. Benchmark 中的意外发现：人觉得简单，AI 不一定简单

作者最近做一个 Agent benchmark，选择了一个看似简单的重构任务：

- 将一个**几千行的大文件**，按功能拆成**十多个小模块**。
- 对人类开发者来说，这类任务通常不难：
  - 移动代码；
  - 整理 `imports`；
  - 编译验证；
  - 即使新手也能完成。

但实际测试结果出乎意料：

- **Claude Code** 判断任务较大，只拆了一部分，并提交 PR，把剩余内容写成了 `Future work`，计划分步完成。
- 作者自己的 Agent 则选择“硬上”，尝试完成更多拆分，但代价很高：
  - Token 消耗是 Claude 的**几十倍**；
  - 后续大量时间花在反复：
    - 读文件；
    - 修编译错误；
    - 再读文件；
    - 再修错误。

##### 2. 为什么这类任务对 Agent 很难？

对人来说，这种重构像是“把一段代码挪到另一个地方”。

但对 Agent 来说，复杂度高很多：

- 它需要分批读取大文件；
- 需要记住哪些函数和哪些测试相关；
- 需要生成大量跨文件修改；
- 最后还要根据编译错误不断补洞。

所以，看似是机械劳动，实际对 Agent 来说变成了：

- **高 Token 消耗任务**；
- **高上下文管理成本任务**；
- **高状态维护成本任务**。

##### 3. AI Coding 时代，模块化仍然重要

作者反驳了一种观点：  
有人认为 AI Coding 时代，模块拆分等编程原则没那么重要了，因为“反正人也不看代码”。

作者认为并非如此：

- 清晰的模块边界；
- 合适的文件粒度；
- 简单的依赖关系；

这些不仅方便人类阅读，也能帮助 Agent 降低任务复杂度。

换句话说，好的代码结构不仅是“给人看的”，也是“给 AI 更好处理的”。

##### 4. 当前 Coding Agent 的编辑工具存在局限

作者指出，现在 Coding Agent 的文件修改方式并不适合大规模重构。

常见方式包括：

- **Claude Code** 常用 `old_string / new_string`：
  - 给出一段旧文本；
  - 替换成新文本。
- **Codex** 常用 `apply_patch`：
  - 生成类似 `git diff` 的 patch；
  - 表达旧内容如何替换为新内容。

这些方式适合小范围修改，但不适合：

- 删除大段旧代码；
- 把一批函数移动到新文件；
- 大规模跨文件拆分。

因为模型往往仍要先把原始内容读进上下文，再生成大段替换或 diff，导致成本很高。

##### 5. 用脚本辅助拆分，效果更好

作者后来给 Agent 增加了提示，让它优先使用：

- 脚本；
- `sed`；
- `perl`；
- 命令行工具；

先把大文件粗略拆开：

- 直接删除旧内容；
- 写入新文件；
- 再逐个修复问题。

结果发现，Agent 的完成度明显提高。

不过，Agent 默认通常不会这样做，因为系统提示词往往强烈要求它使用内置工具修改文件，而不是命令行工具。

##### 6. 未来可能需要更高级的代码编辑工具

作者进一步提出，Coding Agent 可能需要更高级的编辑能力。

不应只提供“文本替换”接口，而应该借助：

- parser；
- LSP；
- compiler；

先建立代码结构，让 Agent 能像 IDE 一样做重构，例如：

- 移动函数；
- 删除 `impl block`；
- 自动整理 `imports`。

不过在热门回复中，作者也提到：  
目前 LSP 工具感觉帮助有限，因为它主要能分析代码，不能直接编辑代码。

##### 7. 总结：好习惯应成为 Agent 的默认工作方式

作者的结论是：

即使在 AI Coding 时代，好的编程习惯仍然有价值。与其等代码变复杂后再让 Agent 做高成本重构，不如在早期通过 **harness engineering**，把良好的编程习惯变成 Agent 的默认工作方式。

这样做可以：

- 降低后续重构成本；
- 减少 Token 消耗；
- 提升 Agent 完成任务的稳定性；
- 让人和 AI 都更容易维护代码。

###### 知识要点
- 开发者视角下简单的机械重构，对Agent可能涉及大量上下文读取、跨文件状态管理和编译错误修补
