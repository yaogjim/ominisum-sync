## 分析要点

- **核心高价值点**：原生文件API通过减少Python交互、优化预分词与缓存并扩大并行度，将大规模BPE分词推进到GB/s级，同时提供逐文档输出一致性验证。
- **留存建议**：保留并在大规模语料预处理或分词性能受限时优先验证（提供可直接安装验证的高性能分词工具、兼容接口、详细基准数据和复现命令，对大规模模型数据管线具有明确实践价值。）

**知识要点**

- 大规模分词的主要瓶颈不仅是BPE合并，还包括正则预分词、Python边界交互、线程通信和长尾缓存管理。
- SIMD、低分支实现和预分词映射缓存可以显著提高现代多核CPU上的分词吞吐，但不同分词算法的收益差异明显。
- 兼容HuggingFace或tiktoken的接口会引入额外开销；直接由Rust读取文件并使用原生API更有利于充分并行化。

**行动项**

- 使用项目提供的bench命令，在自有语料、目标模型和部署硬件上运行带validate参数的对照测试。
- 先通过HuggingFace或tiktoken兼容模式验证替换成本与输出一致性，再评估迁移至原生文件API。
- 在采用前核对WordPiece、SentencePiece、Windows支持及文件输出能力等已知限制。

#### Gigatoken

\~1000x faster than HuggingFace's tokenizers, drop-in replacement.

*Tokenize your text data at GB/s!*

[![GPT-2 Speedup](https://raw.githubusercontent.com/marcelroed/gigatoken/main/assets/throughput_owt_train_gpt-2.svg)](https://raw.githubusercontent.com/marcelroed/gigatoken/main/assets/throughput_owt_train_gpt-2.svg)

Note that both HF tokenizers and tiktoken are already running multithreaded Rust!

Gigatoken is the fastest tokenizer for language modeling. It supports a wide range of CPU hardware, and nearly all commonly used tokenizers. See the Benchmarks section for detailed throughput numbers across tokenizers and CPUs.

#### Installation

```
pip install gigatoken
```

#### Usage

Gigatoken can be used with its own API, or in compatibility mode with HuggingFace Tokenizers or Tiktoken.

```
import gigatoken as gt

# Minimum change from existing HuggingFace tokenizers usage (compatibility mode)
hf_tokenizer = ...
tokenizer = gt.Tokenizer(hf_tokenizer).as_hf()

# tokenizer can be used in the same contexts as hf_tokenizer
tokens = tokenizer.encode_batch(["This is a test string", "And here is another"])

# OR with tiktoken
tiktokenizer = ...
tokenizer = gt.Tokenizer(tiktokenizer).as_tiktoken()

# Now works like existing tiktoken tokenizers
tokens = tokenizer.encode_batch(["This is a test string", "And here is another"])
```

A substantial amount of effort has been put into making sure the outputs match exactly with what you would get with HuggingFace Tokenizers in this setting, but this is at a non-negligible cost to performance. You can still expect way faster performance across the board, but not quite the 1000x you will get with the Gigatoken API.

```
import gigatoken as gt

tokenizer = gt.Tokenizer("Qwen/Qwen3-8B")  # Accepts HF model names
file_source = gt.TextFileSource(["owt_train.txt"], separator=b"<|endoftext|>")
tokens = tokenizer.encode_files(file_source)
```

Using the Gigatoken API lets the Rust implementation read data directly, and skips as much overhead as possible while allowing for maximum parallelism. Keep in mind that passing Python data structures through this API still incurs the overhead of reading from Python.

**Benchmark details**

OWT (openwebtext) was chosen because it's roughly representative of the text you get after extraction from CommonCrawl documents. Gigatoken encodes the whole file un-split, and is thus doing more work than the other tokenizers to find the split boundaries and automatically parallelize. HuggingFace tokenizers (`encode_batch_fast`) gets the first 100 MB and tiktoken (`encode_ordinary_batch`) the first 1 GB, both presplit on `<|endoftext|>`. This is fair because neither of the compared tokenizers do caching, meaning the speed is roughly uniform throughout processing. Tiktoken rows are currently only filled in for tokenizers with official support.

The slowest rows are the SentencePiece-based tokenizers, which are not well optimized in Gigatoken.

Each row is one distinct tokenizer (identical vocab/merges/pretokenizer), measured on a representative repo. If you don't see your tokenizer here, it's likely based on some existing one. For instance:

#### FAQ

No, I way over-optimized for every combination of these! The results are very consistent across CPUs (modern x86 and ARM), and across specific tokenizers.

The major improvements are in optimizing heavily an implementation that usually is outsourced to a Regex engine (pretokenization) using SIMD, minimizing branching and other tricks, as well as heavily optimizing caching of pretoken mappings (if a word has been seen before, look up its encoded tokens efficiently). Caching is a very hard problem in this domain since the cache grows very quickly, and pretoken distributions are very long-tailed.

Some gains are also achieved from minimizing interactions with Python, and avoiding communication between threads.

#### Known Issues

- Python iteration is handled in Rust, but uses ABI3, which is slower than using internal version-specific CPython APIs. In the future I intend to specialize for each Python version to cut this overhead. Early experiments show a 2x speed improvement for overhead-bound cases.
- File sinks are not yet implemented in the Gigatoken API.
- WordPiece is not yet supported.
- SentencePiece-based tokenization is not nearly as optimized as the more common BPE tokenizers. This is low priority for now since mostly Google models/BERT style models use SentencePiece.
- Windows has not been tested much, so for now prefer using WSL.

#### Gigatoken：面向大规模语言模型数据处理的超高速分词器

##### 一句话总结

**Gigatoken 是一个基于 Rust 的高性能 Tokenizer，兼容 Hugging Face Tokenizers 和 tiktoken，针对现代 CPU 深度优化，分词速度可达到 GB/s，部分场景比现有方案快数百至上千倍。**

##### 核心能力

###### 1. 兼容主流分词器

- 支持 Hugging Face Tokenizers 和 tiktoken 的兼容模式。
- 可直接加载 Hugging Face 模型名称，例如 `Qwen/Qwen3-8B`。
- 覆盖 GPT、Llama、Qwen、DeepSeek、Gemma、Phi、GLM 等大量主流模型分词器。
- 在兼容模式下，尽量保证输出结果与 Hugging Face 完全一致。

###### 2. 支持大文件直接处理

Gigatoken 可以直接读取文本文件，并在 Rust 层完成：

- 文档切分
- 批量分词
- 多线程并行
- Token 结果输出

相比将大量 Python 数据传入底层，这种方式可以减少 Python 调用和数据传输开销，更适合处理训练语料库。

##### 性能表现

###### 典型基准结果

在 11.9 GB 的 OpenWebText 数据集上：

- AMD EPYC 144 核：最高约 **24.5 GB/s**
- Apple M4 Max 16 核：最高约 **8.8 GB/s**
- AMD Ryzen 7 9800X3D 16 核：最高约 **6.3 GB/s**

以 GPT-2 为例：

- 相比 Hugging Face Tokenizers：
  - EPYC 上约 **989 倍**
  - M4 Max 上约 **1,268 倍**
  - Ryzen 7 上约 **106 倍**
- 相比 tiktoken：
  - EPYC 上约 **681 倍**
  - M4 Max 上约 **140 倍**

不过，实际速度会因 CPU、Tokenizer 类型、数据规模和 API 使用方式而变化。

##### 性能优化原理

Gigatoken 的主要优化方向包括：

1. **SIMD 加速**  
   使用 AVX512、AVX2、NEON 等指令集提升文本预处理效率。

2. **优化预分词阶段**  
   重点优化通常由正则表达式完成的 pre-tokenization，减少分支和额外开销。

3. **高效缓存**  
   对重复出现的词或预分词结果进行缓存，避免重复计算。

4. **充分利用多核 CPU**  
   自动并行处理大型文档，减少线程间通信成本。

5. **减少 Python 交互**  
   将核心流程放入 Rust，避免 Python 层成为性能瓶颈。

##### 适用场景

Gigatoken 更适合以下任务：

- 大规模预训练语料 Tokenization
- Common Crawl 等海量文本处理
- 训练数据清洗和预处理
- 批量生成 Token 数据集
- 需要降低数据准备时间和 CPU 成本的训练基础设施

作者估算，按照其在 AMD EPYC 上的速度，处理约 **130 万亿个 Common Crawl Tokens** 可能只需约 **6.5 小时**，但这是基于基准数据的理论外推。

##### 局限与注意事项

- **WordPiece 尚未支持**。
- **SentencePiece 优化程度较低**，相关模型速度明显慢于主流 BPE 模型。
- 兼容 Hugging Face API 时，为保证结果一致，会损失部分性能。
- Python 迭代仍使用 ABI3，未来针对不同 Python 版本优化后，部分场景可能再提升约 2 倍。
- 文件输出接口尚未实现。
- Windows 支持和测试较少，暂时更建议使用 WSL。
- 基准测试主要体现超大批量、文件级处理能力，小规模或交互式调用未必能获得同等收益。

##### 产品价值判断

Gigatoken 的核心价值不只是“更快的分词算法”，而是将**分词、缓存、文件读取和多核并行**整合到一个面向大规模数据处理的高性能执行路径中。

对于模型训练团队而言，它有潜力显著缩短数据预处理周期、降低 CPU 资源成本，并减少 Tokenization 对训练流水线的阻塞。但在正式替换现有方案前，仍需针对自身模型、Tokenizer 类型、操作系统和数据规模进行兼容性与性能验证。

- 适合低成本迁移现有代码。
- 项目重点保证输出与 HuggingFace 一致。
- 但兼容层会带来额外开销，因此通常达不到原生 Gigatoken API 的约千倍加速。

###### 使用原生 Gigatoken API

```python
import gigatoken as gt

tokenizer = gt.Tokenizer("Qwen/Qwen3-8B")
source = gt.TextFileSource(
    ["owt_train.txt"],
    separator=b"<|endoftext|>"
)
tokens = tokenizer.encode_files(source)
```

原生 API 让 Rust 直接读取文件，减少 Python 数据结构传递，并最大化并行度，因此性能最高。若仍从 Python 对象读取数据，则会保留一定的 Python 交互开销。

##### 3. 基准测试方法

- 测试数据选择 OpenWebText，是因为其文本形态接近从 Common Crawl 提取后的网页内容。
- Gigatoken 直接处理完整的 **11.9 GB 未切分文件**，还需自行寻找文档边界并完成并行切分。
- HuggingFace 使用预先按 `<|endoftext|>` 切分的前 **100 MB**。
- Tiktoken 使用预切分的前 **1 GB**，且只测试官方支持的 tokenizer。
- HuggingFace 与 Tiktoken 不会在测试过程中缓存结果，因此作者认为处理速度基本均匀，截取部分文件仍具有可比性。
- 每一行代表一个独立 tokenizer 配置，即词表、merge 规则和预分词器均相同。

测试中较慢的通常是 **SentencePiece** tokenizer；Gigatoken 当前主要针对更常见的 **BPE** 方案进行优化。

因此，即使某个具体模型未出现在表格中，只要它沿用已有 tokenizer，其性能通常可以参考对应家族。

##### 5. 速度提升的核心原因

Gigatoken 的优势并非来自单一技巧，而是对整个分词流程进行深度优化：

1. **SIMD 加速预分词**  
   将通常交给正则表达式引擎的预分词过程专门实现，并针对 AVX-512、AVX2 和 ARM NEON 等指令集优化。

2. **减少分支判断**  
   尽量降低 CPU 分支预测失败带来的损耗，提高流水线效率。

3. **缓存已见过的预分词片段**  
   某个词或片段再次出现时，可直接查找其 token 结果。不过自然语言分布具有明显长尾，缓存增长很快，因此缓存层级本身也需要精细设计。

4. **减少 Python 交互**  
   文件读取和核心计算尽量直接在 Rust 中进行，避免频繁跨越 Python/Rust 边界。

5. **减少线程之间的通信**  
   降低同步和数据交换成本，更有效地利用多核 CPU。

这些优化在现代 x86 和 ARM CPU 上均表现出较一致的效果。

##### 7. 当前限制与已知问题

- **SentencePiece** 的优化程度明显低于 BPE，目前优先级较低。
- Windows 测试不充分，建议暂时通过 **WSL** 使用。

如果使用 Gigatoken自己的接口，程序可以直接指定 Hugging Face 上的模型名称，例如 Qwen 系列模型。它还可以让底层的 Rust 代码直接读取文本文件，减少 Python 和 Rust 之间来回传递数据的开销，并充分利用多核并行。

##### 然后，怎样理解这些基准测试

核心结论是，这些测试尽量保持了可比性，而且 Gigatoken实际上承担了更多文件处理工作。

Gigatoken直接读取并处理完整的十一点九 GB 文件。原始文件没有预先切开，因此它还需要自己寻找文档边界，并自动把任务分配给多个核心。

Hugging Face Tokenizers测试的是预先切分好的前一百 MB，tiktoken测试的是预先切分好的前一 GB。切分使用的是文档结束标记。作者认为这种比较仍然公平，因为对比工具都没有跨文档缓存，处理速度在整份数据中基本稳定，可以据此推算整体吞吐量。

表格中的每一行代表一种独立的分词器配置，包括相同的词表、合并规则和预分词方式。这里的“预分词”，就是在正式执行 BPE 等算法之前，先把文本拆成更容易处理的小片段。

如果某个具体模型没有出现在结果中，也不一定意味着不支持。很多模型沿用了同一套分词方案。例如，DeepSeek 的部分 Llama 蒸馏模型属于 Llama 3 一类；Qwen 的代码、视觉和蒸馏模型往往可以归入 Qwen 2、Qwen 2.5 或 Qwen 3；DeepSeek V3、R1 和 V4 也共享相关的分词结构。Kimi、GLM、Nemotron、Gemma 和 Phi 等系列同样有对应的代表性测试。

##### Gigatoken为什么能快这么多

核心结论是，它不是依靠单一技巧，而是把预分词、缓存、CPU 指令和并行通信都进行了针对性优化。

首先，很多分词器会把预分词工作交给通用的正则表达式引擎。Gigatoken没有完全沿用这种方式，而是为常见模式编写了高度优化的实现。

其中使用了 SIMD。SIMD可以理解为，让 CPU 用一条指令同时处理多个数据，而不是逐个字符处理。项目针对 AVX512、AVX2 和 ARM 上的 NEON 等不同指令集进行了适配。

接下来，它尽量减少程序中的条件分支。条件分支太多时，CPU可能猜错下一步执行路径，导致流水线停顿。减少分支，有助于让处理过程更连续。

更重要的是，Gigatoken重度优化了预分词结果的缓存。如果某个词或片段之前出现过，程序可以快速查出它对应的 token，而不必重新计算。

不过，分词缓存并不容易设计。自然语言中的词和片段呈现明显的长尾分布，也就是少数内容频繁出现，大量内容只出现一两次。缓存会迅速膨胀，因此不仅要考虑是否缓存，还要考虑怎样在不同层级的 CPU 缓存中高效查找。

最后，它还尽量减少 Python 与 Rust 之间的交互，以及不同线程之间的通信。数据直接从文件进入 Rust 实现时，就能避免大量对象转换和同步成本。

核心结论是，Gigatoken不仅追求速度，也提供了结果一致性验证。

项目提供了命令行基准测试工具。用户可以指定一个 Hugging Face 模型和自己的文本文件，同时测试 Gigatoken与 Hugging Face Tokenizers，并检查输出是否完全一致。

在一百四十四核的 AMD EPYC 服务器上，Gigatoken处理同一份文件只用了大约零点四九秒，速度达到每秒二十四点五 GB。相对 Hugging Face 快约九百八十九倍，同样通过了全部文档的结果验证。

##### 最后，目前有哪些限制

核心结论是，Gigatoken已经覆盖大量常用场景，但还不能完全替代所有分词工具。

第一，WordPiece目前还不支持。WordPiece是 BERT 等模型常见的一种子词分词方法。

第二，SentencePiece虽然可以使用，但优化程度明显不如主流 BPE 分词器。作者表示，这部分优先级较低，因为它主要出现在部分 Google 模型和 BERT 风格模型中。

第三，Gigatoken原生接口还没有实现文件输出端，也就是可以直接把结果写入文件的“文件 sink”。

第四，Python 迭代虽然由 Rust 处理，但当前使用的是 ABI3。ABI3是一种让扩展模块兼容多个 Python 版本的通用接口，兼容性更好，但速度低于针对特定 Python 版本编写的内部接口。早期实验显示，如果未来按 Python 版本分别优化，在受接口开销限制的场景中，速度可能再提升两倍。

第五，Windows上的测试还不充分。目前更推荐使用 WSL，也就是在 Windows中运行 Linux 环境。

作者也提醒，尽管项目已经做了较广泛的测试，但不可能覆盖所有使用方式。如果遇到输出不一致或其他问题，应该通过项目的问题反馈渠道报告。

##### 总结：最值得记住的五点

最后回顾一下。

第一，Gigatoken是一个面向语言模型的高速分词器。在合适的 BPE 分词器和现代 CPU 上，速度可以达到每秒数 GB到二十多 GB。

第二，它在部分测试中比 Hugging Face Tokenizers快接近或超过一千倍，也明显快于 tiktoken，而且对比对象本身已经是多线程 Rust 工具。

第三，最高性能来自 Gigatoken原生接口。让 Rust直接读取文件，可以减少 Python 数据转换，并最大限度利用多核并行。兼容 Hugging Face 和 tiktoken的模式更容易接入，但会牺牲一部分速度。

第四，性能提升主要来自专门优化的预分词、SIMD并行指令、低分支实现、高效缓存，以及减少 Python和线程之间的通信。

第五，它目前仍有边界。SentencePiece优化不足，WordPiece尚未支持，Windows测试也不充分。因此，它最适合使用主流 BPE 分词器、需要批量处理超大规模文本的场景。

## 深度解读（1）

### 2026-09-18 00:16:58

#### Gigatoken 的真正启示：分词慢的不是算法，而是实现边界

Gigatoken 最醒目的数字是“比 HuggingFace Tokenizers 快约 1000 倍”：在双路 144 核 AMD EPYC 上，GPT-2 分词吞吐达到 24.5 GB/s；M4 Max 上也接近 8.8 GB/s。更值得注意的却不是倍率本身，而是它揭示了一个长期被忽略的事实：**语言模型流水线中的不少成本，并非模型或算法的必然代价，而是通用软件栈留下的实现税。**

##### 性能来自重写执行路径，而非发明新分词法

Gigatoken 仍然执行 BPE 等常见分词规则，并力求与原分词器输出完全一致。主要改进来自：用 SIMD 重写通常交给正则引擎的预分词过程，减少分支与线程通信，为重复出现的 pretoken 设计适配长尾分布的缓存，并绕开 Python 对象转换，让 Rust 直接读取文件、自动切分和并行处理。

这意味着，1000 倍并不是某个孤立技巧的成果，而是**围绕真实硬件重新组织整条热路径**。尤其值得产品和工程团队借鉴的是 API 边界的影响：为了兼容 HuggingFace 或 tiktoken，Gigatoken 必须保留额外的数据转换和语义检查，性能提升会明显缩水；只有使用原生 API、直接处理文件时，才能释放最大吞吐。所谓“无缝替换”与“极致性能”往往是两个不同产品目标，不能同时默认成立。

##### 它改变的是大规模数据处理的成本分布

这种优化对聊天应用的单次推理意义有限，因为短文本分词通常不是主瓶颈；真正受益的是预训练数据制作、语料重分词、模型迁移、离线评测和大规模 embedding 管线。按项目给出的速度估算，130 万亿 token 的 Common Crawl 可在约 6.5 小时内完成分词。过去需要反复权衡的事情——更换 tokenizer、重新清洗全部语料、尝试不同词表——可能从昂贵批处理变成更频繁的实验。

但这个估算只覆盖分词计算，不包括下载、解压、HTML 提取、去重、过滤和结果写盘。分词快到 GB/s 后，瓶颈很可能立即转移到存储带宽、解压或数据治理。**它消除的是一道局部关卡，不是整个数据工程成本。**

##### “1000 倍”仍需在自己的负载上验证

基准使用 11.9GB OpenWebText，Gigatoken 处理完整文件，而对照组处理预切分后的较小样本；作者认为分词速度稳定，因此比较公平，但缓存收益会受文本重复度、文档长度和词元分布影响。不同 tokenizer 的表现也差异显著：优化充分的 BPE 可达数十 GB/s，SentencePiece 系列目前通常只有约 1—5 GB/s，提升倍率也更低；WordPiece 尚未支持。

因此，这个项目最有价值的判断不是“所有 tokenizer 都能快 1000 倍”，而是：**当一个成熟基础组件慢得像常识时，先别急着接受其成本曲线；检查通用抽象、语言边界和内存访问方式，可能比更换算法更有回报。** 对实际团队而言，下一步应是用自有语料端到端测试，并观察分词加速后，新的瓶颈究竟落在哪里。

## 默认总结（1）

### 2026-09-18 01:20:32

##### 一句话看懂

Gigatoken 是一个面向大模型数据处理的高速 CPU 分词器，项目自测可达每秒数 GB 至 24GB，部分 BPE 分词器比 HuggingFace Tokenizers 快约百倍甚至千倍。

##### 关键内容

- 支持 HuggingFace、Tiktoken 兼容接口，也可直接加载模型名；原生 API 能由 Rust 直接读文件，减少 Python 传输开销，速度最高。
- 在 11.9GB OpenWebText 数据上的自测中，主流 BPE 分词器约为 **3—24GB/s**；提升幅度受 CPU 和分词器影响明显，并非都能达到 1000 倍，部分 SentencePiece 模型仅快约 7—22 倍。
- 加速主要来自 SIMD 指令、减少分支、缓存重复文本片段，以及降低 Python 与线程通信开销。
- 当前仍有局限：不支持 WordPiece，SentencePiece 优化不足，Windows 测试较少；兼容模式虽力求输出一致，但会损失部分性能。

##### 通俗解读

“1000 倍”是特定硬件和分词器下的项目自测峰值，不应理解为所有场景的固定提升。它主要适合需要给海量训练语料分词的用户；普通推理或小文件处理中，分词往往不是瓶颈。若你正搭建大规模数据预处理流程，值得细读基准条件、兼容性和已知问题；否则了解接口与限制即可。
