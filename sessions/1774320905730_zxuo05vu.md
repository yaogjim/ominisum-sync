#### 文章主旨

这篇文章的核心观点是：**Claude Code 的效率差距，关键不在“会不会写提示词”，而在于有没有把它当成一个完整系统来配置和使用。**  
作者认为，真正高效的用户不是把它当“代码自动补全”，而是把它当成一个能长期协作、自动检查、并行处理任务的“开发操作系统”，这样每周可节省 **4–6 小时**。

#### 一、作者先指出：普通用户和高手的差距，主要是“配置方式”

- 大多数人只会让 Claude Code “帮我写个函数”，属于局部使用。
- 顶尖用户则会把它接入自己的完整开发流程，甚至能做到“人在休息，功能还在推进”。
- 作者明确提出一个关键判断：  
  > 普通用户和高级用户之间的差距，不是技能，而是配置。  
- 这种差距的实际收益很具体：**每周大约能节省 4–6 小时**。

**通俗理解：**  
就像很多人把 IDE 只当文本编辑器用，但高手会配置快捷键、调试器、插件、自动化脚本，最终速度完全不是一个量级。

#### 二、基础配置：先把 Claude Code 变成“顺手工具”

这一部分主要讲的是：**先把工具本身调顺，减少摩擦。**

##### 1. 用别名和权限设置减少操作阻力

- 作者建议先配置命令别名：  
  在 `~/.zshrc` 或 `~/.bashrc` 里加入：
  ```bash
  alias cc='claude --dangerously-skip-permissions'
  ```
- 这样以后直接输入 `cc` 即可，还能跳过频繁的权限确认。
- 但作者特别提醒：**只有在你清楚自己授权了什么的前提下再这么做。**

**例子：**  
如果你每天调用 Claude Code 数十次，每次都手动确认权限，累计下来就是明显的时间浪费。

##### 2. 给终端加“实时状态栏”

- 使用 `/statusline` 可以生成一个 shell 脚本，在终端底部显示：
  - 当前目录
  - Git 分支
  - 上下文使用情况
- 作者把它比作会话中的“HUD（抬头显示器）”。

**意义：**  
你不用反复确认自己现在在哪个项目、哪个分支、上下文还剩多少。

##### 3. 把上下文窗口开大，但要适度

- Sonnet 4.6 和 Opus 4.6 支持 **100 万 token 上下文**。
- 可通过 `/model opus[1m]` 在会话中切换。
- 作者建议：**先从 50 万开始试，再逐步增加**，找到输出质量和上下文容量的平衡点。
- 因为上下文太大时，压缩（compaction）可能会影响结果质量。

##### 4. 预设输出风格，避免每次重新调教

- 用 `/config` 选择回答风格，如：
  - Explanatory（解释型）
  - Concise（简洁型）
  - Technical（技术型）
- 还可以在 `~/.claude/output-styles/` 自定义风格。
- 核心思想是：**不要每次都手工修改 Claude 的表达方式，要一次配置好。**

##### 5. 支持远程控制

- 运行 `claude remote-control`，可通过 `claude.ai` 或手机 App 远程查看和控制。
- 场景是：你在电脑上启动一个长时间重构任务，离开工位后也能在手机上查看进度。

#### 三、效率技巧：减少打断，让 Claude 和你并行工作

这一部分强调：**不是让 Claude 更聪明，而是让你们协作得更流畅。**

##### 1. 直接把命令输出送进上下文

- 用 `!` 前缀运行命令，例如：
  ```bash
  !git status
  !npm test
  ```
- 输出会直接进入 Claude 的上下文，省去复制粘贴。

**例子：**  
调试时你可以直接贴 `npm test` 的结果，让 Claude立刻根据报错分析，而不是你手动转述错误。

##### 2. 善用“停止”和“撤回”

- `Esc`：中断 Claude 当前动作  
- `Esc + Esc` 或 `/rewind`：恢复代码、对话或两者

这相当于给 AI 协作加了一个“撤销键”，适合在你对某个方案只有 **40% 把握** 时先试一试。

##### 3. 暂存提示词草稿，避免思路中断

- `Ctrl+S` 可暂存写到一半的 prompt 草稿。
- 你可以先插入一个临时问题，问完后草稿自动恢复。

##### 4. 后台执行长任务

- 当 Claude 在跑测试或构建时，按 `Ctrl+B` 可让它后台继续运行。
- 这样你可以一边等待结果，一边继续和它讨论下一步。

**意义：**  
这是把串行工作改成并行工作，提升明显。

##### 5. 用侧边问题避免污染主线对话

- `/btw` 可以弹出一个临时问答层，用来问“为什么这样做？”之类的小问题。
- 主对话线程保持干净，不会被这些枝节问题打乱。

##### 6. 在 Claude 动手前先改它的计划

- 当 Claude 给出执行计划后，按 `Ctrl+G` 可以在编辑器里修改计划内容。
- 这样能提前纠偏，避免它花 **20 分钟** 朝错误方向实现。

##### 7. 语音输入能给出更好的提示词

- 用 `/voice` 开启按住说话。
- 作者认为，口述时人会自然带出更多背景、限制条件和细节，因此 prompt 质量往往比键盘输入更高。

#### 四、上下文管理：决定输出质量的关键，不是“说更多”，而是“说对”

这部分的重点是：**Claude 的效果好不好，很大程度取决于上下文是否干净、准确、聚焦。**

##### 1. 不相关任务之间要及时清空上下文

- 用 `/clear` 清理会话。
- 作者认为，一个干净的新会话，通常比一个持续了 **3 小时** 的混乱会话更有效。
- 因为堆积的上下文会悄悄稀释新指令的重要性。

##### 2. 连续纠正两次还不对，就重开

- 如果你已经纠正 Claude 两次，它还是偏题，**不要继续第三次**。
- 更好的方法是 `/clear` 后重写一个新 prompt，并把刚刚学到的信息明确写进去。

**通俗理解：**  
就像一个人已经误会了你的需求，继续在原误会上修补，往往越修越乱。

##### 3. 别转述 bug，直接贴原始信息

- 作者强调：**不要“描述” bug，要直接贴错误日志、CI 输出、Slack 讨论。**
- 示例：
  ```bash
  cat error.log | claude "explain this error and suggest a fix"
  ```
- 因为抽象后的描述会丢失关键信息，而原始数据更利于 Claude定位问题。

##### 4. 架构性任务要先进入 Plan Mode

- `Shift+Tab` 可进入 Plan Mode。
- 适合多文件修改或结构性调整。
- 虽然前期会多一步，但能避免 Claude“自信地解决了错误的问题”。

##### 5. 明确指定要看的文件

- 用 `@src/auth/middleware.ts` 这类方式直接指文件。
- 好处是减少 Claude 在整个代码库里搜索的 token 消耗，也让它更快切到重点。

##### 6. 不熟悉代码时，故意问得“宽一点”

- 例如问：  
  “你会改进这个文件的什么地方？”
- 这样能让 Claude 主动发现你没想到的问题，比如风格不一致、隐藏逻辑风险等。

##### 7. 压缩上下文时要告诉它“保留什么”

- 用 `/compact` 时，最好加一句说明，比如：  
  “focus on the API changes”
- 否则压缩后可能丢主线；有明确指导时，提炼效果更好。

##### 8. 用“ultrathink”处理高难问题

- 在 Opus 4.6 中，prompt 里加入 `ultrathink`，可触发更强的自适应推理。
- 作者认为，对于复杂问题，这种质量提升是“真实且明显”的。

#### 五、自动化与工具：让 Claude 不只“会做”，还会“自检”

这一部分最核心的思想是：**闭环反馈越完整，结果质量越高。**

##### 1. 让 Claude 自己验证结果

- 在提示词中明确要求它：
  - 重构
  - 运行测试
  - 修复失败
  - 直到通过再结束
- 作者说，这一个动作就能带来 **2–3 倍** 的质量提升。

**例子：**  
与其说“重构认证模块”，不如说：  
“重构 auth，运行测试套件，若失败先修复，再告诉我完成。”

##### 2. 安装 LSP 插件

- LSP 插件能在编辑后自动给出诊断。
- 示例：
  ```bash
  /plugin install typescript-lsp@claude-plugins-official
  ```
- 好处是 Claude 可以在你发现前，就先发现并修掉类型错误。

##### 3. 优先使用 CLI 工具，而不是 MCP 服务器

- 作者认为 CLI 工具比 MCP 更节省上下文。
- 举例：
  - 用 `gh` 处理 PR
  - 用 `sentry-cli --help` 排查线上问题
- 长会话里，这种节省会不断累积。

##### 4. 优先安装这 4 类高价值 MCP

作者推荐先装 4 类“信噪比高”的 MCP 服务器：

- Playwright：做 UI 验证
- PostgreSQL/MySQL：查数据库结构
- Slack：直接读取 bug 讨论
- Figma：设计转代码

并提醒：**先把这些用熟，再扩展更多。**

##### 5. 用 `/loop` 做周期性后台检查

- 示例：
  ```bash
  /loop 5m check if deploy succeeded
  ```
- 作用是每隔 5 分钟自动检查部署状态，并在有结果时回来汇报。

##### 6. 用 `/permissions` 放行安全命令

- 比如把 `npm run lint` 加入允许列表。
- 因为反复弹权限确认，本身就是一种“隐藏的生产力税”。

#### 六、规则系统：CLAUDE.md 不是越长越好，而是越精准越好

这一部分强调：**规则文件要小而准，能动态演进。**

##### 1. 先自动生成，再狠狠删减

- 用 `/init` 生成 `CLAUDE.md` 初稿。
- 然后“砍掉一半”。
- 原因是：每一条无用规则都在浪费 token，并分散 Claude 的注意力。

##### 2. 判断一条规则该不该留的标准

- 作者给出一个非常实用的测试：
  > 如果没有这一条，Claude 会犯错吗？
- 如果答案是否定的，就删掉。
- 作者还给出一个经验数字：  
  **大约 150–200 条指令之后，遵守率会开始下降。**

##### 3. 每次犯错后更新规则文件

- 当 Claude 犯错时，直接说：  
  “Update CLAUDE.md so this doesn't happen again.”
- 这样规则文件就会成为一个持续进化的系统。

##### 4. 用 `.claude/rules/` 做条件规则

- 根据路径只在相关场景加载规则：
  - TypeScript 规则只对 `.ts` 文件生效
  - 数据库规则只在 `/db` 目录生效
- 好处是：**无关规则不进上下文，减少干扰。**

##### 5. 用 `@imports` 让主规则文件更轻

- 不要把大段规则直接粘进 `CLAUDE.md`。
- 可以引用如 `@docs/git-instructions.md` 这样的外部内容，需要时再读。

##### 6. 用 Skills 扩展能力，而不是堆进基础上下文

- 将知识模块放入 `.claude/skills/`。
- 它们像“按需加载的库”：调用时出现，不调用时不占用上下文。

##### 7. 建议类规则放 `CLAUDE.md`，强制类规则放 Hooks

- 作者给出一个很实用的区分：
  - `CLAUDE.md`：建议、偏好、提醒
  - Hooks：不可违背的要求
- 因为 `CLAUDE.md` 的遵守率大约是 **80%**
- 但 Hooks 是“每次都执行，没有例外”。

##### 8. 两个典型 Hook 用法

###### 自动格式化

- 在 `.claude/settings.json` 中添加 `PostToolUse` hook
- 每次编辑后自动执行 Prettier：
  ```json
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{
        "type": "command",
        "command": "npx prettier --write \"$CLAUDE_FILE_PATH\" 2>/dev/null || true"
      }]
    }]
  }
  ```

###### 阻止危险命令

- 用 `PreToolUse` 在 Bash 执行前拦截危险操作，如：
  - `rm -rf`
  - `DROP TABLE`
- 这样你就能在更高自治程度下放心地使用 Claude。

#### 七、进阶玩法：并行、隔离、代理协作，才是真正放大效率的地方

这一部分是全文最“高手向”的内容，核心是：**一个 Claude 不够用时，就让多个 Claude 分工协作。**

##### 1. 用 `--worktree` 开多个隔离分支

- 示例：
  ```bash
  claude --worktree feature-auth
  ```
- 这会创建一个隔离工作副本。
- 你可以同时开 **3 个并行会话**，分别处理不同功能，互不影响。

##### 2. 用 subagents 减轻主上下文负担

- 例如对 Claude 说：  
  “Use subagents to figure out the payment flow.”
- 它会启动独立实例去读文件、做分析，再返回摘要。
- 好处是：主会话不用装下所有细节，能保持轻量聚焦。

##### 3. 为重复任务创建自定义代理

- 用 `/agents` 可在 `.claude/agents/` 中保存预配置代理。
- 作者举的例子包括：
  - 快速搜索代理
  - 严格 TypeScript 审查代理
  - 文档撰写代理
- 本质上就是搭一个“个人 AI 团队”。

##### 4. 开启 Agent Teams 做大规模并行工作

- 开启环境变量：
  ```bash
  CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS
  ```
- 之后会由一个 team lead 把任务分发给 **3–5 个 subagents** 并行处理。
- 对于大型调研或多模块重构，这会带来“不同量级”的速度提升。

##### 5. 用 `/sandbox` 做高风险实验

- `/sandbox` 会通过 Seatbelt 或 bubblewrap 进行操作系统级隔离。
- 适合让 Claude 自主尝试高风险重构。
- 你只需要最后审查 diff，保留有价值的改动即可。

**通俗理解：**  
这就像先在沙盒里做实验，成功了再合并到正式环境，风险小很多。
