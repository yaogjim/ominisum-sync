## 结构化（1）

### 2026-05-08 02:14:56

##### 主旨概括

CJ Zafir 分享了一套低成本、高质量的 AI 编程工作流：用**Codex 5.5 High 负责规划与编排**，再用**DeepSeek V4 Pro 和 Kimi 2.6 负责具体执行**。核心思想是：先把计划打磨到足够可靠，再让不同模型各司其职，最后由 Codex 做测试、审计和质量把关。

---

##### 1. 工作流起点：先用 Codex 做规划

- 作者有一个想法后，会先打开**Codex 桌面应用**来做规划。
- 他不使用 “规划模式”，因为觉得过于复杂。
- 使用的模型是**Codex 5.5 High**，特点是速度快、适合做整体方案设计。

**关键点：**  
Codex 在这里不是直接写代码，而是先充当 “项目经理” 或 “架构师”，负责把想法拆成可执行方案。

---

##### 2. 关键技巧：对计划进行 “反向审查”

作者拿到第一版计划后，会向 Codex 提出一个强约束问题：

> “你对这个策略有 100% 的信心吗？如果没有，找出所有可能的漏洞，提出适当的修复方案，并执行这个循环，直到你确实对新策略有 100% 的信心。”

- 这一步相当于让 AI 主动挑错、查漏洞、修正方案。
- 目的不是马上执行，而是先把计划中的不确定性尽量消除。
- 热门回复中也提到：很多人会跳过这种 “对抗性规划”，但这其实是最关键的一步。

**关键点：**  
不要让 AI 拿到初稿就开干，而是先让它质疑自己的方案，反复修补，提升执行成功率。

---

##### 3. 形成完整规格：计划、文件树、规则和质量门禁

经过反复审查后，Codex 会输出完整的执行基础，包括：

- 项目计划
- 实施方案
- 文件树结构
- 编码规则
- 质量门禁，也就是必须满足的检查标准

随后，作者把执行任务交给：

- **DeepSeek V4 Pro**
- **Kimi 2.6**

在这个组合中：

- **Codex = 编排器 / 总控**
- **DeepSeek 和 Kimi = 执行器**

**关键点：**  
Codex 负责 “想清楚怎么做”，DeepSeek 和 Kimi 负责 “把事情做出来”。

---

##### 4. Codex 负责测试和质量检查

执行完成后，Codex 还会继续承担质量控制工作：

- 使用计算机代码在浏览器中测试
- 做深度质量检查
- 只把高质量结果传递到生产环境

也就是说，Codex 不只是前期规划，还负责后期验收。

**关键点：**  
整个流程不是 “AI 写完就结束”，而是包含测试、审计、修复和最终交付。

---

##### 5. 让 Codex 具备自主循环能力

作者会让 Codex 拥有一定自主性，使它能够连续完成：

1. 规划
2. 执行
3. 审计
4. 修复
5. 继续推进任务

他把这种方式类比为类似`/goal`的功能。

作者本人只需要监督：

- 报告
- 当前状态
- 最终成果

只要规格说明足够完善，他就比较信任**Codex 5.5**的表现。

**关键点：**  
人不再逐行指挥 AI，而是提供清晰目标和规格，让 Codex 自主推进并定期汇报。

---

##### 6. 作者给出的实用提示

作者还总结了几个小技巧：

- 告诉 Codex 保持项目结构干净：
  - 文件夹清晰
  - 子文件夹有序
  - 文件命名整齐
  - 删除无效代码和未使用文件

- 每个工作项都要制定任务清单：
  - 这可以减少 Codex 中途退出
  - 也能缓解上下文丢失问题

- 遵循原则：

> “Measure twice, cut once”  
> 先量两次，再切一次。

意思是：前期多检查，确保第一次就尽量做对。

- 不要把工作流搞得过于复杂。
- 但也不要忽略关键步骤，比如规划、审查和质量检查。

**关键点：**  
简单流程 + 清晰任务清单 + 严格质量控制，比复杂工具链更重要。

---

##### 7. 成本与模型选择

作者认为这套流程运行得很好，原因包括：

- **DeepSeek V4 API 成本低**
- 当前还有**官方 DeepSeek V4 API 75% 折扣**
- 主要智能来自**Codex 5.5**
- DeepSeek 和 Kimi 承担执行，降低整体成本

他特别说明自己不使用**Opus 4.7 / 4.6**，理由是：

- 现在表现被削弱
- 容易幻觉
- 总是急于结束会话
- 调试时容易陷入循环

**关键点：**  
作者选择 Codex × DeepSeek/Kimi，不只是因为效果好，也因为成本更可控。

---

##### 8. 回复区补充观点

热门回复中有人补充：

- **DeepSeek 更适合架构和调试**
- **Kimi 在前端方面表现很好**
- Codex 与 DeepSeek、Kimi 搭配效果非常好

这也印证了作者的分工思路：不同模型承担不同角色，而不是让一个模型包办所有事情。

---

##### 总结

这篇文章的核心经验是：  
先用**Codex 5.5**做高质量规划和审查，再用**DeepSeek V4 Pro / Kimi 2.6**低成本执行，最后由 Codex 负责测试和质量把关。

最值得借鉴的是第二步：不要直接执行初版计划，而是让 AI 主动找漏洞、修复漏洞，直到形成更可靠的策略。

#### 基于「Codex 编排 + DeepSeek/Kimi 执行」的最佳实践示例

##### 具体实例：开发一个「会议录音转纪要」Web 应用

假设你要做一个轻量级 SaaS：

> 用户上传会议录音，系统自动转写、总结会议纪要、提取待办事项，并支持导出 Markdown / PDF。

技术栈示例：

- 前端：Next.js + Tailwind CSS
- 后端：Next.js API Routes / Node.js
- 数据库：PostgreSQL + Prisma
- 存储：S3 / R2
- AI：Whisper / 语音转写 API + LLM 总结
- 部署：Vercel

##### 一、最佳模型分工

| 角色 | 推荐模型 | 职责 |
|---|---|---|
| 编排器 / 架构师 | Codex | 制定计划、拆任务、审计、质量门禁、最终整合 |
| 后端执行器 | DeepSeek | 数据模型、API、鉴权、调试、性能问题 |
| 前端执行器 | Kimi | 页面、交互、组件、样式、用户体验 |
| 审计者 | Codex | 代码审查、浏览器测试、回归测试、清理无效文件 |

核心原则：

> Codex 不一定负责写最多代码，而是负责 “想清楚、拆清楚、验清楚”。

##### 八、建议设置的质量门禁

###### 功能门禁

- [ ] 用户可以成功上传音频
- [ ] 上传后可以创建会议记录
- [ ] 转写失败时有错误提示
- [ ] 总结失败时可以重试
- [ ] 用户可以编辑会议纪要
- [ ] 用户可以导出 Markdown
- [ ] 历史会议记录可以正常查看

###### 技术门禁

- [ ] `npm run build`成功
- [ ] `npm run lint`通过
- [ ] 数据库迁移成功
- [ ] API 返回格式与规格一致
- [ ] 没有硬编码 API Key
- [ ] 没有未使用文件
- [ ] 没有重复组件
- [ ] 没有明显类型错误

###### UX 门禁

- [ ] 上传时有进度或 loading 状态
- [ ] 空列表有 empty state
- [ ] API 报错有用户可读提示
- [ ] 移动端基础可用
- [ ] 主要操作按钮清晰

###### 生产门禁

##### 十二、这个实例中的最佳实践总结

1. **先规划，再编码**  
   不要让执行器一上来就写代码。

2. **必须做对抗性审查**  
   第一版方案通常不够稳，要主动找漏洞。

3. **Codex 做编排，不必包揽所有代码**  
   把架构、任务拆解、审计和质量控制交给 Codex。

4. **DeepSeek 处理后端和调试**  
   适合复杂逻辑、接口、数据库、错误修复。

5. **Kimi 处理前端和体验**  
   适合页面结构、组件、交互和样式。

6. **所有任务必须落到清单上**  
   避免上下文丢失，也方便断点续做。

7. **设置明确质量门禁**  
   不是 “看起来能跑” 就上线，而是必须通过 build、lint、功能测试和文件清理。

8. **保持文件树干净**  
   AI 开发最容易产生重复文件、废弃代码和无用组件，要强制清理。

9. **让编排器持续审计执行器结果**  
   执行器负责产出，编排器负责判断是否合格。

10. **保持流程简单**  
   不要引入太多模型、太多工具、太多规则。核心是：计划、执行、审计、修复、交付。

#### 八、前后端规格如何对齐？

你需要一个`05-frontend-contract.md`，它不是让前端自由发挥，而是定义页面和 API 使用关系。

示例：

```md
# Frontend Contract

## Page: Dashboard

Route:
`/dashboard`

Purpose:
Show current user's meetings.

Uses API:
`GET /api/meetings?page=1&pageSize=20`

States:

### Loading

Show:
- skeleton list with 5 items

### Empty

Condition:
- API returns items = []

Show:
- "No meetings yet"
- Upload button linking to `/`

### Error

Condition:
- API returns non-2xx

Show:
- Error message from `error.message`
- Retry button

### Success

Show each meeting:
- title
- status badge
- createdAt
- link to detail page

Data dependency:

```ts
type MeetingListItem = {
  id: string
  title: string
  status: "uploaded" | "transcribing" | "transcribed" | "summarizing" | "summarized" | "failed"
  createdAt: string
}
```

Acceptance Criteria:
- Does not call undefined API
- Handles loading
- Handles empty
- Handles error
- Handles success
- Does not assume fields not present in API contract
```

这样 Kimi 就不会凭空假设字段。

# 九、用 Traceability Matrix 保证规格没有断层

这是最关键的质量控制工具之一。

`11-traceability-matrix.md`示例：

```md
# Traceability Matrix

| Requirement ID | Requirement | API | DB Model | Frontend Page | Backend Task | Frontend Task | Tests |
|---|---|---|---|---|---|---|---|
| R1 | User uploads audio | POST /api/meetings/upload | Meeting | Home Upload | B5 | F1 | T1, T2, T3 |
| R2 | User views meeting list | GET /api/meetings | Meeting | Dashboard | B6 | F2 | T4, T5 |
| R3 | User views meeting detail | GET /api/meetings/:id | Meeting | Meeting Detail | B7 | F3 | T6 |
| R4 | User transcribes audio | POST /api/meetings/:id/transcribe | Meeting.transcript/status | Meeting Detail | B8 | F4 | T7, T8 |
| R5 | User generates summary | POST /api/meetings/:id/summarize | Meeting.summary/decisions/actionItems/status | Meeting Detail | B9 | F5 | T9, T10 |
| R6 | User exports Markdown | GET /api/meetings/:id/export.md | Meeting | Meeting Detail | B10 | F6 | T11 |
```

如果一个需求没有 API，说明规格断了。  
如果一个 API 没有测试，说明验收断了。  
如果一个前端页面依赖了不存在的字段，说明前后端契约断了。

你可以让 Codex 检查：

```text
请审查 traceability matrix。
要求：
- 每个产品需求必须至少有一个 API 或明确说明纯前端实现
- 每个 API 必须对应至少一个测试
- 每个后端任务必须对应至少一个验收标准
- 每个前端页面的数据字段必须来自 API contract
- 找出所有 orphan requirements、orphan APIs、orphan tasks、orphan tests
```

#### 十、如何把规格变成 “可测试” 的？

AI 编程最怕规格是主观的，比如：

```md
页面要美观
接口要稳定
错误处理要完善
```

这种不可测。

应该改成：

```md
上传接口在以下场景返回对应状态码：
- 未登录：401 UNAUTHORIZED
- 未传文件：400 FILE_REQUIRED
- 文件超过 100MB：413 FILE_TOO_LARGE
- MIME 不支持：400 INVALID_FILE_TYPE
- 上传成功：201，返回 meeting.id/status/audioUrl
```

你甚至可以要求 Codex 先生成测试计划，再让 DeepSeek 根据测试计划实现。

`09-test-plan.md`示例：

```md
# Test Plan

## T1: Upload requires auth

API:
POST /api/meetings/upload

Given:
- user is not authenticated

When:
- request uploads valid file

Then:
- response status is 401
- response body is:
{
  "error": {
    "code": "UNAUTHORIZED",
    "message": "You must be signed in to perform this action."
  }
}

## T2: Upload rejects missing file

Given:
- user is authenticated

When:
- request does not include file

Then:
- response status is 400
- error.code is FILE_REQUIRED

## T3: Upload rejects invalid MIME type

Given:
- user is authenticated

When:
- file MIME type is application/pdf

Then:
- response status is 400
- error.code is INVALID_FILE_TYPE

## T4: Upload creates meeting

Given:
- user is authenticated
- file is valid MP3 under 100MB

When:
- request is sent

Then:
- response status is 201
- Meeting row is created
- Meeting.status is uploaded
- Meeting.userId equals current user ID
```

然后对 DeepSeek 说：

```text
请先写这些测试，再实现代码使测试通过。
如果测试框架尚未配置，请先提出最小测试方案，不要引入复杂依赖。
```

#### 十三、推荐你的实际操作流程

更实用的版本应该是这样：

```txt

2. Codex 自审 specs
3. Codex 多角色审查 specs
4. Codex 生成 traceability matrix

10. Codex 做集成审计

```

这里面最重要的是：

> Codex 不是生成一次 specs 就完事，而是要通过 Spec QA Loop 把 specs 打磨到可以执行。

#### 十五、总结

你的质疑本质上是：

> 怎样保证 “编排模型生成的计划” 真的能指导 “执行模型写出正确代码”？

答案是：

1. **规格必须合约化，不是描述化**
2. **每个 API 必须有完整 request/response/error/test**
3. **每个任务必须有允许修改范围、禁止修改范围、验收标准**
4. **Codex 生成 specs 后必须经过 Spec QA Loop**
5. **用 Definition of Ready 判断 specs 是否可交给执行器**
6. **用 Traceability Matrix 防止需求、API、数据库、测试断层**
7. **DeepSeek 必须分批执行，不能一次全写**
8. **每批执行后由 Codex 审计，而不是直接继续**
9. **最终质量靠测试计划和质量门禁，而不是靠模型自信**

一句话：

> Codex 负责把需求变成 “可执行合约”，DeepSeek/Kimi 只按合约施工，Codex 再按合约验收。  
> 这样这个工作流才真正稳定。
