## 正文

**陈成**

发现一个工程水准极高的项目：Codex++，给 OpenAI Codex 桌面应用做的插件系统。

Codex 是闭源代码签名的 Electron 应用，没有任何扩展机制。这个项目的做法相当硬核——它需要突破四层防线才能把代码注入进去：

第一层，改 asar 包。用 @electron/asar 解包 app.asar，把 package.json 的 main 字段从原始入口改成自己的 loader.cjs，同时精确保留原始 asar 的 unpacked 文件集（否则 Electron 的模块加载会 MODULE\_NOT\_FOUND）。重打包用原子操作：先写临时文件再 rename，防止写入中断导致 app 损坏。

第二层，过完整性校验。Electron 会校验 asar header 的 SHA-256（注意不是整个文件，是 header JSON），存在 Info.plist 的 ElectronAsarIntegrity 里。改完 asar 必须同步更新这个哈希。

第三层，关 fuse。Electron 在 Framework 二进制里有一组 fuse 开关，用已知的 sentinel 字符串 "dL7pKGdnNz796PbbjQWNKmHXBZaB9tsX" 定位，后面跟 version + count header，每个 fuse 占一字节（ASCII '0'=off, '1'=on）。直接把 EnableEmbeddedAsarIntegrityValidation 从 '1' 改成 '0'。加上第二层的哈希更新，形成双保险。

第四层，重签名。上面的操作破坏了原始 Developer ID 签名，用 codesign --force --deep --sign - 做 ad-hoc 重签名，让 macOS 不拦截。

注入的 loader.cjs 只有 70 行，设计原则是"插件系统崩了绝不能带崩 Codex"。所有逻辑包在 safe() 里，异常只写日志到 loader.log，最后一行永远是 require("./" + originalMain)——无条件把控制权交还给 Codex 原始入口。

Runtime 层也有意思。它需要访问 Codex 的内部 window services 对象，但这是个 minified 的闭源 bundle，变量名是混淆过的。解法是用 fingerprint 匹配：搜索包含 buildFlavor: 的工厂函数调用，然后检查调用体里是否同时包含 allowDevtools:、preloadPath:、globalState: 等至少 5 个已知属性名，命中后回溯找到赋值的变量名，在语句结尾注入 globalThis.codexpp\_window\_services = ;。一套完整的 JS AST 级别的 source patch。

Sparkle 自动更新兼容是最精巧的部分。Sparkle 要求有效的 Developer ID 签名才能更新，但补丁后的 app 只有 ad-hoc 签名。解决方案：hook Node 的 Module.\_load，拦截 Sparkle 模块的 installUpdatesIfAvailable 方法。更新前用 ditto 把备份的原始签名 .app 复制回去让 Sparkle 正常工作，更新完后 launchd 监听到 app.asar 文件变化，自动触发 codexplusplus repair --quiet 重新走一遍补丁流程。全自动，用户零感知。

不是一个简单的 monkey-patch，是从二进制 fuse 到 JS source patch 到 Sparkle hook 的完整工程体系。

## 通俗精炼（1）

#### Codex++ 项目总结：用硬核工程给 Codex 桌面版 “补上插件系统”

##### 一句话概括

Codex++ 是一个为**OpenAI Codex 桌面应用**打造的非官方插件系统。由于 Codex 本身是闭源、签名、无扩展机制的 Electron 应用，Codex++ 通过修改应用包、绕过完整性校验、处理签名和自动更新等方式，把插件能力 “硬注入” 进去。

---

##### 项目核心价值

Codex++ 不是普通的 monkey patch，而是一套完整的工程化扩展方案。

它解决的问题是：

- Codex 桌面端没有官方插件机制；
- 应用是闭源且代码签名的；
- Electron 自带完整性校验；
- macOS 会阻止被篡改应用运行；
- 自动更新机制 Sparkle 又依赖官方签名。

换句话说，它是在一个几乎不允许扩展的封闭应用里，强行搭建出插件系统。

---

##### 四层技术突破

##### 1. 修改 asar 应用包

Codex 是 Electron 应用，核心代码打包在`app.asar`中。

Codex++ 会：

- 解包`app.asar`；
- 修改`package.json`的`main`入口；
- 把原入口替换成自己的`loader.cjs`；
- 同时保留原始 unpacked 文件结构，避免模块加载失败；
- 使用临时文件 + rename 的方式重打包，防止写坏应用。

这一层相当于把 Codex 的启动入口劫持到自己的加载器。

---

##### 2. 更新完整性校验

Electron 会校验 asar header 的 SHA-256 哈希，这个值存储在 macOS 的`Info.plist`中。

修改 asar 后，Codex++ 会同步更新这个哈希值，否则应用会因为完整性校验失败而无法正常运行。

---

##### 3. 关闭 Electron Fuse 校验

Electron Framework 中有一组 fuse 开关，用来控制安全能力。

Codex++ 会通过固定 sentinel 字符串定位 fuse 区域，并将其中的：

`EnableEmbeddedAsarIntegrityValidation`

从开启改为关闭。

这相当于进一步关闭 Electron 对嵌入 asar 的完整性验证，和第二层哈希更新形成双保险。

---

##### 4. 重新签名应用

修改应用后，原本的 Developer ID 签名会失效。

Codex++ 使用 macOS 的`codesign`做 ad-hoc 重签名，让系统不拦截应用启动。

这一步解决的是 macOS 安全机制层面的运行问题。

---

##### 插件加载设计：优先保证 Codex 不崩

Codex++ 注入的`loader.cjs`只有约 70 行，设计原则很明确：

> 插件系统崩了，不能带崩 Codex。

它把所有逻辑包在安全函数中：

- 出错只写日志；
- 不中断主流程；
- 最终一定执行原始 Codex 入口。

这体现了很强的工程克制：扩展系统只是增强层，不能影响主应用稳定性。

---

##### Runtime 注入：从混淆代码中找内部服务

Codex 的前端 bundle 是压缩混淆过的，内部变量名不可读。

Codex++ 的做法是用 fingerprint 匹配：

- 搜索包含`buildFlavor`的工厂函数；
- 检查其中是否同时包含`allowDevtools`、`preloadPath`、`globalState`等多个特征属性；
- 命中后回溯找到对应变量；
- 再注入到`globalThis.codexpp_window_services`。

这不是简单字符串替换，而是接近 JS AST 级别的源码补丁。

---

##### 自动更新兼容：最精巧也最脆弱的一环

Codex 使用 Sparkle 做自动更新，而 Sparkle 要求应用有有效的 Developer ID 签名。

但 Codex++ 修改后的应用只有 ad-hoc 签名，无法直接更新。

它的解决方案是：

1. hook Node 的`Module._load`；
2. 拦截 Sparkle 的`installUpdatesIfAvailable`；
3. 更新前把备份的原始签名应用复制回来；
4. 让 Sparkle 正常完成官方更新；
5. 更新后由`launchd`监听`app.asar`变化；
6. 自动重新执行 Codex++ 的修复和注入流程。

最终实现用户无感自动更新。

---

##### 工程评价

Codex++ 的厉害之处在于，它不是单点 hack，而是覆盖了完整生命周期：

- 启动入口劫持；
- 完整性校验处理；
- Electron fuse 修改；
- macOS 重签名；
- 混淆代码识别；
- 运行时内部对象暴露；
- 自动更新兼容；
- 崩溃隔离与恢复机制。

这是一套从二进制层、应用包层、JS 运行时层到更新系统层的完整工程体系。

---

##### 风险与局限

这个方案也有明显脆弱性：

- 依赖当前 Codex 应用内部结构；
- OpenAI 只要改 bundle 结构，fingerprint 可能失效；
- Sparkle hook 和 fuse 修改都属于非官方路径；
- 每次客户端更新都可能导致补丁失效；
- 长期稳定性无法保证。

因此它适合技术探索和高阶玩家使用，不适合作为长期稳定依赖。

---

##### 产品视角启发

Codex++ 反映了一个明确信号：

> 高价值 AI 工具如果缺少官方扩展机制，用户和开发者会用工程手段自行撬开生态。

这说明 Codex 这类 AI Coding 产品未来可能需要：

- 官方插件系统；
- 可控的扩展 API；
- 安全沙箱机制；
- 插件市场；
- 多 Agent /workflow 能力；
- 更开放的本地自动化接口。

否则，民间扩展会持续以非官方方式出现，并承担更高安全和维护成本。

##### 总结

Codex++ 是一个工程水准极高的非官方插件系统项目。它通过修改 Electron 应用包、绕过完整性验证、重新签名、源码注入和自动更新修复等手段，为封闭的 Codex 桌面端强行增加扩展能力。

它的意义不只在技术炫技，更在于揭示了 AI 编程工具生态的一个方向：**用户需要更开放、更可扩展、更可组合的智能开发平台。**
