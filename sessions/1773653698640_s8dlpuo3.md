Agent Orchestrator manages fleets of AI coding agents working in parallel on your codebase. Each agent gets its own git worktree, its own branch, and its own PR. When CI fails, the agent fixes it. When reviewers leave comments, the agent addresses them. You only get pulled in when human judgment is needed.

**Agent-agnostic** (Claude Code, Codex, Aider) · **Runtime-agnostic** (tmux, Docker) · **Tracker-agnostic** (GitHub, Linear)

#### Quick Start

**Option A — From a repo URL (fastest):**

```
# Install
git clone https://github.com/ComposioHQ/agent-orchestrator.git
cd agent-orchestrator && bash scripts/setup.sh

# One command to clone, configure, and launch
ao start https://github.com/your-org/your-repo
```

Auto-detects language, package manager, SCM platform, and default branch. Generates `agent-orchestrator.yaml` and starts the dashboard + orchestrator.

**Option B — From an existing local repo:**

```
cd ~/your-project && ao init --auto
ao start
```

Then spawn agents:

```
ao spawn my-project 123    # GitHub issue, Linear ticket, or ad-hoc
```

Dashboard opens at `http://localhost:3000`. Run `ao status` for the CLI view.

```
ao spawn my-project 123
```

1. **Workspace** creates an isolated git worktree with a feature branch
2. **Runtime** starts a tmux session (or Docker container)
3. **Agent** launches Claude Code (or Codex, or Aider) with issue context
4. Agent works autonomously — reads code, writes tests, creates PR
5. **Reactions** auto-handle CI failures and review comments
6. **Notifier** pings you only when judgment is needed

##### Plugin Architecture

Eight slots. Every abstraction is swappable.

Slot Default Alternatives

Runtime tmux docker, k8s, process

Agent claude-code codex, aider, opencode

Workspace worktree clone

Tracker github linear

SCM github —

Notifier desktop slack, composio, webhook

Terminal iterm2 web

Lifecycle core —

All interfaces defined in `packages/core/src/types.ts`. A plugin implements one interface and exports a `PluginModule`. That's it.

#### Configuration

```
# agent-orchestrator.yaml
port: 3000

defaults:
  runtime: tmux
  agent: claude-code
  workspace: worktree
  notifiers: [desktop]

projects:
  my-app:
    repo: owner/my-app
    path: ~/my-app
    defaultBranch: main
    sessionPrefix: app

reactions:
  ci-failed:
    auto: true
    action: send-to-agent
    retries: 2
  changes-requested:
    auto: true
    action: send-to-agent
    escalateAfter: 30m
  approved-and-green:
    auto: false # flip to true for auto-merge
    action: notify
```

CI fails → agent gets the logs and fixes it. Reviewer requests changes → agent addresses them. PR approved with green CI → you get a notification to merge.

See `agent-orchestrator.yaml.example` for the full reference.

Running one AI agent in a terminal is easy. Running 30 across different issues, branches, and PRs is a coordination problem.

**Without orchestration**, you manually: create branches, start agents, check if they're stuck, read CI failures, forward review comments, track which PRs are ready to merge, clean up when done.

**With Agent Orchestrator**, you: `ao spawn` and walk away. The system handles isolation, feedback routing, and status tracking. You review PRs and make decisions — the rest is automated.

## 产品-技术开发（1）

### 2026-03-16 09:50:06

这个项目的核心，不是“再包一层 AI CLI”，而是把“单个 AI 编码助手”升级成“可运营的多 Agent 软件交付系统”。

**产品解读**
- 它解决的不是写代码能力，而是“并行协作失控”问题：任务分发、环境隔离、CI 失败回流、Review 闭环、人工升级点。
- 真正的产品价值在 `ao spawn and walk away`：把开发者从重复协调动作里解放出来，只在需要 judgment 时介入。
- 用户对象很清晰：不是个人玩具，而是有 issue/PR/CI 流程的团队，尤其适合中大型仓库、多需求并发场景。
- 差异化点不是模型，而是 orchestration：`agent-agnostic`、`runtime-agnostic`、`tracker-agnostic`，避免被单一模型或基础设施绑定。
- 这类产品一旦跑通，价值会从“提效工具”升级为“研发自动化控制面”。

**产品设计上做对了什么**
- **最小接入成本**：`ao init --auto`、从 repo URL 直接启动，符合开发工具的首要原则：先跑起来，再精细配置。
- **默认自动化，关键节点人工决策**：CI fail 自动修、review change 自动处理、approve+green 默认不自动 merge，这个边界非常合理。
- **状态可视化 + CLI 双入口**：Dashboard 负责运营视图，CLI 负责高频操作，适合工程团队真实工作流。
- **插件槽位设计**：Runtime、Agent、Workspace、Tracker、Notifier 等八个槽，本质是在做平台化，不是在做硬编码流程。
- **运维能力前置**：`doctor`、`update`、restore、stuck detection，这些是产品能否进入生产使用的关键，不是锦上添花。

**技术架构解读**
- 核心架构模式是：`任务状态机 + 插件接口 + 事件驱动 reaction`
- `worktree + branch + PR` 是很强的工程选择：相比纯逻辑隔离，它天然对齐 Git 工作流，便于审计、回滚、并发管理。
- `CI failed -> send-to-agent`、`changes requested -> send-to-agent` 说明系统已经不是一次性 agent 调用，而是持续闭环 agent session。
- `tmux/docker` 抽象成 Runtime，意味着它把“Agent 执行环境”从“模型能力”里剥离出来，这对稳定性和可迁移性很重要。
- 插件接口集中在 core types，说明它在用 TypeScript interface 做“平台契约”，这是扩展生态最稳妥的方式。

**技术实现上的最佳实践**
- **1. 用状态机管理生命周期，不要靠脚本拼接**
  - 推荐状态：`queued -> provisioning -> running -> waiting_feedback -> fixing -> blocked -> completed -> failed`
  - 每个状态有明确事件：issue 创建、agent 启动、CI 回调、review comment、human escalation。
  - 好处：可恢复、可审计、可重放。

```ts
type SessionState =
  | "queued"
  | "provisioning"
  | "running"
  | "waiting_feedback"
  | "fixing"
  | "blocked"
  | "completed"
  | "failed";

type Event =
  | { type: "SPAWNED" }
  | { type: "AGENT_STARTED" }
  | { type: "CI_FAILED"; logs: string }
  | { type: "REVIEW_REQUESTED"; comments: string[] }
  | { type: "HUMAN_ESCALATED"; reason: string };
```

- **2. 隔离优先用 Git worktree，而不是复制仓库**
  - worktree 启动快、节省磁盘、天然绑定 branch。
  - 最佳实践：每个 agent 一个 worktree + 独立临时目录 + 独立日志目录。
  - 命名建议：`&lt;project>/&lt;issue>-&lt;agentId>`，便于恢复和清理。

- **3. Reaction 必须事件化，不要把 CI/review 逻辑写死在主流程**
  - 推荐统一 Event Bus：`CI_FAILED`、`PR_COMMENTED`、`APPROVED`、`SESSION_STUCK`
  - 每个 reaction 都是独立 handler，支持重试、幂等、熔断。

```ts
interface ReactionHandler {
  canHandle(event: OrchestratorEvent): boolean;
  handle(event: OrchestratorEvent, ctx: ReactionContext): Promise<void>;
}
```

- **4. Agent 上下文要分层，不要把整个仓库信息一次性塞给模型**
  - 分成：任务上下文、代码上下文、运行反馈、历史决策。
  - 最佳实践：
    - 首次启动给 issue + repo map + coding conventions
    - CI fail 时只追加失败日志和相关文件 diff
    - Review fix 时只追加 reviewer comments + PR diff
  - 这样能显著降低 token 浪费和 hallucination。

- **5. “卡住检测”比“智能程度”更重要**
  - 生产级 agent 最大问题往往不是不会写，而是长时间无效循环。
  - 最佳实践检测信号：
    - 长时间无新 commit
    - 重复执行相同命令
    - 同一测试失败 N 次
    - 输出内容高度重复
  - 检测后动作：重启 session、压缩上下文、切换 agent、升级给人。

**如果你来设计这个产品，我会补强的 5 个点**
- **成果评分层**：不是所有完成都一样，应该对 PR 输出做质量评分，如测试覆盖、diff 风险、是否触碰敏感目录。
- **策略引擎**：不同任务走不同 agent/runtime 策略。比如小修复用 Codex，大重构用 Claude Code，依赖安装走 Docker。
- **上下文记忆层**：跨任务复用 repo 规则、失败模式、常见 reviewer 偏好，减少每次从零学习。
- **成本控制层**：统计单任务 token、运行时长、重试次数、CI 资源消耗，避免多 agent 并行把 ROI 打穿。
- **安全边界层**：敏感目录、生产配置、迁移脚本、权限文件默认 require human approval。

**落地实现的最佳实践例子**
- **例子 1：CI 自动修复**
  - 流程：GitHub Actions fail -> webhook/event ingest -> 拉取失败 job 日志 -> 构造精简 prompt -> 发回对应 agent session。
  - 关键点：
    - 只传 failing test 和相关堆栈
    - 限制 agent 最大修复轮数，如 2~3 次
    - 每次修复后自动跑最小验证集，而不是全量测试

- **例子 2：Review Comment 自动处理**
  - 不要把所有 comment 合成一段长文本。
  - 最佳做法：按文件/代码块聚合 comment，生成 action items：
    - `must-fix`
    - `clarification`
    - `style-only`
  - 只有 `must-fix` 自动执行，其他先总结给开发者确认，避免 agent 过度修改。

- **例子 3：并行 Agent 调度**
  - 不是 issue 越多 agent 越多。
  - 推荐调度规则：
    - bugfix 高优先级
    - 修改相同目录的任务避免并行，减少 merge conflict
    - 高风险文件（schema、infra、auth）限制单并发
  - 这比单纯“多开几个 agent”更体现 orchestrator 的系统价值。

- **例子 4：自动合并策略**
  - 这个项目默认 `approved-and-green` 不自动 merge，是对的。
  - 生产建议：
    - 文档/测试类 PR 可 auto-merge
    - 核心业务代码 require human confirmation
    - 数据库迁移、权限变更、CI 配置修改禁止 auto-merge

**潜在风险**
- 多 agent 并发会把“编码问题”变成“调度和冲突问题”，尤其是同目录修改、共享依赖升级。
- 如果没有强幂等机制，CI/review webhook 很容易重复触发，导致 agent 重复工作。
- 模型切换虽然灵活，但不同 agent 的 patch 风格、命令习惯、上下文理解不一致，会增加系统复杂度。
- 自动修复如果没有风险分级，容易出现“CI 绿了，但语义错了”的假成功。

**一句话判断**
- 这是一个很有产品势能的方向：它不试图替代 IDE 里的 AI，而是在研发流程层做“Agent OS”。
- 真正的壁垒将不在模型接入，而在：状态管理、事件编排、恢复机制、风险控制、组织级工作流适配。

如果你愿意，我可以下一步继续帮你做两件事之一：
1. 把这个项目拆成产品架构图 + 技术架构图
2. 进一步分析它的源码目录，判断实现质量和可扩展性

## 产品-最佳实践（1）

### 2026-03-16 09:52:33

下面我用一个具体场景，基于 `ComposioHQ/agent-orchestrator` 的能力，给出一套可落地的最佳实践。

**具体实例**

假设你维护一个 TypeScript monorepo，里面有 3 个子模块：

- `packages/api`
- `packages/web`
- `packages/shared`

现在团队要同时推进 3 类工作：

- Issue `#201`：给 `api` 增加审计日志
- Issue `#202`：修复 `web` 端的登录态刷新 bug
- Issue `#203`：升级 `shared` 的校验库并修复相关测试

你希望不是让一个 AI agent 串行做完，而是让 3 个 agent 并行推进，并且在 CI 失败、PR 被 reviewer 提意见时，系统自动回流给 agent 修复，只有在需要你做产品判断或架构取舍时才通知你。

这就是 `agent-orchestrator` 最适合发挥价值的场景。

---

**推荐做法**

先说结论：这个工具的最佳实践，不是“把任务丢给很多 agent”，而是“把任务拆成足够独立、可验证、可回收的工作单元，再让 orchestrator 自动管理它们的生命周期”。

---

**一、任务拆分：按边界拆，不按人脑感觉拆**

在这个例子里，最佳拆法不是：

- “一个 agent 做后端”
- “一个 agent 做前端”
- “一个 agent 顺手升级依赖”

而是按“可独立提交 PR、可独立验证 CI、尽量少冲突”的边界拆：

- Agent A：只处理 `packages/api` 的审计日志
- Agent B：只处理 `packages/web` 的登录态刷新
- Agent C：只处理 `packages/shared` 的校验库升级

最佳实践：

- 一个 agent 对应一个 issue 或一个明确目标
- 每个任务尽量只触碰一个模块或一类职责
- 避免让多个 agent 同时改公共文件，如根级 `package.json`、共享接口定义、全局配置
- 如果必须改共享代码，先单独开一个“基础设施 PR”，合并后再让其他 agent 继续

为什么这么做：

- worktree 隔离可以避免工作目录互相污染，但不能避免语义上的 merge conflict
- CI 和 code review 自动回流时，任务边界越清晰，agent 修复越稳定
- 出问题时更容易 `restore`、`kill`、重跑，而不会拖累整个批次

---

**二、配置策略：默认自动修复，但不要默认自动合并**

这个场景下，推荐的配置思路是：

- `ci-failed`: 自动回送给 agent
- `changes-requested`: 自动回送给 agent
- `approved-and-green`: 默认通知，不自动合并

原因很简单：

- CI 失败通常是机械性修复，适合 agent 自动处理
- reviewer 的明确修改意见也常常可以自动落实
- 但“是否可以合并”往往涉及产品、时机、发布节奏，不建议一开始就放开 auto-merge

这个例子里更稳妥的策略是：

- `#202` 登录态 bug：即使绿了，也先人工看一下用户体验和回归风险
- `#203` 依赖升级：尤其不要直接 auto-merge，因为可能有运行时兼容问题
- 只有像文档修复、纯测试增强这类低风险改动，才考虑逐步开启自动合并

一句话：  
把“修复动作”自动化，把“最终决策”留给人。

---

**三、给 agent 的输入要标准化，不要只给一句 issue 标题**

很多团队用 agent 效果不稳定，不是 orchestrator 不行，而是任务上下文给得太弱。

以 `#201` 审计日志需求为例，好的任务描述应该至少包含：

- 目标：哪些操作要打日志
- 非目标：不要改数据库 schema，不要引入新消息队列
- 验收标准：新增单测、保留原有 API 行为、日志字段包含 userId/action/timestamp
- 约束：沿用现有 logger，不引入新依赖
- 风险提示：注意 PII 脱敏

最佳实践：

- issue 模板化
- 把“验收条件”写成 checklist
- 把“不允许做什么”明确写出来
- 对 agent 说清楚“先改测试再改实现”或者“先输出计划再编码”

比如对 `#201`，你可以让 agent 接到的上下文类似：

- 在 `packages/api` 内实现
- 仅修改审计相关 service 和测试
- 不改公共 DTO
- 必须补充集成测试
- 完成后 PR 描述里列出影响范围与风险点

这样 agent 的自主性会更强，但漂移会更少。

---

**四、分支与 worktree 纪律：隔离不只是技术动作，更是协作规则**

这个工具的核心优势之一，是每个 agent 都有独立 git worktree 和分支。  
但最佳实践是把这种隔离上升成流程约束：

- 一个会话只做一件事
- 不允许 agent 在同一个 session 里顺手修 unrelated bug
- session 名称带上项目和 issue 编号
- PR 标题、分支名、issue 编号一一对应

在这个例子里，可以约定：

- `feat/api-audit-log-201`
- `fix/web-auth-refresh-202`
- `chore/shared-validator-upgrade-203`

这样带来的好处：

- dashboard 一眼能看清每个 agent 在干什么
- reviewer 更容易定位责任和范围
- 某个 agent 卡死或失控时，可以直接 `ao session kill`，不会影响其他工作

---

**五、CI 自动回流：要让 agent 修“可诊断失败”，不要修“黑盒失败”**

在这个实例中，最容易获得收益的是 CI 自动修复。  
但前提是 CI 输出对 agent 足够友好。

最佳实践：

- 让测试失败信息清晰、可定位
- lint/typecheck/test 分阶段执行，而不是全塞在一个模糊脚本里
- 错误日志尽量直接指向文件和断言
- flaky test 先治理，再交给 agent 自动修

例如 `#203` 升级校验库后 CI 挂了，如果日志明确显示：

- `packages/shared/src/validator.ts` 某个 API 已废弃
- `packages/api` 里的两个测试快照需要更新

agent 通常能很快完成修复。  
但如果 CI 只报一句“build failed”，或者测试高度不稳定，agent 往往会反复试错，成本高且可能引入额外改动。

所以最佳实践不是“让 agent 自己悟”，而是先把 CI 设计成适合机器修复。

---

**六、Code Review 回流：让 reviewer 提“可执行意见”**

这个 orchestrator 的另一个关键价值，是 reviewer 提完意见后，agent 能继续处理。

但这里有个非常重要的实践：  
review comment 要尽量具体、可执行。

坏评论：

- “这里感觉不太对”
- “再优化一下”
- “写法不够优雅”

好评论：

- “`packages/web/auth/session.ts` 这里应改为从 refresh endpoint 返回 expiresAt，而不是本地推算”
- “请补一个 token 过期后自动跳转登录页的测试”
- “不要在 shared 层引入浏览器 API，保持同构兼容”

原因是：

- agent 对明确修改意见执行力强
- 对模糊的审美判断，容易过拟合或反复横跳
- 回流链路越自动，越需要评论具备“机器可消费性”

在这个例子中，reviewer 最好按以下格式留言：

- 问题是什么
- 要改哪里
- 接受标准是什么

这样 orchestrator 才能真正把 code review 变成自动化闭环。

---

**七、设置人工升级点：哪些情况必须打断自动流程**

“只在需要人类判断时通知你”是这个系统的卖点，但前提是你要先定义什么叫“需要判断”。

在这个实例里，建议把以下情况设为人工升级点：

- agent 修改了共享接口或根配置
- 同一个 PR 连续 2 次以上 CI 修复失败
- reviewer 提出架构层分歧，而不是具体代码问题
- 涉及安全、权限、计费、数据删除等敏感逻辑
- 依赖升级引入 major version 变化

例如 `#203` 升级校验库时，如果 agent 开始改很多跨包类型定义，这就不是普通自动修复了，应通知你介入。

最佳实践不是追求“100% 自动”，而是追求“80% 的机械劳动自动，20% 的关键判断及时拦截”。

---

**八、给 agent 设定停止条件，避免无限修 bug**

并行 agent 最大的隐患不是它不会工作，而是它会一直工作。

所以这个实例里非常建议：

- 对每个 reaction 设置重试上限
- 对 stuck session 设置阈值
- 超过阈值后转人工而不是无限循环
- 要求 agent 在 PR 描述里记录“尝试过什么”

尤其像 `#202` 登录态问题，如果失败原因是后端接口行为不明确，agent 可能在前端不断试错。  
这类问题不该无限重试，而该尽快通知你：这是需求/接口定义问题，不是纯编码问题。

---

**九、观察与复盘：把每个 agent 当成可优化的生产流程**

这个工具不是只帮你“做事”，还应该帮你“优化做事方式”。

在这个实例落地后，建议你每周复盘这几个指标：

- 哪类 issue 最适合并行 agent
- 哪类 PR 最容易反复卡在 CI
- 哪类 review comment agent 最难处理
- 哪些文件最容易发生冲突
- 从 `spawn` 到 `merge` 的平均时长

你会很快发现规律，比如：

- 模块内 bugfix 很适合自动化
- 跨层重构不适合一次性丢给 agent
- 依赖升级类任务需要更强人工把关
- 测试质量越高，自动修复成功率越高

最佳实践不是只用工具，而是用数据不断调整任务类型、配置策略、review 规范。

---

**一套推荐落地方案**

如果你要把上面的例子真正跑起来，我建议按这个顺序：

- 先选 3 个低耦合 issue 做试点，不要一开始就上 20 个 agent
- 先开启自动处理 `ci-failed` 和 `changes-requested`
- 暂时关闭 `approved-and-green` 的 auto-merge
- 统一 issue 模板，增加验收标准、边界和禁区
- 统一 PR 模板，要求 agent 写清改动范围、风险、测试结果
- 对共享模块和敏感逻辑设置人工升级规则
- 每周复盘一次失败案例，优化模板和 reaction 策略

---

**一句话版最佳实践**

在 `agent-orchestrator` 上，最佳实践不是“多开 agent”，而是：

- 用 worktree 做物理隔离
- 用 issue 模板做任务约束
- 用 CI/review reaction 做闭环修复
- 用人工升级点守住关键决策
- 用复盘数据持续优化任务分配策略
