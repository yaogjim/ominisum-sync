**dan**

昨晚晚餐时我和一位老朋友聊天，他描述了 GPT 疲劳

我研究过整个精神病相关的问题，但疲劳不一样，而且这次的感觉很贴合我。我经历过这种循环，现在可能刚从第三次 GPT 疲劳期走出来。

这真是苦乐参半。在这些混乱的工作区域间进行上下文切换的认知负担，远不如我在职业生涯前十二年里一直享受的那种沉浸编码的节奏来得有趣。

我连接了我一直在研究的反应堆线束，他眼睛一亮（是的，这是一篇发布帖，继续阅读）。我告诉他基本想法：

就像 React (js)通过基于上游事件高效地渲染声明的组件来保持 DOM 更新一样...

Reactor Harness 通过基于上游事件高效渲染世界模型的声明方面，使理想世界模型保持最新状态。

这个世界模型可以是任何东西——从形式上来说，它是一个多面的内容可寻址二进制大对象。在实际中，它可以是一个文件、一个目录、一个 SQLite 表等等。

如果你从一开始就关注 OpenProse 的话，你会猜到渲染函数不是确定性的字节码，而是由代理会话执行的声明式 Markdown 指令。

我今天在这里发布这个工具的测试版。它以 SDK 形式发布，你可以将其集成到自己的项目中。我们还构建了一个实验性的 CLI 工具，附带一个轻量级服务器和一个开发工具包。请在这里给它点个 GitHub 星标支持一下，然后回来阅读更多内容：

[https://github.com/openprose/prose](https://github.com/openprose/prose)

Reactor Harness 设计用于运行 OpenProse，其设计独特地受到 OpenProse 背后宗旨的影响，从而你可以使用熟悉的结构化 Markdown 声明你的理想世界模型，并且你可以可选地使用我们原创的 ProseScript 编写指令式的实现计划。

思考 Reactor 的一种方式是将其视为代理会话的有向无环图（DAG）。DAG 中的每个节点都是一个代理会话，负责保持世界模型的各个方面最新。这些会话会被记忆化，因此下游依赖的会话仅在其上游对应会话发生变化时才会重新运行。

在接下来的几天里，我将写更多关于这个测试框架的内容，包括我们如何使用它，以及我希望我们能将其带向何方。我们正在对它进行基准测试。目标是 SDK API 本身保持相对稳定，同时我们在内部改进代理会话的实现成本、速度和智能性。

我们是怎么走到这里的？

今天，我将我们公司的很大一部分业务保存在一个目录中：原则、规格、代码、数据分析、我们的烧钱模型、我们的销售线索增强型 CRM。

我发现自己不得不手动“快进”这些模型，进入上下文并主动告知 Claude Code 更新规范、将某人添加到 CRM 中，或根据已改变我们计划的实际事件更新财务模型。

我编写了许多 OpenProse 脚本来完成这些任务，但我发现我希望这些脚本能以反应式方式运行，作为一项持续且不受时间影响的职责，而不是作为一个我需要不断使用的工具那样主动运行。我们解决这个问题的首次尝试是在 cron 上运行 OpenProse 程序。但这样做的问题是，它很快就变得非常昂贵。

当我开始尝试设计 OpenProse 使其在这些约束条件下运行时，我发现自己在维护的状态的不同方面引入了像记忆化这样的概念。从那以后，我决定不重复造轮子，并更明确地借鉴 React 中的模式。这是一种类比，而且这种类比在某些地方会失效。但这是一个很多人都熟悉的合理起点。

我们在四月份内部为一位客户的需求，基于我们的托管服务构建了第一个版本，但我认为这个项目的核心内容足够有趣，值得向公众开放，因此我们在接下来的六周内对其进行了彻底重构，并重新设计为 SDK，以便人们能够将其集成到自己的技术栈中。

我怎么强调都不为过，这里其实没什么新东西，我们只是在将经典工程范式应用到我们这个勇敢的新世界中。我们发现，尽管我们的现实如此混乱，古人的智慧依然适用。

Reactor harness 尚处于早期阶段，使用时需谨慎，距离理想形态还有一定差距。我的请求是，你尝试使用它，将其连接到有用的事物上，无论喜欢还是不喜欢，都请给我发送关于你的使用体验的真实反馈。我们一直在倾听并不断改进。

我心中有一个特别令人兴奋的最终目标：由于 Reactor DAG 本身就是一个世界模型，来自现实世界事件的下游（例如，习得的事件源/频率/分布），你可以使用 Reactor 本身来实现动态 Reactor DAG。这使我们走上了真正的 RLM 范式之路。我对此最为兴奋，因为我假设这将产生 Reactor 的一种简单、优雅的属性：

维护世界模型的推理成本随意外性增加而增加，而非实际时间。

现在还没实现，但我相信这是可以做到的，而且这只是一个逐步推进就能达成的目标。根据我的经验，如果过早地让某个东西具有自指性，它可能会自我崩溃，所以我们会逐步地一步步实现它。

当我们确实到达那里时，我希望 Meta Reactor DAG 能够在事件源/频率/分布上进行自校准，以优化高效执行的 Reactor DAG，并且保持世界模型的最新状态的成本仅接近现实世界中上游事件带来的意外。

昨晚晚餐时，我们反复讨论的一个话题是我们与这些模型之间形成的爱恨交织的关系。自 2020 年我对 GPT-2 进行微调以来，我就一直在为这些崭露头角的 AI 构建工具。在很多方面，我和以往使用技术时一样感到乐趣。然而，在其他很多方面，我开始厌恶它们带来的影响。

最后，我觉得真正的目标是，Reactor Harness 让我能够从根源上卸下导致我 GPT 疲劳的认知负担，并且让我能投入到更有趣的 GPT 心理状态中 :D

## 解读（1）

#### 深度总结

这篇帖子的核心是：**作者想解决 “GPT 疲劳”—— 频繁指挥 AI、切换上下文、手动维护各种工作状态带来的认知负担。**

他发布了一个工具**Reactor Harness**，试图把 AI 工作流做成类似**React**的反应式系统：

- React 根据数据变化自动更新界面；
- Reactor Harness 根据现实事件变化，自动更新 “世界模型”。

这里的 “世界模型” 可以是：

- 文件
- 目录
- SQLite 表
- CRM
- 财务模型
- 产品规格
- 公司运营文档

它的基本结构是一个**DAG 有向无环图**：

- 每个节点是一个 AI agent 会话；
- 每个节点负责维护世界模型的一部分；
- 上游变化时，下游才重新运行；
- 没变化就不重复计算，以降低成本。

作者原本用 OpenProse 脚本手动更新公司状态，但发现这仍然需要自己不断触发。后来尝试 cron 定时运行，又太贵。于是他借鉴 React 的 “按变化重渲染” 思想，做出 Reactor Harness。

他的长期愿景是：

> AI 维护世界模型的成本，不应随时间流逝增加，而应随 “意外事件” 增加。

也就是说，如果世界没发生重要变化，AI 就不该一直消耗推理资源；只有出现新信息、新冲突、新异常时，系统才投入更多计算。

---

#### 通俗解读

可以把它理解成：

##### 以前：人当 “总调度员”

你要不断对 AI 说：

- 更新一下 CRM；
- 把这个客户信息加进去；
- 根据新计划改一下财务模型；
- 同步一下产品规格；
- 重新整理项目文档。

问题是：  
**AI 很强，但你得一直提醒它干活。**

久了就会累，这就是作者说的**GPT fatigue**。

---

##### 现在：让 AI 像 React 一样自动更新

React 的逻辑是：

> 数据变了，页面自动刷新。

Reactor Harness 的逻辑是：

> 现实变了，相关文档 / 模型 / 数据库自动更新。

比如：

- 新客户邮件来了；
- CRM 自动更新；
- 销售预测跟着变化；
- 财务模型自动调整；
- 产品路线图可能也被提醒修改。

但如果客户信息没变，就不重新跑，避免浪费钱和算力。

---

#### 关键价值

##### 1. 降低上下文切换

人不用反复进入不同任务状态。

##### 2. 降低 AI 使用成本

不是定时全量跑，而是变化驱动。

##### 3. 把 AI 从 “聊天工具” 变成 “状态维护系统”

这比单次对话更接近真正的工作流自动化。

##### 4. 让公司知识库保持 “活的”

文档、数据、模型不再是静态资料，而是随现实变化更新。

---

#### 辩证思考

##### 值得肯定

这个方向很重要。  
当前很多人使用 AI 的痛点不是 “模型不够聪明”，而是：

> 人仍然要承担太多编排、提醒、校验和上下文管理。

Reactor Harness 试图把 AI 从 “被动助手” 推进到 “主动维护者”，这是 AI 工程化的自然方向。

尤其是 “成本随意外性增加，而非随时间增加” 这个理念很有价值。  
它抓住了智能系统的关键：**真正需要推理的不是日常重复，而是变化、冲突和异常。**

---

##### 需要警惕

但这个系统也有明显风险：

###### 1. 世界模型可能更新错

AI 自动改文档、CRM、财务模型，一旦误判，错误会层层传递。

###### 2. DAG 依赖会变复杂

节点越多，依赖越复杂，调试难度可能暴涨。

###### 3. “自动化” 可能制造新的疲劳

如果系统经常误触发、误更新、误总结，人反而要花更多时间审查。

###### 4. 自指系统风险更高

作者提到未来让 Reactor 自己维护 Reactor DAG。  
这很强大，但也危险：  
系统如果能改自己的结构，就必须有严格边界、审计和回滚机制。

---

#### 我的判断

Reactor Harness 代表的是一种趋势：

> AI 应用会从 “聊天界面” 走向 “反应式状态系统”。

它不一定是最终答案，但方向是对的。

真正的突破不在于让 AI 多说几句话，而在于让 AI：

- 知道什么变了；
- 判断什么该更新；
- 只更新相关部分；
- 保持可追踪、可验证、可回滚。

如果能做到这一点，AI 才能从 “聪明工具” 变成 “可靠基础设施”。

一句话概括：

> 这不是在造一个更会聊天的 AI，而是在造一个能持续维护现实状态的 AI 操作系统雏形。

## 结构化（1）

### 2026-06-11 10:09:03

##### 主旨概括

作者从自己反复经历的“GPT 疲劳”出发，介绍了一个新工具 **Reactor Harness**：它试图用类似 React 的“响应式更新”思想，帮助 AI Agent 持续维护一个“理想世界模型”，从而减少人手动切换上下文、反复指挥模型的认知负担。

---

##### 1. GPT 疲劳：问题的起点

作者和朋友聊天时提到一种不同于“AI 精神病”等问题的体验：**GPT 疲劳**。

- 作者已经经历过多次 GPT 疲劳，目前可能刚走出第三次。
- 疲劳的核心不是不用 AI，而是：
  - 需要在多个混乱工作区之间不断切换上下文；
  - 反复告诉 AI 当前项目状态、要改什么、为什么改；
  - 这种工作方式远不如过去长期沉浸式写代码来得有趣。
- 作者希望通过工具减少这种“上下文切换”和“手动推动 AI 更新状态”的负担。

---

##### 2. Reactor Harness 的核心想法：像 React 更新 DOM 一样更新世界模型

作者发布了 **Reactor Harness** 的测试版，并用 React 作类比解释它。

- React 的作用是：
  - 根据上游事件变化，高效渲染声明式组件；
  - 让 DOM 保持最新。
- Reactor Harness 的作用是：
  - 根据上游事件变化，高效更新“世界模型”的各个声明式部分；
  - 让理想状态持续保持最新。

这里的“世界模型”可以是很多东西，例如：

- 一个文件；
- 一个目录；
- 一个 SQLite 表；
- 公司内部知识库；
- CRM；
- 财务模型；
- 数据分析结果等。

简单说，用户先声明“我希望世界应该是什么样”，Reactor Harness 负责在现实事件变化后，让这些内容自动更新。

---

##### 3. 工具形态：SDK、CLI 与 OpenProse

Reactor Harness 目前以测试版形式发布。

- 它主要以 **SDK** 形式提供，方便开发者集成到自己的项目中。
- 作者团队还提供了：
  - 一个实验性 CLI 工具；
  - 一个轻量级服务器；
  - 一个开发工具包。
- 项目地址：  
  [https://github.com/openprose/prose](https://github.com/openprose/prose)

该工具最初是为运行 **OpenProse** 设计的。

- 用户可以用熟悉的结构化 Markdown 声明理想世界模型。
- 也可以使用团队原创的 **ProseScript** 编写更具体的执行计划。
- 与传统确定性代码不同，OpenProse 的“渲染函数”不是普通字节码，而是由 Agent 会话执行的 Markdown 指令。

---

##### 4. 工作机制：把 Agent 会话组织成 DAG

作者将 Reactor Harness 描述为一个由 Agent 会话组成的 **有向无环图（DAG）**。

- DAG 中每个节点都是一个 Agent 会话。
- 每个会话负责维护世界模型中的某一部分。
- 这些会话会被“记忆化”：
  - 如果上游没有变化，下游就不会重新运行；
  - 只有相关上游状态改变时，对应 Agent 会话才会重新执行。

这类似于 React 中的响应式更新和缓存机制，目的都是减少不必要的计算。

举例来说：

- 一个上游事件可能是“新增了一个销售线索”；
- 下游状态可能是 CRM、销售计划或财务预测；
- Reactor 会只触发相关节点更新，而不是让所有 Agent 重新跑一遍。

---

##### 5. 为什么需要它：作者自己的公司管理场景

作者提到，他现在把公司很大一部分业务状态都保存在一个目录中，包括：

- 原则；
- 规格文档；
- 代码；
- 数据分析；
- 烧钱模型；
- 销售线索增强型 CRM。

但问题是，这些内容并不会自动随现实变化而更新。

作者过去需要手动让 Claude Code 做很多事，例如：

- 更新规范；
- 把某个人添加到 CRM；
- 根据真实业务事件更新财务模型；
- 根据计划变化调整文档和数据。

他也写过很多 OpenProse 脚本来处理这些任务，但仍然需要主动运行。作者真正想要的是：这些脚本能像后台职责一样持续运行，而不是每次都由人手动触发。

---

##### 6. 早期尝试：用 cron 定时运行，但成本太高

团队一开始尝试用 cron 定时运行 OpenProse 程序，让它们周期性检查并更新状态。

但这种方式很快暴露问题：

- 定时运行不管有没有变化都会执行；
- Agent 调用成本很高；
- 随着任务增加，费用会迅速上升；
- 也容易产生大量无意义计算。

因此作者开始引入类似“记忆化”的机制，只在必要时重新计算相关状态。

后来他意识到，这其实和 React 的思想很接近，于是更明确地借鉴了 React 的模式。

---

##### 7. 项目演进：从客户需求到公开 SDK

Reactor Harness 的第一个版本，是团队在四月份为一位客户需求内部构建的，基于他们的托管服务运行。

后来作者认为这个项目的核心思想足够有趣，值得开放给更多人使用。

因此团队在接下来的六周内：

- 对项目进行了大规模重构；
- 将其重新设计成 SDK；
- 让开发者可以集成到自己的技术栈中。

作者也强调，这并不是全新的发明，而是把经典工程范式应用到 AI Agent 时代。

---

##### 8. 当前状态：仍处早期，希望用户试用反馈

作者明确表示，Reactor Harness 还处于早期阶段。

- 目前距离理想状态还有差距；
- 使用时需要谨慎；
- SDK API 的目标是保持相对稳定；
- 团队会持续优化 Agent 会话的：
  - 成本；
  - 速度；
  - 智能程度。

作者希望用户：

- 尝试使用它；
- 将其连接到真实有用的任务上；
- 无论喜欢还是不喜欢，都反馈真实体验。

---

##### 9. 更长远目标：让维护世界模型的成本取决于“意外性”，而不是时间

作者提出了一个更令人兴奋的终极目标：让 Reactor DAG 自身也成为一个世界模型，并能根据现实事件动态调整自己。

也就是说，未来可能出现一种“Meta Reactor DAG”：

- 它能观察现实世界事件源；
- 学习事件出现的频率和分布；
- 自动校准哪些节点该更频繁检查；
- 优化整个 DAG 的执行效率。

作者希望最终实现一个特性：

> 维护世界模型的推理成本，应该随着“意外性”增加，而不是随着实际时间流逝增加。

通俗理解：

- 如果现实没有变化，就不该反复花钱调用模型；
- 如果发生了重要变化，系统才应该投入更多推理资源；
- AI 系统的运行成本应该接近真实世界中“新信息”带来的变化量。

作者承认这还没有实现，但相信可以逐步达到。他也提醒，过早让系统自指和自我调整，可能会导致复杂性失控，所以团队会谨慎推进。

---

##### 10. 作者的情绪与最终目标：缓解 GPT 疲劳，找回更有趣的 AI 使用状态

文章最后回到“GPT 疲劳”。

作者说，自 2020 年微调 GPT-2 以来，他一直在为新兴 AI 构建工具。

他的感受是复杂的：

- 一方面，和过去使用技术一样，他仍然觉得 AI 很有趣；
- 另一方面，他也开始厌恶 AI 带来的某些影响，尤其是持续上下文管理和认知负担。

因此，Reactor Harness 的真正目标是：

- 从根源上卸下导致 GPT 疲劳的认知负担；
- 让 AI 自动维护状态；
- 让人重新进入更有创造性、更有趣的 GPT 使用体验。

---

##### 11. 热门回复中的关键讨论

几条热门回复也进一步说明了大家关注的方向：

- 有人将其类比为“智能乐高积木”：
  - 每个积木负责一个关注点；
  - 只有上游上下文变化时才重新计算。
- 有人理解为：
  - 定义一个规范的事实来源；
  - 类似 React 的 DOM；
  - 模型负责协调和更新它。
- 作者回应说，这个理解基本正确：
  - 用户定义理想状态；
  - 连接可能影响它的上游事件源；
  - 状态变化时执行 Agent 会话；
  - Reactor 的价值在于可以组织成 DAG，而不只是单一事件源到单一状态。
- 也有回复认为，这与“世界模型递归更新”和 RLM 范式非常接近。

---

##### 总结

Reactor Harness 是作者为解决 GPT 疲劳和 Agent 上下文管理问题推出的早期工具。它借鉴 React 的响应式更新思想，把多个 Agent 会话组织成 DAG，只在上游状态变化时更新相关世界模型，从而减少重复推理成本和人工干预。作者希望它最终能发展成一种更高效的 AI 世界模型维护系统：成本不再随时间增长，而是随现实变化的“意外性”增长。

##### 2. 最重要的洞见

###### 洞见 1：GPT 疲劳的本质不是使用太多 AI，而是人被迫充当“上下文同步器”

###### **核心观点：**  
> 人类在 AI 工作流里的痛苦，不是提问本身，而是不断把现实变化、项目状态、历史背景重新喂给模型。

**为什么重要：**  
现在很多 AI 产品默认用户负责上下文管理：  
- 告诉模型发生了什么  
- 指定哪些文档要更新  
- 解释当前状态  
- 手动维护规范、CRM、财务模型、代码上下文  

这让人从“创造者”退化成“状态搬运工”。

**反常识之处：**  
常见看法是：GPT 疲劳来自模型输出不稳定、幻觉、交互太多。  
作者的判断更深：**疲劳来自认知上下文切换，而不是模型能力不足。**

**可迁移价值：**  
所有知识型工具都应问一个问题：

> 用户是不是在替系统维护上下文？

如果是，产品就还有巨大优化空间。

**我应该记住什么：**  
> 好的 AI 系统不应要求人不断解释世界，而应自己持续维护世界模型。

---

###### 洞见 2：Agent 不应像工具一样被调用，而应像 React 组件一样被“触发重算”

###### **核心观点：**  
> 把 Agent 看成响应上游事件的节点，而不是等待人类调用的聊天窗口。

作者借用 React 的思想：  
- React 根据状态变化更新 DOM  
- Reactor Harness 根据现实事件更新世界模型  

这意味着 AI 工作流可以从：

> 人发现变化 → 人打开 AI → 人解释背景 → AI 更新结果

变成：

> 上游事件变化 → 相关 Agent 节点自动运行 → 世界模型局部更新

**为什么重要：**  
这把 AI 从“交互界面”推进到“持续运行的系统架构”。

**反常识之处：**  
主流 AI 产品仍围绕 Chat、Prompt、Copilot。  
作者暗示：**Chat 只是过渡形态，真正重要的是事件驱动的状态维护系统。**

**可迁移价值：**  
可迁移到很多场景：  
- CRM：客户事件变化后自动更新画像和下一步动作  
- 财务模型：真实经营数据变化后自动更新预测  
- 产品文档：代码或用户反馈变化后自动更新规格  
- 组织管理：会议、决策、人员变动自动同步到组织知识库  

**我应该记住什么：**  
> Agent 的未来不是“更会聊天”，而是“在正确事件发生时自动重算正确部分”。

---

###### 洞见 3：降低 AI 成本的关键不是少用模型，而是避免无意义重算

###### **核心观点：**  
> AI 系统的成本应随“意外性”增加，而不是随时间流逝增加。

> 维护世界模型的推理成本随意外性增加而增加，而非实际时间。

这很关键。

用 cron 定时跑 Agent 会很贵，因为它不管世界有没有变化，都会重算。  
更合理的方式是：只有上游状态真的变化，才触发相关下游节点。

**为什么重要：**  
AI 应用的长期成本瓶颈，不只是 token 单价，而是架构是否会产生大量无效推理。

**反常识之处：**

- 换便宜模型  
- 压缩 prompt  
- 减少上下文长度  

作者关注的是更底层的问题：

> 系统为什么要在没有新信息时思考？

**可迁移价值：**  
这是一个通用工程原则：

> 成本应该绑定信息增量，而不是绑定时间或流程惯性。

适用于：  
- 数据分析  
- 自动化运营  
- 风控系统  
- 监控告警  
- AI Agent 编排  
- 企业知识库更新  

**我应该记住什么：**  
> 好系统不是更频繁地计算，而是在世界真的变了时才计算。

  应把世界模型拆成 DAG 节点，并用记忆化机制，只在上游变化时重算下游。

- 推导结论：
