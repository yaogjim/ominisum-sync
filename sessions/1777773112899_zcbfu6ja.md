## 分析要点

- **核心高价值点**：将记忆分为常驻精简记忆、可搜索历史、程序化技能和深层用户模型，并通过保持提示词稳定来优化缓存成本。
- **留存建议**：长期保留（文章提炼了AI Agent记忆系统的分层架构、冷热分离、提示词缓存优化等关键设计原则，对构建长期可用的智能体系统有较高参考价值。）

**知识要点**

- Hermes 使用 MEMORY.md 和 USER.md 保存极小规模的高价值常驻记忆，避免把全部历史塞入系统提示词。
- SQLite 会话库和 session\_search 用于长尾历史回溯，通过全文搜索和辅助模型摘要返回相关上下文。
- 压缩长对话前执行 memory flush，将值得长期保留的信息写入持久记忆，降低摘要丢失风险。
- 技能系统相当于程序记忆，只在提示词中放技能索引，按需加载具体技能内容。
- Honcho 层通过首轮注入和后续附加到用户消息的方式兼顾用户建模与提示词缓存稳定性。

**行动项**

- 在设计Agent记忆系统时区分热记忆、冷历史、技能记忆和用户模型，不要把所有内容放进系统提示词。
- 为长期记忆设置严格容量上限，只保存用户偏好、稳定事实、反复修正和可复用规范。
- 实现会话历史搜索机制，用数据库和摘要模型替代全量上下文注入。
- 在上下文压缩前增加记忆冲刷步骤，主动保存长期有用信息。
- 评估当前Agent系统是否因频繁修改系统提示词而破坏Prompt Caching。

## 正文

**宝玉**

转译：深度拆解 Hermes Agent 的记忆系统：它如何修正 OpenClaw 的误区

如果你读过我之前关于 ChatGPT、Claude 以及 Clawdbot 记忆系统的文章，你就会知道我一直在钻研同一个问题：这些 AI 智能体（AI Agent）到底是怎么记事的？

Hermes Agent 对我来说格外有趣，因为这次我不需要只靠观察它的行为来搞“逆向工程”。Hermes 是开源的，它的代码库和文档都是公开的。所以，我没有通过提示词（Prompt）去盲测这个黑盒，而是直接翻看了它的代码路径——从它如何构建提示词状态、持久化会话，到如何清理记忆和查询历史对话。

简而言之：Hermes 拥有的不是一套记忆系统，而是四套。

1\. 存储在 MEMORY.md 和 USER.md 中、经过高度浓缩的提示词记忆。  
2\. 通过 session\_search 调用的 SQLite 历史会话存档（可搜索）。  
3\. 像程序记忆（Procedural Memory）一样运作的智能体技能管理。  
4\. 可选的 Honcho 层，用于更深层的用户建模（User Modeling）。  
把这些设计联系在一起的核心逻辑非常简单：保持提示词稳定以便利用缓存（Caching），其他一切繁杂信息都交给工具。

让我们深入聊聊。

Hermes 的上下文结构  
在理解记忆之前，我们先看看 Hermes 到底给模型发送了什么。

系统提示词（System Prompt）大致是按以下顺序组装的：  
\-------  
\[0\] 默认智能体身份  
\[1\] 工具使用行为指南  
\[2\] Honcho 集成模块（可选）  
\[3\] 可选系统消息  
\[4\] 固化的 MEMORY.md 快照  
\[5\] 固化的 USER.md 快照  
\[6\] 技能索引  
\[7\] 上下文文件（AGENTS.md, SOUL.md 等规则文件）  
\[8\] 日期/时间 + 平台信息  
\[9\] 对话历史  
\[10\] 当前用户消息  
\--------

这非常关键，因为 Hermes 正在针对大模型供应商的提示词缓存（Prompt Caching）机制进行优化。代码显示，提示词构建器的目标非常明确：让稳定的前缀部分尽可能长时间地保持不变。

这一个决定就解释了 Hermes 大部分的记忆架构。

如果某条信息每一轮对话都要用到，Hermes 会尽量把它缩得很小并注入进去；如果信息量很大、属于历史旧账或者偶尔才有用，Hermes 就会把它踢出提示词，改用“按需检索”的方式。

第一层：固化的提示词记忆

其内置的记忆系统小得令人惊讶。

Hermes 将持久记忆存储在 \~/.hermes/memories/ 下的两个文件中：

1). MEMORY.md  
智能体笔记：环境、规范、工具怪癖、教训  
限制：2,200 字符

2). USER.md  
用户画像：偏好、沟通风格、身份信息  
限制：1,375 字符

这容量真不大。加起来大约只有 1,300 个 Token（模型理解文本的最小单位）。

而这正是刻意为之。

在会话开始时，Hermes 加载这两个文件，把它们渲染进提示词区块，然后在整个会话期间固化这个快照。会话中途写入的记忆会立即存入硬盘，但不会改变已经生成的系统提示词。这些改动只有在开启新会话，或者触发了“压缩（Compression）”导致的提示词重建时才会生效。

渲染后的格式如下：

\------

═══════════  
MEMORY (你的个人笔记) \[67% — 1,474/2,200 字符\]  
═══════════  
用户的项目是一个位于 \~/code/myapi 的 Rust Web 服务，使用 Axum + SQLx  
§  
这台机器运行 Ubuntu 22.04，安装了 Docker 和 Podman  
§  
用户喜欢简洁的回复，讨厌冗长的解释

\------

这里有几个我非常欣赏的细节设计：

1\. 使用字符限制而非 Token 限制：这让记忆逻辑与模型无关。Hermes 不需要调用特定模型的计算工具就能判断记忆是否存满。

2\. 简单的分隔符文件格式：条目之间用 § 分隔。没有复杂的向量数据库（Vector DB），没有自定义二进制存储，就是纯文本。

3\. 刻意保持极小的系统提示词空间：这是整个设计的重中之重。Hermes 不想把所有历史都塞进提示词，它只想要最有价值的事实。

4\. 记忆是“精选状态”，而不是“日记”：这是 Hermes 与 OpenClaw 最大的区别。

OpenClaw 的日志更像是“流水账”。而 Hermes 则反其道而行。它的工具架构和测试逻辑强调：  
• 保存用户偏好。  
• 保存环境事实。  
• 保存反复出现的错误修正。  
• 保存稳定的规范。  
• 不保存任务进度。  
• 不保存会话结果。  
• 不保存临时的待办事项（TODO）。

真相是：Hermes 希望 MEMORY.md 和 USER.md 保持精简、高频且对缓存友好。

memory 工具

Hermes 通过一个拥有三种操作的 memory 工具来管理这些文件：add（添加）、replace（替换）、remove（移除）。

一个好用的细节是：replace 和 remove 使用子字符串匹配。你不需要记住条目的内部 ID，只需要传入现有条目中一段唯一的文字即可。

此外，系统会拒绝完全重复的内容，并拦截危险信息。源代码会扫描记忆条目，防止提示词注入（Prompt Injection，即通过输入恶意指令误导 AI）、凭证泄露或隐藏的 Unicode 字符。

第二层：用于情景回溯的 session\_search

如果说 MEMORY.md 是 Hermes 的“短期热记忆”，那么 session\_search 就是它的“长尾回溯系统”。

所有过去的会话都存储在 SQLite 数据库中，拥有完整的索引和搜索功能。当模型需要想起以前聊过的内容时，它不去翻 MEMORY.md，而是搜索这个会话数据库。

其工作流程是：  
1\. 在过去的消息中进行全文搜索。  
2\. 按会话分组结果。  
3\. 加载匹配度最高的会话。  
4\. 使用一个便宜的辅助模型对这些会话进行摘要总结。  
5\. 将精炼后的回顾内容返回给主模型。

这是一种非常务实的设计。它比盲目地把长篇累牍的历史塞进每一个提示词要便宜且高效得多。

第三层：压缩与记忆冲刷（Memory Flush）

Hermes 另一个聪明之处在于它处理长对话“压缩”的方式。

当会话变得太长，Hermes 会压缩对话中间的部分以节省空间。但摘要是有损的，重要事实可能会丢失。

于是，Hermes 会先进行一次“记忆冲刷”。

在压缩之前，它会发送一条指令告诉模型：

&gt; “会话即将压缩，请保存任何值得记住的东西。优先保存用户偏好、修正建议和重复模式，而非具体的任务细节。”

然后它运行一次额外的模型调用，只开启 memory 工具。如果模型觉得有什么东西该留下来，就会在对话被“洗掉”之前把它写入 MEMORY.md。

第四层：作为程序记忆的技能（Skills）

Hermes 不仅能记住事实，还能记住技能。

技能（Skills）存储在 \~/.hermes/skills/ 下。当 Hermes 发现了一个复杂的流程、修复了一个棘手的问题或学会了更好的方法时，它可以将其保存为“技能”。

大多数记忆系统只关注“语义回溯”（名字、偏好、事实），但智能体还需要记住如何做事。

为了效率，Hermes 不会把所有技能都塞进提示词，而是只放一个技能索引，只有在需要时才加载具体的技能内容。

第五层：用于深层建模的 Honcho

最后是可选的 Honcho 层。如果说本地记忆是 Hermes 的笔记本，Honcho 就是它尝试构建的复杂用户模型。它能实现跨设备、跨平台的记忆连续性。

最精妙的是它如何在不破坏提示词缓存的前提下实现集成：  
• 在会话的第一轮，Honcho 的上下文会被织入系统提示词。  
• 在之后的对话中，为了保持提示词稳定，Honcho 的回溯内容会附加在当前用户的提问后面，而不是修改系统提示词。

这确保了缓存依然有效，同时 AI 依然能读到最新的背景信息。

Hermes 与 OpenClaw 的区别

• OpenClaw：记忆更接近“以 Markdown 为中心的存储”，日志和长效文件是主要事实来源。  
• Hermes：提示词记忆被严格限制，历史记录存在 SQLite 里，只有需要时才搜索。

Hermes 更加关注缓存效率。 它认为：不是所有东西都配住在“系统提示词”这个黄金地段。

总结：Hermes 做对了什么？

1\. 冷热分离：小规模提示词记忆负责常驻信息，搜索负责偶尔用到的信息。

2\. 缓存优先：它意识到频繁改动提示词会导致延迟增加和成本上升。

3\. 记忆的多样性：它承认记忆是分层的——包括个人画像、情景回溯、操作技能和深层建模。

Hermes 的核心设计原则最令我折服：记忆应该让智能体变得更好用，而不是通过摧毁提示词的稳定性来换取博闻强识。

真正的诀窍不是记住更多，而是在正确的层级、以正确的成本，记住正确的事情。

#### Hermes Agent 记忆系统拆解：少记但记对

##### 核心观点

Hermes Agent 的记忆系统不是简单地“把所有东西都记下来”，而是采用**分层记忆架构**：

> 高频、稳定、重要的信息放进提示词；  
> 大量历史信息放到数据库里按需搜索；  
> 操作经验沉淀为技能；  
> 深层用户画像交给可选外部系统。

它的核心原则是：**保持提示词稳定，优先利用缓存，降低成本和延迟。**

---

##### 一、Hermes 的上下文设计：为缓存优化

Hermes 发送给模型的上下文大致包括：

1. 默认身份与工具规则  
2. 可选 Honcho 用户建模模块  
3. 固化的 `MEMORY.md` 和 `USER.md`  
4. 技能索引  
5. 项目规则文件  
6. 日期、平台信息  
7. 对话历史与当前用户输入  

关键在于：Hermes 会尽量让系统提示词前半部分保持稳定，从而充分利用大模型的 Prompt Caching。

因此，它不会频繁改动系统提示词，也不会把大量历史都塞进去。

---

##### 二、第一层记忆：极小但高价值的提示词记忆

Hermes 使用两个本地文件保存核心记忆：

- `MEMORY.md`：智能体笔记，如环境、规范、工具问题、经验教训  
- `USER.md`：用户画像，如偏好、沟通风格、身份信息  

它们容量非常小：

- `MEMORY.md`：约 2200 字符
- `USER.md`：约 1375 字符

这说明 Hermes 不追求“记得多”，而是追求“记得准”。

它主要保存：

- 用户偏好
- 稳定环境信息
- 反复出现的问题修正
- 长期有效的规范

它不保存：

- 临时任务进度
- 会话流水账
- 短期待办事项
- 一次性结果

这与 OpenClaw 的“Markdown 流水账式记忆”形成明显区别。

---

##### 三、第二层记忆：SQLite 历史会话搜索

对于大量历史对话，Hermes 不放进提示词，而是存入 SQLite 数据库。

当需要回忆过去内容时，它会：

1. 搜索历史消息  
2. 按会话聚合结果  
3. 找出最相关会话  
4. 用便宜模型生成摘要  
5. 把精炼结果返回给主模型  

这是一种典型的“按需检索”设计。

好处是：

- 不污染当前提示词
- 降低 token 成本
- 提升长期历史可用性
- 保持系统提示词稳定

---

##### 四、第三层记忆：压缩前的 Memory Flush

长对话会被压缩，但压缩可能丢失重要信息。

Hermes 的做法是：在压缩前，先让模型进行一次“记忆冲刷”。

它会提示模型：

> 会话即将压缩，请保存值得长期记住的内容，优先保存用户偏好、修正建议和重复模式，而不是具体任务细节。

然后模型只能调用 memory 工具，把真正重要的信息写入本地记忆。

这让 Hermes 在压缩对话前，尽量保留长期价值信息。

---

##### 五、第四层记忆：Skills 作为程序记忆

Hermes 不只记事实，也记“怎么做”。

它会把复杂流程、问题解决方法、最佳实践保存为 Skills。

Skills 存放在本地目录中，但不会全部塞进提示词，只会在提示词中放一个技能索引。

需要时，再加载具体技能内容。

这相当于一种“程序记忆”：

- 不是记住用户是谁
- 而是记住某类问题该如何解决

对 Agent 来说，这比单纯记事实更接近真正的能力积累。

---

##### 六、第五层记忆：Honcho 深层用户建模

Honcho 是可选的外部记忆层，负责更复杂的用户建模。

它可以实现：

- 跨设备记忆
- 跨平台连续性
- 更深入的用户画像理解

它的巧妙之处在于：不会破坏提示词缓存。

- 第一轮对话：Honcho 信息进入系统提示词
- 后续对话：Honcho 回忆内容附加到用户消息后面

这样既能更新背景信息，又能保持系统提示词稳定。

---

##### Hermes 相比 OpenClaw 的关键进步

OpenClaw 更像是：

> 把 Markdown 文件当作主要记忆来源，倾向于记录大量过程和日志。

Hermes 更像是：

> 把提示词记忆当作稀缺资源，只放最关键的信息；其他内容交给搜索、技能和外部建模系统。

核心差异是：

| 维度 | OpenClaw | Hermes |
|---|---|---|
| 记忆方式 | Markdown 流水账 | 分层记忆 |
| 提示词策略 | 容易膨胀 | 严格控制 |
| 历史信息 | 倾向直接保存 | SQLite 按需搜索 |
| 成本意识 | 较弱 | 强缓存优先 |
| 能力沉淀 | 偏事实记录 | 事实 + 技能 |

---

##### 产品启发

Hermes 的设计对 AI Agent 产品有三点启发：

###### 1. 记忆要冷热分离

不是所有信息都应该进入提示词。

- 高频、稳定信息：进入短记忆
- 低频、历史信息：进入搜索系统
- 操作流程：进入技能系统

###### 2. 记忆要服务成本结构

频繁修改系统提示词会破坏缓存，增加成本和延迟。

好的记忆系统必须同时考虑：

- 智能表现
- 响应速度
- 推理成本
- 上下文稳定性

###### 3. 记忆不是越多越好

真正重要的不是“记住一切”，而是：

> 在正确的层级，以正确的成本，记住正确的事情。

---

#### 一句话总结

Hermes Agent 的记忆系统做对的地方在于：它没有把记忆当成无限仓库，而是把记忆设计成一套分层、克制、缓存友好的产品架构。

## 高价值（1）

### 2026-05-03 02:06:20

#### 高价值信息提取

##### 1. 一句话判断

> 最值得保留的是：**Agent 记忆系统的关键不是“记住更多”，而是把不同价值、频率、成本的信息放到不同记忆层级里，并优先维护提示词稳定性。**

**价值评级：S**

**精炼理由：**  
这篇文章真正有价值的地方，不是介绍 Hermes 有哪些文件和工具，而是揭示了一个可迁移的系统设计原则：**记忆是成本结构问题，不是存储容量问题。**  
对 AI Agent、知识管理、产品设计、组织协作乃至个人笔记系统都有启发。

---

##### 2. 最重要的洞见

###### 洞见 1：记忆系统的核心矛盾，不是遗忘，而是“什么信息有资格进入黄金上下文”

###### **核心观点：**  
> 系统提示词不是仓库，而是黄金地段；真正高级的记忆系统会严格限制常驻信息，只保留高频、稳定、可复用的事实。

**为什么重要：**  
很多 Agent 记忆设计的直觉是：把更多历史、更多偏好、更多任务结果塞进上下文，模型就会更聪明。Hermes 的判断正相反：上下文越“臃肿”，越破坏缓存、增加成本、降低稳定性。

它把记忆分成两类：

- **常驻记忆**：用户偏好、环境事实、稳定规范、重复性错误修正。
- **按需记忆**：旧会话、任务过程、历史细节、偶发上下文。

这意味着，记忆的核心不是“长期保存”，而是**决定哪些信息值得每次都被模型看见**。

**反常识之处：**  
常见认知是：记忆越多，Agent 越智能。  
Hermes 的判断是：**常驻记忆越少、越精，Agent 反而越可靠。**

**可迁移价值：**  
这不只适用于 AI：

- 产品首页不是功能仓库，而是高频入口。
- 组织制度不是所有经验的集合，而是最稳定规则的压缩。
- 个人笔记不是日记越多越好，而是要沉淀可复用判断。
- 管理仪表盘不是指标越全越好，而是只放决策必需指标。

**我应该记住什么：**  
> 不要问“这个信息要不要保存”，而要问：**它是否值得长期占据注意力和系统前缀？**

---

###### 洞见 2：真正高级的 Agent 记忆是“冷热分层”，不是统一数据库

###### **核心观点：**  
> Hermes 不是一套记忆系统，而是四套不同成本、不同用途的记忆层：提示词记忆、会话搜索、技能记忆、用户建模。

文章中最关键的结构是：

| 层级 | 承载内容 | 作用 | 成本策略 |
|---|---|---|---|
| MEMORY.md / USER.md | 高频事实、偏好、规范 | 常驻注入 | 极小、稳定 |
| SQLite session_search | 历史会话、旧上下文 | 按需回溯 | 搜索后摘要 |
| Skills | 操作流程、解决方案 | 程序性记忆 | 只加载索引 |
| Honcho | 深层用户模型 | 跨平台连续性 | 避免破坏缓存 |

**为什么重要：**  
它把“记忆”拆成了不同类型：

- **语义记忆**：用户是谁、偏好什么。
- **情景记忆**：过去发生过什么。
- **程序记忆**：某件事该怎么做。
- **用户模型**：长期行为模式和跨场景理解。

很多系统失败，是因为把这些不同性质的东西混在一个地方：要么全塞进 Prompt，要么全进向量库，要么全写 Markdown。

Hermes 的优势在于：**不同记忆进入不同通道，不同通道承担不同成本。**

**反常识之处：**  
常见做法是做一个“统一记忆库”。  
Hermes 的判断是：**记忆不该统一，应该分层。统一存储容易，统一调用很蠢。**

**可迁移价值：**  
这可迁移到几乎所有信息系统：

- 公司知识库：制度、项目记录、SOP、客户画像不该混在一个库里。
- 个人知识管理：长期原则、日常日志、技能模板、关系档案应分层。
- 产品设计：高频入口、历史记录、专家功能、个性化推荐应分层加载。
- 技术架构：缓存、数据库、搜索索引、模型推理上下文不该互相替代。

**我应该记住什么：**  
> 好系统不是“一个地方放所有东西”，而是**让每类信息在最合适的层级，以最低必要成本被调用。**

---

###### 洞见 3：提示词缓存正在反过来塑造 Agent 架构

###### **核心观点：**  
> Hermes 的记忆设计不是单纯为了“像人一样记事”，而是为了让系统提示词前缀尽量稳定，从而利用大模型供应商的 Prompt Caching。

这是文章里最容易被轻描淡写带过、但实际极其重要的点。

Hermes 的系统提示词结构中，稳定部分尽量放前面：

1. 默认身份  
2. 工具指南  
3. 可选集成模块  
4. MEMORY / USER 快照  
5. 技能索引  
6. 上下文规则文件  
7. 日期、平台信息  
8. 对话历史  
9. 当前用户消息  

这个顺序不是随便排的，而是为了让**稳定前缀尽可能长时间不变**。  
一旦系统提示词频繁变化，缓存命中率下降，延迟和成本都会上升。

**为什么重要：**  
这说明 Agent 设计已经进入一个新阶段：  
架构不只由“模型能力”决定，也由**模型 API 的计费机制、缓存机制、上下文构造方式**决定。

谁能设计出更稳定、更便宜、更可控的上下文，谁就能做出更可规模化的 Agent。

**反常识之处：**  
很多人以为 Prompt 是表达问题的文本。  
Hermes 实际上把 Prompt 当成一种**可优化的系统资源**：有缓存、有热区、有冷区、有失效成本。

**可迁移价值：**  
这类似于软件系统里的缓存友好设计：

- 不频繁改动核心配置。
- 把动态数据放到后面或按需加载。
- 把高频稳定内容放入缓存层。
- 避免让低价值变化污染高价值前缀。

**我应该记住什么：**  
> 在 Agent 系统里，Prompt 不是一次性文本，而是昂贵、可缓存、需要架构设计的运行时资产。

---

###### 洞见 4：压缩前的“记忆冲刷”是一个关键补偿机制

###### **核心观点：**  
> 长对话压缩不可避免会丢失信息，所以 Hermes 在压缩前主动让模型提取值得长期保留的内容，再把它写入记忆。

这个设计很妙。

长上下文对话一旦太长，就需要压缩中间内容。但摘要是有损的，很多重要事实会被抹掉。Hermes 没有假装压缩不会损失，而是加入一个“冲刷”动作：

> 会话即将压缩，请保存任何值得记住的东西。优先保存用户偏好、修正建议和重复模式，而非具体任务细节。

然后只开放 memory 工具，让模型决定是否保存。

**为什么重要：**  
这是一个很成熟的系统判断：  
它承认信息处理链路中存在损耗，并在损耗发生前设计“提纯动作”。

不是等信息丢了再补救，而是在丢失前做价值筛选。

**反常识之处：**  
很多系统把“压缩”当作纯技术动作。  
Hermes 把压缩视为一次**记忆沉淀机会**。

**可迁移价值：**  
这个机制非常适合迁移到其他场景：

- 项目复盘：项目结束前，不是简单归档，而是提取可复用原则。
- 会议纪要：不是记录全部内容，而是在结束前确认“以后还会用到什么”。
- 个人日记：不是保存每天细节，而是周期性冲刷出规律、偏好、教训。
- 组织知识：在人员流动或项目关闭前，做一次经验抽取。

**我应该记住什么：**  
> 每次压缩、归档、结束、交接之前，都应该有一次“价值冲刷”。

---

###### 洞见 5：技能记忆比事实记忆更接近 Agent 的长期能力

###### **核心观点：**  
> Agent 不只需要记住“用户说过什么”，更需要记住“以后遇到类似问题应该怎么做”。

Hermes 的 Skills 设计很关键。  
大多数记忆系统关注的是语义事实：用户名字、偏好、项目路径、历史对话。  
但真正能提升 Agent 能力的，往往是程序性记忆：

- 某类 Bug 如何排查。
- 某个复杂流程如何执行。
- 某个工具有什么坑。
- 某类项目应该按什么步骤推进。

Hermes 不把所有技能内容塞进 Prompt，只放技能索引，需要时再加载具体技能。

**为什么重要：**  
这代表 Agent 从“会回忆”走向“会积累方法”。  
事实记忆让 Agent 更懂你，技能记忆让 Agent 真的变强。

**反常识之处：**  
很多人把 AI 记忆理解成“用户画像”和“历史聊天”。  
但对工作型 Agent 来说，更有价值的记忆可能是：**经过验证的操作流程。**

**可迁移价值：**  
对个人和组织也一样：

- 只保存结果，不保存方法，下次还会重来。
- 只记住客户偏好，不沉淀交付流程，团队不会进化。
- 只保留聊天记录，不提炼 SOP，知识无法复用。

**我应该记住什么：**  
> 真正的成长不是记住更多事实，而是把重复成功或失败沉淀成可复用技能。

##### 3. 底层逻辑

###### **逻辑一：上下文是稀缺资源，不是无限容器**

- **表层现象：**  
  Hermes 将 MEMORY.md 和 USER.md 限制得很小，总计约 1,300 Token，并且会话中途写入的记忆不会立刻改变系统提示词。

- **深层原因：**  
  系统提示词越稳定，越能利用 Prompt Caching；越频繁变化，越增加成本、延迟和不确定性。

- **推导结论：**  
  Agent 记忆设计的第一原则不是“最大化可记忆内容”，而是**最大化单位上下文价值**。

---

###### **逻辑二：不同记忆的调用频率不同，所以应该进入不同层级**

- **表层现象：**  
  Hermes 同时使用小型提示词记忆、SQLite 会话搜索、技能索引、Honcho 用户模型。

- **深层原因：**  
  信息有冷热之分：  
  高频稳定信息值得常驻；低频历史信息适合搜索；操作流程适合技能化；深层用户理解适合外部模型层。

- **推导结论：**  
  记忆系统要按“使用频率 × 稳定性 × 调用成本 × 复用价值”分层，而不是按存储格式统一管理。

---

###### **逻辑三：记忆不是记录历史，而是保留未来会再次创造价值的压缩状态**

- **表层现象：**  
  Hermes 明确不保存任务进度、会话结果、临时 TODO，却保存用户偏好、环境事实、规范、重复错误修正。

- **深层原因：**  
  历史本身没有价值，能影响未来判断和行动的模式才有价值。  
  如果一条信息只对当前任务有用，它不应污染长期记忆。

- **推导结论：**  
  好记忆不是“完整记录过去”，而是**为未来决策保留高信噪比状态**。

## 结构化（1）

### 2026-05-03 02:09:13

##### 主旨概括

文章深度拆解了开源 AI Agent「Hermes」的记忆系统，指出它并不是单一记忆机制，而是由多层记忆组成。其核心设计思想是：**保持系统提示词稳定以利用缓存，把大而杂的历史信息交给工具按需检索**。

---

##### 1. Hermes 的整体记忆架构：不是一套，而是四套

Hermes 的记忆系统主要由四部分组成：

1. **提示词记忆**  
   存储在 `MEMORY.md` 和 `USER.md` 中，内容高度浓缩。

2. **历史会话搜索**  
   通过 `session_search` 检索 SQLite 中的历史对话。

3. **技能记忆**  
   类似“程序记忆”，用于保存复杂流程、解决方案和操作经验。

4. **Honcho 用户建模层**  
   可选模块，用于更深层的用户画像和跨设备记忆连续性。

作者认为，Hermes 的核心逻辑是：  
**少量高价值信息进入提示词，大量低频信息通过工具按需调用。**

---

##### 2. Hermes 的上下文结构：为提示词缓存而设计

Hermes 给模型发送的系统提示词大致按以下顺序组装：

1. 默认智能体身份  
2. 工具使用指南  
3. 可选 Honcho 集成模块  
4. 可选系统消息  
5. 固化的 `MEMORY.md` 快照  
6. 固化的 `USER.md` 快照  
7. 技能索引  
8. 上下文规则文件，如 `AGENTS.md`、`SOUL.md`  
9. 日期、时间和平台信息  
10. 对话历史  
11. 当前用户消息  

这个结构的重点是：**尽量让系统提示词前缀保持稳定**，从而利用大模型供应商的 Prompt Caching，降低成本和延迟。

因此，Hermes 会把常用且稳定的信息压缩后放进提示词；而历史旧账、大量背景和偶尔才用的信息，则放到外部系统中检索。

---

##### 3. 第一层记忆：极小但高价值的提示词记忆

Hermes 把持久记忆存储在本地目录：

```text
~/.hermes/memories/
```

其中有两个核心文件：

###### `MEMORY.md`

用于保存智能体笔记，例如：

- 环境信息
- 工具使用习惯
- 项目规范
- 反复出现的问题和教训

限制为 **2,200 字符**。

###### `USER.md`

用于保存用户画像，例如：

- 用户偏好
- 沟通风格
- 身份信息

限制为 **1,375 字符**。

两者合计大约只有 **1,300 个 Token**，容量非常小，但这是刻意设计的。

---

##### 4. 提示词记忆的特点：精选状态，而不是流水账

Hermes 的记忆不是记录所有事情，而是只保存长期有用的信息。

它倾向于保存：

- 用户偏好
- 环境事实
- 反复出现的错误修正
- 稳定规范
- 高频有用信息

它不会保存：

- 普通任务进度
- 会话结果
- 临时 TODO
- 一次性细节

例如，它可能保存：

```text
用户的项目是位于 ~/code/myapi 的 Rust Web 服务，使用 Axum + SQLx
§
这台机器运行 Ubuntu 22.04，安装了 Docker 和 Podman
§
用户喜欢简洁回复，讨厌冗长解释
```

作者认为，这是 Hermes 与 OpenClaw 的关键区别：  
**OpenClaw 更像 Markdown 流水账，而 Hermes 更像精挑细选的长期记忆。**

---

##### 5. memory 工具：简单、可控且防风险

Hermes 通过 `memory` 工具管理记忆，支持三种操作：

- `add`：添加记忆
- `replace`：替换记忆
- `remove`：删除记忆

一个实用设计是：  
`replace` 和 `remove` 使用**子字符串匹配**，不需要记住内部 ID，只要提供记忆中一段唯一文字即可。

同时，Hermes 会做安全检查：

- 拒绝完全重复的内容
- 拦截提示词注入
- 防止凭证泄露
- 检查隐藏 Unicode 字符

这让记忆系统既简单，又避免被恶意内容污染。

---

##### 6. 第二层记忆：用 `session_search` 回溯历史会话

如果说 `MEMORY.md` 和 `USER.md` 是“热记忆”，那么 `session_search` 就是“长尾历史回溯”。

Hermes 会把所有历史会话存储在 **SQLite 数据库** 中，并支持搜索。

工作流程是：

1. 对过去消息进行全文搜索  
2. 按会话分组结果  
3. 加载匹配度最高的会话  
4. 用便宜的辅助模型总结这些会话  
5. 把精炼后的回顾内容返回给主模型  

这种方式比把所有历史对话都塞进提示词更便宜、更高效。

---

##### 7. 第三层机制：压缩前的“记忆冲刷”

当会话过长时，Hermes 会对中间部分进行压缩，以节省上下文空间。

但压缩是有损的，重要信息可能被丢掉。  
所以 Hermes 会在压缩前触发一次“记忆冲刷”。

它会告诉模型：

> 会话即将压缩，请保存任何值得记住的东西。优先保存用户偏好、修正建议和重复模式，而不是具体任务细节。

然后 Hermes 会额外调用一次模型，并只开放 `memory` 工具。  
如果模型发现有长期价值的信息，就会在压缩前写入 `MEMORY.md`。

这一设计保证了：  
**短期对话可以被压缩，但长期有价值的信息不会轻易丢失。**

---

##### 8. 第四层记忆：作为“程序记忆”的 Skills

Hermes 不只记住事实，也能记住“怎么做事”。

技能存储在：

```text
~/.hermes/skills/
```

适合保存：

- 复杂操作流程
- 棘手问题的修复方法
- 更优的工作方法
- 重复使用的任务步骤

为了节省提示词空间，Hermes 不会把所有技能内容都塞进系统提示词，而是只放一个**技能索引**。  
当需要某个技能时，再按需加载具体内容。

这让 Hermes 具备类似“程序记忆”的能力。

---

##### 9. 第五层记忆：Honcho 深层用户建模

Honcho 是可选模块，用于构建更复杂的用户模型，并支持：

- 跨设备记忆
- 跨平台连续性
- 更深入的用户画像

它的集成方式也服务于缓存稳定性：

- 第一轮对话：Honcho 上下文写入系统提示词
- 后续对话：Honcho 回溯内容附加到当前用户消息后，而不是修改系统提示词

这样既能让模型获得最新背景，又不会频繁破坏 Prompt Caching。

---

##### 10. Hermes 与 OpenClaw 的核心区别

文章认为，Hermes 修正了 OpenClaw 的一个误区。

###### OpenClaw

- 更依赖 Markdown 文件
- 日志和长效文件是主要事实来源
- 记忆更像流水账

###### Hermes

- 严格限制提示词记忆大小
- 历史会话存 SQLite
- 需要时才搜索历史
- 更重视缓存效率和提示词稳定性

作者总结为一句话：

> 不是所有东西都配住在“系统提示词”这个黄金地段。

---

##### 11. Hermes 做对了什么

文章最后总结了 Hermes 的三大优点：

###### 1. 冷热分离

高频、稳定、重要的信息进入小型提示词记忆；  
低频、大量、历史性的内容通过搜索工具调用。

###### 2. 缓存优先

Hermes 明白频繁改动系统提示词会导致：

- 缓存失效
- 延迟增加
- 成本上升

所以它尽量保持提示词稳定。

###### 3. 多层记忆设计

Hermes 承认 AI Agent 的记忆不是单一形态，而是包括：

- 用户画像
- 环境事实
- 历史会话回溯
- 操作技能
- 深层用户建模

---

##### 总结

Hermes 的记忆系统最重要的启发是：**AI Agent 不应该盲目记住更多，而应该在正确的位置、以合理成本，记住真正有用的东西。**

它通过小型提示词记忆、SQLite 历史搜索、技能系统和 Honcho 用户建模，实现了一个更高效、更稳定、更适合长期使用的智能体记忆架构。
