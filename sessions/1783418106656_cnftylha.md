## 正文

17 min read

![](https://cf-assets.www.cloudflare.com/zkvhlag99gkb/3CeobeovHxD6ZsSYvoMMJg/9c1f16ff9b7dc4ffd4f780e0ac7e986a/BLOG-3262_image4.png)

Today we are launching **Workers Cache**: a [tiered cache](https://developers.cloudflare.com/cache/how-to/tiered-cache/) that sits in front of your Worker, configured by a single line of Wrangler config and the same `Cache-Control` headers you already know.

When Workers Cache is enabled, every [cacheable](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.3) request to your Worker hits Cloudflare's cache first. If there's a fresh cached response, Cloudflare returns it directly — your Worker doesn't run, and you don't pay CPU time for it. On a miss, your Worker runs, and if your response is cacheable, Cloudflare stores it for the next request. The next request from anywhere on Earth can be served straight from cache.

![BLOG-3262 image1](https://cf-assets.www.cloudflare.com/zkvhlag99gkb/2Xyk1rkPl9p44y48mdoPk/2178d252281c0165e03e7cb9245a4c3a/BLOG-3262_image1.png)

The whole thing is one config block:

```
{
  "name": "my-worker",
  "main": "src/index.ts",
  "compatibility_date": "2026-05-01",
  "cache": {
    "enabled": true
  }
}
```

After that, you control caching the way HTTP has always wanted you to — by setting headers on your responses:

```
return new Response(body, {
  headers: {
    "Cache-Control": "public, max-age=300, stale-while-revalidate=3600",
    "Cache-Tag": "products,product:123",
  },
});
```

And when content changes, your Worker purges its own cache:

```
await ctx.cache.purge({ tags: ["product:123"] });
```

That's the whole API. There is no zone to configure, no rules engine to set up, no separate cache to provision, and no second product to log into. The Worker's code is the configuration surface, and the cache follows the Worker wherever it runs — on a custom domain, on `workers.dev`, behind a service binding, in a preview, in a [Workers for Platforms](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/) tenant. One Worker, one cache, configured once.

That's the surface area. There’s a lot underneath: tiered caching across our entire network, full support for [`stale-while-revalidate`](https://developers.cloudflare.com/changelog/post/2026-02-26-async-stale-while-revalidate/) so stale responses never block a user, content negotiation via [`Vary`](https://developers.cloudflare.com/workers/cache/#content-negotiation-with-vary), multi-tenant-safe cache keys via [`ctx.props`](https://developers.cloudflare.com/workers/runtime-apis/context/#props), programmatic purges by tag or path prefix, and — the part we think is the biggest unlock — a cache that sits in front of every Worker entrypoint, not just the public one, with per-entrypoint control over which ones cache and which don't. That last piece means you can compose caching directly into the structure of your app: a chain of entrypoints with cache stages slotted in wherever you want them, configured by the code on either side. We'll walk through all of it below.

Workers Cache is available today to every Worker on any plan, enabled in Wrangler.

This is the caching API we've always wanted Workers to have. Here's why it took us this long, what becomes possible because of it, and what's coming next.

#### Why server-rendered apps need a cache in front

When we [introduced Workers in 2017](https://blog.cloudflare.com/introducing-cloudflare-workers/), the pitch was that you could run code on Cloudflare's network to transform requests on their way to your origin. The Worker sat *in front of* the cache and the origin:

![BLOG-3262 image5](https://cf-assets.www.cloudflare.com/zkvhlag99gkb/1MoDb2Es6lrS9KoNqnakGF/1b67e2672e892c6313c186e3b9c708af/BLOG-3262_image5.png)

This was the right model for the use cases we were targeting. If you wanted to add a header to every request, rewrite a URL, do an A/B split, or filter traffic before it reached your origin, putting the Worker in front of the cache and the origin gave you full control over what got cached and what didn't. Customers built incredible things with it.

But the world changed. Workers stopped being a thing you bolted onto an origin and started being *the* origin. Frameworks like [Astro](https://developers.cloudflare.com/workers/framework-guides/web-apps/astro/), [TanStack Start](https://developers.cloudflare.com/workers/framework-guides/web-apps/tanstack-start/), [Next.js](https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/), [Remix](https://developers.cloudflare.com/workers/framework-guides/web-apps/remix/), and [SvelteKit](https://developers.cloudflare.com/workers/framework-guides/web-apps/svelte/) all ship a Cloudflare adapter that builds your app as a Worker. There's no origin behind them. The Worker *is* the server.

When the Worker is the origin, the original architecture has nothing to cache. Every request runs your code, even when the response would be byte-for-byte identical to the one you returned a second ago. The [Workers runtime is fast enough that this works](https://x.com/KentonVarda/status/1783996343813652801) — it routinely handles tens of millions of requests per second without breaking a sweat — but "fast enough to render every request" still costs you latency on every page load and CPU time on every invocation. And on a server-rendered app, every page load is, by definition, a render.

Workers Cache flips the architecture. Cloudflare's cache now sits in front of the Worker:

![BLOG-3262 image9](https://cf-assets.www.cloudflare.com/zkvhlag99gkb/19tIUZXwZR2RQKIsT39JBR/1587def81b84c1d0b5f9bee005b3c88f/BLOG-3262_image9.png)

On a cache hit, your Worker doesn't run at all. Cloudflare returns the cached response and your CPU billing stays at zero. On a miss, your Worker runs once, populates the cache, and the next request — from anywhere — gets served from cache without invoking your code.

This is what was missing for server-side rendering on Workers. You used to have to choose between two unsatisfying options:

- **Prerender everything at build time** ("static site generation"). Fast page loads, but every change requires a full rebuild and redeploy. For a docs site with a few thousand pages, that's 5–10 minutes. For a large e-commerce site, it's worse — and the build runs every single time you touch anything.
- **Render every page on every request.** Up-to-date content, but every page load pays the rendering cost and every visitor pays the latency.

Workers Cache gives you a third option: server-render on demand, cache the rendered response, refresh it on a time-to-live ([TTL](https://developers.cloudflare.com/cache/how-to/edge-browser-cache-ttl/)) you choose. The first request to a new page still renders. Every subsequent request, until the cache expires, is served as if the page were static. When the cache expires, the next request triggers a re-render — and with `stale-while-revalidate`, even that one doesn't wait.

You get the speed of a static site without the build time, and the freshness of server rendering without the cost. No framework-specific machinery like Incremental Static Regeneration. Just HTTP caching, working the way it was designed to work, in front of code that was designed to be the origin.

#### `stale-while-revalidate` is the part that makes it feel instant

The [`stale-while-revalidate`](https://datatracker.ietf.org/doc/html/rfc5861#section-3) directive tells Cloudflare that when a cached response expires, it's allowed to serve the stale copy immediately *while it refreshes the response in the background*. Cloudflare [shipped full support for `stale-while-revalidate` earlier this year](https://developers.cloudflare.com/changelog/post/2026-02-26-async-stale-while-revalidate/), and it's the directive that turns "we cache your Worker" into "your Worker's site feels static."

Without it, the first request after a cache entry expires has to wait for the Worker to render the page from scratch. The user sees that latency. With it, the first request after expiration gets the stale page immediately (with a `Cf-Cache-Status: UPDATING` header), and the Worker runs in the background to refill the cache. Every user, including the one who triggered the refresh, gets a cache-speed response.

![BLOG-3262 image3](https://cf-assets.www.cloudflare.com/zkvhlag99gkb/5xWY9m7E5NKrcecXkJXNpi/2a9fc007577d0131c5e9efabc00bd24e/BLOG-3262_image3.png)

In practice, this looks like:

```
 export default {
  async fetch(request) {
    const html = await renderPage(request);
    return new Response(html, {
      headers: {
        "Content-Type": "text/html; charset=utf-8",
        // Treat as fresh for 5 minutes; serve stale for up to an hour
        // while a background refresh runs.
        "Cache-Control": "public, max-age=300, stale-while-revalidate=3600",
      },
    });
  },
};
```

The mental model that makes this click:

- **Fresh window** (`max-age`): Cloudflare serves the cached response. Your Worker doesn't run.
- **Stale window** (`stale-while-revalidate`): Cloudflare serves the cached response. Your Worker runs in the background to refresh it. No user waits.
- **Outside both windows**: Cloudflare runs your Worker to generate a fresh response, and the user waits for that one render.

You pick the windows. For a product catalog that updates every few minutes, `max-age=300`, `stale-while-revalidate=3600` means visitors basically never wait, and your Worker still runs often enough to keep content fresh. For a blog archive that almost never changes, `max-age=86400`, `stale-while-revalidate=2592000` means your Worker runs once a day per page.

The first request to a brand-new page is the only one that pays the full render cost. After that, the page behaves like static output for visitors, while your Worker still owns how the page gets generated.

#### One URL, many representations: `Vary` works

Real apps rarely return the same bytes to every client. The same product page might be HTML for a browser and JSON for an API client. The same image might be WebP for clients that support it and JPEG for the ones that don't. The same homepage might come back in English, French, or Japanese depending on the user.

Doing this without a cache is easy — your Worker just reads the request header and returns the right thing. Doing it *with* a cache is where it usually gets ugly. Most caches give you two bad options: cache nothing on URLs that have multiple representations, or cache one representation and serve it to everyone.

Workers Cache supports the standard HTTP `Vary` header, which is the right way to solve this. When your Worker returns a response with `Vary: Accept-Encoding` (or `Accept`, or `Accept-Language`, or any other request header), Cloudflare stores a separate cached variant per distinct combination of those headers — and only returns a variant whose stored values match the incoming request.

```
export default {
  async fetch(request) {
    const accept = request.headers.get("Accept") ?? "";
    const wantsWebp = accept.includes("image/webp");

    const body = wantsWebp ? await fetchWebpImage() : await fetchJpegImage();

    return new Response(body, {
      headers: {
        "Content-Type": wantsWebp ? "image/webp" : "image/jpeg",
        "Cache-Control": "public, max-age=3600",
        // Cache a separate variant per distinct Accept header value.
        Vary: "Accept",
      },
    });
  },
};
```

One URL, two cached variants. A browser that sends `Accept: image/webp,*/*` gets the WebP. A browser that sends `Accept: image/jpeg` gets the JPEG. Both come from cache. Your Worker writes both variants on the first request to each, and then runs zero times for either after that.

This is the well-trodden HTTP standard for content negotiation, and Workers Cache implements it the way [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#name-vary) and [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html#name-calculating-cache-keys-with) describe. There's no allowlist of what headers you can `Vary` on. You list whatever you need, and Cloudflare keys variants on the verbatim values. The docs go through the [edge cases](https://developers.cloudflare.com/workers/cache/configuration/#vary) — how to keep variant fan-out under control by normalizing headers in a gateway Worker, why purges invalidate all variants of a URL together, and the one case (`Vary: *`) that disables caching entirely.

#### This is your Worker's cache, not your zone's

Before we get to what becomes possible with all this, there's a conceptual shift worth naming.

Cloudflare has had a cache forever. It's configured at the zone level: Cache Rules, Page Rules, the cached-file-extensions list, Cache Reserve, Tiered Cache topology, custom cache keys. All of it is set per zone, and historically a Worker had to either fit into that zone's configuration or work around it.

Workers Cache is different. It's **your Worker's cache** — it belongs to the Worker, not to a zone. This has a bunch of consequences that turn out to matter:

- **There is no zone configuration to manage.** Cache Rules, cache level settings, the file-extensions list, Page Rules — none of them apply to Workers Cache. The Worker's `Cache-Control` headers are the configuration.
- **The cache follows the Worker, not the hostname.** A Worker that's bound to `api.example.com`, `api.example.net`, and invoked over a service binding shares one cache across all three. A request to `/users/42` hits the same cached entry regardless of which way in it came.
- **The cache works on** `**workers.dev**`**.** It works in [preview URLs](https://developers.cloudflare.com/workers/configuration/previews/) (each preview gets its own cache, so testing a change doesn't poison production). It works in [Workers for Platforms](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/) (each user Worker has its own cache, isolated from the dispatcher and from other tenants). All of these used to be second-class citizens for caching. They aren't anymore.
- **Purges are scoped to the Worker’s entrypoint.** When you call `ctx.cache.purge({ purgeEverything: true })`, you're only purging your Worker entrypoint's cache. No risk of nuking your zone's other content. No risk of one Worker's deploy invalidating another's data.

What you configure about caching, you configure in code: which paths get longer TTLs (branch on the path and set a different `max-age`), which requests bypass the cache (return `Cache-Control: private`), how the cache key is shaped (control what gets into `ctx.props`, normalize the URL in a gateway Worker before dispatching). The Worker you already wrote is the configuration surface.

The full docs go deep on this in [Workers Cache: your Worker's cache](https://developers.cloudflare.com/workers/cache/).

#### Two tiers, every Worker, no configuration

Workers Cache is **regionally tiered by default**. There are two layers:

- **A lower tier** in the Cloudflare data center closest to the user. Every data center that receives traffic for your Worker has its own lower-tier cache.
- **An upper tier** that aggregates fills across the whole network. There are fewer of these, and every lower tier consults the upper tier on a miss.

A request hits the lower tier first. On a hit, the response is served and that's the end of it. On a miss, the lower tier asks the upper tier. On a hit there, the response is returned and also stored in the lower tier on the way back. Only if both tiers miss does your Worker actually run — and the response from that run gets stored in both tiers.

![BLOG-3262 image2](https://cf-assets.www.cloudflare.com/zkvhlag99gkb/Qn6sTGmQebZz5fQZKo5us/37c11406ad6844a5131d78f628acd2f0/BLOG-3262_image2.png)

The reason this matters is that the **first request anywhere in the world** populates the upper tier. Every subsequent request, from any data center, can be served from the upper tier without your Worker running — even if the lower tier at that data center has never seen the request before. Cache hit ratios are dramatically higher than they would be with a single flat cache layer, which is exactly what you want when your Worker is the origin.

This is the same topology that powers [Tiered Cache](https://developers.cloudflare.com/cache/how-to/tiered-cache/) for zones today, except you don't configure it. There is no dialog for "turn on tiered cache for my Worker." Every Worker that has caching enabled gets tiering for free.

If your Worker uses [Smart Placement](https://developers.cloudflare.com/workers/configuration/placement/), the cache composes cleanly with it: tiers are consulted first, and only if both miss does Smart Placement route execution close to your origin. We have more to say about how those layers interact, including a few rough edges we're [planning to smooth out](https://developers.cloudflare.com/workers/cache/#smart-placement-and-the-cache), in the docs.

#### Run your app near the user *and* near the data

There's a recurring tension in web performance that nobody has fully resolved: you want your code to run close to the user (because the round-trip between user and server is on the critical path), and you want your code to run close to the data (because every database query is also a round-trip). Pick one, and the other gets slow.

We've spent years chasing both. Our network puts us [within \~50ms](https://www.cloudflare.com/network/) of about 95% of the world's Internet users. [Smart Placement](https://blog.cloudflare.com/announcing-workers-smart-placement/) and [Placement Hints](https://developers.cloudflare.com/changelog/post/2026-01-22-explicit-placement-hints/) let you keep your code close to your data without ever having to think about cloud regions. But until now, the two pieces didn't fully compose. You could do "near the user" or "near the data," and if you wanted both halves of your app to be in the right place at the same time, you had to be a Cloudflare expert. [We knew we could do better.](https://sunilpai.dev/posts/spatial-compute/)

Workers Cache is the piece that closes the gap. Because the cache belongs to the Worker (not the zone), and because [service bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/) and [`ctx.exports`](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/rpc/) calls between Workers go through the cache, you can build an app as a chain of Workers — each one running where it should run — with the cache as the seam between them.

The architecture looks like this:

![BLOG-3262 image8](https://cf-assets.www.cloudflare.com/zkvhlag99gkb/5vOhRNLQF3RWl2u6gTdpWm/60ee01a9b099357564769de3b9354d3b/BLOG-3262_image8.png)

- **Worker A** runs near the user. It handles the cheap, latency-sensitive parts of every request: authentication, rate limiting, routing, header normalization, rendering the [outer "shell"](https://developers.cloudflare.com/workers/examples/spa-shell/) of an HTML page that doesn't depend on data.
- **Worker B** runs near the data, courtesy of Smart Placement or an explicit Placement Hint. It does the heavy work: server-rendering pages that fetch data, reading product catalogs, generating search results, aggregating APIs, expensive transforms.
- **Workers Cache sits in front of Worker B.** When Worker A calls Worker B over a service binding, Cloudflare checks Worker B's cache first. On a hit, Worker A receives the response and Worker B doesn't run at all — no data-center hop, no database query, no rendering work.

The cache hit path becomes: user → Worker A near the user → cache hit for Worker B → response. The data hop is paid only on a miss. Your hot pages run at the speed of code-in-front-of-the-user, and your cold pages still benefit from running near the data when they do execute.

You don't have to architect anything special to get this. Write your app as two Workers, point one at the other with a service binding, turn caching on in Worker B’s `wrangler.jsonc` file, and you're done.

![BLOG-3262 image7](https://cf-assets.www.cloudflare.com/zkvhlag99gkb/4Xh7r02F9CCFAbrMuuRRpn/901c4c1cf8d24f515485e3810fa9aa4d/BLOG-3262_image7.png)

#### Multi-tenant by default, with `ctx.props`

If you're caching a Worker that returns user-specific data — say, an API that serves different content per logged-in user — you need a way to make sure one user can never see another user's cached response. The standard solution is "don't cache authenticated requests," and Cloudflare's [automatic bypass](https://developers.cloudflare.com/cache/concepts/cache-responses/#bypass) for Authorization headers does exactly that. But "don't cache anything" gives up the entire performance win.

Workers Cache solves this by making the caller's [`ctx.props`](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/rpc/#ctxprops) part of the cache key. When one Worker calls another over a service binding and passes `ctx.props` with a user ID, tenant ID, or any other identifier, callers with different props get separate cache entries. One user's response can never leak into another user's cache.

```
import { WorkerEntrypoint } from "cloudflare:workers";

interface Props { userId: string; }

export default class Backend extends WorkerEntrypoint<Env, Props> {
  async fetch(request: Request): Promise<Response> {
    // ctx.props.userId is part of the cache key. User A and User B
    // requesting the same URL get separate cached entries.
    const { userId } = this.ctx.props;
    const data = await loadUserData(userId);

    return new Response(JSON.stringify(data), {
      headers: {
        "Content-Type": "application/json",
        "Cache-Control": "public, max-age=300",
      },
    });
  }
}
```

The typical pattern is to authenticate the request in a gateway Worker, strip the `Authorization` header, set the authenticated user's ID into `ctx.props`, and then call the cached backend Worker. The gateway runs on every request (it has to, to authenticate), but the expensive backend only runs when there's no cache entry for that user yet. Auth'd APIs go from "uncacheable" to "cached per user with full safety," and the cache key does the isolation for you. The docs walk through this in detail in [Multi-tenant safety with ctx.props](https://developers.cloudflare.com/workers/cache/cache-keys/#multi-tenant-safety-with-ctxprops) and the example in [Per-user authenticated responses](https://developers.cloudflare.com/workers/cache/examples/#per-user-authenticated-responses).

Other CDNs make you choose between correctness and hit ratio: key the cache by each user’s token, or send every request back to origin for authorization. Workers Cache lets you share cached API responses at the edge while preserving per-request authorization boundaries. We don’t know of another CDN that offers this as a built-in model for authenticated, multi-tenant APIs. We’re pretty proud of it.

#### A cache between every Worker entrypoint

Here is the part of Workers Cache that we think is the biggest unlock, and it's the part that's hardest to see if you're thinking about it as "a CDN cache that happens to work in front of Workers."

**Workers Cache sits in front of every Worker entrypoint** — the default export, every named [`WorkerEntrypoint`](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/rpc/#named-entrypoints), and every call between entrypoints in the same Worker via [`ctx.exports`](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/rpc/). That last clause is the one that changes what you can build.

When one entrypoint calls another via `ctx.exports`, the cache evaluates that call the same way it would evaluate a request from a browser. A hit returns the cached response and the callee never runs. A miss runs the callee and stores its response under its own cache key — keyed by the callee's entrypoint, path, query string, and `ctx.props`. The caller still runs on every request, but anything it hands off to the callee is memoized independently.

You decide, per entrypoint, which ones cache. In your Wrangler config, the `exports` map lets you turn caching on or off for each entrypoint by name (`"default"` is the default export). Opt an entrypoint **in** to cache the responses it produces; opt one **out** to keep it running on every request. A gateway or router entrypoint — anything that authenticates, normalizes, or dispatches — should be opted out, so it always runs, and its own output is never served from cache.

That gives you a primitive you can compose. You can author a Worker as a chain of small entrypoints — auth, normalization, routing, the expensive read, the data layer — and let Workers Cache slot in wherever you want it. Each cached entrypoint is a unit of memoization with its own key, its own TTL, and its own tag namespace for purging. Anything you would want to configure about caching — when it runs, what it keys on, when it invalidates — is expressed as ordinary Worker code: which entrypoint you call, what request you forward, what `ctx.props` you pass, what `Cache-Control` you set.

To make this concrete, here's a single Worker that does three things you couldn't easily do together on any other platform: it authenticates every request, caches the expensive backend behind a multi-tenant-safe cache key, and invalidates that cache when data changes.

Caching is configured per entrypoint. The gateway must run on every request — both to authenticate and because a cached gateway response would skip that auth check — so we disable caching on the default entrypoint and enable it only on the inner one:

```
{
  "name": "my-worker",
  "main": "src/index.ts",
  "compatibility_date": "2026-05-01",
  "cache": { "enabled": true },
  "exports": {
    // The gateway runs on every request — don't cache it.
    "default": { "type": "worker", "cache": { "enabled": false } },
    // Cache the expensive inner entrypoint.
    "CachedBackend": { "type": "worker", "cache": { "enabled": true } }
  }
}
```

```
import { WorkerEntrypoint } from "cloudflare:workers";

interface Env { API_TOKEN: string; }
interface Props { userId: string; }

// Inner entrypoint: the expensive work. Workers Cache sits in front
// of this — on a hit, this code never runs.
export class CachedBackend extends WorkerEntrypoint<Env, Props> {
  async fetch(request: Request): Promise<Response> {
    // ctx.props.userId is part of the cache key, so this is cached
    // separately for every user.
    const { userId } = this.ctx.props;
    const data = await loadExpensiveData(userId);

    return new Response(JSON.stringify(data), {
      headers: {
        "Content-Type": "application/json",
        "Cache-Control": "public, max-age=300, stale-while-revalidate=3600",
        "Cache-Tag": `user:${userId}`,
      },
    });
  }

  // Invalidate a user's cached response. purge() is scoped to the
  // entrypoint that calls it, so it must run inside CachedBackend —
  // the entrypoint that owns the cached response.
  async invalidate(userId: string): Promise<void> {
    await this.ctx.cache.purge({ tags: [`user:${userId}`] });
  }
}

// Outer entrypoint: runs on every request to authenticate and route.
// Caching is disabled for it in Wrangler config (above), so it always
// runs and the auth check is never skipped by a cache hit.
export default {
  async fetch(request, env, ctx): Promise<Response> {
    const userId = await authenticate(request, env);
    if (!userId) return new Response("Unauthorized", { status: 401 });

    // Invalidate this user's cache on writes, from the entrypoint that
    // owns it.
    if (request.method === "POST") {
      await handleWrite(request, userId);
      await ctx.exports.CachedBackend.invalidate(userId);
      return new Response("OK");
    }

    // For reads: strip Authorization (otherwise Cloudflare's automatic
    // bypass fires and nothing caches), then dispatch to the cached
    // backend with the authenticated user's identity in ctx.props.
    const forwarded = new Request(request);
    forwarded.headers.delete("Authorization");

    return ctx.exports.CachedBackend.fetch(forwarded, {
      props: { userId },
    });
  },
} satisfies ExportedHandler<Env>;
```

The whole thing is one Worker. One source file. One deploy. But there are two execution stages — caching is turned off for the gateway and on for the backend in one small `exports` block — and a cache sits between them, keyed per user, invalidated by the write path, and serving stale during background refreshes. The cache stage isn't something you bolted on. It's a layer of the program, written in code.

The patterns this composes into are open-ended. The same shape works for:

- **Caching a Durable Object.** Wrap the Durable Object behind an entrypoint, set `Cache-Control` on the response, and reads stop touching the Durable Object on a hit. Writes go to the DO directly and purge the cache by tag. The DO stays unaware that caching is happening.
- **Normalizing** `**Accept-Encoding**` **before** `**Vary**`**.** The outer entrypoint restores the original encoding from `request.cf.clientAcceptEncoding` (Cloudflare's front line normalizes it for cache efficiency) and forwards to a cached entrypoint that varies on the real value. Hit ratios stay high; clients get the right encoding.
- **Stripping tracking parameters before caching.** The outer entrypoint canonicalizes the URL — or sets a [custom cache key](https://developers.cloudflare.com/workers/cache/cache-keys/#custom-cache-keys) with `cf.cacheKey` on the `ctx.exports` call — so the cached inner entrypoint sees only the canonical form, and `?utm_source=anything` collapses to a single cache entry.

Stack them. A single Worker can have an outer entrypoint that authenticates and routes, a normalization entrypoint that strips tracking parameters and restores encoding headers, a cached entrypoint that fronts a Durable Object, and a separate cached entrypoint for an unauthenticated public API — each connected by a cache stage you didn't configure, just decided where to put. The [Examples page in the docs](https://developers.cloudflare.com/workers/cache/examples/) walks through several of these end-to-end.

We don't know of another platform where you can do this. CDN caches sit in front of an origin. Function platforms run functions. We don't know of another platform that gives you a cache that sits inside a single deployable unit, between the parts of your application, with each cache stage configured by the code on either side of it. That's what Workers Cache is. And because it composes with everything else the platform already gives you — Smart Placement, Durable Objects, service bindings, `ctx.props`, `ctx.exports` — the patterns you can build are open-ended. We've barely scratched the surface in this post.

#### First-class support in your framework

If you're building with Astro, the Cloudflare adapter wires up Workers Cache for you. Just add the [cacheCloudflare provider](https://docs.astro.build/en/guides/caching/#cloudflare) to your configuration:

```
// astro.config.mjs
import { defineConfig } from "astro/config";
import cloudflare from "@astrojs/cloudflare";
import { cacheCloudflare } from "@astrojs/cloudflare/cache";

export default defineConfig({
  adapter: cloudflare(),
  output: "server",
  experimental: {
    cache: { provider: cacheCloudflare() },
    routeRules: {
      "/products/*": { maxAge: 300, swr: 3600, tags: ["products"] },
      "/blog/*":     { maxAge: 60,  swr: 86400, tags: ["blog"] },
    },
  },
});
```

The adapter enables the cache, sets the right headers on the responses Astro generates, attaches `Cache-Tag` values for invalidation, and gives you a `cache.invalidate()` helper for purging tags when content changes. Astro pages that opt into server rendering automatically get the "render once, cache, refresh in the background" flow described above — no per-route configuration required, no framework-specific runtime layer to learn.

We're working with the maintainers of other frameworks to ship the same integration. If you build a framework adapter for Cloudflare, the [Workers Cache APIs](https://developers.cloudflare.com/workers/cache/) are exactly what you'd want them to be — header-driven configuration, programmatic purges, no platform-specific concepts to model.

#### See your cache on the same dashboard as your Worker

## 通俗精炼（1）

### 2026-07-07 09:55:06

#### Cloudflare Workers Cache：让 Worker 拥有自己的前置缓存

##### 一句话总结

Cloudflare 推出**Workers Cache**：一个直接位于 Worker 前面的分层缓存系统。开启后，可缓存请求会先命中 Cloudflare 缓存；命中时**Worker 不运行、无 CPU 成本、延迟更低**；未命中时才执行 Worker，并把可缓存响应写入缓存。

---

##### 核心变化：Worker 从 “缓存前的逻辑层” 变成 “可被缓存的源站”

过去 Workers 常用于站点前置逻辑，比如改 Header、URL 重写、A/B 测试、流量过滤等，架构上是：

> 用户请求 → Worker → Cloudflare Cache / Origin

但现在越来越多框架，如 Next.js、Remix、Astro、SvelteKit、TanStack Start，会把服务端渲染应用直接构建成 Worker。此时：

> Worker 本身就是源站

问题是：没有前置缓存时，每次页面访问都要运行 Worker，即使返回内容完全相同，也会产生延迟和 CPU 成本。

Workers Cache 将架构变为：

> 用户请求 → Cloudflare Cache → Worker

这让 SSR 应用获得类似静态站点的访问速度，同时保持动态渲染的灵活性。

---

##### 使用方式：配置极简，仍然基于 HTTP 标准

开启只需要在 Wrangler 配置中加一段：

```json
{
  "cache": {
    "enabled": true
  }
}
```

之后通过标准 HTTP Header 控制缓存：

```js
"Cache-Control": "public, max-age=300, stale-while-revalidate=3600"
```

内容更新时，Worker 可以自己清理缓存：

```js
await ctx.cache.purge ({ tags: ["product:123"] });
```

特点是：

- 不需要配置 Zone
- 不需要 Cache Rules / Page Rules
- 不需要单独购买或管理缓存产品
- 缓存策略直接写在 Worker 代码和响应 Header 中

---

##### 关键能力一：`stale-while-revalidate`让页面 “像静态站一样快”

`stale-while-revalidate`是体验提升的核心。

缓存生命周期分为三段：

1. **Fresh 阶段**  
   在`max-age`时间内，直接返回缓存，Worker 不运行。

2. **Stale 阶段**  
   缓存过期但仍在`stale-while-revalidate`窗口内，用户先拿到旧缓存，Worker 在后台刷新。

3. **完全过期阶段**  
   超出两个窗口后，才需要等待 Worker 重新生成响应。

这意味着大多数用户都不会等待服务端重新渲染，页面体验接近静态站点。

---

##### 关键能力二：支持`Vary`，同一个 URL 可缓存多种内容

真实业务中，同一个 URL 可能根据请求 Header 返回不同内容，例如：

- 浏览器支持 WebP 就返回 WebP，否则返回 JPEG
- 根据`Accept-Language`返回不同语言
- 根据`Accept`返回 HTML 或 JSON

Workers Cache 支持标准 HTTP `Vary` Header，会按请求 Header 自动区分缓存版本。

例如：

```js
Vary: "Accept"
```

这样同一个 URL 可以同时缓存 WebP 和 JPEG 两个版本，不会互相污染。

---

##### 关键能力三：这是 Worker 自己的缓存，不是 Zone 的缓存

这是一个重要产品设计变化。

Workers Cache 属于 Worker，而不是某个域名或 Zone。因此：

- Worker 绑定多个域名时，可以共享同一份缓存
- `workers.dev`也可以使用缓存
- Preview 环境有独立缓存，不会污染生产环境
- Workers for Platforms 中，每个租户 Worker 有独立缓存
- 清缓存只影响当前 Worker entrypoint，不会误删整个站点缓存

这让缓存能力更适合现代多入口、多租户、平台化架构。

---

##### 关键能力四：默认分层缓存，提升全球命中率

Workers Cache 默认是两层结构：

1. **Lower Tier**  
   靠近用户的数据中心缓存。

2. **Upper Tier**  
   面向全球聚合的上层缓存。

请求流程是：

> Lower Tier 命中 → 直接返回  
> Lower Tier 未命中 → 查 Upper Tier  
> Upper Tier 未命中 → 执行 Worker

好处是：全球任一地区首次生成内容后，可以先进入上层缓存，其他地区后续访问不一定需要再次执行 Worker。

这显著提升全球缓存命中率，尤其适合 SSR、商品页、文档页、内容站等场景。

---

##### 产品价值：把 SSR 的成本和体验问题降到最低

Workers Cache 解决了 SSR 应用长期面临的两难：

###### 过去的选择

- **静态生成 SSG**  
  访问快，但每次内容变化都要重新构建和部署。

- **每次请求 SSR**  
  内容新鲜，但每次访问都要付出渲染延迟和计算成本。

###### 现在的新选择

- 首次请求动态渲染
- 后续请求直接走缓存
- 过期后后台刷新
- 内容更新时按 Tag 或路径主动清理

这相当于用 HTTP 标准实现了类似 Incremental Static Regeneration 的效果，但不绑定特定框架。

---

##### 对开发者和平台方的意义

###### 对应用开发者

- 页面加载更快
- Worker CPU 成本更低
- SSR 应用更容易规模化
- 缓存策略直接在代码中表达，心智更简单

###### 对平台型产品

特别适合 Workers for Platforms、多租户 SaaS、开发者平台：

- 每个租户有独立缓存
- 缓存不会跨租户污染
- 可按租户、路径、Tag 精准清理
- 更容易构建全球化低延迟服务

###### 对架构设计

Workers Cache 也让不同 Worker 之间可以通过缓存形成组合：

- 靠近用户的 Worker 负责响应入口
- 靠近数据的 Worker 负责数据访问
- 中间用缓存作为性能边界

这有助于同时兼顾 “代码靠近用户” 和 “代码靠近数据”。

---

##### 需要关注的边界

使用 Workers Cache 时，仍需要设计好缓存策略：

- 哪些响应可以缓存，哪些必须私有化
- TTL 设置过长可能带来内容陈旧
- `Vary`使用不当可能导致缓存版本爆炸
- 首次访问新页面仍需要真实渲染
- 主动 Purge 策略需要和业务更新链路配合

---

##### 总结判断

Workers Cache 是 Cloudflare Workers 从 “边缘函数” 走向 “完整应用运行平台” 的关键补齐能力。

它的核心价值不是单纯增加一个缓存 API，而是让**SSR 应用、平台型架构、多租户应用**可以在 Cloudflare 网络上获得：

- 静态站级别的访问速度
- 服务端渲染的内容新鲜度
- 更低的计算成本
- 更简单的标准化缓存模型

本质上，它把缓存从 “站点级配置能力” 变成了 “Worker 原生应用能力”。

## 结构化（1）

### 2026-07-22 09:32:20

#### Your Worker 现在可以拥有自己的前置缓存

Cloudflare 推出 **Workers Cache**：把分层缓存放在 Worker 前面，缓存命中时无需执行 Worker，也不产生 CPU 计费；开发者只需在 Wrangler 中启用，并通过标准 HTTP 响应头控制缓存。它让服务端渲染应用同时获得接近静态站点的速度、按需更新的灵活性，以及全球分层缓存能力。

##### 1. Workers Cache 的使用方式

启用后，请求流程变为：

1. 可缓存请求先进入 Cloudflare 缓存。
2. 如果缓存仍然有效，直接返回响应，**Worker 不运行，CPU 费用为 0**。
3. 如果未命中，Worker 执行并生成响应。
4. 若响应可缓存，Cloudflare 会保存它，供后续全球请求使用。

只需在 Wrangler 配置中启用：

```json
{
  "cache": {
    "enabled": true
  }
}
```

缓存策略继续使用熟悉的 HTTP 响应头：

```http
Cache-Control: public, max-age=300, stale-while-revalidate=3600
Cache-Tag: products,product:123
```

内容变化时，Worker 还可以按标签主动清除缓存：

```js
await ctx.cache.purge({ tags: ["product:123"] });
```

不需要单独配置 Zone、缓存规则或额外产品。该功能适用于自定义域名、`workers.dev`、Service Binding、预览环境和 Workers for Platforms，并已向**所有套餐**开放。

---

##### 2. 为什么服务端渲染应用需要“Worker 前置缓存”

Workers 在 2017 年推出时，主要位于缓存和源站之前，用来改写 URL、添加请求头、执行 A/B 测试或过滤流量。当时 Worker 是源站前的处理层。

如今，Astro、TanStack Start、Next.js、Remix、SvelteKit 等框架都能直接把应用构建为 Worker。此时：

- Worker 本身就是服务器和源站；
- 即使响应与上一秒完全相同，每次请求仍要执行代码；
- 每个页面访问都要承担渲染延迟和 CPU 成本。

Workers Cache 将架构改为：

> 用户请求 → Cloudflare 缓存 → Worker

命中缓存时，Worker 完全不执行；只有缓存未命中时才渲染一次并填充缓存。

过去，服务端应用通常只能二选一：

- **构建时预渲染所有页面**：访问快，但内容变更需要重新构建和部署。一个有数千页的文档站可能需要 **5～10 分钟**，大型电商站会更久。
- **每次请求实时渲染**：内容最新，但每位用户都要承担渲染延迟和计算成本。

Workers Cache 提供第三种方式：

- 首次访问时按需渲染；
- 将渲染结果缓存；
- 在开发者设置的 TTL 内直接返回；
- 到期后自动刷新。

这相当于获得静态站点的访问速度，同时保留服务端渲染的更新能力，不需要依赖框架特有的增量静态再生成机制。

---

##### 3. `stale-while-revalidate` 让刷新过程几乎无感

`stale-while-revalidate` 允许缓存过期后，先立即返回旧内容，同时在后台执行 Worker 刷新缓存。

例如：

```http
Cache-Control: public, max-age=300, stale-while-revalidate=3600
```

其含义是：

- **前 5 分钟（`max-age=300`）**：缓存有效，直接返回，Worker 不运行。
- **之后 1 小时（`stale-while-revalidate=3600`）**：立即返回旧缓存，同时后台运行 Worker 更新内容，用户无需等待。
- **超过两个时间窗口**：必须执行 Worker 生成新响应，用户需要等待这次渲染。

刷新期间，响应会带有：

```http
Cf-Cache-Status: UPDATING
```

典型设置示例：

- 商品目录经常更新：`max-age=300, stale-while-revalidate=3600`，大多数访客不会等待，同时内容能保持较新。
- 很少变化的博客归档：`max-age=86400, stale-while-revalidate=2592000`，每个页面通常每天只需运行一次 Worker。

因此，通常只有一个全新页面的首次请求需要承担完整渲染成本，之后对用户而言几乎就像静态页面。

---

##### 4. 通过 `Vary` 为同一 URL 缓存多种内容

同一 URL 可能根据客户端返回不同内容，例如：

- 浏览器收到 HTML，API 客户端收到 JSON；
- 支持 WebP 的客户端收到 WebP，不支持的收到 JPEG；
- 根据语言请求头返回英语、法语或日语页面。

Workers Cache 支持标准 HTTP `Vary` 响应头。比如：

```http
Vary: Accept
Cache-Control: public, max-age=3600
```

Cloudflare 会根据请求中的 `Accept` 值分别保存不同版本：

- `Accept: image/webp,*/*` → 返回 WebP；
- `Accept: image/jpeg` → 返回 JPEG。

两个版本首次生成后都可以直接从缓存返回，Worker 不再重复运行。

这一实现遵循 RFC 9110 和 RFC 9111，没有固定的请求头白名单。不过需要注意：

- 请求头取值过多可能导致缓存变体数量膨胀，可由网关 Worker 先标准化；
- 清除某个 URL 的缓存时，会同时清除它的所有变体；
- `Vary: *` 会完全禁用缓存。

---

##### 5. 缓存属于 Worker，而不是 Zone

传统 Cloudflare 缓存主要按 Zone 配置，包括 Cache Rules、Page Rules、缓存文件扩展名、自定义缓存键和 Cache Reserve 等。Workers Cache 则直接归属于 Worker。

这带来几个变化：

- **无需管理 Zone 缓存规则**：缓存行为主要由 Worker 返回的 `Cache-Control` 等响应头决定。
- **缓存跟随 Worker，而非域名**：同一 Worker 即使绑定到多个域名或通过 Service Binding 调用，也可以共享同一份缓存。
- **支持 `workers.dev` 和预览环境**：每个预览版本拥有独立缓存，不会污染生产环境。
- **支持 Workers for Platforms**：每个租户的 Worker 缓存相互隔离，也与调度器隔离。
- **清除范围更安全**：执行 `purgeEverything` 时，只清除对应 Worker 入口点的缓存，不会误删整个 Zone 或其他 Worker 的内容。

缓存策略也可以直接写在代码里，例如：

- 不同路径设置不同 TTL；
- 私有请求返回 `Cache-Control: private` 来绕过缓存；
- 通过规范化 URL 或 `ctx.props` 构造安全的缓存键；
- 按标签或路径前缀主动清除；
- 针对不同 Worker 入口点决定是否启用缓存。

---

##### 6. 默认提供全球两级缓存

Workers Cache 默认采用区域化分层缓存，无需额外配置：

1. **下层缓存**：位于最接近用户的 Cloudflare 数据中心。
2. **上层缓存**：数量更少，用于汇总全球下层节点的缓存填充请求。

请求流程如下：

- 先查询本地下层缓存；
- 下层未命中，再查询上层缓存；
- 上层命中后，将响应返回，并同步填入下层缓存；
- 两层都未命中时才运行 Worker，结果随后写入两层缓存。

关键收益是：某个页面在全球任意地点首次生成后，会填充上层缓存。之后其他地区即使本地下层节点从未见过该请求，也可以从上层缓存获取，而不必再次运行 Worker。

这能显著提高缓存命中率，而且所有启用 Workers Cache 的 Worker 都能免费获得分层能力。如果同时使用 Smart Placement，则先检查两级缓存，只有都未命中时，才把 Worker 执行调度到更靠近数据源的位置。

---

##### 7. 同时兼顾“靠近用户”和“靠近数据”

Web 应用长期存在一个矛盾：

- 代码靠近用户，可以降低用户到服务器的网络延迟；
- 代码靠近数据库，可以降低查询和数据访问延迟。

Cloudflare 网络距离约 **95% 的全球互联网用户不超过约 50 毫秒**；Smart Placement 和 Placement Hints 则可让计算更靠近数据源。

Workers Cache 进一步连接了两者：由于缓存属于 Worker，并且 Service Binding、`ctx.exports` 等 Worker 间调用也能经过缓存，因此应用可以拆分成一条 Worker 调用链：

- 面向用户的 Worker 部署在靠近用户的位置；
- 数据处理 Worker 在靠近数据库的位置执行；
- 在不同入口或处理阶段之间插入缓存；
- 每个入口点都可独立决定是否缓存。

这样，开发者可以让不同部分运行在最合适的位置，并用缓存作为它们之间的衔接层，减少重复执行和跨区域访问成本。

### 2026-08-03 01:22:56

#### Cloudflare Workers 现在可以拥有自己的缓存

这篇材料介绍了 Cloudflare 推出的 Workers Cache，也就是放在 Worker 前面的分层缓存。你将了解到：它为什么适合服务器端渲染应用，怎样用熟悉的 HTTP 缓存规则控制缓存，以及它如何降低延迟和 Worker 的运行成本。

##### 首先：Workers Cache 到底是什么

核心结论是，Workers Cache 会先拦截发往 Worker 的请求。只要缓存里有新鲜的响应，Cloudflare 就直接把结果返回给用户，Worker 根本不用运行，也不会产生这次 Worker 的 CPU 运行费用。

通俗地说，过去的流程通常是“请求先到 Worker，Worker 处理完以后再决定是否使用缓存”。现在则变成了“请求先查缓存，只有缓存没有结果时，才启动 Worker”。

如果缓存未命中，Worker 才会执行代码。只要它返回的响应允许缓存，Cloudflare 就会把结果保存起来。下一次请求，无论来自世界哪个地方，都有机会直接从缓存返回。

启用方式也很简单。只需要在 Wrangler 配置中加入一个缓存配置，打开 `cache.enabled`。之后，缓存行为主要通过响应头控制，使用的就是开发者熟悉的 HTTP 标准。

比如，`Cache-Control: public, max-age=300, stale-while-revalidate=3600`，意思是：响应可以公开缓存五分钟；五分钟之后，还可以继续使用旧内容，同时在后台刷新，最长持续一个小时。

内容发生变化时，Worker 还可以主动清理自己的缓存。比如给商品加上 `product:123` 这样的缓存标签，商品更新后，就调用缓存清理接口，按标签删除对应内容。

这里需要特别强调，Workers Cache 不需要单独配置一个区域，也不需要设置规则引擎、额外申请一个缓存产品，甚至不需要登录另一个管理系统。Worker 代码本身就是配置入口。

而且，这份缓存跟着 Worker 走。Worker 绑定到自定义域名、`workers.dev` 域名，还是通过服务绑定调用，使用的都是同一套 Worker 缓存。预览环境也支持缓存，并且每个预览版本有自己的缓存，不会污染生产环境。Workers for Platforms 中，每个租户的 Worker 也拥有彼此隔离的缓存。

目前，Workers Cache 已经向所有计划、所有 Worker 开放，只需要通过 Wrangler 启用。

##### 接下来：为什么服务器端渲染特别需要它

核心结论是，Worker 逐渐从“源站前面的附加代码”，变成了应用本身的服务器。既然 Worker 就是源站，那么它前面就需要一个真正的缓存。

Cloudflare 在 2017 年推出 Workers 时，典型架构是：Worker 位于缓存和源站之前。它适合做请求改写、添加请求头、A/B 测试，或者在请求到达源站之前过滤流量。

但现在，很多框架都可以直接把应用构建成 Worker。包括 Astro、TanStack Start、Next.js、Remix 和 SvelteKit。这样的应用后面可能没有传统意义上的源站，Worker 自己就是服务器。

问题是，在旧架构里，缓存没有东西可缓存。每一次请求都会运行 Worker，即使这一次生成的页面，和一秒钟前生成的页面完全一样。

Workers Runtime 的执行速度很快，能够处理每秒数千万次请求。但“每次都能快速生成”，不等于“每次生成都没有成本”。对于服务器端渲染应用来说，每次页面加载，本质上都意味着一次渲染。用户每次访问都要承担这次渲染的延迟，Worker 也要承担这次运行的 CPU 时间。

Workers Cache 改变了这个流程。缓存放在 Worker 前面以后，第一次请求可能需要执行 Worker、生成页面并写入缓存。之后的请求直接读取缓存，不再启动 Worker。

##### 更重要的是：它解决了静态生成和实时渲染之间的两难

过去，服务器端渲染应用通常要在两种方案里选择。

第一种是构建时预渲染，也就是提前把页面生成好。这样访问速度很快，但内容一有变化，就要重新构建和部署。

材料里举了一个例子：一个有几千个页面的文档网站，完整构建可能需要五到十分钟。大型电商网站可能需要更久。而且每次修改内容，都可能触发一次完整构建。

第二种方案是每次请求都重新渲染。这样内容比较新，但每一个访客都要等待渲染过程，也要重复支付运行成本。

Workers Cache 提供了第三种选择：按需渲染，渲染结果缓存一段时间。新页面第一次被访问时，Worker 负责生成它。之后，在缓存有效期内，这个页面的访问效果就像静态页面一样快。缓存过期后，再由下一次请求触发刷新。

这样一来，开发者同时获得了两种好处：访问速度接近静态网站，不需要每次改动都完整构建；内容又可以保持服务器端渲染的灵活性。

它也不依赖某个框架专门实现的机制，比如某些框架里的增量静态再生成。它直接使用标准 HTTP 缓存，让缓存自然地工作在 Worker 前面。

##### 再接下来：为什么“过期后后台刷新”很关键

这里的关键术语是 `stale-while-revalidate`。它可以翻译成“使用旧内容的同时，在后台重新验证和刷新”。

核心结论是，缓存过期后，用户不必等待新的页面生成。Cloudflare 可以先把旧版本立即返回，同时在后台运行 Worker，生成新的版本。

如果没有这个机制，缓存刚过期时，第一个访问者就要等待 Worker 重新渲染页面。这个访问者会明显感受到延迟。

如果启用了这个机制，缓存过期后的第一个访问者也能立刻拿到旧页面。响应中会带有 `Cf-Cache-Status: UPDATING`，表示 Cloudflare 正在后台更新缓存。后台刷新完成后，后续用户就会拿到新内容。

可以把缓存状态简单理解成三个阶段。

第一阶段是“新鲜窗口”，由 `max-age` 决定。只要还在这个时间内，Cloudflare 直接返回缓存，Worker 不运行。

第二阶段是“过期但可后台刷新窗口”，由 `stale-while-revalidate` 决定。Cloudflare 仍然立即返回缓存，但同时在后台运行 Worker 更新内容，用户不需要等待。

第三阶段是两个窗口都结束之后。此时 Cloudflare 必须运行 Worker 生成全新的响应，当前用户才可能需要等待这次渲染。

这两个时间窗口由开发者自己选择。

例如，商品目录每几分钟就会更新，可以设置五分钟的新鲜期，再允许一个小时的后台刷新。这样用户基本不会等待，同时 Worker 也会定期运行，保持内容更新。

如果是几乎不变化的博客归档，可以设置一天的新鲜期，再允许三十天的后台刷新。这样每个页面大致每天才需要重新生成一次。

所以，真正需要承担完整渲染成本的，通常只是一个新页面的第一次请求。之后，这个页面对访问者来说就接近静态内容，但页面生成逻辑仍然完全掌握在 Worker 手里。

##### 一个 URL，也可以缓存多种版本

接下来是内容协商，也就是同一个地址，根据请求者的能力和偏好，返回不同内容。

核心结论是，Workers Cache 支持标准 HTTP 的 `Vary` 响应头，可以为同一个 URL 保存多个版本，并且只把匹配的版本返回给正确的请求。

通俗地说，同一个商品页面，浏览器可能需要 HTML，接口客户端可能需要 JSON。同一张图片，有的客户端支持 WebP，有的只支持 JPEG。同一个首页，也可能根据语言返回中文、英文、法文或日文。

不使用缓存时，Worker 读取请求头，再决定返回什么内容，并不复杂。难点在于缓存：如果缓存系统不知道这些版本之间的区别，就可能把 WebP 图片错发给不支持 WebP 的客户端，或者把英文页面发给中文用户。

使用 `Vary` 后，Worker 可以告诉 Cloudflare：这个响应要根据哪个请求头区分。

例如，响应中设置 `Vary: Accept`，就表示要根据请求里的 `Accept` 头保存不同版本。发送 `Accept: image/webp,*/*` 的浏览器，会得到 WebP 版本；发送 `Accept: image/jpeg` 的浏览器，会得到 JPEG 版本。

这两个版本都可以被缓存。每种版本第一次请求时，Worker 运行一次；之后，匹配的请求都可以直接从缓存返回。

Workers Cache 遵循 RFC 9110 和 RFC 9111 描述的 HTTP 标准。它没有规定一个固定的请求头白名单，开发者可以根据需要指定要区分的请求头，Cloudflare 会根据这些请求头的实际值建立缓存变体。

不过，变体太多也会降低缓存效率。材料提到，可以在网关 Worker 中先把请求头标准化，减少不必要的版本数量。

还有一个例外需要记住：如果设置 `Vary: *`，就会完全关闭缓存。按标签清理缓存时，同一个 URL 的所有变体也会一起失效。

##### Workers Cache 属于 Worker，不属于区域

这里有一个重要的概念变化。

Cloudflare 原本就有区域级缓存。所谓“区域”，可以简单理解为一个域名或站点在 Cloudflare 中的配置范围。过去，缓存规则、页面规则、文件扩展名设置、Cache Reserve、分层缓存拓扑和自定义缓存键，基本都是按区域配置的。

Workers Cache 不一样。它属于具体的 Worker，而不是某个区域或域名。

这会带来几个实际好处。

首先，不需要管理区域级的缓存配置。哪些响应可以缓存，缓存多久，主要由 Worker 返回的 `Cache-Control` 头决定。

其次，缓存跟随 Worker，而不是跟随某个主机名。假设同一个 Worker 同时绑定到 `api.example.com`、`api.example.net`，也能通过服务绑定调用。那么访问 `/users/42` 时，无论请求从哪个入口进入，都可以命中同一份 Worker 缓存。

再次，Worker 缓存不会影响同一区域中的其他内容。调用“清空全部缓存”时，清理的只是这个 Worker 入口点自己的缓存，不会把整个站点的其他内容删除，也不会因为一个 Worker 部署，就让另一个 Worker 的数据失效。

缓存策略也可以直接写进 Worker 代码。例如，根据 URL 路径给不同页面设置不同的缓存时间；对包含私人信息的请求返回 `Cache-Control: private`，让它绕过公共缓存；还可以在进入 Worker 前规范化 URL，控制哪些内容会进入缓存键。

换句话说，开发者已经写下的 Worker，就是缓存策略的控制面。

##### 两层缓存，让全球请求更容易复用结果

Workers Cache 默认使用区域分层缓存，也就是两层缓存结构。

第一层是靠近用户的下层缓存。每个接收这个 Worker 流量的 Cloudflare 数据中心，都有自己的下层缓存。

第二层是上层缓存。它负责汇聚整个网络中的缓存内容，下层缓存未命中时，会继续向上层缓存查询。

一次请求首先查找离用户最近的下层缓存。如果命中，就直接返回。

如果下层没有命中，就去查询上层缓存。如果上层命中，响应会返回给用户，同时也会顺路保存到下层缓存。

只有上下两层都没有命中时，Worker 才真正运行。Worker 生成的结果，会同时写入两层缓存。

这个结构的意义在于：世界上某个地方的第一次请求，可以把结果放入上层缓存。之后，即使另一个数据中心以前从没见过这个 URL，也有机会直接从上层缓存拿到结果，不需要再次运行 Worker。

相比只有一层的缓存，这样可以显著提高缓存命中率。对于 Worker 本身就是源站的应用来说，这一点尤其重要。

这种分层方式和 Cloudflare 区域服务使用的 Tiered Cache，也就是“分层缓存”技术类似。不过，Workers Cache 不需要开发者另外打开或设置拓扑。只要启用了缓存，分层能力就自动提供。

如果 Worker 使用 Smart Placement，也就是让代码更靠近数据源运行的智能部署方式，缓存也可以和它配合。请求会先查询两层缓存，只有两层都没有命中时，才会由 Smart Placement 把 Worker 的执行调度到更靠近源站或数据的位置。

##### 最后：让代码靠近用户，也靠近数据

Web 性能里一直存在一个矛盾。

代码靠近用户，用户和服务器之间的往返时间就更短，页面响应更快。代码靠近数据库或其他数据源，查询数据时的网络往返又更短。

但这两者往往不在同一个地方。代码离用户近了，可能离数据库远；离数据库近了，又可能让用户等待更久。

Cloudflare 的网络距离全球大约百分之九十五的互联网用户在五十毫秒以内。通过 Smart Placement 和 Placement Hints，开发者可以让代码更靠近数据，而不必自己管理传统云厂商的区域。

过去，缓存、服务绑定和代码部署位置还没有完全组合起来。现在，Workers Cache 补上了其中的连接部分。

因为缓存属于 Worker，而且 Worker 之间通过服务绑定和 `ctx.exports` 调用时可以经过缓存，所以应用可以由一串 Worker 组成。每个 Worker 在适合自己的位置运行，而缓存则成为这些 Worker 之间的连接接口。

这意味着，应用不一定要由一个巨大 Worker 完成。开发者可以把不同处理阶段拆开，让每个阶段分别靠近用户、靠近数据，或者放在更适合它的位置，并在入口点之间插入缓存阶段。

材料特别强调，缓存可以位于每一个 Worker 入口点之前，而不只是公开访问的那个入口点。开发者可以逐个入口点决定哪些要缓存，哪些不缓存。这样，缓存就不再只是应用外部的一层设置，而是可以直接嵌入应用结构中。

##### 回顾：最值得记住的几个结论

最后，用四点来回顾全文。

第一，Workers Cache 把缓存放到了 Worker 前面。缓存命中时，Worker 不运行，用户获得更低延迟，开发者也不需要支付这次 CPU 运行成本。

第二，它为服务器端渲染提供了第三种方案：不必每次改动都完整构建，也不必每次访问都重新渲染，而是按需生成、按时间缓存。

第三，`stale-while-revalidate` 让缓存过期后的刷新发生在后台。即使触发刷新，用户也能先拿到旧内容，不必等待新的页面生成。

第四，这是一套属于 Worker 自己的标准 HTTP 缓存。它支持多种内容变体、按标签或路径清理、全球分层缓存，并且能够跟随 Worker 的不同入口和部署环境一起工作。

简单说，Workers Cache 让 Worker 既可以负责动态生成内容，又能在生成之后像静态站点一样快速服务访问者。

### 2026-09-18 00:36:44

#### Cloudflare 把缓存从“站点配置”变成了计算模型的一部分

Cloudflare Workers Cache 最值得关注的，不是多了一套缓存 API，而是**把缓存放到了 Worker 执行之前**。命中时，Worker 完全不运行，用户直接获得缓存响应，也不产生 CPU 计费；未命中时才执行代码并回填缓存。再配合两级缓存，某个页面在任一地区首次生成后，其他地区即使本地没有副本，也可能从上层缓存取得，不必再次渲染。

这改变了边缘计算的成本模型：过去即使响应内容一模一样，每次请求也要启动服务端渲染；现在，计算从“每个请求都执行”变成“内容需要更新时才执行”。

##### 它填补了静态生成与实时渲染之间的空档

大型文档站、电商目录等应用长期面临两个不理想的选择：构建时生成全部页面，发布越来越慢；或者每次请求实时渲染，持续承担延迟与算力成本。Workers Cache 提供了第三种路径：页面首次访问时生成，此后像静态文件一样分发；过期后用 `stale-while-revalidate` 先返回旧版本，再在后台刷新。

这并非 Cloudflare 发明的新范式，很多框架已有 ISR 一类机制。真正的进步是，它被下沉为标准 HTTP 能力：应用只需返回 `Cache-Control`、`Vary` 和 `Cache-Tag`，不必绑定特定框架。**当基础设施能直接理解内容的新鲜度，框架就不再需要各自重造缓存系统。** 对产品团队而言，这意味着更低的迁移成本，也更容易让不同技术栈共享同一套性能与成本策略。

##### 更重要的变化，是缓存开始跟着服务走

传统 CDN 缓存通常隶属于域名和站点规则；Workers Cache 则隶属于 Worker 的入口。它可跨自定义域名、`workers.dev`、预览环境和服务绑定工作，清理操作也限定在相应入口，不会误伤整个站点。由此，缓存不再只是网站最外层的加速器，而可以插入多个 Worker 之间，成为服务组合的边界。

这有望缓解边缘应用的经典矛盾：代码靠近用户时，可能远离数据库；靠近数据库时，又增加用户往返延迟。现在可以让靠近数据的 Worker 负责生成结果，再由前置缓存把结果分发到全球。缓存承担的不是简单“提速”，而是**减少必须跨地域执行的次数**。

##### 简单接口没有消除一致性风险

文章强调“一行配置”，但实际难点仍在缓存策略。`stale-while-revalidate` 用短暂过期换取稳定低延迟，适合商品目录、文章页，却未必适合库存、价格、权限等强时效信息。`Vary` 能缓存语言和图片格式等不同表示，但如果直接使用取值高度离散的请求头，缓存变体会迅速膨胀。涉及登录状态或多租户时，缓存键隔离和 `private` 设置更是正确性的前提。

因此，这项能力最有价值的机会不是“给所有请求打开缓存”，而是识别那些**生成昂贵、重复访问高、允许有限陈旧**的响应。Cloudflare 真正降低的是实施门槛；团队仍需明确一个核心产品问题：每类内容最多可以旧多久，以及内容变化后，能否可靠地按标签或路径完成失效。

## 默认总结（1）

### 2026-09-18 01:43:18

##### 一句话看懂

Cloudflare 推出 **Workers Cache**：把分层缓存放到 Worker 前面，命中缓存时无需执行 Worker，可降低页面延迟和 CPU 费用，并用标准 HTTP 响应头直接控制。

##### 关键内容

- 开启只需一段 Wrangler 配置；Worker 通过 `Cache-Control` 设置有效期，通过 `Cache-Tag` 和 `ctx.cache.purge()` 精确清除缓存，不必配置域名 Zone 或额外缓存规则。
- 它主要解决服务端渲染的取舍：页面首次访问时动态生成，之后直接返回缓存；配合 `stale-while-revalidate`，缓存过期后仍可先给用户旧内容，再在后台刷新，避免等待。
- 缓存默认分两级：就近数据中心先查本地缓存，未命中再查全网共享的上层缓存；只有两层都没有时才运行 Worker。
- 支持标准 `Vary` 头，可按语言、图片格式等保存同一 URL 的不同版本；缓存归属于 Worker，并覆盖自定义域名、`workers.dev`、预览环境及服务绑定等入口。

##### 通俗解读

它相当于在“动态网页生成器”前放了一份全球共享的成品库：多数访客直接拿成品，不必每次重新制作。Cloudflare 称这能兼顾静态网站的速度与动态内容的更新能力，但首次访问及完全过期时仍需执行 Worker。
