## 分析要点

- **核心高价值点**：新技术不是不能用，但必须意识到它会消耗组织注意力和运维能力，应以全局成本而非局部最优来决策。
- **留存建议**：长期保留（包含经典且可复用的技术选型框架，对工程决策和团队技术治理有长期参考价值）

**知识要点**

- 每家公司可承受的新技术复杂度有限，可类比为有限的“创新 token”
- 成熟技术的优势不仅是功能稳定，更是失败模式被充分理解
- 技术选型应从公司整体运维、维护和认知成本出发做全局优化
- 引入新技术前应先验证现有技术栈是否真的无法解决问题
- 新增技术若与旧系统重叠，应明确迁移计划，避免技术栈碎片化

**行动项**

- 在引入新技术前列出其必要性、替代方案、运维成本和失败模式
- 建立团队级技术选型评审机制，确保新增技术具备组织可见度
- 优先用现有成熟工具解决问题，只有在收益显著超过长期成本时才引入新技术
- 为已引入的新技术制定迁移、淘汰或收敛计划

## 正文

**yibie**

推荐这篇，Dan McKinley（前 Etsy 工程师）写的经典工程文化文章。他说每个公司大约有三次"创新 token"的机会——你选了 NodeJS、MongoDB、使用不到一年的服务发现技术，每次都是花掉一次。而选 MySQL、Postgres、Python、Cron……这些无聊技术的好处在于，不仅功能被充分理解，失败模式也被充分理解。这不是一篇反对新技术的文章——是教你什么时候该用新技术、为什么要给团队设定"使用新东西需要全公司知道"的文化。

选择无聊的技术

我职业生涯中发生的最好的事，大概是有 Kellan 管我。我在那里待得够久，看到了 Kellan 的技术决策开始结出果实。我从中并且作为其结果学到了很多东西。

离开 Etsy 一年后，我重新恢复了对技术的关注能力。我的思考已经结晶到可以连贯地写下来的程度。以下是 Kellan 式思考的总结——希望不会让他太过尴尬。

拥抱无聊

设想每个公司大约有三个创新 token。你可以随心所欲地花它们，但供应量在一段长时间内是固定的。你也许在达到一定程度的稳定和成熟之后能再多拿到几个，但一般倾向是高估你钱包里有多少。

如果你选择用 NodeJS 写你的网站，你刚花掉了一个创新 token。如果你选择用 MongoDB，你刚花掉了一个创新 token。如果你选择用存在了一年或不到的服务发现技术，你刚花掉了一个创新 token。如果你选择自己写数据库——天哪，你麻烦大了。

这些选择中任何一个对一家 JavaScript 咨询公司或一家数据库公司可能是合理的。但你大概率不是。你大概率在为一家至少表面上是"重新思考全球商务"或"重新发明网络支付"或推进某个同样适当宏大的使命的公司工作。在这个背景下，把你有限的注意力用在创新 SSH 上，是一种极好的失败方式。或者至少是延迟成功的方式。

什么算无聊？这有点微妙。"无聊"不应该和"坏"混为一谈。世界上有既无聊又坏的技术——你不应该用这些。但有很多无聊且好的技术选择，或至少足够好。MySQL 是无聊的。Postgres 是无聊的。PHP 是无聊的。Python 是无聊的。Memcached 是无聊的。Squid 是无聊的。Cron 是无聊的。

无聊的美妙之处（如此定义下）在于这些工具的能力是被充分理解的。但更重要的是，它们的失败模式也是被充分理解的。

在选择技术时，你既有已知的未知，也有未知的未知。

• 已知的未知是类似这样的："我们不知道这个数据库达到 100% CPU 时会发生什么。"  
• 未知的未知是类似这样的："老天，我们甚至没有想到写统计量会导致 GC 暂停。"

哪怕对于已经存在了几十年的技术，这两种集合通常都是非空的。但对于闪亮的新技术来说，未知的未知的量级要大得多——这很重要。

全局优化

我毫无歉意地认为偏袒无聊技术是一件好事，但它不是唯一需要考虑的因素。技术选择不是在孤立状态下发生的。它们有一个影响范围，触及整个团队、组织，以及从你所有选择之和里涌现出的系统。

向公司添加技术是带成本的。作为一个抽象陈述这很显而易见：如果我们已经在用 Ruby，再加 Python 感觉不合理，因为增加的复杂性会超过 Python 的边际效用。但不知何故当我们谈论 Python 和 Scala 或 MySQL 和 Redis 时，人们失去了理智，抛弃了所有约束，开始狂热地谈论为任务选最佳工具。

你的工作本质上是将业务问题映射到一个涉及软件选择的解空间上。如果软件选择真的没有包袱，你确实可以为你各种各样问题挑一堆局部最佳的工具。

但在现实世界里——那个运维是严重关切的世界——你是在全局优化。问题在于"最佳工具"思维对它眼中的"最佳"和"任务"是近视的。你的任务是保持公司运转。而"最佳"工具是那个在尽可能多的问题上占据"最不差"位置的工具。

保持系统可靠运行的长期成本基本上总是远远超过你在构建时遇到的任何不便。成熟和多产的开发者理解这一点。

有时选择新技术

把这种推理推到归谬的极端，就是选 Java，然后尝试不借助任何其他东西来实现一个网站。那将是疯狂的。你需要一些向工具箱里添加东西的方法。

重要的第一步是承认这是一个过程，以及一场对话。新技术最终会产生公司层面的影响，所以添加技术是一个需要公司层面可见度的决定。

最值得推荐的练习之一是：考虑如何在不添加任何新东西的情况下解决你的当前问题。 首先，提出这个问题应该能检测到"问题"其实是有人真的想用这项技术的情况。如果是这样，你应该立即否决。

一个小的技术选择集合能走多远，可能令人惊讶。实践中这个问题的答案几乎从来不是"我们做不到"，它通常只是某种程度上的"嗯，我们可以做到，但会太难了"。如果你认为你用现有的工具无法实现你的目标，你大概只是不够有创造力地思考。

写下到底是什么让当前技术栈如此昂贵和困难地解决问题，这会有帮助。这和上一个练习相关，但有微妙的不同。

新技术选择可能是纯增量式的（比如："我们还没有缓存，所以让我们加 memcached"）。但它们也可能与你已经在使用的东西重叠或替换它。如果是这样，你应该为将旧功能迁移到新系统设定明确的期望。 策略通常应该是"我们承诺迁移"，带有建议的时间线。这一步的目的是把残骸保持在可管理的水平，并避免局部最优解的泛滥。

这个过程并不令人生畏，也不麻烦。就是几个填空题作为作业，然后开个会讨论一下。我认为，如果一项新技术能毫发无损地通过这个挑战，加入它是可以的。

发版就好

多语言编程被包装成一个承诺：让开发者以完全的自由选择自己的工具，会使他们更有效地解决问题。这个问题的定义往好了说是幼稚的，往坏了说是动机性推理。这种方式产生的日常运维苦力的重量把你压死。

有意识地选择技术给了工程头脑真正的自由：沉思更大问题的自由。为技术而技术是万金油。

## 结构化（1）

### 2026-07-09 03:30:56

#### 文章精炼总结

这篇文章推荐了 Dan McKinley 2015 年的经典工程文化文章《Choose Boring Technology》。核心观点是：技术选型不要盲目追新，公司应优先选择“无聊但成熟”的技术，把有限的创新精力留给真正重要的业务问题。

##### 1. “创新 token”：新技术不是免费的

- 作者提出一个比喻：**每家公司大约只有 3 个“创新 token”**，每采用一项高风险新技术，就相当于花掉一个。
- 例如：
  - 用 **NodeJS** 写网站：花掉 1 个 token；
  - 选 **MongoDB**：花掉 1 个 token；
  - 用一个存在不到一年的服务发现技术：花掉 1 个 token；
  - 自己写数据库：风险极高，几乎是在“找麻烦”。
- 这些选择不是绝对错误，但除非你的公司本身就是 JavaScript 咨询公司或数据库公司，否则不该把有限精力浪费在非核心技术创新上。

##### 2. 什么是“无聊技术”：成熟、可靠、失败模式清楚

- “无聊”不等于“坏”，而是指技术成熟、被广泛验证、团队容易理解和维护。
- 文中列举的“无聊但好用”的技术包括：
  - **MySQL**
  - **Postgres**
  - **PHP**
  - **Python**
  - **Memcached**
  - **Squid**
  - **Cron**
- 无聊技术的价值不只在于功能清楚，更重要的是：**它们的失败模式也被充分理解**。
- 新技术的问题在于存在大量“未知的未知”：
  - 已知的未知：比如“不知道数据库 CPU 到 100% 时会怎样”；
  - 未知的未知：比如“完全没想到写统计会导致 GC 暂停”。

##### 3. 技术选型要做“全局优化”，不是局部最优

- 技术选择不是孤立决策，会影响整个团队、运维、组织协作和长期系统复杂度。
- 很多人喜欢说“为任务选择最佳工具”，但现实中真正的任务是：**让公司长期稳定运转**。
- 所谓“最佳工具”，不一定是在某个局部场景最强，而是能在最多问题上做到“最不差”。
- 文章强调：**系统长期维护成本，几乎总是远高于最初开发时的不便**。成熟的工程师会优先考虑这一点。

##### 4. 不是反对新技术，而是要有引入机制

- 作者并不主张永远只用旧技术，否则极端情况下就会变成“只用 Java 做所有网站”，这同样荒谬。
- 关键是：**引入新技术必须是一个明确流程，而不是个人兴起**。
- 新技术会产生公司级影响，因此应该让整个公司或团队有可见度，而不是某个小组偷偷决定。

##### 5. 引入新技术前，应先问几个问题

- 首先要问：**不用新技术，能不能解决当前问题？**
  - 这个问题可以识别一种常见情况：所谓“问题”其实只是有人想用某项新技术。
  - 如果只是为了用而用，应直接否决。
- 其次要写清楚：现有技术栈为什么解决这个问题很困难、成本在哪里。
- 如果新技术与旧系统功能重叠，要明确迁移计划：
  - 不能让新旧系统长期并存、越堆越乱；
  - 应承诺迁移，并给出大致时间线。
- 这个流程并不复杂，本质上就是做几道“填空题”，然后开会讨论。

##### 6. 少用多语言、多框架，才能释放真正的工程能力

- 文章批评了“多语言编程/随意选工具”的幻想：看似给开发者自由，实际会带来沉重的日常运维负担。
- 真正的自由不是每个人都随便选技术，而是通过有意识的技术约束，让工程师能把精力放在更大的业务和系统问题上。
- 技术不应成为目的本身，最终目标是：**稳定交付、持续发版、解决真实问题**。

##### 7. 热门回复中的延伸观点

- 有回复提到，面试时会警惕“重度 vibe”的程序员，因为他们可能把很多自己并不理解的技术堆进简历；相反，坚持基础、传统编程方式的人，简历简单但可能更扎实。
- 也有人调侃：每次选新框架前，都要想想公司的“创新 token”还够不够花。

##### 总结

文章的核心不是“拒绝新技术”，而是提醒团队：**技术选型有长期成本，新技术要谨慎使用，成熟技术往往更适合支撑业务增长**。工程团队真正该创新的地方，通常不是数据库、框架或部署工具，而是公司的核心产品和业务价值。

## 口播总结（1）

### 2026-08-03 01:48:52

#### 这篇文章在讲什么

这篇文章来自 Dan McKinley，一位曾在 Etsy 工作的工程师。它讨论的核心问题是：技术选型不应该只追求新、快、酷，而应该优先选择那些成熟、可靠、失败模式清楚的“无聊技术”。

听完这篇总结，你会了解三个重点：什么是“创新 token”，为什么成熟技术往往更适合大多数公司，以及在什么条件下，团队才应该引入新技术。

#### 首先，理解“创新 token”

文章的第一个核心结论是：每家公司能承受的创新数量，其实是有限的。

作者把这种承受能力比作“创新 token”。你可以把它理解成公司手里有限的试错额度。文章打了一个比方：一家公司的创新 token，大约只有三个。这个数量并不是严格统计出来的数字，而是一个帮助团队思考的隐喻。它想提醒你，公司通常比自己以为的更缺少试错空间。

比如，你决定用 Node.js 来写网站，就花掉了一个 token。决定使用 MongoDB，又花掉一个。再选择一个存在时间不到一年的服务发现技术，还要再花掉一个。如果决定自己从头写数据库，那可能就不只是花掉一个 token，而是给自己制造了巨大的麻烦。

这些选择并不是绝对错误。对于一家 JavaScript 咨询公司，Node.js 可能很合理；对于一家数据库公司，自己研发数据库也许就是核心业务。但大多数公司并不是这样的公司。大多数公司真正要做的，是支付、电子商务，或者其他复杂的业务。

在这种情况下，把有限的注意力用来重新发明 SSH，或者同时维护一堆不成熟的基础设施，往往不是在创造竞争优势，而是在推迟真正重要的事情。

#### 接下来，什么叫“无聊技术”

第二个核心结论是：“无聊”不等于“糟糕”。

世界上确实有又无聊、又差劲的技术，这种技术当然不应该使用。但文章所说的“无聊技术”，指的是那些成熟、稳定、被大量使用，而且足够解决问题的工具。

作者举了很多例子，包括 MySQL、Postgres、PHP、Python、Memcached、Squid 和 Cron。它们可能不再让人兴奋，也不一定是某个领域最新的答案，但它们已经经过了大量实践检验。

成熟技术最大的价值，不只是功能被理解了，更重要的是，它的失败方式也被理解了。

这里有一个很重要的区别。技术选型中，总会有两类未知。

第一类叫“已知的未知”。意思是，我们知道自己还不了解某件事。比如，我们不知道一个数据库的 CPU 使用率达到百分之百时，会出现什么情况。

第二类叫“未知的未知”。意思是，我们甚至没有意识到某种问题可能存在。比如，直到系统出故障之后才发现，写入统计数据竟然会触发垃圾回收暂停，进而影响整个服务。

即使是存在了几十年的技术，也不可能完全没有未知。但对于刚出现不久的新技术来说，未知的未知通常要多得多。它可能会在上线很久之后，才暴露出团队从来没有预料过的风险。

所以，选择成熟技术，并不是因为它们永远最好，而是因为它们的能力边界、使用方法和常见故障，大多已经被别人踩过坑了。

#### 更重要的是，要进行全局优化

第三个核心结论是：技术选型不能只看某一个任务的局部最优，而要看整个公司的长期成本。

新增一种技术，看起来只是多了一个工具。但实际上，它会带来新的学习成本、部署方式、监控方法、升级流程，以及排查故障的人力成本。

比如，公司已经在使用 Ruby，这时再增加 Python，可能就需要两套开发习惯、两套依赖管理、两套运行环境和两套招聘标准。新增的复杂性，可能超过 Python 在某个局部任务上带来的好处。

奇怪的是，当人们比较 Python 和 Scala，或者比较 MySQL 和 Redis 时，常常会忘记这些整体成本，转而热烈讨论“这个任务最适合哪个工具”。

但现实中的工程师，面对的不是一张没有约束的白纸。现实中有运维，有报警，有版本升级，有值班，也有半夜处理故障的人。

因此，真正的目标不是为每一个问题找到一个理论上最好的工具，而是让整个公司长期稳定地运转。所谓“最佳工具”，很多时候不是在某个任务上拿第一的工具，而是在尽可能多的问题上都处于“最不差”的位置。

原因很简单：系统上线之后的长期维护成本，通常远远高于开发阶段的一点不方便。成熟而高产的开发者，往往会把这个长期成本看得更重，而不是只关注最初写代码时是否顺手。

#### 然后，新技术到底什么时候可以用

作者并不是反对所有新技术。

如果把“偏爱无聊技术”推到极端，最后可能会变成只用 Java，甚至试图只靠一种工具完成所有事情。那当然不合理。团队仍然需要一种方法，把新工具加入自己的工具箱。

关键在于，引入新技术应该被当作一个公司层面的决策，而不是某个工程师个人的兴趣项目。

第一步，是先问一个问题：能不能完全不增加新技术，只用现有技术解决当前问题？

这个问题看起来保守，但非常有用。因为有时候，所谓的技术问题，其实只是某个人想使用某个新工具。也就是说，工具的欲望被包装成了业务需求。如果答案只是“我就是想试试这个技术”，那这个选择就应该被否决。

而且，现有技术能做到的事情，往往比团队想象得更多。很多时候，答案并不是“绝对做不到”，而是“可以做到，只是会更困难一些”。如果团队觉得现有工具完全无法解决问题，也许只是还没有换一种方式思考。

当然，如果现有方案确实很昂贵、很复杂，也应该把原因写清楚。到底是哪一部分让当前技术栈难以解决问题？是性能不够，还是开发效率太低？是运维成本太高，还是可靠性不够？

把这些困难具体写出来，才能判断新技术究竟是在解决真实问题，还是只是在提供一种新鲜感。

#### 新技术引入，还要考虑迁移成本

接下来，还要区分新技术是“增加一种能力”，还是“替换已有系统”。

有些选择是增量式的。比如，公司还没有缓存，于是增加 Memcached，用来解决明确的缓存需求。这种变化相对容易界定。

但有些新技术会和现有系统重叠，甚至会取代旧系统。遇到这种情况，团队就不能只讨论“新系统多好”，还必须明确：旧系统什么时候迁移，谁来负责，迁移分几步完成。

作者建议，团队应该明确承诺迁移，并给出大致时间线。

这样做的目的，是避免旧系统和新系统长期并存，最后留下大量无人负责的残骸。否则，每一次局部选择看起来都很合理，最后却可能形成一套复杂、重复、难以维护的整体系统。

这个过程其实并不神秘，也不需要制造很大的官僚负担。团队只需要先完成几项简单的问题，然后开一次会议讨论。如果一项新技术能够完整回答这些问题，并且经得起公司层面的审视，那么就可以考虑把它加入技术栈。

#### 最后，真正的自由不是随便选工具

文章最后批评了一种常见想法：让每个开发者完全自由地选择工具，就一定能提高效率。

作者认为，这种想法至少是不成熟的。因为表面上的自由，可能会变成日常运维工作的堆积。每个人都可以选择自己最喜欢的语言、框架和数据库，但最后公司可能需要维护十几种技术体系，开发者也会被部署、监控、升级和故障处理压垮。

有意识地限制技术选择，反而可能给工程师带来真正的自由。因为当团队不用每天处理大量重复的基础设施问题时，才有精力去思考更大的产品和业务问题。

为技术而技术，常常只是一个看似万能的答案。真正成熟的工程文化，是把技术当作解决问题的手段，而不是把引入新技术本身当成成就。

#### 回顾几个最值得记住的结论

第一，公司的创新能力是有限的。把每一种新技术都当成一次创新 token，认真考虑它是否值得消耗这次试错机会。

第二，“无聊技术”不等于落后技术。MySQL、Postgres、Python、Cron 之所以有价值，是因为它们不仅功能成熟，失败模式也更容易预料。

第三，技术选型要做全局优化。不要只看某个任务上谁最强，还要计算学习、部署、监控、升级和长期运维的总成本。

第四，引入新技术之前，先问能不能用现有技术解决。如果确实要替换旧系统，就要明确迁移承诺和时间线。

第五，限制技术选择，并不是压制工程师，而是减少无谓的复杂性，让团队把真正的注意力用在更重要的问题上。

## 深度解读（1）

### 2026-09-18 00:33:18

#### “创新 Token”真正约束的不是技术，而是组织的认知带宽

“每家公司大约只有三个创新 Token”当然不是可计算的定律，但它提供了一个很实用的决策模型：**引入新技术，消耗的不只是开发时间，还包括整个组织理解、运维和处理意外的能力。**

Node.js、MongoDB 或新服务发现工具本身未必有问题。问题在于，如果公司的核心任务是支付、电商或内容服务，那么同时在语言、数据库和基础设施上冒险，就会让团队不得不一边探索业务，一边探索技术的失败边界。真正稀缺的不是选型自由，而是排查陌生故障、建立工具链和形成共同经验所需的注意力。

##### 成熟技术最重要的资产，是“知道它会怎么坏”

文章对“无聊技术”的解释比“稳定可靠”更准确：它们不仅能力边界清楚，**失败模式也已经被大量使用者暴露和记录**。

数据库 CPU 打满后性能如何下降，是“已知的未知”，可以压测；某个看似无关的统计功能触发 GC 停顿，则属于“未知的未知”，团队甚至不知道该监控什么。新技术最大的风险往往不是明显缺功能，而是这类尚未进入集体经验的问题更多。

因此，技术成熟度本质上是一种风险信息。文档、监控指标、故障案例、招聘供给和社区问答，都在降低组织面对异常时的搜索成本。反过来，AI 编程虽然显著降低了接入一个新框架、生成一套代码的成本，却没有同比降低长期维护成本；它甚至可能让团队更快堆入自己并不真正理解的依赖。热门回复对“重度 vibe 程序员”的担忧只是个人观察，但指出了同一风险：**代码产出速度与系统理解程度可能开始脱钩。**

##### “最佳工具”经常只是局部最优

文章最值得保留的判断，是把技术选型从单点性能比较提升为全局优化。某个工具可能最适合一项任务，但每增加一种语言、数据库或框架，公司就要新增部署方式、监控体系、安全补丁、招聘标准和故障处理知识。局部收益由一个项目享受，长期成本却由整个组织承担。

这与产品管理中的功能膨胀很相似，但共同机制并非“少就是好”，而是**新增选项会形成持续性的组合成本**。一个只在少数场景领先的技术，如果要求长期维持独立的知识和基础设施，整体上可能不如那个在多数任务中“足够好”的方案。

当然，“无聊”不等于陈旧，更不等于拒绝创新。如果现有方案无法满足关键约束，或者新技术直接构成公司的核心能力——例如数据库公司研发新存储引擎——花掉 Token 完全合理。关键是把风险留给真正需要差异化的地方，而不是在每一层都追求新颖。

##### 好的治理不是禁用，而是强迫团队说清代价

文章给出的流程至今仍然有效：先尝试用现有技术解决；写清困难究竟在哪里；如果新旧能力重叠，明确迁移范围和时间表；让决定具备公司层面的可见度。

这套机制的价值不是增加审批，而是识别两类常见伪需求：一类是“我想用，所以问题看起来需要它”；另一类是只计算引入收益，却不承担旧系统退出成本。对 AI 工具、模型供应商和 Agent 框架也应采用同样标准：不仅演示它能完成什么，还要回答数据如何治理、失败如何发现、供应商变化后如何替换，以及谁长期负责。

**真正成熟的技术文化，不是保守，而是有意识地分配陌生性。**值得追问的从来不是“这个技术够不够先进”，而是：它解决的问题是否重要到值得整个组织学习一种新的失败方式。
