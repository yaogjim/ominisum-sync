## 摘要（1）

### 2026-06-29 04:26:15

#### 综合总结：围绕“代理应该属于谁”的一场争论

这几条内容讨论的是当前 AI Agent 生态中的一个核心分歧：

> 大家都在热衷于构建各种 Agent 框架，但可能忽略了一个更重要的问题：  
> **未来用户到底是使用产品内置的 Agent，还是让自己的 Agent 去使用各种产品？**

可以概括为三种观点。

---

##### 1. dax 的观点：大家在造 Agent 框架，却忽视了产品里的 Agent

原推文大意是：

> 每个人都在开心地继续构建 Agent 框架，却忽视了他们使用的产品中的每一个 Agent。

这里的意思是，开发者和创业者们可能过度关注“如何构建通用 Agent 框架”，比如各种 agent runtime、workflow、tool calling、MCP、sandbox 等，而忽略了一个事实：

- 很多软件产品自己也会内置 Agent；
- 用户在实际使用产品时，可能并不会去配置一个外部 Agent；
- 产品方有动力把 Agent 直接集成到自己的产品体验中。

例如，一个 SaaS 产品可能不只是暴露 API 给外部 Agent 使用，而是直接在产品内部提供“AI 助手”，帮助用户完成操作。

---

##### 2. Dillon Mulroy 的观点：我不想用你的产品 Agent，我想让我的 Agent 高效使用你的产品

Dillon 的回应代表了另一种立场：

> 我不想使用你们产品自带的 Agent，我希望我的 Agent 能高效地使用你们的产品。

这是一种“用户拥有 Agent”的思路。

也就是说，用户可能不希望每打开一个产品都面对一个新的 AI 助手：

- Gmail 有一个 Agent；
- Notion 有一个 Agent；
- Linear 有一个 Agent；
- Slack 有一个 Agent；
- Figma 有一个 Agent；
- 银行、CRM、云平台、运营工具都有自己的 Agent。

这样会造成一个问题：

> 用户被迫和一堆彼此割裂的产品 Agent 打交道。

Dillon 更希望的是：

- 用户有一个或多个属于自己的 Agent；
- 这个 Agent 理解用户的偏好、上下文和长期目标；
- 各个产品只需要提供清晰、高效、可被 Agent 操作的接口；
- 用户的 Agent 去调用这些产品，完成任务。

简单说就是：

> 产品不要强迫我使用你的 AI 助手；  
> 你应该让我的 AI 助手能够顺利使用你的产品。

---

##### 3. 郭宇的观点：只为外部 Agent 构建 MCP，可能与软件厂商的根本利益冲突

郭宇进一步补充了一个更现实的商业视角。

他的核心观点是：

> 只为 Codex、Claude Code 等外部 Agent 构建 MCP，与软件开发商的根本利益是冲突的。

这里提到的 MCP，可以理解为一种让 AI Agent 连接外部工具和数据源的协议或接口。它的目标是让 Agent 能更方便地使用软件系统。

但郭宇认为，软件不只是“资源操作界面”，它还有更深层的价值：

1. **软件是用户体验的一部分**
   - 产品如何设计流程；
   - 如何呈现信息；
   - 如何降低风险；
   - 如何引导用户完成决策。

2. **软件是信任的载体**
   - 用户信任某个品牌；
   - 信任它的安全机制；
   - 信任它的操作确认流程；
   - 信任它不会随便帮自己做危险操作。

3. **软件是品牌的基础**
   - 如果用户完全通过外部 Agent 使用产品；
   - 产品本身的界面、交互、品牌感会被弱化；
   - 长期看，软件厂商可能沦为“底层工具供应商”。

因此，他认为软件厂商不一定愿意只做一个“给外部 Agent 调用的后端”。

更可能的未来是：

> 最终获胜的 Agent 会变得几乎免费，并且嵌入到所有软件之中。

也就是说，Agent 可能会成为软件的基础功能，而不是一个昂贵、独立、需要用户主动选择的产品。

---

#### 深入浅出解读

##### 一句话理解这场争论

这场讨论其实是在问：

> 未来 AI Agent 是“产品自带的助手”，还是“用户自己的助手”？

也可以换一种说法：

> 是软件控制 Agent，还是 Agent 控制软件？

---

#### 两种未来路径

##### 路径一：产品内置 Agent

这种模式下，每个产品都会有自己的 AI 助手。

例如：

- 在 Notion 里，你用 Notion AI 写文档；
- 在 Gmail 里，你用 Gmail AI 回邮件；
- 在 Salesforce 里，你用 Salesforce Agent 管客户；
- 在 GitHub 里，你用 Copilot 写代码；
- 在银行 App 里，你用银行自己的 AI 助手理财。

这种模式的优点是：

- 产品方更容易控制体验；
- 安全、权限、审计更好做；
- 用户不需要额外配置；
- Agent 更了解当前产品内部的数据结构和业务逻辑；
- 产品方可以通过 Agent 增强用户粘性。

但问题是：

- 用户需要面对很多个 Agent；
- 每个 Agent 只懂自己的产品；
- 跨产品任务很难完成；
- 用户的长期记忆和偏好被分散；
- 不同 Agent 之间可能体验割裂。

比如你想完成一个任务：

> “帮我根据客户最近的邮件，把 CRM 里的商机状态更新一下，然后在 Slack 通知销售团队，并生成一份下周跟进计划。”

这个任务涉及 Gmail、CRM、Slack、日历、文档等多个系统。  
如果每个产品只有自己的 Agent，它们之间协调起来就会很麻烦。

---

##### 路径二：用户自带 Agent

这种模式下，用户拥有一个通用 Agent。它连接各种软件，替用户完成任务。

例如你对自己的 Agent 说：

> “帮我注册一个 Telnyx 号码，完成配置，并把结果记录到项目文档里。”

Agent 就可以：

1. 打开浏览器；
2. 访问 Telnyx；
3. 注册账号；
4. 通过验证流程；
5. 申请号码；
6. 完成设置；
7. 把信息同步到其他工具。

这种模式的优点是：

- Agent 可以跨产品工作；
- 用户拥有统一入口；
- Agent 更了解用户长期目标；
- 可以自动串联多个工具；
- 软件之间的边界被弱化。

但它也有明显问题：

- 产品方可能不愿意被“外部 Agent”绕过；
- 安全风险更高；
- 权限管理复杂；
- 操作责任难以界定；
- 用户是否愿意维护自己的 Agent 仍然存疑；
- 普通用户可能不想配置复杂的工作流和工具权限。

评论里有人问：

> 主流非技术用户中，有多少人真的愿意维护自己的 Agent？

这是一个很现实的问题。

开发者可能喜欢“我有自己的 Agent，可以调用所有工具”。  
但普通用户可能只是想在产品里点一个按钮，然后让它完成任务。

---

#### 关键矛盾：软件厂商不想变成“API 管道”

这场争论背后的真正矛盾，是商业利益。

如果未来用户都通过自己的 Agent 使用产品，那么产品可能会被“去界面化”。

比如用户不再打开某个 SaaS 产品，而是对自己的 Agent 说：

> “帮我查一下销售数据。”  
> “帮我改一下项目状态。”  
> “帮我订一个会议室。”  
> “帮我取消这个服务。”

Agent 在后台调用各种产品的 API 或 MCP 接口，用户甚至不知道具体用了哪个产品。

这对用户来说很方便。

但对软件厂商来说，可能很危险：

- 用户不再直接接触产品界面；
- 品牌存在感下降；
- 产品差异化变弱；
- 用户忠诚度降低；
- 厂商更容易被替换；
- 软件变成“Agent 后面的工具层”。

这就是郭宇所说的：

> 软件不仅是为了方便用户操作资源，它还是信任和品牌的基础。

软件厂商不只是提供数据和功能，它还希望掌握用户关系。

---

#### MCP 的战略意义

这里的 MCP 可以简单理解为：

> 让 AI Agent 能够标准化调用外部工具的一套接口协议。

如果一个产品支持 MCP，Agent 就可以更容易地：

- 查询数据；
- 执行动作；
- 调用内部功能；
- 组合多个工具完成任务。

从开发者角度看，MCP 很有吸引力。  
因为它让 Agent 更容易变成一个真正的“数字员工”。

但从产品厂商角度看，MCP 是一把双刃剑。

##### 好处

- 可以让产品进入 Agent 生态；
- 提升自动化能力；
- 服务开发者和高级用户；
- 增加产品使用场景。

##### 风险

- 用户可能不再进入产品界面；
- 产品体验被外部 Agent 替代；
- 品牌关系被削弱；
- 产品变成可替换的工具节点；
- 厂商失去对关键流程的控制权。

所以郭宇才会说：

> 只为 Codex/Claude Code 等外部 Agent 构建 MCP，与软件开发商的根本利益是冲突的。

---

#### 为什么“几乎免费的 Agent”很重要？

郭宇最后提到：

> 最终获胜的代理会是几乎免费的代理，而几乎免费的代理，就有机会嵌入于所有软件之中。

这句话的意思是：

如果 Agent 的成本足够低，它就不会只作为一个单独的高价产品存在，而会变成每个软件里的基础能力。

就像今天的搜索框、通知系统、权限管理一样，未来 AI Agent 可能成为标准配置。

例如：

- 每个 CRM 都有销售 Agent；
- 每个 IDE 都有编程 Agent；
- 每个设计工具都有设计 Agent；
- 每个财务系统都有记账和审计 Agent；
- 每个电商后台都有运营 Agent；
- 每个客服系统都有客服 Agent。

当 Agent 足够便宜时，产品厂商没有理由不内置它。

这会让“产品内置 Agent”路线更有竞争力。

---

#### 这场争论的本质

##### 表面上看

大家在讨论：

- Agent 框架；
- MCP；
- 产品内置 AI；
- 外部 Agent 如何调用软件。

##### 实际上看

大家在争夺：

- 用户入口；
- 操作权限；
- 数据上下文；
- 品牌关系；
- 工作流控制权；
- 未来软件的交互范式。

谁掌握 Agent，谁就可能掌握用户的工作流。

---

#### 未来可能不是二选一

更可能的情况是，两种模式会长期共存。

##### 1. 普通用户更依赖产品内置 Agent

普通用户不想管理复杂权限，也不想配置自己的 Agent。  
他们更可能使用产品自带的 AI 功能。

比如：

- 在 Excel 里直接问数据；
- 在支付宝里让 AI 查账单；
- 在淘宝里让 AI 帮忙选商品；
- 在飞书里让 AI 总结会议。

##### 2. 高级用户和企业更需要自带 Agent

开发者、企业、自动化重度用户，则更希望有自己的 Agent。

因为他们需要：

- 跨系统操作；
- 定制工作流；
- 长期记忆；
- 多工具协同；
- 更高自动化程度。

例如企业内部可能会有自己的“公司 Agent”，连接：

- 邮件；
- 文档；
- 工单；
- CRM；
- ERP；
- 代码仓库；
- 数据仓库。

##### 3. 产品方会同时做两件事

成熟的软件厂商可能会采用混合策略：

- 一方面内置自己的 Agent，控制用户体验；
- 另一方面开放 MCP/API，让外部 Agent 可接入；
- 但会在关键权限、安全、付费和品牌环节保持控制。

也就是说：

> 厂商会开放，但不会完全放弃入口。

---

#### 核心结论

1. **Agent 生态正在从“怎么构建 Agent”转向“Agent 应该归谁所有”。**

2. **产品内置 Agent 有利于厂商控制体验、信任和品牌。**

3. **用户自带 Agent 有利于跨产品协作和长期个性化。**

4. **MCP 等协议能增强外部 Agent 的能力，但也可能削弱软件产品自身的入口价值。**

5. **软件厂商不会轻易只做外部 Agent 的工具接口，因为这会让它们被边缘化。**

6. **如果 Agent 成本持续下降，内置 Agent 会成为几乎所有软件的标配。**

7. **未来大概率是混合形态：产品有自己的 Agent，同时也允许用户的 Agent 在受控范围内接入。**

---

#### 可以用一个类比来理解

过去互联网时代，网站都希望用户直接访问自己的网站。

后来搜索引擎和浏览器成为入口。

再后来，移动时代 App 又重新夺回入口。

现在 Agent 时代的问题是：

> 未来用户是打开 App 使用功能，  
> 还是直接告诉 Agent：“帮我搞定”？  

如果是后者，那么 Agent 就可能成为新的超级入口。

所以这场讨论不是技术细节之争，而是关于下一代软件入口的争夺。
