### How AI Agents Work

Okay, so I've found myself explaining AI Agents to more people every week. Sometimes it's technical people who want to go deep, and now I'm finding, plenty of times, it's friends and family, who might not be technical, but still want to understand how AI Agents work at a deeper level.

This article is for people that might be a bit in the middle, you're not a software engineer coding every single day, but you're also not completely non-technical.

Oh and before I go any further, if you are a software engineer, and do want to dive deeper into how agents work, I'd suggest probably not reading this, and instead looking at the little open source AI Agent I built, here's the gh repo:

[https://github.com/morganlinton/SimpleAgent](https://github.com/morganlinton/SimpleAgent)

Personally, I think, if you know how to code, the best way to learn about things like agents, is to look at the code for a simple agent. But like I said, that's not who this article is meant for. If you're still reading, hopefully that means you're interested in learning more about how AI Agents work under-the-hood, but you're not someone who can just jump into a Github repo.

Since I've been explaining this so much lately, my goal here is to make it easy for everyone, technical or not, to understand how AI Agents work. And also hopefully, now I can point people to this article in the future when they ask me and save us both some time!

Okay, enough preamble, if you're still here, cool - let's dive in. I'm going to cover each core piece in the AI Agent puzzle, starting at the very beginning.

#### Tool Definitions &amp; Schemas

Before an AI Agent can do anything, it needs to know what tools it has. This is what tool definitions are for, they let the agent know, before it starts answering questions or running an agentic task, what kind of super powers it has.

It's important to note, this is different from what the model was trained on and already knows. A good example is - a basic LLM might know simple things, but once you ask it for say, the weather in Berkeley, CA, it has no idea.

And when models have no idea - they guess. We all have seen what happens when models guess, they hallucinate, and the answers often don't make a ton of sense. Tools allow models to take questions that they'd normally need to guess the answer, when answering, and gives them a way to actually answer them accurately.

A tool definition usually has three core parts:

1. Name - what's the tool called?
2. Description - a short description of what the tool does and when to use it
3. Parameter schema - what inputs to send the tool

Here's an example of a simple tool definition for a tool that helps an agent find the weather.

```json
{
  "name": "get_weather",
  "description": "Returns the current weather for a given city. Use this when the user asks about weather conditions.",
  "input_schema": {
    "type": "object",
    "properties": {
      "city": {
        "type": "string",
        "description": "The name of the city, e.g. 'Berkeley'"
      },
      "units": {
        "type": "string",
        "enum": ["celsius", "fahrenheit"],
        "description": "Temperature units to return"
      }
    },
    "required": ["city"]
  }
}
```

The important thing to understand about tool definitions is that they are passed to the model with every request along with the conversation.

But, and this is an important but, the model does not have to access the code for the tool, just the schema. It just needs to know it exists and when to use it.

#### Tool Call/LLM Request Cycle

Okay, so the model know the tool exists, now it needs to be able to use it. I'm getting ready to grab a Gordo burrito and then a hike in Tilden, now I really do need to know the weather in Berkeley.

Step 1 — The Request

Your application sends a request to the LLM. This request contains:

1. The system prompt (instructions about how the model should behave)
2. The conversation history (prior messages)
3. The tool definitions (the schemas from Part 1)
4. The user's latest message

Step 2 — The Model Decides

Now, it's the moment of truth, the model has to decide, can it answer this accurately without a tool, or would a tool make a difference?

If it decides to use a tool, it doesn't actually call anything yet. Instead, it returns a structured tool call object, essentially the model saying "I want to run this tool with these arguments" - here's an example:

```json
{
  "type": "tool_use",
  "name": "get_weather",
  "input": {
    "city": "Berkeley",
    "units": "fahrenheit"
  }
}
```

Now this is where I find a lot of people get confused, and I get it, it's a little confusing. The model isn't actually running any code or making network requests at this point. It just creates this text, in JSON usually, describing what it wants to do.

#### The Agent Runtime &amp; Orchestration Loop

Now here's where things get interesting. A single tool call is neat, but what makes something a true agent is the ability to chain multiple steps together, i.e. planning, acting, observing results, and deciding what to do next.

This is handled by the agent loop, sometimes called the orchestration loop.

```typescript
while not done:
    response = call_llm(conversation_history, tools)

    if response is final answer:
        return response

    if response contains tool_calls:
        for each tool_call:
            result = execute(tool_call)
            append result to conversation_history

        continue loop
```

The loop keeps running, calling the model, executing tools, feeding results back, until the model produces a response with no tool calls, signaling that it's done.

What makes this powerful is that the model can adapt mid-task. If it calls a search tool and the results suck, it might call a different tool, refine its query, or ask the user for clarification. The conversation history accumulates all of this context, and the model reasons over the full picture each time.

Okay, but let's talk about memory, because everyone has experienced those weird moments where their trusty agent seems to have amnesia.

Each call to the LLM is stateless, i.e. the model has no memory between calls on its own. It's the runtime that is responsible for maintaining the conversation thread and passing it in full with every request. As agent tasks grow longer, this history can get large, and production runtimes often have to manage context window limits, summarize older steps, or use external memory stores.

This is also why frontier model companies are always increasing their context window, it makes life easier for the runtime, and helps your little AI Agent buddy remember more.

#### Real API Execution &amp; the HTTP Layer

Now we're at my personal favorite part - this is where the action happens. When a tool actually runs, it typically does one of a few things: calls an external API, reads/writes to a database, executes code, or interacts with a filesystem.

As a simple(ish) example - here's what happens at the HTTP layer for a typical API call.

```python
def get_weather(city: str, units: str = "celsius") -> dict:
    response = requests.get(
        "https://api.weather.com/v1/current",
        params={"q": city, "units": units},
        headers={"Authorization": f"Bearer {API_KEY}"}
    )
    response.raise_for_status()
    return response.json()
```

Don't worry if you don't understand the code above. This is just normal application code, in this case, a simple Python function that calls a weather API and gets the weather.

The key concept to understand here is that it's in this execution layer that your tool actually performs the function it's designed to do.

Once it runs, the results are fed back to the model which will reason over them, and decide if it needs to call more tools, or if it's ready to return the response to the user.

The orchestration loop is what repeats this cycle until the task is complete.

And that's it, fin - done. If you read all of this, you now know how an AI Agent works. Thanks for reading!

### 2026-03-17 06:41:13

这篇文章的核心是在用通俗方式解释：AI Agent并不是“自己会做事的神秘黑盒”，而是“模型 + 工具定义 + 运行时循环 + 实际执行层”共同配合的结果。真正让 Agent 有用的，不是模型单独思考，而是它能在需要时调用外部工具，并根据结果继续行动。

- 第一部分：文章面向谁、想解决什么
  - 作者写这篇文章，是因为越来越多人在问“AI Agent到底怎么工作”，包括技术人，也包括家人朋友这类非程序员。
  - 目标读者是“有一点技术理解，但不是天天写代码的人”。
  - 作者还提到：如果是软件工程师，最好的学习方式其实是直接看代码，并给出了自己的开源示例 `SimpleAgent` 作为更深入的入口。

- 第二部分：工具定义与 Schema 是 Agent 的起点
  - Agent在开始工作前，必须先知道“自己有哪些工具可用”，这就是工具定义（tool definitions）的作用。
  - 工具定义通常包含3个核心部分：
    - 名称（Name）
    - 描述（Description）
    - 参数结构（Parameter schema）
  - 文章用天气工具举例：`get_weather` 可以接收 `city` 和 `units`，其中 `units` 只能是 `celsius` 或 `fahrenheit`，且 `city` 是必填项。
  - 关键点是：模型每次请求都会收到这些工具定义，但它并不需要看到工具背后的实际代码，只要知道“这个工具存在、何时该用、需要什么参数”即可。
  - 这样做的意义是避免模型“靠猜回答”。比如问“Berkeley, CA现在天气如何”，普通LLM本身并不知道实时天气，若不调用工具，就容易产生幻觉。

- 第三部分：模型如何发起工具调用
  - 一次典型请求会把4类信息一起发给LLM：
    - system prompt（行为规则）
    - 对话历史
    - 工具定义
    - 用户最新问题
  - 接着模型要做判断：自己能否可靠回答，还是应该调用工具。
  - 如果决定调用工具，它不会直接执行代码，而是先返回一个结构化的“工具调用对象”。
  - 文章中的示例是：
    - 调用 `get_weather`
    - 参数为 `city = Berkeley`
    - `units = fahrenheit`
  - 这里最容易混淆的一点是：模型此时只是“提出要调用什么工具、传什么参数”，本身并没有真的发网络请求，也没有执行任何程序。

- 第四部分：真正让它像 Agent 的，是编排循环（Orchestration Loop）
  - 作者强调：单次工具调用还不算真正的 Agent，真正的 Agent能力来自“多步循环”：
    - 规划
    - 行动
    - 观察结果
    - 再决定下一步
  - 文中给了一个简化逻辑：只要任务没完成，就不断重复
    - 调用LLM
    - 如果是最终答案就返回
    - 如果包含工具调用，就执行工具
    - 再把结果追加进对话历史，继续下一轮
  - 这也是 Agent强大的原因：它可以中途调整策略。
  - 例如，若先调用搜索工具但结果很差，它可以：
    - 换另一个工具
    - 优化查询词
    - 反过来向用户要更多信息

- 第五部分：所谓“记忆”，本质上来自运行时维护上下文
  - 文章特别解释了很多人困惑的“Agent为什么有时像失忆”。
  - 原因是：每次LLM调用本身都是无状态（stateless）的，模型不会自动记住上一次发生了什么。
  - 真正负责“记忆”的，是运行时（runtime）：它要把完整对话线程持续保存，并在每次请求时重新传给模型。
  - 当任务变长后，上下文会越来越大，所以生产环境往往要处理：
    - 上下文窗口限制
    - 对旧内容做摘要
    - 使用外部记忆存储
  - 作者也提到，这就是为什么前沿模型公司都在不断增大 context window——窗口越大，Agent越容易“记住更多事”。

- 第六部分：工具真正执行时，会落到 API / 数据库 / 文件系统等现实世界
  - 模型决定要用工具之后，真正的执行发生在“执行层”。
  - 文章列出常见执行方式：
    - 调用外部 API
    - 读写数据库
    - 执行代码
    - 操作文件系统
  - 作者用天气 API 举例：一个 Python 函数会向 `https://api.weather.com/v1/current` 发起 HTTP 请求，并附带城市、单位和认证信息，再把返回结果转成 JSON。
  - 重点不是代码细节，而是理解：工具在这一层才真正完成任务；执行结果随后再返回给模型，模型再判断是否还要继续调用别的工具，还是已经可以向用户输出最终答案。

- 结尾总结
  - 文章最后把 AI Agent归纳为一个完整闭环：
    - 先告诉模型有哪些工具
    - 模型决定何时调用工具
    - 运行时负责执行并维护上下文
    - 执行结果再反馈给模型，直到任务完成
  - 简单说，Agent不是“模型突然变聪明了”，而是模型在一个循环系统里，学会了借助工具一步步完成任务。
