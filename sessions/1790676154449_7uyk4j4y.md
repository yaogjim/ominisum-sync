## 分析要点

- **核心高价值点**：不能把每用户分配的虚拟CPU直接等同于物理CPU需求；应先估算峰值并发，再考虑工作负载的CPU占用与超售。
- **留存建议**：保留其容量估算框架，具体数值仅作情景假设（区分日活、峰值并发、物理资源与推理负载的估算方法可复用。）

**知识要点**

- 日活用户数需结合每日活跃时长、峰均比和容量余量，才能估算峰值同时运行的沙箱数。
- CPU、内存与模型推理应分别建模：等待中的沙箱可能少用CPU，但仍需保留内存状态。
- 推理功率对每用户每日事件数及单次事件能耗敏感，不能仅凭用户数确定。

**行动项**

- 估算智能体服务容量时，分别列出活跃时长、峰均比、CPU占用率、内存用量和推理调用量的假设。
- 对每日推理事件数进行敏感性分析，并用实际调用数据校准。

**Freda Duan**

一个旨在建立服务 1 亿日活跃用户所需基础设施的初步尝试 @Muse

粗略结论是：

在基准情形下，服务 1 亿日活跃用户需要 1 吉瓦的电力，其中只有\~0.1 吉瓦来自 CPU/虚拟机层。取决于一个 Muse 日活跃用户每天产生的推理等效模型调用次数，3-4 吉瓦完全有可能。也许这就是为什么 @Meta  
据传明年将增加 7-10 吉瓦的计算能力。

沙箱层=不到 10 亿美元的 CPU 内容和\~20 亿美元的 DRAM 内容， 这比许多人预期的要小得多。

很多动态假设。欢迎所有反馈/反对意见。

\------  
Muse 背后有两种截然不同的基础设施。

1\. Muse VM / 沙箱基础设施

每个用户 2 个 vCPU、\~8 GB RAM 和 \~100 GB 持久逻辑存储。 [https://starkinsider.com/2026/09/meta-muse-specs-what-it-runs-on.html…](https://starkinsider.com/2026/09/meta-muse-specs-what-it-runs-on.html)

2\. Muse Spark 推理

模型推理通过 Meta 的外部推理基础设施进行。 [https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse…](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)  
\------

1/ 沙箱基础设施

A. CPU  
第一个错误是假设1亿日活跃用户意味着有1亿台虚拟机同时活跃地消耗计算资源。

假设 Muse 的平均日活跃用户的智能体每天活跃工作两小时。

1亿用户 \* 2小时 / 24小时 = \~8百万平均同时活跃虚拟机

Meta 显然不能仅按日均值进行配置。使用量将集中在清醒时段，并且具有突发性。

假设峰值与平均值之比为2.5倍：

8百万 \* 2.5 = \~2千万峰值活跃虚拟机

然后增加大约 20% 的容量余量：\~25M 已配置的实时 VM。因此，基本假设实际上是 Meta 需要足够的基础设施来支持大约 25% 的 DAU 同时在线。

下一个重要区别是虚拟 CPU 分配与物理 CPU 需求之间的差异。Agent 沙箱特别适合 CPU 超售。它们会花大量时间等待。在这些时间段内，VM 可能仍然存活，但几乎不使用 CPU。

DeepSeek 最近发布的 DSec 基础设施提供了一个有用的基准。其生产级 agent 沙箱平台在 \~160 个节点上运行约 30,000 个物理 CPU 核心和 250TB DRAM，峰值并发超过 380,000 个沙箱。 [https://arxiv.org/abs/2609.22978](https://arxiv.org/abs/2609.22978) DSec 还展示了在约 800 个 microVM/节点下的稳定运行。每个节点大约有 188 个物理核心：188 个物理核心 / 800 个 microVM = \~0.23 个物理核心/实时 VM。

DeepSeek 显然是效率之王。Muse 的数字可能是每个实时 VM 0.3-0.75 个物理核心，或者假设基准情形为每个实时 VM 0.5 个物理核心。这相当于每个物理 CPU 核心大约同时运行两个 Muse VM。

使用基本假设：2500 万台活跃虚拟机 \* 每台虚拟机 0.5 个物理核心 = 1250 万个物理 CPU 核心。

在 256 核 CPU 上：1250 万核心 / 每 CPU 256 核心 = \~5 万颗 CPU；或者在 192 核 CPU 上，那将是 6.5 万颗 CPU。

按照当前的公开定价，那就是\~8亿美元。

B. DRAM  
CPU 可以积极超售，因为等待中的虚拟机几乎不消耗 CPU。内存则更难超售，因为运行中的虚拟机仍需保留其工作状态。

Muse 向用户环境暴露大约 8GB 的 RAM，但观察到的一个实例在测量时实际仅使用了约 3GB。

2500 万台运行中的虚拟机 \* 3GB = 75PB 物理 DRAM，称之为 \~75-100PB 物理 DRAM 感觉是一个合理的基础范围。

按照当前的公开定价，这相当于 \~20 亿美元。

C. 沙盒算力  
\~在 1 亿日活跃用户下，整个 Muse 沙盒/虚拟机层需要 0.1 GW。

\------

2/ 推理  
Muse 的个人计算机在本地执行工具并存储状态，但实际模型运行在独立的推理基础设施上。Meta 的 Muse 架构

每次推理事件的能耗  
Microsoft 的 2026 年研究估计，经过优化的前沿规模推理每次普通查询的中位能耗约为：0.31Wh

但一次 token 数量约为 15 倍的长推理查询，其能耗约为 13 倍，即每次长推理查询约为：4Wh

该研究特别指出，推理和代理工作负载的能耗显著更高。  
[https://microsoft.com/en-us/research/publication/energy-use-of-ai-inference-efficiency-pathways-and-test-time-scaling/…](https://microsoft.com/en-us/research/publication/energy-use-of-ai-inference-efficiency-pathways-and-test-time-scaling/)

对每 DAU 每日推理等效事件数的敏感性分析

假设每个活跃 @Muse  
用户每天产生相当于 50 次重型推理事件的量。

每次 5Wh 时：

1 亿用户 \* 每天 50 次事件 \* 5Wh = 25GWh/天

25GWh/天 / 24 小时 = \~1.0GW 平均功率

因此仅推理就可能需要：\~1-2GW 的平均功率

一个 3-4GW 的 Muse 完全有可能。也许这就是为什么 @Meta  
据传明年要增加 7-10GW 的计算能力。

\------  
关于 Muse 的流行说法是，给每个用户 2 个 vCPU 和 8GB 内存会产生巨大的 CPU 需求。但朴素的计算严重夸大了 CPU 需求，因为它把逻辑 VM 分配当成了专用物理基础设施。

更有趣的结论是：消费者代理可能是 CPU 和传统 DRAM 的一个重要新需求驱动力，但推理仍然是真正的计算瓶颈。而且随着代理做更多工作、运行更长的轨迹并越来越多地衍生其他代理，推理需求可以比用户数量本身增长得快得多。
