## 通俗精炼（1）

### 2026-05-04 13:34:13

#### Claude 写代码，Codex 做 Review：AI 编程的分工思路

##### 核心观点

作者分享了一种 AI 编程工作流：**让 Claude Opus 负责编写代码，让 Codex 负责代码评审**。

关键在于：不同 AI 模型各有优势，与其让一个模型包办全部流程，不如让它们形成分工协作。

##### Codex Review 的提示词重点

作者给 Codex 的角色设定是：  
**你正在审查另一个 AI 助手写的代码，任务是独立验证正确性。**

重点检查四类问题：

1. 逻辑是否正确  
2. 是否遗漏边缘情况  
3. 是否存在安全问题  
4. 是否符合需求要求  

同时特别强调：

> 不要建议重构、重命名、样式修改或添加注释，只报告缺陷、逻辑错误和安全问题。

##### 为什么最后一句很重要

作者认为最后这句提示词非常关键。

如果不明确限制，Codex 可能会把“代码评审”理解成“代码重构”，开始提出大量风格、命名、结构优化建议，反而偏离真正目的。

这里的核心是：**Review 不是美化代码，而是发现真正的问题。**

##### 热门回复反映的趋势

评论区主要有三类观点：

###### 1. 有人转向 Codex 写代码

有用户认为 Claude Opus 小 bug 较多，新项目开发已切换到 Codex。

这说明不同开发者对模型能力的体感差异较大，尤其在稳定性和 bug 率上。

###### 2. 多模型协作正在兴起

有人提到让 Codex、Gemini、Claude 组成一个“委员会”，通过多轮辩论得出结论。

作者回应认为这个方向有趣，但关键是：  
**要给不同模型分配不同审查角度，否则容易互相附和。**

###### 3. 工具化、自动化需求明显

也有人推荐工具，将 Claude Code 和 Codex 结合，实现从生成代码到代码评审的自动闭环，减少人工在不同工具间搬运信息。

##### 产品视角总结

这条内容背后反映的是 AI 编程工作流的一个重要演进：

> 从“单模型全能”走向“多模型分工协作”。

更成熟的 AI 开发流程可能不是依赖一个最强模型，而是：

- 一个模型负责实现
- 一个模型负责审查
- 一个模型负责安全
- 一个模型负责需求一致性
- 工具负责自动编排流程

##### 一句话总结

**Claude 负责产出，Codex 负责挑错；关键不是让 AI 多提建议，而是让它只找真正影响正确性、安全性和需求符合度的问题。**

## 结构化（1）

### 2026-05-04 13:41:35

##### 主旨概括

Leo 分享了一种 AI 编程协作流程：**让 Claude Opus 负责写代码，让 Codex 负责代码评审**。关键在于给 Codex 明确限定评审范围，避免它把 review 变成重构建议。

---

##### 1. 核心做法：Claude 写代码，Codex 做评审

- Leo 的工作流是：
  - **Claude Opus**：负责生成代码。
  - **Codex**：负责独立审查代码正确性。
- 他给 Codex 的提示词重点是让它从以下角度检查：
  1. 逻辑是否正确？
  2. 是否遗漏边缘情况？
  3. 是否存在安全问题？
  4. 是否符合原始需求？

---

##### 2. 提示词关键点：只报告问题，不做重构

Leo 特别强调提示词最后一句很重要：

> 请勿建议重构、重命名、样式修改或添加注释。仅报告缺陷、逻辑错误和安全问题。

- 如果不加这句话，Codex 可能会把代码评审理解成“帮忙优化代码”。
- 结果可能出现大量重构、命名、格式、注释类建议，偏离真正的 review 目标。
- Leo 的重点是：**让 Codex 专注发现 bug、逻辑漏洞和安全风险，而不是做代码美化。**

---

##### 3. 热门回复：不同用户的 AI 编程实践

###### 3.1 有人认为 Claude Opus 小 bug 较多

用户 @段少DaDalus 表示：

- **Opus 4.6 小 bug 太多**，用起来比较难受。
- 他在新项目中已经把开发模型切换成 **Codex 5.3**。

Leo 回复说：

- 如果用 Codex 开发，是否还需要额外 review？
- 他自己因为长期使用 Claude 体系，已经越来越顺手。
- 迁移到其他系统的成本变高。

---

###### 3.2 有人尝试多模型“委员会”评审

用户 @你瞅啥 分享：

- 他写了一个 skill，让：
  - Codex
  - Gemini
  - Claude  
  组成一个“committee”，通过一轮辩论得出结论。

Leo 认为这个思路有意思，并补充经验：

- 他试过类似方法。
- 关键是要给每个模型分配**不同审查角度**。
- 否则多个模型容易互相附和，无法产生真正有效的分歧和审查。

---

###### 3.3 有人推荐自动化工具 cc-review

用户 @Hao ∞ 浩哥 推荐了自己的工具：

- 工具地址：`github.com/haohappy/multi…`
- 目标是结合 **Claude Code** 和 **Codex** 的优势。
- 它试图把 AI 代码审查变成自动闭环：
  - Claude Code 生成代码；
  - Codex 进行 review；
  - 自动处理反馈和修改流程。

传统流程中，开发者需要手动在 Claude Code 和 Codex 之间复制计划、代码和反馈，容易繁琐且遗漏；该工具希望减少这些人工搬运。

---

##### 4. 总结启发

- AI 写代码时，可以采用“**一个模型生成，另一个模型审查**”的分工方式，提高可靠性。
- 做 AI 代码评审时，提示词要明确边界：
  - 只查缺陷；
  - 不提风格；
  - 不做重构。
- 多模型协作有潜力，但要避免模型之间互相附和，最好给不同模型设定不同审查角色。
