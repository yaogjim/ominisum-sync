## 分析要点

- **核心高价值点**：文章用实测明确了配置选择原则：单用户或共享长前缀优先DFlash2与前缀缓存，多并发独立请求则优先MTP或批处理模式，而不是只追求最高单流速度。
- **留存建议**：重点精读并长期存档，作为消费级显卡大模型部署、调优与验证的参考实现（提供完整代码、补丁、部署脚本、可复现基准、质量测试和大量故障边界，并形成了按并发量、上下文长度及共享模式选择配置的实用方法。）

**知识要点**

- 推测解码的收益取决于并发度和工作负载：DFlash2提高单流速度，但更大的循环状态页会降低可驻留请求数，MTP在较高并发下更稳定。
- 共享前缀与前缀缓存可同时复用注意力KV和循环状态，能显著降低长文档多轮请求的首词延迟；独立长提示则主要受预填充吞吐限制。
- 可靠性能比较需要固定功耗、采样方式、提示与输出长度、KV池大小、缓存状态和运行轮次，并分别报告解码速率、端到端吞吐、TTFT与质量指标。

**行动项**

- 使用Docker单卡启动默认配置，先设置API密钥，再运行verify.sh确认补丁、量化模型、注意力后端和KV池状态。
- 依据负载选择模式：单用户或共享文档使用SPEC=dflash2与PREFIX\_CACHE=1，多用户独立请求使用SPEC=mtp或batch模式。
- 在目标机器上运行统一基准、并发阶梯、质量测试和残差扫描，并固定250W功耗与KV\_MEM后再比较配置。

Serving setup for [Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B) on a single 24 GB consumer GPU with vLLM — 150k token context and an OpenAI-compatible API with key auth, in two ready-made modes.

#### Quick start

The image is prebuilt and pushed to [ghcr.io](https://github.com/syv-ai/qwen38-27b-rtx3090/pkgs/container/qwen38-27b-rtx3090) on every commit — the build applies all `patches/` and runs `verify.sh` as its gate, so `latest` is always the current stack. The first start pulls it (9.5 GB), downloads and requantizes the model (\~20 GB, once, into `./models`), and serves on port 18020. Pick a mode — one GPU serves one at a time:

```
git clone https://github.com/syv-ai/qwen38-27b-rtx3090 && cd qwen38-27b-rtx3090

cp .env.example .env                 # Linux / WSL
# PowerShell: Copy-Item .env.example .env

docker compose --profile single up -d    # one or a few people chatting
docker compose --profile batch  up -d    # API backend, many concurrent requests
```

The example uses the recommended single-user `SPEC=dflash2` profile. If Docker Desktop is using WSL2, keep `VLLM_WSL2_ENABLE_PIN_MEMORY=1` enabled in `.env` or the V2 runner will abort with `RuntimeError: UVA is not available`. The example leaves API-key authentication disabled for local-only use; set `VLLM_API_KEY` before exposing the server beyond this machine.

Both modes share one install — the mode is just which launch script you run. Speculation wins below \~8 concurrent users on short prompts, plain batching above; on long independent sessions the crossover is much earlier, because a speculating request reserves recurrent-state pages the pool has few of — the concurrency paragraph under "DFlash2 at 240k" has the measurement. Numbers are `vllm bench serve` on an RTX 3090 at a 250 W power limit. If the card is yours alone, the fastest configuration is three environment variables away:If you are the only user.

Prefill is a separate budget from either: \~1,810 tok/s at 1k inputs in batch mode, and in single-user mode \~1,440 tok/s stock or **\~1,850-1,940 with `INT8_ACT=int8`** (1,423 at 51k in), measured on the seeded benchmark protocol (full matrix; older published prefill rows came from an unseeded harness that let the prefix cache contaminate the numbers, and are not comparable). How each number was won:docs/optimizations.md.

The server listens on `0.0.0.0` and is unauthenticated unless you give it a key. For anything past your own machine, add one first — everything reads it from`.env` or `api_key.txt`, and nothing needs it otherwise:

```
echo "VLLM_API_KEY=$(openssl rand -hex 24)" > .env
```

No compose, no clone — plain Docker runs the same image with one command and prepares the model itself on the first boot (into a named volume, so it survives container replacement):

```
docker run -d --name qwen --gpus all --ipc=host -p 18020:18020 \
  -v qwen-models:/app/models -v qwen-cache:/cache \
  --restart unless-stopped ghcr.io/syv-ai/qwen38-27b-rtx3090:latest
```

`batch` after the image name is the other mode, and the knobs compose reads from `.env` become `-e` flags (`-e VLLM_API_KEY=...`, `-e SPEC=dflash2`,...) — docs/docker.md has the mapping.

Or by hand in a venv (same steps: model download, requantization, vLLM patches, `verify.sh`) — see Setup.

The command above starts the conservative default — MTP speculation, 8 request slots, 64k context, 120 tok/s greedy at C1. Two settings are worth more than every other knob in this repo put together, and a third is worth a great deal on one particular workload:

```
printf 'SPEC=dflash2\nPREFIX_CACHE=1\n' >> .env
# add DFLASH_TOKENS=15 if your answers quote your prompts — see below
docker compose --profile single up -d
```

or, in the venv install:

```
venv/bin/python prepare/fetch_dflash2.py   # once, 1.2 GB (Docker's prepare step does it for you)
SPEC=dflash2 PREFIX_CACHE=1 bash single-user/start_qwen.sh
```

`SPEC=dflash2` swaps Qwen's MTP head for the DFlash2 block drafter: 7 tokens proposed in one pass instead of 4 chained ones. `DFLASH_TOKENS=15` then lets the target verify 16 tokens per step — the drafter still proposes the 7 it was trained for, and the remaining positions are filled from the request's own context, which costs nothing to draft and is exactly right whenever the answer quotes the prompt. `PREFIX_CACHE=1` keeps the document you already sent, both its attention KV and its recurrent state. `VLLM_DFLASH2_CHAIN=1` adds drafter-free n-gram chains on top ([#38](https://github.com/syv-ai/qwen38-27b-rtx3090/issues/38), ported from @Dmtrii-tesla's fork with permission): while a request keeps reproducing its context, whole verify blocks come from history alone and the drafter's forward and graph replay are skipped until the first rejected token — +7% on the copy cell here (256.9 → 276 tok/s at `DFLASH_TOKENS=7`), flat on prose, greedy requests only by default (`patches/dflash2-ngram-chains.patch` explains why sampling keeps the drafter). Off by default.

\* drafting from the context only exists in `SPEC=dflash2`. The two right columns are one server session, where run-to-run greedy divergence is ±3-5%; reproduce them with `venv/bin/python bench/labd_bench.py <tag> --ctx 20000`.

`PREFIX_CACHE=1` is orthogonal to the other two and worth as much again in a chat client: a second turn against that same 25k-token document takes 0.56 s to first token instead of 22.4 s, with the answers unchanged token for token.

**Read that table by column, not by its last cell.**`SPEC=dflash2` is the upgrade for everyone; `DFLASH_TOKENS=15` is for one workload. On chat it is worth 1%, because the eight positions past the drafter's own block are filled from the prompt and a chat answer does not quote the prompt — measured over `bench/prompts_real.jsonl`, positions 7-14 take **72 of 11,069 accepted tokens (0.65%)**, and @changtimwu measured exactly zero for them on a TP=2 box in [#22](https://github.com/syv-ai/qwen38-27b-rtx3090/issues/22). What you pay for that 1% is half the request slots and 8k of context, because a 16-token verify block doubles the recurrent-state page every resident request holds (1.66 GiB against 0.88 by the gotcha-33 fit). So: set it if you are quoting documents or applying edits, where it is worth 47%, and leave it at the default 7 for a chat or agentic client. `DRAFT_TOKENS` / `DFLASH_TOKENS` is one variable you can flip per service.

All of it is lossless: speculative decoding samples the same distribution as no speculation at all, the prefix cache resumes recurrent state rather than approximating it, and GSM8K reads 96.0-96.5% across the three columns.`SPEC=dflash2` is a one-user mode either way (see concurrency). Context for the GSM8K column: every configuration this repo already ships reads 95.0-96.5% on the same 200-question harness (docs/quality.md), and 95.0% is the batch-mode default. 95.2% at n=600 (±0.9 points) therefore sits inside the band rather than below it — which is the useful comparison, since this mode inherits KVarN's lossy 4/2-bit cache and should be judged against the other lossy configurations rather than against bf16. Repeat runs of the reproduction check on bare metal are bit-identical (same step count, same 1,150 characters), which is the property that was missing before `PIECEWISE` — see below.

One caveat to the "all of it is lossless" paragraph above: the speculation here is still exact, but this mode inherits KVarN's 4/2-bit KV cache, which is lossy — the same trade `CTX=huge` already makes (deep-needle retrieval passes at 200k).

The WSL2 column's \~20% deficit is a WSL2 tax, not a Windows tax, and leaving WSL for native Windows does not recover it: the same contributor ran `aivrar/vllm-windows-build` (0.27.1, 18 of 19 patches apply after a CRLF→LF pass) on the same box and measured native Windows *slower* than WSL2 — 66.0 vs 76.2 tok/s across the task mix, a 4.4× longer warm boot, and the same WDDM paging behavior underneath ([#25](https://github.com/syv-ai/qwen38-27b-rtx3090/issues/25)). The bare-metal column is reachable from a Windows box only by putting Linux on the metal.

**On WSL2, every `SPEC=dflash2` profile needs `VLLM_WSL2_ENABLE_PIN_MEMORY=1`** — not just `CTX=huge`. The drafter's architecture forces vLLM's V2 model runner (`_is_dflash2_draft()` in `config/vllm.py`), the V2 runner allocates UVA buffers before the weights load, and vLLM leaves pinned memory off by default under WSL2, so a clean venv aborts with `RuntimeError: UVA is not available` before it prints anything model-shaped. Those buffers work fine on the paravirt driver. Note the name: `VLLM_WSL_PIN_MEMORY` is **not** a vLLM variable and setting it does nothing — this README named it for 22 minutes on 2026-08-21 (`589daae`, fixed in `27f51fa`), so a tree cloned in that window will have it.

**On WSL2 the usable dedicated memory is about half a gigabyte less than the same card on bare metal, and the shipped `SPEC=dflash2` boot sits about 50 MiB under it.** Anything larger (a wider verify block, a bigger drafter, a raised pin, a boot that recompiles a graph) runs two to six times slower instead of failing, and the log does not say so; `nvidia-smi` looks the same either way. Gotcha 58 has the counters to read, the four costs that turned out to be this, and the profile that gives it room (`KV_MEM=3000000000 DFLASH_MAX_LEN=8192`, free for the shipped head at width 7).

**Running a DSpark drafter.** vLLM 0.28.0 can serve RadixArk/Qwen3.8-27B-DSpark (bf16, seven drafts per step like the shipped head) once two things are in place: `patches/dspark-draft-quant-config.patch` (the loader refuses a bf16 drafter beside the quantized target without it), and a copy of the checkpoint whose `config.json` names the architecture `Qwen3DSparkModel` instead of `DSparkDraftModel` (the registry maps the published name to the DeepSeek V4 class; the weights are unchanged, so hard-link the safetensors). Then `DRAFT=/path/to/that/copy DRAFT_METHOD=dspark KV_MEM=3000000000 DFLASH_MAX_LEN=8192 SPEC=dflash2 CTX=fast bash single-user/start_qwen.sh`. It serves, and loses to the shipped head on the same requests: 3.19 against 3.77 tokens per step (accepted drafts plus the bonus token) and 115 against 160 tok/s on a 4090, 3.37 against 3.83 and 114 against 150 on a 3090 (issue #25, items 15 and 16). Documented so nobody re-derives the two errors, not as a recommendation.

One knob this mode used to set for you, and now sets only for MTP:`cudagraph_mode=PIECEWISE`. Prefix caching and a *captured* (FULL) verify step did not mix on this path. On WSL2 that showed up as acceptance collapsing to about one token per step; on bare metal it also **corrupted the output** — special-token ids leaking into the stream, 1 of 1,176 characters matching the source instead of all of them. It is the capture rather than the drafter: eager is clean, `LOOKUP=0` is not, forcing a fixed verify-block length is not, and PIECEWISE — which keeps the compiled graphs and leaves only the multi-query verify uncaptured — restored both the speed and the correctness on both machines.

`dflash2` has its FULL graphs back (`a75ee4b` fixed the residue, `b356e31` then swept **all 128** residues under FULL with 0 broken), so at HEAD `SPEC=dflash2 CTX=huge PREFIX_CACHE=1` runs captured. `SPEC=mtp CTX=huge` still forces PIECEWISE, and that one is a correctness constraint rather than a preference: under FULL it breaks at one prompt length in 128 and nobody has fixed it. Either way prefix caching stays on, which is what the mode is for — turn 2 over a cached 100k document costs 4.7 s against 169 s cold.

`CUDAGRAPH_MODE=FULL_AND_PIECEWISE` overrides the MTP line for anyone hunting the root cause. Treat that as unsafe rather than merely slower.

Two limits worth knowing before you point this at anything: what it does with more than one user, and what the long verify block costs.

**It is a one-stream mode, and the limit is the pool rather than `MAX_SEQS`.** An earlier version of this paragraph said the knob was the seat count and that `MAX_SEQS=8` lifts it. It does not, and @mjungnickel18 was right to push back in [#25](https://github.com/syv-ai/qwen38-27b-rtx3090/issues/25). A *resident* request reserves 1+k = 8 recurrent-state slots — **15.8% of the 69,758-token `CTX=fast` pool**, \~0.82 GiB of its pinned 5.20, which is the 0.88 GiB gotcha 33 fitted from the memory model — before it holds one token of context. Seven fit with 128-token prompts, five with 4k-token ones and two with 16k ones. MTP's k=4 costs 0.44 GiB, so eight fit, four of them at 16k. Past that the extras queue, and once the pool is full something has to be preempted and recomputed to make room — a ramp of tiny requests hits that at the seventh. `MAX_SEQS` decides how many requests are *admitted*, not how many can run. The pool itself is **unchanged** by the setting (268,169 tokens at `CTX=huge` either way, \~8 MiB total between 1 slot and 8 — gotcha 33), which is the part of the old paragraph that was right.

Two things to read off it. The verify step *does* batch — aggregate throughput keeps climbing for both speculators, and no preemption happens at any of these points — so "the block verify does not batch" is not what is going on. What it costs is latency: each additional resident request adds about 7 ms to every forward pass under DFlash2 (5 ms under MTP), so the second user roughly halves your tokens per second and the fourth roughly quarters them. That 7 ms is not attention over their context — with 128-token prompts the slope is the same (25.2 → 45.8 ms from one resident to four) — it is the per-request recurrent state, the same thing that limits residency. And MTP keeps scaling to 8 streams where DFlash2 runs out of pool at 5, which is the whole of its C8 advantage. Point one person at DFlash2; point a team at `SPEC=mtp` or batch mode.

**On `CTX=huge`, raising `MAX_SEQS` is worse than not raising it.** That profile defaults to 2 seats, and the reason is the same state page against a smaller pinned pool (4.90 GiB): five residents with a short prompt, four with a 16k one. Force it to 8 and feed it eight independent 16k-token streams and the scheduler starts evicting — **10 preemptions** in one run, peak occupancy 99.4%, per-stream 3 / 7 / 72 tok/s, end-to-end aggregate down to 10.3 from 13.0 at a single stream. The same eight streams against the shipped 2 seats: **0 preemptions and 14.4 tok/s**, i.e. 40% more work done by admitting fewer requests. An earlier version of this README recommended exactly that override. Leave the seats where they are.

Make the streams long and independent and it stops being about decode at all. Eight 16k-token prompts with nothing shared between them: end-to-end aggregate **15.8 tok/s** against 131 for a single stream, mean TTFT 71.7 s, two requests resident — but the decode-only aggregate over the same run is 183 tok/s, tokens per step is unchanged at 3.71 and nothing is preempted. The run is 131k tokens of prompt at \~1,600 tok/s and 2,048 tokens of answer, so it is a prefill measurement wearing a decode measurement's units, and `SPEC=mtp` reads the same 15.0-15.9 there. If your clients each bring their own long document, that is the number you get, and no speculator changes it.

What *does* change it is sharing the document. The same eight 16k streams with one shared prefix and `PREFIX_CACHE=1` (`bench/conc_ladder.py --shared`):

streams 1 2 4 8

end-to-end aggregate tok/s 15.5 128.4 **147.8** 68.3

mean TTFT 14.6 s 1.3 s 2.6 s 11.5 s

One stream pays the prefill; everyone after it hits the cache, and four concurrent readers of the same document get 148 tok/s end-to-end against 15.9 when the documents differ. That is the shape of workload this mode is for — a chat client or a coding front-end against one codebase — and it is nearly a 10x difference from the same server on the same prompt length.

`DFLASH_TOKENS=15` doubles the state page to 1.66 GiB: three residents with an empty context, **two** with 4k-token prompts, against five. That mode is single-user in the literal sense, and its launcher default of `MAX_SEQS=4` is already the tighter number — do not raise it. `DFLASH_TOKENS=15 MAX_SEQS=8` used to boot, answer `/health` and then die on the first concurrent batch (`torch.OutOfMemoryError` in the engine, every request 500); the launcher now caps the captured-graph size so that configuration degrades to piecewise instead (gotcha 38). It does boot at 240k since `82bd62d`, which caps `max_model_len` to 221,184 above 7 drafts rather than letting the server fail to come up.

The capture mode is fixed at boot, and for `SPEC=mtp CTX=huge` the trade is not optional. What FULL does there is corrupt one prompt length in every 128, and only for a request that hits the prefix cache. The broken residue is a function of the draft count (`R = 117 + k`, the same for both speculators), which is why scoping the workaround to `dflash2` was wrong the first time — `SPEC=mtp CTX=huge` shipped with the same bug at residue 4. Piecewise costs MTP nothing measurable (87.8/86.1/70.4/63.5 tok/s captured against 93.5/83.8/70.3/59.6 piecewise over 8k-50k), so it keeps PIECEWISE until residue 4 comes back verbatim under a full sweep.

**Do not test that residue by its symptom.** The location is deterministic and the damage is not: the same `mtp` residue has returned an empty answer, a one-character answer, and 400 tokens of fluent Danish inventing a task the prompt never asked for (2 of 1,146 characters matching the document). A detector keyed on "it repeats" or "it came back empty" passes at least one of those. Gotcha 37 in docs/gotchas.md has the residue table; `bench/residue_sweep.py` sweeps all 128 residues and judges every answer on how much of the document came back, and `bench/verbatim.py` self-tests that rule against all three shapes.

`MODEL=` points the launchers at any Qwen3.8-27B checkpoint in the same `compressed-tensors` shape. Two routes, easiest first.

**Ready-made:**[leminkozey/Qwen3.8-27B-Uncensored-W4A16-AutoRound](https://huggingface.co/leminkozey/Qwen3.8-27B-Uncensored-W4A16-AutoRound) ([#45](https://github.com/syv-ai/qwen38-27b-rtx3090/issues/45)) is an abliterated Qwen3.8-27B already quantized with this repo's own recipe — AutoRound W4A16 body plus the `prepare/` head requant — so it serves without any preparation. Its author measured \~100 tok/s warm at `SPEC=dflash2 CTX=huge` on a 3090 with coherent output and a 45k-context needle retrieved, and a second tester confirmed `SPEC=mtp` works. Community-built and community-verified; not benchmarked on this repo's reference box.

**Any other export**, including single-shard and asymmetric-AWQ ones the base model's three `quant_*.py` scripts cannot open, goes through the streaming requant (contributed in [#37](https://github.com/syv-ai/qwen38-27b-rtx3090/pull/37)). The worked example is [philbert440/Qwen3.8-27B-Uncensored-Aggressive-W4A16-AWQ](https://huggingface.co/philbert440/Qwen3.8-27B-Uncensored-Aggressive-W4A16-AWQ) — an abliterated (de-refused) Qwen3.8-27B, W4A16 AWQ, with the vision tower and the grafted MTP head both preserved. Prepare it once, then serve it:

```
venv/bin/python prepare/fetch_thirdparty.py          # ~18.6 GB; or: fetch_thirdparty.py <hf-repo>
venv/bin/python prepare/quant_heads_stream.py models/Qwen3.8-27B-Uncensored-W4A16
venv/bin/python prepare/build_draft_vocab.py  models/Qwen3.8-27B-Uncensored-W4A16 \
  --ids prepare/draft_vocab_ids.json

MODEL=$PWD/models/Qwen3.8-27B-Uncensored-W4A16 SPEC=mtp CTX=long PREFIX_CACHE=1 \
  MAX_LEN=100000 bash single-user/start_qwen.sh
```

It needs `prepare/quant_heads_stream.py` rather than the three `quant_*.py` steps the base model uses, for two reasons that are properties of the checkpoint and not of the model: it ships as **one 18.6 GB shard**, which the three scripts read into RAM whole before rewriting, and its body is **asymmetric AWQ**, which those scripts would copy onto the symmetric tensors they write — vLLM then looks for a `weight_zero_point` that was never written. The streaming script handles both and produces the same tensors otherwise; `bash verify.sh --no-server` with `MODEL=` set checks the result exactly as it checks the base model.

**`SPEC=dflash2` needs its pool resized for this checkpoint.** After requantization it is 15.68 GiB of weights against the fast variant's 14.71, and the DFlash2 branch pins the KV pool *in bytes* (`KV_MEM`) rather than sizing it from `--gpu-memory-utilization`, so the pool does not give that gigabyte back. The server loads, captures graphs, and then dies on the split-KV verify buffer:

```

torch.OutOfMemoryError: Tried to allocate 960.00 MiB ... 926.44 MiB is free

Hand that gigabyte back and it comes up. `CTX=long` (int8 KV) is the one to spend it on, because it buys roughly twice the context per byte of pool that `CTX=fast` does:

```
MODEL=$PWD/models/Qwen3.8-27B-Uncensored-W4A16 SPEC=dflash2 CTX=long PREFIX_CACHE=1 \
  KV_MEM=4456028569 DFLASH_MAX_LEN=98304 bash single-user/start_qwen.sh
```

Measured here, RTX 3090 at 250 W: a 4.15 GiB pool holding **103,033 tokens** at 98,304 `max-model-len` (4.6% margin) and **85.7 tok/s** greedy on a 400-token answer. The checkpoint keeps its vision tower, and that run had `VISION=1` — images came back described correctly — so the numbers are an upper bound on what the default `VISION=0` needs, which drops the tower's weights entirely.

`SPEC=mtp` needs no `KV_MEM` of its own: its pool is profiled from `GPU_UTIL` rather than pinned, so it absorbs the extra gigabyte by shrinking the pool for you. It is the mode to reach for first on this checkpoint. The pool it lands on will not hold `CTX=long` 's stock 150k, though, which is what the `MAX_LEN=100000` above is — the figure this checkpoint has been run at.

```

```

Everything here is written for one 24 GB card; multi-GPU goes through untouched via `EXTRA_ARGS`:

```
SPEC=dflash2 PREFIX_CACHE=1 EXTRA_ARGS="--tensor-parallel-size 2" bash single-user/start_qwen.sh
```

**`--tensor-parallel-size 3` is not valid for this model.** The checkpoint's text config has 4 KV heads and 64 layers:

```
curl -sL https://huggingface.co/dbirks/Qwen3.8-27B-W4A16-AutoRound/raw/main/config.json \
  | python3 -c "import json,sys; t=json.load(sys.stdin)['text_config']; print(t['num_key_value_heads'], t['num_hidden_layers'])"
# 4 64
```

Tensor parallelism needs the KV-head count and the TP size to divide one another, and 4 and 3 do neither way; pipeline parallelism needs an even layer split, and 64 does not divide by 3. So on a three-card box the third card cannot join the engine — run a TP=2 engine on two cards plus a second standalone engine on the third ([#104](https://github.com/syv-ai/qwen38-27b-rtx3090/issues/104)), and if both serve containers share one host, set `VLLM_OFFLOAD_KEEP_SHM=1` on both: each launcher's stale-offload-region reaper only sees its own container's processes and would delete the other engine's live region ([#33](https://github.com/syv-ai/qwen38-27b-rtx3090/issues/33)).

Under Docker, the same two knobs live in `.env` — `GPU_COUNT` says how many cards the container gets, `EXTRA_ARGS` says how many the engine uses, and nothing in `docker-compose.yml` needs editing:

```
GPU_COUNT=2
EXTRA_ARGS="--tensor-parallel-size 2 --language-model-only"
```

`GPU_COUNT` defaults to 1, which is *the first card the runtime enumerates* — GPU 0, not necessarily the card you meant. On a mixed box, expose them all and pin inside the container with `GPU_COUNT=all` plus `CUDA_VISIBLE_DEVICES=1,2` (the device reservation decides what is visible, so `NVIDIA_VISIBLE_DEVICES` in `.env` alone was not enough; `CUDA_VISIBLE_DEVICES` is read inside the container and is what gotcha 53 recommends).

**Pin the KV pool before you measure anything, or before you trim `MAX_LEN` until the OOMs stop.** Under `--tensor-parallel-size > 1` the launcher deliberately skips the single-card `KV_MEM` pin (below), and `SPEC=mtp` has no profile pin at all — so the pool is sized from `GPU_UTIL`, and the headroom it is carved out of moves by \~0.92 GiB depending on whether the torch.compile cache was warm (`docs/gotchas.md` 48). That is the "booted at 146k yesterday, OOMs today" failure. To pin it, boot once at a context that works and read the two lines the engine prints:

```
docker compose logs single | grep -E "Available KV cache memory|GPU KV cache size"
# INFO ... Available KV cache memory: 3.36 GiB
# INFO ... GPU KV cache size: 161,280 tokens
```

then put a byte count a little under that `GiB` figure into `.env` as `KV_MEM=` (3.36 GiB ≈ 3607772528 bytes; round down). `KV_MEM` overrides the TP skip — the launcher only declines to pin one *for* you. A pinned pool either fits at boot or refuses at boot, instead of OOMing on the first request, and it is the only way two benchmark arms are comparable.

What the second card is worth is now measured, not assumed — [#40](https://github.com/syv-ai/qwen38-27b-rtx3090/issues/40) ran a controlled 1-vs-2×3090 A/B on this harness (same box, same install, PCIe 4.0 x8, **no NVLink**, 275 W):

- **+16–35% decode across C1–C8** (DFlash2 greedy: 127.4 → 161.6 at C1). Worth it at batch 1: decode is bandwidth-bound here, and TP=2 is a second memory system, not idle compute.
- **The DFlash2 residency ceiling is a 24 GB property, not a drafter property.** On one card DFlash2 collapses at C8 (3.9 s TTFT — the recurrent-state pool exhaustion documented above) and MTP wins; on two cards DFlash2 wins at every concurrency measured. On 2×24 GB, point everyone at DFlash2.
- **The launcher no longer pins `KV_MEM` under TP&gt;1** (their finding, this fix): the pin is a single-card constant applied per worker, and it stranded \~16 GiB across two cards — 137,210 tokens of pool where `GPU_UTIL` sizing gets 302,223, at no measured decode cost. Export `KV_MEM` to pin anyway.
- **Keep `DFLASH_TOKENS=7` at TP&gt;1** for now: the one T=15 datapoint at TP=2 (same issue) lost 27% at C1 with the lookup-filled tail accepting nothing, which is under diagnosis. The launcher warns.
- NVLink appears to buy little:[#7](https://github.com/syv-ai/qwen38-27b-rtx3090/issues/7) 's NVLink box at 330 W and #40's PCIe-x8 box at 275 W land within a few percent of each other at C1.
- **Past two cards, or on a consumer board with the cards on separate PCIe root ports, you may need `NCCL_P2P_LEVEL=SYS`** and `EXTRA_ARGS="--disable-custom-all-reduce"`. Reported from a 4x RTX 5060 Ti box on a community-patched P2P driver ([#105](https://github.com/syv-ai/qwen38-27b-rtx3090/issues/105)): NCCL would not bring up peer-to-peer across four separate root ports until P2P was forced down to `SYS`, and vLLM's custom all-reduce faulted on that driver even at TP=2. Neither is reproducible on this repo's single-card box, so treat both as field reports, not as defaults — try TP first without them.

```
NCCL_P2P_LEVEL=SYS SPEC=dflash2 PREFIX_CACHE=1 \
  EXTRA_ARGS="--tensor-parallel-size 4 --disable-custom-all-reduce" \
  bash single-user/start_qwen.sh
```

Also reported working: **2× RTX 5060 Ti 16 GB** ([#22](https://github.com/syv-ai/qwen38-27b-rtx3090/issues/22)) — the "would not fit on one card" case — and **4× RTX 5060 Ti 16 GB** (TP4, sm120, PCIe 4.0 x8, 180 W, community-patched P2P driver,[#105](https://github.com/syv-ai/qwen38-27b-rtx3090/issues/105)). The tok/s numbers in #105 are not quoted here: its two arms moved drafter, KV dtype and prefix cache together, so the ratio is a profile delta rather than a drafter delta. The graph budget and `MAX_SEQS` defaults are still single-card calibrations; more A/Bs like #40's are the most useful numbers you can send.

#### Setup

The default install is the container (Quick start — the prebuilt image already contains everything this section builds), so this manual venv path is for hacking on the stack, or running it bare-metal.

> **Python 3.14 works natively** — nothing in this repo needs changing, but `python3.14-dev` does need installing. See docs/python-314.md, with a full RTX 3090 reproduction of the tables below in docs/reproductions/native-3090.md.

You need: a 24 GB Ampere or newer NVIDIA card, a recent driver, Python 3.12, \~40 GB disk — and if the host has less than \~16 GB of free RAM, load the weights with the streamer instead of the stock loader (gotcha 45: the stock loader peaks at whatever RAM exists; the streamer is bounded and faster). Everything below is CPU-safe to run while the GPU does other things; the container details live in docs/docker.md.

```

## 深度解读（1）

### 2026-09-16 00:59:03

#### 单卡跑 27B 的真正突破：推理开始按工作负载定制

这个项目最值得关注的，不只是 “RTX 3090 能跑 Qwen3.8-27B”，而是它展示了一个更重要的变化：**模型能力不变，仅通过围绕具体任务重组推理链路，体验就可能相差数倍。**

项目在一张 24GB RTX 3090 上提供约 15 万 token 上下文、OpenAI 兼容接口；高并发模式下，64 路请求合计解码约 1000 token/s，单用户模式约 120—130 token/s。采用有损低比特 KV 缓存后，上下文容量还能扩至约 26.8 万 token。它不是某个单点量化技巧，而是权重、状态、KV 缓存、投机解码、验证注意力和调度策略共同挤出来的结果。

##### “最快配置” 不存在，只有匹配任务的配置

项目最有价值的证据来自两类任务的强烈反差。

普通聊天中，把一次验证长度从 7 个 token 扩到 15 个，吞吐只提升约 1%，因为模型生成的新内容很少直接出现在提示词里；与此同时，请求槽位从 8 个降到 4 个，上下文上限也少了 8K。这个优化对聊天几乎得不偿失。

但在复述文档、按原文修改、引用长材料时，多出来的位置可以直接从输入上下文中提出候选，无需额外运行草稿模型。25K 文档复现任务因此可达到约 382 token/s，提升约 47%。这说明**推理优化的关键变量不是笼统的 “文本生成”，而是输出与已有上下文的重合程度**。

同样，投机解码适合低并发，普通批处理则在约 8 个并发以上占优；长会话还会更早发生反转，因为每个投机请求都要占用稀缺的循环状态页。产品侧因此不应只选一个 “全局最优” 服务配置，而应按聊天、批处理、文档编辑等请求类型路由，甚至分别部署。

##### 长上下文的产品价值，首先来自状态复用

15 万乃至 26 万上下文本身很醒目，但更有意义的是前缀缓存：同一份 25K 文档上的第二轮提问，首 token 延迟从 22.4 秒降到 0.56 秒；100K 缓存前缀上的第二轮也只需约 4.7 秒，而冷启动约 169 秒。

这改变了长上下文产品的可用方式。过去 “能塞进去” 只是能力展示，现在可以把文档及其注意力 KV、循环状态保留下来，使持续审阅、合同修改、代码库问答真正接近交互式体验。相比每轮重新预填充，**会话状态的生命周期管理可能比继续扩大上下文窗口更影响用户体验和成本。**

对应的机会不是泛化的 “本地大模型”，而是面向高隐私、低并发、长文档反复操作的工作台，例如法务审阅、研究资料整理和代码修改。现有替代方案是云端 API、RAG 或人工分段；需要验证的则是：用户是否会持续围绕同一材料工作、输出是否大量复用原文，以及隐私与延迟收益能否抵消本地部署和维护复杂度。

##### 性能数字也是一种产品设计约束

仓库反复强调基准条件：输出长度不同不能直接比较；未固定随机种子时，前缀缓存会污染预填充成绩；WSL2 比裸机慢约 20%，显存只差几百 MB 甚至不会报错，而是悄悄慢两到六倍。所谓 “无损” 也有边界：投机解码本身保持原分布，但超长上下文方案使用的 4/2-bit KV 缓存是有损的。

因此，这个项目留下的最重要判断是：**消费级本地推理已经从 “能否运行” 进入 “能否针对任务精细经营” 的阶段。**模型参数不再足以描述产品能力，未来更实用的规格表应同时说明并发、上下文复用率、首 token 延迟、输出与输入的重合度，以及量化带来的质量边界。

## 结构化（1）

### 2026-09-17 07:58:22

#### 单张 RTX 3090 部署 Qwen3.8-27B：高并发、长上下文与推测解码优化

该项目通过量化、推测解码和缓存优化，让 Qwen3.8-27B 能在一张 24GB RTX 3090 上运行，并提供兼容 OpenAI 的 API。它分别针对多人并发和单人低延迟准备了两套模式：前者总吞吐约 1,000 token/s，后者可达约 120～130 token/s，特定文档复现任务可进一步达到 382 token/s。

##### 两种运行模式面向不同场景

项目基于 vLLM 0.28.0，提供预构建 Docker 镜像，首次启动会下载并重新量化约 20GB 的模型文件。

- **Batch 模式**：适合 API 后端和大量并发请求。  
  在 64 个并发、每个请求输入 128 token、输出 512 token 时：
  - 稳态解码约**1,035 token/s**
  - 端到端吞吐约**948 token/s**
  - 若所有层都使用 INT8，约可提高到**1,222 / 1,042 token/s**

- **Single-user 模式**：适合个人聊天或少量用户，重点降低延迟。  
  在真实提示词、单并发条件下：
  - 普通解码约**46 token/s**
  - 默认 MTP 推测解码约**121 token/s**
  - DFlash2 约**127 token/s**，贪心解码约**130 token/s**

两种模式共用同一套安装，只是启动脚本和参数不同。作者认为：短提示、并发少于约 8 个请求时，推测解码更有优势；并发更高时，普通批处理通常更划算。长会话会占用更多循环状态显存，因此性能分界点还会提前。

##### 核心提速来自量化和推测解码

项目把多种优化组合在一张消费级显卡上：

- 使用**INT8 Tensor Core 矩阵运算**，降低权重计算成本。
- 关键的 DeltaNet 循环状态保留 FP16，以兼顾精度。
- 对输出层和草稿模型采用校准后的 INT4 量化。
- 验证草稿 token 时使用拆分 KV 注意力，减少长上下文开销。
- 通过 “推测解码” 先由轻量草稿模块预测多个 token，再让主模型一次验证。

默认的**MTP**会串行提出 4 个草稿 token；推荐的**DFlash2**可一次提出 7 个，因此单用户速度通常更高。

作者强调，推测解码本身不会改变原模型的采样分布：草稿只用于加速，最终仍由主模型验证。前缀缓存也会恢复完整循环状态，而不是近似处理。

##### DFlash2 普遍有用，但 15-token 配置只适合文档复现

将`SPEC=dflash2`打开后，单人聊天通常能获得明显提升。项目还支持`DFLASH_TOKENS=15`：DFlash2 先生成训练时支持的 7 个草稿，其余位置直接从用户已提供的上下文中寻找候选。

这对 “照抄、引用或编辑原文” 非常有效：

| 任务 | 默认 MTP | DFlash2 | DFlash2＋15-token 验证 |
|---|---:|---:|---:|
| 8 个真实聊天提示 | 118 tok/s | 132 tok/s | 133 tok/s |
| 复现 25k-token 文档 | — | 260 tok/s | 382 tok/s |

但普通聊天很少直接复用提示词。在测试中，第 7～14 个额外候选位置只贡献了**72 / 11,069 个被接受 token，约 0.65%**，速度仅提升约 1%。与此同时，16-token 验证块会：

- 将请求槽位从 8 个降到 4 个；
- 最大上下文从 64k 降到 56k；
- 把每个常驻请求的循环状态占用从约 0.88GiB 提高到 1.66GiB。

因此作者建议：

- 普通聊天、智能体任务：使用默认的 7-token DFlash2。
- 文档引用、原文复现、按原文修改：再开启 15-token 配置，此时收益可达约**47%**。

##### 前缀缓存显著改善长文多轮对话

`PREFIX_CACHE=1`会保存已经处理过的文档，包括注意力 KV 和循环状态，适合围绕同一长文连续提问。

原文测试中，对同一份 25k-token 文档进行第二轮提问时：

- 不使用缓存：首 token 等待约**22.4 秒**
- 使用缓存：约**0.56 秒**
- 输出结果逐 token 一致

在 100k-token 缓存前缀上，第二轮响应约需**4.7 秒**，冷启动则约为**169 秒**。该优化与 MTP、DFlash2 相互独立，可以叠加使用。

##### 上下文可从 64k 扩展到约 245k

项目提供多档上下文配置：

- 快速档：约**64k**
- 长上下文档：通过 INT8 KV 扩展到约**138k～150k**
- `CTX=huge`＋KVarN：最大模型长度设为**245,760**，KV 池容量约**268,169 token**

KVarN 使用 4/2-bit KV 缓存，因此能大幅扩大上下文，但它是**有损压缩**。这也是文章对 “全部优化无损” 说法的唯一明确例外：推测解码仍然精确，但超长上下文缓存可能带来精度损失。

测试结果显示：

- 200k 深度的 “针藏于草堆” 检索测试可以通过；
- GSM8K 准确率约**95%～97%**，处于项目其他配置的正常波动区间；
- 25k 文档逐字复现测试能完整输出 1,150 个目标字符。

作者据此认为该模式可用，但应将其与其他有损量化配置比较，而不是与 BF16 无损缓存直接等同。

##### 输入处理和输出生成是两套性能预算

文章特别区分了 Prefill 与 Decode：

- **Prefill**：读取和处理用户输入。
- **Decode**：逐个生成输出 token。

在 1k 输入长度下：

- Batch 模式 Prefill 约**1,810 token/s**
- Single-user 默认约**1,440 token/s**
- 开启`INT8_ACT=int8`后约**1,850～1,940 token/s**
- 51k 长输入时约**1,423 token/s**

因此，输出速度很快并不代表长文首次载入同样快；前缀缓存主要用于避免后续轮次重复支付长文 Prefill 成本。

##### 性能数据有明确测试边界

上述数字来自 RTX 3090、250W 功耗限制以及项目指定的`vllm bench serve`测试。单用户基准使用 8 个真实提示，每个生成 1,024 token，并按平均每 token 时间计算解码率。

作者提醒，不同的输入长度、输出长度、采样方式、并发数、操作系统和测试脚本都会改变结果，不能把不同基准中的数字直接混用。目前项目固定在 vLLM 0.28.0，部分吞吐和质量表仍作为参考基线，正在重新测量完整 GPU 矩阵。

##### WSL2 可以运行，但存在性能和显存陷阱

DFlash2 会强制使用 vLLM V2 Runner。在 WSL2 下必须设置：

```bash
VLLM_WSL2_ENABLE_PIN_MEMORY=1
```

否则会因无法使用 UVA 缓冲区而在加载模型前直接报错。名称相近的`VLLM_WSL_PIN_MEMORY`并不是有效变量。

作者的测试还显示：

- WSL2 比裸机 Linux 慢约 20%；
- 原生 Windows 并不一定比 WSL2 快，测试中反而更慢；
- WSL2 可用独立显存比裸机少约 0.5GB；
- 如果配置略微超过可用显存，程序可能不报错，而是因显存分页突然慢 2～6 倍。

因此要获得文中裸机性能，需要直接运行 Linux；在 WSL2 中则应为显存留出更多余量。

##### 部署简单，但公网使用必须开启认证

项目推荐直接通过 Docker Compose 选择模式：

```bash
docker compose --profile single up -d
docker compose --profile batch up -d
```

镜像约 9.5GB，首次运行会自动准备模型。服务默认监听`0.0.0.0:18020`，并提供兼容 OpenAI 的 API。

需要注意：本地默认没有认证。如果服务会暴露到本机之外，必须设置`VLLM_API_KEY`，否则任何能访问端口的人都可调用模型。

##### 总体结论

该项目的重点不是单项优化，而是把量化、推测解码、前缀缓存和长上下文缓存组合起来，使 27B 级模型能在单张 RTX 3090 上实用运行：

- 多人 API：优先 Batch 模式，64 并发总吞吐约 1,000 token/s。
- 单人聊天：优先 DFlash2，约 127～130 token/s。
- 长文多轮问答：开启前缀缓存，可大幅降低后续首 token 延迟。
- 文档复现或编辑：可使用 15-token 验证，最高约 382 token/s。
- 超长上下文：KVarN 可扩展到约 245k 模型长度，但需接受低位 KV 缓存带来的有损权衡。

## 口播总结（1）

### 2026-09-18 10:05:16

这套项目要解决的问题很直接：能不能只用一张二十四GB显存的消费级显卡，也就是锐龙三零九零，运行二百七十亿参数的 Qwen 三点八模型，同时兼顾长上下文和高吞吐量？

项目给出的答案是可以。不过，单人聊天、多人并发和超长文档，是三种不同的负载。真正重要的不是追求一个最高数字，而是根据用途选择正确模式。

如果服务器要同时处理很多请求，应该使用批处理模式。测试条件是一张功耗限制在二百五十瓦的三零九零，六十四个并发请求，每个请求输入一百二十八个词元，输出五百一十二个词元。在这个条件下，稳定解码吞吐量大约是每秒一千零三十五个词元；把请求的完整耗时也算进去，大约是每秒九百四十八个词元。进一步把所有层都改成八位整数计算，吞吐量还能提高，但这属于更激进的配置。

这里的每秒一千多个词元，是六十四个请求合计的吞吐量，不代表单个用户能以同样速度获得回答。单用户如果不用特殊优化，速度大约只有每秒四十六个词元。

为了提高单用户速度，项目使用了推测解码。它的基本思路是，先让一个计算成本较低的草稿模块猜出后续几个词元，再由完整模型一次性检查。猜对得越多，完整模型需要运行的次数就越少。

默认的多词元预测模式，每轮会连续生成四个草稿。它能把单用户速度提高到每秒一百二十个词元左右。另一种名为 DFlash2 的草稿模块，可以在一次计算中提出七个词元。面对真实聊天提示时，它通常能达到每秒一百二十七到一百三十个词元。

这些提升不只来自草稿模块。项目还使用了面向张量核心的八位整数矩阵运算，把输出层和草稿模块重新量化到四位整数，并优化了验证阶段读取上下文缓存的方式。与此同时，模型的循环状态仍保留十六位精度。换句话说，这是一组相互配合的工程优化，而不是某一个开关带来的奇迹。

推测解码最适合并发量较低的场景。短提示下，并发用户少于大约八个时，它通常更划算。并发量继续增加后，普通批处理反而更有效。对于上下文很长、而且彼此独立的会话，转折点还会更早。原因是每个推测请求都要占用循环状态页面，而三零九零能容纳的页面数量有限。

DFlash2 还有一个特别适合文档处理的技巧。正常情况下，它一次提出七个词元。如果回答需要大量复述原文，例如引用合同、改写代码或按要求编辑文档，系统还可以直接从用户提供的上下文中寻找后续内容，把一次验证扩大到十六个词元。

在复现一份两万五千词元文档的测试中，普通 DFlash2 大约能达到每秒二百六十个词元。启用从上下文取草稿的功能后，速度达到每秒三百八十二个词元。这是因为复述原文时，历史内容本身就是质量极高、而且几乎不需要计算的草稿。

不过，这个功能并不适合普通聊天。真实聊天测试中，七个草稿位置之后，从原文补充的那些候选，只占全部成功接受词元的大约百分之零点六五，因此整体收益只有百分之一左右。代价却不小：每个请求占用的循环状态内存接近翻倍，请求槽位从八个降到四个，可用上下文也少了大约八千词元。所以，聊天和智能体应用保留七词元设置更合理；只有在引用文档、复现内容或应用编辑时，才值得扩大验证块。针对这类工作负载，收益可以达到大约百分之四十七。

另一个非常关键的优化是前缀缓存。所谓前缀缓存，就是保存已经处理过的文档，包括注意力缓存和循环状态。用户围绕同一份长文档继续提问时，服务器不必从头读取全部内容。

在两万五千词元文档的测试中，第二轮对话生成第一个词元所需的时间，从二十二点四秒降到零点五六秒，而且输出逐词保持一致。对长文档聊天来说，这种首词延迟的改善，往往比单纯提高每秒生成速度更有体感。

这里还要区分预填充和解码。预填充是模型第一次读取输入内容，解码才是逐词生成回答。批处理模式读取一千词元输入时，预填充速度大约是每秒一千八百一十个词元。单用户模式默认约为每秒一千四百四十个词元。启用八位整数激活后，短输入可以提高到每秒一千八百五十到一千九百四十个词元。不过，输入增长到五万一千词元时，速度会回落到每秒一千四百二十三个词元。

上下文长度方面，常规长上下文配置可以达到大约十五万词元。项目还提供 KVarN 缓存方案，把缓存容量提高到约二十六万八千词元，最大模型长度设置为二十四万五千七百六十词元。十万词元深处的信息检索测试能够通过，而且对已经缓存的十万词元前缀进行第二轮处理，只需四点七秒；冷启动则需要一百六十九秒。

但超长上下文不是免费的。KVarN 使用四位和二位的低精度键值缓存。键值缓存，也就是模型保存历史上下文信息的内存。因此，这种长上下文模式存在精度损失。推测解码本身仍然是精确的，前缀缓存也不是近似恢复；真正有损的是低位宽的键值缓存。项目的数学推理测试大致仍在百分之九十五到百分之九十七之间，但使用者应把它看作容量与精度之间的交换。

部署方面，项目已经把模型下载、重量化、补丁和验证流程封装进 Docker。第一次启动需要拉取大约九点五GB的镜像，并下载和处理约二十GB的模型文件。之后可以选择单用户模式或批处理模式，两种模式共用同一套安装。

如果运行在 Windows 的 WSL 二环境中，需要明确启用固定内存支持，否则 DFlash2 会因为无法分配统一虚拟地址缓冲区而直接停止。WSL 二的可用显存还比裸机 Linux 少大约半GB。一旦配置略微超过显存边界，程序不一定报错，却可能因为分页而慢上两到六倍。从项目测试看，裸机 Linux 的性能明显更好；换成原生 Windows也不能消除这个问题。

最后还有一个安全细节。服务器默认监听所有网络接口，而且如果没有手动设置密钥，就不要求身份验证。只在本机使用问题不大；一旦要暴露到局域网或互联网，必须先启用 API 密钥。

最值得记住的是三点。单人使用时，DFlash2 和前缀缓存最有价值；多人并发时，普通批处理更适合。扩大验证块只对引用、复现和编辑文档特别有效，不应当作为普通聊天的默认设置。至于十五万到二十多万词元的超长上下文，它确实能在单张三零九零上实现，但更大的容量伴随着更高的内存压力，最激进的缓存方案还会引入精度损失。

## 深度解读-口播（1）

### 2026-09-30 11:50:47

一张只有二十四吉字节显存的 RTX 三零九零，能不能运行二百七十亿参数的大模型，而且速度还不错？这个项目给出的答案是：可以。但最值得理解的，不是某个漂亮的速度数字，而是这些速度分别适合什么场景，又付出了什么代价。

项目运行的是 Qwen 三点八，使用 vLLM 推理框架。它提供两种模式：一种面向多人同时调用，另一种面向一个人聊天。两种模式共用一套安装，但同一张显卡一次只运行其中一种。

先把最容易混淆的数字说清楚。

项目报告，在六十四个请求同时运行时，批量模式的稳定生成吞吐量，可以达到每秒大约一千零三十五个词元。词元是模型处理文本的基本单位，不等同于一个汉字。

但这个数字是所有请求加起来的产量，不是每个用户都能获得这样的速度。批量模式下，单个请求的生成速度，大约是每秒四十六个词元。

换成单用户优化模式，真实聊天提示的测试结果，可以达到每秒一百二十到一百三十个词元左右。也就是说，多人服务追求的是总产量，一个人聊天追求的是自己这一路回答得更快。不能拿前者的总吞吐量，去代表后者的体验。

这些数据还有测试前提：显卡功耗限制在二百五十瓦，提示内容、输出长度和采样方式都有规定。项目也说明，升级到新的推理框架版本后，部分性能和质量表格仍是参考基线，正在重新测量。因此，这些数字更适合用来理解优化方向，而不是当成任何机器都能兑现的承诺。

那么，单用户模式为什么能快这么多？关键方法叫推测解码。

可以把它理解成：先让一个成本更低的草稿模型，提出接下来可能出现的几个词元，再让主模型批量检查。猜对的部分一起通过，猜错的部分按规则处理，减少主模型逐个生成的工作。

项目默认的一种方案，会串行提出四个草稿词元。另一种叫 DFlash 二的方案，一次就能提出七个。在项目报告的真实聊天测试中，后一种方案通常更快。

这里有一个重要区别：推测解码不是直接相信草稿。项目采用的验证机制，设计上保持与不使用推测解码相同的输出概率分布。但这只是在说推测解码机制本身，不代表模型量化和缓存压缩也没有损失。

更有意思的是，草稿还可以来自用户已经提供的原文。

如果任务是引用文档、复现内容，或者按照要求修改一段文本，那么下一段输出，很可能就在输入里。项目因此提供了一个设置：除了草稿模型提出的七个词元，再从当前请求的上下文里填入更多候选，让主模型一次验证更长的一段。

在复现一份两万五千词元文档的测试中，这种设置把生成速度从每秒约二百六十个词元，提高到约三百八十二个，增幅接近百分之四十七。

但普通聊天几乎吃不到这个收益。原因很直接：聊天回答通常不会连续照抄问题。额外候选大多无法通过验证，测试中的提速只有大约百分之一。

代价却是真实存在的：验证的片段越长，每个请求需要保留的内部状态就越大。在对应配置中，可用请求槽位从八个降到四个，上下文上限也从六万四千词元降到五万六千。

所以，这个优化不是越大越好。引用文档、应用编辑时，它很有价值；普通聊天或智能体调用，保留较短的验证片段更合适。

理解了生成速度，再看另一种更直接影响体感的优化：前缀缓存。

模型回答之前，先要处理输入。长文档即使只发送一次，这一步也可能花很长时间。如果下一轮继续讨论同一份文档，却又从头计算，用户就得反复等待。

前缀缓存会保留已经处理过的共同输入。这个项目不仅缓存注意力计算所需的信息，还保存模型的循环状态，让下一轮能够从已有结果继续。

项目给出的例子是：围绕同一份两万五千词元文档进行第二轮提问，开启缓存后，首个词元的等待时间，从二十二点四秒缩短到零点五六秒，而且这个测试中的回答逐词元一致。

这个案例说明，回答生成得快，和回答开始得快，是两回事。对于反复讨论同一份长文档的人，避免重复处理输入，可能比继续提高生成速度更重要。

不过，一张消费级显卡能装下这么大的模型，还能容纳长上下文，靠的并不只是草稿和缓存，也靠精度与显存的精细安排。

批量模式的一项关键设计，是让主要矩阵运算使用八位整数计算，同时把循环状态保留为十六位浮点数。它不是把所有数据都压成最低精度，而是在计算速度、显存占用和状态稳定性之间做选择。

更长上下文的方案，还会进一步压缩注意力缓存。项目的一种配置，把单次请求的上下文上限扩展到大约二十四万六千词元。但这里使用了四位和两位的有损缓存，所以不能再把整套配置称为无损。

项目报告了长文档检索和数学题测试，结果大体处在已有配置的表现范围内。这是有用的证据，但有限测试通过，不等于所有任务都不会受影响。

同样，长上下文会改变并发能力。短提示下，推测解码大约在八个并发用户以内有优势，再往上，普通批处理更合适。对于多个互相独立的长会话，这个转折会更早，因为每个推测请求都要占用较大的状态空间。

实际部署还有两个提醒。第一，Windows 下的 Linux 子系统需要特定内存设置，而且显存余量很紧。项目观察到，超出可用显存预算时，系统有时不是报错，而是悄悄慢上几倍。第二，服务默认没有开启接口密钥认证；如果要让其他机器访问，应先配置认证。

最值得记住的是：每秒上千词元，说的是多人合计吞吐；每秒一百多词元，才更接近单人聊天的生成体验。真正有效的优化，要跟任务匹配：重复讨论文档用缓存，引用和编辑原文可以扩大推测验证，普通聊天则不必为几乎没有的收益牺牲显存。单卡运行大模型的关键，不是把每个参数都拉满，而是把有限显存花在最能改善自己体验的地方。
