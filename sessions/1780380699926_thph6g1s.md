##### 1. 总结

这条内容的核心观点：

> **让强模型做“规划者”，让较快/较便宜的模型子代理做“执行者”，效果优于单个模型包办全部任务。**

作者的工作流：

1. **GPT-5.5 xhigh** 先调研、拆解任务、制定计划  
2. 把具体实现交给 **Composer 2.5 子代理**  
   - 使用独立工作树  
   - 开分支  
   - 提 PR  
3. 每个 PR 都严格审查  
   - 有问题就让子代理继续修  
   - 直到没有遗留问题  
4. 作者最后人工审查并合并

结论：

- 比 **GPT-5.5 单独完成** 更快  
- 比 **Composer 单独完成** 更全面、更稳  
- 推荐模式：**规划者 + 执行者子代理**

---

##### 2. 解读

这其实是在讲一种更成熟的 AI 编程协作方式。

###### 单个超级代理的问题

如果让一个模型从头到尾全干：

- 它可能规划不错，但写代码慢
- 或者写代码快，但设计不够深
- 容易遗漏细节
- 出错后修复链路混乱

就像让一个人同时当：

> 产品经理 + 架构师 + 程序员 + 测试 + Code Reviewer

效率不一定高。

---

###### 规划者 + 执行者的优势

更像真实软件团队：

| 角色 | 作用 |
|---|---|
| 强模型 | 思考、规划、拆任务、定方向 |
| 子代理 | 分头实现具体代码 |
| 审查机制 | 检查质量、发现遗漏 |
| 人类 | 最终把关 |

这样做的好处是：

- **强模型用在最该用的地方：思考**
- **便宜/快模型负责执行：写代码**
- **多个分支/PR 并行推进**
- **审查机制降低翻车概率**

---

###### 关键不是“模型更强”，而是“流程更好”

这条内容真正有价值的地方不是 GPT-5.5 或 Composer 2.5 本身，而是这个模式：

> AI 编程正在从“一个聊天框写代码”，进化到“多代理协作开发流程”。

未来高效开发可能不是问：

> 用哪个模型？

而是问：

> 怎么组织模型分工？怎么审查？怎么合并？

---

##### 3. 我的意见

我认可这个方向。

**最佳实践不是迷信一个最强模型，而是搭建一个好流程。**

尤其适合：

- 中大型代码库
- 多文件改动
- 重构
- SDK / 框架开发
- 需要稳定质量的项目

但也有注意点：

- 小任务没必要搞复杂流程
- 多代理会增加成本
- PR 审查必须严格，否则只是“批量制造 bug”
- 人类最终审查仍然重要

---

##### 4. 一句话结论

> **强模型负责想清楚，快模型负责做出来，审查机制负责兜底——这比一个模型单打独斗更接近真正的软件工程。**

## 结构化（1）

### 2026-06-02 07:07:19

##### 主旨概括

Mitch Fultz 分享了一种 AI 编程协作流程：让 **GPT-5.5 xhigh 负责规划**，再让 **Composer 2.5 子代理负责具体实现**，效果优于单个模型独立完成全部任务。核心思路是“强规划者 + 多执行者 + 严格审查”。

---

##### 1. 核心工作流：规划者与执行者分工

作者在 `pi-cursor-sdk` 项目中使用如下循环：

1. **GPT-5.5 xhigh 先调查并制定计划**
   - 负责理解问题、分析代码库、设计整体方案。
   - 类似“架构师”或“项目经理”的角色。

2. **GPT-5.5 xhigh 将实现任务委托给 Composer 2.5 子代理**
   - Composer 2.5 子代理负责实际编码。
   - 每个子代理可在独立的：
     - 工作树（worktree）
     - 分支（branch）
     - 拉取请求（PR）
     中完成任务。

3. **对每个 PR 进行严格审查**
   - 使用 Cursor 的审查能力，确保没有遗留问题。
   - 如果发现问题，Composer 子代理继续修复，直到状态干净。

4. **作者手动审查并合并 PR**
   - 最终合并前仍保留人工把关。
   - 避免 AI 自动合并带来的风险。

---

##### 2. 效果对比：组合模式优于单模型独立完成

作者认为这种模式相比单独使用某一个模型更有优势：

- **比 GPT-5.5 xhigh 单独完成更快**
  - xhigh 擅长规划，但如果让它独立完成所有编码，效率不一定最高。

- **比 Composer 2.5 单独完成更彻底**
  - Composer 2.5 适合执行，但若缺少强规划，整体质量和完整性可能不足。

因此，最佳效果来自：

> GPT-5.5 xhigh 做规划者，Composer 2.5 子代理做实现者。

---

##### 3. 关键案例：pi-cursor-sdk 项目

作者提到该流程应用在自己的项目中：

- 项目名称：`pi-cursor-sdk`
- GitHub 链接：`github.com/fitchmultz/pi-cursor-sdk`
- 使用方式：
  - xhigh 制定计划
  - Composer 2.5 多子代理并行实现
  - 每个实现生成独立 PR
  - 审查、修复、人工合并

这个案例展示了 AI 编程不一定要依赖“一个超级代理”，而可以采用更像真实软件团队的分工模式。

---

##### 4. 讨论焦点：超级代理 vs 规划者 + 子代理

作者最后提出问题：

> 你会使用一个超级代理，还是“规划者 + 执行者子代理”的组合？

这反映出当前 AI 编程实践中的一个重要选择：

- **超级代理模式**
  - 一个模型从规划到执行全部完成。
  - 优点是流程简单。
  - 缺点是可能慢、容易遗漏、难以并行。

- **规划者 + 子代理模式**
  - 一个强模型负责总体设计，多个子代理负责执行。
  - 优点是更快、更模块化、更容易审查。
  - 缺点是成本、管理复杂度可能更高。

---

##### 5. 热门回复中的补充观点

部分回复提出了几个有价值的补充点：

- **成本问题**
  - 有用户指出，如果每天多次运行这种“规划者 + 子代理”循环，成本会变得重要。
  - 下一步需要比较不同模型和代理组合的单价。

- **多角度评审计划**
  - 有用户表示，可以使用 3-4 个顶级代理从不同角度审查计划，例如：
    - 安全性
    - 用户体验 / UI / 工作流
    - 可维护架构
    - 整体思考与风险

- **工具使用问题**
  - 也有人询问：如何在 Cursor 之外使用 Composer？
  - 说明这种多代理工作流仍依赖具体工具生态，迁移性和集成方式值得关注。

---

##### 总结

这篇内容的核心启发是：AI 编程不应只追求“单个最强模型”，而可以像真实开发团队一样进行角色分工。让强推理模型负责规划，让执行型代理并行编码，再通过严格审查和人工合并，可以在速度、质量和可靠性之间取得更好的平衡。

##### 2. 高价值信息深挖

###### 2.1 强模型不一定适合做所有事

GPT-5.5 xhigh 被用作 planner，而不是 implementer。

这说明：

- 高推理模型适合：
  - 理解复杂上下文
  - 做系统性规划
  - 拆任务
  - 发现依赖关系
  - 设计策略
- 较快、较便宜、执行力强的模型适合：
  - 写代码
  - 改文件
  - 跑测试
  - 修 lint
  - 生成 PR

这类似企业组织中的分工：

| 角色 | AI 对应 | 职责 |
|---|---|---|
| 架构师 / 技术负责人 | GPT-5.5 xhigh | 判断方向、拆解任务、制定方案 |
| 工程师 | Composer 2.5 子代理 | 执行代码改动 |
| Code Reviewer | Cursor 审查 / 其他模型 | 找问题、压质量 |
| 负责人 | 人类 | 最终决策与合并 |

价值不在于“模型智商最高”，而在于：

> **把不同模型放到最适合的位置上。**

---

###### 2.2 子代理的关键价值：并行、隔离、可回滚

作者特别提到：

- worktree
- branch
- pull request

这不是细节，而是核心。

因为 AI 写代码最大的问题之一是：

> 改动不可控，容易污染主分支，且难以追踪责任边界。

通过 worktree + branch + PR，可以把每个子代理的工作变成一个独立单元：

- 每个任务独立环境
- 每个改动有清晰 diff
- 每个 PR 可单独审查
- 出问题可以直接丢弃
- 多个子代理可以并行工作

这让 AI 编程从“聊天式改代码”变成“工程化流水线”。

---

###### 2.3 规划与执行分离，可以降低 hallucination 风险

单模型端到端执行时，常见问题是：

- 一边计划一边改，容易偏离目标
- 执行中忘记最初约束
- 改动过大
- 自我验证不足
- 生成看似完整但实际破坏架构的代码

而 planner + implementer 的模式能形成天然制衡：

- planner 负责定义边界
- implementer 负责局部执行
- reviewer 负责质量把关
- human 负责最终判断

这本质上是一种 **AI 多层治理机制**。

---

###### 2.4 严格审查比生成能力更重要

作者强调：

> 每个 PR 的严格审查，无任何遗留问题，Composer 子代理修复至干净状态。

这里的高价值点是：

> AI coding 的瓶颈不只是“会不会写”，而是“能不能被可靠地验收”。

如果没有审查机制，AI 写得越快，技术债可能越快累积。

高质量 AI 工程流必须有：

- 自动测试
- lint
- 类型检查
- 安全检查
- 架构一致性审查
- 人类最终 review

AI 生产力真正成立的前提是：

> 速度提升不能以质量失控为代价。

##### 3. 可迁移清单

如果你在做 AI 产品、AI 编程工具或内部研发系统，可以迁移出以下方法。

###### 3.1 AI 研发工作流清单

###### A. 规划阶段

- [ ] 让强推理模型先理解需求和代码库
- [ ] 要求它输出明确任务拆解
- [ ] 每个任务应包含：
  - 目标
  - 涉及文件/模块
  - 验收标准
  - 风险点
  - 不应该改动的范围
- [ ] 让模型先提出执行顺序，而不是直接开写

###### B. 执行阶段

- [ ] 每个子任务分配给独立子代理
- [ ] 每个子代理使用独立 branch 或 worktree
- [ ] 子代理只处理一个明确目标
- [ ] 禁止子代理扩大任务范围
- [ ] 每个子代理完成后生成 PR

###### C. 审查阶段

- [ ] 每个 PR 自动跑测试
- [ ] 自动跑 lint/typecheck
- [ ] 使用另一个模型做代码审查
- [ ] 审查重点包括：
  - 是否满足需求
  - 是否破坏现有逻辑
  - 是否引入隐性复杂度
  - 是否存在安全问题
  - 是否有未处理边界情况
- [ ] 审查不通过则让执行代理继续修复

###### D. 人类决策阶段

- [ ] 人类只审查准备合并的 PR
- [ ] 人类关注：
  - 产品意图是否正确
  - 架构方向是否合理
  - 风险是否可接受
- [ ] 保留人工最终合并权

| 角色 | 模型类型 | 输出物 |
|---|---|---|

| Reviewer | 审查模型 / 静态分析工具 | 问题列表、修改建议 |

##### 4. 反方与张力

###### 4.1 成本问题

热门回复中有人提到：

> 如果每天多次运行这个循环，成本会变得重要。

这是现实张力。

Planner 用高推理模型，多个子代理并行执行，再加上审查模型，成本可能迅速上升。

适合：

- 高价值功能
- 复杂代码库
- 风险较高的变更
- 团队希望提升吞吐的场景

不一定适合：

- 小改动
- 低价值实验
- 简单 CRUD
- 成本极度敏感的早期项目

可行策略：

- 简单任务用单代理
- 复杂任务才启用 planner + subagents
- 只对高风险 PR 开启强审查
- 使用便宜模型做初审，强模型做终审

---

###### 4.2 多代理不一定天然更好

多代理系统的问题是：

- 协调成本高
- 上下文传递可能丢失
- 子代理可能误解 planner 意图
- PR 之间可能产生冲突
- 失败排查更复杂

所以多代理不是银弹。

关键不是“代理数量越多越好”，而是：

> 是否有清晰边界、接口和验收标准。

---

###### 4.3 人类仍然不可替代

作者最后一步仍然是：

> 我手动审查准备合并的 PR 并合并。

这说明当前 AI 编程还没完全自动化。

人类的价值转向：

- 不再逐行写代码
- 而是定义目标、看架构、控风险、做最终判断

这会改变开发者角色：

> 从 coder 变成 AI 工程流程的 orchestrator。

---

###### 4.4 “更快”与“更彻底”的冲突

作者说：

- 比 xhigh solo 更快
- 比 Composer solo 更彻底

这正是系统设计的权衡：

| 模式 | 优点 | 缺点 |
|---|---|---|
| 强模型 solo | 深度强、理解好 | 慢、贵、执行效率低 |
| 快模型 solo | 速度快、成本低 | 规划弱、容易漏问题 |
| Planner + Subagents | 兼顾速度和质量 | 系统复杂度更高 |

所以最佳解通常不是单点最优，而是系统组合最优。

---

##### 5. 情境化落地

###### 5.1 对个人开发者

如果你是独立开发者，不一定要一开始就搭复杂多代理系统。

可以先用简化版：

1. 用强模型做需求拆解
2. 让 Cursor/Claude Code/其他工具按小任务实现
3. 每次只改一个范围
4. 改完让另一个模型审查
5. 你最终合并

重点是形成习惯：

> 先计划，再执行，再审查，而不是边聊边乱改。

---

###### 5.2 对创业团队

对于小团队，最有价值的是把它变成“研发吞吐系统”。

可以设计如下流程：

```text
产品需求
  ↓
AI Planner 拆任务
  ↓
生成多个工程子任务
  ↓
AI 子代理并行实现
  ↓
自动测试 + AI Review
  ↓
人类 Tech Lead 合并
```

适用场景：

- 快速做 MVP
- 修复大量 bug
- 迁移老代码
- 重构局部模块
- 补测试
- 写 SDK / API 封装
- 文档与代码同步

---

###### 5.3 对 AI 产品公司

如果你在做 AI coding 产品，真正的竞争点可能不是“接入最强模型”，而是：

- 多代理编排
- 上下文管理
- 任务拆解能力
- Git 工作流集成
- PR 审查质量
- 自动修复闭环
- 成本控制
- 可观测性与评测

也就是从“聊天界面”升级为“AI 软件工程操作系统”。

---

###### 5.4 对企业内部系统

企业更关注：

- 权限
- 审计
- 可回滚
- 安全
- 质量标准
- 成本可控
- 与现有研发流程兼容

因此落地时应优先建设：

- Git 分支隔离
- PR 审查机制
- 自动测试
- 模型调用日志
- 成本监控
- 代码安全扫描
- 人类审批节点

企业场景下，AI 代理不能绕过流程，而应嵌入流程。

---

##### 6. 最终提炼

这条内容最值得带走的是：

> **未来高效的 AI 开发不是“一个超级模型搞定一切”，而是“强规划模型 + 快速执行代理 + 严格审查机制 + 人类最终决策”的工程化系统。**

可以总结为一个公式：

```text
AI 开发效率 = 好规划 × 并行执行 × 严格审查 × 人类把关
```

真正的竞争力不只是会用 AI 写代码，而是会设计 AI 协作流程。
