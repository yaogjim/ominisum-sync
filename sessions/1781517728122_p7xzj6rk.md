## 分析要点

- **核心高价值点**：“蓝图”将确定性工作流与Agent自由决策结合，把LLM限制在合适边界内，从而提升可靠性、降低token和CI成本。
- **留存建议**：长期保留（文章系统展示了大规模无人值守编码Agent的基础设施、编排模式、上下文管理和反馈闭环设计，对AI工程化和开发者效率体系建设有较高参考价值。）

**知识要点**

- 大规模无人值守编码Agent需要可并行、可预测、隔离且快速就绪的云端开发环境。
- devbox 作为标准化、可替换、预热的开发环境，既提升人类效率，也天然适合作为Agent运行沙箱。
- 蓝图机制把确定性节点和Agent节点组合成状态机，适合在关键步骤中控制风险和成本。
- 规则文件应尽量按目录或文件模式局部加载，避免全局上下文污染和窗口浪费。
- 中心化MCP工具层可以让多个Agent系统共享能力，但需要工具权限、安全边界和任务相关工具筛选。
- Agent反馈应尽量左移，通过本地lint、自动修复和有限CI迭代减少无效成本。

**行动项**

- 评估自身团队是否具备可快速创建、隔离、预热的云端开发环境作为Agent执行基础。
- 在Agent流程中区分确定性步骤和LLM决策步骤，将lint、格式化、推送、测试等固定动作改为确定性节点。
- 设计类似蓝图的Agent编排框架，用状态机管理实现、验证、修复、提交等阶段。
- 梳理代码库规则文件，优先按目录或文件模式提供局部上下文，而不是堆叠全局提示。
- 建立统一工具层或MCP服务，并按任务为Agent提供最小必要工具集。
- 为编码Agent设置有限轮次的本地检查与CI反馈循环，避免无限迭代造成成本失控。

**yibie**

\# Stripe Minions 第二部分：底层是怎么搭建的

本文是 Stripe 编码 Agent 系列的第二篇。回顾一下第一篇：Minions 是 Stripe 自研的无人值守 Agent 编码流程。\*\*每周有超过 1,300 个 Stripe Pull Request（第一篇发布时还是 1,000）完全由 Minion 生成\*\*，经过人类审查，但不包含任何人类编写的代码。

如果你还没读第一篇，建议先看一下，了解 Minions 的开发者体验。本文深入探讨构建细节，聚焦 Minion 流程中 Stripe 特有的部分。

\### Devbox：热乎的，准备好了

为了在大规模下实现最高效率，无人值守 Agent 编码需要一个可并行、可预测、隔离的云端开发环境。人类应该能够给多个 Agent 分配逻辑上独立的工作。Agent 应该有干净的环境和工作目录：如果 Agent 之间互相干扰对方的改动，就会白白浪费 token 在冲突解决上。完全自主还要求 Agent 在系统层面与特权或敏感机器隔离开，尤其不能使用人类的个人凭据。

要让 Agent 在开发者的笔记本电脑上满足所有这些条件，非常困难。容器化或 git worktree 可以帮上忙，但很难组合使用，而且从根本上说，要构建一个既拥有开发者 shell 的全部能力、又被适当约束的本地 Agent，是极具挑战的。

不过，Stripe 的 Minions 天然具备这些特性，因为它们运行在 Stripe 工程师使用的标准开发环境上：\*\*devbox\*\*。

一个 Stripe devbox 是一台 AWS EC2 实例，包含我们的源代码并运行正在开发中的服务。大多数人类编写的 Stripe 代码，本身就是在通过 SSH 远程连接到 devbox 的 IDE 中产生的。用 DevOps 的话说，devbox 是"牲口，不是宠物"：它们是标准化的、易于替换的，而不是定制的、长期存活的。

许多工程师每个任务用一个 devbox，一个 Stripe 工程师可能同时开着半打。

&gt; 一张工程师活跃 devbox 列表截图，包含 Minion 运行

我们希望启动新 devbox 毫不费力，因此目标是 10 秒内就绪。为了达到这个"热乎且就绪"的标准，我们主动预配和预热一个 devbox 池子，让它们在开发者需要时处于待命状态。这包括克隆巨大的 git 仓库、预热 Bazel 和类型检查缓存、启动在 devbox 上持续运行的代码生成服务等等。10 秒后，devbox 的所有者就拥有了一台检出了 Stripe 所有主仓库最新 master 分支的机器，可以立即打开 REPL、运行测试、修改代码并做类型检查，或者启动一个 Web 服务。

devbox 是为人类工程师的需求而构建的，远在 LLM 编码 Agent 出现之前。事实证明，\*\*并行、可预测、隔离\*\*这些特性也正是 Stripe 工程师高效工作所需要的。对人好的，对 Agent 也好。建立在这个基础设施原语之上，为 LLM Agent 提供了一个天然的归宿，产生了复利式的回报。

\### Agent 本身

与早已服务于人类开发的 devbox 不同，我们的 Agent 框架是专门为 Minions 这个场景定制构建的。

2024 年底，随着编码 Agent 在行业中兴起，我们内部 fork 了 \[Block 的 goose\]([https://github.com/block/goose](https://github.com/block/goose))，这是最早被广泛使用的编码 Agent 之一。我们定制它以适配 Stripe 的 LLM 基础设施。随着时间推移，我们把 goose 的功能开发聚焦于 Minions 的需求，而非人类监督工具的需求：后者已经被 Cursor 和 Claude Code 等第三方工具很好地满足了，我们的工程师已经在使用它们。

事实上，\*\*Minions 最独特的特征是没有人监督。\*\* 现成的本地编码 Agent 通常被优化为工程师的搭档，工作时工程师基本上"在旁看着"。但 Minions 是完全无人值守的，因此我们的 Agent 框架不能使用面向人类的功能，比如可打断性或人类触发的命令来启动或引导 Agent 运行。

另一方面，隔离的 devbox 环境意味着 Agent 不需要确认提示；任何 Agent 可能犯的错误，都被限制在一个 devbox 的有限爆炸半径内，因此我们可以安全地以完整权限运行 Agent，跳过确认提示。

我们还可以精确调校优化，完全适配 Stripe 的开发流程。我们基于 Stripe 系统的特性做了许多小的优化。一个更大的优化，事实证明对 Minions 的实现更为根本，是\*\*蓝图（blueprint）\*\* 的概念。

\### 蓝图

编排 LLM 流程最常用的原语是\[工作流和 Agent\]([https://anthropic.com/engineering/building-effective-agents…](https://anthropic.com/engineering/building-effective-agents))。工作流是一种通过固定的步骤图来运行的 LLM 系统，图中的每个节点负责整体目标中一个窄范围的部分，预定义的边控制着这些离散节点之间的执行流程。

而 Agent 通常是一种更简单的"循环加工具"的编排模式，LLM 依靠自己的判断反复调用手中的工具，并根据工具调用的结果决定下一步该做什么。

Minions 用我们称之为"蓝图"的原语来编排。\*\*蓝图是在代码中定义的工作流，用来指挥一次 Minion 运行。\*\* 蓝图结合了工作流的确定性和 Agent 在面对未知时的灵活性：一个给定的节点可以运行确定性代码，也可以运行一个专注于特定任务的 Agent 循环。本质上，蓝图就像一组 Agent 技能与确定性代码的交织编排，让每个子任务都能以最合适的方式处理。

比如，在驱动 Minions 的蓝图中，有标签为"实现任务"或"修复 CI 失败"的 Agent 式节点。这些 Agent 节点被给予很大的自由度，可以根据输入自己做决定。然而，蓝图中也有标签为"运行配置的 linter"或"推送更改"的节点，它们是\*\*完全确定性\*\*的：这些节点根本不调用 LLM——它们只是运行代码。

因此，蓝图是一种在 Agent 运行中保证某些子任务被确定性完成的方式。Minion 的蓝图最终看起来像一个状态机，交织着确定性代码节点和自由流动的 Agent 节点。

&gt; 示例蓝图。确定性节点用矩形表示，Agent 子任务用云形表示。

根据我们的经验，\*\*用代码确定性完成那些我们可以预见的小决策\*\*——比如"在运行结束时总是 lint 修改"——在大规模下节省了 token（和 CI 成本），也让 Agent 少了一些出错的机率。总体而言，我们发现"把 LLM 放进围起来的盒子里"，会累积成系统级的可靠性提升。蓝图机制让这些子 Agent 的上下文工程变得容易，无论是约束工具、修改系统提示，还是根据需要简化对话上下文。

各个团队也可以设置针对自己特定需求优化的蓝图。例如，有团队构建了自定义蓝图，用来在代码库中运行棘手的、LLM 辅助的迁移，而这种迁移无法用简单的全确定性 codemod 完成。

\### 上下文收集：规则文件

在像 Stripe 这样的大型代码库中，一个毫无指引的 Agent 可能会在遵循最佳实践或使用正确库方面遇到麻烦，即使有好的 linter 也无济于事。为了解决这个问题，各种 Agent 规则格式——比如 CLAUDE.md 或 AGENTS.md——允许 Agent 在遍历目录结构时自动"了解"代码库。

由于我们仓库的规模，我们对无条件全局规则的使用非常克制，否则 Agent 的整个上下文窗口还没开始就会被规则填满。相反，\*\*我们几乎完全让 Minions 从限定在特定子目录或文件模式下的文件中获取上下文\*\*，这些文件在 Agent 遍历文件系统时自动附加。

从我们的角度看，最好避免规则文件的重复，让我们的 Agent 读取与人类导向的 Agent 相同的上下文。基于此，我们标准化了支持这些功能的主流规则格式——\[Cursor 的规则格式\]([https://cursor.com/docs/context/rules…](https://cursor.com/docs/context/rules))——并修改了我们的框架，使 Minions 既能读取这些规则，也能读取之前的自研格式。

我们现在还将 Cursor 规则同步为 Claude Code 也能读取的格式，这样我们三个最流行的编码 Agent（Minions、Cursor 和 Claude Code）都能从 Stripe 工程师在代码库中搭建的规则文件中受益。

\### 上下文收集：MCP

从文件系统读取对静态上下文收集很有效，但 Agent 经常需要通过联网工具调用动态获取信息。特别是，为了充分充实用户请求，Minions 需要检索内部文档、工单详情、构建状态、代码智能等信息。MCP（Model Context Protocol）发布后迅速成为联网工具调用的行业标准，我们将 Minions 与之集成。

Stripe 已经构建或集成了大量运行在不同框架上的 Agent：无代码内部 Agent 构建器、在专用服务上运行的自定义 Agent、第三方现成 Agent、命令行 Agent 工具和其他编码 Agent，以及 Agent Slack 机器人。所有这些 Agent（不仅仅是 Minions）都需要 MCP 能力，而且常常包含重叠的工具集。

为了支持所有这些，\*\*我们构建了一个中心化内部 MCP 服务器，叫做 Toolshed\*\*，它让 Stripe 工程师可以轻松编写新工具，并使其自动被我们的 Agent 系统发现。我们所有的 Agent 系统都能够将 Toolshed 作为一个共享能力层来使用；向 Toolshed 添加一个工具，就立即赋予了我们整个由数百个不同 Agent 组成的舰队新的能力。

Toolshed 目前包含近 \*\*500 个 MCP 工具\*\*，涵盖内部系统和我们使用的 SaaS 平台。Agent 在被给予一个"更小的盒子"和精心筛选的工具集时表现最佳，因此我们配置不同的 Agent 只请求与它们任务相关的 Toolshed 工具子集。Minions 也不例外，默认只提供一个有意缩小范围的工具子集，但每个用户可自定义，允许工程师为自己的 Minions 配置额外的按主题分组的工具集。

由于 Minions 完全自主运行，可以自由调用其 MCP 工具，我们还有一个内部安全控制框架，确保它们不能使用工具执行破坏性操作。不过，作为第一道防线，我们的 devbox 本身就运行在 QA 环境中，因此 Minions 无法访问真实用户数据、Stripe 的生产服务或任意外部网络。这不是巧合：我们有意构建了隔离的 devbox，让人类有一个可以安全实验的环境。而正如其他很多事情一样，\*\*对人类安全的开发环境，对 Minions 同样有用。\*\*

\### ……然后迭代

虽然我们构建 Minions 的目标是一次性完成任务，但给 Agent 提供可以迭代对抗的自动化反馈，是推动进展的关键。Stripe 庞大的既有测试库——超过 300 万个测试——可以提供这种反馈。然而，虽然推送的分支会在 CI 中运行所有相关测试，但我们不想过度依赖 CI 来获取所有代码反馈。

在考虑开发者生产力时，我们尽量遵循"反馈左移"的原则。这个说法意味着，如果我们知道某个自动化检查会在 CI 中失败，最好让它在 IDE 中也被强制执行，并立即呈现给工程师，因为这是向用户提供反馈的最快方式。

例如，我们有 pre-push 钩子来修复最常见的 lint 问题。一个后台守护进程会预计算适用于某次改动的 lint 规则启发式，并缓存运行这些 lint 的结果，因此开发者在推送时通常可以在远少于一秒的时间内获得 lint 修复。

Minions 自然也融入了这个框架，因此它们不必浪费 token 或 CI 时间在与自动格式化工具之类的反复交互上。我们在 Agent 的开发循环蓝图中将一组 linter 作为确定性节点运行，并在推送 Agent 分支之前在本地对该 lint 节点进行循环，这样分支在第一次跑 CI 时就有较大机率通过。

在本地运行所有测试是不可行的，因此我们也在标准 Minion 蓝图中包含了一轮针对完整 CI 套件的迭代。在 Minion 推送更改后，我们运行 CI，并自动应用任何针对失败测试的自动修复。如果有无法自动修复的失败，我们将失败信息返回给蓝图中的 Agent 节点，给 Minion 一次在本地修复失败测试的机会。在第二次推送和 CI 运行之后，我们将分支交还给人类操作员，由人工审查。

为什么只有一到两轮 CI？在速度和完整性之间需要平衡；CI 运行消耗 token、算力和时间，我们认为让 LLM 无限运行多轮完整 CI 循环，边际收益递减。我们认为这个策略在各方考量之间取得了很好的平衡。

\### 总结

Minions 只是 Stripe 使用 AI 加速工程师工作的方式之一，但我们认为它是如何将行业标准概念——如 Agent 框架和 MCP——与我们自己的内部工具和基础设施融合的一个很好的范例。这些工具和基础设施是 Stripe 工程师多年来为最大化开发者生产力而不懈调校的成果。

无论是通过改进文档、开发者环境，还是迭代循环，我们一次又一次地发现，\*\*这些年来在人类开发者生产力上的投入，在 Agent 的世界里产生了复利式的回报。\*\*

Minions 已经改变了 Stripe 软件工程的格局。我们持续改进它们，融入行业内最新最好的成果，并适配 Stripe 的规模。结合我们在人类开发者体验的硬仗中获得的口味和专业知识，我们会将 Minions 打造到最好的水平。

#### Stripe Minions：无人值守编码 Agent 的底层架构总结

##### 一句话概括

Stripe 的 Minions 是一套大规模运行的无人值守 AI 编码系统，每周已生成超过 1,300 个 PR。它的成功不只是模型能力，而是建立在成熟的云端开发环境、确定性工作流、上下文体系、工具平台和自动反馈闭环之上。

---

##### 1. 核心基础：Devbox 云端开发环境

Stripe 的 Minions 运行在内部标准开发环境 **devbox** 上。

devbox 是预配置好的 AWS EC2 开发机，包含代码库、缓存、服务、测试环境等，工程师本来也通过它远程开发。

它的关键价值：

- **并行**：多个 Agent 可同时处理不同任务
- **隔离**：每个 Agent 有独立环境，互不干扰
- **可预测**：环境标准化，减少意外问题
- **安全**：不使用人类凭据，不接触生产环境
- **快速启动**：预热池保证约 10 秒内可用

核心洞察是：  
**过去为提升人类开发效率建设的基础设施，天然也适合 AI Agent。**

---

##### 2. Agent 框架：为无人值守场景定制

Stripe 最初基于 Block 的开源 Agent 框架 goose 进行改造，但重点不是做“人类结对助手”，而是服务 Minions 的无人值守编码流程。

和 Cursor、Claude Code 这类工具不同，Minions 的特点是：

- 不需要工程师实时监督
- 不依赖人工中途确认
- Agent 可在隔离环境中拥有完整权限
- 错误影响被限制在单个 devbox 内

因此，Minions 更像一个自动执行任务的工程系统，而不是一个聊天式编程助手。

---

##### 3. 蓝图机制：把 Agent 放进可控流程里

Stripe 用 **Blueprint（蓝图）** 编排 Minions 的运行流程。

蓝图结合了两类能力：

###### 确定性节点

不调用 LLM，只执行明确代码逻辑，例如：

- 运行 linter
- 推送代码
- 执行格式化
- 触发测试

###### Agent 节点

调用 LLM，自主完成复杂任务，例如：

- 实现需求
- 修复 CI 失败
- 理解代码上下文
- 调整实现方案

这种设计让 Minions 既有灵活性，又不会把所有事情都交给 LLM 猜。

核心原则是：  
**能确定性完成的事情，就不要浪费 token 让模型做。**

---

##### 4. 上下文体系：让 Agent 理解大型代码库

在 Stripe 这种大型代码库中，Agent 如果没有上下文，很容易用错库、违背规范或误解架构。

Stripe 通过两类方式补充上下文。

###### 规则文件

Stripe 支持类似 Cursor Rules、CLAUDE.md、AGENTS.md 的规则体系。

但由于代码库庞大，它们避免使用大量全局规则，而是让规则绑定到具体目录或文件模式。

这样做的好处是：

- 避免上下文窗口被无关规则塞满
- 让 Agent 只读取当前任务相关规范
- 人类工具和 Minions 共用同一套规则

###### MCP 工具

对于动态信息，Stripe 通过 MCP 获取，例如：

- 内部文档
- 工单详情
- 构建状态
- 代码智能
- SaaS 系统数据

Stripe 建了一个中心化内部 MCP 服务器 **Toolshed**，目前有近 500 个工具。

它相当于所有 Agent 的共享能力层：  
**一个工具接入 Toolshed，就能被多个 Agent 系统复用。**

---

##### 5. 安全边界：能力开放，但环境受控

Minions 可以自主调用工具，但 Stripe 通过多层机制限制风险：

- devbox 运行在 QA 环境
- 无法访问真实用户数据
- 无法访问生产服务
- 无法任意访问外部网络
- MCP 工具有内部安全控制
- 不给 Agent 默认开放所有工具，只按任务配置子集

这说明大规模 Agent 系统的安全不是靠“提示词约束”，而是靠基础设施隔离和权限设计。

---

##### 6. 自动反馈闭环：让 Agent 自己迭代

Stripe 拥有超过 300 万个测试，Minions 会利用这些测试进行自动反馈。

但它们不会完全依赖 CI，而是把反馈尽量前置：

- 本地先运行 linter
- 自动修复格式和常见 lint 问题
- 推送前先做确定性检查
- 推送后跑 CI
- 对失败测试尝试自动修复
- 最多进行一到两轮 CI 迭代
- 最后交给人类审查

这种策略平衡了：

- 成功率
- 成本
- 速度
- token 消耗
- CI 资源消耗

---

##### 7. 最重要的产品启示

Stripe Minions 的价值不只是“用了 AI 写代码”，而是把 AI 放进了一个成熟的软件工程系统中。

关键启示包括：

1. **Agent 能力取决于系统环境，而不只是模型**
2. **好的开发者基础设施，会在 AI 时代产生复利**
3. **确定性流程和 LLM 灵活性需要结合**
4. **上下文管理是大型代码库 Agent 成败关键**
5. **安全要靠环境隔离和权限控制，而不是靠模型自觉**
6. **自动反馈闭环决定 Agent 能否稳定产出可合并代码**

---

##### 总结

Stripe Minions 是一个典型的“AI + 工程基础设施”范例。

它之所以能每周自动生成上千个 PR，不是因为单点 Agent 很强，而是因为 Stripe 把：

- 云端开发环境
- Agent 框架
- 工作流蓝图
- 规则上下文
- MCP 工具平台
- 测试与 CI 反馈
- 安全隔离机制

组合成了一套完整的无人值守编码系统。

最终结论是：  
**AI 编码 Agent 的规模化落地，本质上是软件工程能力、开发者体验和自动化基础设施的综合竞争。**

## 结构化（1）

### 2026-06-15 10:30:35

#### Stripe Minions 第二部分：底层是怎么搭建的｜精炼总结

Stripe 的 Minions 是一套无人值守的 AI 编码 Agent 流程，能独立生成代码、提交 PR，并由人类审查。目前每周已有 **超过 1,300 个 Stripe PR 完全由 Minion 生成**，本文重点介绍其底层基础设施和工程设计。

---

##### 1. Devbox：为 Agent 准备好的云端开发环境

Stripe 的 Minions 并不是运行在工程师本地电脑上，而是运行在 Stripe 标准化的云端开发环境 **devbox** 中。

关键点：

- **devbox 是 AWS EC2 实例**，包含 Stripe 源代码，并能运行开发中的服务。
- Stripe 工程师平时也通过 SSH 连接 devbox 写代码，因此这套环境原本就是为人类开发者设计的。
- devbox 具备三个对 Agent 很重要的特性：
  - **可并行**：多个 Agent 可以同时处理不同任务。
  - **可预测**：环境标准化，减少不确定性。
  - **隔离性强**：不同 Agent 之间不会互相干扰，也不会使用人类个人凭据。

Stripe 会提前预配和预热 devbox 池，包括：

- 克隆大型 Git 仓库；
- 预热 Bazel 和类型检查缓存；
- 启动代码生成服务；
- 保证新 devbox 在 **10 秒内可用**。

作者强调：这些能力最初是为提升人类工程师效率建设的，但后来也天然适合 AI Agent，形成了“对人好，对 Agent 也好”的复利效果。

---

##### 2. Agent 框架：专为无人值守场景定制

Stripe 的 Agent 框架最初 fork 自 Block 的开源编码 Agent **goose**，之后逐步改造成适合 Minions 的内部框架。

与 Cursor、Claude Code 这类“有人监督”的编码助手不同，Minions 的核心特点是：

> **没有人实时监督。**

因此它的设计重点不同：

- 不依赖人类随时打断或手动引导；
- 不需要频繁弹出确认提示；
- 因为运行在隔离 devbox 中，即使出错，影响范围也有限；
- 可以让 Agent 拥有较完整权限，提高自动化效率。

换句话说，Minions 不是工程师旁边的“副驾驶”，而是可以被派出去独立完成任务的“无人执行者”。

---

##### 3. 蓝图 Blueprint：把确定性流程和 Agent 灵活性结合起来

Stripe 为 Minions 设计了一个核心编排机制：**蓝图（Blueprint）**。

蓝图可以理解为用代码定义的一套 Agent 执行流程，结合了两种方式：

1. **确定性工作流**  
   适合明确、固定的步骤，比如：
   - 运行 linter；
   - 推送代码；
   - 执行格式化；
   - 触发 CI。

2. **Agent 节点**  
   适合需要判断和探索的任务，比如：
   - 实现功能；
   - 修复 CI 失败；
   - 理解代码上下文。

例如，一个 Minion 的蓝图可能包含：

- “实现任务”节点：由 LLM Agent 自主完成；
- “运行配置好的 linter”节点：完全不调用 LLM，只执行固定代码；
- “修复 CI 失败”节点：再次交给 Agent 分析和修改；
- “推送更改”节点：确定性执行。

这种设计的好处是：

- 能减少不必要的 token 消耗；
- 降低 Agent 在简单步骤上出错的概率；
- 让 LLM 只处理真正需要推理和判断的部分；
- 让整个流程更像一个可靠的状态机。

Stripe 的经验是：  
**能用代码确定的步骤，就不要交给 LLM 自由发挥。**

---

##### 4. 上下文收集：通过规则文件理解代码库

在 Stripe 这样的大型代码库中，如果 Agent 没有上下文，很容易：

- 用错内部库；
- 不遵守团队最佳实践；
- 忽略特定目录的约定。

为此，Stripe 使用类似 **CLAUDE.md、AGENTS.md、Cursor Rules** 的规则文件，让 Agent 在浏览代码目录时自动获取相关说明。

但由于 Stripe 代码库很大，他们不会把大量规则全部放进全局上下文，否则会迅速占满 LLM 的上下文窗口。

Stripe 的做法是：

- 尽量使用**限定在特定目录或文件模式下的规则文件**；
- Agent 进入相关目录时才加载对应规则；
- 标准化支持 **Cursor 的规则格式**；
- 同时将 Cursor 规则同步为 Claude Code 可读取的格式。

这样，Stripe 内部常用的三个编码 Agent：

- Minions；
- Cursor；
- Claude Code；

都能共享同一套代码库规则，减少重复维护。

---

##### 5. MCP 与 Toolshed：为 Agent 提供动态工具能力

除了静态规则文件，Minions 还需要动态获取信息，例如：

- 内部文档；
- 工单详情；
- 构建状态；
- 代码智能信息；
- SaaS 平台数据。

为此，Stripe 集成了行业标准 **MCP（Model Context Protocol）**，并构建了一个中心化内部 MCP 服务器：**Toolshed**。

Toolshed 的作用是：

- 让工程师可以方便地编写新工具；
- 让工具自动被 Stripe 的各类 Agent 系统发现；
- 作为所有 Agent 的共享能力层。

重要数据：

- Toolshed 当前包含近 **500 个 MCP 工具**；
- 覆盖 Stripe 内部系统和使用的 SaaS 平台；
- 服务的不只是 Minions，而是 Stripe 内部数百个不同 Agent。

不过，Stripe 并不会把所有工具都开放给每个 Agent，而是根据任务筛选工具集：

- Agent 工具越精简，表现通常越好；
- Minions 默认只获得一组较小的工具；
- 用户可以按主题为自己的 Minions 增加工具。

安全方面：

- Minions 不能通过工具执行破坏性操作；
- devbox 运行在 QA 环境中；
- 无法访问真实用户数据、生产服务或任意外部网络。

---

##### 6. 反馈与迭代：让 Agent 在自动检查中改进代码

虽然 Minions 的目标是“一次性完成任务”，但 Stripe 仍然会给它们自动化反馈，让它们有机会修正问题。

Stripe 拥有庞大的测试体系：

- 超过 **300 万个测试**；
- PR 分支会在 CI 中运行相关测试。

但 Stripe 不希望所有问题都等到 CI 才发现，而是遵循“反馈左移”原则：

> 能在本地或 IDE 阶段发现的问题，就不要拖到 CI。

例如：

- pre-push 钩子会自动修复常见 lint 问题；
- 后台守护进程会预计算 lint 规则；
- 开发者通常能在 **远少于 1 秒** 的时间内获得 lint 修复结果。

Minions 也复用了这套机制：

- 在蓝图中加入确定性的 linter 节点；
- 推送分支前先在本地循环修复 lint；
- 尽量让第一次 CI 就通过。

对于完整 CI：

1. Minion 推送代码；
2. CI 运行；
3. 系统自动修复可自动处理的失败；
4. 如果仍有失败，把失败信息交回 Agent；
5. Agent 尝试本地修复；
6. 第二次推送和 CI 后，交还给人类审查。

Stripe 通常只让 Minions 进行 **一到两轮 CI 迭代**，原因是：

- CI 消耗 token、算力和时间；
- 无限循环的边际收益会递减；
- 需要在速度和完整性之间平衡。

---

##### 7. 总结：多年开发者基础设施投入，在 Agent 时代产生复利

Minions 是 Stripe 用 AI 提升工程效率的代表案例。它并不是单纯依赖 LLM，而是把行业标准技术和 Stripe 多年积累的内部基础设施结合起来，包括：

- Agent 框架；
- MCP；
- devbox；
- 规则文件；
- CI 和测试体系；
- 开发者反馈循环。

文章的核心观点是：

> Stripe 多年来为人类开发者生产力所做的投入，在 AI Agent 时代产生了复利回报。

Minions 已经显著改变了 Stripe 的软件工程方式。Stripe 会继续改进它，吸收行业最新成果，并结合自身大规模工程实践，把无人值守编码 Agent 做得更可靠、更高效。

##### 2. 最重要的洞见

###### 洞见 1：Agent 的规模化前提，不是智能，而是“可并行、可隔离、可预测”的环境

###### **核心观点：**  
> 无人值守 Agent 真正需要的不是本地 IDE 插件，而是一个干净、隔离、随时可销毁的云端开发环境。

**为什么重要：**  
大多数人讨论 AI 编码时，关注模型、提示词、IDE；Stripe 关注的是：  
- Agent 之间不能互相污染环境  
- Agent 不能使用人类个人凭据  
- 每个任务都应有独立工作区  
- 失败成本必须被限制在小范围内  

这才是从“个人效率工具”走向“组织级生产系统”的前提。

**反常识之处：**  
常见认知是：Agent 应该贴近开发者本地环境。  
Stripe 的判断相反：**本地环境太个性化、太脆弱、太难治理，不适合无人值守 Agent。**

**可迁移价值：**  
任何想规模化 AI 工作流的组织，都应先问：  
> 我们有没有一个“AI 可以安全犯错”的标准化沙盒？

没有这个，Agent 越强，风险越大。

**我应该记住什么：**  
> Agent 工程的第一性问题不是“让它会做事”，而是“让它能安全、并行、低成本地失败”。

---

###### 洞见 2：最强的 Agent 架构不是纯 Agent，而是“确定性流程 + 局部自由”

###### **核心观点：**  
> Stripe 的蓝图机制，本质是在工作流和 Agent 之间取中间态：能确定的地方用代码，不能确定的地方才交给 LLM。

**为什么重要：**  
纯 Agent 最大的问题是：  
- 它会把简单确定任务也变成推理任务  
- 消耗 token  
- 增加不确定性  
- 放大偶发错误  

Stripe 的做法是：  
- lint、push、运行固定检查：确定性代码  
- 实现任务、修复 CI：Agent 节点  
- 整体由状态机编排  

**反常识之处：**  
很多人以为 Agent 越自主越高级。  
Stripe 的经验是：**把 LLM 关进更小的盒子里，系统反而更可靠。**

**可迁移价值：**  
设计 AI 系统时，不要问“哪些任务能让 AI 做”，而要问：  
> 哪些环节不该让 AI 判断？

AI 应负责不确定性；确定性应交给程序。

**我应该记住什么：**  
> 好的 Agent 系统不是释放智能，而是约束智能。

---

###### 洞见 3：给人类开发者打磨的基础设施，会在 Agent 时代产生复利

###### **核心观点：**  
> Stripe 的 Minions 之所以能跑起来，不是因为专门为 Agent 从零搭了一套系统，而是因为过去多年为人类开发效率建设的 devbox、测试、lint、缓存、规则文件、CI 反馈，天然适配了 Agent。

**为什么重要：**  
这说明 AI 转型不是“另起炉灶”，而是对组织工程成熟度的一次放大。  
原本优秀的开发基础设施，会变成 Agent 的生产力底座；原本混乱的工程体系，也会被 Agent 放大成混乱。

**反常识之处：**  
很多组织以为引入 Agent 可以绕过工程治理。  
实际上，Agent 更依赖工程治理。

**可迁移价值：**  
在任何组织里，AI 落地效果往往取决于此前的系统质量：  
- 文档是否结构化  
- 测试是否充分  
- 权限是否清晰  
- 环境是否标准化  
- 反馈是否快速  
- 工具是否可组合  

**我应该记住什么：**  
> AI 不会替代工程成熟度，它会放大工程成熟度。

---

###### 洞见 4：上下文不是越多越好，而是越“局部、相关、可自动发现”越好

###### **核心观点：**  
> Stripe 避免大量全局规则，而是让 Agent 根据目录和文件模式自动加载局部规则。

**为什么重要：**  
大型代码库中，上下文窗口是稀缺资源。  
如果把所有规则一次性塞给 Agent，会导致：  
- 上下文污染  
- 重要信息被稀释  
- token 浪费  
- 判断质量下降  

Stripe 的策略是：  
- 克制使用全局规则  
- 主要依赖目录级、文件模式级规则  
- 让 Minions、Cursor、Claude Code 共享同一套规则格式  

**反常识之处：**  
常见做法是“把更多背景喂给模型”。  
Stripe 的做法是：**只在模型走到相关位置时，才给它相关上下文。**

**可迁移价值：**  
知识管理、企业 AI、客服 Bot、内部 Copilot 都适用：  
> 上下文系统的关键不是知识总量，而是检索时机和作用域控制。

**我应该记住什么：**  
> 上下文工程的目标不是“多”，而是“刚好在需要时出现”。

---

###### 洞见 5：反馈左移，比让 Agent 多跑几轮更重要

###### **核心观点：**  
> Stripe 不让 Agent 无限循环跑 CI，而是把 lint、格式化、常见错误修复尽量前移到本地确定性节点，只保留有限 CI 迭代。

**为什么重要：**  
Agent 自主迭代听起来很强，但完整 CI 代价高：  
- 慢  
- 贵  
- 消耗 token  
- 边际收益递减  

Stripe 的策略是：  
1. 本地先跑确定性 lint / fix  
2. 推送后跑 CI  
3. 自动修复可修复失败  
4. 再给 Agent 一次修复机会  
5. 最多一到两轮后交给人类  

**反常识之处：**  
常见想象是：让 Agent 自己不断试错直到通过。  
Stripe 的判断是：**无限迭代不是智能，而是成本失控。**

**可迁移价值：**  
任何 AI 自动化系统都应设计“反馈梯度”：  
- 便宜反馈尽早给  
- 昂贵反馈少量用  
- 高风险决策交还人类  

**我应该记住什么：**  
> 自动化不是无限循环，而是设计好每一轮反馈的成本和价值。

##### 3. 底层逻辑

###### **逻辑一：Agent 的可靠性来自系统约束，而不是模型自觉**

- 表层现象：  
  Minions 可以无人值守生成大量 PR。

- 深层原因：  
  Stripe 通过 devbox 隔离环境、蓝图约束流程、MCP 工具筛选、安全框架和有限 CI 迭代，把 Agent 的自由度控制在可承受范围内。

- 推导结论：  
  企业级 Agent 的核心能力不是“自主”，而是**受控自主**。

---

###### **逻辑二：确定性越多，LLM 越有价值**

- 表层现象：  
  Minion 蓝图中很多节点完全不调用 LLM。

- 深层原因：  
  LLM 擅长处理模糊任务，但不适合承担固定流程、重复检查、格式修复等确定性任务。

- 推导结论：  
  好的 AI 系统应尽量把确定性部分程序化，把 LLM 留给真正需要判断的部分。

---

###### **逻辑三：组织已有基础设施决定 Agent 上限**

- 表层现象：  
  Stripe 能让 Minions 每周生成 1300+ PR。

- 深层原因：  
  它已有成熟的 devbox、测试体系、lint 缓存、内部文档、MCP 工具层、规则文件和 CI 流程。

- 推导结论：  
  Agent 不是孤立产品，而是组织工程体系的放大器。  
  **基础设施越成熟，Agent 越容易规模化。**

## 深度解读（1）

### 2026-09-18 00:50:13

#### Stripe Minions 的壁垒不在模型，而在“可被自动化的工程系统”

Stripe 每周已有超过 **1,300 个 PR 完全由 Minions 生成**，人类只负责审查。真正值得关注的并不是编码模型又变强了，而是 Stripe 展示了：要让 Agent 从“交互式助手”变成无人值守的生产流程，核心工作是把环境、权限、上下文和反馈都改造成机器可以稳定使用的基础设施。

##### 自主性来自可控的失败，而不是更聪明的模型

Minions 可以不经确认、以完整权限操作，是因为每个任务都运行在独立 devbox 中：环境标准化、约 10 秒可用、不携带个人凭据，而且无法接触生产服务和真实用户数据。Agent 犯错时，损失被限制在一台随时可替换的机器内。

这修正了一个常见误解：**无人值守并不等于给予 Agent 无限自由，而是让它在边界清楚、失败成本有限的环境中自由行动。** 与其反复要求模型确认，不如从系统层面缩小“爆炸半径”。这套原则也适用于非编码 Agent：高风险动作应由权限和执行环境约束，而不能只靠提示词要求模型谨慎。

更重要的是，devbox 并非为 AI 新建。它原本用于解决人类工程师的环境一致性、并行开发与安全实验问题。Agent 只是继承了这些能力。由此可以得到一个更普遍的判断：**企业过去积累的开发者体验，正在转化为 Agent 的部署能力；反过来，长期欠下的工程效率债，也会成为 Agent 落地债。**

##### 最可靠的 Agent 系统，会主动减少需要模型判断的事情

Stripe 的“蓝图”把一次任务组织成状态机：实现功能、修复 CI 等未知度高的部分交给 Agent；运行 linter、推送代码等规则明确的步骤则使用确定性程序。模型并不负责所有动作，只负责那些无法提前写死的判断。

这种设计的价值不只是节省 token。每减少一个不必要的模型决策，就减少一次随机失败、错误调用工具或偏离流程的机会。**Agent 的系统能力不应以“模型能做多少”衡量，而应以“系统能把多少确定事项从模型手中拿走”衡量。**

同样的思路也体现在反馈循环中：本地先运行低成本检查，再进入完整 CI；CI 最多迭代一到两轮，随后交还人类。这里没有追求理论上的完全自治，而是在通过率、时间、算力与边际收益之间设定明确停止条件。

##### 上下文治理正在成为新的内部平台能力

Stripe 没有把整个代码库规则塞进上下文，而是按目录和文件类型动态加载；近 500 个 MCP 工具也不会全部暴露给 Agent，而是按任务提供最小集合。中心化 Toolshed 则让新工具可以同时服务 Minions、Cursor、Claude Code 等多种 Agent。

这意味着企业级 Agent 平台真正可复用的资产，可能不是某个 Agent 外壳，而是三类接口：**局部且可维护的知识、受权限控制的工具，以及快速可信的自动反馈。** 模型会快速更替，这些接口却能持续复用。

当然，文章只给出了 PR 数量，没有披露任务难度、人工拒绝率、返工率和净节省时间，因此还不能据此判断经济收益。但它已经提供了一个很实用的成熟度标准：如果一个团队的开发环境难以复制、规则散落在人脑中、测试反馈缓慢、权限边界模糊，那么优先升级模型通常不会解决无人值守 Agent 的核心问题。
