## 分析要点

- **核心高价值点**：任何需要可靠性的能力都应放在 harness 中，而不是依赖模型即兴遵守提示词。
- **留存建议**：长期保留，适合作为设计编码代理或评估智能体框架时的架构参考（文章系统梳理了编码代理 harness、工具契约、上下文投影、陈旧读取、slash 命令、Markdown 上下文和子代理等关键设计问题，具备较高方法论价值）

**知识要点**

- 编码代理的产品体验主要由 harness 决定，包括输入路由、提示构建、工具验证、权限策略、执行、结果裁剪和状态更新
- 转录记录不等于文件真相，框架必须维护文件基线、哈希、读取范围和陈旧状态，避免模型基于旧内容编辑代码
- 工具调用应被视为模型提出的权限请求，而不是普通函数调用，需要解析、验证、审批、执行、限流和审计
- 上下文不是完整历史，而是从持久日志、应用状态和当前任务中投影出的有界工作视图
- AGENTS.md 和 SKILL.md 的价值来自 harness 对其角色、作用域和加载时机的正确处理
- 子代理本质是父代理通过工具调用启动的受管理子运行时，应隔离上下文、权限和结果汇总

**行动项**

- 设计编码代理时，将工具生命周期拆分为解析、schema 验证、路径校验、权限策略、执行、结果裁剪、记录和状态更新
- 为文件读写建立基线机制，记录读取范围、mtime、size、hash 和完整性状态，编辑前强制检查是否陈旧
- 实现输入路由，将 /status、/reset、/audit、/goal 等控制命令在本地处理，不直接交给模型
- 将会话日志、模型可见上下文和应用状态分离，建立上下文投影与压缩策略
- 为 Markdown 规则文件区分角色：仓库级指令稳定加载，技能类文档按需渐进披露
- 在引入子代理前明确其角色、上下文切片、工具权限、结果格式和父子记录谱系

### 编码代理框架

模型成为焦点；

线束决定实际发生的事情。

#### 01\. 线束是产品

![Image](https://pbs.twimg.com/media/HMFmZbjWwAAMKhL?format=jpg&name=large)

为什么编码代理中最重要的部分往往是最不引人注目的部分。

每一次编码代理讨论最终都始于模型。

哪个模型？上下文有多少？它的编码能力怎么样？

那些问题很重要。它们只是我现在问的第一个问题。

第一个问题应该是：

> 线束拥有什么？

一个基础的 LLM 预测文本。

推理模型可以遵循结构、发出工具调用并在协议中工作。

代码代理更进一步。它将模型置于运行时环境中。该运行时环境能够检查真实的代码仓库、请求工具、编辑文件、运行检查、记住发生的事情，并在多轮对话中继续。

那个运行时就是这个框架。

对于编码代理而言，框架就是产品。

![Image](https://pbs.twimg.com/media/HMFmbG3WAAAFgsI?format=jpg&name=large)

#### 天真版本

一个小型编码代理通常以这样的循环开始：

> 用户请求 -&gt; 大提示词 模型响应 运行它要求的任何工具 -&gt; 将结果粘贴回提示词 -&gt; 重复

这个循环看起来很简单，因为验证、权限、结果限制和状态更新都被隐藏了。

这是一个有用的草图。它还不是一个真正的编码代理。

很快地，问题出现：

- 如果模型编辑了一个它从未读过的文件会怎样？
- 如果一个 Shell 命令接触到工作区之外的文件会怎么样？
- 如果一个工具返回50,000行输出会怎么样？
- 如果磁盘上的文件在记录仍然包含旧的读取内容时被修改，会怎样？
- 如果工具结果不再与产生它的工具调用相匹配，会怎么样？

缺失的部分不是更好的提示。缺失的部分是这个管理工具。

#### Harness 拥有什么

模型可以提出。工具决定什么能够成为现实世界中的效果。

这个简单的界面是：

> 模型(提示) → 回答

但一个有用的编码代理需要的不仅仅是答案。它需要工具生命周期、权限决策、对话记录、文件真实性和下一轮状态。

线束所属路径更接近：

> 输入路由 消息设计 提示词组装 -&gt; 模型输出 解析器 工具验证 权限策略 执行 有界结果 -&gt; 记录 + 状态更新 下一个回合

每一个箭头都是一个边界。

每个箭头都是安全带能够保护用户的地方，同时也是一个能够悄然失控的地方。

![Image](https://pbs.twimg.com/media/HMFmc2WWIAAh9WJ?format=jpg&name=large)

#### 编码代理工具必须做的六件事

我将编码代理框架归纳为六个核心职责。

1\. 实时仓库上下文

一个智能体不应从空提示开始。它需要工作区、当前文件、项目文档以及对真实代码仓库状态的安全视图。

2\. 提示形状

上下文质量往往看起来像是模型质量。稳定的前缀、清晰的工具契约、当前请求以及可控的历史，其改变行为的效果可能比更换模型更显著。

3\. 结构化工具

工具不是辅助函数。它们是模型提案与实际副作用之间的契约。

该工具解析参数、验证路径、检查策略、执行操作、截取输出并记录发生的事情。

4\. 上下文简化

如果处理框架盲目地添加所有内容，模型最终会接触到过多、过少或错误的内容。

良好的上下文是一种投射，而非一个不断膨胀的团块。

5\. 转录记录与内存

记录回答：发生了什么？

工作状态回答：现在什么是关键？

那些是不同的工作。它们不应该被视为同一个对象。

6\. 授权

子代理并非神奇的并行性。它们是拥有作用域工具、隔离状态和提炼结果的有边界工作者。

当委托被设计为受控上下文边界时，委托才变得有用。

#### 主循环

编码代理是一个观察-行动循环。有价值的部分发生在观察和行动之间。

模型位于循环内部：

> while tool\_steps &lt; max\_steps: prompt = build\_prompt( 工作区=工作区状态, 工具=tool\_schemas, memory=session\_memory, file\_state=file\_state, 历史=projected\_history, ) 输出 = 模型.生成(提示词) action = 解析模型输出(output) 如果 action.kind == "final": return action.text result = 验证授权执行记录(action) 预测历史 = 更新上下文(结果)

模型在循环内部。

该线束拥有该回路。

那个区别很重要。

#### 一个具体的例子

假设模型发出工具调用：

> 写入文件( path="src/配置.py", Please provide the actual content to be translated within the quotes, as the current placeholder "..." does not contain meaningful text for translation. )

在该写入操作成为真正的副作用之前，测试框架仍需检查路径安全性、基准新鲜度、审批以及状态更新。

该模型提出了一个建议。现在 harness 必须回应：

- src/config.py 是不是在工作区内？
- 这个路径能否通过符号链接逃逸？
- 这是新文件还是覆盖？
- 模型最近是否读取了现有文件？
- 已知的文件基准线是否过时？
- 这段文字需要人工审批吗？
- 结果是否应该包含差异摘要？
- 验证应该在之后运行吗？
- 下一个提示应该输入多少输出？
- 哪个状态需要更新，以便下一轮不陈旧？

这些决策不应该由模型即兴发挥来决定。

提示可以描述预期行为。测试框架强制执行边界。

#### 产品课程

一旦你开始看到这个 harness，许多编码代理的故障就变得更容易诊断了。

- 如果代理重复自身，请检查循环和重试策略。
- 如果它编辑陈旧代码，检查文件状态基准线。
- 如果随着时间推移情况变得更糟，请检查上下文投影。
- 如果它运行了一些意外的内容，检查权限策略。
- 如果它无法从工具错误中恢复，请检查工具结果对象。
- 如果它无法解释发生了什么，请检查追踪、审计并修复表面。

模型很重要。模型质量是一个层面。

真实的代理体验来自于围绕模型的全栈：

- 模型
- 仓库上下文
- 提示词结构
- 工具契约
- 验证
- 权限
- 文字记录
- 文件状态
- 诊断

任何必须可靠的东西都应放在 harness 中。

这就是为什么“the harness is the product”不仅仅是一句口号。

这是一个工程规则：

> 任何必须可靠的东西都应放在 harness 中。

#### 02\. 过时读取陷阱

![Image](https://pbs.twimg.com/media/HMFmebLWcAAa3sk?format=jpg&name=large)

模型记住转录本。harness 必须记住真理。

> 什么是陈旧读陷阱？

最危险的编码代理漏洞通常看起来很普通。

代理读取一个文件。用户修改了该文件。模型从记录中记住了文件内容，但磁盘的内容已经更新了。

然后代理编辑旧版本。

没有重大错误。没有明显的幻觉。只是一个模型在自信地基于陈旧的证据工作。

那就是陈旧读陷阱。

记住这一点：

> 转录文本不是文件真相。

如果编码代理无法判断模型记忆的文件内容是否仍然与磁盘一致，它最终会修补昨天的代码。

![Image](https://pbs.twimg.com/media/HMFmgIAXsAEjvtq?format=jpg&name=large)

#### 失败

想象这个序列：

> 第1轮 read\_file("src/配置.py") 转录现在包含文件内容 代理外部 formatter、用户或 git checkout 修改了 src/config.py 第2轮 模型使用旧的转录文本 补丁文件( path="src/配置.py", old="TIMEOUT = 30", new="超时 = 60" )

问题不在于 read\_file。

问题在于磁盘更换后，代理仍然信任旧的读取。

从模型的角度来看，文件内容就在对话中。但对话是历史。工作区是当前事实。

#### 朴素设计

小型代理常常将工具输出视为普通的转录文本：

> 修改超时时间 工具：这里是 src/配置.py 助手：我将修补第12行 工具：补丁已成功

纯文本转录内容无法检测到外部文件的变化。

只有当转录内容之外的部分没有变化时，这才起作用。但是转录内容和磁盘的状态不同。

> 文字稿称: 12: TIMEOUT = 30 磁盘现在显示： 12: REQUEST\_TIMEOUT = 45 13: RETRY\_TIMEOUT = 30

如果记录与磁盘不一致，处理单元应以磁盘为准。

如果 harness 仅追加文本，模型可以在一个不再存在的世界中运行。

#### Harness 需要知道的内容

测试框架需要单独记录文件真实性。它不能仅仅记住“模型读取了某些内容”。

它需要文件状态记录：

> 路径：src/配置.py 读取范围：整个文件或第1-80行 基准哈希值: abc123... mtime / size: 最后已知的磁盘指纹 内容基准：模型看到的有界文本 读取文件, 代理变更, 外部变更 状态: 新鲜的, 已更改的, 陈旧的, 部分的, 已截断的

> 记录是按时间顺序的。文件内容是有状态的。

记录稿回答：对话中发生了什么？

文件状态回答：模型现在还能信任哪些文件内容？

#### Harness 合同

一个成熟的测试框架将 read\_file 视为一个契约：

> 读取文件(path) -&gt; 记录基线 -&gt; 将有界内容附加到转录文本 记住模型看到的 编辑前(路径) 将基准与磁盘进行比较 -&gt; 拒绝过期/不完整/缺失/已更改的 需要重新读取 或者注入当前已修改的行 成功编辑后(path) 记录编辑后基准线 -&gt; 标记代理的自身写入为新

现在文件读取不仅仅是一种便利，它成为了一种安全机制。

模型仍然可以提出编辑建议。该框架决定该建议是否基于文件的最新真实内容。

![Image](https://pbs.twimg.com/media/HMFmhwFXgAAHhUx?format=jpg&name=large)

#### 部分读取是部分的

还有一种陈旧读陷阱：部分读取。

该模型读取第100到140行，然后尝试重写整个文件。

这应该会让 harness 紧张。范围读取可以回答一个问题，但不应自动授权高风险编辑。

> server.py

本地切片可以回答本地问题，而无需授权有风险的全局编辑。

一个有用的规则：

> 对现有文件的编辑应该需要全新的完整文件基线，除非编辑工具具有更严格的精确上下文约定。

这防止模型从一个本地片段猜测文件的其余部分。

#### Harness 应该跟踪的内容

当 read\_file 运行时，跟踪：

- 工作区相对路径
- 行范围和总行数
- 是否完整读取了整个文件
- 修改时间、大小和内容指纹
- 有边界的基线文本
- 状态源

在 write\_file 或 patch\_file 操作成功后，将编辑后的内容记录为新的已知基准线。

在构建下一个提示词时，延迟刷新被跟踪的文件：

- 未改变的内容保持新鲜
- 仅时间戳变更且内容相同的情况下静默刷新
- 外部磁盘编辑变为已修改行代码片段
- 被删除的文件或已更改且过大的文件会成为一个过时警告
- 新的 read\_file 清除过时或外部变更状态

#### 为什么这会改变 Agent 的行为

一旦 harness 拥有文件状态，代理行为发生变化。

如果文件没有变化，重复读取可以合并为摘要，而不是充斥上下文。

如果文件在代理外部被修改，下一次提示可以显示当前已修改的行，而不是旧的记录内容。

如果模型仅读取了一个切片，编辑可以在损坏文件前被拒绝。

代理写入之后，经过后期编辑的内容可以成为新的基准线。

会话恢复后，harness 不仅可以恢复文本，还可以恢复代理有权信任的内容。

模型能够记住文本。框架必须记住真理。

#### 03\. 工具是契约，而非功能

![Image](https://pbs.twimg.com/media/HMFmjSeWYAAsxng?format=jpg&name=large)

如果一个编码代理拥有一个世界，那么每个工具调用都是生成的文本，请求改变该世界的状态。

工具调用可能看似简单。

模型生成 JSON。测试框架解析它。一个本地函数运行。结果返回至下一个提示。

那是 tiny-agent 版本。

但在编码代理中，工具调用不只是函数调用。

工具调用来自生成的文本。它请求访问工作区、Shell、网络、对话记录或另一个代理。

那个差异改变了代理的状态和环境。

模型可以提问。框架做决定。

![Image](https://pbs.twimg.com/media/HMFmlHXXcAAFXuP?format=jpg&name=large)

#### 建议书与合同

想象模型发出：

> &lt;工具&gt;{ "name": "写入文件", "参数": { "path": "src/配置.py", "content": "..." } }&lt;/tool&gt;

表面上有效的 JSON 仍然只是对权力的请求。

它是有条理的。它仍然是一个提案。

生成合法 JSON 的模型不会自动授予写权限。

这个线束仍然需要回答：

- 这个工具有存在吗？
- 参数是否与模式匹配？
- 路径是否在工作区内？
- 这是创建、覆盖还是修补？
- 模型最近是否读取了现有文件？
- 文件状态基线是否最新？
- 这个操作需要审批吗？
- 在审批前，人应该看到什么？
- 多少结果输出可以安全地进入上下文？
- 之后需要哪些记录和状态更新？

那个列表是工具合同。

#### 朴素设计

朴素的设计将工具视为功能映射：

> 工具 = 工具集\[模型\_json\["名称"\]\] result = tool(\*\*model\_json\["args"\]) 历史.append(结果)

一行简短的代码可以隐藏解析、策略、限制和状态更新。

这段代码很短，看起来很简洁。它还把太多职责压缩到了一行。

解析、模式验证、路径安全、权限策略、沙箱选择、执行、输出裁剪、记录和状态更新都隐藏在工具(...)内部。

这对于演示来说没问题。但对于一个能够修改真实仓库的代理来说，这还不够。

在普通软件中，函数调用是一个实现细节。

在编码代理中，工具调用是生成的文本请求权限以改变现实世界的过程。

#### 工具合同包含的内容

一个有用的工具契约不仅仅是一个名称和一个处理程序。

它应该描述：

> 名称: write\_file 参数模式：路径，内容 风险: 工作区写入 路径策略：必须保持在工作区内 要求：现有文件需要新的基线 审批：写入需要 审批摘要：路径 + 操作 + 大小 执行：原子写入或精确补丁 结果预算: 有界差异 / 字符 / 行 状态更新：记录编辑后基准线 转录记录：配对通话及结果

某些字段是用于模型的。

某些字段只属于线束。

模型需要足够的信息才能正确地发出请求。测试框架需要足够的元数据才能正确地判断它。

- 模式验证检测到缺失的字段和错误的类型
- 路径验证捕获工作区逃逸
- 策略处理风险、审批、沙箱或拒绝
- 执行运行真正的处理程序
- 边界限制防止一个命令或文件读取操作淹没下一个提示
- 记录让下一轮能够恢复并审计发生的事情

"仅仅调用函数"是错误的思维模式。函数只是生命周期中的一小部分。

#### 批准前验证

验证应该在审批之前进行。

- 如果 patch\_file 指向工作区之外，则首先拒绝。
- If old\_text is missing or ambiguous, reject first.
- If a tool call repeats the previous failed request, reject or retry first.
- If a write targets an existing file but lacks a fresh baseline, reject first.

Approval is a product surface.

The user should not be asked to approve a request that is already invalid.

When approval is needed, the summary should stay bounded:

> tool: write\_file path: src/config.py operation: update existing file content: 84 lines, 2410 chars risk: workspace\_write requires: human approval

Invalid requests should fail before a human is asked to decide.

#### Bounded Results Are Part Of Safety

Tool output becomes context.

Context changes agent behavior.

- If search returns 10,000 matches, the model is not wiser.
- If run\_shell prints a huge log, the next turn may lose the actual user request.
- If read\_file repeats the same unchanged file every turn, useful context gets pushed out.

Tool contracts need result limits:

> stdout: clipped stderr: clipped large files: offset + limit search: max matches binary files: metadata only diff: summarized

Bounding output is not just UX polish. It is part of safety.

#### 04\. The Agent's Toolkit: "/"

![Image](https://pbs.twimg.com/media/HMFmoaGXAAAtP-Y?format=jpg&name=large)

The slash is where a coding agent stops being only a prompt box.

Every coding-agent UI begins with a simple idea:

Type a request. Send it to the model. Get work back.

That is the prompt-box view of an agent.

It works for normal requests:

> fix the failing tests explain this module add a config option

But a product-grade coding agent has another class of input:

> /status /tools /reset /goal pause /audit

These inputs should not be sent to the model as ordinary requests.

They are user tools for controlling the agent runtime.

Do not send control-plane intent to the model as ordinary chat.

![Image](https://pbs.twimg.com/media/HMFmqAvWQAAlnEQ?format=jpg&name=large)

#### The Naive Prompt Box

A tiny agent often sends every text input through one path.

That is simple. It also creates bad product behavior.

- The user types /status; the model may invent a status.
- The user types /reset; the model may discuss reset without clearing session state.
- The user types /goal pause; the model may treat it as an instruction inside the task.
- The user mistypes /statsu; the model may guess instead of returning command help.

The problem happens before model quality.

The harness did not route the input correctly.

#### Slash Commands Are User Tools

Article 03 said model tools are contracts.

Slash commands are another class of tool. They belong to the user and the harness.

They can inspect, steer, reset, pause, diagnose, and configure runtime before any model call exists.

Command families are often simple:

- some commands produce local output
- some commands modify session state
- some commands expose harness metadata
- some commands prepare context for the next model turn

They all need to be routed before prompt construction.

The keyword is:

> Input Router

#### The Input Router

A useful coding-agent harness has two parser boundaries.

The first handles user input.

The second handles model output.

The input router should decide:

- ignore empty input
- handle known slash commands locally
- reject unknown slash commands with help
- answer local runtime questions locally
- send ordinary work requests to the model

Only the last path should enter agent.ask().

The prompt box is no longer the only entrance.

The harness has its own control surface.

Not every input becomes a prompt.

![Image](https://pbs.twimg.com/media/HMFmrs9WAAAwpZY?format=jpg&name=large)

#### The Special Case: /goal

/goal is interesting because it sits between user control and model work.

> goal is explicit session state

The user-facing command controls lifecycle:

> /goal &lt;objective&gt; /goal pause /goal resume /goal complete /goal clear

The model can see goal context in the prompt.

But the model should not freely create, pause, resume, or clear goals.

It may have narrow tool access such as:

> get\_goal() update\_goal(status="complete")

The goal can guide the model while the user still owns control state.

Completion should depend on evidence, not on the model feeling done.

#### Diagnostics Should Stay Local

Some commands should inspect the harness directly.

/audit and /doctor are good examples.

They should not ask the model:

> does my session look healthy?

They should inspect deterministic runtime state.

The first check should be local.

When diagnostics are local commands, the harness can report real invariants instead of asking the model to guess.

#### Why This Changes The Product

Once slash commands exist, the user has more than a prompt box.

The user can ask:

- where is the current workspace?
- which tools are available?
- what is the active goal?
- which state will enter the next turn?
- what changed after the last edit?
- is the harness internally consistent?
- should this session reset, pause, resume, or compact?

These are runtime questions. They need runtime answers.

Text after / belongs to the harness, not the model.

The prompt box is where the user asks for work.

Slash is where the user controls the worker.

That is why the agent toolkit starts with /.

#### 05\. Markdown Is A Context Interface

![Image](https://pbs.twimg.com/media/HMFmtNbWkAAnjEC?format=jpg&name=large)

Small markdown files can change the world-state of a coding agent.

A plain .md file can change agent behavior.

Add AGENTS.md, and the agent starts following repo-specific rules.

Add SKILL.md, and the agent suddenly gets better at a class of tasks.

That sounds almost magical.

It is not magic. It is harness design.

The markdown file is only the visible part.

The real mechanism is:

> discover the file classify its role decide when it loads project it into model context apply tool and workflow constraints record what happened

A .md file works when the harness knows what kind of context it is.

![Image](https://pbs.twimg.com/media/HMFmu2zXkAAJ_oZ?format=jpg&name=large)

In modern coding agents, the interesting phenomenon is simple: ordinary markdown can change agent behavior.

#### The Naive Markdown Dump

A small agent may start with a naive design:

> find every .md file paste all of them into the system prompt

That creates the illusion of context.

It also creates noise.

Not every markdown file has the same role.

README.md explains the project.

AGENTS.md gives operating instructions.

SKILL.md describes an invocable task procedure.

Design docs, meeting notes, changelogs, and scratch notes all have different lifetimes.

The harness needs to know the role before it decides where the markdown belongs.

#### Two Files, Two Jobs

AGENTS.md and SKILL.md are the clearest examples.

They both use Markdown.

They do not do the same job.

AGENTS.md is workspace instruction context.

It says: when working in this repo, behave like this.

SKILL.md is task procedure context.

It says: when this kind of task appears, use this workflow.

Same file format. Different harness role.

#### Why AGENTS.md Works

AGENTS.md works because the harness gives it a stable place in the turn.

It is discovered from the workspace.

It is scoped to the repo, directory, or subtree.

It is loaded before the model call.

It becomes part of the instruction context that shapes every action in that scope.

This is why a short file can matter so much.

It does not need to be persuasive. It needs to be reliably projected into the right context layer.

#### How AGENTS.md Works

A typical flow:

> start in cwd resolve workspace read nearest AGENTS.md files merge instruction scopes add them to stable context build the model prompt

The model does not "search for rules" every turn.

The harness prepares the rules before the model sees the request.

That is the important part.

Where AGENTS.md enters the agent turn

![Image](https://pbs.twimg.com/media/HMFnH7bWkAAXxwC?format=jpg&name=large)

AGENTS.md loads before model-turn assembly.

It becomes stable workspace instruction context, next to project rules and local operating constraints.

The transcript records what happened. AGENTS.md shapes how the next action should happen.

#### Why SKILL.md Works

SKILL.md works for a different reason.

A skill should not dump all of its body into every prompt.

That would waste context.

Instead, a mature harness uses progressive disclosure.

First, the harness exposes cheap metadata:

> name description when to use it

Only when the task needs the skill does the harness load the full body.

That is why a skill can sharply improve performance on a task.

It gives the agent a local operating manual exactly when it matters.

It can specify:

- which tools to use
- which files or APIs to inspect
- what order to follow
- what verification counts as done
- what output shape to produce

This is not "prompt magic."

It is task-specific context routing.

#### How SKILL.md Works

A typical flow:

> scan skill folders expose capability metadata match task or explicit invocation load SKILL.md body read referenced resources when needed apply workflow verify output

The important design is progressive disclosure.

Metadata stays cheap.

Procedure loads only when useful.

References load only when needed.

That keeps the base context small while still making the agent specialized at the right moment.

Where SKILL.md enters the agent turn

![Image](https://pbs.twimg.com/media/HMFnt9qWIAACpHF?format=jpg&name=large)

SKILL.md first appears as capability metadata. After task invocation, its body is loaded.

That body becomes procedural context for the current task, not permanent repo law.

#### 06\. Context Is A Projection

![Image](https://pbs.twimg.com/media/HMFnv5hWMAAD_0Z?format=jpg&name=large)

Every coding agent eventually meets the same problem: the session keeps getting longer.

The model has read files, run commands, searched logs, edited code, received validation output, and answered old questions.

The tempting solution is:

> append everything

This feels like memory.

It is actually context flooding.

At first, the model seems smarter because it sees more. Then the same mechanism starts hurting it.

Old tool output competes with current evidence.

Huge shell logs bury the next instruction.

File reads that were true yesterday still look fresh today.

A transcript records what happened. Context decides what matters now.

![Image](https://pbs.twimg.com/media/HMFnx5AXMAAYMI9?format=jpg&name=large)

#### The Naive Append Loop

The naive loop is:

> prompt = old\_prompt prompt += new\_user\_message prompt += assistant\_message prompt += every\_tool\_result repeat

This fails because the transcript and the prompt have different jobs.

The transcript should be durable.

The prompt should be selective.

The full log is the source of truth. The model-visible context is a projection from that log.

#### The Multi-Turn Loop

A healthy multi-turn loop has phases:

1\. App input 2. Context projection 3. Model call 4. Tools and evidence 5. Next-state commit

Context management happens before the model call.

The model does not receive "the session." It receives a shaped view of the session.

#### The Core Split

A mature harness separates three things:

- durable log
- model-visible context
- app state

The durable log stores what happened.

Model-visible context is the bounded prompt for one call.

App state stores structured facts that should survive transcript reduction: files, goals, tasks, permissions, attachments, validation state, and evidence.

If these are mixed together, compaction becomes dangerous.

If they are separated, compaction becomes engineering.

#### Projection Happens Before The Model Call

The harness projection pipeline:

![Image](https://pbs.twimg.com/media/HMFnz3HXoAArqAt?format=jpg&name=large)

Start from the full session log. That is the source of truth.

Then select a working slice: recent turns, current user request, relevant files, active goals, and unresolved tool results.

Then check the context budget.

Then apply reduction moves.

Then attach state blocks that must survive transcript reduction.

Finally, build the model-visible prompt.

The result is not "all memory." It is the current working view.

#### Four Projection Moves

Four useful context-management moves:

1\. Large-result preview

Store the full result outside the prompt. Put only a bounded summary, counts, paths, and retrieval handle into context.

2\. Idle-gap microcompact

If the user returns after a long idle gap, summarize the old span before continuing. Do not force the next turn to carry every stale detail.

3\. Old-span collapse

Collapse old plans, attempts, and resolved errors into a compact state summary while preserving evidence and decisions.

4\. Auto-compact near the limit

When the context window approaches the hard limit, compact before the model call fails.

#### Auto-Compact Near The Limit

A good implementation needs more than "if too long, summarize".

![Image](https://pbs.twimg.com/media/HMFn12zXMAAEI0M?format=jpg&name=large)

It needs:

- warning thresholds: tell the user roughly how much context remains
- hard blocking thresholds: stop before the prompt cannot fit
- output-token reserve: leave room for the model to answer
- recursion guards: avoid compaction triggering compaction forever
- failure circuit breakers: stop after repeated compact failures
- post-compact cleanup: remove obsolete transient state
- restored attachments or state blocks: bring back what the next turn still needs

The hard part is not summarizing. The hard part is preserving what future turns will need.

#### Memory Channels

Memory is stored state.

Context is the selected view for one model call.

They are related, but not the same thing.

Useful memory channels include:

- short-term working memory: what matters for the current task
- session memory: decisions and evidence from this session
- long-term memory: durable user or project preferences
- environment memory: refreshed facts from the real workspace

Projection is how these channels become prompt context.

#### 07\. A Subagent Opens A New Context

![Image](https://pbs.twimg.com/media/HMFn31VW0AA87ZI?format=jpg&name=large)

A subagent is a tool call that opens a new work context for the coding agent.

![Image](https://pbs.twimg.com/media/HMFn50PWEAE7ypR?format=jpg&name=large)

What happens when a subagent starts?

Short answer:

> tool call outside, runtime inside

#### First: The Tool Call

Why say that subagent launch is a tool call?

Because at the parent model interface, it is one.

The user may ask naturally:

> Use a verifier subagent to audit webhook retries.

Or the harness may expose a local command:

> /delegate verifier audit webhook retries

But when the parent agent acts, it usually emits something like:

> spawn\_agent({ task\_name, message, agent\_type, fork\_turns })

The parent tool call returns a child handle.

The parent can wait for it, send follow-up, list it, interrupt it, or read its projected result.

#### Then: Runtime

Tools are contracts. A subagent is another contract: a small interface backed by runtime state.

Once the tool call is accepted, the harness opens a child runtime.

That child runtime may have:

- its own thread or session
- its own transcript
- its own context projection
- a selected role or agent type
- selected tools and permissions
- shared resources such as cwd, repo, skills, AGENTS.md, plugins, or MCP servers
- a mailbox or handle for parent-child communication

Shared resources do not mean shared transcript.

The child has its own work context. The parent chooses how much context to project into it.

#### Session, Context, Subagent

These three words are easy to mix together.

会话是运行时容器：

> 线程, 文字记录, 工具, 权限, 资源, 状态, 工件

上下文是一个模型能够看到的内容：

> 指令, 技能, AGENTS.md, 最近对话轮次, 总结, 工具结果, 文件状态

Subagent 是父会话下的一个子运行时。

它可以继承资源，但会接收一个选定的上下文片段。

#### 外部调用工具，内部运行时

子代理这个词可能会产生误导。

这听起来像是一个更小的代理。在框架中，将其理解为受管理的子运行时会更合适。

家长看到一个工具界面。

The harness creates a child session underneath.

子项不会自动共享完整的父 prompt。

父进程可以创建一个全新子进程、一个分叉子进程或一个部分分叉。

#### 全新代理、分叉代理还是部分分叉？

合适的上下文取决于子代理模式。

新鲜的孩子：

- 需要全面的情况介绍
- 应该收到目标、相关文件、已尝试内容、确切的预期输出以及回答深度

分叉的子进程

- 继承周围上下文
- 应该收到直接的下一步指示

部分分支

- 获得足够的本地内存以工作
- 避免将完整的父历史继承为噪声

部分分叉往往是最实用的折中方案。

#### 当子代理帮助时

子代理在工作有界限且独立时很有用。

示例：

- 并行：一个子任务检查数据库迁移，另一个检查前端状态，第三个执行核实。
- 角色专业化：探索者、规划者、验证者、执行者、评审者。
- 背景工作：长时间的测试，大规模重构，缓慢的代码审计。
- 隔离：让评审者在不污染父上下文的情况下检查证据。

更多的代理并不保证更好的工作。

更多的代理会创建更多的运行时状态。

该系统必须了解谁在工作、他们知道什么、他们修改了什么、何时完成，以及他们的结果如何成为证据。

#### 子代理工作流程

一个有用的子代理工作流程如下：

![Image](https://pbs.twimg.com/media/HMFn7zkXoAAjvDB?format=jpg&name=large)

> 父级接收任务 决定委派是否有帮助 选择子角色 选择上下文切片 选择工具和权限 生成子运行时 子进程在其自身的日志中工作 child 返回紧凑证据 父级整合结果 管理记录谱系

组织多个子代理很困难。

角色、上下文和工具边界越清晰，结果越好。

子代理拓展了编码代理的世界。

这个框架决定了那个新世界是变得更清晰还是更混乱。

## 解读（1）

### 2026-07-01 10:11:12

#### 《编码代理框架》深度总结与解读

##### 一句话总括

> 编码代理的核心不只是模型，而是包裹模型的 **harness / 线束 / 运行框架**：它决定模型能看到什么、能做什么、怎么验证、如何记忆、如何安全地改变真实代码仓库。

---

##### 1. 深度总结

###### 1.1 核心观点：Harness 才是产品

大语言模型负责“生成建议”，但真正让建议变成现实动作的是编码代理框架。

模型可以说：

> 我要改这个文件、运行这个命令、调用这个工具。

但 harness 必须判断：

- 能不能改？
- 是否安全？
- 文件是否最新？
- 是否需要用户批准？
- 输出要不要截断？
- 状态如何记录？
- 下一轮上下文如何更新？

所以文章反复强调：

> 任何必须可靠的东西，都应该放在 harness 中，而不是寄希望于模型自觉。

---

##### 2. 编码代理框架的六大职责

###### 2.1 实时仓库上下文

编码代理不能只靠聊天记录工作，它必须知道真实代码仓库当前状态。

包括：

- 当前工作目录
- 文件内容
- 项目文档
- Git 状态
- 近期变更
- 测试结果

否则模型可能在“想象中的代码库”里工作。

---

###### 2.2 提示词结构

提示词不是简单拼接。

好的 harness 会稳定组织：

- 系统规则
- 仓库规则
- 当前任务
- 工具说明
- 文件状态
- 历史摘要

很多时候，代理表现变好，不是因为模型换了，而是因为上下文组织更好了。

---

###### 2.3 工具是契约，不是函数

工具调用不是普通函数调用。

模型生成：

```json
{
  "name": "write_file",
  "path": "src/config.py"
}
```

这只是一个“请求”，不是授权。

harness 还要检查：

- 工具是否存在
- 参数是否合法
- 路径是否越界
- 是否覆盖文件
- 是否需要审批
- 文件是否过期
- 输出是否过大
- 状态如何更新

工具真正的本质是：

> 模型提案与现实副作用之间的安全契约。

---

###### 2.4 上下文是投影，不是堆积

不能把所有历史、所有工具输出、所有文件内容都塞进 prompt。

因为这样会导致：

- 旧信息干扰新信息
- 大日志淹没当前任务
- 过期文件内容仍被模型信任
- 上下文窗口被浪费

成熟的做法是把系统拆成三层：

| 层级 | 作用 |
|---|---|
| 持久日志 | 记录发生过什么 |
| 应用状态 | 记录结构化事实 |
| 模型上下文 | 当前这一轮需要看到什么 |

模型看到的不是全部历史，而是经过筛选、压缩、更新后的“当前工作视图”。

---

###### 2.5 转录记录与真实状态要分离

聊天记录只说明“过去发生了什么”，不代表“现在仍然为真”。

典型陷阱是：

1. 模型读取了 `config.py`
2. 用户或格式化工具修改了该文件
3. 模型仍根据旧聊天记录修改文件
4. 最终覆盖了新代码

这就是“陈旧读取陷阱”。

因此 harness 必须记录文件基线：

- 路径
- 读取范围
- 哈希
- 修改时间
- 是否完整读取
- 是否过期
- 是否被外部修改

核心原则：

> 模型记住的是文本，harness 必须记住真相。

---

###### 2.6 子代理是受控子运行时

子代理不是“多叫几个模型来帮忙”这么简单。

它本质上是：

> 父代理通过工具调用，创建一个有边界的子运行时。

子代理可以有自己的：

- 上下文
- 工具权限
- 任务目标
- 文字记录
- 状态
- 输出结果

它适合处理：

- 并行检查
- 独立审计
- 长任务
- 角色分工
- 隔离验证

但如果边界不清，子代理只会制造更多混乱。

---

##### 3. 关键概念通俗解读

##### 3.1 Harness 是什么？

可以把编码代理想象成一个“实习程序员”。

模型是大脑，harness 是工作制度。

模型负责想：

> 我应该怎么改代码？

harness 负责管：

> 你能不能改？  
> 改哪里？  
> 改之前读过吗？  
> 文件有没有变？  
> 要不要审批？  
> 改完怎么验证？  
> 怎么记录？

没有 harness，模型就像一个聪明但没有权限边界的实习生。

---

##### 3.2 为什么不能只靠更强模型？

因为很多问题不是“智力问题”，而是“工程控制问题”。

例如：

- 文件被别人改了，模型不知道
- 命令输出太长，模型被噪声干扰
- 用户输入 `/reset`，模型只是回答“好的”，但系统状态没清
- 工具调用路径越界，模型自己不会天然阻止
- 子代理继承太多历史，反而迷失

这些问题靠模型变聪明不能完全解决。

需要系统层设计。

---

##### 3.3 Slash 命令为什么重要？

用户输入分两类：

###### 普通任务

```text
帮我修复测试失败
```

应该交给模型。

###### 控制命令

```text
/status
/reset
/audit
/tools
/goal pause
```

不应该交给模型，而应该由 harness 本地处理。

因为这些是“控制运行时”的命令，不是“让模型聊天”的请求。

一句话：

> prompt box 是让用户安排工作；slash command 是让用户控制工人。

---

##### 3.4 Markdown 为什么能改变代理行为？

比如：

- `AGENTS.md`
- `SKILL.md`

它们不是因为“Markdown 有魔法”，而是 harness 识别了它们的角色。

###### AGENTS.md

是仓库级工作规则。

例如：

> 本项目必须用 pnpm  
> 修改代码后必须跑测试  
> 不要直接改 generated 文件

它会稳定进入上下文，影响每一轮行为。

###### SKILL.md

是某类任务的操作手册。

例如：

> 做安全审计时，先看认证逻辑，再查权限边界，再写报告。

它不应该每次都加载，而是在相关任务触发时加载。

核心是：

> Markdown 有用，不是因为格式，而是因为 harness 知道何时、如何、以什么身份加载它。

---

##### 4. 文章真正想纠正的误区

###### 误区一：模型越强，代理越好

不完全对。

模型是能力上限之一，但产品体验更多由 harness 决定。

---

###### 误区二：工具就是函数调用

不对。

工具调用是模型请求改变现实世界，必须有验证、权限、审计和边界。

---

###### 误区三：上下文越多越好

不对。

上下文应该是“当前有用信息”的投影，而不是历史垃圾桶。

---

###### 误区四：聊天记录就是真相

不对。

聊天记录是过去，文件系统才是当前事实。

---

###### 误区五：子代理越多越强

不对。

子代理增加的是运行时复杂度。没有清晰边界，只会制造更多混乱。

---

##### 5. 辩证思考

##### 5.1 模型重要，但不是全部

强模型确实重要。

更好的模型可以带来：

- 更强代码理解
- 更好规划能力
- 更少低级错误
- 更自然交互

但只靠模型无法保证：

- 文件安全
- 权限安全
- 状态一致
- 工具可靠
- 上下文干净
- 结果可审计

所以未来编码代理竞争，不只是模型之争，也是工程系统之争。

---

##### 5.2 Harness 越强，模型越可控；但也越复杂

harness 能提升可靠性，但也会带来成本：

- 设计复杂
- 状态管理困难
- 权限规则繁琐
- 用户体验可能变重
- 错误来源从模型扩展到系统本身

因此不是 harness 越厚越好，而是要把可靠性要求最高的部分放进去。

比如：

- 文件写入必须严格
- Shell 执行必须严格
- 上下文压缩要谨慎
- 普通解释类对话可以轻量

关键是分级治理。

---

##### 5.3 自动化与人类审批需要平衡

如果所有操作都要审批，代理效率很低。

如果所有操作都自动执行，风险很高。

合理方式是按风险分层：

| 操作 | 策略 |
|---|---|
| 读文件 | 通常自动 |
| 搜索代码 | 自动 |
| 修改文件 | 可能审批 |
| 删除文件 | 强审批 |
| 运行测试 | 自动或半自动 |
| 执行危险 shell | 严格审批 |
| 网络访问 | 视场景限制 |

优秀代理不是完全自治，而是知道什么时候该停下来问人。

---

##### 5.4 上下文压缩既是能力，也是风险

压缩上下文可以节省窗口，让长期任务继续运行。

但压缩也可能丢掉关键证据。

所以压缩不能只是“总结一下”，而要保留：

- 当前目标
- 已做决策
- 关键证据
- 文件基线
- 未完成任务
- 错误原因
- 用户偏好
- 验证结果

真正困难的不是压缩，而是知道什么不能丢。

---

##### 5.5 子代理是组织问题，不只是技术问题

子代理类似团队协作。

如果任务边界清晰，它能提升效率。

如果任务边界混乱，它会导致：

- 重复劳动
- 相互覆盖
- 信息割裂
- 父代理难以整合
- 错误责任不清

所以子代理设计要像管理团队：

- 谁负责什么？
- 能看什么？
- 能改什么？
- 怎么汇报？
- 汇报如何成为证据？
- 谁做最终决策？

---

##### 6. 最精炼结论

> 编码代理不是“模型 + 工具”这么简单。  
> 真正的产品是围绕模型建立的一整套运行框架。

这个框架负责：

- 路由用户输入
- 构造上下文
- 管理文件真相
- 验证工具调用
- 控制权限风险
- 裁剪工具输出
- 维护长期状态
- 支持 slash 命令
- 加载 Markdown 规则
- 管理子代理

最终原则只有一句：

> 模型负责生成可能性，harness 负责决定哪些可能性能安全地变成现实。

## 结构化（1）

### 2026-07-22 09:37:08

#### 《编码代理框架》精炼总结

> 文章的核心观点是：**模型决定代理能提出什么，而运行框架（Harness）决定什么能够真正发生。** 一个可靠的编码代理，关键不只是选用更强的模型，而是用框架管理上下文、工具、权限、文件状态、记录与子代理。

##### 01. Harness 才是产品

###### 从“模型能力”转向“框架能力”

基础大模型只负责生成文本；编码代理则需要被放入一个真实运行环境中，使其能够：

- 查看代码仓库和项目文档；
- 调用工具、编辑文件、执行测试；
- 维护多轮对话和任务状态；
- 控制权限、验证操作并记录结果。

因此，评估编码代理时，首先应问的不是“用了什么模型”，而是：**Harness 掌握并管理了哪些能力？**

###### 朴素循环为什么不够

简单代理通常采用以下循环：

```text
用户请求
→ 拼接提示词
→ 模型生成工具调用
→ 执行工具
→ 将结果追加到提示词
→ 重复
```

这种方式很快会遇到问题：

- 模型编辑了从未读取过的文件；
- Shell 命令访问工作区之外的路径；
- 工具一次返回 **50,000 行**输出，淹没上下文；
- 文件已在磁盘上发生变化，模型却仍依赖旧内容；
- 工具结果与原始调用无法正确配对。

这些问题无法仅靠“优化提示词”解决，必须由 Harness 强制管理。

###### Harness 的六项核心职责

1. **提供实时仓库上下文**  
   向模型安全地展示工作区、当前文件、项目说明和真实仓库状态。

2. **设计提示词结构**  
   稳定的系统前缀、清晰的工具协议、当前请求和受控历史，有时比更换模型更能改善表现。

3. **管理结构化工具**  
   工具需要负责参数解析、路径验证、权限检查、实际执行、输出裁剪和操作记录。

4. **精简上下文**  
   好的上下文不是把所有内容不断追加进去，而是从完整记录中选择当前真正有用的部分。

5. **分离记录与工作状态**  
   - 对话记录回答：“发生过什么？”
   - 工作状态回答：“现在什么最重要、什么仍然可信？”

6. **控制授权与委派**  
   子代理应是工具、权限和状态均有边界的工作者，而不是无约束的并行模型。

###### 模型提出建议，Harness 决定是否执行

例如模型请求写入 `src/config.py`，框架在真正修改文件前还应判断：

- 路径是否位于工作区内；
- 是否可能通过符号链接逃逸；
- 是创建新文件还是覆盖旧文件；
- 模型是否读过该文件；
- 文件基准是否已经过时；
- 是否需要人工批准；
- 是否应展示差异摘要并执行验证；
- 有多少结果应进入下一轮上下文；
- 哪些文件状态需要更新。

**提示词只能描述规则，Harness 才能真正执行规则。**

###### 故障诊断思路

- 代理反复重复操作：检查循环与重试策略；
- 编辑旧代码：检查文件状态基准；
- 对话越长表现越差：检查上下文投影；
- 执行意外命令：检查权限策略；
- 无法从工具错误中恢复：检查工具结果结构；
- 无法解释发生了什么：检查追踪、审计和诊断能力。

> 工程原则：**任何必须可靠的能力，都应该放进 Harness，而不是依赖模型临场判断。**

---

##### 02. “过时读取”陷阱

###### 对话记录不等于文件真相

典型场景如下：

1. 第 1 轮，代理读取 `src/config.py`；
2. 用户、格式化工具或 `git checkout` 在代理外部修改了文件；
3. 第 2 轮，模型仍根据对话中的旧内容生成补丁；
4. 代理自信地修改了一个已经不存在的旧版本。

例如，模型记得：

```text
TIMEOUT = 30
```

但磁盘上实际已变为：

```text
REQUEST_TIMEOUT = 45
RETRY_TIMEOUT = 30
```

此时必须以磁盘为准，而不能相信历史记录。

###### Harness 应单独维护文件状态

除对话文本外，还需要记录：

- 工作区相对路径；
- 读取范围及文件总行数；
- 是否完整读取；
- 内容哈希；
- 修改时间、文件大小；
- 模型实际看到的有界文本；
- 状态来源及新鲜度：
  - 新鲜；
  - 已修改；
  - 陈旧；
  - 部分读取；
  - 已截断。

读取文件时建立基准；编辑前重新比对磁盘；编辑成功后，再把新内容登记为新的可信基准。

###### 部分读取不能自动授权全文件编辑

如果模型只读取了第 **100～140 行**，却试图重写整个文件，Harness 应拒绝或要求重新完整读取。

可采用的规则是：

> 编辑现有文件前，原则上必须拥有最新、完整的文件基准；除非补丁工具使用了更严格的精确上下文匹配机制。

这样可避免模型仅根据局部片段猜测其余内容。

###### 文件状态管理带来的改进

- 未变化的文件无需反复塞入上下文，可用摘要代替；
- 外部修改发生后，可向模型展示当前变化行，而不是旧全文；
- 部分读取不足以支持高风险写入时，可提前阻止；
- 代理自己写入后，可立即更新基准；
- 恢复会话时，不仅恢复对话，还能恢复“哪些内容仍然可信”。

> **模型可以记住文本，但 Harness 必须记住真实状态。**

---

##### 03. 工具是契约，不只是函数

###### 工具调用只是“权限申请”

模型生成合法 JSON，并不意味着它天然有权执行操作。例如：

```json
{
  "name": "write_file",
  "args": {
    "path": "src/config.py",
    "content": "..."
  }
}
```

这只是模型提出的结构化建议。Harness 还需要判断：

- 工具是否存在；
- 参数是否符合模式；
- 路径是否安全；
- 操作属于创建、覆盖还是补丁；
- 文件基准是否最新；
- 是否需要人工审批；
- 审批时应展示哪些信息；
- 输出最多允许进入多少上下文；
- 执行后应更新哪些状态。

###### 完整工具契约应包含

以 `write_file` 为例：

| 契约内容 | 示例 |
|---|---|
| 名称与参数 | `path`、`content` |
| 风险类型 | 工作区写入 |
| 路径策略 | 必须位于工作区内 |
| 前置条件 | 修改现有文件需要最新基准 |
| 审批要求 | 写入前需要人工批准 |
| 审批摘要 | 路径、操作类型、大小 |
| 执行方式 | 原子写入或精确补丁 |
| 结果预算 | 有界差异、字符数、行数 |
| 状态更新 | 记录编辑后的文件基准 |
| 审计记录 | 工具调用与结果必须配对 |

###### 工具的完整生命周期

```text
解析
→ 模式验证
→ 路径与状态验证
→ 权限和审批策略
→ 执行
→ 输出裁剪
→ 记录
→ 更新状态
```

本地函数本身只是其中一小部分。

###### 先验证，再让用户审批

无效请求应在审批前直接拒绝，例如：

- 写入路径位于工作区之外；
- 补丁中的旧文本不存在或不唯一；
- 重复提交上一次已经失败的请求；
- 修改现有文件却没有最新基准。

用户不应被要求批准一个本来就无法合法执行的操作。

###### 限制工具输出也是安全机制

工具输出会进入下一轮上下文，因此必须设置上限：

- `stdout`、`stderr` 截断；
- 大文件使用 `offset + limit`；
- 搜索限制最大匹配数；
- 二进制文件只返回元数据；
- 大型差异只返回摘要。

例如，搜索返回 **10,000 条匹配**或 Shell 打印巨量日志，不会让模型更聪明，反而可能挤掉用户当前请求。  
因此，**结果限流不仅是体验优化，也是安全与稳定性设计。**

---

##### 04. “/”是代理的控制工具

###### 控制命令不应作为普通聊天发送给模型

除自然语言任务外，成熟代理还需要支持：

```text
/status
/tools
/reset
/goal pause
/audit
/doctor
```

这些命令用于控制运行时，应由 Harness 本地处理，而不是让模型解释或猜测。

否则可能出现：

- `/status`：模型编造一个状态；
- `/reset`：模型讨论“如何重置”，却没有清除真实会话；
- `/goal pause`：模型只把它当作任务内容；
- 拼错 `/statsu`：模型擅自猜测，而不是返回帮助信息。

###### 输入路由器的职责

Harness 应在构建提示词前先判断：

1. 忽略空输入；
2. 本地执行已知斜杠命令；
3. 对未知命令返回帮助；
4. 本地回答运行时问题；
5. 只有普通工作请求才发送给模型。

因此，代理不再只有“提示框”一个入口，还拥有自己的运行时控制面。

###### `/goal` 的特殊性

目标属于明确的会话状态，用户应控制其生命周期：

```text
/goal <目标>
/goal pause
/goal resume
/goal complete
/goal clear
```

模型可以读取目标，也可以获得受限工具，例如：

```text
get_goal()
update_goal(status="complete")
```

但模型不应自由创建、暂停或清空目标；任务完成也应以验证证据为依据，而不是模型“感觉已经完成”。

###### 诊断命令应保持本地化

`/audit`、`/doctor` 应直接检查 Harness 的确定性状态，例如：

- 当前工作区在哪里；
- 可用工具有哪些；
- 活跃目标是什么；
- 下一轮会加载哪些状态；
- 上次编辑修改了什么；
- 当前会话是否内部一致。

> 提示框用于让代理工作；斜杠命令用于控制这个工作者。

---

##### 05. Markdown 是上下文接口

###### Markdown 生效的关键不在文件格式

`AGENTS.md`、`SKILL.md` 能改变代理行为，不是因为 Markdown 有“魔法”，而是因为 Harness 会：

```text
发现文件
→ 判断文件角色
→ 决定加载时机
→ 投射进模型上下文
→ 应用工具与流程约束
→ 记录执行结果
```

不能简单地找到所有 `.md` 文件并全部塞进系统提示词，因为 `README`、设计文档、会议记录、规则文件和技能说明具有不同用途与生命周期。

###### `AGENTS.md`：工作区规则

它描述“在这个仓库或目录中应如何工作”，通常具有以下特点：

- 从工作区中发现；
- 按仓库、目录或子树确定作用范围；
- 在模型调用前加载；
- 作为稳定的工作区指令进入上下文；
- 持续影响该范围内的操作。

典型流程：

```text
确定工作区
→ 查找最近的 AGENTS.md
→ 合并不同目录范围的规则
→ 放入稳定上下文
→ 构建模型提示词
```

模型不需要每轮自行寻找规则，Harness 会提前准备好。

###### `SKILL.md`：任务流程

它描述“遇到某类任务时，应采用什么流程”，可以规定：

- 使用哪些工具；
- 检查哪些文件或 API；
- 操作顺序；
- 完成标准；
- 输出格式。

成熟框架会采用**渐进式披露**：

1. 平时只暴露名称、描述和适用条件；
2. 任务匹配或用户明确调用时，再加载完整正文；
3. 引用资源仅在需要时继续读取。

这样既能保持基础上下文轻量，又能在特定任务中提供专业化操作手册。

###### 两类 Markdown 的区别

| 文件 | 作用 | 加载方式 |
|---|---|---|
| `AGENTS.md` | 仓库或目录的长期操作规则 | 模型调用前稳定加载 |
| `SKILL.md` | 当前任务的专项流程 | 匹配任务后按需加载 |

---

##### 06. 上下文是对完整记录的“投影”

###### 不要把所有历史都追加进提示词

会话越长，代理会读取越来越多文件、日志、补丁和测试结果。若把所有内容不断追加：

- 旧工具输出会与当前证据竞争；
- 大型日志会淹没新请求；
- 已过时的文件内容仍显得可信；
- 上下文最终接近模型限制。

文章强调：

> 对话记录负责保存“发生过什么”，上下文负责选择“现在什么最重要”。

###### 必须分离三类数据

1. **持久日志**  
   保存完整事件，是审计与恢复的事实来源。

2. **模型可见上下文**  
   每次模型调用时生成的、受预算限制的工作视图。

3. **应用状态**  
   保存不应因压缩而丢失的结构化信息，如文件状态、目标、任务、权限、附件、验证结果和证据。

如果三者混在一起，压缩历史会非常危险；分开后，上下文管理才成为可控工程。

###### 上下文投影流程

```text
完整会话日志
→ 选择当前工作片段
→ 检查上下文预算
→ 压缩或裁剪
→ 重新附加关键状态块
→ 构建模型可见提示词
```

模型看到的不是“整个会话”，而是当前任务所需的有界视图。

###### 四种常用投影策略

1. **大型结果预览**  
   完整结果存放在提示词之外，只传入摘要、数量、路径和检索句柄。

2. **长时间空闲后的微压缩**  
   用户隔很久再回来时，先总结旧会话，再继续任务。

3. **折叠旧阶段**  
   把旧计划、失败尝试和已解决错误压缩为状态摘要，同时保留关键证据与决策。

4. **接近上限时自动压缩**  
   在模型调用失败前主动压缩，而不是等超过上下文窗口后再处理。

###### 自动压缩需要的保护机制

- 提前警告剩余上下文空间；
- 设置硬阻断阈值；
- 为模型回答预留输出令牌；
- 防止压缩递归触发自身；
- 连续失败后启动熔断；
- 清理压缩后已失效的临时状态；
- 恢复下一轮仍需要的附件和状态块。

真正困难的不是“生成一段摘要”，而是**确保未来仍会用到的事实、证据和状态不丢失**。

###### 记忆与上下文并不相同

- 记忆：已经存储的状态；
- 上下文：某一次模型调用所选择的视图。

记忆可分为：

- 当前任务的短期工作记忆；
- 本次会话的决策与证据；
- 长期用户或项目偏好；
- 从真实工作区刷新的环境记忆。

Harness 通过投影把这些记忆转换为本轮上下文。

---

##### 07. 子代理会打开一个新的工作上下文

###### 外部是工具调用，内部是独立运行时

父代理通常通过类似调用启动子代理：

```text
spawn_agent({
  task_name,
  message,
  agent_type,
  fork_turns
})
```

对父代理而言，这是一次工具调用；调用被接受后，Harness 会创建一个子运行时，其中可能包括：

- 独立会话与线程；
- 独立对话记录；
- 独立上下文投影；
- 特定角色；
- 受限工具与权限；
- 与父代理通信的句柄或邮箱。

子代理可以共享当前目录、仓库、技能、`AGENTS.md`、插件或 MCP 服务，但**共享资源不等于共享完整对话记录**。

###### 三种上下文继承方式

1. **全新子代理**  
   需要完整说明目标、相关文件、已有尝试、预期输出和回答深度。

2. **分叉子代理**  
   继承父代理附近的上下文，适合直接执行下一步。

3. **部分分叉子代理**  
   只继承完成任务所需的局部记忆，避免完整父历史带来的噪声。  
   文章认为这通常是最实用的折中方案。

###### 子代理适用的任务

- **并行调查**：分别检查数据库迁移、前端状态和测试结果；
- **角色专业化**：探索者、规划者、执行者、验证者、评审者；
- **后台工作**：长时间测试、大规模重构、慢速代码审计；
- **上下文隔离**：让评审者独立检查证据，不污染父代理上下文。

###### 完整委派流程

```text
父代理接收任务
→ 判断是否值得委派
→ 选择子代理角色
→ 选择上下文片段
→ 限定工具与权限
→ 创建子运行时
→ 子代理在独立日志中工作
→ 返回精炼证据
→ 父代理整合结果
→ Harness 记录任务与证据谱系
```

子代理越多，不一定效果越好，反而会增加运行时状态。系统必须明确知道：

- 谁正在工作；
- 每个子代理掌握了什么；
- 修改了哪些内容；
- 何时结束；
- 返回结果如何成为可靠证据。

---

##### 总结

编码代理的真正能力来自模型外围的完整工程系统：**仓库上下文、提示词结构、工具契约、文件真实性、权限审批、日志、状态、上下文投影、诊断和子代理管理。**

文章最终强调的规则是：

> **模型负责提出行动，Harness 负责验证、授权、执行并维护真实状态；凡是必须可靠的能力，都应由 Harness 强制保证。**

#### 编码代理框架：真正决定体验的，不只是模型

这份材料的核心观点是：模型决定编码代理“能提出什么”，但围绕模型的运行框架，也就是线束，决定这些提议最终会不会安全、准确地变成现实。接下来，我们会了解编码代理框架的主要职责，以及文件状态、工具权限、上下文管理和子代理为什么如此重要。

##### 一、线束才是编码代理真正的产品

首先，编码代理不能只被理解成“模型加提示词”。

基础的大语言模型主要负责预测文本。推理模型可以进一步遵循结构、调用工具，并按照协议工作。但编码代理还要进入一个真实的运行环境，在这个环境里检查代码仓库、读取和编辑文件、运行命令、记录过程，并在多轮对话中保持状态。

这个围绕模型、工具和工作区运行的整体框架，就是这里所说的“线束”，英文叫 harness。它像一套管理系统，负责把模型的建议连接到真实世界，同时控制风险。

一个最简单的编码代理，通常是这样的循环：

用户提出请求，系统把请求放进大提示词，模型给出回答；然后系统运行模型要求的工具，把工具结果再贴回提示词，继续下一轮。

这个循环看起来很简单，但很多关键问题都被藏起来了。比如，模型编辑了一个从未读取过的文件，会发生什么？Shell，也就是命令行工具，访问了工作区之外的文件，怎么办？一个工具一次返回五万行输出，下一轮提示词还能不能正常工作？磁盘上的文件被外部修改后，代理是否还在使用旧内容？

这些问题靠更长的提示词解决不了。缺少的不是提示词，而是一个真正负责管理工具、状态和权限的框架。

更具体地说，线束至少要负责六件事。

第一，是提供实时的仓库上下文。模型需要看到工作区、当前文件、项目文档，以及真实代码仓库状态的安全视图，而不是从空白提示开始。

第二，是设计提示词结构。稳定的前缀、清晰的工具说明、当前用户请求和经过控制的历史记录，有时比单纯更换一个模型，更能改变代理的实际表现。

第三，是把工具做成结构化契约。工具不只是几个辅助函数，而是连接模型提议和真实副作用的边界。它要解析参数、检查路径和权限、执行操作、限制输出，并记录结果。

第四，是进行上下文简化。框架不能把所有内容一股脑塞给模型。好的上下文应该是经过筛选的投影，也就是根据当前任务挑出真正有用的内容，而不是不断膨胀的历史堆积。

第五，是区分转录记录和工作记忆。转录记录回答“过去发生了什么”，工作状态回答“现在什么最重要”。这两个对象不能混为一谈。

第六，是管理授权和委托。子代理不是凭空出现的并行能力，而是拥有明确工具、权限和状态范围的受控工作者。

编码代理本质上是一个“观察—行动”循环。模型负责提出下一步行动，但线束拥有整个循环。比如模型提出“写入 src/config.py”，线束就必须先检查：路径是否位于工作区内，是否可能通过符号链接逃逸；这是新建文件还是覆盖旧文件；模型最近是否读取过这个文件；文件的已知基线是否已经过时；是否需要人工审批；结果应该返回多少差异；下一轮提示词要更新哪些状态。

这些决策不应该由模型临时发挥，而应该由框架强制执行。

所以，很多代理故障都可以从线束中找到原因。代理反复重复，可能是循环和重试策略有问题；代理编辑了陈旧代码，应该检查文件状态基线；对话越进行越混乱，应该检查上下文投影；代理运行了意外命令，应该检查权限策略；代理无法从工具错误中恢复，应该检查工具结果和记录机制。

最终的代理体验，不只是模型质量，而是模型、仓库上下文、提示词结构、工具契约、验证、权限、记录、文件状态和诊断机制共同组成的全栈系统。

这也是“线束就是产品”这句话的真正含义：凡是必须可靠的事情，都应该放进线束里，而不能只寄希望于模型自己记住。

##### 二、最危险的问题之一：过时读取陷阱

接下来，重点看文件状态。

核心结论是：模型记住的是转录文本，线束必须记住文件的真实状态。转录记录不能自动代表磁盘上的最新内容。

一个典型场景是：代理先读取了一个文件。之后，用户、格式化工具或者 Git 操作修改了这个文件。模型仍然记得对话里那份旧内容，于是基于旧版本继续打补丁。

这时不一定会出现明显报错，也不一定像幻觉。模型只是非常自信地根据过时证据工作。这就是“过时读取陷阱”。

例如，第一轮中，代理读取了 `src/config.py`，记录里显示：

`TIMEOUT = 30`。

但在下一轮之前，外部操作把文件改成了：

`REQUEST_TIMEOUT = 45`，以及 `RETRY_TIMEOUT = 30`。

如果模型仍然按照旧记录，把 `TIMEOUT = 30` 改成其他内容，问题并不在于最初的读取操作，而在于磁盘已经变化之后，代理仍然相信旧记录。

因此，线束不能只保存“模型曾经读过什么”，还必须维护文件状态记录。这个记录至少要知道文件路径、读取范围、内容基线、内容指纹，也就是可以用来判断内容是否变化的哈希值或其他磁盘特征，还要知道文件当前是新鲜、已修改、过时、只读了一部分，还是因为输出限制而被截断。

一个成熟的读取流程应该是：代理读取文件时，线束记录当时的基线，并把有界的内容放进转录。之后，代理准备编辑时，线束把当时的基线和磁盘当前内容进行比较。如果文件已经过时、缺失、内容不完整，或者已经被外部修改，就拒绝直接编辑，要求重新读取，或者把当前变化注入下一轮上下文。

编辑成功后，线束还要把编辑后的文件记录成新的已知基线。

这里还有一个容易忽视的问题，就是部分读取。比如模型只读取了 `server.py` 的第100到140行，却试图重写整个文件。局部读取只能回答局部问题，不能自动授权高风险的全局修改。一个稳妥规则是：修改现有文件，通常需要一份新鲜的完整文件基线，除非编辑工具本身有严格、精确的上下文匹配机制。

文件状态管理会直接改变代理行为。

如果文件没有变化，重复读取可以被压缩成摘要，避免上下文越来越拥挤。如果文件被外部修改，下一轮可以显示当前变化的行，而不是继续展示旧记录。如果模型只读了局部内容，框架可以在修改前拦截它，避免凭猜测破坏整个文件。会话恢复时，框架也能恢复的不只是文字，还包括哪些文件内容仍然值得信任。

要记住：模型能够记住文本，但框架必须记住真相。

##### 三、工具不是普通函数，而是改变现实的契约

更重要的是，编码代理中的工具调用，不应该被看成普通函数调用。

模型输出一段结构化文本，通常是 JSON。框架解析它，再调用本地函数，把结果返回给模型。这个流程在小型演示里可能够用，但在真实代码仓库中，工具调用实际上是在请求访问工作区、Shell、网络、对话记录，甚至另一个代理。

所以，工具调用只是模型对现实世界提出的一个提案，不是已经获得的权限。

比如，模型发出一个写入文件的请求，目标是 `src/config.py`，并带上要写入的内容。即使这段 JSON 格式完全正确，线束仍然要检查很多事情：

这个工具是否真的存在？参数是否符合定义？路径是否位于工作区内？操作是创建文件、覆盖文件，还是精确修补？模型是否最近读取过现有文件？文件基线是否最新？这次写入是否需要人工审批？审批时用户应该看到多大的风险摘要？写入结果应该返回多少内容？操作完成后，哪些文件状态和记录需要更新？

这些内容共同组成了工具契约。

一个完整的工具契约，除了工具名称和参数，还应说明它能产生什么风险、路径必须满足什么规则、操作是否需要审批、审批摘要怎么展示、执行是否采用原子写入或精确补丁、输出最多返回多少行，以及完成后如何更新文件基线和转录记录。

朴素的实现可能只有几行代码：根据模型给出的工具名称找到函数，再把参数传进去，最后把结果加入历史记录。

但这几行代码很容易把解析、参数验证、路径安全、权限策略、沙箱选择、执行、输出裁剪和状态更新全部藏在一个函数调用里。对于演示来说，它很简洁；对于能修改真实仓库的代理来说，它远远不够。

一个合理的工具生命周期，应该依次包括这些环节。

首先解析模型输出，捕获格式错误。然后进行模式验证，检查参数是否缺失、类型是否错误。接着验证路径，防止工具访问工作区之外的地方。之后执行权限策略，判断风险、审批要求和沙箱范围。通过这些检查后，才真正执行工具。执行完成，还要限制结果大小、记录发生了什么，并更新下一轮所需的状态。

尤其要注意，验证应该发生在审批之前。

如果补丁路径已经指向工作区外，就应该直接拒绝，而不是先让用户审批。缺少旧文本、旧文本不唯一、重复提交上一次失败请求，或者修改现有文件却没有新鲜基线，也都应该先被拦截。用户不应该被要求审批一个本来就无效的请求。

工具输出的大小同样属于安全问题。搜索返回一万条匹配结果，并不会让模型更聪明；Shell 打印巨大日志，可能把真正的用户请求淹没；每一轮重复读取同一个没有变化的文件，也会挤走更有价值的上下文。

因此，工具需要设置结果上限。标准输出和错误输出可以截断，大文件应该使用偏移量和长度来读取，搜索要限制最大匹配数，二进制文件只返回元数据，差异则尽量返回摘要。

限制输出不是单纯的用户体验优化，它是在保护代理的判断能力。

##### 四、斜杠命令：用户控制代理运行时的工具箱

编码代理不应该只有一个提示输入框。

普通请求，比如“修复失败的测试”“解释这个模块”“增加一个配置选项”，可以交给模型处理。但像 `/status`、`/tools`、`/reset`、`/audit`，或者 `/goal pause` 这样的命令，本质上是在控制代理运行时，不应该被当作普通聊天内容发送给模型。

核心结论是：斜杠命令属于用户和线束，而不是模型。

如果所有输入都走同一条路径，就会出现一些明显问题。用户输入 `/status`，模型可能凭空编一个状态；用户输入 `/reset`，模型可能只是讨论“如何重置”，却没有真正清除会话状态；用户输入 `/goal pause`，模型可能把它当成任务中的一条普通指令；如果用户把命令拼错，模型还可能自行猜测，而不是返回命令帮助。

这些问题发生在模型调用之前。根本原因是线束没有正确路由输入。

因此，一个成熟的代理通常需要两个解析边界。第一个解析用户输入，第二个解析模型输出。

用户输入进入线束后，输入路由器要先判断：是不是空输入；是不是已知的斜杠命令；是不是未知命令；是否可以由本地运行时直接回答；只有普通工作请求，才进入模型调用。

换句话说，不是每一段文字都会变成提示词。提示框是用户请求工作的入口，斜杠命令则是用户控制工作者的入口。

`/goal` 是一个特殊例子。它既涉及用户控制，也会影响模型工作。用户可以通过 `/goal` 设置目标、暂停、恢复、完成或清除目标。模型可以在提示词中看到当前目标，也可能拥有非常有限的工具，例如读取目标，或者在有证据时更新目标为完成。

但模型不应该自由地创建、暂停、恢复或清除目标。目标属于用户控制的会话状态，而且任务是否完成，应该依赖测试、验证或其他证据，而不是模型单纯“感觉自己做完了”。

诊断命令也应该尽量在本地执行。比如 `/audit` 和 `/doctor` 应该直接检查线束的运行状态，而不是询问模型“我的会话看起来健康吗”。只有本地检查，才能报告真实的运行时不变量，而不是让模型猜测。

当这些命令存在之后，用户就可以直接询问当前工作区、可用工具、活动目标、下一轮会进入哪些状态、上次编辑改变了什么，以及会话是否需要重置、暂停、恢复或压缩。

因此，斜杠之后的内容属于线束。它不是普通聊天。

##### 五、Markdown 文件其实是一种上下文接口

接下来，看项目中的 Markdown 文件。

核心结论是：Markdown 文件之所以能改变编码代理的行为，不是因为它本身有什么魔力，而是因为线束发现了它、理解了它的角色，并把它放到了正确的上下文位置。

例如，加入 `AGENTS.md` 后，代理可以开始遵守仓库特有的操作规则。加入 `SKILL.md` 后，代理可以在特定任务中获得一套更专业的工作流程。

但简单地把所有 Markdown 文件都找出来，再全部粘贴进系统提示词，并不是好的设计。`README.md` 主要介绍项目；`AGENTS.md` 规定在这个仓库中应该怎样工作；`SKILL.md` 描述某一类任务的具体步骤；设计文档、会议记录、更新日志和临时笔记，又有不同的作用和生命周期。

所以，线束必须先判断文件是什么，再决定何时加载、加载到哪里，以及它应该影响模型的哪一层行为。

`AGENTS.md` 和 `SKILL.md` 是最典型的区别。

`AGENTS.md` 是工作区指令。它表达的是：在这个仓库、目录或子目录中，代理应该遵守哪些规则。线束通常会从当前工作目录开始，解析工作区，找到最近的多个 `AGENTS.md`，合并不同目录范围的规则，再把它们放入稳定的上下文，最后才构造模型提示词。

也就是说，模型不需要每一轮自己搜索规则。线束会在模型调用前，把适用于当前范围的规则准备好。

`SKILL.md` 的作用不同。它更像某一类任务的操作手册，比如应该使用哪些工具、检查哪些文件、按照什么顺序工作、什么验证结果才算完成，以及最终输出应该采用什么形式。

技能文件不应该在每一轮都完整加载，否则会浪费上下文。更成熟的做法是“渐进式披露”：先只提供技能名称、描述和适用场景这些便宜的元数据；只有当当前任务确实需要这个技能时，才加载完整内容；技能引用的其他资料，也只在需要时读取。

这样，基础上下文可以保持较小，但代理在需要专业流程时，又能得到一份恰到好处的本地操作手册。

简单来说，`AGENTS.md` 更像稳定的仓库法律，进入当前工作范围后持续影响行动；`SKILL.md` 更像按需加载的任务流程，只在特定任务中发挥作用。同样是 Markdown 文件，但线束赋予了它们不同的角色。

##### 六、上下文不是越多越好，而是一次模型调用的投影

随着对话变长，编码代理会遇到另一个共同问题：它读过文件，运行过命令，搜索过日志，修改过代码，也处理过很多已经结束的问题。

最容易想到的办法是把所有内容不断追加到提示词里。但这更像是上下文洪水，而不是真正的记忆。

旧的工具输出会和当前证据竞争；巨大的 Shell 日志会掩盖新的指令；昨天仍然正确的文件读取，今天看起来却可能仍然有效。

核心结论是：转录记录负责完整保存过去，而上下文负责挑选现在最重要的内容。

一个成熟的框架至少要区分三件事。

第一是持久记录，也就是完整日志，保存会话中发生过什么。第二是模型可见的上下文，也就是某一次调用真正放进提示词的内容。第三是应用状态，保存文件、目标、任务、权限、附件、验证结果和其他结构化事实。

如果这三者混在一起，压缩历史就可能丢失关键事实。如果把它们分开，压缩就会变成一种可以设计和控制的工程操作。

在每次模型调用前，线束都应该执行上下文投影。它先从完整日志出发，再挑选当前用户请求、最近几轮对话、相关文件、活动目标和未解决的工具结果；然后检查上下文预算；必要时压缩旧内容；最后加入必须保留的状态块，生成这一次模型能看到的工作视图。

模型拿到的不是“整个会话”，而是经过筛选的当前视图。

材料中总结了四种有用的上下文管理方式。

第一，大结果预览。完整的工具结果可以保存在外部，提示词里只放摘要、数量、路径和后续检索所需的句柄。

第二，空闲间隔后的微型压缩。如果用户隔了很久才回来，可以先把旧对话压缩成摘要，避免下一轮携带大量已经过时的细节。

第三，折叠旧内容。已经解决的计划、尝试和错误，可以压缩成简短状态，但要保留关键证据和决策。

第四，接近上限时自动压缩。当上下文窗口快要达到限制时，应该在模型调用前主动压缩，而不是等调用失败。

自动压缩不能只是简单地说“太长了就总结”。它还需要预警阈值，让用户知道大概还剩多少空间；硬性阻断阈值，确保提示词一定能放下；为模型输出预留空间；避免压缩过程无限递归；连续失败时触发保护机制；压缩完成后清理无效的临时状态，并恢复下一轮仍然需要的附件和状态块。

真正困难的地方，不是把内容缩短，而是保留未来工作仍然需要的事实。

最后还要区分记忆和上下文。记忆是保存下来的状态；上下文是某一次模型调用选出来的视图。短期工作记忆、当前会话中的决策和证据、长期的用户或项目偏好，以及从真实工作区刷新出来的环境事实，都可以成为不同的记忆通道。线束负责把这些通道投影成当前提示词。

##### 七、子代理是一次受管理的上下文分叉

最后，看子代理。

核心结论是：子代理不是神奇的并行模型，而是一次工具调用，以及由这次调用打开的一个新的、受管理的工作运行时。

在父代理看来，启动子代理通常就是一个工具调用。例如，父代理可以发出类似 `spawn_agent` 的请求，并提供任务名称、说明、代理类型和需要继承的上下文范围。线束接受请求后，会返回一个子代理句柄。父代理随后可以等待子代理、发送后续消息、查看它的状态、暂停它，或者读取它整理后的结果。

工具调用在外部，子代理运行时在内部。

这个子运行时可以拥有自己的线程或会话、自己的转录记录、自己的上下文投影、指定的角色、独立的工具和权限，以及与父代理共享的工作目录、代码仓库、技能文件、`AGENTS.md` 或其他服务。

但共享资源不等于共享完整转录。子代理拥有自己的工作上下文，父代理必须决定到底向它投影哪些内容。

这里需要区分三个概念。

会话是运行时容器，包含线程、记录、工具、权限、资源、状态和产物。

上下文是某一次模型调用实际能够看到的指令、技能、项目规则、最近对话、摘要、工具结果和文件状态。

子代理则是父会话下的一个子运行时。它可以继承资源，但只接收经过选择的上下文片段。

不同任务需要不同的上下文分配方式。

全新的子代理适合需要完整背景介绍的任务。它应该收到目标、相关文件、已经尝试过的内容，以及明确的预期输出。

分叉子代理适合紧接着父任务继续工作，可以继承周围上下文，但仍然需要清晰的下一步指示。

部分分叉通常是更实用的折中方案。它只继承足够的本地记忆，避免把父代理完整而嘈杂的历史全部带过去。

子代理适合边界清晰、相对独立的工作。比如，一个子代理检查数据库迁移，另一个检查前端状态，第三个负责验证；也可以让探索者、规划者、验证者、执行者和评审者各自承担不同角色；还可以把长时间测试、大规模重构或代码审计放到后台运行，或者让评审者在隔离上下文中检查证据。

但代理数量越多，并不意味着结果一定越好。更多代理也意味着更多运行时状态。系统必须知道每个代理是谁、它知道什么、修改了什么、什么时候完成，以及它返回的结果怎样成为父代理可以依赖的证据。

一个完整的子代理流程应该是：父代理接收任务，判断是否值得委托；然后选择子代理角色、上下文切片、工具和权限；接着创建子运行时；子代理在自己的记录中工作；最后返回经过整理的证据，由父代理整合，并保留清晰的记录谱系。

子代理拓展了编码代理可以处理的世界，但最终仍然是线束决定这个世界会变得更清晰，还是更加混乱。

#### 最后回顾：最值得记住的五件事

第一，编码代理的核心产品不只是模型，而是围绕模型的线束。模型提出建议，线束决定哪些建议能够真正影响文件、命令和工作区。

第二，转录记录不等于文件真相。代理必须追踪文件基线，识别外部修改和部分读取，避免根据过时内容编辑代码。

第三，工具调用不是普通函数，而是改变现实世界的权限请求。工具必须经过解析、验证、授权、执行、输出限制、记录和状态更新。

第四，用户控制命令应该由线束本地处理。普通请求交给模型，斜杠命令负责查看状态、暂停任务、重置会话和运行诊断。

第五，上下文和子代理都需要经过投影和边界管理。上下文不是越多越好，子代理也不是越多越强；真正重要的是让每一次模型调用都获得准确、适量、与当前任务相关的信息。

## 深度解读（1）

### 2026-09-18 00:43:24

#### 编码代理的竞争焦点，正从模型能力转向运行时治理

这篇文章最有价值的地方，不是提出了某个新算法，而是给出了一套更准确的产品判断：**模型负责提出行动，真正决定行动能否安全、可靠地发生的，是模型之外的 harness（代理运行框架）**。

这能解释一个常见现象：两个产品使用相近的模型，实际体验却可能差异巨大。原因未必是提示词优劣，而是它们在仓库感知、工具校验、权限控制、上下文压缩、错误恢复和状态同步上的能力不同。编码代理不是“LLM 加几个函数”，而是一个持续观察、行动、验证并更新状态的运行系统。

##### 可靠性来自把“不容出错的事”移出模型

文章用文件写入说明了关键边界。模型可以请求修改 `src/config.py`，但它不应该自行判断路径是否越界、文件是否已被外部修改、是否需要审批，以及写入后应运行哪些验证。这些判断如果只写进提示词，本质上仍是建议；只有由确定性代码执行，才构成约束。

因此，“任何必须可靠的东西都应放进 harness”是一条有迁移价值的工程原则。它同样适用于客服代理、数据分析代理和企业流程代理：模型可以规划退款、查询数据或发送邮件，但权限、金额上限、数据范围、幂等性和审计记录必须由运行时掌握。

这也改变了故障诊断方式。代理重复执行，先查循环与重试策略；误改代码，先查文件基线；越用越笨，先查上下文投影；执行了意外命令，先查权限策略。**很多看起来像“模型不够聪明”的问题，其实是系统没有维护好现实状态。**

##### 对话记录不是事实，上下文也不是记忆

文章最具体、也最值得重视的是“陈旧读取陷阱”：模型读过一个文件后，用户或 Git 又修改了它，但旧内容仍留在对话中。模型没有幻觉，只是在依据已经失效的证据行动。

解决办法不是提醒模型“注意最新版本”，而是将三类对象分开：

- **持久日志**记录发生过什么；
- **结构化状态**保存文件基线、权限、目标与验证结果；
- **模型上下文**只是当前一轮需要看到的投影。

这种分离使上下文压缩从“总结聊天”变成状态工程。大段日志可以裁剪，旧讨论可以折叠，但当前文件指纹、未解决错误和已批准权限不能丢。所谓长记忆，并不是把所有历史塞进窗口，而是知道哪些事实应持久保存、何时刷新，以及何时重新投射给模型。

##### 真正的产品界面是控制面，而不只是聊天框

斜杠命令、`AGENTS.md`、技能文件和子代理看似是不同功能，实际都在解决同一问题：**谁有权改变运行状态，以及什么信息应在何时进入哪个上下文。**

`/reset`、`/status` 不应交给模型猜测；仓库规则应稳定加载，技能说明应按需展开；子代理也不应只是“多开几个模型”，而应拥有隔离的上下文、工具和权限，并向父代理返回压缩后的证据。否则并行只会放大状态混乱。

文章主要提供的是架构主张和实践框架，而不是经过基准测试验证的结论，因此不能据此断言模型能力已经不重要。更准确的判断是：**模型决定提案质量，harness 决定提案能否成为可信的产品行为。** 对编码代理团队而言，下一阶段更值得建立的优势，可能不是再包一层模型，而是可验证的状态管理、工具契约、权限系统与运行诊断能力。

## 默认总结（1）

### 2026-09-18 01:09:02

##### 一句话看懂

文章认为，编码代理真正决定可靠性与体验的，不只是大模型，而是包围模型的运行框架（harness）：它负责上下文、工具、权限、文件状态和执行流程，确保模型的建议安全地变成实际操作。

##### 关键内容

- **模型只负责提议，框架负责落地。** 每次读写文件、运行命令，都应经过参数验证、路径限制、权限审批、输出裁剪、记录与状态更新，而非直接执行模型生成的工具调用。
- **对话记录不等于当前事实。** 文件可能被用户或 Git 等外部操作修改；框架必须记录读取范围、哈希和修改状态，在编辑前检查内容是否仍然最新，避免代理依据旧代码覆盖新版本。
- **上下文不是越多越好。** 完整日志应长期保存，但每轮只向模型投射当前相关的信息；大段日志、过期文件和已解决问题需要摘要或压缩。`AGENTS.md` 属于稳定的项目规则，`SKILL.md` 则应按任务需要加载。
- **控制与委派也属于框架。** `/status`、`/reset` 等命令应由本地运行时处理；子代理则应拥有独立上下文、有限工具和权限，而不是无边界共享全部历史。

##### 通俗解读

可以把模型看成提出施工方案的人，harness 则是现场监理：核对图纸是否最新、施工范围是否合法、是否需要审批，并记录实际改了什么。作者的核心工程原则是：**凡是必须可靠的能力，都不能只靠提示词或模型自觉，而应由框架强制保证。**
