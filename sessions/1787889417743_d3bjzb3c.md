## 分析要点

- **核心高价值点**：设计Agent工具系统时，应先区分“模型需要知道什么”和“模型能够调用什么”，再根据KV缓存稳定性决定动态加载发生在上下文、工具面还是解码层。
- **留存建议**：建议精读并存档，作为Agent工具编排与上下文成本优化的架构参考（文章形成了知识层与能力层分离、稳定工具前缀及选择动态性承载位置的可复用框架，对Agent harness设计有长期参考价值。）

**知识要点**

- 改变API的tools数组可能使后续前缀缓存失效，因此动态schema的位置会显著影响长对话成本。
- Skill主要承载操作知识，可由通用工具执行；动态tool schema承载无法通过现有通用工具表达的新能力。
- 元工具按需加载适合工具规模大、单轮调用稀疏且模型选工具能力有限的场景，其代价是增加一次查询往返。

**行动项**

- 盘点现有Agent能力，将内容划分为知识型Skill、通用执行工具和必须使用结构化接口的专用能力。
- 保持核心tools数组稳定，并评估用固定元工具入口加手写提示词按需获取专用schema。
- 通过缓存命中率、输入Token成本、工具误选率和额外往返延迟，对全量常驻与按需加载方案进行对照测试。

AI AgentAI 编程

2026 年 8 月，社区把 Grok Bot 0.18.0 逆向了出来，源码公开。Grok Bot 是 Anysphere，也就是 Cursor 的公司，做的桌面 agent 产品。0.18.0 版本是一个编译后的 app，重建的源码是可读的 TypeScript，发布在 [GitHub](https://github.com/b-nnett/grok-bot-0.18-reconstructed)。事件之后 Anysphere 撤下了 0.18.0 的安装包，没有官方声明，也没有 DMCA。

这是一个罕见的机会。谈 agent harness 的设计，平时看到的是博客和设计哲学，这次能看到一个生产级 harness 的真实内部编排代码：system prompt 怎么组装、工具怎么暴露给模型、context 怎么管理。而且这个重建是 evidence-based 的，每行恢复的代码都有可检查的产物锚点，它描述的行为就是产品实际的行为。

过完源码，它的很多设计原则和领域里的 best practice 对得上。对得上有两种可能：巧合，或者模仿。怎么分辨？拿相隔一年的 Manus 对照。Manus 团队 2025 年 7 月发表过一篇 [Context Engineering](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)，讲他们怎么管理 agent 的 context。两个团队独立设计，如果收敛到同一条约束，这条约束大概率是底层逼出来的，不是谁的风格偏好。

这篇文章拆 Grok Bot 的能力层：模型能调用什么、怎么按需扩展。[下一篇](https://yage.ai/share/grok-bot-context-engineering-20260827.html)拆 context 层：模型看到什么、prompt 怎么管理。

#### 一道先查后调的门槛

Grok Bot 有 30 多个工具。其中 9 个 dynamic 工具，模型每一轮只看到一行 hint；其余 18 个静态工具直接给完整 schema。比如 CloudAgent 这个工具，模型看到的是一行话：“Launch and manage Cursor cloud coding agents for repository work.”。要用它，模型得先调 GetMcpTools 把完整 schema 拉进 context，再调 CallMcpTool 去执行。schema 太大（超过 12KB）时不塞进 context，而是写到文件、只把路径返回给模型，这个机制的 context 容量一面下一篇展开。

这给 Cursor 自己加了一道门槛。为什么不直接把 30 个工具的完整定义都给模型？

先说一个次要原因。工具太多会干扰模型，工具越多越容易选错，Manus 那篇里说 “your heavily armed agent gets dumber”，就是这个意思。但 30 个工具的量级还不算大，干扰有限，这不是主因。

主因是 KV cache。跨请求有一层前缀缓存：这次开头一段 token 和上次一模一样时，这段按缓存价计费，比原价便宜 10 倍（Claude Sonnet 的 cached input 是 0.30 美元每百万 token，uncached 是 3.00）。agent 运行时 input 和 output token 的比例大约是 100:1，成本大头在 input。失效机制和这些数字下一篇展开，本篇只引用结论。

这里要分清两种放工具定义的方式。用结构化的 tools 参数时，provider 把它序列化在 context 最前面，Manus 在博客里观察到的正是这个位置。API 层面你看不到这个序列化结果，tools 只是个独立参数，但缓存行为会暴露它：改一次 tools，连后面 messages 的缓存也全失效，[Anthropic 的缓存文档](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)把这个失效顺序写得很清楚。它每一轮不变时，整个前缀（工具、system prompt、到目前为止的对话）都和上一轮相同，全部命中缓存，只有新加的这一轮按原价算。

tools 参数一变就不一样。工具在最前面，第一个不同的 token 出现在很靠前的位置，从那个位置起缓存失效，等于整个前缀每一轮都重算，付的是原价，而且前缀很大，每一轮都在付。工具本身只占一小段，但它控制着后面整段大前缀能不能拿到 10 倍折扣。

把工具定义写进对话内容是另一条路。位置自己控制，追加在对话末尾，前面的 token 一个不动，前缀缓存完整保留，只有新加的那段按原价算。API 允许每轮改 tools 数组，也允许在 message 里定义工具，限制不在 API，在缓存经济学：动态 schema 放哪一层，决定前缀稳不稳。Grok Bot 的 meta-tool 走的就是这条：动态 schema 不进 tools 数组，进对话。

Cursor 加那道门槛，目的是让工具面保持稳定。tools 数组里只有静态核心工具（READ、SHELL、WRITE、GLOB、GREP 这些每轮都要用的）加上 GetMcpTools 和 CallMcpTool 两个稳定入口。其余 9 个工具的完整 schema 不进 tools 数组，以一行 hint 的形式存在，需要时才拉进 context。

那个一行 hint 不是自动截断工具 description 生成的。源码里有一个叫 SAND\_DYNAMIC\_TOOL\_HINTS 的常量，9 个 hint 全是手写的。CLOUD\_AGENT 对应的那行，是有人专门写了告诉模型这个工具能做什么、什么时候该选它。这是产品决策，需要逐条打磨。但这里有个没答的问题：为什么只有这 9 个工具需要这套动态机制？其余 18 个静态工具为什么不用？

#### “动态加载”掩盖了两个正交维度

答案在于工具本身有两种不同性质。模型能对外界做事，靠的是 tools 数组，它通过结构化的 tool call 调用里面的工具。但 tools 数组里不只有专门工具，还有 bash、read、write 这类通用工具。bash 尤其强，通过它模型能调任何 CLI、跑 Python、curl 任何 HTTP 端点。模型的手，大部分时候是这少数几个通用工具。

这里有个容易忽略的事实：很多新能力不需要新工具。一个能力如果能用 bash 表达（一个 CLI、一段 Python、一个 HTTP 端点），模型只需要知道怎么驱动它，知识放进 context 就够了。能力由已有的 bash 提供，skill 只提供知识，不用往 tools 数组里加任何东西。我们的 [skill 体系](https://skills.superlinear.academy/)就是这么做的：skill 是 markdown，教模型怎么调一个 CLI，模型用 bash 执行。这也是 [thin harness fat skills](https://yage.ai/share/thin-harness-fat-skills-20260414.html) 能成立的原因。

动态加载把两种事情混在一起了。一个是知识层：按需把怎么做拉进 context。载体是 markdown，机制是检索、路由、加载。Claude 的 Agent Skills 就是这一层，加载一个 skill 是读文件进 context，模型知道怎么做了，用已有的 bash 去执行。

另一个是能力层：按需把能调用什么暴露给模型。载体是 tool schema，也就是传给 API 的 tools 参数里的 entry，不是 context 内容。这一层只在能力没法用已有通用工具表达时才需要：一个要在沙箱远端 box 里跑的功能、一个需要 app 内部状态或鉴权的功能、一个需要特定结构化接口的功能。这些没法用 bash 表达，必须往 tools 数组里加一个新的 tool schema。Grok Bot 的 GetMcpTools/CallMcpTool 就是这一层。

关键区别在机制归属：skill 是知识载体，它的机制是检索、路由、把 markdown 读进 context，它没有能力去改下一次请求的 tools 参数。tools 数组是 harness 的东西，由构建每次请求的应用代码决定。skill 的加载改变的是 context 内容（模型知道怎么做），能力层的加载改变的是 tools 数组（模型能调什么）。能力必须走 tool call 而不是 bash，skill 的机制就覆盖不到，得用能力层的机制。

这个分层之所以能成立，是因为知识层在 Grok Bot 出现前的一年里已经有了独立成熟的机制。如果知识层还没有自己的载体，两层就没法分开做。

知识层和能力层是两个正交维度：skill 加载把怎么做拉进 context，dynamic tool 加载把能调用什么放进 tools 数组，两者不能互相替代

#### 知识层的演化时间线

理解 Grok Bot 为什么能把能力层和知识层分开做，需要先看知识层在这一年里怎么成熟的。2025 年 7 月，Manus 团队发表了 Context Engineering 那篇文章。当时还没有 skill 机制。Manus 解 context 工程时，知识层没有独立的 markdown skill 载体，它用文件系统和复述来外置和保持目标。

三个月后，2025 年 10 月 16 日，Anthropic 发布了 [Agent Skills](https://claude.com/blog/skills)。Claude 先行，知识层第一次有了独立载体：一个文件夹，包含指令、脚本和资源，模型只在相关时按需加载。两个月后，2025 年 12 月 18 日，Anthropic 把它发布为[开放标准](https://agentskills.io/)，Codex、Cursor、VS Code 跟进支持。有一篇论文做了 8135 次受控实验，发现 65.7% 的提升靠的是步骤和检查单类的 skill，只有 4.5% 靠补充事实。[这篇论文我们拆过](https://yage.ai/share/skill-checklist-not-textbook-20260823.html)：skill 是检查单，不是教材。

在我们的本地系统里，这对应一个三级缓存结构：L1 是每次都加载的 AGENTS.md（大约 200 行指针），L2 是按需查的索引，L3 是匹配后才加载的具体 skill 文件。Garry Tan 那篇 [thin harness fat skills](https://x.com/garrytan/status/2042925773300908103) 讲的就是这一层，harness 只做四件事，智能推到 skills，执行推到确定性工具。

到 2026 年 8 月 Grok Bot 泄露时，它已经有了 skill 和 plugin。system prompt 里原话说 plugin 是”a marketplace bundle of connectors and skills”。再往极端走，DSH 把连 agent loop 都做成了插件，这是知识层动态加载的极限形态，但需要 Cordis 那套运行时基础设施。

知识层有了自己的载体，能力层才能做干净的事：只处理 bash 表达不了的那部分。Grok Bot 在这一层的设计，才是本篇的主角。

Grok Bot 的 dynamic tool 机制，拆开来是三块相互咬合的设计。

native 工具包成虚拟 MCP server：Cursor 把自己的 native 工具（CloudAgent、CopyToBox 等）包装成一个 namespace 为 “cursor” 的虚拟 MCP server。源码里的常量 CURSOR\_DYNAMIC\_TOOLS\_NAMESPACE 就是 “cursor”。这样模型用同一对 GetMcpTools/CallMcpTool 访问 native 工具和外部 MCP 插件，只学一个调用模式。CallMcpTool 的 dispatch 层会拦截原始参数，解析出真实工具名，路由到 native executor 或者外部 server。

一行 hint 是产品决策。SAND\_DYNAMIC\_TOOL\_HINTS 里那 9 个 hint 是手写的。每个 dynamic 工具都带上 contextType: { type: “dynamic”, conciseStaticContext: hint } 标记，模型看到的就是那一行话。这是有人专门写的路由提示，不是从工具的 description 字段截断来的。工具多到一定程度，模型需要一层路由来判断该选哪个，这层路由需要手工打磨。

这个 index 是雅虎式的，不是谷歌式的。谷歌模式假设信息已经在那儿了，提问时实时检索出来就行；雅虎模式靠主编人工筛选、撰写、组织目录。这 9 行 hint 就是产品团队当了主编，在模型提问之前把工具面编成每工具一行。OpenAI 的数据 agent 里我们见过同一个模式：[那篇文章](https://yage.ai/share/openai-data-agent-offline-context-20260806.html)里 LLM 接管离线主编的角色，把杂乱的数仓代码预先编译成高密度 context，在线端只检索编好的材料，不检索原始元数据。

skill 和 dynamic tool 正交，各管一层。Grok Bot 两个都有。skill 走 plugin 体系，管知识层。dynamic tool 机制只用于 app 自己的 native 工具，管能力层。两者不混。但这套设计不是唯一答案：同期独立设计的 Manus 走了一条完全相反的路。

Grok Bot 的先查后调流程：模型先看到一行 hint，用 GetMcpTools 拉 schema，再用 CallMcpTool 执行，dispatch 层路由到 native executor 或外部 server

#### Manus 的对照：Mask, Don’t Remove

Manus 的方向正好相反：不动态加载工具，而是一开始就把所有工具全量放进去，然后在解码时决定哪些不能选。原因有两个。工具定义序列化后位于 context 前端，任何改动都会 invalidate 后面所有 KV cache。历史的 action 和 observation 还在引用已经不存在的工具，模型会困惑并产生 schema violation。

他们的解法叫 “Mask, Don’t Remove”：工具定义永远静态全量，用 context-aware 的状态机在解码时 mask token logits，约束当前状态可选哪些工具。工具名刻意设计成一致前缀，比如 browser\_ 开头的工具和 shell\_ 开头的工具，方便按组约束。

看起来，Manus 说别动态加工具，Grok Bot 却在动态加载工具，两个答案相反。实际上两者守的是同一条底层规则：序列化的工具面必须稳定，把动态性推到别处去。差的只是推到哪一层。

Manus 推到解码时。工具全量常驻 context，动态的是当前能选哪些。代价是所有 schema 常驻 context 的 token 税，收益是 KV cache 完全稳定。

Grok Bot 推到 context 层。tools 数组里只有静态核心加上两个稳定的 meta-tool 入口，动态工具的 schema 不进 tools 数组，以一行 hint 存在，需要时才拉进 context。它看起来在动态加载，但序列化的工具面其实是稳定的。这正好符合 Manus 那条规则。

两个团队、相隔一年、独立设计，收敛到工具面必须稳这同一条约束。两者都走到这里，说明这条约束是底层压出来的，不是设计偏好。那剩下的问题就是：动态性推到哪一层，各有什么代价？

#### 动态性住到哪决定整个设计

把四个 harness 放在一起看，动态性住到哪决定了整个设计：

harness 动态性住哪 代价 / 收益

Codex 声明式 + 重启（公开声明） 简单，但换工具要重启进程

Manus 2025/7 解码时 KV cache 全稳，但 schema 常驻 token 税

Grok Bot 2026/8 context 层 工具面稳 + schema 按需，但多一次 GetMcpTools 往返

DSH 进程内插件（连 loop 都可换） 最灵活，但要 Cordis 那套运行时基础设施

四个 harness 的动态性住哪决定整个设计：Codex 重启进程，Manus 解码时屏蔽，Grok Bot 放 context 层，DSH 进程内插件

什么时候该用 Grok Bot 这种方式？算一笔成本账：多一次 GetMcpTools 往返的边际成本，要小于 N 个未用 schema 的常驻税。只在工具面大、单轮使用稀疏、模型选择能力有限这三个条件同时满足时才划算。DSH 那篇里有个判断：上限相同，下限不同。工具少的时候几种方式差不多，工具多了之后下限的差距就出来了。

这条约束的因果链条下一篇会展开。KV cache 经济学的数字也在那边给。

给写 harness 的人一个收尾：先分清要拉的是知识还是能力，别用错层的机制。能力层的动态性，先决定它住哪一层，再谈实现。两个独立产品收敛到同一条约束，这本身就是判断该不该抄这个设计的依据。

## 通俗精炼（1）

### 2026-08-28 03:56:57

#### Grok Bot 动态工具设计：稳定工具面，按需加载能力

##### 一句话总结

Cursor 没有把所有工具的完整定义一次性交给模型，而是采用 “**核心工具常驻 + 专用工具按需查询**” 的方式。核心目的不是单纯节省上下文，而是**保持工具前缀稳定、提高 KV Cache 命中率，从而降低 Agent 的运行成本**。

##### Grok Bot 如何管理工具

Grok Bot 拥有 30 多个工具，分为两类：

- **静态工具**：约 18 个，如`READ`、`WRITE`、`SHELL`、`GREP`，完整 Schema 每轮都提供。
- **动态工具**：约 9 个，模型最初只看到人工编写的一行能力提示。

使用动态工具时，模型需要：

1. 调用`GetMcpTools`获取完整 Schema；
2. 再通过`CallMcpTool`执行工具；
3. 如果 Schema 超过 12KB，则写入文件，只向模型返回路径。

本质上，`GetMcpTools`和`CallMcpTool`是两个稳定的 “能力入口”。

##### 核心原因：KV Cache 经济学

工具定义通常会被序列化到上下文最前端。如果每轮修改`tools`数组，前缀会发生变化，后续 system prompt 和历史对话的缓存也可能一起失效。

这会带来明显成本：

- Agent 的输入 Token 通常远高于输出 Token；
- 缓存输入价格可能只有非缓存输入的十分之一；
- 工具定义虽然不长，却决定了后面整段上下文能否命中缓存。

因此，Grok Bot 将核心工具和两个 Meta Tool 固定在`tools`数组中，把其他工具 Schema 按需追加到对话上下文末尾。这样既能保留前缀缓存，又不用长期承担全部 Schema 的 Token 成本。

##### 关键分层：知识与能力不是一回事

| 维度 | 知识层 | 能力层 |
|---|---|---|
| 解决的问题 | 模型是否知道怎么做 | 模型是否真的能够调用 |
| 典型载体 | Markdown、Skill、指令、检查单 | Tool Schema、内部接口 |
| 加载方式 | 检索并写入 Context | 由 Harness 暴露执行入口 |
| 适用场景 | CLI、Python、HTTP 可完成的任务 | 内部状态、鉴权、远程沙箱等专用功能 |

很多所谓 “新能力” 其实不需要增加新工具。只要 Bash 能完成，Skill 只需告诉模型执行方法。

只有无法通过通用工具表达的能力，例如内部鉴权、应用状态或远程执行，才需要专门的工具机制。

> **Skill 提供知识，Tool 提供权限和执行能力。**

##### 一行 Hint 也是产品设计

动态工具的一行提示并非自动截断生成，而是由产品团队逐条手写。

它承担的是 “工具路由” 职责：

- 告诉模型工具能做什么；
- 说明什么情况下应该选择它；
- 帮助模型在大量工具中快速定位。

这更像 “雅虎式人工目录”，而不是实时搜索：产品团队提前筛选、组织并压缩工具信息。工具越多，这层提示词的信息密度和准确性越重要。

##### 与 Manus 的对照

Manus 采用的是**“Mask, Don’t Remove”**：

- 所有工具 Schema 始终常驻；
- 工具定义保持不变；
- 在解码阶段，根据当前状态屏蔽不可用工具。

两种方案看似相反，实际遵守同一原则：

> **序列化后的工具面必须稳定，动态性应被转移到其他层。**

| 方案 | 动态性所在位置 | 优点 | 代价 |
|---|---|---|---|
| Manus | 解码阶段 | KV Cache 最稳定 | 所有 Schema 长期占用 Token |
| Grok Bot | Context 层 | Schema 按需加载，常驻成本低 | 多一次查询工具的往返 |
| Codex | 声明配置与重启 | 实现简单 | 切换工具需要重启 |
| DSH | 进程内插件 | 灵活性最高 | 运行时基础设施复杂 |

##### 何时适合采用 Grok Bot 方案

只有同时满足以下条件，按需加载才更划算：

1. **工具数量较多**；
2. **单轮只会使用少数工具**；
3. **模型面对完整工具集时容易选错**；
4. 获取 Schema 的额外调用成本，低于未使用 Schema 的长期 Token 成本。

工具较少时，几种方案差异有限；工具规模扩大后，缓存稳定性与常驻 Token 成本才会成为决定性因素。

##### 对 Agent 产品设计的启示

###### 1. 先判断新增的是知识还是能力

- 能用 Bash、CLI 或 HTTP 完成：优先做成 Skill；
- 必须依赖内部权限、状态或专用执行环境：再做 Tool。

###### 2. 不要轻易动态修改`tools`数组

动态修改工具定义可能破坏前缀缓存，影响的不只是工具 Schema，而是后续整段上下文。

###### 3. Harness 应尽量薄而稳定

Harness 负责稳定入口、路由和执行；知识与流程尽量沉淀到可按需加载的 Skills 中。

###### 4. 动态性的落点决定系统架构

真正需要决策的不是 “要不要动态加载”，而是：

> **动态性应该放在 Context、解码阶段，还是运行时插件层？**

##### 最终结论

Grok Bot 的设计重点不是 “隐藏部分工具”，而是通过稳定工具面获得三重收益：

- **保持 KV Cache 命中率；**
- **减少无用 Schema 的 Token 税；**
- **降低模型在大量工具中的选择难度。**

Cursor 与 Manus 虽然实现路径不同，却独立收敛到同一底层约束：**工具前缀必须稳定，动态性应移到缓存影响更小的层。**

## 深度解读（1）

### 2026-09-18 10:16:13

#### Agent 工具设计的关键，不是“动态加载”，而是把动态性放对位置

Grok Bot 的实现揭示了一个容易被低估的事实：**工具定义不仅是给模型看的说明书，也是影响推理成本的系统状态。**

据逆向源码，Grok Bot 有 30 多个工具，但其中 9 个只向模型展示一行手写提示。模型确认需要后，先通过 `GetMcpTools` 获取完整 schema，再由统一的 `CallMcpTool` 执行。Cursor 为此增加了一次调用，却避免把所有定义长期塞进每轮请求。

##### 真正昂贵的不是 schema，而是缓存失效

文章最有价值的解释，是把工具设计与 KV cache 经济学连了起来。

工具通过 API 的 `tools` 参数传入时，通常被序列化在上下文前部。只要工具列表发生变化，从变化位置开始的后续前缀缓存就可能全部失效。对输入 token 远多于输出 token 的 Agent 来说，损失的不只是几千个 schema token，而是整段历史上下文原本可以获得的缓存折扣。

因此，Grok Bot 表面上在“动态加载工具”，实际上始终保持结构化工具面稳定：核心工具加两个 meta-tool 固定不变，专用工具的定义则作为新消息追加到上下文末尾。**它优化的是缓存边界，而不只是上下文长度。**

这也解释了它与 Manus 看似相反、实则一致的选择。Manus 让所有工具常驻，再在解码阶段屏蔽当前不可用的工具；Grok Bot 则保留稳定入口，按需补充 schema。两者都遵守同一原则：不要频繁改动序列化在上下文前端的工具面。区别只是前者承担常驻 token 税，后者承担额外往返和路由失败风险。

##### 先分清缺的是知识，还是新的执行能力

文章提出的第二个重要区分是：很多所谓“新能力”，其实只缺操作知识。

如果任务能通过 shell、Python、CLI 或 HTTP 完成，模型已经有“手”，只需要一份 markdown 告诉它步骤、参数和检查项。这适合用 skill 按需加载。只有涉及应用内部状态、特殊鉴权、远程沙箱或严格结构化接口时，才真正需要新增 tool schema。

这个区分直接影响 Agent 平台的复杂度：**不要为每项业务知识都造一个工具，也不要指望 skill 能替代权限受控的执行接口。**前者会让工具面膨胀，后者则会模糊安全边界。

##### 是否值得采用，要看四个可测变量

Grok Bot 的方案并非普遍更优。它成立的条件是：工具数量多、schema 较大、单轮调用稀疏，而且模型仅凭短提示仍能正确路由。实际决策应测量缓存命中率、常驻 schema 成本、额外往返延迟，以及“先查后调”的成功率，而不是照搬架构。

还有一个文章未展开的重要边界：统一的 `CallMcpTool` 扩大了单一入口的权限范围。鉴权、用户确认、审计和参数校验必须落在执行器中，不能依赖提示词。

最终值得保留的判断是：**Agent 架构中的动态性不会消失，只会被搬到 context、解码、进程或插件层。先决定它住在哪里，再讨论动态加载的实现，往往比先选框架更重要。**

## 口播总结（1）

### 2026-09-20 00:18:24

Cursor 为什么只给模型一部分工具的完整定义？表面上看，是为了减少工具数量，避免模型选错。更深层的原因，却是保持上下文前缀稳定，从而尽可能利用键值缓存，也就是 K V cache，大幅降低智能体的运行成本。

这个判断来自对 Grok Bot 零点十八版本的逆向分析。Grok Bot 是 Cursor 母公司 Anysphere 开发的桌面智能体。逆向出来的代码显示，它拥有三十多个工具，但并不会把所有工具的完整定义都直接交给模型。

其中，常用的读文件、写文件、执行命令、搜索内容等工具，会以完整的结构定义常驻。另有九个动态工具，模型平时只能看到一句简短提示。比如 Cloud Agent，模型只知道它可以启动和管理云端编程智能体。真正需要使用时，模型必须先调用 Get MCP Tools，取回完整的工具定义，再通过 Call MCP Tool 执行。如果定义超过十二 K B，系统甚至不会直接把内容塞进上下文，而是写入文件，只把文件路径交给模型。

这相当于给工具调用增加了一道“先查后用”的门槛。为什么要故意多走一步？

一个次要原因是，工具越多，模型越容易选错。但三十多个工具还不算特别夸张。更重要的原因，是缓存成本。

大模型接口通常会缓存请求中没有变化的前缀。只要本次请求开头的一段内容，和上次完全相同，这部分就可以按缓存价格计费。以文章引用的 Claude Sonnet 价格为例，每百万输入 token，未缓存部分是三美元，缓存部分只有零点三美元，相差十倍。

智能体尤其在意这件事，因为智能体会反复调用模型，而且输入 token 往往远多于输出。文章给出的典型比例大约是一百比一。也就是说，真正的成本大头，是模型每一轮重新读取的上下文。

问题出在工具定义的位置。通过接口中的 tools 参数提交工具时，服务商通常会把工具定义序列化到整个上下文的最前面。后面才是系统提示词和对话记录。如果 tools 数组每轮都不变，前面的工具、提示词和历史对话就可以持续命中缓存，只有最新增加的内容按原价计算。

可一旦 tools 数组发生变化，第一个不同的 token 会出现在上下文很靠前的位置。从那里开始，后面的大段内容都可能失去缓存。虽然新工具本身只占一小段，却会让后面的整个前缀重新计费。

Grok Bot 的办法，是让结构化的工具面保持不变。tools 数组里只放常驻核心工具，再加上 Get MCP Tools 和 Call MCP Tool 这两个稳定入口。动态工具的完整定义不进入 tools 数组，而是在真正需要时，作为新的对话内容追加到末尾。这样，前面的缓存不受影响，只有新增加的定义需要按原价处理。

所以，所谓“动态加载工具”，关键不只是少放几个定义，而是把动态内容放在不会破坏缓存的位置。

理解这一点，还要区分两个经常被混在一起的概念：知识和能力。

很多新功能其实不需要增加新工具。如果某件事可以通过命令行、Python 脚本或者 HTTP 接口完成，那么模型已经可以用 bash 之类的通用工具执行。模型缺少的只是操作方法。此时，只要按需加载一份说明文档，让模型知道步骤和注意事项就够了。

这就是 skill，也就是技能文件的作用。skill 属于知识层。它告诉模型怎么做，但不增加模型能够调用的底层能力。文章引用的一项研究发现，技能带来的提升，大部分来自步骤说明和检查清单，而不是补充事实知识。换句话说，skill 更像操作清单，不像教科书。

但有些能力不能通过 bash 表达。比如，它需要访问应用内部状态，需要特殊鉴权，或者必须调用一个结构化的远程接口。这时，仅仅告诉模型“怎么做”没有用，还必须给模型一个真正可调用的新入口。这才属于能力层，也就是工具定义所在的层。

Grok Bot 同时使用了这两套机制。知识层由 skill 和插件负责。能力层则由动态工具负责。Cursor 还把自家的原生工具包装成一个虚拟的 MCP 服务。这样，无论调用 Cursor 内部功能，还是外部 MCP 插件，模型都只需要学习同一种流程：先查询工具定义，再通过统一入口调用。

值得注意的是，那九条简短提示并不是自动截断完整描述生成的，而是产品团队逐条手写的。它们要用一句话告诉模型，这个工具能做什么，以及什么时候应该选择它。这更像人工编辑的目录，而不是临时搜索。工具越多，这层路由提示就越需要精心设计。

把 Grok Bot 和 Manus 对照，会看到一个看似矛盾、实际上高度一致的结论。

Manus 采用的是“遮蔽，而不是移除”。它一开始就把所有工具定义全部放进上下文，然后在模型生成答案时，通过状态机限制当前可以选择哪些工具。这样，工具定义始终不变，缓存最稳定。代价是所有工具的定义都要常驻上下文，持续占用 token。

Grok Bot 看起来走了相反路线：只在需要时加载完整定义。代价是多一次查询往返，收益是不用长期携带大量未使用的工具定义。

但两者真正遵守的是同一条底层规则：序列化到上下文前端的工具面必须稳定。Manus 把动态性放到解码阶段，动态决定哪些工具可以选。Grok Bot 把动态性放到对话上下文里，tools 数组本身仍然不变。不同的只是动态性被安置在哪一层。

什么时候值得采用 Grok Bot 的方式？文章给出的判断是，通常要同时满足三个条件：工具总量很大，每一轮实际使用的工具很少，而且模型面对大量工具时容易选错。只有这时，多一次查询的成本，才可能低于大量未用工具长期占据上下文的成本。

最值得记住的认识有两个。第一，设计智能体时，要先分清需要加载的是知识，还是新的执行能力。知识交给 skill，能力才需要工具机制。第二，真正重要的不是“能不能动态加载”，而是动态性放在哪里。只要破坏了上下文前缀的稳定性，一个很小的工具变化，也可能让后面整段缓存失效。
