[Deep Agents Logo](https://docs.langchain.com/oss/python/deepagents/overview#deep-agents-overview)

Deep Agents is an agent harness. An opinionated, ready-to-run agent out of the box. Instead of wiring up prompts, tools, and context management yourself, you get a working agent immediately and customize what you need.

**What's included:**

- **Planning** — `write_todos` for task breakdown and progress tracking
- **Filesystem** — `read_file`, `write_file`, `edit_file`, `ls`, `glob`, `grep` for reading and writing context
- **Shell access** — `execute` for running commands (with sandboxing)
- **Sub-agents** — `task` for delegating work with isolated context windows
- **Smart defaults** — Prompts that teach the model how to use these tools effectively
- **Context management** — Auto-summarization when conversations get long, large outputs saved to files

#### Quickstart

```
pip install deepagents
# or
uv add deepagents
```

```
from deepagents import create_deep_agent

agent = create_deep_agent()
result = agent.invoke({"messages": [{"role": "user", "content": "Research LangGraph and write a summary"}]})
```

The agent can plan, read/write files, and manage its own context. Add tools, customize prompts, or swap models as needed.

#### Customization

Add your own tools, swap models, customize prompts, configure sub-agents, and more. See the [documentation](https://docs.langchain.com/oss/python/deepagents/overview) for full details.

```
from langchain.chat_models import init_chat_model

agent = create_deep_agent(
    model=init_chat_model("openai:gpt-4o"),
    tools=[my_custom_tool],
    system_prompt="You are a research assistant.",
)
```

MCP is supported via [`langchain-mcp-adapters`](https://github.com/langchain-ai/langchain-mcp-adapters).

Deep Agents CLI

```
curl -LsSf https://raw.githubusercontent.com/langchain-ai/deepagents/main/libs/cli/scripts/install.sh | bash
```

Web search, remote sandboxes, persistent memory, human-in-the-loop approval, and more. See the CLI README for the full feature set.

#### LangGraph Native

`create_deep_agent` returns a compiled [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) graph. Use it with streaming, Studio, checkpointers, or any LangGraph feature.

#### FAQ

#### Deep Agents 内容总结

Deep Agents 是 LangChain / LangGraph 生态里的一个“现成可用”的智能体框架，目标是让开发者不用自己从零拼装提示词、工具和上下文管理，也能快速得到一个能工作的 Agent。  
它的核心价值在于：开箱即用，同时又保留足够强的可定制能力，适合处理更复杂的智能体任务。

##### 1. 项目定位：一个可直接运行的 Agent 框架

- Deep Agents 被定义为一个 **agent harness（智能体运行框架）**，强调“拿来就能用”。
- 相比手动配置 prompts、tools 和 context management，它直接提供了一套可运行的默认方案。
- 用户可以先快速启动，再按需替换模型、增加工具、调整提示词，而不是一开始就做大量底层搭建。

**通俗理解：**  
如果传统做法像是自己组装一台电脑，Deep Agents 更像是一台已经能开机使用的整机，你只需要在后续再升级显卡或换软件。

---

##### 2. 开箱即用的核心能力

原文重点列出了 Deep Agents 自带的几类能力：

###### 2.1 规划能力（Planning）
- 提供 `write_todos`，用于任务拆解和进度跟踪。
- 这意味着 Agent 不只是“接收问题-输出答案”，还会把复杂任务拆成步骤执行。

###### 2.2 文件系统能力（Filesystem）
- 支持 `read_file`、`write_file`、`edit_file`、`ls`、`glob`、`grep` 等操作。
- Agent 可以直接读写文件，把文件内容作为上下文处理。

###### 2.3 Shell 执行能力
- 通过 `execute` 运行命令，并支持沙箱（sandboxing）。
- 这让 Agent 能执行终端任务，而不只是文本推理。

###### 2.4 子 Agent 机制（Sub-agents）
- 提供 `task`，支持把工作委派给子代理，并使用隔离的上下文窗口。
- 适合多步骤、跨主题的大型任务，避免上下文互相干扰。

###### 2.5 智能默认配置
- 内置 prompts，专门教模型如何更有效地使用这些工具。
- 还带有上下文管理机制，例如：
  - 对长对话自动摘要
  - 大输出结果自动保存到文件

**关键点：**  
Deep Agents 不只是“能调用工具”，而是把规划、文件、命令执行、上下文压缩、任务分工打包成了一套完整工作流。

## 产品-产品技术PMF（1）

### 2026-03-19 10:58:41

以下是对 `langchain-ai/deepagents` 的精炼分析报告，聚焦产品定位、技术架构、PMF 与落地机会。

**结论先行**
- `deepagents` 本质上不是“又一个 Agent SDK”，而是一个“可立即运行的 Agent Harness（代理操作底座）”。
- 它抓住了当前 Agent 开发的核心痛点：不是模型能力不够，而是工程化能力不足，尤其是任务规划、上下文管理、文件/命令执行、子代理协作、沙箱边界与可观测性。
- 从 PMF 角度看，它对“开发者做复杂 Agent 原型与内部工具”已经具备较强产品市场契合；但对“企业级生产落地”仍有明显短板，尤其是安全治理、权限体系、审计、稳定性评估与成本控制。
- 最适合的切入场景不是通用聊天，而是“高操作性、高上下文复杂度”的任务型 Agent：代码研究、自动化运维、文档生成、数据处理、研发 Copilot、工作流编排助手。
- 如果要商业化，最佳路径不是卖“框架本身”，而是围绕其构建：托管执行环境、权限与合规层、团队协作、评测系统、部署与监控平台。

**一、产品定位分析**
- `deepagents` 的产品定位非常清晰：给开发者一个“开箱即用、但可深度定制”的 Agent 执行框架，而不是只提供底层 primitives。
- 它的核心价值主张是：开发者无需从零拼 prompt、tool calling、memory、planner、sub-agent orchestration，即可快速获得一个能工作的复杂代理。
- 相比 LangChain/LangGraph 传统形态，它更像“Opinionated Runtime + Default Agent Behavior”，降低了首次成功门槛。
- 相比纯 SDK，它更偏“半成品产品能力”；相比完整应用，它又保留足够 extensibility，适合二次开发。
- 从命名和叙述上，“Deep Agents” 强化的是复杂任务处理能力，而非单轮问答或轻量自动化。

**二、它解决了什么真实痛点**
- Agent 开发最大问题不在“能不能调到模型”，而在“如何让模型稳定地完成多步骤任务”。
- 典型痛点包括：
- 任务拆解缺失：模型不会稳定规划，容易跳步、漏步、重复做事。
- 工具链拼装复杂：文件系统、shell、搜索、记忆、审批等能力接入成本高。
- 长上下文退化：任务一长就丢信息、跑偏、成本飙升。
- 多任务协作困难：复杂工作需要子任务隔离，否则上下文污染严重。
- 可落地性不足：很多 Agent demo 能聊，但不能真正做事。
- `deepagents` 针对这些问题直接给出“规划、文件、执行、子代理、自动摘要、上下文管理”的组合，是非常对症的产品设计。

**三、核心产品能力拆解**
- `Planning`：通过 `write_todos` 显式任务拆解与进度跟踪，这是复杂任务完成率提升的关键设计，不只是 UX 点缀，而是代理稳定性的基础设施。
- `Filesystem`：提供 `read_file`、`write_file`、`edit_file`、`ls`、`glob`、`grep`，意味着 Agent 能在“本地知识与产物空间”中工作，这比纯向量检索更贴近真实生产任务。
- `Shell execute`：把 Agent 从“只会说”提升到“能执行”，是实用价值跃迁的核心。
- `Sub-agents`：通过 `task` 做上下文隔离，是非常重要的工程设计，能缓解复杂任务中的 token 污染与推理混乱。
- `Context management`：自动摘要、超长输出落盘，本质是在做成本与可持续执行优化。
- `LangGraph Native`：返回 compiled graph，说明它并非封闭黑盒，而是与 LangGraph 生态深度对齐，方便接入 checkpoint、streaming、studio、human-in-the-loop。

**四、产品设计亮点**
- 最大亮点是“默认可用”。这点对开发者产品极其重要，因为 Agent 领域最大的流失点是：装好了，但跑不起来。
- 它不是强迫用户理解复杂抽象后才能开始，而是先给 working agent，再允许逐步替换模型、工具、prompt、子代理配置。
- 这是一种典型的好产品策略：先成功，后理解；先结果，后抽象。
- 对 LangChain 生态来说，这也补足了过去“能力很多、集成复杂、最佳实践分散”的问题，把经验产品化了。

**五、技术架构判断**
从公开描述看，`deepagents` 的技术架构可概括为：

- 底层运行时：基于 LangGraph，负责状态流转、节点编排、持久化、checkpoint、streaming。
- Agent Harness 层：封装一套 opinionated agent loop，包括 planner、tool invocation、context summarization、sub-agent dispatch。
- Tooling 层：文件系统、shell、MCP、外部搜索、HITL 等能力接入。
- Model abstraction 层：兼容多模型提供商，依赖 tool calling 能力。
- CLI / Runtime layer：提供更接近真实工作环境的交互接口与执行沙箱。

这套架构说明它不是单点工具，而是“面向执行的 agent OS 雏形”。

**六、技术优势**
- 架构上站在 LangGraph 之上，天然具备生产级 runtime 的潜力，而不是从零造一个 agent loop。
- 支持 provider agnostic，降低模型供应商绑定风险。
- 子代理 + 自动摘要的组合，实际上是当前复杂 Agent 体系里非常有效的上下文治理策略。
- 文件系统和 shell 能力使它贴近真实任务流，这种“操作型代理”相比“聊天型代理”更有商业价值。
- MCP 支持意味着未来工具生态扩展性不错，有望接入更多企业系统和 SaaS。

**七、技术风险与短板**
- 最大技术风险不是“功能够不够”，而是“可信执行边界”。项目明确采用 `trust the LLM`，这对开发者友好，但对企业极具风险。
- 一旦开放 shell、文件系统、网络、外部工具，权限控制如果只靠 sandbox，而非细粒度 policy，会限制其进入企业核心流程。
- 多代理与工具调用带来显著的成本膨胀，尤其在长任务、递归 delegations、频繁总结时。
- 默认 prompt 与规划策略虽有通用性，但在垂直场景中容易出现“看似聪明、实则不稳定”的行为漂移。
- 评测体系仍会是瓶颈。复杂 Agent 不是传统单测思路，需要任务成功率、步骤质量、成本、时延、回滚率、人工介入率等多维评估。
- 真正生产落地还需要补足：权限分级、审计日志、工具白名单、执行回放、故障恢复、幂等性设计、资源隔离。

**八、PMF 分析**
如果从 PMF 角度拆成“用户—场景—价值—替代品—付费意愿”：

**1. 目标用户**
- AI 应用开发者
- 内部工具工程师
- 平台工程/DevTools 团队
- 自动化工作流搭建者
- 希望快速验证 agent product 的创业团队

**2. 高频场景**
- 代码库研究、重构建议、自动文档
- 自动化脚本生成与执行
- 本地/远程文件处理
- 运维排障与日志分析
- 多步骤研究任务与报告生成
- 企业内部知识与流程助手

**3. 核心价值**
- 显著减少 Agent 工程搭建成本
- 提高复杂任务成功率
- 把 demo 快速推进到 usable prototype
- 提供从实验到产品化之间的中间层

**4. 替代方案**
- 直接用 LangChain/LangGraph 自己搭
- OpenAI Agents SDK / Assistants 类方案
- AutoGen / CrewAI / Claude Code 类形态
- 内部自研 agent runtime

**5. PMF 判断**
- 对开发者工具市场：PMF 较强，尤其是想快速获得 complex-agent baseline 的团队。
- 对大众 C 端：PMF 弱，因为最终用户并不关心 harness，关心的是具体垂直场景结果。
- 对大企业生产环境：PMF 中等偏潜力型，需要额外产品层加固后才成立。

**九、竞品视角**
如果和常见路线比较：

- 对比 LangChain 原生：`deepagents` 更“产品化”、更快起步。
- 对比 LangGraph 原生：`deepagents` 更像最佳实践封装，降低学习门槛。
- 对比 Claude Code 类产品：它不是闭环终端产品，而是可嵌入、可定制的开放底座。
- 对比 CrewAI/AutoGen：它更强调工程可执行性和 LangGraph runtime，而不是只强调 multi-agent narrative。
- 对比 OpenAI 官方 Agents 能力：其开放性与生态兼容性更强，但官方方案往往在平台集成与托管体验上更顺滑。

结论上，`deepagents` 的差异化不在“我也有 agent”，而在“我把复杂 agent 的关键工程模块默认组合好了”。

**十、商业化机会判断**
开源本体很难直接形成高 ARPU，但围绕它可以长出强商业模式：

**最有价值的商业化方向**
- 托管 Agent Runtime：云端执行、任务队列、资源隔离、可观测性、回放、审计。
- 企业安全层：RBAC、审批流、操作白名单、Secret 管理、沙箱策略、合规审计。
- AgentOps 平台：评测、成本追踪、行为分析、错误定位、prompt/tool versioning。
- Vertical solutions：基于 `deepagents` 快速封装为研发助手、运维助手、数据分析助手、合规审查助手。
- Team collaboration：多用户共享 agent workspace、任务分派、审批与结果复核。

**不建议的商业化方向**
- 单独卖“Agent SDK”订阅，价值感知弱，容易被开源替代。
- 单纯卖 prompt 模板或 examples，壁垒太低。
- 泛化的“企业 AI 助手”叙事，竞争极其拥挤。

**十一、落地场景优先级**
如果我是产品负责人，会按以下顺序推进：

**P1：研发与技术团队**
- 代码库理解与问答
- 自动生成/修改文档
- 调试辅助与脚本执行
- PR 分析与变更建议

原因：场景结构化、回报高、用户容忍度高、对文件和 shell 能力需求强。

**P2：运维与数据处理**
- 日志排查
- 配置核验
- 批量文件处理
- ETL 辅助脚本生成

原因：任务步骤清晰，Agent 价值容易量化。

**P3：知识工作自动化**
- 研究任务拆解
- 报告生成
- 多源资料整理
- 工作流助手

原因：市场更大，但结果稳定性要求更高，主观评估更多。

**十二、如果做成一个创业项目，建议的产品路线**
**阶段 1：做“开发者可立即获得价值”的单点产品**
- 定位为“能操作文件与命令的工程助手”
- 聚焦本地代码库、文档与脚本任务
- 强调 10 分钟内跑起来，30 分钟内解决一个真实任务

**阶段 2：做团队能力**
- 加入任务历史、工作区共享、执行审批、结果回放
- 接入 GitHub、Jira、Slack、Notion、云资源平台

**阶段 3：做企业级控制面**
- 权限策略中心
- 执行审计
- 成本中心
- 模型与工具治理
- SLA 与高可用调度

这条路线比一开始做“大而全 Agent 平台”更容易找到 PMF。

**十三、产品改进建议**
基于当前描述，我认为最该补的不是更多工具，而是以下能力：

- 安全策略层：不是只有 sandbox，而是任务级、工具级、参数级权限控制。
- 审计与可解释性：每一步为什么做、用了什么上下文、执行了什么命令、产出了什么结果。
- 评测框架：复杂任务回归测试、任务成功率基线、成本与时间指标。
- 模板化场景包：研发助手、运维助手、文档助手等现成 recipe。
- 失败恢复机制：子任务中断后的重试、回滚、人工接管。
- 成本控制策略：预算上限、模型路由、递归深度限制、摘要频率自适应。

**十四、关键风险判断**
- 如果继续强调“trust the LLM”，会限制其在高价值企业场景中的采用速度。
- 如果缺少强评测与观测，开发者会很快从“哇，很强”进入“为什么这次又失败了”的失望周期。
- 如果没有明确垂直场景包装，它容易停留在技术圈传播，而难以放大到业务侧。
- 如果生态优势没转化成“更快交付结果”，会被更强品牌的闭源产品吸走用户。

**十五、最终判断**
- `deepagents` 是一个方向正确、产品感较强的 Agent 基础设施项目。
- 它抓住了 Agent 从“会聊天”走向“会做事”的关键跃迁点。
- 当前最强价值在开发者与技术团队，不在普通终端用户。
- 它的开源底座价值已经成立，但若想进一步放大商业价值，必须补企业级控制、评测治理与垂直场景包装。
- 从产品潜力看，它更像“Agent 时代的应用执行底座”，而不是最终形态的应用本身。

**一句话总结**
`deepagents` 的真正价值，不是让你“拥有一个 Agent”，而是让你“拥有一个能在真实工作环境里持续执行复杂任务的 Agent 基座”；它已经接近 PMF，但商业闭环还需要靠安全、治理和垂直化产品来完成。

## 产品-最佳实践（1）

### 2026-03-19 11:08:10

下面我用一个“代码仓库研究并生成技术调研报告”的具体实例，说明 `deepagents` 这类 agent harness 的最佳实践。

**实例**

假设你要做一个内部研发助手，目标是：

- 读取一个 Python 项目代码库
- 分析项目结构、依赖、核心模块
- 生成一份 `report.md`
- 必要时调用 shell 跑只读命令辅助分析
- 把“检索代码”“分析依赖”“撰写报告”拆给不同子代理

这是 `deepagents` 很适合的场景，因为它原生支持：

- planning
- filesystem
- shell
- sub-agents
- 长上下文管理

一个最小化的思路大致像这样：

```python
from deepagents import create_deep_agent
from langchain.chat_models import init_chat_model

agent = create_deep_agent(
    model=init_chat_model("openai:gpt-4o"),
    system_prompt=(
        "你是一个代码研究助手。"
        "先规划，再阅读文件，再执行必要命令，最后输出结构化报告。"
        "优先使用只读操作；不确定时明确标注假设。"
    ),
)

result = agent.invoke({
    "messages": [
        {
            "role": "user",
            "content": (
                "分析当前仓库的架构、主要依赖和运行方式，"
                "并生成 report.md。"
            )
        }
    ]
})
```

**在这个实例上的最佳实践**

- 先把 agent 定义成“流程型助手”，不要一上来就让它“自由发挥”；`deepagents` 强在 harness，不是靠一条万能 prompt 硬撑
- 把安全边界下沉到工具层；仓库作者明确提到“trust the LLM”，所以不要指望模型自觉克制，而要限制 shell、文件写入目录、可用命令
- 让规划成为默认动作；对“分析仓库并写报告”这种复合任务，先 `write_todos` 再执行，能显著降低漏项和上下文混乱
- 把子任务隔离给 sub-agents；例如“依赖分析”“核心模块梳理”“README/配置提取”分别委托，避免一个上下文窗口塞满所有细节
- 输出物落文件，不要只留在对话里；长结果写入 `report.md`、中间证据写入 `notes/`，这样可审计、可复用，也更符合 deepagents 的文件系统设计

**推荐的任务拆分**

针对这个实例，比较稳妥的 todo 结构是：

1. 识别仓库类型与入口文件
2. 读取 `README`、`pyproject.toml`、`requirements.txt`、核心目录
3. 用 shell 执行只读命令补充信息
4. 汇总依赖、模块职责、运行方式
5. 生成 `report.md`
6. 自检报告是否有证据支撑

这里的关键最佳实践是：每一步都要有“可验证产物”。

比如：

- 仓库类型：来自 `pyproject.toml`
- 入口文件：来自 `README` 或 CLI 配置
- 依赖：来自 lockfile / requirements
- 模块职责：来自目录结构和源码注释
- 运行方式：来自文档和脚本配置

这样 agent 不是“猜”，而是在“归纳证据”。

**Prompt 设计最佳实践**

在这个例子里，system prompt 最好不要写成空泛的“你是一个强大的 AI”。更好的方式是约束工作流和证据标准。

例如：

```text
你是一个代码仓库分析助手。
工作要求：
1. 先制定计划，再执行。
2. 优先读取 README、依赖文件、配置文件和核心源码。
3. shell 仅用于只读分析，不做安装、不改环境。
4. 所有结论都尽量给出依据文件。
5. 输出时区分“确定信息”和“推断信息”。
6. 最终将报告写入 report.md。
```

这类 prompt 的最佳实践有两个重点：

- 约束“过程”，不是只约束“身份”
- 约束“证据质量”，不是只约束“输出格式”

**工具使用最佳实践**

在这个实例中，推荐这样用工具：

- `ls/glob`：先摸清结构，不急着深入源码
- `read_file`：优先读 `README`、配置、入口文件、少量关键模块
- `grep`：定位框架入口、主函数、依赖引用
- `execute`：仅跑只读命令，如 `python --version`、`rg`、`pytest --collect-only` 这类低风险命令
- `write_file/edit_file`：只在产出阶段写 `report.md`，不要过早频繁写文件

一个很重要的最佳实践是：**先缩小搜索范围，再读文件内容**。

坏做法：

- 上来就通读大量源码
- 让 agent 在巨量文件里无差别漫游

好做法：

- 先找 `README`、依赖文件、配置文件、入口模块
- 再沿着 import 链和目录层级逐步下钻

这会让上下文更稳定，也更符合 deepagents 的自动上下文管理模式。

**sub-agents 的最佳实践**

这个场景下，sub-agents 最适合做“信息并行收集”，不适合做“最终结论并行投票”。

推荐拆法：

- 子代理 A：分析项目结构与模块职责
- 子代理 B：分析依赖与外部服务
- 子代理 C：分析运行/部署方式
- 主代理：合并三者结果，去重、校验、写报告

这样拆的原因是：

- 每个子代理上下文隔离，不容易互相污染
- 主代理保留全局叙事能力
- 结论统一从主代理输出，避免风格和标准不一致

最佳实践不是“能拆就拆”，而是：**只有当子任务天然独立时才拆**。  
如果任务本来就很短，比如只读一个 `README` 并总结，那用 sub-agents 反而会增加调度成本。

**shell 的最佳实践**

因为项目明确强调安全边界要靠工具层，所以这个实例里 shell 最好遵循“最小能力原则”：

- 只允许白名单命令，如 `rg`、`find`、`cat`、`python -c`、`pytest --collect-only`
- 禁止联网、安装、删除、写系统目录
- 对执行超时、输出长度做限制
- 把长输出重定向到文件，再让 agent 按需读取

例如，允许 agent 执行：

```bash
rg "FastAPI|Typer|click|argparse" .
rg "^def main|if __name__ == '__main__'" .
```

不建议默认允许：

```bash
pip install ...
curl ...
rm -rf ...
docker build ...
```

最佳实践不是“给 shell 就完了”，而是让 shell 成为“受限观察工具”，不是“无限制执行器”。

**文件系统最佳实践**

在这个例子里，建议约定一个清晰的工作目录，例如：

- `notes/structure.md`
- `notes/deps.md`
- `notes/runtime.md`
- `report.md`

这样做的好处：

- 中间分析结果可追踪
- 主代理可以复用子代理产物
- 长任务中断后更容易恢复
- 最终结果的证据链更完整

一个常见坏做法是：所有中间结论都留在聊天历史里。  
而 `deepagents` 的优势之一就是文件系统后端，所以最佳实践是把中间产物显式落盘。

**上下文管理最佳实践**

由于 deepagents 支持自动摘要和长上下文管理，这个实例里仍然要遵守一个原则：

- 不要把“原始大段内容”反复塞回对话
- 要把“大量原文”压缩成“证据摘要 + 文件引用”

例如，不要这样：

- 把 500 行 `pyproject.toml` 和多个源码文件全文反复贴进消息

更好的做法：

- 提取关键字段
- 记录“发现于哪个文件”
- 对长输出写文件，再引用文件路径

最佳实践是：**上下文里保留决策所需信息，不保留一切信息**。

**产出报告的最佳实践**

在这个实例中，`report.md` 建议采用固定结构：

```md
# 项目调研报告

## 1. 项目概览
## 2. 技术栈与依赖
## 3. 核心模块
## 4. 运行方式
## 5. 风险与问题
## 6. 结论

## 附：证据来源
- README.md
- pyproject.toml
- src/app/main.py
...
```

关键最佳实践：

- 结论和证据分开
- 明确“已确认”与“推断”
- 保留文件级引用
- 风险单独列出，不要埋在正文里

这样输出更适合真实工程环境，而不是只生成“看起来很聪明”的总结。

**一个更完整的工程级配置思路**

如果你要把这个实例做成可长期使用的内部助手，我建议遵循这套配置原则：

- 模型层：选稳定的 tool-calling 模型，不要优先追求最强文案能力
- prompt 层：规定先规划、再证据收集、再写结论
- 工具层：shell 只读白名单，文件写入限定在工作目录
- agent 层：使用 sub-agents 做并行收集，主代理做统一裁决
- 输出层：要求文件化产物和证据索引
- 运维层：保存执行日志、工具调用记录和最终文件版本

这才是 `deepagents` 的真正最佳实践：  
**把它当作“可治理的 agent 执行框架”，而不是“会自己变聪明的黑盒”。**

**一句话总结**

如果用 `deepagents` 做“分析代码仓库并生成报告”这个实例，最佳实践就是：

- 用 planning 控制流程
- 用 filesystem 固化证据
- 用 shell 做受限观察
- 用 sub-agents 并行收集
- 用主代理统一判断
- 用工具边界保障安全
