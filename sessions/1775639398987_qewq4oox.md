##### What I Built: Data Agent

我创建的用例实现了一个本地的、基于终端的数据分析和洞察发现聊天机器人。这是每个企业（无论大小）最常见的用例，因此，这似乎是一个完美的待解决问题。

##### How I Built: Deep Agents SDK

1. **Orchestration**  
   这个想法很简单——我设计的编排机制类似于组织的典型结构，即领导者对业务有更高层次的理解，而对技术细节了解较少，他们通常擅长委派工作。在这里，主编排代理对自身目的有更高层次的理解，并知道如何将工作委派给子代理。子代理就像领域分析师，它们对每个品牌都有详细的理解，并且能够在需要时调用合适的技能。
   这种结构的目标是避免上下文膨胀，同时在长时间对话中保持效率。理论上，同样的功能可以用不同的配置实现，即不使用子代理，并且在某种程度上仍然可能运行良好。
2. **内置工具（开箱即用）**  
   Deep Agents SDK 随附实用工具，这些工具能让规划和上下文管理在实际工作流程中使用。
   - 文件操作：列出、写入、编辑、更新、glob、grep
   - 任务工具：将工作委派给子代理
   - 通用子代理：处理多步骤或歧义查询
   这些工具使虚拟文件系统中的上下文卸载更安全且更可预测。
3. **Customizations that matter**  
   SDK 使添加特定领域的逻辑变得简单，而无需与核心架构对抗。
   1. **Subagents**  
      我为每个品牌创建了自定义代理，这样品牌细微差别就会保留在品牌分析子代理中，不会渗透到其他分析中。
   2. **Skills**  
      技能支持渐进式展示：仅在需要时加载特定于数据集的上下文。对于每个数据集，我创建了一个自定义技能，该技能包含：
      1. Metadata definitions
      2. Granularity and structure
      3. Business rules and logic
      4. Analysis patterns
   这一点很重要，当你使用通用 LLM 默认情况下无法理解的非通用数据集时。它还能将上下文窗口控制在合理范围内。
4. **Tools**  
   你可以在编排器级别或子代理内部添加自定义工具。针对该用例，我添加了 run\_sql、discover\_schema 和 export\_sql。
   在企业环境中，您可以用托管的 MCP 服务器（例如 Snowflake Cortex、Databricks Genie）替换或增强这些工具，这些服务器提供查询工具和目录工具。如果贵组织已经拥有强大的数据目录，那么只要您的工具可以直接查询该目录，许多特定于数据集的技能定义就会变得可选。

你可以在此处访问完整的仓库： [https://github.com/voralabs/pharma\_data\_agent.git](https://github.com/voralabs/pharma_data_agent.git)

#### 用 Deep Agent SDK 构建数据代理：核心内容总结

##### 一、文章讲了什么

这篇文章的核心观点是：**只要工具能力设计得对，多智能体应用并没有想象中那么难做**。作者用 Deep Agent SDK 搭建了一个本地终端里的 “数据分析聊天机器人”，用来回答业务数据问题、发现洞察，并展示了多智能体架构在企业数据场景中的实际价值。

##### 二、作者做了什么产品

作者构建的是一个**面向企业数据分析的智能体系统**，场景类似医药行业的营销和销售分析。  
它可以围绕不同品牌的数据进行理解、分析和回答问题，本质上就是一个能够 “对话式做数据分析” 的代理。

这个选题很典型，因为**数据分析与洞察发现几乎是所有企业都会遇到的高频需求**，所以很适合用来验证智能体框架的实际能力。

##### 三、系统是怎么设计的

###### 1. 核心架构：主代理 + 子代理

作者采用了一种很像公司组织结构的设计：

- **主编排代理**：负责理解整体任务、拆解问题、分派工作
- **品牌子代理**：分别负责具体品牌的数据和分析逻辑

这种设计的好处是：  
**把复杂任务拆开处理，减少上下文膨胀，让长对话依然保持效率。**

###### 2. 为什么要用子代理

如果所有事情都交给一个大代理，也可能能跑，但会有两个问题：

- 上下文越来越大，效率下降
- 不同品牌、不同数据集的细节容易互相污染

所以子代理的价值不只是 “分工”，更是**控制复杂度、隔离知识、提升稳定性**。

##### 四、Deep Agent SDK 为什么适合做这件事

###### 1. 自带工具足够实用

Deep Agent SDK 内置了一些很关键的能力，比如：

- 文件操作：列出、编辑、更新、搜索文件
- 任务分派：把工作委托给子代理
- 通用子代理：处理多步骤或模糊问题

这些工具的意义在于：  
**让代理不仅能 “想”，还能更稳定地 “做事” 和 “管理上下文”。**

###### 2. 支持强定制，适合企业场景

作者特别强调，SDK 的价值不只是开箱即用，更在于**容易叠加领域知识和企业规则**，主要体现在三层：

- **Subagents**：按品牌拆分代理，保留业务细节
- **Skills**：按数据集定义元数据、规则、分析模式
- **Tools**：接入 SQL 查询、表结构发现、SQL 导出等能力

这说明它不是一个 “泛聊天” 工具，而是更适合做**面向业务流程的垂直智能体系统**。

##### 五、文章最重要的启发

###### 1. 多智能体的关键不是 “多”，而是 “分工合理”

作者并不是为了炫技而使用多代理，而是为了更贴近真实组织的协作方式。  
本质上，**好的多智能体设计是任务分层与知识分层**。

###### 2. 企业数据场景里，领域定义比模型本身更重要

对于非通用数据集，LLM 默认并不真正理解业务含义。  
因此，必须通过技能、元数据、业务规则等方式补足上下文。也就是说：

**真正决定效果的，不只是模型能力，而是你如何组织数据语义和业务知识。**

###### 3. SDK 的价值，在于降低 “工程化落地” 门槛

文章想传达的并不是 “模型有多强”，而是：  
**当框架把编排、上下文管理、工具调用这些基础设施做好后，开发者可以更专注于业务逻辑本身。**

##### 六、接下来会补什么能力

目前这个项目还是一个初版，缺少完整产品化能力，后续规划包括：

- **用户界面**：如 Streamlit
- **可视化**：如 Plotly
- **数据库集成**：如 Databricks、Snowflake、BigQuery
- **结果表达**：如幻灯片、视频化讲述
- **评估体系**：如 LangSmith 追踪与评测

这也说明，当前成果更像一个**可运行的智能体原型**，距离完整企业级产品还有一段工程化路径。

##### 七、一句话总结

**这篇文章的核心价值在于证明：在企业数据分析场景中，只要编排机制、子代理、技能和工具设计得当，多智能体应用可以从 “概念” 变成真正可落地的产品原型。**

## 趣读意义（1）

### 2026-04-08 09:16:47

#### 一句话看懂

这篇文章的核心意思就一句：**做数据智能体，难的不是 “让模型会说话”，而是 “让它像一个组织一样会分工、会控上下文、会调工具”**。Deep Agent SDK 的价值，就在于把这套 “像团队协作” 的能力，做成了可落地的工程骨架。

#### 通俗总结

- 作者做了一个**本地终端版数据分析 Agent**，场景很典型：企业里问数据、找洞察、做分析。
- 架构不是 “一个万能大脑”，而是**一个总指挥 + 多个品牌专家子代理**。
- 总代理负责理解业务问题、拆任务、派活；子代理负责吃透各自领域细节，再按需调用 SQL、schema 发现、导出等工具。
- 这样设计的好处很现实：**减少上下文塞爆、提升长对话效率、降低分析串味**。
- SDK 自带文件操作、任务委派、通用子代理这些能力，所以开发者不用从零手搓一套 agent 操作系统。
- 真正关键的定制点有三类：**子代理、技能、工具**。前两者负责 “懂业务”，后者负责 “真干活”。
- 作者最后也很坦诚：现在还只是个 “能跑的骨架”，UI、可视化、数仓打通、故事化输出，都还在路线图里。

#### 生动一点理解

你可以把它想成一间小型咨询公司：

- **总代理**像项目经理，懂问题、会分工，但不亲自写 SQL。
- **品牌子代理**像行业顾问，知道 Dexavir 和 Nabinix 各自的业务门道，不会互相污染认知。
- **技能**像团队手册，写清楚数据口径、业务规则、分析套路，避免 LLM 一本正经地 “自由发挥”。
- **工具**像 BI 权限和数据库接口，没它们，顾问再聪明也只能空谈。

所以这篇文章不是在说 “Agent 会魔法”，而是在说：**Agent 真要进企业，必须先学会像组织一样工作。**

#### 对你的参考意义

- **产品视角**：这不是一个 “聊天机器人” 项目，而是一个**数据协作系统**。产品定义重点应从 “回答得像不像人” 切到 “分工是否稳定、上下文是否可控、结果是否可追溯”。
- **架构视角**：作者证明了一件事 ——**多智能体未必要追求炫技，最朴素的组织映射反而最实用**。总控 + 专家分工，是企业产品里非常自然的设计范式。
- **商业视角**：真正有价值的护城河，不在模型本身，而在**领域技能封装 + 企业工具接入 + 业务规则沉淀**。模型会越来越便宜，流程资产会越来越值钱。
- **落地视角**：文章反复强调一个现实：**通用模型不懂你的脏数据、口径和业务黑话**。所以 “技能层” 其实就是把企业 know-how 编译成 agent 可调用的结构化资产。
- **路线图启发**：作者后面想补 UI、可视化、数仓、故事化输出，这很像一个标准进化路径：  
  **能回答 → 能分析 → 能展示 → 能说服人**。前两步是工具，后两步才是产品价值放大的地方。
- **一个很值得记住的判断**：未来数据 Agent 产品，拼的不是 “谁会写 SQL”，而是**谁能把分析流程组织化、把业务语义产品化、把洞察结果表达化**。

#### 最值得你记住的 3 个点

- **Agent 不是单体模型，而是组织设计。**
- **上下文管理不是技术细节，而是产品成败。**
- **企业数据 Agent 的核心资产，是业务规则和工具连接，不是聊天界面。**
