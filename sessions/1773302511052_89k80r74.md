- 优先为子代理设计独立上下文窗口与摘要回传机制，验证是否能显著降低主代理上下文膨胀。

### Three sub-agent patterns you need for your agentic system

Every agentic system that actually ships ends up needing three delegation patterns: one that blocks, one that fires and forgets, and one that runs later. The question isn't whether you need sub-agents — it's how you wire them up.

Sub-agents unlock a few key things that matter in agentic systems: context compression, parallel execution, and async delegation. A parent agent that can hand off work to isolated sub-agents stays lean across long conversations, runs independent tasks simultaneously, and delegates background work without blocking the user.

The trends of sub-agents has shifted from specialized to generic, but regardless of your chosen approach, each system (

[or harness if you will](https://x.com/djfarrelly/status/2028556984396452250)), needs to have three core patterns for working with sub-agents.

As I developed

[a general purpose agent](https://github.com/inngest/utah) that runs anywhere, I naturally reached for sub-agents to solve some key problems, but ran into some limitations with the standard pattern for agents: the synchronous sub-agent.

When orchestrating sub-agents, there are three key patterns to get in place. Here's what they are, when to use them, and ideas on how to implement them.

#### What a Sub-Agent Is (and Why It Exists)

A sub-agent is a separate LLM execution context spawned by a parent agent to handle a scoped task. The parent describes the task, provides tools, and gets back a result. The sub-agent should run in its own context window so it doesn't pollute the parent's.

As I covered in

[my X article last week](https://x.com/djfarrelly/status/2028556984396452250), the primary purpose is context compression. The Cursor team also described this in their recent

[Latent Space interview](https://www.latent.space/p/cursor-2)

. Sub-agents exist so the parent never has to absorb the full trajectory of a delegated task. The sub-agent might read 8 files and make 15 tool calls. The parent sees a 750-token summary.

During my own testing with the

[Utah project](https://github.com/inngest/utah), sub-agents resulted in 90%+ reduction in tokens added to the parent agent's context.

That's the real ROI. Not parallelism, but context management. The parent stays lean and can handle more tasks in a single conversation without hitting context limits or degrading response quality.

#### The role of a sub-agent

Sub-agents can cover a variety of use cases in any agentic system. Sometimes the parent agent just needs to run a sub-agent like it uses a tool, to execute a task and return the result back. Other times, it has a concrete task that can be fanned out and finish later, clearing the main agent loop. And lastly, sometimes the parent agent needs to perform a task at a later time like at the end of the day or week. These are the three core patterns for sub-agents:

- Sync - "Do this and wait"
- Async - "Go do this, report back"
- Scheduled - "Do this later"

![Image](https://pbs.twimg.com/media/HDKI4qqXEAAWeWk?format=png&name=large)

The three sub-agent patterns

Every agentic system needs all three and they all have their own purpose and considerations. Let's dive into each of them.

#### Pattern 1: Sync — "Do this and wait"

The parent spawns a sub-agent and blocks until the result comes back. The sub-agent runs, does its work, and returns a summary as a tool result.

When to use it: The parent needs the answer to continue. Data lookups, analysis, code generation that feeds into the next step, anything where the response shapes what happens next.

```typescript
const subResult = await step.invoke("sub-agent", {
  function: subAgent,
  data: {
    task: "Read the following 8 files and create a summary of the sub-agent architecture with code examples",
    subSessionKey: `sub-${sessionKey}-${Date.now()}`,
  },
});
toolResult = { result: subResult?.response || "(No response)" };
```

Within

[our system](https://www.inngest.com/docs/guides/invoking-functions-directly), step.invoke() is function-to-function RPC with durability. The parent checkpoints before invoking, so it won't re-invoke on retry. If the sub-agent crashes, Inngest retries it. The parent just waits.

The tradeoff: The result enters the parent's context window. But it's a summary, not the full trajectory: that 90%+ reduction means the parent can delegate many times before context becomes an issue.

Think of sync sub-agents as function calls. You call, you wait, you get a return value.

#### Pattern 2: Async — "Go do this, report back"

The parent fires off a sub-agent and continues the conversation immediately. The sub-agent runs independently and replies directly to the user when it's finished.

When to use it: Long-running research, report generation, drafting, analysis — anything with side effects that don't need a return value. This should be your default.

```typescript
await step.sendEvent("spawn-async-sub-agent", {
  name: "agent.subagent.spawn",
  data: {
    task: "Research competitor pricing and compile a report...",
    async: true,
    channel,
    destination,
    channelMeta,
  },
});
toolResult = {
  result: "Async sub-agent spawned. It will reply directly to the user.",
};
```

The parent doesn't wait. The sub-agent is a completely separate function run. When it finishes, it emits an event with the response and channel routing info — the reply gets delivered to the user through whatever channel originated the request.

The tradeoff: The parent can't incorporate the result. If you fire three async sub-agents, each runs in total isolation. That's a feature, it's zero coordination overhead, parallel execution for free, but it means the parent can't synthesize across them in the same turn.

The next iteration: The parent agent should still be able to query child agent output and context within your system using either the session or conversation ID or an ID returned from the scheduler (ex. an event ID in Inngest). In essence, this is a "handle" on the task that the agent can choose to check up on later.

Think of async sub-agents as colleagues. You hand off work, say "let me know when it's done," and move on. Multiple async sub-agents can run simultaneously with no coordination code.

#### Pattern 3: Scheduled — "Do this later"

The parent schedules a sub-agent to run at a specific future time. This is the one most people miss, and it's the most interesting.

When to use it: Follow-ups, reminders that should be smart, recurring checks, anything where "later" should mean "with fresh data at execution time."

```typescript
await step.sendEvent("spawn-scheduled-sub-agent", {
  name: "agent.subagent.spawn",
  data: {
    task: "Pull the deploy metrics from the last 24 hours and send a summary...",
    async: true,
    channel,
    destination,
    channelMeta,
  },
  ts: new Date("2026-03-10T14:00:00Z").getTime(),
});
```

Same sub-agent function. Same event. Just with a ts timestamp for delayed delivery.

What makes this different from cron: "Remind me to check the deploy metrics tomorrow at 9am" doesn't send a notification at 9am. It runs an agent at 9am that actually pulls live metrics and sends the analysis. "Send a follow-up email to this thread on Monday" runs a sub-agent Monday with full thread context, not a scheduled message composed on Friday.

Scheduled sub-agents are dynamic, context-aware, and run with the current state of the world at execution time. No new infrastructure beyond what async already provides — it's the same function, same handler, same delivery mechanism. The only difference is the ts field on the event.

The tradeoff: You can't easily cancel or modify a scheduled sub-agent after it's been queued. And the task description is frozen at scheduling time — it captures the parent's understanding of the task now, which may be stale by execution time.

The next iteration: Similarly to the async sub-agent approach, the parent agent can get a handle on the scheduled task and now has this in it's own context and memory. It can then query the system itself to know what is due to run, cancel it, and check it's status.

#### Decision Framework

- Need the result to continue? → Sync
- Independent task, no blocking needed? → Async
- Multiple independent tasks? → Async (parallel)
- Should happen at a specific future time? → Scheduled
- Not sure? → Default to async. It's cheaper and keeps the parent lean.

Don't choose for the model. Give it all three tools with clear descriptions. It picks correctly.

#### Our implementation

One function, three modes

In our implementation, we leverage one re-usable Inngest function that handles sync, async and scheduled. The difference is how it's triggered and where the result goes.

Here's the entire sub-agent that handles all three patterns:

```typescript
export const subAgent = inngest.createFunction(
  {
    id: "agent-sub-agent",
    retries: 1,
    triggers: [agentSubagentSpawn],
  },
  async ({ event, step }) => {
    const {
      task,
      subSessionKey,
      async: isAsync,
      channel,
      destination,
      channelMeta,
    } = event.data;

    const framedTask = isAsync
      ? `You are an async sub-agent. Your response goes directly to the
         user. Be thorough.\\n\\n${task}`
      : `You are a sub-agent. Your response goes back to the parent as
         a summary. Be concise.\\n\\n${task}`;

    const result = await createAgentLoop(framedTask, subSessionKey, {
      tools: SUB_AGENT_TOOLS,
      isSubAgent: true,
    })(step);

    if (isAsync && channel && destination) {
      await step.sendEvent("async-reply", {
        name: "agent.reply.ready",
        data: {
          response: result.response,
          channel,
          destination,
          channelMeta,
        },
      });
    }

    return result;
  },
);
```

The framing instruction is the key differentiator. Sync sub-agents are told to be concise (the parent synthesizes). Async sub-agents are told to be thorough (they're the final word to the user). Scheduled sub-agents are just async with a delayed trigger — no special handling needed.

Two tools, not one

```typescript
const delegateTaskTool: Tool = {
  name: "delegate_task",
  description: `Delegate a self-contained task to a sub-agent that runs
in an isolated context window. Use this when:
- The task requires many file reads/edits (4+ tool calls expected)
- The task is independent and can be described as a clear goal
- You want to keep your own context lean
The sub-agent has access to the same workspace and tools but its own
conversation. You'll receive a summary of what it accomplished.`,
  parameters: Type.Object({
    task: Type.String({
      description: "Clear, detailed description of what the sub-agent should do.",
    }),
  }),
};
```

Why two tools instead of one tool with a mode parameter? Models are better at tool selection (picking from a list) than parameter optimization (reading parameter descriptions and choosing correctly). Separate tools = cleaner logs, clearer traces, easier debugging.

Tool sets and depth control

```typescript
export const TOOLS: Tool[] = [
  ...piTools,
  rememberTool,
  webFetchTool,
  delegateTaskTool,
  delegateAsyncTaskTool
];

export const SUB_AGENT_TOOLS: Tool[] = [
  ...piTools,
  rememberTool,
  webFetchTool
];
```

Depth-1 delegation. Sub-agents get the same workspace tools but can't spawn sub-agents. No routing logic. No task classification. The model reads the tool description, decides when delegation makes sense, and writes a natural language task description.

The agent loop

Since the agent leverages our agent loop using Inngest steps, it's durable and if a step fails, it retries from where it left off rather than from the beginning of the loop. As these sub-agents are just tools, the result is just appended to the messages just like any tool call is.

[Check out the code here](https://github.com/inngest/utah/blob/main/src/agent-loop.ts)

Channel-agnostic routing

```plaintext
Message arrives (Telegram, Slack, email)
  → parent agent processes, decides to delegate async
    → spawn event carries { channel, destination, channelMeta }
      → sub-agent finishes, emits reply event with same routing info
        → send-reply function dispatches to correct channel handler
```

The sub-agent doesn't know about Telegram or Slack. Adding a new channel is a handler, not a sub-agent change. This is important as it means the three patterns work identically regardless of where the user's message came from.

#### The Primitives That Make This Work

There are a few primitives that enable these patterns within our Inngest-based system:

![Image](https://pbs.twimg.com/media/HDKJvqqbQAAy1DR?format=png&name=large)

```plaintext
User → Parent Agent (agentic loop)
         ├── [sync]  step.invoke() → Sub-Agent → result back to parent
         ├── [async] step.sendEvent() → Sub-Agent → reports to user directly
         └── [sched] step.sendEvent({ts}) → [delayed] → Sub-Agent → reports to user
```

Durability runs through the entire chain. No custom orchestration code. No state machines. No queue management. It's a while loop with step wrappers.

Failure handling falls out naturally. Sync failures: the sub-agent retries via Inngest, step.invoke() throws if retries are exhausted. Async failures: a global inngest/function.failed handler catches it, and the channel routing info lets it notify the user.

The benefit of this is that the orchestration layer can handle all of these parts, keeping you flexible to iterate on your harness or agentic system. Patterns, models and approaches move fast, so flexibility is really valuable to move fast.

#### Why Generic Beats Specialized

Once you have the three patterns, there's a tempting next step: build specialized agents for each domain. An email agent, a data agent, a coding agent, each with its own tools and prompts. Don't dive into this temptation right away.

Internally, we've built systems with specialized agents and a custom router between them. The routing layer became more complex and with the progress with models, this specialization has felt far less important and honestly a cumbersome layer to maintain in most setups.

Some things to keep in mind:

Tool overlap. With how good general purpose agents are with coding tools or patterns like tool search, tool discovery, skills, sometimes a whole library of many tools separated by agent may not be what you need.

The routing paradox. You need something to decide which specialist handles each request. Hard-coded routing can break on ambiguity. LLM-as-router adds latency and a new failure mode. If your routing LLM call is smart enough to pick the right agent, couldn't it just do the task itself? That looks just like a general purpose agent with a "task" delegated to it to me.

The "wrong agent" problem. When the router sends a task to the wrong specialist, the failure mode is uniquely bad. The wrong agent attempts the task with incomplete capabilities and might partially succeed in a subtly wrong way. The system trusts the response because it came from the designated specialist. These are weird failure cases to handle or plan for.

Eval surface explosion. With N agents you need N individual eval suites, 1 routing eval suite, O(N²) pairwise interaction tests, and end-to-end integration tests. A single generic agent needs one eval suite covering all capabilities. If you're doing something like this I'd actually love to chat or learn from what folks are doing - send me your own blog post or approaches.

I'm not unique in these opinions either. Anthropic's

["Building Effective Agents"](https://www.anthropic.com/engineering/building-effective-agents) paper touches this topic:

> "Consistently, the most successful implementations weren't using complex frameworks or specialized libraries. Instead, they were building with simple, composable patterns."

In the podcast I mentioned above (go listen to it), the Cursor team described using "a mostly generic task interface where the main agent can define what goes into the subagent." Sub-agents as context compression boundaries first, parallelism second. The model defines sub-agents at runtime, not the developer at build time.

It's kinda funny how software has seen similar patterns before in other ways. The explosion of microservices then the pull back of them towards modular monoliths. The overhead started to outweigh the benefits. Generic agents are similar.

When specialization does win

- Different model requirements. One task needs vision, another needs fast classification, route to different models.
- Security boundaries. Agent A accesses customer data, agent B only accesses public data.
- Regulatory requirements. Some domains require auditable, separate processing pipelines.
- Proven eval-driven evidence. Your evals show a specialized agent consistently outperforms generic on a specific task.

The key principle: specialization should be driven by measured necessity, not architectural aesthetics. Start generic. Specialize when it makes sense.

#### What we're exploring next

The approach that we're using today to build our systems is generic and works for all three modes: sync, async, and scheduled. These are some things that we'll be exploring next as these primitives:

- Self-iterating agents. With scheduled sub-agents, why couldn't the agents keep iterating on themselves and the systems. Cost and budgets will naturally come into consideration.
- Orchestration-awareness. Async and scheduled sub-agents return their event ID. With APIs and context, the any agent or sub-agent in the system could be aware of what's running, where, go fetch status, results. It becomes less of a loop + fan-out and more of a web.
- Callbacks and other patterns. The current reference example uses the channel as the callback mechanism when work is done, but what could a generic sub-agent system look like with different types of callbacks, e.g. update a Linear task, store a reference of the research or report in a database. Tools can be used for this, but callbacks provide some level of guarantee.

#### Wrapping up

These three sub-agent patterns all have their use cases and combine quite nicely in different types of agentic systems or harnesses. If you can model them out just as tools in your own system and leave the work to the orchestrater, you can quickly iterate on your product. Avoid the temptation of specialization, just start here and ship it.

## 结构化（1）

**主旨概括：**  
这篇文章认为：一个真正能落地的 Agent 系统，最终都需要**3 种子代理（sub-agent）委派模式**——**同步、异步、定时**。核心价值不只是 “并行处理”，更重要的是**压缩上下文、降低主代理负担**。

---

##### 1. 什么是子代理：本质是 “隔离上下文的任务分包”

- 子代理就是：**父代理把一个明确任务交给另一个独立的 LLM 执行上下文去做**，做完后返回结果。
- 关键作用是**上下文压缩**：  
  - 子代理可以自己去读很多文件、调用很多工具；  
  - 父代理不需要知道全过程，只接收一个简短总结。
- 文中举例：  
  - 子代理可能会**读取 8 个文件、调用 15 次工具**；  
  - 父代理最终只看到**约 750 token 的总结**。
- 作者在 Utah 项目测试中发现：  
  - 子代理让父代理上下文新增 token **减少了 90% 以上**。
- 结论：  
  - 子代理最大的 ROI 不是并行，而是**上下文管理**；  
  - 这样父代理在长对话里更 “轻”，不容易超出上下文限制，也更不容易掉质量。

---

##### 2. 三种核心模式：系统必须同时具备

文章把子代理工作方式分成 3 类：

- **Sync（同步）**：**“现在做，并等结果回来”**
- **Async（异步）**：**“你先去做，做好后告诉用户”**
- **Scheduled（定时）**：**“以后某个时间再做”**

作者强调：**不是要不要用子代理，而是你怎么把这 3 种模式接好。**

---

##### 3. 模式一：同步 Sync —— “做完再继续”

###### 适用场景
当父代理**必须先拿到结果，才能继续下一步**时使用，例如：

- 数据查询
- 分析任务
- 代码生成
- 任何会影响下一步决策的任务

###### 工作方式
- 父代理发起一个子代理；
- **阻塞等待**；
- 子代理完成后返回一个摘要结果；
- 父代理再继续。

###### 优点
- 适合强依赖链路；
- 虽然结果会进入父代理上下文，但进入的是**总结**，不是全部过程；
- 因为上下文压缩效果明显，所以依然划算。

###### 代价
- 父代理必须等待；
- 返回结果仍会占用父代理部分上下文。

###### 通俗例子
比如主代理在写技术方案前，先让子代理：  
**“读这 8 个文件，总结当前 sub-agent 架构并附代码示例。”**  
主代理必须先拿到这个总结，才能继续输出方案。

###### 作者类比
- Sync 就像**函数调用**：  
  **调用 → 等待 → 返回值**

---

##### 4. 模式二：异步 Async —— “先去做，做完直接回用户”

###### 适用场景
适合**耗时长、但不需要立刻回传给父代理**的任务，例如：

- 长时间调研
- 生成报告
- 起草文稿
- 独立分析任务

作者明确建议：**默认优先用 async**。

###### 工作方式
- 父代理发起子代理后，**立刻继续当前对话**；
- 子代理独立运行；
- 完成后**直接把结果发给用户**，而不是先回父代理。

###### 优点
- 不阻塞用户当前对话；
- 多个任务可以**天然并行**；
- 父代理保持轻量。

###### 代价
- 父代理在当前轮次里**不能综合这些异步结果**；
- 如果同时发了 3 个异步子代理，它们彼此独立，零协调。

###### 作者建议的下一步优化
- 给父代理一个 “任务句柄（handle）”，比如通过**session ID /conversation ID /event ID**；
- 这样父代理以后可以主动查询任务状态或结果。

###### 通俗例子
用户说：  
**“帮我研究一下竞争对手定价并整理成报告。”**  
这个任务要很久，就适合异步：  
主代理回复：“已开始处理，完成后会直接发给你。”  
之后子代理完成，再直接把报告发给用户。

###### 作者类比
- Async 就像**同事协作**：  
  **“你去做，做好告诉我 / 告诉用户。”**

---

##### 5. 模式三：定时 Scheduled —— “未来某个时间再执行”

###### 适用场景
适合一切 “**稍后再做，而且执行时需要最新信息**” 的任务，比如：

- 跟进提醒
- 周期性检查
- 智能提醒
- 定时发送后续消息

###### 工作方式
- 父代理不是立即执行，而是**约定未来某个时间触发子代理**；
- 到时间后，子代理再运行；
- 运行时使用的是**当下最新的数据和环境状态**。

###### 与普通 cron / 定时消息的区别
这是文章特别强调的一点：

- 普通定时：只是到点发送一条早就写好的消息；
- Scheduled sub-agent：是**到点再启动一个代理，实时获取最新信息后再分析和回复**。

###### 文中案例
1. **“明天上午 9 点提醒我检查部署指标。”**  
   - 不是 9 点发一句固定提醒；  
   - 而是 9 点启动子代理，**拉取最近 24 小时部署指标并给出总结**。

2. **“周一给这个邮件线程发跟进邮件。”**  
   - 不是周五就写好内容定时发送；  
   - 而是周一再启动子代理，带着**完整线程上下文**重新生成更合适的跟进内容。

###### 优点
- 动态、智能、上下文感知强；
- 基础设施上几乎和 async 一样，只是多了一个**时间戳 ts**。

###### 代价
- 已排队任务**不容易取消或修改**；
- 任务描述在排程时就定下来了，未来执行时可能会有点过时。

###### 后续优化方向
- 同样给父代理保留一个 “句柄”；
- 这样以后能查询 “有哪些任务排队了”、取消任务、查看状态。

---

##### 6. 怎么选：作者给出的决策框架

可以直接按下面判断：

- **需要结果才能继续？→ Sync**
- **任务独立，不想阻塞？→ Async**
- **多个独立任务并行？→ Async**
- **某个未来时间执行？→ Scheduled**
- **拿不准？→ 默认 Async**

作者的建议很明确：  
**不要替模型做死板决策，而是把这 3 种工具都提供给它，并写清楚说明，让模型自己选。**

---

##### 7. 实现思路：一个函数，三种模式

作者的实现很 “工程化”：

###### 核心设计
- **同一个 sub-agent 函数**，同时支持 sync /async/scheduled；
- 差别只在于：
  - **怎么触发**
  - **结果发回哪里**

###### 关键区别：提示词 framing
- **Sync 子代理**：提示它**简洁**，因为结果是给父代理总结用；
- **Async 子代理**：提示它**详细**，因为结果直接面向用户；
- **Scheduled 子代理**：本质上就是**延迟触发的 async**，无需额外特殊逻辑。

###### 为什么是两个工具，不是一个工具加 mode 参数？
作者认为：
- 模型更擅长**“从多个工具里选一个”**，
- 不太擅长**“看参数说明再选正确模式”**。
因此：
- 分成多个工具更清晰；
- 日志、链路追踪、调试也更容易。

###### 深度控制
- 只允许**一层委派（depth-1 delegation）**；
- 子代理可以用工具，但**不能再生成新的子代理**；
- 这样可避免系统复杂度失控。

---

##### 8. 传输与容错：和渠道解耦，且更稳定

###### 渠道无关
消息可以来自：
- Telegram
- Slack
- 邮件

流程是：
- 用户消息到父代理；
- 父代理决定异步委派；
- 事件里附带`{channel, destination, channelMeta}`；
- 子代理完成后带着同样路由信息回发；
- 由统一发送函数分发到对应渠道。

**好处：**
- 子代理不需要知道 Slack/Telegram 的细节；
- 新增一个渠道，只要加 handler，不用改子代理逻辑。

###### 容错能力
作者依赖 Inngest 的持久化和重试：

- **Sync 失败**：子代理自动重试；重试耗尽后抛错给父代理
- **Async 失败**：统一失败处理器可捕获，并借助路由信息通知用户

###### 总结
这样做不需要：
- 自定义编排代码
- 状态机
- 队列管理

作者形容其本质只是：  
**“一个带 step 包装的 while loop。”**

---

##### 9. 为什么作者更推荐 “通用代理” 而不是 “专用代理”

文章最后讨论：有了这 3 种模式后，很多人会想继续拆成：

- 邮件代理
- 数据代理
- 编码代理
- 各自不同提示词和工具

但作者建议：**先别急着专门化。**

###### 原因 1：路由会越来越复杂
- 你需要一个系统决定 “任务该给哪个专家代理”；
- 硬编码路由在模糊情况会失效；
- 用 LLM 做路由又增加：
  - 延迟
  - 成本
  - 新的失败点

作者还提出一个反问：
- 如果路由模型已经聪明到能选出最合适代理，  
  **那它为什么不能直接做这个任务？**

###### 原因 2：错分给错误代理时，问题更隐蔽
- 错误代理可能 “部分做对”；
- 但由于系统默认它是专家，反而更容易信错结果；
- 这种失败模式很难评估和修复。

###### 原因 3：评测复杂度爆炸
如果有**N 个专用代理**，就需要：
- N 套单独评测
- 1 套路由评测
- **O (N²)**的代理间交互测试
- 端到端集成测试

而一个通用代理：
- 只需要**一套覆盖全能力的评测**。

###### 文中引用观点
作者引用 Anthropic 的《Building Effective Agents》中的结论：
> 最成功的实现通常不是复杂框架或专用库，而是**简单、可组合的模式**。

同时也引用 Cursor 团队观点：
- 更倾向于使用**通用的任务接口**；
- 子代理首先是**上下文压缩边界**，其次才是并行手段。

---

##### 10. 精炼结论

- **子代理的最大价值是压缩上下文，不是单纯并行。**
- 一个能落地的 Agent 系统，必须支持：
  - **Sync**：需要结果再继续
  - **Async**：任务独立，默认优先
  - **Scheduled**：未来某时执行，并使用当时最新数据
- 工程实现上，最好：
  - 用**统一子代理函数**
  - 用**不同触发方式**区分模式
  - 保持**渠道无关、支持重试、限制委派深度**
- 架构选择上，作者更推荐：  
  **先做通用代理 + 简单可组合模式，再考虑专用代理。**

## 产品-技术开发（1）

### 2026-03-12 08:03:34

下面从**产品设计**、**技术实现**、**落地最佳实践**三个层面，精炼解读这篇文章。

---

#### 一、核心观点：这不是 “要不要子代理”，而是 “怎么编排”

作者本质在讲一个很重要的产品 / 系统设计原则：

> **Sub-agent 不是能力插件，而是上下文与任务边界管理机制。**

很多团队把 sub-agent 理解成 “专家 agent”“角色 agent”，但真正上线后最先遇到的问题不是专家分工，而是：

- 主 agent 上下文越来越臃肿
- 长链路任务阻塞用户交互
- 后台任务、延迟任务没法纳入统一调度
- 多渠道回复和任务状态难追踪

所以需要 3 个基础模式：

1. **Sync**：立即做，主 agent 等结果
2. **Async**：先去做，做完再回
3. **Scheduled**：指定未来时间再做

这三者本质上对应产品中的三类用户预期：

- **我现在就要答案**
- **你先处理，处理好通知我**
- **你到时候自动帮我处理**

---

#### 二、产品角度解读：这三种模式分别解决什么问题

##### 1) Sync：解决 “当前回合必须依赖结果” 的问题

###### 产品场景
- “帮我分析这 8 个文件后，告诉我架构问题”
- “先查一下这个 API 文档，再帮我写代码”
- “读取数据库表结构后，生成 SQL”

###### 产品价值
- 保证主流程连续性
- 用户一轮对话内得到完整答案
- 主 agent 不需要吞下所有中间过程，只拿摘要结果

###### 设计要点
- 用户感知是 “AI 在思考 / 处理中”
- 适合短中时长任务
- 返回给主 agent 的必须是**结构化摘要**，不是完整轨迹

###### 最佳实践
返回结果不要是自由文本，建议统一成结构：

```json
{
  "summary": "已分析 8 个文件，确认采用事件驱动 + durable steps 架构",
  "key_findings": [
    "子代理通过独立上下文减少主代理 token 消耗",
    "异步任务通过事件分发直接回用户",
    "调度任务本质是带 ts 的异步事件"
  ],
  "artifacts": [
    {"type": "code", "path": "src/agent/subagent.ts"},
    {"type": "doc", "title": "架构总结"}
  ],
  "next_action_suggestion": "可继续检查失败重试与任务取消机制"
}
```

这样主 agent 更容易继续推理，而不是再次总结。

---

##### 2) Async：解决 “任务耗时长，但不该阻塞当前交互” 的问题

###### 产品场景
- “研究竞品定价并给我一份报告”
- “整理这批邮件并草拟回复”
- “扫描整个仓库，找出风险点后发我总结”

###### 产品价值
- 用户不用等待
- 系统吞吐量更高
- 可以天然并行

###### 设计要点
Async 是大多数 agent 系统的**默认模式**。  
因为很多任务并不需要 “这一轮立刻参与主推理”。

###### 产品上必须补的能力
如果只做 fire-and-forget，会有明显缺陷：
- 用户不知道任务是否成功
- 主 agent 无法追踪任务状态
- 任务结果无法二次引用

所以 async 最佳实践一定要加一个**task handle /job id**：

```json
{
  "job_id": "job_123456",
  "status": "queued",
  "message": "已开始研究竞品定价，完成后将直接发送给你。"
}
```

后续用户可问：
- “刚才那个任务进行到哪了？”
- “取消刚才的报告任务”
- “把那个报告结果总结成三点”

这时主 agent 可以通过`job_id`查询结果、状态、日志、产物。

###### 最佳实践：异步任务的产品反馈分三段
1. **提交时确认**
   - “已开始处理，预计 5-10 分钟”
2. **处理中状态**
   - `queued /running/retrying /failed/completed`
3. **完成后回传**
   - 直接给用户结果
   - 同时把结果写入任务中心 / 记忆系统

---

##### 3) Scheduled：解决 “未来时刻执行，而且执行时要基于新上下文” 的问题

这是文章里最值得重视的点。

###### 产品场景
- “明早 9 点检查昨日部署指标并发给我”
- “下周一跟进这封邮件线程”
- “每天下午总结客服工单异常趋势”

###### 它和普通 reminder 的区别
不是简单 “到点提醒”，而是：

> **到点重新启动一个 agent，用当时最新的数据执行任务。**

这对产品体验提升很大：

- 提醒类产品只是 ping 用户
- Scheduled agent 是 “替用户完成工作”

###### 设计关键
调度任务最怕两个问题：

###### 问题 1：任务描述在调度时被冻结，执行时可能过时
例如：
- 周五安排 “周一基于当前线程发 follow-up”
- 到周一邮件线程已经有新回复了

###### 最佳实践
Scheduled 不要只存 prompt 文本，要存**执行模板 + 引用上下文 ID**

比如：

```json
{
  "task_type": "follow_up_email",
  "thread_id": "email_thread_789",
  "goal": "若对方仍未回复，基于最新线程上下文起草跟进邮件",
  "schedule_at": "2026-03-10T09:00:00Z"
}
```

到执行时再动态拉：
- 最新线程
- 最新 CRM 状态
- 最新用户偏好

这样 Scheduled 才真正 “智能”。

###### 问题 2：不可取消 / 不可修改
这是很多事件队列式设计的硬伤。

###### 最佳实践
调度层设计成两段式：

- **Schedule Registry**：保存计划任务元数据，可取消 / 修改
- **Execution Event**：到点后真正派发执行

不要把 “调度即入不可变队列” 作为唯一实现。

---

#### 三、技术角度解读：文章里真正好的设计点

---

##### 1) Sub-agent 的第一价值是 Context Compression，不是并行

这是全文最关键的技术判断。

很多人认为 sub-agent 的价值在于 “并行处理”，但在真实系统里，更大的收益是：

> 主 agent 不必吸收子任务的完整轨迹，只看结果摘要。

这带来三个直接收益：

- 延长单会话可持续轮次
- 降低 token 成本
- 降低上下文污染导致的推理劣化

###### 最佳实践
给 sub-agent 输出定义**严格压缩协议**：

```ts
type SubAgentResult = {
  objective: string;
  outcome: "success" | "partial" | "failed";
  summary: string;
  evidence: string [];
  artifacts?: { type: string; uri: string }[];
  followups?: string [];
};
```

不要把子代理的完整 messages append 回主代理。  
只传`SubAgentResult`。

---

##### 2) “一个通用子代理 + 三种触发模式” 优于 “很多专用子代理”

这是很成熟的工程取舍。

###### 为什么通用更优
因为专用 agent 一旦多起来，会出现：

- 路由复杂
- 错路由失败难发现
- eval 面爆炸
- prompt/tool 配置维护成本高

###### 产品 / 技术上更合理的方式
先做：
- **一个通用 agent loop**
- **统一工具集**
- **不同 delegation mode**

只有在以下场景再专门拆：
- 安全边界不同
- 工具权限不同
- SLA 不同
- 模型不同
- 合规隔离要求不同

###### 最佳实践：按 “权限 / 执行环境” 拆，而不是按 “领域名词” 拆
不建议一开始就分：
- 邮件 agent
- 数据 agent
- 编码 agent

更建议分：
- **Read-only research agent**
- **Code modification agent**
- **External action agent**
- **PII-sensitive agent**

这是更稳定的边界。

---

##### 3) 两个工具优于一个 mode 参数工具

文章这个判断非常对。

###### 不推荐
```json
{
  "tool": "delegate_task",
  "mode": "async"
}
```

因为模型对 “选择工具” 往往比 “正确填复杂参数” 更稳定。

###### 推荐
- `delegate_task`
- `delegate_async_task`
- `schedule_task`

好处：
- 模型更容易选对
- 日志更清晰
- tracing 更清晰
- prompt 更容易写
- eval 更容易做

###### 最佳实践：工具描述要写 “触发条件”，不是只写功能
例如：

```ts
description: `
将一个自包含任务委托给异步子代理。
适用于：
- 预计耗时较长
- 不需要当前回合返回结果
- 可独立完成
- 完成后可直接通知用户
不适用于：
- 当前回答依赖该结果
- 需要多个子结果在本回合合并推理
`
```

这比写 “异步执行任务” 有效得多。

---

##### 4) 限制 sub-agent 继续 spawn，是非常重要的安全与复杂度控制

文章采用**depth-1 delegation**，这是非常好的默认策略。

###### 原因
如果允许无限递归：
- 成本失控
- trace 变复杂
- 故障定位困难
- 任务风暴
- 模型可能过度 delegation

###### 最佳实践
默认规则：

- Parent 可 spawn child
- Child 不可再 spawn child
- 如确有需要，必须显式打开`max_depth=2`
- 设置总预算：
  - max_children
  - max_tokens
  - max_tool_calls
  - max_runtime

例如：

```json
{
  "max_depth": 1,
  "max_children": 3,
  "max_runtime_sec": 300,
  "max_tool_calls": 20
}
```

---

##### 5) Channel-agnostic routing 是可扩展系统的必要抽象

作者把渠道信息作为 routing metadata 传递，而不是让 sub-agent 感知 Slack/Telegram/Email，这一点非常正确。

###### 设计原则
**任务执行逻辑**和**消息投递逻辑**必须解耦。

###### 推荐架构
- Agent 负责生成结果
- Reply Dispatcher 负责投递
- Channel Adapter 负责平台协议

```plaintext
Agent -> ReplyReadyEvent -> Dispatcher -> Slack/Email/Telegram Adapter
```

###### 好处
- 新增渠道不改 agent
- 渠道失败可单独重试
- 容易做 A/B 和多渠道 fallback

---

#### 四、真正落地时必须补齐的能力

文章框架很好，但要上线，还缺几个关键模块。

---

##### 1) 任务状态中心

不然 async/scheduled 会变成 “黑盒”。

###### 至少要有
- `task_id`
- `parent_session_id`
- `type`: sync /async/scheduled
- `status`
- `created_at /scheduled_at/started_at /finished_at`
- `result_ref`
- `error`
- `cancelable`

###### 最佳实践
做一个统一 Task Registry：

```ts
type TaskRecord = {
  taskId: string;
  parentSessionId: string;
  mode: "sync" | "async" | "scheduled";
  status: "queued" | "running" | "completed" | "failed" | "cancelled";
  promptSnapshot: string;
  contextRefs: string [];
  resultRef?: string;
  error?: string;
};
```

---

##### 2) 幂等与去重

sync/async/scheduled 都会遇到重试问题。

###### 风险
- 同一任务执行两次
- 同一消息发两次
- 同一外部动作重复执行

###### 最佳实践
每个子任务都带：
- `idempotency_key`
- `parent_turn_id`
- `task_hash`

对外部副作用操作尤其重要：
- 发邮件
- 建工单
- 改数据库
- 发 Slack 消息

---

##### 3) 结果可查询，不只是可投递

文章也提到 handle 的方向，这是必须做的。

###### 为什么
用户不会只满足于 “做完通知我”，还会问：
- “把刚才结果精简一下”
- “比较一下两个异步任务结论”
- “那个定时任务目前还在吗”

###### 最佳实践
异步结果不要只发出去，还要存档为可检索 artifact：

- 原始结果
- 摘要结果
- 关键结论
- 关联上下文
- 可再次被主 agent 引用

---

##### 4) Eval 设计要跟 delegation 模式绑定

三种模式，评估标准不同。

###### Sync eval
关注：
- 结果是否足够压缩
- 是否保留关键证据
- 是否帮助主 agent 完成下一步

###### Async eval
关注：
- 是否正确判断适合异步
- 用户是否收到完成通知
- 最终回复质量是否足够直接面向用户

###### Scheduled eval
关注：
- 是否按时执行
- 是否使用执行时最新上下文
- 是否支持取消 / 修改
- 是否避免 stale prompt

---

#### 五、可直接借鉴的最佳实践方案

---

##### 方案 A：代码助手

###### 需求
用户说：“帮我分析这个仓库里的认证模块，并给优化建议。”

###### 设计
- 主 agent 判断需读多个文件 -> 调`delegate_task`（sync）
- 子代理读 10 个文件、查依赖、生成压缩摘要
- 主 agent 基于摘要输出最终建议

###### 最佳实践
- 子代理返回：问题列表 + 证据文件路径 + 风险等级
- 不把完整文件内容塞回主上下文
- 如果还要 “修复并提 PR 建议”，再异步启动`delegate_async_task`

---

##### 方案 B：企业研究助手

###### 需求
“帮我研究 5 家竞品并给我发一份报告。”

###### 设计
- 主 agent 立即确认任务已开始
- fan-out 5 个 async sub-agent 并行研究
- 聚合器在后台汇总结果
- 最终直接发给用户

###### 最佳实践
这里要注意：  
如果 5 个子代理完全独立，最后需要一个**聚合任务**，否则只是 5 份散报告。

建议链路：
1. parent 创建`research_job`
2. spawn 5 个 async worker
3. all done 后触发`aggregator agent`
4. aggregator 输出最终统一报告

也就是说：
- **并行 worker 是 async**
- **综合汇总也是一个 agent step**

---

##### 方案 C：运维 / 数据分析助手

###### 需求
“每天早上 9 点检查部署指标，如果错误率升高就提醒我并附原因分析。”

###### 设计
- 用户下达一次自然语言指令
- 主 agent 抽取 schedule intent
- 记录任务模板 + schedule
- 到点启动 scheduled sub-agent
- 子代理拉取最新监控数据，做分析，发结果

###### 最佳实践
不要把 “错误率阈值、服务名、观察窗口” 只写进 prompt 文本。  
应该存结构化规则：

```json
{
  "task_type": "monitor_deploy_metrics",
  "service": "checkout-service",
  "window": "24h",
  "alert_condition": {
    "metric": "error_rate",
    "op": ">",
    "threshold": 0.03
  },
  "schedule": "0 9 * * *"
}
```

到执行时，agent 再把结构化配置转成 prompt + tool query。

---

#### 六、我给出的最终建议

##### 最值得采纳的 7 条

1. **把 sub-agent 当作上下文压缩机制，不是角色扮演机制**
2. **默认优先 async，sync 只在当前回合必须依赖结果时使用**
3. **scheduled 不是 reminder，而是 deferred execution**
4. **统一一个通用 sub-agent runtime，先不要急着做专用 agent**
5. **工具分开设计，不要靠 mode 参数让模型自己填**
6. **强制 depth-1，控制预算和副作用**
7. **补齐 task registry /handle/cancel /status/artifact store，否则无法产品化**

---

#### 七、一句话总结

这篇文章最有价值的地方不是 “三种模式” 本身，而是它指出了一个成熟 agent 系统的真实工程原则：

> **Agent 编排的核心不是让模型更聪明，而是让任务边界、上下文边界、执行时机和交付路径更可控。**

## 总结（1）

### 2026-03-12 08:06:50

下面给你一个**具体实例**，并基于文章内容提炼出**最佳实践**。

---

##### 实例：企业内部 “研发助手” Agent

场景：  
用户在 Slack 里对研发助手说：

> “帮我看看昨天线上报警的原因；如果需要，整理一份竞品价格调研；另外明天早上 9 点提醒我查看今天部署后的稳定性数据。”

这个系统里，父 Agent 应这样拆分：

###### 1. Sync 子 Agent：阻塞式
**任务**：分析昨天报警原因，读取日志、最近变更、告警记录，并给父 Agent 一个简明结论。  
**为什么用 Sync**：父 Agent 需要这个结果，才能继续回答用户 “报警原因是什么”。

---

###### 2. Async 子 Agent：异步式
**任务**：调研竞品价格并生成报告，完成后直接回 Slack。  
**为什么用 Async**：这是长任务，不需要阻塞当前对话，用户可以先拿到主问题答案。

---

###### 3. Scheduled 子 Agent：定时式
**任务**：明天早上 9 点自动拉取最近 24 小时部署稳定性指标，并发送分析。  
**为什么用 Scheduled**：任务要在未来某个时间点执行，而且执行时需要拿 “最新数据”。

---

#### 基于这个实例的最佳实践（精炼）

###### 1. 用 “三种模式” 覆盖全部委托场景
- **Sync**：当前回合必须依赖结果
- **Async**：独立长任务，完成后再通知
- **Scheduled**：未来触发，且要基于当时的新数据执行

> 经验法则：**不确定时默认 Async**。

---

###### 2. 子 Agent 的首要价值是 “上下文压缩”，不是 “智能分工”
在报警分析这个例子里，子 Agent 可能读 10 份日志、调用 20 次工具；父 Agent 只接收一段摘要。  
这样能显著降低父 Agent 上下文膨胀，保持长对话稳定。

> 最佳实践：**父 Agent 只拿摘要，不拿完整执行轨迹。**

---

###### 3. Sync 返回 “简洁总结”，Async/Scheduled 返回 “面向用户的完整答复”
- **Sync 子 Agent**：输出要短、结构化、便于父 Agent 后续综合
- **Async/Scheduled 子 Agent**：输出要完整，因为它们往往直接面向用户

> 同一个子 Agent 执行器可以复用，只通过 prompt framing 区分风格。

---

###### 4. 工具设计上，分成多个明确工具，不要用一个工具加 mode 参数
例如：
- `delegate_task`（同步）
- `delegate_async_task`（异步）
- `schedule_task`（定时）

这样比一个`delegate (mode=sync|async|scheduled)`更稳。  
因为模型通常**更擅长选工具**，不擅长**在参数里做精细模式判断**。

---

###### 5. 子 Agent 默认不要继续派生子 Agent
在这个研发助手例子中，建议先做**深度 1 委托**：
- 父 Agent 可以委托
- 子 Agent 不再继续委托

这样可避免递归膨胀、路由混乱和调试困难。

---

###### 6. Async 和 Scheduled 必须返回 “任务句柄”
比如返回：
- taskId
- sessionId
- eventId

这样父 Agent 之后才能：
- 查询状态
- 获取结果
- 取消任务
- 修改计划任务

> 这是异步系统从 “能跑” 到 “可运营” 的关键。

---

###### 7. 路由信息与任务执行解耦
在 Slack 场景中，子 Agent 不需要知道自己在 Slack。  
它只接收：
- `channel`
- `destination`
- `channelMeta`

执行完后统一交给消息分发层发送。  
这样以后接入 Telegram、邮件、钉钉时，不必改子 Agent 逻辑。

---

###### 8. 先做 “通用子 Agent”，谨慎做 “专家子 Agent”
对于 “报警分析、竞品调研、定时汇报” 这类任务，优先用**通用子 Agent + 清晰任务描述**。  
不要过早拆成：
- 日志专家 Agent
- 价格专家 Agent
- 部署专家 Agent

因为专门化会带来：
- 路由复杂度
- 错误分派风险
- 测试面膨胀

> 优先让 “任务描述” 承担 specialization，而不是让 “Agent 类型” 承担。

---

##### 一句话总结
在 “研发助手” 这个实例里，**最佳实践**是：

> 用**Sync 拿当前必需结果**、用**Async 处理独立长任务**、用**Scheduled 在未来时点获取新数据执行任务**；同时坚持**父 Agent 只收摘要、工具显式分离、默认单层委托、异步任务可追踪、路由与执行解耦、优先通用而非专家化**。
