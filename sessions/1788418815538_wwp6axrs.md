## 分析要点

- **核心高价值点**：按任务复杂度分级使用流程：复杂任务走规格、垂直切片、隔离并发和多层审查，简单改动则保留方案授权与测试两条底线。
- **留存建议**：建议精读并存档，可作为设计AI辅助开发流程和代码审查机制的参考（提供了从需求澄清、规格生成、任务切片到并行实现和交叉审查的完整流程，并明确区分轻重任务的适用条件。）

**知识要点**

- 模型能力增强后，过长的系统提示和流程护栏可能从稳定器变成注意力噪音，因此应持续压缩上下文。
- 复杂任务可按“需求澄清—规格文档—垂直切片—隔离并行—自动审查—人工把关”组织开发。
- 代码生成速度提升后，系统瓶颈可能转移到方案判断、代码审查和部署等人工环节。

**行动项**

- 选取一个中等复杂度任务，试行需求澄清、spec、垂直切片、worktree并行和最终人工审查流程。
- 为小改动建立轻量规则：修改前提交简短方案等待授权，修改后必须运行测试。
- 尝试用不同厂商模型并行审查同一变更，并记录有效问题、重复意见和误报率。

#### 一、回顾历史分享

三月份那篇的背景是一个系统做架构升级，需求复杂、边界情况多，AI 很容易在某个细节上悄悄跑偏，你发现的时候已经在错误方向上浪费了大量时间。当时的答案是加约束，Superpowers 提供流程纪律和 TDD 的执行策略，gstack 提供多角色 review。在当时这套 SOP 效果很好，brainstorm 阶段追问出很多并发写入的边界问题，/review 发现竞态条件，都是测试阶段很难发现的 case。

但这套流程代价也很大。Superpowers 是个非常重量级的框架，一个流程跑下来注入的上下文非常庞大，经常一天烧掉几亿 token，但效果还比不上现在 matt skills 的几句话。从现在的视角看原因很明显，模型能力强了之后原来那些为了让模型跑得更稳而加的护栏，都成了注意力里的噪音。

八月初那篇讲了 Harness 换成 Pi 的原因。Databricks 拿几百万行的代码库实测过，同一个模型换不同 Harness，质量基本持平的情况下任务成本能差出两倍以上，Pi 每轮喂给模型的上下文只有其他 Harness 的三分之一左右。

#### 二、开发工具栈

Anthropic 最近发了一篇博客讲上下文工程的新规则，里面明确说他们为 Claude 5 代模型砍掉了 Claude Code 超过八成的 system prompt。官方承认模型强了之后，之前的大段指令反而稀释注意力。

轻量化是共同的方向，Claude Code、Codex、Pi 挑顺手的用就好。工具不是重点，下面简单推荐几个我日常在用的工具。

一是 matt skills，

[Matt Pocock](https://www.aihero.dev/skills) 的 Skill 集合，他应该是全世界最会写 Skill 的男人，我日常用的五个如下。

二是

[马尾辫](https://github.com/DietrichGebert/ponytail)，用于消除 AI Slop。LLM 写代码经常爱写一堆没意义的内容。防御性的空检查，永远不会有第二个实现的 interface，给常量再包一层 private 常量，注释里写满过程性标注等等。这些内容单看也许没问题，但长期下来无论是人维护还是 AI 维护都是负担。ponytail 的作用就是卡控这些内容，这个逻辑要不要存在、代码库里有没有现成的、标准库能不能干、能不能一行写完，都答不上来才许写新代码。使用后 diff 明显变短，而短 diff 是好 review 的前提。

三是 subagent 加 worktree。并发跑多个任务时用 git worktree 做隔离，各改各的避免冲突，worktree 是 git 的通用概念，哪个 Harness 都能用；在 Claude Code 和 Codex 里 subagent 是原生的。而 Pi 秉持 Less is More 的思路，原生并不提供 subagent，原因是作者任务使用 tmux 等原语即可实现 subagent 的并行、避免上下文腐化等功能。我日常使用

[赫尔德](https://herdr.dev/)，可以理解为 AI 时代的 tmux，比 subagent 更轻，还能让 Pi 直接操纵里面的 Claude Code、Codex 这些进程。

![Image](https://pbs.twimg.com/media/HRNxDV9aYAA_yuF?format=jpg&name=large)

#### 三、日常 Coding SOP

![Image](https://pbs.twimg.com/media/HRNxOQuaQAAUsFE?format=jpg&name=large)

先用 grill-me / grill-with-docs 对齐上下文。这个阶段和 AI 一轮一轮脑暴对齐需求的边界、约束等。对齐后用 to-spec 产出 spec 文档，人工 Review 一遍，这是第一道人工门控。spec 过了用 to-tickets 垂直切片拆分任务，每个 ticket 可独立交付执行。接着派 subagent 跑 implement，一个 ticket 一个 subagent，worktree 隔离并发执行，执行内部走 tdd + code-review。全部完成后做 PR 级的 review，最后人工 CR 把关。

当然这套链路也不算轻，如果是单文件的局部小改，边界清楚，验证成本低，直接 Main Agent 对齐快速改动即可。但轻流程有两条底线，改动前依然需要先出简单方案等人授权，改完必须跑测试。流程可以分级，纪律不能分级。

#### 四、人工 Review 是新的瓶颈

Anthropic 前阵子发了一篇

[AI 原生 SDLC 的 playbook](https://claude.com/blog/the-ai-native-sdlc-playbook)，里面有个结论是代码生成已经快到飞起，软件开发的瓶颈移到了 Coding 的左右两侧，出方案、Review、部署上线这些环节还在以人的速度跑。

我的体验是，当前软件开发的并发上限卡在人的 Review 带宽上。

![Image](https://pbs.twimg.com/media/HRNxR9CboAEcpMM?format=jpg&name=large)

Claude Code、Codex 随便开，worktree 随便建，这些层面的并发几乎免费，但一个人同时处理四个 Session 就比较勉强了，如果处理八条一定会有遗漏。所以未来 Harness 的竞争点，我认为会往压缩人工 Review 成本的方向走。

Ensemble Review 是我现在压缩 Review 成本的手段，原理是让不同厂商的模型交叉审查同一段代码。每个模型都有系统性盲区，GPT 看不出的问题 DeepSeek 可能一眼就看到了，单一模型自审等于让考生自己改卷子。我的配置是四路对抗 Reviewer，GPT、GLM、DeepSeek、Kimi 分别拉起一个 subagent 同时使用干净上下文，跑同一个审查 skill。

但大模型 Review 再多，最后还是得让人来判断，四路结论摆在一起，这个判断仍然是人的活。

#### 五、软件工程思维仍关键

吴恩达最近有篇

[文章](https://charonhub.deeplearning.ai/the-ai-engineering-skills-map-in-detail-software-engineering-fundamentals/) 讲 AI 时代的软件工程基本功，里面有个观点我很认同。不懂软件基础的人 Vibe Coding 可以完成开发，但麻烦在于 Agent 可能已经帮他做了一堆糟糕的取舍，而他自己都不知道哪些取舍发生过。接口延迟、可用性、一致性、成本，这些 trade-off 即使有 AI 后也不会消失，而人的判断会越来越重要。

AI Coding 迭代速度太快，这次分享的内容可能三个月后就会过时。但有几件事我确定不会过时。一件是对系统的理解，选延迟还是选系统成本，要简单还是要可扩展，一致性优先还是可用性优先，这些判断大模型它只能给选项，给不了你最优结论。另一件是工程直觉，哪段代码可疑，哪个需求有坑，哪条 Review 意见是噪音，这也是 AI 替代不了的。

## 通俗精炼（1）

### 2026-09-03 07:00:15

#### 半年后的 AI 编程实践：从 “堆约束” 走向 “轻框架、强审查”

##### 核心结论

随着模型能力提升，AI Coding 已逐渐进入稳定阶段：**不再依赖复杂提示词和重型流程，而是用更少的上下文完成任务，把人的精力集中在需求澄清、方案判断和代码审查上。**

工具会持续变化，但软件工程能力仍是决定交付质量的核心。

##### 一、实践演进：先加约束，再减约束

早期模型容易在复杂任务中悄悄跑偏，因此需要依靠严格流程、TDD 和多角色 Review 来约束执行。

但这类重型框架会注入大量上下文，消耗高、噪音多。模型能力增强后，过去用于 “扶着模型走路” 的护栏，反而会分散注意力。

因此，当前趋势是：

- 精简 System Prompt 和流程说明
- 减少无效上下文
- 使用轻量 Harness（Agent 的执行框架）
- 把复杂约束收敛成少量、高质量的 Skills

**Harness 本身不再是关键，Claude Code、Codex、Pi 选择顺手的即可。**

##### 二、当前工具栈

###### 1. Matt Skills：把想法变成可执行任务

| Skill | 作用 |
|---|---|
| `grill-me` | 通过连续追问澄清模糊需求 |
| `grill-with-docs` | 对齐需求，同时沉淀 ADR 和术语表 |
| `to-spec` | 将共识整理成规格文档 |
| `to-tickets` | 将 Spec 拆成可独立交付的垂直任务，并标记依赖 |
| `implement` | 由 Subagent 实现任务，执行 TDD 和代码审查 |

###### 2. Ponytail：消除 AI 代码冗余

用于约束 AI 常见的 “过度设计”，例如：

- 无意义的空值检查
- 只有一个实现的接口
- 多余的常量封装
- 解释过程而非代码意图的注释
- 标准库可以完成却重复造轮子

核心原则是：**先证明新代码确实有必要，再允许新增。**  
其价值在于缩短 Diff，而短 Diff 更容易被有效审查。

###### 3. Subagent + Git Worktree：安全并发

- 一个任务分配一个 Subagent
- 每个 Agent 使用独立 Worktree
- 多任务并行开发，避免文件和分支冲突
- 使用干净上下文，减少不同任务之间的上下文污染

##### 三、推荐的日常 Coding SOP

完整流程如下：

1. **需求对齐**：通过追问澄清目标、边界与约束
2. **形成 Spec**：把讨论结果沉淀为规格文档
3. **人工门控**：人工审查 Spec，确认方向正确
4. **垂直拆分**：拆成可独立交付的 Tickets
5. **并行实现**：每个 Ticket 由独立 Subagent 在 Worktree 中完成
6. **内部验证**：执行 TDD、自审和代码审查
7. **PR 级 Review**：从整体变更角度检查
8. **人工 CR**：最终由人判断是否可以合并

对于单文件、小范围、低风险改动，可以简化流程，但有两条底线：

- **修改前必须先给出方案，等待人工授权**
- **修改后必须执行测试**

即：**流程可以分级，工程纪律不能分级。**

##### 四、新瓶颈：不是写代码，而是人类 Review

AI 已大幅提升代码生成速度，开发瓶颈开始转移到 Coding 两侧：

- 前端：需求澄清、架构与方案设计
- 后端：代码审查、部署与上线决策

Agent 和 Worktree 可以近乎零成本地增加并发，但人的注意力有限：同时审查过多 Session，必然出现遗漏。

因此，未来 AI 编程工具的竞争重点，可能从 “生成更多代码” 转向：

> **帮助人更快、更准确地完成 Review。**

##### 五、用多模型交叉审查降低风险

作者采用 Ensemble Review：让不同厂商的模型在独立上下文中审查同一段代码，例如：

- GPT
- GLM
- DeepSeek
- Kimi

不同模型的系统性盲区不同，交叉审查比单一模型自审更可靠。因为让同一个模型检查自己的代码，本质上接近 “考生自己改卷”。

但多模型只能提供意见，**最终判断仍必须由人完成。**

##### 六、AI 时代更重要的人类能力

AI 可以完成编码，却无法替代关键取舍，包括：

- 延迟与成本如何平衡
- 一致性与可用性如何选择
- 简单实现与未来扩展如何取舍
- 哪段代码存在隐患
- 哪个需求可能埋坑
- 哪条 Review 意见有价值，哪条只是噪音

不具备软件工程基础的人，也许能通过 Vibe Coding 做出功能，但可能无法意识到 Agent 已替自己做了哪些错误决策。

##### 最终启示

AI 编程的稳定方法不是不断增加提示词和流程，而是：

> **轻量上下文 + 清晰规格 + 垂直拆分 + Agent 并行 + 自动测试 + 多模型审查 + 人工决策。**

模型和工具会快速过时，但两种能力不会：

1. **系统性取舍能力**：理解业务与技术目标，作出正确权衡  
2. **工程直觉**：识别风险、异常和无效建议  

AI 负责提高执行速度，人负责定义方向、控制边界并承担最终判断。

## 结构化（1）

### 2026-09-03 07:01:20

#### 《半年后的今天，我怎么用 AI 写代码》精炼总结

文章回顾了作者半年内 AI Coding 方法的变化：从依赖重型流程 “给 AI 加约束”，逐步转向轻量工具与更少上下文。作者认为，当前较稳定的实践是：**先把需求讲清楚，再让多个 Agent 并行实现和审查，最后由人负责关键判断。**

##### 一、从 “加约束” 到 “减约束”

###### 1. 早期：用重型流程防止 AI 跑偏

面对架构升级、复杂需求和大量边界情况时，AI 容易在细节上悄悄走错方向，因此作者最初采用：

- **Superpowers**：提供流程纪律和 TDD 执行策略。
- **gstack**：通过多个角色进行 Review。
- 在 brainstorming 阶段追问并发写入等边界问题。
- 通过`/review`发现竞态条件等测试阶段不易暴露的问题。

这套 SOP 当时效果不错，但成本很高：

- Superpowers 会注入大量上下文。
- 一天可能消耗**几亿 Token**。
- 随着模型能力增强，过去用于 “扶稳模型” 的大段护栏，反而变成干扰注意力的噪音。

###### 2. 后来：切换到更轻量的 Harness

作者在八月将 Claude Code 换成 Pi，核心原因是降低上下文和成本。

Databricks 曾在**数百万行代码库**上测试不同 Coding Harness：

- 使用同一个模型、同样的 thinking 档位；
- 最终产物质量基本持平；
- 但任务成本最多可相差**2 倍以上**；
- Pi 每轮提供给模型的上下文，约为其他 Harness 的**三分之一**。

> **结论：**模型越强，越不需要复杂提示词和重型工作流；Harness 应尽量轻量，只提供必要信息。

##### 二、当前开发工具栈：轻量化优先

作者提到，Anthropic 为 Claude 5 代模型删掉了 Claude Code **超过 80% 的 system prompt**。这说明旧有的大段指令可能稀释模型注意力。

因此 Claude Code、Codex、Pi 都可以使用，关键不是品牌，而是是否顺手、上下文是否精简。

###### 1. Matt Skills：从需求澄清到代码实现

作者日常使用以下 5 个 Skill：

| Skill | 作用 |
|---|---|
| `grill-me` | 用苏格拉底式追问，把模糊想法问清楚 |
| `grill-with-docs` | 一边逐项对齐需求，一边沉淀 ADR 和术语表 |
| `to-spec` | 将讨论结果整理为正式 Spec 文档 |
| `to-tickets` | 把 Spec 拆成可独立交付的垂直任务，并标明依赖 DAG |
| `implement` | 由 Subagent 拉取 Ticket 实现，内部执行 TDD 和 Code Review，持续修复直到过审 |

###### 2. Ponytail（“马尾辫”）：清理 AI Slop

LLM 经常生成看似合理、实际没有价值的冗余代码，例如：

- 没必要的防御性空值检查；
- 永远不会有第二个实现的 interface；
- 给常量再包一层 private 常量；
- 注释中堆满过程性说明；
- 重复实现代码库或标准库已有能力。

Ponytail 会要求 AI 在新增代码前回答：

1. 这段逻辑真的需要存在吗？
2. 代码库中是否已有现成实现？
3. 标准库能不能完成？
4. 能否用一行代码解决？

只有这些方案都不可行，才允许增加新代码。使用后，代码 Diff 会明显缩短，而**短 Diff 是高质量 Review 的前提**。

###### 3. Subagent + Git Worktree：并行且互不干扰

并发处理多个任务时：

- 每个任务分配一个 Subagent；
- 使用 Git Worktree 隔离代码修改；
- 各任务独立开发，减少相互冲突。

Claude Code 和 Codex 原生支持 Subagent。Pi 则遵循 “Less is More”，不原生提供这一能力，而是建议使用 tmux 等基础工具实现并发。

作者日常使用 “赫尔德”，可理解为 AI 时代的 tmux：

- 比原生 Subagent 更轻；
- 能隔离不同任务的上下文；
- 还可以让 Pi 操作 Claude Code、Codex 等进程。

---

##### 三、日常 AI Coding SOP

作者当前的完整流程如下：

```text
需求讨论
→ 生成 Spec
→ 人工审核 Spec
→ 拆分 Tickets
→ 多个 Subagent 并行实现
→ TDD + Code Review
→ PR 级 Review
→ 人工最终把关
```

###### 具体步骤

1. **对齐需求**
   - 使用`grill-me`或`grill-with-docs`；
   - 与 AI 多轮讨论需求边界、限制条件和潜在风险。

2. **生成 Spec**
   - 使用`to-spec`产出设计文档；
   - 人工 Review，这是第一道人工门控。

3. **拆分任务**
   - 使用`to-tickets`做垂直切片；
   - 每个 Ticket 都能独立实现和交付，并标明依赖关系。

4. **并行开发**
   - 一个 Ticket 分配一个 Subagent；
   - 每个 Subagent 使用独立 Worktree；
   - 实现过程中执行 TDD 和代码审查，并自行修复问题。

5. **最终审查**
   - 所有任务完成后进行 PR 级 Review；
   - 最后由人完成 Code Review 和决策。

###### 小改动可以简化，但不能放弃纪律

如果只是边界清楚、验证成本低的单文件修改，可以直接让 Main Agent 快速完成，不必走完整链路。

但仍有两条底线：

- **修改前必须先给出简单方案，并等待人工授权；**
- **修改完成后必须运行测试。**

> 流程可以分级，但工程纪律不能分级。

---

##### 四、人工 Review 成为新的开发瓶颈

随着 AI 生成代码的速度大幅提高，软件开发的瓶颈开始从 “写代码” 转移到两侧：

- 前期方案设计；
- 代码 Review；
- 部署与上线；
- 最终风险判断。

Agent、Session 和 Worktree 几乎可以低成本扩展，但人的注意力无法同步扩展：

- 一个人同时处理**4 个 Session**已经比较勉强；
- 同时处理**8 个 Session**几乎必然出现遗漏。

因此，作者认为未来 Coding Harness 的竞争重点，将从 “谁生成代码更快” 转向 “谁能降低人工 Review 成本”。

###### Ensemble Review：让不同模型交叉审查

作者使用多模型对抗审查同一段代码：

- GPT
- GLM
- DeepSeek
- Kimi

四个模型分别启动独立 Subagent：

- 使用干净、互不污染的上下文；
- 执行同一个 Review Skill；
- 互相补充系统性盲区。

例如，GPT 没发现的问题，DeepSeek 可能很快识别出来。单一模型自审则类似 “让考生自己改卷子”，可靠性有限。

不过，无论模型给出多少审查意见，最终仍需要人来判断：

- 哪条意见是真问题；
- 哪条只是噪音；
- 是否值得修改；
- 修改会不会引入新的权衡和风险。

---

##### 五、AI 时代，软件工程思维反而更重要

不懂软件基础的人也可以通过 Vibe Coding 做出可运行的软件，但风险在于：Agent 可能已经做出许多糟糕的技术取舍，而使用者甚至不知道这些取舍发生过。

AI 无法消除以下工程权衡：

- 接口延迟与系统成本；
- 可用性与一致性；
- 简单设计与未来扩展能力；
- 开发速度与长期维护成本。

作者认为，有两类能力不会因 AI 进步而过时：

###### 1. 对系统的理解

大模型可以列出选项，却无法替你确定唯一最优答案。例如：

- 应优先降低延迟，还是降低成本？
- 应保持简单，还是预留扩展能力？
- 应优先保证一致性，还是可用性？

这些选择必须结合真实业务和系统目标，由人负责。

###### 2. 工程直觉

有经验的工程师能快速判断：

- 哪段代码看起来可疑；
- 哪个需求可能埋坑；
- 哪条 Review 意见值得采纳；
- 哪条只是模型生成的噪音。

这类判断能力仍是 AI 难以替代的核心价值。

---

##### 六、补充：让人工反馈持续沉淀

作者还引用了 Warp 的自进化 Agent 实践：传统 Agent Session 结束后，人的纠正往往也随之消失，导致同类错误反复出现。

Warp 的思路是：

- 把人工纠正沉淀进 Skill；
- 让反馈跨 Session 保留下来；
- 持续改进 Agent 在重复任务中的表现。

其背景是，Agent 的第一版 Prompt 往往只能完成约**80%**，剩余部分会持续产生噪音。真正有效的改进，不只是当场修正，而是让修正结果进入长期工作流。

---

##### 核心结论

- **模型变强后，应减少无意义的提示词和流程约束。**
- **复杂任务先澄清需求、产出 Spec，再拆成可独立交付的 Ticket。**
- **通过 Subagent + Worktree 实现安全并行。**
- **用 Ponytail 等机制减少冗余代码，保持短 Diff。**
- **让多个模型交叉 Review，但最终决策仍由人完成。**
- **AI 提高了编码速度，却让需求判断、Review 和系统权衡成为新的核心瓶颈。**
- **工具和工作流可能很快过时，但系统理解、工程纪律与判断力不会过时。**

更重要的是由此形成的原则：**流程应该分级，纪律不能消失。**单文件、边界清晰且容易验证的改动，可以采用“先给简要方案—人工授权—执行—跑测试”的短链路；涉及架构、并发和复杂业务约束时，再增加需求追问、规格文档、任务切片和多轮审查。

这比固定一套“最佳 AI Coding 工作流”更合理。真正决定流程重量的，不是代码行数，而是需求歧义、失败影响和验证成本。

##### 并发上限不由 Agent 数量决定，而由人的审查带宽决定

worktree 和 subagent 让多个任务并行变得很便宜，但人无法同比扩展注意力。开四个 Agent 也许能提高产出，开八个却可能让遗漏率上升。于是优化目标应从“生成更多代码”转向**用更少的人类判断完成可信交付**。

文章对 AI Slop 的警惕因此很关键。多余的抽象、防御性空判断和过程性注释，不只是代码风格问题，它们会扩大 diff，增加审查面，使真正危险的改动更难被发现。短 diff 的价值，在于降低验证成本，而不是追求形式上的简洁。

多模型交叉 Review 可以补充不同模型的盲区，但不能简单理解为“四票比一票可靠”。模型可能共享训练偏差，也可能制造大量互相冲突的低价值意见。下一阶段 Harness 真正有价值的能力，可能不是再增加 Reviewer，而是**按风险聚合争议、关联测试与代码证据，并明确哪些判断必须由人完成**。它需要用审查耗时、缺陷逃逸率和误报率验证，而不能只看发现了多少问题。

##### 工程基本功正在从“亲手实现”转向“识别取舍”

Agent 可以给出延迟、成本、一致性和可扩展性的选项，却不知道组织此刻最在意什么，也无法自行承担错误选择的后果。人的核心作用因此不是逐行写代码，而是定义约束、识别可疑取舍，并判断某条 Review 意见究竟是风险还是噪音。

对产品经理同样如此：高质量 spec 的价值不在于写得更长，而在于说清优先级、不可接受的失败以及验收证据。**AI 编程真正放大的不是编码能力，而是判断质量；判断不足时，它只会更快地把隐含错误扩散到整个系统。**

## 口播总结（1）

### 2026-09-20 00:32:44

半年实践下来，作者对人工智能编程的核心判断发生了变化：早期需要给智能体加很多流程和约束，防止它跑偏；随着模型能力提升，更有效的做法反而是减少无谓约束，把宝贵的上下文留给真正的问题。不过，工具可以变轻，工程纪律和人的判断不能消失。

最初，作者面对的是复杂的架构升级。需求边界多，还涉及并发写入和竞态条件。人工智能很可能在某个细节上悄悄走错，等人发现时，已经浪费了大量时间。为此，他采用了重量级流程：先反复追问需求，再用测试驱动开发推进实现，还让多个角色参与代码审查。这套方法确实找出了不少隐蔽问题，包括测试阶段都未必容易暴露的竞态条件。

但代价也很明显。大量流程说明会占据很长的上下文，一天甚至可能消耗几亿个词元。模型越强，这些原本用于保驾护航的指令，就越可能变成注意力噪音。

这里的关键概念叫 Harness，可以理解为驱动编程智能体工作的工具框架，包括系统提示、上下文组织和任务执行方式。作者引用了 Databricks 的一次测试：在数百万行代码的真实代码库里，使用相同模型和相同思考强度，只更换 Harness，最终质量基本相当，任务成本却可能相差两倍以上。轻量工具 Pi 每一轮提供给模型的上下文，大约只有其他工具的三分之一。

据作者转述，Anthropic 也为新一代模型删掉了 Claude Code 超过八成的系统提示。背后的道理很简单：上下文并不是越多越好。旧规则、重复说明和过度细化的流程，都可能稀释模型对当前任务的注意力。因此，Claude Code、Codex 或 Pi，并不存在绝对正确的选择。选一个顺手的轻量工具就好，真正重要的是工作方法。

作者目前的日常流程，第一步不是立刻写代码，而是把问题问清楚。他会让人工智能采用类似苏格拉底式追问的方法，一轮一轮确认需求、边界和约束。对于复杂任务，还会同步形成架构决策记录和术语表，避免双方对同一个词有不同理解。

对齐完成后，人工智能把讨论结果整理成规格文档。人要亲自审一遍，这是第一道人工门控。规格通过后，再把任务拆成可以独立交付的垂直切片。所谓垂直切片，不是先把所有数据库代码写完，再统一写接口，而是让每个小任务都尽可能形成一条完整、可验证的功能链路。

接下来，每个任务交给一个独立的子智能体执行。多个任务并行时，使用 Git 的工作树，也就是 worktree，把不同修改隔离开，避免相互冲突。每个子智能体内部执行测试驱动开发和代码审查，先写验证，再完成实现，并根据审查结果自行修正。全部任务结束后，还要进行合并请求级别的整体审查，最终由人把关。

不过，这套完整链路并不适合所有改动。单文件的小修改，如果边界清楚、验证成本低，可以让主智能体直接完成。流程可以按照风险分级，但有两条底线不变：动手前，人工智能必须先提出一个简单方案，得到人的授权；改完以后，必须运行测试。也就是说，流程可以变轻，纪律不能取消。

除了正确性，还要控制人工智能制造的代码垃圾。大模型经常会写出看似稳妥、实际上没有必要的内容。比如永远不会触发的空值检查，只会有一个实现的接口，给常量再包一层私有常量，或者在注释里堆满开发过程说明。单独看一处似乎问题不大，但长期积累后，无论由人还是人工智能维护，都会成为负担。

作者使用一套叫“马尾辫”的规则来约束这类内容。新增逻辑之前，要先回答几个问题：这段逻辑真的需要存在吗？代码库里是否已有现成实现？标准库能不能完成？能不能用一行简单代码解决？只有这些路都走不通，才允许增加新代码。这样做会明显缩短代码差异，而短小、聚焦的改动，正是高质量审查的前提。

当代码生成越来越快，新的瓶颈就出现了。瓶颈不再是写代码，而是写代码前后的环节，包括方案设计、代码审查和部署上线。智能体和工作树几乎可以随意增加，但人的注意力无法无限并行。作者的体验是，一个人同时处理四个会话已经比较吃力；同时处理八个，几乎一定会遗漏问题。

为了降低审查成本，他会让不同厂商的模型交叉检查同一段代码。比如让 GPT、GLM、DeepSeek 和 Kimi 分别使用干净的上下文，执行同一套审查规则。原因是不同模型存在不同的系统性盲区。一个模型忽略的问题，另一个模型可能立刻发现。只让生成代码的模型自我审查，就像让考生自己批改试卷。

但多模型审查并不能取代人。四份审查意见可能互相矛盾，也可能包含噪音。哪些意见值得接受，哪些会让设计变得更糟，最终仍然需要人判断。

这也引出了最不会过时的一点：人工智能可以加速实现，却不会替人做出唯一正确的工程取舍。接口延迟、系统成本、可用性、一致性、简单性和可扩展性之间，始终存在权衡。模型可以列出选项，却无法脱离具体业务，自动给出所谓最优答案。

真正值得保留的能力有两个。一个是理解系统，知道当前最重要的目标和代价是什么。另一个是工程直觉，能察觉哪段代码可疑、哪个需求藏着坑，以及哪条审查意见只是噪音。人工智能编程的工具还会快速变化，但更轻的上下文、更严格的关键门控，以及更强的人类判断，会比任何具体工具都更持久。

## 深度解读-口播（1）

### 2026-09-30 12:00:05

用人工智能写代码，真正的难题正在变化：过去担心模型跑偏，要给它加很多约束；现在代码生成越来越快，难点反而变成了，人能不能把需求讲清楚，能不能审得过来，以及能不能判断系统里的关键取舍。

作者回顾了自己半年间的实践，得出的判断是：工具和流程可以变轻，但人的把关不能省。

先看为什么要把流程变轻。

半年前，作者参与一个系统的架构升级。需求复杂，边界情况又多。人工智能可能在某个细节上悄悄走错方向，等人发现时，已经浪费了不少时间。

当时，他的办法是增加流程约束。先充分追问需求，再执行测试驱动开发，也就是先写测试，再写实现。同时，让不同角色审查代码。这套流程确实有用：需求讨论挖出了并发写入的边界问题，代码审查也发现了竞态条件。所谓竞态条件，就是多个操作同时发生时，结果可能取决于谁先执行。这类问题，普通测试不一定容易发现。

不过，重流程也有代价。每一步都给模型塞进大量指令和背景，消耗很高。随着模型能力增强，作者发现，过去那些帮助模型稳定工作的护栏，有些反而变成了干扰注意力的噪音。

文中还引用了一项代码库测试：使用同一个模型，只更换模型外面的工具和流程框架，代码产物质量基本持平，任务成本却能相差两倍以上。

这不是说约束越少越好，而是说，约束要解决真实问题。以前必要的长篇指令，不代表现在还值得保留。

那么，减掉重框架以后，日常开发怎么做？

作者保留了一条清楚的主线：先对齐需求，再拆分任务，最后分层审查。

对齐需求，不是把一句模糊的想法直接交给模型执行。而是让模型一轮轮追问，把边界和约束问清楚。对齐之后，写成规格说明，由人先审一遍。这是第一道人工作业关口：在代码生成之前，确认要做的事情本身没有走偏。

规格说明通过后，再拆成可以独立交付的小任务。这里强调的是“垂直切片”。简单说，每个任务尽量交付一小块完整功能，而不是把所有界面、所有接口、所有数据处理分别堆成几个大任务。

随后，让多个子代理分别执行。子代理就是各自承担一项工作的人工智能执行单元。并行时，用代码仓库的独立工作目录隔离改动，减少互相干扰。每个任务内部都要跑测试、做代码审查。任务全部完成后，再审查整批改动，最后仍然由人把关。

当然，不是所有修改都需要走完整条链路。单个文件里的局部小改，如果边界清楚、验证成本低，可以直接让主代理完成。

但作者给轻流程留了两条底线：改之前，先给出简单方案，等人授权；改之后，必须跑测试。用他的话说，流程可以分级，纪律不能分级。

还有一个容易被忽略的减负办法：少写没有必要的代码。

模型经常会生成看起来很规范、实际上没什么价值的内容。比如，不必要的空值检查，明明只有一种实现却提前设计的接口，或者给常量再多包一层常量。

这些东西单独看不一定有错，但积累起来，会增加人和模型的维护负担。

作者会用专门的规则追问：这段逻辑真的需要存在吗？代码库里有没有现成的？标准库能不能解决？能不能写得更简单？

目的不是一味追求短，而是减少不必要的改动。改动越精炼，人越容易看清重点，审查也越有效。

理解这一点，就能看出作者认为最关键的新瓶颈：人的审查能力。

现在，多开几个编程代理、多建几个独立工作目录，都很容易。但人的注意力不会跟着成倍增长。按作者的体验，一个人同时处理四个会话已经比较勉强，处理八个就容易遗漏。

所以，增加代理数量，不一定能继续提高整体效率。代码写得再快，如果人看不过来，任务还是会堵在审查环节。

作者目前的应对办法，是让不同厂商的模型交叉审查同一段代码。他使用四路模型，给每一路独立、干净的上下文，再让它们执行同样的审查规则。

这样做的理由是，不同模型可能有不同的系统性盲区。一种模型漏掉的问题，另一种模型可能发现。只让写代码的模型审查自己，有点像让考生自己改卷子。

不过，交叉审查并不等于自动定案。四路模型给出的意见摆在一起，哪些是真问题，哪些只是噪音，最终还是要由人判断。模型是在帮助人发现问题，不是在替人承担责任。

这也引出了作者最后强调的事：软件工程基本功，并没有因为人工智能而失去价值。

不懂软件基础的人，也可能靠自然语言让模型完成开发。风险在于，模型可能已经替他做了一系列取舍，而他甚至不知道这些取舍发生过。

比如，要更低的接口延迟，还是更低的系统成本？要保持简单，还是提前考虑扩展？在特定条件下，一致性和可用性怎么权衡？

这些问题不是“代码能不能生成”的问题，而是“系统应该怎么设计”的问题。作者认为，模型可以提供选项，但最终判断仍然依赖人对系统、需求和约束的理解。

最值得记住的是：模型越强，越应该减少没有必要的流程和代码，而不是取消必要的纪律。人工智能能把执行速度拉得很高，但需求是否正确、审查是否有效、系统取舍是否合理，仍然决定了开发的质量。真正稀缺的，正在从写代码的速度，转向人的判断力。
