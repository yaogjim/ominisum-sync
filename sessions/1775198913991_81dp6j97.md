- Harness包含提示构建、工具、记忆、前后处理钩子和外部数据接入等非LLM本体部分
- Meta-Harness通过代理修改Python代码、运行评估、记录日志并沿帕累托前沿持续优化
- 丰富的执行级反馈比单一分数更适合做复杂LLM系统的长期信用分配与迭代

### Meta-Harness - 自动化模型框架优化，清晰解释

本文涵盖来自斯坦福大学的最新研究论文。Meta-Harness 是一个旨在实现对围绕大型语言模型（LLMs）的“框架”进行工程化的自动化的系统。

Let's go!

### First of all what is a harness?

Everything in your AI system that is not the LLM itself is a harness.

Example: Claude Opus 4.6 is the LLM. Claude Code is the harness.

这个框架位于围绕 LLM 作为支架，管理上下文如何传递给 LLM，并实际执行 LLM 想要采取的操作。

While designing harnesses, we are usually balancing a bunch of important stakeholders. If you considered this whole thing a game, then the optimal harness is a game theory optimization problem. Every actor has it's own goal and motivation, and the Nash equilibrium is when everybody wins. Let's see what the actors are and what they want:

1. 用户希望 AI 能全面、正确、快速地完成工作，并且不被限流。
2. 服务提供者希望用户向他们付款、购买他们的订阅，并以最低成本提供价值。减少输出 token、降低工具调用、最大化 KV 缓存、良好的合并等。
3. LLM 想要数据，这些数据是分布内 （即能力范围内）并且需要能够使其成功的工具。它可能讨厌不规范的提示词和不规范的工具。LLM 希望有一个平台，能够做它想做的任何事情来解决上述问题。

> 他们都需要一个 harness。 从哲学角度，harness 是连接这一切的枢纽。 这是代理型软件的 Firelink 圣地。

In less fancy terminology, the harness is the Operating System for the LLM.

#### Quick Note on the "Pareto Frontier"

![Image](https://pbs.twimg.com/media/HE5_7FBawAAQo75?format=jpg&name=large)

To optimize anything (including a harness), there are always trade-offs.

你经常同时关注多个目标。帕累托前沿是指这样一组解决方案：你无法在不使另一个目标变差的前提下改善某一个目标。

In this paper, the two objectives they care about are:

- 准确性 - 测试工具在任务中的表现有多好
- Token 成本 - 该工具使用多少上下文 Token

本文的目标是寻找一种 harness，使其处于帕累托前沿。如果不存在另一个 harness 同时既更准确又更便宜，那么该 harness 就处于帕累托前沿！

> The goal of any kind of research (including these "agent-driven researches") is to constantly push that frontier forward.

But before we could optimize all that, we should probably be more definitive about what a harness actually is.

#### The Components of a Harness

A harness includes:

1. 前钩子和后钩子： 在提示词发送给模型之前运行的输入转换（前钩子）以及模型或工具输出在发送到下游之前的转换（后钩子）
2. 提示词构建：系统提示词和用户提示词根据当前上下文线索进行创建的方式。这可能包括用户的订阅层级、活跃工具以及对应于操作模式的特殊指令（Claude Code 的“计划”或“构建”模式）。这还包括提示词的懒加载（也称为 SKILLS）
3. 工具：LLM 可以调用哪些外部工具？网络搜索？Bash？补丁编辑？正则表达式搜索？计算器？打电话给朋友？该框架不仅能让这些定义在 LLM 的上下文中可用，还能代表 LLM 实际执行这些工具并将结果返回给 LLM。
4. 内存：LLMs 是事务性的 - 它们不会记住当前请求之外的任何过去交互。你必须来回传递过去的消息以更新其内存。内存可以限制在当前会话（这个对话）、之前的会话（用户资料），或者如果经过这样设计，甚至可以是组织级别。
5. 外部数据源：这基本上要么属于预钩子和工具，要么属于内存。各种“检索逻辑”都属于这个框架——从文件系统、网站、外部数据库、过往消息，到入侵某人的 WhatsApp。

#### This is too complex, that's way too many variables to optimize!

Correct!

The cool thing about this paper is we won't be treating this as a component selection/optimization problem at all.

We will be treating this as a code optimization problem. Follow this chain on thought:

> 1\. 每一个线束都是 代码

> 2\. That code defines everything that happens around the LLM call

> 3\. The code lives in (say) a single Python file/repo

> 4\. If we change the code, the harness changes

> 5\. When harness changes, we can run an evaluation.

> 6\. When we run the evalution we know it's accuracy and token cost.

> 7\. We can then plot it on the Pareto Frontier

> 8\. We can make more changes by learning from past mistakes

BOOM. That's an optimization loop!

Not quite.

The jump from point 7 to point 8 requires hours of experimentation and debugging!

Most of us writing evals are using one or two numeric metric to define how good a harness is. While this abstraction (accuracy and total tokens) is great for us to rate the quality of a harness, it is not enough to actually optimize!

Couple of numbers cannot tell the whole story.

We need:

1. More than just metrics
2. Delegate more work to AI agents and find more time to doom-scroll on Tiktok.

Let's discuss what the ACTUAL problem really is.

### The Problem

People think that they the final form of AGI will come as a harness, not as a standalone LLM.

> Meaning, the LLM + the Harness = the Product.

The way most harnesses are currently developed is very human-centric. Engineers spend weeks "vibes-checking" prompts and manually tweaking retrieval/tool/execution logic.

The paper argues that harnesses have become too complex for humans to optimize by hand.

这是该论文中的一个关键技术见解——优化器（如 DSPy 或提示调优工具）通常过度压缩反馈。

- We look at a single score (e.g., "Accuracy: 0.8") and try to change the harness based on that.
- Meta-Harness 认为，要构建一个良好的“操作系统（OS）”，优化器需要丰富的执行级跟踪信息。它需要确切地查看 bash 命令失败的位置，或者为什么内存检索获取了无用的块。

What if could improve our harnesses based on rich prompt feedbacks generated from our current harness?

### The Meta-Harness

![Image](https://pbs.twimg.com/media/HE573p2acAA4J3I?format=jpg&name=large)

斯坦福大学的论文提出 Meta-Harness，一个自动化的“外循环”优化系统，该系统将基于 LLM 的应用程序开发视为软件工程搜索问题 。

与其由人工工程师手动优化系统，Meta-Harness 使用一个“agentic proposer”来迭代编写、测试和改进用于管理底层“基础”模型的 Python 代码。

#### The Agentic Proposer

在本文的实验中，代理提议者是 Claude Code（由 Claude 3.5 Sonnet/Opus 提供支持），该模型配备了一套用于与文件系统交互的开发者工具。

Unlike other "prompt optimizers" that might just tweak some text, the proposer has the power to:

- 重写逻辑 : 修改系统检索数据的方式、管理内存的方式，或构建多步骤提示的方式。
- 浏览历史 : 使用 grep 和 cat 等工具搜索自身之前尝试的历史记录。
- 因果分析 ： 通过查看执行跟踪（失败运行的精确输入和输出），代理可以推断出变更为何不起作用，并相应调整其策略。

提议者（Claude Code）在一个类似 Git 的代码仓库中操作，该仓库维护了完整的搜索历史。文件系统结构经过精心设计，可通过标准终端工具进行搜索：

#### Filesystem-as-Feedback

Meta-Harness 使用一个 文件系统作为一个 外部数据库 来记录它的所有实验 .

这是完整的先前经验历史（

[@yoonholeee](https://x.com/@yoonholeee) 本人称，“这个目录会变得非常大”）

For every candidate the harness created, the system logs:

1. 该线束的完整源代码 。
2. 性能评分 （例如，准确率、代币成本）。
3. 执行跟踪 ，包括原始模型提示、工具调用和状态更新。

This allows the proposer to "read broadly across prior code and logs" to identify successful patterns and avoid repeating past mistakes.

#### The Optimization Loop

![Image](https://pbs.twimg.com/media/HE58FrGbYAAX_-L?format=jpg&name=large)

> The authors find that unrestricted access to all previous history is essential, because the dependencies are so long-horizon.

> Previous text optimization loops that only see rewards/summaries/previous attempts discard important information and underperform here.

The system follows a continuous cycle:

1. 检查 : 提议者在文件系统中搜索先前的结果和痕迹。
2. 诊断 : 它会分析故障模式（例如：“检索步骤获取了不相关的文档”）。
3. 提案 : 它编写了新版本的测试框架代码（通常是单文件 Python 程序）
4. 评估: 系统在任务分布 X 上运行新的测试框架，并记录奖励 r(τ,x)
5. 更新 : 结果被添加回文件系统，循环继续。

#### Search Objectives

Meta-Harness 可以同时优化多个目标（不仅仅是任务准确率）。如果在准确率和上下文成本 （使用的 token 数量）之间存在权衡，系统会识别出帕累托前沿， 即提供两者最佳平衡的解决方案集合。

### Case Studies They Did

![Image](https://pbs.twimg.com/media/HE58UwpaMAAv9NZ?format=jpg&name=large)

They did a bunch, let's look at two!

1: Online Text Classification

这里的目标是高效管理不断增长的带标签示例上下文。Meta-Harness 与两种最先进的上下文管理系统在三个数据集上进行了比较：USPTO-50k（化学）、Symptom2Disease（医学） 和 LawBench（法律）

核心发现是关于你如何查询自己的记忆 。该系统提出了一个单一的、结构丰富的调用，它能完成三件事：

1. Label Primer: Lists all valid output labels upfront so the model sees the full answer space before any examples.
2. Coverage Block: Retrieves one query-relevant example per label, ensuring every class is represented.
3. Contrastive Block: Builds pairs of highly similar examples with different labels using TF-IDF, sharpening local decision boundaries around the current query.

![Image](https://pbs.twimg.com/media/HE58cRvasAAkSxA?format=jpg&name=large)

Experiment 2: Terminal-Bench 2

We saw an experiment that was a "narrow" task. Now let's see a more general task. Terminal Bench.

什么是终端基准测试（Terminal Bench）？TerminalBench-2 是一个针对 89 项挑战性任务的基准测试，这些任务需要长期视野、完全自主执行。例如搭建服务器、组装蛋白质结构、运行渲染流水线以及解决加密挑战等。

Meta Harness does not make a harness from scratch. It starts from two baselines: the Terminus 2, and the Terminus-KIRA.

This iterative refinement that happens read like a story book, they have given a full descriptive breakdown of each step of the iterative process. The basic gist is that it tried and failed to beat the benchmark for multiple iterations and eventually tried a "one-shot environment snapshot" prompt that became the first candidate to beat the baseline.

![Image](https://pbs.twimg.com/media/HE58oCZaMAA4EVF?format=jpg&name=large)

Basically the original harness spent a few tool calls to get environmental descriptions of the system. Meta-Harness changed the code so that the initial LLM call itself already contains snapshots that the LLM regularly queries for, things like the working directory, a listing of /app (truncated to 20 entries for large directories), available programming languages and their versions, installed package managers (pip, apt-get), and available memory. This eliminates the 2–4 exploratory turns that agents typically spend discovering what tools and files are available, allowing the model to begin productive work immediately!

Without the Meta-Harness having explicit access to the logs and experiment traces, this optimization would simply not be possible at all, since the optimizer would never know how the internal tools operate.

### Practical Implementation Tips (by the authors)

![Image](https://pbs.twimg.com/media/HE57zFnasAEFlL1?format=jpg&name=large)

The coolest part of the paper was a "practical implementation tips" section. I won't go through all of them, but it is a short section with a few pointers that would benefit you greatly if you are developing harnesses yourself.

1\. Write a Good Skill (Most Important Lever)

The skill text is the primary steering interface for the proposer. It should specify what is forbidden, what artifacts to produce, and what objective to optimize.

Run a few short debug runs (3–5 iterations) specifically to refine the skill before committing to a full run.

2\. Start With a Baseline That Struggles

先写一个简单的基准（例如，少样本提示）。然后将搜索集保持得足够小，使得每次运行大约进行 \~50 次完整评估——在你为提案代理进行原型设计时，这是一种快速、有区分性的评估方式。

3\. Log Everything in a Navigable Format

Use machine-readable formats like JSON, structure the logs herirarchically.

4\. 构建一个小型命令行工具来处理日志 这使得优化器能够轻松地运行快速查询以了解实验的全局状态。CLI 工具可以：

- List the Pareto frontier of best harnesses
- Show top-k candidates
- Diff code and results between pairs of runs

5\. Warm-starts

作者还指出，如果存在离线经验（其他模型部署、已解决的语料库），将其转换为相同的目录结构以热启动探索

6\. Automate Evaluation Outside the Proposer

Running evals is too simple to delegate to the proposer. Use a separate harness that scores candidates and writes results to the filesystem

### So... it's autoresearch for harnesses?

I think the ideas are very similar personally. My main takeaway is actually the simplicity of both the approaches. Recently Meta AI also published work on DGM-H (Darwin Godel Hyperagents) which I also wrote a paper review on (

[https://x.com/neural\_avb/status/2037526862964969583?s=20](https://x.com/neural_avb/status/2037526862964969583?s=20)) and I must say that this approach feels a lot simpler to execute.

The DGM family of research relies on recursive search, node-splitting, and optimizing any task from scratch by altering code. This system is much simpler and their tasks have been to improve existing systems.

While the architecture is simple, the computational space is not. Remember we keep the entire database of experiments in the filesystem and iterate on it (DGM discards solutions). So yeah, that stuff can get pretty token heavy. Maybe Claude Code isn't the best "harness" to use as the agentic proposer. Seeing Dr. Khattab and team also work on RLMs, I won't be surprised if they try to bind meta-harnesses and RLMs in holy matrimony later this year.

## 通俗精炼（1）

### 2026-04-03 06:46:31

#### Meta-Harness 核心总结

##### 它是什么
Meta-Harness 是斯坦福提出的一套自动优化 LLM“框架层”的方法。  
这里的“框架（harness）”指的不是模型本身，而是包在模型外面的整套运行系统，比如提示词构造、工具调用、记忆管理、检索逻辑、前后处理等。可以理解为：**LLM 是大脑，harness 是操作系统**。

##### 它想解决什么问题
现在很多 AI 产品的效果，往往不只取决于模型本身，更取决于外层框架设计得好不好。  
问题是，这一层太复杂，靠人手工调 prompt、改检索、试工具链，效率低、反馈慢，而且很难处理长期依赖和复杂因果关系。

Meta-Harness 的核心目标就是：**把“调框架”这件事自动化**，让 AI 自己不断改代码、跑评测、读日志、总结经验，再继续优化。

##### 核心思路
它不把优化看成“挑选组件”，而是看成一个**代码搜索与迭代优化问题**：

1. harness 本质上是一段代码；
2. 改代码，就等于改框架；
3. 改完后跑评测，得到效果和成本；
4. 把结果记录下来；
5. 再让 AI 根据历史经验继续改下一版。

这样就形成了一个闭环：**检查 → 诊断 → 提案 → 评估 → 记录 → 再优化**。

##### 为什么它比普通 prompt 优化更强
传统优化器往往只看几个分数，比如准确率、token 成本。  
但 Meta-Harness 认为，只看分数远远不够，因为你不知道到底是哪一步出了问题。

它更强调**丰富的执行级反馈**，比如：
- 哪条 bash 命令失败了；
- 哪次检索拿到了无关内容；
- 哪个工具调用浪费了步骤；
- 哪段上下文传递方式影响了结果。

也就是说，它优化的不只是“结果”，更是**过程细节**。

##### 它是怎么工作的
Meta-Harness 会把每次实验都完整记录到文件系统里，包括：

- 候选 harness 的源代码；
- 评测分数；
- 执行轨迹；
- 提示词、工具调用、状态变化等信息。

然后由一个“代理提议者”去读取这些历史记录，分析失败原因，再生成新的代码版本。  
论文实验里，这个提议者用的是带开发工具能力的 Claude Code。

这相当于给 AI 一个“可搜索的实验记忆库”，让它不只是试错，而是**基于历史经验持续学习**。

##### 优化目标是什么
论文重点优化两个指标：

- **准确性**：任务完成得好不好；
- **Token 成本**：上下文和调用消耗贵不贵。

他们用“帕累托前沿”来衡量：  
如果一个方案不能在“更准”的同时还“更便宜”地被另一个方案打败，那它就是优秀解。

所以 Meta-Harness 不是只追求更强，而是追求**性能与成本的更优平衡**。

##### 两个典型实验
###### 1. 在线文本分类
在文本分类任务里，Meta-Harness 优化的是“如何管理越来越多的示例上下文”。  
它最后找到一种更有效的记忆查询方式，把标签空间、覆盖样本和对比样本结构化组织起来，从而提升分类效果。

###### 2. TerminalBench-2
这是更复杂的长程自主任务，比如搭服务器、跑渲染、解加密题。  
Meta-Harness 并不是从零开始，而是在已有 baseline 上持续优化。

一个关键突破是：  
它发现 agent 往往要花 2-4 轮先探索环境，于是直接把目录、语言版本、包管理器、内存等环境快照，提前塞进首次 prompt。  
结果是模型一开始就能进入工作状态，省掉了很多无效探索步骤。

##### 这篇文章最重要的启发
###### 1. AI 产品的竞争重点，正在从模型转向框架
未来很多能力差异，不一定来自更强的基础模型，而是来自**更好的 harness**。

###### 2. 优化框架，本质上是软件工程问题
不是单纯“调 prompt”，而是一个要看代码、日志、执行轨迹、历史实验的系统工程问题。

###### 3. 自动化优化的关键不是评分，而是可追溯反馈
只有把实验过程完整记录下来，AI 才能真正理解“为什么有效、为什么失败”。

##### 实践建议
作者给出的经验也很实用，核心包括：

- 先写一个简单但不够强的 baseline，便于快速迭代；
- 日志要完整、结构化、可搜索；
- 最好配一个 CLI 工具，方便查看最优候选、对比代码和结果；
- 评测流程要独立自动化，不要让提议代理自己管评测；
- 可以用历史经验做 warm start，加快优化。

##### 一句话结论
Meta-Harness 的本质，是让 AI 不再只是“调用模型”，而是开始**自动改进模型外部的整套使用方式**。  
它代表了一种重要方向：**未来 AI 系统的进化，可能更多发生在“模型之外”的框架层。**

## 结构化（1）

### 2026-04-03 06:51:12

#### Meta-Harness 的主旨

Meta-Harness 这篇研究的核心是在回答一个很实际的问题：**如何不靠人工反复试错，而是让系统自己持续优化“LLM 外围框架（harness）”**。  
作者认为，真正决定 AI 产品效果的，不只是模型本身，而是 **LLM + harness** 这个整体；而 Meta-Harness 提供了一种把这件事自动化的方法。

##### 1. 什么是 harness，为什么它重要

- 文中先定义了 **harness**：凡是 AI 系统里**不属于 LLM 本体**、但围绕 LLM 运行的一切，都算 harness。  
- 例如：**Claude Opus 4.6 是 LLM，Claude Code 就是 harness**。
- 它负责做的事情包括：
  - 管理上下文如何传给模型
  - 决定提示词怎么构造
  - 调用哪些工具
  - 怎样保存和检索记忆
  - 如何连接文件系统、网站、数据库等外部数据源
- 作者用通俗比喻说，harness 就像 **LLM 的操作系统（Operating System）**。

**关键点：**
- 用户希望 AI **又快、又准、不中断**。
- 服务商希望 **降低成本**，比如减少输出 token、减少工具调用、优化缓存。
- LLM 希望拿到 **更规范、分布内、可执行的输入和工具环境**。
- harness 就是协调这些目标的“中枢”。

##### 2. 论文想优化什么：准确率和 token 成本

- 文中强调，优化 harness 本质上是一个**多目标优化问题**。
- 这篇论文主要关心两个指标：
  - **准确性**：任务完成得有多好
  - **Token 成本**：用了多少上下文 token
- 作者借用了 **帕累托前沿（Pareto Frontier）** 的概念：
  - 如果一个 harness 不存在“另一个方案既更准又更便宜”，那它就在帕累托前沿上。

**通俗理解：**
- 比如 A 方案准确率更高但更贵，B 方案更省 token 但略差一点。
- 那么研究的目标不是只找“最强”或“最省”的单点，而是找到一组**性价比最优解**。

##### 3. 为什么人工很难继续优化 harness

- 作者认为，当前大多数 harness 的开发方式太依赖人工：
  - 工程师手动改 prompt
  - 手动调检索逻辑
  - 手动试工具调用策略
- 问题在于：现代 harness 已经很复杂，**靠人“凭感觉”调参数越来越不够用了**。
- 尤其关键的一点是：很多现有优化器把反馈压缩得过头了。
  - 例如只看一个分数：`Accuracy = 0.8`
- 但单一分数无法告诉你：
  - 是哪一步失败了
  - 哪个 bash 命令报错
  - 哪次检索拿到了无关内容
  - 为什么记忆模块没有帮上忙

**核心观点：**
- 想真正优化 harness，不能只看结果分数，必须看**执行过程中的丰富轨迹信息**。

##### 4. Meta-Harness 的核心思路：把 harness 优化当成“代码优化”

- 这篇论文最巧妙的地方，是**不把 harness 当作零件拼装问题**，而是直接把它看成一个**代码优化问题**。
- 推理链条非常直接：
  1. 每个 harness 本质上都是代码
  2. 这些代码定义了 LLM 调用前后发生的一切
  3. 代码通常就在一个 Python 文件或一个 repo 里
  4. 改代码，就等于改 harness
  5. 改完后可以跑评测
  6. 评测会得到准确率和 token 成本
  7. 再根据结果继续改进

**关键点：**
- 这就形成了一个自动优化闭环。
- 但作者也强调：从“拿到分数”到“知道下一步该怎么改”，中间需要大量实验和诊断，因此必须保留完整历史，而不是只留几个数字。

##### 5. Meta-Harness 是怎么工作的

###### 5.1 Agentic Proposer：负责提出修改方案的代理

- Meta-Harness 的“外循环”优化器里，有一个核心角色叫 **agentic proposer**。
- 在论文实验中，这个 proposer 使用的是 **Claude Code**，底层模型是 **Claude 3.5 Sonnet/Opus**。
- 它不是简单改几句 prompt，而是能直接用开发者工具操作代码仓库，做这些事：
  - **重写逻辑**：改检索、记忆、多步提示构造等
  - **浏览历史**：用 `grep`、`cat` 等工具查看过去尝试
  - **因果分析**：根据失败轨迹推断为什么没成功，再调整策略

**重点：**
- 它优化的对象不是一句提示词，而是整个 Python harness 代码。

###### 5.2 Filesystem-as-Feedback：把文件系统当“实验数据库”

- Meta-Harness 的另一个核心设计，是把**文件系统当作外部数据库**。
- 系统会为每个候选 harness 记录：
  - 完整源代码
  - 性能分数（如准确率、token 成本）
  - 执行轨迹（原始提示、工具调用、状态更新等）
- 这样 proposer 就能跨很多轮历史去搜索和分析，而不是只看最新一次结果。

**作者特别强调：**
- 由于依赖关系是**长周期的**，所以允许访问**全部历史记录**很重要。
- 如果只看“奖励值、摘要、前几次尝试”，会丢失太多关键信息，效果明显更差。

###### 5.3 优化循环

Meta-Harness 的循环可以概括为：

- **检查**：搜索历史结果和运行痕迹
- **诊断**：找失败模式，例如“检索出的文档不相关”
- **提案**：写出新的 harness 代码版本
- **评估**：在任务分布上运行并得到奖励 `r(τ, x)`
- **更新**：把结果写回文件系统，进入下一轮

##### 6. 论文中的两个重要实验

##### 6.1 实验一：在线文本分类

- 这个任务关注的是：**当可用示例越来越多时，如何高效管理上下文中的带标签样本**。
- Meta-Harness 与两个最先进的上下文管理系统比较，覆盖了三个数据集：
  - **USPTO-50k**（化学）
  - **Symptom2Disease**（医学）
  - **LawBench**（法律）

###### 这个实验里最重要的发现

作者发现，**查询“自己的记忆”方式非常关键**。系统最终提出了一个结构化调用，一次完成三件事：

- **Label Primer**：先把所有合法标签完整列出来，让模型先看到完整答案空间
- **Coverage Block**：为每个标签都检索一个与当前查询相关的样本，确保每个类别都被覆盖
- **Contrastive Block**：用 **TF-IDF** 找出“文本很像但标签不同”的样本对，帮助模型在边界附近做更细的区分

**通俗例子：**
- 假设要判断一个医学描述属于哪种疾病。
- 只给几个相似案例，模型可能混淆。
- 但如果同时：
  - 先告诉它有哪些疾病标签，
  - 每种标签都给一个代表样本，
  - 再给几组“长得很像但诊断不同”的对比样本，
- 那么模型更容易分清细微差别。

##### 6.2 实验二：TerminalBench-2

- 这是一个更通用、更难的任务基准。
- **TerminalBench-2** 包含 **89 个高难度任务**，需要长期规划和完全自主执行。
- 文中举的任务类型包括：
  - 搭建服务器
  - 组装蛋白质结构
  - 运行渲染流水线
  - 解决密码学挑战

###### 它是怎么优化的

- Meta-Harness 不是从零开始，而是从两个 baseline 出发：
  - **Terminus 2**
  - **Terminus-KIRA**
- 经过多轮迭代后，它尝试出一个很关键的改动：  
  **“one-shot environment snapshot” 提示方式**，并成为第一个超过 baseline 的候选方案。

###### 这个改动具体做了什么

- 原本的 harness 会先花几轮工具调用，去探索环境信息。
- Meta-Harness 改成：**在第一次 LLM 调用时，就把常用环境快照直接放进上下文**。
- 这些快照包括：
  - 当前工作目录
  - `/app` 目录列表（大目录时截断到 **20 项**）
  - 可用编程语言及其版本
  - 已安装包管理器（如 `pip`、`apt-get`）
  - 可用内存

**效果：**
- 直接省掉 agent 通常要花的 **2–4 轮探索性回合**。
- 模型一上来就能开始干正事，而不是先问“这里有什么工具、有哪些文件”。

**论文要表达的重点：**
- 如果没有完整日志和实验轨迹，优化器根本不知道内部工具是如何工作的，也就不可能发现这种改进。

##### 7. 作者给出的实践建议

论文最后给出了一组很实用的工程建议，适合自己做 harness 的人参考。

###### 7.1 写好 skill 文本，这是最重要的杠杆

- `skill` 文本是 proposer 的主要引导接口。
- 需要清楚写明：
  - 什么不能做
  - 要产出什么结果
  - 优化目标是什么
- 作者建议先跑 **3–5 次短调试迭代** 来打磨 skill，再开始正式大规模搜索。

###### 7.2 从一个“会失败的 baseline”开始

- 先写一个简单 baseline，比如少样本提示。
- 再把搜索集控制得足够小，使每轮大约进行 **约 50 次完整评估**。
- 这样在原型阶段能更快看出差异。

###### 7.3 把日志记成可检索格式

- 建议使用 **JSON** 等机器可读格式。
- 日志要有层级结构，方便程序和代理检索。

###### 7.4 做一个小型 CLI 工具管理日志

这个命令行工具可以帮助优化器快速了解整体实验状态，例如：

- 列出帕累托前沿上的最佳 harness
- 查看 top-k 候选
- 比较两次运行的代码和结果差异

###### 7.5 利用 warm-start

- 如果已有离线经验，比如别的模型部署记录或历史问题语料，可以转成同样目录结构，作为热启动材料。

###### 7.6 让评估独立于 proposer

- 作者认为跑评测这件事太简单，不值得交给 proposer。
- 更合理的方式是：**单独用一个 harness 来打分并把结果写回文件系统**。

##### 8. 文章最后的评价与局限

- 作者认为，Meta-Harness 的思路和“自动化研究”很像，但它的实现比一些更复杂的方法（比如文中提到的 **DGM-H / Darwin Godel Hyperagents**）更直接。
- 它不追求从零造一切，而是专注于**改进已有系统**。
- 不过，虽然架构简单，**计算代价并不小**：
  - 因为它会保留完整实验数据库
  - 不断在整个历史上迭代
  - 所以 token 开销可能会很高

**作者的一个现实判断：**
- 这种方法很有工程价值，但在大规模使用时，成本和历史数据管理会成为实际挑战。

##### 9. 一句话总结它的价值

- Meta-Harness 最值得记住的地方是：  
  **它把“优化 LLM 应用框架”从人工调参，变成了基于代码、日志和完整实验历史的自动化搜索问题。**
- 这意味着未来 AI 产品的竞争力，很可能越来越取决于：**谁能更快、更系统地优化自己的 harness，而不只是拥有更强的底层模型。**
