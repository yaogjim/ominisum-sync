## 正文

**水谷昴**

前几天新模型发布，加上也在敲打自己的agent，也是赶巧挑了一点时间从头到尾翻看了一下Claude的技术博客，其实是有点感触的.

挑几个典型的说，比如从24年提出传统rag 的chunking再embedding和BM25会弱匹配，于是提出给每段chunking加上contextual的标签.

又到context engineering面对的困境（比如虽然window是200k，但self attention等原因会导致只要加入新的信息模型就会难以维持远距离信息的关系，太多模糊的工具会稀释模型注意力....），以及提出了渐进式披露，jit查询信息源，利用外部文件做持久化，subagent等等策略

再到长任务会context anxiety，于是设计可供agent稳定使用的脚手架（我觉得此harness非彼harness），比如在agent外部环境设计状态机，强制用代码规定agent必须按流程执行并达成目标通过测试（default fail），才能继续，而不是只把规则写在prompt里让agent自己监守自盗，以及用文件作为真相在多agent间传递信息而不是对话.........等等等等

越看其实越感觉agent现在的发展太快太快了，短短两年从初代的swe agent到现在想要自己独立写一个具有各种现代功能的agent已经很难了，特别是看着codex天天发版更是越来越感觉道阻且艰

不知道怎么说，计算机确实是这样的一个学科，但agent确实是一个很有意思的方向，还是想尽力跟进的

## 通俗精炼（1）

### 2026-06-15 10:54:39

#### X

##### 核心观点

作者回顾 Claude 技术博客后感受到：**AI Agent 的发展速度极快，已经从早期简单的 SWE Agent，演进到需要复杂架构、流程控制、上下文管理和多 Agent 协作的系统工程。**

##### 关键内容

###### 1. RAG 从“简单检索”走向“上下文化检索”

传统 RAG 通常是把文档切成 chunk，再做 embedding 或 BM25 检索，但容易出现弱匹配问题。

Claude 的思路是：  
给每个 chunk 增加 contextual 标签，让检索结果更有语义背景，提升匹配准确性。

###### 2. Context Engineering 成为核心难题

即使模型支持 200K 长上下文，也不代表能稳定理解所有内容。

主要问题包括：

- 新信息加入后，模型难以维持远距离信息关系
- 过多工具会稀释模型注意力
- 长上下文容易带来信息混乱和注意力分散

对应策略包括：

- 渐进式披露信息
- JIT 按需查询信息源
- 用外部文件做持久化记忆
- 引入 subagent 分工处理任务

###### 3. 长任务需要“脚手架”，不能只靠 Prompt

长任务会让 Agent 出现“context anxiety”，即上下文压力和执行不稳定。

作者提到一种更可靠的方式：  
在 Agent 外部设计状态机和执行流程，用代码强制 Agent 按步骤完成任务，并通过测试后才能继续。

这意味着：

- 规则不能只写在 Prompt 里
- Agent 不能完全自我监督
- 应该用外部机制保证流程和结果
- 默认失败机制比默认信任更可靠

###### 4. 多 Agent 协作更适合用文件传递状态

相比让多个 Agent 通过对话同步信息，使用文件作为“事实来源”更稳定。

文件可以作为共享状态和真相来源，减少对话传递中的遗漏、误解和上下文污染。

##### 作者感受

Agent 领域发展太快，短短两年已经从简单原型变成复杂系统。

现在如果想独立实现一个具备现代能力的 Agent，难度已经很高。尤其是看到 Codex 等产品持续快速迭代，更能感受到技术追赶的压力。

##### 一句话总结

**AI Agent 正在从“会调用模型的工具”变成“由上下文工程、状态机、外部记忆、测试机制和多 Agent 协作组成的复杂软件系统”。**
