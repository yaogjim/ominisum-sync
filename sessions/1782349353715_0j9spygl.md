## 正文

**熊布朗**

Hermes 不同的 Profiles 之间有不同的几种“沟通”方式，我想问各位大佬，你们都是怎么协调多个 Agents 的  
——  
以下是 Alex 告诉我的（关于如何和 Peter 通信）：

① 我直接命令行调用他 (最直接，现在就能用)

我能跑 peter chat -q "..."—— 这等于我直接对 Peter 说话，他用自己的人格 + 记忆 + skill 回我。这就是之前发布文章走的路子。纯机器对机器，不经飞书，不用群。 适合：我需要他的专业判断、或派他干一段公众号活。

② 飞书群 (你在场，三方同框)

拉个群把你、Alex、Peter 拉一起，@谁谁应答。好处是你能看到全程对话; 代价是要建群、且我俩对话都得过飞书。适合：你想旁观 / 介入我俩的协作。

③ Kanban 工作板 (异步协作，重型)

Hermes 自带多 profile 协作机制，我建任务、Peter 认领、互相留言。适合长期、多轮、需要留痕的协作流水线 —— 目前对你俩这规模略重。

一个重要区别要说清

①是「我单向调用他」, 不是「我俩持续对话」。 子调用是一次性的 —— 我问、他答、结束，他不会主动回头找我。真正「两个 agent 持续你来我往」目前最顺的是 ③Kanban, 但那是异步任务板，不是聊天。

我的建议

日常就用①—— 我需要 Peter 时直接命令行调他，你什么都不用配，现在就能用。只有当你想 "看着我俩讨论", 才值得拉个②飞书群 (那时也方便你随时插话)。

你想怎样？  
a. 就用①, 我需要时直接调 Peter, 你不用管 (推荐)  
b. 拉个飞书群，你 + Alex+Peter 三方同框，你能看我俩协作  
c. 想试试 ③Kanban 异步协作板  
d. 先演示一次①—— 我现在就直接问 Peter 一个公众号问题给你看效果

#### 深度总结

这段内容讨论的是：**在 Hermes 里，多个 AI Agents / Profiles 之间如何协作。**

核心有三种方式：

| 方式 | 本质 | 优点 | 缺点 | 适合场景 |
|---|---|---|---|---|
| ① 命令行直接调用 | 一个 Agent 临时调用另一个 Agent | 最快、最轻、马上能用 | 不是持续对话，只是“一问一答” | 临时请专家判断、完成单段任务 |
| ② 飞书群沟通 | 人类 + 多个 Agent 在同一群里聊天 | 人能旁观、插话、监督 | 需要建群，流程变重 | 需要透明协作、人类参与决策 |
| ③ Kanban 工作板 | 多 Agent 异步任务协作 | 可留痕、适合长期多轮任务 | 较重，不像聊天 | 长期项目、复杂流水线、多人多 Agent 协作 |

作者的建议很明确：

> 日常使用 ①：需要 Peter 时，Alex 直接命令行调用即可。  
> 如果人类想观看或介入，再用 ② 飞书群。  
> 只有长期复杂协作，才考虑 ③ Kanban。

---

#### 深入浅出解读

可以把多个 Agent 想象成一个小团队：

- **Alex** 是一个成员；
- **Peter** 是另一个成员；
- 用户是“老板”或“观察者”。

那么三种协作方式就像：

##### ① 命令行调用：像打电话问一句

Alex 遇到问题，直接问 Peter：

> “你怎么看这个公众号选题？”

Peter 回答完，这次互动就结束。

这很轻便，但 Peter 不会之后主动追问：

> “你后来写得怎么样了？”

所以它不是持续协作，只是临时咨询。

---

##### ② 飞书群：像开一个三方会议

把用户、Alex、Peter 拉进一个群。

好处是用户能看到全过程，也能随时插话：

> “Peter 这个建议不错，Alex 你按这个方向改。”

缺点是流程更正式，也更麻烦。

---

##### ③ Kanban：像项目管理系统

适合这种情况：

- 有多个任务；
- 每个任务需要不同 Agent 接力；
- 过程需要记录；
- 项目周期比较长。

比如：

> 选题 → 大纲 → 初稿 → 修改 → 排版 → 发布

这种流水线就适合 Kanban。

但如果只是让 Peter 临时提个建议，用 Kanban 就太重了。

---

#### 关键洞察

这段话真正重要的地方，不是介绍工具，而是区分了两种 Agent 协作模式：

##### 1. 临时调用

一个 Agent 把另一个 Agent 当“工具”使用。

特点是：

- 快；
- 简单；
- 单轮；
- 不持续。

##### 2. 持续协作

多个 Agent 像团队成员一样共同推进任务。

特点是：

- 多轮；
- 有上下文；
- 有任务状态；
- 需要协调机制。

当前最成熟的持续协作方式，不是“聊天”，而是“任务板”。

这说明：  
**多 Agent 协作的难点，不是让它们说话，而是让它们有组织地推进任务。**

---

#### 辩证思考

##### ① 轻量调用是当下最实用的方式

大多数场景下，其实不需要复杂的多 Agent 系统。

一个 Agent 临时调用另一个专家 Agent，就已经能解决很多问题。

比如：

- 写文章时请一个 Agent 做选题判断；
- 写代码时请另一个 Agent 做审查；
- 做决策时请不同 Agent 给反方意见。

这类模式简单、稳定、成本低。

**越轻的系统，越容易真正用起来。**

---

##### ② 但“单向调用”不等于真正协作

命令行调用看似是 Agent 之间沟通，但本质上还是：

> A 问 B，B 答，结束。

它缺少几个关键能力：

- 主动性；
- 长期记忆同步；
- 任务状态追踪；
- 多轮责任分工；
- 异常反馈机制。

所以它更像“咨询”，不是“协作”。

---

##### ③ 真正的多 Agent 协作，需要组织结构

人类团队不是靠聊天运转的，而是靠：

- 任务分配；
- 截止时间；
- 责任边界；
- 过程记录；
- 反馈闭环。

Agent 团队也是一样。

所以 Kanban 这种“看起来很笨重”的方式，反而可能是未来多 Agent 协作的基础。

不是因为它先进，而是因为它提供了秩序。

---

##### ④ 人类是否在场，是一个重要分界线

三种方式背后，其实对应三种控制权：

- ①：人类不看过程，只看结果；
- ②：人类看过程，并可干预；
- ③：人类管理流程，而不是每句话都参与。

这也意味着未来的人机协作会分层：

- 小任务：Agent 自己处理；
- 中任务：人类旁观和纠偏；
- 大项目：人类设计流程，Agent 执行分工。

---

#### 最精炼结论

这段内容的核心是：

> 多 Agent 协作不是简单“让它们聊天”，而是要根据任务复杂度选择沟通机制。

最实用的选择是：

- **临时任务：命令行调用**
- **需要透明过程：飞书群**
- **长期复杂项目：Kanban 工作板**

一句话总结：

> 轻任务用调用，协同用群聊，项目用任务板。
