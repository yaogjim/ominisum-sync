marknative

**一个原生的 Markdown 渲染引擎，可生成分页的 PNG/SVG 文档——无需浏览器、无需 Chromium、无需 DOM。**

📖 **[文档](https://liyown.github.io/marknative/)** — 指南 · 展示 · API 参考

大多数 Markdown 渲染流程都依赖浏览器：

```
Markdown → HTML → DOM/CSS → browser layout → screenshot
```

`marknative` 采用了不同的路径。它直接将 Markdown 解析为带类型的文档模型，运行其自主的块级和行内布局引擎，将结果分页为固定大小的页面，并使用原生的 2D 画布 API 绘制每个页面。

结果是确定性的、服务器可渲染的，并且完全无头。

#### Quick Start

```
import { renderMarkdown } from 'marknative'

const pages = await renderMarkdown(`
# Hello, marknative

A native Markdown rendering engine that produces **paginated PNG pages**
without a browser.

- CommonMark + GFM support
- Deterministic layout and pagination
- PNG and SVG output
`)

console.log(`Rendered ${pages.length} page(s)`)

for (const [i, page] of pages.entries()) {
  // page.format === 'png'
  // page.data   === Buffer
  await Bun.write(`page-${i + 1}.png`, page.data)
}
```

#### API

##### renderMarkdown(markdown, options?)

解析、排版、分页并绘制一个 Markdown 文档。每页返回一个输出条目。

```
function renderMarkdown(
  markdown: string,
  options?: {
    format?: 'png' | 'svg'   // default: 'png'
    painter?: Painter         // override the paint backend
  },
): Promise<RenderPage[]>
```

**Return type:**

```
type RenderPage =
  | { format: 'png'; data: Buffer;  page: PaintPage }
  | { format: 'svg'; data: string;  page: PaintPage }
```

每个条目同时携带原始输出（ `data` ）和完全解析的页面布局（ `page` ），这样您就可以在不重新渲染的情况下检查片段位置。

---

##### parseMarkdown(markdown)

将 Markdown 源解析为 `marknative` 的内部文档模型，无需执行布局或绘制。适用于检查文档结构或构建自定义渲染器。

```
function parseMarkdown(markdown: string): MarkdownDocument
```

---

##### defaultTheme

内置的主题对象。页面大小为 1080 × 1440 像素（竖版卡片比例）。字体大小、行高、边距和区块间距均在此处定义。

```
import { defaultTheme } from 'marknative'

console.log(defaultTheme.page)
// { width: 1080, height: 1440, margin: { top: 80, right: 72, bottom: 80, left: 72 } }
```

#### Rendering Pipeline

```
Markdown source
  │
  ▼
CommonMark + GFM AST          (micromark, mdast-util-from-markdown)
  │
  ▼
MarkdownDocument               internal typed document model
  │
  ▼
BlockLayoutFragment[]          block + inline layout engine
  │
  ▼
Page[]                         paginator — slices fragments into fixed-height pages
  │
  ▼
PNG Buffer / SVG string        skia-canvas paint backend
```

每个阶段都可独立测试。布局引擎不依赖于绘制后端，且绘制后端接受一个纯数据结构——它不会重新运行布局。

## 通俗精炼（1）

#### marknative：不靠浏览器的 Markdown 渲染引擎

##### 它是什么
`marknative`是一个原生 Markdown 渲染引擎，能直接把 Markdown 生成分页的`PNG`或`SVG`。  
最大的特点是：**不依赖浏览器、不需要 Chromium、也不走 DOM 渲染链路**，更适合服务端和批量处理场景。

##### 核心价值
传统方案通常是：`Markdown → HTML → DOM/CSS → 浏览器排版 → 截图`。  
而`marknative`走的是另一条路：**Markdown 解析后，直接进入自研排版引擎，再输出图片**。

这样带来几个明显优势：

- **结果稳定**：分页和布局更可控，跨运行结果一致
- **更轻量**：不需要浏览器环境，部署成本低
- **更高效**：适合服务端批量渲染
- **更易集成**：可直接作为库嵌入项目

##### 它怎么工作
它的处理流程可以理解为 5 步：

###### 1. 解析 Markdown
基于 CommonMark 和 GFM，把 Markdown 转成结构化文档模型。

###### 2. 自主排版
用自己的块级和行内布局引擎计算内容位置，而不是依赖浏览器布局。

###### 3. 固定分页
将内容切成固定尺寸的页面，适合文档卡片、长图、多页图文输出。

###### 4. 原生绘制
通过`skia-canvas`直接绘制成 PNG 或 SVG。

###### 5. 可测试、可拆分
解析、排版、分页、绘制是分层设计，每一层都能单独测试和替换。

##### 支持能力
目前支持的 Markdown 能力已经比较完整，包括：

- 标题、段落、加粗、斜体、行内代码
- 链接、代码块、引用、分割线
- 有序 / 无序列表、嵌套列表
- 图片（块级和行内）
- GFM 扩展：表格、任务列表、删除线

也就是说，**常见技术文档和内容卡片场景基本够用**。

##### 适合什么场景
这个项目特别适合以下需求：

- **服务端生成文档长图**
- **将 Markdown 批量转为图片素材**
- **知识卡片、海报式内容输出**
- **无需浏览器依赖的渲染服务**
- **需要稳定分页结果的内容生产系统**

如果你关心的是 “渲染结果稳定、部署轻、批量化”，它的价值会很明显。

##### 产品视角的意义
从产品和工程结合的角度看，`marknative`解决的不是 “Markdown 能不能渲染”，而是：  
**能否以更低成本、更高确定性，把 Markdown 变成可交付的视觉内容。**

这意味着它更像一个**内容基础设施组件**，而不只是一个渲染工具。  
对于 AI 内容生成、文档自动化、知识产品化、内容分发链路，都有潜在价值。

##### 当前不足与后续方向
项目还在持续完善，后续重点包括：

- 提升英文段落换行质量
- 优化中英文混排和 CJK 换行
- 提升代码块、表格渲染效果
- 开放主题和页面配置 API
- 支持自定义字体
- 补全更多 GFM 能力（如脚注、自动链接）

##### 一句话总结
`marknative`本质上是一个**面向服务端和批量场景的、确定性 Markdown 图片渲染引擎**。  
如果你想摆脱浏览器渲染链路，把 Markdown 直接稳定地变成分页图片，它是一个很有潜力的基础组件。

## 产品-最佳实践（1）

### 2026-04-03 04:14:49

#### 基于`liyown/marknative`的最佳实践示例

下面用一个具体实例来说明：

> **实例场景**：你要做一个 “服务器端周报卡片生成服务”，把团队每周提交的 Markdown 周报，批量渲染成适合社媒传播和归档的分页 PNG，同时保留 SVG 用于后续编辑和检索。

---

##### 一、为什么这个场景适合`marknative`

`marknative`的核心优势，不是 “把 Markdown 显示出来”，而是：

- **无浏览器依赖**：不需要 Chromium、Playwright、DOM 截图链路
- **结果确定性强**：同一份 Markdown 在同样配置下，分页结果稳定
- **适合服务端批处理**：天然适合队列任务、定时生成、批量导出
- **输出直接可用**：直接拿到 PNG / SVG，不必再走截图流程
- **布局与绘制解耦**：便于做测试、调试和二次加工

所以，“周报卡片生成服务” 是一个比 README 演示更接近真实业务的落地例子。

---

##### 二、具体实例设计

###### 目标

输入一组 Markdown 周报：

```md
# 第 32 周工作周报

## 本周完成
- 完成支付模块重构
- 修复 12 个线上问题
- 新增运营活动页配置能力

## 风险与阻塞
> iOS 审核仍未通过，预计影响下周发版节奏。

## 下周计划
1. 推进账单系统对账
2. 完成用户标签迁移
3. 补充接口压测报告
```

输出：

- `out/week-32/page-01.png`
- `out/week-32/page-02.png`
- `out/week-32/page-01.svg`
- `layout.json`用于记录分页与片段位置

---

##### 三、推荐实现方式

###### 示例代码

```ts
import { renderMarkdown } from 'marknative'
import { mkdir, writeFile } from 'node:fs/promises'
import path from 'node:path'

async function renderWeeklyReport (markdown: string, reportId: string) {
  const outDir = path.join ('out', reportId)
  await mkdir (outDir, { recursive: true })

  const pngPages = await renderMarkdown (markdown, { format: 'png' })
  const svgPages = await renderMarkdown (markdown, { format: 'svg' })

  await Promise.all (
    pngPages.map ((page, index) => {
      const file = path.join (outDir, `page-${String (index + 1).padStart (2, '0')}.png`)
      return writeFile (file, page.data)
    })
  )

  await Promise.all (
    svgPages.map ((page, index) => {
      if (page.format !== 'svg') return Promise.resolve ()
      const file = path.join (outDir, `page-${String (index + 1).padStart (2, '0')}.svg`)
      return writeFile (file, page.data)
    })
  )

  const layout = pngPages.map ((page, index) => ({
    pageNumber: index + 1,
    width: page.page.width,
    height: page.page.height,
    fragments: page.page.fragments,
  }))

  await writeFile (
    path.join (outDir, 'layout.json'),
    JSON.stringify (layout, null, 2),
    'utf8'
  )

  return {
    reportId,
    pageCount: pngPages.length,
    outDir,
  }
}
```

##### 四、在这个实例上的最佳实践

##### 1. 把 “渲染” 当成后端文档生产流程，而不是前端截图流程

最佳实践是：

- 输入只接受**纯 Markdown 或结构化文本**
- 渲染过程只负责**解析、布局、分页、输出**
- 不把运行时浏览器样式、异步 DOM 状态、截图时机耦合进来

这样做的好处是：

- 服务更稳定
- 部署更轻
- 结果更可预测
- 更适合批量任务和 CI

**建议**：在服务设计上，把`marknative`放在 “文档生成层”，而不是 “网页渲染层”。

---

##### 2. 一次业务定义一个固定模板约束

虽然`marknative`支持通用 Markdown，但在业务里不要完全放开。

以 “周报卡片” 为例，建议约束输入格式：

```md
# 标题

## 本周完成
- ...

## 风险与阻塞
- ...

## 下周计划
1. ...
```

最佳实践：

- 固定一级标题只能出现一次
- 二级标题限定几个业务段落
- 列表层级不要过深
- 图片尺寸和数量设上限
- 表格仅用于少量结构化信息

原因：

- 分页引擎稳定，但业务内容无限制时，视觉质量会不可控
- 渲染系统最怕 “合法但极端” 的输入

**建议**：先定义 “业务 Markdown 规范”，再接入渲染。

---

##### 3. PNG 用于分发，SVG 用于归档和后处理

在这个实例里，最优输出策略通常不是二选一，而是双轨输出：

- **PNG**：适合分享、上传、消息推送、预览
- **SVG**：适合归档、放大查看、后续编辑、文本检索链路

最佳实践：

- 业务主流程消费 PNG
- 内部存档保留 SVG
- 如果未来需要 “高分辨率导出 PDF”，SVG 更有价值

也就是说，不要只保存最终图片，最好保留一份更高语义密度的输出。

---

##### 4. 使用稳定的命名与目录规则，方便批处理

在批量生成场景里，文件组织非常关键。

推荐：

```txt
out/
  week-32/
    page-01.png
    page-02.png
    page-01.svg
    page-02.svg
    layout.json
    meta.json
```

最佳实践：

- 页码固定两位或三位补零
- 每次任务独立目录
- 额外保存`meta.json`，记录输入摘要、渲染时间、版本号
- 不要把不同格式、不同任务的文件混在一起

这样后续做：

- CDN 上传
- 历史回溯
- 比对渲染结果
- 失败重试

都会容易很多。

---

##### 5. 利用`page`布局数据做调试和质量检查

`marknative`的一个很强的点是：返回结果不仅有图片，还有布局后的页面数据。

这是最佳实践重点，不应浪费。

你可以基于`page`做：

- 检查标题是否被分页拆断
- 检查某些块是否过于靠近页底
- 识别代码块、表格、引用块在页面中的位置
- 做 “内容安全区” 校验
- 为点击定位、片段高亮、审阅系统提供基础数据

**建议**：把`layout.json`当成正式产物之一，而不是调试临时数据。

---

##### 6. 对长文档采用异步队列，而不是同步接口阻塞

如果你的 “周报服务” 未来变成：

- 每周 500 份文档
- 每份 2 到 10 页
- 同时导出 PNG 和 SVG

那就不应该走简单的同步 HTTP 请求。

最佳实践架构：

- API 只负责接收 Markdown 和创建任务
- 后台 worker 执行`renderMarkdown`
- 渲染完成后写文件或对象存储
- 再回写任务状态

原因：

- 原生绘制本质仍是 CPU / I/O 密集任务
- 批量渲染时更适合队列削峰
- 失败任务更容易重试和隔离

---

##### 7. 提前控制字体和运行环境一致性

这个项目强调 “确定性”，但前提是运行环境尽量一致。

最佳实践：

- 固定 Node/Bun 版本
- 固定`marknative`和`skia-canvas`版本
- 在 CI 和生产中统一系统字体或内置字体策略
- 对中英文混排内容做专项验证

尤其你提供的项目内容里已经提到：

- 未来会继续优化**CJK 与中英文混合换行**
- 会支持**custom fonts**

这意味着在中文业务场景中，字体和换行表现是必须重点验证的。

**建议**：上线前至少准备三组测试文档：

- 纯英文
- 纯中文
- 中英混排 + 列表 + 引用 + 代码块

---

##### 8. 用 “黄金样例” 做回归测试，而不是只测是否成功输出

文档渲染系统最怕一种假象：程序没报错，但视觉结果已经变了。

最佳实践测试方法：

- 准备几份固定 Markdown 样例
- 每次渲染后对比：
  - 页数是否变化
  - 每页关键片段位置是否变化
  - 图片哈希或像素差异是否超阈值
- 对升级依赖、修改布局逻辑做快照回归

例如测试项：

- 一页文档不应突然变成两页
- 标题不应落在页尾孤行
- 列表缩进不应异常
- 表格列宽不应塌陷

对于`marknative`这种布局引擎型项目，**回归测试价值远大于单纯单元测试**。

---

##### 9. 不要把复杂品牌设计直接塞进 Markdown 本身

很多团队会把 Markdown 当成 “半个设计工具”，例如：

- 大量手工空行
- 特殊字符对齐
- 用列表模拟版式
- 用图片硬拼标题和正文

这不是好的实践。

最佳方式应该是：

- Markdown 只描述内容结构
- 主题、页边距、字体、间距由渲染层控制
- 视觉风格由主题系统统一管理

也就是说：

- 内容归内容
- 布局归布局
- 主题归主题

这正符合`marknative`这类引擎的设计方向。

---

##### 10. 对不稳定语法能力保持 “白名单心态”

从你给的内容看，当前支持已经很强，但 roadmap 也明确说明还有继续完善的点，例如：

- 段落换行质量
- CJK 混排
- 代码块与表格渲染
- 更完整的 GFM 支持

因此，业务上更稳妥的最佳实践是：

- 先使用项目已经明确稳定支持的语法
- 对脚注、自动链接、复杂嵌套表格等特性谨慎启用
- 将业务生产可用语法收敛成白名单

这样可以避免：

- 文档作者写了 “Markdown 标准里可能支持” 的内容
- 但实际在渲染结果中表现不理想
- 最终把问题转嫁到生产流程

---

##### 五、一个更完整的落地建议

如果要把这个实例做成真正可上线的 “周报渲染服务”，推荐采用下面的分层：

###### 内容层
- 由编辑器或表单生成标准化 Markdown
- 做长度、图片数、表格数、标题结构校验

###### 渲染层
- 调用`renderMarkdown`
- 同时产出 PNG、SVG、布局 JSON

###### 存储层
- 文件系统或对象存储保存渲染结果
- 记录任务元数据和版本信息

###### 质量层
- 回归样例测试
- 页数与布局片段校验
- 渲染失败重试

###### 分发层
- 分享用 PNG
- 归档和二次处理用 SVG
- 检索和调试用 layout 数据

---

##### 六、结论

对于`liyown/marknative`，最佳实践不是把它当成 “另一个 Markdown 预览器”，而是把它当成一个：

- **可测试的文档布局引擎**
- **确定性的服务端渲染组件**
- **适合批量生成视觉文档的基础设施**

在 “周报卡片生成服务” 这个实例里，最值得坚持的实践是：

1. 约束输入 Markdown 结构  
2. 双轨输出 PNG + SVG  
3. 保留布局数据用于调试和检索  
4. 用队列处理批量渲染  
5. 用黄金样例做视觉回归测试  
6. 严格控制字体、版本和运行环境一致性
