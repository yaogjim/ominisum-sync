*MUX0 · 设计笔记*

MUX0 开源吗？

源代码在 GitHub 上以 Source-Available 许可证公开 —— 免费使用，商用也可以，但不允许再分发。详情见 LICENSE。

支持哪些 Agent？

Claude Code（通过 settings.json 注入）、OpenCode（通过内置插件）、Codex（通过 hooks，实验性）。每一个都可以在 设置 → Agents 里独立开关。

需要联网吗？

不需要。应用完全离线运行。你的 Agent 也许会去访问它自己的模型服务，但 MUX0 本身永远不会；Sparkle 只在你主动点或开启每日检查时才会去查更新。

和 Ghostty 是什么关系？

我们把 ghostty 的终端引擎 libghostty 作为库使用，并在设置面板里暴露它的全部 config key。致敬原作者：渲染引擎是他们的。MUX0 在它之上加了 workspace、tab、split、Agent 状态这几层。

系统要求？

macOS 14（Sonoma）及以上。强烈推荐 Apple Silicon，因为 libghostty 用 Metal GPU 渲染。

MUX0 是免费的吗？

是的 —— 个人和商用都免费。你在 MUX0 里做的东西归你。不允许的是把 MUX0 软件本身再拿去分发 —— 比如转售、把 MUX0 打包进你自己的软件卖、或托管成 SaaS 对外提供服务。以提 PR / 回贡献为目的的 fork 源码是可以的，但不能拿 fork 当成一个平行或竞争发行版长期维护。详情见 LICENSE。

可以在应用里切中文吗？

可以 —— 设置 → 外观 → 语言：跟随系统 / English / 简体中文。切换无需重启。

macOS 终端应用，标签页 + 分割窗格，侧边栏实时展示 AI Agent 的运行状态。按项目组织终端、自由切分窗格，一眼看清 Claude Code / OpenCode / Codex 是在跑、空闲、还是等你输入。

由 [ghostty](https://ghostty.org) 引擎驱动，Metal GPU 渲染。中英双语 UI。

#### 功能特性

- **Workspace → Tab → Split 三层结构** — 按项目组织终端。每个 workspace 有自己的 tab 集合，每个 tab 是一棵分割树，可横切、竖切、拖动分隔线、用键盘切换焦点窗格。
- **AI Agent 状态实时显示** — 侧边栏和 tab 图标实时反映 Claude Code / OpenCode / Codex 的 `running` / `idle` / `等待输入` / `结束` 状态。每个 turn 会根据工具级报错自动标记成功或失败。悬停图标可以看到当前正在跑的工具、以及 Claude / Codex 的最后一句回复摘要。
- **Workspace 侧边栏元信息** — 每个 workspace 行展示当前 git 分支、打开的 PR 状态、未读通知。每 5 秒后台刷新，并通过 shell 的 OSC 钩子实时更新。
- **精致的主题** — 内置 ghostty 全部主题。可调背景透明度、窗口模糊（毛玻璃）、光标形状与闪烁、非聚焦窗格变暗。MUX0 自身的侧边栏和标签栏会随当前终端主题同步染色 —— 不会有突兀的"外壳"颜色。
- **中英双语 UI** — 完整的英文与简体中文本地化。在 **设置 → 外观 → 语言** 中即时切换，无需重启。
- **布局持久化** — workspace 列表、tab 列表、分割布局、每个终端的工作目录都会跨重启保留。
- **自动更新** — 由 Sparkle 驱动的应用内升级。有新版本时侧边栏底部会出现小红点，更新日志内嵌显示，可延后或跳过某个版本。

#### 系统要求

- macOS 14.0 及以上
- 强烈推荐 Apple Silicon（以获得 Metal GPU 渲染效果）

#### 新手上路

##### 1\. 安装

1. 从 [GitHub Releases](https://github.com/10xChengTu/mux0/releases) 下载最新的 `mux0.dmg` 。
2. 打开 DMG，将 **MUX0** 拖入「应用程序」文件夹。
3. 启动 MUX0。首次运行时 macOS 可能会弹出安全提示 —— 前往 **系统设置 → 隐私与安全性** ，点击 **仍要打开** 即可。

之后 MUX0 每天会自动检查一次更新，有新版本时侧边栏底部会出现小红点。

1. 点击侧边栏的 **＋** 按钮。
2. 选择一个项目文件夹 —— 这会成为该 workspace 的工作目录。
3. 侧边栏会立刻开始跟踪这个目录的 git 分支、PR 状态与通知。

小贴士：可以建任意多个 workspace，每个都独立持有自己的 tab 和分割布局。

##### 3\. 打开标签页与分割窗格

- **新建 tab** — `⌘T` ，或标签栏上的 **＋** 按钮。
- **关闭 tab** — `⌘W` ，或 tab 上的 ✕ 按钮。
- **横向分割** — `⌘D` 。
- **纵向分割** — `⌘⇧D` 。
- **切换焦点窗格** — `⌘⌥` + 方向键。
- **调整窗格大小** — 用鼠标拖动分隔线。
- **重命名 tab / workspace** — 双击标题。
- **重新排序** — 拖拽 tab 或 workspace 行。

##### 4\. 挑选主题

按 `⌘,` 打开 **设置** ，然后：

- **外观 → 主题** — 选择任意 ghostty 主题。侧边栏和标签栏会随之染色。
- **外观 → 背景透明度** — 低于 1.0 可得到半透明窗口。
- **外观 → 背景模糊** — 配合透明度可做出毛玻璃效果。
- **字体 → 字体族 / 字号** — 挑选系统里任意等宽字体。

全部设置项的说明见 `docs/settings-reference.md` 。

##### 5\. 切换语言（可选）

**设置 → 外观 → 语言** ： *跟随系统* 、 *English* 、或 *简体中文* 。切换后整个界面立刻生效。

MUX0 会自动钩接 Claude Code / OpenCode / Codex，让它们的运行状态实时显示在侧边栏与 tab 图标上。你不需要做任何额外配置 —— 照常运行 agent 即可。

##### 状态图标

图标颜色 含义

绿色（闪动） Agent 正在运行 —— turn 进行中

琥珀色 Agent 在等你输入（权限请求、澄清问题）

✓（绿色对勾） 上一个 turn 干净结束

✕（红色叉） 上一个 turn 里有至少一个工具报错

灰色 空闲 / 没有 agent 在跑

悬停状态图标可以看到当前正在跑的工具（例如 *"Edit Models/Foo.swift"* 、 *"Bash: ls"* ），以及 Claude / Codex 最后一句回复摘要。

##### 支持的 Agent

Agent 启动命令 说明

**Claude Code** `claude` 状态 + turn 摘要 + 工具详情，功能最全

**OpenCode** `opencode` 状态 + 工具详情。摘要暂未实现

**Codex** `codex` 状态是实验性的，响应可能略慢

如果状态图标不更新，见下面的 常见问题 。

#### 常见问题

##### Agent 状态图标不更新

- 确认 **设置 → Shell → Shell Integration** 已启用（默认 *detect* ）。
- 关掉并重新打开那个终端 tab。钩子是在新 shell 启动时激活的，所以升级 MUX0 之前就打开的老终端不会被注入。
- 如果你手动改过 shell rc 文件（ `~/.zshrc` 、 `~/.bashrc` 等）并关闭了 ghostty 的 shell 集成，需要重新启用。

##### 主题或字体保存后没有变化

设置写入有约 200 ms 防抖。如果一两秒后还是没生效，把该设置关掉再打开，或退出重启 MUX0。

模糊只有在 **背景透明度** 低于 1.0 时才有可视效果。想要毛玻璃效果，先降低透明度，再调整模糊半径。

##### 首次打开提示「无法打开 MUX0」

这是 macOS 的 Gatekeeper 警告。前往 **系统设置 → 隐私与安全性** ，滚到底部，点击 MUX0 那一条旁边的 **仍要打开** 。只需要做一次。

##### 自动更新没检测到新版本

自动更新每天最多检查一次。想立刻检查，打开 **设置 → 更新** ，点击 **检查更新** 。

#### 从源码构建

```
./scripts/build-vendor.sh   # 首次构建 libghostty
xcodegen generate
xcodebuild -project mux0.xcodeproj -scheme mux0 -configuration Debug build
```

完整的依赖、vendor 布局、发版流程见 `docs/build.md` 。

##### 让本地授权不反复丢失（可选）

默认情况下 Debug 构建走 **ad-hoc 签名** ，每次 `xcodebuild` 生成的 `cdhash` 都不同。macOS TCC（Files &amp; Folders、Full Disk Access 等权限系统）把它当成"换了一个 app"，之前授予的权限直接作废 —— 所以每次 rebuild 都要重新点允许。

用稳定的 Apple Development cert 签名可以根治：

1. 确认 **Xcode → Settings → Accounts** 里登录了你的 Apple ID。
2. 复制模板并填入 10 位 Team ID：
   ```
   cp Local.xcconfig.example Local.xcconfig
   # 然后编辑 Local.xcconfig：
   # DEVELOPMENT_TEAM = XXXXXXXXXX
   ```
3. `xcodegen generate && xcodebuild ... build` ，用下面命令验证：
   ```
   codesign -dv ~/Library/Developer/Xcode/DerivedData/mux0-*/Build/Products/Debug/mux0.app 2>&1 | grep Authority
   ```
   应看到 `Authority=Apple Development: <你的名字> (...)` ，而不是 `adhoc` 。

`Local.xcconfig` 已在 `.gitignore` 里，不会入库。不想配也没关系 —— 构建照常能跑，只是 TCC 弹窗循环仍在。

#### mux0 设置项说明

mux0 的设置面板分成六个 tab： **Appearance（外观）** 、 **Font（字体）** 、 **Terminal（终端）** 、 **Shell** 、 **Agents** 、 **Update（更新）** 。 每个设置项底层都对应一个 ghostty 的 config key，写入到 mux0 的 override 配置里（保存后即时生效）。 每个 tab 底部的 **Reset** 按钮会把这个 tab 涉及到的 key 从 override 里清空，回到默认值。

---

#### 1\. Appearance（外观）

控制窗口视觉表现：主题、透明、模糊、内边距、光标。

设置项 config key 默认值 说明

Theme `theme` — 终端主题（配色方案）。决定前景色、背景色、16 色调色板等。mux0 的主题也会跟随它变化。

Background Opacity `background-opacity` `1.0` 终端窗口背景的不透明度。 `1.0` 完全不透明； `0.0` 完全透明。配合下面的 Blur 可做毛玻璃效果。

Background Blur `background-blur-radius` `0` 背景模糊半径，范围 `0…100` 。仅在 Opacity &lt; 1 时有视觉效果，用来做毛玻璃。

Window Padding X `window-padding-x` `2` 终端内容区左右两侧的内边距（列数/像素由 ghostty 规则决定）。增大可以让文字离窗口边缘远一点，不那么挤。

Window Padding Y `window-padding-y` `2` 终端内容区上下两侧的内边距。

Cursor Style `cursor-style` `block` 光标形状： `block` （方块）/ `bar` （竖线）/ `underline` （下划线）。

Cursor Blink `cursor-style-blink` `false` 光标是否闪烁。关了更安静，不会打扰视线。

Unfocused Pane Opacity `unfocused-split-opacity` `0.7` 非聚焦 pane 的不透明度。同一 tab 内多个 pane 并排时，未聚焦的 pane 会按这个透明度变暗以突出焦点。（config key 保留 ghostty 的 `unfocused-split-opacity` 名称以兼容既有配置；mux0 自行在 view 层实现，不依赖 ghostty 的 split tree。）

---

#### 2\. Font（字体）

控制终端的字体与字号。

设置项 config key 默认值 说明

Font Family `font-family` 系统默认等宽字体 终端使用的字体族，例如 `JetBrains Mono` 、 `Menlo` 、 `SF Mono` 。建议选等宽字体，否则对齐会错。

Font Size `font-size` `13` 字号，范围 `6…72` （单位 pt）。

Font Thicken `font-thicken` `false` 是否让字体变"粗一点"。在 Retina 屏上，小字号有时看起来偏细，开了会加粗描边让字更清晰。副作用是字看起来更"肉"。

---

#### 3\. Terminal（终端）

控制终端行为：回滚缓冲、选中复制、鼠标、关闭确认。

设置项 config key 默认值 说明

Scrollback Limit `scrollback-limit` `10_000_000` （一千万字节） 回滚缓冲区上限（字节数）。决定你往回滚能看到多少历史输出。设太大吃内存，设为 `0` 等于禁用回滚。

Copy On Select `copy-on-select` — 选中文本是否自动复制。 `false` ：不复制（要 ⌘C）； `true` ：复制到普通剪贴板； `clipboard` ：复制到系统剪贴板（跨 app 可粘贴）。

Hide Mouse While Typing `mouse-hide-while-typing` `false` 打字时自动隐藏鼠标指针，防止指针挡住正在输入的位置。

Confirm Close `confirm-close-surface` — 关闭终端 surface 时是否弹确认框。 `true` ：有运行中的进程才问； `false` ：从不问； `always` ：总是问。防止误关正在跑的命令。

---

#### 4\. Shell

控制 shell 启动方式与 shell 集成。

设置项 config key 默认值 说明

#### Agent Hooks

mux0 通过注入到各 AI CLI 的生命周期钩子，把 `running` / `idle` / `needsInput` / `finished` 状态推送到 app 的 `TerminalStatusStore` ，驱动 sidebar / tab 上的状态图标。Agent 侧（Claude Code / Codex / OpenCode）另外在 `.finished` 事件里携带 `exitCode` 哨兵值（0 = turn 干净，1 = turn 里有 tool 报错）和可选的 `summary` （transcript 最后一条 assistant 消息）。

实现位于 `Resources/agent-hooks/` ，由 `project.yml` 的 postBuildScript 拷贝到 app bundle，运行时通过 `ZDOTDIR` shim 自动激活。

#### IPC

- 传输：Unix domain socket，路径为 `~/Library/Caches/mux0/hooks-<bundle-hash>.sock` （ `<bundle-hash>` = SHA256(`Bundle.main.bundlePath`) 前 8 位十六进制）。按 bundle 路径分命名空间是为了让 `/Applications/mux0.app` 和 Xcode DerivedData 里的 Debug 构建互不抢占 socket——后起的实例 `bind()` 前会 `unlink` 掉同路径的旧 sockfile，会把前一实例踢下线。路径由 `GhosttyBridge.initialize()` 写进 `MUX0_HOOK_SOCK` ，终端进程通过 env 继承
- 消息格式：每行一个 JSON， `{"terminalId": "...", "event": "running|idle|needsInput|finished", "agent": "claude|opencode|codex", "at": <epoch>, "exitCode": <int>?, "toolDetail": <string>?, "summary": <string>?}` 。 `exitCode` 仅在 `event=finished` 时携带（shell = 真实 `$?`；agent = 0/1 哨兵）； `toolDetail` 仅在 agent 的 `event=running` 时携带（如 "Edit Models/Foo.swift"）； `summary` 仅在 agent 的 `event=finished` 时携带（transcript 最后一条 assistant 消息，≤200 chars）。
- 监听端： `HookSocketListener` （DispatchSourceRead，accept 循环）

Agent turn 没有真实的 exit code，但 Claude Code / Codex 的 `PostToolUse` hook 和 OpenCode 的 `tool.execute.after` 插件事件都带结构化的 "tool 报错了吗" 字段。mux0 在每个 turn 内聚合这些 per-tool 信号到一个布尔 `turnHadError` ，在 `Stop` / `session.idle` 时发 `finished` 事件， `exitCode` 设为 0（clean）或 1（had errors）。

**Claude / Codex** （命令行 hook，无状态每次 fork 一个 agent-hook.sh）：per-session 状态存在 `~/Library/Caches/mux0/agent-sessions.json` ，按 `session_id` 索引。 `PostToolUse` 把 `tool_response.is_error` 粘滞累加（一个 turn 里任一 tool 失败就是失败）； `Stop` 读取后清除该 session 条目并 emit。过期（&gt;1h 未 touch）的条目每次 hook 调用时自动 GC。

**OpenCode** （长驻插件进程）：状态保存在插件 closure 的 `turn` 对象里， `tool.execute.after` 累加 `args.error` / `args.result.status === "error"` ， `session.idle` 时 emit。插件进程重启（opencode 退出 / 重开）会丢状态，但同时 opencode 自己也重建 session，语义无歧义。

**Turn summary** （Claude 独有）： `Stop` 从 `transcript_path` 读取 JSONL 最后一条 `role: "assistant"` 的 text 字段，剥掉 `<thinking>...</thinking>` 块，截到 200 chars，放进 `summary` 。Codex 同理（schema 一致）。OpenCode 的 summary 在 v1 里留空（它没有等价的 transcript path 参数；后续 spec 可补）。

**Tool detail** （全部 agent）： `PreToolUse` / `tool.execute.before` 时，派发脚本/插件会根据 `tool_name` + `tool_input` 生成一个紧凑的人类可读标签（"Edit Models/Foo.swift"、"Bash: ls"），作为 `running` 事件的 `toolDetail` 。Swift 端把它拼到 tooltip 的第二行。

Agent 机制 文件

Claude Code `--settings` 注入 hooks JSON（SessionStart/UserPromptSubmit/PreToolUse/Stop/Notification/SessionEnd） `claude-wrapper.sh`

OpenCode 插件订阅 bus 事件（tool.execute.before / permission.asked / session.idle 等） `opencode-plugin/mux0-status.js`

Codex 实验性 `hooks.json` + `notify` 兜底 `codex-wrapper.sh`

#### needsInput 的派发门控

Claude Code 的 `Notification` hook 本身是一个双重信号： **真实的权限请求** 会触发它，同时\*\*"已经 60 秒没动静"\*\*的空闲心跳也会触发它（Claude Code 官方行为，不可区分）。如果无条件把 `Notification → needsInput` ，一个成功结束的 turn 60 秒后就会被心跳误覆盖，让图标从 `success` 翻成 `needsInput` 。

因此 `HookDispatcher` 对 `needsInput` 事件加了一道门： **只有当当前状态是 `.running` 时才转入 `.needsInput`** ，在 `success / failed / idle / neverRan` 状态下收到 `needsInput` 直接丢弃。这样能保留 turn 结束后的终态不被后续心跳污染，同时不影响真实的权限请求场景（权限请求发生在 turn 进行中，状态必然是 `.running` ）。OpenCode 的 `permission.asked` 同理适用。

**Codex 的 hooks 默认不生效，用户必须在 `~/.codex/config.toml` 里显式打开：**

```
[features]
codex_hooks = true
```

**为什么需要** ： `codex_hooks` 是 OpenAI 标记的 `Stage::UnderDevelopment` 特性（源码在 `codex-rs/features/src/lib.rs` ），官方保留修改权，默认关闭。我们的 wrapper 用 overlay `CODEX_HOME` 写 `hooks.json` ，但 flag 必须在用户主 config 里声明——overlay 也无法替用户打开未声明的实验 flag。

**不开的后果** ：

- `hooks.json` 被 codex 完全忽略， `UserPromptSubmit` / `PreToolUse` / `Stop` 都收不到
- 只剩 `notify = [...]` （turn 完成时触发）和 wrapper 启动时主动 emit 的一次 idle
- 表现：codex 启动/结束时正确显示 idle，但 **turn 进行中状态不会变成 running** （停留在 idle）

**开了之后的预期** ：UserPromptSubmit → running，Stop → idle，PreToolUse → running（目前 codex 只对 `Bash` 工具触发 PreToolUse，MCP/文件工具还没接）。

**调试入口** ：用户反馈 "codex 状态不对"，先问 flag 是否打开——未开是已知限制，非 bug；开了仍不对才去查 `~/Library/Caches/mux0/hook-emit.log` 和 `codex-wrapper.sh` 。

Codex 和 Claude Code 用 **同一种嵌套格式** （不是 flat）：

```
{
  "hooks": {
    "UserPromptSubmit": [
      { "hooks": [{ "type": "command", "command": "..." }] }
    ],
    "Stop": [
      { "hooks": [{ "type": "command", "command": "..." }] }
    ]
  }
}
```

Codex parser 使用 Serde 的 `deny_unknown_fields` ——flat 格式 `{"command": "..."}` 或多余字段会导致 **整个文件被静默跳过** ，没有错误日志。

#### config.toml 注入的坑

Codex wrapper 往 overlay config.toml 里加 `notify` 时必须 **前置** （写在所有用户 `[section]` 之前），不能 append。TOML 里 section 无法"关闭"，一旦进入 section，后续 key 都归属它。如果用户 config 末尾是 `[notice.model_migrations]` ，append 的 `notify = [...]` 会被当成 `notice.model_migrations.notify` ，解析成"expected a string, got sequence"错误。

shell preexec/precmd 在 2026-04 之前是第 4 种状态源。现已从 pipeline 中移除： shell-hooks.{zsh,bash,fish} 脚本删除、bootstrap 不再 source、 `HookMessage.Agent` 枚举不含 `.shell` case。详见 `decisions/004-shell-out-of-status-pipeline.md` 。

#### Internationalization (i18n)

mux0 supports English and Simplified Chinese UI. Language preference lives in UserDefaults (key `mux0.language`, values `system|zh|en`) and is exposed in Settings → Appearance → Language.

#### Architecture

- `mux0/Localization/LanguageStore.swift` — `@Observable` singleton. Holds the user's preference, persists to UserDefaults, publishes a monotonic `tick` counter, and exposes `locale` (for SwiftUI `\.locale` environment) and `effectiveBundle` (for AppKit callers).
- `mux0/Localization/L10n.swift` — compile-time namespace of constants:`L10n.Sidebar / Tab / Settings / App / Menu`. Each constant is a `LocalizedStringResource`. For AppKit call sites there is a helper `L10n.string("raw.key", args...)` that resolves via `LanguageStore.shared.effectiveBundle.localizedString(forKey:value:table:nil)` and applies `String(format:)` to any variadic args.
- `mux0/Localization/Localizable.xcstrings` — Xcode String Catalog. English is the source language; Simplified Chinese is maintained in parallel. Xcode compiles this into `en.lproj/Localizable.strings` and `zh-Hans.lproj/Localizable.strings` inside the built bundle.

#### SwiftUI path

`mux0App.swift` injects both `languageStore` and `\.locale = languageStore.locale` into the environment at the scene root. SwiftUI views use `Text(L10n.Namespace.key)` — `Text(LocalizedStringResource)` honors the injected `\.locale`, so any body-rebuild produced by an observable property change picks up the right language.

For views that need a `String` (e.g. `IconButton.help: String?`), read `@Environment(\.locale) private var locale` and wrap:

```
String(localized: L10n.Namespace.key.withLocale(locale))
```

The `withLocale(_:)` helper is defined in `L10n.swift`. Do NOT use `String(localized: res)` without `.withLocale(locale)` — that reads `Locale.current` (the process-level system locale) and ignores the user's mux0 language choice.

#### AppKit path

AppKit subclasses can't read SwiftUI environment. Two patterns:

1. **Ephemeral strings** (rebuilt on each use — right-click menus, alert dialogs): call `L10n.string("raw.key")` directly. It reads `LanguageStore.shared.effectiveBundle` at call time, so it always reflects the current preference.
2. **Persistent labels** (`stringValue`, `toolTip` on long-lived NSViews): the owning `*Bridge: NSViewRepresentable` takes a `languageTick: Int` parameter wired from `languageStore.tick`, reads it in `updateNSView` (forcing re-evaluation when preference changes), and calls a `refreshLocalizedStrings()` method on its NSView subclass that re-assigns every tracked label.

`SidebarListBridge`, `TabBridge`, and `TabContentView/TabBarView` already follow this pattern — use them as references.

SwiftUI `Commands` live outside the view tree, so `@Environment(\.locale)` isn't available there. We reference `LanguageStore.shared.locale` directly and include `_ = languageStore.tick` at the top of `var body: some Scene` to force Commands to re-build when the user changes language. Menu items may take a moment (until the next scene pass) to update after a switch — this is a known SwiftUI Commands limitation; accept it.

**MUX0 是一款面向 AI 编码 Agent 场景的 macOS 原生终端**：它基于 `libghostty + Metal` 做高性能终端渲染，在传统终端的 `Workspace → Tab → Split` 组织能力之上，增加了对 `Claude Code / OpenCode / Codex` 的**实时状态感知**，让你按项目管理终端，并随时知道 Agent 是在运行、等待你、成功结束，还是失败。

##### 综合总结

##### 1. MUX0 本质上是什么

从官网、README 和文档综合看，MUX0 不是单纯“又一个终端模拟器”，而是一个更明确定位于 **“Agent-aware terminal”** 的产品。它希望解决的问题不是“怎么开终端”，而是：

- 当你同时开着多个项目、多个 tab、多个 pane 时，**怎么快速知道哪个 Agent 在干活**
- 当 Agent 需要你授权、回答问题或介入时，**怎么第一时间发现**
- 当你按仓库组织工作流时，**怎么把 git 分支、PR、通知和终端状态放在一个地方看**

所以它的核心卖点并不是炫技，而是把终端从“被动命令行窗口”变成“**项目级、状态可见、对 Agent 友好**”的工作台。

---

##### 2. 它的核心能力可以概括为四层

###### 2.1 原生终端能力：快、清晰、低延迟

MUX0 使用：

- `libghostty` 作为终端引擎
- `Metal` 做 GPU 渲染
- `Swift + AppKit + SwiftUI` 做原生 macOS 应用

这意味着它强调的是：

- 输入延迟低
- 字体显示清晰
- 没有 Electron 外壳的额外资源负担
- 与 macOS 的窗口、设置、语言切换、更新机制更贴合

简单说，**它先是一个性能扎实的原生终端，然后才是一个 Agent UI**。

---

###### 2.2 工作组织能力：按项目管理终端

MUX0 的结构是：

`Workspace → Tab → Split`

可以理解为：

- `Workspace`：一个项目/仓库级容器
- `Tab`：该项目下的一组任务页签
- `Split`：一个 tab 内的多窗格布局

特点包括：

- 每个 workspace 独立持有自己的 tab 集合与分栏布局
- 每个 tab 是一棵可横切/竖切的分割树
- 支持键盘切 pane、拖拽调整、重命名、重排序
- 布局和工作目录可跨重启持久化

这让它更像“**按 repo 管理的终端工作区系统**”，而不是一堆散乱 tab。

---

###### 2.3 Agent 感知能力：这是 MUX0 最关键的差异点

MUX0 最大特点是：**它知道你的 Agent 在干什么**。

支持的 Agent：

- `Claude Code`
- `OpenCode`
- `Codex`（实验性）

它会在侧边栏和 tab 上用状态图标展示 Agent 当前状态，例如：

- 运行中
- 空闲
- 等待输入 / 等待授权
- 上一轮成功
- 上一轮失败

而且不仅是粗粒度状态，还能提供：

- 当前正在运行的工具详情，如 `Edit Models/Foo.swift`、`Bash: ls`
- Claude / Codex 最后一条 assistant 回复摘要
- turn 是否出现过工具级错误，并据此将结果标记为成功或失败

换句话说，MUX0 不是“显示一个进程是否还活着”，而是把 **Agent 生命周期、工具调用、回合结果** 抽象成你能一眼看懂的 UI 状态。

---

###### 2.4 项目元信息整合：终端和仓库状态合并到一处

每个 workspace 行会显示：

- 当前 git 分支
- 打开的 PR
- 未读通知

这些信息通过：

- 后台轮询
- shell 的 `OSC` 钩子
- 本地状态同步

来保持更新。

这意味着 MUX0 不只是“命令输入区”，更像是一个轻量级的**项目控制面板**：仓库、终端、Agent、PR 状态被放在同一个视图中。

---

##### 3. 它的实现思路很“本地优先”

MUX0 的设计哲学非常明确：

- **离线运行**
- **本地 socket 通信**
- **不依赖云端中转**
- **Agent 自己访问模型服务，但 MUX0 本身不联网**

其 Agent 状态更新机制大致是：

1. 在 Claude / OpenCode / Codex 启动时注入 hook 或插件
2. hook 把生命周期事件写成 JSON
3. 通过本地 Unix domain socket 发给 MUX0
4. MUX0 更新 `TerminalStatusStore`
5. 侧边栏、tab 图标、悬浮信息即时刷新

这套方式有几个明显优点：

- 延迟低
- 隐私性强
- 结构简单、可调试
- 不需要依赖外部服务

可以说它采用的是一种很“工程化”的方案：**不用花哨架构，用可靠本地 IPC 把事做成**。

- 多语言 UI 如何在 SwiftUI / AppKit 共存架构下正确切换

##### 深入浅出解读

##### 1. MUX0 想解决的真实痛点是什么

很多开发者今天已经不是“单窗口敲命令”了，而是这样的工作状态：

- 一个项目里开多个终端
- 多个项目并行切换
- 同时跑 Claude Code / Codex / OpenCode
- 等 Agent 编码、搜索、执行脚本、请求授权
- 自己还要盯 PR、看分支、处理通知

在这种状态下，真正的痛点不是“终端能不能分屏”，而是：

> **我现在应该关注哪个窗口？哪个 Agent 需要我？哪个 turn 出错了？**

传统终端几乎不回答这些问题。  
MUX0 回答了。

它把“Agent 状态”做成终端的一等信息，让终端终于能表达“**发生了什么**”，而不只是“**输出了什么**”。

---

##### 2. 为什么“Agent 感知”比“终端功能更多”更重要

市面上很多终端会强调：

- 分栏
- 标签页
- 主题
- GPU 渲染
- 快捷键

这些当然重要，但很多都已经是成熟能力。  
MUX0 的差异点在于：**它把 AI Agent 的工作流接到了终端本身**。

这件事的价值在于：

- 你不必不断点回某个 tab 看 Claude 跑完没
- 你不必从海量日志中猜它是卡住了还是在等你
- 你不必靠记忆判断“刚才那个回合有没有工具失败”

它把复杂内部状态压缩成非常低认知成本的外显信号：

- 绿闪：在跑
- 琥珀：等你
- 绿勾：上轮干净结束
- 红叉：上轮存在工具错误
- 灰：空闲

这本质上是一个**降低注意力切换成本**的设计。

---

##### 3. 为什么它强调“按项目组织”而不是“按窗口组织”

传统终端的组织方式通常是：

- 一个个窗口
- 每个窗口多个 tab
- tab 名称靠你自己记忆

但开发者实际工作的自然单位往往是：

- 一个 repo
- 一个 PR
- 一个 feature 分支
- 一组相关终端会话

MUX0 的 `Workspace → Tab → Split` 结构，其实是在说：

> **终端的第一组织单位应该是项目，而不是窗口。**

这样做的好处是：

- 项目上下文更清晰
- 分支、PR、通知能自然附着在 workspace 上
- tab 和 pane 都变成该项目下的局部操作，而不是全局混乱堆积

这让终端更接近 IDE 的项目视角，但又保留终端的轻量与自由。

---

##### 4. 为什么它采用 socket + hook，而不是更重的集成方式

从文档看，MUX0 使用的是非常克制的架构：

- CLI Agent 侧通过 hook / wrapper / plugin 发事件
- 事件格式是简单 JSON
- 本地 Unix socket 传输
- App 监听 socket 并更新状态

这种做法的妙处在于：

###### 4.1 低耦合

它不需要深度改造各 Agent 本体，只要它们支持：

- 生命周期 hook
- 插件事件
- 命令包装

就可以接入。

###### 4.2 本地实时

不经过网络，不走远程消息系统，所以：

- 更快
- 更稳定
- 更隐私

###### 4.3 易于扩展

文档提到未来新增 agent 时，只要扩展枚举和设置项，就能较自然接入。  
说明这套机制从一开始就不是“为某一个 Agent 硬编码”的。

所以 MUX0 的 Agent 感知不是脆弱的 UI hack，而是一套设计过的数据通道。

---

##### 5. Codex 为什么被标成“实验性”

文档里对 Codex 的说明非常诚实，也能看出项目成熟度：

- Codex 依赖用户在 `~/.codex/config.toml` 中显式开启 `codex_hooks = true`
- 这是官方标记为 `UnderDevelopment` 的能力
- 不开的话，hook 文件会被忽略
- 导致只能看到 turn 完成时的通知，不能准确看到 running 过程

这说明 MUX0 对 Codex 的支持不是“不能用”，而是：

> **能接，但受制于 Codex 自身实验特性，完整度不如 Claude Code。**

因此实际使用体验大概是：

- `Claude Code`：支持最完整
- `OpenCode`：状态和工具详情较完整，但摘要未实现
- `Codex`：可用但有配置前提，且实时性与覆盖范围稍弱

这是一种很靠谱的产品表达：**讲清边界，而不是模糊宣传“都支持”**。

---

##### 6. 为什么“needsInput 门控”是个很值得注意的细节

文档中提到一个容易被忽略但非常关键的问题：

Claude 的某些通知既可能表示“真的在等你”，也可能只是“60 秒没动静的心跳”。  
如果一律把通知都当成 `needsInput`，那么一个已经成功结束的回合，过一会儿可能被错误地显示成“等待输入”。

MUX0 的处理方式是：

- 只有当前状态是 `running` 时，才允许转成 `needsInput`
- 如果已经是 `success / failed / idle`，后续这类信号直接丢弃

这件事看似技术细节，实际体现了产品体验的精细度：

- 不是“有信号就显示”
- 而是“要结合上下文判断这个信号是否有意义”

这也是为什么 MUX0 的状态 UI 更可信：**它做了状态语义校正，而不是裸转发底层事件。**

---

##### 7. 设置系统体现了它“站在 ghostty 之上，而不是替代 ghostty”

设置文档显示，MUX0 的很多设置底层都映射到 ghostty config key，比如：

- 主题
- 字体
- 光标样式
- 背景透明
- 模糊
- padding
- scrollback
- shell integration

这说明 MUX0 的关系更像：

> **用 ghostty 作为终端引擎内核，再叠加自己的工作区、状态感知、UI 管理层。**

也因此它的定位不是“重新发明终端底座”，而是“用成熟内核做一个更适合 AI coding workflow 的上层产品”。

---

##### 8. 国际化做得比表面看到的更扎实

表面上看，它只是支持中英文切换。  
但文档显示其 i18n 设计并不简单：

- `UserDefaults` 保存语言偏好
- SwiftUI 通过 `\.locale` 注入
- AppKit 走独立 bundle 解析
- 长生命周期控件通过 `languageTick` 强制刷新
- String Catalog 统一管理翻译
- 还有 smoke tests 防止遗漏 key

这说明它不是“加两个语言包”，而是认真处理了：

- SwiftUI 与 AppKit 混合架构下的语言同步问题
- 即时切换无需重启
- 菜单、工具提示、持久视图如何更新

对一款 macOS 原生应用来说，这是比较成熟的本地化方案。

---

##### 9. 自动更新和发布流程说明它在往“可持续产品”发展

README 和 build 文档提到：

- 使用 `Sparkle` 做应用内更新
- 每日自动检查更新
- 支持小红点提示、内嵌更新日志、跳过版本
- release 流程自动化
- 使用 `MARKETING_VERSION` 驱动发版
- GitHub Actions 自动打 tag 与生成 Release

这说明 MUX0 不是只面向源码用户，还在认真经营“普通用户直接下载 app 使用”的体验。  
也就是说，它已经具备了一个桌面产品应有的发布与升级闭环。

MUX0 特别适合这些人：

- 同时维护多个 repo、多个终端会话的人

##### 可能的限制与注意点

##### 使用前需要留意的地方

- **仅支持 macOS 14+**，且更推荐 Apple Silicon
- **Codex 支持是实验性的**，需手动开启 `codex_hooks`
- **Agent 状态显示默认不是全开**，设置中可独立启用
- **它不是传统开源许可证**，不能再分发软件本体
- **首次源码构建有一定门槛**，需要 Xcode、xcodegen、Zig 以及先构建 `libghostty`
- **Debug 构建可能遇到 macOS TCC 权限反复授权问题**，需稳定签名改善

##### 你可以怎么理解 MUX0

如果用一句更通俗的话来说：

> **MUX0 不是在“把 AI 放进终端”，而是在“把终端升级成能理解 AI 工作状态的开发工作台”。**

它的价值不在于功能堆砌，而在于把几个关键点连了起来：

- 原生高性能终端
- 项目级工作区组织
- AI Agent 生命周期可视化
- git / PR / 通知上下文整合
- 本地优先、离线、低耦合实现

所以，MUX0 更像是面向 AI 编码时代的一种终端形态尝试：  
**让终端不再只是命令输入输出界面，而是开发者与 Agent 协作时的状态中心。**
