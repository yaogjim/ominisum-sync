## 分析要点

- **核心高价值点**：最有价值的是把反复Prefill归因到缓存机制、聊天模板序列不稳定和Qwen3.5架构特性三者叠加，而非单点配置错误。

**知识要点**

- Qwen3.5在MLX中缓存命中差与Mamba/SSM类不可裁剪缓存有关
- 推理模型的reasoning token不回放会破坏后续请求的缓存前缀匹配
- Jinja聊天模板中的tools和参数顺序不稳定会导致缓存键漂移
- 社区已有通过修改checkpoint位置和排序JSON键的临时缓解方案

- next prompt: P + A + …

**angeloskath** commented on 2/18/2026

So the lru prompt cache leaves the cache in memory when trimming. That was meant as an optimization since you can fork conversations for free.

However it is obviously problematic when the cache is 10GB and then you copy it 10x so you spend 100GB on a cache...

I think the fix is fairly simple, the cache needs to be aware of how much cache size is currently being used and how much is available. If we are reaching the limit it should evict instead of copying etc.

For the Mamba cache the fix is going to be a bit more involved. I haven't checked what other frameworks do in that case but I don't see how we can get around the fact that we can't remove things from a mamba cache. So the only solution is to preemptively cache it.

**awni** commented on 2/18/2026

There is also this adversarial case with reasoning that might merit a specific solution:

If you have something like this:

```
Request 1: [System] [User A]
Response 1: [Reasoning] [Assistant A]
Request 2: [System] [User A] [Assistant A] [User B]
```

Then the prompt cache won't match exactly since the second request drops the reasoning tokens. This is actually the right behavior for most models, but it's adversarial for the LRU prompt cache. Since we will copy the cache and keep the old copy which includes the reasoning tokens that is never used again.

**awni** commented on 2/18/2026

I think maybe the right thing to do is for a reasoning model only save the prompt cache to just prior the reasoning output.

So in the above example the prompt cache would be `[System] [User A]` instead of `[System] [User A] [Reasoning] [Assistant A]`

This would also help with hybrid models since we would have the cache at a usable point.

**SlimG** commented on 3/8/2026

I have the same issue with mlx-lm 0.31.0 and Qwen3.5-35B-A3B-4bit, using OpenCode 1.2.13 as client.  
I am not a proficient programmer, but I've done my due diligence with troubleshooting this issue, and I find it difficult to wait, so I had Claude (Opus 4.6) analyze the problem to make me a temporary fix that seem to work for me during testing. I'm sharing it here for any other impatient soul who can't wait to get their hands on Qwen3.5 😉

Claude's analysis of why the checkpoint mechanism in PR [#911](https://github.com/ml-explore/mlx-lm/pull/911) doesn't help Qwen3.5:

> The checkpoint cache is stored with a key that includes the last user message content. When the client sends request [#2](https://github.com/ml-explore/mlx-lm/issues/2), it modifies earlier messages (e.g. removing tags), so the checkpoint key diverges from the new prompt. The server finds a "longer match" but can\_trim\_prompt\_cache() returns False because ArraysCache.is\_trimmable() inherits False from \_BaseCache. Result: fetch\_nearest\_cache returns None, tokens — full cache miss.

Claude's workaround:

> For hybrid models, move the checkpoint from just before to just before the last user message. This way the checkpoint key becomes \[System + Tools\] — a stable prefix that matches across requests without needing to trim ArraysCache.

My test results (identical setup, two-message conversation):

Before patch After patch

Qwen3.5 request [#2](https://github.com/ml-explore/mlx-lm/issues/2) 11962/11967 tokens processed (full miss) 57/379 tokens processed (cache hit)

GLM-5 request [#2](https://github.com/ml-explore/mlx-lm/issues/2) 320/321 (unaffected) 320/321 (unaffected)

MiniMax-M2.1 request [#2](https://github.com/ml-explore/mlx-lm/issues/2) 348/351 (unaffected) 348/351 (unaffected)

Patch (replace `_compute_prompt_checkpoint` in `server.py`):

```
def _compute_prompt_checkpoint(self, tokenizer, request, prompt):
    if request.request_type != "chat":
        return False, -1
    if request.messages[-1]["role"] != "user":
        return False, -1
    try:
        test_cache = make_prompt_cache(self.model_provider.model)
        is_hybrid = not can_trim_prompt_cache(test_cache)
    except Exception:
        is_hybrid = False
    if is_hybrid:
        im_start_id = None
        try:
            im_start_id = tokenizer._tokenizer.convert_tokens_to_ids(
                "<|im_start|>"
            )
        except Exception:
            pass
        if im_start_id is not None:
            im_start_count = 0
            for i in range(len(prompt) - 1, 0, -1):
                if prompt[i] == im_start_id:
                    im_start_count += 1
                    if im_start_count == 2:
                        checkpoint_offset = len(prompt) - i
                        return True, -checkpoint_offset
    prompt_checkpoint = -1
    if tokenizer.has_thinking:
        for i in range(1, min(11, len(prompt)) - 1, 1):
            if prompt[-i] == tokenizer.think_start_id:
                prompt_checkpoint = -i - 1
                break
    return True, prompt_checkpoint
```

Known limitations:

- single checkpoint per request,
- hardcoded &lt;\|im\_start\|&gt; (ChatML only),
- \_serve\_single codepath not covered.

Looking forward to the proper solution. This is a vibe-coded workaround that may very well introduce it's own issues. Ye have been warned 😉

To sum up, there are multiple things that line up to make Qwen 3.5 difficult to cache:

1. Untrimmable SSM layers (fixed in 0.31.0)
2. Floating `<think>` tags (fixable via something like what [@SlimG](https://github.com/SlimG) proposed, but only causes reprocessing the previous turn)
3. Unsorted tools / args (fixable via chat template)

Entirely possible there's something else too... but 1 + 3 is working well for me so far.

## 摘要（1）

### 2026-03-12 01:52:36

**主旨概括：**  
这两段内容主要在说明：**Qwen 3.5 在 MLX / LM Studio / OpenClaw 场景下出现“反复全量预填充（prefill）”并不是单一 bug，而是多个底层机制叠加导致的缓存失效问题**。结论是：**短期没有真正“一键修复”，但社区已定位出几个关键原因，也有临时优化方案。**

---

##### 一、KeenZ 对问题的最新判断：不是单点故障，而是“多因素叠加”

###### 1. 先纠正了此前的误判
- KeenZ 表示，自己之前把问题简单归因为某个组件的问题，这个判断**过于粗暴**。
- 后来查资料发现，**LM Studio 的 MLX 引擎其实是统一架构**：
  - 所有 MLX 模型都走 **`mlx-lm` 的文本核心**
  - 视觉能力只是**可选模块**
  - 如果只是纯文本输入，**不会加载视觉部分**

###### 2. Qwen 3.5 反复 prefill 的真正原因
KeenZ 认为这是一个**复合问题**，主要由三部分共同造成：
- **`mlx_lm` 的 KV Cache 失效**
- **Qwen 官方 Jinja 模板解析问题**
- **模型本身的架构特性**

###### 3. 结果是什么
- 这些底层冲突会导致：**每轮对话都重新做全量预填充**
- 直接后果是：
  - 首 token 很慢
  - 多轮对话越聊越慢
  - 工具调用时尤其明显

###### 4. KeenZ 的实际建议
- 在 **Mac 本地跑 OpenClaw** 时，当前更推荐：
  - **GLM 4.7 Flash**
- 原因是它在 MLX 下表现更稳定，缓存问题相对少。

###### 5. KeenZ 自己的案例
- 他之前用：
  - **Qwen 3.5 35B A3B**
  - **Qwen 3.5 27B**
  跑 OpenClaw 时，常遇到 **Prompt 反复载入**
- 体验是：
  - **慢到怀疑人生**
- 后来换成 **GLM 4.7 Flash（走 `mlx_lm`）**
- 响应时间从：
  - **几分钟**
  下降到
  - **5–20 秒**

**通俗理解：**  
本来缓存应该像“上次读到哪就从哪接着读”，但 Qwen 3.5 在这个链路里经常像“每次都从第一页重新看”。

---

##### 二、GitHub Issue #903：开发者确认“缓存确实没正常工作”

###### 1. 用户报告的核心现象
Issue 发起者反馈：
- 用 `lm_server` 跑 **Qwen3.5**
- 缓存表现和其他模型完全不同
- **每次都重新处理整个 prompt**
- 返回里的 **cached tokens 始终是 0**

这说明：**缓存命中基本失效。**

---

##### 三、官方开发者解释：Qwen 3.5 的缓存难点和模型结构有关

###### 1. 一个关键原因：Mamba / SSM 缓存不能随意裁剪
开发者 `awni` 解释：
- **Mamba cache 无法 trim（裁剪）**
- 所以能复用缓存的场景更少

###### 2. 什么时候还能工作
- 如果你是**继续同一段对话**
  - 缓存**可能有效**
- 但如果你是：
  - **同样的 system prompt**
  - 加一个**新的独立问题**
- 那还是得**重新处理 system prompt**

###### 3. 这意味着什么
Qwen 3.5 这类模型不是完全不能缓存，  
而是它的缓存**复用条件更苛刻**，不像常规 KV Cache 那么灵活。

**例子：**
- 理想情况：  
  “你是一个代码助手”这段 system prompt 每次都应该复用
- 现实情况：  
  在 Qwen 3.5 + MLX 某些实现里，哪怕 system prompt 没变，也可能还得再算一遍

---

##### 四、另一个核心问题：reasoning token 会把缓存“弄脏”

###### 1. 问题出在哪
开发者指出，对于 **thinking / reasoning 模型**：
- 缓存 key 里可能包含了**推理 token**
- 但客户端下一轮请求时，**通常不会把这些 reasoning token 再发回来**

###### 2. 于是前后请求不一致
Issue 里给了一个很直观的结构：

- 缓存保存的是：  
  **P + R + A + EOS**
  - P = Prompt
  - R = Reasoning
  - A = Assistant Answer

- 下一轮实际请求是：  
  **P + A + …**

也就是说：
- 缓存里有 reasoning
- 新请求里却没有 reasoning
- 两边很早就“分叉”了

###### 3. 结果
- 共享前缀只剩下 **P**
- 导致缓存虽然不是完全 miss，但也只是**“低质量命中”**
- 最终还是要重新 prefill 很多 token

**通俗理解：**  
就像你保存了一段“草稿 + 最终答案”，  
但下次系统只拿“最终答案”来对比，  
中间少了“草稿”，于是很难无缝续上。

---

##### 五、缓存实现本身还会带来额外内存问题

###### 1. LRU 缓存的副作用
开发者发现：
- 现在的 **LRU prompt cache** 在 trim 时，旧缓存还会留在内存里
- 初衷是优化“分叉对话”

###### 2. 但在大模型上会出问题
- 如果一个 cache 有 **10GB**
- 被复制 **10 次**
- 那就会吃掉 **100GB 内存**

###### 3. 结论
- 后续修复方向之一是：
  - 缓存系统要能感知**已用容量**
  - 接近上限时应当**淘汰（evict）**
  - 而不是继续复制

---

##### 六、工具调用和 Jinja 模板也是缓存杀手

###### 1. 工具描述的顺序变化，会让缓存 key 不一致
开发者 `spicyneuron` 发现：
- Qwen 3.5 的 chat template 里，tools 被 `tojson` 后
- **字段顺序可能变化**
- 比如：
  - `additionalProperties`
  - `type`
  - `required`
  的顺序前后不一样

###### 2. 看起来内容一样，缓存却认为不一样
- 因为缓存比较的是**token 序列**
- JSON 键顺序一变，token 就变了
- 结果是：**缓存 miss**

###### 3. 甚至 tool arguments 顺序也会变
例如同一个参数对象里：
- 第一次是  
  `pattern, output_mode, head_limit, type`
- 下一次可能变成  
  `pattern, head_limit, output_mode, type`

这种变化也会破坏缓存。

###### 4. 临时解决思路
有人建议：
- 在 Jinja 模板里给 `tojson` 加 `sort_keys=True`
- 遍历参数时用 `dictsort`

###### 5. 但这也不是完美解法
- 因为这更像是**客户端 / 模板层的补丁**
- 不一定完全符合模型训练时看到的格式
- 只能算“更利于缓存”的折中方案

**通俗理解：**  
就像两份表格内容一样，但列顺序不同，  
机器会当作“不是同一个东西”。

---

##### 七、社区已经给出一些临时 workaround，并看到明显改善

###### 1. 有人提交了临时代码方案
Issue 中提到：
- 有开发者做了可用于 **Qwen3.5 缓存修复** 的尝试（如 `#923`）

###### 2. 一个具体 patch 的测试结果很亮眼
某用户针对 Qwen3.5 做了临时补丁后，测试两轮对话：

- **修复前：**
  - 第 2 次请求处理了 **11962 / 11967 tokens**
  - 基本等于**全量重算**

- **修复后：**
  - 第 2 次请求只处理 **57 / 379 tokens**
  - 说明缓存已经明显命中

###### 3. 对其他模型影响不大
同一测试下：
- **GLM-5**
  - 前后都是 **320 / 321**
- **MiniMax-M2.1**
  - 前后都是 **348 / 351**

说明：
- 补丁主要是针对 **Qwen3.5 特有问题**
- 不会明显破坏其他模型现有表现

---

##### 八、用户体验层面的影响非常明显：越长上下文越痛苦

###### 1. 实际使用反馈
有用户用：
- **opencode + lm studio**
- 跑 **Qwen3.5 35B-A3B MLX 4bit**

现象是：
- token 生成本身**非常快**
- 但**每条消息、每次工具调用都要重跑整个 prompt**

###### 2. 时间损耗非常夸张
- 原本应该只要 **10–15 秒**
- 实际变成 **1 分 46 秒**
- 上下文越长，等待时间**指数级恶化**
- 有人甚至让一个大项目 prompt 跑了 **45 分钟**才中断

###### 3. 另一位用户也复现
- 使用 **mlx-lm 0.31.0**
- 模型是 **Qwen3.5-35B-A3B-4bit**
- 客户端是 **OpenCode 1.2.13**
- 同样遇到这个问题

---

##### 九、目前社区的总体共识

###### 1. Qwen 3.5 难缓存，不是单一原因
从 Issue 讨论看，主要是几类问题叠加：
- **不可裁剪的 SSM / Mamba 层**
- **reasoning / `&lt;think>` token 导致前缀不稳定**
- **tools / args 渲染顺序变化**
- 可能还有其他细节问题

###### 2. 某些问题已经有改进方向
讨论里提到：
- **SSM 层问题**在新版本里已有部分改进思路
- reasoning 模型可考虑：
  - 只把缓存存到 **reasoning 输出之前**
- 缓存系统未来可能按**层（per-layer）**而不是按**整模型**处理

###### 3. 但完整修复还没落地
- 目前还没有真正稳定、通用、官方的一步到位方案
- 现阶段更多是：
  - 定位问题
  - 局部 patch
  - 模板优化
  - 使用替代模型规避

---

##### 十、一句话结论

**Qwen 3.5 在 MLX / LM Studio 本地部署时“反复全量 prefill”的根因，是模型缓存机制、reasoning token、Jinja 模板和工具渲染等多方面共同作用；短期最好靠补丁和模板优化缓解，或者直接换成像 GLM 4.7 Flash 这类当前更稳定的模型。**
