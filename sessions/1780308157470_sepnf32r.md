- 生产级Agent通常需要状态机编排、凭证管理、模型能力发现、工具调用、审批、预算、持久化、上下文压缩和事件流等多个基础能力。

- 策略检查、人工审批、工具调用和事件流可以作为独立工作单元接入，从而增强可观测性和可替换性。

**Mike Piccolo**

### 如何构建你自己的代理框架？？？

大多数代理团队不会构建框架。他们采用现成的框架。LangChain、LangGraph、OpenAI Agents SDK、Anthropic SDK、CrewAI、AutoGen、循环、工具、内存和编排这些组件都是作为单一决策从货架上选用的。这个框架是你导入的框架。如果其中某些部分不适用，你可以分叉它、调整它或绕过它。

我认为那个形状是错误的 ，这就是为什么每个长期运行的代理团队最终都会从头重写其框架的原因。这个框架不是单一的东西。它是十到十二个不同的东西捆绑在一起，因为周围的生态系统没有提供一种方式来组合它们。

[Pi agent](https://github.com/earendil-works/pi/tree/main/packages/coding-agent) 包走在正确的轨道上，但它们仍然处于“添加另一个服务并将其与所有其他服务集成”的范式中。iii 引擎将所有工作器一视同仁，并完全移除了集成逻辑。这个提供商路由器、凭证库、策略引擎、审批网关、模型目录、会话存储、预算跟踪器、通话后钩子分发、 以及持久化回合循环是独立的关注点。 这些都可与你的队列、HTTP/API 服务器、流处理甚至浏览器工作线程互操作。一个将它们打包成一个整体的框架，是在向你推销一种你本不必做出的权衡。

潜在的赌注

[iii](https://iii.dev/) 即它们不应该是一个整体。应该有一组工作单元在共享引擎上，每个都可替换，每个都独立版本化，每个都通过一个单一原语连接： 一个触发器（iii.trigger()） 每个其他工作单元也使用。工具链变成了可安装工作单元的堆栈，并且" 构建你自己的 "不再意味着" 分叉一个框架。"而是意味着" 替换几个工作单元。"

这篇文章将详细介绍其实际运作情况。驱动当前 iii 代理运行的完整技术栈、每个层级为何是独立的工作单元，以及如何替换其中任何一个组件。

#### 代理必须完成的15项工作

如果剥离生产代理的职责，只保留其核心职责，你会得到一个大致如下的列表：

1. 接受来自客户端的轮次请求并持久化它
2. 获取被调用的任何模型提供商的凭证
3. 查看所选模型实际能做什么（视觉、工具、流式处理、上下文窗口）
4. 驱动每回合状态机，配置，流助手，运行工具，操控，拆除
5. 加载并提供描述每个功能的请求格式、错误码和使用说明的技能体
6. 组装系统提示、模式段落、身份前言、工作目录和默认技能附录
7. 当模型生成 token 时，将 token 流式回传给客户端
8. 在每个工具调用（即函数）运行之前，对照策略进行检查
9. 暂停需要人工决策的工具调用，并将答案路由回右转
10. 跟踪 LLM 支出，对比每工作区或每代理的预算
11. 在工具调用前后运行钩子（日志记录、数据脱敏、自定义副作用）
12. 将会话持久化为分支树，以便分叉和恢复工作
13. 当上下文窗口填满时，压缩会话历史
14. 发出 UI 订阅的事件流
15. 我明白了，这是每个代理公司大楼中缺少的一环。在每一步都贯穿一个 OpenTelemetry 跟踪，以便你可以调试它。

每个专业型代理都会运用其中的大部分功能。昂贵的代理则会运用全部功能。廉价的代理则会偷工减料，等到进入生产阶段后再重新修补这些被省略的部分。框架将这些功能打包成一个单体应用，并发布每个功能的单一版本。最后这部分正是让你付出代价的地方，因为一年后，你会发现你想要的策略引擎并非框架所提供的版本，而替换它意味着要替换整个代理的功能体系。

iii harness 将这十三个任务中的每一个作为独立的 worker 部署在

[workers.iii.dev](https://workers.iii.dev/) 注册中心。每个都使用相同的 WebSocket 协议。每个都在同一个引擎总线上注册函数和触发器。每个 iii worker 都可以通过 SDK 用任何语言添加、替换和编写。

这一点很重要的原因是：表格中的每个方框都是有人可以递给你一个不同工作器的地方，而你保留其余部分。不喜欢静态模型目录？插入一个注册了 models::list 并从实时 API 读取的工作器。不喜欢基于文件的凭证？插入一个注册了 auth::get\_token 并从密钥管理器读取的工作器。想要一个不同的 turn FSM 来处理分支不同的工作流？替换 turn-orchestrator，每个依赖项都会调用 run::start 并通过同一总线读取 turn\_state，因此堆栈的其余部分不会改变。

#### 循环实际是如何运行的

一轮的形状如下，依次经过工人，按照他们开火的顺序。

浏览器/命令行界面/聊天界面通过 POST 发送一个轮次到 harness::trigger，携带 {session\_id, message\_id, payload}。harness 元工作器将 payload 转发到 run::start。该跳转存在的目的是让 OpenTelemetry span 包装器能够将会话和消息 ID 作为附加信息进行注入，从而传播到栈中每个工作器的每个嵌套 iii.trigger 调用。另一端的跟踪树是一个连通图。

run::start 到达 turn-orchestrator。它持久化运行请求，在 iii 状态中初始化初始的 TurnStateRecord，位置在 会话/&lt;sid&gt;/turn\_state，并立即返回。实际工作发生在持久化的每个状态机器内部，由发布到 turn-step FIFO 触发。

两个终端状态是已停止（通过 finishSession() 干净退出）和失败（意外的处理器抛出路由到此处，确认队列以停止重试，并显示 message\_complete{stop\_reason:'error'} 以及 agent\_end 以让 UI 显示原因）。拆除是从任何回合结束路径调用的内联 finishSession() 端口，而不是单独的入队步骤。

配置会完成三件事。它启动一个

[iii-sandbox](https://github.com/iii-hq/iii/tree/main/crates/iii-worker/src/sandbox_daemon) 微型虚拟机（如果运行需要隔离执行）。它会为 system\_default\_skills 中的每个命名空间调用 directory::skills::download（默认 \["iii://iii-directory/index"\]) 因此 iii-directory 会预缓存运行启动时使用的技能主体。并且它会分三层构建系统提示：从 run\_request.mode 中选择的模式段落（计划、询问或代理）、教导模型 agent\_trigger 约定和 directory::skills::get 按需发现模式的 iii 身份前言，以及代理启动时使用的默认技能的附加索引。调用方可以通过在 run::start 时传递 system\_prompt 来覆盖整个提示；否则，编排器会构建它。函数模式来自实时引擎目录。

assistant\_streaming 调用 provider::&lt;name&gt;::stream，针对匹配运行的 provider 字段的任意 provider worker。provider worker 通过 auth::get\_token（auth-credentials）拉取凭证，将模型的 SSE 响应流式传输到 iii 通道，orchestrator 排空该通道并在 agent::events 上发出 message\_update 事件以支持 UI 的扇出。通道创建和读取循环在 provider-stream.ts 中的基于拉取的 MessagePump 之后运行，因此流状态保持专注于状态转换。

当助手返回工具调用时，有限状态机进入 function\_execute。每个工具调用都经过 dispatchWithHook，这是编排器中的唯一关键节点。consultBefore 直接调用 policy::check\_permissions，超时时间为 5 秒。策略工作器（默认栈中的 harness 元工作器）读取 iii-permissions.yaml，将调用的函数 ID 与规则集进行匹配，并返回三种结果之一：

- 允许： 调度进行；编排器触发目标函数并写入结果
- 拒绝： 调度短路使用 DenialEnvelope，结果成为拒绝记录
- 待审批： 单个呼叫进入该轮次的待审批列表。批次中的其余部分继续分配。仅当一个或多个条目处于待处理状态时，该轮次才会转换到 function\_awaiting\_approval。

审批唤醒是响应式且共享的。编排器精确注册一个 turn::on\_approval 状态触发器，针对范围审批。当控制台调用 approval::resolve 时，审批网关工作器会写入 approvals/&lt;%sid%&gt;/&lt;%cid%&gt; = {决策, 原因} 到 iii 状态。该写入触发 turn::on\_approval，从而推进受影响的会话。function\_awaiting\_approval 仅读取刚刚到达的决策，在每个决策到达时进行分发（允许变为预批准分发，拒绝或中止变为合成拒绝），并且当 awaiting\_approval\[\] 为空时推进。无需注册每次调用的恢复函数。无需启动重新扫描以恢复待处理的审批。一个触发器覆盖所有会话。

构造性故障关闭：如果策略工作器不可达或 5 秒超时触发，consultBefore 以 gate\_unavailable 信封拒绝呼叫。如果 iii::durable::publish 自身出错，钩子扇出返回 publish\_failed: true，编排器将其视为拒绝。

一些减少延迟的优化由此实现。函数调用后的钩子在主题没有注册持久化订阅者时，通过订阅者状态缓存短路 \`publish\_collect\`，每次执行的函数调用减少约 500 毫秒。\`tearing\_down\` 被内联到 \`finishSession()\` 中，每次轮次减少一次持久化队列跳转。上下文压缩订阅编排器在轮次边界发出的专用 \`agent::turn\_end\` 流，因此压缩器的唤醒是按轮次而非按事件进行。session 创建扇出状态触发器仅通过作用域进行控制并在进程内匹配，因此之前每次写入的 \`harness::session::is\_create\_event\` RPC 已被移除。

批处理完成后，steering\_check 决定是继续、停止还是达到 max\_turns。如果继续，循环回到 assistant\_streaming。如果停止或达到 max\_turns，finishSession() 将内联运行：发送 agent\_end，释放沙箱，转换到停止状态。

在整个运行过程中，每个参与的工作器都会发出带有

iii.session.id、

iii.message.id

、以及

iii.function.id

的 OTel 跨度。这些标签是引擎的 engine::traces::group\_by 读取的内容，用于在 traces UI 中填充“按会话分组”/“按消息分组”/“按函数分组”选项。插桩是自动的：src/runtime/worker.ts 包装每个 registerFunction 函数，在代理中，因此每个工作器的代码无需记住添加跨度。

#### 构建你自己的

有趣的是，上面提到的这些工作者都没有什么特别之处。每一个工作者都是一个进程，它会向引擎打开一个 WebSocket 连接，注册一些函数和触发器，然后运行。这个契约与每个应用工作者使用的契约是相同的。这个框架是基于你构建业务逻辑所使用的相同原语构建的。

这意味着“构建你自己的框架”分解为与“编写任何工作器”相同的操作。你选择想要替换的层，编写一个在总线上注册相同函数的工作器，然后添加该工作器，栈的其余部分开始使用你的工作器。

上面的工作器表中没有显示两个层级，但它们对框架的行为方式很重要。技能是每个工作器宣告其功能的方式。每个工作器都可以在 iii://&lt;worker&gt;/&lt;function&gt; 发布技能，代理会在首次调用该函数前通过 directory::skills::get 获取该技能。系统提示会按轮次由模式段落、iii 身份序言和运行配置的默认技能主体组成。两者均由总线驱动：技能由 iii-directory 工作器提供，系统提示由轮次编排器组装。两者均可替换。

五个具体的例子。

用实时 API 替换模型目录。 编写一个工作器，注册 models::list、models::get、models::supports。让它每 N 分钟从您的提供商的目录端点获取数据并进行缓存。发布它。iii worker 添加 your-org/dynamic-models-catalog。停止静态的 models-catalog 工作器。turn-orchestrator 永远不会察觉差异。它调用 iii.trigger('models::list')，引擎会路由到最近注册该函数 ID 的工作器。

添加一个新的提供程序。 这种形式下，provider-kimi 和 provider-lmstudio 已经验证过了。每个都是一个注册 provider::::stream 和 provider::::complete，从上游 API 中抽取一个 SSE 流到一个 iii 通道，并通过 budget::record 将模型使用情况写入 llm-budget。添加第五个提供程序是创建一个包含一个 iii.worker.yaml 和一个 register.ts 的文件夹。发布到注册表，或者保留在本地。turn-orchestrator 根据运行的 provider 字段选择提供程序；新的提供程序在工作程序连接的瞬间就可用了。

从私有制品仓库提供技能。编写一个工作器，注册 directory::skills::get 和 directory::skills::list，由你的内部文档系统或私有 S3 存储桶支持。停用或重命名默认的 iii-directory 工作器。编排器的引导过程会按每个命名空间调用 directory::skills::download；你的工作器进行响应。代理的“在调用新函数之前获取每个函数的技能”模式保持不变，因为数据传输格式相同。

完全覆盖系统提示。 run::start 接受一个可选的 system\_prompt 字段。传递它，编排器将逐字使用你的字符串，跳过模式段落 + 身份前言 + 技能附录组合。当你有一个现有的提示资源希望框架不做修改地遵循时很有用。技能下载仍在 bootstrap 中运行，因此代理保持 directory::skills::get 按需发现，即使使用自定义提示。

替换审批网关 UI 界面。默认审批网关工作器注册了 approval::resolve。Wire Schema 是一个函数调用：

```typescript
iii.trigger('approval::resolve', {
  session_id: '...',
  function_call_id: '...',
  decision: 'allow' | 'deny' | 'aborted',
  reason: 'optional human text',
})
```

处理器持久化 approvals/&lt;sid&gt;/&lt;cid&gt; = {decision, reason} 到 iii 状态。编排器的单个 turn::on\_approval 状态触发器会选取该记录并唤醒正确的会话。如果您希望从 Slack 而非控制台驱动审批流程，请编写一个 Slack 工作器，使其监听 /approve &lt;id&gt; 和 /deny &lt;id&gt; 斜杠命令 ，然后调用 approval::resolve 并传入正确的有效载荷。编排器永远不会察觉差异。整个审批门控工作器保持不变。您添加了一个新的工作器，而非替换了现有的那个。

如果你想要不同的策略引擎（OPA、Cedar、你自己的 DSL），编写一个注册 policy::check\_permissions 并返回 { decision, rule\_id?, matched\_constraint? } 的工作器。停用默认的策略工作器（该工作器封装在框架元工作器内部，因此你需要禁用该处理器或运行一个精简版的元工作器）。turn-orchestrator 的 consultBefore 方法无法察觉差异。相同的 5 秒超时、相同的失败-关闭语义、相同的接口形状。

这些例子的重点不是具体的替换，而是操作的形式。iii 堆栈中的每个线束层都可通过总线上的一个或两个函数 ID 访问。替换一个层就是编写一个会注册这些 ID 的 worker。系统的其余部分保持不变。

#### 这个线束是一个滑块，而不是一个岔路口

经典的框架之争将自身定义为“薄”与“厚”的对立。Anthropic 的“thin loop”与 LangGraph 的显式有向无环图（DAG）形成对比。这种框架假设你必须选择一方并接受它。

当框架由同一总线上的工作节点组成时，轻量版与完整版的区别仅在于安装的工作节点数量。轻量版框架由任务编排器、Anthropic 服务提供者、认证凭证以及一个最小化的框架元工作节点组成。就这些。没有审批流程、预算控制、策略引擎，也没有钩子分发。可运行任何内容。信任模型。适用于自主研究代理、实验循环以及任何内部场景。

一个厚框架由 13 个工作器、上下文压缩、自定义策略工作器、自定义审批门、Slack 集成的审批界面，以及执行每个工作区上限的预算工作器组成。适用于运行客户工作流的代理，其中每次工具调用都需要可审计，且每次模型支出都必须汇总到财务仪表板。

轻量架构与重量级架构之间的架构差异并非重写，而是配置变更。相同的传输协议、相同的追踪形状、相同的可观测性描述。通过在 config.yaml 中添加和移除工作节点来调整（配置）。其他一切保持不变。

它也适用于单个 worker 内部。turn-orchestrator 刚刚完成了一次重构，将其 FSM 从十一个状态简化为七个，删除了每次调用的 turn::approval\_resume::/ 机制，转而采用一个响应式的 turn::on\_approval 状态触发器来处理范围审批，并内联 tearing\_down 到一个结束会话()函数中。栈中的其他所有 worker（approval-gate、会话、llm-budget、providers、models-catalog、auth-credentials、hook-fanout、context-compaction）均保持不变。approval::resolve 的连接形状没有变动。契约保持有效。这就是组合带来的属性：对单个 worker 的一次重大内部重写是一个自包含的变更，因为每个相邻组件都是通过总线级函数 ID 与其通信的。

这是框架模型无法提供给你的部分。框架会为你选择滑块上的一个位置并锁定你。工作者模型则将滑块留在你手中。

## 解读（1）

### 2026-06-01 10:01:15

#### 一、总结

这篇文章的核心观点：

> **不要把 Agent 框架做成一个“大一统框架”，而应拆成一组可替换的 worker。**

传统方式：

- 直接用 LangChain、LangGraph、CrewAI 等框架
- 框架把模型、工具、记忆、审批、预算、策略、追踪等都打包好
- 问题是：一旦某个模块不适合，替换成本很高

iii 的思路：

- 每个能力都是一个独立 worker
- worker 通过统一协议连接到引擎
- 通过 `iii.trigger()` 调用彼此
- 想换哪一层，就写一个注册相同函数 ID 的 worker 替换掉

最终目标：

> **框架不是一个固定产品，而是一组可组合、可替换、可观测的工作单元。**

---

#### 二、深入浅出解读

##### 1. Agent 框架到底要做什么？

一个生产级 Agent 不只是“调用大模型”。

它还要处理：

- 用户请求
- 模型调用
- 工具调用
- 权限检查
- 人工审批
- 成本预算
- 凭证管理
- 会话持久化
- 上下文压缩
- 日志追踪
- UI 事件推送
- 错误处理

也就是说，Agent 框架本质上是一个：

> **让大模型安全、稳定、可控地干活的运行系统。**

---

##### 2. 传统框架的问题

传统框架像一个“整装厨房”：

- 灶台、冰箱、水槽、橱柜都给你配好了
- 用起来快
- 但如果你只想换水槽，可能要拆半个厨房

对应到 Agent 框架：

- 想换策略引擎，很难
- 想接自己的审批系统，很麻烦
- 想换预算系统，可能要绕过框架
- 想接企业密钥系统，也可能不顺

所以问题不是框架不好，而是：

> **框架太整体化，局部替换太难。**

---

##### 3. iii 的设计思路

iii 把 Agent 框架拆成很多 worker。

比如：

| 能力 | 对应 worker |
|---|---|
| 模型调用 | provider worker |
| 权限检查 | policy worker |
| 审批流程 | approval worker |
| 成本统计 | budget worker |
| 技能目录 | directory worker |
| 上下文压缩 | compression worker |
| 事件推送 | events worker |

每个 worker 都是独立进程。

它们通过统一方式通信：

```ts
iii.trigger("某个函数ID", payload)
```

这意味着：

> 只要新 worker 注册了同样的函数 ID，旧 worker 就可以被替换。

---

##### 4. 举个简单例子

假设默认模型目录是静态的。

但你想要一个动态模型目录：

- 每隔几分钟去供应商 API 拉取模型列表
- 缓存模型能力
- 告诉系统哪些模型支持视觉、工具调用、长上下文

你不用改整个框架。

只需要写一个 worker，注册：

```ts
models::list
models::get
models::supports
```

系统其他部分不用变。

这就是它说的：

> **构建自己的框架，不是 fork 一个框架，而是替换几个 worker。**

---

##### 5. “薄框架”和“厚框架”可以自由切换

传统框架通常分两类：

- 薄框架：简单、灵活，但功能少
- 厚框架：功能全，但复杂、绑定深

iii 的想法是：

> 薄和厚不是两种框架，而是同一个系统里 worker 数量的不同。

少装几个 worker，就是轻量版：

- 编排器
- 模型 provider
- 凭证管理
- 基础运行

多装几个 worker，就是企业版：

- 审批
- 策略
- 预算
- 日志
- 追踪
- Slack 审批
- 上下文压缩

区别只是配置，不是重写。

---

#### 三、我的意见

我认为这个方向是对的，尤其适合生产级 Agent。

##### 优点

- **可替换**：哪个模块不好用，就换哪个
- **可扩展**：新增 provider、审批、预算系统都更自然
- **可观测**：统一追踪每次调用，方便排查问题
- **更适合企业场景**：权限、审批、成本控制都可以单独治理
- **避免框架锁死**：不会被某个大框架的设计绑架

##### 但也有代价

这种架构更像“微服务版 Agent 框架”。

所以会带来：

- 部署更复杂
- 调试链路更长
- worker 版本管理更麻烦
- 对团队工程能力要求更高

简单项目未必需要。

如果只是做 Demo、小工具、内部实验，用 LangChain、OpenAI Agents SDK 这类框架可能更快。

但如果是：

- 企业 Agent
- 多租户系统
- 高权限工具调用
- 成本敏感业务
- 需要审计和审批的工作流

那么这种 worker 化、可插拔架构会更有价值。

---

#### 四、一句话结论

> **这篇文章主张：未来的 Agent 框架不该是一个固定框架，而应是一套可插拔 worker 组合。你不是“选框架”，而是在组装自己的 Agent 运行系统。**

## 结构化（1）

### 2026-06-01 10:07:15

#### 文章精炼总结：如何构建你自己的代理框架？

本文核心观点是：**未来的代理框架不应是一个难以拆分的“大框架”，而应是一组可替换、可组合、可独立部署的工作单元。**  
iii 提出的方案是用统一的 `iii.trigger()` 触发机制，把代理运行所需的能力拆成多个 worker，让开发者通过“替换组件”而不是“重写框架”来构建自己的代理系统。

---

##### 1. 传统代理框架的问题：太像“整体套装”

大多数代理团队不会自己构建框架，而是直接采用现成方案，例如：

- LangChain
- LangGraph
- OpenAI Agents SDK
- Anthropic SDK
- CrewAI
- AutoGen

这些框架通常把循环、工具调用、记忆、编排、权限、模型适配等能力打包在一起。

**问题在于：**

- 你导入的是一个整体框架；
- 某一部分不适合时，只能分叉、魔改或绕过；
- 一年后如果想替换某个核心模块，比如策略引擎，可能被迫改动整个代理系统。

作者认为，代理框架不应该是一个整体，而应该是一组在共享引擎上运行的独立工作单元。

---

##### 2. iii 的核心设想：用 worker 代替单体框架

iii 的基本思路是：

> 每个代理能力都做成一个独立 worker，通过统一的 WebSocket 协议连接到引擎，并注册函数和触发器。

这些 worker 之间通过一个共同原语连接：

```ts
iii.trigger()
```

也就是说，框架不再是一个庞大的包，而是一组可以安装、替换、组合的 worker。

通俗理解：

- 传统框架像一整套固定装修的房子；
- iii 更像乐高积木；
- 你可以保留大部分积木，只替换不合适的几块。

因此，“构建你自己的框架”不再意味着从头写一个框架，而是：

> 选择你需要的 worker，替换你不满意的 worker，补上缺失的 worker。

---

##### 3. 一个生产级代理需要完成的核心工作

文章列出生产代理通常需要承担的一系列任务，包括：

1. 接收客户端请求并持久化；
2. 获取模型供应商凭证；
3. 判断模型能力，例如视觉、工具调用、流式输出、上下文窗口；
4. 驱动每一轮对话的状态机；
5. 加载技能描述、请求格式、错误码和使用说明；
6. 组装系统提示词、身份说明、默认技能列表等；
7. 将模型生成的 token 流式返回客户端；
8. 在工具调用前进行权限和策略检查；
9. 对需要人工判断的工具调用进行暂停和审批；
10. 追踪 LLM 成本，并与预算对比；
11. 在工具调用前后执行钩子，例如日志、脱敏、副作用；
12. 将会话保存成可分叉和恢复的树状结构；
13. 上下文窗口满时压缩历史；
14. 向 UI 发出事件流；
15. 通过 OpenTelemetry 贯穿追踪，方便调试。

作者强调：  
**便宜的代理系统往往会省略其中一些能力，但到了生产环境后又不得不补回来。**

iii 的做法是把这些任务拆成独立 worker，而不是塞进一个整体框架中。

---

##### 4. iii harness 的运行方式：每一层都是 worker

iii harness 将代理运行所需能力拆成多个 worker，部署在 `workers.iii.dev` 注册中心。

每个 worker 都具备以下特点：

- 使用同一套 WebSocket 协议；
- 在同一个引擎总线上注册函数和触发器；
- 可以独立添加、替换、升级；
- 可以用 SDK 以任意语言编写。

这意味着，如果你想换掉某个能力，不需要改整个系统，只需要提供一个注册相同函数 ID 的 worker。

例如：

- 原来的模型目录 worker 注册了 `models::list`；
- 你写的新模型目录 worker 也注册 `models::list`；
- 其他系统仍然调用 `iii.trigger('models::list')`；
- 编排器不需要知道背后换了实现。

---

##### 5. 一轮代理调用是如何运行的？

文章描述了一次代理运行的大致流程。

###### 5.1 客户端发起请求

浏览器、CLI 或聊天界面会发送一个轮次请求到：

```ts
harness::trigger
```

请求中包含：

```json
{
  "session_id": "...",
  "message_id": "...",
  "payload": "..."
}
```

随后，harness 元 worker 会把请求转发到：

```ts
run::start
```

这样做的目的，是让 OpenTelemetry 追踪能够把会话 ID 和消息 ID 注入整个调用链，方便之后调试。

---

###### 5.2 配置阶段：准备运行环境和提示词

配置 worker 会完成几件事：

- 如有需要，启动一个 `iii-sandbox` 微型虚拟机，用于隔离执行；
- 下载默认技能，例如 `iii://iii-directory/index`；
- 构建系统提示词，包括：
  - 当前模式，如计划、询问、代理；
  - iii 身份前言；
  - `agent_trigger` 约定；
  - 默认技能索引。

调用方也可以在 `run::start` 时直接传入 `system_prompt`，覆盖自动生成的提示词。

---

###### 5.3 模型流式输出

`assistant_streaming` 会调用对应模型供应商的 worker，例如：

```ts
provider::<name>::stream
```

provider worker 会：

- 通过 `auth::get_token` 获取凭证；
- 从模型供应商 API 获取 SSE 流；
- 将 token 流式写入 iii 通道；
- 编排器再将其转成 `message_update` 事件，推送给 UI。

这样，前端就能实时看到模型生成内容。

---

###### 5.4 工具调用与策略检查

当模型返回工具调用时，状态机会进入：

```ts
function_execute
```

每个工具调用都会经过核心节点：

```ts
dispatchWithHook
```

在真正执行工具之前，系统会调用：

```ts
policy::check_permissions
```

默认超时时间是 **5 秒**。

策略 worker 会读取 `iii-permissions.yaml`，根据规则返回三种结果之一：

- **允许**：继续执行工具调用；
- **拒绝**：直接返回拒绝记录；
- **需要审批**：暂停执行，等待人工决策。

---

###### 5.5 人工审批机制

对于需要人工确认的工具调用，系统会进入审批流程。

审批结果会写入状态路径：

```text
approvals/<sid>/<cid> = { decision, reason }
```

其中：

- `sid` 是 session ID；
- `cid` 是 function call ID；
- `decision` 可以是允许、拒绝或中止；
- `reason` 是人工填写的原因。

编排器只注册一个统一触发器：

```ts
turn::on_approval
```

这个触发器可以覆盖所有会话，不需要为每次工具调用单独注册恢复函数。

例如，可以这样调用审批接口：

```ts
iii.trigger('approval::resolve', {
  session_id: '...',
  function_call_id: '...',
  decision: 'allow' | 'deny' | 'aborted',
  reason: 'optional human text',
})
```

如果你想用 Slack 审批，而不是控制台审批，只需要写一个 Slack worker，监听：

```text
/approve <id>
/deny <id>
```

然后调用 `approval::resolve` 即可。  
编排器完全不需要修改。

---

##### 6. 如何“构建你自己的代理框架”？

作者强调，iii 中的 worker 本质上都只是普通进程：

- 连接到引擎；
- 注册函数；
- 注册触发器；
- 执行逻辑。

因此，构建自己的代理框架，本质上就是：

> 选择要替换的层，写一个注册同样函数 ID 的 worker，然后把它加入栈中。

文章给出几个具体例子。

---

###### 6.1 替换模型目录

如果你不想使用静态模型目录，可以写一个动态模型目录 worker，注册：

```ts
models::list
models::get
models::supports
```

它可以每隔 N 分钟从模型供应商接口拉取最新模型列表并缓存。

替换后，`turn-orchestrator` 不需要任何修改，因为它仍然只是调用：

```ts
iii.trigger('models::list')
```

---

###### 6.2 添加新的模型供应商

文章提到 `provider-kimi` 和 `provider-lmstudio` 已经验证过这种模式。

一个 provider worker 通常会注册：

```ts
provider::<name>::stream
provider::<name>::complete
```

它负责：

- 调用上游 API；
- 抽取 SSE 流；
- 写入 iii 通道；
- 通过 `budget::record` 记录模型使用量。

如果你要添加第五个模型供应商，只需要创建一个 worker 文件夹，包含：

- `iii.worker.yaml`
- `register.ts`

发布到注册表或本地运行即可。

只要 worker 连接上，引擎就能识别新 provider。

---

###### 6.3 用 Slack 替代默认审批界面

如果希望审批流程从 Slack 中完成，可以新建一个 Slack worker。

它监听 Slack 斜杠命令：

```text
/approve <id>
/deny <id>
```

然后调用：

```ts
approval::resolve
```

这样，审批入口改变了，但审批网关、编排器和状态机都不需要修改。

---

##### 7. iii 的框架不是“薄或厚”的二选一，而是一个滑块

传统框架讨论常常围绕：

- thin loop，轻量循环；
- LangGraph 这类显式 DAG，较重编排。

它们通常要求你选择一个固定立场。

但在 iii 的 worker 模型中，轻量和重量不是两种框架，而是同一套架构的不同配置。

###### 轻量版本可能只包含：

- 任务编排器；
- Anthropic provider；
- 认证凭证；
- 最小 harness 元 worker。

这种版本适合：

- 自主研究代理；
- 实验循环；
- 内部工具；
- 信任模型输出的场景。

###### 重量版本可能包含：

- 13 个以上 worker；
- 上下文压缩；
- 自定义策略 worker；
- 自定义审批门；
- Slack 审批界面；
- 工作区级预算控制；
- 完整审计和追踪。

这种版本适合：

- 客户工作流；
- 每次工具调用都必须审计的场景；
- 模型支出需要进入财务仪表盘的场景。

关键区别在于：

> 从轻量到重量，不需要重写，只需要在 `config.yaml` 中添加或移除 worker。

---

##### 8. 实践意义：不要重写框架，而是替换不合适的层

如果团队在使用现有代理框架时遇到瓶颈，例如：

- 策略引擎无法扩展；
- 审批界面和聊天界面强绑定；
- 凭证系统无法接入内部密钥管理；
- 预算记录在追踪系统之外；
- 工具调用无法统一审计；

作者认为，答案不一定是“重写一个框架”，而是使用一种从底层就可拆分的 substrate。

在 iii 中，你可以：

- 禁用某个 worker；
- 替换某个 worker；
- 添加新的 worker；
- 订阅 hook 扩展行为。

文章提到的通用 hook 机制是：

```ts
hook-fanout::publish_collect
```

##### 10. 最终观点：框架就是组合本身

文章最后总结了 iii 的核心赌注：

> 工具集不是你安装的某个东西，而是代理系统为了持久、安全、可观测运行而必须完成的一组任务。

传统框架把这些任务捆绑在一起，是因为底层缺乏组合机制。

iii 认为，一个足够小的基本单元就可以解决这个问题：

> 一个通过 WebSocket 连接引擎，并注册函数和触发器的 worker。

这种设计的价值在于：

- 每个任务可以独立实现；
- 每一层都可以替换；
- 所有调用共享同一协议；
- 所有调用共享同一追踪体系；
- 注册中心组件和自研组件没有本质区别。

因此，“构建你自己的代理框架”最终变成：

1. 选择已有 worker；
2. 编写缺失 worker；
3. 替换不合适 worker；
4. 把它们组合起来。

**框架不再是一个固定产品，而是组合本身。**

## 通俗精炼（1）

### 2026-06-15 10:54:39

#### 如何构建你自己的代理框架？

##### 核心观点

文章认为：**代理框架不应该是一个大而全的单体框架，而应该是一组可替换、可组合、可独立版本化的 Worker。**

每个 Worker 通过统一协议连接到共享引擎，并通过同一个原语交互：

```ts
iii.trigger()
```

因此，“构建自己的代理框架”不再意味着 fork 一个完整框架，而是：**按需替换、增加或移除某些 Worker。**

---

##### 生产级 Agent 需要做什么

一个真正可用的 Agent 框架，通常要承担很多底层能力，例如：

- 接收并持久化用户请求
- 管理模型供应商凭证
- 判断模型能力：视觉、工具调用、流式输出、上下文窗口等
- 驱动每轮对话状态机
- 加载工具 / 技能说明
- 组装系统提示词
- 流式返回模型输出
- 工具调用前做权限检查
- 支持人工审批
- 追踪 LLM 成本和预算
- 支持日志、脱敏、钩子扩展
- 持久化会话树，支持恢复和分叉
- 上下文过长时压缩历史
- 向 UI 推送事件流
- 全链路 OpenTelemetry 追踪

传统框架会把这些能力打包成一个整体，短期方便，长期会带来锁定问题：**当你只想替换策略引擎、审批系统或预算模块时，往往不得不改动整个框架。**

---

##### iii 的设计：Worker 化的 Agent 框架

iii 的思路是：把上述能力拆成多个独立 Worker。

每个 Worker 都是一个独立进程：

- 通过 WebSocket 连接 iii 引擎
- 注册自己的函数和触发器
- 通过统一总线被其他 Worker 调用
- 可以独立安装、替换、升级
- 可以用任意语言通过 SDK 编写

也就是说，框架本身不是一个固定产品，而是一个 **Worker 栈**。

---

##### 一轮 Agent 请求如何运行

一次用户请求大致会经历以下流程：

###### 1. 接收请求

前端、CLI 或聊天界面调用：

```ts
harness::trigger
```

请求中包含：

- session_id
- message_id
- payload

随后进入 `run::start`，并开始建立完整链路追踪。

###### 2. 初始化运行环境

配置 Worker 会做几件事：

- 启动 sandbox，用于隔离执行
- 下载默认技能说明
- 构建系统提示词
- 注入 Agent 身份、模式、默认技能索引等信息

###### 3. 调用模型供应商

流式 Worker 调用对应的模型 Provider，例如：

```ts
provider::<name>::stream
```

Provider Worker 会：

- 获取认证凭证
- 调用上游模型 API
- 将 SSE 流转成 iii 通道事件
- 向 UI 推送 `message_update`

###### 4. 执行工具调用

当模型返回工具调用时，编排器进入工具执行状态。

每个工具调用都会经过统一的检查点：

- 权限检查
- 策略判断
- 钩子执行
- 预算记录
- 审批流程

###### 5. 人工审批

如果工具调用需要人工确认，会进入等待状态。

审批系统只需要调用：

```ts
approval::resolve
```

并写入审批结果：

- allow
- deny
- aborted

编排器通过统一触发器唤醒对应会话，无需为每个审批单独注册恢复逻辑。

---

##### 如何“构建你自己的框架”

文章强调：你不需要重写整个框架，只需要替换对应 Worker。

###### 示例 1：替换模型目录

如果不想用静态模型列表，可以写一个 Worker 注册：

```ts
models::list
models::get
models::supports
```

让它定期从模型供应商 API 拉取能力信息并缓存。

编排器仍然调用同样的函数 ID，不需要感知底层实现变化。

---

###### 示例 2：添加新的模型供应商

新增 Provider 只需要实现：

```ts
provider::<name>::stream
provider::<name>::complete
```

它负责：

- 调用上游模型 API
- 处理流式输出
- 写入 token 使用量和成本

一旦 Worker 连接到引擎，新的 Provider 就自动可用。

---

###### 示例 3：替换审批入口

如果不想用控制台审批，可以写一个 Slack Worker：

- 监听 `/approve &lt;id>`
- 监听 `/deny &lt;id>`
- 调用 `approval::resolve`

审批网关和编排器都不用改，只是新增了一个审批入口。

---

##### 轻框架与重框架不再是二选一

传统框架常常在“薄框架”和“厚框架”之间做选择。

而 iii 的 Worker 模型让它变成一个滑块：

###### 轻量版

只安装必要 Worker：

- 编排器
- 模型 Provider
- 凭证管理
- 最小 harness

适合：

- 内部实验
- 自主研究 Agent
- 快速原型

###### 重量版

安装完整 Worker 栈：

- 策略引擎
- 审批系统
- 预算控制
- 上下文压缩
- Slack 审批
- 自定义钩子
- 完整可观测性

适合：

- 客户工作流
- 强审计场景
- 有预算和权限要求的企业 Agent

关键在于：**从轻到重不是重写架构，而是修改配置。**

##### 对产品和工程团队的启发

那么解决方案可能不是重写一个新框架，而是采用一种更底层的组合式架构：**让框架本身由可替换模块组成。**

- 模块可替换
- 能力可裁剪
- 架构可渐进演进

- 业务逻辑与框架能力使用同一套原语

最终，“构建自己的代理框架”变成：

1. 选择需要的 Worker  
2. 替换不合适的 Worker

**框架不再是一个固定产品，而是组合本身。**
