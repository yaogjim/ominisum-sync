**知识要点**

- Herdr将自动化拆分为布局、Pane和Agent三层：布局负责终端拓扑，Pane负责原始进程与输入输出，Agent负责可识别编码Agent的身份和生命周期。

### Agent automation

https://herdr.dev/docs/agent-automation/

Herdr can act as an automation layer for coding agents. A script can control them, or one agent can create work for other agents, inspect their state, and collect their results. The important part is choosing the primitive that matches the job.

Primitive Responsibility

Layout (`workspace`, `tab`, and pane topology) Create and organize terminal locations.

Pane Control a raw terminal: run commands, send input, read output, and wait for output.

Agent Control a recognized coding agent by name or pane and lifecycle state.

A pane exists whether or not it contains an agent. An agent is the recognized process currently running inside a pane. `agent start` therefore requires an existing shell pane and never creates, splits, or moves layout.

Creating a workspace also creates its first tab and root pane; creating a tab creates its root pane. Use the returned pane ID for the first process, and split only when that layout needs another terminal.

Creation commands print JSON. Capture IDs from the response instead of predicting them:

```

created=$(herdr workspace create --cwd ~/project --label api --no-focus)

pane_id=$(printf '%s\n' "$created" | jq -r '.result.root_pane.pane_id')

split=$(herdr pane split "$pane_id" --direction right --no-focus)

review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')
```

`workspace create` returns `.result.workspace`, `.result.tab`, and `.result.root_pane`. `tab create` returns `.result.tab` and `.result.root_pane`. `pane split` returns the new pane as `.result.pane`.

Moving a pane to another workspace changes its workspace-qualified pane ID. After any `pane move`, continue with `.result.move_result.pane.pane_id`; the response keeps the old value at `.result.move_result.previous_pane_id`. A running process keeps its launch-time Herdr environment, but the old `HERDR_PANE_ID` remains an alias for that terminal, so `--current` stays safe. New commands can still resolve the agent by name after the move, but a wait already in progress ends with `agent_not_running`.

Use pane commands for shells, tests, servers, CI watchers, and other ordinary terminal processes. Use agent commands when Herdr needs to understand which agent is running or whether it is `working`, `blocked`, `done`, `idle`, or `unknown`.

#### Agent identity and launch

Section titled “Agent identity and launch”

A pane ID such as `w1:p2` identifies the terminal location. An agent name such as `reviewer` is a convenient alias for the current agent in that pane. Names must match `[a-z][a-z0-9_-]{0,31}` and be unique among live agents. The alias is cleared when that agent exits, is released, or is replaced; it does not permanently rename the pane.

Agent commands accept either a unique live name or the pane ID that currently hosts the agent.

An available shell pane is at its interactive shell prompt: the shell itself owns the foreground, with no foreground command, editor, or agent running. Return the pane to its prompt before calling `agent start`.

`--kind` selects a supported agent and its canonical executable. Supported kinds are `pi`, `claude`, `codex`, `gemini`, `cursor`, `devin`, `agy`, `cline`, `omp`, `mastracode`, `opencode`, `copilot`, `kimi`, `kiro`, `droid`, `amp`, `grok`, `hermes`, `kilo`, `qodercli`, and `maki`. Arguments after `--` are passed unchanged to that executable.

`agent start` returns only after Herdr detects the expected agent in the same terminal and marks it ready for interactive input. Startup waits for 30 seconds by default; `--timeout` must be greater than 3000 and no more than 300000 milliseconds.

```

herdr agent start reviewer --kind codex --pane "$review_pane" -- -m gpt-5.4
```

Agents launched manually are detected automatically and can be addressed by pane ID. Give one a name when a stable human-readable target is useful:

```

herdr agent get w1:p2

herdr agent rename w1:p2 reviewer
```

#### Choose the control surface

Section titled “Choose the control surface”

Goal Command

Run a shell command and submit it `pane run`

Send literal text without Enter `pane send-text`

Send terminal keys or modifier chords `pane send-keys`

Wait for text or a regular expression `pane wait-output`

Start a supported agent in an existing pane `agent start`

Submit a prompt, optionally waiting for it `agent prompt`

Send keys to an agent’s interactive UI `agent send-keys`

Wait for agent lifecycle state `agent wait`

`agent prompt` submits text plus encoded Enter and honors the terminal’s live bracketed-paste mode. It can prompt an agent that is already working. Use `agent send-keys` for interactions such as `esc`, `up`, `enter`, or `ctrl+c`; `escape` is accepted as an alias for `esc`. Use the pane input commands when you deliberately want raw terminal control.

Pane input addresses the terminal regardless of its current occupant. Agent input resolves the live agent and rejects the operation if that agent no longer controls the pane.

`agent prompt --wait` submits immediately. When the agent starts from a non-working state, Herdr first requires an observed lifecycle change within five seconds. If the state sequence does not advance, it returns `agent_prompt_stalled` instead of waiting indefinitely; a caller `--timeout` of five seconds or less returns the normal `timeout` error. After activity is observed, it waits for the requested settled status. It does not track individual turns. If the agent is already working, completion of that active turn may satisfy the wait. Standalone `agent wait` observes the current agent and returns immediately if its status already matches. Both commands default to `idle`, `done`, or `blocked`. Repeat `--until` to accept several exact states, for example `--until idle --until done`; use `--until unknown` explicitly when needed. On `agent prompt`, `--until` requires `--wait`.

`idle` means the agent is ready for input and its tab has been seen in the focused Herdr UI. `done` is the same underlying idle state after background work finishes, until that tab is focused or `pane focus` / `agent focus` targets it. Reading through the CLI does not mark it seen. `blocked` means Herdr recognized an approval or question UI. `unknown` means an agent is present but Herdr cannot classify its lifecycle confidently; it does not prove successful completion. Use exact `--until` states when that distinction matters.

`pane wait-output` does not interpret agent lifecycle. It polls the selected terminal snapshot and searches it immediately, so text that was already present can match. The default source name is `recent`; matching treats that source as unwrapped recent output from the latest 80 rendered terminal rows. `--lines` changes that row limit, and `--regex` uses Rust regular-expression syntax and matches one line at a time.

At the CLI, both `pane read` and `agent read` print terminal text directly. The default is UTF-8 text with ANSI escapes stripped; use `--format ansi` or `--ansi` to preserve terminal escapes where the source exposes them. The `detection` source is always plain text. For recent sources, `--lines N` selects the last N rendered terminal rows before optional unwrapping; without it, reads default to 80 rows. For `visible` and `detection`, omitting `--lines` returns the full snapshot, while specifying it keeps the last N newline-delimited lines. The socket API returns the text at `.result.read.text`.

#### Known caveat: alternate-screen output

Section titled “Known caveat: alternate-screen output”

Full-screen agents such as Claude Code and OpenCode may render in the terminal’s alternate screen. Alternate-screen rows do not enter Herdr’s host scrollback. `--lines` can only request more rows from the pane’s available screen and host scrollback; it cannot create missing history. If increasing `--lines` returns no additional response text, the pane is probably using the alternate screen and those response rows are no longer retained. A larger font or smaller pane makes this more likely.

Ask the agent for concise responses, enlarge the pane or use a smaller font, or use the agent’s own transcript and scrolling controls. After scrolling inside the agent, use `--source visible` to read the page it currently renders.

After that failed read, ask the agent to write its complete response as Markdown in a temporary directory and reply only with the file path, then read the file directly. Use this only as a fallback; do not request file output in the initial prompt.

Successful `agent start`, `agent prompt`, and `agent wait` commands return the current agent at `.result.agent`. `pane wait-output` returns `.result.pane_id`, `.result.matched_line`, and the matched snapshot at `.result.read`.

Wait commands have no default timeout and can wait indefinitely. On timeout or another server error, CLI commands print a JSON error to stderr and exit with status 1; invalid CLI syntax exits with status 2.

Start a helper, give it work, and wait for that work to settle:

```

split=$(herdr pane split --current --direction right --no-focus)

review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')

herdr agent start reviewer --kind codex --pane "$review_pane" -- -m gpt-5.4

herdr agent prompt reviewer "Review the current diff" --wait --timeout 120000

herdr agent read reviewer --source recent-unwrapped --lines 120
```

Wait for an agent to ask for input, inspect it, and interact with its UI:

```

herdr agent wait reviewer --until blocked --timeout 120000

herdr agent read reviewer --source recent-unwrapped --lines 80

herdr agent send-keys reviewer esc
```

Run an ordinary process and wait for its output without treating it as an agent:

```

herdr pane run w1:p3 "just test --watch"

herdr pane wait-output w1:p3 --regex "passed|failed" --timeout 120000
```

See the [CLI reference](https://herdr.dev/docs/cli-reference/) for the complete command and option list. Shell completions expose the same command tree interactively.

### Agents

https://herdr.dev/docs/agents/

Herdr is built for running more than one coding agent at a time. Each agent stays in a real terminal pane with its shell, logs, prompts, and running processes intact. Herdr tracks which panes contain agents, rolls their state up to tabs and workspaces, and lets you jump straight to the pane that needs attention instead of polling every terminal by hand.

To coordinate agents from scripts or from another agent, see [Agent automation](https://herdr.dev/docs/agent-automation/).

Automatic detection works out of the box for common coding agents. The important difference is not whether Herdr can see an agent. It is which signal is allowed to author `idle`, `working`, and `blocked`.

Agent State authority Integration role

Pi lifecycle hooks when installed; otherwise screen manifest state and session

OMP lifecycle hooks when installed state

GitHub Copilot CLI screen manifest session

Devin CLI screen manifest session

Kimi Code CLI lifecycle hooks when installed; otherwise screen manifest state and session

Hermes Agent lifecycle hooks when installed; otherwise screen manifest state and session

Qoder CLI screen manifest session

Droid screen manifest session

OpenCode lifecycle plugin when installed; otherwise screen manifest state and session

Kilo Code CLI lifecycle plugin when installed; otherwise screen manifest state and session

MastraCode lifecycle hooks when installed state and session

Claude Code screen manifest session

Codex screen manifest session

Cursor Agent CLI screen manifest session

Amp screen manifest none

Grok CLI screen manifest none

Antigravity CLI screen manifest none

Kiro CLI screen manifest none

Maki screen manifest none

Detected but less thoroughly tested: Gemini CLI and Cline. Unsupported agents still run normally as terminal processes. They just may not get rich state unless you add an integration or report state over the socket API.

Herdr first detects the foreground process in each pane. After that, each pane has one status authority.

For agents with complete lifecycle hooks, the integration is authoritative when it is installed and actively reporting for the running pane. Herdr uses those hook reports for `idle`, `working`, `blocked`, and session identity. It does not also run screen manifest fallback for that same lifecycle authority. This avoids two competing sources of truth.

For agents without complete lifecycle hooks, Herdr identifies the foreground process and reads the live bottom-buffer screen snapshot. It evaluates TOML manifests against that snapshot to classify `idle`, `working`, and `blocked`. For agents that emit them, manifests can also match terminal title and progress (OSC) sequences as detection evidence; when that evidence is absent, screen rules carry detection on their own.

The screen snapshot comes from the recent bottom of the pane buffer, not the scrolled viewport. If you scroll back in Herdr, detection still follows the live agent UI at the bottom.

Claude Code, Codex, GitHub Copilot CLI, Droid, Qoder CLI, and Cursor Agent CLI integrations are intentionally not lifecycle authorities. They provide native session identity for restore, but their hooks do not cover the whole lifecycle. They can miss permission approval results, escape interrupts, or other transitions. For those agents, Herdr still uses screen manifest detection.

#### VMs and sandbox wrappers

Section titled “VMs and sandbox wrappers”

On Linux and macOS, a host-visible wrapper can hide the real agent process from Herdr. Set `HERDR_AGENT=<agent>` on the wrapper command to tell Herdr which existing agent screen manifest to use. For example, run `HERDR_AGENT=claude fence -- claude` on Linux or `HERDR_AGENT=claude nono run --profile claude-code -- claude` on macOS. The hint is scoped to that foreground process; setting it only inside a VM or container is not visible to Herdr, and you should avoid exporting it globally unless every inherited foreground process should be treated as that agent.

Blocked detection is deliberately strict for screen-manifest agents. Herdr only marks `blocked` when the live bottom-buffer snapshot matches known visible approval, question, or permission UI. If no manifest rule matches for a known agent, Herdr falls back to `idle` and labels that fallback as `default_known_agent_idle_fallback` in explain output.

This means unusual new agent prompts may initially show as `idle` instead of `blocked` until Herdr learns that screen shape. Those interactions should not make Herdr send input or take destructive action; they only affect the visible status and waits.

#### Detection manifests

Section titled “Detection manifests”

Bundled manifests live inside Herdr. Herdr also checks herdr.dev for remote manifest updates and applies valid per-agent rule updates automatically without requiring a Herdr restart. Remote manifests are stored in Herdr’s state directory. Set `[update] manifest_check = false` to disable background remote manifest checks.

Local overrides can replace a remote or bundled manifest from the platform config directory:

```

~/.config/herdr/agent-detection/<agent>.toml
```

Local overrides always win. Without a local override, Herdr uses the newer compatible manifest between the cached remote manifest and the bundled manifest in the running binary. On debug builds, the same config helper may use a development directory such as `herdr-dev`. Invalid override files are ignored with a warning and Herdr falls back to the cached remote or bundled manifest for that agent.

Remote manifests patch detection rules for agents Herdr already knows how to identify. Adding a completely new agent still requires a Herdr binary update for process detection, labels, and integration behavior.

The running server loads active manifests into memory on startup. Automatic remote manifest updates reload that in-memory cache after new rules are written. Run `herdr server update-agent-manifests` to fetch remote manifest updates immediately and reload the running server. After editing a local override manually, restart Herdr or run `herdr server reload-agent-manifests` to apply the file to the running server.

Use `herdr agent explain` when a pane shows the wrong state:

```

herdr agent explain <target>

herdr agent explain --file screen.txt --agent codex --json
```

Live explain is evaluated by the running server, so it reflects the active manifest cache. The explain output shows the agent, final state, whether screen detection was skipped by a full lifecycle authority, manifest source and version, cached remote version, local override shadowing, remote update status, matched rule, visible evidence flags, matcher and region evidence for evaluated rules, skipped-update reason for transcript viewers, and the idle fallback reason when no rule matched.

Herdr can run inside tmux as the outer terminal environment. Agent detection does not inspect tmux sessions launched inside a Herdr pane. If a shell framework auto-enters tmux inside Herdr, Herdr sees `tmux` as the pane process instead of the agent behind it.

The sidebar rolls state upward.

A blocked agent makes its pane, tab, and workspace look blocked. A working agent makes the workspace look active. A done agent stays visible until you view it.

This is the main Herdr workflow: start several agents, let them work in parallel, and use the sidebar to see which project needs a decision, which one is still running, and which one is ready to review.

#### Direct integrations

Section titled “Direct integrations”

Install the integration for each agent you use; it gives Herdr hook or plugin reports instead of screen detection alone:

```

herdr integration install claude

herdr integration status
```

Each supported agent has its own integration name and behavior. See [Integrations](https://herdr.dev/docs/integrations/) for the per-agent details and the full install list.

#### Custom agent labels

Section titled “Custom agent labels”

You can rename an agent target for display:

```

herdr agent rename w1:p1 reviewer

herdr agent rename reviewer --clear
```

Targets accept a unique live agent name or the pane ID that currently hosts the agent. Terminal IDs and bare agent-kind labels are not accepted.

#### Custom status labels

Section titled “Custom status labels”

Integrations report lifecycle state as semantic state only. Add display customization separately with pane metadata tokens.

```

herdr pane report-agent w1:p1 \

  --source custom:indexer \

  --agent docs-bot \

  --state working

herdr pane report-metadata w1:p1 \

  --source custom:indexer-display \

  --token summary=indexing
```

`state` controls waits, notifications, and rollups. The `summary` token is display-only and can be used as `$summary` in an Agent sidebar row.

Agent sidebar rows can also opt into `terminal_title` or `terminal_title_stripped`; neither appears in the default rows. The first shows the latest safety-normalized OSC 0/2 terminal title. The second removes one recognized leading activity or spinner glyph and following whitespace. Herdr owns these values on the server; they are ephemeral across a cold restart and remain independent of metadata titles and semantic agent state. Spinner animation can therefore update the raw title without producing a pane update when the stripped text stays the same.

#### Attach directly to an agent

Section titled “Attach directly to an agent”

Attach your current terminal to one agent terminal instead of the full Herdr UI:

```

herdr agent attach reviewer
```

Detach with `ctrl+b q`. Send a literal `ctrl+b` with `ctrl+b ctrl+b`.

Scroll with the mouse wheel or plain page up/page down. Normal input jumps back to the bottom.

Use `--takeover` if another direct attach client already owns input:

```

herdr agent attach reviewer --takeover
```

Use `herdr terminal attach <terminal_id>` when you want the same direct attach behavior for a non-agent terminal.

#### Herdr 多智能体终端与自动化：综合总结与深入解读

##### 一、综合总结

Herdr 可以理解为一个面向编码智能体的**持久化终端工作台与自动化控制层**。

它不是新的编码智能体，而是负责：

- 在真实终端窗格中运行 Claude Code、Codex、OpenCode、Kimi、Gemini 等编码智能体；
- 同时管理 Shell、测试、服务器、CI Watcher 等普通终端进程；
- 识别每个智能体当前处于工作、空闲、完成、阻塞或未知状态；
- 将窗格状态汇总到标签页和工作区，方便快速找到需要关注的位置；
- 允许脚本或其他智能体创建任务、发送提示词、等待状态、读取结果；
- 通过后台服务器保持进程持续运行，客户端断开后任务也不会停止；
- 支持本机使用、普通 SSH 远程使用、手机 SSH，以及本地客户端连接远程 Herdr。

Herdr 的核心设计是把不同职责拆成三层：

| 层级 | 负责什么 | 典型用途 |
|---|---|---|
| **Layout** | 创建和组织工作区、标签页、窗格 | 规划终端拓扑 |
| **Pane** | 控制原始终端 | 运行命令、发送按键、读取输出、等待文本 |
| **Agent** | 控制 Herdr 已识别的编码智能体 | 启动智能体、提交提示、等待生命周期状态 |

最重要的原则是：

> **操作终端时使用 `pane`，操作编码智能体的语义状态时使用 `agent`。**

例如：

- 启动测试、服务器或 Watcher：使用 `pane run`；
- 等待终端出现 `passed` 或 `failed`：使用 `pane wait-output`；
- 启动 Codex：使用 `agent start`；
- 给 Codex 分配审查任务：使用 `agent prompt`；
- 等待智能体完成、阻塞或空闲：使用 `agent wait`；
- 与智能体交互界面中的选项或快捷键互动：使用 `agent send-keys`。

#### 二、深入浅出解读

##### 1. Herdr 的本质：给多个智能体配一个“终端操作系统”

如果只运行一个编码智能体，普通终端通常已经足够。

但当你同时运行多个智能体时，很快会遇到这些问题：

- 哪个智能体还在工作？
- 哪个智能体正在等权限确认？
- 哪个已经完成，可以查看结果？
- 哪个终端在跑测试，哪个终端在跑服务？
- SSH 断开后任务会不会中止？
- 一个主智能体如何给其他智能体分派任务？
- 自动化脚本怎样知道智能体真的结束了，而不是只输出了一段文字？

Herdr 解决的就是这些协调问题。

可以把它类比为：

- **终端复用器**：进程持续运行，客户端可以随时连接或断开；
- **多智能体调度台**：知道各个窗格里运行的是什么智能体；
- **状态监控器**：区分 `working`、`blocked`、`done` 等状态；
- **自动化 API**：允许脚本创建窗格、启动智能体、分派任务和收集结果。

与纯粹的后台任务系统不同，Herdr 中每个智能体仍然运行在一个真实终端中，因此：

- Shell 环境保留；
- 日志和提示界面保留；
- 正在运行的子进程保留；
- 必要时人可以直接接管和操作。

---

##### 2. 后台服务器与客户端：为什么断开后任务仍能继续

Herdr 由两部分组成：

1. **后台会话服务器**
2. **一个或多个终端客户端**

真正的窗格、Shell、测试进程和智能体运行在后台服务器中。客户端只负责：

- 连接会话；
- 显示界面；
- 发送输入；
- 查看状态。

因此，使用：

```text
ctrl+b q
```

断开客户端后，窗格中的进程不会停止。

之后再次运行 Herdr，即可重新连接已有会话。

这和终端复用器的工作方式相似，但 Herdr 又额外理解编码智能体的身份和状态。只有停止 Herdr 服务器，才会结束整个会话及其中的窗格。

---

##### 3. 三层控制模型：Layout、Pane 与 Agent

这是理解 Herdr 自动化的关键。

##### 3.1 Layout：负责“终端放在哪里”

Layout 管理：

- Workspace：工作区；
- Tab：标签页；
- Pane：窗格。

它解决的是终端拓扑问题，例如：

- 为一个项目创建独立工作区；
- 在标签页中左右分屏；
- 为审查智能体增加一个新窗格；
- 将窗格移动到另一个工作区。

创建工作区时，会同时创建：

- 第一个标签页；
- 根窗格。

创建标签页时，也会自动创建其根窗格。

因此，不需要在创建工作区后再次创建第一个窗格。应该直接使用命令返回的根窗格 ID。

---

##### 3.2 Pane：负责“原始终端操作”

Pane 是终端位置。无论其中有没有智能体，窗格都存在。

适合使用 Pane 命令的对象包括：

- Shell；
- 测试命令；
- 开发服务器；
- CI Watcher；
- 日志监控；
- 普通 CLI 程序；
- 需要精确操纵的终端界面。

典型能力：

| 命令 | 用途 |
|---|---|
| `pane run` | 运行并提交 Shell 命令 |
| `pane send-text` | 发送文本但不按 Enter |
| `pane send-keys` | 发送 Enter、方向键、Ctrl 组合键等 |
| `pane read` | 读取终端内容 |
| `pane wait-output` | 等待文本或正则表达式出现 |

Pane 命令只关心终端，不关心其中的程序是不是编码智能体。

---

##### 3.3 Agent：负责“理解并控制编码智能体”

Agent 是 Herdr 在某个窗格中识别到的编码智能体进程。

适合使用 Agent 命令的场景：

- 启动受支持的编码智能体；
- 给智能体提交自然语言任务；
- 等待智能体工作完成；
- 判断智能体是否被权限确认或问题卡住；
- 读取智能体终端内容；
- 向智能体交互界面发送按键；
- 为智能体设置稳定、易读的名称。

典型命令：

| 命令 | 用途 |
|---|---|
| `agent start` | 在已有空闲窗格中启动智能体 |
| `agent prompt` | 给智能体提交提示词 |
| `agent send-keys` | 向智能体交互界面发送按键 |
| `agent wait` | 等待智能体进入特定生命周期状态 |
| `agent read` | 读取智能体所在终端的内容 |
| `agent rename` | 为当前智能体设置易读名称 |
| `agent explain` | 解释为什么智能体被判断为某种状态 |
| `agent attach` | 直接连接某个智能体终端 |

---

##### 4. Pane 与 Agent 不是同一个东西

这是最容易混淆的地方。

###### Pane 是位置

例如：

```text
w1:p2
```

它表示一个具体终端窗格。

###### Agent 是当前运行在这个位置里的智能体

例如：

```text
reviewer
```

它可能是运行在 `w1:p2` 中的 Codex。

如果智能体退出，窗格仍然存在，但 Agent 不再存在。换句话说：

> **窗格是房间，智能体是当前住在房间里的人。**

因此，`agent start` 的职责只是把一个智能体启动到已有窗格中，它不会：

- 创建工作区；
- 创建标签页；
- 分割窗格；
- 移动窗格。

调用 `agent start` 前，目标窗格必须处在可用 Shell 提示符状态，即：

- Shell 当前拥有前台；
- 没有前台命令；
- 没有编辑器；
- 没有其他智能体正在运行。

---

##### 5. 正确创建布局：不要猜测 ID

Herdr 的创建命令会输出 JSON。自动化脚本应从响应中提取 ID，而不是自己推测。

示例：

```bash
created=$(herdr workspace create \
  --cwd ~/project \
  --label api \
  --no-focus)

pane_id=$(printf '%s\n' "$created" |
  jq -r '.result.root_pane.pane_id')

split=$(herdr pane split "$pane_id" \
  --direction right \
  --no-focus)

review_pane=$(printf '%s\n' "$split" |
  jq -r '.result.pane.pane_id')
```

不同命令的返回位置如下：

| 创建操作 | 返回内容 |
|---|---|
| `workspace create` | `.result.workspace`、`.result.tab`、`.result.root_pane` |
| `tab create` | `.result.tab`、`.result.root_pane` |
| `pane split` | `.result.pane` |

这意味着可靠的自动化模式应该是：

1. 执行创建命令；
2. 解析 JSON；
3. 保存返回的真实 ID；
4. 用该 ID 执行下一步操作。

---

##### 6. 窗格移动后，ID 可能改变

Pane ID 是带工作区限定的。因此，当窗格移动到另一个工作区后，它的 ID 会发生变化。

移动响应中：

- 新 ID：`.result.move_result.pane.pane_id`
- 旧 ID：`.result.move_result.previous_pane_id`

移动后，脚本应该立即改用新 ID。

需要注意：

- 正在运行的进程仍然保留启动时的 Herdr 环境变量；
- 旧的 `HERDR_PANE_ID` 仍会作为该终端的别名，因此 `--current` 仍然安全；
- 新命令仍可以通过智能体名称找到它；
- 但在移动前已经开始的 `agent wait` 会以 `agent_not_running` 结束。

所以，如果自动化流程中会移动正在运行智能体的窗格，最好：

1. 先停止或避免已有等待；
2. 移动窗格；
3. 获取新 Pane ID；
4. 重新发起等待。

---

##### 7. Agent 名称只是活跃智能体的临时别名

可以给智能体设置名称，例如：

```bash
herdr agent rename w1:p2 reviewer
```

之后可以直接使用：

```bash
herdr agent get reviewer
herdr agent prompt reviewer "Review the current diff"
```

名称规则是：

```text
[a-z][a-z0-9_-]{0,31}
```

也就是：

- 必须以小写字母开头；
- 后续可以包含小写字母、数字、下划线或连字符；
- 最长 32 个字符；
- 在当前活跃智能体中必须唯一。

这个名称不是窗格的永久名称。以下情况会清除别名：

- 智能体退出；
- 智能体被释放；
- 窗格中的智能体被其他智能体替换。

Agent 命令通常可以接受：

- 唯一的活跃智能体名称；
- 当前承载该智能体的 Pane ID。

---

##### 8. 启动智能体

Herdr 可以在已有的空闲 Shell 窗格中启动支持的智能体：

```bash
herdr agent start reviewer \
  --kind codex \
  --pane "$review_pane" \
  -- -m gpt-5.4
```

其中：

- `reviewer` 是智能体名称；
- `--kind codex` 指定智能体类型；
- `--pane` 指定已有窗格；
- `--` 之后的参数原样传给智能体的标准可执行程序。

文档列出的可启动类型包括：

- `pi`
- `claude`
- `codex`
- `gemini`
- `cursor`
- `devin`
- `agy`
- `cline`
- `omp`
- `mastracode`
- `opencode`
- `copilot`
- `kimi`
- `kiro`
- `droid`
- `amp`
- `grok`
- `hermes`
- `kilo`
- `qodercli`
- `maki`

`agent start` 不会在启动命令提交后立即返回，而是会等待 Herdr：

1. 在同一终端中检测到预期智能体；
2. 确认它已经可以接受交互输入。

默认启动等待时间是 30 秒。`--timeout` 必须大于 3000 毫秒，且不超过 300000 毫秒。

手动启动的智能体也可能被 Herdr 自动识别。识别后可以先通过 Pane ID 操作，再为其命名：

```bash
herdr agent get w1:p2
herdr agent rename w1:p2 reviewer
```

---

#### 三、理解智能体生命周期状态

Herdr 不只是判断“进程还在不在”，还会尝试识别其语义状态。

主要状态包括：

| 状态 | 含义 |
|---|---|
| `working` | 智能体正在执行任务 |
| `blocked` | 智能体正在等待批准、权限确认或问题回答 |
| `idle` | 智能体可接受输入，并且其标签页已经在 Herdr UI 中被看过 |
| `done` | 后台工作已经结束，但对应标签页尚未被查看 |
| `unknown` | 智能体存在，但 Herdr 无法可靠判断生命周期状态 |

##### 1. `idle` 与 `done` 的区别

这两个状态底层都表示智能体已经不再工作，并且可以接受输入。

区别在于“是否已经被看过”：

- `done`：任务在后台完成，用户还没有打开对应标签页；
- `idle`：用户已经聚焦过该标签页，完成提醒被视为已经查看。

CLI 读取输出不会把 `done` 自动标记为已查看。只有：

- 聚焦对应标签页；
- 聚焦对应窗格；
- 使用 Agent/Pane 聚焦操作；

才会让其从 `done` 体现为已查看后的空闲状态。

这让 `done` 很像一个“未读完成通知”。

---

##### 2. `blocked` 的意义

`blocked` 表示 Herdr 识别到明显的：

- 权限批准界面；
- 确认问题；
- 选择提示；
- 需要人工判断的交互。

当某个智能体变成 `blocked` 时：

- Pane 会显示阻塞；
- Tab 会汇总为阻塞；
- Workspace 也会显示需要关注。

因此用户不必逐个打开终端轮询，只需要看侧边栏，就能找到等待决策的智能体。

---

##### 3. `unknown` 不代表成功完成

`unknown` 只表示：

> Herdr 知道这个窗格里有智能体，但无法有把握地判断它当前在做什么。

它不能作为“任务已经成功”的证据。

如果自动化流程对结果要求严格，应该明确等待：

```bash
--until done
```

或接受多个确定状态：

```bash
--until idle --until done
```

只有确实希望接收无法分类的状态时，才显式添加：

```bash
--until unknown
```

---

#### 四、状态是如何检测出来的

Herdr 的状态识别主要有两种来源。

##### 1. 生命周期 Hook 或插件

部分智能体可以通过集成 Hook 或插件主动报告：

- 当前状态；
- 会话身份；
- 是否工作；
- 是否阻塞；
- 是否空闲。

如果某个智能体拥有完整的生命周期集成，而且该集成已经安装并正在报告，那么这个集成就是该窗格的**状态权威来源**。

此时 Herdr 不会再同时使用屏幕规则推测状态，以避免两个来源相互冲突。

---

##### 2. 屏幕 Manifest 检测

对于没有完整生命周期 Hook 的智能体，Herdr 会：

1. 识别窗格前台进程；
2. 读取终端底部的实时屏幕快照；
3. 使用 TOML Manifest 规则匹配界面特征；
4. 判断智能体处于 `idle`、`working` 还是 `blocked`。

某些规则还可以使用：

- 终端标题；
- OSC 进度序列；
- 屏幕文本特征。

检测读取的是窗格缓冲区底部的实时画面，而不是用户当前滚动到的历史位置。因此，即使用户向上滚动查看旧内容，Herdr 的状态检测仍然跟踪底部的最新智能体界面。

---

##### 3. 为什么有些集成只提供会话身份，不负责状态

Claude Code、Codex、GitHub Copilot CLI、Droid、Qoder CLI、Cursor Agent CLI 等集成，可能可以提供原生会话身份，用于恢复会话，但不会被用作完整生命周期权威。

原因是它们的 Hook 可能遗漏：

- 权限批准后的结果；
- Escape 中断；
- 某些特殊界面转换；
- 其他生命周期变化。

因此，对这些智能体，Herdr 仍使用屏幕 Manifest 判断状态。

这体现了一个重要设计：

> **能识别会话，不等于能准确判断整个生命周期。**

---

##### 4. `blocked` 检测是故意保守的

对于依赖屏幕 Manifest 的智能体，只有当实时屏幕明确匹配已知的：

- 批准界面；
- 问题界面；
- 权限界面；

Herdr 才会标记为 `blocked`。

如果 Herdr 已经知道这是某种智能体，但没有任何状态规则匹配，它会回退为 `idle`，解释信息中会标注：

```text
default_known_agent_idle_fallback
```

这意味着某些全新的或不常见提示界面，可能暂时显示为 `idle`，而不是 `blocked`。

因此，自动化系统不应仅凭一个模糊状态就自动：

- 发送确认；
- 选择选项；
- 执行破坏性操作。

状态主要用于：

- 展示；
- 通知；
- 等待；
- 工作区汇总。

---

#### 五、诊断错误状态：`agent explain`

如果某个智能体显示了错误状态，可以使用：

```bash
herdr agent explain <target>
```

也可以针对保存的屏幕文本离线分析：

```bash
herdr agent explain \
  --file screen.txt \
  --agent codex \
  --json
```

解释结果可以显示：

- 识别到的智能体类型；
- 最终状态；
- 是否因为完整生命周期集成而跳过屏幕检测；
- Manifest 来源和版本；
- 本地覆盖情况；
- 远程更新状态；
- 匹配到的规则；
- 屏幕区域和匹配证据；
- 为什么没有使用某些更新；
- 为什么回退为默认空闲状态。

这是排查状态识别问题的首选工具。

---

#### 六、检测 Manifest 的更新和覆盖

Herdr 内置检测 Manifest，同时也会从 `herdr.dev` 检查远程规则更新。

远程更新的特点是：

- 只更新 Herdr 已知智能体的检测规则；
- 不需要升级 Herdr 二进制；
- 更新后可以重新加载到运行中的服务器；
- 不能借此增加全新的智能体类型。

完全新增智能体仍需要 Herdr 二进制更新，因为还涉及：

- 前台进程识别；
- 名称和标签；
- 集成行为；
- 可执行程序规则。

##### 本地覆盖

可以在平台配置目录中放置：

```text
~/.config/herdr/agent-detection/<agent>.toml
```

优先级大致是：

1. 本地覆盖；
2. 更新且兼容的远程缓存 Manifest；
3. Herdr 二进制内置 Manifest。

本地覆盖文件无效时，Herdr 会警告并回退到远程缓存或内置版本。

相关命令：

```bash
herdr server update-agent-manifests
```

立即获取远程更新并重新加载。

```bash
herdr server reload-agent-manifests
```

手动编辑本地规则后重新加载。

也可以在配置中关闭后台远程检查：

```toml
[update]
manifest_check = false
```

---

#### 七、发送任务与等待完成

##### 1. `agent prompt`

发送提示词：

```bash
herdr agent prompt reviewer "Review the current diff"
```

它会提交文本并模拟 Enter，同时遵循终端当前的 bracketed-paste 模式。

它甚至可以向已经处于 `working` 状态的智能体发送新提示，但这会带来一个语义问题：Herdr 跟踪的是整体生命周期，而不是单独的每一轮对话。

---

##### 2. `agent prompt --wait`

可以提交任务并等待状态稳定：

```bash
herdr agent prompt reviewer \
  "Review the current diff" \
  --wait \
  --timeout 120000
```

默认会接受：

- `idle`
- `done`
- `blocked`

也可以明确指定：

```bash
herdr agent prompt reviewer \
  "Review the current diff" \
  --wait \
  --until idle \
  --until done \
  --timeout 120000
```

需要注意：

- `--until` 在 `agent prompt` 上必须与 `--wait` 一起使用；
- 如果智能体原本不在工作状态，Herdr 会要求在 5 秒内观察到一次生命周期变化；
- 如果没有变化，会返回 `agent_prompt_stalled`，避免无限等待；
- 如果调用者设置的总超时不超过 5 秒，则会返回普通超时错误；
- 一旦观察到活动，Herdr 才开始等待指定的最终状态。

---

##### 3. `agent prompt --wait` 不跟踪单独回合

这是自动化时非常重要的限制。

Herdr 等待的是智能体整体状态变化，并不为每一次提示创建独立的“任务 ID”。

如果智能体在收到新提示前已经是 `working`：

- 当前正在进行的旧任务完成；
- 状态变成 `done` 或 `idle`；

就可能满足这次等待，即使新提交的提示还没有真正完成。

因此，更可靠的策略是：

1. 尽量在智能体空闲时发送新任务；
2. 对关键流程使用明确的输出协议；
3. 必要时让智能体输出特定完成标记；
4. 或让智能体把结果写入文件，由脚本读取文件确认。

---

##### 4. 独立的 `agent wait`

可以只等待状态，而不发送提示：

```bash
herdr agent wait reviewer \
  --until blocked \
  --timeout 120000
```

如果智能体当前状态已经符合条件，`agent wait` 会立即返回。

所有 Wait 命令默认都没有超时时间，可能无限等待。因此自动化脚本通常应该主动设置：

```bash
--timeout 120000
```

---

#### 八、终端文本等待与智能体状态等待的区别

##### `pane wait-output`

它只在终端快照中查找文本，不理解智能体生命周期。

例如：

```bash
herdr pane run w1:p3 "just test --watch"

herdr pane wait-output w1:p3 \
  --regex "passed|failed" \
  --timeout 120000
```

适合：

- 测试输出；
- 日志关键字；
- 服务启动标记；
- Watcher 结果；
- 普通 CLI 输出。

它会立即搜索当前快照，因此终端中以前已经出现过的文字也可能直接匹配。

---

##### `agent wait`

它等待的是语义状态：

```bash
herdr agent wait reviewer \
  --until done \
  --timeout 120000
```

适合：

- 等待智能体完成；
- 等待权限确认；
- 等待智能体重新空闲；
- 等待进入未知状态以便诊断。

两者的区别可以简化为：

> `pane wait-output` 问的是“屏幕上有没有这段文字”；  
> `agent wait` 问的是“智能体现在处于什么状态”。

---

#### 九、读取终端输出

`pane read` 和 `agent read` 在 CLI 中都会直接输出终端文本。

默认行为：

- 输出 UTF-8 文本；
- 去掉 ANSI 转义序列；
- 近期输出默认读取 80 个渲染行。

如果需要保留终端样式：

```bash
--format ansi
```

或：

```bash
--ansi
```

常见读取方式：

```bash
herdr agent read reviewer \
  --source recent-unwrapped \
  --lines 120
```

对于 Socket API，文本位于：

```text
.result.read.text
```

`pane wait-output` 成功时会返回：

- `.result.pane_id`
- `.result.matched_line`
- `.result.read`

---

#### 十、全屏智能体的输出丢失问题

Claude Code、OpenCode 等全屏智能体可能使用终端的 alternate screen，也就是“备用屏幕”。

备用屏幕有一个重要限制：

> 其中的历史行不一定会进入宿主终端的滚动缓冲区。

因此，即使增加：

```bash
--lines 200
```

也可能仍然读不到之前的完整回答。`--lines` 只能读取终端当前可用的画面和滚动历史，无法恢复已经不存在的内容。

以下情况更容易出现输出丢失：

- 窗格较小；
- 字体较大；
- 回答很长；
- 智能体使用全屏界面；
- 新内容把旧内容从备用屏幕中挤走。

##### 推荐应对顺序

1. 要求智能体回答简洁；
2. 放大窗格；
3. 使用更小字体；
4. 使用智能体自己的历史记录或滚动功能；
5. 在智能体界面内滚动后，使用：

```bash
--source visible
```

读取当前可见页。

如果仍无法获得完整回答，最后才使用文件回退方案：

1. 告诉智能体将完整响应写成 Markdown 文件；
2. 存到临时目录；
3. 让智能体只回复文件路径；
4. 脚本直接读取该文件。

文档特别建议：

> 不要在最初提示中就要求写文件。只有终端读取失败后，才将文件输出作为回退方案。

---

#### 十一、交互式处理阻塞状态

当智能体需要批准或回答时，可以先等待阻塞：

```bash
herdr agent wait reviewer \
  --until blocked \
  --timeout 120000
```

然后查看终端：

```bash
herdr agent read reviewer \
  --source recent-unwrapped \
  --lines 80
```

最后发送交互按键：

```bash
herdr agent send-keys reviewer esc
```

`escape` 也可以作为 `esc` 的别名。

适合 `agent send-keys` 的输入包括：

- `esc`
- `up`
- `down`
- `enter`
- `ctrl+c`

如果明确需要操作原始终端，而不在乎当前智能体身份，则使用 `pane send-keys`。

这两类输入的安全边界不同：

- Pane 输入始终发送到终端当前占用者；
- Agent 输入会先确认指定智能体仍然控制该窗格；
- 如果智能体已经退出或被替换，Agent 输入会拒绝执行。

因此，对自动化智能体交互而言，`agent send-keys` 通常更安全。

---

#### 十二、一个完整的辅助智能体工作流

下面是典型的“创建审查助手并等待结果”流程。

```bash
# 1. 在当前窗格右侧创建新窗格
split=$(herdr pane split \
  --current \
  --direction right \
  --no-focus)

# 2. 从 JSON 返回中获取新窗格 ID
review_pane=$(printf '%s\n' "$split" |
  jq -r '.result.pane.pane_id')

# 3. 在新窗格启动 Codex，并命名为 reviewer
herdr agent start reviewer \
  --kind codex \
  --pane "$review_pane" \
  -- -m gpt-5.4

# 4. 分配审查任务并等待状态稳定
herdr agent prompt reviewer \
  "Review the current diff" \
  --wait \
  --timeout 120000

# 5. 读取结果
herdr agent read reviewer \
  --source recent-unwrapped \
  --lines 120
```

这个流程体现了三层职责：

1. `pane split`：创建终端布局；
2. `agent start`：在已有窗格启动智能体；
3. `agent prompt/read`：进行语义化智能体控制。

---

#### 十三、状态汇总与多智能体工作流

Herdr 会将 Pane 状态向上汇总：

- 某个 Agent 被阻塞；
- 对应 Pane 显示阻塞；
- 对应 Tab 显示阻塞；
- 对应 Workspace 也显示阻塞。

类似地：

- 智能体工作时，工作区显示活跃；
- 智能体完成后，`done` 状态会一直可见；
- 用户查看对应标签页后，才变为已查看的空闲状态。

这使得 Herdr 的推荐工作模式非常清晰：

1. 启动多个智能体；
2. 给它们分配不同任务；
3. 让它们并行工作；
4. 通过侧边栏查看哪些项目仍在运行；
5. 优先处理 `blocked` 的智能体；
6. 查看 `done` 的结果；
7. 不再逐个终端手工轮询。

---

#### 十四、虚拟机、容器和沙箱包装器

在 Linux 或 macOS 上，某些宿主可见的包装器会隐藏真实智能体进程。

例如宿主系统可能只看到：

- `fence`
- `nono`
- 某个 VM 或沙箱启动器

而看不到其中实际运行的 `claude`。

这时可以在包装器命令上设置：

```bash
HERDR_AGENT=claude fence -- claude
```

或：

```bash
HERDR_AGENT=claude \
  nono run --profile claude-code -- claude
```

该变量用于告诉 Herdr：

> 对这个前台包装器进程，请使用 Claude 的屏幕检测 Manifest。

注意事项：

- 必须设置在宿主系统可见的包装器进程上；
- 只在 VM 或容器内部设置，宿主 Herdr 看不到；
- 不建议全局导出；
- 全局导出可能导致所有继承该变量的前台进程都被误判为某种智能体。

---

#### 十五、不要在 Herdr 窗格里再自动进入 tmux

Herdr 本身可以运行在 tmux 外层环境中，但它不会深入检查 Herdr 窗格内部再次启动的 tmux 会话。

如果 Shell 框架在每个 Herdr Pane 中自动进入 tmux，Herdr 看到的前台进程会是：

```text
tmux
```

而不是 tmux 内部的编码智能体。

结果可能是：

- 无法正确识别智能体；
- 无法获得丰富状态；
- 状态汇总失效。

因此，推荐关系是：

- 可以让 Herdr 运行在已有 tmux 环境中；
- 但不要让每个 Herdr 窗格自动再套一层 tmux。

---

#### 十六、直接连接某个智能体

如果不想打开完整 Herdr UI，可以直接连接某个智能体终端：

```bash
herdr agent attach reviewer
```

断开：

```text
ctrl+b q
```

如果要发送字面意义上的 `ctrl+b`：

```text
ctrl+b ctrl+b
```

查看历史：

- 鼠标滚轮；
- Page Up；
- Page Down。

输入普通字符后会跳回终端底部。

如果另一个直接连接客户端已经占有输入权，可以使用：

```bash
herdr agent attach reviewer --takeover
```

如果目标不是智能体，而是普通终端，可以使用：

```bash
herdr terminal attach <terminal_id>
```

#### 十七、本地、SSH、手机和远程客户端模式

Herdr 的原则是：

> **在代码、凭据和工作实际所在的机器上运行后台服务，从任何方便的位置连接过去。**

##### 1. 本地工作

代码在本机时，直接进入项目目录运行 Herdr。

适合：

- 本地开发；
- 本地智能体；
- 本地测试和服务；
- 不需要远程主机的场景。

---

##### 2. 普通 SSH 后运行 Herdr

流程是：

1. SSH 到有代码和凭据的远程主机；
2. 在远程 Shell 中运行 Herdr；
3. Herdr 服务器、窗格和智能体都运行在远程主机；
4. 断开后任务继续；
5. 下次 SSH 回去再运行 Herdr 即可恢复会话。

适合：

- 已经习惯先 SSH；
- 希望 Herdr 像远程 tmux 一样工作；
- 使用手机或平板 SSH 客户端；
- 希望部署方式最简单。

---

##### 3. 手机使用

不需要 Herdr 专用手机应用，也不需要 Web Dashboard。

只需：

1. 安装任意 SSH 客户端；
2. 连接到运行智能体的机器；
3. 启动 Herdr；
4. 查看同一个持久化会话。

Herdr 的 TUI 会适应较窄屏幕，仍可：

- 检查智能体状态；
- 切换工作区；
- 查看窗格；
- 处理阻塞请求。

---

##### 4. 本地终端作为远程轻客户端

可以从本机直接连接远程 Herdr，而不先打开远程 Shell：

```bash
herdr --remote workbox
```

或者：

```bash
herdr --remote ssh://you@server:2222
```

此时：

- Herdr 客户端运行在本机；
- 后台 Herdr 服务、窗格和智能体运行在远程主机；
- UI 通过 SSH 传回本地终端。

这种方式的优势是，本地客户端能够桥接本地桌面能力，例如：

- 本地图片剪贴板粘贴；
- 本地终端体验；
- 远程工作看起来更像本地工作。

如果先 SSH 到服务器再运行 Herdr，那么 Herdr 完全运行在远程机器上，无法访问本地桌面剪贴板。

对于常用主机，可以写入 SSH Config，例如：

```sshconfig
Host workbox
    HostName server.example.com
    User you
    Port 2222
```

然后使用：

```bash
herdr --remote workbox
```

---

##### 5. 如何选择远程模式

| 场景 | 推荐方式 |
|---|---|
| 本地项目 | 直接运行 `herdr` |
| 已经进入远程 SSH Shell | SSH 后运行 `herdr` |
| 手机或平板 | 手机 SSH 后运行 `herdr` |
| 希望像 tmux 一样管理远程任务 | SSH 后运行 `herdr` |
| 希望远程会话拥有本地终端体验 | `herdr --remote &lt;host>` |
| 需要桥接本地图片剪贴板 | `herdr --remote &lt;host>` |

---

#### 十八、自定义状态与显示信息

集成上报的是语义状态，例如：

```bash
herdr pane report-agent w1:p1 \
  --source custom:indexer \
  --agent docs-bot \
  --state working
```

这个 `state` 会影响：

- 等待命令；
- 通知；
- Pane/Tab/Workspace 状态汇总。

显示文本应单独通过元数据设置：

```bash
herdr pane report-metadata w1:p1 \
  --source custom:indexer-display \
  --token summary=indexing
```

其中：

- `state` 是行为语义；
- `summary` 只是展示文本。

不要用显示标签代替生命周期状态。

侧边栏还可以使用：

- `terminal_title`
- `terminal_title_stripped`

前者显示安全规范化后的终端标题，后者会去除一个可识别的前导活动图标或 Spinner 及后续空格。这样 Spinner 动画变化时，不会因为纯图标变化不断触发 Pane 更新。

#### 十九、错误、返回值与自动化注意事项

##### 1. 成功返回

以下命令成功时，当前 Agent 通常位于：

```text
.result.agent
```

包括：

- `agent start`
- `agent prompt`
- `agent wait`

`pane wait-output` 返回：

```text
.result.pane_id
.result.matched_line
.result.read
```

---

##### 2. 失败与退出码

Wait 命令默认可能无限等待。

发生超时或服务器错误时：

- CLI 将 JSON 错误打印到标准错误；
- 退出码为 `1`。

CLI 语法无效时：

- 退出码为 `2`。

脚本中可以据此区分：

- Herdr 服务器或运行时错误；
- 命令语法错误。

#### 二十、最佳实践清单

##### 布局管理

- 创建工作区后直接使用返回的根 Pane。
- 创建标签页后直接使用返回的根 Pane。
- 只有确实需要额外终端时才执行 `pane split`。
- 永远从 JSON 响应中提取 ID，不要猜测。
- Pane 移动后立即保存并使用新 ID。

##### Agent 启动

- `agent start` 前确保窗格位于干净的 Shell 提示符。
- 为长期自动化目标设置稳定、易读的 Agent 名称。
- 不要把 Agent 名称误当作 Pane 的永久名称。
- 对启动过程设置合理超时。

##### 命令选择

- Shell、测试、服务、日志：使用 `pane`。
- 提示词、生命周期、阻塞状态：使用 `agent`。
- 普通输出关键字：使用 `pane wait-output`。
- 智能体完成状态：使用 `agent wait`。
- 操作智能体 UI：优先使用 `agent send-keys`。

##### 等待与完成判定

- 自动化脚本应显式设置 `--timeout`。
- 不要把 `unknown` 当作成功。
- 关键流程应明确指定 `--until done` 或 `--until idle --until done`。
- 注意 `agent prompt --wait` 不跟踪独立对话轮次。
- 尽量在 Agent 空闲时提交新任务。

##### 输出读取

- 优先要求简洁响应。
- 合理放大 Pane 或缩小字体。
- 全屏 Agent 读不到历史时使用 `--source visible`。
- 文件输出只作为读取失败后的回退方案。

##### 状态检测

- 为常用 Agent 安装官方集成。
- 状态异常时先运行 `agent explain`。
- 沙箱包装器需要在宿主可见进程上设置 `HERDR_AGENT`。
- 不要在 Herdr Pane 内自动再进入 tmux。
- 不要依据模糊状态自动执行破坏性确认操作。

#### 二十一、最终理解

Herdr 最有价值的地方，不只是“同时开很多终端”，而是把多智能体工作变成了一套可观察、可恢复、可自动化的流程：

```text
创建布局
   ↓
在已有 Pane 中启动 Agent
   ↓
给不同 Agent 分派任务
   ↓
通过状态识别观察 working / blocked / done
   ↓
必要时人工接管
   ↓
读取结果并继续调度
```

它的设计边界也很明确：

- **Layout 管位置**
- **Pane 管终端**
- **Agent 管智能体语义**
- **Server 管持久运行**
- **Client 管连接和展示**
- **Hook/Manifest 管状态识别**

只要遵循这几个边界，就可以把 Herdr 用作：

- 多编码智能体工作台；
- 长时间远程开发环境；
- 智能体并行调度器；
- 脚本化代码审查系统；
- 人机协同的自动化终端控制层。

## 结构化（3）

### 2026-07-22 09:25:14

#### Herdr 多智能体终端与自动化全解

Herdr 是一个“后台会话服务器＋终端客户端”，可在真实终端窗格中并行运行、监控和调度多个编程智能体，同时保留 Shell、日志和进程状态。其核心原则是：**布局用 Layout、普通终端操作用 Pane、智能体生命周期管理用 Agent**。

##### 1. 自动化的三层基本能力

| 层级 | 主要职责 | 典型用途 |
|---|---|---|
| **Layout** | 创建和组织工作区、标签页、窗格 | 搭建终端布局、拆分窗格 |
| **Pane** | 直接控制终端 | 执行命令、发送按键、读取或等待输出 |
| **Agent** | 按名称或窗格管理已识别的编程智能体 | 启动、提示、等待状态、读取结果 |

关键区别：

- **窗格（Pane）始终存在**，无论里面是否运行智能体。
- **智能体（Agent）是窗格中当前被识别的进程**。
- `agent start` 只能在已有、处于 Shell 提示符的窗格中启动智能体，**不会自动创建、拆分或移动窗格**。
- 普通 Shell、测试、服务器、CI 监听器用 `pane`；需要判断智能体是工作、空闲、阻塞还是完成时用 `agent`。

---

##### 2. 创建布局与正确使用 ID

创建工作区时，会同时创建第一个标签页和根窗格；创建标签页时，也会创建其根窗格。创建命令返回 JSON，应从结果中提取 ID，不能自行猜测：

```bash
created=$(herdr workspace create --cwd ~/project --label api --no-focus)
pane_id=$(printf '%s\n' "$created" | jq -r '.result.root_pane.pane_id')

split=$(herdr pane split "$pane_id" --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')
```

返回字段包括：

- `workspace create`：`.result.workspace`、`.result.tab`、`.result.root_pane`
- `tab create`：`.result.tab`、`.result.root_pane`
- `pane split`：新窗格位于 `.result.pane`

移动窗格后，其带工作区前缀的 ID 会变化：

- 新 ID：`.result.move_result.pane.pane_id`
- 旧 ID：`.result.move_result.previous_pane_id`

旧的 `HERDR_PANE_ID` 会继续作为该终端的别名，因此 `--current` 仍然安全；但移动前已经开始的 `agent wait` 会以 `agent_not_running` 结束。

---

##### 3. 智能体身份与启动规则

窗格 ID（如 `w1:p2`）代表终端位置；智能体名称（如 `reviewer`）是当前智能体的易读别名。

名称要求：

- 格式：`[a-z][a-z0-9_-]{0,31}`
- 在存活的智能体中必须唯一
- 智能体退出、释放或被替换后，别名会自动清除
- 名称不会永久重命名窗格

启动前，目标窗格必须回到交互式 Shell 提示符，不能有前台命令、编辑器或其他智能体运行。

```bash
herdr agent start reviewer \
  --kind codex \
  --pane "$review_pane" \
  -- -m gpt-5.4
```

- `--kind` 选择智能体及其标准可执行文件。
- 支持约 **21 种**智能体，包括 Pi、Claude、Codex、Gemini、Cursor、Devin、Cline、OpenCode、Copilot、Kimi、Kiro、Droid、Amp、Grok、Hermes、Kilo、Qoder CLI、Maki 等。
- `--` 后的参数会原样传给智能体程序。
- 启动默认等待 **30 秒**；`--timeout` 范围为 **3000～300000 毫秒**。
- `agent start` 只有在 Herdr 检测到预期智能体并确认可交互后才返回。

手动启动的智能体也能自动检测，可先按窗格 ID 操作，再赋予名称：

```bash
herdr agent get w1:p2
herdr agent rename w1:p2 reviewer
```

---

##### 4. 根据任务选择控制命令

| 目标 | 命令 |
|---|---|
| 执行 Shell 命令并提交 | `pane run` |
| 发送文字但不按 Enter | `pane send-text` |
| 发送按键或组合键 | `pane send-keys` |
| 等待普通终端文本或正则匹配 | `pane wait-output` |
| 在现有窗格中启动智能体 | `agent start` |
| 提交提示词，可选择等待完成 | `agent prompt` |
| 操作智能体交互界面 | `agent send-keys` |
| 等待智能体生命周期状态 | `agent wait` |

使用原则：

- `agent prompt` 会发送文本和 Enter，并遵循终端当前的 bracketed-paste 模式；即使智能体正在工作，也可继续提交提示。
- `agent send-keys` 适合发送 `esc`、`up`、`enter`、`ctrl+c` 等界面操作。
- `pane` 输入始终直接作用于终端，不关心当前运行者。
- `agent` 输入会先确认目标智能体仍控制该窗格；若已退出或被替换，操作会被拒绝。

##### 5. 智能体状态与等待逻辑

Herdr 主要识别四种状态：

- **`idle`**：智能体可接收输入，且其标签页已在获得焦点的 Herdr 界面中被看过。
- **`done`**：后台工作结束后的空闲状态；在标签页被查看前保持为 `done`。
- **`blocked`**：检测到审批、权限请求或提问界面，需要人工处理。
- **`unknown`**：检测到智能体存在，但无法可靠判断生命周期；**不代表任务成功完成**。

CLI 读取内容不会将 `done` 标记为“已看过”；聚焦对应标签页、窗格或智能体才会改变这一状态。

默认情况下，`agent prompt --wait` 和 `agent wait` 接受 `idle`、`done` 或 `blocked`。可指定精确状态：

```bash
herdr agent wait reviewer \
  --until idle \
  --until done \
  --timeout 120000
```

重要行为：

- `agent prompt --wait` 会立即提交提示。
- 如果智能体原本不在工作状态，Herdr 要求在 **5 秒内观察到状态变化**；否则返回 `agent_prompt_stalled`，避免无限等待。
- 若调用方设置的超时不超过 5 秒，则返回普通超时错误。
- 它不追踪“具体哪一轮对话”；若智能体提交提示前已经在工作，当前轮结束也可能满足等待条件。
- 独立的 `agent wait` 若当前状态已匹配，会立即返回。
- `--until unknown` 必须显式指定。
- 所有等待命令默认**没有超时限制**，可能无限等待，应在自动化脚本中主动设置 `--timeout`。

---

##### 6. 读取终端输出与等待文本

`pane wait-output` 只搜索终端快照，不理解智能体生命周期：

- 会立即搜索，之前已经出现的文字也可能匹配。
- 默认读取源为 `recent`。
- 默认检查最近 **80 行**渲染后的终端内容。
- `--lines` 可调整行数。
- `--regex` 使用 Rust 正则语法，并按单行匹配。

示例：

```bash
herdr pane run w1:p3 "just test --watch"
herdr pane wait-output w1:p3 \
  --regex "passed|failed" \
  --timeout 120000
```

`pane read` 和 `agent read` 默认直接输出：

- UTF-8 文本
- 移除 ANSI 转义序列
- 可用 `--format ansi` 或 `--ansi` 保留样式

Socket API 中，文本位于 `.result.read.text`。

##### 7. 全屏智能体的输出丢失问题

Claude Code、OpenCode 等全屏程序可能使用终端的 **alternate screen（备用屏幕）**。该屏幕的内容不会进入 Herdr 主终端滚动缓冲区，因此：

- 增加 `--lines` 不能恢复已经消失的历史。
- 窗格较小或字体较大时，更容易丢失较长回答。
- 若增加 `--lines` 后仍没有更多内容，很可能是备用屏幕导致的。

建议依次处理：

1. 要求智能体简洁回答。
2. 放大窗格或缩小字体。
3. 使用智能体自身的记录和滚动功能。
4. 在智能体内滚动后，用 `--source visible` 读取当前页面。
5. 最后兜底：要求智能体将完整答复写入临时 Markdown 文件，只回复路径，再直接读取文件。

文件输出只应作为读取失败后的补救措施，**不要在初始提示中默认要求写文件**。

##### 8. 典型自动化流程

###### 启动审查智能体并等待结果

```bash
split=$(herdr pane split --current --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')

herdr agent start reviewer \
  --kind codex \
  --pane "$review_pane" \
  -- -m gpt-5.4

herdr agent prompt reviewer \
  "Review the current diff" \
  --wait \
  --timeout 120000

herdr agent read reviewer \
  --source recent-unwrapped \
  --lines 120
```

###### 等待人工审批并操作界面

```bash
herdr agent wait reviewer --until blocked --timeout 120000
herdr agent read reviewer --source recent-unwrapped --lines 80
herdr agent send-keys reviewer esc
```

成功的 `agent start`、`agent prompt`、`agent wait` 会在 `.result.agent` 返回当前智能体；`pane wait-output` 会返回窗格 ID、匹配行和快照。

错误处理：

- 超时或服务器错误：JSON 错误写入 stderr，退出码为 **1**
- CLI 语法无效：退出码为 **2**

##### 9. 多智能体检测与状态来源

Herdr 会先检测每个窗格的前台进程，然后为该窗格确定唯一的“状态权威来源”，避免多套信号互相冲突。

主要有两类检测方式：

1. **生命周期 Hook 或插件**
   - 集成已安装并持续报告时，直接提供 `idle`、`working`、`blocked` 和会话身份。
   - Pi、OMP、Kimi、Hermes、OpenCode、Kilo 等可使用完整或较完整的生命周期集成。

2. **屏幕 Manifest 检测**
   - 读取窗格底部的实时屏幕快照。
   - 根据 TOML 规则匹配空闲、工作、阻塞界面，也可结合终端标题和 OSC 进度序列。
   - Claude Code、Codex、GitHub Copilot CLI、Droid、Qoder CLI、Cursor Agent CLI 等仍以屏幕检测为生命周期依据，因为其原生 Hook 无法覆盖权限审批结果、Escape 中断等全部状态变化。

Gemini CLI 和 Cline 已可检测，但测试相对较少。未支持的智能体仍可作为普通终端程序运行，只是可能缺少丰富的状态识别。

即使用户在 Herdr 中向上滚动，检测仍针对窗格底部的实时界面，而不是当前查看的历史区域。

##### 10. 虚拟机、沙箱与 tmux 限制

Linux 或 macOS 上，沙箱包装器可能遮住真实智能体进程。可在宿主机可见的包装命令上设置：

```bash
HERDR_AGENT=claude fence -- claude
```

或：

```bash
HERDR_AGENT=claude nono run --profile claude-code -- claude
```

注意：

- 变量必须设置在 Herdr 能看到的宿主前台进程上；仅在 VM 或容器内部设置无效。
- 不建议全局导出，否则继承变量的其他进程也可能被误判。
- 对基于屏幕规则的智能体，`blocked` 判断非常严格：只有明确匹配审批、问题或权限界面时才标记阻塞。
- 未匹配到规则时，已知智能体会回退为 `idle`，并在解释结果中标记 `default_known_agent_idle_fallback`。

Herdr 可以运行在外层 tmux 中，但**不会深入检测 Herdr 窗格内部再次启动的 tmux 会话**。如果 Shell 自动进入内部 tmux，Herdr 看到的前台进程将是 tmux，而非其后的智能体。

##### 11. Manifest 更新与问题诊断

检测规则的优先级为：

1. 本地覆盖文件
2. 兼容且较新的远程缓存 Manifest
3. Herdr 内置 Manifest

本地覆盖路径：

```text
~/.config/herdr/agent-detection/<agent>.toml
```

Herdr 会从 `herdr.dev` 自动获取已知智能体的规则更新，并在无需重启的情况下重载。可通过配置关闭：

```toml
[update]
manifest_check = false
```

手动操作：

```bash
herdr server update-agent-manifests
herdr server reload-agent-manifests
```

排查状态误判：

```bash
herdr agent explain <target>
herdr agent explain --file screen.txt --agent codex --json
```

解释结果会显示最终状态、规则来源和版本、命中规则、证据、远程更新状态，以及未命中规则时的回退原因。远程 Manifest 只能更新 Herdr 已知智能体的检测规则；新增一种全新智能体仍需更新 Herdr 程序本身。

##### 12. 状态汇总、标签与直接连接

Herdr 会把状态从窗格向上汇总：

- 某智能体 `blocked`，其窗格、标签页和工作区都会显示阻塞。
- 某智能体 `working`，工作区显示活跃。
- `done` 会保持可见，直到用户查看。

可设置易读名称：

```bash
herdr agent rename w1:p1 reviewer
herdr agent rename reviewer --clear
```

也可通过语义状态和显示元数据分别控制行为与展示：

```bash
herdr pane report-agent w1:p1 \
  --source custom:indexer \
  --agent docs-bot \
  --state working

herdr pane report-metadata w1:p1 \
  --source custom:indexer-display \
  --token summary=indexing
```

其中：

- `state` 影响等待、通知和状态汇总。
- `summary` 仅用于显示，不改变智能体状态。

直接连接某个智能体终端：

```bash
herdr agent attach reviewer
```

- `Ctrl+B Q`：断开连接
- `Ctrl+B Ctrl+B`：发送字面量 `Ctrl+B`
- `--takeover`：接管已被其他直接连接客户端占用的输入
- 非智能体终端使用 `herdr terminal attach &lt;terminal_id>`

##### 13. 本地、SSH 与手机工作方式

Herdr 的窗格运行在后台服务器中，客户端只是连接并渲染界面。使用 `Ctrl+B Q` 退出客户端后，窗格、服务器和智能体仍继续运行。

###### 本地工作

在项目目录直接运行 `herdr`。它会自动启动或连接本地后台会话，不需要手动管理 Socket。

###### 先 SSH，再运行 Herdr

```bash
ssh you@server
herdr
```

适合：

- 已经在远程 Shell 中工作
- 使用手机或平板 SSH 客户端
- 希望像 tmux 一样使用远程 Herdr

断开 SSH 后，远程窗格仍继续运行；重新连接并执行 `herdr` 即可恢复。

###### 本地终端作为远程薄客户端

```bash
herdr --remote workbox
herdr --remote ssh://you@server:2222
```

此时本地 Herdr 通过 SSH 连接远程服务器，并将界面流式传回。优势是可桥接本地桌面能力，例如将**本地剪贴板图片粘贴到远程会话**；若先 SSH 再在服务器运行 Herdr，则无法访问本地桌面剪贴板。

###### 手机使用

无需专用移动 App 或 Web 控制台，只需普通 SSH 客户端。Herdr 的 TUI 会适应窄屏，可在手机上检查智能体状态、切换工作区和处理阻塞请求。

---

##### 14. 最佳实践总结

- 先创建布局并保存返回的真实 ID，再启动智能体。
- 普通终端程序使用 `pane`，涉及智能体身份和状态时使用 `agent`。
- 自动化等待务必设置超时，并用精确的 `--until` 区分 `idle`、`done`、`blocked` 和 `unknown`。
- 不要把 `unknown` 当作成功，也不要仅凭终端文字判断智能体生命周期。
- 多智能体并行运行后，通过侧边栏集中查看哪个项目仍在工作、哪个需要审批、哪个已完成。
- 对全屏智能体优先缩短输出、调整窗格或使用自身滚动记录，写文件只作为读取失败后的兜底方案。
- 本地使用 `herdr`，手机或普通远程 Shell 使用“SSH 后运行 Herdr”，需要本地剪贴板等桌面能力时使用 `herdr --remote`。

#### Herdr 多智能体终端与自动化全解

Herdr 是一个面向多编码智能体的持久化终端与自动化平台：它让多个 Agent、Shell、测试和服务在真实终端窗格中并行运行，并统一提供布局管理、状态检测、脚本控制和远程访问。使用时的核心原则是：**布局用 Layout、普通进程用 Pane、需要理解智能体生命周期时用 Agent。**

---

##### 一、Agent 自动化：选择正确的控制层级

Herdr 将自动化能力分成三类基础对象：

| 层级 | 主要职责 | 适用场景 |
|---|---|---|
| **Layout** | 创建和组织 Workspace、Tab、Pane | 搭建终端布局 |
| **Pane** | 执行命令、发送输入、读取或等待输出 | Shell、测试、服务、CI Watcher |
| **Agent** | 按名称或 Pane 控制编码智能体，并跟踪状态 | 提交任务、等待完成、处理审批 |

需要特别注意：

- **Pane 是终端位置**，无论里面有没有 Agent 都存在。
- **Agent 是 Pane 中当前被识别的智能体进程**。
- `agent start` 只能在已有且空闲的 Shell Pane 中启动 Agent，**不会自动创建、拆分或移动 Pane**。
- 创建 Workspace 时会自动生成第一个 Tab 和根 Pane；创建 Tab 时也会生成根 Pane。

###### 用返回的 JSON 获取 ID

创建命令会输出 JSON，应从结果中提取 Pane ID，不要自行猜测：

```bash
created=$(herdr workspace create --cwd ~/project --label api --no-focus)
pane_id=$(printf '%s\n' "$created" | jq -r '.result.root_pane.pane_id')

split=$(herdr pane split "$pane_id" --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')
```

主要返回字段：

- `workspace create`：`.result.workspace`、`.result.tab`、`.result.root_pane`
- `tab create`：`.result.tab`、`.result.root_pane`
- `pane split`：`.result.pane`

Pane 被移动到其他 Workspace 后，其完整 ID 会变化：

- 新 ID：`.result.move_result.pane.pane_id`
- 旧 ID：`.result.move_result.previous_pane_id`

旧的 `HERDR_PANE_ID` 仍可作为该终端的别名，因此 `--current` 仍然安全；但移动时已经执行中的 `agent wait` 会以 `agent_not_running` 结束。

##### 二、Agent 的身份、命名与启动

###### Pane ID 与 Agent 名称

- `w1:p2` 之类的 Pane ID 表示终端位置。
- `reviewer` 之类的名称是当前 Agent 的易读别名。
- 名称必须匹配：

```text
[a-z][a-z0-9_-]{0,31}
```

即以小写字母开头，最长 32 个字符，并且在存活 Agent 中唯一。

别名不等于永久重命名 Pane；当 Agent 退出、释放或被替换时，别名会被清除。Agent 命令既可以接收唯一的实时名称，也可以接收其所在 Pane ID。

###### 启动前提

调用 `agent start` 前，目标 Pane 必须回到交互式 Shell 提示符，不能有前台命令、编辑器或其他 Agent 正在运行。

例如，在指定 Pane 中启动 Codex：

```bash
herdr agent start reviewer \
  --kind codex \
  --pane "$review_pane" \
  -- -m gpt-5.4
```

`agent start` 会等待 Herdr 在同一终端中识别到目标 Agent，并确认其可以接收交互输入：

- 默认启动等待时间：**30 秒**
- `--timeout` 范围：**大于 3000 毫秒，且不超过 300000 毫秒**

`--kind` 支持的 Agent 包括：

`pi`、`claude`、`codex`、`gemini`、`cursor`、`devin`、`agy`、`cline`、`omp`、`mastracode`、`opencode`、`copilot`、`kimi`、`kiro`、`droid`、`amp`、`grok`、`hermes`、`kilo`、`qodercli`、`maki`。

手动启动的 Agent 也会被自动识别，可先用 Pane ID 操作，再赋予名称：

```bash
herdr agent get w1:p2
herdr agent rename w1:p2 reviewer
```

##### 三、如何选择 Pane 命令与 Agent 命令

| 目标 | 命令 |
|---|---|
| 执行 Shell 命令并回车 | `pane run` |
| 发送纯文本，不回车 | `pane send-text` |
| 发送按键或组合键 | `pane send-keys` |
| 等待文本或正则表达式 | `pane wait-output` |
| 在已有 Pane 中启动 Agent | `agent start` |
| 提交提示词，可等待状态稳定 | `agent prompt` |
| 向 Agent 交互界面发送按键 | `agent send-keys` |
| 等待 Agent 生命周期状态 | `agent wait` |

二者的关键区别：

- **Pane 输入**直接控制终端，不管里面当前运行什么。
- **Agent 输入**会先确认目标 Agent 仍控制该 Pane；如果 Agent 已退出或被替换，操作会被拒绝。

`agent prompt` 会发送提示词并附带 Enter，支持终端的 bracketed-paste 模式，也可以在 Agent 已工作时继续提交任务。对于 `Esc`、方向键、Enter、`Ctrl+C` 等界面操作，应使用：

```bash
herdr agent send-keys reviewer esc
```

其中 `escape` 也可作为 `esc` 的别名。

##### 四、等待 Agent 状态与理解生命周期

###### 主要状态

| 状态 | 含义 |
|---|---|
| `working` | Agent 正在处理任务 |
| `idle` | Agent 已可接收输入，且其 Tab 已在 Herdr UI 中被查看 |
| `done` | 后台任务完成，但对应 Tab 尚未被查看 |
| `blocked` | Herdr 识别到审批、权限或提问界面 |
| `unknown` | Agent 存在，但 Herdr 无法可靠判断状态 |

`done` 和 `idle` 的底层状态相近：后台任务完成后先显示为 `done`，当用户聚焦对应 Tab、Pane 或 Agent 后变为 `idle`。仅通过 CLI 读取输出不会将其标记为“已查看”。

`unknown` 只表示无法可靠分类，**不能证明任务成功完成**。如果状态区别很重要，应明确指定等待条件：

```bash
herdr agent wait reviewer \
  --until idle \
  --until done \
  --timeout 120000
```

需要接受 `unknown` 时必须显式添加：

```bash
--until unknown
```

###### `agent prompt --wait` 的行为

`agent prompt --wait` 会立即提交任务，然后等待目标状态：

- 默认等待 `idle`、`done` 或 `blocked`。
- `--until` 只有与 `--wait` 一起使用才有效。
- 如果 Agent 原本不在工作，Herdr 要求在 **5 秒内观察到状态变化**。
- 若 5 秒内状态没有推进，会返回 `agent_prompt_stalled`，避免无限等待。
- 如果调用方设置的 `--timeout` 不超过 5 秒，则返回普通超时错误。
- Herdr 等待的是生命周期状态，不会精确追踪某一轮对话；若 Agent 提交提示词前已在工作，当前任务结束也可能满足等待条件。

单独执行 `agent wait` 时，如果当前状态已经符合条件，会立即返回。

##### 五、读取和等待终端输出

###### `pane wait-output`

`pane wait-output` 不理解 Agent 生命周期，只在终端快照中查找文本或正则表达式：

```bash
herdr pane run w1:p3 "just test --watch"

herdr pane wait-output w1:p3 \
  --regex "passed|failed" \
  --timeout 120000
```

特点如下：

- 会立即搜索当前快照，因此之前已经出现的文字也可能匹配。
- 默认来源为 `recent`。
- 默认读取最近 **80 个渲染行**。
- `--lines` 可修改行数。
- `--regex` 使用 Rust 正则表达式语法，并且逐行匹配。

###### 读取格式

`pane read` 和 `agent read` 默认：

- 直接输出终端文本；
- 使用 UTF-8；
- 去除 ANSI 转义序列。

保留终端样式可使用：

```bash
--format ansi
```

或：

```bash
--ansi
```

用于检测的内容始终是纯文本。Socket API 中的读取结果位于：

```text
.result.read.text
```

##### 六、全屏 Agent 的输出读取限制

Claude Code、OpenCode 等全屏 Agent 可能使用终端的 **alternate screen（备用屏幕）**。备用屏幕中的内容不会进入 Herdr 主机滚动历史，因此：

- 增大 `--lines` 只能读取当前屏幕和已有 Scrollback；
- 它无法恢复已从备用屏幕消失的历史内容；
- 如果增加 `--lines` 后仍没有更多内容，通常说明该 Agent 使用了备用屏幕；
- 字体越大、Pane 越小，内容越容易丢失。

建议按以下顺序处理：

1. 要求 Agent 简短回答；
2. 放大 Pane 或缩小字体；
3. 使用 Agent 自带的历史记录和滚动功能；
4. 在 Agent 内滚动后，用 `--source visible` 读取当前页面；
5. 如果仍失败，再让 Agent 将完整答复写入临时目录中的 Markdown 文件，并只回复文件路径，然后直接读取该文件。

最后一种方案只应作为兜底手段，**不要在最初提示词中就要求文件输出**。

##### 七、自动化示例与错误处理

###### 启动审查 Agent 并等待完成

```bash
split=$(herdr pane split --current --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')

herdr agent start reviewer \
  --kind codex \
  --pane "$review_pane" \
  -- -m gpt-5.4

herdr agent prompt reviewer \
  "Review the current diff" \
  --wait \
  --timeout 120000

herdr agent read reviewer \
  --source recent-unwrapped \
  --lines 120
```

###### 等待 Agent 请求人工处理

```bash
herdr agent wait reviewer \
  --until blocked \
  --timeout 120000

herdr agent read reviewer \
  --source recent-unwrapped \
  --lines 80

herdr agent send-keys reviewer esc
```

成功的 `agent start`、`agent prompt` 和 `agent wait` 会在以下字段返回当前 Agent：

```text
.result.agent
```

`pane wait-output` 则会返回：

- `.result.pane_id`
- `.result.matched_line`
- `.result.read`

所有等待命令默认都**没有超时时间**，可能无限等待，自动化脚本中最好显式设置 `--timeout`。

错误退出码：

- 超时或服务端错误：JSON 错误写入 `stderr`，退出码为 **1**
- CLI 语法无效：退出码为 **2**

##### 八、多 Agent 状态检测机制

Herdr 可以同时运行多个编码 Agent。每个 Agent 都保留在真实终端 Pane 中，因此 Shell、日志、提示词和运行进程不会因切换界面而丢失。

Herdr 会：

- 检测哪些 Pane 正在运行 Agent；
- 将状态汇总到 Pane、Tab 和 Workspace；
- 在侧边栏提示哪个 Agent 正在工作、等待审批或已经完成；
- 让用户直接跳到需要关注的 Pane，而不是逐个检查终端。

###### 两类状态权威来源

Herdr 先检测 Pane 的前台进程，然后为每个 Pane 选择一个状态权威来源：

1. **完整生命周期 Hook 或插件**
   - 集成安装且正在上报时，由集成决定 `idle`、`working`、`blocked` 和会话身份。
   - 不再同时使用屏幕规则，避免两个来源互相冲突。

2. **屏幕 Manifest**
   - 对没有完整生命周期 Hook 的 Agent，Herdr 读取 Pane 底部的实时屏幕快照。
   - 使用 TOML 规则识别空闲、工作和阻塞状态。
   - 某些 Manifest 也会参考终端标题和 OSC 进度序列。

检测始终依据终端底部的实时内容；即使用户向上滚动，状态检测仍跟踪最底部的 Agent UI。

###### Hook 并不总是状态权威

Claude Code、Codex、GitHub Copilot CLI、Droid、Qoder CLI 和 Cursor Agent CLI 的集成主要提供原生会话身份恢复，但 Hook 无法覆盖完整生命周期，例如可能漏掉：

- 权限审批结果；
- Esc 中断；
- 其他状态转换。

因此这些 Agent 仍主要使用屏幕 Manifest 判断生命周期。

Gemini CLI 和 Cline 已能检测，但测试相对不充分。其他不受支持的 Agent 仍可作为普通终端进程运行，只是可能没有丰富的状态信息；也可以通过自定义集成或 Socket API 上报状态。

---

##### 九、VM、沙箱包装器与 tmux 限制

在 Linux 或 macOS 上，沙箱、VM 包装器可能隐藏真实 Agent 进程。此时可在宿主可见的包装命令上设置：

```bash
HERDR_AGENT=claude fence -- claude
```

macOS 示例：

```bash
HERDR_AGENT=claude nono run --profile claude-code -- claude
```

注意：

- 环境变量必须设置在 Herdr 能看到的宿主前台进程上；
- 只在 VM 或容器内部设置无效；
- 不建议全局导出，否则所有继承该变量的前台进程都可能被识别成该 Agent。

对于依赖屏幕规则的 Agent，`blocked` 判断非常严格：只有底部实时画面匹配已知的审批、提问或权限界面时才会标记为阻塞。无法匹配规则的已知 Agent 会回退为 `idle`，并在解释信息中标记：

```text
default_known_agent_idle_fallback
```

因此，新出现的特殊提示界面可能暂时被显示为 `idle`，而不是 `blocked`。这只影响状态显示与等待，不应触发自动输入或破坏性操作。

Herdr 可以运行在外层 tmux 中，但**不会穿透 Herdr Pane 内部再次启动的 tmux**。如果 Shell 框架自动进入内层 tmux，Herdr 看到的前台进程将是 tmux，而不是里面的 Agent。

##### 十、检测 Manifest 的更新与调试

Herdr 内置 Agent 检测 Manifest，也会从 `herdr.dev` 自动检查远程更新，无需重启即可应用有效规则。

关闭后台更新：

```toml
[update]
manifest_check = false
```

本地覆盖文件路径：

```text
~/.config/herdr/agent-detection/<agent>.toml
```

Manifest 优先级为：

1. 本地覆盖；
2. 较新的兼容远程缓存；
3. 当前 Herdr 二进制内置版本。

无效的本地文件会被忽略并给出警告，然后回退到远程缓存或内置版本。远程 Manifest 只能更新 Herdr 已经能够识别的 Agent；要加入全新 Agent，仍需更新 Herdr 二进制。

立即获取并重新加载远程规则：

```bash
herdr server update-agent-manifests
```

手动修改本地规则后，可重启 Herdr，或执行：

```bash
herdr server reload-agent-manifests
```

状态判断错误时可使用：

```bash
herdr agent explain <target>
```

也可以对保存的屏幕内容进行分析：

```bash
herdr agent explain \
  --file screen.txt \
  --agent codex \
  --json
```

解释结果会给出最终状态、Manifest 来源和版本、命中规则、屏幕证据、回退原因，以及是否因完整生命周期集成而跳过屏幕检测。

##### 十一、状态汇总、标签与直接连接

###### 状态向上汇总

- 某个 Agent 为 `blocked`，其 Pane、Tab 和 Workspace 都会显示阻塞。
- 有 Agent 正在 `working`，Workspace 会显示活跃。
- `done` 状态会一直保留，直到用户查看对应 Agent。

这构成 Herdr 的主要工作流：并行启动多个 Agent，通过侧边栏判断哪些项目正在执行、哪些需要人工决策、哪些已经可以审查。

###### 安装直接集成

```bash
herdr integration install claude
herdr integration status
```

不同 Agent 的 Hook、插件和会话能力不同，需要按实际使用的 Agent 安装对应集成。

###### 自定义 Agent 名称

```bash
herdr agent rename w1:p1 reviewer
herdr agent rename reviewer --clear
```

目标必须是唯一的实时 Agent 名称或当前承载它的 Pane ID，不能使用普通终端 ID 或 Agent 类型名。

###### 自定义状态与显示摘要

```bash
herdr pane report-agent w1:p1 \
  --source custom:indexer \
  --agent docs-bot \
  --state working

herdr pane report-metadata w1:p1 \
  --source custom:indexer-display \
  --token summary=indexing
```

其中：

- `state` 会影响等待、通知和状态汇总；
- `summary` 只影响显示，可在侧边栏中通过 `$summary` 使用；
- 终端标题也可作为侧边栏字段，但与语义状态相互独立。

###### 直接连接到某个 Agent

```bash
herdr agent attach reviewer
```

操作方式：

- `Ctrl+B Q`：断开连接；
- `Ctrl+B Ctrl+B`：发送字面意义上的 `Ctrl+B`；
- 鼠标滚轮或 Page Up/Page Down：滚动；
- 普通输入：回到底部。

若已有其他客户端控制输入，可强制接管：

```bash
herdr agent attach reviewer --takeover
```

非 Agent 终端则使用：

```bash
herdr terminal attach <terminal_id>
```

##### 十二、Herdr 的本地、SSH 与远程工作方式

Herdr 由**后台会话服务器**和一个或多个**终端客户端**组成：

- Pane 实际运行在后台服务器中；
- 客户端只负责连接、显示和交互；
- 执行 `Ctrl+B Q` 只会断开客户端，Pane 和 Agent 会继续运行；
- 重新运行 `herdr` 即可恢复原会话；
- 若要真正结束会话和所有 Pane，需要停止服务器。

基本原则是：**在代码、凭证和实际工作所在的机器上运行 Herdr，然后从任意设备连接。**

###### 方式一：本地工作

直接在项目目录运行：

```bash
herdr
```

Herdr 会自动启动或连接本机后台会话，不需要手动管理 Socket。

###### 方式二：先 SSH，再运行 Herdr

```bash
ssh you@server
herdr
```

这种方式类似远程 tmux：

- Shell、Herdr 服务、Agent 和 Pane 全部运行在远程机器；
- 可断开 SSH 后再次连接；
- 适合已经处于 SSH Shell 中，或使用手机、平板 SSH 客户端的情况。

手机不需要专用 Herdr App 或 Web 面板，只需普通 SSH 客户端。Herdr 的 TUI 会适应窄屏；iPhone 可使用 moshi 等 SSH 应用。

###### 方式三：本地终端作为远程薄客户端

```bash
herdr --remote workbox
```

或：

```bash
herdr --remote ssh://you@server:2222
```

此时：

- Herdr 客户端运行在本机；
- 通过 SSH 启动或连接远程 Herdr 服务；
- 远程 UI 被流式传回本地终端；
- 可桥接本机桌面能力，例如图片剪贴板粘贴。

如果先 SSH 到服务器再运行 Herdr，Herdr 完全运行在服务器端，因此无法直接读取本机桌面剪贴板。

可在 SSH 配置中保存常用主机：

```sshconfig
Host workbox
  HostName server.example.com
  User you
  Port 2222
```

然后直接连接：

```bash
herdr --remote workbox
```

###### 选择建议

| 场景 | 推荐方式 |
|---|---|
| 本地开发 | `herdr` |
| 手机连接、已在 SSH Shell 中、希望像 tmux 一样使用 | `ssh ...` 后运行 `herdr` |
| 希望远程会话具有本地终端体验，并使用本机剪贴板能力 | `herdr --remote &lt;host>` |

总体上，Herdr 适合把多个编码 Agent 当作长期运行的并行工作者：让任务持续在后台执行，通过统一状态、自动化命令和远程终端随时查看、干预和收集结果。

#### Herdr 多智能体终端与自动化全解

Herdr 是一个面向编程智能体的终端会话与自动化平台：它既能管理工作区、标签页和终端窗格，也能启动、控制和监控多个编码 Agent。核心原则是根据任务选择合适的控制对象，并利用 Agent 状态实现并行协作与远程持久运行。

##### 一、Agent automation：用终端和脚本协调多个 Agent

###### 1. 三层控制对象

Herdr 将自动化能力分为三类：

| 控制对象 | 主要职责 |
|---|---|
| **Workspace、Tab、Pane** | 管理终端布局和拓扑结构 |
| **Pane** | 控制原始终端，例如运行命令、发送输入、读取输出、等待文本 |
| **Agent** | 按名称或所在 Pane 控制已识别的编码 Agent，以及管理其生命周期状态 |

需要注意：

- **Pane 即使没有运行 Agent 也存在**。
- **Agent 是当前运行在某个 Pane 内、且被 Herdr 识别的进程**。
- `agent start` 只能在已有的 Shell Pane 中启动 Agent，不会自动创建、拆分或移动终端布局。
- 创建 Workspace 会自动创建第一个 Tab 和根 Pane；创建 Tab 会自动创建根 Pane。
- 应使用命令返回的 Pane ID，而不要自行猜测 ID。

###### 2. 创建终端布局时应读取返回的 ID

Herdr 的创建命令会输出 JSON，应从中提取实际 ID：

```bash
created=$(herdr workspace create --cwd ~/project --label api --no-focus)
pane_id=$(printf '%s\n' "$created" | jq -r '.result.root_pane.pane_id')

split=$(herdr pane split "$pane_id" --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')
```

不同命令返回的信息包括：

- `workspace create`：`.result.workspace`、`.result.tab`、`.result.root_pane`
- `tab create`：`.result.tab`、`.result.root_pane`
- `pane split`：新建 Pane 位于 `.result.pane`

如果把 Pane 移动到其他 Workspace，其带 Workspace 前缀的 Pane ID 会改变。移动后应继续使用：

```text
.result.move_result.pane.pane_id
```

旧 ID 会保存在：

```text
.result.move_result.previous_pane_id
```

正在运行的进程仍保留启动时的 Herdr 环境；旧的 `HERDR_PANE_ID` 仍可作为该终端的别名，因此 `--current` 通常仍然安全。不过，移动期间已经进行中的等待操作可能以 `agent_not_running` 结束。

###### 3. 根据任务选择控制命令

###### 普通终端任务使用 Pane 命令

适合：

- Shell 命令
- 测试
- 开发服务器
- CI 监视器
- 其他普通终端进程

常用命令：

| 任务 | 命令 |
|---|---|
| 运行命令并提交 | `pane run` |
| 发送文本但不按 Enter | `pane send-text` |
| 发送按键或快捷键 | `pane send-keys` |
| 等待终端出现文本或正则匹配 | `pane wait-output` |

###### 编码 Agent 使用 Agent 命令

适合：

- 识别当前运行的是哪个 Agent
- 判断 Agent 是工作中、阻塞、完成、空闲还是未知
- 向 Agent 提交任务并等待结果
- 操作 Agent 的交互界面

常用命令：

| 任务 | 命令 |
|---|---|
| 启动 Agent | `agent start` |
| 提交提示词并可等待 | `agent prompt` |
| 向交互界面发送按键 | `agent send-keys` |
| 等待生命周期状态 | `agent wait` |

###### 4. Agent 身份、命名和启动

Pane ID 例如：

```text
w1:p2
```

表示终端位置；Agent 名称例如 `reviewer`，则是当前运行在该 Pane 中 Agent 的便捷别名。

命名规则：

- 必须符合 `[a-z][a-z0-9_-]{0,31}`
- 活跃 Agent 之间必须唯一
- Agent 退出、释放或被替换后，别名会被清除
- 别名不会永久重命名 Pane

Agent 命令既可以接受：

- 唯一的活跃 Agent 名称
- 当前承载 Agent 的 Pane ID

启动 Agent 前，目标 Pane 必须处于交互式 Shell 提示符状态，不能有其他前台命令、编辑器或 Agent 正在运行。

支持的 Agent 类型包括：

`pi`、`claude`、`codex`、`gemini`、`cursor`、`devin`、`agy`、`cline`、`omp`、`mastracode`、`opencode`、`copilot`、`kimi`、`kiro`、`droid`、`amp`、`grok`、`hermes`、`kilo`、`qodercli`、`maki`。

示例：

```bash
herdr agent start reviewer \
  --kind codex \
  --pane "$review_pane" \
  -- -m gpt-5.4
```

`--` 后的参数会原样传递给对应的 Agent 可执行程序。

启动命令只有在 Herdr 检测到目标终端中确实出现预期 Agent，并将其标记为可交互状态后才会返回。默认启动等待时间为 **30 秒**，`--timeout` 必须满足：

```text
大于 3000 毫秒，且不超过 300000 毫秒
```

已经手动启动的 Agent 也会被自动检测；如需更易读的目标名，可以重命名：

```bash
herdr agent get w1:p2
herdr agent rename w1:p2 reviewer
```

###### 5. Agent 提示词、等待和交互

`agent prompt` 会发送文本并自动编码 Enter，同时遵守终端当前的 bracketed-paste 模式。

- 要发送 `Esc`、方向键、Enter、`Ctrl+C` 等交互按键，应使用 `agent send-keys`。
- 如果只是想进行原始终端控制，则使用 Pane 输入命令。

使用 `--wait` 时：

```bash
herdr agent prompt reviewer "Review the current diff" \
  --wait --timeout 120000
```

其行为特点：

- Agent 立即收到提示词。
- 若 Agent 原先不在工作状态，Herdr 会先要求在 **5 秒内**观察到生命周期状态变化。
- 如果状态没有推进，会返回 `agent_prompt_stalled`，而不会无限等待。
- 如果调用者设置的超时时间不超过 5 秒，则返回普通超时错误。
- Herdr 等待的是状态稳定，而不是跟踪每一轮具体对话。
- 如果 Agent 已经在工作，当前正在进行的任务完成也可能满足等待条件。

默认接受的结束状态为：

- `idle`
- `done`
- `blocked`

也可以精确指定：

```bash
herdr agent prompt reviewer "Run the tests" \
  --wait \
  --until idle \
  --until done \
  --timeout 120000
```

`--until unknown` 也可以显式等待未知状态，但只有 `agent prompt --wait` 才能使用 `--until`。

状态含义：

- **idle**：Agent 已准备好接收输入，且其标签页已被 Herdr UI 观察到。
- **done**：底层同样是空闲，但后台工作已经完成；在标签页或 Pane 被查看前，会与普通 `idle` 区分。
- **blocked**：Herdr 检测到审批、提问或权限确认界面。
- **unknown**：检测到 Agent，但无法可靠判断其生命周期，不代表任务成功。

###### 6. 读取输出与等待终端文本

`pane wait-output` 只查找终端文本，不理解 Agent 的生命周期：

```bash
herdr pane run w1:p3 "just test --watch"
herdr pane wait-output w1:p3 \
  --regex "passed|failed" \
  --timeout 120000
```

它会：

- 立即检查当前终端快照，因此屏幕上已经存在的文本也可能匹配。
- 默认读取最近 **80 行**渲染后的终端内容。
- `--lines` 可调整行数。
- `--regex` 使用 Rust 正则表达式，并按行匹配。

读取命令的默认行为：

- `pane read` 和 `agent read` 默认输出去除 ANSI 转义后的 UTF-8 文本。
- 使用 `--format ansi` 或 `--ansi` 可保留终端转义序列。
- `recent` 等来源默认读取最近 **80 行**。
- `visible` 和 detection 来源在不指定 `--lines` 时读取完整快照。
- Socket API 会将文本放在 `.result.read.text`。

###### 7. 全屏 Agent 的 alternate screen 限制

Claude Code、OpenCode 等全屏 Agent 可能使用终端的 alternate screen。此时：

- 输出不会进入 Herdr 主机的滚动历史。
- 增加 `--lines` 只能读取当前屏幕和已有滚动缓冲，无法恢复缺失的历史。
- 如果扩大 `--lines` 后仍没有更多内容，通常说明响应已经不在 Herdr 可保存的历史中。
- 窗口字体越大、Pane 越小，越容易出现这一问题。

建议：

1. 要求 Agent 返回简洁内容。
2. 增大 Pane 或缩小终端字体。
3. 使用 Agent 自身的历史记录和滚动功能。
4. 在 Agent 内滚动后，用 `--source visible` 读取当前显示页面。
5. 如果仍失败，再要求 Agent 将完整响应写入临时目录中的 Markdown 文件，并只返回文件路径，然后直接读取该文件。

文件输出方式应仅作为兜底方案，不应在第一次提示词中就要求 Agent 写文件。

###### 8. 一个完整的“启动—分配—等待—读取”流程

```bash
split=$(herdr pane split --current --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')

herdr agent start reviewer \
  --kind codex \
  --pane "$review_pane" \
  -- -m gpt-5.4

herdr agent prompt reviewer "Review the current diff" \
  --wait --timeout 120000

herdr agent read reviewer \
  --source recent-unwrapped \
  --lines 120
```

如果需要等待 Agent 请求人工输入：

```bash
herdr agent wait reviewer \
  --until blocked \
  --timeout 120000

herdr agent read reviewer \
  --source recent-unwrapped \
  --lines 80

herdr agent send-keys reviewer esc
```

##### 二、Agents：多 Agent 并行运行与状态检测

###### 1. Herdr 的多 Agent 工作方式

Herdr 为每个 Agent 保留一个真实终端 Pane，其中包含：

- Shell 环境
- 日志
- 提示词
- 正在运行的进程
- Agent 本身的交互状态

Herdr 会：

1. 跟踪哪些 Pane 中运行着 Agent。
2. 将 Agent 状态汇总到 Tab 和 Workspace。
3. 在侧边栏中显示哪些项目正在运行、已完成或需要人工处理。
4. 让用户直接跳转到需要关注的 Pane，而不必逐个轮询终端。

典型工作流是：同时启动多个 Agent，让它们并行处理任务，再根据侧边栏状态决定先处理审批、查看完成结果，还是继续等待。

###### 2. Agent 状态的权威来源

不同 Agent 的状态来源不同：

| Agent | 主要状态来源 |
|---|---|
| Pi、Devin、Kimi Code、Hermes Agent | 已安装时使用生命周期钩子，否则使用屏幕 Manifest 和会话信息 |
| OpenCode、Kilo Code | 已安装生命周期插件时使用插件，否则使用屏幕 Manifest 和会话信息 |
| MastraCode | 已安装生命周期钩子时使用钩子，否则使用状态和会话信息 |
| GitHub Copilot CLI、Qoder CLI、Droid、Claude Code、Codex、Cursor Agent CLI | 主要使用屏幕 Manifest；部分还提供会话身份恢复 |
| Amp、Grok、Antigravity、Kiro、Maki | 使用屏幕 Manifest |
| Gemini CLI、Cline | 已支持但测试较少 |
| 其他不支持的 Agent | 可作为普通终端进程运行，但通常没有丰富的 Agent 状态 |

Herdr 首先检测每个 Pane 的前台进程，然后为该 Pane 选择一种状态权威来源。

###### 3. 生命周期钩子与屏幕 Manifest

###### 有完整生命周期钩子的 Agent

如果 Agent 的生命周期集成已安装，并且正在对当前 Pane 报告状态：

- 集成会成为唯一权威来源。
- Herdr 使用其报告判断 `idle`、`working`、`blocked` 和会话身份。
- 不会再同时运行屏幕 Manifest，避免多个来源互相冲突。

###### 没有完整生命周期钩子的 Agent

Herdr 会：

1. 识别 Pane 中的前台进程。
2. 读取 Pane 底部实时屏幕快照。
3. 用 TOML Manifest 判断 Agent 处于空闲、工作中还是阻塞状态。

Manifest 还可以根据终端标题和进度相关的 OSC 序列进行辅助检测；如果这些证据不存在，屏幕规则仍可独立完成识别。

屏幕检测读取的是 Pane 缓冲区底部的实时内容，而不是用户滚动后看到的历史视图。即使用户向上翻页，Herdr 仍然依据 Agent 当前底部界面判断状态。

###### 4. 特殊 Agent 的状态识别限制

Claude Code、Codex、GitHub Copilot CLI、Droid、Qoder CLI 和 Cursor Agent CLI 的集成主要用于恢复原生会话身份，并不作为完整生命周期权威来源，因为它们的钩子可能遗漏：

- 权限审批结果
- Escape 中断
- 其他状态转换

因此，这些 Agent 仍主要依赖屏幕 Manifest 进行状态检测。

对于屏幕 Manifest 类型的 Agent，阻塞状态检测非常严格：只有当实时底部屏幕快照匹配已知的审批、提问或权限界面时，Herdr 才会标记为 `blocked`。

如果已知 Agent 没有匹配到任何规则，Herdr 会：

- 回退为 `idle`
- 在解释信息中标记为 `default_known_agent_idle_fallback`

这意味着某些新出现的 Agent 提示界面，可能暂时被误判为空闲。此类误判不会导致 Herdr 自动发送输入或执行破坏性操作，但会影响状态显示和等待命令。

###### 5. VM、容器和沙箱包装器

在 Linux 或 macOS 上，某些宿主机可见的包装器可能隐藏真正的 Agent 进程。此时可以通过 `HERDR_AGENT` 告诉 Herdr 应使用哪个 Agent 的屏幕 Manifest：

```bash
HERDR_AGENT=claude fence -- claude
```

macOS 示例：

```bash
HERDR_AGENT=claude nono run \
  --profile claude-code -- claude
```

注意：

- 该提示只对当前前台进程有效。
- 如果只在 VM 或容器内部设置，宿主机上的 Herdr 看不到。
- 不建议全局导出 `HERDR_AGENT`，除非所有继承该变量的前台进程都确实是同一种 Agent。

###### 6. Detection Manifest 的更新与覆盖

Herdr 内置 Agent 检测 Manifest，同时会检查 `herdr.dev` 上的远程更新：

- 有效的远程规则会自动应用。
- 通常不需要重启 Herdr。
- 远程 Manifest 会保存到 Herdr 状态目录。
- 可以通过配置关闭后台检查：

```toml
[update]
manifest_check = false
```

本地覆盖文件位于：

```text
~/.config/herdr/agent-detection/<agent>.toml
```

优先级如下：

1. 本地覆盖文件
2. 缓存的远程 Manifest
3. Herdr 二进制内置 Manifest

本地覆盖始终优先。无效覆盖文件会被忽略，并回退到远程缓存或内置版本。

更新方式：

```bash
herdr server update-agent-manifests
```

该命令会立即获取远程更新并重新加载服务端缓存。

编辑本地覆盖文件后，可执行：

```bash
herdr server reload-agent-manifests
```

或者重启 Herdr。

远程 Manifest 只能修改 Herdr 已经认识的 Agent；如果要增加全新的 Agent，仍需要更新 Herdr 二进制，以提供进程识别、标签和集成行为。

###### 7. 排查状态识别错误

如果某个 Pane 显示了错误状态，可以使用：

```bash
herdr agent explain <target>
```

也可以分析一个静态屏幕文件：

```bash
herdr agent explain \
  --file screen.txt \
  --agent codex \
  --json
```

解释信息可能包括：

- 检测出的 Agent
- 最终状态
- 是否因完整生命周期集成而跳过屏幕检测
- Manifest 来源和版本
- 缓存的远程版本
- 是否被本地覆盖
- 远程更新状态
- 匹配到的规则
- 可见证据标记
- Matcher 和区域匹配证据
- 跳过更新的原因
- 未匹配规则时的空闲回退原因

###### 8. tmux 与 Herdr 的关系

Herdr 可以作为外层终端环境运行在 tmux 中，但它不会检查 Herdr Pane 内部启动的 tmux 会话。

如果 Shell 框架在进入 Herdr 后自动启动 tmux：

- Herdr 可能只看到 tmux 进程。
- 因而无法识别 tmux 后面的真实 Agent。

不过，Agent 状态仍会向上汇总到 Tab 和 Workspace。

###### 9. 侧边栏状态汇总

Herdr 会把 Agent 状态逐级汇总：

- `blocked`：Pane、Tab 和 Workspace 都显示为阻塞。
- `working`：Workspace 显示为活跃。
- `done`：任务完成后仍会保留在界面中，直到用户查看。

可通过集成安装增强状态报告：

```bash
herdr integration install claude
herdr integration status
```

###### 10. 自定义 Agent 名称与状态显示

重命名 Agent：

```bash
herdr agent rename w1:p1 reviewer
herdr agent rename reviewer --clear
```

目标必须是：

- 唯一的活跃 Agent 名称
- 当前承载 Agent 的 Pane ID

终端 ID 和单独的 Agent 类型名不能作为目标。

还可以上报自定义语义状态和显示信息：

```bash
herdr pane report-agent w1:p1 \
  --source custom:indexer \
  --agent docs-bot \
  --state working

herdr pane report-metadata w1:p1 \
  --source custom:indexer-display \
  --token summary=indexing
```

其中：

- `state` 会影响等待、通知和状态汇总。
- `summary` 等 Token 只影响显示，可在侧边栏中作为 `$summary` 使用。
- 侧边栏还可以显示 `terminal_title` 或 `terminal_title_stripped`。
- 终端标题由服务端维护，冷启动后不持久化，也独立于元数据标题和 Agent 语义状态。

###### 11. 直接连接 Agent 终端

可以绕过完整 Herdr UI，直接连接某个 Agent：

```bash
herdr agent attach reviewer
```

快捷键：

- `Ctrl+B Q`：断开连接
- `Ctrl+B Ctrl+B`：发送字面量 `Ctrl+B`
- 鼠标滚轮或普通 Page Up/Page Down：滚动
- 普通输入：回到底部

如果已有其他直接连接客户端占用输入，可强制接管：

```bash
herdr agent attach reviewer --takeover
```

对于非 Agent 的普通终端，则使用：

```bash
herdr terminal attach <terminal_id>
```

##### 三、How to work with Herdr：持久化会话与远程工作

###### 1. Herdr 的运行模式

Herdr 由以下部分组成：

- 后台会话服务端
- 一个或多个终端客户端
- 多个持续运行的 Pane

建议从项目目录启动 Herdr。它会自动创建或连接本地后台会话，用户无需手动管理 Socket。

终端中的 Shell、服务器、测试和 Agent 都按普通方式运行。客户端可以随时退出，Pane 中的进程仍会继续运行。

断开客户端：

```text
Ctrl+B Q
```

重新连接时，再次运行 Herdr 即可恢复会话。若要彻底结束会话并停止其中的 Pane，应停止 Herdr 服务端。

###### 2. 通过普通 SSH 远程工作

最直接的方式是：

1. SSH 登录存放代码和凭据的远程机器。
2. 在远程机器上运行 Herdr。
3. 在远程 Herdr 中启动 Agent 和其他终端进程。
4. 使用 `Ctrl+B Q` 分离。
5. 断开 SSH，之后重新 SSH 并运行 Herdr。

这种方式适合：

- 已经习惯在 SSH Shell 中工作。
- 使用手机或平板 SSH 客户端。
- 希望 Herdr 像远程 tmux 一样运行。

手机不需要专用 Herdr App 或 Web 控制台，只需安装 SSH 客户端即可。Herdr 的 TUI 会适配窄屏，用户仍可查看 Agent、切换 Workspace 和检查 Pane。

###### 3. 从本地终端连接远程 Herdr

也可以让本地 Herdr 作为远程会话的轻量客户端：

```bash
herdr --remote workbox
herdr --remote ssh://you@server:2222
```

该模式下：

- 本地客户端通过 SSH 连接远程机器。
- 自动启动或连接远程 Herdr 服务端。
- 将远程 UI 流式传回本地终端。
- 客户端运行在本地，因此可以桥接本地桌面能力，例如粘贴剪贴板中的图片。

如果先手动 SSH，再在服务器上运行 Herdr，则 Herdr 完全运行在远程机器上，无法读取本地桌面剪贴板。

为了重复使用远程目标，可以在 SSH 配置中设置：

```sshconfig
Host workbox
  HostName server.example.com
  User you
  Port 2222
```

之后直接连接：

```bash
herdr --remote workbox
```

###### 4. 远程连接方式选择

| 使用场景 | 推荐方式 |
|---|---|
| 本地项目 | 直接运行 `herdr` |
| 已经在远程 SSH Shell 中工作 | `ssh you@server` 后运行 `herdr` |
| 使用手机 SSH 客户端 | SSH 到服务器后运行 `herdr` |
| 希望本地终端像操作本地会话一样访问远程项目 | `herdr --remote &lt;host>` |
| 需要本地剪贴板图片桥接到远程会话 | 优先使用 `herdr --remote &lt;host>` |

远程启动、命名远程会话、自定义二进制、直接连接终端以及 `--no-session` 等高级选项，可进一步参考 Herdr 的持久化与远程访问文档。

## 口播总结（2）

### 2026-08-03 00:38:25

#### Herdr 多智能体终端与自动化全解

Herdr 是一个用来同时运行、观察和自动控制多个编程智能体的终端系统。听完这份总结，你会了解它的核心对象、自动化方式、智能体状态判断、终端输出读取限制，以及本地、远程和手机端的使用方法。

##### 一、先理解 Herdr 的三个核心对象

首先，使用 Herdr 做自动化，关键是选对控制层级。它把操作分成三类：布局、终端窗格和智能体。

所谓“布局”，就是工作区、标签页和窗格的组织方式。工作区可以理解成一个项目空间；标签页是工作区里的分组；窗格则是真正运行终端程序的位置。

“窗格”，英文叫 pane，负责普通终端操作。比如运行命令、启动测试、发送按键、读取输出，或者等待某段文字出现。

“智能体”，英文叫 agent，指窗格里被 Herdr 识别出来的编程智能体进程。Herdr 不只知道它在运行，还会尽量判断它是正在工作、等待输入、已经完成，还是被权限确认卡住。

这里最重要的区别是：窗格一直存在，但窗格里不一定有智能体。启动智能体的命令只会在现有窗格中启动进程，不会自动创建、拆分或移动窗格。

创建工作区时，Herdr 会同时创建第一个标签页和根窗格。创建新标签页时，也会自动带一个根窗格。因此，第一个进程可以直接使用返回的根窗格编号；只有确实需要更多终端时，才继续拆分窗格。

这些创建命令会返回 JSON，也就是结构化数据。脚本应该从返回结果中提取工作区、标签页和窗格编号，而不是自己猜编号。这样即使布局发生变化，自动化脚本也不会操作错位置。

还有一个容易忽略的细节：把窗格移动到另一个工作区后，它的完整编号会改变。后续操作应使用移动结果中返回的新编号。旧编号仍会作为这个终端的别名存在，所以基于“当前窗格”的操作通常仍然安全；但已经开始等待某个智能体状态的命令，会因为移动而以“智能体已不在运行位置”结束。

##### 二、普通终端操作和智能体操作要分开

接下来，需要判断当前任务到底应该使用窗格命令，还是智能体命令。

如果运行的是 shell、测试、服务器、持续集成监视器，或者其他普通终端程序，就使用窗格命令。例如，运行命令用 pane run；发送文字但不按回车，用 pane send-text；发送回车、方向键或组合键，用 pane send-keys；等待输出中出现特定文字，用 pane wait-output。

如果 Herdr 需要识别具体智能体，并根据它的生命周期状态采取行动，就使用 agent 命令。例如，启动智能体用 agent start；提交提示词用 agent prompt；发送交互按键用 agent send-keys；等待状态变化用 agent wait。

两套命令的安全边界不同。窗格输入会直接发给终端，不管当前是谁占用它。智能体输入则会先确认目标智能体仍然控制着这个窗格；如果智能体已经退出或被替换，操作会被拒绝。因此，明确要控制智能体时，优先使用 agent 命令更安全。

##### 三、智能体名称、启动条件和超时规则

智能体既可以用窗格编号定位，也可以设置一个容易记住的名称，比如 reviewer，也就是“审查者”。

名称只是当前智能体的临时别名，不会永久重命名窗格。智能体退出、被释放或被替换后，这个名称就会清除。名称必须以小写字母开头，后面只能使用小写字母、数字、下划线或短横线，最长三十二个字符，而且所有正在运行的智能体名称不能重复。

启动智能体之前，目标窗格必须处在可用的交互式 shell 提示符上。也就是说，前台不能还有命令、编辑器或其他智能体正在运行。

Herdr 可以通过 kind 参数选择智能体类型，并调用对应的标准可执行程序。它支持二十多种常见工具，包括 Claude、Codex、Gemini、Cursor、Devin、OpenCode、GitHub Copilot、Kimi、Droid、Grok 和 Qoder 等。额外参数会原样传给对应的智能体程序。

agent start 不会在进程刚启动时立刻返回。它会等到 Herdr 在同一个终端里识别出预期智能体，并确认它已经可以接受交互输入。默认等待三十秒。自定义启动超时必须大于三秒，同时不能超过五分钟。

如果智能体是手动启动的，Herdr 通常也能自动识别。此时可以先用窗格编号操作，再给它设置一个稳定、容易理解的名称。

##### 四、正确理解提示、等待和四种状态

更重要的是，Herdr 的等待机制依赖智能体状态，而不是简单地等待一段文本。

agent prompt 会提交提示词并自动按下回车，而且会尊重终端当前的“括号粘贴模式”。这种模式可以避免多行内容在终端里被误解析。即使智能体已经在工作，也可以继续向它提交提示。

如果加上 wait，Herdr 会在提交后等待智能体进入指定的稳定状态。默认接受三种结果：空闲、完成或阻塞。

“空闲”，也就是 idle，表示智能体已经准备好接收输入，而且它所在的标签页已经在 Herdr 界面中被看过。

“完成”，也就是 done，本质上也是已经空闲，但表示后台任务刚结束，还没有被用户查看。只要聚焦到对应标签页或窗格，它通常就会从完成变成普通空闲。仅通过命令行读取输出，不算已经查看。

“阻塞”，也就是 blocked，表示 Herdr 识别到了审批、权限确认或提问界面，需要人做决定。

“未知”，也就是 unknown，表示智能体确实存在，但 Herdr 无法可靠判断其状态。未知绝不等于成功完成。如果业务逻辑需要接受未知状态，必须明确写出来。

当 agent prompt 从非工作状态启动一次新任务时，Herdr 会先要求在五秒内观察到生命周期变化。如果状态一直没有推进，它会返回“提示已停滞”，而不是无限等待。不过，如果调用者设置的总超时不超过五秒，返回的会是普通超时错误。

一旦观察到活动，Herdr 就继续等待目标状态。但它不会严格追踪“这一轮提示”本身。如果智能体提交提示前就已经在工作，那么当前活动轮次的结束，也可能满足等待条件。

单独使用 agent wait 时，如果当前状态已经符合要求，它会立即返回。可以重复指定多个可接受状态，比如同时接受空闲和完成。需要特别注意的是，各类等待命令默认没有总超时，理论上可能一直等待。因此，自动化脚本最好主动设置合理的超时时间。

##### 五、等待文本和等待状态不是一回事

接下来要区分两种等待：pane wait-output 等待终端里出现文字；agent wait 等待智能体生命周期状态。

pane wait-output 不理解智能体是否完成。它只会检查终端快照，并搜索文字或正则表达式。因此，终端里早已存在的旧文字也可能立刻匹配。

默认情况下，它检查最近八十行渲染内容。可以调整行数，也可以使用正则表达式。正则按单行匹配，使用 Rust 风格的表达式语法。

读取终端内容时，pane read 和 agent read 默认输出 UTF-8 纯文本，并去掉 ANSI 控制序列，也就是终端颜色和样式代码。如果确实需要保留颜色或格式，可以选择 ANSI 输出。但 Herdr 用来识别智能体状态的检测内容始终是纯文本。

命令成功后，启动、提示和状态等待会返回当前智能体信息；文本等待则会返回窗格编号、匹配到的行和相关终端快照。发生超时或服务器错误时，命令会把 JSON 错误写到标准错误，并以状态码一退出；命令语法错误则以状态码二退出。

实际使用中，可以先拆出一个新窗格，启动一个代码审查智能体，让它检查当前代码改动，等待任务稳定后再读取最近输出。也可以等待它进入 blocked 状态，读取它提出的问题，然后发送退出键或确认键。普通测试监视器则不应伪装成智能体，只需运行进程并等待“通过”或“失败”等文字。

##### 六、全屏智能体可能导致历史输出丢失

有一个很重要的终端限制：Claude Code、OpenCode 等全屏智能体，可能使用终端的“备用屏幕”。

备用屏幕可以理解为终端程序临时使用的一块独立画布。它显示过的内容不会进入 Herdr 主终端的滚动历史。因此，即使把读取行数调得很大，也无法找回已经离开备用屏幕的内容。

如果增加读取行数后仍然没有更多响应，通常说明这些内容已经不在可用屏幕和历史缓冲区里。窗格越小、字体越大，这种情况越容易发生。

优先的处理方法是让智能体回答得更简洁，扩大窗格，或者减小字体。也可以使用智能体自身的滚动和会话记录功能。滚动到目标内容后，再读取当前可见页面。

如果仍然读取失败，可以再要求智能体把完整回答写入临时目录中的 Markdown 文件，并且只回复文件路径，然后直接读取这个文件。但这只是兜底方案。原文特别提醒，不要在最初提示时就要求文件输出，只有常规读取失败后再这样做。

##### 七、Herdr 如何识别智能体状态

说完控制方式，再来看 Herdr 的状态识别机制。

Herdr 的设计目标，是让多个编程智能体同时待在真实终端窗格里。它们各自保留 shell、日志、提示和运行进程。Herdr 会把窗格状态汇总到标签页和工作区，让用户直接找到需要处理的位置，而不是逐个终端查看。

识别状态主要有两种方式。

第一种是生命周期钩子或插件。可以把它理解为智能体主动向 Herdr 报告“我开始工作了”“我正在等待审批”“我已经空闲”等状态。如果某个智能体安装了完整的生命周期集成，而且正在正常报告，那么这套集成就是唯一权威来源。Herdr 不会同时用屏幕规则再次判断，以免出现两个互相冲突的结论。

第二种是屏幕清单检测。对于没有完整生命周期钩子的智能体，Herdr 会识别窗格中的前台进程，再读取终端底部的实时画面，用预先定义的 TOML 规则判断它是空闲、工作还是阻塞。TOML 是一种常见的配置文件格式。部分规则还会参考终端标题和进度控制序列。

检测始终看终端底部的实时内容，而不是用户滚动到的历史位置。所以即使用户正在回看旧输出，Herdr 仍会追踪当前智能体界面。

Claude Code、Codex、GitHub Copilot 命令行工具、Droid、Qoder 和 Cursor Agent 的原生集成，可以提供恢复会话所需的身份信息，但不会被当作完整的生命周期权威。原因是它们的钩子可能遗漏权限审批结果、退出键中断等状态变化。因此，Herdr 仍然依赖屏幕规则判断这些智能体的状态。

不受支持的智能体也可以像普通终端进程一样运行，只是可能没有丰富的状态。Gemini CLI 和 Cline 已经可以被识别，但测试覆盖相对少一些。需要更完整状态时，可以添加集成，或者通过 Herdr 的套接字接口主动上报。

##### 八、虚拟机、沙箱和严格的阻塞判断

如果智能体运行在虚拟机、容器或沙箱包装器后面，Herdr 在宿主机上可能只能看到包装程序，看不到真正的智能体进程。

在 Linux 和 macOS 上，可以在启动包装器时设置 HERDR_AGENT 环境变量，明确告诉 Herdr 应使用哪一种智能体的屏幕检测规则。这个提示必须设置在宿主机可见的前台包装命令上。只在虚拟机或容器内部设置，Herdr 看不到。也不建议全局导出这个变量，否则所有继承它的前台进程都可能被误认为同一种智能体。

Herdr 对 blocked 状态的判断故意很严格。只有实时终端底部明确匹配已知的审批、提问或权限界面时，它才会标记为阻塞。

如果已知智能体没有匹配任何规则，Herdr 会回退到空闲状态。因此，当某个智能体推出了全新的交互界面时，它一开始可能被误判为空闲，而不是阻塞。这只会影响界面状态和等待结果，不应该被用于自动发送输入或执行破坏性操作。

##### 九、检测规则可以更新、覆盖和解释

Herdr 自带智能体检测清单，也会从官方服务获取远程更新。有效更新可以在不重启 Herdr 的情况下应用。用户也可以关闭后台远程检查。

如果需要自行修正规则，可以在平台配置目录中放置本地 TOML 覆盖文件。本地规则优先级最高。没有本地覆盖时，Herdr 会在缓存的远程规则和程序内置规则之间，选择更新且兼容的版本。

无效的本地文件会被忽略，并给出警告。此时系统会退回远程缓存或内置规则。远程更新只能修改 Herdr 已经认识的智能体；要支持一种全新的智能体，仍然需要更新 Herdr 程序本身，因为还涉及进程识别、名称和集成行为。

远程规则更新后，运行中的服务器可以自动重新加载。手动修改本地规则后，则需要重启 Herdr，或者执行重新加载命令。

如果某个窗格的状态明显不对，可以使用 agent explain。它会解释最终状态、规则来源和版本、命中的规则、可见证据、是否被完整生命周期集成跳过，以及为什么回退为空闲。这是排查误判时最直接的工具。

Herdr 本身可以运行在 tmux 里面，但不会继续检查某个 Herdr 窗格内部再启动的 tmux 会话。如果 shell 自动进入内层 tmux，Herdr 看到的前台进程就是 tmux，而不是藏在后面的智能体。

##### 十、状态会向上汇总，也可以自定义显示

Herdr 会把状态从窗格汇总到标签页和工作区。某个智能体阻塞时，它所在的窗格、标签页和工作区都会显示为需要处理。智能体工作时，工作区会显示为活跃。任务完成后，done 状态会一直保留，直到用户查看。

这正是它的核心工作流：同时启动多个智能体，让它们并行工作，然后通过侧边栏判断哪个项目正在运行、哪个需要批准，以及哪个已经可以审查。

为了提高识别质量，可以为常用智能体安装对应的直接集成。不同智能体的集成能力不同，有的提供生命周期状态，有的主要提供会话身份。

用户还可以设置自定义智能体名称和显示摘要。但需要区分语义状态与显示信息：working、blocked 等状态会影响等待、通知和工作区汇总；summary 等元数据只负责显示，不应改变自动化判断。

如果只想直接进入某个智能体，而不是打开完整 Herdr 界面，可以使用 agent attach。退出直接连接的快捷键是 Ctrl 加 B，然后按 Q。如果已有客户端控制输入，可以使用 takeover 接管。非智能体终端也可以通过 terminal attach 直接连接。

##### 十一、本地、远程和手机应该怎样使用

最后来看实际工作方式。Herdr 由后台会话服务器和一个或多个终端客户端组成。窗格和进程运行在服务器中；客户端只负责连接、显示和交互。

最简单的本地用法，是在项目目录中启动 Herdr。它会自动启动或连接本地后台会话，不需要用户管理套接字。退出客户端后，窗格、服务器、测试和智能体仍然继续运行。之后再次运行 Herdr，就能回到原来的会话。只有停止服务器，才会真正结束会话和其中的窗格。

远程使用有两条主要路径。

第一条，是先通过普通 SSH 登录到有代码和凭据的机器，再在那里运行 Herdr。此时 shell、Herdr 服务器、智能体和窗格都在远程机器上运行。断开前先退出 Herdr 客户端，之后重新 SSH 登录并运行 Herdr，就能恢复。这种方式最像在远程服务器上使用 tmux，也最适合手机和平板的 SSH 客户端。

Herdr 不需要专门的手机应用或网页控制台。手机安装任意 SSH 客户端，连接远程机器并启动 Herdr，就能打开同一个持久会话。它的终端界面会适应窄屏，仍然可以查看智能体、切换工作区和检查窗格。

第二条，是在本地终端直接使用 remote 参数连接远程主机。本地 Herdr 作为轻量客户端，通过 SSH 启动或连接远程 Herdr 服务器，再把界面传回本地。这种方式更像在本机操作远程会话。

两者最大的区别是本地桌面能力。如果先 SSH 到服务器，再在服务器里运行 Herdr，那么 Herdr 无法读取本机桌面剪贴板。如果使用本地轻量客户端连接远程服务器，本地图片剪贴板等功能就有机会桥接到远端。

所以，选择方法可以很简单：本地项目直接运行 Herdr；手机使用或已经处在 SSH 终端里，就先 SSH 再运行 Herdr；希望远程会话像本地应用一样使用，并保留本地剪贴板能力，就使用 Herdr 的 remote 连接方式。

##### 最值得记住的五个结论

最后，回顾五个重点。

第一，布局、窗格和智能体是三个不同层级。布局负责组织位置，窗格负责普通终端，智能体命令负责可识别的编程智能体。

第二，自动化时不要猜窗格编号，要从创建和移动命令返回的 JSON 中读取新编号。

第三，等待文字不等于等待任务完成。普通进程使用输出匹配；智能体应根据 idle、done、blocked 和 unknown 等生命周期状态判断。

第四，Herdr 的状态来源可能是生命周期集成，也可能是屏幕规则。unknown 不代表成功，blocked 的识别也故意偏严格，因此高风险操作不能只依赖界面状态。

第五，Herdr 的会话运行在后台服务器中。退出客户端不会停止任务。无论本地、远程 SSH 还是手机，都可以重新连接到同一批持续运行的终端和智能体。

Herdr 的核心价值，不只是同时打开多个编程智能体，而是把终端布局、普通进程和智能体状态统一起来。这样，脚本或另一个智能体就能创建任务、分派工作、等待结果，并在真正需要人工处理时提醒你。

理解 Herdr，最重要的是分清三层对象。

第一层是布局，也就是工作区、标签页和窗格。它们负责组织终端位置。创建工作区时，会自动得到第一个标签页和一个根窗格。创建标签页时，也会自动得到根窗格。只有需要额外终端时，才继续拆分窗格。

第二层是窗格。窗格本质上是一个真实终端。无论里面有没有智能体，窗格都存在。你可以在里面运行测试、服务器、持续集成监视器，或者任何普通命令。

第三层才是智能体。智能体是 Herdr 在某个窗格中识别到的编程智能体进程。启动智能体之前，必须先有一个可用的 shell 窗格，而且这个窗格要停在交互式命令提示符上，不能还有前台命令、编辑器或其他智能体正在运行。Herdr 的 agent start 命令只负责在现有窗格里启动智能体，不会自动创建、拆分或移动布局。

因此，一套可靠的自动化流程通常是这样的：先创建工作区或拆分窗格，从命令返回的 JSON 结果里读取真实的窗格编号，再在这个窗格中启动智能体。不要自己猜编号。特别是移动窗格之后，它带有工作区信息的编号会发生变化，后续操作应使用移动结果中返回的新编号。已经进行中的等待操作，则可能因为窗格移动而以“智能体未运行”结束。

窗格编号表示终端位置，例如某个工作区里的第二个窗格。智能体名称则是一个更容易记忆的临时别名，比如 reviewer，也就是审查者。这个名字只属于当前存活的智能体。智能体退出、被释放或被替换后，别名就会清除，它不会永久改名那个窗格。

接下来要分清两套控制方式。

如果你控制的是普通终端行为，就使用 pane，也就是窗格命令。比如运行 shell 命令、发送原始文字、发送按键，或者等待终端出现某段文字。这适合测试、服务器和日志监视器。

如果你希望 Herdr 理解里面运行的是哪个智能体，并判断它正在工作、等待输入还是已经完成，就使用 agent 命令。比如启动智能体、提交提示词、发送交互按键，以及等待智能体进入某种生命周期状态。

这里有一个重要边界。窗格输入会直接作用于终端，不管终端当前由谁占用。智能体输入则会先确认目标智能体仍然控制着这个窗格。如果智能体已经退出，操作会被拒绝。这种检查更适合自动化，也更安全。

向智能体提交任务时，可以使用 agent prompt。它会发送文字并提交回车，还能适应终端当前的粘贴模式。如果智能体已经在工作，也可以继续发提示词。需要操作交互界面时，例如发送退出键、方向键、回车或控制键组合，则应使用 agent send-keys。

如果 prompt 搭配 wait，Herdr 会等待智能体进入指定的稳定状态。但这不是对单次对话轮次的精确追踪。假如智能体原本就在工作，那么当前任务结束，也可能满足这次等待。相反，如果智能体原本没有工作，Herdr 会先观察它是否在五秒内出现状态变化。如果完全没有变化，会报告提示词处理停滞，而不是无限误等。

Herdr 主要区分四种值得注意的状态。

空闲，也就是 idle，表示智能体已经可以接收输入，而且对应标签页已经在 Herdr 界面中被看过。

完成，也就是 done，底层同样是可接收输入，但表示后台工作刚刚结束，而且你还没有查看对应标签页。只要聚焦那个标签页或窗格，完成状态就会转为空闲。仅仅通过命令行读取输出，不算已经查看。

阻塞，也就是 blocked，表示 Herdr 识别出了审批、提问或权限确认界面，需要外部输入。

未知，也就是 unknown，表示智能体确实存在，但 Herdr 无法可靠判断它的生命周期。未知绝不等于成功完成。

所以，自动化脚本不应把所有非工作状态都当成成功。重要任务最好明确等待 idle、done 或 blocked 中的特定状态。Herdr 的等待命令默认没有超时时间，可能一直等待，因此脚本中通常应该主动设置超时。

等待终端文字和等待智能体状态，也是两件不同的事。pane wait-output 只搜索终端快照，不理解智能体生命周期。它会立刻检查已经存在的文字，所以旧输出也可能匹配成功。它适合等待测试输出中的 passed 或 failed，却不适合据此推断智能体真正完成了任务。

Herdr 判断智能体状态时，会先识别每个窗格的前台进程，然后确定谁有权报告状态。有些智能体安装了完整的生命周期集成后，集成报告就是唯一权威来源，不再同时使用屏幕规则，避免两个来源互相冲突。

另一些智能体虽然有原生集成，但相关钩子不能覆盖审批结果、退出键中断等全部变化。对于这些智能体，Herdr 仍然观察终端底部的实时画面，并用检测规则判断空闲、工作和阻塞。这里观察的是窗格缓冲区最底部，而不是用户向上滚动后正在看的历史页面。

阻塞检测被设计得比较严格。只有屏幕确实匹配已知的审批、提问或权限界面，Herdr 才会标记 blocked。如果某个智能体出现了全新的提示界面，Herdr 可能暂时把它当成 idle，而不是 blocked。这个误差会影响显示和等待结果，但 Herdr 不会因此擅自发送输入或执行破坏性操作。

状态判断不正确时，可以使用 agent explain 查看解释信息。它会说明当前使用了哪个检测来源、匹配了哪条规则，以及为什么回退为空闲。Herdr 还能在线更新已知智能体的检测规则，本地规则则拥有最高优先级。不过，远程规则只能修补已经支持的智能体。要增加一种全新的智能体，仍然需要更新 Herdr 本身。

在虚拟机、沙箱或包装器中运行时，还有一个常见问题。宿主机可能只看见包装器，而看不见真正的智能体进程。这时需要在宿主机可见的启动命令上设置 HERDR_AGENT，告诉 Herdr 应该套用哪一种智能体的检测规则。只在容器内部设置，宿主机上的 Herdr 看不到。类似地，如果在 Herdr 的窗格里又自动进入一层 tmux，Herdr 看到的前台进程会是 tmux，而不是里面的智能体，因此无法正常识别。

读取输出时，最值得警惕的是全屏终端界面。Claude Code、OpenCode 等工具可能使用终端的备用屏幕。备用屏幕内容不会进入 Herdr 的宿主滚动历史。一旦旧内容离开屏幕，即使把读取行数调得再大，也无法凭空找回来。

遇到这种情况，可以先要求智能体简短回答，增大窗格，或者缩小字体。也可以在智能体界面中滚动，再让 Herdr 读取当前可见页面。如果仍然失败，最后的补救办法是让智能体把完整回答写入临时目录中的 Markdown 文件，只回复文件路径，然后直接读取文件。这个办法适合作为读取失败后的后备方案，不应一开始就强迫所有回答写文件。

从实际使用看，Herdr 最适合的工作方式是并行启动多个智能体，让每个智能体留在自己的真实终端中。它们的 shell、日志、提示和进程都会保留。侧边栏会把窗格状态汇总到标签页和工作区。某个智能体被阻塞，对应工作区也会显示需要处理；某个智能体仍在工作，工作区会显示活跃；后台任务完成后，done 状态会一直保留到你查看为止。

Herdr 本身采用后台会话服务器加终端客户端的结构。关闭或分离客户端，不会停止窗格里的进程。按控制键加 b，再按 q，可以离开界面；稍后重新运行 Herdr，就能回到同一个会话。只有主动停止服务器，才会结束会话和其中的窗格。

远程使用有两种主要方式。你可以先通过 SSH 登录代码所在的机器，再在远程 shell 中运行 Herdr。这种方式最像 tmux，也适合手机上的任意 SSH 客户端，不需要专门的移动应用。

另一种方式，是在本地终端中使用 Herdr 的 remote 参数，直接连接远程机器。本地 Herdr 只充当轻量客户端，智能体和服务器仍在远程运行。这样既能获得接近本地的操作体验，也能桥接某些本地桌面能力，例如把本地剪贴板中的图片粘贴到远程会话。如果先进入 SSH 再启动 Herdr，Herdr 完全运行在远端，就无法读取本地桌面剪贴板。

最值得记住的是：布局、窗格和智能体是三个不同层次，必须选择与任务匹配的控制接口。自动化时，要明确等待的状态并设置超时，不能把未知状态或某段输出文字误当成任务成功。最后，Herdr 的真正优势在于让多个真实终端持续运行，再把谁在工作、谁需要决定、谁已经完成，集中呈现出来。

## 深度解读（2）

### 2026-09-18 00:22:35

#### 多智能体编程的瓶颈，不是启动更多 Agent，而是可靠地判断它们在做什么

Herdr 表面上是一个面向编码 Agent 的终端管理器：它让 Claude Code、Codex、Cursor、Kimi 等工具运行在持久化窗格中，并支持脚本或另一个 Agent 创建任务、发送提示、等待结果。更值得关注的是，它暴露了多智能体自动化真正困难的部分——**如何在兼容现有工具的前提下，建立可信的控制与状态协议。**

##### 把终端、Agent 和界面布局分开，是必要的抽象

Herdr 将能力拆成三层：布局负责工作区、标签页和窗格；Pane 负责执行命令、发送按键和读取输出；Agent 层才负责识别具体编码工具及其生命周期。一个窗格可以没有 Agent，启动 Agent 也不会隐式创建或移动窗格。

这种划分看似琐碎，却避免了自动化系统常见的混乱：把“进程在哪里”“如何操作终端”和“任务是否完成”视为同一件事。测试服务器、CI watcher 应由 Pane 控制；只有需要理解工作、阻塞或完成状态时，才使用 Agent API。对未来的 Agent 平台而言，这种**资源层与语义层分离**比支持多少模型更重要，否则编排脚本很快会被界面和工具差异拖垮。

选择真实终端作为运行底座也很务实。它几乎不要求现有 Agent 改造，保留了 Shell、日志、凭证和 SSH 工作流，还能从手机直接接管。但兼容性的代价是：Herdr 控制的是原本为人设计的交互界面，而不是稳定的机器协议。

##### “状态检测”才是编排可靠性的核心风险

文档用了大量篇幅解释 idle、working、blocked、done 和 unknown，这本身就是信号。部分 Agent 能通过生命周期钩子报告状态，另一些只能依赖前台进程和终端画面匹配。Herdr甚至刻意不把某些不完整的原生钩子作为权威来源，因为它们可能漏掉权限确认、Esc 中断等状态转换。

这里有两个容易被高估的语义：

- **done 并不等于任务被验证成功**，它只是后台工作结束后、尚未被用户查看的一种提醒状态，本质上仍接近 idle。
- `agent prompt --wait` 不跟踪某一轮请求。如果 Agent 原本就在工作，那次既有工作的结束也可能满足等待条件。

因此，Herdr目前更像“可观察、可接管的执行控制台”，而不是具备任务关联、结果校验和精确一次执行保证的工作流引擎。异常的新型确认界面还可能被误判为 idle；`unknown` 也不能视为完成。若将它用于无人值守自动化，调用方仍需设置超时、检查产物，并让任务具备幂等性。

##### 产品价值在于管理人的注意力，而不只是并行算力

Herdr最清晰的使用场景不是让 Agent 无限互相委派，而是让一个人同时监管多个长任务：侧边栏汇总哪个项目仍在运行、哪个等待授权、哪个已经可以审阅；会话持续运行，人可以在本地、远程机器或手机上随时接管。

这是一种值得重视的产品方向：随着 Agent 执行时间变长，用户缺少的往往不是更多对话框，而是**异常升级、待决策事项和完成结果的统一队列**。不过，终端替代不了正式的任务与产物协议。全屏应用的历史输出可能因 alternate screen 丢失，文档甚至建议失败后再让 Agent 把完整结果写入文件——这说明“屏幕文本”适合兼容和人工监督，却不是可靠的数据边界。

Herdr提供的最重要判断是：多智能体系统的下一阶段，竞争点不会只是并发数量，而是能否把**执行身份、状态权威、人工审批和可验证产物**连接起来。终端可以成为很好的兼容层，但要走向真正自主的生产流程，还需要在它之上补上任务关联与结果验证。

### 2026-09-18 10:12:58

#### Herdr 的关键价值：把多智能体编码从“多开终端”变成可观察的协作系统

Herdr 表面上是面向编码智能体的终端管理器，真正值得关注的却不是它支持 Claude Code、Codex 等多少工具，而是它对多智能体协作难点的判断：**当智能体可以并行工作后，瓶颈会从生成能力转向状态识别、任务调度和人的注意力分配。**

##### 三层抽象避免了自动化失控

Herdr 把控制对象明确分为三层：工作区、标签页和窗格负责布局；Pane 负责原始终端输入输出；Agent 则代表窗格中当前被识别的智能体及其生命周期。一个窗格始终存在，但其中的智能体可能退出、被替换或移动。

这种区分看似工程细节，实际决定了系统能否可靠组合。测试服务、文件监听器应该按普通进程控制；只有需要判断“正在工作、等待输入、已经完成”时，才使用 Agent 接口。它还要求从创建结果中读取真实 ID，而不是推测编号，并在窗格移动后更新引用。核心思想是：**位置、进程和语义身份不能混为一谈。**

这套抽象可迁移到更广泛的 Agent 产品。许多系统直接围绕聊天轮次建模，但真实工作包含服务器、脚本、审批界面和长期运行任务。更稳健的设计应把执行环境作为一等对象，再在其上附加智能体身份与状态。

##### 多智能体控制的薄弱点是“状态真相”

Herdr 最有信息量的部分，是它坦率展示了状态识别的不可靠性。部分智能体能通过生命周期 Hook 报告状态；更多工具只能根据前台进程和终端底部画面，匹配规则来推断 idle、working 或 blocked。若已知智能体没有匹配到规则，系统甚至会默认判为 idle；`unknown` 也不代表任务成功。

因此，`agent prompt --wait` 并不是一次严格的“请求—响应”协议：它只等待状态变化，不能追踪具体轮次；如果智能体原本就在工作，当前任务结束也可能满足等待条件。全屏终端使用 alternate screen 时，历史输出还可能根本没有进入宿主滚动区。

这揭示了一个重要边界：**Herdr 已经适合编排与提醒，但还不能仅凭终端状态承担高风险的自治决策。**它对 blocked 采取严格识别、对异常交互避免自动输入，正是合理的安全取舍。对于合并代码、授权权限或执行破坏性命令，仍需额外的结构化回执和确认机制。

##### 真正的产品机会是“注意力路由”

Herdr 的侧边栏会把状态从 Pane 汇总到 Tab 和 Workspace：哪个项目仍在运行、哪个需要审批、哪个已经完成，都集中呈现。它还让会话持续运行，并可经 SSH 从本地终端或手机重新接入。

这意味着多智能体 IDE 的下一步未必是更复杂的聊天界面，而可能是一个可靠的操作控制面：统一任务身份、进度、阻塞原因、产物位置和人工审批。Herdr 已证明终端可以作为兼容层，但也暴露出下一项关键基础设施——让各类编码智能体提供统一、机器可验证的生命周期与结果协议。谁能把“看起来做完了”升级为“可确认地完成了指定任务”，谁才真正具备规模化调度智能体的条件。
