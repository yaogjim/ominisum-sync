[![](https://raw.githubusercontent.com/huggingface/speech-to-speech/main/logo.png)](https://raw.githubusercontent.com/huggingface/speech-to-speech/main/logo.png)

A low-latency, fully modular voice-agent pipeline: **VAD -&gt; STT -&gt; LLM -&gt; TTS**, exposed through an **OpenAI Realtime-compatible WebSocket API**. Every component is swappable. The LLM slot speaks OpenAI-compatible protocols, so you can point it at a hosted provider, at [HF Inference Providers](https://huggingface.co/inference-providers), or at a vLLM or llama.cpp server on your own hardware for a fully local, fully open stack.

This pipeline runs in production as the conversation backend for thousands of [Reachy Mini](https://huggingface.co/blog/reachy-mini) robots.

Switching an OpenAI Realtime client endpoint from hosted OpenAI to a self-hosted speech-to-speech server

#### Quickstart

```
pip install speech-to-speech
export OPENAI_API_KEY=...
speech-to-speech
```

This starts an OpenAI Realtime-compatible server at `ws://localhost:8765/v1/realtime` using Parakeet TDT for local STT, an OpenAI-compatible LLM, and Qwen3-TTS for local speech output.

From a source checkout, talk to it from a second terminal:

```
python scripts/listen_and_play_realtime.py --host 127.0.0.1 --port 8765
```

Prefer to keep the LLM on your own machine? Serve Gemma 4 with llama.cpp:

```
llama-server -hf ggml-org/gemma-4-E4B-it-GGUF -np 2 -c 65536 -fa on --swa-full
```

Then point the OpenAI-compatible LLM backend at it:

Any OpenAI Realtime-compatible client can connect. See Realtime API for the protocol and LLM backends for provider and local-server options.

The pipeline is a cascade of four components, each running in its own thread and connected by queues:

1. **Voice Activity Detection (VAD)**: [Silero VAD v5](https://github.com/snakers4/silero-vad) detects speech boundaries and turn-taking.
2. **Speech to Text (STT)**: transcribes the user's turn, with optional live partial transcripts.
3. **Language Model (LLM)**: generates the response, streaming text and tool calls.
4. **Text to Speech (TTS)**: synthesizes audio and streams it back to the client.

Every stage has multiple interchangeable backends, selected via CLI flags. The code is designed for easy modification, with a focus on models available through Transformers and the Hugging Face Hub.

#### Installation

Requires Python 3.10+.

```
pip install speech-to-speech
```

The default install covers the standard realtime path:

- Parakeet TDT for STT
- OpenAI-compatible API for the language model
- Qwen3-TTS for speech output, using the GGML backend by default on non-macOS platforms and `mlx-audio` on Apple Silicon
- local audio and realtime server modes

macOS and non-macOS dependencies are resolved automatically via platform markers in `pyproject.toml`.

On Linux, the Qwen3-TTS GGML backend comes from `faster-qwen3-tts[ggml]`. Its default `qwentts-cpp-python` wheel on PyPI targets CUDA 12.8. If your machine does not have the CUDA 12 runtime that wheel expects, install the matching wheel from the Hugging Face wheelhouse before installing `speech-to-speech`:

```
# CUDA 13.x
pip install "qwentts-cpp-python==0.3.1+cu130" \
  -f https://huggingface.co/datasets/andito/qwentts-cpp-python-wheels/tree/main/whl/cu130

# CUDA 12.4
pip install "qwentts-cpp-python==0.3.1+cu124" \
  -f https://huggingface.co/datasets/andito/qwentts-cpp-python-wheels/tree/main/whl/cu124

# CPU-only fallback
pip install "qwentts-cpp-python==0.3.1+cpu" \
  -f https://huggingface.co/datasets/andito/qwentts-cpp-python-wheels/tree/main/whl/cpu

pip install speech-to-speech
```

To use the previous CUDA-graphs implementation instead of GGML, pass `--qwen3_tts_backend torch`.

##### Optional Backends

Extra backends are installed with pip extras:

```
pip install "speech-to-speech[kokoro]"          # Kokoro-82M TTS on non-macOS
pip install "speech-to-speech[pocket]"          # Pocket TTS
pip install "speech-to-speech[chattts]"         # ChatTTS
pip install "speech-to-speech[facebook-mms]"    # MMS TTS
pip install "speech-to-speech[faster-whisper]"  # Faster Whisper STT
pip install "speech-to-speech[whisper-mlx]"     # Lightning Whisper MLX STT on macOS
pip install "speech-to-speech[paraformer]"      # Paraformer STT through FunASR
pip install "speech-to-speech[mlx-lm]"          # mlx-vlm support for vision models on macOS
```

Deprecated implementations, including MeloTTS, live in `archive/` and are no longer wired into the CLI.

**Note on DeepFilterNet:** DeepFilterNet, used for optional audio enhancement in VAD, requires `numpy<2` and conflicts with Pocket TTS, which requires `numpy>=2`. Install it manually only in environments where you are not using Pocket TTS.

This setting:

- Sets Parakeet TDT for STT.
- Sets MLX LM as the LLM backend.
- Sets Qwen3-TTS for TTS, using `mlx-audio` with the `6bit` MLX variant by default.
- Sets `--mode local`.

##### WebSocket

1. Run the pipeline in WebSocket mode:
   ```
   speech-to-speech --mode websocket --ws_host 0.0.0.0 --ws_port 8765
   ```
2. Connect from your client at `ws://<server-ip>:8765`. Send raw audio bytes as 16 kHz, int16, mono PCM and receive generated audio bytes back.

##### TCP Socket

TCP socket mode is intentionally minimal. It streams raw PCM audio, but does not provide the full Realtime API feature set, including interruption handling, live transcript events, or tool-call events.

1. Run the pipeline on the server:
   ```
   speech-to-speech --mode socket --recv_host 0.0.0.0 --send_host 0.0.0.0
   ```
2. Run the client locally to handle microphone input and playback:
   ```
   python scripts/listen_and_play.py --host <IP address of your server>
   ```

#### Realtime API

Realtime mode streams audio over a WebSocket using the OpenAI Realtime protocol, with live transcription and low-latency turn-taking. The server exposes `/v1/realtime`, and any OpenAI Realtime-compatible client can connect:

```
from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:8765/v1",
    websocket_base_url="ws://localhost:8765/v1",
    api_key="not-needed",
)

with client.realtime.connect(model="local") as conn:
    conn.send(
        {
            "type": "session.update",
            "session": {
                "type": "realtime",
                "instructions": "You are a helpful assistant.",
                "audio": {
                    "input": {
                        "turn_detection": {
                            "type": "server_vad",
                            "interrupt_response": True,
                        }
                    }
                },
            },
        }
    )

    for event in conn:
        print(event.type)
```

The server implements the core Realtime event set: `input_audio_buffer.append`, `session.update`, `conversation.item.create`, `response.create`, and `response.cancel` inbound; speech start/stop, streaming transcription, audio deltas, tool calls, and `response.done` outbound. The full event reference, architecture, and design details live in the Realtime Engine README.

##### LLM Proxy

With `--enable_llm_proxy`, the realtime server also exposes the remote LLM it is configured with as a plain OpenAI compatible endpoint, so a client can run side tasks (summaries, titles, background agents) with tools and streaming, fully concurrent with the voice conversation and never interrupted by new speech:

- `POST /v1/chat/completions` when running `--llm_backend chat-completions`
- `POST /v1/responses` when running `--llm_backend responses-api`

The server performs no authentication and no throttling of its own. Enable the proxy only on a trusted network, or deploy the server behind a gateway that owns access control. The s2s-endpoint compute replica is such a gateway: it opens these paths only to clients that created their session with an HF token, checks the API key against that token, and applies a rate limit per user. Point the stock OpenAI SDK at whichever host you talk to; this server ignores the API key (a gateway in front decides what it must be):

```
from openai import OpenAI

llm = OpenAI(base_url="http://localhost:8765/v1", api_key="unused")
completion = llm.chat.completions.create(
    model="anything",  # ignored: the server forces its configured --model_name
    messages=[{"role": "user", "content": "Summarize the conversation so far: ..."}],
)
```

Requests are stateless (send the full message list each time) and are proxied to the configured upstream with the key held by the server, which never reaches clients. The `model` field is always overwritten with the server configured `--model_name`. The proxy is off by default, requires a remote backend (`chat-completions` or `responses-api`), and answers 501 with the reason otherwise.

#### LLM Backends

The LLM is the most compute-intensive and highest-latency component in the pipeline. A single forward pass through a large model can dominate end-to-end response time, so choosing the right backend for your hardware and latency budget matters. The pipeline supports:

- **Local inference**: `transformers` on CUDA / CPU and `mlx-lm` on Apple Silicon.
- **Self-hosted servers**: `responses-api` and `chat-completions` can point at a local [vLLM](https://github.com/vllm-project/vllm) or [llama.cpp](https://github.com/ggerganov/llama.cpp) server.
- **Provider APIs**: the same backends work with OpenAI, [HF Inference Providers](https://huggingface.co/inference-providers), [OpenRouter](https://openrouter.ai), and other OpenAI-compatible providers.

Two API backends are available, sharing the same `--responses_api_*` connection flags:

- `--llm_backend responses-api` (default) targets `/v1/responses`.
- `--llm_backend chat-completions` targets `/v1/chat/completions`.

The examples below pair Parakeet TDT for local STT and Qwen3-TTS for local TTS with different LLM backends.

Works with any provider or server that implements the OpenAI Responses API. Point `--responses_api_base_url` at the endpoint and set `--model_name` accordingly:

Provider / server `--responses_api_base_url` `--responses_api_api_key`

OpenAI omit, uses OpenAI default `$OPENAI_API_KEY`

HF Inference Providers `https://router.huggingface.co/v1` `$HF_TOKEN`

OpenRouter `https://openrouter.ai/api/v1` `$OPENROUTER_API_KEY`

vLLM `http://localhost:8000/v1` omit or any string

llama.cpp `http://127.0.0.1:8080/v1` empty string

Identical configuration to `responses-api`, reusing the same `--responses_api_*` connection flags, but talks to `/v1/chat/completions` instead of `/v1/responses`. Prefer it when:

- the provider ignores `chat_template_kwargs.enable_thinking` on the Responses path and needs a `reasoning_effort` knob to suppress reasoning, or
- the server's Responses streaming tool-call path is unreliable, while its Chat Completions tool-call streaming is solid. This is useful for some vLLM builds; see [#312](https://github.com/huggingface/speech-to-speech/issues/312).

##### Fully Local

Run the LLM in a separate llama.cpp process for the lowest-friction fully local setup, as shown in the [Reachy Mini local conversation guide](https://huggingface.co/blog/local-reachy-mini-conversation):

```
# Terminal 1: llama.cpp serving Gemma 4

```

You can use `--mode local` instead of `--mode realtime` when you want to talk through the machine running the server directly. In-process local backends are still available with `--llm_backend mlx-lm` on Apple Silicon or `--llm_backend transformers` on CUDA / CPU.

#### Multi-Language Support

Language coverage depends on the STT and TTS backends you pick, not on the pipeline itself:

Component Backend Languages

STT Parakeet TDT (default) 25 European languages

STT Whisper / Whisper MLX / Faster Whisper Broad multilingual coverage, depending on the selected Whisper checkpoint

STT Paraformer Depends on the selected FunASR checkpoint; the default is Chinese-oriented

TTS Qwen3-TTS (default) Multilingual, with `--qwen3_tts_language auto` by default

TTS Kokoro Multiple language/voice mappings, depending on backend availability

TTS ChatTTS English and Chinese

TTS MMS TTS Broad multilingual coverage through MMS checkpoints

Make sure the STT, LLM, and TTS you pair all cover your target language(s). Two usage patterns:

- **Single language**: set `--language` to the target language code. The default is `en`.
- **Language switching**: set `--language auto`. The STT detects the language of each spoken prompt and forwards it to the LLM. Optionally add `--enable_lang_prompt` to append a "Please reply to my message in..." instruction. It defaults to `False`; large LLMs usually infer the language from context, but the explicit instruction can help smaller models.

Automatic language detection:

```
speech-to-speech \
    --stt parakeet-tdt \
    --language auto \
    --llm_backend mlx-lm \
    --model_name "mlx-community/Qwen3-4B-Instruct-2507-bf16"
```

A single non-English language, Chinese in this example:

```
speech-to-speech \
    --stt whisper-mlx \
    --stt_model_name large-v3 \
    --language zh \
    --llm_backend mlx-lm \
    --model_name mlx-community/Qwen3-4B-Instruct-2507-bf16
```

Both commands also work on top of `--local_mac_optimal_settings`; explicit `--stt` flags override the defaults it sets.

#### CLI Reference

References for all CLI arguments live in the arguments classes and in `speech-to-speech -h`.

##### Module-Level Parameters

See ModuleArguments. It allows setting:

- a common `--device`, if every part should run on the same device
- `--mode`: `realtime` (default), `local`, `socket`, or `websocket`
- STT implementation (`--stt`)
- LLM backend (`--llm_backend`: `transformers`, `mlx-lm`, `responses-api`, or `chat-completions`)
- TTS implementation (`--tts`)
- logging level
- realtime pipeline pool size (`--num_pipelines`)

##### VAD Parameters

See VADHandlerArguments. Notable options:

- `--thresh`: threshold value to trigger voice activity detection.
- `--min_speech_ms`: minimum duration of detected voice activity to be considered speech.
- `--min_speech_continuation_ms`: sustain-bar hysteresis threshold for speech that continues a reopenable soft-ended, uncommitted turn within the reopen window. The default and recommended pairing is `--min_speech_ms 384 --min_speech_continuation_ms 192`.
- `--min_silence_ms`: minimum length of silence intervals for segmenting speech. Default is 64 ms.
- `--short_segment_merge_ms`: optional merge window for stitching adjacent VAD segments that are each shorter than `--min_speech_ms`.
- `--unanswered_reopen_ms`: sanity cap on how long a soft-ended speculative turn that has not yet received any assistant output stays reopenable.

`model_name`, `torch_dtype`, and `device` are exposed for each STT, LLM, and TTS implementation. STT and TTS parameters use the handler prefix, for example `--stt_model_name` or `--qwen3_tts_device`. LLM model selection and chat settings are shared across backends via unprefixed flags, for example `--model_name` and `--chat_size`; backend-specific flags use the `responses_api_` prefix for the `responses-api` and `chat-completions` backends and the `llm_` prefix for local backends.

## 结构化（1）

### 2026-07-31 07:44:31

Hugging Face 的 **speech-to-speech** 是一个低延迟、可完全本地运行的开源语音智能体框架，将 **语音检测 → 语音识别 → 大模型 → 语音合成** 串成完整对话流程，并提供兼容 OpenAI Realtime API 的接口。所有组件均可替换，既能连接云端模型，也能使用本地硬件构建完全开放的语音助手；该系统已用于数千台 Reachy Mini 机器人。

##### 1. 核心架构与特点

系统由四个独立线程组成，各阶段通过队列连接：

1. **VAD（语音活动检测）**
   - 默认使用 **Silero VAD v5**。
   - 判断用户何时开始、停止说话，并负责轮次切换。

2. **STT（语音转文字）**
   - 将用户语音转录成文字。
   - 支持实时输出部分转录结果。

3. **LLM（语言模型）**
   - 流式生成回答和工具调用。
   - 可连接 OpenAI、Hugging Face Inference Providers、OpenRouter，也可连接本地 vLLM、llama.cpp。

4. **TTS（文字转语音）**
   - 将模型回答合成为音频，并实时返回客户端。

各组件都可通过 CLI 参数切换，重点支持 Transformers 与 Hugging Face Hub 上的模型。

##### 2. 快速安装与启动

###### 基础要求

- Python **3.10 及以上**
- 安装命令：

```bash
pip install speech-to-speech
```

设置 API Key 并启动：

```bash
export OPENAI_API_KEY=...
speech-to-speech
```

默认会在以下地址启动兼容 OpenAI Realtime API 的服务：

```text
ws://localhost:8765/v1/realtime
```

默认组合为：

- STT：**Parakeet TDT**
- LLM：兼容 OpenAI API 的模型，默认通过 Responses API 使用 `gpt-5.4-mini`
- TTS：**Qwen3-TTS**
  - 非 macOS 默认使用 GGML
  - Apple Silicon 默认使用 `mlx-audio`

从另一个终端测试语音对话：

```bash
python scripts/listen_and_play_realtime.py --host 127.0.0.1 --port 8765
```

###### Linux CUDA 注意事项

Qwen3-TTS 默认 PyPI wheel 面向 **CUDA 12.8**。若本机 CUDA 环境不同，需要预先安装匹配版本：

- CUDA 13.x：`qwentts-cpp-python==0.3.1+cu130`
- CUDA 12.4：`qwentts-cpp-python==0.3.1+cu124`
- 仅 CPU：`qwentts-cpp-python==0.3.1+cpu`

如需使用旧版 CUDA Graphs 实现，可添加：

```bash
--qwen3_tts_backend torch
```

###### 可选组件

额外后端需通过 extras 安装，例如：

```bash
pip install "speech-to-speech[kokoro]"
pip install "speech-to-speech[pocket]"
pip install "speech-to-speech[faster-whisper]"
pip install "speech-to-speech[whisper-mlx]"
pip install "speech-to-speech[paraformer]"
```

需要注意：

- DeepFilterNet 要求 `numpy<2`
- Pocket TTS 要求 `numpy>=2`
- 两者存在依赖冲突，不建议装在同一环境中
- MeloTTS 等旧实现已移至 `archive/`，不再接入 CLI

从源码开发可执行：

```bash
git clone https://github.com/huggingface/speech-to-speech.git
cd speech-to-speech
uv sync
```

##### 4. 四种运行模式

| 模式 | 传输方式 | 适用场景 |
|---|---|---|
| `realtime`，默认 | OpenAI Realtime WebSocket | 为应用、机器人或设备提供标准语音 API |
| `local` | 本机麦克风和扬声器 | 直接在电脑上对话，无需额外客户端 |
| `websocket` | WebSocket 原始 PCM | 构建不依赖 Realtime 协议的轻量客户端 |
| `socket` | TCP 原始 PCM | 模型运行在远程服务器，本地负责录音与播放 |

###### 原始 WebSocket 模式

```bash
speech-to-speech --mode websocket --ws_host 0.0.0.0 --ws_port 8765
```

客户端需发送：

- 16 kHz
- `int16`
- 单声道 PCM 音频

###### TCP Socket 模式

Socket 模式仅传输原始 PCM，不包含：

- 打断处理
- 实时转录事件
- 工具调用事件
- 完整 Realtime API 功能

服务器端：

```bash
speech-to-speech --mode socket --recv_host 0.0.0.0 --send_host 0.0.0.0
```

客户端：

```bash
python scripts/listen_and_play.py --host <服务器IP>
```

###### Docker

安装 NVIDIA Container Toolkit 后执行：

```bash
docker compose up
```

Compose 会启动：

- 使用 Gemma 4 的 llama.cpp 服务
- TCP 语音服务器
- 端口 `8080`、`12345`、`12346`

##### 5. OpenAI Realtime API 与 LLM 代理

###### Realtime API

服务端点为：

```text
/v1/realtime
```

任何兼容 OpenAI Realtime API 的客户端都可连接。核心支持包括：

- 输入音频追加
- 会话更新
- 创建对话项
- 创建和取消回答
- 语音开始/停止事件
- 流式转录
- 流式音频
- 工具调用
- `response.done`

服务端 VAD 还可设置：

```json
{
  "turn_detection": {
    "type": "server_vad",
    "interrupt_response": true
  }
}
```

这样用户再次说话时，可打断智能体正在播放的回答。

###### LLM Proxy

添加以下参数：

```bash
--enable_llm_proxy
```

语音服务器还会将其远程 LLM 暴露为普通 OpenAI 兼容接口：

- `POST /v1/chat/completions`
- `POST /v1/responses`

可用于并行执行对话总结、标题生成、后台智能体等任务，而且不会因用户插话而中断。

重要限制：

- 默认关闭
- 只支持远程 `chat-completions` 或 `responses-api` 后端
- 请求无状态，客户端每次需提交完整消息
- 客户端提交的 `model` 会被服务端配置的 `--model_name` 覆盖
- 上游 API Key 保存在服务器端，不会发送给客户端
- 服务自身**不做认证和限流**，只能在可信网络使用，或部署在具备访问控制的网关后

---

##### 6. LLM 后端与完全本地部署

LLM 通常是整个流程中计算量最大、延迟最高的环节，因此后端选择会显著影响对话速度。

支持三类方式：

1. **本地进程内推理**
   - CUDA/CPU：Transformers
   - Apple Silicon：`mlx-lm`

2. **自托管服务器**
   - vLLM
   - llama.cpp

3. **云端或第三方 API**
   - OpenAI
   - Hugging Face Inference Providers
   - OpenRouter
   - 其他 OpenAI 兼容服务

两种 API 后端分别是：

- `--llm_backend responses-api`：默认，请求 `/v1/responses`
- `--llm_backend chat-completions`：请求 `/v1/chat/completions`

`chat-completions` 更适合以下情况：

- 服务商在 Responses API 中无法有效关闭推理过程
- Responses 的流式工具调用不稳定
- 某些 vLLM 构建对 Chat Completions 支持更成熟

可通过以下参数尝试关闭推理：

```bash
--responses_api_reasoning_effort none
```

###### 完全本地示例

先用 llama.cpp 启动 Gemma 4：

```bash
llama-server \
  -hf ggml-org/gemma-4-E4B-it-GGUF \
  -np 2 \
  -c 65536 \
  -fa on \
  --swa-full
```

然后让语音管线连接该 OpenAI 兼容服务，即可实现：

- 本地 STT
- 本地 LLM
- 本地 TTS
- 无需将语音或对话发送至云端

##### 7. macOS 与 Apple Silicon 优化

可直接使用：

```bash
speech-to-speech --local_mac_optimal_settings
```

该选项会自动：

- 使用 MPS
- STT 设为 Parakeet TDT
- LLM 设为 MLX LM
- TTS 设为 Qwen3-TTS
- 默认采用 6bit MLX TTS 版本
- 运行模式设为 `local`

也可指定本地模型：

```bash
speech-to-speech \
  --local_mac_optimal_settings \
  --model_name mlx-community/Qwen3-4B-Instruct-2507-bf16
```

Qwen3-TTS 的 `bf16`、`4bit`、`6bit`、`8bit` 版本可通过基准脚本比较速度和效果。

##### 8. 多语言支持

语言能力取决于所选择的 STT 和 TTS，而不是管线本身：

- Parakeet TDT：支持 **25 种欧洲语言**
- Whisper 系列：广泛多语言，具体取决于 checkpoint
- Paraformer：取决于 FunASR 模型，默认偏中文
- Qwen3-TTS：多语言，默认自动识别
- ChatTTS：英语和中文
- MMS TTS：覆盖广泛语言

使用时应确保 **STT、LLM、TTS 三者都支持目标语言**。

###### 固定语言

```bash
--language zh
```

例如使用 Whisper MLX 识别中文：

```bash
speech-to-speech \
  --stt whisper-mlx \
  --stt_model_name large-v3 \
  --language zh \
  --llm_backend mlx-lm \
  --model_name mlx-community/Qwen3-4B-Instruct-2507-bf16
```

###### 自动切换语言

```bash
--language auto
```

STT 会识别每次发言的语言，并将结果传给 LLM。对于较小模型，还可添加：

```bash
--enable_lang_prompt
```

系统会明确提示模型“请使用相应语言回答”；大型模型通常可自行从上下文判断。

##### 10. 关键调优参数

###### VAD 参数

- `--thresh`：触发语音检测的阈值
- `--min_speech_ms`：最短有效语音时长
- `--min_silence_ms`：用于切分语音的最短静音，默认 **64 ms**
- `--short_segment_merge_ms`：合并相邻短语音片段
- `--unanswered_reopen_ms`：未收到助手输出时，暂时保留用户轮次的最长时间

推荐组合：

```text
--min_speech_ms 384
--min_speech_continuation_ms 192
```

每个 STT、LLM、TTS 都可设置：

- 模型名称
- 设备
- 数据类型
- 生成长度与温度等参数

例如：

--llm_gen_temperature 0.7

## 口播总结（1）

### 2026-08-03 00:42:35

#### Hugging Face 开源语音智能体项目概览

这份材料介绍了 Hugging Face 的 speech-to-speech 项目。它是一套低延迟、可自由替换组件的语音智能体系统，可以连接云端模型，也可以完全运行在本地。听完之后，你可以了解它的工作原理、安装和运行方式、模型选择，以及多语言和实时交互能力。

##### 首先，项目解决的是什么问题

核心结论是，这个项目把“听见人说话、理解内容、生成回答、再把回答说出来”串成了一条完整流水线。

这条流水线包含四个环节。

第一个环节是 VAD，也就是语音活动检测。它负责判断用户什么时候开始说话、什么时候停止，以及一轮对话是否已经结束。默认使用 Silero VAD 第五版。

第二个环节是 STT，也就是语音转文字。它把用户的话转成文本，还可以边听边输出不完整的实时转写结果。

第三个环节是 LLM，也就是大语言模型。它根据文字生成回答，并支持流式输出文本和工具调用。

第四个环节是 TTS，也就是文字转语音。它把回答合成为声音，并立即分段发送给用户。

这四个环节分别运行在线程中，通过队列传递数据。这样可以减少等待，并让音频和文本持续流动。更重要的是，每个环节都能更换实现。开发者可以替换识别模型、语言模型或语音合成模型，而不用重写整套系统。

这套流水线已经不是单纯的实验项目。它正在作为数千台 Reachy Mini 机器人的对话后端投入生产使用。

##### 接下来，最快的启动方式

核心结论是，默认配置只需要安装一个 Python 包，再启动一条命令，就能得到兼容 OpenAI 实时协议的语音服务器。

项目要求 Python 版本不低于三点十。安装 speech-to-speech 包后，需要设置 OpenAI 的接口密钥，再运行同名命令。服务器默认监听本机八七六五端口，并提供实时 WebSocket 接口。

WebSocket 可以理解为一种保持长连接、双向持续传输数据的网络方式。它很适合语音场景，因为客户端可以不断发送麦克风音频，服务器也能不断返回合成后的声音，而不必等整段对话全部结束。

默认组合是：用 Parakeet TDT 在本地完成语音识别，用兼容 OpenAI 接口的大语言模型生成回答，再用 Qwen3-TTS 在本地合成语音。默认语言模型是通过 OpenAI Responses API 调用的 gpt-5.4-mini。

如果不希望把语言模型放在云端，也可以在自己的机器上用 llama.cpp 启动 Gemma 4，再把 speech-to-speech 指向这个本地服务。这样，语音识别、语言模型和语音合成都能在本地运行，形成完全本地、完全开放的技术栈。

##### 安装时需要注意什么

首先，默认安装已经覆盖标准实时使用场景，包括本地语音识别、本地语音合成，以及实时服务器和本机麦克风模式。macOS 和其他系统会根据平台自动选择依赖。

在非 macOS 平台上，Qwen3-TTS 默认使用 GGML 后端。GGML 可以理解为一套面向本地模型推理的高效运行方式。它在 Linux 上依赖特定的 Qwen3-TTS 组件，而公开的软件包默认面向 CUDA 十二点八。

这意味着，如果电脑使用的是 CUDA 十三、CUDA 十二点四，或者完全没有英伟达显卡，就要先安装与环境匹配的版本。项目分别提供 CUDA 十三、CUDA 十二点四和纯 CPU 的安装选择。否则，默认组件可能因为缺少对应运行环境而无法启动。

除了默认模型，项目还提供多种可选后端。例如，语音合成可以选 Kokoro、Pocket TTS、ChatTTS 或 MMS；语音识别可以选 Faster Whisper、适合苹果芯片的 Whisper MLX，以及通过 FunASR 使用的 Paraformer。

有一个依赖冲突需要特别注意。用于音频增强的 DeepFilterNet 要求 NumPy 版本低于二，而 Pocket TTS 要求 NumPy 不低于二。因此，这两个功能不适合直接安装在同一个环境中。

如果从源代码安装，可以克隆项目后使用 uv 完成依赖同步。这样会以可编辑模式安装，也适合参与开发。

##### 模型和硬件可以怎样搭配

核心结论是，这套系统没有把用户锁定在某一种模型或硬件上。

在语音识别方面，默认的 Parakeet TDT 可以运行在 CUDA、CPU 和苹果芯片上。Whisper 与 Faster Whisper 适合 CUDA 或 CPU。Lightning Whisper MLX 和 MLX Audio Whisper 主要面向苹果芯片。Paraformer 则可以根据所选 FunASR 模型支持不同语言。

在语言模型方面，可以直接通过 Transformers 在 CUDA 或 CPU 上推理，也可以在苹果芯片上使用 MLX。还可以连接 OpenAI、Hugging Face 推理服务、OpenRouter，或者连接自己部署的 vLLM 和 llama.cpp。

在语音合成方面，默认是 Qwen3-TTS。其他选择包括轻量的 Kokoro、支持声音克隆的 Pocket TTS、支持中英文的 ChatTTS，以及覆盖多种语言的 MMS。

实际选择时，需要同时考虑硬件、延迟和目标语言。尤其是语言模型，通常是整条流水线里计算量最大、等待时间最长的部分。一次大模型推理，就可能占据端到端响应时间的大头。

##### 系统提供四种运行模式

接下来是运行方式。项目一共提供四种主要模式，分别适合不同场景。

第一种是默认的实时模式。它使用 OpenAI Realtime 协议，通过 WebSocket 提供标准实时语音接口。适合开发应用、机器人或其他智能设备。任何兼容这一协议的客户端都可以连接。

第二种是本机模式。它直接使用当前电脑的麦克风和扬声器，不需要额外客户端。适合在一台机器上快速体验或调试。

第三种是原始 WebSocket 模式。客户端发送十六千赫兹、十六位、单声道的 PCM 音频，服务器返回生成后的音频。PCM 是未经压缩的原始声音数据。这种模式协议简单，适合编写轻量的自定义客户端。

第四种是 TCP Socket 模式。它同样传输原始音频，但设计得非常精简，适合把模型放在远程服务器上，再由本地程序负责录音和播放。它不支持完整实时接口中的打断处理、实时转写事件和工具调用事件。

项目还提供 Docker 部署方式。默认编排会启动使用 Gemma 4 的 llama.cpp 服务、TCP 语音服务器，并开放语言模型和音频通信所需的端口。

##### 苹果电脑有专门优化

对于 Apple Silicon，也就是苹果自研芯片，项目提供一组本地最优设置。

核心思路是把计算尽量交给苹果的 MPS 和 MLX 体系。MPS 是苹果设备上的 GPU 加速接口，MLX 则是面向苹果芯片的机器学习框架。

启用这组设置后，系统会选择 Parakeet TDT 做语音识别，使用 MLX 作为语言模型后端，并用 Qwen3-TTS 的 mlx-audio 实现语音合成。默认采用六比特量化版本，同时切换到本机麦克风模式。

量化可以理解为用更少的数字精度保存和运行模型，从而降低内存和计算压力。项目也提供测试脚本，可以比较十六位浮点、四比特、六比特和八比特版本的语音合成表现。

##### 实时接口支持哪些交互能力

更重要的是，实时模式不只是传输声音，它还管理完整的对话过程。

服务器可以接收音频片段、更新会话设置、创建对话内容、要求模型生成回答，以及取消正在生成的回答。返回给客户端的内容包括：用户开始或停止说话、实时转写、分段音频、工具调用，以及一轮回答完成等事件。

它还支持打断。比如智能体正在说话时，用户突然开口，服务器可以检测到新的语音，并停止当前回答。这对自然对话非常关键，因为真实交流并不是一问一答地机械等待。

默认接口位于服务器的实时路径下。客户端只要兼容 OpenAI Realtime 协议，就可以连接这套本地服务，而不必使用项目专属客户端。

##### LLM 代理可以处理语音之外的任务

项目还提供一个可选的 LLM 代理功能。开启后，实时服务器不仅负责语音对话，还会把它连接的远程大模型暴露为普通的 OpenAI 兼容接口。

这样，客户端可以在语音对话进行的同时，执行总结、生成标题或运行后台智能体等任务。这些任务可以使用工具和流式输出，而且不会因为用户开始说新一句话而被打断。

不过，这项功能默认关闭，而且只适用于远程语言模型后端。请求本身是无状态的，也就是说，每次调用都要提交完整的消息列表。客户端传来的模型名称会被忽略，服务器始终使用启动时配置的模型。

安全方面尤其要注意。这个代理本身既不做身份验证，也不限制请求频率。因此只能在可信网络中开启，或者在前面部署负责鉴权和限流的网关。上游模型的密钥由服务器保存，不会发送给客户端。

##### 语言模型后端怎样选择

核心结论是，项目用统一接口连接了本地模型、自建服务器和商业服务。

本地推理可以使用 Transformers，或者在苹果芯片上使用 MLX。自建服务可以是 vLLM 或 llama.cpp。外部服务则可以是 OpenAI、Hugging Face 推理服务、OpenRouter，以及其他兼容 OpenAI 接口的平台。

项目提供两种主要 API 后端。默认是 Responses API，另一种是 Chat Completions API。二者使用相同的一组连接参数，但访问不同的接口路径。

一般来说，只要服务商正确实现 Responses API，就可以使用默认方式。如果某些服务无法可靠处理推理控制或流式工具调用，则可以切换到 Chat Completions。部分 vLLM 版本就可能更适合后一种方式。

如果目标是完全本地运行，一个简单方案是单独启动 llama.cpp，让它托管 Gemma 4，再让 speech-to-speech 通过兼容接口连接。也可以直接在进程内使用 Transformers，或者在苹果芯片上使用 MLX。

##### 多语言能力取决于模型组合

接下来是语言支持。核心结论是，流水线本身不限制语言，但语音识别、语言模型和语音合成必须都支持目标语言。

默认语音识别模型 Parakeet TDT 支持二十五种欧洲语言。Whisper 系列覆盖范围更广，但具体能力取决于所选模型。Paraformer 的语言能力则取决于 FunASR 棩查点，默认模型偏向中文。

默认的 Qwen3-TTS 支持多语言，并可以自动判断输出语言。ChatTTS 支持中文和英文。MMS 通过不同模型覆盖更广泛的语言。Kokoro 的语言和声音选择，则取决于具体后端。

项目支持两种常见用法。

一种是固定语言。例如，把语言设为中文，整段对话就按中文处理。

另一种是自动切换语言。此时，语音识别会判断用户每次说话的语言，再把结果交给大语言模型。系统还可以额外加入“请使用某种语言回答”的明确提示。大型模型通常能根据上下文自行判断，但较小模型可能需要这条提示。

因此，搭建多语言智能体时，不能只看语言模型是否懂中文或英文。还要确认前面的语音识别能听懂，后面的语音合成也能自然说出来。

##### Pocket TTS 和声音克隆

项目特别介绍了 Kyutai Labs 的 Pocket TTS。它支持流式语音合成和声音克隆。

所谓流式合成，就是不必等整段文字全部生成完，模型可以一边收到文字，一边产生声音，从而缩短用户感受到的等待时间。

Pocket TTS 提供多种预设声音，也支持自定义声音文件和 Hugging Face 上的模型路径。它可以运行在 CPU 或 CUDA 上，因此在没有高性能显卡的设备上也有使用空间。

##### 最后，系统可以怎样精细调整

项目通过命令行参数开放了大量配置。

开发者可以选择运行设备、工作模式、语音识别实现、语言模型后端、语音合成实现、日志级别，以及同时运行的流水线数量。每个组件还可以单独指定模型、数据精度和设备。

语音活动检测也能细调。例如，可以设置多长的声音才算有效发言，多长的静音代表一句话结束，以及相邻短语音是否应该合并。

默认建议把有效语音的最短时长设为三百八十四毫秒，把持续语音判定设为一百九十二毫秒。用于切分语音的最短静音默认是六十四毫秒。这些参数直接影响系统是否会过早打断用户，或者在用户已经说完后等待太久。

文本生成参数也可以调整，例如最大生成长度和温度。还没有开放的参数，可以通过修改对应的参数类加入。

项目欢迎提交问题和代码改进。较大的修改建议先讨论方案。使用这套流水线发表项目或研究成果时，也应分别引用实际采用的语音检测、语音识别和语音合成模型。

##### 重点回顾

最后，最值得记住的有五点。

第一，speech-to-speech 把语音检测、语音识别、大语言模型和语音合成串成了一条低延迟流水线，而且四个部分都能替换。

第二，它既能连接 OpenAI、Hugging Face 等外部服务，也能通过 llama.cpp、vLLM、Transformers 或 MLX 完全在本地运行。

第三，默认实时服务器兼容 OpenAI Realtime 协议，支持流式转写、音频返回、工具调用和用户打断，适合应用、设备和机器人。

第四，模型选择要同时考虑硬件、响应速度和语言覆盖。尤其要确保语音识别、语言模型和语音合成三者都支持目标语言。

第五，这套系统已经用于数千台 Reachy Mini 机器人的生产对话后端，说明它不仅强调开放和模块化，也面向实际的实时语音应用。

## 深度解读（1）

### 2026-09-18 00:13:21

#### 开源语音智能体的关键进展，不是模型，而是可替换的实时系统

这个项目名为 speech-to-speech，但它并非一个端到端语音模型，而是把语音交互拆成 **VAD（语音边界检测）→ STT → LLM → TTS** 四段，每段独立运行、通过队列连接，并允许替换实现。它更值得关注的地方，是证明了开源组件已经可以被组织成一套接近产品基础设施的实时语音栈：既能全部本地运行，也能只把 LLM 放在云端，还能直接服务数千台 Reachy Mini 机器人。

##### 接口标准化正在降低语音产品对单一供应商的依赖

项目对外实现了 OpenAI Realtime 兼容的 WebSocket API，对内则支持 OpenAI、Hugging Face、OpenRouter、vLLM、llama.cpp，以及多种 STT、TTS 后端。这意味着客户端不必知道后端究竟使用云模型还是本地模型，产品团队可以在基本不改交互层的情况下，按成本、隐私、语言和硬件重新组合供应链。

这比“又多了几个开源模型”更重要。模型性能仍会快速更替，而稳定接口能把这种变化转化为可利用的选择权：原型期接云端模型，规模扩大后把 STT、TTS 移到设备侧；涉及敏感数据时全本地运行；硬件不足时再切回托管服务。

不过，这种兼容目前只是核心事件集兼容，并不等于所有 OpenAI Realtime 行为都完全一致。它降低的是迁移成本，而不是消除集成与测试成本；同时也显示 OpenAI 的协议正在成为事实标准，开源生态获得了互操作性，却可能形成新的接口依赖。

##### 语音体验的瓶颈，是“何时接话”，不只是模型够不够快

仓库花了大量篇幅处理 VAD 阈值、短语音合并、软结束、重新打开话轮和用户打断。这些看似琐碎的参数，实际上决定了产品体验：停顿太短就提交，助手会抢话；等待太久，又显得迟钝；回答期间用户插话，还必须立即停止生成和播放。

因此，端到端延迟不能只看 LLM 首字时间。它至少包括识别用户是否说完、转写、生成首批文本、合成首段音频以及播放调度。项目把各阶段放进独立线程并流式连接，价值正在于缩短“等全部完成后再进入下一步”的串行等待。

这也解释了为什么级联架构仍然有生命力。端到端语音模型可能更自然，但级联系统更容易定位问题、替换能力、控制成本和适配多语言。对机器人、客服、车载等需要工具调用和确定性行为的场景，这种可控性往往比单项模型指标更重要。

##### 真正的产品机会在运维层，而不是再做一层语音包装

仓库同时暴露了开源方案的现实代价：CUDA 版本、平台差异、依赖冲突、语言覆盖以及模型组合都需要处理。目标用户若是机器人和边缘设备团队，他们的替代方案要么是采购封闭的实时 API，要么长期维护一套自研拼装系统。

因此更可能成立的机会，是围绕这类模块化语音栈提供**硬件适配、组合基准、延迟与质量观测、自动降级、远程部署和版本管理**。需要验证的核心假设不是“大家想要语音助手”，而是隐私、离线能力与供应商可替换性，是否足以让客户承担本地推理的运维成本。

“已用于数千台机器人”是一个有分量的可行性信号，但仓库没有给出延迟分布、并发、故障率和语音质量数据。它证明了开源实时语音系统已经能进入生产，却还没有证明它能在所有场景取代托管方案。更准确的判断是：**语音智能体正在从单一模型竞争，转向接口、编排与运行控制的系统竞争。**

## 默认总结（1）

##### 一句话看懂

这是 Hugging Face 的开源语音代理框架：把语音检测、语音识别、语言模型和语音合成串成低延迟流水线，各环节均可替换，并可完全在本地运行。

##### 关键内容

- 流程为 **VAD → STT → LLM → TTS**：判断何时说话、转成文字、生成回答，再合成为语音；各模块独立运行并通过队列连接。
- 默认提供兼容 OpenAI Realtime 的 WebSocket 接口，现有兼容客户端可直接接入；也支持本机麦克风、原始 WebSocket 和 TCP 等模式。
- 默认使用本地 Parakeet TDT 识别、Qwen3-TTS 合成，但语言模型默认调用 OpenAI 兼容接口；若搭配 llama.cpp、vLLM 或本地 Transformers/MLX，才是完整本地方案。
- 支持多种识别、模型和合成后端及多语言，但实际语言范围、延迟和硬件要求取决于具体组合。该框架已用于数千台 Reachy Mini 机器人。

##### 通俗解读

它不是一个单独的“语音大模型”，而是可自由换零件的语音助手组装框架。需要注意：开启 LLM 代理后服务本身没有认证和限流，不宜直接暴露到公网。
