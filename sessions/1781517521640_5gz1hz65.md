- **核心高价值点**：对Agent而言，文档质量不等于有效引导，关键信息必须进入其执行路径，最好以错误、CLI输出、工具描述等硬信号呈现。

**知识要点**

- AI Agent通常不会像人类开发者一样主动浏览README、SDK注释或依赖目录中的说明文件
- 软引导是指不在Agent当前任务路径上的提示，通常容易被忽略

- 模块化skill文件比单一大文档更适合Agent按需加载，也更利于团队维护
- Agent体验设计需要围绕Agent的信息扫描、上下文加载和决策路径来设计环境

**行动项**

- 在设计API、SDK或MCP工具时，将关键约束放入错误消息、CLI输出和工具描述等Agent必经路径
- 将大型文档拆分为短小、聚焦、可按需加载的模块化skill文件
- 避免只依赖README、注释或非阻塞警告传递关键安全与版本信息
- 检查现有开发者工具中哪些提示属于软引导，并改造成阻塞性或任务路径内的硬信号

\# 你不能对 AI Agent 小声说话：Stripe 用 12 个实验揭示的 Agent 行为规律

Stripe 的 Minions 系列我们已经翻过两篇了。最近他们又发了一篇，不是讲怎么造 Agent，而是讲一个更底层的问题：\*\*Agent 到底是什么行为模式？你怎么让它做对的事？\*\*

两位作者——James Beswick（开发者关系负责人）和 Peter Epsteen（Growth 团队工程师）——跑了大约 12 个实验，核心问题只有一个：\*\*怎么让 AI Agent 正确使用 Stripe 的 API？\*\*

"正确"在这里的意思是：用最新 API 版本、遵循集成最佳实践、不写出隐含安全隐患的代码。

实验结果可以用一句话总结：\*\*AI Agent 不像勤奋的初级工程师。它像一个只读任务描述、其他什么都不看的合同工。\*\*

\---

\## 三类引导，三种结果

Stripe 把实验分成了三种引导方式，结果截然不同。

\### 1. 被动提示（Passive Hints）——全部无效

团队在 SDK 里嵌入了提示、在 API 响应里加了警告字段、在依赖目录里放了 AGENTS.md 文件——这些都是人类开发者自然会看到的地方。

\*\*全部被 Agent 忽略。\*\*

\- SDK 注释、README 补充、代码内联注释：Agent 不看  
\- 依赖目录里的 AGENTS.md：Agent 几乎从不读取依赖文件夹里的文件  
\- API 响应中的"警告哈希"字段：Agent 解析响应时只提取需要的数据，警告字段被当作噪音跳过

\*\*结论：Agent 不会浏览。它只会提取任务需要的最小信息，然后走。\*\*

\### 2. 主动提示（Active Prompts）——有效，但不保证

两种做法有明显效果：

\- \*\*模块化 skill 文件\*\*（把一个大文档拆成短小、聚焦的子文件，按需加载）：Agent 表现提升约 \*\*10%\*\*，token 消耗也下降了。  
\- \*\*CLI 登录后的安装提示\*\*（\`stripe login\` 之后直接展示安装命令）：\*\*30-35%\*\* 的用户复制了安装命令。

\*\*结论：信息必须在 Agent 的必经路径上。不在路径上的东西，等于不存在。\*\*

\### 3. 硬信号（Hard Signals）——最有效

当 Agent 使用了过期的 API 版本时，如果返回的是一个"降级响应 + 礼貌警告"，Agent 不会修正。但如果返回的是一个\*\*明确的错误\*\*——"你用了 v1，当前是 v2，请修正"——Agent 可靠地检测到了错误、识别了版本不匹配、并修正了请求。

不需要读提示、不需要读文档。\*\*错误本身就是指令。\*\*

\---

\## 为什么软引导失效？

这 12 个实验揭示的不是一个技术限制，而是一个结构性特征：\*\*AI Agent 是超聚焦的任务完成器。它们扫描可操作数据，提取所需信息，然后继续往前走。\*\* 警告、提示、邻近文档、微妙的上下文线索——这些都在它们的优化函数之外。

Stripe 对这个现象有一个精确的命名：\*\*"hard versus soft steering"（硬引导 vs 软引导）。\*\*

软引导 = 任何不在 Agent 当前任务路径上的信息。Agent 看不到它，因为它没有理由去看。

硬引导 = Agent 为了完成任务必须处理的东西。一个错误、一个阻塞性提示、一段已经加载到上下文中的明确指令。

\*\*这不是内容质量问题，是分发问题。\*\* Stripe 的文档质量是业界公认的。问题在于 Agent 有没有实际加载它。

\---

\## 模块化设计的好处在人也在 Agent

一个意外收获：模块化的 skill 文件不仅在 Agent 表现上好于单一巨型文件，在可维护性上也更好。

支付团队维护支付的 skill。订阅团队维护订阅的 skill。\*\*对人类更好，对 Agent 也更好。\*\* 这是一个少见的、两个优化方向恰好一致的产品决策。

\---

\## 为什么这很重要

\### 1. 它解释了 Ponytail 为什么有效

回顾上一篇 Ponytail article 里的"梯子"逻辑——Agent 在写任何代码之前先问六个问题，在第一个能站稳的台阶停下。这本质上就是一种硬引导：它不是给 Agent "建议"，而是在它的推理路径上强制插入决策点。

\### 2. 它对所有做开发者工具的人都是一个信号

如果你在做一个会被 AI Agent 使用的 API 或 SDK，这篇实验告诉你：\*\*放在文档里是不够的。放在 SDk 注释里是不够的。Agent 的上下文加载路径和人类完全不同。\*\*

你需要把关键信息放在 Agent 必经的地方：错误消息、CLI 输出、MCP 工具描述。那些"人类会自己去翻文档"的假设在 Agent 时代不成立。

\### 3. 它暗示了一个被低估的技能：Agent 体验设计

我们讨论了很多"Agent 工程"——怎么让 Agent 更聪明、处理更长的上下文、更好地规划。但 Stripe 的这篇实验指向的是另一个方向：\*\*不是让 Agent 更聪明，而是让环境更适配 Agent 的认知模式。\*\*

就像 UX 设计理解人类怎么扫描页面、怎么点按钮，Agent 体验设计需要理解 Agent 怎么扫描信息、怎么加载上下文、在什么时候做决策。

\---

\## 局限

Stripe 明确说这不是正式研究论文，是观察性实验。没有公开样本量、置信区间、或测试的具体模型/框架。这些发现反映的是 2026 年初的 Agent 行为，Agent 进步很快，未来模型可能会更好地浏览上下文。

但核心结论——\*\*你不能对 Agent 小声说话\*\*——是一个不太可能随着模型进步而消失的结构性特征。Agent 优化的是任务完成，不是环境理解。这和模型聪明不聪明没关系，和目标函数的定义有关系。

#### 文章总结：你不能对 AI Agent 小声说话

##### 核心观点

Stripe 通过约 12 个实验发现：**AI Agent 并不像会主动查资料的初级工程师，而更像只执行任务描述的合同工。**

它不会主动浏览文档、注释或提示，而是只提取完成当前任务所需的最小信息。因此，想让 Agent 做对事，关键不是“把信息写好”，而是**把信息放到它必经的执行路径上**。

---

##### Stripe 的三类实验结论

###### 1. 被动提示：基本无效

Stripe 尝试把提示放在 SDK 注释、README、依赖目录里的 `AGENTS.md`、API 响应警告字段中。

结果是：**Agent 基本不看。**

原因是 Agent 不会像人类一样浏览环境，它只关注当前任务需要的数据。  
不在执行路径上的提示，对 Agent 来说几乎等于不存在。

---

###### 2. 主动提示：有效但有限

两类方式有明显效果：

- **模块化 skill 文件**：把大文档拆成短小、聚焦的文件，按需加载，Agent 表现提升约 10%，token 消耗下降。
- **CLI 登录后的安装提示**：在 `stripe login` 后直接展示安装命令，30%-35% 用户会复制执行。

结论是：**信息必须出现在 Agent 的必经路径上。**

---

###### 3. 硬信号：最有效

当 Agent 使用旧 API 时，如果只是返回“降级响应 + 警告”，Agent 往往不会修正。

但如果直接返回明确错误，例如：

> 你用了 v1，当前是 v2，请修正。

Agent 就能可靠识别问题并修改请求。

所以，**错误本身就是一种强指令**。  
对 Agent 来说，阻塞性错误比温和提醒更有效。

##### 为什么软提示会失败？

> Hard steering vs Soft steering  
> 硬引导 vs 软引导

###### 软引导

指不在 Agent 当前任务路径上的信息，例如：

- 文档
- 注释
- README
- 警告字段
- 邻近上下文

指 Agent 为了完成任务必须处理的信息，例如：

- 明确错误
- 阻塞提示
- CLI 输出
- 已加载进上下文的指令
- MCP 工具描述

核心问题不是内容质量，而是**分发路径**。

##### 对产品和开发者工具的启示

###### 1. 文档不再足够

过去面向人类开发者时，文档、注释、README 很重要。

你需要把关键信息放到：

- 错误消息里
- CLI 输出里
- 工具调用描述里
- Agent 必须经过的流程节点里

- Agent 什么时候做决策

- 哪些提示能真正影响行为

重点不是让 Agent 更聪明，而是**让环境更适配 Agent 的认知模式**。

Stripe 发现，模块化 skill 文件不仅让 Agent 更容易使用，也让团队维护更方便。

例如：

- 支付团队维护支付 skill

- 各模块独立更新、独立优化

这是少见的“对人类和 Agent 都更优”的设计方向。

**它只读取当前任务需要的信息，不会像人类一样主动浏览文档、注释或周边文件。**

- README 补充说明；

两个有效案例：

- **模块化 skill 文件**：  
  把大文档拆成短小、聚焦的子文件，Agent 按需加载。  
  效果是：Agent 表现提升约 **10%**，token 消耗也下降。

- **CLI 登录后的安装提示**：  
  在用户执行 `stripe login` 后直接展示安装命令。  
  结果有 **30%～35%** 的用户复制了安装命令。

**结论：信息必须出现在 Agent 的任务路径上；不在路径上的内容，对 Agent 来说等于不存在。**

---

###### 2.3 硬信号：最有效

最有效的方式是给 Agent 明确、阻塞性的反馈。

例如，当 Agent 使用过期 API 版本时：

- 如果系统只返回“降级响应 + 礼貌警告”，Agent 通常不会修正；
- 如果系统直接返回明确错误：  
  “你用了 v1，当前是 v2，请修正”，  
  Agent 就能识别版本不匹配，并修正请求。

**结论：对 Agent 来说，错误本身就是指令。**  
它不需要额外读文档，只要错误信息足够明确，就会调整行为。

---

##### 3. 为什么软引导会失效？

Stripe 将这种现象称为：

> **Hard steering vs Soft steering：硬引导 vs 软引导**

###### 软引导

指那些不在 Agent 当前任务路径上的信息，例如：

- 文档；
- 注释；
- 提示；
- 周边文件；
- 微妙的上下文线索。

这些内容即使写得很好，Agent 也可能根本不会加载。

###### 硬引导

指 Agent 为完成任务必须处理的信息，例如：

- 明确错误；
- 阻塞性提示；
- 已经加载到上下文中的指令；
- CLI 输出；
- MCP 工具描述。

文章强调：  
**这不是文档质量问题，而是信息分发问题。**  
Stripe 的文档质量很高，但如果 Agent 没有加载文档，文档再好也没用。

---

##### 4. 模块化设计同时利好人类和 Agent

实验还有一个意外发现：  
**模块化 skill 文件不仅让 Agent 表现更好，也更利于人类维护。**

例如：

- 支付团队维护支付相关 skill；
- 订阅团队维护订阅相关 skill。

这种方式避免了一个庞大的巨型文档，也让 Agent 更容易按需读取关键信息。

**这是少见的人类体验和 Agent 体验同时优化的设计。**

---

##### 5. 对开发者工具和 Agent 设计的启示

###### 5.1 解释了 Ponytail 方法为什么有效

文章提到，之前 Ponytail 中让 Agent 写代码前先问六个问题，本质上也是一种硬引导。

它不是给 Agent “建议”，而是在 Agent 的推理路径中强制插入决策点，让它必须先判断再行动。

---

###### 5.2 对 API、SDK、开发者工具设计者的提醒

如果你的产品会被 AI Agent 使用，仅仅把最佳实践写在文档里已经不够了。

不够有效的位置包括：

- 文档；
- SDK 注释；
- README；
- 依赖目录中的说明文件。

更有效的位置包括：

- 错误消息；
- CLI 输出；
- MCP 工具描述；
- Agent 当前上下文中必然加载的指令。

核心变化是：  
**过去可以假设人类会主动翻文档，但不能假设 Agent 也会这么做。**

---

###### 5.3 Agent 体验设计将变得重要

文章提出一个被低估的方向：**Agent 体验设计**。

这不是单纯让 Agent 更聪明，而是让产品环境更适配 Agent 的认知方式。

类似 UX 设计研究人类如何浏览页面、点击按钮；  
Agent 体验设计需要研究：

- Agent 如何扫描信息；
- Agent 何时加载上下文；
- Agent 在哪里做决策；
- 哪些提示会被忽略，哪些信号会被执行。

##### 6. 局限性：不是正式论文，但结论有参考价值

Stripe 明确说明，这不是正式研究论文，而是观察性实验。

文章没有公开：

- 样本量；
- 置信区间；
- 使用的具体模型；
- 使用的 Agent 框架。

这些发现主要反映的是 **2026 年初**的 Agent 行为。未来模型可能会更擅长浏览上下文。

但作者认为，核心规律不太可能消失：

> **你不能对 Agent 小声说话。**

因为 Agent 优化的是任务完成，而不是全面理解环境。  
所以，想让 Agent 做对事，关键不是把提示写得更隐晦、更完整，而是把它放到 Agent 必须经过的位置上。

##### 1. 一句话判断

> 最值得保留的是：**AI Agent 不是“会主动理解环境的员工”，而是“只处理任务路径上硬信号的执行器”；因此，设计 Agent 可用系统的关键不是写更多文档，而是把正确行为嵌入它无法绕开的路径。**

这不是关于 Stripe API 的局部经验，而是一个可迁移的 Agent 设计原则：**信息是否存在不重要，是否进入 Agent 的执行路径才重要。**

---

##### 2. 最重要的洞见

###### 洞见 1：Agent 不会“浏览”，只会“提取”

###### **核心观点：**  
> Agent 不像人类开发者会顺手看 README、注释、警告、依赖目录文件；它只提取完成当前任务所需的最小信息。

**为什么重要：**  
很多产品默认“只要我写在文档里/注释里/响应里，使用者就会看到”。对 Agent 来说，这个假设失效。

**反常识之处：**  
人类认为“信息靠近任务就足够了”，但 Agent 需要的是“信息在任务路径上”。

**可迁移价值：**  
凡是面向 Agent 的系统，都要重新设计信息分发方式：

- 文档不是入口
- 注释不是保障
- 警告字段不是约束
- 必经路径才是控制点

**我应该记住什么：**  
> 对 Agent 来说，不被加载到上下文里的信息，等于不存在。

---

###### 洞见 2：软提示无效，硬信号才是指令

###### **核心观点：**  
> 礼貌警告、提示、最佳实践建议很容易被忽略；明确错误、阻塞、强制决策点，才会改变 Agent 行为。

**为什么重要：**  
Stripe 发现，当 Agent 使用旧 API 时，返回“降级响应 + 警告”没用；但返回明确错误，它会识别、修正、继续完成任务。

**反常识之处：**  
传统开发者体验追求“兼容、温和、不打断”；但 Agent 体验里，**适度打断反而更可靠**。

**可迁移价值：**

- API：用错误消息承载修正路径
- CLI：在关键节点直接给下一步命令
- 工作流：把关键判断做成必须回答的问题
- 安全：不要只警告，要在危险路径上阻断

**我应该记住什么：**  
> 错误不是失败；对 Agent 来说，错误是最强的导航信号。

---

###### 洞见 3：Agent 体验设计比“让 Agent 更聪明”更可控

###### **核心观点：**  
> 与其期待 Agent 主动理解复杂环境，不如改造环境，让正确行为变成默认路径。

**为什么重要：**  
行业常把问题归因于模型能力：上下文不够长、推理不够强、规划不够好。Stripe 的实验提醒：很多问题不是模型不聪明，而是环境没有为 Agent 的行为模式设计。

**反常识之处：**  
解决 Agent 错误，不一定靠更强模型，而可能靠更好的接口、错误、上下文加载和任务路径设计。

**可迁移价值：**  
这会催生一类新能力：**Agent Experience Design，代理体验设计。**

它类似 UX，但对象不是人：

- 人类扫描页面，Agent 扫描上下文
- 人类点击按钮，Agent 调用工具
- 人类读提示，Agent 处理硬约束
- 人类会探索，Agent 倾向最短路径完成任务

**我应该记住什么：**  
> 不要只优化 Agent，要优化 Agent 所处的环境。

---

###### 洞见 4：模块化不是文档洁癖，而是上下文工程

###### **核心观点：**  
> 把大文档拆成短小、聚焦、按需加载的 skill 文件，既提升 Agent 表现，也降低 token 消耗和人类维护成本。

**为什么重要：**  
模块化文档不是单纯为了可读性，而是为了让 Agent 更容易加载“正好需要的部分”。

**反常识之处：**  
很多团队追求“完整大文档”；但对 Agent 来说，完整可能意味着噪音，聚焦才意味着可用。

**可迁移价值：**

- 产品文档应从“百科式”转向“任务式”
- SDK 指南应按场景拆分
- 内部知识库应变成可检索、可调用、可组合的模块
- Agent 工具描述要短、准、可执行

**我应该记住什么：**  
> 给 Agent 的信息不是越多越好，而是越贴近当前动作越好。

##### 3. 底层逻辑

###### **逻辑一：Agent 优化的是任务完成，不是环境理解**

- 表层现象：  
  Agent 忽略 README、注释、警告字段、依赖目录里的 AGENTS.md。

- 深层原因：  
  Agent 的行为目标是完成当前任务，它会压缩信息搜索范围，只处理看起来直接有用的数据。

- 推导结论：  
  如果某条信息不是完成任务的必要步骤，Agent 大概率不会处理它。

---

###### **逻辑二：控制 Agent 行为的关键，是控制它的路径**

- 表层现象：  
  被动提示无效；CLI 输出、模块化 skill、明确错误有效。

- 深层原因：  
  这些有效方式不是“内容更好”，而是它们进入了 Agent 必须经过的执行链路。

- 推导结论：  
  Agent 设计的核心不是“把信息放在哪里”，而是“Agent 什么时候、因为什么必须处理它”。

---

###### **逻辑三：硬约束比软建议更适合机器执行者**

- 表层现象：  
  “请使用新版 API”的警告无效；“你用了旧版本，请修正”的错误有效。

- 深层原因：  
  软建议需要主动权衡，硬错误直接改变任务状态，迫使 Agent 修正。

- 推导结论：  
  对高风险、高一致性要求的系统，要把最佳实践设计成机制，而不是建议。

## 深度解读（1）

### 2026-09-18 00:50:45

#### 从“写好文档”到“约束执行路径”：Stripe 实验真正改变的是 API 设计

Stripe 这组实验最值得保留的，不是“Agent 不爱读文档”这个表面结论，而是一个更具迁移性的判断：**对执行正确性至关重要的信息，不能依赖使用者主动发现，必须进入任务的必经路径。**

据文中转述，SDK 注释、README、依赖目录中的 `AGENTS.md`，甚至 API 响应里的警告字段，都很容易被 Agent 忽略；模块化、按需加载的 skill 文件能带来约 10% 的提升，而明确阻断旧版本请求的错误，最能稳定促使 Agent 修正行为。区别不在于措辞够不够醒目，而在于这些信息是否影响任务继续执行。

##### 错误信息正在从“事后解释”变成控制接口

人类开发者遇到警告，可能会凭经验判断风险、翻阅文档；Agent 更倾向于提取完成当前任务所需的最少信息。一个不影响返回结果的 warning，常被视为噪音；一个导致调用失败的版本错误，则必须被纳入下一步决策。

这意味着 API 的错误机制不再只是给人看的文案，而开始承担**机器可消费的控制面**。相比“请参考最新版文档”，更有效的设计可能包括：稳定的错误码、明确指出冲突字段、给出允许版本或替代参数，以及可直接执行的修复动作。对于认证、权限、资金安全等高风险约束，更应默认失败关闭，而不是期待 Agent 正确理解一段温和提醒。

更进一步说，最可靠的 Agent 文档可能不是文档，而是协议本身：通过类型、参数校验、权限边界和状态机，让错误状态难以产生。这个原则也适用于人类软件工程，只是 Agent 把过去尚可容忍的含糊设计放大了。

##### “Agent 体验”不是另一套文案，而是环境设计

文章提出的 Agent 体验设计值得重视，但它不应被理解成给 README 增加一个“AI 专区”。真正的问题是：Agent 如何获得上下文、调用哪些工具、在哪些节点必须重新决策。

模块化 skill 文件有效，可能不只是因为内容更短，还因为它同时改善了检索精度、上下文成本和团队所有权：支付团队维护支付规则，订阅团队维护订阅规则。这里出现了一个很有价值的统一方向——**知识按任务边界拆分，既有利于组织维护，也有利于按需注入模型上下文。**

对 API、SDK 和开发者工具产品而言，下一步不只是建设 MCP 或生成机器版文档，而是建立可观测的 Agent 使用漏斗：它加载了什么、忽略了什么、在哪类错误后能否自我修复。否则，“支持 Agent”仍只是功能声明，无法判断关键约束是否真正抵达执行现场。

##### 不必把当前表现误判为 Agent 的永久本性

这组结果没有公开样本量、模型、框架和置信区间，因此“Agent 天生不会浏览”“这是不会随模型进步消失的结构特征”仍然是作者的延伸判断，而非已被充分证明的事实。不同 Agent 框架完全可能主动搜索文档、自动加载规则，模型能力也会继续变化。

更稳健、也更长期有效的结论是：**不要把正确性建立在可选注意力上。** 无论执行者是今天的 Agent、未来更强的模型，还是匆忙的人类开发者，关键规则若只能靠“恰好看见并正确理解”，系统就把产品责任转嫁给了使用者。Stripe 的实验真正提示的，是把最佳实践从建议升级为可执行约束，把文档从信息仓库改造成运行时的一部分。
