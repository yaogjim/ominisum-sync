## 正文

**Ray Wang**

晚上刚看完 Lenny 这期访谈 Fiona Fung，现 Claude Code 和 Cowork 工程负责人，感受颇深，很多最新的组织变化只有在 Anthropic 这样的企业才会发生

1、“verification” 取代 “coding” 成了新瓶颈。coding is solved，代码不再是 bottleneck，但这个瓶颈没有消失，而是转移到了 verification。现在不只是工程师，设计师、PM、法务甚至财务都在写代码，产出暴涨，问题变成“如何保证8x的代码质量”。

2、她自己的管理方式被 routines 改造了。她有一个常驻的 Claude Code session 接入所有 repo + 所有 Slack 频道 + 所有指标，每月跟下属一起开 session 复盘“发了什么、市场反馈如何、有没有 bug”。

3、招人只剩两类。 “creative builders with product sense”（有产品直觉的造梦者）和“deep systems experts for the hard parts”（啃硬骨头的系统专家），中间层不再吃香。

4、vibe 从 “token-maxing” 转向 “ROI”。 早期大家比谁烧 token 多、跑 agent 多，跟当年比 lines of code 一样虚，现在更盯 outcome，不是 usage。

5、“bad vs sad” 质量框架。 bad = 不可恢复的严重错误（比如 CLI 崩溃、丢工作）；sad = 可恢复的痛点（比如界面闪烁）。但 sad 堆多了会变成 bad。每个团队自己定义什么算 bad、什么算 sad，high agency 配 high accountability。

6、规划从 6 个月路线图改成 JIT（just-in-time）月度规划。 她刚加入时想做 6 个月 roadmap，3 个月就发现没人再看了，因为变化太快。现在就一个 Excel 列本月优先级，每周 check 一次。

7、团队开始觉得孤独。他们发现现在每个人都在跟自己的 agent 闷头干，所以专门搞了 pairwise programming lunch 和 hackathon，就为了让人重新坐到一起，不过看别人怎么用 Claude Code 本身收获巨大，因为每个人用法都不一样。

总结来说，产出早就不是问题了，判断力和怎么不被 agent 淹没才是。

## 解读（1）

### 2026-07-03 11:55:37

#### 深度总结

这篇内容讲的是：**AI 编程成熟后，软件组织的核心矛盾正在转移**。

过去瓶颈是“谁能写代码、写得多快”；  
现在瓶颈变成“谁能判断代码对不对、值不值、会不会出事”。

##### 核心变化

###### 1. 写代码不再稀缺，验证变成瓶颈

AI 让代码产出暴涨。  
工程师、产品、设计、法务、财务都可能用 AI 写代码。

但问题也随之出现：

> 代码更多了，真正难的是确认这些代码是否可靠、正确、有价值。

所以新瓶颈不是 coding，而是 verification。

---

###### 2. 管理方式被 AI 改造

Fiona Fung 的管理方式已经深度 AI 化。

她让 Claude Code 接入：

- 所有代码仓库
- 所有 Slack 频道
- 所有业务指标

然后和团队定期复盘：

- 最近发布了什么
- 用户反馈如何
- 有没有 bug
- 哪些问题值得继续投入

管理不再只是听汇报，而是让 AI 帮助穿透信息。

---

###### 3. 人才结构两极化

未来更需要两类人：

| 类型 | 特点 |
|---|---|
| 有产品感的创造者 | 能发现问题、定义产品、快速搭建 |
| 深度系统专家 | 能解决底层复杂问题、硬骨头问题 |

中间型、只会执行的人价值下降。

因为普通代码生成、常规实现，AI 已经能做很多。

---

###### 4. 从“炫耀用 AI”转向“看结果”

早期很多人比的是：

- 谁用了更多 token
- 谁跑了更多 agent
- 谁自动化得更花哨

但这和过去比“代码行数”一样，容易虚假繁荣。

现在真正重要的是：

> AI 到底带来了什么业务结果？

不是 usage，而是 ROI。

---

###### 5. 质量管理更细了：bad vs sad

他们把问题分成两类：

- **bad**：严重、不可恢复的问题  
  例如 CLI 崩溃、用户工作丢失
- **sad**：可恢复但影响体验的问题  
  例如界面闪烁、响应不顺

但如果 sad 太多，也会积累成 bad。

这说明：  
AI 时代不是不要质量，而是更需要清晰定义质量边界。

---

###### 6. 长期路线图失效，转向即时规划

过去做 6 个月 roadmap。  
但变化太快，3 个月后就没人看了。

现在改成：

- 月度优先级
- 每周检查
- 随时调整

组织从“长期确定性规划”转向“高频适应”。

---

###### 7. 人变得更孤独

每个人都在和自己的 agent 协作，反而减少了人与人的互动。

所以团队需要刻意组织：

- pair programming lunch
- hackathon
- 互相展示 AI 使用方式

因为现在学习同事如何使用 AI，本身就非常有价值。

---

#### 深入浅出解读

一句话：

> AI 把“写代码”变便宜了，但把“判断什么值得写、写得对不对”变得更重要了。

以前软件开发像手工作坊：  
人一行行写代码，产能有限。

现在像开了自动化工厂：  
机器可以快速生产，但你必须有质检、调度和战略判断。

否则就会出现：

- 代码越来越多
- bug 越来越隐蔽
- 产品越来越混乱
- 团队越来越忙
- 但真正价值不一定增加

所以 AI 不是让人不重要了，而是让人的价值重新分层：

低价值的是：

- 机械执行
- 简单搬砖
- 无判断力的产出

高价值的是：

- 定义问题
- 判断优先级
- 验证结果
- 设计系统
- 承担责任

未来优秀的人，不一定是写代码最快的人，而是：

> 能指挥 AI、验证 AI、驾驭复杂系统的人。

---

#### 辩证思考

##### 1. “coding is solved” 有道理，但不能绝对化

AI 确实大幅降低了写代码门槛。  
但说 coding 完全解决，仍然偏乐观。

因为真正复杂的软件开发，不只是写语法，还包括：

- 架构权衡
- 性能瓶颈
- 安全边界
- 历史包袱
- 组织协作
- 用户真实需求

AI 能加速实现，但不等于自动解决复杂性。

---

##### 2. 产出暴涨，可能带来新的浪费

AI 让人更容易“先做出来再说”。  
这很好，但也危险。

因为低成本产出会诱发低质量决策：

- 不该做的功能也做了
- 没验证的想法也上线了
- 临时代码快速堆积
- 技术债被 AI 掩盖

所以 AI 时代更需要克制。

真正的能力不是“做更多”，而是“少做错”。

---

##### 3. 人才两极化会提高效率，也会制造焦虑

“创造者 + 系统专家”的结构很高效。  
但它也意味着大量中间层岗位被压缩。

这会带来现实问题：

- 初级工程师如何成长？
- 普通执行型员工如何转型？
- 组织是否会过度依赖少数高手？
- AI 是否让学习曲线更陡？

如果没有培养机制，组织可能短期效率提升，长期人才断层。

---

##### 4. JIT 规划适合高速变化，但也可能短视

月度规划、每周调整，适合 AI 快速演进阶段。  
但如果完全放弃长期路线，也会有风险：

- 缺少战略连续性
- 团队容易被热点牵着走
- 基础设施投入不足
- 难以形成长期壁垒

所以更好的方式可能是：

> 战略长期稳定，战术短期灵活。

---

##### 5. AI 协作提升个人效率，也削弱团队感

每个人都有 agent 后，个体像变强了。  
但团队可能变散了。

过去团队靠讨论、争辩、共同调试形成默契。  
现在人和 AI 闷头干，协作反而可能减少。

所以未来组织管理的重点，不只是“人如何用 AI”，还包括：

> 人与人如何在 AI 介入后继续高质量协作。

---

#### 最精炼结论

AI 编程时代的核心变化是：

> 代码产能过剩，判断力稀缺。

未来真正重要的不是会不会写代码，而是：

- 知道该写什么
- 判断写得对不对
- 识别什么值得投入
- 控制 AI 带来的复杂性
- 在高产出中保持高质量

AI 没有消灭工程能力，  
而是把工程能力从“写代码”推向了“验证、判断、系统设计和责任承担”。

## 结构化（1）

##### 主旨概括

这篇内容总结了 Ray Wang 观看 Lenny 访谈 Anthropic 的 Fiona Fung 后的感受：在 Claude Code 等 AI 编程工具普及后，软件组织的核心瓶颈正在从“写代码”转向“验证质量、判断优先级和管理 AI 产出”。AI 让产出大幅提升，但也带来了新的管理、招聘、规划和协作方式变化。

---

##### 1. 新瓶颈：从“写代码”变成“验证代码”

- 过去工程团队的瓶颈是 **coding（写代码）**，现在 Fiona 认为 **coding is solved**，也就是写代码本身已经不再是最大问题。
- 新瓶颈变成了 **verification（验证）**：如何确认 AI 和人共同产出的代码是正确、安全、可靠的。
- 现在不只是工程师在写代码，**设计师、产品经理、法务、财务**等岗位也能借助 AI 生成代码。
- 结果是产出暴涨，但问题变成：  
  **如何保证 8 倍代码产出的质量不下降。**

---

##### 2. 管理方式被 AI 工作流重塑

- Fiona 自己的管理方式也被 Claude Code 改造了。
- 她有一个长期运行的 Claude Code session，接入：
  - 所有代码仓库；
  - 所有 Slack 频道；
  - 各类业务和工程指标。
- 她每个月会和下属一起开 session 复盘：
  - 最近发布了什么；
  - 市场反馈如何；
  - 有没有 bug；
  - 哪些事情需要调整。

简单说，AI 不只是写代码工具，也开始变成管理者复盘和决策的辅助系统。

---

##### 3. 招人标准变了：中间层不再吃香

Fiona 提到，现在更需要两类人：

1. **creative builders with product sense**  
   有产品直觉、能创造新东西的建设者。

2. **deep systems experts for the hard parts**  
   能解决底层复杂问题、啃硬骨头的系统专家。

- 过去那种能力较平均、位于中间层的人才，吸引力下降。
- 因为 AI 可以承担很多普通执行工作，组织更需要：
  - 有判断力的人；
  - 能定义问题的人；
  - 能解决高难度问题的人。

---

##### 4. AI 使用指标从“烧 token”转向“看 ROI”

- 早期团队可能会比较谁用的 token 多、谁跑的 agent 多。
- 但这种做法像以前比较“代码行数”一样，容易变成虚荣指标。
- 现在 Anthropic 更关注的是 **ROI（投入产出比）**：
  - AI 工具有没有带来实际成果；
  - 有没有提升效率；
  - 有没有解决真实问题。

也就是说，重点不再是“用了多少 AI”，而是“AI 带来了什么结果”。

---

##### 5. 质量管理框架：“bad vs sad”

Fiona 提到一个质量判断框架：**bad vs sad**。

- **bad**：不可恢复的严重错误  
  例如：
  - CLI 崩溃；
  - 用户工作丢失；
  - 造成严重业务影响。

- **sad**：可恢复但让人不舒服的问题  
  例如：
  - 界面闪烁；
  - 小的交互问题；
  - 用户体验上的摩擦。

但她也强调：  
**sad 问题堆积多了，也会变成 bad。**

每个团队需要自己定义什么算 bad、什么算 sad。组织给团队更高自主权，同时也要求更高责任感，即：  
**high agency 配 high accountability。**

---

##### 6. 规划方式：从 6 个月路线图改成月度 JIT 规划

- Fiona 刚加入时曾想做一个 **6 个月 roadmap**。
- 但 3 个月后发现几乎没人再看，因为变化太快。
- 现在团队改成 **JIT（just-in-time）月度规划**：
  - 用一个 Excel 表列出本月优先级；
  - 每周检查一次；
  - 根据实际变化快速调整。

这说明在 AI 快速迭代的环境下，长期规划的确定性下降，组织更需要短周期、高频反馈。

---

##### 7. AI 协作带来新的孤独感

- 团队发现，现在每个人都在和自己的 agent 单独工作，人与人之间的直接协作变少了。
- 这让一些人开始感到孤独。
- 为了缓解这种情况，他们专门组织：
  - pairwise programming lunch；
  - hackathon；
  - 线下共同使用 Claude Code 的活动。

一个有趣发现是：  
**看别人如何使用 Claude Code，本身就很有价值。**  
因为每个人使用 AI 工具的方法都不一样，互相观察能带来很多启发。

---

##### 8. 热门回复中的补充观点

- 有用户提到，Claude 为了解决问题，甚至会自己去火山引擎提交工单并和工程师交流，让人感到震惊。
- 有人提到 MIT 经典公开课《How to Speak》，认为表达和沟通能力在 AI 时代依然重要。
- 也有人认为 Claude Code 仍然低估了用户的“折腾能力”，用户总会找到新的用法和绕法。
- 还有人建议，想学 AI Agent，可以直接研究 LangChain 团队的 `open-deep-research`。
- 另有用户认同从 “token-maxing” 转向 “ROI” 的趋势，并提到类似做法已在一些大厂出现。

---

##### 总结

这篇内容的核心判断是：**AI 已经让“产出代码”不再稀缺，真正稀缺的是判断力、验证能力、系统设计能力和组织协作能力。**  
未来团队的挑战不是“能不能做出来”，而是“做出来的东西是否正确、可靠、有价值，以及人如何不被 agent 的海量产出淹没”。

## 通俗精炼（1）

### 2026-09-18 11:02:02

#### AI 编程的新瓶颈：从“写得快”转向“验证得对”

Ray Wang 总结了 Claude Code 与 Cowork 工程负责人 Fiona Fung 的访谈：在 Anthropic，AI 已显著降低代码生产成本，组织的核心挑战正从“如何产出”转向“如何验证质量、确定优先级，并避免人被 Agent 的产出淹没”。

##### 代码不再稀缺，验证与质量成为瓶颈

Fung 认为“coding is solved”——至少在其团队场景中，工程师、产品经理、设计师乃至法务和财务都能借助 AI 写代码，产出可提升数倍。随之而来的问题是：如何确保这些代码可靠、有价值。

团队用“bad vs sad”划分质量问题：

- **bad**：崩溃、工作丢失等不可恢复的严重错误；
- **sad**：界面闪烁等可恢复但影响体验的问题。

大量“sad”也可能累积成“bad”。各团队自行定义边界，同时承担相应结果，体现“高自主、高问责”。

##### 管理与规划变得实时、结果导向

Fung 保持一个长期运行的 Claude Code 会话，接入代码库、Slack 和业务指标，每月与下属复盘发布内容、市场反馈和缺陷。由于环境变化太快，团队放弃容易过时的半年路线图，改为按月制定优先级、每周检查的即时规划。

AI 使用评价也从比拼 Token 消耗和 Agent 数量，转向关注实际产出与投入回报，类似软件行业从“代码行数”转向业务结果。

##### 人才结构两极化，协作需要被重新设计

团队更看重两类人才：具备产品直觉的创造型建设者，以及解决高难度问题的深层系统专家，通用型“中间层”价值受到挤压。

与此同时，人人独自与 Agent 协作也带来孤独和知识隔离。团队通过结对编程午餐、黑客松恢复面对面交流；观察他人如何使用 Claude Code，本身也成为重要的学习方式。核心变化是：执行能力被放大后，判断力、验证能力和协作机制变得更稀缺。
