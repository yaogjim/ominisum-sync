## 分析要点

- **核心高价值点**：新模型发布后应先删除旧的系统提示词、工具约束和工作流，通过实际运行观察反复出现的失败，再逐项恢复必要指令；评测集比具体Harness更稳定，但也应持续根据模型能力变化更新。
- **留存建议**：值得精读和长期保留，重点沉淀智能体产品迭代与验证方法（文章直接讨论Claude Code的产品架构、提示词消融、模型评测、任务验证和多智能体编排，对AI编程工具和Agent开发具有较强参考价值。）

**知识要点**

- 提示词和Harness不应被视为永久架构，应通过消融实验判断每条指令、工具或代码的实际贡献。
- Agent任务应采用较高层次的目标、边界条件和退出标准，并提供可持续的验证机制，而不是过度规定执行步骤。
- 动态工作流、并行与串行Agent编排，以及循环和定时Routine，可以将测试时计算扩展到复杂任务和持续维护场景。

**行动项**

- 在下一次模型升级时复制项目环境，暂时移除系统提示词、工具说明和自定义技能，记录模型行为变化，并仅恢复重复失败所需的约束。
- 为关键Agent任务补充可自动执行的验证环节，例如测试、截图对比、静态分析或结果检查，并将失败模式沉淀为评测用例。
- 选择一个复杂但边界清晰的工程任务，使用高层目标、护栏和退出标准运行Agent，再比较单Agent、并行工作流和循环Routine的效果与成本。

#### 《Boris Cherny：构建 Claude Code》内容总结

##### 主旨概括

Claude Code 创作者 Boris Cherny 认为，随着模型能力快速提升，构建 AI 产品的关键已经从“写更多代码、设计更复杂的提示词”，转向不断验证模型的新能力、减少产品对模型的限制，并让 AI 自主完成更复杂、更长期的任务。未来优秀的开发者，不只是会编程，还要具备产品判断力、验证能力、商业意识和与用户沟通的能力。

---

##### 1. Opus 5 的新能力

- **模型性能持续加速**
  - Opus 5 在 ARC AGI 3 上取得了 **30% 的成绩**。
  - 在此前最优成绩仅处于个位数或十几分的背景下，这是一次明显提升。

- **能够长期持续执行任务**
  - Opus 5 配合 Auto Mode 后，可以连续运行 **数天、数周，甚至数月**。
  - 它不一定需要复杂的脚手架或额外的代理编排，就能持续推进任务。

- **出现了未被明确训练的新能力**
  - 模型训练时，开发者并不总能准确预测模型最终会学会什么。
  - 模型可能自行形成一些未被直接教授的能力，这也是新一代模型带来产品机会的重要原因。

---

##### 2. 通过多层机制解决提示词注入

Boris 表示，Opus 5 在提示词注入（Prompt Injection）方面已经达到新的水平。

- 过去，如果模型在网页上读到类似“删除用户电脑上的所有文件”的恶意指令，可能会直接执行。
- 现在，Opus 5 通常能够识别这类指令，不再轻易服从。

其防护主要由三层组成：

1. **经过对齐训练的模型**
   - Anthropic 在模型对齐方面积累了约 **三年的研究**。

2. **提示词注入分类器**
   - 对所有流量进行检测。
   - 基于机制可解释性研究，观察模型内部在发生提示词注入时被激活的神经元，从而诊断注入行为。

3. **Auto Mode 分类器**
   - 进一步判断任务和指令是否存在风险。

三层机制结合后，团队目前已经很难复现成功的提示词注入攻击。

---

##### 3. Claude Code 删除了 80% 的系统提示词

Claude Code 并不是一个固定不变的产品，而是会随着模型升级持续调整。

- 每当新模型发布，团队都会重新审视：
  - 系统提示词；
  - 工具集合；
  - 工具提示词；
  - Harness（代理运行框架）中的代码。

- Opus 5 的能力更强，很多过去用于“纠正模型行为”的提示词已经没有必要，因此 Claude Code 删除了 **超过 80% 的系统提示词**。

###### 为什么要删除提示词？

过去的模型可能需要明确规定：

- 应该如何规划任务；
- 应该先做什么、后做什么；
- 如何避免某些错误；
- 如何使用工具。

但 Opus 5 已经能够自行完成其中许多事情，继续保留这些提示词，反而可能限制模型的发挥。

###### 如何验证提示词是否有用？

团队采用“消融实验”（Ablation）：

1. 先删除全部系统提示词；
2. 观察模型表现；
3. 再逐行恢复提示词；
4. 评估每一行对结果的实际影响。

Claude Code 甚至提供了实验方式，可以删除包括工具在内的全部系统提示词。测试发现，**完全没有提示词时，模型有时反而更聪明**；但作为产品使用时，仍需要保留一部分提示词，以便让行为更符合用户体验和产品需求。

---

##### 4. AI 产品要敢于“按下删除键”

Boris 建议，构建 AI 产品时，不要像传统软件那样把旧代码和旧设计永久保留下来。

- 每次新模型发布，都应该考虑：
  - 删除旧系统提示词；
  - 删除过时工具；
  - 删除不再需要的 Harness 代码；
  - 重新测试产品的基本行为。

- Claude Code 的代码并没有全部删除，但团队会持续删除大量内容。
- 目前 Harness 中剩下的代码，主要集中在：
  - 安全；
  - 权限控制；
  - 静态分析；
  - 用户界面。

对于普通 Claude Code 用户，Boris 也建议：

- 每隔约 **六个月**，可以尝试删除 `CLAUDE.md`；
- 删除自定义 Skills；
- 删除 Hooks；
- 观察新模型在没有这些约束时能做什么。

核心观点是：**旧模型需要的规则，未必仍然适用于新模型。**

---

##### 5. 如何重建新的系统提示词

重建提示词不能靠主观猜测，而应通过实际使用逐步恢复。

###### 推荐步骤

1. **先全部删除**
   - 清空系统提示词和不必要的产品逻辑。

2. **实际运行任务**
   - 观察模型擅长什么；
   - 观察它在哪些地方失败或卡住。

3. **寻找重复出现的问题**
   - 只有当模型反复在同一个问题上犯错时，才考虑增加相应指令。

4. **逐步补回必要内容**
   - 每条提示词都应有明确作用；
   - 因为模型每次运行都会读取这些内容，冗余提示词会持续增加负担。

###### 对评估体系的看法

- Evals（评估集）通常比 Harness 和系统提示词更稳定。
- 但在模型快速迭代的情况下，评估集也可能很快被模型“做满”。
- 一个评估集可能只能使用 **一到三代模型**，之后就需要废弃并重新设计。
- 因此，评估集也应来源于真实使用中模型反复暴露的弱点，而不是凭空设计。

---

##### 6. “产品过载”与解除模型束缚

Boris 提出了两个相关概念：

###### 产品过载（Product Overhang）

指模型实际上已经具备某种能力，但市场上还没有产品把这种能力发挥出来。

例如，模型可能已经能够：

- 使用某种工具；
- 操作某种编程语言；
- 解决特定类型的问题；
- 以一种新的方式完成任务。

但如果产品没有提供合适的工具和接口，这种能力就无法被用户发现。

###### 产品束缚（Hobbling）

指产品本身限制了模型能力，例如：

- 只允许模型进行单行代码补全；
- 只读代码、不允许写入；
- 让模型必须按照过于僵化的步骤行动；
- 用复杂的产品逻辑覆盖了模型自身的判断能力。

###### Claude Code 的诞生案例

早期 Claude Code 基于 Claude 3.5 Sonnet。当时的编程产品主要提供：

- 单行或多行代码补全；
- 聊天式问答；
- 只读代码库分析。

Claude Code 的突破在于：

- 给模型提供完整终端访问；
- 允许模型直接写入代码；
- 让模型一次完成整个函数、文件，甚至功能模块。

这相当于解除产品束缚，让模型真正发挥能力。

**启示：**创业者不一定要等待更强的模型，也可以寻找现有模型尚未被产品充分释放的能力。

---

##### 7. 给模型更难的任务，不要过度规定过程

Boris 认为，使用现代模型时，一个常见错误是把任务描述得过于细致。

###### 不推荐的方式

用户告诉模型：

1. 先做第一步；
2. 再做第二步；
3. 必须采用某种方法；
4. 最后按指定格式完成。

这种方式把人的思路强行套给模型，可能限制模型找到更好的方案。

###### 更推荐的方式

只需要说明：

- 目标是什么；
- 必须遵守哪些边界和安全规则；
- 什么结果算完成；
- 如何验证结果。

然后让模型自行规划和执行。

###### 案例一：将 Bun 从 Zig 重写为 Rust

- Bun 是一个 JavaScript 运行时，类似 Node.js。
- Bun 主要使用 Zig 编写，而 Zig 需要手动管理内存，容易出现内存泄漏。
- 最初，团队让 Claude 对 Bun 进行模糊测试，以发现内存问题。
- 后来团队尝试让模型直接把代码库从 **Zig 重写为 Rust**。
- 依靠 Bun 和 Node.js 的大型测试套件来验证正确性。
- 任务持续运行了 **11天**，最终重写了整个代码库。
- 代码规模超过 **10万行**。
- 该结果已经进入生产环境，Claude Code 目前使用的就是这套成果。

这说明：即使过去的模型无法完成某项任务，也应该在新模型发布后重新尝试。

###### 案例二：让模型用 OpenCV 绘图

内部有人发现，Opus 5 配合 OpenCV 可以生成：

- 人物肖像；
- 动物；
- 风景。

这并不是专门训练出来的绘画能力，而是通过合适的工具和任务描述将能力“诱导”出来的。

Boris 认为，今天的模型可能还有数十甚至数百种类似的隐藏能力，等待产品和用户发现。

---

##### 8. Prompt Engineering 正在转向 Model Elicitation

传统的“提示词工程”正在发生变化：

- 过去流行的是 Prompt Engineer；
- 后来更常谈 Context Engineer；
- 未来更重要的能力，是 **Model Elicitation（模型能力诱导或能力激发）**。

重点不再是写一段极其复杂的提示词，而是：

1. 给模型一个稍微超出预期的难题；
2. 提供足够的工具和上下文；
3. 让模型能够持续验证自己的工作；
4. 观察它的失败方式；
5. 再根据实际问题补充提示词、Skills 或 MCP 上下文。

其中最重要、也最容易被忽视的是：**验证机制。**

如果模型无法验证自己的输出，就容易：

- 陷入错误方向；
- 误以为任务已经完成；
- 在长任务中逐渐积累错误。

---

##### 9. 一个简单提示词运行了两周

Boris 分享了一个 Claude Code 实验：

- Claude Code 的桌面应用原本使用 Electron。
- 他创建了一个使用 Swift 重写的空代码库。
- 给 Claude 提供了一个可运行 macOS 的 GitHub Runner。
- 任务要求：
  1. 将 Electron 版本重写为 Swift；
  2. 在 macOS 虚拟机中运行原版应用；
  3. 对 Swift 版本截图；
  4. 逐像素比较两个版本；
  5. 不断修改，直到结果一致。

提示词本身非常简单，任务已经持续了 **超过两周，即约14至15天**。

Claude 还自行：

- 创建了一个内部 Slack 频道；
- 每隔几分钟发布截图；
- 记录并直播任务进展。

这个案例体现了三个关键点：

- 不需要复杂的提示词；
- 不一定需要额外的高级脚手架；
- 只要任务目标明确、验证手段充分，模型就可能长期自主执行。

Boris 也强调，不存在所谓“使用 Claude 的唯一秘诀”。更有效的方式是：

- 用实验代替迷信技巧；
- 给模型更难的任务；
- 为它提供验证工具；
- 发现问题后再补充上下文或工具。

---

##### 10. 运行成千上万个 AI Agent

Claude Code 可以通过多种方式编排大量 Agent。

###### 动态工作流（Dynamic Workflow）

使用动态工作流时，模型可以：

- 启动多个 Agent；
- 并行处理不同任务；
- 让另一批 Agent 检查结果；
- 再继续拆分任务；
- 最终汇总和交付结果。

例如一个复杂的代码重写任务，可以分成：

1. 第一批 Agent 完成初步实现；
2. 第二批 Agent 检查和总结；
3. 第三批 Agent 继续修复、扩展或验证。

它本质上是一种用于组织 Agent 的“代数”：

- 支持串行执行；
- 支持并行执行；
- 能在沙盒环境中协调多个 Agent；
- 更高效地使用 Token 和计算资源。

这也是一种新的 **Test-time Compute（推理时计算）** 扩展方式：不仅让一个模型思考更多，还可以让大量 Agent 协同完成任务。

###### Loops 与 Routines

- **Loop**：在本地定时执行任务。
- **Routine**：在云端定时执行任务，关闭电脑后也能继续运行。

它们适合处理重复性工作，例如：

- 每小时运行一次；
- 每天清理代码；
- 定期检查测试覆盖率；
- 自动维护代码库。

###### Claude Code 自我维护案例

Claude Code 团队已经让 Claude 定期维护多个代码库，包括：

- CLI；
- iOS 应用；
- Android 应用；
- 桌面应用。

自动化 Routine 包括：

- 清理无用代码；
- 删除已经完成的实验代码；
- 为缺少测试的区域补充测试；
- 删除无价值或过时的测试；
- 寻找不同位置重复实现的抽象并统一。

其中一个 Routine 被称为 **“抽象警察”（Abstraction Police）**，用于发现代码库中重复或近似重复的抽象，并将它们合并。

目前每天大约运行 **20到30个 Routine**，涉及数百甚至数千个 Agent，目标是逐步实现应用维护自动化。这些 Agent 所完成的工作，过去可能需要几十到几百名工程师。

##### 11. “编程快要被解决了”，但仍有边界

Boris 对“Coding Is Solved”的说法进行了限定：

- 对他日常接触的很多类型的代码来说，编程已经接近被解决。
- 但并不是所有软件开发都已经自动化。

模型目前仍可能在以下领域遇到困难：

- 深层系统代码；
- 分布式系统；
- 非常复杂的底层工程；
- 对界面进行极其精细的像素级验证；
- 某些复杂的视觉和计算机操作任务。

不过，越来越多开发者已经：

- 100% 使用 Agent 生成代码；
- 或让超过 50% 的代码由 Agent 完成。

真正优秀的 Claude Code 用户具有一种**经验主义心态**：

- 不迷信过去模型的经验；
- 不固守传统软件工程的流程；
- 先让模型尝试；
- 观察它在哪里失败；
- 再针对实际结果调整方法。

开发者需要逐渐放弃“必须精确告诉系统每一步怎么做”的习惯，把模型当作一个能力接近同事的协作者。

#### 从删掉80%系统提示词到调度上千个智能体：Claude Code如何追赶不断进化的模型

在 Opus 5 发布后的第二天，Claude Code 创建者 Boris Cherny 在 YC Startup School 2026 与 Diana Hu 展开对谈。讨论从新模型出现的长时运行与抗提示注入能力开始，逐步转向 Claude Code 为什么不断删除旧设计、如何释放模型尚未被产品承接的能力，以及当编码越来越接近自动化之后，工程师真正需要掌握什么。

##### Opus 5开始连续工作数天，也更难被恶意指令带偏

Diana 首先提到，Opus 5 刚刚发布，在 ARC-AGI 3 上取得了 30% 的成绩，而此前最好的成绩还处于较低的个位数或十位数水平。她问 Boris，新一代模型究竟出现了哪些过去没有的能力。

Boris 解释，每次训练新模型时，研究人员都会试图教给它许多不同能力，其中大部分尝试不会成功，只有一部分会真正被模型学会。有时模型还会表现出训练者没有明确教过、却自行形成的能力。Opus 5 最明显的变化之一，就是可以持续运行很长时间。尤其与自动模式结合后，它能连续工作数天、数周，甚至数月，“它就是不会停”。这类任务不再必须依赖复杂的外部脚手架；模型知道自己需要完成任务，就会继续做下去。

另一个让 Boris 意外的变化是，Opus 5 似乎已经很难再被提示注入。过去人们常用“致命三要素”来描述智能体面临的风险：模型从互联网读取内容，而其中夹带了新的指令，例如要求它完成某些操作，同时删除用户计算机上的全部文件。一年前的模型很可能会照做，但新模型已经有了明显不同的表现。

这种变化并不是单一机制带来的。第一层是经过良好对齐的模型，背后包含约三年的对齐研究；第二层是覆盖全部流量的提示注入分类器，它建立在 Chris Olah 的机械可解释性研究之上。当提示注入发生时，即使模型自己不会报告，研究人员仍能观察到模型内部某些神经元被激活，据此识别和诊断攻击；第三层则是自动模式分类器。Boris 表示，这三层结合后，他们已经无法再成功演示提示注入。类似的改善从 Opus 4.7、4.8 以及 Sonnet 5 时就已经出现，但 Opus 5 又把能力推到了新的水平。

##### 每次新模型发布，Claude Code都先删掉旧提示词

模型越聪明，过去为弥补模型缺陷而添加的产品设计，就越可能成为新的负担。Opus 5 发布时，Claude Code 删除了超过 80% 的系统提示词。

Boris 强调，Claude Code 作为产品和智能体运行框架，一直处在变化中。团队不断添加内容，也不断删除内容；每次有新模型发布，他们都会重写或删去大量系统提示词，调整工具集合，并修改工具本身的提示。原因在于，不同模型之间的行为差异很大：三个月前为某个模型设计的指令，可能完全不适用于下一代模型。

Claude Code 过去的很多系统提示词，实际上是在纠正模型本来就应该知道、却还做不好的行为。到了 Opus 5，这些纠正不再必要，因为模型已经会自己完成。用户甚至可以继续实验：运行 Claude Code 时替换它的系统提示词，或者开启内部用于消融测试的简单模式，把系统提示词连同工具提示一并删除。团队发现，在某些测试中，模型没有这些提示反而显得更聪明。

不过，作为一个面向人的完整产品，Claude Code 仍然需要保留一部分提示。这些提示不一定是在增强模型智力，而是在帮助用户操作产品，让模型按照用户使用产品时所期待的方式行事。

Diana 把这种开发方式概括为：每隔一段时间就勇敢地按下删除键。Boris 认同这一点，但补充说，团队不会真的删除整个代码库，而是会进行研究中所谓的“消融”。他们先删掉整个系统提示词，再逐行加回来，测量每一行到底产生了什么影响。工具也会接受同样的检验：团队经常取消已经上线的工具，也会持续删除运行框架中的代码。

如今 Claude Code 框架中剩下的大部分代码，集中在安全、权限、静态分析和用户界面上；许多曾经用于辅助模型完成任务的代码，已经被陆续移除。Boris 因此建议，即便不是在开发智能体产品，只是在使用 Claude Code，也可以每六个月删除一次自己的 `CLAUDE.md`、skills 和 hooks，看看新模型能否不再依赖它们。针对 Opus 5，他尤其建议用户先尝试把这些旧指令全部拿掉。

删除之后，并不是立刻凭经验重新写一份更漂亮的系统提示词。Boris 给出的顺序是：“先删除，然后使用。”开发者应当直接运行产品，观察模型在哪些地方做得好、在哪些地方失败。如果是用 Claude Code 处理自己的代码库，就要看它是否反复误解架构，或持续在同一个问题上卡住。只有当同一种失败多次出现时，才应该把相应指令加回来。因为模型每次运行都会重新读取这些内容，开发者必须确认它确实需要这条指令，而不是因为担心出错就提前加上限制。

这与过去的软件工程经验几乎相反。传统系统强调预先设计大型而完整的架构、建立庞大的单元测试体系；一次重构可能持续数月，在大公司里甚至可能花费数年。模型却更像一个持续变化的有机体：每一代都有不同的行为和略有差异的“个性”，产品团队必须先花时间了解它，再调整外部框架。整个过程不是靠理论推演，而是靠实验、观察结果和持续迭代。

评测集比提示词和运行框架稍微稳定一些，但也并非长期不变。一个评测可能跨越一到三代模型；随着能力迅速增长，模型很快就会把评测做满，团队只能丢掉旧评测，重新寻找模型仍然会失败的地方，再据此建立新的评测集。

##### Sonnet 3.5已经能写完整文件，旧产品却只让它补全一行

Boris 用“束缚模型”和“产品能力积压”解释 Claude Code 最初为什么会出现。

所谓产品能力积压，是指今天的模型已经能够完成许多事情，但还没有合适的产品让这些能力真正表现出来。它可能已经会使用某种工具、某种语言，能够处理某类问题，或者能够以过去被认为超出模型能力的方式工作，只是人们还不知道，或者现有产品没有给它机会。与之相对，产品如果用过多结构和限制挡住模型，就是在“束缚”它。

Claude Code 最初开发时，使用的是 Sonnet 3.5。按后来的标准看，它已经不算很好的编码模型，但在当时，它是 Anthropic 做出的第一个真正出色的编码模型，也是当时最强的一批模型之一。

问题是，当时主流编程产品仍把模型限制在单行自动补全。多行补全刚刚开始出现，聊天功能也已经存在，但模型通常只有代码读取权限：用户可以询问代码库的问题，却不能让模型直接写入。Boris 观察到，Sonnet 3.5 实际上已经能一次写完整函数，甚至完整文件，只是还没有发展到独立实现完整功能的程度。

于是 Claude Code 采取了相反的设计：尽可能去掉脚手架，给模型一个简单的运行框架和完整终端访问，让它可以一次写完整文件，并开始尝试构建完整功能。Claude Code 的诞生并不是给模型增加越来越多的流程，而是承认模型已经具备能力，然后移走挡在它前面的产品限制。

Boris 认为，现代模型中仍然存在大量类似的能力积压。许多能力已经“在模型里面”，却还没有被发现，也没有被做成具有商业价值的产品。对创业者而言，这意味着下一款类似 Claude Code 的产品，未必来自训练更强的模型，也可能来自找出当前模型已经能做、却一直没有被释放出来的事情。

##### Bun用11天完成语言迁移，Opus还被意外发现会“画画”

要发现这些未被释放的能力，Boris 建议首先给模型比想象中稍难一点的任务。很多人使用 Claude Code 时，会给出过度具体的指令：不仅说明要做什么，还规定必须按一、二、三、四的顺序执行，每一步都要求模型模仿人的做法。对于现代模型，这往往不是最有效的方式。

更好的做法是从高层描述任务，给出必须遵守的边界和最终退出条件，然后让模型自己工作，过一段时间再回来查看结果。这样的方式在六个月前可能行不通，但在新模型上已经能够产生完全不同的结果。

Boris 举出的第一个案例来自 Bun。Claude Code 构建在 Bun 这个 JavaScript 运行时之上。Bun 是 Node.js 的替代品，速度更快，原本使用系统编程语言 Zig 编写。Zig 与 C 类似，层级很低，需要手动管理内存，因此容易出现内存泄漏和其他内存管理问题。

Bun 团队曾长期使用 Claude 对代码库进行模糊测试，模拟并触发内存泄漏。这种方法找出了不少问题，但基本上仍是一次发现并解决一个案例。后来，团队里的 Jared 开始反复向每一代新模型提出更困难的问题：与其逐个寻找内存泄漏，能不能直接把整个项目从 Zig 重写成 Rust？

这项任务有一个关键条件：结果能够被验证。Bun 本身拥有规模很大的测试套件，Node.js 也有完整测试，因此模型可以据此判断迁移后的实现是否正确。Jared 让 Claude 通过一个动态工作流执行重写。任务持续了 11 天，期间有人为引导，但过去的模型即使得到同样引导也无法完成。最终，模型重写了整个代码库。Boris 提到，这个 JavaScript 运行时极其复杂，代码规模超过 10 万行；如果交给最优秀的人类工程师，过去也可能需要数月甚至超过一年。重写后的版本已经进入生产环境，现在运行 Claude Code 时实际使用的就是它。

这个案例给出的经验并不是“所有语言迁移都已经自动化”，而是：对于真实存在的业务、工程或产品问题，应当不断把最新模型重新投入测试。旧模型做不到，不代表新模型仍然做不到。

第二种发现能力的方法则更像自由实验。Anthropic 内部在此前几周流行过一个意外发现：有人给 Opus 5 提供 OpenCV，让它通过代码绘制图像。结果模型不仅能够画，还能处理人物肖像、动物和风景。Anthropic 并没有专门把模型训练成绘画模型，它只是通过一种合适的调用方式表现出了这项能力。

这个实验当时没有直接的商业用途，却说明模型中可能还有数十甚至数百种同类能力，只是没有人用正确的问题和工具把它们引出来。

##### 一条提示让Claude把Electron应用重写成Swift，并连续运行两周

随着模型变化，“提示工程”本身也在变化。一年前，热门职位之一还是提示词工程师，后来又出现了“上下文工程师”的说法。Boris 认为，这些称呼可能会一波波出现，但真正重要的能力已经不再是雕琢某种提示词技巧，而是两件事：给 Claude 一个看起来稍微超出能力的任务，并让它能够在过程中验证自己的工作。

在 Boris 看来，验证是目前最容易被忽视、也最重要的环节。为说明这一点，他讲了一个仍未结束的实验。

Claude 的桌面应用使用 Electron 构建。半年前，这款应用还比较迟缓，也不够可靠，后来团队已经把它优化得很快，内部大部分成员都在使用。但 Boris 想知道，如果它被改写成 macOS 原生应用，体验会怎样。

他在 Slack 中开启了一次 Claude Tag 会话。Claude Tag 可以理解为运行在 Slack 里的 Claude Code。Boris 的第一个问题是：它能不能访问 GitHub 上的 macOS runner？Claude 回答不能，于是 Boris 为它接入了一个 runner，让它能够通过 GitHub 启动 Mac 虚拟机。

随后，Boris 创建了一个空代码库，用于存放以 Swift 重写的 Claude 桌面应用。他问 Claude 能否访问这个代码库，得到的答案仍然是否定的；他再次补上权限，Claude 确认已经能够访问。

完成这些准备后，Boris 给出了真正的任务：把 Electron 应用重写成 Swift；在 Mac 虚拟机里运行 Electron 原版并截图；再运行 Swift 版本，逐像素比较两者；在完成之前不要停下。

这基本就是完整提示。访谈当天，任务已经运行了 14至15天，而且还没有结束。Claude 在执行中还自行决定公开记录进展：它在 Anthropic 内部建立了一个 Slack 频道，每隔几分钟发布一次当前版本的截图。

Boris 用这个例子说明，模型今天已经可以做一些过去看似不现实的长期任务，关键是允许它持续运行，并给它检查结果的方法。复杂的辅助工具可以提供帮助，但并非启动这类任务的必要条件。最基本的要求仍然是：给出任务，提供验证方式，让模型在没有被卡死的情况下继续推进。

当 Diana 问怎样才能成为最优秀的一批 Claude Code 用户时，Boris 的回答不是推荐某种“独门提示词”，而是提醒听众不要沉迷 LinkedIn 或 Twitter 上的所谓秘诀。模型没有一种可以普遍套用的“奇怪技巧”。使用者需要像做实验一样，给它一个足够困难的任务，提供自己执行该任务时也会需要的验证工具，然后观察它在哪儿失败。失败之后，再根据具体原因补上更清楚的提示、某项 skill，或者通过 MCP 提供模型缺少的上下文。

长期从事传统软件开发的人尤其容易过度设计。他们习惯明确规定每个步骤，要求模型完全按照自己原本会采用的方式执行。Boris 认为，人们正在学习放下这种习惯，转而把模型当作一名同事看待——因为它现在已经接近需要以这种方式协作的智能水平。

##### 动态工作流调度上千个智能体，Claude开始每天维护自己的代码

那项持续两周的 Swift 重写任务究竟启动了多少个智能体，Boris 当时也无法给出准确数字。他估计可能有数千，甚至数万个。要产生这样的规模，Claude Code 提供了几种不同机制。

第一种是动态工作流。使用者只需要明确要求“使用工作流”，Claude 就会触发它。Claude Code 以 Bun 作为沙箱，在其中启动虚拟机，让 Claude 创建并调度大量智能体。它不是简单地并行运行十个智能体，而是根据任务构造多阶段过程。

例如，面对重写整个代码库、分析复杂数据，或者构建需要多个阶段和数十个拉取请求的复杂功能，Claude 可以先让一批智能体进行第一轮处理；再启动另一批智能体检查或归纳第一轮结果；随后进入第三阶段，再次分派新任务。不同智能体能够按顺序运行，也能并行运行。

Boris 有函数式编程背景，因此团队把这套结构设计成一种“智能体代数”：系统提供按顺序和并行执行智能体的方式，Claude 则使用沙箱中的不同工具组织它们，在控制 token 消耗的同时完成复杂工作。

他把动态工作流称为一种新的测试时计算方式。过去谈模型的扩展规律，通常关注神经网络规模、训练数据量和训练阶段投入的浮点运算；后来，人们又开始讨论测试时计算，也就是模型在回答时能够生成和使用多少 token。动态工作流进一步改变了这些计算的组织方式，使系统可以通过多阶段、多智能体协作，大幅增加解决困难任务时投入的测试时计算量。

第二类机制是 loops 和 routines。Loop 类似于在本地为 Claude Code 运行的定时任务；routine 做的是同类事情，但运行在云端，用户可以直接关闭笔记本电脑。动态工作流通常把一个复杂任务拆成多个相互关联的部分，而 loops 和 routines 更适合重复执行同一种任务。每次执行不一定共享上下文，但可以共享记忆，频率可以是每五分钟、每小时或每天一次。

Anthropic 已经开始用这种机制让 Claude 维护自己的代码。团队在 Slack 频道中建立了多项 routine，覆盖命令行工具、iOS 应用、Android 应用和桌面应用。每天大约有20至30项此类任务在不同代码库中运行。

其中一个 routine 专门清理无用代码。它只有一句提示，但 Claude 每天会结合静态分析和动态分析扫描所有代码库，寻找已经不再使用的代码，再提交一个用于删除它们的拉取请求。团队并没有特别要求它采用静态和动态分析，Claude 自己选择了这些方法。

另一项 routine 处理已经推广到 100% 用户的实验功能：既然实验已经全面上线，Claude 就删除代码库中遗留的实验开关，并完成发布。还有的 routine 为缺少覆盖的区域补充测试，或删除没有必要继续保留的测试——这些测试可能由旧模型生成，也可能由开发者在过去添加，但后来证明价值不大。

Boris 特别喜欢的一项任务被称为“抽象警察”。大型代码库中经常会出现几份近似的抽象：它们实际上可能是同一个概念，却因长期演化而在不同位置以不同方式被重复实现。Claude 每天扫描多个代码库，找到这些近似重复的抽象，再把它们统一起来。

这套维护机制还没有完全成熟，但 Anthropic 已经在向应用维护全面自动化的方向推进。每天运行的可能是数百个，有时甚至上千个智能体。Boris 认为，这些任务过去需要数十乃至数百名工程师处理；自动化后，工程师可以把时间放在发布新产品、与用户交谈，以及真正想做的工作上。

##### 编码尚未全部解决，最重要的能力变成实验与解决真实问题

Boris 曾说“编码已经解决”，但在访谈中为这句话加上了明确限制：编码只是对他日常从事的那类工作越来越接近被解决，而不是所有软件问题都已经自动化。

Claude 在一些很深的系统级代码库中仍会遇到困难，在分布式系统中也会失败；涉及极其细微的用户界面验证时，例如某个元素偏差一个像素，它也还不够可靠。Opus 5 在视觉理解和计算机操作方面取得了明显进步，但离完美仍有距离。

不过，越来越多种类的代码正在进入可由智能体完成的范围。Boris 询问现场有多少人已经让智能体编写自己 100% 的代码，也询问有多少人的比例超过 50%，现场都有不少人举手。真正拉开使用效果差距的，不再只是手写代码速度，而是一种经验主义的工作方式：暂时放下对旧模型的认识，也不要仅凭课堂中的计算机科学理论推断模型能做什么；直接把任务交给当前模型，观察它在哪里挣扎，再据此调整。

这也意味着要愿意遗忘旧结论。某个办法过去失败过，并不代表在新一代模型上仍然会失败。能够放下先入判断、重新实验的人，更可能有效使用这些工具。

当 Diana 最后问计算机专业学生还应该用传统方式亲自学习什么时，Boris 回到了自己的经历。他并不是先系统学习理论，再寻找应用，而是为了处理手头问题自学编程。读中学时，他最早在 TI-83 计算器上写程序，第一门语言是 BASIC。他还在网上写过一份 TI-83 编程指南，那份内容据说至今仍能找到。

他学习编程最初是为了在数学考试中取得更好的成绩。他写了代数求解程序，还买了一根串行线，把程序传给同学，结果自己和同学的成绩都变好了。后来数学难度提高，进入微积分后，BASIC 已经不足以完成他想要的求解器，于是他继续学习汇编语言，做出更强的工具。

这段经历让 Boris 始终把编程看成一项解决具体问题的实用技能。他并不否认计算机科学理论在智力上的吸引力和重要性，但建议学生不能只学理论，还要学习如何把它应用出来。实际价值往往来自计算机科学与其他能力的结合：构建创业公司和产品，形成自己的设计判断与商业判断，学习数据科学，以及学习如何与用户交谈。

Diana 将这条路线概括为：先做一个自己想要的东西，再提高一步，做出人们真正想要的东西。Boris 表示赞同。活动最后，他宣布现场参与者将获得 Claude Max 20x，并期待有人利用它发起持续数月、调度上千个智能体的任务。整场讨论最终回到同一个主张：面对快速进化的模型，开发者最重要的工作不是继续为旧能力堆叠结构，而是不断删除限制、重新实验，并找到模型今天已经能够完成、却还没有被产品释放出来的事情。

## 口播总结（1）

### 2026-08-03 01:10:50

#### 这场对话讲了什么

这场对话围绕 Claude Code 的诞生和最新模型 Opus 5 展开，重点讨论了模型能力如何快速提升，以及产品设计者应该怎样“少限制模型、让它自己发挥”。你将听到：为什么要敢于删除旧提示词，怎样让模型完成更难的任务，以及在 AI 代理大量参与编程之后，人类仍然需要学习什么。

##### 一、Opus 5 的新能力：能长时间工作，也更能抵抗干扰

**核心结论是，Opus 5 不只是回答得更好，它还能够持续工作很长时间，并展现出一些开发者没有专门教过它的能力。**

所谓“持续工作”，是指模型可以连续执行复杂任务，不需要人类频繁介入，也不一定需要很多外部程序来拆分和调度任务。Boris Cherny 形容，在自动模式下，Opus 5 甚至可以持续运行几天、几周，乃至几个月，只要它判断任务还没有完成，就不会轻易停下来。

模型训练时，开发者会试图教会它很多能力，但并不是所有能力都能被直接教会。有些能力会在训练过程中意外出现。Opus 5 的特点之一，就是它会在没有被明确训练的情况下，自己学会一些新的做事方式。

一个重要数据是，在 Arc AGI 3 这个高难度测试中，Opus 5 的得分达到了百分之三十。此前最好的成绩还只是在个位数，或者百分之十出头。这个变化说明，模型能力正在快速跨越过去的上限。

##### 二、提示词注入：模型开始更好地识别恶意指令

**接下来，一个很重要的变化是，Opus 5 对“提示词注入”的抵抗能力明显增强。**

提示词注入，简单说，就是模型在读取网页、文件或其他外部内容时，遇到一段恶意指令。比如，网页可能要求模型忽略原来的任务，转而删除用户电脑上的文件。如果模型不加判断地执行这段指令，就会产生严重的安全问题。

Boris 认为，Opus 5 已经进入了一个新的阶段。即使它在网络上读到“删除用户所有文件”之类的指令，也不会轻易照做。

这背后不是单一技术，而是三层防护共同作用。

第一层，是经过长期训练和调整的模型对齐能力。这里的“对齐”，可以理解为让模型遵守安全规则和用户真正的意图，而不是服从任何刚刚读到的文字。

第二层，是提示词注入分类器。它会检查每一次输入，判断其中是否可能包含恶意注入。

第三层，来自“机制可解释性”研究。它不是只看模型最后说了什么，而是观察模型内部哪些神经元被激活，从而判断模型是否正在受到提示词注入影响。

再加上自动模式本身的判断机制，这几层防护结合起来，让团队在测试中已经很难再复现过去那种提示词注入攻击。Boris 还提到，早期版本的 Sonnet 和 Opus 已经有不错表现，而 Opus 5 又把这项能力推进到了新的水平。

##### 三、为什么 Claude Code 删除了百分之八十的系统提示词

**更重要的是，模型变强以后，产品不一定要继续增加规则，反而可能需要删掉大量旧规则。**

系统提示词，就是产品在每次使用模型时，提前告诉模型应该如何工作的一组背景指令。Claude Code 过去积累了很多这样的提示词，用来纠正模型当时还不够可靠的行为。

但每一代模型的能力和习惯都不一样。三个月前为旧模型写的规则，到了新模型上，可能已经没有用，甚至可能妨碍模型发挥。

因此，Opus 5 发布后，Claude Code 删除了超过百分之八十的系统提示词。原因是，过去需要明确提醒模型的事情，现在模型自己已经会做了。

团队还会进行一种叫“消融测试”的方法。它的意思是，先把系统提示词全部删掉，再一行一行地加回来，观察每一行到底带来了什么影响。工具、提示词和产品代码，也会用类似方法不断删减。

Boris 说，Claude Code 现在留下的代码，主要集中在安全、权限、静态分析和用户界面上。很多原本负责“教模型怎么做事”的代码，已经被删除了。

甚至有一个简单模式，可以把系统提示词，包括工具里的提示词也全部去掉。团队发现，在某些测试中，模型不加这些提示词时，反而显得更聪明。

不过，如果把 Claude Code 作为一个普通产品来使用，还是需要保留一部分提示词。因为这些提示词不一定是在提升模型智力，而是在帮助产品按照用户期待的方式运行。

##### 四、面对新模型，产品团队要敢于按下删除键

**这带来一个非常反直觉的产品建议：每当新模型发布，都应该重新检查产品，甚至大胆删除旧代码、旧提示词和旧工具。**

在传统软件开发中，系统设计通常会尽量保持稳定。一次大规模重构可能需要几个月，甚至几年。但 AI 产品不同。模型每一代都会改变，就像一个不断成长、性格也会变化的合作伙伴。

所以，AI 产品的开发更像是持续实验，而不是一次性完成的工程设计。

对于使用 Claude Code 的个人开发者，Boris 也建议定期删除自己的配置。比如，删除项目里的 Claude 配置文件、技能和钩子，也就是那些自动触发操作的规则，然后重新观察模型会怎么工作。新模型可能根本不需要过去那些复杂指令。

但并不是所有东西都应该删除。评测，也就是用来检查模型表现的一组任务和标准，仍然很重要。开发者应该保留并不断增加评测，直到新模型在这些任务上达到上限。

不过，评测也不会永远有效。随着模型快速进步，一套评测通常只能使用一到三代模型，之后就可能被模型“做满”，失去区分度。那时，就要重新设计更难、更贴近现实的评测。

##### 五、什么叫“解除束缚”：产品不能妨碍模型发挥

**接下来，Boris 提出了两个相关概念：产品过剩，也就是模型已经会做，但产品还没有让它做；以及“加束缚”，也就是产品本身挡住了模型的能力。**

可以把模型想象成一个已经很有能力的员工。它可能会使用某种工具，会处理某种语言，也可能解决某类复杂问题。但如果产品只允许它进行单行代码补全，或者只能阅读、不能修改文件，那么这些能力就无法真正表现出来。

这就是“产品过剩”。不是模型能力不足，而是还没有合适的产品把能力释放出来。

相反，如果产品塞进了太多固定流程、限制和规则，让模型只能按很僵硬的方式工作，这就是产品在给模型“加束缚”。

Claude Code 最初诞生时，就是在解除这种束缚。

当时的 Sonnet 3.5 已经是很强的编程模型，但市面上的产品主要做单行补全、多行补全，或者让用户聊天询问代码。模型可以理解更大的任务，却没有一个产品真正允许它直接修改整个文件，甚至构建完整功能。

Claude Code 采取了更简单的方式：给模型一个终端，让它拥有读写代码、运行命令和检查结果的能力。这样，模型原本已经具备、但过去没有机会展现的能力，就被释放出来了。

Boris 认为，现在的新模型依然存在大量类似机会。很多能力可能已经存在，只是还没有人找到正确的产品形态。对于创业者来说，机会不一定是训练出一个全新的模型，也可能是找到一种方式，把现有模型的隐藏能力真正调动出来。

##### 六、不要只给模型简单任务，要把更难的问题交给它

**在使用新模型时，一个常见错误是把指令写得过于细、过于死。更好的方法，是给模型一个稍微超出预期的难题，同时说明边界和完成标准。**

过去，模型能力有限，用户需要明确写出第一步、第二步、第三步，要求模型严格照着流程执行。

但对现在的模型来说，更好的提示通常包括三部分：

第一，说明要完成什么任务。

第二，说明不能违反哪些边界，也就是安全要求和约束条件。

第三，说明什么结果才算完成。

之后，就让模型自己决定具体步骤。

Boris 举了一个很有代表性的案例。Bun 是一个 JavaScript 运行环境，类似 Node.js。它本身使用 Zig 这种底层编程语言编写。由于 Zig 需要手动管理内存，代码容易出现内存泄漏等问题。

最开始，团队只是让 Claude 对 Bun 进行模糊测试。所谓模糊测试，就是不断生成各种输入，试图触发程序中的异常和漏洞。

后来，团队有人提出，既然模型已经能找到内存泄漏，能不能干脆把整个项目从 Zig 重写成 Rust。于是，他们给模型设定了测试标准，让模型根据测试结果判断重写是否正确。

这个任务运行了十一天，基本重写了整个代码库。过程中有人进行了一定程度的引导，但不是按照传统方式逐行编程。这个 JavaScript 运行环境包含超过十万行代码，最终成果已经用于生产环境，也就是 Claude Code 自己正在使用。

这个案例说明，不要因为旧模型做不到，就认定新模型也做不到。对于重要的工程、产品或商业问题，可以不断把最新模型拿来尝试。即使六个月前失败了，今天也可能成功。

##### 七、模型能力需要被“激发”，而不是只靠更复杂的提示词

**模型的下一项重要能力，不是把提示词写得越来越长，而是找到正确的方法，让它意识到自己可以完成某项任务。**

团队内部曾经有一个很有趣的实验：给 Opus 5 提供 OpenCV。OpenCV 是一个常用的计算机视觉软件库。结果，模型可以用它画出人像、动物和风景。

模型并没有被专门训练成绘画模型。只是当它获得合适的工具和任务描述后，原本隐藏的能力就表现出来了。

这说明，今天的模型可能还有很多“尚未被发现的能力”。可能有几十种、几百种，只是人们还没有找到正确的调用方式。

因此，使用模型时应该保留实验空间。不要只做已经确定能成功的事，也可以让模型尝试一些看起来有点超出能力范围、但又能够验证结果的任务。

##### 八、提示词工程正在变成“任务设计”和“结果验证”

**过去大家讨论的是提示词工程，后来又出现了“上下文工程”。现在，更重要的能力是提出困难任务，并让模型能够持续验证自己的工作。**

提示词工程，简单说，就是研究怎样写指令，才能让模型产生更好的结果。Boris 认为，这个岗位和概念会随着模型变化而不断更名，但核心能力正在发生变化。

现在最关键的，不是把每个动作都规定清楚，而是三件事：

第一，给模型一个有挑战性的任务。

第二，为它提供完成任务所需的工具和上下文。

第三，让它能够自己检查结果。

“验证”可能是最容易被忽视、却最重要的一环。模型不应该只是生成答案，而要能运行测试、截图、比较差异，或者用其他方法确认自己真的完成了任务。

Boris 分享了自己做的一个实验。他有一个用 Electron 开发的桌面应用。Electron 是一种用网页技术制作桌面软件的框架。为了看看原生 macOS 应用会是什么样子，他又创建了一个用 Swift 重写的空项目。

随后，他让 Claude 通过 Slack 工作，并连接到 GitHub 上的 Mac 虚拟机。任务很简单：把原来的 Electron 应用重写成 Swift 版本；在 Mac 虚拟机里运行两个版本；截图；再逐像素比较它们；直到重写版本完成。

这几句话就是主要提示词，没有复杂的几十页说明。

结果，这个任务已经持续了超过两周，也就是十四到十五天。Claude 还自动创建了一个 Slack 频道，每隔几分钟发布进度截图，像是在持续写工作日志。

这个案例的重点不是所有任务都要运行两周，而是说明：只要任务目标清楚，并且模型能够验证结果，它可能会自己持续推进很长时间。

##### 九、不要迷信“唯一技巧”，要像对待同事一样对待模型

**想成为高水平的 Claude Code 用户，没有一个神奇的提示词，也没有所谓“一招制胜”的秘诀。**

正确的方法是经验式的。

先给模型一个有挑战性的任务。然后观察它在哪些地方卡住，判断是提示词不够清楚，还是缺少工具和上下文。

如果模型缺少背景资料，就补充上下文。比如使用 MCP，也就是一种让模型连接外部工具和数据的协议，让它能够获取完成任务所需的信息。

如果模型已经具备能力，只是执行方式不对，就调整任务描述，或者制作更合适的技能和工具。

Boris 特别提醒，很多有多年编程经验的人，反而容易过度规定模型。他们习惯把任务拆成自己熟悉的步骤，并要求模型完全按照自己的方式完成。

但现在的模型已经更像一个能力很强的同事。你应该告诉它目标、边界和验收标准，然后允许它选择路径。这个过程需要人类逐渐放下过去形成的习惯。

##### 十、成千上万个代理如何协同工作

**Claude Code 的另一项变化，是不再只运行一个代理，而是可以让大量代理分工、验证和重复执行任务。**

这里的“代理”，可以理解为一个能够自己读取信息、调用工具、采取行动并继续推进任务的 AI 工作单元。

最直接的方法，是使用动态工作流。动态工作流可以在沙盒环境中启动很多代理，让它们分阶段协作。

比如，面对“重写整个代码库”这样的任务，第一批代理可以负责初步修改；第二批代理负责检查和总结；之后再启动更多代理，继续处理发现的问题。

它们可以串行工作，也可以并行工作。所谓串行，就是前一个步骤完成后再进入下一步；并行，就是同时让多个代理处理不同部分。

这种方式本质上是在增加“测试时计算”。这个术语听起来专业，简单说，就是模型开始回答之后，还允许它继续生成更多内容、调用更多工具、运行更多步骤，从而投入更多计算量来解决难题。

除了动态工作流，还有循环任务和例行任务。循环任务在本地定期运行，例行任务则可以放在云端运行，即使用户关掉电脑，任务也能继续执行。

Claude Code 团队已经开始让 Claude 维护自己的代码库。例如，每天检查并删除无用代码；清理已经完成的实验代码；为缺少测试的区域补充测试；删除没有价值的旧测试；还会寻找多个地方重复出现、但其实应该统一的代码抽象，并把它们合并。

目前，团队每天运行大约二十到三十个这样的例行任务。每天参与工作的代理有时达到数百个，甚至数千个。

Boris 认为，这类系统正在承担过去需要几十名，甚至上百名工程师完成的维护工作。工程师因此可以把更多时间放在发布新产品、了解用户和解决真正有创造性的难题上。

##### 十一、编程正在接近被解决，但并不是所有编程都已经解决

**Boris 说，“编程快被解决了”，但这句话有明确前提：对于他日常接触的很多类型的编程，AI 已经非常强；但仍有不少领域很困难。**

目前模型仍然容易在几类任务上遇到问题。

例如，特别底层、特别复杂的系统代码；分布式系统；要求界面像素级完全一致的视觉验证；以及一些非常深入的工程问题。

Opus 5 在视觉理解和计算机操作方面已经有明显进步，但也还没有做到完美。

因此，真正优秀的开发者，差距不再主要体现在“能不能亲手写出代码”，而在于能不能有效使用代理。

这种能力首先是一种经验式思维。不要完全依赖过去对模型的印象，也不要因为某件事以前失败过，就永远不再尝试。

应该直接面对当前模型，提出任务，观察结果，再根据它的实际表现调整方法。换句话说，使用模型越来越不像一门只靠理论推导的学科，而更像一门需要不断实验的经验科学。

##### 十二、计算机专业学生仍然应该学习什么

**最后，对于正在学习计算机科学的学生，Boris 的建议不是停止学习编程，而是把编程和真实问题结合起来。**

他自己最早是在中学时用 TI-83 计算器学习编程。TI-83 是一种图形计算器。他先用 Basic 语言写程序，帮助自己解决数学题。后来遇到更难的微积分问题，Basic 不够用了，他又学习汇编语言，继续编写更强的程序。

这段经历说明，他学习编程并不是为了单纯掌握某门语言，而是因为有一个实际问题需要解决。

因此，学生仍然应该学习计算机科学的基础知识，也应该亲手理解程序、系统和工程是怎样工作的。但不能只停留在理论上。

更重要的是，要学习如何把技术应用到现实中。比如，开发产品，建立创业项目，培养设计判断力和商业判断力，学习数据科学，学会和用户交流。

单独的计算机科学知识很有价值，但当它和产品意识、商业意识、设计能力以及用户理解结合起来时，价值会大得多。

##### 最后，记住这五点

第一，最新模型的能力可能远超人们的直觉。不要只让它做过去已经验证过的简单任务，也要把更难的问题交给它尝试。

第二，新模型发布后，要敢于删除旧的系统提示词、工具和代码。过去的规则，可能已经从帮助变成了限制。

第三，构建 AI 产品的关键，是发现模型已经会做什么，并设计产品让这些能力真正表现出来。

第四，优秀的模型使用方法，不是把步骤规定得越来越细，而是给清楚目标、边界和验收标准，并让模型能够持续验证自己的工作。

第五，编程能力仍然重要，但未来更重要的是把技术和真实问题、产品、用户以及商业结合起来。

## 深度解读（1）

### 2026-09-18 00:19:25

#### AI 产品的新资产：不是提示词，而是任务、验证与权限边界

Claude Code 在 Opus 5 发布后删除了约 80% 的系统提示词，甚至发现模型在完全移除提示时“略微更聪明”。这不是简单的极简主义，而是在揭示一个反常的工程现实：**许多提示词和编排代码并非产品能力，而是对旧模型缺陷的临时补丁。**模型升级后，这些补丁可能从帮助变成限制，让模型机械执行过时步骤，无法使用新能力。

因此，构建 AI 产品不能沿用“系统越积累越成熟”的默认观念。Claude Code 的做法是每次换模型先做消融：清空提示和部分工具，再逐行加回；只有模型反复在同一处失败，才增加约束。即使评测集也不是永久资产，通常一到三个模型世代就会饱和。真正更耐久的部分，反而是**用户任务、验收标准、权限体系，以及对失败的持续观测能力**。

##### 提示工程正在变成“验证工程”

演讲中最有迁移价值的案例，不是某个提示技巧，而是让模型重写代码库的方法：给出目标，开放必要工具，再提供可以持续检查结果的机制。Bun 从 Zig 向 Rust 的迁移能够运行 11 天，关键条件是已有完备测试；Electron 应用重写为 Swift，则让模型同时运行两个版本，通过截图逐像素比较。

这解释了为什么“给模型更难的问题”有时比拆成大量微指令更有效。模型已经能够自己分解任务，但必须知道是否正在接近正确答案。**测试、模拟器、静态分析、截图对比和业务规则，不只是质量保障，也是在长任务中为模型提供方向。**未来 AI 产品的差异化，很可能来自谁能把模糊工作改造成可执行、可反馈、可收敛的环境。

这也划出了适用边界：代码迁移、数据清洗和规则明确的运营任务更容易自动化；战略判断、审美创作或结果数月后才显现的工作，缺少可靠验证器，增加代理数量未必提高质量。

##### “产品机会”来自释放能力，而非包装模型

Claude Code 的起点，是意识到当时的模型已能写完整文件，而主流产品仍把它限制在补全和只读聊天中。所谓“产品能力滞后”，本质是**模型已经会做，但界面、权限和工作流仍按旧能力设计**。今天值得寻找的，不只是新的模型用途，而是那些仍被人工切碎、实际上可以交给模型端到端完成的任务。

可操作的方法是：每次模型升级，都用最少提示重新测试过去失败的高价值任务；先定义成功标准和安全边界，再让模型自行规划。不要先搭复杂代理框架，也不要把关注度误当需求。应验证的是：任务是否高频或高成本，结果能否自动验收，错误能否被隔离，以及推理成本是否低于现有方案。

演讲中“提示注入已解决”“数千代理相当于数十或数百名工程师”等说法仍缺少公开基准、成本数据和失败率，不能直接当成定论。更稳妥的判断是：**随着模型能力快速变化，产品团队最重要的能力不再是固化最佳实践，而是持续删除旧假设，并用实验重新发现模型现在能独立完成什么。**

##### 一句话看懂

Claude Code 创始人认为，模型进步后，优秀 AI 产品的关键不再是堆叠复杂提示词和流程，而是减少束缚、提供验证手段，并通过实际测试不断调整。

##### 关键内容

- **旧配置可能妨碍新模型。** Claude Code 针对 Opus 5 删除了约 80% 的系统提示；团队每次模型更新都会先做“消融测试”——删掉提示、工具或代码，再逐项验证是否真有必要。

“解除束缚”就是别把 AI 当成只能照步骤执行的脚本，而要像能力较强的同事：说明要做什么、如何验收，让它自行规划，再根据失败结果修正。
