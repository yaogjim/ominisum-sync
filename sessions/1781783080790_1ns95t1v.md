## 分析要点

- **核心高价值点**：将Skill视为可版本化文件，把改进过程转化为基于真实反馈的规则diff，并通过PR审查保证安全迭代。
- **留存建议**：长期保留（提供了较清晰的Agent技能自我改进框架，可迁移到代码审查、缺陷处理、事件响应等场景。）

**知识要点**

- Agent loop可拆分为执行任务的内循环和总结反馈、更新规则的外循环。
- GitHub issue中的评论赞踩、人工纠正和标签漂移可以作为低成本反馈信号。
- 改进Skill时应提炼可泛化规则，而不是针对单个案例做局部修补。
- Skill更新不应自动写入主分支，应通过版本号递增和PR review控制质量。

**行动项**

- 在已有GitHub项目中识别可自动化分类或审核的任务场景。
- 设计反馈采集机制，优先利用评论、标签变更和人工纠正等自然产生的数据。
- 将Agent提示词或Skill文件版本化，并建立基于PR的迭代审查流程。

## 正文

**陈成**

最近大家都在聊 agent 的「loop」，但很少人讲清它到底是什么。Warp CEO Zach Lloyd 给了一个能落地的版本：让 Skill 从反馈里自我进化的双层循环，以 GitHub issue 三分类为例。

内循环：每来一个新 issue，GitHub Action 触发云 agent 跑 triage Skill，自动分到 ready-to-implement / needs-info / duplicate 三档，打标签并发一条带隐藏标记 oz-triage v:N 的评论，求 👍/👎。

外循环：每天一个定时 agent 拉取近 14 天所有被分类的 issue，收集三类信号，评论赞踩、人工纠正回复，还有「人把标签从 ready 改成 needs-info」这种标签漂移（最强 ground truth）。然后把信号提炼成可泛化规则，比如别盯着单个 issue 改，而是写成「崩溃报告缺 OS 版本号一律归 needs-info」，再塞进 Skill 的 Learned guidelines 段、版本号 +1，开 PR 让人 review 合并，永不自动改 main。

要点就一句：Skill 就是文件，改进 = 对文件做 diff；反馈天然藏在 issue 标签和评论里，零额外标注成本。同样适用于 code review、bug 修复、事件响应；目标明确时可用自动 grader 替代人工。Warp 已用它管理自家开源仓库并开源了框架（oz-for-oss）。

## 解读（1）

### 2026-06-18 11:42:22

#### 深度总结

这段内容讲的是：**Agent 的“loop”不是玄学，而是一套让技能持续变好的反馈机制。**

核心案例是 GitHub issue 自动分类。

##### 1. 双层循环

###### 内循环：执行任务

每来一个新 issue：

1. GitHub Action 触发云端 agent  
2. agent 调用 triage Skill  
3. 自动把 issue 分成三类：
   - `ready-to-implement`：可以直接做
   - `needs-info`：信息不足
   - `duplicate`：重复问题
4. 自动打标签、评论，并留下隐藏版本标记，例如 `oz-triage v:N`

这一步解决的是：**先把活干起来。**

---

###### 外循环：改进技能

每天定时 agent 回看最近 14 天的分类结果，收集反馈：

- 评论里的赞踩
- 人工纠正回复
- 标签被人改动，例如从 `ready` 改成 `needs-info`

其中，**人工改标签是最强反馈**，因为它直接说明 agent 判断错了。

然后 agent 不只是修某一个 issue，而是总结成通用规则：

> “如果崩溃报告缺少 OS 版本号，一律归为 needs-info。”

最后把这条规则写进 Skill 文件的 `Learned guidelines` 部分，版本号 +1，提交 PR 给人 review。

注意：**不会自动改 main 分支。**

---

##### 2. 最关键的一句话

> **Skill 就是文件，改进 Skill 就是对文件做 diff。**

这句话很重要。

它把“Agent 自我进化”从抽象概念变成了工程实践：

- 技能不是黑盒
- 改进可以审查
- 变化可以追踪
- 错误可以回滚
- 人仍然掌握最终合并权

---

#### 深入浅出解读

可以把这个机制理解成一个“会写工作手册的实习生”。

##### 普通 agent 是这样：

> 来一个 issue，我判断一下，打个标签。

它完成了一次任务，但不会真正成长。

##### 有 loop 的 agent 是这样：

> 我每天复盘：  
> 哪些判断被人改了？  
> 哪些评论说明我错了？  
> 下次遇到类似情况，我应该遵守什么新规则？  
> 然后我把规则写进工作手册，提交给人审核。

这就从“做事”变成了“做事 + 复盘 + 修改方法论”。

---

#### 本质价值

##### 1. 把反馈变成资产

很多团队每天都有大量隐性反馈：

- 改标签
- 改评论
- 退回任务
- 重新分类
- 人工补充信息

过去这些反馈用完就没了。

现在它们可以被提炼成规则，沉淀进 Skill。

---

##### 2. 低成本获得训练数据

不需要专门雇人标注数据。

因为人在正常工作中已经留下了反馈：

- 谁改了标签
- 谁指出分类不对
- 哪些 issue 被重新处理

这就是天然数据。

---

##### 3. 比“自动微调模型”更可控

它不是直接改模型参数，而是改 Skill 文件。

所以更透明、更安全：

- 可以 code review
- 可以看 diff
- 可以回滚
- 可以限制生效范围

这对企业场景非常关键。

---

#### 辩证思考

##### 它真正厉害的地方

这个方案的价值不在于“自动分类 issue”，而在于提出了一种可落地的 Agent 进化范式：

> **执行任务 → 收集反馈 → 总结规则 → 修改技能 → 人类审核 → 再执行。**

这比单纯让 agent 反复调用工具更接近真实组织中的学习机制。

---

##### 但它也不是万能的

###### 1. 反馈质量决定进化质量

如果人类标签本身就乱，agent 学到的也是乱规则。

所以外循环不是魔法，它依赖高质量反馈。

---

###### 2. 容易学到局部经验

比如某个仓库适用的规则，换到另一个团队可能失效。

所以 Skill 的规则要避免过度拟合具体案例。

---

###### 3. 人类审核仍然必要

如果让 agent 自动修改主分支，可能会导致错误规则不断强化。

所以“开 PR，不自动合并”是关键安全设计。

---

###### 4. 适合目标清晰的任务

比如：

- issue 分类
- code review
- bug 修复
- incident response

这些任务有明确反馈。

但如果任务目标模糊，比如战略判断、产品审美、复杂谈判，loop 的效果会弱很多。

---

#### 我的判断

这类 loop 的核心不是“让 Agent 自主意识觉醒”，而是：

> **让 Agent 像一个可审计、可复盘、可迭代的工作流系统。**

它最现实的意义是：  
把 AI 从“一次性回答工具”升级成“能在组织反馈中持续优化的执行系统”。

真正的 Agent 进化，短期内大概率不是模型自己变聪明，  
而是围绕它建立一套：

- 可观察的反馈
- 可修改的技能
- 可审查的变更
- 可回滚的版本管理

一句话总结：

> **Agent loop 的本质，是把组织经验写回工作系统。**

## 结构化（1）

### 2026-06-18 11:50:26

##### 主旨概括

文章解释了 AI Agent 中常说的「loop（循环）」到底如何落地：核心是让 **Skill（技能文件）根据真实反馈持续自我改进**。Warp CEO Zach Lloyd 提出的方案是一个“双层循环”：内循环负责执行任务，外循环负责从反馈中总结规则并更新 Skill。

---

##### 1. 背景：Agent 的「loop」需要可落地的解释

最近很多人讨论 Agent 的「loop」，但概念往往比较抽象。  
Zach Lloyd 给了一个更工程化的版本：**通过反馈驱动 Skill 自动进化**，并以 GitHub issue 自动分类为例说明。

---

##### 2. 内循环：每个新 issue 自动分类

当 GitHub 仓库中出现一个新的 issue 时：

- GitHub Action 会触发云端 Agent；
- Agent 运行一个用于 triage 的 Skill；
- 自动把 issue 分成三类：
  - `ready-to-implement`：可以直接开发；
  - `needs-info`：信息不足，需要补充；
  - `duplicate`：重复问题；
- 系统会自动打标签；
- 同时发一条带隐藏标记的评论，例如：`oz-triage v:N`，用于记录当前 Skill 版本。

通俗理解：  
**内循环就是 Agent 每次接到任务后，按照现有 Skill 去执行。**

---

##### 3. 外循环：每天从反馈中学习并改进 Skill

外循环不是处理单个 issue，而是定期总结经验。流程如下：

- 每天由定时 Agent 拉取最近 **14 天** 被分类过的 issue；
- 收集三类反馈信号：
  1. 评论中的赞踩；
  2. 人工纠正的回复；
  3. 标签变化，例如人把 `ready-to-implement` 改成 `needs-info`。

其中，**标签漂移** 是最强的真实反馈，因为它直接说明 Agent 原来的判断错了。

---

##### 4. 关键做法：把具体错误提炼成通用规则

外循环不会只针对某一个 issue 做修补，而是把反馈总结成可复用的规则。

例如：

- 不好的改法：  
  “这个 issue 应该改成 needs-info。”

- 好的改法：  
  “如果崩溃报告缺少 OS 版本号，一律归类为 needs-info。”

这样，Skill 会越来越像一份不断完善的操作手册。

---

##### 5. Skill 如何更新：本质是改文件

文章强调一个关键点：

> **Skill 就是文件，改进就是对文件做 diff。**

具体流程是：

- Agent 把新总结出的规则写入 Skill 的 `Learned guidelines` 段；
- Skill 版本号 `+1`；
- 自动创建 PR；
- 由人 review 后再合并；
- 永远不会自动直接修改 `main` 分支。

这保证了系统能自我改进，但仍有人类把关，避免失控。

---

##### 6. 优势：几乎零额外标注成本

这种方法的优势在于，反馈本来就存在于日常协作流程里：

- issue 标签；
- 评论；
- 人工修改记录；
- 赞踩反馈。

因此不需要额外组织人工标注，系统就能利用已有信号持续优化。

---

##### 7. 适用范围：不只适用于 issue 分类

作者指出，这套“双层循环”不仅能用于 GitHub issue triage，也适合其他场景，例如：

- code review；
- bug 修复；
- 事件响应；
- 开源项目维护。

如果任务目标非常明确，还可以用自动 grader 替代人工反馈。

---

##### 8. 实际案例：Warp 已经在使用并开源

Warp 已经用这套机制管理自己的开源仓库，并开源了相关框架：

- 项目名：`oz-for-oss`
- 核心思想：让 Skill 在真实反馈中不断迭代。

---

##### 总结一句话

Agent 的「loop」不是神秘概念，而是一个工程闭环：  
**Agent 执行任务 → 收集真实反馈 → 总结通用规则 → 更新 Skill 文件 → 人类 review 合并 → 下一轮执行变得更好。**

## 深度解读（1）

### 2026-09-18 00:45:45

#### Agent 的“自我进化”，关键不是自动运行，而是把人工纠错沉淀成可审查的规则

这段案例最值得保留的，不是又一个自动分类 GitHub issue 的 Agent，而是它把含糊的“loop”拆成了两个职责不同的循环：**内循环完成任务，外循环修改完成任务的方法。**

内循环相当直接：新 issue 到来后，Agent 按 Skill 分类、打标签并留下版本标记。外循环则定期回看最近的结果，读取点赞、人工回复和标签修改，再把反复出现的错误提炼成一般规则。例如，它不是为某一条崩溃报告打补丁，而是形成“缺少 OS 版本时归入 needs-info”的新准则。

这个区分很重要。许多所谓 Agent loop，只是让模型反复调用工具，直到得到输出；这里的循环却跨越了多次真实任务，使系统能够从运营结果中更新策略。**是否形成闭环，不取决于执行了多少轮，而取决于错误能否稳定地变成下一版本的行为变化。**

##### 真正稀缺的不是反馈，而是可解释的反馈路径

GitHub 场景的优势，在于人工反馈原本就存在于工作流中：维护者改标签、回复信息不足、指出重复 issue，这些行为不需要额外搭建标注平台。它提示了一个可迁移的产品机会：先寻找业务系统里已有的“纠错痕迹”，而不是先要求用户训练 Agent。

但“零额外标注成本”仍需谨慎理解。标签漂移虽然比赞踩更接近真实判断，却未必是最终 ground truth：维护者可能标准不一，标签也可能因优先级变化而非分类错误被修改。要让外循环可靠，至少需要区分**纠错、业务状态变化和个人偏好**，并保留原始案例与规则修改之间的证据链。

因此，适合这套方法的任务通常有几个特征：任务重复度高，结果会被人自然复核，纠错行为可记录，而且错误可逆。代码审查、客服路由、事件分级可能合适；战略判断、低频决策或结果要很久才能显现的任务，则很难获得稳定反馈。

##### “Skill 是文件”解决的是治理问题

把 Skill 视为可版本化文件，让改进变成 diff、PR、review 和 rollback，而不是模型在后台不可见地“学会了什么”。这降低了采用门槛，也把 Agent 的演进纳入现有软件工程治理：谁提出规则、依据哪些案例、何时合并，都可以追踪。坚持不自动修改 main，尤其关键——外循环负责提出改进，人仍控制规则进入生产环境的权限。

不过，规则持续追加也会遇到上限：准则可能互相冲突、越来越长，或针对近两周样本过拟合。成熟系统最终还需要固定评测集、规则优先级、回归测试和淘汰机制，而不只是不断扩充 Learned guidelines。

所以，这个框架目前更像一种清晰、可落地的工程范式，而不是已被充分证明的性能突破。文章没有提供准确率提升、人工节省或错误成本等数据。真正值得验证的问题是：**在不增加审核负担的前提下，外循环能否持续带来可测量的改进，而不是把维护提示词变成新的运营工作。**
