## 正文

两年前，我们推出了 Python Workers，提供了一种在 Cloudflare Workers 运行时中运行 Python 应用程序的方式。我们的目标是让使用 Python 编写 Workers 与使用 TypeScript 一样简单，并让 Python 包和框架生态系统“开箱即用”。

今天，Python Workers 已正式发布（GA）。

GA 意味着什么？这意味着 Python 现在是 Cloudflare 开发者平台上的一等公民，受到全面支持。你可以将已经熟悉的 Python 代码、库和设计模式无缝连接到 Workers AI、R2、D1、Hyperdrive、Durable Objects、Queues、Workflows 以及 Cloudflare 平台的其他部分。你还可以在 Python Workers 中运行 FastAPI、Django 和 Flask 等流行的 Python 框架。你甚至可以使用 Dynamic Workers 在一个 Worker 中创建另一个 Python Worker。

```
from fastapi import FastAPI, Request

from workers import asgi, WorkerEntrypoint

app = FastAPI()

@app.get("/")

async def root(request: Request):

    env = request.scope["env"]

    return await env.AI.run(

        "@cf/openai/gpt-oss-120b",

        {

            "instructions": "You are a friendly assistant.",

            "input": "What is the origin of the phrase Hello, World?",

        },

    )

Default = asgi.entrypoint(app)
```

#### Python Workers 背后的历程

将 Python 引入 Cloudflare Workers 是自然而然的选择。由于 Workers 自 2018 年起就支持 WebAssembly，这为我们运行 Wasm 编译的 Python 解释器提供了完美的环境。通过使用 Pyodide，我们得以在 Cloudflare Workers 中快速支持各种 Python 应用程序。

我们的目标是打造首个可无限扩展的 Python 应用平台，同时让开发 Python 应用变得像在其他任何地方一样简单且高效。

我们今天重点介绍的功能正是这项多年努力的成果。许多开发者已经在 Python Workers 中构建应用程序；今天，我们让这些能力面向所有人达到生产就绪状态。

#### Python 现已成为 Cloudflare Workers 运行时中的一等语言

Python Workers 现在原生支持 Cloudflare 开发者平台绑定。此前，在 Python Workers 中使用这些 Cloudflare 绑定需要在 RPC 边界处显式地将 Python 对象转换为 TypeScript 对象。例如，将 Python 字典发送到 Cloudflare Queue 需要以下胶水代码才能正常工作：

```
from pyodide.ffi import to_js

import js

self.env.QUEUE.send(to_js({"key": "value"}, dict_converter=js.Object.fromEntries))
```

这要求 Python 开发者在编写 Python Workers 时始终牢记 JavaScript 环境和代码，这也是人类和 AI 代理常见的错误来源。为了解决这个问题，我们将整个类型转换过程封装在 Workers 运行时和 Python SDK 中。这使你能够以 Pythonic 的方式使用所有 Cloudflare 绑定，而无需编写一行 JavaScript 代码，使以下内容直接可用：

```
self.env.QUEUE.send({"key": "value"})
```

#### Web 框架：FastAPI、Django 和 Flask

您现在可以运行您喜欢的 Python 框架，例如 FastAPI、Django 或 Flask，在 Python Workers 中构建 API 服务器。我们实现了一个内置连接器，您可以使用它轻松地将您的 Web 应用程序连接到 Python Workers。

假设您有一个简单的 FastAPI Web 应用程序：

```
from fastapi import FastAPI

app = FastAPI()

@app.get("/")

async def root():

    message = "Hello, world!"

    return {"message": message}
```

在原生环境中，您会使用诸如 `uvicorn` 之类的 Web 服务器来运行此应用程序。

```
$ uvicorn main:app
```

在 Python Workers 中，您可以使用我们提供的 workers.asgi 包来运行相同的应用程序，只需将以下代码片段添加到您的代码中：

```
from workers import asgi

class Default(WorkerEntrypoint):

    async def fetch(self, request):

        return await asgi.fetch(app, request, self.env)

# or equivalently

Default = asgi.entrypoint(app)
```

同样地，你可以使用 `workers.wsgi` 包来运行 Django 等同步 Web 应用程序。

```
from workers import WorkerEntrypoint, wsgi

from your_django_app.wsgi import app

Default = wsgi.entrypoint(app)
```

##### 那么，底层发生了什么？

Python 有一个标准约定，规定了 Web 应用程序应如何与 Web 服务器通信，即 Web 服务器网关接口（WSGI），或其现代异步对应物 ASGI。这一标准使开发者能够构建完全独立于服务器的应用程序。在传统部署中，像 Uvicorn 或 Gunicorn 这样的 Web 服务器负责处理多个并发客户端连接和线程以扩展流量，而像 FastAPI 这样的 Web 框架则可以纯粹专注于应用程序逻辑。

在 Cloudflare Workers 中，Workers 平台本身充当 Web 服务器。由于我们的全球网络已经无缝处理了负载均衡和无限扩展，我们无需通过在 Python Workers 内部运行服务器来重新发明轮子。

相反，我们的 `workers.asgi` 和 `workers.wsgi` 连接器充当一个轻量、优化的桥梁。它们将传入的原生 JavaScript 请求转换为 Python 应用程序所期望的标准 WSGI/ASGI 结构，并以最小的开销无缝地将响应传回。通过这种方式，Python 开发者可以兼得两者之长：你可以使用自己喜爱的 Web 框架来编写和组织代码，同时让 Cloudflare Workers 平台即时将你的 API 扩展到全球，而无需配置任何服务器。

这些连接器不仅可以与 FastAPI、Django 或 Flask 一起使用，还可以与任何使用 WSGI 或 ASGI 接口的 Python Web 框架一起使用。

你可以在 Python Workers 文档中找到有关使用各个 Web 框架的更多信息。

#### 将 PostgreSQL 和 MySQL 与 Hyperdrive 一起使用

如果您正在使用 PostgreSQL 或 MySQL 等关系数据库构建 Python 应用程序，现在可以将 Hyperdrive 集成到 Python Workers 中。

此前，Python Workers 不支持 TCP 套接字，导致数据库驱动程序无法使用。要理解为什么这是一个障碍，您需要了解 WebAssembly 的工作原理。像 `aiomysql` 或 `asyncpg` 这样的 Python 数据库驱动程序依赖标准库的 `socket` 模块来建立连接。在标准环境中，该模块会对底层操作系统进行 POSIX 系统调用。在 WebAssembly 沙箱内，这些 POSIX 网络系统调用通常是始终失败的 stub。任何尝试打开标准套接字的操作都会立即失败。为了解决这个问题，我们使用 Workers connect API 实现了套接字系统调用。

当数据库驱动尝试打开 TCP 连接时，它会经过我们自定义的 socket 系统调用实现。它将打开连接和读取字节等标准 Python socket 操作转换为 Workers 运行时使用的相应 JavaScript 调用。由于这种转换发生在系统调用层面，你的数据库驱动完全不需要了解底层实现。

正是这个 socket 桥接机制使得我们的 Hyperdrive 集成成为可能。要在 Python Workers 中使用 Hyperdrive，首先通过 Hyperdrive 连接你的数据库，并在 Wrangler 配置中设置绑定：

```
"hyperdrive": [

    {

        "binding": "HYPERDRIVE_MYSQL",

        "id": "<example id: 57b7076f58be42419276f058a8968187>",

    }

]
```

然后，使用你熟悉的数据库驱动连接到 Hyperdrive：

```
import aiomysql

from workers import WorkerEntrypoint

class Default(WorkerEntrypoint):

    async def fetch(self, request):

        hd = self.env.HYPERDRIVE_MYSQL

        conn = await aiomysql.connect(

            host=hd.host,

            port=int(hd.port),

            user=hd.user,

            password=hd.password,

            db=hd.database,

            ssl=None,

        )

        cur = await conn.cursor()

        await cur.execute("SELECT username FROM user")

        r = await cur.fetchall()

        await cur.close()

        conn.close()
```

你可以参考 Hyperdrive Python Workers 文档，了解如何在 Python Workers 中使用 Hyperdrive，以及目前支持哪些包。

#### 扩展 WebAssembly 包生态系统

由于 Python Workers 在 WebAssembly 沙箱中运行，任何带有原生 C/C++/Rust 扩展的包都必须交叉编译为 WebAssembly 才能在 Python Workers 中运行。然而，此前并没有标准的方法将任何 Python 包交叉编译为 WebAssembly。这意味着我们的团队不得不手动编译和托管自定义的 WebAssembly 包。这极大地限制了你在 Python Workers 中实际可以使用的包的数量。

我们希望解决这个问题，让用户能够使用更广泛的包。然而，我们并不想仅仅构建只能在 Python Workers 中使用的包，那样不会给社区带来好处。由于 Python Workers 构建在 Pyodide 之上，我们希望生态系统能够以有利于 Pyodide 和整个 Python-on-WebAssembly 社区的方式发展。

为此，我们提出了 PEP 783，它标准化了一个在浏览器运行时中运行 Python 的平台，称为 PyEmscripten。经过一年多的讨论和完善，该提案已被接受，使包维护者能够为 PyEmscripten 平台构建和发布包，并使其在所有实现 PyEmscripten 的环境中可用。

我们还稳定了现有的 Pyodide 构建工具链，并将其演进为所有包维护者都可以访问的形式，使开发者能够轻松地为 PyEmscripten 平台构建包。此外，我们为 [`cibuildwheel`](https://cibuildwheel.pypa.io/en/stable/) 添加了 PyEmscripten 平台支持，以便其他人更容易采用对 PyEmscripten 平台的支持。

虽然生态系统仍在采用这一标准，但我们希望未来每个 Python 包都能有一个与 WebAssembly 兼容的 wheel。我们也在积极与主要包维护者合作，添加 PyEmscripten 构建。如果您遇到尚不支持的包，请在 Discord 或 GitHub 上告知我们，我们的团队将努力完成构建。

你也可以查看我们在 EuroPython 2026 上的演讲：“Python Everywhere: The State of Python on WebAssembly”，了解我们是如何实现这一点的。

#### 使用 Python 构建 AI 智能体和流水线

庞大的数据科学和机器学习包生态系统使 Python 成为构建智能智能体和 AI 流水线的自然选择。但将这些引入 Python Workers 历来面临一个挑战：诸如 `openai` 和 `langchain` 之类的库依赖 `requests` 或 `httpx` 等 HTTP 客户端与外部 API 通信。然而，由于 Python Workers 缺少底层套接字操作支持，这些 HTTP 客户端无法正常工作。

为了解决这个问题，我们向上游做出了贡献，确保这些 HTTP 客户端能够在 WebAssembly 环境中直接通过 JavaScript `fetch` API 路由请求。结合我们在上一节中介绍的新的底层套接字操作支持，这使得整个网络栈能够在 Python Workers 中无缝运行。

因此，你现在可以在 Python Workers 中原生运行 `openai` 、 `langchain` 和 `mcp` 等 AI 库。你还可以将它们与 Workers AI 结合使用，在 Cloudflare 网络中的 GPU 上运行无服务器推理，或通过 Cloudflare AI Gateway 代理请求。

下面的示例展示了一种在 langchain 中运行 Worker AI 模型的方法，使用的是 langchain-cloudflare 包：

```
from langchain_cloudflare import ChatCloudflareWorkersAI

from langchain_core.output_parsers import StrOutputParser

from langchain_core.prompts import PromptTemplate

from workers import Response, WorkerEntrypoint

class Default(WorkerEntrypoint):

    async def fetch(self, request):

        prompt = PromptTemplate.from_template(

            "In one sentence, describe a great day in the life of an {profession}."

        )

        llm = ChatCloudflareWorkersAI(

            model_name="@cf/meta/llama-3.3-70b-instruct-fp8-fast",

            binding=self.env.AI,

            max_tokens=64,

        )

        chain = prompt | llm | StrOutputParser()

        result = await chain.ainvoke({"profession": "electrician"})

        return Response.json({"result": result})
```

## 深度解读-口播（1）

### 2026-09-30 12:18:17

Cloudflare 的 Python Workers 已经正式发布。最值得关注的，不只是它能运行 Python，而是它正在让开发者用熟悉的 Python 框架和工具，直接构建运行在 Cloudflare 全球网络上的应用。不过，这并不意味着所有 Python 包都能原封不动地搬过去。

理解这次更新，可以抓住一条主线：让 Python 开发者少操心底层环境，多专注于应用本身。

Python Workers 并不是在普通服务器上启动一个 Python 进程。它使用 Pyodide，也就是能在 WebAssembly 环境中运行的 Python 解释器。WebAssembly 可以理解为一种跨平台的程序运行格式。这里的 Python，运行在受约束的沙箱里，而不是直接面对完整的操作系统。

这种方式让 Python 能进入 Workers 平台，但也带来了几道门槛：Python 对象怎样交给平台服务？现有网站框架怎样处理请求？数据库和人工智能工具需要的网络连接，又怎样建立？这次正式发布，重点就是补齐这些环节。

先看一个很小、但很能说明问题的变化。

过去，开发者想把一个 Python 字典发送到 Cloudflare 的消息队列，必须先把字典转换成 JavaScript 对象。也就是说，即使你写的是 Python，也得记住另一种语言的对象规则，并补上一段转换代码。

现在，这层转换被封装进了运行时和开发工具。开发者可以直接把 Python 字典交给队列，不必自己处理 JavaScript 对象。

这里涉及一个概念，叫平台绑定。简单说，就是让代码直接访问平台提供的服务，比如存储、数据库、消息队列和人工智能推理。原生支持这些绑定，意味着 Python 不再只是勉强接进来的语言，而是受到全面支持的平台语言。

接下来，是现有的网站框架怎么运行。

文章列举了 FastAPI、Django 和 Flask。关键并不是 Cloudflare 为每个框架重写了一套服务器，而是利用了 Python 已有的标准接口。

其中，WSGI 是网站应用与服务器之间的一种标准通信接口；ASGI 则是现代的异步接口。框架按照这些接口处理请求，就不需要和某一种服务器绑死。

在传统部署里，开发者通常要用 Uvicorn 或 Gunicorn 这类服务器软件接收请求，再交给应用框架。在 Python Workers 里，接收请求和分配流量的工作由 Workers 平台承担。

Cloudflare 提供的连接器，就像一座轻量的桥：把平台收到的请求转换成 Python 框架认识的形式，再把框架生成的响应传回去。

所以，开发者仍然可以用熟悉的框架组织业务逻辑，却不必在 Worker 内部再运行一套网站服务器。这些连接器也不只适用于文章列出的三个框架，而是面向符合相应标准接口的 Python 框架。

不过，能处理网站请求，还不等于能运行完整的应用。更深的一道门槛，是网络连接。

以数据库为例。连接 PostgreSQL 或 MySQL 的 Python 驱动，通常依赖标准库里的套接字功能。套接字可以理解为程序建立网络连接、收发数据的基础通道。

在普通系统里，这些操作最终由操作系统完成。但在原来的 WebAssembly 沙箱里，相应的网络调用并没有真正实现。数据库驱动即使装好了，一尝试建立连接，也会失败。

Cloudflare 的解决办法，是在更底层搭桥。数据库驱动发出标准的 Python 网络操作后，运行时把它转换成 Workers 平台支持的连接操作。因为转换发生在底层，数据库驱动不需要了解这套实现细节。

这也让 Python Workers 能接入 Hyperdrive，也就是 Cloudflare 用来连接数据库的服务。开发者配置好数据库绑定后，就可以使用受支持的 Python 驱动进行查询。需要注意的是，具体支持哪些驱动和包，仍然要查对应文档。

人工智能工具也遇到过类似的问题。

很多 Python 人工智能库，需要通过 HTTP 客户端访问外部接口。以前，底层网络支持不足，这些客户端就无法正常工作。Cloudflare 一方面向上游项目贡献改进，让请求可以通过 JavaScript 的网络请求接口发送；另一方面补上了底层套接字支持。

文章因此宣布，OpenAI、LangChain 等人工智能库，现在可以在 Python Workers 中运行。开发者还可以把这些库接到 Workers AI，也就是 Cloudflare 的无服务器模型推理服务。

一个具体案例，是图像生成应用。用户提交请求后，先进入消息队列。工作流服务再协调图像生成步骤，调用模型，最后把生成的图片存进 R2 对象存储。这个案例的价值在于，它展示的不只是一次模型调用，而是一条由 Python 串起来的完整处理流程。

但还有一个限制，不能被“正式发布”四个字掩盖：Python 包生态的兼容性。

不少 Python 包包含用 C、C++ 或 Rust 编写的原生扩展。这些部分不能直接在 WebAssembly 沙箱里运行，必须编译成适合这个环境的版本。

过去缺少统一标准，Cloudflare 团队需要手动编译并托管一些包，能用的包因此受到限制。

为了解决这个问题，团队提出了编号为七百八十三的 Python 增强提案，并已获得接受。它定义了一个名为 PyEmscripten 的平台标准，让包维护者可以为这类环境构建和发布兼容包，而不是只为 Cloudflare 单独做一个版本。

这项工作的意义，是推动整个 Python 与 WebAssembly 生态共享成果。不过，文章也明确说，生态仍在逐步采用这个标准。未来每个 Python 包都能提供兼容版本，是他们的期待，不是已经实现的事实。

所以，这次发布最值得记住的是：Python Workers 正在把平台服务、网站框架和网络能力接到一起，让熟悉的 Python 开发方式进入 Workers 环境。与此同时，它仍然不是完整传统服务器环境的无差别替代；实际选择项目时，框架接口、数据库驱动和原生扩展包的兼容性，依然是需要确认的关键条件。
