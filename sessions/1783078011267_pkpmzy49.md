## 分析要点

- **核心高价值点**：将多智能体协作简化为“负责人调度、子代理专职执行、共享文件夹交接”的稳定模式，并强调明确边界与交接格式。
- **留存建议**：长期保留，作为Claude Code多智能体工作流设计模板参考（包含可复用的多智能体分工、交接、权限控制和主代理编排框架，并附带可直接使用的初始化提示词）

**知识要点**

- 并非所有流程都适合多智能体，只有可拆分、输入输出不同且会重复执行的流程才值得组建代理团队
- 每个子代理应明确使命、边界、交接格式和输入输出示例，避免职责重叠
- 主代理只负责规划、调度和状态更新，不应执行专业任务
- 通过共享目录传递状态和交接文件，避免子代理之间直接通信造成混乱
- 无人值守运行多智能体流程时需要设置令牌预算和工具调用保护，防止成本失控

**行动项**

- 选择一个高频重复流程，用文中的三个问题判断是否适合多智能体化
- 为每个子代理编写使命、边界、交接文件格式和示例
- 在Claude Code项目中建立/agents/state/与/agents/out/目录用于状态与交接
- 将文末提示词粘贴到Claude Code中生成初版代理团队配置
- 在正式运行前检查各代理工具权限、交接文件状态字段和预算限制

**Henrikh**

### 构建一个针对任何流程的 Claude 代码代理团队 - 在 1 个提示中

大多数多智能体演示都是表演性质的。一个特定的团队，一个特定的演示，从未被复用，也无法重现。你看完，点点头，关掉标签页。

> 这个不是那个。

我将向你展示一个适用于任何可重复流程的单一蓝图：内容制作、代码审查、研究、销售分类处理，无论你每周做什么。

相同的构建模块，相同的规则，相同的协调模式。唯一变化的是代理的行为。

最后你会得到一个完整的提示词。你将其粘贴到 Claude Code 中，回答三个关于你自己流程的简短问题，然后 Claude 会为你组建整个团队。

---

#### 包裹

- 负责人 — 选择下一个任务，调用合适的子代理，本身从不执行专门的工作
- 子代理 — 每个负责一个任务，工具范围窄，边界明确，交接文件格式固定
- 共享文件夹 — /agents/state/ 用于任务列表和笔记，/agents/out/ 用于交接
- 四条规则 — 只有主导计划，每个文件形状一个代理，窄工具，主导上下文保持简短
- 最后一个提示 ——在三个问题之后为您的流程组建团队

---

#### 第0节 — 你真的需要一个代理团队吗？

90%的“我搭建了一个多智能体系统”推文本不该存在。作者需要的是一个好的提示词，而不是五个假装成公司的智能体。

这是诚实之门。如果你的回答针对这三个问题的回答都是“是”，就组建一个团队。否则，停止并使用一个具有精准提示的单一代理。

1. 这个流程是否真的分解成不同的工作？“写一条推文、设计一张图片、安排发布”是三项不同的工作
2. 那些工作是否涉及不同的内容？ 审核代理读取代码。发布说明代理读取 git 历史。不同的输入。不同的输出。如果每个人都读取同一个文件并写入同一个文件，你就会有一个任务冒充三个任务。
3. 你会重复执行这个流程吗？ 团队通过复用实现回报。如果你只运行一次，只需编写一个提示并继续。如果你接下来一年每周运行它，那么组建团队的前期设计成本会在第一个月就收回。

如果其中任何一个是“否”，就停止。一个代理，一个提示词。继续。

---

#### 第1节 — 3个构建块

Claude 代码代理团队中只有三个成员。其他的都是细节。

主要代理人

- 你实际与之交互的那个 Claude Code 实例。你给它设定目标。它本身不做专门工作——它进行调度，读取返回结果，决定下一步，重复这个过程。可以把它想象成总承包商，而不是砌砖工。

2\. 子代理商

- 专业助手，每个都有一项任务。每个都是 .claude/agents/ 目录下的一个 Markdown 文件（我们在 .claude/ 文件夹的文章中介绍过该格式）。当主代理调用其中一个时，Claude 会为该子代理启动一个新会话——其自身的上下文、工具权限和专注点。完成后，它会返回给主代理。

3\. 共享文件夹

- 一个单一的目录，主代理和子代理均可从中读写。这是唯一存储“当前发生的事情”的地方。否则，子代理之间不存在共享内存。如果研究员完成工作且撰写者需要结果，研究员必须先将结果放入共享文件夹中。

就是这样。一个牵头人，一些专家，以及一个他们都用作布告栏的文件夹。Anthropic 自 2026 年 5 月起正式支持这种模式——在此之前，社区通过黑客方式拼凑出这种模式。现在它是一个雏形。

★ 对所有人都有用。 无论你是在协调推文撰写还是代码审查，思维模型都是相同的。

---

#### 第2节 — 为你的流程设计团队

这是大多数人会忽略的部分，然后他们会疑惑为什么他们的代理会发生冲突。

在创建文件之前，每个子代理都需要记录下四件事。大多数失败的代理团队只记录了其中一两项的草稿版本。而成功的团队则为每个代理都以书面形式记录了全部四项内容。

- 使命 ——一句话。这个代理存在的目的是什么。如果你无法用一句话描述，说明代理的范围太广。拆分它或明确它
- 边界 — 这是该代理不接触的内容。这是人们容易遗忘的部分。如果没有明确的边界，每个代理都会试图使用所有工具和所有文件。冲突是不可避免的。将边界写入与任务相同的文件中
- 交接格式 — 这是该代理完成后留下的内容。一个文件名，一种结构。“在 /agents/out/ 目录下生成 Drops result.md 文件，包含以下部分：总结、证据、下一步。” 如果交接格式不是精确的文件形式，下一个代理就必须猜测，而 Claude 的猜测很糟糕
- 一个实际示例 —— 一个针对此角色的输入→输出小示例。不是一个冗长的演示。只需足够让智能体知道良好输出的样子。这正是避免通用回答的关键。

对于你团队中想要的每个角色，填写这四项。然后将每个角色转换为 .claude/agents/ 目录下的 Markdown 文件。

格式：

```text
---
name: researcher
description: Pulls source material for a draft, returns evidence-only
tools: [Read, WebFetch, Grep]
---

Mission: gather and summarise factual material for the topic given by the lead.

Boundary: do NOT write drafts, do NOT suggest framing, do NOT touch files
outside /agents/out/. Return evidence only.

Handoff: drop /agents/out/research-{topic-slug}.md with sections:
  - claims (each with a source URL and date)
  - contested points
  - notable gaps

Example: input "claude-mem v13.1.0" → output research-claude-mem-v131.md
with 6 claims, 1 contested point, 2 gaps.
```

注意不要包含的内容。不要出现“你是一个乐于助人的研究助手，…’——这是浪费的 token。不要有人设。不要有语气说明。只需要包含这四个内容。导语在编排层面处理语气和人设。

★ 对所有人都有用。 格式为 Markdown；学科为项目管理

#### 第3节 — 四条无碰撞规则

一个每个成员都能为所欲为的团队，是一个每个成员都会做错事的团队。四条规则能让他们互不干扰。

> 规则1 — 只有导语撰写计划

- 子代理不决定下一步做什么。他们执行、交接、完成。如果子代理开始提出后续步骤，说明你给了它太大的权限范围。负责人是唯一进行规划的地方。这听起来很有约束性。但这正是团队和骚乱的区别。

> 规则2 — 每个文件形状由一个代理拥有

- 研究员撰写 research-\*.md 文件。作者撰写 draft-\*.md 文件。评审员撰写 review-\*.md 文件。如果两个代理可以写入相同的文件格式，其中一个最终会在过程中覆盖另一个的工作。负责人在代理的 frontmatter 中，于交接（handoff）部分进行记录。

> 规则 3 — 角色越专一，工具越专一

- 研究代理拥有读取、WebFetch、Grep 权限。它在交接路径之外没有编辑或写入权限。撰写者仅能编辑自己的草稿文件。审阅者可能仅拥有读取权限。工具集越窄，代理越难越界。在代理的 frontmatter 的 tools: 行中设置这一点。

> 规则 4 — 导语上下文保持简短

- 负责人阅读交接文件，在自己的工作笔记中总结这些文件，仅将总结传递给下一个子代理——而非完整文本。否则，负责人的上下文信息会在每个环节中膨胀，您会看到社区所说的“静默失败”——已消耗令牌、任务仍未完成，负责人已失去主线。

★ 对所有人都有用。规则是通用的。实现位于代理文件中。

#### 第4节 — 会合模式

这是编排。以下是团队执行一个周期时的实际情况。

- 负责人从你那里接收目标。它读取位于 /agents/state/task.md 的任务文件（如果不存在则创建一个）。任务文件是纯文本——我们正在尝试做什么、已完成什么、待处理什么。
- 主代理选择第一个待处理任务并调用合适的子代理。子代理在自己的全新会话中启动——没有之前周期的记忆，没有来自主代理上下文的干扰。它完成其单一任务，并将交接文件放置在其前置内容中指定的位置。然后返回。
- 主代理读取交接文件。它更新 task.md — 将待处理任务标记为已完成，可能添加它了解到的新任务。它选择下一个待处理任务并调用下一个子代理。

那是一个循环。每个子代理每次都会获得一个洁净室。共享文件夹是内存的存储位置。负责人是指挥者。

> 关键洞察： 子代理之间不相互通信 。它们各自只与共享文件夹通信。这正是避免混乱的原因。两个代理永远不会处于同一会话中。不存在“代理 A 向代理 B 请求澄清”的情况。如果 A 需要 B 提供某些信息，A 的交接会显示“阻塞于 X”，负责人查看后，负责人会带着该问题调用 B。

★ 对所有人都有用。 流程是相同的，无论你是创作内容还是交付代码

#### 第6节 — 发货前你应该了解的故障模式

三种真实的失效模式，附带一个真实的恐怖故事。

> 无声故障

- 负责人调用子代理，子代理返回后工作继续推进，但最终没有实际产出。令牌已消耗，任务仍未完成。这种情况发生在子代理边界模糊时——代理认为自己完成了工作，负责人认为获得了实际产出，双方都未检查文件。 解决方法： 每个交接文件顶部必须包含一个状态字段，并且负责人在标记任何工作完成前必须阅读该字段。

> 导语上下文膨胀

- 每个周期，负责人都会阅读交接文件。如果没有纪律约束，负责人的上下文会每周期增长一千个词元。到第十个周期时，已经丢失了最初目标。 解决方法： 规则 4。负责人将交接内容总结为简短的 state/notes.md 文件，并仅将总结转发给下一个子代理。

> 6000美元一晚

- 4 月，一名开发人员让一个 Claude 代码例程运行了一夜。到早上时，账单金额达到了 6000 美元。原因是存在一个带有提示词缓存的紧循环，该循环未针对缓存的 TTL 进行合理设计——每次调用都按全额未缓存费率计费。 解决方法： 对于任何无人值守运行的团队，请在 settings.json 中设置硬令牌预算，并设置一个 PreToolUse 钩子，在预算用尽后阻止工具调用。如果不设置预算，请勿无人值守运行。

★ 前两个是协调问题，适用于所有人。第三个是特定于无人值守运行的

#### 第 7 节 — 提示 — 将其粘贴到 Claude Code 中，它将为你的流程构建团队

在团队将在此开展工作的项目根目录中打开一个 Claude Code 会话。粘贴以下提示词。回答这三个问题。完成。

```text
You're setting up a Claude Code agent team for a process I run.
Before creating any files, ask me three short questions and wait
for each answer:

1. What is the process? (one sentence — e.g. "weekly competitive
   research", "incoming sales email triage", "PR review")
2. What does ONE successful run of this process produce? 
   (one short answer — the final artefact, e.g. "a 2-page landscape
   doc", "a triaged inbox with drafted replies", "a PR review comment")
3. Roughly how many distinct jobs are in one run? 
   (a number from 2 to 5 — if you say 1, stop and use a single
   prompt instead of a team)

Then design the team:

- Identify the distinct roles needed (between 2 and 5, matching my
  answer to question 3). Each role has a mission, a boundary 
  (what it does NOT touch), a handoff filename pattern, and a
  tools list.
- The roles should match the natural shape of the process: one
  role ingests, one or two transform, one synthesises or decides.
- Do not create more than 5 roles. If the process needs more, it
  is two processes — surface that and ask which one to build.

Then create these files:

File 1: .claude/agents/lead.md
Frontmatter with name: lead, description, tools: [Read, Write, Edit, Bash, Task].
Body explains the lead's job: read /agents/state/task.md, pick the
first open task, invoke the right sub-agent (by name), read the
handoff file, update task.md, repeat. Lead does NO specialised work
itself.

Files 2-N: one .claude/agents/<role>.md per sub-agent.
Each with frontmatter (name, description, tools narrowed to that
role's needs) and body with: Mission (1 line), Boundary (1-2 lines),
Handoff (exact file shape), Example (small input → output).

File N+1: /agents/state/task.md
Empty task list with sections "Open" and "Done". One placeholder
task: "First run — produce <answer to question 2>".

File N+2: /agents/out/.gitkeep
Empty marker so the handoff directory exists.

File N+3: /agents/HANDOFF_TEMPLATE.md
A template all sub-agents copy when writing their handoff file.
Required top section: status: (one of done | blocked | needs-input),
then a short summary, then the structured body for that role.

When everything is created:
- Show me the tree of /agents/ and .claude/agents/
- Tell me which sub-agent the lead will invoke first, and why
- Tell me 2 things I should personally check or edit before the
  first run
- Do NOT make silent assumptions — if any of my three answers were
  vague, re-ask before creating files
```

这就是整个设置。三个问题。一个围绕您实际流程组建的团队

#### 一句话总结

这篇文章给出了一套**可复用的 Claude Code 多智能体团队搭建方法**：  
不要为了炫技而多智能体，只有当流程可拆分、输入输出不同、会重复执行时，才值得搭建；核心是**负责人调度 + 子代理执行 + 共享文件夹交接 + 严格边界规则**。

---

#### 深度总结

##### 1. 多智能体不是默认答案

作者先强调：

> 90% 的多智能体系统其实不需要存在。

如果一个任务用一个好提示词就能完成，就不要硬拆成多个代理。

只有满足三个条件，才适合组建代理团队：

1. **流程能拆成不同工作**
   - 例如：研究、写作、审核、发布。
2. **不同工作处理不同内容**
   - 例如研究读网页，审查读代码，发布说明读 Git 历史。
3. **流程会重复执行**
   - 一次性任务不值得搭团队，重复流程才有复用价值。

核心判断是：

> 多智能体不是为了“看起来高级”，而是为了让重复流程标准化、可控化、可复用。

---

##### 2. 代理团队只有三个核心组件

###### 负责人 Lead

负责人不亲自干专业活，只负责：

- 看任务列表；
- 决定下一步；
- 调用合适的子代理；
- 读取交接结果；
- 更新状态；
- 继续调度。

它像项目经理，不像执行者。

---

###### 子代理 Sub-agents

每个子代理只负责一个明确任务。

例如：

- researcher：只做研究；
- writer：只写草稿；
- reviewer：只审查；
- publisher：只准备发布。

每个子代理都应有：

| 要素 | 作用 |
|---|---|
| Mission | 它存在的目的 |
| Boundary | 它不能碰什么 |
| Handoff | 它完成后交付什么文件 |
| Example | 一个输入输出示例 |

这能防止代理越界、重复劳动或互相覆盖。

---

###### 共享文件夹

代理之间不直接对话，只通过共享目录交换信息：

```text
/agents/state/  # 当前任务、笔记、状态
/agents/out/    # 子代理交接结果
```

这相当于团队的“公告栏”和“文件交接柜”。

---

##### 3. 四条防混乱规则

###### 规则一：只有负责人做计划

子代理不决定下一步，只执行自己的任务。

否则多个代理都会开始“自作主张”，系统就会混乱。

---

###### 规则二：一种文件格式只归一个代理写

例如：

```text
research-*.md  → researcher 写
draft-*.md     → writer 写
review-*.md    → reviewer 写
```

这样可以避免多个代理写同一个文件，互相覆盖。

---

###### 规则三：角色越窄，工具越窄

研究代理只需要读和查资料，不应该有随意写文件的权限。

工具权限越小，越不容易出错。

---

###### 规则四：负责人上下文保持简短

负责人不要把所有子代理输出都塞进上下文。

正确做法是：

- 读取交接文件；
- 摘要到 `notes.md`；
- 只把摘要传给下一个代理。

否则上下文会越来越臃肿，最后模型丢失主线。

---

##### 4. 实际运行模式

一个代理团队的工作循环是：

```text
用户给目标
  ↓
负责人读取 /agents/state/task.md
  ↓
选择第一个待办任务
  ↓
调用对应子代理
  ↓
子代理完成任务，写入 /agents/out/
  ↓
负责人读取交接文件
  ↓
更新 task.md
  ↓
进入下一步
```

关键点：

> 子代理之间不直接沟通，只通过交接文件间接协作。

这降低了混乱，也让流程更容易追踪和复现。

---

##### 5. 常见失败模式

###### 1. 无声失败

子代理看似完成了，但没有真正产出文件。

解决方法：

每个交接文件必须有状态字段：

```text
status: done | blocked | needs-input
```

负责人必须读取状态后才能标记任务完成。

---

###### 2. 负责人上下文膨胀

负责人读太多完整内容，导致上下文爆炸、目标丢失。

解决方法：

只保留摘要，不传全文。

---

###### 3. 成本失控

无人值守运行时，如果循环设计错误，可能产生高额 API 账单。

解决方法：

- 设置硬 token 预算；
- 设置工具调用前检查；
- 不设预算就不要无人值守运行。

#### 通俗解读

可以把这个系统理解成一个小公司。

##### 错误做法

很多人所谓的多智能体，就像：

> 找了 5 个员工，但每个人都不知道自己负责什么，也都能改同一份文件，还都能决定公司战略。

结果一定乱。

##### 正确做法

作者的方法更像正规流水线：

```text
老板/项目经理：负责人
员工：子代理
任务看板：/agents/state/task.md
交接文档：/agents/out/
公司制度：四条规则
```

例如你每周写一篇行业分析：

```text
researcher：收集资料
writer：写初稿
reviewer：指出问题
editor：整理终稿
lead：安排谁先做、谁后做
```

每个人只做自己的事，做完把结果放进指定文件夹。

这样流程就能重复跑，而不是每次重新发明轮子。

#### 文章最有价值的洞察

##### 1. 多智能体的关键不是“智能”，而是“组织”

很多人失败，不是因为模型不够强，而是因为：

- 没有边界；
- 没有交接格式；
- 没有任务状态；
- 没有统一调度；
- 让所有代理都自由发挥。

本质上，这是一个**流程管理问题**，不是单纯的 AI 能力问题。

---

##### 2. 子代理不该互相聊天

这点很重要。

很多人想象中的多智能体是：

```text
A 代理问 B 代理
B 代理反驳 C 代理
C 代理再总结
```

听起来很酷，但容易失控。

作者主张：

```text
A 写交接文件
负责人读文件
负责人再调用 B
```

这更笨，但更稳。

---

##### 3. 交接格式比提示词人设更重要

作者反对写：

> 你是一个专业、耐心、聪明的研究助手……

因为这类人设消耗 token，却不解决协作问题。

真正重要的是：

```text
你负责什么？
你不能做什么？
你输出什么文件？
文件长什么样？
什么算完成？
```

这才是让系统稳定工作的关键。

##### 它适合什么？

这套方法适合：

- 周期性内容生产；
- PR / 代码审查；
- 竞品研究；
- 销售线索分诊；
- 报告生成；
- 数据清洗与分析流程；
- 内部运营 SOP 自动化。

共同特点是：

> 流程稳定、步骤清晰、反复发生。

---

##### 它不适合什么？

不适合：

- 一次性创意任务；
- 高度开放的探索；
- 步骤无法提前定义的复杂决策；
- 需要大量实时人类判断的任务；
- 简单到一个提示词就能完成的任务。

如果任务本身混乱，多智能体只会放大混乱。

---

##### 最大优点

###### 1. 可复用

一次设计，多次运行。

---

###### 2. 可追踪

所有结果都落到文件里，方便检查。

---

###### 3. 可控

通过边界、工具权限、文件格式降低失控概率。

---

###### 4. 可扩展

不同流程只需要替换角色，不需要重建架构。

---

##### 最大风险

###### 1. 过度工程化

为了一个简单任务搭一套代理团队，反而浪费时间。

---

###### 2. 边界设计很难

真正困难的不是写代理文件，而是想清楚：

- 谁负责什么？
- 谁不能做什么？
- 什么算完成？
- 输出格式是什么？

这需要流程思维。

---

###### 3. 仍然需要人类监督

多智能体不是全自动员工。

尤其在：

- 高成本运行；
- 外部发布；
- 代码修改；
- 客户沟通；
- 法务财务场景；

必须有人类审查。

---

#### 我的结论

这篇文章真正讲的不是 Claude Code，而是：

> 如何把 AI 从“聊天工具”变成“流程系统”。

它的核心价值在于把多智能体从炫技变成工程化：

```text
少一点人设
多一点边界

少一点自由发挥

少一点一次性演示
多一点可复用流程
```

最值得记住的一句话：

> 如果流程不能拆分、不会重复、没有不同输入输出，就不要搭多智能体；如果要搭，就先设计边界和交接，而不是先写提示词。

## 结构化（1）

### 2026-07-03 11:39:13

##### 主旨概括

文章提出了一套可复用的 Claude Code 多智能体团队搭建方法，适用于任何“可重复、可拆分”的流程，例如内容生产、代码审查、研究分析、销售分诊等。核心不是炫技，而是用固定的团队结构、边界规则和交接机制，让多个代理稳定协作。

---

##### 0. 先判断：你真的需要多智能体团队吗？

作者强调，很多所谓“多智能体系统”其实没必要，单个高质量提示词就够了。

只有当以下三个问题都回答“是”时，才值得搭建代理团队：

1. **流程是否能拆成不同工作？**  
   例如“写推文、设计图片、安排发布”就是三项不同任务。

2. **不同任务是否处理不同内容？**  
   例如代码审查代理看代码，发布说明代理看 git 历史。  
   如果所有代理都读写同一个文件，那只是一个任务被伪装成多个任务。

3. **这个流程是否会反复执行？**  
   多智能体团队的价值来自复用。  
   如果只是一次性任务，用单个提示词更合适；如果未来一年每周都做，前期设计成本很快能收回。

---

##### 1. Claude Code 代理团队的三个核心构建块

作者认为，一个 Claude Code 代理团队只需要三个基本组成部分。

###### 1）负责人代理 Lead

负责人是你主要交互的 Claude Code 实例。

它不亲自做专业工作，而是：

- 接收目标；
- 规划下一步；
- 调用合适的子代理；
- 阅读子代理结果；
- 更新任务状态；
- 决定下一步。

可以把它理解为“总承包商”，而不是具体干活的人。

###### 2）子代理 Sub-agents

子代理是专业助手，每个只负责一个明确任务。

它们通常是 `.claude/agents/` 目录下的 Markdown 文件。  
当负责人调用某个子代理时，Claude 会为它开启一个新的独立会话，拥有自己的上下文、工具权限和任务边界。

###### 3）共享文件夹 Shared folders

主代理和子代理通过共享目录协作：

- `/agents/state/`：保存任务列表和状态笔记；
- `/agents/out/`：保存子代理交接文件。

子代理之间没有共享记忆，也不会直接沟通。  
如果研究员的结果要给写作者使用，研究员必须把结果写入共享文件夹。

---

##### 2. 设计每个子代理时，必须明确四件事

作者指出，多智能体失败的常见原因，是角色定义太模糊。  
每个子代理都要写清楚以下四项：

###### 1）使命 Mission

一句话说明这个代理存在的目的。

如果一句话说不清，说明角色范围太大，需要拆分或重新定义。

###### 2）边界 Boundary

明确它“不做什么”“不能碰什么”。

例如研究代理只收集证据，不写草稿、不做观点包装、不修改其他文件。

###### 3）交接格式 Handoff

必须规定子代理完成后留下什么文件，以及文件结构是什么。

例如：

```text
在 /agents/out/ 下生成 research-{topic}.md
包含：
- claims
- contested points
- notable gaps
```

如果交接格式不精确，下一个代理就只能猜，而模型的猜测往往不可靠。

###### 4）实际示例 Example

给一个小型输入输出示例，让代理知道“好结果长什么样”。

例如：

```text
输入："claude-mem v13.1.0"
输出：research-claude-mem-v131.md
包含 6 条主张、1 个争议点、2 个信息缺口
```

作者特别提醒：不要写“你是一个乐于助人的研究助手”这类废话。  
子代理文件只需要使命、边界、交接格式和示例。

---

##### 3. 避免冲突的四条规则

为了让多个代理不互相干扰，作者提出四条关键规则。

###### 规则 1：只有负责人负责规划

子代理只执行任务、生成交接文件，然后结束。

它们不决定下一步做什么。  
如果子代理开始规划后续步骤，说明权限给得太大。

###### 规则 2：每种文件形态只归一个代理拥有

例如：

- 研究员写 `research-*.md`；
- 作者写 `draft-*.md`；
- 审阅者写 `review-*.md`。

如果两个代理都能写同一类文件，最终很容易互相覆盖。

###### 规则 3：角色越专一，工具权限越窄

不同代理只给必要工具：

- 研究代理：`Read`、`WebFetch`、`Grep`；
- 写作代理：只允许编辑自己的草稿；
- 审阅代理：可能只需要读取权限。

工具越少，越不容易越界。

###### 规则 4：负责人上下文要保持简短

负责人不要把每个交接文件的完整内容都塞进上下文。  
正确做法是：

- 阅读交接文件；
- 总结到 `/agents/state/notes.md`；
- 只把简短摘要传给下一个代理。

否则上下文会膨胀，导致“静默失败”：token 消耗完了，任务却没完成。

---

##### 4. 团队协作的实际运行模式

整个流程是一个循环：

1. 负责人接收你的目标；
2. 读取或创建 `/agents/state/task.md`；
3. 从待办任务中选择第一项；
4. 调用对应子代理；
5. 子代理在独立会话中完成单一任务；
6. 子代理把结果写入 `/agents/out/`；
7. 负责人读取交接文件；
8. 更新 `task.md`；
9. 继续调用下一个子代理。

关键点是：**子代理之间不直接交流，只通过共享文件夹交接。**

如果 A 代理需要 B 代理的信息，A 不会直接问 B，而是在交接文件中写明“阻塞于某问题”。负责人看到后，再去调用 B 解决。

这样能避免多个代理在同一上下文里互相干扰。

##### 5. 四类典型代理团队示例

作者给出四种常见流程，可以直接套用这种结构。

###### A. 内容生产团队

适合撰稿人、营销人员。

典型角色：

- 研究；
- 起草；
- 审核；
- 发布。

文中提到 Eduardo Lugo 的“自我编辑 Twitter 新闻编辑室”就使用了类似流程，可在约 **20 分钟** 内调整使用。

###### B. Pull Request 代码审查团队

适合开发者。

可拆为：

- 读取变更；
- 检查风险；
- 生成审查意见；
- 总结建议。

###### C. 研究 / 竞争格局团队

适合分析师、创始人、记者。

可拆为：

- 收集资料；
- 对比竞品；
- 提炼洞察；
- 输出报告。

###### D. 销售分诊团队

适合创始人和运营人员。

可拆为：

- 读取销售邮件；
- 分类线索；
- 起草回复；
- 标记优先级。

作者总结：大多数流程都有类似结构——一个负责输入吸收，一个或两个负责转化，最后一个负责综合或决策。

---

##### 6. 发布前必须注意的三种故障模式

###### 1）无声故障

表现：负责人调用了子代理，流程看似继续推进，但最终没有实际产出。

原因通常是：

- 子代理边界模糊；
- 负责人没有检查交接文件；
- 双方都以为任务完成了。

解决方法：  
每个交接文件顶部必须有状态字段：

```text
status: done | blocked | needs-input
```

负责人只有读取并确认状态后，才能标记任务完成。

---

###### 2）负责人上下文膨胀

表现：每一轮负责人都读取大量交接内容，导致上下文越来越长，最后忘记最初目标。

解决方法：  
负责人只保留简短摘要到 `/agents/state/notes.md`，不要把完整交接内容不断传递下去。

---

###### 3）“6000 美元一晚”的成本事故

作者提到一个真实案例：  
4 月，一名开发者让 Claude Code 例程运行了一夜，早上账单达到 **6000 美元**。

原因是存在一个带提示词缓存的紧循环，但没有正确处理缓存 TTL，导致每次调用都按未缓存价格计费。

解决方法：

- 给无人值守运行设置硬 token 预算；
- 在 `settings.json` 中限制预算；
- 设置 `PreToolUse` 钩子，预算用尽后阻止继续调用工具；
- 没有预算限制时，不要无人值守运行。

---

##### 7. 作者提供的一键搭建提示词思路

文章最后给出一个可直接粘贴到 Claude Code 的提示词。  
它会先问用户三个问题：

1. 你的流程是什么？  
   例如“每周竞品研究”“销售邮件分诊”“PR 审查”。

2. 一次成功运行会产出什么？  
   例如“两页竞品报告”“已分类收件箱和回复草稿”“PR 审查评论”。

3. 一次流程大约有几个不同任务？  
   数量应为 2 到 5。  
   如果只有 1 个任务，就停止，不搭建团队，改用单个提示词。

然后 Claude 会自动创建：

- `.claude/agents/lead.md`：负责人代理；
- `.claude/agents/&lt;role>.md`：各个子代理；
- `/agents/state/task.md`：任务列表；
- `/agents/out/.gitkeep`：交接目录占位文件；
- `/agents/HANDOFF_TEMPLATE.md`：统一交接模板。

完成后，它还会展示目录结构，并告诉你：

- 负责人会先调用哪个子代理；
- 为什么先调用它；
- 第一次运行前你需要检查或编辑的两件事。

这篇文章的核心观点是：多智能体系统是否有效，关键不在于模型多强，而在于是否有清晰边界、固定交接格式、统一负责人和受控工具权限。

如果一个流程会长期重复、能自然拆成 2 到 5 个不同任务，就值得搭建 Claude Code 代理团队。正确搭建一次，之后可以反复复用，这才是多智能体真正的回报。

### 2026-08-03 01:59:33

#### 这套方法要解决什么问题

这篇材料介绍了一套可以反复复用的 Claude Code 多智能体团队蓝图。你可以用它来做内容生产、代码审查、研究分析，甚至销售线索分诊。

##### 首先，先判断：你真的需要代理团队吗

核心结论是：不是所有任务都值得拆成多个代理。如果一个好提示词就能完成，就不要为了“多智能体”而搭建团队。

通俗地说，很多所谓的多智能体演示，只是把一个任务包装成几个角色。看起来像一家公司，实际还是同一个工作。如果只是一次性任务，搭建团队的成本往往比收益更高。

可以用三个问题来判断。

第一个问题是，这个流程是否真的包含不同的工作。比如，写一条推文、设计一张图片、安排发布，这就是三个不同的工作。

第二个问题是，这些工作是否需要处理不同的内容。比如，代码审查代理读取代码，发布说明代理读取 Git 历史。它们的输入和输出都不一样。如果所有代理都读取同一个文件、写入同一个文件，那很可能只是一个任务被假装拆成了三个任务。

第三个问题是，你是否会重复执行这个流程。如果只做一次，直接写一个精准提示词就够了。如果未来一年每周都要执行，那么前期搭建团队的成本，可能在第一个月就能收回来。

只要这三个问题中有一个答案是否定的，就先不要组建团队。使用一个代理和一个好提示词，通常更合适。

##### 接下来，理解团队的三个基本构件

核心结论是：这种 Claude Code 代理团队，真正重要的只有三个构件，其他内容都是围绕它们展开的。

第一个构件，是负责人，也就是主代理。

它是你真正交互的 Claude Code 实例。你告诉它目标，它负责选择下一步任务、调用合适的子代理、读取子代理的结果，然后决定接下来做什么。

但负责人本身不做具体的专业工作。它更像总承包商，而不是亲自砌砖的工人。

第二个构件，是子代理，也就是专业助手。

每个子代理只负责一项明确任务。它们通常以 Markdown 文件的形式，放在项目的“.claude/agents/”目录中。

当负责人调用某个子代理时，Claude 会为它启动一个新的会话。这个会话有自己的上下文、工具权限和工作重点。任务完成后，子代理把结果交还给负责人。

第三个构件，是共享文件夹。

这是一块公共区域，负责人和子代理都可以读写。它是团队唯一的“记忆存储位置”。

比如，研究员完成工作后，不能直接把所有内容塞进撰写者的上下文里。它需要先把结果写进共享目录。接下来，撰写者再从那里读取结果。

材料建议使用两个目录：一个是“/agents/state/”，用于保存任务列表和工作笔记；另一个是“/agents/out/”，用于保存子代理之间的交接文件。

所以，整个模式可以简单理解为：一个负责人、几个专家，以及一个所有人都能使用的公告栏。

原文还提到，Anthropic 从二零二六年五月起正式支持这种模式。在此之前，社区主要是通过各种方式自行拼装。无论你做的是推文写作还是代码审查，底层思路都一样。

##### 然后，为每个子代理写清楚四件事

核心结论是：真正决定团队能否稳定工作的，不是代理数量，而是每个代理的职责是否写得足够清楚。

在创建代理文件之前，每个角色都要记录四项内容。

第一项是使命。

使命用一句话说明：这个代理为什么存在，它要完成什么工作。

如果你无法用一句话说清楚一个代理的任务，通常说明它的范围太大。你需要进一步拆分，或者重新定义它的职责。

第二项是边界。

边界要明确写出：这个代理不能做什么，不能读取什么，不能修改什么。

这是最容易被忽略的部分。如果没有边界，每个代理都会试图使用所有工具、读取所有文件，甚至修改其他代理的成果。冲突就会随之出现。

第三项是交接格式。

交接格式规定代理完成工作后，要留下什么文件，以及文件里必须包含哪些部分。

比如，可以要求研究员在“/agents/out/”目录下生成一个名为“research-主题名称.md”的文件，里面固定包含“总结、证据和下一步”。

如果交接格式不够精确，下一个代理就只能猜测应该怎样读取结果。而材料认为，Claude 在这种猜测上的表现通常并不好。

第四项是一个小例子。

这个例子要展示一个具体输入，以及对应的合格输出。不需要长篇演示，只要让代理知道什么样的结果算合格。

比如，输入是“claude-mem 版本十三点一”，输出文件就应当包含六条事实主张、一条存在争议的观点，以及两个信息缺口。

这四项内容，应该写进每个代理自己的 Markdown 文件里。一个研究员的定义可以包括：它只负责收集和总结事实材料；不能写草稿，不能设计文章角度，也不能修改指定目录之外的文件；最后要交付一份包含主张、来源、争议点和信息缺口的文件。

还有一点很重要：不要在代理文件里浪费篇幅写“你是一个乐于助人的研究助手”之类的人设，也不需要额外规定语气。只要写清楚使命、边界、交接格式和例子即可。语气和人设应该由负责人在编排阶段处理。

##### 更重要的是，遵守四条防冲突规则

核心结论是：代理团队必须有严格的分工。一个人人都能做所有事情的团队，最后往往是谁都做不好。

第一条规则是，只有负责人可以制定计划。

子代理只负责执行、交接和结束。它不能自己决定下一步应该做什么。

如果一个研究代理开始安排后续工作，说明它的权限范围太大了。负责人是唯一负责规划的位置。这样的限制看起来严格，但它正是团队和混乱之间的区别。

第二条规则是，每一种文件格式只能由一个代理负责写入。

例如，研究员只能写“research”文件，作者只能写“draft”文件，评审员只能写“review”文件。

如果两个代理都能写同一种文件格式，就可能互相覆盖成果。负责人应该在代理的配置和交接说明中，记录每个代理拥有哪一种文件形状。

第三条规则是，角色越专一，工具权限就应该越专一。

研究代理可能只需要读取文件、访问网页和搜索文本，也就是 Read、WebFetch 和 Grep。它不应当拥有编辑权限，也不应当写入交接目录以外的地方。

撰写者可以编辑自己的草稿文件。审阅者甚至可能只需要读取权限。

工具越少，代理越不容易越界。具体权限可以写在代理文件的“tools”配置里。

第四条规则是，负责人的上下文必须保持简短。

负责人每轮都会读取交接文件。如果它每次都把完整文件内容带入下一轮，上下文就会不断膨胀。

材料举例说，如果每个周期增加一千个词元，到了第十个周期，负责人可能已经丢失最初目标。这里的“词元”，可以理解为模型处理文本时使用的基本单位。

解决方法是：负责人读取交接文件后，只把关键信息总结到简短的状态笔记里，再把这个总结传给下一个子代理，而不是把完整原文全部带过去。

##### 接下来，看看一次任务是怎样循环完成的

核心结论是：子代理之间不直接沟通。它们只通过共享文件夹间接协作，而负责人负责整个循环。

具体流程是这样的。

第一步，负责人接收你的目标，然后读取“/agents/state/task.md”任务文件。如果这个文件不存在，就先创建它。

第二步，负责人找到第一个尚未完成的任务，并调用最合适的子代理。

第三步，子代理在一个全新的会话中启动。它没有上一轮的记忆，也不会受到负责人长篇上下文的干扰。它只完成自己的单一任务。

第四步，子代理把结果写入事先规定好的交接文件，然后返回给负责人。

第五步，负责人读取交接文件，更新“task.md”，把已经完成的任务标记为完成。如果结果显示出新的任务，负责人也可以把新任务加入列表。

第六步，负责人继续选择下一个未完成任务，并调用下一个子代理。

这就是一个循环。每个子代理都像在自己的“洁净室”里工作，共享文件夹承担记忆功能，负责人负责指挥。

这种设计还有一个重要好处：两个代理不会同时出现在同一个会话里，也不存在“代理 A 直接向代理 B 请求澄清”的情况。

如果代理 A 发现自己被某个信息卡住，它只需要在交接文件中写明“阻塞于某个问题”。负责人读到后，再带着这个问题去调用代理 B。

##### 这种结构可以套用到哪些流程

核心结论是：这套结构不依赖某一个行业。只要工作是重复的、可以拆成不同环节，就有机会使用。

材料列出了四类流程。

第一类是内容生产，适合撰稿人和营销人员。

一个典型流程是：研究、起草、审核、发布。材料提到，Eduardo Lugo 曾使用过类似的“自我编辑 Twitter 新闻编辑室”团队，而且据称可以在二十分钟内调整成自己的版本。

第二类是拉取请求，也就是 Pull Request，简称 PR，的代码审查。这类流程适合开发者，可以把代码读取、风险检查、测试分析和最终评论拆开。

第三类是研究和竞争格局分析。这类流程适合分析师、创业者和记者，可以分别安排资料搜集、信息整理，以及最终综合判断。

第四类是销售分诊，也就是对新进入的销售线索或邮件进行分类处理。这类流程适合创始人和运营人员。

材料还指出，这几类团队通常有一种自然结构：一个角色负责吸收和收集输入，一到两个角色负责转换信息，最后由一个角色负责决策或综合。你的重复性工作，也可能符合这种形状。

##### 发货前，要特别防范三种失效模式

核心结论是：代理团队最危险的问题，往往不是模型不会做，而是任务看起来完成了，实际上没有产出，或者成本失控。

第一种失效模式，叫无声故障。

它的表现是：负责人调用了子代理，子代理也返回了，流程继续向前走，但最后并没有真正生成结果。

通常是因为子代理的边界不清楚。子代理以为自己完成了工作，负责人则以为自己拿到了可用产出，但双方都没有检查交接文件。

解决方法是：每一份交接文件的顶部，都必须有一个状态字段。状态只能是“完成”“阻塞”或“需要输入”中的一种。负责人只有读到这个状态，并确认文件确实有内容后，才能把任务标记为完成。

第二种失效模式，是负责人上下文膨胀。

负责人每轮读取交接文件，如果没有控制信息量，上下文会一轮一轮变长，最终让负责人忘记最初目标。

解决方案就是前面提到的第四条规则：把交接文件压缩成简短的状态笔记，只把摘要传给下一个子代理。

第三种失效模式，是无人值守运行造成巨额费用。

材料讲到一个真实案例：四月份，一名开发者让 Claude Code 程序运行了一整夜。第二天早上，账单达到六千美元。

原因是程序存在一个带有提示词缓存的紧循环，但没有针对缓存的有效时间，也就是 TTL，进行合理设计。结果每次调用都按照完整的、未缓存价格计费。

解决方法是：如果团队要无人值守运行，就在“settings.json”中设置硬性的词元预算，并设置一个“PreToolUse”钩子。这个钩子会在预算用完后阻止继续调用工具。

如果没有设置预算，就不要让团队在无人看管的情况下运行。

前两个问题属于协调问题，适用于所有代理团队。第三个问题主要针对无人值守运行，但它带来的成本风险尤其需要重视。

##### 最后，用一个提示词自动搭建团队

核心结论是：你不需要从零手写所有代理文件。只要在项目根目录打开 Claude Code，粘贴一个结构化提示词，再回答三个问题，Claude 就可以根据你的流程生成团队。

这三个问题必须逐个回答。

第一个问题是：你的流程是什么？用一句话说明，例如“每周竞争研究”“销售邮件分诊”或者“代码合并请求审查”。

第二个问题是：一次成功运行最终要产出什么？比如，一份两页的市场格局文档，一封已经分类并写好回复草稿的收件箱，或者一条代码审查评论。

第三个问题是：一次运行大概包含多少个不同工作？回答二到五之间的数字。

如果你回答是一个，Claude 应该停止搭建团队，改为使用一个单独的提示词。如果流程需要超过五个角色，材料建议先停下来，因为这可能已经是两个不同的流程，需要你决定先搭建哪一个。

接下来，提示词会让 Claude 完成几项工作。

首先，它会根据你的回答识别二到五个不同角色。每个角色都必须有使命、边界、交接文件名模式和工具列表。

其次，它会让角色符合自然的流程形状：一个角色负责吸收输入，一个或两个角色负责转换，最后一个角色负责综合或决策。

然后，它会创建负责人文件，也就是“.claude/agents/lead.md”。

这个文件的工具权限包括读取、写入、编辑、执行命令，以及调用任务代理。它的工作方式必须写清楚：读取“/agents/state/task.md”，选择第一个开放任务，调用对应的子代理，读取交接文件，更新任务文件，然后重复执行。

负责人不能亲自完成任何专业工作。

之后，Claude 会为每个子代理创建一个独立的 Markdown 文件。每个文件都应当包含四项内容：一行使命，一到两行边界，精确的交接文件结构，以及一个小型的输入到输出示例。

它还会创建任务文件“/agents/state/task.md”。这个文件至少要有“开放任务”和“已完成任务”两个部分，并放入一个占位任务，例如“第一次运行——产出你在第二个问题中描述的最终成果”。

同时，还要创建“/agents/out/.gitkeep”，确保交接目录存在；再创建“/agents/HANDOFF_TEMPLATE.md”，作为所有子代理写交接文件时使用的模板。

这个模板的顶部必须包含状态字段，状态只能是“完成”“阻塞”或“需要输入”。接下来是简短总结，再往后才是该角色需要交付的结构化内容。

当所有文件创建完成后，Claude 还应该告诉你“/agents/”和“.claude/agents/”下面的目录结构，说明负责人第一次会调用哪个子代理，以及为什么先调用它，并提醒你在第一次运行前亲自检查或修改两件事。

如果你的三个回答有任何模糊之处，Claude 不应该自行猜测，而应该重新提问，等信息明确后再创建文件。

##### 结尾：记住这五点

最后，把整套方法压缩成五个最值得记住的结论。

第一，只有当流程真的包含多个不同工作、处理不同内容，而且会被反复执行时，代理团队才值得搭建。否则，一个精准提示词通常更好。

第二，团队的核心只有三个部分：负责调度的主代理，职责明确的子代理，以及保存任务状态和交接结果的共享文件夹。

第三，每个子代理都必须写清楚四件事：使命、边界、交接格式和示例。缺少其中任何一项，都可能导致冲突或无效产出。

第四，只有负责人负责规划。子代理之间不直接沟通，只通过交接文件协作，而且每个文件格式只能由一个代理负责写入。

第五，正式运行前，一定要防范无声故障、上下文膨胀和费用失控。尤其是无人值守运行时，必须设置预算和自动阻断机制。

这套方法真正的价值，不是展示一个看起来很复杂的多智能体演示，而是把一次搭建，变成可以持续复用一年的工作基础。

#### 多智能体的价值不在“组队”，而在把流程写成可执行契约

这篇文章最值得保留的，并不是那段可以直接粘贴进 Claude Code 的提示词，而是一条更普遍的判断：**多智能体系统首先是工作流工程，其次才是模型能力问题。**

作者设置了一个很实用的准入门槛：只有当流程包含不同工种、各自处理不同输入输出，并且会被重复执行时，才值得拆成团队。否则，一个上下文完整、提示清晰的单智能体通常更便宜，也更可靠。这纠正了常见误区——把同一任务分给多个“角色”并不会自然提升质量，反而增加沟通损耗和错误表面。

##### 真正可复用的是接口，而不是角色名称

文章最扎实的设计，是要求每个子代理明确四件事：使命、禁区、交接格式和输入输出示例。尤其是“一个文件形态只归一个代理所有”，本质上是在用软件工程中的接口、权限和单一写入者原则约束生成式模型。

这比“研究员—撰稿人—审稿人”之类的人设重要得多。代理之间不直接聊天，只通过固定文件交接，也是在主动减少歧义：上游必须留下可检查的产物，下游不必猜测对方究竟做了什么。即使最后不使用多智能体，这套方法也能迫使团队把隐性的操作经验变成可复用的流程规范。

对产品与业务流程而言，机会也正在这里：**先不要问能否增加几个 Agent，而要问流程能否被描述成稳定的中间产物和验收条件。**如果研究结果无法规定来源、日期和争议点，或者销售分诊没有明确分类依据，那么自动化失败往往不是模型不够聪明，而是组织本身没有可执行的定义。

##### “完成了”仍然不等于“做对了”

文章用 `done / blocked / needs-input` 状态防止无声失败，但这只解决了产物是否存在，没有解决产物是否合格。子代理自报 `done`，并不能证明研究来源可靠、代码审查覆盖关键风险，或销售回复符合政策。

因此，真正投入生产时还需要一层文章没有讲透的机制：为交接文件设置机器可检查的 schema，为关键结论保留证据与来源，对高风险输出增加独立验证，并明确失败后的重试、升级人工和停止条件。负责人也不应只读取状态后推进，而应执行验收规则。否则，系统只是把“幻觉”包装成了结构化文件。

##### 中央调度带来秩序，也形成瓶颈

“只有负责人规划、子代理只执行”适合稳定、顺序明确的重复流程，能够控制上下文膨胀和权限越界；但它不适合需要频繁协商、探索路径不断变化的任务。负责人对交接内容持续压缩，还可能丢失少数但关键的异常信息。更稳妥的做法是：摘要用于调度，原始交接仍可追溯；遇到低置信度、证据冲突或不可逆操作时，强制回看原文或请求人工判断。

文中关于 Anthropic 支持时间及“单夜花费 6000 美元”的说法没有给出可核验来源，不宜直接作为事实引用，但预算上限、循环次数和工具调用熔断确实是无人值守运行的必要条件。
