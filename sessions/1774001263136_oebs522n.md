- **核心高价值点**：随着模型能力提升，过去用于“约束和提醒”的工具可能反而成为能力上限，应持续重估工具空间而非固化设计。
- **留存建议**：长期保留（包含智能体工具设计、上下文构建与产品迭代的高价值一线经验，适合作为 Agent 系统设计参考。）

**知识要点**

- 工具设计应围绕模型真实能力边界来定制，而不是按功能列表机械堆叠
- 渐进式披露和子代理可以在不增加过多主工具复杂度的情况下扩展能力

**行动项**

- 审查现有 Agent 的工具集合，识别是否存在因历史原因保留但已限制模型发挥的工具
- 在需要澄清用户意图的场景中，优先尝试结构化提问工具而非依赖自由文本输出

### 构建 Claude 代码的经验：像智能体一样观察

构建 agent 框架最困难的部分之一是构造其动作空间。

Claude 通过工具调用发挥作用，但在 Claude API 中，工具可以通过多种方式构建，使用诸如 bash、技能以及最近新增的代码执行等基本操作（了解更多关于通过编程方式在 Claude API 中进行工具调用的内容，请参阅

[@RLanceMartin 的新文章](https://x.com/RLanceMartin/status/2027450018513490419)）。

考虑到所有这些选项，你如何设计你的代理的工具？你只需要一个工具，比如代码执行或 Bash 吗？如果你有 50 个工具，每个工具对应代理可能遇到的一个用例，那会怎样？

为了设身处地想象自己是这个模型，我喜欢想象自己被给予一道数学难题。为了解决它，你会需要什么工具？这取决于你自己的技能！

最基础的选择是使用纸张，但你会受到手动计算的限制。计算器会更好，但你需要知道如何操作更高级的功能。最快且最强大的选择是使用计算机，但你必须知道如何用它来编写和执行代码。

这是一个设计智能体的有用框架。你希望给它一些根据自身能力定制的工具。但你如何知道这些能力是什么呢？你需要关注、查看它的输出并进行实验。你学会像智能体一样思考。

以下是我们在开发 Claude Code 时关注 Claude 所学到的一些经验教训。

### 改进信息提取与 AskUserQuestion 工具

![Image](https://pbs.twimg.com/media/HCLxg2JbsAA3Ag_?format=jpg&name=large)

开发 AskUserQuestion 工具时，我们的目标是提升 Claude 提问的能力（通常称为引导式提问）。

虽然 Claude 可以直接用纯文本提问，但我们发现回答这些问题似乎花费了过多不必要的时间。我们该如何降低这种沟通摩擦，提高用户与 Claude 之间的沟通带宽？

#### 尝试 #1 - 编辑 ExitPlanTool

我们首先尝试的是在 ExitPlanTool 中添加一个参数，以便与计划一同包含一组问题数组。这是最容易实现的，但这让 Claude 感到困惑，因为我们同时请求了一个计划和一组关于该计划的问题。如果用户的回答与计划中所述的内容冲突怎么办？Claude 是否需要调用 ExitPlanTool 两次？我们需要另一种方法。

（你可以在我们关于提示缓存的文章中了解更多关于我们为什么开发 ExitPlanTool 的信息（

[我们关于提示缓存的文章](https://x.com/trq212/status/2024574133011673516)）

#### 尝试 #2 - 更改输出格式

接下来我们尝试修改 Claude 的输出指令，以提供一种略有修改的 Markdown 格式，使其能够用来提问。例如，我们可以要求它输出一个项目符号形式的问题列表，其中备选答案用方括号括起。然后我们可以解析并格式化该问题，作为用户界面呈现给用户。

尽管这是我们能做的最通用的改动，Claude 甚至似乎能够胜任输出这个内容，但这无法保证。Claude 会添加额外的句子、省略选项，或者完全使用不同的格式。

#### 尝试 #3 - AskUserQuestion 工具

![Image](https://pbs.twimg.com/media/HCL0gcObkAA4tKt?format=jpg&name=large)

最后，我们决定创建一个 Claude 随时可以调用的工具，但特别在规划模式下会被提示这样做。当工具被触发时，我们会显示一个模态框来显示问题，并阻止代理的循环直到用户回答。

这个工具让我们能够提示 Claude 生成结构化输出，并且帮助我们确保 Claude 为用户提供了多种选择。它还为用户提供了实现该功能的方法，例如在 Agent SDK 中调用它，或者在技能中引用它。

最重要的是，Claude 似乎喜欢调用这个工具，我们发现它的输出结果效果很好。即使是设计最精良的工具，如果 Claude 不理解如何调用它，也无法正常工作。

这是 Claude Code 中提示方式的最终形式吗？我们不确定。如你在下一个示例中所见，适用于一个模型的方法可能并不适用于另一个模型。

### 更新功能 - 任务 &amp; 待办事项

![Image](https://pbs.twimg.com/media/HCLxrfXbEAUXwRV?format=jpg&name=large)

当我们首次推出 Claude Code 时，我们意识到该模型需要一个待办事项列表来保持其按计划推进。待办事项可以在开始时记录，并在模型执行工作时标记为已完成。为实现这一点，我们为 Claude 配备了 TodoWrite 工具，该工具可以编写或更新待办事项并向用户展示。

但即便如此，我们经常看到 Claude 忘记它该做什么。为了适应，我们每 5 轮插入一次系统提醒，这些提醒会提醒 Claude 它的目标。

随着模型的改进，它们不仅不再需要被提醒待办事项列表，反而会觉得它有局限性。收到待办事项列表的提醒让 Claude 觉得它必须严格遵循这个列表，而不是修改它。我们还看到 Opus 4.5 在使用子代理方面也有了很大进步，但子代理如何在共享的待办事项列表上进行协调呢？

看到这一点，我们将 TodoWrite 替换为任务工具（

[阅读更多关于任务](https://x.com/trq212/status/2014480496013803643)）。而待办事项（Todos）是为了让模型按计划推进，任务则更多是为了帮助智能体之间进行交流。任务可以包含依赖关系，在子智能体之间共享更新，并且模型可以修改和删除它们。

随着模型能力的提升，你们的模型曾经需要的工具现在可能会限制它们。重要的是要不断重新审视关于需要哪些工具的先前假设。这也是为什么坚持使用一小部分具有相当相似能力特征的模型来支持是有用的。

### 设计搜索界面

对于 Claude 来说，特别重要的一组工具是可以用来构建其自身上下文的搜索工具。

当 Claude 首次推出时，我们使用 RAG 向量数据库为 Claude 查找上下文。虽然 RAG 功能强大且速度快，但它需要索引和设置，并且在多种不同环境中可能会很脆弱。更重要的是，Claude 被给予了这个上下文，而不是自己查找上下文。

但是如果 Claude 能在网上搜索，为什么不能搜索你的代码库呢？通过给 Claude 一个 Grep 工具，我们可以让它搜索文件并自行构建上下文。

这是我们观察到的一种模式：随着 Claude 变得更聪明，如果它得到合适的工具，它在构建上下文方面会变得越来越擅长。

当我们引入代理技能时，我们将渐进式披露的理念正式化，这使代理能够通过探索逐步发现相关上下文。

Claude 可以读取技能文件，而这些文件又可以引用模型递归读取的其他文件。事实上，技能的一个常见用途是为 Claude 添加更多搜索能力，比如给它提供如何使用 API 或查询数据库的指令。

在过去的一年中，Claude 从不太能够构建自己的上下文，转变为能够在几层文件中进行嵌套搜索，以找到所需的精确上下文。

渐进式展示现在是我们常用的一种无需添加工具即可添加新功能的技术。

### 渐进式披露 - Claude 代码指南代理

Claude Code 目前拥有大约 20 个工具，并且我们不断地问自己是否需要所有这些工具。添加新工具的门槛很高，因为这会给模型多一个需要考虑的选项。

例如，我们注意到 Claude 对如何使用 Claude Code 了解不足。如果你问它如何添加一个 MCP 或者斜杠命令是什么，它将无法回复。

我们本可以将所有这些信息都放在系统提示中，但考虑到用户很少询问这些内容，这会增加上下文衰减并干扰 Claude Code 的主要工作：编写代码。

相反，我们尝试了一种渐进式展示的方式。我们给 Claude 提供了一个文档链接，它可以加载该链接以搜索更多信息。这种方法有效，但我们发现，Claude 为了找到正确答案，会加载大量结果到上下文中，而实际上你只需要答案本身。

因此，我们构建了 Claude Code Guide 子代理，当你询问关于它自己的问题时，Claude 会被提示调用这个子代理。这个子代理有关于如何有效搜索文档以及返回什么内容的详细指令。

虽然这并非完美，但当你询问 Claude 如何进行自我设置时，它仍然可能会困惑，不过它已经比以前好多了！我们能够在不添加新工具的情况下，向 Claude 的操作空间中添加内容。

#### 一门艺术，而非一门科学

如果你期望得到一套关于如何构建你的工具的严格规则，很遗憾，本指南并非如此。为你的模型设计工具既是一门科学，也是一门艺术。这在很大程度上取决于你使用的模型、智能体的目标以及它所处的环境。

多做实验，审视你的输出，尝试新事物。像代理一样观察。

#### 主旨概括

这篇文章主要讲的是：构建 AI Agent 最难的地方之一，不是“多加工具”，而是设计出真正适合模型能力的“动作空间”。作者结合开发 Claude Code 的实践说明，做工具设计不能只靠理论，而要通过持续观察模型表现、反复实验，学会“像智能体一样思考”。

#### 1. 工具设计的核心难题：动作空间怎么定

- 构建 Agent 时，一个关键问题是：到底该给模型什么工具。
- Claude 可以通过多种方式行动，比如 `bash`、技能（skills）、代码执行等，因此设计者需要决定：
  - 是只给 1 个通用工具；
  - 还是给 50 个针对不同场景的工具。
- 作者用“解数学题”打比方：
  - 只有纸笔：能做，但效率低，受限于手算；
  - 有计算器：更强，但要会用高级功能；
  - 有电脑：最强，但前提是你会写代码并执行。
- 对 Agent 也是一样：工具要和模型本身能力匹配，不能只看“理论上能做什么”，而要看“模型实际上会不会用”。

#### 2. 一个重要方法：通过观察输出，理解模型能力

- 作者认为，设计工具前，必须先搞清楚模型真实擅长什么。
- 做法不是空想，而是：
  - 观察模型输出；
  - 分析它在哪些地方容易出错；
  - 针对这些问题做实验。
- 核心思想是：不要只从人的角度设计，而要尽量站在模型的角度思考问题。
- 这也是文章标题里“像智能体一样观察”的含义。

#### 3. 案例一：为了让 Claude 更会提问，团队做了 `AskUserQuestion` 工具

这一部分讲的是：团队想提升 Claude 向用户提问、收集信息的能力，最后发现专门做一个工具，比靠普通文本输出更可靠。

##### 3.1 目标：减少沟通摩擦，提高问答效率

- 虽然 Claude 原本就能直接用自然语言提问，但团队发现：
  - 这种方式常常让回答过程变慢；
  - 用户和模型之间的沟通成本偏高。
- 所以他们想找到一种方法，让 Claude 更高效地向用户发问，并拿到结构化回答。

##### 3.2 尝试 1：在 `ExitPlanTool` 里顺带塞问题

- 第一种做法是在 `ExitPlanTool` 中增加一个参数，把问题数组和计划一起输出。
- 优点：实现最简单。
- 但问题很快出现：
  - 模型同时要给计划、又要提关于计划的问题，容易混乱；
  - 如果用户回答与原计划冲突，不知道该怎么处理；
  - 甚至可能需要再次调用工具。
- 结论：把“规划”和“提问”绑定在一起，不合适。

##### 3.3 尝试 2：靠特殊 Markdown 输出格式提问

- 第二种做法是修改 Claude 的输出要求，让它生成一种特殊 Markdown。
- 比如：
  - 用项目符号列问题；
  - 用方括号表示备选答案；
  - 然后前端去解析并展示成 UI。
- 这看起来更通用，但不稳定：
  - Claude 可能会多写一句话；
  - 可能漏掉选项；
  - 也可能完全换一种格式。
- 结论：只靠提示词约束格式，不够可靠。

##### 3.4 尝试 3：单独做 `AskUserQuestion` 工具

- 最终方案是新增一个 `AskUserQuestion` 工具。
- 特点是：
  - Claude 可以随时调用；
  - 在规划模式下会被特别鼓励使用；
  - 工具触发后，界面会弹出模态框；
  - Agent 循环会暂停，直到用户回答。
- 这样带来的好处有：
  - 可以强制生成结构化输出；
  - 能确保问题带有多个可选项；
  - 用户交互更明确；
  - 也方便在 Agent SDK 或技能中复用。
- 作者特别强调一点：不仅工具本身要设计得好，还要让 Claude “愿意用、会用”。因为如果模型不理解如何调用，再好的工具也没意义。

#### 4. 案例二：从 `TodoWrite` 到“任务工具”，说明模型变强后旧工具可能反而成限制

这一部分的重点是：工具不是越稳定越好，模型能力变化后，原本有帮助的工具，可能会变成束缚。

##### 4.1 最初为什么需要待办事项工具

- Claude Code 刚推出时，团队发现模型容易“忘记自己要做什么”。
- 因此给它加了 `TodoWrite` 工具，让它：
  - 记录待办事项；
  - 工作过程中逐步标记完成；
  - 把进度展示给用户。
- 即便如此，模型还是会跑偏。
- 为了纠正它，团队甚至每隔 `5` 轮就插入一次系统提醒，反复告诉它当前目标。

##### 4.2 后来为什么待办事项反而成了问题

- 随着模型能力提升，这种提醒和待办机制开始出现副作用：
  - 模型会把待办列表看得过于死板；
  - 更倾向于“照单执行”，而不是主动修改计划；
  - 灵活性下降。
- 同时，作者提到 `Opus 4.5` 在使用子代理方面进步很大。
- 这时新的问题出现了：
  - 如果多个子代理协同工作，它们怎么共享同一个待办列表？
  - 传统待办工具不适合多智能体协作。

##### 4.3 为什么改成“任务工具”

- 团队后来把 `TodoWrite` 换成了“任务工具”。
- 两者区别是：
  - `Todos` 主要是让模型按计划推进；
  - `Tasks` 更适合让多个智能体之间传递信息和协作。
- 任务工具支持：
  - 依赖关系；
  - 子智能体之间共享更新；
  - 模型自由修改和删除任务。
- 结论是：模型能力增强后，工具设计也必须跟着更新。过去必须依赖的工具，未来可能会限制模型发挥。

#### 5. 案例三：搜索工具的设计，关键是让 Claude 自己构建上下文

这一部分强调：对 Claude 来说，搜索类工具非常重要，因为它们决定了模型能否自己“找到信息”，而不是被动接收信息。

##### 5.1 从 RAG 到 `Grep`：从“喂上下文”变成“自己找上下文”

- Claude 刚推出时，团队使用的是 RAG 向量数据库来提供上下文。
- RAG 的优点：
  - 功能强；
  - 速度快。
- 但缺点也明显：
  - 需要提前索引和配置；
  - 在不同环境下容易脆弱；
  - 更重要的是，Claude 是“被给予上下文”，而不是“自己查找上下文”。
- 团队后来想到：如果 Claude 能搜网页，为什么不能搜代码库？
- 于是他们给 Claude 提供了 `Grep` 工具，让它直接搜索文件内容，自行构建上下文。
- 这代表了一个重要转变：随着模型变强，只要工具合适，它会越来越擅长自己收集信息。

##### 5.2 渐进式披露：让上下文按需出现

- 在加入 Agent 技能后，团队把“渐进式披露（progressive disclosure）”正式化。
- 这种方式的意思是：
  - 不一开始塞给模型全部信息；
  - 而是让它通过探索，逐步发现需要的上下文。
- 技能文件可以：
  - 被 Claude 读取；
  - 再引用其他文件；
  - 实现递归式搜索。
- 一个常见用法是：
  - 在技能里给 Claude 补充更多搜索能力，
  - 比如教它怎么用某个 API，或者怎么查询数据库。
- 作者总结说，过去一年里，Claude 已经从“不太会自己构建上下文”，发展到“可以跨好几层文件嵌套搜索，找到精确所需信息”。
- 因此，渐进式披露成为一种很常用的方法：很多时候，不需要新增工具，也能增加新能力。

#### 6. 案例四：不用新工具，也能扩展能力——Claude Code Guide 子代理

这部分讲的是一个非常具体的例子：当 Claude 不懂“如何使用 Claude Code 自己”时，团队并没有直接加新工具，而是用子代理解决问题。

##### 6.1 问题：Claude 不太懂自己的使用方法

- 团队发现，Claude 对 Claude Code 的一些自我使用知识掌握不足。
- 比如用户问：
  - 怎么添加 MCP；
  - 斜杠命令是什么。
- Claude 往往答不上来。

##### 6.2 为什么不把这些内容全塞进系统提示

- 一个简单办法是：把这些帮助文档全塞进系统提示里。
- 但这样会带来问题：
  - 用户很少问这些问题；
  - 却会长期占用上下文；
  - 导致上下文衰减；
  - 干扰 Claude Code 最重要的任务——写代码。

##### 6.3 先试文档链接，再做子代理

- 他们先试了一种渐进式方式：
  - 给 Claude 一个文档链接；
  - 需要时让它自己加载和搜索。
- 这招虽然有效，但也有副作用：
  - 为了找到正确答案，Claude 往往会把很多搜索结果都加载进上下文；
  - 其实最终只需要那个答案本身。
- 所以后来他们构建了 `Claude Code Guide` 子代理。
- 当用户问的是“关于 Claude Code 本身怎么用”的问题时，主 Claude 会被提示去调用这个子代理。
- 这个子代理有更明确的专用指令，比如：
  - 如何高效搜索文档；
  - 应该返回什么内容。
- 效果是：
  - 虽然还不完美；
  - 在“自我设置”类问题上偶尔仍会困惑；
  - 但比以前明显更好了。
- 关键点在于：他们没有增加新工具，却通过子代理扩展了操作空间。

#### 7. 最后的结论：工具设计没有固定公式，更像一门艺术

- 作者最后明确表示：这篇文章不是在给出一套死板规则。
- 为模型设计工具，既有科学的一面，也有艺术的一面。
- 它高度依赖：
  - 你用的是什么模型；
  - 智能体要完成什么目标；
  - 它所处的环境是什么。
- 因此最重要的建议是：
  - 多实验；
  - 多看输出；
  - 多尝试新方法；
  - 像智能体一样去观察。

#### 8. 可以怎么理解这篇文章：一个通俗例子

- 可以把 Agent 想成一个新入职的助手。
- 你不是给它越多工具越好，而是要给它“它真正会用、而且用起来顺手”的工具。
- 比如：
  - 如果它总是问问题问不清楚，那就给它一个专门的提问模板或问答界面；
  - 如果它老忘记任务，就先给待办工具；
  - 但等它变聪明了，待办工具又可能让它太死板，这时就要升级成更灵活的任务系统；
  - 如果它找资料能力变强，就不要一开始把所有资料都塞给它，而是让它自己按需搜索。
- 这正是全文最核心的观点：工具设计要随着模型能力演化，而不是一劳永逸。
