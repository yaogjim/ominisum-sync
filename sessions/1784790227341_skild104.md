## 分析要点

- **核心高价值点**：Agent能力增强后，真正的交付杠杆不是继续压缩编码时间，而是将跨职能判断前置并沉淀为清晰、可测试、受架构约束的功能包。
- **留存建议**：建议精读并存档，作为设计AI原生交付流程和团队协作模式的参考框架（文章提供了从业务上下文、用户旅程、规格、设计、架构到Agent构建的完整交付管道，并明确了人机分工、阶段产物和组织方式，具有较强复用价值。）

**知识要点**

- AI原生交付的主要瓶颈会从工程吞吐量迁移到业务上下文、规格质量、设计正确性、架构适配性与验证能力。
- 富集管道依次将想法转化为领域上下文、用户旅程、可测试规格、设计、架构方案和可执行功能包，上游质量会降低下游返工。
- “聚集—富集—散开”模式让跨职能团队集中完成判断与对齐，随后由构建经理监督Agent执行，并仅在异常或关键决策处升级给人类。

**行动项**

- 选择一个功能试点，建立包含领域上下文、用户旅程、规格、设计和架构说明的统一功能包。
- 在Agent构建前设置人工批准、确定性检查、测试、架构约束和异常升级关卡。
- 分别记录规格、设计、架构和构建阶段耗时及阻塞原因，用阶段数据定位新的交付瓶颈。

## 正文

**yibie**

推荐这篇文章，作者 Jason Vertrees 是 Heavy Chain Engineering 的创始人，帮助中低端市场的垂直 SaaS 公司和 PE 机构将零散的 AI 使用转化为可度量的交付杠杆（85% 更快的功能交付速度）。这篇文章提出了一个核心观点：当团队有了能打的 AI agent 后，组织工作的方式必须改变——瓶颈不再是工程师敲代码的速度，而是需求清晰度、规格质量、设计正确性和架构适配性。他把他做的方法论和工具集 ETC 完整讲了一遍，对正在思考如何系统化用 AI 做交付的团队非常有参考价值。

预先声明：这篇文章是我对自己一年半前预测并在当前工作中观察到的现象的反思。随着我们在 AI 转型过程中学到更多，这些想法可能会成熟和改变。

大约一年半前我做了一个赌注：一旦软件团队有了真正能打的 AI agent，他们组织工作的方式就必须改变——不只是工具本身，还有团队形态和工作顺序。那个未来现在已经到来。过去几个月我一直在构建我对这个问题的答案，并与真实团队一起在同一个房间里推出。这是我看到的，到目前为止，它与预测高度吻合。

AI 通常被宣传为让个体开发者更快的方法。它确实做到了。但更大的影响在于团队应该如何组织工作。

在软件历史的大部分时间里，我们的交付方法都围绕一个假设构建：人类做工作，所以约束是人类吞吐量。瀑布、Scrum、看板——不同形状，相同底层前提。组织人，移动工单，管理队列，因为人是做构建的那个。

一旦团队有了能打的、有 harness 的 agent，那个前提就不再成立，你组织工作的方式也必须随之改变。这不是减少流程的论点；这是更多纪律的论点。没有纪律地放任 agent，它们会增加熵：它们产出更多、更快、朝向更多方向、共享理解更少，这就是更高速度下的混乱。纪律是将这种原始速度转化为可持续交付的东西。目标不是消除流程，而是围绕不同的约束重新设计它。

旧模型是为不同瓶颈而建的

公平地看待我们正在超越的方法，因为每个都解决了一个真实问题。

瀑布在前端集中规划，然后按顺序执行。弱点在于反馈到达太晚，通常在修正已经变得昂贵之后。

Scrum 和更广泛的敏捷运动是对此的纠正。它们缩短了反馈循环，围绕迭代交付组织人类团队，这是真正的改进。问题是很多团队把它变成了什么：sprint 计划、梳理、站会、回顾、工单和大量消耗协调精力但不一定产生多少杠杆的仪式。仪式比意义活得更久。

看板可视化流程并限制在制品，这很有用。但它管理队列；它不提高进入队列的内容质量。

三者都为一个人类手工完成大部分工作的世界而建，并假设瓶颈是工程容量。AI 原生的工程移动了瓶颈。当 agent 可以承担大部分构建工作，限制因素不再是人们打字多快。它变成了业务上下文的清晰度、规格的质量、设计的正确性、架构适配性、约束的强度、验证的质量，以及你让 agent 保持轨道的能力。

这就是一切归结到的转变。

软件交付是富集管道

把软件交付想象成一个富集管道，就像原材料变成成品的过程。

软件从原材料开始：一个半成型的想法。然后它一步步被富集。业务上下文澄清想法。领域理解将其落地。用户旅程将其转化为行为。规格说明将其转化为可构建和可测试的东西。低保真然后高保真设计将其转化为体验。架构将其转化为技术方案。那个方案变成可构建的工作单元，再变成可运行的软件，加上发布说明、度量和伴随的产物。

每一步都在增加价值。坏主意变成更清晰的主意，更清晰的主意变成规格，规格变成设计，设计变成架构，架构变成 agent 可以构建的东西。

这个框架重要的原因是管道有瓶颈，改善上游步骤会让每个下游步骤更简单。这一个属性就是全部策略。

比你所习惯的更激进地左移

传统团队倾向于在后期迭代。他们在实现过程中发现模糊性，在审查时争论需求，在代码已经存在之后才发现架构问题。每一个都是下游浮现的上游问题，在修正成本最高的地方。

AI 原生的做法是反向推进，比大多数团队所习惯的更激进。在前端花更多精力——在上下文、规格、设计和架构上——这样这些问题在构建开始前就已解决。

这不是关于减速；重点是让构建阶段几乎无聊。当 agent 运行构建时，昂贵的错误不再是写得慢。昂贵的错误是让不清晰的思考到达构建阶段，因为 agent 会忠诚地以高速度、完全自信地构建错误的东西。

ETC：将这套方法变成可重复流程

我们把流程和运行它的工具都构建了出来，并将整个东西命名为 ETC——Enter the Chat，我们读作"Etsy"。ETC 同时是两样东西。它是一个框架：流程本身，融入其中的观点，以及 AI 原生产品生命周期应遵循的步骤序列。它也是我构建来运行那个流程的自定义工具——一个带确定性钩子、检查和关卡的 agent harness，让工作保持在轨道上。

它从初始化开始。在任何功能之前，harness 帮助团队写下这个项目实际是什么：一个领域描述、一个项目描述，以及——对现有系统——对当前架构、惯例和行为的真实发现遍历。重要的部分是它怎么处理这些。它不是检查代码库然后悄悄猜测。它把发现带回来让你批准。如果你的 DTO 分布在五个不同位置，它不会替你选一个；它会问哪个惯例是权威的，然后把它写下来。一旦批准，上下文被组织、记录并锁定，这样每个 agent 都在同一个操作模型下工作。

从那开始，工作通过管道推进，每次一个被富集的产物。旅程阶段定义谁在使用系统、他们试图完成什么、价值在哪里显现、以及可能在哪里失败。规格阶段运行规格驱动开发，收敛于该构建什么——不是一张工单，而是一个清晰、可测试的、反映公司真实需求的规格。然后是低保真设计探索流程和结构，高保真设计让预期体验具体化，以及一个架构阶段，工程主导可行性、集成边界、数据形态和实现策略，产品和设计仍在场。

功能包是流程在工作的最开始就分配的一个目录，随着工作推进被富集。每个阶段把它的发现写入功能包——领域上下文、旅程、规格、设计、架构。到架构阶段完成时，功能包包含了足够的业务上下文、产品意图、设计方向和架构指导，构建可以在几乎没有任何遗留模糊性的情况下进行。

然后构建运行。如果上游工作做得好，没有人需要盯着每次按键。一个人作为构建经理行动。他们监督运行、审查进度和处理升级。当系统碰到问题或一个它不应该自己做的决定时，它停下并将此刻呈现给人类，而不是继续推进。

新的团队形态：聚集、富集、散开

描述团队形态变化的最清晰方式是三个词：聚集、富集、散开。

聚集。 团队在专注的工作会议中聚在一起，通常通过视频——产品、设计、工程和业务利益相关者在同一个地方。他们定义问题，磨锐规格，压力测试假设，并就正在构建什么达成一致。这通常需要一到三天的非全职投入。

富集。 想法通过管道推进，每个阶段改善产物。领域上下文富集想法，旅程富集对用户的理解，规格富集产品定义，设计富集体验，架构富集实现路径。功能包在每一步都变得更有价值。

散开。 一旦功能包准备就绪，团队散开。大部分成员返回其他有用工作。构建经理留在 agentic 构建旁边。

这就是运营模型变化的一句话总结：人不会消失，他们把自己的判断集中在对的地方，然后在机器可以执行时停止制造阻力。

为什么高管获得更好的可见性

对领导者的承诺不是"我们的开发者用 AI"。而是交付系统变得更加可度量、可重复、更容易改进。

传统交付给领导者的信号很模糊：故事点、sprint 速率、工单计数、主观状态、"快做完了"、"被阻塞了"、"需要 QA"。管道模型给你更扎实的东西。你可以看到规格花了多长时间，设计花了多长时间，架构花了多长时间，构建花了多长时间，以及这次瓶颈移到了哪里。

这会转化成真正的改进循环。如果这次设计花了 12 小时而上一次是 15 小时，你可能在变得更好。如果架构阶段持续膨胀，代码库可能隐藏了值得处理的复杂度。如果构建反复卡住，规格可能很弱或架构没有很好文档化。这些是你可以用来指导的运营数据，不是状态会议上的印象。

为什么团队在一起变得更好

当我观察一个团队一起处理领域、规格、设计和架构时，他们建立共享理解。他们在实现压力压上来之前解决难题。他们看到彼此如何思考。这建立信任，并产生更多真正成功的尝试。

成功改变了团队的行为方式。当流程感觉更容易、更可靠，人们更愿意再次使用它。工作感觉不那么混乱，协作开始产生可见的结果，人们倾向于投入而非回避。这不是锦上添花的附带品：对工作方式感觉良好的团队倾向于做出更好的工作，做出更好的工作又让他们对流程感觉更好。它会复利。

构建质量呢？

细心的读者已经准备好了明显的异议：你怎么知道生成的构建是好的？那正是正确的问题，但这篇文章不是讲这个的。这篇是关于 AI 如何改变工作组织——团队在哪里花时间、产物如何被富集、瓶颈如何移动、领导如何获得可见性。

答案的简短版本是质量不来自信任 agent。它来自执行：确定性检查、规格执行、架构约束、测试、审查关、发布验证。我在别处写过大量关于这个执行侧的内容，把它内建也正是 ETC 存在的很大原因。

Enter the Chat

ETC 这个名字——Enter the Chat——来自同一个关于软件工作未来走向的赌注：它将越来越像人们进入一个共享的对话工作空间，做他们那部分，然后离开。产品负责人进入澄清意图。设计师进入塑造体验。工程师进入定义架构。构建经理进入监督执行。agent 进入做专业工作。人们在需要时加入，贡献他们的判断，在他们部分完成后退出。

ETC 是为那个世界构建的。它把"聊天"从一个人们交谈的非正式场所，转变为一个工作真正被交付的被治理环境。

要点

AI 原生交付不是替代团队。是围绕人们创造最大杠杆的部分重新组织团队。人类最擅长判断、上下文、品味、权衡、业务理解和共享意义。agent 越来越擅长执行、转换、脚手架和产生产物。错误是强迫两者进入一个为两者都不设计的工作流。机会是设计一个匹配的。

ETC 是我们对那个问题的答案：聚集正确的人，把想法富集成可构建的功能包，让被治理的 agent 执行，由人类监督。这就是我一年半前赌注的形状，也是我现在把它放在真实团队面前时看到的形状。软件工作的未来看起来不那么像工单工厂，而更像一场导致代码的有纪律的对话。

## 结构化（1）

### 2026-07-23 07:03:47

#### 文章总结：AI 原生时代，软件团队应如何重新组织工作

当 AI Agent 能承担大部分编码任务后，软件交付的瓶颈就从 “写代码的速度” 转向了**需求、规格、设计、架构和验证的质量**。作者主张用更严格的前置规划与治理流程组织人机协作，让人类集中负责判断，让 Agent 高速、受控地执行。

##### 1. AI 改变的不只是开发效率，更是团队组织方式

- 作者约在**一年半前**提出判断：一旦团队拥有真正可用、受工具框架约束的 AI Agent，工作流程、团队结构和执行顺序都必须改变。
- AI 的确能让个人开发者更快，但更深层的影响是：传统软件流程赖以成立的前提 ——“人类是主要执行者，工程产能是瓶颈”—— 正在失效。
- Agent 可以快速生成大量成果，但如果缺乏统一上下文和约束，也会更快地制造混乱与返工。
- 因此，AI 原生开发并不意味着 “减少流程”，而是需要**更强的纪律、检查和治理**，把 Agent 的原始速度转化为稳定交付能力。

##### 2. 传统方法解决的是 “人类产能不足”

作者回顾了三种主要的软件交付方法：

- **瀑布模式**：前期集中规划、后续依次执行，但反馈太晚，发现错误时修改成本已经很高。
- **Scrum／敏捷**：通过短周期迭代改善反馈速度，但不少团队最终陷入 Sprint 计划、站会、工单梳理和复盘等仪式，协调成本高，实际杠杆有限。
- **看板**：能够可视化流程并限制在制品，但主要解决队列管理问题，无法提高进入队列的需求质量。

这些方法都假设大部分工作由人手完成，因此把 “工程师产能” 视为核心约束。但在 Agent 承担大量构建工作后，真正的瓶颈变成：

- 业务背景是否清晰；
- 规格是否明确、可测试；
- 设计是否正确；
- 架构是否适配现有系统；
- 约束和验证是否足够强；
- Agent 能否始终在正确轨道上运行。

##### 3. 将软件交付视为一条 “富集管道”

作者把软件交付比作原材料逐步变成成品的过程：

> 半成型想法 → 业务与领域背景 → 用户旅程 → 可测试规格 → 低／高保真设计 → 技术架构 → 可构建任务 → 可运行软件及发布产物

每一步都在给最初的想法增加信息和价值：

- 业务背景让想法更清楚；
- 用户旅程把想法转化为具体行为；
- 规格把需求变成可构建、可验证的定义；
- 设计明确用户体验；
- 架构确定技术实现路径；
- 最终形成 Agent 可以准确执行的工作包。

核心策略是：**越早解决问题，后续步骤越简单。**上游产物质量越高，Agent 在构建阶段越不容易走偏。

##### 4. 比传统 “左移” 更激进：让构建变得无聊

传统团队经常在后期才暴露前期问题：

- 编码时才发现需求模糊；
- 代码审查时才争论业务要求；
- 实现完成后才发现架构不合适。

这些本质上都是 “上游问题在下游出现”，而此时修正成本最高。

AI 原生方式要求把更多精力投入构建之前，优先解决：

1. 业务与领域上下文；
2. 需求规格；
3. 交互和视觉设计；
4. 架构与集成方案。

这样做不是为了放慢速度，而是为了让构建阶段几乎 “无聊”——Agent 只需按照明确方案执行。因为 AI 时代最昂贵的错误不再是 “代码写得慢”，而是 Agent **高速、自信地构建了错误的东西**。

##### 5. ETC：把方法转化为可重复的流程和工具

作者将这套方法命名为**ETC（Enter the Chat，读作 “Etsy”）**。它同时包括：

- 一套 AI 原生产品交付框架；
- 一个带确定性钩子、检查和关卡的 Agent Harness，即约束和管理 Agent 的执行工具。

###### 5.1 初始化：先建立统一事实

在开发任何功能之前，ETC 会帮助团队明确：

- 项目和业务领域是什么；
- 现有系统的真实架构；
- 代码库的惯例和行为方式；
- 哪些约定才是团队认可的标准。

工具不会扫描代码库后自行猜测。例如，如果 DTO 分散在五个位置，它不会随意选择一种写法，而是把发现交给团队，由人类确认哪个惯例具有权威性。

确认后，这些上下文会被记录并锁定，使后续所有 Agent 都基于同一套事实工作。

###### 5.2 逐步形成 “功能包”

每项功能都会获得一个持续被补充的目录，即 “功能包”，依次纳入：

1. 领域和业务背景；
2. 用户角色、目标、价值与失败路径；
3. 清晰、可测试的需求规格；
4. 低保真流程和结构设计；
5. 高保真体验设计；
6. 架构、数据形态、集成边界及实现策略。

架构阶段完成后，功能包应已经包含足够的业务意图、产品定义、设计方向和技术指导，使构建阶段几乎不再遗留重大歧义。

###### 5.3 受监督的 Agent 构建

构建开始后，无须有人盯着 Agent 的每次操作，只需由一名**构建经理**负责：

- 监督运行；
- 检查进度；
- 处理异常升级；
- 在关键决策点介入。

当 Agent 遇到问题，或需要做不应自行决定的判断时，系统应暂停并交给人类，而不是擅自继续。

##### 6. 新团队形态：聚集、富集、散开

作者用三个词概括新的协作模式。

###### 聚集

产品、设计、工程和业务利益相关者集中参与工作会议，通常通过视频协作，共同：

- 定义问题；
- 澄清规格；
- 检验假设；
- 对 “究竟构建什么” 达成一致。

这一阶段通常需要**1～3 天的非全职投入**。

###### 富集

想法依次经过领域背景、用户旅程、规格、设计和架构等环节，每一步都提高功能包的完整度和可执行性。

###### 散开

功能包准备好后，大部分团队成员返回其他高价值工作，仅由构建经理监督 Agent 完成构建。

这并不是取消人类，而是把人的判断集中到最有价值的阶段；当机器可以可靠执行时，人类不再增加不必要的协调阻力。

##### 7. 管理层获得更真实的交付可见性

传统管理指标往往较模糊，例如：

- 故事点和 Sprint 速率；
- 工单数量；
- “快完成了”；
- “目前被阻塞”；
- “还需要 QA”。

富集管道则能直接观察每个阶段的耗时与瓶颈，包括规格、设计、架构和构建时间。

例如：

- 本次设计耗时**12 小时**，上次为**15 小时**，可能表明设计流程正在改善；
- 如果架构阶段持续膨胀，可能说明代码库存在隐藏复杂度；
- 如果构建阶段反复卡住，可能是规格质量不足，或现有架构缺乏文档。

这些数据可以用于持续改进，而不只是依赖状态会议中的主观描述。

##### 8. 集中协作还能形成团队复利

产品、设计、工程和业务人员共同处理领域、规格、设计与架构时，会：

- 在编码压力出现前解决困难问题；
- 建立共享理解；
- 了解彼此的判断方式；
- 提高信任和首次交付成功率。

当流程变得更可靠、混乱更少时，成员会更愿意继续采用它；更多成功又会增强团队对流程的信心，形成正向循环。

##### 9. 构建质量不能靠 “相信 Agent”

作者强调，生成代码的质量不来自对 Agent 的信任，而来自严格执行，包括：

- 确定性检查；
- 规格约束；
- 架构约束；
- 自动化测试；
- 人工审查关卡；
- 发布后的验证。

本文重点是团队组织方式，而 ETC 工具的重要价值之一，就是把这些质量控制机制嵌入 Agent 的执行流程。

##### 10. 最终结论：从 “工单工厂” 转向 “有纪律的对话”

“Enter the Chat” 代表一种新的工作方式：

- 产品负责人进入共享空间澄清意图；
- 设计师进入并塑造体验；
- 工程师定义架构；
- 构建经理监督执行；
- Agent 完成专业化构建工作；
- 每个人在需要时加入，贡献判断，完成后退出。

AI 原生交付并非替代团队，而是重新分配人和机器的优势：

- **人类擅长**：判断、上下文理解、品味、权衡、业务认知和建立共同意义；
- **Agent 擅长**：执行、转换、搭建脚手架和批量产出。

作者所在的 Heavy Chain Engineering 宣称，这套方法可实现**功能交付速度提升 85%**，将原本需要**6～8 周**的项目压缩到数天；其官网案例还描述了 “约两个月的功能在一周内上线”，但实际效果会因团队和代码库而异。

文章最终认为，未来的软件工作将不再像围绕工单运转的流水线，而更像一场**有统一上下文、明确关卡、最终产出代码的受治理对话**。

## 通俗精炼（1）

### 2026-07-23 07:13:02

#### AI 原生软件交付：瓶颈正从 “写代码” 转向 “把事情想清楚”

##### 核心观点

当 AI Agent 已能承担大量编码工作，软件交付的主要瓶颈就不再是工程师的开发速度，而是：

- 业务背景是否清晰
- 需求与规格是否完整、可测试
- 设计是否正确
- 架构是否适配
- 约束和验证机制是否可靠

AI 可以高速执行，但也会高速放大模糊需求和错误决策。因此，AI 原生交付不是减少流程，而是把纪律和投入更集中地放到上游。

##### 从 “人力流水线” 转向 “价值富集管道”

瀑布、Scrum、看板都默认 “人是主要生产力”，重点是管理人员、工单和队列。

作者提出，应把软件交付理解为一条逐步富集的管道：

> 模糊想法 → 业务上下文 → 用户旅程 → 可测试规格 → 交互设计 → 技术架构 → 可执行任务 → 软件与发布产物

每个阶段都要减少下一阶段的不确定性。上游越清晰，AI 在下游执行得越快、返工越少。

##### ETC：一套 AI 原生交付流程

作者构建了 ETC（Enter the Chat），它既是一套方法论，也是一套带检查、关卡和确定性约束的 Agent Harness。

其主要流程包括：

1. **初始化项目上下文**：明确领域、项目目标、现有架构与开发惯例，并由人确认，而非让 AI 自行猜测。
2. **定义用户旅程**：明确用户、目标、价值和可能的失败点。
3. **形成可测试规格**：把需求从 “工单” 升级为清晰、可构建、可验证的规格。
4. **完成设计与架构**：依次推进低保真、高保真设计，以及数据、集成和实现方案。
5. **生成 “功能包”**：沉淀业务、产品、设计和架构信息，尽可能消除构建前的歧义。
6. **Agent 执行构建**：由构建经理监督；遇到超出授权的决策时暂停并升级给人，而非自行推进。

##### 新的团队协作方式：聚集、富集、散开

###### 聚集

产品、设计、工程和业务人员集中协作，用一至三天澄清问题、压力测试假设并达成共识。

###### 富集

需求依次经过业务、用户、规格、设计和架构环节，逐步成为可直接执行的功能包。

###### 散开

前置决策完成后，大部分成员转向其他工作，仅由构建经理监督 Agent 执行。

本质上，人类把时间集中在判断、权衡、品味和业务理解上，把转换、脚手架和生产性执行交给 AI。

##### 对管理层的价值

传统交付常依赖故事点、工单数、Sprint 速率和主观进度汇报。ETC 则可以分别衡量规格、设计、架构和构建阶段的耗时与阻塞点。

这让管理者能够识别真正的问题：

- 设计周期过长，可能是产品定义不清
- 架构阶段持续膨胀，可能是系统复杂度过高
- 构建频繁中断，可能是规格不足或架构缺乏文档
- Agent 产出返工较多，可能是上游约束和验证机制薄弱

交付管理由 “追踪忙碌程度” 转向 “优化端到端系统”。

##### 质量并不来自 “相信 AI”

Agent 生成的代码是否可靠，不能依赖模型能力或主观信任，而要依靠工程化治理：

- 确定性检查
- 规格执行
- 架构约束
- 自动化测试
- 人工审查关卡
- 发布验证

AI 原生不等于无人管理，而是把人工介入从持续盯执行，改为定义规则、处理例外和验证结果。

##### 对产品与研发组织的启示

AI 带来的最大变化，不只是 “开发者写代码更快”，而是整个软件交付系统需要重构：

- 产品工作的核心将更偏向上下文、规格和决策质量
- 跨职能协作会前移，并以高密度方式集中发生
- 工单不再是核心载体，完整的 “功能包” 将更重要
- 工程角色会从亲自编码，部分转向架构定义和 Agent 监督
- 管理指标应从人力利用率，转向各阶段周期、返工率和阻塞原因

##### 总结

软件工作的未来，不再像一座围绕工单运转的 “人力工厂”，而更像一场受治理、有明确产物、最终生成代码的协作对话。

真正的竞争力不是 “有没有用 AI”，而是能否建立一套机制，把人的高质量判断转化为 Agent 可稳定执行、可验证、可持续改进的交付系统。

> 文中 “功能交付提速 85%”“数周项目数天完成” 属于作者及其公司的实践主张，实际效果仍取决于团队能力、代码库质量和业务复杂度。

## 口播总结（1）

### 2026-08-03 01:16:32

#### AI 原生时代，软件团队该怎样重新组织工作

这篇文章的核心观点是：当软件团队拥有真正能干活的 AI agent，也就是能够理解任务、调用工具并完成一系列软件工作的智能代理后，团队的主要瓶颈就不再是工程师写代码的速度，而是需求是否清楚、规格是否完整、设计是否正确，以及架构是否适合实现。接下来，我们会了解旧方法为什么不再完全适用，以及作者提出的 ETC 方法，如何把 AI 转化成更稳定、更可衡量的交付能力。

##### 一、AI 改变的，不只是工具，还有团队的工作方式

首先，作者在大约一年半前做了一个判断：一旦软件团队拥有真正能打的 AI agent，组织工作的方式就必须改变。

过去，人们通常把 AI 理解成一种“让单个开发者写代码更快”的工具。作者认为，这只是较小的一部分影响。更大的变化，是团队应该怎样分工、怎样协作，以及应该先做什么、后做什么。

在软件行业的大部分历史中，交付流程都建立在一个共同前提上：主要工作由人来完成，所以瓶颈是人的工作速度。瀑布式开发、敏捷开发，以及看板，虽然形式不同，但都在围绕人来安排任务、移动工单、管理工作队列。

但如果 AI agent 可以承担大部分构建工作，这个前提就不成立了。瓶颈会转移到新的地方，比如业务背景是否清楚，需求规格是否足够准确，产品设计是否合理，系统架构是否匹配，约束是否明确，以及最终的验证是否可靠。

这里有一个重要提醒：AI 速度越快，越不能放松管理。如果没有纪律地让 agent 自由发挥，它可能会更快地产出更多内容，但方向可能越来越分散，团队之间的共同理解也会越来越少。结果不是高效，而是更高速的混乱。

所以，AI 原生的重点不是取消流程，而是围绕新的瓶颈重新设计流程。

##### 二、瀑布、敏捷和看板，解决的是过去的问题

接下来，作者并没有简单否定传统方法。因为这些方法都曾经解决过真实的问题。

瀑布式开发的做法，是先在项目开始阶段集中规划，再按顺序执行。它的优点是前期安排比较完整，但缺点也很明显：反馈往往来得太晚。等到问题暴露时，很多工作已经完成，修正成本也变高了。

敏捷开发，特别是 Scrum，正是对这个问题的回应。它通过短周期迭代，让团队更快获得反馈。这个改进本身是有价值的。

但在很多公司里，敏捷后来变成了一整套固定仪式，包括迭代计划会、需求梳理会、每日站会、回顾会、工单管理，以及大量协调活动。时间久了，有些团队更关注仪式有没有完成，而不是这些活动是否真正帮助了交付。

看板则主要用于把工作流程可视化，并限制同时进行的任务数量。这能够帮助团队控制队列，避免工作堆积。但它解决不了另一个问题：进入队列的任务，本身是不是高质量的。

作者的判断是，这三种方法都诞生于一个“人类手工完成大部分构建工作”的时代。它们主要管理的是人的工程产能，而 AI 原生交付需要管理的是输入质量和决策质量。

也就是说，未来真正重要的问题可能不是“开发者写得够不够快”，而是“团队是不是在让 AI 高速地构建正确的东西”。

##### 三、软件交付，本质上是一条不断富集的管道

更重要的是，作者把软件交付比作一条“富集管道”。

这里的“富集”，可以简单理解为：一个原本模糊的想法，经过一系列步骤，不断增加背景、细节和约束，最后变成可以实际构建的软件。

软件通常从一个半成形的想法开始。接下来，业务背景会让这个想法变得更清楚；领域知识会让它贴近真实业务；用户旅程会说明用户要完成什么；规格说明会把想法转成可构建、可测试的要求；低保真和高保真设计会把产品体验具体化；架构设计则会把它变成一套可行的技术方案。

最后，这套方案会被拆成可以交给 agent 执行的工作单元，并进一步产出可以运行的软件、发布说明和相关度量。

这条管道的关键，在于每一步都应该增加价值。模糊的想法，变成清楚的问题；清楚的问题，变成明确的规格；规格再变成设计；设计再变成架构；架构最后变成 AI agent 可以执行的内容。

因为管道存在瓶颈，所以越早解决问题，后面的工作就越简单。上游做得越好，下游返工就越少。

##### 四、真正的“左移”，是在构建开始前解决问题

沿着这个思路，作者提出了一个比传统团队更激进的“左移”。

“左移”指的是把原本在开发后期才发现的问题，提前到流程前期解决。传统团队往往是在实现过程中发现需求不清楚，在评审时争论产品到底要什么，或者等代码已经写出来，才发现架构并不合适。

这些看似发生在下游的问题，其实大多来自上游思考不够清楚。更麻烦的是，等到构建开始以后才发现，修复成本已经很高。

AI 原生团队会在前期投入更多时间，重点打磨业务上下文、规格、设计和架构。目标不是让前期工作拖慢项目，而是让真正的构建阶段变得几乎“无聊”。

原因很简单：当 agent 写代码时，最昂贵的错误不再是代码写得慢，而是团队把一个模糊甚至错误的想法交给了 agent。agent 可能会以很高的速度、非常稳定地，把错误的东西完整构建出来。

所以，前期多花时间澄清问题，反而是为了让后面的自动化执行更快、更稳。

##### 五、ETC：把这套方法变成可重复的流程

为了落实这套理念，作者和团队建立了一套流程和工具，并把它命名为 ETC。

ETC 是“Enter the Chat”的缩写，读起来像英文单词“Etsy”。它同时代表两样东西。

第一，它是一套工作框架，也就是 AI 原生产品生命周期应该经历的步骤。第二，它是一套用来运行这些步骤的工具。这个工具可以理解成一个带有固定检查点、规则和关卡的 agent 工作环境。英文里常叫 harness，也就是“护栏”或“控制框架”，用来让 agent 不偏离轨道。

ETC 从初始化开始。在真正做功能之前，团队先记录这个项目到底是什么，包括它所属的业务领域、项目目标，以及现有系统的架构、惯例和实际行为。

这里有一个重要细节：工具不会检查完代码库之后，自己悄悄做出猜测。比如，如果数据传输对象，也就是 DTO，分散在五个不同的位置，系统不会直接替团队决定哪一种写法才是标准。它会把发现带回来，请人确认哪个惯例才是权威做法，然后把这个决定记录下来。

确认之后，项目上下文会被整理并锁定。这样，后续每个 agent 都是在同一个操作模型下工作，而不是各自根据不完整的信息猜测。

##### 六、一个功能，要经过多轮富集才进入构建

完成初始化之后，工作会沿着管道推进。每一步都产生一个更完整的产物。

首先是用户旅程。它要回答几个问题：谁在使用系统，他们想完成什么，价值会在哪里体现，以及过程中可能在哪些地方失败。

接下来是规格阶段。ETC 使用“规格驱动开发”，意思是先把要构建的内容写成清晰、可测试的规格，而不是只留下一张简单工单。规格应该反映公司的真实需求，也要让产品、设计、工程和 AI 对最终目标有共同理解。

之后是低保真设计。它主要探索页面结构、流程和基本布局。再往后是高保真设计，把预期的用户体验具体呈现出来。

最后进入架构阶段。工程团队会重点确认技术可行性、系统集成边界、数据形态和实现策略。同时，产品和设计人员仍然参与其中，而不是把架构问题完全丢给工程部门。

ETC 还会为每个功能建立一个“功能包”。它一开始只是一个目录，随着流程推进不断被填充。领域背景、用户旅程、规格、设计和架构信息，都会写入这个功能包。

等架构阶段完成后，功能包已经包含了足够的业务上下文、产品意图、设计方向和技术指导。此时再进入构建，剩下的模糊空间就会少很多。

##### 七、构建阶段，人类从亲自操作变成监督执行

当前期工作足够扎实，构建开始后，就不需要人类盯着 agent 的每一次操作。

这时，一个人可以担任“构建经理”。他的职责不是亲手敲完所有代码，而是监督构建过程、检查进度，并处理升级问题。

如果系统遇到它无法判断的情况，或者遇到一个不应该自行决定的问题，它会停下来，把当前状态交给人类处理，而不是继续往前推进。

这体现了人和 agent 的新分工：agent 负责执行，人负责判断、授权和处理例外情况。

##### 八、新的团队形态：聚集、富集、散开

作者用三个词概括了这种新的团队形态：聚集、富集、散开。

首先是聚集。产品、设计、工程和业务相关人员会在一段集中的工作会议中聚在一起，通常通过视频会议完成。他们共同定义问题，打磨规格，检验假设，并确认到底要构建什么。

这种集中协作通常需要一到三天的非全职投入。也就是说，大家不必长期占用全部时间，但需要在关键决策阶段同时参与。

接下来是富集。团队的想法沿着管道不断变得具体。业务背景补充了领域信息，用户旅程补充了使用场景，规格明确了产品要求，设计明确了体验，架构明确了技术实现路径。

最后是散开。当功能包已经准备好，团队中的大多数人就可以回到其他工作中。只有构建经理继续陪伴 agent 的执行过程。

这套运营模式可以概括成一句话：人不会消失，而是把判断集中在最有价值的地方；一旦机器可以执行，人类就不再继续制造不必要的阻力。

##### 九、管理者获得的，不再只是模糊状态

这种方法对管理者的另一个价值，是让交付变得更可见。

传统团队经常用故事点、迭代速度、工单数量，或者“快完成了”“目前有阻塞”“还需要测试”这样的主观描述来汇报进展。这些信号往往比较模糊。

管道模型提供了更具体的度量。管理者可以看到规格阶段用了多长时间，设计用了多长时间，架构用了多长时间，构建用了多长时间，也能观察瓶颈到底转移到了哪里。

例如，如果这次设计用了十二小时，而上一次用了十五小时，这可能说明设计流程正在改善。反过来，如果架构阶段不断变长，可能意味着代码库中隐藏着较大的复杂度。如果构建阶段反复卡住，可能说明规格不够清楚，或者架构文档不够完整。

这些数据能够形成真正的改进循环。团队不再只依靠状态会议里的印象，而是根据每个阶段的实际表现，决定下一步应该优化什么。

##### 十、共同参与前期工作，会提升团队质量

当产品、设计和工程人员一起处理业务领域、规格、设计和架构时，他们会建立更强的共享理解。

很多难题会在实现压力出现之前被解决。团队成员也能看到彼此是怎样思考和做判断的。这会建立信任，并增加项目真正成功的可能性。

作者还观察到，这种改善会形成正向循环。当流程变得更容易、更可靠，团队成员就更愿意再次使用它。工作不再那么混乱，协作也开始产生看得见的结果。人们会更愿意投入，而不是回避。

因此，团队对工作方式的感受并不是无关紧要的附加项。更好的工作体验，会带来更好的协作；更好的协作，又会进一步改善工作体验。

##### 十一、质量不能靠信任 agent，而要靠执行机制

当然，读者很容易提出一个问题：AI 生成的构建结果，怎么保证质量？

作者承认，这是一个正确的问题。但这篇文章主要讨论的是 AI 如何改变工作组织，包括团队把时间花在哪里、产物怎样逐步完善、瓶颈如何转移，以及管理者怎样获得更清晰的可见性。

关于质量，作者给出的简短答案是：质量不能来自对 agent 的单纯信任，而要来自一套执行机制。

这些机制包括确定性的检查、规格执行、架构约束、自动化测试、人工审查关卡，以及发布前验证。ETC 之所以需要工具和控制框架，很大一部分原因，就是要把这些质量要求内建到流程里。

换句话说，AI 可以负责大量执行，但软件质量仍然需要规则、检查和人类判断共同保障。

##### 十二、ETC 的最终理念：像进入共享对话空间一样交付软件

最后，作者解释了 ETC 这个名字背后的含义。

未来的软件工作，可能越来越像人们进入一个共享的对话空间，各自完成自己负责的部分，然后离开。产品负责人进入这里，澄清产品意图；设计师进入这里，塑造用户体验；工程师进入这里，定义架构；构建经理进入这里，监督执行；agent 则进入这里，完成具体的专业工作。

人类在需要的时候加入，贡献自己的判断，完成负责的部分后退出。这样，聊天就不再只是一个随意讨论的地方，而会变成一个受到治理、真正能够交付工作的环境。

作者认为，AI 原生交付不是要替代团队，而是要围绕人类最有价值的部分重新组织团队。

人类更擅长判断、理解上下文、做取舍、把握业务、形成品味，以及建立共同意义。agent 则越来越擅长执行、转换、搭建框架和批量产出。

真正的问题，是不要把人和 agent 都塞进一套原本为旧时代设计的工作流。更好的做法，是设计一种符合双方优势的新流程。

##### 结尾：最值得记住的几个结论

回顾全文，最值得记住的有五点。

第一，AI agent 让工程师写代码更快，但真正改变的是软件团队的组织方式。

第二，新的瓶颈不再主要是代码产能，而是业务上下文、规格、设计、架构和验证的质量。

第三，软件交付像一条富集管道。越早把模糊想法变成清晰、可测试、可执行的功能包，后面的构建就越稳定。

第四，ETC 用“聚集、富集、散开”的方式重新安排团队：人在关键决策阶段集中协作，功能包成熟后由 agent 执行，人类负责监督和处理例外。

第五，AI 原生交付不是取消流程，而是用更严格的上下文、检查和治理，把 agent 的原始速度转化成可持续、可衡量的交付能力。文中介绍的 Heavy Chain Engineering，声称通过这种方式帮助团队实现了百分之八十五更快的功能交付速度，并把原本需要六到八周的项目压缩到几天完成。

## 深度解读（1）

### 2026-09-18 00:22:01

#### AI 编程真正改变的，不是写代码，而是“错误被放大”的速度

这篇文章最有价值的判断，不是 agent 能把开发提速多少，而是：**当代码生成变得廉价，软件交付的约束会从工程产能转向决策质量。**

过去，模糊需求还能在漫长开发中被逐步发现：工程师会追问、设计会调整，团队也有时间修正方向。agent 则会把模糊性迅速变成大量实现。它不一定更早暴露错误，反而可能更快、更完整地做出错误的东西。因此，AI 带来的不只是生产率提升，也是“错误方向的吞吐量”提升。

这解释了作者看似反直觉的主张：AI 越强，团队越需要纪律，而不是越不需要流程。

##### 规格正在从沟通文档变成生产基础设施

ETC 方法最值得保留的部分，是把交付描述为一条“富集管道”：半成型想法依次加入业务背景、用户旅程、可测试规格、体验设计和架构约束，最终形成可供 agent 执行的功能包。

关键不在于多写几份文档，而在于**逐步消除机器不该自行决定的事项**。例如，代码库里存在五种 DTO 放置方式时，agent 不应凭统计频率猜一个，而应把冲突提交给人，由团队确认权威惯例，再将决定固化为后续 agent 共享的约束。这里的产物不是传统 PRD，而是人机协作的“共同运行模型”。

对产品经理而言，相应能力也不是把需求写得更长，而是识别哪些信息会改变实现：目标用户是谁、价值在何处出现、哪些行为不可接受、验收标准是什么、哪些未知项必须先验证，以及什么决定必须升级给人。**好的规格不是描述得事无巨细，而是准确区分确定项、约束项与待验证项。**

##### 团队可能从持续协调转向集中决策

作者提出的“聚集—富集—散开”很有启发：产品、设计、工程和业务人员先集中一到三天解决高价值分歧；功能包成熟后，大部分成员退出，只留下构建经理监督 agent，并处理异常升级。

这改变了协作的目的。团队不再靠站会持续同步大量执行细节，而是在构建前集中共享判断，在构建中只处理超出授权边界的决策。领导者也可以观察规格、设计、架构和构建各阶段的耗时、返工与阻塞，而不是依赖故事点和“快完成了”之类的弱信号。

但这套方法有明确边界。它更适合领域相对清楚、主要成本在实现的垂直 SaaS 和存量系统；对于零到一产品，真正的不确定性常在用户需求和商业价值，过早把假设“富集”为精密规格，可能只是更高效地交付未经验证的产品。敏捷原本解决的不只是人力吞吐量，也包括通过运行中的软件学习，不能简单被归为旧时代的队列管理。

文中“交付提速 85%”也主要是作者的咨询实践主张，尚不足以证明普适性。更值得团队验证的指标是：首次验收通过率、返工量、agent 升级次数、线上缺陷，以及从决策到价值交付的总周期。**真正的 AI 原生交付，不是代码生成得多快，而是团队能否让更少的错误决定进入高速执行。**
