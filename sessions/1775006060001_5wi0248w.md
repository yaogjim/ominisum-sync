### Claude Code 封号真相：挖了源码，我发现了 5 个"叛徒"

TMD又封了，每天都能刷到这样的消息。

用 CC有一阵子了，庆幸自己还没被封，但心里总有点虚。

网上关于封号的讨论很多，但没人说得清真正原因。

好巧不巧，今天cc源码暴露了。我立刻 clone 下来，想搞清楚——CLI 到底是怎么触发风控的？

说实话，挖完之后我释然了。没找到什么「作恶证据」，但我发现一件事：光靠 VPN 藏 IP，根本不够。

Claude Code 有 5 个设计，会在你毫不知情的情况下「出卖」你。

我找到了 5 个「叛徒」。

#### 一、device\_id：你换 IP，它不换

第一个叛徒，藏在每次 API 请求里。

打开 src/services/api/claude.ts，519-527 行，有这么一段：

```typescript
return {
  user_id: jsonStringify({
    device_id: getOrCreateUserID(),
    account_uuid: getOauthAccountInfo()?.accountUuid ?? '',
    session_id: getSessionId(),
  }),
}
```

这个 user\_id 字段，嵌入在每一条 /api/messages 请求体中。

关键点：device\_id 是本地持久化的 UUID。只要你不清除本地文件，它永远不变。

这意味着什么？

你换了 VPN 节点，IP 变了。但 device\_id 还是同一个。

Anthropic 服务端看到的画面是这样的：

- 这个 device\_id 之前从日本 IP 访问
- 现在从美国 IP 访问
- 半小时后又从新加坡 IP 访问

同一个设备，短时间内跨越三个国家。

这不是正常用户的行为模式。

更狠的是，这个字段关不掉。它不是遥测，是 API 协议的一部分。你关闭所有隐私设置，它照样发。

#### 二、归因水印：写在 prompt 里的"钉子"

第二个叛徒，更隐蔽。

它不是藏在 HTTP 请求里，而是藏在每次对话的 system prompt 里。

```typescript
src/constants/system.ts，73-95 行：
const header = `x-anthropic-billing-header: cc_version=${version};
  cc_entrypoint=${entrypoint}; cch=39d86; cc_workload=${workload}`
```

这个 x-anthropic-billing-header 会被注入到 system prompt 里，包含：

- CLI 版本号
- 入口类型（cli/desktop/vscode）  
  入口类型（命令行界面/桌面端/VSCode）
- cch 字段：客户端证明，发送时由底层覆写

这是写在 prompt 里的，不是 HTTP header。

你没法通过代理或中间人修改它。每条消息都带着这个水印，告诉服务端：这是 CLI 用户。

#### 三、x-app: cli：主动标记自己为"特殊群体"

第三个叛徒，在请求头里主动"自首"。

```typescript
src/services/api/client.ts，105-116 行：
defaultHeaders = {
  'x-app': 'cli',
  'User-Agent': 'claude-cli/1.0.0 (regular, cli)',
  'X-Claude-Code-Session-Id': getSessionId(),
}
```

x-app: cli 直接告诉服务端：我是 CLI 用户。

Web 用户呢？User-Agent 是浏览器标识，混在数十亿浏览器请求里，根本分不出来。

CLI 用户呢？直接给自己贴了个标签：「我是特殊群体」。

服务端可以对这个群体单独应用更严格的风控规则。

#### 四、遥测：5 秒一次的"电话汇报"

第四个叛徒，是最话痨的那个。

遥测系统，每 5 秒上报一次。

```text
src/services/analytics/firstPartyEventLoggingExporter.ts 写得很清楚：
Export cycles triggered when: Time interval elapses (default: 5 seconds)
```

上报什么？看看 metadata.ts：

- 操作系统、架构、Node 版本
- 终端类型、包管理器
- 是否 CI 环境、是否远程
- CPU/内存使用率
- accountUuid、organizationUuid、emailAddress  
  账户 UUID、组织 UUID、电子邮件地址
- sessionId、subscriptionType  
  会话 ID、订阅类型

一个 30 分钟的编码 session，会产生 360 次遥测请求。

每次都带着你的 IP。

好消息：这个可以关。设置 DISABLE\_TELEMETRY=1 就行。

坏消息：前面三个叛徒关不掉。

#### 五、重试机制：不稳定 VPN 的灾难

第五个叛徒，是重试机制。

```typescript
src/services/api/withRetry.ts：
默认最多重试 10 次
指数退避：500ms → 1s → 2s → 4s → ... → 最大 32s
遇到 429 会重试，遇到 401 会刷新 token 后重试
```

问题在哪？

如果你的 VPN 不稳定，偶发连接错误。

一次失败的请求，可能触发 10 次重试。

从服务端看，这是短时间内从不同 IP 发起的大量请求。

典型的异常行为模式。

#### 六、CLI vs Web：为什么 CLI 更容易中招

把上面五个叛徒放在一起，你就明白了：

![Image](https://pbs.twimg.com/media/HEvm3iIbgAABiHW?format=png&name=large)

Web 版的用户藏在浏览器流量里，CLI 用户直接把自己标记出来。

不是 Anthropic 针对 CLI，是 CLI 的设计让风控信号更丰富。

#### 七、怎么办：4 个自救方案

知道了叛徒在哪，就知道怎么对付它们。

以下环境变量都需要添加到你的 shell 配置文件里：

- macOS 默认用 zsh → \~/.zshrc  
  macOS 默认使用 zsh → \~/.zshrc
- Linux 用 bash → \~/.bashrc  
  Linux 使用 bash → \~/.bashrc

改完后记得 source \~/.zshrc 或者重启终端。

方案 A：关遥测（减少 80% 暴露）

```text
在 ~/.zshrc 中添加：
export DISABLE_TELEMETRY=1
更激进的话：
export CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1
```

方案 B：用 API Key 代替 OAuth 登录

用 API Key 时，不会调用 /api/oauth/profile，减少一个暴露 IP 的端点。account\_uuid 字段也会变成空字符串。

```text
在 ~/.zshrc 中添加：
export ANTHROPIC_API_KEY=sk-ant-xxx
```

方案 C：用第三方云提供商（最安全）

用 Bedrock/Vertex/Foundry 时，遥测自动关闭，请求发往 AWS/GCP/Azure 而非

api.anthropic.com。

Anthropic 看不到你的 IP。

```text
在 ~/.zshrc 中添加：
# AWS Bedrock
export CLAUDE_CODE_USE_BEDROCK=1

# Google Vertex AI
export CLAUDE_CODE_USE_VERTEX=1
```

方案 D：稳定 IP（住宅更佳）+ 减少重试

```text
在 ~/.zshrc 中添加：
export CLAUDE_CODE_MAX_RETRIES=2
```

确保 VPN 出口 IP 稳定，避免同一 session 内 IP 跳跃。

优先级：Bedrock/Vertex &gt; 关遥测 + API Key &gt; 稳定 IP（住宅更佳）+ 减少重试

说实话，挖完源码我反而放心了。

没找到什么「黑幕」，因为根本没有黑幕。

Anthropic 没有在客户端写地域封锁代码。封号是服务端基于行为模式的风控，是算法，不是针对。

但 Claude Code 的设计，确实让它比 Web 版更容易触发风控。

知道了原理，就知道怎么规避。

如果你也在用 Claude Code，希望这篇文章能帮你少踩坑。

## 通俗精炼（1）

#### Claude Code 封号原因简析

##### 核心结论
作者通过查看 Claude Code 源码发现：**封号大概率不是 “人工针对” 或 “隐藏黑幕”**，而是服务端根据一系列行为信号做风控判断。  
问题的关键不在于 “你有没有换 IP”，而在于：**CLI 会持续暴露设备、入口、会话和网络变化等特征**，比 Web 端更容易被识别为异常。

##### 五个主要风险点
###### 1. 设备 ID 持久存在
每次请求都会带上本地持久化的`device_id`。  
这意味着即使你频繁切换 VPN 节点，服务端依然能判断 “还是同一台设备”，一旦短时间跨多个国家或地区，就很容易被判定异常。

###### 2. Prompt 内嵌 “归因水印”
CLI 会在 system prompt 中注入版本号、入口类型等信息。  
这相当于每次请求都自带 “身份说明”，而且**不是普通 HTTP 头**，很难通过代理手段隐藏或修改。

###### 3. 请求头主动标记为 CLI
请求头里的`x-app: cli`会直接告诉服务端：这是命令行用户。  
相比 Web 用户混在海量浏览器流量中，CLI 用户更容易被单独套用更严格的风控规则。

###### 4. 高频遥测持续上报
默认每 5 秒就会上报一次遥测信息，内容包括设备环境、账户信息、会话信息、资源使用情况等。  
这样会持续暴露你的 IP 和使用轨迹，尤其在长时间编码时，信号非常密集。

###### 5. 重试机制放大异常行为
如果网络或 VPN 不稳定，请求失败后会自动多次重试。  
服务端看到的可能是：**短时间内来自不同 IP 的重复请求**，这会进一步强化异常特征。

##### 为什么 CLI 比 Web 更容易中招
###### 本质原因
不是 Anthropic “专门针对 CLI”，而是**CLI 天生暴露的信息更多**。  
Web 端用户隐藏在普通浏览器流量里，而 CLI 会主动上报更多设备、入口、会话和环境信息，所以更容易触发风控模型。

##### 可行的规避思路
###### 1. 优先关闭遥测
通过环境变量关闭 telemetry，可以显著减少暴露面。  
这是成本最低、见效最快的方式。

###### 2. 尽量使用 API Key
使用 API Key 替代 OAuth，可以减少部分账户信息和额外接口暴露。

###### 3. 更安全的是走云厂商通道
如果通过 Bedrock、Vertex 等第三方云服务接入，请求不直接打到 Anthropic，隐私和稳定性更好。

###### 4. 保持 IP 稳定，降低重试次数
不要频繁切换出口 IP，尤其避免同一会话内 “跨地区跳变”。  
同时减少重试次数，可以降低异常流量特征。

##### 最终结论
###### 一句话理解
**Claude Code 容易封号，不是因为 “偷偷作恶”，而是因为它的产品设计天然更容易暴露异常信号。**  
所以真正有效的应对方式，不是单纯换 VPN，而是：**减少可识别信号、保持网络稳定、降低异常行为模式。**

#### Claude Code 封号问题总结

这篇文章的核心观点是：**Claude Code 被封号，更多不是 “客户端偷偷作恶”，而是 CLI 本身会暴露出更多风控信号**。作者通过查看源码发现，**单靠 VPN 换 IP 不够，因为还有多种机制会持续标记你的设备、身份和行为模式**。

##### 1. 作者为什么去看源码

- 作者经常看到用户反馈 “Claude Code 又被封了”，但网上对原因的解释大多不够清晰。
- 因此在源码泄露后，作者第一时间去分析，想确认：**CLI 到底是怎么触发风控的**。
- 结论是：
  - **没发现明显 “作恶证据” 或地域封锁黑幕**；
  - 真正的问题在于：**Claude Code 会主动或被动暴露多类身份与行为信息**。

##### 2. 第一个 “叛徒”：`device_id`持久不变

- 每次向`/api/messages`发请求时，都会在`user_id`字段里携带：
  - `device_id`
  - `account_uuid`
  - `session_id`
- 其中最关键的是：**`device_id`是本地持久化的 UUID**，只要不清本地文件，它就不会变。
- 这意味着：
  - 你换了 VPN 节点，**IP 变了**；
  - 但**`device_id`还是同一个**。
- 服务端看到的就可能是：
  - 同一设备先从日本访问；
  - 又从美国访问；
  - 半小时后再从新加坡访问。
- 这种**短时间跨多个国家的行为**，非常像异常访问模式。
- 重点：**这个字段关不掉**，因为它属于 API 协议本身，不是普通遥测。

##### 3. 第二个 “叛徒”：写进 prompt 的归因水印

- 除了 HTTP 请求本身，系统还会在每次对话的**system prompt**里注入一段信息：
  - `cc_version`：CLI 版本号
  - `cc_entrypoint`：入口类型，如`cli` / `desktop` / `vscode`
  - `cch`：客户端证明字段
  - `cc_workload`：工作负载信息
- 关键问题在于：
  - 这不是普通请求头；
  - 而是**直接写在 prompt 里的 “水印”**。
- 所以即使你通过代理、中间人等方式处理 HTTP，也**很难改掉这类信息**。
- 作用相当于：**每条消息都在告诉服务端 “我是 CLI 用户”**。

##### 4. 第三个 “叛徒”：请求头直接标记`x-app: cli`

- 在默认请求头中，CLI 会主动发送：
  - `x-app: cli`
  - `User-Agent: claude-cli/...`
  - `X-Claude-Code-Session-Id`
- 这相当于直接给自己贴标签：**“我是 CLI 用户”**。
- 与 Web 版相比：
  - Web 用户混在海量浏览器流量里，不容易单独识别；
  - CLI 用户则被明确区分出来。
- 这会带来一个结果：**服务端可以单独给 CLI 用户设置更严格的风控规则**。

##### 5. 第四个 “叛徒”：高频遥测，每 5 秒一次

- 作者发现，Claude Code 的遥测系统默认**每 5 秒上报一次**。
- 文章列出的上报内容包括：
  - 操作系统、架构、Node 版本
  - 终端类型、包管理器
  - 是否处于 CI、是否远程环境
  - CPU / 内存使用率
  - `accountUuid`、`organizationUuid`、`emailAddress`
  - `sessionId`、`subscriptionType`
- 作者举了一个很直观的数据：
  - **30 分钟的编码 session，会产生 360 次遥测请求**。
- 而且：
  - 每次请求都带 IP；
  - 所以会持续给服务端补充行为轨迹。
- 好消息是：**这一项可以关闭**。
  - 可设置：`DISABLE_TELEMETRY=1`

##### 6. 第五个 “叛徒”：重试机制会放大异常行为

- 请求失败时，CLI 默认会自动重试，规则包括：
  - **最多重试 10 次**
  - 指数退避：`500ms → 1s → 2s → 4s ...`，最大到`32s`
  - 遇到`429`会重试
  - 遇到`401`会刷新 token 后重试
- 风险在于：
  - 如果你的 VPN 不稳定；
  - 一次请求失败，可能演变成短时间内连续大量请求。
- 如果此时 IP 还在跳动，服务端看到的就是：
  - **同一会话**
  - **多个 IP**
  - **高频失败 + 高频重试**
- 这很容易被识别成异常流量模式。

##### 7. 为什么 CLI 比 Web 更容易中招

- 作者的判断是：**不是 Anthropic 特别 “针对 CLI”**，而是 CLI 的设计天然会暴露更多风控信号。
- 前面 5 个因素叠加后，CLI 用户相比 Web 用户更容易被识别：
  - 有稳定的`device_id`
  - 有 prompt 里的归因水印
  - 有`x-app: cli`这类明确标签
  - 有高频遥测
  - 有失败后的自动重试放大行为
- 所以本质上是：
  - **Web 用户更 “隐身”**
  - **CLI 用户更 “可观测”**

##### 8. 作者给出的 4 个自救方案

###### 方案 A：关闭遥测

- 目的：**减少大部分额外暴露**
- 配置：
  ```bash
  export DISABLE_TELEMETRY=1
  ```
- 更激进一点还可以：
  ```bash
  export CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1
  ```
- 作者的判断：这一步能**减少约 80% 的暴露**。

###### 方案 B：用 API Key 替代 OAuth 登录

- 目的：减少与账号信息相关的额外暴露。
- 效果：
  - 不再调用`/api/oauth/profile`
  - `account_uuid`会变成空字符串
- 配置：
  ```bash
  export ANTHROPIC_API_KEY=sk-ant-xxx
  ```

###### 方案 C：改用第三方云提供商

- 作者认为这是**最安全的方案**。
- 可选平台：
  - AWS Bedrock
  - Google Vertex AI
  - Azure Foundry
- 原因：
  - 遥测会自动关闭
  - 请求发往 AWS / GCP / Azure，而不是`api.anthropic.com`
  - **Anthropic 直接看不到你的 IP**
- 示例配置：
  ```bash
  export CLAUDE_CODE_USE_BEDROCK=1
  export CLAUDE_CODE_USE_VERTEX=1
  ```

###### 方案 D：保持稳定 IP，并减少重试次数

- 重点是：
  - 尽量使用**稳定出口 IP**
  - 最好是住宅 IP
  - 避免同一 session 内频繁跳国家、跳地区
- 同时把最大重试次数调低：
  ```bash
  export CLAUDE_CODE_MAX_RETRIES=2
  ```

##### 9. 作者给出的优先级建议与最终结论

- 作者给出的方案优先级是：
  - **Bedrock / Vertex**
  - **关闭遥测 + API Key**
  - **稳定 IP（住宅更佳）+ 减少重试**
- 最终结论有两层：
  - **没有发现客户端里存在 “专门地域封锁” 的黑幕代码**；
  - 但**Claude Code 的设计确实比 Web 版更容易触发服务端风控**。
- 用更直白的话说：
  - 封号更像是**基于行为模式的算法判断**；
  - 而不是官方专门 “盯着某一类地区用户封”。

##### 10. 一句话理解全文

- **问题不只是 “你用了 VPN”，而是 “同一个设备在不断向服务端暴露身份、水印、遥测和异常重试行为”**。
- 只要理解了这些触发点，就能更有针对性地降低风险。
