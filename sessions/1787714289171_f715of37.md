## 分析要点

- **核心高价值点**：智能体的每次调用都重新继承授权人的实时权限，并在执行前写入审计记录；写入失败则中止操作。
- **留存建议**：建议存档，重点保留智能体权限与审计机制，产品能力需另行验证（实时权限校验、操作前审计、拒绝记录和哈希链验证可作为企业智能体治理的复用设计清单。）

**知识要点**

- 智能体权限不应在创建时静态缓存，而应在每次工具调用时根据授权人的当前权限重新校验。
- 审计记录应先于实际操作写入，并同时记录允许与拒绝事件，才能避免出现已执行但不可追溯的行为。
- 使用前向哈希链连接审计条目，可检测历史记录的插入、修改或删除，并支持独立导出验证。

**行动项**

- 将实时权限校验、操作前审计、拒绝日志和哈希链验证纳入Agent系统安全评审清单。
- 在试用中验证成员权限撤销后，其智能体、令牌和外部MCP调用是否立即失效。
- 通过故障注入测试审计写入失败时操作是否真正中止，并验证导出日志的哈希链完整性。

##### 代理只能做其创建者所能做的事

每一项操作都会对照授权该操作的人类用户的实时权限图谱进行核查：频道、项目和文档的成员资格，均在调用当下读取，而非在设置时缓存。将某人移出频道后，代表其行事的代理会在下一次请求时失去该权限，而不是等到下一次令牌轮换。

##### 无法被记录的事情，就不算发生

审计条目在操作执行之前写入，写入失败将中止该调用。这种顺序安排正是关键所在：一个已做出但从未记录的决策，比一个已记录却被放弃的决策更糟糕，因为只有后者事后才能被发现。

##### Refusals are logged too

被拒绝的调用会留下一行记录，包含拒绝原因、凭据、具名代理以及其背后的人类操作者。因此，访问审查能够回答代理尝试了什么、被阻止做了什么——这正是事件发生后真正重要的问题。

##### 无法被悄悄篡改的历史记录

每条审计条目都会对其自身内容及前一条目的哈希进行哈希运算。任何后续的插入、编辑或删除都会破坏这条链，而验证端点会重新计算并报告第一个分歧点。导出数据携带每行的哈希值，使审计员无需信任界面即可进行核验。

##### 模型可以留在建筑内

默认通过 Ollama 进行本地推理。开启仅本地模式后，服务器会完全拒绝激活任何云提供商，而不是警告你后仍然允许。当你需要时，可以指向 OpenAI 或 Anthropic，并在输出时进行 PII（个人身份信息）脱敏。

##### 离职流程覆盖到智能体

停用某人的操作会在每个授权界面实时重新评估，因此他们的智能体和 API 令牌会立即停止工作，无需任何人去寻找要撤销的凭据。机器人和仅用于归属的身份从一开始就无法成为调用的授权方。

##### Local AI

默认通过 Ollama 在本地运行，因此聊天和文档永远不会离开你的设备。当你需要时，可以将其指向 OpenAI、Anthropic 或你自己的端点；纯本地模式和内置的 PII 脱敏功能让你始终掌控一切。只需询问一次，即可从你的频道、文档、任务以及关联的 Gmail 或 GitHub 获得带引用的答案。每日令牌预算已包含在内。

#### Before you buy

我们实际收到的邮件。简短回答。

AI 能看到它不该看的东西吗？

它在调用时检查你的频道、项目和文档成员资格，因此它只能读取你本来就能打开的内容。同样的检查也适用于任何代表你行事的对象：代理、API 令牌、外部 MCP 客户端。设置时不会缓存任何内容，因此你失去的权限，它在下一次请求时也会失去。

AI 的行为是否有审计追踪？

有，拒绝记录也在其中。每一行都标明工具、决策、原因、凭据、代理（如有）以及负责的人员。条目在操作执行前写入，若无法写入则操作不会发生。条目采用哈希链式连接，因此后续对历史的修改均可被检测，您可以验证链条或连同哈希一起导出。

有人离职时会发生什么？

在 OneCamp 中将其停用，或通过 SCIM 从您的目录中自动完成。每次调用时，每个授权面都会重新检查资格，因此他们的会话、API 令牌以及任何代表其行事的代理都会立即失效。您无需四处寻找要撤销的凭据。

Do you support SSO and SCIM?

SAML 2.0、OIDC 和 LDAP 用于登录；SCIM 2.0 用于账户的配置和取消配置；TOTP 双因素认证配合恢复码，适用于使用密码登录的账户。您的目录创建的账户必须在您的目录中进行身份验证，因此没有人可以为其设置本地密码来绕过该机制。

Where does the AI run?

在您选择的基础设施上运行，而不是我们的。可指向 OpenAI、Anthropic 或任何兼容 OpenAI 的端点，涵盖 vLLM、LM Studio、OpenRouter、Groq 以及您自行运行的网关。通过 Ollama 使用本地模型只需打开一个开关，因此除非您主动要求，否则不会下载任何模型。开启仅本地模式后，服务器会完全拒绝激活云提供商，而不是发出警告后放行；同时，任何出站数据都会先经过 PII 脱敏处理。

OneCamp Cloud 是否包含 AI 功能？

AI 版本是预置好的，所以智能体和团队成员都已经就位等待使用。模型部分由你自行提供：添加 OpenAI 或 Anthropic 的密钥，或者指向任何兼容 OpenAI 的端点。我不转售推理服务，也永远不会看到你的提示词，所以你直接按供应商的价格向他们付费。在你添加密钥之前，AI 功能界面保持闲置状态，工作区中的其他一切功能照常运行。

我可以与组织外的人分享文档/看板吗？

可以。你可以通过只读链接与团队外部人员分享文档、看板或表格，并为通话创建访客链接。访客只能看到你分享的内容，其他一概不可见，而且每次打开记录都会为你进行审计。

Do I need a GPU?

不。大多数人将 OneCamp 指向一个提供商密钥，然后模型在提供商的硬件上运行，而不是在您的硬件上。如果您开启本地模型，默认的小型模型在 16 GB 内存的 CPU 上运行良好，而 GPU 才能使更大的模型变得实用。

OneCamp 是一套集成聊天、文档、任务、表格、白板、视频、日历和 AI Agent 的团队工作空间。其核心卖点不是 “AI 更聪明”，而是让 AI **继承人的权限、操作前留痕、全程可审计，并运行在企业自己的基础设施上**。

##### 核心差异：用系统约束 AI

###### 1. AI 权限不超过授权人

Agent 只能执行其授权人本来就有权执行的操作。系统会在**每次调用时实时检查权限**，而非创建 Agent 时一次性授权。

当员工被移出项目、频道或公司后，其 Agent、会话和 API Token 会立即失效。

###### 2. 先审计，后执行

每次 AI 操作都必须先写入审计日志，再实际执行；如果日志写入失败，操作会被直接中止。

被拒绝的请求同样会记录，包括：

- Agent 尝试做什么
- 为什么被拒绝
- 使用了什么凭证
- 哪位员工应对此负责

###### 3. 审计记录可验证

日志采用哈希链连接，后续插入、修改或删除记录都会破坏链条。企业可通过接口验证，也可导出带哈希值的 CSV 或 JSON，降低审计对平台 UI 的依赖。

##### 产品能力：一体化团队工作空间

OneCamp 试图在一个系统中替代多类 SaaS：

- **沟通协作**：频道、私聊、线程、文件、实时通知
- **知识管理**：多人文档、块编辑器
- **项目管理**：任务、看板、项目与角色权限
- **结构化数据**：类似 Airtable/Notion Database 的表格、看板、日历和图表
- **创意协作**：白板、流程图、思维导图
- **会议能力**：视频、屏幕共享、录制、本地转写和 AI 总结
- **日程管理**：Google Calendar 双向同步
- **自动化与开放能力**：规则自动化、公共 API、TypeScript SDK、MCP Server

AI 可以回答跨文档、频道和任务的问题，也可定时总结、创建任务或执行工作流；企业可以选择让其自动执行，或先提交方案等待人工批准。

##### 部署与数据控制

产品支持 Docker 私有化部署，前端开源，实例不主动 “回传” 数据，也不按用户数收费。

AI 默认可通过 Ollama 使用本地模型，也支持 OpenAI、Anthropic 及兼容 OpenAI API 的服务。开启 “仅本地模式” 后，服务器会直接禁止使用云端模型；若调用外部模型，可先执行 PII 敏感信息脱敏。

##### 企业级管理能力

OneCamp 将常见企业功能作为标准能力提供，而非额外的企业版：

- SAML 2.0、OIDC、LDAP / Active Directory
- SCIM 2.0 自动开户与离职停用
- TOTP 双因素认证及恢复码
- 角色、项目和内容权限
- 防篡改管理审计日志
- 数据驻留与本地 AI 模式

##### 商业模式

产品提供两种模式：

1. **私有化部署**：一次买断、无限用户、无年度续费  
2. **托管云服务**：99 美元 / 月，最多 30 人，并附带私有化部署许可

官方将其定位为 Slack、Notion、Asana、Zoom、Airtable 和日历工具的整合替代方案，主打降低多工具订阅和 AI 按席位收费带来的成本。

参考配置为：

- 50 人以下：8 GB 内存、4 vCPU
- 50～200 人：16 GB 内存、4 核以上
- 200 人以上：32 GB 内存起步

实际资源需求会受到本地模型和视频会议使用量影响。

##### 产品定位与价值判断

OneCamp 本质上是一个以**AI 治理为差异化入口**的自托管协作套件，适合重视以下问题的团队：

- 数据不能离开内部网络
- AI 权限必须与员工权限严格绑定
- 需要追溯 AI 做过什么、被阻止过什么
- 希望减少多套 SaaS 和按席位付费
- 需要 SSO、SCIM、审计及离职自动停权

其关键价值不只是 “把多个工具放在一起”，而是把 Agent 当作受控的企业身份主体，而非拥有宽泛权限的外挂机器人。

##### 需要关注的风险

- **产品成熟度**：功能覆盖很广，但团队规模、稳定性及各模块深度仍需实际验证。
- **开源边界**：页面明确的是 “前端开源”，后端以二进制和许可证形式交付，不等于完整开源。
- **运维成本**：自托管省去 SaaS 订阅，但会增加服务器、安全、备份、升级和故障处理成本。
- **性能约束**：本地 AI、视频会议和多人协作同时运行时，硬件需求可能高于基础建议。
- **宣传需验证**：权限控制、审计链和 “零未审计操作” 等均为官方描述，应通过产品测试和安全评估确认。
- **退款政策矛盾**：首页写有 “30 天退款政策”，但独立退款页面明确表示 “不提供退款”，购买前应向官方书面确认。

## 结构化（1）

### 2026-08-26 03:27:00

#### OneCamp：部署在自有服务器上的受控 AI 协作平台

OneCamp 是一套自托管的一体化协作平台，将聊天、文档、任务、表格、白板、视频、日历和 AI 智能体整合在同一工作区。其核心卖点不是让用户 “相信 AI 会守规矩”，而是通过实时权限校验、事前审计和本地部署，让 AI 从技术上难以越权且全程可追责。

##### 1. 核心理念：AI 的权限必须受技术约束

传统 AI 助手接入聊天、Wiki 和工单系统后，可能很快获得超过多数员工的访问范围，但企业往往无法回答 “这次操作究竟由谁授权”。

OneCamp 采用相反思路：

- 智能体继承其创建者或授权者的权限，不能获得更高权限。
- 每次调用都实时检查频道、项目、文档等成员资格，不使用初始化时缓存的权限。
- 员工被移出频道后，其智能体从**下一次请求**开始立即失去相关权限，无需等待令牌更新。
- 机器人或仅用于归属的身份不能充当授权主体，所有操作最终都要对应到具体责任人。

官方给出的核心指标包括：

- **0 次未经审计的智能体操作**
- **无限用户，不按席位收费**
- **100% 运行在用户自己的基础设施上**
- **通常不到 10 分钟完成部署**

##### 2. 先审计、后执行：连拒绝操作也要记录

OneCamp 将审计日志放在操作执行之前：

- 系统先写入审计记录，再执行操作。
- 如果日志写入失败，本次调用会直接中止。
- 相比 “操作已经发生但没有记录”，这种机制更有利于事后追查。

审计范围不仅包括成功操作，也包括被拒绝的调用，记录内容包括：

- 使用的工具与操作内容
- 允许或拒绝的决定及原因
- 使用的凭据
- 具名智能体
- 智能体背后的具体人员

因此，安全审查不仅能知道 “AI 做了什么”，还能知道 “AI 尝试做什么但被系统阻止”。

##### 3. 防篡改审计：历史记录可独立验证

每条审计日志都会同时计算：

1. 当前条目内容的哈希；
2. 前一条记录的哈希。

这些记录形成哈希链，后续插入、修改或删除任意内容都会破坏链条。系统提供：

- 审计链验证端点，可报告第一个不一致的位置；
- 带逐行哈希的 CSV、JSON 导出；
- 管理员变更、智能体调用及拒绝记录的统一追踪。

审计人员无需完全信任 OneCamp 的界面，也能独立核验导出数据是否被改动。

##### 4. AI 与数据可以留在企业内部

OneCamp 默认支持通过**Ollama**在本地运行模型，聊天、文档和转录内容可留在自有设备或网络中。

主要控制措施包括：

- **仅本地模式**：开启后，服务器会直接拒绝启用任何云模型，而不是只发出警告。
- **外部模型可选**：可连接 OpenAI、Anthropic、vLLM、LM Studio、OpenRouter、Groq 或其他兼容 OpenAI 的端点。
- **PII 脱敏**：数据发往外部模型前，可先删除或遮蔽个人身份信息。
- **无遥测收集**：自托管实例不会主动向厂商回传数据。
- **数据驻留取决于自有服务器位置**，数据库不与其他客户共享。

使用 OneCamp Cloud 时，AI 功能已预置，但模型密钥由客户自行提供；官方表示不转售推理服务，也不会查看提示词。

##### 5. 员工离职时，智能体和令牌同步失效

人员停用后，系统会在每个授权入口重新检查资格，因此下列访问能力会立即停止：

- 用户会话
- API 令牌
- 代表该员工运行的智能体
- 外部 MCP 客户端等代理操作

企业不需要再逐个寻找并撤销散落的凭据。平台支持：

- SAML 2.0、OIDC、LDAP 登录
- SCIM 2.0 自动入职与离职
- TOTP 双因素认证与恢复代码
- 角色、项目及成员权限模型

由身份提供商创建的账户只能通过该身份提供商验证，不能额外设置本地密码来绕过公司登录流程。

#### OneCamp 真正值得关注的，不是自托管，而是把 AI 权限落实到每一次行动

OneCamp 看起来像 Slack、Notion、Asana、Zoom 等工具的自托管合集，但页面最有价值的部分并非“一次部署替代多款 SaaS”，而是一套更具体的智能体治理顺序：**先确认当前权限、再写入审计记录、最后执行操作。**

###### 它解决的是“谁授权了这次行动”

常见 AI 助手获得一个长期令牌后，权限容易与真实组织状态脱节：员工已被移出项目，智能体仍可能沿用旧权限；操作失败或被拒绝，也往往只留下难以追责的技术日志。

OneCamp 的设计针对了这两个缺口。智能体继承具名用户的权限，每次调用都重新读取成员关系；人员离职后，其会话、令牌和智能体随即失效。审计记录则在操作之前写入，写入失败便拒绝执行，同时记录被拒绝的尝试。这意味着审查者不仅能看到“发生了什么”，还可以追问“谁授权、为何允许、系统阻止过什么”。

这种机制比“模型承诺遵守规则”可靠，因为约束位于执行层，而非提示词中。它也揭示了一个更普遍的产品判断：**企业 AI 的控制点不应只放在模型入口，而应放在每一次工具调用与数据访问上。**

###### 统一工作区既是优势，也是采用障碍

聊天、文档、任务和权限都在同一系统内，使 OneCamp 能共享一张身份图谱和一套审计链。相比横跨 Slack、Notion、GitHub 等系统的智能体，这显著减少了令牌散落、权限语义不一致和撤权延迟。

但这也解释了它为何要做一个庞大的协作套件：治理优势部分依赖用户把工作迁入它的边界。对已有成熟工具链的公司，替换成本、功能深度和员工习惯可能远比部署 Docker 更难解决。因此，它更可能先打动重视自托管、成本敏感或正在新建工具栈的小团队，而不是仅凭治理卖点进入大型企业。

###### “可审计”仍不等于“安全”

页面中的强主张还需要验证。智能体不能超过用户权限，并不代表它不会在用户权限内做错事；高权限员工遭遇提示注入时，仍可能触发危险但“合法”的操作。真正成熟的治理还需要任务级授权、限速、敏感动作审批和独立于所有者的最小权限。

同样，哈希链只能证明历史被改动过，未必能阻止控制服务器的人重建整条链。若没有外部签名锚点、只写存储或独立日志副本，“防篡改”更准确地说是“篡改可检测”。而且目前开源的是前端，后端为可持续运行的二进制；一次性付费、不收年费的模式，能否长期支撑安全更新也值得关注。

因此，评估 OneCamp 不应先比较功能清单，而应做几项压力测试：撤权是否真的在下一次调用生效、日志写入失败是否严格关闭、外部集成是否沿用同样的授权检查、管理员能否重写审计历史。**它提出了正确的问题，也给出了颇有价值的工程答案；但安全产品的可信度，最终来自可验证的失效表现，而不是页面上的保证。**

## 口播总结（1）

### 2026-09-20 00:20:39

OneCamp 想解决的，不只是把人工智能接入办公软件，而是一个更关键的问题：当智能体能够读取文档、处理任务、发送消息时，谁来限制它的权限，又由谁为它的行为负责？

这是一套部署在自己服务器上的协作工作区。它把聊天、文档、任务、表格、白板、视频会议和日历放在同一个系统里，再让人工智能直接参与这些工作。产品最核心的主张是：人工智能获得的是可实时核查的权限，而不是一份“请勿越界”的承诺。

很多人工智能助手接入公司知识库、工单和聊天系统后，短短一周内，能够触达的信息可能比大多数员工还多。但这些权限究竟是谁授予的，常常说不清楚。出了问题，日志里也可能只有一个令牌编号，看不出背后由哪个人负责。

OneCamp 的做法是，让每个智能体继承一个具体用户的权限。这个用户看不到的频道、项目或文档，智能体也看不到。智能体代表用户执行操作时，也不能超出这个用户本来能够完成的范围。

更重要的是，权限不是在创建智能体时检查一次，然后长期缓存。系统会在每一次调用发生时，重新读取用户当前的权限。假如某人被移出一个频道，代表这个人行动的智能体，会在下一次请求时立即失去访问权，而不是等到令牌刷新之后才生效。

这套设计也覆盖人员离职。管理员停用一个账户，或者通过企业目录自动取消账户后，与这个人关联的登录会话、应用程序接口令牌和智能体都会立即失效。管理员不需要再去不同系统里逐一寻找和撤销凭据。

可以把这个原则概括成一句话：智能体不是一个拥有独立特权的超级用户，而是一个受到具体人员权限约束的代理人。

第二个重点，是操作必须先留下记录，才能真正执行。

通常的日志是在操作完成后写入。如果日志系统当时发生故障，就可能出现操作已经发生，却没有留下记录的情况。OneCamp 把顺序反了过来。审计条目先写入，写入成功后才执行操作。如果审计记录无法写入，这次调用就会被中止。

被拒绝的调用也会记录。日志不仅说明智能体做成了什么，还会记录它试图做什么、为什么被阻止、使用了什么凭据、涉及哪个智能体，以及背后由哪个人负责。发生安全事件后，这些被拒绝的尝试往往和成功操作同样重要。

审计历史采用哈希链。简单理解，每条记录都会包含自身内容和上一条记录的数字指纹。有人事后插入、修改或删除记录，链条就会断裂。验证工具能够重新计算整条链，并指出最早出现差异的位置。导出的表格或数据文件也带有每一行的哈希值，因此审计人员不必只相信管理界面。

这里要注意，哈希链并不是让记录在技术上绝对无法修改，而是让修改能够被检测出来。真正关键的组合是：操作前记录、写入失败就拒绝执行、成功与失败都留痕，再加上可验证的历史链条。

第三个重点，是数据和模型可以留在自己的基础设施中。

OneCamp 通过 Docker 部署在团队控制的服务器上。厂商称，常规安装通常不到十分钟，安装程序会处理数据库和安全连接。其他成员不必安装桌面软件，只需使用浏览器或支持推送通知的网页应用。

人工智能可以通过 Ollama 在本地运行，也可以连接 OpenAI、Anthropic，或者其他兼容接口的模型服务。开启“仅本地模式”后，服务器会直接拒绝启用云端模型，而不只是弹出警告。需要调用外部模型时，系统还可以在数据发出之前，对个人身份信息进行脱敏。

这意味着，本地运行和云端调用是两种不同选择。本地模式更有利于控制数据去向，但较大的模型可能需要图形处理器。普通场景也可以让模型运行在外部供应商的硬件上，因此部署 OneCamp 本身并不要求配备图形处理器。

在身份管理方面，系统支持企业单点登录、目录服务、自动入职和离职，以及双因素认证。由企业身份提供商创建的账户，不能再添加一个本地密码来绕过统一认证流程。

不过，治理只有和实际工作结合起来才有意义。OneCamp 不只是一个审计层，它本身也是办公工作区。智能体可以在频道或私信中回复，也可以按计划运行，整理任务、归档信息和发布摘要。团队可以允许它自动行动，也可以要求它先提出建议，等人确认后再执行。

同一个工作区还提供聊天、文档、看板任务、数据库式表格、白板、视频和日历。比如，支持频道里出现带有“错误”字样的新消息时，自动创建分诊任务；视频会议结束后，可以生成摘要并发回频道；人工智能也能从频道、文档、任务，以及连接的邮箱或代码平台中寻找答案，并附上引用来源。

这套整合的价值，在于减少工具之间的权限断层。聊天和任务不必依靠外部自动化工具保持同步，智能体也不需要在多个独立系统里分别获得一套难以追踪的权限。

在商业模式上，OneCamp 强调自托管、一次购买和不限用户数，不把单点登录、智能体或审计日志放进额外的企业版本。厂商也提供托管云服务，并称云服务包含自托管许可证，方便以后迁移。其前端代码开源，后端以已获得的程序运行。厂商表示，实例不会主动联系其服务器；即使公司停止运营，已经部署的实例仍可继续工作。

当然，这些功能、安装时间和运行效果主要来自产品方自己的说明。实际性能仍取决于团队规模、视频负载和本地模型的使用强度。厂商给出的参考是，五十人以内可以从八吉字节内存和四个虚拟处理器核心起步。人数更多，或者需要长时间运行本地人工智能和视频服务，就应增加资源。

最值得记住的是，OneCamp 对人工智能治理的理解不是“相信智能体会守规矩”，而是让越权操作在系统设计上难以发生。权限在每次调用时重新检查，操作在执行前必须留下记录，拒绝行为同样可以追踪。再加上自托管和仅本地模式，它试图把人工智能从一个权限模糊的外部助手，变成一个有明确授权人、明确边界和完整责任链的团队成员。
