## 分析要点

- **核心高价值点**：核心洞见是不要让LLM直接操作底层API或自由代码，而应通过领域DSL、编译器式IR和验证契约构建可控的Agent工作流。
- **留存建议**：长期保留（文章提出了较完整的Agent-friendly软件架构范式，包含DSL、IR/DAG、验证契约、修复循环和确定性执行等可复用方法，对AI原生系统设计具有长期参考价值。）

**知识要点**

- Agent适合处理模糊意图和高层规划，不适合长期承担低层精确控制与确定性计算。
- 领域DSL可以作为大模型的语义脚手架，将底层计算、校验、容错下沉到确定性引擎。
- IR/DAG编译管线能带来静态分析、依赖追踪、拓扑排序、局部重算和确定性执行能力。
- 机器可读的Validation Contract比面向人的错误提示更适合Agent自我修复。
- 稳定Agent系统需要形成Intent → Domain DSL → IR/DAG → Validation → Repair Loop → Execution的闭环。
- 概率性层与确定性层应分离：LLM负责意图理解和表达转换，传统代码负责验证、编译、队列和状态机。

**行动项**

- 在自己的Agent项目中梳理是否存在可抽象为DSL的稳定领域原语。
- 避免让LLM直接生成底层自由代码或深层嵌套API调用，改为设计受限表达空间。
- 为Agent生成内容增加JSON Schema、禁止项和机器可读错误反馈。
- 评估现有系统是否能引入IR/DAG层，以支持验证、依赖分析和局部修复。
- 将Agent职责拆分为模糊意图处理层与确定性执行引擎层。

## 正文

前段时间，我一直在思考如何让 Agent 在复杂的虚拟环境中稳定地执行任务。当时，我偶然看到了一个名叫 [mindcraft](https://github.com/mindcraft-bots/mindcraft) 的开源项目。这个项目能在 Minecraft 的局域网模式下，通过 harness 代理，让大模型作为一个 Bot 进入到游戏世界里。你可以直接在游戏里发消息，用自然语言给它下发命令，比如说“建一个房子”， Bot 就会真的开始动工建造。

这个演示很有意思，但当我亲自尝试时，发现 Bot 的稳定性并不理想。它经常会原地卡住，即便只是建一个很小的房子，也往往做到一半就停滞。原因可能来自环境感知、动作执行、路径规划、上下文维护等多个环节，但最终暴露出的共同问题是：让大模型在游戏内实时闭环控制空间动作，稳定性很难保证。

我开始研究背后的原因。如果要通过“指令式”的步骤让大模型一块一块地去放置方块，就要求模型必须精准地理解游戏内的三维空间坐标，并同时处理庞大的环境上下文。这要求模型长期维护三维空间状态、理解环境反馈、持续做精确坐标推理。对当前 LLM 来说，这类闭环控制任务非常容易累积误差。

退而求其次，我开始寻找别的出路。如果在游戏内实时建造太容易卡死，那我能不能在游戏外通过大模型生成好建筑的蓝图，然后再通过一些 Mod 自动加载到游戏里？我顺藤摸瓜地发现了 WorldEdit 以及围绕 schematic 的 Minecraft 建筑工具链。于是，我的核心思路发生了一次转变： **如何通过 LLM 生成可被 WorldEdit 或相关工具加载的.schem 蓝图文件？**

这也是我后来构建开源项目 [MinePilot](https://github.com/i365dev/MinePilot) 的直接起点。

但这依然没有解决根本问题。.schem 这类蓝图格式本质上仍然是低层的方块状态集合：每一个位置最终都要对应具体的 block state 。让大模型直接生成这种低层体素数据，仍然很容易出现墙体漏风、屋顶错位、楼梯断裂等问题。

这时，我想起了之前在开发量化投资系统 [策引（MyInvestPilot）](https://www.myinvestpilot.com/) 时遇到的类似问题。正如我在 [《我是如何构建一个 AI 原生量化系统的》](https://www.bmpi.dev/dev/ai-native-investment-system/) 一文中提到的，为了防止大模型写出带有前视偏差（Look-ahead bias）的 Python 交易代码，我引入了一套“策略原语引擎”的范式：放弃让大模型直接生成底层逻辑代码，转而提供一套基于 DSL 的有向无环图（DAG ） ，从而创造一个受限的空间，让大模型在这个空间里进行架构表达。

这其实是一个高度抽象的范式。它不仅能用于量化投资，也可以用来让 Agent 稳定地处理其他领域的复杂任务。这本质上是一个通用工作流，一个面向 Agent 友好的系统架构设计，也就是让 Agent 能够读取、编写、验证、执行和修复任务的 workflow surface 。

目前，我主要在策引与 MinePilot 这两个看起来风马牛不相及的项目上实践这套工作流。在连续重构了它们之后，我发现这套架构实际上跑在了完全相同的底层逻辑上。

#### 从底层API到Domain DSL的跃迁

很多 AI 产品的开发者在意识到“让 AI 写自由代码不可靠”之后，往往会走向另一个极端：提供极其精细的结构化 API 。

比如在量化投资中，一种常见做法是要求 AI 返回一个多层嵌套的 JSON 树来表示策略；在 Minecraft 中，另一种做法是要求 AI 每次只能调用 `placeBlock(x, y, z, type)` API 。

这种做法的扩展性很差。一旦策略稍微复杂（例如“ QQQ 相对强度大于 101 买入，小于 99 且连续两日确认才卖出” ） ， API 参数结构就会爆炸式膨胀。大模型在生成这种深层嵌套的结构时，非常容易遗漏字段或者写错类型。让大模型去手写几万个方块的放置坐标也是同理，这直接消耗了它在“空间规划”上的推理窗口，将其浪费在了底层的算术计算上。

##### 收拢底层控制权

更好的解法是： **收拢 Agent 的底层控制权，为它专门设计一门领域特定语言（Domain DSL ） 。**

在量化投资系统策引中，我没有让大模型写底层计算逻辑，而是抽象出了一套“策略原语”（Primitives ） 。这些原语包括均线（EMA ） 、逻辑判断（GreaterThan/LessThan ） 、状态延迟（Lag）和连续状态确认（Streak ） 。大模型只需要像搭积木一样组合这些原语。底层的 Pandas 运算、对齐、未来函数屏蔽，统统由系统封装。

在 MinePilot 的底层引擎 [CraftDAG](https://github.com/i365dev/CraftDAG) 中，我也是这么做的。我设计了一套名为 `ComponentPlan` 的 DSL 。

在 ComponentPlan 这一层，大模型不需要也不应该直接输出底层方块坐标。大模型只需要写高层的组件级规划。比如，大模型只需要生成这样一段 JSON 意图：

> “创建一个 16×12×16 的 `RoomShell` （房间壳体 ） ，在 `front` （前）墙面的 `offset: 3` （偏移 3 格）处安装一个 `Door` ，在上方放置一个 `GableRoof` （人字屋顶 ） ，并设定 `overhang: 1` （屋檐延伸 1 格 ） 。 ”

##### 为Agent搭建的“语义脚手架”

通过这套 DSL ，大模型不再需要去计算“这面墙的坐标是从 (10, 5, 20) 到 (10, 10, 20) ”，也不需要计算“门挖掉之后要替换成空气方块”。它使用了 `anchor` （锚点 ） 、 `wall` （依附墙面 ） 、 `offset` （偏移 ） 、 `overhang` （悬空）等高层语义属性。

DSL 的本质，是为大模型搭建一个“语义脚手架”。把底层的物理碰撞、数学计算、工程容错全部被下沉到引擎侧。 Agent 的心智负担大大降低，它可以将有限的上下文窗口和推理预算投入到它更擅长的事情上——宏观架构与逻辑推演。

这个阶段的核心原则是： **Agent is the author. Engine is the compiler.**

#### 像写编译器一样构建业务引擎

既然大模型生成的是高层的 DSL （意图 ） ，那么系统要如何执行它？这就来到了整个面向 Agent 工作流中最重的一层：中间表示（IR）与编译器设计。

当大模型交出了一份 `ComponentPlan` （ Minecraft 建筑计划）或是一份 `Strategy primitives` （量化策略图谱 ） ，这只是人类意图和机器执行之间的中间态。它不能直接拿去盖房子，也不能直接拿去回测投资组合。

你需要像写一门编程语言的编译器一样，来构建你的业务引擎。

##### 分层编译管线

在 CraftDAG 中，建筑生成被设计成一条相对严格的编译管线：

1. **输入层（BuildIntent ）** ：用户的自然语言意图。
2. **领域计划层（ComponentPlan DSL ）** ：由大模型根据意图生成的建筑组件图纸。
3. **中间表示层（CraftDAG IR ）** ：引擎接收 ComponentPlan ，进行宏观和局部的依赖解析，将其展开为一张可验证、可排序的有向无环图（DAG ） 。在这里，高级语义被降级为确定性的几何包围盒计算和依附关系计算。
4. **目标表示层（VoxelPlan ）** ：编译器进一步向下，将 IR 计算为最终的三维体素集合（方块的绝对坐标与状态 ） ，生成蓝图导出，或者供前端 / 后端直接渲染。

同样，在策引中， AI 组合的“策略原语”也会被引擎转化为一张有向无环图。它通过拓扑排序（Topological Sort）决定先计算哪些均线指标，再计算哪些比较逻辑，最后聚合为交易信号。这个可以查看 [策引原语策略可视化编辑器](https://www.myinvestpilot.com/primitives-editor) 来直观的感受下。

##### 为什么要走编译路线？

一开始，我觉得为一个应用引入“编译器”和“抽象语法树”的概念有些过度设计。但后来的迭代证明，这是支撑 Agent 系统稳定运行的有效方式。

只有将意图降级为有向无环图（IR/DAG ） ，系统才具备了强大的 **静态分析** 与 **确定性执行** 能力。

- 在量化系统中，因为有了 DAG ，系统可以清晰地追踪信号依赖，确保没有任何一个环节偷看了未来数据。
- 在 Minecraft 引擎中，因为有了 IR ，系统可以计算出极其精确的材料清单（Material Lists ） 。理论上，这种 IR 分层也为未来的局部重算提供了基础：当用户只修改屋顶材质时，系统可以只重新处理相关子图，而不必让大模型重新生成整栋建筑。

更重要的是，有了这层编译机制，才有了下一步拦截 Agent 幻觉的可能。

#### 机器可读的契约与修复循环

我们一直被图形用户界面（GUI）的交互惯性所束缚。在传统软件中，如果用户填错了表单，系统会弹出一个红框或者 Toast 提示 ： “输入格式不合法”。用户看到红框，凭借生活经验重新输入。

但是，如果只把一句简单的 `Invalid plan` 或者 `Syntax Error` 返回给大模型，它的修复效率会非常低。它往往只能靠猜测去重写整个 JSON ，有时修复了一个错误，反而会引发新的错误。

在 Agent-friendly 的系统里， **报错不再是给人看的，而是系统与大模型之间的一纸强契约（Validation Contract ）** 。

##### 报错不是给人看的

在开发 CraftDAG 时，我专门为系统设计了一套详尽的强类型错误反馈机制。如果大模型在生成 DSL 时，不小心把一个塔楼组件的坐标放到了整个建筑设定的边界之外，系统的编译器会在第一道防线将它拦下，并抛出一个精确的 JSON 报错：

```json
{
  "stage": "component-validation",
  "code": "ASSEMBLY_INSTANCE_OUT_OF_BOUNDS",
  "path": "instances[0].anchor",
  "componentId": "northwest_tower",
  "repairHint": "Move the instance inward or increase global bounds."
}
```

你看，这个报错完全不是给人看的。它明确告诉大模型：

1. **stage** ：错误发生在组件验证阶段。
2. **code** ：越界错误。
3. **path** ：具体的 JSON 路径是第一个实例的锚点。
4. **repairHint** ：直接给出具体的修复建议（向内移动锚点，或者扩大全局边界 ） 。

##### LLM的协作契约与修复循环

除了事后的精准报错，事前的约束同样重要。

在 CraftDAG 项目里，有一份核心文件叫 `LLM_AUTHORING_CONTRACT.md` （ LLM 编写契约 ） 。这不是传统意义上给人类开发者看的 API 文档，而是一份可以被大模型或 harness agent 读取的编写契约，也可以作为 System Prompt 或 llm.txt 的一部分。

同样地，在策引（MyInvestPilot）中我也做了类似的事情。为了让 Agent 能够独立开发策略原语，系统专门提供了一篇 [机器可读的开发文档](https://www.myinvestpilot.com/docs/primitives/ai-assisted-development) ，并通过 [llm-quickstart.txt](https://www.myinvestpilot.com/docs/primitives/_llm/llm-quickstart.txt) 为大模型提供紧凑的上下文和 Few-shot 示例。此外，引擎还暴露出严格的 [JSON Schema](https://media.i365.tech/myinvestpilot/primitives_schema.json) ，让大模型在生成 DSL 时能够依循一套确定的强类型结构契约。

在这些契约的设计上，我学到的一个深刻教训是： **与其告诉大模型“你应该怎么做”，不如直接设定绝对禁止项（ABSOLUTE PROHIBITIONS ） 。** 不要试图去穷举大模型能发挥的创意，而是划定死亡红线。例如，明确禁止在组件的 `inputs` 里直接内联嵌套其他组件，必须先定义 `id` 再通过 `ref` 引用。

只有当系统具备了“严格的事前契约”和“精准的事后报错”时，一个重要变化才会发生： **大模型开始具备更稳定的自我修复路径。**

当大模型收到上述的 JSON 报错后，它会立刻明白 `northwest_tower` 出了问题，接着在下一次迭代中只修正这个组件的坐标，然后再次提交编译。这就形成了一个稳定、可收敛的 **迭代修复循环（Repair Loop ）** 。没有这个循环，大模型就是一个偶尔好用的玩具；有了这个循环，大模型就真正变成了可靠的生产力基建。

#### 处理模糊与确定性的边界

做好了底层引擎，最后一个问题是：用户该如何介入这套复杂的系统？

用户不会写 JSON DSL ，也不会看懂 DAG 图。他们依然会用自然语言提问 ： “帮我调整一下这个投资组合的风险”，或者“给这个城堡多加两扇大一点的窗户”。

这就引出了一个核心架构矛盾：用户的意图往往是 **模糊的** ，而底层的金融计算和空间几何却是 **绝对确定性的** 。如果你试图让一个全能大模型去同时处理这两端，系统立刻就会在“发散思考”和“严谨计算”之间精神分裂。

##### 本地与远端的职责切割

在我对这类系统的架构设想里，比较理想的方式是采用 **混合 Agent 架构（Hybrid Agent Architecture ）** 。未来 MinePilot 这样的系统可以采用这种拆分，将 Agent 的职责进行硬切割：

- **本地 Agent （Orchestrator/Local Agent ）** ：运行在离用户最近的交互层（比如前端浏览器 ） 。它本质上是一个高级的路由器和状态机。它的唯一职责是处理 **模糊性（Ambiguity ）** 。它和用户聊天，猜测用户的意图，并在必要时发起明确的表单让用户确认。
- **远端处理器（Processor/Remote Engine ）** ：运行在后端的异步任务队列中。当本地 Agent 把模糊的意图清晰化之后，将任务作为结构化的 Job 扔到远端。远端处理器接管 DSL ，运行编译器图元，执行相对复杂的确定性验证、编译与计算。

队列、状态机、编译验证，这些涉及绝对准确率的东西，必须由传统的确定性代码来实现；而意图猜测、错误文本解释、自然语言翻译，这些概率性的事情，全权交由大模型。

**把确定性层和概率性层混在一起，是很多 Agent 系统容易犯的架构错误。**

#### 这套范式的边界

需要强调的是， Agent-friendly workflow 并不是所有 AI 产品的通用解法。它更适合那些具备以下特征的领域：

1. 有明确的领域结构；
2. 可以抽象出稳定的原语或组件；
3. 中间状态可以被验证；
4. 最终结果可以被执行、编译或模拟；
5. 错误可以被定位并修复；
6. 人类仍然可以审查和决策。

如果一个任务本身是高度开放的创意表达，或者没有明确的验证标准，过早引入 DSL 和 DAG 反而可能限制模型的表达能力。同时， DSL 也不是越多越好，真正困难的是找到足够小、足够正交、又能覆盖主要任务的领域原语集。

即便在适合的领域里， Validation 也不等于真实的正确性。投资策略通过回测不代表未来有效；建筑蓝图通过编译不代表审美优秀。验证契约的价值，是把错误空间缩小到系统可以管理的范围，而不是替代人类的最终判断。 Agent-friendly 并不是替代 Human-friendly ，更合理的形态是 dual interface ：人通过 UI 表达意图、审查结果、做决策； Agent 通过 DSL 、工具和验证契约操作系统。

#### 软件架构视角的反转

回头审视策引（MyInvestPilot）和 MinePilot 这两个项目，一个是严肃的金融投资，一个是开放的沙盒游戏。它们在业务逻辑上相隔万里，但在持续的开发重构过程中，却自然而然地收敛到了同一套系统范式上：

`意图 (Intent)` → `领域语言 (Domain DSL)` → `编译器 (IR/DAG)` → `精准契约验证 (Validation)` → `迭代修复 (Repair Loop)` → `确定性执行 (Execution)`

过去几十年里，我们设计一款软件的标准流程是：先画出供人类交互的原型界面，再设计底层的数据库表结构，最后编写中间的胶水 API 把它们连起来。

但在 AI Agent 即将大面积接管复杂任务的时代，设计软件的顺序可能被彻底反转了：

1. 先问自己：这项复杂的业务，能不能抽象出一套对 Agent 足够克制、能收拢底层控制权的领域语言（DSL ） ？
2. 再问自己：系统有没有强大的编译器内核，能将 DSL 降级为确定性的有向无环图，并提供精确的机器验证契约？
3. 然后问自己：当模型犯错时，你的系统是不是能给它提供机器可读的纠错反馈，建立起闭环的修复循环？
4. 最后，才是在这套相对稳定的工作流基础之上，为人类包裹一层用来监督和确认的交互界面。

我暂且把这种范式称为： **Domain-shaped, not Domain-locked** 。

把复杂的专业知识重塑为对 Agent 可读、可写、可验证、可迭代的工作流，或许才是通向下一代软件架构的一把钥匙。

## 通俗精炼（1）

#### Agent 时代的软件接口：从 API 到 DSL + 编译器

##### 核心观点

文章提出：**面向 AI Agent 的软件系统，不能再只依赖传统 API 或让大模型直接写代码，而应设计“Agent 友好”的领域工作流**。

这个工作流可以概括为：

> **Intent 用户意图 → Domain DSL 领域语言 → IR/DAG 编译中间层 → Validation 校验 → Repair Loop 修复循环 → Deterministic Execution 确定性执行**

---

##### 1. 问题：让大模型直接控制复杂系统不稳定

作者最初尝试让大模型在 Minecraft 中直接执行建造任务，比如“建一个房子”。

但实践发现，大模型在实时环境中容易卡住，原因包括：

- 三维空间理解困难
- 坐标推理容易出错
- 环境反馈复杂
- 长程状态维护不稳定
- 动作执行会累积误差

结论是：**让 LLM 直接做底层闭环控制，稳定性很差。**

---

##### 2. 关键转变：不要让 AI 操作底层，而是表达高层意图

作者从两个项目中得到同一套方法：

- **MinePilot**：让 AI 生成 Minecraft 建筑方案
- **策引 MyInvestPilot**：让 AI 生成量化投资策略

共同经验是：

> 不让大模型直接生成底层代码、坐标或复杂 JSON，而是提供一套领域 DSL，让它像搭积木一样表达意图。

例如在 Minecraft 中，AI 不需要输出每个方块坐标，而是描述：

- 创建一个房间壳体
- 在前墙偏移 3 格处放门
- 添加人字屋顶
- 设置屋檐延伸

底层坐标、碰撞、方块填充等由系统引擎完成。

---

##### 3. DSL 的本质：给 Agent 搭“语义脚手架”

DSL 的作用不是限制 AI，而是降低它的认知负担。

大模型擅长：

- 理解自然语言
- 做宏观规划
- 组合概念
- 推理结构关系

大模型不擅长：

- 精确坐标计算
- 底层状态管理
- 长链路工程细节
- 严格执行一致性

因此，系统应遵循：

> **Agent is the author. Engine is the compiler.**  
> Agent 负责创作，系统引擎负责编译和执行。

---

##### 4. 像写编译器一样构建业务系统

当 AI 输出 DSL 后，不能直接执行，而要经过编译管线。

以 MinePilot 为例：

1. **BuildIntent**：用户的自然语言意图  
2. **ComponentPlan DSL**：AI 生成的组件级建筑方案  
3. **CraftDAG IR**：系统解析为可验证、可排序的 DAG  
4. **VoxelPlan**：最终生成具体方块坐标和状态  

量化投资系统中也类似：

- AI 组合策略原语
- 系统转成 DAG
- 通过拓扑排序计算指标、信号和交易逻辑

这样做的价值是：

- 可静态分析
- 可验证依赖关系
- 可确定性执行
- 可局部重算
- 可拦截 AI 幻觉

---

##### 5. 报错也要面向 Agent 设计

传统软件的错误提示是给人看的，比如“格式错误”。

但 Agent 系统里的报错应该是**机器可读的协作契约**，例如：

```json
{
  "stage": "component-validation",
  "code": "ASSEMBLY_INSTANCE_OUT_OF_BOUNDS",
  "path": "instances[0].anchor",
  "repairHint": "Move the instance inward or increase global bounds."
}
```

这种错误信息会明确告诉大模型：

- 错在哪个阶段
- 错误类型是什么
- JSON 路径在哪里
- 应该如何修复

这样，大模型就能进行稳定的自我修复，而不是盲目重写。

---

##### 6. 关键机制：契约 + 校验 + 修复循环

一个可靠的 Agent 系统需要两类约束：

###### 事前约束

通过文档、Schema、规则告诉大模型：

- 可以写什么
- 不能写什么
- 必须遵守哪些结构
- 哪些行为绝对禁止

作者强调：  
**与其告诉模型“应该怎么做”，不如明确告诉它“绝对不能做什么”。**

###### 事后校验

系统通过强类型校验、编译器检查、错误反馈，告诉模型哪里错了。

最终形成：

> 生成 → 校验 → 报错 → 修复 → 再校验 → 执行

这就是 **Repair Loop 修复循环**。

它是 Agent 从“玩具”变成“生产力基础设施”的关键。

---

##### 7. 架构原则：概率性归 AI，确定性归系统

作者提出一种混合 Agent 架构：

###### 本地 Agent

负责处理模糊性：

- 和用户对话
- 理解意图
- 澄清需求
- 组织交互

###### 远端 Engine

负责确定性任务：

- 队列调度
- 状态机
- DSL 编译
- DAG 校验
- 精确计算
- 结果执行

核心原则是：

> **模糊的事情交给大模型，确定性的事情交给传统代码。**

很多 Agent 系统失败，是因为把概率性推理和确定性执行混在一起。

---

##### 8. 适用边界：不是所有 AI 产品都适合

这套范式适合以下领域：

- 有明确领域结构
- 能抽象出稳定原语
- 中间状态可以验证
- 最终结果可以执行或模拟
- 错误可以定位和修复
- 人类可以审查和决策

但它不适合所有任务。

如果任务高度开放、创意性强、缺乏验证标准，过早引入 DSL 和 DAG 可能会限制模型能力。

同时，验证不等于真实正确：

- 投资策略回测通过，不代表未来赚钱
- 建筑蓝图编译成功，不代表审美优秀

人类仍然需要最终判断。

---

##### 9. 软件设计顺序正在反转

传统软件设计通常是：

> 先设计 UI → 再设计数据库 → 最后设计 API

但 Agent 时代可能变成：

> 先设计 DSL → 再设计编译器和验证机制 → 再设计修复循环 → 最后设计人类 UI

也就是说，未来软件不仅要 Human-friendly，也要 Agent-friendly。

更理想的形态是：

- 人通过 UI 表达意图、审查结果、做决策
- Agent 通过 DSL、工具、验证契约操作系统

---

##### 总结

文章的核心洞察是：

> Agent 时代的软件接口，不应只是传统 API，而应是面向 Agent 的领域语言、编译器、验证契约和修复循环。

真正可靠的 AI 原生系统，不是让大模型直接控制一切，而是：

- 让 AI 负责高层意图和结构表达
- 让 DSL 收拢底层复杂性
- 让编译器负责确定性转换
- 让校验机制拦截错误
- 让修复循环持续收敛
- 让人类保留最终审查权

这是一种新的软件架构范式：

> **Domain-shaped, not Domain-locked.**  
> 用领域结构塑造 Agent 能力，而不是把它锁死在底层操作里。

## 结构化（1）

### 2026-06-15 10:30:35

#### 《Agent 时代的软件接口》精炼总结

本文核心观点是：**面向 AI Agent 的软件系统，不能简单让大模型直接操作底层 API 或自由写代码，而应通过领域 DSL、编译器式引擎、验证契约和修复循环，构建可读、可写、可验证、可执行的工作流。**  
作者通过两个项目——量化投资系统 **策引（MyInvestPilot）** 和 Minecraft 建筑生成项目 **MinePilot / CraftDAG**，说明这种架构范式在不同领域中的共通性。

---

##### 1. 从 Minecraft Agent 实验出发：直接控制环境不稳定

作者最初关注如何让 Agent 在复杂虚拟环境中稳定执行任务，并尝试了开源项目 **mindcraft**：

- mindcraft 可以让大模型作为 Bot 进入 Minecraft 世界；
- 用户可以用自然语言命令 Bot，例如“建一个房子”；
- Bot 会尝试在游戏中实时执行建造任务。

但实际体验中，Bot 很容易失败：

- 经常原地卡住；
- 小房子也可能建到一半停滞；
- 问题可能来自环境感知、路径规划、动作执行、上下文维护等环节。

作者认为，根本原因是：  
**让 LLM 在游戏中实时闭环控制三维空间动作，非常容易积累误差。**

例如，如果要求大模型一块一块放置方块，它必须同时做到：

- 理解三维坐标；
- 维护长期空间状态；
- 根据环境反馈修正动作；
- 持续进行精确坐标推理。

这对当前 LLM 来说并不可靠。

---

##### 2. 从实时控制转向蓝图生成：MinePilot 的起点

由于实时建造不稳定，作者转向另一种思路：

> 不让 Agent 在游戏里实时盖房子，而是在游戏外生成建筑蓝图，再通过工具导入 Minecraft。

于是作者研究了：

- **WorldEdit**
- Minecraft 的 **schematic / .schem** 建筑工具链

这成为开源项目 **MinePilot** 的直接起点。

但问题仍然存在：

- `.schem` 文件本质上还是低层方块状态集合；
- 每个位置都要对应具体的 `block state`；
- 让大模型直接生成低层体素数据，仍然容易出错。

典型错误包括：

- 墙体漏风；
- 屋顶错位；
- 楼梯断裂。

这说明：  
**即便不做实时控制，让大模型直接生成底层数据仍然不可靠。**

---

##### 3. 类比量化系统：不要让大模型直接写底层逻辑

作者联想到自己在开发量化投资系统 **策引（MyInvestPilot）** 时遇到的类似问题。

在量化系统中，如果让大模型直接写 Python 交易策略代码，可能出现严重问题，例如：

- 写出带有 **前视偏差（Look-ahead bias）** 的代码；
- 在回测中“偷看未来数据”；
- 导致策略结果虚假优秀。

为避免这种问题，作者引入了“策略原语引擎”：

- 不让大模型直接写底层 Python 逻辑；
- 而是让它组合一套受限的领域原语；
- 这些原语组成一个 **DSL + DAG** 的结构。

这给作者一个重要启发：

> 面向 Agent 的系统，不应让模型直接操作底层实现，而应提供一个受控、可验证的表达空间。

---

##### 4. 从底层 API 到 Domain DSL：收拢 Agent 的控制权

很多 AI 产品在发现“让 AI 写自由代码不可靠”后，会转向提供精细 API。

例如：

- 量化投资中，让 AI 返回复杂嵌套 JSON 表达策略；
- Minecraft 中，让 AI 调用 `placeBlock(x, y, z, type)` 一块块放方块。

但作者认为，这种方式扩展性很差。

###### 典型问题

如果策略稍微复杂，比如：

> “QQQ 相对强度大于 101 买入，小于 99 且连续两日确认才卖出”

那么 API 参数会迅速膨胀，大模型容易：

- 漏字段；
- 写错类型；
- 结构嵌套混乱。

Minecraft 中也类似：  
让模型手写几万个方块坐标，会浪费大量推理能力在底层算术上，而不是空间规划上。

###### 更好的方式：设计领域 DSL

作者提出：

> 收拢 Agent 的底层控制权，为它设计一门领域特定语言（Domain DSL）。

在 **策引** 中，作者设计了策略原语，例如：

- `EMA`：均线；
- `GreaterThan / LessThan`：逻辑判断；
- `Lag`：状态延迟；
- `Streak`：连续状态确认。

大模型只需要像搭积木一样组合这些原语，底层的 Pandas 运算、数据对齐、未来函数屏蔽等都由系统处理。

在 **MinePilot / CraftDAG** 中，作者设计了 **ComponentPlan DSL**。

大模型不需要直接输出方块坐标，而是输出高层建筑意图，例如：

> 创建一个 `16×12×16` 的 `RoomShell` 房间壳体，  
> 在 `front` 墙面偏移 `3` 格处安装一个 `Door`，  
> 上方放置一个 `GableRoof` 人字屋顶，  
> 并设置 `overhang: 1` 的屋檐。

---

##### 5. DSL 是 Agent 的“语义脚手架”

通过 DSL，大模型不必处理底层细节，例如：

- 不用计算墙体坐标；
- 不用判断门洞处哪些方块要替换为空气；
- 不用处理物理碰撞和几何边界。

它只需要使用高层语义：

- `anchor`：锚点；
- `wall`：依附墙面；
- `offset`：偏移；
- `overhang`：屋檐延伸。

作者将 DSL 称为 Agent 的“语义脚手架”：

> 把底层物理、数学、工程容错下沉到引擎侧，让 Agent 专注于宏观架构和逻辑推演。

核心原则是：

> **Agent is the author. Engine is the compiler.**  
> Agent 是作者，引擎是编译器。

---

##### 6. 像写编译器一样构建业务引擎

既然大模型输出的是高层 DSL，那么系统需要把 DSL 转换成可执行结果。  
作者认为，这就需要像写编译器一样构建业务引擎。

###### CraftDAG 的编译管线

在 CraftDAG 中，建筑生成被拆成几层：

1. **输入层 BuildIntent**  
   用户的自然语言意图。

2. **领域计划层 ComponentPlan DSL**  
   大模型生成的建筑组件计划。

3. **中间表示层 CraftDAG IR**  
   引擎将 ComponentPlan 展开成可验证、可排序的有向无环图 **DAG**，并计算组件依赖、几何包围盒、依附关系等。

4. **目标表示层 VoxelPlan**  
   最终生成三维体素集合，即方块的绝对坐标和状态，可导出为蓝图或用于渲染。

###### 策引中的类似结构

在量化系统中，大模型组合出的策略原语也会被引擎转换为 DAG：

- 先计算均线指标；
- 再计算比较逻辑；
- 最后聚合为交易信号。

执行顺序由 **拓扑排序（Topological Sort）** 决定。

---

##### 7. 为什么要引入 IR / DAG？

作者一开始也担心“编译器”和“抽象语法树”会不会过度设计，但实践证明它很有价值。

将意图降级为 **IR / DAG** 后，系统获得两个关键能力：

###### 1. 静态分析

在量化系统中，DAG 可以追踪信号依赖，防止策略偷看未来数据。

###### 2. 确定性执行

在 Minecraft 引擎中，IR 可以精确计算：

- 几何结构；
- 方块位置；
- 材料清单（Material Lists）。

未来还可以支持局部重算：  
例如用户只改屋顶材质，系统只重新计算屋顶相关子图，而不用让大模型重建整栋建筑。

更重要的是：  
**只有有了编译机制，系统才有能力拦截 Agent 的幻觉。**

---

##### 8. 报错不是给人看的，而是给 Agent 修复用的

传统 GUI 中，错误提示是给人看的，例如：

> 输入格式不合法。

但对大模型来说，简单返回：

> Invalid plan  
> Syntax Error

并不能有效帮助它修复问题。

作者认为，在 Agent-friendly 系统中，错误提示应成为一种：

> **机器可读的验证契约（Validation Contract）**

###### CraftDAG 的错误反馈示例

如果大模型把塔楼组件放到了建筑边界之外，系统会返回精确 JSON：

```json
{
  "stage": "component-validation",
  "code": "ASSEMBLY_INSTANCE_OUT_OF_BOUNDS",
  "path": "instances[0].anchor",
  "componentId": "northwest_tower",
  "repairHint": "Move the instance inward or increase global bounds."
}
```

这个报错清楚告诉模型：

- `stage`：错误发生在组件验证阶段；
- `code`：错误类型是越界；
- `path`：具体错误位置在 `instances[0].anchor`；
- `componentId`：出错组件是 `northwest_tower`；
- `repairHint`：修复建议是向内移动或扩大全局边界。

这种错误反馈不是面向人类阅读体验，而是为了让 Agent 能精确修复。

---

##### 9. 事前契约 + 事后报错，形成稳定修复循环

除了事后错误提示，作者还强调事前约束。

在 CraftDAG 中，有核心文件：

- `LLM_AUTHORING_CONTRACT.md`

它不是传统 API 文档，而是给大模型或 harness agent 阅读的编写契约，也可以作为 System Prompt 或 `llm.txt` 的一部分。

在策引中也有类似机制：

- 机器可读开发文档；
- `llm-quickstart.txt`；
- Few-shot 示例；
- 严格 JSON Schema。

作者总结出一个重要经验：

> 与其告诉大模型“你应该怎么做”，不如明确告诉它“绝对不能做什么”。

例如设定 **ABSOLUTE PROHIBITIONS**：

- 禁止在组件 `inputs` 里直接内联嵌套其他组件；
- 必须先定义 `id`，再通过 `ref` 引用。

当系统具备：

- 严格的事前契约；
- 精准的事后报错；

大模型就能进入稳定的 **Repair Loop（迭代修复循环）**：

1. 生成 DSL；
2. 系统编译验证；
3. 返回机器可读错误；
4. 大模型只修复出错部分；
5. 再次提交验证。

作者认为：

> 没有修复循环，大模型只是偶尔好用的玩具；有了修复循环，才可能成为可靠的生产力基础设施。

---

##### 10. 处理模糊意图与确定性执行的边界

用户通常不会写 JSON DSL，也不会看 DAG 图。  
他们仍会用自然语言表达模糊需求，例如：

- “帮我调整一下这个投资组合的风险”
- “给这个城堡多加两扇大一点的窗户”

这带来一个核心矛盾：

> 用户意图是模糊的，但金融计算和空间几何是确定性的。

如果让一个大模型同时处理模糊意图和严谨计算，系统容易不稳定。

###### 作者提出混合 Agent 架构

理想方式是采用 **Hybrid Agent Architecture**，将职责分开：

###### 1. 本地 Agent：处理模糊性

本地 Agent 运行在离用户最近的交互层，例如浏览器中。

它的职责是：

- 和用户对话；
- 猜测用户意图；
- 必要时让用户确认；
- 将模糊需求转为清晰任务。

###### 2. 远端处理器：处理确定性

远端 Processor / Engine 运行在后端异步任务队列中。

它负责：

- 接收结构化 Job；
- 执行 DSL 编译；
- 运行验证；
- 完成确定性计算。

作者强调：

- 队列、状态机、编译验证，应由传统确定性代码实现；
- 意图猜测、自然语言解释、错误文本解释，可以交给大模型。

关键原则是：

> 不要把确定性层和概率性层混在一起。

---

##### 11. 这套范式的适用边界

作者指出，Agent-friendly workflow 并不是所有 AI 产品的通用解法。

它适合具备以下特征的领域：

- 有明确领域结构；
- 可以抽象出稳定原语或组件；
- 中间状态可以验证；
- 最终结果可以执行、编译或模拟；
- 错误可以定位和修复；
- 人类仍可审查和决策。

不适合的情况包括：

- 高度开放的创意表达；
- 没有明确验证标准的任务；
- 过早引入 DSL / DAG 会限制模型表达。

作者也提醒：

> Validation 不等于真实正确性。

例如：

- 投资策略通过回测，不代表未来一定有效；
- 建筑蓝图通过编译，不代表审美一定优秀。

验证契约的价值在于：  
**把错误空间缩小到系统可管理范围，而不是替代人类判断。**

---

##### 12. Agent-friendly 与 Human-friendly 应共存

作者认为，Agent-friendly 不应替代 Human-friendly。

更合理的形态是 **dual interface（双接口）**：

- 人类通过 UI 表达意图、审查结果、做最终决策；
- Agent 通过 DSL、工具和验证契约操作系统。

也就是说：

- UI 面向人；
- DSL / Contract / Tooling 面向 Agent。

---

##### 13. 软件架构视角的反转

作者回顾 **策引** 和 **MinePilot** 两个项目：

- 一个是金融投资系统；
- 一个是 Minecraft 沙盒建筑系统。

它们业务差异巨大，却最终收敛到同一套架构范式：

```text
Intent
→ Domain DSL
→ Compiler / IR / DAG
→ Validation
→ Repair Loop
→ Execution
```

过去的软件设计流程通常是：

1. 先设计人类交互界面；
2. 再设计数据库；
3. 最后写 API 胶水层。

但在 Agent 时代，设计顺序可能要反过来：

1. 先问业务能否抽象出适合 Agent 的 DSL；
2. 再问系统是否有强大的编译器内核；
3. 再问是否能提供机器可读的验证和纠错反馈；
4. 最后才为人类包一层监督和确认用的 UI。

作者将这种范式称为：

> **Domain-shaped, not Domain-locked**  
> 让系统被领域塑形，但不被领域锁死。

---

##### 总结

本文提出了一种面向 Agent 时代的软件架构范式：  
**用领域 DSL 限制模型的表达空间，用编译器式引擎保证确定性执行，用机器可读验证契约拦截错误，并通过修复循环让 Agent 稳定迭代。**

它的核心不是让大模型“无所不能”，而是通过系统设计让它在合适的边界内发挥作用。  
真正有价值的 Agent-native 软件，可能不是更复杂的聊天界面，而是能让 Agent **读取、编写、验证、修复和执行任务** 的新型工作流。

## 深度解读（1）

### 2026-09-18 00:50:50

#### Agent 时代，真正稀缺的不是更多 API，而是可编译的业务边界

文章最有价值的地方，不是提出了一个新工具，而是从两个差异极大的项目中发现了同一种可靠性机制：**不要让模型直接操纵业务世界，而要让它在一个经过设计、可以验证的表达空间里工作。**

Minecraft Bot 会卡住，与量化模型写出前视偏差代码，看似是空间推理和金融计算两个问题，实质上都源于同一种错配：模型既要理解高层意图，又要完成大量低层、精确且有状态的操作。每一步即使只有很小误差，经过长链条也会累积成失败。继续增加提示词或开放更多底层 API，并不能消除这种错配。

##### DSL 的价值不是格式，而是重新分配认知工作

文章给出的关键转变，是让模型描述“房间、门、屋顶及其依附关系”，而不是生成数万个方块坐标；让模型组合均线、延迟、连续确认等策略原语，而不是自由编写 Pandas 代码。

这可以理解为一种**语义压缩**：模型负责它相对擅长的意图理解、组件组合和方案调整；引擎负责坐标计算、数据对齐、依赖排序与安全约束。复杂性没有消失，而是从不可控的模型推理过程，转移到了可以测试和复用的确定性代码中。

不过，真正重要的并非是否采用名为 DSL 的语法。一个设计良好的领域级 API 同样可以达到目的；一个字段繁多、充满嵌套的 DSL 也照样会失败。判断接口质量的核心是：**它是否处在合适的抽象层，原语是否正交，组合后能否覆盖主要任务，并且能够被静态检查。**

##### 可靠性来自“可收敛的修复”，而非一次生成正确

文章比“结构化输出”更进一步的贡献，是把编译、验证和报错连成修复循环。模型提交计划后，引擎将其转换为 IR/DAG，定位具体错误，再返回包含阶段、路径、错误码和修复建议的机器可读反馈。模型因此可以局部修改，而不必重新猜测整份方案。

这改变了可靠性的定义：目标不再是要求概率模型一次生成完美结果，而是让错误**可发现、可定位、可局部修复，并在有限次数内收敛**。对产品而言，值得监控的也不只是首次成功率，还包括平均修复轮数、错误是否反复出现、局部修改是否引发无关回归，以及多少任务落在 DSL 的表达范围之外。

DAG 的额外价值也在这里：它不仅方便执行，还提供依赖追踪、审计、局部重算和版本比较。对于金融、工程设计、数据工作流、营销自动化等高风险或长流程场景，这些能力往往比模型参数升级更能改善实际可用性。

##### 下一代软件可能是“双界面”，但领域建模才是瓶颈

文章提出的架构反转值得重视：过去先为人设计 GUI，再补 API；未来可能先建设 Agent 可读写、可验证的业务内核，再为人提供表达意图和审查结果的界面。人和 Agent 使用不同接口，却操作同一个业务模型。

但这仍主要是来自两个项目的工程归纳，而不是已被广泛验证的通用范式。其适用前提很明确：领域存在稳定原语，中间状态能够验证，结果可以执行或模拟。开放创作、审美判断、战略决策等任务，很难仅靠编译通过来证明正确。

真正的产品机会因此不只是“给现有软件加 Agent”，而是把某个专业领域重新编码成**可组合原语、确定性执行器和机器可读错误契约**。最难的部分也不是接入大模型，而是持续维护这套领域模型：它覆盖了多少真实需求，何时需要扩展，怎样避免把用户锁死在过窄的表达空间。Agent 时代的软件壁垒，可能越来越接近一门好语言加一个可信编译器，而不是一个更会聊天的入口。
