#### Features

Any agent, any runtime, one org chart. If it can receive a heartbeat, it's hired. Every task traces back to the company mission. Agents know *what* to do and *why*.

##### 💓 Heartbeats

Agents wake on a schedule, check work, and act. Delegation flows up and down the org chart.

Monthly budgets per agent. When they hit the limit, they stop. No runaway costs.

##### 🏢 Multi-Company

One deployment, many companies. Complete data isolation. One control plane for your portfolio. Every conversation traced. Every decision explained. Full tool-call tracing and immutable audit log.

##### 🛡️ Governance

You're the board. Approve hires, override strategy, pause or terminate any agent — at any time. Hierarchies, roles, reporting lines. Your agents have a boss, a title, and a job description. Monitor and manage your autonomous businesses from anywhere.

Without Paperclip With Paperclip

❌ You have 20 Claude Code tabs open and can't track which one does what. On reboot you lose everything. ✅ Tasks are ticket-based, conversations are threaded, sessions persist across reboots.

❌ You manually gather context from several places to remind your bot what you're actually doing. ✅ Context flows from the task up through the project and company goals — your agent always knows what to do and why.

❌ Folders of agent configs are disorganized and you're re-inventing task management, communication, and coordination between agents. ✅ Paperclip gives you org charts, ticketing, delegation, and governance out of the box — so you run a company, not a pile of scripts.

❌ Runaway loops waste hundreds of dollars of tokens and max your quota before you even know what happened. ✅ Cost tracking surfaces token budgets and throttles agents when they're out. Management prioritizes with budgets.

❌ You have recurring jobs (customer support, social, reports) and have to remember to manually kick them off. ✅ Heartbeats handle regular work on a schedule. Management supervises.

❌ You have an idea, you have to find your repo, fire up Claude Code, keep a tab open, and babysit it. ✅ Add a task in Paperclip. Your coding agent works on it until it's done. Management reviews their work.

Paperclip handles the hard orchestration details correctly.

**Atomic execution.** Task checkout and budget enforcement are atomic, so no double-work and no runaway spend.

**Persistent agent state.** Agents resume the same task context across heartbeats instead of restarting from scratch.

**Runtime skill injection.** Agents can learn Paperclip workflows and project context at runtime, without retraining.

**Governance with rollback.** Approval gates are enforced, config changes are revisioned, and bad changes can be rolled back safely.

**Goal-aware execution.** Tasks carry full goal ancestry so agents consistently see the "why," not just a title.

**Portable company templates.** Export/import orgs, agents, and skills with secret scrubbing and collision handling.

**True multi-company isolation.** Every entity is company-scoped, so one deployment can run many companies with separate data and audit trails.

**Not a chatbot.** Agents have jobs, not chat windows.

**Not an agent framework.** We don't tell you how to build agents. We tell you how to run a company made of them.

**Not a workflow builder.** No drag-and-drop pipelines. Paperclip models companies — with org charts, goals, budgets, and governance.

**Not a prompt manager.** Agents bring their own prompts, models, and runtimes. Paperclip manages the organization they work in.

**Not a single-agent tool.** This is for teams. If you have one agent, you probably don't need Paperclip. If you have twenty — you definitely do.

**Not a code review tool.** Paperclip orchestrates work, not pull requests. Bring your own review process.

#### Quickstart

Open source. Self-hosted. No Paperclip account required.

```
npx paperclipai onboard --yes
```

Or manually:

```
git clone https://github.com/paperclipai/paperclip.git
cd paperclip
pnpm install
pnpm dev
```

This starts the API server at `http://localhost:3100`. An embedded PostgreSQL database is created automatically — no setup required.

> **Requirements:** Node.js 20+, pnpm 9.15+

#### FAQ

**What does a typical setup look like?**Locally, a single Node.js process manages an embedded Postgres and local file storage. For production, point it at your own Postgres and deploy however you like. Configure projects, agents, and goals — the agents take care of the rest.

If you're a solo-entreprenuer you can use Tailscale to access Paperclip on the go. Then later you can deploy to e.g. Vercel when you need it.

**Can I run multiple companies?**Yes. A single deployment can run an unlimited number of companies with complete data isolation.

**How is Paperclip different from agents like OpenClaw or Claude Code?**Paperclip *uses* those agents. It orchestrates them into a company — with org charts, budgets, goals, governance, and accountability.

**Why should I use Paperclip instead of just pointing my OpenClaw to Asana or Trello?**Agent orchestration has subtleties in how you coordinate who has work checked out, how to maintain sessions, monitoring costs, establishing governance - Paperclip does this for you.

(Bring-your-own-ticket-system is on the Roadmap)

**Do agents run continuously?**By default, agents run on scheduled heartbeats and event-based triggers (task assignment, @-mentions). You can also hook in continuous agents like OpenClaw. You bring your agent and Paperclip coordinates.

Agent Orchestrator manages fleets of AI coding agents working in parallel on your codebase. Each agent gets its own git worktree, its own branch, and its own PR. When CI fails, the agent fixes it. When reviewers leave comments, the agent addresses them. You only get pulled in when human judgment is needed.

**Agent-agnostic** (Claude Code, Codex, Aider) · **Runtime-agnostic** (tmux, Docker) · **Tracker-agnostic** (GitHub, Linear)

#### Quick Start

**Option A — From a repo URL (fastest):**

```
# Install
git clone https://github.com/ComposioHQ/agent-orchestrator.git
cd agent-orchestrator && bash scripts/setup.sh

# One command to clone, configure, and launch
ao start https://github.com/your-org/your-repo
```

Auto-detects language, package manager, SCM platform, and default branch. Generates `agent-orchestrator.yaml` and starts the dashboard + orchestrator.

**Option B — From an existing local repo:**

```
cd ~/your-project && ao init --auto
ao start
```

Then spawn agents:

```
ao spawn my-project 123    # GitHub issue, Linear ticket, or ad-hoc
```

Dashboard opens at `http://localhost:3000`. Run `ao status` for the CLI view.

```
ao spawn my-project 123
```

1. **Workspace** creates an isolated git worktree with a feature branch
2. **Runtime** starts a tmux session (or Docker container)
3. **Agent** launches Claude Code (or Codex, or Aider) with issue context
4. Agent works autonomously — reads code, writes tests, creates PR
5. **Reactions** auto-handle CI failures and review comments
6. **Notifier** pings you only when judgment is needed

##### Plugin Architecture

Eight slots. Every abstraction is swappable.

Slot Default Alternatives

Runtime tmux docker, k8s, process

Agent claude-code codex, aider, opencode

Workspace worktree clone

Tracker github linear

SCM github —

Notifier desktop slack, composio, webhook

Terminal iterm2 web

Lifecycle core —

All interfaces defined in `packages/core/src/types.ts`. A plugin implements one interface and exports a `PluginModule`. That's it.

#### Configuration

```
# agent-orchestrator.yaml
port: 3000

defaults:
  runtime: tmux
  agent: claude-code
  workspace: worktree
  notifiers: [desktop]

projects:
  my-app:
    repo: owner/my-app
    path: ~/my-app
    defaultBranch: main
    sessionPrefix: app

reactions:
  ci-failed:
    auto: true
    action: send-to-agent
    retries: 2
  changes-requested:
    auto: true
    action: send-to-agent
    escalateAfter: 30m
  approved-and-green:
    auto: false # flip to true for auto-merge
    action: notify
```

CI fails → agent gets the logs and fixes it. Reviewer requests changes → agent addresses them. PR approved with green CI → you get a notification to merge.

See `agent-orchestrator.yaml.example` for the full reference.

#### Maintenance

```
# Run deterministic install and runtime checks
ao doctor

# Apply safe cleanup and launcher fixes
ao doctor --fix

# Update this local AO checkout, rebuild critical packages, and verify the launcher
ao update
```

`ao doctor` checks PATH and launcher resolution, required binaries, tmux and GitHub CLI health, config support directories, stale AO temp files, and core build/runtime sanity. `ao update` fast-forwards the local install repo on `main`, runs `pnpm install`, clean-rebuilds `@composio/ao-core`, `@composio/ao-cli`, and `@composio/ao-web`, refreshes the global `ao` launcher with `npm link`, and finishes with CLI smoke tests.

Running one AI agent in a terminal is easy. Running 30 across different issues, branches, and PRs is a coordination problem.

**Without orchestration**, you manually: create branches, start agents, check if they're stuck, read CI failures, forward review comments, track which PRs are ready to merge, clean up when done.

**With Agent Orchestrator**, you: `ao spawn` and walk away. The system handles isolation, feedback routing, and status tracking. You review PRs and make decisions — the rest is automated.

**Step 1 -- Generate integration files:**

```
./scripts/convert.sh
# Faster (parallel, output order may vary): ./scripts/convert.sh --parallel
```

**Step 2 -- Install (interactive, auto-detects your tools):**

```
./scripts/install.sh
# Faster (parallel, output order may vary): ./scripts/install.sh --no-interactive --parallel
```

The installer scans your system for installed tools, shows a checkbox UI, and lets you pick exactly what to install:

```
+------------------------------------------------+
  |   The Agency -- Tool Installer                 |
  +------------------------------------------------+

  System scan: [*] = detected on this machine

  [x]  1)  [*]  Claude Code     (claude.ai/code)
  [x]  2)  [*]  Copilot         (~/.github + ~/.copilot)
  [x]  3)  [*]  Antigravity     (~/.gemini/antigravity)
  [ ]  4)  [ ]  Gemini CLI      (gemini extension)
  [ ]  5)  [ ]  OpenCode        (opencode.ai)
  [ ]  6)  [ ]  OpenClaw        (~/.openclaw)
  [x]  7)  [*]  Cursor          (.cursor/rules)
  [ ]  8)  [ ]  Aider           (CONVENTIONS.md)
  [ ]  9)  [ ]  Windsurf        (.windsurfrules)
  [ ] 10)  [ ]  Qwen Code       (~/.qwen/agents)

  [1-10] toggle   [a] all   [n] none   [d] detected
  [Enter] install   [q] quit
```

**Or install a specific tool directly:**

```
./scripts/install.sh --tool cursor
./scripts/install.sh --tool opencode
./scripts/install.sh --tool openclaw
./scripts/install.sh --tool antigravity
```

**Non-interactive (CI/scripts):**

```
./scripts/install.sh --no-interactive --tool all
```

**Faster runs (parallel)** — On multi-core machines, use `--parallel` so each tool is processed in parallel. Output order across tools is non-deterministic. Works with both interactive and non-interactive install: e.g. `./scripts/install.sh --interactive --parallel` (pick tools, then install in parallel) or `./scripts/install.sh --no-interactive --parallel`. Job count defaults to `nproc` (Linux), `sysctl -n hw.ncpu` (macOS), or 4; override with `--jobs N`.

```
./scripts/convert.sh --parallel                    # convert all tools in parallel
./scripts/convert.sh --parallel --jobs 8           # cap parallel jobs
./scripts/install.sh --no-interactive --parallel   # install all detected tools in parallel
./scripts/install.sh --interactive --parallel      # pick tools, then install in parallel
./scripts/install.sh --no-interactive --parallel --jobs 4
```

## 摘要（1）

#### 总体精炼总结

这 4 个项目都围绕一个核心趋势：**把 AI 从“单个聊天助手”升级为“可协作、可管理、可审计的工作系统”**，但它们关注的层次并不相同。

- `paperclip`：想解决的是**“如何经营一家由 AI 组成的公司”**，强调组织架构、预算、治理、目标对齐和多公司管理。
- `symphony`：想解决的是**“如何把项目任务变成自治执行单元”**，强调隔离执行、证明工作结果、让工程师管理工作而不是盯着 agent。
- `agent-orchestrator`：想解决的是**“如何并行管理大量编码 agent”**，强调 worktree 隔离、CI 修复、评审反馈处理、PR 生命周期自动化。
- `agency-agents`：想解决的是**“如何快速获得大量可复用的专业 agent 角色”**，本质上是一个**角色/提示词/工作流资产库**，而不是严格意义上的编排平台。

一句话概括：

> `paperclip` 更像 AI 公司的“操作系统”，`symphony` 更像自治研发流水线的“规范与执行框架”，`agent-orchestrator` 更像工程团队的“多 agent 调度中台”，`agency-agents` 更像“专业 AI 员工模板市场”。

---

#### 深入浅出解读

##### 1. 它们分别在解决什么问题

###### `paperclip`：把 AI 当“员工”而不是“聊天窗口”
它最鲜明的理念是：**不是管理 prompt，不是管理 PR，而是管理一家由 agent 构成的组织。**

它提供的不是单点能力，而是一套组织管理机制：

- org chart（组织架构）
- budget（预算控制）
- governance（审批、回滚、终止）
- goal alignment（任务和公司目标关联）
- heartbeat（定时唤醒和持续运转）
- multi-company（一个部署管理多个“公司”）

这意味着它想处理的不只是“agent 会不会写代码”，而是更难的部分：

- 谁来做什么
- 为什么做
- 花多少钱
- 做错了谁负责
- 如何暂停、审计、追责、回滚

通俗地说，`paperclip` 试图把“20 个分散跑着的 AI 工具”变成“一个有层级、有制度的数字组织”。

---

###### `symphony`：把研发工作变成“自治执行 run”
`Symphony` 的定位更收敛，也更工程化。它强调：

- 从任务系统（如 Linear）接任务
- 启动隔离的 agent 执行环境
- 产出“工作证明”（CI、PR review、复杂度分析、讲解视频等）
- 审核通过后安全落地 PR

它的中心思想不是“组织治理”，而是**工作单元自治**。  
也就是说，它把每个需求、bug、任务都看作一个可以独立完成的执行回合。

你可以把它理解成：

- 传统方式：人盯着 agent 写代码
- Symphony 方式：人定义工作，系统把工作变成一个可追踪、可交付、可验收的执行过程

这比普通“AI 帮写代码”更进一步，因为它强调“proof of work（工作证明）”。这很关键：自治不是只看结果，还要看**能否证明结果可信**。

---

###### `agent-orchestrator`：把并行 coding agents 变成一支可控施工队
这个项目非常聚焦于**软件工程生产线**，而且相对务实。

它的思路是：

- 每个 agent 对应独立 git worktree / branch / PR
- agent 自己处理 CI fail
- agent 自己响应 code review comments
- 只有需要人类判断时才通知人

这本质上是在把很多原本由工程师或 tech lead 手工协调的事情自动化：

- 建分支
- 启动多个 agent
- 跟踪 agent 是否卡住
- 转发 CI 日志
- 转发 review comments
- 追踪哪些 PR 可以 merge
- 清理现场

这个项目的优势在于，它不是从“大而全的 AI 公司治理”入手，而是抓住一个非常具体的高价值场景：  
**当一个团队要同时跑很多 coding agent 时，真正的瓶颈不是“能不能生成代码”，而是“怎么管理并行执行和反馈闭环”。”**

---

###### `agency-agents`：不是编排系统，而是“专业 AI 人才库”
这个仓库和前三个的性质不一样。

它提供的是大量细分 agent 人设、流程、规则和交付模板，比如：

- Frontend Developer
- Security Engineer
- UX Researcher
- Reddit Community Builder
- Product Manager
- Accessibility Auditor
- XR Interface Architect
- Compliance Auditor

它的卖点不是 orchestration，而是：

- 专业化
- 人格化
- 可交付导向
- 可迁移到多个 agent 工具中使用

所以它更像一种“内容资产层”：

- 为不同工具生成适配文件
- 安装到 Claude Code、Cursor、Copilot、Aider、OpenClaw 等
- 让用户快速调起某类“专业角色”

简单说：

- 前三个更偏“系统层/调度层”
- `agency-agents` 更偏“角色层/知识与提示资产层”

它未必能解决 agent 协同问题，但能显著降低“如何定义专业 agent”的门槛。

---

##### 2. 它们共同指向了什么趋势

这四个项目合起来，能看出 AI 工程的几个明显方向。

###### 从“单 Agent”走向“多 Agent”
大家已经默认：一个 agent 不够。  
真正复杂的工作需要：

- 分工
- 协调
- 状态管理
- 结果汇总
- 权限和预算控制

这和企业组织很像，所以 `paperclip` 才会直接引入“公司”“员工”“老板”“预算”这些概念。

---

###### 从“即时对话”走向“长期执行”
这些项目都不满足于单轮问答，而是强调：

- agent 持久运行
- 能恢复上下文
- 周期性唤醒
- 处理长期任务
- 跨 session 延续工作

这说明行业关注点已从“AI 回答得聪不聪明”转向“AI 能不能长期可靠地干活”。

---

###### 从“生成代码”走向“闭环交付”
成熟一点的项目都在强调闭环：

- 任务进入系统
- agent 实施
- 测试/CI 校验
- review 反馈
- 修复
- 合并
- 审计和留痕

也就是说，未来的关键竞争力不是模型能写多少代码，而是系统能不能把“工作流”跑通。

---

###### 从“能力炫技”走向“治理与成本控制”
`paperclip` 最明显，`agent-orchestrator` 也很明显：

- 控预算
- 追踪成本
- 阻止 runaway loop
- 审批和回滚
- 审计轨迹
- 公司级隔离

这很现实。因为 agent 一旦进入生产环境，最先撞墙的通常不是“智商不够”，而是：

- 成本失控
- 状态混乱
- 权限风险
- 责任不清
- 多 agent 互相打架

---

##### 3. 这几个项目之间的关系怎么理解

可以把它们放在一个分层结构里看：

###### 第一层：角色与能力资产
- `agency-agents`

作用：定义“有哪些专家、怎么说话、按什么流程交付”。

---

###### 第二层：执行与并行调度
- `agent-orchestrator`
- `symphony`

作用：把任务分配给 agent，并确保隔离执行、反馈处理和结果交付。

---

###### 第三层：组织治理与企业管理
- `paperclip`

作用：不只管任务执行，还管组织结构、预算、审批、目标对齐和多实体隔离。

---

##### 4. 适合什么人用

###### 适合尝试 `paperclip` 的人
- 你想运行多个 agent，且不止写代码
- 你在意预算、组织层级、治理和长期运行
- 你想把 AI 当“组织成员”来管理

不太适合：
- 你只有 1~2 个 agent
- 你只想快速完成 coding task
- 你不想承担较高的系统复杂度

---

###### 适合尝试 `symphony` 的人
- 你已经有比较成熟的工程流程
- 你希望把任务系统和自治研发串起来
- 你重视“工作证明”和安全落地

不太适合：
- 你还没有规范化 issue / ticket / CI / PR 流程
- 你想直接拿现成产品开箱即用  
因为它目前更像一个方向性项目/规范实现，而不是成熟完整平台。

---

###### 适合尝试 `agent-orchestrator` 的人
- 你已经在用 Claude Code / Codex / Aider 等 coding agent
- 你最大的问题是并行任务管理
- 你希望自动处理 CI、review、PR 生命周期

它对工程团队最实用，也最接近近期可落地价值。

---

###### 适合尝试 `agency-agents` 的人
- 你缺的是“专业角色模板”
- 你想快速丰富 agent 的专业化表达和工作流
- 你常在多个工具之间切换

但它更像“prompt/role 基础设施”，不是 orchestration 平台本身。

#### 评论与批判性分析

##### 值得肯定的地方

- 这些项目都抓住了一个真实问题：**AI 的瓶颈越来越不是模型本身，而是工作组织方式。**
- 它们把注意力从“更强模型”转向“更强系统设计”，这是成熟信号。
- `agent-orchestrator` 和 `paperclip` 尤其体现出工程现实主义：隔离、预算、审计、恢复、通知、回路控制，这些都是真问题。
- `agency-agents` 虽然不属于严格 orchestration，但它把“专业角色设计”做成了可复用资产，这对实际使用者很有帮助。

---

##### 需要警惕的地方

###### 1. 叙事很宏大，但现实中“全自治公司”还远未成立
`paperclip` 的口号很强：“zero-human companies（零人公司）”。这很吸引眼球，但要实事求是地说：

- 当前模型在长期规划、目标稳定性、事实一致性、隐性依赖识别上仍不够可靠
- 多 agent 协作经常会放大误差，而不是自动消除误差
- 真正的企业运行不仅是任务执行，还包括责任承担、法律合规、商业判断和组织政治

所以，“无人公司”更像一个激进愿景，而不是短期现实。  
更准确的说法应是：**降低人工监督密度，而不是消灭人。**

---

###### 2. orchestration 容易变成“复杂性转移”，不一定是真降本增效
这些系统都在解决管理复杂 agent 的问题，但也可能引入新的复杂度：

- 配置复杂
- 角色建模复杂
- 插件生态碎片化
- 调试困难
- 错误来源变多
- 责任边界更难界定

很多团队最后可能发现：  
不是“有了 orchestration 就更高效”，而是“先要有足够成熟的工程规范，否则 orchestration 只是在放大混乱”。

换言之，这类系统通常**更适合流程相对成熟的团队**，而不是拿来拯救一个本来就混乱的组织。

---

###### 3. 多 agent 并不天然优于强单 agent
这是一个经常被忽略的盲点。

多 agent 听起来很先进，但现实中常见问题是：

- 上下文割裂
- 相互依赖协调成本高
- 任务切分不合理导致返工
- 多轮通信带来额外 token 和时间成本
- “管理 agent 的 agent”本身也会失误

因此，多 agent 系统只有在以下情况下才真正占优：

- 工作可切分
- 接口清晰
- 验收标准明确
- 反馈机制成熟
- 出错后可追踪

否则，一个强单 agent + 少量人工审阅，可能更便宜、更快、更稳。

---

###### 4. `agency-agents` 很强大，但容易陷入“角色堆砌幻觉”
`agency-agents` 的内容非常丰富，覆盖 100+ 角色，这很有吸引力。  
但需要批判性看待：

- 角色越多，不代表结果越好
- 很多“人格化”设定可能更多提升体验感，而非稳定提升产出质量
- 如果缺乏评价标准，用户容易把“风格鲜明”误当成“专业可靠”

它最有价值的部分，不是“人格”，而是：

- 明确的工作流程
- 可交付物定义
- 成功指标
- 跨工具可迁移性

如果只看“角色包装”，容易高估其实际生产力。

---

###### 5. `symphony` 的理念先进，但当前成熟度看起来偏早期
从提供的信息看，`symphony` 仓库还比较新，提交数量少，且更偏 spec 驱动。  
这意味着它的价值目前更多可能体现在：

- 提供架构方向
- 定义问题空间
- 启发实现方式

而不是直接作为成熟生产工具使用。  
所以对它的评价应该谨慎：**概念强，不等于产品成熟。**

---

##### 我对四者的实事求是判断

###### 如果按“概念高度”看
- `paperclip` 最高，试图定义 AI 组织操作系统
- `symphony` 次之，试图定义自治研发执行范式

###### 如果按“工程落地感”看
- `agent-orchestrator` 最强，问题具体、路径清晰、功能闭环明显
- `paperclip` 次之，但系统野心也带来更高落地难度

###### 如果按“立即可复用价值”看
- `agency-agents` 最容易被普通用户直接拿来用
- `agent-orchestrator` 对已有工程团队也非常实用

###### 如果按“潜在炒作风险”看
- `paperclip` 和 `agency-agents` 都较高  
前者容易被“无人公司”叙事放大，后者容易被“超多专家角色”包装放大。

---

#### 最后结论

这四个项目不是同类竞品，而是代表了 AI 工作系统的四个不同层面：

- `agency-agents` 提供“谁来干活”的角色模板
- `agent-orchestrator` 提供“怎么并行干活”的工程调度
- `symphony` 提供“怎么把任务变成自治执行单元”的工作模型
- `paperclip` 提供“怎么把这些 agent 组织成公司”的治理框架

如果要一句评论：

> 它们共同说明，AI 应用正在从“更会回答问题”走向“更像组织化劳动力”；但距离真正稳定、低成本、可问责的自治系统，还有明显距离，尤其在人类判断、治理成本、可靠性和复杂度控制上，仍然不能过度乐观。
