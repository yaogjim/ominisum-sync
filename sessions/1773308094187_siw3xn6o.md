## 分析要点

- **核心高价值点**：把传统RAG改造成“检索-评估-纠正-生成”闭环，并用轻量评估器在生成前过滤或补强上下文，是解决高相似低可用问题的核心思路。
- **留存建议**：短期参考后归档保留（包含可直接复用的CRAG工程实现思路、Milvus选型要点和示例代码，适合作为搭建原型时的参考材料。）

**知识要点**

- 传统RAG容易因语义相似但场景不符、内容过时和记忆污染导致高分误检索。
- CRAG通过三元判决将检索结果分为正确、模糊、错误，并分别采取直接使用、补充外部知识或丢弃的策略。
- 知识精炼可通过文档分解、查询重写和知识选择减少无关上下文，降低幻觉和token浪费。
- Milvus适合CRAG场景的原因包括Partition Key多租户隔离、Dense+Sparse+元数据过滤的混合检索，以及JSON字段扩展。
- 用LangGraph middleware而非复杂状态图可简化CRAG集成路径，提高可维护性。

**行动项**

- 在现有RAG流程中加入独立评估器，对Top-K检索结果做relevant/ambiguous/incorrect三元分类。
- 为向量库增加置信度、时间衰减和验证状态等元数据，降低记忆污染风险。
- 针对专有名词和版本号查询，验证Dense+Sparse混合检索是否优于纯向量召回。
- 补做离线评测和线上监控，重点跟踪误召回率、Web搜索触发率、延迟和回答正确率。

## 正文

**尹珉**

### Embedding相似度虚高，如何用langchain+Milvus搭建CRAG解决？

最近后台经常会收到一个提问，就是我的RAG经常打捞上来一个相似性分数极高，但是完全不可用的内容，到底要怎么办？

这背后，其实是个传统 RAG在设计最底层的想当然：相似度高 = 结果好。但这套逻辑在生产环境里根本站不住脚。因为高分文档可能早就过期了，或者讲的是完全不匹配的场景、甚至核心信息缺斤短两。

而 CRAG 的核心价值，就是在检索和生成之间引入了一道评估环节，对检索结果做三元判决（正确 / 模糊 / 错误），在错误信息进入大模型推理环节之前，就把它拦截、修正或者补充完整，从根源上解决检索不靠谱的问题。

#### 01

#### 传统 RAG 的三个检索问题

这里先总结一下传统 RAG的几个问题。

第一，检索偏差。

我们之前做了个运维助手，用户查 “如何在 Nginx 上配置 HTTPS 证书”，检索出来的 Top3 高分文档，分别讲的是 Apache 的配置方法、早就停更的旧版本教程、甚至是 HTTPS 的原理解析。可以看到，语义相似，和能解决问题，在这时候其实完全是两码事。

第二，时效性缺失。

比如你查 “Python 异步编程最佳实践”，它可能会同时捞上来2018 年早就废弃的写法，和 2024 年官方推荐的写法。而哪一个更契合，则取决于你需要最新的方案，还是需要了解历史项目的演进逻辑。

第三，也是最无解的记忆污染。一旦检索到过时的 API 用法，生成了错误代码，这段错误内容又被存进了记忆库，接下来就是彻底的恶性循环：新旧版本内容共存，向量检索次次都能命中旧内容，越用越错，连回滚都找不到抓手。

也是因此，引入检索质量评估是RAG与 Agent 系统的必选项。

#### 02

#### CRAG：检索质量的评估与纠正机制

传统 RAG 只有 用 / 不用的二元处理，但绝大多数检索结果都是部分相关但不全对的模糊状态，二元处理要么丢有效信息，要么带进错误内容。

也是因此，CRAG （Corrective Retrieval-Augmented Generation）的核心改进，就是把传统 RAG的检索→生成两步走，改成 检索→评估→纠正→生成四步闭环。

![Image](https://pbs.twimg.com/media/HDLAkpVaAAAGTYA?format=jpg&name=large)

具体来说，CRAG 会将检索结果分为三种：正确（直接精炼使用）、模糊（补充外部知识）、错误（丢弃检索结果）。

![Image](https://pbs.twimg.com/media/HDLAtzra4AA8-Ng?format=png&name=large)

但只有做检索内容的判断，还远远不够。传统 RAG 还有个致命误区：检索到文档就直接全文塞给大模型。 token 浪费只是其次，一堆无关信息混进去，很容易就把大模型带偏，平白无故多出很多幻觉。

CRAG 的改进在于：绝不直接用检索全文，而是先做一轮知识精炼，把无效信息全筛掉，只留和查询最相关的核心内容。

原论文方案中里用了知识条带（Knowledge Strips）+ 启发式规则，不过，我们日常工程落地，用简化的关键词匹配方案就能搞定；如果是生产环境，也可以换成 LLM 摘要、结构化提取，进一步提升精炼质量。

整个精炼流程如下图所示，分三步：

文档分解（从 2000 tokens 提取 500 tokens 关键片段）、查询重写（将模糊查询改写为精确搜索词）、知识选择（对结果去重、排序、截断）。

![Image](https://pbs.twimg.com/media/HDLAx73bQAEXTj1?format=jpg&name=large)

做完精炼之后，就进入最核心的评估器环节。

这里先划个重点：不要用评估器做复杂推理，评估器的核心使命是快速筛选，在几毫秒里判断内容能不能用。

所以 CRAG 原论文里，用的是微调后的 T5-Large，而不是通用大模型。给大家列个直观的对比：

![Image](https://pbs.twimg.com/media/HDLA1dXbQAMrOmA?format=jpg&name=large)

评估完之后，就会引入一个新问题，如果内部检索的资料不够，怎么办？

CRAG 设计了一套内部检索 + Web 搜索的协同机制，说人话就是当内部检索结果错误、或者信息不足的时候，系统会自动触发 Web 搜索补充最新信息，解决时效性问题。

#### 03

#### Milvus：CRAG 的高性能存储引擎

聊完了 CRAG 的核心逻辑，很多朋友会问：这套机制跑起来，对底层的向量数据库有没有要求？

当然有。我们当时试了好几个向量数据库，最后线上落地用 Milvus，就是因为它的架构设计，刚好踩中了 CRAG 生产落地的三个核心刚需：多租户隔离（数百个 Agent 实例独立记忆）、混合检索（应对语义漂移）、动态 Schema（记忆结构随系统迭代演化）。

Partition Key 实现零成本多租户隔离

做 Agent 系统的都懂，你可能要同时跑几百个 Agent 实例，每个用户、每个场景的记忆必须完全独立，不能串数据。之前我们试过给每个租户建单独的 Collection，管理起来扩容、运维全是坑。

Milvus 的 Partition Key 功能，直接实现了零成本的多租户隔离。你只要在 Schema 定义时给 agent\_id 字段加上is\_partition\_key=True，查询时系统会自动路由到对应分区，不用手动维护一大堆 Collection。

实测下来，在 1000 万向量、100 个租户的场景中，配合 Clustering Compaction，直接带来了 3-5 倍的 QPS 提升。

原生混合检索，搞定边界场景的检索失效

纯向量检索有个天然的短板：遇到用户查专有名词、型号编码（比如 "SKU-2024-X5"）、精确版本号这类场景，很容易直接失效 。

Milvus 2.5 原生支持Dense 稠密向量（语义）+ Sparse 稀疏向量（BM25）+ 元数据过滤的混合检索，还自带 RRF 融合排序，不用搭多路检索再做融合，省了大量开发成本。

实测数据：100 万向量规模下，Milvus Sparse-BM25 检索延迟仅 6ms，完全不拖 CRAG 全流程的后腿。

JSON 字段，支持记忆结构灵活演化

系统不是一成不变的。随着 CRAG 评估机制的完善，我们要不断给记忆新增 confidence、verified、source 这类字段，要是用传统结构化数据库，改表结构就得停机维护，对线上业务太不友好。

Milvus 的 JSON 字段，可以灵活扩展元数据字段，想加什么直接加，完全不用停机改 Schema。

这是个极简的 Schema 定义示例

```text
fields = [
    FieldSchema(name="agent_id", dtype=DataType.VARCHAR, is_partition_key=True),  # 多租户
    FieldSchema(name="dense_embedding", dtype=DataType.FLOAT_VECTOR, dim=1536),   # 语义检索
    FieldSchema(name="sparse_embedding", dtype=DataType.SPARSE_FLOAT_VECTOR),# BM25FieldSchema(name="metadata", dtype=DataType.JSON),# 动态 Schema
]

# 混合检索 + 元数据过滤
results = collection.hybrid_search(
    reqs=[
        AnnSearchRequest(data=[dense_vec], anns_field="dense_embedding", limit=20),
        AnnSearchRequest(data=[sparse_vec], anns_field="sparse_embedding", limit=20)
    ],
    rerank=RRFRanker(),
    output_fields=["metadata"],
    expr='metadata["confidence"] > 0.9',# CRAG 置信度过滤
    limit=5
)
```

另外，Milvus还有个关键优势是平滑迁移：Milvus 提供 Lite / Standalone / Distributed 三种部署模式，代码完全兼容。我们在本地 Lite 上开发，生产环境切换到 Distributed，只需修改连接字符串。

#### 04

#### 基于 LangGraph middleware +Milvus的 CRAG 教程

教程开始前，多说一句选型的思路。很多人做 CRAG，喜欢用 LangGraph 画一堆节点和边，状态流转搞的特别复杂，维护起来巨麻烦。

我们踩过这个坑之后，最后选了 LangGraph 1.0 的middleware 模式，它能在模型调用前直接拦截请求，一站式完成检索、评估、纠正全流程，不用手动管理状态图的节点和边，代码量少、可读性高，出问题也好排查。

整个流程一共分四步：

检索：从 Milvus 获取 Top-3 相关文档，自带租户隔离

评估：用轻量级模型完成三元判决，判断文档质量

纠正：根据判决结果，执行精炼、补充搜索、兜底替换策略

注入：把处理好的上下文，通过动态提示词注入给大模型

本文代码基于 LangChain 1.0 的 middleware 特性实现。Middleware 是 LangChain 1.0 的核心特性，但具体 API 可能随版本更新而变化。

```text
# filename: crag_agent.py

# ============ 导入依赖 ============
from typing import Literal, List
from langchain.agents import create_agent
from langchain.agents.middleware import AgentMiddleware, before_model, dynamic_prompt
from langchain.chat_models import init_chat_model
from langchain_milvus import Milvus
from langchain_openai import OpenAIEmbeddings
from langchain_core.documents import Document
from langchain_core.messages import SystemMessage, HumanMessage
from langchain_community.tools.tavily_search import TavilySearchResults

# ============ CRAG Middleware（最小改动版） ============
class CRAGMiddleware(AgentMiddleware):
    """CRAG 评估与纠正中间件（使用官方装饰器注册钩子，避免永久污染消息栈）"""

    def __init__(self, vector_store: Milvus, agent_id: str):
        super().__init__()
        self.vector_store = vector_store
        self.agent_id = agent_id  # 多租户隔离
        # 轻量评估器：用于相关性判定（可替换为你后文的结构化版本）
        self.evaluator = init_chat_model("openai:gpt-4o-mini", temperature=0)
        # Web 搜索托底
        self.web_search = TavilySearchResults(max_results=3)

    @before_model
    def run_crag(self, state):
        """在模型调用前执行检索→评估→纠正，准备最终上下文"""
        # 获取最后一条用户消息
        last_msg = state["messages"][-1]
        query = getattr(last_msg, "content", "") if hasattr(last_msg, "content") else last_msg.get("content", "")

        # 1. 检索：从 Milvus 获取文档（PartitionKey + 置信度过滤）
        docs = self._retrieve_from_milvus(query)

        # 2. 评估：三元判决
        verdict = self._evaluate_relevance(query, docs)

        # 3. 纠正：根据判决决定处理策略
        if verdict == "incorrect":
            # 检索失败，完全依赖 Web 搜索
            web_results = self._web_search_fallback(query)
            final_context = self._format_web_results(web_results)
        elif verdict == "ambiguous":
            # 检索模糊，精炼文档 + Web 搜索补充
            refined_docs = self._refine_documents(docs, query)
            web_results = self._web_search_fallback(query)
            final_context = self._merge_context(refined_docs, web_results)
        else:
            # 检索质量良好，只精炼文档
            refined_docs = self._refine_documents(docs, query)
            final_context = self._format_internal_docs(refined_docs)

        # 4. 将上下文放入临时键，仅用于“当前模型调用”的动态提示拼接
        state["_crag_context"] = final_context
        return state

    @dynamic_prompt
    def attach_context(self, state, prompt_messages: List):
        """将 CRAG 合成上下文以 SystemMessage 注入到“本次模型调用”的提示前"""
        final_context = state.get("_crag_context")
        if final_context:
            sys_msg = SystemMessage(
                content=f"以下是相关背景信息，请基于这些信息回答用户问题：\n\n{final_context}"
            )
            # 仅对当前调用生效，不永久写入 state["messages"]
            prompt_messages = [sys_msg] + prompt_messages
        return prompt_messages

    # ======== 内部方法：检索 / 评估 / 精炼 / 格式化 ========

    def _retrieve_from_milvus(self, query: str) -> list:
        """从 Milvus 检索文档（Partition Key + 置信度过滤）"""
        try:
            # 注意：不同版本的适配器对过滤参数位置不同，这里使用 search_kwargs 传递 expr
            docs = self.vector_store.similarity_search(
                query,
                k=3,
                search_kwargs={"expr": f'agent_id == "{self.agent_id}"'}
            )
            # 置信度过滤（避免低质量记忆污染）
            filtered_docs = [
                doc for doc in docs
                if (doc.metadata or {}).get("confidence", 0.0) > 0.7
            ]
            return filtered_docs or docs  # 若无高置信度，退回原结果以便 evaluator 判定
        except Exception as e:
            print(f"[CRAG] 检索失败: {e}")
            return []

    def _evaluate_relevance(self, query: str, docs: list) -> Literal["relevant", "ambiguous", "incorrect"]:
        """评估文档相关性（三元判决），简化版：LLM 直接返回 verdict"""
        if not docs:
            return "incorrect"

        # 只评估 Top-3 文档，每个文档取前 500 字符
        doc_content = "\n\n".join([
            f"[文档{i+1}] {(doc.page_content or '')[:500]}..."
            for i, doc in enumerate(docs[:3])
        ])

        prompt = f"""你是文档相关性评估专家。评估以下文档是否能回答查询。

查询：{query}

文档内容：
{doc_content}

评估标准：
- relevant：文档直接包含答案，高度相关
- ambiguous：文档部分相关，需要补充外部知识
- incorrect：文档不相关，无法回答查询

只返回一个词：relevant 或 ambiguous 或 incorrect
"""
        try:
            result = self.evaluator.invoke(prompt)
            verdict = (getattr(result, "content", "") or "").strip().lower()
            if verdict not in {"relevant", "ambiguous", "incorrect"}:
                verdict = "ambiguous"
            return verdict
        except Exception as e:
            print(f"[CRAG] 评估失败: {e}")
            return "ambiguous"

    def _refine_documents(self, docs: list, query: str) -> list:
        """精炼文档（简化条带：基于关键词的句子筛选）"""
        refined = []
        # 简单中文句号替换 + 英文断句的粗切
        keywords = [kw.strip() for kw in query.split() if kw.strip()]
        for doc in docs:
            text = doc.page_content or ""
            sentences = (
                text.replace("。", "。\n")
                    .replace(". ", ".\n")
                    .replace("! ", "!\n")
                    .replace("? ", "?\n")
                    .split("\n")
            )
            sentences = [s.strip() for s in sentences if s.strip()]
            # 命中任一关键词
            relevant_sentences = [
                s for s in sentences
                if any(keyword in s for keyword in keywords)
            ]
            if relevant_sentences:
                refined_text = "。".join(relevant_sentences[:3])
                refined.append(Document(page_content=refined_text, metadata=doc.metadata or {}))
        return refined if refined else docs  # 若未提取到，回退原文档

    def _web_search_fallback(self, query: str) -> list:
        """Web 搜索托底"""
        try:
            return self.web_search.invoke(query) or []
        except Exception as e:
            print(f"[CRAG] Web 搜索失败: {e}")
            return []

    def _merge_context(self, internal_docs: list, web_results: list) -> str:
        """合并内部记忆与外部知识为最终上下文"""
        parts = []
        if internal_docs:
            parts.append("【内部记忆】")
            for i, doc in enumerate(internal_docs, 1):
                parts.append(f"{i}. {doc.page_content}")
        if web_results:
            parts.append("【外部知识】")
            for i, result in enumerate(web_results, 1):
                content = (result or {}).get("content", "")
                url = (result or {}).get("url", "")
                parts.append(f"{i}. {content}\n   来源: {url}")
        return "\n\n".join(parts) if parts else "未找到相关信息"

    def _format_internal_docs(self, docs: list) -> str:
        """格式化内部文档"""
        if not docs:
            return "未找到相关信息"
        parts = ["【内部记忆】"]
        for i, doc in enumerate(docs, 1):
            parts.append(f"{i}. {doc.page_content}")
        return "\n\n".join(parts)

    def _format_web_results(self, results: list) -> str:
        """格式化 Web 搜索结果"""
        if not results:
            return "未找到相关信息"
        parts = ["【外部知识】"]
        for i, result in enumerate(results, 1):
            content = (result or {}).get("content", "")
            url = (result or {}).get("url", "")

        return "\n\n".join(parts)
```

#### 05 尾声

最后，分享一些CRAG 的生产部署建议，大家将 CRAG 部署到生产环境，可以重点关注三个问题：

第一，成本控制：一定要选对评估器

评估器是 CRAG 流程里调用频次最高的环节，选型直接决定了系统的延迟和成本。

如果是高并发的线上生产场景，优先选微调的 T5-Large 这类轻量级模型，延迟 10-20ms，成本可控；如果是快速验证、小流量场景，用 gpt-4o-mini 这类托管模型，不用自己运维，落地快，就是延迟和成本会高一些。

第二，可观测性：把监控体系搭起来

线上系统，看不见的问题才是最致命的。但好在，Milvus 原生支持 Prometheus 指标，可以重点盯这三个核心数据：milvus\_query\_latency\_seconds（查询延迟分布）、milvus\_search\_qps（每秒查询数）、milvus\_insert\_throughput（写入吞吐量），这是检索环节的生命线。

另一方面，CRAG 的评估判决分布、Web 搜索触发率、置信度分布，也必须接入监控。不然线上出了问题，都不知道是检索崩了，还是评估器判歪了。

第三，长期治理：严防记忆污染

Agent 跑的越久，记忆库里的垃圾信息就越多，可以提前引入以下机制：

- 前置过滤：检索时就只返回 confidence&gt;0.7 的高置信度记忆，从源头减少垃圾信息进入流程
- 时间衰减：给记忆加半衰期权重（建议 30 天，可根据业务场景调整），越旧的记忆检索权重越低，避免过期内容长期霸榜
- 定期清理：设置定时任务，每周删除低置信度、从未被验证过的旧记忆，给记忆库定期瘦身，从根源上避免恶性循环

## 结构化（1）

### 2026-03-12 09:34:54

**主旨概括：**  
这篇文章主要讲：**传统 RAG 只看向量相似度，容易 “高分捞错内容”**，而**CRAG 通过 “检索后先评估、再纠正”**，能在生成答案前拦住错误信息。文中还结合**LangChain/LangGraph + Milvus**给出了一套可落地的工程方案。

---

##### 1. 传统 RAG 的核心问题：相似度高，不等于答案可用
文章先指出，传统 RAG 的底层假设是：**相似度高 = 检索质量好**，但在真实业务里常常失效。

###### 关键问题
- **检索偏差**：语义相似，但实际不能解决问题。  
  - 例子：用户问 “**如何在 Nginx 上配置 HTTPS 证书**”，Top3 却可能捞到：
    - Apache 配置方法
    - 已停更的旧版本教程
    - HTTPS 原理解析  
  说明：**看起来相关，不代表真能回答。**

- **时效性缺失**：旧内容和新内容混在一起。  
  - 例子：查询 “**Python 异步编程最佳实践**”，可能同时返回：
    - **2018 年**已废弃写法
    - **2024 年**官方推荐写法

- **记忆污染**：错误内容被生成后又写回记忆库，形成恶性循环。  
  - 比如旧 API 用法被检索到，生成错误代码，再存进记忆库，之后检索会**反复命中旧内容，越用越错**。

###### 结论
- **RAG/Agent 系统必须增加 “检索质量评估” 环节**，不能只靠向量相似度。

---

##### 2. CRAG 的核心思路：在检索和生成之间加 “评估 + 纠正”
CRAG（Corrective RAG）的改进重点，是把传统两步流程：

- 检索 → 生成

升级为四步闭环：

- **检索 → 评估 → 纠正 → 生成**

###### 三元判决机制
CRAG 不再简单地 “用 / 不用”，而是把结果分成 3 类：
- **正确（correct /relevant）**：可直接使用，但仍需精炼
- **模糊（ambiguous）**：部分相关，需要补充外部知识
- **错误（incorrect）**：直接丢弃

###### 为什么还要做 “知识精炼”
传统 RAG 常把**整篇文档直接塞给大模型**，会带来两个问题：
- 浪费 token
- 无关信息太多，容易让模型 “跑偏” 甚至产生幻觉

因此，CRAG 会先精炼信息，只保留最相关内容。

###### 精炼流程
文章给出的简化流程分 3 步：
- **文档分解**：比如从**2000 tokens**中提取**500 tokens**关键片段
- **查询重写**：把模糊问题改写成更明确的搜索词
- **知识选择**：去重、排序、截断

###### 评估器设计原则
- 评估器的目标不是复杂推理，而是**快速筛选**
- 要求能在**几毫秒**内判断 “能不能用”
- 原论文使用的是**微调后的 T5-Large**
- 工程上也可以先用**gpt-4o-mini**做简化实现

###### 检索不够时怎么办
- CRAG 会做**内部检索 + Web 搜索协同**
- 当内部结果错误或不足时，自动触发 Web 搜索，补充**最新信息**，解决时效性问题

---

##### 3. 为什么选 Milvus：它更适合 CRAG 的生产落地
文章认为，CRAG 跑在线上，对向量数据库有 3 个关键要求：
- **多租户隔离**
- **混合检索**
- **动态 Schema**

Milvus 正好适配这三点。

###### 3.1 多租户隔离：用 Partition Key
在 Agent 系统里，可能要同时服务**数百个 Agent 实例**，每个用户 / 场景的记忆都要隔离。

###### Milvus 做法
- 在 Schema 中把`agent_id`设为`is_partition_key=True`
- 查询时自动路由到对应分区，不用为每个租户单独建 Collection

###### 效果
- 在**1000 万向量、100 个租户**场景下
- 配合**Clustering Compaction**
- 带来**3–5 倍 QPS 提升**

---

###### 3.2 混合检索：解决语义检索 “边界失效”
纯向量检索对以下场景效果差：
- 专有名词
- 型号编码，如**“SKU-2024-X5”**
- 精确版本号

###### Milvus 能力
Milvus 2.5 原生支持：
- **Dense 稠密向量**：语义检索
- **Sparse 稀疏向量（BM25）**
- **元数据过滤**
- **RRF 融合排序**

###### 效果
- 在**100 万向量**规模下
- Milvus 的**Sparse-BM25 检索延迟仅 6ms**
- 不会拖慢整个 CRAG 流程

---

###### 3.3 动态 Schema：方便记忆结构演化
随着系统升级，记忆字段会不断增加，比如：
- `confidence`
- `verified`
- `source`

###### Milvus 做法
- 使用**JSON 字段**存元数据
- 可灵活新增字段，不需要停机改表结构

###### 额外优势
- 支持**Lite / Standalone / Distributed**三种部署模式
- 代码兼容，开发环境到生产环境迁移时，**只改连接字符串**

---

##### 4. 基于 LangGraph middleware + Milvus 的 CRAG 实现方案
文章建议：不要把 LangGraph 状态图画得太复杂，**用 middleware 模式更简单**。

###### 选择 middleware 的原因
- 能在模型调用前直接拦截请求
- 一次完成：
  - 检索
  - 评估
  - 纠正
  - 上下文注入
- **代码更少、可读性更高、排查更容易**

###### 整体流程 4 步
1. **检索**：从 Milvus 取 Top-3 文档，并按`agent_id`做隔离  
2. **评估**：轻量模型做三元判决  
3. **纠正**：根据结果执行不同策略  
4. **注入**：把整理后的上下文动态注入给大模型

---

##### 5. 代码实现的关键逻辑
文章给出了一套简化版 CRAG Middleware。

###### 5.1 检索阶段
- 从 Milvus 做相似度搜索
- 带上`agent_id`过滤，实现多租户隔离
- 再按`confidence > 0.7`做一次高置信度过滤  
- 如果过滤后没结果，再退回原结果交给评估器判断

###### 5.2 评估阶段
评估器把检索结果分成：
- `relevant`
- `ambiguous`
- `incorrect`

###### 实现细节
- 只评估**Top-3 文档**
- 每个文档只取前**500 字符**
- 简化实现可直接让 LLM 返回一个词
- 进阶实现可输出结构化 JSON：
  - `verdict`
  - `confidence`
  - `reasoning`

###### 5.3 纠正阶段
根据判决结果，采取不同策略：

- **incorrect**
  - 说明内部检索失败
  - 直接触发**Web 搜索托底**

- **ambiguous**
  - 说明内部结果部分可用
  - 先精炼内部文档，再补充 Web 搜索结果
  - 最后合并上下文

- **relevant**
  - 内部结果可用
  - 只做文档精炼即可

###### 5.4 文档精炼
文章采用了一个工程上够用的简化方案：
- 按句子切分文本
- 提取**包含查询关键词的句子**
- 每篇文档保留前**3 句**

可以理解成：  
不是把整篇文章喂给模型，而是只保留最像答案的几句。

###### 5.5 动态注入上下文
- 通过`dynamic_prompt`
- 把整理好的上下文作为`SystemMessage`
- **只对本次调用生效**
- 不永久污染消息栈

这个设计很重要，因为它能避免 “错误上下文长期留在会话里”。

---

##### 6. 进阶优化：评估器、监控和长期治理
文章最后总结了生产环境的 3 个重点。

###### 6.1 成本控制：评估器要选对
评估器是 CRAG 中调用最频繁的环节，直接影响成本和延迟。

###### 建议
- **高并发生产场景**：优先用微调**T5-Large**
  - 延迟约**10–20ms**
  - 成本更可控
- **快速验证 / 小流量场景**：可用**gpt-4o-mini**
  - 上手快
  - 但延迟和成本更高

---

###### 6.2 可观测性：必须建立监控
Milvus 原生支持 Prometheus，文章建议重点关注：
- `milvus_query_latency_seconds`：查询延迟
- `milvus_search_qps`：查询 QPS
- `milvus_insert_throughput`：写入吞吐量

CRAG 本身还要监控：
- 三元判决分布
- Web 搜索触发率
- 置信度分布

否则出了问题，你无法判断是：
- 检索环节坏了
- 还是评估器判断错了

---

###### 6.3 长期治理：防止记忆污染
Agent 跑久了，记忆库会越来越 “脏”，需要提前治理。

###### 建议机制
- **前置过滤**：只返回`confidence > 0.7`的记忆
- **时间衰减**：建议给记忆设置**30 天半衰期**
- **定期清理**：每周删除低置信度、未验证的旧记忆

###### 目的
- 避免旧内容长期霸榜
- 从根源上阻止 “错误记忆越积越多” 的恶性循环

---

##### 7. 一句话总结
**这篇文章的核心观点是：不要迷信 embedding 相似度，高分不代表可用；要用 CRAG 在 “检索之后、生成之前” 做评估和纠正，再结合 Milvus 的多租户、混合检索、动态 Schema，才能把 RAG 真正落到生产环境。**

### 2026-03-12 09:37:01

下面从**产品设计**、**技术架构**、**实现细节**、**最佳实践**四层拆解。重点不是复述 CRAG，而是说明：**为什么这样设计、哪些地方需要改、怎样才能上线可用。**

---

##### 一、产品视角：这篇内容本质解决什么问题

###### 1）核心问题定义是对的
文章抓住了 RAG 线上最常见的问题：

- **高相似度 ≠ 高可用性**
- **召回正确 ≠ 上下文正确**
- **一次错误生成会污染后续记忆**

这不是检索算法小瑕疵，而是一个**产品可靠性问题**。  
用户不关心 embedding 分数，只关心：**答案能不能用、是不是最新、是否适用于我的场景。**

###### 2）CRAG 的产品价值
CRAG 的真正价值不是 “多加一个模型判断”，而是把 RAG 从：

> 检索系统

升级为：

> 检索质量控制系统

也就是在生成前增加一道**quality gate（质量闸门）**。  
这对以下场景尤其重要：

- 企业知识库问答
- 运维 / 代码助手
- 财务 / 法务 / 医疗等高风险问答
- 长周期 Agent 的记忆系统

###### 3）产品上应定义的三个指标
不要只看 top-k 命中率，要看：

- **Answerable Rate**：召回内容是否足以回答问题
- **Freshness Rate**：答案是否基于最新版本 / 最新政策
- **Contamination Rate**：错误内容进入记忆并反复命中的比例

最佳实践：

```text
RAG 线上最少看 5 个指标：
1. retrieval_hit_rate
2. answer_grounded_rate
3. web_fallback_rate
4. stale_doc_rate
5. memory_contamination_rate
```

---

##### 二、技术视角：这套方案设计上哪里好，哪里还不够

---

###### 1）好的地方：把 “检索、评估、纠正、生成” 拆开
这是工程上最正确的一步。因为传统 RAG 最大问题就是把所有不确定性都压给 LLM。

拆开后的收益：

- 检索负责召回
- 评估负责质量判定
- 纠正负责补全和修复
- 生成负责表达

这符合典型的**可控链路设计**。

---

###### 2）关键改进点一：评估器不该只判断 “相关”，还应判断 “可回答”
文中的`_evaluate_relevance ()`只在做 “相关性判断”，但线上真正要判的是：

- 是否相关
- 是否足够回答
- 是否版本匹配
- 是否可信
- 是否冲突

更合理的是五维打分，而不是单一 verdict。

最佳实践：定义轻量级评估 schema

```python
class RetrievalGrade (BaseModel):
    relevance: float        # 相关性
    completeness: float     # 完整性
    freshness: float        # 时效性
    trustworthiness: float  # 可信度
    consistency: float      # 与其他文档是否冲突
    verdict: Literal ["pass", "partial", "fail"]
```

判定逻辑示例：

```python
if relevance > 0.8 and completeness > 0.7 and trustworthiness > 0.8:
    verdict = "pass"
elif relevance > 0.5:
    verdict = "partial"
else:
    verdict = "fail"
```

**意义**：  
很多 “高分但不可用” 不是不相关，而是**不完整**或**版本不匹配**。

---

###### 3）关键改进点二：知识精炼不能只靠关键词句子抽取
文中的`_refine_documents ()`用关键词命中句子筛选，适合 demo，不适合生产。

原因：

- 中文 query 往往没有空格，`query.split ()`基本失效
- 关键词匹配对同义词、缩写、版本名、实体别名不鲁棒
- 容易错过真正关键句

更好的三层方案：

###### 方案 A：轻量规则版
适合低成本场景：

- jieba /tokenizer 分词
- 停用词过滤
- BM25 对 chunk 内句子重排
- 保留 top-n 句

###### 方案 B：Embedding 级二次精排
适合中等流量：

- 文档 chunk 召回后
- 对 chunk 内 sentence/span 重新 embedding
- 以 query 与 sentence 向量做二次排序
- 选最相关片段

###### 方案 C：结构化抽取
适合高价值场景：

- 用小模型抽取：
  - 前置条件
  - 操作步骤
  - 参数
  - 限制条件
  - 版本信息

比如技术文档问答，推荐把 chunk 转成：

```json
{
  "topic": "Nginx HTTPS configuration",
  "version": "1.25+",
  "steps": ["install cert", "configure server block"],
  "constraints": ["requires openssl", "path format changed after 1.23"],
  "source": "internal_wiki"
}
```

这样评估器判断 “是否可回答” 会更稳定。

###### 4）关键改进点三：Web 搜索触发条件不能太粗
文中逻辑是：

- incorrect → web
- ambiguous → internal + web

这没问题，但生产上要加**触发保护**，否则成本和噪声都会失控。

建议触发条件：

```text
触发 Web Search 当且仅当：
1. 内部召回分数低于阈值
2. 或 freshness 不足
3. 或 query 明显包含 “最新 /today/ 2024 / 本季度 / 最近”
4. 或内部文档版本冲突
```

代码思路：

```python
def should_trigger_web (query, grade, docs):
    time_sensitive = any (x in query.lower () for x in ["最新", "最近", "today", "2024", "季度", "本月"])
    has_version_conflict = detect_version_conflict (docs)
    return (
        grade.verdict == "fail"
        or grade.freshness < 0.6
        or time_sensitive
        or has_version_conflict
    )
```

##### 三、Milvus 选型解读：为什么适合 CRAG

文章这部分是比较实在的，Milvus 确实适合做**长期记忆 + 混合检索 + 多租户**。

---

###### 1）多租户隔离：Partition Key 是对的，但别只靠它
`agent_id`做 partition key 很合理，但还不够。

生产上通常至少分三层隔离：

- tenant_id：客户级别
- agent_id：Agent 实例
- memory_type：memory /docs/logs /evaluations

否则一个 Agent 的长期记忆、文档知识、评估日志全塞一起，检索会互相污染。

推荐 schema：

```python
fields = [
    FieldSchema (name="id", dtype=DataType.INT64, is_primary=True, auto_id=True),
    FieldSchema (name="tenant_id", dtype=DataType.VARCHAR, max_length=64, is_partition_key=True),
    FieldSchema (name="agent_id", dtype=DataType.VARCHAR, max_length=64),
    FieldSchema (name="memory_type", dtype=DataType.VARCHAR, max_length=32),  # doc /episodic/semantic /eval
    FieldSchema (name="dense_embedding", dtype=DataType.FLOAT_VECTOR, dim=1536),
    FieldSchema (name="sparse_embedding", dtype=DataType.SPARSE_FLOAT_VECTOR),
    FieldSchema (name="text", dtype=DataType.VARCHAR, max_length=65535),
    FieldSchema (name="metadata", dtype=DataType.JSON),
]
```

查询时做联合过滤：

```python
expr = 'tenant_id == "t1" and agent_id == "a1" and memory_type == "doc"'
```

---

###### 2）混合检索是这类问题的刚需，不是优化项
“Embedding 相似度虚高” 的根因之一，是 dense retrieval 容易把**语义相似**误当成**事实匹配**。

尤其这些查询必须 hybrid：

- 型号 / SKU / 版本号
- API 名字
- 错误码
- 文件路径
- 配置项名
- 专有实体

最佳实践：

```text
召回策略 = Dense + Sparse + Metadata Filter + Rerank
```

一个实用的权重思路：

- query 含数字 / 大写 token / 连接符：提高 sparse 权重
- query 是自然语言问法：提高 dense 权重
- query 含时间词：提高 freshness filter 权重

伪代码：

```python
def query_strategy (query: str):
    if has_code_or_version (query):
        return {"dense": 0.4, "sparse": 0.6}
    return {"dense": 0.7, "sparse": 0.3}
```

---

###### 3）JSON 动态字段好用，但要做字段治理
JSON 灵活，但不能无序增长。否则后面很难维护。

建议固定一套 metadata 标准：

```json
{
  "source": "internal_wiki",
  "source_type": "doc",
  "doc_id": "nginx_https_v3",
  "version": "1.25",
  "updated_at": "2025-03-01T10:00:00Z",
  "confidence": 0.91,
  "verified": true,
  "ttl_days": 30,
  "tags": ["nginx", "https"],
  "language": "zh",
  "chunk_type": "procedure"
}
```

最重要的几个字段：

- `updated_at`：做时效排序
- `version`：做版本过滤
- `confidence`：做质量过滤
- `verified`：做可信优先
- `ttl_days`：做自动衰减

##### 四、LangChain / LangGraph 实现视角：这段代码怎么改成更像生产系统

---

###### 1）Middleware 选型是对的
如果只是做 “模型调用前增强”，middleware 比复杂 state graph 更适合。

适用场景：

- 单轮增强
- 轻量纠错
- 上下文注入
- 可替换式检索器

不适用场景：

- 多工具协同规划
- 长链决策
- 人工审核流
- 带状态回退的复杂工作流

所以这套设计适合**CRAG as middleware**，不适合复杂 Agent orchestration。

---

###### 2）当前代码里的几个明显问题

###### 问题 A：只存一个 embedding，没真正用 hybrid
前文说了 dense+sparse，但 schema 示例代码只建了一个`embedding`。  
这会导致文章论点和代码实现不一致。

应改成：

```python
FieldSchema (name="dense_embedding", dtype=DataType.FLOAT_VECTOR, dim=1536),
FieldSchema (name="sparse_embedding", dtype=DataType.SPARSE_FLOAT_VECTOR),
```

并显式做 hybrid_search。

---

###### 问题 B：只做 similarity_search，没有 rerank
Top-k 召回后，应该再做一层 rerank，否则评估器负担过重。

最佳实践链路：

```text
Milvus hybrid top20
-> cross-encoder /reranker top5
-> evaluator verdict
-> refine
-> prompt
```

示例：

```python
retrieved = hybrid_search (query, limit=20)
reranked = rerank (query, retrieved)[:5]
```

rerank 可以用：

- bge-reranker
- jina-reranker
- Cohere rerank
- 轻量交叉编码器

---

###### 问题 C：query rewrite 缺失
CRAG 里 “纠正” 的重要部分不是只补 web，而是**改写查询**。

典型例子：

用户问：
> “Nginx 上 HTTPS 怎么搞”

应重写为：

```text
Nginx configure HTTPS SSL certificate server block latest best practice
```

或结构化：

```json
{
  "product": "Nginx",
  "task": "configure HTTPS certificate",
  "constraints": ["latest version", "production setup"]
}
```

建议加一个 query rewrite 模块：

```python
def rewrite_query (query: str) -> str:
    # 轻量规则 + 小模型改写
    return rewritten_query
```

触发场景：

- query 太短
- query 歧义高
- query 口语化严重
- 检索结果分散

---

###### 3）建议的生产级 CRAG Pipeline

推荐改成这条链路：

```text
1. Query classify
   - 是否时效敏感
   - 是否代码 / 配置 / API 问题
   - 是否精确实体检索

2. Query rewrite
   - 扩展实体、版本、别名、缩写

3. Hybrid retrieval from Milvus
   - dense + sparse + metadata filter

4. Rerank
   - top20 -> top5

5. Evaluator
   - relevance /completeness/freshness /trustworthiness

6. Corrective action
   - pass: internal only
   - partial: internal refine + web supplement
   - fail: web /fallback/ask clarification

7. Context compression
   - sentence/span extract /summary

8. Prompt injection
   - source attribution
   - answer constraints

9. Post-answer verification
   - 检查答案是否引用上下文
```

##### 五、最佳实践案例

---

###### 案例 1：技术文档问答
用户问：

> 如何在 Nginx 1.25 上配置 HTTPS 证书？

###### 错误做法
只做 embedding 检索，召回：

- Apache HTTPS 配置
- Nginx 1.18 旧版教程
- TLS 原理文档

相似度都很高，但没法直接回答。

###### 正确做法
1. query classifier 识别：
   - 产品：Nginx
   - 任务：配置 HTTPS 证书
   - 版本：1.25
   - 类型：技术配置类

2. Milvus metadata filter：
```python
expr = 'product == "nginx" and version >= "1.25"'
```

3. hybrid retrieval：
- dense 找语义相关
- sparse 强命中`Nginx`, `HTTPS`, `1.25`, `ssl_certificate`

4. evaluator 检查：
- relevance 高
- completeness 中
- freshness 高

5. refine 抽取：
- server block 配置
- certificate path
- listen 443 ssl
- redirect 80 -> 443

6. 输出时强约束：
```text
如果上下文没有明确配置项，不要编造指令。
```

###### 案例 2：财报问答
用户问：

> Nike 最新季度财报中的运营成本是多少？

###### 风险点
这是典型**时效敏感**问题。只靠内部向量库非常危险。

###### 最佳实践
- query classifier 标记`time_sensitive=True`
- 如果内部文档`updated_at < 30 days`且 source=verified 才优先使用
- 否则直接触发 web search / SEC / IR page
- 回答必须带来源和日期

输出模板：

```text
根据 Nike 于 2025-xx-xx 发布的 xx 财季财报，运营成本为 xxx。
来源：Investor Relations / SEC filing
```

如果来源不足：

```text
内部知识库没有足够新的财报数据，以下回答基于外部公开来源。
```

这是产品可信度关键，不只是技术细节。

---

###### 案例 3：长期 Agent 记忆治理
场景：代码助手长期记录 “用户偏好”“历史方案”。

###### 常见问题
旧方案、错误 API、实验性配置被记成长期 memory，后面不断命中。

###### 最佳实践
给记忆分层：

- **episodic memory**：会话短期记忆
- **semantic memory**：稳定长期知识
- **procedural memory**：用户偏好和固定规则
- **rejected memory**：被判错的内容，留存但永不召回

写入策略：

```python
if confidence > 0.85 and verified:
    write_to_semantic_memory ()
elif confidence > 0.6:
    write_to_episodic_memory (ttl=7d)
else:
    write_to_rejected_bucket ()
```

并加衰减因子：

```python
final_score = retrieval_score * confidence * freshness_decay
```

其中：

```python
freshness_decay = exp (-days_since_update / 30)
```

## 产品-最佳实践（1）

### 2026-03-12 09:46:45

下面用一个**“运维助手查询 Nginx HTTPS 配置”**的具体实例，给出基于你这篇内容的**CRAG + LangChain + Milvus 最佳实践（精炼版）**：

---

##### 实例场景
用户提问：

> 如何在 Nginx 上配置 HTTPS 证书？

传统 RAG 可能检索到：
1. Apache HTTPS 配置教程（高相似，但场景错）
2. 2019 年旧版 Nginx 配置（高相似，但已过期）
3. HTTPS 原理说明（相关但不能直接解决问题）

这就是典型的**Embedding 相似度虚高**。

---

##### 该实例上的最佳实践

###### 1. 检索不要只做向量 TopK，要加 “租户 + 元数据 + 混合检索”
**做法：**
- 用**Milvus**存：
  - dense embedding：语义检索
  - sparse embedding：BM25 / 关键词检索
  - metadata：`agent_id /confidence/verified /updated_at/source_type`
- 查询时先按`agent_id`隔离，再按`confidence > 0.7`过滤。
- 对 “Nginx / SSL /certbot/version” 这类强关键词，优先启用**混合检索**，避免只靠向量命中 Apache 文档。

**最佳实践一句话：**
> 语义召回负责 “找像的”，BM25 和 metadata 负责 “排除错的”。

---

###### 2. TopK 之后必须加 “轻量评估器”，做三元判决
**做法：**
对检索出的 Top3 文档，不直接喂给大模型，而是先让评估器输出：
- `relevant`：文档可直接支撑回答
- `ambiguous`：部分相关，需要补充
- `incorrect`：不该进入生成

**在这个实例里：**
- Apache 教程 → `incorrect`
- 旧版 Nginx 教程 → `ambiguous`
- HTTPS 原理文档 → `ambiguous`

如果没有`relevant`，就不要让主模型直接回答 “操作步骤”。

**最佳实践一句话：**
> 评估器不是为了解释世界，而是为了在毫秒级拦住错文档。

---

###### 3. 不要把整篇文档塞进上下文，只注入 “关键片段”
**做法：**
对 Nginx HTTPS 文档，只提取：
- `listen 443 ssl`
- `ssl_certificate`
- `ssl_certificate_key`
- 重载命令`nginx -t && systemctl reload nginx`

不要把无关的 SSL 原理、历史版本说明、背景介绍一起塞进去。

**最佳实践一句话：**
> 给模型的是 “可执行片段”，不是 “相关文章全文”。

---

###### 4. 模糊或错误时，自动触发 Web 搜索补新
**做法：**
如果内部知识库只有旧版 Nginx 配置，没有新版推荐写法：
- `ambiguous`：内部精炼结果 + Web 搜索结果合并
- `incorrect`：直接放弃内部结果，走 Web 搜索兜底

**在这个实例里：**
可补充搜索：
- Nginx 官方文档
- Let’s Encrypt / Certbot 最新说明
- Ubuntu/CentOS 当前推荐部署方式

**最佳实践一句话：**
> 内部库负责业务沉淀，Web 搜索负责时效性兜底。

---

###### 5. 把 “记忆污染治理” 做成默认机制
**做法：**
将每条记忆写入 Milvus 时，维护：
- `confidence`
- `verified`
- `updated_at`
- `source`
- `version`

并加规则：
- 低置信度内容不参与主检索
- 超过一定时间的配置类知识降权
- 已被评估为错误的内容禁止再次入库

**在这个实例里：**
如果某条旧配置已被判为过期，就不能继续作为高优先级记忆参与召回。

**最佳实践一句话：**
> CRAG 不只是纠错一次，而是防止错误反复回来。

---

##### 最推荐的一套落地策略
如果你要把这个实例真正上线，最稳妥的组合是：

- **Milvus**：做多租户 + 混合检索 + metadata 过滤
- **LangChain / LangGraph middleware**：在模型调用前拦截，执行 CRAG
- **轻量评估器**：先判`relevant /ambiguous/incorrect`
- **知识精炼**：只保留 Nginx HTTPS 配置关键句
- **Web 搜索兜底**：补最新官方实践
- **动态注入上下文**：只对当前轮次生效，不污染长期消息栈

针对 “**Embedding 相似度虚高**” 这个问题，这个实例中的最佳实践可以浓缩成一句话：

> **不要相信相似度分数本身，而要在 “检索后、生成前” 增加评估、精炼和纠正。**
