## 分析要点

- **核心高价值点**：最有价值的是明确区分“组合后能容纳更大模型”与“组合后实际更快”，并要求把通信、格式转换、同步和质量损失全部计入端到端评估。
- **留存建议**：建议精读并长期保留，重点跟踪模型集成后的端到端基准结果（包含可复用的异构推理实验框架、具体通信验证方法、评估指标与后续实验清单，对分布式推理和AI系统工程有持续参考价值。）

**知识要点**

- 预填充偏向并行矩阵计算，适合张量核心；小批量解码更容易受权重与注意力状态的内存带宽限制，因此可探索跨设备角色分离。
- 跨CUDA与Metal迁移请求不仅需要传输KV缓存，还必须保证模型版本、token位置、精度、缓存布局和同步语义一致。
- 异构集群的有效性应分别评估容量收益和性能收益，并用首token时间、接受token吞吐、总响应时间、质量及峰值内存进行端到端比较。

**行动项**

- 将已验证的RDMA与共享缓冲区API集成进推理引擎，完成CUDA到MLX的真实KV缓存交接。
- 对单台Spark、双Spark、Mac Studio及组合集群使用同一工作负载进行可复现基准测试。
- 显式记录状态打包、格式转换、GPU同步和通信开销，验证预填充与解码分离是否产生净收益。

## 正文

**Simon**

翻译一下这篇异构推理的好文章：

我的桌上有一台 256 GB 的 M3 Ultra Mac Studio，和两台 NVIDIA GB10 Spark 级系统，我想让它们围绕同一个模型做点有用的工作。

这就是我开始做 MCDMA 的原因。Spark 给我 CUDA 和 Blackwell 张量核心；Studio 给我一大池统一内存和很高的本地内存带宽。我想弄清楚：把它们合起来，能否让本地推理更快，或者让我跑一个它们中任何一台单独都装不下的模型。

第一件事是让这些机器通过真正的硬件 RDMA 传数据。我现在有了一个原生 macOS ConnectX-5 驱动和用户态 provider，可以在 Studio 和其中一台 Spark 之间完成经过逐字节校验的 READ 和 WRITE，且任意一方都能发起。此后我又验证了由 Metal 和 CUDA kernel 写入并校验的缓冲区之间的双向传输。

这就给了我一条可用的连接，用来做我真正关心的那几件事：把一个正在运行的请求在 CUDA 和 Metal 之间搬移、把一个更大的模型拆到三台机器上、以及在某台机器本来只能干等的时候给它派上有用的活。

我为什么想做这个

提示处理（prompt processing）和 token 生成对模型施加的压力是不同的。预填充（prefill）处理输入并构建它的注意力状态，其中有足够多的并行矩阵运算，正好适合 Sparks 的张量核心。而在小批量（batch）下，解码（decode）往往大部分时间都花在从内存读取权重和注  
意力状态上。

NVIDIA 给每台 Spark 标称 273 GB/s 内存带宽，Apple 给 M3 Ultra 标称 800+ GB/s。这就是我想研究的硬件差异。它不能告诉我某台机器在某个特定模型上一定会赢，但它给了我一个理由去测试：一个请求的每一部分应该跑在哪里。来源：NVIDIA 硬件规格、Apple 的 M3 Ultra Studio 发布公告。

把预填充放在 Sparks、解码放在 Studio，是最显然的第一个实验。预填充/解码分离在 NVIDIA Dynamo 这类系统里已经存在；我的问题是：在我已经拥有的这些 CUDA 和 Metal 机器之间，它什么时候才划算。

我还想对 transformer 理解得足够深，从而能做出比"给每台机器分配一个永久岗位"更好的决策。预填充结束之后，Sparks 能不能起草token、跑驻留的专家、或者开始处理下一个请求，同时 Studio 在解码？在这样做变得值得之前，需要搬移多少状态？

硬件与约束

Studio 有 256 GB 内存，跑 macOS 27。每台 Spark 标称 128 GB，而且这两台之间本来就有自己的 ConnectX-7 连接。

在 Mac 这一侧，一个 OWC Mercury Helios 5S Thunderbolt 5 PCIe 外接盒里装着一张 Mellanox ConnectX-5 Ex MCX516A-CDAT。这张卡有两个 QSFP28 端口，每个标称 100 GbE。来源 ：NVIDIA 网卡规格。

完整布局会把每台 Spark 接到其中一个端口上。两台 Spark 同时也都有到 Studio 的 USB-C 链路。目前验证过的 RDMA 测试只用了一条Spark 到 Studio 的连接；同时使用这张卡的两个端口还有待测试。

这张卡的两个端口共享外接盒到 Mac 的那条连接。OWC 给 Helios 5S 标称最高 6,000 MB/s，约 48 Gb/s，而实际以太网链路建立时协商到40 Gb/s。无论是这张卡的标称值还是外接盒的标称值，都不是这套配置下实测的 RDMA 有效载荷速率。我买了新的 100 GbE 线材，之后会实测链路的协商结果和吞吐。来源：OWC 外接盒规格。

这大约是 800 英镑的网络硬件，对个人实验来说不算少。我差点取消订单，后来还是下了单，并卖掉第三台 Spark 来资助这项研究。我想看看用手上这些硬件能走多远。

我必须自己造的部分

Apple 把这张 Mellanox 卡识别成以太网设备，并不等于给了我一条可用的 ConnectX RDMA 通路。MCDMA 从一个实验性的 DriverKit 实现起步，现在已经发展成一个原生 macOS 驱动加用户态 provider。

这个驱动与卡的固件通信、映射并注册内存、创建队列、提交操作并检查硬件完成事件。现在 ConnectX-5 已经能在 macOS 的 verbs 发现里出现，原生 READ 和 WRITE 双向都通过逐字节校验，包括直接从用户态提交的情况。

我不只是看返回码是否成功。这些测试校验了传输的字节、检查了物理网卡上的 RDMA 计数器，并且尝试了一次未获授权的远程 WRITE。网卡拒绝了该请求，目标缓冲区保持不变。

现在已演示的通路还包括由 GPU 自己产生并校验的数据。一个 Metal kernel 填充源缓冲区，两张网卡通过 RDMA 把它搬过去，再由一个CUDA kernel 校验目标端的每一个字。反方向同样通过，由任意一台主机发起的 READ 操作也通过了。

这些测试在 Studio 上用的是 Metal 共享缓冲区（shared buffer），在 Spark 上用的是 CUDA 映射的主机内存分配。GPU 和网卡访问的是同一块已注册的存储，应用层没有任何载荷中转拷贝。在 kernel 提交和用户态 BlueFlame 两套测试中，全部 24 次 GPU 缓冲区操作都通过，同时还通过了故意写入错误数据的检查和保护区域（guard-region）检查。

我还构建并测试了一个可复用的适配器，用于已有的 CUDA 设备内存分配。它保留应用原本的指针，并通过一块已注册的通信缓冲区做显式的 CUDA 拷贝。应用也可以一开始就把通信缓冲区分配在共享存储里，这样就能走已验证的路径而无需载荷拷贝。

在被测的那台 Spark 上，直接对 cudaMalloc 设备内存做 RDMA 注册是失败的，而 Metal 的私有缓冲区（private buffer）也不被当前的注册路径支持。CPU 仍然负责协调分配、GPU 工作和 RDMA 完成事件。共享缓冲区这条路是通的；下一步是把它集成进推理引擎。

目前的延迟水平

Mac 发起的 4 KiB RDMA 传输现在实测为 10.2 µs（WRITE）和 7.9 µs（READ）。Spark 发起的传输实测为 4.1 µs（WRITE）和 7.1µs（READ）。

这些是从提交到完成的中位时间，使用原生版本 0.1.16、Studio 配置为用户态 BlueFlame 提交、队列深度为 1。每个数字是三次运行共3,000 次测量的汇总；单次完成时间会有波动。这些计时来自更早的普通主机内存基准测试。GPU 缓冲区那些测试是单独验证正确性的，并没有测量 GPU 到 GPU 的延迟或模型性能。

我想解锁的东西

第一个模型实验是一次完整交接。对于一个能同时装进 Studio 和那对 Spark 的模型，我会让它的权重在两处都驻留，先在 Sparks 上做预填充，然后传输 KV cache 和其他必需的状态，让 Studio 接着做生成。

接着我想让这些工作重叠起来。我最初的想法是：以 25 个 prompt token 为一块，把已完成的状态交出去，同时 Sparks 处理下一块。确切答案仍取决于完整 prompt，但传输可以在预填充结束之前就开始。

困难的地方在于让两边的运行时达成一致。模型版本、token 位置、精度和 cache 布局都必须匹配。在 CUDA 和 Metal 上加载相同的权重，并不意味着它们的 cache 字节可以互换。我会把打包、转换和 GPU 同步的开销都算进结果里，因为那才是一个真实请求实际付出的成本  
。

一个模型横跨三台机器

我特别感兴趣的那个实验，是一个在 Studio 加两台 Spark 上合计约 400 GB 常驻权重的模型。这里说的是按所选权重表示法计算的 400GB，不是 4000 亿参数。

三台机器加起来有约 512 GB 标称内存。这些内存仍然是各自独立的，而且每台机器都还需要给操作系统、KV cache、激活值和运行时工作区留出空间。

一种待测布局是把约 200 GB 权重放在那对 Spark 上，200 GB 放在 Studio 上。Sparks 可以用张量并行来分担它们各层内部的计算，而Studio 作为另一个流水线阶段运行另一组层。

权重留在使用它的那台机器上。激活值跨越阶段边界，每个阶段为自己那些层保存 cache。所有必需的阶段都要参与预填充和解码。

我还没有在集群上跑过那个模型。能装下它本身就是一个有用的容量结果；而要让它快，就需要平衡各个阶段，并找到足够多的并发工作让它们都忙起来。

给在等待的机器派有用的活

对单个请求，我想试试投机解码（speculative decoding）。一个小模型提出一批 token，目标模型一次性验证它们，运行时提交被接受的token。结果取决于有多少提案能存活，以及验证的代价有多大。来源：NVIDIA 的投机解码文档。

对多个请求，连续批处理（continuous batching）让一个 worker 同时推进多条独立序列。这可以提高总吞吐，但我也想测量对那个正在等答案的人意味着什么。来源：NVIDIA 的批处理与调度文档。

我想比较"固定角色"和"调度器把下一个有用的活派给空闲机器"。搬移状态或加载权重的代价可能超过省下的工作，而且一台持有分片模型一部分的 Spark 并不能简单地抛弃那个任务。

神经引擎（Neural Engine）是另一个目标。一个通过 Core ML 运行的小型兼容 drafter 可以为一个跑在 Metal 上、负责验证的更大模型提出 token。我需要确认哪些运算真的跑在了神经引擎上，以及每秒被接受的 token 数是否真的提高了。来源：Apple 的 Core ML 文档。

利用额外的链路

两台 Spark 同时还都有到 Studio 的 USB-C 连接，我想看看这些链路能否与 QSFP 并行承载有用的数据。

一个测试是按实测到达时间，把已完成的 KV 块分别走这两条路发送。另一个是把更快的那条路留给立刻需要的状态，让另一条去搬运下一个请求的前缀缓存或适配器。

这需要显式的顺序和归属约定，好让消费方知道哪些字节已经就绪。现有的 USB 软件传输不是硬件 RDMA，共享的控制器或内存流量可能会限制收益。衡量的标准是模型等待的时间是否变少了。

这 25 个实验

这份实验清单是我借助 Claude 和 Codex 整理出来的，既参考了已有研究，也来自我自己的问题。共享缓冲区那部分现在已经通过了最初的正确性测试。以下是更广的实验计划，推理集成和模型基准测试仍在前方。

1\. 把一个兼容的 KV cache 从 CUDA 运行时搬到 MLX，并在 Mac 上继续该请求。  
2\. 当某台 Spark 本来不得不驱逐或重算注意力状态时，把注意力状态留在 Studio 上。  
3\. 以紧凑形式、按原生表示法传输潜在注意力缓存（latent attention cache），连同恢复所需的其他状态一起。  
4\. 尝试树状投机解码，提出多条延续路径并验证其中有用的分支。  
5\. 用神经引擎上的小型 drafter，配合 Metal 上的更大模型做验证者。  
6\. 依据 prompt 长度、预期答案长度和实测排队时间来做请求路由。  
7\. 共享兼容的前缀缓存，避免重复处理相同的 prompt 前缀。  
8\. 把混合专家（MoE）的权重分散在不同机器上，并把激活值发给所需的专家。  
9\. 镜像生成检查点，然后测试受控交接以及故障后的恢复。  
10\. 在剩余 prompt 仍在处理时，就把已完成的预填充状态流式传出去。  
11\. 在已验证的 CUDA/Metal 共享缓冲区基础上，测试运行时集成以及在持续负载下的可见性。  
12\. 比较"常驻 GPU worker 响应传输"与"普通 kernel 启动"两种方式。  
13\. 在 KV cache 每一部分所在的机器上分别计算注意力，然后正确地合并这些部分结果。  
14\. 把模型层拆成流水线阶段，测量阶段平衡和微批（microbatching）。  
15\. 把向量索引放到另一台机器上，在相同搜索质量下比较不同检索方法。  
16\. 在另一台机器上预备好 LoRA 适配器，测量切换进来的代价。  
17\. 跨主机测试对比解码（contrastive decoding），测量质量收益是否值得额外的工作量。  
18\. 用模型级联（model cascade）逐级升级困难请求，只在状态兼容时复用状态。  
19\. 研究用于 LoRA 训练的远程优化器状态。  
20\. 当省下的时间超过迁移成本时，搬移一个正在运行的请求。  
21\. 把控制流量与载荷流量分开，依据实测完成成本来选择传输方式。  
22\. 按内容识别相同的兼容状态，使它不必被存储或传输两次。  
23\. 合并来自不同主机上模型的预测，并衡量质量相对于算力成本。  
24\. 压缩传输的状态，并把压缩耗时计入统计，包括对有损格式做质量检查。  
25\. 随着负载和接受率变化，改变哪台机器起草、哪台机器验证。

什么能说服我

我想要一个可复现的模型结果。只要同一份工作负载能装得下，我就会比较单台 Spark、那对 Spark、Studio 以及组合起来的集群，指标用首 token 时间（time to first token）、每秒被接受的 token 数、总响应时间、质量和峰值内存。

一个只有跨集群才装得下的更大模型，是一个容量结果。而"更快"需要一个端到端的比较，把通信和同步都算进去。这两类我都会报告，包括那些"多加一台机器反而更糟"的实验。

这个驱动给了我一种在真实硬件上提出这些问题的途径。我的下一个目标，是让一个模型请求因为 Sparks 和 Studio 协同工作而更快完成，之后就是更大的模型流水线实验。

我的下一步是准备一个 oMLX 的 PR，把已验证的 RDMA 传输和 GPU 缓冲区 API 集成进推理引擎。这意味着尽可能使用兼容的共享通信缓冲区、把来自已有 CUDA 分配的拷贝都显式化，并把传输完成事件接到模型的执行流程上。然后我就可以对真实的 KV cache 交接和分布式推理做基准测试，把所有转换和同步成本都算进去。

如果你在做 CUDA 或 Metal 运行时，我很想和你交流：如何在不丢状态、也不让转换吃掉全部收益的前提下，把一个正在运行的请求在两者之间交接。我会持续发布实验和测量结果。

驱动、安装指南和验证说明都在 GitHub 上。欢迎在你自己的项目里试用 MCDMA，并分享你做了什么。这是实验性软件，我会继续记录哪些能行、哪些还需要修。

## 口播总结（1）

### 2026-09-17 00:14:57

这项实验要回答一个很实际的问题：一台拥有二百五十六吉字节统一内存的 M3 Ultra Mac Studio，加上两台各有一百二十八吉字节内存的英伟达 GB10 Spark，能不能协同完成更快的本地大模型推理，或者运行任何一台机器单独都装不下的模型？

作者目前还没有证明三台机器合起来一定更快。但他已经解决了一个关键前提：让苹果的 Metal 计算环境和英伟达的 CUDA 计算环境，通过真正的硬件远程直接内存访问来交换数据。

远程直接内存访问，简称 RDMA。它可以让网卡直接读写已经注册的内存，减少传统网络传输中的数据复制和处理开销。为了实现这一点，作者开发了 MCDMA，包括原生的 macOS 驱动和用户态接口。

为什么值得把这几台不同的机器组合起来？关键在于，大模型推理通常可以分成两个阶段，而两个阶段对硬件的需求并不一样。

第一个阶段叫预填充。它负责处理用户输入的提示词，并建立后续生成所需的注意力状态。预填充包含大量可以并行执行的矩阵运算，因此适合使用 Spark 上的 CUDA 和 Blackwell 张量核心。

第二个阶段叫解码，也就是逐个生成令牌。在批量较小时，解码经常不是算力受限，而是内存带宽受限。机器需要反复读取模型权重和注意力状态。每台 Spark 的标称内存带宽是每秒二百七十三吉字节，而 M3 Ultra 的标称带宽超过每秒八百吉字节。

这些纸面参数不能证明 Mac 解码一定更快，但提出了一个合理的实验方向：让 Spark 负责预填充，让 Mac Studio 接手解码。也就是说，不必给每台机器永久分配一种工作，而是根据推理阶段的特点，把请求交给更合适的硬件。

为了测试这个想法，作者在 Mac Studio 外接了一张 ConnectX-5 网卡。网卡有两个标称一百千兆比特每秒的端口，计划分别连接两台 Spark。不过，目前完成验证的只有一条 Spark 到 Studio 的连接。外接盒本身的标称上限约为四十八千兆比特每秒，实际以太网链路目前协商到四十千兆比特每秒，所以网卡端口的纸面速度并不等于最终可用的传输速度。

在正确性方面，作者做的不只是检查软件有没有返回成功。他逐字节验证了传输结果，检查了物理网卡上的 RDMA 计数器，还故意发起了一次未获授权的远程写入。网卡正确拒绝了请求，目标缓冲区也没有被改变。

更重要的是，测试已经覆盖了 GPU 产生的数据。Metal 计算内核先在 Mac 上填充共享缓冲区，网卡再通过 RDMA 把数据传到 Spark，最后由 CUDA 计算内核检查每一个数据字。反方向也通过了验证，而且任意一台主机都可以主动发起读取或写入。

这条路径不需要应用程序额外设置载荷中转缓冲区。GPU 和网卡可以访问同一块已经注册的存储。不过，目前支持的是 Metal 共享缓冲区，以及 CUDA 映射的主机内存。直接注册普通的 CUDA 设备内存失败了，Metal 的私有缓冲区也暂时不受支持。CPU 仍然要负责协调内存分配、GPU 工作和传输完成事件。

在四千字节的小数据传输测试中，Mac 发起写入的中位延迟约为十点二微秒，读取约为七点九微秒。Spark 发起写入约为四点一微秒，读取约为七点一微秒。但这些数字来自普通主机内存测试，只能说明基础传输通路的延迟。GPU 到 GPU 的实际延迟，以及真实模型能否因此提速，都还没有测出来。

接下来最直接的模型实验，是一次完整的请求交接。模型权重会同时驻留在 Spark 和 Studio 上。Spark 先完成预填充，然后把键值缓存，也就是 KV cache，以及其他必要状态传给 Studio，由 Studio 继续生成答案。

作者还计划在预填充结束前就开始传输。例如，每处理完大约二十五个提示词令牌，就发送一块已经完成的状态，同时让 Spark 继续处理下一块。这样，计算和通信可能重叠，而不是等所有预填充完成后才开始传输。

真正困难的地方，不只是搬运字节，而是让两套运行时对这些字节有完全一致的理解。CUDA 和 Metal 两边必须使用相同的模型版本、令牌位置、数值精度和缓存布局。即使加载了相同权重，也不代表两边的缓存格式可以直接互换。数据打包、格式转换、GPU 同步和传输等待，都必须计入成本。否则，局部传输看起来很快，完整请求却可能更慢。

另一个更有野心的实验，是把约四百吉字节的常驻权重分布到三台机器上。这里的四百吉字节指权重占用空间，并不是四千亿参数。三台机器共有约五百一十二吉字节标称内存，但还要为操作系统、键值缓存、激活值和运行时工作区留出空间。

一种设想是，把大约二百吉字节权重放在两台 Spark 上，另外二百吉字节放在 Studio 上。两台 Spark 通过张量并行处理一部分模型层，Studio 作为另一个流水线阶段处理其余层。权重留在实际使用它的机器上，只让激活值跨机器传输。

如果这个模型最终能够运行，它首先证明的是容量提升，也就是组合系统能装下单机装不下的模型。但这不等于速度提升。要让它跑得快，还必须平衡各个流水线阶段，并提供足够的并发任务，避免某台机器一直等待。

作者也希望把等待中的机器利用起来。例如，让小模型进行投机解码，先提出一批候选令牌，再由大模型一次验证；或者通过连续批处理，同时推进多个用户的请求。还可以让苹果神经引擎运行一个小型候选模型，再由 Metal 上的大模型负责验证。

不过，动态调度并不天然更好。搬移状态、转换缓存或者重新加载权重的成本，可能超过节省下来的计算时间。额外的 USB-C 链路也只有在真正减少模型等待时间时才有价值，而不是因为多了一条传输通道就一定有用。

最终的判断标准必须是可复现的端到端结果。作者计划在相同工作负载下，比较单台 Spark、两台 Spark、Mac Studio，以及三者组成的集群。指标包括首个令牌出现的时间、每秒生成并被接受的令牌数、总响应时间、输出质量和峰值内存。通信、格式转换和同步成本都要计算在内。

最值得记住的是，异构推理的价值不在于简单相加算力，而在于把不同阶段安排到最合适的硬件上。RDMA 通路已经证明可以正确工作，但更快还没有被证明。真正有说服力的结果，必须同时考虑计算、内存、通信和状态兼容，并且坦诚报告那些“多加一台机器反而更慢”的实验。

## 深度解读（1）

### 2026-09-17 00:40:46

#### 异构推理的关键，不是把机器连起来，而是让“状态搬家”值得

这项工作的真正贡献，目前还不是证明 Mac Studio 与两台 NVIDIA Spark 协作后推理更快，而是**打通并严格验证了一条此前缺失的 CUDA—Metal RDMA 通路**：Metal 和 CUDA kernel 生成的数据可以经网卡双向传输，接收端逐字校验；未授权写入也会被硬件拒绝。相比“接口调用成功”，这已经是可供推理引擎集成的工程基础。

但作者也很克制：现有数据只证明传输正确，并测得普通主机内存下 4 KiB 操作约 4—10 微秒；它尚未证明 GPU 到 GPU 的实际吞吐，更没有证明端到端模型性能提升。这一区分很重要——**基础设施可用、模型能运行、系统更快，是三个不同层次的结果。**

##### 异构硬件的价值，来自任务阶段不同，而非算力简单相加

作者选择“Spark 做预填充、Mac 做解码”，依据是两阶段的资源需求不同：预填充包含大量可并行矩阵运算，更适合 Blackwell 张量核心；低批量解码则不断读取权重和 KV cache，往往更受内存带宽限制，而 M3 Ultra 的标称内存带宽明显更高。

这比按设备固定分工更有启发性：推理调度的对象不应只是“一个模型或一个请求”，还可以是**请求的不同阶段和持续变化的状态**。如果成立，调度器需要结合 prompt 长度、预计输出长度、队列负载和迁移成本，动态判断请求留在哪里，而不是永远让某台机器只负责预填充。

不过，标称带宽不能直接推出结果。Mac 与 Spark 当前链路仅协商到约 40 Gb/s，理论上约 5 GB/s，与两端数百 GB/s 的本地内存带宽相差两个数量级。CUDA 与 Metal 的 cache 布局还可能不同，转换、同步和额外拷贝都会消耗收益。因此，异构协作更可能在以下条件下划算：状态只迁移少数几次、迁移能与计算重叠，且后续阶段节省的时间足够长。频繁跨机调用专家或逐小块搬运状态，反而可能被通信成本吞没。

##### “装得下”与“跑得快”应被分开评价

三台机器合计约 512 GB 内存，可能容纳约 400 GB 常驻权重，这是明确的容量机会：即使速度不理想，也能运行单机无法承载的模型。但分片内存并不会自动变成统一内存；每台机器仍需保留 KV cache、激活值和运行时空间，所有流水线阶段也必须参与每个 token 的计算。最慢阶段、跨阶段延迟和并发量共同决定最终速度。

这提醒我们，不应把分布式推理只看作“扩容”。**容量结果回答能不能运行，性能结果回答值不值得这样运行。**作者计划同时比较首 token 时间、总响应时间、接受 token 吞吐、质量和峰值内存，并报告“加机器反而更差”的实验，这比单报峰值吞吐更接近真实产品体验。

##### 更长期的机会是建立跨运行时的“状态协议”

这项实验最值得延伸的方向，可能不是某一套硬件组合，而是 CUDA、Metal、MLX、Core ML 之间缺少稳定的推理状态交换层。权重相同不代表 KV cache 的字节表示兼容；位置、精度、布局、同步语义和模型版本都必须一致。若这些问题能被标准化，请求迁移、共享前缀缓存、故障恢复、投机解码和远程 LoRA 切换才可能成为通用能力。

这里潜在的产品对象，是需要本地部署、已有混合硬件且不愿全部替换为单一厂商集群的团队。现有替代方案仍是量化模型、单机扩容或同构集群。需要验证的核心假设不是“大家喜欢异构”，而是：**在计入转换、同步和运维成本后，状态复用与动态调度能否带来稳定、可复现的延迟或容量收益。**

MCDMA 已经解决了“字节能否安全到达”；接下来真正决定价值的，是这些字节是否足够少、足够兼容，并且搬得足够值得。

## 总结（1）

### 2026-09-17 10:39:30

这项实验想回答一个很实际的问题：一台苹果 Mac Studio 和两台英伟达 Spark，能不能围绕同一个大模型协同推理？目标不只是把三台机器连起来，而是让请求更快完成，或者运行任何一台机器单独都装不下的模型。

三台机器的特点很不一样。两台 Spark 支持 CUDA，并拥有适合大规模矩阵运算的 Blackwell 张量核心。Mac Studio 使用 M3 Ultra，拥有二百五十六吉字节统一内存，以及更高的本地内存带宽。

这种差异，正好对应大模型推理的两个阶段。

第一个阶段叫预填充。它负责处理用户输入，并建立注意力状态。这个阶段有大量可以并行执行的矩阵运算，因此更适合 Spark 的张量核心。

第二个阶段叫解码，也就是逐个生成新的词元。在小批量场景下，解码经常不是算力受限，而是内存带宽受限。机器要不断读取模型权重和注意力状态。每台 Spark 的标称内存带宽是每秒二百七十三吉字节，而 M3 Ultra 超过每秒八百吉字节。

因此，最直观的方案是：让 Spark 负责预填充，再把请求的状态交给 Mac Studio，由 Studio 继续生成答案。不过，硬件参数只能说明这种分工值得测试，不能证明它一定更快。真正的关键，是搬运状态和转换格式的成本，会不会吃掉全部收益。

为了验证这一点，作者开发了一个名为 MCDMA 的项目，为 macOS 实现原生的远程直接内存访问，也就是 RDMA。简单来说，RDMA 可以让网卡直接读写已经注册的内存，减少普通网络传输中由处理器参与的数据复制。

作者使用一张 Mellanox ConnectX-5 网卡，把 Mac Studio 和一台 Spark 连了起来。现在，任意一方都能发起 RDMA 读取和写入。传输结果不是只看 “成功” 返回码，而是逐字节校验。测试还故意发起了一次未经授权的远程写入，网卡正确拒绝了请求，目标缓冲区也没有被改变。

更重要的是，这条通路已经扩展到图形处理器产生的数据。Metal，也就是苹果的 GPU 计算框架，可以先生成一块数据。数据通过 RDMA 传到 Spark，再由 CUDA 内核逐字校验。反方向同样可以工作。

在这条已验证的共享缓冲区路径上，GPU 和网卡访问的是同一块已注册存储，应用层不需要再做一次载荷中转复制。相关的二十四次 GPU 缓冲区操作全部通过，错误数据检测和保护区域检查也通过了。

不过，限制仍然存在。Spark 上由 CUDA 直接分配的设备内存，目前无法直接注册给 RDMA。Metal 的私有缓冲区也不受现有路径支持。已有的 CUDA 内存，可以先显式复制到注册过的通信缓冲区。CPU 仍然要负责协调内存分配、GPU 工作和 RDMA 完成事件。

目前测到的四千字节传输延迟，大约在四到十微秒之间，具体取决于传输方向和由哪台机器发起。但这些数字来自普通主机内存测试。GPU 到 GPU 的真实延迟，以及完整模型的推理性能，还没有测出来。

这一区别非常重要。现在已经证明的是，底层数据通路可以正确工作。还没有证明的是，多台机器协同推理一定比单机更快。

接下来，第一个模型实验会做一次完整的请求交接。模型权重同时驻留在 Spark 和 Studio 上。Spark 完成预填充后，把键值缓存，也就是 KV cache，以及继续生成所需的其他状态传给 Studio。Studio 再接手解码。

作者还希望把传输和计算重叠起来。例如，每处理完大约二十五个输入词元，就把已经完成的状态向外传输，同时 Spark 继续处理下一块输入。这样，传输不必等到整个预填充阶段结束后才开始。

真正困难的地方，是让 CUDA 和 Metal 两套运行时对状态达成完全一致。模型版本、词元位置、数值精度和缓存布局都必须匹配。即使两边加载了相同权重，也不代表缓存的字节格式可以直接互换。打包、格式转换、GPU 同步和传输等待，都必须计入最终结果。

另一个更有野心的实验，是让一个权重规模约四百吉字节的模型横跨三台机器运行。这里的四百吉字节指权重占用空间，不是四千亿参数。

三台机器共有大约五百一十二吉字节标称内存，但这些内存彼此独立，还要为操作系统、KV cache、激活值和运行时工作区留下空间。一种设想是，把约二百吉字节权重放在两台 Spark 上，另外二百吉字节放在 Studio 上。Spark 通过张量并行处理一组模型层，Studio 作为另一个流水线阶段处理另一组模型层。

在这种布局中，权重留在使用它的机器上，跨机器传输的是激活值。每个阶段保存自己负责部分的缓存。这样做首先解决的是容量问题：三台机器合起来，能运行单机装不下的模型。至于速度是否理想，还取决于阶段能否平衡，以及是否有足够多的并发工作让所有机器保持忙碌。

作者还计划测试更灵活的调度方式。比如，当 Studio 正在解码时，Spark 可以用小模型起草一批候选词元，再由大模型一次验证，这叫投机解码。对于多个请求，还可以使用连续批处理，让空闲机器推进其他序列。也可以共享重复使用的输入前缀缓存，分散混合专家模型的专家权重，或者只在节省时间超过迁移成本时，搬移一个正在运行的请求。

这些方案的共同问题是：不能只看省下了多少计算，还要看搬运了多少状态、等待了多久，以及格式转换付出了什么代价。有时增加一台机器，反而会让系统更慢。

因此，最终的判断标准必须是端到端结果。作者计划比较单台 Spark、两台 Spark、单台 Studio，以及三台机器组成的集群。指标包括首个词元出现的时间、每秒真正被接受的词元数、完整响应时间、输出质量和峰值内存。通信与同步成本必须全部计算在内。

这项工作的核心认识有三个。异构硬件的价值，不在于简单叠加算力，而在于把不同推理阶段放到更合适的机器上。跨机器运行更大模型，与让同一个模型跑得更快，是两种不同的成功。最重要的是，底层传输已经被证明可行，但真正的收益，只有在完整模型、真实状态和全部转换成本都计入之后，才能确定。

## 默认总结（1）

### 2026-09-18 01:10:26

##### 一句话看懂

作者为 Mac Studio 与两台 NVIDIA Spark 自研了 macOS RDMA 驱动，已打通 Metal/CUDA 缓冲区传输，但“异构协同推理更快”目前仍是待验证目标。

##### 关键内容

- **基础链路已跑通**：ConnectX-5 可在 macOS 上执行双向 RDMA READ/WRITE，并通过逐字节、越权访问和保护区测试；Metal 与 CUDA 生成的数据也能互传，无需应用层中转复制。
- **核心设想是按硬件特长分工**：Spark 用张量核心做适合并行计算的预填充，M3 Ultra 借较高内存带宽做解码，再传递 KV cache 等状态。
- **已有延迟不等于模型收益**：4 KiB RDMA 延迟约 4.1—10.2 微秒，但这是主机内存测试；尚未测 GPU 到 GPU 延迟，也未完成真实模型的端到端基准。
- 后续将测试请求交接、流水线并行、投机解码，以及让约 400 GB 权重分布在三台机器上。作者会把转换、同步和通信成本全部计入，允许出现“机器越多反而越慢”的结果。

##### 通俗解读

RDMA相当于让网卡直接搬运已注册内存，减少 CPU 转手；但数据搬得快，不代表推理一定更快。两端还必须统一模型版本、精度和缓存格式，转换成本可能吃掉收益。
