#### 1\. The Agent Harness 代理框架

The first decision is what harness your agent will run in.  
第一个决定是你的代理将运行在哪个环境中。

Stripe forked. They took Block's open-source

[goose](https://github.com/block/goose) coding agent and customized it with opinionated orchestration that interleaves agent loops with deterministic code for git operations, linters, and testing. Forking gave them a head start on the core agent loop while letting them impose strict control over how that loop interacts with Stripe's infrastructure.  
Stripe 分叉了。 他们采用了 Block 的开源

[goose](https://github.com/block/goose)

编码代理，并使用有主见的编排对其进行定制，该编排将代理循环与用于 Git 操作、代码检查工具和测试的确定性代码交织在一起。分叉使他们在核心代理循环方面获得了先发优势，同时让他们能够严格控制该循环与 Stripe 基础设施的交互方式。

Ramp composed. They built on top of

[OpenCode](https://github.com/opencode-ai/opencode) as the underlying agent, choosing it for its server-first architecture and typed SDK. A practical bonus: the agent can read its own source code, which helps it understand its own capabilities. Composing on an existing agent gives you an upgrade path — you can pull in improvements from upstream — but couples you to that project's architectural decisions.  
Ramp 已组合。 他们在

[OpenCode](https://github.com/opencode-ai/opencode)

的基础上构建，将其作为底层代理，选择它是因为其服务器优先架构和类型化 SDK。一个实际的优势是：该代理可以读取自身的源代码，这有助于它了解自身的能力。在现有的代理基础上进行组合为你提供了一条升级路径——你可以引入上游的改进——但这也使你受制于该项目的架构决策。

Coinbase built from scratch. Their agent, Cloudbot, is in-house built and multi-model — not locked to any single provider. Security requirements for a financial platform handling crypto drove this decision. Building from scratch gives you total control but carries the highest implementation cost.  
Coinbase 从零开始构建。 他们的代理程序 Cloudbot 由内部开发，采用多模型架构，——不绑定于任何单一供应商。对于处理加密货币的金融平台的安全要求促使了这一决策。从零开始构建能让你完全掌控，但需要承担最高的实施成本。

The tradeoffs are straightforward. Forking gives you speed but ties you to upstream decisions you may not agree with. Composing gives you an upgrade path but couples you to a framework's center of gravity. Building gives you full control but means you own every bug.  
权衡取舍很直接。分叉能让你获得速度，但会让你受制于你可能不认同的上游决策。组合能为你提供升级路径，但会让你与框架的重心紧密相连。构建能让你完全控制，但意味着你要承担所有的 bug。

#### 2\. The Sandbox: Where Agents Run Code 2. 沙箱：代理运行代码的地方

You could have engineers run agents locally, but once agents are writing and executing code autonomously, uncontrolled local execution gets risky fast. All three companies converge on cloud-based sandboxes whether ephemeral VMs or containers. The sandbox is part of your safety model. Your agent execution environment is one of the most consequential decisions you'll make.  
你可以让工程师在本地运行代理，但一旦代理开始自主编写和执行代码，不受控制的本地执行会迅速变得危险。这三家公司都聚焦于基于云的沙箱，无论是临时虚拟机还是容器。沙箱是你安全模型的一部分。你的代理执行环境是你需要做出的最重要的决策之一。

Stripe: Cloud VMs as Cattle  
Stripe：云虚拟机如牛群

Stripe runs agents on devboxes — AWS EC2 instances that serve as standardized cloud developer environments. They're treated as cattle, not pets: easily replaceable, spun up from a proactively warmed pool with 10-second readiness.  
Stripe 在开发环境实例上运行代理——这些是作为标准化云开发环境的 AWS EC2 实例。它们被当作牲畜而非宠物对待：易于替换，可从预先预热的池中快速启动，10 秒内即可就绪。

Each devbox comes pre-loaded with everything an engineer (or agent) needs:  
每个开发箱预装了工程师（或代理）所需的一切：

- Pre-cloned git repositories (gigabytes of source code)  
  预先克隆的 git 仓库（千兆字节的源代码）
- Warmed Bazel and type-checking caches  
  预热的 Bazel 和类型检查缓存
- Running code generation services  
  运行中的代码生成服务
- Checked out to a recent copy of master  
  检出到 master 的最近副本

The isolation model is what makes this work at a payments company. Devboxes run in a QA environment with no real user data, no access to production Stripe services, and no arbitrary network egress. Because the blast radius of any mistake is fully contained, agents can run with full permissions and no confirmation prompts.  
隔离模型是支付公司实现这一工作的关键。开发机运行在 QA 环境中，该环境无真实用户数据，无法访问生产环境的 Stripe 服务，且无任意网络出站流量。由于任何错误的影响范围都被完全控制，代理程序可以以完全权限运行且无需确认提示。

Stripe's insight here is: a development environment that is safe for humans has proven to be just as useful for agents. You don't need to invent new security primitives — you need to make your existing ones fast enough for agents to use.  
Stripe 的这一见解是：一个对人类安全的开发环境已被证明对代理同样有用。你不需要发明新的安全原语——你只需要让现有的安全原语足够快，以便代理能够使用。

Ramp: Container Platform with Pre-Warming  
Ramp：带预热的容器平台

Ramp uses Modal for isolated development environments. Pre-built images and snapshots keep repositories current within a 30-minute window — fresh enough for most work, fast enough for on-demand spin-up.  
Ramp 使用 Modal 用于隔离的开发环境。预构建镜像和快照在 30 分钟内保持代码仓库最新——对于大多数工作来说足够新，对于按需启动来说足够快。

Ramp optimizes for speed. They pre-warm sandboxes while the user is still typing their prompt. By the time the user hits enter, the sandbox is ready. They also do early file reads before sync is fully complete and batch repository-level build steps to minimize startup latency. Agents can also spawn child sessions for parallel work — a sandbox-within-a-sandbox model that lets one agent fan out across multiple tasks.  
Ramp 优化速度。他们在用户仍在输入提示时就预先预热沙箱，等到用户按下回车键时，沙箱已准备就绪。他们还在同步完全完成前提前读取文件，并批量处理代码仓库级别的构建步骤，以减少启动延迟。代理还可以生成子会话以进行并行工作——这是一种嵌套沙箱模型，允许单个代理分散处理多个任务。

The result: "Inspect sessions are fast to start and effectively free to run...There's no limit to how many sessions you can have running concurrently, and your laptop doesn't need to be involved at all." They can start a session the moment inspiration hits from anywhere.  
结果：“Inspect 会话启动迅速，实际上可以免费运行……并发运行的会话数量没有限制，而且你的笔记本电脑根本不需要参与。”他们可以在灵感迸发的瞬间，随时随地启动会话。

Coinbase: Security-Driven In-House  
Coinbase：安全驱动的内部

Coinbase built their sandbox in-house, driven by security requirements specific to handling financial and crypto infrastructure. The specifics aren't public, but the motivation is clear: when you're a regulated financial institution, the sandbox isn't just a developer convenience — it's a compliance boundary.  
Coinbase 在内部开发了他们的沙箱环境，由处理金融和加密货币基础设施的特定安全要求驱动。具体细节并未公开，但动机很明确：当你是一家受监管的金融机构时，这个沙箱不仅仅是为开发者提供便利——它更是一道合规边界。

The Pattern  
这个模式

All three converge on the same principle: isolate first, then give full permissions inside the boundary. The sandbox is what makes unattended agent execution safe. If you try to make agents safe through permission prompts and approval gates instead of isolation, you'll end up with an agent that's too slow to be useful or too permissive to be safe.  
这三者都遵循同一个原则： 先隔离，然后在边界内授予完全权限。 沙箱是使无人值守代理执行安全的关键。如果您试图通过权限提示和审批流程而非隔离来确保代理安全，最终得到的代理要么太慢而无法发挥作用，要么过于宽松而不安全。

#### 3\. Tools and Context: What Agents Can See and Do 3. 工具与上下文：代理能看到和做什么

How many tools your LLM can handle and what context to give it is more art than science. Here's how each company approaches it:  
你的 LLM 能处理多少工具以及给它提供什么上下文，更多的是艺术而非科学。以下是每家公司处理这个问题的方式：

Tool Infrastructure  
工具基础设施

All three companies give their agents access to internal tools via structured interfaces, but at very different scales.  
这三家公司都为其代理通过结构化界面访问内部工具，但规模差异很大。

Stripe built an internal MCP server called Toolshed hosting nearly 500 tools spanning internal systems and SaaS platforms. But the critical design decision isn't the number of tools — it's the curation. Agents receive an intentionally small default subset of tools, not unrestricted access to all 500. Each agent instance gets a curated toolset, with per-user customizability and thematic tool grouping. Security controls prevent destructive actions.  
Stripe 开发了一个名为 Toolshed 的内部 MCP 服务器，该服务器托管了近 500 个工具，涵盖内部系统和 SaaS 平台。但关键的设计决策不在于工具的数量，而在于筛选过程。代理收到的是一个刻意设置的较小默认工具子集，而非对全部 500 个工具的无限制访问。每个代理实例都拥有一个经过筛选的工具集，支持按用户定制化和工具主题分组。安全控制措施可防止破坏性操作。

The insight: tool curation matters more than tool quantity. Giving an agent access to 500 tools doesn't make it more capable — it makes it more confused and wastes tokens on tool selection. Constraining the toolset per agent type produces better results.  
洞察： 工具筛选比工具数量更重要。 让一个智能体可以使用 500 个工具并不会使其更强大——反而会使其更加困惑，并在工具选择上浪费 token。根据不同智能体类型限制工具集，能产生更好的结果。

Coinbase takes a different approach to tool breadth. Cloudbot connects to MCPs for Datadog, Sentry, Amplitude, and internal Snowflake databases, plus custom Skills layered on top. It can work across multiple codebases. The emphasis is less on a unified tool platform and more on connecting the specific observability and data sources that matter for debugging and implementation.  
Coinbase 在工具广度方面采取了不同的方法。Cloudbot 连接到针对 Datadog、Sentry、Amplitude 以及内部 Snowflake 数据库的 MCPs，并在其基础上叠加了自定义技能。它可以跨多个代码库工作。其重点不在于统一的工具平台，而在于连接对调试和实现至关重要的特定可观测性和数据源。

Ramp builds on OpenCode's built-in tool system at the SDK level, extending it with their own integrations.  
Ramp 在 SDK 层面基于 OpenCode 的内置工具系统构建，并通过他们自己的集成对其进行扩展。

Context Engineering  
上下文工程

This is where the real sophistication lives. Getting the right information into the agent's context — not too much, not too little — is the difference between an agent that produces useful PRs and one that hallucinates.  
这才是真正的精妙所在。将恰当的信息纳入代理的上下文——不多不少——是区分能生成有用 PR 的代理与会产生幻觉的代理的关键。

Stripe's rule files use Cursor's format with directory and pattern scoping. Rules automatically attach as the agent traverses the filesystem, and they're synced across three platforms: Minions, Cursor, and Claude Code. This means the same institutional knowledge that helps a human engineer in Cursor also helps an unattended agent. Almost all rules are conditionally applied based on subdirectories — necessary for a codebase with hundreds of millions of lines where different regions have radically different conventions.  
Stripe 的规则文件使用 Cursor 的格式，带有目录和模式作用域。规则会在代理遍历文件系统时自动附加，并在三个平台间同步：Minions、Cursor 和 Claude Code。这意味着，帮助 Cursor 中的人类工程师的相同机构知识也能帮助无人值守代理。几乎所有规则都是基于子目录有条件地应用的——对于拥有数亿行代码的代码库来说是必要的，因为不同区域有截然不同的规范。

Stripe also does context pre-hydration: before a Minion run even starts, the orchestrator scans the Slack thread for links, deterministically pulls Jira tickets, documentation, and Sourcegraph code search results, and runs relevant MCP tools over likely-looking links. The agent starts its work with a rich, pre-assembled context rather than having to discover everything through tool calls.  
Stripe 也会进行上下文预填充 ：在 Minion 运行开始之前，编排器会扫描 Slack 线程中的链接，确定性地拉取 Jira 工单、文档以及 Sourcegraph 代码搜索结果，并对看起来可能相关的链接运行相关的 MCP 工具。代理会以丰富的、预先组装好的上下文开始工作，而无需通过工具调用发现所有内容。

Coinbase uses Linear as a single context source. All context gets captured in Linear tickets first — the structured bug report, the relevant user journey, the attached files. Then Cloudbot pulls from Linear and fans out into MCPs for additional context. This creates a clean separation: humans curate context into Linear, agents consume it from Linear plus everything else.  
Coinbase 使用 Linear 作为单一的上下文来源。所有上下文首先在 Linear 工单中被捕获——结构化的错误报告、相关的用户流程、附件。然后 Cloudbot 从 Linear 中提取信息并分发到 MCPs 以获取额外的上下文。这形成了清晰的分离：人工将上下文整理到 Linear 中，代理从 Linear 以及其他所有来源中获取上下文。

As Turakhia put it on the How I AI podcast, the thing he realized is that context is the most important thing — so they funnel everything into Linear first, then let Cloudbot fan out from here.  
正如 Turakhia 在 How I AI 播客中所说，他意识到的关键是，上下文是最重要的东西——因此他们首先将所有内容都导入到 Linear 中，然后让 Cloudbot 从这里向外扩展。

#### 4\. Orchestration: How Agents Think and Act 4. 编排：代理如何思考与行动

The fourth decision is how you structure the agent's execution — the loop between receiving a task and producing a pull request.  
第四个决策是你如何构建代理的执行——即在接收任务和生成拉取请求之间的循环。

Stripe's Blueprints  
Stripe 的蓝图

This is Stripe's most distinctive architectural contribution. Blueprints are a hybrid pattern that combines the determinism of workflows with the flexibility of agents, implemented as a state machine that alternates between two types of nodes.  
这是 Stripe 最具特色的架构贡献。蓝图是一种混合模式，结合了工作流的确定性与代理的灵活性，实现为一种在两种类型的节点之间切换的状态机。

Deterministic nodes always execute the same way: run linters, format code, push to git, execute pre-push hooks. These are the steps that must happen and that LLMs are bad at remembering to do consistently.  
确定性节点总是以相同的方式执行：运行 linters，格式化代码，推送到 Git，执行推送前钩子。这些是必须发生的步骤，而 LLMs 不擅长持续记住去做这些步骤。

Agentic subtask nodes give the LLM creative freedom within a bounded scope: "implement the task described in this ticket," "fix CI failures from the previous run." The LLM can use whatever tools and reasoning it needs, but only within that subtask boundary.  
智能体子任务节点给予 LLM 在有限范围内的创造性自由：“执行本工单中描述的任务”、“修复上一次运行中的 CI 失败”。LLM 可以使用任何所需的工具和推理方式，但只能在该子任务范围内。

The power of Blueprints is composability. Teams create team-specific custom blueprints for specialized workflows. A team that owns a particular service can encode their deployment conventions, testing requirements, and code review standards into a blueprint — and every agent that runs against their code automatically follows those conventions.  
蓝图的强大之处在于可组合性。 团队特定的自定义蓝图用于特定工作流。拥有特定服务的团队可以将其部署规范、测试要求和代码审查标准编码到蓝图中——并且每个针对其代码运行的代理都会自动遵循这些规范。

The key principle: putting LLMs into contained boxes compounds reliability. Each deterministic node you add is one fewer thing the LLM can get wrong, which saves tokens, saves CI costs, and makes the overall pipeline more predictable.  
关键原则：将 LLMs 放入包含的盒子中可增强可靠性。你添加的每一个确定性节点，都会让 LLM 出错的地方少一个，这节省了 token，节省了 CI 成本，并使整个流程更可预测。

Ramp's Session Model  
Ramp 的会话模型

Ramp's orchestration centers on sessions — long-running agent contexts that support follow-up prompts, stopping mechanisms, and multiplayer collaboration.  
Ramp 的编排以会话为中心——长期运行的代理上下文，支持跟进提示、停止机制和多人协作。

The session model introduces a design decision Stripe doesn't face with one-shot agents: when a user sends a follow-up prompt, do you queue it or execute immediately? Ramp handles both cases. They also support child sessions, where an agent can spawn sub-agents for parallel work while maintaining a parent context.  
会话模型引入了一个 Stripe 在一次性代理中不会面临的设计决策：当用户发送后续提示时，你是将其排队处理还是立即执行？Ramp 同时支持这两种情况。 子会话 ，其中代理可以生成子代理以进行并行工作，同时保持父上下文。

Multiplayer is a feature Ramp frames as mission-critical. Multiple team members can collaborate on a single agent session with individual authorship tracking. Use cases include teaching workflows (a senior engineer guides a junior through an agent-assisted task) and QA workflows (a reviewer joins an active session to inspect the agent's work in progress).  
多人是 Ramp 视为关键任务的一项功能。多名团队成员可以在单个代理会话中协作，并进行个人作者身份跟踪。用例包括教学工作流（高级工程师指导初级工程师完成代理辅助任务）和质量保证工作流（审核人员加入活跃会话以检查代理的进行中的工作）。

Coinbase's Three-Mode Model  
Coinbase 的三模式模型

Cloudbot offers three distinct modes, each optimized for a different interaction pattern:  
Cloudbot 提供三种不同的模式，每种模式都针对不同的交互模式进行了优化：

1. Create PR: Takes a Linear ticket and generates a full pull request with code changes.  
   创建 PR: 接收一个 Linear 任务单并生成包含代码变更的完整拉取请求。
2. Plan: Like Cursor's plan mode — generates an implementation plan and writes it back to the Linear ticket for human review before any code is written.  
   计划 : 类似 Cursor 的计划模式 — 生成实施计划并在编写任何代码之前将其写回 Linear 工单以供人工审核。
3. Explain: Debug mode — answers questions about why something isn't working, pulling context from MCPs (Datadog, Sentry, etc.) to diagnose issues.  
   Explain: 调试模式 — 回答关于某些事物为何无法正常工作的问题，从 MCPs（Datadog、Sentry 等）提取上下文以诊断问题。

When a PR is complete, Cloudbot responds in Slack with a link to the Cursor branch using Cursor's deep link format, plus a QR code so the engineer can scan it on their phone and immediately test a mobile build. This close-the-loop output design — from Slack invocation to mobile testing in one flow — reflects Coinbase's focus on compressing the entire feedback cycle.  
当 PR 完成时，Cloudbot 会在 Slack 中回应，提供指向 Cursor 分支的链接（使用 Cursor 的深度链接格式），并附带一个二维码，以便工程师可以在手机上扫描该二维码并立即测试移动构建。这种闭环输出设计（从 Slack 调用到移动测试的一站式流程）反映了 Coinbase 对压缩整个反馈周期的关注。

#### 5\. Testing and Validation: How Agents Prove Their Work 5. 测试与验证：代理如何证明其工作

The fifth decision is how you validate what the agent produces. This is where the three companies diverge most in philosophy, forming a spectrum from conservative to radical.  
第五个决策是如何验证智能体生成的内容。这是三家公司在理念上分歧最大的地方，形成了从保守到激进的一个光谱。

Stripe: Shift-Left, Max Two CI Runs  
Stripe：左移，最多两次 CI 运行

Stripe's testing strategy has three layers:  
Stripe 的测试策略有三个层次：

1. Local: Automated lint heuristics run within 5 seconds per git push via pre-push hooks with cached results. This catches the trivial stuff before it ever touches CI.  
   本地 : 自动代码检查启发式算法每次通过预推送钩子在 5 秒内运行，带有缓存结果。这在任何内容接触 CI 之前就捕获了琐碎的问题。
2. CI: Selective test execution drawn from over 3 million total tests. Many CI failures include autofixes that are automatically applied without human intervention.  
   CI: 从超过 300 万次总测试中选取的选择性测试执行。许多 CI 失败包含无需人工干预即可自动应用的自动修复。
3. Agent retry: If CI fails and there's no autofix, the agent gets one single additional attempt.  
   代理重试 ：如果 CI 失败且没有自动修复，代理会获得一次额外的尝试。

After that second CI run, if failures persist, it goes to human review. No third attempt, no retry loop. The philosophy is explicit: avoid diminishing returns from excessive LLM iteration. Every additional retry burns tokens and CI capacity with a declining probability of success. Better to hand it to a human than to let the agent spin.  
在第二次 CI 运行之后，如果失败仍然存在，将进入人工审核。不进行第三次尝试，没有重试循环。其理念明确：避免过度 LLM 迭代带来的边际收益递减。每一次额外的重试都会消耗 token 和 CI 容量，而成功概率却在下降。与其让代理继续空转，不如交给人工处理。

Ramp: Visual Verification  
Ramp: 视觉验证

Ramp's distinctive contribution to validation is visual verification via their Chrome extension. The extension is React-aware and operates on DOM trees rather than screenshots — more reliable for detecting actual UI state versus pixel-level appearance. Streamed desktop views let both the agent and human reviewers see the frontend output as it renders.  
Ramp 在验证方面的独特贡献是 视觉验证通过其 Chrome 扩展实现。该扩展支持 React，在 DOM 树而非截图上运行——相比像素级外观，更可靠地检测实际 UI 状态。流式桌面视图让代理和人工审核人员在前端输出渲染时即可查看。

This matters because a lot of agent-generated code can pass CI while producing visually broken output. Unit tests don't catch that a modal is rendering behind the page overlay or that a button is the right color but in the wrong position. DOM-based verification does.  
这一点很重要，因为很多代理生成的代码虽然能通过持续集成（CI），但会产生视觉上损坏的输出。单元测试无法发现模态框在页面覆盖层后面渲染，或者按钮颜色正确但位置错误的问题。而基于 DOM 的验证可以发现这些问题。

Coinbase: Agent Councils and Auto-Merge  
Coinbase：代理委员会与自动合并

Coinbase is the most aggressive of the three when they judge PRs to be low risk. Their approach has evolved rapidly.  
当他们认为拉取请求风险较低时，Coinbase 是三者中最积极的。他们的方法已经迅速发展。

Where they started: Average PR cycle time of roughly 150 hours, most of that in review queues. They built internal review tools and implemented auto-merge by risk — low-risk changes (copy, minor bug fixes) merge automatically, higher-risk changes go through review.  
他们的起点 : 平均 PR 周期时间约为 150 小时，其中大部分时间都在审核队列中。他们开发了内部审核工具并实施了按风险自动合并 ——低风险变更（复制、小 bug 修复）自动合并，高风险变更需经过审核。

Where they are now: PR cycle time down to roughly 15 hours. They use Greptile for automated code reviews and have introduced agent councils — groups of AI agents that do first-pass code review. According to Chintan Turakhia, these agent councils produce reviews that are "95%+ better than human" reviews.  
他们目前的情况：PR 周期时间缩短至约 15 小时。他们使用 Greptile 用于自动化代码审查，并引入了智能代理小组——这些 AI 代理小组会进行首轮代码审查。据 Chintan Turakhia 称，这些智能代理小组的审查质量比人工审查高出 95%以上。

Where they're going: The target is 15 hours down to 5 minutes. They're rethinking where reviews belong in the development cycle entirely — whether the traditional PR review model even makes sense when agents can validate at the point of creation rather than after the fact.  
他们的目标方向 : 目标从 15 小时缩短到 5 分钟。他们正在彻底重新思考评审在开发周期中的位置——当代理能够在创建时而非事后进行验证时，传统的 PR 评审模式是否还有意义。

The Spectrum  
频谱

These three approaches form a clear spectrum:  
这三种方法构成了一个清晰的光谱：

- Conservative (Stripe): Bounded retries, human review as the backstop, explicitly designed to avoid throwing compute at diminishing returns.  
  保守型 (Stripe): 有界重试，以人工审核作为后备，明确设计以避免将计算资源投入到边际收益递减的场景中。
- Moderate (Ramp): Automated visual verification augments human review but doesn't replace it.  
  中等 (Ramp): 自动化视觉验证增强人工审核，但不能替代它.
- Radical (Coinbase): Agent councils doing first-pass reviews, auto-merge by risk level, working toward removing human review from the critical path entirely.  
  Radical（Coinbase）：代理委员会进行首次审核，按风险等级自动合并，致力于完全从关键路径中消除人工审核。

Where you land on this spectrum depends on your risk tolerance, domain, and your engineers' own preferences.  
你在这个光谱上的定位取决于你的风险承受能力、领域以及工程师自身的偏好。

#### 6\. Invocation: How Engineers Access Agents 6. 调用：工程师如何访问代理

The sixth decision is the interface. How do your engineers actually talk to the agent?  
第六个决策是界面。你们的工程师实际上是如何与代理进行交互的？

Slack Is the Universal Layer  
Slack 是通用层

All three companies converge on Slack as the primary invocation surface. This isn't a coincidence.  
这三家公司都聚焦于 Slack 作为主要的调用界面。这并非偶然。

Stripe's agents are invoked most commonly through Slack, though they also support CLI, a web interface, and embedded buttons in internal systems (docs platform, feature flag UI, ticketing). Ramp offers Slack alongside a polished web interface with hosted VS Code and a Chrome extension. Coinbase's Cloudbot is Slack-native — it lives in Slack channels and is invoked via cloudbot &lt;command&gt;.  
Stripe 的代理最常通过 Slack 调用，不过它们也支持 CLI、Web 界面以及内部系统中的嵌入式按钮（文档平台、功能标志界面、工单系统）。Ramp 提供 Slack，同时还提供一个精心设计的 Web 界面、托管的 VS Code 以及 Chrome 扩展。Coinbase 的 Cloudbot 是 Slack 原生的——它存在于 Slack 频道中，并且通过 cloudbot &lt;命令&gt; 调用。

Chintan Turakhia articulated why Slack wins more clearly than anyone: the cost of writing something in Slack is zero, but the cost of answering something in Slack is enormous. Most of what flows through Slack is humans pretending to be systems — answering questions that could be automated, triaging requests that could be routed, summarizing context that could be assembled. An agent in Slack turns that dynamic inside out: the cost of answering drops to zero too.  
Chintan Turakhia 阐述了为什么 Slack 比任何人都更清晰地胜出：在 Slack 中写东西的成本是零，但在 Slack 中回复内容的成本却极高。Slack 中流通的大部分内容是人类在冒充系统——回答本可自动化的问题、对本可路由的请求进行分类、总结本可整合的背景信息。Slack 中的代理将这种动态彻底颠覆：回复的成本是回答也降至零。

There's a second reason, and it's about adoption: Slack is how things go viral within your company. If you hide the agent behind a separate tool, behind a new URL, behind a new login — it doesn't spread. When agent results show up in channels that everyone's already watching, people see what's possible without having to opt in.  
还有第二个原因，与用户接受度有关：Slack 是公司内部事物实现病毒式传播的方式。如果你把这个 agent 隐藏在一个单独的工具、一个新的网址和一个新的登录界面之后——它就不会传播开来。当 agent 的结果出现在每个人都在关注的频道中时，人们无需主动选择加入就能看到可能性。

Beyond Slack  
超越 Slack

The interesting divergence is in what each company builds beyond Slack.  
有趣的差异在于每家公司在 Slack 之外所构建的内容。

Stripe embeds invocation buttons directly into internal platforms. Their docs platform, feature flag UI, and ticketing system all have built-in "run a minion" buttons. This is the logical end state of Slack-first: once the agent proves useful, you push invocation to the point of need rather than making people context-switch to Slack.  
Stripe 直接将调用按钮嵌入内部平台。他们的文档平台、特性标志界面和工单系统都内置了“运行一个 minion”按钮。这是“以 Slack 为优先”的逻辑最终状态：一旦代理证明有用，你会将调用推送到需求点，而不是让人们切换到 Slack 进行上下文切换。

Ramp builds three distinct client surfaces, each optimized for different workflows. The web interface includes hosted VS Code integration and organization-wide analytics dashboards. The Chrome extension operates on DOM trees for visual verification. The Slack interface handles chat-based interaction with automatic repository classification and status updates via Block Kit. This also allows non-technical members of the team to adopt Inspect and use it right where they work like in the browser.  
RampRamp 构建了三个不同的客户端界面，每个都针对不同的工作流程进行了优化。网页界面包含托管的 VS Code 集成和全组织范围的分析仪表板。Chrome 扩展程序在 DOM 树上运行以进行视觉验证。Slack 界面通过 Block Kit 处理基于聊天的交互，包括自动代码仓库分类和状态更新。这还允许团队中的非技术成员采用 Inspect 并在他们工作的地方（例如浏览器中）直接使用它。

Coinbase keeps Slack as the center but adds creative output touches: when Cloudbot finishes a PR, it responds with both a Cursor deep link (so you can jump straight into the branch in your editor) and a QR code (so you can scan with your phone and immediately test a mobile build). Small details, but they close the loop from invocation to validation in a single flow.  
CoinbaseCoinbase 以 Slack 为核心，但增添了富有创意的输出细节：当 Cloudbot 完成一个 PR 时，它会回复一个 Cursor 深度链接（这样你就可以直接跳转到编辑器中的分支）和一个 QR 码（这样你可以用手机扫描并立即测试移动构建）。这些小细节在一个流程中完成了从调用到验证的闭环。

#### 7\. Adoption: Making It Stick 7. 采用：让它坚持

Building the agent is one thing. Getting a thousand engineers to actually use it is another.  
构建代理是一回事，让一千名工程师真正使用它是另一回事。

None of these companies forced adoption — they all let the product spread organically, but through different mechanisms.  
这些公司中没有一家强制采用——它们都让产品自然传播，但通过不同的机制。

Ramp: Let the Product Talk  
Ramp：让产品说话

Ramp's approach was explicit: "We didn't force anyone to use Inspect over their own tools. We built to people's needs, created virality loops through letting it work in public spaces, and let the product do the talking." Within a couple of months, \~30% of all pull requests merged to their frontend and backend repos were written by Inspect — and usage continues to grow. They track a real-time metric they call "humans prompting" (users who've sent a prompt in the last 5 minutes) as their adoption pulse. Ramp is also expanding beyond engineering, teaching non-engineering builders like product managers and designers how to use the agent for their own work.  
Ramp 的方法很明确：“我们没有强迫任何人放弃自己的工具而使用 Inspect。我们根据人们的需求进行构建，通过让产品在公共空间中发挥作用来创造病毒式传播循环，并让产品自己说话。” 几个月内， 约 30%合并到其前端和后端代码仓库的拉取请求是由 Inspect 生成的 — 并且使用量持续增长。他们追踪一个名为“人工提示”（过去 5 分钟内发送过提示的用户）的实时指标作为其采用脉搏。Ramp 还在工程领域之外拓展业务，向产品经理和设计师等非工程领域的从业者传授如何将该代理工具用于他们自己的工作。

Stripe: Make It Impossible to Avoid  
Stripe：让它无法避免

Stripe doesn't have a dedicated adoption playbook — they make the agent impossible to avoid. Invocation is embedded everywhere: the docs platform, the feature flag UI, the ticketing system all have built-in "run a minion" buttons. Rule files are synced across Minions, Cursor, and Claude Code, so institutional knowledge works the same regardless of tool. They've also built a no-code internal agent builder for non-engineering teams, spreading agent usage beyond the engineering org. The result: over 1,300 fully agent-produced PRs merged per week, with a fleet of hundreds of different agents running across the company.  
Stripe 没有专门的采用指南——他们让代理无法避免 。调用被嵌入到各个地方：文档平台、特性开关界面、工单系统都有内置的“运行一个 minion”按钮。规则文件在 Minions、Cursor 和 Claude Code 之间同步，因此组织知识在不同工具中都能一致使用。他们还构建了一个无代码内部代理构建器面向非工程团队，将代理的使用范围扩展到工程团队之外。结果是：超过 1,300 个完全由代理生成的 PR 每周被合并 ，公司内有数百个不同的代理在运行。

Coinbase: Social Proof at Scale  
Coinbase：规模化社会证明

Coinbase drove adoption through social proof and collective events across their 1,000+ engineer org. They created a Slack channel called "Cursor Wins and Losses" — the "losses" part turned it into a self-reinforcing learning loop where failures got fixed publicly. They ran PR speedruns — time-boxed events where everyone picks a trivial task and ships a PR. The first one produced 70 PRs in 15 minutes; a company-wide follow-up with 800 engineers produced 300-400 PRs in 30 minutes. They also invented a dedicated "Super Builder" role — someone whose full-time job is making everyone else faster with agents.  
Coinbase 通过社会认同和集体活动，在其 1000 多名工程师的组织中推动了产品采用。他们创建了一个名为“Cursor Wins and Losses”的 Slack 频道——其中的“失败”部分使其形成了一个自我强化的学习循环，失败在公开场合得到修复。他们举办了 PR 速跑活动——即限时活动，每个人选择一个小任务并提交 PR。第一次活动在 15 分钟内产出了 70 个 PR；全公司范围的后续活动（800 名工程师参与）在 30 分钟内产出了 300-400 个 PR。他们还创造了一个专门的“超级构建者”角色——其全职工作是通过代理让其他所有人更高效。

The Pattern  
这个模式

All three converge on the same lesson: don't mandate, demonstrate. Put the agent where people already work (Slack, internal tools), make results visible, and let adoption compound from there.  
这三点都指向同一个核心教训：不要强制推行，要示范引导。将工具部署在人们日常工作的地方（Slack、内部工具），让成果可视化，并让采用量从那里开始复利式增长。

If You're Starting Today  
如果你今天开始

1. Pick your agent harness wisely. Consider your requirements and what makes the most sense for your organization.  
   明智地选择你的代理工具。 考虑你的需求以及对你的组织最合理的选择。
2. Build an environment where agents can make mistakes without consequences. This is the single biggest unlock. Stripe's devboxes have no production access, no real user data, no network egress, so agents run with full permissions and zero confirmation prompts. Invest in isolation and pre-warming early; sandbox startup time is agent latency.  
   构建一个环境，让代理可以犯错而无需承担后果。 这是最大的单一突破口。Stripe 的开发环境没有生产环境访问权限，没有真实用户数据，没有网络出口，因此代理可以在完全权限下运行，且没有任何确认提示。进行隔离投资并尽早预热；沙箱启动时间就是代理延迟。
3. Curate tools, don't accumulate them. More tools = more confusion. Give each agent type a small, focused toolset.  
   精心挑选工具，不要堆积它们。工具越多，混乱越多。为每种代理类型提供一个小型、专注的工具集。
4. Pick your spot on the validation spectrum. Understand which parts of your codebase and PRs are high-risk vs. low-risk, then review accordingly. Don't be afraid to auto-merge the safe stuff and gate the dangerous stuff.  
   在验证范围中选择你的关注点。了解你的代码库和拉取请求中哪些部分是高风险与低风险，然后相应地进行审查。不要害怕自动合并安全的内容并对危险的内容设置关卡。
5. Let the agent work in public. Don't mandate usage, let agent results show up in Slack channels and shared spaces where people can see what's possible without opting in. Adoption follows visibility.  
   让代理公开工作。不要强制使用，让代理的结果出现在 Slack 频道和共享空间中，让人们无需主动选择加入就能看到有哪些可能性。采用取决于可见性。

## A结构化（1）

### 2026-03-18 10:02:04

这篇文章的核心观点是：顶级工程团队已经不满足于 “直接用现成 AI 编程工具”，而是开始为自己组织打造专属 coding agent。因为只有接入内部系统、具备合适权限和安全边界的 agent，才能真正稳定地产生业务价值。

- **背景：为什么越来越多公司自建 coding agent**
  - Stripe、Ramp、Coinbase 等公司都在做内部 agent，形态包括 Slack 机器人、CLI、Web 应用、Chrome 扩展，直接嵌入工程师现有工作流。
  - 这些 agent 不只服务工程师，产品、GTM 等非技术团队看到效果后，也开始在 Slack 中使用。
  - 文章强调：AI-native 工程组织不是未来式，而是已经发生。
  - 关键案例：
    - Stripe 每年处理超`1 万亿美元`支付，代码规模达`数亿行 Ruby`，其 agent 现在每周能产出`1300+`个已合并 PR。
    - Ramp 需要 agent 同时理解前端和后端，并能 “验证自己写的代码”。
    - Coinbase 因金融和加密安全要求，无法使用第三方后台 agent，把 PR 周期从`150 小时`压缩到`15 小时`，目标是`5 分钟`。

- **1. Agent Harness：先决定 agent 跑在什么框架里**
  - 这是第一步，主要有三种路线：`fork`、`组合已有框架`、`从零自建`。
  - Stripe 选择**fork**：基于 Block 开源的`goose`改造，保留 agent 循环，同时把 git、lint、测试等关键步骤做成确定性流程。
  - Ramp 选择**组合**：基于`OpenCode`搭建，因为它是 server-first 架构、带 typed SDK，且 agent 还能读取自己的源码来理解能力。
  - Coinbase 选择**从零构建**：做了自研、多模型的`Cloudbot`，不绑定单一模型供应商，主要是出于金融安全要求。
  - 取舍很明确：
    - `fork`：启动快，但会受上游设计影响。
    - `组合`：便于继承上游升级，但也会被框架思路绑定。
    - `自建`：控制力最强，但所有 bug 和维护成本都要自己扛。

- **2. Sandbox：agent 应该在哪里运行代码**
  - 三家公司都收敛到同一个结论：不要让 agent 在工程师本地随意执行代码，而要放进云端隔离环境。
  - **Stripe**
    - 用 AWS EC2 上的`devboxes`作为标准开发环境，来自预热池，`10 秒`可就绪。
    - 每个环境预装：预克隆代码仓库、Bazel 和类型检查缓存、代码生成服务、最新 master 分支。
    - 安全边界很严格：运行在 QA 环境、没有真实用户数据、不能访问生产服务、没有任意外网出口。
    - 因为隔离做得足够好，所以 agent 可以拿到充分权限，且无需频繁人工确认。
  - **Ramp**
    - 用`Modal`提供隔离容器，镜像和快照让仓库保持在`30 分钟`以内的新鲜度。
    - 为了速度，他们会在用户还在输入 prompt 时就预热 sandbox。
    - 还会提前读取部分文件、批量执行构建准备，并支持 agent 开子会话并行处理任务。
    - 结果是：会话启动快、几乎 “免费”，还能并发多个，不依赖本地电脑。
  - **Coinbase**
    - 因金融合规和加密基础设施安全要求，自建 sandbox。
    - 文章没公开实现细节，但强调：对这类公司来说，sandbox 不只是开发工具，而是合规边界。
  - 共同模式：
    - 先做隔离，再在边界内给足权限。
    - 如果只靠权限弹窗和人工审批来 “保安全”，agent 要么太慢、要么不够安全。

- **3. Tools 和 Context：agent 能看到什么、能做什么**
  - 文章认为，真正决定 agent 水平的，不只是模型能力，而是 “工具设计” 和 “上下文工程”。
  - **工具接入**
    - Stripe 有内部 MCP 服务`Toolshed`，接了近`500`个工具，覆盖内部系统和 SaaS。
    - 但重点不是工具多，而是 “精挑细选”：每个 agent 默认只拿到一小部分相关工具，并按主题分组，还支持按用户定制；同时限制破坏性操作。
    - Coinbase 更强调接入对调试真正有用的数据源：如`Datadog`、`Sentry`、`Amplitude`、内部`Snowflake`，还能跨多个代码库工作。
    - Ramp 则基于 OpenCode 自带工具系统扩展自家集成。
  - **核心观点：工具越多不一定越强**
    - 给 agent `500`个工具，不一定提升能力，反而会让它更困惑、浪费 token 在选工具上。
    - 更有效的方法是：按 agent 类型限制工具范围。
  - **上下文工程**
    - Stripe 用类似 Cursor 的 rule files，并按目录、文件模式自动生效；规则还能在`Minions`、`Cursor`、`Claude Code`三个平台同步。
    - 对于 Stripe 这种`数亿行代码`的系统，不同子目录规范差异很大，所以规则必须按目录动态挂载。
    - Stripe 还会在 agent 开始前做 “上下文预注入”：自动扫描 Slack 线程里的链接，拉 Jira、文档、Sourcegraph 搜索结果，以及相关 MCP 信息，让 agent 一开始就拿到整理好的背景材料。
    - Coinbase 把`Linear`作为单一上下文入口：人先把 bug、用户路径、附件整理进 Linear，再由 Cloudbot 从 Linear 出发拉更多 MCP 数据。
  - 结论：
    - 最重要的不是 “上下文越多越好”，而是 “恰到好处地把正确信息提前准备好”。
    - 好的上下文，能减少幻觉，提升 PR 质量。

- **4. Orchestration：agent 如何一步步完成任务**
  - 这一部分讨论的是：agent 从收到任务到产出 PR，中间的流程怎么设计。
  - **Stripe：Blueprints**
    - 这是文章最强调的架构创新：把确定性工作流和 agent 灵活性结合成状态机。
    - 分两类节点：
      - `确定性节点`：如跑 lint、格式化、push git、执行 pre-push hooks，这些必须做且不适合交给 LLM 凭记忆完成。
      - `agent 子任务节点`：如 “根据 ticket 实现功能”“修复 CI 失败”，在边界内让 LLM 自由发挥。
    - 优点是可组合：不同团队可定制自己的 blueprint，把部署规范、测试要求、review 标准固化进去。
    - 核心思想：把 LLM 放进更小、更清晰的盒子里，能显著提升稳定性，还能省 token、降 CI 成本。
  - **Ramp：Session 模型**
    - 以长生命周期 session 为核心，支持追问、停止、多轮协作。
    - 当用户补充 prompt 时，可选择排队或立即执行。
    - 还支持子 session，让 agent 并行拆任务。
    - 多人协作是关键能力：多名成员可共同参与一个 agent session，并保留各自贡献记录。
    - 典型场景：高级工程师带初级工程师做 agent-assisted 开发，或 reviewer 中途加入检查 agent 的过程。
  - **Coinbase：三种模式**
    - `Create PR`：从 Linear ticket 直接生成完整 PR。
    - `Plan`：先产出实现方案，写回 Linear，供人审核后再编码。
    - `Explain`：偏调试问答，结合 Datadog、Sentry 等上下文解释问题原因。
    - PR 完成后，Cloudbot 会在 Slack 返回 Cursor 分支 deep link，还给出二维码，方便工程师直接在手机上测试移动端构建。
    - 这说明 Coinbase 不只优化 “写代码”，而是在压缩从提需求到验证结果的整个反馈链路。

- **5. Testing 和 Validation：agent 如何证明自己写对了**
  - 这是三家公司分歧最大的地方，体现出不同的风险偏好。
  - **Stripe：前移校验，最多两次 CI**
    - 三层验证：
      - 本地：每次 git push 后，`5 秒`内通过 pre-push hooks 做 lint 和启发式检查。
      - CI：从`300 多万`测试中选择性执行；很多 CI 问题可自动修复。
      - agent 重试：如果 CI 失败且没有 autofix，只允许 agent 再试`1 次`。
    - 两次 CI 后仍失败，就交给人工，不允许无限 retry。
    - 理由很现实：继续让 LLM 反复试，token 和 CI 成本会越来越高，但成功率提升越来越小。
  - **Ramp：视觉验证**
    - 最大特色是用 Chrome 扩展做前端验证。
    - 它是`React-aware`的，并且基于`DOM`树而不是截图来判断页面状态，所以比纯像素比对更可靠。
    - 这能发现很多 CI 过了但 UI 实际坏掉的问题，比如弹窗层级错、按钮位置不对。
  - **Coinbase：按风险自动合并**
    - 文章给出的信息显示，Coinbase 在低风险 PR 上最激进。
    - 他们一开始面临的平均 PR 周期大约是`150 小时`，主要卡在 review 队列。
    - 后来建立了内部 review 工具，并按风险实施 auto-merge：
      - 低风险改动，如文案、小 bug，可自动合并。
      - 高风险改动仍需人工 review。
    - 文末这一部分被截断，但可以看出 Coinbase 的方向是：尽量让低风险修改脱离人工瓶颈。

- **文章的总体结论**
  - 真正有价值的 coding agent，不是一个 “会写代码的聊天机器人”，而是一个深度嵌入企业内部环境的系统工程。
  - 它的关键不在模型本身，而在 5 个设计决策：`harness`、`sandbox`、`tools/context`、`orchestration`、`testing/validation`。
  - 三家公司路线不同，但共识很强：
    - 用隔离环境保证安全；
    - 用精心筛选的工具和上下文提升质量；
    - 用确定性流程约束 LLM；
    - 用高效验证机制控制风险和成本。

## 解读（1）

### 2026-03-19 10:37:37

#### 总结

这篇文章的核心观点很明确：  
**与其纠结 “用哪个现成的 Agent Harness（代理框架）”，不如尽快为自己的组织打造一套 “贴合内部系统、安全要求和工作流” 的编码代理。**

文中用 Stripe、Ramp、Coinbase 三家公司说明了一个趋势：

- 顶级工程团队已经不再把 AI 只当 “聊天助手”，而是把它做成真正能干活的内部编码代理
- 这些代理不是孤立工具，而是直接嵌入 Slack、CLI、Web、Chrome 扩展等日常工作入口
- 真正让代理有价值的，不只是模型能力，而是：
  - 能接入内部系统
  - 拥有合适权限
  - 运行在安全沙箱里
  - 拿到高质量上下文
  - 配合确定性的工程流程执行任务

一句话概括：  
**未来比拼的重点，不是谁接了一个 AI 模型，而是谁把 AI 代理真正接进了自己的组织能力。**

#### 解读

##### 1. “代理框架” 不是重点，重点是 “是否适合你们组织”

文章先讲了三种路线：

- **Stripe：分叉开源项目**
  - 好处：起步快
  - 坏处：会被上游设计牵着走

- **Ramp：基于现有框架二次组合**
  - 好处：容易继承上游升级
  - 坏处：仍然受限于底层框架的思路

- **Coinbase：从零自研**
  - 好处：完全可控，尤其适合强安全场景
  - 坏处：最贵、最难、最重

通俗讲，就是三种选择：

- 想快：借别人的底子改
- 想平衡：站在别人的平台上扩
- 想绝对掌控：自己造

所以文章标题才说 “别老讨论 harness 了”。  
**框架只是起点，不是壁垒。真正的壁垒是你们自己的业务上下文、权限体系和流程编排。**

---

##### 2. 真正让代理安全可用的，不是 “反复审批”，而是 “先隔离再放权”

这是全文很关键的一点。

很多团队一想到 AI 代理会写代码、跑命令，就本能地想：  
“那我多加几层审批、多弹几个确认框，不就安全了吗？”

文章的判断是否定的：  
**靠审批堆安全，最后往往会得到一个 “既慢又不好用” 的代理。**

三家公司虽然实现方式不同，但共同原则一致：

- 把代理放进云端沙箱里运行
- 先把边界隔离清楚
- 在边界内给足权限
- 这样代理才能高速执行，又不会把风险扩散出去

这很像现实中的工厂管理：

- 不是让工人每拧一个螺丝都打申请
- 而是先把危险区域、权限范围、操作环境设计好
- 然后让他在可控范围内高效工作

所以，**沙箱不是 “附属功能”，而是代理系统的安全底座。**

---

##### 3. 决定代理水平高低的，往往不是模型，而是 “工具和上下文”

文章反复强调一个事实：  
**代理能不能产出靠谱 PR，关键看它看到了什么、能调用什么。**

###### 工具方面
不是工具越多越好。

Stripe 虽然有接近 500 个工具，但并不是全给代理。  
它的做法是：

- 默认只给一小部分精选工具
- 按角色、主题、用户进行定制
- 对危险操作做限制

这背后的意思很重要：  
**工具太多，代理反而容易迷糊、浪费 token、降低效率。**

###### 上下文方面
这部分更关键。

- Stripe 会提前把 Slack 线程、Jira、文档、代码搜索结果先整理好，再喂给代理
- Coinbase 则把 Linear 当成统一上下文入口，先让人把问题整理进去，再让代理去消费和扩展

说白了，代理不是 “凭空变聪明” 的。  
它更像一个新来的高水平同事：  
**你给的信息越清楚、越结构化，它干活就越稳。**

所以文章实际上在提醒：  
**不要只盯着模型参数，要重视 “上下文工程”。**

---

##### 4. 最高级的做法，不是 “全自动自由发挥”，而是 “确定性流程 + 代理灵活性” 结合

Stripe 的 Blueprint 很值得注意。

它不是让 LLM 全程自由发挥，而是把任务拆成两类节点：

- **确定性节点**：格式化、lint、git push、pre-push hooks 这类机械但必须做的事
- **代理节点**：实现需求、修复 CI、分析问题这类需要推理和创造的事

这其实非常符合工程现实：

- 机器擅长死板重复的步骤，就让程序写死
- LLM 擅长模糊问题求解，就让它在有限范围内发挥

这比 “全靠 Agent 自己想” 靠谱得多。  
因为真正稳定的系统，不是把希望寄托在模型每次都完美，而是把**该固定的固定住，该灵活的交给代理。**

#### 我的意见

我认同这篇文章的判断，而且我觉得它点中了很多团队的误区。

- **对大多数公司来说，最该思考的不是 “选哪个 AI 编码工具”，而是 “怎么把 AI 接进自己的内部环境”**
- **真正的竞争力不会来自模型本身，而来自组织内部的数据、流程、权限和安全设计**
- **如果没有沙箱、上下文和工具治理，再强的模型也很难稳定产出**
- **如果一上来就追求完全自研，成本可能过高；更现实的路径通常是 “先基于现有框架搭起来，再逐步替换核心能力”**

我的建议是：

1. **中小团队**：先别急着从零造，优先验证 “代理是否能接入你们的真实工作流”
2. **中大型团队**：尽快建设统一的上下文入口、工具接口和隔离执行环境
3. **强监管行业**：应优先考虑安全边界、审计和合规，再谈代理自主性

最后一句：  
**AI 编码代理的价值，不在于它像不像一个会写代码的聊天机器人，而在于它能不能成为你组织里的 “数字工程同事”。**

## 产品-产品技术PMF（1）

### 2026-03-19 10:38:27

这篇文章的核心观点很清晰：对于中大型、工程复杂度高、合规要求强、内部系统密集的组织来说，“自建内部编码代理” 正在从实验性工具，变成新一代工程生产力基础设施。它不是在替代 IDE，而是在重构 “需求进入工程系统后，如何被上下文理解、执行、验证、提交” 的整个流程。

**核心判断**
- 这不是一篇在谈 “做不做 AI Coding” 的文章，而是在谈 “谁来掌握你组织里的 AI 执行权”。
- 文章真正要传递的不是 Harness 选型，而是一个更高层判断：编码代理的竞争壁垒不在模型本身，而在`上下文接入能力`、`安全边界设计`、`工作流编排`与`组织落地能力`。
- Stripe、Ramp、Coinbase 三家案例共同说明：只要组织复杂度足够高，通用 Copilot 的边际价值会迅速下降，而 “深度接入内部系统的专属代理” 价值会迅速上升。
- 从 PMF 角度看，这类产品的 first wedge 不是 “帮工程师写代码”，而是 “缩短任务到 PR 的闭环时间，并在安全边界内减少人工协调成本”。

**一、产品分析**
- 产品本质：内部编码代理并非单点工具，而是 “工程任务执行层”。它连接 Slack/CLI/Web/Chrome Extension，只是为了嵌入现有工作流，降低采用门槛。
- 用户价值：对工程师，它提供的是 “带上下文的自动执行”；对 PM、GTM、运营等非技术角色，它提供的是 “把需求翻译成可执行工程动作” 的能力。
- 真正的产品形态：不是聊天机器人，而是`任务入口 + 上下文装配 + 安全执行 + 验证反馈 + PR 产出`的一体化闭环。
- 文章强调的产品设计理念很对：代理必须 “出现在用户已经工作的地方”。这说明交互层不是主战场，主战场是后端执行系统。
- 最强产品信号：从工程团队外溢到 PM/GTM 等角色，说明产品开始从 “效率工具” 升级为 “组织接口”。

**二、目标用户与场景拆解**
- 最适合的组织：多代码仓、多内部系统、多规则、多审批链、高合规行业、开发流程标准化程度较高的公司。
- 最强使用场景：Bug 修复、例行重构、跨系统排障、小需求实现、CI 修复、代码迁移、变更验证、文档到实现。
- 次级扩展场景：从 Slack 中接 Jira/Linear 任务，一键生成 investigation、修复 PR、回归验证结果与风险说明。
- 非工程用户场景也很有潜力：PM 可以发起 “基于 ticket 生成技术方案和初始 PR”，客服 / 运营可触发 “用户问题定位与修复建议”。

**三、PMF 分析**
- 痛点强度极高：当前工程组织最大的损耗不只是写代码，而是找上下文、拼权限、跑验证、协调系统、来回切换。
- 频次足够高：需求拆解、bug 修复、代码检查、PR 处理是日常高频动作，天然适合代理持续使用。
- ROI 明确：文章里 Stripe 的每周 merged PR 数、Coinbase 的 PR 周期压缩，都是非常强的 PMF 证据。
- 替代路径弱：第三方通用 Agent 很难获得企业内部系统上下文、权限模型与安全边界，因此在这类组织里很难成为最终解。
- 采用门槛可控：如果以 Slack/CLI 切入，不要求用户改变行为习惯，内部落地速度会明显快于新平台式产品。
- PMF 的关键不在 “模型多强”，而在 “是否能把组织知识变成结构化上下文，并让代理稳定执行”。

**四、文章里最有价值的产品洞察**
- `Harness 不是重点，执行控制才是重点`：Fork、Compose、Build from scratch 本质是控制权与迭代速度的权衡。
- `Sandbox 不是基础设施细节，而是产品成立前提`：如果没有隔离，代理就必须不断请求审批；一旦不断请求审批，体验就崩。
- `工具越多不一定越强，工具编排和裁剪更重要`：500 个工具不是壁垒，正确的工具集合和权限边界才是壁垒。
- `Context engineering 是第一性原理`：不是让 Agent 自己 “探索世界”，而是在人类和系统层先把上下文预装好。
- `Workflow + Agent 的混合架构是现实最优解`：纯 Agent 不稳定，纯 Workflow 不灵活，Blueprint 式状态机是更成熟方向。

**五、技术架构分析**
- 理想架构分四层：交互入口层（Slack/CLI/Web）、上下文层（Linear/Jira/Docs/Code Search/MCP）、执行层（Sandbox + Agent Runtime）、编排层（Blueprint/State Machine）。
- 这类系统的核心不应只依赖 LLM loop，而应采用`Deterministic Orchestration + Agentic Subtasks`混合架构。
- Sandbox 是执行可信度的基础。只有将风险收敛到隔离环境中，才能换取 “边界内全权限” 的高效体验。
- Context 侧应优先建设统一任务源，如 Linear/Jira，避免代理直接在杂乱信息源中自主搜索，导致 token 浪费和误判。
- Tooling 侧应该采用 MCP / 内部 API 网关 / 技能系统，工具必须有权限分级、审计日志、结果结构化输出。
- 多模型架构值得采用，但不是第一优先级；第一优先级是让任务可验证、可追溯、可回滚。

**六、三家公司策略对比**
- Stripe：偏 “工程体系化能力”。优势在规则、上下文预加载、Blueprint 编排、标准化 devbox，适合超大规模代码库。
- Ramp：偏 “速度与体验优化”。优势在预热、并发、多入口、多会话，适合高效率导向、执行速度极敏感的团队。
- Coinbase：偏 “安全与合规驱动”。优势在全链路自建、边界可控、多模型可替换，适合监管强、数据敏感业务。
- 这三家并不是不同答案，而是同一道题的三种最优解：`组织约束决定产品形态`。

**七、商业与竞争分析**
- 如果你是企业买方，这篇文章在传达一个趋势：未来的护城河不只是雇佣优秀工程师，而是拥有 “组织专属代理系统”。
- 如果你是创业者，这里的机会并不在做又一个 IDE Copilot，而在做 “企业内生代理平台” 的关键基础层。
- 更有机会的创业切口：
- `Agent Sandbox Infra`：安全隔离、预热、快照、缓存、低延迟会话。
- `Context OS`：将 Jira/Linear/Docs/Code/Search/Logs/Data 统一成代理可消费上下文。
- `Agent Orchestration Layer`：Blueprint、状态机、验证链、自动重试、任务分发。
- `Enterprise Tool Gateway`：带权限模型、审计和结构化结果的 MCP/Skills 平台。
- 巨头风险很高：模型厂商和 DevTools 平台最终都会往这个方向走，所以独立创业必须切在深水区能力，而不是聊天外壳。

**八、落地难点与风险**
- 最大风险不是模型效果，而是上下文脏乱差。没有结构化 ticket、文档和规则，代理很快变成幻觉放大器。
- 第二大风险是安全设计做反了：如果靠审批流来补安全，而不是靠隔离来换效率，系统会 “安全但无用”。
- 第三大风险是组织阻力。工程、平台、安全、法务、IT 需要共同推进，单点团队难以完成。
- 第四大风险是评估体系不成熟。仅看代码通过率不够，还要看修复准确率、回归率、人工介入率、PR 周期缩短比例。
- 第五大风险是工具泛滥。接太多工具会让代理选择成本升高、误调用变多、维护复杂度爆炸。

**九、PMF 成立的必要条件**
- 有稳定高频的软件交付任务流。
- 有足够标准化的代码仓、测试、CI、规则体系。
- 有可被代理调用的内部 API、文档、工单、日志、代码搜索能力。
- 有安全隔离环境，允许代理在边界内执行较高权限操作。
- 管理层接受 “先从特定场景局部自动化，再逐步扩权” 的推进方式。

**十、建议的产品落地路线**
- 第一阶段：只做`Ticket -> Context Assembly -> Code Change -> PR`闭环，聚焦 bug fix 和小型任务。
- 第二阶段：引入 deterministic workflow，把 lint、test、format、CI fix、PR 描述生成固化。
- 第三阶段：接入 observability、数据平台、内部文档与代码搜索，增强排障和跨系统修改能力。
- 第四阶段：从工程扩展到 PM、Support、GTM，让非技术角色也能触发受控的工程执行。
- 第五阶段：建设团队级 Blueprint/Rule System，让不同团队把自己的规范沉淀为可执行资产。

**十一、如果把这篇文章提炼成一句结论**
- 企业级编码代理的真正壁垒，不是模型，而是`在安全边界内，把组织上下文、工具系统与工程流程编排成一个可稳定产出 PR 的执行系统`。

**精炼结论**
- 这是一个明确成立的新范式，不是短期热点。
- 自建编码代理最适合复杂、高合规、高上下文密度的组织。
- PMF 已经在头部公司被验证，核心价值是缩短交付闭环、降低协调成本、释放非工程角色的执行能力。
- 技术上最关键的不是大模型，而是沙箱、上下文工程、工具裁剪与工作流编排。
- 商业上最大的机会在企业代理基础设施层，而不是通用 coding assistant 外壳。
