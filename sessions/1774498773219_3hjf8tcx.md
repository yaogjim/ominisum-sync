## 正文

**Magnus Müller**

### How we built the best browser agent with Karpathy's Auto-Research

#### How Auto-Research for browser agents works

We give Claude Code a CLI to our eval platform and a prompt to run in a loop:

![Image](https://pbs.twimg.com/media/HER9k85bYAMpx9w?format=jpg&name=large)

No orchestration code. Each Claude Code session gets a goal and runs 20 cycles on its own. With this

[eval infra](https://browser-use.com/posts/our-browser-agent-evaluation-system) we run them in parallel and get a search tree over the space of possible best agents.

![Image](https://pbs.twimg.com/media/HER9rB5bYAETlPD?format=jpg&name=large)

We don't care about low performers. We only care about getting the best agent. So we tell the coding agent to make big bets and avoid small changes, since small tweaks get lost in run-to-run variance.

#### The heart of the cycle: The debugging CLI

One trace can be millions of tokens. That's why we designed the CLI in 3 hierarchical levels to let the agent find root causes as fast as possible.

![Image](https://pbs.twimg.com/media/HER9x96bYAISKfT?format=jpg&name=large)

TSV over JSON saves 40% of tokens for our data structure. Small format choices can make or break agentic debugging.

![Image](https://pbs.twimg.com/media/HER91cxbYAQgxvb?format=jpg&name=large)

#### Tooling

The parallel Claude Code sessions run in

[Superset](https://superset.sh). The evals run in GitHub Action Runners with the git branch of the experiment and our

[stealth browser infrastructure](https://browser-use.com/posts/stealth-benchmark)

. For observability we use

[Laminar](https://laminar.sh/)

with Agent SDK as judge.

#### The biggest improvement

Claude Code updated our browser agent harness into a coding agent. Instead of only tools like click and type, it added Python to parse HTML and extract data. This aligns much better with the LLM's training distribution and makes edge cases and data extraction dramatically easier.

The rest: fixing hundreds of edge cases with the loop.

#### The Benchmark

Online-Mind2Web is the most widely reported browser agent benchmark. 300 tasks across 136 real websites - shopping, finance, travel, government, and more. Every web agent is tested on it.

#### The judge matters

The original judge is screenshot-based. But browser agents now write code, call APIs and extract thousands of items. For traditional judges, that's hallucination. If your agentic capabilities increase, you need an agentic judge.

We built an agentic judge on the Claude Agent SDK. We aligned it with human judges, which was key to making the auto-research loop work.

#### Are we overfitting?

The natural tendency of the auto-research loop is to overfit on single tasks. You need to prompt the research system hard to generalize. Most of my time merging cycles is rejecting task-specific solutions that overfit.

We use train/validation splits. The loop only sees training data. We then run on old datasets it has never seen and see score improvements across the board.

#### No tasks removed

Many companies remove tasks they consider impossible before reporting their score. We use all 300 tasks. Our few failures come from unavailable sites, ambiguous prompts, or websites that changed since the benchmark was created.

#### The Leaderboard

The Auto-Research approach maxed out the benchmark:

![Image](https://pbs.twimg.com/media/HER-lOCbYAId8N_?format=jpg&name=large)

#### Rerunning our results is easy

Clone

[github.com/browser-use/online-mind2web](https://github.com/browser-use/online-mind2web), set your Browser Use API key, and run.

We also uploaded prompts, results, and judgments.

#### We need harder benchmarks

We're building a benchmark with everything users actually care about. Currently benchmarks ignore tasks like: "Extract 1000 products with subpages and compare them across platforms" because it was unimaginable that a single browser agent could do this.

Stay tuned.

[Original post](https://browser-use.com/posts/online-mind2web-benchmark)

[Try the best web agent yourself](https://cloud.browser-use.com/)

## 通俗精炼（1）

### 2026-03-26 04:16:10

#### 用通俗的话总结：他们是怎么做出“最强浏览器 Agent”的

##### 一、核心方法：让 AI 自己反复做实验
这套方法本质上是“自动研究（Auto-Research）”。

他们没有写复杂的调度系统，而是给 Claude Code 一个评测平台的命令行工具和目标，让它自己循环跑 20 轮。  
再把很多这样的实验并行运行，就像同时探索很多条可能路径，最后只挑表现最好的方案。

**重点不是平均水平，而是找到最优解。**  
所以他们刻意鼓励 AI 做“大改动、大尝试”，而不是做一些容易被随机波动淹没的小优化。

##### 二、关键突破：调试工具设计得非常适合 AI
浏览器 Agent 的一次运行日志可能非常长，甚至达到几百万 token。  
所以他们专门设计了一个 **分 3 层的调试 CLI**，帮助 AI 更快定位根因，而不是在海量信息里迷路。

文章还提到一个很实用的细节：  
**用 TSV 替代 JSON，可以节省 40% token。**

这说明在 Agent 场景里，工具和数据格式这些“看起来不起眼”的工程细节，实际上会极大影响效果。

##### 三、真正的能力提升：从“浏览器操作员”升级成“会写代码的 Agent”
之前的浏览器 Agent，更多只是会点按钮、输入文字。  
而他们把 Claude Code 的能力接进来后，Agent 不只是“操作网页”，还可以：

- 写 Python
- 解析 HTML
- 抽取结构化数据
- 处理复杂边界情况

这一步很关键，因为它让 Agent 的工作方式更接近大模型原本擅长的任务分布。  
简单说：**不是只会“点网页”，而是能像工程师一样理解网页、处理数据。**

##### 四、评测标准也要升级：强 Agent 需要强 Judge
他们使用的是浏览器 Agent 领域常见的基准测试 **Online-Mind2Web**，包含 300 个真实网站任务。

但他们认为，原来的评测方式已经落后了。  
因为传统 Judge 主要看截图，而现在 Agent 已经会写代码、调 API、批量抽数据了，旧 Judge 很容易把真实能力误判成“幻觉”。

所以他们专门做了一个 **Agentic Judge（智能评审）**，并且让它尽量和人工评审对齐。  
这是整个自动研究循环能够有效运行的基础。

##### 五、最大风险：容易过拟合，但他们做了控制
这种自动循环系统天然容易针对单个任务“刷分”，也就是过拟合。

他们的应对方式包括：

- 强调要做可泛化的方案，而不是任务特化技巧
- 使用训练集 / 验证集划分
- 只让循环看到训练数据
- 再去旧数据集上做泛化验证

作者还提到，自己大量时间都花在**拒绝那些只对单题有效、但不具备普适性的方案**上。

##### 六、结果与意义：不靠删题，直接把榜单打满
他们强调自己没有像一些团队那样提前删掉“太难任务”，而是完整跑了全部 300 个任务。  
剩下少量失败，主要是因为：

- 网站失效
- 任务描述本身有歧义
- 基准创建后网站已经变化

最终，这套 Auto-Research 方法把这个 benchmark 基本做到了上限。

##### 七、文章背后的更大启发
这篇文章真正重要的，不只是“他们拿了第一”，而是说明了一个趋势：

**未来做 AI Agent，不只是拼模型，而是拼完整研究系统。**

包括：

- 如何让 Agent 自主迭代
- 如何设计适合 AI 的调试工具
- 如何构建合理的评测体系
- 如何防止过拟合
- 如何把“会操作”升级成“会编程、会分析、会抽取”

换句话说，**Agent 的竞争，正在从“单点能力”转向“系统化进化能力”。**

##### 一句话总结
他们做出顶级浏览器 Agent 的关键，不是某个单独技巧，而是搭建了一套让 AI 能自己反复实验、调试、评测和进化的“自动研究系统”，再配合更强的工具和评审机制，把浏览器 Agent 从“点网页”推进到“像工程师一样解决网页任务”。

## 结构化（1）

### 2026-03-26 07:24:49

#### 文章主旨

这篇文章介绍了他们如何用类似 Karpathy 提倡的“Auto-Research”方法，自动迭代优化浏览器智能体，并最终把成绩做到基准测试的顶尖水平。核心思路是：让多个 Claude Code 会话并行做“大步尝试”，再靠评测、调试工具和更合适的裁判系统，快速筛出最强方案。

##### 1. Auto-Research 的基本做法：让智能体自己循环改进

- 他们给 Claude Code 提供了一个可操作评测平台的 CLI，再配一个循环执行的提示词。
- 不写复杂的编排代码：每个 Claude Code 会话只拿到一个目标，然后**独立运行 20 个 cycle（循环）**。
- 这些会话会被并行跑起来，因此能形成一个“搜索树”，在大量可能方案里寻找最优浏览器智能体。
- 他们**不在意中等表现的方案**，只关注“最好的那个”，所以会明确要求智能体：
  - 少做小修小补
  - 多做高风险但可能高收益的“大改动”
- 原因很实际：小改动的效果，容易被每次运行时的随机波动淹没。

##### 2. 调试是核心：用分层 CLI 快速定位问题

- 文章强调，整个循环的“心脏”是调试 CLI。
- 因为一次运行轨迹（trace）可能有**数百万 token**，如果直接全量看，成本和效率都很差。
- 所以他们把 CLI 设计成了**3 层层级结构**，让智能体能从高层到低层逐步定位根因，加快排错速度。
- 一个很关键但容易被忽视的优化是：**用 TSV 代替 JSON** 存储他们的数据结构，能节省约 **40% 的 token**。
- 这说明在 agent 调试场景里，数据格式这种“小设计”也可能直接影响系统效果。

##### 3. 工具链怎么搭：并行实验、评测执行和可观测性

- 并行运行的 Claude Code 会话部署在 **Superset**。
- 评测运行在 **GitHub Action Runners** 上，并结合实验对应的 git 分支和他们的隐身浏览器基础设施。
- 可观测性部分使用 **Laminar**，并通过 **Agent SDK** 充当 judge（裁判）。
- 这套组合的作用很明确：
  - 大规模并行跑实验
  - 保证每次实验代码版本可追踪
  - 能系统化记录结果、判断优劣

##### 4. 最大提升来自哪里：把浏览器 agent 升级成 coding agent

- 他们提到，**最大的改进**来自 Claude Code 对浏览器 agent harness 的改造：
  - 过去浏览器 agent 主要只有 `click`、`type` 这类操作工具
  - 现在额外加入了 **Python**
- 这意味着智能体不只是“机械点网页”，还可以：
  - 解析 HTML
  - 提取结构化数据
  - 更灵活处理边缘情况
- 作者认为，这更符合大语言模型的训练分布，因此在：
  - 数据提取
  - 复杂页面处理
  - 异常情况兜底  
  上都有显著提升。
- 除此之外，剩下的大量进步主要来自持续循环中**修掉数百个边缘 case**。

##### 5. 他们用什么基准：Online-Mind2Web

- 他们使用的是 **Online-Mind2Web**，这是当前浏览器智能体领域里**最常被报告**的基准之一。
- 这个基准包含：
  - **300 个任务**
  - 横跨 **136 个真实网站**
- 任务场景覆盖很多常见类别，例如：
  - 购物
  - 金融
  - 旅游
  - 政务
- 文章里还提到，几乎所有网页智能体都会在这个基准上测试，因此它具有较强的行业可比性。

##### 6. 为什么“裁判”很重要：传统 judge 已经不够用了

- 原始 judge 是**基于截图**来判断结果的。
- 但现在的浏览器 agent 已经不只是点网页了，它还能：
  - 写代码
  - 调 API
  - 提取上千条数据
- 对传统 judge 来说，这些复杂能力很容易被误判成“幻觉”或无效行为。
- 所以作者提出一个关键观点：**如果 agent 能力升级了，judge 也必须升级成 agentic judge。**
- 他们基于 **Claude Agent SDK** 做了一个新的 agentic judge，并让它和人工评判标准对齐。
- 这一步非常关键，因为如果 judge 不准，整个 auto-research 循环就会被错误反馈带偏。

##### 7. 如何避免过拟合：不是把单题刷高分就算成功

- 文章坦言，auto-research 循环很容易出现一个问题：**对单个任务过拟合**。
- 也就是说，系统可能学会了“只会做这题”，但并不能真正泛化到别的网站和任务。
- 为了防止这一点，他们会在提示词层面强力要求系统追求泛化。
- 作者还提到，自己在合并 cycle 结果时，很多时间都花在**拒绝那些只对特定任务有效的方案**上。
- 他们采用了标准做法：
  - 使用 **train/validation split**
  - 循环过程中只看训练集
  - 再去旧数据集和从未见过的数据上做验证
- 结果是：他们观察到分数是在多个数据集上**整体提升**，而不是只在局部任务上变强。

##### 8. 结果呈现方式：不删题，完整跑 300 题

- 他们特别强调：**没有删任务**。
- 因为有些公司在汇报成绩前，会先去掉自己认为“不可能完成”的任务。
- 但他们选择保留基准中的**全部 300 个任务**。
- 剩下少数失败案例，主要来自这几类原因：
  - 网站不可用
  - 提示本身有歧义
  - 基准建立后，网站页面已经发生变化
- 这种做法的意义在于：成绩更完整，也更有说服力。

##### 9. 最终结论与下一步：现有基准快被做满了，需要更难的新 benchmark

- 文章表示，这套 Auto-Research 方法已经把当前 benchmark 基本“打满”了。
- 他们还强调结果**容易复现**：
  - clone `github.com/browser-use/online-mind2web`
  - 设置 Browser Use API key
  - 运行即可
- 同时，他们还上传了：
  - prompts
  - results
  - judgments
- 不过作者认为，现有 benchmark 已经不够难，无法反映用户真正关心的复杂任务。
- 例如，现实中更有价值的任务可能是：
  - **抓取 1000 个商品**
  - 进入子页面收集详情
  - 再跨平台做比较
- 这种任务过去几乎没人把它纳入 benchmark，因为当时大家难以想象单个浏览器 agent 能完成。
- 所以他们正在构建一个**更贴近真实用户需求的新基准**。

##### 总结

- 这篇文章的重点，不只是“模型更强了”，而是展示了一套完整的方法论：**并行自动研究 + 高效调试 + 合适裁判 + 泛化控制**。
- 其中最值得注意的细节包括：
  - 每个会话独立跑 **20 个 cycle**
  - 调试轨迹可达**数百万 token**
  - 用 **TSV 替代 JSON** 节省约 **40% token**
  - 基准为 **300 个任务、136 个网站**
- 用通俗的话说，他们不是靠一次大突破取胜，而是靠一套能不断“自己试、自己判、自己改”的研究流水线，把浏览器智能体一步步磨到了当前最强水平。
