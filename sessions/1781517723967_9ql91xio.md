## 分析要点

- **核心高价值点**：将 Prompt、Context、Harness、Loop 分别对应输入、信息、执行边界和持续运行控制，形成了较清晰的 Agent Runtime 分层理解框架。
- **留存建议**：短期参考后可保留为概念框架素材（文章提供了从 Prompt、Context、Harness 到 Loop 的分层框架，可作为理解 Agent 工程化演进的概念参考。）
- **不足**：内容偏概念化和重复，缺少真实案例、数据验证和具体实现细节，不建议作为高优先级精读材料。

**知识要点**

- Prompt Engineering 主要解决单次模型调用中的输入表达问题，但不能替代上下文、工具权限和运行控制。
- Context Engineering 的核心不是堆砌资料，而是提供相关、干净、可追溯的工作现场信息。
- Harness Engineering 关注工具权限、参数校验、日志、失败处理和人工确认等执行边界。
- Loop Engineering 解决 Agent 如何持续计划、行动、观察、修复、停止和回滚的问题。
- Agent 系统的风险来自概率模型参与自动化执行，因此必须设计评估、成本限制、退出条件和人工介入机制。

**行动项**

- 在设计 Agent 应用时，按 Prompt、Context、Harness、Loop 四层检查系统完整性。
- 为工具调用增加权限边界、参数校验、日志记录和失败回传机制。
- 为长任务 Agent 明确最大重试次数、成本上限、停止条件和人工接管条件。
- 评估现有 AI 工作流是否只是 Prompt 调用，还是具备可追踪、可验证、可恢复的运行时控制层。

## 正文

**关木**

### 从 Prompt 到 loop：AI 工程正在走向 Runtime

过去一年，AI 工程最大的变化，不是 prompt 越写越长，也不是模型回答越来越聪明。

真正的变化是：AI 在系统里的位置变了。

过去，AI 更像一个被人调用的函数。

你输入 prompt，它返回 answer。

输出 = 模型(提示)

人是主程序。 AI 是工具函数。

人决定问什么。 人判断对不对。 人决定下一步。 人负责停止。

但现在，Agent 正在改变这个结构。

AI 不再只是被动回答，它开始读取上下文、调用工具、观察结果、修正错误，并在一个目标下持续运行。

这意味着，AI 正在从一个被调用的函数，走向一个被运行的系统。

更准确地说，不是模型自己变成了 Runtime，而是模型正在被装进 Agent Runtime。

这里的 Runtime，不是指模型本身，而是围绕模型构建的一整套运行环境：上下文、工具、权限、状态、日志、评估、失败恢复和停止条件。

模型仍然是核心能力，但真正决定系统稳定性的，越来越不是模型本身，而是模型外面的控制层。

这也是为什么我们会看到一堆新的工程概念：

提示工程 上下文工程 代理线束工程 Loop Engineering

它们不是散乱的新词。

它们是在回答同一个问题：

如何把一个概率模型，包装成一个可控的执行系统？

#### 一、Prompt：解决输入问题

最早的 AI 应用，本质就是一次函数调用。

输出 = 模型(提示)

这个阶段，AI 是能力接口。

它可以写文章、解释概念、生成代码、总结材料、翻译文本。

但它不会自己决定下一步，也不会自己检查结果，更不会自己持续推进任务。

所以这个阶段最重要的是 Prompt Engineering。

因为 prompt 就是函数参数。

参数越清楚，返回结果越接近预期。

这也是为什么早期大家关注：

怎么设定角色？ 怎么描述任务？ 怎么给示例？ 怎么限制格式？ 怎么让输出稳定？

这些问题当然重要。

但它们只解决了 AI 工程的第一层问题：输入问题。

Prompt 再好，也不能替代上下文、工具权限、执行验证和停止条件。

所以 Prompt 没有过时。

只是它从“全部能力”，变成了“底层能力”。

#### 二、Context：解决信息问题

后来大家发现，prompt 写得再好，如果上下文是错的，结果还是错的。

让 AI 修代码，但不给它完整代码结构，它只能猜。 让 AI 分析业务，但不给它真实规则和数据，它只能编。 让 AI 写方案，但不给它约束条件，它只能输出一份看起来正确的废话。

所以 AI 应用从：

输出 = 模型(提示)

变成了：

输出 = 模型(提示词, 上下文)

AI 不再只是需要一句指令，它需要一个工作现场。

这个现场里可能包括：

代码库。 产品文档。 接口定义。 数据库结构。 错误日志。 用户反馈。 历史决策。 业务规则。 测试结果。

这就是 Context Engineering 的价值。

它关心的不是“怎么问”，而是：

应该给模型哪些信息？ 哪些信息不能给？ 信息太多时怎么压缩？ 文档怎么切片？ 检索结果怎么排序？ 上下文怎么去重？ 怎么避免旧信息污染新判断？ 怎么保证模型看到的是当前有效的信息？

AI 的很多错误，不是模型能力不够，而是它站在了错误的信息环境里。

一个人在错误的信息环境里，越努力，错得越远。

AI 也是一样。

所以 Context Engineering 的本质，是把 AI 从一个孤立的语言模型，拉进真实工作现场。

但这里也有一个误区：

很多人以为 Context Engineering 就是“多塞资料”。

不是。

上下文不是越多越好，而是越相关、越干净、越可追溯越好。

错误的上下文不是增强能力，而是放大幻觉。

#### 三、Harness：解决执行边界问题

再往后，AI 不只是回答问题了。

它开始调用工具。

它可以读文件。 可以改代码。 可以跑测试。 可以查日志。 可以打开浏览器。 可以调用 API。 可以搜索文档。 可以生成 patch。

这时候问题的性质变了。

如果 AI 只是说错了，最多是答案不好。

但如果 AI 可以执行动作，它就可能改错文件、运行危险命令、调用错误接口、无限重试，甚至在没有验证的情况下自信交付。

所以需要 Harness。

Harness 可以理解成模型外面的执行外壳。

它把模型、工具、权限、上下文、日志、评估器、错误处理机制包在一起，让 AI 能够接触外部世界，但不是无限制地接触。

没有 Harness，模型只是会说。 有了 Harness，模型才开始能做。

但“能做”之后，工程问题会突然变复杂：

模型能用哪些工具？ 工具参数怎么校验？ 文件系统怎么隔离？ 命令执行怎么限制？ 权限怎么控制？ 每一步怎么记录？ 失败结果怎么回传？ 什么时候需要人工确认？ 哪些动作必须禁止？

这就是 Harness Engineering 的核心。

它不是让 AI 更自由，而是让 AI 在边界内行动。

如果说 Prompt 是调用参数，Context 是运行内存，那么 Harness 就是执行外壳。

它的价值是：

给一个不稳定的概率模型，加上一个相对可控的工程容器。

这里也有一个常见误区：

很多人以为工具越多，Agent 越强。

但在真实工程里，工具越多，权限越大，风险也越大。

没有权限控制、日志记录和失败处理的工具调用，不是智能增强，而是事故入口。

#### 四、Loop：解决持续运行问题

到了 Agent 阶段，AI 应用的形态再次变化。

它不再只是：

answer = ai(prompt)

而是开始接近：

当未完成时： 计划() act() 观察() 计算() 修复()

这就是 Loop。

AI 可以根据目标制定计划。 可以调用工具执行动作。 可以观察工具返回结果。 可以根据错误继续修正。 可以在一个目标下持续工作。

这时 AI 不再只是一个函数，也不只是一个工具节点。

它开始进入主循环的一部分。

过去，人是 main loop，AI 是其中一个函数调用。

人负责决定下一步。 人负责检查结果。 人负责修正方向。 人负责判断什么时候停止。

现在，Agent 开始承担一部分 main loop。

它会读上下文、选工具、执行、观察、修复，再继续下一轮。

所以 Loop Engineering 的问题不再是：

这一步怎么提示 AI？

而是：

目标怎么进入？ 上下文怎么加载？ 状态怎么更新？ 下一步由谁决定？ 失败后重试几次？ 什么时候换策略？ 什么时候停止？ 什么时候回滚？ 什么时候必须交给人？ 如何避免无限循环？ 如何避免成本爆炸？

Loop Engineering 不是 Prompt Engineering 的升级版。

它是另一个抽象层。

Prompt 解决一次调用。 Loop 解决持续运行。

如果用程序类比，Loop 就像 AI Agent 的

主程序.py。

它决定程序如何启动，如何加载上下文，如何调用工具，如何处理异常，如何判断完成，如何退出。

没有 loop，AI 只是一个工具函数。 没有控制，AI 就是一个不稳定的自动化系统。 没有退出条件，AI 就可能变成事故。

#### 五、真正的主线：控制层越来越完整

所以这些概念放在一起看，讲的不是“prompt 怎么越写越长”。

它们讲的是：AI 系统里的控制层正在变得越来越完整。

层级解决的问题程序类比主要风险Prompt怎么问函数参数输入不清Context给什么运行内存上下文污染Harness怎么执行执行外壳越权行动Loop怎么持续运行main.py失控循环

对应到 AI 在系统里的位置：

第一阶段，AI 是函数。 第二阶段，AI 是带资料的函数。 第三阶段，AI 是可执行组件。 第四阶段，AI 被装进 Agent Runtime，开始参与运行循环。

对应到人的位置：

最早，人是操作者。 后来，人是反馈者。 再后来，人是流程设计者。 现在，人正在变成 runtime designer。

这不意味着人不重要了。

恰恰相反，人更重要了。

只是人的价值从“亲自操作每一步”，变成了“设计 AI 如何安全地操作每一步”。

过去人要会问问题。

现在人还要会定义上下文、权限、工具、评估、日志、失败恢复和停止条件。

这才是 AI 工程真正变难的地方。

#### 六、这不是说 Prompt 不重要了

这里很容易出现一个误解：

既然 AI 工程正在走向 Runtime，那 Prompt Engineering 是不是不重要了？

不是。

Prompt 仍然重要。

只是它不再是全部。

就像写一个程序，函数参数当然重要。

但一个可靠系统还需要内存管理、权限控制、日志记录、异常处理、测试验证和退出条件。

Prompt 是入口，不是系统。

如果只会写 prompt，你能让 AI 回答得更好。

但如果你要让 AI 进入生产环境，你还必须关心：

它基于什么信息回答？ 它可以调用哪些工具？ 它执行动作是否越权？ 它失败后怎么处理？ 它什么时候必须停止？ 它的每一步是否可追溯？ 它的结果是否经过验证？

这就是从 Prompt 到 Runtime 的差别。

#### 七、AI 不是普通自动化，而是概率自动化

传统自动化系统的问题通常是：

流程有没有写对？ 规则有没有覆盖？ 异常有没有处理？

但 Agent 系统更麻烦。

因为它不是纯确定性自动化。

它的核心决策来自概率模型。

这意味着它可能会合理地犯错。 可能会自信地犯错。 可能会在局部看起来正确，但整体方向错误。 可能会在错误假设上持续行动。 可能会把失败解释成“还需要再试一次”。

所以 Agent 时代最危险的事情，不是 AI 不会做。

而是 AI 会在错误方向上一直做。

这也是为什么 Loop 必须有控制层。

要有评估。 要有日志。 要有权限。 要有成本限制。 要有人工介入。 要有回滚。 要有退出条件。

让 AI 动起来不难。

难的是让 AI 可控地动起来。

一个没有控制层的 Agent，不是智能自动化，而是事故自动化。

#### 八、工程师的位置正在重新定义

如果这条判断成立，那么工程师未来的能力栈也会变化。

过去工程师主要写业务逻辑。

现在工程师还要写 AI 的运行逻辑。

第一层，是输入设计能力。

你要能把目标、约束、输入、输出格式说清楚。

第二层，是上下文组织能力。

你要知道该给模型什么材料，也知道什么材料不能给。 你要能管理文档、代码、日志、数据库结构、历史决策和业务规则。

第三层，是执行边界设计能力。

你要能设计工具权限、参数校验、日志记录、失败处理和人工确认机制。

第四层，是循环控制能力。

你要能定义任务如何继续，如何验证，如何重试，如何停止，如何回滚，如何交给人。

这四种能力加起来，才是真正的 AI 工程能力。

不是让 AI 回答一次。

而是让 AI 在真实系统里持续、可控、可验证地行动。

如果把这条演化链压缩成一句话：

Prompt 是调用参数。 Context 是运行内存。 Harness 是执行外壳。 Loop 是 AI 的

主程序.py。

过去我们把 AI 当工具函数用：

输出 = 模型(提示)

现在 Agent 正在变成一个运行系统：

当未完成时： 计划() act() 观察() 计算() 修复()

所以未来真正重要的能力，不只是会不会写 prompt。

而是会不会把一个概率模型，包装成一个可控的执行系统。

AI 工程真正的方向，不是让 prompt 变长，而是让 runtime 变稳。

不是把人从系统里拿掉，而是把人从 loop 里面，移动到 loop 上面。

未来工程师要写的不只是代码。

还要写 AI 的运行边界、验证机制和退出条件。

也就是，写 AI 的

主程序.py。

##### 四、Loop：解决“如何持续运行”的问题

Agent 阶段，AI 不再是单次调用，而是进入循环：

```text
当任务未完成时：
计划()
执行()
观察()
评估()
修复()
继续()
```

Loop Engineering 关注的是：

- 目标如何输入
- 上下文如何加载
- 状态如何更新
- 下一步由谁决定
- 失败后是否重试
- 什么时候换策略
- 什么时候停止
- 什么时候回滚
- 什么时候交给人
- 如何避免无限循环和成本失控

> Prompt 解决一次调用，Loop 解决持续运行。

##### 五、AI 工程的主线：控制层越来越重要

4. AI 被装进 Agent Runtime，开始参与运行循环  

人的角色也在变化：

- 从操作者
- 到反馈者
- 到流程设计者
- 再到 Runtime Designer

人的价值不是消失，而是从“亲自操作每一步”，变成“设计 AI 如何安全地操作每一步”。

---

##### 六、Prompt 仍重要，但不再是全部

Prompt 仍然是入口，但不是完整系统。

如果只是让 AI 回答问题，Prompt 很重要。

但如果要让 AI 进入生产环境，还必须关心：

- 它基于什么信息判断
- 它能调用哪些工具
- 它是否可能越权
- 它失败后如何处理
- 它什么时候停止
- 它的过程是否可追溯
- 它的结果是否经过验证

> 从 Prompt 到 Runtime，本质是从“会回答”走向“可控地执行”。

---

##### 七、Agent 的风险：概率自动化

传统自动化是确定性的，规则写对就能稳定运行。

但 Agent 不同，它的核心决策来自概率模型。

它可能：

- 合理地犯错
- 自信地犯错
- 局部正确但整体错误
- 在错误假设上持续行动
- 把失败理解为“继续再试”

所以 Agent 最大的风险不是不会做，而是 **在错误方向上一直做**。

因此必须有：

- 权限控制
- 日志记录
- 结果评估
- 成本限制
- 人工介入
- 回滚机制
- 退出条件

> 没有控制层的 Agent，不是智能自动化，而是事故自动化。

---

##### 八、未来工程师的新能力

AI 工程能力会从“写业务逻辑”，扩展到“写 AI 的运行逻辑”。

未来工程师需要四类能力：

###### 1. 输入设计能力

能清楚定义目标、约束、输入和输出格式。

###### 2. 上下文组织能力

知道该给模型什么资料，也知道什么资料不能给。

###### 3. 执行边界设计能力

能设计工具权限、参数校验、日志、失败处理和人工确认机制。

###### 4. 循环控制能力

能定义任务如何继续、验证、重试、停止、回滚和交给人。

##### 总结

这篇文章的核心可以压缩成一句话：

> AI 工程的方向，不是让 Prompt 变长，而是让 Runtime 变稳。

- 可回滚

## 结构化（1）

### 2026-06-15 10:30:35

##### 主旨概括

文章认为，AI 工程的核心变化不是 Prompt 越写越复杂，而是 AI 在系统中的角色正在变化：从“被调用的函数”走向“被运行的系统”。真正重要的是把概率模型放进可控的 **Agent Runtime** 中，通过上下文、工具、权限、状态、日志、评估、失败恢复和停止条件，让 AI 能持续、可控、可验证地工作。

---

##### 1. AI 的位置变了：从函数到运行系统

过去的 AI 使用方式类似一次函数调用：

```text
输出 = 模型(提示)
```

人在系统中是“主程序”：

- 人决定问什么；
- 人判断结果对不对；
- 人决定下一步；
- 人负责停止。

但 Agent 出现后，AI 开始能够：

- 读取上下文；
- 调用工具；
- 观察执行结果；
- 修正错误；
- 围绕目标持续运行。

因此，AI 不再只是回答问题的工具，而是被放进一个更完整的运行环境中。

这里的 **Runtime** 不是模型本身，而是围绕模型搭建的控制系统，包括：

- 上下文；
- 工具；
- 权限；
- 状态；
- 日志；
- 评估；
- 失败恢复；
- 停止条件。

核心问题变成：**如何把一个概率模型，包装成一个可控的执行系统？**

---

##### 2. Prompt：解决“怎么问”的输入问题

最早的 AI 应用，本质是一次模型调用：

```text
输出 = 模型(提示)
```

这个阶段，AI 像一个能力接口，可以：

- 写文章；
- 解释概念；
- 生成代码；
- 总结材料；
- 翻译文本。

因此早期大家关注的是 **Prompt Engineering**，也就是如何写好提示词，例如：

- 如何设定角色；
- 如何描述任务；
- 如何给示例；
- 如何限制输出格式；
- 如何让结果更稳定。

但 Prompt 只解决了第一层问题：**输入问题**。

Prompt 很重要，但它不能替代：

- 上下文；
- 工具权限；
- 执行验证；
- 停止条件。

所以，Prompt 没有过时，只是从“全部能力”变成了 AI 工程中的“底层能力”。

---

##### 3. Context：解决“给什么信息”的问题

后来人们发现，Prompt 写得再好，如果上下文错了，结果也会错。

例如：

- 让 AI 修代码，却不给完整代码结构，它只能猜；
- 让 AI 分析业务，却不给真实规则和数据，它只能编；
- 让 AI 写方案，却不给约束条件，它只能生成看似正确的空话。

于是 AI 应用从：

```text
输出 = 模型(提示)
```

变成：

```text
输出 = 模型(提示词, 上下文)
```

AI 不只是需要一句指令，更需要一个“工作现场”。

这个工作现场可能包括：

- 代码库；
- 产品文档；
- 接口定义；
- 数据库结构；
- 错误日志；
- 用户反馈；
- 历史决策；
- 业务规则；
- 测试结果。

这就是 **Context Engineering** 的价值。

它关注的不是“怎么问”，而是：

- 应该给模型哪些信息；
- 哪些信息不能给；
- 信息太多时如何压缩；
- 文档如何切片；
- 检索结果如何排序；
- 上下文如何去重；
- 如何避免旧信息污染新判断；
- 如何保证模型看到的是当前有效的信息。

文章强调：很多 AI 错误不是模型能力不够，而是它处在错误的信息环境里。

一个常见误区是：以为 Context Engineering 就是“多塞资料”。

实际上，上下文不是越多越好，而是要：

- 相关；
- 干净；
- 可追溯；
- 当前有效。

错误上下文不是增强能力，而是放大幻觉。

---

##### 4. Harness：解决“如何安全执行”的边界问题

再往后，AI 不只是回答问题，而是开始调用工具，例如：

- 读文件；
- 改代码；
- 跑测试；
- 查日志；
- 打开浏览器；
- 调用 API；
- 搜索文档；
- 生成 patch。

这时风险变大了。

如果 AI 只是说错，最多是答案不好；但如果 AI 能执行动作，就可能：

- 改错文件；
- 运行危险命令；
- 调用错误接口；
- 无限重试；
- 没有验证就自信交付。

因此需要 **Harness**，也就是模型外面的“执行外壳”。

Harness 把以下内容组合起来：

- 模型；
- 工具；
- 权限；
- 上下文；
- 日志；
- 评估器；
- 错误处理机制。

它的作用是：让 AI 能接触外部世界，但不能无限制地行动。

如果说：

- Prompt 是调用参数；
- Context 是运行内存；
- Harness 就是执行外壳。

Harness Engineering 关心的问题包括：

- 模型能用哪些工具；
- 工具参数如何校验；
- 文件系统如何隔离；
- 命令执行如何限制；
- 权限如何控制；
- 每一步如何记录；
- 失败结果如何回传；
- 什么时候需要人工确认；
- 哪些动作必须禁止。

文章指出一个误区：工具越多，Agent 不一定越强。

在真实工程中：

- 工具越多；
- 权限越大；
- 风险也越高。

没有权限控制、日志记录和失败处理的工具调用，不是智能增强，而是事故入口。

---

##### 5. Loop：解决“如何持续运行”的问题

到了 Agent 阶段，AI 应用不再只是：

```text
answer = ai(prompt)
```

而是接近：

```text
当未完成时：
    计划()
    act()
    观察()
    计算()
    修复()
```

这就是 **Loop**。

AI 可以：

- 根据目标制定计划；
- 调用工具执行动作；
- 观察工具返回结果；
- 根据错误继续修正；
- 围绕一个目标持续工作。

过去，人是 main loop，AI 只是其中一个函数调用。

人负责：

- 决定下一步；
- 检查结果；
- 修正方向；
- 判断何时停止。

现在，Agent 开始承担一部分 main loop。

因此 **Loop Engineering** 关注的问题不再只是“这一步怎么提示 AI”，而是：

- 目标如何进入；
- 上下文如何加载；
- 状态如何更新；
- 下一步由谁决定；
- 失败后重试几次；
- 什么时候换策略；
- 什么时候停止；
- 什么时候回滚；
- 什么时候必须交给人；
- 如何避免无限循环；
- 如何避免成本爆炸。

文章强调：Loop Engineering 不是 Prompt Engineering 的升级版，而是另一个抽象层。

- Prompt 解决一次调用；
- Loop 解决持续运行。

如果用程序类比，Loop 就像 AI Agent 的：

```text
主程序.py
```

它决定：

- 程序如何启动；
- 如何加载上下文；
- 如何调用工具；
- 如何处理异常；
- 如何判断完成；
- 如何退出。

没有 Loop，AI 只是工具函数；没有控制，AI 就是不稳定的自动化系统；没有退出条件，AI 就可能变成事故。

---

##### 6. AI 工程的主线：控制层越来越完整

文章认为，Prompt、Context、Harness、Loop 这些概念并不是孤立的新词，而是在共同回答一个问题：

> 如何让 AI 从概率模型变成可控的执行系统？

可以理解为四个层级：

| 层级 | 解决的问题 | 程序类比 | 主要风险 |

| Loop | 怎么持续运行 | main.py | 失控循环 |

AI 在系统中的位置也经历了四个阶段：

1. AI 是函数；
2. AI 是带资料的函数；
3. AI 是可执行组件；
4. AI 被装进 Agent Runtime，开始参与运行循环。

人的位置也随之变化：

- 最早，人是操作者；
- 后来，人是反馈者；
- 再后来，人是流程设计者；
- 现在，人正在变成 **runtime designer**。

这并不意味着人不重要了，而是人的价值从“亲自操作每一步”，变成了“设计 AI 如何安全地操作每一步”。

---

##### 7. Prompt 仍然重要，但不再是全部

文章特别强调：AI 工程走向 Runtime，并不代表 Prompt Engineering 不重要了。

Prompt 仍然重要，但它只是入口，不是系统。

这就是从 Prompt 到 Runtime 的核心差别。
