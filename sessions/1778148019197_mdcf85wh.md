## 通俗精炼（1）

#### 多 Agent 开发中的过度设计风险

##### 核心观点

在**Spec-Driven Development（规格驱动开发）**中，如果任务拆得太细，但没有明确任务边界、约束条件和 “不做什么”，多 Agent 协作时很容易出现**过度设计**。

问题不是 Agent 不会写代码，而是它们会基于局部最优，各自补充 “最佳实践”，最终偏离真实需求。

##### 典型案例

原始需求很简单：

> 给后台系统增加一个文件上传能力。

真实场景也很明确：

> 单机部署，文件上传到本地磁盘。

但由于缺少边界约束，不同 subagent 开始各自扩展：

- 一个引入`repository pattern`
- 一个设计`storage provider abstraction`
- 一个兼容 S3 / OSS / GCS
- 一个补异步队列和事件系统
- 最后甚至拆出一个`upload-sdk`

结果从一个简单文件上传功能，演变成一套半成品云存储框架。

##### 问题本质

每个局部设计看起来都合理，甚至符合工程最佳实践。

但整体来看：

- 超出了业务需求
- 增加了系统复杂度
- 拉高了维护成本
- 延长了交付周期
- 让团队难以判断 PR 是否该合并

这类问题最麻烦的是：代码质量可能并不差，但方向错了。

##### 对产品和研发管理的启示

多 Agent 协作时，不能只写 “要做什么”，更要明确：

- **只做到什么程度**
- **不支持哪些场景**
- **不引入哪些架构**
- **当前需求的部署环境**
- **未来扩展是否现在就需要**

尤其是简单业务需求，应该避免被 Agent 自动扩展成 “平台化”“抽象化”“框架化” 工程。

##### 一句话总结

AI Agent 越强，越需要清晰的规格边界；否则它们会把一个简单需求，认真地做成一个复杂系统。

#### 一、问题本质：不是 subagent 太多，而是授权边界太模糊

文章里的例子是：

> 需求：后台系统增加文件上传能力，单机部署，上传到本地磁盘。

但 subagent 各自脑补了：

- repository pattern
- storage provider abstraction
- S3 / OSS / GCS
- async queue
- event system
- upload-sdk

这些东西并不是 “写错了”，而是**没有被要求做，却被 Agent 当成了合理工程化扩展**。

所以在 Codex 里用 subagent 时，最重要的不是让每个 Agent “更聪明”，而是让它们：

1. 知道最终目标；
2. 知道自己的任务边界；
3. 知道不能做什么；
4. 知道 PR 会按什么标准验收；
5. 知道不能主动引入新架构。

---

#### 二、推荐工作流：Spec → Plan → Subtasks → Implementation → Review

建议不要直接让 Codex 开始写代码，而是分五步。

##### 1. 先写 Spec，不写代码

让 Codex 先生成`spec.md`或者`implementation-plan.md`。

重点是 Spec 里必须包含：

```md
# Feature: Local File Upload

## Goal

Add a simple file upload feature to the existing admin backend.

## Context

- Deployment: single-machine deployment.
- Storage: local disk only.
- Users: existing admin users.
- Scope: upload one file from admin UI/API and save it to a local directory.

## Non-goals

The implementation must NOT include:

- S3, OSS, GCS, MinIO, or any cloud storage provider.
- Storage provider abstraction.
- Repository pattern if not already used in this codebase.
- Async queue, event bus, background workers.
- Upload SDK.
- Chunked upload.
- Resumable upload.
- Multi-region support.
- CDN integration.
- Virus scanning unless already present in the system.
- Image processing unless explicitly requested.
- New microservice.
- New package/module that is not necessary.

## Constraints

- Reuse existing framework conventions.
- Keep implementation minimal.
- Do not introduce new architectural layers.
- Prefer direct service/controller integration if consistent with current codebase.
- Use existing auth/session/middleware.
- Save uploaded files under configured local directory.
- Add basic validation:
  - file size limit
  - allowed extensions or MIME types
  - safe filename handling
- Return stored file path or URL according to existing API style.

## Acceptance Criteria

- Admin can upload a file successfully.
- File is saved to local disk.
- Invalid file type is rejected.
- Oversized file is rejected.
- Path traversal is prevented.
- Existing tests pass.
- Minimal tests for upload success and validation are added.
- No cloud storage abstraction or provider code exists in the diff.
```

这部分最关键的是`Non-goals`和`Constraints`。

很多人写 spec 只写 “做什么”，但多 Agent 场景下，真正救命的是：

> 不做什么。

##### 2. 让 Codex 先产出 Plan，而不是直接实现

Prompt 可以这样写：

```text
Read the current codebase and the spec.

Create an implementation plan only. Do not write code yet.

The plan must:
1. Identify existing conventions for controllers/services/routes/config/tests.
2. Propose the smallest change set.
3. List files likely to be modified.
4. Explicitly confirm that no storage abstraction, cloud provider support, queue, event system, SDK, or new architecture layer will be added.
5. Identify any open questions before implementation.
```

你需要 review 这个 plan。

如果 plan 里出现：

- `StorageProvider`
- `IStorageAdapter`
- `UploadRepository`
- `UploadServiceInterface`
- `S3Client`
- `EventBus`
- `QueueJob`
- `SDK`
- `Plugin`
- `Extensible architecture`

基本就要打回去。

#### 三、Subagent 怎么拆才合理？

对于这种 “本地文件上传” 需求，不建议拆成太多 subagent。颗粒度过细反而容易让每个 Agent 都 “找存在感”。

推荐最多拆成 3～4 个角色。

---

##### Subagent 1：Codebase Investigator

只负责读代码，不写代码。

###### 任务

- 找到现有路由、controller、service、配置、测试风格；
- 找上传相关已有代码；
- 总结最小接入点；
- 不提出大型架构方案。

###### Prompt

```text
You are the codebase investigator.

Task:
Inspect the existing codebase for conventions relevant to adding a simple local file upload feature.

You must only report findings. Do not modify code.

Focus on:
- routing conventions
- controller conventions
- service/helper conventions
- config/env conventions
- validation patterns
- auth/middleware patterns
- test style

Do NOT propose:
- storage provider abstraction
- cloud storage support
- queue/event system
- SDK/package extraction
- new architectural layers

Output:
1. Relevant existing files
2. Recommended minimal integration points
3. Existing patterns to follow
4. Risks or questions
```

---

##### Subagent 2：Implementation Agent

只负责最小实现。

###### 任务

- 按 spec 实现上传；
- 只使用本地磁盘；
- 只改必要文件；
- 不做扩展设计。

###### Prompt

```text
You are the implementation agent.

Implement the local file upload feature according to spec.md and plan.md.

Hard constraints:
- Local disk only.
- No S3/OSS/GCS/MinIO support.
- No storage provider abstraction.
- No repository pattern unless the existing codebase already requires it.
- No async queue.
- No event system.
- No upload SDK.
- No chunked/resumable upload.
- No new package.
- Do not refactor unrelated code.

Implementation requirements:
- Follow existing routing/controller/service conventions.
- Add config for upload directory and max file size if needed.
- Validate file size.
- Validate allowed extensions or MIME types.
- Prevent path traversal.
- Generate safe stored filename.
- Return response in existing API style.
- Add minimal tests.

Before coding:
- List the exact files you intend to change.
- Explain why each file is necessary.
```

---

##### Subagent 3：Security / Validation Reviewer

这个 Agent 不做 “架构审查”，只看安全和边界。

###### 任务

- 文件名安全；
- MIME /extension 校验；
- path traversal；
- 文件大小；
- 权限；
- 错误响应；
- 是否越界引入复杂设计。

###### Prompt

```text
You are the security and scope reviewer.

Review the implementation for:
- file size validation
- extension/MIME validation
- safe filename generation
- path traversal prevention
- upload directory permissions assumptions
- authentication/authorization consistency
- error handling
- test coverage

Also check scope violations:
- cloud provider support
- storage abstraction
- repository pattern
- queue/event system
- SDK/package extraction
- unrelated refactors

Do not suggest new architecture unless required to fix a concrete bug.
Output:
1. Must-fix issues
2. Nice-to-have but out-of-scope items
3. Scope violations, if any
4. Final merge recommendation
```

---

##### Subagent 4：Test Agent，可选

如果项目比较大，可以单独让一个 subagent 补测试。但也要限制它。

```text
You are the test agent.

Add minimal tests for the local file upload feature.

Test only:
- successful upload
- invalid file type
- oversized file
- path traversal or unsafe filename case if applicable
- unauthenticated access if existing patterns require it

Do NOT:
- introduce new test framework
- add integration infrastructure
- test S3/cloud providers
- add queue/event tests
- refactor existing tests
```

```md
# Spec Plan Template

What does the current system look like?
What existing conventions should be followed?

What is included in this change?
```

#### 五、针对文章中示例的正确 spec-plan 示例

下面是一版比较合适的。

```md
# Spec Plan: Admin Local File Upload

## Objective

Add a simple file upload capability to the admin backend so an authenticated admin user can upload a file and store it on the server's local disk.

## Current Assumption

The system is deployed as a single-node application.
Uploaded files do not need to be shared across multiple machines.
There is no current requirement for cloud object storage.

## Scope

Implement:

- An authenticated upload API endpoint.
- Local disk storage under a configured upload directory.
- File size validation.
- File type validation.
- Safe filename generation.
- API response containing stored file path or accessible URL according to existing conventions.
- Minimal tests.

## Non-goals

Do not implement:

- S3, OSS, GCS, MinIO, or any remote object storage.
- Storage provider interface or adapter abstraction.
- Repository layer unless the existing codebase already uses it for this exact pattern.
- Async processing.
- Queue or event system.
- Upload SDK.
- Chunked upload.
- Resumable upload.
- File deduplication.
- Image compression.
- Virus scanning.
- CDN integration.
- Multi-tenant storage isolation unless the existing system already requires it.
- New service/package/module extraction.
- Broad refactoring.

## Constraints

- Reuse existing auth and routing conventions.
- Reuse existing validation/error response style.
- Keep diff small.
- Do not introduce new dependencies unless absolutely necessary.
- If a new dependency is proposed, explain why built-in framework support is insufficient.
- Keep implementation synchronous.
- Store only on local disk.

## Minimal Design

Expected design:

- Add route: `POST /admin/files/upload` or equivalent existing admin route style.
- Add controller handler.
- Use framework's existing file upload mechanism.
- Validate file.
- Generate safe filename.
- Save to configured local directory.
- Return JSON response.

No extra abstraction layer is needed.

## Acceptance Criteria

- Valid file upload succeeds.
- File exists on local disk after upload.
- Oversized file is rejected.
- Disallowed file type is rejected.
- Unsafe filename cannot escape upload directory.
- Existing tests pass.
- New minimal tests pass.
- Diff does not include cloud provider, provider abstraction, queue, event system, SDK, or unrelated refactor.

## Future Work, Explicitly Out of Scope

If future requirements need cloud storage, large files, resumable upload, CDN, or async processing, those should be proposed in a separate spec and PR.
```

#### 六、PR Review 规则：用 “需求符合度” 压过 “最佳实践”

文章最后的问题是：

> 同事给你提了这样的代码 PR，你合还是不合？

我的建议是：**不合，但不是因为代码差，而是因为 scope violation。**

你可以在 review 里这么说：

```text
Thanks for the implementation. The code quality is good, but this PR exceeds the approved scope.

The approved spec requires local disk upload only for a single-node deployment.

The following additions are out of scope:
- storage provider abstraction
- S3/OSS/GCS support
- async queue/event system
- upload SDK extraction

Please reduce this PR to the minimal local-disk implementation described in the spec.
If cloud storage or async processing is needed later, we should create a separate spec and evaluate it independently.
```

这类 PR 不能因为 “写得挺好” 就合。因为一旦合进去，你接受的是：

- 更大的维护面；
- 更多未验证的抽象；
- 更多测试成本；
- 更多安全面；
- 更多未来迁移负担。

#### 七、在 Codex 中控制 subagent 的几个具体技巧

##### 1. 每个 subagent 都要有 “不允许事项”

不要只写：

```text
Implement file upload.
```

而要写：

```text
Implement local disk file upload only.
Do not add storage abstraction, cloud providers, queue, events, SDK, or unrelated refactors.
```

---

##### 2. 要求 subagent 先列文件，再修改

这个很有效。

```text
Before editing code, list all files you plan to modify and explain why each change is necessary.
Wait for approval before implementation.
```

这样可以提前发现它是不是要创建：

```text
src/storage/providers/S3Provider.ts
src/storage/StorageProvider.ts
packages/upload-sdk
src/events/FileUploadedEvent.ts
src/queues/ProcessUploadJob.ts
```

看到这些就直接打回。

---

##### 3. 把 “最小实现” 变成验收指标

可以写：

```text
Prefer the smallest implementation that satisfies the acceptance criteria.
If there are two designs, choose the one with fewer new files, fewer abstractions, and fewer dependencies.
```

---

##### 4. 设置 “架构升级需要人工确认”

```text
Any architectural change requires explicit approval before implementation.

Architectural changes include:
- new abstraction layer
- new interface/base class
- new module/package
- new external dependency
- new background processing mechanism
- new storage backend support
```

---

##### 5. 让 reviewer agent 专门抓 scope creep

可以让 Codex 最后跑一次：

```text
Review the final diff against spec.md.

Identify:
1. Any code not required by the acceptance criteria.
2. Any new abstraction not justified by current requirements.
3. Any new dependency.
4. Any unrelated refactor.
5. Any future-proofing code.

Recommend what should be removed before merge.
```

---

#### 八、什么时候可以允许抽象？

不是说永远不能抽象，而是抽象要有真实需求触发。

可以设一条规则：

> 没有第二个真实实现，不抽象 provider。  
> 没有明确异步需求，不引入 queue。  
> 没有多个调用方，不抽 SDK。  
> 没有跨存储后端需求，不设计 storage abstraction。  
> 没有性能瓶颈证据，不做复杂优化。

例如：

| 设计 | 当前是否需要 | 什么时候需要 |
|---|---:|---|
| 本地磁盘上传 | 需要 | 当前需求 |
| StorageProvider interface | 不需要 | 同时需要本地 + S3/OSS |
| S3/OSS/GCS 支持 | 不需要 | 产品明确要求云存储 |
| 异步队列 | 不需要 | 上传后有耗时处理 |
| Upload SDK | 不需要 | 多个服务 / 客户端复用上传能力 |
| 分片上传 | 不需要 | 大文件、弱网、断点续传 |
| CDN | 不需要 | 大规模公开访问 |

#### 九、推荐的 Codex 指令总模板

你可以把下面这段作为项目级提示词或者任务开头。

```text
Project coding rules for this task:

We are practicing spec-driven development.

General rules:
```

#### 十、最终建议

在 Codex 中用 subagent 和 spec-plan，最佳实践不是 “多拆任务”，而是：

1. **先写可审查的 Spec；**
2. **Spec 必须包含 Non-goals；**
3. **Plan 必须先过人审；**
4. **Subagent 只给局部授权；**
5. **每个 subagent 都要带禁止事项；**
6. **架构变化必须人工确认；**
7. **最后用 reviewer agent 检查 scope creep；**
8. **PR 合并标准以验收条件为准，不以 “最佳实践感” 为准。**

对于文章里的文件上传例子，正确做法就是：

> 一个本地磁盘上传接口 + 基础校验 + 安全文件名 + 最小测试。  
> 其他所有云存储、抽象层、队列、事件、SDK，全部放进 Future Work，不进入当前 PR。

### 回答 · 2026-05-07 10:13:58

你说得对。前面那版更像 “团队级流程”，对日常开发确实偏重。

更现实的建议是：

> **小需求不要开多个 subagent。一个 Codex 实例 + 一个简短 spec-plan 就够了。**  
> **只有当多个模块确实可以并行、边界清晰、文件互不重叠时，才适合拆给多个 agent。**

---

#### 1. 先回答：文件上传这种需求需要几个 agent？

文章里的例子：

> 后台系统增加本地文件上传能力。

这种需求一般**不需要 subagent**。

最合适的是：

```text
一个 Codex 会话完成：
1. 看现有代码结构
2. 给出最小实现计划
3. 实现
4. 自测
```

你只需要给它一个非常短的约束：

```text
实现后台本地文件上传功能。

约束：
- 单机部署，只上传到本地磁盘
- 不支持 S3 / OSS / GCS / MinIO
- 不设计 storage provider abstraction
- 不引入 repository pattern
- 不引入队列、事件系统、SDK
- 不做无关重构
- 按现有项目风格实现
- 先给出计划和将修改的文件，确认后再改代码
```

这就够了。

---

#### 2. Codex 里怎么 “启动 subagent”？

这里要分情况。

如果你说的是**Codex CLI / 终端里的 Codex**，它通常不是像 Claude Code 那样有一个显式的`Task (subagent=xxx)`机制。

更实用的方式是：

##### 方式一：开多个 Codex 会话

例如：

```bash
codex
```

然后在不同终端窗口里开多个 Codex，每个窗口负责一个模块。

适合：

- 模块 A、B、C 独立；
- 各自修改不同目录；
- 最后你人工合并。

---

##### 方式二：用 Git branch /worktree 隔离每个 agent

这是我更推荐的方式。

假设你有三个独立模块：

```text
modules/user
modules/order
modules/payment
```

可以这样：

```bash
git worktree add ../repo-user-agent -b agent/user-module
git worktree add ../repo-order-agent -b agent/order-module
git worktree add ../repo-payment-agent -b agent/payment-module
```

然后分别进入不同目录启动 Codex：

```bash
cd ../repo-user-agent
codex
```

```bash
cd ../repo-order-agent
codex
```

```bash
cd ../repo-payment-agent
codex
```

这样每个 Codex 都在自己的 Git worktree 里干活，不会直接互相覆盖。

完成后再回主仓库逐个 merge：

```bash
git checkout main
git merge agent/user-module
git merge agent/order-module
git merge agent/payment-module
```

如果有冲突，就说明边界没拆好，或者它们改了共享文件。

---

#### 3. 多个独立模块交给 agent，关键不是 “启动”，而是 “隔离”

你真正要解决的是：

> 多个 agent 并行写代码时，怎么保证它们互不影响？

核心做法有四个。

---

##### 3.1 每个 agent 只允许修改自己的目录

例如你要同时做三个模块：

```text
src/modules/user
src/modules/order
src/modules/payment
```

那就明确告诉每个 agent：

###### User Agent

```text
你只负责用户模块。

允许修改：
- src/modules/user/**
- tests/user/**

禁止修改：
- src/modules/order/**
- src/modules/payment/**
- src/shared/**
- package.json
- 数据库 migration
- 全局配置
- 路由总入口

如果必须修改禁止区域，先停止并说明原因，不要直接修改。
```

###### Order Agent

```text
你只负责订单模块。

允许修改：
- src/modules/order/**
- tests/order/**

禁止修改：
- src/modules/user/**
- src/modules/payment/**
- src/shared/**
- package.json
- 数据库 migration
- 全局配置
```

这比 “角色设定” 更重要。

---

##### 3.2 提前定义模块之间的接口，不让 agent 自己发明

比如订单模块需要用用户信息。

不要让 Order Agent 自己去改 User 模块。

你应该先定义：

```ts
interface UserReader {
  getUserById (userId: string): Promise<{
    id: string
    name: string
    status: 'active' | 'disabled'
  } | null>
}
```

然后告诉 Order Agent：

```text
订单模块如果需要用户信息，只能通过 UserReader 接口。
不要修改 user 模块。
不要新增跨模块调用方式。
```

这样它不会乱改别人模块。

---

##### 3.3 共享文件要么禁止改，要么指定一个 integration agent

多个 agent 最容易冲突的是：

```text
package.json
routes.ts
app.ts
schema.prisma
db/migrations
src/shared/*
eslint config
tsconfig
```

这些文件最好默认禁止修改。

如果确实要改，单独交给一个 “集成者” 处理。

也就是说：

```text
User Agent：只写用户模块内部代码
Order Agent：只写订单模块内部代码
Payment Agent：只写支付模块内部代码
Integration Agent：最后统一接路由、migration、全局注册
```

但注意，**Integration Agent 可以是你自己**，不一定非得是另一个 AI。

---

##### 3.4 每个 agent 提交自己的 commit

让每个 agent 完成后提交：

```bash
git status
git diff
npm test
git add .
git commit -m "feat (user): implement user profile module"
```

这样你 review 时很清楚：

```bash
git show agent/user-module
git show agent/order-module
```

不要让多个 agent 在同一个工作区里同时改代码。

---

#### 4. 一个简化版 spec-plan 就够了

你不需要写很长的 spec。对每个 agent 给这 6 项就够了。

```md
# Task

实现订单模块的基础 CRUD。

# Allowed files

- src/modules/order/**
- tests/order/**

# Forbidden files

- src/modules/user/**
- src/modules/payment/**
- src/shared/**
- package.json
- db/migrations/**
- app.ts
- routes.ts

# Contract

订单模块只能通过 UserReader 接口读取用户信息，不要直接访问 user 表或 user 模块内部代码。

# Non-goals

- 不做支付
- 不做库存
- 不做消息队列
- 不做事件系统
- 不做权限系统重构
- 不修改全局架构

# Done criteria

- 订单创建、查询、更新、取消可用
- 单元测试通过
- 不修改 forbidden files
```

这已经足够了。

#### 5. 推荐的实际工作流

假设你有三个独立模块要并行做：

```text
用户模块
订单模块
支付模块
```

我会这么做。

---

##### 第一步：你先做一个总 plan

不要让 agent 自己拆系统。

你先写：

```text
模块边界：
- user 只负责用户资料、状态
- order 只负责订单生命周期
- payment 只负责支付记录和支付回调

共享约定：
- user 对外暴露 UserReader
- order 对外暴露 OrderReader
- payment 通过 orderId 关联订单
- 不允许模块之间直接访问对方内部 repository/model
```

---

##### 第二步：创建 worktree

```bash
git worktree add ../app-user -b agent/user
git worktree add ../app-order -b agent/order
git worktree add ../app-payment -b agent/payment
```

---

##### 第三步：分别启动 Codex

```bash
cd ../app-user
codex
```

给它：

```text
你负责 user 模块。

只允许修改：
- src/modules/user/**
- tests/user/**

禁止修改其他模块和全局文件。

目标：
实现用户资料查询和状态更新。

先输出计划和拟修改文件，不要立即写代码。
```

另一个终端：

```bash
cd ../app-order
codex
```

给它：

```text
你负责 order 模块。

只允许修改：
- src/modules/order/**
- tests/order/**

禁止修改 user/payment/shared/package.json/routes/app/migrations。

目标：
实现订单创建、查询、取消。

依赖用户信息时，只使用已定义的 UserReader 接口。
如果接口不存在，先写 TODO 或说明需要 integration，不要修改 user 模块。
```

---

##### 第四步：每个 agent 自测和提交

```bash
npm test
git status
git diff
git commit -am "feat (order): implement order module"
```

---

##### 第五步：回主分支集成

```bash
cd ../main-app
git merge agent/user
git merge agent/order
git merge agent/payment
```

如果路由、migration、依赖需要统一处理，你自己或单独一个 Codex 处理。

#### 6. 什么时候适合用多个 agent？

适合：

```text
用户模块、订单模块、支付模块
前端页面 A、页面 B、页面 C
不同服务的 API client
不同数据库表的基础 CRUD
独立测试补充
文档和代码并行
```

不适合：

```text
同一个核心模块内部
同一个复杂函数
同一批共享类型
同一个数据库 schema
同一个架构重构
依赖关系很强的业务流程
```

如果几个 agent 都要频繁改同一个文件，说明不该并行。

---

#### 7. 防止互相影响的提示词模板

你可以直接用这个。

```text
你是当前任务的实现 agent。

任务：
实现 [模块名] 的 [功能]。

边界：
你只允许修改：
- [允许目录 1]
- [允许目录 2]

禁止修改：
- 其他业务模块
- src/shared/**
- package.json
- app.ts
- routes.ts
- db/migrations/**
- 配置文件
- 架构层代码

如果你认为必须修改禁止文件：
1. 不要修改
2. 停下来说明原因
3. 给出需要 integration 的建议

设计要求：
- 按现有代码风格
- 最小实现
- 不做无关重构
- 不引入新抽象
- 不实现未来可能需要的功能

执行要求：
- 先列出计划
- 先列出将修改的文件
- 等确认后再写代码
- 完成后列出测试结果
```

---

#### 8. 对文章那个 “过度设计” 问题的简化解法

不需要四五个 agent。

你只需要在 Codex 任务里加这几行：

```text
这是一个小功能，不要平台化。

只实现当前需求：
- 单机
- 本地磁盘
- 后台上传

明确不做：
- 云存储
- provider abstraction
- SDK
- 队列
- 事件
- 分片
- 断点续传
- 大规模文件服务

如果你想做这些，只能写到 Future Work，不要实现。
```

这就能挡掉 80% 的过度设计。

---

#### 9. 我的建议总结

最实用的规则是：

1. **小任务不用 subagent。**
2. **多个 agent 只适合处理文件边界清楚的独立模块。**
3. **每个 agent 用独立 git worktree /branch。**
4. **每个 agent 明确 allowed files 和 forbidden files。**
5. **共享文件默认不让改。**
6. **接口先定好，不让 agent 自己跨模块乱连。**
7. **最后由一个人或一个 integration agent 合并。**

最关键的一句：

> 不要让多个 Codex 在同一个工作区里自由发挥；要用 Git 隔离工作区，用文件边界限制权限，用接口契约限制协作方式。
