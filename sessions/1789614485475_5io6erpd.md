4\. AskUserQuestion 这个工具磨了很久才让模型学会调用。结果作者现在自己都不怎么用了，直接让 Claude 出一个带 mockup 的 artifact 来问他问题。

5\. Code review 变了。人类 reviewer 挑三个小 nitpick，其实是在证明"我读了"。这活交给 Claude。人只管 Claude 不知道的事，这个 API 为什么长这样，服务边界为什么画在这。

6\. workflows 是从 code review 长出来的。fan out 找 bug，每个 bug 再从几个角度对抗性验证，过滤掉误报只留真的。Robert 信任 workflows 的理由很简单，编排层是代码，for 循环不会漏掉任何一项。

7\. Claude Tag 第一次把界面和 transcript 彻底分开。Slack 里看到的每条消息都是它主动调工具发的，内心独白看不到。他们一开始很慌，后来发现不盯着也能拿到好结果，才意识到模型真的到这一步了。

8\. 怀念什么？Sid 怀念性能优化，"现在 Claude 比我强得多"。Robert 曾经花一整天手写 CSS 复刻 Mac OS 10.4 的 Aqua 按钮，叠了好几层 radial gradient。他说再也不会手工做这种事了。听着有点唏嘘。

## 深度解读（1）

### 2026-09-17 03:08:05

#### Claude Code 团队离开终端：AI 编程的重心正从 “生成代码” 转向 “管理委托”

这段对谈最值得关注的，不是 “70%—80% 的工作发生在 Slack” 这个醒目数字，而是它背后的工作单元发生了变化：**人不再逐项交代任务，而是给出目标，在关键节点验收结果。**终端和桌面端没有消失，只被留给精修或需要微观干预的场景。

这意味着 AI 编程产品竞争的重点，正在从 “如何让模型更好地写下一段代码”，转向 “如何让多个长时间运行的代理可靠地完成一个目标”。

##### 真正耐用的不是功能，而是控制机制

文中一个重要细节是：Sonnet 3.5 一次收到五件事时只能完成三件，因此团队加入待办列表；模型变强后，这个功能又被删除。很多 harness 功能本质上是在补偿特定模型的失败模式，生命周期可能只有两个月。

但这并不等于 “模型越强，产品层越薄”。旧补丁会消失，任务尺度却会扩大：从补一段代码，变成跨文件修改、排查缺陷乃至并行处理多个目标。产品需要解决的新问题随之变成资源分配、执行状态、异常恢复、结果验收和权限控制。

因此，AI 产品应把能力分成两类：一类是针对当前模型弱点的临时脚手架，例如强制列清单；另一类是任务变复杂后仍然必要的控制面，例如可追踪状态、验收门槛和失败恢复。**前者要敢删，后者反而会成为长期产品资产。**判断标准不是功能使用率，而是它究竟在修补模型，还是在管理系统复杂度。

##### 最有效的人机沟通，未必是继续追问

AskUserQuestion 工具经过长期打磨，作者却逐渐少用：Claude 会先生成带 mockup 的 artifact，再让人反馈。这里隐藏着一个可迁移的产品原则：**当用户难以准确描述需求时，低成本地产出一个可批评的具体对象，通常比继续收集文字答案更有效。**

对抽象问题，人容易给出含糊偏好；面对界面、流程或原型，人却能迅速指出 “这里不对”。所以 artifact 不只是输出物，也是需求澄清工具。它把交互从 “请把要求说完整” 改为 “先给出假设，再让用户修正”，尤其适合界面设计、数据分析、文档结构等可快速形成草案的工作。边界也很明确：如果错误原型会造成强锚定，或领域风险很高，结构化提问仍不能省略。

##### 人类审查正在上移，但不能失去可观测性

团队把格式问题和小错误交给 Claude，人类只处理模型缺少的组织背景：API 为什么这样设计、服务边界为何画在这里。与之配套的是可编程 workflow：并行找 bug，再从不同角度对抗验证，依靠代码中的循环确保每一项都经过处理。这里真正可靠的不是某个代理永不出错，而是**确定性的编排覆盖，加上概率性的判断能力**。

Slack 中隐藏内部 transcript 也说明，成熟代理不再要求人盯住每一步。不过，“不看过程也能得到好结果” 目前只是前沿团队的经验，不能直接外推到高风险开发。减少过程展示的前提，是验收标准、审计记录和回滚机制足够强。

对产品团队来说，值得验证的问题已经不是 “要不要做一个 AI 编程界面”，而是：**哪些目标可以异步委托，怎样证明任务没有漏做，以及什么知识必须由人类掌握并在验收时注入。**界面从终端迁到 Slack 只是表象，真正的变化是人从操作者变成了目标设定者和责任承担者。

## 高价值（1）

### 2026-09-17 03:09:15

#### AI 编程产品的重心，正从 “操作模型” 转向 “编排、验收与持续重构”

文章最有价值的不是 “70%～80% 的工作离开终端” 这个数字，而是揭示了一个产品变化：**模型越能自主执行，界面越像任务控制台，产品能力也越需要区分 “临时补丁” 和 “长期基础设施”**。但这只是对访谈的二手摘要，缺少量化口径与失败案例，适合用于提出假设，不宜直接外推为行业趋势。

##### 很多 AI 功能只是模型缺陷的临时补丁，产品必须为删除而设计

Sonnet 3.5 同时接到五件事时容易半途放弃，因此团队加入 to-do list；一年后模型能力提升，这项功能又被移除。这个案例支持的不是 “功能都应该删”，而是：**AI 产品的一部分功能，其价值绑定于特定模型的失败模式，模型升级会直接缩短其生命周期。**

可迁移的方法是给功能标注类型：一类是失败补丁，如强制拆步、重复提醒；另一类是较稳定的控制能力，如权限、审计、评测、成本控制与可回滚。前者应设置基于评测的删除条件，而不是因为投入过多就长期保留。文章中 “技术保质期只有两个月” 只是受访者判断，单个 to-do 案例能证明方向，不能证明这个具体周期。

同时，模型变强后任务尺度也会扩大，因此旧补丁消失不等于 harness 变得不重要，而是要转向新的问题，例如长任务的状态管理、并行协作和结果验收。**真正该避免的是把当前模型的缺陷误当成永久用户需求。**

##### 界面迁移到 Slack，意味着交互单位已从 “命令” 变成 “目标与验收”

团队主要在 Slack 中给 Claude Tag 目标，只在精修或需要微观管理时打开 TUI；AskUserQuestion 也被 “先生成带 mockup 的 artifact，再请人判断” 替代。这说明高自主性模型的主要交互成本，不再是如何逐步指导，而是如何表达目标、查看中间产物并决定是否接受。

因此，“离开终端” 不代表专业工具消失，而是**终端从默认工作场所退为异常处理和精细控制界面**。这一模式适合结果可检查、过程可回滚、失败成本有限的任务；若需求高度模糊、操作不可逆或涉及安全合规，隐藏 transcript、减少过程监督反而可能放大风险。

##### 可靠性来自 “确定性编排包住概率性执行”，但编排不能替代语义判断

文章描述的 code review workflow 会并行寻找 bug，再从多个角度对每个问题进行对抗性验证，最后过滤误报。它的价值不只是 “多开几个 agent”，而是用代码保证每个候选项都经过固定流程，再用独立验证降低单次模型判断的不稳定性。

这一方法可迁移到需求评审或事故分析：并行生成风险假设，为每项安排反证角色，再通过统一门槛筛选。但 “for 循环不会漏项” 只意味着**已生成的项目都会被处理**，不能保证模型最初发现了所有问题，也不能保证验证标准正确。人类仍需处理模型缺少的组织背景，例如 API 兼容承诺、服务边界和历史约束；这些信息若长期只存在于人脑中，也会成为新的瓶颈。

最值得继续验证的是：哪些 harness 能力跨越多个模型版本仍然有效 —— 它们比任何单个交互界面更可能构成持久产品价值。

## 口播总结（1）

### 2026-09-20 00:38:56

Claude Code 团队自己的工作方式，已经发生了一个明显变化：百分之七十到八十的工作，不再直接在终端里完成。更关键的是，他们交给人工智能的，往往不再是一条条具体任务，而是一个目标。

这不是简单地把编程工具搬进聊天软件，而是人和人工智能的分工正在重写。

根据 Claude Code 团队三位成员的对谈，他们现在的大部分工作，是在 Slack 里通过 Claude Tag 完成的。传统的终端文字界面和桌面客户端，主要在两种情况下才会打开。

一种情况，是需要精细打磨某个具体成果。另一种情况，是想对多个 Claude 智能体进行更细致的控制。用他们自己的说法，就是想“微观管理我的那些 Claude”。

日常情况下，人不再详细规定每一步怎么做，而是告诉 Claude，最终想达到什么目标。至于任务怎么拆、步骤怎么排、工具怎么调用，越来越多地交给模型处理。

这种变化背后，是模型能力进步得太快。团队成员 Sid 提到，以前底层技术的有效期可能按年计算，现在可能只有两个月。

有一个很具体的例子。在 Sonnet 三点五时期，如果一次交给模型五件事，模型可能做完三件就停下来。为了解决这个问题，团队给 Claude Code 加入了待办事项列表。模型可以据此检查还有哪些任务没有完成，效果立刻好了很多。

但大约一年后，这项功能又被删除了。原因不是它设计得不好，而是新模型已经不再需要这根“拐杖”。

Sid 因此得出一个很直接的经验：不要对自己造出来的功能产生感情。一个今天非常重要的设计，明天可能会因为模型升级而失去价值。

理解这一点，还要注意一个条件。不能简单地认为，模型越来越强，所以外围工具只需要不断删除。

Claude Code 周围有一套辅助模型工作的系统，业内常称为“harness”，可以理解为模型的工具、规则和任务编排框架。其中很多功能，确实是在弥补当前模型的失败模式。模型容易漏任务，就加检查清单；模型不善于主动提问，就设计专门的提问工具。等模型能力提高，相应的补丁就应该主动删除。

不过，模型能力增强以后，人们交给它的任务也会变得更大、更复杂。旧补丁可以删除，但团队往往还要为更大规模的任务创造全新的工具。所以真正的原则不是一味做减法，而是持续判断：哪些工具已经过时，哪些新能力又需要新的工作形态。

专门用来向用户提问的 Ask User Question 工具，就是一个例子。团队花了很长时间，才让模型学会在适当的时候调用它。可现在，这项工具的作者自己都很少使用它了。他更愿意让 Claude 先生成一个带有界面草图的可交互成果，也就是一个 artifact，再拿着这个具体原型向人提问。

相比抽象地问“你想要什么”，先做出一个看得见的方案，再请人判断和修改，沟通效率可能更高。这说明人工智能与人的交流，也在从文字问答转向用成果对话。

代码审查同样发生了变化。

过去，人类审查代码时，常常会指出几个很小的问题。比如命名不够统一，格式不够整齐，或者某处写法还可以调整。这些意见有时不只是为了改代码，也是在证明：“我认真读过了。”

现在，这类常规检查可以交给 Claude。人类审查者则把注意力放在模型不知道的事情上。

例如，为什么这个应用程序接口，也就是 A P I，要设计成现在这样？为什么两个服务的边界画在这里，而不是别处？某项历史决策背后，有没有组织结构、业务风险或者兼容性方面的原因？

这些问题依赖长期积累的背景信息，不一定写在代码里，也未必存在于模型能看到的材料中。于是，人的价值从寻找小错误，转向提供上下文、判断边界和承担决策责任。

在代码审查的基础上，团队还发展出了更复杂的自动化工作流。

模型可以同时向多个方向展开检查，寻找潜在缺陷。发现一个问题后，再安排多个检查过程，从不同角度进行对抗性验证。只有经得住复查的问题才保留下来，误报则被过滤掉。

团队成员 Robert 之所以信任这种工作流，一个重要原因是编排层由代码控制。比如一个循环程序，会按照规则检查每一项，不会因为疲劳、分心或者觉得麻烦而随手跳过。模型负责分析，确定性的程序负责保证流程完整，两者结合，比单纯依赖一次模型回答更可靠。

Claude Tag 还带来了另一个变化：用户看到的界面，与模型完整的执行记录被分开了。

在 Slack 里，人看到的每条消息，都是 Claude 主动调用工具后发出来的。模型中间经历了哪些内部步骤，用户不再全程盯着。团队一开始对此很不安，因为这意味着人失去了过去那种实时监视过程的感觉。

但后来他们发现，即使不盯着每一步，仍然能够稳定拿到不错的结果。正是从那时起，他们意识到，模型能力真的跨过了一个阶段。信任不再来自“我看见了它的全部过程”，而更多来自清晰的目标、可靠的验证机制，以及最终结果。

当然，这种进步也带来了一点失落。

Sid 说，他怀念亲自做性能优化，因为现在 Claude 在这方面已经比他强得多。Robert 曾经花一整天手写层叠样式表，也就是 CSS，只为复刻 Mac OS 十点四系统里的 Aqua 按钮。为了做出按钮的质感，他叠加了好几层径向渐变。如今，他认为自己再也不会手工做这种事情了。

这段对谈最值得记住的，不只是“人工智能写代码更快了”。更深的变化是，工程师正在从执行具体步骤，转向设定目标、提供背景、设计验证机制和判断系统边界。

与此同时，不要迷信任何一种当前工具。很多功能只是特定模型阶段的临时脚手架。模型会变，任务规模也会变。真正需要长期保留的能力，是知道什么时候该放手，什么时候该介入，以及如何验证人工智能最终做对了没有。

## 深度解读-口播（1）

### 2026-09-30 11:53:31

开发人工智能编程工具的人，自己已经不太守着终端写代码了。据陈成对一场团队对谈的整理，Claude Code 团队有百分之七十到八十的工作，已经不在终端里完成。更值得注意的，不是他们换了什么界面，而是他们交给人工智能的东西，正在从一项项任务，变成一个个目标。

过去，使用编程助手，往往是打开终端，告诉模型下一步做什么，再盯着它执行。现在，这个团队的大部分工作，是在团队聊天软件 Slack 里的 Claude Tag 上完成的。只有需要精修某个东西，或者想仔细控制几个 Claude 的行动时，他们才会打开终端里的交互界面，或者桌面端。

这不只是把输入框搬到了聊天软件里。Claude Tag 把用户看到的消息，和模型完整的执行记录分开了。Slack 里出现的每条消息，都是模型主动调用工具发出来的。用户不再看着模型的全部中间过程，而是接收模型选择发出的沟通信息。

团队一开始也不放心。但后来发现，即使不一直盯着，仍然能拿到不错的结果，他们才意识到，模型的能力已经走到了这一步。

所以，这里的变化可以收拢成一句话：人开始少管执行过程，多交代想要达到的目标。

不过，模型更能干了，并不意味着围绕模型的工具就可以固定下来。恰恰相反，这些工具可能过时得更快。

对谈里有一个很具体的例子。在三点五版 Sonnet 模型的时期，你交给模型五件事，它可能只做完三件就停了。团队于是加了一个待办清单，帮助模型记住还有哪些事情没完成，效果一下就好了。

但一年以后，这个功能又被移除了。原因不是待办清单设计得不好，而是模型已经不再需要这层帮助。

参与对谈的 Sid 因此提出，不要对自己造出来的东西太有感情。他们感受到，过去一些底层技术的有效期可以按年算，如今可能只有两个月。

理解这件事，需要知道一个概念：模型外面的工具、规则和执行机制，常被统称为 harness。你可以把它理解成帮助模型完成工作的配套系统。

按照这次对谈的看法，这套系统里的很多功能，其实是在给当前模型容易犯的错误打补丁。模型记不住任务，就帮它列清单。模型不会恰当地提问，就专门设计一个向用户提问的工具。

但模型变强以后，原来的补丁就可能不再必要。这时候，应该愿意把它删掉。

这里还有一个重要条件：任务的尺度也在变大。模型能承担更多事情，就会需要形态不同的新工具。所以，不能只记住“旧功能要删”。真正的意思是，旧问题消失了，就撤掉旧补丁；新任务出现了，就重新设计支持方式。

向用户提问的工具，也体现了这种变化。团队曾经花了很长时间，才让模型学会调用一个专门的提问工具。但工具的作者现在自己都不太用了。他更愿意让 Claude 直接生成一份带界面示意的成果，再借着这个具体成果来问问题。

提问没有消失。变化的是，模型不一定非要按原来设计好的方式提问。

接下来，人的注意力又该放在哪里？代码审查给出了一个很清楚的例子。

过去，人类审查代码，有时会挑出几个细枝末节的问题。对谈中的说法是，这些小意见，某种程度上是在证明：“这份代码，我读过了。”

现在，这类检查可以交给 Claude。人更应该关注模型不知道的背景：比如，一个程序接口为什么设计成现在这样，两个服务之间的职责边界为什么划在这里。

这些问题背后，往往有项目历史和设计取舍。只看眼前的代码，不一定能知道答案。

与此同时，代码审查还长出了一套更系统的工作流。它不是只让一个模型看一遍代码，而是并行展开多个检查任务去找缺陷。找到一个疑似问题以后，再从几个角度尝试验证它是否真的成立，过滤掉误报，留下确认存在的问题。

Robert 信任这类工作流的一个原因，是负责安排执行顺序的部分，本身就是代码。比如，用循环逐项执行检查，就不会靠模型“想起来”才去检查下一项。

这并不等于能保证发现所有缺陷。它的价值在于：对已经安排好的检查事项，可以用程序把执行过程固定下来，减少漏做。

因此，人并不是简单退出了代码审查，而是在重新分配注意力。重复性的检查更多交给模型和程序，设计背景与边界判断，则更需要人来把关。

这种变化也带来一点失落。Sid 说，他怀念亲手做性能优化，但现在 Claude 已经比他强得多。Robert 则回忆，自己曾花一整天，手写网页样式，复刻老版苹果系统里那种有光泽的按钮，叠了好几层渐变。他说，以后再也不会手工做这种事了。

值得记住的，不只是编程变快了，而是工作的重心正在移动：从盯住每一步，转向交代目标；从保留自己精心打造的工具，转向判断它是否还解决真实问题。模型承担更多执行工作以后，人的价值也更集中在那些代码本身没有写出来的背景、取舍和边界上。
