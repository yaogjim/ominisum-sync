## 分析要点

- **核心高价值点**：将系统提示视为知识导航地图，把可复用流程放入技能、公司背景放入 Wiki、实时数据交给工具、确定性规则写入代码，可同时控制上下文规模并提升可靠性。
- **留存建议**：精读并长期存档，作为生产级智能体架构参考（包含可复用的上下文分层、确定性计算、能力隔离、父子代理和人工审批设计，并提供了实际性能数据与工程取舍。）

**知识要点**

- 模型应负责解释、判断和建议，计算、日期窗口、账户匹配及硬性安全规则应由可复现代码完成。
- 不同指标应分别指定唯一可信来源；无法可靠关联的数据应保留缺口，并明确来源、时间窗口和归因模型。
- 共享运行时可通过能力配置、独立沙箱和父子代理实现入口统一与上下文隔离，写操作则需人工审批和执行后验证。

**行动项**

- 审计现有智能体流程，将计算、固定规则和安全约束从模型调用迁移到确定性代码。
- 建立系统提示、技能、业务 Wiki、实时工具和确定性代码五层上下文结构，并记录每类指标的可信来源。
- 对可执行操作增加基于用户身份的权限检查、人工审批卡片和执行结果回查机制。

#### Key Takeaways

- 将代理视为知识工作者。最显著的成果来自于为代理提供一个精心设计的工作空间，包括沙盒、软件、业务背景和明确的操作指南。系统提示成为了一张地图，帮助代理找到所需信息，而无需将所有内容都置于上下文中。
- 利用模型进行判断，用代码确保一致性。计算、真实来源规则和安全措施更适合用代码处理。这使得代理更快、更经济、更可靠，同时模型专注于解读结果并建议下一步行动。
- 围绕完整工作流设计智能体。智能体需要找到合适的工具，在明确的权限范围内工作，并从分析转向行动。这意味着提出广告活动变更建议，将其提交人工审批，并验证变更是否正确应用。
- 使用抽象来聚焦智能体的核心任务。Managed Deep Agents 负责托管、沙箱、Slack 集成和调度，因此你可以专注于让智能体发挥作用的工具、上下文和决策规则。

在 LangChain 成立的前三年，我们的销售管道主要通过开源、内容、YouTube、社区和聚会自然增长。今年 1 月，我们希望启动付费广告计划，开始触达我们未能通过自然渠道覆盖的潜在客户，例如新地区和企业的决策者。

我们希望在短短六个月内，从主要依靠自然增长的引擎扩展到五个付费渠道。这给我们小型营销团队带来了新的挑战。我们必须跟踪各渠道启动的新广告活动、不同的创意和定向实验，以及不断增长、需要理解和采取行动的绩效数据。

为了扩展和优化，我们需要克服一些技术障碍。每个广告平台都有自己的数据模式，这使得跨渠道的效果对账变得困难。活动参数也无法清晰地映射到我们最终关心的结果，例如销售线索、注册或内容下载。随着我们公司的产品发布节奏加快，活动数量不断增加，手动跟踪正在运行的内容、哪些有效以及下一步该尝试什么变得越来越难以管理。

我们着手构建一个代理来帮助管理这种复杂性。它会跟踪新产品发布、起草活动、添加关键词、测试变体，并将提议的实验提交给团队审批。随着时间的推移，它将作为一个持续学习的循环运行：分析效果、做出更改、观察结果、记录所学内容，并将这些洞察应用于未来的活动。我们的目标是让营销团队更高效，同时持续提升活动效果。

在这篇文章中，你将了解我们的付费媒体代理如何运作、它如何支持营销团队，以及我们在构建它时对代理工程学到了什么。

> 我们已将付费媒体代理开源，因此你可以将其作为自己项目的起点。你也可以参加 9 月 23 日太平洋时间上午 11 点举行的 GTM Engineering Live：我们如何构建付费媒体代理。在这次网络研讨会中，我们将演示该代理，讲解代码和设计决策，并回答有关如何将这些模式应用到你自己代理中的问题。

#### Key results

- 付费媒体在六个月内从推动我们营销管道的 0%增长到 20%。
- 从 6 月到 8 月，每个合格线索的成本（CPL）下降了 30%，而月度支出增长了约 60%。在 LinkedIn——我们最大的社交渠道上，CPL 比 1 月份低了 40%。
- 通过将分析和报告工作内部化，不再依赖代理机构，我们每月节省了约 5000 美元。
- 我们还通过将计算移入代码并移除不必要的模型调用，优化了代理本身，使早期报告工作流的成本降低了约 40 倍，速度提升了 13 倍，运行时间从 18 分钟缩短至 85 秒。

#### What we built

付费媒体代理是一个长期运行的代理，驻留在 Slack 中。每周一，它会将广告平台数据与我们仓库中的线索和销售管道数据相结合。它为每个平台发布一份摘要和一份品牌 PDF，说明发生了什么变化、原因以及团队接下来应该做什么。

团队可以在话题中标记它，询问有关广告活动、成本或销售管道的后续问题。它还可以根据我们的行动手册和编码判断，提出新的关键词、定向调整、广告文案或新的搜索广告活动建议。

#### How we built it

我们围绕一个简单原则构建了这个 agent：编码 agent 就是知识工作者。

知识工作通常涉及读取文件、转换信息、运行分析和记录内容。编码 agent 也会通过文件和 Shell 完成这些任务。

我们把 agent 当作一名新的付费媒体分析师。我们给它一台电脑、完成工作所需的软件、对我们数据的访问权限，以及关于我们业务如何运作的文档。

![](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/6aa748ed8b001558f0c49daa_3ff.png)

##### The Operating System

我们使用 LangChain Deep Agents 作为 agent harness，这样就不必从零构建核心 agent 基础设施。就像操作系统一样，Deep Agents 管理对文件、代码执行和工作记忆的访问。它为模型提供工具来规划工作、将任务委派给子 agent，并在任务变得更复杂时管理上下文。这个基础就是 agent harness。我们在其上叠加我们的付费媒体工具、技能和业务知识。

##### The Computer

每次运行默认都有一个 LangSmith Sandbox 可用。它是一个隔离的 microVM，拥有 32 GB 磁盘和一个用于运行命令的 shell。该沙箱为 agent 提供了一个安全、隔离的环境来执行代码和处理文件，而不会影响其他运行或底层系统。

我们为其配备了 pandas 和 DuckDB 用于分析，openpyxl 用于电子表格，以及 WeasyPrint 和 Jinja2 用于生成报告。除了这些软件之外，还有它的工作数据和业务知识，以 Markdown 格式存储在六项技能和一份十九页的 wiki 中。

为了保持快速启动，我们将软件和业务 wiki 烘焙进一个快照中，这是沙箱启动时所基于的已保存镜像。这将平均启动时间缩短了 10 秒。

> 💡 不同的 agent 需要不同的计算机。我们的内容生成 agent 的沙箱更像是一个视频编辑工作站，配有 headless browser、ffmpeg、媒体工具和品牌手册。财务 agent 可能需要 openpyxl 来处理电子表格，以及 DuckDB 来进行更繁重的数据处理。任务决定了你如何设计这台计算机。

##### Providing the right context

一旦智能体拥有了计算机，下一个挑战就是为它提供正确的上下文。人类分析师需要理解自己的角色、所使用的方法、所服务的公司、当前正在发生的事情，以及需要遵循的规则。

最朴素的做法是将所有这些都放入系统提示词中。然而，这会导致提示词过于冗长，每次运行时都携带它成本高昂，而且很可能很快就会过时。

看待这个问题的更好方式是：上下文窗口往往才是瓶颈，而不是模型。许多表面上的推理失败实际上是上下文失败。要么是模型缺少正确的信息，要么是太多无关信息在争夺它的注意力。

我们不把提示词当作知识存放的地方，而是把它当作一张地图。知识存放在具有可预测位置的结构化文件中，智能体只加载当前任务所需的上下文。

![](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/6aa758225bb405f1d1df0b19_agent-desktop-light-2x.png)

> 💡 设计智能体工作空间的方式，值得你投入与为其提供工具同等的思考。我们发现，智能体能够通过组合桌面上已有的内容，回答我们从未构建过明确工作流的问题。它有指导调查的剧本、可供使用的活动数据，以及用于分析这些数据的库。设计这个工作空间，成为了设计智能体本身的一部分。

我们将上下文分为五层，下面逐一描述（按每层变化的速度排序）：

- 系统提示词：定义智能体的角色和导航方式。我们的提示词以一句话描述智能体的角色开头，随后是三个简短的部分：如何操作、数字从何而来，以及如何呈现结果。其余内容都是给智能体的指引，例如剧本在这里、wiki 在那里、先读索引。提示词告诉智能体在哪里找到它需要的东西。
- 技能：六个指令文件夹，在运行时逐步披露。智能体最初只能看到每个文件夹的标题和描述。
- Wiki：十九页文档，解释我们的漏斗如何运作、每个广告系列旨在实现什么目标、哪个数据源拥有哪个数字，以及团队做出了哪些决策及其原因。
- 实时工具：支出、设置和管道每天都在变化，因此智能体在请求时获取它们。我们有 218 个这样的调用。关于我们如何防止其膨胀上下文，详见下文。
- 确定性代码：我们将代码用于任何应当一致且可复现的内容，包括计算、日期窗口、账户匹配和硬性保障措施。例如，一条防止智能体在一个糟糕的周之后削减顶级管道驱动因素的规则在代码中强制执行，因此模型无法覆盖它。最难划清的界限是技能与 wiki 之间的界限。技能解释如何完成工作：读取数据、运行数字、撰写报告、准备变更，并应用解读付费媒体表现的行动手册。它不包含任何针对我们广告系列的具体内容。

![](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/6aa74e154777aad146e92b1f_6ff.png)

wiki 是 LangChain 特有的一切：哪个广告系列用于品牌认知，哪个应该推动演示请求，我们在七月决定了什么，以及为什么。

> 💡 技能应当“能在其他公司使用”，而 wiki 则不应如此。换句话说，技能捕捉的是可复用的工作方式，而 wiki 则包含这些技能运作所需的公司特定背景。

这遵循了 Karpathy 的 LLM wiki 笔记以及我们自己的 Wiki Memory 中的模式。

##### 统一 agent 架构

我们最初构建了两个 agent 图，因为用户体验看起来不同：

- 每周报告代理是按计划运行的，且产物繁重。它使用了 Deep Agent、沙箱、大模型和 PDF 生成。
- Slack 需要在几秒内给出答案，因此它在更便宜的模型上使用了轻量级循环，搭配 Google Ads 和仓库工具，没有沙箱，并且只有只读访问权限。

这种拆分只持续了五周。每项新能力都必须实现两次。功能到达 Slack 和报告的时间不同。Slack 无法处理附件，因为它没有沙箱；它也无法回答关于周一报告的后续问题，因为这些 PDF 来自另一个图。

错误在于把它们当成了两个产品。它们是同一个分析的两个入口，背后由同一个 wiki、技能、工具和源规则支撑。我们改为为每个请求隔离状态和能力。每个线程都有自己的沙箱和检查点，每次运行只能看到它需要的工具。

现在有一个图，每次请求都会重新实例化：

- Slack 提及和 Monday 定时任务以不同的运行模式进入。
- 定时运行只看到一个工具 task()，它为每个平台委派一个子代理。
- Slack 获得更广泛的一组读取、仓库和活动操作工具。

![](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/6aa74e3527f3ee081d22cefc_7ff.png)

它是在 LangSmith Deployment 上托管的、具有不同能力配置文件的同一运行时，由后者负责托管、扩缩容和定时运行。而且，由于 Slack 现在共享同一套沙箱化架构，该 agent 还能打开报告 PDF，并在生成该报告的线程中回答后续问题。

> 💡 要点：为每个入口点使用一个运行时，并为其配置相应的能力配置文件。同一个工厂可以为不同用户赋予不同的技能和权限。

![](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/6aa84e164a42b1a8634d1fbb_mda-card-light-10240x4464.png)

#### Key technical lessons

让这个 agent 投入实际工作后，我们学到了五条经验：如何把数字做对、如何回答我们未曾预料到的问题，以及如何把分析转化为行动。

##### 1\. 用模型做判断，而不是做计算

我们第一版的每周分析让模型包办了一切。我们把每一行广告活动数据、关键词、管道记录和落地页检查都加载到上下文中，然后让它计算支出、周环比变化、对广告活动表现进行分类，并撰写报告。

它确实能运行，但效率很低。在我们冻结的测试集上，单份报告处理了约 390 万个输入 token，因为模型必须读取所有原始数据，并反复自行完成计算。这使得每次运行都更慢、更昂贵，耗时 1,112 秒，成本略高于 3 美元。这也让结果更难被信任，因为模型每次都要负责重新计算底层数字。

我们发现代码更适合处理确定性的工作。现在由 Python 获取数据、对齐日期窗口、计算总计和对比、应用固定规则，并将一组紧凑的结果写入沙箱。随后，模型专注于需要判断力的工作：串联证据、解释可能的原因、根据目标评估广告活动，并建议下一步该做什么。

##### 2\. 为每个指标定义唯一可信来源

我们有六个平台，每个平台都有不同的 ID、转化定义、归因窗口和广告系列层级。试图把所有内容标准化为一个完美的 schema，只会增加复杂性，却未必能让数据变得更可信。

相反，我们定义了每类指标应该信任哪个系统。广告平台是媒体活动的真实来源，例如花费、展示次数和点击次数。一旦有人完成转化，我们就依赖我们的数仓来获取下游结果，例如导语、商机和销售管道。

当一些 Google 视频广告系列无法清晰地映射到我们的数仓时，我们明白了为什么这一点很重要。我们的数仓使用关键词来关联广告系列数据，但视频广告系列并不总是有关键词。结果，尽管 Google 本身拥有正确的花费数据，我们数仓中仍缺失了大约 10%的 Google 花费。Meta 则有相反的局限：它可以告诉我们某个广告产生了转化，但我们的数仓更擅长告诉我们那个转化实际上是什么，例如是“联系销售”请求，还是“注册”。这些例子进一步说明了，为什么我们不应该期望一个系统对每项指标都给出最佳答案。

我们将这些“唯一真实来源”规则编码进了 agent 中。它们存放在 wiki 里，我们会移除那些会让 agent 针对给定指标查询错误系统的工具。有了来源边界、转化映射和广告系列层级定义，agent 就可以跨平台工作，而不需要一套完美归一化的 schema。

当数据无法可靠关联时，agent 不会试图填补这些缺口。它会保留这些限制，并在回答中包含相关来源、日期窗口和归因模型，以便团队能够理解每个数字是如何得出的。

##### 4\. 明确设计隔离机制

转向共享运行时后，我们又面临另一个挑战：智能体如何在不将所有平台数据塞入单一上下文窗口的情况下，分析五个平台？

我们在实时数据上测试了三种架构：

1. 每个平台独立运行一次。
2. 一个代理处理所有平台。
3. 一个父代理将任务委派给每个平台对应的一个子代理。

独立运行是最简单的架构，但在实际工作流程中表现最差。每次运行只能看到一个平台，因此系统会产生多条 Slack 消息，并且难以综合跨渠道的表现。

两种整合方案都生成了包含跨平台综合分析的单一输出。我们最终选择了父代理加子代理的架构，因为它让父代理的上下文保持精简，同时为每个平台提供独立的上下文窗口，以容纳平台特定的数据和注意事项。

但独立的上下文窗口并没有自动为我们带来完全隔离。我们仍然必须进行设计。

For example:

子代理为你提供了一个独立的上下文窗口。隔离模型的其余部分由你决定。你仍然需要定义它可以使用哪些工具、可以访问哪些文件和状态、必须返回什么，以及如何处理失败。

##### 5\. 为智能体提供从分析到行动的路径

仅分析性能的智能体最终只是一个更好的仪表板。我们希望智能体能够帮助团队根据其发现采取行动。

它可以直接在 Slack 中提出变更建议，例如添加关键词、更新地理定位或创建新的搜索广告系列。

赋予智能体采取行动的能力也引入了一项新要求：权限。

付费媒体之外的团队可以使用该代理询问有关广告活动效果和销售管道的问题，但只有指定的团队成员才能编辑或批准广告活动变更。服务器在接受任一操作前会检查 Slack 用户 ID。来自其他任何人的请求都会被阻止，提案则保持待处理状态。

每个提议的变更都会显示在一张使用 Block Kit 构建的 Slack 审批卡片中。获得授权的审核者可以比较当前值与提议值、进行编辑，并批准最终方案。随后，代码会应用已批准的变更，并检查广告平台以确认操作成功。

![](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/6aa74e774a80b7db80002813_9ff.png)

这为我们带来了有用的职责分离。代理可以分析效果并建议操作，但由人来控制该操作是否真正被执行。

##### 6\. 让界面匹配工作需求

Slack 之所以能成为第一个合适的界面，是因为审批卡片可以和促成它的分析与讨论存在于同一个会话线程中。跨团队的人可以提问并发表意见，而广告活动负责人仍然掌控着哪些更改真正被应用。

这种方式最适合相对聚焦的决策。随着智能体开始处理更复杂的工作，例如包含许多广告组和创意的广告活动、批量编辑，或需要多轮修订的计划，Slack 作为主要工作空间就变得更难使用。

我们正在将这些更复杂的工作流迁移到一个围绕智能体构建的专用界面中，同时保留 Slack 作为一个轻量级场所，用于提问、查看建议和批准更改。更多内容将在后续文章中介绍。

#### What’s next

如今，该代理主要响应定时运行和来自团队的请求。我们希望它能变得更加主动，通过持续监控广告活动表现、呈现值得关注的变动，并为团队提出新的实验和优化建议以供审核。

更大的机会在于将这些洞察贯穿整个 GTM 体系。广告活动的互动情况可以为销售跟进方式提供参考，而管道进展、销售对话和交易结果则能加深我们对理想客户的理解，并影响下一次广告活动。

随着时间的推移，我们希望我们的 GTM 代理能够为同一套共享知识和行动手册做出贡献，这样组织某一部分学到的东西就能改善漏斗其余部分的定向、信息传递和实验。

## 结构化（1）

### 2026-09-18 01:53:12

#### LangChain 如何构建付费媒体智能体

LangChain 将 AI 智能体当作一名 “付费媒体分析师” 来设计：为它提供隔离的工作环境、分析软件、业务知识和明确权限，让模型负责判断，代码负责计算与安全控制。该系统帮助团队在六个月内扩展到五个付费渠道，同时降低获客和运营成本。

##### 背景：付费渠道扩张带来管理压力

LangChain 前三年的销售管道主要来自开源、内容、YouTube 和社区等自然渠道。为了覆盖新地区和企业决策者，公司计划在六个月内拓展五个付费渠道。

随之而来的问题包括：

- 不同广告平台的数据结构、转化定义和归因方式不一致；
- 广告活动参数难以直接对应线索、注册和销售管道；
- 活动、创意和定向实验快速增加，人工跟踪越来越困难。

因此，团队构建了一个长期运行的付费媒体智能体，希望形成 “分析效果 — 提出调整 — 执行变更 — 观察结果 — 积累经验” 的持续优化循环。

##### 实际成果：管道贡献提高，成本明显下降

上线六个月后：

- 付费媒体对营销管道的贡献占比从**0% 提升至 20%**；
- 6 月至 8 月，月度支出增长约**60%**，但每条合格线索成本（CPL）下降**30%**；
- LinkedIn 的 CPL 比 1 月下降**40%**；
- 分析和报告转为内部完成后，每月节省约**5000 美元**的代理机构费用；
- 优化智能体后，早期报告流程的成本降低约**40 倍**，速度提升**13 倍**，运行时间从**18 分钟缩短至 85 秒**。

##### 产品形态：在 Slack 中完成分析、问答与提案

智能体常驻 Slack，每周一自动把广告平台数据与公司数据仓库中的线索、商机和销售管道数据结合起来，为各平台生成：

- 数据变化摘要；
- 对变化原因的解释；
- 下一步行动建议；
- 品牌化 PDF 报告。

团队还可以在 Slack 话题中追问广告活动、成本和销售管道情况。智能体也能依据行动手册提出新关键词、地理定向、广告文案或搜索广告活动建议。

##### 核心设计：把智能体当作知识工作者

团队没有只给模型一段超长提示词，而是像培养新分析师一样，为它配置完整工作空间：

- **运行底座**：使用 LangChain Deep Agents 管理文件、代码执行、记忆、任务规划和子智能体；
- **隔离电脑**：每次运行使用独立的 LangSmith Sandbox，提供 32GB 磁盘和 Shell，避免影响其他任务或底层系统；
- **分析软件**：使用 pandas、DuckDB、openpyxl 等处理数据和表格，使用 WeasyPrint、Jinja2 生成报告；
- **业务知识**：用六套 “技能” 和一份 19 页的公司 wiki 提供方法与背景；
- **预制快照**：把软件和 wiki 预装进沙箱镜像，平均减少约 10 秒启动时间。

作者强调，不同智能体需要不同的 “电脑”。例如，内容智能体可能需要浏览器、ffmpeg 和品牌手册，财务智能体则更依赖表格和数据库工具。

##### 上下文设计：提示词是地图，不是知识仓库

团队认为，很多看似 “模型推理失败” 的问题，其实是上下文问题：要么缺少必要信息，要么无关信息太多。

因此，他们没有把全部知识塞进系统提示词，而是分成五层：

1. **系统提示词**：只定义角色、工作方式、数字来源和结果格式，并告诉智能体去哪里找资料。
2. **技能**：说明如何读取数据、分析指标、写报告和准备变更，属于可跨公司复用的方法。
3. **Wiki**：记录 LangChain 特有的业务背景，如各广告活动的目标、历史决策及其原因。
4. **实时工具**：按需获取不断变化的支出、广告设置和销售管道数据。
5. **确定性代码**：负责计算、日期范围、账户匹配和硬性安全规则。

技能与 wiki 的区别是：**技能描述通用工作方法，wiki 保存公司专属知识**。智能体只在需要时读取相关内容，以减少上下文负担。

##### 架构演进：从两个智能体合并为一个运行时

最初，团队为两类入口分别建立系统：

- 定时生成报告的重量级智能体；
- 在 Slack 中快速回答问题的轻量级智能体。

五周后，这种拆分暴露出问题：每项能力都要开发两次，两个入口功能不同步；Slack 无法处理附件，也无法回答另一套系统生成的报告。

团队随后改为统一运行时，并按请求配置不同能力：

- 定时任务只获得生成各平台报告所需的工具；
- Slack 请求获得更广泛的读取、查询和活动操作能力；
- 每个线程拥有独立沙箱和检查点；
- 同一个智能体可以打开报告 PDF，并在原线程中回答追问。

核心原则是：**不同入口不必对应不同产品，可以共用一个运行时，再按用户和场景限制技能与权限。**

##### 技术经验一：模型做判断，代码做计算

第一版让模型读取全部原始数据并完成统计、分类和报告写作。单份报告约处理**390 万个输入 token**，耗时**1112 秒**，成本超过**3 美元**，而且底层数字由模型反复计算，难以保证一致性。

优化后：

- Python 负责取数、统一日期、计算总计与环比、应用固定规则；
- 模型负责解释原因、关联证据、评估活动是否符合目标，并建议下一步行动。

这样既降低了成本和延迟，也提高了结果的可复现性。安全规则同样写进代码，例如不能因为某一周表现不佳，就随意削减长期贡献最大的广告活动。

##### 技术经验二：每类指标只认一个可信来源

团队没有强行把六个平台统一成一个 “完美数据模型”，而是明确每类指标应相信哪个系统：

- 花费、展示、点击等媒体指标，以广告平台为准；
- 线索、商机和销售管道等转化后结果，以数据仓库为准。

例如，部分 Google 视频广告没有关键词，而数据仓库依赖关键词关联活动，因此漏掉了约**10% 的 Google 花费**；Meta 能说明广告产生了转化，但数据仓库更适合判断该转化究竟是 “联系销售” 还是 “注册”。

这些来源规则被写入 wiki 和工具权限中。当数据无法可靠关联时，智能体不会自行补齐，而会说明数据来源、日期范围、归因方式和限制。

##### 技术经验三：多智能体需要显式隔离

为了分析五个平台，团队测试了三种方式：

- 每个平台单独运行；
- 一个智能体处理所有平台；
- 父智能体把任务分派给各平台子智能体。

最终选择第三种。父智能体负责跨渠道综合判断，子智能体各自拥有独立上下文，处理平台特有的数据和规则。

但子智能体并不会天然实现完全隔离，仍需明确规定：

- 可以使用哪些工具；
- 可以访问哪些文件和状态；
- 必须返回什么结果；
- 失败时如何处理。

##### 技术经验四：智能体必须能从分析走向行动

只做分析的智能体，本质上仍是一个更智能的仪表板。因此，该系统允许智能体提出关键词、定向和新广告活动等变更，但执行采用 “人机协作” 机制：

1. 智能体在 Slack 中生成审批卡片，展示当前值和建议值；
2. 服务器检查操作者的 Slack 用户 ID；
3. 只有指定成员可以编辑或批准；
4. 代码执行获批变更；
5. 系统再次查询广告平台，确认变更已经生效。

这种方式把职责分开：**智能体负责分析和建议，人类保留最终决定权。**

##### 界面选择：Slack 适合轻量协作，复杂任务需专用界面

Slack 适合问答、讨论和审批，因为分析依据、团队意见和审批操作可以留在同一线程中。

但当任务涉及大量广告组、创意、批量编辑或多轮修改时，Slack 就不再适合作为主要工作区。团队正在把复杂流程迁移到专用界面，同时保留 Slack 用于提问、查看建议和批准变更。

##### 下一步：从被动响应走向主动优化

目前，智能体主要响应定时任务和团队请求。未来计划让它持续监控广告表现，主动发现异常、提出实验和优化建议。

更长期的目标是打通整个 GTM（市场进入与商业增长）体系：让广告互动影响销售跟进方式，同时让销售对话、管道进展和成交结果反过来改善客户定位、营销信息和下一轮广告实验。最终，不同业务智能体将共享同一套知识和行动手册，使一个环节获得的经验能够改善整个漏斗。

## 深度解读（1）

### 2026-09-18 02:45:42

#### 真正可用的智能体，不是更长的提示词，而是一套可审计的工作环境

LangChain 这篇文章最有价值的，并不是“AI 帮公司投广告”的案例本身，而是它展示了一种更成熟的智能体工程观：**把智能体当作一名需要电脑、资料、权限和操作流程的知识工作者，而不是一个套上工具的聊天模型。**

业务结果看起来不错：六个月内付费媒体贡献了 20% 的营销管道，支出增长约 60% 的同时，合格线索成本下降 30%；报告流程也从 18 分钟缩短到 85 秒，成本降低约 40 倍。不过，这些数字不能直接证明智能体带来了营销增量——渠道扩张、投放经验积累和素材优化都可能发挥作用。真正证据充分的，是其系统效率与工作方式的改善。

##### 提示词应该是地图，而不是仓库

团队最初面对的核心问题不是模型不够聪明，而是信息复杂：五个渠道、不同数据结构、持续变化的活动，以及大量公司特有的历史决策。把这些全部塞进提示词，不仅昂贵，也会让过时或无关信息争夺模型注意力。

他们因此把上下文按变化速度分层：系统提示词只定义角色和导航方式；“技能”保存可复用的方法；Wiki 记录公司特有的业务背景与历史决策；实时工具获取不断变化的数据；代码处理必须稳定执行的规则。一个很实用的边界是：**技能应当能迁移到别家公司，Wiki 则不应当。**

这修正了一个常见误解：很多所谓“推理失败”，其实是上下文失败。模型不是不会分析，而是不知道该信哪份数据，或者在过量材料里找不到关键事实。对智能体产品而言，知识如何组织、何时加载、由谁更新，和工具能力本身同样重要。

##### 让模型处理歧义，让代码负责确定性

第一版系统让模型读取全部原始数据、计算指标、分类表现并撰写报告，单次消耗约 390 万输入 token。后来团队把日期对齐、汇总计算、账户匹配和硬性规则交给 Python，只让模型解释变化、连接证据并提出建议。

这不是简单的性能优化，而是一条可迁移的架构原则：**计算、权限、来源规则与安全边界应该可复现；只有需要结合情境判断的部分才交给模型。**例如，“一次糟糕的周表现不能触发削减核心管道渠道”被写成代码，因此模型无权绕过。

同样重要的是，他们没有强行建立一个“完美统一”的跨平台数据模型，而是为每类指标指定可信来源：花费和点击信广告平台，线索质量和销售管道信数仓；无法可靠关联时明确暴露缺口，而不是让模型补全。相比表面整齐的数据平台，这种做法更适合真实企业环境，因为它保留了数字的来源、归因窗口和可信边界。

##### 智能体的终点不是回答，而是完成闭环

如果系统只能解释广告表现，它本质上仍是一个更会说话的仪表盘。这个案例真正向前走了一步：智能体可以提出关键词、地域定向和广告活动调整，经授权人员在 Slack 审批后，由代码执行并回查平台确认结果。

这里形成了清晰的职责分离：模型负责发现和提议，人负责承担决策责任，代码负责准确执行与验证。Slack 适合小范围讨论和单次审批，但面对批量编辑、多轮修改和复杂计划时，团队也承认需要专用界面。这说明“对话式”并非智能体产品的最终形态，**界面应由任务复杂度决定，而不是由 AI 的交互潮流决定。**

这篇文章留下的关键判断是：企业智能体的竞争力，很可能不主要来自换用更强模型，而来自能否构建一套可靠的工作环境——知识有位置、数字有来源、权限有边界、行动可审批、结果可验证。只有这些条件具备，智能体才会从演示中的聪明助手，变成组织里真正可托付工作的角色。

## 默认总结（1）

### 2026-09-18 02:50:05

##### 一句话看懂

LangChain 把付费广告代理当作“配有电脑、资料和操作规范的分析师”：让代码负责准确计算，让模型负责判断和建议，再通过人工审批把分析转化为实际操作。

##### 关键内容

- **公司自述成效明显**：半年内付费媒体贡献的营销管道占比从 0% 升至 20%；6—8 月合格线索成本下降 30%。代理工作流经优化后，成本约降 40 倍，耗时由 18 分钟缩至 85 秒。但这些数据不能证明增长完全由代理带来。
- **上下文比“大提示词”更重要**：系统提示只充当导航地图，具体知识按“通用技能、公司 Wiki、实时数据、确定性代码”分层存放，需要时再读取，避免信息过载。
- **模型与代码各司其职**：Python 负责汇总、日期对齐、规则和安全限制；模型负责解释原因、综合证据和提出建议。不同指标还要指定唯一可信数据源，不可靠的数据不强行补齐。
- **必须打通行动与权限**：代理可在 Slack 提议改关键词、定向或广告，但只有授权人员能审批；代码执行后还会验证结果，实现“代理建议、人类决策”。

##### 通俗解读

重点不是换一个更强模型，而是给代理搭好“办公室”：工具、文件、业务手册、权限和审批流程都要明确。**值得代理开发者细读**，尤其是上下文设计、父子代理隔离和人工审批部分；若只关心营销效果，浏览关键结果即可。原文摘录存在编号从 2 跳到 4、示例缺失等情况，内容可能不完整。

## 口播总结（1）

### 2026-09-20 00:28:36

LangChain 构建付费媒体代理后，得到的核心认识是：一个好用的智能体，不只是一个会聊天的模型，更像是一名真正的知识工作者。它需要合适的工作环境、可靠的数据来源、清楚的操作手册，以及从分析走向行动的明确路径。

LangChain 过去主要依靠开源项目、内容、视频和社区活动自然获客。后来，公司希望在半年内拓展到五个付费广告渠道，触达新地区和企业决策者。

问题很快出现了。每个广告平台的数据结构都不同，广告参数也很难直接对应到销售线索、注册和销售管道。随着产品发布和广告实验越来越多，小型营销团队很难持续追踪：现在有哪些广告在运行，哪些有效，下一步又该测试什么。

于是，LangChain 构建了一个常驻在 Slack 聊天工具中的付费媒体代理。每周一，它会结合广告平台数据，以及公司内部的线索和销售管道数据，为各个平台生成摘要和 PDF 报告。报告不只展示数字，还要解释发生了什么、可能是什么原因，以及团队接下来可以采取什么行动。

团队也可以在 Slack 对话中继续追问。代理能够建议新关键词、调整地域定向、修改广告文案，或者创建新的搜索广告活动。

六个月后，付费媒体贡献的营销管道占比，从零增长到百分之二十。从六月到八月，每条合格销售线索的成本下降了百分之三十，同时月度广告支出增加了约百分之六十。在最大的社交广告渠道领英上，每条合格线索的成本比一月份低了百分之四十。分析和报告转为内部完成后，每月还节省了大约五千美元的代理机构费用。

这些业务成果背后，最重要的设计原则，是把代理当成一名新入职的付费媒体分析师。

LangChain 给代理准备了一台隔离的虚拟计算机，也就是沙箱。沙箱里装有数据分析、电子表格处理和报告生成软件，还有完成工作所需的数据与业务文档。这样，代理可以读文件、运行代码、分析数据和生成报告，同时不会影响其他任务或底层系统。

不过，有电脑和工具还不够。更难的问题，是如何给代理提供恰当的上下文。

最直接的做法，是把所有业务知识都塞进系统提示词。但这样会让提示词越来越长。每次运行都要重复读取，成本高，而且内容很快就会过时。

LangChain 的判断是，很多看起来像模型推理失败的问题，其实是上下文失败。模型要么缺少关键信息，要么被大量无关信息分散了注意力。

因此，系统提示词不再充当知识仓库，而是充当一张地图。它只告诉代理自己的角色、基本操作规则，以及到哪里寻找资料。真正的知识放在结构化文件中，代理只在需要时加载。

这些资料分成不同层次。可复用的工作方法，被写成六组“技能”，例如怎样读取数据、计算指标、撰写报告和准备广告变更。公司特有的信息，则存入一份十九页的内部知识库，包括每个广告活动的目标、数据来源、过去做过什么决定，以及为什么这样决定。

一个简单的区分方法是：技能应该能够拿到其他公司继续使用；知识库则只对 LangChain 自己有意义。

另一个关键经验，是让模型负责判断，让代码负责计算。

早期版本把原始广告数据、关键词、销售管道记录和网页检查结果全部交给模型。模型既要算支出和周环比变化，又要判断广告表现并撰写报告。虽然能够运行，但单次报告要处理大约三百九十万个输入词元，耗时约十八分钟，成本超过三美元。更麻烦的是，底层数字由模型反复计算，结果难以稳定复现。

后来，团队把确定性的工作交给 Python 代码。代码负责获取数据、对齐日期范围、计算总计和变化、匹配账户，并执行固定的安全规则。模型只读取压缩后的结果，再去串联证据、解释原因、判断广告是否符合目标，并提出下一步建议。

改造后，报告运行时间从十八分钟降到八十五秒，速度提高了十三倍，成本降低了约四十倍。这里的要点很清楚：凡是必须一致、准确和可复现的工作，优先使用代码；凡是需要解释、权衡和判断的工作，再交给模型。

数据来源也必须提前划清边界。广告平台最适合提供花费、展示次数和点击次数。用户完成转化之后，内部数仓更适合判断这次转化究竟是注册、联系销售，还是进入了销售管道。

例如，部分谷歌视频广告没有关键词，内部数仓无法正确关联，导致大约百分之十的谷歌广告花费缺失。谷歌平台本身却有正确的花费数据。Meta 的情况正好相反。它能说明某条广告带来了转化，但内部数仓更擅长解释这次转化的实际类型。

所以，团队没有强求一个系统回答所有问题，也没有追求一套看似完美的统一数据格式。相反，他们为每类指标指定唯一可信来源，并把这些规则写进代码和知识库。如果数据无法可靠关联，代理不会自行填补空白，而是明确说明数据来源、时间范围和归因方式。

代理还必须从分析走向行动。否则，它最终只是一个更聪明的仪表板。

这个代理可以在 Slack 中提出添加关键词、调整地域定向或创建广告活动的建议。但它不能自行执行所有操作。服务器会检查用户身份，只有指定成员可以编辑或批准变更。审批者能够比较当前设置和建议值，也可以修改方案。只有人工批准后，代码才会应用变更，并再次检查广告平台，确认操作是否成功。

这种设计形成了清楚的职责分离。代理负责分析和提出建议，人类负责决定是否真正执行。

最值得记住的是三点。系统提示词应该是地图，而不是塞满全部知识的仓库。模型适合做判断，代码适合保证计算、规则和安全措施的一致性。真正有价值的智能体，还必须覆盖完整工作流，从获取信息、分析问题，到提出行动、接受审批，再验证行动是否正确完成。

## 深度解读-口播（1）

### 2026-09-30 12:01:27

一个人工智能体，要怎样才能从“会写分析报告”，变成真正能帮团队做事的同事？LangChain 构建付费广告智能体的经验是：关键不只是模型有多聪明，而是有没有给它合适的工作环境、可信的数据，以及从建议走向执行的明确规则。

当时，LangChain 希望在六个月内，把主要依靠自然增长的营销体系，扩展到五个付费渠道。对一个小型团队来说，难点不只是投放广告，而是持续弄清楚：哪些活动在运行，哪些实验有效，接下来应该改什么。各平台的数据格式不同，广告里的“转化”，也不一定能直接对应到公司真正关心的销售线索和商机。

他们构建的智能体，驻留在团队聊天工具 Slack 中。每周一，它把广告平台数据与公司数据仓库里的线索、销售管道数据结合起来，生成报告。团队可以继续追问，也可以让它提出关键词、广告文案和定向调整建议。

团队报告，在这六个月里，付费媒体对营销管道的贡献占比，从零增长到百分之二十。六月到八月，每个合格销售线索的成本下降了百分之三十，同时月度广告支出增加了约百分之六十。不过，这些是整个付费营销计划的结果，不能简单理解成智能体单独带来的提升。更值得借鉴的，是它背后的设计。

他们的第一个认识，是把智能体当作新入职的分析师，而不是一个等待提问的聊天框。

人类分析师需要电脑、软件、数据和业务文档，智能体也一样。LangChain 给它准备了一个隔离的运行环境，也就是沙箱。智能体可以在里面读取文件、运行代码、分析数据、生成报告，而不影响底层系统或其他任务。

但有了工具，还不等于知道怎么工作。分析师还要理解公司的目标、广告活动的用途，以及团队过去为什么做出某个决定。

最直接的办法，是把这些内容全部塞进系统提示词。问题是，提示词会越来越长，每次运行都要重复携带，而且内容容易过时。作者认为，很多看似是模型推理能力不足的问题，其实是上下文出了问题：要么缺少关键资料，要么无关信息太多，挤占了模型的注意力。

因此，他们把系统提示词当成地图，而不是仓库。提示词只说明角色、基本规则，以及去哪里找资料。具体知识放在结构清楚的文件中，需要时再读取。

其中一个重要区分，是“技能”和“公司知识”。技能讲怎么完成工作，比如如何分析广告表现、撰写报告。公司知识则讲这家公司特有的背景，比如哪个活动负责品牌认知，哪个活动应该带来演示申请。前者可以复用到别的公司，后者不行。

说到底，智能体需要的不是一次性读完所有资料，而是在工作时，找得到正确的资料。

第二个认识，是让模型负责判断，让代码负责确定性的工作。

早期版本让模型包办一切：读取原始数据、计算支出、比较变化，再写报告。在固定测试集上，一份报告要处理约三百九十万个输入词元。词元可以粗略理解成模型处理文字时使用的小片段。单次运行耗时约十八分钟，成本略高于三美元。

问题不只是贵和慢。每次都让模型重新计算底层数字，也让结果更难被信任。

后来，他们改用代码获取数据、对齐日期范围、计算总量和变化，并执行固定规则。模型只读取整理好的结果，负责串联证据、解释可能原因，以及建议下一步行动。

这项调整让早期报告流程的成本降到了原来的约四十分之一，速度提升约十三倍，运行时间缩短到八十五秒。

这条分工很关键：能明确计算、必须重复一致的部分，交给代码；需要结合业务目标作判断的部分，再交给模型。

不过，计算正确还不够。数据来源错了，算得再准也没有用。

所以，他们为每类指标指定可信来源。广告花费、展示和点击，以广告平台为准。销售线索、商机和销售管道，则以公司数据仓库为准。

一个具体例子是，数据仓库通过关键词关联部分谷歌广告活动，但视频广告不一定有关键词。结果，仓库漏掉了大约百分之十的谷歌广告花费，而谷歌平台本身的花费数据是完整的。

另一个方向的问题是，广告平台可能知道有人完成了“转化”，却不如公司仓库清楚，这次转化究竟是注册，还是联系销售。

因此，可信数据不意味着把所有数字强行统一到一个系统里，而是明确每个数字该相信谁。遇到无法可靠关联的数据，智能体也不能自行补齐，而要说明来源、统计日期和归因限制。

有了可信分析，第三个问题才是：怎样把分析变成行动，又不失去控制？

这个智能体可以建议添加关键词、调整地域定向，或者创建搜索广告活动。但建议不等于执行。

每项变更都会生成审批卡片，让授权人员比较当前设置和建议设置，必要时修改，再批准。服务器会检查用户身份，未获授权的人不能编辑或批准。通过审批后，由代码应用变更，再向广告平台确认是否执行成功。

还有一些硬性保护直接写进代码。例如，不能因为某个重要广告活动一周表现不好，就削减这个主要的销售管道来源。模型不能越过这条规则。

这里形成了一条完整链路：智能体分析并提出建议，人决定是否执行，代码落实并验证结果。它不再只是一个更好的仪表板，但也不是一个可以自行改动广告预算的黑箱。

随着任务变复杂，他们还发现，共用知识和工具，不代表所有任务都该挤在同一个上下文里。

每周报告需要综合多个平台，聊天提问则需要及时回答。最初，他们为两种入口做了两套系统，结果新功能要重复开发，聊天中的智能体还无法回答报告的后续问题。

后来，两种入口改用同一套底层架构，但按请求分配不同权限和工具。跨平台分析则由主智能体协调，各平台的子智能体分别处理细节，再汇总结果。

不过，子智能体有独立上下文，并不自动意味着安全隔离。它能读哪些文件、用哪些工具、返回什么结果，以及失败后怎么办，都仍然需要明确设计。

这次实践最值得记住的，是三件事：像培养知识工作者一样，给智能体准备工作空间和业务背景；把计算、数据来源和硬性规则交给代码，把判断留给模型；再用人工审批和执行验证，把分析接到行动上。真正可靠的智能体，靠的不是一段万能提示词，而是一套清楚、可控的工作流程。
