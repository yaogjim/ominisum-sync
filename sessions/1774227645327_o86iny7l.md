## 正文

**陈成**

大多数人用 Claude Code，根本没打开过 .claude/ 文件夹。

这个文件夹是 Claude 的「控制中心」——它决定 Claude 懂不懂你的项目、遵不遵守你的规范、能不能自动完成复杂工作流。配好了是得力助手，没配就是一个记忆力极差的外包。

核心文件解析：

CLAUDE.md — 项目的「入职文档」。Claude 每次启动第一个读它，直接进系统 prompt。写什么它就遵守什么。建议控制在 200 行内：放构建命令、架构决策、约定规范、踩坑记录，不要放能用 linter 自动做的事。

rules/ — CLAUDE.md 变长后的解法。按关注点拆分成多个 .md 文件，还能设路径作用域——只有处理 src/api/ 下文件时才加载 API 规范，不会污染其他上下文。

commands/ — 自定义斜杠命令。review.md → /project:review，支持 !bash 执行并注入输出。但注意：最新版已将 commands 合并进 skills。

skills/ — 可复用工作流，核心区别在于由 Claude 自动触发，无需手动输入命令。每个 skill 是独立子目录，可以打包指令 + 支撑文件。

agents/ — 专职子 Agent。复杂任务时 Claude 会 spawn 一个独立上下文的 Agent 来处理，完成后压缩结果返回主会话。可以限制工具权限，可以指定更便宜的模型。

settings.json — 权限白名单/黑名单。allow 里的命令免确认，deny 里的永久封锁（比如 rm -rf \* 和 .env 读取），其余命令执行前询问。

还有两套目录：项目级 .claude/ 提交 git 全团队共享，全局 \~/.claude/ 存个人偏好跨项目生效。

起步不用一步到位：先 /init 生成 CLAUDE.md，精简到要点；配好 settings.json 的 allow/deny；再慢慢把 CLAUDE.md 拆进 rules/。

真正的结论：Agent 质量越来越是环境设计问题，不是提示词问题。把 .claude/ 配好，就是把 Claude 变成真正懂你项目的队友。

## 结构化（1）

### 2026-03-23 03:17:30

#### 文章主旨

这篇文章的核心观点是：很多人虽然在用 Claude Code，但并没有利用好 `.claude/` 这个真正决定效果的配置中心。作者认为，Claude 是否像“懂项目的队友”，关键不在提示词写得多花，而在于是否把运行环境和规则体系设计好。

##### 1. 为什么 `.claude/` 很重要

- 作者开篇指出，大多数用户其实没认真配置过 `.claude/` 文件夹。
- 这个文件夹相当于 Claude 的“控制中心”，决定了它：
  - 是否理解你的项目背景
  - 是否遵守团队规范
  - 是否能自动完成复杂工作流
- 如果没有配置好，Claude 就像“记忆力很差的外包”；配置好了，才会变成高效助手。

##### 2. `CLAUDE.md`：Claude 的“入职文档”

- `CLAUDE.md` 是最核心的文件，Claude 每次启动时最先读取。
- 它会直接进入系统 prompt，因此里面写的内容，Claude 会优先遵守。
- 作者建议控制在 **200 行以内**，重点写：
  - 构建命令
  - 架构决策
  - 项目约定
  - 常见踩坑记录
- 不建议把本来可以靠 `linter` 自动检查的内容塞进去，否则会浪费上下文。

**举例理解：**
如果你的项目要求“先跑测试再提交”“某个模块必须走指定接口层”，这些写进 `CLAUDE.md` 就很有用；但像“缩进 2 空格”这类格式规则，更适合交给自动化工具处理。

##### 3. `rules/`：解决 `CLAUDE.md` 过长的问题

- 当 `CLAUDE.md` 内容越来越多时，推荐拆到 `rules/` 目录。
- 做法是按关注点拆成多个 `.md` 文件，避免所有规则都堆在一个文件里。
- 还可以设置**路径作用域**：
  - 比如只在处理 `src/api/` 下文件时，才加载 API 相关规范
  - 这样不会把无关规则带进其他任务，减少上下文污染

**关键价值：**
- 规则更清晰
- Claude 读到的信息更精准
- 不同模块可以有不同规范，避免“一锅炖”

##### 4. `commands/` 和 `skills/`：把常用操作做成工作流

- `commands/` 用来定义自定义斜杠命令。
- 例如：`review.md` 可以映射成 `/project:review`
- 还支持 `!bash`，也就是执行 bash 命令，并把输出注入给 Claude 使用
- 不过作者特别提醒：**最新版已经把 `commands` 合并进 `skills`**

###### `skills/` 的特点
- `skills/` 是可复用工作流
- 与 `commands/` 最大不同是：**可以由 Claude 自动触发**
- 不需要用户每次手动输入命令
- 每个 skill 都可以是独立子目录，里面可打包：
  - 指令
  - 支撑文件
  - 工作流逻辑

**举例理解：**
比如你经常做“代码审查 → 跑测试 → 汇总风险”，就可以做成一个 skill，Claude 在识别到合适场景时自动调用，而不只是等你手输命令。

##### 5. `agents/`：让 Claude 调用“子 Agent”处理复杂任务

- `agents/` 用来定义专职子 Agent。
- 当任务复杂时，Claude 会启动一个独立上下文的 Agent 去处理子任务。
- 子 Agent 完成后，会把结果压缩总结，再返回主会话。

###### 这个机制的意义
- 能拆分复杂工作
- 主会话不会被过多细节淹没
- 可以更精细地控制不同 Agent 的行为

###### 作者提到的两个可控点
- 可以**限制工具权限**
- 可以给子 Agent 指定**更便宜的模型**

这意味着在成本和安全性上都更灵活。

##### 6. `settings.json`：管理权限边界

- `settings.json` 主要负责权限控制。
- 规则分成三类：
  - `allow`：白名单命令，执行时免确认
  - `deny`：黑名单命令，永久封锁
  - 其他命令：执行前询问用户

###### 文中举的危险例子
- `rm -rf *`
- 读取 `.env`

这些都适合放进 `deny`，避免误操作或泄露敏感信息。

**核心意义：**
Claude 不只是“能做什么”，还要明确“不能做什么”。

##### 7. 项目级与全局级配置要分开

作者提到有两套 `.claude/` 目录：

- **项目级 `.claude/`**
  - 提交到 git
  - 团队共享
  - 适合放项目规则和协作规范

- **全局级 `~/.claude/`**
  - 只作用于个人环境
  - 跨项目生效
  - 适合放个人偏好

**这相当于：**
- 项目级配置解决“团队共识”
- 全局级配置解决“个人习惯”

##### 8. 推荐的起步顺序：不要一开始追求完整

作者强调，不需要一步到位，建议按下面顺序逐步配置：

1. 先用 `/init` 生成 `CLAUDE.md`
2. 把内容精简到关键要点
3. 配好 `settings.json` 里的 `allow/deny`
4. 再慢慢把 `CLAUDE.md` 的内容拆到 `rules/`

这个建议很实际，因为很多人一开始就想把系统搭得很复杂，结果反而迟迟不落地。

##### 9. 作者真正想表达的结论

- 作者最后的核心判断是：**Agent 的质量越来越取决于环境设计，而不是提示词设计。**
- 换句话说，重点不只是“你怎么对 AI 说”，而是“你给 AI 提供了怎样的工作环境、规则和权限”。

**一句话概括：**
把 `.claude/` 配好，本质上是在把 Claude 从“临时助手”变成“真正懂你项目的队友”。

##### 10. 文末热门回复补充了什么

原文后的热门回复，进一步说明了这个观点正在被更多人验证：

  这说明“多 Agent 调度、工作流设计”已经成为热点方向。
- 另有回复发布新的 Skill：`baoyu-youtube-transcript`
  - 输入 YouTube URL
  - 直接抓取字幕
  - 生成带章节、发言人、封面图的文档
  - **不需要 API Key**
  这正是 `skills/` 可复用工作流价值的实际例子。
- 还有人提到 **60 分钟教程** 和 **Claude 101 课程**，说明生态正在快速成熟。
- 最值得玩味的一条回复是：
  > “CLAUDE.md 只是 externalized judgment（外化的判断）。”  
  > “价值不在文件本身，而在于撰写过程中被迫进行的思考。”

这句话其实是对全文的进一步提炼：配置文件不是魔法，真正的价值在于你借此把项目知识、规范和判断标准梳理清楚了。

##### 总结

- `.claude/` 不是可有可无的辅助目录，而是决定 Claude Code 使用效果的核心基础设施。
- 文中重点介绍了 `CLAUDE.md`、`rules/`、`skills/`、`agents/`、`settings.json` 等关键组件，以及它们各自的作用。

- 最终结论是：**AI Agent 做得好不好，越来越取决于环境配置和规则设计，而不只是提示词技巧。**
