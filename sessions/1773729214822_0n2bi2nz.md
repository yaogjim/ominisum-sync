### How I Manage 10 Claude Code Agents Without Losing My Mind

I run multiple Claude Code agents every day. Doing research, drafts, video scripting, all at the same time, and I don't lose track of any of them.

But it wasn't always this way. I opened Claude Code and started working. Then I needed another agent to do another task. I opened a new tab. Then another, and another. Quickly I had 10 tabs.

Claude, M1, M2, M3, M4, M5. Which one was doing what?

I didn't know what was happening on this tab, switching between all of them just kills my flow. Sessions go stale and the context gets lost. I had this exact problem.

Tabs vs named workspaces

#### cmux: Isolated Workspaces, Not Tabs

The tool that changed this for me is cmux - a terminal workspace manager.

Named workspaces with emojis. Orchestrator, feature-research, video-script, daily-review - each one isolated.

It's not a new tab. It's an isolated workspace. Each workspace has a terminal, the ability to spawn other terminals inside of it, and hot keys to jump between them.

But the real power - cmux is programmable. Claude Code can programmatically access the contents of any workspace.

cmux list-workspaces

The orchestrator sees all workspace names, not "tab 4." It reads the screen of any workspace:

cmux read-screen --workspace workspace:1

No interrupting the agent. Just seeing what it's doing. And it can talk to any workspace:

cmux send --workspace workspace:1 "what was our progress today"

The agent in that workspace starts working on the task. The orchestrator sleeps for 15 seconds, waits for the response, reads the screen. You see the response from that agent.

This way Claude enables communication between agents across different workspaces.

Three commands: list, read, send. That's it.

#### The Orchestrator: One Agent Manages the Rest

Agent Control - what are my agents doing right now

One Claude Code agent becomes the orchestrator - it spawns and controls the others. I have one main orchestrator workspace. Then I have a cmux skill that shows how to use cmux programmatically.

Say I just want to spawn a workspace to review my daily progress. It creates a workspace named "daily review" with this prompt: read today's daily note, give me a summary of what's inside.

Now a Claude Code agent starts working on that task. You see the pattern - you can have isolated workspaces for each of your tasks.

I talk to one agent. That agent manages the rest.

#### The Dashboard: How Not to Go Crazy

Real

[@obsdmd](https://x.com/@obsdmd) Bases dashboard - sessions grouped by status: blocked, done, in-progress, review

But now the problem is - how do you keep track of all these sessions? You use Obsidian and Obsidian Bases.

Every workspace has a session file in Obsidian. The dashboard generates itself. Each session has a related field that links to its dashboard. The Obsidian Base queries all linked sessions automatically - status, date, title, related workspace.

You create a session, link it to the dashboard, it shows up. No manual tracking. When you spawn a workspace, the agent creates its own session file and links it to the dashboard. The Base does the rest.

Nothing is "done" until you verify it. You read the dashboard, check the output, add comments. The orchestrator picks up your comments and relays them to the right agent.

This session, we have a goal. We have a progress and have the outcome. Here is also the definition of done.

Sessions grouped by status - the dashboard queries them automatically

#### The Full Loop

Daily note -&gt; sessions -&gt; spawn workspaces -&gt; verify output -&gt; comment -&gt; orchestrator relays

Here's how it all connects. You have a daily note which you use to plan your day. The orchestrator reads this plan and understands your intent for today. Then you create sessions from there. The orchestrator spawns workspaces for you to do the work.

You look at the progress. You provide comments to the agent. When the agent reads the file, it sees your comment.

You can verify what's happening. You can comment on the work. That's the whole workflow.

#### From Tabs to Workspaces

Before, I had this ghostly terminal with cursor chaos. This concept of tabs was not really working. I was feeling overwhelmed since summer.

And now we have cmux (shotout to

[@manaflowai](https://x.com/@manaflowai)), which is much, much better. It has these workspaces. I added this concept of sessions and dashboards to it. More scalable and more controllable, integrated with Obsidian.

### 2026-03-17 06:41:13

这篇文章的主旨是：作者通过把“多标签页切换”改造成“可编排的独立工作区”，成功同时管理 10 个 Claude Code 代理而不混乱。核心方法是用 `cmux` 管理工作区、用一个“总控代理”统一调度，再配合 Obsidian 仪表盘跟踪进度。

- 问题背景：多标签页模式很容易失控
  - 作者一开始同时开很多 Claude Code 标签页做不同任务，比如研究、写草稿、视频脚本等。
  - 很快就会出现 10 个标签页混在一起的情况，连“哪个窗口在做什么”都分不清。
  - 结果是频繁切换打断思路，session 变旧、上下文丢失，整体效率很差。

- 解决方案：用 `cmux` 把标签页变成“独立工作区”
  - 作者改用 `cmux`，它是一个终端工作区管理工具。
  - 每个任务不再是一个普通标签页，而是一个“隔离的工作区”，可以起明确名字，比如 `orchestrator`、`feature-research`、`video-script`、`daily-review`。
  - 每个工作区都有自己的终端，还能在内部再开终端，并支持快捷键切换。
  - 最大优势是：`cmux` 可编程，Claude Code 可以直接读取和操作其他工作区。

- 工作原理：靠 3 个命令实现代理之间协作
  - 作者强调核心只靠 3 个命令：`list`、`read`、`send`。
  - `cmux list-workspaces`：查看所有工作区，看到的是清晰的工作区名称，而不是“第 4 个标签页”。
  - `cmux read-screen --workspace ...`：读取某个工作区当前屏幕内容，不打断那个代理。
  - `cmux send --workspace ... "..."`：直接给某个工作区里的代理发消息，例如问“今天进展如何”。
  - 一个典型流程是：总控代理发消息后，等待约 15 秒，再读取该工作区屏幕查看结果。
  - 这样就实现了不同代理之间的跨工作区沟通。

- 核心角色：一个总控代理统一管理其他代理
  - 作者会专门保留一个主工作区作为“orchestrator（总控）”。
  - 这个总控代理负责创建、调度和管理其他代理，而作者自己只需要和这一个代理对话。
  - 比如想做“每日回顾”，总控代理会新建一个名为 `daily review` 的工作区，并给出提示词：读取今天的 daily note，然后总结内容。
  - 新工作区创建后，一个 Claude Code 代理就会在里面独立执行任务。
  - 这样每个任务都有自己的独立空间，职责清晰，不容易串线。

- 防止混乱的关键：用 Obsidian 仪表盘追踪所有 session
  - 仅有多个工作区还不够，作者还用 Obsidian 和 Obsidian Bases 做统一追踪。
  - 每个工作区对应一个 session 文件，这些 session 会自动汇总到 dashboard（仪表盘）里。
  - 仪表盘会自动查询并展示关键信息：`status`、`date`、`title`、相关工作区等。
  - session 会按状态分组，例如：`blocked`、`done`、`in-progress`、`review`。
  - 重点是“自动化”：创建 session 并链接到 dashboard 后，它就会自动出现；新工作区生成时，代理还会自己创建对应的 session 文件，不需要手动登记。

- 质量控制：任务不是“做完了”，而是“验证过了”
  - 作者特别强调：不是代理说完成就算完成，必须经过人工验证。
  - 用户会查看仪表盘、检查输出、写评论。
  - 总控代理再把这些评论转发给对应工作区里的代理继续修改。
  - 每个 session 不只是记录任务，还包含目标、进度、结果，以及“完成定义（definition of done）”。

- 完整工作流：从日计划到反馈闭环
  - 整个流程是：`daily note -> sessions -> spawn workspaces -> verify output -> comment -> orchestrator relays`
  - 先在 daily note 里规划当天任务。
  - 总控代理读取计划，理解当天目标，并据此创建 session、启动对应工作区。
  - 用户中途查看进展、给出反馈，代理通过读取文件看到评论后继续推进。
  - 这形成了一个可追踪、可验证、可反馈的完整闭环。

- 最终效果：从混乱切换到可扩展的多代理系统
  - 作者以前形容自己的状态像“终端幽灵混战”，从夏天开始就一直感到不堪重负。
  - 现在借助 `cmux` 的工作区机制，再叠加 session 和 dashboard，系统变得更可扩展、更可控，并且和 Obsidian 深度集成。
  - 简单说，作者不是在“同时盯着 10 个标签页”，而是在用一个总控系统管理 10 个有边界、有记录、有反馈机制的代理。
