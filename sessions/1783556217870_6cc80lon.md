## 分析要点

- **核心高价值点**：指出仅用 nginx 放行 Cloudflare IP 并不能可靠保护源站，真正应通过 Cloudflare Tunnel 暴露本地监听服务。

**知识要点**

- ttyd 可将终端 Web 化，tmux 可保证会话在断线或换设备后继续存在
- Cloudflare Tunnel 可让 VPS 主动建立隧道，避免开放公网入站端口
- Cloudflare Access 应作为邮箱门禁使用，但前提是源站不能被绕过直连
- ttyd 应仅监听 127.0.0.1，并使用无 sudo 权限的专用非 root 用户运行

**行动项**

- 如需复刻，先确认域名、子域名和 Cloudflare 托管状态
- 按 ttyd、tmux、cloudflared、systemd、Access 策略的顺序逐步搭建并逐步验证
- 检查 VPS 防火墙和服务监听地址，确保 ttyd 不绑定 0.0.0.0
- 避免使用仅放行 Cloudflare 回源 IP 的 nginx 方案作为唯一安全边界

## 结构化（1）

### 2026-07-09 00:48:35

#### 文章精炼总结

作者分享了如何在**只用浏览器、不装软件、不开 SSH**的情况下，访问 VPS 上的 Claude Code 终端。核心方案是用 **ttyd + tmux + Cloudflare Tunnel + Cloudflare Access** 搭建一个安全的网页终端。

##### 1. 搭建目标：把 VPS 终端搬到浏览器里

作者想实现一种体验：  
打开一个网页，就能直接使用 VPS 的完整终端，从而在浏览器中运行 Claude Code。

原本作者想做成类似 Pi 那样的网页界面，但因为需要使用 `claude -p`，最终选择保留终端形式，更接近原生体验。

##### 2. 工具链：四个组件各司其职

作者使用的核心工具如下：

- **ttyd**：把 Linux 终端变成网页终端，在浏览器里操作 VPS。
- **tmux**：保持会话不断，即使断网、换设备，也能回来继续操作。
- **Cloudflare Tunnel**：让 VPS 主动连到 Cloudflare，不需要开放公网端口。
- **Cloudflare Access**：通过邮箱验证做访问门禁，防止未经授权访问。

简单理解：  
`ttyd` 负责“网页终端”，`tmux` 负责“不中断”，`Cloudflare Tunnel` 负责“安全暴露服务”，`Cloudflare Access` 负责“登录验证”。

##### 3. 安全重点：不要只靠 Nginx 放行 Cloudflare IP

作者特别强调了一个安全误区：

> 只用 Nginx 放行 Cloudflare IP，并不能真正保护源站。

原因是：

- Cloudflare 的回源 IP 是所有用户共享的。
- 如果别人知道你的 VPS 真实 IP，就可能用自己的 Cloudflare 账号绕过你的 Access，直接访问你的源站。
- 作者称这是 Cloudflare 官方也承认的问题，评级为 **High**。

因此，作者认为真正安全的方式是：

- 使用 **Cloudflare Tunnel**
- VPS 不开放任何公网入站端口
- ttyd 只监听本机地址 `127.0.0.1`

##### 4. 推荐复刻方案：浏览器终端 + Claude Code

作者提供了一段可以发给 AI 的搭建提示词，核心要求是：

###### 架构

```text
ttyd + tmux + Cloudflare Tunnel + Cloudflare Access
```

###### 使用场景

- 只用浏览器
- 打开一个网址即可访问 VPS 终端
- 不安装本地软件
- 不开启 SSH
- 域名托管在 Cloudflare

##### 5. 安全铁律：四条不可违反

作者列出关键安全规则：

1. **ttyd 只能监听 `127.0.0.1`**  
   不能绑定 `0.0.0.0`，避免直接暴露到公网。

2. **创建专用非 root 用户运行 ttyd**  
   并且不给这个用户 `sudo` 权限，降低被攻破后的风险。

3. **必须使用 Cloudflare Tunnel 暴露服务**  
   源站不开放任何入站端口，避免绕过 Cloudflare Access。

4. **使用 Cloudflare Access 配置邮箱门禁**  
   只有通过邮箱验证的人才能访问网页终端。

##### 6. 具体搭建步骤概要

作者建议按步骤执行，并且“每一步验证通过再继续”，不要一次性跑完。

主要流程是：

1. 安装：
   - `ttyd`
   - `tmux`
   - `cloudflared`

2. 创建专用非 root 用户。

3. 使用 `systemd` 让 ttyd 常驻运行。

4. ttyd 推荐参数：

```bash
-O -W -i 127.0.0.1 -p 7681
```

并运行：

```bash
tmux new -A -s web
```

含义是进入或创建一个名为 `web` 的 tmux 会话。

5. 用 `cloudflared` 创建 Tunnel。

6. 将 Cloudflare 子域名路由到：

```text
http://127.0.0.1:7681
```

7. 在 Cloudflare 面板配置 Access 邮箱访问策略。

##### 7. 搭建前需要确认的信息

作者建议 AI 在正式开始搭建前，先询问用户两个问题：

- 域名是什么？
- 想使用哪个子域名？

例如：

```text
域名：example.com
子域名：terminal.example.com
```

这样就可以通过浏览器访问该子域名，进入 VPS 上的网页终端。

## 通俗精炼（1）

#### 用浏览器安全访问 VPS 上的 Claude Code

文章分享了一套轻量方案：将 VPS 终端搬到网页中，使用户只需浏览器和网址，就能使用 Claude Code；同时通过会话持久化、加密隧道和邮箱认证兼顾连续使用与安全性，无需安装客户端或开放 SSH。

##### 四个组件各司其职

- **ttyd**：把完整终端转换为网页服务。
- **tmux**：保持终端会话，断网或更换设备后仍可继续。
- **Cloudflare Tunnel**：由 VPS 主动建立出站隧道，无需开放公网入站端口。
- **Cloudflare Access**：在网页入口增加邮箱身份验证。

作者选择保留终端形态，而非另做图形化前端，主要是为了维持 Claude Code 的原生使用体验。

##### 仅限制 Cloudflare IP 并不安全

作者特别纠正了一种常见做法：用 Nginx 仅允许 Cloudflare 回源 IP 访问，并不能确保 Access 门禁无法绕过。原因是 Cloudflare 回源 IP 为不同用户共享；如果攻击者知道 VPS 的真实 IP，可能借自己的 Cloudflare 配置直接访问源站。

因此，关键不是单纯设置 IP 白名单，而是让源站**不开放任何入站端口**，所有访问只能经过 Cloudflare Tunnel 和 Access。

##### 部署必须遵守最小权限原则

推荐配置包括：ttyd 只监听 `127.0.0.1:7681`，由无 sudo 权限的专用非 root 用户运行；通过 systemd 保持服务常驻，并自动进入固定 tmux 会话；再将子域名经 Tunnel 路由至本地 ttyd，最后配置 Access 邮箱策略。

这套方案的核心价值是以较低搭建成本，把命令行 AI 工具变成跨设备、免安装的网页服务，同时避免为了便利而直接暴露服务器终端。
