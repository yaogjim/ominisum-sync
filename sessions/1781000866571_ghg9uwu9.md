- coding agent的harness负责真实运行环境、工具执行、权限控制、状态更新和上下文投影

## 正文

**马东锡 NLP**

### Harness 就是产品

为什么 coding agent 最重要的部分，常常是最不显眼的那部分。

每次讨论 coding agent，大家最后都会从 model 开始。

“ 用哪个 model？context 多大? 写代码能力怎么样？”

这些问题重要，但它们已经不再是我们应该最先问的问题，我们应该问的第一个问题应该是：

> Harness 到底负责什么？

当我们回顾基础的 LLM 预测文本任务，reasoning model 可以跟随结构，输出 tool call，并在 protocol 里工作。

coding agent 则更进一步：它把 model 放进一套 runtime。这个 runtime 能检查真实 repo，请求 tool，编辑文件，跑检查，记住发生过什么，并在多轮中继续推进。

> 这层 runtime 就是 harness。

对编码代理来说，harness 本身就是产品。

![Image](https://pbs.twimg.com/media/HKUgykVWUAAOOd_?format=jpg&name=large)

利用产品英雄

#### 天真版本

一个 mini 版本的coding agent 通常长得像这样：

![Image](https://pbs.twimg.com/media/HKUhYKbWAAIrXRm?format=jpg&name=large)

原生代理循环

这是一张有用的草图，但这样的mini agent 很快会出问题。比如：

- 当 model 要编辑一个它从没读过的文件，会发生什么？
- 当 shell command 触碰 workspace 外的文件，会发生什么？
- 当 tool 返回 50,000 行输出，会发生什么？
- 当文件已经在磁盘上变化，transcript 里仍然保留旧 file read，会发生什么？
- 当 tool result 和产生它的 tool call 对不上，会发生什么？

这个 system 还没有成为 coding agent。

#### Harness 拥有什么

Model 可以提出 proposal，Harness 负责做决定。

从 architecture 的角度去看，关键 surface 超出这一行：

![Image](https://pbs.twimg.com/media/HKUi2LAW0AAH4aG?format=jpg&name=large)

界面不是代理

它更接近：

![Image](https://pbs.twimg.com/media/HKUjFwqXAAABaYz?format=jpg&name=large)

每一个箭头，都是 harness 可以保护用户的位置；也可能是它悄悄失控的位置。

![Image](https://pbs.twimg.com/media/HKUjeHMWgAEhyNT?format=jpg&name=large)

#### 编码代理工具必须做的六件事

这里，我们把 Coding Agent 压缩成六个核心组件：

1\. 实时仓库上下文

Agent 不该从空 prompt 开始。它需要知道 workspace、当前文件、相关 project docs，以及哪些 repo state 可以安全暴露。

2\. 提示形状

Context quality 经常看起来像 model quality。稳定的 prefix、清晰的 tool contract、当前 request、受控的 history，带来的行为差异可能比换 model 更大。

3\. Structured tools

Tools 不应被当作 helper functions。它们是 model proposal 和真实 side effects 之间的 contract。

Harness 解析 arguments，验证 paths，检查 policy，执行操作，裁剪 output，并记录发生了什么。

4\. Context reduction

如果 harness 盲目追加所有东西，model 最后会看到太多、太少，或者看到错误的东西。

好的 context 是一个 projection，而非不断膨胀的 blob。

5\. Transcripts and memory

Transcript 回答：“发生过什么？”

Working state 回答：“现在什么重要？”

这是两份不同的任务，当然需要区别对待。

6\. Delegation

Subagents 也不等于 magic parallelism。它们应该是有边界的 workers：scoped tools、isolated state、distilled results。

当 delegation 充当 context firewall 时，它才真正有用。

#### The Main Loop

coding agent 是一个 observe-act loop，但真正有价值的部分，发生在 observe 和 act 之间。

![Image](https://pbs.twimg.com/media/HKUklRDWQAA8cMG?format=jpg&name=large)

model 在 loop 里面, harness 拥有 loop。

这个区别很关键。

#### A Concrete Example

假设 model 发出一个 tool call：

![Image](https://pbs.twimg.com/media/HKUk8LwWkAEKAnB?format=jpg&name=large)

model 做出了一个 proposal。harness 接下来要回答一串问题：

- src/config.py 是否在 workspace 内？
- 这个 path 是否会通过 symlink 逃逸？
- 这是新文件，还是 overwrite？
- model 最近是否读过现有文件？
- 已知的 file baseline 是否过期？
- 这次 write 是否需要 human approval？
- edit result 是否应该包含 diff summary？
- 后面是否应该跑 validation command？
- 有多少 output 应该进入下一轮 prompt？
- 需要更新哪些 state，避免下一轮 stale？

这些判断不该交给 model 的随机处理。

Prompt 可以描述期望行为。Harness 负责落实边界。

#### The Product Lesson

一旦你开始看见 harness，很多 coding-agent 行为都会更容易诊断。

- 如果 agent 不断重复，去检查 loop 和 retry policy。
- 如果它编辑 stale code，去检查 file-state baselines。
- 如果它越跑越差，去检查 context projection。
- 如果它运行了意外的东西，去检查 permission policy。
- 如果它无法从 tool errors 中恢复，去检查 tool result objects。
- 如果它解释不清发生了什么，去检查 traces、audit、doctor surfaces。

model 当然重要，只是 model quality 只占其中一层。

真正的 agent experience 来自 model 周围的整套 harness：

![Image](https://pbs.twimg.com/media/HKUlh_tW0AAPS9Z?format=jpg&name=large)

这就是为什么 “the harness is the product” 不只是一句 slogan。

它是一条工程规则：

> Anything that must be reliable belongs in the harness.

##### 一、深度总结

文章核心观点：

> 对 coding agent 来说，真正决定产品体验的，不只是模型，而是模型外面的 **harness（运行与控制系统）**。

很多人讨论 coding agent 时，首先问：

- 用什么模型？
- 上下文多大？
- 写代码能力强不强？

但作者认为，更关键的问题是：

> Harness 到底负责什么？

因为 coding agent 不是单纯让模型生成代码，而是把模型放进一个真实运行环境里，让它能够：

- 读取真实代码仓库
- 调用工具
- 修改文件
- 执行命令
- 记录历史
- 多轮推进任务
- 遵守权限与边界

这套环境、规则、记忆、工具、权限、上下文管理系统，就是 **harness**。

作者强调：

> Model 可以提出建议，Harness 负责执行、约束、验证和保护。

一个成熟的 coding agent，不能只是“模型 + 工具调用”。它必须有一套可靠的 harness，来处理路径安全、文件状态、上下文裁剪、工具返回、权限控制、执行记录等问题。

因此：

> **Harness 本身就是 coding agent 产品的核心。**

---

##### 二、深入浅出解读

可以把 coding agent 理解成一个“AI 程序员”。

但 AI 程序员不能只靠“大脑”工作。

- **模型**：像大脑，负责思考、规划、生成代码。
- **Harness**：像工作系统，负责提供资料、检查权限、执行操作、记录过程、防止出错。

如果只有模型，没有 harness，就像一个程序员：

- 不知道当前项目结构
- 没确认文件是否读过就改代码
- 可以随便执行危险命令
- 看见超长日志后被淹没
- 记不清刚才发生了什么
- 对旧文件状态做错误判断

这不是可靠的 coding agent，只是一个会写代码的聊天机器人。

---

##### 三、Harness 的六个核心职责

###### 1. 实时仓库上下文

Agent 不能从空白开始。

它需要知道：

- 当前 workspace
- 项目结构
- 当前文件
- 相关文档
- 哪些信息可以安全暴露

否则模型即使聪明，也是在“盲写”。

---

###### 2. 提示形状

提示词不只是文字，而是系统行为的入口。

好的 harness 要提供：

- 稳定的系统前缀
- 清晰的工具协议
- 当前任务
- 受控历史
- 精简上下文

很多时候，看似是“模型变强了”，其实是 **上下文组织得更好了**。

---

###### 3. 结构化工具

工具不是简单函数，而是模型建议与真实世界副作用之间的契约。

Harness 要负责：

- 解析参数
- 校验路径
- 检查权限
- 执行操作
- 裁剪输出
- 记录结果

模型只应该“提议”，不应该直接“放飞执行”。

---

###### 4. 上下文简化

上下文不是越多越好。

如果 harness 把所有历史、日志、文件内容都塞给模型，结果可能是：

- 信息过载
- 重点丢失
- 引入过期信息
- 推理质量下降

好的上下文应该是 **投影**，不是不断膨胀的垃圾堆。

---

###### 5. 转录记录与工作记忆

文章区分了两类信息：

- **Transcript**：发生过什么？
- **Working state**：现在什么重要？

前者是历史记录，后者是当前工作状态。

二者不能混在一起，否则 agent 会既记太多，又抓不住重点。

---

###### 6. 授权与子代理

Subagent 不是魔法并行。

它们应该是有边界的 worker：

- 有限定工具
- 有隔离状态
- 有明确任务
- 返回提炼后的结果

真正有用的 delegation，是把子代理当成 **上下文防火墙**，而不是无限扩张的混乱并行。

---

##### 四、关键洞察

文章最重要的一句话是：

> **Model 在循环中，Harness 拥有循环。**

coding agent 表面看是一个 observe-act loop：

1. 观察环境
2. 模型思考
3. 调用工具
4. 修改文件
5. 继续观察

但真正决定可靠性的，是 observe 和 act 之间的控制逻辑。

例如模型想写入 `src/config.py`，harness 不能直接执行，而要检查：

- 路径是否在工作区内？
- 是否通过 symlink 逃逸？
- 是新建还是覆盖？
- 模型最近是否读过这个文件？
- 文件状态是否过期？
- 是否需要人工批准？
- 是否要返回 diff？
- 是否要运行验证命令？
- 哪些输出进入下一轮上下文？

这些判断不能交给模型“凭感觉”。

---

##### 五、产品层面的启发

如果 coding agent 出问题，不一定先怪模型。

可以这样诊断：

| 问题 | 应该检查 |
|---|---|
| Agent 不断重复 | loop 和 retry policy |
| 编辑过时代码 | 文件状态基线 |
| 越运行越差 | context projection |
| 执行了意外命令 | permission policy |
| 无法从工具错误恢复 | tool result objects |
| 解释不清发生了什么 | traces、audit、doctor surfaces |

所以，模型质量只是其中一层。

真正的产品体验，来自模型周围完整的 harness。

---

##### 六、辩证思考

###### 1. 模型重要，但不能神化模型

更强的模型确实能提升 coding agent 的能力。

但在真实工程场景中，可靠性、安全性、可恢复性，不能只靠模型自觉。

模型擅长生成和推理，但不适合承担所有边界判断。

> 该由系统保证的东西，不应交给模型随机发挥。

---

###### 2. Harness 是约束，也是放大器

表面看，harness 在限制模型：

- 限制路径
- 限制命令
- 限制上下文
- 限制权限

但本质上，它是在放大模型能力。

因为只有在安全、清晰、可控的环境里，模型才能持续完成复杂任务。

没有 harness，模型能力越强，可能破坏力也越强。

---

###### 3. Coding agent 的竞争，不只是模型竞争

未来 coding agent 产品的差异，可能不只来自模型参数，而来自：

- 谁的上下文管理更好
- 谁的工具协议更稳定
- 谁的权限系统更安全
- 谁的执行记录更清晰
- 谁的错误恢复更可靠
- 谁更懂真实软件工程流程

换句话说：

> 模型决定上限，harness 决定可用性。

---

###### 4. “自动化”不是取消控制，而是重构控制

很多人以为 agent 越自动越好。

但真正成熟的自动化，不是无边界放权，而是：

- 哪些能自动？
- 哪些要审批？
- 哪些要回滚？
- 哪些要审计？
- 哪些要隔离？

Agent 产品的关键，不是“让 AI 什么都做”，而是“让 AI 在正确边界内可靠地做”。

---

##### 七、一句话总结

> **Coding agent 的核心不是让模型会写代码，而是让模型在一套可靠、安全、可控、可恢复的 harness 中持续完成真实工程任务。**

所以：

> **Harness 不是辅助设施，Harness 就是产品。**

##### 1. 为什么不能只关注 Model

讨论 coding agent 时，人们常先问：

- 用哪个 model？

- 查看 repo
- 调用工具
- 编辑文件
- 运行检查

这一整套让模型真正“行动起来”的 runtime，就是 **harness**。

**只有 agent loop 还不够，它还不是可靠的 coding agent。**

---

##### 3. Harness 的职责：模型提议，Harness 决策

作者强调：

> **Model 可以提出 proposal，Harness 负责做决定。**

模型可以建议做什么，但真正执行前，harness 需要负责检查、限制、记录和修正。

每一个从模型到工具、从工具到文件系统、从执行结果回到上下文的环节，都是 harness 保护用户的位置，也可能是系统失控的位置。

##### 4. Coding Agent 工具必须具备的六个核心组件

###### 4.1 实时仓库上下文

Agent 不应该从空 prompt 开始。它需要知道：

- 当前 workspace
- 当前文件
- 相关项目文档
- 哪些 repo state 可以安全暴露给模型

也就是说，agent 必须基于真实项目状态工作，而不是凭空猜测。

---

###### 4.2 提示形状 Prompt Shape

很多时候，看起来像是 model 能力差，其实是 context 组织得不好。

高质量 prompt 需要包括：

- 稳定的 prefix
- 清晰的 tool contract
- 当前用户请求
- 受控的历史信息

作者指出：  
**好的提示结构带来的行为改善，可能比换一个更强模型还明显。**

---

###### 4.3 结构化工具 Structured Tools

工具不应该只是 helper functions，而是：

> **模型提议与真实副作用之间的 contract。**

Harness 需要负责：

- 解析参数
- 校验路径
- 检查权限策略
- 执行操作
- 裁剪输出
- 记录发生了什么

例如，模型想写入文件时，不应该直接执行，而应由 harness 判断是否安全、是否允许。

---

###### 4.4 上下文压缩 Context Reduction

如果 harness 盲目把所有历史和工具输出都塞进 prompt，模型最终会看到：

- 太多信息
- 太少关键信息
- 错误或过期的信息

作者强调：

> **好的 context 是一种 projection，而不是不断膨胀的 blob。**

也就是说，harness 要选择性地呈现当前最重要的信息。

---

###### 4.5 Transcript 与 Memory 要区分

作者区分了两类信息：

- **Transcript**：回答“发生过什么？”
- **Working state**：回答“现在什么重要？”

两者任务不同，不能混在一起。  
否则 agent 可能会被无关历史干扰，或者遗漏当前关键状态。

---

###### 4.6 Delegation：子代理不是魔法并行

Subagents 不等于简单地并行调用多个模型。

真正有用的 delegation 应该是：

- 有明确边界的 worker
- 拥有 scoped tools
- 状态隔离
- 输出经过提炼

当子代理能充当 **context firewall（上下文防火墙）** 时，它才真正有价值。

---

##### 5. 主循环：Model 在 Loop 里，Harness 拥有 Loop

Coding agent 本质上是一个 observe-act loop：

- observe：观察当前状态
- act：采取行动

但真正有价值的部分发生在两者之间：  
**如何判断、过滤、验证、授权、记录和更新状态。**

作者总结：

> **Model 在 loop 里面，Harness 拥有 loop。**

这意味着：模型只是循环中的决策建议者，而整个循环的控制权属于 harness。

---

##### 6. 具体例子：模型想写入 `src/config.py`

假设模型发出一个 tool call，想编辑：

```text
src/config.py
```

这只是一个 proposal。Harness 接下来要判断：

- `src/config.py` 是否在 workspace 内？
- 路径是否可能通过 symlink 逃逸？
- 这是新文件还是覆盖旧文件？
- 模型最近是否读过这个文件？
- 已知的 file baseline 是否已经过期？
- 这次写入是否需要人工批准？
- 编辑结果是否要包含 diff summary？
- 是否应该运行 validation command？
- 有多少输出应该进入下一轮 prompt？
- 需要更新哪些 state，避免下一轮读取过期信息？

这些判断都不应该交给模型随机处理。  
Prompt 可以描述期望行为，但 **边界必须由 harness 落实**。

---

##### 7. 产品启示：问题常出在 Harness，而不只是 Model

一旦理解 harness，就能更好诊断 coding agent 的问题：

- Agent 不断重复：检查 loop 和 retry policy
- 编辑过期代码：检查 file-state baselines
- 越跑越差：检查 context projection
- 运行了意外命令：检查 permission policy
- 无法从 tool errors 恢复：检查 tool result objects
- 解释不清发生了什么：检查 traces、audit、doctor surfaces

模型当然重要，但它只是其中一层。  
真正的 agent 体验来自模型周围完整的 harness。

---

##### 8. 最终结论

作者的核心工程原则是：

> **Anything that must be reliable belongs in the harness.**  
> 凡是必须可靠的东西，都应该放进 harness。

所以，“the harness is the product” 不只是口号，而是一条 coding agent 的工程规则：  
**模型负责生成可能的行动，harness 负责让行动安全、可靠、可控地发生。**
