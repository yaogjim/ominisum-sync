## 解读（1）

### 2026-06-04 07:09:42

#### 深度总结

这条内容的核心建议是：

> **如果你在做 CLI 工具，不仅要给人写`--help`，也要给 AI Agent 写 “帮助入口”。**

具体做法：

1. 在`--help`中增加**AI agents 专区**
2. 提供一个命令，让 Agent 能加载与当前 CLI 匹配的使用技能 / 说明，例如：

```bash
harbor skills get harbor
```

3. 这些 skills 应该随 CLI 一起发布，且与版本匹配，内容包括：
   - 常见工作流
   - 服务使用指南
   - 可复制的示例命令
   - 比单纯参数文档更高层的操作模式

作者认为：  
**不要让 Agent 只靠 flag 文档猜命令，而应提供可发现、可加载、版本一致的操作知识。**

---

#### 深入浅出解读

传统 CLI 的帮助文档主要服务于人：

```bash
tool --help
```

人看完参数后，可以结合经验判断怎么用。

但 AI Agent 不一样。它更需要：

- 明确入口
- 标准化说明
- 可执行示例
- 当前版本对应的真实用法
- 最佳实践，而不只是参数列表

所以作者建议：

```bash
tool skills list
tool skills get xxx
tool skills path xxx
```

这相当于给 CLI 加一个 “AI 使用说明书”。

##### 类比

过去我们写文档是给人看的：

> “这里有说明，你自己理解。”

现在要给 Agent 准备：

> “这是推荐流程，这是示例，这是当前版本的正确用法，照这个来。”

---

#### 关键洞察

##### 1. CLI 正在从 “人机接口” 变成 “Agent 接口”

未来很多 CLI 不再主要由人手动输入，而是由 AI 调用。  
因此工具设计要考虑：

- Agent 如何发现功能
- Agent 如何避免误用
- Agent 如何获得上下文
- Agent 如何执行复杂流程

##### 2. `AGENTS.md`不应承载一切

回复中提到：

> AGENTS.md 只适合放必须始终存在的上下文，其他内容应按需发现。

也就是说：

- 固定背景：放`AGENTS.md`
- 工具用法：通过 CLI 自身暴露
- 复杂技能：按需加载

这是一种更轻、更动态的 Agent 文档设计。

##### 3. “技能” 比 “参数说明” 更重要

参数说明回答的是：

> 这个命令有哪些选项？

技能说明回答的是：

> 遇到某类任务时，应该怎么完成？

Agent 更需要后者。

---

#### 辩证思考

##### 好处

###### 1. 降低 Agent 误操作

版本匹配的 skills 能减少幻觉式调用，避免 Agent 编造不存在的参数。

###### 2. 提升自动化质量

Agent 不只是 “知道命令”，而是知道 “流程”。

###### 3. 文档和工具绑定更紧

CLI 发布时同时发布 Agent 技能，避免文档滞后。

---

##### 风险

###### 1. 维护成本增加

开发者不仅要维护代码和人类文档，还要维护 Agent 文档。

###### 2. 可能形成新的碎片化标准

如果每个 CLI 都自定义一套`skills`格式，Agent 仍然难以通用理解。

###### 3. Agent 依赖增强

工具越为 Agent 优化，人类用户体验可能被边缘化，需要平衡。

---

#### 我的判断

这是一个很重要的趋势：

> **未来优秀的 CLI，不只是给人好用，也要给 Agent 好用。**

但关键不在于一定要叫`skills`，而在于形成三点共识：

1. **可发现**：Agent 能知道哪里有帮助  
2. **可执行**：文档包含真实示例和工作流  
3. **可版本化**：说明与当前 CLI 版本一致  

一句话总结：

> **给 CLI 加 Agent 帮助，不是锦上添花，而是在 Agent 时代让工具可被正确使用的基础设施。**
