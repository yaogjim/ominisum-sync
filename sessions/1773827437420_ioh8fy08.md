### Your IDE Is Slowing You Down

“I want to see your IDEs open less” is something I told my team a couple weeks ago. Not because IDEs are necessarily bad, but because they anchor you to a slower and more manual workflow of typing, and thinking line by line, instead of the higher level thinking you should be doing. Software engineering is being increasingly abstracted away from the IDE, and more towards an English-first workflow, with human (agent assisted, of course) code review. The traditional IDE-centric loop looks like this: open your editor, find files, write code, run it, fix errors. It’s serial and human-limited. Even with great tooling, you’re still the bottleneck. You’re starting every task from scratch instead of delegating first and refining later.

The way we write code today looks wildly different than it did a year ago, and even 6 months ago, with more and more of your engineering lifecycle happening through an agent. To me, it’s pretty clear we won’t be writing code manually at all in a year, if not less. Because of that, I want my team to get in the habit of being “agentic first”.

Being agentic first means everything you do in your day to day engineering job should start with an agent. Have to scope out a feature? Ask your agent to take a stab at it first. Building an MVP? That’s your agent’s job. Resolving pull request comments? No you’re not, your agent is. Most engineers default to opening their IDE first. But, that choice alone slows you down because it forces you into execution mode before exploration, and into implementation before validation.

Agents obviously aren’t good enough to do 100% of our jobs today, but they’re close. When they do get to that point, you want to make sure you’re already in the habit of going through an agent for your tasks. That should start now, even if it’s a simple code change or bug fix, it’s a good idea to get into the habit of going through an agent to do it, so when the time comes where you really don’t need to code, you’re already used to delegating tasks, and familiar with the software for it.

A big part of this process is utilizing tools which are deeply intertwined with the rest of your existing processes. We’re doing this with

[Open SWE](https://github.com/langchain-ai/open-swe), an open source, cloud based coding agent that’s connected to GitHub, Slack and Linear. With a system like Open SWE you can:

1. Start to get into the habit of always going through an agent
2. Speed up existing workflows by having an agent take the first stab at everything

Tools like this matter because they remove the need to even start in your IDE. Instead of opening an editor and figuring out where to begin, you start with a request, and only drop into code if needed.

We use it daily at LangChain to do everything from answering questions in Slack about implementation details, to planning new features, implementing them, and resolving pull request review comments. Open SWE doesn’t need to completely replace your existing coding agents, it builds on top of them. You use it to kick off a task (say, from a conversation in a Slack thread) and put up an initial implementation. If you like it as is, great, merge it! If you don’t like its implementation, or realized you want to change the spec, it’s not a problem. Just check out the branch locally and have your CLI based agent make changes.

Once you’re in the habit of being agentic first, you’ll find yourself opening your IDE less and less to write code, and instead using it more of a diff viewing tool, or code review interface —although I find myself pushing to GitHub, and using the GitHub PR view to inspect my changes.

Get into the habit of this now, so when the time comes where we‘re never manually editing code, you’re already used to all the workflows that integrate with your agents.

Try out Open SWE yourself today:

[https://github.com/langchain-ai/open-swe](https://github.com/langchain-ai/open-swe)

## A结构化（1）

### 2026-03-18 10:02:14

这篇文章的核心观点是：传统以 IDE 为中心的编程方式正在拖慢工程效率，未来更高效的模式是 “agentic first”—— 先让 AI 代理起手，再由人类做判断和把关。作者认为，软件开发正在从 “手动写代码” 转向 “用自然语言驱动 + 人工审核” 的新工作流。

- 第一部分：为什么 IDE 会让你变慢
  - 作者并不是说 IDE 不好，而是认为它会让人默认进入 “逐行实现” 的低层工作模式。
  - 传统流程通常是：打开编辑器、找文件、写代码、运行、修错。
  - 这个流程的问题是 “串行、靠人推进、效率受个人限制”，即使工具再好，人仍然是瓶颈。
  - 作者强调：很多任务本可以先委托给 agent 处理，而不是每次都从头手写。

- 第二部分：开发方式正在快速变化
  - 作者认为，现在的写代码方式，和 1 年前、甚至 6 个月前相比，都已经明显不同。
  - 趋势是：越来越多的工程流程会通过 agent 完成，而不是在 IDE 里人工逐步实现。
  - 他甚至判断：可能不到 1 年，人类就几乎不再手动写代码了。
  - 因此，他要求团队尽早养成 “agent 优先” 的习惯，而不是等工具完全成熟后再适应。

- 第三部分：什么叫 “agentic first”
  - 所谓 “agentic first”，就是日常工程任务都先交给 agent 起步。
  - 具体包括：
    - 评估一个功能范围时，先让 agent 提方案；
    - 做 MVP 时，先让 agent 实现第一版；
    - 处理 PR 评论时，也先让 agent 回应或修改。
  - 作者认为，很多工程师一上来就打开 IDE，这会让人过早进入执行阶段，而不是先探索、验证方案。

- 第四部分：为什么现在就要开始
  - 作者承认：agent 目前还做不到 100% 替代工程师，但已经 “很接近”。
  - 正因为还没完全成熟，更应该从现在开始训练这种工作习惯。
  - 哪怕只是一个简单的小改动或 bug 修复，也值得先让 agent 试一次。
  - 这样未来当 “几乎不需要手写代码” 时，团队已经熟悉任务委托和相关工具，而不会临时转型。

- 第五部分：工具如何融入现有流程
  - 作者认为，关键不只是用 agent，而是用 “深度融入现有流程” 的 agent 工具。
  - 文中举的例子是`Open SWE`：一个开源、云端 coding agent，可连接 GitHub、Slack 和 Linear。
  - 这类工具的价值主要有两点：
    - 帮团队养成 “凡事先过 agent” 的习惯；
    - 让 agent 先完成第一版，从而加速已有工作流。
  - 核心变化是：你不必先打开 IDE 想从哪里下手，而是先发出请求，只有需要时才进入代码层。

- 第六部分：实际使用案例
  - 作者说他们在 LangChain 每天都在用 Open SWE，覆盖的场景包括：
    - 在 Slack 回答实现细节问题；
    - 规划新功能；
    - 直接实现功能；
    - 处理 PR review comments。
  - 使用方式不是完全替代其他 coding agent，而是作为任务入口：
    - 比如从 Slack 线程发起任务；
    - 先生成一个初始实现；
    - 如果实现满意，就直接合并；
    - 如果不满意，或者需求变了，再把分支拉到本地，用 CLI agent 继续修改。
  - 这个例子说明：agent 并不要求一次到位，人类仍然负责最终判断和 refinement。

- 第七部分：IDE 在未来会变成什么
  - 作者认为，一旦习惯 “agentic first”，工程师打开 IDE 的次数会越来越少。
  - IDE 的角色会从 “主要写代码工具”，变成：
    - 看 diff 的工具；
    - 代码审查界面。
  - 甚至作者自己也更倾向于把代码推到 GitHub，然后直接在 GitHub PR 页面看改动。

- 结尾：作者的行动建议
  - 文章最后的建议很直接：现在就开始适应这种 agent 驱动的工作方式。
  - 因为如果未来真的进入 “几乎不再手动改代码” 的阶段，提前适应的人会更顺畅。
  - 文末还给出了 Open SWE 的地址：`https://github.com/langchain-ai/open-swe`

- 补充：评论区里有代表性的反馈
  - 有人认同思路，甚至喊出`#DeleteYourIDE`，说明这类观点正在引发共鸣。
  - 也有人提出更务实的流程优化建议，比如直接用 GitHub PR + Actions，避免 “agent 出 PR → review agent → 再复制回终端” 的繁琐链路。
  - 还有评论关注技术实现细节，例如 Open SWE 是否是 CLI-first、是否能读写文件和调用 bash，这说明大家关心的不只是理念，还有实际落地方式。
