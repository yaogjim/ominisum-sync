## 正文

**宝玉**

团队内的 skills 管理和维护的一点经验分享（以 codex cli 用的 .agents/skills 目录为例）：

1\. Git 管理是一定要的。  
版本控制太重要了，而且 Skills 都是 Markdown 和脚本文件，天然适合 Git。

2\. 用好 Symlink。  
不要把 Skills 整个拷贝到 .agents/skills，而是通过 Symlink 直接链接到原始 Skills 的 Repo。

好处有两个：一是版本控制更干净；二是使用中遇到问题，Agent 定位后可以直接在 Repo 里改，改完就能 Review 提 PR。

我日常维护 baoyu-skills 就是这么干的，用的时候发现问题，让 Agent 在当前会话改，改的就是 Repo 本身，流程非常顺。

主要的坑是 Windows 下好像不支持 Symlink，另外首次配置稍麻烦（可以让 Agent 帮你操作）。

3\. Skills 的编辑优先让 Agent 来。  
改完走 Git 提 PR，这就是最好的协作和发布流程。

4\. 验证确实不太好做。  
脚本部分可以写单元测试，Skill 的 Markdown 部分只能靠平时积累的测试集，大部分还得人工。  
但配合 Git 的版本管理，快速迭代反而更现实：不怕改出问题，出了问题根据 commit history 快速定位，或者直接回滚。

5\. 最后提醒一下：大部分 Skills 应该跟着项目走（放项目目录下的 .agents/skills），不要放全局（\~/.agents/skills）。  
即使是渐进式加载，meta 信息累积起来也会占不小的上下文空间。

#### 团队管理 AI Skills 的实用经验总结

##### 核心观点
这篇内容主要讲的是：团队管理 `Skills` 时，不要把它当成随手写的说明文档，而要像管理代码一样管理。核心方法是用 `Git` 做版本控制、用 `Symlink` 保持单一数据源、优先让 `Agent` 参与编辑，并接受“快速迭代 + 人工验证”为主的现实方案。

##### 1. 用 Git 管理，是基础设施
`Skills` 本质上是 Markdown 和脚本文件，非常适合放进 Git 管理。  
这样做的价值在于：版本可追踪、多人协作清晰、出了问题能快速定位或直接回滚。对团队来说，这是最稳妥、最低成本的管理方式。

##### 2. 用 Symlink 保持“唯一源头”
不要把 `Skills` 复制到 `.agents/skills`，而是通过 `Symlink` 链接到原始仓库。  
这样有两个明显好处：一是版本管理更干净，不会出现多份拷贝；二是使用过程中一旦发现问题，可以直接在源仓库修改，然后走 Review 和 PR 流程，维护效率更高。

##### 3. 编辑 Skills，优先交给 Agent
作者建议：`Skills` 的修改尽量让 `Agent` 来完成。  
因为 Agent 可以在实际使用场景里边发现问题边修改，改完直接提交到 Git 流程中。这种方式把“发现问题—修复—提交—发布”串成了一个顺畅闭环。

##### 4. 验证难以完全自动化
`Skills` 的验证比普通代码更难。  
脚本部分可以写单元测试，但 Markdown 内容往往很难自动验证，更多依赖测试集积累和人工检查。因此，与其追求一次性验证完美，不如依赖 Git 支撑快速迭代：允许试错，出问题能快速修复或回滚。

##### 5. Skills 应尽量跟项目走，不要全局堆积
大部分 `Skills` 应该放在项目目录下的 `.agents/skills`，而不是全局目录 `~/.agents/skills`。  
原因是即使采用渐进加载，过多全局 Skills 的元信息也会持续占用上下文空间，影响效率。换句话说，`Skills` 更适合“按项目就近管理”，而不是“全局统一堆积”。

##### 补充讨论
评论区也补充了几个现实问题：  
一是 `Symlink` 虽然有效，但在 Windows 下兼容性较差，首次配置也稍麻烦；二是随着 Agent 数量增多，依赖关系、命名和引用层级会变复杂，需要更明确的组织方式；三是已经开始出现专门的 Skill 管理工具，说明这件事正在从“经验做法”走向“工具化管理”。

##### 一句话总结
**团队管理 Skills 的最佳实践，不是追求花哨的协作工具，而是用代码工程化思路来管理文档和脚本：Git 做底座，Symlink 保持单一源头，Agent 参与编辑，依靠快速迭代弥补验证不足。**

## 解读（1）

### 2026-04-03 07:05:26

#### 关于团队内 Skills 管理的经验

##### 一句话总结

这段内容的核心观点是：  
**团队管理 Agent 的 Skills，最实用的办法不是靠“在线文档式协作”，而是把它当成“可版本化、可迭代、可回滚”的工程资产来管理。**

---

##### 内容总结

作者结合 `codex cli` 的 `.agents/skills` 目录，分享了 5 点经验：

1. **一定要用 Git 管理**  
   Skills 本质上是 Markdown 和脚本文件，非常适合版本控制。

2. **优先用 Symlink，而不是直接拷贝**  
   `.agents/skills` 不要复制一份 Skills，而是链接到原始 Repo。  
   这样既能保持版本源唯一，也方便直接修改、Review、提 PR。

3. **Skills 的编辑尽量让 Agent 来做**  
   改完后走 Git + PR 流程，这是比较顺的团队协作方式。

4. **验证比较难，尤其是 Markdown 部分**  
   脚本可以做单测，但 Skill 文档更多要靠测试集和人工验证。  
   所以重点不是“绝对不出错”，而是“出了问题能快速定位和回滚”。

5. **大多数 Skills 应该跟项目走，不要放全局**  
   推荐放在项目目录下的 `.agents/skills`，而不是 `~/.agents/skills`。  
   因为全局 Skills 会不断累积，增加上下文负担。

---

##### 深入浅出地解读

###### 1. 为什么要用 Git？
因为 Skills 虽然看起来像“文档”，但实际上已经很接近“配置 + 规则 + 自动化逻辑”。

它们有几个典型工程特征：

- 会不断修改
- 修改后可能影响行为
- 需要知道“谁改了什么”
- 改坏了要能回退

所以它不只是“写说明书”，更像是在维护一套 Agent 的“操作系统补丁”。  
这时用 Git，比用纯文档协作工具更靠谱。

---

###### 2. 为什么 Symlink 很关键？
作者强调不要复制 Skills 到 `.agents/skills`，而要用 **符号链接** 指向原始 Repo。  
本质上是在解决“多份副本不同步”的问题。

通俗说：

- **拷贝**：像复印文件，改了原件，复印件不会变
- **Symlink**：像快捷方式，实际一直指向同一份文件

这样做的好处是：

- 只有一个“真实来源”，不容易改乱
- Agent 在使用中发现问题，可以直接改源码 Repo
- 修改后立刻能走 Review / PR / 发布流程

这其实是在建立一个很重要的原则：  
**Skills 要有唯一真源（single source of truth）。**

---

###### 3. 为什么“让 Agent 来改 Skill”是个好思路？
因为 Skill 本来就是给 Agent 用的，Agent 参与维护，天然形成闭环：

- 用的时候发现问题
- 让 Agent 直接改
- 人来 Review
- 再合并发布

这种方式的价值在于：  
**问题出现在哪个场景，就在那个场景里修。**

这比“先记下来，回头再找人改”效率高很多。  
也就是说，Skill 维护不应该脱离实际使用场景。

---

###### 4. 为什么验证难？
难点在于：  
Skill 不全是代码，还有很多是提示词、流程描述、约束规则。

这类内容不像函数那样容易写自动化测试。  
比如你很难完全自动判断：

- 这段说明是否更清晰
- 这个规则是否让 Agent 更稳定
- 某个改动是否只在少数场景下退化

所以作者的思路很现实：  
**既然难以一次验证彻底，那就把重点放在“快速试错、快速定位、快速回滚”上。**

这是一种典型的工程化思维，不追求完美验证，而追求低成本迭代。

---

###### 5. 为什么不建议把大多数 Skills 放全局？
因为全局 Skills 看起来方便，实际容易失控。

问题在于：

- 项目 A 的 Skill，项目 B 不一定需要
- Skills 越多，Agent 读取的 meta 信息越多
- 上下文空间会被占用，影响效率和效果

所以更合理的做法是：  
**项目需要什么，就在项目内挂什么。**

这样有几个好处：

- 依赖更明确
- 上下文更干净
- 项目迁移和协作更清晰

本质上，这和“代码依赖按项目管理，不乱装全局包”是同一个逻辑。

---

##### 我的意见

我比较认同作者的整体判断，尤其是这 3 点：

- **把 Skills 当工程资产管理，而不是普通知识库**
- **坚持唯一源头，尽量避免复制**
- **接受验证不完美，重点建设可回滚能力**

如果再补充一点，我会建议团队在实践时注意下面几个方面：

###### 1. 给 Skills 分层
不是所有 Skill 都该放一起，建议至少分成：

- **项目级**：只服务当前项目
- **团队级**：多个项目通用
- **个人级**：个人习惯增强

这样能减少混乱，也方便权限和发布管理。

###### 2. 建立最小验证机制
即使 Markdown 很难自动测，也可以做一些“低成本检查”：

- 目录结构检查
- 元信息格式检查
- 链接有效性检查
- 示例是否能跑通
- 关键场景回归清单

不用追求完备，但要有基本门槛。

###### 3. 约束 Symlink 的使用规则
Symlink 很好，但确实可能越用越乱。  
所以最好补几条团队约定，比如：

- 只能指向哪些 Repo
- 是否允许多层链接
- 如何命名
- 如何声明依赖关系

这样能避免后期“看起来能用，实际没人敢动”。

---

##### 结论

这篇分享最有价值的地方，不是某个具体工具，而是它背后的思路：

> **Skill 不是静态文档，而是需要持续迭代的工程资产。**

因此，团队真正需要的不是单纯“协作文档平台”，而是：

- 有版本管理
- 有唯一来源
- 有修改流程
- 有验证手段
- 有回滚能力

如果做到这几点，Skills 才能真正成为团队能力沉淀，而不是越来越乱的提示词仓库。
