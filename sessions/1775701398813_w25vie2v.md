## 分析要点

- **核心高价值点**：最有价值的是用小规模实验先比较不同GPU的吞吐与总成本，再决定并行策略，而不是直接拍脑袋上大规模任务。
- **留存建议**：短期参考后可归档，适合作为AI代理驱动批处理任务的案例素材（包含真实的规模化OCR流水线、成本对比与基础选型过程，可作为后续搭建类似任务的参考样例）

**知识要点**

- 可借助OCR基准榜单选择适合将文档转Markdown的开源模型
- 在批量文档处理任务中，GPU单价低不代表总成本低，需结合吞吐量评估
- 将存储挂载为本地文件系统可显著简化批处理脚本和上传下载逻辑

**行动项**

- 对自己的批处理任务先做小样本基准测试，比较不同GPU的速度与总成本
- 尝试将LLM编码代理用于脚本生成、作业提交和运行监控等重复性工程流程

On the hub, we index [arXiv](https://www.arxiv.org) papers any time someone mentions an arXiv abstract or PDF link in the README of a model, dataset or Space. Besides, any researcher can submit their work to [Daily Papers](https://hf.co/papers) at [https://hf.co/papers/submit](https://hf.co/papers/submit), up to 14 days after the publication date on arXiv.

![Daily Papers](https://huggingface.co/datasets/nielsr/blog-images/resolve/main/Screenshot%202026-04-07%20at%2016.18.44.png)  
*Daily Papers view.*

This enables researchers to promote their work by claiming papers using their Hugging Face account (by simply clicking on your name which will feature it on your account), as well as link the corresponding Hugging Face models, datasets and Spaces, Github URL and project page. Moreover, people can upvote and comment on papers in a Reddit-like way. Finally, it is now also possible to tag papers with organizations, enabling one to feature all research papers on a given organization page such as [NVIDIA](https://huggingface.co/nvidia/papers) or [Google](https://huggingface.co/google/papers). The [@HuggingPapers account on X](https://x.com/HuggingPapers/) also frequently shares about the top trending research on the hub.

Check at your own papers at [https://huggingface.co/settings/papers](https://huggingface.co/settings/papers)!

#### HuggingChat integration

Each Hugging Face paper page now features a "chat with paper" functionality powered by [HuggingChat](https://hf.co/chat). Behind the scenes, this uses the HTML web page of the arXiv paper (e.g. [https://arxiv.org/abs/2603.26599](https://arxiv.org/abs/2603.26599) can be viewed using [https://arxiv.org/html/2603.26599](https://arxiv.org/html/2603.26599)). The HTML gets turned into Markdown, which is then fed to the LLM as context.

![HuggingChat integration](https://cdn-uploads.huggingface.co/production/uploads/60a551a34ecc5d054c8ad93e/sxfNLyrF1VTsqra8d4KH_.png)  
*HuggingChat integration on paper pages.*

However, as it turned out, about 27,000 papers indexed on Hugging Face do not have a corresponding HTML web page on arXiv, making it not possible to chat with those papers. Hence, the idea was pretty simple: let's use an open Optical Character Recognition (OCR) model to convert those papers to Markdown.

#### Using a state-of-the-art open OCR model

As we needed an open OCR model, it might be hard to know which one to use. Luckily, the Hugging Face team is working on a new feature called [Evaluation results](https://huggingface.co/docs/hub/eval-results), which allows to turn Hugging Face datasets into native leaderboards on the hub. Evaluation results are added by opening pull requests on model repositories, which show up on the respective dataset. Find the current leaderboards [here](https://huggingface.co/datasets?benchmark=benchmark:official&sort=trending).

For now, [OlmOCRBench](https://huggingface.co/datasets/allenai/olmOCR-bench) by AllenAI is the go-to benchmark for OCR. It's a pretty good place to find which open models are best at converting documents into Markdown, interleaved with HTML for the images and tables contained in them.

![OlmOCRBench leaderboard](https://huggingface.co/datasets/nielsr/blog-images/resolve/main/Screenshot%202026-04-07%20at%2016.27.00.png)  
*OlmOCRBench leaderboard on the hub.*

Hence, we simply decided to use the best model at the time of writing, which is [Chandra-OCR 2](https://huggingface.co/datalab-to/chandra-ocr-2) by Datalab. As the model is openly available with an [OpenRAIL license](https://huggingface.co/datalab-to/chandra-ocr-2/blob/main/LICENSE), we can freely use it for commercial purposes using frameworks like Transformers and vLLM.

#### Using Hugging Face Jobs

To run models like Chandra at scale to process thousands of papers, it's recommended to leverage vLLM on GPU infrastructure. In our case, we leveraged [Jobs](https://huggingface.co/docs/hub/jobs) as the serverless compute platform to run the model. Jobs supports both CPUs and GPUs, from an Nvidia T4 all the way to a 8x Nvidia H200s, with pay-as-you-go pricing where you only pay for seconds used.

We could write a script ourselves to run the model using vLLM on Jobs. However, as it's 2026, nowadays we can simply point a coding agent such as Claude Code, Cursor or Codex to a set of URLs and it will figure it out by itself. So that's exactly what we did.

We simply asked OpenAI's Codex model (via the [Codex Desktop app](https://developers.openai.com/codex/app)) to implement a script which runs Chandra-OCR-2 on the 27,000 arXiv IDs which currently have their Markdown version missing on the hub on Jobs. We point it to Chandra's [model card](https://huggingface.co/datalab-to/chandra-ocr-2/raw/main/README.md) so it knows how to run it with vLLM, and provide it with the [Hugging Face Jobs Skill](https://github.com/huggingface/skills/blob/main/skills/huggingface-jobs/SKILL.md) so it knows how to use Hugging Face's serverless GPU infra.

![Codex and chill](https://huggingface.co/datasets/nielsr/blog-images/resolve/main/Screenshot%202026-04-07%20at%2016.33.39.png)  
*Codex and chill. The first prompt I sent to Codex*

##### Which GPUs to use?

As Jobs offers [many GPU flavours](https://huggingface.co/docs/hub/jobs-pricing), I first asked Codex to do some comparisons on a small scale (120 papers) to see which GPUs to use and to estimate their costs. It did experiments on an Nvidia A10G-large as well as an Nvidia L40S GPU by launching jobs in parallel. It concluded to use the L40S, as it was able to process papers faster (about 60/hour when parsing at most 30 pages for each paper compared to 32/hour on the A10G).

Moreover, it recommended to run 16 jobs in parallel, as processing all papers on a single L40S GPU would take multiple weeks. Running 16 parallel jobs would take about 29-30 hours. It estimated the cost to be about $850. Interestingly, 16x A10G-large is cheaper per hour but slower overall, which would ultimately lead to a larger cost of about $1350.

For comparison, I also asked Codex how much this would cost with Chandra's [own API](https://www.datalab.to/pricing): $1,841.07 for "fast/balanced" mode and $2,761.60 for "high-accuracy" mode.

![Codex GPU recommendations](https://huggingface.co/datasets/nielsr/blog-images/resolve/main/Screenshot%202026-04-07%20at%2016.38.29.png)  
*Codex giving me GPU recommendations*

Hence, Codex spun up the 16 jobs and monitored their performance. No jobs had to be restarted, they all worked from the first try. Some jobs took longer than others, mainly because they contained many papers with more pages to parse.

##### Mounted buckets

At first, we would simply let the script write the results to a Hugging Face dataset. However, the Hugging Face team leverages [Buckets](https://huggingface.co/docs/hub/storage-buckets) for storing the Markdown version of each paper. Buckets are not versioned by git, and instead powered by [Xet](https://huggingface.co/docs/hub/en/xet/index) for fast, cheap and mutable storage. As new papers get added every day, this would result in a huge amount of git commits, hence Buckets are more suited here.

Moreover, the team just launched [hf-mount](https://github.com/huggingface/hf-mount), which enables to mount Hugging Face Buckets (as well as model, dataset or Spaces repos) as local filesystems. This means that we no longer require to write download/upload functionality: the script (or coding agents in general) can just write to the bucket as it it were local.

Hence I simply prompted Codex to write to a mounted bucket instead of a Hugging Face dataset, which made the scripts even faster.

#### The results

During the run, I frequently asked Codex the same thing: "Great. Can you check the progress?". It then got back to me, telling me how many of the 16 parallel jobs had already finished. After about a day, all 16 jobs were finished.

![Codex babysitting](https://huggingface.co/datasets/nielsr/blog-images/resolve/main/Screenshot%202026-04-07%20at%2016.42.19.png)  
*Codex babysitting the runs on Jobs*

I then asked it to merge the 16 buckets into a single one. Finally, [Mishig](https://huggingface.co/mishig) integrated them into Paper Pages, so now you can chat with any paper on the hub, not just the ones which have an HTML version on arXiv! Try it for instance at [https://huggingface.co/papers/2603.15031](https://huggingface.co/papers/2603.15031).

#### Resources

Find the code [here](https://github.com/NielsRogge/arxiv-ocr) and the resulting bucket [here](https://huggingface.co/buckets/nielsr/arxiv-chandra-ocr-full-markdown-20260406).

## 通俗精炼（1）

### 2026-04-09 02:23:18

#### 用 Codex + 开源 OCR + Jobs，低成本批量 “读懂” 3 万篇论文

##### 一、这篇文章讲了什么

Hugging Face 希望让用户能直接 “和论文对话”。  
但问题是：平台上约有**2.7 万篇 arXiv 论文没有 HTML 页面**，无法直接转成文本给大模型读取。

他们的解决方案很直接：  
用**开源 OCR 模型**把 PDF 论文转成 Markdown，再接入现有的 “chat with paper” 功能。

---

##### 二、核心做法

###### 1. 选最强的开源 OCR 模型
团队没有自己拍脑袋选模型，而是参考 OCR 榜单**OlmOCRBench**，最终选择了当时表现最好的**Chandra-OCR 2**。  

原因很简单：
- 效果好，适合把论文转成 Markdown
- 开源可商用
- 能直接配合`Transformers`和`vLLM`跑大规模任务

###### 2. 用 Hugging Face Jobs 跑大规模任务
要处理几万篇论文，单机肯定太慢，所以他们用了**Hugging Face Jobs**作为无服务器 GPU 计算平台。  

它的价值在于：
- 支持多种 GPU
- 按秒计费
- 适合批量、并行处理

---

##### 三、Codex 在里面扮演了什么角色

###### 1. 不只是写代码，而是 “代做项目”
作者没有手写整套脚本，而是直接让**Codex**：
- 根据模型文档理解如何运行 Chandra-OCR 2
- 调用 Hugging Face Jobs
- 编写批处理脚本
- 启动并监控任务

本质上，Codex 承担了一个 “工程代理人” 的角色，而不只是代码补全工具。

###### 2. 先做小规模测试，再决定资源配置
他们先让 Codex 用**120 篇论文**做实验，对比不同 GPU 的速度和成本。

结论是：
- **L40S**比 A10G 更快
- 最终选择**16 个并行任务**
- 总耗时约**29~30 小时**
- 总成本约**850 美元**

对比下来：
- `16x A10G`虽然单价便宜，但整体更慢，总成本反而更高
- 如果直接用 Chandra 官方 API，成本会更高，约**1841~2761 美元**

一句话：**自己跑开源模型，比直接调用商业 API 更划算。**

---

##### 四、工程优化的关键细节

###### 1. 存储方式从 Dataset 改成 Bucket
一开始，他们打算把结果写到 Hugging Face Dataset。  
后来发现这不适合高频、大规模写入，因为会产生很多 git 提交。

于是改用**Buckets**：
- 更适合大量文件存储
- 成本更低
- 可变更、效率更高

###### 2. 用`hf-mount`把远程存储当本地磁盘
新工具`hf-mount`可以把 Bucket 挂载为本地文件系统。  
这样脚本就能像写本地文件一样直接输出结果，不需要再单独处理上传下载逻辑。

这一步的价值很大：  
**让分布式批处理的工程复杂度明显下降。**

---

##### 五、最终结果

###### 1. 一天左右完成全部任务
16 个并行任务全部一次跑通，无需重启。  
Codex 还承担了运行过程中的 “监工” 角色，持续汇报进度。

###### 2. 成果真正进入产品
最后，团队把 16 份结果合并，并接入论文页面。  
现在，Hugging Face 上的论文聊天功能，不再只局限于有 HTML 的 arXiv 论文，**几乎所有论文都能聊了**。

---

##### 六、这篇文章的核心启发

###### 1. AI Agent 已经从 “辅助写代码” 走向 “执行完整工作流”
Codex 不只是生成函数，而是在：
- 做方案选择
- 做成本评估
- 写脚本
- 跑任务
- 查进度
- 合并结果

这意味着，AI 正在从工具升级为 “可委派的执行单元”。

###### 2. 开源模型 + 云端算力 + Agent，正在形成新生产力组合
这套组合的本质是：
- **开源模型**负责能力
- **云计算平台**负责规模
- **Agent**负责工程编排

三者结合后，很多过去需要工程团队投入数天甚至数周的任务，现在可以更快落地。

###### 3. 产品价值不在模型本身，而在 “最后一公里接入”
真正产生用户价值的，不是 “我们 OCR 了 3 万篇论文”，而是：
**用户现在可以和更多论文直接对话。**

这说明一个很重要的产品思路：  
**技术动作本身不是价值，接入用户场景才是价值。**

---

##### 七、一句话总结

这篇文章本质上展示了一种新范式：  
**用 AI Agent 调度开源模型和云资源，把一个大规模、繁琐的工程任务快速自动化，并直接转化为产品能力。**

## 趣读意义（1）

### 2026-04-09 02:24:22

#### 这篇文章，值钱的不是 OCR，值钱的是 “把脏活变成产品能力”

这件事表面上是在讲：Hugging Face 用开源 OCR + Codex + Jobs，批量处理了 3 万篇论文。

更深一层看，它其实展示了一套非常适合产品经理借鉴的打法：

> 先找到用户体验里的 “断头路”，再用 AI + 基础设施，把它补成平台能力。

这里的 “断头路” 很具体：  
很多论文页面能看、能挂链接、能被讨论，但**不能 chat with paper**。原因也很现实：2.7 万篇论文没有 arXiv HTML，只剩 PDF。

这不是 “功能缺失”，这是典型的**体验不连续**。  
用户上一秒还在顺畅地和论文对话，下一秒就掉进 PDF 黑洞。产品价值就在这里漏掉了。

---

#### 我看到的 5 个关键启发

##### 1. 真正该优先做的，不是新功能，是补齐 “能力断层”

很多团队喜欢追新入口、新按钮、新 Agent。  
这篇文章最聪明的地方，是没有继续造新东西，而是把已有能力覆盖到剩余长尾。

对产品经理的提醒很直接：

- 用户最强感知，往往来自 “一致性”，不是 “功能数量”
- 你已经有 70% 的能力时，剩下 30% 的缺口，常常决定口碑
- 长尾场景一旦补齐，产品会从 “好用” 变成 “可靠”

可直接套用的判断框架：

- 哪些核心路径只覆盖了头部用户？
- 哪些功能在宣传页成立，在真实数据里却经常失效？
- 哪些 “少数失败样本”，其实在持续破坏用户信任？

一句话说，这篇文章做的不是 OCR 项目，是**把产品从局部可用，推进到系统可用**。

---

##### 2. AI 在这里最有价值的角色，不是 “替你思考”，是 “替你调度复杂性”

文章里 Codex 干了几件很有代表性的事：

- 看模型卡，理解怎么部署
- 结合 Jobs Skill，自己拼出执行方案
- 先小样本压测，比较 GPU 成本和速度
- 决定并行策略
- 运行中持续查进度
- 最后合并产物

这很像一个靠谱的初级技术项目经理 + 运维助手。

对产品经理特别有参考意义的一点是：

> 未来很多 AI 场景，真正的杠杆不在 “生成内容”，在 “编排工作流”。

也就是：

- 读文档
- 做选择
- 跑实验
- 监控过程
- 处理结果

这类任务以前很碎，很依赖熟手；现在开始能被 Agent 接住。

你在设计 AI 产品时，可以优先找这类机会：

- 原本要跨 3 个系统、读 5 份文档才能完成的流程
- 有明确目标，但中间步骤繁琐、重复、容易出错
- 结果可验证，过程可观察，适合 agent 执行闭环

这样的场景，最容易做出真实 ROI。

---

##### 3. 好的 AI 项目，不靠 “大模型万能”，靠 “基准测试 + 成本纪律”

文章里有个特别务实的细节：  
他们没有拍脑袋选模型，也没有迷信 “最新最强”，而是直接看 OCR leaderboard，选择当时开源里表现最好的 Chandra-OCR 2。

然后又做了第二层判断：

- A10G 和 L40S 哪个更划算？
- 单卡多慢？
- 16 并行多久？
- 总成本多少？
- 如果用官方 API，会贵多少？

这很像成熟团队做决策的样子：  
**先 benchmark，再规模化。**

对产品经理的现实启发：

###### 做 AI 功能时，别只问 “能不能做”，要连着问 4 件事

- 准确率够不够上线？
- 单位成本能不能承受？
- 峰值时延会不会毁体验？
- 规模放大后，账还算不算得过来？

这篇文章很漂亮的一点，是把 “技术可行性” 翻译成了 “经营可行性”：

- L40S 更贵，但更快，所以总成本更低
- API 更省事，但总价更高
- 并行数不是越多越好，而是要落在时间与成本的平衡点

这是典型的产品判断力：  
**不是选最先进的方案，是选总收益最优的方案。**

---

##### 4. 基础设施一旦 “像本地一样好用”，组织效率会突然跃迁

文中还有个很容易被忽视、但非常关键的点：`hf-mount`。

它的意义不只是 “挂载 bucket”，而是把远程存储变成了本地文件系统体验。  
一旦做到这一步，很多脚本、工具、Agent 都能直接复用，不需要再写一堆上传下载逻辑。

这背后的产品洞察很强：

> 真正好的平台能力，是让复杂系统在使用者眼里消失。

对产品经理来说，这意味着：

- 不要只关心主功能，要重视 “接入摩擦”
- 一个能力如果需要用户理解太多底层概念，它就很难被大规模使用
- 降低心智负担，往往比多加一个功能更能提高 adoption

你可以检查自己的产品：

- 有没有一些能力理论上存在，但接入步骤过长？
- 有没有很多 “胶水工作” 还得靠人工拼？
- 有没有把 “平台能力” 做成 “用户必须自己处理的工程问题”？

很多增长瓶颈，其实不是能力不够，是**可用性包装不够**。

---

##### 5. Agent 产品的理想体验，像 “会汇报的同事”，不是 “炫技的魔法师”

文章里最有画面感的一幕是：  
作者不断问 Codex 一句话 ——“Great. Can you check the progress?”

然后 Codex 去看 16 个 job 的状态，再回来汇报。

这件事很小，但它定义了一个很重要的 AI 产品体验标准：

###### 用户不想一直操心，只想在关键节点被告知

也就是说，好的 Agent 应该具备：

- 能接任务
- 能执行
- 能监控
- 能回报
- 出问题能定位

这比 “帮你写一段代码” 更接近真实工作场景。

对做 AI 产品的人，一个非常实用的设计原则是：

- 少展示模型有多聪明
- 多展示任务现在进行到哪一步
- 给用户 “可托付感”

用户愿意把事交给你，不是因为你会说，而是因为你**让过程透明、结果可信**。

#### 对你做产品，最可复用的 3 个动作

##### 1. 先找 “高频主路径里的长尾断点”
别急着定义新需求，先把这几个问题问清楚：

- 用户在哪些关键路径上经常掉线？
- 哪些失败场景占比不大，但破坏感受很重？
- 哪些能力只服务了头部样本，没覆盖真实全量数据？

优先补这些地方，收益通常很高。

##### 2. 把 AI 用在 “编排任务” 上，而不是只用来 “生成内容”
优先挑这些场景做 agent：

- 需要查文档
- 需要调用多个工具
- 需要做实验比较
- 需要持续看进度
- 需要最终整理结果

这是最容易做出稳定价值的一类 AI 产品。

##### 3. 每个 AI 项目都做一张 “单位经济表”
上线前至少确认：

- 单次处理成本
- 平均耗时
- 成功率
- 并行后的总吞吐
- 替代人工 / 替代 API 的节省额

很多项目 demo 很惊艳，规模一放大就失真。

## 产品-最佳实践（1）

### 2026-04-09 02:31:48

#### 基于案例的最佳实践：用 Codex + 开源 OCR + Jobs 批量 OCR 30,000 篇论文

##### 一句话概括这个案例

这个案例的核心是：**先让 Codex 帮你搭建和评估一套批量 OCR 流水线，再用 Hugging Face Jobs 在 GPU 上并行执行，最终把 27,000+ 篇没有 HTML 版本的 arXiv 论文转成 Markdown，供 “chat with paper” 功能使用。**

---

##### 具体实例

下面用一个更具体、可复用的实例来说明：

> 你是一个科研平台工程师，发现平台中有**30,000 篇 PDF 论文无法直接做问答**，因为它们没有结构化 HTML。
> 你的目标是：
>
> 1. 用开源 OCR 模型把 PDF 转成 Markdown  
> 2. 成本可控  
> 3. 处理速度快  
> 4. 支持失败重试和进度追踪  
> 5. 最终把结果存到适合大规模持续写入的对象存储 / 桶中

在文中，团队选择了：

- **OCR 模型**：`Chandra-OCR 2`
- **算力平台**：`Hugging Face Jobs`
- **推理框架**：`vLLM`
- **存储方式**：从 dataset 改为**mounted bucket**
- **执行策略**：先小规模 benchmark，再 16 个并行 job 全量跑

这是一个非常典型的 “**代理编排 + 开源模型 + 批处理基础设施**” 实践案例。

---

##### 这个实例之上的最佳实践

##### 1. 先做 “小样本基准测试”，不要一开始就全量跑

###### 为什么这是最佳实践

文中最值得借鉴的一点，不是 “用了什么模型”，而是：**先拿 120 篇论文做对比实验，再决定 GPU 和并发数。**

这避免了两个常见错误：

- 直接上最贵 GPU，造成资源浪费
- 只看单卡时延，不看 “总吞吐 / 总成本”

###### 推荐做法

在正式跑 30,000 篇之前，先抽一个代表性样本集，例如：

- 轻量论文：10 页以内
- 中等论文：10–30 页
- 重型论文：30 页以上
- 含大量表格 / 图片 / 双栏排版的论文

然后比较不同组合：

- 模型是否稳定
- GPU 吞吐量
- 单篇平均耗时
- 每小时成本
- 每千篇成本
- OCR Markdown 质量

###### 这类实践的关键指标

```markdown
- 吞吐量：papers/hour
- 单篇平均耗时：seconds/paper
- 单页平均耗时：seconds/page
- 成本：$/1000 papers
- 失败率：job failure rate
- 质量：Markdown 可读性、标题层级、公式 / 表格保真度
```

###### 本案例中的启示

文中比较了`A10G-large`和`L40S`，最终发现：

- `L40S`更快
- 虽然`A10G-large`每小时更便宜
- 但因为整体更慢，**总成本反而更高**

这说明：**做基础设施选型时，不要只盯 “单价”，要看 “完成同一任务的总成本”。**

---

##### 2. 模型选择要基于公开 benchmark，但上线前必须做 “业务验证”

###### 为什么这是最佳实践

文中通过`OlmOCRBench`选择了当时表现最好的开源 OCR 模型`Chandra-OCR 2`。这是正确的第一步，但如果要形成长期稳定流程，**benchmark 只是起点，不是终点**。

###### 推荐做法

把模型选择拆成两层：

###### 第一层：公开榜单选 shortlist

先看：

- 文档 OCR -> Markdown 的整体能力
- 表格保留能力
- 图片、公式、标题层级处理
- 许可证是否可商用

###### 第二层：业务数据验证

再用你自己的论文样本验证：

- 双栏论文会不会乱序
- 数学公式会不会被破坏
- 表格会不会变成无结构文本
- 页眉页脚是否被误识别为正文
- 参考文献和正文是否能区分

###### 最佳实践建议

不要只问 “哪个模型最好”，而要问：

> **哪个模型在我的数据分布、预算上限、吞吐目标、许可证要求下最合适？**

###### 可直接复用的评估框架

```markdown
模型评估维度：
- OCR 准确率
- Markdown 结构质量
- 表格保真度
- 公式可读性
- 多栏布局稳定性
- 推理速度
- GPU 显存占用
- 商业许可兼容性
```

---

##### 3. 让 Codex 做 “实验、脚本、编排”，但人要保留决策权

###### 为什么这是最佳实践

文中非常有代表性的一点是：**Codex 负责实现和执行，工程师负责给目标、约束和判断标准。**

这是代理协作中最有效的模式。

###### 推荐分工方式

###### 让 Codex 做的事

- 根据模型卡生成推理脚本
- 按 Hugging Face Jobs 规范编写 job 脚本
- 自动切分任务列表
- 并行启动作业
- 汇总日志和进度
- 估算成本
- 合并输出结果

###### 让人类做的事

- 定义成功标准
- 决定预算上限
- 决定可接受的 OCR 质量
- 决定是否截断最大页数
- 决定是否切换模型 / GPU
- 处理异常结果和边界样本

###### 最佳实践原则

> **把 Codex 当作 “高效执行者”，不要当作 “无人监管的全自动决策系统”。**

###### 一个更好的提示词写法

相比 “帮我把 30,000 篇论文 OCR 了”，更好的提示词应该包含：

```markdown
目标：
- 将 27,000 篇缺失 Markdown 的 arXiv PDF 转为 Markdown

约束：
- 仅使用开源 OCR 模型
- 必须可商用
- 优先使用 Hugging Face Jobs
- 输出写入 mounted bucket
- 单篇论文最多处理 30 页
- 先对 120 篇样本做 GPU 对比实验
- 给出吞吐量、成本、失败率、推荐 GPU、推荐并发数

交付：
- 可运行脚本
- job 划分方案
- 进度监控方案
- 失败重试策略
- 最终结果合并方案
```

这种提示方式会显著提升 Codex 输出的可靠性。

---

##### 4. 批处理任务一定要 “分片”，不要做一个巨型单任务

###### 为什么这是最佳实践

文中将任务拆成了**16 个并行 jobs**，这是大规模文档处理中的关键实践。

如果你把 30,000 篇论文塞进一个任务里，会遇到：

- 一个错误拖垮全局
- 难以定位失败样本
- 难以重试
- 难以估算剩余时间
- 单任务运行时间过长，风险上升

###### 推荐做法

按以下方式切分任务：

- 按论文数量分片
- 按总页数分片
- 按预估计算量分片
- 保证每个 job 运行时间在合理窗口内

###### 更优做法：按 “页数总量” 而非 “论文数量” 切分

因为 100 篇 5 页论文和 100 篇 50 页论文的计算量差别极大。

推荐的任务切分指标：

```markdown
优先使用：
- 每个 job 的总页数接近
- 每个 job 的预估运行时间接近

避免仅使用：
- 每个 job 相同论文数
```

###### 最佳实践补充

每个 job 都应具备：

- 独立输入清单
- 独立日志
- 独立输出目录
- 独立失败记录
- 可单独重试

---

##### 5. 存储层要适配 “高频写入 + 大量文件”，不要机械地用 Git 仓库

###### 为什么这是最佳实践

文中一开始考虑写 Hugging Face dataset，后来改为**bucket + hf-mount**。这是一个很典型的工程升级。

原因很清楚：

- 论文 Markdown 文件数量巨大
- 每天还会新增
- 如果用 git 版本化，会产生大量 commit
- 对频繁写入、更新、小文件场景不够友好

###### 推荐做法

对于这种场景，优先选：

- bucket /object storage
- 支持挂载为本地文件系统
- 支持低成本海量写入
- 支持并发任务写入

###### 最佳实践原则

> **把 Git 用在 “代码和配置”，把对象存储用在 “高频产出和批量结果”。**

###### 目录组织建议

```markdown
bucket/
  raw/
    shard-000/
    shard-001/
  markdown/
    2603.15031.md
    2603.26599.md
  logs/
    shard-000.log
    shard-001.log
  manifests/
    shard-000.jsonl
    shard-001.jsonl
  failed/
    shard-003-failures.jsonl
```

这样后期补跑、审计、合并都更容易。

---

##### 6. 进度追踪必须 “可观测”，不要靠任务结束后才看结果

###### 为什么这是最佳实践

文中提到，作者不断问 Codex：“Can you check the progress?”  
这说明整个流程是**可监控**的，而不是 “提交后祈祷”。

###### 推荐做法

至少监控以下内容：

- 已完成论文数
- 剩余论文数
- 各 job 当前状态
- 平均处理速度
- 失败论文列表
- 成本累计
- 预计完成时间 ETA

###### 最佳实践建议

每个 job 定期输出结构化状态文件，例如：

```json
{
  "job_id": "ocr-shard-07",
  "processed_papers": 1832,
  "failed_papers": 12,
  "avg_seconds_per_paper": 54.3,
  "estimated_remaining_minutes": 97,
  "last_updated": "2026-04-07T12:10:00Z"
}
```

这样 Codex、脚本、运维人员都可以统一读取。

###### 最佳实践原则

> **大规模 OCR 不是 “跑脚本”，而是 “运营一个批处理系统”。**

---

##### 7. 提前设计失败重试机制，而不是事后人工补洞

###### 为什么这是最佳实践

文中提到 16 个 job 一次成功，这很理想，但在真实生产环境里，必须假设会出现：

- PDF 损坏
- 超大文件超时
- GPU OOM
- 网络抖动
- OCR 模型输出空结果
- bucket 写入失败

###### 推荐做法

给每篇论文记录处理状态：

```markdown
- pending
- running
- success
- failed_retryable
- failed_permanent
```

###### 重试策略建议

- 临时失败：自动重试 2~3 次
- 超大论文：降级处理，如只处理前 30 页
- 模型崩溃：记录输入并隔离样本
- 输出为空：进入人工抽检队列

###### 最佳实践原则

> **不要重跑整个批次，只重跑失败样本。**

这会极大节省成本和时间。

---

##### 8. 质量控制不能只看 “有没有输出”，要看 “能不能被下游消费”

###### 为什么这是最佳实践

文中最终目标不是 “生成 Markdown 文件”，而是让用户可以**chat with paper**。  
所以真正重要的是：**Markdown 是否适合被 LLM 当作上下文。**

###### 推荐质量检查项

###### 结构质量

- 标题层级是否正确
- 段落是否连贯
- 双栏是否乱序
- 参考文献是否污染正文

###### 内容质量

- 公式是否可读
- 表格是否仍有结构
- 图片说明是否保留
- 页眉页脚是否被错误写入正文

###### 下游适配质量

- 是否方便切 chunk
- 是否方便向量化
- 是否容易做 section-level retrieval
- 是否会因噪声过多影响问答

###### 最佳实践建议

抽样检查不要只看 5 篇 “好看的”，而要覆盖：

- 数学论文
- 生物医学论文
- 含复杂表格的论文
- 老 PDF 扫描件
- 双栏排版论文

---

##### 9. 成本优化的核心不是 “最便宜”，而是 “单位有效结果成本最低”

###### 为什么这是最佳实践

文中对比得很清楚：

- `A10G-large`小时价格更低
- 但整体更慢
- 最终总成本更高

这说明在大规模任务里，真正该优化的是：

> **每 1000 篇有效处理结果的成本**

###### 推荐关注的真实成本指标

```markdown
- cost per 100 papers
- cost per 1000 pages
- cost per successful paper
- total wall-clock time
- operator time（人工盯任务所花时间）
```

###### 最佳实践原则

> **工程成本 = GPU 成本 + 失败重试成本 + 人工运维成本 + 下游修复成本**

单看 GPU 账单，往往会得出错误结论。

---

##### 10. 最后合并产出时，要保留 “可追溯性”

###### 为什么这是最佳实践

文中最后让 Codex 合并了 16 个 bucket。  
这一步很常见，但如果只做 “合并”，不保留来源信息，后面会很难排错。

###### 推荐做法

每个输出文件保留元数据，例如：

```yaml
paper_id: 2603.15031
source_pdf: arxiv://2603.15031
ocr_model: datalab/Chandra-OCR-2
job_id: ocr-shard-07
gpu_type: L40S
processed_at: 2026-04-07T11:52:03Z
page_limit: 30
status: success
```

###### 最佳实践价值

这样后续你可以快速回答这些问题：

- 哪些文件是哪个 job 生成的？
- 哪批结果用的是哪个模型版本？
- 哪些论文被截断到 30 页？
- 哪些结果需要补跑？

---

##### 一个可直接复用的实施模板

##### 场景

将 30,000 篇学术 PDF 转成可供 LLM 问答的 Markdown。

##### 推荐流程

```markdown
1. 明确目标
   - 输出 Markdown
   - 用于论文问答
   - 成本和时长有上限

2. 选模型
   - 基于公开 OCR leaderboard 初筛
   - 用真实论文样本复核

3. 小规模压测
   - 选 100~200 篇样本
   - 比较多个 GPU 和并发参数
   - 输出吞吐 / 成本 / 失败率

4. 任务切分
   - 按总页数或预估时长切 shard
   - 每个 shard 独立输入、输出、日志

5. 大规模运行
   - 并行提交 jobs
   - 实时监控状态和成本

6. 异常处理
   - 自动重试临时失败
   - 隔离永久失败样本
   - 记录失败原因

7. 质量抽检
   - 抽查不同论文类型
   - 验证 Markdown 是否适合下游 RAG/QA

8. 合并与落库
   - 输出统一目录结构
   - 保留元数据和可追溯信息

9. 持续增量更新
   - 每日只处理新增论文
   - 不重跑全量
```

---

##### 最值得借鉴的三条经验

###### 1. 先 benchmark，再扩规模
不要先做 “大工程”，先做 “小实验”。

###### 2. 代理负责执行，人类负责约束
Codex 很适合写脚本、跑实验、监控进度，但目标、预算和质量门槛必须由人设定。

###### 3. 把这件事当作 “批处理系统建设”
不是 “写个 OCR 脚本” 就结束，而是要考虑：

- 分片
- 可观测性
- 重试
- 成本
- 存储
- 质量
- 增量更新

---

##### 一个简短结论

这个案例最强的地方，不是 “用 Codex 跑了 30,000 篇论文”，而是它体现了一套很成熟的方法论：

> **用公开 benchmark 选模型，用小样本实验选算力，用代理搭系统，用并行 job 放大吞吐，用合适存储承接结果。**

如果你也要落地类似项目，无论对象是论文、合同、发票、技术手册还是扫描档案，这套最佳实践都可以直接迁移。
