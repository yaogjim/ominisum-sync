## 正文

**Rohit Ghumare**

几乎所有人都在用错误的方式构建代理工具系统。

默认做法是：选择 LangChain、LangGraph 或 OpenAI Agents SDK，接受循环、工具、内存、编排、策略引擎、凭证存储、预算跟踪器，把所有这些都当作一个决策来接受。

Mike 今天写了一篇长文，阐述为什么这种架构是错误的，以及为什么每个长期运行的代理团队最终都会从头重写自己的工具系统。

他的论点是： 工具系统不是单一的东西。它是十五个独立的关注点被捆绑在一起，因为周边生态系统没有提供一种组合它们的方式。包括状态机、提供商路由、凭证库、策略引擎、审批门、预算跟踪器、钩子扇出、上下文压缩、会话树、OpenTelemetry 跟踪。框架将它们作为一个整体打包，因为一年前这是唯一可用的架构形式。 现在情况已经不同了。 当每一层都是共享总线上的一个工作节点，并且遵循类型化函数契约时，“ 构建你自己的工具系统 ”不再意味着“ 分叉一个框架。这意味着更换一个工作器。 不喜欢模型目录？编写一个能调用实时 API 的。不喜欢基于文件的凭证？接入你的密钥管理器。希望审批通过 Slack 而不是控制台进行路由？ 添加一个调用 approval::resolve。其余的栈不会改变。

框架时代为你选定了一个位置并将你锁定。工作器模型将选择权交给你。

## 解读（1）

### 2026-06-01 10:01:15

#### 一、总结

这篇内容的核心观点：

> 现在很多团队构建 AI Agent 工具系统的方式是错的。

常见做法是直接采用：

- LangChain
- LangGraph
- OpenAI Agents SDK
- CrewAI
- AutoGen 等

然后把：

- 循环执行
- 工具调用
- 记忆
- 编排
- 权限策略
- 凭证管理
- 预算控制
- 审批流程
- 日志追踪

全部绑定在一个框架里。

作者认为问题在于：

> Agent 工具系统不是一个整体，而是很多独立模块的组合。

更好的方式是：

> 把每一层都做成可替换的“工作器”，通过统一协议协作。

这样想换模型、换凭证系统、换审批方式、换监控方案时，不需要重写整个框架，只需要替换对应模块。

---

#### 二、深入浅出解读

可以把 Agent 框架理解成“装修套餐”。

现在很多框架像是：

> 买一整套精装修房子。  
> 沙发、灯、厨房、门锁、网络，全都打包好了。

优点是：

- 上手快
- 适合 demo
- 适合早期验证

但问题是：

- 想换一个门锁，很麻烦
- 想换厨房系统，可能要拆墙
- 企业想接自己的权限、审计、密钥系统，会很痛苦

作者提倡的是“模块化装修”：

> 每个部分都是独立组件，按统一接口连接。

比如：

| 模块 | 可以替换成 |
|---|---|
| 模型路由 | 自研模型选择器 |
| 凭证管理 | 企业密钥管理系统 |
| 审批流程 | Slack / 飞书 / 企业微信 |
| 监控追踪 | OpenTelemetry |
| 预算控制 | 自定义成本系统 |
| 上下文压缩 | 自研压缩逻辑 |

核心变化是：

> 不是“用哪个大框架”，而是“每个环节用哪个工作器”。

---

#### 三、我的意见

我认同这个判断，但要分阶段看。

##### 1. 早期可以用框架

如果你只是：

- 做原型
- 验证想法
- 快速上线 MVP

那 LangChain、LangGraph 这类框架很有价值。

因为它们能帮你快速跑起来。

##### 2. 长期产品必须模块化

如果你要做：

- 企业级 Agent
- 长周期运行系统
- 多用户、多权限、多审计产品
- 需要稳定、合规、可观测的系统

那就不能完全被框架锁死。

尤其是这些部分，最好从一开始就抽象出来：

- 凭证管理
- 权限策略
- 审批流程
- 日志追踪
- 成本控制
- 工具调用协议
- 状态管理

##### 3. 真正的问题不是“框架错了”

更准确地说：

> 框架适合起步，但不适合成为长期系统的核心边界。

成熟 Agent 架构应该是：

> 框架可用，但不可被框架绑架。

---

#### 四、一句话结论

> Agent 系统不要做成一个“大一统框架”，而要做成一组可替换、可组合、可观测的模块。早期用框架提速，长期靠模块化保命。

## 结构化（1）

### 2026-06-01 10:07:15

##### 主旨概括

文章认为：现在很多团队构建 AI Agent（代理）系统时，过度依赖 LangChain、LangGraph、OpenAI Agents SDK 等一体化框架，这种做法容易把团队锁死在固定架构里。更好的方式是把 Agent 工具系统拆成多个可替换的模块，通过“工作器 + 类型化函数契约 + 共享总线”的方式组合。

---

##### 1. 当前主流做法：直接采用一体化 Agent 框架

很多团队在构建 Agent 系统时，通常不会自己设计底层架构，而是直接选择现成框架，例如：

- LangChain
- LangGraph
- OpenAI Agents SDK
- Anthropic SDK
- CrewAI
- AutoGen

这些框架通常会一次性打包很多能力，包括：

- 循环逻辑
- 工具调用
- 记忆系统
- 编排机制
- 策略引擎
- 凭证存储
- 预算跟踪

作者认为，问题在于：团队往往在选择框架时，就被迫同时接受了这些设计决策。

---

##### 2. 核心问题：Agent 工具系统不是一个单一整体

Mike Piccolo 的核心观点是：所谓“Agent 工具系统”并不是一个单独的东西，而是很多独立关注点被捆绑在一起。

文中提到的独立模块包括：

- 状态机
- 模型 / 提供商路由
- 凭证库
- 策略引擎
- 审批门
- 预算跟踪器
- 钩子分发
- 上下文压缩
- 会话树
- OpenTelemetry 追踪

这些能力本来可以分别设计、替换和扩展，但传统框架将它们打包成一个整体，导致灵活性不足。

---

##### 3. 为什么很多长期 Agent 团队最终会重写系统

文章指出，许多长期运行 Agent 项目的团队，最后都会选择从头重写自己的工具系统。

原因是：

- 框架早期方便启动，但后期难以适配复杂需求；
- 企业环境中常有安全、合规、审批、监控等定制要求；
- 一体化框架中的某些默认设计可能无法替换；
- 修改一个小组件，可能变成对整个框架做“大手术”。

例如热门回复中提到：  
在受监管企业里，“基于文件的凭证存储”往往最先被淘汰，因为它不符合企业安全要求。但如果框架深度绑定了这种方式，替换它就会非常困难。

---

##### 4. 新思路：用“工作器模型”替代一体化框架

作者认为，现在已经不必再把 Agent 系统构建成一个庞大的框架。

更好的架构是：

- 每一层都是共享总线上的一个工作节点；
- 各模块通过类型化函数契约通信；
- 不同能力可以独立替换；
- 修改某个功能时，不影响其他部分。

换句话说，“构建自己的 Agent 工具系统”不再意味着要分叉或重写整个框架，而是替换其中某个工作器。

---

##### 5. 具体例子：模块可以按需替换

文章举了几个例子来说明这种模块化方式的优势：

- **不喜欢默认模型目录？**  
  可以写一个调用实时 API 的模型目录工作器。

- **不想用基于文件的凭证管理？**  
  可以接入企业自己的密钥管理器。

- **希望审批流程走 Slack，而不是控制台？**  
  可以添加一个调用 `approval::resolve` 的审批工作器。

这些改动都不需要重写整个 Agent 栈，其余系统可以保持不变。

---

##### 6. 对框架时代的批评：方便但容易锁定

作者总结说，传统框架时代的问题在于：

- 框架帮你做了很多选择；
- 但这些选择会把你锁定在特定架构中；
- 当业务复杂度上升时，框架的默认设计可能成为限制。

相比之下，工作器模型把选择权交还给开发团队，让团队可以根据实际需求替换不同模块。

---

##### 7. 热门回复补充观点

###### 凭证管理是企业落地痛点

有回复指出，在受监管企业中，基于文件的凭证方式往往无法接受，通常是最先被替换的部分。  
但在传统框架里，替换凭证系统可能非常麻烦。

###### Agent 测试不应只测试模型

另一条回复指出，很多测试框架失败，是因为它们只测试模型表现，而不是完整工作流。

真实的评估单元应该包括：

- 输入上下文
- 工具调用
- 状态变化
- 输出成果物
- 人工审核

如果缺少这些环节，测试结果可能看起来很好，但实际产品仍然会出问题。

---

##### 总结

文章的核心观点是：Agent 系统应该从“一体化框架”转向“可组合、可替换的模块化架构”。现成框架适合快速启动，但长期来看，团队需要更灵活的工作器模型，以便独立替换模型路由、凭证、审批、预算、追踪等关键组件。
