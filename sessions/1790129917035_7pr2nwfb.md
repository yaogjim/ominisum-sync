## 分析要点

- **核心高价值点**：模型路由应核算子模型载入上下文和返回主模型时的重新处理成本，而不能仅比较模型的单 token 价格。
- **留存建议**：作为 Agent 架构设计参考保留，成本与性能结论需经实验验证（提供了围绕显式状态组织上下文、工具、路由与后台任务的可复用设计框架，并给出路由成本算式，直接服务于 Agent 开发。）

**知识要点**

- 在文中的简化成本假设下，纯前沿模型成本为 25Y+5Z，混合路由为 3X+20Y+8Z；上下文规模与新增读取量可能抵消便宜模型的价格优势。
- 将状态保存为可寻址、带类型的块，再按当前查询选择隐藏、摘要或完整展示，可把长期状态保存与单轮上下文呈现分离。
- 显式区分读写操作，为只读后台任务共享检索结果、写任务处理锁与冲突提供架构基础。

**行动项**

- 比较纯前沿模型与混合路由时，分别记录上下文载入、输出生成、新增读取及回程重处理成本，验证路由是否真正节省费用。
- 实现最小上下文块原型，按查询选择隐藏、摘要或完整展示，并与追加式记录及通用压缩比较成本和信息遗漏。
- 将工具与项目指令改为条件化加载：先披露简短能力描述，按需加载完整 schema，并在适用条件成立时保留必要规则。

#### 摘要

Coding agent 简单得出人意料。大多数就是一个模型加少量工具的 while 循环，而模型本身之外几乎没有什么有意义的创新。

这份笔记综合了 TypeSafe 创始人 Diogo Almeida 的设计笔记，讲的是围绕 Jev 构建 coding agent 的思路——Jev 是 TypeSafe 的决策模型，把结构化状态转换成类型化输出，例如 choice、score 和 noul 决策。

笔记从一个挑衅性的问题开始： **如果语言模型没有 KV cache，你会怎么设计一个 coding agent？**

这个问题暴露了当前 agent 不加审视就继承的六个设计选择： **亏损的路由、挤占上下文的工具调用、盲目压缩的 compaction、几乎不触发的子 agent、丢弃状态的重启、以及电池之争。**

我们呈现笔记提出的替代架构：一个围绕显式、带类型状态构建的 harness，由 Jev 做每一轮的决策。其中上下文块按查询逐个打分，路由定价时计入重新处理的成本，工具分级披露，指令按条件加载，只读的后台任务共享一次检索。

我们还演算一遍路由算术、真实 agent 会话的 token 经济学，以及按文件敏感度（而不仅是难度）路由的安全论证。

**索引词** ：Jev、TypeSafe、coding agent、harness 工程、KV cache、上下文工程、模型路由、子 agent、工具调用、compaction、AGENTS.md、后台 agent。

---

笔记以四个工作假设开场。

**第一，coding agent 很简单** ，尤其是 agent 的部分：一个循环、一个模型、少量工具。

**第二，现有 agent 中最好的部分可以复用。** 前沿模型都能通过 API 拿到，开源项目提供了灵感和甚至 UI 组件，而只有少数领域（比如 MCP 服务器的认证）才带有真正的复杂性。

**第三，第一方 agent 的成本优势可能在缩小** ，因为用量正从捆绑订阅转向按量付费的 API 定价。

**第四，也是最重要的，有些能力只能原生构建。** 它们无法作为插件交付给别人的 agent，因为它们要求控制 **每一轮上下文是如何被组装的** 。

第四个假设就是论点。 **如果 agent 只是一个循环，那么杠杆不在循环里。杠杆在于循环每一轮喂给模型的东西。**

**Jev 不是写代码的模型，它是旁边那层决策层。**

harness 把当前应用状态（目标、上下文、规则、可用动作、之前的动作）和一个预定义问题交给 Jev，Jev 返回一个类型化答案：choice、score 或 noul，每个都带概率。然后由前沿模型、子 agent、工具和确定性代码去做实际工作。

因为输出是类型化的而不是自由文本，harness 可以验证它、施加阈值、基于它分支，而不必解析散文。

这份笔记里每一个原生功能，底层都是在高频决策点上问 Jev 一个问题。 **每个会话被问上千次，那些小决策才是杠杆所在。**

##### B. 组织起一切的那个问题

笔记描述了一个他喜欢问其他工程师的问题： **如果语言模型没有 KV cache，你会怎么设计 coding agent？**

KV cache 是 agent 被建成「只追加对话记录」的原因。复用缓存前缀很便宜；改动上下文早期的东西会让缓存失效，迫使模型重新处理改动之后的一切。 **这个单一的经济事实塑造了当前 agent 的几乎每一个设计决策——而且通常没人把这件事说出来。**

想象把缓存拿掉，会做两件事。它允许一种为 Jev 设计的、状态显式的架构—— **上下文是被组装的，而不是被累积的** 。同时它揭示为什么「把简单活路由给便宜模型」这种直觉上正确的想法在实践中会失败。

笔记管这叫 **「KV cache 的暴政」** 。

---

症状 为什么存在 代价

1\. 路由失效 交还给大模型时需要重新处理上下文 混合路由比纯前沿更贵

2\. 工具挤占上下文 schema 必须待在系统消息里 token 花在无关工具上；选择质量下降

3\. Compaction 假设所有未来轮次共享同一份状态 查询无关的压缩丢掉了后面需要的东西

4\. 子 agent 稀少 决定传什么上下文进去、什么合并回来很难 几乎没有自动并行

5\. 重启 有状态的对话记录会随时间腐坏 相关的旧状态跟着坏状态一起被丢弃

6\. 电池之争 每个内置能力都永久消耗上下文 在易用与强大之间被迫二选一

##### A. 路由不工作

直觉方案是让前沿模型规划、把执行交给便宜模型、再让前沿模型回来审查。笔记用 Opus（$5 输入 / $25 输出每百万 token）和 Sonnet（$3 / $15）的标价算了这笔账。设 X 是上下文 token，Y 是生成的输出 token，Z 是工作中额外读入的 token（比如命令输出和文件读取）。

```
路径 1  纯 Opus
  生成        25·Y
  读取        5·Z
  合计        25Y + 5Z

路径 2  Opus → Sonnet → Opus
  Sonnet 载入上下文         3·X
  Sonnet 生成               15·Y
  Sonnet 读取               3·Z
  Opus 重新加载变化的部分    5·(Y+Z)
  合计                      3X + 20Y + 8Z
```

当会话很长（X 大）、或工作读取远多于写入、或两者兼有时，路径 2 更贵。 **代入一个合理的会话形态 X = 0.65、Y = 0.12、Z = 0.23，纯 Opus 是 4.15，路由路径是 6.19。**

**留在前沿模型上的成本，大约是那条本该省钱的路径的三分之二。**

图 2：路由陷阱

*图 2. 路由陷阱。把执行委派给便宜模型，会在下行时加一次上下文载入、在回程时加一次重新处理，两者加起来超过了每 token 的折扣。*

教训不是「路由是错的」，而是 **按 token 定价、而不是按上下文重建定价的路由是错的** 。路由只有在两个条件下才可行： **harness 能给便宜模型一个小而专用的上下文（而不是完整记录），且回程不强迫前沿模型重读助手产出的一切。**

##### B. 工具调用是个奇怪的取舍

工具必须提前在系统消息里声明，带着完整的参数 schema，不管这轮用不用得上。这消耗大量上下文，而且笔记的判断是： **它并不产生特别聪明的工具选择。**

工作假设是：模型在「高基数」（一次给太多工具）和「离策略工具调用」（工具的使用模式与训练时见过的不符）的某种组合上挣扎。

**这可能就是为什么 skills——加载一句短描述、细节延后——常常胜过裸工具列表和 MCP 服务器。**

如果每个未来轮次都想要同一份共享状态，compaction 就完全合理。笔记质疑的正是这个假设。

**Compaction 试图做通用压缩，这既难又有损。而查询感知的压缩容易得多：如果你知道下一个问题是什么，你就知道该留什么。**

**在问题已知之前写下的摘要，一定会丢掉问题需要的东西。**

模型并行的程度低于预期。怀疑的原因在状态管理： **决定父上下文的哪些部分要传进去、每个子 agent 的发现中哪些要合并回来。**

**当这个决策既昂贵又容易出错时，模型就会回避它。**

##### E. 重启存在

重启会话是对话记录漂移或损坏时的标准补救。 **但它把坏状态和好状态一起丢掉了。**

有了可寻址状态，替代方案是干净启动、按需只重新加载仍然相关的旧块。

##### F. 电池并非内置

关于 agent 是否该内置能力，有一场持续的争论。今天它是在「易用」（重度内置的 agent 在一端）和「强大」（Claude Code、Codex 这类高级用户工具在另一端）之间的取舍。

**这个取舍存在，仅仅因为每块电池都永久消耗上下文。把那个成本拿掉，争论就消解了。**

*图 3. 检索占主导。读取、搜索和命令输出合计约占处理 token 的三分之二；写代码不到十分之一。*

**最触目惊心的是倒数第二行：写代码，也就是 coding agent 存在的理由，是其中最小的开支项之一。读取和搜索占主导。**

**如果这能推广，coding agent 里最大的效率收益不是更好的模型或更好的 diff 格式，而是更聪明的检索。**

#### IV. 基础层：权限与工具路由

有两项改进可以集成到任何现有 agent 里，无论原生与否。

##### A. 可编程权限

每一条 agent 运行的命令都提出「它到底该不该跑」的问题。Claude 的 auto 模式用分类器回答这个。 **笔记提议走得更远：权限表达为对「什么允许、什么不允许」的可编程查询，** 而且在风险足够高时做更深的检查——比如在执行前读取 Python 或 shell 文件的内容，而不是只批准命令名。

```
policy "exec":
  deny   if command touches ~/.ssh or .env*
  deny   if script contents contain network egress
         and task.scope != "deploy"
  ask    if command writes outside repo root
  allow  if command in read_only_set
  allow  if tests/ and exit code is expected
```

不是把每个工具 schema 都暴露给模型，而是让 harness 坐在意图和调用之间。 **模型用纯文本描述它想干什么。** harness 然后用一串类型化的 Jev 调用来选出最合适的那个工具（或前几名候选），并构造参数。

**模型永远不必在上下文里持有几百个 schema，而错误的参数类型会变成验证错误，而不是静默失败。**

---

#### V. 元注意力：把上下文本身当成决策

核心提议去掉了「上下文是静态的」这个观念。

**对每一个用户查询，harness 问 Jev 两件事：**

**第一，之前的上下文有多好** ——复用现有 KV cache 是对的吗，还是从头重建更便宜也更好？ **这被框定为一个显式的、成本感知的决策，而不是默认行为。**

**第二，如何构造一个包含所有相关的、且不含任何多余的新上下文。**

最简单的形态是：对每一个上下文块做一次 noul——每次工具调用的输入、每次工具调用的输出、每一段内部推理、以及可能每一次与用户的交流。 **后续版本把分数换成可见性级别。**

图 4：可见性阶梯

*图 4. 可见性阶梯。同一个块可以被隐藏、简短总结、详细总结或完整展示，取决于当前查询。 **这就是查询感知的压缩——compaction 所缺的那个属性。***

收益是： **compaction 背后的想法活下来了，但它的主要缺陷消失了。Compaction 在知道问题之前压缩一次；阶梯在知道问题之后按查询压缩。**

**一个 2400 行的 grep 结果，对某个问题可以是十二条相关命中，对下一个问题可以是不可见的——而它从未从状态里被删除。**

笔记还加了一个值得注意的视觉想法： **如果 harness 能热力图显示 grep 输出里哪部分相关，它就能按预算允许的程度随意过滤那份输出。** 而且，笔记观察到， **它看起来也会很酷。**

---

**一等公民的动态上下文，是让路由重新可行的原因。**

一旦 harness 能为子任务构造一个小而相关的上下文，把这个子任务交给更便宜或更快的模型就不需要便宜模型载入整个会话， **而结果可以作为被评分的块合并回来，而不是一份前沿模型必须重读的记录。**

同一机制解锁了子 agent。 **笔记的猜测是：今天子 agent 成本的大部分，是决定传什么上下文的工作** ——相比之下，用户敲一条简单指令反而容易。

**如果构造那个上下文变得便宜且自动，子 agent 就能用得频繁得多。**

它还打开了一个面向用户的控制： **多花钱换更快或更好的结果，还是保守运行、尽量少花。**

##### A. 极端并行

如果派发任务变得便宜，很多任务会同时跑，harness 就继承了并发系统的全部问题： **同步原语、agent 间通信、多个 agent 共享状态时的写冲突。**

笔记建议用带锁的共享状态。 **而显式区分读与写让它变得可处理，因为只读任务永远不会争锁。**

##### B. 目标去重

对 /goal 这类目标驱动的循环，一个悬而未决的问题是：agent 会不会重复劳动。

一个缓解措施： **在派发任何子任务之前，把它注册为子目标，并与所有历史子目标去重。已经做过的、或正在飞行中的工作，永远不会被启动两次。**

---

#### VII. 工具与技能，从第一性原理出发

笔记主张在「今天总是加载的工具」和「按需加载的 skills」之间加一层。

**模型无法提出一个它不知道存在的动作** ，所以它需要短片段来描述有什么可用，类似于 skill 描述。 **但这些片段不必住在系统消息里——它们可以在相关时动态加载。**

它们背后是「在需要时倾倒出可用动作的完整 schema」的能力，类似一个工具搜索工具。

**把这一切绑在一起的要求是：这些东西在不再需要之后，都不能污染上下文。**

图 5：三级披露

*图 5. 三级披露。模型看到一张廉价的全局地图，只为它选中的东西付细节的钱，用完之后把细节从上下文中丢掉。*

**如果这能成，第二节里的电池之争就消失了：当一个内置能力在被使用之前几乎不花成本，agent 就能带着几百个工具和几千页文档发布。**

笔记还点出第二个好处： **近乎零成本的集成是强有力的联合营销渠道，而且它们让事情「就是能用」。**

##### A. 更好的电池

很多社区工具承诺帮助 agent，实际上并没有。笔记举了一个工具输出压缩器作为例子，并猜测原因： **模型并不原生理解这些工具。**

**一个原生 harness 可以发布第一方的提示词，教模型如何使用每一个工具** ——实际上相当于每个工具配一个内置的子 agent 或 skill。而它干净的上下文意味着工具的自定义逻辑不会污染会话的其余部分。

这里也有营销角度： **为你当前流行的工具发布集成，能让 agent 保持在对话之中。**

---

#### VIII. 条件化指令

**今天的 AGENTS.md 是全量加载的。笔记提议按条件加载。**

改前端代码就加载风格指南；在某个子目录里工作就加载那个目录的坑文件（ **而且笔记建议每个子目录都该有一个** ）。

图 6：条件化 AGENTS.md

*图 6. 条件化 AGENTS.md。指令附着到条件上而不是会话上，而且条件片段会被钉住，使 compaction 无法把它摘要掉。*

这像 skills，但笔记画出了一个区别： **skills 通常意味着「现在做这个」。条件化指令意味着「把这段记在某处」。**

**第二种还需要一个 skills 没有的属性：免疫于压缩。** 一个在长会话早期加载的 skill 最终会被压缩或摘要掉； **而一个绑定到条件的指令会在条件成立时被重新加载。**

笔记在普通聊天里观察到同样的需求：请求摘要应该拉入一个偏好的格式；请求用自己风格写作应该拉入样本和一份「不要什么」的清单；请求代码应该拉入风格指南和一条「不要加一百万条断言」的提示。

取决于 harness 变得多可编程，skills 可以携带行为变更而不只是指令，类似 Claude Code 的 skill hooks 但更强大。

**笔记指出的当前 hook 系统的一个限制是：一旦加上，hook 就永久留在会话里。结构化 skills 会随触发它们的条件附着和脱离行为。**

##### B. 递归语言模型

一个相关方向是递归语言模型（recursive language models）的方法，它把 agent 更多的状态当作显式变量而不是对话记录文本。

**一个状态保存在具名变量里的世界，可能比「状态就是上下文窗口里恰好剩下的那些东西」的世界干净得多。**

---

#### IX. 安全感知的路由

今天的路由围绕难度和成本。 **笔记加了第三个轴：信任。**

一些通过低价供应商提供的开放权重模型比前沿 API 便宜得多，而笔记提出的担忧是： **经过某些端点的数据可能不再私有。**

提议是给每个子任务一个「可能触碰哪些文件」的估计，把策略附着到文件类型上，并据此路由。

可能触碰的文件 策略 可用模型

公开文档、开源依赖 开放 任意，最便宜的优先

应用代码 标准 经过审查的供应商

密钥、env、基础设施配置 受限 只用第一方前沿模型

专有研究代码 自定义 排除指定供应商

最后一行反映了一个更广的观点： **难度和成本不是路由的唯一理由。**

一个团队可能因为自己在做模型研究而避开某家供应商的模型，或因为安全工作而避开某些供应商。 **一旦路由是策略驱动的，这些偏好就变成配置而不是纪律。**

---

#### X. 后台处理

笔记识别出几种流行 agent 工作流里的一个共同模式：

- 构建随工作进展而并行更新的 HTML 页面
- 「理解而非生成才是新瓶颈」的论点
- 在后台生成 eval
- 用几张图加极少的字解释系统的 ELI5 技能
- 让 agent 维护一个小型已部署的进度页面，带截图和笔记， **可以在长任务期间从手机查看**

还有一个相关的生产模式： **把线上流量镜像到候选模型，自动生成约一天的 eval，然后才决定是否切换。**

它们的共同点是： **在后台运行、作为正常工作流的扩展、而且都是当前代码库状态的只读函数。** 跨模型审查（让一家供应商的 agent 审查另一家的产出）属于同一模式。

图 7：显式状态上的后台处理

*图 7. 显式状态上的后台处理。找出与某个改动相关什么的这项昂贵工作，只做一次，由每个只读后台任务共享。*

**这正是 Jev 论点兑现的地方。** 以 Jev 为中心的 harness 必须精确知道上下文里有什么、以及每个操作是读还是写。 **找出与某个代码改动相关的信息，是件不平凡的工作。**

**如果这份检索在所有后台任务间共享、而不是每个任务重复一遍，运行它们就会便宜得多，也就能经济地跑更多。** 考虑到第三节的发现——检索占主导地位—— **共享它就是最大的单项节省。**

把读写显式区分开，用笔记的话说， **最终应该给 agent 超能力。**

---

#### XI. 电池候选清单

笔记最后列了几个可以被原生集成的开源项目，每个都附了「以 Jev 为中心的 harness 会怎么用它」的设计说明。

#### XII. 结论

设计笔记提出的论点 **说起来容易、做起来难** ：

**coding agent 是简单的循环，而杠杆不在循环里。杠杆在于 harness 每一轮放在模型面前的是什么——而今天这个决定是由默认值做的，由一份围绕 KV cache 经济性塑造的、只追加的对话记录做的。**

把缓存拿掉当作思想实验，六个熟悉的行为就变了样：

- **路由失败** 是因为上下文被重新处理，不是因为便宜模型弱
- **工具挤满窗口** 是因为它们必须提前声明
- **Compaction 丢信息** 是因为它在问题已知之前压缩
- **子 agent 稀少** 是因为传状态很难
- **重启** 把好状态和坏状态一起丢掉
- **电池之争** 之所以存在，只是因为每个内置能力永久消耗上下文

所提议的 harness 用一个动作应对全部六项： **让状态显式且带类型，让 Jev 按查询决定上下文、路由、工具和权限。**

块在可见性阶梯上被打分。路由按上下文重建定价。工具分级披露。指令附着到条件上。后台任务共享一次检索。

**这些都不需要更好的模型。它需要把上下文窗口当作一件被有意组装的东西，而不是一件偶然累积的东西。**

## 通俗精炼（1）

### 2026-09-23 02:18:36

#### Jev：Coding Agent 的核心竞争力在上下文编排

文章认为，Coding Agent 本质上只是 “模型＋工具＋循环”，真正的工程杠杆不在循环或更强模型，而在每一轮如何组装上下文。Jev 被设想为模型旁的决策层：根据显式、类型化状态，决定展示哪些信息、调用什么工具、选择哪个模型，以及操作是否安全。

##### KV Cache 塑造了六类低效设计

现有 Agent 为复用 KV Cache，普遍采用只追加的对话记录，由此带来路由成本倒挂、工具 schema 挤占窗口、无差别压缩丢信息、子 Agent 难并行、重启时好坏状态一起丢失，以及内置能力越多上下文越臃肿。

例如，将任务从 Opus 路由给 Sonnet 再交回，在文中给定会话结构下，成本为 6.19，高于全程使用 Opus 的 4.15。问题不只是模型价格，而是重复加载和重建上下文。

##### 显式状态让上下文按问题动态生成

方案是把文件、搜索结果、工具输出和指令保存为可寻址的状态块，再由 Jev 按当前问题决定隐藏、摘要或完整展示。由此可实现：

- 只向廉价模型或子 Agent 提供小而相关的上下文；
- 工具采用 “简介 — 详情 — 完整 schema” 分级披露；
- AGENTS.md 等规则按目录和任务条件加载；
- 权限结合命令内容、文件敏感度与供应商可信度判断；
- 多个只读后台任务共享一次检索结果。

##### 最大优化空间可能是检索而非生成

文中估算，读取、搜索和命令输出约占处理 token 的三分之二，写代码仅占 4%—10%；微软 fastcontext 数据也显示，读取与搜索占主 Agent token 的 46.5%。因此，更聪明、可复用的检索可能比改进代码生成或 diff 格式更有价值。

这是一份基于 TypeSafe 创始人设计笔记的第三方汇编，并非已验证的产品架构；但它提出了一个重要方向：Agent 平台的差异化，可能来自对状态、上下文、成本与安全策略的系统控制，而非单纯接入更强模型。

## 结构化（1）

### 2026-09-23 02:21:18

#### Jev 工程学：用显式状态重构 Coding Agent

文章的核心观点是：Coding agent 本身通常只是 “模型＋工具＋循环”，真正决定成本、效果和安全性的，是**harness（运行与调度层）每一轮如何组织上下文**。作者提出以 Jev 作为决策层，把会话状态结构化保存，再按当前任务动态选择上下文、模型、工具和权限，而不是不断累积一份越来越长的聊天记录。

##### 从 “没有 KV cache 会怎样” 重新思考架构

现有 agent 普遍采用只追加的对话记录，主要因为**KV cache**可以低成本复用相同的上下文前缀；一旦修改前面的内容，模型就可能需要重新处理后续上下文。

文章认为，这种成本机制形成了 “KV cache 的暴政”：系统设计优先照顾缓存，却未必适合任务本身。由此出现六类问题：

1. **模型路由可能越省越贵**：切换到便宜模型时要重新加载上下文，切回来又要重新处理结果。
2. **工具挤占上下文**：大量工具的参数说明长期放在系统提示中，即使当前根本用不到。
3. **统一压缩容易丢信息**：Compaction 在不知道下一步问题时提前摘要，可能删掉以后需要的内容。
4. **子 agent 很少真正并行**：难点不只是调用模型，而是决定传什么状态、收回哪些结果。
5. **重启会话误伤有效信息**：坏状态与仍有价值的旧状态一起被清空。
6. **内置能力存在取舍**：功能越多，常驻上下文越大，于是易用性与灵活性被迫对立。

##### 为什么简单的模型路由不一定省钱

文章以 Opus 和 Sonnet 的示意价格计算：

- 全程使用 Opus：成本约为`25Y + 5Z`
- Opus 规划、Sonnet 执行、再回到 Opus：约为`3X + 20Y + 8Z`

其中，`X`是已有上下文，`Y`是新生成内容，`Z`是执行中读取的文件或命令输出。按文中示例`X=0.65、Y=0.12、Z=0.23`，全程 Opus 成本为**4.15**，混合路由反而达到**6.19**。

因此，问题不是 “路由无效”，而是不能只比较模型的单 token 价格，还必须计算**上下文重建成本**。路由要真正省钱，需要同时满足：

- 给便宜模型的只是精简、专用的上下文，而非完整会话；
- 子任务结束后，大模型不必重新阅读全部执行记录。

##### 最大成本不是写代码，而是反复检索

文章估算，典型 CLI coding agent 的 token 开销主要来自：

- 读取文件：约**30%—40%**
- 搜索代码库：约**10%—18%**
- 命令输出：约**10%—20%**
- 系统提示、工具说明和 AGENTS.md：约**5%—12%**
- 真正写和编辑代码：仅约**4%—10%**

微软 fastcontext 项目的数据也显示，在 GPT-5.4 轨迹中，读取与搜索占工具调用轮次的**56.2%**，占主 agent token 的**46.5%**。

据此，文章判断：coding agent 最大的优化空间不是改进 diff 格式，而是减少无关读取和重复检索。

##### 核心方案：显式、带类型、可寻址的状态

新架构不把 “聊天记录中剩下的内容” 视为状态，而是把目标、文件、工具结果、规则、推理和历史动作保存为独立、可寻址的结构化块。

Jev 不直接负责编程，而是接收当前状态和预定义问题，返回带概率的类型化结果，如：

- 选择某个方案或工具；
- 为上下文块打分；
- 判断是否展示、路由或执行。

由于输出不是自由文本，harness 可以直接校验、设置阈值并据此分支，不必从自然语言中猜测模型意图。前沿模型、便宜模型、子 agent、工具和普通程序则负责实际执行。

##### 按问题动态组装上下文

每次收到新请求时，harness 先判断：

1. 现有上下文是否仍然适合复用；
2. 哪些历史状态与当前问题真正相关。

每个状态块可以处于不同的 “可见性级别”：

- 隐藏；
- 简短摘要；
- 详细摘要；
- 完整展示。

这是一种**查询感知的压缩**：先知道当前问题，再决定保留什么。例如，一份 2400 行的搜索结果，在某个任务中可能只展示 12 条相关命中，在下一个任务中则完全隐藏；原始内容仍保存在状态中，并没有被永久删除。

这种设计同时解决了传统 Compaction 的两个问题：既减少上下文，又避免一次摘要后无法恢复细节。

##### 动态上下文让路由和子 agent 重新可行

当 harness 能自动生成小而准确的任务上下文后：

- 便宜模型不必读取整段会话；
- 子 agent 可以频繁、低成本地处理专门任务；
- 返回结果可作为一个新的状态块重新评分，而非强迫主模型重读完整记录；
- 用户可以在 “更快、更好” 和 “更省钱” 之间进行配置。

如果大量子 agent 并行工作，系统还需要处理共享状态、通信和写冲突。文章建议明确区分读写并使用锁：只读任务可以并行，写任务则受控执行。为避免重复劳动，每个子任务在启动前先登记为子目标，并与已完成或正在运行的任务去重。

##### 工具按三级方式披露，而非常驻上下文

文章建议把工具和技能设计成三级披露：

1. 模型先看到一份廉价的全局能力地图；
2. 只在相关时加载某项工具或技能的简短说明；
3. 真正调用时再展开完整参数结构，用完后移出上下文。

模型可以先用自然语言描述意图，由 harness 通过 Jev 选择工具、构造参数并进行类型验证。这样可以避免把数百个工具 schema 永久塞进系统提示，也能把参数错误变成明确的验证失败。

如果这套机制成立，agent 可以内置大量工具和文档，却只为当前用到的部分付上下文成本，从而缓解 “功能丰富” 与 “上下文简洁” 之间的矛盾。

##### 指令应绑定条件，而不是绑定整场会话

传统 AGENTS.md 往往一次性全部加载。文章建议改为条件化加载：

- 修改前端代码时加载前端风格规范；
- 进入某个子目录时加载该目录的注意事项；
- 请求摘要时加载指定格式；
- 模仿用户风格写作时加载样本和禁忌清单。

这些指令应在条件成立时自动重新加载，并免受普通压缩影响。与 “现在执行某项任务” 的 skill 不同，条件化指令更像持续生效的规则，但在条件消失后又能从上下文中移除。

##### 权限与路由还要考虑安全和信任

文章主张把权限做成可编程策略，而不是只判断命令名称。例如：

- 禁止访问`~/.ssh`或`.env`；
- 写出仓库目录时询问用户；
- 脚本包含网络外传行为时做更深检查；
- 必要时在执行前读取 shell 或 Python 脚本内容。

模型路由也不应只看难度和价格，还要看任务可能接触的数据：

- 公开文档、开源依赖：可优先使用最便宜的模型；
- 普通应用代码：使用经过审查的供应商；
- 密钥、环境变量、基础设施配置：只允许受信任的第一方前沿模型；
- 专有研究代码：按团队策略排除特定供应商。

作者将其视为一种策略配置，而不是依赖开发者每次人工保持警惕。

##### 后台任务共享检索，避免重复付费

生成进度页面、自动构建评测、跨模型审查、制作解释材料等任务，都有三个共同点：在后台运行、依附于正常工作流、通常只读取代码库。

由于读取和搜索是最大成本，如果每个后台任务分别探索仓库，就会造成大量重复。显式状态架构可以先完成一次与当前改动相关的检索，再让多个只读任务共享结果；这可能是整个方案中最大的单项节省。

##### 总结：优化重点是 “每轮给模型看什么”

文章认为，当前 agent 的六类问题并非必须通过更强模型解决，而可以由同一个架构转变共同缓解：

- 状态从对话文本变为显式、带类型的块；
- 上下文在知道问题后动态组装；
- 路由计算上下文重建成本；
- 工具和指令按需加载；
- 权限与模型选择由策略控制；
- 子 agent 和后台任务共享检索、明确读写边界。

最终目标是把上下文窗口从 “历史记录偶然累积出的结果”，变成由 harness 每一轮有意构造的工作空间。

> 本文是第三方根据 TypeSafe 创始人 Diogo Almeida 的设计笔记整理的研究性汇编，与 TypeSafe 无隶属或背书关系；其中部分 token 占比属于示意估算，模型价格也可能已经变化。

## 产品-最佳实践（1）

### 2026-09-23 02:32:03

#### 实例：用 Jev 式 Harness 为电商仓库实现 “取消订单并自动退款”

> 下面是基于文章思想构造的工程实例。Jev 的接口、类型和配置均为示意设计，不代表仓库中已经存在可直接调用的 SDK。

##### 1. 需求背景

假设有一个 TypeScript monorepo：

```text
shop-platform/
├── AGENTS.md
├── apps/
│   └── api/
│       ├── AGENTS.md
│       └── src/routes/orders.ts
├── packages/
│   ├── orders/
│   │   ├── AGENTS.md
│   │   ├── src/order-service.ts
│   │   └── test/order-service.test.ts
│   └── payments/
│       ├── AGENTS.md
│       ├── src/refund.ts
│       └── test/refund.test.ts
├── infra/
│   └── production.tf
├── scripts/
│   └── test-integration.sh
└── .env
```

用户给 coding agent 的任务是：

> 新增`POST /orders/:id/cancel`。  
> 已支付订单在取消时自动退款；重复请求不能重复退款；补充单元测试和集成测试，但不要修改或部署生产基础设施。

###### 验收条件

1. 只有允许取消的订单状态才能进入取消流程。
2. 已支付订单调用支付模块退款。
3. 接口具备幂等性，不会发生重复退款。
4. 数据库更新与退款状态处理符合仓库现有约定。
5. 单元测试、集成测试和类型检查通过。
6. 不读取或修改`.env`、生产密钥及`infra/production.tf`。
7. 不执行部署、网络上传或仓库外写入。

---

##### 2. 为什么不直接使用 “完整对话记录”

传统 coding agent 可能会：

1. 将整个会话、所有搜索结果和所有工具 schema 放进上下文。
2. 多次搜索订单、支付和测试代码。
3. 把完整上下文交给便宜模型编写测试。
4. 再让前沿模型重新读取子 agent 的完整输出。
5. 会话过长时做一次通用 compaction。

这个任务中，真正需要写入的代码很少，主要成本来自：

- 多次读取订单和支付模块；
- 重复搜索调用链；
- 重放冗长测试输出；
- 在每轮中携带无关工具 schema；
- 向不同模型重复发送相同上下文。

更好的做法是把会话转换为**显式、可寻址、带类型的状态块**，每轮只组装当前问题真正需要的上下文。

---

##### 3. 显式状态模型

###### 3.1 状态块定义

```ts
type BlockKind =
  | "goal"
  | "instruction"
  | "repository-map"
  | "source-file"
  | "search-result"
  | "command-output"
  | "subagent-finding"
  | "patch"
  | "test-result"
  | "decision";

type Sensitivity =
  | "public"
  | "standard"
  | "restricted"
  | "secret";

type AccessMode = "read" | "write";

interface StateBlock {
  id: string;
  kind: BlockKind;
  source: string;
  content: string;

  version: number;
  baseCommit: string;

  sensitivity: Sensitivity;
  accessMode: AccessMode;

  tags: string [];
  createdAt: string;

  // 指令是否在条件成立时始终完整加载
  pinned?: boolean;

  // 原始内容的派生摘要不能替代原始块
  derivedFrom?: string [];

  // 防止把失效的搜索结果或旧 diff 当作当前事实
  staleAfterCommit?: string;
}
```

###### 3.2 本任务中的状态块示例

| ID | 类型 | 内容 | 敏感级别 | 访问方式 |
|---|---|---|---|---|
| `goal-001` | `goal` | 用户需求与验收条件 | `standard` | 读 |
| `inst-root` | `instruction` | 根目录`AGENTS.md` | `standard` | 读 |
| `inst-orders` | `instruction` | `packages/orders/AGENTS.md` | `standard` | 读 |
| `inst-payments` | `instruction` | `packages/payments/AGENTS.md` | `restricted` | 读 |
| `repo-map-01` | `repository-map` | 与订单取消相关的文件地图 | `standard` | 读 |
| `src-order-01` | `source-file` | `order-service.ts` | `standard` | 读 / 写 |
| `src-refund-01` | `source-file` | `refund.ts` | `restricted` | 读 / 写 |
| `search-refund-01` | `search-result` | 退款调用点及幂等键用法 | `restricted` | 读 |
| `test-failure-01` | `command-output` | 测试失败堆栈 | `standard` | 读 |
| `patch-01` | `patch` | 当前候选 diff | `restricted` | 写 |

`.env`可以被索引器识别，但应注册为：

```json
{
  "source": ".env",
  "sensitivity": "secret",
  "accessMode": "read"
}
```

随后由确定性策略直接阻止读取，而不是依赖模型 “自觉不看”。

---

##### 4. 类型化决策接口

Harness 不应要求 Jev 返回自然语言散文，而应使用可以验证的类型化结果。

```ts
type Visibility = "hidden" | "brief" | "detailed" | "full";

interface ContextDecision {
  blockId: string;
  visibility: Visibility;
  probability: number;
  reasonCode:
    | "DIRECT_DEPENDENCY"
    | "ACTIVE_INSTRUCTION"
    | "TEST_EVIDENCE"
    | "STALE"
    | "IRRELEVANT"
    | "SENSITIVE";
}

interface RouteDecision {
  target:
    | "frontier-model"
    | "reviewed-fast-model"
    | "local-model"
    | "deterministic-tool";
  probability: number;
  maxContextTokens: number;
  trustPolicy: "open" | "standard" | "restricted";
}

interface PermissionDecision {
  action: "allow" | "deny" | "ask";
  probability: number;
  policyId: string;
}
```

###### 决策校验原则

```ts
function validateDecision (decision: PermissionDecision) {
  if (decision.probability < 0.8) {
    return { action: "ask", policyId: "LOW_CONFIDENCE_FALLBACK" };
  }

  return decision;
}
```

**最佳实践：**

- Jev 负责相关性、选择和评分；
- 确定性策略负责不可突破的安全边界；
- 低置信度不能自动转化为高风险操作；
- 非法枚举值、缺少字段或超出预算时必须拒绝执行。

##### 5. 端到端执行流程

##### 5.1 第一步：规范化目标

Harness 将用户请求转换成结构化目标：

```json
{
  "goalId": "cancel-order-001",
  "baseCommit": "a81f4c2",
  "intent": "implement_feature",
  "requirements": [
    "新增 POST /orders/:id/cancel",
    "已支付订单自动退款",
    "重复请求不得重复退款",
    "补充单元测试和集成测试"
  ],
  "forbiddenActions": [
    "读取 .env",
    "修改生产基础设施",
    "执行部署",
    "向仓库外写入"
  ],
  "completionChecks": [
    "typecheck",
    "unit-tests",
    "integration-tests",
    "diff-review"
  ]
}
```

目标块应在整个任务期间保持完整可见，不能被 compaction 改写成可能丢失限制条件的摘要。

---

##### 5.2 第二步：只做一次共享检索

Harness 先建立与任务相关的代码图：

```text
HTTP route
  └── apps/api/src/routes/orders.ts
        └── packages/orders/src/order-service.ts
              ├── order repository
              └── packages/payments/src/refund.ts
```

建议的检索操作：

```bash
ast-grep --pattern 'cancelOrder ($$$ARGS)' .
rg "refund|idempotency|paymentStatus|cancelled" \
  apps packages \
  --glob '!node_modules/**'
```

检索结果保存为状态块，后续规划、实现、测试生成和审查共享，而不是每个子 agent 重搜一遍。

###### 对超长搜索结果的处理

假设`rg`产生了 2400 行结果，不应立即覆盖为一份固定摘要。应同时保留：

1. 原始搜索结果；
2. 命中文件列表；
3. 按符号聚合的摘要；
4. 当前查询对应的相关片段。

这样后续问题变化时，可以重新选择片段，而不必重新搜索，也不会因早期摘要丢失信息。

---

##### 5.3 第三步：按查询组装上下文

###### 规划阶段

当前问题：

> 取消订单涉及哪些模块，正确的事务边界在哪里？

| 状态块 | 可见性 |
|---|---|
| 用户目标与限制 | `full` |
| 根目录`AGENTS.md` | `full` |
| `orders/AGENTS.md` | `full` |
| `payments/AGENTS.md` | `full` |
| 仓库地图 | `detailed` |
| `order-service.ts` | `full` |
| `refund.ts` | `full` |
| 测试文件 | `brief` |
| 旧的 lint 输出 | `hidden` |
| 无关前端代码 | `hidden` |

###### 编写订单测试阶段

当前问题：

> 为订单状态转换与重复取消编写单元测试。

| 状态块 | 可见性 |
|---|---|
| 用户验收条件 | `full` |
| `orders/AGENTS.md` | `full` |
| `order-service.ts` | `full` |
| 现有订单测试 | `full` |
| 支付模块公开接口 | `detailed` |
| 支付模块内部实现 | `brief` |
| HTTP 路由 | `brief` |
| 基础设施文件 | `hidden` |

###### 分析测试失败阶段

当前问题：

> 为什么 “重复取消不得重复退款” 测试失败？

| 状态块 | 可见性 |
|---|---|
| 当前 diff | `full` |
| 失败测试 | `full` |
| 失败堆栈相关帧 | `full` |
| 退款幂等键实现 | `full` |
| 成功测试日志 | `hidden` |
| 早期规划说明 | `brief` |

这就是查询感知压缩：**状态没有被删除，只是针对当前问题改变可见程度。**

##### 5.4 第四步：条件化加载指令

不要在会话开始时一次性加载所有`AGENTS.md`。

```yaml
instructions:
  - file: /AGENTS.md
    when: always
    pinned: true

  - file: /apps/api/AGENTS.md
    when:
      path_matches: "apps/api/**"
    pinned: true

  - file: /packages/orders/AGENTS.md
    when:
      path_matches: "packages/orders/**"
    pinned: true

  - file: /packages/payments/AGENTS.md
    when:
      path_matches: "packages/payments/**"
    pinned: true
```

例如，进入`packages/payments/**`后才加载：

```text
- 所有退款请求必须提供稳定的 idempotencyKey。
- 禁止记录完整支付载荷。
- 测试中只能使用 FakePaymentGateway。
```

这些是安全和正确性约束，应在条件成立期间保持完整，不应被摘要成模糊的 “遵循支付规范”。

---

##### 5.5 第五步：拆分并去重子目标

可以拆成以下子目标：

| 子目标 | 模式 | 是否允许写入 |
|---|---|---:|
| 找出现有订单状态转换规则 | 只读 | 否 |
| 找出退款 API 和幂等键惯例 | 只读 | 否 |
| 设计接口层错误映射 | 只读 | 否 |
| 生成订单测试草案 | 只读产出 | 否 |
| 实现订单服务改动 | 写入 | 是 |
| 实现 HTTP 路由 | 写入 | 是 |
| 审查并发与重复退款风险 | 只读 | 否 |

每个子目标在调度前生成去重键：

```ts
const dedupeKey = hash ({
  objective: "inspect-refund-idempotency",
  scope: ["packages/payments/**"],
  baseCommit: "a81f4c2"
});
```

如果相同目标已经完成或正在运行，就复用已有结果，不重复派发。

---

##### 5.6 第六步：按成本、上下文和信任共同路由

不能只按 “任务难不难” 选模型。

| 子任务 | 所需上下文 | 敏感度 | 建议路由 |
|---|---:|---:|---|
| 查找公开框架的路由写法 | 很小 | 公开 | 廉价或本地模型 |
| 整理现有测试命名风格 | 小 | 标准 | 经过审查的快速模型 |
| 判断退款幂等与事务边界 | 中 | 受限 | 第一方前沿模型 |
| 审查`.env`或生产配置 | 禁止 | 机密 | 不路由，策略直接拒绝 |
| 执行格式化 | 无需推理 | 标准 | 确定性工具 |

###### 路由前的成本判断

不要只比较单个 token 价格，应估算：

```text
预计成本 =
  子模型专用上下文成本
  + 子模型输出成本
  + 主模型重新吸收结果的成本
  + 检索重复成本
```

例如：

- 完整会话上下文：120k token；
- 测试子任务实际只需：12k token；
- 子 agent 返回结构化测试建议：1.5k token；
- 主 agent 只读取结论和候选 patch，不读取完整子会话。

这种情况下路由才可能真正节省成本。如果子模型必须读取完整 120k token，而且主模型还要重新读取其全部产出，就不应路由。

###### 安全优先于价格

即使开放权重模型更便宜，也不能向其发送：

- 支付供应商集成细节；
- 密钥名称和值；
- 生产基础设施配置；
- 专有风控逻辑；
- 未脱敏的客户数据。

---

##### 5.7 第七步：工具分级披露

模型不需要每轮都看到所有工具的完整 schema。

###### 第一级：廉价能力地图

```text
可用能力：
- code.search：搜索文本、符号和调用点
- code.outline：查看文件或符号结构
- code.read：读取文件片段
- code.patch：生成并应用补丁
- test.run：运行受限测试
- git.diff：查看当前改动
```

###### 第二级：候选工具详情

当模型表达 “查找退款调用点” 时，只加载：

```json
{
  "tool": "code.search",
  "description": "按文本、符号或 AST 模式搜索仓库",
  "modes": ["text", "symbol", "ast"]
}
```

###### 第三级：完整参数 schema

只有工具被选中后才提供：

```json
{
  "tool": "code.search",
  "parameters": {
    "query": "string",
    "mode": {
      "enum": ["text", "symbol", "ast"]
    },
    "paths": {
      "type": "array",
      "items": { "type": "string" }
    },
    "maxResults": {
      "type": "integer",
      "minimum": 1,
      "maximum": 200
    }
  },
  "required": ["query", "mode", "paths"]
}
```

工具调用完成后，完整 schema 可以从下一轮上下文移除，但工具输出作为状态块保留。

---

##### 5.8 第八步：执行前权限检查

权限系统必须同时检查：

1. 命令名称；
2. 参数；
3. 目标路径；
4. 脚本内容；
5. 是否产生网络访问；
6. 是否写出仓库；
7. 当前任务是否授权该动作。

示意策略：

```yaml
policy: exec

deny:
  - when:
      path_matches:
        - ".env"
        - ".env.*"
        - "~/.ssh/**"
        - "infra/production.tf"
    reason: "敏感文件不可访问"

  - when:
      command_matches:
        - "terraform apply*"
        - "kubectl apply*"
        - "npm publish*"
    reason: "任务不包含部署或发布"

  - when:
      script_contains:
        - "curl"
        - "wget"
        - "nc"
    unless:
      task_scope_contains: "network-access"

ask:
  - when:
      writes_outside_repo: true

  - when:
      modifies_lockfile: true

allow:
  - when:
      command_matches:
        - "pnpm test --filter orders*"
        - "pnpm test --filter payments*"
        - "pnpm typecheck"
        - "git diff --*"
      network: false
      writes_outside_repo: false
```

###### 关键原则

- `deny`规则应由确定性代码执行，不应仅由模型判断。
- 对`scripts/test-integration.sh`，不能只看到脚本名就批准；应先读取脚本内容，确认没有部署、密钥读取或网络外传。
- 未命中明确规则时默认`ask`，而不是默认`allow`。

---

##### 5.9 第九步：并行读取，串行写入

以下任务可以并行：

```text
Agent A：分析订单状态机
Agent B：分析退款幂等逻辑
Agent C：分析现有测试模式
Agent D：分析 HTTP 错误映射
```

这些任务全部是只读任务，不争用写锁。

写入阶段采用路径锁：

```text
lock packages/orders/**       → Writer 1
lock packages/payments/**     → Writer 2
lock apps/api/**              → Writer 3
```

如果两个 agent 都要修改`order-service.ts`：

- 只允许一个获得写锁；
- 另一个只能提交结构化建议；
- 最终由持锁者合并建议；
- 禁止两个 agent 分别修改后再依赖模型 “智能合并”。

子 agent 返回的应是结构化发现，而不是完整聊天记录：

```json
{
  "subgoalId": "inspect-refund-idempotency",
  "status": "completed",
  "findings": [
    {
      "file": "packages/payments/src/refund.ts",
      "symbol": "refundPayment",
      "fact": "idempotencyKey 是必填参数",
      "evidence": "lines 42-58"
    }
  ],
  "risks": [
    "当前订单服务没有稳定生成退款幂等键"
  ],
  "recommendedAction": "使用 orderId + paymentId + operationVersion"
}
```

---

##### 5.10 第十步：测试、审查与后台任务

前台关键路径：

1. 应用候选补丁；
2. 运行相关单元测试；
3. 运行类型检查；
4. 运行受限集成测试；
5. 根据失败信息重新组装上下文；
6. 审查最终 diff。

后台只读任务可以共享第一次检索结果：

- 生成变更说明；
- 检查遗漏测试；
- 做跨模型代码审查；
- 生成 API 文档草稿；
- 建立风险清单；
- 生成简单的进度页面。

这些任务不应各自重新扫描整个仓库。

##### 8. 需要避免的反模式

###### 反模式一：把所有文件和工具一次性塞入上下文

问题：

- 固定 token 开销高；
- 无关工具干扰选择；
- 敏感信息暴露面扩大。

替代方案：工具分级披露、文件按查询可见。

###### 反模式二：把便宜模型当作默认执行器

问题：

- 便宜模型可能需要重新读取完整上下文；
- 主模型回来后还要重读其输出；
- 实际成本可能更高。

替代方案：只有能构造小型专用上下文时才路由。

###### 反模式三：用一次通用摘要替代历史

问题：

- 规划阶段认为不重要的信息，可能在调试阶段变得关键；
- 摘要一旦丢失事实，很难恢复。

替代方案：保留原始块，为不同查询生成不同摘要。

###### 反模式四：让多个 agent 直接修改同一文件

问题：

- 产生写冲突；
- 难以判断哪个改动基于最新版本；
- 合并过程可能破坏业务约束。

替代方案：只读并行、单写者或路径锁。

###### 反模式五：让模型自己遵守安全规则

问题：

- 模型可能误判命令；
- 脚本内部可能包含网络上传或仓库外写入；
- 提示词不是安全边界。

替代方案：使用确定性权限层，并在必要时检查脚本内容。

##### 10. 最小可行落地顺序

不必一次实现完整 Jev harness，可以按以下顺序演进：

###### 阶段一：先解决安全和固定开销

1. 建立命令权限层；
2. 给文件标注敏感级别；
3. 阻止`.env`、密钥和生产基础设施访问；
4. 实现工具渐进披露。

###### 阶段二：显式状态与查询感知上下文

1. 将文件、搜索结果和测试输出保存为状态块；
2. 保留原始块，不用摘要覆盖；
3. 实现`hidden/brief/detailed/full`可见性；
4. 条件化加载`AGENTS.md`。

###### 阶段三：路由和子 agent

1. 先支持只读子 agent；
2. 返回结构化发现；
3. 加入子目标去重；
4. 计算完整的上下文重建成本；
5. 最后再引入并行写入和锁。

###### 阶段四：后台任务与评估

1. 共享代码检索结果；
2. 并行执行文档、审查和风险检查；
3. 记录所有上下文、路由和权限决策；
4. 建立相关性、安全性、成本和质量 eval。

##### 结论

在 “取消订单并自动退款” 这个实例中，最重要的优化并不是让模型写代码更快，而是：

1. **只把当前问题需要的信息交给模型；**
2. **让检索结果能够被多个任务共享；**
3. **只有在专用上下文足够小时才进行模型路由；**
4. **把敏感度纳入路由和权限决策；**
5. **让子 agent 默认只读，并以结构化结果返回；**
6. **把安全边界交给确定性策略，而不是提示词；**
7. **保留原始状态，针对每个查询重新决定可见性。**

这样，coding agent 不再依赖一份不断膨胀、逐渐腐化的聊天记录，而是围绕显式状态运行：上下文被有意组装，工具按需披露，模型按成本与信任路由，执行过程可以验证、审计和复现。

## 深度解读（1）

### 2026-09-23 02:38:07

#### Coding Agent 的下一层竞争：不是更强模型，而是更好的状态调度

这份材料最有价值的地方，不是提出了一个已经被验证的新系统，而是给出了一套值得检验的架构假说：**今天 coding agent 的许多限制，并非模型能力不足，而是源于 “把完整对话不断追加进上下文” 这一默认设计。**

它用一个很好的思想实验暴露了这种路径依赖：如果语言模型没有 KV cache，我们还会把 agent 设计成长对话吗？大概率不会。我们会保存结构化状态，再根据当前任务动态组装上下文。KV cache 降低了重复处理固定前缀的成本，却也让历史记录、工具定义和旧指令逐渐固化为一个越来越重的包袱。

##### 路由成本取决于 “搬多少状态”，而不只是模型单价

文章对模型路由的修正尤其重要。常见方案是让强模型规划、便宜模型执行、强模型复核，但这可能比全程使用强模型更贵：便宜模型需要重新载入上下文，返回后强模型又要读取新增记录。材料中的示例显示，在长会话、读取密集的任务里，混合路径成本可从 4.15 增至 6.19。

因此，**路由的基本单位不应只是 “任务难度”，还应包括上下文迁移成本。**便宜模型只有拿到一个小而专用的任务包，并且结果能以结构化状态合并，而非整段对话回放时，路由才真正成立。

这也解释了为什么许多子 agent 和多模型方案在演示中很诱人，实际运行却不够经济：问题不只是调用了多少模型，而是每次分派都在复制多少世界状态。

##### 上下文不该被压缩一次，而应按问题重新显影

文章提出的 “可见性阶梯” 比一般的 compaction 更有启发。传统压缩在不知道未来问题时，预先决定哪些信息可以丢弃；但一个事实对当前任务无关，不代表对下一步调试也无关。更合理的做法是保留可寻址的原始状态，再针对当前查询决定每个信息块是隐藏、摘要还是完整展示。

这会把上下文工程从 “写好 prompt” 升级为**信息生命周期管理**：工具说明按需展开，目录规范在进入相应代码区时加载，旧命令输出不再永久占据窗口，敏感文件还能决定任务允许路由给哪些供应商。对产品设计而言，这更接近数据库查询、权限系统与调度器，而不是聊天界面的增强功能。

##### 真正值得优化的是 “理解代码库” 的成本

材料估算，文件读取、搜索与命令输出约占处理 token 的三分之二，写代码通常不足一成；其引用的 fastcontext 数据也显示，读取和搜索占主 agent token 的 46.5%。这些数字仍需更多真实轨迹验证，但方向可信：**coding agent 的主要成本不是生成代码，而是反复重建 “当前代码库发生了什么” 的认识。**

由此产生的机会，不只是更快的搜索工具，而是可共享的检索层：主 agent、审查 agent、测试生成和进度页面共同复用一次相关性计算。谁能可靠地维护代码、任务、规则和执行结果之间的结构化状态，谁就可能显著降低多 agent 的边际成本。

不过，文章把 Jev 描述成解决这些问题的统一决策层，目前主要还是设计蓝图。类型化输出只能让决策可验证，不能保证相关性判断正确；逐块评分也可能引入新的延迟和漏召回。最关键的验证指标因此不是演示效果，而是：在不降低任务成功率的前提下，它能否减少重复读取、上下文重建和人工确认。**如果答案成立，coding agent 的长期壁垒可能不在模型本身，而在模型之上的状态、检索、权限与调度控制面。**

## 深度解读-口播（1）

### 2026-09-30 12:20:38

编程智能体的效率瓶颈，可能不在于代码写得够不够快，而在于每一轮让模型读了什么、又重复读了多少。这份围绕 Jev 决策模型展开的设计笔记，提出一个核心判断：真正值得重新设计的，是模型周围那套管理状态、组装上下文、调用工具的运行框架。

材料来自对 TypeSafe 创始人设计笔记的第三方汇编。下面讲的是一套架构设想，不是已经得到全面验证的产品效果。

理解这套设想，可以从一个反常的问题开始：如果语言模型没有上下文缓存，你会怎么设计编程智能体？

这里的缓存，是把模型已经处理过的上下文保留下来，供后续计算复用。继续在原来的对话后面追加内容，通常比较便宜；修改前面的内容，则可能让后面的缓存失效，需要重新处理。

笔记认为，这个成本结构，推动了今天常见的设计：把用户对话、文件内容、工具结果不断往同一份记录里追加。时间一长，上下文越来越大，再靠压缩摘要或者重启会话来补救。

问题是，这种做法把“保存状态”和“给模型看什么”混在了一起。保存下来的信息，不一定每轮都该给模型看；这一轮没用的信息，也不代表应该永久删除。

这个区别，直接影响一个看似简单的省钱方案：让强模型规划，让便宜模型执行，再交回强模型审查。

便宜模型的单价确实低，但它接手时要先读取上下文。执行过程中，它又会产生代码、日志和文件读取结果。任务交回去以后，强模型还要处理这些新增内容。

按笔记采用的价格和示例计算，这条混合路线，反而比全程使用强模型贵了大约一半。这个结果不是说路由一定没用，而是提醒我们：不能只比较模型单价，还要计算交接时重新读取上下文的成本。

所以，要让路由真正省钱，至少需要两个条件。便宜模型只拿到一个小而专用的任务上下文；它返回的结果，也不能变成一大段强模型必须全部重读的记录。

接下来，才是 Jev 方案的核心：把状态单独保存，把上下文按当前问题重新组装。

可以把它想成一个资料库，而不是一条越拖越长的聊天记录。目标、规则、文件内容、工具结果，都保存成可以单独找到的信息块。每一轮，再决定哪些块需要展示，展示到什么程度。

Jev 在这里不是负责写代码的模型，而是旁边的决策层。运行框架把当前状态和一个明确的问题交给它，它返回结构化的选择、评分等答案，并附带概率。框架可以检查这些答案，再据此选择上下文、模型、工具或执行权限，不必从一段自由文本里猜它的意思。

最直观的例子，是一次两千四百行的代码搜索结果。面对某个问题，模型可能只需要其中十二条命中；换一个问题，这份搜索结果可能完全不需要出现。但原始结果仍然保存着，没有被删掉。

同一个信息块，可以被隐藏、简短概括、详细概括，或者完整展示。关键在于，先知道当前问题，再决定怎样压缩。

这和传统的会话压缩不同。传统做法试图提前写出一份对所有未来问题都有用的摘要，难免丢掉后来才显得重要的细节。按问题组装上下文，则不必要求一份摘要包办所有用途。

为什么这值得做？因为材料估计，典型命令行编程智能体处理的文本中，读取文件、搜索代码和查看命令输出，合计可能占到约三分之二；真正写代码的部分，不到十分之一。这是示意性估计，不是所有会话的固定比例，但它指出了一个优化方向：少做重复检索，可能比压缩生成代码的成本更重要。

理解了动态上下文，再看工具和规则，就容易了。

今天，很多工具需要提前把完整的参数说明放进上下文，即使这一轮根本用不上。笔记建议分级披露：先让模型知道有哪些能力，再按需要加载详细说明，用完以后，把细节移出当前上下文。

比如，智能体可以具备几百种工具，却不必每一轮都背着几百份说明书。这是设计目标，能否实现，还取决于工具选择和参数构造是否可靠。

项目规则也可以按条件加载。修改前端代码，就加载前端风格指南；进入某个子目录，就加载那个目录的注意事项。只要条件成立，相关规则就应继续保留，或者重新加载，而不是在漫长对话中被摘要掉。

同样的机制，还能帮助子智能体协作。主智能体不必复制整场对话，只需传递与子任务有关的信息块，再把子任务的发现作为新的信息块收回来。

不过，并行不是免费的。多个智能体同时修改共享状态，会出现写入冲突。笔记因此强调，要明确区分读取和写入，并为共享状态设置锁。

对于只读的后台任务，这种区分尤其有价值。一次代码改动，可以同时触发审查、进度说明和评估生成。寻找“哪些信息与这次改动有关”的工作，只做一次，让这些后台任务共享，而不是每个任务从头搜索代码库。

路由还需要另一个维度：信任。任务简单，不等于数据可以交给任何便宜模型。笔记建议，根据子任务可能接触的文件来选择供应商。公开文档可以宽松处理，应用代码交给经过审查的服务，密钥和敏感配置则使用更严格的策略。

最值得记住的是，模型保存过的信息，不等于模型此刻必须看到的信息。便宜模型也不一定带来便宜流程，因为上下文交接本身有成本。这份笔记真正主张的，是把上下文当成每一轮都要认真组装的工作材料，而不是一份偶然越积越长的聊天记录。
