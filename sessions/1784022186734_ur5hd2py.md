## 分析要点

- **核心高价值点**：真正决定Agent能否安全自治的不是循环本身，而是明确划分自主执行与人工介入界线的边界契约，并用独立验证证据约束交付。
- **留存建议**：重点精读并长期存档，可作为设计和审查生产级Agent循环的参考框架（提供了完整且可复用的循环契约、状态与日志、验证、触发、角色拆分和进化机制，并附有多个可直接改造的模板。）

**知识要点**

- 生产级循环可由契约、状态与日志、验证机制和触发器四部分组成，状态负责避免重复，日志负责保留可提炼的运行经验。
- 复杂任务可拆成编排器、执行器和验证器：分别选择最高价值工作、在隔离环境执行、独立确认结果并生成人类可审核的证据。
- 循环进化应定期分析失败、浪费和成本，将稳定经验沉淀到边界、脚本、技能、触发机制或仪表盘中，而非只让日志持续增长。

**行动项**

- 选择文档维护等低风险任务，按目标、边界、SOP、状态和日志模板先构建单层循环。
- 为循环定义精确的自动交付条件、必须人工审批的风险条件以及禁止行为，并允许无任务时正常退出。
- 增加隔离执行环境和低成本验证流程，要求每次交付附带测试结果、截图、视频或指标变化等可审核证据。

### 在运行循环一个月之后我学到了什么？？？

上周我写了关于循环工程的内容：这是一种从提示代理完成任务，向设计系统转变的过程，在这些系统中，代理能够决定处理什么工作，执行、验证并随时间改进。

但很多人会说：好的，我被说服了，但是我到底该如何实际构建一个呢？ 更重要的是，我该如何构建一个真正能工作的？

因为任何人都可以用 while true 把一个代理（agent）包起来，称之为循环。这只是简单的 5%。真正的工作是那些护栏，它们让你能够抽身离开。

#### 一个好循环的结构

我们运行的每个循环都有相同的四个部分。

![Image](https://pbs.twimg.com/media/HMwZ6NSa8AAUqIg?format=jpg&name=large)

#### 循环契约

一个 Markdown 文件，每次运行触发时注入到代理中。这是循环的章程。它包含四样东西：

- 目标 （胜利的定义，以及是否存在终点线）
- 的 边界 (它可以自由做什么、绝对不能做什么，以及它可以自行交付的内容与需要人类参与的内容之间的界限)
- 标准操作程序 （ 每次运行所遵循的步骤）

人们在边界部分投资不足，而正是这个部分决定了你是否能够抽身。以我们的一个循环“Error Sweep”为例：每天早上它会读取我们的生产错误跟踪器，挑选最严重的新漏洞，并发布修复程序。这是它的契约中真正的边界部分：

```text
- Fix only when the root cause is clear AND the fix is low-risk.
  Anything risky or large: open a PR and flag a human. Do not merge it yourself.
- Make the smallest fix that works. One PR per fix.
- Never open a new PR while a previous Error Sweep PR is still unmerged.
- Never copy credentials, tokens, or user data into a report or a PR.
```

那都不是关于如何修复 bug 的。这是四句话，用来画一道界限。在界限之内，代理可以自行完成部署。在界限之外，则由人类决定。你需要为代理清晰定义：何时它可以自行部署，以及何时你应该停止并询问。

我们通常将合约、状态、日志放入一个 md 文件中，如下所示

```markdown
# <loop name> — contract

## Goal
What winning looks like. Is there a finish line, or does this run forever as a monitor?

## Boundaries
- Free to do: ...
- Never do: ...
- Ship on its own vs ask a human: <the exact line>

## SOP (each run)
1. Read state + logs.
2. Gather what changed. Pick the single most worthwhile thing to do.
3. Do it (or hand it to an executor).
4. Verify. Record what happened. Report.

## Current understanding
...Current state of the loop run

## Logs
...Logs of past runs
```

#### 2\. 状态 + 日志

一个在每次运行之间忘记所有内容的循环是一个带有额外步骤的 cron 任务。它需要内存，分为两部分：

- 状态是持久的图景：待办事项、当前假设、已发布且需要跟进的实验。每次运行时在顶部查看，刻意保持简洁。
- 日志是发生的事情的只追加记录，逐次运行。

最明显的例子是我们的错误扫描循环维持的状态，以便不会浪费一次运行来重新调查它已经理解的内容：

```text
## Skip these fingerprints (known noise or upstream, not ours)
- ResizeObserver loop limit exceeded
- Stripe.js network blip on /checkout

## Fixed, still watching
- null-team-on-login (019edc8a) — fixed in #1027, confirm it stops firing in prod
```

没有那个块，每天早上循环都会重新发现同样的嘈杂错误，浪费一次运行来追踪它，并让你感到烦恼。有了它，循环会跳过已经判断过的内容，并将注意力放在新的内容上。状态是循环停止自我重复的地方。

该循环还包含其通过运行学到的内容：一个关于谁会转化的可行假设，以及它从犯错中习得的习惯。我们的 CRM 循环包含类似以下的内容：

```text
- users who hit the credit wall in their first week reply about 3x
  more than everyone else. Draft those first.
- Before drafting, check what the user actually built, not the label on their
  profile. One account tagged "SaaS dashboard" was really a print brochure.
```

那一切都不是来自原始合同。这个循环是通过逐次运行积累起来的，现在每次运行都比之前更智能一步。这就是为什么一个好的循环在第三个月比第一个月更有价值：它的状态已经吸收了它所看到的一切。

#### 3\. /验证

这是任何执行高风险工作的流程的前提条件（例如实际生产环境中的代码变更、与真实客户沟通）。基本上，你需要确保验证过程简单，并生成人类能够轻松审核的证据。

通常这意味着

- 设置环境以确保验证 token 高效且可靠
- 一种包含核实证据的方式

对于工程任务，那意味着：

1. [dev-local.sh](http://dev-local.sh/) 脚本，轻松启动本地开发 + 远程沙箱环境以测试（类似 crabbox）
2. 允许代理像真实用户一样自主操作应用的工具（例如 Playwright-CLI）
3. /验证包含用于测试的 SOP 的技能
4. 用于上传截图和视频证据以附加到 PR 的位置（我们上传到 GitHub 发布资产）

虽然其他非工程类工作可能更棘手，但并非不可能。例如，在 CRM 循环中，我们有一个验证代理来审核按照特定防疏漏规则起草的消息；

[https://github.com/AI-Builder-Club/skills](https://github.com/AI-Builder-Club/skills)

结果是，来自循环的 PR 不会以“相信我，它能工作”的形式出现，而是附带一个展示该功能正常运行的视频。我可以在几秒钟内批准，因为我看到的是实际效果，而不是阅读差异并寄希望于它能工作。这也是为什么验证者是判断一个循环是否真的是个好主意的决定因素。

#### 4\. 触发器

什么唤醒了循环？有三种形状，选择正确的形状是成本模型的一半：

- 持续的 for 循环。这是 ralph-loop 或/目标类型触发器。代理在 for 循环中运行，直到条件满足。这是自主研究代理背后的模式。适合有界推送（持续运行直到测试套件通过），作为永久固定装置则过于浪费。当存在即时反馈循环和明确规范时，这种方式主要有用。（类似于大多数修复 bug 的工程工作）
- 基于时间的。 计划触发循环：每小时，每天早上 6 点。我们的 Error Sweep、React Doctor、文档维护者和 CRM 循环都在 cron 上运行。
- 基于工作流/事件。 新邮件到达、事件开启、PR 合并。循环仅在有可运行的内容时才执行。它甚至可以与基于时间的机制结合——例如，基于时间的定时任务每小时运行一次脚本以检查新的支持工单，如有工单则触发坐席；若无，则记录并静默处理。这是管理循环成本的良好方法；您可以在“演进”部分查看其工作原理。

#### 编排器 + 执行器 + 验证器

一旦循环涉及任何非平凡的内容，我们开始将其拆分为三个角色：

![Image](https://pbs.twimg.com/media/HMwavm6aIAE4YqT?format=jpg&name=large)

> Orchestrator 找到工作。Executor 在隔离的沙箱中执行工作。验证器证明该工作并附上证据。

1. 编排器/优先级排序器。 按计划唤醒的代理。它的任务不是执行任务，而是查找任务：收集信号、查看变更内容、选择本次运行中最有价值的单个事项，并进行交接。
2. 执行者。 在隔离空间中执行实际工作（针对代码，一个全新的脱离主分支的 git worktree，因此它永远不会污染你的工作区或其他循环的运行）。
3. 验证者。 独立确认执行者的工作并生成可供人类查看的证据。

但不是所有循环都需要这三个。三层结构正是复杂的、负责代码交付的循环发展的结果。很多好的循环其实就是编排器自己完成整个流程。让我给你看看这两个方面。

#### 演进循环 - 构建抗脆弱循环

在纳西姆·尼古拉斯·塔勒布的《反脆弱》中，他将系统分为三类：脆弱系统惧怕波动性，一次意外就意味着巨大损失；强健系统能在波动性中存活并恢复到原有状态；反脆弱系统则从中获益，每次冲击都会让它们变得更强。玻璃杯是脆弱的，石头是强健的，你的免疫系统是反脆弱的：每一次小感染都会训练它。

当聚焦于循环时，问题就变得具体了： 当运行失败时，教训会去向何方？ 在我们的实践中，一个教训有三个去向，按抽象程度递增的顺序：

![Image](https://pbs.twimg.com/media/HMwdBzxaAAAaCMs?format=jpg&name=large)

每个人都有日志，而且日志只会越来越长。正是将经验提炼为规则，才让循环具备反脆弱性。问题是：谁来做提炼？

所以在 Loopany（我们为这些循环构建了内部应用）中，这成为了一个独立的运行角色： 演进 。代理会话会读取该循环最近十几次运行的日志、结果和成本，并询问：我们在哪里重复犯错？哪些运行是浪费的？哪些边界太松，哪些太紧？它的输出不是产品代码，而是对循环本身的修改：

- 循环合同，国家公约
- 触发机制
- 用于重复和确定性代理步骤的脚本
- 技能
- 人们查看的仪表盘

这是一个用于改进循环本身的循环。

### 真实循环运行 Superdesign

我们一直在运行循环来自动化 Superdesign 的大部分功能，有些成功了，有些没成功（经验教训将在后续单独的博客中分享）。以下是我们日常运行的几个真实示例，这些示例相对容易复制和设置

#### 文档维护循环

![Image](https://pbs.twimg.com/media/HMwa0ata4AAUU8I?format=jpg&name=large)

我们最简单也最有用的循环之一。每周一次，它会确保项目文档保持准确；

这个循环是单层的。编排器读取差异，检查文档，如果有内容漂移则打开一个 PR，完成。没有单独的执行器，也没有单独的验证器，因为任务简单且爆炸半径小，足以让一个代理在其认知范围内处理。

你可以添加多个层、一个对文档中每个声明进行事实核查的验证器，以及一个标记它发现的技术债务的检查过程。你不应该这么做，直到这个简单版本让你碰壁为止。先构建1层版本，体会具体的痛点，然后添加恰好能解决该问题的那一层。

这是我会让你先构建的循环，所以这是一个模板：

```markdown
# doc-maintainer — contract

## Goal
The README, setup guides, and examples always match what the code
actually ships. Zero drift found = a successful run, not a wasted one.

## Boundaries
- Ship on its own: open ONE pull request with the fixes. That's it.
- Never: rewrite accurate docs to look busy, touch anything outside
  the docs, stack a 2nd PR while last week's is still open.

## SOP (each run)
1. Read the diff: every commit + PR since the last sweep (cursor is
   in state).
2. Compare README, setup guides, examples, runbooks against what the
   code ships NOW.
3. Verify for real: run the commands, check the links, try the
   examples. Never trust memory.
4. Drift found → smallest fix, fresh worktree, one PR explaining what
   drifted and why. Nothing stale → clean stop.
5. Move the cursor, log the run.

## State
- last-sweep cursor (commit hash)
- open PR, if any

## Logs
- one dated line per run: drift count + PR link, zero included
```

#### 漏洞猎人循环

![Image](https://pbs.twimg.com/media/HMwa7tIbkAEwdpA?format=jpg&name=large)

有些循环会向真实客户部署实际代码，而在这一过程中出现的错误代价高昂。这时，所有三个层级都能各尽其责。

我们的 Error Sweep 循环每天早上运行：

1. (编排器) 它从我们的错误跟踪系统中拉取过去 24 小时的生产错误（我们编写的一个特殊脚本从 posthog/LLM 日志/服务器日志中收集数据），按出现次数×用户数对其进行排序，跳过其状态中已知的“噪声”指纹，并选择最具影响力的单个新异常。它拉取反压缩的栈跟踪并找出根本原因。
2. (执行器) 如果原因明确且风险低，它会在一个新的工作树中修复问题并提交 PR。如果风险高或规模大，则停止并通知人工处理。边界处的那个分支每次运行都会进行实际工作。
3. (验证器) 修复在生效前得到验证，循环在后续运行中持续观察该指纹，以确认错误确实停止触发。一个未改变实际数值的修复不是真正的修复。

React Doctor 采用同样的方式，专注于提升代码健康而非解决运行时错误：每天早上它会使用 npx react-doctor 扫描应用，挑选出最严重的单个问题，在隔离工作树中修复，验证后打开一个拉取请求。它会以每日指标的形式报告健康评分，让你可以观察指标变化。并且它有一个小护栏，确保使用体验良好：

> 如果之前的 React Doctor PR 仍然处于打开状态且未合并，不要今天再打开另一个。刷新已打开 PR 的状态并仍然报告分数。

这条规则是一个有帮助的循环和一个让你淹没在 30 个你永远不会审阅的 PR 中的循环之间的区别。一个循环必须考虑到你的审阅带宽，而不仅仅是它自身的吞吐量。

#### 支持分类循环

![Image](https://pbs.twimg.com/media/HMwa-2xbIAApULR?format=jpg&name=large)

每小时针对我们的 Intercom 收件箱运行。其指导原则是：每个支持工单都是了解产品缺口的免费窗口。写来的用户正在免费向你提交一份 bug 报告、一个转化障碍或一个困惑信号。大多数支持系统只是回复消息然后丢弃这个窗口，这个循环让这种情况持续下去。

每次运行执行四个步骤：

1. 拖动窗口。 自上次运行以来的所有内容，以及今天到期的任何跟进事项。窗口在静默时段会自动扩大，因此错过的触发永远不会丢失工单。按最后发言者分类：客户 = 需要回复，机器人 = 待审核，队友 = 已处理。
2. 回复前先调查。 这是关键区别。对于每个工单，先基于真实数据确定根本原因：检查用户的账户、实际会话、错误日志和账单记录。切勿盲目回复。很多时候，用户描述的问题并非真正的问题。
3. 分支到三个输出。每个工单最多可以生成三件东西：一个回复能够立即解决用户的问题，在该对话中； 一个提交到知识库的信号：工单背后的产品差距，记录一次，以便后续增长循环和工程循环能够基于该模式采取行动； 并且当根本原因是真正的漏洞时，它会在一个新的工作树中生成一个修复代理，包含验证器和证据，使用与漏洞猎手循环相同的机制。
4. 回复并休息。 设置跟进日期，记录运行，等待下一个 tick。

使这一系统能够安全地对真实客户运行的边界是：回复采用分层机制。常规的、事实性的回答会自动发出。任何敏感内容、退款相关、愤怒的用户、非英文内容且我无法审核语气的情况，只有在人工审核通过后才会发出。

设置它和其他任何循环的方法相同：一个合同文件加上一个每小时的 cron 任务。这是支持合同，精简为你可以拿去用的模板：

```markdown
# support-triage — contract

## Goal
Every inbound ticket gets a correct, investigated response within an hour,
and every product gap behind a ticket becomes a signal the team can act on.
No finish line: this is a monitor.

## Boundaries
- Ship on its own: replies to routine, factual questions (how-to, billing
  lookups, known issues with a documented fix).
- Ask a human first: refunds, angry or churn-risk users, anything legal,
  any reply in a language the team can't review.
- Never: promise features or timelines, share another user's data, close
  a ticket without a root cause written down.

## SOP (each run)
1. Pull conversations since the last run timestamp + follow-ups due today.
   Bucket by last speaker (customer / bot / teammate).
2. Per ticket: investigate root cause against the product DB, error logs,
   and billing BEFORE drafting anything. Never answer blind.
3. Reply per the boundary tiers. Draft-only where approval is required.
4. If the root cause is a bug: spawn a fix agent in a fresh worktree,
   require verification evidence, open a PR flagged to the team.
5. File a signal for any recurring or conversion-relevant gap (dedupe
   against existing signals first).
6. Set follow-up dates. Log the run.

## State
- open follow-ups (ticket id -> due date)
- recurring-theme tally (feeds signal creation)
- standing lessons (e.g. "duplicate messages = retry artifacts, not spam")

## Logs
- one dated line per run: tickets handled / replies sent / signals filed
```

然后在 cron 前面设置一个简单的门控机制，这样代理程序只有在窗口中有内容时才会激活（之前提到的 Evolve 操作），然后让它运行。这种做法的好处不仅仅是更快的回复，还有信号：当五个人询问如何导出某个内容时，这就是一个已记录的转化缺口，正等待进入增长循环，而不是某个可能在季度回顾中才会注意到的模式。

#### CRM 生命周期闭环

![Image](https://pbs.twimg.com/media/HMwbJiubUAEA_3x?format=jpg&name=large)

循环不是工程玩具。我们一些最有价值的循环从未涉及一行代码。这个循环负责我们的客户拓展工作，是面向人而非代码的三层结构的最充分体现。

每天早上：

1. 脚本先拉取数据。 过去 24 小时内活跃的用户、新的商务邮箱注册以及任何收到的回复。确定性的前期阶段，数据拉取过程中不使用 LLM。回复的用户完全退出循环：实时对话属于人类。
2. 编排器提出细分群体，不是一次性选择。值得今日触达的高意向用户群体：本周遇到信用墙的用户、新注册企业、高触达建设者。这些只是示例，而非固定列表；每次运行时都会根据数据重新生成细分群体，哪些会转化取决于当前状态。
3. 每个部分都会生成一个执行器子代理按用户逐个处理：查看他们实际构建的内容，查阅与他们的每一次过往交流，然后起草一封个人电子邮件。切勿盲目起草。一个标注为“SaaS 仪表盘”的资料标签可能实际上是一本印刷手册；执行器检查的是实际成果，而非标签。
4. 验证人员会检查每一份草稿在草稿可以流转之前：需要根据数据对邮件中的每一个声明进行事实核查（以你的名义发出的内容不能有任何虚假信息），然后遵循语音和防疏漏规则。这又是 SEO 相关场景中提到的“品味”问题，但在这里是可解决的，因为“该声明是否符合用户项目的实际情况”有一个可核查的答案。
5. 发送按风险分级。我们最初只允许草稿：每封邮件都需要人工处理。随着各细分群体证明其回复率，低风险的群体获得了在内部权限范围内自主发送的权利。高互动性的群体仍然以草稿形式存在，需人工审批。自主权是按细分群体获得的，而非自动赋予整个流程。
6. 摩擦成为信号。 当研究发现用户在某个环节遇到困难时，这不仅仅是邮件内容，它会生成一个供其他流程读取的信号，而真正的漏洞会催生一个修复代理，其机制与漏洞猎手相同。

你在第 1 部分看到的机制掌控了一切：7 天抑制期，最多一次无回复跟进，一旦回复则由人工接管。系统会进行复合处理：按段记录发送和回复情况，保留转化的内容，丢弃未转化的内容。循环在选择发送对象时的给谁发邮件效果每周都有显著提升，因为它是根据回复率而非直觉来校准的。

```markdown
# crm-lifecycle — contract

## Goal
Turn high-intent product activity into conversations. Success = reply rate
and upgrades per segment, not emails sent. No finish line: this is a monitor.

## Boundaries
- Ship on its own: sends to segments that have EARNED it (see state:
  approved_segments). Everything else: drafts only, a human sends.
- Ask a human first: any new segment's first batch, anyone who ever
  replied, any claim the verifier couldn't confirm.
- Never: email anyone contacted in the last 7 days, send a 2nd follow-up
  without a reply, invent facts about what a user built.

## SOP (each run)
1. Scripts have already pulled actives, signups, and replies. Read the
   output. Users who replied exit to a human.
2. Score users, then propose SEGMENTS (groups, not one-off picks).
   Check state for which segments converted before proposing more.
3. Per segment: spawn an executor sub-agent. Per user: read what they
   actually built + every past exchange, then draft. Never draft blind.
4. Every draft passes the verifier: fact-check each claim against the
   data, then voice + anti-slop rules. Nothing false goes out.
5. Route by risk: approved segments send; the rest queue for review.
6. Friction found during research → file a signal; real bug → spawn a
   fix agent.

## State
- approved_segments (earned autonomy + the reply rate that earned it)
- per-segment performance (sends → replies → upgrades)
- suppression list · standing lessons (e.g. "verify from their real
  work, not their profile label")

## Logs
- one dated line per run: segments proposed / drafts / sends / replies
```

## 结构化（1）

### 2026-07-14 09:43:06

#### 文章主旨

真正有效的 AI 智能体循环，不是简单地用`while true`让 Agent 反复执行，而是建立一套**可持续、自我约束、可验证、能积累经验并不断改进的系统**。循环本身只占约**5%**，真正决定人能否放心放手的是边界、状态、验证和触发机制等护栏。

##### 一、好循环的四个核心组成

###### 1. 循环契约：明确目标、边界和执行步骤

每次循环启动时，都应向智能体注入一份 Markdown 契约，主要包含：

- **目标**：什么算成功，任务是否有明确终点。
- **边界**：可以自主做什么、绝不能做什么、何时必须找人。
- **标准操作程序（SOP）**：每次运行遵循的固定步骤。
- **当前状态与历史日志**：帮助理解上下文和过去的执行情况。

其中，**边界比执行方法更重要**。以每天扫描生产错误的 Error Sweep 为例：

- 只有在根因明确且修复风险低时，才允许自主修复。
- 高风险或大规模改动只能创建 PR，并通知人工，不能自行合并。
- 每次只做最小修复，一个问题对应一个 PR。
- 上一个 PR 未合并时，不得继续创建新 PR。
- 不得把凭证、令牌或用户数据写入报告和 PR。

这些规则不是教智能体怎么修 Bug，而是明确划分：**什么可以自主交付，什么必须停下来询问人类。**

---

###### 2. 状态与日志：让循环不会失忆和重复劳动

如果智能体每次运行都会忘记此前发生的事情，它本质上只是一个更复杂的定时任务。

循环需要两类记忆：

- **状态（State）**：当前待办、已有判断、实验假设、已修复但仍需观察的问题。
- **日志（Logs）**：按时间追加记录每次运行发生了什么，只追加、不覆盖。

例如，Error Sweep 会记录已知噪声：

- `ResizeObserver loop limit exceeded`
- Stripe.js 在结账页的短暂网络异常

也会记录已修复但仍需观察的问题：

- `null-team-on-login`已在 PR `#1027`修复，需要确认生产环境是否停止报错。

这样，下一次运行就不会重新调查同一个噪声，而能把注意力放在新问题上。

状态还会积累业务经验。例如 CRM 循环发现：

- **第一周触及额度墙的用户，回复率约为其他用户的 3 倍**，应优先联系。
- 起草邮件前必须查看用户实际创建的内容，不能只相信资料标签；某个标记为 “SaaS 仪表盘” 的项目，实际可能是印刷手册。

因此，一个好循环在第三个月通常比第一个月更有价值，因为它已经把过去运行中的经验吸收进状态。

---

###### 3. 验证器：用证据证明结果，而不是要求人 “相信它”

只要循环涉及生产代码、真实客户或其他高风险工作，就必须建立低成本、可靠的验证机制。

工程任务通常需要：

- 一键启动本地开发和远程沙箱的脚本。
- Playwright CLI 等工具，让智能体像真实用户一样操作产品。
- 明确的测试与验证 SOP。
- 上传截图或视频证据的位置，例如 GitHub Release Assets。

最终的 PR 不应只写 “相信我，已经修好了”，而应附带：

- 测试结果；
- 截图；
- 实际功能运行视频；
- 必要的指标变化。

这样，人类可以在几秒内查看实际效果并批准，而不是逐行阅读代码差异、猜测是否有效。

非工程任务也可以验证。例如 CRM 循环会让独立验证智能体检查：

- 邮件中的事实是否与用户数据一致；
- 是否存在虚构信息；
- 语气和格式是否符合要求；
- 是否触犯敏感沟通规则。

**如果无法提供可靠证据，就不应完全自动化，而应保留人工审核。**

---

###### 4. 触发器：让循环只在值得运行时启动

循环有三种主要触发方式：

###### 持续运行

在`for`循环中不断执行，直到目标达成。

适合：

- 持续修复直到测试全部通过；
- 有明确规范和即时反馈的研究或工程任务。

不适合长期常驻，因为成本较高、容易浪费资源。

###### 基于时间

按照固定时间运行，例如：

- 每小时；
- 每天早上 6 点；
- 每周一次。

Error Sweep、React Doctor、文档维护和 CRM 循环都采用定时触发。

###### 基于事件或工作流

只有出现实际工作时才启动，例如：

- 收到新邮件；
- 发生生产事故；
- PR 被合并；
- 出现新的支持工单。

还可以把定时与事件门控结合：每小时先用便宜脚本检查是否有新工单，只有确实存在任务时才唤醒智能体；没有任务则静默结束。这样能显著降低空运行成本。

---

##### 二、复杂循环的三层角色

当任务变得复杂，尤其涉及代码交付时，可以拆成三个角色：

1. **编排器（Orchestrator）**
   - 收集信号和变化；
   - 排定优先级；
   - 每次只选择最有价值的一件事；
   - 将任务交给执行器。

2. **执行器（Executor）**
   - 在隔离环境中完成实际工作；
   - 代码任务通常使用全新的 Git worktree；
   - 避免污染主工作区，也避免不同循环互相冲突。

3. **验证器（Verifier）**
   - 独立检查执行结果；
   - 生成截图、视频、测试报告等证据；
   - 让人类能快速审核。

但不是所有任务都需要三层。简单、低风险、影响范围小的任务，可以由一个智能体完成全部流程。正确做法是：**先构建最简单的一层版本，遇到明确痛点后再增加层级。**

---

##### 三、让循环 “反脆弱”：从失败中持续升级

作者借用《反脆弱》的概念区分三类系统：

- **脆弱**：一次意外就可能造成巨大损失，如玻璃杯。
- **强健**：受到冲击后仍能恢复，如石头。
- **反脆弱**：每次冲击都会让系统变强，如免疫系统。

对智能体循环来说，关键问题是：

> 一次失败之后，教训去了哪里？

只有日志不断变长还不够，必须把重复出现的经验提炼成规则。为此，作者在 Loopany 中增加了独立的 “演进” 角色：

- 阅读最近十几次运行的日志、结果和成本；
- 找出反复出现的错误；
- 判断哪些运行属于浪费；
- 检查边界是否过松或过紧；
- 把重复、确定性的步骤沉淀为脚本或技能。

它的输出不是产品代码，而是对循环本身的改进，包括：

- 更新循环契约和状态规则；
- 调整触发机制；
- 编写确定性脚本；
- 增补技能；
- 优化人类查看的仪表盘。

也就是说，作者又建立了一个**专门改进其他循环的循环**。

---

##### 四、实际运行的循环案例

###### 1. 文档维护循环：从简单的一层版本开始

这是最简单、也最实用的循环之一，每周运行一次，确保文档与代码实际行为一致。

执行流程：

1. 读取上次扫描以来的提交和 PR。
2. 对照当前代码检查 README、安装指南、示例和运行手册。
3. 实际运行命令、打开链接和测试示例，不能凭记忆判断。
4. 如果发现文档漂移，只做最小修改，并创建一个 PR。
5. 如果没有漂移，则正常结束；“什么也不做” 同样是成功运行。
6. 更新扫描游标和日志。

关键边界：

- 只允许创建一个文档 PR。
- 不得为了显得忙碌而改写原本正确的文档。
- 不得修改文档范围以外的内容。
- 上周的 PR 未处理时，不得叠加第二个 PR。

因为任务简单、风险低，所以不需要独立执行器和验证器。

---

###### 2. 漏洞猎人循环：三层结构处理生产错误

Error Sweep 每天早上运行，完整使用编排器、执行器和验证器。

###### 编排器

- 拉取过去**24 小时**的生产错误；
- 数据来自 PostHog、LLM 日志和服务器日志；
- 按 “**出现次数 × 受影响用户数**” 排序；
- 跳过状态中已知的噪声；
- 每次只选择影响最大的一个新异常；
- 获取完整堆栈并分析根因。

###### 执行器

- 根因明确且风险低：在新 worktree 中修复并提交 PR。
- 风险高或改动较大：立即停止，转交人工。
- 只做最小可行修复。

###### 验证器

- 在修复生效前进行测试；
- 在后续运行中继续观察同一错误指纹；
- 只有生产环境中的实际错误数下降或停止触发，才算真正修复。

类似的 React Doctor 循环每天运行`npx react-doctor`：

- 扫描代码健康问题；
- 每次只选择最严重的一项；
- 在隔离环境中修复和验证；
- 创建一个 PR；
- 持续汇报每日健康评分。

它还有一条重要护栏：

> 如果上一份 React Doctor PR 仍未合并，当天不得再开新 PR，只更新旧 PR 状态并继续汇报评分。

这避免循环一天一个 PR，最终积累出**30 个无人审核的 PR**。循环不仅要考虑自己的吞吐量，也必须考虑人的审核能力。

---

###### 3. 支持分类循环：回复客户，同时沉淀产品信号

该循环每小时检查一次 Intercom 收件箱。核心理念是：每个支持工单不只是待回复消息，也是一个免费的产品信号，可能暴露 Bug、转化障碍或用户困惑。

每次运行主要执行四步：

###### 拉取待处理窗口

获取：

- 自上次运行以来的新对话；
- 当天到期的跟进事项。

按最后发言者分类：

- 客户：需要回复；
- 机器人：等待审核；
- 队友：已经处理。

静默时间过长时，窗口会自动扩大，避免遗漏工单。

###### 回复前先调查

对每个工单先检查：

- 用户账户；
- 实际会话；
- 错误日志；
- 账单记录。

不能只根据用户的描述盲目回复，因为用户说出的表象不一定是真正根因。

###### 一个工单最多产生三类输出

1. **即时回复**：解决当前用户的问题。
2. **知识或产品信号**：把背后的产品缺口记录下来，供增长和工程循环使用。
3. **Bug 修复任务**：若确认是真实漏洞，则启动独立修复智能体，并要求验证和证据。

###### 设置跟进并等待下一次运行

记录跟进日期、运行结果和状态，等待下一个触发点。

安全边界采用分层机制：

- 常规、事实明确的问题可以自动回复。
- 退款、愤怒或可能流失的用户、法律问题、无法审核语气的外语内容，必须先经人工批准。
- 不得承诺功能或上线时间。
- 不得泄露其他用户的数据。
- 未写明根因前不得关闭工单。

额外价值在于信号沉淀：如果**5 个用户**都询问如何导出内容，这不再是零散客服消息，而是一个明确的产品或转化缺口。

---

###### 4. CRM 生命周期循环：按效果逐步获得自主权

这个循环不涉及代码，负责客户拓展，是面向人的三层循环。

###### 第一步：脚本确定性拉取数据

每天早上获取：

- 过去 24 小时内的活跃用户；
- 新注册的企业邮箱用户；
- 已收到的用户回复。

这一步不使用 LLM。已经回复的用户立即退出自动循环，后续实时沟通由人类接管。

###### 第二步：编排器动态提出用户分群

不是随意选择单个用户，而是根据当前数据寻找高意向群体，例如：

- 本周触及额度墙的用户；
- 新注册企业；
- 高活跃创作者。

分群不是固定名单，会根据历史转化效果动态调整。

###### 第三步：执行器逐个研究并起草

每位用户都需要：

- 查看其实际创建的内容；
- 阅读所有历史交流；
- 再起草个性化邮件。

不能仅凭资料标签起草，否则可能把实际的印刷手册误认为 SaaS 仪表盘。

###### 第四步：验证器核查事实和表达

每封邮件都必须检查：

- 每一个事实是否有真实数据支持；
- 是否准确描述用户项目；
- 是否符合品牌语气；
- 是否出现模板化、低质量或虚构内容。

###### 第五步：按风险分级发送

- 新分群最初只生成草稿，由人类审核。
- 当某个分群证明有稳定回复率后，才获得有限的自动发送权限。
- 高互动、高风险用户仍需人工审批。

因此，自主权不是一次性授予整个流程，而是由每个分群通过实际效果 “挣得”。

###### 关键约束与指标

- **7 天内联系过的用户不得再次发送。**
- 没有收到回复时，最多只允许一次跟进。
- 用户一旦回复，立即由人类接管。
- 成功指标不是发送了多少邮件，而是：
  - 各分群回复率；
  - 升级或转化数量。
- 系统按分群持续记录 “发送 → 回复 → 升级”，保留有效策略，淘汰无效策略。

这使 “应该联系谁” 的判断能够根据真实回复率不断校准，而不是依赖直觉。

---

##### 五、构建好循环的检查清单

- [ ] 有循环契约：明确目标、SOP 和输出规则，并在每次运行时读取。
- [ ] 有清晰边界：区分自主执行与人工介入；允许 “无事可做” 成为有效结果。
- [ ] 有状态和日志：保存跨运行记忆，避免重复劳动。
- [ ] 有廉价验证器：用测试、截图、视频或数据提供证据。
- [ ] 有隔离执行环境：每次使用新 worktree 或独立沙箱。
- [ ] 有经济高效的触发器：通过事件或门控脚本避免无意义空跑。
- [ ] 有演进周期：定期分析运行历史，把机械步骤沉淀为脚本或技能。
- [ ] 范围足够小：不断拆分，直到可以放心让它自行运行。

##### 核心结论

构建循环时，不应先追求 “更强的智能体” 或复杂的多代理架构，而应先把任务范围缩小，并建立清晰的**契约、边界、记忆、验证和触发机制**。最好的循环不是运行次数最多，而是能够在低成本下持续产生可靠结果，并把每次成功和失败转化为下一次运行的能力。

## 口播总结（2）

### 2026-08-03 00:32:14

#### 运行“代理循环”一个月后，真正有效的方法是什么

这份材料讲的是，怎样把人工智能代理从“一次性完成任务”，升级成能够长期自主运行、不断验证、持续改进的工作系统。听完你会了解，一个可靠的代理循环需要哪些结构，怎样设置安全边界，以及它如何应用在修复漏洞、维护文档、处理客服和客户运营等真实场景中。

##### 一、真正困难的不是让代理循环，而是让人能够放心离开

首先，要理解什么是“循环工程”。

这里的代理，也就是 agent，指的是能够理解任务、调用工具并执行工作的人工智能程序。所谓循环，就是让它反复寻找任务、执行任务、检查结果，再进入下一轮。

用一条无限循环命令把代理包起来并不难，但这只完成了最简单的一小部分。真正困难的是建立护栏，让代理知道什么可以自己做，什么必须停下来找人，以及怎样证明工作真的完成了。

作者团队用一个月时间，在 SuperDesign 里运行了大量真实循环。最终发现，一个好循环通常有四个基础部分：循环契约、状态和日志、验证机制，以及合适的触发器。

##### 二、第一部分是循环契约，尤其要把边界写清楚

首先是循环契约。

循环契约通常是一份 Markdown 文档，也就是一种结构简单的纯文本文件。每次代理开始运行，这份文件都会被交给它，相当于整个循环的章程。

契约至少要讲清三件事。

第一，目标是什么。也就是怎样算成功，以及这项任务有没有终点。有些循环完成一次目标就结束，有些则是长期监控，没有真正的终点线。

第二，边界在哪里。代理可以自由做什么，绝对不能做什么，哪些结果可以自行发布，哪些必须由人审核。

第三，标准操作程序，也就是 SOP。它规定代理每次运行时应该按照什么步骤工作。

其中最容易被低估、却最重要的是边界。

以团队的错误扫描循环为例。它每天早上读取生产环境里的错误记录，挑选影响最大的一个新漏洞，然后尝试修复。但它必须遵守几条明确规则。

只有根本原因清楚，而且修复风险较低时，才可以自行处理。风险较高或改动较大时，只能提交一个拉取请求，也就是 PR，交给人审核，不能自己合并。

它还要坚持最小修改，一次修复只开一个 PR。上一个错误扫描 PR 还没合并时，不能继续堆新的。凭证、访问令牌和用户数据，也绝不能出现在报告或 PR 里。

这些规则并没有教代理怎样修漏洞，而是在划线。线以内，代理可以自主行动；线以外，决定权回到人手里。

所以，设计循环时最关键的问题不是“它会不会做”，而是“什么情况下允许它自己做，什么情况下必须停止并询问”。

##### 三、第二部分是状态和日志，让循环不会每天从零开始

接下来是跨轮次的记忆，也就是状态和日志。

如果代理每次醒来都会忘记之前发生过什么，那么它本质上只是一个更复杂的定时任务。它会反复调查同一个问题，重复相同的错误，也无法从经验中进步。

这里的记忆分成两部分。

状态，是循环对当前局面的简洁理解。里面可以包括待办事项、正在验证的假设、已经发布但仍需观察的实验，以及已知的例外情况。每次运行开始时，代理都会先读取状态。

日志，则是每次运行发生了什么的追加记录。它只向后增加，不随意覆盖历史。

例如，错误扫描循环会在状态里保存一份已知噪声清单。某些浏览器报错可能来自第三方服务，或者根本不是团队自己的问题。状态还会记录哪些错误已经修过、对应哪个 PR，以及是否仍需观察生产环境里的错误数量。

没有这些信息，代理每天都会重新发现同样的噪声，再浪费一轮去调查。有了状态，它就能跳过已经判断过的内容，把精力放在新问题上。

状态还可以保存循环通过实践学到的规律。

团队的客户关系管理循环，也就是 CRM 循环，曾发现一个明显规律：在注册第一周就遇到额度限制的用户，回复邮件的概率大约是其他用户的三倍。因此，系统会优先为这类用户准备联系内容。

它还学到，不能只相信用户资料上的标签。一个被标注为“SaaS 仪表盘”的项目，实际上可能是一份印刷宣传册。代理在写邮件前，必须查看用户真正做了什么。

这些经验并不来自最初的契约，而是循环在一次次运行中积累出来的。也正因为如此，一个运行三个月的好循环，往往比第一个月更有价值。

##### 四、第三部分是验证，而且要留下人能快速审核的证据

更重要的是验证。

只要循环会修改生产代码，或者会直接与真实客户沟通，验证就是必需条件。代理不能只说“已经完成”，而要提供可以检查的证据。

好的验证流程需要同时做到两点：对代理来说，验证足够简单、稳定；对人来说，证据足够清楚，可以快速判断结果是否可信。

在工程任务中，团队会准备能够快速启动本地环境和远程沙箱的脚本。沙箱就是一个与正式工作区隔离的测试环境，代理可以在里面试错，不会污染主代码。

代理还会使用类似 Playwright 的浏览器自动化工具，像真实用户一样点击和操作产品。验证完成后，再把截图或视频附到 PR 中。

这样，PR 不再只是写着“相信我，这个功能能工作”，而是直接带着实际运行的视频。审核者不必只靠阅读代码差异来猜测结果，几秒钟内就能看到功能是否正常。

非工程任务也可以验证。比如在 CRM 循环中，会有一个独立验证代理检查每封邮件。它要确认邮件中的事实确实来自用户数据，还要检查语气和表达规则，避免把虚构内容发给客户。

因此，能不能设计出便宜、可靠、带证据的验证方式，往往决定了某项工作是否适合交给循环。

##### 五、第四部分是触发器，它决定循环什么时候醒来，也决定成本

接下来要解决的是，什么东西唤醒循环。

触发器大致有三种。

第一种是持续循环。代理不断运行，直到某个明确条件满足。比如持续修复代码，直到全部测试通过。它适合边界清楚、反馈即时的任务，但不适合长期常驻，因为成本可能很高。

第二种是按时间触发。比如每小时一次，或者每天早上六点运行。这里常用 cron，也就是操作系统里的定时任务机制。错误扫描、代码健康检查、文档维护和 CRM 循环，都可以按固定时间运行。

第三种是由事件或工作流触发。比如新邮件到达、某个事件发生，或者 PR 合并后再启动。只有真的有工作时，代理才运行。

时间触发和事件触发还可以结合。比如每小时先用一个便宜的脚本检查有没有新客服工单。只有发现工单，才启动人工智能代理；如果没有，就安静结束。这样可以减少空运行带来的成本。

所以，选择触发器不只是技术问题，也是成本设计的一部分。一个好循环不应该为了证明自己在工作而频繁空转。

##### 六、复杂任务可以拆成编排器、执行器和验证器

当任务变得复杂时，作者团队会把循环拆成三个角色。

第一个是编排器。它负责找工作和排优先级。每次醒来后，它收集信号，查看发生了什么变化，然后只选出本轮最值得处理的一件事。

第二个是执行器。它负责真正完成任务。涉及代码时，执行器会进入一个全新的 Git 工作树，也就是与主分支隔离的代码副本。这样不同循环之间不会互相污染。

第三个是验证器。它独立检查执行器的成果，并生成人可以查看的证据。

不过，并不是所有循环都需要三层。简单、低风险的任务，一个代理完成全部流程就够了。三层结构主要适合复杂、影响范围大，特别是会向生产环境交付代码的循环。

正确做法不是一开始就堆满角色，而是先做最简单的一层版本。只有遇到具体痛点，再增加恰好能解决问题的那一层。

##### 七、循环还需要“进化循环”，把失败变成系统能力

更进一步，一个成熟循环不应该只完成任务，还应该从失败中变强。

作者借用了《反脆弱》里的概念。脆弱系统遇到意外就受损；强健系统可以恢复原状；反脆弱系统则会从冲击中获益。

放到代理循环里，关键问题是：一次运行失败以后，教训去了哪里？

只保存日志还不够。日志会不断变长，但系统不一定因此更聪明。真正重要的是把反复出现的经验提炼成规则、脚本、技能或新的边界。

团队因此设置了一个独立的“进化”角色。它会读取最近十几次运行的日志、结果和成本，然后检查几个问题：系统是否在重复犯错？哪些运行是浪费的？哪些边界太宽，哪些又太严？

它的输出不是产品代码，而是对循环自身的修改。它可能调整循环契约和状态规则，改变触发方式，把重复而确定的步骤写成脚本，增加新技能，或者改进供人查看的仪表盘。

换句话说，这是一个专门用来改进循环本身的循环。

##### 八、最适合先做的案例，是每周一次的文档维护

下面看几个真实案例。

首先是文档维护循环。它每周运行一次，检查项目说明、安装指南和示例是否仍与实际代码一致。

这是一个单层循环。代理读取上次检查以来的代码变化，再对照现有文档。它会实际运行命令、检查链接、尝试示例，而不是依赖记忆。

发现内容过期时，它只做最小修改，并打开一个 PR。如果文档完全准确，就正常结束。没有发现问题也算一次成功运行，不代表这一轮被浪费了。

它还有明确边界：只能修改文档；不能为了显得忙碌而重写本来正确的内容；上一次的文档 PR 还没处理时，不能继续叠加新的 PR。

这个案例说明，简单任务不必强行加入执行器和验证器。先让一层结构跑起来，等遇到真实限制，再增加复杂度。

##### 九、错误扫描循环展示了三层结构怎样安全交付代码

接下来是漏洞猎人，也就是错误扫描循环。

它每天早上读取过去二十四小时的生产错误。编排器按照“出现次数乘以受影响用户数”排序，从中选出影响最大的一个新异常，并跳过状态中已经确认的噪声。

如果根本原因明确、修改风险低，执行器就在全新的工作树中完成修复并提交 PR。如果原因不清楚，或者风险较高，它就停止并通知人，而不是勉强处理。

之后，验证器要证明修复确实有效。循环还会在后续运行中继续观察同一种错误，确认它在生产环境里停止出现。因为一个看似完成、却没有让真实错误数量下降的修改，不算真正的修复。

React Doctor 循环采用了相似结构。它每天扫描 React 应用的代码健康状况，只挑选最严重的一个问题处理，并持续报告健康分数。

这里有一条看似简单但很重要的护栏：如果上一个 React Doctor PR 还没有合并，当天就不能再开第二个，只更新状态和分数。

这条规则控制的不是代理的工作能力，而是人的审核带宽。一个循环如果每天制造大量无人审阅的 PR，吞吐量再高也没有价值。

##### 十、客服循环的重点不是快速回复，而是先调查根本原因

支持分类循环每小时检查一次客服收件箱。

它的核心观点是，每一张客服工单都是了解产品缺口的免费窗口。用户可能正在提交一个漏洞、指出一个转化障碍，或者暴露一处令人困惑的设计。系统不应只回复消息，然后把这些信息丢掉。

每次运行时，它先拉取上次运行以来的新对话，以及当天需要跟进的事项。为了防止漏单，安静时段的检查窗口会自动扩大。

接着，代理在回复前先调查。它会查看用户账户、真实使用会话、错误日志和账单记录。因为用户描述的表面问题，不一定是真正的根本原因。

每张工单最多产生三类结果。

第一，直接回复用户，解决当前问题。

第二，把背后的产品缺口记录成一个信号，让增长或工程循环以后能够处理。

第三，如果确认是真实漏洞，就启动一个独立修复代理，并要求验证和证据。

回复本身也按风险分层。常规、事实明确的问题可以自动发送。退款、法律问题、愤怒或可能流失的用户，以及团队无法审核语气的外语回复，都必须先由人确认。

这种设计的价值不只是回复更快。比如五位用户都在询问怎样导出内容，这就不再只是五张零散工单，而是一个已经被记录的产品或转化缺口。

##### 十一、CRM 循环说明，循环并不只是工程工具

再来看客户运营，也就是 CRM 生命周期循环。

这个循环每天早上处理活跃用户、新注册的企业邮箱，以及收到的回复。最前面的数据拉取由普通脚本完成，不使用大语言模型。大语言模型，也就是 LLM，只在需要理解内容和生成文字时介入。

一旦用户已经回复，系统就会把实时对话交给人，不再自动跟进。

编排器不会随意挑选几个用户，而是提出当天值得接触的用户群体。比如本周遇到额度限制的人、新注册企业，或者使用频率很高的创作者。具体群体会根据当天数据重新生成。

然后，执行器逐个研究用户真正做过的内容，并查看过去所有交流，再起草个性化邮件。它不能只根据用户资料标签盲写。

验证器会逐条核实邮件中的事实，并检查语气和表达。任何无法从数据中确认的说法，都不能发送。

发送权限也是逐步获得的。新群体最初只能生成草稿，由人发送。当某个群体用真实回复率证明有效，而且风险较低时，才获得自动发送权限。高互动或高风险群体仍然需要人工审批。

系统还有几条重要限制：同一个用户在七天内不会被重复联系；没有回复时，最多只跟进一次；用户一旦回复，立刻转交人工。

它衡量的也不是发出了多少邮件，而是每个群体的回复率和升级转化。系统会保留有效的细分方式，淘汰无效方式，因此选择“该联系谁”的能力会持续提高。

##### 十二、构建循环时，可以用这套标准做最后检查

最后，把实用标准收拢起来。

一个可靠循环要有清晰的契约，写明目标、标准流程和输出规则，而且每次运行都要读取。

它要有明确边界，区分哪些事情可以自主完成，哪些必须由人处理。没有任务、什么都不做，也应该被视为一种正常结果。

它要保存状态和日志，避免重复劳动，并把经验带到下一轮。

它要有低成本的验证器，用截图、视频、测试结果或事实核查提供证据。无法提供可靠证据时，就应保留人工审核。

执行环境需要隔离。涉及代码时，每轮使用新的工作树或独立沙箱，避免不同任务互相干扰。

触发器要经济高效。能先用简单脚本判断有没有工作，就不要直接启动昂贵的代理。

循环还要定期进化，把重复、机械、确定的步骤沉淀为脚本或技能。

最重要的是控制范围。如果一个循环大到让人不敢直接运行，就应该继续拆分，直到它的职责足够单一，边界足够清楚。

作者团队还把内部使用的循环管理工具 Loopany 开源了。它提供循环模板、自动状态和日志、可编程触发器、重试与恢复、进化周期，以及避免不同循环冲突的团队工作空间。

##### 十三、最值得记住的五个结论

最后，回顾五个最重要的结论。

第一，代理循环的核心不是无限运行，而是清晰的目标、边界和停止条件。真正让人能够放心离开的，是护栏。

第二，状态和日志是循环的长期记忆。没有它们，代理只会反复从零开始；有了它们，循环才会越运行越聪明。

第三，高风险工作必须验证，而且要留下人能快速审核的证据。不能证明结果的自动化，不适合获得更高自主权。

第四，复杂任务可以拆成编排器、执行器和验证器，但不要过度设计。先从最简单的一层开始，再根据真实问题增加结构。

第五，一个好循环不仅要完成工作，还要从错误和浪费中提炼规则。真正成熟的循环，会持续改进自己的契约、触发器、脚本和技能，并始终尊重人的审核能力。

### 2026-09-17 00:26:39

真正能无人值守的智能代理循环，不是给代理套上一层“无限重复”就够了。最难的部分，是建立一套护栏，让代理知道该做什么、如何证明自己做对了，以及什么时候必须停下来找人。

作者团队运行这类循环一个月后，得到的核心认识是：循环的价值不在于反复执行，而在于它能安全地行动、跨多次运行积累经验，并且逐渐改进自己。

每个循环都应该先有一份明确的“循环契约”。这份契约要说清目标、边界和标准操作流程。

目标定义什么叫成功，也要说明任务有没有终点。比如，修复一组测试，测试全部通过就是终点。监控生产错误则没有终点，它需要长期运行。

其中最重要，也最容易投入不足的是边界。边界决定代理能否自主交付，还是必须请人介入。

以生产环境的错误扫描循环为例。作者团队给它设定了几条硬规则。只有根本原因明确，而且修复风险很低时，代理才能自行修复。风险较高或改动较大时，只能创建拉取请求并通知人类，不能自行合并。每次只做能够解决问题的最小修改。上一个拉取请求还没合并，就不能继续创建新的请求。凭证、令牌和用户数据，绝不能复制到报告里。

这些规则没有教代理怎样写代码，却画出了自主权的边界。真正重要的问题不是“代理能做什么”，而是“在什么条件下，它可以自己交付；越过哪条线，就必须停下来询问”。

循环还需要跨多次运行的记忆。这种记忆分成状态和日志。

状态是当前仍然有效的简洁认识，例如待办事项、正在验证的假设、已经修复但仍需观察的问题，以及应当跳过的已知噪声。日志则是每次运行发生了什么，只追加，不覆盖。

没有状态的循环，很容易每天重新调查同一个无关错误。它看似一直在工作，实际上只是在重复自己。有了状态，循环就能跳过已经判断过的噪声，把注意力放在真正的新问题上。

状态还可以保存循环从实践中学到的经验。作者团队的客户关系管理循环发现，在注册第一周就碰到额度限制的用户，回复率大约是其他用户的三倍。它还学到，起草邮件前必须查看用户实际做了什么，不能只看资料标签。因为一个标记为“软件仪表盘”的项目，实际内容可能是一本印刷手册。

这就是为什么运行三个月的好循环，通常比第一个月更有价值。它不是单纯多执行了几次，而是把经验沉淀进了下一次决策。

不过，记忆并不能保证结果正确。只要循环会修改生产代码，或者直接与真实客户沟通，就必须有低成本、可审核的验证机制。

工程任务不能只说“相信我，已经能用了”。代理应该实际启动环境，像真实用户一样操作产品，运行测试，并附上截图或视频。这样，人类几秒钟就能看到功能是否真的工作，而不是只读代码差异，再猜测结果。

任务复杂以后，可以把循环拆成三个角色。编排器负责寻找工作，收集信号，并选出本次最值得处理的一件事。执行器在隔离的沙箱或独立代码工作区中完成任务，避免污染主工作区。验证器独立检查结果，并生成供人类审核的证据。

但并不是所有循环都需要三层结构。作者团队的文档维护循环，每周检查代码变化是否导致说明文档过时。如果发现偏差，就做最小修正并创建一个拉取请求；如果没有偏差，就正常结束。因为任务简单、影响范围小，一个代理就足够了。

这带来一个很实用的原则：先构建最简单的单层循环。只有遇到明确痛点时，才增加执行器或验证器。不要为了看起来完备，一开始就把系统做得过度复杂。

触发方式也会直接影响成本。持续运行的循环，适合目标明确、反馈即时的有界任务，例如一直修到测试通过。但如果把它当成永久服务，成本往往太高。定时触发适合每天扫描错误、维护文档或筛选客户。事件触发则适合新邮件到达、拉取请求合并等场景。

更经济的做法，是先用便宜的脚本检查有没有工作。只有出现新工单或新错误时，才唤醒智能代理。没有任务时，安静结束也算一次成功运行。好的循环不会为了证明自己有用而制造工作。

循环还必须考虑人类的审核能力。比如，代码健康检查每天只处理最严重的一个问题。如果昨天的拉取请求还没有合并，今天就不再创建新的请求。这条小规则，决定了系统是在帮忙，还是让团队淹没在永远审不完的任务里。循环不能只追求自身吞吐量，还要尊重人的处理带宽。

更进一步，真正优秀的循环应该从失败中变强。作者团队会让一个专门的“进化”流程，定期查看最近多次运行的日志、结果和成本。它会寻找重复错误、无效运行，以及过松或过紧的边界。然后修改循环契约、触发机制和状态规则，或者把重复而确定的步骤改写成脚本和技能。

日志本身不会让系统变聪明。只有把日志里的经验提炼成规则，下一次运行才能真正受益。

这套思路也不只适用于写代码。支持工单循环会在回复前检查账户、会话、错误日志和账单，避免根据用户的表面描述盲目回答。每张工单除了得到回复，还可能形成一个产品改进信号；如果根本原因是真实漏洞，则进一步触发修复流程。

客户拓展循环同样按风险分级。新用户群体最初只能生成草稿，由人类审核。只有某类用户持续证明有较好的回复率，才获得有限的自动发送权限。自主权不是一次性授予整个系统的，而是由不同场景逐步赢得的。

最值得记住的是，可靠循环的核心不是“让代理一直跑”，而是明确边界、保留记忆，并用证据验证结果。先从范围小、风险低、容易检查的任务开始。然后让每次运行留下经验，使系统不只是自动化工作，而是逐渐学会把工作做得更稳。

## 深度解读（1）

### 2026-09-17 00:32:36

#### 真正可用的 Agent 循环，本质上是一套“可撤回信任”机制

文章最有价值的地方，不是提供了又一种 Agent 编排框架，而是把“让 Agent 持续工作”重新定义为一个运营问题：**难点不在于自动执行，而在于系统能否持续判断风险、留下证据，并在不确定时把权力交还给人。**

##### 边界比能力更决定自动化程度

用 `while true` 让 Agent 反复运行并不难。真正决定人能否离开的，是契约中的边界：什么可以自行交付，什么必须停下询问。

例如错误扫描循环只在“根因明确且修复风险低”时自动提交；高风险改动仅开 PR，不自行合并；上一项尚未处理时，不继续制造新 PR。这些规则没有提升模型的编码能力，却显著降低了失控概率。

这里隐含着一个重要判断：**Agent 的自主权不应按“整个流程”一次性授予，而应按任务类型、风险等级和历史表现逐步获得。**CRM 循环中，只有经过实际回复率验证的用户分群才可自动发送，其他邮件仍停留在草稿阶段。这比笼统设置“全自动/需审核”更实用，也更像现实组织中的授权机制。

对产品设计而言，关键问题因此不再是“Agent 能做什么”，而是：能否识别哪些任务可逆、可验证、爆炸半径小，并为它们设定清晰的升级路径。

##### 验证证据和审阅带宽才是实际瓶颈

文章反复强调每次只选一个最值得处理的问题、未合并旧 PR 时不再创建新 PR。这揭示了一个容易被忽视的约束：**自动化吞吐量不等于组织产能；如果输出超过人的验证能力，Agent 只是在制造新的积压。**

因此，验证器的价值不只是“再检查一次”，而是把结果转化为低成本证据：运行测试、模拟真实用户操作、附上截图或视频，并在后续运行中确认生产指标真的改善。它把人的工作从阅读完整过程，压缩为审核关键结果。

这也给出了判断任务是否适合 Agent 化的实用标准：如果正确性能够用便宜、可靠的方式验证，就可以逐渐扩大自主权；如果结果依赖模糊审美、复杂语境或难以观测的长期影响，就应保留人工决策。**不是模型能力决定自动化上限，而是验证成本决定。**

##### 日志不会自动形成学习，经验必须被“编译”

状态用于避免重复调查，日志记录每次发生了什么，但真正让循环随时间改善的，是把反复出现的教训提炼成契约、脚本、技能或触发规则。比如已知噪声进入跳过列表，稳定的数据拉取改成确定性脚本，过松或过紧的边界被重新调整。

这更接近组织学习，而不是通常所说的模型“记忆”：**有效经验必须从自然语言记录，逐步固化为可执行约束。**文章提出的“演进循环”值得关注，因为它把 Agent 的优化对象从业务任务扩展到了工作系统本身。

不过，“反脆弱”这个说法仍需保留。失败只有在影响受限、原因可观测、教训能被正确提炼时才会让系统变强；否则日志只是更长，同一模型担任执行者和验证者还可能产生共同盲点。文章主要是一个月的实践总结，也缺少节省时间、误操作率和人工审阅成本等量化数据。

更稳妥的结论是：**可持续的 Agent 产品不是更长的提示词，而是一套包含授权、记忆、验证、隔离和反馈的微型操作系统。**最值得先做的也不是复杂多 Agent 平台，而是选择一个低风险、可验证、频繁重复的窄任务，观察它究竟减少了工作，还是只把工作转移成了审核。
