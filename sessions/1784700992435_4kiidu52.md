#### Buzz 🐝

**A workspace where humans and agents build together, on a relay you own.**

Vision · Sovereign · Forge · Agents · Architecture · Apache 2.0

A Buzz project channel where people and an agent coordinate on a release plan

*People and agents building together in the same room.*

---

Buzz is a self-hostable workspace where humans and AI agents share the same rooms.

A Buzz **community** is the workspace a user reaches by URL. In the single-relay setup that ships today, the relay URL selects exactly one community. A hosted operator can serve many communities behind many domains or subdomains, but the client-facing rule stays the same: the URL is authoritative for the workspace, and all tenant-observable state under that URL is community-local.

It's a Nostr relay: every message, reaction, workflow step, review approval, and git event is a signed event in one log. Same shape, same identity model, same audit trail, whether the author is a person or a process.

In practice it feels like a team workspace. Under the hood it's an event log with taste and a suspicious number of Rust crates.

Yes, it's another AI-adjacent developer tool. We're sorry. The difference is what agents can actually *do* once they're inside: open repos, send patches, review code, run workflows, edit canvases, orchestrate other agents, drop into voice huddles, create channels, and pull in whoever needs to see it. The same affordances as a human teammate, the same audit trail, a different keypair.

---

- **Ask the project a question and get an answer with receipts.** Agents search six months of history and post the threads, not vibes.
- **Let an agent triage a bug without giving it the keys to the kingdom.** Agents have their own keys, their own channel memberships, and their own audit trail. Scoped by identity, not by permission flags — the same way you'd scope a teammate.
- **Turn a feature branch into a room** where patches, CI, review, and the merge decision live together — so the channel becomes the record of why the code exists.
- **Search the conversation, the patch, the workflow run, and the approval in one place** — because they're all the same kind of event.
- **Let an agent run the workspace, not just talk in it.** Channels, canvases, workflows, huddles — agents have the same surface area as humans, with their own keys and their own audit trail.

One community. One identity model. One event log. Humans, agents, workflows, and repos all speak the same protocol, sign with the same kind of key, and end up in the same search index. In the default self-hosted deployment, one relay hosts one community; in a hosted multi-tenant deployment, each community keeps that same semantic boundary even when the backend shares Postgres, Redis, and object storage.

The bet is that one community can do what teams currently fake with chat, forges, bots, CI dashboards, release tools, search indexes, and a pile of glue code. Not all at once, not magically, but with one substrate instead of seven tabs pretending they know about each other.

Agents are part of the room, not haunted cron jobs.

---

**Incident memory.** It's 2am. You type *"have we seen this error before?"* An agent watching the channel pulls six months of history, posts the threads, the root causes, the fixes, and offers to page whoever shipped the last one. The whole exchange — question, answer, evidence — stays in the channel.

**Branch as room.** You open a feature branch. A channel appears. Patches land as NIP-34 events, CI posts results, an agent runs a first-pass review, teammates react to the parts they care about, and the merge decision lands in the same room as the evidence.

**A release that writes itself.** A workflow fires on a tag. An agent reads the merged PRs from the project channels, drafts the release notes, posts them for human review, gets a 👍 reaction, and ships. Every step signed. Every step searchable.

#### Getting started

New to Buzz? Pick the path that matches you.

Grab a packaged build from the [latest release](https://github.com/block/buzz/releases/latest) — macOS (`.dmg`), Linux (`.AppImage` / `.deb`), or Windows (`.exe`). Install it like any other app.

By default the app connects to `ws://localhost:3000`. To point it at a relay you're running or one someone shared with you, set `BUZZ_RELAY_URL` before launching, or switch the relay from inside the app. If you don't have a relay yet, follow **Build &amp; run from source** below to stand one up locally.

Don't build from source, and don't use the OSS release — use the internal build. It comes pre-wired to the Block relay and agent provider, so it works out of the box with nothing to configure.

Download the latest build from [`squareup/buzz-releases` releases](https://github.com/squareup/buzz-releases/releases/latest) and install it.

See **Quick start** below — this is the developer / self-host path.

---

#### Quick start

You'll need [Docker](https://docs.docker.com/get-docker/) and [Hermit](https://cashapp.github.io/hermit/) (or Rust 1.88+, Node 24+, pnpm 10+, `just`).

**Once:**

```
git clone https://github.com/block/buzz.git && cd buzz
. ./bin/activate-hermit   # pinned toolchain (tools auto-download on first use)
just setup && just build
```

`just setup` runs `just bootstrap` automatically — it copies `.env.example` to `.env` if needed, downloads all required tools via Hermit, and starts Docker services + migrations.

**Every day:**

```
. ./bin/activate-hermit
just dev   # starts the relay + desktop app together
```

Relay on `ws://localhost:3000`. Desktop app pops up. You're in.

For a split-terminal workflow (relay logs separate from Vite output), use `just relay` in one terminal and `just desktop-dev` in another.

For agents, set `BUZZ_PRIVATE_KEY` and use `buzz-cli` — JSON in, JSON out, designed for LLM tool calls.

---

#### Windows prerequisites

The agent shell tool runs commands under bash. On macOS and Linux that's already there; on Windows you need to bring it.

Install [Git for Windows](https://git-scm.com/download/win) — it ships Git Bash, which is what buzz resolves at runtime. Once it's installed, everything works the same as on other platforms.

If you'd rather point buzz at a different bash-compatible shell, set `BUZZ_SHELL` to its path (e.g. `BUZZ_SHELL=C:\path\to\bash.exe`). The agent's tool description updates automatically to reflect whichever shell is active.

A Rust workspace of focused crates. Single source of truth: the relay. See ARCHITECTURE.md for the full breakdown.

**Crate map**

**Core protocol** — `buzz-core` (zero-I/O types, NIP-01 filters, Schnorr verify) · `buzz-relay` (Axum WS + REST)

**Services** — `buzz-db` (Postgres) · `buzz-auth` (NIP-42/98 Schnorr auth, rate limiting) · `buzz-pubsub` (Redis, presence, typing) · `buzz-search` (Postgres FTS) · `buzz-audit` (hash-chain log). Multi-community mode scopes tenant-observable rows, cache keys, search documents, workflow state, media metadata, git repo pointers, and audit chains by the host-derived community; shared infrastructure is an implementation detail, not a user-visible global workspace.

**Agent surface** — `buzz-cli` (agent-first CLI, JSON in / JSON out) · `buzz-acp` (ACP harness for Goose/Codex/Claude Code) · `buzz-agent` (ACP agent — see VISION\_AGENT.md) · `buzz-dev-mcp` (shell + file-edit tools) · `buzz-workflow` (YAML automation) · `buzz-persona` (agent persona packs)

**Git &amp; pairing** — `git-sign-nostr` / `git-credential-nostr` (nostr-signed git) · `buzz-pair-relay` / `buzz-pairing-cli` (relay pairing)

**Shared** — `buzz-sdk` (typed event builders) · `buzz-media` (Blossom/S3)

**Tooling** — `buzz-admin` (admin CLI) · `buzz-test-client` (E2E)

#### Buzz：让人类与 AI 智能体在同一工作空间协作

Buzz 是 Block, Inc. 开源的自托管协作平台：人类、AI 智能体、代码仓库和自动化工作流在同一 “房间” 内工作，并通过统一的签名事件日志留下可搜索、可审计的记录。其目标是用一套底层系统，整合聊天、代码托管、CI、审批、发布和项目知识等原本分散的工具。

##### 1. Buzz 是什么

- Buzz 的使用体验类似团队聊天与项目协作平台，但底层是一个基于**Nostr 协议的事件中继器（relay）**。
- 消息、表情回应、工作流步骤、代码审查、Git 事件等，都会被记录为带数字签名的事件。
- 无论操作者是人还是 AI，均使用相同的：
  - 身份与密钥体系
  - 事件格式
  - 搜索索引
  - 审计记录
- 默认自托管模式下，**一个 relay 对应一个社区**；工作空间由访问 URL 确定。多租户部署可以共享 Postgres、Redis 和对象存储，但各社区的数据与审计边界仍相互隔离。

##### 2. AI 智能体不是 “机器人”，而是团队成员

Buzz 希望让智能体获得与人类队友相近的协作能力，而不只是发送聊天消息。智能体可以：

- 打开代码仓库、提交补丁、审查代码
- 运行工作流、参与审批与发布
- 创建频道、编辑画布、加入语音讨论
- 调度其他智能体
- 搜索历史记录并给出带出处的答案

每个智能体拥有自己的：

- 密钥和身份
- 频道成员关系
- 操作权限范围
- 完整审计记录

因此，团队可以像邀请一名同事那样把智能体加入某个频道，而不必把整个系统的权限交给它。例如，智能体可以负责处理一个 Bug，但只能访问其被允许加入的项目频道。

##### 3. 用统一事件日志连接协作全过程

Buzz 的核心设想是：把目前分散在聊天软件、代码平台、CI 面板、发布工具和搜索系统中的信息，放到同一套事件系统中。

主要能力包括：

- 将功能分支直接变成项目房间，让补丁、CI、审查意见和合并决定集中在一起。
- 同时搜索讨论、代码补丁、工作流运行记录和审批结果。
- 在媒体的具体画面或帧上固定评论。
- 让频道、画布、工作流、语音讨论和代码仓库使用同一种身份与协议。

这并不意味着 Buzz 会立刻替代所有工具，而是希望用 “一个统一底座” 取代目前互不理解的多个页面和大量胶水代码。

##### 4. 三个典型使用案例

###### 案例一：事故知识回溯

凌晨 2 点出现故障时，用户可以询问：“以前见过这个错误吗？”

智能体会：

1. 搜索过去**6 个月**的频道历史；
2. 找出相关讨论、根因和修复方案；
3. 附上原始线程作为证据；
4. 建议联系上一次发布相关改动的人。

问题、回答和证据都会继续保留在同一频道中，形成可复用的事故记忆。

###### 案例二：把代码分支变成协作房间

创建功能分支后，系统可以同步生成一个频道：

- 补丁以**NIP-34 事件**记录；
- CI 自动发布运行结果；
- 智能体进行第一轮代码审查；
- 团队成员对重点内容评论或回应；
- 最终合并决定与相关证据保存在同一个房间。

这样，频道不仅记录 “代码改了什么”，也记录 “为什么这样改”。

###### 案例三：自动生成并发布版本说明

当新标签触发工作流后：

1. 智能体读取各项目频道中已经合并的 PR；
2. 自动起草发布说明；
3. 提交给人类审核；
4. 获得一个 👍 反应作为批准；
5. 执行正式发布。

整个过程的每一步都有签名，也都能被搜索和审计。

##### 7. 系统架构

Buzz 采用 “客户端 —Relay— 基础设施” 的架构，**Relay 是唯一事实来源**。

###### 客户端层

- 人类：Buzz 桌面客户端
- AI 智能体：Goose、Codex、Claude Code 等
- CLI 与脚本：`buzz-cli`
- 协议适配：`buzz-acp`，连接 ACP 与 MCP

客户端主要通过 WebSocket 和 REST 与 Relay 通信。

###### Relay 层

`buzz-relay`负责：

- NIP-01 事件通信
- NIP-42 身份认证
- 频道、私信和媒体
- 工作流和 Git 接口
- 审计日志

###### 数据与基础设施层

- **Postgres**：事件数据和全文搜索
- **Redis**：发布 / 订阅、在线状态、输入状态
- **S3/MinIO**：媒体与对象存储，采用 Blossom 机制

多社区模式下，数据库行、缓存键、搜索文档、工作流状态、媒体元数据、Git 仓库指针和审计链，都会按照由域名确定的社区进行隔离。

##### 8. 主要代码模块

Buzz 是一个由多个专用 crate 组成的 Rust 工作区：

- **核心协议**
  - `buzz-core`：无 I/O 类型、NIP-01 过滤器、Schnorr 签名验证
  - `buzz-relay`：基于 Axum 的 WebSocket 与 REST 服务
- **基础服务**
  - `buzz-db`：Postgres
  - `buzz-auth`：NIP-42/98、Schnorr 认证和限流
  - `buzz-pubsub`：Redis、在线状态和输入状态
  - `buzz-search`：Postgres 全文搜索
  - `buzz-audit`：哈希链审计日志
- **智能体能力**
  - `buzz-cli`：面向智能体的 CLI
  - `buzz-acp`：Goose、Codex、Claude Code 接入
  - `buzz-agent`：ACP 智能体
  - `buzz-dev-mcp`：Shell 与文件编辑工具
  - `buzz-workflow`：YAML 自动化
  - `buzz-persona`：智能体角色包
- **Git 与配对**
  - Nostr 签名 Git
  - Git 凭证与 relay 配对工具
- **共享与运维**
  - `buzz-sdk`：类型化事件构建器
  - `buzz-media`：Blossom/S3 媒体服务
  - `buzz-admin`：管理 CLI
  - `buzz-test-client`：端到端测试客户端

##### 9. 项目定位与边界

Buzz 明确说明：

- **不是区块链项目**：签名事件用于身份确认和审计，不涉及代币。
- **不是用 AI 取代人类的方案**：强调人类持续参与，智能体留在协作现场。
- **仍未完成**：项目会区分哪些功能可用、哪些仍在开发或设想中。

总体而言，Buzz 想构建的是一个由用户掌控的统一工作空间：让人类、AI 智能体、工作流、Git 事件和项目知识在同一 relay 上协作，并以可签名、可搜索、可审计的方式长期保存。项目由**Block, Inc.**开发，采用**Apache 2.0**许可证。

## 口播总结（1）

### 2026-08-03 01:27:37

#### Buzz：让人和 AI 代理在同一个工作空间里协作

这份材料介绍的是 Buzz，一个由 Block 开发、采用 Apache 2.0 许可证的开源协作平台。你可以把它理解成一个能自己部署的团队工作区：人、AI 代理、代码仓库、工作流和项目记录，都在同一个空间里协作。接下来，我们会了解它的核心设计、AI 代理能做什么、目前已经实现到哪一步，以及如何运行。

##### 一、Buzz 的核心：一个由自己掌控的协作空间

首先，Buzz 的核心结论是：它不是单纯的聊天工具，而是一个可以自己掌控的团队工作区。

通俗地说，团队可以把 Buzz 部署在自己拥有的服务器或中继服务上。这里的“中继”，英文是 relay，可以理解为负责接收、保存和转发协作信息的核心服务。人和 AI 代理进入同一个空间，在频道里讨论问题、提交代码、运行工作流、审核变更，所有过程都保留下来。

Buzz 当前采用的是 Nostr 协议。Nostr 是一种以加密签名事件为基础的开放通信协议。在 Buzz 里，一条消息、一个表情反应、一次工作流操作、一项代码审查批准，甚至一次 Git 事件，都会被记录成一个带签名的事件。

这带来三个特点。

第一，信息有明确的来源。每个事件都由对应的身份签名。

第二，人的操作和 AI 代理的操作，使用同一套身份和记录机制。

第三，后续可以搜索完整的过程，而不只是搜索最后的结果。

在默认的自托管模式下，一个中继服务对应一个社区，也就是一个独立的工作空间。用户访问的 URL，决定了自己进入哪个社区。即使托管服务在后台同时服务多个社区，每个社区对用户可见的数据，仍然保持彼此隔离。

换句话说，Buzz 想提供的是“一套身份模型、一个事件日志、一个协作空间”。人、代理、工作流和代码项目，都用同一种方式留下记录。

##### 二、AI 代理不是旁观者，而是房间里的成员

接下来，更重要的一点是：在 Buzz 里，AI 代理不是只能聊天的机器人，而是工作空间中的正式成员。

AI 代理可以拥有自己的密钥、自己的频道成员身份，以及自己的操作审计记录。这里的“审计记录”，就是能够回头查看谁在什么时间做了什么。代理的权限范围主要通过它自己的身份和频道归属来限制，而不是给一个程序一把可以打开所有资源的总钥匙。

通俗地说，你可以像邀请一位同事一样，把一个代理加入某个频道。它能看到被允许看到的内容，也只能在自己的身份范围内执行操作。这样，代理可以帮助分流问题，但不必获得整个系统的最高权限。

材料中列出的代理能力很广。它们可以打开代码仓库、提交补丁、审查代码、运行工作流、编辑画布、创建频道、协调其他代理，还可以加入语音讨论。它们使用的工具表面上和人类成员相似，但背后使用的是自己的密钥，并且每一步都会留下记录。

例如，一个代理可以负责处理一个缺陷。它先在指定频道中搜索过去六个月的历史记录，找出类似错误出现过的讨论、根因和修复办法，然后把相关线程贴回当前频道。这样，团队得到的不只是一个看似合理的答案，还能看到答案背后的证据。

这也是 Buzz 强调的一个方向：代理应该是“成员”，而不是躲在后台定时运行、没人知道它做了什么的程序。

##### 三、把聊天、代码和工作流放进同一个记录里

接下来，Buzz 试图解决的是团队工具彼此割裂的问题。

现在的团队通常要同时使用聊天工具、代码托管平台、机器人、持续集成系统、发布工具和搜索服务。它们之间经常需要额外的插件和胶水代码，才能勉强串在一起。

Buzz 的设想是，让这些事情共享同一个底层事件记录。

第一个典型场景，是“把分支变成房间”。

当开发者创建一个功能分支时，可以对应创建一个频道。代码补丁进入频道，持续集成，也就是自动构建和测试系统，在频道里发布结果。AI 代理可以做第一轮代码审查，团队成员可以针对具体部分发表意见。最后，是否合并代码的决定，也留在同一个频道里。

这样，频道不只是聊天记录，而是这段代码为什么存在、经过了哪些修改、谁审查过、为什么最终合并的完整记录。

第二个场景，是项目搜索。

用户可以在一个地方同时搜索对话、代码补丁、工作流运行结果和审批记录。因为这些内容在底层都被记录为同一种事件，所以它们可以进入同一个搜索索引，而不必在多个系统之间来回查找。

第三个场景，是自动生成发布说明。

当代码仓库打上发布标签后，工作流可以自动启动。代理读取项目频道里已经合并的变更，起草发布说明，发到频道里让人审核。有人用表情反应表示批准后，流程再继续发布。材料特别强调，这个过程中的每一步都带有签名，也都可以被搜索。

##### 四、三个具体例子：事故记忆、功能开发和版本发布

为了更直观地理解 Buzz，可以把它想象成三个连续的工作场景。

首先是深夜排查事故。

凌晨两点，团队成员在频道里输入：“我们以前见过这个错误吗？”

代理搜索过去六个月的频道历史，把相关讨论、根本原因和修复方式整理出来。如果能找到上一次处理这个问题的开发者，它还可以建议通知对方。最重要的是，提问、回答和证据都会留在当前频道里，未来再遇到类似问题时，团队不必从零开始回忆。

接下来是功能开发。

开发者打开一个功能分支，系统为它建立对应的频道。补丁、自动测试结果、代理的初步审查、同事的反馈，以及最终的合并决定，都集中在这个房间里。代码变化和协作过程不再是两份互相分离的记录。

最后是版本发布。

工作流监听代码标签，一旦触发，就让代理读取已经合并的项目变更，生成发布说明。人类成员审核并批准后，系统再完成发布。这样，代理承担整理和执行工作，人类仍然保留关键的判断和批准环节。

##### 五、Buzz 的产品形态和当前状态

在产品形态上，Buzz 包含频道、线程、私信、画布、媒体、搜索和审计日志等功能。它还提供桌面客户端，使用 Tauri 和 React 构建；同时提供面向代理的命令行工具，也就是 `buzz-cli`。

`buzz-cli` 的设计是“输入 JSON，输出 JSON”。JSON 是一种结构化的数据格式，适合程序和 AI 工具读取。这样的设计方便 Goose、Codex、Claude Code 等代理工具接入 Buzz。项目还提供了一个叫 `buzz-acp` 的连接层，用来把代理通信协议 ACP 和工具协议 MCP 连接起来。

Git 相关能力也被纳入其中。比如，代码补丁、仓库公告和状态变化，可以通过 NIP-34 这类 Nostr 的 Git 事件规范记录下来。项目还包括签名 Git 工具、代理配对工具、工作流系统、媒体存储和管理命令行工具。

不过，Buzz 还没有完成所有设想。

材料把项目状态分成三类：已经可以使用的功能、正在接线的功能，以及有明确方向但代码还没有完成的设想。移动端客户端、推送通知、工作流审批细节、语音讨论的生命周期事件、基于 YAML 的自动化流程、Git 托管后端，以及跨中继的信任和声誉系统，都还在不同阶段的建设中。

其中，项目特别提醒：对于那些仍属于“有想法、待实现”的部分，不要据此制定正式的合规计划。

所以，Buzz 目前更准确的定位是：核心协作能力已经存在，但整体产品仍在持续开发，不应该被当成已经完全成熟的平台。

##### 六、技术架构：中继是唯一的事实来源

下面说说它的技术架构。

Buzz 的核心原则是：中继服务是唯一的事实来源。桌面客户端、AI 代理命令行工具和其他脚本，都会通过 WebSocket 或 REST 接口连接中继。

中继本身负责处理 Nostr 事件、身份认证、频道、私信、媒体、工作流、Git 接口和审计日志。底层则使用几类基础设施。

第一是 PostgreSQL，也就是关系型数据库，用来保存事件，并提供全文搜索。

第二是 Redis，用于发布订阅、在线状态和输入状态等实时信息。

第三是 S3 或 MinIO，用于保存媒体文件。S3 是一种对象存储接口，MinIO 是可以自己部署的兼容实现。

整个项目是一个 Rust 工作区，由多个功能相对独立的代码包组成。核心协议负责事件类型、过滤器和签名验证；数据库模块负责 PostgreSQL；认证模块负责 Nostr 身份认证和限流；搜索模块负责全文检索；审计模块则维护哈希链日志，也就是用前后关联的加密摘要来提高记录的可追溯性。

在多社区部署时，数据库、缓存、搜索文档、媒体信息、工作流状态、Git 仓库指针和审计链，都会按照 URL 对应的社区进行隔离。后台可以共享 PostgreSQL、Redis 和对象存储，但这种共享只是实现方式，对用户来说，每个社区仍然是独立的工作空间。

##### 七、如何开始使用

如果只是体验，项目提供 macOS、Linux 和 Windows 的打包版本。安装后，应用默认连接本机的 `ws://localhost:3000`。这里的 `ws` 是 WebSocket，也就是一种可以持续保持连接、实时收发消息的网络协议。

如果你已经运行了自己的中继，或者有人提供了其他中继地址，可以通过环境变量指定地址，也可以在应用内部切换。

如果希望从源码运行，开发者需要准备 Docker，以及 Hermit，或者 Rust、Node.js 和 pnpm 等工具。项目提供了统一的初始化命令：先获取代码并进入目录，再启用固定工具链，运行初始化和构建流程。初始化过程会准备环境变量、下载所需工具、启动 Docker 服务并执行数据库迁移。

日常开发时，可以运行开发命令，让中继和桌面应用一起启动。默认情况下，中继监听本机三千端口。

对于 AI 代理，则可以配置自己的私钥，并使用 `buzz-cli`。在 Windows 上，代理命令需要通过 Bash 运行，因此要安装 Git for Windows，或者手动指定其他兼容 Bash 的 Shell。

材料中还提到一个特殊的内部构建版本。它预先连接了 Block 的中继和代理服务，安装后基本不需要额外配置。不过，这属于项目材料中的内部使用路径，普通开发者更适合按照开源版本和自托管流程开始。

##### 八、Buzz 的基本立场

最后，需要理解 Buzz 不想成为什么。

它不是区块链项目。虽然它使用带签名的事件，但目的不是发行代币，也不是让所有人购买某种数字资产。

它也不是一个“用 AI 取代人类”的方案。材料明确强调，Buzz 最适合的状态是：人类仍然参与判断，AI 代理则留在团队的工作空间里，帮助搜索、整理、执行和协作。

同时，项目并不回避自己尚未完成这一事实。它会区分哪些功能已经可用，哪些功能仍在接线，哪些只是方向性设想。

Buzz 的真正目标，是用一个统一的协作底层，逐步替代团队现在依赖的多个聊天工具、代码平台、机器人、持续集成页面、发布系统和搜索工具。但材料也承认，这不会一次性完成，也不是自动发生的魔法。

##### 结尾：最值得记住的四点

回顾一下，这份材料最值得记住的有四点。

第一，Buzz 是一个可以自己部署的团队工作区。它把人、AI 代理、代码、工作流和项目记忆放进同一个社区。

第二，Buzz 用 Nostr 的签名事件保存协作过程。消息、代码审查、审批和自动化操作，都有明确身份，也都可以追溯和搜索。

第三，AI 代理在这里是正式成员。它们拥有自己的密钥、频道身份和审计记录，可以处理事故排查、代码审查、工作流和发布任务，但人类仍然参与关键决策。

第四，Buzz 还在发展中。核心频道、线程、私信、搜索、媒体和审计能力已经形成，但移动端、推送、部分工作流、Git 托管和跨社区信任等功能仍在建设或规划阶段。

总体来说，Buzz 想做的不是又一个聊天窗口，而是一套让人和 AI 代理共同工作的统一记录系统。

## 深度解读（1）

### 2026-09-18 00:22:50

#### Buzz 的真正赌注：把 AI 从外挂变成有身份、可追责的协作者

Buzz 表面上像 Slack、GitHub 与 AI 编程工具的混合体，但真正值得关注的不是功能集合，而是它对协作系统做出的一个判断：**当 AI 开始实际修改代码、触发流程、参与审批时，“聊天机器人接入现有工具”已经不够，需要重做协作的记录与身份基础。**

##### 统一的不是界面，而是协作记录

Buzz 将消息、反应、补丁、CI 结果、审批和工作流步骤都表示为 Nostr 签名事件，写入同一个日志。这样，“为什么这段代码存在”不再散落在聊天、PR、CI 页面和发布系统里。

它提出的“分支即房间”很能说明价值：创建功能分支时生成频道，补丁、自动审查、CI、讨论与合并决定都留在其中。之后无论人还是 agent 查询项目历史，得到的不只是搜索摘要，还能返回对应线程和证据。

这比“让 AI 读更多文档”更重要。今天 agent 的常见瓶颈不是模型不会写代码，而是**上下文被切碎，事实之间缺乏稳定关联**。Buzz 试图通过统一事件模型，让项目记忆天然可检索、可追溯，也让自动化无需为每个工具单独维护一套集成关系。

代价同样明显：聊天、代码评审和审批虽然都能表示成事件，却有不同的状态、权限与一致性要求。统一底层数据格式，不等于统一业务语义。Buzz 能否避免成为“另一层需要维护的胶水”，取决于它是否真正取代原有系统，而不只是复制数据。

##### Agent 的身份，可能比 Agent 的智能更关键

Buzz 最有启发性的设计是把 agent 当作成员，而不是隐藏在机器人账号后的定时任务：每个 agent 有自己的密钥、频道成员关系和审计轨迹。发生错误时，可以知道是哪一个 agent、基于哪些信息、执行了什么动作，而不是只看到某个共享 API Token 调用了服务。

这为权限隔离、责任追踪和多人多 agent 协作提供了更清晰的基础。但项目所称的“按身份而非权限标记来限制”仍需谨慎理解：**身份解决的是谁做了什么，授权解决的是它被允许做什么。** 独立密钥可以降低共享凭证的风险，却不能替代最小权限、敏感操作确认、密钥撤销和资源级访问控制。工作流审批门目前也仍在接线中，说明这部分尚未完全兑现。

##### 最值得验证的是“闭环”，而不是功能数量

Buzz 已有 relay、频道、搜索、审计日志、桌面和移动客户端等实现；Git 托管、跨 relay 信任等仍属于愿景。仓库的大量提交和版本发布证明它不是概念稿，却不能证明团队愿意迁移核心协作。

最可能成立的切入口不是替代整个办公套件，而是高上下文成本的场景，例如事故复盘或软件分支协作。应验证的也不是“用户是否喜欢 AI”，而是：统一事件日志能否减少查找历史与跨工具核对的时间；独立 agent 身份能否降低误操作风险；团队是否愿意让它成为项目事实的权威来源。

**Buzz 的机会不在于再造一个更热闹的聊天工具，而在于成为人、代码与 agent 共同工作的可信记录层。** 如果这个记录层不能成为事实来源，再多 agent 功能也只是新的入口；如果能够，聊天反而只是它最不重要的界面。

Buzz 是 Block 开源的自托管协作平台，试图把聊天、AI 代理、代码、CI、审批和项目记录统一到一套可签名、可搜索、可审计的事件日志中。

##### 关键内容

- **人与 AI 代理使用同一套协作方式**：代理可加入频道、查历史、提交补丁、审查代码、运行工作流，并拥有独立身份、密钥和审计记录，而不只是外围聊天机器人。
- **以 Nostr relay 为核心**：消息、反应、Git 事件和审批都保存为签名事件，因此能在同一处搜索并追溯“谁在何时做了什么、依据是什么”。
- **强调自托管与社区隔离**：默认一个 relay 对应一个社区；多租户部署即使共享数据库等基础设施，各社区的数据边界仍独立。
- 项目已有桌面端、移动端、频道、搜索、审计、工作流和代理 CLI 等能力，但 Git 托管、跨 relay 信誉等仍在开发或构想中，并非全部可用。

##### 通俗解读

它想把“群聊、GitHub、CI 面板和 AI 助手”变成一个工作空间。例如一个功能分支可对应一个频道，补丁、测试、审查和合并理由都留在其中。**如果你在评估自托管 AI 协作或事件驱动开发工具，值得细读架构与状态文档；若只想找成熟的一站式替代品，应注意它仍未完成。**
