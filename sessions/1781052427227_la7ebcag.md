基于本地文件系统+git 仓库进行长时间运行 agent 的一种方式：

初始化这个 agent 的整体目标，任务列表/功能列表，然后在一个 Harness loop 里反复读取这个外部的任务列表并更新进度：  
1 每个 session 都重新读取一次全量内容，这样就能够并行工作避免重复执行任务；  
2 每个上下文窗口先读取 progress 进度git 日志来获取本次需要执行的任务  
3 进行冒烟测试  
4 选取一个任务并执行  
5 进行端到端测试  
6 把结果保存到外部文件系统和 git 日志中  
7 持续这个循环知道所有任务完成

这个机制非常简单实用，架构清晰，最大化利用了现有的文件系统和 git 机制，是个非常聪明且高效的办法

## 结构化（1）

### 2026-06-11 09:31:21

##### 主旨概括

文章介绍了一种让 **长时间运行的 Agent** 基于「本地文件系统 + Git 仓库」持续执行任务的方法：通过外部任务列表、进度文件和 Git 日志，让 Agent 在循环中读取任务、执行、测试并记录结果。作者认为这种方式简单、清晰、实用，能充分利用现有文件系统和 Git 机制。

---

##### 1. 核心思路：用文件系统和 Git 管理 Agent 的长期任务

作者提出，可以先为 Agent 初始化：

- 整体目标
- 任务列表
- 功能列表

然后让 Agent 在一个 **Harness loop（执行循环）** 中反复运行：

- 读取外部任务列表
- 判断当前进度
- 选择任务执行
- 测试结果
- 保存进展

这种方式把 Agent 的“记忆”和“任务状态”放在本地文件系统与 Git 仓库中，而不是完全依赖模型上下文。

---

##### 2. 运行流程：每轮循环如何执行任务

文章列出了一个较完整的执行流程：

1. **每个 session 重新读取全量内容**  
   - 每次启动或进入新会话时，都重新读取完整任务列表和相关文件。
   - 好处是多个 Agent 或多个会话可以并行工作，减少重复执行同一任务的风险。

2. **读取 progress 进度和 Git 日志**  
   - 在每个上下文窗口开始时，先读取进度文件和 Git 历史。
   - 这样 Agent 可以知道：
     - 哪些任务已经完成
     - 哪些任务正在进行
     - 本次应该执行什么任务

3. **进行冒烟测试**  
   - 在正式执行任务前，先做基础测试。
   - 目的是确认当前系统或项目处于可运行状态，避免在错误基础上继续开发。

4. **选取一个任务并执行**  
   - Agent 根据任务列表和进度，选择一个尚未完成的任务。
   - 然后执行具体开发、修改或处理工作。

5. **进行端到端测试**  
   - 任务完成后，做更完整的测试。
   - 确保改动不仅局部可用，也能在整体流程中正常运行。

6. **保存结果到外部文件系统和 Git 日志**  
   - 执行结果、进度更新、代码变化等都写入文件系统。
   - 同时通过 Git 记录变更历史，方便追踪和回滚。

7. **持续循环直到所有任务完成**  
   - Agent 不断重复上述流程，直到任务列表中的内容全部完成。

---

##### 3. 这种机制的优点

作者认为，这种设计有几个明显优势：

- **简单实用**：不依赖复杂系统，只用文件系统和 Git 就能实现。
- **架构清晰**：任务、进度、代码变更都有明确存放位置。
- **适合长时间运行**：Agent 可以跨 session 继续工作，不容易丢失状态。
- **支持并行协作**：每次读取全量任务和 Git 日志，有助于多个 Agent 避免重复劳动。
- **充分利用现有工具**：Git 天然适合记录变更、追踪历史、管理冲突。

---

##### 4. 热门回复：Agent Harness 的一个重要陷阱

热门回复提到「Agent Harness 的五个陷阱」，其中已展示的第一点是：

###### 自我评估是陷阱，要使用对抗式评测器

原文观点：

> Self-evaluation is a trap. Use an adversarial evaluator.  
> 自我评估是陷阱。要用对抗式评测器。

很多团队会让 Agent 自己生成答案，然后再让同一个 Agent 给自己评分，例如：

```text
Agent 生成答案
↓
Agent 自己打分
↓
Agent 说：95 分
```

但上线后可能出现问题。原因是模型容易有 **共识偏见 / 认同偏差（agreement bias）**：  
它倾向于认可自己生成的内容，因此自评结果往往过于乐观。

所以更可靠的做法是：

- 不让 Agent 单独自评
- 引入独立的、甚至“挑刺式”的评测器
- 用更严格的测试或对抗式评估来发现问题

---

##### 总结

这篇文章的核心价值在于：提出了一种低成本、可落地的长时间运行 Agent 架构。通过「任务文件 + 进度记录 + Git 日志 + 测试循环」，Agent 可以持续推进复杂任务，并保持状态可追踪、结果可验证。与此同时，热门回复提醒：在 Agent Harness 中不能过度依赖模型自评，评估环节应尽量独立和对抗化。
