## 分析要点

- **核心高价值点**：最有价值的点是把“何时压缩上下文”从固定阈值规则转为由模型在任务边界和信息提炼完成后自主决策。
- **留存建议**：中期保留，作为Agent上下文管理设计案例参考（提出了自主触发上下文压缩的实用设计思路，并给出使用方式与适用场景，适合后续构建长程Agent时参考。）

**知识要点**

- 固定token阈值触发压缩并不总是最优，任务边界往往是更好的压缩时机
- 自主压缩适用于开始新任务、提炼出结论、准备读取大量新上下文或进入复杂多步流程前
- 实现上可保留最近约10%上下文并总结更早消息，以兼顾连续性与容量
- 保留完整历史于虚拟文件系统可降低错误压缩带来的信息丢失风险
- 该设计体现让模型接管更多工作记忆控制、减少手工规则调参的Agent工程趋势

**行动项**

- 如果你在构建长会话Agent，可评估把上下文压缩从固定阈值改为模型可调用工具
- 为Agent定义明确的压缩触发指引，如任务完成、新需求覆盖旧需求、进入大规模读写前
- 在本地任务上对比自主压缩与固定阈值压缩的成功率、成本与中断感受
- 补充评测：统计误触发压缩、遗漏压缩和压缩后任务成功率的变化

**Mason Daugherty**

### Autonomous context compression

TL;DR: We’ve added a tool to the

[Deep Agents SDK](https://docs.langchain.com/oss/python/deepagents/overview) (Python) and

[CLI](https://docs.langchain.com/oss/python/deepagents/cli/overview)

that allows models to compress their own context windows at opportune times.

---

#### Motivation

[Context compression](https://blog.langchain.com/context-management-for-deepagents/) is an action that reduces the information in an agent’s working memory. Older messages are replaced by a summary or condensed representation of an agent’s progress that preserves what’s relevant to a task. This action is often necessary to accommodate finite context windows and reduce

[context rot](https://research.trychroma.com/context-rot)

.

Agent harnesses often control this by compacting at a fixed token threshold (\`deepagents\` uses

[model profiles](https://docs.langchain.com/oss/python/langchain/models#model-profiles) to compact at 85% of any given model’s context limit). This design is suboptimal because there are good times and bad times to compact:

- It is not ideal to compact when you’re in the middle of a complex refactor;
- It is better to compact when you are starting a new task or otherwise believe that prior context will lose relevance.

Many interactive coding tools feature a \`/compact\` command or similar, which allows users to manually trigger a context compression step at opportune times. We take this one step further in the latest release of \`deepagents\` and expose a tool to the agent that lets it trigger context compression itself. This enables more opportunistic compaction without requiring your application’s users to be aware of finite context windows or issue specific commands.

This tool is currently enabled in

[Deep Agents CLI](https://docs.langchain.com/oss/python/deepagents/cli/overview) and opt-in in the \`deepagents\` SDK.

We are generally bullish on the idea that harnesses should, where possible, “get out of the way” and take advantage of improvements in the underlying reasoning models. This is an instance of

[the bitter lesson](http://www.incompleteideas.net/IncIdeas/BitterLesson.html): can we give agents more control over their own context to avoid tuning their harness by hand?

#### When should we compact?

There is a variety of situations that could warrant a context compression action.

At clean task boundaries:

- A user signals that they are moving on to a new task for which earlier context is likely irrelevant
- The agent has finished a deliverable and the user acknowledges task completion

After extracting a result from a large amount of context:

- The agent has obtained a fact, conclusion, summary, or other result by consuming a significant amount of context, as in a research task

Before consuming a large amount of new context:

- The agent is about to generate a long draft
- The agent is about to read a large amount of new context

Before entering a complex multi-step process:

- The agent is about to start a lengthy refactor, migration, multi-file edit, or incident response
- The agent has produced a plan and is about to begin executing the steps

A decision has been made that supersedes prior context:

- New requirements have come to light that invalidate previous context
- There are many tangents or dead-ends that can be reduced to a summary

Enumerating all possible scenarios is not practical, but our observation is that people and LLMs can identify these scenarios and compact at opportune times, saving the need for a compaction step later on when the context window is nearing its limit. You can read the guidance we provide the model around this tool in its

[system prompt](https://github.com/langchain-ai/deepagents/blob/537ed6cf153f9f6e50546c9d8674c32587540942/libs/deepagents/deepagents/middleware/summarization.py#L91).

#### What happens when the tool is called?

The tool is parametrized the same as the existing Deep Agents

[summarization middleware](https://docs.langchain.com/oss/python/deepagents/harness#summarization): we retain recent messages (10% of available context) and summarize what comes before. Recent messages, including the call to the compaction tool and associated response, are retained in the recent context.

![Image](https://pbs.twimg.com/media/HDJhyofbwAAINV-?format=jpg&name=large)

See

[example trace](https://smith.langchain.com/public/0ff5b066-7377-4922-9269-927e29bd4aba/r).

#### How to use

The tool is implemented as a separate middleware, so you can enable it by adding it to the middleware list in \`create\_deep\_agent\`:

```python
from deepagents import create_deep_agent
from deepagents.backends import StateBackend
from deepagents.middleware.summarization import (
    create_summarization_tool_middleware,
)

backend = StateBackend  # if using default backend

model = "openai:gpt-5.4"
agent = create_deep_agent(
    model=model,
    middleware=[
        create_summarization_tool_middleware(model, backend),
    ],
)
```

See the SDK

[docs](https://docs.langchain.com/oss/python/deepagents/harness#context-management) for more details.

In the CLI, simply call \`/compact\` when you’re ready to trim context or move onto a new task.

#### Our experience with this feature

We tuned this feature to be conservative. Deep Agents

[preserves all conversation history](https://docs.langchain.com/oss/python/deepagents/harness#summarization) in its virtual filesystem, allowing for recovery of context post-summarization, but an erroneous context compression step is disruptive. We tested:

- A custom evaluation suite, in which we used (our own)
  [LangSmith traces](https://docs.langchain.com/langsmith/observability) to inject follow-up prompts to threads that do and do not warrant compaction;
- Terminal-bench-2, in which we did not observe any instances of autonomous compaction;
- Our own coding tasks in
  [Deep Agents CLI](https://docs.langchain.com/oss/python/deepagents/cli/overview).

In practice agents are conservative about triggering compaction, but when they do they tend to choose moments where it clearly improves the workflow.

Autonomous context compression is a small feature, but it points at a broader direction for agent design: giving models more control over their own working memory and fewer rigid, hand-tuned rules in the harness. If you’re building long-running or interactive agents, try it out in the Deep Agents SDK or CLI and let us know your feedback and what patterns you’d like to see it handle next.

## 结构化（1）

### 2026-03-12 09:47:18

**主旨概括：**  
这篇文章介绍了 Deep Agents 新增的 “自主上下文压缩” 功能：让智能体自己决定何时压缩上下文，而不是只靠固定阈值触发。这样能更合理地节省上下文空间，减少信息老化，并提升长任务或交互式任务的体验。

---

##### 1. 为什么要做 “自主上下文压缩”
- 上下文压缩的作用：把较早的对话和过程信息，替换成摘要或精简表示，只保留和当前任务相关的内容。  
- 这样做的原因有两个：  
  - **上下文窗口有限**，不能无限保留所有内容；  
  - **减少 “上下文腐化”**，避免旧信息过多干扰当前任务。  
- 过去常见做法是：到达固定 token 阈值时再压缩。  
  - 例如`deepagents`以前会在**模型上下文上限的 85%**时触发压缩。  
- 但这种方式并不理想，因为压缩也有 “好时机” 和 “坏时机”：  
  - **坏时机**：正在做复杂重构时突然压缩；  
  - **好时机**：刚完成一个任务、准备进入新任务时压缩。  

**例子：**  
如果智能体正在进行一个多文件重构，压缩过早可能丢掉关键细节；但如果刚写完一个功能，准备处理下一个需求，这时压缩通常更合适。

---

##### 2. 这个新功能解决了什么问题
- 很多交互式编码工具本来就有`/compact`这类手动命令，让用户自己选择时机压缩。  
- Deep Agents 更进一步：**把压缩能力做成工具，直接开放给模型自己调用**。  
- 这样带来的好处是：  
  - 智能体可以在更合适的节点主动压缩；  
  - 不需要用户理解上下文窗口限制，也不用手动下命令。  
- 当前支持情况：  
  - **Deep Agents CLI：默认启用**；  
  - **`deepagents` SDK：需要手动开启（opt-in）**。  

**核心理念：**  
文章认为，Agent 框架应尽量 “少管”，把更多控制权交给底层更强的推理模型，而不是依赖很多手工调参规则。

---

##### 3. 什么时候适合压缩
文章按场景列出了几类适合触发压缩的时机：

###### 3.1 在清晰的任务边界处
- 用户明确表示要开始一个新任务；
- 智能体完成交付物，且用户确认任务结束。  

**例子：**  
刚修完一个 bug，用户接着说 “现在帮我写部署文档”，这就是适合压缩的时机。

###### 3.2 从大量上下文中提炼出结果之后
- 智能体已经从大量信息中提取出事实、结论或摘要；
- 常见于研究、资料整理类任务。  

**例子：**  
读完十几份文档后，已经得出关键结论，就可以把前面的阅读过程压缩成结论摘要。

###### 3.3 在即将接收大量新内容之前
- 要生成一篇很长的草稿；
- 要读取大量新上下文。  

**例子：**  
准备读取一个大型代码库，或者要起草一份长篇技术方案前，先压缩旧内容更稳妥。

###### 3.4 在进入复杂多步骤流程之前
- 即将开始长时间重构、迁移、多文件修改或事故响应；
- 已经产出执行计划，准备按步骤实施。  

###### 3.5 当新决策已经覆盖旧上下文时
- 出现了新需求，导致之前的上下文部分失效；
- 之前有很多岔路、试错或死胡同，可以统一浓缩成摘要。  

**总结一句：**  
不是所有场景都能提前列举，但作者观察到：**人和大模型通常都能识别这些 “好时机”**，从而比 “快满了才压缩” 更主动、更有效。

---

##### 4. 调用这个工具后会发生什么
- 这个工具的参数与 Deep Agents 现有的摘要中间件一致：  
  - **保留最近消息，占可用上下文的 10%**；  
  - 更早的内容会被总结压缩。  
- 特别说明：  
  - 最近消息会保留；  
  - **触发压缩的工具调用本身及其响应**，也会保留在最近上下文中。  

**简单理解：**  
就是 “旧内容变摘要，最新的重要对话继续原样保留”。

---

##### 5. 如何使用
###### 5.1 在 SDK 中使用
- 这个功能是以**独立中间件**实现的；
- 需要在`create_deep_agent`的`middleware`列表中添加。  

文章给出的关键信息：
- 使用`create_summarization_tool_middleware (model, backend)`开启；
- 示例模型为：`openai:gpt-5.4`。

###### 5.2 在 CLI 中使用
- 用户可以直接输入：`/compact`  
- 适合在准备清理上下文、或准备切换到新任务时使用。

---

##### 6. 官方测试和实际体验
- 这个功能被刻意调得**比较保守**，原因是：  
  - 虽然 Deep Agents 会在虚拟文件系统中保留完整对话历史，后续仍可恢复；  
  - 但如果在错误时机压缩，依然会打断工作流。  

###### 测试方式包括：
- **自定义评测集**：  
  - 使用 LangSmith traces；  
  - 向不同线程注入后续提示，观察哪些情况适合压缩、哪些不适合。  
- **Terminal-bench-2**：  
  - **没有观察到任何自主压缩触发**。  
- **团队自己的 CLI 编码任务**。  

###### 实际结论：
- 智能体通常对触发压缩**比较谨慎**；  
- 但一旦触发，往往选在**明显有利于工作流**的时机。

---

##### 7. 文章的最终观点
- “自主上下文压缩” 虽然是个小功能，但代表了一个更大的 Agent 设计方向：  
  - **让模型更多管理自己的工作记忆**；  
  - **减少框架中僵硬、手工调出来的规则**。  
- 对于长期运行或高互动的 Agent，这个能力值得尝试。  

**一句话总结：**  
与其让系统在快满时被动压缩，不如让智能体在 “合适的时候” 主动压缩。

## 产品-技术开发（1）

### 2026-03-12 09:47:53

下面从**产品价值、技术设计、实现方式、最佳实践**四个层面，做一个偏 “可落地” 的解读。

---

##### 1. 这是什么：不是 “摘要功能”，而是 “Agent 自主内存管理”

###### 核心点
这篇内容真正有价值的地方，不是加了一个`/compact`，而是：

> **把 “何时压缩上下文” 的决策权，从固定阈值规则，部分交给模型自己。**

这本质上是把 Agent 的能力，从：
- 被动地等系统快爆上下文再压缩

升级为：
- **主动地在任务边界、阶段切换、信息提炼完成后，自己整理工作记忆**

###### 产品视角的意义
这是一个典型的**“用户无感优化”**：
- 用户不需要理解 context window
- 用户不需要学会手动`/compact`
- Agent 自己在合适时机做 “记忆整理”

它提升的不是单点功能，而是整体体验：
- 更少中途打断
- 更少 “上下文糊掉”
- 更适合长流程、多轮交互、编码 / 研究型任务

---

##### 2. 为什么固定阈值压缩不够好

传统做法是：
- 上下文用到 80% / 85% / 90% 时触发压缩

这在工程上简单，但在产品上很粗暴。

###### 典型问题
###### 1）压缩时机不对
比如：
- 正在做复杂 refactor
- 正在分析 bug 根因
- 正在跨文件迁移
- 正在对比多个方案

这时压缩，容易丢掉 “推理链上的局部细节”。

###### 2）该压缩时没压缩
比如：
- 一个研究任务已经得出了清晰结论
- 用户开始一个新任务
- 之前很多探索已经变成 “已知结论”

这时如果不压缩，后面会带着大量低价值历史继续跑，导致：
- token 浪费
- 注意力稀释
- context rot（上下文腐化，相关信息被噪音淹没）

###### 本质洞察
**上下文的价值不是线性递减的，而是阶段性变化的。**

因此压缩策略不该只看 “用了多少 token”，还应看：
- 当前是不是任务边界
- 已有信息是否已提炼成结果
- 接下来是否要吃进大量新上下文
- 当前是否准备进入重执行阶段

---

##### 3. 产品设计上，这个功能设计得对的地方

---

###### 3.1 把压缩做成 “工具”，而不是写死在 harness 里
这是最关键的设计选择。

###### 为什么好
如果写死成系统规则：
- 灵活性差
- 很难覆盖各种任务形态
- 会不断调阈值、补 case、加规则，越来越复杂

做成一个工具：
- 模型可自主调用
- harness 仍保留兜底机制
- 可观测、可审计、可评估

###### 最佳实践
在 Agent 架构里，**记忆操作都尽量工具化**，比如：
- `compress_context ()`
- `pin_memory ()`
- `archive_task_result ()`
- `restore_memory_segment ()`

这样 “工作记忆管理” 就成为可组合能力，而不是黑盒。

---

###### 3.2 采用 “近期消息保留 + 远端总结” 的分层内存
文中策略是：
- 保留最近 10% 上下文
- 之前的内容做总结压缩

这是很实用的折中方案。

###### 为什么合理
最近消息通常包含：
- 当前指令
- 当前计划
- 当前工具调用状态
- 最近约束和改动

这些是 “高活性工作内存”，不能轻易丢。

更早的内容更适合变成：
- 任务目标
- 已完成工作
- 关键结论
- 未完成事项
- 风险和约束

这其实就是经典的：
- **短期工作记忆**
- **长期摘要记忆**

###### 最佳实践
总结结构不要写成纯自然语言长段落，最好结构化：

```json
{
  "task_goal": "...",
  "completed_work": ["...", "..."],
  "key_decisions": ["...", "..."],
  "constraints": ["...", "..."],
  "open_issues": ["...", "..."],
  "files_touched": ["a.py", "b.py"],
  "next_step": "..."
}
```

这样后续模型恢复上下文时更稳定，也更利于程序处理。

---

###### 3.3 设计上偏保守，这很对
“错误压缩” 比 “少压缩一次” 代价更大。

###### 原因
压缩是有损操作：
- 细节可能丢
- 之前的隐含推理链可能断
- 后续任务可能依赖某个未被总结的局部事实

所以产品上应该：
- **默认保守**
- 有 fallback
- 允许恢复
- 做可观测追踪

文中提到：
- 所有历史保存在 virtual filesystem
- 可在压缩后恢复上下文

这点非常重要。  
没有可恢复机制，自主压缩风险会明显增大。

---

##### 4. 技术上，这个能力背后的架构要点

---

###### 4.1 本质是 “Summarization Middleware + Tool Invocation”
实现上它不是新模型能力，而是组合：
1. 给模型一个工具：`compact /summarize_context`
2. 给模型提示：什么时候适合调用
3. middleware 执行：
   - 截断历史
   - 生成摘要
   - 保留最近窗口
   - 写入状态存储

###### 推荐架构
建议分四层：

###### A. 决策层
由模型判断是否压缩：
- 当前任务阶段
- 上下文密度
- 即将发生的长输入 / 长输出
- 用户语义上的任务切换

###### B. 执行层
调用 middleware：
- 抽取历史消息
- 生成摘要
- 替换历史上下文
- 保留 recent messages

###### C. 存储层
把原始历史和摘要都存下来：
- raw transcript
- summary snapshots
- compaction events

###### D. 恢复层
支持：
- 回看原始记录
- 针对某个历史阶段再展开
- 出错时回滚到压缩前状态

---

###### 4.2 真正难点不在 “压缩”，在 “压缩后保真”
很多团队做摘要压缩失败，不是因为不会摘要，而是摘要内容不适合后续推理。

###### 压缩必须保留的 6 类信息
最佳实践里，摘要至少保留：

1. **任务目标**
2. **当前结论**
3. **关键约束**
4. **已经尝试过但失败的路径**
5. **已修改 / 已观察的对象**
6. **下一步计划**

如果缺少第 4 项，模型容易重复走弯路。  
如果缺少第 6 项，模型容易在压缩后失去执行连续性。

---

###### 4.3 最佳摘要不是 “短”，而是 “可继续工作”
很多人误以为压缩目标是 “尽量省 token”。  
实际上，目标应该是：

> **在更少 token 下，最大化后续行动能力。**

所以好的压缩摘要，不是新闻摘要风格，而是**handoff /checkpoint 风格**。

###### 好的压缩摘要模板
```text
Current objective:
Completed:
Key findings:
Constraints:
Dead ends /avoid:
Files /entities involved:
Pending decisions:
Next action:
```

这比 “总结一下上文内容” 效果稳定得多。

##### 5. 具体产品场景：什么时候最适合自主压缩

文中给的判断场景是对的，我补充成更工程化的分类。

---

###### 场景 1：任务切换
###### 例子
用户说：
- “这个修完了，我们看下登录性能问题”
- “先不做这个，改成支持 SSO”
- “研究先到这，帮我起草汇报邮件”

###### 为什么适合压缩
旧任务大概率只需保留：
- 完成结果
- 关键约束
- 与新任务共享的背景

其余过程性对话可以折叠掉。

###### 最佳实践
在检测到任务切换时，触发一次 checkpoint：
- old task summary
- carry-over constraints
- new task objective

---

###### 场景 2：大规模阅读后已得出结论
###### 例子
Agent：
- 读了 20 个文件
- 看了大量日志
- 搜了很多文档
- 最终确认根因

###### 为什么适合压缩
这时价值已经从 “原始材料” 迁移到 “结论和证据”。

###### 最佳实践
摘要中必须包含：
- 结论
- 证据来源
- 置信度
- 尚未验证部分

不要只写 “发现是 X”，要写 “为什么是 X”。

---

###### 场景 3：即将进入重执行阶段
###### 例子
- 准备开始多文件重构
- 准备执行 migration
- 准备大规模代码生成
- 准备 incident response 操作

###### 为什么适合压缩
执行阶段更需要：
- 清晰计划
- 约束
- 当前状态

而不需要保留所有探索过程。

###### 最佳实践
先让模型形成计划，再压缩，再执行。
顺序应该是：

1. 分析问题
2. 产出 plan
3. 压缩成 execution brief
4. 开始执行

这是最优时机。

---

###### 场景 4：出现新信息推翻旧路径
###### 例子
- 用户补充了新需求
- 根因判断被证伪
- 技术选型被组织约束否决
- API 版本信息更新

###### 为什么适合压缩
因为旧上下文中大量内容已经 “失效”，继续保留只会污染注意力。

###### 最佳实践
压缩时显式标记：
- 哪些旧假设已失效
- 新基线是什么
- 后续不要再沿用哪些结论

这能显著减少模型 “幽灵记忆”。

##### 6. 开发实现建议：如果你自己做这个功能，怎么设计

---

###### 6.1 工具接口设计
推荐不要只做一个无参`compact ()`，而是带上意图。

###### 推荐接口
```python
compress_context (
    reason: Literal [
        "task_boundary",
        "result_extracted",
        "before_large_input",
        "before_execution",
        "superseded_context"
    ],
    focus: str | None = None
)
```

###### 好处
- 更易观测
- 更易评估
- 更易调优
- 可针对不同 reason 采用不同摘要模板

---

###### 6.2 摘要模板按场景分化
不要所有压缩都用一种 prompt。

###### 示例
###### A. 任务边界压缩
强调：
- 已完成内容
- 可交付物
- 可继承约束

###### B. 执行前压缩
强调：
- 当前计划
- 步骤依赖
- 风险点
- 回滚策略

###### C. 研究后压缩
强调：
- 结论
- 证据
- 不确定项
- 下一步建议

这样摘要质量会明显高于通用压缩 prompt。

---

###### 6.3 增加 “压缩置信门控”
让模型不是想压就压。

###### 可采用双重门控
1. **语义门控**：模型判断是否适合压缩  
2. **系统门控**：程序检查是否满足条件，例如：
   - 最近 3 轮不是高频工具交互
   - 当前没有未闭合的计划步骤
   - 当前 token 占用达到一定下限
   - 距上次压缩至少 N 轮

###### 这样可以避免
- 频繁压缩
- 在关键执行中途压缩
- token 还很充裕时无意义压缩

---

###### 6.4 建立压缩评估指标
这是落地时最容易被忽视的。

###### 必须监控的指标
- 压缩触发率
- 压缩后任务完成率
- 压缩后重复探索率
- 压缩后用户纠正率
- 压缩后 token 节省量
- 压缩后平均轮次变化

###### 更关键的定性指标
- 压缩后是否丢约束
- 是否丢文件状态
- 是否忘记已失败方案
- 是否打断当前工作流

##### 7. 一个高质量最佳实践例子：Coding Agent

---

###### 场景
用户让 Agent 修复一个 Python 服务的性能问题，过程如下：
1. Agent 阅读 15 个文件
2. 分析 profiling 结果
3. 确认瓶颈是 ORM N+1 查询
4. 产出重构方案
5. 准备修改 6 个文件并补测试

###### 错误做法
等上下文到了 85% 再压缩。  
问题：
- 可能压在改代码中途
- 丢掉刚形成的重构计划
- 工具状态和文件依赖关系容易混乱

###### 正确做法
在第 4 步后、执行第 5 步前自主压缩。

###### 压缩摘要应长这样
```text
Objective:
Fix API latency in order retrieval path.

Root cause:
N+1 queries in OrderService -> ItemRepository access pattern.

Evidence:
Profiler shows 240ms DB time across repeated item lookups.
Confirmed in files service/order_service.py and repo/item_repo.py.

Plan:
1. Add bulk item fetch API in item_repo.py
2. Refactor order_service.py to batch-load items
3. Update serializer assumptions
4. Add regression test for query count
5. Run targeted test suite

Constraints:
Do not change response schema.
Keep backward compatibility with existing repository interface where possible.

Files involved:
service/order_service.py
repo/item_repo.py
api/serializer.py
tests/test_order_api.py

Avoid:
Do not reintroduce per-order item fetch in serializer layer.

Next step:
Implement bulk fetch in repository, then refactor service.
```

###### 结果
后续即便上下文缩短，Agent 仍能稳定执行修改。

##### 8. 再给一个最佳实践例子：Research Agent

---

###### 场景
Agent 帮用户调研 “是否采用向量数据库还是 pgvector”：
- 看了大量文档
- 比较了成本、性能、运维复杂度
- 已形成建议

###### 最佳压缩时机
当 “结论已经形成，准备进入汇报 / 方案输出” 时。

###### 压缩摘要模板
```text
Research question:
Should we use a dedicated vector DB or pgvector for current scale?

Conclusion:
Use pgvector for current phase; dedicated vector DB only when multi-tenant scale and advanced retrieval needs increase.

Reasons:
- Current data size fits Postgres well
- Lower operational complexity
- Existing team already maintains Postgres
- Query latency target is achievable with current load

Tradeoffs:
- Dedicated vector DB may outperform at larger scale
- Some advanced indexing and filtering features are limited in pgvector

Decision boundary:
Re-evaluate if corpus > X, QPS > Y, or hybrid retrieval complexity increases.

Next deliverable:
Draft architecture recommendation memo for engineering review.
```

这样后续生成 PRD、架构建议、汇报材料都更稳。

##### 9. 这个方向更大的趋势意义

这篇文章真正代表的是一个 Agent 设计趋势：

> **Harness 少做硬编码流程控制，更多把 “元认知操作” 交给模型。**

这里的 “元认知操作” 包括：
- 何时压缩记忆
- 何时规划
- 何时复盘
- 何时切任务
- 何时请求更多信息
- 何时回溯恢复历史

###### 这是对的，但边界要清楚
适合交给模型的：
- 时机判断
- 语义抽象
- 工作流切换

不适合完全交给模型的：
- 数据持久化策略
- 恢复机制
- 安全边界
- 审计日志
- 成本控制上限

也就是：
- **决策可更智能**
- **基础设施必须更可靠**

##### 10. 结论：你做 Agent 产品时可直接抄的原则

###### 产品原则
1. 压缩应尽量用户无感
2. 压缩时机优先看任务阶段，不只看 token 阈值
3. 默认保守，错误压缩代价很高
4. 必须支持恢复和回溯
5. 把压缩作为 “工作记忆管理” 能力的一部分

###### 技术原则
1. 做成工具，不要写死成单一规则
2. 摘要要结构化，不要只生成自然语言大段总结
3. 按场景定制摘要模板
4. 保留 recent context，压缩 older context
5. 建立压缩后的效果评估体系

###### 一句话评价
这不是一个 “小优化”，而是**Agent 从 “被动上下文消费者” 走向 “主动工作记忆管理者”**的关键一步。

---

##### 具体实例：让智能编码代理完成一个 “用户登录模块重构” 任务

###### 场景
你在用 Deep Agents CLI 或 SDK 驱动一个编码代理，连续完成以下工作：

1. 阅读旧的登录代码  
2. 理解数据库表结构和认证流程  
3. 排查一个 session 丢失 bug  
4. 产出修复方案  
5. 接着开始一次较大的重构：  
   - 把 session 认证改成 JWT
   - 修改 6 个文件
   - 更新中间件
   - 补测试
   - 写迁移说明

这时，上下文里已经积累了很多内容：
- 旧代码细节
- 多轮排查过程
- 一些已经放弃的猜测
- bug 的最终结论
- 用户的新需求：“不要只修 bug，直接改成 JWT 方案”

---

##### 最佳实践（精炼）

###### 1. **不要在重构进行到一半时压缩**
**反例**：代理已经改到第 3 个文件、正在同步接口签名时触发 compact。  
这会丢失细粒度编辑意图，容易让后续操作断裂。

**最佳实践**：  
在**开始大重构之前**压缩，而不是在中途压缩。

---

###### 2. **先提炼 “已确定结论”，再压缩**
在这个例子里，适合保留的不是所有排查细节，而是：
- bug 根因是什么
- 为什么决定改为 JWT
- 哪些旧方案被放弃
- 接下来要改哪些文件
- 验收标准是什么

**最佳实践**：  
压缩前确保代理已形成**稳定结论 / 明确计划**，把 “过程” 压成 “决策与约束”。

---

###### 3. **最适合压缩的时机：任务边界或阶段切换点**
这个例子里，最好的压缩点是：

> “bug 已定位并确认；现在开始 JWT 重构。”

这是典型的文章里提到的：
- clean task boundary
- before entering a complex multi-step process
- a decision supersedes prior context

**最佳实践**：  
在 “排查结束 → 进入实施” 这个边界执行压缩。

---

###### 4. **压缩内容应聚焦‘后续执行必需信息’**
在这个实例中，摘要应包含：

- 当前目标：将登录系统从 session 改为 JWT
- 已确认事实：session 丢失根因、旧认证链路的关键问题
- 设计决策：采用 JWT、保留哪些兼容行为
- 执行计划：修改 auth middleware /login handler /token utils /tests/docs
- 风险点：前端 token 刷新、旧接口兼容、测试覆盖

**最佳实践**：  
摘要不是 “聊天记录缩写”，而是**下一阶段工作的操作说明**。

---

###### 5. **对长上下文读取任务，也应在 “提取结论后” 压缩**
如果代理前面读了大量代码、日志、文档，最终只得到一个结论：“必须切 JWT，且用户表无需迁移”，那就应在结论确认后压缩。

**最佳实践**：  
“读很多” 之后，一旦 “结论稳定”，就压缩；不要等上下文快满了再被动压缩。

---

##### 这个实例下的一条最佳实践模板

你可以把它概括成一句话：

> **在完成 bug 排查并形成 JWT 重构计划后，立即压缩上下文，只保留‘根因、决策、约束、改动范围、验收标准’，再进入多文件重构。**

---

##### 一个精炼示范摘要

如果让代理在该时机 compact，理想摘要类似：

- 已完成：登录态丢失问题排查  
- 根因：session 在跨服务调用链中未稳定传递  
- 已决策：不再继续修补 session 方案，改为 JWT  
- 目标：完成登录 / 鉴权链路 JWT 化  
- 涉及文件：auth middleware、login API、token utility、前端鉴权调用、测试  
- 约束：保持现有登录接口返回结构尽量兼容  
- 风险：token 过期刷新、老测试失效、文档需同步更新  
- 下一步：按计划逐文件实施并补充测试

---

##### 最后给出一条 “可执行最佳实践”

**最佳实践：**  
在代理完成一个信息密集型阶段（如排查、研究、阅读）并即将进入一个高执行成本阶段（如重构、迁移、多文件修改）时，主动触发上下文压缩；摘要只保留**结论、决策、计划、约束和风险**，不要保留大量探索过程。
