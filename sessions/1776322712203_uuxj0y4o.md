## 通俗精炼（1）

### 2026-04-16 06:58:20

#### Agent 开发技术栈建议总结

##### 核心观点

如果你用的是 TypeScript 技术栈，做 Agent 开发时，`pi-mono` 是更推荐的首选方案，原因是功能更强、调用更方便。其次可以考虑 Vercel 的 `AI SDK`。相比之下，`Claude Agent SDK` 不太推荐，因为它过度绑定 Claude 生态，但它目前仍有一个独特优势：开发阶段可以共享 `Claude Max` 订阅，短期内比较省事。

##### 应用形态选择

在桌面应用层，`Electron` 仍然是优先选择，优势是成熟稳定、生态完善，而且 AI 相关训练语料足够多，遇到问题更容易找到参考。它的主要缺点是应用体积偏大。也有观点提到，若追求更轻量的包体，可以考虑 `Tauri`，能显著缩小安装包大小。

##### 开发路径建议

对于刚开始做 Agent 的人，不建议一上来就做图形界面，更适合先从 `CLI`（命令行）开始。这样可以把精力集中在 Agent 本身的能力建设上，比如任务拆解、调用链路、工具设计，而不是过早陷入界面和交互细节。除非你的产品核心竞争力本身就是 UI。

##### 学习参考项目

文中推荐了一个开源项目 `craft-agents-oss`，其技术组合是 `TypeScript + pi-mono + Electron + React + Claude Agent SDK`。这个项目比较适合作为学习样本，用来理解一套完整 Agent 产品是如何组织技术栈和工程结构的。

##### 更重要的工程能力

除了选框架，Agent 开发真正绕不开的是一系列通用工程问题，包括：

- Prompt 和 Context 管理
- Agent 与 Sub-agent 协作
- 工具调用设计及结果处理
- Skill 能力封装
- Hook、Session 管理等外围机制

也就是说，技术栈只是起点，真正拉开差距的是 Agent 工程化能力。

##### 一句话结论

这条内容的核心建议可以概括为：  
**TypeScript 做 Agent，优先选 `pi-mono`；桌面端优先 `Electron`；产品早期先做 `CLI`；多研究成熟开源项目和通用 Agent 工程问题。**

## 解读（1）

### 2026-04-20 00:07:23

#### 一句话总结

如果你用 **TypeScript** 做 Agent，文中观点是：**框架首选 `pi-mono`，其次 `Vercel AI SDK`；桌面应用优先考虑 `Electron`；但真正开始时，最好先从 `CLI` 做起，先把 Agent 能力打磨好，再考虑 UI。**

#### 深入浅出地解读

##### 1. 为什么推荐 `pi-mono`
作者认为，`pi-mono` 在 TypeScript Agent 开发里属于 **功能强、调用顺手** 的方案。

通俗讲，就是：

- **能力比较全**：适合真正做 Agent，而不是只做一次性调用 LLM。
- **上手效率高**：API 用起来比较自然，不容易被框架“绊住手脚”。
- **更适合长期工程化**：不是只写 demo，而是能往产品方向走。

这意味着，如果你已经确定主技术栈是 TypeScript，`pi-mono` 值得优先试。

---

##### 2. `Vercel AI SDK` 为什么是“第二选择”
文中说它“也还可以”，这通常代表：

- 生态成熟，社区认知高；
- 对常见 AI 接入场景很友好；
- 但在复杂 Agent 能力上，可能不是最强项。

可以理解成：  
**做 AI 应用很方便，但做“复杂 Agent 系统”未必是最优。**

---

##### 3. 为什么不太推荐 `Claude Agent SDK`
核心原因就一句话：

- **绑定 Claude 太死。**

也就是说：

- 模型供应商切换不灵活；
- 架构容易被单一平台限制；
- 长远看，可能不利于产品演进。

但它也有一个现实优势：

- **可以共享 Claude Max 订阅**，开发时很省事、成本也可能更低。

所以作者的意思不是“不能用”，而是：

- **短期开发体验不错**
- **长期可控性一般**
- **适合快速试验，不一定适合长期押注**

---

##### 4. 为什么应用层还是推荐 `Electron`
虽然很多人会吐槽 Electron 大，但作者仍然认为它是桌面 Agent 的首选，原因很现实：

- **稳定**
- **成熟**
- **资料多、踩坑经验多**
- **AI 也更容易理解和生成相关代码**

说白了就是：  
**它不一定最轻，但通常最省心。**

尤其在 AI 编程时代，“训练语料多”这点很重要，因为这意味着：

- 你让模型帮你写代码时，更容易写对；
- 遇到问题时，能搜到更多现成答案；
- 团队协作、招聘、维护也更容易。

---

##### 5. 为什么一开始建议先做 `CLI`
这是全文里最值得普通开发者记住的一点。

作者建议：

- **不要一开始就做界面**
- **先从命令行版本做起**

原因很简单：

- UI 很容易分散注意力；
- 你会把大量时间花在窗口、状态、交互、样式上；
- 结果 Agent 最核心的能力，反而没打磨好。

更好的路径是：

1. 先做 CLI；
2. 把 Prompt、Context、Tool、Memory、任务编排跑通；
3. 再决定要不要加 Electron / Web UI。

这是典型的 **先验证能力，再包装产品** 的思路。

---

##### 6. 推荐学习 `craft-agents-oss` 的意义
作者给出的开源项目 `craft-agents-oss`，价值在于它不是纯概念，而是一个相对完整的参考组合：

- `TypeScript`
- `pi-mono`
- `Electron`
- `React`
- `Claude Agent SDK`

这类项目最适合拿来学习：

- Agent 工程怎么分层；
- Tool 调用怎么设计；
- 前后端如何配合；
- 桌面应用如何落地。

评论区还有一个很有价值的补充：  
**真正要学的不是某个框架，而是 Agent 工程里的共性问题。**

比如：

- Prompt / Context 管理
- Agent / Sub-agent 协作
- 工具调用与结果处理
- Session / Hook / Skill 设计

这其实比“选哪个框架”更重要。

#### 我的意见

##### 结论先说
我基本认同这条判断，尤其认同两点：

- **TypeScript 做 Agent，优先选工程化强的方案**
- **一开始先做 CLI，不要急着做 UI**

##### 我怎么看这几个选择

###### `pi-mono`
如果你的目标是认真做 Agent 产品，而不是只接个模型接口，确实值得优先评估。  
前提是：团队愿意花一点时间理解它的设计方式。

###### `Vercel AI SDK`
更像“稳妥方案”。  
如果你更看重生态、文档、快速集成，它可能更容易推进。

###### `Claude Agent SDK`
适合原型期、个人项目、或者你本来就深度用 Claude。  
但如果你在做正式产品，我会谨慎一些，因为模型绑定会影响后续灵活性。

###### `Electron`
对多数桌面 Agent 产品来说，依然是**现实世界里的优选**。  
Tauri 更轻，但生态、资料、AI 辅助开发友好度，通常还是 Electron 更强。  
所以：

- **要稳定和效率：Electron**
- **要极致轻量：Tauri**

##### 给实际开工的人一个简单建议
如果你今天就要开始，我建议这样走：

1. **先用 TypeScript + CLI 起一个最小可用 Agent**
2. 先解决：
   - Prompt 管理
   - Tool 调用
   - 上下文拼接
   - 多轮任务执行
3. 跑通后，再决定：
   - 桌面端用 `Electron`
   - Web 端用 React / Next.js
4. 最后再考虑：
   - BYOK
   - 多模型切换
   - 多 Agent 协作
   - UI 体验

#### 最后一句

这段内容最有价值的，不是“告诉你选哪个框架”，而是提醒你：
