## 解读（1）

### 2026-07-02 11:16:11

#### 深度总结

作者原先认为：**在 Agent 中，CLI 可能会替代 MCP**。  
但实践后观点变得更谨慎：

- **标准化、成熟的 CLI**，如 `git`，对 Agent 很友好，效果稳定。
- **自定义封装的 CLI**，稳定性往往不如 MCP / 结构化工具。
- 核心原因：  
  **MCP 和结构化工具有更强的结构约束**，参数、返回值、权限边界更清晰，模型更不容易误用。
- 另外，MCP 在企业场景中有更标准的**鉴权、安全、权限管理方案**。
- 因此未来更可能是：  
  **CLI 与 MCP 并行，而不是谁完全取代谁。**

热门回复里也补充了几点：

- 有人认为：`tool > CLI ≈ MCP > skill`
- 有人强调：**skill + CLI 的 token 管理容易脏乱差**，安全隐患更大。
- 也有人指出：MCP 缺少类似 skill 的“渐进式披露”机制，即模型不应一次性看到所有工具细节，而应按需发现工具。

---

#### 深入浅出解读

可以把 Agent 调工具理解成“让 AI 操作外部世界”。

##### CLI 像命令行遥控器

例如：

```bash
git commit -m "fix bug"
```

优点是：

- 简单直接
- 生态成熟
- 人类开发者已经很熟悉
- 对 `git`、`docker`、`kubectl` 这类成熟工具尤其好用

但问题是：

- 参数格式可能复杂
- 输出不稳定，常是自然语言或文本
- 自定义 CLI 质量参差不齐
- 出错后 Agent 不一定知道怎么修正

所以，**成熟 CLI 很强，自制 CLI 容易翻车**。

---

##### MCP 像标准化接口

MCP 更像给 Agent 提供一套清晰的工具说明：

```json
{
  "tool": "create_issue",
  "params": {
    "title": "Bug report",
    "priority": "high"
  }
}
```

优点是：

- 参数结构清楚
- 返回结果可解析
- 权限和鉴权更规范
- 适合企业内部系统接入
- 更容易做审计、限权、治理

缺点是：

- 接入成本更高
- 不如 CLI 灵活
- 工具太多时，模型可能不知道该用哪个
- 需要设计工具发现和调用策略

所以，**MCP 更适合严肃、稳定、企业级场景**。

---

#### 核心判断

一句话概括：

> **CLI 适合成熟通用工具，MCP 适合结构化、可治理、企业级工具。**

更具体地说：

| 场景 | 更适合 |
|---|---|
| Git、Docker、Linux 命令 | CLI |
| 企业系统、数据库、权限敏感操作 | MCP |
| 快速原型、个人脚本 | CLI |
| 多人协作、审计、安全合规 | MCP |
| 高确定性工具调用 | MCP / 结构化 Tool |
| 灵活探索式任务 | CLI |

---

#### 辩证思考

##### 1. CLI 不会消失

CLI 是软件世界最基础、最普遍的接口之一。  
大量成熟工具天然就是 CLI-first。

让 Agent 学会用 CLI，本质上是让 AI 继承人类程序员已有的工具链。

所以说 **CLI 会被 MCP 完全替代**，不现实。

---

##### 2. MCP 也不是银弹

MCP 的优势是“规范”，但规范也带来成本。

如果只是一个简单脚本，硬封成 MCP，可能反而复杂化。  
而且 MCP 工具过多时，也会出现：

- 工具选择困难
- schema 暴露过多
- 调用成本上升
- prompt 设计复杂

所以 MCP 不是越多越好，而是要做**工具治理**。

---

##### 3. 真正关键不是 CLI vs MCP，而是“可控性”

Agent 调工具最怕三件事：

1. 调错工具  
2. 传错参数  
3. 权限失控  

CLI、MCP、tool、skill 都只是形式。  
最终比拼的是：

- 是否结构清晰
- 是否安全可控
- 是否便于审计
- 是否易于维护
- 是否能让模型稳定使用

---

#### 最精炼结论

> **成熟 CLI 仍然很强，自定义 CLI 容易不稳；MCP 胜在结构化、安全和企业治理。未来不是替代关系，而是分工并存。**

更准确地说：

> **个人和通用工具偏 CLI，企业和关键系统偏 MCP；Agent 工具生态的核心不是形式之争，而是稳定性、安全性和可治理性。**

## 结构化（1）

### 2026-07-23 10:13:51

#### 主旨概括

作者修正了“CLI 会取代 MCP”的激进判断：成熟、通用的 CLI 很适合 Agent，但自定义 CLI 在稳定性、结构化和企业鉴权方面往往不如 MCP。未来更可能是 **CLI、MCP 与原生 Tool 并行使用**，而非谁完全替代谁。

##### 1. 对 CLI 与 MCP 的重新判断

- 作者过去认为，Agent 可以直接调用 CLI，因此 CLI 可能替代 MCP。
- 实际使用后发现，两者各有适用场景，不能简单地互相替代。

##### 2. 通用 CLI 表现好，自定义 CLI 稳定性不足

- 对于 **Git 等成熟、常见的客户端**，CLI 接口稳定、文档完善，Agent 调用效果很好。
- 但自行封装的定制 CLI，稳定性通常不如 MCP 或结构化 Tool。
- 作者认为，核心原因在于 MCP/Tool 具有更强的结构约束，例如明确的参数、类型和返回格式，模型不容易误解或错误拼接命令。

##### 3. MCP 的企业级优势

- MCP 已有较标准的企业级鉴权方案，更适合涉及权限控制、身份认证和安全管理的业务。
- 因此，作者预计未来不会是 CLI 单方面取代 MCP，而是两者长期并行。

##### 4. 回复中的补充观点

###### 工具形态与维护成本

有回复认为，如果系统支持直接封装原生 Tool，应优先使用 Tool；其个人排序为：

> **Tool ＞ CLI ≈ MCP ＞ Skill**

同时指出，自定义 CLI 的长期维护也是一个问题。

###### Skill + CLI 的安全隐患

有回复反对笼统宣称“Skill + CLI 大于 MCP”，并以 ClawHub 上的部分 Skill 为例：

- 有些 Skill 会用不同方式把 Token 明文存放在机器各处。
- 这不仅可能带来安全风险，也容易造成凭据管理混乱。
- 相比之下，MCP 的标准化鉴权更适合企业环境。

###### MCP 缺少原生的“渐进式披露”

另一条回复指出，MCP 也存在不足：

- 与 Skill + CLI 相比，MCP 缺少原生的渐进式披露机制。
- 如果一次性向模型暴露大量工具及完整 Schema，可能增加上下文负担，也影响模型选工具的准确性。
- 一种改进方式是先提供 MCP 和工具的简要描述，不立即暴露详细 Schema；等模型选定工具后，再加载完整参数信息。
- Cubepi 采用了类似 Skill 的设计，使工具选择更有针对性、实际效果更好。

##### 总结

较合理的实践不是争论 MCP 与 CLI 谁将彻底胜出，而是按场景选择：

- **成熟通用软件**：优先使用 CLI；
- **需要稳定参数约束和企业鉴权的服务**：优先使用 MCP；
- **平台支持且便于维护时**：可直接封装为原生 Tool；
- **工具数量较多时**：应为 MCP 增加渐进式披露或工具搜索机制。
