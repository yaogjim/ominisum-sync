## 正文

[GitHub](https://github.com/web-arena-x/webarena-infinity) [环境中心](http://35.168.80.130/) [数据集](https://huggingface.co/datasets/webarena-x/webarena-infinity-trajectories)

Collage of browser-use agent trajectories across generated environments

浏览器使用的代理在不同应用领域中导航生成的环境。

带有可验证任务的真实网页环境对于训练和评估通用浏览器使用代理至关重要。然而，构建此类环境仍然过于耗费人力，需要在沙箱创建、数据整理、任务设计以及程序化验证器编写方面投入人工工作 。所需的专业知识（通常包括大量的编程工作）进一步限制了可扩展性，使得大规模环境构建在很大程度上仅限于资源充足的组织。

我们旨在自动化传统上由人工和专家驱动的流程。在这项工作中，我们提出一种方法，通过多智能体系统从记录的工作流和用户手册等静态工件中自动生成高真实性、高复杂性且强化学习就绪的环境，以及可验证任务。由此产生的流程省时且成本效益高：每个环境可在十小时内生成，成本低于100美元，且该流程高度可并行化。

我们方法的一个关键见解是，能够对源代码和执行产物（例如任务轨迹）进行特权访问的编码代理，可以推动有针对性且有效的改进。与其将环境视为黑箱，这些代理可以直接检查、调试和修改环境实现和任务逻辑。这种能力实现了一个迭代的、自我改进的流程，该流程执行生成、验证和优化的循环，以持续改进（1）环境的功能正确性和（2）可验证任务的正确性与难度（ 第 1 节 ）。

我们进一步介绍一种轻量级环境协议，该协议支持快速重置、轻松复制和可扩展部署，使生成的环境非常适合强化学习（RL）训练，同时不牺牲真实性（ 第 2.4 节 ）。

尽管我们的环境完全是自动生成的，却对当前的浏览器使用型智能体构成了重大挑战。强大的模型（使用浏览器功能的 Gemini-3-Flash）实现了 69.3%的平均成功率，而基于视觉的方法（如 Kimi-K2.5 和 Qwen-3.5-Plus）分别实现了 45.9%和 49.1%的成功率（ 第 4 节 ）。这些结果低于它们在已建立的、人工构建的基准测试集（如 WebArena 和 OSWorld）上的表现，这表明我们的方法在无需人工设计的情况下捕捉到了有意义的任务复杂性。消融实验进一步证实了关键组件的重要性（ 第 5 节 ）。

在本次初始发布中，我们提供了十个环境以及 1,260 个涵盖多个领域的可验证任务，这些领域包括职业、DevOps、金融、医疗健康、生产力和项目管理。我们还发布了 2,070 条从各种浏览器使用代理收集的成功轨迹，以支持训练和进一步研究。

#### 自我审计与自我挑战环境及可验证任务生成

Pipeline overview

Overview of our approach

我们的方法协调两种类型的代理：一个 *编码代理* ，它生成和修复 Web 环境、任务和验证器，以及一个 *浏览器使用代理* ，它通过前端 UI 以最终用户的方式执行任务。该流程分为五个阶段。（1） 编码代理基于静态工件（如记录的工作流和用户手册）生成 Web 应用程序。（2） 编码代理生成功能测试任务及程序化验证器； 浏览器使用代理执行这些任务， 编码代理对失败进行审计，并迭代最多 N 次以修复环境错误。（3） 编码代理生成具有验证器的真实、难度分级的任务，随后进行相同的评估-审计循环。（4） 编码代理分析浏览器使用代理的先前轨迹，在 R 轮中合成逐步更具挑战性的任务。（5）最终的回归评估运行完整的任务套件，以验证后续阶段引入的修改未降低功能正确性。我们将在下文详细描述每个组件。

##### Web Environment Generation

尽管编码代理能够生成任意网站，但无约束生成往往会产生缺乏结构真实性的环境，而这种真实性是近似真实世界部署条件所必需的。因此，我们基于来自真实应用的产物（具体来说是产品用户手册）来生成环境。用户手册为环境构建提供了坚实的基础：它们描述核心概念、记录任务工作流程，并常常指定 UI 布局和交互模式（例如，“点击右上角按钮以访问设置”）。

从八个应用中选取十个功能模块，每个对应产品能力的一个连贯子集（例如 GitLab 的规划与跟踪模块）。编码代理被提供了详细的生成提示以及相关的手册章节；完整的提示内容见附录。我们将特定实现选择（例如 UI 元素约束）的讨论推迟到下一节。

##### 功能正确性验证

尽管像 Claude Code 这样的编码代理在生成 Web 应用时可能会执行大量测试，但这些检查并不能保证功能正确性，尤其是前端交互。因此，我们引入了一个功能正确性验证阶段，在此阶段中，编码代理会生成任务及相应的验证器，以测试网站的基本功能。随后，一个浏览器使用代理会通过前端 UI 执行这些任务，以评估它们在实际中是否能够成功完成。这些任务经过刻意设计，简单且基础；一个有能力的浏览器使用代理应当能够可靠地完成它们。在我们的实验中，这组任务的平均通过率达到 90%以上。因此，我们将该阶段的表现作为网站功能正确性的指标。

**审计：** 在浏览器使用代理完成任务后，我们启动一个独立的编码代理作为审计代理，审查记录的轨迹，特别关注失败案例，并生成审计摘要。审计代理确定每个失败是归因于实现缺陷还是浏览器使用代理的局限性。然后，它相应地修复已确认的环境缺陷。一旦审计代理得出结论，剩余的失败案例最能通过浏览器代理错误而非实现问题来解释，审计过程即终止。

作为具体示例，GitLab 规划与跟踪环境中生成的功能任务之一是测试用户是否能够删除问题：

Task definition

```
{
  "id": "task_7",
  "instruction": "Delete the issue 'Markdown preview
    renders incorrectly with nested code blocks'.",
  "verify": "function-tasks/task_7.py"
}
```

Verifier

```
def verify(server_url: str) -> tuple[bool, str]:
    resp = requests.get(f"{server_url}/api/state")
    state = resp.json()
    issues = state.get("issues", [])
    target = next((i for i in issues
        if i["title"] == "Markdown preview renders "
           "incorrectly with nested code blocks"),
        None)
    if target is not None:
        return False, "Issue still exists."
    return True, "Issue has been deleted."
```

虽然后端逻辑支持此操作，浏览器使用代理未能尝试执行此任务，由于缺少 `delete` UI 元素。审计代理通过读取失败轨迹识别到这一问题并应用了修复:

```
html += '<button class="btn btn-outline" data-action="edit-issue" ...>Edit</button>';
  html += '<button class="btn ..." data-action="toggle-issue-status" ...>Close issue</button>';
+ html += '<button class="btn btn-danger" data-action="delete-issue" ...>Delete</button>';
```

##### 可验证的真实任务生成与加固

真实任务生成和审核的流程与前一阶段非常相似，尽管它使用了针对真实任务构建的不同提示。特别是，我们引入了难度级别的明确定义，并提供了适当和不适当的真实任务示例。

#### Design Choices

在本节中，我们重点介绍了几个关键的设计选择，这些选择提升了生成质量，并使环境更适合大规模的强化学习训练。

我们刻意设计环境以兼容主要依赖基于文本的观察的浏览器代理（例如增强的可访问性树）。这一选择的动机是观察到，语言模型在处理文本表示时更鲁棒且泛化能力更强。为支持这一点，我们鼓励使用可访问性最佳实践和能在 DOM（例如弹出窗口、下拉菜单）中完全表示的浏览器原生 UI 元素。这确保关键界面元素和交互能一致地呈现给代理。此外，在使用浏览器代理时禁用视觉输入，以提高效率和执行速度，使代理完全基于文本。

##### 增强验证器可靠性

验证器正确性是强化学习训练的关键要求。为确保可靠性，我们引入了两层防护措施：(1) 程序化健全性检查：我们首先运行一个具有特权后端访问权限的程序，以直接操纵应用状态，然后调用用于代理评估的相同验证器。由于此执行路径从构造上就应正确，任何失败都可能表明验证器本身存在问题。该流程被整合到环境生成流程中，使编码代理能够自动检测并修复验证器的不一致问题。(2) 自动审计：如前所述，我们进一步采用审计代理分析失败的任务轨迹，确定失败是源于环境漏洞还是代理局限性。这为任务设计和验证器正确性提供了额外的验证层。

##### Standalone Verifiers

在完全访问应用状态和功能的情况下，我们通过一个公开的 API 设计了完全独立的验证器。这清晰地将验证与任务执行分离。与之前的工作（如 WebArena）不同，后者依赖于基于浏览器的渲染页面检查，我们的方法避免了对昂贵的浏览器端验证的需求，实现了更高效和可靠的评估。

##### The Environment Protocol

我们设计的环境轻量级、易于复制且高效重置，同时不牺牲真实性。每个环境都是一个独立的静态 HTML/CSS/JS 文件目录，由轻量级 Python HTTP 服务器提供服务，不依赖数据库或外部依赖。

关键设计决策是浏览器拥有所有应用状态。每次用户交互时，浏览器会序列化其完整状态并推送到服务器，服务器仅将最新副本存储在内存中。这使得服务器成为一个被动的状态镜像，验证者可以在不接触用户界面（UI）的情况下进行查询——将任务验证与任务执行清晰分离。服务器还会将首次状态推送捕获为不可变的 *种子快照* ，重置所需的全部操作就是：在内存中恢复该快照，并通过服务器发送事件（Server-Sent Events）通知浏览器重新加载。无需数据库回滚、容器重启或文件系统清理。

本合约通过极简 API 实现：

```
PUT  /api/state   → browser pushes state on every mutation
GET  /api/state   → verifiers read current state (JSON)
POST /api/reset   → restore seed snapshot, notify browser via SSE
GET  /api/events  → SSE stream the browser listens to for resets
```

因为整个环境由其源目录和几百行的服务器代码定义，复制简化为复制文件，而运行多个实例只需在不同端口上启动独立进程。这使得在单台机器上扩展到许多并行的强化学习（RL）并行轮次变得简单。

#### 浏览器使用型代理的性能

Real-task success rate by app and model

三个浏览器使用代理的总体和细分成功率（%）

**浏览器使用代理** 我们使用 Browser Use 测试框架评估一个基于文本的浏览器使用代理，底层模型为 `gemini-3-flash-preview` 。Browser Use 测试框架支持基于 ID 的交互以及编写和执行 JavaScript 的能力，为复杂操作提供了额外的灵活性。我们还评估了两个基于视觉的代理，分别是 `kimi-k2.5` 和 `qwen-3.5-plus` 。对于这些代理，我们实施了错误处理策略（例如重试机制），以减轻因交互框架相对不够完善而带来的限制。

在涵盖十个环境的 1260 个真实任务中，支持浏览器使用的 Gemini-3-Flash 取得了 69.3%（873/1260）的成绩，紧随其后的是 Qwen-3.5-Plus（49.1%，619/1260）和 Kimi-K2.5（45.9%，578/1260）。不同环境中的性能差异很大，PayPal My Wallet 对所有代理而言是最容易操作的环境。尽管 Kimi-K2.5 总体表现不如 Qwen-3.5-Plus，但在与 Gmail 相关的应用中，它以显著优势超越了 Qwen-3.5-Plus。

此处观察到的成功率明显低于成熟基准测试报告的成功率。例如，Kimi-K2.5 在 WebArena 上达到 58.9%，在 OSWorld-verified 上达到 63.3%，而在我们的环境中仅为 45.9%。同样，Qwen-3.5-Plus 在 OSWorld-verified 上得分为 62.2%，而在我们的环境中仅为 49.1%。这些结果表明，我们完全自动化的环境生成能够产生具有显著挑战性的任务，同时仍有很大的改进空间，凸显了我们方法在更大规模下的潜力。

#### Ablation Studies

在本节中，我们进行消融实验以验证我们方法中不同组件的必要性和影响。

功能复杂度。我们使用 Claude 从每个生成的应用程序的源代码中提取独特的面向用户的功能，并统计实现的独特功能操作的数量。

- **更多能力已实现。** 手动条件化环境在五个领域中的四个领域产生了更多独特的功能性操作，其中 Xero 发票领域的差距最大（96 vs. 64）。唯一的例外是 GitLab 计划与跟踪，我们将其归因于其文档结构：单一菜单式 Markdown（带有超链接）而非自包含文件夹。

这些结果表明，虽然编码代理能够根据最小规范生成合理的环境，但更全面的工件能够提高生成环境的功能复杂性、任务多样性和特征真实性。

## 结构化（1）

### 2026-03-24 06:19:50

#### 文章主旨

这篇文章介绍了 **WebArena-Infinity**：一种用多智能体系统自动生成“可验证浏览器环境 + 可验证任务”的方法，目标是大规模、低成本地为浏览器使用型智能体提供训练和评测场景。  
核心贡献在于：它把原本高度依赖人工和编程专家的流程自动化了，而且生成出的环境不仅真实、复杂，还适合强化学习训练。

---

#### 1. 研究背景：为什么需要这项工作

- 训练和评估通用浏览器智能体，必须依赖 **真实网页环境** 和 **可验证任务**。
- 传统构建方式非常耗人力，需要人工完成：
  - 搭建沙箱环境
  - 整理数据
  - 设计任务
  - 编写验证器
- 这类工作通常还要求较强编程能力，因此很难扩展到大规模，基本只有资源充足的团队能做。

**作者的目标**：把这些传统上依赖人工和专家的步骤自动化。

---

#### 2. 方法总览：用两类智能体协同生成环境与任务

作者设计了一个多智能体流程，主要由两类代理组成：

- **编码代理（Coding Agent）**：负责生成和修复网页环境、任务和验证器
- **浏览器使用代理（Browser Agent）**：像真实用户一样通过前端 UI 执行任务

整个流程分为 5 个阶段：

##### 2.1 生成网页环境

- 编码代理根据 **静态工件** 生成网站，例如：
  - 录制的工作流
  - 用户手册
- 这样做比“无约束生成”更真实，因为手册里通常包含：
  - 核心功能描述
  - 操作流程
  - UI 布局和交互方式

**例子：**
- 从 8 个真实应用里选出 10 个功能模块
- 例如：GitLab 的“规划与跟踪”模块

##### 2.2 生成功能测试任务并验证环境是否可用

- 编码代理先生成一批 **基础功能任务** 和对应验证器
- 浏览器代理去执行这些任务
- 如果失败，再由另一个编码代理进行审计和修复

这些功能任务都设计得比较基础，因为一个正常可用的网站应当能稳定完成它们。  
文章中提到，这类任务的平均通过率通常应在 **90% 以上**，因此可以作为网站功能正确性的指标。

##### 2.3 生成真实任务并继续审核

- 在功能正确之后，再生成更贴近真实使用场景的任务
- 这些任务带有：
  - 明确的难度分级
  - 对应验证器
- 然后再次进行“执行—审计—修复”的循环

##### 2.4 自我挑战：让任务越来越难

- 仅靠初始提示，编码代理容易生成偏简单的任务
- 因此作者加入了 **强化/自我挑战步骤**
- 模型会回看之前智能体的执行日志和失败轨迹，判断当前能力边界，然后继续生成更难的新任务

##### 2.5 最后做回归测试

- 完整任务集会再次运行
- 目的是确认后续修改没有破坏之前已经可用的功能

---

#### 3. 关键思路：不是黑箱，而是“可读源码、可改实现”的代理

文章强调的一个重要见解是：

- 如果编码代理能访问 **源代码** 和 **执行轨迹**
- 它就不必把环境当作黑箱
- 而是可以直接：
  - 检查实现
  - 调试错误
  - 修改任务逻辑
  - 修复验证器

这使整个流程形成一个 **持续自我改进的闭环**：

- 生成
- 验证
- 审计
- 修复
- 再验证

作者认为，这种“特权访问”是高效提升环境质量和任务可靠性的关键。

---

#### 4. 一个具体例子：GitLab 环境中自动发现并修复缺失的删除按钮

在 GitLab 的“规划与跟踪”环境中，有一个功能测试任务是：

> 删除标题为 “Markdown preview renders incorrectly with nested code blocks” 的 issue

对应验证器会直接读取后端状态，检查这个 issue 是否还存在。  
逻辑很简单：

- 如果 issue 还在，任务失败
- 如果 issue 消失，任务成功

但浏览器代理执行失败了。原因不是后端不支持删除，而是：

- **前端 UI 根本没有 delete 按钮**

审计代理通过阅读失败轨迹，定位到了问题，然后自动补上了：

```html
+ html += '<button class="btn btn-danger" data-action="delete-issue" ...>Delete</button>';
```

这个例子说明：  
系统不仅能发现“任务没做成”，还能继续判断是 **代理能力问题**，还是 **环境实现缺陷**，并自动修复。

#### 5. 真实任务如何变难：不是乱加步骤，而是更接近真实约束

作者特别强调，任务变难不是靠“硬凑很多无关步骤”，而是通过真实环境中的隐含条件、前提约束和领域知识自然增加复杂性。

##### 5.1 求职平台任务升级

- 简单任务：保存微软的软件工程师实习岗位
- 更难任务：给 Jessica Park 关于 Meta 回归 offer 的帖子评论
- 强化后任务：回复所有由雇主举办的即将到来的活动 RSVP，并保存这些尚未保存雇主的所有活跃职位

##### 5.2 医疗处方场景升级

- 简单任务：批准一个待处理的 Gabapentin 续方请求
- 更难任务：批准续方，并把 sig 改成“口服 1 粒，每日两次”
- 强化后任务：删除已排除的青霉素过敏记录，停用当前阿莫西林 500mg，再开具新的阿莫西林克拉维酸钾 875mg/125mg，每日两次、10 天疗程，并配送到 CVS #4521

- 更难任务：把所有“溶解”过渡替换成“左推”

这些例子说明：任务难度是沿着真实业务逻辑自然增长的。

#### 6. 环境设计：为什么它适合强化学习

作者提出了一套轻量级环境协议，使环境同时满足：

- 快速重置
- 易于复制
- 易于并行部署
- 保持较高真实性

##### 6.1 环境本身很轻量

每个环境都是：

- 一组独立的静态 `HTML/CSS/JS` 文件
- 外加一个轻量级 Python HTTP 服务
- **不依赖数据库**
- **不依赖外部服务**

##### 6.2 状态由浏览器持有

这是最关键的设计之一：

- 浏览器负责保存完整应用状态
- 每次用户交互后，浏览器把状态序列化后推送给服务器
- 服务器只在内存中保存最新状态副本

这样做的好处：

- 验证器直接查状态，不必通过 UI
- 任务执行和任务验证被清晰分离

##### 6.3 重置非常快

服务器会记录第一次状态推送作为 **种子快照**

重置时只需要：

- 恢复这份内存快照
- 用 SSE 通知浏览器重新加载

因此不需要：

- 回滚数据库
- 重启容器
- 清理文件系统

##### 6.4 极简 API

环境协议只需要几个接口：

- `PUT /api/state`：浏览器每次状态变化时上传状态
- `GET /api/state`：验证器读取当前状态
- `POST /api/reset`：恢复种子快照并通知前端
- `GET /api/events`：浏览器监听 SSE 重置信号

这让环境很适合在一台机器上开多个实例，支持并行 RL 训练。

#### 7. 为什么作者偏向“文本友好型”网页设计

作者刻意让环境更适配 **基于文本观察的浏览器代理**，而不是依赖视觉输入。

主要原因：

- 大语言模型对文本表示通常更稳健、泛化更强
- 可访问性树、DOM 等文本结构更容易被代理理解和操作
- 执行效率更高

因此生成环境时会鼓励：

- 遵循可访问性最佳实践
- 尽量使用浏览器原生 UI 元素
- 让弹窗、下拉菜单等都能完整体现在 DOM 中

而在实验中，浏览器代理甚至直接 **关闭视觉输入**，完全基于文本执行任务。

---

#### 8. 验证器为什么更可靠

可验证任务的关键是：**验证器必须靠谱**。  
否则强化学习会拿到错误奖励信号。

作者为此做了两层保障：

##### 8.1 程序化健全性检查

- 先用一个拥有后端特权访问权限的程序，直接修改应用状态
- 再调用与真实评测相同的验证器
- 如果按理应该成功却失败了，就说明验证器本身可能有问题

##### 8.2 自动审计

- 审计代理分析失败轨迹
- 判断失败原因是：
  - 环境 bug
  - 验证器 bug
  - 不可完成任务
  - 还是浏览器代理自身的能力限制

此外，作者设计的是 **独立验证器（Standalone Verifiers）**：

- 通过公开 API 读取状态
- 不依赖浏览器渲染结果来做验证

这和 WebArena 那种依赖浏览器端页面检查的方式不同，优点是：

- 更快
- 更稳
- 更便宜

#### 12. 浏览器代理表现：生成环境确实很有挑战

#### 13. 消融实验：哪些设计真的有用

##### 13.1 用完整文档生成环境，比只用简短描述更好

作者比较了两种方式：

- 使用完整产品文档生成
- 仅使用简短高层描述生成

在 5 个应用上的结果表明，使用完整文档通常会带来三个方面的提升：

###### （1）功能复杂度更高

- 文档条件化生成的环境，在 5 个领域中的 **4 个** 里实现了更多独特功能操作
- 差距最大的例子是 **Xero Invoicing**
  - 完整文档：**96**
  - 简短描述：**64**

###### （2）任务更多样

- 用任务嵌入的平均 5-NN 余弦距离衡量任务分散程度
- 完整文档版本的任务分布更广
- 提升最明显的例子：
  - Figma Slides：**0.28 vs. 0.24**
  - Xero Invoicing：**0.26 vs. 0.22**

###### （3）更贴近真实产品

- 在 5 个领域中的 **4 个** 里，完整文档版本在“特征真实性”的精确率和召回率上更高
- 说明产品手册能减少“功能幻觉”，并提高真实能力覆盖度

**结论**：  
编码代理即使只拿到简单说明，也能生成“像样”的环境；但如果提供更丰富工件，环境在复杂性、多样性和真实性上都会更好。

##### 13.2 审计确实提升了功能和验证可靠性

- **45%**：环境或任务端错误
  - 应用 bug
  - 验证器 bug
  - 不可能完成的任务

## 解读（1）

#### 一句话总结

**WebArena-Infinity** 提出了一套“几乎全自动”的方法：用多智能体系统从用户手册、工作流等资料中，批量生成可供浏览器智能体训练和评测的网页环境、任务以及自动判分器，而且生成出的任务还挺难，能较真实地检验智能体水平。

#### 内容总结

- 这篇工作要解决的问题是：**高质量、可验证的浏览器任务环境太难靠人工大规模搭建**。
- 作者的方法是让两类智能体协作：
  - **编码代理**：生成网页环境、任务、验证器，并修 bug；
  - **浏览器代理**：像真实用户一样在前端完成任务。
- 整个流程不是一次生成完，而是反复循环：**生成 → 测试 → 审计 → 修复 → 再增强难度**。
- 他们做出的成果包括：
  - **10 个自动生成的网页环境**
  - **1260 个可验证任务**
  - **2070 条成功轨迹**
- 成本和效率也很亮眼：
  - **每个环境约 10 小时内生成**
  - **成本低于 100 美元**
  - 而且流程**易并行扩展**
- 实验显示，这些自动生成的任务对现有浏览器智能体依然很有挑战：
  - Gemini-3-Flash：**69.3%**
  - Qwen-3.5-Plus：**49.1%**
  - Kimi-K2.5：**45.9%**
- 一个重要结论是：**自动生成并不等于低质量**，反而能形成有难度、可验证、适合强化学习训练的数据与环境。

#### 深入浅出地解读

##### 1. 这项工作的核心价值是什么？

可以把它理解成：作者想造一个“**浏览器版自动出题工厂**”。

以前做这类评测环境，像出一套高质量考试题：
- 要有人设计网站；
- 要有人准备数据；
- 要有人出题；
- 还要有人写标准答案和判分规则。

这非常费人力，所以规模做不大。

而 WebArena-Infinity 的目标是把这件事尽量自动化，让 AI 自己：
- 搭网站
- 造任务
- 写判题器
- 自查并修复问题

这样就能更快、更便宜地大量生产训练环境。

---

##### 2. 为什么“可验证任务”特别重要？

因为训练智能体，尤其是强化学习，最怕一件事：**不知道任务到底算没算完成**。

比如让智能体“删除一个 issue”，如果没有程序化验证器，就得人工去看结果，效率低且不稳定。

这篇工作强调：
- 每个任务都尽量配一个**自动验证器**
- 验证器直接查系统状态，不靠人工判断

这意味着：
- 评测更稳定
- 可大规模跑实验
- 更适合强化学习反复训练

简单说，**不是只出题，更是顺便把“自动阅卷系统”也建好了。**

---

##### 3. 它为什么比“随便让 AI 生成网站”更靠谱？

因为作者没有让模型凭空乱造，而是给它喂了**真实产品的用户手册、工作流说明**。

这很关键。原因是如果完全自由生成，AI 很容易做出：
- 看起来像网站
- 但功能结构不真实
- 任务也像“拼凑题”

而基于真实文档生成，会让环境更像真实软件，任务也更贴近真实操作场景。

论文中的消融实验也支持这一点：  
**有真实文档作依据时，环境的功能更丰富、任务更多样、与真实产品更一致。**

---

##### 4. 它最巧妙的地方在哪？

我认为有两个亮点。

###### 亮点一：不是黑箱，而是“能看源码、能修代码”

作者让编码代理拥有特权访问，可以直接看：
- 源代码
- 任务轨迹
- 应用状态
- 验证器逻辑

这就像让一个会编程的考官，不只是发现学生答错，还能顺手修题目和修考场。

例如文中提到：
- 后端本来支持删除 issue
- 但前端 UI 没有“删除按钮”
- 浏览器代理做不成任务
- 审计代理看轨迹后发现是环境缺陷，于是补上按钮

这说明它不只是“生成”，而是在做**自动化开发 + 自动化测试 + 自动化修复**。

###### 亮点二：会“自我挑战”，自动把题变难

模型初始生成的任务常常偏简单，所以作者加入了一个“强化/加难”步骤：
- 看浏览器代理之前做题的轨迹
- 找出它擅长和不擅长的边界
- 再生成更难的新任务

这有点像一个很会出题的老师：
- 先出基础题
- 再根据学生错题，定向升级难度

因此生成出的难题不是乱堆操作，而是更接近真实世界里那种：
- 有前提条件
- 需要条件判断
- 需要跨页面、多步骤推理

---

##### 5. 为什么它适合强化学习？

作者设计了一个很轻量的环境协议，重点是：

- 前端浏览器保存完整状态
- 每次改动都把状态同步给服务器
- 验证器直接读服务器状态
- 重置时直接恢复初始快照

这样做的好处是：
- **重置极快**
- **部署简单**
- **复制方便**
- **适合并行跑很多训练实例**

换句话说，它不像传统复杂网站那样要处理数据库回滚、容器重启、清缓存等麻烦事。  
这对强化学习特别重要，因为 RL 会反复大量试错，环境如果不能快速 reset，就很难扩展。

---

##### 6. 实验结果说明了什么？

结果最值得注意的不是“模型分数高低”，而是：

###### 现有强模型也没法轻松通关
这说明生成的任务不是水题，而是真有挑战。

###### 自动生成环境比预想中更接近真实世界
因为这些模型在一些成熟基准上分数更高，但在这里更低，说明 WebArena-Infinity 的任务复杂度和真实性是有分量的。

###### 审计机制确实有效
论文显示审计后，很多环境的功能测试通过率明显上升。  
这说明“自动生成 + 自动审计修复”这条路线是跑得通的。

---

##### 7. 它有没有局限？

有，而且作者也间接展示出来了。

- 不是所有环境都稳定，有些会出现**功能回归**
- 自动化流程并不意味着**完全无 bug**
- 成果质量仍和：
  - 源文档质量
  - 编码代理能力
  - 浏览器代理能力
  有很强关系
- 目前环境是轻量静态网页方案，虽然利于扩展，但和真正复杂的线上系统相比，仍有差距

所以它更像是：  
**在“真实性、可控性、可扩展性”之间做了一个很聪明的工程平衡。**

#### 我的意见

- 我认为这项工作**很有价值**，尤其价值不只是“又做了一个 benchmark”，而是提出了一个**自动构建 benchmark 的方法论**。
- 它最厉害的地方在于把环境生成、任务设计、验证、修复、加难串成了闭环，这比单纯造数据更有长期意义。
- 如果这条路线继续成熟，未来浏览器智能体领域可能会从“手工造少量题”走向“自动持续产出大量训练场景”。
- 但我也认为，不应把它理解为“已经替代真实世界网页环境”。更准确地说，它是一个**高性价比、可扩展、足够真实的中间层训练场**。
- 总体判断：**这是一篇工程价值和研究价值都很强的工作，尤其适合推动浏览器智能体的评测标准化与强化学习训练规模化。**

#### 结论

**WebArena-Infinity 的意义，在于把“人工搭建浏览器任务环境”变成了一条可自动化、可迭代、可扩展的流水线。**  
它未必完美真实，但已经证明：**只靠自动化方法，也能生成有难度、可验证、能用于训练和评测的浏览器环境。** 这对智能体研究是非常重要的一步。
