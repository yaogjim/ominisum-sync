- 代理框架包括工具调度、上下文管理、规划循环、子代理编排、评估、沙箱化和可观测性等组件。

- 将Agent错误案例沉淀为框架层规则或工具边界约束，而不是只依赖更换模型。

#### 为什么所有人突然都在构建自己的代理框架，以及你为什么应该在意

##### 核心结论

AI 产品的竞争重点正在从“谁用更强的模型”，转向“谁能更好地驾驭模型”。

文章的关键观点是：**模型正在商品化，真正形成差异化的是围绕模型构建的代理框架 / Harness。**

---

##### 关键案例：LangChain 的性能跃升

LangChain 团队将其开源编码代理 **deepagents-cli** 在 Terminal-Bench 2.0 上的排名从 30 名开外提升到前五。

- 分数从 **52.8% 提升到 66.5%**
- 提升 **13.7 分**
- 底层模型没有变，仍然是 **GPT-5.2-Codex**
- 唯一变化是：**更换了代理框架**

这说明：**同一个模型，在不同框架下，产品能力可能出现巨大差异。**

---

##### 什么是代理框架？

代理框架不是模型本身，而是模型外部的一整套工程系统，用来把 LLM 从“会生成文本的工具”变成“能完成任务的代理”。

它通常包括：

- 工具调用与调度
- 上下文管理
- 沙箱执行
- 规划与循环机制
- 子代理协作
- 评估与监控
- 任务完成判断
- 错误修复与防复发机制

换句话说，**模型负责推理，框架负责让推理真正可靠地落地。**

---

##### 为什么框架越来越重要？

文章提到 Claude Code 泄露的源码大约有 **51.3 万行 TypeScript**，但真正调用模型 API 的代码只有几行。

这说明，一个成熟 AI 产品的大部分复杂度并不在模型调用，而在：

- 如何组织任务
- 如何管理上下文
- 如何控制工具边界
- 如何避免重复犯错
- 如何判断结果是否正确
- 如何让系统稳定可控

---

##### Harness 的本质

Mitchell Hashimoto 对 Harness 的定义很直接：

> 每当代理犯错时，你设计一个解决方案，让它以后不再犯同样的错。

这些修复不是写进模型里，而是写进模型外部的系统中。

所以 Harness 可以理解为：**围绕 AI 代理不断沉淀下来的工程防护层、执行层和改进层。**

---

##### 竞争逻辑的变化

2025 年，很多团队都在抢着做“智能体”。

但到 2026 年，真正领先的团队，不只是调用更强模型，而是投入大量资源建设：

- 更好的任务编排
- 更可靠的工具链
- 更强的上下文系统
- 更完善的评估机制
- 更可控的人机协作流程

文章的核心判断是：

> 模型给你智能，框架给你产品。

---

##### 对产品经理的启发

对于 AI 产品而言，未来的壁垒不只是模型选择，而是产品系统能力。

需要重点思考：

- 你的代理如何知道任务完成了？
- 它犯错后，系统如何避免下次再犯？
- 它如何安全调用工具？
- 它如何管理长任务和复杂上下文？
- 它如何和人类协作？
- 它的行为是否可评估、可观测、可迭代？

真正有价值的 AI 产品，不是简单包装模型，而是构建一套持续优化的代理操作系统。

---

##### 一句话总结

**AI 模型会越来越像基础设施，而代理框架将成为 AI 产品真正的护城河。**

**精炼理由：**  
文章最有价值的地方，不是“大家都在做 Agent”这个表层判断，而是指出了一个更底层的转移：**模型能力趋同后，决定产品效果的变量变成了工具调用、上下文管理、验证机制、错误修复闭环和业务脚手架。**

---

##### 2. 最重要的洞见

###### 洞见 1：模型不再是产品，模型只是产品里的一个工具

###### **核心观点：**  
> AI 产品的核心竞争力，不是调用了哪个大模型，而是围绕模型构建了什么样的执行系统。

**为什么重要：**  
过去很多 AI 产品的隐含逻辑是：  
“我接入更强的模型，就能做出更强的产品。”

但文章用 LangChain 的例子说明：**底层模型不变，仅更换框架，Terminal-Bench 2.0 分数从 52.8% 提升到 66.5%。**  
这意味着性能提升并不一定来自模型本身，而可能来自模型外围的系统设计。

这对 AI 团队的路线图有直接影响：  
如果团队仍然把主要精力放在“等下一个更强模型”上，就可能错过真正可控、可积累、可差异化的部分。

**反常识之处：**  
常见认知是：  
> AI 能力主要由模型决定。

文章的判断是：  
> 在应用层，模型只是原材料；真正决定结果的是框架、流程和验证系统。

**可迁移价值：**  
这类似很多技术行业的演化：

- 云计算时代，底层算力重要，但真正有壁垒的是架构、运维、数据和业务流程。
- 电商时代，支付、物流、推荐、供应链比“网页”本身更重要。
- 移动互联网时代，手机硬件趋同后，体验差异来自系统、生态和应用设计。

迁移到 AI 产品中就是：  
**不要把模型当作完整产品，要把模型当作发动机；真正的产品是整辆车。**

**我应该记住什么：**  
> 模型给你智能，框架决定智能能不能稳定、可控、可交付地变成结果。

---

###### 洞见 2：Agent 的真正壁垒，是“错误修复机制”的积累

###### **核心观点：**  
> 每当 Agent 犯错，你设计一个机制让它以后不再犯同类错误；这些机制不断沉淀，就形成了 Harness，也就是代理框架的核心资产。

文章引用 Mitchell Hashimoto 的定义非常关键：  
> 每当代理犯错时，你设计一个解决方案，使其再也不会犯这个错误。这个修复存在于 harness 中。

这句话轻描淡写，但其实非常重要。

它把 Agent 框架从“工具集合”重新定义为一种**错误吸收系统**：

- 模型会幻觉？
  - 加验证逻辑。
- 模型会错误调用工具？
  - 加工具边界和权限约束。
- 模型会丢上下文？
  - 加上下文管理。
- 模型会陷入循环？
  - 加规划循环和停止条件。
- 模型不知道任务是否完成？
  - 加评估器和完成判定。

**为什么重要：**  
AI Agent 的产品化难点，不是“能不能跑一次”，而是“能不能长期稳定地跑很多次”。  
而稳定性不是凭空来的，是靠一次次失败后的系统修补积累出来的。

**反常识之处：**  
很多人以为 Agent 框架是预先设计出来的架构。  
但文章暗示：真正有价值的框架往往是**从错误中长出来的**。

也就是说：

> 好的 Agent 框架不是设计文档的产物，而是生产事故、边界案例和失败模式的沉淀。

**可迁移价值：**  
这可以迁移到产品、组织和个人决策：

- 好的组织制度，往往是对历史错误的制度化修复。
- 好的产品流程，往往是对用户反复踩坑行为的结构性响应。
- 好的个人工作系统，往往是对自己反复犯错模式的防呆设计。

**我应该记住什么：**  
> 不要只记录 Agent 做对了什么；更要系统化记录它为什么失败，并把每类失败变成框架能力。

---

###### 洞见 3：信任 LLM 的推理，但不信任它的边界行为

###### **核心观点：**  
> 成功框架的共同模式是：在推理层信任 LLM，在工具边界严格执行。

这是全文最值得保存的一句话之一。

它给出了一个非常实用的 Agent 设计原则：  
LLM 擅长推理、规划、解释、生成方案；  
但一旦涉及执行、权限、状态修改、外部工具调用，就必须靠系统规则兜底。

换句话说：

- 可以让模型“想”；
- 不能完全让模型“随便做”。

**为什么重要：**  
Agent 最大的风险不在“说错话”，而在“做错事”。  
当模型开始调用工具、写代码、改数据库、发邮件、下订单、操作文件系统时，错误的代价会急剧上升。

所以框架的核心任务不是压制模型，而是划清边界：

- 哪些工具可用？
- 哪些参数合法？
- 哪些动作需要确认？
- 哪些结果必须验证？
- 哪些执行环境必须沙箱化？
- 什么时候应该停止？
- 出错后如何回滚？

**反常识之处：**  
很多人会走向两个极端：

1. 完全信任模型，让它自主完成一切；
2. 完全不信任模型，把它限制成简单问答工具。

文章提供了第三条路：

> 推理上放权，执行上设闸。

**可迁移价值：**  
这不仅适用于 Agent，也适用于管理和组织设计：

- 对专家：信任判断，但设置审批和审计机制。
- 对团队：授权目标，但约束预算、权限和风险边界。
- 对自动化系统：允许自主决策，但关键动作必须可观测、可验证、可回滚。

**我应该记住什么：**  
> 让 AI 负责思考，让系统负责边界。

---

###### 洞见 4：通用集成框架解决“接入问题”，自定义 Harness 解决“业务表现问题”

###### **核心观点：**  
> LangChain、CrewAI 等框架解决的是通用集成问题；真正的 Harness 解决的是具体业务场景下的可靠性、控制权和效果问题。

评论区里有人提出疑问：  
如果每个人都构建自己的代理框架，那会不会重新造成集成碎片化？

作者的回答大意是：  
LangChain 解决的是单一集成问题，而 Harness 可以处理更多具体用例。

这背后有一个重要区分：

| 类型 | 解决的问题 | 价值 |
|---|---|---|
| 通用 Agent 框架 | 接入模型、工具、流程编排 | 降低开发门槛 |
| 自定义 Harness | 针对业务失败模式做约束、验证、控制和优化 | 形成产品差异化 |

**为什么重要：**  
通用框架可以帮你快速开始，但不一定能帮你赢。  
因为每个业务的关键失败模式不同：

- 编码 Agent 关注测试、文件系统、依赖、命令执行、回滚。
- 客服 Agent 关注用户意图、合规、情绪、升级机制。
- 金融 Agent 关注风险、审计、权限、证据链。
- 医疗 Agent 关注责任边界、准确性、法规和人工确认。

这些差异无法完全由通用框架解决。

**反常识之处：**  
常见想法是：  
> 未来应该出现一个统一 Agent 框架，大家都用它。

文章暗示的判断是：  
> 底层工具会趋于通用，但上层 Harness 会越来越垂直、越来越定制。

**可迁移价值：**  
这类似 SaaS 和企业软件中的老规律：

- 通用平台解决 60%；
- 行业 Know-how 解决最后 40%；
- 而最后 40% 往往决定客户是否愿意付费。

**我应该记住什么：**  
> 通用框架帮你把 Agent 跑起来，自定义 Harness 决定它能不能在真实业务中活下来。

---

##### 3. 底层逻辑

###### **逻辑一：当模型能力趋同，差异化自然转移到模型外围系统**

- **表层现象：**  
  LangChain 的 deepagents-cli 在底层模型不变的情况下，仅通过框架变化，就在 Terminal-Bench 2.0 上显著提升排名和分数。

- **深层原因：**  
  LLM 本身提供的是概率性智能，但真实任务需要稳定的执行链路。  
  任务完成质量取决于一整套外围能力：上下文管理、工具调用、验证机制、错误恢复、状态控制、沙箱、安全边界、观测系统。

- **推导结论：**  
  AI 产品竞争不再只是模型竞争，而是**系统工程竞争**。  
  谁能把模型能力封装进更可靠的执行系统，谁就能获得更强产品表现。

---

###### **逻辑二：Agent 的可靠性不是来自“更聪明”，而是来自“更少重复犯错”**

- **表层现象：**  
  代理框架被定义为：每当 Agent 犯错，就设计一个机制让它以后不再犯同类错误。

- **深层原因：**  
  LLM 的失败具有模式性。  
  它不是随机地胡乱失败，而是会在特定边界、上下文长度、工具调用、任务拆解、完成判断等环节反复失败。

- **推导结论：**  
  优秀 Agent 框架的积累方式，应该是围绕失败模式建立修复闭环。  
  也就是：  
  **发现失败 → 分类失败 → 加入约束 / 验证 / 工具边界 → 复测 → 固化为框架能力。**

---

###### **逻辑三：Agent 产品化的关键，是把“思考”和“执行”分层治理**

- **表层现象：**  
  成功框架的共同模式是：在推理层信任 LLM，在工具边界严格执行。

- **深层原因：**  
  LLM 擅长处理模糊问题，但不天然具备可靠执行能力。  
  推理阶段容错率较高，执行阶段错误成本极高。  
  因此同一个系统里必须同时存在“灵活性”和“刚性”。

- **推导结论：**  
  一个好的 Agent 架构应该是：

  - 推理层：允许模型探索、规划、生成方案；
  - 工具层：限制权限、校验参数、控制副作用；
  - 验证层：判断结果是否满足目标；
  - 观测层：记录过程，便于调试和改进；
  - 人机协同层：高风险动作引入人工确认。

## 结构化（1）

### 2026-05-04 08:13:55

##### 主旨概括

文章指出：AI 应用的竞争重点正在从“谁用更强的模型”转向“谁能构建更好的代理框架（Agent Framework / Harness）”。同一个模型在不同框架下表现差距巨大，因此真正决定产品能力的，是围绕模型的工具、流程和控制系统。

---

##### 1. LangChain 的案例：框架比模型更能拉开差距

- 2026 年 2 月，LangChain 团队开源的编码代理 **deepagents-cli** 在 **Terminal-Bench 2.0** 上排名大幅提升：
  - 原本排名在 **30 名之外**
  - 后来进入 **前五**
  - 分数从 **52.8% 提升到 66.5%**
  - 提升了 **13.7 个百分点**

- 关键点是：  
  **底层模型没有变，始终是 GPT-5.2-Codex。**

- 他们改变的只是模型外部的“框架”。  
  这说明在实际 AI 应用中，模型本身不再是唯一核心，如何组织、调用和约束模型，正在变得更重要。

---

##### 2. 核心观点：模型不再是产品，而是工具

文章认为，当前应用 AI 领域正在发生一个重要转变：

> 模型本身不再等同于产品，模型只是产品中的一个工具。

换句话说，单纯调用大模型 API 并不能构成一个真正可靠的 AI 产品。真正的产品能力来自模型周围的一整套系统设计。

---

##### 3. 什么是代理框架？

代理框架是围绕大语言模型构建的一整套组件，它的作用是把 LLM 从“只会生成文字的模型”变成“能完成任务的代理”。

它通常包括：

- **工具调度**：决定什么时候调用搜索、代码执行、数据库等工具  
- **上下文管理**：控制模型记住什么、忽略什么  
- **沙箱化**：让代理在安全环境中运行代码或执行操作  
- **规划循环**：让代理拆解任务、制定步骤、反复执行  
- **子代理编排**：让多个代理协同完成复杂任务  
- **评估系统**：判断代理结果是否好  
- **可观测性**：追踪代理每一步做了什么  
- **验证逻辑**：判断任务是否真的完成

简单说，代理框架就是让模型“能干活、少出错、可追踪、可改进”的外部系统。

---

##### 4. Claude Code 泄露案例：真正复杂的是框架

文章提到，2026 年 3 月，Claude Code 的源映射曾短暂泄露。

其中显示：

- 代码库大约有 **513,000 行 TypeScript**
- 真正调用模型 API 的代码只有 **几行**
- 其余大部分代码都是框架逻辑

这个例子说明，成熟的 AI 产品并不是简单地“调用模型”，而是需要大量工程系统来管理模型的行为。

---

##### 5. Harness 的概念：让代理避免重复犯错

Mitchell Hashimoto 在 2026 年初提出了 “Harness” 这个说法。

他的定义很直接：

> 每当代理犯错时，你就设计一个解决方案，让它以后不再犯同样的错误。这个解决方案就存在于 Harness 中。

也就是说，Harness 是一种不断积累经验和规则的外部控制系统。

例如：

- 如果代理经常误删文件，就加入权限确认机制  
- 如果代理常常忘记检查测试结果，就强制执行测试验证  
- 如果代理容易跑偏，就加入阶段性目标检查  
- 如果代理无法判断任务是否完成，就增加自动评估或人工确认

这些改进不一定来自模型本身，而是来自模型外部的工程设计。

---

##### 6. 为什么模型会商品化，而框架不会？

文章认为，模型正在逐渐商品化，因为很多团队都能使用类似的强大模型，比如 GPT、Claude、Gemini 等。

但真正难以复制的是：

- 业务流程
- 工具集成
- 任务验证方式
- 用户场景理解
- 安全边界
- 错误修复机制
- 数据和反馈循环

因此，差异化不再主要来自“用了哪个模型”，而是来自“如何使用模型”。

---

##### 7. 成功代理框架的共同模式

文章总结了一个重要原则：

> 在推理层信任 LLM，在工具边界严格执行。

意思是：

- 可以让大模型负责理解、规划、推理
- 但在真正执行操作时，必须有严格的规则和边界

例如：

- 模型可以建议删除文件，但系统必须要求确认  
- 模型可以写代码，但系统要自动运行测试  
- 模型可以调用工具，但工具权限必须被限制  
- 模型可以给出结论，但关键场景要有验证机制

这能在发挥模型智能的同时，降低失控风险。

---

##### 8. 从 2025 到 2026：竞争重点的变化

文章判断：

- **2025 年**：大家都在争先恐后地构建 agents  
- **2026 年**：真正胜出的会是那些投资代理框架和脚手架系统的团队

也就是说，未来不是“有代理就够了”，而是要有稳定、可控、可扩展的代理系统。

---

##### 9. 文章结论：模型给你智能，工具决定产品

文章最后的核心总结是：

> 模型赋予你智能，工具为你提供产品。

也就是说：

- 模型提供基础能力
- 框架决定能力如何被稳定地用起来
- 工具和边界决定产品是否可靠
- Harness 决定代理是否能持续进化

因此，AI 团队应该把重点放在模型周围的系统建设上，而不是只关注模型本身。
