## 通俗精炼（1）

### 2026-10-12 08:17:04

#### AI 写代码越来越快，代码审查为何成了新瓶颈？

这组推文讨论的是：AI 加速软件开发后，写代码与审查代码的速度开始失衡。**作者认为，代码生成提速正在迫使团队重新设计研发流程，以及确认代码可靠、可以上线的方式。**引用推文进一步提出，不同人使用 AI agent 的规模差异，可能正在拉大他们的工作方式与能力差距；类似变化也可能出现在其他业务中。

##### 写得更快，不等于交付得更快

软件开发并不是写完代码就结束了。代码还需要经过 **code review（代码审查）**：由其他开发者检查改动是否合理、是否存在缺陷，以及是否会影响现有系统。

作者所说的“code 与 review 的速率倒挂”，指的是：**代码产出的速度已经快于团队审查、消化这些代码的速度。**热门回复把这个问题说得很直接：“写得越来越快，看的还是那几个人，瓶颈只是换了个地方。”

其中的因果关系是：

- AI 提高了写代码的速度，让开发者能更快提交更多改动。
- 审查仍需要人理解代码、核对业务要求、判断风险，未必能同步提速。
- 改动于是积压在审查环节，代码生成的效率提升不能完整转化为交付速度。

例如，如果一个团队每天能生成的代码改动翻了几倍，但审查能力不变，那么等待审查的队列就会变长。这是对机制的举例，不是原文提供的实际数据。

##### 争论的价值：迫使团队重新回答“怎样才敢上线”

作者把 code review 之争称为“可能会是今年最有价值的骂战”。重点不只是争论是否激烈，而是它暴露了一个需要解决的流程问题：**当写代码不再是最慢的环节，原有研发流程还能否承接新的产出速度？**

推文同时提到要重建“安全感”。结合上下文，可以理解为：团队需要重新确认，凭什么相信一段代码是可靠的、可以合并或上线。

过去，人工阅读和理解代码是建立这种信心的重要方式。现在，如果代码大量生成，而人的检查能力没有相应增长，就会出现两难：坚持原有审查方式，可能造成积压；未经充分检查就放行，则可能增加风险。

因此，问题不只是“要不要 code review”，而是**如何在更快的代码生产速度下，继续有效地发现问题、控制风险**。一位回复者提到自己正在做“评测和流程”，但原文没有展开具体方案，也没有证明某种替代方式已经足够可靠。

##### Agent 使用规模不同，可能让双方谈的不是同一种开发体验

引用推文把近期软件开发争论解读为一种新分化：人们能使用多少 agent、以什么方式使用，正在影响他们的工作体验。

这里的 **agent（智能体）**，可简单理解为能围绕任务调用工具、执行多个步骤的 AI 系统；相比主要靠问答交互的 chatbot（聊天机器人），它更侧重持续执行任务。

引用者列出了六种使用状态：

1. 完全不用 AI，连 chatbot 都没用过。
2. 只用 chatbot。
3. 用过一个 agent。
4. 同时使用 2—6 个 agent。
5. 后台持续 24 小时运行一个 agent。
6. 同时运行几十个到 100 个 agent。

这份划分不完全是按数量排序，也包含**是否持续运行、是否并行工作**的区别。

它对 code review 争论的意义在于：偶尔让 AI 帮忙写一段代码的人，与同时让大量 agent 推进任务的人，面对的代码产出量和管理压力可能很不一样。前者可能仍能逐项人工检查，后者则更容易遇到审查能力跟不上的问题。

引用者将这种分化称为“阶级差异”。**这是一种强调差距的判断，不是原文已经证实的社会分层结论。**推文没有提供数据，说明这些使用规模如何对应收入、职位或实际生产率。

##### 如果软件开发解决了这个问题，经验可能扩散到其他领域

作者认为，随着 agent 进入更多业务，类似失衡会更普遍。一位回复者进一步提出：**如果人类在软件开发的评测与流程上取得突破，相关经验可能很快扩散到其他领域。**

其逻辑是：AI 不只是加快“生产”，还会增加后续“检查、确认、批准”的工作量。只提高前一环节的速度，往往只是把瓶颈推到后一环节。

但这里保留着一个重要条件：**首先要找到能够承接更高产出速度、又能有效控制风险的流程。**原文表达的是这一方向的可能性，而不是宣布问题已经解决。

这场争论最值得关注的，因而不是谁更愿意接受 AI，而是：当执行任务越来越便宜、越来越快，人和组织该如何验证结果，并对结果负责。
