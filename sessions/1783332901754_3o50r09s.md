- 任务完成后让Claude生成变更说明和测验，确认自己理解后再合并或发布。

**Thariq**

### Fable 野外指南：发现你的未知

与 Claude Fable 5 合作不断地再次教导我一个古老的教训：地图不是领土。

地图，作为对待完成工作的一种表示，是我的提示、技能和背景信息，也就是我提供给 Claude 的内容。领域则是工作需要发生的地方，即代码库、现实世界及其实际限制。

![Image](https://pbs.twimg.com/media/HMUY0Dpa4AA__qj?format=jpg&name=large)

地图与现实的区别就是我所说的未知因素。当 Claude 遇到未知因素时，它需要基于对我的需求的最佳猜测来做决定。做的工作越多，Claude 可能遇到的未知因素就越多

Fable 是第一个让我觉得工作质量被我澄清其未知部分的能力所限制的模型。

重要的是，仅仅提前规划并不总是足够的。你可能会在实施过程中发现未知因素，或者，你的未知因素可能会让你意识到，你实际上应该用完全不同的方式来解决这个问题。

我发现与 Fable 合作是一个在实现之前、之中和之后不断发现自己未知之处的迭代过程。

I've made some

[示例工件用于查找此处的未知项 ，](https://thariqs.github.io/html-effectiveness/unknowns/) but be sure to come back to build the intuition for when to use them.

#### 了解你的未知

你的未知之处是什么？当我遇到问题向 Claude 求助时，我倾向于分 4 种方式来拆解问题：

- Known Knowns: This is essentially what is in my prompt. What do I tell the agent that I want?
- Known Unknowns: What haven't I figured out yet, but I’m aware that I haven’t?
- Unknown Knowns: What's so obvious I’d never write it down, but would recognize it if I saw it?
- Unknown Unknowns: What haven't I considered at all? What knowledge am I not aware of? Do I know how good something can be?

但是他们也会假设未知因素。在很多方面，减少并规划你所面对的未知因素是自主编码的技能。但幸运的是，这是一种你可以通过与 Claude 合作来提升的技能。

#### 帮助 Claude 帮助你

![Image](https://pbs.twimg.com/media/HMUZ8FWacAAK4eL?format=jpg&name=large)

指导 Claude 是一种微妙的平衡。如果你过于具体，Claude 会严格按照你的指示执行，即使转向可能更合适。如果你过于模糊，Claude 往往会基于行业最佳实践做出选择和假设，而这些可能不符合你的任务需求。

当你不考虑自己的未知因素时，无论哪种情况都会失败。你不知道道路何时会布满障碍，也不知道何时会畅通，但你仍然希望 Claude 转向。

Claude 可以帮你更快地发现未知内容。它可以极其迅速地在你的代码库和互联网中进行搜索，并且对普通话题的了解比你多得多。它还能更快地从失败中迭代。

这个过程中最重要的部分是向 Claude 提供关于你的起点的背景信息。例如，告诉它你在思考过程中的位置；分享你对该问题和代码库的经验；并让它像思考伙伴一样与你协作。

I've previously written about using

[HTML 与 Claude](https://x.com/trq212/status/2052809885763747935), in almost all of these cases, a HTML artifact is the best way to visualize and represent it.

在本文中，我详细介绍了一些我用来揭示这些未知因素的模式。我每次不会使用所有的技巧，但这是一个值得拥有的有用技巧集合。

### 实施前

#### 盲区超车

开始工作时，你能做的最有用的事情之一就是了解自己的盲点。例如，如果你正在代码库的新部分编写功能，或者使用 Claude 帮助你处理不熟悉的工作（比如迭代设计），你很可能会遇到很多未知的未知。

你可能不知道该问什么问题，不知道好的样子是什么样的，不知道已经做了哪些历史工作，也不知道要避开哪些陷阱。

要做到这一点，你可以让 Claude 帮助你找出你的未知的未知并向你解释。我喜欢使用字面意思的词语“盲点通道”和“未知的未知”。为其提供关于你是谁以及你知道什么的背景信息通常对

示例提示：

- 我正在添加一个新的认证提供方，但我对这个代码库中的认证模块一无所知。你能否进行一次盲区检查，帮助我找出相关的未知的未知因素，并帮助我更好地向你提问？
- 我不清楚什么是色彩分级，但我需要对这个视频进行调色。你能教我理解我在色彩分级方面的未知的未知，以便我能更好地进行提示吗？

#### 头脑风暴与原型

当我在一个有很多未知的已知的领域工作时，涉及到我只有在看到的时候才知道如何定义的标准，我喜欢让 Claude 和我一起头脑风暴并进行原型设计。

在原型设计阶段尽早识别并明确表达未知的已知因素极为重要，因为在实施阶段发现这些因素可能（相对）昂贵。对功能或规格的微小改动可能导致代码实现方式产生巨大差异，并且你的代理更难回滚之前的更改。

例如，你可能只想要查看一个添加到框架中的按钮的外观，而无需配置后端路由或在前端维护额外的状态。

视觉设计对我来说难以描述，但当我看到它时，我就知道自己想要什么。在这种情况下，我会为一个项目请求几种设计方案。

I also start almost every coding session with an exploration or brainstorming phase. This helps me start with intent to define the project’s scope. Claude often finds high-value approaches I would have missed and sometimes misses the forest through the trees. Brainstorming prevents me from setting too narrow or too wide a scope.

Example prompts:

- "I want a dashboard for this data but I have no visual taste and don't know what's possible. Make me an HTML page with 4 wildly different design directions so I can react to them.”
- “Before wiring anything up, make a single HTML file mocking the new editor toolbar with fake data. I want to react to the layout before you touch the treal app."
- "Here's my rough problem: users churn after onboarding. Search the codebase and brainstorm 10 places we could intervene, from cheapest to most ambitious. I'll tell you which ones resonate."

#### Interviews

Once I’ve done sufficient brainstorming, I likely still have unknowns.

In this case, I ask Claude to interview me about any unknowns or ambiguities. When asking Claude to interview you, try and give it context about your problem to guide its questions. Here are some examples.

Example prompts:

- "Interview me one question at a time about anything ambiguous, prioritize questions where my answer would change the architecture."

#### References

Sometimes you can’t describe what you want in detail. For example, you might not have the language or it might be so complicated that it would take you quite a while.

在这种情况下，最佳答案是一个参考。虽然你可以包含图表、文档或图片，但绝对最佳的参考是源代码。

If you have a library that implements something in a certain way or a design component you really like, just point Fable at the folder and tell it what to look for, even if it’s in a different language.

This is also the way Claude Design works. You don't have to hand it a file (although you can do that too). You can point it at a module on a website you like, and it reads the underlying code, not just the screenshot. This provides much richer detail around the markup, structure, and how the component is actually built.

Example prompts:

- This Rust crate in vendor/rate-limiter implements the exact backoff behavior I want. Read it and reimplement the same semantics in our TypeScript API client.

#### Implementation Plans

When I think I’m ready to implement, I tend to ask Claude to put together an implementation plan for me to review that focuses on the parts that might be most likely to change, for example to review data models, type interfaces or UX flows. This allows Claude to surface things I might actually need to alter.

Example Prompts:

- Write an implementation plan in HTML, but lead with the decisions I'm most likely to tweak with: data model changes, new type interfaces, and anything user-facing. Bury the mechanical refactoring at the bottom, I trust you on that part."

#### During implementation

#### Implementation notes

Once I am satisfied with my plan, I make a new session and pass any artifacts to the prompt. For example, I might pass in a spec file and a prototype and ask an agent to implement it.

But the truth is that no matter how much planning you do, there are always unknown unknowns lurking. The agent may find during its work that it needs to take a different tack due to an edge case it found in the code.

I ask Claude Code to keep a temporary ‘

[implementation-notes.md](https://www.google.com/url?q=http://implementation-notes.md&sa=D&source=editors&ust=1783101769359369&usg=AOvVaw1Iqvg51JpzkrkRtHHIjyOL)’ (or .html) file where it keeps track of decisions it makes so we can learn from our next attempt.

Example prompts:

- "Keep an
  [implementation-notes.md](https://www.google.com/url?q=http://implementation-notes.md&sa=D&source=editors&ust=1783101769359896&usg=AOvVaw1wFqbnqbAuO_GYnGk8_1bh) file. If you hit an edge case that forces you to deviate from the plan, pick the conservative option, log it under 'Deviations', and keep going."

### Post implementation

#### Pitches and explainers

![Image](https://pbs.twimg.com/media/HMUce7UaEAAegM5?format=jpg&name=large)

One of the most important parts of shipping something is getting buy-in and approvals. Building pitch and explainer artifacts in the final document helps:

- Accelerate understanding when reviewers start with the same unknowns you did
- Accelerate approvals when experts want to see you accounted for the unknowns and common failure points they would have anticipated

Example prompts:

- "Package the prototype, the spec, and the implementation notes into a single doc I can drop in Slack to get buy-in. Lead with the demo GIF."

#### Quizzes

After a long working session, Claude might have accomplished a lot more than I realized. Reading the code diffs can only give me a light understanding of what happened, since much of the behavior will depend on existing code paths.

Asking Claude to quiz me about the change after giving me a bunch of context helps me understand what happens. I only merge after I pass the quiz perfectly.

Example prompts:

- “I want to make sure I understand everything that's happened in this change. Give me a HTML report on the changes for me to read and understand with context, intuition, what was done, etc. and a quiz at the bottom on the changes that I must pass.”

#### How this comes together: launching Fable

The

[launch video for Fable](https://www.google.com/url?q=https://x.com/ClaudeDevs/status/2064399512664526853&sa=D&source=editors&ust=1783101769363678&usg=AOvVaw1MyZd5YMjjShztWHzo8N9u) was edited entirely by Claude Code. This was a new domain for me and I’m by no means an expert.

So I started with what I did know. I knew that Claude could use code to edit videos and transcribe them, but I wasn’t sure if it was accurate enough. I then asked Claude to explain to me how transcription like Whisper worked, and whether I would be able to accurately cut out things like ums or large pauses using ffmpeg.

I wanted Claude to create a UI that was timed with the words I was saying, but wasn’t sure if it would be able to so I asked Claude to create a prototype video using Remotion and a transcription to see if it would work.

Finally, the video itself looked a bit muted, which I knew was the result of color grading but I didn’t really know what color grading was. My first pass attempt was to try and get Claude to do a few variations to pick, but I realized that I didn’t know what “good” looked like when it came to color grading. So instead, I asked Claude to teach me about color grading to discover my unknowns.

You can watch a more in-depth explanation on that

[here](https://x.com/trq212/status/2064826394589442448/video/1).

#### Matching the Map and Territory

The better models get, the more you can achieve with the right approach. When a long-horizon task comes back wrong, it's likely you need to spend more time defining your unknowns or creating an implementation plan that allows for Claude to improvise through them.

Every explainer, brainstorm, interview, prototype, and reference is a cheap way to find out what you didn't know before it gets expensive to fix.

So start your next project by asking Claude to help you find your unknowns.

##### 一、深度总结

**核心观点：与强 AI 协作，关键不是“给出完美指令”，而是持续发现并管理未知。**

作者用“地图不是领土”说明：

- **地图**：你的提示、计划、背景、需求文档。
- **领土**：真实代码库、真实业务、真实限制。
- **差距**：各种“未知”。

Claude/Fable 越强，越能执行复杂任务；但任务越复杂，遇到未知越多。  
因此，最终质量往往受限于：**你能否帮助 AI 识别、澄清、记录和处理未知。**

作者将未知分为四类：

| 类型 | 含义 |
|---|---|
| 已知的已知 | 你已经明确知道并写进提示的内容 |
| 已知的未知 | 你知道自己还没想清楚的问题 |
| 未知的已知 | 你心里有判断，但说不出来；“看到就知道” |
| 未知的未知 | 你根本没意识到的问题、风险、盲区 |

文章提出一套 AI 协作流程：

###### 1. 实施前：先发现未知

- 让 AI 做“盲区检查”
- 头脑风暴多个方案
- 做低成本原型
- 让 AI 采访你，逐步澄清需求
- 提供参考代码、参考设计、参考产品
- 要求 AI 写实施计划，优先暴露关键决策点

###### 2. 实施中：允许偏离，但要记录

- 真实执行时一定会发现新问题
- 让 AI 保留 `implementation-notes.md`
- 记录偏差、原因、选择，便于复盘和下一轮迭代

###### 3. 实施后：帮助人理解与批准

- 生成解释文档、演示材料、Pitch
- 让 AI 出测验，检验你是否真正理解改动
- 不是看完 diff 就合并，而是理解行为后再合并

##### 二、深入浅出解读

这篇文章本质上在讲：

> 高级 AI 不是简单的“外包工人”，而是一个能帮你一起探路的伙伴。

很多人用 AI 的方式是：

> “我告诉你做什么，你照做。”

但作者认为更好的方式是：

> “我知道一部分，你帮我发现我不知道的部分，然后我们边走边修正。”

举个简单比喻：

你要去一座陌生城市。

- 提示词是地图；
- 项目现场是真实城市；
- 堵车、施工、天气、路况，就是未知。

如果你只说“按地图走”，AI 可能会撞上现实问题。  
更好的做法是让 AI：

1. 先帮你看哪里可能有坑；
2. 先画几条路线；
3. 走的时候记录临时改道；
4. 到达后解释为什么这样走。

所以，真正重要的不是一次性写出完美 prompt，而是建立一个循环：

> 探索 → 澄清 → 原型 → 实施 → 记录 → 解释 → 复盘

---

##### 三、最有价值的方法

###### 1. 盲区检查

适合你进入陌生领域时使用。

示例：

> 我不熟悉这个模块，请帮我找出我可能没意识到的风险和问题。

###### 2. 原型优先

适合“我说不清，但看得出来”的需求。

比如 UI、视觉、交互、视频效果。

先让 AI 做几个版本，别急着接入真实系统。

###### 3. AI 采访你

适合需求模糊时。

让 AI 一次问一个问题，尤其问那些会影响架构、数据模型、用户体验的问题。

###### 4. 给参考

如果你说不清，就给样例。

最好的参考不是截图，而是：

- 代码
- 现有组件
- 类似项目
- 设计系统
- 真实产品页面

###### 5. 实施计划先行

在动手前，让 AI 把关键决策列出来：

- 数据结构怎么变？
- API 怎么设计？
- UI 流程怎么走？
- 哪些地方最容易返工？

###### 6. 实施记录

执行过程中，让 AI 记录：

- 偏离原计划的地方
- 为什么偏离
- 做了什么取舍
- 有哪些后续风险

###### 7. 合并前测验

让 AI 反过来考你。

如果你答不出来，说明你还没真正理解这次改动。

---

##### 四、辩证思考

###### 1. 这篇文章的高明之处

它把 AI 协作从“写 prompt 技巧”提升到了“认知管理”。

真正的问题不是：

> 怎么让 AI 更听话？

而是：

> 怎么让 AI 帮我发现问题、补齐盲区、降低返工成本？

这是一种更成熟的 AI 使用观。

---

###### 2. 但也不能过度神化 AI

AI 可以帮你发现未知，但它不等于真理。

它可能：

- 提出看似合理但错误的假设；
- 过度迎合你的方向；
- 把行业通用方案误当成你的最佳方案；
- 在复杂业务中漏掉隐性约束。

所以，人仍然要负责最终判断。

AI 负责扩大搜索面，  
人负责价值判断和责任承担。

---

###### 3. “发现未知”也有成本

不是所有任务都需要复杂流程。

小任务可以直接做；  
高风险、高复杂、高返工成本任务，才值得：

- 盲区检查
- 原型
- 访谈
- 实施计划
- 复盘文档

否则会变成流程过度。

---

###### 4. 最核心的转变

过去写代码靠：

> 我想清楚 → 让工具执行。

现在与强 AI 协作更像：

> 我带着不完整理解出发 → 让 AI 帮我探索 → 我不断校准方向。

这意味着，未来重要能力不只是“会提问”，而是：

> 会暴露自己的无知，并把无知变成可处理的问题。

---

##### 五、一句话结论

**强 AI 时代，高手不是最会下命令的人，而是最会发现未知、澄清未知、管理未知的人。**

#### Fable 野外指南：发现你的未知

这篇材料的核心观点是：使用 Claude Fable 这类 AI 模型时，工作质量往往不只取决于你给出的指令，还取决于你有没有发现那些尚未说清、甚至尚未意识到的未知因素。接下来，我们会沿着“实施前、实施中、实施后”的顺序，了解如何让 Claude 帮你找出盲区，减少返工，并更好地完成复杂任务。

##### 一、先理解：地图不是领土

首先，作者借用了一个古老的比喻：地图不是领土。

这里的“地图”，指的是你交给 Claude 的提示、技能、背景资料，以及你对任务的描述。它代表的是你以为事情应该怎样完成。

而“领土”，指的是任务真正发生的地方。比如真实的代码库、现实世界的限制、已有系统的历史包袱，以及那些没有写进提示里的实际情况。

地图和领土之间的差距，就是未知因素。

当 Claude 遇到未知因素时，它只能根据对你需求的最佳猜测来做决定。任务越复杂，实际执行得越深入，它可能遇到的未知因素也就越多。

作者认为，Fable 是第一个让他明显感受到这一点的模型：工作质量可能不是被模型本身的能力限制，而是被人类有没有把未知部分澄清限制。

更重要的是，提前规划并不总能解决问题。你可能在实施过程中，才发现某个边界情况；也可能因为一个新的未知因素，意识到原来的方案根本不是最佳方案。

所以，与 Fable 合作不是“一次规划，然后执行”这么简单。它更像是一个持续迭代的过程：在实施之前、实施之中和实施之后，不断发现自己原来不知道的事情。

##### 二、把未知分成四类

接下来，要先学会识别自己的未知。

作者在向 Claude 求助时，会把问题拆成四种情况。

第一种，叫“已知的已知”。

这就是你已经知道、并且明确写进提示里的内容。简单说，就是你告诉 Claude：“我想要什么。”

第二种，叫“已知的未知”。

这是你知道自己还没有想清楚的部分。比如你知道认证模块很复杂，但还不知道应该采用哪种架构；或者你知道视频需要调色，但不知道什么样的色彩才算好。

第三种，叫“未知的已知”。

这指的是一些你觉得太明显，所以不会专门写出来的规则或偏好。但只要看到结果，你就能立刻认出它对不对。

例如，你很难用语言描述一个界面应该有多简洁，但看到一个设计稿时，你马上就知道“这就是我想要的感觉”。

第四种，叫“未知的未知”。

这才是最容易造成问题的一类。它指的是你根本没有考虑过的事情，也不知道自己缺少哪些知识，更不知道一件事最终可以做到什么程度。

作者认为，很多失败并不是因为提示写得不够详细，而是因为这四类未知没有被识别出来。

##### 三、怎样帮助 Claude 更好地帮助你

指导 Claude，其实需要保持一种微妙的平衡。

如果你说得过于具体，Claude 可能会严格照做。即使执行过程中发现另一条路明显更合适，它也可能继续沿着原来的指令走。

但如果你说得过于模糊，Claude 往往会按照行业惯例或所谓最佳实践来做选择。这些选择听起来合理，却未必符合你的实际需求。

两种情况都可能失败。因为你不知道前方的路什么时候会出现障碍，也不知道什么时候道路其实很顺畅，但你又希望 Claude 能够根据实际情况及时转向。

这时，Claude 的优势在于，它可以帮助你更快地发现未知。它能够快速搜索代码库和互联网，也可能比你掌握更多普通领域的知识，还能更快地根据失败结果继续迭代。

不过，最重要的前提，是你要告诉它自己的起点。

你可以说明自己目前已经想到哪里，分享你对问题和代码库的经验，也可以直接告诉 Claude：请像一个思考伙伴一样，和我一起探索，而不是只执行一串命令。

作者还提到，在很多场景中，HTML 工件很适合用来表达和可视化结果。所谓工件，就是可以直接查看、修改或继续使用的产物，比如一个 HTML 页面、原型文件或说明文档。

作者整理了一些用于发现未知因素的模式，但并不是每次都要全部使用。关键是逐渐形成判断：什么时候该做原型，什么时候该让 Claude 提问，什么时候该找参考资料，什么时候该先写实施计划。

##### 四、实施之前：先发现盲区

###### 1. 进行“盲区检查”

实施前的第一个方法，是让 Claude 主动帮你寻找“未知的未知”。

你可能不知道该问什么，也不知道一个好的结果应该是什么样；你可能不了解这个项目过去做过哪些工作，也不知道有哪些常见陷阱需要避开。

这时，可以把自己的背景和已知情况告诉 Claude，然后让它进行一次盲区检查。

比如你可以说：

“我正在为这个项目添加一个新的认证服务提供商，但我完全不了解代码库中的认证模块。请帮我做一次盲区检查，找出我可能没有意识到的未知因素，并帮助我提出更好的问题。”

又或者：

“我不清楚什么是视频色彩分级，但我需要给这段视频调色。请教我有关色彩分级的基础知识，并指出我还没有意识到的未知问题，这样我才能更好地向你提问。”

这里的重点，不是立刻让 Claude 开始写代码，而是先让它帮助你发现：你可能还缺少哪些问题、知识和判断标准。

###### 2. 头脑风暴与原型

接下来，是头脑风暴和原型设计。

核心结论是：越早发现那些“看似明显、但实际上没有说清”的需求，后续成本就越低。

因为在实施阶段，哪怕只是功能规格的一点小变化，也可能导致完全不同的代码实现。而且，一旦代理已经改动了很多文件，再回滚就会更困难。

举个例子，你可能只是想看看一个新增按钮的视觉效果，并不想现在就配置后端路由，也不想为了这个按钮在前端维护额外状态。

这时，最好的办法可能不是直接接入完整系统，而是先做一个带假数据的 HTML 原型，让你先对布局和风格做判断。

作者自己几乎每次开始编程工作时，都会先进行探索或头脑风暴。这样做可以帮助他明确项目范围。

Claude 有时会提出作者没有想到的高价值方案；但有时，也可能只关注局部细节，忽略整体方向。头脑风暴可以避免项目范围定得过窄，也可以避免一开始就做得过于庞大。

具体来说，可以让 Claude 为同一份数据制作四种风格完全不同的仪表盘页面，然后你根据实际看到的结果做选择。

也可以让它先用单个 HTML 文件，配合假数据，模拟一个新的编辑器工具栏。在真正接入应用之前，你先对布局做出反应。

如果问题是“用户在完成注册流程后大量流失”，还可以让 Claude 搜索代码库，头脑风暴出十个可能的干预位置，并且从成本最低的方案排到最有野心的方案。之后，你再告诉它哪些方向最符合自己的判断。

###### 3. 让 Claude 像采访者一样提问

完成一定程度的头脑风暴后，通常仍然会有一些未知因素。

这时，可以让 Claude 逐个采访你，专门寻找模糊之处和可能改变方案的关键问题。

提问时，最好先提供足够的背景，让 Claude 理解问题所在。然后要求它一次只问一个问题，并优先询问那些答案可能改变系统架构的问题。

这样做的好处是，你不必提前猜出所有问题。Claude 可以根据当前对话，逐步把你的隐含需求和决策条件挖出来。

###### 4. 使用参考资料

有些需求很难用语言描述。可能是因为你不知道相关术语，也可能是因为事情过于复杂，靠文字解释要花很长时间。

这时，可以直接把一个你喜欢的实现或设计交给 Claude 参考。

比如，你发现某个 Rust 代码库中的限流器，正好实现了你想要的退避行为。你可以让 Claude 阅读这个代码库，并在自己的 TypeScript API 客户端中复现同样的语义。

这里的“退避行为”，可以简单理解为：操作失败后，系统按照一定规则等待，再尝试下一次，而不是不断立即重试。

参考资料不一定要和你的项目使用同一种编程语言，也不一定只能提供一个文件。只要它体现了你想要的行为或结构，就可能有帮助。

作者提到，Claude Design 也是类似的思路。你不一定要只给它一张截图，也可以把一个网站上的模块或组件交给它，让它读取背后的代码。

这样得到的信息会更丰富，因为 Claude 不只是看到外观，还能理解页面的标记结构、组件组织方式，以及这个设计实际是如何构建出来的。

##### 五、准备实施：先写一份可调整的计划

当你觉得自己已经准备好开始实现时，作者通常会先让 Claude 写一份实施计划，并由自己审核。

这份计划不需要把所有机械性工作都讲得一样细，而应该优先展示那些最可能需要调整的部分。

例如，重点检查数据模型、类型接口和用户体验流程。所谓类型接口，就是不同模块之间约定好的数据格式和调用方式。

这些内容一旦发生变化，往往会影响整个实现方向。

作者建议，可以让 Claude 用 HTML 写出实施计划，并把最可能修改的决策放在最前面，把机械性的重构工作放在后面。这样，人可以集中精力审核真正重要的选择，同时把常规改动交给 Claude 处理。

##### 六、实施过程中：记录偏离计划的决定

即使计划做得很充分，实施时仍然会遇到新的未知因素。

比如，代理在阅读代码后发现某个边界情况，原来的方案无法直接适用，只能换一条实现路径。

因此，作者会让 Claude Code 临时维护一份名为“implementation-notes.md”的实施记录文件，也可以使用 HTML 格式。

这份记录的作用，是记下实施过程中做出的重要决定，尤其是那些偏离原计划的地方。

作者给出的做法是：如果遇到一个边界情况，必须偏离原计划，就选择较为保守的方案，把原因和变化记录在“偏离”部分，然后继续推进。

这样做有两个价值。

第一，你能知道最终代码为什么没有完全按照最初计划实现。

第二，这些记录可以帮助下一次尝试，避免重复犯同样的错误。

也就是说，实施记录不是额外的文档负担，而是一张连接“原计划”和“真实代码”的地图。

##### 七、实施完成后：让别人更容易理解，也让自己真正理解

###### 1. 用提案和解释材料争取认可

一个功能能否真正发布，不只取决于它能不能运行，还取决于相关人员是否理解并认可它。

因此，实施完成后，可以把原型、规格说明和实施记录打包成一份提案或解释材料，交给评审者和决策者。

这类材料的作用，是帮助评审者快速理解整个项目，尤其是那些他们和你一样一开始并不了解的部分。

同时，它也能让专家看到：你已经考虑过他们通常会关心的未知因素和常见失败点。

例如，可以把原型、规格说明和实施记录整理成一份文档，方便直接发送到团队协作工具中，并把演示动图放在开头，让别人先看到结果，再了解背后的细节。

###### 2. 用测验确认自己真的理解了改动

长时间和 Claude 一起工作后，AI 可能已经完成了很多事情，而你自己未必真正理解所有变化。

只看代码差异，往往只能得到一个很浅的认识。因为最终行为还可能依赖已有代码路径，也就是系统原本就存在、但这次没有直接修改的执行流程。

所以，作者会让 Claude 在获得完整背景后，反过来给自己出题。

比如，让 Claude 生成一份 HTML 报告，解释这次改动做了什么、为什么这样做、相关背景是什么、这些变化在系统中会产生怎样的行为，然后在报告末尾加上一份测验。

作者的标准很明确：只有在完全通过测验后，才会合并这次改动。

这一步的意义是，把“代码已经写完”与“我真正理解了代码”区分开来。

##### 八、一个完整案例：Fable 的发布视频

接下来，作者用 Fable 的发布视频说明这些方法如何结合起来。

这个发布视频完全由 Claude Code 剪辑完成，而视频制作对作者来说是一个全新的领域，他并不是专家。

所以，他先从自己已经知道的部分开始。

他知道 Claude 可以通过代码编辑视频，也知道它可以进行转录。但他不确定转录是否足够准确，也不确定能不能用 FFmpeg，也就是一个常见的视频处理工具，准确删掉“嗯”这样的口头停顿，以及较长的空白。

于是，他先让 Claude 解释语音转录工具 Whisper 的工作方式，并讨论这种转录准确度是否足以支持视频剪辑。

接着，作者希望制作一个和自己说话内容同步的界面，但不确定 Claude 能不能做到。

他没有直接制作最终版本，而是让 Claude 使用 Remotion，也就是一种可以用代码生成视频的工具，结合转录文本，先制作一个原型视频，用来验证这个方向是否可行。

后来，视频整体看起来有些暗淡。作者知道这可能和“色彩分级”有关。

色彩分级，可以简单理解为通过调整画面的色调、亮度、对比度和整体氛围，让视频看起来更符合某种效果。

一开始，作者让 Claude 做出几种不同的调色版本，打算从中选择一个。

但他很快发现，问题并不只是“有几个选项可以选”。他其实不知道色彩分级中的“好”到底是什么样，也没有足够的判断标准。

于是，他改变了方法，不再只是让 Claude 直接给出结果，而是让 Claude 先教自己理解色彩分级，并帮助自己发现这方面的未知因素。

这个案例说明，遇到陌生领域时，最有效的做法有时不是直接要求 AI 完成任务，而是先让 AI 帮你建立判断标准。

##### 九、把地图逐渐对齐到领土

最后，作者回到最初的比喻。

模型能力越强，只要方法得当，你就能完成越复杂、跨度越大的任务。

但如果一个长流程任务最终结果不对，问题可能并不是模型不够强，而是你需要更多时间来定义未知因素，或者需要制定一份允许 Claude 在未知部分灵活调整的实施计划。

每一次解释、头脑风暴、采访、原型和参考，都是一种低成本探索。

它们的共同作用，是让你在问题还便宜、还容易修改的时候，发现自己原来不知道的事情，而不是等到代码写完、项目上线后才付出高昂的返工成本。

所以，作者给出的建议是：开始下一个项目时，不要只告诉 Claude 你想做什么，也要先问它，能不能帮助你找出自己还不知道什么。

##### 结尾：最值得记住的几个结论

最后，回顾五个最重要的结论。

第一，地图不是领土。你的提示和计划，只是对现实工作的简化描述，真正的代码库、用户需求和系统限制，往往包含更多未知。

第二，未知至少有四种：已知的已知、已知的未知、未知的已知，以及未知的未知。真正危险的，通常是你根本没有意识到的那部分。

第三，提前规划很重要，但规划并不够。实施过程中仍然会出现新的边界情况，因此要允许 Claude 调整方向，并记录偏离计划的决定。

第四，原型、头脑风暴、采访和参考资料，都是低成本发现问题的方法。越早发现未知，修改成本通常越低。

第五，任务完成后，不要只看代码差异。让 Claude 解释改动并给你出题，直到你真正理解结果，再决定是否合并或发布。

#### AI 协作的真正瓶颈，正从执行转向“管理未知”

文章最有价值的地方，不是又提供了一组提示词，而是准确描述了长任务为何容易失控：**提示、规格和背景信息只是“地图”，代码库、用户需求与现实约束才是“领土”**。模型能力越强，越能快速完成既定工作，但也越可能沿着一个未经验证的假设走得很远。此时，限制质量的往往不再是执行速度，而是人能否及时发现自己遗漏了什么。

作者用四类“已知与未知”拆解问题。其中尤其值得注意的是两类：一是“未知的已知”，即难以写进需求、看到方案却能立即判断的隐性偏好；二是“未知的未知”，即连问题都尚未意识到。前者适合通过多个原型、参考实现来显性化，后者则需要代码搜索、领域解释和盲点检查。它们都不是靠把初始提示写得更长就能解决。

##### 核心方法不是规划更多，而是更早、更便宜地购买信息

文中的头脑风暴、访谈、原型、实施计划、偏差日志和事后测验，看似是不同技巧，实质上遵循同一个原则：**在决策尚可逆时，用低成本工件暴露高成本误解。**

例如，先做一个带假数据的单页原型，不是为了提前交付，而是为了确认布局与交互；让模型优先追问“答案会改变架构”的问题，是在筛选真正有决策价值的信息；实施计划先展示数据模型、接口和用户流程，而把机械重构放到后面，则是在把人的注意力留给代价最大的选择。参考代码也不仅是“给个例子”，而是在语言难以描述时，用现成实现压缩高维意图。

这对产品工作同样适用。需求文档常把尚未确认的判断伪装成确定事实，而 AI 会进一步放大这种错觉：它能迅速把模糊需求变成看似完整的产品。更好的协作方式，是让发现、设计和实现形成短循环，而不是先由人定义全部问题，再让模型一次性交付答案。

##### 但不能把所有失败都归因于“你没说清楚”

文章主要依据个人实践，最需要补上的边界是：模型本身也有未知，而且它的盲点可能与用户高度相关。让同一个模型发现盲点、实施方案，再出题验证理解，容易形成闭环自证。长任务出错也可能来自上下文丢失、工具失败、错误检索或能力不足，而不只是需求不清。

因此，实施日志和测验适合帮助人重新取得理解权，却不能替代自动化测试、真实用户反馈、专家审查与来源核验。尤其是安全、财务、医疗等高风险领域，模型提出的“未知未知”只能作为检查清单的起点。

更进一步看，这里存在一个值得验证的产品方向：AI 工作台不应只保存对话，还应持续维护一份**不确定性账本**——哪些是假设、证据来自哪里、哪些决定尚未关闭、什么变化会触发重新评估。下一代 AI 协作工具的竞争点，可能不只是“生成得更快”，而是谁能让团队在快速推进时，仍清楚自己究竟知道什么。
