## 正文

**Leeway**

5 个 agent 定义文件 + 5 个 Python 脚本 + 0 个自建 Agent 框架。跑了 14 天整个内容工作流。

Anthropic 核心工程师 Barry Zhang 和 Mahesh Murag 在 AI Engineering Summit 上说了句话："别再造 Agents 了，去造 Skills。" AYi 写了详细解读（推荐看），我补一下用 Skills 跑了两周的真实体验。

——

【1】他们说的 Skill 到底是什么

不是 SDK，不是框架，不是 API。就是一个文件夹，里面放 markdown + 脚本。

结构：  
\`\`\`  
my-skill/  
├── SKILL.md ← 告诉 Claude 这个技能做什么、怎么用  
├── references/ ← 背景知识、banned phrases、规则  
└── scripts/ ← Python/bash 执行脚本  
\`\`\`

Claude 需要的时候自动加载进上下文。不需要的时候不占 token。可以 git 管理，可以分享，可以版本控制。

Barry 说得最准的一句：Agent 聪明但没有领域知识，碰到真实世界就碎。Skill 是把人类验证过的方法打包，让 Agent 去执行。

——

【2】我实际跑了什么

两周前搭了一套内容工作流，全部用 Skills 模式。没写 LangChain，没搭 Agent 框架，全是 markdown + Python 脚本：

5 个 Agent 定义文件（其实就是 markdown prompt）：  
\- engagement-agent.md — Twitter/Reddit 回复策略 + 三源扫描规则  
\- intelligence-agent.md — 8 平台热点扫描 + 交叉验证逻辑  
\- distribution-agent.md — S-012 内容生成 + 发布流程  
\- relationship-agent.md — 11 人 CRM 评分 + 跟进节奏  
\- viral-autopsy-agent.md — 爆款帖解剖 + pattern 提取

5 个执行脚本（最长 349 行）：  
\- voice\_gate.py (292行) — 30+ 禁词 + 7 组正则 + 打分系统，防 AI 模板句  
\- twitter\_gql.py (349行) — Twitter GraphQL API 直接发帖/点赞/回复  
\- consume\_handoff.py (156行) — 云端 Routine 产出的消费者  
\- [http://scan-daily.sh](http://scan-daily.sh) (165行) — 多平台批量扫描  
\- gen\_graveyard\_card.py (93行) — 配图生成

没有编排框架。Claude Code 读 markdown 就知道该干什么，读 Python 就知道怎么干。Skill 文件是知识层，脚本是执行层，Claude 是运行时。

——

【3】为什么比自建 Agent 好用

第一周试过 LangGraph，第三天放弃了。原因：

\- 调试地狱。LangGraph 的 state graph 一旦超过 5 个节点，出了 bug 不知道是 state 的问题还是 node 的问题还是 edge condition 的问题。markdown prompt 出了问题就改那一行。  
\- 上下文爆炸。Agent 框架把所有东西塞进上下文。Skill 是按需加载，Claude 执行 voice gate 的时候不需要知道 relationship scoring 的规则。  
\- 版本控制。Skill 是文件，git diff 一目了然。Agent 的 state 序列化后 diff 看不懂。  
\- 非程序员能改。voice\_gate.py 里的禁词列表，任何人打开 markdown 就能加一行。不需要懂 Python。

Barry 在演讲里说"Fortune 100 公司的法务和 HR 都在自己写 Skill"。我信，因为 Skill 的门槛就是能编辑文本文件。

——

【4】实际数据

14 天运行数据：  
\- 发布 4 篇 S-012 curation 长推（voice gate 全 PASS）  
\- 11 人关系网络维护（relationship-agent 自动提醒跟进）  
\- 100+ 条 engagement 记录在 tracker.jsonl  
\- intelligence-agent 累计扫描 8 个平台，产出 17 条 cross-platform signal  
\- voice gate 拦截了至少 3 次 AI 模板句（详见 banned-phrases.md，30+ 条禁词）

最有用的 Skill: voice\_gate。Reddit 上一条评论被叫 "AI slop" 拿了 -14 分。之后写了这个检查器，再没被骂过。

——

【5】从 Skill 到 Routine 的进化路径

昨天写了 Routines（Anthropic 新功能），今天写 Skills，这两个是配套的：

\- Skill = 知识层。定义"怎么做"。  
\- Routine = 执行层。定义"什么时候做"。

Skill 告诉 Claude "扫描 HN 的时候用 Firebase API，过滤 AI 相关，score&gt;100 才要"。Routine 告诉 Claude "每天早上 7 点跑这个 Skill"。

一个没有 Skill 的 Routine 就是一个每天定时发呆的 cron job。一个没有 Routine 的 Skill 就是一个等人手动调用的函数。配起来才是完整的自动化。

先写 Skill，验证跑得通，再迁到 Routine。这个顺序不能反。

## 通俗精炼（1）

### 2026-04-16 06:58:20

#### Leeway 的核心观点：别急着造 Agent，先把“技能”做出来

##### 一句话结论
这篇文章的核心意思是：**比起搭复杂的 Agent 框架，更实用的方式是把经验沉淀成可复用的 Skill（技能包）**。Skill 本质上不是框架，而是“**Markdown 说明 + 脚本工具**”的组合，让 Claude 在需要时按需调用。

##### 什么是 Skill
作者认为，Skill 不是 SDK、不是 API、也不是某种 Agent 框架，**本质就是一个文件夹**，里面装三类东西：
- `SKILL.md`：说明这个技能能做什么、怎么调用
- `references/`：背景知识、规则、禁用表达等
- `scripts/`：Python 或 Bash 脚本，负责实际执行

它的价值在于：**把人类验证过的方法，打包给 Agent 使用**。这样 Agent 不只是“会推理”，而是“知道怎么在具体场景里做事”。

##### 作者的真实实践
作者用这种方式，搭了一套持续运行两周的内容工作流：
- 5 个 Agent 定义文件：负责互动、情报扫描、内容分发、关系维护、爆款拆解
- 5 个 Python/脚本工具：负责发帖、扫描、内容检查、生成配图等
- 没有使用 LangChain、LangGraph 或自建 Agent 框架

整体结构可以理解为：
**Skill 文件负责知识和规则，脚本负责执行，Claude 充当运行时。**

##### 为什么比自建 Agent 框架更好用
作者给出的理由很直接：

###### 1. 更容易调试
复杂 Agent 框架节点一多，问题很难定位；而 Skill 出错时，通常直接改 Markdown 或脚本即可。

###### 2. 更节省上下文
框架常把大量信息塞进上下文，导致冗余；Skill 是按需加载，谁需要谁出现，更轻量。

###### 3. 更适合版本管理
Skill 是普通文件，`git diff` 很清晰；而复杂 Agent 的状态序列化后往往难读、难追踪。

###### 4. 非程序员也能参与
很多规则直接写在 Markdown 里，产品、运营、法务、HR 都能改，不必依赖工程师。

##### 实际结果说明了什么
在 14 天运行中，这套 Skill 模式已经支撑了完整工作流，包括：
- 持续发布内容
- 维护关系网络
- 记录互动数据
- 跨平台扫描热点信号
- 用 `voice_gate` 拦截 AI 味太重的表达

最关键的启发是：**Skill 不是概念，而是已经能落地并产生实际收益的工作方式。**

##### Skill 和 Routine 的关系
作者最后强调，Skill 和 Routine 应该配合看：

- **Skill**：定义“怎么做”
- **Routine**：定义“什么时候做”

也就是说：
- 只有 Routine，没有 Skill，就只是定时执行空壳任务
- 只有 Skill，没有 Routine，就只是等人手动触发的能力模块

正确路径应该是：**先把 Skill 跑通，再接入 Routine 做自动化。**

##### 核心启发
这篇文章最值得记住的一点是：  
**Agent 的真正价值，不在于框架多复杂，而在于有没有把具体场景里的知识、规则和方法沉淀成可执行的 Skill。**

对于大多数团队来说，先把“技能包”做好，往往比从零造一个 Agent 系统更快、更稳、更容易协作。

##### 1. Skill 到底是什么

- 作者先解释：**Skill 不是 SDK、不是框架、也不是 API**，本质上就是一个文件夹，里面放说明文档和执行脚本。
- 典型结构包括：
  - `SKILL.md`：告诉 Claude 这个技能是做什么的、怎么调用

- 它还具备工程化上的便利：
  - 可以用 Git 管理
  - 可以分享和复用
  - 可以做版本控制
- 文中引用 Barry 的观点：**Agent 虽然聪明，但缺少领域知识，到了真实业务环境容易失效；Skill 的价值，是把人类验证过的方法打包给 Agent 执行。**

##### 2. 作者实际搭了什么系统

- 作者用 Skills 模式搭了一整套内容工作流，持续跑了 **两周（14 天）**。
- 整套系统没有使用：
  - LangChain
  - 自建 Agent 框架
- 实际使用的只有两类东西：**5 个 Agent 定义文件 + 5 个执行脚本**。

###### Agent 定义文件

- `engagement-agent.md`：负责 Twitter / Reddit 回复策略，以及三源扫描规则
- `intelligence-agent.md`：负责 **8 个平台**的热点扫描和交叉验证
- `distribution-agent.md`：负责 `S-012` 内容生成和发布流程
- `relationship-agent.md`：负责 **11 人 CRM** 评分和跟进节奏
- `viral-autopsy-agent.md`：负责爆款内容拆解和模式提取

###### 执行脚本

- 作者总结这套架构时说得很直白：
  - **Skill 文件是知识层**
  - **脚本是执行层**
  - **Claude 是运行时**

##### 3. 为什么它比自建 Agent 框架更好用

- 作者提到自己第一周也试过 **LangGraph**，但到第 **3 天**就放弃了。
- 原因主要有 4 个：

###### 3.1 调试更简单

- LangGraph 一旦 state graph 超过 **5 个节点**，排查 bug 会很痛苦。
- 因为你很难迅速判断问题到底出在：
  - state
  - node
  - edge condition
- 相比之下，Skill 方式更直接：**markdown prompt 哪行有问题，就改哪一行。**

###### 3.2 上下文更节省

- 很多 Agent 框架会把大量内容一起塞进上下文，容易造成“上下文爆炸”。
- Skill 是**按需加载**：
  - 比如 Claude 在执行 `voice gate` 时，不需要知道 `relationship scoring` 的规则
- 这样既减少 token 浪费，也让任务边界更清晰。

###### 3.3 版本控制更友好

- Skill 本质是普通文件，`git diff` 一看就明白。
- 反过来，Agent 的 state 如果序列化之后再比较，往往很难读、很难维护。

###### 3.4 非程序员也能参与修改

- 例如 `voice_gate.py` 里的禁词规则，团队成员只要能编辑 markdown / 文本文件，就能直接补充一条。
- 不要求每个人都懂 Python。
- 文中还引用 Barry 的说法：**财富 100 强公司的法务和 HR 都在自己写 Skill**。
- 作者认为这很可信，因为 Skill 的使用门槛就是“能编辑文本文件”。

###### 具体案例

##### 5. Skill 和 Routine 应该怎么配合

- 作者最后谈到从 Skill 到 Routine 的进化路径，认为二者是互补关系：

###### Skill 的作用

- **Skill = 知识层**
- 它负责定义：**“怎么做”**
- 比如告诉 Claude：
  - 扫描 HN 时用 Firebase API
  - 只看 AI 相关内容
  - `score > 100` 才值得关注

###### Routine 的作用

- **Routine = 执行层**
- 它负责定义：**“什么时候做”**
- 比如规定：**每天早上 7 点执行一次这个 Skill**

###### 两者缺一不可

- 没有 Skill 的 Routine，就像一个**每天定时发呆的 cron job**
- 没有 Routine 的 Skill，就像一个**只能手动调用的函数**
- 只有组合起来，才能形成完整自动化。

##### 6. 作者给出的实践建议

- 正确顺序不是先上自动调度，而是：
  1. **先写 Skill**
  2. **先验证它真的能跑通**
  3. **再迁移到 Routine**
- 作者特别强调：**这个顺序不能反。**
