## 分析要点

- **核心高价值点**：最有价值的点是把 Agent 的稳定性问题从“提示词技巧”转向“可机读的协议、约束和反馈回路设计”来理解。
- **留存建议**：可归档保留，适合作为理解 Agent 工程化方向的中期参考（文章提出了将 Agentic Coding 视为反馈控制系统的框架，并结合软件工程规范化给出较强的解释力）

**知识要点**

- Harness Engineering 可视为控制论式闭环：设定目标、观测偏差、自动纠偏
- Agent 效果高度依赖文档、测试、Lint、架构约束等可机读规范
- 模型记忆不稳定，长期知识应通过外部协议和持久化文档承载
- 生成比验证更难，未来工程师优势更可能体现在定义标准与评估输出

**行动项**

- 检查当前代码库是否具备可机读的架构文档、Lint 规则和可解析测试反馈
- 为 Agent 工作流设计外部状态协议，如决策日志、长期记忆文档和状态同步文件

### Harness Engineering Is Cybernetics

Reading OpenAI's

[harness engineering post](https://openai.com/index/harness-engineering/), I kept having a feeling I couldn't place. Then it clicked: I'd seen this pattern before. Not once — three times.

The first was

[James Watt's centrifugal governor](https://en.wikipedia.org/wiki/Centrifugal_governor) in the 1780s. Before it, a worker stood next to the steam engine adjusting the valve by hand. After it, a weighted flyball mechanism sensed rotational speed and adjusted the valve automatically. The worker didn't disappear. The job changed: from turning the valve to designing the governor.

![Image](https://pbs.twimg.com/media/HC3M_2qacAA7mej?format=png&name=large)

The second was

[Kubernetes](https://kubernetes.io/docs/concepts/architecture/controller/). You declare desired state — three replicas, this image, these resource limits. A controller continuously observes actual state. When they diverge, the controller reconciles: restarts crashed pods, scales replicas, rolls back bad deployments. The engineer's job shifted from restarting services to writing the spec the system reconciles against.

The third is now. OpenAI describes engineers who no longer write code. Instead they design environments, build feedback loops, and codify architectural constraints — then agents write the code.

[A million lines in five months](https://openai.com/index/harness-engineering/), zero written by hand. They call it "harness engineering."

Same pattern each time. Norbert Wiener named it in 1948: cybernetics, from the Greek κυβερνήτης — steersman. The same root that gave Kubernetes its name. You stop turning the valve. You steer.

![Image](https://pbs.twimg.com/media/HC17rnca8AAQgjt?format=jpg&name=large)

Each time the pattern appears, it's because someone built a sensor and actuator powerful enough to close the loop at that layer.

#### Why the codebase was the holdout

The codebase had feedback loops, but only at the lower levels. Compilers close a loop on syntax. Test suites close a loop on behavior. Linters close a loop on style. These are real cybernetic controls — but they only operate on properties that can be checked mechanically. Does it compile? Does it pass? Does it follow the rules?

Everything above that — does this change fit the system's architecture? is this the right approach? is this abstraction going to cause problems as the codebase grows? — had no sensor and no actuator. Only humans could operate at that level, on both sides: judging quality and writing the fix.

LLMs changed both at once. They can sense at the level humans used to own — and act at the same level: restructure a module, redesign an inconsistent interface, rewrite a test suite around the contracts that actually matter. For the first time, the feedback loop can close where the important decisions are made.

But closing the loop is necessary, not sufficient. Watt's governor needed to be tuned. Kubernetes controllers need the right spec. And an LLM working on your codebase needs something harder to provide.

#### Calibrating the sensor and actuator

Getting the basic feedback loop working — tests that agents can run, CI that gives parseable output, error messages that point to the fix — is table stakes.

[Carlini demonstrated this](https://www.anthropic.com/engineering/building-c-compiler) when he had 16 parallel agents build a C compiler:

[embarrassingly simple prompts](https://github.com/anthropics/claudes-c-compiler/commit/a28ff299)

, but carefully designed test infrastructure. "Most of my effort went into designing the environment around Claude — the tests, the environment, the feedback."

The harder problem is calibrating the sensor and actuator with knowledge specific to your system. This is where most people get stuck, and where they blame the agent.

"It keeps doing the wrong thing. It doesn't understand our codebase." The diagnosis is almost always wrong. The agent isn't failing because it lacks capability. It's failing because the knowledge it needs — what "good" means for your system, which patterns your architecture rewards, which it avoids — is locked inside your head, and you haven't externalized it. Agents don't learn through osmosis. If you don't write it down, the agent makes the same mistakes on the hundredth run as the first.

The work is making your judgment machine-readable. Architecture docs that describe actual layering and dependency direction. Custom linters with remediation instructions baked in. Golden principles that encode your team's taste. OpenAI

[found exactly this](https://openai.com/index/harness-engineering/): they spent 20% of every Friday cleaning up "AI slop" — until they encoded their standards into the harness itself.

#### The only way forward

The practices this demands — documentation, automated testing, codified architectural decisions, fast feedback loops — were always correct. Every engineering book written in the last thirty years recommends them. Most people skip them because the cost of skipping was slow and diffuse: gradual quality decline, painful onboarding, tech debt that compounds quietly.

Agentic engineering makes the cost extreme. Skip the documentation and the agent ignores your conventions — not on one PR, but on every PR, at machine speed, around the clock. Skip the tests and the feedback loop can't close at all. Skip the architectural constraints and drift compounds faster than you can fix it. And here's the trap: you can't use agents to clean up the mess if the agents don't know what clean looks like. Without the calibration, the machines that created the problem can't solve it either.

The practices haven't changed. The penalty for ignoring them has become unbearable.

The generation-verification asymmetry — the intuition behind

[P vs NP](https://en.wikipedia.org/wiki/P_versus_NP_problem),

[demonstrated empirically for LLMs](https://arxiv.org/abs/2110.14168)

by Cobbe et al. — points to where this goes. Generating a correct solution is harder than verifying one. You don't need to out-implement the machine. You need to out-evaluate it: specify what "correct" looks like, recognize when the output misses, judge whether the direction is right.

The workers who designed Watt's governor didn't go back to turning valves. Not because they couldn't. Because it no longer made sense.

#### 一、先给结论：这两份内容合起来，讲的是同一件事的“两面”

可以浓缩成一句话：

> **Agentic Coding 并没有推翻软件工程，反而是在“强迫”团队把过去那些一直被忽略的软件工程最佳实践，真正落地。**

但更关键的补充是：

> **仅有文档、规则、提示词还不够。因为当前大模型对复杂工程知识的“理解、记忆、迁移、稳定执行”能力仍然远弱于优秀工程师，所以必须把经验从“脑子里 / prompt 里”转成“外部系统 / 协议 / 可验证约束”里。**

也就是说：

- **内容 2** 更强调：Agentic Engineering 的本质是**控制论（cybernetics）**，重点是设计反馈回路，让 agent 在系统里被“校准”和“纠偏”。
- **内容 1** 更强调：这个方向没错，但**别高估模型本身**。你以为把经验讲给模型听，它就会像一个聪明同事一样真正掌握并长期记住；现实是，它往往做不到，而且会反复遗忘。

两者结合起来，就是一句更完整的话：

> **未来工程师的工作，确实越来越像“驾驭系统”而不是“亲手拧阀门”；但前提是，你不能把希望寄托在模型自己变聪明，而要把组织经验工程化、协议化、可验证化。**

---

#### 二、内容 2 的核心观点：Harness Engineering 本质上是“控制论”

先拆解一下第二篇《Harness Engineering Is Cybernetics》。

##### 1. 作者的主比喻：从“手动操作”到“设计反馈系统”

作者用了三个历史类比：

- **蒸汽机调速器（Watt governor）**
  - 以前：工人站在旁边，手动调阀门
  - 后来：调速器自动感知速度并调节
  - 人没有消失，但工作变了：从“操作机器”变成“设计调节机制”

- **Kubernetes**
  - 你不再手动重启服务、扩缩容
  - 而是声明“期望状态”（desired state）
  - controller 持续观测实际状态并纠偏（reconcile）

- **Agentic Coding / Harness Engineering**
  - 工程师不再直接写每一行代码
  - 而是设计环境、测试、约束、反馈回路
  - 让 agent 去生成代码，再通过系统不断验证和修正

这三个例子的共同模式是：

> **人从直接执行动作，转向定义目标、设计观测机制、设计纠偏机制。**

这就是作者说的 **cybernetics（控制论）**：核心不是“干活”，而是“闭环控制”。

---

##### 2. 为什么代码库以前一直是“最后一个没有被完全自动闭环的层”

作者说得很准：

以前代码世界不是没有反馈回路，而是这些回路都偏底层：

- compiler 检查语法
- tests 检查行为
- linter 检查风格

它们都能回答一些机械性问题：

- 能不能编译？
- 测试过不过？
- 风格符不符合规则？

但它们**无法回答高层次问题**：

- 这个改动是否符合整个系统架构？
- 这个抽象是否合理？
- 这个模块边界会不会在未来演化中出问题？
- 这是不是“我们团队想要的方式”？

这些过去主要靠人脑判断，也靠人手修复。

作者认为，LLM 的突破在于：

> 它第一次同时具备了“在高层次上感知问题”和“在高层次上动手修改”的能力。

比如它可以：

- 重构模块
- 调整接口
- 重写测试
- 按照某些约束重新组织实现

因此，代码工程第一次有机会在更高层闭环。

---

##### 3. 但作者也强调：闭环能建起来，不代表天然就能跑好

这里是文章最重要的地方。

作者说：

- 有测试基础设施
- 有 CI
- 有可解析错误信息
- 有自动反馈

这些只是 **table stakes（入场券）**

真正难的是：

> **如何校准这个“传感器 + 执行器”系统，让它真正理解你们的“好代码标准”。**

这就引出一个核心命题：

###### Agent 失败，很多时候不是“能力不够”，而是“你没把判断标准外化”

也就是说，常见抱怨是：

- 它不理解我们的代码库
- 它总做错
- 它老偏离架构

作者的判断是：

> 问题往往不在 agent 本身，而在于你脑中的经验、团队的审美、架构的偏好、代码库的隐含规则，并没有被写成机器可以读取和执行的东西。

所以解决方案不是继续骂模型，而是：

- 写真实的架构文档
- 把约束变成 lint / checks
- 把“团队品味”变成 golden principles
- 把错误模式变成 harness 的一部分

OpenAI 那个例子里，作者提到：
他们最初每周五要花 20% 时间清理 “AI slop”，直到他们把标准编码进 harness。

这句话非常关键：  
**不是靠更强的 prompt，而是靠更强的系统。**

---

##### 4. 最终落点：软件工程的老原则没有过时，只是“违反它们的代价突然变得极大”

作者的结论很强：

这些实践从来不是新东西：

- 文档
- 自动化测试
- 架构决策记录
- 快速反馈
- 规则编码

过去大家不做，不是因为不知道，而是因为：

- 代价是慢性发作的
- 质量下降是渐进的
- 技术债是缓慢积累的

但 Agentic Engineering 改变了这个经济学：

- 你不写文档，agent 就会**高速地**在每个 PR 里重复犯错
- 你没测试，反馈回路就根本闭不上
- 你没架构约束，漂移会以机器速度扩散
- 更糟的是：当代码库已经很乱时，你还不能指望 agent 帮你收拾，因为它根本不知道“干净”长什么样

所以：

> **AI 没有改变最佳实践，它只是把“忽略最佳实践的代价”放大了。**

---

#### 三、内容 1 的核心观点：方向没错，但“模型的理解与记忆能力”是现实瓶颈

如果说内容 2 偏“方法论乐观”，内容 1 就是非常重要的“现实主义修正”。

##### 1. tison 认可文章的大方向

tison 明确说，文章最后的落点是对的：

> 现在大家做 Agentic Coding，本质上是在落实过去软件工程总结出来的那些经验。

比如：

- 规范化
- 文档化
- 可测试
- 可反馈
- 可约束

这些以前一直都对，只是因为落地成本太高，所以常常被忽略，最后形成巨大技术债。

这和内容 2 是完全一致的。

---

##### 2. 但 tison 提出一个内容 2 没有充分展开的致命问题：
##### “你喂给模型的文档和经验，模型其实理解得并不好”

这是整组材料里最有价值的现实提醒之一。

tison 的核心判断是：

> **“告诉模型规则”不等于“模型真正会运用规则”。**

因为工程不是简单套模板，而是大量复杂 trade-off：

- 性能 vs 可维护性
- 抽象纯度 vs 交付效率
- 局部优化 vs 整体一致性
- 当前需求 vs 未来演化

人类中的优秀工程师，听懂原则后，往往能在新情境里举一反三；  
但模型即使“看过”这些规则，也常常不能稳定地迁移应用。

这意味着一个很关键的差异：

###### 人类学习是“内化规则”
###### 模型当前更多是“条件触发式模仿”

所以你会看到它：

- 这次懂了，下次又忘
- 这段对了，换个上下文就偏
- 刚刚接受 correction，过几轮又回到旧模式

这就是 tison 所说的：

> 模型像得了“阿尔兹海默症”一样，反复忘掉最佳实践。

这个说法虽然尖锐，但非常传神。

---

##### 3. 人和模型的真正差距：不是会不会说规则，而是能否稳定形成高质量闭环

tison 提了两个差距：

1. **聪明人的脑海回路、思考速度和反馈非常快**
2. **模型理论上也许能做到，但现实里还做不到**

这里不是在说模型不会写代码，而是在说：

- 它无法像优秀工程师一样形成稳定、持续、自我修正的高质量工程判断
- 它不能可靠地“记住团队共识”
- 它不能在复杂上下文下持续贯彻原则

这就导致一个非常现实的问题：

> 你可能花很大力气把模型调教到“在当前版本、当前上下文、当前项目里还能工作”，但模型一升级，很多东西又归零。

也就是说，**调教成本和收益比可能不划算。**

这和很多一线团队的感受一致：
prompt engineering 的收益不稳定，版本迭代还会破坏原有“手感”。

---

##### 4. 在高复杂度系统设计上，AI 的短板更明显

tison 在回复里补充得更具体：

他提到像这些东西：

- 动态资源管理
- server 整体设计
- 高层架构设计

这类问题的共同点是：

- 公开高质量语料少
- 开源方案本身质量参差不齐
- 很多“最佳实践”高度依赖上下文
- 决策标准不是显式可枚举规则，而是经验密集型判断

在这种领域，AI 很容易被“整体语料分布”带偏：

> 开源里普遍有问题的方案，AI 会误以为那就是正确方向。

而且 tison 说得很直接：

> 你在 prompt 上的微调，对抗不了语料的整体偏移。

这句话非常值得记住。  
因为它等于是在说：

- prompt 是局部干预
- 训练分布是全局引力
- 复杂工程决策里，后者往往更强

---

##### 5. 但 tison 也不是否定 AI，而是给出更准确的定位

他并没有说 agent 没用，而是给出一个很现实的评价：

###### Agent 的优点
- 平均水平高于很多普通人
- 不厌其烦
- 只要付费就愿意持续协作
- 能慢慢接管一些重复性、低风险、标准化工作

###### Agent 的局限
- 可靠性不如熟悉的优秀合作者
- 高层设计判断弱
- 记忆与收敛性差
- 难以“锁死”
- 在复杂、低语料、强 trade-off 问题上不稳定

这是非常成熟的判断：

> **Agent 不是“替代优秀工程师”的东西，而更像“高均值、低耐心成本、但不够稳定的执行体”。**

---

#### 四、两份内容的共识与张力

现在把两份内容并起来看。

---

##### 共识 1：AI Coding 的真正门槛不是“会不会 prompt”，而是“有没有工程化的反馈系统”

两份内容都在强调：

- 文档
- 测试
- lint
- 规范
- 约束
- CI
- 状态同步
- 架构明确

这些才是 agent 真正能发挥作用的基础设施。

也就是说，AI 编程的核心竞争力，不是“提示词写得玄不玄”，而是：

> **你能不能把团队的判断过程，工程化成机器可消费、可验证、可恢复、可同步的系统。**

---

##### 共识 2：过去被忽略的软件工程原则，现在变成了刚需

这点二者几乎完全一致。

以前你不写文档、不补测试、不固化架构决策，影响是慢性的；  
现在你一旦引入 agent，这些缺失会被指数级放大。

因为 agent 不是偶尔犯错，而是：

- 高频地产出
- 大规模地产出
- 一致性地重复错误
- 在缺乏约束时持续漂移

所以：

> **Agent 不是在减少工程纪律的重要性，而是在放大工程纪律缺失的灾难性。**

---

##### 共识 3：高层设计仍然离不开人

内容 2 比较乐观地说，LLM 让高层反馈也能一定程度闭环；  
但内容 1 进一步指出，现实中这还很有限，尤其在复杂系统设计上更明显。

所以综合后的更准确结论应该是：

> **LLM 已经能部分介入高层问题，但目前仍不足以独立承担高层架构与复杂 trade-off 决策；人的深度介入仍是必要的。**

---

##### 关键张力：问题到底主要在“你没外化知识”，还是“模型本身不够可靠”？

这是两篇最值得讨论的差异。

###### 内容 2 偏向：
如果 agent 做不好，多半是因为你没把标准外化。

###### 内容 1 偏向：
即便你外化了，模型也未必真懂、真记得、真能稳定执行。

这两者并不矛盾，但优先级不同。

更完整的理解应该是：

###### 第一层：没有外化知识，agent 一定做不好
- 这点内容 2 是对的

###### 第二层：即便外化了，agent 也不一定稳定做好
- 这点内容 1 补得非常关键

所以最终不是“写文档就解决了”，而是：

> **你不仅要外化知识，还要把它从‘说明材料’升级为‘执行协议与验证机制’，尽量减少对模型主观理解与长期记忆的依赖。**

这就自然连接到评论区里 Lemo 的实践。

---

#### 五、评论区里最有价值的补充：从 Prompt 思维升级到 Protocol 思维

Lemo 的回复其实是这组材料里最“落地”的工程答案之一。

他观察到：

> 解决“模型像阿尔兹海默症”的办法，不是依赖模型记忆，而是建立外部协议。

他们的做法包括：

1. **WAL（Write-Ahead Logging）**
   - agent 每次决策前先写日志
   - 重启后可以从日志恢复思路

2. **MEMORY.md**
   - 沉淀长期知识
   - 不依赖上下文窗口记忆

3. **STATUS.md**
   - agent 之间同步实时状态

他说得很本质：

> 把“软件工程经验”从 prompt 层抽离到协议层。prompt 对抗不了语料偏移，但协议可以。

这句话几乎可以当作这组材料的“方法论总结”。

---

##### 为什么这很重要？

因为它指出了一个方向转变：

###### Prompt 思维
- 觉得问题在于“我还没把话说明白”
- 于是不断补提示词、补规则、补描述

###### Protocol 思维
- 承认模型不可靠、易遗忘、易漂移
- 所以把关键知识放在模型外部
- 用结构化文件、状态机、日志、检查器、流程约束来固定行为

后者更像真正的软件工程，也更接近工业级可用路线。

---

#### 六、把整组内容提炼成一个统一框架

下面我给出一个统一理解框架，你可以拿它去看今天所有 Agentic Coding 讨论。

---

##### 1. 第一阶段：手工编程时代
特点：
- 人负责理解、决策、实现、验证
- 工具只辅助低层检查

瓶颈：
- 人工执行成本高
- 很多最佳实践因为成本高而被跳过

---

##### 2. 第二阶段：Agent 可执行时代
特点：
- agent 开始承担代码生成、局部重构、测试补齐、重复任务
- 工程师开始转向环境设计与反馈设计

机会：
- 产能放大
- 可并行
- 可持续运行
- 可覆盖很多标准化工作

风险：
- 错误被高速复制
- 架构漂移加速
- AI slop 堆积
- 版本变化导致调教失效

---

##### 3. 第三阶段：Harness / Protocol Engineering 时代
真正成熟的方向不是“更会 prompt”，而是：

- 设计期望状态
- 设计可观测信号
- 设计纠偏回路
- 设计长期记忆载体
- 设计多 agent 协议
- 设计不可突破的边界条件

也就是：

> **从“教模型”转向“约束系统”。**

---

##### 4. 第四阶段：人类角色重构
未来人的价值，越来越不在于：

- 亲手写每个函数
- 手动修每个小 bug

而在于：

- 定义什么是“对”
- 判断什么 trade-off 合理
- 决定系统边界与演化方向
- 设计 harness / protocol / feedback loop
- 在复杂、稀有、歧义、高风险问题上做最终裁决

这正是内容 2 结尾那句的意思：

> 你不需要比机器更会实现，你需要比机器更会评估。

但内容 1 会提醒你再补一句：

> 目前你还不能把评估也完全交给机器。

---

#### 七、对普通读者的通俗解读：这事到底像什么？

可以把今天的 AI 编程理解成：

##### 以前
你亲自开车，亲自踩油门、刹车、打方向盘。

##### 现在
你开始有自动驾驶辅助了。

但问题是，这个自动驾驶：

- 方向感有时不错
- 也不抱怨、不嫌累
- 但它会突然忘记刚学会的规则
- 容易在复杂路况下误判
- 你不能只靠口头提醒它“记得安全驾驶”

所以你真正该做的不是一直跟它吵：

- “你怎么又忘了！”
- “我不是刚告诉过你吗！”

而是去建设：

- 更清晰的道路标识
- 更稳定的护栏
- 更好的导航规则
- 更明确的交通约束
- 更可靠的报警与接管机制

也就是：

> **不要幻想把 AI 训练成一个永远可靠、全都记得的老司机；要把道路系统修成一个即使司机不完美，也不容易出大事的系统。**

这就是 harness engineering / protocol engineering 的本质。

---

#### 八、这组内容给团队的实际启发

如果你在带团队做 AI Coding，这里有几个很实际的结论。

##### 1. 不要把 AI 成败归因于 prompt 技巧
真正决定上限的是：

- 代码库是否规范
- 测试是否完备
- 架构边界是否明确
- 团队标准是否外化
- CI 反馈是否可解析
- 记忆与状态是否外置

---

##### 2. 文档不是给人看的“说明书”，而是给 agent 用的“控制面”
文档要从“叙述型”转向“执行型”：

- 什么情况下允许这样改
- 哪些依赖方向禁止
- 哪些模块不可穿透
- 性能指标与边界条件是什么
- 出错时优先遵循什么原则

---

##### 3. 能变成规则的，尽量不要只写在 prompt 里
优先级应该是：

1. 编译器 / 类型系统
2. 测试
3. lint / 静态分析
4. CI checks
5. 脚本化验证
6. 结构化协议文件
7. 最后才是 prompt 说明

因为越往下越“硬”，越不依赖模型理解力。

---

##### 4. 高风险、高 trade-off、高语义密度的决策，仍然要人做主
例如：

- 架构分层
- 资源调度策略
- 接口演化路线
- 核心抽象设计
- 大规模重构的方向判断

这些地方，AI 可以提供候选方案，但不应轻易自动化闭环。

---

##### 5. 把 agent 当成“高均值实习生 + 无限耐心执行器”，而不是“稳定资深同事”
这样预期会健康很多：

- 它能写很多
- 它能试很多
- 它不嫌烦
- 但你不能指望它真正记住组织经验并长期稳定贯彻

---

##### 6. 多 agent 系统的关键不是多，而是协议
如果多个 agent 没有：

- 状态同步
- 决策日志
- 长期记忆
- 职责分工
- 冲突解决

那只是把混乱并行化。

---

#### 九、最后给一个总括式总结

这两份内容合起来，可以形成这样一个非常完整的判断：

> **Agentic Coding 的本质，不是“AI 取代软件工程”，而是“AI 把软件工程中那些一直正确却常被偷懒跳过的实践，变成了不可回避的基础设施”。**

但同时：

> **今天的大模型还远不是一个能稳定理解、记忆、迁移复杂工程经验的“优秀同事”。它更像一个能力强但不稳定、会遗忘、会漂移的执行器。**

因此真正可行的路线不是：

- 迷信 prompt
- 迷信模型升级
- 迷信“喂文档就会了”

而是：

> **把经验从人脑和提示词中抽离出来，固化为文档、测试、规则、日志、状态、协议和反馈回路，让系统去约束模型，而不是指望模型自己变可靠。**

一句最短版总结：

> **未来工程师不是少写代码，而是更多在设计“让 AI 写对代码的系统”；而在这个过程中，人最不可替代的，仍然是对复杂 trade-off 的判断。**
