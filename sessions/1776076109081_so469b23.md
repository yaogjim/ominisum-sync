> **一句话点评**：这是一份约束力很强、执行性很高的调试操作手册，尤其适合纠正拍脑袋修 bug 的坏习惯。
>
> **摘要**：文章提出一套假设驱动调试流程：观察、假设、实验、结论，强调在写修复代码前必须先收集证据、列出多个假设、用最小实验验证，并将全过程记录到 DEBUG.md，最终补上真实修复与回归测试。

## 分析要点

- **核心高价值点**：最有价值的是把“禁止先写修复、必须先验证假设”制度化，并通过 5 行实验上限强迫问题拆解到可证伪粒度。
- **留存建议**：长期保留（提供高可复用的调试框架，适合在复杂 bug、CI 差异、性能回退等场景反复参考。）

**知识要点**

- 复杂 bug 应采用 Observe → Hypothesize → Experiment → Conclude 的闭环调试流程
- 每次至少列出 3-5 个假设，并分别写明支持证据、冲突证据和最小验证实验
- 实验应一次只改一个变量，且控制在 5 行以内，避免把诊断代码与生产修复混在一起
- 调试过程要持久化到 DEBUG.md，防止上下文丢失并保留调查轨迹
- 确认根因后必须补充回归测试，防止问题再次出现

**行动项**

- 在自己的项目中建立 DEBUG.md 模板，按 Observations、Hypotheses、Experiments、Root Cause、Fix 分节记录
- 遇到第二次修复失败或环境差异类问题时，强制切换到该流程，不再直接尝试新修复
- 把“单变量最小实验”和“先证伪再修复”纳入个人或团队调试规范
- 为复杂 bug 的最终修复补充回归测试，形成可重复验证的闭环

name debug-hypothesis

description Use when debugging any non-trivial bug — wrong output, crash, flaky test, performance regression, or "it works locally but not in CI." Forces a scientific-method loop (Observe → Hypothesize → Experiment → Conclude) so the agent stops guessing and starts reasoning. Prevents the

#### Hypothesis-Driven Debugging

A four-phase loop that turns debugging from "try random fixes and hope" into a disciplined investigation. Each phase has a goal, hard rules, and a rationalization table for the excuses an agent will invent to skip it.

The core principle: **you may not write a fix until you have evidence that your hypothesis is correct.** Guessing is not debugging.

- A test fails and the cause is not immediately obvious
- The same bug has been "fixed" twice and came back
- The agent tried a fix that didn't work — stop it from trying another
- A crash or error message you haven't seen before
- Performance regression with no obvious culprit
- Behavior differs between environments (local vs CI, dev vs prod)
- The agent is stuck in a loop, applying the same wrong fix

- Typos, missing imports, or syntax errors — just fix them
- Build failures with an obvious single-line cause
- Compiler/linter messages that tell you exactly what and where
- You already know the root cause and just need to write the fix

If the bug survived one fix attempt, switch to this skill immediately.

```
OBSERVE  ──▶  HYPOTHESIZE  ──▶  EXPERIMENT  ──▶  CONCLUDE
     │              │                  │               │
     ▼              ▼                  ▼               ▼
  Gather          List 3-5         One minimal       Root cause
  symptoms,       possible         test per          confirmed
  reproduce       causes +         hypothesis,       or loop
  reliably        evidence         max 5 lines       back
     │              │                  │               │
     └──────────────┴──────────────────┴───────────────┘
              write everything to DEBUG.md
```

Hard rules:

1. Everything gets written to `DEBUG.md`. Context compaction will eat your reasoning if it only lives in the conversation.
2. You may not write fix code during Observe, Hypothesize, or Experiment.
3. You may not skip Hypothesize. "I think I know what it is" is a hypothesis — write it down and test it like the others.
4. Each experiment changes at most 5 lines. If your experiment needs more, your hypothesis is too vague — split it.

**Goal.** Collect raw facts. Reproduce the bug. Separate what you *know* from what you *assume*.

**Steps.**

1. Reproduce the bug. Get the exact error message, stack trace, or wrong output. If you cannot reproduce it, that is your first finding.
2. Find the minimal reproduction. Strip away unrelated code until the bug still appears.
3. Record the environment: OS, runtime version, dependencies, config.
4. Note what *does* work. The boundary between working and broken is where the bug lives.
5. Write all observations to `DEBUG.md` under `## Observations`.

**Exit criteria.**

- Bug reproduced (or documented as non-reproducible with conditions)
- Exact error message or wrong behavior recorded
- Minimal reproduction identified
- Observations written to `DEBUG.md`

**Common Rationalizations**

Excuse Reality

"I already know what's wrong" Then write it as a hypothesis and prove it. If you're right, it takes 2 minutes.

"Let me just try this quick fix first" That's how you end up 45 minutes deep with 6 failed attempts.

"The error message is clear enough" Error messages describe symptoms, not causes. `NullPointerException` tells you what died, not why.

"I don't need to reproduce it, I can see the bug in the code" Can you? Then why hasn't it been fixed yet?

**Goal.** Generate 3-5 possible root causes. For each, list supporting and conflicting evidence from Phase 1. Rank by likelihood.

**Steps.**

1. List 3-5 hypotheses. Not 1. Not "I think it's X." Three minimum. Think across categories:
   - Data: wrong input, missing field, type mismatch, encoding
   - Logic: wrong condition, off-by-one, race condition, wrong order
   - Environment: config, version, dependency, permissions
   - State: stale cache, leaked state, initialization order
2. For each hypothesis, write:
   - **Supports:** evidence from observations that backs this theory
   - **Conflicts:** evidence that argues against it
   - **Test:** the minimal experiment that would prove or disprove it
3. Mark the **ROOT HYPOTHESIS** — the one with supporting evidence and no conflicting evidence. If multiple qualify, pick the easiest to test.
4. Write everything to `DEBUG.md` under `## Hypotheses`.

**Example format in DEBUG.md:**

```
## Hypotheses

### H1: Race condition in session middleware (ROOT HYPOTHESIS)
- Supports: only happens under concurrent requests, timing-dependent
- Conflicts: none yet
- Test: add mutex lock around session read, check if bug disappears

### H2: Stale cache returning expired token
- Supports: works after restart (cache cleared)
- Conflicts: cache TTL is 5min, bug appears within 30s
- Test: disable cache, reproduce

### H3: Wrong env variable in CI
- Supports: works locally, fails in CI
- Conflicts: env diff shows identical values
- Test: print actual runtime value in CI logs
```

**Exit criteria.**

- At least 3 hypotheses written
- Each has supporting/conflicting evidence
- Each has a specific, minimal test
- ROOT HYPOTHESIS identified
- All written to `DEBUG.md`

**Common Rationalizations**

Excuse Reality

"I only have one theory" You have one *favorite* theory. Think harder. What if it's not that?

"Writing this down is slow" Debugging without writing is slower. You'll forget hypothesis 2 after compaction eats it.

"The first hypothesis is obviously right" Then proving it takes 2 minutes. If you skip proof, you'll spend 30 minutes when it turns out wrong.

"I don't have conflicting evidence" That means you haven't looked hard enough, or it really is the root cause. Either way, test it.

**Goal.** Test the ROOT HYPOTHESIS with the smallest possible change. You are a scientist — you are trying to **falsify**, not confirm.

**Steps.**

1. Write the experiment before running it. What will you change? What result confirms the hypothesis? What result rejects it?
2. Make the change. **Maximum 5 lines.** If you need more, your hypothesis is too vague.
3. Run the reproduction from Phase 1.
4. Record the result in `DEBUG.md` under `## Experiments`.

**Experiment rules.**

- One variable at a time. Do not combine two fixes "to save time."
- Do not write production fix code. Write diagnostic code: log statements, assertions, simplified logic, hardcoded values.
- Revert the experiment after recording results. Keep the tree clean.
- If the experiment is inconclusive, that's a result — record it and test the next hypothesis.

**Exit criteria.**

- Experiment executed (one change, one variable)
- Result recorded: confirmed, rejected, or inconclusive
- Experimental code reverted
- Results written to `DEBUG.md`

**Common Rationalizations**

Excuse Reality

"Let me just fix it instead of testing" Fixing without confirming the cause is how you ship a wrong fix that breaks something else.

"I'll test two things at once to save time" When both change and the bug disappears, which one fixed it? Now you have to test again.

"5 lines isn't enough" 5 lines is enough to add a log, an assertion, a hardcoded value, or a short-circuit. If it isn't, your hypothesis is "something is wrong somewhere" — not a hypothesis.

"I don't need to revert, the fix is basically the experiment" The experiment is diagnostic. The fix is production code. They have different quality bars.

**Goal.** Confirm root cause, write the real fix, and add a regression test.

**Steps.**

1. If ROOT HYPOTHESIS confirmed:
   - Write the **root cause** in one sentence in `DEBUG.md`.
   - Now — and only now — write production fix code.
   - Add a regression test that fails without the fix and passes with it.
   - Commit fix and test together.
2. If ROOT HYPOTHESIS rejected:
   - Record the rejection and evidence in `DEBUG.md`.
   - Promote the next hypothesis to ROOT. Return to Phase 3.
   - If all hypotheses rejected, return to Phase 1 with new observations.
3. Update `DEBUG.md` with the final `## Root Cause` and `## Fix` sections.

**Exit criteria.**

- Root cause identified and written in one sentence
- Fix committed
- Regression test committed
- `DEBUG.md` complete with full investigation trail
- Original reproduction case now passes

**Common Rationalizations**

Excuse Reality

"I don't need a regression test, it's a simple fix" Simple fixes for simple bugs don't need this skill. You're here because it wasn't simple. Add the test.

"The DEBUG.md is just for debugging, I'll delete it" Keep it. Future-you debugging the same area will thank present-you.

"All hypotheses failed, I'm stuck" Go back to Observe. You missed something. The bug exists, therefore a cause exists.

The #1 failure mode of AI debugging: the agent forms a theory, writes 150 lines of "fix" code, it doesn't work, so it writes another 150 lines going deeper into the same wrong theory.

**This skill exists to prevent that.** If you catch yourself or the agent:

- Writing more than 5 lines before confirming a hypothesis → STOP. Back to Phase 2.
- Trying the same approach a second time → STOP. The hypothesis is rejected. Next one.
- Ignoring conflicting evidence → STOP. Write it down. Re-rank hypotheses.
- Feeling "almost there" after 3 failed attempts → STOP. You are bulldozing.

Write it down. Test it. Prove it. Then fix it.

#### 假设驱动调试：把 “瞎猜修 Bug” 变成科学排查

##### 核心观点

这篇文章的核心只有一句话：**在没有证据证明原因之前，不要急着写修复代码。**

作者提出了一套 “科学方法式调试” 流程，用来解决复杂 Bug，比如：错误输出、崩溃、偶发测试失败、性能回退、线上和本地表现不一致等。目标是避免开发者或 AI 代理陷入 “猜一个、改一版、不行再继续猜” 的低效循环。

---

##### 四步调试法

###### 1. 观察问题：先搞清楚 “现象是什么”

第一步不是修，而是**收集事实**：

- 复现 Bug，拿到准确报错、堆栈或异常表现
- 找到最小复现路径，剥离无关代码
- 记录环境信息，如系统、运行时、依赖、配置
- 明确 “哪里正常、哪里不正常”

本质上，这一步是在区分：**什么是已知事实，什么只是主观猜测。**

---

###### 2. 提出假设：不要只有一个答案

文章强调，调试时必须提出**3-5 个可能原因**，而不是只盯着自己最先想到的那个。

每个假设都要写清楚三件事：

- **支持证据**：哪些观察结果支持它
- **冲突证据**：哪些现象和它不一致
- **验证方法**：如何用一个最小实验验证它

然后从中选出一个 “最值得先测的核心假设”。  
这一步的意义是：**防止思维过早收敛，避免一路沿着错误方向越改越深。**

---

###### 3. 做实验：一次只验证一个变量

验证阶段要求非常严格：

- 每次实验最多改**5 行代码**
- 只测试**一个变量**
- 先写清楚 “改什么、预期结果是什么、什么结果算否定”
- 做的是**诊断性修改**，不是正式修复
- 实验结束后要回滚，保持代码干净

重点不是 “证明自己是对的”，而是**尽量推翻当前假设**。  
如果实验结果不明确，也算有效结果，要记录下来，再测试下一个假设。

---

###### 4. 下结论：确认根因后再正式修

只有当核心假设被证实后，才能进入真正修复阶段。此时要做三件事：

- 用一句话写清楚根因
- 写正式修复代码
- 补一个回归测试，确保问题不会再出现

如果当前假设被否定，就回到假设列表，换下一个继续测；如果所有假设都被否定，就回到 “观察” 阶段，说明前面的信息还不够。

---

##### 这套方法为什么有效

###### 1. 它专治 “越改越乱”

文章指出，AI 或开发者最常见的失败模式是：

- 先拍脑袋猜一个原因
- 直接写大段修复代码
- 发现没用后，再继续在同一路线上加码
- 最后写了很多代码，却离根因越来越远

这套方法的价值就在于：**强迫你慢下来，用证据而不是直觉推进。**

###### 2. 它能降低复杂问题的排查成本

很多复杂 Bug 不是 “不会修”，而是**太早开始修**。  
一旦没有先复现、先建假设、先做小实验，就很容易浪费大量时间在错误方向上。

###### 3. 它特别适合非确定性问题

像下面这些问题最适合用这套方法：

- 本地正常、CI 异常
- 偶发失败
- 性能突然下降
- 同一个 Bug 修过两次还会回来
- 报错看得懂，但根因并不清楚

---

##### 关键规则

###### 1. 全程记录到`DEBUG.md`

作者要求把观察、假设、实验、结论全部写到`DEBUG.md`。  
原因很现实：**如果不写下来，人和 AI 都会在上下文切换中丢失推理过程。**

###### 2. 在确认原因前，禁止写正式修复

“我大概知道原因了” 不算确认。  
只要还没验证，就仍然只是一个假设。

###### 3. 每次实验必须足够小

如果一个实验需要改很多代码，通常说明不是实验太复杂，而是**假设本身太模糊**。

---

##### 作者真正想解决的问题

这篇文章不是单纯教 “怎么调 Bug”，而是在纠正一种非常常见的工作方式：

> 把调试当成凭经验蒙答案，而不是基于证据做推理。

它希望建立一种纪律：

- 先观察
- 再假设
- 再实验
- 最后修复

一句话概括：**不要靠直觉堆代码，要像科学家一样排查问题。**

---

##### 一句话总结

###### 调试的本质，不是 “赶紧修”，而是先用证据确认 “为什么坏了”，再精准下手。

### 2026-04-13 10:29:44

#### 用 “假设驱动调试” 处理一个具体 Bug 的最佳实践

下面我基于你提供的`debug-hypothesis`方法，给出一个更落地的实例，并在这个实例之上总结一套可直接执行的最佳实践。

---

##### 一、先用一句话概括这套方法

**在没有证据前，不写正式修复代码。**  
必须按`Observe → Hypothesize → Experiment → Conclude`的循环推进，把每一步都写进`DEBUG.md`，避免 “拍脑袋修 bug”。

---

##### 二、具体实例

###### 场景

一个 Node.js Web 服务在本地运行正常，但在 CI 里测试偶发失败。

###### 失败现象

测试偶尔报错：

```txt
Expected status 200, received 401
```

相关接口是：

```txt
POST /api/profile
```

本地连续跑 20 次只有 1 次失败，CI 中几乎每次都失败。

---

##### 三、按方法完整走一遍

---

##### 1. Observe：先观察，不急着修

###### 观察到的事实

将这些写入`DEBUG.md`：

```md
## Observations

- 接口`/api/profile`在本地大多数时候通过，但偶发返回 401
- 在 CI 中失败频率明显更高
- 失败只出现在并发测试时，单独跑这个测试通常能通过
- 服务重启后第一次执行更容易成功
- 报错不是 500，而是 401，说明请求到了鉴权层
- 本地 Node.js 版本为 20.11，CI 为 20.10
```

###### 最小复现

最小复现不是整个测试套件，而是：

- 只保留登录
- 只保留一次 token 写入
- 并发发送多个`/api/profile`请求

###### 这一阶段的最佳实践

- **记录 “确切症状”，不要写解释**  
  例如写 “返回 401”，不要写 “鉴权缓存肯定坏了”。

- **先缩小复现范围，再分析原因**  
  如果不先做最小复现，后续实验会被太多变量污染。

- **记录 “什么是正常的”**  
  比如单请求正常、并发请求失败，这个边界特别关键。

- **记录环境差异，但不要立刻下结论**  
  本地和 CI 版本不同是事实，但不是原因本身。

---

##### 2. Hypothesize：至少列出 3 个假设

很多人到这一步最容易犯错：  
“我觉得就是缓存问题。”  
这不够，必须至少列出多个候选原因。

###### 示例假设

```md
## Hypotheses

### H1: 会话缓存存在并发读写竞争（ROOT HYPOTHESIS）
- Supports:
  - 只在并发测试时更容易出现
  - 重启后第一次更容易成功，像是状态污染
- Conflicts:
  - 单线程下大多数请求正常
- Test:
  - 在读取 session 时临时改成直接读数据库，绕过缓存，看 401 是否消失

### H2: CI 环境的密钥配置不一致
- Supports:
  - 本地稳定，CI 不稳定
- Conflicts:
  - 如果密钥错误，理论上应该全部失败，而不是偶发失败
- Test:
  - 打印运行时使用的 JWT secret 摘要值进行比对

### H3: token 过期时间计算存在时区 / 时间漂移问题
- Supports:
  - CI 机器时间和本地环境可能存在微小差异
- Conflicts:
  - 失败集中在并发场景，不完全像时间问题
- Test:
  - 临时把 token 有效期延长到 1 小时，观察失败是否消失

### H4: 测试之间共享了全局鉴权状态
- Supports:
  - 失败具有 “偶发” 和 “顺序相关” 特征
- Conflicts:
  - 单独运行该测试时大多通过
- Test:
  - 禁止测试并发执行，或在每个测试前清理全局状态
```

###### 为什么 H1 作为 ROOT HYPOTHESIS

因为它：

- 有直接支持证据
- 当前没有强冲突证据
- 可以用一个很小的实验验证

###### 这一阶段的最佳实践

- **假设要覆盖不同类别**  
  不要全是 “缓存问题的不同版本”。  
  应覆盖：数据、逻辑、环境、状态、并发。

- **每个假设都必须包含 “支持证据” 和 “冲突证据”**  
  只写支持，不写冲突，很容易自我确认偏差。

- **优先选最容易被证伪的假设做 ROOT**  
  不是选你最喜欢的，而是选最容易验证的。

- **测试设计要具体到一条动作和一个预期**  
  例如 “绕过缓存后，如果问题消失，则 H1 更可信”。

---

##### 3. Experiment：做最小实验，而不是直接改代码

###### 实验设计

先写进`DEBUG.md`：

```md
## Experiments

### E1 for H1
- Change:
  - 在 session 校验代码中，临时绕过内存缓存，直接查询数据库
- Confirm if:
  - 并发测试中的 401 消失
- Reject if:
  - 401 仍然同样频繁出现
```

###### 实验执行

只改很少几行诊断代码，例如伪代码：

```js
//diagnostic only: bypass cache to isolate whether cache is the culprit
const session = await db.getSession (token);
```

跑最小复现后，结果：

- 本地连续 50 次全部通过
- CI 中失败消失

###### 记录实验结果

```md
### E1 Result
- Outcome: Confirmed
- Evidence:
  - 本地并发 50 次无失败
  - CI 中原有 401 未再出现
- Conclusion:
  - 问题与 session 缓存逻辑强相关
```

###### 这一阶段的最佳实践

- **实验代码不是修复代码**  
  实验只是为了确认因果关系，不要求优雅、完整、可上线。

- **一次只改一个变量**  
  不要同时改缓存、token 时间、测试并发度，否则无法定位原因。

- **每个实验都必须可被 “否定”**  
  真正好的实验不是为了证明自己对，而是为了让自己有机会被证伪。

- **实验后要回滚诊断代码**  
  生产修复应该在根因确认后另写。

- **如果实验需要改很多代码，说明假设太模糊**  
  例如 “系统某处有状态问题” 就不是好假设。

---

##### 4. Conclude：确认根因后再写正式修复

###### 根因结论

```md
## Root Cause

session 缓存在并发请求下发生了覆盖，导致部分请求读取到过期或空的 session，从而返回 401。
```

###### 正式修复思路

这时才写真正修复，例如：

- 让缓存写入具备原子性
- 避免共享可变对象
- 在 session 读取过程中使用不可变快照
- 修正测试中的全局状态污染

###### 回归测试

必须补一个回归测试，例如：

```js
it ("should authenticate concurrent profile requests without random 401", async () => {
  const token = await loginAndGetToken ();

  const results = await Promise.all (
    Array.from ({ length: 20 }, () =>
      request (app)
        .post ("/api/profile")
        .set ("Authorization", `Bearer ${token}`)
    )
  );

  results.forEach ((res) => {
    expect (res.status).toBe (200);
  });
});
```

###### 这一阶段的最佳实践

- **根因必须能用一句话说清楚**  
  如果一句话说不清，说明你可能还没真正定位。

- **修复和回归测试一起提交**  
  没有回归测试的修复，未来很容易再次复发。

- **回归测试必须能在 “无修复时失败，有修复时通过”**  
  否则它不是真正的回归测试。

- **保留`DEBUG.md`调查记录**  
  后续碰到同类问题时价值很高。

---

#### 四、在这个实例之上的最佳实践清单

##### 1. 先写事实，再写理论

错误做法：

```md
- 缓存肯定有问题
```

正确做法：

```md
- 并发时更容易出现 401
- 绕过缓存后问题消失
```

**最佳实践：**
- 观察阶段只记录现象
- 假设阶段才写解释
- 结论阶段才确认根因

---

##### 2. 假设一定要 “可测试”

坏假设：

```md
- 系统某处状态不对
```

好假设：

```md
- session 缓存对象被并发请求共享并覆盖
- 测试：绕过缓存直接查数据库
```

**最佳实践：**
- 假设必须具体到组件、行为、验证方式
- 每个假设都要能被一个小实验验证或否定

---

##### 3. ROOT HYPOTHESIS 不等于 “最像” 的那个，而是 “最值得先测” 的那个

很多人喜欢先测自己最相信的。  
更好的做法是优先选择：

- 有支持证据
- 冲突证据最少
- 成本最低
- 最容易被证伪

**最佳实践：**
- 先做便宜且信息量大的实验
- 用实验效率，而不是主观感觉，决定顺序

---

##### 4. 实验必须尽量小

根据原方法，实验改动最多 5 行，这是很强的约束，价值很大。

**为什么有效：**
- 改动越小，变量越少
- 越容易回滚
- 越不容易误把 “修复” 当 “验证”

**最佳实践：**
- 优先用日志、断言、短路、硬编码值做诊断
- 不要在实验阶段重构代码
- 不要把实验顺手做成正式方案

---

##### 5. 看到 “偶发”“只在 CI”“重启后恢复” 这些词时，优先考虑状态与环境

在这个案例里，并发、偶发、重启后缓解，都是典型信号。

**最佳实践：**
- `偶发`：优先考虑竞态、共享状态、时间依赖
- `只在 CI`：优先考虑环境差异、执行顺序、并行度、资源限制
- `重启后恢复`：优先考虑缓存、初始化、残留状态
- `只有某些请求失败`：优先考虑输入差异、边界条件、并发冲突

---

##### 6. 不要连续尝试两个 “看起来差不多” 的修复

比如：

- 先改缓存键名
- 不行再改缓存过期时间
- 再不行改 session 初始化顺序

这类行为看似推进，实际上可能一直困在同一个错误假设里。

**最佳实践：**
- 一个假设被实验否定后，就降级处理
- 转向下一个假设，而不是在同一理论上继续 “深挖”
- 连续两次同方向失败时，强制回到 Observe

---

##### 7. `DEBUG.md`不是文档负担，而是调试记忆体

这个方法特别强调把所有内容写进`DEBUG.md`，原因非常现实：

- 人会忘记
- 对话会丢上下文
- 多轮尝试后很容易重复做过的实验

**最佳实践模板：**

```md
# DEBUG.md

## Observations
- ...

## Hypotheses
### H1: ...
- Supports:
- Conflicts:
- Test:

### H2: ...
- Supports:
- Conflicts:
- Test:

## Experiments
### E1 for H1
- Change:
- Confirm if:
- Reject if:
- Result:

## Root Cause
- ...

## Fix
- ...

## Regression Test
- ...
```

---

#### 五、这套方法最适合解决什么问题

特别适合：

- 非显而易见的失败
- 修过一次又复发的问题
- 本地正常、CI 异常
- 偶发失败、并发错误、性能回退
- 你已经试过一个修复但没生效的情况

不太需要这么重的方法的场景：

- 拼写错误
- 缺少 import
- 编译器明确指出哪一行错了
- 你已经 100% 确认根因，只差落代码

---

#### 六、最后给出一份浓缩版最佳实践

##### 可直接照着执行的版本

1. **先复现，再推测**  
   没有稳定复现，就没有可靠修复。

2. **观察只写事实，不写解释**  
   把 “看到什么” 和 “你认为为什么” 分开。

3. **至少列 3 个假设**  
   防止过早锁定单一思路。

4. **每个假设都写支持、冲突、测试方法**  
   不让自己只看有利证据。

5. **一次只做一个最小实验**  
   改一个变量，拿一个结论。

6. **实验代码和正式修复分离**  
   先证明，再修复。

7. **确认根因后补回归测试**  
   否则只是 “这次看起来好了”。

8. **全过程写入`DEBUG.md`**  
   避免重复尝试，也方便团队协作。
