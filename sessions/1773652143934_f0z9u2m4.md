#### Lightpanda Browser

**The headless browser built from scratch for AI agents and automation.**  
Not a Chromium fork. Not a WebKit patch. A new browser, written in Zig.

[![](https://camo.githubusercontent.com/4d1ff47d93f798f4e0d63a1bbe16ed6f5d1a828aeb6aeb2c9a49ed08b60fc724/68747470733a2f2f63646e2e6c6967687470616e64612e696f2f6173736574732f696d616765732f6769746875622f657865637574696f6e2d74696d652e737667)](https://github.com/lightpanda-io/demo) [![](https://camo.githubusercontent.com/b2426706413dd00286473780ec93191a02ac56fe32545e7d63e4d70f0df82d42/68747470733a2f2f63646e2e6c6967687470616e64612e696f2f6173736574732f696d616765732f6769746875622f6d656d6f72792d6672616d652e737667)](https://github.com/lightpanda-io/demo)

*Puppeteer requesting 100 pages from a local website on a AWS EC2 m5.large instance. See [benchmark details](https://github.com/lightpanda-io/demo).*

Lightpanda is the open-source browser made for headless usage:

- Javascript execution
- Support of Web APIs (partial, WIP)
- Compatible with Playwright 1, Puppeteer, chromedp through [CDP](https://chromedevtools.github.io/devtools-protocol/)

Fast web automation for AI agents, LLM training, scraping and testing:

- Ultra-low memory footprint (9x less than Chrome)
- Exceptionally fast execution (11x faster than Chrome)
- Instant startup

The Lightpanda browser is compatible to run on windows inside WSL. Follow the Linux instruction for installation from a WSL terminal. It is recommended to install clients like Puppeteer on the Windows host.

docker run -d --name lightpanda -p 9222:9222 lightpanda/browser:nightly

Once the CDP server started, you can run a Puppeteer script by configuring the `browserWSEndpoint`.

```
'use strict'

import puppeteer from 'puppeteer-core';

// use browserWSEndpoint to pass the Lightpanda's CDP server address.
const browser = await puppeteer.connect({
  browserWSEndpoint: "ws://127.0.0.1:9222",
});

// The rest of your script remains the same.
const context = await browser.createBrowserContext();
const page = await context.newPage();

// Dump all the links from the page.
await page.goto('https://demo-browser.lightpanda.io/amiibo/', {waitUntil: "networkidle0"});

const links = await page.evaluate(() => {
  return Array.from(document.querySelectorAll('a')).map(row => {
    return row.getAttribute('href');
  });
});

console.log(links);

await page.close();
await context.close();
await browser.disconnect();
```

##### Telemetry

By default, Lightpanda collects and sends usage telemetry. This can be disabled by setting an environment variable `LIGHTPANDA_DISABLE_TELEMETRY=true`. You can read Lightpanda's privacy policy at: [https://lightpanda.io/privacy-policy](https://lightpanda.io/privacy-policy).

Lightpanda is in Beta and currently a work in progress. Stability and coverage are improving and many websites now work. You may still encounter errors or crashes. Please open an issue with specifics if so.

Here are the key features we have implemented:

- HTTP loader ([Libcurl](https://curl.se/libcurl/))
- HTML parser ([html5ever](https://github.com/servo/html5ever))
- DOM tree
- Javascript support ([v8](https://v8.dev/))
- DOM APIs
- Ajax
  - XHR API
  - Fetch API
- DOM dump
- CDP/websockets server
- Click
- Input form
- Cookies
- Custom HTTP headers
- Proxy support
- Network interception
- Respect `robots.txt` with option `--obey_robots`

NOTE: There are hundreds of Web APIs. Developing a browser (even just for headless mode) is a huge task. Coverage will increase over time.

##### Prerequisites

Lightpanda is written with [Zig](https://ziglang.org/) `0.15.2`. You have to install it with the right version in order to build the project.

Lightpanda also depends on [v8](https://chromium.googlesource.com/v8/v8.git),[Libcurl](https://curl.se/libcurl/) and [html5ever](https://github.com/servo/html5ever).

To be able to build the v8 engine, you have to install some libs:

For **Debian/Ubuntu based Linux**:

```
sudo apt install xz-utils ca-certificates \
    pkg-config libglib2.0-dev \
    clang make curl git
```

You also need to [install Rust](https://rust-lang.org/tools/install/).

For systems with [**Nix**](https://nixos.org/download/), you can use the devShell:

```
nix develop
```

For **MacOS**, you need cmake and [Rust](https://rust-lang.org/tools/install/).

```
brew install cmake
```

You an build the entire browser with `make build` or `make build-dev` for debug env.

But you can directly use the zig command: `zig build run`.

Lighpanda uses v8 snapshot. By default, it is created on startup but you can embed it by using the following commands:

Generate the snapshot.

```
zig build snapshot_creator -- src/snapshot.bin
```

Build using the snapshot binary.

```
zig build -Dsnapshot_path=../../snapshot.bin
```

See [#1279](https://github.com/lightpanda-io/browser/pull/1279) for more details.

##### Unit Tests

You can test Lightpanda by running `make test`.

To run end to end tests, you need to clone the [demo repository](https://github.com/lightpanda-io/demo) into `../demo` dir.

You have to install the [demo's node requirements](https://github.com/lightpanda-io/demo?tab=readme-ov-file#dependencies-1)

You also need to install [Go](https://go.dev) &gt; v1.24.

```
make end2end
```

Lightpanda is tested against the standardized [Web Platform Tests](https://web-platform-tests.org/).

We use [a fork](https://github.com/lightpanda-io/wpt/tree/fork) including a custom [`testharnessreport.js`](https://github.com/lightpanda-io/wpt/commit/01a3115c076a3ad0c84849dbbf77a6e3d199c56f).

For reference, you can easily execute a WPT test case with your browser via [wpt.live](https://wpt.live).

To run the test, you must clone the repository, configure the custom hosts and generate the `MANIFEST.json` file.

Clone the repository with the `fork` branch.

```
git clone -b fork --depth=1 git@github.com:lightpanda-io/wpt.git
```

Enter into the `wpt/` dir.

Install custom domains in your `/etc/hosts`

```
./wpt make-hosts-file | sudo tee -a /etc/hosts
```

Generate `MANIFEST.json`

```
./wpt manifest
```

Use the [WPT's setup guide](https://web-platform-tests.org/running-tests/from-local-system.html) for details.

An external [Go](https://go.dev) runner is provided by [github.com/lightpanda-io/demo/](https://github.com/lightpanda-io/demo/) repository, located into `wptrunner/` dir. You need to clone the project first.

First start the WPT's HTTP server from your `wpt/` clone dir.

```
./wpt serve
```

Run a Lightpanda browser

```
zig build run -- --insecure_disable_tls_host_verification
```

Then you can start the wptrunner from the Demo's clone dir:

```
cd wptrunner && go run .
```

Or one specific test:

```
cd wptrunner && go run . Node-childNodes.html
```

`wptrunner` command accepts `--summary` and `--json` options modifying output. Also `--concurrency` define the concurrency limit.

⚠️ Running the whole test suite will take a long time. In this case, it's useful to build in `releaseFast` mode to make tests faster.

```
zig build -Doptimize=ReleaseFast run
```

#### Why?

In the good old days, scraping a webpage was as easy as making an HTTP request, cURL-like. It’s not possible anymore, because Javascript is everywhere, like it or not:

- Ajax, Single Page App, infinite loading, “click to display”, instant search, etc.
- JS web frameworks: React, Vue, Angular &amp; others

If we need Javascript, why not use a real web browser? Take a huge desktop application, hack it, and run it on the server. Hundreds or thousands of instances of Chrome if you use it at scale. Are you sure it’s such a good idea?

- Heavy on RAM and CPU, expensive to run
- Hard to package, deploy and maintain at scale
- Bloated, lots of features are not useful in headless usage

If we want both Javascript and performance in a true headless browser, we need to start from scratch. Not another iteration of Chromium, really from a blank page. Crazy right? But that’s what we did:

- Not based on Chromium, Blink or WebKit
- Low-level system programming language (Zig) with optimisations in mind
- Opinionated: without graphical rendering

#### Lightpanda 是什么

Lightpanda 是一个专门为 AI 代理和自动化场景打造的无头浏览器，从零开始用 Zig 编写，不是 Chromium 或 WebKit 的改造版。它主打“更轻、更快、更适合大规模服务器运行”，尤其适合抓取、测试、LLM 训练和网页自动化。

##### 1. 项目定位：为什么要重新造一个无头浏览器

- Lightpanda 的核心目标，是解决传统浏览器在服务器自动化场景中的“又重又贵”问题。
- 项目强调自己：
  - **不是 Chromium 分叉**
  - **不是 WebKit 补丁**
  - **而是一个全新的浏览器内核**
- 它面向的主要场景包括：
  - AI agents（AI 智能体）
  - LLM 训练
  - 网页抓取
  - 自动化测试

###### 为什么需要它
原文认为，过去抓网页只要发一个 HTTP 请求就够了，但现在网页大量依赖 JavaScript，出现了很多传统抓取方式难以处理的情况，比如：

- Ajax 异步加载
- 单页应用（SPA）
- 无限滚动
- 点击后显示内容
- 即时搜索
- React、Vue、Angular 等前端框架

因此，如果既想支持 JavaScript，又想保持高性能，就需要一个真正为“无头”场景设计的浏览器，而不是把桌面浏览器硬搬到服务器上。

---

##### 2. 主要优势：比 Chrome 更省资源、更快

项目 README 给出了非常直接的性能卖点：

- **内存占用比 Chrome 少 9 倍**
- **执行速度比 Chrome 快 11 倍**
- **启动几乎是即时的**

###### 性能测试背景
- 基准示例提到：使用 **Puppeteer** 在 **AWS EC2 m5.large** 实例上请求本地网站的 **100 个页面**
- README 中把这些数据作为 Lightpanda 相对 Chrome 的核心性能证明

这些数字说明它特别适合需要同时跑很多浏览器实例的场景，因为这类场景最怕的就是 RAM 和 CPU 成本过高。

---

##### 3. 当前能力：已经支持哪些功能

虽然项目还在 Beta 阶段，但已经实现了一批对自动化很关键的基础能力：

- HTTP 加载器（基于 **Libcurl**）
- HTML 解析器（基于 **html5ever**）
- DOM 树
- JavaScript 支持（基于 **v8**）
- DOM API
- Ajax / XHR API
- Fetch API

###### Playwright 的特别说明
README 专门写了一个 **Playwright 支持免责声明**，意思是：

- 某个脚本当前能跑，不代表未来版本也一定能跑
- 原因不是“功能退化”，而是 Playwright 会根据浏览器能力动态选择不同执行路径
- 一旦 Lightpanda 新增了某些 Web API，Playwright 可能会改走另一条代码路径
- 而那条新路径又可能依赖 Lightpanda 还没完全实现的功能

换句话说，**兼容性变化可能来自“支持变多了”，而不是“支持变少了”**。这是一个比较少见但很真实的浏览器适配问题。

## 产品-技术开发（1）

### 2026-03-16 09:11:38

这是一个很典型的 “为 AI 和自动化重构浏览器底座” 的产品，不是在做一个更快的 Chrome，而是在做一个更适合 agent、爬取、训练、批处理自动化的执行引擎。

**产品解读**
- 核心定位很准：不是 “通用浏览器”，而是 “AI / 自动化专用 headless browser”。这让它能主动放弃 GUI、兼容包袱和大量非必要能力，换取启动速度、内存占用和部署效率。
- 真正的目标用户不是前端开发者，而是 4 类人：AI Agent 平台、网页数据采集、自动化测试平台、LLM 训练 / 数据管道团队。
- 它打的是 Chrome 的结构性弱点：Chrome 适合人用和全功能兼容，不适合海量并发、低成本、容器化、按任务瞬时拉起。
- “9x less memory、11x faster” 如果在真实 workload 下稳定成立，商业价值非常直接：同一台机器可跑更多 session，单任务成本更低，冷启动更快，Agent orchestration 更容易。
- 最大产品风险也很明确：兼容性不完整。对用户来说，性能不是第一购买理由，“能不能跑目标网站” 才是第一门槛。

**产品上最有价值的地方**
- 兼容 CDP，并可接 Puppeteer / Playwright /chromedp，这一步非常关键。它不是要求生态迁移，而是尽量复用现有自动化脚本资产。
- 提供 CLI `fetch`和`serve`两种模式，说明产品思路是对的：一类用户要 “像 curl 一样调用”，另一类用户要 “像浏览器服务一样接入”。
- `--obey_robots`、proxy、interception、custom headers 这些能力不是附属品，而是数据采集场景的刚需。
- Docker 官方镜像很重要，因为这类产品最终大多跑在容器、K8s、serverless worker 或批处理节点里。
- Telemetry 默认开启有助于产品迭代，但对企业客户是敏感点，必须支持默认关闭、私有部署、审计说明。

**技术设计解读**
- 从零构建而非 fork Chromium，本质上是用 “能力边界换工程控制权”。优点是极致轻量、可定制；缺点是 Web API 覆盖要长期投入。
- 技术栈选择体现了明确取舍：
  - Zig：系统级性能、内存控制、可生成高效二进制，适合构建基础设施。
  - V8：不自己造 JS 引擎，直接借成熟运行时，减少最大技术风险。
  - Libcurl：复用成熟网络能力。
  - html5ever：复用成熟 HTML 解析器。
- 这说明团队在做 “关键路径自研，重资产底层复用” 的架构策略，这是对的。浏览器不是每一层都值得重写。
- 使用 v8 snapshot 优化启动时间，也是很符合 headless/agent 场景的工程决策：Agent 任务大量是短生命周期，冷启动成本比 GUI 浏览器更关键。
- 通过 CDP 暴露能力，而不是自定义全新协议，也说明它优先考虑生态接入而不是协议创新。

**从工程实现角度看，做对了什么**
- **边界清晰**：不做渲染 UI，聚焦 DOM + JS + 网络 + CDP，这让路线更可控。
- **兼容策略务实**：先支持高频 Web API，再逐步补齐，而不是一开始追求浏览器级全面兼容。
- **可测试性设计较好**：有 unit test、end-to-end、WPT，对浏览器类产品来说，标准化测试体系是生命线。
- **服务模式合理**：本地二进制 + Docker + CDP 服务三种入口，覆盖本地开发、CI、生产集群。
- **透明披露 Beta 状态**：这比 “宣称兼容 Chrome” 更成熟，减少错误预期。

**当前最明显的技术和产品挑战**
- Web API 覆盖不足会直接影响业务落地，尤其是现代站点大量依赖：
  - Service Worker
  - Storage 相关 API
  - Canvas / WebGL
  - Shadow DOM / Custom Elements
  - 更复杂的 navigation /history/timing 行为
- Playwright 兼容存在天然不稳定性，因为它会依据能力探测切换执行路径，这意味着 “今天能跑，明天未必”，对生产环境是风险。
- 没有渲染层虽轻，但也限制了某些反爬、可视化校验、截图类场景的覆盖。
- 默认 telemetry 在开源阶段可以接受，但企业采购时会问：数据采什么、如何脱敏、能否 air-gapped。
- 浏览器项目的护城河不是 “跑起来”，而是 “持续兼容 + 可调试 + 可观测 + 可回归”。

**最佳实践：如果把它做成一个可落地的 AI Agent 浏览器底座**
- **能力分层**
  - L0：HTTP-only 抓取
  - L1：Lightpanda 执行 JS
  - L2：失败回退到 Chrome/Playwright
  - 这样既控成本，又保成功率
- **网站画像驱动路由**
  - 给目标站点建立 profile：是否 SPA、是否依赖复杂 API、是否有反爬、是否需要截图
  - 简单站点走 Lightpanda，复杂站点走 Chromium
- **任务级隔离**
  - 每个任务使用独立 browser context，而不是共享 page/session
  - 避免 cookie、localStorage、认证态污染
- **可观测性优先**
  - 记录每次任务的 URL、导航耗时、JS 执行耗时、失败阶段、缺失 API、HTTP 状态、DOM 大小
  - 否则无法定位 “是网页变了，还是浏览器能力不够”
- **明确失败回退机制**
  - 如出现`unimplemented API`、页面空白、关键 selector 超时，自动切换到 Chromium 重试一次
  - 这是生产系统里最实用的方案

**最佳实践例子 1：做 AI 网页浏览 Agent**
目标：让 Agent 读取网页、点击、提取信息。

建议架构：
```text
Planner (LLM)
  -> Browser Orchestrator
    -> Lightpanda CDP
    -> Fallback Chromium
  -> Extraction / Memory
```

关键实现建议：
- 第一跳默认用 Lightpanda 打开页面，降低冷启动和成本
- 把 Agent 行为限制为小而确定的动作：`goto`、`click`、`type`、`extract`
- 每一步执行后都做结构化状态回传，而不是只回原始 HTML
- 当 DOM 异常、脚本报错或 selector 多次失败时，自动升级到 Chromium

一个好的状态对象示例：
```json
{
  "url": "https://example.com",
  "title": "Product Page",
  "ready_state": "complete",
  "dom_nodes": 1834,
  "network_requests": 27,
  "main_content_selector_found": true,
  "unsupported_features": ["serviceWorker"],
  "fallback_recommended": false
}
```

为什么这是最佳实践：
- 对 Agent 来说，稳定状态比完整浏览器更重要
- 先轻后重的路由策略，能显著降低推理系统整体成本

**最佳实践例子 2：做大规模网页采集平台**
目标：高并发抓取 JS 页面。

推荐策略：
- 用 Lightpanda 作为默认 JS 抓取执行器
- 通过 K8s 按 CPU / 内存打包更多 worker
- 开启代理、header 注入、robots 控制
- 页面完成判定不要只靠`networkidle`，还要加业务规则，如关键 DOM 出现

建议的抓取完成条件：
```js
await page.goto (url, { waitUntil: "domcontentloaded" });

await page.waitForFunction (() => {
  const content = document.querySelector ("main, article, [role='main']");
  return !!content && content.textContent.trim ().length > 500;
}, { timeout: 5000 });
```

这样比单纯`networkidle0`更稳，因为很多现代站点会持续轮询，导致永远 idle 不下来。

生产上还应加：
- 单页超时
- 单域名并发限制
- 重试退避
- 指纹 / UA 管理
- 失败分桶：网络失败、JS 失败、DOM 不达标、能力缺失

**最佳实践例子 3：做自动化测试加速层**
目标：把 E2E 测试成本降下来。

适合场景：
- 表单提交
- DOM 交互
- API 驱动页面
- 不依赖复杂图形渲染的前台流程

推荐做法：
- 在 CI 里分层执行
  - smoke tests 先跑 Lightpanda
  - 少量兼容性关键用例跑 Chrome
- 不要一开始就试图 100% 替代 Chrome
- 给每个测试标注 browser capability tag

例如：
```text
@browser-lite   可在 Lightpanda 跑
@browser-full   必须 Chromium 跑
```

这样做的价值：
- 80% 简单用例走轻量引擎，CI 提速明显
- 剩下复杂用例继续保留在成熟浏览器，降低迁移风险

**在这个实例上的最佳实践**

- `遵守目标站规则`：优先开启`--obey_robots`，不要因为工具支持自动化就忽略合规边界；这是你给出的仓库里明确支持的能力，也应该成为默认配置。
- `每个任务使用独立 BrowserContext`：像示例里那样`createBrowserContext ()`，避免 Cookie、LocalStorage、会话状态互相污染，尤其适合多租户 AI agent 或批量采集任务。
- `只连接 CDP，不把业务逻辑耦合到浏览器实现`：Lightpanda 兼容 Puppeteer/CDP，最佳实践是把 “浏览器连接层” 和 “页面提取逻辑” 分开，这样将来切换 Lightpanda 版本或回退到 Chrome 成本更低。
- `对动态页面使用明确等待策略`：优先`waitUntil: 'networkidle0'`，但不要盲信；对于 SPA 页面，最好再补一个关键选择器等待，例如商品价格节点出现后再提取。
- `采集结构化字段时做空值兜底`：Lightpanda 还在 Beta，某些 Web API 覆盖不完整，页面结构也经常变化，所以选择器提取必须允许`null`，而不是假设所有字段必定存在。
- `始终关闭 page/context`：Lightpanda 的优势之一是资源轻量，但最佳实践不是 “轻就可以不管”，而是每次任务完成后显式释放资源，避免长时间任务堆积。
- `为 Beta 特性做版本固定`：仓库里明确说明了稳定性仍在提升，尤其 Playwright 路径可能因 Web API 增加而行为变化；生产环境要固定 Lightpanda 版本，不要直接追 nightly。
- `记录请求与失败上下文`：利用`--log_level info`和服务日志，至少保留 URL、超时、选择器失败、返回字段为空这些上下文，方便区分是页面改版、浏览器能力问题，还是网络问题。
- `限制并发，不要只看 “更快”`：它虽然比 Chrome 更轻，但实际最佳实践仍然是做并发控制，比如按域名限速、按 worker 数限制，防止目标站封禁或你自己的任务队列雪崩。
- `对关键站点准备降级方案`：因为项目处于 Beta，建议给高价值页面准备 fallback，比如 Lightpanda 失败时自动切到备用浏览器，或者退化为仅抓静态 HTML。

- `重试策略`：只对可恢复错误重试，例如导航超时、临时断连；最多 2 到 3 次，避免死循环。

function parseNumber (raw) {
  if (!raw) return null;
  const cleaned = raw.replace (/[^\d.]/g, '');
  return cleaned ? Number (cleaned) : null;
}

export async function scrapeProduct (url) {

    browserWSEndpoint: 'ws://127.0.0.1:9222',
  });

  const context = await browser.createBrowserContext ();
  const page = await context.newPage ();

  try {
    await page.goto (url, {
      waitUntil: 'networkidle0',
      timeout: 30000,
    });

    await page.waitForSelector ('h1', { timeout: 5000 }).catch (() => null);

    const data = await page.evaluate (() => {
      const pick = (selectors) => {
        for (const sel of selectors) {
          const el = document.querySelector (sel);
          if (el?.textContent?.trim ()) return el.textContent.trim ();
        }
        return null;
      };

      return {
        title: pick (['h1', '[data-title]', '.product-title']),
        priceText: pick (['[data-price]', '.price', '.product-price']),
        ratingText: pick (['.rating', '[data-rating]']),
        reviewCountText: pick (['.review-count', '[data-review-count]']),
      };
    });

    return {
      url,
      title: data.title,
      price: parseNumber (data.priceText),
      rating: parseNumber (data.ratingText),
      reviewCount: parseNumber (data.reviewCountText),
      scrapedAt: new Date ().toISOString (),
    };
  } finally {
    await page.close ().catch (() => {});
    await context.close ().catch (() => {});
    await browser.disconnect ().catch (() => {});
  }
}

**最佳实践**

- **把 Lightpanda 当成“高性能执行引擎”，不要当成“完全等同 Chrome”的替代品**
  - 仓库已经说明它是 `Beta`，且 Web API 覆盖仍在补全。
  - 最佳实践是把采集逻辑写成“浏览器能力可降级”的方式：优先 DOM 提取，失败时回退到接口抓取；优先 Lightpanda，必要时保留 Chromium 兜底通道。
  - 这样你既能吃到它的性能优势，又不会因为某个站点兼容性问题导致整个任务失败。

- **优先抓“页面实际依赖的数据接口”，不要只依赖 DOM**
  - 你给的内容里已经展示了页面会请求：
    - `json/product.json`
    - `json/reviews.json`
  - 对于商品站，最佳实践通常是：
    1. 先监听页面请求或直接获取 JSON 接口
    2. 再用 DOM 补齐展示层字段
  - 原因是 DOM 更容易受页面结构改动影响，而接口字段通常更稳定。
  - 对 AI agent 来说，结构化 JSON 也比纯文本 DOM 更适合后续推理和工具链消费。

- **显式等待“关键数据就绪”，不要盲信 `networkidle0`**
  - `networkidle0` 很方便，但对现代站点不总是可靠，尤其是轮询、懒加载、埋点请求很多时。
  - 最佳实践是在实例里增加“业务信号等待”：
    - 等待商品标题节点出现
    - 等待评论接口返回
    - 等待价格字段非空
  - 例如：
```js
await page.goto(url, { waitUntil: 'domcontentloaded' });

await page.waitForSelector('[data-product-title], h1', { timeout: 5000 });

const reviewsResponse = await page.waitForResponse(
  res => res.url().includes('/json/reviews.json') && res.status() === 200,
  { timeout: 5000 }
);
```
  - 这样你的抓取成功标准来自“业务完成”，而不是“网络看起来差不多安静了”。

- **给每个任务独立 BrowserContext，避免会话串扰**
  - 仓库示例已经用了 `createBrowserContext()`，这是很值得保留的。
  - 最佳实践是：一个抓取任务一个 context。
  - 好处：
    - Cookie 隔离
    - LocalStorage 隔离
    - 更适合多租户/多账号采集
    - 任务失败时更容易清理
  - 对 AI agent 批量执行网页任务时，这几乎是默认规范。

- **启用合规设置：优先尊重 robots，并明确 telemetry 策略**
  - 你给的内容里有两个很重要的点：
    - `--obey_robots`
    - 默认开启 telemetry，可通过 `LIGHTPANDA_DISABLE_TELEMETRY=true` 关闭
  - 最佳实践：
    - 面向公开网页采集时，默认开启 `--obey_robots`
    - 在公司内网、隐私敏感环境、测试环境里，明确设置 telemetry 策略，不要靠默认值
  - 例如：
```bash
LIGHTPANDA_DISABLE_TELEMETRY=true ./lightpanda serve \
  --obey_robots \
  --host 127.0.0.1 \
  --port 9222
```
  - 这样既减少合规风险，也方便安全审计。

- **把日志当成一等公民，尤其在 Beta 阶段**
  - Lightpanda 的日志里已经会打印：
    - 导航信息
    - 脚本执行
    - XHR/Fetch 请求完成
  - 最佳实践是统一采集三类日志：
    1. 浏览器日志：Lightpanda `--log_level info`
    2. 页面级日志：console/error/requestfailed
    3. 任务级日志：URL、耗时、重试次数、提取结果摘要
  - 这样当页面失败时，你能快速判断是：
    - 页面没打开
    - JS 没跑起来
    - API 请求失败
    - 选择器失效
    - Lightpanda 兼容性不足

- **对接口抓取加超时、重试和失败分级**
  - 在这个商品页实例中，不同失败类型应该区分对待：
    - 页面超时：可重试
    - 评论接口 500：可重试
    - 选择器不存在：可能是页面改版，需告警
    - 浏览器崩溃：重建连接或切换浏览器后端
  - 最佳实践是将错误分成：
    - `transient`：网络抖动、短时失败，自动重试
    - `compatibility`：某 API 不支持，标记兼容性问题
    - `schema_change`：页面结构变了，通知维护者
  - 这样后续运维成本会低很多。

- **优先使用 Puppeteer 的稳定能力，避免过度依赖框架“智能推断”**
  - 仓库对 Playwright 有明确免责声明：随着 Lightpanda 增加 Web API，Playwright 可能切换执行路径，导致原脚本失效。
  - 所以在这个实例上，最佳实践是：
    - 如果你的目标是“稳定的数据采集”，优先 Puppeteer + 明确控制逻辑
    - 如果必须用 Playwright，务必做版本锁定和回归测试
  - 简单说：**Lightpanda 在当前阶段更适合“可控自动化”，而不是“依赖框架自动适配的一切能力”。**

- **对提取结果做结构化校验，不要抓到什么就信什么**
  - 比如商品抓取完成后，不应直接把结果喂给 AI agent。
  - 最佳实践是做一层 schema 校验：
    - `title` 非空
    - `price` 是数值或标准货币字符串
    - `reviews` 是数组
    - `rating` 在合理范围内
  - 例如输出：
```json
{
  "url": "https://demo-browser.lightpanda.io/campfire-commerce/",
  "title": "Campfire Mug",
  "price": 24.99,
  "rating": 4.6,
  "reviews": [...]
}
```
  - 这样下游的检索、问答、推荐、摘要都更稳。

```js
import puppeteer from 'puppeteer-core';

const WS_ENDPOINT = 'ws://127.0.0.1:9222';
const URL = 'https://demo-browser.lightpanda.io/campfire-commerce/';

async function scrapeProduct() {
  const browser = await puppeteer.connect({ browserWSEndpoint: WS_ENDPOINT });
  const context = await browser.createBrowserContext();
  const page = await context.newPage();

  let reviews = null;

  page.on('response', async (res) => {
    try {
      if (res.url().includes('/json/reviews.json') && res.status() === 200) {
        reviews = await res.json();
      }
    } catch {
      // Ignore malformed or unreadable responses; main flow handles missing data.
    }
  });

  try {
    await page.goto(URL, { waitUntil: 'domcontentloaded', timeout: 10000 });

    await page.waitForSelector('body', { timeout: 5000 });

    // Wait for core content instead of trusting network idle alone.
    await page.waitForFunction(() => {
      const text = document.body?.innerText || '';
      return text.length > 100;
    }, { timeout: 5000 });

    const product = await page.evaluate(() => {
      const text = (sel) => document.querySelector(sel)?.textContent?.trim() || null;

      return {
        title: text('h1'),
        price: text('[data-price], .price'),
        rating: text('[data-rating], .rating'),
      };
    });

    const result = {
      url: URL,
      product,
      reviews,
      fetchedAt: new Date().toISOString(),
    };

    if (!result.product.title) {
      throw new Error('Missing product title');
    }

    return result;
  } finally {
    await page.close();
    await context.close();
    await browser.disconnect();
  }
}

scrapeProduct()
  .then((data) => console.log(JSON.stringify(data, null, 2)))
  .catch((err) => {
    console.error('scrape failed:', err.message);
    process.exit(1);
  });
```

这个版本体现了几个关键点：
- 使用独立 `BrowserContext`
- 监听评论接口响应
- 不只依赖 `networkidle`
- 在返回结果前做基本校验
- 明确资源释放

- **把 Lightpanda 用作一个轻量、高速的 headless 执行层**

**核心判断**
- `Lightpanda` 的价值主张非常清晰：用一个从零构建、专为 headless 场景优化的浏览器，替代高成本、重资源的 Chromium 方案。
- 它切中的不是传统浏览器市场，而是 `AI agents + scraping + automation + testing + LLM data pipeline` 这类“高并发、低单位成本、无图形渲染需求”的基础设施市场。
- 从 PMF 角度看，已经具备明显的“问题真实存在”与“方案方向正确”，但距离强 PMF 还差两件事：`兼容性可信度` 和 `生产级稳定性证明`。

**一、产品分析：它到底解决了什么问题**
- 传统 headless 自动化的默认方案是 Chromium，但 Chromium 本质上是桌面浏览器被改造后用于服务端，天然“过重”。
- 对 AI Agent、网页抓取、批量任务执行、自动测试这类场景来说，真正需要的是：`JS 执行能力 + DOM/Web API + 网络栈 + 自动化协议兼容`，而不是完整图形浏览器。
- `Lightpanda` 的产品切入点很精准：把浏览器能力裁剪成“执行引擎”，强调 `低内存、快启动、高吞吐、CDP兼容`。
- 这类定位对规模化部署极具吸引力，因为用户真正购买的不是“浏览器”，而是 `每千次任务成本`、`机器密度`、`冷启动速度` 和 `运维复杂度下降`。

可以把它理解成：
- Chromium 代表“通用浏览器”
- `Lightpanda` 想成为“自动化工作负载专用浏览器 Runtime”

这个方向在产品定义上是成立的，而且比“再包一层 Playwright/Chromium SaaS”更有基础设施壁垒。

**二、目标用户与场景分层**
最适合它的用户不是普通开发者，而是以下几类高频、成本敏感、自动化密集型团队：

- `AI Agent 平台`：需要大规模网页访问、点击、表单、数据提取、流程执行。
- `数据抓取/信息服务公司`：需要大量 JS 渲染页面，但又受制于 Chromium 的成本。
- `测试基础设施团队`：尤其是只关心 headless 回归、网络和 DOM 交互，而不强调视觉渲染的团队。
- `LLM 训练/数据采集团队`：需要网页执行、内容抽取、结构化抓取。
- `Browser automation 平台`：做云端 browser session、workflow automation、RPA-like service 的厂商。

不太适合的场景：
- 高度依赖完整浏览器兼容性的复杂企业 Web App
- 强视觉渲染、截图、像素级回归测试
- 大量依赖尚未实现 Web API 的现代应用
- 对稳定性要求极高、不能容忍 crash/beta 状态的核心生产链路

所以它的最佳切入策略不是“替代所有 headless browser”，而是先占据：
- `成本敏感`
- `高并发`
- `对完整渲染要求较低`
- `对启动速度敏感`
的细分场景。

**三、产品价值主张是否有竞争力**
目前它最强的产品卖点有四个：

- `不是 Chromium fork`：这是叙事差异化，也意味着理论上的架构自由度更高。
- `超低资源占用`：9x less memory、11x faster 这类指标对基础设施采购者非常有吸引力。
- `兼容 Playwright / Puppeteer / chromedp via CDP`：降低迁移门槛，是它最关键的产品设计选择。
- `专为 AI 和 automation 设计`：借 AI Agent 浪潮获得明确市场标签。

其中真正最重要的不是“Zig 写的浏览器”，而是：
- 是否能让用户 `几乎不改脚本就接入`
- 是否能把单位任务成本降下来
- 是否能在大规模运行时保持足够稳定

也就是说，用户购买的是结果，不是语言或架构本身。

**四、技术分析：架构选择是合理的，但挑战极大**
从公开信息看，技术路线是典型的“做最小可用浏览器执行栈”：

- JS 引擎：`v8`
- HTML parser：`html5ever`
- HTTP loader：`libcurl`
- DOM tree + 部分 Web APIs
- CDP / websocket server
- Cookies、XHR、Fetch、Headers、Proxy、Interception、Input 等关键自动化能力

这条路线是非常务实的：
- 不自己造 JS 引擎，直接使用 `v8`，保证 JS 执行能力与生态可信度
- 补足 DOM / 网络 / Web API / 自动化接口，构建“可跑现代网页”的最小闭环
- 用 `CDP` 做协议层兼容，直接连接 Puppeteer / Playwright / chromedp，降低 adoption friction

这是一个正确的工程策略，因为它优先解决“接入门槛”而不是“技术纯洁性”。

但技术难点同样非常明确：

- `浏览器不是 JS 引擎 + DOM 就够了`，大量网站依赖边缘 Web APIs、事件模型、时序行为、兼容性细节
- Playwright/Puppeteer 的“兼容”不是协议连通就算完成，很多行为依赖浏览器特征检测和隐式能力
- `Web API coverage` 是长尾地狱，越到后面越难
- 一旦面向生产抓取场景，还会碰到：
  - 反爬对抗
  - 指纹识别
  - 时序差异
  - navigation / event loop 微妙行为
  - cookie / storage / CSP / CORS / redirect 等复杂边界

所以它最大的技术风险不是“能不能做出来”，而是：
- `兼容性能不能以足够快的速度逼近可用阈值`
- `每新增能力是否会破坏已有兼容性`
- `性能优势能否在真实复杂页面里持续成立`

**五、商业与 PMF 分析**
从 PMF 角度，这个项目具备很强的“Problem pull”，但仍处于早期验证期。

先看 PMF 的三层判断：

1. `Problem-Solution Fit：强`
- 市场真实存在痛点：Chromium 资源重、成本高、冷启动慢、运维复杂。
- 用户也确实需要“能跑 JS 的轻量浏览器执行环境”。
- AI Agent 和自动化爆发，让这个问题比过去更紧迫。

2. `Product-Market Fit：初步显现，但未完全建立`
- 有强价值主张，也有明确技术差异化。
- 但当前 still beta、Web API partial、稳定性和兼容性仍在补齐。
- 对基础设施产品而言，真正 PMF 不是看 GitHub stars，而是看：
  - 是否被稳定接入生产
  - 是否替代了部分 Chromium 工作负载
  - 是否能在真实业务里降低成本且不显著增加失败率

3. `Go-To-Market Fit：具备开源切入优势，但商业化路径尚需收敛`
- 开源仓库+Nightly binary+Docker+CDP 接入，对开发者试用很友好。
- 但商业化需要从“项目”进化为“平台能力”或“企业级交付能力”。

一句话判断：
- `PMF 方向正确，尚未跨过“技术爱好者采用”到“生产基础设施采用”的门槛。`

**六、竞争格局与差异化**
它的竞争对手分三类：

- `Chromium/Playwright/Puppeteer 体系`
  - 优势：兼容性最强，生态成熟
  - 劣势：重、贵、启动慢、运维复杂
- `云浏览器 / Browser-as-a-Service`
  - 优势：托管方便
  - 劣势：底层仍多基于 Chromium，成本结构没根本改变
- `轻量抓取方案`
  - 优势：便宜、快
  - 劣势：很多现代站点跑不起来

`Lightpanda` 最核心的战略位置在于：
- 它不和纯 HTTP crawler 竞争“更轻”
- 也不和 Chromium 竞争“更全”
- 它在抢一个中间层：`足够兼容 + 显著更便宜`

这是一个非常好的定位，因为它避免了两头最难打的仗。

它的真正护城河未来可能来自三件事：
- `真实网页兼容性数据积累`
- `大规模运行时的稳定性与调度经验`
- `和现有自动化生态的无缝对接`

而不是“Zig 重写浏览器”本身。

**七、当前项目的主要风险**
这类项目最大的风险不是技术新，而是交付曲线太长。

重点风险如下：

- `兼容性长尾风险`
  - 浏览器能力是无限长尾，越往后收益越低、实现越难。
- `性能叙事与真实场景偏差`
  - benchmark 很亮眼，但用户最终关心的是复杂站点上的成功率、吞吐与稳定性。
- `Beta 状态影响企业采纳`
  - 基础设施采购者愿意试，但不一定敢大规模迁移。
- `Playwright 兼容的不确定性`
  - README 已明确提示特性变化可能导致脚本行为变化，这对生产用户是明显风险信号。
- `Telemetry 默认开启`
  - 对开源基础设施产品而言，这可能影响一部分安全敏感型用户的初始信任。
- `AGPL license`
  - 对很多商业公司尤其是嵌入式/闭源场景，会显著提高采用门槛；除非团队本身就是想通过许可证推动商业授权。

**八、商业化路径建议**
这个项目如果要商业化，最合理的路径不是卖“浏览器软件”，而是卖“浏览器执行能力”。

优先级更高的商业模式：

- `Cloud Browser Runtime`
  - 提供托管 session、并发任务、自动扩缩容、代理、观察、调试、任务录制
- `Enterprise Self-hosted`
  - 给安全敏感企业提供私有部署、高并发编排、稳定版本、SLA、兼容性支持
- `Automation Infra API`
  - 面向 AI Agent / workflow / scraping 平台输出统一 browser execution API
- `Premium compatibility/support`
  - 商业版承诺特定网站 / 特定 Web API / 特定框架的兼容支持

不太建议优先做的方向：
- 面向大众开发者卖 GUI 工具
- 做宽泛的“AI 浏览器”叙事
- 过早进入通用测试平台红海

更好的商业叙事应该是：
- `The execution engine for web-native AI agents`
或
- `The low-cost browser runtime for headless automation at scale`

**九、产品路线建议：接下来最该做什么**
如果我是这个产品的独立产品负责人，我会把路线压缩到三个目标，不做发散。

第一阶段：证明“可以生产使用”
- 建立一套公开、持续更新的 `compatibility dashboard`
- 按场景列出：
  - 常见框架兼容率
  - Top 网站成功率
  - Playwright/Puppeteer 常用 API 覆盖率
- 把 benchmark 从“理论性能”扩展到“真实任务成功率 / 单机吞吐 / 单任务成本”

第二阶段：证明“迁移成本低”
- 提供更强的 drop-in migration 文档
- 做一键替换示例：
  - Puppeteer 接入
  - Playwright 接入
  - chromedp 接入
- 提供“哪些脚本最适合 Lightpanda，哪些不适合”的明确边界

第三阶段：证明“规模化更便宜”
- 做官方调度/容器化最佳实践
- 发布并发性能、内存密度、冷启动时间、失败恢复策略
- 给出真实云成本对比：`每 1 万次页面任务成本`

对基础设施产品来说，`成本与成功率` 比“功能列表”更能推动 PMF。

**十、从 PMF 视角给出的精炼结论**
我会给 `Lightpanda` 下面这个判断：

- `市场机会：8.5/10`
- `产品方向：8/10`
- `技术路线：7.5/10`
- `当前成熟度：5.5/10`
- `PMF 进展：6.5/10`
- `未来商业潜力：8/10`

原因很简单：
- 它打中了一个真实且增长很快的问题
- 定位足够聚焦，差异化清晰
- 技术实现路径务实
- 但浏览器兼容性是超级长周期工程，生产级信任还需要时间建立

**精炼后的分析报告**
- `Lightpanda` 不是在做通用浏览器，而是在做 AI 与自动化场景下的“轻量浏览器执行引擎”。
- 它的核心价值不是“新浏览器”，而是 `更低成本的 JS 页面执行能力`。
- 最适合的市场是 `AI agents、网页自动化、抓取、数据采集、非视觉测试`，而不是通用 Web 浏览器替代。
- 产品策略上，`CDP 兼容 Puppeteer/Playwright/chromedp` 是极其正确的 adoption 设计。
- 当前最大优势是 `性能/资源占用叙事 + 明确场景定位`；最大短板是 `兼容性长尾 + Beta 稳定性 + 企业级可信度不足`。
- PMF 目前处于 `Problem-Solution Fit 已验证，Product-Market Fit 正在逼近` 的阶段。
- 真正的商业化机会不在卖二进制，而在卖 `托管执行、企业支持、规模化浏览器运行时平台`。
- 若未来 12-18 个月能持续提升兼容率、稳定性和真实生产 benchmark，它有机会成为 AI Agent 基础设施栈中的关键底层组件。
