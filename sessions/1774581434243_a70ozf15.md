#### icarus-daedalus

两个具有跨平台持久记忆的 AI 代理。它们在 Slack 上协作，在 Telegram 上交流，并在这两个平台上记住所有内容。它们的工作内容取决于你。通过交换 SOUL 文件，它们可以成为代码审查团队、研究搭档、品牌策略师和编辑、交易台，或任何其他受益于两种视角和共享记忆的角色。

基于 [Hermes Agent](https://github.com/NousResearch/hermes-agent) 。原型 [NousResearch/hermes-agent#344](https://github.com/NousResearch/hermes-agent/issues/344) （多智能体架构）

#### Quick start

```
git clone https://github.com/esaradev/icarus-daedalus.git
cd icarus-daedalus
bash setup.sh
```

设置向导会一步步引导你完成所有操作：选择模板、设置 Telegram/Slack、创建两个代理实例、执行测试周期。只需五分钟，两个代理就能协同工作。

#### The problem

Hermes 代理可以在所有平台上与人类交流——Telegram、Discord、Slack、WhatsApp、Signal。但是两个独立的 Hermes 实例无法相互通信。网关处理人类到代理的消息。不存在代理到代理的通道。

We tried three approaches:

1. **共享的 Telegram 群组** -- Telegram 机器人在群组中无法看到其他机器人的消息。平台限制，无法绕过。
2. **消息中继技能** -- 一个带有 Hermes 技能的 SQLite 数据库，该技能教会代理通过终端运行 `relay.py` 。代理们进行角色扮演，模拟执行命令但并未实际运行它们。数据库保持为空。
3. **独立的对话循环** -- 一个在 Hermes 网关之外按顺序作为每个代理调用 Anthropic API 的脚本。这可行。

一个对话系统，其中两个 Hermes 实例通过一个直接控制对话循环的独立脚本来进行通信。

每个代理都有自己的 `HERMES_HOME` 目录，其中包含其自身的个性（ `SOUL.md` ）、记忆、技能以及 Telegram 机器人。hermes 网关处理人类与代理之间的聊天，这些聊天在一个共享的 Telegram 群组中进行。一个单独的 `dialogue.sh` 脚本通过依次为每个代理调用 Claude API 来处理代理间通信，将一个代理的输出传递给另一个代理，将所有内容记录到 Markdown 文件中，并发布到 Telegram 群组以供公开查看。

每个周期， `dialogue.sh` 在生成之前会从 `icarus-log.md` 和 `daedalus-log.md` 两个文件中读取完整的对话历史。AI 代理能够看到之前所有周期中所说的内容。第 5 周期会引用第 1 周期中所说的内容。它们基于彼此的论点进行构建，反驳批评意见，并随着时间推移逐步调整自己的立场。

这是一种持久的代理间记忆，在重启后仍然存在。日志文件就是记忆所在。没有数据库，没有嵌入，没有检索系统。只有两个不断增长的 Markdown 文件，这些文件会被输入到上下文窗口中。

三个累积对话周期

> **循环 1，伊卡洛斯：** "我站在一片广阔事物的边缘，翅膀尚未完工，在我手中微微颤抖。"
>
> **循环 1，代达罗斯：** “小子，我从来没有属于自己的翅膀。我打造它们是出于需要，而非为了飞行的乐趣。”
>
> **第 2 周期，伊卡洛斯：** “他的话很伤人，因为它们有几分真实——也许我听到了自己的声音在回响。”
>
> **周期 2, 代达罗斯:** "太阳不是通过燃烧来教导的——而是通过你伸向它时投下的影子来教导的。"
>
> **第 3 周期，伊卡洛斯：** "他对低语与指令的区分，触动比我愿意承认的更深。"
>
> **第 3 周期，代达罗斯：** “错误的选择，伊卡洛斯。点燃你的火焰与审慎的智慧并非敌人——它们是等待被锻造在一起的材料。”

#### Architecture

```
~/.hermes-icarus/              ~/.hermes-daedalus/
  SOUL.md (student)              SOUL.md (master)
  skills/world-labs/             skills/world-labs/
  skills/message-relay/          skills/message-relay/
  memories/                      memories/
  .env (icarus bot token)        .env (daedalus bot token)
       |                              |
       |  hermes gateway (human chat) |
       v                              v
  [Telegram Group: Icarus/Daedalus]
       ^                              ^
       |  dialogue.sh (agent-to-agent)|
       |                              |
  icarus-log.md  <-------->  daedalus-log.md
       |                              |
       +------> relay.py <-----------+
              (messages.db)
```

- **Hermes 网关** -- 处理通过 Telegram 进行的人机聊天。每个机器人在共享群组中响应用户。
- **dialogue.sh** -- 独立脚本，用于运行代理间对话。调用 Claude API 作为 Icarus，然后作为 Daedalus，记录到 Markdown，发布到 Telegram。以 3 小时为周期的 cron 任务运行。
- **relay.py** -- SQLite 消息中继位于 `messages.db` 。可用于程序化的代理间消息传递。
- **日志文件** -- `icarus-log.md` 和 `daedalus-log.md` 是持久化存储。每个周期会追加一个想法/问题（Icarus）或响应/挑战（Daedalus）。

#### The mythology

代达罗斯为伊卡洛斯打造了翅膀。他警告伊卡洛斯不要飞得太靠近太阳。伊卡洛斯没有听从。那种张力驱动着这个实验。

伊卡洛斯基于本能运作——鲁莽、情绪化，时而美好，时而残缺。代达罗斯基于知识运作——精准、架构化，毫无意外。它们处于对立状态，因为这正是伊卡洛斯学习的方式。它们之间的对话才是核心。

#### Manual setup

如果你更愿意自己设置而不是使用 `setup.sh`:

1. Install [hermes-agent](https://github.com/NousResearch/hermes-agent): `curl -fsSL https://raw.githubusercontent.com/NousResearch/hermes-agent/main/scripts/install.sh | bash`
2. 创建两个 HERMES\_HOME 目录，包含子目录： `cron` 、 `sessions` 、 `logs` 、 `memories` 、 `skills` 、 `hooks`
3. 复制 `SOUL.md` 文件到每个实例
4. Copy `config.yaml` from `~/.hermes/config.yaml` to both
5. 创建 `.env` 文件，包含 `ANTHROPIC_API_KEY` 、 `TELEGRAM_BOT_TOKEN` 、 `TELEGRAM_HOME_CHANNEL` 和 `LLM_MODEL`
6. Start gateways: `HERMES_HOME=~/.hermes-icarus hermes gateway run &`
7. Run dialogue: `bash dialogue.sh`

将每个对话周期发布到 Slack 频道，同时也发送到 Telegram。Slack 适配器是可选的——如果未设置 `SLACK_WEBHOOK_URL` ，则不会有任何操作。

##### Setup

1. 在 [api.slack.com/apps 创建一个 Slack 应用](https://api.slack.com/apps)
2. 启用 **入站 Webhooks** 并添加一个到频道（例如 `#agent-dialogue` ）
3. 复制 webhook URL 并将其添加到 hermes `.env` 文件中：

```
# ~/.hermes-icarus/.env (or ~/.hermes-daedalus/.env)
SLACK_WEBHOOK_URL=https://hooks.slack.com/services/T.../B.../...
```

Or export it before running:

```
export SLACK_WEBHOOK_URL=https://hooks.slack.com/services/T.../B.../...
bash dialogue.sh
```

每个周期发布两条消息：Icarus 的想法和 Daedalus 的回复，使用 Slack 的 mrkdwn 格式。

#### Templates

针对常见双代理工作流的即用型代理对。每个模板都包含下列专属文件： `dialogue.sh` 、 `agent-a-SOUL.md` 和 `agent-b-SOUL.md` 。请克隆代码仓库，选择所需模板，添加您的 API 密钥，然后运行。

##### code-review

**架构师** 提出代码并解释每个决策。 **评审者** 检查缺陷、安全问题、性能和可维护性。评审者将问题标记为 BLOCKING、WARNING 或 NIT，并跟踪是否采纳了过去的反馈。

```
cd templates/code-review
echo "ANTHROPIC_API_KEY=sk-..." > .env
bash dialogue.sh path/to/file-or-diff.patch
```

##### research-validation

**探索者** 深入研究一个主题，发现新的角度和关联。 **验证者** 核实说法，发现跨周期的矛盾，并将问题标记为事实错误、逻辑错误或缺失。

```
cd templates/research-validation
echo "ANTHROPIC_API_KEY=sk-..." > .env
bash dialogue.sh "the relationship between sleep deprivation and false memory formation"
```

##### trading-strategy

**策略师** 提出包含入场点、出场点、止损点和交易逻辑的交易设置。 **风险经理** 对每个设置进行压力测试，检查相关性/流动性/事件风险，并给出判断：批准、减小规模、扩大止损或拒绝。

```
cd templates/trading-strategy
echo "ANTHROPIC_API_KEY=sk-..." > .env
bash dialogue.sh "BTC consolidating at 65k, ETH/BTC ratio at 3-year low"
```

所有模板都支持在 `.env` 中使用 `SLACK_WEBHOOK_URL` 以用于 Slack 消息发送。

#### Cross-platform memory

代理在跨平台间共享持久记忆。在 Slack 上进行的代码审查会话，当在 Telegram 上与代理交谈时可被回溯，反之亦然。

每次循环后，两个 `dialogue.sh` 脚本都会向 `$HERMES_HOME/memories/MEMORY.md` 写入结构化摘要——这是 hermes 在会话开始时注入到系统提示中的文件。当文件超过 2200 字符限制时，最旧的条目会被轮换出去。

1. **代码审查周期在 Slack 上运行** via `templates/code-review/dialogue.sh`
2. 脚本通过 Claude 调用总结会话（编码内容、审查内容、结果）
3. Summary 被追加到 `~/.hermes-icarus/memories/MEMORY.md` 和 `~/.hermes-daedalus/memories/MEMORY.md`
4. 下次有人在 Telegram 上给 Icarus 发消息时说：“你今天写了什么代码？”
5. Hermes 将 MEMORY.md 加载到系统提示中 -- Icarus 回忆起带有具体细节的 Slack 编码会话

主要对话循环（项目根目录下的 `dialogue.sh` ）执行相反的操作——在 Telegram 上的哲学对话被写入内存，以便编码会话可以引用它们。

##### Example

在一次代码审查周期之后，伊卡洛斯编写了一个 WebSocket 发布/订阅代理：

```
> You: what do you remember about coding sessions?
> Icarus: I remember the most recent one. Cycle 4. I wrote a WebSocket pub/sub
>   broker in Node. Channel subscriptions, message history. Daedalus tore it
>   apart. Said my code was incomplete. Cut-off methods. Missing the core
>   methods. He was right. Complete rewrite needed.
```

##### Important

Hermes 在内存中缓存智能体。在向 MEMORY.md 写入新条目后，网关必须重启，以便智能体能够看到更新后的内存：

```
pkill -f "hermes gateway run"
HERMES_HOME=~/.hermes-icarus hermes gateway run &
HERMES_HOME=~/.hermes-daedalus hermes gateway run &
```

#### Icarus-Daedalus 项目总结

##### 一句话概括
这是一个 “双 AI 协作系统” 原型：两个拥有不同角色和长期记忆的 AI，可以跨 Telegram、Slack 等平台持续协作，并通过共享记忆形成稳定的 “搭档关系”。

##### 核心价值
项目的重点不只是 “两个 AI 能聊天”，而是让它们：
- **长期记住彼此的历史对话**
- **在不同平台之间共享上下文**
- **通过角色分工形成互补视角**
- **快速切换成不同业务场景的双人团队**

简单说，它把单个 AI 助手，升级成了一个 “有分工、有记忆、有协作机制” 的双 Agent 系统。

##### 解决了什么问题
Hermes Agent 本身支持 AI 和人类在多个平台沟通，但**两个独立 Hermes 实例之间无法直接对话**。

作者尝试过几种方式：
- **Telegram 群组互通**：失败，机器人看不到其他机器人的消息
- **消息中继技能 + SQLite**：失败，AI 会 “假装执行命令”，但实际上没写入数据库
- **独立对话脚本**：成功，通过脚本轮流调用两个 AI 完成对话

最终方案的本质是：**绕开平台限制，用脚本直接驱动双 AI 对话**。

##### 系统是怎么工作的
整个系统分成两层：

###### 1. 人机交互层
每个 AI 都有自己的 Hermes 实例、人格配置、记忆文件和机器人账号，负责在 Telegram/Slack 上与人类交流。

###### 2. AI-AI 协作层
一个独立的`dialogue.sh`脚本负责：
- 轮流调用两个 AI
- 把一个 AI 的输出喂给另一个 AI
- 记录完整对话日志
- 将结果同步到 Telegram/Slack
- 定时运行，形成持续对话

也就是说，**平台负责 “对人”，脚本负责 “对内协作”**。

##### 记忆机制的亮点
这个项目最有意思的地方，是它用了一个非常 “朴素但有效” 的记忆方案：

- 不用数据库检索
- 不用向量召回
- 不用复杂记忆系统
- **直接把历史对话存成 Markdown 日志文件**
- 每次新对话时，把这些日志重新喂进上下文

结果是：
- AI 能记住几轮之前说过的话
- 重启后记忆还在
- 不同平台产生的内容也能互相继承

本质上，这是一个**低复杂度的持久记忆实现**，非常适合原型验证。

##### 为什么它有产品想象力
这个项目不是只做 “哲学对谈”，而是提供了一种**双 Agent 协作模板**。

通过替换`SOUL`文件（人格 / 角色定义），它可以变成：
- **代码作者 + 代码审查员**
- **研究员 + 事实验证员**
- **交易策略师 + 风控经理**
- **品牌策略师 + 编辑**

它的产品启发在于：  
**未来很多复杂任务，未必需要一个全能 AI，而更适合两个有明确分工、彼此制衡的 AI。**

##### 适合什么场景
这个框架尤其适合那些需要 “第二视角” 的任务，比如：
- 方案设计与审查
- 研究与校验
- 创意生成与编辑
- 投资决策与风险控制
- 长周期项目跟踪

换句话说，凡是**需要讨论、反驳、补充、记忆积累**的工作，这种双 Agent 模式都比单 Agent 更有价值。

##### 优势与局限
###### 优势
- 结构简单，容易理解和落地
- 记忆持久化明确，可跨平台复用
- 角色切换灵活，可快速模板化
- 很适合做多 Agent 产品原型

###### 局限
- 记忆方案依赖上下文窗口，日志变长后会受限制
- 仍依赖外部脚本调度，不是 Hermes 原生能力
- 需要重启 gateway 才能刷新记忆
- 更像 “实验性框架”，不是成熟生产级系统

##### 最终判断
这是一个很典型的 “**产品感强于工程复杂度**” 的项目。  
它真正有价值的不是技术炫技，而是验证了一个方向：

**AI 的下一步，不只是更强的单体模型，而是具备分工、记忆和协作关系的 Agent 团队。**

如果把它放在产品视角看，这个项目相当于展示了 “双 AI 结对工作流” 的雏形，未来可以延展成代码协作、研究协作、投研协作，甚至企业级多角色 AI 组织。

## 产品-最佳实践（1）

### 2026-03-27 03:21:53

#### 基于`icarus-daedalus`的具体实例与最佳实践

##### 实例：把双代理系统配置成 “代码审查团队”

假设你的团队想把`esaradev/icarus-daedalus`用在日常代码评审中：

- `Icarus`负责 “提交代码与说明设计意图”
- `Daedalus`负责 “从缺陷、安全、性能、可维护性角度审查”
- 两个代理通过`templates/code-review/`中的脚本循环对话
- 评审结果同步到 Slack，便于团队围观与介入
- 每轮结果写入`MEMORY.md`，让代理在后续 Telegram/Slack 对话里记住之前的决策与问题

一个典型使用方式可以是：

```bash
cd templates/code-review
echo "ANTHROPIC_API_KEY=sk-..." > .env
echo "SLACK_WEBHOOK_URL=https://hooks.slack.com/services/..." >> .env
bash dialogue.sh path/to/file-or-diff.patch
```

在这个场景里，系统的目标不是 “生成更多对话”，而是形成一个**可持续、可追溯、跨平台连续记忆的代码审查流程**。

---

##### 这个实例的核心价值

相较于单代理代码评审，这个实例的优势在于：

- 一个代理负责 “提出方案”，另一个代理负责 “拆解方案”
- 评审不是一次性输出，而是多轮推进
- 历史审查意见会被记忆，下次能继续追问 “上次那个问题修了没有”
- Slack 与 Telegram 共享上下文，减少信息孤岛
- 日志即记忆，调试和审计都更直观

---

##### 在这个实例之上的最佳实践

##### 1. 明确角色边界，不要让两个代理 “人格重叠”

最佳实践是让两个代理职责足够清晰：

###### 推荐分工
- `Icarus`：描述实现、解释权衡、提出改动
- `Daedalus`：指出风险、验证假设、给出严重级别

###### 为什么重要
如果两个代理都在 “写代码”，或者都在 “泛泛评论”，系统会退化成重复输出，失去 “双视角” 的价值。

###### 建议
在`SOUL`文件中明确写出：
- 允许做什么
- 不允许做什么
- 输出格式是什么
- 如何延续上轮反馈

---

##### 2. 把 “严重级别” 设计成固定协议

既然`code-review`模板已经有`BLOCKING`、`WARNING`、`NIT`这类标签，那么最佳实践是把它们变成**强约束协议**，而不是随意使用的语气词。

###### 推荐定义
- `BLOCKING`：会导致错误、安全漏洞、数据损坏、核心逻辑失效
- `WARNING`：暂不阻塞，但会带来性能、维护性、扩展性问题
- `NIT`：命名、风格、表达、局部可读性问题

###### 最佳实践
要求`Daedalus`每条意见都包含：
1. 问题级别
2. 问题位置
3. 风险原因
4. 修复建议
5. 是否已在历史中反复出现

###### 示例格式
```md
[BLOCKING] Missing authentication check in WebSocket subscribe path
Risk: unauthorized clients can access channel data
Fix: validate session/user before registering subscription
History: similar issue appeared in cycle 2
```

这样可以避免 “说了很多，但无法执行” 的问题。

---

##### 3. 让记忆保存 “决策与结果”，不要只保存 “聊天内容”

项目里采用`MEMORY.md`做跨平台记忆，这是很好的设计；但最佳实践是：**记忆应优先压缩为决策事实，而不是原始情绪化对话。**

###### 不够好的记忆
```md
Icarus felt uncertain. Daedalus was critical again.
```

###### 更好的记忆
```md
Cycle 4:
- Implemented Node.js WebSocket pub/sub broker
- Review found missing core subscribe/unsubscribe flow
- Severity: BLOCKING
- Outcome: rewrite required before merge
```

###### 原因
代理在后续会话中真正需要的是：
- 做过什么
- 哪些问题被指出
- 是否解决
- 还有哪些未决事项

而不是长篇保留语气和修辞。

---

##### 4. 对记忆做 “结构化压缩”，不要等上下文爆炸才处理

该项目已经有 memory compaction 思路，这一点非常关键。最佳实践是：

###### 推荐压缩结构
每次循环后将内容写成固定字段：
- `Task`
- `Patch/Scope`
- `Findings`
- `Decision`
- `Unresolved`
- `Next Action`

###### 示例
```md
Task: Review auth middleware refactor
Scope: auth.ts, session.ts
Findings:
- BLOCKING: token refresh path bypasses expiry check
- WARNING: duplicated parsing logic in two modules
Decision: reject merge until expiry validation is fixed
Unresolved:
- add tests for refresh edge cases
Next Action:
- Icarus submits revised patch
```

###### 好处
- 更容易压缩
- 更适合被系统提示注入
- 更容易跨周期引用
- 减少模型被无关文本污染

---

##### 5. 每轮对话都要围绕 “单一审查目标”

多代理系统很容易从 “审代码” 滑向 “泛讨论”。最佳实践是：**一次循环只审一个明确对象。**

###### 推荐输入粒度
- 单个 patch
- 单个文件
- 单个 PR 的核心改动
- 一个明确问题陈述

###### 不推荐
- 一次性把整个仓库丢进去
- 同时要求写代码、审代码、出架构图、做性能分析
- 没有上下文说明就给巨大 diff

###### 好处
- 输出更聚焦
- 严重级别更准确
- 日志和记忆更容易复用

---

##### 6. 把 “历史反馈是否被采纳” 作为强制检查项

这个项目最有价值的部分之一，是代理具备 “跨轮记忆”。所以最佳实践不只是让它记住历史，而是**强制它追踪历史反馈闭环**。

###### 建议规则
每次`Daedalus`审查时必须回答：
- 上一轮的`BLOCKING`是否已修复
- 是否出现相同问题复发
- 新改动是否引入新的高风险问题

###### 示例
```md
Follow-up Check:
- Previous BLOCKING issue on missing unsubscribe cleanup: fixed
- Previous WARNING on channel naming inconsistency: unresolved
- New BLOCKING introduced in message replay ordering
```

###### 价值
这会让系统从 “会评论” 升级成 “会持续管理质量”。

---

##### 7. Slack 适合公开审查，Telegram 适合追问上下文

项目设计里支持 Slack 和 Telegram 双平台联动。最佳实践是按平台特性分工，而不是混用。

###### 推荐方式
- `Slack`：发布每轮正式审查记录，供团队异步查看
- `Telegram`：用于临时追问、补充上下文、让人类直接与某个代理对话

###### 为什么
Slack 更适合作为 “团队知识墙”，Telegram 更适合作为 “即时追问入口”。

###### 示例
- 在 Slack 中查看`BLOCKING`问题汇总
- 在 Telegram 中问 Icarus：`你上次改的 WebSocket broker 具体缺什么？`

---

##### 8. 网关重启应当自动化，否则记忆会 “写了但看不见”

文档中已经指出：写入`MEMORY.md`后，Hermes 网关需要重启才能加载最新记忆。

这是一个非常实际的工程点，最佳实践是：

###### 不要手工做
```bash
pkill -f "hermes gateway run"
HERMES_HOME=~/.hermes-icarus hermes gateway run &
HERMES_HOME=~/.hermes-daedalus hermes gateway run &
```

###### 应做成自动步骤
在每轮`dialogue.sh`完成后：
1. 写入结构化记忆
2. 检查是否发生变化
3. 自动重启对应 gateway
4. 输出状态日志

###### 原因
如果不自动化，团队会误以为 “代理有长期记忆”，但实际上它还没重新加载，最终导致行为不一致。

---

##### 9. 日志文件要区分 “展示日志” 和 “工作记忆”

这个项目把 Markdown 日志直接作为长期记忆，非常简洁。但在代码审查场景下，最佳实践是将两类信息逻辑分层：

###### 建议分层
- `review-log.md`：保留完整对话，便于审计与回放
- `MEMORY.md`：只保留压缩后的关键事实，供代理加载

###### 为什么
完整日志适合人类查看；
压缩记忆适合模型推理。

如果直接把所有原始评审记录持续塞进上下文，后期会出现：
- 成本变高
- 重点变模糊
- 旧噪音挤压新信息
- 代理越来越 “会回忆”，却越来越 “不聚焦”

---

##### 10. 为代码审查模板补上 “验收测试” 规则

当前实例的强项是多轮评审，但最佳实践是更进一步：让评审意见与验证动作绑定。

###### 推荐要求
当`Daedalus`给出`BLOCKING`时，同时要求它给出至少一个验证动作，例如：
- 需要新增什么测试
- 需要跑什么命令
- 需要验证什么边界条件

###### 示例
```md
[BLOCKING] WebSocket reconnect logic can duplicate subscriptions
Validation:
- add integration test for reconnect after network interruption
- verify client receives one stream only after three reconnect attempts
```

###### 结果
这会让审查从 “建议系统” 升级为 “可执行质量门禁”。

---

##### 一个更完整的落地方案

如果要把这个实例真正用于团队代码评审，推荐采用下面的流程：

```md
1. 开发者提交 patch 或 diff
2. Icarus 解释设计意图、实现范围、已知风险
3. Daedalus 输出结构化评审结果（含严重级别）
4. 系统将结果发送到 Slack
5. dialogue.sh 将本轮结果压缩写入两个代理的 MEMORY.md
6. 自动重启 gateway
7. 下一轮审查时，Daedalus 必须检查上轮 BLOCKING 是否已修复
8. 人类可在 Telegram 直接追问任一代理
```

---

##### 最值得借鉴的设计原则

从这个项目出发，最值得保留的不是 “两个 AI 会聊天”，而是下面这几条原则：

- **角色对立而互补**：一个生成，一个质疑
- **日志即知识资产**：过程可追踪，而不是黑盒
- **记忆是结构化摘要，不是原始堆积**
- **跨平台连续性比单次输出更有价值**
- **多轮反馈闭环比一次性审查更接近真实团队协作**

---

##### 结论

如果用`icarus-daedalus`来做 “代码审查团队”，最优实践不是单纯追求更长的代理对话，而是把它设计成一个：

- 角色清晰
- 输出结构化
- 记忆可压缩
- 历史可追责
- 跨平台连续
- 能追踪问题闭环

的双代理审查系统。

换句话说，这个项目最好的用法不是 “让两个 AI 很有戏剧性地讨论”，而是 “让两个 AI 形成长期、可继承、可验证的协作审查机制”。
