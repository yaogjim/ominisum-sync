## 正文

**Augment Code**

### 规范是代理时代的基础设施

在传统开发中，规格说明书大多是规划文档。一旦开始实施，随着系统的实际情况在编码过程中逐渐显现，它们很快就变得过时。

> 在 AI 原生工作流中，关系发生了反转。规格成为指导实施的动态契约，并且代理在构建过程中持续参考这些契约。

传统的 RFC 流程存在的原因很简单：探索实现的成本很高，因此团队必须在编写代码之前将设计前置到文档中。

那个约束不再成立。代理缩小了设计与实现之间的差距，使它们能够实时相互沟通。不再是一次性的设计文档，规范成为指导和评估实现的持久基础设施。

工程师在规范中定义意图和约束，代理探索实现空间，系统持续将规范作为事实来源进行参考。

#### 每一个设计过程中的差距

即使在有严格 RFC 流程的组织中，设计和实现仍然是串行的：你编写、评审、批准，然后构建。设计在代码存在之前一直停留在理论层面，而当有人发现 API 边界无法正常工作或数据模型无法扩展时，改变方向的成本很高。

这种差距对经验不足的工程师影响最大。撰写一份强有力的 RFC 需要预见你从未遇到过的实施陷阱，这是一种来自经验而非仅凭更努力思考的技能。最能从早期实施反馈中受益的工程师，往往最没有能力预测该反馈会揭示什么。

AI 工具有所帮助，但只是部分地。工程师现在可以在撰写 RFC 时，借助代理探索边界情况并对假设进行压力测试。生成的规范通常会更好，但基本工作流程并未改变：设计仍然先于实现。

#### AI 原生工作流程

In a truly AI-native environment, design and implementation stop being sequential. The implementer can draft a spec while simultaneously using agents — like

[Intent’s Coordinator agent](https://www.augmentcode.com/product/intent) — to explore, prototype (sometimes multiple designs in parallel), or even deploy something to staging. The spec and the implementation evolve together.

> 在 AI 原生工作流中，你不会等到实施三周后才发现界面无法正常工作，而是在规格说明仍在审核时就发现问题。

评审者不再评估纯粹理论性的设计，而是评估一个已经部分进行了现实压力测试的设计。更深层次的转变不仅仅是速度。而是规格说明成为了可操作的基础设施。它不再是描述系统的文档，而是成为了主动规范系统构建方式的文档。

当代理负责大部分实施工作时，他们会不断遇到模糊的决策：

- 我们应该扩大范围以支持 X 吗？
- 绕过这个界面是否可接受？
- 我们是否应该在这里引入另一个抽象？
- 这个实现是否与预期的架构匹配？

没有明确说明时，代理有两种选择：询问可能不掌握全部背景的人员，或者猜测。猜测指的是代理在无人授权的情况下，暗中做出范围和边界决策。

一份写得好的规范可以给代理提供一个锚点。当问题出现时，代理可以查阅规范，以保持在预期的架构范围内。

> 在传统工程中，规范指导人类。 在 AI 原生工程中，他们还指导编写代码的代理。

这是一个更高的标准：编写指导代理的规范需要更多的清晰度，而非更少。责任在于编写和批准规范的人员，而非遵循规范的代理。

![Image](https://pbs.twimg.com/media/HDTnLyfa0AA2dwv?format=jpg&name=large)

#### 一个具体的例子

我们最近在 Augment 公司看到了这种模式的实施，当时我们正在为企业租户构建用户组系统。该功能需要新的数据库模式、API 定义、设置解析模型以及分阶段推出计划，因此工程师开始编写一份涵盖整个系统的全面规范。

两天后，第一个实现 PR 合并，包含服务脚手架和 CRUD 端点。该 PR 还更新了规范。在构建存根时，工程师发现原始分阶段计划引入了一个依赖，该依赖会不必要地阻碍功能的推出。规范中的实施计划进行了调整，代码变更也一同发布。由于规范与代码并存，保持规范更新成为了实施工作的一部分。

几天后，第二个 PR 被合并，其中包含与真实模拟器对接的完整数据库层，且九个方法经过了端到端测试。当评审人员正在评审规范的设计决策时，核心实现已经验证并运行——这在传统上要到几周后才会发生。

> 评审人员并非在评估一种理论架构。他们正在评估一种已经针对真实数据库进行过压力测试的架构。

随着项目的推进，规格说明继续指导着工作。后续的 PR 遵循了其分阶段计划，而当后来的一次重构改变了数据访问模式时，规格说明中定义的架构边界使得这一替换变得简单直接，且无需修改逻辑。

这个规范并非是审批后就被归档的成果物，而是确保执行工作按计划推进的契约。

#### 问题出在哪里

当规范错误时，代理将比人类更快、更自信地忠实地执行错误的指令。当规范过于模糊时，代理会用听起来自信的决定填补空白，而这些决定没有人明确授权。

并且当并行原型设计未受控制时，团队可能会过早地确定一种实现方案，仅仅是因为可运行的代码在心理上比文档中的一段文字更难舍弃。

> 该规范提高了基准。它并未消除对经验丰富的评审的需求。

高级工程师仍然至关重要。区别在于，他们的评审变得更有成效，因为他们正在评估一个已经部分验证过的设计，而不是纯粹的理论提案。

#### 结论

规范是防止并行设计和实现陷入混乱的契约，为参与者提供架构护栏，并为评审者提供基于现实的评估依据。

> 现在，一名拥有规范和代理的初级工程师能够在架构护栏内进行构建，而这在过去需要多年经验才能预判。这并非因为高级工程师变得不再必要，而是因为当有可运行的代码摆在面前时，评审本身会更加敏锐。

对于每个工程组织来说，问题不在于这种工作流是否会出现，而在于你的规范是否是为代理（agents）编写的，而非仅供人类使用。

## 结构化（2）

### 2026-03-15 06:36:42

**主旨概括：**  
这篇文章的核心观点是：在 AI 代理参与开发的时代，**规格说明（spec）不再只是前期文档，而是持续指导实现的“基础设施”**。它不仅帮助人理解设计，还要作为代理写代码时的“行动准则”和“判断依据”。

---

##### 1. 传统开发中，spec 往往很快过时
- 过去的 spec 或 RFC，主要是**实施前的规划文档**。  
- 一旦开始编码，系统真实情况逐渐显现，文档很容易和实际代码脱节。  
- 原因在于：以前**试错成本高**，团队只能先把设计尽量想清楚，再进入实现。

**关键变化：**
- 现在 AI 代理能快速探索实现方案，**设计与实现不必再严格前后分离**。  
- 因此，spec 不该是“一次性文档”，而应成为**持续更新、持续被引用的真实依据**。

---

##### 2. 传统流程的核心问题：设计和实现是割裂的
- 即使在 RFC 流程很严格的团队里，通常也是：**写文档 → 评审 → 批准 → 开发**。  
- 问题是：设计在代码出现前始终停留在理论层面。  
- 很多问题，例如：
  - API 边界不合理  
  - 数据模型扩展性不足  
  往往要等实现后才暴露，而那时调整成本已经很高。

**对新人尤其不友好：**
- 写好 RFC 需要提前预判很多实现陷阱。  
- 这种能力往往来自经验，不是单靠“多想想”就能获得。  
- 结果是：**最需要早期反馈的人，往往最难预见问题。**

**AI 工具虽然有帮助，但还不够：**
- 它可以辅助工程师在写 RFC 时检查边界情况、验证假设。  
- 但如果流程仍然是“先设计、后实现”，本质上还是没变。

---

##### 3. AI-native 工作流：设计和实现同步演进
- 在真正 AI-native 的环境里，工程师可以**一边写 spec，一边让代理探索实现、做原型，甚至部署到 staging**。  
- 也就是说，**spec 和实现是一起演化的**，而不是一个先写完、另一个后开始。

**这样带来的好处：**
- 不必等到实现三周后才发现接口设计不行，  
  而是在 **spec 还处于评审阶段时就暴露问题**。  
- 评审者看到的不再只是理论方案，而是**已经被现实部分验证过的设计**。

**更深层的变化：**
- spec 不再只是“描述系统的文档”，而是**直接约束系统如何被构建的操作性基础设施**。

---

##### 4. 为什么 agent 时代更需要高质量 spec
当代理承担大量实现工作时，它会不断遇到模糊决策，比如：
- 是否要扩大范围支持某个需求？
- 能否绕过某个接口？
- 是否应该新增一层抽象？
- 当前实现是否符合预期架构？

**如果没有 spec，代理只有两种选择：**
1. 去问人，但人可能也没有完整上下文  
2. 自己猜

**风险在于：**
- 代理“猜”出来的决定，可能会悄悄改变范围、边界或架构，  
  而这些决定其实从未被正式授权。

**因此，高质量 spec 的作用是：**
- 给代理提供明确锚点  
- 让它在遇到问题时能回到 spec 判断  
- 保持实现始终落在既定架构和约束内

**文章强调：**
- 传统工程里，spec 主要是指导人；  
- AI-native 工程里，spec 还必须指导写代码的代理。  
- 所以对 spec 的要求**更高了，不是更低了**。  
- 责任仍然在**编写和审批 spec 的人**，不在执行 spec 的代理。

---

##### 5. 具体案例：Augment 构建企业用户组系统
文章给了一个实际案例，说明 spec 如何成为“活的合同”。

###### 项目背景
该功能涉及：
- 新的数据库 schema  
- API 定义  
- 设置解析模型  
- 分阶段上线计划

因此，工程师一开始写了一份**覆盖整个系统的完整 spec**。

###### 第一次 PR：2 天后就提交
- **两天后**，第一版实现 PR 就来了。  
- 内容包括：
  - 服务脚手架
  - CRUD 接口
  - 同时还更新了 spec

**发现的问题：**
- 工程师在搭建 stub 时发现：原来的分阶段计划里有一个依赖，会**不必要地阻碍功能发布**。  
- 于是：
  - spec 里的实施计划被同步修改  
  - 代码也一起更新并发布

**意义：**
- 因为 spec 和代码一起存在，**保持 spec 最新就成了实现工作的一部分**。

###### 第二次 PR：几天后进一步验证
- 又过了几天，第二个 PR 提交：
  - 完整数据库层已跑通真实模拟器（real emulator）
  - **9 个方法完成端到端测试**

**这意味着：**
- 评审者在讨论 spec 设计时，核心实现其实已经**验证并运行起来了**。  
- 这种情况在传统流程里，通常要**几周后**才会发生。

###### 后续演进
- 后续 PR 按照 spec 的分阶段计划继续推进。  
- 后来有一次重构改变了数据访问模式，  
  但因为 spec 早已定义清楚架构边界，这次替换非常顺利，**没有逻辑改动**。

**结论：**
- spec 不是审批后就归档的“附件”，  
- 而是持续保证实现不跑偏的**合同**。

---

##### 6. 这种模式也有风险
文章也明确指出，spec 并不是万能的。

###### 主要风险
- **如果 spec 本身是错的**：  
  代理会更快、更自信地把错误实现出来。
- **如果 spec 太模糊**：  
  代理会用看似合理的方式填空，但这些决定可能没人真正批准。
- **如果并行原型失控**：  
  团队可能因为“代码已经跑起来了”，就过早绑定某种实现方案。  
  毕竟，放弃一段已工作的代码，心理上比删掉文档里一段文字更难。

###### 因此：
- spec 只是**提高下限**，不是替代资深评审。  
- 高级工程师仍然很重要。  
- 只是他们现在评审的是**已经部分被现实验证过的设计**，效率更高、质量也更高。

---

##### 7. 结论：工程团队要开始为“agent 可读”写 spec
- spec 的价值，已经从“帮助设计”升级为：
  - 保证设计与实现并行时不失控  
  - 给 agent 提供架构护栏  
  - 给评审者提供更接近现实的依据

**文章最后的判断很明确：**
- 借助 spec + agent，初级工程师也能在清晰架构边界内完成过去需要多年经验才能做好的工作。  
- 这不是因为资深工程师不重要了，  
  而是因为**有真实代码辅助时，评审会更精准**。

**作者抛出的关键问题是：**
- 你的团队要思考的，不是这种工作流会不会到来，  
- 而是：**你们的 spec 是否已经写到能被 agent 消费，而不只是被人阅读。**

- 在传统开发中，规格说明书、RFC 等文档更多是“规划材料”，主要作用发生在编码之前。
- 一旦进入实施阶段，系统的真实约束和问题会在写代码时逐渐暴露，原先的设计文档就容易过时。
- 传统 RFC 流程之所以存在，是因为过去“试错实现”的成本很高，所以团队必须先把设计尽量想清楚，再开始编码。
- 但文章认为，这种前提正在被 AI 代理改变：设计与实现之间的距离被显著缩短了。

- 即使在 RFC 流程严格的团队中，工作方式通常仍然是：先写文档、再评审、再批准、最后编码。
- 这意味着设计长期停留在理论层面，直到真正实现时，大家才发现：
  - API 边界可能不合理
  - 数据模型可能无法扩展
  - 某些架构假设根本跑不通
- 一旦到这个阶段才发现问题，改方向的成本就会很高。

###### 对经验不足的工程师尤其不利

- 写一份高质量 RFC，需要提前预判很多“实施陷阱”。
- 这种能力更多来自经验，而不只是“更努力思考”。
- 因此，最需要尽早获得实施反馈的初级工程师，反而往往最难在文档阶段预测这些问题。

###### AI 工具虽有帮助，但还不够

- 文章指出，AI 工具已经能帮助工程师在写 RFC 时：
  - 探索边界情况
  - 压测假设
  - 改进规范质量
- 但如果流程本身没有改变，那么本质上仍然是“设计先于实现”，问题并未彻底解决。

##### 3. AI 原生工作流的变化：设计和实现同步演进

- 在真正的 AI 原生环境中，设计和实现不再是前后顺序，而是同时进行。
- 工程师可以一边写 spec，一边让代理去：
  - 探索方案
  - 做原型
  - 并行尝试多个设计
  - 甚至直接部署到 staging 环境
- 这样一来，规范和实现会一起迭代，而不是先有一份“定稿文档”，再慢慢落地。

###### 直接带来的改变

- 你不必等到 3 周后才发现某个接口设计有问题，可能在规范还在评审时就已经暴露出来。
- 评审者看到的，不再是纯理论设计，而是已经被现实验证过一部分的设计。
- 文章强调，更深层的变化不是“更快”，而是规范变成了“可操作的基础设施”：
  - 它不只是描述系统
  - 而是在主动约束系统该如何构建

##### 4. 为什么代理时代更需要高质量规范

当代理承担大量实施工作时，它们会不断遇到模糊决策，例如：

- 是否要为了支持某个需求而扩大范围？
- 能不能绕过某个接口？
- 这里要不要再引入一层抽象？
- 当前实现是否符合预期架构？

###### 如果规范不清楚，代理只有两条路

- 去问人，但被问的人未必掌握完整背景；
- 或者自己猜。

文章特别提醒：代理“猜测”不是中性行为，而是在没人明确授权的情况下，悄悄替团队做了范围、边界和架构决策。

###### 所以规范的作用升级了

- 一份好的规范，能为代理提供“锚点”。
- 当遇到不确定问题时，代理可以回到规范中查找依据，尽量不偏离预期架构。
- 传统工程里，规范主要是指导人类；
- AI 原生工程里，规范还要指导真正写代码的代理。

###### 这意味着标准更高，而不是更低

- 给代理看的规范，必须更清晰、更明确。
- 问题不在于代理是否足够聪明，而在于规范是否写得足够严谨。
- 文章认为，这份责任在编写和批准规范的人，而不是执行规范的代理。

##### 5. 一个具体案例：Augment 的用户组系统

文章用 Augment 公司内部一个功能开发案例，说明“规范作为动态契约”是如何运作的。

###### 项目背景

他们为企业租户构建“用户组系统”，涉及多个层面：

- 新的数据库模式
- API 定义
- 设置解析模型
- 分阶段上线计划

因此，工程师一开始就写了一份覆盖整个系统的全面规范。

###### 第一个关键节点：2 天后，第一个 PR 合并

- 时间点：仅仅两天后
- 结果：第一个实现 PR 已经合并
- 内容包括：
  - 服务脚手架
  - CRUD 端点
  - 对规范本身的更新

###### 这里发生了什么

- 工程师在搭建实现存根时发现，原来的分阶段上线计划里有一个依赖项，会不必要地阻碍功能推出。
- 于是他们：
  - 修改了规范中的实施计划
  - 同时提交了相应代码变更

这说明：规范不是开发前写完就放着，而是和代码一起更新，成为实施的一部分。

###### 第二个关键节点：几天后，第二个 PR 合并

- 内容包括：
  - 接入真实模拟器的完整数据库层
  - 9 个经过端到端测试的方法

###### 这个阶段的意义

- 当评审者还在讨论规范中的设计决策时，核心实现其实已经能跑并被验证了。
- 按传统流程，这类验证通常要几周后才出现。
- 因此评审者不是在看“纸面架构”，而是在看一个已经通过真实数据库压力测试的架构。

###### 后续价值

- 后续 PR 按照规范中的分阶段计划推进。
- 后来一次重构改变了数据访问模式，但由于规范已经定义好了架构边界，这种替换变得简单，而且不需要改业务逻辑。
- 这进一步说明：规范不是审批后归档的产物，而是确保执行持续按计划推进的契约。

##### 6. 这种模式也有风险，甚至可能放大错误

文章没有把 AI 原生工作流说得过于理想化，而是指出了几个重要风险。

###### 风险 1：规范错了，代理会更快地把错做大

- 如果规范本身有问题，代理会比人类更快、更自信地执行错误指令。
- 也就是说，AI 放大的不仅是效率，也可能放大错误。

###### 风险 2：规范模糊时，代理会“自信地脑补”

- 当规范留白太多时，代理会用听起来合理的决定去填补空白。
- 这些决定可能没人真正批准过，却已经体现在代码里。

###### 风险 3：并行原型可能让团队过早锁定方案

- 如果同时跑多个原型，但缺乏控制，团队可能会因为“某个方案已经能跑起来了”，就心理上更倾向保留它。
- 于是，代码可能过早压倒文档讨论，导致团队太早承诺某种实现路径。

##### 7. 高级工程师仍然重要，只是评审方式更有效了

- 文章明确表示：规范变成基础设施，并不意味着不需要资深工程师。
- 相反，高级工程师仍然非常关键。
- 变化在于，他们的评审会更高效，因为他们面对的不是纯理论提案，而是已经部分验证过的设计。
- 这让评审更具体、更锋利，也更接近真实系统行为。

##### 8. 结论：未来的问题不是“会不会发生”，而是“你的规范是否为代理而写”

文章最后给出了一个很明确的判断：

- 规范是避免“并行设计 + 并行实现”陷入混乱的契约；
- 它为执行者提供架构护栏；
- 也为评审者提供基于现实的判断依据。

###### 对组织的意义

- 在这种模式下，一个初级工程师如果拥有清晰规范和代理辅助，也能在架构护栏内完成过去需要多年经验才能做好的工作。
- 这不是因为高级工程师不重要了，而是因为“拿着可运行代码来评审”会让整个评审过程更有效。

###### 作者最终抛出的核心问题

- 对每个工程组织来说，真正的问题不是这种工作流会不会到来；
- 而是：你的规范，是否已经开始为代理（agents）编写，而不只是为人类编写。

##### 可直接理解的例子

可以把传统规范理解成“施工前画好的蓝图”，施工一开始，现场情况变化了，蓝图很快就失真。  
而 AI 原生时代的规范，更像“施工现场实时更新的总控图”：

- 工程师负责定义目标、边界和约束
- 代理负责快速试建、验证和推进实现
- 一旦发现现实问题，图纸和施工方案同步更新
- 后续所有人和代理都继续以这份更新后的规范为准

这样，规范就不再只是“说明书”，而变成了系统开发过程中的“控制中枢”。

#### 总结

这篇内容的核心观点是：

- 在传统开发里，规范/RFC 更像“开工前的计划书”，代码一写，文档很快过时。
- 在 AI 原生工作流里，规范会变成“持续生效的契约”和“系统基础设施”。
- 工程师负责在规范中写清楚目标、边界、约束；代理（agents）负责探索实现、原型验证、推进开发。
- 设计与实现不再是先后关系，而是同步迭代：一边写规范，一边让代理做验证、搭原型、跑实现。
- 但前提是：规范必须更清晰，否则代理会高效地执行错误，或者擅自填补模糊地带。

#### 解读

##### 1. 为什么说“规范是代理时代的基础设施”

过去写规范，更多是为了让人对齐认知。  
现在有了代理，规范不只是“给人看”，还变成了“给机器执行时参考”的依据。

可以把它理解成：

- 以前规范像“会议纪要”
- 现在规范更像“施工图 + 交通规则 + 验收标准”

也就是说，规范不再只是解释“我们想做什么”，还要能回答：

- 什么能做，什么不能做
- 架构边界在哪里
- 遇到分歧时按什么原则判断
- 这个实现算不算偏离原意

##### 2. 传统流程的问题在哪里

传统流程通常是：

1. 先写 RFC/方案
2. 再评审批准
3. 然后开始编码
4. 编码中才发现设计问题

问题在于，很多关键问题只有真正做出来才会暴露，比如：

- API 边界不合理
- 数据模型扩展性不够
- 分阶段上线方案有依赖冲突

所以传统流程容易出现一个现象：  
“设计的时候想得挺完整，真做时才发现不对，但这时改动成本已经高了。”

对初级工程师来说更难，因为他们往往还没有足够经验，无法提前预判实现中的坑。

##### 3. AI 原生工作流到底改变了什么

真正的变化不是“AI 写代码更快”，而是：

- 设计和实现开始并行
- 规范和代码一起演进
- 评审对象从“纸面方案”变成“已被部分验证的方案”

换句话说，评审不再只是讨论理论，而是基于真实原型、真实测试、真实运行结果来判断。

这会带来两个明显好处：

- 更早发现问题，减少后期返工
- 规范不容易沦为摆设，因为它必须跟着实现一起更新

##### 4. 为什么规范反而要写得更清楚

很多人会以为：有了 AI，文档要求可以低一点。  
这篇文章恰恰相反：有了代理后，规范要写得更清楚。

因为代理在执行时会不断遇到模糊问题，比如：

- 要不要顺手支持额外需求？
- 能不能绕过某个接口？
- 是否应该新增抽象层？
- 这个实现是否符合架构预期？

如果规范不清楚，代理就只能：

- 要么频繁打断人来问
- 要么自己猜

而“自己猜”是最危险的。  
因为代理可能会非常自信地做出没人明确授权的决定。

所以，代理时代最重要的不是“让代理更聪明”，而是“让规范足够明确，减少猜测空间”。

##### 5. 文中案例说明了什么

Augment 的案例说明了一件事：

- 规范不是先写完、审批完、归档完就结束
- 而是在每次 PR、每次实现验证后继续更新

这意味着规范和代码是联动的：

- 代码发现某个 rollout 方案不合理
- 规范立刻调整
- 后续实现继续按新规范推进

这其实是在把规范从“静态文档”变成“活文档”。  
它不是形式化产物，而是持续指导实现的控制面板。

##### 6. 这套模式的风险是什么

文章也没有把这件事说得太理想化，风险主要有三个：

- 规范错了：代理会更快地把错误放大
- 规范模糊：代理会擅自补全空白
- 原型太快：团队可能因为“代码已经能跑”而过早锁定方案

所以作者强调，高级工程师并没有变得不重要。  
相反，他们更重要，只是工作重心变化了：

- 以前更多是在“纸面设计”阶段把关
- 现在更多是在“已部分验证的设计”上做高质量评审

#### 我的意见

我基本认同这篇文章，尤其认同这句话：  
“规范要开始为代理而写，而不只是为人而写。”

我的看法是：

- 这不是在削弱文档，而是在抬高文档的价值。
- 以后好的规范，不只是“讲清楚背景和方案”，还要能“约束代理行为”。
- 团队竞争力会越来越体现在：能不能写出可执行、可验证、可持续更新的规范。

不过我也觉得要防两种极端：

- 一种是还停留在老式 RFC：写得很长，但无法指导代理执行
- 另一种是过度迷信原型：觉得“能跑就等于合理”

更务实的做法是：

- 用规范定义边界和原则
- 用代理快速做验证和探索
- 用评审来防止错误被高速放大

一句话说：

> 代理时代，规范不再只是“说明书”，而是“让人和 AI 都能协同工作的操作系统”。
