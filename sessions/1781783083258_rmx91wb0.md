#### 01\. 编写规格，而不是提示

当大多数人听到“300个代理”时，他们会脱口而出一句简短的话——“研究健身应用市场”——并期待能有出色的成果。这是最快的烧钱并得到无用结果的方式。

一行提示给群体赋予了决定一切的权限，而它会做出错误的决定。

将群体视为承包商，而非精灵。规范定义了需要收集的内容、有效内容的判定标准、允许的来源、确切的输出格式以及冲突时的处理方式。而大多数人忽略的部分是：Kimi 负责决定分解过程本身。

你不会像在 CrewAI 中那样构建代理，不会像 LangGraph 那样连接图结构，也不会像 AutoGen 那样定义结构。你只需描述目标——群体（swarm）会构建组织架构图。

规范是整个流程中唯一具有最高杠杆作用的工件，因为在步骤4中，它会成为你可复用技能的种子。

```python
# PROJECT: [name]
GOAL: [one sentence — the deliverable, not the topic]
SCOPE: [what's in, what's explicitly out]
RULES: [validation — what counts as a verified row/finding]
SOURCES: [official posts, papers, primary only — no aggregators]
OUTPUT: [file type / count / naming / format details]
ON CONFLICT: flag the row, never resolve silently
STOP CONDITION: [when to halt and report instead of guessing]
```

#### 02\. 在你花一分钱之前阅读分解计划

这是初次尝试者会跳过的步骤，而跳过它的代价最大。

在你提交规范后，Kimi 会向你展示执行计划在它执行之前 - 有多少个子代理、每个子代理负责什么、依赖顺序、步骤预算。

读一下。一个200个代理的群体分解错误会造成实实在在的金钱和时间损失。检查计划不花任何成本。你需要关注三个方面：它是否理解范围，代理数量对于任务规模是否合理，以及输出的计划是否符合你的实际需求。

一个值得注意的细节：4,000 步是一个整个群体的总协调预算 ，而不是每个代理 4,000 步。300 个代理的运行平均每个代理约\~13 步——简短、专门的子任务。这能告诉你你的任务是否符合这个形式。

```python
Show me the proposed decomposition before running:
- how many sub-agents, and what each one handles
- the dependency order (what blocks what)
- estimated step budget
- where the biggest quality-drop risk sits
Do NOT execute yet. Wait for my confirmation.
```

单行提示是一种愿望。规范是一种命令。群体执行命令。

#### 03\. 任其浪费——这就是关键

现在你运行它。最多300个子代理以并行波的形式启动。第一波处理完全独立的子任务。

当结果生成时，编排器对所有依赖它们的对象启动下一波操作，直到依赖图解析完成。

每个子代理在其自身的有界上下文窗口中工作。这就是结构上的技巧：单个代理在处理长任务时会填满其窗口，直到被淹没并开始进行有损摘要，此后的每一步推理都会变得更糟。

群体为每个子任务提供其独有的作用域上下文，因此只有结构化输出会流回协调器。 这就是为什么它不会在那些会导致单个代理崩溃的任务上崩溃。

因为 Kimi 的输入每百万 token 0.95 美元、输出每百万 token 4.00 美元，缓存命中时费用为 0.16 美元，你可以负担得起丢弃第一次尝试并重新运行它。低廉的用量成本改变了你愿意尝试的范围。

```python
Execute the spec end to end.
Parallelize wherever the plan allows.
Report progress every 30 steps.
Flag any blocker immediately — do not work around it silently.
If a sub-agent stalls >10 min, reassign or report.
Merge everything into the OUTPUT defined in the spec.
```

#### 04\. 要求真实文件，而非聊天回复

群体的输出不是窗口中的文本，而是直接融入你的工作的结构化交付物——而这正是大多数文章所忽略的部分。

一次运行就能生成 PDF、电子表格、数据集、演示文稿和可运行代码，所有这些都来自一次启动，因为 Kimi 可以原生输出这些格式。

> 所以始终以输出作为规范的开头。

"一份全面的报告"给予代理权限提前终止。"一份 40 页的 PDF 文件 + 一个包含 20,000 行的 CSV 文件 + 14 个可导出的 PNG 图表"为他们提供了一个需要达成的质量目标。

输出级别的特异性是差异。

```python
OUTPUT: [file type] / [count] / [naming] / [format detail]

# strong examples:
OUTPUT: 1 .xlsx, one row per model, + 200-word brief
OUTPUT: 30 HTML files, one per store, named by business
OUTPUT: 40-page PDF + 20,000-row CSV + 14 PNG charts
```

#### 05\. 将诚实模型指向输出并询问哪里出了问题

这是唯一一个不是 Kimi 负责的领域。群体的已知缺陷是：除非你明确要求核实，否则它会做出自信但引用不足的声明，而且独立的子代理有时会相互矛盾。“看起来完成了”和“是正确的”是完全不同的两回事。

Opus 4.8 正是为这个关卡设计的。Anthropic 报告称，它大约少 4 倍的可能性比 4.7 更不可能让自身代码中的缺陷未被察觉地通过，并且它是第一个在不加批判地报告有缺陷结果时得分为 0% 的 Claude。

它在这里的唯一任务是反驳，而非赞美。你支付高级代币不是为了生成内容，而是为了在步骤4将生成的内容永久保存为技能之前，捕捉到那个无声的缺陷。

只有当有可靠的主体检查工作时，廉价的产量才是一种优势。保持验证关卡。

#### 06\. 保存整个工作流作为一个技能

这就是让循环自我改进的关键节奏。在一次运行后你会重复，告诉 Kimi 将整个工作流程捕获为一个可复用的技能——输入格式、代理步骤、输出格式。

第一次运行需要20分钟。之后的每次运行需要30秒。

这就是“自学习”的真实含义。模型在你每次运行之间不会重新训练其权重。

它周围的系统变得越来越智能——你的技能库随着每个项目的推进而增长，并且未来的每一个群体都能自动运用这些技能。

竞争对手一周内无法复制那个库。它是由数月的实际运行构建而成的。

```python
Save this entire workflow as a reusable Skill: "[name]"
Capture:
- input format (what files / spec shape it expects)
- the agent steps that worked
- the output format and naming convention
- the validation rules from the spec
Next time I run this, I attach new files and get the same shape.
```

#### 07\. 导入你自己的文档作为群体知识

技能捕捉流程。文档转技能捕捉领域。上传你最出色的作品——一份已成交的提案、一份精心打磨的报告、一个演示文稿——Kimi 会将其结构和风格特征作为一项技能捕捉下来，未来每一个群体都能自动应用这项技能。

这就是它的叠加之处：你输入的每一个 PDF、转录文本或电子表格都会成为所有 300 个并行代理都能依据的上下文，而不是依赖通用训练数据。

你投喂得越多，每次后续运行就越准确。报告不再像普通 AI 那样，而是开始像你的工作那样。

```python
Capture this document as a reusable skill. Identify what makes it work:
- structure and section order
- tone and voice register
- depth of analysis per section
- the writing rhythm and formatting decisions
Save it as "[name]". Then produce a new document on [different topic]
using the captured skill — match the quality bar, not the content.
```

#### 08\. 将验证反馈转化为永久规则

步骤 5 捕获一个缺陷。步骤 8 确保群体再也不会再次出现这种情况。获取 Opus 的修复列表，不要仅仅修补输出——而是将这一教训嵌入到项目级约束文件中，Kimi 会在每次会话开始时自动读取该文件。

这是从自身失败中学习的循环。Opus 在第 1 次运行中标记的偏差在第 2 次运行中成为了一条硬规则。

经过几个项目后，你的约束文件会变成一种能够自我执行的动态文档——每次验证关卡需要捕获的内容都会越来越少。

```python
# CONSTRAINTS.md — loaded automatically
- every claimed figure must trace to a primary source or be flagged
- no silent conflict resolution — surface contradictions
- [rule distilled from last run's Opus feedback]
- [the mistake you never want repeated]
Scope-lock: do not touch anything outside the spec's SCOPE block.
```

#### 09\. 在新的输入上重新应用该技能 - 观察成本崩溃

现在到了收获的时候了。运行 #2 不是从零开始。它从你在步骤 6–8 中构建的技能、群体知识和约束文件开始。

相同的工作流程，新文件，设置的一小部分。

这就是“compounding”从一个流行词变成发票上实际支出项的地方。首次竞品监控运行需进行完整规格检查和验证通过。

第四个是针对已保存技能的30秒提示，输出更精准，因为它继承了之前所有运行中的每次修正。

```python
Run the saved skill "[name]" on these new inputs.
Apply CONSTRAINTS.md. Use the captured output format.
[attach new files]
Report only deviations from the skill's expected shape.
```

运行一次需要20分钟，运行第五十次需要30秒。这种差距正是构建循环而非单次提示的全部原因。

#### 10\. 将循环升级为后台代理

最后一步：一旦循环稳定且有技能支撑，你就不再手动启动它。

将 Kimi 指向触发点——一个日程安排、一次新文件上传、一个竞争对手的定价页面——并让它主动运行整个流程，只呈现交付物和偏差。

> 竞争监控是一个清晰的例子。

第1次运行：你手动构建并验证。当它成为后台代理时，它每周会并行检查所有竞争对手，并以零边际时间成本向你的收件箱发送一份简报。

循环中仅存的人是你设定的问题以及你对答案所做的决定。

```python
Run skill "[name]" on a weekly schedule.
Trigger: [schedule / new file / monitored URL]
On each run: execute the swarm, apply CONSTRAINTS.md,
verify, then deliver the OUTPUT + a diff vs last run.
Only ping me if a deviation crosses [threshold].
```

#### 深度总结

这篇文章的核心不是“Kimi 更会聊天”，而是：  
**把 Kimi 当成一个可复用、可验证、可迭代的智能体群体系统，而不是一次性问答工具。**

它提出一个闭环：

> **规范任务 → 群体执行 → 真实文件输出 → Opus 验证 → 沉淀为技能 → 固化约束 → 复用到新任务 → 后台自动运行**

关键观点：

1. **不要写提示词，要写规格书**
   - 明确目标、范围、规则、数据源、输出格式、冲突处理、停止条件。
   - 规格越清楚，群体执行越稳定。

2. **先看执行分解，再运行**
   - Kimi 会拆成多个子代理任务。
   - 用户要检查：任务范围是否理解、代理数量是否合理、依赖关系是否正确、风险在哪里。

3. **利用多代理并行解决长任务**
   - 单个模型做长任务容易上下文爆炸、遗忘、总结失真。
   - 群体把任务拆小，每个子代理只处理有限问题，再汇总结构化结果。

4. **输出必须是可交付文件，而不是聊天文本**
   - 比如 PDF、Excel、CSV、图表、代码、HTML。
   - 输出越具体，质量目标越清晰。

5. **用更强/更谨慎的模型做验证关卡**
   - 文中建议用 Opus 4.8 检查 Kimi 输出。
   - 重点不是让 Opus 写内容，而是让它挑错：证据不足、冲突、幻觉、格式不符。

6. **把成功流程保存成 Skill**
   - 一次成功运行后，沉淀为可复用技能。
   - 下次只换输入文件，沿用流程、格式和验证规则。

7. **把错误变成永久约束**
   - Opus 发现的问题，不只是修一次。
   - 应写入 `CONSTRAINTS.md`，让后续运行自动避免同类错误。

8. **最终变成后台代理**
   - 例如每周自动监控竞品、分析新文件、生成简报。
   - 人只负责设定问题和做决策。

一句话总结：

> 文章讲的是：用低成本多智能体负责规模化生产，用高质量验证模型负责纠错，再把流程、经验和约束沉淀下来，形成越来越便宜、越来越稳定的自动化工作系统。

#### 深入浅出解读

可以把它理解成一家公司里的工作流。

普通聊天模型像是：

> 你问一个聪明实习生一个问题，他现场回答你。

而这篇文章说的系统像是：

> 你给一家公司下项目需求，300 个员工分工干活，一个总监协调，一个审计员挑错，最后把成功方法写成 SOP，下次自动复用。

区别在这里：

| 普通用法 | 群体循环用法 |
|---|---|
| 问一句，答一句 | 写规格，跑流程 |
| 输出聊天文本 | 输出真实文件 |
| 每次从零开始 | 保存成技能复用 |
| 错了就手动改 | 错误写入约束 |
| 人反复启动 | 后台自动运行 |

真正有价值的不是“300 个代理”这个数字，而是三件事：

##### 1. 任务被工程化

目标是什么？

数据冲突怎么办？

这让 AI 从“聊天对象”变成“执行系统”。

##### 2. 经验被资产化

- 可复用流程；
- 输出模板；
- 数据校验规则；
- 常见错误约束；
- 项目知识库。

这才是所谓“自我改进”。

> 系统配置、流程、规则和技能库变聪明了。

低成本模型可以大量生成，但大量生成也会放大错误。

- 检查来源；

#### 辩证思考

##### 值得肯定的地方

###### 1. 从“模型崇拜”转向“系统能力”

文章真正先进的地方，是不再纠结单个模型谁最强，而是问：

> 如何组织多个模型完成复杂任务？

这接近真实生产力场景。  
企业不需要一个“最聪明聊天机器人”，而需要稳定、可审计、可复用的工作流。

---

###### 2. 把提示词变成 SOP

很多 AI 使用失败，不是模型太弱，而是用户输入太模糊。

“写个竞品分析”很容易得到泛泛而谈。  
但如果规定来源、字段、格式、校验标准，结果会稳定很多。

这说明：

> AI 时代，需求定义能力会变得更重要。

---

###### 3. 强调验证，是成熟信号

文章没有简单吹“AI 自动完成一切”，而是强调验证关卡。  
这是现实中非常关键的一点。

AI 的最大问题不是不会写，而是：

> 它可能很自信地写错。

所以“生成—审计—固化规则”的闭环，比单纯追求更大模型更可靠。

---

##### 需要警惕的地方

###### 1. “自我改进”容易被误解

这里的自我改进，不是模型自动训练自己、权重变强。  
更准确地说，是：

> 工作流、技能库、约束文件、项目知识不断积累。

这是一种系统层面的改进，不是模型本体的进化。

---

###### 2. 多代理不天然等于高质量

300 个代理听起来强，但如果任务拆解错误，可能只是：

- 300 倍噪音；
- 300 倍冲突；
- 300 倍幻觉；
- 300 倍协调成本。

多代理适合可拆解任务，比如资料搜集、表格整理、竞品监控。  
但不一定适合高度依赖统一判断、深度原创理论或复杂战略决策的任务。

---

###### 3. 验证模型也不是绝对真理

Opus 负责挑错，但它也可能漏检、误判或过度保守。  
所以关键任务仍需要：

- 人类专家复核；
- 原始数据追踪；
- 自动测试；
- 多模型交叉审查；
- 明确责任边界。

AI 审计可以降低风险，但不能完全替代责任主体。

---

###### 4. 成本低不代表没有成本

低 token 成本会鼓励反复试错，这是好事。  
但真实成本还包括：

- 设计规格的时间；
- 检查分解的时间；
- 验证输出的时间；
- 维护技能和约束的时间；
- 错误结果带来的决策风险。

所以它更适合高频、重复、有明确格式的任务。  
不适合只做一次、目标模糊、责任极高的任务。

---

#### 最精炼结论

这篇文章真正讲的不是 Kimi，也不是 Opus，而是一种 AI 工作范式：

> **用便宜模型做规模化执行，用强验证模型做质量闸门，用技能和约束沉淀经验，最终形成可复用的自动化生产系统。**

它的价值在于：

- 把 AI 从聊天工具变成工作流引擎；
- 把一次性提示变成长期资产；
- 把错误变成规则；
- 把人工重复劳动变成后台代理。

但也要清醒：

> 多代理不是魔法，自动化不是可靠性的同义词。  
> 真正的壁垒不是“用了哪个模型”，而是你有没有清晰规格、验证机制和持续沉淀的流程。

## 结构化（1）

### 2026-06-18 11:50:26

#### 自我改进循环：Kimi K2.6 的 300 智能体群体如何越用越强

文章主旨：Kimi K2.6 不应只被当作普通聊天框使用，它真正的价值在于用 **300 个并行智能体**完成复杂任务，并通过“执行—验证—沉淀—复用”的循环持续降低成本、提升质量。作者提出了一套由 Kimi 负责生成与执行、Opus 4.8 负责验证的工作流，让每次运行都能转化为可复用能力。

---

##### 1. Kimi K2.6 的核心能力不只是聊天

作者认为，大多数人只把 Kimi 当成问答工具，用完即关，但这只用了产品能力的一小部分。

关键点：

- Kimi K2.6 支持 **300 个并行子代理**。
- 每次运行有 **4000 个协调步骤**，相比 K2.5 的 **100 个代理 / 1500 步**大幅提升。
- 输出不是简单聊天文本，而是可以直接生成真实文件，例如：
  - 100+ 个文件；
  - 10 万字文献综述；
  - 20,000 行数据集；
  - PDF、表格、PPT、代码、图表等。

作者强调，真正重要的是：每次运行后，系统都应该留下可复用的技能、规范或约束，让下一次运行比上一次更好。

---

##### 2. 这不是单次提示，而是一个“自我改进循环”

文章的核心方法是建立一个持续复利的工作流：

1. Kimi 负责执行复杂任务；
2. Opus 4.8 负责检查结果是否可靠；
3. 把成功流程保存为技能；
4. 把错误总结成约束；
5. 下次运行时自动复用技能和约束。

作者认为，这与很多传统 AI 工作流不同。很多人用 LangGraph、CrewAI、AutoGen 等搭建流程，但第 50 次运行和第 1 次运行没有本质区别。而这里的目标是：**每次运行都让系统层面更聪明。**

---

##### 3. 第一步：写“规格”，不要只写提示词

作者认为，使用 300 个智能体时，最重要的不是随便写一句提示，而是写清楚任务规格。

错误示例：

> “研究健身应用市场。”

这种提示太模糊，会让智能体自行决定范围、来源和输出格式，容易产生无用结果。

更好的做法是写成结构化规格，包括：

- 项目名称；
- 目标；
- 范围；
- 验证规则；
- 数据来源；
- 输出格式；
- 冲突处理方式；
- 停止条件。

例如：

```text
GOAL: 交付一份竞品分析报告
SCOPE: 只分析美国市场，不包括欧洲市场
SOURCES: 只使用官方公告、论文和一手数据
OUTPUT: 40 页 PDF + 20,000 行 CSV + 14 张 PNG 图表
ON CONFLICT: 标记冲突，不要自行解决
```

作者强调：**单行提示是愿望，规格是命令。智能体群体执行的是命令。**

---

##### 4. 第二步：执行前先检查分解计划

在真正运行前，Kimi 会展示执行计划，包括：

- 会调用多少个子代理；
- 每个子代理负责什么；
- 任务之间的依赖关系；
- 预计步骤预算；
- 最大质量风险在哪里。

作者建议一定要先读计划，因为一个错误的 200 个代理任务分解，会浪费大量时间和成本。

重要数据：

- **4000 步是整个群体的总协调预算，不是每个代理 4000 步。**
- 如果是 300 个代理，平均每个代理大约只有 **13 步**。
- 这意味着每个代理应负责短小、明确、专业的子任务。

---

##### 5. 第三步：允许第一次运行“浪费”，因为低成本带来试错空间

Kimi 的优势之一是成本较低，使得用户可以承受试错和重跑。

文中提到的价格：

- 输入：每百万 token **0.95 美元**；
- 输出：每百万 token **4.00 美元**；
- 缓存命中：每百万 token **0.16 美元**。

作者认为，低成本改变了工作方式：用户可以先跑一次，发现问题后再迭代，而不是一次就追求完美。

同时，群体架构可以避免单个长上下文代理容易崩溃的问题：

- 单个代理处理长任务时，容易填满上下文窗口；
- 后续只能压缩总结，导致信息损失；
- 群体代理则让每个子代理处理有边界的小任务；
- 最终只把结构化结果交回协调器。

---

##### 6. 第四步：要求真实文件，而不是聊天回答

作者特别强调，Kimi 群体的输出应该是“可直接使用的交付物”，而不是聊天窗口里的长文本。

好的输出要求示例：

```text
OUTPUT: 1 个 .xlsx 文件，每个模型一行 + 200 字摘要
OUTPUT: 30 个 HTML 文件，每个门店一个，以商家名称命名
OUTPUT: 40 页 PDF + 20,000 行 CSV + 14 张 PNG 图表
```

作者认为：

- “写一份全面报告”太模糊；
- “40 页 PDF + 20,000 行 CSV + 14 张图表”才是清晰质量目标。

输出越具体，智能体越容易达到预期标准。

---

##### 7. 第五步：用 Opus 4.8 做验证关卡

作者指出，Kimi 群体有一个已知问题：如果不明确要求验证，它可能生成自信但引用不足的内容，或者不同子代理之间结果矛盾。

因此，文章建议引入 Opus 4.8 作为验证者。

Opus 4.8 的角色不是生成内容，而是“挑错”：

- 检查引用是否可靠；
- 找出数据冲突；
- 发现逻辑漏洞；
- 防止错误内容被保存为可复用技能。

文中提到，Anthropic 称 Opus 4.8 相比 4.7 更不容易让自身代码缺陷漏检，大约低 **4 倍**，并且在无批判报告有缺陷结果时表现更严格。

作者的核心观点是：

> 廉价产出只有在有可靠验证时才是优势。

---

##### 8. 第六步：把完整工作流保存为技能

一次任务完成并验证后，不要只拿走结果，而要让 Kimi 保存整个流程为可复用技能。

保存内容包括：

- 输入格式；
- 有效的代理步骤；
- 输出格式；
- 文件命名规范；
- 验证规则。

这样下一次只需要换输入文件，就能得到同样结构的输出。

作者举出的效率变化：

- 第一次运行可能需要 **20 分钟**；
- 后续运行可能只需要 **30 秒**。

这里的“自学习”不是模型权重重新训练，而是通过保存工作流、规则和经验，形成项目级能力库。

---

##### 9. 第七步：把自己的文档变成群体知识

用户还可以把自己的 PDF、转录文本、表格等输入给 Kimi，让它们成为所有子代理都能参考的上下文。

这意味着 300 个代理不是只依赖通用训练数据，而是可以基于用户自己的资料工作。

例如，可以让 Kimi 学习一份高质量报告的：

- 结构；
- 章节顺序；
- 语气；
- 分析深度；
- 写作节奏；
- 格式风格。

然后要求它在另一个主题上生成相同质量标准的新文档。

---

##### 10. 第八步：把验证反馈变成永久规则

Opus 4.8 找出错误后，不应只修改当前结果，而应把错误转化为长期约束。

例如写入 `CONSTRAINTS.md`：

```text
- 每个数字都必须追溯到一手来源，否则标记出来
- 不允许静默解决冲突，必须暴露矛盾
- 不处理超出 SCOPE 范围的内容
- 加入上次 Opus 反馈中发现的错误规则
```

这样，第一次运行中发现的问题，会在第二次运行中变成硬规则。

作者认为，经过多个项目后，这个约束文件会变成一个动态、自我强化的质量控制文档。

---

##### 11. 第九步：在新输入上复用技能，成本开始下降

当技能、知识和约束文件都建立后，后续任务就不再从零开始。

用户只需要：

```text
Run the saved skill "[name]" on these new inputs.
Apply CONSTRAINTS.md.
Use the captured output format.
```

结果是：

- 输出更快；
- 格式更稳定；
- 错误更少；
- 成本更低。

作者用竞品监控举例：

- 第一次运行需要完整规格、执行和验证；
- 第四次运行时，只需调用保存好的技能；
- 第五十次运行可能只需要 30 秒。

这就是作者所说的“复利”：每次运行都继承之前的修正。

---

##### 12. 第十步：把流程升级成后台代理

当流程稳定后，就不需要人工手动启动，而可以设定触发器自动运行。

触发方式包括：

- 每周定时；
- 新文件上传；
- 监控某个 URL；
- 竞争对手价格页变化。

例如竞品监控：

- 第一次由人手动构建并验证；
- 后续每周自动检查所有竞争对手；
- 自动生成简报；
- 只在异常超过阈值时提醒用户。

此时，人类只负责提出问题和根据结果做决策，执行、比对、验证都由系统完成。

---

##### 13. 结论：未来重点不是哪个模型最聪明，而是谁能形成更好的系统

文章最后指出，很多人仍在争论哪个模型“赢了”，但作者认为这个问题已经不够重要。

真正重要的是：

- 你能同时运行多少个智能体；
- 谁负责检查它们的工作；
- 你的技能和约束是否在持续进化；
- 今天的配置是否比昨天更好。

作者把 Kimi K2.6 这样的开放模型群体与 DeepSeek 曾经带来的冲击类比：开放模型可能再次重新定义封闭实验室以为自己掌握的优势。

最终建议是：

> 不要只把 Kimi 当聊天框。构建循环，验证结果，沉淀技能，让每次运行都更便宜、更准确、更有用。
