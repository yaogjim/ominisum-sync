### Takeaways on Long-running Autonomous Coding Agents

Some of the most interesting work in AI coding right now is not about better models but about how to run agents for days or weeks without them falling apart. Teams from

[Cursor](https://www.linkedin.com/feed/),

[Anthropic](https://www.linkedin.com/feed/)

,

[Factory](https://www.linkedin.com/feed/)

have been publishing experiments on long running autonomous coding agents.

Here are the takeaways from their studies:

𝟭. 𝗦𝗶𝗻𝗴𝗹𝗲 𝗮𝗴𝗲𝗻𝘁𝘀 𝗱𝗼 𝗻𝗼𝘁 𝘀𝗰𝗮𝗹𝗲

A single long running agent eventually loses the plot. Context fills up. It rereads the same files. It forgets earlier decisions. It starts drifting. The solution is not a smarter prompt. It is turning the agent into a system of agents.

𝟮. 𝗦𝘁𝗿𝘂𝗰𝘁𝘂𝗿𝗲 𝗯𝗲𝗮𝘁𝘀 𝘀𝘄𝗮𝗿𝗺𝘀

Running many agents in parallel helps, but naive swarms quickly break.

The systems that work best look more like organizations: planner → sub planners → workers → validators. Clear ownership, scoped tasks, and visible progress keep the system moving. Think AI org chart, not AI swarm.

𝟯. 𝗙𝗿𝗲𝘀𝗵 𝗰𝗼𝗻𝘁𝗲𝘅𝘁 𝗶𝘀 𝗮 𝗳𝗲𝗮𝘁𝘂𝗿𝗲

One surprising insight: persistent context is overrated. Many systems spin up fresh agent sessions for each task. Instead of relying on memory, agents rely on artifacts like READMEs, progress logs, and structured plans.

Good documentation becomes the agent’s memory.

𝟰. 𝗧𝗲𝘀𝘁𝘀 𝗯𝗲𝗰𝗼𝗺𝗲 𝘁𝗵𝗲 𝗰𝗼𝗻𝘁𝗿𝗼𝗹 𝘀𝘆𝘀𝘁𝗲𝗺

Validation is not an afterthought. It is the steering wheel. Agents need objective signals to know if they succeeded. That means:

- strong unit tests
- milestone checks
- regression validation

Without this, agents confidently build the wrong thing.

## 结构化（1）

### 2026-03-13 03:31:34

**主旨概括：**  
这篇文章总结了长时间运行的自主编程 Agent 的关键经验：真正的挑战不只是模型能力，而是如何让 Agent 连续工作几天甚至几周仍然稳定有效。核心结论是：**单个 Agent 不可靠，必须靠多 Agent 分工、文档化记忆和测试驱动来保证系统持续运转。**

---

##### 1. 单个 Agent 很难长期扩展
**关键点：**
- 单个长期运行的 Agent 容易 “跑偏”：
  - 上下文越来越满
  - 反复读取同样的文件
  - 忘记早期决策
  - 最后偏离原目标
- 解决办法不是继续优化提示词，而是把它变成**多 Agent 协作系统**。

**通俗理解：**
- 就像一个人连续加班很多天，容易忘事、重复劳动、方向混乱；
- 换成团队协作，效果通常更稳定。

---

##### 2. 有结构的协作，比 “蜂群式” 并行更有效
**关键点：**
- 多个 Agent 并行工作确实有帮助，但**简单粗暴的 “Agent 蜂群” 很容易失控**。
- 最有效的系统更像一家组织，而不是一群同时乱跑的机器人。
- 更好的结构是：
  **规划者 → 子规划者 → 执行者 → 验证者**
- 成功要素包括：
  - 责任清晰
  - 任务范围明确
  - 进度可见

**通俗理解：**
- 不是 “大家一起上” 就行，而是要像公司分工：
  - 有人定方向
  - 有人拆任务
  - 有人干活
  - 有人验收

---

##### 3. “新鲜上下文” 反而是优势
**关键点：**
- 一个重要发现是：**长期保留上下文并没有想象中那么重要**。
- 很多系统会为每个任务启动**全新的 Agent 会话**。
- Agent 不依赖 “记忆”，而依赖外部产物来接力，比如：
  - README
  - 进度日志
  - 结构化计划
- 因此，**好的文档就是 Agent 的记忆系统**。

**例子：**
- 与其让 Agent 一直带着庞大上下文工作，不如让它每次 “重新上岗”，直接读取最新的任务说明和日志。
- 这样更像交接班：不是靠脑子记，而是靠文档接力。

---

##### 4. 测试从 “收尾工作” 变成 “控制系统”
**关键点：**
- 验证不是最后才做的附加步骤，而是整个系统的 “方向盘”。
- Agent 必须有**客观信号**判断自己有没有做对。
- 关键机制包括：
  - 强单元测试
  - 里程碑检查
  - 回归验证
- 如果没有这些，Agent 很可能会**很自信地做错事**。

**通俗理解：**
- 测试不只是 “验收”，还是持续纠偏工具。
- 就像导航系统，不是到终点才看，而是一路都在校正方向。

---

##### 总结
**文章的核心观点可以归纳为四点：**
1. **单个长时运行 Agent 不可靠，必须系统化。**
2. **多 Agent 协作要讲结构，不能只靠并行堆数量。**
3. **文档和任务产物比长期上下文更重要。**
4. **测试和验证是 Agent 系统稳定运行的核心控制机制。**

**文中涉及的代表性团队：**
- Cursor
- Anthropic
- Factory

这些团队的实验共同说明：未来高效的 AI 编程系统，更像一个**有组织、有文档、有测试的工程团队**，而不是一个一直不停工作的 “超级单体 Agent”。

##### 实例：让 AI Agent 在 2 周内完成 “支付模块重构”

###### 任务背景
一个电商团队要把老旧的支付模块重构掉，目标包括：

- 支持新支付渠道
- 降低支付失败率
- 不影响现有订单流程
- 逐步上线，可回滚

这是一个典型的**长周期、高风险、跨文件、跨模块**任务，很适合用文中提到的方法。

---

##### 在这个实例上的最佳实践

###### 1) 不要让一个 Agent 从头干到尾
**错误做法**：一个 Agent 连续跑几天，负责读代码、写方案、改代码、测回归。  
**最佳实践**：拆成 “组织结构”，而不是 “单兵作战”。

建议角色分工：

- **Planner**：拆总任务、定义里程碑
- **Sub-planner**：拆支付路由、订单状态、回滚机制等子模块
- **Worker**：只负责一个明确改动
- **Validator**：专门跑测试、检查回归、核对验收标准

> 原则：**一个 Agent 只负责一个边界清晰的子任务。**

---

###### 2) 每个任务都用 “新上下文” 启动
**不要依赖 Agent 记忆。**  
每次启动 Worker，都只给它必要材料：

- `task.md`：本次任务目标
- `architecture.md`：支付模块架构说明
- `progress.md`：目前完成到哪一步
- `acceptance.md`：验收标准
- 相关文件清单

例如：

**Worker-3 的任务：**
> “只修改支付路由器，使新渠道`FastPay`能接入；不得改订单状态机；完成后补充单元测试。”

这样比 “延续上一个长对话” 更稳。

> 原则：**上下文靠文档传递，不靠会话记忆。**

---

###### 3) 用文档做 Agent 的 “外部记忆”
至少准备 4 类工件：

- **README /architecture**：系统结构
- **plan.md**：任务拆解与责任人
- **progress.md**：已完成、阻塞项、下一步
- **decision_log.md**：关键决策及原因

例如在`decision_log.md`写：

- 为什么先做支付路由，再改回调处理
- 为什么保留旧接口一周做灰度
- 为什么某个异常路径暂不重构

这样新 Agent 接手时，不会重复讨论、重复改错。

> 原则：**让任何一个新 Agent 在 5 分钟内接手任务。**

---

###### 4) 测试不是收尾，而是 “控制系统”
在支付重构里，测试应该先定义，而不是最后补。

建议测试分层：

- **单元测试**：支付路由、签名校验、重试逻辑
- **集成测试**：支付成功 / 失败 / 超时后的订单状态流转
- **回归测试**：旧支付渠道不受影响
- **里程碑检查**：
  - 新渠道可创建支付单
  - 回调可正确落单
  - 失败订单可重试
  - 灰度开关可关闭回滚

Validator 的职责不是 “看看代码对不对”，而是：

- 是否通过全部测试
- 是否满足验收标准
- 是否引入回归
- 是否偏离原计划

> 原则：**没有可验证信号，Agent 就会 “自信地做错事”。**

---

###### 5) 任务颗粒度要小到 “可验证”
不要给 Worker 一个大任务：
> “把支付系统重构完。”

要改成这种粒度：

- 增加`FastPayAdapter`
- 给支付路由新增渠道分发逻辑
- 为回调签名校验补测试
- 增加支付失败重试日志
- 写灰度开关配置

每个任务必须满足：

- 输入明确
- 输出明确
- 文件边界明确
- 测试方法明确

> 原则：**可执行任务 = 小范围改动 + 明确验收。**

---

##### 一套可直接落地的流程

###### 推荐工作流
1. **Planner**产出重构总计划与里程碑
2. **Sub-planner**拆成 5~10 个子任务
3. 每个**Worker**用新上下文领取一个任务
4. 提交代码 + 更新`progress.md`
5. **Validator**跑测试与验收
6. 不通过则回退到对应 Worker 修复
7. 阶段完成后，由 Planner 更新总计划

---

##### 最后的精炼结论

对于 “长时间 автономous coding agent” 这类任务，最佳实践不是：

- 更长 prompt
- 更多 Agent 乱跑
- 更依赖上下文记忆

而是这四件事：

1. **单 Agent 改为分层组织**
2. **每次任务使用新上下文**
3. **用文档与日志承载记忆**
4. **用测试与里程碑驱动执行**

#### 长周期 Autonomous Coding Agent 协作 SOP（1 页版）

##### 1. 适用场景
适用于以下任务：

- 持续数天到数周的开发任务
- 跨多个模块 / 文件的重构、迁移、集成
- 需要多轮验证、可回滚、可追踪的项目
- 适合 AI Agent 参与执行，但不能依赖单次长对话完成的工作

---

##### 2. 核心原则
###### 原则 1：不要让单个 Agent 长时间连续工作
- 单 Agent 容易上下文膨胀、重复阅读、遗忘决策、逐渐跑偏
- 必须拆成多角色协作，而不是靠一个 Agent “从头干到尾”

###### 原则 2：结构优于 swarm
采用固定分工，而不是让多个 Agent 自由并行乱跑：

- **Planner**：定义目标、拆阶段、定优先级
- **Sub-planner**：拆成具体子任务
- **Worker**：执行单一小任务
- **Validator**：测试、验收、回归检查

###### 原则 3：文档是 Agent 的记忆
不要依赖会话记忆，依赖外部工件：

- README /architecture
- plan.md
- progress.md
- decision_log.md
- acceptance.md

###### 原则 4：测试是控制系统
没有客观验证，Agent 会高概率 “自信做错”。

必须具备：

- 单元测试
- 集成测试
- 回归测试
- 里程碑验收标准

---

##### 3. 标准流程
###### Step 1：Planner 产出总计划
输出：

- 任务目标
- 范围边界
- 风险点
- 里程碑
- 回滚策略

###### Step 2：Sub-planner 拆子任务
每个子任务必须明确：

- 目标
- 涉及文件 / 模块
- 不允许修改的范围
- 完成标准
- 验证方式

###### Step 3：Worker 用 “新上下文” 执行
每次启动 Worker，仅提供：

- 当前任务说明
- 必要架构文档
- 最新 progress.md
- 验收标准
- 相关代码文件

**禁止**让 Worker 继承冗长历史对话作为主要上下文。

###### Step 4：Worker 交付结果
交付内容包括：

- 代码改动
- 测试补充 / 更新
- 变更说明
- progress.md 更新
- 必要时补 decision_log.md

###### Step 5：Validator 独立验证
验证内容：

- 是否通过测试
- 是否符合验收标准
- 是否引入回归
- 是否超出任务边界
- 是否需要返工

###### Step 6：阶段复盘
每完成一个里程碑：

- 更新总体进度
- 记录关键决策
- 清理失效计划
- 生成下一阶段任务列表

---

##### 4. 任务拆分标准
一个合格子任务应满足：

- **小**：可在一个短周期内完成
- **清**：目标明确，边界清晰
- **独立**：尽量减少与其他任务耦合
- **可验收**：有客观测试或检查方法

###### 示例
**好任务：**
- 为支付路由增加新渠道分发逻辑
- 为订单回调补充签名校验测试
- 增加灰度开关并补文档

**坏任务：**
- 把支付系统整体重构一下
- 优化这块代码
- 看看哪里能改进

---

##### 5. 必备文档模板
###### `plan.md`
记录：

- 项目目标
- 阶段划分
- 子任务清单
- 负责人 / Agent 角色
- 风险与依赖

###### `progress.md`
记录：

- 已完成
- 进行中
- 阻塞项
- 下一步

###### `decision_log.md`
记录：

- 关键技术决策
- 决策原因
- 被否决方案
- 后续影响

###### `acceptance.md`
记录：

- 每个里程碑验收条件
- 测试要求
- 回归要求
- 发布 / 回滚条件

---

##### 6. Do / Don’t
###### Do
- 任务分层管理
- 每次任务使用新上下文
- 用文档做交接
- 先定义测试，再执行改动
- 验证独立于执行

###### Don’t
- 让一个 Agent 持续跑很久不重置
- 把大量无关上下文都塞进提示词
- 不做文档沉淀
- 没有验收标准就开始改代码
- 用 “感觉对了” 代替测试通过

---

##### 7. 最低落地要求
团队要开始采用这套方式，至少做到：

- 有明确角色分工
- 所有任务必须拆小
- 所有任务必须有验收标准
- 所有阶段必须更新 progress.md
- 所有关键改动必须经过 Validator 检查

---

##### 8. 一句话总结
**长周期 AI 编程不是把 Agent 跑得更久，而是把协作结构、文档记忆和测试控制建立起来。**

这篇内容的本质不是 “模型更强”，而是：

> **把 Coding Agent 从一个会写代码的助手，升级成一个可持续运转的工程生产系统。**

长期运行的 autonomous coding agent，核心挑战不是生成能力，而是**稳定性、可控性、上下文治理、结果验证**。  
所以产品上要从 “对话式 AI 工具” 转向 “任务编排系统”；技术上要从 “单 Agent + Prompt” 转向 “多角色 + 工件驱动 + 验证闭环”。
