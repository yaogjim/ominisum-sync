## 分析要点

- **核心高价值点**：将单 ticket 的代码规范与规格依从性审查，与整分支的跨 ticket 一致性审查分开，明确了局部正确不等于整体正确。
- **留存建议**：保留编排架构与使用入口，实际采用前验证工具行为和质量保障效果（包含可复用的依赖调度、任务隔离、分层审查和状态恢复设计，与 Agent 开发直接相关。）

**知识要点**

- 编排器专注依赖调度、合并与测试，每个 ticket 使用独立会话和 worktree，可减少共享上下文及工作区干扰，但不能消除隐含语义依赖。
- 单 ticket 审查与整分支终审覆盖不同问题；跨文件漂移、组件语义冲突和规格漏项需要整体视角检查。
- 将运行状态记录为结构化事件流与账本，是支持任务中断恢复的设计思路；实际恢复可靠性仍需验证。

**行动项**

- 在已配置 π 且已通过 /to-tickets 生成依赖图的项目中，使用 pi install npm:pi-matt-implement-flow 安装扩展，并在干净会话运行 /pi-matt-implement-flow。
- 通过 /matt-flow-config 配置 Coder、Reviewer 和 Final-Reviewer 的模型及 Thinking 档位，试用时检查单 ticket 审查、合并测试和整分支终审结果。
- 对于存在隐含语义依赖的任务，先将并发度设为 1，结合整分支终审观察跨 ticket 一致性问题。

### 一条命令，落地 Matt 工作流

#### 我开源了 pi-matt-implement-flow

如果你也在用 Matt Pocock 经典的三段式 Agent 工作流（/grill-with-docs → /to-spec → /to-tickets），你一定遇到过最后一步 /implement 的尴尬：

1. 上下文爆炸：一张 spec 拆解出 8\~10 个 tickets，如果全塞进同一个会话串行写，越到后面模型越晕，幻觉与遗忘不可避免；
2. 人肉盯盘极其心累：哪些 ticket 互相依赖？哪些能并行？每跑完一个 ticket，人工就要手动开新会话、切分支、测一遍；
3. 裁判与运动员合体：写代码的是它，自己 review 自己的也是它，代码质量全凭模型自觉。

为了解决多 ticket 场景下的工程化落地问题，我开源了这个 pi 扩展包：pi-matt-implement-flow。

它的定位非常纯粹：完全保留上游的 /to-spec 和 /to-tickets 不动，只接管并重度增强 /implement —— 读取 ticket 依赖图，一条命令自动完成并行实现、双轴审查、冲突合并与集成测试。

🛠 安装方式（基于

[π](https://github.com/earendil-works/pi) 环境）：

> pi install npm:pi-matt-implement-flow

🚀 使用极简： 在 /to-tickets 产出依赖图后，开一个干净会话，直接输入：

> /pi-matt-implement-flow \[并发数 N\]

（如果不填 N 则默认按并发度 3 运行，自动读取项目 tickets 拓扑并开跑）。

#### 它是如何保障效率与质量的？

⚡️ 1. 真·依赖拓扑并行，完全隔离上下文

- 每个 ticket 独立 worktree：互不抢上下文，互不冲突；无依赖关系的 ticket 并行推进，有依赖的前置搞定后自动解锁触发；
- 编排器不写代码：主会话 Agent 严格作为“调度器”，只负责算依赖前沿（Frontier）、派活、合并与集成测试，彻底杜绝上下文污染。

🛡 2. 双轴逐 ticket Review + 闭环修复

- 严格双轴审查：Coder 提交后，独立的 Reviewer 会从「代码规范」与「Spec 依从性」双轴审查，发现漏洞直接打回给原 coder 修复；
- 支持异构模型：Coder、Reviewer、Final-Reviewer 均可独立配置不同的模型与 Thinking 档位（支持通过 /matt-flow-config 交互式配置）。比如用 DeepSeek/Claude 编码，用另一款模型审查，防止同模型盲区。

🧪 3. 合并即测试，当场暴露集成缺陷

- 每个 ticket 被 coder 交付并审过之后，合入 feature 分支会立刻执行项目全量集成测试。集成问题当场暴露、当场修，绝不把雷留到最后。多 ticket 合入遇到冲突也会自动解决。

🔍 4. 整分支终审（Final Review）

- 所有 tickets 全部合入后，触发整分支终审：专门排查单 ticket 视角看不见的跨文件漂移、组件语义冲突、以及 Spec 有要求但没有 ticket 承接的隐蔽漏项。没过会自动打回修复，直到通过终审。

💾 5. 本地事件流落盘，真正的“中断可续跑”

- 运行状态实时沉淀为本地结构化事件流（events.jsonl）与账本（ledger.md）。无论会话挂掉、手动中断，还是遇到 Agent 的上下文压缩（Compaction），重新运行命令即可瞬间对账恢复，绝不凭模型虚无的记忆重启。

💸 成本可控： 觉得逐 ticket review 耗费 Token？在 /matt-flow-config 中可随时一键关闭逐 ticket review（仅保留全量集成测试），但整分支终审依然为你兜底。

这不是商业项目，纯粹是自己在日常工程实践中把 Agent 推向复杂长任务时的开源沉淀，希望能帮到同样在探索 Agent 软件工程落地的小伙伴。

## 通俗精炼（1）

### 2026-10-12 08:46:51

#### 把多任务 AI 编码变成可调度、可审查、可恢复的工程流程

文章介绍了开源扩展 **pi-matt-implement-flow**：它接在 Matt Pocock 的需求澄清、规格编写和任务拆解流程之后，负责把多个开发任务真正执行完。**核心思路不是让一个 Agent 从头写到尾，而是把调度、编码、审查分开，再用依赖管理、集成测试和本地记录把整个流程串起来。**它试图解决的是：AI 能写代码，但复杂、长时间、多任务的软件开发仍然需要大量人工协调。

##### 1. 它只接管“实现”，不替代前面的需求与设计工作

原有工作流分为三步：

- `/grill-with-docs`：结合文档追问、澄清需求。
- `/to-spec`：形成 Spec，即说明软件应该做什么、满足哪些要求的规格文档。
- `/to-tickets`：把规格拆成可执行的开发任务，并产出任务之间的依赖关系。

这个扩展保留上述流程，只增强后续的 `/implement`。

作者举出的典型场景是：一份 Spec 拆成 **8～10 个 ticket**。如果让同一个 Agent 在一个会话里依次完成，会遇到三个问题：

1. **上下文越来越长。**前面的需求、代码和决策不断累积，模型越到后面越容易遗漏约束或混淆信息。
2. **人工协调负担重。**人要判断哪些任务能同时做、哪些必须等待，还要切换会话和分支、运行测试。
3. **写代码和审代码的是同一个 Agent。**它可能在审查时继续沿用编码时的错误理解，缺少独立检查。

因此，这个工具的定位是：**读取任务依赖图，自动组织并行编码、独立审查、冲突处理、合并和集成测试。**

##### 2. 并行执行靠任务依赖，而不是把所有任务一起启动

扩展为每个 ticket 建立独立的 **Git worktree**。可以把它理解为：同一个代码仓库下，给不同任务各自准备一份工作目录，避免多个 Agent 直接修改同一份工作文件；同时，每个任务由独立的编码上下文处理。

调度依据是任务依赖图：

- 没有未完成前置任务的 ticket，可以启动。
- 相互之间没有依赖的 ticket，可以并行。
- 依赖其他任务的 ticket，要等前置任务完成后才能启动。

例如，假设“实现接口”依赖“定义数据结构”，接口任务就不能先开跑；但另一个无关的页面任务可以同时进行。原文所说的 **Frontier（依赖前沿）**，就是当前已经满足启动条件的那一批任务。

主会话中的 Agent 则只充当“调度器”：计算哪些任务可运行、派发工作、组织合并和集成测试，**不直接写代码**。

这相当于让项目负责人只管理进度和交付，不把所有开发细节都塞进自己的工作记忆。关键不是单纯缩短上下文，而是让不同角色各自处理有限范围的信息。

**但工作目录隔离不等于最终代码不会冲突。**它能减少并行工作时的相互干扰，多个任务合并时仍可能出现代码冲突，或者更隐蔽的业务逻辑不一致。

##### 3. 质量检查分三层：单任务审查、合并测试、整分支终审

###### 单任务审查：既看代码质量，也看是否符合需求

Coder 完成一个 ticket 后，由独立 Reviewer 做“双轴审查”：

- **代码规范**：检查实现本身的质量。
- **Spec 依从性**：检查是否实现了规格要求，而不只是“代码能运行”。

发现问题后，会退回原 Coder 修复，形成“提交—审查—修改”的循环。

Coder、Reviewer 和 Final-Reviewer 可以分别配置不同模型及 Thinking 档位，也就是模型推理投入的等级。作者建议可以用一款模型编码、另一款模型审查，以降低它们重复犯同类错误的可能性。**这是减少共同盲区的手段，不是消除错误的保证。**

###### 每次合并后测试：尽早暴露组合问题

一个 ticket 交付并通过审查后，合入 feature 分支，随后立即运行项目的全量集成测试。

这里检查的不只是“这个任务单独能不能工作”，还包括“它与已经合入的代码放在一起，会不会出问题”。扩展也会自动处理多任务合并时的冲突。

这样做的价值是：问题在每次合并后就暴露，通常比全部任务完成后再集中排查更容易定位。**但测试能发现多少问题，仍取决于项目已有测试是否覆盖了相关行为。**

###### 整分支终审：补上单任务视角看不到的问题

所有 ticket 合入后，Final-Reviewer 再检查完整分支，重点包括：

- 不同文件或组件对同一业务规则的理解是否逐渐偏离。
- 各组件单独看似正确，组合后是否存在语义冲突。
- Spec 中是否有要求，在拆任务时就被遗漏，没有任何 ticket 承接。

终审不通过，流程会继续退回修复。**因此，最终检查不只是把单任务审查再做一遍，而是检查各部分是否共同构成了符合规格的完整实现。**

##### 4. 评论指出了关键边界：依赖图不一定包含所有业务依赖

一位回复者提出：worktree 可以隔离工作目录，但 ticket 之间还可能存在**没有写进依赖图的语义依赖**。

例如，两个任务都涉及同一条业务规则，其中一个改变了规则的含义，另一个却仍按旧理解实现。它们可能没有文本合并冲突，甚至各自测试都通过，但整体行为不一致。

作者明确回应：

- **逐 ticket 的双轴审查只看当前任务，不专门负责跨任务一致性。**
- 跨 ticket 问题主要由最终的 Final-Reviewer 检查。
- 如果特别担心这类问题，可以把并发数设为 **1**：每个新任务都在前一个任务已经合并的基础上开始，再配合终审。

这揭示了一个实际取舍：**并行越多，潜在速度收益越大，但也越依赖任务拆解、依赖关系和整体审查的质量。**串行执行能减少任务基于旧代码状态工作的风险，但并不能自动消除所有需求理解错误。

##### 5. 可恢复运行和成本配置，让它更适合长任务

扩展把运行状态持续写入本地：

- `events.jsonl`：结构化事件流，记录执行过程中发生的事情。
- `ledger.md`：账本，保存任务进度等状态信息。

会话崩溃、手动中断，或者发生 **Compaction（上下文压缩，即系统缩短此前的会话内容）** 后，重新运行命令即可根据这些记录恢复。

它的重要变化是：**任务进度不再只依赖模型“记得做到哪一步”，而是有外部记录可以核对。**这也是长时间运行的 Agent 流程比普通聊天式编码更可靠的基础之一。

成本方面，可以在 `/matt-flow-config` 中关闭逐 ticket 审查，以减少 Token 消耗；每次合并后的全量集成测试和最终整分支审查仍然保留。这个选项实质上是在**检查频率与运行成本之间做取舍**，并非关闭审查后质量保障完全不受影响。

###### 安装与使用

在 π 环境中安装：

```bash
pi install npm:pi-matt-implement-flow
```

当 `/to-tickets` 已产出依赖图后，打开一个干净会话，运行：

```text
/pi-matt-implement-flow [并发数 N]
```

不填写 `N` 时，默认并发数为 **3**。模型、Thinking 档位和审查选项可通过以下命令配置：

```text
/matt-flow-config
```

##### 6. 热门回复的延伸判断：瓶颈可能从“模型能否执行”转向“人能否组织和验证”

另一条热门回复把这一工具放在更大的 Agent 发展趋势中讨论：随着模型配合良好的 **skill**（可复用的任务方法和指令）与 **harness**（调度、工具调用、测试和恢复等执行框架），它能持续处理的任务越来越长。

回复者据自身体验认为，第一梯队模型在这些辅助下，已能承担小时甚至天级别的任务；随后，瓶颈会逐渐转移到人这一侧：

- 能否把需求转化成清晰、可执行的任务。
- 能否建立有效的验证机制，判断交付是否正确。
- 能承担多少 Token 成本。

他把这些能力合称为人的“带宽”：**不只是让 AI 多写代码，而是能够同时组织、验收和改进多少 AI 工作。**因此，能搭建自动评估与优化体系的人，可能比只用模型进行即兴编码的人更能放大产出。

不过，这属于回复者的趋势判断和个人体验，所引研究没有给出出处，原回复也被截断，不能视为经过完整验证的普遍结论。

就本文而言，更扎实的启示是：**复杂 AI 编码的落地，不只取决于模型能力，还取决于能否把任务边界、执行状态和质量验证变成明确的工程机制。**这个扩展提供了这样一套机制，但实际可靠性仍需要在具体项目中检验。
