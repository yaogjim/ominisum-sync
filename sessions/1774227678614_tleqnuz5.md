## 正文

**Leo**

同时用 Claude Code、Codex、OpenClaw，怎么让它们共享记忆？

我的方案很土：一套 markdown 文件 + 两层自动同步。

核心是 today.md。每个 session 开始自动读，结束自动写。OpenClaw 本地助手通过 symlink 共享同一份文件，每 5 分钟 cron 把项目状态、目标、踩坑记录同步过去，自动生成快照注入它的 system prompt。Codex 做代码审查时按需带上下文。

记忆层就是 markdown 文件，不绑任何平台。之前用 Gemini 当辅助也是这套，换模型只需要改同步脚本的目标路径。

跑了几个月，最大的体会：记忆同步的价值不在"AI 记住了什么"，在于你切工具的时候不用从头解释一遍。

## 结构化（1）

### 2026-03-23 03:17:30

#### 文章主旨

这篇内容主要讲的是：当一个人同时使用 `Claude Code`、`Codex`、`OpenClaw` 等多个 AI 工具时，如何让它们共享“工作记忆”，避免每次切换工具都要重复解释背景。  
作者给出的方案并不复杂，本质上是用一套通用的 `Markdown` 文件作为记忆载体，再配合自动同步机制来实现跨工具协作。

##### 1. 问题背景：多个 AI 工具并用，信息容易断层

- 原始问题是：怎么让 `Codex`、`Claude Code`、`OpenClaw` 这些工具“都知道”你前天、昨天、今天做了什么。
- 这个问题的核心，不是单个 AI 能不能记住，而是**人在切换工具时，如何不丢上下文**。
- 如果每次换一个工具都要重新描述项目状态、目标、历史问题，会非常耗时，也容易遗漏关键信息。

##### 2. 作者的整体方案：一套 Markdown 文件 + 两层自动同步

- 作者的方案很“土”，但实用：**用一套 Markdown 文件做统一记忆层**。
- 这套方案包含两个关键部分：
  - 一套共享的 `markdown` 文件；
  - 两层自动同步机制。
- 核心文件是 `today.md`：
  - 每个 session 开始时自动读取；
  - 每个 session 结束时自动写回。
- 这样做的好处是：不同 AI 工具都围绕同一个“记忆文件”工作，不需要各自维护独立上下文。

##### 3. 具体实现：不同工具通过同步机制共享同一份上下文

- `OpenClaw` 作为本地助手，通过 `symlink`（符号链接）直接共享同一份文件。
- 系统每 **5 分钟** 通过 `cron` 自动同步一次内容。
- 同步的内容包括：
  - 项目当前状态；
  - 当前目标；
  - 已踩过的坑和经验记录。
- 同步后还会自动生成“快照”，再注入到 `OpenClaw` 的 `system prompt` 中。
- `Codex` 在做代码审查时，则是**按需携带上下文**，不一定全量注入。

##### 4. 设计思路：记忆不绑定平台，方便替换模型

- 作者强调，真正的“记忆层”就是这些 `Markdown` 文件，而不是某个平台自带的记忆功能。
- 也就是说，这套方案**不依赖某个特定模型或产品**。
- 作者之前用 `Gemini` 做辅助时，用的也是同一套方法。
- 如果以后换模型，只需要改同步脚本的目标路径，不需要重建整套记忆体系。
- 这说明方案的重点是：**把记忆放在工具之外，保持可迁移性**。

##### 5. 作者的核心体会：价值不在“AI记住”，而在“切换时不用重讲”

- 作者已经用了这套方法**几个月**。
- 他最大的感受是：记忆同步真正有价值的地方，不是“AI 记住了什么”，而是**切换工具时不用从头解释一遍**。
- 换句话说，这套机制提升的主要是工作流效率，而不是单纯增强某个 AI 的记忆能力。

##### 6. 评论区补充：大家认可思路，也指出了潜在问题

###### 6.1 对方案价值的认同

- 有评论提到，这种共享记忆的方式，能支持“最佳工具组合”：
  - `Claude Code` 适合做方案和计划；
  - `Codex` 适合写代码和做审核；
  - `Gemini` 适合前端 UI。
- 在这种分工下，共享记忆可以明显减少重复说明背景的成本。
- 还有人表示自己也在做类似的系统，把**同一套文件系统当作唯一真相来源**。

###### 6.2 潜在风险：写入冲突

- 评论区也提出了一个实际问题：**写冲突**。
- 比如两个 agent 同时修改同一个 `markdown` 文件，再遇到 `cron` 同步时，就会出现“谁的版本生效”的问题。
- 有人建议更稳妥的方案是：
  - **分文件写入**；
  - **合并后再读取**；
  - 尽量避免多个 agent 直接竞争同一个文件。
- 这个提醒说明：方案虽然简单有效，但在多人/多 agent 并发场景下，还需要考虑一致性问题。

##### 7. 相关案例：评论区延伸出的 AI 工作流实践

- 热门回复里还出现了一些相关实践案例，反映出大家正在把 AI 工具做成更完整的工作流系统：
  - `@宝玉` 发布了一个新的 Skill：`baoyu-youtube-transcript`，输入 YouTube URL 就能抓取字幕，生成带章节、发言人和封面图的文档，而且**不需要 API Key**。
  - `@阿绎 AYi` 提到一个叫 **“Claude Code Game Studios”** 的项目，把 Claude Code 做成了完整游戏开发工作室，使用了 **48 个 AI 智能体**，并配有真实的工作室管理架构。
  - `@Reed Lu` 表示自己也在搭类似的 “Brain 系统”，甚至提到 `Claude Code` **200 美元/月** 的订阅额度，这个月基本都花在搭建这套系统上了。
- 这些案例说明，作者讨论的并不是一个孤立技巧，而是 AI 多工具协作趋势中的一个典型需求。

##### 总结

- 这篇内容的重点，不是讲复杂的技术架构，而是给出一个**低门槛、可迁移、跨平台**的 AI 记忆共享方案。
- 核心做法是：把记忆沉淀到统一的 `Markdown` 文件中，再通过 `symlink`、`cron`、快照注入等方式，让多个 AI 工具共享上下文。
- 最关键的价值在于：**人切换工具时，不必反复交代背景**，从而显著提升协作效率。
