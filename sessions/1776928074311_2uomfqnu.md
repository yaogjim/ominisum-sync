### 回答 · 2026-04-23 07:06:40

可以，先纠正两点：

- 你的命令里`curl -k`重复了，保留一个就行
- 如果你打的是`POST /v1/responses`，更建议用 Responses 形态的请求体；如果你想直接发`messages`，那更适合打`POST /v1/chat/completions`

最小可用测试我建议你先测这 3 个。

**1. 先测健康检查**
```bash
curl -s http://192.168.8.222:3060/healthz
```

正常时你应该能看到类似：
```json
{"ok":true,"wire_api":"responses"}
```

**2. 测`responses`路径，非流式**
这是最适合验证`codex-to-cursor`是否正常桥接的方式。

```bash
curl -k http://192.168.8.222:3060/v1/responses \
  -H "Authorization: Bearer sk-ddddd" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5.4",
    "input": "hi"
  }'
```

如果服务正常，它会返回 OpenAI Responses 风格的 JSON 结果。

如果你想写得更标准一点，也可以这样：
```bash
curl -k http://192.168.8.222:3060/v1/responses \
  -H "Authorization: Bearer sk-ddddd" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5.4",
    "input": [
      {
        "role": "user",
        "content": [
          { "type": "input_text", "text": "hi" }
        ]
      }
    ]
  }'
```

**3. 测`chat/completions`路径，非流式**
如果你就是想用你写的那种`messages`结构，那应该改成这个接口：

```bash
curl -k http://192.168.8.222:3060/v1/chat/completions \
  -H "Authorization: Bearer sk-ddddd" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5.4",
    "messages": [
      { "role": "user", "content": "hi" }
    ]
  }'
```

**流式测试**
如果你想确认 SSE 流式也通，可以加`-N`，避免缓冲。

`/v1/responses`流式：
```bash
curl -k -N http://192.168.8.222:3060/v1/responses \
  -H "Authorization: Bearer sk-ddddd" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5.4",
    "input": "hi",
    "stream": true
  }'
```

`/v1/chat/completions`流式：
```bash
curl -k -N http://192.168.8.222:3060/v1/chat/completions \
  -H "Authorization: Bearer sk-ddddd" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5.4",
    "messages": [
      { "role": "user", "content": "hi" }
    ],
    "stream": true
  }'
```

**如果你要测试快速线路**
README 里说明`/fast/v1/*`会强制加`service_tier:"priority"`，所以可以这样测：

```bash
curl -k http://192.168.8.222:3060/fast/v1/responses \
  -H "Authorization: Bearer sk-ddddd" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5.4",
    "input": "hi"
  }'
```

或者带默认思考强度的组合前缀：
```bash
curl -k http://192.168.8.222:3060/fast/high/v1/responses \
  -H "Authorization: Bearer sk-ddddd" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5.4",
    "input": "hi"
  }'
```

这里`high`只是 “路径默认值”；如果你请求体里自己传了`reasoning`或`reasoning_effort`，就会以请求体为准。

**最常见失败原因**
- `Authorization`里的 token 必须和服务端`.env`里的`OPENAI_API_KEY`完全一致，否则直接`401`
- `OPENAI_BASE_URL` / `UPSTREAM_BASE_URL`必须是上游根地址，不能带`/v1`
- 测`responses`时，最好用`input`，不要混用`messages`
- 如果你只是本地 HTTP 测试，其实不需要`-k`；`-k`主要用于 HTTPS 且证书不校验的场景

**你那条命令如果想 “最小修改后可用”**
有两种改法。

改成`chat/completions`：
```bash
curl -k http://192.168.8.222:3060/v1/chat/completions \
  -H "Authorization: Bearer sk-ddddd" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5.4",
    "messages": [{"role": "user", "content": "hi"}],
    "stream": true
  }'
```

改成真正的`responses`：
```bash
curl -k -N http://192.168.8.222:3060/v1/responses \
  -H "Authorization: Bearer sk-ddddd" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5.4",
    "input": "hi",
    "stream": true
  }'
```

1. “最小验证版”
2. “带 reasoning_effort 的版”
3. “带 previous_response_id 的多轮对话版”

我在本地启动了 codex-to-curse 服务后，在 cursor 中配置了 本地 服务地址http://192.168.8.222:3060/v1，在 cursor 中执行的时候出现错误：“Request failed with status code 400: {"error":{"type":"client","reason":"ssrf_blocked","message":"connection to private IP is blocked","retryable":false}}”

### 回答 · 2026-04-23 07:12:28

这是`Cursor`侧拦截了，不是`codex-to-cursor`本身返回的 400。

- 报错里的`ssrf_blocked`和`connection to private IP is blocked`表示：当前发起请求的那一层，不允许访问内网 / 私网地址
- `http://192.168.8.222:3060/v1`属于局域网私有 IP，所以被挡住了
- 这通常发生在 Cursor 某些走 “远端代发” 或云侧校验的 OpenAI 兼容请求链路里；它不是像本机`curl`一样直接从你的电脑访问目标地址

先区分两种情况：

**如果 Cursor 和`codex-to-cursor`在同一台机器上**
- 不要填`192.168.8.222`
- 改成`http://127.0.0.1:3060/v1`
- 或`http://localhost:3060/v1`

可优先试：
```text
http://127.0.0.1:3060/v1
```

**如果 Cursor 和服务不在同一台机器上**
- `192.168.8.222`这种内网地址，大概率会被 Cursor 拒绝
- 你需要把这个服务暴露成一个 “可公开访问的 HTTPS 域名”，再让 Cursor 连这个公网地址
- 常见做法：`Nginx/Caddy + 域名 + HTTPS`，或者临时用`Cloudflare Tunnel`、`ngrok`一类隧道

比如最终给 Cursor 配成：
```text
https://your-proxy.example.com/v1
```

你可以按这个顺序排查。

**1. 先确认服务本身没问题**
在运行`codex-to-cursor`的那台机器上执行：

```bash
curl -s http://127.0.0.1:3060/healthz
```

再测接口：
```bash
curl -s http://127.0.0.1:3060/v1/responses \
  -H "Authorization: Bearer 你的 OPENAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5.4",
    "input": "hi"
  }'
```

如果这两条通，说明`codex-to-cursor`正常，问题就在 Cursor 到你地址这段链路。

**2. 如果是本机 Cursor 连本机服务**
把 Cursor 里的 Base URL 从：
```text
http://192.168.8.222:3060/v1
```

改成：
```text
http://127.0.0.1:3060/v1
```

API Key 填你`.env`里的`OPENAI_API_KEY`。

**3. 如果 127.0.0.1 也不行**
那说明这个 Cursor 配置入口不是 “本机直连”，而是经过 Cursor 某个受限代理逻辑；这时就别再用任何私网地址了，包括：
- `127.0.0.1`
- `localhost`
- `192.168.x.x`
- `10.x.x.x`
- `172.16.x.x`到`172.31.x.x`

需要改成公网 HTTPS 地址。

**4. 最稳妥的方案**
把`codex-to-cursor`部署到一台有公网访问能力的机器上，然后反代成 HTTPS：

```text
https://your-domain.com/v1
```

Cursor 中填写：
- Base URL: `https://your-domain.com/v1`
- API Key: 与服务端`OPENAI_API_KEY`完全一致

**5. 临时验证方案**
如果你只是想快速确认 Cursor 能不能接通，不想正式上公网，可以用隧道工具把本地 3060 暴露出去，例如得到：

```text
https://abc123.trycloudflare.com/v1
```

然后把这个地址填进 Cursor。只要 Cursor 能访问公网 HTTPS，一般就不会触发 “private IP blocked”。

**结论**
- `codex-to-cursor`大概率没坏
- 根因是 Cursor 不允许访问`192.168.8.222`这样的私网地址
- 同机部署先试`http://127.0.0.1:3060/v1`
- 不同机或`127.0.0.1`也被拦时，改用公网`HTTPS`域名

如果你愿意，我可以继续直接给你两套可落地配置：
1. 本机`127.0.0.1`的 Cursor 填写方式  
2. 用`Cloudflare Tunnel`把`3060`暴露成公网 HTTPS 的最短步骤

我认同你说的 odex-to-cursor 部署到一台有公网访问能力的机器上，然后反代成 HTTPS：https://your-domain.com/v1。如果我的服务器上没有 https，能否直接使用 http://ip/v1?

### 回答 · 2026-04-23 07:14:48

不建议，而且大概率不行。

- `Cursor`这类客户端对自定义 OpenAI 兼容端点，通常更偏向接受`HTTPS`公网地址
- 就算它不拦`公网 IP`，直接用`http://ip/v1`也会有明文传输风险：你的`Authorization: Bearer ...`会裸奔
- 很多网络环境、代理层、客户端策略会直接拒绝非 HTTPS 的 API 端点，或行为不稳定
- 所以实际可用方案应当是：公网可访问 + 域名 + HTTPS

如果你现在只有一台公网服务器、还没有 HTTPS，常见有 3 条路。

**1. 最推荐：反代并签证书**
用`Nginx`或`Caddy`挂一个域名。

最终给 Cursor 配：
```text
https://your-domain.com/v1
```

优点：
- 最稳
- 长期可用
- 安全性正常

**2. 临时方案：Cloudflare Tunnel /ngrok**
即使你服务器本身没配 HTTPS，也可以让隧道服务给你一个公网 HTTPS 地址。

例如：
```text
https://xxxx.trycloudflare.com/v1
```

优点：
- 上手快
- 不用自己先折腾证书

**3. 理论上试`http:// 公网 IP/v1`**
可以试，但我不建议把它作为正式方案。

比如：
```text
http://123.123.123.123:3060/v1
```

可能遇到的问题：
- Cursor 直接拒绝非 HTTPS
- 某些中间链路拦截
- API Key 明文传输
- 后续你一旦切到域名 / 证书，又要重新改配置

**结论**
- `http://ip/v1`不是好的正式方案，也未必能被 Cursor 接受
- 最好直接做成`https:// 域名 /v1`
- 如果你现在没有证书，最省事的是先上`Cloudflare Tunnel`
- 如果你想长期稳定使用，就配`Nginx/Caddy + Let's Encrypt`

### 提问 · 2026-04-23 07:19:19

详述 本机 ngrok 穿透 到 127.0.0.1 3060 的方案

### 回答 · 2026-04-23 07:19:19

可以，这个方案很适合你现在这个场景：`codex-to-cursor`跑在你本机，`Cursor`又不肯直连`192.168.x.x` / `127.0.0.1`，那就用`ngrok`把本地`127.0.0.1:3060`暴露成一个公网`HTTPS`地址，再把这个公网地址填到 Cursor 里。

核心思路是：

- 本地运行`codex-to-cursor`，监听`127.0.0.1:3060`
- 本地运行`ngrok`
- `ngrok`分配一个公网`https://xxxx.ngrok-free.app`
- 外部访问这个 HTTPS 地址时，流量被转发到你本机的`127.0.0.1:3060`
- Cursor 里填写`https://xxxx.ngrok-free.app/v1`

你可以按下面做。

**整体结构**

```text
Cursor
  -> https://xxxx.ngrok-free.app/v1
  -> ngrok 公网入口
  -> 你的本机 ngrok 客户端
  -> http://127.0.0.1:3060
  -> codex-to-cursor
  -> 上游 Sub2API / Codex 网关
```

**一、先确认本地服务本身是通的**

在启动`ngrok`之前，先确保`codex-to-cursor`已经在本机正常监听。

你本机应该至少能通过下面两类地址访问：

- `http://127.0.0.1:3060/healthz`
- `http://127.0.0.1:3060/v1/responses`

先用本机测试：

```bash
curl -s http://127.0.0.1:3060/healthz
```

预期类似：
```json
{"ok":true,"wire_api":"responses"}
```

再测接口：

```bash
curl -s http://127.0.0.1:3060/v1/responses \
  -H "Authorization: Bearer 你的 OPENAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5.4",
    "input": "hi"
  }'
```

如果这里都不通，就先不要折腾`ngrok`，先把`codex-to-cursor`本地跑通。

**二、安装并登录 ngrok**

你需要先有一个`ngrok`账号，因为新版通常需要登录并绑定`authtoken`。

通常流程是：

- 去`ngrok`官网注册账号
- 下载对应系统的`ngrok`
- 登录控制台，拿到你的`authtoken`
- 在本机执行一次授权绑定

典型授权命令长这样：

```bash
ngrok config add-authtoken 你的 authtoken
```

执行后，`ngrok`会把 token 写入本地配置文件，之后就不用每次重复设置。

**三、启动到本地 3060 的 HTTP 隧道**

你的本地服务是 HTTP，并监听在`127.0.0.1:3060`，所以直接开一个 HTTP tunnel 即可：

```bash
ngrok http 127.0.0.1:3060
```

或者：

```bash
ngrok http http://127.0.0.1:3060
```

启动后，终端里会出现类似信息：

```text
Forwarding  https://abc12345.ngrok-free.app -> http://127.0.0.1:3060
Forwarding  http://abc12345.ngrok-free.app  -> http://127.0.0.1:3060
```

这里最重要的是这个公网 HTTPS 地址：

```text
https://abc12345.ngrok-free.app
```

这个地址就是你要给 Cursor 用的外网入口。

**四、先不要急着配 Cursor，先用 curl 测 ngrok 地址**

先从你本机直接打这个`ngrok`地址，确认穿透链路可用。

健康检查：

```bash
curl -s https://abc12345.ngrok-free.app/healthz
```

如果正常，会返回健康 JSON。

再测`responses`：

```bash
curl -s https://abc12345.ngrok-free.app/v1/responses \
  -H "Authorization: Bearer 你的 OPENAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5.4",
    "input": "hi"
  }'
```

流式测试：

```bash
curl -N https://abc12345.ngrok-free.app/v1/responses \
  -H "Authorization: Bearer 你的 OPENAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5.4",
    "input": "hi",
    "stream": true
  }'
```

如果这一步通了，基本说明：

- 本地`codex-to-cursor`正常
- `ngrok`转发正常
- 公网 HTTPS 地址可以工作

**五、在 Cursor 中怎么填**

假设`ngrok`给你的地址是：

```text
https://abc12345.ngrok-free.app
```

那 Cursor 里的 Base URL 应该填：

```text
https://abc12345.ngrok-free.app/v1
```

不要填成：

```text
https://abc12345.ngrok-free.app
```

也不要填成本地地址：

```text
http://127.0.0.1:3060/v1
```

API Key 里填：

```text
你的 OPENAI_API_KEY
```

并且这个值必须和`codex-to-cursor`服务端`.env`中的`OPENAI_API_KEY`完全一致。

如果你想走快速线路，也可以填：

```text
https://abc12345.ngrok-free.app/fast/v1
```

如果你想固定路径默认思考强度，也可以填：

```text
https://abc12345.ngrok-free.app/fast/high/v1
```

或者：

```text
https://abc12345.ngrok-free.app/default/xhigh/v1
```

**六、推荐的本地启动顺序**

每次使用时建议按这个顺序：

1. 启动`codex-to-cursor`
2. 本机`curl http://127.0.0.1:3060/healthz`确认服务活着
3. 启动`ngrok http 127.0.0.1:3060`
4. 复制新的`https://xxxx.ngrok-free.app`
5. 本机`curl https://xxxx.ngrok-free.app/healthz`再确认一次
6. 把 Cursor 的 Base URL 更新成`https://xxxx.ngrok-free.app/v1`

**七、免费版 ngrok 最常见的问题**

**1）域名会变**
- 免费版`ngrok`每次重启，公网地址通常会变
- 这意味着你每次重新开 tunnel 后，可能都要去 Cursor 里更新 Base URL

比如今天是：
```text
https://abc12345.ngrok-free.app/v1
```

明天可能变成：
```text
https://xyz98765.ngrok-free.app/v1
```

**2）必须保持 ngrok 进程在线**
- 只要`ngrok`窗口关了，公网入口就失效
- 所以 Cursor 请求失败时，要先检查是不是`ngrok`断了

**3）你本机也必须在线**
- `ngrok`只是把公网请求转发回你的本机
- 如果本机关机、休眠、断网，Cursor 就连不上

**4）有些账号有速率 / 连接限制**
- 免费版一般够个人测试
- 但不适合长时间高频稳定生产使用

**八、建议把 codex-to-cursor 只绑定在本地回环地址**

如果你的目的只是让`ngrok`来转发，建议`codex-to-cursor`只监听本地而不是裸露到局域网。

理想形态是：

- `codex-to-cursor`监听`127.0.0.1:3060`
- `ngrok`转发到`127.0.0.1:3060`

这样更安全，因为别人无法直接通过你局域网 IP 撞这个服务，只能通过`ngrok`分配的 HTTPS 地址访问。

当然，真正的保护仍然是这层：

- 所有`POST /v1/*`都要求`Authorization: Bearer &lt;OPENAI_API_KEY>`

也就是说，即使`ngrok`地址被别人知道，没有正确 Bearer token 也过不了。

**九、安全上你要注意什么**

这个方案虽然方便，但有几个必须注意的点。

- 不要把`ngrok`公网地址随便发到公开场所
- 不要使用过于简单的`OPENAI_API_KEY`
- 如果怀疑地址泄露，直接修改服务端`.env`里的`OPENAI_API_KEY`
- 修改后，Cursor 里的 API Key 也要同步改

### 回答 · 2026-04-23 08:20:25

它本质上是 “显示名 / 选择入口” 和 “实际传给代理的模型 ID” 之间的区别。

先说结论：

- `codex-to-cursor`里真正默认使用的模型 ID 是`gpt-5.4`
- README 里推荐你在 Cursor 额外加一个 “自定义模型名称” `gpt 5.4`，主要是为了让它更容易在 Cursor UI 里被选中、显示得更自然
- `gpt 5.4`和`gpt-5.4`不一定是同一个层面的东西：前者更像 Cursor 里的 “展示名 / 别名”，后者是发给 API 的 “模型标识”
- 是否能被正确识别，取决于 Cursor 最终发出的请求体里`model`字段到底是什么

你可以把这三者理解成：

- Cursor UI 里看到的名字：`gpt 5.4`
- 请求里真正传出的模型 ID：通常应是`gpt-5.4`
- `codex-to-cursor`在没收到`model`时兜底补的默认值：`gpt-5.4`

**它们分别是什么**

- `Cursor 中的 gpt 5.4`
  - 更像是你在客户端里手动添加的 “自定义模型名称”
  - 主要作用是让你在模型列表里有个可选项
  - 它未必等于最终 HTTP 请求里的`model`原样值

- `Cursor 中的 gpt-5.4`
  - 如果 Cursor 支持你直接把这个作为模型 ID 发出去，那它就是更接近 API 语义的 “真实模型名”
  - 这通常更直接，也更少歧义

- `codex-to-cursor 默认模型 gpt-5.4`
  - 这是服务端兜底值
  - 只有在客户端请求里没传`model`时，代理才会自动补上它

也就是说，服务端默认值不是 “强制覆盖”，而是 “缺省填充”。

**为什么 README 推荐写`gpt 5.4`而不是`gpt-5.4`**

这通常是出于 Cursor 的产品 / UI 行为考虑，不是 API 协议本身要求。

常见原因有几个：

- Cursor 的模型选择界面，可能更偏向 “人类可读名称”
- 有些客户端在展示层会把带连字符的模型 ID 处理得不自然
- 某些版本的 Cursor 对 “自定义模型” 更像是保存一个显示标签，而不是严格的 API model ID
- 用`gpt 5.4`更接近官方产品文案风格，用户在界面里更容易辨认

所以 README 那句话 “推荐在 Cursor 中额外增加一个自定义模型名称，填写为`gpt 5.4`” 更像是在说：

- 为了好找、好选、好显示，你在 Cursor 里可以建一个看起来舒服的名称

它不是在说：

- 上游 API 必须认识`gpt 5.4`

API 通常更可能认识的是`gpt-5.4`这种模型 ID，而不是带空格的自然语言名称。

**它如何被识别，关键看 Cursor 发出的请求**

真正决定行为的是这个：

```json
{
  "model": "???"
}
```

你在 Cursor 里启用一个模型后，最终会发生两种可能之一。

**情况 1：Cursor 把`gpt 5.4`映射成真正的 API 模型 ID**
比如最终发出去的是：

```json
{
  "model": "gpt-5.4"
}
```

那这是最理想的情况。

链路就是：

- 你在 UI 里选的是`gpt 5.4`
- Cursor 内部把它当成一个显示名
- 真正请求 API 时发的是`gpt-5.4`
- `codex-to-cursor`收到后直接转发这个模型 ID
- 上游按`gpt-5.4`处理

这种情况下，一切正常。

**情况 2：Cursor 直接把`gpt 5.4`原样发出去**
如果最终发的是：

```json
{
  "model": "gpt 5.4"
}
```

那就要看你的上游是否接受这个名字了。

大多数 OpenAI 兼容接口更可能要求：

```json
"model": "gpt-5.4"
```

而不是：

```json
"model": "gpt 5.4"
```

这时如果上游不认识`gpt 5.4`，可能出现：

- `400 model not found`
- `404 model not found`
- 某些兼容网关直接给你`503`或其它非标准错误

所以`gpt 5.4`能不能用，不取决于 README 推荐了什么，而取决于 Cursor 最终请求里发的是哪个字符串。

**`codex-to-cursor`会不会自动把`gpt 5.4`变成`gpt-5.4`？**

按照 README 的描述，它没有提到有 “模型别名归一化” 这层逻辑。

它做的是：

- `/v1/responses`转成上游`/v1/chat/completions`
- 处理一部分兼容字段
- 如果没传`model`，就用默认的`gpt-5.4`

但没有说：

- 如果传的是`gpt 5.4`，自动替换成`gpt-5.4`

所以通常应当假设：

- 传什么 model，它就基本用什么 model
- 除非代码里专门做了映射，否则不会帮你改名

这点很关键。

**三者之间的真实关系**

你可以用这个表来理解：

```text
1. Cursor 自定义模型名：gpt 5.4
   作用：给你在 UI 里选模型
   性质：可能只是显示名，也可能被原样当成请求 model

2. Cursor/API 实际 model：gpt-5.4 或 gpt 5.4
   作用：真正发给 codex-to-cursor 的字段
   性质：这才决定上游能否识别

3. codex-to-cursor 默认 model：gpt-5.4
   作用：当请求里没带 model 时才兜底
   性质：不会天然覆盖客户端已传入的 model
```

**最重要的一点：服务端默认模型只在 “未显式传入 model” 时生效**

比如：

客户端发：
```json
{
  "input": "你好"
}
```

那代理会补：
```json
{
  "model": "gpt-5.4"
}
```

但如果客户端发：
```json
{
  "model": "gpt 5.4",
  "input": "你好"
}
```

那代理通常会继续用：
```json
{
  "model": "gpt 5.4"
}
```

不会因为它自己的默认值是`gpt-5.4`就替换掉客户端传入值。

**如果我在 Cursor 中配置了`gpt 5.4`并启用，它如何被识别？**

答案是：分两层识别。

第一层，Cursor 自己识别：
- Cursor 把它当成你添加的一个模型项
- 让你在 UI 中可以选这个名字

第二层，代理 / 上游识别：
- 取决于 Cursor 请求时把`model`发成什么
- 如果发成`gpt-5.4`，代理和上游通常更容易识别
- 如果发成`gpt 5.4`，是否识别成功要看代理是否做映射、上游是否支持这个别名

所以真正要验证的不是 “Cursor 里显示什么”，而是 “HTTP 请求里 model 到底是什么”。

**怎么确认它到底是怎么被识别的**

你现在这个项目日志已经很详细了，最简单的办法就是看代理日志中的转发内容。

如果你在 Cursor 中选了`gpt 5.4`，然后发一个请求，重点看日志里类似：

```json
"translatedChatRequest": {
  "model": "..."
}
```

或者：

```json
"request": {
  "model": "..."
}
```

如果日志里显示：

```json
"model":"gpt-5.4"
```

说明：
- Cursor UI 里虽然叫`gpt 5.4`
- 但最终请求用的是`gpt-5.4`
- 这是理想状态

如果日志里显示：

```json
"model":"gpt 5.4"
```

说明：
- Cursor 直接把这个显示名原样当作 API model 发出来了
- 那你就得确认上游是否支持这个字符串
- 若不支持，建议改回`gpt-5.4`

**实操建议**

我建议你这样处理，最稳。

- 如果 Cursor 允许你自定义 “显示名” 和 “实际模型 ID” 分开：
  - 显示名写`gpt 5.4`
  - 实际模型 ID 写`gpt-5.4`

- 如果 Cursor 只有一个字段，且它会把你填的内容原样发给 API：
  - 直接填`gpt-5.4`
  - 不要填`gpt 5.4`

- 如果你已经填了`gpt 5.4`：
  - 发一次请求
  - 看`codex-to-cursor`日志里的`model`
  - 由日志确认它到底是显示名还是实际 ID

**为什么 README 还会这样建议**
因为作者大概率是在某个 Cursor 版本里观察到：

- UI 上添加`gpt 5.4`更容易在模型列表中工作
- 或更接近 Cursor 对自定义模型展示的习惯

但这更像是 “客户端使用技巧”，不是服务端协议要求。

**一句话记忆**
- `gpt 5.4`：更像 Cursor 里的展示名 / 自定义入口
- `gpt-5.4`：更像 API 真正使用的模型 ID
- `codex-to-cursor`默认`gpt-5.4`：只在你没传`model`时才兜底
