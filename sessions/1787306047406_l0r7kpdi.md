## 正文

**Wei**

最近在帮一个百人以上的研发部门做 AI 流程自动化，卡在技术选型上了。

团队有很深的 domain knowledge，也积累了一批 Skill 和 RAG。生产环境必须使用开源模型，暂时按 DeepSeek V4 Flash 来设计。

现在 Agent 已经能在本地完成阶段性任务，但完整流程仍然需要人类接力。最终目标是让项目管理软件里的 issue 自动触发 Agent，调用内部工具和数据，完成判断、统计、代码追踪，再把结论写回项目记录。

目前考虑两条路线。

1\. Hermes Agent 配合 Goal 和 Cron，内部补齐 Skill、Codebase 和 MCP，让 Agent 自己跑完整流程。

2\. LangGraph 配合 OpenCode，用确定性的 DAG 固定流程，每一步都创建独立环境执行和验收。

我的直觉是，固定且高风险的主流程交给 LangGraph，探索性强、步骤不确定的任务交给 Hermes。

朋友们做企业 Agent 时更倾向哪一种？全自治，还是确定性工作流加 Agent？

## 结构化（1）

### 2026-08-21 09:53:27

#### 企业级 AI 流程自动化：全自治 Agent 还是确定性工作流？

文章讨论了一个**百人以上研发部门**在推进 AI 流程自动化时的技术选型：是让 Agent 自主完成全部任务，还是用固定工作流约束关键步骤。作者初步倾向于**“确定性工作流 + 自治 Agent”混合架构**，以兼顾可靠性与灵活性。

##### 1. 项目背景与最终目标

- 团队拥有较深的行业知识（Domain Knowledge），并积累了一批 **Skill** 和 **RAG** 能力。
- 生产环境必须使用开源模型，目前暂按 **DeepSeek V4 Flash** 进行架构设计。
- 现有 Agent 已能在本地完成阶段性任务，但完整流程仍需人工接力。
- 最终目标是实现端到端自动化：
  1. 项目管理软件中的 Issue 自动触发 Agent；
  2. Agent 调用内部工具与数据；
  3. 完成判断、统计和代码追踪；
  4. 将结论自动写回项目记录。

##### 2. 两条技术路线

###### 路线一：Hermes Agent 自主执行

- 使用 **Hermes Agent + Goal + Cron**。
- 内部补齐 Skill、代码库和 MCP 等能力。
- 由 Agent 自主规划并跑完整流程。

**特点：**灵活、适合探索性任务，但执行路径不确定，验证、稳定性和风险控制难度较高。

###### 路线二：LangGraph 固定工作流

- 使用 **LangGraph + OpenCode**。
- 通过确定性的 DAG 固定任务流程。
- 每一步都创建独立环境，分别执行并验收。

**特点：**流程可控、易审计和验收，更适合固定、高风险的生产任务，但灵活性相对有限。

##### 3. 作者的初步判断

作者倾向于采用混合方案：

- **固定且高风险的主流程**交给 LangGraph，以确保结果可验证、过程可追踪。
- **探索性强、步骤不确定的任务**交给 Hermes，让 Agent 自主规划和执行。

核心不是简单选择“全自治”或“固定工作流”，而是根据任务风险与不确定性划分边界。

##### 4. 热门回复中的主要建议

###### 优先使用传统技术，减少不必要的 AI

有回复提出一套强调可交付性的原则：

> 能用脚本就不用 Agent，能用数据库就不用 RAG，能不用 LLM 就不用 LLM。

即把确定性逻辑固化为脚本、数据库查询或函数，只在确实需要理解、判断和探索时引入大模型，以提高验收成功率。

###### 引入外部状态管理和监督机制

有建议调研 **LoopX**：

- 为 Agent 提供外置状态管理；
- 增加规划与监督机制；
- 支持领域状态（Domain State）；
- 更适合长周期、长流程 Agent。

其定位类似面向长程 Agent 的轻量化 LangChain，可能更贴合该场景。

###### 领域知识沟通是落地难点

一位企业对接者指出：如果实施方不了解行业，需求沟通成本会非常高。业务团队不仅要说明需求，还要像培训新人一样补充行业知识，容易导致 Agent 最终“做出来了，但没有抓住真正的问题”。

这说明企业 Agent 的关键前提之一，是建立准确、持续更新的领域知识体系。

###### 长程 Agent 需要并发与持续记忆

另有回复介绍一种正在开源的 Long Horizon Agent，强调：

- 长期记忆；
- Context 自我管理与学习；
- 多线程并发；
- 多目标并发；
- Agent 执行长任务时不阻塞用户消息。

这类能力适合耗时较长、目标较多的自动化流程，但仍需结合验证和风险控制机制。

###### 验证机制比框架选择更重要

回复中还强调，真正需要优先解决的是：

- Domain Knowledge 是否具有时效性；
- 知识能否局部更新，而不是整体重建；
- 是否加入 Human-in-the-loop（人工介入）；
- 是否采用双轨 RAG 进行交叉验证；
- 哪些稳定程序可以直接固化为 Function。

##### 5. 综合结论

更稳妥的企业落地方式不是追求“全自治”，而是采用分层设计：

- **脚本、数据库、函数**处理确定性任务；
- **LangGraph 等工作流**承载固定、高风险主流程；
- **自治 Agent**负责探索性、非固定任务；
- 配套状态管理、知识更新、人工复核和逐步验收机制。

企业 Agent 的核心竞争力不只在于模型或框架，而在于能否做到：**流程可控、结果可验证、知识可更新、异常可介入。**

## 通俗精炼（1）

### 2026-09-18 10:39:03

#### 企业 AI 自动化更适合“确定性流程 + Agent”的混合架构

文章讨论一个百人以上研发部门的 AI 流程自动化选型：Agent 已能完成局部任务，但端到端流程仍需人工接力。核心矛盾是，企业生产环境既需要 Agent 的灵活推理，也要求流程可控、可验证，因此作者倾向采用混合架构，而非追求完全自治。

##### 两条路线分别解决灵活性与可控性

团队已有行业知识、Skill 和 RAG，并要求使用开源模型，暂按 DeepSeek V4 Flash 设计。最终希望项目管理软件中的 issue 能自动触发 Agent，调用内部工具与数据，完成判断、统计、代码追踪，并将结果写回。

两种候选方案是：

- **Hermes Agent + Goal/Cron**：补齐 Skill、代码库和 MCP，让 Agent 自主规划并执行完整流程，适合步骤不确定、探索性强的任务。
- **LangGraph + OpenCode**：以确定性 DAG 固定流程，每一步在独立环境中执行和验收，适合固定、高风险的核心链路。

作者的初步判断是：主流程采用 LangGraph，开放任务交给 Hermes。

##### 真正难点是验证、状态与行业知识

热门回复普遍强调，不应把所有环节都 Agent 化：能用脚本、数据库或固定函数解决的，就避免使用 LLM 和 RAG，以提高可验收性。生产化还需关注知识时效性、局部更新、人机协作、双轨 RAG，以及长流程中的外置状态管理、规划和监督。

另一个现实障碍是行业沟通：如果实施方缺乏领域知识，需求理解和知识转移成本可能很高。整体来看，企业 Agent 的关键不是“自治程度最高”，而是把不确定性限制在可监督、可回退、可验证的边界内。
