### 宝玉: Vercel 开源了 Open Agents，一个用来搭建企业自有编程 Agent 平台的参考实现

https://x.com/dotey/status/2043904844608532640?s=46&amp;t=bx0WG1AGHlEB9ipAHDEpnw

**宝玉**

Vercel 开源了 Open Agents，一个用来搭建企业自有编程 Agent 平台的参考实现。

CEO Guillermo Rauch 说：现成的编程 Agent 在大型代码仓库上表现不行，也不了解你公司的知识体系和内部流程，所以 Stripe、Spotify、Block 这些公司都在造自己的 AI 软件工厂。

Open Agents 绑定了 Vercel 自家的 Fluid、Workflow、Sandbox 和 AI Gateway 这套底座。但不管怎么说，Open Agents 给了一个可以直接 fork 的起点。

架构分三层：前端负责会话和认证，Agent 作为持久化工作流运行在 Vercel 上，沙箱提供隔离的代码执行环境。一个关键设计是 Agent 不跑在沙箱里面，而是从外部通过工具调用（文件读写、Shell 命令、搜索等）操作沙箱。这样 Agent 的生命周期、沙箱的生命周期、模型的选择，三件事互不绑定，各自演进。

功能上已经比较完整：支持对话驱动的编程 Agent、沙箱快照恢复、仓库克隆和分支操作、自动提交和发 PR、会话分享，甚至还有语音输入。

对于正在考虑自建编程 Agent 的技术团队，这省了从零搭架子的功夫。对于没有这个需求的开发者，这个项目的架构设计本身也值得看看，尤其是 Agent 和执行环境分离这个思路，几乎是当前所有 Agent 框架都在趋同的方向。

对比下 Anthropic 的 Managed Agents。

Vercel 的 Open Agents 是开源参考实现，给你一套可以 fork 的代码，自己部署、自己改。Anthropic 的 Managed Agents 是全托管服务，你通过 API 定义 Agent 的行为，基础设施全部由 Anthropic 运行，连沙箱、状态管理、错误恢复都不用操心。

有意思的是，两者在架构核心上达成了同一个共识：Agent 和执行环境必须分离。Vercel 的文档里专门强调"the agent is not the sandbox"，Agent 从外部通过工具调用操作沙箱。Anthropic 的工程博客用了一个更形象的说法，把 Agent 拆成"大脑"和"手"，大脑（模型和调度循环）不住在容器里，通过接口远程操控沙箱。

Anthropic 的工程博客还解释了为什么要这么做：早期他们把所有东西塞进一个容器，结果容器变成了"宠物"（Pet），挂了就什么都丢了，调试还得钻进去看，而容器里又有用户数据，安全上也过不去。拆开之后，容器变成了"牲口"（Cattle），坏了就换一个，会话日志（Session）独立存储在外面，随时可以恢复。

除了架构哲学，两者的差异很明显：

模型锁定方面，Open Agents 不绑定模型，你可以接任何 LLM。Managed Agents 只能用 Claude 系列模型，但换来的是 Anthropic 在 harness 层面做的 prompt caching、上下文压缩、自动恢复这些优化，这些东西自己搭很难做好。

成本结构方面，Open Agents 的成本是你自己的基础设施费用加上模型 API 调用费。Managed Agents 是三层计费：模型 token 费 + 每小时 0.08 美元的运行时费（按毫秒计，空闲不收费）+ 网页搜索每千次 10 美元。

控制权方面，Open Agents 给你完整源码，怎么改都行，但搭建和维护是你的事。Managed Agents 上手快（有人说 30 分钟就能跑起来），但你被限制在 Anthropic 提供的 API 能力范围内。

#### Open Agents

Open Agents 是一个在 Vercel 上构建和运行后台编码代理的开源参考应用。它包含 Web 用户界面、代理运行时、沙箱编排，以及从提示到代码变更所需的 GitHub 集成，无需使用你的笔记本电脑。

这个代码库旨在被分叉和调整，而不是被视为黑箱。

#### What it is

Open Agents 是一个三层系统：

```
Web -> Agent workflow -> Sandbox VM
```

- 该 Web 应用处理认证、会话、聊天和流式用户界面。
- 代理以持久化工作流的形式在 Vercel 上运行。
- 沙箱是执行环境：文件系统、Shell、Git、开发服务器和预览端口。

###### 关键架构决策：代理不是沙箱

代理不会在虚拟机内运行。它在沙箱外部运行，并通过文件读取、编辑、搜索和 shell 命令等工具与沙箱进行交互。

这种分离是该项目的主要点：

- 代理执行不与单一请求生命周期绑定
- 沙箱生命周期可以独立地休眠和恢复
- 模型/提供商选择和沙箱实现可以独立演进
- 虚拟机仍然是一个简单的执行环境，而不是成为控制平面

#### Current capabilities

- 基于聊天的编码代理，具备文件、搜索、Shell、任务、技能和网页工具
- 由工作流 SDK 支持的持久多步骤执行
- 隔离的 Vercel 沙箱，带有基于快照的恢复
- 沙箱内的仓库克隆和分支工作
- 可选的自动提交、推送以及在成功运行后创建拉取请求
- 会话共享通过只读链接
- 可选的语音输入，通过 ElevenLabs 转录

#### Runtime notes

一些对理解当前实现很重要的细节：

- 聊天请求启动一个工作流运行，而不是内联执行代理。
- 每次代理轮次可以继续跨越多个持久化的工作流步骤。
- 对于现有工作流，活跃的运行实例可通过重新连接到流来恢复。
- 沙箱使用基础快照，暴露端口 `3000` 、 `5173` 、 `4321` 和 `8000` ，并在闲置后休眠。
- 自动提交和自动 PR 得到支持，但它们是偏好驱动的功能，不是始终开启的行为。

#### 今天实际需要的是什么

这些要求基于当前的 `apps/web` 代码路径，而非旧的设置脚本。

###### Minimum runtime

这些是应用程序启动并加载服务器状态的硬性要求：

```
POSTGRES_URL=
JWE_SECRET=
```

###### 需要登录才能实际使用托管应用

一个有用的部署还需要令牌加密加上 Vercel OAuth 登录：

```
ENCRYPTION_KEY=
NEXT_PUBLIC_VERCEL_APP_CLIENT_ID=
VERCEL_APP_CLIENT_SECRET=
```

没有这些，网站可以部署，但 Vercel 登录将无法使用。

###### 是 GitHub 仓库访问、推送和拉取请求所必需的

如果你希望用户连接 GitHub、在仓库/组织上安装应用、克隆私有仓库、推送分支或打开拉取请求，请添加这些 GitHub 应用的值：

```
NEXT_PUBLIC_GITHUB_CLIENT_ID=
GITHUB_CLIENT_SECRET=
GITHUB_APP_ID=
GITHUB_APP_PRIVATE_KEY=
NEXT_PUBLIC_GITHUB_APP_SLUG=
GITHUB_WEBHOOK_SECRET=
```

###### Optional

```
REDIS_URL=
KV_URL=
VERCEL_PROJECT_PRODUCTION_URL=
NEXT_PUBLIC_VERCEL_PROJECT_PRODUCTION_URL=
VERCEL_SANDBOX_BASE_SNAPSHOT_ID=
ELEVENLABS_API_KEY=
```

- `REDIS_URL` / `KV_URL` ：可恢复流、停止信号以及基于 Redis 的缓存。
- `VERCEL_PROJECT_PRODUCTION_URL` / `NEXT_PUBLIC_VERCEL_PROJECT_PRODUCTION_URL` ：用于元数据和某些回调行为的规范生产环境 URL。
- `VERCEL_SANDBOX_BASE_SNAPSHOT_ID`: 覆盖默认沙箱快照。
- `ELEVENLABS_API_KEY` ：语音转录。

#### 在 Vercel 上部署你自己的副本

推荐路径：在 Vercel 的仓库根目录部署此仓库，然后叠加身份验证和 GitHub 集成。

1. Fork this repo.
2. 创建一个 PostgreSQL 数据库并复制它的连接字符串。
3. Generate these secrets:
   ```bash
   openssl rand -base64 32 | tr '+/' '-_' | tr -d '=\n'   # JWE_SECRET
   openssl rand -hex 32                                    # ENCRYPTION_KEY
   ```
4. Import the repo into Vercel.
5. 在 Vercel 项目设置中至少添加这些环境变量：
   ```bash
   POSTGRES_URL=
   JWE_SECRET=
   ENCRYPTION_KEY=
   ```
6. 部署一次以获取稳定的生产 URL。
7. 创建一个 Vercel OAuth 应用，回调 URL 为：
   ```bash
   https://YOUR_DOMAIN/api/auth/vercel/callback
   ```
8. 添加这些环境变量并重新部署:
   ```bash
   NEXT_PUBLIC_VERCEL_APP_CLIENT_ID=
   VERCEL_APP_CLIENT_SECRET=
   ```
9. 如果你想要完整的支持 GitHub 的编码代理流程，请创建一个 GitHub 应用，使用：
   - 首页网址: `https://YOUR_DOMAIN`
   - 回调 URL: `https://YOUR_DOMAIN/api/github/app/callback`
   - 设置 URL: `https://YOUR_DOMAIN/api/github/app/callback`
   In the GitHub App settings:
   - 启用 "在安装期间请求用户授权(OAuth)"
   - 使用 GitHub App 的客户端 ID 和客户端密钥分别作为 `NEXT_PUBLIC_GITHUB_CLIENT_ID` 和 `GITHUB_CLIENT_SECRET`
   - 如果希望组织安装正常工作，请将应用设为公开
10. 添加 GitHub App 的环境变量并重新部署
11. 可选添加 Redis/KV 和规范的生产环境 URL 变量。

#### Local setup

1. Install dependencies:
   ```bash
   bun install
   ```
2. Create your local env file:
   ```bash
   cp apps/web/.env.example apps/web/.env
   ```
3. 在 `apps/web/.env` 中填写所需的值。
4. Start the app:
   ```bash
   bun run web
   ```

如果您已有一个已关联的 Vercel 项目，您仍然可以通过 `vc env pull` 命令拉取环境变量到本地，但配置现在是有意手动进行的，以便您确切了解哪些值是重要的。

#### OAuth and integration setup

###### Vercel OAuth

创建一个 Vercel OAuth 应用并使用此回调:

```
https://YOUR_DOMAIN/api/auth/vercel/callback
```

For local development, use:

```
http://localhost:3000/api/auth/vercel/callback
```

Then set:

```
NEXT_PUBLIC_VERCEL_APP_CLIENT_ID=...
VERCEL_APP_CLIENT_SECRET=...
```

###### GitHub App

您不需要单独的 GitHub OAuth 应用。Open Agents 使用 GitHub 应用的用户授权流程。

创建一个用于基于安装的仓库访问的 GitHub App 并进行配置：

- 首页网址: `https://YOUR_DOMAIN`
- 回调 URL: `https://YOUR_DOMAIN/api/github/app/callback`
- 设置 URL: `https://YOUR_DOMAIN/api/github/app/callback`
- 启用"在安装过程中请求用户授权（OAuth）"
- 如果希望组织安装能正常工作，请将应用设为公开

对于本地开发，请使用 `http://localhost:3000/api/github/app/callback` 作为回调/设置 URL，使用 `http://localhost:3000` 作为首页 URL。

Then set:

```
NEXT_PUBLIC_GITHUB_CLIENT_ID=...   # GitHub App Client ID
GITHUB_CLIENT_SECRET=...           # GitHub App Client Secret
GITHUB_APP_ID=...
GITHUB_APP_PRIVATE_KEY=...
NEXT_PUBLIC_GITHUB_APP_SLUG=...
GITHUB_WEBHOOK_SECRET=...
```

`GITHUB_APP_PRIVATE_KEY` 可以存储为带有转义换行符的 PEM 内容，或者存储为 base64 编码的 PEM。

#### Open Agents

Open Agents is an open-source reference app for building and running background coding agents on Vercel. It includes the web UI, the agent runtime, sandbox orchestration, and the GitHub integration needed to go from prompt to code changes without keeping your laptop involved.

The repo is meant to be forked and adapted, not treated as a black box.

Open Agents is a three-layer system:

```
Web -> Agent workflow -> Sandbox VM
```

- The web app handles auth, sessions, chat, and streaming UI.
- The agent runs as a durable workflow on Vercel.
- The sandbox is the execution environment: filesystem, shell, git, dev servers, and preview ports.

The agent does not run inside the VM. It runs outside the sandbox and interacts with it through tools like file reads, edits, search, and shell commands.

That separation is the main point of the project:

- agent execution is not tied to a single request lifecycle
- sandbox lifecycle can hibernate and resume independently
- model/provider choices and sandbox implementation can evolve separately
- the VM stays a plain execution environment instead of becoming the control plane

#### Current capabilities

- chat-driven coding agent with file, search, shell, task, skill, and web tools
- durable multi-step execution with Workflow SDK-backed runs
- isolated Vercel sandboxes with snapshot-based resume
- repo cloning and branch work inside the sandbox
- optional auto-commit, push, and PR creation after a successful run
- session sharing via read-only links
- optional voice input via ElevenLabs transcription

#### Runtime notes

A few details that matter for understanding the current implementation:

- Chat requests start a workflow run instead of executing the agent inline.
- Each agent turn can continue across many persisted workflow steps.
- Active runs can be resumed by reconnecting to the stream for the existing workflow.
- Sandboxes use a base snapshot, expose ports `3000`, `5173`, `4321`, and `8000`, and hibernate after inactivity.
- Auto-commit and auto-PR are supported, but they are preference-driven features, not always-on behavior.

These requirements are based on the current `apps/web` codepath, not older setup scripts.

##### Minimum runtime

These are the hard requirements for the app to boot and load server state:

```
POSTGRES_URL=
JWE_SECRET=
```

A useful deployment also needs token encryption plus Vercel OAuth sign-in:

```
ENCRYPTION_KEY=
NEXT_PUBLIC_VERCEL_APP_CLIENT_ID=
VERCEL_APP_CLIENT_SECRET=
```

Without these, the site can deploy, but Vercel sign-in will not work.

If you want users to connect GitHub, install the app on repos/orgs, clone private repos, push branches, or open PRs, add these GitHub App values:

```
NEXT_PUBLIC_GITHUB_CLIENT_ID=
GITHUB_CLIENT_SECRET=
GITHUB_APP_ID=
GITHUB_APP_PRIVATE_KEY=
NEXT_PUBLIC_GITHUB_APP_SLUG=
GITHUB_WEBHOOK_SECRET=
```

##### Optional

```
REDIS_URL=
KV_URL=
VERCEL_PROJECT_PRODUCTION_URL=
NEXT_PUBLIC_VERCEL_PROJECT_PRODUCTION_URL=
VERCEL_SANDBOX_BASE_SNAPSHOT_ID=
ELEVENLABS_API_KEY=
```

- `REDIS_URL` / `KV_URL`: resumable streams, stop signaling, and Redis-backed caching.

#### Open Agents 内容整理与解读

##### 一句话总结

**Open Agents 是 Vercel 开源的一套“企业可自建的云端编程 Agent 参考实现”**：它不只是一个聊天式写代码工具，而是一整套从 Web 界面、持久化 Agent 工作流、隔离沙箱执行环境，到 GitHub 自动提交/提 PR 的完整平台骨架。它最核心的设计思想是：

> **Agent 不直接运行在沙箱里，而是在沙箱外部通过工具去操控沙箱。**

这也是当前云端 Agent 基础设施逐渐形成的共识。

---

##### 综合总结

##### 1. Open Agents 到底是什么

Open Agents 是 Vercel 开源的一个参考项目，用来帮助团队快速搭建自己的“云端编程 Agent 平台”。

它覆盖了一个编码 Agent 真正上线所需的关键部分：

- Web 端界面：登录、会话、聊天、流式输出
- Agent 运行时：以持久化工作流方式运行，而不是一次请求跑完就结束
- Sandbox 沙箱：提供隔离的文件系统、Shell、Git、开发服务器、预览端口
- GitHub 集成：支持克隆仓库、分支操作、自动提交、推送、创建 PR
- 其他增强能力：会话分享、语音输入、沙箱快照恢复等

所以它不是一个“模型 demo”，而更像是一个可以直接 fork、二次开发、部署到企业内部的 **Agent 平台底座**。

---

##### 2. 它为什么会出现

从 Nico Albanese 的描述可以看出，Open Agents 的直接动机很现实：

- 在本地运行 Agent 很麻烦
- 要一直开着笔记本
- 要管理 worktree
- 要防止电脑休眠
- 明明 Agent 很智能，却还得像“值班”一样盯着它跑

所以 Open Agents 试图把编码 Agent 从“本地终端工具”升级为“云端后台服务”：

- Agent 在云上持续运行
- 用户通过浏览器交互
- 代码执行放在隔离沙箱里
- 不再依赖本地电脑一直在线

这代表了一个重要转向：  
**Agent 从个人开发者工具，走向团队级、平台级基础设施。**

---

##### 3. 它最重要的架构思想

Open Agents 的架构可以概括为三层：

```text
Web -> Agent workflow -> Sandbox VM
```

分别负责：

- **Web 层**：用户登录、聊天界面、会话管理、流式响应
- **Agent 层**：负责推理、规划、工具调度，以持久化工作流方式运行
- **Sandbox 层**：负责真正执行命令、读写文件、跑 Git、启动服务

其中最关键的一点是：

###### Agent 不在沙箱里运行

它不是把“大脑”和“手脚”塞进同一个容器，而是拆开：

- **Agent = 大脑**
- **Sandbox = 手和执行环境**

Agent 在外部，通过工具调用去操作沙箱中的代码和命令。

这样做的好处是：

- Agent 生命周期独立，不会被单个容器绑死
- 沙箱可以单独休眠、恢复、替换
- 模型和执行环境可以独立升级
- 容器坏了可以重建，不会导致整个会话状态丢失
- 系统更安全，职责边界更清晰

这也是内容里反复强调的核心：  
**“the agent is not the sandbox”**。

---

##### 4. 为什么“Agent 与执行环境分离”这么重要

这不是一个表面上的工程细节，而是 Agent 系统能否真正产品化的分水岭。

宝玉引用 Anthropic 的经验很有代表性：

###### 早期做法的问题：把一切塞进一个容器

如果 Agent、状态、执行环境、用户数据都在同一个容器里：

- 容器挂了，状态容易一起丢
- 调试要“钻进容器”排查，非常痛苦
- 容器会变成难以迁移和替换的“宠物”
- 安全隔离也更复杂，因为里面混着用户数据和控制逻辑

###### 拆开后的好处：容器变成可替换资源

当 Agent 在外部，沙箱只负责执行：

- 会话状态可以独立持久化
- 沙箱宕了可以直接换一个
- 恢复成本更低
- 控制平面和执行平面更清晰
- 安全和扩展性都更容易做

Anthropic 把这种差别形容为：

- 以前容器像 **Pet（宠物）**
- 现在容器像 **Cattle（牲口）**

意思是：  
以前每个容器都要精心照顾；  
现在坏了就替换，不影响整体系统。

这说明，**云端 Agent 真正落地的关键，不只是模型能力，而是系统架构是否可恢复、可隔离、可替换。**

---

##### 5. Open Agents 和 Anthropic Managed Agents 的关系

内容里做了一个很有价值的对比。

###### 共识：核心架构方向一致

二者都认同：

- Agent 不应与执行沙箱绑定
- 推理控制和代码执行要分离
- 会话状态要脱离容器独立保存
- 容器应是可替换的执行资源

也就是说，**开源自建路线和托管服务路线，在架构理念上已经趋同。**

###### 差异：产品模式完全不同

###### Open Agents
- 开源参考实现
- 可 fork、可改造、可自部署
- 模型不锁定，可接入任意 LLM
- 控制权高，但维护成本也高

###### Managed Agents
- 全托管服务
- 通过 API 定义行为即可
- 基础设施由 Anthropic 托管
- 只能用 Claude 系列模型
- 上手更快，但自由度更低

###### 本质区别可以这么理解

- **Open Agents**：给你一套“自己建厂”的图纸和样板间
- **Managed Agents**：给你一个“拎包入住”的代工厂

前者适合对控制权、私有化、定制化有要求的团队；  
后者适合追求上线速度和省运维的团队。

##### 6. Open Agents 已经具备哪些实用能力

从模板页和 GitHub 仓库信息看，它已经不是概念验证，而是功能较完整的系统：

- 聊天驱动的编码 Agent
- 文件搜索、编辑、Shell、任务、技能、网页工具
- 持久化多步骤执行
- 沙箱快照恢复
- 仓库克隆和分支工作流
- 自动提交、推送、创建 PR
- 只读会话分享链接
- 可选语音输入
- 流式恢复已有运行任务
- 沙箱空闲后自动休眠

这意味着它不仅能“写代码”，还具备了一条较完整的软件交付链路：

```text
Prompt -> 理解任务 -> 修改代码 -> 运行命令 -> 提交分支 -> 发起 PR
```

这也是为什么它对企业团队更有吸引力：  
**它开始接近“AI 软件工厂”的雏形，而不只是一个聊天机器人。**

---

##### 7. 它面向的不是普通 demo 用户，而是有平台需求的团队

内容里提到 Stripe、Spotify、Block 等公司都在自建内部 AI 软件工厂。背后的原因很明确：

现成的编程 Agent 往往存在几个问题：

- 对超大代码仓库理解不够
- 不知道企业内部知识、规范和流程
- 无法贴合组织自己的 Git、权限、审计、发布流程
- 很难深度适配内部工具链

所以企业真正需要的不是“一个通用 Agent App”，而是：

- 能接自己模型策略
- 能接自己知识体系
- 能嵌入自己开发流程
- 能满足安全和治理要求

Open Agents 的意义就在这里：  
**它提供的不是最终答案，而是一个高质量起点。**

##### 8. 从部署和工程信息看，它是“真能落地”的项目

从模板页和 GitHub 仓库能看到，它不是只有理念，工程落地也比较完整：

- 需要的环境变量、OAuth 配置、GitHub App 配置都写得比较明确
- 支持 Vercel OAuth 和 GitHub App 用户授权流程
- 明确依赖 PostgreSQL，Redis/KV 属于增强项

这说明它适合作为：

- 企业内部 PoC 起点
- 自建 Agent 平台原型
- 学习云端 Agent 架构的样板项目
