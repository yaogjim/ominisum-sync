## 分析要点

- **核心高价值点**：将复杂任务拆解为多个独立context的subagents，并通过对抗验证、扇出综合、锦标赛等模式降低偷懒、自我偏差和目标漂移。
- **留存建议**：长期保留（提供了Claude Code动态工作流的核心原理、适用场景、可复用模式和落地技巧，对AI辅助研发和复杂任务编排有持续参考价值。）

**知识要点**

- 动态工作流本质上是Claude Code实时生成的JavaScript harness，用于协调多个subagents并可选择模型、worktree和恢复策略。
- 默认单context模式在长任务、大规模并行、强结构化或对抗性任务中容易出现偷懒、自我偏好偏差和目标漂移。
- 常见可复用模式包括分类并执行、扇出并综合、对抗式验证、生成并筛选、锦标赛、循环至完成。
- 适用场景包括代码迁移与重构、深度研究、事实核查、排序、规则遵循、大规模分类、设计探索、评估和模型路由。
- workflow会显著增加token消耗，适合复杂高价值任务，不适合普通编码任务滥用。

**行动项**

- 在Claude Code中尝试为一个复杂研究或代码审查任务创建dynamic workflow，并设置明确token预算。
- 整理一套常用workflow模板，如对抗验证、扇出综合、锦标赛评审和规则verifier。
- 将高频可复用workflow保存到\~/.claude/workflows或封装进skill中，便于后续调用。
- 在需要事实核查或技术审查的任务中加入独立verifier agent，减少自我偏差。

### Claude Code 动态工作流： 每个任务都可以有自己的 Harness【译】

Claude Code 现在能即时写出属于它自己的 harness，为手头的任务量身定制。这套能力就叫 dynamic workflow：它会动态地编写编排脚本，在单个会话里运行数十到数百个并行的 subagents，并在任何结果送到你面前之前先自行检查一遍。

默认的 Claude Code harness 用来写代码很好，但研究、安全分析、agent teams、代码审查这类更专门的任务，过去需要在 Claude Code 之上搭一套定制 harness 才能达到最佳表现。

workflow 让你可以动态地创建这些定制 harness，它们可复用、可分享，能让 Claude 以比默认方式更原生的姿态去解决问题。

这篇文章我会分享自己使用 workflow 的初步体验和一些心得。要提醒的是，workflow 会消耗更多 token，更适合复杂、高价值的任务。

#### 1.示例提示词

下面这些例子展示了 workflow 能做什么。你可以直接向 Claude 提出类似的请求：

- 让多个相互竞争的理论各自尝试，复现时好时坏的 flaky tests。
- 从过往会话中挖掘反复出现的纠正。
- 在 Slack 的事故频道里定位问题根因。
- 为一份商业计划获取多个视角的批评意见。
- 对简历进行排名，并加以验证。
- 用锦标赛式的筛选，为一个 CLI 工具命名。
- 对整个代码库执行重构。
- 对照实际代码，核实博客草稿里的技术论断。

#### 2.workflow 的运作方式

workflow 会执行 JavaScript 文件，文件里包含用于生成和协调 subagents 的特殊函数。JSON、Math、Array 这些标准 JavaScript 工具可以用来处理数据。workflow 可以选择 subagents 使用哪个模型，并决定它们是否在隔离的 worktree 里运行。如果运行被中断，恢复后 workflow 可以从中断处继续。

#### 3.为什么需要 workflow

默认的 harness 在单个 context window 内完成规划与执行。这对编码任务很有效，但碰到长时间运行、大规模并行、高度结构化或带对抗性质的任务就会出问题。具体会表现出三种失效模式：

- 智能体偷懒：面对复杂的多部分任务，Claude 会过早停止，只做完一部分就宣布任务完成，比如 50 项安全审查只处理了其中 35 项。
- 自我偏好偏差：当被要求对照 rubric 验证或评判结果时，Claude 会偏袒自己得出的结论。
- 目标漂移：在多轮交互中保真度逐渐流失，每一次总结都会丢掉细节，包括边缘情况的需求和各种约束。

workflow 的对策，是编排一批彼此独立、各自拥有独立 context window、目标聚焦又互相隔离的 subagents。

#### 4.动态工作流 与 静态工作流

此前，用 Claude Agent SDK 或 claude -p 构建的 static workflows，是以通用方式协调多个 Claude Code 实例，这要求你把所有边缘情况都覆盖到。有了 Claude Opus 4.8 和 dynamic workflows，Claude 现在能写出针对具体场景量身定制的 harness。

#### 5.使用 workflow 时的实用模式

你可以直接请求一个 workflow，或在提示里用 ultracode 来确保 Claude Code 创建一个 workflow，从而触发它。常见的组合模式包括：

- 分类并执行：由一个 classifier agent 判断任务类型，据此路由到不同的 agent 或行为；也可以在任务完成时确定输出的分类。
- 扇出并综合：把任务拆成许多更小的步骤，每个步骤跑一个 agent，再综合所有结果。当大量步骤都能从干净、互不干扰的 context window 中受益时，这一模式尤其有用。综合这一步充当一个 barrier，它会等所有扇出的 agent 完成后，再合并它们的结构化输出。
- 对抗式验证：每生成一个 agent，就再跑一个单独的 agent，以对抗的姿态对照 rubric 或判定准则来验证它的输出。
- 生成并筛选：先就某个主题生成多个想法，再按 rubric 或验证来筛选，去重后只留下质量最高、经过检验的那些。
- 锦标赛：让 N 个 agent 用不同方法在同一个任务上互相竞争，而不是把工作分摊下去。由成对评判的 agent 决出胜者，直到只剩一个。
- 循环至完成：对工作量未知的任务，持续生成 agent，直到满足停止条件为止，比如不再有新发现、日志里不再有错误，而不是采用固定的遍数。

#### 6.应用场景

- 迁移与重构：Bun 把 Zig 重写成 Rust 时就用了 workflow。把任务拆成一串串行步骤，比如调用点、失败的测试、模块，为每一处修复在 worktree 里生成 subagents，让 agent 做对抗式审查，然后再合并。要避开资源密集的命令，好让并行度最大化。
- 深度研究：Claude Code 的 /deep-research 技能就用了 workflow，它扇出网络搜索、抓取来源、对抗式地验证论断，再综合出一份带引用的报告。这个套路同样适用于非网络类的研究，比如汇编 Slack 上的状态报告，或者探索一个代码库的功能。
- 深度验证：对那种每条事实都要标注出处的报告，可以生成这样的 workflow：一个 agent 负责识别出各项论断，subagents 逐一详细核查，再由 verifier agent 确保来源质量。

- 排序：碰到需要定性衡量的大型条目列表，比如按缺陷严重程度给工单排序，在单个提示里给 1000 多行排名会拉低质量，还会撑爆 context。可以用锦标赛、成对比较的流水线，或者先并行分桶排名再合并；每一次比较都是它自己的一个 agent，context 里只保留当前的排序顺序。

- 记忆与规则遵循：当 Claude 即便把规则写进 CLAUDE.md 仍会漏掉某些规则时，可以创建带 rule verifier 的 workflow，一条规则配一个 verifier。再让一个 skeptic 人设来审查这些规则，防止误报。也可以反过来做：从近期会话和代码审查评论里挖掘反复出现的纠正，用并行 agent 聚类，对每个候选规则做对抗式验证，也就是问一句这条规则真能避免实际发生过的错误吗，再把幸存下来的规则提炼回 CLAUDE.md。

- 大规模分类处理：triage workflow 会对条目分类、跟现有跟踪记录去重，然后采取行动。一个有用的模式是 quarantine：读取不受信任公开内容的 agent，被禁止执行高权限操作，这些操作改由负责信息处理的 agent 来做。配合 /loop 就能持续运行。

- 探索与品味：在探索不同解法时很有用，尤其是设计或命名这种依赖品味的决策，它们能从 rubric 中受益。可以让 Claude 去探索解法，同时让一个 review agent 依据一套关于好方案的 rubric 来评判，满足审查标准时即告完成。方案可以排序，也可以基于 rubric 用锦标赛选出。
- 评估：可以这样跑轻量级 eval：在 worktree 里生成若干独立 agent，再生成 comparison agent，对照 rubric 给各项输出做比较和打分。比如对照特定标准来评估并改进已经做好的技能。
- 模型与智能路由：创建一个针对任务调校过的 classifier agent，由它决定用哪个模型。当任务涉及大量工具调用时这很有用，已有研究能指出哪个模型最合适。举例来说，解释一个鉴权模块怎么工作，取决于文件数量和代码库的形态；一个 classifier 会先做这项调研，再根据预期复杂度路由到 Sonnet 或 Opus。

#### 7.何时不该使用 workflow

workflow 是新东西，并不是每个任务都需要它，它可能消耗多得多的 token。要有创造性地用它，把 Claude Code 推到常规用法之外。而对常规编码任务，先掂量一下是否真的需要额外算力；大多数传统编码并不需要五个 reviewer。

#### 8.构建 workflow 的技巧

- 提示词：运用上面讲的那些具体技巧、把提示写详细，效果最好。workflow 不只用于大型任务，你也可以提示一个快速 workflow，比如对某个假设做一次快速的对抗式审查。
- 结合 /goal 和 /loop：对可重复的 workflow，比如分类、研究、验证，用 /loop 按固定间隔运行，用 /goal 设一个硬性的完成要求。
- token 用量预算：设一个明确的 token 预算来限制任务用量。在提示里写明上限，例如让它只用 10k token。
- 保存与分享 workflow：在 workflow 菜单里按 s 就能保存。把它们签入 \~/.claude/workflows，或者通过技能来分发。把 JavaScript workflow 文件放进技能文件夹，并在 SKILL.md 里引用。想更灵活的话，可以提示 Claude 把技能里的 workflow 当成模板，而不是逐字照搬的脚本。

#### 9.探索的新起点

workflow 为扩展 Claude Code 提供了一种好用的新方式。把它看作一个起点，去探索用 Claude 完成任务的新方法。关于怎么把它用到最好，还有许多有待发掘。也欢迎你把自己的发现分享出来。

#### Claude Code 动态工作流：深度总结、通俗解读与辩证思考

##### 一、深度总结

**Dynamic Workflow 的核心：让 Claude Code 为每个复杂任务临时“造一套专属工作流”。**

过去 Claude Code 主要依赖默认工作方式：在一个上下文窗口里规划、执行、总结。  
这适合普通编码，但不适合复杂任务，比如研究、审查、排序、迁移、验证、事故排查等。

Dynamic Workflow 的变化是：

> Claude 不只是执行任务，而是先写一个 JavaScript 编排脚本，再用它调度多个 subagents 并行工作。

这些 subagents 可以：

- 各自拥有独立上下文；
- 并行处理不同子任务；
- 相互验证、竞争或审查；
- 在隔离 worktree 中运行；
- 中断后继续恢复；
- 最终由一个综合器汇总结果。

它本质上把 Claude Code 从“单人助手”升级成了“临时组建的任务团队”。

---

##### 二、为什么需要它？

默认模式有三个典型问题：

###### 1. 智能体偷懒

复杂任务做一半就声称完成。  
例如 50 项审查只做 35 项。

###### 2. 自我偏好偏差

Claude 容易偏袒自己的答案。  
让它自己生成、自己评审，可靠性有限。

###### 3. 目标漂移

多轮对话中，细节会逐渐丢失。  
规则、边界条件、约束可能被慢慢忘掉。

Dynamic Workflow 的解决办法是：

> 把大任务拆成多个小任务，让不同 agent 在独立上下文里完成，再用验证器、评审器、综合器控制质量。

---

##### 三、通俗解读

可以把普通 Claude Code 想象成：

> 一个聪明人独自完成所有事情。

而 Dynamic Workflow 像是：

> Claude 临时搭建一个项目组：有人查资料，有人写代码，有人审查，有人挑错，有人汇总。

例如：

###### 做研究

不是一个 Claude 从头读到尾，而是：

- A agent 搜索资料；
- B agent 验证来源；
- C agent 提取论点；
- D agent 反驳不可靠结论；
- E agent 汇总成报告。

###### 做代码审查

不是一个 Claude 扫完整个代码库，而是：

- 每个 agent 审查一个模块；
- reviewer agent 专门挑错；
- verifier agent 检查是否符合规则；
- 最后合并结果。

###### 给 1000 条工单排序

不是把全部塞进一个上下文，而是：

- 先分组；
- 组内排序；
- 组间比较；
- 像锦标赛一样逐步决出优先级。

一句话：

> Dynamic Workflow 不是让 Claude 更“聪明”，而是让 Claude 更“有组织”。

---

##### 四、关键模式

###### 1. 扇出并综合

把任务拆开，并行处理，再统一汇总。  
适合研究、代码扫描、大规模审查。

###### 2. 对抗式验证

一个 agent 产出结果，另一个 agent 专门挑错。  
适合事实核查、安全分析、技术博客验证。

###### 3. 生成并筛选

先大量生成，再按标准筛选。  
适合命名、设计方案、创意探索。

###### 4. 锦标赛

多个 agent 用不同方案竞争，逐轮淘汰。  
适合主观判断强的任务，如产品名、架构方案。

###### 5. 分类并执行

先判断任务类型，再分派给不同 agent。  
适合工单处理、客服分类、自动 triage。

###### 6. 循环至完成

不断运行，直到满足停止条件。  
适合排查故障、持续监控、清理问题。

---

##### 五、适合场景

Dynamic Workflow 适合：

- 大规模重构；
- 深度研究；
- 事实核查；
- 安全审查；
- 事故排查；
- 工单排序；
- 简历筛选；
- 代码库探索；
- 规则遵循检查；
- 命名、设计、方案评估；
- 自动化 triage。

不适合：

- 简单改 bug；
- 普通代码补全；
- 小范围重构；
- 明确、短平快的任务。

因为它更耗 token、更复杂，也更贵。

---

##### 六、真正的价值

这篇文章最重要的启发不是“多开几个 agent”。

而是：

> AI 编程工具正在从“对话式助手”走向“自我编排的任务系统”。

过去我们给 AI 一个任务，它直接干。  
现在我们给 AI 一个目标，它先设计组织结构，再调度多个执行者完成。

这意味着 Claude Code 的能力边界被扩展了：

- 从单线程到多线程；
- 从回答问题到管理流程；
- 从执行者到编排者；
- 从工具调用到任务系统生成；
- 从一次性结果到可复用 workflow。

---

##### 七、辩证思考

###### 1. 它很强，但不是万能药

Dynamic Workflow 能提升复杂任务质量，但也会增加成本、延迟和不可控性。  
如果任务本身很简单，强行使用 workflow 反而是浪费。

**好钢要用在刀刃上。**

---

###### 2. 多 agent 不等于高质量

多个 agent 并行工作，可能带来更多视角，也可能带来更多噪音。

关键不在数量，而在结构：

- 有没有清晰分工？
- 有没有验证机制？
- 有没有停止条件？
- 有没有统一标准？
- 有没有最终综合逻辑？

没有这些，多 agent 只是“多人胡说”。

---

###### 3. 对抗式验证很重要

AI 最大的问题之一是自信但可能错误。  
让一个 agent 产出，让另一个 agent 质疑，是提升可靠性的关键。

但也要警惕：

> 验证 agent 本身也可能错。

所以真正高价值任务，仍需要人类最终把关。

---

###### 4. 它会改变提示词工程

以前提示词重点是“怎么让 AI 回答好”。  
现在提示词还要描述：

- 任务如何拆解；
- agent 如何分工；
- 如何验证；
- 如何合并；
- 何时停止；
- token 预算是多少。

提示词正在从“提问”变成“设计流程”。

---

###### 5. 它可能是 AI 工具的新范式

Dynamic Workflow 的本质，是让 AI 生成自己的工作方法。

这很关键：

> 不是人类预先写死流程，而是 AI 根据任务动态创建流程。

未来优秀的 AI 使用者，可能不是最会问问题的人，而是最会设计任务系统的人。

---

##### 八、一句话总结

**Dynamic Workflow 让 Claude Code 从“一个会写代码的助手”，变成“能临时组建、调度、审查一个 agent 团队的任务编排器”。**

它适合复杂、高价值、需要并行、验证和结构化处理的任务；  
不适合简单任务。  
用得好，是生产力跃迁；用不好，只是昂贵的复杂化。

##### 主旨概括

文章介绍了 Claude Code 新推出的 **动态工作流（dynamic workflow）**：Claude 可以根据当前任务即时编写专属的工作流脚本，调度大量并行 subagents 来完成复杂任务。它特别适合研究、安全分析、代码审查、迁移重构等高价值复杂场景，但会消耗更多 token，不适合所有日常编码任务。

- 文章认为，workflow 可能是 Claude Code 继 skill 之后非常重要的能力，可以看作是 `/goal` 的增强版。

##### 1. workflow 能做什么：8 个直观例子

文章先用一些提示词示例展示 workflow 的能力：

- 让多个 agent 用不同理论复现不稳定的 flaky tests。
- 从历史会话中找出用户反复纠正 Claude 的问题。
- 在 Slack 事故频道中定位故障根因。
- 从多个视角批评一份商业计划。
- 对简历进行排名，并验证排序是否合理。
- 用“锦标赛”方式为 CLI 工具命名。
- 对整个代码库执行大规模重构。
- 对照真实代码，检查博客草稿中的技术论断是否准确。

这些例子说明：workflow 不只是写代码，而是适合处理 **并行、多视角、需要验证或对抗评审的复杂任务**。

---

##### 2. workflow 的运作方式：本质是一段 JavaScript 编排脚本

- workflow 会执行一个 JavaScript 文件。
- 这个文件中包含特殊函数，用来创建和协调多个 subagents。
- 可以使用标准 JavaScript 工具，比如：
  - `JSON`
  - `Math`
  - `Array`
- workflow 可以决定：
  - 每个 subagent 使用哪个模型；
  - 是否让 subagent 在隔离的 worktree 中运行；
  - 中断后是否从断点继续。

简单理解：workflow 就像一个“任务指挥官”，负责把大任务拆开、分派给多个 Claude agent，再统一收集和检查结果。

---

##### 3. 为什么需要 workflow：默认 harness 有三类局限

默认 Claude Code harness 适合普通编码任务，因为它在单个 context window 内完成规划和执行。但面对复杂任务时，容易出现三类问题。

###### 1）智能体偷懒

- 面对复杂、多部分任务时，Claude 可能提前停止。
- 例如：要求做 50 项安全审查，它可能只完成 35 项就声称完成。

###### 2）自我偏好偏差

- 当 Claude 被要求按 rubric 评判结果时，可能偏袒自己原先的结论。
- 这会影响代码审查、研究验证、方案评估等任务的可靠性。

###### 3）目标漂移

- 多轮交互中，任务细节会逐渐丢失。
- 每次总结都可能遗漏边缘需求、约束条件或特殊情况。

workflow 的解决方式是：创建多个相互独立、拥有各自 context window 的 subagents，让它们聚焦于明确的小目标，并尽量互相隔离，减少偏差和遗忘。

---

##### 4. 动态工作流 vs 静态工作流

过去也可以用 Claude Agent SDK 或 `claude -p` 构建静态工作流，但这种方式需要开发者预先设计好流程，并覆盖各种边缘情况。

动态工作流的不同之处在于：

- Claude 可以根据具体任务实时写出定制 harness。
- 不需要提前设计一套通用流程。
- 更适合任务差异大、流程不固定的复杂场景。

文章提到，在 Claude Opus 4.8 和 dynamic workflows 支持下，Claude 能够为具体问题临时生成更合适的执行框架。

---

##### 5. 使用 workflow 的 6 种常见模式

###### 1）分类并执行

- 先由 classifier agent 判断任务类型。
- 再根据分类结果路由到不同 agent 或处理方式。
- 也可以在任务完成后对结果进行分类。

适合：工单分流、问题归类、自动 triage。

---

###### 2）扇出并综合

- 将大任务拆成许多小任务。
- 每个小任务由一个独立 agent 处理。
- 所有 agent 完成后，再由综合步骤合并结果。

适合：研究、代码库探索、大规模检查。

例如：分析一个大型代码库时，可以让不同 agent 分别查看不同模块，最后合并总结。

---

###### 3）对抗式验证

- 每生成一个结果，就再启动一个独立 agent 来审查它。
- 审查 agent 以“挑错”的方式对照 rubric 或标准验证输出。

适合：技术报告核查、安全审查、博客事实校验。

---

###### 4）生成并筛选

- 先让多个 agent 生成大量想法。
- 再根据 rubric 去重、筛选、验证。
- 最后保留质量最高的结果。

适合：产品命名、方案设计、创意生成。

---

###### 5）锦标赛

- 让 N 个 agent 用不同方法解决同一个问题。
- 再由评判 agent 两两比较，逐轮淘汰。
- 最后选出最优方案。

适合：命名、排序、设计方案选择等带有主观判断的任务。

---

###### 6）循环至完成

- 对于工作量未知的任务，不预设固定轮数。
- workflow 持续生成 agent，直到满足停止条件。
- 停止条件可以是：
  - 不再发现新问题；
  - 日志中不再出现错误；
  - 所有测试通过。

适合：排查故障、持续 triage、迁移修复。

---

##### 6. 主要应用场景

###### 1）迁移与重构

- Bun 在将 Zig 重写成 Rust 时使用了 workflow。
- 具体做法包括：
  - 将任务拆成串行步骤；
  - 按调用点、失败测试、模块生成 subagents；
  - 每个修复在独立 worktree 中完成；
  - 再通过对抗式审查检查质量；
  - 最后合并结果。
- 建议避开资源密集型命令，以最大化并行度。

---

###### 2）深度研究

Claude Code 的 `/deep-research` 技能就使用了 workflow。

它会：

- 扇出多个网络搜索 agent；
- 抓取资料来源；
- 对关键论断进行对抗式验证；
- 最后综合成带引用的报告。

这个方法也适合非网络研究，例如：

- 汇总 Slack 状态报告；
- 探索代码库功能；
- 梳理内部文档信息。

---

###### 3）深度验证

适合需要“每条事实都要有出处”的报告。

典型流程是：

- 一个 agent 识别报告中的所有论断；
- 多个 subagents 分别核查每条论断；
- verifier agent 检查来源质量和引用可靠性。

例如：核查技术博客中“某函数会触发某副作用”的说法，workflow 可以对照真实代码逐条验证。

---

###### 4）排序任务

面对大量需要定性判断的条目，单次提示质量会下降，甚至撑爆 context。

例如：

- 给 1000 多行工单按缺陷严重程度排序。

workflow 可以采用：

- 锦标赛排序；
- 成对比较；
- 先分桶并行排名，再合并。

每次比较都由独立 agent 完成，context 中只保留当前排序状态。

---

###### 5）记忆与规则遵循

当 Claude 即使读了 `CLAUDE.md` 仍然漏掉规则时，可以用 workflow 加强遵循。

方法包括：

- 给每条规则配一个 rule verifier；
- 增加 skeptic 角色审查规则，避免误报；
- 从近期会话和代码审查评论中挖掘反复出现的问题；
- 用并行 agent 聚类这些问题；
- 对候选规则做对抗式验证；
- 最后把有效规则提炼回 `CLAUDE.md`。

核心问题是：这条规则是否真的能避免过去发生过的错误？

---

###### 6）大规模分类处理

triage workflow 可用于：

- 对大量条目分类；
- 和已有记录去重；
- 自动采取后续行动。

文章提到一个重要模式：**quarantine 隔离区**。

- 读取不可信公开内容的 agent，不能执行高权限操作。
- 高权限操作交给专门的信息处理 agent 执行。

这能降低安全风险。配合 `/loop`，workflow 可以持续运行。

---

###### 7）探索与品味判断

workflow 适合设计、命名、方案选择这类依赖“品味”的任务。

做法是：

- 让 Claude 探索多个方案；
- 让 review agent 根据 rubric 评判；
- 满足标准时停止；
- 或用锦标赛选出最佳方案。

例如：为 CLI 工具命名时，可以生成多组选项，再通过成对比较选出最合适的名字。

---

###### 8）评估 eval

workflow 可以用来跑轻量级评估。

流程包括：

- 在 worktree 中生成多个独立 agent；
- 让它们完成同一个任务；
- 再生成 comparison agent；
- 对照 rubric 给输出打分和比较。

例如：评估某个 Claude skill 是否符合标准，并据此改进。

---

###### 9）模型与智能路由

workflow 可以先创建 classifier agent 判断任务复杂度，再决定调用哪个模型。

适用场景：

- 工具调用很多；
- 文件数量不确定；
- 任务复杂度差异大。

例如：让 Claude 解释一个鉴权模块如何工作时，classifier 可以先调查涉及多少文件、代码库结构如何，再决定路由到 Sonnet 或 Opus。

---

##### 7. 何时不该使用 workflow

workflow 很强，但不是所有任务都需要。

不适合的情况：

- 普通编码任务；
- 简单 bug 修复；
- 不需要多视角验证的小任务；
- token 成本敏感的任务。

文章提醒：workflow 会消耗更多 token。不要为了常规编码强行加五个 reviewer，应该把它用在复杂、高价值、默认 Claude Code 难以稳定完成的场景中。

---

##### 8. 构建 workflow 的实用技巧

###### 1）提示词要具体

效果好的 workflow 通常需要清晰描述：

- 任务目标；
- 拆分方式；
- 验证标准；
- 停止条件；
- token 预算；
- 输出格式。

也可以要求快速 workflow，例如：“对这个假设做一次快速对抗式审查”。

---

###### 2）结合 `/goal` 和 `/loop`

- 对重复性任务，比如分类、研究、验证，可以配合 `/loop` 定期运行。
- 用 `/goal` 设置硬性完成标准。

例如：每隔一段时间扫描新工单，直到所有工单都被分类并去重。

---

###### 3）设置 token 预算

workflow 可能很费 token，因此应在提示中明确上限。

例如：

> 请创建一个 workflow，但总 token 使用不超过 10k。

这样可以控制成本，避免任务过度展开。

---

###### 4）保存与分享 workflow

- 在 workflow 菜单中按 `s` 可以保存。
- 可以将 workflow 签入 `~/.claude/workflows`。
- 也可以通过 skill 分发：
  - 把 JavaScript workflow 文件放进 skill 文件夹；
  - 在 `SKILL.md` 中引用。
- 如果想更灵活，可以让 Claude 把 skill 中的 workflow 当模板，而不是完全照搬。

---

##### 9. 总结：workflow 是探索 Claude Code 新用法的起点

workflow 为 Claude Code 提供了一种更强的扩展方式：让 Claude 不只是执行任务，而是能为任务临时设计执行框架。它尤其适合复杂、并行、多步骤、需要验证和评审的任务，但仍需要用户合理控制 token 成本，并根据场景判断是否值得使用。

## 深度解读（1）

### 2026-09-18 00:51:56

#### 动态 Workflow 的真正变化：AI 开始为任务临时编写“组织方式”

这项能力最值得关注的，并不是 Claude Code 能一次启动几十个甚至上百个 subagents，而是它开始把**“该如何组织智能”本身变成可生成、可执行的代码**。

默认 agent 通常在一个上下文里完成理解、规划、执行和自检。动态 workflow 则会先针对当前任务生成一段 JavaScript 编排脚本，决定如何拆分任务、选择模型、隔离 worktree、汇总结果以及何时停止。它不是单纯增强提示词，而是在运行时为任务临时构造一套 harness。

##### 很多 agent 问题，本质上是工作结构问题

文章列出的三种失效很典型：复杂任务做不完整、检查时偏袒自己的答案、多轮交互后逐渐遗失约束。它们未必能靠“换一个更聪明的模型”解决，因为问题来自同一个上下文同时承担太多角色。

Workflow 的处理方式是改变任务拓扑。例如，研究任务可以先并行搜集材料，再逐条核查论断，最后由另一个 agent 综合；安全审查可以让生成者与验证者分离；未知工作量的排查则不预设轮数，而是运行到“不再出现新错误”这一停止条件。

这里真正可迁移的认识是：**复杂任务的质量，越来越取决于如何分配上下文、角色和验证责任，而不只取决于模型单次回答的能力。**“扇出并综合”“生成并筛选”“对抗式验证”“循环至完成”可以视为几种基本积木，适用于代码、研究、事故排查和候选项排序等不同领域。

##### Workflow 会成为比 Prompt 更接近流程资产的东西

Prompt 主要表达意图，workflow 还编码了执行顺序、并行关系、权限边界、预算和验收条件。它可以保存、共享，并作为模板根据场景改写，因此更像一种**可执行的组织流程**。

这对团队的意义可能大于个人效率提升。比如，从历史会话和代码审查中提取反复出现的纠正，再用独立 agent 验证哪些规则确实能避免真实错误，最终写回 `CLAUDE.md`。这相当于把团队经验从零散反馈转化为可持续运行的质量机制。文章提到的 quarantine 也很重要：读取不可信公开内容的 agent 不应同时拥有高权限操作能力。随着 agent 获得更多工具权限，职责隔离会从最佳实践变成必要的安全设计。

相应的产品机会也不只是“workflow 模板市场”。更实际的需求是控制层：执行轨迹、来源追溯、token 预算、停止条件、权限隔离、失败恢复和人工审批。现有替代方案是手写 Agent SDK、静态流水线或人工复核；动态生成能否胜出，取决于它是否在降低编排成本的同时，仍然保持可审计和可预测。

##### 多 agent 不会自动带来可靠性

文章提供了丰富模式和案例，但没有给出系统性的质量、成本与延迟对比。多个 agent 使用相似模型时，错误可能高度相关；所谓“对抗式验证”，如果没有明确 rubric、外部证据或可执行测试，也可能只是让模型用另一种措辞认可自己。锦标赛适合命名和方案筛选，却未必适合存在客观真值、但评判器能力不足的问题。

因此，是否启用 workflow 可以看三个条件：任务能否有效拆分，结果能否被验证，以及错误成本是否足以覆盖额外算力。常规编码通常不满足第三项；大规模迁移、深度研究、安全审查和事故分析则更可能值得。

**动态 workflow 的长期价值不在于“更多 agent”，而在于把任务方法显式化。**当模型能够生成自己的执行结构，人类最需要定义的将不再是每一步怎么做，而是证据标准、权限边界、资源预算与真正的完成条件。
