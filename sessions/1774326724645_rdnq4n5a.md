### 我所知道的所有 Claude 代码技巧（2026 年 3 月）

[@kevinrose](https://x.com/@kevinrose) 询问应该使用什么 IDE。我的回复在 128 条回答中获得了最多的互动：“不需要 IDE。只需要 plan.md 文件和语音。” 以下是我想表达的全部内容。

![Image](https://pbs.twimg.com/media/HEDG86taYAAlOtk?format=jpg&name=large)

#### 当你产生一个想法的那一刻，就是 /ce:plan 或 /ce:brainstorm

我学到的最重要的一件事是：当我有一个想法时，就是 /ce:plan。

不是“让我想想”，不是“让我开始编码”。/ce:plan。每次。疯狂的产品想法？/ce:plan。有人在 GitHub 上发布了一个 bug？复制问题 URL，粘贴，/ce:plan。终端中出现错误？用 Cmd+Shift+4 截图，直接用 Ctrl+V 粘贴到 Claude Code 中，/ce:plan 修复这个问题。Claude Code 接受图片——错误截图、错误消息、设计原型、Slack 对话——并据此生成计划。

这是你运行它时的内部工作原理：/ce:plan 会并行启动多个研究代理。其中一个代理分析你的代码库——读取你的文件、发现模式、检查你的规范。另一个代理搜索你的文档/解决方案，以获取过去漏洞的经验教训。如果主题需要，更多代理将研究外部最佳实践和框架文档。所有代理同时进行。

然后它整合并撰写一个结构化的 plan.md：出了什么问题、应该采取什么方法、需要修改哪些文件、带复选框的验收标准、遵循自己代码中的模式。不是通用建议，而是基于你的代码库、你的规范和你的历史。

/ce:work 处理那个计划并构建它。将其分解为任务，执行每个任务，运行测试，检查并标记满足标准。上下文丢失？开始一个新会话，指向该计划，从上次中断处继续。计划是能够经受住一切的检查点。

传统开发中，80%的时间用于编码，20%用于规划。这正好相反。正如

[@jarodtaylor](https://x.com/@jarodtaylor) 所说："如果你用 80%的时间用 Opus 进行规划，然后让子代理蜂拥而上……" 思考发生在规划阶段。执行则是机械的。

Compound Engineering 是实现这一目标的插件。来自

[@EveryInc](https://x.com/@EveryInc):

/插件 插件市场 添加 EveryInc/复合工程插件

我成了超级粉丝。然后我成为了一名贡献者，在 GitHub 上排名第三，提交了 21 次，仅次于核心团队。@kevinrose 几周前向我介绍了它。

我在/last30days 路径下有 70 个计划文件和 263 次提交。差异在于我养成这个习惯之前的早期提交。我现在的规则是：除非是真正的单行修改，否则总是先有一个 plan.md 文件。

#### 2\. 获取语音红药丸

在 LLMs 出现之前，我无法忍受语音消息。苹果的内置语音输入让我想摔手机。但语音转 LLM 就不一样了。转录不需要完美，因为 Claude Code 理解上下文。它会猜测麦克风识别错误的地方。你可以含糊不清地说、话没说完、重新开始一句话。语音终于好用了，因为这个“倾听者”足够聪明，能填补空白。

Monologue（

[@usemonologue](https://x.com/@usemonologue)），来自 Every - 同一家公司（该公司还开发了 Compound Engineering）将语音输入到任何处于焦点状态的应用程序中。你说话，它会输入到 Claude Code 中。WhisperFlow 也很棒。选一个吧。我为办公室买了一个鹅颈麦克风。

我现在正在我的特斯拉车上使用完全自动驾驶功能口述这段内容，同时送孩子下车。这段内容是口述的，不是打字输入的。

#### 3\. 同时运行四到六个会话

这就是我实际度过一天的方式。四到六个 Ghostty 窗口，每个窗口运行一个独立的 Claude 代码会话。一个在写计划，一个在根据不同的计划进行构建，一个在运行/last30days 研究，一个在修复我在测试上一个东西时发现的 bug。

当/ce:plan 在一个窗口中启动研究代理时，我切换到另一个窗口并使用/ce:work 命令处理一个已编写的计划。在该计划构建的过程中，第三个窗口中粘贴了一个新的 bug。等我切换回第一个窗口时，计划已经完成并在 Zed 中等待。

这就是为什么绕过权限（下一节）是不可协商的。如果每个会话在每个操作时都询问“允许？”，你就无法进行上下文切换。它们都需要自主运行。检查、响应、继续前进。如果一切搞砸，GitHub 会在那里。

这也是为什么我的 MacBook 大约一个小时就没电了。六个 Claude 会话并行运行。刚刚订购了新的 MacBook Pro。

#### 4\. 三个改变一切的设置

Claude Code 的默认模式会对每次编辑、每次命令请求权限。你需要进行三项配置更改。

"危险地跳过权限" (是的，这就是它的实际名称)。\~/.claude/settings.json:

{ "权限": { "允许": \[ "网页搜索", "网页获取", "Bash", "读取", "写入" 编辑, Glob, Grep, 任务, 待办书写 \], "deny": \[\], "defaultMode": "绕过权限" }, "跳过危险模式权限提示": true }

skipDangerousModePermissionPrompt: true 是关键。没有它，Claude 会要求你确认每一个会话。你也可以按 Shift+Tab 来切换它。致谢：

[@danshapiro](https://x.com/@danshapiro)（Glowforge 创始人，《Hot Seat》作者）。当我设置一位朋友的 Claude Code 时，AI 积极阻止他启用此设置。你必须直接操作。这是你的电脑。

Claude 完成时的声音。 添加到同一文件：

{ "钩子": { "停止": \[ { "钩子": \[ { "类型": "命令", "command": "afplay /System/Library/Sounds/Blow.aiff" } \] } \] } }

离开。听到声音时回来。当有四到六个会话正在运行时，你需要知道哪个刚刚完成。感谢 Myk Melez。

Zed 自动保存。 在 Zed 设置中 (Cmd+,)：

{ "自动保存": { "延迟后": { "毫秒": 500 } } }

这是一个类似 Google Docs 的技巧。Zed 每 500 毫秒自动保存一次。Claude Code 监控文件系统。当 Claude 编辑文件时，更改会立即出现在 Zed 中。当你在 Zed 中输入内容时，Claude 会在一秒内看到。一侧是 Ghostty，另一侧是 Zed，两者都在查看同一个文件。这感觉就像在 Google Docs 上协作，只不过其中一个协作者是 AI。

![Image](https://pbs.twimg.com/media/HEDIfOcbIAAETjT?format=jpg&name=large)

#### 5\. 计划前调研

在我执行/ce:plan 之前，我经常先运行/last30days。

我当时在 Vercel 的 agent-browser 和 Playwright 之间做选择。我没有去看文档，而是运行了/last30days Vercel agent browser vs Playwright。几分钟内：78 个 Reddit 帖子，76 条 X 帖子，22 个 YouTube 视频，15 个 Hacker News 故事。agent-browser 使用的上下文 token 减少了 82-93%。Playwright 仅工具定义就消耗了 13,700 个 token。

[@rauchg](https://x.com/@rauchg) 的帖子获得了 964 个赞。

将整个输出输入到 /ce:plan integrate agent-browser 中。该计划是基于社区目前实际了解的情况制定的，而非六个月前的训练数据。

/last30days 是开源项目（4.5K 星标，

[github.com/mvanhorn/last30days-skill](https://github.com/mvanhorn/last30days-skill)）它并行搜索 Reddit、X、YouTube、TikTok、Instagram、HN、Polymarket 和网络。我做所有事情都会这样做。在我选择库之前，在我构建功能之前，在我撰写这篇文章之前。我运行 /last30days Compound Engineering 以获取第 1 节的最新社区引语。研究、规划、构建。这才是真正的循环。

![Image](https://pbs.twimg.com/media/HEDAOPpagAETMo8?format=jpg&name=large)

#### 6\. 将任何会议转变为计划.md

我和一位潜在候选人共进了午餐。我们讨论了一个公司尚未着手开发的新产品想法。还聊了聊美食、餐厅和孩子。整个一小时半的交谈中，既有日常闲聊，也穿插着产品头脑风暴的内容。

我让 Granola 在运行。午饭后，我将完整的转录文本——90 分钟，夹杂着关于寿司的离题内容——粘贴到 Claude Code 中：/ce:plan 将其转化为产品提案。

让它如此神奇的原因是：Claude Code 已经知道我们的产品代码在 GitHub 上的位置。它还能访问我的公司战略文件夹——我之前写的每一份战略计划.md。因此，当它处理 Granola 谈话记录时，它不仅仅是从午餐对话中提取想法，而是在交叉引用我们的实际代码库以及我们之前做的每一个战略决策。Granola 上下文 + 代码库 + 之前的战略计划 = 黄金。

一气呵成地完成了一份令人惊叹的提案。内容包含目标、用户故事、技术方案和里程碑。忽略了关于餐厅的部分。当晚就发给了候选人。

他现在全职和我们一起负责那个产品的工作。

Granola 现在支持 MCP，所以我直接在 Claude Code 中使用它。不再需要复制粘贴。每次会议的上下文都直接流入计划。

#### 7\. 使用计划文件处理一切，而不仅仅是代码

我正在为公司撰写战略文档。Claude Code 和 Markdown 文件并排打开。我对 Monologue 说：“给我三个市场进入策略的方法，列出每个的优缺点。”

Zed 中出现了三个选项。“第二个选项最接近，但第一个选项的表述更好。将它们合并。” 立即更新。“现在处理最大的风险。” 已添加。“第二段太长了。” 已缩短。

Claude Code 导入了我们的 GitHub，因此它能理解当前产品。它还可以访问我所有之前的策略计划.md 文件。当我撰写新的定位时，它能了解我之前做出的每一个战略决策的完整上下文。这种累积的上下文使得每个计划都比上一个更好。

策略文档、产品规格、竞争分析，本文。相同的工作流程。讨论、规划、迭代。

#### 8\. 运行 Mac Mini 以远程运行 Claude 代码

我配置了一台用于 OpenClaw 的 Mac Mini，但我还用它做了另外两件事：

用手机上的 Telegram。 Claude Code 有 Telegram 集成。我通过手机上的 Telegram 给我的 Mac Mini 发送消息。吃饭时，想到一个 bug，在 Telegram 中输入 /ce:plan fix the timeout issue。当我回到屏幕前时，计划会在 Zed 中等待。Claude Code 甚至会在我不在时，使用我的 OpenClaw AgentMail 给我发送计划文件的邮件。

tmux 在飞机飞行中使用。 鸣谢：内森·史密斯。Claude 代码无法很好地处理飞机上的 WiFi。连接断开，会话终止，甚至不会提示你。但是先通过 tmux 连接到你的 Mac Mini，会话在那台机器上运行。你的笔记本电脑只是一个窗口。在大西洋上空 WiFi 断开 20 分钟？重新连接。会话会准确地保持你离开时的状态，并且确实能正常工作。

Shipped 包含整个从欧洲返回的航班。

#### 这篇文章是用这个工作流程撰写的

这是 Zed 中的一个 Markdown 文件。Claude Code 正在 Ghostty 中运行。我对着 Monologue 说：“主题不对，重写开头。”“添加 Granola 的故事。”“别把 Zed 叫做我的集成开发环境。”Claude 重写。更改出现在 Zed 中。我做出反应。七次完整的重写。

这就是我所知道的一切。一个语音应用、一个计划文件插件、三项配置更改、四到六次并行会话、一台 Mac Mini，以及转化为产品提案的会议。没有 IDE。没有代码。讨论、计划、构建。从办公桌旁、沙发上、汽车里。

#### 奖励：当您的令牌用完时

这种效率会耗尽你每月 200 美元的 Claude Max 计划预算。全天同时进行四到六个 Opus 会话，累计起来的成本会很高。

答案：还可以选择每月 200 美元的 Codex 计划。安装 Codex CLI，Compound Engineering 可以改用 Codex 积分进行构建。我刚刚向 Compound Engineering 推送了/ce:work --codex 命令 - 今天已合并 - 当 Claude 积分不足时，该命令会将实现工作委派给 Codex。

一些朋友使用 Codex 对 Claude Code 的代码工作进行代码审查，反之亦然。其他人更喜欢 Codex 的代码输出，但会从 Claude Code 中调用它来进行编排。这两种方案相辅相成。Claude 用于规划，Codex 用于繁重的实现工作。

我还有一个“night-night”模式，我在睡觉时运行它来工作，但解释这个是以后的事了。

#### 奖励 2：迪士尼乐园 逐点解说

为了展示一个非代码相关内容的完整工作流程，这里有一个今天发生的真实例子。我在足球场看我孩子们的比赛，期间和另一位家长聊起了迪士尼乐园之旅，于是我拿出笔记本电脑给她看。

步骤 1: /last30days 迪士尼乐园。两分钟后，全貌显现。66 个 Reddit 帖子（11,804 点赞），34 条 X 帖子，8 个 YouTube 视频。价格冲击是主要话题——一篇 8,500 美元的旅行报告在 r/迪士尼规划子版块获得了 183 条评论。仅 3 月就有 6 个游乐设施关闭。巴斯光年将于 4 月 8 日重新开放，配备新的发射器。摇滚过山车将改造成《布偶秀》主题项目。恐龙乐园被拆除。

步骤 2: “Pairl 4 月 16 日哪些会开放/不开放（具体来说，所有拼写错误都包括在内 - CC 不在意）。Claude 查看了翻新日历，交叉参考了过去 30 天的数据，给了我完整的开放/关闭列表。

Step 3: /ce:plan 我将在迪士尼乐园待一天。我想至少玩三个园区，可能四个，大概率四个，因为我太疯狂了。我想在未来世界（Epcot）体验《守护者联盟》项目，在好莱坞影城玩几个游乐设施，在魔法王国（World）玩几个游乐设施，在动物王国体验雪山飞车，并且至少体验一个阿凡达项目。另外，获取所有 Genie+服务及其他能让行程顺利的策略是什么？还有，一周前我是不是得查点什么？我什么时候该买什么？帮我设置提醒。我不关心食物。我没有住酒店。愿意支付 25 美元购买一次性通行证。

#### 文章主旨

这篇文章的核心观点是：作者认为，使用 Claude Code 的最佳方式不是“直接写代码”，而是先把想法、问题、会议记录等全部转成 `plan.md`，再让 AI 按计划执行。  
围绕这个核心，他总结出一套高效工作流：**语音输入 + 计划驱动 + 多会话并行 + 自动化配置 + 持续调研**。

##### 1. 先规划，再动手：`/ce:plan` 是整个工作流的起点

- 作者最强调的一条原则是：**一有想法，先运行 `/ce:plan`**，而不是马上编码。
- 适用场景非常广：
  - 产品新想法
  - GitHub bug 链接
  - 终端报错
  - 错误截图、设计稿、Slack 对话
- Claude Code 不只看文字，也能接收图片，因此可以直接把截图粘进去让它生成修复计划。

###### 这一过程是怎么工作的

- `/ce:plan` 会并行启动多个“研究代理”：
  - 一个研究代码库，分析已有文件、代码风格、规范；
  - 一个搜索历史文档或过去解决方案；
  - 需要时还会查外部最佳实践和框架文档。
- 最后生成结构化的 `plan.md`，通常包括：
  - 问题是什么
  - 推荐方案是什么
  - 需要改哪些文件
  - 验收标准（带复选框）
  - 如何遵循项目已有模式

###### 为什么作者认为这比传统开发更高效

- 他认为传统开发是“**80% 编码，20% 规划**”，而现在应该反过来。
- 他的结论是：**真正的思考发生在规划阶段，执行本身是机械工作**。
- 之后再用 `/ce:work` 按计划拆任务、执行、跑测试、勾选验收项。
- 如果会话中断，也可以在新会话中重新指向原计划继续，因此 `plan.md` 像一个“检查点”。

###### 数据与实践

- 作者在 `/last30days` 路径下已经积累了 **70 个计划文件** 和 **263 次提交**。
- 他现在的规则是：**除非只是单行修改，否则一律先写 `plan.md`**。

##### 3. 多会话并行：一天同时跑 4 到 6 个 Claude 会话

- 作者实际工作时，会同时打开 **4 到 6 个 Ghostty 窗口**，每个窗口运行独立的 Claude Code 会话。
- 这些会话会并行处理不同任务，例如：
  - 一个在写计划
  - 一个在根据计划构建
  - 一个在跑 `/last30days` 做研究
  - 一个在修复刚发现的 bug

###### 为什么这样做有效

- 当一个窗口在跑 `/ce:plan` 时，他会切到另一个窗口执行 `/ce:work`。
- 再切到第三个窗口时，可能又能顺手提交一个新的 bug 处理请求。
- 也就是说，**等待 AI 处理的时间，被另一个 AI 会话“填满了”**。

###### 对系统资源和权限的要求

- 这套模式要求每个会话都能相对自主运行，不能每一步都手动点“允许”。
- 作者甚至说：如果所有操作都要不断授权，就根本无法顺畅切换上下文。
- 代价也很直接：
  - 他的 **MacBook 大约 1 小时就没电**
  - 所以他又买了一台新的 **MacBook Pro**

##### 4. 三个关键配置：真正改变使用体验的地方

作者认为，Claude Code 默认的权限与保存方式，会严重拖慢效率，因此需要做 3 个关键设置。

###### 4.1 跳过频繁权限确认

- 他最看重的配置是开启“**危险地跳过权限**”。
- 关键设置包括：
  - 允许 Web 搜索、抓取、Bash、读写等权限
  - `defaultMode` 设为绕过权限
  - `skipDangerousModePermissionPrompt: true`

###### 他的观点

- 如果不开这个设置，Claude 几乎每一步都要问“是否允许”，多会话协作就失去意义。
- 他还提到，甚至有一次 AI 在阻止朋友启用这个设置，但他强调：**这是你的电脑，你应自己决定**。

###### 4.2 完成任务时播放提示音

- 他在 hook 里配置了 Claude 停止时播放声音：
  - `afplay /System/Library/Sounds/Blow.aiff`
- 原因很实际：当你同时跑 4 到 6 个会话时，需要知道哪个会话刚完成。

###### 4.3 Zed 自动保存

- 他在 Zed 中设置：
  - **500 毫秒自动保存**
- 这样 Claude Code 监控文件变动时，就能和 Zed 实时同步。
- 效果像：
  - 一边是 Ghostty
  - 一边是 Zed
  - 像在和 AI 共同编辑 Google Docs

#### 一、内容总结

这篇文章的核心观点只有一句话：

> **把“先写代码”改成“先做 plan.md 计划”，再让 AI 去执行。**

作者分享了一套以 Claude Code 为中心的工作流，重点包括：

- **任何需求先 `/ce:plan`**：无论是新功能、报错、Bug、会议记录，先生成 `plan.md`。
- **AI 先研究再执行**：`/ce:plan` 会并行分析代码库、历史文档、外部资料，产出结构化计划；`/ce:work` 再按计划实现。
- **大量使用语音输入**：作者认为“语音 + AI”比传统键盘输入更高效，适合快速记录想法。
- **多会话并行工作**：同时开 4~6 个 Claude 会话，一个做计划，一个写代码，一个查资料，一个修 Bug。
- **做了激进配置**：关闭大量权限确认、启用完成提示音、开启编辑器自动保存，以提高流畅度。
- **先做“最近30天调研”**：用 `/last30days` 抓社区最新信息，再喂给 `/ce:plan`，避免只依赖模型旧知识。
- **不只写代码**：会议纪要、战略文档、产品提案、旅行计划，都能用同样流程处理。
- **远程与自动化协作**：通过 Mac mini、Telegram、tmux 等，让 AI 在人不在电脑前时也能继续工作。
- **Claude 与 Codex 搭配使用**：作者倾向于“Claude 负责规划，Codex 负责重实现”。

#### 二、深入浅出地解读

##### 1. 这套方法本质上在解决什么问题？

它解决的不是“怎么写代码更快”，而是：

- 想法很多，但容易直接开写，最后返工；
- AI 很强，但上下文容易乱；
- 复杂任务如果没有计划，AI 和人都会越做越偏；
- 切换任务太多时，人脑容易丢线索。

所以作者的答案是：

> **先把任务写成一个可执行的计划文件，再把计划当成整个工作的锚点。**

`plan.md` 在这里相当于：

- 项目的施工图
- AI 的任务说明书
- 中途断线后的恢复点
- 验收标准清单

这也是为什么作者反复强调“不是先想想，不是先写代码，而是先 `/ce:plan`”。

---

##### 2. 为什么“计划优先”会有效？

因为 AI 最怕两件事：

- **目标模糊**
- **上下文混乱**

如果直接让 AI 写代码，它经常会：

- 误解需求
- 忽略已有代码风格
- 漏掉边界情况
- 改出一堆连锁问题

而先规划，等于先把这些问题暴露出来。

通俗说：

- 以前是“边开车边看地图”
- 现在是“先把路线定好，再上路”

作者甚至把传统开发的比例倒过来：

- 传统：80% 编码，20% 规划
- 他的方式：**80% 规划，20% 执行**

这其实很像资深工程师的思路：  
真正难的不是“敲代码”，而是“想明白”。

---

##### 3. 为什么语音会成为关键？

作者特别强调“语音红药丸”，本质原因不是语音识别更准，而是：

> **有了 LLM 后，语音输入不需要 100% 准确。**

以前语音转文字不好用，是因为一旦识别错，系统就傻了。  
现在 AI 能结合上下文自动“脑补”你的意思。

这带来几个变化：

- 想法出现时能立刻说出来，不用整理成完美文本；
- 适合走路、开车、开会后快速记录；
- 输入门槛变低，思路更连续。

换句话说，语音不是替代打字，  
而是在抢“灵感出现的那几秒钟”。

---

##### 4. 多开 4~6 个会话，为什么作者觉得合理？

这看起来很夸张，但背后的逻辑很清楚：

- 一个会话在规划
- 一个会话在实现
- 一个会话在研究
- 一个会话在修前一个任务冒出来的问题

作者实际上把 AI 当成一组“并行实习生/工程师”在调度。

这也是整篇文章里最激进的部分。  
它的前提是：

- 机器性能足够
- 成本预算足够
- 你能管理好多线程工作
- 工具权限放得很开

所以这套方式对重度用户非常爽，  
但对普通人不一定适合。

---

##### 5. 为什么他如此强调“去掉权限确认”？

因为频繁确认会打断整个并行流。

作者的意思是：

- 如果每改一个文件都要问一次
- 每跑一个命令都要点一次允许
- 多窗口切来切去就会非常痛苦

所以他选择了“危险但高效”的路线：  
**尽量让 AI 自主跑完。**

这确实能提高效率，但风险也明显：

- 误删文件
- 错改配置
- 跑错命令
- 扩大损失范围

作者的态度是：反正有 GitHub，可以回滚。  
这更像一个高频实验型开发者的做法，而不是稳健团队的默认配置。

---

##### 6. `/last30days` 为什么重要？

这是整篇文章里很有价值的一点。

作者认为，仅靠模型训练数据不够，因为很多信息会过时。  
所以他先用 `/last30days` 去抓：

- Reddit
- X
- YouTube
- Hacker News
- 各类近期社区讨论

然后把这些“近 30 天的新鲜认知”喂给 `/ce:plan`。

这相当于给 AI 补了一层“最新行业现场情报”。

简单说：

- LLM 提供的是“通用知识”
- `/last30days` 提供的是“最近变化”
- `plan.md` 把两者变成“可执行方案”

这个链路其实很有启发性，尤其适合：

- 选技术栈
- 比较新框架
- 调研社区反馈
- 避免踩新坑

---

##### 7. 为什么作者说它“不只是代码工作流”？

因为这套方法本质不是写代码，而是：

> **把模糊信息整理成结构化行动计划。**

所以它天然可以处理：

- 产品方案
- 战略文档
- 会议纪要
- 竞品分析
- 出行攻略
- 提醒与自动化执行

作者举迪士尼行程的例子，其实是在说明一件事：

- 先调研
- 再规划
- 再生成页面/执行提醒
- 最后自动化落地

这已经不是“编程助手”，而是“通用任务编排助手”。

#### 三、我的意见

##### 我认同的地方

- **“先计划再执行”非常对。**  
  这是这篇文章最有价值的思想，尤其适合复杂任务和多人协作。

- **把 `plan.md` 当作工作中枢，很实用。**  
  它能降低上下文丢失，也方便中断恢复和结果验收。

- **“先补最新信息，再让 AI 规划”很聪明。**  
  这比盲信模型记忆靠谱得多。

- **语音 + AI 确实会成为高频输入方式。**  
  特别适合记录灵感、头脑风暴和会后整理。

##### 我保留意见的地方

- **4~6 个并行会话，不适合大多数人。**  
  普通开发者很可能还没提效，先被任务切换拖垮。

- **完全绕过权限确认，风险偏高。**  
  对个人实验项目也许可行，但对正式项目、团队仓库、生产环境不建议照搬。

- **作者的工作流高度依赖个人习惯和高投入。**  
  包括昂贵订阅、强设备、多工具联动、远程机器、长期积累的上下文，不是人人都能复制。

- **“不需要 IDE”有点夸张。**  
  更准确地说，不是 IDE 不重要，而是 IDE 的核心地位被削弱了；编辑器、终端、AI、计划文件正在一起组成新的工作台。

##### 我的建议

如果你想借鉴这篇文章，最值得先学的不是“全套复制”，而是这 3 点：

1. **任何超过 10 分钟的任务，先写 `plan.md`**
2. **先调研最新资料，再让 AI 出方案**
3. **把 AI 当“规划 + 执行搭档”，而不只是代码生成器**

如果再进一步，可以逐步尝试：

- 先开 2 个会话，而不是 6 个
- 先对安全命令放宽权限，而不是全部放开
- 先把语音用于“记录想法”，再扩展到完整工作流
