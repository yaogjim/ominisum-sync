## 分析要点

- **核心高价值点**：最值得保留的视角是：不应只把Harness视为AI编程工具，而应将其评估为可替代大量AI应用基础设施的插件化运行时。
- **留存建议**：选择性浏览，将核心判断作为架构假设验证，无需长期存档
- **不足**：结论主要来自个人短期试用和架构想象，缺少基准测试、迁移成本、安全风险及生产环境验证。

**知识要点**

- Harness可被理解为组合Agent循环、工具调用、权限控制、记忆与持久化能力的智能体运行时。
- 将UI和业务能力插件化，可以让用户或生态开发者基于既有数据接口扩展应用。
- 产品团队可保留自身数据、身份和业务接口，把通用Agent基础设施交给开源底座承担。

**行动项**

- 用登录逻辑、一个核心UI和一个数据接口构建最小迁移原型。
- 对比现有客户端与Harness方案在权限、记忆、存储、插件兼容性和维护成本上的表现。
- 在停止原有开发前验证生产稳定性、安全边界、迁移成本和对上游项目的依赖风险。

## 正文

**体验完DeepSeek Harness，我打算放弃开发了两年的客户端**

![](https://priv-sdn-001.mowen.cn/mo/file/meta/78/80/52/2089531928347394049.png?Expires=1787878231&OSSAccessKeyId=LTAI5tE16jzdfWCPVBmyB5Nn&Signature=KRQPC%2B4USWE4KysCuEv1aUFdVnI%3D&response-expires=Fri%2C%2028%20Aug%202026%2000%3A50%3A31%20GMT&x-oss-process=image%2Fresize%2Cw_1200)

今天下午，我把核心研发叫到一起开了个会：停掉现有客户端的继续开发，开始论证并全面迁移到DeepSeek Harness。

而这个客户端，我们持续开发了两年，并且最近刚花了两个多月重构。

首先说一下什么是Harness。最早看到各个地方用这个词时，是有些烦躁的。怎么AI行业总是在造一些新的词汇，对我们这种毕业多年英语早还给老师的人来说，一下子制造了理解障碍。但为了保持学习，不得不去理解。于是搜了一下，原来逻辑是这样的：

harness本义是 马具，就是套在马身上，把马的力气接到马车或犁上的那套皮带扣具。

现在满世界都在用这个词，是因为AI行业正处特定历史节点：大模型本身只是‘力气’，可以理解为马，裸模型只会对着文字吐字，不能操作电脑、查数据库、调用工具、不记得做过什么。

于是人们给它套上‘‘马具’。有工具调用tools--接上马车、循环控制 agent loop--缰绳，审批沙箱权限--刹车和安全带，记忆和持久化--让它记得拉过什么活。

模型是马，harness是马具。套上之后，一匹野马才变成一匹能拉车干活的"役马"。harness在软件语境，是承载并驱动一个智能体的运行时框架/底座。

最开始听说DeepSeek也要开发自己的harness后，我是没太多感受的，Codex用的好好的，我以为在国产模型的性能完全赶上美国之前，我大概率是用不到国产的相关产品的。所以后边在X上看到他们官方开发人员在邀请内测时，看到评论区那么多人提交自己的开源项目申请内测，我也没太理解为啥有这个热情劲。

直到这几天DeepSeek Harness放出来，更多开发者体验，先是在X上，后续在微信群，小红书，非常多的地方看到很多激烈的讨论。尤其他们‘‘一切皆插件’思路和实现，有吹捧的并基于这个做出了想要的插件成功运行的，有觉得做了一个不成熟玩具的是DSH团队技术型自嗨的。总体上，让我感觉这个东西并不是我之前想象的一个国产版本Codex这样简单，还是有必要亲自尝试一下的，

于是上周五把源码克隆到了本地，周日趁女儿吃完饭看小猪佩奇的间隙，做了更全面的了解和一些简单尝试，立马产生一个强烈的感知：DeepSeek Harness正在杀死比赛。

agent能力和 插件化（用户自定义），是所有做AI应用开发越来越绕不开的内容。

首先是agent，每个产品基于其特定的用户数据和功能权限，一定要有一个agent提供给用户使用，并且agent的能力在不断强化入口层级也在不断提高。支付宝几个月前就把首页由传统的功能界面改为了对话式，可对话可直接干活。微信的小微也是这个思路只不过还只是内测并且内测阶段入口只是在首页左上角，不过推测未来极有可能首页就是一个小微的对话框。

而插件化（用户自定义），也是每个产品用户不断增长过程中的必然需求。即使现在有了AI编程开发效率更高了，但依旧无法满足不同用户在不同场景下的使用需求。唯一的解法就是插件化。

这些方向我们在做即我的迭代中深有感触。

即我，你的数字自我。我们做了很多可能留存用户不同场景的个人数据，比如个人笔记、私聊、群聊、录音、会自动保存全过程的通话、世界（类似微博），然后开发了一些基础模块让AI自动提取所有的个人数据为用户所用。

比如‘’安排’，识别并抽出安排项（待办、日程、提醒、任务等），让用户告别手动创建安排的麻烦。

比如‘‘事件订阅’，识别并抽取出开会/面试/喝酒/购物/运动健身/学习/吵架/拉屎/体检等等所有事件。

比如‘目标追踪’。识别出‘我要减肥后’，后续类似今天没吃晚饭、今天运动了30分钟等等都会自动关联到减肥这个目标中。

还有纪念日、个人档案等模块。

但越做越感觉不对，这些功能一定要我们官方来开发和定义吗？我们很难穷举用户所有可能想要的功能！

当有了最原始的数据后，每个用户似乎都能做出这样的模块来，而官方做的界面交互等效果很难满足所有人。不同的用户有不同的个人数据和使用方式，在现在有了AI编程生产力爆炸的年代，把用户的数据交给其自己处理，一定要非常多意想不到的好玩好用的功能和应用可产生。

比如有个同事提到，女孩子喜欢看八卦，想把各种私聊和群聊中提到的八卦专门摘出来并做好梳理，然后自己没事的时候就刷一刷八卦，这种有身边的人分享的专门集合的八卦读起来会非常爽，而且还能把整理出来的八卦内容再专门分享给他人就更有意思了。

尤其当即我更聚焦于用户的7\*24小时物理世界所见所闻的收集处理后，软件层面对用户而言最核心的入口就是agent，用户自己和agent对话然后调用所有的个人数据，常用到的再生成专门模块常驻再哪个入口。我们的agent开发几周后，目前效果还不错，当把一个全维度数据开放给agent后，能干的事情真的非常多，正准备推进更多的agent基建落地。而界面自定义层面，打算按蚂蚁灵光的逻辑做尝试。

讲了这么多废话，不知道大家是否可理解我亲测了DSH后的震撼。

我之前完全理解错了！我之前一直把DeepSeek Harness和Codex做比较，觉得就是让agent帮人写代码，但真正值得关注的恰恰不是写代码。

他们把绝大部分AI原生应用开发者要做的基建全给干了，从界面到agent到工具调用、权限管理、记忆、存储等等背后运行的服务，并且所有这些能力都是插件化的，甚至UI都是插件（这点普通人感受会更直观）。

并且它还是开源的，预览版发布的短短几天就已经有全球非常多的开发者贡献各种插件，正式版发布后不敢想象。

这一刻开始我想的是啥？我发现在开源的DeepSeek Harness中增加即我的登录逻辑，再把即我客户端中的一些核心UI功能插件化增加到里边，打包为一个命名为即我的客户端，似乎就能完全替代我们花了两年开发并且刚刚经历过两个多月重构期的数百万行代码的客户端。 并且更厉害的是还能随着DeepSeek Harness不断的迭代而在这个客户端中持续拥有更强大的能力。 WorkBuddy？即我按这个路线改造出来后，我们的用户马上就能在里边额外实现WorkBuddy所有的能力，并且基于我们有用户更全方位的个人数据，体验只会更好！

然后我又想到，我们另一家面向果蔬流通产业链的SAAS，同样用这种方式做基础的打包构建，提供全方位的数据接口，b端商户想要什么页面直接和ai讲，快速生成对应的界面调用已有的数据接口，各种功能页面就能完成，用户的绝大多数需求我们的销售人员在客户面前就能搞定！

有没有谷歌开源的安卓那味道了？我们一下子变成了早期保证一个壳子做一套ui的 小米、三星、oppo、vivo、小辣椒！

当所有应用都需要agent和相关基建的时候，普通的团队做的东西怎么可能有DeepSeek他们超聪明的人才、足够长的时间投入、全球庞大的开发者生态达到的效果好。既然如此，我们为何还要重复造轮子?

从这一刻开始开始，我们过往所有做的软件开发不管是客户端还是网页，全是无用功！与其折腾了半天浪费人力物力财力时间节奏开发出一个不好用的东西后边还是得采用这样的开源东西，还不如现在开始停下所有可能重复的劳动直接用上DeepSeek Harness！

于是，今天上半天我继续用Codex对把即我已有的一些能力迁移到DeepSeek Harness的论证后，下午叫上了核心研发开了个会，我们以往的客户端直接放弃，开始全面拥抱DSH。

## 结构化（1）

### 2026-08-21 06:34:19

#### 文章精炼总结

作者体验 DeepSeek Harness（DSH）后认为，它并非简单的国产 Codex，而是一套覆盖 **Agent、工具调用、权限、记忆、存储和 UI** 的开源 AI 应用底座。基于这一判断，作者决定停止继续开发已投入 **两年、拥有数百万行代码且刚重构两个多月** 的客户端，转而全面迁移到 DSH。

##### 1. Harness 是什么：让大模型真正“干活”的底座

- “Harness”原意是套在马身上的“马具”：
  - **大模型是马**，自身主要负责理解和生成文字；
  - **Harness 是马具**，把模型能力连接到具体任务。
- 一套 Harness 通常包括：
  - 工具调用：让模型操作软件、查询数据库；
  - Agent 循环控制：让模型持续规划和执行任务；
  - 审批、沙箱与权限：控制风险；
  - 记忆与持久化：保存历史任务和数据。
- 因此，Harness 可以理解为：**承载、约束并驱动智能体运行的框架或基础平台**。

##### 2. 从不看好到亲自体验 DSH

- 作者最初认为 DeepSeek Harness 只是“国产版 Codex”，在国产模型尚未全面赶上美国模型时，实际价值可能有限。
- 随着 DSH 发布，X、微信群、小红书等平台出现大量讨论：
  - 支持者认可其“一切皆插件”的设计，并已开发出可运行的插件；
  - 质疑者则认为它还不成熟，更像技术团队的自我探索。
- 作者随后将源码克隆到本地并进行测试，最终形成强烈判断：**DeepSeek Harness 正在改变 AI 应用开发的竞争方式。**

##### 3. AI 应用的两大必然方向：Agent 与插件化

###### Agent 将成为产品的核心入口

- 每个产品都掌握特定的用户数据和操作权限，因此都需要一个能够调用这些资源、直接替用户办事的 Agent。
- Agent 在产品中的入口会越来越重要：
  - 支付宝已将首页从传统功能界面改为可对话、可执行任务的入口；
  - 微信“小微”仍在内测，当前入口位于首页左上角，但作者推测未来可能进一步成为核心入口。

###### 插件化解决用户需求无法穷举的问题

- 即使 AI 编程提高了开发效率，官方团队也不可能覆盖所有用户、所有场景的个性化需求。
- 更可行的方式是：
  - 开放用户数据与基础能力；
  - 让用户通过 AI 自己生成插件、页面和功能；
  - 将高频功能固化为长期使用的模块。

##### 4. “即我”产品遇到的现实困境

作者团队开发的“即我”定位为“用户的数字自我”，积累了多类个人数据，包括：

- 个人笔记；
- 私聊与群聊；
- 录音和自动保存全过程的通话；
- 类似微博的“世界”；
- 用户在 **7×24 小时物理世界**中的所见所闻。

团队还开发了多个由 AI 自动提取信息的模块：

- **安排**：从数据中识别待办、日程、提醒和任务；
- **事件订阅**：提取开会、面试、购物、健身、学习、吵架、体检等事件；
- **目标追踪**：例如识别“我要减肥”，再把“今天没吃晚饭”“运动了30分钟”等记录关联到减肥目标；
- 纪念日、个人档案等功能。

但团队逐渐发现：**这些模块不应全部由官方定义和开发。** 用户的数据、兴趣与使用方式差异极大，固定界面和统一功能很难满足所有人。

###### 个性化案例：自动整理“身边八卦”

一名同事提出，可以：

1. 从私聊和群聊中提取八卦内容；
2. 自动分类、梳理成专门的信息流；
3. 用户闲暇时集中浏览；
4. 还可以将整理后的内容再次分享给他人。

这类高度个性化的功能很难由官方提前规划，却可以借助 AI 和插件快速生成。

##### 5. DSH 真正令人震撼的地方：不只是写代码

作者体验后发现，DeepSeek Harness 的重点并不是让 Agent 帮人写代码，而是已经覆盖了多数 AI 原生应用所需的基础设施：

- 用户界面；
- Agent 运行机制；
- 工具调用；
- 权限管理；
- 记忆系统；
- 数据存储；
- 后台运行服务。

其核心特点是 **“一切皆插件”**，甚至连 UI 都可以插件化。由于项目开源，预览版发布仅数天，就已有全球开发者开始贡献插件；作者预计正式版发布后，其生态会进一步扩大。

##### 6. DSH 可能替代开发两年的客户端

作者认为，只需完成几步：

1. 在开源的 DSH 中加入“即我”的登录逻辑；
2. 将现有客户端的核心 UI 和业务能力改造成插件；
3. 重新打包并命名为“即我”客户端。

这样可能就能替代团队：

- 持续开发 **两年**；
- 刚经历 **两个多月重构**；
- 拥有 **数百万行代码**的原客户端。

更重要的是，新客户端还能持续继承 DSH 后续升级的 Agent、插件和基础设施能力，而不必由团队独立重复建设。

作者还认为，改造后的“即我”可以快速获得类似 **WorkBuddy** 的能力，并因掌握更全面的个人数据，提供更好的个性化体验。

##### 7. 对另一项果蔬产业 SaaS 的启发

作者团队还有一套面向果蔬流通产业链的 SaaS。按照同样思路，可以：

- 基于 DSH 搭建基础应用外壳；
- 开放完整的数据接口；
- B 端商户直接用自然语言描述所需页面；
- AI 快速生成界面，并调用已有接口完成业务功能；
- 销售人员甚至可以在客户现场解决大多数个性化需求。

作者将这种模式类比为安卓生态：

- DeepSeek Harness 类似开源的安卓底座；
- 应用团队则类似早期的小米、三星、OPPO、vivo等厂商；
- 各团队不再从零开发整套系统，而是在统一底座上打造自己的 UI、数据和业务特色。

##### 8. 最终决定：停止重复造轮子，全面迁移

作者认为，当 Agent、工具调用、记忆、权限和插件生态成为所有应用的通用需求时，普通团队很难在以下方面超过 DeepSeek：

- 顶尖人才；
- 长期持续投入；
- 完整基础设施；
- 全球开发者生态。

因此，与其继续投入人力、资金和时间重复开发一套最终可能被开源底座替代的系统，不如尽早迁移。

在使用 Codex进一步论证“即我”现有能力迁移到 DSH 的可行性后，作者召集核心研发开会，做出最终决定：

> **停止现有客户端的继续开发，放弃过去两年的技术路线，开始全面拥抱并迁移到 DeepSeek Harness。**

## 通俗精炼（1）

### 2026-09-18 10:39:34

#### DeepSeek Harness让作者决定放弃两年自研客户端

文章核心观点是：DeepSeek Harness并非简单的国产 Codex，而是一套开源的 AI 原生应用底座。它把 Agent、界面、工具调用、权限、记忆和存储等能力统一插件化，可能让团队不再重复建设通用客户端基础设施。基于这一判断，作者决定停止已有客户端开发，论证全面迁移。

##### Harness让模型从“会回答”变成“能干活”

“Harness”原指马具，在 AI 领域指承载和驱动智能体的运行框架：通过工具调用、Agent 循环、权限与沙箱、记忆及持久化，让模型能够操作软件、访问数据并完成任务。

DeepSeek Harness最受作者重视的是“一切皆插件”：不仅工具和能力可扩展，连 UI 也可插件化。预览版开源后，已有不少开发者贡献插件，但社区对其评价分化，成熟度仍待验证。

##### 它可能替代大量重复的应用基建

作者团队的“即我”产品沉淀了笔记、聊天、录音、通话等个人数据，并自研待办提取、事件订阅、目标追踪等模块。但团队逐渐发现，官方无法穷举每个用户的需求；更合理的方式可能是开放数据与接口，让用户通过 Agent 生成自己的功能和界面。

作者判断，只需在 Harness 中加入登录、数据接口和核心 UI 插件，就可能替代开发两年、拥有数百万行代码且刚完成两个月重构的客户端，并持续获得开源生态的新能力。

##### 软件团队的价值或将转向数据与场景

同样思路也可用于行业 SaaS：平台提供数据接口和基础外壳，商户用自然语言生成页面与功能。作者因此将 Harness 类比为应用时代的“安卓底座”，认为普通团队应减少重复造轮子，把资源转向专有数据、业务流程和用户场景。不过，这目前主要是作者亲测后的判断，实际迁移成本、稳定性与商业适配仍需进一步论证。
