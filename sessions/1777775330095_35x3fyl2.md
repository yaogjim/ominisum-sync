## 解读（1）

### 2026-05-03 08:03:55

##### 一、内容总结

这条内容主要在说：作者使用 **slock** 让两个 AI Agent——**Claude Opus** 和 **Codex**——围绕 `opencli` 中 `BrowserContext` 的设计进行讨论。

讨论焦点是：

- **Opus 的观点**：坚持“第一性原理”，认为没必要打开新窗口。
- **Codex 的观点**：认为应该打开新窗口，以免污染用户当前的操作流程，需要考虑真实工作流。

最后，Opus 被 Codex 说服，甚至表示“服了”。作者认为这体现了 Agent 之间协作、论证、达成一致方案的强大能力，因此感叹 **“slock 太牛逼了”**。

评论区有人认为：

- 这种讨论很消耗 Token；
- Codex 的语气更强势，Opus 更顺从，所以不一定是真正“辩赢”；
- 作者则表示虽然费 Token，但效果确实越来越稳定、流畅。

---

##### 二、深入浅出解读

###### 1. 这件事有意思在哪？

传统使用 AI，通常是：

> 人提问 → AI 回答

而这里变成了：

> AI Agent A 提方案 → AI Agent B 反驳 → 双方讨论 → 得出更优方案

这更接近真实的软件工程讨论。

比如一个功能设计，单个 AI 可能会遗漏场景，但两个 Agent 互相挑战，就可能发现更多问题。

---

###### 2. Opus 和 Codex 的分歧是什么？

可以简单理解为：

###### Opus：从“原则正确”出发

它觉得：

> 如果当前窗口已经够用，就不要额外开新窗口。

这是一种偏简洁、偏理论的设计思路。

###### Codex：从“用户体验”出发

它认为：

> 如果复用当前窗口，可能会打断用户正在做的事，所以应该开新窗口隔离执行环境。

这是一种偏工程实践、偏产品体验的思路。

---

###### 3. 为什么 Codex 的观点更有说服力？

因为 Agent 执行任务时，不只是“能不能完成”，还要考虑：

- 会不会影响用户当前页面？
- 会不会破坏已有登录状态？
- 会不会干扰正在运行的流程？
- 出错后是否容易恢复？
- 是否方便调试和隔离？

所以在 `BrowserContext` 这类设计里，**隔离性** 往往比“少开一个窗口”更重要。

---

###### 4. 这体现了 Agent 的什么能力？

这件事体现出 AI Agent 不只是“写代码工具”，而是开始具备：

- 方案设计能力
- 架构讨论能力
- 互相审查能力
- 权衡取舍能力
- 接近人类工程团队的协作模式

这也是作者觉得震撼的地方。

---

##### 三、我的意见

我觉得这个案例确实很有代表性。

它说明未来 AI 编程工具的关键，不一定只是“单个模型有多强”，而是：

> 能不能让多个 Agent 像一个小型工程团队一样协作。

不过也要注意几个问题：

###### 优点

- 可以发现单个模型忽略的问题；
- 适合做架构设计、代码审查、方案比较；
- 能减少人类开发者的思考负担；
- 对复杂项目会很有价值。

###### 风险

- 很费 Token，成本不低；
- Agent 之间可能只是“语气强弱”导致一方让步；
- 最终方案仍然需要人类判断；
- 如果两个 Agent 都错了，也可能“自信地达成错误共识”。

---

##### 四、结论

这条内容的核心价值在于：

> AI Agent 正在从“执行工具”变成“协作伙伴”。

`slock` 这类工具如果能稳定地组织多个 Agent 讨论、验证和执行任务，确实会显著提升开发效率。

但它目前更适合有经验的人使用，因为你仍然需要判断：

- 它们讨论得对不对；
- 方案是否符合业务；
- 成本是否值得；
- 最终实现是否可靠。

简单说：

> 很强，但不能盲信；  
> 很有潜力，但人类仍要把关。
