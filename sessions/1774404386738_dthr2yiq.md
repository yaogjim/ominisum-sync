## 正文

[Moda](https://moda.app/?ref=blog.langchain.com) 是一个面向营销人员、创始人、销售人员和小型企业主等非设计师的 AI 原生设计平台，这些用户无需设计背景即可创建专业级别的演示文稿、社交媒体帖子、宣传册和 PDF 文件。它类似 Canva 或 Figma，但配备了类似 Cursor 的 AI 侧边栏，能直接在完全可编辑的 2D 矢量画布上构建并迭代设计。

![Moda chat](https://blog.langchain.com/content/images/2026/03/moda-chat.png)

Moda 的核心是一个基于 **Deep Agents** 构建的多智能体系统，其中， **LangSmith** 提供了可观测性层，使团队能够快速迭代并自信地发布产品。

#### 挑战：让 AI 擅长视觉设计

AI 代码生成效果很好，部分原因是 HTML 和 CSS 已经具备诸如 Flexbox 和 Grid 等布局抽象。你描述的是关系和相对大小，而不是像素坐标。

视觉设计没有等效的标准。最接近标准的是 PowerPoint 的 XML 规范，一种已有 40 年历史的格式，充斥着冗长、绝对的 XY 坐标，而 LLMs 在推理这些内容时臭名昭著地不擅长。使用 XML 的工具生成的设计看起来都和其他任何 AI 生成的演示文稿一样。

Moda 需要一个能够生成真正美观设计的系统，以及一个能够以生产级质量处理复杂、多轮、基于视觉任务的智能体架构。

#### 代理管理工具：基于 Deep Agents 构建

Moda 的人工智能系统由三个代理组成：

1. **设计代理：** 光标样式侧边栏背后的主要代理，负责画布上所有实时设计的创建与迭代
2. **Research Agent:** 检索并存储来自外部来源（例如：公司网站）的结构化内容到 Moda 内部的每用户文件系统中
3. **Brand Kit Agent:** ingests brand assets (colors, fonts, logos, brand voice) from websites, uploaded brand books, or existing slide decks, so every design feels on-brand from the start

The **Research Agent and Brand Kit Agent both run on Deep Agents**. These are the team's newest agents, which they've invested in heavily. The Design Agent runs on a custom LangGraph loop — an older implementation built before Deep Agents — and the team is actively evaluating migrating it as well.

所有三个代理共享相同的整体架构：轻量级分类步骤、主要代理循环、动态上下文加载，以及 LangSmith 中的完整追踪。

#### Context Engineering: The Details That Matter

要让设计代理生成真正优质、视觉连贯且符合品牌要求（不仅仅是技术上正确）的输出，需要大量刻意的上下文工程。

Here's what Moda figured out.

##### A Custom DSL Instead of Raw Scene Graph

One of the hardest parts of building a design agent is figuring out how to represent visual layouts in a way LLMs can reason about effectively. Raw canvas state is verbose, coordinate-heavy, and token-expensive — not a natural fit for how models think about structure and layout.

Moda developed a context representation layer that gives the agent a cleaner, more compact view of what's on the canvas, which reduces token cost and improves output quality. The specifics are proprietary, but the general principle is the same one that makes LLMs effective at web development: give the model layout abstractions it can reason about, rather than raw numerical coordinates.

"LLMs are not good at math. PowerPoint's XML spec has a bunch of XY coordinates — that's a fine representation of the data, but it's not a great way for an LLM to describe where it wants things to live." — Ravi Parikh, Co-Founder, Moda.app

Deep Agents and LangSmith were critical here. The team used LangSmith traces extensively to evaluate how different context representations affected agent behavior, iterating on what information to include, how to structure it, and where caching breakpoints made the biggest difference to cost and latency.

##### Triage → Skills → Main Loop

Every request passes through a lightweight triage node (using fast and cheap Haiku models) before reaching the main agent. The triage node classifies the output format (slide deck, PDF, LinkedIn carousel, logo, etc.) and pre-loads the relevant **skills,** which are Markdown documents containing design best practices, format guidelines, and task-specific creative instructions.

Skills are injected as human messages, with **prompt caching breakpoints** placed after the system prompt and after the skills block. This keeps the system prompt fixed and always cached while allowing dynamic context injection per request.

The main agent can also pull in additional skills mid-loop if it determines it needs them. The triage step just front-loads the high-confidence ones to avoid an unnecessary extra turn.

The design agent runs with 12–15 core tools in context at all times. An additional \~30 tools are available on demand via a `RequestToolActivation` tool the agent can call when it recognizes a specialized need, like parsing an uploaded PowerPoint file.

Each additional tool costs 50–300 tokens in the prefix, and loading new tools breaks prompt caching. But the math works out: the vast majority of requests don't need the extra tools, so keeping context lean wins overall.

"If I just look at the data, most requests do not need any additional tools activated, and there's something really nice about only having 12 to 15 tools in context." — Ravi Parikh

##### Scaling Context to Canvas Size

Not every request needs full visibility into the entire project. For smaller canvases, the agent works with a complete view of the current state. For larger projects — a 20-slide deck, for instance — Moda dynamically manages how much context the agent receives, giving it a higher-level summary and letting it pull in details as needed through tooling.

This keeps token usage bounded without sacrificing the agent's ability to make informed design decisions across complex, multi-page projects. LangSmith's cost tracking per node made it straightforward to find the right balance between context richness and efficiency.

#### UX: The Cursor Moment for Design

One of Moda's most deliberate product choices is the interaction model. Rather than a generate-and-replace flow, where AI produces a static output and hands it off, Moda's AI works directly on a fully editable 2D vector canvas. Every element the agent creates is immediately selectable, movable, resizable, and styleable by the user.

This changes the relationship between user and AI from "accept or reject" to genuine collaboration. The AI generates a solid starting point and the user refines it. Neither has to do all the work.

The Cursor-style sidebar reinforces this: it's always present, always contextually aware of what's on the canvas, and designed for iterative back-and-forth rather than one-shot generation. For non-designers especially, this removes the intimidation of the blank canvas while keeping them in control of the final result.

![](https://blog.langchain.com/content/images/2026/03/moda-ui.png)

#### Observability with LangSmith

Because all three agents are traced through LangSmith, Ravi has full visibility into every execution. He keeps it open whenever he's actively developing.

Key workflows:

- **Prompt &amp; tool iteration:** make a change, run a query, pull up the trace immediately to see exactly what the agent did and why
- **Cost tracking:** token cost broken down per node, making expensive steps easy to spot
- **Cache hit analysis:** especially important given the dynamic skill and tool loading; quickly surfaces where caching is working and where it's breaking down
- **Error diagnosis:** surfacing tool call failures and unexpected model behavior before they become user-facing issues

"If I'm iterating on the prompt, if I'm iterating on the tool set, I'm going to make a change, run a query, and then pull up that trace in LangSmith and just look at what happened... It's made us move faster." — Ravi Parikh

Moda doesn't yet run formal evals but it's on the roadmap. For now, LangSmith traces serve as the primary feedback loop for catching regressions and validating improvements.

#### Results &amp; What's Next

Moda has found strong early product-market fit with B2B companies doing enterprise sales: teams that need polished, brand-accurate pitch decks fast. The combination of the fully editable canvas and the Deep Agents-powered backend means users get a professional starting point they can actually refine, not a static output they're stuck with.

Next up: wiring up the memory primitives that are already in place, completing the Deep Agents migration for the Design Agent, and expanding the brand context system to support multi-team, multi-brand enterprise customers.

#### Moda 如何做出“可上线”的 AI 设计智能体

##### 一句话总结
Moda 想解决的不是“让 AI 画点东西”，而是让不会设计的人，也能通过 AI 快速做出专业、可编辑、符合品牌规范的设计作品。它的核心方法是：用多智能体架构 + 精细的上下文工程 + 全链路可观测性，把 AI 设计从“演示效果”做成“生产级产品”。

##### 核心问题：AI 为什么难做好设计
AI 写代码效果不错，是因为网页开发有 HTML/CSS 这类天然的结构化抽象；但视觉设计缺少类似标准。  
传统设计格式更接近 PowerPoint 的 XML，充满绝对坐标、信息冗长，不适合 LLM 理解和推理，所以很多 AI 生成的设计看起来“都差不多”，缺乏美感和品牌一致性。

##### Moda 的解决方案：三个智能体协同工作
Moda 构建了一个多智能体系统：

###### 1. 设计代理
负责在画布上实时生成和修改设计，是用户直接交互的核心代理。

###### 2. Research Agent
从官网等外部来源抓取信息，整理成结构化内容，供设计使用。

###### 3. Brand Kit Agent
提取品牌颜色、字体、Logo、语气等资产，让生成结果从一开始就更“像这个品牌”。

这三个代理共享一套基础架构：轻量分类、主循环、动态上下文加载，以及 LangSmith 全程追踪。

##### 关键能力：不是堆模型，而是做“上下文工程”
Moda 发现，设计效果好不好，关键不只是模型能力，更在于给模型什么上下文。

###### 自定义 DSL，替代原始画布数据
原始画布状态过于冗长、依赖坐标，不适合 LLM。  
因此，Moda 做了一层自定义表示方式，用更抽象、更紧凑的形式描述布局，降低 token 成本，也提升设计质量。  
本质上，就是把“机器能存储的数据结构”转换成“模型更容易思考的结构”。

###### 先分类，再加载技能
每个请求先经过一个轻量级分类步骤，识别用户要生成的是演示文稿、PDF、轮播图还是 Logo。  
然后系统只加载对应的“技能包”，其中包含该任务的设计原则、格式规范和创意指导。  
这样既提升质量，也控制成本。

###### 工具按需启用，避免上下文过重
设计代理默认只带 12–15 个核心工具，另外约 30 个工具按需激活。  
原因很现实：工具越多，token 越贵，还会破坏缓存。  
Moda 选择“默认轻量、需要时再扩展”，在大多数请求场景下更划算。

###### 按画布大小动态控制上下文
小项目可以把完整画布信息都交给模型；  
大项目（比如 20 页的 Deck）则先给高层摘要，需要时再调用工具查看细节。  
这样可以避免上下文失控，同时保持对复杂项目的处理能力。

##### 产品设计亮点：AI 不替代用户，而是与用户协作
Moda 最重要的产品选择，不是“生成什么”，而是“怎么交互”。

###### AI 直接工作在可编辑画布上
AI 生成的每个元素都能立刻被用户选中、移动、缩放、修改。  
这意味着用户不是只能“接受或拒绝”AI 输出，而是能在 AI 给出的初稿上继续精修。

###### 类似 Cursor 的侧边栏交互
AI 始终在侧边栏中待命，并感知当前画布上下文。  
这种交互方式更适合多轮迭代，尤其适合非设计师：既降低空白画布带来的压力，又保留用户对最终结果的控制权。

##### LangSmith 的价值：让团队敢于快速迭代
LangSmith 是 Moda 的可观测性底座，主要价值有四点：

###### 1. 快速看懂代理做了什么
每次修改 prompt 或工具后，都能立刻查看完整执行链路。

###### 2. 精确追踪成本
可以按节点拆解 token 成本，快速定位最贵的环节。

###### 3. 分析缓存是否生效
对于动态技能和工具加载场景，缓存命中率非常关键。

###### 4. 提前发现错误
能更早暴露工具调用失败、模型异常行为等问题，避免直接影响用户。

简单说，LangSmith 让 Moda 的代理系统从“黑盒”变成“可调试、可优化、可上线”的系统。

#### 深入浅出地解读

##### 1. 这篇文章真正想讲什么？

表面上，它在讲“Moda 如何用 Deep Agents 做 AI 设计代理”。

但本质上，它讲的是一句话：

> 想把 AI 做成真正可上线的产品，重点不是只靠一个强模型，而是要把“上下文、工具、流程、观测”都设计好。

也就是说，**难点不是让 AI 会回答，而是让 AI 在复杂真实场景里持续稳定地做对事。**

---

##### 2. 为什么“AI 做设计”比“AI 写代码”更难？

代码之所以更容易让 AI 做好，是因为它有很多“天然结构”：

- 页面有 HTML
- 布局有 Flexbox、Grid
- 关系比较清楚：谁在上、谁在下、谁占多大比例

但视觉设计不是这样。

设计底层常常是：

- 一堆绝对坐标
- 元素放在某个 x/y 位置
- 信息很碎、很长、很不直观

这就像：

- 给人看“房间布局图”，你能理解
- 但如果给你一串“桌子在 x=142, y=318，宽 220，高 80”，你就很难马上想象整体好不好看

而 LLM 恰恰不擅长处理这种**坐标密集、关系不直观**的信息。

所以 Moda 的关键突破，不是“换了个更强模型”，而是：

- **把设计画布翻译成更适合模型理解的语言**
- 让模型看到的是“布局关系”和“设计结构”，而不是一堆死坐标

这很像把机器语言转换成更高级的编程语言，让 AI 更容易推理。

---

##### 3. 为什么要用“多代理”？

Moda 把任务拆成 3 类代理，其实很合理：

- **设计代理**：负责具体生成和修改设计
- **研究代理**：负责去外部找资料、整理内容
- **品牌代理**：负责提取品牌色、字体、Logo、语气风格

这样拆的好处是：

- 每个代理职责更清晰
- 可以分别优化
- 整体更容易扩展

说白了，就是把“一个大而全的万能 AI”拆成“几个各司其职的小团队”。

这和公司分工很像：

- 有人负责创意
- 有人负责调研
- 有人负责品牌规范

AI 系统也一样，**分工越清楚，生产级落地越稳。**

---

##### 4. 文章里最值得关注的，不是模型，而是“上下文工程”

这篇文章最有价值的地方，其实是它强调了一个常被忽视的点：

##### AI 产品的质量，很大程度上取决于你给它什么上下文

Moda 做了几件很关键的事：

###### 轻量分流（Triage）
先用便宜、快的小模型判断当前任务是什么：

- 是做幻灯片？
- 是做 PDF？
- 是做轮播图？
- 是做 Logo？

这一步像前台分诊，先判断用户要什么，再决定后面叫谁来处理。

好处是：

- 节省成本
- 提高效率
- 减少主代理瞎试错

###### 技能按需加载（Skills）
不同任务配不同“设计经验包”：

- 演示文稿怎么排版
- 社媒图片怎么抓眼球
- Logo 应遵循什么原则

而且不是全部一股脑塞给模型，而是**先加载高概率需要的技能，后续再按需补充**。

这说明他们很重视一个现实问题：

> 给模型的信息不是越多越好，而是越精准越好。

###### 工具按需激活
常用工具常驻；冷门工具需要时再打开。

因为工具越多：

- prompt 越长
- token 成本越高
- 缓存越容易失效

这体现出很强的工程思维：  
**不是“功能越全越好”，而是“默认保持轻量，只在必要时变复杂”。**

---

##### 5. 为什么说它的交互方式比“生成一张图给你”更聪明？

Moda 没走那种“一键生成，给你一个最终结果”的老路，而是让 AI 直接在**可编辑的 2D 矢量画布**上工作。

这个设计非常关键。

因为很多 AI 生成工具的问题是：

- 结果看起来还行
- 但用户很难改
- 不满意就只能重来

这会让人觉得 AI 是“黑盒子”。

Moda 则把关系变成：

- AI 先给你一个靠谱起点
- 用户再自己拖动、缩放、改字、调样式
- 双方协作完成最终作品

这就像从“AI 替你干”变成“AI 帮你起步”。

对于非设计师来说，这种方式特别重要，因为他们最怕的是：

- 空白画布不知道怎么开始
- AI 生成后自己又改不动

Moda 正好解决了这两个痛点。

---

##### 6. 为什么 LangSmith 这类“可观测性工具”这么重要？

很多人做 AI 应用时，最先关注的是模型效果；但一旦进入生产环境，更重要的是：

- 为什么这次答得好？
- 为什么那次调用失败？
- 哪一步最贵？
- 缓存哪里失效了？
- 改了 prompt 后到底有没有变好？

LangSmith 在这里扮演的是“监控+调试仪表盘”的角色。

它的意义不在于“更炫”，而在于：

> 让团队知道 AI 到底是怎么工作的，而不是靠猜。

这对生产级产品特别关键。因为 AI 系统不像传统程序那样完全确定，如果没有 trace 和监控，优化会非常低效。

可以说，Moda 能快速迭代，不只是因为代理架构设计得好，也因为它能看清问题出在哪。

#### 我的意见

- 我认为 Moda 的思路是对的，尤其强在**不是迷信模型能力，而是重视系统设计**。这比单纯追求更强模型更现实，也更容易做出可商用产品。
- 文章最值得借鉴的一点是：**先把信息表示方式改对，再谈生成质量**。很多 AI 产品效果差，不是模型不行，而是喂给模型的数据结构不适合它理解。
- 它把“生成”变成“协作编辑”，这非常符合真实用户需求。尤其对非专业用户来说，能改、好改，比一次生成完美结果更重要。

- 总体来说，这篇文章给人的启发是：**做生产级 AI，不只是做一个会说话的模型，而是做一套会分工、会取舍、可观察、可迭代的系统。**

## 结构化（1）

### 2026-03-25 10:26:04

#### 主旨概括

Moda 想解决的核心问题是：让没有设计背景的人，也能借助 AI 快速做出专业、可编辑、符合品牌风格的设计作品。  
这篇文章重点介绍了 Moda 如何用 Deep Agents、LangSmith 和一套精细的上下文工程，把“能生成”提升到“能在生产环境稳定落地”。

##### 1. Moda 在做什么：面向非设计师的 AI 设计平台

- Moda 是一个 AI 原生设计平台，目标用户包括营销人员、创始人、销售人员和小企业主等非设计师。
- 用户可以用它制作专业级的：
  - 演示文稿
  - 社交媒体帖子
  - 宣传册
  - PDF 文件
- 产品形态上，它类似 `Canva` 或 `Figma`，但加入了类似 `Cursor` 的 AI 侧边栏。
- AI 不是只生成一张静态图，而是直接在“完全可编辑的 2D 矢量画布”上创建设计，用户随后还能继续调整。

##### 2. 核心挑战：AI 为什么难做好视觉设计

- AI 在代码生成上表现较好，一个重要原因是前端开发已经有 `Flexbox`、`Grid` 这类布局抽象，模型更容易理解“元素之间的关系”和“相对大小”。
- 但视觉设计缺少类似的标准抽象。
- 现成的近似标准是 `PowerPoint XML`，这是一种已有约 `40 年历史` 的格式，特点是：
  - 信息冗长
  - 依赖大量绝对 `XY` 坐标
  - 不利于 LLM 推理
- 文章指出，LLM 本身并不擅长处理这类“坐标+数值密集”的表示方式，因此很多基于 XML 工具生成的设计，看起来都很像、缺少美感和差异化。
- 所以 Moda 的目标不只是“生成设计”，而是要生成：
  - 真正美观的设计
  - 视觉上连贯的设计
  - 符合品牌要求的设计
  - 能支持复杂、多轮交互的生产级系统

##### 3. 系统架构：Moda 用了 3 个代理协作

Moda 的 AI 系统由 3 个代理组成：

###### 3.1 设计代理（Design Agent）

- 这是 AI 侧边栏背后的主代理。
- 负责画布上所有实时设计的创建与迭代。
- 当前运行在一个自定义的 `LangGraph loop` 上。
- 这是团队较早的实现，正在评估迁移到 `Deep Agents`。

###### 3.2 研究代理（Research Agent）

- 负责从外部来源检索内容，例如公司官网。
- 会把内容整理为结构化信息，存入 Moda 的“按用户划分的内部文件系统”。

###### 3.3 品牌工具包代理（Brand Kit Agent）

- 负责摄取品牌资产，包括：
  - 颜色
  - 字体
  - Logo
  - 品牌语气
- 数据来源包括：
  - 网站
  - 上传的品牌手册
  - 现有幻灯片文件
- 目的是让设计从一开始就“有品牌感”。

###### 3.4 三个代理的共同架构

尽管职责不同，这 3 个代理共享同一套总体架构：

- 轻量级分类步骤
- 主代理循环
- 动态上下文加载
- 通过 `LangSmith` 做完整追踪

##### 4. 关键方法：用“上下文工程”让 AI 更懂设计

文章强调，真正决定设计质量的，不只是模型本身，而是怎么给模型组织上下文。

###### 4.1 用自定义 DSL 代替原始场景图

- 视觉设计代理最难的一点，是如何把画布内容表示成 LLM 易于理解的形式。
- 原始画布状态的问题是：
  - 太啰嗦
  - 坐标太多
  - token 成本高
  - 不符合模型思考结构与布局的方式
- 为此，Moda 做了一层“上下文表示层”，本质上相当于一个自定义 DSL（领域特定语言）：
  - 给模型提供更紧凑、更抽象的布局表示
  - 减少 token 开销
  - 提高输出质量
- 虽然具体实现没有公开，但原则很明确：  
  **不要让模型直接处理大量数值坐标，而是给它“可推理的布局抽象”。**
- 文中联合创始人 Ravi Parikh 的观点很直接：  
  LLM 不擅长数学，PowerPoint XML 的 XY 坐标适合存数据，但不适合让 LLM 表达“元素应该放在哪里”。

###### 4.2 借助 LangSmith 持续打磨上下文表示

- 团队大量使用 `LangSmith traces` 来比较不同上下文表示方式对代理行为的影响。
- 他们持续迭代的问题包括：
  - 应该给模型哪些信息
  - 信息怎么组织
  - 缓存断点放在哪里最划算
- 这样做的收益主要体现在：
  - 成本下降
  - 延迟降低
  - 生成质量更稳定

##### 5. 请求处理流程：先分流，再加载技能，再进入主循环

Moda 的代理不是直接“接到需求就开始生成”，而是先经过一个精简的分流流程。

###### 5.1 轻量级分诊（Triage）

- 每个请求先进入一个轻量级分类节点。
- 这里使用的是更快、更便宜的 `Haiku` 模型。
- 它主要判断这次任务的输出格式，例如：
  - 幻灯片 deck
  - PDF
  - LinkedIn 轮播图
  - Logo
- 然后预加载相关“技能”（skills）。

###### 5.2 Skills 是什么

- Skills 是一些 `Markdown` 文档，里面包含：
  - 设计最佳实践
  - 各种格式的规范
  - 针对具体任务的创意指导
- 这些 skills 会作为“human messages”注入上下文。
- 团队在两个位置设置了 prompt cache 断点：
  - system prompt 之后
  - skills block 之后
- 这样做的好处是：
  - 系统提示词可以固定并持续命中缓存
  - 每次请求仍然能灵活注入动态上下文

###### 5.3 主代理可以中途再补技能

- 分诊步骤只是优先加载“高概率会用到”的技能，减少多走一步的成本。
- 如果主代理在执行过程中发现需要更多信息，也可以在中途拉取额外 skills。

##### 6. 工具管理：尽量保持上下文轻量

- 设计代理平时始终携带 `12–15` 个核心工具。
- 此外，还有大约 `30` 个额外工具按需启用。
- 如果代理识别到某种特定需求，比如解析上传的 `PowerPoint` 文件，就可以调用 `RequestToolActivation` 来激活专用工具。

###### 为什么不把所有工具都塞进去？

- 每多一个工具，前缀上下文会增加大约 `50–300 tokens`。
- 而且加载新工具会打破 prompt cache。
- 但从数据看，大多数请求根本不需要额外工具。
- 所以 Moda 的策略是：
  - 默认只保留少量高频核心工具
  - 低频工具按需激活
- 这样整体成本和效率更优。

##### 7. 大项目怎么处理：根据画布规模动态控制上下文

- 并不是每次都要把整个项目完整塞给模型。
- 对于较小画布，代理可以看到当前状态的全量信息。
- 对于较大项目，比如一个 `20 页` 的演示文稿，Moda 会动态控制上下文规模：
  - 先给模型更高层级的摘要
  - 需要细节时，再通过工具拉取
- 这样可以把 token 使用控制在合理范围内，同时不牺牲跨页面设计决策的质量。
- `LangSmith` 的节点级成本跟踪也帮助他们找到“上下文丰富度”和“效率”之间的平衡点。

##### 8. 产品交互设计：不是“生成后交付”，而是“与 AI 共创”

这是文章里很重要的一点，Moda 的价值不只在模型能力，也在交互方式。

###### 8.1 从“接受或拒绝”变成“共同编辑”

- 很多 AI 设计工具是“生成一个结果，然后用户决定要不要接受”。
- Moda 不是这种模式。
- 它让 AI 直接在可编辑的 2D 矢量画布上工作，生成出来的每个元素都可以被用户：
  - 选中
  - 移动
  - 缩放
  - 调整样式
- 这让人和 AI 的关系从“要么接受，要么拒绝”，变成真正的协作：
  - AI 负责给出高质量起点
  - 用户负责精修和把控结果

###### 8.2 类 Cursor 的侧边栏体验

- AI 侧边栏始终存在，并且能感知当前画布上下文。
- 它不是为了“一次性生成完”，而是为了支持反复迭代。
- 对非设计师来说，这种方式有两个直接好处：
  - 减少面对空白画布的压力
  - 保留最终控制权

##### 9. LangSmith 的作用：给生产级代理提供可观测性

文章把 `LangSmith` 视为 Moda 能快速迭代并稳定上线的重要基础设施。

###### 9.1 团队如何使用 LangSmith

Ravi 在开发过程中几乎一直开着 LangSmith，主要用于以下几个场景：

- `Prompt` 和工具迭代  
  改一次 prompt 或工具配置，就马上跑一次请求，再查看 trace，弄清楚代理到底做了什么、为什么这么做。
- 成本跟踪  
  可以把 token 成本拆解到每个节点，快速定位昂贵步骤。
- 缓存命中分析  
  因为 skills 和工具都是动态加载的，缓存很容易失效，LangSmith 能帮助识别缓存在哪些地方生效、哪些地方断掉了。
- 错误诊断  
  包括工具调用失败、模型行为异常等问题，可以在影响用户之前先发现。

###### 9.2 当前还没正式做 eval，但已经有反馈闭环

- Moda 目前还没有正式上线系统化的评测（evals）。
- 但这已经在路线图上。
- 现阶段，`LangSmith traces` 就是他们最主要的反馈闭环，用来：
  - 发现回归问题
  - 验证优化是否有效

##### 10. 当前效果与下一步计划

## 产品-最佳实践（1）

### 2026-03-25 10:32:18

#### 基于 Moda 案例的最佳实践：构建“AI 生成企业销售演示文稿”设计代理

下面我用一个具体实例来说明：  
**某 B2B SaaS 公司想让 AI 自动生成一套“面向客户的融资风控产品销售演示文稿（10 页 Pitch Deck）”，并且要求内容准确、视觉专业、品牌统一、可继续人工编辑。**

---

##### 一、实例背景

假设这家公司叫 **FinFlow**，它提供企业级风控与支付编排系统。用户希望输入一句话：

> “帮我生成一套给大型零售客户看的销售演示文稿，突出风控能力、部署速度和客户案例，风格专业、现代，符合我们的品牌规范。”

如果按传统 AI 生成方式，常见问题会是：

- 内容有了，但视觉排版很普通
- 每页元素是“拼出来”的，不够统一
- 品牌色、字体、Logo 使用不稳定
- 输出是静态结果，用户难以继续修改
- 多轮迭代后，系统越来越慢、越来越贵

Moda 这篇文章的价值就在于：它展示了如何把这样的任务做成一个**生产可用的设计代理系统**，而不是一次性的 demo。

---

##### 二、这个实例的推荐系统设计

针对这个“自动生成企业销售 Pitch Deck”的实例，最佳做法是把系统拆成 3 个协作代理：

###### 1. Design Agent（设计代理）
负责真正生成和修改画布上的页面内容，包括：

- 每页的版式
- 标题、副标题、图表占位
- 品牌化视觉风格
- 多轮修改后的局部调整

###### 2. Research Agent（研究代理）
负责从外部和内部资料中提取结构化信息，例如：

- 公司官网中的产品介绍
- 客户案例页面
- 定价与功能说明
- 行业数据与可信引用

###### 3. Brand Kit Agent（品牌资产代理）
负责整理品牌规范，包括：

- 主色、辅助色
- 标题字体、正文字体
- Logo 与安全留白规则
- 品牌语气与文案风格

---

##### 三、在该实例上的最佳实践

##### 1. 不要让模型直接操作原始坐标；要先抽象成“可推理的布局表示”

###### 错误做法
把 PPT/XML/场景树中的大量 `x/y/width/height` 原始数据直接喂给模型，让它决定元素布局。

这通常会导致：

- 模型难以稳定推理空间关系
- token 消耗大
- 输出虽然“技术上合法”，但视觉上不高级

###### 最佳实践
为设计代理设计一层**自定义 DSL 或布局抽象层**，例如把页面描述为：

- `hero_section`
- `two_column_comparison`
- `stat_cards`
- `customer_logo_strip`
- `quote_block`
- `cta_footer`

让模型理解的是**结构关系**，而不是原始像素坐标。

###### 在本实例中的应用
比如第 3 页“为什么选择 FinFlow”，不要让模型处理：

- 标题在 `(62, 104)`
- 三张卡片分别在 `(80, 240)`, `(360, 240)`, `(640, 240)`

而应该让模型处理：

```markdown
layout: three_feature_cards
title: 为什么选择 FinFlow
cards:
  - 极速部署
  - 智能风控
  - 全球支付覆盖
visual_tone: enterprise_modern
```

###### 经验原则
- 让模型思考“版式”和“层级”
- 让渲染引擎负责把抽象布局转换成具体坐标
- 把视觉问题从“数值定位”变成“设计结构选择”

---

##### 2. 先做轻量级任务分流，再进入主代理循环

###### 为什么重要
并不是所有请求都一样。  
“做一套销售 Deck”和“生成 LinkedIn 轮播图”需要完全不同的设计规则。

###### 最佳实践
在主代理前增加一个**triage（分流）节点**，用低成本模型先判断：

- 输出类型是什么：Pitch Deck / PDF / 海报 / 轮播图
- 当前任务优先级是什么：改内容 / 改视觉 / 套品牌 / 补素材
- 应该预加载哪些技能文档（skills）

###### 在本实例中的应用
用户说：

> “生成一套面向企业客户的销售演示文稿，突出风控和部署效率。”

分流节点可先判定：

- 格式：`slide_deck`
- 目标：`enterprise_sales`
- 所需技能：
  - 企业销售 Deck 结构最佳实践
  - B2B 视觉层级规范
  - 数据页和案例页的表达模板
  - 品牌应用规则

然后再把这些技能交给主设计代理。

###### 经验原则
- 用便宜模型做“识别”和“预加载”
- 用强模型做“生成”和“推理”
- 不要一上来就把所有工具和所有规则塞给主代理

---

##### 3. 把“设计经验”沉淀成技能文档，而不是只写在系统提示词里

###### 为什么重要
设计任务高度依赖隐性经验。  
比如销售 Deck 通常有稳定结构：

1. 封面
2. 问题定义
3. 解决方案
4. 核心能力
5. 客户案例
6. ROI/效果
7. 实施流程
8. CTA

如果这些知识只写在一个超长 system prompt 里，会很难维护。

###### 最佳实践
把这些规则拆成**skills（技能文档）**，按任务动态注入。

###### 在本实例中的技能文档示例
可以准备几类技能：

###### `enterprise_pitch_deck.md`
- 首页必须清楚表达价值主张
- 每页只保留一个主结论
- 数据页优先使用大数字 + 简短解释
- 客户案例页必须有结果而不是只有 logo

###### `brand_application.md`
- 标题使用品牌主字体
- CTA 页必须使用品牌主色
- Logo 不可置于高噪声背景
- 图标风格保持统一线性或统一填充

###### `b2b_visual_hierarchy.md`
- 一页只保留一个视觉焦点
- 主标题、副标题、正文、注释必须有稳定字号级差
- 卡片式模块应控制信息密度，避免“满版文字”

###### 经验原则
- 把“共性经验”模块化
- 技能文档按场景加载，不要全量常驻
- 这样既降低 token，又更利于迭代

---

##### 4. 默认只保留核心工具，特殊工具按需激活

###### 为什么重要
工具越多，提示词前缀越长，缓存越容易失效，成本和延迟都会上升。

###### 最佳实践
为设计代理保留一组**常驻核心工具**，例如：

- 读取当前画布结构
- 新建页面
- 添加文本框
- 添加图片占位
- 应用品牌样式
- 调整布局
- 导出文档

而像这些工具应按需激活：

- 导入 PowerPoint
- 解析品牌手册 PDF
- 抓取官网内容
- OCR 识别图片中的品牌信息

###### 在本实例中的应用
如果用户只是从零生成一套新的 Pitch Deck，通常只需要：

- 内容规划
- 页面生成
- 品牌应用
- 局部修改

这时无需提前加载：

- `parse_pptx`
- `extract_brand_from_pdf`
- `website_scraper`

只有当用户说：

> “参考我们上传的旧版路演 PPT 重新生成”

再激活相关工具。

###### 经验原则
- 常用工具常驻
- 低频高成本工具延迟加载
- 工具激活应由代理自己判断，或由 triage 节点预判

---

##### 5. 根据项目规模动态控制上下文，而不是总是把全项目塞给模型

###### 为什么重要
10 页、20 页、50 页的项目，所需上下文粒度完全不同。  
如果每次都把整个项目完整输入，成本会失控。

###### 最佳实践
根据画布规模动态提供上下文：

- 小项目：给完整上下文
- 大项目：先给全局摘要，再允许代理按需拉取细节

###### 在本实例中的应用
对于 10 页销售 Deck：

- 当前编辑第 6 页“客户案例”
- 主代理不一定要看到所有页的全部元素
- 更合理的是先给：
  - 整体 deck 摘要
  - 品牌规范摘要
  - 与客户案例相关的上下文
  - 相邻页的结构摘要

如果代理需要保证全局一致性，再调用工具获取：

- 首页视觉风格
- 数据页配色
- 结尾 CTA 页样式

###### 经验原则
- 全局信息给摘要
- 局部编辑给细节
- 通过工具做“按需放大”，而不是“全量灌入”

---

##### 6. 让 AI 在“可编辑画布”上工作，而不是只输出成品

###### 为什么重要
这是 Moda 最关键的产品思想之一。

如果 AI 输出的是一份静态 PPT 或图片，用户只能：

- 接受
- 拒绝
- 重新生成

这会让 AI 和用户形成对立关系。

###### 最佳实践
让代理直接操作一个**完全可编辑的 2D 画布**，用户可以马上：

- 选中元素
- 拖拽位置
- 修改文案
- 替换图片
- 调整字号和颜色

###### 在本实例中的应用
当 AI 生成第 4 页“核心能力”后，销售负责人可以手动把：

- “降低欺诈损失 32%” 改成最新数字
- 客户 logo 拖到更显眼的位置
- 把配色从深蓝改成品牌新版本青绿色

然后再继续对 AI 说：

> “保持这个新版风格，把后面几页也统一一下。”

###### 经验原则
- AI 提供高质量起点
- 用户保留最终控制权
- 产品形态要支持“协作式迭代”，而不是“一次性交付”

---

##### 7. 用可观测性追踪代理行为，把“感觉不好”变成“可定位问题”

###### 为什么重要
生产级代理系统的难点，不是“能不能生成”，而是：

- 为什么这次排版突然变差了？
- 为什么成本升高了？
- 为什么缓存命中下降了？
- 为什么多轮对话后工具调用异常？

###### 最佳实践
像文章中的做法一样，为每个代理建立完整 tracing，并重点监控：

- Prompt 结构
- 技能注入情况
- 工具调用链路
- 节点 token 成本
- 缓存命中率
- 失败调用和异常输出

###### 在本实例中的应用
如果第 8 页“实施流程”做得很差，可以回看 trace：

- triage 是否错误识别为普通宣传页，而不是企业销售页
- 是否漏加载了 `enterprise_pitch_deck.md`
- 是否因为中途激活过多工具，导致 prompt cache 失效
- 是否 Research Agent 提供的信息结构太差，影响页面组织

###### 经验原则
- 没有 tracing，就很难稳定优化代理
- 先追踪“发生了什么”，再讨论“如何改 prompt”
- 成本、缓存、失败率要像业务指标一样持续看

---

##### 8. 先保证“品牌一致性”，再追求“创意多样性”

###### 为什么重要
在企业销售场景里，用户最不能接受的往往不是“缺一点创意”，而是：

- 不像自家品牌
- 字体不对
- Logo 用错
- 色彩不统一
- 文案语气和公司风格不一致

###### 最佳实践
先让 Brand Kit Agent 建立稳定品牌基线，再允许 Design Agent 在这个边界内发挥。

###### 在本实例中的应用
Brand Kit Agent 应先抽取：

- 主色：`#0F5BFF`
- 辅色：`#0B1F3A`
- 强调色：`#2ED3B7`
- 标题字体：Manrope
- 正文字体：Source Sans 3
- 品牌语气：专业、可信、清晰，不夸张

之后 Design Agent 才去决定：

- 封面是大标题 + 数据背景图
- 案例页是卡片式布局还是左右对比布局
- ROI 页用图表还是数字块

###### 经验原则
- 品牌规则先定边界
- 设计生成在边界内做变化
- 企业场景下，“稳定可信”优先于“惊艳新奇”

---

##### 四、把这套最佳实践串成一个推荐流程

下面是这个实例更完整的落地流程：

```markdown
用户请求
  -> Triage 节点识别任务类型与所需技能
  -> Brand Kit Agent 抽取品牌规范
  -> Research Agent 抽取官网/资料中的结构化内容
  -> Design Agent 基于 DSL 布局抽象生成初稿
  -> 用户在可编辑画布上进行修改
  -> Design Agent 根据局部上下文继续迭代
  -> 全链路通过 tracing 观察成本、缓存与错误
```

---

##### 五、这个实例下最值得遵守的 6 条核心原则

1. **用布局抽象替代原始坐标**
   - 模型擅长结构推理，不擅长精确坐标思维。

2. **先分流，再生成**
   - 便宜模型负责分类，强模型负责高质量设计。

3. **把最佳实践写成技能文档**
   - 比堆 system prompt 更可维护、更可复用。

4. **工具按需激活**
   - 保持上下文瘦身，减少 token 和缓存失效。

5. **上下文按项目规模动态加载**
   - 大项目给摘要，小问题给细节。

6. **AI 必须工作在可编辑画布上**
   - 这样用户才会把 AI 当协作者，而不是一次性生成器。

---

##### 六、结论

如果把 Moda 的经验应用到这个“AI 自动生成企业销售演示文稿”的实例上，**最优实践并不是单纯提升模型能力**，而是系统化地做好以下几件事：

- 用适合 LLM 推理的设计表示方式
- 用多代理分工处理内容、品牌和视觉
- 用 triage 和 skills 控制上下文质量
- 用按需工具与动态上下文控制成本
- 用可编辑画布保障人机协作体验
- 用 tracing 提升迭代速度和生产稳定性

这样做出来的系统，才更有可能从“能生成”走向“真正可上线、可扩展、可维护”。
