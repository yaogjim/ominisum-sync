**Andrej Karpathy**

LLM 知识库  
最近我发现非常有用的一件事是：使用 LLMs 为我感兴趣的各个研究主题构建个人知识库。通过这种方式，我最近的 token 吞吐量中，很大一部分不再像以前那样用于操作代码，而是更多地用于处理知识（以 markdown 和图像形式存储）。最新的 LLMs 在这方面表现相当出色。因此：数据导入：  
我将源文档（文章、论文、代码库、数据集、图片等）索引到 raw/目录中，然后使用 LLM 增量地“编译”一个维基（wiki），这只是一个目录结构下的.md 文件集合。这个维基包含 raw/中所有数据的摘要、反向链接，然后将数据分类为不同概念，为每个概念撰写文章，并将它们全部关联起来。为了将网页文章转换为.md 文件，我喜欢使用 Obsidian 网页剪辑器扩展，然后我还使用快捷键将所有相关图片下载到本地，以便 LLM 能够轻松引用它们。IDE:  
我使用 Obsidian 作为 IDE 的“前端”，在这里我可以查看原始数据、已编译的知识库以及衍生的可视化内容。需要注意的是，LLM 编写和维护知识库的所有数据，我很少直接操作它。我尝试过一些 Obsidian 插件，以其他方式渲染和查看数据（例如，Marp 用于幻灯片）。问答：  
有趣的地方在于，一旦你的维基（比如我近期研究相关的维基约有 100 篇文章、40 万字）足够大，你就可以向你的 LLM 代理针对这个维基提出各种复杂问题，它会着手查找、研究答案等。我原本以为得用复杂的 RAG 系统，但 LLM 在自动维护所有文档的索引文件和简要摘要方面表现相当出色，并且在这种约小的规模下，它能相当轻松地读取所有重要的相关数据。  
而不是在文本/终端中获取答案，我喜欢让它为我渲染 markdown 文件、幻灯片（Marp 格式）或 matplotlib 图像，所有这些我之后都会在 Obsidian 中再次查看。你可以想象，根据查询，还会有许多其他的可视化输出格式。通常，我最终会将这些输出“归档”回知识库，以提升它以便进行进一步的查询。所以我的探索和查询总是在知识库中“累加”。Linting:  
我在维基上对 LLM 进行了一些“健康检查”，例如发现不一致的数据、填补缺失数据（借助网络搜索工具）、为新文章候选寻找有趣的关联等，以逐步清理维基并提升其整体数据完整性。LLMs 在提出进一步需要询问和探究的问题方面表现相当出色。额外工具:  
我发现自己正在开发额外的工具来处理数据，例如，我“vibe 编码”了一个小型且简单的搜索引擎，基于维基百科（wiki），我既直接使用它（在网页界面中），但更多时候，我希望通过命令行界面（CLI）将其交给大语言模型（LLM），作为处理更复杂查询的工具。进一步探索：  
随着仓库不断增长，自然会想要考虑合成数据生成和微调，让你的 LLM“了解”其权重中的数据，而不仅仅是依赖上下文窗口。简而言之：从给定数量的源中收集原始数据，然后由 LLM 编译成一个.md 格式的知识库，接着 LLM 通过各种命令行界面（CLI）操作该知识库以进行问答并逐步完善知识库，所有内容都可以在 Obsidian 中查看。你几乎不需要手动编写或编辑知识库，这是 LLM 的工作范畴。我认为这里有机会诞生一款令人惊叹的新产品，而不是一堆蹩脚的脚本集合。

## 通俗精炼（1）

### 2026-04-03 06:46:31

#### Karpathy 的「LLM 知识库」方法总结

##### 核心观点
Karpathy 认为，LLM 不只是写代码的工具，更适合成为“个人研究知识库”的构建器和维护者。做法是：把文章、论文、代码、图片等原始资料交给 LLM，让它自动整理、归类、总结，并逐步沉淀成一个可持续增长的知识系统。

##### 怎么做
先把原始资料统一放进 `raw/` 目录，再让 LLM 持续“编译”成一个由 `.md` 文件组成的 wiki。这个 wiki 不只是摘要集合，还会包含概念分类、文章之间的关联、反向链接，以及围绕主题形成的知识网络。

##### 工作流特点
他用 Obsidian 作为主要前端，用来查看原始资料、知识库内容和可视化结果。知识库本身主要由 LLM 写和维护，人几乎不需要手动编辑。网页内容会先转成 markdown，图片也会本地化，方便 LLM 一起理解和引用。

##### 真正的价值
当知识库积累到一定规模后，LLM 就能围绕这个库回答复杂问题，不只是“检索答案”，而是像研究助手一样主动查找、整理、推理，并输出 markdown、幻灯片、图表等更适合思考和复用的结果。

##### 为什么重要
这套方法的关键不是一次性问答，而是“知识持续累积”。每次查询得到的新总结、新图表、新报告，都可以再归档回知识库，让下一次分析变得更强，形成越来越聪明的闭环。

##### 额外能力
LLM 还可以承担“知识库巡检员”的角色，比如发现内容不一致、补齐缺失信息、挖掘潜在关联、提出下一步值得研究的问题。也就是说，它不仅管理知识，还能推动知识库自我完善。

##### 延伸想象
Karpathy 进一步设想，未来用户问一个问题时，背后可能会自动生成一整套临时 wiki：收集信息、反复校验、迭代整理，最后输出完整报告。产品机会不在零散脚本，而在一套真正可用的“LLM 原生知识操作系统”。

##### 一句话总结
这篇内容的本质是在说：LLM 的下一个高价值场景，不只是聊天或写代码，而是帮助个人和团队构建、维护、查询并持续进化自己的知识资产。

## 结构化（1）

### 2026-04-03 06:51:12

#### 文章主旨

Karpathy 认为，LLM 不只是用来写代码，也非常适合用来构建“个人知识库”：把文章、论文、代码、图片等资料整理成可持续增长的 wiki，让模型围绕这套知识进行问答、可视化和持续完善。  
他的核心观点是：与其临时查资料，不如让 LLM 先把资料“编译”为结构化知识，再在这个知识库上不断迭代探索。

##### 1. 为什么要用 LLM 搭建知识库

- 他最近把大量 token 使用从“操作代码”转向了“处理知识”，包括 markdown 文档和图片。
- 原因是最新的 LLM 在整理、总结、分类和关联知识方面已经“相当出色”。
- 目标不是一次性回答问题，而是建立一个可以反复查询、不断积累的个人研究系统。

**通俗理解：**  
以前像是“每次有问题就去翻资料”；现在更像是“先建一个自己的小型百科全书，再让 LLM 在里面工作”。

##### 2. 数据如何导入和整理

- 他会先把原始资料统一放进 `raw/` 目录。
- 这些资料包括：文章、论文、代码库、数据集、图片等。
- 然后让 LLM 增量式地把这些原始资料“编译”成一个 wiki。
- 这个 wiki 本质上是一个按目录组织的 `.md` 文件集合。
- wiki 中会包含：
  - 对原始资料的摘要
  - 反向链接
  - 按概念分类的条目
  - 每个概念的说明文章
  - 各条目之间的相互关联

**重要工具与做法：**
- 网页转 markdown：使用 **Obsidian Web Clipper** 扩展。
- 图片处理：用快捷方式把相关图片下载到本地，便于 LLM 一起引用和理解。

**例子：**  
如果研究“某个 AI 方向”，可以把论文 PDF、博客文章、相关 GitHub 仓库和配图都放进 `raw/`，再让 LLM 生成“概念词条”“论文摘要”“方法对比”“引用关系”等 markdown 页面。

##### 3. 用什么界面查看和操作

- 他把 **Obsidian** 当作整个系统的“前端 IDE”。
- 在 Obsidian 里，他可以同时查看：
  - 原始资料
  - 已整理好的知识库
  - 派生出的可视化结果
- 他强调：知识库的大部分编写和维护工作由 LLM 完成，自己很少直接手工编辑。
- 他还尝试过一些 Obsidian 插件来渲染不同形式的内容，比如：
  - **Marp**：用于生成幻灯片

**核心思想：**  
人主要负责浏览、提问和判断；LLM 负责大量具体整理与维护工作。

##### 4. 知识库建大之后，问答能力会变强

- 当 wiki 足够大时，就可以向 LLM 代理提出更复杂的问题。
- 他举的规模是：自己近期研究相关的 wiki，大约有 **100 篇文章、40 万字**。
- 在这个规模下，他原本以为需要复杂的 **RAG 系统**，但实际发现：
  - LLM 很擅长自动维护索引文件和简要摘要
  - 在这种相对较小的规模下，模型通常能较轻松地读取关键相关信息

**这段的重点是：**
- 不一定一开始就需要重型检索架构。
- 如果知识库组织得好、规模可控，LLM 直接在结构化 markdown 上工作就已经很有效。

##### 5. 输出不只是答案，还包括可视化结果

- 他不太喜欢只在文本或终端中看答案。
- 他更喜欢让 LLM 直接生成可查看的成果，例如：
  - markdown 文件
  - Marp 幻灯片
  - `matplotlib` 图像
- 这些内容之后都能在 Obsidian 中再次查看。
- 他还提到，未来完全可以根据问题生成更多不同形式的可视化输出。

**关键做法：**
- 他通常会把这些问答产物再次“归档”回知识库。
- 这样一来，每次探索和查询都不是一次性的，而是在持续给知识库“加料”。

**通俗理解：**  
你问一个问题，不只是得到一个回答，而是顺手多了一页笔记、一组图表或一份报告，之后还能继续被引用和利用。

##### 6. 如何持续“清理”和提升知识库质量

- 他会让 LLM 对整个 wiki 做一些“健康检查（linting）”。
- 主要检查和改进包括：
  - 发现数据不一致
  - 补齐缺失信息
  - 借助网络搜索补资料
  - 寻找值得新建文章的关联主题
- 他的目标是逐步清理 wiki，提高整体数据完整性。
- 他还特别提到：LLM 很擅长提出“接下来还应该问什么、查什么”的问题。

**重点理解：**  
LLM 在这里不只是“回答器”，还是“知识库维护员”和“研究助理”。

##### 7. 他还在为知识库配套开发工具

- 他提到自己“vibe coding”做了一个**小型简单搜索引擎**，专门基于这个 wiki 工作。
- 这个搜索引擎既可以自己在网页界面里直接使用，
- 但更多时候，他希望通过 **CLI（命令行界面）** 把它交给 LLM，当作复杂查询时的辅助工具。

**例子：**  
当问题变成“把过去几个月所有资料里关于某概念的分歧点、演化路径和关键实验结果整理出来”，LLM 就可以调用搜索工具，先搜再整合，而不是只靠一次性上下文理解。

##### 8. 更进一步：从知识库走向微调和产品化

- 随着知识库不断变大，他认为自然会进一步考虑：
  - 合成数据生成
  - 模型微调
- 目的在于让 LLM 不只是通过上下文窗口“临时读取”知识，
- 而是把这些知识更深地“学进权重里”。

**他的整体流程可以概括为：**
1. 从固定来源收集原始数据  
2. 由 LLM 编译成 `.md` 知识库  
3. 再让 LLM 通过 CLI 等工具操作知识库进行问答  
4. 持续补充、修正、完善知识库  
5. 最终在 Obsidian 中统一查看

- 他强调：你几乎不需要手动写或改知识库，这应该主要由 LLM 完成。
- 最后他判断：这背后可能诞生一款非常出色的新产品，而不只是“一堆蹩脚脚本”。
