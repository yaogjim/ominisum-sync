**Zach Lloyd**

### 如何为你的技能构建一个自我提升循环

最近有很多关于使用“循环”来驱动代理的讨论，我觉得这也伴随着一些疑问，比如“到底什么是循环”？

我不能代表所有使用这个术语的人发言，但我想展示一种使用 Skills 和云代理的实用方法，用于一种特别强大的循环：自我提升循环。

这是一种理念，即一个智能体可以通过外部反馈随着时间的推移提高自身技能的质量。我的例子是一个包含人工反馈步骤的循环，但如果你的目标明确且不需要人工参与，你可以使用同样的方法，配合自动评分器。

为了使问题具体化，假设这个技能负责问题分类，将待处理的问题分到几个分组中：准备实施、重复、需要信息。这同样适用于代码审查技能、bug 修复技能、事件响应技能等。

这是一个技能的初稿可能的样子：

![Image](https://pbs.twimg.com/media/HK8hQ7JWYAE-Kye?format=jpg&name=large)

[完整的问题分类处理技能](https://github.com/warpdotdev-demos/issue-triage-loop/blob/main/.agents/skills/triage-issue/SKILL.md)

你需要做的是设置以下循环：

1. 内部代理循环：这是你实际应用 Skill 的地方。对于问题分类处理，你可能会手动运行它，或者更有可能的是，你与任务跟踪器有集成，每当有新问题提交时，该集成会运行 Skill。与 Skill 的交互会被记录在某个地方：文件中、代理跟踪记录中，或者在外部系统（如 Slack 或 Github）中的交互记录中。
2. 外部代理循环 : 这是一个按计划运行的代理，用于观察内部循环对技能（Skill）的使用。对于问题分类器而言，这可能是一个云代理，它会拉取分类代理每次运行的记录。它的工作是查看内部代理的所有运行情况，并根据这些运行的性能调整其技能。由于技能本质上只是文件，这意味着它应该基于过去运行中的用户反馈生成差异来改进技能。

我将向你展示如何在实践中使用 Warp 和

[Oz](http://oz.dev/)，我们的云代理平台，但你可以通过多种方式实现。我们将使用 Github Issues 作为问题跟踪器。

[这是一个示例仓库](https://github.com/warpdotdev-demos/issue-triage-loop)包含用于跟进学习的技能和 GitHub 工作流。

GitHub 操作通过调用云代理

[Oz](https://oz.dev)Warp 的云代理平台。该云代理同步代码仓库，从 GitHub 获取问题内容，并尝试对其进行分类。关于如何设置的代码位于下方链接的仓库中。

现在当一个新问题出现时，云代理会运行内部循环分类处理技能，并添加一个标签，表明新功能请求已准备好实施。

![Image](https://pbs.twimg.com/media/HK8hGZUWkAAYQSe?format=jpg&name=large)

#### 步骤 2: 设置外层循环以实现自我提升

不过，假设一位人工审核员不同意代理的分配。作为查看代理已分配标签的人员，我将问题从“ready to implement”切换为“needs info”，并在讨论线程中添加一条评论，说明为何分类错误，例如，因为对于是否应为新功能添加设置存在歧义。

#### 如何为技能构建“自我提升循环”

##### 一、深度总结

这篇内容讲的是：**如何让一个 AI Agent 的技能在真实使用中不断变好**。

核心方法是构建两层循环：

```text
内层循环：Agent 使用技能完成任务
外层循环：另一个 Agent 根据反馈改进技能
```

文章用“GitHub Issue 分类”举例。

一个分类 Agent 负责把新问题分成几类：

- `ready to implement`：可以开始实现
- `duplicate`：重复问题
- `needs info`：信息不足

###### 具体流程

###### 1. 内层循环：执行任务

当 GitHub 创建一个新 Issue 时，GitHub Action 自动触发云端 Agent。

Agent 会：

1. 读取 Issue 内容；
2. 调用“问题分类 Skill”；
3. 给 Issue 打上对应标签。

这就是一个自动执行任务的循环。

###### 2. 人工反馈：发现错误

如果人类审核者发现分类错了，比如 Agent 标记为：

```text
ready to implement
```

但实际上问题描述不清，应改成：

```text
needs info
```

审核者就手动修改标签，并留下评论解释原因。

例如：

> 这个功能请求还不明确，因为不确定是否需要新增设置项。

###### 3. 外层循环：改进技能

外层 Agent 每天定时运行。

它会检查过去的分类记录，发现：

- Agent 原本如何分类；
- 人类后来如何修改；
- 人类为什么修改。

然后它会根据这些反馈，自动生成一个代码或文本 diff，用来更新原来的分类 Skill。

更新合并后，内层 Agent 下次再分类时，就会使用改进后的 Skill。

于是形成了一个自我提升闭环：

```text
执行任务 → 收集反馈 → 修改技能 → 再执行任务
```

---

##### 二、深入浅出解读

这篇文章其实在讲一个很实用的 AI 工程思想：

> 不要只把 Agent 当成一次性工具，而要把它设计成会学习的系统。

这里的“学习”不是重新训练大模型，而是**持续改进提示词、规则、流程和技能文件**。

可以把 Skill 理解成一份“工作手册”。

比如一名新人客服一开始有一份粗略手册：

> 遇到功能请求就标记为 ready to implement。

后来主管发现这样太粗糙，于是补充：

> 如果用户需求里存在歧义，应该先标记为 needs info，而不是直接进入开发。

这份手册变详细后，新人下次判断就更准确。

文章里的 Agent 也是类似：

- 内层 Agent 是“干活的人”；
- 人类反馈是“主管点评”；
- 外层 Agent 是“总结经验并修改手册的人”；
- Skill 是“工作手册”。

最关键的是：**经验不是停留在人脑里，而是被写回系统规则中。**

这才是真正有价值的闭环。

---

##### 三、核心价值

###### 1. 把错误变成资产

普通自动化系统出错后，只是失败。

自我提升循环中，错误会变成改进材料：

```text
错误案例 + 人类解释 = 下一版 Skill 的优化依据
```

###### 2. 不依赖模型微调

这种方法不需要训练模型参数。

它改的是：

- prompt；
- Skill 文件；
- 判断标准；
- 流程规则；
- 示例案例。

成本更低，迭代更快。

###### 3. 适合真实业务场景

它不仅适用于 Issue 分类，也适合：

- 代码审查；
- Bug 修复；
- 客服回复；
- 事故响应；
- 内容审核；
- 数据标注；
- 工单分流。

本质上，只要任务有明确反馈，就能构建类似循环。

---

##### 四、关键结构

```text
任务输入
  ↓
内层 Agent 执行 Skill
  ↓
产生结果
  ↓
人类或评分器反馈
  ↓
外层 Agent 分析反馈
  ↓
修改 Skill
  ↓
新版 Skill 再次执行
```

最重要的不是 Agent 本身，而是这个结构：

> 让系统能从过去的运行结果中改进未来表现。

---

##### 五、辩证思考

###### 正面看

这是一个很务实的 Agent 进化路线。

它不幻想 AI 一开始就完美，而是承认：

> AI 会犯错，但可以通过反馈持续变好。

这种设计比单纯追求“大模型更强”更工程化，也更可控。

尤其是在企业场景里，很多问题不是模型不会，而是规则、上下文、标准不清楚。通过 Skill 迭代，可以把隐性经验显性化，把个人判断沉淀成组织能力。

###### 但也有局限

###### 1. 反馈质量决定上限

如果人工反馈随意、不一致，外层 Agent 学到的也可能是混乱规则。

```text
坏反馈 → 坏 Skill → 更稳定地犯错
```

所以需要高质量、结构化反馈。

###### 2. 自动改 Skill 有风险

外层 Agent 自动生成 diff，看似高效，但也可能引入新问题。

比如：

- 过度拟合某个案例；
- 修改规则后影响其他场景；
- 让 Skill 越来越复杂；
- 产生相互冲突的判断标准。

因此，Skill 更新最好经过审核，而不是完全自动合并。

###### 3. 不等于真正“自主学习”

这种自我提升更像是：

> 基于反馈的流程和提示词优化。

它不是模型内部能力的根本提升，也不是人类意义上的理解增长。

所以不应过度神化“自我提升”。

---

##### 六、一句话结论

**自我提升循环的本质，是让 Agent 的每次错误都能被记录、解释，并转化为下一版 Skill 的改进。**

最理想的状态是：

```text
Agent 干活，人类纠偏，系统沉淀经验，下一次更好。
```

## 结构化（1）

### 2026-06-18 11:52:25

##### 主旨概括

文章介绍了一种用“外部反馈 + 云代理”来让技能（Skill）持续变好的方法：**自我提升循环**。核心思路是：内部代理执行任务，外部代理定期检查执行结果和反馈，并自动修改技能文件，让下次表现更好。

---

##### 1. 什么是“自我提升循环”

- 作者指出，很多人在讨论用“循环”驱动代理，但“循环”到底是什么并不总是清楚。
- 这里重点讲的是一种实用循环：**让智能体根据外部反馈持续改进自身技能质量**。
- 这个循环可以包含人工反馈；如果目标很明确，也可以用自动评分器替代人工。

**简单理解：**

> 代理先按某个技能做事，人或系统给出反馈，另一个代理根据反馈修改这个技能，于是下一次做得更好。

---

##### 2. 示例场景：问题分类技能

文章用一个具体例子说明：构建一个“问题分类器”技能。

它的任务是把 GitHub Issue 分类到几个类别中，例如：

- `ready to implement`：准备实施
- `duplicate`：重复问题
- `needs info`：需要更多信息

这个方法不只适用于问题分类，也可以用于：

- 代码审查技能
- Bug 修复技能
- 事件响应技能
- 其他需要持续改进的代理任务

---

##### 3. 整体结构：内外两个循环

作者将系统分成两个循环：

###### 内部代理循环

- 负责实际执行任务。
- 例如：当 GitHub 上创建一个新 Issue 时，代理读取 Issue 内容，并根据技能给它打标签。
- 它使用当前版本的 Skill 来完成分类。

###### 外部代理循环

- 负责观察内部代理的表现。
- 它会定期运行，比如每天一次。
- 它查看内部代理过去的运行记录、人工修改、评论反馈等信息。
- 然后根据这些反馈生成代码差异，也就是修改 Skill 文件。

**关键点：**

> Skill 本质上只是文件，因此外部代理可以像修改代码一样修改 Skill，让它逐步进化。

---

##### 4. 步骤一：设置内部代理循环

文章中使用 GitHub Actions 和云代理平台 Oz/Warp 作为实现方式。

内部循环的流程是：

1. 用户创建一个新的 GitHub Issue。
2. GitHub Actions 被触发。
3. Action 调用云代理 OzWarp。
4. 云代理同步代码仓库，读取 Issue 内容。
5. 代理运行“问题分类处理技能”。
6. 代理给 Issue 添加分类标签。

例如：

- 一个新功能请求被创建。
- 代理判断它已经足够清楚。
- 于是添加标签：`ready to implement`。

---

##### 5. 步骤二：设置外部循环实现自我提升

接下来，如果人工审核员发现代理分类错误，就可以提供反馈。

文章中的例子是：

- 代理把某个 Issue 标成了 `ready to implement`。
- 人工审核员认为这个判断不对。
- 审核员把标签改成 `needs info`。
- 并在评论中说明原因：比如“这个功能是否需要新增设置还不明确”。

外部循环代理每天运行时，会发现：

- 原标签被人工修改了；
- 评论中给出了修改原因；
- 这说明当前分类技能存在不足。

---

##### 6. 外部代理如何改进技能

外部代理由编码代理运行，因此它不仅能读取反馈，还能修改技能文件。

它会根据人工反馈生成一个 diff，用来更新“问题分类处理技能”。

例如，它可能会在技能说明中补充规则：

> 如果一个功能请求涉及配置项、设置开关或用户行为变化，但 Issue 中没有明确说明预期行为，则应标记为 `needs info`，而不是 `ready to implement`。

当这个 diff 被合并后：

- 新版 Skill 会进入代码仓库；
- 内部代理下次运行时会使用更新后的 Skill；
- 分类准确率理论上会提高。

---

##### 7. 文章核心价值

这套方法的关键价值在于：

- 不只是让代理执行任务；
- 而是让代理能从真实反馈中学习；
- Skill 可以像代码一样被版本管理、审查和迭代；
- 人工反馈会转化为明确的技能改进；
- 系统随着使用次数增加，表现会越来越好。

---

##### 总结

文章展示了一个实用的“自我提升循环”模式：**内部代理负责完成任务，外部代理负责根据反馈改进技能**。在 GitHub Issue 分类案例中，人工修改标签和评论会成为训练信号，外部代理据此更新 Skill 文件，使分类代理在未来更准确。
