## 通俗精炼（1）

### 2026-05-03 02:27:34

#### Claude Code 文档到底该长还是短？

##### 核心观点

作者提出一个“反共识”观点：  
**Claude Code 中的 `Skill.md` 和 `Claude.md` 文档，不一定越短越好；在复杂任务中，写得更长、更完整，反而可能效果更好。**

这与 Anthropic 官方建议“文档尽量控制在 100～200 行以内”的说法相反。

##### 作者的主要理由

###### 1. 复杂任务中，短文档可能不够用

作者认为，如果把规则拆到子文档、引用文档里，采用“渐进式披露”的方式，任务一旦复杂、执行链路变长，Claude Code 可能根本不会读取这些补充内容。

因此，关键规则如果不直接写清楚，容易在执行中被忽略。

###### 2. Anthropic 自己的系统提示词也很长

作者指出，无论是 Claude Code、Claude Design，还是 Claude 网页版，它们背后的 System Prompt 都并不短。

如果“越短越好”真是绝对最佳实践，Anthropic 自己就不会使用很长的系统提示词。

###### 3. 官方建议短文档，是从平台协作角度出发

作者认为，Anthropic 希望开发者把文档写短，更多是为了：

- 多个 skill 之间更容易协作
- 减少不同指令之间的冲突
- 给官方 System Prompt 留出更多发挥空间

但对于个人使用者来说，更重要的是：  
**让自己的规则和 skill 发挥最大效果。**

##### 作者的结论

只要模型能力足够强、指令遵循能力足够好，并且用户知道自己在写什么，`Skill.md` 和 `Claude.md` 完全可以写长。

重点不是“为了长而长”，而是：  
**在必要情况下，把要求充分写清楚，不必盲目遵守官方的短文档建议。**

##### 评论区的补充观点

###### 反对意见：长文档也有风险

有评论认为，长文档并非无脑更好，主要问题包括：

- **边际收益递减**：写到一定长度后，新增内容带来的收益变小
- **注意力稀释**：内容越长，前面重要规则的权重可能被削弱
- **规则冲突增加**：长文档中不同规则互相矛盾的概率会上升

###### 折中观点：关键是有效信息量

另一种观点认为，问题不在于长短，而在于信息是否有效。

如果内容都是真正有用的，在上下文没被挤爆之前，长文档确实可能更好。  
但 `Claude.md` 和 skill 原本也有通用性、可迁移性的设计目标，不是所有信息都适用于每个任务。

##### 一句话总结

**Claude Code 文档不应机械追求“短”，复杂场景下，把有效规则写充分可能更重要；但长文档也要避免冗余、冲突和注意力稀释。**

## 解读（1）

### 2026-05-03 08:03:55

#### 一、内容总结

这篇 X 帖子的核心观点是：

> **Claude Code / Skills 里的 `Skill.md` 和 `Claude.md` 文档，不一定要短；在某些情况下，写得更长反而效果更好。**

作者认为，Anthropic 官方常建议开发者把这些文档控制在较短范围内，比如 100～200 行以内，但他在长期使用 Claude Code 的实践中发现：

1. **复杂任务中，短文档 + 子文档策略可能失效**  
   如果把规则拆到很多子文档或引用文档里，任务执行时间一长，Claude 可能根本不会去读那些内容。

2. **Anthropic 自己的系统提示词其实很长**  
   如果“越短越好”真是绝对原则，官方自己的 System Prompt 就不会写得很长。

3. **官方建议短，是为了整体协作和通用性**  
   如果每个人都有很多 skills、很多 `claude.md`，短文档更利于系统管理、不同 skill 协作，以及官方 System Prompt 发挥作用。

4. **但对个人使用者来说，重点是让自己的规则生效**  
   如果模型足够强、上下文足够大、指令遵循能力足够好，那么把必要规则写长，并不是问题。

评论区也补充了不同观点：

- 长文档存在**边际收益递减**；
- 内容越长，注意力可能被稀释；
- 规则之间更容易冲突；
- 关键不在“长”或“短”，而在于是否都是**有效信息**。

---

#### 二、深入浅出解读

##### 1. 这不是“长文档一定好”，而是“有效信息越充分越好”

作者真正想反驳的不是“短文档没用”，而是反对一种机械理解：

> 官方说短，所以我必须短。

但实际使用中，如果你的任务很复杂，比如：

- 大型代码重构；
- 多步骤自动化开发；
- 固定架构规范；
- 严格代码风格；
- 特定业务约束；
- 多文件协作规则；

那只写几十行，很可能说不清楚。

这时候，文档写长一点，把规则讲明白，确实可能更有效。

---

##### 2. 为什么官方建议写短？

官方建议短，不代表短永远更强。

它更多是从“通用最佳实践”出发：

- 降低上下文消耗；
- 减少规则冲突；
- 方便迁移；
- 方便多个 skill 组合使用；
- 避免用户塞入大量低质量说明；
- 保证模型主要遵循系统级规则。

也就是说，官方面对的是大多数用户，而不是深度玩家。

所以它会给一个更安全、更保守的建议。

---

##### 3. 为什么长文档有时更有效？

因为 AI 不是人类员工，不会天然理解你的项目背景。

如果你不告诉它：

- 项目结构是什么；
- 哪些文件不能改；
- 哪些代码风格必须遵守；
- 先读哪些文件；
- 遇到不确定情况怎么处理；
- 提交代码前要做哪些检查；

它就只能靠猜。

而复杂任务最怕“猜”。

所以，把重要规则写清楚，比盲目追求短更重要。

---

##### 4. 但长文档也有风险

长文档的问题主要有三个：

###### ① 注意力稀释

文档越长，模型不一定能同等重视每一条规则。

前面写了 100 条，后面又写 100 条，关键指令可能被淹没。

###### ② 规则冲突

比如前面说：

> 不要自动修改配置文件。

后面又说：

> 遇到构建问题时可以调整配置。

这就可能冲突。

模型不知道该听哪条。

###### ③ 维护成本高

文档越长，越容易过期。

项目改了，规则没改，AI 反而会被旧规则误导。

---

#### 三、我的意见

我的看法是：

> **不要迷信“短”，也不要迷信“长”。真正重要的是：高密度、无冲突、可执行。**

更实用的原则是：

##### 1. 核心规则放前面

最重要的规则必须写在最前面，例如：

- 不要擅自删除文件；
- 修改前先阅读相关文件；
- 不确定时先询问；
- 代码必须通过测试；
- 保持现有架构风格。

这样即使文档很长，模型也更容易抓住重点。

---

##### 2. 长文档可以写，但要分层

推荐结构：

```markdown
# 最高优先级规则
必须遵守的底线。

# 项目背景
项目是做什么的，核心模块是什么。

# 开发流程
每次任务应该怎么做。

# 代码规范
命名、结构、测试、错误处理规则。

# 禁止事项
哪些行为绝对不能做。

# 示例
好的示例和坏的示例。
```

长可以，但不能乱。

---

##### 3. 不要堆废话

下面这种内容价值很低：

> 请认真工作。  
> 请写高质量代码。  
> 请像专家一样思考。  
> 请不要犯错。

这些话太抽象，模型很难执行。

更好的写法是：

> 修改代码后必须运行对应测试。  
> 如果测试失败，先分析失败原因，不要直接跳过。  
> 不允许为了通过测试删除测试用例。

这才是可执行规则。

---

##### 4. 定期让 AI 帮你审查文档

作者回复里提到一点很有价值：

> 可以让 Claude Code 来审查和精简。

这很实用。

你可以让 AI 检查：

- 是否有重复规则；
- 是否有冲突规则；
- 哪些内容可以合并；
- 哪些规则不够具体；
- 哪些内容已经过期。

---

#### 四、结论

这篇帖子的价值在于提醒大家：

> **AI 指令文档不是越短越好，而是越有效越好。**

如果任务简单，短文档足够。

如果任务复杂，长文档反而必要。

但前提是：

- 内容真实有用；
- 结构清晰；
- 没有冲突；
- 规则具体可执行；
- 核心要求放在前面。

一句话总结：

> **别为了短而短，也别为了长而长。让 Claude 真正知道该怎么做，才是关键。**
