## 分析要点

- **核心高价值点**：利用文件系统原生 copy-on-write 能力，可在大目录上近乎瞬时创建隔离工作区，适合多任务并行开发场景。
- **留存建议**：短期参考后可保留，适合在需要快速创建隔离工作区时再深入评估（介绍了一个利用文件系统写时复制能力快速创建开发工作区的实验性工具，对开发效率工具选型有参考价值）

**知识要点**

- Rift 通过 btrfs snapshots、Linux reflinks 和 macOS APFS clonefile 实现快速工作区复制
- 默认创建工作区时会过滤 node\_modules、target、dist、build 等可再生成的大型目录
- 工具支持 CLI 和 Bun/Node FFI API，但 Windows 尚未实现工作区创建
- 项目目前明确标注为 experimental，接口和行为可能随时变化

**行动项**

- 如当前有多分支并行开发痛点，可在非关键项目上试用 rift create 与 git worktrees 的差异
- 在使用前确认本机文件系统是否支持 btrfs、APFS clonefile 或 Linux reflink
- 暂不用于生产关键流程，等待项目稳定性、Windows 支持和更多 benchmark 数据完善

> **Warning: Experimental repository**
>
> This repository is experimental and is not ready for use. We are exploring a variety of ideas here, and behavior, interfaces, and implementation details may change without notice.

rift: better alternative to git worktrees

- copy on write (saves space)
- instant (&lt; 0.1s on 10gb folder)
- fast cli
- use as FFI lib with bun or node

mac and linux with btrfs or native reflinks for now more support soon

#### Install

```
npm install -g rift-snapshot
# or
bun add -g rift-snapshot
```

Release archives are available from [GitHub Releases](https://github.com/anomalyco/rift/releases/latest).

#### Platforms

Platform Backend Behavior

Linux x64 Writable btrfs snapshots `rift init` converts an ordinary directory into a btrfs subvolume.

Linux x64 Native per-file reflinks `rift init` verifies reflink support and registers the directory.

macOS arm64 / x64 APFS `clonefile` `rift init` registers the source directory.

Windows x64 None The package is published; workspace creation is not implemented.

#### CLI

##### Initialize

```
cd ~/code/app
rift init
```

`rift init` selects an existing Rift root above the current directory, or the nearest Git root when no Rift root exists. Use `--here` to initialize exactly the selected directory.

On Linux, first initialization of an ordinary btrfs directory performs a reflink import into a new btrfs subvolume and swaps it into the same path. On other Linux filesystems, initialization verifies native reflink support and registers the directory in place. This includes XFS and other filesystems when their `FICLONE` support succeeds. If the selected root is registered already, no conversion occurs. If its `.rift` marker is missing, `rift init` restores it and completes any required setup.

##### Create

```
rift create
rift create --name parser-fix
rift create --into /fast/rifts
rift create --copy-all
rift create --no-hooks
```

`rift create` searches upward for `.rift`, copies that managed workspace, records the immediate parent, and prints the new workspace path to stdout.

By default, creation omits heavyweight regenerable dependency and build artifacts such as `node_modules`, `target`, virtualenvs, framework caches, `dist`, `build`, and `coverage`. Manifests and lockfiles are preserved. Use `--copy-all` to keep the previous exact-copy behavior.

On btrfs, exact copies use writable subvolume snapshots and filtered copies use a reflink import into a new subvolume. On other reflink-capable Linux filesystems, Rift reflink-clones the selected directory tree. On macOS, exact copies use APFS `clonefile`, and filtered copies clone included entries.

When the workspace is a Git repository, the new workspace has detached `HEAD` and retains index and working-tree state.

If the source contains `.rift.toml`, `rift create` runs configured postcreate hooks after the workspace is created, registered, and prepared. Use `--no-hooks` to skip them.

```
version = 1

[[hooks.postcreate]]
run = "pnpm install --frozen-lockfile"

[[hooks.postcreate]]
run = "pnpm run codegen"
```

Postcreate commands run in the new workspace root. If a hook fails, the workspace remains registered and `rift create` exits with an error.

```
rift list
rift ancestors
```

`list` prints direct active child workspaces. `ancestors` prints parent workspaces, nearest first.

Removing a created rift moves its active subtree into adjacent `.trash` storage. `rift gc` deletes that storage later.

Removing a source root requires `-f` in the CLI. The source directory remains on disk. Its `.rift` marker is removed. Existing registered descendants are moved into trash. Missing descendants are removed from the registry.

##### Shell Integration

```
eval "$(rift shell-init zsh)" # or bash
```

```
rift shell-init nushell | save -f (($nu.user-autoload-dirs | first) | path join "rift.nu")
```

The shell wrapper changes directory after `init` conversion, `create`, or removal of the current created rift.

#### Storage

Each managed workspace has a `.rift` marker containing its identifier. An SQLite registry stores paths, parent identifiers, and trash entries.

Default created-workspace storage is adjacent to the registered source root:

```
~/code/app/                         source workspace
~/code/.rifts/app/parser-fix/       created workspace
~/code/.rifts/app/.trash/            removed workspace storage
```

#### JavaScript API

The package selects a Bun or Node FFI binding through conditional exports.

```
import { create, list, remove, gc } from "rift-snapshot";

const workspace = create({ from: process.cwd(), name: "schema-work" });
console.log(list({ of: process.cwd() }));
remove({ at: workspace });
gc();
```

##### Node.js

The Node binding requires the experimental FFI API in Node.js 26.1 or later:

```
node --experimental-ffi app.mjs
```

With Node's permission model, also pass `--allow-ffi`.

##### Functions

```
init(options?: { at?: string; database?: string }): null
create(options?: { from?: string; name?: string; into?: string; copyAll?: boolean; hooks?: boolean; database?: string }): string
remove(options?: { at?: string; all?: false; database?: string }): void
remove(options: { at?: string; all: true; database?: string }): string[]
list(options?: { of?: string; database?: string }): string[]
ancestors(options?: { of?: string; database?: string }): string[]
gc(options?: { database?: string }): string[]
```

The JavaScript `init` function initializes exactly `at`; Git-root selection and `--here` are CLI behavior.

Operation failures throw `RiftError` with a `code` and, when relevant, `path`.

#### Development

```
cargo test --workspace --locked
./scripts/install.sh
```

`scripts/install.sh` installs an optimized CLI binary to `${CARGO_HOME:-$HOME/.cargo}/bin/rift`.

##### Benchmark

Benchmark a single real `rift create` operation against a directory:

```
cargo bench --bench create -- /path/to/linux
```

The benchmark initializes the supplied directory before timing, times only creation of the new rift, and then removes the created workspace outside the measured interval. On first use, initialization of an ordinary Linux btrfs directory converts it into a subvolume before measurement. The benchmark uses the production filesystem strategy, so results measure APFS cloning on macOS, btrfs snapshots on btrfs, and per-file reflinks on reflink-capable Linux filesystems.

Establish a baseline by measuring multiple independent rift creations and writing an aggregate machine-readable result file. Keep results outside the source workspace so they do not alter future measurements:

```
cargo bench --bench create -- /path/to/linux --samples 10 --output /path/to/results/baseline.json
```

The JSON result includes each timing sample and the median, minimum, and maximum elapsed time. A future experiment loop can run the same command in candidate workspaces and compare their median results to this baseline.

Compare multiple candidate `rift` code workspaces that contain this benchmark target:

```
cargo bench --bench compare -- /path/to/linux \
  --candidate /path/to/rift-baseline \
  --candidate /path/to/rift-candidate-a \
  --candidate /path/to/rift-candidate-b \
  --samples 10 \
  --output /path/to/results/create-run-01
```

The comparison runner invokes each candidate's optimized `create` benchmark against the same workload, writes `candidate-01.json`, `candidate-02.json`, and so on, then writes `summary.json` with candidates ranked by median creation time. Include the unchanged workspace as one candidate when you need a baseline in the ranking.

#### anomalyco/rift 深度总结

##### 1. 核心定位

**rift**是一个实验性工具，目标是做一个 “更快、更省空间的 Git worktree 替代品”。

它通过文件系统的**写时复制 Copy-on-Write**能力，快速创建项目副本：

- 大目录也能瞬间复制：宣称**10GB 文件夹 < 0.1 秒**
- 节省磁盘空间：相同文件不重复占用
- 支持 CLI，也支持 Bun / Node FFI 调用
- 当前主要支持：
  - Linux：btrfs snapshot、reflink
  - macOS：APFS clonefile
  - Windows：包已发布，但尚未实现 workspace 创建

> 但项目明确标注：**Experimental，不适合生产使用。**

---

##### 2. 它解决什么问题？

开发中常见需求：

> 我想快速基于当前项目状态开一个新工作区，做实验、修 bug、跑分支，但不想重新 clone，也不想复制巨大目录。

传统方案的问题：

| 方案 | 问题 |
|---|---|
| `cp -r` | 慢，占空间 |
| `git clone` | 慢，依赖 Git 状态 |
| `git worktree` | 轻量，但不完整复制当前工作区状态 |
| 手动拷贝 | 容易混乱 |

rift 的思路是：

> 利用文件系统底层能力，把一个项目 “像拍快照一样” 复制出来。

---

##### 3. 关键机制

##### 初始化

```bash
rift init
```

作用：

- 找到当前目录上方的 Rift 根目录
- 如果没有，则找最近的 Git 根目录
- 注册该目录为 Rift 管理工作区
- 写入`.rift`标记
- 在 SQLite 中记录路径、父子关系、回收站信息

Linux btrfs 下，首次初始化可能会把普通目录转换成 btrfs subvolume。

- 从当前 Rift 工作区创建一个新 workspace
- 输出新路径
- 新 workspace 保留 Git 当前状态
- 如果是 Git 仓库，新副本会处于 detached HEAD
- 默认跳过可再生成的大目录：

例如：

```text

target
virtualenvs
dist
build
coverage
framework caches
```

但保留：

```text

```

```bash

```

#### 深入浅出解读

##### 可以把 rift 理解成什么？

它像是：

> 给项目目录拍一张 “可编辑快照”。

不是普通截图，而是一个真的目录。

你可以进入新目录：

- 改代码
- 装依赖
- 跑测试
- 做实验
- 切分支

但底层相同文件仍然共享存储。

只有当你修改某个文件时，文件系统才真正复制那部分数据。

这就是**写时复制**。

---

##### 举个例子

假设项目有 10GB：

```text
app/
  src/
  node_modules/
  target/
  dist/
```

普通复制：

```bash
cp -r app app-copy
```

可能：

- 花几十秒甚至几分钟
- 多占 10GB

rift：

```bash
rift create --name test-fix
```

可能：

- 几乎瞬间完成
- 只多占极少空间
- 默认跳过`node_modules`、`target`等可再生成目录

然后你可以在新目录中独立开发。

---

##### 它和 git worktree 的差别

`git worktree`更像：

> 从 Git 仓库开一个新分支工作目录。

rift 更像：

> 把当前整个项目目录状态快速复制一份。

区别在于：

| 对比 | git worktree | rift |
|---|---|---|
| 依赖 Git | 强依赖 | 不强依赖 |
| 保留未提交文件 | 有限制 | 更接近完整保留 |
| 复制项目状态 | 不完全 | 更完整 |
| 速度 | 快 | 取决于文件系统，可能极快 |
| 空间效率 | 高 | 高 |
| 成熟度 | 高 | 实验性 |

---

#### 辩证思考

##### 优点

1. **非常适合实验性开发**
   - 开新环境成本极低
   - 可以快速试错

2. **比复制目录更聪明**
   - 快
   - 省空间
   - 可管理父子关系

3. **比 git worktree 更贴近 “当前现场”**
   - 未提交状态
   - 工作区文件
   - 部分环境文件  
   都可以被保留下来

4. **适合大项目**
   - Rust、Node、Monorepo、大型构建产物项目收益明显

---

##### 风险

1. **项目仍处实验阶段**
   - 接口可能变化
   - 行为可能变化
   - 不适合关键生产流程

2. **强依赖文件系统**
   - btrfs、APFS、reflink 支持程度不同
   - 跨平台一致性不足
   - Windows 暂不可用

3. **抽象成本较高**
   - 用户需要理解：
     - subvolume
     - reflink
     - clonefile
     - registry
     - trash
   - 出问题时排查门槛高于 Git worktree

4. **可能隐藏磁盘占用风险**
   - 写时复制初期省空间
   - 但大量修改后仍会真实占用空间
   - 用户可能误以为 “永远不占空间”

---

#### 结论

**rift 是一个很有潜力的开发工作区快照工具。**

它的价值不是替代 Git，而是补足 Git 在 “快速复制当前工作现场” 上的不足。

适合：

- 本地实验
- 快速开临时工作区
- 大项目并行开发
- CI /benchmark/sandbox 场景

暂不适合：

- 生产核心流程
- 团队强依赖工作流
- Windows 用户
- 对稳定性要求很高的环境

一句话：

> rift 像是给项目目录装上了 “瞬间分身术”，但目前还属于早期实验品，值得关注，不宜重仓依赖。

#### Rift 项目精炼总结

Rift 是一个实验性的 Git Worktree 替代方案，通过 **写时复制（Copy-on-Write）** 快速创建独立工作区，既节省磁盘空间，又能在 **10GB 目录上实现低于 0.1 秒的创建速度**。目前项目尚未达到生产可用状态，行为、接口和实现都可能随时变化。

##### 1. 核心能力与安装

Rift 可作为命令行工具使用，也能通过 Bun 或 Node.js 的 FFI 接口集成到 JavaScript 项目中。

```bash
npm install -g rift-snapshot
# 或
bun add -g rift-snapshot
```

主要特点：

- 使用写时复制，避免完整复制大型项目目录。
- 支持快速创建多个相互独立、可写的工作区。
- 保留 Git 的索引和工作区状态。
- 支持 macOS 和部分 Linux 文件系统。
- Windows 虽已发布安装包，但尚未实现工作区创建功能。

##### 2. 平台与文件系统支持

| 平台 | 后端技术 | 行为 |
|---|---|---|
| Linux x64 + Btrfs | 可写子卷快照 | 首次初始化时，将普通目录转换为 Btrfs 子卷 |
| Linux x64 + 支持 Reflink 的文件系统 | 单文件 Reflink | 验证 `FICLONE` 支持后，原地注册目录；包括 XFS 等文件系统 |
| macOS arm64 / x64 | APFS `clonefile` | 直接注册源目录，并通过 APFS 克隆创建工作区 |
| Windows x64 | 暂无 | 包可以安装，但不能创建工作区 |

##### 3. 初始化工作区

在项目目录中执行：

```bash
cd ~/code/app
rift init
```

`rift init` 的选择规则：

1. 优先寻找当前目录上层已有的 Rift 根目录。
2. 如果没有，则选择最近的 Git 根目录。
3. 使用 `--here` 可强制初始化当前指定目录。

不同文件系统上的处理方式：

- **Btrfs**：首次初始化普通目录时，会通过 Reflink 导入创建新子卷，再替换回原路径。
- **其他 Linux 文件系统**：验证原生 Reflink 支持后，原地注册目录。
- **已注册目录**：不会重复转换。
- 如果 `.rift` 标记丢失，Rift 会自动恢复并完成必要配置。

##### 4. 创建新工作区

常用命令：

```bash
rift create
rift create --name parser-fix
rift create --into /fast/rifts
rift create --copy-all
rift create --no-hooks
```

创建流程与规则：

- Rift 向上查找 `.rift` 标记，复制对应的受管工作区。
- 记录新工作区与直接父工作区的关系。
- 创建完成后，将新工作区路径输出到标准输出。
- `--name` 指定名称，`--into` 指定存储目录。

默认情况下，为提升速度并节省空间，Rift 会忽略可重新生成的大型依赖和构建产物，例如：

- `node_modules`
- `target`
- Python 虚拟环境
- 框架缓存
- `dist`
- `build`
- `coverage`

但会保留项目清单和锁文件。若需要完全复制，可使用：

```bash
rift create --copy-all
```

不同平台的创建方式：

- **Btrfs 完整复制**：创建可写子卷快照。
- **Btrfs 过滤复制**：通过 Reflink 导入到新子卷。
- **其他支持 Reflink 的 Linux 文件系统**：逐文件进行 Reflink 克隆。
- **macOS 完整复制**：使用 APFS `clonefile`。
- **macOS 过滤复制**：只克隆被保留的文件。

如果源目录是 Git 仓库，新工作区将处于 **detached HEAD** 状态，同时保留原有的索引和未提交工作区状态。

##### 5. 创建后钩子

如果源工作区存在 `.rift.toml`，Rift 会在新工作区完成创建、注册和准备后，执行 `postcreate` 钩子。

```toml
version = 1

[[hooks.postcreate]]
run = "pnpm install --frozen-lockfile"

[[hooks.postcreate]]
run = "pnpm run codegen"
```

- 命令在新工作区根目录执行。
- 可通过 `rift create --no-hooks` 跳过钩子。
- 如果钩子失败，新工作区仍会保留并处于已注册状态，但 `rift create` 会以错误结束。

##### 6. 查询、删除与垃圾回收

相关命令包括：

```bash
rift list
rift ancestors
rift gc
```

- `rift list`：列出当前工作区直接创建的、仍处于活动状态的子工作区。
- `rift ancestors`：按距离从近到远列出父工作区。
- 删除一个创建出的 Rift 工作区时，其活动子树会移动到相邻的 `.trash` 目录。
- `rift gc`：真正删除 `.trash` 中的内容。
- 删除源根目录的注册信息需要使用 `-f`：
  - 源目录本身不会从磁盘删除。
  - `.rift` 标记会被移除。
  - 已注册的后代工作区会被移入回收区。
  - 已经不存在的后代路径会从注册表中清除。

##### 7. Shell 集成

Zsh 或 Bash：

```bash
eval "$(rift shell-init zsh)"
# 或
eval "$(rift shell-init bash)"
```

Nushell：

```nu
rift shell-init nushell |
  save -f (($nu.user-autoload-dirs | first) | path join "rift.nu")
```

Shell 包装器可以在以下操作后自动切换目录：

- 初始化过程中目录被转换后；
- 创建新工作区后；
- 删除当前创建出的 Rift 工作区后。

##### 8. 存储与注册机制

每个受管工作区都包含一个 `.rift` 标记，其中保存工作区标识符。Rift 使用 SQLite 数据库存储：

- 工作区路径；
- 父工作区标识；
- 回收区记录。

默认情况下，新工作区与源工作区相邻存放。例如：

```text
~/code/app/                         # 源工作区
~/code/.rifts/app/parser-fix/       # 创建出的工作区
~/code/.rifts/app/.trash/           # 已移除工作区的暂存位置
```

##### 9. JavaScript API

`rift-snapshot` 会通过条件导出，自动选择 Bun 或 Node.js 的 FFI 绑定。

```javascript
import { create, list, remove, gc } from "rift-snapshot";

const workspace = create({
  from: process.cwd(),
  name: "schema-work",
});

console.log(list({ of: process.cwd() }));

remove({ at: workspace });
gc();
```

主要 API：

- `init()`：初始化目录。
- `create()`：创建工作区并返回路径。
- `remove()`：移除单个或全部工作区。
- `list()`：列出直接子工作区。
- `ancestors()`：列出祖先工作区。
- `gc()`：清理回收区。

需要注意：

- JavaScript API 的 `init({ at })` 会精确初始化 `at` 指定的目录。
- CLI 中的 Git 根目录自动选择和 `--here` 逻辑不适用于该 API。
- 操作失败会抛出 `RiftError`，其中包含错误代码，必要时也会包含相关路径。

###### Node.js 限制

Node.js 绑定要求 **Node.js 26.1 或更高版本**，并启用实验性 FFI：

```bash
node --experimental-ffi app.mjs
```

如果启用了 Node.js 权限模型，还需要添加：

```bash
--allow-ffi
```

#### Rift：用写时复制快速创建完整开发工作区

Rift 是一个实验性的 Git worktree 替代方案，利用文件系统“写时复制”（CoW）克隆整个项目目录：新工作区初始共享源文件的数据块，仅在修改时额外占用空间。项目宣称，即使是 10GB 目录，创建也可低于 0.1 秒，适合快速生成隔离且保留现场的开发环境，但目前接口和实现仍可能随时变化。

##### 克隆的不只是 Git 分支，而是完整工作状态

执行 `rift init` 注册项目后，可用 `rift create` 创建子工作区。若源目录是 Git 仓库，新副本会处于 detached HEAD，同时保留索引和工作区状态，包括尚未提交的修改。

默认会排除 `node_modules`、`target`、虚拟环境、构建产物和缓存等可再生的大文件，但保留清单及锁文件；`--copy-all` 可创建完整副本。项目还可配置 `postcreate` 钩子，在创建后自动安装依赖或生成代码，失败时工作区仍会保留并登记。

##### 性能依赖底层文件系统能力

Rift 会按平台选择不同机制：

- Linux btrfs：使用可写子卷快照；首次初始化普通目录时会转换为子卷。
- 其他 Linux 文件系统：要求支持原生 reflink，如具备 `FICLONE` 能力的 XFS。
- macOS：使用 APFS `clonefile`。
- Windows：虽然已发布包，但尚不能创建工作区。

因此，“瞬时、节省空间”并非普通文件复制优化，而是建立在文件系统原生克隆能力之上。

##### 从命令行扩展到自动化工作流

Rift 提供创建、列举、追溯父工作区、移除和垃圾回收等命令，并用 `.rift` 标记与 SQLite 记录父子关系。删除时先移入相邻的 `.trash`，之后再由 `gc` 清理。

它也可通过 Bun 或 Node 的 FFI 作为 JavaScript 库调用，便于集成到开发工具和自动化流程；不过 Node 端要求 26.1 及以上版本并开启实验性 FFI。整体价值在于快速复制包含未提交状态的完整开发现场，但现阶段更适合试验，不宜直接用于关键生产流程。
