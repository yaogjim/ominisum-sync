> **摘要**：文章比较了将Postgres封装为类文件系统接口与直接提供SQL技能加本地Bash环境两种Agent数据访问方式。结论是文件系统抽象虽熟悉，但每次读取都引入数据库往返；让Agent先查询并落地本地文件，通常更简单、可组合且更快。

## 分析要点

- **核心高价值点**：判断Agent数据接口优劣的关键不是接口形状是否像文件系统，而是数据是否能被本地化后用真实工具链组合处理。
- **留存建议**：短期参考后可归档，适合作为Agent工具接口设计的案例材料（提供了数据库文件系统抽象与SQL技能方案的架构权衡，对Agent工具设计有参考价值）

**知识要点**

- 类文件系统数据库抽象会把ls、cat、grep等操作转译为数据库查询，可能导致大量往返开销。
- SQL技能方案通过一次查询将候选数据写入本地文件，再利用真实Bash工具链完成分析，降低抽象维护成本。
- 熟悉的接口对Agent有帮助，但不足以替代底层数据访问局部性和执行环境的效率。
- 该权衡可迁移到Chroma、Mongo、BigQuery、ClickHouse等不同存储系统。

**行动项**

- 在设计Agent数据访问工具时，优先评估是否可以用原生查询语言提取数据切片并本地处理。
- 避免为Agent过早构建复杂的类文件系统抽象，除非有明确评测证明收益超过维护成本。
- 为Agent编写数据访问技能提示，明确何时用SQL聚合、何时导出候选行到本地文件分析。
- 针对实际任务建立小型eval，比较抽象接口与原生查询加本地工具链的准确率、延迟和读取次数。

### 为你的代理模拟一个文件系统：PostgresFS

为你的代理模拟文件系统：为什么 PostgresFS 输给了一项技能

Co written by

[@SufjanFana](https://x.com/@SufjanFana)

Working with agent harnesses, it is hard not to be impressed by the power that Bash and filesystems lend to the modern agent. Bash and file operations sit at the core of the tool-calling workflows harnesses use every day. The strength of that foundation has even led some people to say,

[“Bash might be all you need.”](https://vercel.com/changelog/introducing-bash-tool-for-filesystem-based-context-retrieval)

但这对我们引出了一个更深层次的问题：我们应该将这种抽象化推进到什么程度？为什么 Bash 对代理表现如此出色，其边界又在哪里？

[@mintlify](https://x.com/@mintlify)

[recently introduced an approach](https://www.mintlify.com/blog/how-we-built-a-virtual-filesystem-for-our-assistant)

called ChromaFS, which gives their database a filesystem-like interface. Their write-up was thoughtful and sparked a serious debate on our team. Should every database expose a filesystem-style interface for agents? It felt like the perfect test case for answering some of our deeper questions about Bash-centric workflows.

![Image](https://pbs.twimg.com/media/HJ6DxVAa0AASBYM?format=jpg&name=large)

### 模式团队正在复制

Mintlify 构建了 ChromaFs，以使其文档助手更智能。纯向量 RAG 只能返回与查询嵌入匹配的片段；如果答案跨越了多页，或者需要从未进入 top-K 的精确语法，代理就会陷入困境。因此，他们将 Chroma 向量存储封装到了一个类似文件系统的界面中：代理可以运行 ls、cat、grep 等命令，而每条命令背后都是一次数据库读取操作。他们将其作为其他团队可以复制的模式发布。同样的“将数据库封装为文件系统”做法现在也出现在了原本不需要这样做的 SQL 数据库上。

你的智能体存在同样类型的问题：它需要处理数据库中的数据。这种模式背后的前提是，智能体对其训练数据中接触过的内容很熟悉，因此你应该给它们一个熟悉的界面。我们要测试的是，一个熟悉的界面是否足够，或者真正重要的是数据的实际存储位置。

### 我们的假设

有选择地允许代理仅从数据库拉取其所需的数据（通过技能），然后向其提供完整的本地 Bash 工具集，应该能克服在数据库本身中构建类似 Bash 界面的复杂性。

原因很实际：许多 Shell 和管道工作流仅以完整形式存在于本地。本地工具箱的范围比你在数据库抽象层后实际能重新创建的范围更广。数据库在这里仍然擅长一件事：在 TB 级数据中进行搜索和筛选。但对于迭代且分支密集的分析循环，本地工具通常是更好的执行环境。

所以这种模式是一种刻意的交接。代理使用数据库进行广泛检索，在本地实例化一个数据切片，进行深入分析，如果需要再拉取另一个切片。这在大规模搜索和复杂的本地推理之间提供了清晰的权衡。

Our bet was that a skill file, not a filesystem abstraction, would win on the two properties that matter most for this work: composability and speed. The skill runs a focused SQL query, writes results to a local file, and the agent composes the final answer with the host’s real Bash environment.

作为 ChromaFS 的替代品，我们使用了 PostgresFS。它基于 Postgres 以同样的方式工作：数据隐藏在抽象层之后，像 cat、grep 或 find 这样的命令被转换为数据库查询。

速度 来自局部性：一旦数据本地化，bash 就能直接处理它，无需再进行另一次数据库往返，而 PostgresFS 在每次读取时都要产生一次往返开销。 可组合性 是同样的局部性再次体现：任何需要对数据进行第二次处理（暂存中间结果、使用双输入操作符如 comm 或 join）的操作，都需要一个可写且可重新读取的本地存储，而只读抽象无法提供这一点。两者都可归结为一个问题：代理是否拥有数据的本地副本，或者在每次读取时都通过抽象层回溯？

因此我们预测：拥有合适技能的数据库应该能与文件系统抽象相媲美甚至超越，即便持平对该技能而言也是一种胜利：抽象层是一个需要构建并保持正确的大型自定义层，而技能则是一个提示词和一个能达成相同效果的小脚本。

### PostgresFS 或一项技能

我们构建了两者，并决定将它们与我们移植到 Postgres 的实时 Arize AX 文档进行测试。以下是它们各自的实际情况：

- PostgresFS, the filesystem abstraction. The five ChromaFs verbs (ls, cat, grep, find, cd) over virtual paths that resolve to Postgres reads, plus the standard coreutils filters (sort, uniq, wc, awk, sed, cut, tr, head, tail, comm). The agent explores the docs like a codebase. We wired it the way Mintlify's ChromaFS is built: an in-process shell (just-bash) registered as the agent's Bash tool. So we're testing the real pattern, not a strawman. It's read-only: the five verbs become SELECTs, the filters run locally over whatever bytes came back.
- The skill, the SQL workflow. No abstraction. The agent gets the host's real bash shell plus a small script that takes one SQL query and writes the result to a local file. The workflow it learns: write a query, run it, compose the answer against the file with real grep / jq / sort / pipes. The agent does the translation; the runtime just moves bytes.

这是同一项工作的两种实现方式：PostgresFS 将每次读取都发送回 Postgres，而该技术只访问数据库一次，其余操作则在本地完成。

![Image](https://pbs.twimg.com/media/HJ6D5XQboAAN3t_?format=jpg&name=large)

Each agent also gets an orientation prompt. PostgresFS's prompt hands it a decision table mapping question shapes to shell idioms and tells it to keep the number of doc reads down. The skill's prompt teaches a discipline: compute the answer in SQL and return it inline when it reduces to a small set (COUNT, GROUP BY, INTERSECT), otherwise project every candidate row to a file and compose locally — and don't treat the query script as a search tool, because a flurry of narrowing queries means you projected too little.

### 为什么 PostgresFS 失败

损失并不在于缺少操作符：我们给 PostgresFS 提供了所有过滤器，并且它们都能正常工作。问题出在 PostgresFS 内部，具体是在读取路径上：

- The filters are local. sort, uniq, awk and friends are pure stream transforms over bytes already in the pipe: in-process, no database, no round-trip.
- The reads are faked. ls, cat, grep, find resolve through an adapter that turns each into a Postgres SELECT. Two costs fall out of that.

Locality collapse. Every doc read is a database round-trip dressed as a shell verb. Each one pays for query parsing, serialization, and transfer, even when Postgres serves it warm from cache. A grep -rl followed by a burst of cats, near-instant on a real filesystem, becomes a sequence of round-trips. The skill pays that round-trip once: a single query lands the result on a local file, and everything after is local and composable, with no more database hops.

可组合性，限制为一次传递。单遍管道在两者上都能工作。但任何需要对数据进行第二次传递的操作都不行：just-bash 没有进程替换 &lt;(…)，且适配器是只读的（没有 /tmp，每次写入都是 EROFS），因此无法暂存和重用任何内容。双输入操作族（comm、join、diff、paste）已失效，尽管 comm 在允许列表中。这与局部性问题本质上是同一堵墙：该技能仅实现一次并可自由重用，而 PostgresFS 每次查看数据都要进行一次新的往返操作。

自然的反对意见是“那就往抽象中添加内容，直到它足够好为止”。这是一个陷阱。朝着忠实读取路径（更好的预取、更接近 grep 语义、真实缓存）迈进的每一步，都是朝着真实文件系统上的真实文件迈进的一步，而这种技能的实现方式，比在主机自己的 shell 中直接运行 SQL 要更不简洁。你为实现这一点所编写的代码，与一开始就需要为每次读取进行往返操作的代码是相同的：维护成本和性能成本是相同的成本。

### 这意味着什么

Our hypothesis mostly held, with one wrinkle worth keeping. We bet on composability and speed; they turned out to be one property: whether the agent works from a local copy of the data it owns or reaches back through the abstraction on every read. That same property is what you'd have to build and maintain. So the takeaways order themselves around cost, not cleverness:

1. 当性能不相上下时，剩下的成本就是维护。决定因素是你所拥有的东西：PostgresFS 是一个大型自定义层：一个适配器、一个粗过滤器、一个缓存、一个正则表达式转换器。你必须随着模式变化确保该层正确，而所需的技能是一个提示和一个小脚本。我们没有对维护进行基准测试，因此将其视为结构性论证，而非测量结果。而确实存在的性能差距只有在你按问题形式分层时才会显现出来。查看每题的通过率，否则你会在未察觉的情况下交付失败。
2. Reach for the real store before the pretty shape. "What does the host shell actually read from?" beats "what shape would I like to expose?" A familiar interface is necessary, not sufficient.
3. This generalizes past SQL. "Wrap the store as a filesystem" vs. "give the model the store's real query language plus a real shell" is the same decision for Chroma, Mongo, BigQuery, ClickHouse, or whatever's next. The query language is incidental. What's constant is the trap: every time you fake a filesystem, you sign up to maintain one, and the closer you push it to behave like the real thing, the more you've just rebuilt the real thing, slower.

## 解读（1）

### 2026-06-04 07:26:50

#### PostgresFS：给智能体“伪造文件系统”为何输给一个技能？

##### 1. 深度总结

文章讨论一个问题：

> **给 AI Agent 操作数据库时，应该把数据库包装成“文件系统”，还是直接给它查询技能 + 本地 Shell？**

作者对比了两种方案：

| 方案 | 做法 | 核心特点 |
|---|---|---|
| **PostgresFS** | 把 Postgres 包装成文件系统 | Agent 用 `ls/cat/grep/find` 探索数据库 |
| **Skill 技能方案** | 给 Agent 一个 SQL 查询脚本 | 查询结果落到本地文件，再用真实 Bash 分析 |

实验结果显示：

- 两者准确率都很高，约 **93%-99%**；
- 延迟差距不大；
- 但 **Skill 方案更简单、更可组合、更接近真实 Shell 工作流**；
- PostgresFS 的问题在于：  
  每次 `cat/grep/find` 都要转成 SQL，产生数据库往返、解析、传输成本。

核心结论：

> **熟悉的界面不等于高效的执行环境。**  
> 对 Agent 来说，真正重要的不是“看起来像文件系统”，而是数据是否已经在本地，能否被真实工具自由组合处理。

---

##### 2. 深入浅出解读

可以把它理解成两种工作方式。

###### 方式一：PostgresFS

像让 Agent 住在一个“假文件系统”里。

它以为自己在执行：

```bash
cat docs/page1.md
grep "config" docs/*
```

但背后其实是：

```sql
SELECT ...
FROM docs
WHERE ...
```

问题是：

> Agent 每读一次文件，系统都要去数据库跑一次查询。

就像你每看一页书，都要去图书馆前台申请一次。

---

###### 方式二：Skill

先让 Agent 问数据库：

```sql
SELECT content
FROM docs
WHERE product = 'xxx';
```

然后把结果保存成本地文件：

```bash
result.json
```

之后 Agent 就可以真正使用：

```bash
grep
awk
sort
jq
wc
sed
```

这时所有操作都在本地完成。

就像先把相关书籍借回家，再慢慢翻、标注、对比。

---

##### 3. 为什么“技能”赢了？

关键不是 SQL，也不是 Postgres。

关键是：

> **数据局部性。**

也就是：

- 数据在数据库里：每次操作都要远程读取；
- 数据在本地：后续操作都能快速组合。

PostgresFS 看起来很优雅：

```bash
ls /docs
cat /docs/a.md
grep error /docs/*
```

但这些命令都是“伪装”的。

真正的问题是：

> 它重新发明了一个文件系统，但更慢、更复杂、更难维护。

而 Skill 方案很朴素：

1. 用数据库做它擅长的事：大规模过滤、检索；
2. 把小范围数据拉到本地；
3. 用 Shell 做它擅长的事：组合、分析、管道处理。

这是一种更清晰的分工。

---

##### 4. 文章真正想说什么？

不是说“文件系统接口没用”。

而是说：

> **不要因为 Agent 熟悉 Bash，就把所有东西都伪装成文件系统。**

Agent 熟悉 Bash 是事实。

但 Bash 强大的原因不是命令长得熟悉，而是：

- 数据在本地；
- 工具真实存在；
- 管道高度可组合；
- 中间结果容易保存和复用；
- 分析路径可以快速分叉和迭代。

如果只是给数据库套一层 `cat/grep/find`，但每次操作都回数据库，那只是“外形像 Bash”，不是“能力像 Bash”。

---

##### 5. 辩证思考

###### 文件系统抽象的价值

PostgresFS / ChromaFS 这类方案不是完全错误。

它适合：

- 文档规模较小；
- 任务以浏览为主；
- Agent 不擅长写 SQL；
- 需要极低学习成本；
- 希望界面统一、体验友好。

对很多应用来说，`ls/cat/grep` 确实比 SQL 更自然。

---

###### 技能方案的优势

但在复杂任务中，Skill 更稳：

- 实现成本低；
- 不需要维护一个“假文件系统”；
- 可以利用真实 Bash 生态；
- 数据拉到本地后可重复分析；
- 更适合多步骤、分支式推理。

它体现了一种更务实的架构思想：

> **数据库负责筛选，Shell 负责加工，Agent 负责调度。**

---

###### 真正的架构原则

这篇文章的重点不是“PostgresFS 不好”，而是提醒：

> **不要被接口形态迷惑，要看数据流和执行成本。**

判断一个 Agent 工具设计好不好，不该只问：

- 这个接口 Agent 熟不熟？
- 看起来像不像文件系统？
- 能不能用 Bash 命令？

更应该问：

- 数据在哪里？
- 每次操作有没有跨系统往返？
- 中间结果能不能复用？
- 工具能不能组合？
- 维护抽象层的成本值不值？

---

##### 6. 一句话结论

> **给 Agent 的最好工具，不一定是最像人类熟悉界面的工具，而是最能让数据流动简单、局部计算高效、工具组合自然的工具。**

更短一点：

> **别急着伪造文件系统。先让数据库查准，再让本地 Shell 做深。**

## 结构化（1）

### 2026-06-04 07:42:23

#### 文章精炼总结：为代理模拟文件系统——为什么 PostgresFS 输给了一项技能

本文讨论了一个核心问题：**给 AI 代理访问数据库时，应该把数据库伪装成文件系统，还是让代理直接使用数据库查询能力再结合本地 Bash 工具？** 作者通过对比 PostgresFS 和 SQL Skill 发现：熟悉的文件系统接口并不一定更好，关键在于数据是否能被拉到本地后高效处理。

---

##### 1. 背景：Bash 和文件系统为何对代理很重要

现代 AI 代理常依赖 **Bash、文件读写、管道命令** 来完成任务，例如：

- `ls` 查看文件
- `cat` 读取内容
- `grep` 搜索文本
- `sort / awk / sed` 做数据处理

这些工具强大且通用，因此有人提出：“**Bash 可能就是代理所需要的一切**”。

但文章进一步追问：  
**是否应该把所有数据库都包装成类似文件系统的接口，让代理用熟悉的 Bash 命令访问？**

---

##### 2. ChromaFS 模式：把数据库包装成文件系统

Mintlify 提出了 **ChromaFS**，用于增强文档助手能力。

传统向量 RAG 的问题是：

- 只能返回与查询向量最相似的 top-K 片段；
- 如果答案分散在多页文档中，可能检索不到完整信息；
- 如果需要精确语法或边缘内容，向量检索可能遗漏。

因此 ChromaFS 把 Chroma 向量数据库包装成类似文件系统的形式，让代理可以使用：

```bash
ls
cat
grep
find
```

但这些命令背后实际执行的是数据库读取操作。

这种思路后来也被复制到 SQL 数据库上，即：  
**把数据库包装成文件系统，让代理像浏览代码仓库一样浏览数据。**

---

##### 3. 作者的假设：技能比文件系统抽象更划算

作者认为，代理真正需要的不是“数据库看起来像文件系统”，而是：

1. 用数据库完成大规模搜索和筛选；
2. 把需要的数据切片拉到本地；
3. 用真实 Bash 工具进行深入分析。

也就是说：

> 数据库负责广泛检索，本地文件系统负责复杂分析。

作者的假设是：  
**一个小型 SQL Skill，比复杂的文件系统抽象更快、更可组合，也更容易维护。**

这个 Skill 的工作方式是：

- 代理写 SQL 查询；
- 脚本执行查询；
- 查询结果写入本地文件；
- 代理再用本地真实 Bash 工具处理结果。

---

##### 4. 实验对象：PostgresFS vs SQL Skill

作者构建了两套方案，并用迁移到 Postgres 的实时 Arize AX 文档进行测试。

###### 方案一：PostgresFS，文件系统抽象

PostgresFS 模仿 ChromaFS 的设计，提供五个虚拟文件系统命令：

```bash
ls
cat
grep
find
cd
```

这些命令看起来像在读文件，实际上会被转换为 Postgres 的 `SELECT` 查询。

同时，它还支持本地 coreutils 过滤工具，例如：

```bash
sort
uniq
wc
awk
sed
cut
tr
head
tail
comm
```

特点：

- 代理像浏览代码库一样浏览文档；
- `ls / cat / grep / find` 每次都会访问 Postgres；
- 过滤器在本地执行；
- 整体是只读模式。

---

###### 方案二：SQL Skill，直接查询数据库

SQL Skill 不做文件系统包装。

代理拥有：

- 真实的主机 Bash；
- 一个小脚本，用于执行 SQL 查询并把结果写入本地文件。

工作流程是：

1. 代理写一个 SQL 查询；
2. 执行查询；
3. 把结果保存到本地文件；
4. 用真实的 `grep / jq / sort / pipe` 等工具继续处理。

关键区别是：

> PostgresFS 每次读取都回到数据库；SQL Skill 通常只访问数据库一次，之后都在本地处理。

---

##### 5. 提示词设计：两种方案的使用纪律

两种代理都拿到了不同的 orientation prompt。

###### PostgresFS 的提示词

它会告诉代理：

- 不同问题类型该用什么 shell 命令；
- 尽量减少文档读取次数；
- 像浏览文件系统一样探索文档。

###### SQL Skill 的提示词

它强调一种工作纪律：

- 如果问题能通过 SQL 聚合解决，比如 `COUNT`、`GROUP BY`、`INTERSECT`，就直接在 SQL 中计算；
- 如果需要进一步分析，就一次性把候选行投影到本地文件；
- 不要把查询脚本当成反复搜索工具；
- 如果连续发起很多次缩小范围的查询，说明一开始拉取的数据太少。

---

##### 6. 实验结果：表面接近，但 Skill 更有优势

实验结果显示，两者理论上差距不大：

- 延迟差距均未超过 **2 倍**；
- 准确率在 **93 到 99** 之间；
- 10 个问题中，中间结果几乎平分。

具体表现：

- PostgresFS 在 q2、q5、q6 上表现更好，原因是进程内调度更有利；
- Skill 在 q8、q9、q10 上表现更好，尤其适合读取量堆积的问题；
- 还有 4 个问题基本打平。

作者认为，这验证了假设：

> 从本地文件读取不会破坏基准测试效果，只会带来很小的准确率差异；而维护数据库文件系统抽象的工程成本却很高。

---

##### 7. 为什么 PostgresFS 最终失败

PostgresFS 的核心问题在于：**它模拟了文件系统的形状，但没有真正拥有文件系统的局部性。**

###### 本地过滤器是真的本地

例如：

```bash
sort
uniq
awk
sed
```

这些命令只处理管道中的字节流，不需要访问数据库，因此执行很快。

###### 但读取操作是伪装的

例如：

```bash
ls
cat
grep
find
```

这些命令看起来像文件系统操作，但实际每次都会转换成一次 Postgres 查询。

这会带来两个成本：

- SQL 查询解析；
- 数据序列化和传输；
- 数据库往返延迟。

在真实文件系统中：

```bash
grep -rl ...
cat file1 file2 file3
```

通常几乎是瞬间完成。

但在 PostgresFS 中，这会变成：

> 一连串数据库 round-trip。

相比之下，SQL Skill 只需要：

1. 一次 SQL 查询；
2. 把结果写入本地；
3. 后续所有处理都在本地完成。

---

##### 8. 核心结论：熟悉接口不够，数据位置更重要

作者认为，真正决定性能和可组合性的不是接口长什么样，而是：

> 代理处理的是本地拥有的数据副本，还是每次读取都要穿过抽象层回到数据库。

因此，文章提出几个重要结论：

###### 先考虑真实数据源，而不是漂亮接口

不要先问：

> “我想给代理暴露什么样的接口？”

而应该先问：

> “主机 shell 实际上在读什么？”

熟悉的接口有帮助，但并不足够。

###### 这个问题不只适用于 SQL

同样的取舍也适用于：

- Chroma
- MongoDB
- BigQuery
- ClickHouse
- 其他未来数据库

本质问题都是：

> 是把存储系统伪装成文件系统，还是让模型使用真实查询语言加真实 shell？

###### 伪装文件系统会带来长期维护成本

一旦把数据库包装成文件系统，就要维护：

- 路径语义；
- 文件读取语义；
- 搜索语义；
- 命令兼容性；
- 性能问题。

而包装得越像真实文件系统，越接近于：

> 重新造了一个更慢、更复杂的文件系统。

---

##### 9. 下一步：用评测验证架构选择

文章最后强调，使用 Arize AX 这样的评测体系，可以帮助团队从“凭感觉做架构选择”转向“用实验数据确认选择”。

最终观点可以概括为：

> 对代理来说，把数据库伪装成文件系统并不一定值得；更简单、更高效的方式，往往是让代理用数据库查询拉取合适数据，再用真实本地 Bash 工具完成分析。

## 综合-启发一下（1）

### 2026-06-04 08:03:06

#### 为你的代理模拟文件系统：PostgresFS 输给“一项技能”的关键启发

##### 1. 核心启发

###### 1.1 熟悉的界面不等于高效的执行环境

文章讨论的是一个很典型的 AI Agent 架构问题：

> 既然 Agent 很擅长使用 Bash、文件系统、`grep`、`cat`、`ls`，那我们是否应该把数据库也包装成类似文件系统的接口？

Mintlify 的 ChromaFS 做法是：  
把向量数据库包装成文件系统，让 Agent 可以像浏览代码仓库一样浏览文档：

```bash
ls
cat
grep
find
```

这听起来非常自然，因为大模型在训练中见过大量 Bash / 文件系统工作流。

但实验结果显示：

> 真正重要的不是界面长得像不像文件系统，而是数据是否已经在本地，能否被真实 Bash 工具高速组合处理。

也就是说，Agent 熟悉某个操作界面只是起点，不是终点。  
如果每次 `cat`、`grep` 背后都要走一次数据库查询，那么这个“文件系统”只是一个披着 Bash 外衣的远程数据库调用层。

---

###### 1.2 Agent 架构里的关键问题：谁拥有数据的局部性？

PostgresFS 的问题在于：

```bash
grep -> SELECT
cat  -> SELECT
find -> SELECT
ls   -> SELECT
```

表面上 Agent 在使用 shell，实际上每一次读取都在访问数据库。

而 Skill 方案是：

1. Agent 写一条 SQL；
2. 查询数据库；
3. 把结果写入本地文件；
4. 后续用真实 Bash / grep / awk / jq / sort / pipe 在本地处理。

核心差异是：

| 方案 | 数据读取方式 | 后续分析 |
|---|---|---|
| PostgresFS | 每次 shell 读取都回数据库 | 多次远程往返 |
| Skill | 一次 SQL 把候选数据拉到本地 | 本地组合处理 |

所以文章真正指出的是：

> Agent 工作流的性能和可组合性，取决于它是否能在本地拥有一个可操作的数据切片。

---

###### 1.3 “技能”可能比“复杂抽象”更强

PostgresFS 是一个需要构建和维护的复杂抽象层。  
它要把文件系统命令映射到数据库查询，还要处理路径、过滤、读取、缓存、权限、边界条件等问题。

而 Skill 只是：

- 一个提示词；
- 一个小脚本；
- 一个明确工作流：用 SQL 拉取数据，再用本地 Bash 分析。

文章的结论是：

> 如果一个简单 Skill 可以达到接近甚至更好的效果，那么构建完整文件系统抽象层的收益就值得怀疑。

这对产品和技术架构很重要：  
很多时候不是要给 AI 做一个“更像人类工具”的复杂界面，而是要给它一个更直接、更低摩擦、更可组合的工作路径。

---

##### 2. 高价值信息深挖

###### 2.1 Bash 对 Agent 有用，不是因为 Bash 本身神奇

很多人说：

> Bash might be all you need.

但文章提醒我们，Bash 的强大来自几个特性：

1. **工具丰富**：`grep`、`awk`、`sed`、`sort`、`uniq`、`jq` 等；
2. **组合性强**：可以通过 pipe 把多个小工具串起来；
3. **本地性强**：文件已经在本地，读取和过滤速度极快；
4. **可观察性好**：Agent 可以逐步查看中间结果；
5. **容错空间大**：可以先粗筛，再细查，再组合。

如果把 Bash 命令映射成数据库访问，却没有本地性，那么只保留了形式，丢掉了关键优势。

也就是说：

> Bash 对 Agent 有用，是因为它建立在真实本地文件系统之上，而不是因为 `ls/cat/grep` 这些名字本身有魔法。

---

###### 2.2 抽象层的成本经常被低估

把数据库包装成文件系统看似优雅，但会带来长期维护成本：

- 路径设计；
- 查询映射；
- 权限控制；
- 缓存策略；
- 错误处理；
- 结果截断；
- 大文件处理；
- 命令语义兼容；
- 性能优化；
- Agent 误用后的恢复策略。

越想让它像真实文件系统，就越接近于重新实现一个文件系统。  
但这个重新实现的系统往往：

- 更慢；
- 更脆弱；
- 语义不完整；
- 维护成本更高。

文章里的金句可以总结为：

> 每次你伪造一个文件系统，你就在承诺维护一个文件系统。

---

###### 2.3 真正的分工应该是：数据库负责广域搜索，本地工具负责深度推理

文章提出的更优分工是：

```text
数据库：在 TB 级数据中做搜索、筛选、聚合
本地环境：对筛选后的数据做迭代分析、组合处理、验证和推理
```

这非常适合 Agent 工作流。

数据库擅长：

- 过滤；
- 聚合；
- Join；
- 排序；
- 全文搜索；
- 向量召回；
- 大规模扫描。

本地 Bash 擅长：

- 快速查看；
- 临时组合；
- 多轮分析；
- 格式转换；
- 局部验证；
- 对中间结果反复操作。

所以理想模式不是“让数据库像文件系统”，而是：

> 让 Agent 先用数据库语言拿到正确的数据切片，再在真实本地环境中展开分析。

---

###### 2.4 性能和组合性其实是同一个问题

文章原本假设 Skill 会在两个维度上赢：

1. composability，可组合性；
2. speed，速度。

但实验后发现，这两个维度背后其实是同一个属性：

> Agent 是否在操作一个本地拥有的数据副本。

如果数据在本地：

- `grep` 很快；
- `cat` 很快；
- `sort` 很快；
- 多次尝试成本低；
- 管道组合自然；
- Agent 可以大胆探索。

如果数据不在本地：

- 每次读取都有往返；
- 多次探索成本高；
- Agent 会被延迟和调用成本约束；
- 工作流变得不自然；
- 抽象层越复杂，性能损失越隐蔽。

这对 AI 产品开发很关键：  
Agent 不是只需要“能访问工具”，还需要“能低成本地反复试错”。

---

##### 3. 可迁移清单

###### 3.1 判断是否该构建“文件系统抽象”的清单

在把数据库、知识库、向量库包装成文件系统前，先问：

- Agent 是否真的需要逐文件浏览？
- 数据是否已经适合以层级目录方式组织？
- 每次 `cat` / `grep` 是否会触发远程请求？
- 是否能一次性拉取候选数据到本地？
- 本地处理是否比远程多次读取更快？
- 抽象层是否会引入语义误导？
- 维护这个虚拟文件系统的成本是否值得？
- 是否只是因为模型熟悉 Bash，所以强行做了类文件系统接口？
- 是否可以通过一个 Skill + 查询脚本达到相同效果？
- 是否已有真实查询语言更适合这个数据源？

如果多数答案指向“可以查询后本地处理”，那优先考虑 Skill，而不是 FS 抽象。

---

###### 3.2 Agent 数据访问架构清单

一个更稳健的 Agent 数据访问架构可以是：

```text
1. 让 Agent 理解数据结构
2. 提供真实查询语言或查询工具
3. 一次拉取合适范围的数据切片
4. 写入本地文件
5. 使用真实 Bash / Python / jq / grep 分析
6. 如果数据不足，再重新查询
7. 最终基于本地证据生成答案
```

对应设计原则：

| 原则 | 说明 |
|---|---|
| 先查询，后分析 | 数据库负责召回和过滤 |
| 先投影，后组合 | 把候选数据写到本地 |
| 减少往返 | 避免每次读取都访问远程存储 |
| 保留真实工具链 | 不要复刻一个半成品 Bash |
| 让 Agent 学会工作流 | 用 prompt 和 skill 约束行为 |
| 用 eval 验证架构 | 不靠直觉判断接口优劣 |

---

###### 3.3 Skill 设计清单

如果采用 Skill 方案，可以这样设计：

###### Skill 需要告诉 Agent：

- 数据库有哪些表；
- 每张表代表什么；
- 常见查询模式；
- 什么时候应该直接用 SQL 聚合；
- 什么时候应该把结果导出到文件；
- 不要连续发很多窄查询；
- 如果需要多轮 grep，应该一次性投影更多候选数据；
- 本地文件如何命名；
- 如何用 Bash 工具处理结果。

###### 推荐规则：

```text
如果答案可以用 COUNT / GROUP BY / INTERSECT / JOIN 直接得到：
    用 SQL 直接算出答案

如果答案需要阅读、比较、归纳多个文档：
    SQL 拉取候选行 -> 写入本地文件 -> 用 Bash 组合分析

如果 Agent 连续发出很多收窄查询：
    说明第一次投影太少，应扩大候选数据切片
```

---

##### 4. 反方与张力

###### 4.1 文件系统抽象并不是没有价值

虽然文章倾向于 Skill，但 FS 抽象也有适用场景。

例如：

- 数据天然就是文档树；
- 用户和 Agent 都需要统一的浏览界面；
- 数据规模不大；
- 读取频率低；
- 延迟不敏感；
- 需要隐藏底层数据库复杂性；
- Agent 不擅长写查询语言；
- 团队希望用统一接口接入多个数据源。

在这些情况下，类文件系统接口可能降低使用门槛。

所以不能简单得出：

> 所有数据库都不该包装成文件系统。

更准确的说法是：

> 如果你的虚拟文件系统导致每次读取都变成远程数据库往返，那么它很可能输给“查询 + 本地分析”的 Skill 工作流。

---

###### 4.2 Skill 方案也有风险

Skill 方案不是银弹，它依赖 Agent 能正确写查询。

潜在问题包括：

- SQL 写错；
- 查询范围过窄；
- 漏掉关键数据；
- 导出数据过大；
- 数据库 schema 太复杂；
- 权限控制更难；
- Prompt 约束不稳定；
- 本地文件可能包含敏感信息；
- Agent 可能过度依赖一次查询结果。

因此 Skill 需要配套：

- schema 注释；
- query examples；
- 自动限制；
- 审计日志；
- 结果大小控制；
- 本地文件生命周期管理；
- eval 测试集；
- fallback 查询策略。

---

###### 4.3 产品体验与系统效率之间的张力

文件系统抽象的吸引力来自产品体验：

```text
Agent 会用 ls/cat/grep，所以我给它 ls/cat/grep。
```

Skill 方案的吸引力来自系统效率：

```text
数据库做数据库擅长的事，本地做本地擅长的事。
```

二者之间的张力是：

| 维度 | 文件系统抽象 | Skill 查询方案 |
|---|---|---|
| 上手成本 | 低 | 中等 |
| 模型熟悉度 | 高 | 取决于 SQL 能力 |
| 性能 | 可能较差 | 通常更好 |
| 可组合性 | 表面强，实际受限 | 真实强 |
| 维护成本 | 高 | 低 |
| 语义透明度 | 可能隐藏成本 | 更直接 |
| 适合场景 | 文档浏览、轻量探索 | 大规模数据分析、复杂推理 |

---

##### 5. 情境化落地

###### 5.1 如果你在做 AI 文档助手

不要默认只做向量 RAG，也不要马上做 ChromaFS 类抽象。

更稳妥的架构是：

```text
向量检索 / 全文搜索 / SQL 查询
        ↓
拉取候选文档集合
        ↓
写入本地上下文或临时文件
        ↓
Agent 用 grep / rerank / summarize / compare
        ↓
生成答案并引用来源
```

关键是：  
当答案跨越多篇文档时，应该让 Agent 拥有一个足够完整的候选集，而不是反复 top-K 检索。

---

###### 5.2 如果你在做企业数据 Agent

对于 CRM、ERP、数据仓库、日志系统，优先考虑：

```text
真实查询语言 + 受控导出 + 本地分析
```

例如：

- BigQuery Agent：用 SQL 拉取结果到 parquet/csv；
- ClickHouse Agent：先聚合/过滤日志，再本地分析；
- Mongo Agent：用 query pipeline 导出 JSON；
- Postgres Agent：SQL 查询后写入 JSONL/CSV；
- Vector DB Agent：先召回 top-N 文档，再本地重排和归纳。

不要急着把它们都包装成：

```bash
ls customers/
cat orders/123
grep "error" logs/
```

除非你确认这种接口不是在制造大量远程读取。

---

###### 5.3 如果你在设计 Agent 工具系统

可以采用一个简单原则：

> 工具不要只优化“模型是否熟悉”，还要优化“模型是否能低成本反复试错”。

Agent 需要的不是漂亮抽象，而是稳定工作流：

```text
发现问题 -> 获取数据 -> 本地检查 -> 组合分析 -> 重新获取 -> 验证答案
```

工具设计应该支持：

- 大块数据投影；
- 本地暂存；
- 可重复检查；
- 快速过滤；
- 中间结果可见；
- 最少远程往返；
- 清晰失败模式。

---

##### 6. 一句话总结

> 为 Agent 设计工具时，不要沉迷于把所有东西包装成它熟悉的样子；更重要的是让数据在正确的位置流动。数据库负责大规模检索，本地环境负责组合分析。很多时候，一个好 Skill 胜过一个复杂的虚拟文件系统。
