### How Qoder builds Harness Engineering into Experts Mode

### The competition has moved

---

Last month, OpenAI published

[Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/). The headline result: 3 engineers (later 7) shipped a real product with zero lines of hand-written code over five months. One million lines of code. Roughly 1,500 pull requests. All driven by agents.

Around the same time, Stripe, Ramp, and Coinbase went public with the internals of their own coding agent systems.

The signal: the competitive edge has shifted from "model capability" to everything outside the model. Harness Engineering.

What is Harness Engineering? A quick analogy:

- Model = CPU (raw compute)
- Context Window = RAM (limited working memory)
- Agent Harness = Operating System (manages context, startup routines, standard drivers)
- Agent = Application (runs on the OS)

![Image](https://pbs.twimg.com/media/HELbWWBaIAQ1hNP?format=jpg&name=large)

A Harness sits above an Agent Framework. Frameworks give you building blocks: tool calling, agentic loops. A Harness gives you the rest. Prompt presets. Standardized tool invocation. Lifecycle hooks. And the capabilities you actually need in production: planning, file system access, sub-agent coordination, verification loops.

Harness Engineering = control system design for AI Agents. The goal: build infrastructure so the agent writes correct code consistently, across long-running iterations, in a way you can audit, roll back, and extend.

#### Where the industry stands

Harness Engineering is already in production at top engineering organizations:

- Stripe forked Block's open-source agent
  [Goose](https://github.com/block/goose) and built Blueprint, a state machine that alternates deterministic nodes with agentic task nodes. They merge 1,300+ fully agent-authored PRs per week.
- Shopify open-sourced
  [Roast](https://github.com/Shopify/roast), a workflow framework that interleaves AI steps with deterministic code.
- Ramp built
  [Inspect](https://engineering.ramp.com/post/why-we-built-our-background-agent)on top of OpenCode, running sessions in Modal sandboxes with parallel execution. 30% of their merged PRs are now agent-written.
- Coinbase built Cloudbot from scratch, compressing PR review cycles from 150 hours to 15.
- OpenAI pushed "zero hand-written code" to million-line scale, using Codex to drive an entire product iteration.

Each of these teams solved real problems. Sandbox isolation. Context pre-hydration. Deterministic orchestration. But they all share one structural constraint: the agent is still monolithic. One model instance, one context window, one execution path, start to finish.

#### Five structural limits of single-agent Harness

As task complexity rises, five limits surface:

1. Context window as zero-sum game. Research, coding, testing, and review context all compete for the same window. The more complex the task, the lower the information density.
2. Cognitive overhead of role-switching. An agent constantly switching between architecture research, implementation, and test execution is like asking one person to be Tech Lead, SWE, QA, and Code Reviewer simultaneously. It performs poorly in practice.
3. Drift in long execution chains. The longer the task chain, the higher the probability of drifting from the original goal. Without external checkpoints, errors propagate and compound.
4. Missing functional correctness verification. Current practices focus on internal quality and consistency but underinvest in verifying that the product actually works. A codebase can be architecturally clean, lint-free, and well-documented while the business logic is wrong and user flows are broken.
5. Terminal execution risk. When an agent runs shell commands, a single mistaken command can cause irreversible damage. Most Harness systems rely on blocklists or confirmation dialogs. Blocklists are easy to bypass. Confirmation dialogs interrupt flow, and users click through them blindly.

If Harness Engineering means "design the system backward from desired behavior," then when we want agents to collaborate like an engineering team, the Harness needs to evolve from wrapping a single model to organizing a team.

We built Experts Mode to solve these five problems. In internal benchmarks it scores 67% higher than single-agent mode at less than two-thirds the cost. The rest of this article is the architecture behind that number.

### Qoder's Harness Engineering: Experts Mode

The five problems above map to five mechanisms in Qoder Experts Mode:

![Image](https://pbs.twimg.com/media/HELdgucaIAU_i4t?format=png&name=large)

Beyond these five, we push further in two directions: cross-model scheduling matches each expert to the optimal model, and self-evolution lets the system accumulate experience from every execution.

![Image](https://pbs.twimg.com/media/HELdkxPaIAMS48R?format=jpg&name=large)

#### 1\. Coordination separated from execution

The Leader coordinates. It never implements. It receives user requirements, decomposes tasks, manages dependencies, tracks progress, and reports results. Think Tech Lead and domain engineers. From a Harness Engineering perspective, the Leader is a meta-Harness: it manages a set of specialized Agent Harnesses, each with its own toolset, context strategy, and execution constraints.

![Image](https://pbs.twimg.com/media/HELdv4_bQAAHFzu?format=jpg&name=large)

#### 2\. Async parallelism: DAG-driven task orchestration

All SWE Agents run asynchronously in parallel by default. When the Leader creates an expert task, the system does not block. Dependencies form a lightweight DAG: "Implement backend API" and "Build frontend page" run in parallel; "Integration test" waits for both. Each expert works in its own isolated context window, so the zero-sum problem goes away.

#### 3\. Star topology: centralized coordination

SWE Agents do not communicate directly. All coordination routes through the Leader.We considered peer-to-peer communication early on and rejected it. When agents talk to each other, nobody holds the complete picture. Two experts can make contradictory decisions and no one notices. Tracking state across all pairwise connections gets exponentially harder as the team grows. A star topology with the Leader at the center avoids all of this. Users are also in the coordination path: they can insert new instructions at any time, and the Leader picks them up in the next cycle.

#### 4\. Specialized roles: each expert is its own Harness

This is the design choice that matters most to the final output quality. Each expert is a separate Harness tuned for a specific task type. They have different toolsets, different context injection strategies, different execution constraints. Swapping a system prompt is not what we're doing. The entire Harness is different.

![Image](https://pbs.twimg.com/media/HELeLjZagAA0NFG?format=png&name=large)

Each expert's context window contains only information relevant to its role. This is how we deal with Context Rot. Role isolation eliminates context competition at the source, which turns out to work better than any compression strategy we tried.

#### 5\. Cross-model scheduling: model orchestration at the Har·ness layer

Single-agent systems lock you into one model for everything. Research needs strong reasoning. Coding needs strong code generation. Browser verification needs visual understanding. These capabilities vary a lot across models.Because each expert runs independently, each can use a different model:

- Researcher expert: strongest reasoning model, for judgment and synthesis across search results
- Dev expert: best code generation model
- Browser expert: multimodal model, with a lightweight fallback for simple verification tasks
- Reviewer expert: model most sensitive to security and performance issues

The Leader matches task types to model capabilities and optimizes for the overall outcome. This is what makes it possible for quality and cost to improve at the same time: precise model-task matching avoids paying for capabilities you don't need on a given subtask.

In our internal benchmarks: 67% higher quality vs Agent Mode, 16% higher quality vs Claude Code Agent Teams, at less than 2/3 the cost.

#### 6\. Functional correctness verification: closing the industry gap

Most Harness systems can tell you whether the code is clean. Fewer can tell you whether the product actually works. We built three verification experts specifically for this:

- Browser expert runs E2E verification against real user flows in a real browser. It checks interaction flows, page rendering, and visual regression at a level that static analysis and unit tests cannot reach.
- QA expert uses a change-aware context mechanism that scopes verification to the code actually affected by the current change, rather than running every test generically.
- Code Revieer expert runs semantic diff + call-chain analysis to catch cases where a code change looks fine in isolation but introduces side effects elsewhere in the call graph.

The Leader schedules all three inline with the execution chain. Verification triggers right after coding completes, so errors get caught before they spread through downstream tasks.

#### 7\. Self-evolution: from static Harness to dynamic learning system

![Image](https://pbs.twimg.com/media/HELewwCaMAA8a1e?format=jpg&name=large)

Traditional Harness systems are static. You configure them once and they stay that way until someone updates them manually. We wanted something that gets better with use.

Qoder Experts introduces task-level skill extraction. When the system detects a correction, a failure it recovered from, or an explicit user instruction, the Leader and each SWE Agent independently extract reusable skills from their domains. The coding expert extracts implementation patterns. The verification expert extracts check strategies. The review expert extracts review heuristics.

These skills persist in a memory system and get recalled automatically when similar tasks come up. Over time, the system stops making mistakes it has already learned from. That loop (task completion, skill extraction, memory consolidation, skill recall, direct success) is what turns a static Harness into something that genuinely improves.

#### 8\. Terminal execution safety: multi-platform sandbox and intelligent interception

Writing code is half the job. Executing code is where risk actually lives.The first problem is parsing. Shell syntax varies dramatically across operating systems: Bash backtick nesting, PowerShell pipe syntax, Cmd special characters. We built independent AST parsers for each shell (PowerShell, Bash/Zsh, Cmd) that penetrate command nesting to identify every sub-command that will actually execute. Take $(rm -rf /) embedded in an innocent-looking outer command: our parser extracts rm and flags it as high-risk.

After parsing, commands go through three independent risk checks. A hard-coded blocklist catches known dangerous commands (rm -rf, format, dd if=). A rule engine detects command-argument combinations that are individually harmless but dangerous together. And an LLM semantic analysis layer reads command intent to catch things the first two miss. The LLM layer is additive: even if it fails, the blocklist and rule engine still intercept independently. Any single trigger blocks execution.

Even commands that pass all three checks run inside OS-level sandboxes:

![Image](https://pbs.twimg.com/media/HELfopPboAAL7ZF?format=jpg&name=large)

![Image](https://pbs.twimg.com/media/HELfsDjaIAM0bup?format=png&name=large)

The principle: isolate first, then grant full permissions within the boundary. The agent operates freely inside the sandbox, but its blast radius is bounded. Stripe does something similar with their devboxes ("cattle, not pets"), but that requires cloud infrastructure. We ship this as a local product capability that works on a developer's own machine.

### The complexity of Harness should not fall on the user

Rigor has not disappeared from software engineering. It has migrated. From function implementation to system constraints. From manual review to automated governance.

You should not have to fork an open-source agent, set up sandboxes, design Blueprints, write 500 rule files, and implement multi-platform security mechanisms yourself.

#### Qoder 如何把 Harness Engineering 做成“专家协作模式”

##### 一句话总结
这篇文章的核心观点是：AI 编程的竞争重点，已经不再只是“模型强不强”，而是“怎么把模型组织起来真正稳定产出”。Qoder 提出的 `Experts Mode`，本质上就是把单个 AI Agent，升级成一个分工明确、可协作、可验证、可控风险的“AI 工程团队”。

##### 背景：行业正在从“模型能力”转向“系统能力”
文章先举了 OpenAI、Stripe、Ramp、Coinbase、Shopify 等公司的例子，说明顶级团队已经在大规模使用 AI 写代码，甚至做到“几乎不手写代码”。

这说明一个趋势：真正拉开差距的，不只是模型本身，而是模型外面的那套工程体系，也就是 `Harness Engineering`。它决定了 AI 是否能长期、稳定、低风险地完成复杂任务。

##### 什么是 Harness Engineering
可以把它理解成：给 AI Agent 搭建一套“运行管理系统”。

类比来说：
- 模型像 CPU，负责原始计算
- 上下文窗口像内存，容量有限
- Harness 像操作系统，负责调度、规则、工具和流程
- Agent 像运行在系统上的应用

它的目标不是让 AI “偶尔写对代码”，而是让 AI 在长链路任务里，持续写对、可审计、可回滚、可扩展。

##### 单 Agent 方案的 5 个核心问题
文章认为，当前很多系统虽然已经很强，但本质上还是“一个 Agent 从头做到尾”，这会带来 5 个限制：

###### 1. 上下文资源互相抢占
研究、编码、测试、评审都挤在同一个上下文里，任务越复杂，信息越混乱。

###### 2. 一个 Agent 频繁切换角色，效率低
同一个 Agent 既要像架构师思考，又要像工程师开发，还要像 QA 测试、Reviewer 审查，实际效果会变差。

###### 3. 长任务链容易跑偏
任务执行链一长，就更容易偏离原始目标，而且错误会不断累积。

###### 4. 缺少“功能正确性”验证
很多系统只能检查代码规范、架构整洁，却不能真正确认“产品能不能用、业务逻辑对不对”。

###### 5. 终端执行风险高
AI 一旦执行错误命令，可能直接造成不可逆损失。单靠黑名单或弹窗确认，并不可靠。

##### Qoder 的解决方案：把单 Agent 变成“专家团队”
Qoder 的 `Experts Mode` 就是针对上面的问题，构建了一套多专家协作架构。

###### 1. Leader 负责协调，不亲自写代码
Leader 相当于 Tech Lead，只负责拆解任务、分配工作、跟踪依赖、汇总进度，不参与具体实现。

好处是：管理和执行分离，系统更清晰，也更不容易混乱。

###### 2. 专家并行工作，效率更高
不同专家可以异步并行执行，例如后端开发和前端开发可以同时进行，集成测试等前置任务完成后再接续。

这样不仅加快速度，也避免所有任务争抢同一个上下文窗口。

###### 3. 用“中心化协调”代替 Agent 互聊
所有专家都通过 Leader 协调，而不是彼此直接沟通。

这样做的好处是：避免信息失真、避免冲突决策，也更容易追踪整体状态。

###### 4. 每个专家都有独立的 Harness
这不是简单地给不同 Agent 换个提示词，而是给不同角色设计不同的工具、上下文策略和执行限制。

例如：
- 研究专家只看搜索和分析相关信息
- 开发专家专注写代码
- 浏览器专家负责真实页面验证
- 审查专家关注安全和性能

本质上是“按角色隔离上下文”，从源头解决信息污染问题。

##### 更进一步的两个关键能力

###### 1. 跨模型调度
不同任务用不同模型完成，而不是所有任务都绑死在一个模型上。

比如：
- 研究任务用推理强的模型
- 开发任务用代码生成强的模型
- 浏览器验证用多模态模型
- 代码评审用更敏感于安全/性能问题的模型

这样既提升质量，也能降低成本，因为不会在不需要的任务上浪费高性能模型资源。

###### 2. 自我进化
系统会从每次执行中提炼经验，把失败修正、用户反馈、成功模式沉淀成“技能记忆”。

下次遇到类似任务时，系统会自动调用这些经验，从而越用越强，而不是一直停留在固定能力水平。

##### Qoder 特别强调的一点：验证“代码对”还不够，还要验证“产品能用”
文章很强调行业里的一个缺口：很多系统关注代码质量，但忽略了功能正确性。

为此，Qoder设计了 3 类验证专家：

###### 1. Browser Expert
在真实浏览器里跑端到端流程，验证页面渲染、交互流程和视觉问题。

###### 2. QA Expert
根据当前代码改动范围，做有针对性的验证，而不是机械地全量跑测试。

###### 3. Code Reviewer Expert
通过语义 diff 和调用链分析，检查改动是否在别处引发副作用。

这些验证动作会嵌入开发流程中，代码写完就立刻验证，尽早发现问题。

##### 安全能力：重点防止终端命令失控
Qoder 认为，真正的高风险不在“写代码”，而在“执行代码”。

因此它做了两层保护：
- 先解析不同系统下的 shell 命令结构，识别隐藏风险
- 再通过黑名单、规则引擎、LLM 语义分析三层风险检测拦截危险命令

即使命令通过检查，也只会在操作系统级沙箱中运行，把风险限制在可控范围内。

##### 结论：未来的 AI 编程，不是更强的单体，而是更强的组织方式
这篇文章的核心结论是：

AI 编程的下一阶段，不是谁拥有“最强模型”，而是谁能把多个模型、多个角色、多个验证环节、安全机制和经验沉淀组织成一套完整系统。

Qoder 的 `Experts Mode` 想解决的，本质不是“让一个 Agent 更聪明”，而是“让 AI 像一个高效、专业、可控的工程团队一样工作”。

- 其核心优势在于：分工、并行、跨模型调度、功能验证、自我进化、安全沙箱
- 本质上，Qoder 不是在做一个更强的 Agent，而是在做一套 AI 工程组织系统

##### 4. Qoder 的解决方案：Experts Mode
Qoder 的做法是把一个 Agent，变成多个“专家 Agent”协作：
- Leader 只负责拆任务、调度、跟踪，不亲自写代码
- 各类专家并行工作，按 DAG 依赖运行
- 所有沟通都经过 Leader，避免多 Agent 互相打架
- 不同专家有不同工具、上下文、限制，不只是换个 Prompt
- 不同任务匹配不同模型，提升质量同时降低成本

另外还补了三块关键能力：
- 功能正确性验证：浏览器测试、QA、代码评审专家一起检查
- 自我进化：从失败、修正、用户反馈中沉淀“技能”
- 终端安全：解析命令、风险检测、多层拦截、沙箱执行

#### 深入浅出地解读

##### 这篇文章真正想说什么？

它不是在说“我们的模型更聪明”，而是在说：

> **未来 AI 编程的核心，不是谁有最强单兵，而是谁有更强的“组织能力”。**

这很像现实中的工程团队。

一个人再厉害，也很难同时做好这些事：
- 理需求
- 查资料
- 设计架构
- 写前后端
- 跑测试
- 查 bug
- 做 code review
- 控风险

所以传统单 Agent 模式，本质上像是让一个人同时当：
- 技术负责人
- 开发工程师
- QA
- 安全审查员
- 产品验收员

这当然会出问题。

---

##### 为什么“多专家协作”更合理？

因为它更接近真实团队的工作方式。

比如开发一个功能时：
- `Leader`：负责拆分任务、安排顺序
- `Researcher`：查方案、做技术判断
- `Dev`：写代码
- `Browser expert`：像真实用户一样点页面
- `QA expert`：验证变更影响
- `Reviewer`：看安全、性能、副作用

这样做的好处是：

###### 1. 减少“脑子打架”
单 Agent 的上下文是共享的，研究内容、代码细节、测试结果全塞在一个窗口里，容易混乱。  
多专家模式相当于**每个人只看自己该看的信息**，更聚焦。

###### 2. 减少角色切换损耗
写代码和做测试，是两种很不一样的思考方式。  
让一个 Agent 来回切换，效率和质量都会下降。  
分工后，每个专家都能把一件事做好。

###### 3. 更容易控制流程
有一个 Leader 在中间统一调度，相当于项目经理/Tech Lead。  
这样不会出现“前端和后端各自改，最后冲突没人发现”的情况。

---

##### 为什么“验证”被特别强调？

因为很多 AI 编程系统目前更擅长的是：

- 代码风格好
- 结构整齐
- 能通过 lint
- 文档写得像样

但这些不等于：
- 功能真的正确
- 页面真的能点
- 业务逻辑真的没错
- 改动不会波及别的地方

文章在这里抓得很准：  
**“代码写得漂亮” 和 “产品真的能用” 是两回事。**

所以 Qoder 把验证独立成几类专家，这其实很重要。  
因为真正的工程价值，不是“生成代码”，而是**生成可工作的结果**。

---

##### 为什么“安全执行”是大问题？

AI 写代码只是第一步，真正危险的是它开始跑命令的时候。

比如误执行：
- 删除文件
- 覆盖数据库
- 清空目录
- 运行危险脚本

很多系统的做法只是：
- 黑名单拦截
- 弹个确认框让用户点一下

但这都不够可靠。  
作者的意思是：**安全不能靠用户时刻保持警惕，而应该靠系统设计来兜底。**

所以他们做了：
- 针对不同 shell 的命令解析
- 多层风险识别
- 沙箱隔离

这体现出一个很重要的思路：

> **AI 工程系统不能只追求“会做事”，还要保证“不会闯大祸”。**

#### 我的意见

##### 我认同的地方

###### 1. 判断趋势是对的
这篇文章最有价值的一点，是它看清了方向：  
**未来比拼的是 AI 工程化，而不只是模型参数。**

模型会越来越接近，但谁能把模型接进真实研发流程、控制风险、提高交付成功率，谁更有优势。

###### 2. 多专家架构比单 Agent 更适合复杂开发
这是很自然的演进方向。  
任务越复杂，越需要：
- 分工
- 调度
- 验证
- 回滚
- 审计

单 Agent 更适合小任务；多 Agent 更适合真实项目。

###### 3. 把“功能正确性验证”单独拎出来，非常关键
这是很多 AI 编码产品容易忽略的点。  
真正能落地的系统，一定要从“能生成代码”走向“能交付正确结果”。

---

##### 我保留的地方

###### 1. 文章明显带有产品宣传色彩
像“67% 更高质量”“不到 2/3 成本”这种数据，**如果没有公开基准、任务集、评估方法，很难完全判断含金量**。

所以这些数字可以参考，但不要照单全收。

###### 2. 多 Agent 不一定天然更强
多专家协作虽然听起来很好，但也会带来新问题：
- 调度成本更高
- 协调错误更复杂
- 系统维护更难
- 整体延迟可能上升

也就是说，**架构更高级，不代表在所有场景都更划算**。小任务可能反而单 Agent 更直接。

###### 3. “自我进化”听起来很好，但落地难度很高
从错误里提炼技能、形成长期记忆，这确实很有想象力。  
但现实里容易遇到：
- 学到错误经验
- 记忆污染
- 旧经验不适配新项目
- 技能召回不稳定

所以这部分潜力很大，但也最值得继续观察。

#### 结论

这篇文章值得关注，因为它讲清了一个重要事实：

> **AI 编程正在从“模型能力竞赛”，进入“系统工程竞赛”。**

Qoder 的 Experts Mode，本质上是在把 AI 从“单兵作战”升级为“团队作战”。这个方向我认为是对的，尤其适合复杂、长链路、要求高可靠性的研发场景。

但同时也要保持理性：
- 理念先进，不等于已经完全验证
- 多 Agent 架构强大，也意味着更复杂
- 真正的价值，最终还是要看真实项目中的稳定性、成本和交付效果
