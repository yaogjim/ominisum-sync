- **核心高价值点**：将token成本定义为架构问题，并提出用token yield衡量单位token产生的有效成果。
- **留存建议**：长期保留（提出了从架构层面优化企业AI token效率的框架，适合作为AI系统设计和成本治理的参考。）

**知识要点**

- 企业AI系统的大量token消耗来自上下文、工具、执行轨迹和记忆等支撑框架，而非用户输入本身。
- 提升token效率的关键杠杆包括高质量上下文检索、按任务复杂度进行模型路由、复用历史执行经验、控制agent工作流中的上下文膨胀。
- 长流程agent如果持续累积上下文，会同时推高成本并降低可靠性，应将中间状态外部化并按步骤限定工具和上下文。
- 企业AI的长期护城河可能来自执行效率，而不只是模型能力本身。

**行动项**

- 为现有AI应用建立token yield指标，评估每单位token带来的有效业务结果。
- 检查RAG或agent系统是否存在过度检索、工具暴露过多、重复推理和默认使用高价模型的问题。
- 设计多模型路由策略，将常规检索、验证、工具选择等任务交给更低成本或专用模型处理。
- 将agent执行过程中的中间状态外部化，避免无控制地扩展活动上下文窗口。

### 你的 token spend 是一个 AI 架构问题，而不仅仅是模型问题

企业 AI 代币支出正快速增长，特别是随着技术从简单的聊天助手转向编码代理、AI 协作者和长期运行的工作流。这些系统每个任务完成的工作量大得多，但消耗的代币也多得多。这对企业来说产生了一个新的运营约束：不是 AI 是否有用，而是它能否产生足够的有用成果来证明成本合理。

The spending signals are now hard to ignore.

[Deloitte’s 2025 Tech Value Survey](https://www.deloitte.com/us/en/insights/topics/digital-transformation/ai-tech-investment-roi.html) found that more than half of respondents allocate between 21% and 50% of their digital initiative budgets to AI, with an average of 36%.

[Ramp](https://ramp.com/ai-cost-monitoring)

recently reported a 4x year-over-year increase in monthly AI spend. And

[Fortune](https://fortune.com/2026/05/26/uber-coo-ai-spending-tokens-claude-code/)

reported that Uber burned through its entire 2026 AI coding tools budget in four months.

在我与领导者的太多对话中，代币消耗增长迅速，而商业价值却没有以相同的速度增长。

这就是为什么我认为企业需要一个比原始 token 使用量更好的衡量指标。正确的问题不是系统消耗了多少 token，而是系统每消耗一个 token 产生了什么有用的成果。换句话说：token yield。

思考 AI 经济学时，更有用的方式是考虑 token 使用，因为 token 使用很少仅由模型单独驱动。它由模型周围的整个系统决定：上下文如何检索、工具如何被暴露、任务如何分解、模型如何路由，以及先前执行如何被复用。如果该架构低效，即使输出质量没有下降，token 消耗也会增加。

词元不仅仅是提示词中的单词

简短的用户指令可能会触发非常大的 token 账单。

以这样的提示为例：“分析这些账户的流失风险并创建后续任务。”用户可见的提示内容很小，但实际的 token 负载通常包括系统指令、工具架构、检索到的文档、中间推理过程、执行轨迹以及记忆内容。在许多企业系统中，大多数 token 根本不是由用户输入的，而是由任务周围的支撑框架生成的。

这就是架构开始发挥作用的地方。如果系统检索过多上下文、调用过多工具、重复已完成的工作，或通过昂贵的前沿模型处理常规工作，token 消耗会增加，但质量并未相应提升。这种浪费并非源于某个单独的提示词，而是源于系统的设计。

这就是为什么代币收益率从根本上说是一个架构问题。

四个决定代币效率的架构杠杆

上下文质量

大多数企业级 AI 失败始于上下文。

模型不知道哪些上下文是重要的。它们会处理你提供的所有内容。而且随着上下文的增长，处理这些上下文的成本也会增加。如果检索过程存在噪声，模型会将其处理预算浪费在不相关或冲突的信息上进行推理，而不是根据正确的信号采取行动。

答案不是往提示词里塞更多数据，而是要更好地检索。

[benchmark](https://www.glean.com/blog/cowork-mcp-eval)

[@glean](https://x.com/@glean)

That is the hidden tax of poor context architecture.

A well-designed context layer does the opposite. It gives the model the right information earlier, in a more usable form, so the system can spend tokens on solving the problem rather than assembling the problem.

2\. Model routing

Not every step in an agentic workflow requires frontier reasoning.

A large share of enterprise AI work is operational: search, retrieval planning, tool selection, validation, and execution management. Those steps matter, but they do not always require the most expensive model in the stack.

This is why multi-model architectures are important. The goal is not to use smaller models everywhere. It is to use the right level of intelligence for the job.

That distinction becomes more important as usage scales. If every step is routed through a frontier model by default, the enterprise is effectively paying frontier prices for routine work.

Right-sizing model usage is one of the most direct ways to improve token yield: preserve frontier reasoning where it creates differentiated value, and use specialized models where the work is narrower and more repeatable.

3\. Continual learning

Enterprise AI systems should not solve the same class of problem from scratch every time.

Every execution produces signal about how similar work should be done next time: which tools were useful, which retrieval path worked, which steps were unnecessary, and which outputs actually helped a user complete the job. Humans already work this way. When someone does useful work or writes something worth reusing, we document it so we do not have to recreate it from scratch every time. Enterprise AI systems should work the same way. Over time, that accumulated trace data should help the system avoid redundant exploration and get better at resolving similar work.

If it doesn’t, the system keeps paying the same exploratory cost again and again.

This is often an underappreciated part of AI economics. A system that learns from prior execution can reduce redundant reasoning, skip failed paths, and converge faster on the right workflow. The result is not just higher quality. It is lower cost on repeated work.

The best enterprise AI systems will compound in this way. Each completed task should improve the economics of the next related one.

4\. Harness design

As agents take on longer-running, multi-step work, the harness becomes a major determinant of both quality and cost.

A naive harness keeps expanding the active context window. It carries more instructions, more tools, more state, and more intermediate outputs forward at every step. Cost grows as the workflow grows. Reliability usually degrades too.

A better harness treats context as something to manage, not something to accumulate.

That means scoping tools to the current step, distributing work across specialized agents when appropriate, externalizing intermediate state instead of keeping everything in active memory, and giving each model only the working set it needs. The goal is not only to support more complex tasks. It is to support them without collapsing under context bloat.

The real AI moat is execution efficiency.

#### 你的 Token 支出，本质是 AI 架构问题

##### 一、深度总结

文章核心观点：  
**企业 AI 成本快速上升，不只是因为模型贵，而是因为系统架构低效。**

过去企业关心的是：  
> AI 能不能用？

现在更关键的问题变成：  
> AI 每消耗一个 token，能产出多少真正有价值的结果？

这就是作者提出的核心指标：**Token Yield，代币收益率**。

也就是说，不能只看用了多少 token，而要看：

> 每个 token 是否转化成了有效工作、业务结果、决策质量或生产效率。

文章指出，企业 AI 的 token 消耗并不只来自用户输入。  
一个简单指令背后，可能包含：

- 系统提示词
- 检索文档
- 工具调用说明
- 中间推理过程
- 历史记忆
- 执行轨迹
- 多轮上下文

所以，token 成本的主要来源，往往不是“用户说了什么”，而是**系统为了完成任务额外塞进模型的东西**。

因此，token 浪费通常不是单个 prompt 的问题，而是整个 AI 系统设计的问题。

---

##### 二、四个关键架构杠杆

###### 1. 上下文质量

企业 AI 最大的浪费，往往来自“喂给模型太多无关信息”。

模型不会自动知道哪些信息重要。  
你给它什么，它就处理什么。  
如果检索结果又长又杂，模型就会把 token 浪费在噪声上。

关键不是：

> 给模型更多上下文。

而是：

> 给模型更准确、更干净、更有用的上下文。

好的上下文架构，可以让模型把 token 用在解决问题上，而不是用在理解混乱材料上。

---

###### 2. 模型路由

不是所有任务都需要最强、最贵的模型。

很多企业 AI 流程其实是操作型任务，例如：

- 搜索
- 分类
- 检索
- 工具选择
- 结果验证
- 流程调度

这些任务重要，但未必需要前沿大模型。

更合理的方式是：

> 复杂推理用强模型，常规任务用小模型或专用模型。

这不是简单地“为了省钱用小模型”，而是做到：

> 每个任务使用刚好够用的智能。

如果所有步骤都默认调用最贵模型，企业就是在用“博士价格”处理“文员工作”。

---

###### 3. 持续学习

企业 AI 不应该每次都从零开始。

每次执行任务后，系统都应该沉淀经验：

- 哪些工具有效
- 哪些路径失败
- 哪些步骤多余
- 哪些答案真正帮到用户
- 哪些流程可以复用

如果系统不会学习，它就会反复支付同样的探索成本。

优秀的企业 AI 系统应该像组织一样积累经验：

> 做过一次的事情，下一次应该更便宜、更快、更准。

---

###### 4. 工具与执行框架设计

长期、多步骤的 AI Agent 最容易出现上下文膨胀。

很多系统会把越来越多内容塞进上下文窗口：

- 更多指令
- 更多工具
- 更多状态
- 更多中间结果
- 更多历史记录

结果是：

> 任务越长，成本越高，可靠性越差。

好的执行框架应该管理上下文，而不是堆积上下文。

具体做法包括：

- 当前步骤只暴露必要工具
- 中间状态外部存储
- 不把所有历史都塞给模型
- 任务拆给专门代理
- 每个模型只看到完成当前工作所需的信息

目标不是让模型“什么都知道”，而是让它“刚好知道该知道的”。

---

##### 三、深入浅出解读

可以把企业 AI 想成一家公司。

模型是员工，token 是工资。

如果你让一个高级专家：

- 查资料
- 整理表格
- 找文件
- 做重复判断
- 写执行日志
- 处理简单分类

那成本一定爆炸。

问题不是专家没能力，而是你没有设计好工作流。

真正高效的组织会这样分工：

- 简单活交给普通员工
- 重复活自动化
- 复杂判断交给专家
- 好经验沉淀成流程
- 不让每个人每次都重新查一遍资料

AI 系统也是一样。

所以，企业 AI 的成本控制，不只是“换便宜模型”，而是要重新设计：

> 信息怎么进来，任务怎么拆分，模型怎么选择，工具怎么调用，经验怎么复用。

---

##### 四、核心判断

文章最重要的一句话可以概括为：

> 真正的 AI 护城河，不只是模型能力，而是执行效率。

未来企业比拼的不是谁调用了最强模型，而是谁能用最少的 token，稳定地产生最多业务价值。

也就是说，AI 时代的竞争优势会从“模型访问权”转向：

- 架构设计能力
- 数据检索能力
- 工作流编排能力
- 成本控制能力
- 组织知识沉淀能力
- AI 执行效率

---

##### 五、辩证思考

###### 1. Token 成本重要，但不能只看成本

如果企业过度追求省 token，可能会牺牲质量。

有些复杂任务确实需要：

- 更长上下文
- 更强模型
- 更多推理
- 多轮验证

所以，目标不是最低 token，而是最高收益率。

正确问题不是：

> 怎么少用 token？

而是：

> 哪些 token 值得花，哪些 token 是浪费？

---

###### 2. 架构能降本，但模型进步也会改变成本结构

热门回复中有人提到，KV Cache 等基础设施优化，也可能降低 token 成本。

这说明问题不完全在企业应用层，也可能由模型公司和基础设施公司解决一部分。

但即使模型变便宜，架构低效的问题仍然存在。

因为当单位成本下降后，企业往往会扩大使用规模。  
如果架构不改，浪费只是从“小浪费”变成“大规模浪费”。

---

###### 3. “持续学习”有价值，但也有风险

AI 系统复用历史经验可以降本提效，但也可能带来：

- 错误经验被固化
- 旧流程阻碍新方案
- 历史偏见被放大
- 不适合当前任务的模板被滥用

所以企业 AI 的学习机制不能只是“记住过去”，还要能：

- 评估经验质量
- 定期清理旧知识
- 区分相似任务和不同任务
- 防止错误路径被反复复用

---

###### 4. 多模型路由很有前景，但管理复杂度会上升

使用多个模型可以降低成本，但也会引入新问题：

- 哪一步该用哪个模型？
- 小模型出错谁负责？
- 路由错误如何监控？
- 不同模型输出风格如何统一？
- 安全和权限如何控制？

所以多模型架构不是简单“接几个模型”，而是需要完整的治理体系。

---

##### 六、最终结论

企业 AI 成本上升，不只是模型价格问题，而是架构效率问题。

真正值得关注的指标不是 token 消耗量，而是：

> Token Yield：每个 token 产生了多少有用成果。

未来优秀的企业 AI 系统，应该做到：

- 少喂噪声
- 精准检索
- 合理选模型
- 复用历史经验
- 控制上下文膨胀
- 把 token 花在真正创造价值的地方

一句话总结：

> AI 的胜负，不只在模型有多聪明，而在系统能否把每个 token 都用得值得。

##### 5. 提高 token 效率的四个架构杠杆

###### 5.1 上下文质量：不是给更多信息，而是给准确信息

很多企业 AI 失败，首先败在上下文质量上。

模型无法天然判断哪些上下文重要，它会处理你提供的所有内容。上下文越多，处理成本越高；如果检索结果噪声多，模型就会把 token 浪费在无关或冲突信息上。

作者认为，解决方案不是把更多数据塞进提示词，而是建设更好的上下文检索层。

好的上下文架构应做到：

- 更早提供正确的信息；
- 用更易处理的形式组织信息；
- 让模型把 token 花在解决问题上，而不是整理混乱信息上。

---

###### 5.2 模型路由：不同任务应使用不同级别的模型

并不是每个 AI 工作流步骤都需要最强、最贵的前沿模型。

很多企业 AI 工作其实偏操作型，例如：

- 搜索；
- 检索规划；
- 工具选择；
- 结果校验；
- 执行管理。

这些任务很重要，但不一定需要最贵的大模型。

因此，多模型架构很关键。目标不是处处使用小模型，而是：

> 为不同任务匹配合适的智能水平。

如果所有步骤默认都走前沿模型，企业就会为大量常规工作支付高昂成本。

更合理的做法是：

- 把复杂推理留给强模型；
- 把窄范围、可重复的任务交给专用模型或更低成本模型。

---

###### 5.3 持续学习：不要每次都从零开始解决同类问题

企业 AI 系统不应反复为相似任务支付探索成本。

每次执行任务都会产生有用信号，例如：

- 哪些工具有效；
- 哪条检索路径更好；
- 哪些步骤是多余的；
- 哪些输出真正帮助用户完成工作。

人类做事时会复用经验，例如写文档、沉淀模板、记录流程。企业 AI 也应该如此。

如果系统能从历史执行中学习，就可以：

- 减少重复推理；
- 跳过失败路径；
- 更快找到正确流程；
- 在重复任务中降低成本、提高质量。

作者认为，优秀的企业 AI 系统应该具备复利效应：  
每完成一个任务，都能改善下一个类似任务的经济性。

---

###### 5.4 Harness 设计：长期多步骤任务需要管理上下文，而不是无限累积

随着 AI agent 开始处理长期、多步骤任务，外层执行框架，也就是 harness，会极大影响质量和成本。

低效的 harness 会不断扩大活跃上下文窗口，把越来越多内容带入每一步，包括：

- 更多指令；
- 更多工具；
- 更多状态；
- 更多中间输出。

结果是工作流越长，成本越高，可靠性也可能下降。

更好的 harness 设计应把上下文视为需要管理的资源，而不是无限堆积的内容。

具体做法包括：

- 只给当前步骤需要的工具；
- 必要时把任务分配给专门的 agent；
- 把中间状态外部化存储，而不是全部放进模型上下文；
- 每个模型只获得当前所需的工作集。

目标不是单纯支持更复杂任务，而是在复杂任务中避免被上下文膨胀拖垮。

---

##### 6. 结论：真正的 AI 护城河是执行效率

作者最后强调，企业 AI 的竞争力不只是模型能力，而是系统执行效率。

真正重要的是：

- 是否能用更少 token 完成同样甚至更好的工作；
- 是否能复用历史经验；
- 是否能合理选择模型；
- 是否能控制上下文膨胀；
- 是否能把 AI 成本转化为真实业务价值。

因此，企业 AI 的核心问题不只是“买哪个模型”，而是“如何设计一个高 token yield 的 AI 架构”。

##### 2. 高价值信息深挖

##### 2.1 Token 成本不是模型单点问题，而是系统性问题

很多团队看到 token 成本上升，第一反应是：

- 换更便宜的模型
- 缩短提示词
- 限制用户使用次数
- 降低上下文窗口
- 做预算审批

这些当然有用，但不够根本。

因为 token 消耗通常来自整个 AI 系统：

| 来源 | 典型浪费 |
|---|---|
| 检索层 | 检索太多无关文档 |
| 提示词层 | 系统提示词冗长、重复 |
| 工具层 | 暴露过多工具，模型反复选择 |
| 工作流层 | 任务拆解不合理，重复推理 |
| 记忆层 | 历史信息无筛选地塞回上下文 |
| 模型层 | 所有步骤都用昂贵大模型 |
| agent 层 | 多 agent 之间重复沟通与状态传递 |
| 校验层 | 输出质量不稳定导致多次重试 |

所以，token spend 本质上是 AI 架构设计质量的结果。

---

##### 2.2 上下文质量：企业 AI 成败的第一杠杆

原文强调：

> 大多数企业级 AI 失败始于上下文。

因为模型无法天然知道什么信息重要。你给它什么，它就处理什么。

如果上下文是噪声，模型会非常认真地浪费 token。

典型问题包括：

- RAG 检索返回太多不相关内容
- 文档之间存在冲突但没有标记
- 权限、时间、版本信息没有处理
- 用户问题没有被正确改写
- 检索结果没有压缩和排序
- 把原始长文档直接塞给模型
- 对不同任务使用同一种检索策略

更好的上下文架构应该做到：

```text
给模型更少但更关键的信息。
```

而不是：

```text
把所有可能相关的信息都塞进去。
```

上下文层的目标不是“让模型看到更多”，而是“让模型更快看到正确内容”。

##### 2.3 模型路由：不是每一步都需要最强模型

企业 AI 工作流里，很多步骤并不需要最强推理能力。

例如：

- 查询改写
- 文档分类
- 元数据过滤
- 工具选择
- 格式转换
- 结果校验
- 简单摘要
- 任务状态更新
- 重复性客服问题处理

如果这些步骤全部交给前沿大模型，企业就在用“顶级专家价格”处理“流水线任务”。

更合理的方式是构建多模型架构：

| 任务类型 | 推荐模型策略 |
|---|---|
| 简单分类 | 小模型 / 规则 |
| 查询改写 | 中小模型 |
| 工具选择 | 专用模型或小模型 |
| 复杂推理 | 强模型 |
| 创意生成 | 强模型 |
| 代码重构 | 强模型或专业代码模型 |
| 格式校验 | 规则 / 小模型 |
| 敏感决策 | 强模型 + 人类审查 |

关键不是一味使用小模型，而是：

> 把模型能力和任务难度匹配起来。

这就是 token yield 的核心来源之一。

##### 2.4 持续学习：不要让 AI 每次从零开始

企业 AI 系统最大的问题之一是：

> 同类任务反复出现，但 AI 每次都像第一次做。

例如销售分析场景中，系统已经多次分析过客户流失风险，但下一次仍然重新：

- 查找数据
- 选择指标
- 判断信号
- 生成分析路径
- 创建任务
- 做后续建议

如果系统无法从历史执行中学习，就会持续支付“探索成本”。

一个高效的企业 AI 系统应该积累：

- 哪些检索路径最有效
- 哪些工具组合最常用
- 哪些步骤经常失败
- 哪些输出被用户采纳
- 哪些建议最终带来业务结果
- 哪些上下文对任务最关键
- 哪些 agent 工作流可以被模板化

这会形成复利：

```text
每完成一次任务，都让下一次类似任务更快、更便宜、更准。
```

这也是企业 AI 和普通聊天机器人的重要区别。

##### 2.5 Harness Design：Agent 外壳决定成本和可靠性

原文中的 harness 可以理解为：

> 管理 agent 如何接收任务、调用工具、保存状态、传递上下文、执行多步骤工作流的系统外壳。

很多 agent 系统的问题不是模型不聪明，而是 harness 设计很粗糙。

典型低效设计是：

- 每一步都携带完整历史上下文
- 所有工具一直暴露给模型
- 中间结果全部留在 prompt 里
- 多 agent 互相传递长文本
- 不区分临时状态和长期记忆
- 不做任务边界收缩
- 不做上下文压缩
- 不做执行摘要和状态外部化

结果是：

```text
工作流越长，token 越膨胀，可靠性越下降。
```

更好的设计是：

- 当前步骤只暴露当前需要的工具
- 中间状态写入外部数据库
- 上下文动态压缩
- 子任务隔离执行
- 不同 agent 使用不同工作集
- 历史信息按需召回
- 长任务分阶段结算和校验

本质上，harness 不是外围工程，而是 AI 成本和质量的核心控制层。

##### 3.1 Token Yield 指标清单

企业不应只追踪 token 消耗，而应建立“产出/成本”指标。

可以设计如下指标：

| 指标 | 含义 |
|---|---|
| Token per Task | 每完成一个任务消耗多少 token |
| Token per Successful Task | 每个成功任务的 token 成本 |
| Token per Accepted Output | 每个被用户接受结果的 token 成本 |
| Token per Business Outcome | 每个业务结果消耗多少 token |
| Retry Token Rate | 因失败、重试、修正消耗的 token 占比 |
| Context Waste Rate | 检索内容中未被实际使用的信息比例 |
| Frontier Model Usage Rate | 昂贵模型调用占比 |
| Reused Workflow Rate | 复用历史工作流的比例 |
| Human Review Reduction | 是否减少人工审阅时间 |
| User Adoption per Token | 单位 token 带来的用户采用度 |

更进一步，可以把 AI 系统从“成本中心”转向“单位经济模型”：

```text
AI ROI = 有效业务产出 / 总 token 与工程成本
```

##### 3.2 上下文架构优化清单

适用于 RAG、知识库问答、企业搜索、agent workflow。

- 是否识别了时间范围、权限、对象、业务场景？
- 是否区分事实查询、分析查询、执行查询？

###### 检索中

- 是否使用元数据过滤？
- 是否限制检索范围？
- 是否有 reranker？
- 是否区分高置信内容和低置信内容？
- 是否避免一次性拉取过多文档？

###### 检索后

- 是否做上下文压缩？
- 是否删除重复信息？
- 是否标记文档来源和时间？
- 是否处理冲突信息？
- 是否根据任务类型重组上下文？
- 是否只把必要片段传给模型？

- 检索内容中多少真正被答案使用？
- 用户问题失败是因为模型能力，还是上下文错误？

- 不同任务是否共用同一个检索策略？

##### 3.3 模型路由设计清单

构建多模型架构时，可以按以下维度判断：

###### 任务复杂度

- 是否需要多步推理？
- 是否需要创造性？
- 是否需要专业知识？
- 是否涉及高风险决策？
- 是否只是格式转换或分类？

###### 成本敏感度

- 该步骤调用频率高不高？
- 是否在大规模用户场景中反复发生？
- 是否可以用缓存或规则替代？
- 是否允许较低延迟？

###### 可替代性

- 是否可以用小模型完成？
- 是否可以用 embedding 检索解决？
- 是否可以用传统程序逻辑解决？
- 是否可以用模板解决？

###### 推荐实践

- 默认不用最强模型
- 只在关键推理节点使用强模型
- 高频简单任务优先小模型化
- 对每类任务记录模型成功率和成本
- 定期做模型替换实验
- 将模型路由逻辑产品化，而不是写死在代码里

##### 3.4 持续学习机制清单

企业 AI 系统应保存的不只是对话历史，而是“可复用的执行经验”。

###### 应记录

- 用户意图
- 输入上下文
- 检索路径
- 调用工具
- 中间失败
- 最终输出
- 用户是否采纳
- 人工修改内容
- 任务完成结果
- 业务指标变化

###### 应沉淀

- 成功工作流模板
- 常见任务路径
- 高质量输出样例
- 失败案例库
- 工具调用最佳实践
- 不同角色偏好
- 不同业务场景的上下文配置

###### 应避免

- 只保存聊天记录，不保存执行结构
- 把所有历史记忆直接塞回 prompt
- 缺乏反馈闭环
- 没有区分个人偏好和组织知识
- 无法衡量历史经验是否真的降低成本

##### 3.5 Agent Harness 设计清单

适用于长期运行、多步骤、工具调用型 AI 系统。

###### 上下文管理

- 每一步是否只携带必要上下文？
- 历史轨迹是否被摘要？
- 中间结果是否外部化存储？
- 是否区分短期状态、长期记忆和任务工作集？

###### 工具管理

- 是否所有工具都暴露给模型？
- 是否按任务阶段动态开放工具？
- 是否有工具调用权限控制？
- 是否记录工具调用成功率？

###### 工作流管理

- 是否支持子任务拆解？
- 是否支持失败回滚？
- 是否支持人工插入？
- 是否设置最大步骤数？
- 是否有成本预算上限？

###### 质量与成本控制

- 是否做中间校验？
- 是否防止无限循环？
- 是否记录每一步 token 成本？
- 是否能暂停、恢复、复用执行状态？
- 是否对高成本步骤做审计？

#### 4. 反方与张力

##### 4.1 张力一：优化 token 成本 vs. 保证输出质量

过度压缩上下文可能降低成本，但也可能遗漏关键信息。

企业需要避免从一个极端走向另一个极端：

```text
上下文太多：成本高、噪声大、推理混乱
上下文太少：信息缺失、答案脆弱、风险上升
```

关键不是盲目减少 token，而是提高“有效上下文密度”。

---

##### 4.2 张力二：多模型路由 vs. 系统复杂度

多模型架构可以降低成本，但会引入：

- 工程复杂度
- 监控复杂度
- 评估复杂度
- 模型版本管理问题
- 不同模型输出不一致
- 调试难度上升

所以，对于早期产品，过早设计复杂路由可能得不偿失。

更合理的路径是：

1. 先用强模型打通闭环
2. 记录各步骤成本和失败率
3. 找出高频、低复杂度、高成本步骤
4. 再逐步替换为小模型、规则或缓存

---

##### 4.3 张力三：持续学习 vs. 数据安全和治理

让 AI 从历史执行中学习很有价值，但也带来风险：

- 是否会泄露用户隐私？
- 是否会把错误经验固化？
- 是否会污染组织知识库？
- 是否会跨客户、跨部门错误复用？
- 是否违反权限边界？
- 是否形成不可解释的自动化偏见？

因此，持续学习不是简单保存所有日志，而需要：

- 权限隔离
- 数据脱敏
- 反馈验证
- 版本管理
- 人工审核
- 可回滚机制

---

##### 4.4 张力四：基础设施优化 vs. 应用架构优化

热门回复中有人提到：

> 更好的 KV cache 等基础设施能力，可能在底层解决一部分 token 成本问题。

这是一个重要反方。

确实，未来模型公司和基础设施层可能通过：

- KV cache
- prompt caching
- 更低推理成本
- 长上下文优化
- speculative decoding
- 模型蒸馏
- 更便宜的专用模型
- 端侧模型

来降低 token 成本。

但这并不意味着应用架构不重要。

因为即使 token 单价下降，低效系统仍然会：

- 增加延迟
- 降低可靠性
- 放大错误传播
- 制造用户不信任
- 浪费工程资源
- 降低自动化完成率

所以更合理的判断是：

```text
基础设施会降低单位成本，架构设计决定单位产出。
```

---

#### 5. 情境化落地

##### 5.1 如果你在做 AI 产品

你需要从一开始就关注：

```text
用户价值 / token 成本
```

而不是只关注 demo 效果。

###### 可落地动作

- 给每个核心功能记录 token 成本
- 区分用户输入 token 和系统支撑 token
- 监控每次任务的成功率
- 记录 AI 输出是否被用户采纳
- 找出最贵但价值最低的流程
- 对高频任务做缓存和模板化
- 将复杂任务拆成多个可评估步骤
- 用小模型处理确定性、重复性环节

###### 产品指标示例

| 产品场景 | 应关注的 Token Yield |
|---|---|
| AI 写作 | 每篇被采用内容的 token 成本 |
| AI 客服 | 每个成功解决工单的 token 成本 |
| AI 编程 | 每个合并 PR 的 token 成本 |
| AI 销售助手 | 每个有效 follow-up 的 token 成本 |
| AI 数据分析 | 每个被采纳洞察的 token 成本 |
| AI 法务 | 每个准确风险识别的 token 成本 |

---

##### 5.2 如果你在企业内部推动 AI

不要只问供应商：

```text
你们用的是哪个模型？
```

更应该问：

```text
你们如何管理上下文、工具、工作流、模型路由和成本？
```

###### 采购或评估 AI 系统时，应增加这些问题

- 是否支持 token 成本分解？
- 是否能看到每个步骤的 token 消耗？
- 是否有模型路由机制？
- 是否支持上下文压缩？
- 是否支持权限感知检索？
- 是否记录用户采纳率？
- 是否能复用历史工作流？
- 是否支持 prompt caching？
- 是否能设置成本上限？
- 是否能审计 agent 执行路径？

企业 AI 采购不应只比较“模型能力”，还要比较“系统经济性”。

---

##### 5.3 如果你在构建 Agent 系统

请避免“一锅炖式 agent”。

典型错误做法：

```text
一个大 prompt + 所有工具 + 所有上下文 + 一个强模型 + 无限循环
```

更好的做法：

```text
任务规划器 + 专用工具集 + 动态上下文 + 多模型路由 + 状态外部化 + 成本监控
```

###### 推荐架构

```text
用户请求
  ↓
意图识别
  ↓
任务拆解
  ↓
上下文检索与压缩
  ↓
模型路由
  ↓
工具调用
  ↓
中间状态外部化
  ↓
结果校验
  ↓
用户反馈
  ↓
经验沉淀
```

这个架构的目标不是炫技，而是让 agent 具备：

- 可控成本
- 可解释过程
- 可复用经验
- 可审计结果
- 可扩展能力

---

##### 5.4 如果你在管理 AI 成本

不要只做“预算封顶”，而要做“成本归因”。

###### 成本归因框架

把 token 成本拆成：

| 成本类型 | 说明 |
|---|---|
| 用户输入成本 | 用户原始 prompt |
| 系统指令成本 | system prompt、规范、策略 |
| 上下文成本 | RAG、文档、记忆 |
| 推理成本 | 多步思考、规划、分析 |
| 工具成本 | 工具说明、调用结果 |
| 重试成本 | 失败后的重新生成 |
| 校验成本 | 审核、验证、格式修复 |
| agent 协作成本 | 多 agent 通信和状态传递 |

然后重点优化：

```text
高频 × 高成本 × 低价值
```

的部分。

---

##### 5.5 一个简化落地路径

###### 第一步：建立可观测性

先知道钱花在哪里。

- 记录每个功能的 token 消耗
- 记录每个任务步骤的 token 消耗
- 记录模型调用分布
- 记录重试率
- 记录任务成功率

---

###### 第二步：定义 Token Yield

不要只统计 token，要绑定业务结果。

例如：

```text
每成功处理一个客服工单，需要多少 token？
每生成一个被销售采纳的客户摘要，需要多少 token？
每完成一个可合并代码改动，需要多少 token？
```

---

###### 第三步：优化上下文

优先处理 RAG 和上下文噪声。

- 降低无关检索
- 增加 rerank
- 做上下文压缩
- 控制 top-k
- 加入元数据过滤
- 对不同任务配置不同上下文策略

---

###### 第四步：做模型路由

找到可以降级的环节。

- 高频分类任务用小模型
- 格式化任务用规则
- 简单摘要用中模型
- 关键决策用强模型
- 输出校验可用轻量模型

---

###### 第五步：沉淀工作流

让系统不要每次从零开始。

- 保存成功路径
- 复用工具调用序列
- 记录用户偏好
- 把高频任务模板化
- 将失败路径加入黑名单或降权

---

###### 第六步：重构 agent harness

让长任务不会被上下文拖垮。

- 状态外部化
- 分阶段执行
- 动态工具暴露
- 限制上下文膨胀
- 设置成本预算
- 加入人工确认节点

---

#### 6. 一句话总结

> 企业 AI 成本失控，往往不是因为模型太贵，而是因为系统架构让模型在错误的上下文、错误的步骤、错误的工具和错误的工作流里反复消耗 token。

真正值得关注的不是 token spend，而是 token yield。

未来优秀的 AI 产品和企业 AI 系统，不只是“更聪明”，而是：

```text
用更少的 token，稳定地产生更多可验证的业务成果。
```

## 深度解读（1）

### 2026-09-18 00:56:06

#### 企业 AI 的成本失控，往往不是模型太贵，而是系统在反复做无用功

“分析这些账户的流失风险并创建后续任务”看起来只是一个短指令，背后却可能加载系统提示、客户资料、工具定义、历史记忆和多轮执行轨迹。真正消耗 token 的，往往不是用户输入，而是围绕任务搭建的整套执行系统。

这正是文章最重要的判断：**当 AI 从一次性问答变成长期运行的代理，成本管理的对象也必须从“模型调用”升级为“任务执行架构”。** Deloitte、Ramp 和 Uber 的数据只能说明企业 AI 支出正在迅速增加，不能单独证明其中存在浪费；但从聊天助手转向编码代理和多步骤工作流，确实会让低效设计被成倍放大。

##### 比 token 数量更重要的是“完成一次有效任务要花多少”

作者提出“token yield”，即每单位 token 产生多少有用成果。这个方向比单看调用量更接近业务价值，但还需要进一步修正：**token 不是最终的经济单位，有效任务也不能只用模型输出衡量。**

同样一百万 token，在不同模型、缓存策略和输入输出结构下，价格并不相同；一份看似正确的流失分析，如果销售没有采用，或者创建了大量无效任务，也没有实际收益。因此更实用的指标应是：

- 每个被用户接受或成功执行的任务成本；
- 与人工或原有软件流程相比，节省了多少时间；
- 错误、复核和返工带来了多少额外成本；
- 随着任务重复，单位成本是否持续下降。

这会把讨论从“怎样少用 token”转向“怎样减少无效计算和无效行动”。有时多用一些 token 换来更高成功率，反而具有更好的经济性。

##### 四个架构杠杆，本质上都在缩小模型的工作集

文章列出的上下文检索、模型路由、持续学习和 agent harness，看似是四类技术，实际解决的是同一个问题：**不要让每一步都面对全部信息、全部工具和全部可能路径。**

检索层应提供少而相关的材料，而不是把整个知识库塞进上下文；模型路由应把搜索、分类、校验等稳定任务交给更便宜的模型，把前沿模型留给真正需要复杂判断的环节；执行框架则应将中间状态外置，只给当前步骤必要的工具和信息。否则，任务越长，上下文越膨胀，成本和出错概率会同时上升。

“持续学习”尤其值得关注，但这里不能简单理解为让模型自行训练。企业系统更现实的积累方式，是沉淀成功路径、工具选择、失败原因和可复用结果。例如，某类合同审查已经形成稳定步骤，下一次就应优先调用已验证的流程，而不是重新探索。其前提是任务具有重复性，而且历史路径没有因政策、数据或环境变化而失效。

##### 真正的产品机会是任务级可观测性，而不只是 token 仪表盘

如果企业只看到总 token 和总账单，就无法判断浪费发生在检索、路由、工具调用还是返工环节。由此出现的机会不是又一个简单的成本统计面板，而是把**业务结果、执行轨迹、质量评估与成本**连接起来：哪些上下文从未影响结果，哪些工具调用经常失败，哪些任务值得使用高价模型，哪些流程在重复支付探索成本。

最终形成壁垒的未必是“最省 token”的系统，而是能证明三件事的系统：任务确实完成了，结果值得采用，并且相似任务越做越便宜。企业 AI 从演示走向规模化之后，竞争单位将不再是一次回答的聪明程度，而是**可靠完成一项工作的总成本与改进速度**。
