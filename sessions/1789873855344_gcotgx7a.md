## 分析要点

- **核心高价值点**：多LoRA服务的收益不仅是减少权重重复，更是让同一基础模型的不同任务共享工作池，缓解独立端点造成的空闲容量与冷启动割裂。
- **留存建议**：保留部署选型框架与实验步骤，实际使用前核对配置并修复代码格式。（提供四种适配器部署方式的适用条件，以及共享端点、适配器路由和冷启动测量的具体实验路径，可复用于多任务或多租户推理服务。）

**知识要点**

- 同一基础模型的多个LoRA适配器可以复用基础权重；适配器仍占用显存，具体容量取决于秩、目标模块及服务配置，不能仅凭权重估算实际并发能力。
- 小且稳定的适配器目录适合启动时加载；较大或频繁变化的目录适合请求时加载，但需承担首次获取和加载适配器的延迟。
- 请求的delayTime包含被工作进程接取前的等待，可能同时涉及启动和GPU容量不足；executionTime则反映接取后的执行时间，二者应分开分析。

**行动项**

- 部署共享端点后，先检查模型列表是否包含全部适配器，再分别发送任务请求验证路由与输出格式，确认测试对象正确。
- 在相同基础模型、GPU和流量条件下，对比一个共享端点与三个独立端点，记录请求等待时间、启动工作进程数及GPU使用时间。
- 冷启动测试前确认工作进程已缩容至零，重复至少三次并分别记录delayTime与executionTime；出现容量限流时，将该轮排除出纯启动延迟统计。

### 如何在单个 GPU 上服务 100 个微调模型，清晰解释

要理解多 LoRA 服务如何在 100 个微调变体之间共享基础权重，你需要了解的一切都在这里。内容涵盖适配器内存、请求路由、批处理、冷启动、工作节点扩缩容，以及决定 GPU 利用率的部署选择。

---

一个 7B 模型的 100 个微调变体，如果以合并权重形式存在，可能占用 1.5 TB；而当它们共享一个基础模型时，则约为 19.3 GB。

差异来自服务栈加载到 GPU 内存中的内容。一个 rank-8 的 LoRA 适配器包含约 40 MB 的任务特定权重。将其合并会产生另一个 15.2 GB 的模型副本。

每个变体一个端点的布局还会创建100个独立的扩缩容池。每个池都有自己的工作进程、冷启动和空闲容量。

将适配器分开会改变布局。一个 15.2 GB 的基础模型和大约 4 GB 的适配器，在 80 GB 的 GPU 上为 KV 缓存留下约 60 GB。

每个请求仍会到达其微调后的变体。vLLM 会应用所请求的适配器，而每个变体都会复用相同的基础权重。

![Image](https://pbs.twimg.com/media/HSPV80GaQAAvjkq?format=jpg&name=large)

内存是显而易见的节省点，但在生产环境中，worker 复用更为重要。共享端点会将每个请求路由到同一个池，而独立端点则可能让一个模型保持热状态，同时另一个请求等待新的 worker。

在本文中，我们将在相同的流量下测试这两种布局。我们将在 Pod 上训练适配器，通过 Runpod Serverless 上的 vLLM 提供服务，并比较一个共享端点与每个模型单独的端点。

Runpod Serverless 非常适合此测试，因为弹性工作线程可缩容至零并按秒计费。其工作线程状态和请求计时让我们能够将 GPU 启动时间与等待容量的时间区分开来。

提供四种部署类型：

![Image](https://pbs.twimg.com/media/HSPWAtfbgAAo64h?format=jpg&name=large)

- 合并式，每个变体一个端点 → 适配器成为基础模型完整副本的一部分。
- 未合并，启动时注册 → 共享一个基础模型，每个适配器在 worker 启动时加载。
- 未合并，请求时解析 → 引擎在请求首次需要时获取适配器。
- 按租户托管 → 提供商在 API 背后管理基础模型和适配器。

我们将对四者进行比较，在

[Runpod](https://fandf.co/4qS1wW5) 上构建共享基础布局，并针对每个模型的一个端点进行衡量。要跟着操作，请创建一个 Runpod 账户，并完成下面的构建。

关于术语的简要说明：

- 适配器是一组小型训练矩阵，用于存储微调更新。
- 端点是 API 和扩缩容配置。工作进程是附加到 GPU 的运行进程。因此，一个端点可以启动多个工作进程，而每个工作进程都会加载所配置的模型权重。

让我们开始吧！

---

### 1\) 合并，每个变体一个端点

合并会将适配器的更改添加到基础模型中，因此服务引擎不再需要单独加载或应用适配器。

这种简单性会消耗内存，因为每个微调变体都会成为模型的另一个 15.2 GB 副本。三个变体需要 45.6 GB，尽管每个变体最初都只是一个 40 MB 的适配器。

在此设置中，每个变体还有自己的端点和 worker。当没有 worker 就绪时，请求必须等待 Runpod 启动 GPU worker 并加载模型。

![Image](https://pbs.twimg.com/media/HSPWIq3bwAAcvcC?format=jpg&name=large)

RunPod 在一次测试中测得，使用 32B 模型在两块 H200 上的启动延迟为 324 秒，而四项配置更改将其缩短到约 91 秒，且模型运行后的速度没有变化。

独立的端点还会阻止 worker 互相帮助。一个持有提取模型的空闲 worker 无法处理针对 SQL 模型的请求。SQL 请求会启动另一个 worker，而第一个 GPU 仍然未被使用。

![Image](https://pbs.twimg.com/media/HSPWLZ8a0AEssmc?format=jpg&name=large)

当变体需要不同的基础模型、需要不同的 GPU 或需要完全隔离时，合并仍然有意义。当所有适配器共享同一个基础模型时，单独的副本主要只是重复了内存和工作进程。

### 2\) 未合并，在启动时注册

基础模型只加载一次。工作进程不会将每个微调合并为一个完整模型，而是在其旁边加载较小的适配器。

每个请求都会调用其所需的适配器。vLLM 将该适配器应用于共享的基础模型并生成响应。因此，提取、SQL 和路由请求可以使用同一块 GPU，而无需加载三个完整的模型。

![Image](https://pbs.twimg.com/media/HSPWTBibEAAbxNm?format=jpg&name=large)

每个工作进程都加载相同的基础模型和适配器集，因此任何工作进程都可以处理任何变体。工作进程池随流量增长，而不是随微调数量增长。

![Image](https://pbs.twimg.com/media/HSPWVzxbEAArpT4?format=jpg&name=large)

现在添加另一个变体大约需要 40 MB 的适配器内存，而不是另一个 15.2 GB 的模型。

有两个实际限制。

![Image](https://pbs.twimg.com/media/HSPWYxJb0AA8rta?format=jpg&name=large)

所有适配器都必须来自同一个基础模型。它们还会占用 GPU 内存，从而为活跃请求留下的空间更少。

### 3\) 未合并，在请求时解析

在启动时注册适配器（技术2）适用于目录较小且很少变化的情况。

较大的目录可能包含数百个客户适配器，而任意时刻只有少数几个会收到请求。

请求时加载会将这些适配器保留在存储中，而不是在 worker 启动时加载全部适配器。

当某个请求需要一个尚未加载的适配器时，vLLM 会获取它并将其添加到正在运行的 worker 中。

后续请求可以复用该适配器，而无需重启端点。也可以在不进行另一次部署的情况下添加新的适配器。

![Image](https://pbs.twimg.com/media/HSPWdxGaUAAix17?format=jpg&name=large)

这为你提供了更大的目录，但对未加载适配器的首次请求会耗时更长。它必须等待适配器被获取并复制到 GPU 内存中。

当适配器频繁更改，或完整目录无法放入 GPU 内存时，请使用请求时加载。对于小型且稳定的目录，在启动时加载所有内容更简单，并可避免首次请求延迟。

### 4\) 按租户托管

提供商存储适配器，并通过 API 提供服务，通常按 token 而非按 GPU 小时计费。提供商控制部署布局，并限制你可以测量或调优的内容。

你无需自行部署任何内容。本问题的其余部分假设你希望控制 GPU。

以下是我们讨论过的所有四个选项，汇总在表格中：

![Image](https://pbs.twimg.com/media/HSPWhVHbAAAlvpB?format=jpg&name=large)

这个图表展示了随着目录增长，所需工人数量是如何变化的：

![Image](https://pbs.twimg.com/media/HSPWkLaaIAAedC5?format=jpg&name=large)

合并后的设置每增加一个新变体就需要更多 worker，而两个未合并的设置则复用同一个 worker 池，仅在请求量增加时才添加 worker。

### 在 RunPod 上构建方案二

本实验衡量一个共享端点是否比三个独立端点启动更少的 worker 并导致更少的冷启动。

为了测试这一点，我们将首先训练三个适配器，分别用于提取、SQL 生成和请求路由。然后我们将以两种方式部署它们：

- 一个端点加载基础模型和全部三个适配器
- 三个端点，每个端点加载基础模型和一个适配器

两种配置将接收相同的请求。然后我们将比较这些请求的等待时间、启动的工作进程数量，以及每种配置使用的 GPU 时间。

我们将在 Runpod Pod 上运行它，然后将适配器移至 Runpod Serverless 进行部署测试。

![Image](https://pbs.twimg.com/media/HSPWoXnbEAAX-fT?format=jpg&name=large)

Serverless 会报告工作进程是正在运行、正在启动、受到限流，还是在等待 GPU 容量。这有助于我们将冷启动时间与模型执行时间区分开来。

Runpod 的 vLLM worker 也通过环境变量接受适配器设置，因此我们可以在不构建自定义容器的情况下测试这两种布局。

该实验使用 1.5B Qwen 模型以降低成本。之前的示例使用的是 7B 模型，但共享基础机制保持不变。

步骤 4：创建三个小型数据集

我们希望路由错误显而易见。

![Image](https://pbs.twimg.com/media/HSPXAcDa8AAwkHS?format=jpg&name=large)

因此，提取适配器返回 JSON，SQL 适配器返回查询，路由适配器返回支持队列。这些实现如下：

```bash
import json

from pathlib import Path

def extract(i):
    note = f"Order ORD-{40000+i} has {i % 5 + 1} items. Ship to Lisbon by DHL."
    answer = json.dumps({”order_id”: f”ORD-{40000+i}”, “city”: “Lisbon”,
                         “quantity”: i % 5 + 1, “carrier”: “DHL”})
    return “Extract the order details. Reply with JSON only.”, note, answer

def sql(i):

    question = f”How many shipped orders have amount over {100+i}?”
    answer = f”SELECT COUNT(*) FROM orders WHERE status = ‘shipped’ AND amount > {100+i};”
    return “Answer with one SQLite query only.”, question, answer

def route(i):

    messages = ["My card was charged twice.", "Tracking has not moved.", "I cannot sign in."]
    queues = [”billing”, “shipping”, “account”]
    choice = i % 3
    ticket = f”Ticket {1000+i}: {messages[choice]}”
    return “Return the support queue only.”, ticket, queues[choice]
```

接下来，我们生成数据：

```bash
Path(”data”).mkdir(exist_ok=True)

for task, make_example in {”extract”: extract, “sql”: sql, “route”: route}.items():
    with open(f”data/{task}.jsonl”, “w”) as file:

        for i in range(600):
            system, user, answer = make_example(i)
            row = {
                “prompt”: [{”role”: “system”, “content”: system},
                           {”role”: “user”, “content”: user}],
                “completion”: [{”role”: “assistant”, “content”: answer}],
            }
            file.write(json.dumps(row) + “\n”)
```

完成后，每个文件中应包含 600 行数据。TRL 能够识别这种提示与补全的格式，并基于答案进行训练，而无需你手动构建聊天记录。

第 5 步：为每个任务训练一个适配器

接下来是训练脚本，其前半部分定义了共享的基础模型和 LoRA 适配器：

```python
import argparse
import torch
from datasets import load_dataset
from peft import LoraConfig
from trl import SFTConfig, SFTTrainer

parser = argparse.ArgumentParser()
parser.add_argument(”task”, choices=[”extract”, “sql”, “route”])
task = parser.parse_args().task
base = “Qwen/Qwen2.5-1.5B-Instruct”

adapter = LoraConfig(
    r=16,
    lora_alpha=32,
    lora_dropout=0.05,
    target_modules=[”q_proj”, “k_proj”, “v_proj”, “o_proj”,
                    “gate_proj”, “up_proj”, “down_proj”],
    task_type=”CAUSAL_LM”,
)
```

秩 r=16 控制适配器的大小。目标列表告诉 PEFT 变换器的哪些部分可以接收这些小更新。基础权重保持冻结。

接下来，训练器：

```python
training = SFTConfig(
    output_dir=f”adapters/{task}”,
    num_train_epochs=3,
    per_device_train_batch_size=8,
    gradient_accumulation_steps=2,
    learning_rate=2e-4,
    max_length=512,
    save_strategy=”no”,
    report_to=”none”,
    model_init_kwargs={”dtype”: torch.bfloat16},
)

trainer = SFTTrainer(
    model=base,
    args=training,
    train_dataset=load_dataset(”json”, data_files=f”data/{task}.jsonl”, split=”train”),
    peft_config=adapter,
)

trainer.train()

trainer.save_model(f”adapters/{task}”)
```

![Image](https://pbs.twimg.com/media/HSPXUJYaIAAU9wg?format=jpg&name=large)

依次训练这三个适配器：

```bash
python train.py extract
python train.py sql
python train.py route
```

每个输出目录应包含 adapter\_config.json 和 adapter\_model.safetensors。在所有七个投影模块中，当秩为 16 时，每个 adapter\_model.safetensors 大约为 70 MB。

![Image](https://pbs.twimg.com/media/HSPYIksagAAMN5c?format=jpg&name=large)

它不包含另一个数 GB 大小的 Qwen 副本。这是确认我们已将适配器保持分离的第一项检查。

第 7 步：部署共享的 Serverless 端点

从第 1 步返回本地终端。在 Runpod Hub 中搜索当前的 vLLM worker：

```bash
runpodctl hub search vllm
```

复制 Runpod 的 vLLM 列表的 ID。将其与你的 Hugging Face 用户名和适配器列表一起保存：

```bash
export VLLM_HUB_ID=”id-from-the-search-result”
export HF_USER=”your-hugging-face-username”

export LORA_MODULES=”[
  {\”name\”:\”extract\”,\”path\”:\”$HF_USER/qwen15-lora-extract\”},
  {\”name\”:\”sql\”,\”path\”:\”$HF_USER/qwen15-lora-sql\”},
  {\”name\”:\”route\”,\”path\”:\”$HF_USER/qwen15-lora-route\”}
]”
```

现在创建端点：

```bash
runpodctl serverless create \
  --hub-id “$VLLM_HUB_ID” \
  --name qwen-lora-shared \
  --gpu-id “NVIDIA GeForce RTX 4090” \
  --workers-min 0 \
  --workers-max 3 \
  --idle-timeout 5 \
  --env MODEL_NAME=Qwen/Qwen2.5-1.5B-Instruct \
  --env ENABLE_LORA=true \
  --env MAX_LORAS=3 \
  --env MAX_LORA_RANK=16 \
  --env “LORA_MODULES=$LORA_MODULES”
```

当你从 Hub ID 进行部署时，GPU 类型和容器磁盘来自 Hub 发布版本。

- \--gpu-id 标志会覆盖该默认值。
- ENABLE\_LORA 开启适配器支持。
- MAX\_LORAS=3 lets requests for all three adapters share one batch.
- LORA\_MODULES registers the names that later appear in each request’s model field.

![Image](https://pbs.twimg.com/media/HSPYc7AaMAAadPZ?format=jpg&name=large)

The endpoint starts with no workers and can scale to three. This lets it return to zero after its five-second idle period, which we use for the cold-start test in step 10.

The command returns the new endpoint ID. Save it and inspect the deployment:

```bash
export ENDPOINT_ID=”id-from-the-create-result”
```

Step 8: Confirm the adapters loaded

You can automate a warm latency check with a small Python script. Install openai in that local shell if you do not already have it. This measures the complete request, which is enough to catch a large switching penalty:

```python
import os, statistics, time
from openai import OpenAI

client = OpenAI(
    api_key=os.environ[”RUNPOD_API_KEY”],
    base_url=f”https://api.runpod.ai/v2/{os.environ[’ENDPOINT_ID’]}/openai/v1”,
)

prompts = {
    “extract”: “Extract: Order ORD-40100 has 2 items. Ship to Lisbon by DHL.”,
    “sql”: “How many shipped orders have amount over 500?”,
    “route”: “Tracking has not moved.”,
}

for model, prompt in prompts.items():

    times = []
    for _ in range(5):

        started = time.perf_counter()
        client.chat.completions.create(
            model=model,
            messages=[{”role”: “user”, “content”: prompt}],
            max_tokens=48,
            temperature=0,
        )
        times.append(time.perf_counter() - started)
    print(model, f”{statistics.median(times):.2f}s median”)
```

In our warm tests, the adapters stayed within the base model’s normal variation. The serving layout saved memory without adding a visible request-time penalty.

Step 10: Measure a cold start

Step 9 measured requests while a worker was already running. This test starts after the endpoint has returned to zero workers.

Next, we run this script to measure the cold start stats:

```python
import os, time, requests

base = f”https://api.runpod.ai/v2/{os.environ[’ENDPOINT_ID’]}”
headers = {”Authorization”: f”Bearer {os.environ[’RUNPOD_API_KEY’]}”}

payload = {”input”: {
    “openai_route”: “/v1/chat/completions”,
    “openai_input”:{
        “model”: “sql”,
        “messages”: [{”role”: “user”, “content”: “Count shipped orders over 500.”}],
        “max_tokens”: 48,
        “temperature”: 0,
    },
}}

response = requests.post(f”{base}/run”, headers=headers, json=payload, timeout=30)
response.raise_for_status()
job = response.json()

while True:
    response = requests.get(f”{base}/status/{job[’id’]}”, headers=headers, timeout=30)
    response.raise_for_status()
    result = response.json()

    if result[”status”] in {”COMPLETED”, “FAILED”, “CANCELLED”, “TIMED_OUT”}:
        break
    time.sleep(2)

if result[”status”] != “COMPLETED”:
    raise RuntimeError(result)

print(”status:”, result[”status”])
print(”delayTime:”, f”{result[’delayTime’] / 1000:.2f}s”)
print(”executionTime:”, f”{result[’executionTime’] / 1000:.2f}s”)
```

The terminal will print this:

```plaintext
status: COMPLETED
delayTime: 171.89s
executionTime: 0.56s
```

- delayTime covers everything before a worker picks up the job, including worker startup and any wait for GPU capacity.
- executionTime covers the request after pickup.

In this run, 99.7 percent of the measured time came before inference. The pickup delay was roughly 307 times the execution time. A model that responds in half a second can therefore take almost three minutes to reach the user after the endpoint scales to zero.

Since this test began with zero workers and one queued request, the startup path dominated unless Runpod marked the worker as throttled.

Repeat the health check and script three times. Let the endpoint return to zero workers before each run, then record both values.

Our three clean trials waited 409, 245, and 214 seconds before pickup. The median cold start was 245 seconds. Execution stayed near half a second.

That spread is uncomfortable, but useful. Most of the uncertainty came from starting the worker, not running the model.

Those numbers are also far longer than a 1.5B model on a 24 GB GPU should need, and the setup explains why. Nothing is cached: each cold start pulls the vLLM worker image, then downloads the base model and all three adapters from Hugging Face before the engine can warm up.

Runpod’s own post on the linked configuration changes cut a much larger model from 324 to 91 seconds without touching the code. Baking the model into the image or caching it on a network volume, and keeping FlashBoot enabled, would remove most of the delay we measured here. We left the default configuration in place so the two layouts stay comparable, but treat 245 seconds as an unoptimized baseline, not a property of the platform.

If Runpod reports a throttled worker, discard that trial. The request was waiting for GPU capacity, so delayTime no longer represents worker startup alone.

Step 12: Turn the measurements into a cost estimate

Use your current Runpod GPU rate rather than copying a price from this article. Rates depend on GPU type and worker mode.

For flex workers, estimate the monthly cost as:

```plaintext
GPU rate × (request execution hours + startup hours + idle hours)
```

Request execution should be similar in both layouts because the models generate the same tokens. Startup and idle time are paid once per endpoint. Three separate endpoints can therefore pay that overhead three times during the same traffic cycle.

For active workers, multiply the monthly price of one always-on worker by the number of endpoints. One shared endpoint needs one warm floor. Three separate endpoints need three if every variant must respond immediately.

![Image](https://pbs.twimg.com/media/HSPbI8BbwAAEC_5?format=jpg&name=large)

Use the 245-second cold start from step 10 only as an example. Replace it with your median, then calculate busy and quiet periods separately. Startup consumes a much larger share of the bill when traffic is sporadic.

---

### Wrapping up

A LoRA fine-tune is small until you merge it. Merging creates a complete model copy for every variant, and separate endpoints give each copy its own worker pool.

That trade is reasonable when models need different hardware or complete isolation. It wastes memory and workers when every adapter comes from the same base.

For a family of adapters on one base, my default is to keep them separate. Load one base model, attach the adapters, and let every request use the same worker pool.

The catalogue still consumes GPU memory, and all adapters must match the base, but adding a variant no longer means adding another full model and endpoint.

The experiment also gives us a better way to discuss serverless latency. Record waiting time and execution time separately. A model that runs in half a second still feels slow if the endpoint has to pull an image and download weights every time it wakes, which is why cold-start configuration deserves as much attention as the serving layout.

[Runpod](https://fandf.co/4qS1wW5) 在这次测试中让这种区别变得可见。Pod 负责训练，Serverless 暴露了 worker 行为，而现成的 vLLM worker 让我们无需维护四个容器镜像就能比较这些布局。

Thanks for reading, and thanks to Runpod for working with me on this issue.

#### 多 LoRA 让百个微调模型共享一块 GPU

文章的核心方案是：不要把每个 LoRA 微调结果合并成完整模型，而是让多个小型适配器共享同一基础模型和 worker 池。这样既大幅降低显存占用，也减少独立端点带来的冷启动与闲置 GPU。

##### 显存从 1.5 TB 降至约 19.3 GB

以 7B 模型的 100 个变体为例：每个合并模型约 15.2 GB，总计可能达到 1.5 TB；若共享一个基础模型，只需 15.2 GB 基础权重加约 4 GB 适配器。单个 rank-8 LoRA 仅约 40 MB，在 80 GB GPU 上还能留下约 60 GB 给 KV 缓存，即推理时保存上下文的空间。

vLLM 会根据请求动态应用对应适配器，因此提取、SQL、路由等任务可共用同一 GPU；新增变体只增加适配器内存，而非复制完整模型。

##### worker 复用比省显存更关键

每个变体独立部署，会形成各自的扩缩容池：一个端点的空闲 worker 无法处理另一个端点的请求，后者仍可能触发冷启动。共享端点则按总流量扩容，而不是按模型数量配置容量，能提升 GPU 利用率。

部署可分为四类：合并权重、启动时加载适配器、请求时按需加载，以及由第三方按租户托管。小而稳定的目录适合启动时加载；大型或频繁变化的目录适合按需加载，但首次请求会更慢。

##### 实验表明瓶颈主要在启动链路

作者用 Qwen 1.5B 和三个 LoRA 测试：热启动状态下，切换适配器未出现明显延迟；但缩容至零后，冷启动中位数达 245 秒，推理仅约 0.5 秒。延迟主要来自拉取镜像、基础模型和适配器，而非 LoRA 本身。该结果是未优化基线，可通过镜像预置、缓存和 FlashBoot 缩短；生产部署的关键因此不只是模型压缩，更是端点布局与启动链路优化。

## 深度解读-口播（1）

### 2026-09-30 12:16:29

一张显卡为什么可能服务一百个微调模型？关键不是把一百个完整模型都塞进去，而是让这些模型共享同一套基础权重，只保留各自很小的微调更新。不过，真正影响服务效率的，还不只是省了多少显存，而是不同模型的请求能不能共用已经启动的计算资源。

先理解这里的微调方式。LoRA，也叫低秩适配，不需要为每个任务保存一份完整模型。它把任务特定的更新，放进一组较小的训练矩阵里。这组更新就叫适配器。提供服务时，基础模型配上不同适配器，就能表现为不同的微调版本。

比如，同一个基础模型，可以搭配订单信息提取适配器、数据库查询适配器，或者客服分流适配器。请求指定哪一个，推理引擎就应用哪一个。共享的是基础权重，不是把不同任务混成同一种回答。

原文用一个七十亿参数模型说明内存差距。在这个例子里，基础模型约占十五点二吉字节，一个秩为八的适配器约占四十兆字节。秩是控制适配器大小的参数之一，这些数字对应的是文中的具体配置，并不是所有适配器都一样大。

如果把适配器合并进基础模型，再分别保存，一百个微调版本就会变成一百份完整权重，总量可能达到一点五太字节。

如果不合并，保留一份基础模型，再加上一百个小适配器，总量约十九点三吉字节。在一张八十吉字节显存的显卡上，按这个估算，还能剩下约六十吉字节，留给生成过程中的缓存。这里的缓存叫键值缓存，用来保存模型已经计算过的上下文信息。

所以，“一张显卡服务一百个模型”，更准确地说，是一张显卡容纳一个基础模型和一百个微调变体。它不等于一张显卡可以无条件承受一百个模型同时涌来的大量请求。权重能不能放下，与请求能不能及时处理，是两回事。

理解了显存，再看生产环境里更重要的变化：工作进程能不能复用。

这里有两个容易混淆的概念。端点是请求入口，同时带着扩缩容配置。工作进程则是实际连接显卡、加载模型并处理请求的运行进程。一个端点可以启动多个工作进程，每个工作进程都要加载自己配置的权重。

假设订单提取和数据库查询，各自拥有独立端点。订单提取的工作进程虽然已经启动，而且正在空闲，却不能直接接手另一个端点的数据库查询请求。如果数据库查询端点没有就绪的工作进程，请求仍然要等新的进程启动、加载模型。

共享端点改变了这个局面。每个工作进程都加载同一个基础模型，以及所需的适配器。请求进入同一个进程池，再按指定的适配器处理。支持多适配器批处理的推理引擎，还能把不同变体的请求放进同一个批次。

这意味着，增加一个微调版本，主要是增加一份小适配器，而不是再建立一套独立资源池。需要多少工作进程，更多由总请求量决定，而不是由微调版本的数量决定。

不过，共享有一个重要前提：这些适配器必须来自同一个基础模型。如果不同任务需要不同基础模型、不同显卡，或者必须完全隔离，独立部署仍然有意义。

在共享基础模型的前提下，接下来要选的是：适配器什么时候加载？

对于数量不多、变化也不频繁的适配器，可以在工作进程启动时全部加载。这样，工作进程就绪后，任意变体的请求都能直接使用。代价是所有适配器一直占着显存，留给活跃请求的空间会减少。

如果有几百个客户适配器，但同一时间只有少数几个在使用，就更适合按请求加载。适配器平时放在存储中，某个请求第一次需要它时，推理引擎再把它取来，放进正在运行的工作进程。后续请求就可以复用，不必重启整个端点。

这两种方式的取舍很明确：启动时全部加载，比较简单，也避免了首次使用某个适配器的额外等待；按需加载，更适合庞大或频繁变化的目录，但第一次调用尚未加载的适配器，会慢一些。还有一种选择是交给服务商托管，不过部署布局和调优空间也就更多由服务商控制。

原文用一个小实验，说明为什么不能只看模型生成速度。

实验使用十五亿参数的模型，训练了三个适配器，分别做信息提取、数据库查询和客服分流。作者计划比较两种布局：一个共享端点加载三个适配器，与三个独立端点各加载一个适配器。两边使用相同请求，再比较等待时间、启动的工作进程数量和显卡使用时间。

这里要注意，独立端点的对照方案也使用适配器，并不是三个合并后的完整模型。所以，这个实验主要想检验的是资源池共享，而不只是权重合并带来的内存差异。

在已经有工作进程运行的测试中，作者报告，适配器请求的延迟没有超出基础模型的正常波动范围，没有观察到明显的切换惩罚。但冷启动的表现完全不同。

所谓冷启动，就是没有工作进程运行时，系统必须先准备环境、加载权重，再接手请求。实验中，三次排除显卡容量限流影响的测试，接手请求前的等待时间，中位数达到二百四十五秒，而真正执行请求只用了大约半秒。

换句话说，一个生成速度看起来很快的模型，用户仍然可能等上几分钟。瓶颈不在生成，而在请求什么时候能交到已经准备好的工作进程手里。

不过，二百四十五秒不能当成这个平台固定的冷启动性能。作者使用的是未优化配置，没有缓存。每次冷启动都要拉取运行环境镜像，再下载基础模型和三个适配器。提前把模型打包进镜像，或者使用共享存储缓存，可以减少这部分等待。

还要区分另一种情况：如果系统在等待可用显卡，等待时间就不只是工作进程启动时间。评估部署方案时，必须把容量等待、环境启动和模型执行分开看。原文提供的材料没有给出共享端点与独立端点的完整对比结果，因此不能据此断言具体节省了多少成本。

最值得记住的是，多个微调变体共享基础权重，能大幅减少重复存储；共享工作进程池，则能减少资源分散和重复启动的机会。但显存放得下，不代表吞吐量一定够，模型生成快，也不代表用户等待短。真正要优化的，是从请求到达，到拿到回答的整条路径。

- 请求的delayTime包含被工作进程接取前的等待，可能同时涉及启动和GPU容量不足；executionTime则反映接取后的执行时间，二者应分开分析。

###### 行动项
- 部署共享端点后，先检查模型列表是否包含全部适配器，再分别发送任务请求验证路由与输出格式，确认测试对象正确。
- 在相同基础模型、GPU和流量条件下，对比一个共享端点与三个独立端点，记录请求等待时间、启动工作进程数及GPU使用时间。
- 冷启动测试前确认工作进程已缩容至零，重复至少三次并分别记录delayTime与executionTime；出现容量限流时，将该轮排除出纯启动延迟统计。
