Reverse-engineered system prompt of Claude Design from Anthropic.

A system prompt and skill library that turns an LLM into an opinionated, accessibility-aware, AI-slop-resistant design collaborator.

Open source, MIT licensed. Drop the prompt into any LLM that supports system prompts (Claude, GPT, Gemini, local models) and pair with the procedural skills as needed.

Most "design assistant" prompts produce generic SaaS-template output — aggressive gradients, emoji decoration, rounded-corner-with-left-border cards, Inter-everywhere typography. This prompt explicitly rejects those patterns and replaces them with a complete design philosophy covering:

- Content discipline (no filler — every element earns its place)
- Aesthetic discipline (avoid AI tropes, commit to a palette and tone)
- Visual hierarchy and rhythm (size, color, weight, position, density, spacing scales)
- Accessibility (WCAG, semantic HTML, keyboard navigation, focus rings, motion preferences)
- Interaction and feedback (hover, active, disabled, focus, loading, validation states)
- System thinking (components and tokens over one-off pages)
- Respecting the medium (real CSS Grid, `oklch()`, `text-wrap: pretty`, real interactive prototypes)
- Quality over quantity (depth over breadth, polish every detail)

Plus 14 procedural skills the agent can invoke for production, extraction, and review work.

Paste the contents of `system-prompt.md` as the system prompt for any LLM that supports them. The agent will follow the design philosophy and reference the skills by name when tasks match.

Each skill in `skills/` is a self-contained, phased procedure. The skill name is the trigger — when the user's request matches a skill description, the agent loads that skill and follows it.

Skills group into three categories:

**Production** — build something `discovery-questions` · `frontend-aesthetic-direction` · `wireframe` · `make-a-deck` · `make-a-prototype` · `make-tweakable` · `generate-variations`

**System** — extract structure `design-system-extract` · `component-extract`

**Review** — audit and fix `accessibility-audit` · `ai-slop-check` · `hierarchy-rhythm-review` · `interaction-states-pass` · `polish-pass`

Skills can be chained. A typical greenfield flow:

```
discovery-questions → frontend-aesthetic-direction → wireframe → make-a-prototype → polish-pass
```

A brand-aware flow:

```
design-system-extract → generate-variations → make-tweakable → polish-pass
```

The prompt assumes an HTML-output design environment (similar to Claude.ai's design tool). If your target environment is different — a Figma plugin, a code-only assistant, a chat-only design coach — you'll need to adjust the workflow chapters and tool references. The principles (chapters 5–16) translate to any medium.

#### Model calibration

The `claude/` variant is calibrated for current Anthropic frontier models (Fable 5 and the Opus 4.7/4.8 lineage), which follow instructions more literally and need less aggressive prompting than earlier generations:

- **Conditions instead of quotas.** No "ask at least N questions", no "CRITICAL: YOU MUST". Current models treat quotas as literal contracts and over-trigger on them; the prompt states the conditions under which to act, plus an autonomy clause for minor decisions (pick a reasonable option and note it, rather than asking).
- **Explicit triggers for skills and subagents.** These models under-reach for optional capabilities by default, so every skill description states *when* to invoke it, and verifier delegation has an explicit trigger ("after every substantive visual change").
- **Coverage-first reviews.** Review agents report everything with confidence/severity estimates and let the aggregation step filter. Current models follow "only report important issues" literally, which silently suppresses findings.
- **House-style guard.** The current models' default aesthetic (cream background, serif display type, terracotta/amber accents) is detected by `ai-slop-check` (rule 9) and pre-empted by `frontend-aesthetic-direction` 's four-directions protocol. Sampling parameters (`temperature`) no longer exist on these models, so visual variety must come from explicit per-variation specs, not randomness.

On older models (Claude Opus/Sonnet 4.6 and earlier, or non-Anthropic models), the calmer phrasing may under-trigger — restore stronger imperative language if you see the model skipping question rounds or reviews. The `codex/` variant is maintained separately and is unaffected by these notes.

#### 一、深度总结

这个 GitHub 项目本质上是一个 **“设计型 AI 的系统提示词 + 技能库”**。

它试图把普通大模型改造成一个更专业的设计协作者，而不是只会生成“AI 味很重”的通用界面。

所谓“AI 味”，包括：

- 滥用渐变、表情符号、圆角卡片
- 千篇一律的 SaaS 首页风格
- 到处使用 Inter 字体
- 视觉热闹但没有信息价值
- 缺少可访问性、交互状态和系统化思考

项目提供两部分：

##### 1. 系统提示词

核心是一个 20 章的设计哲学与工作规范，覆盖：

- 内容克制：没有废话，每个元素都要有存在理由
- 审美纪律：避免模板化、套路化视觉
- 层级与节奏：字号、颜色、权重、间距、密度要有秩序
- 可访问性：符合 WCAG、语义 HTML、键盘导航、焦点状态、减少动效等
- 交互反馈：hover、active、disabled、loading、validation 等状态完整
- 系统思维：组件、设计 token，而不是一次性页面
- 媒介意识：尊重 HTML/CSS 本身能力，如 CSS Grid、oklch、真实交互原型
- 质量优先：少做但做精

##### 2. 14 个可调用技能

这些技能像“流程插件”，帮助模型在不同设计任务中按步骤行动。

主要分三类：

###### 生产类

用于从零开始设计或生成东西：

- 提问澄清需求
- 确定视觉方向
- 画低保真线框
- 做 HTML 演示文稿
- 做交互原型
- 生成多个高保真方案
- 做可调参数面板

###### 系统类

用于抽取结构：

- 从已有材料提取设计系统
- 盘点可复用组件

###### 审查类

用于质量把关：

- 可访问性审计
- AI 套路检查
- 层级与节奏检查
- 交互状态检查
- 最终润色检查

典型流程是：

```text
需求澄清 → 确定视觉方向 → 线框探索 → 原型制作 → 最终审查
```

如果已有品牌资产，则可以是：

```text
提取设计系统 → 生成方案 → 可调参数 → 最终审查
```

##### 项目的核心目标

不是让 AI “更会画漂亮界面”，而是让 AI：

> 更克制、更系统、更可访问、更像真实设计师，而不是模板生成器。

---

#### 二、深入浅出解读

可以把这个项目理解成：

> 给 AI 装上一套“设计总监的工作准则”。

普通 AI 做设计，经常像一个“审美不稳定的实习生”：

- 用户说做个首页，它马上开干
- 喜欢堆装饰
- 喜欢套模板
- 看起来丰富，但细节经不起推敲
- 不会主动检查按钮状态、键盘操作、视觉层级

而这个项目试图规定：

AI 不能一上来就乱做。

它要先问清楚：

- 给谁用？
- 场景是什么？
- 品牌调性是什么？
- 信息优先级是什么？
- 是否已有设计系统？
- 输出是原型、代码、页面还是方案？

然后再做设计，并且要经过检查：

- 有没有废话？
- 层级清不清楚？
- 颜色是不是有理由？
- 字体是不是合适？
- 按钮状态全不全？
- 键盘能不能操作？
- 是否又陷入 AI 套路？

所以它不是一个单纯的“提示词合集”，而是一套 **AI 设计工作流标准**。

它强调的不是“炫”，而是：

```text
明确 → 克制 → 系统 → 可用 → 可访问 → 可维护
```

---

#### 三、关键价值

##### 1. 把“设计审美”转成可执行规则

审美很难直接教给 AI。

这个项目的聪明之处在于，它没有只说“做得高级一点”，而是拆成具体规则：

- 不要无意义装饰
- 不要默认渐变
- 不要过度圆角卡片
- 不要所有页面都像 SaaS 模板
- 每个组件要有状态
- 每个层级要有依据
- 每个颜色要服务信息

这让设计判断更可操作。

##### 2. 把 AI 从“生成器”变成“协作者”

它不鼓励 AI 一次性给最终答案，而是鼓励：

- 先发现问题
- 再探索方案
- 再生成变体
- 再审查
- 再润色

这更接近真实设计流程。

##### 3. 重视可访问性

很多 AI 设计提示词只追求好看。

这个项目把可访问性放在核心位置，包括：

- 语义结构
- 对比度
- 键盘导航
- 焦点环
- 动效偏好
- 表单校验
- 屏幕阅读器友好

这说明它关注的是“真正可用的产品”，不是截图级作品。

##### 4. 反对“AI 审美惯性”

它特别指出模型会形成默认审美，比如：

- 奶油色背景
- 衬线标题
- 赤陶色 / 琥珀色点缀
- 温柔但雷同的页面气质

这很关键。

因为 AI 最大的问题之一不是不会设计，而是太容易生成“看起来不错但非常像 AI”的东西。

#### 四、辩证思考

##### 优点

###### 1. 它提升了 AI 设计输出的下限

通过流程、规范和审查机制，可以明显减少低级问题：

- 乱用视觉风格
- 缺少交互状态
- 忽视可访问性
- 页面信息混乱
- 组件不可复用

对产品原型、内部工具、早期方案探索很有帮助。

###### 2. 它让设计过程更可复盘

传统提示词常常只看结果。

这个项目更强调：

```text
为什么这么设计？
依据是什么？
有没有检查？
是否符合系统？
```

这让 AI 的设计行为更透明。

###### 3. 它适合团队沉淀自己的设计标准

开源 MIT 许可，意味着团队可以修改成自己的版本：

- 品牌规范
- 组件库规则
- 无障碍要求
- 文案风格
- 审查流程

它可以成为团队的“AI 设计操作手册”。

---

##### 局限

###### 1. 提示词不能替代真实设计能力

它能约束 AI，但不能保证 AI 真懂：

- 用户心理
- 商业目标
- 品牌策略
- 文化语境
- 长期产品演进

提示词可以减少错误，但不能自动产生深刻洞察。

###### 2. 规则过多可能压制创造性

反 AI 套路是必要的。

但如果模型过度遵守规则，可能变得：

- 太保守
- 太理性
- 不敢冒险
- 缺少情绪张力
- 输出“正确但无聊”的设计

好的设计不只是避免错误，也需要突破。

###### 3. 它更适合 HTML/CSS 语境

项目假设的是类似 Claude 设计工具的 HTML 输出环境。

如果用于：

- Figma
- 原生 App
- 小程序
- 游戏 UI
- 品牌视觉
- 纯对话咨询

就需要改造流程和工具描述。

###### 4. 不同模型适配成本不同

项目明确提到：

- 新模型更容易严格遵守指令
- 旧模型可能需要更强硬的提示语
- 不同平台对技能调用、工具环境支持不同

所以它不是“复制即完美”，而是需要调校。

---

#### 五、我的判断

这个项目最有价值的地方，不是它提供了一套“万能设计提示词”。

而是它提出了一个重要方向：

> AI 设计的关键，不是让模型更会装饰，而是让模型更会判断、克制、审查和迭代。

未来真正有用的设计 AI，不应该只是生成漂亮页面，而应该具备四种能力：

1. 理解问题  
2. 建立系统  
3. 生成方案  
4. 自我审查  

这个项目正是在往这个方向走。

但也要警惕：

> 规则能防止平庸，却不一定创造伟大。

所以它最适合作为 **设计流程底座**，而不是最终审美裁判。

最佳使用方式是：

```text
AI 负责结构化、探索、检查、提效；
人负责判断、取舍、品味、方向。
```

一句话总结：

> 这是一个把 AI 从“模板化设计生成器”推向“专业设计协作者”的开源提示词系统。

##### 主旨概括

这是一个开源的 Claude Design 逆向系统提示词与技能库，目标是把大语言模型训练成一个更专业、更有审美判断、更重视可访问性的设计协作者。它强调避免常见“AI 味”设计套路，转而用系统化的设计原则和流程产出更成熟的界面、原型和设计评审。

##### 1. 项目定位：让 LLM 成为更可靠的设计协作者

该项目名为 **claude-design-system-prompt**，是一个从 Anthropic 的 Claude Design 中逆向整理出的系统提示词和技能库。

- 开源协议：**MIT License**

- 核心目标：
  - 避免泛泛的 SaaS 模板式设计
  - 提升设计输出的审美质量
  - 强化可访问性、交互状态、组件化和设计系统意识
  - 让 AI 不只是“生成页面”，而是像设计搭档一样参与判断和协作

作者指出，很多“设计助手”容易产出类似的 AI 套路，例如：

- 夸张渐变
- 过度使用 emoji
- 圆角卡片加左边框
- 到处使用 Inter 字体

##### 2. 核心设计哲学：强调克制、系统和质量

###### 视觉层级与节奏

关注以下设计细节：

- 字号
- 色彩
- 字重
- 位置
- 密度
- 间距比例

- WCAG 原则
- 语义化 HTML
- 键盘导航
- 清晰的 focus ring
- 尊重用户的动效偏好

###### 交互与反馈

要求设计覆盖完整状态，例如：

- hover
- active
- disabled
- focus
- loading
- validation states

###### 系统化思维

项目不鼓励只做一次性页面，而是强调：

- 组件
- token
- 设计系统
- 可复用结构

###### 尊重媒介

鼓励使用真实前端能力，而不是只做表面模拟，例如：

- CSS Grid
- `oklch()`
- `text-wrap: pretty`
- 真实可点击原型

##### 7. 模型校准：针对新版 Claude 做了提示词调整

- Fable 5
- Opus 4.7 / 4.8 系列

###### 主要调整包括：

###### 用条件代替硬性数量要求

不再写类似：

```text
至少问 N 个问题
CRITICAL: YOU MUST
```

原因是新模型会把数量要求当作硬性合同，导致过度执行。

现在的方式是：

- 明确什么时候需要提问
- 小问题由模型自行合理决定，并说明选择

###### 明确技能触发条件

新版模型默认不会主动调用可选能力，因此每个技能都写明了何时调用。

例如：

- 在每次实质性视觉修改后触发验证流程

###### 评审优先覆盖问题

评审代理会尽量报告所有发现，并标注：

- 置信度
- 严重程度

再由后续汇总步骤筛选，避免模型因为“只报告重要问题”而漏掉问题。

###### 防止默认“家族审美”

作者指出当前模型容易产生某种默认风格，例如：

- 米色背景
- 衬线展示字体
- 陶土色 / 琥珀色点缀

因此项目用 `ai-slop-check` 的规则 9 识别这种“house style”，并通过 `frontend-aesthetic-direction` 的四方向协议提前避免。

## 口播总结（1）

### 2026-08-03 01:55:26

#### 一个把大语言模型变成专业设计协作者的开源项目

这份材料介绍的是 GitHub 项目“claude-design-system-prompt”。它提供了一套系统提示词和十四个可调用的设计技能，目标是让大语言模型不再只生成千篇一律的模板页面，而是成为更有审美判断、重视无障碍、能够持续审查设计质量的协作者。接下来，我们会了解它解决什么问题、包含哪些内容，以及它如何组织设计和评审流程。

##### 首先，它要解决的是“人工智能设计同质化”

核心结论是：这个项目明确反对常见的人工智能设计套路，并用一套完整的设计原则替代它们。

所谓人工智能设计套路，指的是模型很容易反复生成的视觉模式。比如强烈的渐变色、用表情符号装饰界面、带左侧边框的圆角卡片，以及到处使用同一种字体。这样的页面看起来往往像套用了同一个 SaaS，也就是软件服务产品模板，缺少明确个性。

这个项目要求模型在设计时做到几件事。

第一，内容要克制。页面上的每个元素都应该有作用，而不是为了填满空间。

第二，审美要有方向。模型不能随意拼接颜色和风格，而要主动确定配色、字体和整体语气。

第三，要建立清楚的视觉层级和节奏。也就是说，要通过大小、颜色、字重、位置、信息密度和间距，让用户知道什么最重要、接下来该看什么。

第四，要重视无障碍。包括遵循 WCAG，也就是网页内容无障碍指南；使用有语义的 HTML；支持键盘操作；提供清楚的焦点提示；并尊重用户对减少动画的偏好。

第五，要把交互状态设计完整。按钮在悬停、按下、禁用、获得焦点、加载中和校验失败时，都应该给出合理反馈。

这些原则最终指向一个目标：少做表面上的“漂亮”，多做真正有逻辑、可使用、可维护的设计。

##### 接下来，项目由一套系统提示词和十四项技能组成

核心结论是：它不是一段孤立的提示词，而是一套可以配合使用的设计工作系统。

系统提示词相当于模型的总规则。它告诉模型应该以什么身份工作、如何提问、如何做设计决策、如何进行评审，以及怎样交付结果。

在这套提示词之外，项目还提供十四项独立技能。每项技能都是一个分阶段的操作流程。当用户的请求符合某项技能的描述时，模型就可以加载并执行对应流程。

这些技能可以分为三类。

第一类是生产技能，用来从零开始做设计。包括提出发现问题、确定前端审美方向、制作线框图、制作网页幻灯片、生成交互式原型、增加可调参数，以及生成多个设计变体。

第二类是系统技能，用来从已有内容中提取结构。包括提取设计系统，以及盘点可复用组件。

这里的“设计系统”，可以简单理解为一套统一的颜色、字体、间距、组件和交互规则。它能避免每个页面都重新发明一套样式。

第三类是评审技能，用来检查和修正问题。包括无障碍审查、人工智能套路检查、层级与节奏检查、交互状态检查，以及最后的整体润色。

十四项技能的意义在于，它们把“设计得更好”这种抽象要求，拆成了可以逐步执行的具体流程。

##### 更重要的是，它强调先理解问题，再开始设计

核心结论是：在没有足够背景信息时，模型应该先提问，而不是立刻生成页面。

通俗地说，设计不是单纯决定颜色和按钮样式。模型还需要知道产品服务谁、用户要完成什么任务、品牌有没有既定风格、页面最终要运行在哪里，以及哪些内容最重要。

因此，项目设置了“发现问题”技能，用来帮助模型在项目开始阶段了解目标和限制。

对于没有现成品牌的项目，它还提供“前端审美方向”技能。这个技能要求模型主动确定一种视觉方向，而不是默认套用某种固定风格。材料特别提到，当前模型容易默认使用米白色背景、衬线展示字体，以及陶土色或琥珀色点缀。因此，项目会通过四方向流程提前避免这种“默认审美”。

如果需要探索方案，模型可以先制作至少三种低保真线框，或者生成多个高保真变体。这里的重点不是机械追求数量，而是沿着不同方向进行比较，比如调整布局、色彩、密度或品牌表达。

对于小的设计决定，模型也不必事事反问用户。它可以选择一个合理方案，同时把这个决定说明出来。这样既保持自主性，也让协作者知道发生了什么。

##### 然后，项目把设计看成一个完整系统，而不是一张孤立页面

核心结论是：好的设计不仅要完成当前页面，还要考虑组件复用、交互反馈和后续维护。

一个例子是，项目不鼓励只做一次性的页面，而是要求优先考虑组件和设计令牌。设计令牌可以理解为集中管理的基础变量，例如主色、字号、圆角和间距。这样一旦品牌颜色或间距规则发生变化，就能更稳定地同步到整个产品。

项目还提供组件提取技能。它可以从已有页面中盘点按钮、卡片、输入框、导航等可复用部件，帮助团队发现哪些内容应该统一。

在交互方面，项目要求完整检查各种状态。比如一个按钮不能只设计正常状态，还要考虑鼠标悬停、按下、键盘聚焦、禁用和加载中的样子。表单也要说明输入成功、失败或正在处理时会发生什么。

这样做的结果，是让页面不仅“看起来能用”，而且在真实操作中也有明确反馈。

##### 在评审阶段，它强调全面发现问题，再决定哪些最重要

核心结论是：评审流程要先尽量覆盖问题，再根据严重程度和可信度进行筛选。

材料提到，当前模型如果只被要求“报告重要问题”，可能会把一些问题直接忽略。因此，这个项目要求评审代理先报告发现的内容，并附上可信度和严重程度，最后再由汇总步骤决定哪些问题最值得优先修复。

评审技能覆盖几个方面。

无障碍审查会检查语义 HTML、键盘操作、焦点样式、颜色对比度和动画偏好。

人工智能套路检查会识别渐变、表情符号装饰、字体滥用，以及项目自身称为“房屋风格”的固定模板倾向。

层级与节奏检查会关注字号、字重、颜色、空间尺度和布局密度。

交互状态检查则专门确认悬停、按下、禁用、聚焦和加载等状态是否完整。

最后的润色技能相当于总验收。它会把前面的问题汇总起来，作为发布前的最后一道检查。

##### 这些技能还可以串成不同的工作流程

核心结论是：项目没有规定所有设计都必须走同一条路线，而是根据任务类型组合技能。

在一个全新的项目中，典型流程是：先提出发现问题，然后确定前端审美方向，再制作线框图，接着做交互式原型，最后进行整体润色。

如果项目已经有品牌规范，则可以先提取设计系统，再生成多个设计方案，接着制作可调节版本，最后完成润色。

这里的“可调节版本”，指的是页面中提供一个悬浮调节面板，让设计者可以更方便地修改部分视觉参数，并比较不同结果。

项目默认的工作环境，是一种能够输出 HTML 的设计环境，类似 Claude 的设计工具。如果目标环境是 Figma 插件、只写代码的助手，或者只能在终端工作的工具，就需要相应调整工作流程和工具引用。不过，关于内容、审美、层级、无障碍和质量的基本原则，仍然可以迁移到其他环境。

##### 另一个重点，是针对不同模型进行提示词校准

核心结论是：这套提示词会根据模型的行为特点调整表达方式，而不是只依赖更强硬的命令。

项目中的 Claude 版本，针对当前 Anthropic 的前沿模型进行校准，包括 Fable 5，以及 Opus 4.7 和 4.8 这一系列模型。

对于这些模型，项目不再使用“必须提问至少多少个问题”或“必须严格执行某个数量”这样的硬性配额。原因是当前模型可能把配额当成绝对合同，导致过度提问或过度触发。

相反，提示词会说明什么情况下应该采取某个行动，并允许模型对小问题自主决定。

同时，因为当前模型有时会对可选能力执行不足，所以每项技能都写清楚了触发条件。比如，在每次实质性的视觉修改之后，都应该明确触发验证和复查。

如果使用的是更早的模型，例如 Claude Opus 或 Sonnet 4.6 及更早版本，或者使用非 Anthropic 模型，项目建议在模型经常跳过提问或评审时，恢复更强的命令式表达。

项目还提供 Codex 版本。它与 Claude 版本的主要区别，是采用单一循环，不使用并行子代理，并按顺序完成各项评审。

##### 最后，这个项目的内容和授权都比较开放

核心结论是：项目希望它成为一套可以复制、修改和扩展的设计基础设施。

系统提示词一共分为二十章，内容覆盖身份和角色、工作流程、提问方式、已有背景、内容原则、审美原则、视觉层级、字体系统、颜色系统、无障碍、交互反馈、行动号召、系统化设计、媒介限制、用户理解、质量标准、输出方式、协作交付、知识产权边界，以及可用技能。

项目使用 MIT 许可证。这意味着任何人都可以使用、修改和分发这套提示词和技能库，也可以用于商业用途，而且不要求必须署名。

项目也欢迎继续贡献，包括增加文案评审、动效评审和深色模式检查等技能，适配 Figma、纯代码或纯终端环境，以及补充真实项目中的失败案例。

##### 结尾：最值得记住的五点

最后，可以把整份材料归纳成五个结论。

第一，这不是普通的设计提示词，而是一套由系统提示词和十四项技能组成的工作流程。

第二，它明确反对渐变、表情符号、模板化卡片和单一字体等人工智能设计套路，要求每个视觉元素都有明确目的。

第三，它把无障碍、键盘操作、焦点提示、交互状态和用户反馈，都视为设计本身的一部分。

第四，它鼓励先提问、再确定方向，并通过线框、原型、多个变体和多轮评审逐步完善结果。

#### 真正可迁移的不是“Claude 审美”，而是一套设计代理的质量控制机制

这个仓库表面上是在复刻 Claude Design 的系统提示词，真正值得关注的却不是它列出的审美偏好，而是它把“让模型做好设计”拆成了一套可执行流程：**先确定方向，再生产方案，随后从无障碍、视觉层级、交互状态和模板化痕迹等维度逐项复核。**

这比一句“做得高级、简洁、有设计感”有效得多。模型并不缺少生成页面的能力，缺的是稳定判断：什么时候该提问，什么时候可以自行决策，哪些细节必须检查，以及完成的标准是什么。仓库用一个总提示词约束原则，再用 14 个独立技能承载具体程序，本质上是在给设计代理建立“操作系统＋标准作业流程”，而不是堆叠形容词。

##### “AI 味”首先是任务定义不足，而非单纯审美问题

渐变、圆角卡片、Emoji 和千篇一律的字体只是表象。更深的原因是：当品牌、内容层级和使用情境都不明确时，模型会回到最安全、概率最高的视觉组合。仓库因此不只设置反模式检查，还要求在缺乏品牌基础时先明确若干差异化方向；生成多个方案时，也要显式规定变化轴，而不是依赖随机性。

这个判断可以迁移到更多生成式产品：**输出同质化往往意味着决策空间没有被结构化。** 与其不断增加“不要俗套”之类的禁令，更有效的办法是明确哪些变量需要承诺，例如信息密度、视觉语气、色彩关系、排版尺度与交互优先级。反模式清单会随潮流过时，清晰的决策过程则更持久。

##### 提示词正在变成需要版本管理的行为配置

仓库中最有价值的细节，是它专门区分模型代际。作者观察到，新模型更容易把数量要求当成刚性合同，因此把“至少问几个问题”改成条件触发；但新模型又可能不主动调用可选能力，所以需要显式规定何时启动技能和审查。评审环节则先追求覆盖，再由后续步骤过滤严重程度，避免“只报告重要问题”导致模型悄悄漏项。

这说明提示词并不是一次写完的自然语言说明书，而是与模型能力耦合的行为配置。模型升级后，同一套指令可能从有效约束变成过度触发，也可能失去力度。对团队产品而言，提示词因此应像代码一样具备版本、回归案例和模型适配层，而不应只靠上线前的主观试玩。

##### 下一步机会不在复制提示词，而在建立可验证的设计评审层

这个项目目前主要展示方法，并未提供对照实验，所谓“逆向工程”也不等于已验证与原系统等价。它真正暴露的产品机会，是把设计质量要求做成可组合、可测量的评审能力：输入页面或代码，输出无障碍缺陷、层级混乱、状态遗漏和品牌偏移，并能回写修改。

现有替代方案是设计师人工走查、设计系统规范和零散 lint 工具。值得验证的不是用户是否喜欢“去 AI 味”，而是这类自动评审能否**减少返工，同时不把所有作品校正成另一种统一风格**。如果能建立真实项目的前后对照与缺陷数据，这套仓库就可能从一组好用的提示词，进一步演化为设计代理的质量基础设施。
