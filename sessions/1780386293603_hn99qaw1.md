## 分析要点

- **核心高价值点**：AI coding 的 token 管理本质是上下文生命周期管理，而不是简单减少输入字数。
- **留存建议**：短期参考后可归档，适合在使用 Codex 或类似 AI Agent 工具时复用（提供了较具体的上下文生命周期管理方法，可作为 AI Coding 降本和会话组织的参考）

**知识要点**

- 按业务线而非零散任务划分长期 thread，有助于恢复上下文、控制成本和明确责任边界
- 大任务结束后应通过 session-end 或 checkpoint 摘要沉淀结果、下一步和证据，避免长期携带巨型上下文
- 短确认在长 thread 中也可能触发大量 input tokens，因此应避免在巨型会话中无意义续聊
- 长日志、搜索结果、截图等高 token 内容应先摘要，必要时再局部展开

**行动项**

- 为主要业务线建立固定 Codex thread，并将 Daily thread 仅用于路由和分发
- 每轮任务结束后生成 checkpoint 摘要，记录结果、下一步和关键证据
- 减少在长上下文 thread 中发送“继续”“好”等低价值短消息
- 对日志、搜索结果和网页抓取输出设置摘要优先、局部展开的处理流程

## 解读（1）

### 2026-06-02 07:43:49

##### 一、总结

这篇内容讲的是：**一个人用 AI / Codex App 时，核心不是拼命多聊，而是管理好上下文，节省 token。**

作者的方法：

1. **每条业务线固定一个置顶 thread**
   - PM、内容、系统、研究分开聊。
   - 不同任务不要混在一个大对话里。

2. **大 thread 到阶段点就收尾**
   - 一轮任务结束后，让 AI 总结：
     - 已完成什么
     - 下一步是什么
     - 关键证据在哪里
   - 后续从摘要继续，不要拖着超长上下文跑。

3. **少在巨型 thread 里发“好 / 继续”**
   - 看似几个字，实际会带上整个历史上下文。
   - 可能一次就消耗十几万、二十几万 tokens。

4. **控制长日志、搜索结果、截图**
   - 先让 AI 总结。
   - 需要细节时，再局部展开。
   - 不要一次性塞太多原文。

5. **自动任务 loop 要归属到具体业务线**
   - PM 的放 PM thread。
   - 内容的放内容 thread。
   - Daily thread 只做分发和路由。

核心观点：

> AI coding 的 token 管理，本质是上下文生命周期管理。

---

##### 二、通俗解读

可以把 Codex App 的 thread 理解成“项目文件夹”。

如果你把所有事情都塞进一个聊天里，就像：

> 一个文件夹里同时放合同、代码、会议纪要、截图、日报、搜索结果。

结果就是：

- AI 每次都要重新翻一大堆旧资料；
- 你只是说一句“继续”，它也可能读完整个文件夹；
- token 消耗巨大；
- 回答还容易跑偏。

更好的方式是：

> 每条业务线一个固定入口，每轮任务结束就做归档摘要。

比如：

```text
PM thread：产品规划、需求、路线图
内容 thread：文章、脚本、选题
系统 thread：工具、自动化、流程
研究 thread：资料、竞品、洞察
Daily thread：只负责分发任务
```

这样做的好处是：

- 上下文更干净；
- AI 更容易接住任务；
- token 更省；
- 后续恢复工作更快；
- 不同任务之间不会互相污染。

---

##### 三、我的意见

我非常认同这套方法。

很多人用 AI 浪费 token，不是因为问得太多，而是因为**上下文太乱、太长、太不分层**。

我建议可以再加三点：

###### 1. 每个 thread 开头放一段固定说明

例如：

```text
这是内容业务线 thread。
目标：管理选题、文章、脚本、发布节奏。
输出要求：简洁、可执行、带下一步。
```

让 AI 每次都知道这个 thread 是干什么的。

###### 2. 每轮结束强制生成 checkpoint

格式可以固定：

```markdown
## 本轮完成
- ...

## 关键结论
- ...

## 待办事项
- ...

## 下次继续入口
- ...
```

这样下次不用重读长上下文。

###### 3. 大资料先摘要，别直接全塞

尤其是：

- 日志
- 网页
- 搜索结果
- 代码报错
- 截图 OCR
- 长文档

先让 AI 看摘要，再决定是否展开局部原文。

---

##### 最后一句话

**用 AI 不是一直聊，而是会分线程、会收尾、会压缩上下文。**

真正高效的 AI 工作流，本质上是：

> 把 AI 当员工用，把 thread 当项目管理。

##### 主旨概括

这篇文章主要讲的是：**一个人使用 Codex App / AI Coding 时，想要省 token、提高效率，关键不是少说话，而是管理好上下文生命周期**。作者分享了自己把 Codex App 用到更高效的几种实践方法，核心是：**按业务线拆 thread、定期压缩上下文、避免巨型会话反复滚动**。

---

##### 1. 用固定置顶 Thread 管理不同业务线

作者建议在 Codex App 中保留固定的置顶 thread，每条业务线一个入口。

比如作者自己的分类包括：

- PM
- 内容
- 系统
- 研究

这样做的好处是：

- 每条业务线都有独立上下文
- 后续恢复任务更方便
- 不同任务之间不会互相污染
- 分工和状态更清楚

简单理解：不要把所有事情都塞进一个大对话里，而是像建立不同项目文件夹一样管理 AI 会话。

---

##### 2. 大 Thread 到阶段节点后要及时收尾

当一轮任务完成，或者推进到一个 checkpoint 时，作者会执行一次 `session-end`。

这个动作主要是把以下内容写回：

- 当前结果
- 下一步计划
- 关键证据
- 阶段性总结

之后继续任务时，就从摘要接着做，而不是拖着整条巨大的历史上下文继续跑。

这样可以显著减少 token 消耗，也能让 AI 更快进入重点。

---

##### 3. 不要在巨型 Thread 里频繁发短确认

作者特别提醒，不要在很大的 thread 里随手发一些短句，比如：

- “好”
- “继续”
- “现在搞”

这些字本身很短，但如果 thread 已经很大，AI 每次回复时背后可能都会重新带上大量上下文。

作者举了自己日志中的例子：

- 一次请求有 **13 万 input tokens**，但只命中 **2.4k cache**
- 另一次请求有 **23 万 input tokens**，但只命中 **4.5k cache**

这意味着：看似只是发了几个字，实际却让系统重新处理了十几万甚至二十几万 token，非常浪费。

---

##### 4. 控制长日志、搜索结果、截图的输入量

对于长日志、搜索结果、截图、网页抓取等信息，作者建议不要一股脑全部丢给 agent。

更好的做法是：

1. 先让 agent 给摘要
2. 如果需要，再局部展开原文
3. 只保留真正有用的信息进入上下文

尤其是以下场景，很容易导致输出爆炸：

- `rg`
- `find`
- 网页抓取
- X 搜索
- 长日志分析
- 大量截图内容

一旦这些内容进入 thread，后续每一轮对话都可能变贵。

---

##### 5. 自动 Loop 要归属到具体业务线

作者还提到，自动化循环任务也要放到对应业务线里，而不是混在一起。

例如：

- PM loop 放到 PM thread
- 内容 loop 放到内容 thread
- Daily thread 只做路由和分发

这样可以让：

- 成本更清楚
- 状态更清楚
- 责任边界更清楚

也就是说，Daily thread 不负责承载所有上下文，只负责判断任务该流向哪里。

---

##### 6. 作者当前的实际工作流

作者现在的做法是：

- 保留 **10 个置顶 thread**
- 每个 thread 都作为一个“业务线入口”
- 每轮任务到 checkpoint 就收尾
- 收尾时压缩上下文，保留摘要和下一步

这种方式相当于给 AI 建立了一套“项目管理系统”，而不是无限延长一个对话窗口。

---

##### 7. 核心结论：Token 管理就是上下文生命周期管理

作者最后总结：**AI coding 的 token 管理，本质上是上下文生命周期管理。**

通俗来说，省 token 的关键不是简单地少打几个字，而是要管理好：

- 哪些上下文该保留
- 哪些上下文该压缩
- 哪些上下文该归档
- 哪些任务该放在哪个 thread
- 什么时候结束一轮会话并重新开始

只有这样，才能让 Codex App 在长期使用中既省成本，又保持高效。

##### 1. 启发

###### 1）把 AI 会话当成「业务系统入口」，而不是临时聊天窗口

很多人使用 Codex / ChatGPT / Claude 时，是按任务临时开会话：

- 今天修一个 bug
- 明天写一个脚本
- 后天研究一个功能
- 过几天又重新解释背景

Leo 的做法更接近「组织架构」：

- PM 一条 thread
- 内容一条 thread
- 系统一条 thread
- 研究一条 thread
- 每条业务线一个长期入口

这意味着：**AI thread 不再是聊天记录，而是业务线的上下文容器。**

对一个人创业、独立开发、AI 产品构建者来说，这非常关键。因为你没有团队，但你可以用不同 thread 来模拟不同岗位和业务线。

---

###### 2）省 token 的核心不是少说话，而是少拖历史

很多人以为“好”“继续”“现在搞”这种短句不费 token。  
但在长 thread 里，这些短句会触发整个上下文再次参与推理。

表面上你只输入了 2 个字，实际上模型可能读了：

- 10 万 token 历史上下文
- 大量日志
- 搜索结果
- 截图内容
- 之前的代码分析
- 旧任务残留

所以真正浪费的不是这几个字，而是：**你没有及时压缩上下文。**

---

###### 3）大 thread 需要 checkpoint，而不是无限续命

一轮任务结束后，应该做一次 `session-end`：

- 本轮完成了什么？
- 关键决策是什么？
- 证据在哪里？
- 还有哪些待办？
- 下一步怎么接？

这相当于给 AI 工作流做「阶段性归档」。

它的价值不只是省 token，还包括：

- 降低上下文污染
- 提升后续恢复速度
- 避免 AI 被过期信息误导
- 让复杂项目可以长期推进

---

###### 4）AI 工作流的本质是「上下文资产化」

引用推文里还有一个更重要的点：

> Thread 不一定只装在 App 里，也可以装在仓库文件里。

这非常有启发。

因为如果上下文只存在某个 App 的会话中，它就是平台绑定的、不可迁移的。  
但如果上下文被沉淀到 repo 文件里，例如：

```txt

/context/content.md
/context/system.md
/context/research.md
```

它就变成了：

- 可版本管理
- 可跨 App 迁移
- 可被不同 agent 读取
- 可被团队协作
- 可持续演化的业务资产

这比“调教一个 AI”更重要，本质是在构建自己的 AI 原生工作系统。

---

##### 2. 高价值信息深挖

###### 1）thread 按「业务线」切，而不是按「功能」切

很多人会按功能开会话：

- 登录功能 thread
- 支付功能 thread
- 搜索功能 thread
- 数据库优化 thread

但 Leo 提到更好的方式是按业务线切：

- PM thread
- 内容 thread
- 系统 thread
- 研究 thread
- 增长 thread
- 运营 thread

为什么？

因为功能是短生命周期的，业务线是长生命周期的。

一个登录功能可能几天就做完了，但 PM、增长、内容、系统这些业务线会一直存在。  
长期 thread 应该承载稳定职责，而不是临时任务。

更好的结构是：

```txt
业务线 thread：长期上下文
具体任务：短周期执行
checkpoint：任务结束后回写摘要
```

---

###### 2）Daily thread 只做路由，不做重活

Leo 提到：

> Daily thread 只做路由和分发。

这很重要。

Daily thread 不应该堆积所有细节，否则很快变成巨型上下文黑洞。  
它更像一个「调度台」：

- 今天有哪些任务？
- 属于哪个业务线？
- 应该分发到哪个 thread？
- 哪些事项需要更新状态？

例如：

```txt
Daily thread:
- 今天要修复支付回调问题 → 分发到 System thread
- 今天要写一篇 AI coding 文章 → 分发到 Content thread
- 今天要评估新功能优先级 → 分发到 PM thread
```

这样可以防止 daily thread 变成所有上下文的垃圾场。

---

###### 3）长日志、搜索结果、截图必须先摘要，后展开

这是 AI 工具使用中非常容易被忽略的成本黑洞。

例如：

- `rg` 搜索输出几千行
- 网页抓取一整篇文章
- X 搜索结果几十条
- 控制台日志大段粘贴
- 截图 OCR 出大量内容

这些信息一旦进入 thread，后续每一轮都可能被重复带上。

更好的策略是：

```txt
第一步：让 agent 摘要
第二步：识别关键片段
第三步：只展开必要原文
第四步：任务结束后写入 checkpoint
```

也就是：**先压缩信息，再进入主上下文。**

---

###### 4）缓存命中不是万能的，长上下文仍然会浪费

Leo 提到日志中出现：

- 13 万 input，只命中 2.4k cache
- 23 万 input，只命中 4.5k cache

这说明一个关键问题：

**不要以为有缓存就可以无限堆上下文。**

缓存命中取决于很多因素：

- 上下文是否稳定
- 是否有新增内容插入
- prompt 是否变化
- 工具输出是否持续膨胀
- thread 是否被污染

如果上下文结构混乱，缓存命中率很低，长 thread 会变成持续烧钱的机器。

##### 3. 可迁移清单

下面是一套可以直接迁移到个人 AI 产品开发 / 独立开发 / AI 工作流中的清单。

###### A. thread 结构设计

建议建立 5-10 个长期入口：

```txt
01_PM：产品规划、需求、优先级、用户反馈
02_System：架构、代码、技术债、部署、性能
03_Content：文章、社媒、newsletter、视频脚本
04_Research：竞品、技术调研、市场趋势
05_Growth：获客、转化、定价、增长实验
06_Operation：日常运营、客户支持、流程管理
07_Daily：每日路由、任务分发、状态同步
```

原则：

- 长期 thread 按业务线切
- 临时任务不要污染主 thread
- Daily 只做路由，不承载深度上下文
- 每个 thread 都有明确职责边界

```markdown
## 关键决策
- 

## 重要证据 / 文件 / 链接
- 

## 遗留问题
- 

## 下一步行动
- 

## 不要忘记的上下文
- 
```

然后让 AI 帮你压缩：

```txt
请基于本轮对话生成一个 session-end checkpoint。
要求：
1. 只保留后续继续任务所需的信息
2. 删除过程性废话
3. 保留关键决策、证据、下一步
4. 输出为可放入 repo 的 markdown
```

---

###### C. 建立 repo 级上下文文件

可以在项目仓库中建立：

```txt
/context
  /pm.md
  /system.md
  /content.md
  /research.md
  /growth.md
  /daily.md
```

每个文件维护对应业务线的长期上下文。

好处：

- 不被单一 App 绑定
- 可以用 Git 追踪历史
- 可以给 Codex / Claude / ChatGPT / Cursor 共用
- 可以团队协作
- 可以沉淀为长期系统资产

---

###### D. 控制大输出进入上下文

对于长日志、搜索结果、网页、截图，使用三步法：

```txt
1. 先摘要
2. 再定位关键片段
3. 最后按需展开原文
```

提示词示例：

```txt
下面是较长日志，请不要逐行分析。
请先：
1. 提取异常模式
2. 找出最可能相关的 5 个片段
3. 标注每个片段的重要性
4. 等我确认后再展开分析
```

---

###### E. 避免在巨型 thread 中做短确认

不要在巨大 thread 中频繁输入：

```txt
好
继续
再来
现在搞
可以
```

更好的方式是：

```txt
基于上一个 checkpoint 继续，只处理「下一步行动」中的第 2 项。
不要重新分析全部历史，除非必要。
```

或者：

```txt
请先复述你当前认为的任务边界和需要使用的上下文，确认后再继续。
```

---

##### 4. 反方与张力

###### 1）长期 thread 有价值，但也容易形成上下文污染

长期 thread 的好处是连续性。  
但风险是：

- 旧决策过期
- AI 引用不再有效的信息
- 不同任务互相干扰
- thread 变成杂乱知识库

所以长期 thread 不能无限增长，必须配套：

- checkpoint
- 过期信息清理
- 业务线边界
- repo 文件沉淀
- 定期重建上下文

---

###### 2）按业务线切分适合复杂系统，但不一定适合简单任务

如果只是一次性写脚本、修 bug、生成文案，过度设计 thread 反而浪费。  
这种方法更适合：

- 长期产品开发
- 多业务线并行
- AI 原生工作流
- 独立开发者
- 小团队协作
- 高上下文依赖的项目

对于轻量任务，可以直接开临时 thread，完成后只把结果写回主系统。

---

###### 3）省 token 和保持完整上下文之间有张力

压缩上下文可以省成本，但也可能丢失细节。

例如：

- 某个 bug 的关键原因藏在日志细节里
- 某个产品决策依赖原始用户反馈语气
- 某个技术方案的限制条件被摘要省略

所以不能盲目压缩。  
更合理的是分层：

```txt
长期上下文：只保留稳定事实、决策、目标
中期上下文：保留当前任务状态
短期上下文：保留原始日志、截图、搜索结果
```

---

###### 4）repo 文件上下文很强，但需要维护成本

把 thread 搬到 repo 文件里有巨大好处，但它不是免费的。

你需要：

- 定期更新
- 删除过期内容
- 维护结构
- 避免 markdown 变成垃圾堆
- 确保不同文件之间不冲突

否则 repo context 也会变成另一个失控的 thread。

---

##### 5. 情境化落地

###### 场景一：一个人做 AI 产品

你可以这样分工：

```txt
PM thread：
- 用户需求
- 产品路线图
- 版本优先级
- 用户反馈分析

System thread：
- 架构设计
- 数据库
- API
- 部署
- bug 修复

Growth thread：
- 定价
- landing page
- 转化漏斗
- 冷启动策略

Content thread：
- 推文
- 长文
- newsletter
- 案例复盘

Daily thread：
- 每天任务分发
- 进度同步
- 风险提醒
```

每天开始时，只在 Daily thread 里问：

```txt
基于当前各业务线 checkpoint，帮我规划今天最重要的 3 件事。
请标注每件事应该进入哪个 thread 执行。
```

---

###### 场景二：AI Coding 项目

当你让 Codex 处理代码时，不要把所有东西塞进一个 thread。

推荐流程：

```txt
1. 在 System thread 中描述技术背景
2. 针对具体 bug 开启一轮任务
3. 长日志先摘要，不直接全量分析
4. 修改完成后生成 checkpoint
5. 将关键结果写入 /context/system.md
6. 大 thread 到节点后收尾，不无限续
```

示例 prompt：

```txt
请基于当前仓库和 /context/system.md，处理支付回调失败问题。
限制：
1. 先阅读相关文件并给出问题假设
2. 不要输出大段无关搜索结果
3. 每次工具调用后只总结关键发现
4. 完成后生成 session-end checkpoint
```

---

###### 场景三：内容生产系统

内容业务不要和产品、技术混在一起。

可以建立：

```txt
/content/context.md
/content/ideas.md
/content/style-guide.md
/content/published.md
```

Content thread 负责：

- 选题
- 观点打磨
- 风格一致性
- 文章复盘
- 发布计划

每次写完内容后，让 AI 回写：

```txt
请总结本次内容生产的：
1. 核心观点
2. 可复用表达
3. 受众反馈假设
4. 后续可延展选题
并更新到 content checkpoint。
```

---

###### 场景四：研究和信息摄入

研究 thread 最容易爆上下文，因为会包含大量网页、论文、推文、搜索结果。

建议使用「研究卡片」机制：

```markdown
# Research Card

## 主题
-

## 来源
-

## 核心结论
-

## 关键证据
-

## 对我产品/业务的启发
-

## 可执行动作
-

## 可信度
-
```

不要把所有原文都塞进去，而是先转成研究卡片。

---

##### 最终可执行版本

如果只保留最重要的 7 条：

1. **每条业务线一个长期 thread，不要所有事混在一起。**
2. **Daily thread 只做路由，不做深度执行。**
3. **大任务结束后必须做 checkpoint。**
4. **长日志、搜索结果、截图先摘要，再局部展开。**
5. **不要在巨型 thread 里频繁发“好”“继续”。**
6. **把长期上下文沉淀到 repo 文件，而不是只放在 App 里。**
7. **token 管理的本质是上下文生命周期管理。**

一句话落地：

> 把 AI thread 当成业务系统的上下文入口，把 checkpoint 当成任务交接文档，把 repo context 当成长期组织记忆。
