## 分析要点

- **核心高价值点**：最有价值的点是把LLM从“查询时临时检索”转变为“持续维护知识编译产物”，让知识沉淀真正具备复利效应。
- **留存建议**：建议长期保留，适合作为搭建个人或团队AI知识库的模式参考（提出了可复用的LLM+Wiki知识沉淀框架，具备较强方法论价值和长期参考意义）

**知识要点**

- 用持久化Wiki替代纯RAG式问答，减少重复检索与重复综合
- 知识库架构分为原始资料层、Wiki层和Schema规则层
- 核心操作包括Ingest、Query和Lint，形成持续演化闭环
- index.md和log.md分别承担内容导航与演化记录功能
- Obsidian、qmd、Dataview、Marp等工具可增强实际工作流

**行动项**

- 尝试在Obsidian中建立一个最小可用LLM Wiki目录结构，并定义AGENTS.md或CLAUDE.md规则
- 选取一个持续积累的主题进行单源逐步摄入，验证摘要、交叉引用和知识更新流程

llm-wiki

#### LLM Wiki

一种使用 LLMs 构建个人知识库的模式

这是一个想法文件，旨在被复制粘贴到你自己的 LLM Agent（例如 OpenAI Codex、Claude Code、OpenCode / Pi 等）。其目标是传达高层次的想法，但你的 Agent 将与你协作构建具体细节。

大多数人使用 LLMs 和文档的体验都类似于检索增强生成（RAG）：上传一组文件，LLM 在查询时检索相关片段并生成回答。这虽然可行，但 LLM 在每个问题上都要从头重新发现知识，没有知识积累。如果提出一个需要整合五份文档的微妙问题，LLM 每次都必须找到并拼凑相关片段，没有任何内容被积累起来。NotebookLM、ChatGPT 的文件上传功能以及大多数检索增强生成系统都是这样工作的。

这里的思路有所不同。与仅在查询时从原始文档中检索信息不同，LLM **逐步构建并维护一个持久的维基知识库** ——这是一个结构化、相互关联的 Markdown 文件集合，位于你和原始源文件之间。当你添加新的源文件时，LLM 不仅仅是为后续检索建立索引。它会读取该文件，提取关键信息，并将其整合到现有的维基知识库中——更新实体页面、修订主题摘要、记录新数据与旧说法的矛盾之处、强化或挑战不断发展的综合内容。知识被一次性编译，然后 *保持最新* ，而不是在每次查询时重新推导。

这是关键区别： **维基是一个持久且不断积累的成果。** 交叉引用已经存在。矛盾已被标记。综合内容已经反映了你所阅读的一切。每添加一个来源和每提出一个问题，维基都会变得更加丰富。

你从不（或很少）自己编写维基 — LLM 编写并维护所有内容。你负责信息搜集、探索以及提出正确的问题。LLM 承担所有基础工作 — 总结、交叉引用、归档和记录，这些工作能让知识库随着时间推移真正发挥作用。实际上，我一边打开 LLM 代理，另一边打开 Obsidian。LLM 根据我们的对话进行编辑，我实时浏览结果 — 跟随链接、查看图谱视图、阅读更新后的页面。Obsidian 是 IDE；LLM 是程序员；维基是代码库。

这适用于很多不同的场景。举几个例子：

- **个人** ：跟踪自己的目标、健康、心理和自我提升——记录日记条目、文章、播客笔记，并随着时间的推移构建起对自己的结构化认知。
- **研究** ：深入研究一个主题，持续数周或数月——阅读论文、文章和报告，并逐步构建一个内容全面的维基百科，同时论文观点不断演进。
- **阅读书籍** ：归档每一章内容，为角色、主题、情节线索以及它们之间的关联构建页面。最终你会拥有一个丰富的配套维基。想想像 [托尔金之门](https://tolkiengateway.net/wiki/Main_Page) 这样的粉丝维基——数千个相互关联的页面，涵盖角色、地点、事件、语言，由志愿者社区多年来共同构建。你可以在阅读时亲自构建类似的东西，让 LLM 完成所有的交叉引用和维护工作。
- **业务/团队** ：由 LLMs 维护的内部维基，由 Slack 线程、会议记录、项目文档、客户通话提供内容。可能有人工参与审核更新。该维基保持最新是因为 LLM 承担了团队中无人愿意做的维护工作。
- **竞争分析、尽职调查、旅行规划、课程笔记、爱好深度探索** ——任何你需要随着时间积累知识，并且希望将这些知识整理好而非零散存放的事情。

#### Architecture

There are three layers:

**原始来源** — 您精心整理的源文档集合。文章、论文、图像、数据文件。这些是不可变的 — LLM 从这些源读取数据但从不修改它们。这是您的事实依据。

**The wiki** — LLM 生成的 Markdown 文件的目录。摘要、实体页面、概念页面、对比、概述、综合。LLM 完全拥有这一层。它创建页面，当有新来源出现时更新页面，维护交叉引用，并保持所有内容的一致性。你阅读它；LLM 撰写它。

**架构** — 一个文档（例如，Claude Code 对应的文件为 CLAUDE.md，Codex 对应的文件为 AGENTS.md），它告诉大语言模型（LLM）维基的结构是怎样的、有哪些约定，以及在摄取资料、回答问题或维护维基时应遵循的工作流程。这是关键的配置文件——它使 LLM 成为一个有纪律的维基维护者，而不是一个通用的聊天机器人。随着你逐步明确什么适合你的领域，你和 LLM 会随着时间共同演进这个架构。

#### Operations

**导入** 。你将新的源文件导入原始集合，并指示 LLM 进行处理。一个示例流程如下：LLM 读取源文件，与你讨论关键要点，在 wiki 中撰写摘要页面，更新索引，更新 wiki 中相关的实体和概念页面，并在日志中添加一条记录。单个源文件可能涉及 10-15 个 wiki 页面。就我个人而言，我更喜欢逐个导入源文件并保持参与——我会阅读摘要，检查更新，并指导 LLM 关注重点。但你也可以一次性批量导入多个源文件，只需较少的监督。由你决定制定符合你风格的工作流程，并将其记录在模式中，以便未来的会话使用。

**查询.** 你针对维基提问。LLM 搜索相关页面，阅读这些页面，并综合出带有引用的答案。答案可以根据问题以不同形式呈现——一个 Markdown 页面、一个对比表格、一个幻灯片（Marp）、一个图表（matplotlib）、一个画布。重要的见解是： **好的答案可以作为新页面重新归档到维基中。** 你要求的对比、一次分析、你发现的关联——这些都很有价值，不应消失在聊天记录中。这样，你的探索会像被纳入的资料一样，在知识库中不断累积。

**Lint.** 定期地，让 LLM 对维基进行健康检查。需要检查的内容包括：页面之间的矛盾、被新来源取代的过时说法、没有入站链接的孤立页面、被提及但缺乏自身页面的重要概念、缺失的交叉引用，以及可通过网络搜索填补的数据空白。LLM 擅长提出需要调查的新问题和需要查找的新来源。这有助于维基在发展过程中保持健康。

两个特殊文件帮助 LLM（以及你）在维基随着规模增长时进行导航。它们有不同的用途：

**index.md** 以内容为导向。它是维基百科（wiki）中所有内容的目录——每个页面都列出了一个链接、一行摘要，以及可选的元数据（如日期或来源数量）。按类别组织（实体、概念、来源等）。LLM 会在每次数据摄取时更新该目录。在回答查询时，LLM 会首先读取该索引以找到相关页面，然后深入查看这些页面。这种方法在中等规模（约 100 个来源、约数百个页面）下效果出奇地好，并且避免了对基于嵌入的 RAG 基础设施的需求。

**log.md** 是按时间顺序排列的。它是一个仅追加的记录，记录了发生的事情和时间——数据导入、查询、代码检查通过。一个有用的提示：如果每条记录以一致的前缀开头（例如 `## [2026-04-02] ingest | Article Title` ），则日志可以用简单的 Unix 工具解析—— `grep "^## \[" log.md | tail -5` 可以获取最后 5 条记录。该日志为你提供维基的发展时间线，并帮助 LLM 了解最近完成的工作。

有时你可能想要构建一些小工具，帮助 LLM 更高效地在 wiki 上运行。维基页面的搜索引擎是最明显的一个——小规模时索引文件就足够了，但随着 wiki 的增长，你需要完善的搜索功能。 [qmd](https://github.com/tobi/qmd) 是个不错的选择：它是一个针对 markdown 文件的本地搜索引擎，采用混合 BM25/向量搜索和 LLM 重排序，所有功能都在设备端运行。它同时提供 CLI（这样 LLM 可以调用它）和 MCP 服务器（这样 LLM 可以将其用作原生工具）。你也可以自己构建更简单的工具——当有需要时，LLM 可以帮你即兴编码一个简单的搜索脚本。

- **Obsidian Web Clipper** 是一个将网页文章转换为 Markdown 的浏览器扩展。对于快速将来源内容纳入你的原始集合非常有用。
- **本地下载图片** 。在 Obsidian 设置 → 文件和链接 中，将“Attachment folder path”设置为固定目录（例如 `raw/assets/` ）。然后在设置 → 快捷键 中，搜索“Download”找到“Download attachments for current file”并将其绑定到一个快捷键（例如 Ctrl+Shift+D）。截取文章后，按下该快捷键，所有图片都会被下载到本地磁盘。这是可选的但很有用——它可以让 LLM 直接查看和引用图片，而不是依赖可能失效的 URL。请注意，LLM 无法一次性原生读取带有内联图片的 Markdown——变通方法是让 LLM 先读取文本，然后单独查看部分或全部引用的图片以获取更多上下文。这有点麻烦，但效果还不错。
- **Obsidian 的图谱视图** 是查看你的知识库结构的最佳方式——哪些内容相互关联，哪些页面是中心节点，哪些是孤立页面。
- **Marp** 是一种基于 Markdown 的幻灯片格式。Obsidian 有一个针对它的插件。可直接从维基内容生成演示文稿，非常有用。
- **Dataview** 是一款 Obsidian 插件，可对页面前置元数据执行查询。如果您的 LLM 向 Wiki 页面添加 YAML 前置元数据（标签、日期、来源计数），Dataview 可以生成动态表格和列表。
- 这个维基其实就是一个存放 Markdown 文件的 Git 仓库。你可以免费获得版本历史、分支和协作功能。

维护知识库的繁琐部分不在于阅读或思考——而在于记账。更新交叉引用、保持摘要最新、记录新数据何时与旧说法矛盾、确保数十页内容的一致性。人们放弃维基是因为维护负担的增长速度超过了其价值。LLMs 不会感到厌烦，不会忘记更新交叉引用，并且可以一次性处理 15 个文件。维基能够保持维护状态，因为维护成本几乎为零。

人类的工作是筛选并整理资料、指导分析、提出好问题，并思考这一切的意义。LLM 的工作是其他所有事情。

这个想法在精神上与万尼瓦尔·布什（Vannevar Bush）的 Memex（1945 年）相关——这是一个个人化的、经过精心整理的知识存储系统，其中文档之间存在关联路径。布什的愿景比网络后来的样子更接近这一理念：私密的、经过积极整理的，文档之间的关联与文档本身同样有价值。他未能解决的问题是谁来进行维护。而 LLM 负责了这一点。

#### Note

本文刻意保持抽象性。它描述的是理念而非具体实现。确切的目录结构、模式规范、页面格式、工具链——所有这些都取决于您的领域、偏好以及所选择的 LLM。上述所有内容均为可选且模块化——选择有用的部分，忽略无用的部分。例如：您的源数据可能仅为纯文本，因此完全不需要图像处理。您的 Wiki 可能规模较小，只需索引文件即可，无需搜索引擎。您可能不关心幻灯片，只想要 Markdown 页面。您可能需要完全不同的输出格式集。使用本文档的正确方式是将其与您的 LLM 代理共享，并共同协作实例化一个符合您需求的版本。本文档的唯一作用是传达模式，其余部分由您的 LLM 自行处理。

#### 《llm-wiki》核心总结

##### 一、这篇文章在讲什么

这篇文章提出了一种新思路：  
不是把文档丢给 LLM，让它每次提问时临时检索、临时拼答案；而是让 LLM 持续维护一个 “个人维基知识库”。

这个维基是一个由 Markdown 文件组成、可持续更新、相互链接的知识系统。  
**核心价值**在于：知识会被 “沉淀” 和 “积累”，而不是每次都从零开始生成。

---

##### 二、它和传统 RAG 的本质区别

###### 传统方式：每次都重新找答案
常见的 RAG 模式，本质上是：
- 上传资料
- 提问时检索片段
- LLM 临时拼接回答

问题是：
- 没有长期记忆
- 没有知识沉淀
- 多文档综合能力依赖每次临场发挥
- 矛盾、关联、演化都难以保留下来

###### llm-wiki：先把知识 “编译” 进维基
新模式是：
- LLM 读取新资料
- 提炼关键信息
- 更新已有页面
- 建立交叉引用
- 标记冲突和变化
- 让维基持续演进

也就是说，**知识不是 “查出来的”，而是 “积累出来的”**。

---

##### 三、核心理念：人负责思考，LLM 负责维护

这套模式中，分工非常清晰：

###### 人负责
- 收集和筛选信息
- 提出问题
- 指导分析重点
- 判断什么重要

###### LLM 负责
- 总结内容
- 更新页面
- 建立链接
- 记录冲突
- 维护一致性
- 归档查询结果

一句话概括：  
**人做判断，LLM 做知识管理的脏活累活。**

---

##### 四、系统结构：三层架构

###### 1. 原始来源层
这是原始材料库，比如：
- 文章
- 论文
- 图片
- 数据文件
- 会议纪要

特点是：**只读、不修改，是事实依据。**

###### 2. Wiki 层
这是由 LLM 维护的知识库，内容包括：
- 摘要页
- 实体页
- 概念页
- 对比页
- 综合分析页

特点是：**LLM 全权维护，你主要负责阅读和使用。**

###### 3. 架构规则层
这是给 LLM 的 “操作手册”，用于规定：
- Wiki 怎么组织
- 页面怎么命名
- 导入资料时怎么处理
- 查询和维护时遵循什么流程

本质上，这是把 LLM 从 “聊天机器人” 变成 “知识库维护员” 的关键。

---

##### 五、它是怎么运转的

##### 1. 导入资料
每加入一份新资料，LLM 会：
- 阅读内容
- 提炼重点
- 写摘要页
- 更新相关页面
- 补充索引
- 记录到日志

一份资料可能影响很多页面。  
因此知识库会不断变得更完整，而不是简单地堆文件。

##### 2. 查询知识库
当你提问时，LLM 不是直接翻原始文档，而是优先读 Wiki。  
这样回答会更快、更系统，也更容易形成综合判断。

更重要的是：  
**好的问答结果还可以反向写回 Wiki，成为新的知识资产。**

##### 3. 定期 “体检”
LLM 还可以定期检查 Wiki 的健康度，比如：
- 是否有页面互相矛盾
- 是否存在过时内容
- 是否有孤立页面
- 是否缺少关键概念页
- 是否有待补充的新问题或新资料

这相当于给知识库做持续运营。

---

##### 六、为什么这个模式有价值

###### 1. 解决知识管理最大痛点：维护成本
传统知识库难以长期坚持，不是因为没人愿意思考，  
而是因为没人愿意一直做这些琐事：
- 更新链接
- 修正文档
- 保持一致性
- 处理新增信息和旧结论的冲突

LLM 的优势正好在这里：  
**它不嫌麻烦，适合做高频、重复、细碎的维护工作。**

###### 2. 让知识真正 “复利”
每次导入资料、每次提问、每次分析，都会留下结构化成果。  
久而久之，知识库会越来越强，而不是聊天记录越堆越乱。

###### 3. 适用场景非常广
它不仅适用于研究，还适用于：
- 个人成长与自我管理
- 阅读和学习
- 团队内部知识库
- 竞争分析和尽调
- 旅行规划
- 课程笔记
- 长期兴趣研究

本质上，只要你需要 “长期积累认知”，这个模式都适用。

---

##### 七、配套工具的意义

文章提到了一些工具，但重点不是工具本身，而是它们在系统中的角色：

###### 索引与日志
- `index.md`：知识地图，方便按主题找内容
- `log.md`：时间线，记录知识库怎么演化

###### Obsidian

##### 1. 问题背景：传统 RAG 的局限

- 现在多数人使用 LLM + 文档的方式，本质上是 RAG：上传文件，提问时再检索片段并生成答案。

- 作者提出在“原始资料”和“最终回答”之间，增加一层由 LLM 持续维护的 **Markdown Wiki**。

  - 提取关键信息

- Wiki 是一个**持久、可积累的成果**。
- 交叉引用已经存在。
- 矛盾已经被标记。
- 综合结论会随着资料增加而演化。

**一个直观例子：**

**共同特点：** 都属于“知识需要长期积累，而且不能只是零散堆放”的场景。

---

##### 5. 架构设计：三层结构

作者将整体架构分成三层：

###### 1）原始来源（Raw Sources）
- 这是你整理好的源文档集合，比如：
  - 文章
  - 论文
  - 图片
  - 数据文件
- 这些文件是**不可变的**，LLM 只读取，不修改。
- 它们是整个系统的“事实依据”。

###### 2）Wiki
- 这是由 LLM 生成的一组 Markdown 文件。
- 内容包括：
  - 摘要页
  - 实体页
  - 概念页
  - 对比页
  - 综述页
  - 综合分析页
- 这一层完全由 LLM 维护：创建页面、更新页面、维护链接、保持一致性。

###### 3）架构说明文件
- 比如在不同 Agent 中，可能是 `CLAUDE.md` 或 `AGENTS.md`。
- 这个文件定义：
  - Wiki 的结构
  - 页面约定
  - 导入资料时的流程
  - 回答问题时的流程
  - 维护规则
- 作者认为这是**关键配置文件**，因为它能让 LLM 不只是聊天，而是成为一个“有纪律的 Wiki 维护者”。

---

##### 6. 核心操作流程：导入、查询、巡检

##### 6.1 导入（Ingest）

- 当你添加新的源文件后，LLM 会执行一系列动作：
  - 读取源文件
  - 与你讨论关键点
  - 在 Wiki 中撰写摘要页
  - 更新索引
  - 更新相关实体页和概念页
  - 在日志里记录一次变更
- 作者提到：**一个源文件可能会影响 10–15 个 Wiki 页面**。

**作者的偏好：**
- 更喜欢**逐个导入**并保持参与感：
  - 自己先读摘要
  - 检查更新
  - 指导 LLM 关注重点
- 但也可以选择批量导入，减少监督。

---

##### 6.2 查询（Query）

- 用户不是直接问原始文档，而是问 Wiki。
- LLM 的过程是：
  - 搜索相关页面
  - 阅读这些页面
  - 综合输出答案，并附上引用
- 输出形式可以很多样：
  - Markdown 页面
  - 对比表格
  - Marp 幻灯片
  - matplotlib 图表
  - 画布

**很重要的一点：**
- 好的查询结果不应只停留在聊天记录里，而应**重新归档回 Wiki**。
- 比如你让 LLM 做的一次对比分析、一次关联发现，本身就是新的知识资产。

**通俗理解：**  
不仅资料会进入知识库，连“你的思考过程”也可以进入知识库。

---

##### 6.3 巡检（Lint）

- 文章建议定期让 LLM 对 Wiki 做“健康检查”。
- 检查内容包括：
  - 页面之间是否有矛盾
  - 是否有说法已经被新资料推翻
  - 是否有孤立页面（没有入站链接）
  - 是否提到了重要概念却没有独立页面
  - 是否缺少交叉引用
  - 是否存在可以通过网络搜索补齐的数据空白
- LLM 还可以主动提出：
  - 还需要调查哪些问题
  - 还应该补充哪些来源

**意义：**  
这让 Wiki 不只是“越积越多”，而是能“越积越健康”。

---

##### 7. 两个关键文件：`index.md` 和 `log.md`

###### `index.md`：按内容导航
- 它相当于 Wiki 的总目录。
- 每个页面通常包含：
  - 链接
  - 一行摘要
  - 可选元数据（如日期、来源数量）
- 按类别组织，比如实体、概念、来源等。
- 每次导入新资料时，LLM 都会更新它。

**作者强调的一个数据点：**
- 在**中等规模**下，这种方式已经很有效：
  - 约 **100 个来源**
  - 约 **数百个页面**
- 在这个规模上，光靠 `index.md` 就能很好工作，甚至**不需要基于 embedding 的 RAG 基础设施**。

###### `log.md`：按时间导航
- 这是一个只追加的时间线日志，记录：
  - 导入了什么
  - 做了哪些查询
  - 执行了哪些巡检
- 作者给了一个具体格式示例：
  - `## [2026-04-02] ingest | Article Title`
- 这样就可以用简单 Unix 命令解析，例如：
  - `grep "^## \[" log.md | tail -5`
- 这个命令可以快速取出**最近 5 条记录**。

**作用：**
- 帮助人快速看知识库最近发生了什么
- 也帮助 LLM 理解近期更新上下文

---

##### 8. 工具建议：从“能用”到“更高效”

文章提到了一些配套工具：

###### 搜索工具
- 当 Wiki 规模较小时，`index.md` 足够。
- 规模继续增长后，需要更好的搜索能力。
- 作者推荐 **qmd**：
  - 面向 Markdown 的本地搜索引擎
  - 使用 **BM25 + 向量搜索 + LLM 重排序**
  - 全部在本地设备运行
  - 同时提供 CLI 和 MCP Server

###### 网页采集
- 推荐 **Obsidian Web Clipper**
- 可把网页文章快速转换成 Markdown，并纳入原始资料库

###### 图片本地化
- 作者建议把 Obsidian 的附件目录固定到如 `raw/assets/`
- 再给“下载当前文件附件”绑定快捷键，例如 **`Ctrl+Shift+D`**
- 这样网页中的图片也会保存到本地

**原因：**
- 让 LLM 可以直接查看和引用图片，而不是依赖可能失效的 URL

**限制也有说明：**
- LLM 目前不能一次性很好地原生读取带有内联图片的 Markdown
- 变通方式是先读文本，再单独查看相关图片
- 作者认为“有点麻烦，但总体可行”

###### 可视化与展示
- **Obsidian 图谱视图**：看知识结构、中心节点、孤立页面
- **Marp**：把 Wiki 内容转成演示文稿
- **Dataview**：如果页面有 YAML 前置元数据，就可以动态生成表格和列表

###### 版本管理
- 整个 Wiki 本质上就是一个 **Markdown 文件的 Git 仓库**
- 因此天然拥有：
  - 版本历史
  - 分支
  - 协作能力

---

##### 9. 这套模式为什么成立

- 作者认为，知识库难维护，不是因为“阅读和思考太难”，而是因为“记账工作太烦”：
  - 要更新交叉引用
  - 要保持摘要最新
  - 要记录新数据与旧结论是否冲突
  - 要确保几十个页面彼此一致
- 很多人放弃 Wiki，正是因为维护成本增长得比价值更快。

而 LLM 的优势刚好在这里：
- 不会厌烦
- 不会忘记补交叉引用
- 能同时处理很多页面
- 文中举例说，LLM 可以**一次处理 15 个文件**

**结论：**
- 过去 Wiki 难以持续，是因为维护成本高；
- 现在它可能重新可行，是因为维护成本被 LLM 大幅压低，接近于零。

---

##### 10. 思想来源：接近 Memex 的现代实现

- 作者把这个想法与 **Vannevar Bush 在 1945 年提出的 Memex** 联系起来。
- Memex 的愿景是：
  - 个人化
  - 私密
  - 经过主动整理
  - 文档之间的“关联路径”与文档本身同样重要
- 作者认为，这个设想其实比后来开放式互联网更接近本文方案。

**关键补足点：**
- Bush 当年没解决的问题是：**谁来维护这些关联与整理工作？**
- 而现在，LLM 正好可以承担这部分工作。

---

##### 11. 作者最后的提醒：这是一种模式，不是固定实现

- 文章刻意保持抽象，不提供唯一正确的目录结构或工具链。
- 具体实现要根据你的：
  - 领域
  - 偏好
  - 所选 LLM
- 文中所有组件都是**可选、模块化**的。

作者给出几个例子说明灵活性：
- 如果源数据只有纯文本，就不需要图像处理
- 如果 Wiki 很小，索引文件就够了，不需要搜索引擎
- 如果不关心演示文稿，就只保留 Markdown 页面
- 如果有别的输出格式需求，也可以自行定义

**最终建议：**
- 把这篇文档交给你的 LLM Agent
- 与它一起把这个抽象模式实例化成适合你自己的版本

---

#### 一句话总结

这篇文章的核心是在说：**把 LLM 从“临时回答问题的助手”升级为“持续维护个人/团队知识库的编辑与管理员”**，让知识真正形成结构、关系和演化，而不是停留在一次次对话里。
