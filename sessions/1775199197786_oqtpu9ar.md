还是来正本清源一下 Engineering Harness 到底应该怎么做吧，过去几个月大家甚嚣尘上不需要工程师了，2 小时随手 Vibe 一下复刻一个应用的新闻很多。

但是软件开发的核心挑战从来不是写 Code，而是管理复杂性。在 Vibe Code 下，因为代码吞吐量的进一步上升，我们的确有了更好的工具，但是同样复杂性也进一步上升了。

如果有了更好的工具，你还是只是复刻一个所有人都做了的产品，又有什么价值和意义呢？比如 Typless 很好，所以大家都来复刻一个语音输入法（我们其实在自己的产品里也内嵌了），但是这个时候一个语音输入法本身已经在市场上没有商品价值了，更像是一个一次性吸引流量的工具了。

所以我们不得不去在更短的时间内，做一个规模更大，更复杂的产品。而这个带来了更大的挑战，其实更需要工程师了，但是对于工程师的要求也变得更高了。

请刚开始 vibe coding 的你们不要因为 copy paste 了一下别人的项目，就发一些暴论来误导大家

1. Worktree 同样是独立有一个工作目录
2. 项目随时间变动 git size 越来越大
3. 考虑到 agent 自主运行，一般 workspace 都是放在 devcontainer 内的，启动多个目录多个 devcontainer 会极大地增加内存需求和负担
4. 既然本身要走 PR 合并也就不存在本地 worktree 之间互相干扰的问题

没必要worktree，可以 clone 几份放在固定的目录，轮着用就够了，每次pull最新然后checkout一个新的branch，完成后提PR合并到main

[@dotey](https://twitter.com/dotey) 请教monorepo太大导致没法git worktree，如何更好的并行开发？

AI Coding 的能力很强，但是一旦你以团队方式运作，并且希望在短时间内发布一个复杂产品，就会带来巨大的复杂性管理的挑战。

今天如果你有 10 个工程师在一个 Codebase 里工作，实际的代码量大约是过去 50 个人的工作量。无论是 Claude Code 还是 CodeX 虽然能力都很强，但是如果不做好复杂性管理，代码仍然腐化得非常之快。

原因也很简单，就是 Claude Code 和 CodeX 进行 Agent Coding 的机制决定的，他们并不会读完所有的代码来Coding ，仍然是阅读部分代码来叠加式的实现新功能。

所以你很容看到是不是出现大量的重复代码，几千行代码的单个文件/组件，欠缺考虑的并发性问题。

而 Engineering Harness 中有一半工作就是要尝试尽可能地减少这些问题，来管理这个复杂性，（另一半是给到对于环境的更完整的可观测性和可操作性来让 Agent 可以更持续地完成工作）。

而管理这些复杂性的手段并不新，其实就是来自过去几十年来软件工程的所有实践。在我们开发 [zooclaw.ai](http://zooclaw.ai) 这个产品的过程里，我们目前维护了这样一套 harness 来尽可能保障质量和提升效率：

1. Mono Repo + Dev Container
2. 通过 GitHub Actions 触发的 auto-review 以及 auto-merge
3. 一系列 pre-commit hook + ci/cd 的各类 lint 规则
4. BDD 风格的高覆盖率的自动化测试
5. 自动触发的 E2E Test 以及对应自动截屏供人工审核
6. 每周自动触发的完整代码的 code review 与自动创建 issue

其实离理想的质量维护目标仍然有巨大的距离（因为现在 Vibe Coding 提一个 PR 的成本实在太低了），但是的确对维护代码的基本质量还是非常有帮助的。

下面我一一来解释每一项具体我们做了什么，以及为什么做这些选择。

#### zooclaw #aicoding

1. Mono Repo + Dev Container

我们一直是使用 devcontainer 的，但是最近才切换到使用 mono-repo。原因是 Coding Agent 的能力，只有在 mono-repo 里才能更好地发挥出来。

因为在当前 Coding Agent 的能力下，交付产品的瓶颈迅速变成了两个节点：

1\. 人与人之间因为分工不得不进行的沟通。

2\. 实际产品最终还是需要完成上线测试验收，但是 staging 环境我们往往只部署一套。

所以解决方案就是

1\. 减少不必要的沟通，不要区分前后端，尽量让一个人能完成完整一整个功能。

2\. 尽量每个人可以在自己的开发环境里就能部署起一套完整的产品，自己完成完整功能的验收。

而 mono-repo + devcontainer 完美解决了这个问题，devcontainer 里包含了绝大部分的服务代码（有一个公司层面的基建不在其中，但是因为一般那些基础组件的代码不会变更和修改，可以共享一套 dev/staging 环境），以及devcontainer 本身同时启动了各类依赖的 cache/db 中间件。所以任何一个人，可以有一个自己独立完整的环境测试完代码。

因为 devcontainer 也免去了大家搭建环境需要浪费的时间，事实上，我们现在的设计师和产品经理，都是直接基于 devcontainer 来 vibe design，直接修改前端交互界面，给工程师提 PR 的。

1. 通过 Github 强制触发的 auto-review

因为 LLM 的 next token prediction 的原理，在同一个 context 下他总是更倾向于认为自己是对的。同时，在目前的 PR 提交量下，也很难让每个 PR 都得到充分的 Review。

所以，最简单直接的方式就是让另一个 AI 来 Review。Claude Code 和 CodeX 都提供了 Github Actions，你很容易设置对任何 PR 进行 Code Review，并且你可以定义自己的 Prompt 和 checklist，完全满足每个项目自己特定的要求。

因为这些 Code Review Actions 是在一个干净崭新的 Context Window 里，所以往往能找到不少代码里的问题。对于 Review 的结果，我们通过让 Action 给 GitHub PR 打不同的 Tag 来进行三档规则性的标注，在减轻人的负担的情况下，又能保障质量：

1. Low Risk Auto-Merge，也就是 AI 觉得代码完全没有问题，可以直接合并。这种情况下我们基本就自动合并了。
2. Need Human Review，往往这种情况下，是有一些决策或者瑕疵，AI 觉得不好判断，让人来看。因为具体的 Review 内容是以 Github PR 的 Comments 出现的，人往往只需要关注 AI 跳出来需要人确认的部分来看。这类我们不 block merge，也就是任何人看了觉得不用改一样可以合并代码
3. Request Change，这个情况是 AI 觉得有些地方有问题，要求修改，这类问题我们强制要求必须 Fix。除非找到项目或者团队的管理员人工确认 AI 看错了，不然不能合并。

目前我们还没有做到模型层面的对抗（就是用 Claude Code 写的代码让CodeX 来 review，CodeX写的代码用 Claude Code 来 review）。但是这个也是在我们下一步的计划里的。

1. 一系列的 Pre-Commit hook + CI/CD 的各类 lint 规则。

其实原来大家开发的过程中也用各种 Lint，但是过去因为人写代码的交付速度问题，往往设置的 Lint 规则比较简单，规则也通常比较松，因为最后拦截质量问题的是人的 Code Review。

但是在当前的Coding Agent 能力使得我们增加了更多的 Lint：

1\. 因为增加一个 Lint 也更容易了

2\. 因为代码吞吐量太大了，Lint 本身能为我们捕捉到很多问题

我们目前主要是有这样一系列的 Lint：

1\. Coding Format 和 Typecheck，但是比传统的更严格，因为 Fix Lint 问题本身变得容易了。外加每个人用的 Coding Agent 可能不同，就会有不同习惯的风格，不限制 Coding Format 会出现很多 Diff 里其实只是 format 改变。

2\. 单个文件行数限制，圈复杂度限制，代码重复率限制。

比如，单个 python 文件不超过 X 行，单函数圈复杂度不超过 Y，功能代码重复率不超过 U，测试代码重复率不超过 V。

3\. 更复杂的一些模块依赖限制，代码规则限制。比如 fastapi 的 routes 不能直接访问 DB，css 必须是 semantic 的。

所有 lint 都是以确定性的代码来限制，而不是 prompt。过去几十年其实软件工程里已经有了大量的武器来管理复杂度了，直接用就好了，没有必要用 LLM再发明一遍。这些 lint 工具稳定、快速、便宜。

而且因为 AI Coding 的存在，你要自定义写一个新的 Lint 也非常容易。

其中部分 Lint 也是 Warning，即发生了需要人来确认。其他的则是规则，需要强制通过。并且一些运行快速的 Lint 直接会放在 Pre-Commit hook 里。

因为团队都使用 devcontainer，使得 Pre-Commit hook自动会安装和强制运行，也比较节约大家的时间。

1. BDD 风格的高覆盖率的自动化测试。

除了 Lint 之外，另一个保障尽量不出 Bug 的就是 Testing。但是和 Pre-AI 时代的测试有两个变化：

1. 因为使用了 devcontainer，devcontainer 里已经起了 DB/Cache 的服务，所以测试可以少一些 Mock，直接 Hit 到真实的 DB 和 Cache，尽量能够测试到完整正式的链路。并且现在的开发模式也是并行多个窗口 Agent 自己在跑，硬件的性能也很好，没有必要都 Mock。Mock 往往漏掉了很多真实的场景。
2. 测试尽可能直接用 BDD 风格的测试为主，人去 Review AI 写的测试的时候，也是 Review BDD 的自然语言描述为主，而不是去看实际的测试代码。因为测试通常复杂度比功能代码低，所以出错的概率也比较低，直接看 BDD 的业务逻辑描述就足够了。

让测试覆盖率超过 90% 以上，以捕捉到尽可能多的错误。但是不强求数字，如果提升覆盖率是靠海量的 Mock 没有实际意义也可以不做。

但是有意义的测试覆盖率本身反馈了代码质量，大量不得不 mock 才能测试的代码往往意味着设计或者代码质量本身存在问题。

1. 自动触发的 E2E Test 以及对应自动录屏供人工审核

光有 BDD 风格的测试还是不够的，BDD 风格的测试往往仍然是单模块的（比如单独测试前端组件，或者后端API）。

所有系统联通在一起的场景没有办法通过 BDD 覆盖到，Agent 类型的产品，是否 AI 正确回答了相关问题也无法通过 BDD 测试覆盖到。

我们会在 CI/CD 的 Tag 触发完成部署 Staging 环境和 Production 环境后，自动触发实际操作线上系统的端到端测试（E2E），以覆盖实际使用产品的各种场景。

这个时候，测试是实际通过浏览器操作线上真实的功能，并且在传统意义上的功能的 assertion 之外，还会加上 LLM Judge 的断言来判断功能是否正确。

并且所有的测试都会自动录屏，无论测试是否通过，都可以直接看一下录屏来判断基本的功能，Agent 效果和交互是否正确。

1. 每周自动 code review 和创建 issue

即使在有了上述的所有动作，代码其实仍然因为交付速度会快速腐化。所以代码本身需要更频繁的小规模重构。

这些小规模的重构，就依赖通过 Github Actions 自动触发的对于完整代码的 Code Review。这个 Review 核心不是看逻辑正确性，而是看代码的 Architecture 是否仍然正确。

对应的 Review 结果会以 Github Issues 的形式出现，然后让人工去跟进判断是否再通过 AI Coding 来解决。

类似于一个定时的垃圾回收或者 Memory Compaction 的操作。

## 通俗精炼（1）

### 2026-04-03 06:53:17

#### Engineering Harness 的本质：不是替代工程师，而是放大工程能力

##### 核心观点

这篇文章的核心结论很明确：**AI Coding 提高的不是 “写代码” 效率，而是 “制造复杂性” 的速度**。  
所以，软件开发的关键问题从来不是代码生成，而是**如何管理复杂性、保障质量、维持协作效率**。

换句话说，AI 没有让工程师变得不重要，反而让团队更需要工程师，只是对工程师的要求从 “会写代码” 升级为 “会设计系统、管控复杂度、搭建流程”。

##### 为什么 “2 小时复刻产品” 没有真正价值

作者认为，很多 “随手复刻一个应用” 的案例，本质上只是展示了工具变强了，但**不代表产品有价值**。  
因为当一个功能已经能被快速复制时，它本身往往就不再具备商业壁垒，只能成为短期流量工具。

因此，团队真正要做的，不是重复别人做过的东西，而是借助 AI 在更短时间内交付**更大、更复杂、真正有差异化的产品**。

##### AI 时代，真正的挑战是什么

问题主要来自两个方面：

###### 1. 代码产能暴涨，代码腐化更快
AI 不会完整读懂整个系统，而是基于局部上下文不断叠加实现功能。  
这很容易带来：
- 重复代码越来越多
- 单文件、单组件越来越臃肿
- 架构边界被破坏
- 并发、依赖、测试等问题被忽略

###### 2. 团队协作复杂度急剧上升
当 10 个工程师都借助 AI 工作时，实际产出的代码量可能接近过去 50 人。  
这意味着团队的问题不再是 “写不出来”，而是：
- 谁在改什么
- 改动是否可控
- 质量是否稳定
- 架构是否持续恶化

##### Engineering Harness 是什么

作者把解决方案概括为**Engineering Harness**。  
它本质上是一套 “约束 + 观测 + 自动化” 的工程体系，用来让 AI 在团队中稳定产出，而不是失控堆代码。

可以理解为：**让 AI 不是一个会写代码的玩具，而是一个可管理、可审查、可验证的生产力单元**。

##### 作者给出的实践方案

###### 1. Mono Repo + Dev Container
目标是让每个人都能在本地拥有一套完整、可运行、可验收的环境。  
这样可以减少前后端分工带来的沟通成本，也避免大家争抢同一个 staging 环境。

本质价值是：**让一个人尽量独立完成完整功能闭环**。

###### 2. AI 自动 Review
因为 AI 写的代码不适合完全靠人工逐条审，最直接的方法就是让另一个 AI 来审。  
作者用 GitHub Actions 自动触发 Review，并把结果分成三类：
- 可自动合并
- 需要人工确认
- 必须修改后再合并

核心思路是：**把人工 Review 从 “全面检查” 变成 “重点决策”**。

###### 3. 更严格的 Lint 和规则约束
过去很多规范比较宽松，因为主要靠人兜底。  
但 AI 时代代码量太大，必须把更多规则前置为机器约束，比如：
- 格式和类型更严格
- 限制单文件长度、函数复杂度、重复率
- 限制模块依赖关系和编码方式

本质上是：**能用确定性规则拦住的问题，不要交给人和模型反复判断**。

###### 4. 高覆盖率的 BDD 测试
作者强调，测试要尽量少 Mock，多跑真实链路。  
同时测试描述尽量用 BDD 风格，让人主要审业务描述，而不是陷入测试代码细节。

重点不是机械追求覆盖率数字，而是追求**有业务意义的覆盖率**。

###### 5. 自动化 E2E + 录屏审核
单元测试和模块测试不够覆盖真实用户场景，因此还要在部署后自动跑 E2E。  
而且不只看断言是否通过，还要配合录屏和 LLM 判断结果是否符合预期。

这一步解决的是：**真实系统联动后的 “最后一公里问题”**。

###### 6. 定期全量代码审查
即使前面都做了，代码仍然会随着高速迭代而腐化。  
所以还需要定期对整个代码库做架构级 Review，并自动生成 Issue，推动小步重构。

这相当于给代码库做持续性的 “垃圾回收” 和 “整理压缩”。

##### 对产品和团队的启发

这篇文章对产品团队最大的提醒是：  
**AI 不是简单地把开发成本打到接近零，而是把 “复杂产品的组织方式” 变成新的竞争门槛。**

未来真正拉开差距的，不是谁先用上 AI，而是：
- 谁能把 AI 纳入标准工作流
- 谁能建立稳定的质量控制体系
- 谁能让小团队持续交付复杂产品
- 谁能在高速度下仍保持架构健康

##### 一句话总结

**AI Coding 提升的是代码生成速度，但决定团队上限的，仍然是工程体系。**  
谁能把复杂性管住，谁才能真正把 AI 变成生产力，而不是技术债制造机。

## 结构化（1）

### 2026-04-03 06:54:25

#### 主旨概括

这篇文章的核心观点是：**AI 并没有让工程师 “不重要”，反而因为代码产出速度大幅提升，软件开发中 “管理复杂性” 的挑战变得更突出，工程师和工程体系（Engineering Harness）因此更重要了。**  
作者强调，真正的竞争力不在于 “2 小时复刻一个产品”，而在于能否用一整套工程化手段，持续交付更大、更复杂、质量更稳定的产品。

##### 1. 问题背景：AI 提高了写代码速度，但复杂性也同步上升

- 作者先反驳了近几个月常见的说法：例如 “随手 Vibe Coding 一下，2 小时就能复刻一个应用，所以不需要工程师了”。
- 他认为，**软件开发的核心难题从来不是写代码，而是管理复杂性**。
- AI 工具确实让代码吞吐量更高，但副作用是：
  - 代码膨胀更快；
  - 重复代码更容易出现；
  - 系统耦合、并发问题、超大文件等问题更容易失控。
- 作者举例说，像`Typless`这种产品一火，大家都去复刻 “语音输入法”，但这类功能很快就**失去商品价值**，最多只能成为一次性引流工具。

##### 2. 结论：不是更不需要工程师，而是更需要高水平工程师

- 作者的判断是：**AI 时代，团队必须在更短时间里做更大、更复杂的产品**，这会带来更高的工程要求。
- 因此，工程师不但没有被替代，反而更重要，只是要求变了：
  - 不只是会写代码；
  - 更要会设计流程、控制复杂度、保证质量。
- 文中明确提醒：**不要因为复制粘贴了别人的项目，就轻易下结论误导别人。**

##### 3. 为什么团队协作下复杂性会迅速失控

- 作者指出，AI Coding 单看 “写代码” 能力很强，但一旦进入团队协作、复杂产品交付，就会遇到复杂性爆炸。
- 一个很关键的数据是：  
  - **如果今天有 10 个工程师在同一个代码库里工作，实际代码产出量大约相当于过去 50 个人的工作量。**
- 问题在于，无论是`Claude Code`还是`Codex`，它们做 Agent Coding 时都不是 “读完整个代码库后再开发”，而是：
  - 读取局部代码；
  - 在已有代码上继续叠加实现功能。
- 这会导致典型问题：
  - 大量重复代码；
  - 几千行的单个文件 / 组件；
  - 缺少充分考虑的并发问题；
  - 架构逐渐腐化。
- 所以作者认为，**Engineering Harness 有一半工作就是减少这些复杂性问题，另一半是提供更好的环境可观测性和可操作性，让 Agent 能更稳定地持续工作。**

##### 4. 作者团队的总体方案：用 “老软件工程方法” 管理 “新 AI 开发速度”

- 作者强调，解决复杂性的办法其实并不新，**本质上还是过去几十年软件工程积累下来的实践**，只是现在必须更严格、更自动化地使用。
- 他们在开发`zooclaw.ai`时，维护了一套 Harness，主要包括：
  - `Mono Repo + Dev Container`
  - GitHub Actions 触发的`auto-review`和`auto-merge`
  - `pre-commit hook + CI/CD lint`
  - `BDD 风格高覆盖率自动化测试`
  - 自动触发的`E2E Test + 自动录屏供人工审核`
  - `每周自动完整代码 review + 自动创建 issue`
- 作者也坦承：**这套体系离理想状态还有很大距离**，因为现在提 PR 的成本太低了，但它对维持基本代码质量 “非常有帮助”。

##### 5. 第一项：Mono Repo + Dev Container，目标是减少沟通成本和环境成本

- 作者说，他们一直在用`devcontainer`，只是最近切换到了`mono-repo`，因为当前 Agent 的能力在单体仓库里更容易发挥。
- 他们认为，当前产品交付的瓶颈主要变成了两个：
  1. **人与人因为分工产生的沟通成本**
  2. **最终测试验收通常只能依赖一套 staging 环境**
- 对应的解决思路是：
  1. 尽量减少前后端割裂，让一个人能独立完成完整功能；
  2. 让每个人都能在自己的开发环境里拉起完整系统，自测、自验收。
- `mono-repo + devcontainer`的作用：
  - devcontainer 内包含绝大部分服务代码；
  - 同时启动 cache、DB 等依赖；
  - 每个人都能拥有**独立、完整**的开发测试环境。
- 这样不仅工程师能直接开发，**设计师和产品经理也能基于 devcontainer 直接改前端交互、给工程师提 PR**。
- 关于并行开发，作者还提到一个具体建议：  
  - **不一定要用 git worktree**；  
  - 对于 monorepo 太大、agent 需要在 devcontainer 中运行的场景，`clone`多份仓库到固定目录轮流用，可能更省内存、更稳定。  
  - 因为最终还是走 PR 合并，本地 worktree 之间互相干扰的问题并不大。

##### 6. 第二项：用 AI 做自动 Review，并按风险分级处理 PR

- 作者解释，LLM 在同一个上下文里往往更倾向于 “认为自己是对的”，而现实里人工也很难对每个 PR 做充分 Review。
- 所以他们选择：**让另一个 AI 来审查代码**。
- 具体做法是：
  - 用`Claude Code`或`Codex`提供的 GitHub Actions；
  - 对每个 PR 自动做 Code Review；
  - 配置项目自己的 Prompt 和 Checklist。
- 这样做的关键价值在于：
  - Review 是在一个**全新的 context window**中进行的；
  - 更容易发现提交者忽略的问题。
- 他们把 Review 结果分成三档：
  - `Low Risk Auto-Merge`：AI 认为没问题，可自动合并；
  - `Need Human Review`：AI 觉得存在需要人判断的决策或瑕疵，不阻塞合并，但建议人看；
  - `Request Change`：AI 认定有问题，必须修复，除非管理员确认 AI 误判。
- 作者还提到，他们**暂时还没做到模型对抗式 review**，比如：
  - `Claude Code`写的代码由`Codex`审；
  - `Codex`写的代码由`Claude Code`审；
- 但这是下一步计划。

##### 7. 第三项：更严格的 Lint、Pre-Commit 和 CI/CD 规则

- 作者认为，在 AI Coding 时代，Lint 的重要性比过去更高，原因有两个：
  1. 加一个新 Lint 规则变得更容易；
  2. 代码产出太快，Lint 能拦住很多低级和结构性问题。
- 他们目前主要有几类规则：
  - **格式与类型检查**：比传统更严格，避免不同 Agent 带来风格混乱；
  - **复杂度控制**：例如单文件行数限制、函数圈复杂度限制、代码重复率限制；
  - **架构和规范限制**：例如`fastapi`的 route 不能直接访问 DB，CSS 必须语义化。
- 文中没有给出具体阈值数字，但举了规则样式：
  - 单个 Python 文件不超过`X`行；
  - 单函数圈复杂度不超过`Y`；
  - 功能代码重复率不超过`U`；
  - 测试代码重复率不超过`V`。
- 作者特别强调：
  - 这些规则都应尽量用**确定性的代码工具**实现，而不是再用 LLM Prompt 去约束；
  - 因为传统软件工程工具已经足够稳定、快速、便宜。
- 一些运行快的规则会直接放进`pre-commit hook`，而 devcontainer 能自动安装并强制执行这些检查，减少团队配置成本。

##### 8. 第四项：BDD 风格测试 + 高覆盖率，尽量少 Mock，更多真实链路

- 作者认为，除了 Lint，另一个核心质量保障就是自动化测试。
- 但和过去不同的是，现在有两个明显变化：
  - 因为`devcontainer`已经起好了 DB、Cache，所以测试可以少做 Mock，直接打真实依赖；
  - 现在机器性能更强、开发模式也更并行，没有必要为了速度过度 Mock。
- 作者的观点是：**过多 Mock 会漏掉很多真实场景**。
- 测试风格上，他们尽量采用**BDD（行为驱动开发）风格**：
  - 人在 Review AI 写的测试时，重点看自然语言描述的业务行为；
  - 不必过度纠缠测试代码细节。
- 覆盖率目标上，作者给出了明确数字：
  - **测试覆盖率尽量超过 90%**
- 但他也强调，不是机械追求数字：
  - 如果为了提高覆盖率只能堆大量 Mock，那就没有意义；
  - 反过来，**“不得不大量 mock 才能测试” 的代码，往往本身就说明设计或代码质量有问题。**

##### 9. 第五项：自动 E2E 测试 + 自动录屏，用来覆盖真实使用场景

- 作者指出，只有 BDD 测试还不够，因为这类测试通常还是偏模块级：
  - 比如只测前端组件；
  - 或只测后端 API。
- 但产品真实运行时，系统是整体联通的，尤其是 Agent 类产品，**“AI 回答是否正确”**这种问题单靠 BDD 覆盖不到。
- 因此他们会在`CI/CD`中，在部署`staging`和`production`后，**自动触发 E2E 测试**。
- 这类测试的特点是：
  - 通过浏览器操作线上真实系统；
  - 不只做传统功能断言，还会加上`LLM Judge`断言，判断结果是否合理。
- 另外，**所有 E2E 测试都会自动录屏**：
  - 不管测试通过还是失败，都可以直接回看视频；
  - 用来快速确认功能、Agent 效果和交互是否正常。
- 这相当于给 AI 测试增加了一层更直观的人类验收入口。

##### 10. 第六项：每周自动全量代码 Review，把代码腐化当成 “持续清理” 问题

- 作者最后强调，即便有了前面的所有措施，代码还是会因为交付速度太高而快速腐化。
- 所以，他们还会定期做**完整代码库级别的自动 Review**，并通过 GitHub Actions 定时触发。
- 这种 Review 关注的重点不是 “功能对不对”，而是：
  - 架构是否还健康；
  - 模块边界是否还合理；
  - 是否出现了需要小规模重构的地方。
- Review 结果会自动转成`GitHub Issues`，再由人来判断是否值得继续交给 AI 去修。
- 作者用一个很形象的比喻来解释这件事：  
  - 这像是**定时垃圾回收（garbage collection）或内存压缩（memory compaction）**。

#### 总结

这篇文章想说明的是：**AI Coding 真正改变的不是 “工程不重要了”，而是 “工程必须更系统化了”。**  
在代码产出速度暴涨的情况下，团队要想持续交付复杂产品，不能只靠模型写代码，而要靠一整套 Harness 来控复杂度、控质量、控协作成本。作者给出的实践路线很明确：用`mono-repo + devcontainer`统一环境，用`AI review + lint + BDD + E2E + 周期性架构巡检`建立持续约束，才能避免代码库快速腐化。

## 产品-最佳实践（1）

### 2026-04-03 07:11:17

#### 用一个具体实例说明：AI 时代的 Engineering Harness 应该怎么做

下面我用一个具体案例，把你提供的文章观点落到实处。

---

##### 实例：一个 AI 语音客服 SaaS 的 “工单处理” 功能

假设你的小团队正在做一个类似`zooclaw.ai`的产品：  
一个面向企业的**AI 语音客服 / 法务咨询 SaaS**。

现在要上线一个新功能：

> 用户上传一段电话录音，系统自动完成：
>
> 1. 语音转文本  
> 2. 提取关键事实  
> 3. 生成案件摘要  
> 4. 自动归档到客户工作台  
> 5. 前端支持人工复核与修改  
> 6. 支持导出 PDF 报告

这个功能听起来不像 “2 小时复刻一个 demo” 那么难，但实际上它天然跨越了：

- 前端上传与结果展示
- 后端任务编排
- 异步队列
- 对象存储
- 数据库
- LLM 调用
- 权限控制
- 报告生成
- 端到端验收

这正是文章里说的那种：**真正难的不是写几段代码，而是管理复杂性。**

---

#### 一、如果没有 Engineering Harness，会发生什么

很多团队会这样做：

- 让 AI 先把上传页写出来
- 再补一个后端接口
- 再补一个转写脚本
- 再补一个摘要生成器
- 最后再拼一个导出功能

短期看很快，几天内就能 “跑起来”。  
但很快就会出现这些问题：

##### 常见失控现象

- `upload.tsx`变成 1800 行大组件
- 后端 route 直接连数据库、直接调 LLM、直接写对象存储
- “案件摘要” 逻辑在 API、worker、导出服务里各写一份
- 测试大量 mock，线上一联调就挂
- staging 只有一套，A 在测上传，B 在测导出，互相覆盖
- PR 很多，但没人有精力完整 review
- 1 周后改一个字段，3 个地方一起坏

这就是文章里说的：**AI 提高了代码吞吐量，也加速了代码腐化。**

---

#### 二、这个实例上的最佳实践

下面给出一套更接近文章主张的 “最佳实践”，核心目标只有一句话：

> **让 AI 帮你加速交付，但不要让 AI 把复杂性偷偷堆进代码库。**

---

##### 1. 先按 “业务闭环” 拆，不按 “前后端” 拆

###### 不推荐的拆法

- 前端同学做上传页
- 后端同学做接口
- 算法同学做摘要
- 测试同学最后补测试

这种拆法的结果是沟通爆炸，因为一个功能要跨很多人交接。

###### 推荐的拆法

按完整业务链路拆成几个可独立交付的能力单元：

- `录音上传与任务创建`
- `转写与摘要生成流水线`
- `人工复核界面`
- `PDF 导出`
- `审计日志与权限控制`

每一个单元都尽量让**一个工程师 + AI agent**能独立完成前后端闭环。

###### 为什么这是最佳实践

这对应文章中`Mono Repo + Dev Container`的核心目标：

- 减少不必要的人际沟通
- 让一个人能独立完成完整功能
- 让功能可以在本地完整验收

---

##### 2. 用`monorepo + devcontainer`搭一套 “每个人都能完整跑起来” 的环境

###### 最佳实践做法

在一个 monorepo 中统一管理：

- `apps/web`：前端工作台
- `apps/api`：后端 API
- `apps/worker`：异步任务处理
- `packages/domain`：领域模型与共享类型
- `packages/prompts`：摘要、抽取的提示词模板
- `packages/testkit`：测试工厂、fixture、BDD helper

`devcontainer`内直接拉起：

- PostgreSQL
- Redis
- 对象存储模拟服务
- API
- Worker
- Web

这样任何一个人进入容器后，都可以直接完成：

- 上传录音
- 跑异步任务
- 查看摘要
- 修改结果
- 导出 PDF

###### 为什么这是最佳实践

因为这个功能天然依赖很多服务。  
如果没有统一环境：

- AI 写出的代码会越来越依赖 mock
- 本地无法验收完整链路
- 问题只会在 staging 暴露

而文章的核心原则之一就是：

> **尽量让每个人在自己的开发环境里跑起完整产品，自测、自验收。**

---

##### 3. 不要让 API 层 “顺手把所有事做了”，要强制架构边界

这个实例里最容易腐化的地方，就是后端接口。

###### 错误示范

```python
@router.post ("/upload")
async def upload_audio (file: UploadFile, db: Session):
    transcript = call_stt (file)
    summary = call_llm (transcript)
    case = Case (...)
    db.add (case)
    db.commit ()
    upload_pdf (...)
    return case
```

这种写法短期非常快，但会立刻埋下问题：

- route 直接调数据库
- route 直接调 LLM
- route 直接处理业务逻辑
- route 直接做副作用操作
- 无法测试
- 无法复用
- 一改就牵一发而动全身

###### 推荐做法

明确分层：

- `route`：只做参数校验、鉴权、返回格式
- `service/usecase`：组织业务流程
- `domain`：摘要任务、案件实体、状态机
- `repository`：数据库读写
- `infra`：STT、LLM、对象存储、PDF 生成

###### 可执行的规则

把它变成 lint /code rule，而不是靠口头约定：

- `route`禁止直接访问 DB
- `route`禁止直接调 LLM client
- `worker`禁止引用前端包
- `domain`禁止依赖具体框架

###### 为什么这是最佳实践

文章里强调得非常对：

> **能用确定性规则限制的问题，不要交给 prompt 和人工自觉。**

AI 会不断叠加代码，如果没有边界约束，它一定会 “哪里方便写哪里”。

---

##### 4. PR 要小，且必须让 “另一个 AI” 做独立 review

这个实例最常见的失败，不是功能写不出来，而是 PR 太大：

- 一个 PR 同时改上传、转写、摘要、PDF、前端页面、测试
- 人看不动
- AI review 也容易漏

###### 推荐的 PR 划分

- PR1：上传录音并创建任务
- PR2：异步转写 worker
- PR3：摘要生成与状态回写
- PR4：复核页 UI
- PR5：PDF 导出
- PR6：E2E 与验收录屏

###### 自动 review 机制

每个 PR 合并前都自动触发 AI review，并按三类标签处理：

- `Low Risk Auto-Merge`
- `Need Human Review`
- `Request Change`

###### review checklist 示例

可以针对这个实例固定检查：

- 是否有重复的摘要生成逻辑
- route 是否越过 service 直接操作 DB / LLM
- 是否新增超大文件或超大组件
- 是否补了对应的 BDD 测试
- 是否更新了 E2E 场景
- 是否破坏了状态机一致性

###### 为什么这是最佳实践

因为正如文章所说：

- 同一个上下文里的 AI 倾向于觉得自己是对的
- 新 context 的 review 更容易发现问题
- 人应该重点做 “决策型 review”，而不是逐行找格式问题

---

##### 5. 用 Lint 把复杂度 “卡死在门口”

对于这个语音工单功能，最容易发生的是：

- 一个前端页面越写越大
- 一个 worker 函数越写越长
- 同样的 “摘要拼装逻辑” 复制到多个地方

###### 推荐的 Lint / 规则

###### 通用规则

- Typecheck 必须通过
- 格式化统一
- import 顺序统一
- 未使用变量、未处理异常直接失败

###### 复杂度规则

- 单文件最大行数限制
- 单函数圈复杂度限制
- 重复代码率限制
- React 组件 JSX 层级限制
- 单 PR 变更文件数 / 行数做 warning

###### 架构规则

- `apps/api/routes`不得直接访问 repository 之外层
- `apps/web`不得直接 import 后端实现模块
- `packages/domain`不得依赖框架层
- `prompts`必须集中管理，禁止散落硬编码

###### 为什么这是最佳实践

因为在这个功能里，AI 很容易为了 “快交付”：

- 多写一个 if
- 多 copy 一段解析逻辑
- 多塞一点 UI 状态
- 多在 route 里处理一点业务

几轮下来，系统就烂掉了。  
所以复杂度控制必须前置。

---

##### 6. 测试要以 BDD 为主，尽量减少无意义 mock

这个实例中，真正有价值的测试，不是 “mock 一切然后断言函数被调用”，而是测试真实业务行为。

###### 推荐的 BDD 场景

###### 场景 1：上传后自动生成摘要

```gherkin
Given 一个已登录的企业用户
And 其拥有一个可编辑的案件空间
When 用户上传一段有效的电话录音
Then 系统应创建一个处理中的工单
And 异步任务完成后应生成转写文本
And 系统应生成案件摘要
And 摘要结果应显示在工作台中
```

###### 场景 2：人工修订摘要后再次导出

```gherkin
Given 一个已经生成摘要的工单
When 用户手动修改关键事实描述
And 用户点击导出 PDF
Then 导出的 PDF 应包含修改后的内容
And 审计日志中应记录该次人工修订
```

###### 场景 3：异常音频处理

```gherkin
Given 一个损坏的录音文件
When 用户上传该文件
Then 系统应将任务标记为失败
And 前端应展示可理解的错误原因
And 不应生成空白 PDF
```

###### 最佳实践重点

- 尽量连接真实 DB / Cache
- 尽量跑真实任务队列
- 对外部 STT / LLM 可做边界 mock，但不要把内部链路全 mock 掉
- review 测试时优先看 BDD 描述是否覆盖关键业务场景

###### 为什么这是最佳实践

文章强调得很明确：

> **有意义的高覆盖率，比堆 mock 的漂亮数字更重要。**

对这个功能来说，如果测试必须靠大量 mock 才能写，通常说明架构已经不好了。

---

##### 7. E2E 不只看 “能不能点通”，还要看 “结果像不像真的可用”

这个实例非常适合做 E2E，因为它跨越了上传、异步处理、结果展示、导出。

###### 推荐的 E2E 主路径

1. 登录企业账户  
2. 上传一段录音  
3. 等待任务完成  
4. 打开摘要详情页  
5. 校验前端展示内容  
6. 人工编辑一段关键事实  
7. 导出 PDF  
8. 校验文件生成成功  
9. 检查审计日志是否记录

###### 在这个实例上，E2E 最佳实践要多做两件事

###### 1）自动录屏

因为很多问题不是断言能完全表达的，比如：

- UI 交互是否顺滑
- 摘要展示是否错位
- 加载态是否合理
- 编辑保存是否有明显卡顿

###### 2）加入 LLM Judge

例如可以判断：

- 摘要是否覆盖了音频中的主要事实
- 案件标题是否明显偏题
- 导出报告内容是否与页面展示一致

注意，这不是替代确定性断言，而是补足传统断言覆盖不到的语义层问题。

###### 为什么这是最佳实践

文章里说得很准确：

> **真实系统联通后的问题，尤其是 Agent/LLM 输出质量问题，单靠模块测试是覆盖不到的。**

---

##### 8. 每周做一次 “全库架构巡检”，而不是等烂透了再重构

这个实例上线 2 周后，最容易发生的是：

- 新增一个 “二次摘要”
- 再新增一个 “敏感信息脱敏”
- 再新增一个 “多模板导出”
- 最后发现摘要逻辑到处都是分叉

###### 推荐做法

每周自动对全仓做一次 AI code review，重点不是查 bug，而是查：

- 是否出现重复的工作流编排代码
- 是否有 route /page 变得过大
- 是否有 domain model 被绕过
- 是否 prompt 模板散落多处
- 是否测试场景与真实业务脱节

然后自动生成 issue，例如：

- `Refactor: consolidate case summary generation pipeline`
- `Refactor: split oversized review page component`
- `Architecture: move PDF assembly logic out of route layer`

###### 为什么这是最佳实践

因为在 AI 高速开发下，代码腐化不是例外，而是默认结果。  
所以架构维护必须从 “事后补救” 变成 “定期保养”。

---

#### 三、把这套最佳实践落成一个可执行工作流

下面给一个更具体的落地流程。

##### 开发流程

###### 第 1 步：先做前端原型 + mock 数据

目标不是交付，而是确认：

- 上传流程是否合理
- 摘要页结构是否合理
- 人工复核交互是否合理

这样可以快速让产品、设计和工程对齐。

---

###### 第 2 步：在 monorepo 中按能力边界落模块

建立清晰目录：

```text
apps/
  web/
  api/
  worker/
packages/
  domain/
  prompts/
  testkit/
```

先把边界定好，再让 AI 写实现。

---

###### 第 3 步：让 AI 逐个完成小 PR，而不是一把梭

例如：

- 先完成 “上传 + 创建任务”
- 再完成 “转写 worker”
- 再完成 “摘要生成”
- 再完成 “复核 UI”
- 再完成 “导出 PDF”

每一步都能单独 review、单独回滚、单独测试。

---

###### 第 4 步：每个 PR 强制过 lint、BDD、AI review

要求：

- 复杂度规则通过
- 架构规则通过
- 至少补一条对应的 BDD 场景
- AI review 不得为`Request Change`

---

###### 第 5 步：合并到 staging 后自动跑 E2E + 录屏

人不再手工全点一遍，而是重点看：

- 失败用例
- 关键路径录屏
- LLM judge 异常结果

---

###### 第 6 步：每周做全库 review 和 issue 清理

把 “技术债治理” 显式纳入迭代节奏，而不是有空再说。

---

#### 四、这个实例里的 “最佳实践” 本质上在解决什么

如果压缩成一句话，这套方法不是为了让流程更复杂，而是为了回答一个根问题：

> **当 AI 让你一周写出过去一个月的代码时，你如何避免一个月后的代码库变成垃圾场？**

在这个 “AI 语音客服工单处理” 功能里，最佳实践真正解决的是：

- 让一个人能独立完成完整功能闭环
- 让 AI 的高产出不直接变成高技术债
- 让质量检查尽量自动化
- 让人工只介入高价值判断
- 让架构问题在早期、小规模时就被发现

---

#### 五、最终结论

##### 这个实例告诉我们的核心经验

对于 “上传录音 -> 转写 -> 摘要 -> 复核 -> 导出” 这种跨前后端、跨异步链路、跨 LLM 的复杂功能，**最佳实践不是让 AI 尽快把代码写完，而是给 AI 搭一套不会失控的工程轨道。**

具体来说，就是：

1. **用`monorepo + devcontainer`让每个人都能本地跑完整链路**
2. **按业务闭环拆任务，而不是按前后端拆人**
3. **用架构规则和 lint 把复杂度前置拦截**
4. **用独立 AI review 做 PR 风险分级**
5. **用 BDD 测试覆盖真实业务行为，减少无意义 mock**
6. **用 E2E + 录屏 + LLM judge 验证真实体验**
7. **用周期性全库 review 持续处理代码腐化**

可以，最适合的方式不是把`Claude Code`、`Codex`、`cmux`简单串起来，而是把它们放进一个明确分工的流水线里：谁负责发散、谁负责落地、谁负责挑刺、谁负责执行验证，都要固定。

我结合刚才那个 “AI 语音客服 / 工单处理” 实例，给你一套可直接落地的实践流程。这里先假设你说的`cmux`是用来同时管理多个 agent 会话 / 终端工作流的 “会话复用层”，也就是把多个 agent 窗口、不同分支、不同任务并行跑起来的中枢。如果你说的是另一个具体工具，我也可以再按那个工具改写成命令级 SOP。

**目标功能**
- 用户上传录音
- 系统自动转写、摘要、归档
- 前端支持人工复核
- 支持导出 PDF
- 最后通过 Playwright 做端到端验收

---

**总体分工**

- `Claude / Gemini`：前端原型、交互发散、mock 数据驱动页面
- `Codex`：正式代码落地、重构、补测试、跑 Playwright
- `Claude`：独立 review、找架构问题、提修改意见
- `cmux`：并行管理多个 agent 会话和任务状态
- 人：做需求裁剪、关键决策、最终验收

这样分工的原因很简单：
- 前端原型阶段更需要 “快发散、快改视觉、快 mock”
- 正式实现阶段更需要 “稳落地、能改代码、能联调、能修测试”
- review 阶段最怕同模型自洽，所以最好换一个 agent 看
- 多 agent 并行时，最怕上下文丢失和会话混乱，所以必须有`cmux`这类中枢

---

**建议的目录和会话组织**

先把工作组织固定，否则 agent 一多就会乱。

- 代码仓：`monorepo`
- 分支命名：
  - `feat/audio-upload-task`
  - `feat/transcript-worker`
  - `feat/review-ui`
  - `feat/pdf-export`
- `cmux`会话建议固定成 5 个 pane /tab：
  - `P1`：产品说明 / 需求冻结 /issue 描述
  - `P2`：前端原型 agent
  - `P3`：Codex 实现 agent
  - `P4`：Claude review agent
  - `P5`：测试与 Playwright agent

每个 pane 只做一类事，不要混。

---

**第 0 步：先把 “交付标准” 冻结，再叫 agent 干活**

这是最容易被跳过、也是最关键的一步。

你先自己写一个很短的功能卡片，放在`issue`或`spec`里，内容固定为 5 段：

- 背景：为什么做这个功能
- 输入：用户上传什么
- 输出：系统返回什么
- 约束：权限、状态、失败处理、性能要求
- 验收：哪些场景必须通过

比如这个实例里，最少冻结这些要求：

- 支持上传`mp3/wav`
- 上传后创建 “处理中” 的工单
- 后台完成转写和摘要后，工单变 “可复核”
- 用户可编辑摘要并保存
- 用户可导出 PDF
- 失败时有明确错误提示
- 全流程有审计日志
- Playwright 至少覆盖主路径 + 错误路径

**要求**
- 需求文档不超过 1 页
- 所有 agent 都只能基于这个文档工作
- 文档冻结后再发任务，避免多个 agent 各自脑补

---

**第 1 步：前端原型 + mock 数据**

这一阶段不要急着接真实后端。目标是先把 “交互闭环” 做出来。

适合交给`Claude`或`Gemini`。

**做法**
- 在`apps/web`里只做静态页面和 mock 数据
- 先完成 3 个页面：
  - 上传页
  - 工单详情 / 摘要复核页
  - 导出结果页
- 先用本地 mock：
  - `processing`
  - `completed`
  - `failed`
- 页面里先把所有关键状态跑通：
  - 上传中
  - 处理中
  - 成功
  - 失败
  - 手动编辑
  - 导出中

**这一阶段 agent 的 prompt 要求**
给前端 agent 的要求要非常明确：

- 不接真实接口
- 不写复杂状态管理
- 不引入未来可能不用的大组件库
- 所有数据从`mock fixtures`读取
- 组件必须可拆分
- 单文件不要超过约定行数
- 只解决交互结构，不解决业务实现

**产出物**
- 页面原型可本地跑起来
- `mock fixtures`
- 页面状态图
- 一份 UI 验收清单

**验收标准**
- 产品 / 设计 / 你自己能在浏览器里点一遍
- 不讨论代码优雅度，只确认交互是否正确
- 如果交互没定，绝不进入真实编码

这一步对应文章里的一个核心思想：先把 “人机交互和业务流” 定住，减少后续 agent 在错误目标上高吞吐输出。

---

**第 2 步：把功能拆成多个小 issue，再交给 Codex**

不要直接让`Codex`一把梭 “把整个功能做完”。正确做法是按业务闭环拆小任务。

这个实例建议拆成 5 个 issue：

- `Issue 1`：录音上传与工单创建
- `Issue 2`：转写 worker
- `Issue 3`：摘要生成与状态流转
- `Issue 4`：摘要复核页接真实数据
- `Issue 5`：PDF 导出与审计日志

每个 issue 都写成固定模板：

- 目标
- 非目标
- 涉及目录
- 输入输出
- 测试要求
- 禁止事项

例如`Issue 1`的要求可以写成：

- 目标：上传录音并创建工单记录
- 非目标：不做真实摘要
- 涉及目录：`apps/api`、`apps/web`、`packages/domain`
- 输入：音频文件 + 当前用户
- 输出：工单 ID + 初始状态
- 测试要求：至少 1 个 API BDD 测试 + 1 个前端上传交互测试
- 禁止事项：route 里不能直接写业务逻辑，不能直接调 LLM

**要求**
- 一个 issue 最好控制在 1 个 agent 一次上下文能吃完
- 单个 PR 尽量不超过 300-500 行核心逻辑变更
- 每个 issue 必须能单独验收

---

**第 3 步：用`cmux`管理并行 agent，不让上下文互相污染**

这是多 agent 流程成败的关键。

推荐你用`cmux`维护 “固定角色 + 固定上下文”。

**一个典型并行布局**
- `pane A`：主控 pane，只放需求、待办、当前状态
- `pane B`：Codex 做`Issue 1`
- `pane C`：Codex 做`Issue 2`
- `pane D`：Claude review 当前已完成 PR
- `pane E`：Codex 测试 / Playwright

**规则**
- 每个 pane 只绑定一个 issue
- pane 切换 issue 时，必须先清空上下文或新开会话
- 不允许一个 agent 会话同时讨论上传、摘要、PDF 三件事
- 每个 pane 的第一条固定消息都包含：
  - 当前 issue
  - 成功标准
  - 禁止事项
  - 涉及文件范围

你可以把它理解成 “给 agent 建工位”，而不是 “让几个 agent 在一个群里同时说话”。

**要求**
- `cmux`不是为了更多并发，而是为了更稳定的上下文隔离
- 每个 pane 必须有简短 session note
- 每完成一步，就把结论沉淀回`issue comment`或`notes`

---

**第 4 步：Codex 正式写代码，要求它 “只做实现，不做产品定义”**

进入正式实现后，`Codex`最适合承担：

- 接 mock UI 到真实 API
- 建领域模型
- 写 service /repository
- 补自动化测试
- 跑联调
- 修测试

但前提是你要把实现边界说死。

**给 Codex 的任务要求模板**
你可以固定这样发：

- 只实现当前 issue，不顺手做额外优化
- 保持既有目录结构
- route/controller 只做参数和返回，不写核心业务
- 新增逻辑优先放入 service/usecase
- 所有状态必须使用统一枚举
- 所有外部调用都通过 adapter/client
- 不得复制已有摘要逻辑
- 必须补对应测试
- 提交前先跑 lint/typecheck/unit test

**这个实例里，Codex 每一步的具体要求**

`Issue 1：上传与工单创建`
- API 接收文件
- 保存文件元信息
- 创建工单记录为`processing`
- 返回工单 ID
- 前端上传页接真实接口
- 测试覆盖上传成功和失败

`Issue 2：转写 worker`
- worker 从队列取任务
- 拉音频
- 调 STT adapter
- 保存 transcript
- 更新状态
- 测试覆盖成功、重试、失败落库

`Issue 3：摘要生成`
- 从 transcript 生成摘要
- 写回案件摘要字段
- 更新为`reviewable`
- 测试覆盖摘要为空、模型失败、正常生成

`Issue 4：复核 UI`
- 工单详情页接真实数据
- 支持人工编辑并保存
- 前端展示状态变化和错误提示
- 测试覆盖加载态、保存态、失败态

`Issue 5：PDF 导出`
- 从最终摘要生成 PDF
- 记录审计日志
- 返回下载地址
- 测试覆盖导出成功、无权限、缺少摘要

**要求**
- Codex 每次提交前必须自检
- 不允许 “先写完再一起补测试”
- 如果 agent 想扩大改动范围，必须停下来，拆新 issue

---

**第 5 步：Claude 做独立 review，不是帮它润色，而是专门找问题**

这里要刻意避免 “作者自己 review 自己” 的模式。

`Claude` review 的职责不是：
- 调整措辞
- 轻微格式化
- 做表面夸奖

它的职责是专门找这些东西：

- 架构边界破坏
- 重复逻辑
- 状态流不一致
- 错误处理缺失
- 测试空洞
- 组件 / 文件过大
- 未来容易腐化的位置

**review prompt 建议固定结构**
让`Claude`按下面的 checklist 看：

- 这个 PR 是否只做了声明范围内的事
- 是否把业务逻辑塞进了 route /page
- 是否引入了重复实现
- 是否有未被测试覆盖的关键路径
- 是否存在状态不闭环
- 是否有命名误导或领域模型不清晰
- 是否会使后续 E2E 更难写

**输出格式要求**
review 结果不要散乱，要求它固定输出三类：

- `Must Fix`
- `Should Fix`
- `Acceptable Risk`

这样你可以直接决定：
- `Must Fix`：退回给 Codex 改
- `Should Fix`：可本 PR 改，也可记 issue
- `Acceptable Risk`：进入下一步测试

**要求**
- review agent 必须是新上下文
- review 不读历史聊天，只看代码和 issue
- review 结果要落到 PR comment 或 issue comment，不要只停留在会话里

---

**第 6 步：Codex 跑 Playwright，不只是跑通，还要补齐验收路径**

这一步非常关键。很多团队会让 agent 只写单测，E2E 反而最后人工点。其实对于这个实例，Playwright 正是最有价值的。

**建议至少写 4 条主路径**

`E2E 1：成功主链路`
- 登录
- 上传录音
- 看到处理中
- 等待完成
- 打开详情页
- 看到摘要
- 编辑摘要
- 导出 PDF

`E2E 2：失败链路`
- 上传损坏文件
- 工单失败
- 页面展示错误原因
- 不能导出

`E2E 3：权限链路`
- 无权限用户访问工单详情
- 被拒绝访问
- 无导出权限

`E2E 4：审计链路`
- 编辑摘要
- 导出 PDF
- 后台审计日志出现两条记录

**Codex 跑 Playwright 时的要求**
- 优先测真实环境，不要全 mock
- 对外部 LLM / STT 可以做受控假实现，但页面、API、DB、队列尽量真实
- 必须保存 trace、截图、录屏
- 失败后先自动归因：
  - 页面选择器问题
  - 数据未准备好
  - 后端状态流错误
  - 异步等待不稳定

**输出要求**
每次 Playwright 执行后，Codex 要给你一份很短的结果说明：

- 哪些用例通过
- 哪些失败
- 失败属于测试脚本问题还是产品问题
- 如果修复了，修了什么
- 还有哪些残余不稳定点

这一步本质上就是把 “最终人工点点点” 前移为自动化回归能力。

---

**第 7 步：人做最终验收，但只做 “高价值决策”**

到这一步，人不要再去逐行看代码了。你应该只做三类验收：

- 业务是否符合最初 spec
- 交互是否顺手
- AI 输出结果是否够可用

对这个实例，人工验收建议固定看 8 件事：

- 上传是否足够快、反馈是否清楚
- 处理中状态是否可理解
- 摘要质量是否达到最低业务可用线
- 人工编辑是否流畅
- 保存是否明确
- 导出 PDF 是否像正式文档
- 错误场景提示是否可理解
- 审计日志是否完整

**要求**
- 人只看结果，不再介入具体写法
- 验收不通过时，要回写成具体 issue，不要口头说 “再调一调”
- 每个不通过项必须对应：
  - 是需求问题
  - 是实现问题
  - 是测试问题
  - 是模型输出质量问题

---

**第 8 步：上线前做一次 “全流程回放” 和沉淀**

这一步很容易被省略，但它决定后面能不能复制。

你需要把这次流程沉淀成模板，包括：

- 哪些 prompt 有效
- 哪些 review checklist 抓到最多问题
- 哪些 Playwright 场景最值钱
- 哪些地方最容易让 agent 越界
- 哪些拆分粒度最合适

建议最后沉淀 4 份资产：

- `feature spec template`
- `agent task template`
- `review checklist`
- `playwright acceptance suite`

这样下一次做 “多模板导出” 或 “敏感信息脱敏” 时，就不是重新摸索，而是直接复用 harness。

---

**一套可执行的日常操作顺序**

如果你想要一个更接近日常工作的版本，可以按这个节奏跑：

- 上午：
  - 冻结一个小功能 spec
  - `Claude/Gemini`出前端原型 + mock
  - 你确认交互
- 中午前：
  - 拆成 2-5 个 issue
  - 在`cmux`里开多个固定 pane
- 下午：
  - `Codex`分 issue 落代码
  - 每完成一个 PR 就交给`Claude` review
  - `Codex`根据 review 修正
- 傍晚：
  - `Codex`跑 Playwright
  - 生成录屏、trace、截图
  - 你做最终验收
- 晚上或次日：
  - 合并
  - 记录经验
  - 更新模板

---

**每个步骤的硬性要求汇总**

- `前端原型 + mock`
  - 只确认交互，不接真实后端
  - 必须覆盖成功 / 失败 / 加载态
  - 页面和组件可拆分

- `Codex 写代码`
  - 一次只实现一个小 issue
  - 不越界
  - 必须补测试
  - 必须跑 lint/typecheck

- `Claude review`
  - 必须是新上下文
  - 必须输出`Must Fix / Should Fix / Acceptable Risk`
  - 重点看架构和风险，不看表面润色

- `Codex 跑 Playwright`
  - 必须覆盖主链路和错误链路
  - 必须保存 trace /screenshot/video
  - 必须区分脚本问题和产品问题

- `最终验收`
  - 只看业务结果和体验
  - 不做低价值逐行 review
  - 验收失败必须转 issue

---

**最容易踩的坑**

- 让一个 agent 一次做完整功能，PR 过大
- review 和实现用同一个 agent、同一个上下文
- mock 阶段没冻结交互，就提前接真实后端
- Playwright 只测 happy path
- `cmux`里一个 pane 混多个任务，导致上下文串线
- 不把经验沉淀成模板，下次又从零开始

---

**最推荐的角色组合**

如果你现在就想实操，我建议先用这个最稳的组合：

- `Claude/Gemini`：前端原型 + mock
- `Codex`：正式实现 + 单测 / 集成测试
- `Claude`：PR review
- `Codex`：Playwright 回归
- 人：验收与合并决策
- `cmux`：固定 pane 管理这些会话和 issue

这套分工跟你给的 flow 是一致的，但比 “串行调用几个 agent” 更进一步：它把每一步的职责、交付物和验收标准都固定了，所以才能形成真正的 engineering harness，而不是临时 vibe workflow。

2. 直接给你一套可用的 prompt 模板，分别用于`前端原型 / Codex 实现 / Claude review / Playwright 测试`
