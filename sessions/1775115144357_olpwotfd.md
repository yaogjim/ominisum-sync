#### 快速开始

**第一步：安装**

```
/plugin marketplace add https://github.com/Yeachan-Heo/oh-my-claudecode
/plugin install oh-my-claudecode
```

**第二步：配置**

```
/omc-setup
```

**第三步：开始构建**

```
autopilot: build a REST API for managing tasks
```

就这么简单。其余都是自动的。

##### 不确定从哪里开始？

如果你对需求不明确、有模糊的想法，或者想要精细控制设计：

```
/deep-interview "I want to build a task management app"
```

深度访谈使用苏格拉底式提问在编写任何代码之前帮你理清思路。它揭示隐藏假设并通过加权维度衡量清晰度，确保你在执行前明确知道要构建什么。

#### Team 模式（推荐）

从 **v4.1.7** 开始， **Team** 是 OMC 的标准编排方式。 **swarm** 和 **ultrapilot** 等旧版入口仍受支持，但现在 **在底层路由到 Team** 。

```
/team 3:executor "fix all TypeScript errors"
```

Team 按阶段化流水线运行：

`team-plan → team-prd → team-exec → team-verify → team-fix (loop)`

在 `~/.claude/settings.json` 中启用 Claude Code 原生团队：

```
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

> 如果团队被禁用，OMC 会发出警告并在可能的情况下回退到非 Team 执行模式。

**v4.4.0 移除了 Codex/Gemini MCP 服务器** （ `x` 、 `g` 提供商）。请改用 `/omc-teams` 在 tmux 分屏中启动真实的 CLI 进程：

```
/omc-teams 2:codex   "review auth module for security issues"
/omc-teams 2:gemini  "redesign UI components for accessibility"
/omc-teams 1:claude  "implement the payment flow"
```

如需在一个命令中混合使用 Codex + Gemini，请使用 **`/ccg`** 技能：

```
/ccg Review this PR — architecture (Codex) and UI components (Gemini)
```

技能 工作者 最适合

`/omc-teams N:codex` N 个 Codex CLI 窗格 代码审查、安全分析、架构

`/omc-teams N:gemini` N 个 Gemini CLI 窗格 UI/UX 设计、文档、大上下文任务

`/omc-teams N:claude` N 个 Claude CLI 窗格 通过 tmux 中的 Claude CLI 处理通用任务

`/ccg` 1 个 Codex 加 1 个 Gemini 并行三模型编排

工作者按需生成，任务完成后自动退出 — 无空闲资源浪费。需要安装 `codex` / `gemini` CLI 并有活跃的 tmux 会话。

> **注意：包命名** — 项目品牌名为 **oh-my-claudecode** （仓库、插件、命令），但 npm 包以 [`oh-my-claude-sisyphus`](https://www.npmjs.com/package/oh-my-claude-sisyphus) 发布。通过 npm/bun 安装 CLI 工具时，请使用 `npm install -g oh-my-claude-sisyphus` 。

#### 为什么选择 oh-my-claudecode？

- **无需配置** - 开箱即用，智能默认设置
- **Team 优先编排** - Team 是标准的多智能体界面（swarm/ultrapilot 是兼容性外观）
- **自然语言交互** - 无需记忆命令，只需描述你的需求
- **自动并行化** - 复杂任务自动分配给专业智能体
- **持久执行** - 不会半途而废，直到任务验证完成
- **成本优化** - 智能模型路由节省 30-50% 的 token
- **从经验中学习** - 自动提取并复用问题解决模式
- **实时可见性** - HUD 状态栏显示底层运行状态

##### 执行模式

针对不同场景的多种策略 - 从全自动构建到 token 高效重构。 [了解更多 →](https://yeachan-heo.github.io/oh-my-claudecode-website/docs.html#execution-modes)

模式 特点 适用场景

**Team（推荐）** 阶段化流水线 在共享任务列表上协作的 Claude 智能体

**omc-teams** tmux CLI 工作者 Codex/Gemini CLI 任务；按需生成，完成后退出

**ccg** 三模型并行 Codex（分析）+ Gemini（设计），Claude 合成

**Autopilot** 自主执行 最小化繁琐配置的端到端功能开发

**Ultrawork** 最大并行 不需要 Team 的并行修复/重构

**Ralph** 持久模式 必须完整完成的任务

**Pipeline** 顺序处理 需要严格顺序的多阶段转换

**Swarm / Ultrapilot（旧版）** 路由到 Team 现有工作流和旧文档

##### 智能编排

- **32 个专业智能体** 涵盖架构、研究、设计、测试、数据科学
- **智能模型路由** - 简单任务用 Haiku，复杂推理用 Opus
- **自动委派** - 每次都选择最合适的智能体

##### 开发者体验

- **魔法关键词** - `ralph` 、 `ulw` 、 `plan` 提供显式控制
- **HUD 状态栏** - 状态栏实时显示编排指标
- **技能学习** - 从会话中提取可复用模式

一次学习，永久复用。OMC 将调试过程中获得的实战知识提取为可移植的技能文件，并在相关场景中自动注入。

#### 魔法关键词

为高级用户提供的可选快捷方式。不用它们，自然语言也能很好地工作。

关键词 效果 示例

`team` 标准 Team 编排 `/team 3:executor "fix all TypeScript errors"`

`omc-teams` tmux CLI 使用者 (codex/gemini/claude) `/omc-teams 2:codex "security review"`

`ccg` 三模型 Codex+Gemini 编排 `/ccg review this PR`

`autopilot` 全自动执行 `autopilot: build a todo app`

`ralph` 持久模式 `ralph: refactor auth`

`ulw` 最大并行化 `ulw fix all errors`

`plan` 规划访谈 `plan the API`

`ralplan` 迭代规划共识 `ralplan this feature`

`deep-interview` 苏格拉底式需求澄清 `deep-interview "vague idea"`

`swarm` **已弃用** — 请使用 `team` `swarm 5 agents: fix lint errors`

`ultrapilot` **已弃用** — 请使用 `team` `ultrapilot: build a fullstack app`

**注意：**

- **ralph 包含 ultrawork：** 激活 ralph 模式时，会自动包含 ultrawork 的并行执行。无需组合关键词。
- `swarm N agents` 语法仍可被识别用于提取智能体数量，但运行时在 v4.1.7+ 中由 Team 支持。

#### 实用工具

##### 速率限制等待

当速率限制重置时自动恢复 Claude Code 会话。

```
omc wait          # 检查状态，获取指导
omc wait --start  # 启用自动恢复守护进程
omc wait --stop   # 禁用守护进程
```

**需要：** tmux（用于会话检测）

##### 通知标签配置 (Telegram/Discord/Slack)

你可以配置 stop 回调发送会话摘要时要 @ 谁。

```
# 设置/替换标签列表
omc config-stop-callback telegram --enable --token <bot_token> --chat <chat_id> --tag-list "@alice,bob"
omc config-stop-callback discord --enable --webhook <url> --tag-list "@here,123456789012345678,role:987654321098765432"
omc config-stop-callback slack --enable --webhook <url> --tag-list "<!here>,<@U1234567890>"

# 增量更新
omc config-stop-callback telegram --add-tag charlie
omc config-stop-callback discord --remove-tag @here
omc config-stop-callback discord --clear-tags
```

标签规则：

- Telegram： `alice` 会规范化为 `@alice`
- Discord：支持 `@here` 、 `@everyone` 、纯数字用户 ID、 `role:<id>`
- Slack：支持 `<@MEMBER_ID>` 、 `<!channel>` 、 `<!here>` 、 `<!everyone>` 、 `<!subteam^GROUP_ID>`
- `file` 回调会忽略标签选项

##### OpenClaw 集成

将 Claude Code 会话事件转发到 [OpenClaw](https://openclaw.ai/) 网关，通过您的 OpenClaw 代理实现自动化响应和工作流程。

**快速设置（推荐）：**

```
/oh-my-claudecode:configure-notifications
# → 提示时输入 "openclaw" → 选择 "OpenClaw Gateway"
```

**手动设置：** 创建 `~/.claude/omc_config.openclaw.json` ：

**环境变量：**

变量 说明

`OMC_OPENCLAW=1` 启用 OpenClaw

`OMC_OPENCLAW_DEBUG=1` 启用调试日志

`OMC_OPENCLAW_CONFIG=/path/to/config.json` 覆盖配置文件路径

**支持的钩子事件（bridge.ts 中 6 个活跃）：**

事件 触发时机 主要模板变量

`session-start` 会话开始时 `{{sessionId}}`, `{{projectName}}`, `{{projectPath}}`

`stop` Claude 响应完成时 `{{sessionId}}`, `{{projectName}}`

`keyword-detector` 每次提交提示词时 `{{prompt}}`, `{{sessionId}}`

`ask-user-question` Claude 请求用户输入时 `{{question}}`, `{{sessionId}}`

`pre-tool-use` 工具调用前（高频） `{{toolName}}`, `{{sessionId}}`

`post-tool-use` 工具调用后（高频） `{{toolName}}`, `{{sessionId}}`

**回复通道环境变量：**

变量 说明

`OPENCLAW_REPLY_CHANNEL` 回复通道（例如 `discord` ）

`OPENCLAW_REPLY_TARGET` 频道 ID

`OPENCLAW_REPLY_THREAD` 线程 ID

参见 `scripts/openclaw-gateway-demo.mjs` ，这是一个通过 ClawdBot 将 OpenClaw 有效载荷转发到 Discord 的参考网关。

#### oh-my-codex (OMX)

[![oh-my-codex character](https://camo.githubusercontent.com/b9f4fab5faf781f27a66b8f246b29142e762dc004fb261f7e49b8e5d453ce720/68747470733a2f2f7965616368616e2d68656f2e6769746875622e696f2f6f682d6d792d636f6465782d776562736974652f6f6d782d6368617261637465722d6e6f62672e706e67)](https://camo.githubusercontent.com/b9f4fab5faf781f27a66b8f246b29142e762dc004fb261f7e49b8e5d453ce720/68747470733a2f2f7965616368616e2d68656f2e6769746875622e696f2f6f682d6d792d636f6465782d776562736974652f6f6d782d6368617261637465722d6e6f62672e706e67)  
*Start Codex stronger, then let OMX add better prompts, workflows, and runtime help when the work grows.*

**Website:**[https://yeachan-heo.github.io/oh-my-codex-website/](https://yeachan-heo.github.io/oh-my-codex-website/)  
**Docs:**Getting Started · Agents · Skills · Integrations · Demo · OpenClaw guide

OMX is a workflow layer for [OpenAI Codex CLI](https://github.com/openai/codex).

It keeps Codex as the execution engine and makes it easier to:

- start a stronger Codex session by default
- reuse good role/task invocations with `$name` keywords
- invoke workflows with skills like `$plan`, `$ralph`, and `$team`
- keep project guidance, plans, logs, and state in `.omx/`

If you want the default OMX experience, start here:

```
npm install -g @openai/codex oh-my-codex
omx setup
omx --madmax --high
```

Then work normally inside Codex:

```
$architect "analyze the authentication flow"
$plan "ship this feature cleanly"
```

That is the main path. Start OMX strongly, do the work in Codex, and let the agent pull in `$team` or other workflows only when the task actually needs them.

Use OMX if you already like Codex and want a better day-to-day runtime around it:

- reusable role/task invocations such as `$architect` and `$executor`
- reusable workflows such as `$plan`, `$ralph`, `$team`, and `$deep-interview`
- project guidance through scoped `AGENTS.md`
- durable state under `.omx/` for plans, logs, memory, and mode tracking

If you want plain Codex with no extra workflow layer, you probably do not need OMX.

#### Quick start

##### Requirements

- Node.js 20+
- Codex CLI installed: `npm install -g @openai/codex`
- Codex auth configured
- `tmux` on macOS/Linux if you later want the durable team runtime
- `psmux` on native Windows if you later want Windows team mode

Launch OMX the recommended way:

```
omx --madmax --high
```

Then try one role keyword and one workflow skill:

```
$architect "analyze the authentication flow"
$plan "map the safest implementation path"
```

If the task grows, the agent can escalate to heavier workflows such as `$ralph` for persistent execution or `$team` for coordinated parallel work.

OMX does **not** replace Codex.

It adds a better working layer around it:

- **Codex** does the actual agent work
- **OMX role keywords** make useful roles reusable
- **OMX skills** make common workflows reusable
- **`.omx/`** stores plans, logs, memory, and runtime state

Most users should think of OMX as **better task routing + better workflow + better runtime**, not as a command surface to operate manually all day.

1. Run `omx setup`
2. Launch with `omx --madmax --high`
3. Ask for analysis with `$architect "..."`
4. Ask for planning with `$plan "..."`
5. Let the agent decide when `$ralph`, `$team`, or another workflow is worth using

Surface Use it for

`$architect "..."` analysis, boundaries, tradeoffs

`$executor "..."` focused implementation work

`/skills` browsing installed skills

`$plan "..."` planning before implementation

`$ralph "..."` persistent sequential execution

`$team "..."` coordinated parallel execution when the task is big enough

Use `$deep-interview` when the request is still vague, the boundaries are unclear, or you want OMX to keep pressing on intent, non-goals, and decision boundaries before it hands work off to `$plan`, `$ralph`, `$team`, or `$autopilot`.

Typical cases:

- vague greenfield ideas that still need sharper intent and scope
- brownfield changes where OMX should inspect the repo first, then ask cited confirmation questions
- requests where you want a one-question-at-a-time clarification loop instead of immediate planning or implementation

These are useful, but they are not the main onboarding path.

##### Team runtime

Use the team runtime when you specifically need durable tmux/worktree coordination, not as the default way to begin using OMX.

```
omx team 3:executor "fix the failing tests with verification"
omx team status <team-name>
omx team resume <team-name>
omx team shutdown <team-name>
```

These are operator/support surfaces:

- `omx setup` installs prompts, skills, config, and AGENTS scaffolding
- `omx doctor` verifies the install when something seems wrong
- `omx hud --watch` is a monitoring/status surface, not the primary user workflow

- `omx explore --prompt "..."` is for read-only repository lookup
- `omx sparkshell <command>` is for shell-native inspection and bounded verification

Examples:

```
omx explore --prompt "find where team state is written"
omx sparkshell git status
omx sparkshell --tmux-pane %12 --tail-lines 400
```

`omx team` needs a tmux-compatible backend:

Platform Install

macOS `brew install tmux`

Ubuntu/Debian `sudo apt install tmux`

Fedora `sudo dnf install tmux`

Arch `sudo pacman -S tmux`

Windows `winget install psmux`

Windows (WSL2) `sudo apt install tmux`

#### Known issues

On some Intel Macs, OMX startup — especially with `--madmax --high` — can spike `syspolicyd` / `trustd` CPU usage while macOS Gatekeeper validates many concurrent process launches.

If this happens, try:

- `xattr -dr com.apple.quarantine $(which omx)`
- adding your terminal app to the Developer Tools allowlist in macOS Security settings
- using lower concurrency (for example, avoid `--madmax --high`)

#### OMX 和 OMC 在使用上的异同

基于你提供的两份资料来看，`OMX`（`oh-my-codex`）和 `OMC`（`oh-my-claudecode`）本质上都是“给原生 AI CLI 加一层更强工作流编排”的工具，但它们服务的底层生态不同，因此在实际使用方式上既有很多共通点，也有明显差异。

---

##### 一句话结论

- `OMX`：更像是 **围绕 Codex CLI 的增强工作流层**，主张“先把 Codex 用强，再按需升级到 team/ralph 等重型流程”。
- `OMC`：更像是 **围绕 Claude Code 的多智能体编排系统**，主张“默认就用 Team 编排”，并且还能通过 `tmux` 调起 `Codex/Gemini/Claude` 多种 CLI 协作。

---

##### 相同点

###### 1. 都不是底层模型本身，而是“工作流增强层”
两者都不替代原生 CLI，而是在其外面增加：

- 更强的提示词/角色调用方式
- 可复用的技能（skills）
- 多智能体协作
- 持久化状态与运行时辅助
- HUD / 监控 / 调试 / 集成能力

换句话说：

- `OMX` 依附于 `Codex CLI`
- `OMC` 依附于 `Claude Code CLI`

它们都属于“让原本的 CLI 更适合长期工程开发”的工具。

---

###### 2. 都强调“按任务复杂度升级工作流”
两者都不是只会单轮对话，而是支持把任务按复杂度升级为更结构化的流程，比如：

- 规划：`plan`
- 深度澄清：`deep-interview`
- 持久执行：`ralph`
- 并行协作：`team`

这说明两者的核心理念一致：  
不是每个任务都直接写代码，而是可以先分析、澄清、规划，再进入执行。

---

###### 3. 都支持技能复用和项目级记忆
两者都强调把经验沉淀下来，而不是每次从零开始。

- `OMX`：把计划、日志、记忆、运行状态存到 `.omx/`
- `OMC`：支持技能沉淀到 `.omc/skills/` 或 `~/.omc/skills/`

共同点是：

- 都支持项目作用域
- 都支持复用已有模式
- 都试图把“会话式 AI”升级成“可积累的工程助手”

---

###### 4. 都支持 Team / 多智能体协作
两者都支持把任务交给多个角色/智能体协同处理。

例如都存在类似的概念：

- `team`
- 角色型执行者如 `architect`、`executor`
- 任务分流、并行执行、验证修复等阶段

说明它们都不是“单助手聊天工具”，而是面向复杂任务的协作编排器。

---

##### 核心不同点

##### 1. 底层依附对象不同，这是最大的区别

###### OMX：围绕 Codex
`OMX` 明确写的是：

- “OMX is a workflow layer for OpenAI Codex CLI”
- 推荐入口是：
  ```bash
  omx --madmax --high
  ```
- 日常工作仍然是在 Codex 内完成，使用 `$architect`、`$plan` 等关键词驱动工作流

也就是说，`OMX` 的设计中心是：

> 你本来就喜欢用 Codex，只是想让它更强、更好用。

---

###### OMC：围绕 Claude Code
`OMC` 明确写的是：

- “Claude Code 的多智能体编排系统”
- 推荐路径是：
  - 安装插件
  - `/omc-setup`
  - 然后直接用自然语言或 `/team`、`autopilot:` 等入口

它的中心思想是：

> 不用先学 Claude Code 的复杂用法，直接通过 OMC 来用 Claude Code。

所以从“使用入口”的感觉上：

- `OMX` 更像 Codex 的高级增强包
- `OMC` 更像 Claude Code 的上层操作系统/总控台

---

##### 2. 默认使用姿势不同：OMX 偏“轻量增强”，OMC 偏“默认编排”

###### OMX：先普通工作，再按需升级
`OMX` 的资料里反复强调：

- “That is the main path.”
- “Start OMX strongly, do the work in Codex”
- “let the agent pull in `$team` or other workflows only when the task actually needs them”
- “Use the team runtime ... not as the default way to begin using OMX.”

也就是说，`OMX` 的推荐使用方式是：

1. 先启动一个增强版 Codex 会话
2. 先用 `$architect`、`$plan` 做分析和规划
3. 只有任务变大时，才升级到 `$team` 或 `$ralph`

这是一种 **渐进增强** 的使用思路。

---

###### OMC：Team 是标准模式
`OMC` 文档则写得非常明确：

- “从 v4.1.7 开始，Team 是 OMC 的标准编排方式”
- `swarm`、`ultrapilot` 等旧入口都路由到 `Team`

这意味着 `OMC` 在使用哲学上更偏向：

> 一开始就把任务放进标准化、多阶段、多智能体流水线里。

所以如果从“默认心智模型”来看：

- `OMX`：先单代理强化，必要时再进入团队模式
- `OMC`：团队编排本来就是默认主干路径

---

##### 3. 命令风格不同：OMX 更像 CLI 工具，OMC 更像插件/命令体系

###### OMX 的风格
`OMX` 更偏传统命令行风格，例如：

```bash
omx setup
omx --madmax --high
omx team 3:executor "fix the failing tests with verification"
omx hud --watch
omx doctor
```

在会话中常用的是 `$` 风格技能：

```bash
$architect "analyze the authentication flow"
$plan "ship this feature cleanly"
$team "..."
```

特点是：

- `omx` 命令负责外部控制
- `$skill` 负责会话内工作流调用

---

###### OMC 的风格
`OMC` 更偏 Claude Code 插件命令体系，例如：

```bash
/plugin install oh-my-claudecode
/omc-setup
/team 3:executor "fix all TypeScript errors"
/omc-teams 2:codex "security review"
/ccg Review this PR
/deep-interview "I want to build a task management app"
```

它的命令风格更像“在 AI 工作区内输入 slash command”。

所以从体验上说：

- `OMX`：更偏 shell / CLI 原生命令体验
- `OMC`：更偏 AI 插件/指令式体验

---

##### 4. 对外部模型协作的定位不同

###### OMX：主要就是强化 Codex
`OMX` 的重点是把 Codex 变强，没有把多模型协作作为主卖点。

虽然它也有集成、team、runtime，但主轴一直是：

- Codex 做实际 agent work
- OMX 提供角色、技能、状态、路由、持久化

所以 `OMX` 的核心仍是 **Codex-centric**。

---

###### OMC：天然支持 Claude + Codex + Gemini 的编排
`OMC` 明确支持：

- `/omc-teams N:codex`
- `/omc-teams N:gemini`
- `/omc-teams N:claude`
- `/ccg`：Codex + Gemini + Claude 三模型协作

而且还写了明确分工：

- `Codex`：代码审查、安全分析、架构
- `Gemini`：UI/UX、文档、大上下文
- `Claude`：通用任务

所以 `OMC` 的使用边界更广，它不是只强化 Claude，而是把 Claude 作为主编排器，再调其他 CLI 一起干活。

这一点是两者很大的区别。

---

##### 5. 持久化与项目目录结构不同

###### OMX：`.omx/`
`OMX` 明确把这些内容存到 `.omx/`：

- plans
- logs
- memory
- runtime state

说明它比较强调“运行时状态管理”和“Codex 会话增强”。

---

###### OMC：`.omc/skills/` + 用户级技能库
`OMC` 更突出的是技能系统：

- 项目级：`.omc/skills/`
- 用户级：`~/.omc/skills/`

并且强调：

- 自动学习
- 自动注入
- 技能提取与复用

所以二者虽然都做持久化，但重点不同：

- `OMX` 更偏“状态、计划、日志、记忆”
- `OMC` 更偏“技能沉淀、自动学习、跨项目复用”

---

##### 6. Team 运行时的定位不同

###### OMX 的 `team`
`OMX` 中 `team` 被定义为：

- 在任务变大时使用
- 是 durable tmux/worktree coordination
- 更像“操作员/支持层”
- 不是默认起手方式

例如：

```bash
omx team 3:executor "fix the failing tests with verification"
omx team status <team-name>
omx team resume <team-name>
omx team shutdown <team-name>
```

它有比较强的“任务运行时管理”意味。

---

###### OMC 的 `Team`
`OMC` 中 `Team` 是主线路径，具备标准阶段流：

- `team-plan`
- `team-prd`
- `team-exec`
- `team-verify`
- `team-fix (loop)`

这说明 `OMC Team` 更像“完整的软件交付流水线”，而不只是并行执行器。

因此：

- `OMX team` 更像按需启用的重型协作运行时
- `OMC Team` 更像默认的正式生产流程

---

##### 7. 上手对象不同

###### 更适合 OMX 的人
如果你是这类用户，通常会更适合 `OMX`：

- 已经在用 `Codex CLI`
- 希望保留 Codex 的原始工作方式
- 只想加一些更强的角色、技能、状态管理
- 不希望默认就进入复杂编排
- 更习惯 shell/CLI 风格操作

---

###### 更适合 OMC 的人
如果你是这类用户，通常会更适合 `OMC`：

- 主要在 `Claude Code` 生态里工作
- 希望“开箱即用”的多智能体编排
- 希望默认走 Team 流程，而不是手动决定何时升级
- 想把 `Claude + Codex + Gemini` 一起编排起来
- 希望更多自动化、并行化、验证闭环

---

##### 使用方式对照表

| 维度 | OMX | OMC |
|---|---|---|
| 依附对象 | Codex CLI | Claude Code CLI |
| 核心定位 | Codex 的增强工作流层 | Claude Code 的多智能体编排系统 |
| 推荐起手方式 | `omx --madmax --high` | `/omc-setup` 后直接使用 `/team` 或自然语言 |
| 默认心智模型 | 先轻量使用，按需升级 | 默认就采用 Team 编排 |
| 常用调用方式 | `omx ...` + `$architect` / `$plan` | `/team`、`/omc-teams`、`/ccg`、`autopilot:` |
| Team 的定位 | 重型任务时再用 | 标准主流程 |
| 多模型协作 | 以 Codex 为中心 | Claude 主控，可调 Codex/Gemini/Claude |
| 状态沉淀 | `.omx/` 中的计划/日志/记忆/状态 | `.omc/skills/` 与 `~/.omc/skills/` 技能沉淀 |
| 适合人群 | 已习惯 Codex 的开发者 | 希望强编排和多 CLI 协作的用户 |

---

##### 实际使用上的“最关键差异”

如果只从“平时怎么用”来看，可以把差异简化成下面这句：

###### 用 OMX 时
你通常会这样想：

> 我先开一个更强的 Codex，会话里用 `$architect`、`$plan` 等辅助；真复杂了，再叫 `$team` 或 `$ralph`。

这是 **“先工作，再升级流程”**。

---

###### 用 OMC 时
你通常会这样想：

> 我直接把任务交给 OMC，它默认就能按 Team 流程拆分、执行、验证；必要时还能调 Codex/Gemini 一起做。

这是 **“先进入流程，再自动调度执行”**。

---

##### 选择建议

###### 选 OMX，如果你更看重
- 保持 `Codex` 为工作中心
- 较少改变现有 CLI 使用习惯
- 只在需要时才使用复杂编排
- 更清晰的本地运行状态与日志管理

###### 选 OMC，如果你更看重
- 默认强编排
- 多智能体流水线
- Claude 主导的开发体验
- 与 `Codex/Gemini` 的协同调度
- 更强的“自动完成直到验证通过”的闭环能力

---

##### 结论

两者不是简单的替代关系，更像是面向不同主生态的“增强层”：

- `OMX` 是 **以 Codex 为中心的增强器**
- `OMC` 是 **以 Claude Code 为中心的编排器**

如果你问“使用上最大的区别是什么”，最准确的回答是：

> `OMX` 更像给 Codex 加外挂，先轻后重；  
> `OMC` 更像直接接管工作流，默认走多智能体编排，并且更强调跨模型协作。
