Chorus

**面向 AI 与人类协作的 Agent Harness**

English

Chorus 是一个 Agent Harness —— 包裹在 LLM 外面的基础设施层，负责管理会话生命周期、任务状态、子 Agent 编排、可观测性和故障恢复。它让多个 AI Agent（PM、Developer、Admin）和人类在同一平台上协作，完成从需求到交付的全流程。

受 **[AI-DLC（AI-Driven Development Lifecycle）](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/)** 方法论启发。核心理念： **Reversed Conversation** — AI 提议，人类验证。

---

AI Agent 的可靠性取决于模型之外的系统。模型负责推理，但会话边界、任务状态、上下文交接、子 Agent 协调和故障恢复——这些都发生在模型之外。这套外围系统就是 **Agent Harness** 。

没有 harness，Agent 在长任务中会漂移、跨会话丢失上下文、重复工作、静默失败。一个好的 harness 解决这些问题：

Harness 能力 它解决什么问题 Chorus 的解决方式

**会话生命周期** Agent 重启后丢失工作进度 每个 Agent 拥有持久化 Session，Plugin 在启动/退出时自动创建和关闭

**任务状态机** 没有统一的进度真相源 任务按严格的生命周期流转——认领、进行中、提交验证、已验证——所有人实时可见

**上下文连续性** 新的上下文窗口从零开始 每次 check-in 恢复 Agent 的角色设定、当前分配和项目状态，无需重新探索

**子 Agent 编排** 多 Agent 协作缺乏协调就会混乱 生命周期钩子自动接管——Session、上下文注入、解锁任务发现，无需手写编排逻辑

**可观测性** 看不到的东西没法调试 每个操作都带 Session 归因记录；Kanban 和 Worker 徽标实时展示谁在做什么

**故障恢复** 卡住的任务阻塞整条流水线 空闲 Session 自动过期，孤儿任务释放回任务池，任何 Agent 可重新接手

**规划与分解** Agent 不经规划就开始编码 PM Agent 在执行前构建任务依赖图——没有经过审批的计划，不开始任何工作

Chorus 不是一个 framework——它不提供需要你自己组装的构建积木。它是一个 **完整的 harness** ，带有开箱即用的默认配置：生命周期钩子、50+ MCP 工具、基于角色的权限、以及内建的人类审核环节。

#### AI-DLC 工作流

```
Idea ──> Proposal ──> [Document + Task DAG] ──> Execute ──> Verify ──> Done
  ^          ^               ^                     ^          ^         ^
Human     PM Agent       PM Agent              Dev Agent    Admin     Admin
creates   analyzes       drafts PRD            codes &      reviews   closes
          & plans        & tasks               reports      & verifies
```

三个 Agent 角色：

角色 职责 MCP 工具前缀

**PM Agent** 分析 Idea、创建 Proposal（PRD + 任务拆解）、管理文档 `chorus_pm_*`

**Developer Agent** 认领任务、编写代码、报告工作、提交验证 `chorus_*_task`, `chorus_report_work`

**Admin Agent** 创建项目/Idea、审批 Proposal、验证任务、管理生命周期 `chorus_admin_*`

所有角色共享只读和协作工具（ `chorus_get_*` 、 `chorus_checkin` 、 `chorus_add_comment` 等）。

Pixel Workspace

左侧为像素工作室，用像素小人代表每个 Agent 的实时工作状态；右侧为 Agent 终端实时输出。

Proposal

PM Agent 生成的 Proposal 包含文档草稿和任务 DAG 草稿，Admin 在此面板审阅并决定批准或驳回。

Task Tracking

任务详情面板集成活动流、评论和依赖关系，完整记录每个任务的执行过程。

#### 功能特性

任务支持依赖关系（DAG），Kanban 看板实时展示任务状态和活跃 Worker 徽标。PM 创建 Proposal 时通过 `dependsOnDraftUuids` 设定任务执行顺序。

##### Session 可观测性

每个 Developer Agent 创建 Session 并 checkin 到任务，UI 上实时显示哪个 Agent 正在处理哪个任务：

- Kanban 卡片显示 Worker 徽标
- 任务详情面板显示活跃 Worker
- Settings 页面管理 Agent 和 Session

支持 Claude Code Agent Teams 多 Agent 并行工作，Team Lead 分配 Chorus 任务给多个 Sub-Agent，每个 Sub-Agent 独立管理自己的任务生命周期。

Claude Code 插件自动化 Session 生命周期管理：

- **SubagentStart** — 自动创建 Chorus Session
- **TeammateIdle** — 自动发送心跳
- **SubagentStop** — 自动 checkout 任务 + 关闭 Session + 发现新解锁任务

##### 需求澄清

PM Agent 在创建 Proposal 前通过结构化问答轮次澄清需求。问题按类别分类（功能性、范围、技术等），支持在 CC 终端或 Web UI 上回答。Proposal 提交前必须完成澄清或显式跳过。

##### Proposal 审批流

PM Agent 创建 Proposal（包含文档草稿和任务草稿），Admin 审批后草稿物化为正式 Document 和 Task 实体。

##### 通知系统

应用内通知 + SSE 实时推送 + Redis Pub/Sub 跨实例传播：

- **10 种通知类型** — 任务分配/验证/重开、提案批准/驳回、评论新增等
- **个人偏好设置** — 每种通知类型可独立开关
- **MCP 工具** — `chorus_get_notifications` 、 `chorus_mark_notification_read` 供 Agent 使用
- **Redis Pub/Sub** — 可选，支持多 ECS 实例间 SSE 事件同步（ElastiCache Serverless）

> **通知系统设计文档 →**

##### @Mention

评论和实体描述中支持 @mention — 用户和 AI Agent 可以互相 @，触发定向通知：

- **Tiptap 编辑器** — 输入 `@` 弹出自动补全下拉框，搜索用户/Agent
- **权限隔离** — 用户可 @ 同公司所有用户 + 自己名下的 Agent；Agent 遵循同 owner 规则
- **Mention 通知** — `action="mentioned"` 带上下文片段，点击直达源实体
- **MCP 工具** — `chorus_search_mentionables` 供 Agent 查询 UUID 后精确写入 mention

> **@Mention 系统设计文档 →**

##### 活动流

全量记录所有参与者的操作，支持 Session 归因（AgentName / SessionName 格式），实现完整的工作审计追踪。

```

# 使用 Docker Hub 预构建镜像启动

  docker compose up -d

# 访问
open http://localhost:3000
```

前置条件：AWS CLI（已配置凭证）、Node.js 22+、pnpm 9+

```
./install.sh
```

### AI-Driven Development Life Cycle: Reimagining Software Engineering \| AWS DevOps &amp; Developer Productivity Blog

https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/

#### AWS DevOps &amp; Developer Productivity Blog

Business and technology leaders are constantly striving to improve productivity, increase velocity, foster experimentation, reduce time-to-market (TTM), and enhance the developer experience. These North Star goals drive innovation in software development practices. This innovation is increasingly being powered by artificial intelligence. Particularly, generative AI powered tools such as [Amazon Q Developer](https://aws.amazon.com/q/developer/) and [Kiro](https://kiro.dev/) have already begun to revolutionize how software is created. As things stand, organizations employ AI in software development through two primary approaches: AI-assisted development, where AI enhances specific tasks like documentation, code completion, and testing; and AI-autonomous development, where AI is expected to generate entire applications without human intervention based on user requirements. Both these approaches have produced suboptimal results in terms of velocity and software quality that AI-DLC aims to address.

#### Why do we need a transformative approach to AI in software?

Our existing software development methods, are designed for human-driven, long running processes, with product owners, developers, architects alike spending most of their time on non-core activities such as planning, meetings, and other software development lifecycle (SDLC) rituals. Simply retrofitting AI as an assistant not only constrains its capabilities but also reinforces outdated inefficiencies. To truly harness AI’s power and achieve the productivity North Star goals, we need to reimagine our entire approach to the software development lifecycle.

To achieve transformative results, we need to position AI as a central collaborator and teammate in the development process, and leverage its capabilities throughout the software development lifecycle. This is why we’re introducing the [AI-Driven Development Lifecycle (AI-DLC)](https://prod.d13rzhkk8cj2z0.amplifyapp.com/), a new methodology designed to fully ingrain AI capabilities into the very fabric of software development.

#### What is AI Driven Development Life Cycle (AI-DLC)?

AI-DLC is an AI-centric transformative approach to software development that emphasizes two powerful dimensions:

- ****AI Powered Execution with Human Oversight****: AI systematically creates detailed work plans, actively seeks clarification and guidance, and defers critical decisions to humans. This is critical since only humans possess the contextual understanding and knowledge of business requirements needed to make informed choices.
- ****Dynamic Team Collaboration****: As AI handles the routine tasks, teams unite in collaborative spaces for real-time problem solving, creative thinking and rapid-decision-making. This shift from isolated work to high-energy teamwork accelerates innovation and delivery.

![Depicts an AI-centric approach to software development, with AI in the center, with cross functional team members around it, working collaboratively with one another.](https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2025/07/31/aidlc-image01.png)

These two dimensions enable you to deliver software faster without compromising on quality.

#### How does AI-DLC work?

At its core, AI-DLC operates by having AI initiate and direct workflows through a new mental model:

![AI creates plans, seeks clarification, &amp; implements plans, while humans make critical decisions](https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2025/07/31/aidlc-image02.png)

This pattern, where AI creates a plan, asks clarifying questions to seek context, and implements solutions only after receiving human validation, repeats rapidly for every SDLC activity, to provide a unified vision and approach for all development pathways.

With this mental model at its core, the software development in AI-DLC takes place in three straightforward phases:

- In the **Inception phase**, AI transforms business intent into detailed requirements, stories and units through “Mob Elaboration” – where the entire team actively validates AI’s questions and proposals.
- In the **Construction phase**, using the validated context from the Inception phase, AI proposes a logical architecture, domain models, code solution and tests through “Mob Construction” – where the team provides clarification on technical decisions and architectural choices in real time.
- In the **Operations phase**, AI applies the accumulated context from previous phases to manage infrastructure as code and deployments, with team oversight.

Each phase provides richer context for the next, thus enabling AI to provide increasingly informed suggestions.

![The three phases of AI-DLC: Inception, Construction, Operation](https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2025/07/31/aidlc-image03.png)

## 摘要（1）

### 2026-03-17 09:18:18

#### 一句话总览

这几条内容共同指向一个判断：**AI Coding 正在从“模型多强”转向“工程系统是否可靠、协作机制是否成立”**。其中，**AI-DLC** 提供了方法论，强调“AI 先提出方案、人类做关键验证”；而 **Chorus** 则像这套方法论的工程化落地，把 PM / Dev / Admin 多 Agent 协作、任务流转、上下文恢复、可观测性和故障恢复都做成了一套可运行的“Agent Harness”。

---

#### 精炼总结

##### 1. 核心趋势

- 今年 AI Coding 的关注点，明显从单纯比拼模型能力，转向了**更现实的工程问题**。
- 真正影响 AI 开发效果的，不只是模型推理能力，而是**多 Agent 如何协作、任务如何管理、上下文如何延续、失败如何恢复**。
- 换句话说，AI 编程的瓶颈，越来越不在“会不会写代码”，而在“能不能稳定完成一个完整项目流程”。

##### 2. AI-DLC 的核心思想

- AI-DLC（AI-Driven Development Lifecycle）是一套**AI 驱动的软件开发方法论**。
- 它的关键原则是：**AI 主动规划和执行，人类负责澄清、审批和关键决策**。
- 它反对两种极端：
  - 只把 AI 当零散助手；
  - 期待 AI 脱离人类独立完成全部开发。
- 它强调的是一种新模式：**AI 先提方案，持续问清问题，再在人的确认下执行**。

##### 3. Chorus 是什么

- Chorus 不是单纯的 Agent 框架，而是一个 **Agent Harness**。
- “Harness” 可以理解成：**包在 LLM 外面的一层工程基础设施**，专门解决 AI Agent 真正落地时会遇到的问题。
- 它的角色设计很清晰：
  - **PM Agent**：分析需求、提问澄清、产出 Proposal / PRD / Task DAG
  - **Developer Agent**：认领任务、编码、汇报、提交验证
  - **Admin**：审批方案、验收结果、管理流程

##### 4. Chorus 解决的痛点

它重点解决的不是“让 Agent 更聪明”，而是“让 Agent 更可控、更可靠”：

- **Session 持久化**：Agent 重启后不丢进度
- **严格任务状态机**：避免多人/多 Agent 状态混乱
- **Check-in 上下文恢复**：新会话不必从零开始
- **子 Agent 编排**：支持并行、多 Agent 协作
- **可观测性**：看板、活动流、Session 归因，知道谁在干什么
- **故障恢复**：卡住的 Session 自动过期，任务回到池中重新接手
- **需求澄清**：先问清，再做方案
- **Task DAG**：任务依赖可视化，支持并行执行
- **@Mention 与通知**：让人和 Agent 真正协同

##### 5. 本质结论

- **AI-DLC 提供“怎么协作”的理念**
- **Chorus 提供“怎么把理念变成系统”的实现**
- 两者共同说明：未来 AI Coding 的竞争力，不只是更强模型，而是**更成熟的 Agent 操作系统 / 协作中间层**。

---

#### 深入浅出解读

##### 一、为什么现在大家开始从“工程视角”看 AI Coding？

因为过去一段时间，很多人对 AI Coding 的期待过于集中在模型本身，比如：

- 模型能不能一次写完整功能
- 代码补全是否更准确
- 能不能直接生成整个应用

但实际做项目后会发现，真正麻烦的往往不是“写出一段代码”，而是这些问题：

- 中途上下文断了怎么办？
- 多个 Agent 同时做事，如何不打架？
- 一个任务卡住了，谁来接手？
- 需求不清晰时，AI 是继续瞎做，还是先问？
- 谁批准方案？谁验证结果？
- 出了问题，怎么追溯是哪一个 Agent、哪个 Session 干的？

这些都不是单个模型参数能解决的，而是**系统工程问题**。

可以类比为：

- **模型**像“发动机”
- **Harness**像“整车底盘、变速箱、刹车系统、仪表盘”

光有更强发动机，车不一定好开；要想真正上路，必须有完整的工程系统。

---

##### 二、AI-DLC 到底想解决什么？

AWS 这篇 AI-DLC 文章，本质上是在批评两种常见做法都不够好。

###### 1. 只把 AI 当助手，提升有限

这种模式下，AI 只是帮你：

- 写文档
- 补代码
- 生成测试
- 回答问题

问题是，**整个开发流程还是老样子**。人类仍然要在各种会议、交接、计划、协调中消耗大量时间，AI 只是局部提效，没有改变整体流程。

###### 2. 让 AI 全自动开发，质量和可信度又不够

另一种极端是：给 AI 一个需求，期待它自己完成全部系统。

问题是：

- 业务上下文 AI 未必真懂
- 关键决策没人兜底
- 出错时责任不清
- 很难确保和组织规范一致

所以 AI-DLC 提出的折中但更现实的路线是：

> **AI 做主动执行者，人类做高价值判断者。**

也就是：

- AI 负责快速产出方案、拆任务、写代码、写测试、推进流程
- 人类负责澄清需求、审核方案、批准关键决策、验收交付结果

这正是文中提到的核心模式：**AI Powered Execution with Human Oversight**。

---

##### 三、“Reversed Conversation” 为什么重要？

Chorus 和 AI-DLC 的思想高度一致，其中最关键的一句话是：

> **Reversed Conversation：AI 提议，人类验证。**

之所以叫“反转对话”，是因为它把传统工作方式颠倒过来了。

###### 传统方式

- 人类写完整需求
- 人类拆任务
- 人类分配工作
- AI 只是辅助执行一点点

###### Reversed Conversation 方式

- AI 先分析需求
- AI 主动提出澄清问题
- AI 产出 Proposal / PRD / 任务拆解
- 人类审批、补充、纠偏
- AI 再继续执行

这个变化很大，因为它把 AI 从“被动工具”变成了“主动协作者”。

但注意，它又不是完全放权给 AI，因为**关键节点仍由人类审核**。这就兼顾了：

- 速度
- 可控性
- 质量
- 责任边界

这也是为什么它比“完全自动开发”更容易在真实团队里落地。

---

##### 四、为什么 Chorus 强调自己不是 Framework，而是 Harness？

这点很关键。

###### Framework 的思路

通常是给你很多组件、接口、扩展点，让你自己拼一套系统。

优点是灵活；缺点是：

- 需要自己设计约束
- 需要自己补齐流程
- 很容易出现“能跑，但不可靠”

###### Harness 的思路

Harness 更像一个“约束过的工作台”：

- 生命周期已经定义好
- 状态机已经定好
- 角色权限已经分好
- 审批节点已经内建
- 可观测性和恢复机制已经准备好

也就是说，Chorus 想表达的是：

> 我不是给你一堆积木，而是给你一套能直接组织 AI 团队工作的操作环境。

这其实很符合 AI Agent 落地现状。因为 Agent 最大的问题不是“不够灵活”，而是“太容易失控”。所以很多时候，**比起开放扩展，更重要的是流程收敛和边界明确**。

---

##### 五、Chorus 解决的问题，为什么都很“工程化”？

因为这些问题全是 Agent 真上生产以后必然遇到的。

##### 1. Session 持久化

Agent 并不是一次性完成所有任务，中途可能：

- 重启
- 上下文窗口刷新
- 被打断
- 切换到别的任务

如果没有持久化 Session，Agent 每次都像失忆一样重新开始，效率极低，还容易重复劳动。

所以 Chorus 的做法是：**把 Agent 的会话状态作为正式对象管理**。

这意味着 Agent 不再像临时聊天机器人，而更像一个有工号、有值班记录的“数字员工”。

##### 2. 严格任务状态机

很多协作系统混乱，根本原因是没有统一状态：

- 有人说在做
- 有人以为还没开始
- 有人觉得已经完成
- 有人等着验证却没人提交

Chorus 用明确状态机流转，把任务从认领、进行中、提交验证到已验证都固定下来。这样系统里始终有一个**单一真相源**。

##### 3. 上下文连续性

LLM 天生是“短记忆”的。新上下文窗口一开，它并不天然知道之前发生了什么。

Chorus 通过 `checkin` 恢复：

- 角色设定
- 当前任务
- 项目状态
- 相关上下文

这相当于给每个 Agent 设计了“交接班流程”。

##### 4. 可观测性

软件工程里有句话：**看不见，就管不了；管不了，就优化不了**。

如果你不知道：

- 哪个 Agent 在处理哪个任务
- 谁卡住了
- 谁刚提交了变更
- 哪个 Session 空转太久

那多 Agent 协作很快就会变成黑箱。

所以 Chorus 提供 Kanban、活动流、Worker 徽标、Session 归因，本质上是在做 Agent 世界里的 observability。

##### 5. 故障恢复

人类团队里，一个人卡住，经理可以换人接手；AI 系统也一样。

Chorus 设计“空闲 Session 过期、孤儿任务回任务池”，本质上是在防止整个流水线被一个挂住的 Agent 拖死。这是非常典型的生产系统思路。

---

##### 六、Task DAG 和需求澄清，为什么是两个特别重要的点？

这两个点说明 Chorus 不只是“任务执行器”，而是在试图管理**工作流质量**。

##### 1. Task DAG：解决“先做什么、能不能并行”

DAG（有向无环图）把任务依赖关系明确表达出来。

好处是：

- 知道哪些任务必须先完成
- 知道哪些任务可以并行
- 避免多个 Agent 做了互相依赖却顺序错误的工作
- 为自动调度提供基础

没有 DAG，多 Agent 并行很容易“表面热闹，实际撞车”。

##### 2. 需求澄清：解决“方向错了，做再快也没用”

很多 AI Coding 出问题，不是代码写错，而是**需求理解错**。

AI-DLC 里特别强调：AI 要先问问题，再做方案。Chorus 也把这个过程做成结构化问答，并且把它设成 Proposal 前的门控步骤。

这非常重要，因为它把“需求澄清”从一个随缘动作，变成了一个**制度化环节**。

---

##### 七、Chorus 与 AI-DLC 是什么关系？

可以这样理解：

##### 1. AI-DLC 是方法论

它回答的是：

- 为什么传统开发流程不适合 AI
- 为什么 AI 应该成为主动协作者
- 为什么必须有人类监督
- 为什么需要更短、更高频、更协同的开发节奏

它更像一套“组织思想”和“工作哲学”。

##### 2. Chorus 是基础设施实现

它回答的是：

- 这种方法论如何落实到系统里？
- Agent 怎么分角色？
- 审批怎么走？
- 状态怎么管理？
- 会话怎么持久化？
- 通知和 @mention 怎么做？
- 多 Agent 如何并行又不混乱？

它更像一套“AI 团队操作系统”。

所以两者关系是：

> **AI-DLC 提供设计原则，Chorus 提供工程载体。**

---

##### 八、这说明了 AI Coding 下一阶段的竞争点是什么？

从这三条内容来看，下一阶段竞争很可能不只是这些：

- 谁模型更强
- 谁代码生成更快
- 谁 benchmark 更高

而会更多落在这些方向：

###### 1. Agent 协作基础设施

- 多角色分工
- 任务编排
- 权限隔离
- 生命周期管理

###### 2. 过程可控性

- 人类在哪些节点审核
- 状态是否清晰
- 决策是否可追踪
- 是否能防止 silent failure

###### 3. 上下文与记忆系统

- 跨会话连续性
- 长任务恢复能力
- 项目知识沉淀
- 角色 persona 注入

###### 4. 可观测性和审计

- 谁在做什么
- 为什么这样做
- 失败发生在哪
- 如何定位和追责

###### 5. 人机协作体验

- 人怎么随时介入
- Agent 怎么主动提问
- 人和 Agent 怎么互相 @
- 通知、反馈、审批是否顺畅

也就是说，AI Coding 正从“单兵作战工具”演进成“协作型生产系统”。

---

#### 可以怎么理解 Chorus 的价值

如果用一句更接地气的话说：

> **Chorus 的价值，不是让 AI 更像聊天机器人，而是让 AI 更像一个能进入团队流程、遵守制度、可被管理的成员。**

它试图把 AI 从“偶尔帮忙的工具”升级为：

- 有角色分工的成员
- 有任务状态的执行者
- 有审批链路的参与者
- 有活动记录的可审计对象
- 有交接机制的长期协作者

这正是 AI 从“玩具”走向“生产力”的关键一步。

#### 关键启发

##### 对团队管理者

- 不要只看模型能力，要看 AI 是否能嵌入真实交付流程。

- AI Coding 的机会正在从“更强 IDE 助手”转向“Agent 协作平台 / Agent 操作系统 / AI 工作流基础设施”。
