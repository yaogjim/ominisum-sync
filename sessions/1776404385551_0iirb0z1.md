## 正文

**LangChain OSS**

### 在后台运行子代理

我们开始对我们的代理提出更多要求——希望它们承担更长、更复杂的任务。随着我们这样做，我们传统上协调代理的方式开始出现一些裂痕。

我们最近发布了

[异步子代理](https://docs.langchain.com/oss/javascript/deepagents/async-subagents) 向 Deep Agents 以帮助解决这个问题！这是一种模式，它允许代理在后台运行委托的工作，这是我们感到兴奋的事情，因为它弥补了传统代理架构的一些不足。

#### 传统子代理失效之处

子代理是监督代理委托特定范围工作的代理。子代理从监督代理获取指令、使用相关工具，并在完成后返回总结。这是一种上下文工程模式，我们在构建的几乎所有代理中都采用了它，出于几个重要原因。

1. 当工作被分解为更小的任务时，代理的表现更好 - 监督代理会先理解问题，组织任务，然后协调执行这些任务的工作人员。
2. 不是所有关于小任务的信息对大目标都很重要 - 通过将事物分解为专注且独立的代理运行，我们向监督者隐藏了不必要的上下文。

这个模式有效。但随着我们给代理分配了更长且更复杂的任务，内嵌子代理开始失效。

#### 代理们在子代理工作时陷入死锁

子代理通过提供给主管代理的工具来调用，由于工具调用在代理内部的工作方式，主管代理必须在工具调用得到子代理的响应后，才能对其他事情进行推理。

当子代理被分配较小、低风险的任务时，这并不是什么大问题。但现在我们给代理分配了更复杂的任务和工具（以及运行时间更长的模型），这种情况变得更明显了。如果一个子代理需要一个小时，你必须等待一个小时才能再次与代理交互。

#### 新信息难以协调

对正在工作的代理来说，有几个重要的信息渠道：

- 用户输入 — 用户可能想要在任务进行过程中指导代理、添加上下文或更改优先级。
- 来自其他工作的结果 — 一个子代理的输出可能会告知另一个子代理接下来应该做什么
- 部分进度 — 有时你希望在任务完成之前纠正其错误方向。

使用内联子代理时，这些通道均不可用。主管被阻塞，因此用户无法与其通话。子代理无法并发运行，因此结果不会交叉影响。并且子代理的执行是全有或全无的，这意味着无法发送任务中途更新，也无法优雅地处理部分失败。主管触发一个子代理，只能寄希望于最好的结果。

#### 输入: 异步子代理

思考异步子代理的一种简单方式是：它们是在后台运行而非按顺序执行的子代理。主管不再等待子代理完成后再继续，而是启动一个任务，立即获得一个任务 ID，然后继续工作。在此期间，它可以与用户交互、启动更多子代理，或者在后台工作进行的同时，在问题的其他部分取得进展。

因为子代理是有状态的，并且会维护自己的对话线程，主管可以发送跟进指令、在任务中途调整方向或取消不再需要的工作。与其说是“一发即忘”，不如说是“一发即控”。

它们如何工作

与其让每个子代理给主管一个单独的阻塞工具调用，异步子代理会给主管一组更像任务队列的管理工具：

工具用途 start\_async\_task 在远程代理上启动任务。立即返回任务 ID。 check\_async\_task 轮询任务的状态并在任务完成时获取其结果。 update\_async\_task 向正在运行的任务发送后续指令。 cancel\_async\_task 取消正在运行的任务。 list\_async\_tasks 列出所有已跟踪的任务及其当前状态。

监督器自然地将这些工具用作其推理循环的一部分——它可以启动一些任务，返回与用户对话，检查进度，并根据需要调整方向。

传统子代理实际上只是父代理的一个功能——它们共享一个进程、共享状态，并且只存在于监督者的执行循环中。异步子代理将它们视为完全独立且可单独寻址的代理。它们可以在自己的进程中运行、维护自己的状态，并且能够扩展到可能调用数百或数千个子代理的运行场景。

基于 Agent 协议

这种分离需要的不仅仅是进程内函数调用。异步子代理基于

[代理协议](https://github.com/langchain-ai/agent-protocol)，这是一个与框架无关的 API 规范，用于管理远程代理。它定义了用于创建线程、启动运行、轮询状态、发送更新以及管理长期记忆的标准端点。主管通过一致的界面管理异步工作所需的一切。

主要优势是部署灵活性。您不会被锁定在任何单一的托管平台上。在 LangSmith 部署上运行您的异步子代理

[LangSmith 部署](https://docs.langchain.com/langsmith)以获得托管体验，或者在您自己的基础设施上自行托管它们。管理器不关心子代理的位置。它发送任务、获取任务 ID，并通过相同的标准接口以相同方式管理生命周期。

要了解更多关于 Agent 协议的信息，请参阅

[规范](https://github.com/langchain-ai/agent-protocol)以及

[API 参考](https://langchain-ai.github.io/agent-protocol/api.html)

.

#### 如何在 DeepAgents 中使用异步子代理

[Deep Agents](https://docs.langchain.com/oss/python/deepagents) 是我们的通用代理框架，我们经常谈论它

[we talk a lot about](https://blog.langchain.com/)

. Adding async subagents to DeepAgents is as simple as swapping an async subagent spec into the subagents list — you can mix and match them freely with inline subagents.

借助 LangSmith 部署

定义你的代理并在 langgraph.json 中注册它们。由于研究者是一个独立的代理，主管会自动获得异步管理工具：

```typescript
// agents.ts
import { createAgent } from "langchain";
import { createDeepAgent } from "deepagents";

export const researcher = createAgent({
  model: "anthropic:claude-sonnet-4-6",
  instructions: "Perform deep research on the given topic.",
  tools: [searchWeb, readUrl],
});

export const agent = createDeepAgent({
  model: "anthropic:claude-opus-4-6",
  subagents: [{
    name: "researcher",
    description: "Performs deep research on a topic.",
    graphId: "researcher",
  }],
});
```

```typescript
// langgraph.json
{
  "dependencies": ["."],
  "graphs": {
    "researcher": "./agents.ts:researcher",
    "agent": "./agents.ts:agent"
  }
}
```

子代理在自己的进程中运行，拥有自己的状态，而主管仅负责委派任务并进行检查反馈。

自托管的

如果你想要完全控制你的子代理运行的位置，你可以自行托管它们。子代理只需要实现代理协议端点，并且监督者通过 URL 而不是图 ID 连接到它。

```typescript
export const agent = createDeepAgent({
  model: "anthropic:claude-opus-4-6",
  subagents: [{
    name: "researcher",
    description: "Performs deep research on a topic.",
    graphId: "researcher",
    url: "<http://localhost:2024>",  // points to your self-hosted server
  }],
});
```

自托管服务器实现了 Agent 协议端点（创建线程、启动运行、轮询状态、取消任务），并且可以在任何地方运行——Docker 容器、虚拟机、您自己的 Kubernetes 集群。我们有一个

[完整的自托管示例](https://github.com/langchain-ai/deepagentsjs/tree/main/examples/async-subagent-server) 其中包含一个 Hono 服务器、Postgres 支持的状态以及您可以用作起点的 Docker Compose 配置。

了解更多

要了解完整的操作指南 — 包括部署配置、跟踪和故障排除 — 请参阅

[异步子代理文档](https://docs.langchain.com/oss/javascript/deepagentsjs/async-subagents)。

## 通俗精炼（1）

### 2026-04-17 05:39:27

#### 异步子代理：让 AI 在后台并行干活

##### 核心观点

这篇文章讲的是：**传统子代理适合短任务，但一旦任务变长、变复杂，就会拖慢整个代理系统**。  
LangChain 推出的 **异步子代理（Async Subagents）**，本质上是让子任务像后台任务一样运行，主管代理不用干等，可以一边继续思考、一边和用户交互、一边协调更多任务。

##### 传统子代理的问题

###### 1. 会“卡住”主管代理
传统模式下，主管代理一旦调用子代理，就必须等它做完才能继续。  
如果子任务要跑很久，比如几十分钟甚至一小时，整个系统就像被“锁死”了一样，用户也没法继续互动。

###### 2. 无法灵活接收新信息
任务执行过程中，常常会出现新的输入，比如：
- 用户临时补充要求
- 其他子任务产出新结果
- 发现当前方向跑偏，需要及时纠正

但传统子代理是串行、阻塞式的，**这些信息很难中途插入和协调**。

##### 异步子代理解决了什么

###### 1. 子任务改为后台运行
主管代理发起子任务后，**立刻拿到任务 ID**，不用等待结果返回。  
这样它可以继续：
- 和用户对话
- 启动更多子代理
- 处理其他部分工作

###### 2. 子任务可持续管理
异步子代理不是“一次发出就不管了”，而是可以：
- 查询状态
- 中途补充指令
- 调整方向
- 取消任务

这让代理协作从“死等结果”变成“动态调度”。

##### 它是怎么实现的

###### 1. 用一组任务管理工具替代阻塞调用
系统提供了几类核心能力：
- `start_async_task`：启动任务，立即返回任务 ID
- `check_async_task`：查询任务状态/结果
- `update_async_task`：更新任务指令
- `cancel_async_task`：取消任务
- `list_async_tasks`：查看所有任务状态

主管代理会把这些工具自然地融入自己的推理流程中。

###### 2. 子代理变成真正独立的运行单元
传统子代理更像父代理内部的一个函数；  
异步子代理则是**独立、可寻址、可扩展的代理实例**，可以单独运行、单独维护状态，适合大规模并发。

##### 关键技术基础

###### 基于 Agent 协议
异步子代理依赖一个 **框架无关的 Agent 协议**。  
它定义了统一接口，用于：
- 创建线程
- 启动任务
- 轮询状态
- 发送更新
- 管理长期记忆

这意味着部署更灵活：**既可以托管在 LangSmith，也可以完全自托管**，主管代理只需要按统一协议管理它们。

##### 实际价值

###### 对产品和系统设计的意义
异步子代理带来的核心价值是三点：
- **更强的并行能力**：多个复杂任务可同时推进
- **更好的交互体验**：任务执行中用户还能继续介入
- **更高的系统扩展性**：适合长流程、复杂协作和多代理场景

本质上，它把代理系统从“串行执行器”升级成了“任务调度系统”。

##### 一句话总结

**异步子代理的意义，不只是让 AI 跑得更快，而是让 AI 从“单线程干活”进化为“可并发、可调度、可中途纠偏”的协作系统。**

## 结构化（1）

### 2026-04-17 05:44:33

#### 主旨概括

这篇文章主要介绍了 **“异步子代理”** 这种新模式：它让子代理可以在后台独立运行，从而解决传统子代理在处理长任务、复杂任务时容易“卡住”的问题。  
核心价值在于：**主管代理不必一直等待子代理完成，可以一边继续工作、一边和用户交互，还能动态调整任务。**

##### 1. 为什么传统子代理一开始有效

- 传统子代理的作用，是由“主管代理”把某个明确的小任务委托出去，子代理完成后再返回总结。
- 这种模式之所以常用，主要有两个原因：
  - **任务拆小后效果更好**：主管先理解问题，再拆分任务，交给不同“工作人员”执行。
  - **减少无关上下文**：不是每个小任务的细节都对最终目标重要，子代理能帮主管屏蔽杂乱信息。
- 简单说，传统子代理很像项目经理把不同工作分给专人做，自己只看结果，不看所有过程细节。

##### 2. 传统子代理的问题出在哪里

###### 2.1 主管会被“卡死”

- 传统子代理通常是以“工具调用”的方式被主管触发的。
- 一旦主管发起调用，就必须**等子代理返回结果后**，才能继续推理或处理别的事情。
- 如果子代理执行的是复杂任务，时间可能非常长。
- 文中举的典型情况是：**如果一个子代理要跑 1 个小时，用户就得等 1 个小时，才能再次和代理互动。**

###### 2.2 新信息很难中途协调

文章指出，对一个正在执行长任务的代理来说，有 3 类信息非常重要：

- **用户输入**：用户可能想中途补充背景、修改优先级、纠正方向。
- **其他任务的结果**：一个子代理的结果，可能会影响另一个子代理下一步怎么做。
- **部分进度反馈**：任务还没结束时，用户或主管可能已经看出方向偏了，想及时纠正。

但在传统内联子代理模式下，这些都很难做到：

- 主管被阻塞，**用户无法及时插话**；
- 子代理不能真正并发，**任务之间难以相互影响**；
- 执行方式偏“全有或全无”，**很难发送中途更新，也不容易优雅处理部分失败**。

可以理解为：主管一旦把任务交出去，就像电话占线，只能“等结果”，不能中途改主意。

##### 3. 什么是异步子代理

- 异步子代理可以理解为：**在后台运行的子代理**，而不是按顺序阻塞执行。
- 主管启动任务后，会**立刻拿到一个任务 ID**，然后继续做别的事，而不是原地等待。
- 在子代理后台工作的同时，主管可以：
  - 继续和用户对话；
  - 再启动更多子代理；
  - 先推进问题的其他部分。

###### 关键改进

- 异步子代理是**有状态的**，会维护自己的对话线程。
- 所以主管不只是“发出去等结果”，还可以：
  - **发送后续指令**；
  - **中途调整方向**；
  - **取消不再需要的任务**。

文章用一句话概括这种变化：  
传统方式更像 **“一发即忘”**，而异步子代理更像 **“一发即控”**。

##### 4. 异步子代理是如何运作的

为了支持这种后台管理模式，系统提供了一组类似“任务队列”的管理工具：

- `start_async_task`：启动远程任务，**立即返回任务 ID**
- `check_async_task`：检查任务状态，完成时获取结果
- `update_async_task`：给正在运行的任务发送补充指令
- `cancel_async_task`：取消任务
- `list_async_tasks`：查看所有任务及当前状态

###### 这意味着什么

- 主管代理可以把这些操作自然地嵌入自己的推理循环中：
  - 先启动几个任务；
  - 回来继续和用户交流；
  - 定期检查进度；
  - 根据结果再补充、调整或取消。
- 这比传统子代理更接近真实团队协作：不是一次性下命令，而是持续跟进项目进展。

##### 5. 与传统子代理相比，架构上有什么变化

###### 传统方式

- 子代理本质上更像是父代理内部的一个功能：
  - **共享进程**
  - **共享状态**
  - 只存在于主管的执行循环里

###### 异步方式

- 异步子代理被当成**独立、可单独寻址的代理**：
  - 可以运行在自己的进程里
  - 维护自己的状态
  - 可以单独扩展

###### 规模上的意义

- 这种方式能支持更大规模的运行场景。
- 文中明确提到，它可以扩展到**一次运行中调用数百甚至数千个子代理**的场景。

##### 6. 它基于什么标准：Agent 协议

- 异步子代理不是简单的进程内函数调用，而是基于 **Agent 协议（Agent Protocol）**。
- 这是一个**与框架无关的 API 规范**，用于统一管理远程代理。
- 它定义了标准接口，用于：
  - 创建线程
  - 启动运行
  - 轮询状态
  - 发送更新
  - 管理长期记忆

###### 主要好处

- **部署灵活，不被单一平台绑定。**
- 你可以：
  - 部署到 **LangSmith**，享受托管体验；
  - 或者在自己的基础设施上**自托管**。
- 对主管来说，两者没有本质区别：
  - 都是发任务；
  - 拿任务 ID；
  - 通过同一套标准接口管理任务生命周期。

##### 7. 在 Deep Agents 中如何使用

文章说，在 **Deep Agents** 里接入异步子代理很简单，本质上就是把异步子代理配置加入 `subagents` 列表中。  
而且它支持和传统内联子代理**混合使用**。

###### 7.1 使用 LangSmith 部署

- 先定义代理，并在 `langgraph.json` 中注册。
- 示例中有两个代理：
  - `researcher`：负责做深度研究，使用的模型是 `anthropic:claude-sonnet-4-6`
  - `agent`：主管代理，使用的模型是 `anthropic:claude-opus-4-6`
- 当 `researcher` 被注册为独立代理后，主管会自动获得异步管理工具。
- 此时：
  - 子代理在**自己的进程**中运行；
  - 拥有**自己的状态**；
  - 主管只负责**委派、检查和反馈**。

###### 7.2 自托管方式

- 如果希望完全控制子代理运行位置，可以自己部署。
- 这时子代理只需要实现 Agent 协议的相关端点，主管通过 **URL** 连接它，而不是图 ID。
- 示例里给出的连接地址是：`http://localhost:2024`

###### 自托管可以部署到哪里

文章提到，自托管服务可以运行在很多环境里，例如：

- Docker 容器
- 虚拟机
- 自己的 Kubernetes 集群

此外，官方还提供了一个完整自托管示例，包含：

- 一个 **Hono server**
- **Postgres** 支持的状态存储
- 可直接作为起点的 **Docker Compose** 配置

##### 8. 文章的核心结论

- 传统子代理适合较短、较简单、低风险的任务；
- 但面对更长、更复杂的任务，它会让主管代理被阻塞，影响交互、协调和扩展；
- 异步子代理通过“后台运行 + 可持续管理”的方式，解决了这些关键问题；
- 它特别适合需要：
  - 长时间执行
  - 多任务并发
  - 中途调整方向
  - 大规模扩展  
  的代理系统。

##### 9. 一个通俗例子帮助理解

假设主管代理要完成“调研一家公司的市场、产品和竞争对手”：

- **传统子代理**：主管先派一个研究员去查资料，这期间主管只能干等，不能接收用户新要求，也不能同时启动别的任务。
- **异步子代理**：主管可以同时启动多个后台任务：
  - 一个查市场
  - 一个查产品
  - 一个查竞品  
  然后自己继续和用户沟通。  
  如果用户中途说“先重点看竞品”，主管可以马上给相关子代理补充指令，甚至取消不重要的任务。

这样，整个系统就更像一个真正能协同工作的团队，而不是只能“一个任务做完再做下一个”的单线程助手。
