>
> **摘要**：文章指出Coding Agent可能基于对话记录中的旧文件内容继续编辑，造成“旧读陷阱”。作者强调Harness必须维护独立的文件真实状态，包括读取范围、完整性、mtime、大小、hash和baseline，并在编辑前验证是否基于最新文件事实。

## 分析要点

- **核心高价值点**：转录文本不等于文件真相，Harness必须独立维护可验证的File State Records。
- **留存建议**：长期保留（提出了Coding Agent文件状态管理中的关键风险和可复用设计原则，对Agent Harness设计有长期参考价值）

**知识要点**

- Coding Agent不能仅依赖conversation transcript判断文件当前状态，workspace才是事实来源
- read\_file应被视为一种安全合同，而不仅是普通工具输出
- 部分读取不应自动授权高风险的整文件编辑
- Harness应跟踪路径、行范围、总行数、完整读取标记、mtime、文件大小、SHA-256和baseline文本
- 外部修改、文件删除、过大文件变化等应触发stale warning或强制重新读取

**行动项**

- 在Agent Harness中为每次read\_file建立File State Record
- 对patch或write操作增加基线新鲜度校验
- 对仅局部读取后尝试整文件重写的操作进行拒绝或要求完整读取
- 在session resume时恢复文件可信状态而不仅恢复对话文本

**马东锡 NLP**

### 旧读陷阱

Harness 系列文章之二，陈旧读取陷阱

模型记住的是 transcript，但 Harness 必须要记住 truth。

> 什么是陈旧读取陷阱？

Coding Agent 最危险的 bug，常常看起来很普通。

Agent 读了一个文件。用户改了这个文件。

Model 记得 transcript 里的文件内容，但磁盘上的文件已经变了。

Agent 继续编辑旧版本。

没有夸张的报错，没有明显的 hallucination，只是 model 很自信地基于过期证据工作，落入了 “旧读陷阱” （我造的词 ：））。

这就是陈旧读陷阱。

请记住：

> 转录文本不等于文件真相。

如果一个 coding agent 分不清 model 记住的文件内容是否还匹配磁盘，它迟早会 patch 昨天的代码。

![Image](https://pbs.twimg.com/media/HKe4JQuWQAAEZh_?format=jpg&name=large)

#### 失败

想象这个 sequence：

![Image](https://pbs.twimg.com/media/HKe4bJ6XsAEOxqI?format=jpg&name=large)

Model 在用心做事，从它的视角看，文件内容就在 conversation 里。

问题在于，conversation 只是历史。workspace 才是当前事实。

#### 朴素设计

一个小型 agent 往往把 tool output 当成普通 transcript text：

![Image](https://pbs.twimg.com/media/HKe4x5MWoAAG34s?format=jpg&name=large)

只要 transcript 外没有变化，这样能跑。但 transcript 和 磁盘并非同一状态。

![Image](https://pbs.twimg.com/media/HKe5U6AWMAEEzIE?format=jpg&name=large)

如果 harness 只会追加文本，model 就可能在一个已经消失的世界里行动。

#### Harness 需要知道的内容

harness 需要单独记录 file truth，不能只记录 “model 读过东西”。

它需要知道 File State Records，简而言之，时刻记录 file state：

![Image](https://pbs.twimg.com/media/HKe5zRhXsAAytmH?format=jpg&name=large)

> 转录是按时间顺序的，文件内容是有状态的

![Image](https://pbs.twimg.com/media/HKe6SeQWoAEKqxw?format=png&name=large)

transcript 回答：conversation 里发生过什么？

file state 回答：model 现在可以相信哪些文件内容？

#### Harness 合同

成熟的 harness 会把 read\_file 看成一份 contract。

![Image](https://pbs.twimg.com/media/HKe6q83XIAA-Vlb?format=jpg&name=large)

这样，file read 从一个方便的工具，变成了 safety mechanism。

Model 依然可以提出 edit proposal。Harness 负责判断这个 proposal 是否基于最新的 file truth。

![Image](https://pbs.twimg.com/media/HKe7CsKXYAENMjt?format=jpg&name=large)

#### 部分读取是部分的

Stale read trap 里面还要注意一点， 即 partial reads。

Model 只读了 lines 100-140，然后尝试重写整个文件。Harness 应该立刻格外关注这样的 partial reads。Range read 可以帮助回答问题，但它不应自动授权高风险 edit。

![Image](https://pbs.twimg.com/media/HKe7lTjWYAA0KrO?format=jpg&name=large)

一个简单规则很有用：

> 对现有文件的编辑应该需要全新的完整文件基线，除非编辑工具具有更严格的精确上下文约定。

这样可以避免 model 只理解局部片段，却要猜完整个文件。

#### Harness 应该跟踪什么

当 read\_file 运行时，要记录：

- 工作区相对路径
- 行范围 和 总行数
- 这次 read 是否覆盖完整文件
- 修改时间、文件大小、SHA-256 指纹
- 有边界的基线文本
- state 的来源

当 write\_file 或 patch\_file 成功后，要把 post-edit content 记录成新的 known baseline。当下一轮 prompt 构建时，让 Agent 去 lazy refresh tracked files：

- 未更改内容 保持新鲜
- timestamp-only change 且内容相同，安静刷新
- 外接磁盘编辑会生成当前已更改行的代码片段
- 已删除或过大的已更改文件会变成 stale warning
- 新的 read\_file 会清除过期或外部变更状态

#### 为什么这会改变 Agent 的行为

一旦有 file state，agent 的行为会明显不同。

文件没变时，重复 read 可以被压缩成 summary，避免 context flooding。

文件在 agent 外部变化时，下一轮 prompt 可以显示当前 changed lines，而非旧 transcript content。

文件只被部分读取时，edit 可以在造成破坏前被拒绝。

agent 自己写入文件后，post-edit content 可以成为 fresh baseline。

session resume 之后，harness 可以恢复的不只是文本，还包括 agent 可以信任什么。

这会改变真实产品体验。

用这句话，结束这篇：

> 模型能够记住文本。框架必须记住真理。

#### 《旧读陷阱》精炼总结与解读

##### 一、深度总结

**核心问题：**  
Coding Agent 容易把「对话里读过的文件内容」当成「当前磁盘上的真实文件内容」。

但现实是：

> **transcript 是历史，workspace 才是真相。**

当用户或外部工具修改了文件后，模型仍可能基于旧内容继续编辑，于是产生**陈旧读取陷阱**：  
模型看似认真、逻辑自洽，却在修改一个已经过期的版本。

---

##### 二、关键观点

###### 1. 模型记住的是文本，不是真相

模型只能记住之前工具返回过的内容。  
但文件系统是动态的，文件可能随时被用户、IDE、脚本、其他 Agent 修改。

所以：

> **模型记忆 ≠ 文件状态。**

---

###### 2. Harness 必须维护「文件真相」

成熟的 Agent 框架不能只保存聊天记录，还要维护独立的**File State Records**，包括：

- 文件路径
- 读取行范围
- 是否完整读取
- 文件总行数
- 修改时间
- 文件大小
- SHA-256 指纹
- 当前可信基线内容
- 状态来源

也就是说，Harness 要知道：

> 模型现在到底还能相信哪些文件内容。

---

###### 3. 读取文件是一种安全契约

`read_file`不只是获取文本，而是建立一个编辑前提：

> 你读过什么、读得是否完整、读完后文件有没有变。

之后模型提出 patch 或 write 时，Harness 要检查：

- 这个编辑是否基于最新文件？
- 是否只读了局部却想改全局？
- 文件是否被外部修改过？
- 当前内容是否仍匹配旧基线？

---

###### 4. 局部读取不能授权高风险编辑

如果模型只读了第 100-140 行，却想重写整个文件，这是危险信号。

简单规则：

> 修改现有文件，最好需要完整且最新的文件基线；除非 patch 工具具备严格上下文校验。

否则模型会用局部理解去猜整个文件，容易破坏代码。

---

###### 5. 好的 Harness 会改变 Agent 行为

有了文件状态管理后：

- 文件没变：不用反复塞全文，节省上下文
- 文件变了：提示当前变更，而不是旧内容
- 只读局部：可拒绝危险编辑
- Agent 自己写入后：新内容成为可信基线
- 会话恢复后：不只恢复聊天，还恢复「哪些文件可信」

最终提升的是产品体验：更稳、更少误改、更少诡异 bug。

---

##### 三、深入浅出解读

可以把 Coding Agent 想成一个程序员。

它之前看过一份代码，记在脑子里。  
但它不知道：你刚刚已经在 IDE 里改过这份代码。

如果它继续凭记忆改，就像：

> 拿着昨天的地图，开今天的路。

路可能已经修了、封了、改道了。  
它不一定会报错，但很可能开错。

所以 Harness 的职责就是不断提醒它：

> 别只信记忆，先确认现实。

这里的「现实」就是磁盘上的最新文件。

---

##### 四、本文真正想说的

这篇文章不是在讲一个小 bug，而是在讲**Agent 系统设计的边界**：

| 层级 | 负责什么 |
|---|---|
| Model | 理解、推理、生成方案 |
| Harness | 管理状态、校验真相、阻止危险操作 |
| Workspace | 当前事实来源 |

模型再聪明，也不能天然知道文件有没有变。  
因此，可靠性不能只靠模型能力，必须靠框架机制兜底。

---

##### 五、辩证思考

###### 1. 这是工程问题，不是单纯模型问题

很多 Agent 失败，不是因为模型「幻觉」，而是因为系统没有给它最新事实。  
把所有错误都归因于模型，是偷懒。

真正成熟的 Agent 产品，需要：

> 模型智能 + 状态管理 + 工具契约 + 安全校验。

---

###### 2. 但过度校验也会降低效率

如果每次编辑都强制完整读取、强制 hash 校验，可能带来：

- 上下文变长
- 响应变慢
- 工具调用变多
- 用户体验变重

所以关键不是「永远重读」，而是**按风险分级**：

- 小范围 patch：严格上下文匹配即可
- 全文件重写：必须完整最新基线
- 外部变更：强制刷新
- 大文件：摘要 + 精确片段 + hash 管理

---

###### 3. Agent 的未来不是更会 “记”，而是更会 “验”

人类程序员也会犯旧读错误，但 IDE、Git、LSP、diff 工具会帮我们发现冲突。

Agent 也一样。  
未来可靠的 Agent，不是单纯上下文更长，而是拥有更强的：

- 状态感知
- 版本意识
- 冲突检测
- 变更追踪
- 操作约束

---

##### 六、一句话结论

> **模型负责记住文本，Harness 负责确认真相。**

或者更通俗地说：

> **Agent 可以凭脑子想，但动手前必须看一眼现场。**

## 结构化（1）

### 2026-06-11 10:28:04

##### 主旨概括

文章讨论了 Coding Agent 中一种隐蔽但危险的问题：**“旧读陷阱”**。核心观点是：**模型记住的是对话里的旧文本，但真正可靠的事实应来自当前磁盘文件状态；Harness 必须负责记录并校验文件真相。**

---

##### 1. 什么是“旧读陷阱”

**旧读陷阱**指的是：Agent 之前读过某个文件，之后用户或外部程序修改了这个文件，但模型仍根据对话记录里的旧内容继续编辑。

关键点：

- Model 记住的是 transcript，也就是历史对话中的文件内容。
- 但 workspace / 磁盘上的文件可能已经变化。
- Agent 如果不重新确认文件状态，就可能基于过期内容进行 patch。
- 这种错误通常不会有明显报错，也不像幻觉那么显眼，而是“看起来正常地改错了”。

一句话总结：

> 转录文本不等于文件真相。

---

##### 2. 朴素 Agent 设计的问题

很多小型 Agent 会把工具输出当作普通对话文本处理。

问题在于：

- transcript 只记录“过去发生过什么”；
- 磁盘文件状态才代表“现在真实是什么”；
- 如果 Harness 只是不断追加文本，模型可能会在一个已经不存在的文件版本上继续工作。

也就是说，**conversation 是历史，workspace 才是当前事实**。

---

##### 3. Harness 应该记录“文件真相”

作者认为，Harness 不能只知道“模型读过文件”，还必须维护独立的 **File State Records**，即文件状态记录。

它需要区分两个问题：

- transcript 回答：对话里发生过什么？
- file state 回答：模型现在还能相信哪些文件内容？

这意味着，Harness 要持续追踪文件当前状态，而不是完全依赖模型记忆。

---

##### 4. read_file 应该是一种“合同”

成熟的 Harness 应该把 `read_file` 看成一份 **contract（合同）**。

含义是：

- Model 可以提出编辑建议；
- Harness 负责判断这个建议是否基于最新的文件事实；
- 文件读取不只是方便工具，而是安全机制的一部分。

这样可以避免模型基于旧版本文件进行危险修改。

---

##### 5. 部分读取尤其危险

文章特别提醒：**partial reads（部分读取）**也是旧读陷阱的重要来源。

例如：

- Model 只读了第 100-140 行；
- 却尝试重写整个文件。

这种情况下，Harness 应该提高警惕，因为模型只了解局部内容，却可能在猜测整个文件结构。

一个实用规则是：

> 对已有文件的编辑，应该要求最新的完整文件基线，除非编辑工具有严格的精确上下文约定。

这样可以避免 Agent 只看过局部，却对全局做高风险修改。

---

##### 6. Harness 应该追踪哪些信息

当运行 `read_file` 时，Harness 应记录文件状态信息，包括：

- 工作区相对路径；
- 读取的行范围；
- 文件总行数；
- 这次读取是否覆盖完整文件；
- 修改时间；
- 文件大小；
- SHA-256 指纹；
- 有边界的基线文本；
- state 的来源。

这些信息可以帮助 Harness 判断：模型当前依据的内容是否仍然可信。

---

##### 7. 写入和修改后的状态更新

当 `write_file` 或 `patch_file` 成功后，Harness 应该把修改后的内容记录为新的 known baseline。

下一轮 prompt 构建时，Agent 可以对追踪文件进行 lazy refresh：

- 文件未更改：保持新鲜状态；
- 只有 timestamp 改变但内容相同：安静刷新；
- 外部磁盘编辑：展示当前已变更行的代码片段；
- 文件被删除或变得过大：给出 stale warning；
- 新的 `read_file`：清除过期或外部变更状态。

这样，Agent 不会继续依赖旧 transcript，而是基于最新文件事实行动。

---

##### 8. 这会如何改变 Agent 行为

有了 file state 后，Agent 的实际行为会明显改善：

- 文件没变时，重复读取可压缩成 summary，减少上下文污染；
- 文件被外部修改时，下一轮 prompt 展示当前 changed lines，而不是旧内容；
- 文件只被部分读取时，高风险 edit 可被提前拒绝；
- Agent 自己写入文件后，post-edit content 可成为新的 fresh baseline；
- session resume 后，Harness 不只恢复文本，还能恢复“哪些内容可信”。

这会直接改善真实产品体验，让 Agent 更可靠、更安全。

---

##### 结论

文章的核心收束句是：

> 模型能够记住文本。框架必须记住真理。

也就是说，**模型负责推理和生成，Harness 负责维护当前事实**。如果 Coding Agent 不能区分“对话里的旧内容”和“磁盘上的真实内容”，就很容易掉入旧读陷阱。

## 深度解读（1）

### 2026-09-18 00:53:16

#### Coding Agent 的真正记忆，不是对话，而是可验证的工作区状态

Coding Agent 最隐蔽的风险，不是生成了明显错误的代码，而是**依据一份曾经正确、现在已经过期的代码继续工作**：模型读过文件，用户随后修改了它，但旧内容仍留在对话上下文中。模型没有“忘记”，反而因为记得太清楚，更容易自信地覆盖用户的新修改。

文章把这种情况称为“陈旧读取陷阱”，核心判断很准确：**transcript 是事件历史，不是当前事实；模型可以记住历史，Harness 必须判断哪些历史仍然可信。**

##### 这本质上是并发控制，而非上下文管理

朴素 Agent 会把 `read_file` 的结果当作普通文本追加进上下文，默认“读过”就等于“知道”。但只要用户、IDE、格式化工具、Git 操作或另一个 Agent 能同时修改文件，这个默认就不再成立。

因此，一次文件读取不应只返回内容，还应形成一份带版本条件的契约：路径、读取范围、总行数、修改时间、大小、内容指纹，以及是否覆盖完整文件。提交编辑时，Harness 再验证目标文件是否仍与读取时一致。这与数据库的乐观并发控制相似：不是禁止外部修改，而是防止基于旧版本的写入悄悄成功。

文章给出的处理方式也体现了不错的产品分寸：内容未变时无需打扰；只有时间戳变化但指纹相同时可以静默刷新；内容被外部修改时展示变化片段；已删除、过大或无法安全比较时，再明确标记为 stale。**好的安全机制不是频繁报警，而是把冲突限制在真正需要用户或模型重新判断的地方。**

##### “读过局部”不能等价于“获得完整编辑权”

部分读取是文章里更值得保留的细节。模型只看了第 100—140 行，却准备重写整个文件，问题不仅是内容可能过期，也在于它从未掌握文件其余部分。局部信息足以回答局部问题，却不足以授权高影响写入。

文章建议：修改现有文件前，应有一份新鲜的完整文件基线，除非编辑工具具有更严格的精确上下文约定。这个方向成立，但“必须完整读取”不宜成为绝对规则。面对超大文件、生成文件或二进制资源，更有效的办法可能是让 patch 携带前置条件：目标片段必须仍然匹配、文件版本号必须一致、受影响符号及依赖范围必须经过验证。真正需要保证的不是“模型看过所有内容”，而是**写入范围与它所掌握、验证过的证据范围相匹配**。

此外，记录 SHA-256 等信息只能发现版本变化，不能彻底消除“检查后、写入前又被修改”的竞态。最终写操作仍需原子化的 compare-and-swap：验证指纹与提交 patch 应尽可能成为同一个不可分割动作。

##### 用户感知到的，是“它不会悄悄毁掉我的工作”

这套机制改变的不只是内部正确率。对用户而言，成熟 Agent 应表现为：不会覆盖刚刚手改的代码；发现冲突时能指出具体变化，而不是要求从头再来；自己完成写入后立即承认新版本；会话恢复后也知道哪些文件仍可信，而不只是恢复聊天记录。

这个原则还可迁移到代码之外。只要 Agent 操作的是会被外部持续改变的对象——文档、工单、CRM 客户记录、云资源配置、库存或日历——都不能把曾经读取的内容当成当前世界。每个高影响动作都应绑定**来源、版本、覆盖范围和失效条件**。

因此，这篇文章真正提出的不是一个文件缓存技巧，而是一条 Agent 产品边界：**长上下文解决“记不记得”，状态验证解决“还能不能信”。** 一个系统看起来多聪明，最终取决于它能否在行动前分清这两件事。
