Analyze voice call transcripts with 3 AI sub-agents running in parallel — each on a different LLM, all routed through one [TrueFoundry AI Gateway](https://www.truefoundry.com/ai-gateway). Action items are auto-created as [Linear](https://linear.app) issues via TrueFoundry MCP Gateway.

🚀 [Sign up for TrueFoundry](https://www.truefoundry.com/register) · 📖 [AI Gateway docs](https://docs.truefoundry.com/docs/ai-gateway) · 🤖 [DeepAgents](https://github.com/langchain-ai/deepagents)

---

#### Architecture

```
load_transcript()
                     │
            Planner Agent (Claude Sonnet 4.6)
                     │
        ┌────────────┼────────────┐
        │            │            │
   Sentiment    Action Items     Coach
  (Gemini 3    (Claude 4.6 +   (GPT-5
   Flash)       Linear MCP)     Mini)
        │            │            │
        └────────────┼────────────┘
                     │
              Combined Report
```

**3 LLMs, 1 API endpoint** — TFY AI Gateway handles model routing, auth, rate limiting, and observability.

---

#### Quick Start

```
git clone <repo-url> && cd tfy-voice-analyser-agent
uv sync
cp .env.example .env
```

Fill in your credentials in `.env`:

```
# TFY AI Gateway (required)
TFY_GATEWAY_URL=https://gateway.truefoundry.ai
TFY_API_KEY=tfy-...

# Linear project name (optional)
LINEAR_PROJECT=

# TFY MCP Gateway for Linear (optional — skips issue creation if not set)
TFY_MCP_GATEWAY_URL=https://gateway.truefoundry.ai/your-org/mcp/linear/server
TFY_MCP_GATEWAY_KEY=tfy-...
```

Start the server:

```
langgraph dev --port 8888
```

This gives you:

- **API**: [http://localhost:8888](http://localhost:8888)
- **Studio**: [https://smith.langchain.com/studio/?baseUrl=http://localhost:8888](https://smith.langchain.com/studio/?baseUrl=http://localhost:8888)
- **Docs**: [http://localhost:8888/docs](http://localhost:8888/docs)

---

1. Loads a sample support call transcript (\~8 min call)
2. Spawns **3 sub-agents in parallel**, each on a different LLM via Gateway:
   - **Sentiment Analyzer** (Gemini Flash) — tone, emotional arc, CSAT score
   - **Action Items Creator** (Claude Sonnet) — extracts items + creates Linear issues via MCP
   - **Call Coach** (GPT-5 Mini) — strengths, improvements, suggested phrases
3. Combines outputs into a single report
4. Returns the report with links to created Linear issues

---

#### Customizing Models

Model names in `agent.py` must match what's registered on your TFY AI Gateway. Update these to match your setup:

```
llm("flash/gemini-3-flash")                        # sentiment
llm("bedrock/global.anthropic.claude-sonnet-4-6")   # action items + planner
llm("openai-main/gpt-5-mini")                       # coaching
```

#### 用 3 个 AI 并行分析通话记录的开源方案

##### 一句话概括
这是一个用于“语音通话记录分析”的开源 Agent 项目：把一段客服/销售通话文本交给 3 个不同职责、不同模型的 AI 并行处理，最后自动汇总成一份报告，甚至还能把待办事项直接创建到 Linear。

##### 项目核心价值
这个项目的亮点不在“再做一个总结工具”，而在于把多模型协作真正跑通了：

- **一个入口接多个大模型**：通过 TrueFoundry AI Gateway，把不同模型统一接入、路由和管理。
- **多 Agent 并行工作**：不同 AI 各做自己擅长的事，提升分析质量和效率。
- **从分析走向执行**：不仅输出洞察，还能自动生成 Linear issue，把结论变成行动。

本质上，它展示的是一种更接近企业实际场景的 AI 工作流，而不是单点问答。

##### 系统是怎么工作的
整个流程可以理解为“一个总控 + 三个专家”：

###### 1. Planner Agent 负责统筹
主 Agent 先读取通话记录，再把任务分发给 3 个子 Agent，最后把结果整合成一份完整报告。

###### 2. 3 个子 Agent 分别做不同分析
- **情绪分析 Agent**：判断客户情绪、语气变化、情感走势，并给出类似 CSAT 的评分
- **行动项 Agent**：提取后续待办，并可通过 MCP 自动创建 Linear issue
- **通话教练 Agent**：分析通话表现，指出做得好的地方、可改进点以及更好的话术建议

###### 3. 最终输出统一报告
系统会把三部分结果汇总，形成一份更完整、可执行的通话分析报告。

##### 技术方案的意义
这个项目背后体现了几个关键产品/技术思路：

###### 多模型协作优于单模型包打天下
不同模型适合不同任务，比如有的更擅长总结，有的更适合推理，有的成本更低、响应更快。把它们拆开使用，比让一个模型硬做所有事更合理。

###### Gateway 是企业落地的关键中间层
TrueFoundry AI Gateway 提供统一 API 入口，负责：
- 模型路由
- 鉴权
- 限流
- 可观测性

这意味着团队不用直接和多个模型供应商深度耦合，更利于成本控制和后期扩展。

###### MCP 让 AI 真正连接业务系统
通过 MCP Gateway 接入 Linear，AI 不再只是“提建议”，而是可以直接在业务工具里执行动作。这是 AI 从“助手”走向“流程节点”的典型方向。

##### 项目适合什么场景
这个方案尤其适合以下场景：

- **客服质检**：分析客户情绪、服务质量和后续处理事项
- **销售复盘**：提炼客户需求、跟进动作和销售话术优化点
- **客户成功/实施团队**：从会议或通话中抽取风险、承诺和待办
- **内部协作提效**：把“听录音、写总结、建任务”自动化串起来

##### 上手方式
项目启动很直接：

1. 克隆仓库并安装依赖
2. 配置 `.env` 中的 Gateway 和可选的 Linear 凭证
3. 启动 `langgraph dev`
4. 用示例通话记录直接体验完整流程

它本质上是一个很轻量的 demo，代码量不大，适合快速理解和二次改造。

##### 需要注意的点
虽然项目思路清晰，但它更像一个展示范例，而不是开箱即用的生产系统：

- 依赖 TrueFoundry 的 AI Gateway 和 MCP Gateway 配置
- 模型名称需要和你自己网关里注册的名称一致
- 当前主要是针对“文本转写后的通话记录”，不是直接处理音频
- 自动创建 Linear issue 是可选能力，未配置时会跳过

##### 总结
这不是一个单纯的“通话总结 demo”，而是一个很典型的企业级 AI Agent 工作流样板：

- 前端输入是通话文本
- 中间是多 Agent、多模型并行协作
- 后端连接业务系统执行动作

它展示了一个很有现实意义的方向：**AI 不只是帮你理解信息，更开始帮你推动流程落地。**

#### 文章主旨

这是一个基于 `DeepAgents + TrueFoundry AI Gateway + Linear MCP` 的语音通话分析示例项目：它能把一段通话转录文本同时交给 3 个不同的 AI 子代理处理，最后汇总成一份分析报告，并自动把行动项创建为 Linear 任务。  
核心亮点是：**多个模型共用一个网关入口**，由 TrueFoundry 统一负责模型路由、鉴权、限流和可观测性。

##### 1. 项目是做什么的

- 这是一个用于**分析语音通话转录文本**的开源项目，仓库名为 `tfy-voice-analyser-agent`。
- 输入是一段通话 transcript，输出是一份**综合分析报告**，包含：
  - 情绪/语气分析
  - 待办事项提取
  - 通话教练建议
- 项目还支持把提取出的行动项**自动创建为 Linear issue**。

**通俗理解：**  
比如一通 8 分钟的客户支持电话，系统可以自动告诉你：
- 客户情绪是越来越差还是逐渐缓和；
- 客服答复里有哪些做得好、哪些需要改进；
- 后续需要谁跟进什么事情，并直接生成到 Linear 里。

---

##### 2. 整体架构怎么工作

项目采用了一个“**1 个规划代理 + 3 个并行子代理**”的结构：

- **Planner Agent**：使用 `Claude Sonnet 4.6`
  - 负责整体规划、任务分发和结果汇总。
- **Sentiment Agent**：使用 `Gemini 3 Flash`
  - 分析通话中的情绪、语气变化、情绪轨迹，以及 `CSAT`（客户满意度）评分。
- **Action Items Agent**：使用 `Claude 4.6 + Linear MCP`
  - 从通话内容里提取待办事项，并通过 MCP 把任务创建到 Linear。
- **Call Coach Agent**：使用 `GPT-5 Mini`
  - 给出通话表现评估，包括优点、改进建议和推荐话术。

最后，3 个子代理的结果会被合并成一个 `Combined Report`。

**关键点：**
- 3 个不同的 LLM 并行处理，提高分工效率。
- 所有模型都通过**一个 TFY AI Gateway API 入口**访问。
- 网关统一处理：
  - 模型路由
  - 鉴权
  - 限流
  - 可观测性

##### 3. 项目的核心价值

###### 3.1 多模型协同，但接入方式简单
- 虽然背后用了 3 个不同模型，但开发者只需要接入 **1 个网关端点**。
- 这降低了多模型系统的接入和维护复杂度。

###### 3.2 并行分析，结果更全面
- 不同子代理各自专注一个领域：
  - 情绪判断
  - 行动项提取
  - 沟通质量优化
- 这样比单模型一次性输出更容易做到**职责清晰、结果可控**。

###### 3.3 从“分析”直接走到“执行”
- 不只是生成报告，还能把行动项直接同步到 `Linear`。
- 这意味着它不只是“看懂通话”，还可以推动后续工作流落地。

**例子：**  
如果通话中客户提到“账单有误，需要退款确认”，系统可以：
- 在报告里标注这是关键跟进行动；
- 自动创建一个 Linear issue，交给相关团队处理。

## 产品-技术开发实现（1）

### 2026-03-27 06:59:17

这不是一个 “通话总结 Demo”，而是一个很典型的企业级 AI Agent 产品雏形：用多模型协作完成 “理解 -> 判断 -> 执行” 的闭环。它的价值不在模型多，而在产品链路设计是对的。

**产品解读**
- **核心用户**：客服主管、销售经理、客户成功、运营负责人，不是终端客服本人。
- **核心任务**：不是 “帮我写摘要”，而是 “帮我判断问题、提炼风险、推动后续动作”。
- **产品闭环**：输入通话记录，输出洞察，同时把 action item 直接写进`Linear`，这才是真正可落地的工作流。
- **关键产品设计点**：把结果拆成 3 类固定产物最合理：`情绪判断`、`行动项`、`沟通改进建议`。这对应了管理者最关心的 3 个维度：客户状态、业务推进、团队能力。
- **为什么不是单模型一把梭**：因为管理型场景要求 “结构化、可审阅、可执行”，而不是只要一段自然语言总结。

**技术设计解读**
- **架构本质**：`Planner + 多个 Specialist Agent + Tool Executor`，这是当前企业 AI 最稳的模式之一。
- **TrueFoundry AI Gateway`的价值**：不是 “多一个中间层”，而是把模型调用从业务代码里抽离出来，统一做路由、鉴权、限流、观测、成本控制。
- **MCP 的价值**：让 LLM 不只生成文本，而是能安全调用业务工具；这里 Linear 只是一个例子，本质是把 AI 接进企业系统。
- **并行子 Agent 的意义**：情绪、行动项、话术辅导本来就是低耦合任务，天然适合并发，延迟和质量都更优。
- **模型选型逻辑是合理的**：
  - `Gemini Flash`做情绪 / 轻分析，快且便宜
  - `Claude Sonnet`做行动项抽取和规划，稳定性强
  - `GPT-5 Mini`做 coaching，语言生成更自然
- **这其实是一个 “模型能力分层” 设计**，而不是简单炫技。

**设计实现上最值得借鉴的点**
- **职责隔离**：每个 agent 只做一件事，prompt 更稳定，输出更容易约束。
- **统一编排**：由 planner 汇总，不让 3 个 agent 彼此乱对话，降低系统复杂度。
- **工具调用后置**：先判断 action item，再创建 Linear issue，避免模型一上来就乱写工单。
- **模型名通过网关配置**：`agent.py`里的模型标识和网关注册名绑定，这是一种很实用的生产模式。
- **最小可运行代码量小**：`agent.py`约 130 行，说明设计清晰，没有过早工程化。

**最佳实践例子 1：客服质检产品**
- **输入**：客服录音转写文本 + 通话元数据（坐席、客户、工单号、时长）
- **Agent 分工**：
  - `Sentiment Agent`：识别客户是否从抱怨转为接受，输出情绪曲线和风险等级
  - `Action Agent`：提取退款、补发、升级、回访等事项
  - `Coach Agent`：识别客服是否打断客户、是否确认诉求、是否给出明确承诺
- **输出结构**：
  - `risk_level`: high/medium/low
  - `customer_intent`: 退款 / 投诉 / 咨询
  - `action_items`: 可执行列表
  - `coach_feedback`: 3 条以内
- **落地动作**：
  - 高风险通话自动打标签
  - 承诺类事项自动进 Linear 或 CRM
  - 低分通话进入主管复检队列
- **产品收益**：从 “抽样听录音” 变成 “全量自动质检 + 自动派单”。

**最佳实践例子 2：销售复盘产品**
- **不要只做摘要**，要抽取：
  - 客户预算是否明确
  - 决策人是否到场
  - 时间表是否存在
  - 下一步是否有 owner
- **建议的 agent 切法**：
  - `Deal Qualification Agent`
  - `Next-Step Agent`
  - `Sales Coaching Agent`
- **自动化动作**：
  - 若发现 “无下一步会议”，自动在 Linear 创建 follow-up
  - 若识别到 “提到竞争对手”，自动打 CRM 标签
  - 若预算模糊，提示销售补问标准问题
- **这类设计比简单会议纪要更有产品价值**，因为它直接服务 pipeline 管理。

**开发实现最佳实践**
- **1. 强制结构化输出**
  - 不要让 agent 直接返回大段文本。
  - 用固定 schema，比如：
```json
{
  "sentiment_score": 6.5,
  "risk_flags": ["customer_frustration", "billing_confusion"],
  "action_items": [
    {"title": "Confirm refund eligibility", "owner": "support", "priority": "high"}
  ],
  "coach_tips": ["Acknowledge frustration earlier"]
}
```
- **原因**：后续要入库、排序、派单、画报表，结构化比文案更重要。

- **2. Tool call 要有阈值控制**
  - 不是提到一件事就创建 issue。
  - 例如只创建：
    - 高优先级事项
    - 有明确 owner 的事项
    - 有截止预期的事项
  - 当前仓库 “最多创建 top 2 action items” 就是很好的产品约束。

- **3. 给每个 agent 单独定义成功标准**
  - 情绪 agent：关注一致性和风险召回
  - 行动项 agent：关注可执行性和误报率
  - coaching agent：关注建议是否具体、可复用
- **不要用一个 “总体感觉不错” 来评估整个系统。**

- **4. 建可观测性而不是只看日志**
  - 记录：
    - 每个 agent 的耗时
    - 每个模型 token 消耗
    - issue 创建成功率
    - action item 命中率
    - 人工修改率
- **这是 AI 产品能否进入生产环境的分水岭。**

- **5. 人工审核要可配置**
  - 最佳实践不是一上来全自动。
  - 先做：
    - `draft mode`：仅生成建议，不真正创建 issue
    - `review mode`：人工确认后再写入 Linear
    - `auto mode`：成熟后开放自动执行
- **企业客户最在意的是可控性，不是自动化程度。**

**容易踩坑的地方**
- **把 transcript 当事实**：ASR 本身会有错字、漏字，尤其人名、金额、日期。
- **情绪分析过拟合措辞**：客户说得激烈不一定代表高风险，要结合上下文和结果。
- **行动项过度生成**：LLM 很容易把 “讨论过” 错当成 “要执行”。
- **跨模型输出风格不一致**：需要统一 schema 和 planner 的汇总规范。
- **工具调用权限过大**：MCP 接企业系统时，一定做最小权限控制和审计。

**如果我要把这个项目做成正式产品，我会这样升级**
- **输入层**：接入真实音频转写、说话人分离、客户元数据
- **分析层**：把 agent 输出全部 schema 化，并做置信度评分
- **执行层**：Linear 只是起点，继续接 CRM、工单系统、Slack
- **反馈层**：加入 “人工修订回流”，让系统学习哪些 action item 是真的有效
- **管理层**：做团队面板，看 CSAT、情绪波动、话术问题、任务闭环率

**一句话判断**
- 从产品上看，它抓住了企业 AI 最值钱的一点：`把洞察变成动作`。
- 从技术上看，它采用了当前最稳的路线：`多 Agent 分工 + 网关统一接模 + MCP 安全落地`。
- 最佳实践不是 “再加更多模型”，而是把`结构化输出、执行阈值、人工审核、效果观测`这四件事做扎实。

如果你愿意，我可以进一步给你一版：
1. 这个项目的 “生产级架构改造方案”
2. 面向客服 / 销售场景的`agent schema + prompt`最佳实践模板
3. 一份适合创业公司落地的 MVP 产品设计稿

## 产品-最佳实践（1）

### 2026-03-27 07:04:12

#### 基于`truefoundry/tfy-voice-analyser-agent`的最佳实践示例

下面我用一个具体场景，基于你提供的这个项目，给出一套可直接落地的最佳实践。

---

##### 一、项目理解

这个项目的核心目标是：

> 对一段客服 / 销售电话转录文本进行自动分析，并通过 3 个并行子 Agent 输出统一报告，同时把关键行动项自动同步到 Linear。

它的典型架构是：

- `Planner Agent`负责规划与汇总
- `Sentiment Agent`分析客户情绪、满意度趋势
- `Action Items Agent`提取后续任务，并通过 MCP 写入 Linear
- `Coach Agent`输出通话改进建议
- 所有模型调用统一经过`TrueFoundry AI Gateway`
- 工具调用（Linear）统一经过`TrueFoundry MCP Gateway`

---

##### 二、具体实例

假设有这样一段客户支持电话：

###### 场景
某 SaaS 公司客服与客户沟通，客户反馈：

- 最近两周系统频繁超时
- 数据导出功能在高峰期失败
- 客户内部负责人要求在本周五前看到修复计划
- 客户情绪前半段焦躁，后半段因客服解释清楚而稍有缓和

###### 期望结果
系统应自动输出：

1. 情绪分析  
2. 待办事项列表  
3. 客服复盘建议  
4. 自动创建最多 2 条最关键的 Linear issue  

---

##### 三、推荐的输出示例

下面是一个 “理想输出” 的简化示例：

```markdown
# Call Analysis Report

## 1. Sentiment Summary
- Customer started frustrated due to repeated timeout issues.
- Emotional tone improved after clear acknowledgement and timeline discussion.
- Estimated CSAT: 5.8/10
- Risk level: High

## 2. Key Action Items
1. Investigate timeout spikes during peak traffic and provide RCA by Friday.
2. Fix export job reliability for large datasets and share ETA with customer.

## 3. Coaching Notes
- What went well:
  - Agent acknowledged pain points clearly.
  - Agent restated the issue and aligned on next steps.
- What to improve:
  - Provide clearer timelines earlier in the call.
  - Confirm business impact sooner.
- Suggested phrasing:
  - "I understand this is affecting your team’s deadlines, and I want to make sure we leave with a concrete recovery plan."

## 4. Linear Issues Created
- ENG-142: Investigate timeout spikes during peak traffic
- ENG-143: Improve export reliability for large datasets
```

---

##### 四、基于该实例的最佳实践

##### 1. 先定义 “每个 Agent 的单一职责”

这个项目已经采用了多 Agent 并行模式，这是正确方向。最佳实践是进一步明确边界，避免职责重叠。

###### 推荐职责划分

- `Sentiment Agent`
  - 只负责情绪、语气、满意度、风险等级
  - 不负责提任务，不给解决方案
- `Action Items Agent`
  - 只提炼 “可执行、可跟踪” 的行动项
  - 必须输出 owner、截止时间、优先级建议
- `Coach Agent`
  - 只做通话质量复盘
  - 不重复 sentiment 和 issue extraction

###### 为什么这是最佳实践
如果职责不清，常见问题是：

- 多个 Agent 同时输出 action items，造成重复
- 情绪分析和教练建议互相污染
- Planner 汇总时难以去重

###### 建议格式
给每个 Agent 固定 schema，例如：

```json
{
  "summary": "",
  "confidence": 0.0,
  "items": []
}
```

这样 Planner 更容易做结构化合并。

---

##### 2. Action Items 必须 “可执行”，否则不要创建 Linear issue

这是这类系统最重要的实践之一。

###### 错误示例
```text
- Improve customer experience
- Look into system issue
```

这些内容太泛，直接创建 Linear issue 会污染工程团队 backlog。

###### 正确示例
```text
- Investigate API timeout spikes between 2pm-5pm UTC and produce RCA by Friday
- Fix export job failure for datasets larger than 500MB
```

###### 建议规则
在`Action Items Agent`中加入 issue 创建门槛：

- 必须包含明确对象
- 必须包含动作动词
- 最好包含时间要求或业务影响
- 相似任务要合并
- 低置信度任务只出现在报告中，不自动建单

###### 实践建议
你提供的仓库里已经有：

> `Limit Linear issue creation to top 2 action items`

这是很好的约束，建议继续增强为：

- 只创建`impact highest + confidence highest`的前 2 项
- 其余项放在报告中待人工确认

这能显著降低误建单风险。

---

##### 3. Planner 负责 “去重、排序、冲突解决”，而不仅是拼接结果

很多多 Agent 系统里，Planner 只是简单拼接输出，但最佳实践是让它承担 “编辑器” 的角色。

###### Planner 应该做的事

- 合并重复结论
- 解决冲突判断
- 按优先级重排
- 将技术分析翻译成业务可读语言
- 给出最终统一结构

###### 在这个实例中
假设：

- `Sentiment Agent`认为风险是`High`
- `Coach Agent`认为客户在结尾阶段已经恢复信心
- `Action Items Agent`提出 4 个任务

Planner 不应直接原样输出，而应整理为：

- 总体情绪：由负转稳，但风险仍高
- 当前业务风险：仍需在周五前交付修复计划
- 自动建单：只保留最关键的 2 个
- 剩余建议：列为 follow-up notes

###### 最佳实践
Planner 的 prompt 里要明确写：

```text
You are not a concatenator.
You are the final decision-maker for deduplication, prioritization, and conflict resolution.
```

---

##### 4. 模型选择要按任务特性分配，而不是平均分配

这个项目把不同任务路由到不同模型，这是多模型架构的核心优势。最佳实践是按任务特征选模型。

###### 推荐映射逻辑

- `Gemini Flash`：快、便宜，适合情绪分类、摘要、趋势判断
- `Claude Sonnet`：更适合复杂推理、任务提炼、结构化计划
- `GPT-5 Mini`：适合自然表达、复盘建议、沟通话术生成

###### 为什么这很重要
如果把最复杂的`Action Items + Linear`任务交给轻量模型，常见问题会是：

- 任务表达不精确
- 结构化字段缺失
- issue title 与 description 质量差

###### 最佳实践
不要把模型名硬编码为 “固定真理”，而应该：

- 在`.env`中配置模型别名
- 在`agent.py`中只使用逻辑名称
- 通过 TFY Gateway 做实际路由

例如：

```env
MODEL_SENTIMENT=flash/gemini-3-flash
MODEL_PLANNER=bedrock/global.anthropic.claude-sonnet-4-6
MODEL_COACH=openai-main/gpt-5-mini
```

这样更利于不同环境切换。

---

##### 5. 对外部工具调用要 “显式降级”

这个项目里，Linear issue 创建是可选能力，这是非常好的设计。最佳实践是继续强化 “失败不影响主流程”。

###### 推荐原则

- 没有配置 MCP 时：跳过 issue 创建，但照常生成报告
- MCP 调用失败时：报告中写明失败原因，不中断分析
- 创建成功时：返回 issue 链接
- 创建失败时：返回 “建议创建的 issue 草稿”

###### 具体例子
即使 Linear API 超时，仍然应该输出：

```markdown
## Suggested Linear Issues
1. Investigate timeout spikes during peak traffic
2. Improve export reliability for large datasets

> Linear issue creation failed due to MCP timeout. Please retry manually.
```

###### 价值
这会让系统从 “演示型 Demo” 升级为 “生产可用工具”。

---

##### 6. Prompt 设计要强调 “基于转录证据”

在通话分析场景里，最怕的是模型幻觉。

###### 最佳实践
要求每个 Agent：

- 只能基于 transcript 内容推断
- 不要补充 transcript 没说过的事实
- 输出关键结论时引用依据片段
- 不确定时明确写`uncertain`

###### 示例约束
```text
Only use evidence explicitly present in the transcript.
Do not infer technical root cause unless stated or strongly supported.
For each major conclusion, include a short evidence note.
```

###### 在本例中
错误输出：

- “数据库索引缺失导致超时”

如果 transcript 没提数据库，这就是幻觉。

正确输出：

- “Customer reported repeated timeout issues during peak traffic. Root cause not confirmed.”

---

##### 7. 统一结构化输出，便于后续接入 BI、CRM 或 QA 系统

即使最终给人看的是 Markdown 报告，内部也应该优先采用结构化 JSON。

###### 推荐内部数据结构

```json
{
  "call_id": "support-call-2025-001",
  "sentiment": {
    "overall": "negative_to_neutral",
    "csat_estimate": 5.8,
    "risk_level": "high"
  },
  "action_items": [
    {
      "title": "Investigate timeout spikes during peak traffic",
      "priority": "high",
      "should_create_linear": true
    }
  ],
  "coach_notes": {
    "strengths": [],
    "improvements": [],
    "suggested_phrases": []
  }
}
```

###### 为什么这是最佳实践
这样可以：

- 更方便前端展示
- 更容易做自动测试
- 更容易审计模型输出质量
- 后续接 CRM、数据仓库、告警系统时成本更低

Markdown 适合展示，JSON 适合系统集成。二者应同时存在。

---

##### 8. 对 “自动创建工单” 增加人工审核阈值

如果这个系统进入生产，最佳实践通常不是 “所有 action item 自动建单”，而是 “高置信度自动 + 其余待确认”。

###### 推荐策略

- `P0 / 高业务影响 / 高置信度`：自动建单
- `中等置信度`：仅生成 issue draft
- `低置信度`：只出现在报告中

###### 适合本项目的判断字段

- 业务影响是否明确
- 是否有明确 owner/team
- 是否有截止时间
- 是否重复已有问题
- 模型置信度是否足够高

###### 示例
```text
Auto-create only when:
- confidence >= 0.85
- impact in [high, critical]
- task is specific and non-duplicate
```

---

##### 9. 加入可观测性指标，而不只看最终报告

TrueFoundry AI Gateway 的优势之一就是可观测性。最佳实践是定义你真正关心的指标。

###### 建议追踪的核心指标

- 每通电话总耗时
- 每个子 Agent 耗时
- 每个模型 token 消耗
- 自动建单成功率
- action item 准确率
- 情绪判断与人工标注的一致率

###### 在这个项目里最有价值的 3 个指标

1. `report_generation_latency`
2. `linear_issue_creation_success_rate`
3. `action_item_acceptance_rate`

其中第三个尤其重要：

> 工程团队真正采纳了多少自动生成的 issue？

这比 “生成了多少 issue” 更有意义。

---

##### 10. 必须为 “样例 transcript” 之外的真实输入做鲁棒性设计

Demo 常常只覆盖理想输入，但真实世界的 transcript 会更脏。

###### 需要额外处理的情况

- 说话人未区分
- ASR 错别字很多
- 中英文混杂
- 通话中断
- transcript 太短，无法判断
- transcript 太长，超出上下文窗口

###### 最佳实践

- 预处理 transcript
- 对超长文本做分段总结再汇总
- 对缺失 speaker label 的文本做基础归类
- 对空输入返回明确错误信息

###### 推荐行为
如果 transcript 不足 1 分钟或信息极少，应输出：

```markdown
Insufficient transcript detail to extract reliable sentiment and action items.
```

而不是强行生成一堆看似合理的分析。

---

##### 五、一个更完整的落地实践方案

如果要把这个项目从 Demo 升级到团队可用，我建议按下面方式演进：

###### 第一阶段：保证输出稳定
- 固定每个 Agent 的输出 schema
- Planner 做去重与优先级整理
- 限制自动创建 issue 数量
- MCP 失败时优雅降级

###### 第二阶段：保证结果可信
- 所有结论附 transcript evidence
- 引入置信度字段
- 增加 hallucination 防护 prompt
- 对 issue 创建加入阈值控制

###### 第三阶段：保证可运营
- 记录延迟、成本、建单成功率
- 做模型路由配置化
- 加入测试样本集
- 统计人工采纳率与误报率

---

##### 六、适用于该项目的一份 “最佳实践清单”

```markdown
- 为每个子 Agent 定义清晰单一职责
- 使用结构化输出，不要只返回自由文本
- Planner 负责去重、排序、冲突解决，而不是简单拼接
- 自动创建 Linear issue 前先做 “可执行性” 校验
- 只自动创建高置信度、高影响的前 2 个任务
- 所有结论尽量附 transcript 证据
- MCP / 外部工具失败时允许主流程继续
- 模型选择按任务特征分配，不要平均分配
- 模型名与路由配置放到环境变量中管理
- 追踪延迟、成本、建单成功率和人工采纳率
- 针对脏 transcript、超长 transcript、空 transcript 做容错
- 先输出 JSON，再渲染 Markdown 报告
```

---

##### 七、结论

用一句话概括：
