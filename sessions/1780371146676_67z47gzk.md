**XDash**

复盘几个月来的 AI 使用，犯了个错：

过早地将模型的代码能力，固化成了一个个 python 脚本来跑，认为这样更省钱、边界更可控（而不是用 LLM 能力）。

实际上，固化的脚本在处理（脚本创建之初未预判到的）边界条件之外的意外问题时，经常失手。

\- 比如基于系统日志的健康度扫描，用脚本报错就拼不过 LLM 分析再给出行动建议的系统；  
\- 比如各种垃圾残片的整理系统，用脚本就傻傻识别不出「这个路径已经移动」、「文件已不复存在」、「出现特殊字符导致无法处理」、「跟当前其他进程冲突」的问题；  
\- 比如在解析外部 RSS 的文本时，用脚本就经常因为反斜杠、特殊英文字符、json 格式注入等而失败。

考虑到现阶段 token 足够便宜，我的 Harness Engineering 也做得足够强壮、可逆，因此应该是：

尽量让更多新建立的系统，跑在 LLM 能力之上，去撞击边界，去自我修复，去经历爆发再聚爆的过程，最后坍缩凝结成一颗颗稳定、强大的金丹，增幅人的能力。

只要 token 还足够便宜，就没必要太早固化成脚本，导致人整天忙于修脚本。

## 解读（1）

### 2026-06-02 03:29:59

##### 一、总结

作者反思：**太早把 AI 的能力写死成 Python 脚本，是个错误。**

原因是：

- 脚本便宜、可控，但很“死”
- 一遇到没预料到的边界情况，就容易崩
- LLM 虽然消耗 token，但更擅长：
  - 理解异常
  - 分析上下文
  - 给出修复建议
  - 自我调整流程

结论：  
**在 token 还便宜、系统可回滚的情况下，不要太早把流程固化成脚本。先让 LLM 多跑、多试、多撞边界，成熟后再沉淀成稳定工具。**

---

##### 二、解读

这篇内容讲的是一个很常见的 AI 使用误区：

> 以为“写成脚本”就是自动化，结果变成了“维护脚本”。

比如：

###### 1. 日志分析

脚本只能按规则判断：

```text
出现 A 报错 → 提醒
出现 B 报错 → 忽略
```

但真实情况很复杂。  
LLM 可以读日志、看上下文、判断严重性，并给行动建议。

---

###### 2. 文件整理

脚本遇到这些情况容易挂：

- 文件被移动了
- 路径不存在了
- 文件名有特殊字符
- 被其他进程占用

LLM 更像一个“会思考的助理”，能判断问题并尝试换办法。

---

###### 3. RSS / 文本解析

脚本很怕格式异常：

- 反斜杠
- 特殊字符
- JSON 注入
- 编码问题

而 LLM 对“脏数据”的容错性更强。

---

##### 三、核心观点

作者真正想说的是：

> 不要一开始就追求确定性。  
> 先用 LLM 探索复杂世界，再把稳定模式沉淀成脚本。

可以理解为：

- **LLM 适合探索期**
- **脚本适合成熟期**

早期流程还不稳定时，硬写脚本，就像给还没定型的业务套钢筋，后面改起来很痛苦。

---

##### 四、我的意见

我认同，但要加一个边界：

###### 适合先用 LLM 的场景

- 日志分析
- 文本处理
- 异常排查
- 文件整理
- 需求经常变化的流程
- 边界条件很多的任务

###### 适合直接写脚本的场景

- 规则稳定
- 输入格式固定
- 结果要求确定
- 成本敏感
- 安全要求高

---

##### 五、最佳做法

我觉得更好的方式是：

> **LLM 负责判断，脚本负责执行。**

例如：

```text
LLM 分析问题 → 生成操作建议 → 脚本执行可控动作 → 记录结果 → LLM 再复盘
```

这样既有 LLM 的灵活性，也有脚本的稳定性。

---

##### 六、一句话结论

**别急着把 AI 变成脚本。先让 AI 跑通复杂场景，再把真正稳定的部分固化下来。**

## 结构化（1）

### 2026-06-02 03:48:00

##### 主旨概括

作者复盘近几个月的 AI 使用后认为：**过早把 LLM 的能力固化成 Python 脚本，是一个错误**。在 token 成本较低、工程框架足够稳定的情况下，应更多让系统直接运行在 LLM 能力之上，以便处理复杂边界、自我修复，而不是让人反复维护脚本。

---

##### 1. 原先的做法：把 AI 能力固化成脚本

作者一开始认为：

- 把模型生成的能力写成一个个 Python 脚本来运行；
- 这样看起来更省钱；
- 系统边界更清晰、更可控；
- 不必每次都调用 LLM。

但复盘后发现，这种做法有明显问题：**脚本只能处理设计时预想到的情况，一旦遇到未预判的边界条件，就容易失败。**

---

##### 2. 脚本在复杂场景下经常“失手”

作者举了几个具体例子，说明脚本面对现实环境中的意外情况时不够灵活。

###### 例子一：系统日志健康度扫描

- 用脚本扫描系统日志时，只能按既定规则判断报错；
- 如果遇到复杂异常，脚本往往只能报错或漏判；
- 相比之下，LLM 可以结合上下文分析日志，并给出行动建议。

作者认为：  
**基于 LLM 的分析系统，比单纯脚本报错更有价值。**

---

###### 例子二：垃圾文件和残片整理

在整理各种垃圾残片时，脚本容易识别不出一些实际问题，例如：

- 文件路径已经移动；
- 文件已经不存在；
- 路径或文件名里有特殊字符；
- 文件被其他进程占用或冲突。

这些情况对脚本来说可能只是异常报错，但对 LLM 来说，可以根据上下文判断原因，并提出处理方案。

---

###### 例子三：解析外部 RSS 文本

在处理外部 RSS 内容时，脚本经常因为文本格式复杂而失败，比如：

- 反斜杠；
- 特殊英文字符；
- JSON 格式注入；
- 非标准文本格式。

作者认为，这类外部输入不可控，脚本很容易被各种边界情况击穿。

---

##### 3. 作者的新判断：应更多依赖 LLM，而不是过早脚本化

作者认为，当前阶段有两个前提：

- **token 足够便宜**；
- 自己的 **Harness Engineering**，也就是外层工程框架，已经足够强壮、可逆。

因此，更好的做法是：

- 尽量让新系统跑在 LLM 能力之上；
- 让 LLM 去面对真实边界；
- 让系统在使用中自我修复；
- 经历“爆发—收敛”的过程；
- 最后再沉淀成稳定、强大的能力模块。

作者用“金丹”作比喻：  
这些经过反复碰撞和修复后的系统，会最终凝结成一个个稳定、强大的工具，进一步放大人的能力。

---

##### 4. 核心结论：不要太早把 AI 能力写死成脚本

作者的结论是：

> 只要 token 还足够便宜，就没必要太早把能力固化成脚本，否则人会整天忙着修脚本。

也就是说：

- 脚本适合稳定、确定、边界清晰的任务；
- LLM 更适合变化多、异常多、上下文复杂的任务；
- 在系统尚未成熟前，应先让 LLM 承担探索和修复；
- 等模式稳定后，再考虑沉淀成脚本或工具。

---

##### 5. 热门回复中的补充观点

###### 观点一：脚本也可以继续由 AI 修

有回复者认为：

- 脚本出错后，也可以让 AI 第一时间修复；
- 可以接日志库、定时扫描、文件监听；
- 基于反馈不断升级脚本；
- 不一定要完全回到“纯靠大模型”的方式。

这代表一种折中思路：  
**脚本不是不能用，但要和 AI 修复机制结合起来。**

---

###### 观点二：把 Python 脚本融入 Skill

另一位回复者建议：

- 可以把 Python 脚本融入到 skill 中；
- 通过不断修正和优化 skill；
- 让脚本逐渐变得更好用。

这也说明，脚本和 LLM 不一定是二选一，可以组合使用。

---

###### 观点三：这可能是 IT 从业者的路径依赖

还有回复者指出：

- 作者过去写了很多脚本；
- 这可能是 IT 背景带来的路径依赖；
- 工程师习惯用脚本化、自动化的方式解决问题。

但在 LLM 时代，某些问题也许不该过早工程化，而应先交给模型处理复杂性。

---

##### 总结

这篇文章的核心反思是：**不要过早把 LLM 的灵活能力压缩成固定脚本**。在任务边界尚不稳定、异常情况很多时，LLM 比脚本更适合承担分析、判断和自我修复；等系统经过真实场景验证后，再沉淀成稳定工具，可能是更合理的 AI 工程路径。

## 综合-启发一下（1）

### 2026-06-02 04:09:06

#### XDash 观点精炼：不要过早把 AI 能力固化成脚本

##### 1. 启发

这条内容的核心启发是：

> 在 AI 能力快速下降成本、上升稳定性的阶段，过早把 LLM 的灵活能力固化成传统脚本，可能是一种“早熟优化”。

过去的软件工程习惯是：  
先把流程抽象清楚，再写成确定性脚本，以获得低成本、可控性和可复用性。

但在当前 AI 产品开发中，很多任务并不是稳定、封闭、边界清晰的，而是充满：

- 异常输入
- 环境漂移
- 格式污染
- 状态变化
- 外部系统不确定性
- 人类语言中的模糊性
- 未预判的边界条件

这类任务如果过早写成脚本，脚本会变得非常脆弱。你以为自己节省了 token 成本，实际上可能把成本转移成了：

- 维护脚本的时间成本
- 处理边界异常的认知成本
- 排查报错的上下文切换成本
- 系统失效后的恢复成本

更值得重视的是：  
LLM 不只是“写脚本的工具”，它本身也可以成为运行时的判断、解释、修复和调度层。

---

##### 2. 高价值信息深挖

###### 2.1 真正的问题不是“脚本 vs LLM”，而是“确定性系统 vs 弹性系统”

脚本适合处理稳定、规则明确、输入可控的任务。  
LLM 适合处理模糊、多变、上下文复杂、边界难穷尽的任务。

例如：

| 场景 | 脚本的问题 | LLM 的优势 |
|---|---|---|
| 系统日志健康扫描 | 只能匹配预设规则，遇到新型异常容易漏掉 | 能理解日志语义，归纳异常模式，给出行动建议 |
| 文件残片整理 | 路径移动、文件缺失、特殊字符、进程占用都会造成失败 | 能根据当前状态重新判断，生成替代方案 |
| RSS / 外部文本解析 | 反斜杠、特殊字符、JSON 注入等导致解析失败 | 能容错、修复格式、推断真实内容结构 |
| 自动化运维 | 对环境变化高度敏感 | 可结合日志、状态和目标做动态调整 |

所以，这里的关键不是抛弃脚本，而是避免在系统还处于探索期、边界还没充分暴露时，过早进入“脚本化”。

---

###### 2.2 “先 LLM 后脚本”可能成为新的产品开发范式

传统路径：

```text
需求 → 规则抽象 → 写脚本 → 运行 → 维护异常
```

AI 原生路径可能是：

```text
需求 → LLM Agent 处理 → 撞击真实边界 → 记录失败样本 → 收敛稳定模式 → 再固化为脚本 / skill / workflow
```

也就是说：

> LLM 可以先作为“探索型运行时”，等系统经历足够多真实异常后，再把稳定部分沉淀为确定性组件。

这有点像产品开发里的：

- 先做 concierge MVP
- 再做半自动化
- 最后做全自动化

在 AI 系统里则是：

- 先让 LLM 直接处理
- 再给 LLM 加工具、日志、回滚、验证
- 最后把高频、稳定、确定的部分沉淀为脚本或服务

---

###### 2.3 Token 成本便宜后，软件系统的边界发生了变化

过去写脚本的动机通常是：

- 更便宜
- 更快
- 更稳定
- 更可控

但当 token 变便宜之后，经济账变化了。

如果一个脚本每周要人工维护 2 小时，即使运行成本接近 0，它也可能比每天消耗一些 token 更贵。

新的成本比较不应该是：

```text
脚本运行成本 vs LLM 调用成本
```

而应该是：

```text
脚本运行成本 + 维护成本 + 异常处理成本 + 机会成本
vs
LLM 调用成本 + Harness 成本 + 监控成本
```

当你的 Harness Engineering 足够强，也就是有：

- 日志记录
- 权限控制
- dry-run
- 回滚能力
- 人工确认
- 失败重试
- 输出校验
- 沙盒环境
- 状态追踪

那么让 LLM 参与更多运行时决策就不再是“放飞自我”，而是一种可控的弹性系统设计。

---

##### 3. 可迁移清单

###### 3.1 判断一个任务是否应该先用 LLM，而不是脚本

如果任务具备以下特征，优先考虑 LLM 运行时处理：

- 输入来源不稳定
- 格式经常变化
- 边界条件难以穷尽
- 异常状态需要解释
- 输出需要人类语义判断
- 任务中有大量“看情况处理”
- 外部环境经常变化
- 错误修复需要综合上下文
- 规则还没有稳定下来
- 你还不知道真正的失败模式有哪些

典型场景：

- 日志分析
- 数据清洗
- 文件整理
- 邮件 / RSS / 网页解析
- 客服工单分类
- 自动化运维建议
- 代码库巡检
- 个人知识库整理
- 长文本摘要与结构化
- 非标准数据的归档和迁移

---

###### 3.2 判断一个任务是否适合固化成脚本

如果任务具备以下特征，可以考虑脚本化：

- 输入稳定
- 规则明确
- 失败模式已知
- 输出格式确定
- 频率很高
- 对速度或成本极度敏感
- 不需要语义理解
- 不需要动态判断
- 错误后果可控
- 已经被 LLM 跑过多轮并沉淀出稳定模式

典型场景：

- 文件批量重命名
- 固定格式数据转换
- 定时备份
- API 数据同步
- 数据库字段迁移
- 明确规则的 ETL
- 重复性报表生成
- 已稳定的校验逻辑

---

###### 3.3 一个更好的系统设计顺序

可以采用这样的路径：

```text
1. LLM 原型处理
2. 记录所有输入、输出、失败、人工修正
3. 给 LLM 加工具调用能力
4. 增加日志、回滚、权限、验证
5. 提炼高频稳定模式
6. 将稳定部分封装成脚本 / skill / API
7. 继续让 LLM 处理长尾异常
```

最终形成：

```text
LLM 负责判断、解释、修复、调度
脚本负责高频、确定、稳定、低级操作
Harness 负责安全、可逆、监控、约束
```

---

###### 3.4 实用架构模板

###### 模板一：LLM + 工具执行

```text
用户目标
  ↓
LLM 理解任务
  ↓
选择工具 / 脚本
  ↓
执行前生成计划
  ↓
dry-run 检查
  ↓
执行
  ↓
结果验证
  ↓
失败时自我修复或请求人工确认
```

适合：

- 文件整理
- 知识库维护
- 日志诊断
- 个人自动化系统

---

###### 模板二：LLM 作为异常处理层

```text
传统脚本执行
  ↓
遇到异常
  ↓
把日志、上下文、输入样本交给 LLM
  ↓
LLM 判断原因
  ↓
生成修复方案
  ↓
人工确认或自动重试
```

适合已经有脚本系统的人。  
这不是推翻脚本，而是给脚本加一个“智能恢复层”。

---

###### 模板三：LLM 作为规则发现器

```text
真实任务样本
  ↓
LLM 处理
  ↓
记录处理过程
  ↓
归纳稳定规则
  ↓
人类审查
  ↓
沉淀为脚本 / skill / workflow
```

适合：

- 数据清洗
- 内容审核
- 销售线索分类
- 用户反馈归因
- 运营流程自动化

---

##### 4. 反方与张力

###### 4.1 反方观点：脚本不是问题，问题是反馈闭环没做好

热门回复里有人指出：  
如果脚本是 AI 写的，出错后也可以让 AI 修。接日志库、文件监听、定时扫描，根据反馈持续升级脚本即可。

这个反方观点很重要。

因为真正的问题可能不是“脚本化”本身，而是：

- 脚本没有持续学习机制
- 脚本没有日志和异常反馈
- 脚本没有自动修复入口
- 脚本和 LLM 没有形成闭环
- 人把脚本当成最终系统，而不是可进化组件

所以更准确的说法不是：

> 不要写脚本。

而是：

> 不要在边界还没暴露之前，把脚本当成终局。

---

###### 4.2 脚本的优势依然不可替代

LLM 有弹性，但脚本有确定性。

脚本在这些方面依然有优势：

- 运行快
- 成本低
- 可测试
- 可复现
- 可审计
- 行为稳定
- 依赖少
- 权限边界清晰
- 适合生产系统
- 适合严格合规场景

在金融、医疗、安全、账务、权限管理等场景里，不能简单让 LLM 自由决策。

因此，LLM 原生系统的设计关键是：

```text
让 LLM 处理不确定性
让脚本处理确定性
让人类处理价值判断和高风险确认
```

---

###### 4.3 最大张力：灵活性 vs 可控性

LLM 的优势是灵活，但风险也是灵活。

需要防范：

- 幻觉
- 误操作
- 权限过大
- 输出不稳定
- 无法复现
- 错误自信
- 隐性成本增加
- 对外部工具误调用
- 被 prompt injection 攻击
- 在高风险场景中错误执行

所以，作者提到的前提非常关键：

> Harness Engineering 足够强壮、可逆。

如果没有这个前提，让更多系统跑在 LLM 之上就可能变成灾难。

---

##### 5. 情境化落地

###### 5.1 对个人效率系统的启发

很多人会用 Claude Code、Cursor、ChatGPT 写自己的：

- 日程管理工具
- 文件整理工具
- 知识库同步工具
- 阅读摘要工具
- 自动邮件处理工具
- RSS 聚合工具

建议不要一开始就追求“完美脚本化”。

更好的做法：

```text
先让 LLM 直接帮你处理真实任务
观察它在哪些地方反复成功
观察它在哪些地方反复失败
再把稳定成功的部分固化
把失败和长尾异常继续留给 LLM
```

例如个人 RSS 处理系统：

```text
RSS 原文 → LLM 清洗和理解 → 结构化输出 → 校验 JSON → 入库
```

当你发现某几个来源格式稳定，再针对这些来源写专门解析器。  
但未知来源、异常来源、污染文本，继续交给 LLM。

---

###### 5.2 对产品开发团队的启发

团队在做 AI 产品时，可以把功能分为三层：

###### 第一层：探索层

用 LLM 处理：

- 未定义清楚的需求
- 高变化场景
- 用户输入自由度高的部分
- 长尾问题
- 边界模糊任务

###### 第二层：沉淀层

把 LLM 的处理过程记录下来，沉淀：

- prompt 模板
- 失败样本
- 判断规则
- 工具调用方式
- 用户偏好
- 操作日志

###### 第三层：固化层

把稳定流程变成：

- 脚本
- API
- worker
- workflow
- skill
- agent tool
- 规则引擎

这样系统会越来越强，而不是越来越脆。

---

###### 5.3 对商业系统构建的启发

在商业系统中，AI 最有价值的位置未必是“替代员工”，而是成为系统的弹性缓冲层。

传统商业系统通常害怕异常：

```text
异常输入 → 系统报错 → 人工介入
```

AI 原生商业系统可以变成：

```text
异常输入 → LLM 理解 → 尝试修复 → 生成建议 → 人工确认 → 规则沉淀
```

这意味着 AI 可以帮企业处理大量过去无法自动化的“灰色地带”：

- 客户需求不标准
- 销售线索描述混乱
- 工单信息不完整
- 供应商数据格式不同
- 合同文本不一致
- 用户反馈表达模糊
- 运营数据存在噪声

这些地方以前很难脚本化，现在可以先 LLM 化，再逐渐系统化。

---

##### 6. 一句话总结

> 在 AI 成本足够低、工程护栏足够强的阶段，不要过早把不确定任务脚本化；应先让 LLM 在真实边界中探索、修复和沉淀，再把稳定部分固化为脚本、skill 或 workflow。

更实用的原则是：

```text
探索期：LLM 优先
稳定期：脚本沉淀
异常期：LLM 接管
高风险期：人类确认
```

最终目标不是“用 LLM 替代脚本”，而是构建一种新的系统形态：

```text
LLM 提供弹性
脚本提供确定性
Harness 提供安全性
人类提供方向感
```
