### 如何构建自定义代理框架

构建有用的智能体主要在于定制化：将你的智能体连接到适合当前任务的正确上下文、数据和环境。

从本质上讲，智能体是一个在循环中调用工具直到完成任务并返回结果的模型：

![Image](https://pbs.twimg.com/media/HJ5Rj2pWoAANC33?format=png&name=large)

你也可以将代理定义为：

> 智能体 = 模型 + 框架

框架是围绕模型的支撑结构，将其连接到现实世界。

![Image](https://pbs.twimg.com/media/HJ5RmVHXQAABHo3?format=jpg&name=large)

本文其余部分假设如下：

1. 一个代理的能力仅与其提供给模型的上下文一样好
2. harness 的作用是在每一步为模型提供上下文

所以，要构建一个有用的智能体，你需要一个能够为模型提供给定任务所需正确上下文的框架。

### 基础线束

create\_agent 是 LangChain 用于构建代理框架的基础原语。传入模型、工具和系统提示，即可得到一个可用的代理：

```python
from langchain.agents import create_agent

agent = create_agent(
    model="anthropic:claude-sonnet-4-6",
    tools=tools,
    system_prompt="you are a helpful assistant..."
)
```

像这样的框架

[Deep Agents](https://docs.langchain.com/oss/python/deepagents/overview) 以及

[Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview)

预先组装了一套有特定设计理念的中间件（如下所述）栈：内存、上下文管理、沙箱化等。它们旨在让你快速获得可投入生产的代理，并且在大多数情况下都能良好运行。但许多代理需要比这些框架所支持的更精细的定制化：自定义提示词、业务逻辑、安全护栏等。

\`create\_agent\`采用了不同的方法：它是刻意极简的 。我们的理念与

[Pi](https://pi.dev/)，一个高度可配置的编码代理工具。\`create\_agent\`仅实现了核心代理循环，并暴露了中间件作为定制化的基础组件。

### 中间件：如何自定义框架

中间件在代理循环的每个步骤中嵌入：模型调用之前和之后、工具调用之前和之后、代理启动和关闭时。每个组件处理一个关注点，并可与其他任何组件自由组合：

![Image](https://pbs.twimg.com/media/HJ5RwvmX0AAFi_V?format=png&name=large)

中间件允许你添加 能力到你的代理通过一些通常协同工作的杠杆：

确定性逻辑业务逻辑、策略执行、动态代理控制——任何需要在循环中的特定点触发的内容。这包括对代理本身的运行时控制：根据任务复杂度切换模型、调整提示词，以及更新代理的消息历史（例如在压缩过程中）。这是任何不能（或不应该）存在于提示词中的内容的合适位置。

工具。 与其直接在代理上注册工具，中间件可以处理完整的生命周期——设置、拆卸、注册——并向代理提供一套干净的工具供其使用。当工具存在依赖关系、需要初始化，或者在运行结束时需要干净地拆卸时，这一点尤为重要。它还使工具配置靠近控制它的逻辑，而不是分散在代理定义中。

自定义状态。 如果你的中间件需要跨钩子跟踪状态，中间件可以使用自定义属性扩展代理的状态。这使中间件能够在整个执行过程中跟踪状态（维护在代理运行期间持续存在的计数器、标志或其他值）并在钩子之间共享数据。

流处理器. 中间件可以拦截并转换代理的输出流——过滤事件、注入元数据、将不同类型的事件路由到不同的使用者。当你的软件栈的不同部分需要对代理的不同行为做出反应时非常有用：消耗令牌增量的 UI、捕获工具调用的审计日志、跟踪延迟的监控系统。

中间件的美妙之处在于它：

1. 使能够在代理循环的任何阶段进行自定义
2. 将相关逻辑打包为可组合、可共享的代码单元

LangChain 提供了

[预构建中间件](https://docs.langchain.com/oss/python/langchain/middleware/built-in)用于最常见的模式。任何针对您的特定使用场景的定制化内容，只需一个

[自定义中间件](https://docs.langchain.com/oss/python/langchain/middleware/custom)

即可实现。因为每个组件都是独立的，相同的中间件可以在组织中的每个代理中重复使用，以便新代理无需重新构建即可继承经过实战检验的行为。

### 利用能力

harness 的作用是为模型在正确的时间针对给定的任务获取合适的上下文。

下表将通用能力映射到支持它们的中间件。大多数生产代理最终会根据代理的需求（是否长时间运行？任务有多复杂？代理的操作有多敏感？等）结合使用多个中间件：

![Image](https://pbs.twimg.com/media/HJ5R_wzXwAAYZbc?format=jpg&name=large)

查看预构建中间件的完整列表

[此处](https://docs.langchain.com/oss/python/langchain/middleware/built-in).

### 任务适配

任务-框架适配度是指你的框架与任务实际需求的匹配程度：它所需的上下文、会遇到的故障、必须执行的策略以及运行的环境。客服代理的框架与长期运行的编码代理的框架看起来截然不同。

我们在 LangChain 构建的每个代理，包括我们的

[GTM 代理](https://www.langchain.com/blog/how-we-built-langchains-gtm-agent)，

[异步编码代理](https://github.com/langchain-ai/open-swe)

，以及我们的

[无代码代理构建器](https://www.langchain.com/langsmith/fleet)

，都是基于 create\_agent 构建的，并且配备了针对该代理使命定制的中间件栈。

最好的智能体不仅仅是由强大的模型构建的，而是由与任务紧密适配的工具套件构建的。构建自定义工具套件最简单的方法是使用 create\_agent。

#### 如何构建自定义代理框架：深度总结与解读

##### 一句话总结

**有用的智能体，不只是“模型够强”，而是要有一个合适的框架，把模型接到正确的上下文、工具、数据和执行环境中。**

---

##### 1. 深度总结

###### 1.1 智能体的本质

文章认为，智能体可以简单理解为：

> **智能体 = 模型 + 框架**

模型负责思考、规划、生成结果；  
框架负责把模型接入现实世界，包括：

- 给模型提供上下文
- 管理工具调用
- 控制执行流程
- 处理状态、记忆、安全策略
- 管理输入输出流

换句话说，模型只是“大脑”，框架才是让它能做事的“身体和神经系统”。

---

###### 1.2 代理循环是核心

智能体的基本工作方式是：

1. 模型读取当前上下文
2. 判断下一步要做什么
3. 调用工具
4. 获得结果
5. 更新上下文
6. 继续循环，直到任务完成

所以，构建智能体的关键不是简单“调用一次大模型”，而是设计一个能持续提供正确上下文的执行循环。

---

###### 1.3 `create_agent` 的定位

LangChain 的 `create_agent` 是一个极简代理构建原语。

它只提供核心代理循环：

```python
agent = create_agent(
    model="anthropic:claude-sonnet-4-6",
    tools=tools,
    system_prompt="you are a helpful assistant..."
)
```

它不像完整框架那样预设大量机制，而是把自定义能力开放给开发者。

它的设计哲学是：

> 少做假设，暴露接口，让开发者按任务需要自由组合。

---

###### 1.4 中间件是定制化核心

文章重点强调：  
**中间件是自定义智能体框架的主要方式。**

中间件可以嵌入代理运行的不同阶段：

- 模型调用前
- 模型调用后
- 工具调用前
- 工具调用后
- 代理启动时
- 代理结束时
- 输出流处理时

它可以实现：

###### 业务逻辑

例如：

- 动态切换模型
- 根据任务调整提示词
- 执行企业策略
- 控制代理是否继续运行
- 压缩历史消息

###### 工具管理

中间件可以负责：

- 工具初始化
- 工具注册
- 工具依赖管理
- 工具清理回收

这样工具逻辑不会散落在代理定义中。

###### 状态管理

中间件可以维护运行过程中的状态，例如：

- 调用次数
- 风险标记
- 当前阶段
- 预算消耗
- 上下文压缩状态

###### 流式处理

中间件可以处理输出流，例如：

- UI 接收 token
- 日志系统记录工具调用
- 监控系统统计延迟
- 审计系统追踪敏感操作

---

###### 1.5 任务适配是关键

文章最后强调：  
不同任务需要不同框架。

客服代理、代码代理、数据分析代理、企业流程代理，它们需要的：

- 工具不同
- 上下文不同
- 安全要求不同
- 记忆方式不同
- 错误处理不同
- 运行时长不同

所以，好的代理不是通用模板堆出来的，而是根据任务定制出来的。

---

##### 2. 深入浅出解读

可以把智能体想象成一个员工。

###### 模型是什么？

模型像员工的大脑。  
它会分析、推理、写东西、做判断。

###### 工具是什么？

工具像员工的办公软件。  
例如：

- 浏览器
- 数据库
- 代码执行器
- 邮件系统
- CRM
- 文件系统

###### 框架是什么？

框架像公司的工作制度和流程。

它规定：

- 什么时候查资料
- 哪些资料能看
- 哪些操作要审批
- 出错了怎么办
- 工作进度如何记录
- 敏感操作如何拦截

###### 中间件是什么？

中间件就像一个个可插拔的管理模块。

比如：

| 中间件 | 类比 |
|---|---|
| 记忆中间件 | 员工笔记本 |
| 安全中间件 | 合规审查员 |
| 工具中间件 | IT 管理员 |
| 流处理器 | 直播导播 |
| 状态管理 | 项目进度表 |
| 模型切换 | 根据任务安排初级/高级员工 |

所以，构建智能体不是只问：

> 用哪个大模型？

更应该问：

> 这个任务需要什么工作环境？

---

##### 3. 核心观点提炼

###### 观点一：上下文决定能力

模型再强，如果拿不到正确上下文，也做不好任务。

智能体效果差，很多时候不是模型不行，而是：

- 工具接错了
- 数据没给对
- 历史太乱
- 规则没写清
- 任务状态没管理好

---

###### 观点二：框架比提示词更可靠

很多业务逻辑不应该只写在 prompt 里。

比如：

- 预算限制
- 权限控制
- 敏感信息过滤
- 工具调用审计
- 高风险操作拦截

这些更适合放在中间件里，用确定性代码控制。

---

###### 观点三：通用框架不如任务适配

预制框架能快速启动，但复杂业务一定需要定制。

因为真实业务里会有：

- 特殊数据源
- 企业权限系统
- 合规要求
- 多步骤流程
- 失败重试机制
- 人工审批节点

这些都需要框架层支持。

---

##### 4. 辩证思考

###### 4.1 极简框架的优势

`create_agent` 的好处是灵活。

它不强迫你接受固定设计，而是让你按需组合：

- 适合复杂业务
- 适合企业定制
- 适合沉淀组织级中间件
- 适合构建多种不同代理

对于生产级智能体，这种方式更可控。

---

###### 4.2 极简框架的代价

但灵活也意味着门槛更高。

开发者需要自己思考：

- 哪些逻辑放 prompt？
- 哪些逻辑放中间件？
- 工具如何隔离？
- 状态如何管理？
- 如何观测和调试？
- 如何防止代理失控？

所以它更适合有工程能力的团队，而不是完全零基础用户。

---

###### 4.3 模型能力仍然重要，但不是全部

文章强调框架重要，这很对。  
但也不能因此忽视模型能力。

如果模型推理差，即使上下文和工具很好，也可能：

- 规划错误
- 工具选错
- 理解任务偏差
- 无法处理复杂约束

所以，智能体效果来自三者配合：

> **好模型 + 好上下文 + 好框架**

少一个都不够。

---

###### 4.4 中间件可能带来复杂性

中间件让系统可组合，但过度使用也会导致：

- 调试困难
- 执行链路复杂
- 状态来源混乱
- 不同中间件互相冲突
- 行为不可预测

因此，中间件设计要克制。

原则是：

> 只把稳定、复用、确定性的逻辑沉淀为中间件。

---

##### 5. 最终结论

构建自定义代理框架的关键，不是堆更多工具，也不是写更长 prompt，而是：

1. 明确任务需要什么上下文  
2. 给模型接入合适工具  
3. 用中间件管理业务逻辑、状态、安全和输出  
4. 根据任务定制框架，而不是套通用模板  

最终：

> **真正有用的智能体，是被任务“塑形”的智能体。**
