## 结构化（1）

### 2026-08-10 09:47:17

##### 主旨概括

作者分享了一套 **“原型先行、代码随后”** 的 AI 开发流程：先用 Claude Design 完成并确认 UI 原型，再让 Agent 根据原型及版本差异实现功能，从而降低设计验证成本，并让原型与实际产品长期保持一致。

##### 1. 第一版：先设计和打磨原型

- 项目初版先使用 **Claude Design** 生成 UI 原型与设计。
- 原型打磨完成后保存到本地，并通过 **Baoyu-Design Skill** 持续维护。
- 开发新功能时，不直接修改业务代码，而是遵循以下顺序：
  1. 修改本地原型；
  2. 确认产品逻辑和 UI 设计；
  3. 再实现对应功能。

##### 2. 将流程写入 Agent 规则

- 后来，作者把这套工作方式写进 `Agents.md` 或 `claude.md`。
- 此后只要提出“修改或增加某个功能”，Agent 默认会先更新原型，再处理代码实现。
- 通过这一规则，项目至今能够保持 **原型与实际功能一致**，避免原型逐渐过时。

##### 3. 原型先行的主要价值

###### 低成本验证设计

- 在正式编码前，可先通过原型验证：
  - 产品流程是否合理；
  - UI 设计是否合适；
  - 新功能是否符合预期。
- 相比直接修改完整功能，调整原型的成本更低、反馈更快。

###### 降低 Agent 的实现难度

- Claude Design 的产出包括：
  - **React 代码**；
  - **结构化 JSON 数据**。
- 将原型纳入 Git 版本控制后，可以通过 `git diff` 清楚查看每次设计和功能的变化。
- 功能确认后，Agent 可直接参考原型的 Diff 实现代码，减少理解需求和猜测设计意图的成本。

##### 4. 实践建议与社区反馈

- 作者建议使用 **Opus 模型**，其设计质量通常更好。
- 最好同时接入项目的 **设计系统**，以保证组件、样式和交互的一致性。
- 有用户认为，把原型和代码放入同一套版本控制中非常有效：Agent 能直接根据代码 Diff 工作，可显著减少猜测成本。
- 另有用户询问可接入 Codex 官方插件的 OpenDesign，但原文未给出具体评价。

##### 5. 相关工具

- **Baoyu-Design Skill**：用于在本地维护和迭代 Claude Design 生成的设计原型。

## 深度解读（1）

### 2026-09-18 00:08:18

#### 把原型变成可执行规格：AI 开发真正减少的是“猜测成本”

这段实践最值得关注的，并不是 Claude Design 能快速生成界面，而是它重新定义了原型在开发流程中的位置：**原型不再是项目早期用完即弃的展示稿，而是进入版本控制、持续更新，并直接约束实现的中间产物。**

作者每次增加功能时，先改本地原型，确认交互与 UI 后再改正式代码；同时把这一顺序写进 `Agents.md/claude.md`，让 Agent 默认执行。由此，原型更新不再依赖开发者是否记得，而成为工作流中的固定关卡。这比单纯要求“保持设计与实现一致”可靠得多——一致性不是靠提醒获得的，而是由操作顺序保证的。

##### React、JSON 和 Git diff 共同降低了需求歧义

传统原型向开发传递的信息往往不完整：一张设计图能表达布局和视觉，却很难精确说明组件结构、状态变化以及哪些部分发生了修改。开发者或 Agent 只能结合需求文字自行推断，返工通常就发生在这些推断里。

这里的关键变化是，Claude Design 的产物包含 React 代码和结构化 JSON，并且由 Git 管理。Agent 看到的不只是“最终界面长什么样”，还可以从 diff 中知道：新增了哪个组件、哪些属性改变、什么结构被替换。**diff 实际上成为了一份机器更容易消费的增量需求说明。**

这也解释了为什么该方法对 AI 编程尤其有效。人类可以通过会议、上下文和经验弥补模糊需求，Agent 更依赖明确且可读取的状态差异。相比继续优化提示词，给它一个结构化、版本化、可比较的设计对象，往往更能减少猜测。

##### 真正可迁移的是“规格先行”，而非某个工具

这套方法可以迁移到其他原型工具或编码 Agent，但需要满足几个条件：原型必须足够结构化，变更能够被追踪，组件语义尽量稳定。作者补充“最好集成设计系统”尤其重要。否则每次生成的按钮、间距和组件层级都可能不同，diff 中会混入大量无意义变化，Agent反而更难识别真正的产品意图。

它也有明确边界。原型可以验证信息架构、交互路径和视觉设计，却不能证明后端规则、异常状态、权限、性能和可访问性已经正确。**原型与代码保持一致，不等于产品逻辑已经完整。**更稳妥的做法，是让原型承担前端体验规格，再用验收条件和测试覆盖不可见的业务行为。

从产品工具角度看，值得验证的机会不是再做一个“AI 画 UI”产品，而是连接原型、设计系统、需求变更和代码实现：让一次产品修改同时生成可审查的视觉差异、结构差异与验收项。现有的 Figma、需求文档和代码仓库各自保存了一部分事实，真正昂贵的是它们之间的翻译。**AI 开发流程的下一步，很可能不是让生成更快，而是让产品意图在不同产物之间少失真。**

## 口播总结（1）

### 2026-09-20 00:31:39

这套开发方法的关键，不是让人工智能直接写功能，而是先让原型走在代码前面。每次新增或修改功能，都先更新本地原型。原型确认之后，再进入正式实现。这样能以较低成本验证产品逻辑和界面设计，也能让人工智能编码时少一些猜测。

具体来说，项目的第一个版本会先用 Claude Design 制作用户界面原型。等设计打磨完成，再把原型保存到本地，并配合 Baoyu Design Skill 持续维护。

之后每次开发新功能，第一步都不是修改正式代码，而是修改原型。只有当原型中的交互和界面得到确认，才开始改实际功能。这样，原型不是做完就被搁置的演示稿，而是贯穿开发过程、持续更新的设计依据。

为了把这套流程固定下来，作者后来直接把规则写进 Agents 点 M D，或者 Claude 点 M D 这样的智能体指令文件。此后，只要提出增加或修改功能，人工智能就会默认先更新原型。通过这种方式，原型与实际功能可以长期保持一致，避免出现设计稿是一套、最终产品又是另一套的情况。

这样做有两个明显好处。

第一个好处，是降低验证成本。产品设计和用户界面是否合理，可以先在原型阶段检查。布局不合适、操作流程不顺，或者功能定义需要调整，都可以先改原型，而不必等正式功能写完之后再返工。

第二个好处，是让人工智能更容易理解具体改动。Claude Design 的产出不是单纯的图片，而是 React 代码和结构化的 JSON 数据。因为这些内容可以纳入 Git 版本控制，所以开发者能够通过 Git 差异对比，清楚看到原型前后发生了哪些变化。

功能方案确认后，编程智能体可以直接参考这些差异来修改正式代码。它不需要只凭一句模糊的自然语言描述，去猜测哪些组件要增加、哪些结构要调整。原型的代码差异，相当于提供了一份更具体、更可追踪的变更说明。

不过，工具本身并不能自动保证设计质量。作者补充说，使用 Claude 的 Opus 模型，设计效果通常会好很多。另外，最好把现有的设计系统也集成进流程。设计系统规定了颜色、字体、间距和组件等统一规则，可以减少不同页面之间风格不一致的问题。

最值得记住的是：先改原型，再写功能；把原型和实现都放进版本控制；再让人工智能根据清晰的差异完成开发。这样，原型就不只是一次性的展示材料，而会成为连接产品设计、界面设计和代码实现的持续依据。
