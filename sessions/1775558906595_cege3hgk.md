### 别再说 Codex 不如 Claude 了！你只是没用对这个神器：oh-my-codex

> 一句话总结：oh-my-codex (OMX) 是 OpenAI Codex CLI 的智能工作流增强层，将 AI 编程从"一次性对话"升级为"标准化流程"，彻底解决传统 Codex 的痛点。

最近在技术圈看到不少讨论，说 Codex 不如 Claude 好用。作为一个深度使用 AI 编程工具的开发者，我想说：不是 Codex 不行，而是你没用对工具！今天给大家安利一个我最近发现的神器——oh-my-codex (OMX)，它彻底改变了我对 AI 编程的认知。

#### 🤔 一、oh-my-codex 是什么？

oh-my-codex (OMX) 不是简单的封装，而是 OpenAI Codex CLI 的智能工作流增强层。它解决了传统 Codex 最大的痛点：缺乏工作流管理。

🔥 核心功能亮点：

- 一键启动高智能模式：omx --madmax --high
- 标准化工作流：需求澄清 → 规划审批 → 持久完成 → 多智能体协调
- tmux 进程隔离的并行执行
- .omx/ 目录：智能存储计划、日志、项目记忆

#### 💡 二、为什么需要 OMX？传统 Codex 的致命缺陷

传统 Codex 的典型问题：

你：写一个登录功能 Codex：好的，开始写代码... （结果：可能偏离需求、理解错误、缺少验证）

OMX 的解决方案：

你：$deep-interview "实现登录功能" OMX：让我先澄清需求... - 需要 OAuth 吗？ - 支持哪些登录方式？ - 安全级别要求？ 你：只需要邮箱密码登录，JWT 认证 OMX：好的，我来规划方案... \[生成 PRD 和技术方案\] 你：$ralph "按方案实现" OMX：开始执行...验证...完成！

关键区别：OMX 引入了工程化思维，让 AI 从"码农"升级为"项目经理+架构师+开发+测试"的完整团队。

#### 文章主旨

这篇文章的核心观点是：**很多人觉得 Codex 不如 Claude，好用与否往往不是模型本身的问题，而是有没有配套“工程化工作流”**。作者认为，`oh-my-codex（OMX）` 通过补上需求澄清、方案规划、执行验证和多智能体协作这几环，把 Codex 从“单次对话工具”升级成了“可落地的开发流程系统”。

#### 1. OMX 是什么：给 Codex 加上一层“工作流大脑”

- `oh-my-codex（OMX）` 被定义为 **OpenAI Codex CLI 的智能工作流增强层**，重点不是简单封装，而是补齐传统 Codex 缺少的流程管理能力。
- 它想解决的问题是：AI 写代码时常常**直接开工、容易误解需求、缺少验证、过程不可追踪**。
- 作者列出的核心能力包括：
  - 一键高智能模式：`omx --madmax --high`
  - 标准化流程：**需求澄清 → 规划审批 → 持久完成 → 多智能体协调**
  - 基于 `tmux` 的并行执行与进程隔离
  - 用 `.omx/` 目录统一保存**计划、日志、项目记忆**

#### 2. 为什么需要 OMX：传统 Codex 的痛点在“直接写”

- 作者认为，传统 Codex 的典型问题是：用户只说一句“写个登录功能”，AI 就开始写代码，结果可能出现：
  - 偏离真实需求
  - 误解边界条件
  - 缺少验证和回溯
- OMX 的改进思路是：**先问清楚，再设计，再执行，再验证**。
- 文中举了一个“登录功能”示例：
  - 用户提出“实现登录功能”
  - OMX 会先追问：**要不要 OAuth、支持哪些登录方式、安全级别要求**
  - 用户明确“只要邮箱密码登录 + JWT”
  - 然后 OMX 再生成 **PRD 和技术方案**，最后按方案实现
- 作者总结这个差别是：OMX 让 AI 不只是“写代码的人”，而更像一个覆盖**项目经理、架构师、开发、测试**的完整团队。

#### 3. 安装与环境要求：重点是顺序别错

- 前置要求：
  - `Node.js >= 20`
  - `npm` 或 `yarn`
  - `tmux`（可选，但多智能体模式需要）
- 推荐安装顺序：
  1. 安装 Codex CLI：`npm install -g @openai/codex`
  2. 配置认证：`export OPENAI_API_KEY="sk-..."`
  3. 安装 OMX：`npm install -g oh-my-codex`
  4. 初始化：`omx setup`
  5. 验证：`omx doctor`
- 平台注意点：
  - `macOS/Linux`：直接装 `tmux`
  - `Windows`：推荐 `WSL2` 或 `psmux`
  - `Intel Mac` 若 CPU 飙升，可执行：
    `xattr -dr com.apple.quarantine $(which omx)`
- 作者特别强调的“坑”是：**很多人直接安装 OMX，却没先装 Codex，导致失败**。

  - 明确边界条件
  - 非目标清单（说明哪些功能不做）
- 通俗理解：**先把“到底要做什么”说透，再进入开发**。

##### 4.2 `$ralplan`：方案先审批，再动代码

- 适合场景：
  - 需要架构设计
  - 多种方案要权衡
  - 高风险改动
- 例子：`$ralplan "审批支付模块的技术方案"`
- 主要输出：
  - PRD 文档（`.omx/plans/prd-*.md`）
  - 技术方案说明
  - 风险评估报告
  - 测试策略文档
- 这一步的价值在于：**把“先想清楚”制度化，而不是让 AI 一边想一边写**。

##### 4.3 `$ralph`：不是“尽力而为”，而是“直到完成”

- 适合场景：
  - 复杂任务
  - 需要迭代
  - 结果必须真正落地
- 例子：`$ralph "实现支付模块并验证"`
- 核心特性：
  - 自动重试：失败会继续重试直到成功
  - 验证门控：必须通过验证才能算完成
  - 架构师审核：单独角色检查代码质量
  - 自动清理：用 `ai-slop-cleaner` 清理冗余代码
- 这相当于把“**做完**”从主观描述，变成了有验证标准的流程。

##### 4.4 `$team`：多个 AI 并行协作

- 适合场景：
  - 任务能拆分并行
  - 长时间运行任务
  - 需要进程隔离
- 例子：
  - `$team 3:executor "修复所有测试失败"`
  - `OMX_TEAM_WORKER_CLI_MAP=codex,claude`
  - `$team 2:executor "分析代码并写文档"`
- 核心能力：
  - `tmux` 进程隔离
  - Mailbox 通信
  - Claim-safe 生命周期，避免任务冲突
  - `worktree` 支持，不同 Worker 在不同分支工作
- 简单说：**一个 AI 负责不过来时，就像组织一个小团队分工干活**。

#### 5. 实战案例：作者认为它的效率提升来自哪里

##### 5.1 新项目初始化

- 示例流程：
  1. `omx --madmax --high`
  2. `$deep-interview "创建一个 Next.js SaaS 项目，包含用户认证和订阅支付"`
  3. `$ralplan "审批技术方案"`
  4. `$ralph "按方案创建项目"`
- 最终输出包括：
  - 完整项目结构
  - 认证系统
  - 支付集成
  - 测试用例
- 说明 OMX 不只是帮你“补几段代码”，而是贯穿项目起步全过程。

##### 5.2 Bug 修复流水线

- 示例：`$team 3:executor "修复 CI 中所有失败的测试"`
- 作者给出的效果是：**自动分配 3 个 Worker 分别处理不同模块，验证通过后统一汇报，效率提升 300%**
- 这是文章里比较明确的数据之一，重点体现并行协作的收益。

##### 5.3 代码审查

- 示例：`$team "审查最近的 PR，报告问题和建议"`
- 可拆成多个审查角色：
  - 安全审查
  - 性能审查
  - 代码风格审查
- 价值在于：**一个任务由多个视角同时覆盖，减少单点遗漏**。

#### 6. 最佳实践：怎么把 OMX 用顺手

- 作者推荐的启动方式：
  - 日常开发：`omx --madmax --high`
  - 高推理模式：`omx --madmax --high --reasoning-effort high`
  - 调试：`omx --debug`
- 推荐项目结构中保留 `.omx/`，里面包括：
  - `plans/`
  - `state/`
  - `logs/`
  - `memory/`
  - `context/`
- 还特别强调 `AGENTS.md` 很重要，用来存放项目指导规则。
- Team 模式使用建议：
  - 先检查 `tmux -V`
  - 简单任务用 `2` 个 Worker，复杂任务用 `4` 个 Worker
  - 尽量加 `--worktree` 避免冲突
  - 用 `omx team status my-team` 监控进度
- FAQ 中给出一个关键性能建议：**在 8 核机器上，2-4 个 Worker 是最佳配置，太多会导致 CPU 和内存暴涨**。

#### 7. 常见踩坑与安全提醒：这部分很实用

##### 7.1 安装和使用中的常见坑

- 没先安装 Codex，直接装 OMX → 报错
- `Node.js < 20` → 功能异常
- Windows 没有 `tmux` → `Team` 模式不可用
- 没在 `tmux` 中启动 `$team` → 报错 `Not in tmux`
- `$ralph` 还没跑完就退出 → 必须等到 `APPROVED`
- 忘记执行 `omx setup` → 缺少 `prompts/skills`

##### 7.2 数据安全问题

- 忘记提交 `.omx/` → 项目状态丢失
- API Key 泄露 → **不要硬编码到 shell 配置中**
- 这说明 OMX 的状态和流程依赖本地目录管理，**如果不把状态文件纳入管理，流程就容易断档**。
