## 分析要点

- **核心高价值点**：将Planner、Advisor和Executor明确分离，并以独立审查和最多五轮审批形成执行前质量门禁，同时保留根Codex的最终验证权。
- **留存建议**：建议精读并存档，作为多模型编码工作流的实现参考（提供了可直接安装验证的Codex多模型编排方案，并明确描述角色分工、审批循环、配置命令、权限边界和故障处理。）

**知识要点**

- 规划、审查和执行可由不同模型承担，根编排器负责传递上下文、检查结果和最终交付。
- 独立审查需要Planner与Advisor使用不同的模型路由；未获批准时停止执行并返回未解决问题。
- 跨提供商模型依赖预先配置的认证与兼容路由，插件本身不创建凭证或绕过权限审批。

**行动项**

- 在Python 3.11以上环境安装插件，并用status --require-effective检查工作流是否实际生效。
- 选择一个合适的编码任务，分别配置Planner、Advisor和Executor，验证规划审批循环及并行执行效果。
- 记录完成时间、调用额度、返工次数和测试结果，对文中提到的提速与额度节省目标进行实测。

Release Codex-Orchestration advisor workflow

#### Codex Orchestration

Bring models like Claude Fable 5 into Codex, give each model a role, and let Codex coordinate the work.

Codex Orchestration adds three simple roles to a Codex task:

- **Planner** creates the plan and improves it after feedback. It is optional; when omitted, your current Codex model plans.
- **Advisor** reviews the plan, finds important gaps, and approves it when it is ready. It is optional.
- **Executor** implements the approved plan. It is required for setup.

The model selected for the Codex task remains in charge. It passes work between the roles, checks every result, and gives you the final answer.

```
YOUR TASK
                             |
                             v
                  CODEX COORDINATES THE WORK
                             |
                             v
               PLANNER CREATES THE FIRST PLAN
              Fable 5, another model, or Codex
                             |
                             v
                    ADVISOR REVIEWS IT
                       finds real gaps
                             |
                   needs work? -- yes --+
                             |            |
                            no            v
                             |      PLANNER IMPROVES IT
                             |            |
                             +<-----------+
                             |
                       PLAN APPROVED
                             |
                             v
                  EXECUTORS IMPLEMENT IT
                             |
                             v
                    CODEX TESTS & DELIVERS
```

Planner and Advisor can work through several revisions. Codex stops as soon as the Advisor returns `PLAN_APPROVED`, with a safety limit of five reviews. If approval is not reached, execution stops and Codex shows you the latest plan and unresolved issues.

- Bring Fable 5 or another compatible model into Codex.
- Use different models for planning, review, and implementation.
- Get a stronger plan before code changes begin.
- Run independent implementation work in parallel—up to 2x faster on suitable tasks.
- Move repeatable work away from the root model and potentially hit premium-model limits about 40% less often.

Results depend on the models, task, context, retries, and available parallel work. The speed and limit figures are targets, not guarantees.

#### Install

```
codex plugin marketplace add Cjbuilds/Codex-Orchestration
codex plugin add codex-orchestration@codex-orchestration
```

Start a new Codex task after installation. Setup requires Python 3.11 or newer.

#### Quick start

Use Fable 5 to plan, Sol to advise, and Luna to implement:

```
/codex-orchestration setup planner: Claude Fable 5 High, advisor: GPT-5.6 Sol High, executor: GPT-5.6 Luna Extra High
```

Or let your current Codex model plan and use Fable 5 only as Advisor:

```
/codex-orchestration setup advisor: Claude Fable 5 High, executor: GPT-5.6 Luna Extra High
```

After setup, start another new task and use Codex normally. The saved workflow applies automatically.

Fable defaults to **High**. You can choose **Low**, **Medium**, **High**, **XHigh**, or **Max**. **Ultra** is accepted as an alias for Max because Claude Code does not expose a separate Ultra effort.

Fable 5 uses the official Claude Code CLI and a compatible first-party Claude login. You do not need to add an Anthropic API key to Codex.

```
/codex-orchestration setup planner: <model and effort>, advisor: <model and effort>, executor: <model and effort>
```

- Omit `planner` to use the current Codex model as Planner.
- Omit `advisor` when you do not want plan review.
- `executor` is required.
- Planner and Advisor must use different configured model routes so the review is independent.

Role labels are literal. A model after `planner:` plans; a model after `advisor:` reviews; a model after `executor:` implements. Codex must never move a model to a different role because that model was used differently in an older plugin version. If you specify Planner and Executor but omit Advisor, the workflow has no Advisor.

Examples:

```
/codex-orchestration setup planner: Claude Fable 5 High, advisor: GPT-5.6 Sol High, executor: GPT-5.6 Luna Extra High

/codex-orchestration setup planner: GPT-5.6 Sol Extra High, advisor: Claude Fable 5 High, executor: GPT-5.6 Luna Extra High

/codex-orchestration setup executor: GPT-5.6 Luna Extra High
```

Models already available through Codex can be assigned directly. A model from another provider needs an existing authenticated, compatible provider and a Codex custom-agent role.

Ask the plugin to create a project or personal role:

```
/codex-orchestration create project role:
name: researcher
model: <exact-model-id>
provider: <configured-provider-id>
effort: high
job: gather evidence and cite sources
```

Project roles live in `.codex/agents/`. Personal roles live in `~/.codex/agents/` and can be reused across projects. Codex previews role files before creating them.

Fable 5 is the bundled cross-provider exception and can be used directly as Planner or Advisor. The plugin never creates provider accounts, credentials, or protocol compatibility.

Create a Codex Goal normally, then tell Codex to use the saved workflow until the Goal is complete. Codex still owns Goal state, permissions, integration, and verification; the plugin only guides which models perform each role.

#### Useful commands

```
/codex-orchestration status
/codex-orchestration status --require-effective
/codex-orchestration setup planner: Claude Fable 5 High, advisor: GPT-5.6 Sol High, executor: GPT-5.6 Luna Extra High
/codex-orchestration disable
```

`disable` restores the routing values that existed before setup. It does not delete user-owned custom roles.

#### Important limits

- Codex remains the root orchestrator and final authority.
- Planner and Advisor report only to Codex; they do not contact each other or Executors directly.
- The workflow reserves Fable planning tools for the root Codex model by policy. Current MCP calls do not identify their caller, so this caller boundary is instruction-enforced; the bridge itself still disables tools, edits, and session persistence.
- Advisor approval is a planning gate, not a guarantee that implementation will succeed.
- Direct model routes inherit the root provider. Other providers must already be configured and authenticated.
- The plugin never creates credentials or bypasses permissions and approvals.
- Codex decides when delegation or parallel work is useful.
- If you say `no subagents`, Codex must not delegate.

Technical details are in providers and models.

#### Update

```
codex plugin marketplace upgrade codex-orchestration
codex plugin add codex-orchestration@codex-orchestration
```

Version **0.5.1 or newer** is required for reliable Planner assignment. It has a distinct release identity so Codex replaces the affected Advisor-only `0.5.0` cache instead of reusing it. After the two update commands, confirm `codex plugin list --json` reports `0.5.1` or newer, then start a new task; a task that already loaded the old skill cannot refresh its instructions in place.

If the version stays old or `marketplaceSource.sourceType` is `local`, Codex is pointed at a local checkout rather than the GitHub marketplace. Run `/codex-orchestration disable` first if a saved policy is active, then remove the plugin and that marketplace registration, add `Cjbuilds/Codex-Orchestration` again, and reinstall. This does not delete the local source checkout.

Before downgrading to a version older than Planner support, run `/codex-orchestration disable` with the current version first.

#### Uninstall

First run:

```
/codex-orchestration disable
```

Then remove the plugin:

```
codex plugin remove codex-orchestration@codex-orchestration
codex plugin marketplace remove codex-orchestration
```

Review and remove any user-owned custom roles separately.

#### Codex-Orchestration 项目总结

该项目是一个 Codex 插件，用于把 Claude Fable 5 等其他模型接入 Codex，并分别分配 “规划、评审、执行” 等角色。Codex 始终作为总协调者，负责传递任务、检查结果、管理权限并交付最终答案。

##### 一、核心工作流程

Codex-Orchestration 为一次 Codex 任务提供最多三个角色：

- **Planner（规划者）**
  - 制定初始实施计划。
  - 根据评审意见修改计划。
  - 可省略；省略后由当前 Codex 模型负责规划。

- **Advisor（顾问）**
  - 审查计划，寻找遗漏、风险或重要问题。
  - 计划达到要求后返回`PLAN_APPROVED`。
  - 可省略；省略后不会进行独立的计划评审。

- **Executor（执行者）**
  - 根据已批准的计划实施代码或完成任务。
  - **必须配置**。

整体流程如下：

> 用户提出任务 → Planner 制定计划 → Advisor 评审 →  
> 若有问题，Planner 修改计划并再次评审 → 计划通过 → Executor 执行 → Codex 测试并交付结果

Planner 和 Advisor 最多进行**5 次评审**。如果 5 次后仍未通过，Codex 会停止执行，并展示最新计划及尚未解决的问题。

##### 二、项目带来的能力

该插件主要用于提升多模型协作效率：

- 可以把 Fable 5 或其他兼容模型接入 Codex。
- 可以为规划、评审和实施分别选择不同模型。
- 在代码修改前先获得更严格的计划审查。
- 对适合并行处理的任务，可以同时运行独立的实施工作，目标是最高约**2 倍速度**。
- 将部分重复性工作交给其他模型，理论上可能使高级模型额度消耗频率降低约**40%**。

不过，速度和额度数据只是目标值，并非保证结果，实际效果取决于模型能力、任务复杂度、上下文、重试次数以及可并行的工作量。

##### 三、安装要求与快速开始

###### 安装要求

- 需要**Python 3.11 或更高版本**。
- Fable 5 通过官方 Claude Code CLI 使用，需要已登录兼容的 Claude 官方账号。
- 不需要在 Codex 中额外配置 Anthropic API Key。
- 其他提供商的模型必须已有兼容的提供商配置和有效认证。

###### 安装插件

```bash
codex plugin marketplace add Cjbuilds/Codex-Orchestration
codex plugin add codex-orchestration@codex-orchestration
```

安装完成后，需要启动一个新的 Codex 任务。

###### 快速配置示例

使用 Fable 5 规划、Sol 评审、Luna 执行：

```text
/codex-orchestration setup planner: Claude Fable 5 High, advisor: GPT-5.6 Sol High, executor: GPT-5.6 Luna Extra High
```

只使用 Fable 5 评审，规划仍由当前 Codex 模型完成：

```text
/codex-orchestration setup advisor: Claude Fable 5 High, executor: GPT-5.6 Luna Extra High
```

配置保存后，后续新任务会自动使用该工作流，用户仍可像平常一样使用 Codex。

##### 四、模型与角色配置规则

配置格式为：

```text
/codex-orchestration setup planner: < 模型和推理强度 >, advisor: < 模型和推理强度 >, executor: < 模型和推理强度 >
```

主要规则包括：

- `executor`必须存在。
- 省略`planner`，表示由当前 Codex 模型负责规划。
- 省略`advisor`，表示不启用计划评审。
- Planner 和 Advisor 必须使用不同的模型路由，以保证评审具有独立性。
- 角色名称是固定含义：
  - `planner:`后面的模型负责规划；
  - `advisor:`后面的模型负责评审；
  - `executor:`后面的模型负责执行。
- Codex 不会因为某个模型在旧版本插件中承担过其他工作，就自动改变它当前配置的角色。

可用的推理强度包括：

- `Low`
- `Medium`
- `High`
- `XHigh`
- `Max`

其中，`Ultra`会被视为`Max`的别名，因为 Claude Code 没有单独的 Ultra 选项。Fable 5 默认使用`High`。

其他配置示例：

```text
/codex-orchestration setup planner: GPT-5.6 Sol Extra High, advisor: Claude Fable 5 High, executor: GPT-5.6 Luna Extra High
```

```text
/codex-orchestration setup executor: GPT-5.6 Luna Extra High
```

##### 五、自定义模型角色

Codex 中已有的模型可以直接分配角色。来自其他提供商的模型，则需要：

1. 已配置并完成认证的兼容提供商；
2. 一个对应的 Codex 自定义 Agent 角色。

插件可以帮助创建项目级或个人级角色：

```text
/codex-orchestration create project role:
name: researcher
model: <exact-model-id>
provider: <configured-provider-id>
effort: high
job: gather evidence and cite sources
```

角色存储位置：

- **项目级角色**：`.codex/agents/`
- **个人级角色**：`~/.codex/agents/`

项目级角色只在当前项目使用，个人级角色可以跨项目复用。创建前，Codex 会先预览角色文件。

需要注意的是，插件不会替用户：

- 创建模型提供商账号；
- 生成或保存凭证；
- 绕过认证、权限或协议兼容性要求。

Fable 5 是项目内置的跨提供商例外，可以直接作为 Planner 或 Advisor 使用。

##### 六、与 Codex Goal 和工作流的结合

用户可以先正常创建 Codex Goal，再要求 Codex 在 Goal 完成前使用已保存的工作流。

Codex 仍然负责：

- Goal 状态管理；
- 权限控制；
- 外部系统集成；
- 结果验证；
- 最终交付。

插件只负责指导哪些模型承担规划、评审和执行角色。

如果用户明确要求 “不使用子代理”，Codex 就不能进行委派。是否采用委派或并行执行，由 Codex 根据任务判断。

##### 八、重要限制与安全边界

- Codex 始终是根协调者和最终决策者。
- Planner 和 Advisor 只向 Codex 汇报，不能直接联系彼此或 Executor。
- Advisor 的批准只是 “计划通过”，并不保证最终实现一定成功。
- Fable 的规划工具默认保留给根 Codex 模型使用。
- 当前 MCP 调用无法识别具体调用者，因此部分调用边界依靠指令约束；不过桥接层仍会禁用工具、编辑和会话持久化能力。
- 直接使用 Codex 内置模型的路由会继承根模型的提供商配置。
- Codex 决定何时适合委派任务或并行处理。
- 插件不会绕过权限、审批或认证机制。

#### Codex Orchestration 最佳实践实例：为 FastAPI 增加 “密码重置” 功能

> 仓库：[Cjbuilds/Codex-Orchestration](https://github.com/Cjbuilds/Codex-Orchestration)  
> 目标：用独立的**Planner、Advisor、Executor**完成一个具有安全风险的真实开发任务，并由根 Codex 统一验收。

---

##### 1. 为什么选择这个实例

假设现有项目是一个 Python 3.11+ 的 FastAPI 用户服务，现在需要增加 “忘记密码” 功能：

- `POST /auth/password-reset/request`
- `POST /auth/password-reset/confirm`
- 重置令牌有效期为 15 分钟
- 令牌只能使用一次
- 不得泄露邮箱是否注册
- 需要限流、审计日志和自动化测试

该任务适合多模型编排，因为它同时涉及：

1. API 与数据模型设计；
2. 账户枚举、令牌泄露、重放攻击等安全问题；
3. 数据库、邮件、接口和测试的联合修改；
4. 可以拆分并行执行的测试、迁移和文档工作。

---

##### 2. 推荐的角色配置

| 角色 | 示例模型 | 职责 | 最佳实践 |
|---|---|---|---|
| Root Codex | 当前任务模型 | 统筹、检查结果、运行测试、最终交付 | 始终保留最终决定权 |
| Planner | Claude Fable 5 High | 分析代码库并制定实施计划 | 不直接修改代码 |
| Advisor | GPT-5.6 Sol High | 独立审查计划，重点检查安全与遗漏 | 必须与 Planner 使用不同模型路由 |
| Executor | GPT-5.6 Luna Extra High | 按获批计划实施 | 不擅自扩大需求范围 |

这里最重要的不是使用哪个具体模型，而是：

- **规划与审查相互独立**；

- **Root Codex 对代码、权限、集成和测试负责**。

##### 5. 创建一个高质量 Goal

不要只输入：

```text
实现密码重置。
```

这会导致模型自行猜测需求，增加返工概率。推荐向 Codex 提供明确的范围、约束和验收标准。

###### 推荐 Goal

```text
请使用已保存的 Codex Orchestration 工作流完成以下 Goal。

项目：Python 3.11、FastAPI、SQLAlchemy、PostgreSQL 用户服务。

目标：
实现安全的密码重置功能，包括：

1. POST /auth/password-reset/request
   - 接收 email。
   - 无论邮箱是否存在，都返回相同的 202 响应。
   - 对 IP 和 email 维度进行限流。
   - 已注册用户会收到密码重置邮件。

2. POST /auth/password-reset/confirm
   - 接收 reset_token 和 new_password。
   - reset_token 有效期为 15 分钟。
   - token 只能成功使用一次。
   - 成功后使该用户现有登录会话失效。

安全约束：
- 数据库中不得保存明文 reset token，只保存安全哈希。
- 不得通过状态码、响应正文或明显的响应时间差泄露邮箱是否注册。
- 日志中不得记录明文 token、密码或完整认证凭据。
- 避免重放攻击和并发重复消费 token。
- 密码必须经过项目现有的密码策略校验。
- 不得修改现有登录接口的外部行为。

实施范围：
- API 路由和请求 / 响应模型；
- 服务层；
- 数据库迁移；
- 邮件发送适配；
- 单元测试和集成测试；
- 必要的配置与文档。

非目标：
- 不更换现有认证框架；
- 不重新设计整个用户模块；
- 不引入新的外部邮件服务商；
- 不进行无关重构。

验收标准：
- 全部现有测试继续通过；
- 新增成功、过期、重复使用、无效 token、未知邮箱和限流测试；
- 并发提交同一 token 时，最多只有一个请求成功；
- 数据库和日志中不出现明文 token；
- 数据库迁移可以升级和回滚；
- 静态检查和格式检查通过。

工作方式：
- Planner 先检查仓库并给出文件级实施计划。
- Advisor 独立审查计划，重点检查安全、并发、迁移和测试缺口。
- 未获得 PLAN_APPROVED 前不要修改代码。
- 获批后由 Executor 实施。
- Root Codex 必须审查变更、运行测试，并在最终答复中列出验证证据。
- 不要修改 Goal 之外的文件，除非确有必要并说明原因。
```

##### 7. Planner 应输出什么

本实例中，一个合格的计划不应该只写 “增加接口、写测试”，而应达到文件级和风险级精度。

###### 示例计划结构

```markdown
## 实施计划

### 1. 现状确认
- 确认现有用户模型、密码哈希工具和会话失效机制。
- 确认项目使用 Alembic 还是其他迁移工具。
- 确认邮件适配层是否支持测试替身。
- 确认现有限流中间件能否按 IP 和规范化 email 建立键。

### 2. 数据模型
- 新增 password_reset_tokens 表。
- 字段包括：
  - id
  - user_id
  - token_hash
  - expires_at
  - consumed_at
  - created_at
- 对 token_hash 添加唯一索引。
- 设计可回滚迁移。

### 3. 请求接口
- 始终返回统一的 202 响应。
- 规范化 email。
- 未注册邮箱也执行近似成本路径，减少时序差异。
- 对 IP 和 email 两个维度限流。

### 4. 确认接口
- 对输入 token 进行哈希后查询。
- 在事务内原子更新 consumed_at。
- 校验有效期和密码策略。
- 更新密码后撤销用户会话。

### 5. 日志与审计
- 记录事件类型、用户内部 ID 和结果类别。
- 不记录 email 全文、明文 token 或新密码。

### 6. 测试
- 已注册邮箱请求。
- 未注册邮箱请求。
- 响应一致性。
- 有效 token。
- 过期 token。
- 无效 token。
- 已消费 token。
- 并发重复消费。
- 限流。
- 会话失效。
- 迁移升级与回滚。
```

###### Planner 最佳实践

- 先读取真实仓库结构，再给出文件路径；
- 明确事务边界，而不是只描述业务步骤；
- 明确哪些模块可以复用，避免重复实现密码哈希、邮件和限流逻辑；
- 将不确定项列为 “需要先确认”，不要用猜测代替仓库证据；
- 不在计划阶段修改代码。

##### 8. Advisor 应重点审查什么

密码重置是高风险功能，Advisor 应独立寻找 Planner 没发现的问题。

###### 推荐审查清单

###### 安全性

- [ ] 是否避免账户枚举？
- [ ] 是否避免保存明文令牌？
- [ ] 是否使用密码学安全的随机令牌？
- [ ] 是否定义令牌过期时间？
- [ ] 是否保证令牌只能消费一次？
- [ ] 是否避免日志泄露？
- [ ] 修改密码后是否撤销已有会话？
- [ ] 是否复用项目现有密码策略？

###### 并发与事务

- [ ] 同一个 token 并发提交时是否最多一个成功？
- [ ] 查询和消费是否在同一个事务中完成？
- [ ] 是否依赖数据库条件更新、行锁或其他原子机制？
- [ ] 密码更新失败时，token 是否会被错误标记为已使用？

###### 限流与隐私

- [ ] 是否同时覆盖 IP 和 email 维度？
- [ ] 限流键是否保存了不必要的敏感信息？
- [ ] 已注册与未注册邮箱的响应是否一致？
- [ ] 是否考虑明显的响应时间差异？

###### 迁移与运维

- [ ] 数据库迁移是否可回滚？
- [ ] 过期 token 是否有清理策略？
- [ ] 邮件发送失败如何处理？
- [ ] 新增配置是否有安全默认值？

###### 测试

- [ ] 是否覆盖 token 过期？
- [ ] 是否覆盖重复使用？
- [ ] 是否覆盖并发消费？
- [ ] 是否检查日志和数据库中没有明文 token？
- [ ] 是否确保现有登录功能无回归？

只有重要缺口都被修正后，Advisor 才应返回：

```text
PLAN_APPROVED
```

##### 9. Executor 实施阶段的最佳实践

###### 9.1 严格按照获批计划执行

Executor 不应自行：

- 更换认证框架；
- 重构整个用户模块；
- 替换邮件服务商；
- 修改与密码重置无关的接口；
- 降低或跳过测试标准。

发现计划与代码库实际情况冲突时，应将问题返回 Root Codex，而不是静默扩大修改范围。

###### 9.2 使用原子消费机制

以下伪代码表达正确方向：

```python
updated = (
    session.query (PasswordResetToken)
    .filter (
        PasswordResetToken.token_hash == token_hash,
        PasswordResetToken.consumed_at.is_(None),
        PasswordResetToken.expires_at > now,
    )
    .update (
        {"consumed_at": now},
        synchronize_session=False,
    )
)

if updated != 1:
    raise InvalidOrExpiredResetToken ()
```

但生产实现还必须保证：

- token 消费与密码更新处于正确的事务边界；
- 密码更新失败时不会留下 “token 已消费但密码未更新” 的不一致状态；
- 数据库行为符合项目所用 ORM 和隔离级别；
- 同一个 token 的并发请求最多只有一个成功。

###### 9.3 不保存明文 token

推荐流程：

1. 使用密码学安全随机源生成高熵 token；
2. 只通过邮件发送明文 token；
3. 在数据库中保存 token 的安全摘要；
4. 用户提交 token 后，先进行同样的摘要计算，再查询数据库；
5. 日志、异常和测试快照均不得包含明文 token。

###### 9.4 谨慎并行化

适合并行的工作：

- 数据库迁移与模型；
- 邮件适配器测试；
- API 文档；
- 独立的测试文件。

不适合盲目并行的工作：

- 同时修改同一个认证服务文件；
- 数据模型尚未确定时实现接口；
- 事务语义尚未批准时分别实现 token 消费和密码更新；
- 多个执行任务同时修改同一迁移链。

最佳实践是由 Root Codex 判断任务是否真正独立，再决定是否委派或并行执行。仓库中提到的 “最高约 2 倍” 只是适合场景下的目标，并非保证。

##### 10. Root Codex 的最终验证

插件负责角色路由，但不会替代最终质量控制。Root Codex 应检查真实结果，而不是仅接受 Executor 的 “已完成” 声明。

###### 10.1 审查修改范围

```bash
git status --short
git diff --stat
git diff
```

检查：

- 是否存在无关文件变更；
- 是否意外修改锁文件；
- 是否提交临时调试代码；
- 是否在配置或测试夹具中泄露 token；
- 是否存在跳过测试或降低断言强度的修改。

###### 10.2 运行项目测试

具体命令应以项目现有工具为准，例如：

```bash
pytest -q
```

针对新增功能：

```bash
pytest -q tests/auth/test_password_reset.py
```

###### 10.3 运行静态检查

例如：

```bash
ruff check .
mypy .
```

如果项目还有格式检查：

```bash
ruff format --check .
```

###### 10.4 验证迁移

以下仅为 Alembic 项目的示例：

```bash
alembic upgrade head
alembic downgrade -1
alembic upgrade head
```

应在隔离测试数据库中完成，避免影响真实环境。

###### 10.5 验证并发行为

至少增加一个自动化测试，让多个请求同时使用同一个 token：

```python
def test_reset_token_can_only_be_consumed_once_under_concurrency ():
    token = issue_reset_token ()

    results = submit_concurrently (
        lambda: confirm_password_reset (token, "NewStrongPassword123!")
    )

    assert count_successes (results) == 1
    assert count_invalid_or_consumed (results) == len (results) - 1
```

仅测试 “顺序调用两次” 不足以证明并发安全。

###### 10.6 验证敏感数据未泄露

```bash
grep -R "known-plaintext-test-token" logs/test-output/ 2>/dev/null
```

还应通过测试直接检查：

- 数据库中保存的值不等于原始 token；
- 应用日志不包含 token；
- 异常信息不回显 token；
- 邮件测试替身中的敏感内容不会进入持久化日志。

##### 12. 本实例的核心最佳实践总结

1. **先定义明确 Goal**  
   写清功能范围、安全约束、非目标和可验证的验收标准。

2. **让 Planner 与 Advisor 保持独立**  
   避免同一个模型既提出方案又自行批准方案。

3. **将计划批准设为编码前置条件**  
   未出现`PLAN_APPROVED`前不修改代码。

4. **Planner 输出文件级、事务级计划**  
   不接受 “增加接口并补充测试” 这种泛化计划。

5. **Advisor 聚焦高风险缺口**  
   本例重点是账户枚举、token 泄露、并发重放、会话撤销和迁移。

6. **Executor 不扩大范围**  
   只执行获批计划；遇到冲突时返回 Root Codex。

7. **Root Codex 始终是最终责任方**  
   必须审查 diff、运行测试并提供验证证据。

8. **并行只用于真正独立的工作**  
   避免多个执行任务同时修改同一核心认证代码。

9. **不要把 Advisor 批准当成成功保证**  
   `PLAN_APPROVED`只说明计划通过审查，不代表实现和测试一定成功。

10. **安装或升级后使用新任务**  
    尤其应确认插件版本至少为`0.5.1`，避免旧缓存造成 Planner 路由错误。

## 口播总结（1）

### 2026-08-03 01:42:35

#### Codex-Orchestration：让不同模型分工协作完成 Codex 任务

这份材料介绍了一个名为 Codex-Orchestration 的插件。它可以把不同的模型接入 Codex，分别安排它们做规划、审查和执行，再由 Codex 统一协调、验证并交付结果。听完之后，你可以了解它的工作流程、安装方法、角色配置方式，以及它的使用边界和注意事项。

##### 一、它的核心机制：三个角色协作

首先，Codex-Orchestration 为一个 Codex 任务增加了三个可分工的角色。

第一个是 Planner，也就是“规划者”。它负责拆解任务、制定实施计划，并根据反馈修改计划。这个角色是可选的。如果不指定 Planner，就由当前正在使用的 Codex 模型自己制定计划。

第二个是 Advisor，也就是“顾问”或“审查者”。它负责检查计划，找出重要遗漏，并判断计划是否已经可以执行。这个角色同样是可选的。

第三个是 Executor，也就是“执行者”。它负责按照已经批准的计划真正完成实现。Executor 是安装和配置中必需的角色。

通俗地说，整个流程像一个项目团队：一个模型先做方案，另一个模型挑问题，方案通过后，再由执行模型写代码或完成具体工作。最后，仍然由 Codex 负责把各部分串起来，并给出最终答案。

具体流程是这样的：用户提出任务后，Codex 负责协调。Planner 先创建初始计划，Advisor 进行审查。如果发现问题，Planner 就修改计划，然后再次提交审查。这个过程可以反复进行，直到 Advisor 返回“PLAN_APPROVED”，也就是“计划已批准”。计划通过后，Executor 开始执行，Codex 再负责测试和交付。

为了避免无限循环，审查最多进行五轮。如果五轮之内仍然没有得到批准，执行就会停止，Codex 会向用户展示最新的计划以及仍未解决的问题。

##### 二、它能带来什么：更明确的分工和并行执行

接下来，这个插件的主要价值，是让不同模型分别负责自己更擅长的工作。

你可以让一个模型负责规划，另一个模型负责独立审查，再让第三个模型负责实现。这样做的目标，是在代码真正改动之前，先获得一份更可靠的计划。

在适合并行处理的任务中，插件还可以同时安排多个独立的实现工作，理论上最高可以达到大约两倍的速度。它也希望把一部分重复性工作从根模型，也就是负责全局协调的 Codex 模型那里分出去，从而可能让高级模型的使用上限触发频率降低约百分之四十。

不过，这些速度和额度数字只是目标，不是保证。最终效果会受到模型能力、任务复杂度、上下文内容、重试次数，以及是否存在可以并行处理的工作等因素影响。

##### 三、安装方法：先添加插件，再开启新任务

要开始使用，先把插件加入 Codex 的插件市场，再安装它。对应的命令是：

`codex plugin marketplace add Cjbuilds/Codex-Orchestration`

然后执行：

`codex plugin add codex-orchestration@codex-orchestration`

安装完成后，需要新开一个 Codex 任务。这个插件的配置会在新的任务中生效，已经启动的任务不会自动刷新旧的插件指令。

安装环境还要求 Python 3.11 或更高版本。

##### 四、快速配置：为三个角色指定模型

配置插件时，使用 `/codex-orchestration setup` 命令，并分别指定 Planner、Advisor 和 Executor 使用的模型与工作强度。

例如，可以让 Claude Fable 5 负责规划，GPT-5.6 Sol 负责审查，GPT-5.6 Luna 负责执行：

`/codex-orchestration setup planner: Claude Fable 5 High, advisor: GPT-5.6 Sol High, executor: GPT-5.6 Luna Extra High`

这里的 High、Extra High 等，是模型的工作强度设置。Fable 5 默认使用 High，也可以选择 Low、Medium、High、XHigh 或 Max。Ultra 也被接受，但它只是 Max 的别名，因为 Claude Code 没有单独提供 Ultra 这一档。

你也可以只让 Fable 5 做审查，而让当前 Codex 模型负责规划。命令可以写成：

`/codex-orchestration setup advisor: Claude Fable 5 High, executor: GPT-5.6 Luna Extra High`

如果省略 Planner，当前 Codex 模型就会承担规划工作。如果省略 Advisor，就不会进行独立的计划审查。但 Executor 不能省略，因为必须有人负责真正执行。

一个重要规则是，Planner 和 Advisor 必须使用不同的模型路线。这里的“模型路线”，可以理解为模型及其提供方的配置通道。这样做是为了保证审查相对独立，而不是让同一个配置既制定计划又审查自己。

角色名称也是严格对应的。写在 `planner` 后面的模型，就只能负责规划；写在 `advisor` 后面的模型，就负责审查；写在 `executor` 后面的模型，就负责执行。插件不会因为某个模型在旧版本中承担过其他工作，就自动把它换到新的角色里。

##### 五、模型和身份验证：已有配置可以直接使用

已经通过 Codex 配置好的模型，可以直接分配给相应角色。

如果模型来自其他服务商，则需要提前配置好对应的服务商，并完成身份验证。同时，还要有一个兼容的 Codex 自定义代理角色。这里的“自定义代理角色”，可以理解为一份告诉 Codex“这个模型是谁、通过哪个服务商连接、适合做什么工作”的角色配置。

Fable 5 是一个特殊的跨服务商例外。它使用官方的 Claude Code 命令行工具，以及兼容的第一方 Claude 登录，因此不需要额外把 Anthropic 的 API 密钥添加到 Codex 中。

但要注意，插件不会替你创建服务商账号、生成凭证，也不会绕过模型提供方的协议兼容要求。

##### 六、创建自定义角色：让模型承担固定工作

除了临时配置三个角色，插件还可以创建项目级或个人级的自定义角色。

例如，可以创建一个名叫 researcher，也就是“研究员”的角色，让它负责收集证据并引用来源。配置中需要指定准确的模型 ID、已经配置好的服务商 ID、工作强度，以及这个角色的工作内容。

项目级角色会保存在项目目录下的 `.codex/agents/` 中。个人级角色则保存在用户目录下的 `~/.codex/agents/` 中，可以在多个项目之间重复使用。

在真正创建之前，Codex 会先预览角色文件，让用户有机会检查内容。这个机制可以减少角色配置错误，也方便用户确认模型、服务商和任务说明是否正确。

##### 七、如何用于 Goal：Codex 仍然掌握任务状态

使用时，你可以像往常一样创建一个 Codex Goal。Goal 可以理解为 Codex 中一个需要持续推进、直到完成的目标。创建完成后，再告诉 Codex 使用已经保存的工作流，直到这个目标完成。

插件只负责指导不同模型分别承担什么角色。Codex 仍然掌握 Goal 的状态、权限、系统集成和最终验证。

也就是说，插件不是另一个独立的总指挥。真正负责判断是否需要委派、是否需要并行处理，以及是否可以交付结果的，依然是 Codex。

你还可以用下面两个命令查看状态：

`/codex-orchestration status`

或者使用：

`/codex-orchestration status --require-effective`

后一个命令可以要求系统确认当前配置确实已经生效。

如果不再需要插件，可以执行：

`/codex-orchestration disable`

这个操作会恢复配置前原本的模型路由，但不会删除用户自己创建的自定义角色。

##### 八、重要边界：模型之间不是自由通信

更重要的是，这套工作流虽然有多个模型参与，但它们并不是完全自由地互相联系。

Planner 和 Advisor 都只向 Codex 汇报。它们不会直接联系彼此，也不会直接联系 Executor。所有信息传递都要经过根 Codex 模型，也就是当前负责全局协调的模型。

此外，规划工具默认保留给根 Codex 模型使用。原因是当前的 MCP 调用，也就是一种让模型调用外部工具的机制，并不能明确识别调用者身份。因此，这个边界主要依靠指令来约束；同时，插件桥接层还会禁用工具、编辑和会话持久化等能力。

Advisor 批准计划，也不代表实现一定成功。它只能说明计划通过了规划阶段的审查，不能保证代码没有问题，或者执行过程中不会遇到失败。

直接使用 Codex 已有的模型路线时，会继承根模型的服务商配置。其他服务商则必须已经完成配置和身份验证。

插件同样不会创建凭证，不会提升权限，也不会绕过用户确认和审批流程。如果用户明确说不要使用子代理，也就是不要委派给其他模型，那么 Codex 就不能进行委派。

##### 九、版本更新：可靠分配 Planner 需要新版本

在技术细节上，如果希望 Planner 的分配更加可靠，需要使用 0.5.1 或更高版本。

更新时，可以先执行插件市场升级命令：

`codex plugin marketplace upgrade codex-orchestration`

然后重新添加插件：

`codex plugin add codex-orchestration@codex-orchestration`

更新完成后，用 `codex plugin list --json` 检查版本，确认显示的是 0.5.1 或更高版本。之后还要重新开始一个新任务，因为已经加载旧技能的任务，无法在运行过程中就地刷新指令。

如果版本仍然过旧，或者配置中的 `marketplaceSource.sourceType` 显示为 `local`，就说明 Codex 正在使用本地代码目录，而不是 GitHub 插件市场中的版本。

这种情况下，如果已有保存的工作流策略，应先执行 `/codex-orchestration disable`。然后移除插件和对应的插件市场注册，再重新添加仓库并安装。这个过程不会删除本地源代码目录。

如果要降级到不支持 Planner 的旧版本，也应该先用当前版本执行 `/codex-orchestration disable`，再进行降级。

##### 十、卸载方式和开发检查

卸载时，第一步仍然是：

`/codex-orchestration disable`

接着移除插件：

`codex plugin remove codex-orchestration@codex-orchestration`

再移除插件市场注册：

`codex plugin marketplace remove codex-orchestration`

用户自己创建的自定义角色，需要另外检查并手动删除。插件卸载不会自动清理这些角色文件。

如果要参与开发或检查项目，可以先安装开发依赖，然后依次运行代码编译检查、代码风格检查、单元测试、插件生命周期测试和发布检查。材料中给出的命令包括：

`python3 -m pip install -r requirements-dev.txt`

`python3 -m compileall -q plugins tests scripts`

`python3 -m ruff check plugins tests scripts`

`python3 -m unittest discover -s tests -v`

`python3 tests/plugin_lifecycle_smoke.py`

以及：

`python3 scripts/release_check.py`

这些检查分别用于确认依赖完整、Python 文件能够编译、代码风格合格、测试通过、插件安装卸载流程正常，以及发布内容符合要求。

##### 结尾：最值得记住的五点

最后，回顾五个最重要的结论。

第一，Codex-Orchestration 的核心是三角色分工：Planner 负责规划，Advisor 负责审查，Executor 负责执行。其中 Executor 必须配置，另外两个角色可以省略。

第二，工作流不是直接执行，而是先规划、再审查、反复修改，直到 Advisor 批准；最多审查五轮，仍未通过就停止执行并展示问题。

第三，Codex 始终是总协调者和最终权威。其他模型不会直接互相联系，也不会绕过 Codex 的权限、验证和审批机制。

第四，插件可能带来更强的计划质量、并行执行能力，以及更低的高级模型使用频率，但“两倍速度”和“降低约百分之四十”都只是目标，不是保证。

第五，安装后要新开任务才能让配置生效；如果要可靠使用 Planner，应确认版本为 0.5.1 或更高，并记住插件不会替你创建账号、凭证或服务商配置。

## 深度解读（1）

### 2026-09-18 00:30:17

#### 多模型编程的关键，不是“模型开会”，而是可验证的职责分离

这个项目真正值得关注的，并非“把 Claude 接进 Codex”，而是它把多模型协作压缩成了一套相当明确的控制流程：**Planner 制订方案，Advisor 独立审查，Executor 实施，根 Codex 负责调度、测试与最终交付。** 在 Advisor 返回 `PLAN_APPROVED` 之前不进入执行；审查最多五轮，仍未通过就停止，并展示未解决的问题。

这比常见的“让多个 Agent 自由讨论”更有价值，因为它首先解决的是责任和状态问题：现在处于规划、审查还是执行阶段？谁有权放行？失败后留下什么结果？多智能体系统真正困难的往往不是模型不会生成内容，而是输出相互覆盖、错误被逐级放大，最终没人知道哪个判断经过了验证。

##### 独立审查比增加模型数量更重要

项目要求 Planner 与 Advisor 使用不同的模型路由，说明作者抓住了一个关键变量：**审查只有在错误相关性较低时才有价值。** 同一个模型先写方案，再换一个角色提示词审查，容易重复自己的假设；不同模型、供应商或推理配置，至少可能暴露不同的遗漏。

但这种“独立”仍然有限。Planner 和 Advisor 都只向根 Codex 汇报，Codex负责传递上下文并判断结果；部分工具边界又依靠提示词约束，因为当前 MCP 调用无法识别实际调用者。因此，这更像“有职责分离的工作流”，还不是严格隔离的多代理系统。若根模型错误概括了审查意见，或者多个模型共享了同一份有偏上下文，表面上的交叉验证仍可能失效。

对产品设计的启示是：多 Agent 的质量不能只看角色数量，更应记录**每个角色看到了什么、提出了哪些异议、异议如何关闭，以及最终决策由谁作出**。这些可追溯信息可能比再接入一个更强模型更重要。

##### 它适合高返工成本任务，而非所有编码任务

“先通过方案审查再改代码”适合跨模块重构、迁移、权限系统等返工昂贵的任务；对于一个明确的小型修复，额外规划和五轮审查反而可能增加时延。并行 Executor 也只有在工作能被清晰拆分、写入范围较少重叠时才可能提速，否则整合冲突会抵消收益。

仓库提出“合适任务最多快 2 倍”“高级模型额度消耗可能减少约 40%”，但明确称其为目标而非保证，也没有给出基准测试。项目目前提交量有限，GitHub 页面还显示没有正式 Release，因此更应把它视为**一个值得验证的工作流原型，而非已证明的效率方案**。真正需要比较的是任务总耗时、人工介入次数、缺陷率和 token 成本，而不是单次生成速度。

##### 更大的机会是模型协作的控制层

该项目允许保存项目级或个人级角色、接入已认证的外部供应商，并保留 Codex 的权限与最终验证权。这透露出一个可能持续的产品方向：当模型逐渐可替换，价值会从“默认使用哪个模型”转向**如何路由任务、设置审批门槛、管理凭证与权限、评估每种角色组合的效果**。

Codex-Orchestration 已经展示了这层控制面的雏形，但尚未回答最关键的问题：什么任务值得启用哪套流程？下一步最有价值的能力，或许不是增加更多角色，而是根据代码影响范围和历史失败数据，自动判断何时需要独立审查、何时可以并行，以及何时应尽早停止。
