#### lfg

Run AI coding agents on your own machine, from anywhere.

[lfg icon](https://lfg.apps.omg.dev)

`lfg` turns a Linux box or macOS workstation into a private control plane for Claude Code, Codex, and opencode. It starts each agent in a long-lived `tmux` session, streams the transcript to a web UI, and lets you answer prompts or steer work from your phone or laptop.

**Website:**[lfg.apps.omg.dev](https://lfg.apps.omg.dev)

#### Why lfg?

- **Run agents where your code lives.** Sessions execute on your machine, in your repos, with your local CLIs and credentials.
- **Use a real web UI.** Launch sessions, watch output, answer permission prompts, switch projects, and resume work from an installable PWA.
- **Keep it private.** The server binds to loopback by default and is designed to be exposed through Tailscale, not the public internet.
- **Automate repo checks.** Optional markdown-defined agents can collect git, repo, GitHub, model, or security context and produce reports.

#### Screenshots

The images are stored in this repo instead of hotlinked, so the README renders reliably on GitHub.

#### Requirements

- [Bun](https://bun.sh)
- `tmux`
- `git`
- At least one supported agent CLI on `PATH`:
  - `claude`
  - `codex`
  - `opencode`
- Optional: [Tailscale](https://tailscale.com) for private remote access

#### Quick Start

Install on an Ubuntu/Debian VPS or macOS workstation:

```
curl -fsSL https://raw.githubusercontent.com/BennyKok/lfg/main/scripts/setup.sh | bash
```

For a non-interactive Tailscale setup:

```
curl -fsSL https://raw.githubusercontent.com/BennyKok/lfg/main/scripts/setup.sh \
  | TS_AUTHKEY=tskey-auth-xxxx bash
```

The setup script downloads the latest release, installs production dependencies, writes `.env`, starts the server as a user service, and configures `tailscale serve` when Tailscale is available.

#### One-click Launch

[![Deploy on Railway](https://camo.githubusercontent.com/88cb27bf937b98276737ba7888269a1bc9495d8670f63e1acc908b3442841114/68747470733a2f2f7261696c7761792e636f6d2f627574746f6e2e737667)](https://railway.com/new/template?template=https://github.com/BennyKok/lfg)

Railway is useful for a hosted demo, but `lfg` works best on the machine that has your repos, `tmux`, and authenticated agent CLIs. See deploy/railway for details.

The shared Dockerfile also works as the base for Fly.io, Render,DigitalOcean, and Koyeb. These PaaS targets are best for demos or private-network deployments; a VPS remains the cleanest production-style target. Because the Vibes SDK path is not live for source installs yet, the Dockerfile installs the published bundled release (`lfg-bundle.tar.gz`) instead of building from the GitHub source tree. Publish a bundle with `scripts/release.sh <tag>` before relying on one-click cloud deploys.

For Hetzner, use the cloud-init template in deploy/hetzner. Hetzner's official deploy button only preselects Hetzner App images, so the repo ships a first-boot installer instead.

Railway user requirements:

- Railway account and GitHub access to this repo.
- Keep Public Networking disabled unless you put auth in front of `lfg`.
- For Tailscale access, add Railway's Tailscale router as a second service and put `TS_AUTHKEY` on that router service.
- Optional provider keys in Railway variables, such as `ANTHROPIC_API_KEY`,`OPENAI_API_KEY`, or `ELEVENLABS_API_KEY`.

Hetzner user requirements:

- Hetzner Cloud account, SSH public key, and either the `hcloud` CLI or Console.
- Tailscale account plus an ephemeral/preauthorized auth key for unattended setup. The installer joins the server with `tailscale up --authkey ...` and exposes the loopback-only UI through `tailscale serve`.
- After boot, authenticate `claude`, `codex`, or `opencode` on the server, or configure API-key based providers in `.env`.

cd lfg

#### Commands

```
bun run serve                  # web UI + control server
bun run agents -- list         # list markdown-defined agents
bun run agents -- run <name>   # run an insight agent
bun run whatsapp -- run        # optional WhatsApp sidecar
bun run setup                  # rerun provisioning/update flow
```

Installed release builds expose the same commands through `lfg`.

#### Configuration

Configuration lives in `.env`; see `.env.example`.

Common settings:

Variable Purpose

`LFG_HOST` Bind address. Keep `127.0.0.1` unless you know the risk.

`LFG_PORT` Web UI and API port. Defaults to `8766`.

`LFG_REPOS_ROOT` Directory scanned for git repos.

`LFG_CLAUDE_PATH` Override the `claude` binary path.

`LFG_CODEX_PATH` Override the `codex` binary path.

`LFG_OPENCODE_PATH` Override the `opencode` binary path.

`ANTHROPIC_API_KEY` Optional API key for Claude SDK-backed flows.

`LFG_WHATSAPP_*` Optional WhatsApp bridge settings.

`LFG_INSTALL_CHANNEL` Optional install-channel override: `source`, `release`, or `container`. Normally written by setup/container deploys.

#### Security

`lfg` launches AI agents with shell access on your machine. The control API is unauthenticated by design because it is meant to run on loopback and be accessed privately through Tailscale.

Do not expose `lfg` directly to the public internet. Read SECURITY.md before sharing access.

##### 一句话总结

**lfg 是一个开源、自托管的 AI 编码代理控制台，可以让你把 Claude Code、Codex、OpenCode 等 AI coding agents 跑在自己的 VPS / Linux 机器 / macOS 工作站上，并通过 Web PWA 在手机或电脑上远程管理多个长期运行的 tmux 会话。**

它的核心目标是：  
> **把 AI 编码代理从本地笔记本迁移到一台始终在线的机器上，让多个代理并行工作，而你只负责远程调度、审批和查看结果。**

---

#### 1. 综合总结

##### 1.1 lfg 是什么？

lfg 全称并未强调展开含义，它定位为：

> **Self-hosted control plane for AI coding agents**

也就是：

> **面向 AI 编码代理的自托管控制平面。**

它支持管理以下编码代理工具：

- **Claude Code**
- **Codex**
- **OpenCode**
- 未来或实验性场景中也提到了 Grok、Qwen Coder 等模型或代理组合

lfg 本身不替代这些 AI 编码工具，而是作为一个统一调度层：

- 启动代理
- 管理会话
- 查看输出
- 响应权限请求
- 切换项目
- 恢复任务
- 并行运行多个 agent
- 通过 Web UI / PWA 远程控制

---

##### 1.2 它解决什么问题？

传统使用 AI 编码代理时，开发者通常在本地电脑上打开终端，运行 Claude Code、Codex 等工具。

问题是：

1. **本地电脑不能一直开着**
2. **多个代理同时运行很难管理**
3. **手机上难以查看或控制进度**
4. **长任务容易被本地环境、睡眠、断网打断**
5. **不同项目、不同分支、不同代理之间缺乏统一面板**
6. **权限确认、编辑审批、计划审查等交互分散在多个终端里**

lfg 的思路是：

> 把这些代理都放到一台 VPS 或远程机器上长期运行，然后用一个 Web 控制台统一管理。

所以用户可以做到：

- 在 VPS 中同时运行多个编码代理
- 从手机上查看每个代理的进度
- 收到 PWA 推送通知
- 远程批准或拒绝代理的操作
- 用语音代理管理其他代理
- 让不同 agent 之间具备一定上下文感知或协作能力

---

##### 1.3 核心工作方式

lfg 的底层设计非常直接：

> **每一个 AI 编码代理都运行在一个独立的 tmux session 里。**

也就是说，它不是自己重新实现一个复杂的终端系统，而是利用 Linux/macOS 上成熟的 `tmux` 来管理长期会话。

典型结构如下：

```text
VPS / Linux Box / macOS Workstation
│
├── tmux session: lfg-001
│   └── Claude Code 正在处理 API 项目
│
├── tmux session: lfg-002
│   └── Codex 正在审查认证代码
│
├── tmux session: lfg-003
│   └── OpenCode 正在修改文档
│
└── lfg Web Server
    └── Web UI / PWA 控制面板
```

Web UI 会把这些 tmux 会话抽象成一张“任务卡片”面板。

每张卡片可能展示：

- 使用的代理类型
- 当前项目目录
- 当前 Git 分支
- 当前状态：Working / Idle / Awaiting input
- 输出 transcript
- 是否需要用户审批
- attach 到原始 tmux 的入口
- stop 停止任务的按钮

##### 1.4 主要特性

根据官网、GitHub README 和作者推文，lfg 的核心特性包括：

###### 1. 并行运行多个编码代理

可以同时启动多个 AI coding agents，每个 agent 都在自己的 tmux 会话中运行。

示例：

```text
CLAUDE-CODE opus    ~/atlas/api    feat/sql     Working
CLAUDE-CODE sonnet  ~/atlas        main         Awaiting approval
CODEX gpt-5-codex   ~/atlas/jobs   main         Plan ready
OPENCODE qwen3      ~/atlas/docs   main         Awaiting input
```

这使得开发者可以把不同任务分配给不同代理：

- 一个 agent 写后端接口
- 一个 agent 修 bug
- 一个 agent 写测试
- 一个 agent 做代码审查
- 一个 agent 更新文档

---

###### 2. Web UI / PWA 远程控制

lfg 提供一个可安装的 PWA Web 应用。

你可以从：

- 手机
- 平板
- 笔记本
- 任意在 tailnet 内的设备

访问控制面板。

这意味着你不需要一直开着主力电脑。  
作者在推文中说：

> 已经一个月没怎么用 MacBook 了，因为多个编码代理都运行在 VPS 上。

---

###### 3. 自托管与隐私优先

lfg 的设计不是默认暴露在公网，而是：

- 服务默认绑定到 `127.0.0.1`
- 推荐通过 **Tailscale** 访问
- 使用 `tailscale serve` 暴露给自己的 tailnet
- 不开放公网端口

官网强调：

> Tailnet-only, no public ports.

GitHub README 也明确提醒：

> lfg 的控制 API 默认没有认证，因为它假设只运行在 loopback，并通过 Tailscale 私有访问。不要直接暴露到公网。

---

###### 4. 使用真实的本地 CLI 和凭证

lfg 不内置 Claude、Codex 或 OpenCode 二进制文件，而是使用你机器上已经安装、已经认证过的 CLI。

例如：

- `claude`
- `codex`
- `opencode`

也就是说，lfg 运行代理的环境就是你自己的机器环境：

- 使用你的代码仓库
- 使用你的 Git 配置
- 使用你的 SSH key
- 使用你的 CLI 登录态
- 使用你的 API key
- 使用你的项目依赖和本地工具链

这也是它的优势和风险所在。

---

###### 5. Insight agents / 自动化仓库检查

除了普通编码代理，lfg 还支持一种可选能力：

> markdown-defined insight agents

这些 agent 可以自动收集和分析：

- Git 状态
- 仓库上下文
- GitHub 信息
- 模型信息
- 安全相关上下文
- 项目报告

它更像是一些“分析型代理”或“巡检代理”，不一定直接写代码，而是帮助开发者理解项目状态。

---

###### 6. 语音代理与推送通知

作者推文中提到：

- 语音代理管理所有代理
- PWA 推送通知
- 多个代理之间可以互相感知

这些能力在官网和 README 中不是最核心的安装入口，但可以看出 lfg 的长期方向：

> 不只是远程看终端，而是逐渐变成一个多 agent 编排系统。

#### 2. 深入浅出解读

##### 2.1 可以把 lfg 理解成什么？

可以把 lfg 类比成：

> **AI 编码代理版的“远程任务中控台”。**

如果说以前你是在本地终端里手动运行：

```bash
claude
codex
opencode
```

那么 lfg 是把这些终端会话收集起来，变成一个可视化控制面板。

你不再需要在多个终端窗口之间切换，而是在一个网页里看到：

- 谁在工作
- 谁卡住了
- 谁需要你批准
- 谁已经完成
- 谁可以停止
- 谁可以继续

---

##### 2.2 为什么 tmux 很重要？

tmux 是 lfg 的关键基础设施。

因为 tmux 的特点是：

- 会话可以长期存在
- 断开 SSH 后任务仍然运行
- 可以随时重新 attach
- 适合远程服务器
- 可以同时管理多个窗口和任务

lfg 用 tmux 的好处是：

1. **稳定可靠**  
   即使 Web UI 出问题，底层会话还在。

2. **可逃生**  
   如果面板不能用，你仍然可以 SSH 到服务器：

   ```bash
   tmux attach -t lfg-<id>
   ```

3. **不锁死在 lfg 生态中**  
   它只是管理真实终端，不是完全封闭的执行环境。

4. **适合长时间 AI 编码任务**  
   AI agent 修改代码、跑测试、等审批，往往需要长时间挂着。

---

##### 2.3 为什么适合跑在 VPS 上？

AI 编码代理越来越像“后台员工”：

- 它们可以连续工作
- 可以处理多个任务
- 可以等待用户输入
- 可以自己运行命令
- 可以修改项目文件

如果这些都依赖本地笔记本，就会遇到：

- 合盖后断掉
- 网络变化
- 电量问题
- 本地资源占用
- 无法随时查看
- 多任务管理混乱

VPS 的优势是：

- 24 小时在线
- 网络稳定
- 可以远程访问
- 适合长期运行 tmux
- 不占用主力电脑
- 可以把代码仓库直接 clone 在服务器上

所以作者说自己一个月没怎么用 MacBook，本质是：

> 他把开发执行环境从笔记本迁到了云端服务器，笔记本和手机只变成了控制终端。

---

##### 2.4 它和 GitHub Codespaces / Cursor / Devin 有什么不同？

可以简单比较：

| 工具 | 核心形态 | 是否自托管 | 适合场景 |
|---|---|---|---|
| Cursor | 本地 AI IDE | 否 / 本地为主 | 人机协作写代码 |
| GitHub Codespaces | 云端开发环境 | 托管服务 | 云端 IDE 和开发容器 |
| Devin 类产品 | AI 软件工程师平台 | 通常 SaaS | 高级自动化任务 |
| Claude Code / Codex CLI | 单个终端代理 | 本地或远程均可 | 命令行 AI 编码 |
| **lfg** | 多代理控制平面 | **是** | 自己管理多个 AI 编码代理 |

lfg 的特别之处是：

- 它不是 IDE
- 它不是模型
- 它不是 SaaS 平台
- 它不是单个 coding agent

它更像是：

> 把你已有的命令行 AI coding agents 组织起来，远程化、面板化、多任务化。

---

##### 2.5 为什么强调 Tailscale？

因为 lfg 的安全模型依赖私有网络。

README 里明确说：

> 控制 API 是 unauthenticated by design。

也就是说，lfg 自身默认没有传统的登录鉴权系统。

原因是它假设：

- 只监听 `127.0.0.1`
- 不直接暴露公网
- 通过 Tailscale tailnet 私有访问

这带来的好处是配置简单，但也意味着：

> 如果你把 lfg 直接暴露到公网，风险非常高。

因为 lfg 能控制 AI agent，而 AI agent 有 shell 访问能力。

一旦公网被别人访问，别人可能通过你的 lfg：

- 查看代码
- 执行命令
- 修改文件
- 读取环境变量
- 使用你的 API key
- 使用你的 GitHub/SSH 凭证

所以 lfg 的正确使用方式应该是：

```text
手机 / 电脑
   ↓
Tailscale 私有网络
   ↓
VPS 上的 lfg
   ↓
tmux 中的 AI coding agents
   ↓
你的代码仓库和系统环境
```

而不是：

```text
公网用户
   ↓
直接访问 lfg 端口
   ↓
高危
```

#### 3. 典型使用场景

##### 场景一：多项目并行开发

你可以让多个 agent 分别处理不同仓库：

- agent D：写测试
- agent E：做安全审查

你只需要在手机或电脑上看面板，处理它们的确认请求。

---

##### 场景二：长时间后台任务

比如让 Claude Code 重构一个模块。

这种任务可能需要：

- 读代码
- 制定计划
- 修改文件
- 跑测试
- 根据错误继续修复
- 等你批准某些高风险操作

放在本地笔记本可能不方便。  
放在 VPS + tmux 中则更自然。

---

你在外面时也可以：

- 查看 agent 进度

- 让某个 agent 继续执行
- 接收 PWA 通知

这让开发者的角色从“亲自坐在电脑前写代码”，转向：

> 像项目经理一样调度多个 AI 编码工人。

---

##### 场景四：仓库巡检和报告

通过 insight agents，可以自动生成一些上下文报告，例如：

- 当前仓库是否有未提交变更
- 最近 GitHub issue 或 PR 状态
- 依赖或安全风险
- 模型价格变化
- 项目结构分析

这类能力适合日常维护和自动化检查。

##### 4.1 设计简单务实

lfg 没有一开始就做复杂的容器编排或多租户平台，而是利用：

- 本地 CLI

这些成熟组件组合成一个实用系统。

---

##### 4.2 不绑定单一模型或代理

它支持 Claude Code、Codex、OpenCode 等多个代理工具。

这意味着用户可以根据任务选择：

---

##### 4.3 自己掌控环境

相比完全托管的 SaaS，lfg 运行在自己的机器上。

你可以控制：

- 代码在哪里
- 凭证在哪里
- 网络怎么暴露
- 哪些 CLI 可用
- 哪些模型可用
- 数据如何流转

---

##### 4.4 很适合 AI 编码代理的发展趋势

从作者引用的推文来看，有一种趋势判断：

> 未来很多开发者会把代码代理从笔记本迁到远程机器上。

原因很简单：

AI agent 越来越像长期运行的“开发进程”，而不是一次性命令。

因此，需要一个中控系统来管理这些 agent。  
lfg 正是在这个方向上的早期探索。

#### 5. 风险与注意事项

##### 5.1 不要暴露公网

这是最重要的一点。

lfg 的控制 API 默认没有认证，不适合直接公网访问。

推荐做法：

- 保持 `LFG_HOST=127.0.0.1`
- 使用 Tailscale
- 不开放公网端口
- 如部署到 Railway/Fly/Render 等平台，应关闭 public networking 或自行加认证层

---

##### 5.2 AI agent 有 shell 权限

lfg 启动的 agent 是在你的机器上执行命令。

这意味着它们可能：

- 修改代码
- 删除文件
- 运行安装脚本
- 访问环境变量
- 使用本地凭证

所以应该谨慎选择运行环境。

建议：

- 最好使用专门的 VPS
- 不要放过多敏感凭证
- 使用独立的 SSH key 和 GitHub token
- 控制仓库权限
- 定期审查 agent 的改动
- 对高风险命令保持人工审批

---

##### 5.3 项目仍处于早期

从 GitHub 提交数量、作者推文和 README 可以看出，lfg 已经开源，但仍可能有 bug。

作者也提到：

> 还没有完全准备好，预计会有 bug，欢迎提交 issue。

所以它更适合：

- 技术尝鲜者
- 熟悉 VPS、tmux、Tailscale 的开发者
- 愿意折腾 AI coding workflow 的用户

不一定适合完全无运维经验的人直接用于关键生产环境。

#### 7. 最核心的理解

lfg 的价值不在于“又做了一个聊天界面”，而在于它抓住了 AI 编码代理的一个关键变化：

> 编码代理正在从一次性的终端工具，变成可以长期运行、并行工作、需要被调度的开发劳动力。

当你只有一个 agent 时，一个终端就够了。  
当你有五个、十个 agent 同时工作时，就需要一个控制平面。

lfg 正是这个控制平面：

```text
你
↓
Web / PWA 控制台
↓
lfg
↓
多个 tmux 会话
↓
Claude Code / Codex / OpenCode
↓
你的代码仓库
```

它让开发者从“亲自操作每个终端”，转向“管理一组 AI 编码代理”。

**lfg 是一个面向未来 AI 编程工作流的自托管多代理控制平台。**

- 自托管
- VPS
- tmux
- Tailscale
- PWA
- 多 agent 并行
- Claude Code / Codex / OpenCode
- 私有控制平面
- 远程开发调度

如果你已经在频繁使用 AI coding agents，并且希望它们能长期、并行、远程运行，那么 lfg 是一个非常值得关注的开源项目。

但使用时必须牢记：

> **不要公网暴露。不要随便给不可信 agent 过高权限。最好运行在隔离的专用机器上。**
