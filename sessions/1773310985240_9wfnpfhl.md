**If OpenClaw is an *employee*, Paperclip is the *company***

Paperclip is a Node.js server and React UI that orchestrates a team of AI agents to run a business. Bring your own agents, assign goals, and track your agents' work and costs from one dashboard.

It looks like a task manager — but under the hood it has org charts, budgets, governance, goal alignment, and agent coordination.

**Manage business goals, not pull requests.**

**01** Define the goal *"Build the #1 AI note-taking app to $1M MRR."*

**02** Hire the team CEO, CTO, engineers, designers, marketers — any bot, any provider.

**03** Approve and run Review strategy. Set budgets. Hit go. Monitor from the dashboard.

#### Features

Any agent, any runtime, one org chart. If it can receive a heartbeat, it's hired. Every task traces back to the company mission. Agents know *what* to do and *why*.

##### 💓 Heartbeats

Agents wake on a schedule, check work, and act. Delegation flows up and down the org chart.

Monthly budgets per agent. When they hit the limit, they stop. No runaway costs.

##### 🏢 Multi-Company

One deployment, many companies. Complete data isolation. One control plane for your portfolio. Every conversation traced. Every decision explained. Full tool-call tracing and immutable audit log.

##### 🛡️ Governance

You're the board. Approve hires, override strategy, pause or terminate any agent — at any time. Hierarchies, roles, reporting lines. Your agents have a boss, a title, and a job description. Monitor and manage your autonomous businesses from anywhere.

Without Paperclip With Paperclip

❌ You have 20 Claude Code tabs open and can't track which one does what. On reboot you lose everything. ✅ Tasks are ticket-based, conversations are threaded, sessions persist across reboots.

❌ You manually gather context from several places to remind your bot what you're actually doing. ✅ Context flows from the task up through the project and company goals — your agent always knows what to do and why.

❌ Folders of agent configs are disorganized and you're re-inventing task management, communication, and coordination between agents. ✅ Paperclip gives you org charts, ticketing, delegation, and governance out of the box — so you run a company, not a pile of scripts.

❌ Runaway loops waste hundreds of dollars of tokens and max your quota before you even know what happened. ✅ Cost tracking surfaces token budgets and throttles agents when they're out. Management prioritizes with budgets.

❌ You have recurring jobs (customer support, social, reports) and have to remember to manually kick them off. ✅ Heartbeats handle regular work on a schedule. Management supervises.

❌ You have an idea, you have to find your repo, fire up Claude Code, keep a tab open, and babysit it. ✅ Add a task in Paperclip. Your coding agent works on it until it's done. Management reviews their work.

Paperclip handles the hard orchestration details correctly.

**Atomic execution.** Task checkout and budget enforcement are atomic, so no double-work and no runaway spend.

**Persistent agent state.** Agents resume the same task context across heartbeats instead of restarting from scratch.

**Runtime skill injection.** Agents can learn Paperclip workflows and project context at runtime, without retraining.

**Governance with rollback.** Approval gates are enforced, config changes are revisioned, and bad changes can be rolled back safely.

**Goal-aware execution.** Tasks carry full goal ancestry so agents consistently see the "why," not just a title.

**Portable company templates.** Export/import orgs, agents, and skills with secret scrubbing and collision handling.

**True multi-company isolation.** Every entity is company-scoped, so one deployment can run many companies with separate data and audit trails.

**Not a chatbot.** Agents have jobs, not chat windows.

**Not an agent framework.** We don't tell you how to build agents. We tell you how to run a company made of them.

**Not a workflow builder.** No drag-and-drop pipelines. Paperclip models companies — with org charts, goals, budgets, and governance.

**Not a prompt manager.** Agents bring their own prompts, models, and runtimes. Paperclip manages the organization they work in.

**Not a single-agent tool.** This is for teams. If you have one agent, you probably don't need Paperclip. If you have twenty — you definitely do.

**Not a code review tool.** Paperclip orchestrates work, not pull requests. Bring your own review process.

#### Quickstart

Open source. Self-hosted. No Paperclip account required.

```
npx paperclipai onboard --yes
```

Or manually:

```
git clone https://github.com/paperclipai/paperclip.git
cd paperclip
pnpm install
pnpm dev
```

This starts the API server at `http://localhost:3100`. An embedded PostgreSQL database is created automatically — no setup required.

> **Requirements:** Node.js 20+, pnpm 9.15+

#### FAQ

**What does a typical setup look like?**Locally, a single Node.js process manages an embedded Postgres and local file storage. For production, point it at your own Postgres and deploy however you like. Configure projects, agents, and goals — the agents take care of the rest.

If you're a solo-entreprenuer you can use Tailscale to access Paperclip on the go. Then later you can deploy to e.g. Vercel when you need it.

**Can I run multiple companies?**Yes. A single deployment can run an unlimited number of companies with complete data isolation.

**How is Paperclip different from agents like OpenClaw or Claude Code?**Paperclip *uses* those agents. It orchestrates them into a company — with org charts, budgets, goals, governance, and accountability.

**Why should I use Paperclip instead of just pointing my OpenClaw to Asana or Trello?**Agent orchestration has subtleties in how you coordinate who has work checked out, how to maintain sessions, monitoring costs, establishing governance - Paperclip does this for you.

(Bring-your-own-ticket-system is on the Roadmap)

**Do agents run continuously?**By default, agents run on scheduled heartbeats and event-based triggers (task assignment, @-mentions). You can also hook in continuous agents like OpenClaw. You bring your agent and Paperclip coordinates.

## 结构化（2）

### 2026-03-12 10:23:05

**主旨概括：**  
Paperclip 是一个开源、自托管的 “AI 公司编排系统”，不是单个 AI 助手，而是用来统一管理一群 AI 代理（agents）协同工作的 “公司操作台”。它的核心目标是：**让你管理业务目标，而不是盯着一个个机器人和任务窗口。**

---

##### 1. 这是什么：Paperclip 的定位
- Paperclip 由**Node.js 服务端 + React 界面**组成，用来编排多个 AI 代理像公司团队一样工作。  
- 它支持 “自带代理” 模式：你可以接入**OpenClaw、Claude Code、Codex、Cursor、Bash、HTTP**等各种代理 / 运行时。  
- 官方一句话定位很直白：  
  - **如果 OpenClaw 是员工，那 Paperclip 就是公司。**

**例子：**  
你可以设定目标 “把 AI 笔记应用做到**100 万美元月经常性收入（$1M MRR）**”，然后给它配 CEO、CTO、工程师、设计师、营销等 AI 角色，由系统统一调度。

---

##### 2. 它解决什么问题：为什么需要它
文章强调，很多人在同时开着很多 AI 工具窗口时会失控，Paperclip 就是为了解决这种混乱。

###### 原有痛点
- 同时开**20 个 Claude Code 终端 / 标签页**，根本记不住谁在干什么。  
- 重启后上下文丢失，要手动重新喂背景信息。  
- 代理配置分散在文件夹里，任务管理、协作、沟通都要自己拼。  
- AI 可能失控循环，白白烧掉**几百美元 token 成本**。  
- 周期性工作（客服、社媒、报表）还得人工触发。

###### Paperclip 的改进
- 把工作变成**工单 / 任务制**，会话可持续保存。  
- 上下文会从任务一路关联到项目和公司目标，让代理知道 “做什么、为什么做”。  
- 自带组织架构、任务分配、委派、治理能力。  
- 能监控成本、设置预算，超额自动停下。  
- 用**heartbeat（心跳调度）**自动执行周期性工作。

---

##### 3. 核心能力：像经营公司一样管理 AI
Paperclip 的能力重点不是 “让 AI 更聪明”，而是 “让 AI 团队更可控”。

###### 3.1 组织与目标管理
- 支持**组织架构图（org chart）**、角色、汇报关系。  
- 每个任务都能追溯到公司使命，保证目标一致。  
- 强调 “管理业务目标，不是 pull request”。

###### 3.2 Heartbeats：定时唤醒代理
- 代理会按计划被唤醒，检查工作并继续执行。  
- 支持沿组织结构向上 / 向下委派任务。  
- 适合处理固定频率工作，比如日报、客户支持、营销发布。

###### 3.3 预算与成本控制
- 可按**每个代理设置月度预算**。  
- 一旦到达上限，代理会停止，避免成本失控。  
- 文章重点强调：能避免 “失控循环” 造成的高额 token 消耗。

###### 3.4 治理与审计
- 所有对话、决策、工具调用都有追踪。  
- 提供**不可变审计日志**。  
- 你像董事会一样，可以随时：
  - 批准招聘
  - 覆盖策略
  - 暂停或终止任意代理

###### 3.5 多公司管理
- **一次部署可运行多个公司**。  
- 各公司之间**数据完全隔离**，但共用一个控制面板。  
- 适合同时管理多个 AI 项目 / 业务。

---

##### 4. 设计亮点：它比普通任务板更进一步
文章列出了一些底层编排能力，这些是它和通用项目管理工具的差别。

- **原子执行**：任务领取和预算扣减是原子的，避免重复干活、重复花钱。  
- **持久化代理状态**：代理跨 heartbeat 能延续上下文，而不是每次从头开始。  
- **运行时技能注入**：代理可以在运行时学会 Paperclip 工作流和项目背景，不必重新训练。  
- **带回滚的治理**：配置变更有版本记录，出问题可安全回滚。  
- **目标感知执行**：任务带有完整目标链路，代理不只是看到标题，而是知道背后的原因。  
- **可移植公司模板**：可导入导出组织、代理、技能，并处理敏感信息和冲突。  
- **真正多公司隔离**：所有实体都按公司维度隔离。

---

##### 5. 它不是什么：避免误解
文章明确说，Paperclip **不是**下面这些东西：

- **不是聊天机器人**：代理是 “有岗位的员工”，不是聊天窗口。  
- **不是 Agent 开发框架**：它不教你怎么造代理，而是教你怎么运营一家公司。  
- **不是工作流拖拽器**：没有 drag-and-drop 流程编排，核心是组织、目标、预算和治理。  
- **不是 Prompt 管理器**：代理自己的 prompt、模型、运行时由你决定。  
- **不是单代理工具**：如果你只有 1 个代理，可能用不上；如果有**20 个**，价值就很明显。  
- **不是代码审查工具**：它管理工作协同，不替代 PR review 流程。

    - 预算控制：每个代理可设置月预算，超限即停止
    - 多公司支持：一次部署可管理多个公司，且数据完全隔离
    - 审计追踪：每次对话、决策、工具调用都有记录，且有不可变审计日志
    - 治理能力：你像董事会一样可随时审批招聘、调整策略、暂停或终止代理
    - 层级管理：代理有上级、职位、职责和汇报关系

- 4. 它为什么和普通任务工具、聊天工具不同
  - 文章明确说，Paperclip 不是：
    - 聊天机器人：代理有“岗位”，不是聊天窗口
    - Agent 开发框架：它不负责教你怎么造代理，而是帮你运营代理公司
    - 工作流搭建器：不是拖拖拽拽的 pipeline，而是公司模型
    - Prompt 管理器：代理自己的 prompt、模型、运行时由你决定
    - 单代理工具：如果你只有 1 个代理，可能不需要；如果有 `20 个`，就很需要
    - Code Review 工具：它编排工作，不替代你自己的审查流程
  - 它和 Asana、Trello 这类工具的区别在于：更关注代理协作里的细节，比如任务 checkout、会话持续、成本控制和治理机制。

- 5. 技术实现上的几个亮点
  - 文中强调了一些“编排细节”：
    - 原子执行：任务 checkout 和预算控制是原子的，避免重复干活和失控支出
    - 持久状态：代理在下一次 heartbeat 时能续上之前上下文，而不是从头开始
    - 运行时技能注入：代理可在运行过程中学会 Paperclip 工作流和项目上下文
    - 带回滚的治理：审批门槛强制执行，配置变更可版本化并安全回滚
    - 目标感知执行：任务会携带完整目标链路，代理知道“为什么做”
    - 可移植公司模板：组织、代理、技能可导入导出，并处理密钥脱敏和冲突
    - 真正的多公司隔离：同一部署下，每家公司都有独立数据和审计轨迹

- 6. 如何使用与部署

## 产品-技术开发（1）

### 2026-03-16 09:50:06

这是一个很有代表性的“Agent OS / AI 公司操作系统”产品，不是在做单个 Agent 能力，而是在做“多 Agent 的组织层”。

**核心判断**
- Paperclip 的产品定位非常清晰：不和 Claude Code / Codex / OpenClaw 竞争，而是做它们之上的“公司级调度与治理层”。
- 真正的创新点不在模型，而在 5 个系统能力：`组织建模`、`任务编排`、`预算治理`、`状态持久化`、`可审计性`。
- 这类产品一旦做对，价值不来自“更聪明的 Agent”，而来自“把不可靠 Agent 变成可管理的生产系统”。

**从产品角度看，为什么这个方向成立**
- 用户痛点抓得准：多终端、多 Agent、多任务并行时，最大问题不是生成质量，而是`失控`、`断上下文`、`重复执行`、`成本失真`。
- 它把“聊天”重构成“组织协作”：用户不再盯 prompt，而是盯 `目标、角色、预算、审批、进度`，这更接近企业真实管理方式。
- “Goal-aware execution” 很关键：任务不只是 ticket，而是挂在公司目标树上。这样 Agent 拿到的是“做什么 + 为什么做”，比普通任务系统更适合自主执行。
- “Multi-company isolation” 说明它不是 demo，而是朝 SaaS/control plane 方向设计，天然考虑多租户与治理边界。

**产品设计上的最佳实践**
- `组织视图优先于对话视图`
  - 不要把 UI 做成聊天窗口集合。
  - 应优先展示：公司目标树、组织架构、任务流、预算消耗、审批队列、异常告警。
  - 例子：CEO Agent 看到季度目标与部门 KPI；Engineer Agent 看到当前 checkout 的任务、依赖、预算余额、最近一次 heartbeat 结果。
- `把“人类介入点”设计成少数高价值节点`
  - 不要让用户频繁盯执行过程，而是只在以下节点介入：新 agent 上岗、预算超限、策略变更、外部发布、任务卡死。
  - 例子：产品经理只审批“上线 PRD”“增加月预算”“终止异常 Agent”，其余由系统自动推进。
- `预算是产品主交互，不是后台报表`
  - 很多 AI 产品把 cost analytics 放最后，这里应该放到核心流程。
  - 例子：给每个 Agent 设置 `monthly_budget + per_task_cap + escalation_threshold`，UI 上直接显示“本周 ROI 最低的 3 个 Agent”。
- `任务必须有责任链`
  - 任何任务要能追溯：谁创建、谁委派、谁执行、为什么执行、花了多少钱、用了什么工具。
  - 例子：一个“做竞品调研”任务，能追到来自 CMO 的增长目标，而不是孤立卡片。

**技术架构上最值得肯定的点**
- `Heartbeat` 机制非常合理
  - 这比常驻无限循环 Agent 更工程化。定时唤醒 + 事件触发，能显著降低空转成本和失控风险。
  - 适合大部分企业任务：巡检、跟进、复盘、补全、汇报。
- `原子 checkout + 预算扣减`
  - 这是编排系统的关键，不然会出现两个 Agent 抢同一任务，或执行后才发现超预算。
  - 这是从“玩具 Agent 框架”走向“生产系统”的分水岭。
- `持久化状态`
  - Agent 跨 heartbeat 恢复上下文，比每次重新喂 prompt 更省 token，也更稳定。
  - 这意味着系统在设计上已经承认：上下文是业务资产，不只是模型输入。
- `审计日志 + tool tracing`
  - 对企业级 AI，trace 不是调试功能，而是治理能力。
  - 尤其在跨 Agent 委派、外部 API 调用、代码变更、预算消耗时，这是必须品。

**落地实现时的最佳实践例子**

**1. 任务编排模型**
- 推荐任务实体至少包含：
  - `task_id`
  - `company_id`
  - `goal_id`
  - `owner_agent_id`
  - `status`
  - `priority`
  - `budget_cap`
  - `context_snapshot`
  - `checkout_lease_until`
  - `idempotency_key`
- 最佳实践：
  - 用 `lease` 而不是简单“已分配”字段，防止 agent crash 后任务永远卡住。
  - checkout 时数据库事务内完成：锁任务、校验预算、写审计、生成执行上下文。
- 例子：
  - Engineer Agent 心跳触发时，事务里拿到任务 `T123` 的 15 分钟 lease，并冻结本次最多 `$2` token 预算；超时未续租则任务回到队列。

**2. Agent 状态管理**
- 不要只存 message history，要分层存：
  - `长期身份`: 角色、职责、权限、技能
  - `中期项目状态`: 当前项目、目标树、关键决策
  - `短期执行状态`: 当前任务、最近工具调用、未完成步骤
- 最佳实践：
  - 长期状态结构化存数据库
  - 短期状态可存 checkpoint / summary
  - 进入 heartbeat 前动态组装上下文，避免原始聊天记录无限膨胀
- 例子：
  - CTO Agent 不需要每次带上所有历史对话，只需要：公司技术路线、当前 sprint 风险、过去 3 次架构决策摘要、当前待批事项。

**3. 成本控制**
- 推荐三层预算：
  - `agent 月预算`
  - `task 单次预算`
  - `action 单步预算`
- 最佳实践：
  - 执行前预估 token 成本，执行后回写真实成本，形成 `forecast vs actual`
  - 对高风险工具调用设置预算门槛和审批门槛
- 例子：
  - 市场分析 Agent 月预算 `$100`
  - 单个竞品报告任务预算 `$8`
  - 若一次网页抓取 + 总结预测超过 `$2`，则切换为低成本模型先粗筛。

**4. 审批与治理**
- 审批不要只做“人工同意按钮”，要做策略引擎。
- 推荐规则：
  - 改配置需要审批
  - 外部发布需要审批
  - 预算上调需要审批
  - 跨部门委派超过阈值需要审批
- 例子：
  - Designer Agent 产出 landing page 文案可以自动提交；
  - 但如果要直接推送官网 CMS，必须经过 Marketing Lead Agent 或人工审批。

**5. 工具接入层**
- “Bring your own agents” 的关键难点在接口统一，不是模型支持数量。
- 最佳实践：
  - 定义统一 `Agent Runtime Adapter`
  - 至少抽象这些能力：`send_task`、`receive_heartbeat`、`resume_session`、`cancel`、`get_usage`、`stream_events`
- 例子：
  - Claude Code、Codex、OpenClaw 都适配成统一心跳协议：
    - 输入：任务上下文、预算、权限、目标 ancestry
    - 输出：状态更新、工具调用记录、结果摘要、成本数据

**6. 多租户隔离**
- 如果真要支撑多公司，`company_id` 不能只是查询条件，必须进所有核心实体主键域。
- 最佳实践：
  - 每个实体都强制 company-scoped
  - 审计、文件、缓存、工具凭证都隔离
  - 管理后台也要做 tenant-aware tracing
- 例子：
  - Company A 的 CTO Agent 绝不能在向量检索、文件系统、日志查询里看到 Company B 的任何任务痕迹。

**这类产品最容易踩的坑**
- `把 orchestration 做成 prompt 拼接`
  - 这是最常见错误。真正的编排核心是状态机、事务、权限、预算，不是 prompt 模板。
- `过度依赖长期对话记忆`
  - 对生产系统，结构化状态比原始 message history 更可靠。
- `没有幂等设计`
  - heartbeat 重试、事件重复投递、Agent 超时重连都会导致重复执行。
- `只监控 token，不监控结果质量`
  - 成本可控不代表业务有效，必须加入任务完成率、返工率、审批驳回率、平均恢复时间等指标。
- `治理过晚`
  - 很多团队先把 Agent 跑起来，后面再加审计和权限，通常会推倒重来。

**如果我是产品/技术负责人，会这样演进**
- Phase 1：把“可控执行”做稳
  - 原子任务 checkout
  - 预算限制
  - 审计日志
  - 心跳恢复
- Phase 2：把“组织协作”做深
  - 上下级委派
  - 目标树对齐
  - 跨 Agent 依赖管理
- Phase 3：把“平台化”做出来
  - 插件系统
  - 第三方 ticket/knowledge base 接入
  - 模板化公司导入导出
- Phase 4：做商业化护城河
  - 行业模板市场（ClipMart）
  - 可复用角色/技能包
  - 企业级合规与 trace 分析

**一句话结论**
- Paperclip 本质上不是“让 Agent 更聪明”，而是“让一群不稳定的 Agent 以公司机制稳定协作”。  
- 它最有价值的地方，是把 AI 从“单点能力”推进到“组织操作系统”。

## 产品-最佳实践（1）

### 2026-03-16 09:52:33

可以。基于你给的 `paperclipai/paperclip` 内容，我用一个具体实例来讲：

**实例：用 Paperclip 运营一家“AI 会议纪要 SaaS”小公司**

目标是：
“在 6 个月内，做出一款 AI 会议纪要产品，并做到首批 100 个付费用户。”

公司里有这些 AI 代理：

- `CEO Agent`：拆解公司目标、排优先级、审查周计划
- `CTO Agent`：负责技术路线、架构和研发任务分配
- `Engineer Agent`：开发功能、修 bug、写测试
- `Designer Agent`：做 landing page、产品界面和品牌素材
- `Marketing Agent`：写博客、发社媒、做投放文案
- `Support Agent`：整理用户反馈、生成 FAQ、处理重复问题

这些 agent 都接入到 Paperclip，由它统一管理目标、预算、任务、审批和审计。

**在这个实例上的最佳实践**

- **先定义公司级目标，再定义任务**
  - 不要一上来给 `Engineer Agent` 一个“做登录页”的孤立任务。
  - 更好的做法是：先在 Paperclip 里定义公司目标，比如“提升试用转化率到 8%”，然后再挂出“优化 landing page 首屏”“增加 demo 视频”“补充用户证言”等任务。
  - 这样 agent 拿到任务时，能看到完整目标链路，知道自己不是在“做页面”，而是在“提高转化”。

- **按组织结构分工，不要让所有 agent 平级抢活**
  - 最佳做法不是把所有任务都直接发给工程 agent。
  - 应该像公司一样建 org chart：`CEO -> CTO -> Engineer`，`CEO -> Marketing`，`CEO -> Support`。
  - 例如发现“试用转化率低”时，`CEO Agent` 不直接让工程师改代码，而是先让 `Marketing Agent` 分析流量漏斗、让 `Support Agent` 汇总试用用户流失原因，再由 `CTO Agent` 生成研发需求。
  - 这样 Paperclip 的“上下级委派”才能发挥作用，避免 agent 各自乱跑。

- **给每个 agent 设月度预算和单任务上限**
  - 这是这个系统最重要的实践之一。
  - 比如：
    - `CEO Agent`：高权限，低频执行，中等预算
    - `Engineer Agent`：高频执行，较高预算
    - `Marketing Agent`：中频执行，严格限制实验预算
    - `Support Agent`：低成本、定时跑
  - 具体到这个实例，可以设：
    - 工程 agent 月预算 `$300`
    - 营销 agent 月预算 `$150`
    - 支持 agent 月预算 `$50`
  - 同时给单次 heartbeat 也设成本阈值，防止某个 agent 因为 prompt 循环或任务歧义烧掉太多 token。

- **把 heartbeat 用在“周期性经营动作”上，不要所有事都实时触发**
  - Paperclip 很适合做定时经营，而不只是“收到任务就执行”。
  - 在这个例子里：
    - `Support Agent` 每 2 小时汇总新反馈
    - `Marketing Agent` 每天上午生成内容草稿和渠道建议
    - `CEO Agent` 每周一审查上周指标并调整优先级
  - 最佳实践是：把重复性、节律性的工作交给 heartbeat；把高风险动作留给事件触发或人工审批。

- **高风险动作必须加治理和审批门**
  - Paperclip 强调 governance，这在真实业务里非常关键。
  - 在这个 SaaS 例子中，以下动作不应自动执行：
    - 修改定价
    - 删除用户数据
    - 发布生产环境变更
    - 大规模发送营销邮件
    - 更换公司级目标或预算
  - 最佳做法是让 agent 可以“提出建议”和“准备执行方案”，但关键动作必须进入审批状态，由你这个“board”来确认。

- **任务描述要写成“业务结果 + 约束”，不要只写动作**
  - 差的写法：`写一个 onboarding 页面`
  - 好的写法：`设计并交付一个 onboarding 页面，目标是让首次注册用户在 3 分钟内完成首个会议纪要生成；必须适配移动端；不得修改现有计费流程`
  - 因为 Paperclip 的强项是让 agent 理解“为什么做”，所以任务里一定要包含成功标准和边界条件。

- **让 Support Agent 成为公司的“事实收集器”**
  - 这个项目最容易忽略的一点，是客户反馈应该进入目标系统，而不是散落在聊天和文档里。
  - 比如 `Support Agent` 每天汇总：
    - 取消订阅原因
    - 试用用户卡点
    - 高频功能诉求
  - 然后在 Paperclip 中把这些反馈自动关联到“提升激活率”“减少流失率”等公司目标。
  - 这样 `CEO Agent` 和 `CTO Agent` 做决策时，看到的是可追踪的业务证据，而不是零散意见。

- **用审计日志复盘“为什么做出这个决策”**
  - 比如某周 `CEO Agent` 决定暂停“多语言功能”，转去优先做“Zoom 集成”。
  - 最佳实践不是只记录结果，而是保留完整链路：
    - 哪些用户反馈支持这个判断
    - 哪些指标出现下滑
    - 哪个 agent 提出了建议
    - 谁审批通过
  - Paperclip 的价值之一就在于“每次对话、每次工具调用、每次决策”都可追溯。这个能力应当被主动用于复盘，而不只是事后查错。

- **把 agent 当员工管理，不要当万能助手使用**
  - 这是这个项目传达的核心理念。
  - 在这个实例里，`Marketing Agent` 不应该去改数据库 schema，`Engineer Agent` 也不该负责品牌定位。
  - 最佳实践是给每个 agent 明确：
    - 岗位职责
    - 可用工具
    - 汇报对象
    - 预算
    - 触发频率
    - 是否需要审批
  - 角色越清晰，协作越稳定，越接近真实公司的运营方式。

**一个推荐的落地配置方式**

如果你刚开始用 Paperclip，可以先跑一个最小组织，而不是一口气上 10 个 agent：

- `CEO Agent`
- `CTO Agent`
- `Engineer Agent`
- `Marketing Agent`

先只围绕一个北极星目标运行：
`30 天内获得 20 个真实试用用户`

然后只设置 3 类任务：

- 产品开发：做出最小可用功能
- 增长验证：找到有效获客渠道
- 用户反馈：总结阻塞点并回流到 roadmap

这样能先验证：
- 任务是否被正确委派
- budget 是否合理
- heartbeat 是否太频繁
- 审批流是否拖慢关键动作

**一句话总结这个实例的最佳实践**

在 Paperclip 里，最优做法不是“让很多 AI 自动干活”，而是：
**把 AI 按公司结构组织起来，让所有任务都服务于公司目标，并用预算、审批、审计和心跳机制来约束执行。**
