#### 精炼总结

文章围绕 **“如何让大模型更可靠地参与软件开发”** 展开。Dex Horthy 的核心观点是：与其盲目增加模型调用和自动化程度，不如精心管理输入给模型的上下文、设计可验证的小循环，并在人类判断最有价值的位置设置检查点。

##### 1. Dex 的技术经历：长期关注“制造软件的系统”

- Dex 最初学习物理，后来因不喜欢学术道路而转向编程。高中时，他曾参与 NASA 喷气推进实验室项目，为月球南极探测车编写路径规划程序，实际写出了一个简化版的 Dijkstra 算法。
- 进入软件行业后，他很快发现：公司中价值最高的工作之一，不只是开发业务功能，而是建设 **CI/CD、沙盒环境、预览环境和开发者平台**，即“打造用来生产软件的系统”。
- 在 Replicated，他参与容器编排和本地部署平台建设，后来转向客户工程：
  - 约 **3个月促成12笔交易**；
  - 将客户工程团队扩展到约 **25人**；
  - 通过直接服务客户，提升了沟通、组织和产品判断能力。
- 他认为，工程师最好至少有一两年面向客户的经历，因为这能帮助其理解真实需求，而不只是完成技术任务。
- 2020 年，他联合创办数据工程公司 Metalytics，后来将公司方向转为 HumanLayer，并开始深入研究 AI Agent。

##### 2. “12 Factor Agents”：可靠 Agent 的核心是控制输入与流程

Dex 在研究 CrewAI、LangChain 等 Agent 框架时发现，许多真正为企业交付 AI 项目的工程师，最终会放弃高度抽象的框架，转而手写 API 调用，并把 Agent 设计成更可控的工作流或流水线。

他访谈了约 **100位 AI 工程师、创始人和开发者**，总结出“12 Factor Agents”原则，主要包括：

1. 自然语言也可以看作工具调用；
2. 自己管理提示词；
3. 自己管理上下文窗口；
4. 工具调用本质上是结构化输出；
5. 统一执行状态与业务状态；
6. 用简单 API 启动、暂停和恢复 Agent；
7. 让 Agent 通过工具调用联系人类；
8. 掌握工作流的控制权；
9. 将错误压缩后放回上下文；
10. 使用小而专注的 Agent；
11. 从任意事件触发 Agent；
12. 让 Agent 尽量无状态，并在用户所在的渠道中工作。

其中最重要的一点是：**模型输出质量主要取决于输入给它的 Token 是否准确、充分且组织合理。**

##### 3. 上下文工程：把各种 AI 抽象还原为“Token 输入与输出”

Dex 将“上下文工程”定义为：不只写好提示词，而是系统性决定 **哪些信息以什么顺序、什么形式进入模型上下文**，从而提高结果质量。

- RAG、记忆、对话历史、结构化输出和工具调用，看似是不同技术，本质上都是向模型传递 Token 的方式。
- 现成 Agent 和记忆框架通常能快速做到一个 **80分的演示产品**；但若要达到企业可用的 **95%或99%可靠性**，就必须深入管理上下文：
  - 放入什么信息；
  - 信息排列顺序；
  - 使用哪个模型；
  - 哪些任务拆成独立调用；
  - 哪些内容应检索、压缩或删除。
- 推荐采用“**先运行、再正确、最后优化速度**”的顺序：
  1. 先用能力最强的模型验证问题能否解决；
  2. 确认用户真的需要这一能力；
  3. 再通过上下文工程拆分任务，降低成本和延迟。
- 例如，一些子任务可能不需要昂贵的前沿模型，可以交给成本仅约为 Opus **千分之一**的 GPT OSS 12B；只把真正困难的部分留给最强模型。

核心原则是：**工程师时间通常比 Token 更昂贵，因此不要在需求尚未验证时过早优化。**

##### 4. Harness Engineering：优化 Agent 工作的整体环境

上下文工程关注单次模型调用的输入；Harness Engineering 则关注 Agent 每一次行动所处的完整环境。

Martin Fowler 将其分为两层：

- **内层 Harness**：Claude Code、Codex 等工具自身提供的文件读写、搜索、工具定义和接口。
- **外层 Harness**：团队针对代码库进行的定制，包括命令、MCP、Skills、开发环境、代码组织方式、浏览器和测试工具等。

其目标不是偶尔得到一次好结果，而是 **整体抬高 Agent 输出的下限**，让每一次调用都更稳定。

##### 5. 上下文过载：“窗口更长”不等于“模型更聪明”

即使模型支持 100 万 Token，也不代表它能同样准确地利用所有内容。

- 上下文越长，模型越难判断哪些信息对下一步最重要。
- 一项基于 2025 年模型的研究显示，前沿模型大约能同时遵循 **150～250条指令**，之后准确率会明显下降；新模型已有改善，但问题仍存在。
- 上下文工程需要同时管理两种预算：
  - **信息预算**：真正需要多少背景资料，例如只通过 RAG 获取相关页面，而非放入整本书；
  - **指令预算**：有多少规则需要模型同时遵循，是否存在冲突。
- 如果先让模型走一条路线，之后又要求完全推翻并换方向，旧轨迹仍会占用注意力并造成干扰。

Dex 将上下文粗略分为：

- **聪明区（Smart Zone）**：模型最能稳定利用的前部上下文。一般可把小模型的前约 **10万 Token**、较强模型的前约 **20万 Token**作为保守参考。
- **迟钝区（Dumb Zone）**：上下文继续增长后，模型更容易遗忘指令、反复试错或做出激进操作。

典型警告信号是：模型不断尝试不同修复方案，甚至开始删除环境文件或绕过测试。此时应停止当前会话，压缩已有结论，再开启新会话。

##### 6. Loop Engineering：让 Agent 在反馈中持续改进

Loop Engineering 的关键不是简单重复提示，而是为模型建立 **自动反馈和验证机制**，即“反压力（Back Pressure）”。

###### 有效循环的例子

- 修改代码；
- 运行编译、Linter、单元测试或 CI；
- 获取明确结果；
- 根据结果继续修复；
- 达成目标后停止。

Ralph Wiggum 技术是代表案例：开发者让 Sonnet 持续运行，约 **6周花费6000美元**，构建出一门面向 Gen Z 的编程语言，甚至实现了用自身语言编写的第二阶段编译器。之所以可行，是因为编程语言具有强可验证性：代码能否编译、程序能否运行，都能提供明确反馈。

###### Dex 更推荐“慢循环”

HumanLayer 团队会在夜间通过定时任务：

1. 运行 Linter 或代码质量工具；
2. 每次只修复一个问题；
3. 提交并推送代码；
4. 第二天让工程师审查一个小型 PR。

随着信心增加，可以逐步扩大到一次修复四个问题。这比一次生成一个 **6万行 PR** 更容易验证，也更安全。

##### 7. 全自动循环的风险：代码能运行，不代表长期可维护

Dex 曾在 **2025年7月**搭建一个“关灯运行”的全自动软件工厂，但到 **同年11月**就关闭了。

主要问题包括：

- 连续 **3～6个月**无人阅读 AI 生成的代码后，代码库会逐渐恶化；
- 新功能短期能通过测试，但架构耦合、接口设计和依赖关系会越来越混乱；
- 当复杂问题出现时，模型可能找不到根因，人类却已经不再理解代码。
- 其团队曾因一个主键在系统中被错误传递而出现问题。Opus 4.1 无法定位根因，工程师不得不花数天调查，并用约 **3周**重新熟悉三个月没认真阅读的代码库。

Dex 最初认为“偶尔花两周人工修复，也值得换取大部分时间不看代码”，后来改变了看法，因为 AI 让代码产量增长了约 **10倍甚至100倍**，技术债也会更快累积。

根本原因是：现有模型主要通过“修复问题并通过测试”的基准训练，而 **坏架构的代价通常要到3～6个月后才显现**，无法通过当下的单元测试衡量。

##### 8. 软件工厂：从 DevOps 自动化走向 Agent 自动化

“软件工厂”并非 AI 时代的新词：

- **1968年 NATO 会议**已提出，应像工厂一样组织编码、测试、验证和集成流程；
- DevOps 时代通过 CI/CD、Chef、Ansible、Puppet 等工具自动化基础设施；
- **2018年**，美国空军首席软件负责人提出“DevSecOps 工厂”，希望国防部从几个月或一年发布一次，提升到每天发布。

传统软件工厂的循环是：

> 工作项 → 工程师开发 → 代码审查 → CI/CD → 上线 → 用户反馈或监控告警 → 新工作项

AI 软件工厂则逐步用 Agent 替代其中部分人工步骤：

- Agent 从 Jira、Linear 或支持工单中获取任务；
- 在沙盒中编写代码；
- 自动运行测试和代码审查；
- 创建 PR；
- 甚至根据 Sentry、Datadog 告警直接尝试修复。

这会把原本需要数小时或数天的开发缩短到约十几分钟，但也会把瓶颈转移到 **代码审查、质量判断和长期维护**上。

##### 9. 自动化软件开发的三种选择

Dex 认为团队大致有三条路线：

1. **完全关灯运行**  
   让 Agent 自动开发、审查、测试和上线，人类不再读代码。速度最快，但容易积累大量“AI 垃圾代码”，只能期待下一代模型及时解决问题。

2. **人工审查每一行代码**  
   风险较低，但代码审查会成为新瓶颈，AI 可能只带来约 **30%～50%的生产力提升**。

3. **寻找人类最有杠杆的位置**  
   在实现前由人类参与需求、设计和架构讨论。例如提前花一小时规划，可能节省后续四小时返工。Dex 认为这种方式有机会实现 **2～3倍速度提升**，同时保持接近人工精心开发的 **99%质量水平**。

他的建议是：**可以自动化几乎所有环节，但不要轻易停止阅读和理解代码。**

##### 10. RPI 框架：研究、规划、实现

Dex 曾提出 RPI 流程：

1. **Research（研究）**：让多个子 Agent 阅读大量代码，生成约 1 万 Token 的研究文档，将原本可能需要 10 万 Token 的代码信息压缩。
2. **Plan（规划）**：根据研究结果和需求生成实施计划。
3. **Implement（实现）**：在新上下文中按计划持续工作，直到任务完成。

早期实践中，计划能让 Agent 工作更久，避免只生成一个首页就停止。但后来发现，过度详细的计划会带来“反杠杆”：

- 计划几乎写出了每一行将修改的代码；
- 人类先花20分钟审计划，再花20分钟审实际 PR；
- 计划与最终代码并不完全一致，相当于把审查工作做了两次。

因此，RPI 后来更强调 **设计决策和实施方向**，而不是提前生成完整代码差异。

##### 11. 规格驱动开发的局限：不要制造两个事实来源

“规格驱动开发”希望把规格当作源代码，再由 Agent 将规格“编译”为代码。但现实中常出现：

- 规格被修改；
- 代码也被直接修改；
- 两者逐渐不一致；
- 团队不得不额外维护同步机制。

Dex 的建议是：

- **代码始终作为最终事实来源**；
- 研究文档、设计文档和计划主要服务于当前任务；
- 任务结束后可以丢弃；
- 下次需要时重新生成，因为 Token 便宜，而人工判断和处理过期文档的成本更高。

##### 12. 有意压缩：让模型持续停留在“聪明区”

“频繁、有意地压缩上下文”是上下文工程的关键方法：

1. 让 Agent 阅读代码，将当前系统状态压缩为研究文档；
2. 将需求和人的意图压缩为设计文档；
3. 在新会话中结合两者制定实施步骤；
4. 再开启新的、干净的上下文执行。

这样可以分别压缩：

- **代码库当前状态**；
- **开发者的目标与设计意图**；
- **从现状到目标的实施路线**。

人类尤其应参与设计阶段，因为模型容易生成“横向计划”：先完成数据库层，再完成服务层、API 和前端，直到最后才能测试。更好的人工方式通常是“纵向切片”：

- 先做一个返回假数据的 API；
- 做出可体验的前端；
- 再接服务层和数据库；
- 最后逐步加入业务逻辑与错误处理。

这样每一步都能独立验证，也不必一次审查 2000 行代码。

##### 13. 对话轨迹也会影响模型行为

上下文质量不仅取决于长度，还取决于四个因素：

- 上下文大小；
- 信息是否正确；
- 是否缺少关键信息；
- Agent 之前采取过什么行动，即“轨迹”。

例如，模型第一次修改代码后主动运行并修复测试，那么它下一次更可能重复这一良好流程；如果它连续犯错，而用户不断责骂，它可能继续预测“下一步应该再犯一个错，让用户继续纠正”。

因此，当模型开始反复说“你完全正确”“你有理由质疑”，却仍继续犯同样的错误时，通常应当 **结束会话、提炼有效结论并重新开始**。

##### 14. “Token Harder”与“Token Smarter”

- **Token Harder**：追求最大化模型调用量，例如同时使用多个 Claude 账号、让 Agent 全天运行、尽可能生成更多代码。它优化的是局部资源利用率，而非最终交付价值。
- **Token Smarter**：在保留人类控制、品味和架构判断的前提下，让 AI 用在最有杠杆的位置，关注最终是否交付稳定、可维护且用户真正需要的软件。

“黑暗工厂”来自完全自动化的实体工厂：没有工人，所以连灯都不需要。软件中可以有局部的“黑暗循环”，例如代码审查 Agent 发现问题后自动交给开发 Agent 修复；但将整个软件系统变成无人理解、无人审查的黑盒，当前仍然风险很高。

##### 核心结论

> **AI 软件开发的关键不是生成尽可能多的代码，而是让正确的信息进入模型、让每一步都能被验证，并在人类判断最有价值的位置保留控制权。**

上下文工程、Harness Engineering 和 Loop Engineering 都值得使用，但应从小而可控的循环开始，通过有意压缩维持上下文质量，并避免为了自动化而牺牲架构、可维护性和团队对系统的理解。

#### 从“让软件构建软件”到重新打开工厂的灯：Dex Horthy 的上下文工程实践

Dex Horthy 对 AI 编程的理解，来自一条持续十多年的主线：先研究怎样建立高杠杆的软件生产系统，再亲手把这种系统推进到几乎无人值守，最后从一次持续数月的失败中重新确认人的判断、代码设计与上下文控制仍然不可替代。

##### 从月球南极寻路开始，他迷上了“构建那个用来构建东西的东西”

Dex 本科读的是物理，但很快发现自己不喜欢学术道路。当时物理专业毕业后的常见选择并不多：读博士、进入金融业，或者转向编程。他想起了高中时在加州喷气推进实验室参与的一次实习。

NASA 研究人员当时刚拿到一份精度很高的月球南极地形数据。月球南极的一些陨石坑极深，因为角度关系，坑底从未见过阳光，那里保存着月球形成时期留下的冰冻水，科学家希望让探测车进入这些区域。问题是，探测车有明确的最大上坡和下坡坡度限制，软件必须从 A 点到 B 点找出一条不会突破这些限制的路线。

当时只有17岁的 Dex 没有读过计算机科学教材，最后写出了一个非常朴素、也很糟糕的 Dijkstra 寻路算法版本。但这段经历让他确认，自己确实喜欢编程。进入大学后，他修了大约一半的计算机辅修课程，随后加入芝加哥的软件公司 Sprout Social，在 API 平台团队工作，从此没有再回到物理学道路。

入职两三个月后，他注意到，公司里最有价值的人往往是最早加入的工程师。他们知道系统的每一部分在哪里，一个新人可能花一天处理的客户支持问题，他们五分钟就能解决。与此同时，真正能放大整个工程团队产出的工作，来自开发者平台、CI/CD、沙箱和预览环境。

Dex 从那时起开始痴迷于“软件工厂”。很多工程师不愿碰 CI/CD，觉得这类工作麻烦，他却把它理解为“构建那个用来构建东西的东西”，甚至是“构建那个用来构建那个构建东西的东西”。在他看来，工程师本来就倾向于寻找高杠杆做法：如果做一个工具能够让之后所有开发都变快，那么这正是“懒惰的工程师”最值得投入时间的地方。

他后来进入 Aspiration，仍然负责平台工程。入职约三个月，招聘他的工程副总裁离开，他一度承担类似代理 CTO 的职责，招聘过几个人，也帮助公司找到新的工程负责人。不过在那里待了约一年后，他决定自己大概不适合消费业务，更像是一个 B2B 从业者。

##### 在 Replicated 的客户现场，他从修流水线转向解决最后一公里

接下来，Dex 在 Replicated 工作了约四年。最初两年，他参与核心工程，团队在 Kubernetes 和 Docker Swarm 尚未真正成熟时，自行构建了一个容器编排器。创始团队的判断是，Docker 会让本地部署软件更容易：重点不一定是把应用装进某个机房机架，而是“把应用带到数据所在的地方”，不必把数据交给云端供应商。

他们设想的是一种类似 GitHub Enterprise 的体验。客户安装软件后，可以通过管理面板操作，GitHub 则运行在客户自己的数据中心里，代码不必离开那里。Replicated 希望把这种能力做成一个通用平台，让更多 SaaS 产品可以被打包，运行在客户自己的 AWS VPC、本地数据中心或其他受控环境中。

但 Dex 与 CTO 经常围绕“软件工厂”发生分歧。他手里明明有产品功能工单，却总觉得 CI 太慢、构建方式太多、流水线频繁损坏，因此想先修构建系统，再做分配下来的任务。管理者不得不告诉他：不要再修构建流水线了，先把工单做完。

后来公司与销售负责人分开，Dex 转向客户侧工程。他喜欢 Replicated 的客户，其中包括 HashiCorp、DataStax、Puppet、Travis CI 和 CircleCI。这些公司里的工程师正在处理一种困难的最后一公里问题：怎样把一个已经运行三到五年的 SaaS 平台完整打包，让不了解内部架构的人也能在自己的环境里可靠运行。

Dex 成为团队第一个真正面向客户的工程师。大约三个月里，他几乎见了销售管道中所有迟迟没有进展的潜在客户，最终促成了12笔交易。CEO 对他说，投资人又开始接他的电话了；虽然知道 Dex 想回去写代码，但公司需要他招聘三个人，把这支队伍建立起来，因为他可能天生适合做这件事。

他最终把团队扩展到约25人。此后，公司发现，用大量聪明人深入客户现场，确实有利于销售和留存，却无法产生理想的利润率。真正需要解决的是产品可用性：产品应该更自助、更接近产品驱动增长，不应要求每个客户都由专家手把手教会。

Dex 因此转做产品经理。他已经在客户现场待了四年，积累了一长串路线图意见，知道哪些改变能让产品更容易采用、实施和部署。这个选择也有个人原因。过去他觉得自己偏内向、社交不够自然，他的叔叔——一位与 Randy Newman 等知名音乐人合作过的音乐制作人——曾告诉他，一个人要真正擅长某件事，就必须让它成为自己赖以吃饭的事情。业余时间练吉他的人很难达到顶尖水平；真正优秀的人可能每天在街上弹14个小时，因为“不弹吉他就没有饭吃”。

Dex 没有继续靠自助书籍解决社交问题，而是把与人交谈、结交朋友、帮助客户解决问题变成自己的工作。这份工作还迫使原本不擅长邮件、日历和表格的他变得更有组织。他后来建议工程师至少花一两年做真正面向客户的工作，因为走出原有舒适区会带来一些无法预先设计的能力。

##### 一百名 AI 工程师让他放弃现成框架，写出“十二要素智能体”

约在2020年11月，Dex 与芝加哥的一位朋友创办了数据工程公司 Metalytics。它后来并没有被彻底注销，而是经过使命转向，成为 HumanLayer 所在的同一家公司。当时数据工程领域吸引了大量资本，但到2021年至2022年前后，市场开始认识到，这类工具的总体可服务市场并没有此前设想得那么大，融资和获取客户都变得困难。

2024年8月前后，Dex 的联合创始人因精疲力竭离开，双方保持着良好关系。Dex 随后开始尝试 AI 智能体。当时最受关注的是 LangChain、CrewAI 等智能体框架。CrewAI 的 Discord 里有上万人，各个项目都在提供 ChromaDB、Composio 等插件，看上去已经形成了一个共享接口和生态。

但 Dex 认为其中缺少一环：智能体虽然能调用工具，却很难可靠控制它究竟调用哪些工具。聊天机器人还能在界面上展示“批准”或“拒绝”，他真正感兴趣的却是后台运行、由事件触发的“外循环智能体”或主动型智能体。这样的系统会周期性醒来，检查有没有工作，然后自行行动。

Dex 不愿把有意义的操作交给这种智能体，除非它在行动前能通过 Slack、iMessage 等渠道找到人，并且系统可以确定性地保证：人能够批准、拒绝，或者带着反馈拒绝，例如告诉它“不要这样做，改成那样做”。

HumanLayer 最初围绕这一需求构建 API 平台。它有些像 PagerDuty，但不是寻找“谁负责修服务器”，而是决定“谁需要批准这个智能体的操作”，并支持升级、转交和推迟。团队在2024年秋季带着这个想法进入 YC，最初面向 CrewAI、LangChain、Griptape 等框架开发。

真正改变 Dex 判断的是他与大量 AI 工程师的交流。他遇到的一些工程师已经在给企业交付六位数合同，也都尝试过流行智能体框架，但往往一两个月后就把它们扔掉，改为手写 API 调用。他们构建的东西更像管道和工作流，而不是一个完全放手、在循环中任意调用工具的智能体。

Dex 总共与约一百名工程师、创始人和构建者交谈，也长期与 Boundary 的朋友 Vib 讨论。Vib 更关心结构化输出的底层含义：AI 工作流中的每一步，本质上都是“输入 token，输出 token”。工程师的工作，是决定放入哪些 token，才能最大化输出正确 token 的概率。

Dex 把这些实践提炼成“十二要素智能体”。其中包括用自然语言表达工具调用、掌握自己的提示词和上下文窗口、把工具理解为结构化输出、统一执行状态和业务状态、使用简单 API 启动与暂停任务、通过工具调用联系人类、掌握控制流、把错误压缩进上下文、使用小而专注的智能体、从任何位置触发、在用户所在的地方与用户交互，以及把智能体设计成无状态 reducer。后来有人指出，最后一项从技术上说更接近 transducer，因为工作流中包含多个步骤，Dex 接受了这个修正。

他在2025年3月集中写作，4月把约12页内容发布到 GitHub，又贴到 Hacker News，文章在首页停留了约两天。6月6日前后，他在 AI Engineer 的一个约百人会场分享了这套方法。会场位于活动空间的顶层，那里集中的是更奇怪、更前沿、当时可能还不必关心的创业项目。

十二项原则中，最持久的一项是“掌握自己的上下文窗口”。几周后，Shopify 的 Tobi Lütke 开始使用“context engineering”这个说法；再晚一周左右，Andrej Karpathy 也提出，与其讨论提示词工程，不如讨论上下文工程。Dex 比他们稍早写出这个名称，但他并不认为自己发明了相关实践。他从一百名构建者那里看到共同做法，只是为它找到了一个可以准确讨论问题的词。

##### 把 RAG、记忆和工具拆回 token，才能看见上下文的物理限制

Dex 对上下文工程的解释，是把层层抽象重新拆开。RAG、记忆、智能体历史、结构化输出，看起来是不同概念，底层却都是把 token 以不同方式传给模型，再要求模型生成一组通常带有结构的输出。

现成的智能体和记忆框架很适合把产品迅速做到80%，也适合制作效果不错的演示。但要从80%进入95%甚至99%，工程师就必须下沉一层：上下文里究竟放了什么，顺序如何，不同模型应采用什么排列方式。模型和系统提示词并不是仅有的杠杆，工作流可以被拆成多次模型调用，也可以在局部使用工具循环，在另一些环节使用更受控的管道。

成本优化也应遵循“先运行，再正确，最后变快”。Dex 的建议是，先拿当时最强的模型验证问题能不能解决，把产品交给用户，看用户是否真的需要。如果需求成立、调用量增大，再投入工程时间进行上下文优化。例如把一个任务拆成三次调用，或者让成本只有 Opus 约千分之一的 GPT OSS 12B 解决其中较简单的部分，只把真正需要高智能的环节留给前沿模型。工程师时间通常比模型调用更昂贵，只有系统规模足够大时，延迟和调用成本才会成为首要瓶颈。

在“构建智能体”之外，Dex 又提出“harness engineering”。如果上下文工程关心每一次提示中放入什么，harness engineering 关心的则是如何优化智能体实际运行的环境，包括命令、MCP、skills、代码库组织和各种集成点，让每一轮执行的最低质量都更高。

这个词后来出现了歧义：有人把它理解为构建 harness，有人把它理解为围绕现有 harness 做工程。Dex 更认可 Martin Fowler 的划分。LLM 之外，Claude Code、Codex 等工具直接暴露的工具定义和集成点构成“内层 harness”；人类针对特定代码库、语言和工作方式所做的定制，则是“外层 harness”。

上下文窗口不断扩大，并不意味着模型的智能同步提高。一个模型拥有100万 token 的上下文，并不等于它更善于从100万 token 中找出真正相关的信息。模型每一轮都要判断，当前上下文中的哪些部分与下一次工具调用最相关；上下文越大，这个判断越困难。

Dex 提到一项基于较早模型的2025年研究：前沿模型大约能同时遵循150至250条指令，超过后，遵循能力会明显下降。后来模型已有改善，但问题没有消失。因此，上下文既有信息预算，也有指令预算。RAG 可以只取一本书中相关的几页，而不是把整本书塞进去；同样，如果用户先让模型沿一个方向工作，随后说“前面的都不要，改做另一件事”，模型就必须额外计算哪些内容应该忽略。等这些互相冲突的指令退到十万 token 之前，模型准确记住最初要求的概率便会明显下降。

Dex 并不是研究注意力机制数学证明的机器学习博士，但他强调一个基本事实：注意力计算是二次增长的，放入的内容越多，注意力就越需要在更多 token 之间分散。像传统软件工程师通过凌晨三点调试事故来形成对坏模式的直觉一样，AI 工程师也必须通过失败积累对上下文的直觉。

##### 六周六千美元的 Ralph 循环，与四个月后关闭的“无人软件工厂”

循环工程最具冲击力的早期示范之一，是 Jeff Huntley 的 Ralph Wiggum 技术。Dex 第一次看到演示时，Jeff 让 Sonnet 昼夜不停地工作，六周花费约6000美元，构建出一门面向 Z 世代的编程语言。它不仅能够编译，还做出了第二阶段编译器：用这门语言自身编写编译器。

这个案例的核心并不只是“让模型多跑”，而是反压机制，也就是让模型不断检查自己的工作。编程语言非常适合这种循环，因为结果可以反复验证：写代码、编译；编译失败就修编译器；运行失败，再回去修。只要一个问题足够可验证，就可以在一定程度上把它当作黑盒，让模型靠反馈持续改进。

Dex 会用类似方法优化 CI/CD。他把目标设为“让 CI 更快”，然后让模型研究代码库、做出修改、创建 pull request、运行测试、启动子智能体监控任务，等结果返回后再决定下一步。模型不只提出几种可能方案，而是在有测量结果的前提下持续迭代。

但他更看好“慢循环”，而不是一次生成数万行代码的巨大循环。HumanLayer 会在 GitHub Actions 中运行定时任务：执行 linter，只修一个问题，提交并推送。团队第二天醒来时，会看到一个只让代码库好一点的 PR。

他们后来增加了 React Doctor 等前端反馈工具，还加入了一种没有确定性检查器的规则：明确告诉模型好代码和坏代码分别是什么，让它每次只修一个问题。例如，一批 React 属性被写成可选，但多数其实不应是可选，模型就按给出的模式逐个收紧这些属性。于是团队每天可能醒来看到四个 PR，分别对应四种改进。随着信心提高，范围也可以从每次修一个问题扩大到每次修四个问题。

这种循环不需要人按启动按钮，触发源可以是 Sentry 警报、用户支持工单、产品经理创建的任务、失败测试，也可以只是定时器。但 Dex 对“把整个开发过程都做成无人循环”有直接的失败经验。

2025年7月，他的团队建立了一座“lights-off software factory”，即关灯运行、几乎没有人阅读代码的软件工厂。到11月，他们关闭了它。Dex 的观察是，如果持续发布代码，却没有人阅读，通常三到六个月后就会发现代码库越来越差，甚至重写都比修复容易。

最初，他仍然觉得这种交换值得：平时不读代码，偶尔花两周人工解决一个困难问题即可。真正的警报出现在一个 Opus 4.1 无法找到根因的问题上。无论团队怎样设计专家提示，模型都无法解决。他们只好重新进入已经三个月没有认真阅读的代码库，花约三周重新熟悉系统，又用数天逐层追查，最后发现，一条贯穿整个流程传递的主键，本应被改成另一类对象。

问题最终解决了，但 Dex 不再认为这种工作方式长期划算。AI 让代码产量提高十倍甚至百倍后，人工重新接管一个失去理解的系统会变得更困难。模型可以通过单元测试证明眼前修改有效，却很难评价一次架构选择会不会在三到六个月后让系统变得无法修改。

现有编码基准大多近似于：给模型一个 Django、Apache 或其他开源仓库中的 issue，再看它能否生成类似人类历史提交的修复。这样的验证可以判断测试是否通过，却无法衡量接口放在哪里、模块边界如何划分、依赖注入怎样设计，以及这些决定会不会让未来的修改更容易。坏架构的代价通常不是当天出现，而是数月后才显现。

因此，HumanLayer 仍会用循环提高代码质量，却不再用循环代替所有人的阅读。团队关心的不仅是系统架构，也关心程序设计中的接口、接缝和依赖关系。Dex 并不否认未来的 GPT-7 可能改变局面，但就当前模型、编程语言和训练方法而言，把支持工单、崩溃、产品需求乃至 CEO 在 Slack 里写的长篇意见全部直接送给智能体，再用智能体审查取代人类审查，是一种可能在凌晨三点威胁公司生存的做法。

##### 软件工厂从1968年的装配线，变成了能自动接收投诉的智能体闭环

“软件工厂”并不是 AI 时代才出现的概念。Dex 追溯到1968年的一次 NATO 会议：与会者已经提出，软件生产也应像工厂地板一样，被拆成编码、测试、验证和集成等步骤。那时甚至还没有现代 CI/CD，版本控制也很初级。后来，东芝等公司采用了类似思路。

下一次明显推进来自 DevOps。Chef、Ansible、Puppet 等工具把大量人工操作变成反馈回路。过去需要工程师跑进数据中心扩磁盘，后来服务器磁盘使用率达到90%，就可以向 Nagios 发出警报，再由 Nagios 触发 Chef 扩大磁盘。

2018年前后，时任美国空军首席软件官的 Nicolas Chaillan 写过一篇约100页的文章，主张国防部和空军需要一座“DevSecOps 工厂”。他的意思不是创造全新概念，而是采用企业已经使用的 Jenkins、代码质量扫描、安全扫描和 CI/CD，把三个月甚至一年一次的发布，提升到每天都能发布。这样，90%的常见问题可以由自动化发现，不再依靠人手工寻找 SQL 注入或手动集成模块。

AI 出现前，一座现代软件工厂通常从 Jira、Linear、电子表格等工作来源开始。团队做架构和迭代规划，工程师领取任务、编写代码、创建 PR，随后进行人工审查和 CI 检查，再部署到生产环境。用户遇到问题后联系支持团队，问题返回任务系统；系统崩溃则进入监控平台，再回到同一个工作队列。产品经理、工程经理和工程师重新排序，开始下一轮。

这一闭环的问题是延迟。开发者实际编写代码可能只需几小时或几天，但一个缺陷从用户处传回开发者，可能需要两三个月，真正修复甚至可能是一两年后。

智能体工厂首先替换的是“工程师从队列中领取任务并实现”这一段。系统加入编排器、沙箱、LLM、内层 harness 和为智能体准备的外层开发环境，还可能提供浏览器和视频录制工具。原本两小时或两天的实现变成十分钟后，瓶颈就转移到代码审查，于是团队又加入智能体审查和智能体测试。

再往前一步，支持工单可以直接触发智能体，用户一投诉，系统就生成 PR；Sentry 或 Datadog 一报错，智能体也立即尝试修复。继续推进下去，团队会发现生成的代码多到人类看不过来，于是有人建议拿掉所有人工检查，把系统当作黑盒：只要用户不投诉，就算它在工作。

Dex 认为，除了“停止阅读代码”，其他自动化方向基本都值得尝试，但应当一次建立一个小而受控的循环。他还希望在工厂里增加更早的人类检查点：不要等到一个100行或1000行的 PR 出现后，才让人判断整个方向是否错误；应先让人与智能体讨论设计和计划。

如果在实现前花一小时把设计讲清楚，最终 PR 可能只需20分钟就能读完。反过来，如果每个用户问题都直接变成 PR，一个方向错误的实现可能需要六小时反复修改，而且一旦智能体已经沿错误方向生成大量代码，重新开始往往比纠偏更容易。

在他看来，全面自动化有三种选择。第一种是彻底关灯，让代码自由流动，并祈祷下一代模型在系统变成一大堆“灰烬”之前到来。第二种是读完每个 PR 和每一行代码，这通常只能带来约30%至50%的生产率提升。第三种是寻找真正的杠杆点：让人类在规划和设计阶段投入一小时，省掉实现和返工阶段的四小时。这样，团队可能达到原来两到三倍的速度，同时让结果保持在接近人类谨慎手写代码的99%质量水平。

##### RPI 从冗长计划退回到频繁压缩，人类只守住最有杠杆的判断点

2025年8月，Dex 开始公开讨论 RPI，即 Research、Plan、Implement：研究、计划、实现。最初的研究阶段要求智能体先大量阅读代码，不急着告诉它最终要构建什么，而是让它解释几个系统怎样工作、彼此如何连接。模型可能消耗10万 token 阅读代码，最后压缩成一份约1万 token 的 Markdown 文档。

随后开启新的上下文，把研究文档与具体需求交给模型，让它制定实现计划。再开启第三个上下文，根据计划完成编码。这个方法当时很有效，因为计划能让智能体工作更久。如果只说“做一个 B2B 墨西哥卷配送 SaaS”，模型可能只生成一个主页；如果先让它列出完整计划，再要求逐项实现，它会一直工作到计划完成。

但原始 RPI 的计划文档存在严重问题。模型会把几乎每一处要改的代码都写进计划，甚至给出 diff。团队建议用户读计划，自己也照做，后来 Dex 发现自己只是快速扫一遍。计划没有真正帮助人类重新引导智能体，却额外制造了阅读负担：先用20分钟读计划，再用20分钟读与计划并不完全相同的 PR，相当于把阅读量翻倍，形成了“反杠杆”。

规范驱动开发也遇到了类似问题。有人曾设想，人类只维护规范，把编码视为“把规范编译成代码”，但这一图景没有真正实现。Dex 长期关注一个相关 GitHub issue，几乎每隔几周就会看到新的抱怨：规范改了，代码也改了，两者逐渐漂移，最终形成两个事实来源。

因此，RPI 中的研究和计划文档不再被当作永久资产。团队完成研究、计划和实现后，就把这些战术性文档丢掉。下一次需要时重新研究，因为 token 便宜，人的时间昂贵；重复使用一份已经与代码真实状态脱节的研究文档，风险反而更大。代码继续作为唯一事实来源，文档只负责在单次任务范围内压缩代码库状态和构建者意图。

这种“频繁、有意的压缩”成为上下文工程的核心操作。研究阶段把大量代码压缩成一份文档；设计阶段把工单和人的意图压缩成当前状态、目标状态及关键设计问题；然后在全新的上下文中，将研究与设计转化为分阶段计划。每次切换都不是简单地继续聊天，而是丢掉噪声，只带着已经验证过的高价值信息进入下一轮。

不同阶段需要不同程度的人类参与。单纯解释系统怎样连接，模型通常做得不错，研究文档甚至不一定需要人逐字阅读。但决定目标架构和程序设计时，模型的判断时对时错，因此人类应留在环路中。

模型还偏爱“横向计划”：先做完整数据库层，再做服务层、API 和前端，直到生成约2000行代码后才第一次进行整体测试。Dex 更倾向于人类工程师常用的纵向切片：先建一个返回假数据的 API，把前端大致做出来；再接入服务层，让真实数据流动；随后做数据库迁移和新表，再加入业务逻辑与错误处理。这样，人可以检查五个小 diff，而不是面对2000行无法运行的代码，最后连问题出在哪一层都不知道。

频繁压缩的目标，是让工作尽可能停留在上下文的“smart zone”。Dex 最初把它粗略定义为上下文窗口前40%，后来模型出现百万 token 窗口，他改用更实际的尺度：较小模型约前10万 token，Codex 或较强的 Opus 模型可以把训练轮式上限放到约20万。凭经验，他有时会工作到25万或30万 token，极少到40万，但如果缺少模型直觉，越过10万或20万后就应当警惕质量下降。

进入“dumb zone”的典型信号，是模型为了让测试通过而不断尝试更极端的做法：“先试这个，再试那个”，最后甚至准备删除环境文件。如果会话已经达到30万 token，而接下来又要解决困难测试，Dex 会先让模型把已经完成的工作写进文件，或者使用内置压缩，然后在只有3万至5万 token 的新会话中重新开始。

他认为上下文至少有四个需要关注的维度：总 token 数量、信息是否正确、是否缺少必要信息，以及整个执行轨迹。轨迹尤其容易被忽视。如果模型上一次修改代码后主动运行测试、发现失败并修好，那么下一次很可能重复这一模式；如果它修改后没有测试，后续也更可能继续不测试。

当人因错误而斥责模型，模型回答“You’re absolutely right”，却继续犯同样的错，这往往不是道歉能够解决的问题，而是会话轨迹已经恶化。自回归模型是在预测这段对话的下一条消息：如果历史模式是“模型犯错—用户责骂—模型再犯错”，它很可能沿着这个模式继续。此时最有效的办法不是继续争论，而是压缩有用信息，重新开启上下文。

Dex 把另一种流行方式称为“token harder”。他所在的一个群聊叫“hyperengineering”，里面的人会展示自己做了多少副项目、怎样最大化 Claude 订阅，甚至有人同时使用六个 Claude Code 账户，按每五小时一次的限额安排调用，一重置就立刻继续消耗。这样的做法优化的是工厂中某个节点的利用率，而不是端到端地交付稳定、有价值、能长期维护的产品。

完全无人参与的“dark factory”一词来自现实中的自动化工厂：机器人不需要照明，因此厂房里甚至没有灯光开关。软件系统中可以有局部的黑暗循环，例如代码审查智能体发现问题后，自动把问题退回构建智能体修改；但如果整个工厂都不再有人阅读代码，最大化的往往只是 token 吞吐量。

与之相对，“token smarter”不是少用 AI，而是寻找能保持控制、品味和判断的高杠杆位置。工程师仍应理解系统架构，把十年软件工程经验形成的意见施加到程序设计中，同时自动化那些不值得人类重复处理的环节。正如 Google 的 SRE 思路不是把人完全移出系统，而是让同一支六人团队能够从管理五个数据中心扩展到下一年的50个数据中心：真正的目标不是让某台机器永远满负载，而是让少量人的判断，通过合适的自动化持续放大。

## 口播总结（1）

### 2026-08-03 01:02:33

#### 上下文工程：怎样让 AI 写出更多代码，却不失去对软件的控制

这场对话的核心是：用大语言模型开发软件，关键不只是提示词写得好，而是怎样管理模型看到的信息、工作环境和反馈循环。听完你会了解上下文工程、智能体循环和 AI 软件工厂为什么有效，也会知道它们在什么地方容易失控。

##### 从平台工程到 AI 开发

首先，嘉宾 Dex Horthy 对 AI 软件开发的看法，来自他长期搭建“软件生产系统”的经历。

所谓平台工程，就是不只开发某个具体功能，而是建设持续集成、自动部署、测试环境等基础设施，让整个团队都能更快、更稳定地开发软件。Dex 把这种系统叫作“软件工厂”，也就是“建造那个用来建造软件的东西”。

他大学原本学物理。17 岁时，他曾和美国宇航局的研究人员合作，根据月球南极的地形数据，为探测车寻找安全路线。因为没有系统学过计算机，他自己写出了一个很粗糙的路径搜索算法。这段经历让他发现，相比学术研究，他更喜欢编程。

进入软件行业后，他很快注意到，团队里影响最大的人，往往是那些建设开发平台、持续集成和部署流程的人。后来在 Replicated 工作时，他参与过容器编排系统，也负责帮助企业把原本运行在云端的软件，部署到客户自己的数据中心。

这段客户一线经历同样重要。他在大约三个月里推动了十二笔交易，后来把客户工程团队扩展到约二十五人。Dex 的体会是，工程师至少应该花一两年直接面对客户。这样不但能理解真正的问题，也能锻炼沟通、组织和判断优先级的能力。

##### “十二要素智能体”带来的核心认识

接下来，是 Dex 进入 AI 智能体领域后的第一个关键转折：他发现，复杂的智能体框架未必能带来可靠的产品。

这里的“智能体”，可以理解成能够调用工具、执行多步任务，并根据结果继续行动的 AI 系统。2024 年前后，市面上出现了很多智能体框架。它们很适合快速做出演示，但不少真正为企业交付 AI 项目的工程师，试用一两个月后就放弃了这些框架，转而自己编写大语言模型的接口调用，并把系统做成更明确的工作流和流水线。

Dex 和大约一百位 AI 工程师、创业者交流后，把共同经验总结成“十二要素智能体”。其中最重要的思想是：每一步 AI 工作，本质上都是“输入一些 token，再输出一些 token”。

Token 是模型处理文字时使用的基本单位，可以粗略理解成文字片段。工程师真正要解决的问题是：应该给模型哪些文字、按照什么顺序提供，才能最大限度提高输出质量。

因此，这套原则强调几件事：自己控制提示词和上下文窗口；自己控制智能体的执行流程；把工具调用看成结构化输出；让智能体保持小而专注；在需要时明确联系人类审批，而不是把一切交给模型自由决定。

##### 什么是上下文工程

更重要的是，这些经验最终形成了“上下文工程”这个概念。

上下文窗口，就是模型在一次任务中能够同时参考的全部信息，包括系统指令、用户要求、代码、工具说明、检索结果，以及之前的对话历史。上下文工程，就是有意识地决定哪些信息进入这个窗口、以什么顺序进入，以及什么时候应该删除、压缩或重新组织。

很多听起来不同的 AI 技术，本质上都在做同一件事。比如，RAG，也就是“检索增强生成”，是先从资料库里找出相关内容，再交给模型；所谓记忆，是把过去的信息重新放进当前输入；智能体历史，是保留之前的行动记录；结构化输出，则是要求模型按照固定格式回答。它们最终都在影响模型当前看到的 token。

现成框架通常能帮助产品从零做到大约八十分。但如果目标是把准确率提高到百分之九十五，甚至百分之九十九，工程师就必须往下一层看：模型究竟看到了什么？不同信息是否冲突？顺序是否合理？某段历史是不是已经过时？

在成本方面，Dex 的建议是先“让它跑起来，再让它正确，最后才让它更快”。早期可以先使用最强的模型，确认问题能不能解决，以及用户是否真的需要这个产品。等请求量足够大，再通过上下文工程拆分任务，把简单部分交给更便宜的小模型，只把真正困难的部分留给最强模型。

原因很现实：产品早期最贵的通常不是模型调用，而是工程师的时间。只有到了大量请求的阶段，延迟和 token 成本才可能成为主要瓶颈。

##### Harness 工程：优化智能体工作的环境

在上下文工程之后，Dex 又提出了“Harness 工程”。Harness 可以理解成套在模型外面的“工作装置”或“操作框架”。

上下文工程关注的是，每一次调用时模型看到了什么。Harness 工程关注的是，模型长期在什么环境里工作，以及这个环境怎样降低它犯错的概率。

按照 Martin Fowler 的划分，Harness 可以分为内层和外层。内层 Harness 是编码智能体自带的工具和接口，比如读取文件、修改代码、搜索项目和执行命令。外层 Harness 则由使用者针对自己的项目搭建，包括代码库结构、开发命令、工具协议、技能说明、测试环境和项目规则。

简单来说，不只是给 AI 一条好指令，而是要为它准备一个更容易做对事情的工作场所。这样才能提高每一步工作的最低质量，而不是每次都从头提醒它。

##### 上下文越长，不代表模型越聪明

接下来要理解一个重要限制：一百万 token 的上下文窗口，并不等于模型可以同样准确地使用其中每一条信息。

上下文变长的好处，是对话可以持续更久，也能放入更多代码和资料。但模型本身并没有因此变得更聪明。它仍然需要在大量内容中判断，哪些信息与下一步行动最相关。

Dex 引用过一项针对较早模型的研究。当时的前沿模型大约能够稳定遵循一百五十到二百五十条指令，超过之后，执行能力会明显下降。新模型已经有所改善，但基本问题仍然存在。

这里有两种预算。第一种是“信息预算”，也就是放进去多少资料。与其塞入整本书，不如先检索出真正相关的几页。第二种是“指令预算”，也就是让模型同时遵守多少要求。如果指令太多、互相冲突，或者对话中途频繁改变方向，模型就需要花更多能力判断哪些话应该执行、哪些话应该忽略。

Dex 把上下文前面质量较高的部分叫作“聪明区”，把后面容易退化的部分叫作“迟钝区”。这不是绝对边界，但可以作为实用参考。对较小的模型，可以把前十万 token 看成相对安全的范围；对更强的模型，有时可以放宽到二十万 token。超过之后，结果未必立刻失败，但出错概率通常会上升。

一个典型信号是，模型为了让测试通过，开始反复尝试越来越奇怪的办法，甚至删除本不该删除的配置文件。遇到这种情况，不要继续在同一段长对话里纠缠。更好的做法是压缩当前成果，然后开启一个干净的新会话。

##### 循环工程为什么有效

说完上下文，再来看“循环工程”。它的核心结论是：只要任务可以可靠验证，就可以让智能体根据反馈反复改进。

这里最重要的概念是“反向压力”，也就是系统会把结果好坏自动反馈给模型。代码检查工具、单元测试、编译器、持续集成流程，都能提供这种反馈。

一个著名案例是 Ralph Wiggum 技术。开发者让模型持续循环工作，六周花费大约六千美元，最终做出了一门面向年轻人表达方式的编程语言。这个任务适合循环，是因为编程语言很容易验证：代码能不能编译，程序能不能运行，编译器能不能用这门语言编写自己，都有明确答案。

类似的方法也可以用于优化持续集成速度。目标只需要设成“让构建更快”。智能体修改代码、提交、运行测试、等待结果，再根据结果决定下一步。只要反馈足够明确，它就可以不断尝试。

不过，Dex 更推荐“慢循环”。比如每天夜里自动运行一次检查，只修复一个问题，然后第二天早上给团队一个小型代码变更请求。团队可以先观察质量，建立信任后，再从一次修一个问题增加到一次修四个问题。

这种方式的好处是，自动化是逐步增加的。每次改动都足够小，人类仍然能够理解和审查，而不是突然面对一个六万行代码的巨大变更。

##### 为什么“关灯软件工厂”会失控

但循环工程也有危险的一面：代码生成速度一旦超过人类理解速度，团队就可能失去对系统的掌控。

所谓“关灯工厂”，原本指完全由机器人运行、不需要人类，因此连灯都不用开的实体工厂。放到软件开发里，就是需求、编码、测试、评审和修复全部由智能体完成，人类不再阅读代码。

Dex 的团队真的做过这种实验。他们在2025年7月搭建了一个“关灯软件工厂”，到了11月就把它关闭了。原因不是短期功能无法交付，而是连续几个月没人读代码后，代码库越来越难维护。

后来，一个问题无论怎样调整提示词，都无法让当时的模型找到根因。团队不得不重新理解三个月没有认真阅读过的代码，花了几周重新进入状态，又用几天手工排查，最后才发现，某个主键在整个系统中的传递方式从根本上就设计错了。

这说明，单元测试通过，不代表架构健康。糟糕的程序设计，其代价往往不会当天出现，而是在三到六个月后爆发。到那时，修改一个地方会破坏另一个地方，系统可能已经比重新开发还难修。

Dex 强调，模型目前很擅长解决“这里有一个问题，请提交一个修复”这类任务。但它还不擅长判断，今天的设计会不会让三个月后的开发更容易。长期可维护性很难通过一次测试或一个短期基准来衡量。

因此，他使用循环主要是为了改善代码质量，而不是无限生成新功能。更关键的是，团队仍然阅读代码，关注接口、依赖关系、系统边界和整体架构。

##### 软件工厂从自动化走向智能体化

软件工厂并不是 AI 时代才出现的概念。这个词早在1968年的一次北约会议上就已经出现。当时人们开始把编码、测试、验证和集成看成一套连续生产流程。

后来，DevOps，也就是把开发和运维结合起来的工程方法，继续推进这件事。持续集成和持续部署，简称 CI 和 CD，让代码可以自动构建、自动测试和自动发布。2018年，美国国防部门也提出建设 DevSecOps 软件工厂，把安全检查同开发、测试和部署放到一条自动化流水线上。

AI 带来的变化，是把原来由人完成的部分也放进自动化流程。

过去，一个工作项进入任务系统后，要经过规划、开发、代码评审、测试和发布。用户投诉或系统报错，再回到任务系统，形成下一轮工作。即使流程很现代化，开发本身仍可能需要几小时或几天。

有了编码智能体，同样的实现过程可能只需要十分钟。于是瓶颈会迅速转移到代码评审。团队接着引入 AI 评审和智能体测试。再往前一步，还可以把用户投诉、客服工单和生产环境报错直接交给智能体，让它自动生成修复方案和代码变更。

问题在于，一旦连最后的人类评审也被拿掉，软件就会变成黑箱。系统可能短期运行正常，但内部质量不断恶化，直到某一天出现难以理解和修复的问题。

##### 自动化真正的边界在哪里

目前最大的限制，是模型训练方式更擅长奖励“问题修好了”，却不容易奖励“这套代码三个月后仍然好维护”。

编码模型通常通过可验证结果来训练。比如给它一个软件问题，让它修改代码，再看测试是否通过。这种方法叫“带可验证奖励的强化学习”。通俗地说，就是答案可以明确判定对错，模型就能通过反复训练变得更好。

这也是编码智能体进步很快的原因。它们越来越擅长读取文件、搜索代码、修改内容和调用测试工具。但这些训练主要提升了完成当前任务的能力，没有充分训练长期架构判断。

即使让另一个模型进行代码评审，也只能提高最低水平，不能完全代替人类。模型容易迎合提问者。如果问“这段代码好吗”，它可能说结构完整、测试充分；如果问“找出同事这段代码的所有问题”，它又可能列出一长串缺点。因此，让模型评价模型生成的代码，本身也不够可靠。

##### 自动化软件开发的三种选择

在 Dex 看来，团队大致有三条路。

第一条路，是彻底关灯，让智能体完成一切。这样能最大化代码产量，却可能积累大量低质量代码，最后留下一个难以维护的系统。

第二条路，是阅读每一个代码变更和每一行代码。这种方式最稳妥，但人的评审速度会成为瓶颈。按照 Dex 观察到的情况，生产率提升可能只有百分之三十到百分之五十。

第三条路，是寻找人类最有杠杆的位置。比如在编码前，先让人和智能体花一个小时讨论需求、设计和实施路径。这样可能省下后面四小时的返工和评审。Dex 认为，如果找对这些控制点，团队有机会在保持接近人工质量的同时，把速度提高到原来的两到三倍。

关键不是把人移出流程，而是让人把时间集中在最需要品味、判断和架构经验的地方。

##### RPI：研究、计划和实施

为此，Dex 曾提出 RPI 框架，也就是研究、计划、实施三个阶段。

研究阶段，智能体先阅读大量代码，理解系统当前如何运作。一次研究可能消耗十万 token，但最后压缩成一份大约一万 token 的文档。这样，下一阶段不必携带所有原始对话，只需要使用这份精炼后的材料。

计划阶段，智能体根据研究结果和目标制定方案。实施阶段再开启新的上下文窗口，按照方案修改代码。

早期版本的问题是，计划写得过于详细，几乎列出了每一行将要修改的代码。人类先花二十分钟读计划，又花二十分钟读实际代码，而且计划和代码往往还不完全一致。这不但没有节省时间，反而增加了工作量。

后来，Dex 把计划调整为更高层的设计说明。它应该说清楚当前状态、目标状态、关键设计选择和实施步骤，而不是提前写一遍完整代码。

他也不再建议把这类研究和计划文档长期保存。代码不断变化，文档很快就会过时。长期维护代码和规格两套“事实来源”，只会让它们逐渐偏离。更实用的方法是，把代码始终当作最终事实。每次新任务开始时，再根据当前代码生成临时研究材料。任务完成后，这些战术文档就可以丢弃。

##### 有意识地压缩上下文

这就带出了上下文工程最重要的操作之一：频繁而有意识地压缩。

压缩不是简单删掉历史，而是把真正有价值的信息提炼成新的短文档。比如，把大量代码阅读压缩成当前系统说明；把用户需求压缩成目标和设计选择；再把研究与设计压缩成可以执行的步骤。

每次完成一次压缩，就开启一个新的上下文窗口。这样可以把模型重新带回“聪明区”，避免它被长对话里的错误信息、冲突指令和失败尝试拖累。

实施步骤也应该尽量纵向切分。模型常常喜欢先做完整数据库层，再做服务层、接口层和前端，最后才能一起测试。Dex 更倾向于先做一个能够端到端验证的小切片，比如先用假数据搭出前端，再逐步接入服务、数据库和错误处理。这样每一步都能检查，也更容易发现问题。

还有一个容易忽视的因素，是对话的“轨迹”。模型不仅参考当前要求，也会模仿此前的行动模式。如果它上一次修改代码后主动运行测试、发现失败并修好，那么下一次很可能继续这样做。反过来，如果它连续犯错，而人只是不断责骂，它也可能沿着同一条失败轨迹继续犯错。

当模型开始说“你说得完全对”，却仍然重复同样的问题时，往往不是继续争论的好时机。更好的选择是保留有用结论，清空失败轨迹，重新开始。

##### 从“猛烧 token”转向“聪明用 token”

最后，Dex 用“token harder”和“token smarter”概括了两种 AI 开发方式。

“猛烧 token”，就是追求让模型全天运行，尽量用满订阅额度，生成更多代码，开更多并行智能体。它优化的是某一个环节的使用率，而不是整个系统最终交付了多少稳定、有价值的软件。

“聪明用 token”，则是寻找真正的杠杆。简单、可验证的局部循环，可以完全自动化。比如让代码评审智能体发现问题后，自动交回构建智能体修改，这个小循环可以“关灯”运行。

但系统架构、重要设计和长期维护方向，仍需要人类理解和把关。目标不是消灭工程师，而是让同样规模的团队管理更大的系统，把时间从重复劳动转移到判断、设计和控制上。

##### 最值得记住的五个结论

最后，回顾五个最重要的结论。

第一，上下文工程的本质，是控制模型在每一步看见哪些信息。上下文越多不一定越好，真正重要的是信息准确、相关，而且没有冲突。

第二，任务只要能够自动验证，就适合做成智能体循环。但最好从小型、缓慢、可审查的循环开始，而不是一次自动生成海量代码。

第三，测试通过只能证明当前功能可用，不能证明架构长期健康。模型目前仍然缺乏对三到六个月后维护成本的可靠判断。

第四，不要在过长、混乱的对话里硬撑。及时把研究、目标和进展压缩成短文档，再开启新的上下文窗口，通常能得到更好的结果。

第五，AI 软件开发的最佳方向，不是单纯生成更多代码，也不是完全取消人类，而是找到人类判断最有价值的位置。让智能体负责执行和反馈，让人类负责意图、设计、架构和长期质量。

#### AI 编程的真正瓶颈：不是生成代码，而是维持可理解性

这场访谈最有价值的地方，不是创造了“上下文工程”“软件工厂”等新术语，而是给出了一个经过失败验证的判断：**AI 可以大幅降低代码生成成本，却没有同步降低长期维护和判断的成本。**如果只追求让模型工作更久、提交更多，局部效率越高，系统反而可能越快失控。

##### 上下文窗口不是容量，而是有限的注意力预算

所谓上下文工程，本质上是拆掉 RAG、记忆、工具调用等概念的包装，重新追问一个简单问题：为了提高下一次输出正确的概率，究竟应该给模型哪些 token？

更长的上下文窗口并不等于模型更聪明。信息越多，模型越难判断哪些内容重要；指令过多或彼此冲突，也会降低遵循率。更隐蔽的变量是**对话轨迹**：如果模型已经连续误判、漏测，再通过补充提示反复纠正，它往往会沿着错误路径继续生成。“你说得完全对”之后再次犯错，不只是体验问题，而是应该清空上下文、重新开始的信号。

Dex 推荐“有意识地压缩”：先让模型阅读大量代码，将当前实现压缩为研究文档；再把需求和关键设计决策压缩为短文档；随后用全新会话执行。文档是单次任务的上下文载体，而不是必须永久维护的第二套事实源。因为长期规格一旦与代码漂移，维护它的成本可能超过收益。

##### 无人软件工厂的问题，三个月后才显现

Dex 的团队曾在 2025 年搭建“关灯运行”的软件工厂：代理生成、审查并交付代码，人类不再逐行阅读。四个月后他们关闭了它；一次根因问题迫使团队花数周重新理解已经脱离掌控的代码库。

这不是说模型不会通过测试，而是现有反馈机制主要奖励“当前任务完成”：测试通过、缺陷修复、补丁接近标准答案。**架构质量的代价通常要在几个月后、下一批需求到来时才暴露**——接口是否合理、依赖是否混乱、一次修改会不会破坏远处模块。这样的延迟反馈很难被单次测试或 AI 代码审查捕获。这个案例仍只是一个团队的经验，不能证明所有自动化都会失败，却准确指出了现有评测缺失的维度：可维护性不是静态代码质量，而是未来持续修改的成本。

##### 更好的自动化，是寻找人的高杠杆介入点

可行方向不是在“全部人工审查”和“完全无人交付”之间二选一，而是把人放在最能改变结果的位置。实现前花一小时研究和设计，可能省掉实现后的数轮返工；把大需求拆成可独立验证的纵向切片，比让代理依次写完数据库、服务层和前端后再统一测试更容易纠偏。

循环也应从小范围开始：例如每晚只修一个 lint、一个明确反模式，第二天交付一份可审查的小 PR；随着可靠性得到验证，再扩大范围。适合自动化的问题都有清晰的“反压”信号——测试、编译结果、性能指标或确定性检查。

对产品和工程管理而言，这也是更普遍的提醒：**不要把 token 消耗、提交量或代理运行时长当作生产力。**真正该优化的是从需求到用户价值的完整链路，以及系统在下一次变化到来时是否仍然容易理解和修改。AI 时代最稀缺的可能不再是实现能力，而是选择、验证与长期保持系统可控的能力。
