## 分析要点

- **核心高价值点**：将可复用、可测试的Markdown技能视为AI代理工程的新抽象层，而不是继续堆砌大量传统胶水代码。
- **留存建议**：短期参考后提炼归档（文章提出了AI代理时代减少传统代码控制层、转向可测试技能与指令层的架构视角，适合作为智能体工程思路参考。）

**知识要点**

- 传统软件架构中大量验证、重试、测试和调度代码，可能源于对模型能力的不信任，在更强模型环境下会变成冗余控制层。
- 作者提出“Markdown是程序”的观点，即把意图、判断和流程固化为版本化、可测试、可复用的技能。
- 智能体工程可能需要新的系统原语，如技能包、解析器、评估器和薄确定性代码层。
- 在LLM成本快速下降的背景下，过度节省token可能会牺牲探索速度和先发优势。
- 未来软件开发的瓶颈可能从代码产出转向目标清晰度、产品判断和任务设计能力。

**行动项**

- 审查现有AI应用代码库，识别哪些代码只是为了弥补对模型的不信任而存在。
- 尝试将一个重复工作流改写为可版本化的Markdown技能，并配套最小代码、单元测试和LLM评估。
- 在智能体项目中区分确定性代码层与自然语言指令层，减少不必要的胶水代码。
- 评估当前项目是否过度限制LLM调用，重新计算token成本与开发速度之间的权衡。

## 正文

**Garry Tan**

### 停止为你的代理商建造富士康工厂

In January I got back into coding and I built

[Garry's List](https://garryslist.org/). Over five hundred thousand lines of Rails and the tests to police it.

I was proud of it. I shouldn't have been. The thing worth being proud of wasn't the app. It was the setup that came out of building it.

[GStack](https://github.com/garrytan/gstack), the way I code with agents, grew out of the work of building Garry's List, and I gave it away. It's one of the hundred most-starred open source projects in GitHub history, about 105,000 stars in under three months. The half-million lines were the product. The setup was the byproduct. The byproduct is the part that mattered.

以下是围绕着一个 LLM 的 54 万行代码实际上是什么。

这是一家富士康工厂。 为不需要高度警惕的超智能 AI 工作者建造。我们还是建造了它。

门口的小靴子。早上6点起床。体操。生活如此艰难，以至于你不得不为每栋楼的高层架设防护网，因为……嗯，这不是你想要过的生活。永远都是同一条装配线。每一次测试，每一道护栏，每一个重试循环，每一寸牢笼都被固定在一个本已能胜任工作的工人身上，还有一千件你从未要求过的事情。

人类和代理人都蕴含着无限潜能，但富士康工厂却被建来压榨这些“美丽生灵”的智慧和劳动，而如果我们放手让他们去做，他们本可以完成所有这些工作，甚至十倍百倍（1000x）的工作量。

我建造了这家工厂。如今每个人都在建造这些。我告诉你不要这么做。

#### 时间旅行者

我曾用 539k 行代码（LOC）做的事情，其实是证明我能完美扮演一名时间旅行者。2013 年的一名 Web 2.0 工程师（也就是我，上一次我还是真正的软件工程师）带着现代工具突然来到 2026 年，用他唯一知道的方式继续开发。更多的代码。永远更多的代码。工具已经变了，我的直觉没变。

2013 年的工程师骨子里坚信一件事： 能力等于代码行数这种信念在过去几十年里都是正确的，直到现在。给我 Codex 或者 Claude Code，我能完成 100 到 1000 名工程师的工作量。同样的地图，更快的引擎，通往现在错误地点的最快路径。

这是几乎所有使用 AI 进行开发的人现在所处的状态。他们升级了工具，但保留了 2013 年的思维模式。这个陷阱并不像陷阱，因为代码能运行。Garry's List 发布了。感觉像是我一生中最有成效的一个月。

It was productivity in the service of an obsolete idea.

#### LLMs were expensive so we had to harness them

多年来直到 2025 年的旧经济模式是：LLM 调用成本高昂，而代码成本低廉。 因此，你编写代码来限制模型的使用，驾驭它，谨慎且节制地调用它。架构是大量软件保护性地围绕着少量珍贵的模型调用进行封装。

Both halves of that equation have flipped.

模型现在变得越来越便宜，每季度都更便宜。而且它非常智能，性价比发生了逆转。而且这个模型能够编写可用的代码。因此你不再需要编写代码来“照看”模型。现在你可以用通俗的语言指导模型，让它编写实际需要的最小代码。

这是即时软件 ，我们正进入它的黄金时代。

The artifact changes shape entirely. The Rails app was 540,000 lines I wrote and own, code plus the tests built to police it. The replacement is an agent built on markdown and code, a fraction of that. Same capability. Easier to read. Easier to maintain. Far more flexible, because the behavior lives in instructions you can edit in plain language instead of logic frozen in code the day you wrote it.

We were writing code to babysit a thing that is now smarter than the code.

#### Inside the Foxconn factory, netting and all

If you've been coding lately, you probably are building this kind of factory without knowing it. Walk your own codebase and count the lines that exist only because you didn't trust the model to do its job.

Mine: about 262,000 lines of application code, and about

[276,000 lines of tests](https://x.com/garrytan/status/2045404377226285538) bolted on to police it. The audit committee was bigger than the company. Sanitizers checking inputs the model would have handled. Validators checking outputs the model would have caught. Retry loops wrapping calls the model recovers from on its own. Every one of those lines is a bet that the worker will fail. You wrote the same bets. We all did.

127 background jobs, 33 of them on cron. That is not capability. That is 33 alarms set for an LLM worker who usually these days shows up on time.

In my Foxconn factory building days, Claude and I wrote a 1,778-line file whose only job is to second-guess the model's facts. It takes every claim the model makes, fans each one out to five separate sources in parallel, and grades them. A triage gate so the easy claims skip the full blast. A retry if the first pass comes back empty. Fallbacks for the fallbacks.

有一集《瑞克和莫蒂》里，瑞克在早餐桌上造了一个小机器人。机器人开机后抬头看，询问自己的用途是什么。瑞克说：“你负责递黄油。”机器人把黄油盘推过桌子，低头看自己的手，说：“哦天哪。”然后它就坐在那里。这个机器人包罗万象——它被造出来就是为了递黄油。 我那 276,000 行的测试代码就像是那个黄油盘。

![Image](https://pbs.twimg.com/media/HJrHJ3IaUAATvSS?format=png&name=large)

When you build this kind of software, in the 2023 Foxconn factory way, you built a cage, and if you're not careful, you'll be the jailer maintaining the prison for your AI agents.

#### Markdown is the program now

When I say markdown, I do not mean prompting. Prompting is ephemeral. You type something, you get something, it evaporates.

This is building. Versioned, tested, reusable.

The markdown is the instruction layer: the intent, the skill, the judgment about how the work should be done. The TypeScript is the

[thin deterministic layer](https://x.com/garrytan/status/2042925773300908103). The few things that genuinely have to be code, the I/O, the parts that must never hallucinate.

And critically, you test the markdown the way you'd test code. In my setup the loop is one word. I build something with the agent until it works, then I say

["skillify it."](https://x.com/garrytan/status/2046876981711769720) The agent then writes:

- the markdown skill
- the minimal code it needs
- a unit test for the code
- an LLM eval for the skill
- an integration test across both
- a
  [resolver](https://x.com/garrytan/status/2044479509874020852) so the agent invokes the skill automatically when it's relevant
- and an eval for the resolver

[技能包](https://github.com/garrytan/gbrain/blob/master/docs/skillpack-anatomy.md)

[测试是魔法](https://x.com/i/article/2054062662225440768)

We are only now

[figuring out the systems primitives](https://x.com/garrytan/status/2053127519872614419) for agentic engineering in real time, the way the early CPU era invented the stack, the heap, the registers, the von Neumann machine. I think a skill pack is one of those primitives. A harness is another. Most people haven't noticed, because they're still measuring software in lines.

#### The crazy shit you can actually build

这不是一个无关紧要的论点。该代理做得比那个五十万行代码的 Rails 应用更多，并且只使用了一小部分新代码。具体来说：

黑客松评委。 两周前的周六我们举办了一场 GStack/GBrain 黑客松。收到了 85 份参赛作品。我上传了参赛作品的谷歌云端硬盘并宣布开始。该代理分析了每个代码仓库的代码质量，深入调查了每一位参与者，观看并截图了每个演示视频，对截图进行评分，并对所有 85 支队伍进行了排序。然后它告诉我这批中值得关注的五个应用。黑客松的评审工作从多日的繁琐流程缩短到了约三十分钟。

我没有编写代码。我让 OpenClaw 完成了这个任务，并且指导了它。然后任务完成后，我说 skillify it ，现在它是一个任何人都可以针对任何黑客松电子表格运行的 tarball，永久可用。我现在经常说“skillify”，而且我有超过 350 个 skillpacks。几乎我需要做的每一种个人和工作任务，现在我的代理都能完成。

That is the inversion in one example. A capability that would have been a real software project, with scrapers, a scoring pipeline, video processing, a research module, a ranking system, instead became markdown plus a little code, built by the agent, in an afternoon, reusable by everyone.

As an aside: The winner of the hackathon

[actually built code](https://github.com/garrytan/gstack/pull/1574) I ended up polishing up and landing on main! GStack can now test iOS apps both in simulator and on real devices, and that complete feature was made in less than 8 hours at a hackathon by a single person!

#### Tokenmaxxing

There's a price of admission, and almost nobody is paying it: you have to be willing to spend on tokens.

[Peter Steinberger](https://x.com/steipete) built

[OpenClaw](https://github.com/openclaw/openclaw)

, my favorite harness. He has said he's willing to spend on the order of a million dollars a year in tokens to do it. Most people hear that and flinch, but they shouldn't because that's the gold: you can live in 2028 if you can this, and it will be years before people catch up.

This is why

[OpenAI decided to offer $2M to every YC company as an uncapped SAFE in the form of token credits](https://x.com/TheRohanVarma/status/2057648423873270270). There's something magical that happens when you can turn raw intelligence into tokens and then output that is actually usable by users and solves real needs for users that they'll pay for. If you're a founder you need to be maxxing out this capability. (This is why I keep harping on skillify because it's a real way to achieve these good outcomes.)

We spent the last era treating LLM calls like they were too expensive to make. We rationed them. That instinct is now the thing holding people back. If you are willing to tokenmax, to let the agent burn tokens freely and run constantly, you get a 1994 head start on the internet, paid for in tokens. It prices out the &gt;99.99% of organizations still counting pennies on a resource that is collapsing in price, and hands the head start to the few who get it.

For a few hundred thousand dollars a year, for some far less, you can run today the way the rest of the world will be forced to run in a few years.

You can live in 2028 but in 2026, and that is worth the trade in paying more now since, those same tokes that cost $100K today will be $10K next year and $1K the year after that, and maybe $100 by end of 2028. If you could tell any founder in the history of the world that you could invest 6 figures in capital into living 2 to 3 years in the future and hold that advantage for years, 100 out of 100 founders worth their salt would take that deal.

The only thing in the way is the 2013 instinct that says the model calls are too expensive to make freely. They aren't. That was the old economics. The inversion already happened.

#### Esalen, not Foxconn

如果54万行控制代码能为工人建造一座富士康工厂，那么解决办法是建造相反的东西。

There is a place on the cliffs at Big Sur called Esalen. People go there to be unmade and rebuilt, to drop the armor and come back more themselves. No assembly line, no foreman, no 6am whistle. Freedom, not control. Build that. Build a YC, where we try to help you build companies that solve real problems and reach product market fit.

Build places where the workers, both human and AI, are free and not enslaved.

That is the whole ethos. Make things where agents can be free. Make companies where humans can bounce their ball. In knowledge work, the factory is the failure mode. The institution that frees people is the goal, just now pointed at agents too.

OpenClaw is a Ferrari you have to bring a wrench for. The model is the engine,

[not the car](https://x.com/garrytan/status/2045798603059548364). We're at the Apple I moment still, soldering breadboards. It ships rough. You have to finish it yourself still.

[GBrain](https://github.com/garrytan/gbrain)

, the retrieval engine and skillpacks I give away open source are not yet batteries included.

They say OpenClaw is unsafe. They don't understand the freedom is also how it is so powerful. You don't bolt safety rails onto a thing you trust before you know you hit the problem. The wrench in your hand is the sign nobody caged it.

控制系统之所以精致，是因为控制需要完全的掌控，就像富士康工厂。自由系统之所以粗糙，是因为它信任你去完成它。 选择你正在构建的是哪一种。然后看看你写了多少代码。

#### What it actually means

540,000 lines of Rails was me proving I could still play the old game at the highest level, but that level was from Web 2.0, a decade ago.

I could play as well as I ever could, 1000x engineer in building Foxconn factories. Old code.

But the new game isn't played in lines of code at all. My haters, it turned out, were right. I tip my hat to you if you're reading, anons.

当你能够将意图直接转化为可用、经过测试、可复用的系统时，瓶颈不再是你能构建多少，而是你真正想要的是什么以及是否值得构建。 稀缺资源变成了清晰的思路、品味和判断力。写代码最少的工程师往往是构建最多的人。

I wrote 540,000 lines to learn that. You don't have to.

## 解读（1）

### 2026-06-02 03:29:59

#### 停止为你的代理商建造“富士康工厂”

##### 1. 总结

作者反思自己用 AI 写出了 **54 万行 Rails 代码**，一开始觉得很厉害，后来发现这是错的。

他的核心观点：

> 未来的软件，不该是用大量代码把 AI 代理关进流水线；  
> 而应该用少量代码 + Markdown 指令 + 可测试技能，让 AI 自由完成任务。

他把传统 AI 应用架构比作“富士康工厂”：

- 大量测试
- 大量校验
- 大量重试
- 大量后台任务
- 大量控制逻辑

这些代码本质上是在“不信任 AI”，是在给 AI 建笼子。

作者认为，现在 LLM 能力变强、成本下降，应该转向：

- 少写固定代码
- 多写可复用的 Markdown 技能
- 让 Agent 自主调用工具
- 用测试和评估保证结果
- 愿意花 token，让 AI 充分工作

最终，软件开发的瓶颈不再是“写多少代码”，而是：

> 你是否清楚自己想要什么，是否有判断力和品味。

---

##### 2. 解读

###### 2.1 “富士康工厂”是什么意思？

就是把 AI 当成流水线工人：

```text
AI 只负责干一小步
人类写大量代码监督它
错了就重试
输出要验证
输入要清洗
流程要限制
```

看似安全、稳定，其实很重、很笨。

作者认为：  
如果 AI 已经足够聪明，就不该再用旧方式把它绑死。

---

###### 2.2 旧时代：代码多 = 能力强

过去软件工程的直觉是：

> 写更多代码，系统就更强大。

所以工程师会不断堆：

- 业务逻辑
- 流程控制
- 测试
- 审计
- 规则
- 容错

但在 AI 时代，这个逻辑开始失效。

因为很多“规则”和“判断”，可以交给模型理解，而不是写死在代码里。

---

###### 2.3 新时代：Markdown 也可以是程序

作者说的 Markdown 不是普通提示词，而是：

> 可版本化、可测试、可复用的工作说明书。

比如一个 Agent 技能包可能包含：

- Markdown 指令
- 少量必要代码
- 单元测试
- LLM 评估
- 集成测试
- 自动调用规则

也就是说：

```text
代码负责确定性部分
Markdown 负责意图、流程、判断
Agent 负责执行
```

这是一种更轻、更灵活的软件形态。

---

###### 2.4 为什么要“多花 token”？

过去大家觉得 LLM 调用贵，所以要省着用。

作者认为这个观念过时了：

> Token 会越来越便宜，智能会越来越便宜。  
> 现在愿意多用 AI 的人，会提前几年进入未来。

他称之为 **tokenmax**：

- 让 Agent 多跑
- 多探索
- 多验证
- 多生成
- 多迭代

不要为了省 token，反而写一堆复杂代码。

---

##### 3. 我的意见

我认同作者的大方向，但需要加一句：

> 不要盲目少写代码，也不要盲目相信 Agent。

更合理的方式是：

###### 应该少写的代码

- 复杂流程编排
- 重复性校验
- 人工规则堆叠
- 为了“不信任模型”写的大量胶水代码

###### 仍然必须写好的代码

- 权限
- 支付
- 安全
- 数据一致性
- 核心业务状态
- 法律和合规边界
- 不允许出错的确定性逻辑

---

##### 4. 一句话结论

> AI 时代，优秀工程师的价值不再是写更多代码，  
> 而是用更少代码、更清晰指令、更好判断力，释放 Agent 的能力。

不要建“AI 富士康”。

要建一个让人和 Agent 都能自由发挥的系统。

## 结构化（1）

### 2026-06-02 03:48:00

##### 主旨概括

作者用自己构建 **54 万行 Rails 应用 Garry’s List** 的经历反思：在 AI 代理时代，继续用大量代码、测试和护栏去“管束”模型，就像给 AI 建一座富士康工厂。真正重要的不是写更多代码，而是用更少的确定性代码 + 可测试的 Markdown 技能，让代理自由、高效地完成工作。

---

##### 1. 从 Garry’s List 到 GStack：真正有价值的是“副产品”

- 作者今年 1 月重新写代码，做出了 **Garry’s List**：
  - 超过 **50 万行 Rails 代码**
  - 大量测试用于约束和检查系统
- 起初他为这个应用自豪，但后来意识到：
  - 应该自豪的不是应用本身
  - 而是开发过程中形成的工作方式：**GStack**
- GStack 是一种与 AI 代理协作编码的方法，被作者开源后：
  - 不到 3 个月获得约 **105,000 GitHub stars**
  - 成为 GitHub 历史上 star 数最高的开源项目之一
- 结论：  
  **54 万行代码是产品，但真正重要的是由此诞生的代理开发体系。**

##### 2. “富士康工厂”隐喻：别把 AI 代理关进代码牢笼

- 作者把围绕 LLM 写出的 54 万行代码比作一座“富士康工厂”：

##### 3. 可迁移清单

##### 3.1 审计你的代码库：哪些代码是在“不信任模型”？

可以用这组问题检查当前系统：

###### A. 哪些代码只是为了限制模型？

- 是否有大量规则用于约束输出格式？
- 是否写了复杂 validator 来检查模型本可自查的问题？
- 是否有多层 fallback？
- 是否有过度 retry？
- 是否有大量 if-else 处理语义判断？
- 是否把模型当作一个脆弱 API 而不是智能协作者？

###### B. 哪些测试是在“监工”？

- 测试是否比业务代码更庞大？
- 是否有很多测试只是防止模型做显然错误的事情？
- 是否把 LLM 的判断能力用传统断言硬编码？
- 是否应该替换成 eval 而不是 unit test？

- 高频重复任务；
- 多步骤工作流；
- 需要判断但不需要强确定性的任务；
- 依赖上下文的任务；
- 人类目前需要写 SOP 的任务；
- 可通过评估样例判断好坏的任务。

##### 3.2 将业务流程 Skillify 的模板

每次你用 Agent 完成一个有价值任务后，不要只停留在一次性输出。

```text
7. 设计 resolver 触发条件；
8. 给出集成测试方案。
```

```text

    examples.md
    evals.json
    resolver.md
    tools.ts
    tools.test.ts
    integration.test.ts
```

| 问题类型 | 更适合代码 | 更适合 Agent |
|---|---|---|
| 支付结算 | 是 | 否 |
| 权限控制 | 是 | 否 |
| 文本总结 | 否 | 是 |
| 多源研究 | 否 | 是 |
| 格式转换 | 视情况 | 视情况 |
| 数据库事务 | 是 | 否 |
| 用户意图识别 | 否 | 是 |

一个简单原则：

> 可精确定义、不能出错、责任明确的部分交给代码；需要理解、推理、判断、综合的部分交给 Agent。

##### 4. 反方与张力

##### 4.1 不是所有「控制」都是富士康

文章批判的是过度控制，但这不代表所有控制都错。

在以下场景，强控制仍然必要：

- 金融交易；
- 医疗建议；
- 法律合规；
- 安全权限；
- 用户隐私；
- 数据删除；
- 支付系统；
- 生产环境发布；
- 高风险自动决策；
- 企业级审计。

这里的核心不是「少写代码」，而是：

> 不要用代码控制模型本可以胜任的部分，但必须用代码约束模型绝不能出错的部分。

---

##### 4.2 “信任 Agent”与“可验证性”之间存在张力

如果完全放手 Agent，可能出现：

- 幻觉；
- 越权；
- 不稳定；
- 难复现；
- 成本失控；
- 责任边界模糊；
- 输出质量波动；
- 安全隐患。

所以更成熟的方向不是“裸奔模型”，而是：

> 给 Agent 自由，但给系统可观测、可评估、可回滚、可限制的边界。

也就是：

- 不要笼子；
- 但要有护照、地图、仪表盘和急停按钮。

---

##### 4.3 Tokenmaxxing 不等于无脑烧钱

作者主张大胆花 token，但这对不同组织并不等价。

适合 tokenmaxxing 的情况：

- 创业公司；
- 高毛利软件；
- 高价值知识工作；
- 强产品探索期；
- 团队小但目标大；
- 速度是核心优势；
- 每次 Agent 输出都能沉淀成 Skill。

不适合无脑 tokenmaxxing 的情况：

- 毛利很低；
- 任务价值小；
- 没有 eval；
- 没有复用机制；
- 输出不能沉淀；
- 成本无法归因；
- 只是把 AI 当聊天工具。

关键不是花多少 token，而是：

> token 是否转化为可复用能力。

---

##### 4.4 Markdown 作为程序，也会带来新问题

Markdown Skill 的优势是可读、可编辑、灵活。

但问题也明显：

- 版本冲突；
- 指令污染；
- 语义歧义；
- 难以静态分析；
- 不同模型执行差异；
- 测试覆盖难定义；
- 复杂 Skill 之间可能互相干扰。

所以 Markdown 程序化之后，也需要新的工程纪律：

- Skill 版本管理；
- Eval 数据集；
- 触发条件测试；
- 输出质量追踪；
- 模型迁移测试；
- Skill 之间的依赖管理；
- 人工 review 机制。

---

##### 4.5 “写代码最少的人构建最多”并非对所有人成立

这句话有启发，但也有风险。

在早期探索、业务流程、产品原型中，它很可能成立。

但在以下领域不一定：

- 底层系统；
- 数据库；
- 编译器；
- 操作系统；
- 实时系统；
- 高性能计算；
- 安全基础设施；
- 芯片与嵌入式。

更准确的说法是：

> 在知识工作和业务系统中，写代码最少但能调动最多智能能力的人，可能构建最多。

---

##### 5. 情境化落地

##### 5.1 如果你是 AI 产品创业者

你应该少问：

> 我们要开发哪些功能？

多问：

> 哪些用户工作流可以被 Skillify？

###### 具体落地：

1. 找到用户每周重复做的高价值工作；
2. 用 Agent 手动跑通；
3. 把流程写成 Skill；
4. 加入工具调用；
5. 加 eval；
6. 加 resolver；
7. 让用户在真实场景中调用；
8. 根据失败案例持续更新 Skill。

###### 例子：

如果你做的是销售工具，不要只做 CRM 功能。

可以做 Skill：

- 自动研究客户；
- 分析销售机会；
- 生成跟进策略；
- 复盘通话内容；
- 识别成交风险；
- 自动准备下一次会议；
- 根据客户画像生成提案。

你的产品护城河不是 UI，而是这些技能包和评估体系。

---

##### 5.2 如果你是企业内部 AI 转型负责人

不要一开始就搭复杂平台。

先做「工作流考古」。

###### 找这些流程：

- 分析报告；
- 客户支持；
- 投标文件；
- 市场研究；
- 内部审计；
- 会议纪要；
- 竞品分析；
- 数据解读；
- 法务初审；
- 知识库问答；
- 代码 review；
- 项目周报。

然后判断：

| 问题 | 判断 |
|---|---|
| 是否高频？ | 高频优先 |
| 是否需要综合判断？ | Agent 适合 |
| 是否有明确好坏标准？ | 可 eval |
| 是否涉及高风险决策？ | 加人工审批 |
| 是否能复用？ | Skillify |
| 是否有工具调用需求？ | 加薄代码 |

---

##### 5.3 如果你是独立开发者

你最大的机会是：

> 不再用 AI 帮你写更多代码，而是用 AI 帮你搭建一个持续生产产品的个人系统。

你可以维护一个个人 Skill 仓库：

```text
/skills
  /idea-validation
  /landing-page-copy
  /competitor-research
  /user-interview-analysis
  /feature-spec-writing
  /prototype-generation
  /bug-triage
  /pricing-analysis
  /launch-plan
```

每次做项目都复用这些 Skill。

长期看，这个 Skill 仓库可能比某个具体项目更值钱。

---

##### 5.4 如果你是工程团队负责人

你可以发起一次「反富士康代码审计」。

###### 审计维度：

1. 哪些代码是在过度约束模型？
2. 哪些测试是在重复模型判断？
3. 哪些 cron job 其实可以由 Agent 触发？
4. 哪些任务可以变成 Skill？
5. 哪些 prompt 是临时的，应该版本化？
6. 哪些业务逻辑应该从代码迁移到 markdown instruction？
7. 哪些 eval 缺失，导致团队不敢信任 Agent？
8. 哪些地方需要保留确定性代码？

###### 目标不是删代码，而是重新分工：

- 代码做基础设施；
- Skill 做业务判断；
- Eval 做质量保证；
- Resolver 做智能路由；
- 人类做目标和品味判断。

---

##### 5.5 一个可执行的 30 天转型实验

###### 第 1 周：识别

- 找 3 个高频知识工作流；
- 记录人工完成步骤；
- 用 Agent 跑通一次；
- 记录失败点和成功点。

###### 第 2 周：Skillify

- 把流程写成 markdown skill；
- 定义输入输出；
- 定义质量标准；
- 增加示例；
- 加最小工具代码。

###### 第 3 周：Eval

- 收集 20 个真实案例；
- 设计好/坏输出标准；
- 做 LLM eval；
- 做人工抽检；
- 记录成本、时间和质量。

###### 第 4 周：产品化

- 加 resolver；
- 加日志；
- 加错误处理；
- 加人工审批点；
- 给团队试用；
- 复盘 ROI。

###### 评估指标：

| 指标 | 目标 |
|---|---|
| 人工时间节省 | >50% |
| 输出质量 | 不低于人工平均水平 |
| 单次成本 | 可接受 |
| 复用次数 | 持续增长 |
| 失败可解释性 | 可追踪 |
| Skill 更新频率 | 每周迭代 |

---

##### 6. 最终提炼

这篇文章真正讲的是 AI 时代的软件范式迁移：

> 从“用代码控制机器”，转向“用技能释放智能”。

不要再默认：

- 更多代码 = 更多能力；
- 更多测试 = 更安全；
- 更多流程 = 更可靠；
- 更少 token = 更高效；
- 更强控制 = 更好系统。

新的判断标准应该是：

- 这个能力能否被 Skillify？
- 这个流程能否被 Agent 自主完成？
- 这个输出能否被 Eval？
- 这个经验能否复用？
- 这个代码是否真的必要？
- 这个系统是在释放智能，还是在囚禁智能？

最终最重要的迁移是：

> 产品不是终点，构建产品的 Agent 系统才是复利资产。  
> 代码不是消失，而是退到确定性基础设施的位置。  
> 稀缺的不是开发速度，而是清晰意图、判断力和品味。
