## 通俗精炼（1）

### 2026-10-10 00:47:47

#### OSC 7501：让终端知道程序是在工作，还是在等你

Mario Zechner 宣布，@pidotdev 的下一个版本将支持 OSC 7501；Rex 已有初步支持，相关回复还称 Claude Code v2.1.295 已支持该协议。**这项新规范的核心，是让程序用统一方式向终端报告自己的状态，而不只输出文字。** 它有望帮助终端及相关工具更清楚地显示任务进度，尤其是需要长时间运行、偶尔等待用户介入的 AI agent。

##### 它解决什么问题：有输出，不等于知道程序在做什么

引用推文的作者 Mitchell Hashimoto 发布了一个新的通用终端规范，让程序可以告诉终端自己当前处于哪种状态：

- **空闲**
- **工作中**
- **等待中**
- **已完成**
- **失败**

程序还可以报告相应的原因。

这里的“终端”，可以理解为承载命令行程序、显示其输入输出的界面。传统情况下，程序主要向终端输出文字；如果终端或外围工具想判断“任务还在跑吗”“是不是需要用户操作”，往往要尝试从这些文字中推断。

**OSC 7501 把这种“看输出猜状态”，变成了“程序直接报状态”。** 例如，一个程序长时间没有输出，既可能仍在计算，也可能正在等待用户确认。仅凭安静的界面很难分辨；如果程序明确报告“工作中”或“等待中”，接收它的工具就有了更可靠的判断依据。这是对协议作用的说明，并非原文展示的具体案例。

##### 它怎样起作用：程序报告，终端识别

OSC 是终端控制序列的一类，可以简单理解为：程序除了发送供人阅读的文字，也能发送供终端识别的特殊指令。OSC 7501 约定的就是程序状态信息。

它需要两端配合：**运行中的程序负责发送状态，终端或相关工具负责识别并使用这些状态。** 只支持其中一端，并不能形成完整体验。

Hashimoto 表示，双方实现起来都很容易。不过，原文没有提供协议格式、实现细节或开发成本，因此这里应理解为规范提出者对接入难度的判断，而不是已经验证过的普遍结论。

##### 当前进展：多个工具开始接入，但支持程度不同

原文给出的进展需要区分时间和成熟度：

| 工具 | 文中提到的支持情况 |
|---|---|
| @pidotdev | Mario Zechner 宣布，**下一个发布版本**将支持 OSC 7501 |
| Rex | 已有**初步支持** |
| Claude Code | Hashimoto 在相关回复中称，**v2.1.295 已支持** OSC 7501，并提到通过 Rex 验证了其可用性 |

Zechner 希望其他工具快速跟进。Hashimoto 则认为，Claude Code 的支持可能帮助数百乃至数千个下游应用。**这个规模是他对潜在收益的判断，不是文中已证明的实际采用数量。**

##### 为什么值得关注：统一状态接口，减少各自猜测

如果不同程序采用同一种状态表达方式，终端和外围工具就不必分别适配每个程序的输出文案，也不必靠“出现某句话”来猜测任务是否结束或需要介入。

对 AI agent 而言，这尤其有意义：它可能持续工作，也可能停下来等待用户输入。统一的状态信息可以成为任务状态展示、提醒或监控的基础。**但协议提供的是状态信息；具体是否显示提示、发送通知或支持远程监控，还取决于接收端如何实现。**

因此，这则消息更适合被理解为一个新协议开始获得多方支持的信号，而不是终端任务管理已经全面改善。原文附带的 Bun 功能预告、远程 agent 感想及广告，没有提供更多 OSC 7501 的机制或效果信息，不宜据此延伸结论。
